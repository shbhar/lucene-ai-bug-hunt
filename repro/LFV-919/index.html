Surround QueryParser.parse throws StackOverflowError instead of its declared ParseException on deeply nested groups (as few as about 740 levels, about 1.5 KB of query text, on a 1 MB thread stack)

Bug LFV-919Area: queryparser / surround (generated JavaCC parser, QueryParser.jj)Priority: lowImpact: wrong errorNovelty: new

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You call the surround parser's documented entry point QueryParser.parse(String), which declares only ParseException and already turns the lexer's TokenMgrError (an Error) into a ParseException, on a valid query with many nested groups, for example "(".repeat(d) + "a" + ")".repeat(d) or a long chain of "(a OR " groups, and expect a query or a ParseException. Instead the generated recursive-descent grammar, which spends seven frames per "(" (FieldsQuery -> OrQuery -> AndQuery -> NotQuery -> NQuery -> WQuery -> PrimaryQuery -> FieldsQuery) and has no depth bound, runs out of stack and java.lang.StackOverflowError escapes parse, so a caller that handles ParseException gets an undeclared Error. On a 1 MB thread stack as few as about 740 nested groups (1,473 chars) are enough on the first deep parse, and an 800-term chain of parenthesised binary ORs (7,884 chars, under the module's 1024-basic-query limit) fails even after JIT warm-up.

Expected vs actual

  • Expected: The test passes: it asserts the documented behaviour.
