AI-assisted bug hunt in Apache Lucene

Postings docIDRunEnd returns Integer.MIN_VALUE for dense blocks after a term's last level-1 skip block when doc IDs are within 8,192 (4,096 before 10.4) of 2^31, so CheckIndex at level 2 or higher reports a healthy segment of about 2^31 documents as corrupt

Bug LFV-170Area: codecs / postings reader (Lucene104 BlockPostingsEnum#docIDRunEnd, also the Lucene101 and Lucene103 readers); index / CheckIndexPriority: lowImpact: wrong errorNovelty: new

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You have one segment of about 2^31 documents (within about 8,000 docs of IndexWriter.MAX_DOCS) with a term whose postings are dense near the end of the doc-ID space, for example a term that every document has, and you call docIDRunEnd on its postings or run CheckIndex at level 2 or higher. You expect docIDRunEnd to return a doc ID greater than the current one, as its javadoc promises, and CheckIndex to pass. Instead, in the dense blocks after the term's last full 8,192-doc level-1 skip block (4,096 docs in 10.2-10.3), the default postings reader returns Integer.MIN_VALUE and CheckIndex reports the healthy segment as corrupt ('Run end -2147483648 is <= doc ID 2147475456'); query results stay correct, and the repro writes the postings through the public codec API rather than indexing 2^31 documents with IndexWriter.

The test shows that Lucene104 postings docIDRunEnd() on a dense 256-doc block that follows the term's last level-1 block, with doc IDs within 8,192 of 2^31, returns NO_MORE_DOCS + 1 = Integer.MIN_VALUE. The test is codec level: it writes 8,448 doc IDs with the postings writer.

Expected vs actual

Expected: docIDRunEnd() > docID() = 2147475456. Actual (-ea and -da): -2147483648.
