What it shows

The javadoc of ConcurrentMergeScheduler.AUTO_DETECT_MERGES_AND_THREADS, the automatic setting that an untouched IndexWriterConfig uses, says that the default maxThreadCount is max(1, min(4, cpuCoreCount/2)) and maxMergeCount is maxThreadCount + 5, so a reader expects at most 4 and 9. Since 10.0.0 the code sets max(1, cpuCoreCount/2), without the cap of four (#13294; deliberate, and stated in the 10.0.0 change list): on a JVM that reports 10 processors the scheduler's getters return 5 and 10 once an IndexWriter has been opened with the config, and on one that reports 64 they return 32 and 37, while at 9 they return the documented 4 and 9 (run on the 10.6.0 release jars, branch_11x 262e019500ec and main b5a4546a5964). Nothing runs wrong and the code is the intended side: the defect is the stale javadoc sentence. Lucene's own test of the default (TestConcurrentMergeScheduler.testNonSpinningDefaults, a LuceneTestCase) asserts threadCount <= 4, and for a LuceneTestCase suite the test framework sets the core count that the scheduler reads to a value from 1 to 4, where that bound holds with and without the cap.

Expected vs actual

  • Expected: getMaxThreadCount() returns 4, the number that the javadoc's formula max(1, min(4, cpuCoreCount/2)) gives at the test's core count of 10.
  • Actual: getMaxThreadCount() returns 5, the code's max(1, 10/2): java.lang.AssertionError: expected:<4> but was:<5>. The 5 is intended; the stale side is the javadoc sentence.

No code is wrong here: the finding is one javadoc sentence, and the half-the-processors default of the code is deliberate and stated in the 10.0.0 change list. What the test asserts is the documented formula, not a behaviour of the scheduler that is wrong: it sets the scheduler's own core-count system property (ConcurrentMergeScheduler.DEFAULT_CPU_CORE_COUNT_PROPERTY, 'lucene.cms.override_core_count') to 10 inside the test, opens an IndexWriter with an untouched IndexWriterConfig over a ByteBuffersDirectory, compares the scheduler's getMaxThreadCount() with 4, the value of the javadoc's max(1, min(4, cpuCoreCount/2)) at a core count of 10, and clears the property again. The getter returns 5, the value of the code's max(1, cpuCoreCount/2): java.lang.AssertionError: expected:<4> but was:<5>. Control: with the 9.12.3 release jars, whose code still has the cap of four, the same block reports 1 test successful, with and without assertions. The two formulas give the same number up to a core count of 9 (at 9 both give 4) and differ from 10 on: a probe program printed the documented limits at the core counts 1, 2, 3, 4, 8 and 9 and other limits at 10, 11, 16 and 64 on main b5a4546a5964, branch_11x 262e019500ec, 10.6.0 and 10.0.0, and the documented limits at all ten counts on 9.12.3; an SMT model of the two formulas (Z3, 32-bit integers) gives 10 as the smallest core count at which they differ. The test is a plain JUnit 4 class, not a LuceneTestCase, and draws nothing from the seed.
