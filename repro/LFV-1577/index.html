AI-assisted bug hunt in Apache Lucene › Repro tests › LFV-1577

Weight#matches of an interval query can throw ArrayIndexOutOfBoundsException for a matching document when one sub-source of an ordered, unordered or atLeast source has 13 or more sub-matches (for example a 13-term phrase followed by a term; run at seven sizes from 13 to 300), so a default UnifiedHighlighter call can fail when one of its hits is such a document; search, count and explain are unaffected

What it shows

You index the 14-word text 'a b c d e f g h i j k l m n' and ask Weight#matches for the interval query ordered(phrase(a ... m), term(n)), a 13-term phrase followed by a term; the default UnifiedHighlighter asks the same question when it highlights a hit of such a query. The document is a hit (count is 1), so you expect the one match at positions 0 to 13, as ordered(phrase(a ... l), term(m)), a 12-term phrase followed by a term, gives positions 0 to 12 on the same text. Instead the call throws java.lang.ArrayIndexOutOfBoundsException (Index 50 out of bounds for length 50) from CachingMatchesIterator.cache(), with and without assertions: the buffer that copies the sub-matches of each sub-source is grown only when 'count * 4 >= length', a test that is right only while the length is a multiple of 4, and after four growths the length is 50, so the 13th sub-match of one sub-source cannot be stored; the search itself is unaffected.

Expected vs actual

  • Expected: One match at positions 0 to 13: the document is a hit of the query (its count is 1).
  • Actual: weight.matches throws java.lang.ArrayIndexOutOfBoundsException: Index 50 out of bounds for length 50 at CachingMatchesIterator.cache(CachingMatchesIterator.java:54), assertions on and off.
