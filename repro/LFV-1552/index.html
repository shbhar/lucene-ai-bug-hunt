AI-assisted bug hunt in Apache Lucene › Repro tests › LFV-1552

ClassicTokenizer, WikipediaTokenizer and HTMLStripCharFilter throw IndexOutOfBoundsException on valid text when a supplementary character (for example an emoji) directly follows an unbroken run that has left exactly one free char in the scan buffer (run: one leading space and 4,095 letters from a StringReader for the two tokenizers): the refill of Lucene's default JFlex skeleton holds the lone first surrogate back and still reports new input (ClassicTokenizer in the releases run from 6.0.0, the other two from 4.10.0, to 10.6.0, and on branch_11x and main; known outside Lucene)

What it shows

You tokenize, with ClassicTokenizer at default settings, a valid text made of one space, a run of 4,095 letters, an emoji (U+1F600) and ' b', read from a java.io.StringReader. You expect the one token b: a run longer than the default maximum token length of 255 is skipped, and that is what the same text gives with 4,094 or 4,096 letters. Instead incrementToken() throws IndexOutOfBoundsException, with and without assertions: the scanner's 4,096-char buffer holds the 4,095 letters and has one free slot, the refill reads the first half of the emoji's surrogate pair into it, takes it back out because the pair is incomplete, and still reports new input, so the scanner asks for a character at the end of the buffered text. In the runs WikipediaTokenizer throws on the same text and HTMLStripCharFilter on 16,382 chars of text followed by '<p' and 16,383 chars of that tag before the emoji; IndexWriter.addDocument with ClassicAnalyzer passes the exception on, that document is not indexed and the writer stays usable; StandardTokenizer and UAX29URLEmailTokenizer did not throw on the text. Not new in 11: 10.6.0 fails the same test.
