AI-assisted bug hunt in Apache Lucene

CJKBigramFilter with outputUnigrams=false (its default) keeps its run of CJK characters across a non-CJK token when the next CJK token starts where the last CJK character ended, and can then leave a CJK character out of every term with no error (ICUNormalizer2CharFilter > StandardTokenizer > CJKBigramFilter on 月㏠, where the char filter turns ㏠ into '1日': the terms are 月 and 1, no 日) or emit a bigram behind that token whose start offset goes backwards, so that IndexWriter rejects the document (日日㋀日); run with ICUNormalizer2CharFilter in front of StandardTokenizer and of ICUTokenizer and with a MappingCharFilter rule in front of StandardTokenizer; outputUnigrams=true and the stock CJKAnalyzer, which has no char filter, showed neither

Finding LFV-1587Area: analysis / CJK (CJKBigramFilter behind a char filter that turns one source character into a non-CJK token and a CJK token; a chain the application builds)Priority: lowImpact: silent wrong resultsNovelty: known outside Lucene

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You build an analyzer with ICUNormalizer2CharFilter in front of StandardTokenizer and CJKBigramFilter and index the text 月㏠, in which the char filter turns the day symbol ㏠ (U+33E0) into '1日'. You expect the document to hold the term 日, as it does when you index the already normalized text 月1日 (terms 月, 1 and 日): the class javadoc says 'when a CJK character has no adjacent characters to form a bigram, it is output in unigram form'. Instead the document is indexed with no error and holds only the terms 月 and 1: the digit gets a zero-width offset, 日 starts where 月 ended, and the filter appends 日 to a run that the digit has already interrupted and then emits it neither in a bigram nor as a unigram; with two CJK characters in front (日日㋀日) it emits the bigram 日月 behind the digit with a start offset that goes backwards, and IndexWriter.addDocument throws IllegalArgumentException.

Expected vs actual

  • Expected: You expect the document to hold the term 日, as it does when you index the already normalized text 月1日 (terms 月, 1 and 日): the class javadoc says 'when a CJK character has no adjacent characters to form a bigram, it is output in unigram form'.
  • Actual: The document is indexed with no error and holds only the terms 月 and 1: the digit gets a zero-width offset, 日 starts where 月 ended, and the filter appends 日 to a run that the digit has already interrupted and then emits it neither in a bigram nor as a unigram; with two CJK characters in front (日日㋀日) it emits the bigram 日月 behind the digit with a start offset that goes backwards, and IndexWriter.addDocument throws IllegalArgumentException.

The chain is one that the application builds: a char filter that turns one source character into a digit and a CJK character (here ICUNormalizer2CharFilter with its default normalizer), a tokenizer, and CJKBigramFilter with outputUnigrams=false, its default. The stock CJKAnalyzer, which has no char filter, and outputUnigrams=true showed neither outcome in the runs. Which characters: with the default normalizer a run over all 1,112,064 code points found 68 (the telegraph symbols for months, days and hours: U+32C0 to U+32CB, U+33E0 to U+33FE, U+3358 to U+3370), and in the runs the character had to stand directly behind a CJK character (with no CJK character in front of it, or with a space between the two, neither outcome showed). Known outside Lucene: the downstream bug report elastic/elasticsearch#50008 (open when read on 2026-11-23) reports the second outcome, the rejected document, with ICUTokenizer in the chain; the silent outcome, which this test shows, is not in that report. What the test does: it builds an Analyzer with ICUNormalizer2CharFilter in front of StandardTokenizer and CJKBigramFilter, indexes one document with the text 月㏠ (the char filter turns ㏠, U+33E0, into '1日') and expects docFreq of the term 日 to be 1, as for the already normalized text 月1日. The document is indexed with no error and docFreq is 0: java.lang.AssertionError: expected:<1> but was:<0>. The second outcome, the rejected document (日日㋀日 behind the same chain: IndexWriter.addDocument throws IllegalArgumentException, 'offsets must not go backwards startOffset=1,endOffset=3,lastStartOffset=2'), is not what this test runs; two probe programs and a test showed it on branch_11x 262e019500ec, main b5a4546a5964 and 10.6.0. The block names every jar that the run needs: ICU4J is the third-party jar of the analysis-icu module (Maven Central, com.ibm.icu:icu4j; version 79.1 on main and on branch_11x, 77.1 for 10.6.0); without it the run reports 1 test failed with java.lang.NoClassDefFoundError: com/ibm/icu/text/Normalizer2$Mode, which is not the finding. The test is a LuceneTestCase: its input has no randomness, the test framework draws its environment from the seed, and the outcome was the same under each seed that was run. On a branch_11x checkout set V=11.0.0-SNAPSHOT; for the release, set V=10.6.0 and ICU=77.1 and use the five 10.6.0 jars from Maven Central (org.apache.lucene: lucene-core, lucene-codecs, lucene-test-framework, lucene-analysis-common, lucene-analysis-icu) in place of the five $LUCENE jars. For the Gradle alternative at the end of this page the module is lucene/analysis/icu: with the test copied to lucene/analysis/icu/src/test/org/apache/lucene/analysis/icu/ it reports 1 test completed, 1 failed, with the same message, on branch_11x 8e4ee3d41386 and on main 3cee9ed259e9, with -Ptests.asserts=true and with -Ptests.asserts=false.
