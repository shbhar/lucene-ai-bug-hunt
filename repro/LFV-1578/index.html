SortedSetDocValuesFacetCounts and ConcurrentSortedSetDocValuesFacetCounts count a FacetsCollector that visited exactly one segment of a multi-segment reader in that segment's ordinals, so its counts can land on other labels with no error; the merged collector of the stock FacetsCollectorManager counted right in the runs

Finding page for LFV-1578

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You search a six-segment index (one document a segment: a=x in the first five, a=z in the sixth) with an IndexSearcher that has an executor, give each slice of the search its own stock FacetsCollector through your own CollectorManager, count each collector with SortedSetDocValuesFacetCounts and add the counts. You expect x=5 z=1, which the merged collector of the stock FacetsCollectorManager gives on the same searcher. Instead the sum is x=6 z=0, with no error, with and without assertions. The collector of the second slice visited one segment, and for a list of exactly one per-segment record the counter leaves out the reader's ordinal map ('matchingDocs.size() > 1') and uses the segment's own ordinal 0 (z, its only label) as the reader's ordinal 0 (x); with the documents in the other order (z first) the same search counts right, because the segment's ordinals then agree with the reader's.

Expected vs actual

  • Expected: x=5 z=1: the six hits carry x five times and z once, and the merged collector of the stock FacetsCollectorManager counts that on the same searcher.
  • Actual: x=6 z=0 (org.junit.ComparisonFailure: expected:<x=[5 z=1]> but was:<x=[6 z=0]> at line 78), with no exception from Lucene, assertions on and off.

Run it

  • Tested on Lucene main b5a4546a5964 (a commit of 2026-11-22): still reproduces.
  • Not new in 11.0: the test fails the same way with the 10.6.0 release jars, on a build of branch_11x (262e019500ec) and on Lucene main (b5a4546a5964), with and without assertions. What the test does: it indexes six documents with a commit after each and NoMergePolicy, which gives six one-document segments (the facet label a=x in the first five, a=z in the sixth), and searches them with a query that matches every document through IndexSearcher.search(Query, CollectorManager), on a searcher whose executor runs each slice on the calling thread; default slicing makes two slices here, the first five segments and the sixth. Its own CollectorManager gives each slice a stock FacetsCollector, counts each collector by itself with SortedSetDocValuesFacetCounts and adds the counts; the test expects x=5 z=1. The run reports 1 test found and 1 test failed, with org.junit.ComparisonFailure: expected:<x=[5 z=1]> but was:<x=[6 z=0]>; Lucene itself throws no exception. The commands below print one run, with assertions off; with -ea -esa in place of -da -dsa -Dtests.asserts=false the outcome is the same. The test has no random() call of its own; the test framework draws its environment (the codec and the directory among other things) from the seed, and the outcome was the same under each seed that was run. On a branch_11x checkout set V=11.0.0-SNAPSHOT; for the release, set V=10.6.0 and use the four 10.6.0 jars from Maven Central (org.apache.lucene: lucene-core, lucene-codecs, lucene-test-framework, lucene-facet) in place of the four $LUCENE jars. For the Gradle alternative at the end of this page the module is lucene/facet: with the test copied to lucene/facet/src/test/org/apache/lucene/facet/sortedset/ it reports 1 test completed, 1 failed, with the same message, on branch_11x 262e019500ec and on main b5a4546a5964, with -Ptests.asserts=true and with -Ptests.asserts=false.
