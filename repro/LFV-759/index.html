AI-assisted bug hunt in Apache Lucene

IndexWriter accepts doc-values updates of a field that a custom index-sort key reads (such as a BinarySortField subclass that derives its key from another doc-values field), so the segment keeps its old order while still declaring the index sort: CheckIndex rejects it, sorted searches that terminate early return wrong top hits, and merges carry the disorder forward

Bug LFV-759Area: index / IndexWriter doc-values updates with index sorting (BinarySortField, custom IndexSorter)Priority: lowImpact: data corruptionNovelty: new

Bug page for LFV-759

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You configure an index sort with a BinarySortField subclass whose key is derived from another doc-values field (sort by the numeric field price, ties broken by the binary field sku, declared on sku), index a(5), b(7), c(8), and then change c's price to 1 with updateNumericDocValue; you expect the writer either to reject the update, as it rejects an update of sku itself ('cannot update docvalues field involved in the index sort'), or to keep the segment sorted. Instead the update is accepted, the segment stays in the order a, b, c while still declaring the sort, CheckIndex reports 'segment has indexSort=<binary: "sku"> but docID=1 sorts after docID=2', and a top-1 search sorted by the index sort returns a instead of c because it stops at the first non-competitive document. The cause is that IndexWriterConfig#setIndexSort protects only the SortField#getField names, while a custom index sort may read any field.

IndexWriter accepts updateNumericDocValue of the field a BinarySortField subclass derives its index-sort key from, so the segment keeps its old order while still declaring the sort.

Expected vs actual

Expected: the update is rejected (as it is for the sort's own field) or the segment stays sorted; actual: CheckIndex reports segment has indexSort=<binary: "sku"> but docID=0 sorts after docID=1.
