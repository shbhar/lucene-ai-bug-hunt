AI-assisted bug hunt in Apache Lucene

PassageSelector.pickBest (MatchHighlighter) silently drops the highlight passages of permitted ranges that start after offset 0 when maxPassageWindow is Integer.MAX_VALUE: the int window shift 'to += range.from - from' wraps negative, so the second and later values of a multi-valued field lose their snippets (the residue of the LUCENE-10135 overflow fix)

Bug LFV-387Area: highlighter / matchhighlight PassageSelector (MatchHighlighter, FieldValueHighlighters)Priority: lowImpact: silent wrong resultsNovelty: known upstream

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You highlight a document whose stored field has two values, 'aaaa foo' and 'bbbb foo', for the query text:foo with MatchHighlighter and FieldValueHighlighters.highlighted(Integer.MAX_VALUE, 10,...), meaning 'no limit on the passage size', and expect both values highlighted, [aaaa >foo<, bbbb >foo<], as a window of 1000 gives. Instead you get only [aaaa >foo<], with no error: PassageSelector.pickBest centres each window in long arithmetic but then shifts it into the value's range with the int statement 'to += range.from - from', which wraps negative for a range that starts after offset 0, so the match in the second value gets no passage. If only the second value matches, both values come back unhighlighted ([bbbb bar, aaaa foo] instead of [aaaa >foo<]).

Expected vs actual

  • Expected: The test passes: it asserts the documented behaviour.
  • Actual: You get only [aaaa >foo<], with no error: PassageSelector.pickBest centres each window in long arithmetic but then shifts it into the value's range with the int statement 'to += range.from - from', which wraps negative for a range that starts after offset 0, so the match in the second value gets no passage.
