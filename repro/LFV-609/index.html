AI-assisted bug hunt in Apache Lucene

matchhighlight PassageFormatter closes crossing markers in opening order instead of innermost first, so per-marker end strings come out mis-nested (e.g. '<a>one <b>two</a></b><b> three</b>' instead of '<a>one <b>two</b></a><b> three</b>')

Bug LFV-609Area: highlighter / matchhighlight: PassageFormatter multi-marker formatting (crossing markers with per-marker end strings; also end to end through MatchHighlighter, FieldValueHighlighters.highlighted and MatchHighlighter.QueryOffsetRange)Priority: lowImpact: minorNovelty: new

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You format the passage 'one two three' with two crossing markers, [0,7) written as <a>...</a> and [4,13) as <b>...</b>, using PassageFormatter's Function constructor, or you highlight the crossing phrase queries 'one two' and 'two three' with MatchHighlighter.highlight(topDocs, q1, q2) and one tag per query. You expect well-nested output, '<a>one <b>two</b></a><b> three</b>', because when a marker ends the formatter closes and re-opens the markers opened after it precisely to resolve the overlap into nested markup (Passage javadoc: markers 'can be overlapping or nested'). Instead it closes those markers in opening order rather than innermost first and returns '<a>one <b>two</a></b><b> three</b>' (end to end '<q1>one <q2>two</q1></q2><q2> three</q2>'), which an XML parser rejects.

Expected vs actual

  • Expected: You expect well-nested output, '<a>one <b>two</b></a><b> three</b>', because when a marker ends the formatter closes and re-opens the markers opened after it precisely to resolve the overlap into nested markup (Passage javadoc: markers 'can be overlapping or nested').
  • Actual: It closes those markers in opening order rather than innermost first and returns '<a>one <b>two</a></b><b> three</b>' (end to end '<q1>one <q2>two</q1></q2><q2> three</q2>'), which an XML parser rejects.
