AI-assisted bug hunt in Apache Lucene

A multi-segment kNN query's optimistic second pass, when cut short by the IndexSearcher timeout, replaces the hits a complete first pass already found, so a later timeout can return fewer or farther hits than an earlier one, down to 0 hits

Bug LFV-117Area: search / kNN query rewrite (AbstractKnnVectorQuery optimistic re-entry pass) under the IndexSearcher timeoutPriority: lowImpact: silent wrong resultsNovelty: known upstream

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You set a timeout with IndexSearcher#setTimeout and run a kNN query on an index with several segments; Lucene searches every segment once and, if that first pass completed, searches the segments that supplied the best hits a second time to improve the answer. You expect a timeout to give you the partial results found so far ('Return partial results only when timeout is met', AbstractKnnVectorQuery.java:296), so hits that the complete first pass already found are kept. Instead, when the timeout fires during the second pass, each re-entered segment's cut-short second-pass result (usually empty) replaces its first-pass hits, so the query keeps fewer or farther hits than a slightly earlier timeout would have given, down to 0 hits (IndexSearcher#count goes 6 -> 0 when one more timeout check is allowed).

Expected vs actual

  • Expected: You expect a timeout to give you the partial results found so far ('Return partial results only when timeout is met', AbstractKnnVectorQuery.java:296), so hits that the complete first pass already found are kept.
