AI-assisted bug hunt in Apache Lucene

With assertions enabled, the default UnifiedHighlighter fails an assertion in OffsetsEnum.OfMatchesIteratorWithSubs (its source comment: 'miOE should follow cached entries') when a span clause and another clause of a disjunction match the same token (body:qu* OR spanTerm(body:quick) on 'the quick brown fox'): AssertionError with -ea, the expected snippet without assertions

Finding LFV-1491Area: highlighter / UnifiedHighlighter (Matches-based offsets, HighlightFlag.WEIGHT_MATCHES, the default since 9.0.0)Priority: lowImpact: minorNovelty: new

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You highlight the text 'the quick brown fox' with the default UnifiedHighlighter for the query body:qu* OR spanTerm(body:quick), in a JVM that runs with assertions enabled. You expect 'the <b>quick</b> brown fox', which is what the same two clauses in the other order return and what a JVM without assertions returns. Instead the call throws an AssertionError without a message from Lucene's own assert statement, whose source comment reads 'miOE should follow cached entries': both clauses match the token 'quick', and the highlighter's queue puts the prefix clause's match ahead of the span clause's cached sub-match, an order that the queue's comparator allows and the assert rules out. With assertions off, which is how production JVMs run, the same call returns the expected snippet: for this query nothing is wrong there.

Expected vs actual

  • Expected: the <b>quick</b> brown fox, as the other clause order and a JVM without assertions return.
  • Actual: java.lang.AssertionError at OffsetsEnum$OfMatchesIteratorWithSubs.nextWhenMatchesIterator(OffsetsEnum.java:216), with assertions on.

It asserts the snippet 'the <b>quick</b> brown fox'. With assertions on, as in the recipe (-ea -esa), the highlight call throws java.lang.AssertionError, without a message, from Lucene's own assert statement in OffsetsEnum.OfMatchesIteratorWithSubs.nextWhenMatchesIterator (OffsetsEnum.java:216 on main) before the test's own check runs; 'miOE should follow cached entries' is the comment on that source line, not a message in the output. With assertions off (-da -dsa -Dtests.asserts=false) the test passes: the highlighter returns the expected snippet. For this finding a passing run without assertions is the expected outcome and does not mean that the finding is gone.
