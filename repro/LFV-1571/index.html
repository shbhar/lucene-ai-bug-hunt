AI-assisted bug hunt in Apache Lucene › Repro tests › LFV-1571

On Lucene 3.4.0 to 10.6.0 SynonymMap.Builder.build() can hand its keys to the FST out of order when one key holds an unpaired surrogate: the synonym rule of another, well-formed word can then never fire in the map that build() returns, with no error when assertions are off, or build() can throw ArrayIndexOutOfBoundsException (run: five one-word rules behind a filter that cuts every word to its first UTF-16 unit, the stock TruncateTokenFilter from 4.8.0 on, fail with and without assertions on each of the 136 releases that were run; a second set of five rules throws with assertions off on each of the 55 releases from 8.4.0; branch_11x and main, both unreleased, no longer have that code)

Fixed upstream: #16834 (commit 2eb462541b1c), merged 2026-10-13; also on branch_11x (the same commit). On released lines only (3.4.0 to 10.6.0): main no longer had the failing code when the finding was listed.

What it shows

You load five well-formed synonym rules (for 'a', the fullwidth letter U+FF21 and three emoji) through SolrSynonymParser with an analyzer that cuts every word to its first UTF-16 unit (WhitespaceTokenizer and TruncateTokenFilter.truncateAfterChars(1)), and you expect the fullwidth letter, which is one unit long and is never cut, to be replaced by its synonym. Instead, on Lucene 10.6.0 with assertions off it comes back unchanged and nothing throws (with assertions on, build() stops at the FST compiler's internal assertion 'inputs are added out of order'), and a second set of five rules makes build() throw ArrayIndexOutOfBoundsException with assertions off. The cut turns the three emoji into keys that are unpaired surrogates; SynonymMap.Builder.build() sorts its keys with a comparator that places such a key behind U+E000 to U+FFFF but hands the FST the keys' code points, where it belongs in front, so the FST is built from keys that are out of order (FSTCompiler.add: 'The provided input must be sorted after the previous one according to IntsRef#compareTo'; the compiler checks the order by an assertion only) and a lookup can miss a key that is stored in it (in the run the root node holds the label of U+FF21 and the lookup of it returns nothing). The same rules, in a form adapted to each release's API, fail on each of the 136 releases from 3.4.0 to 10.6.0 that were run (with the stock filter from 4.8.0 on) and pass on 10.6.0 when the filter cuts by code point, so that no pair is split, or when only the sort of build() is replaced by a comparison of code points; branch_11x and main (both unreleased) pass: there build() sorts by code point since Alan Woodward's #16834, a removal of the deprecated comparator whose description, comment, review and changelog entry (read on 2026-11-23) name no defect, and the paper that the comparator's own comment links (Markus W. Scherer, 'UTF-16 String Comparison in Code Point Order') notes that its fix-up 'may yield unexpected results for malformed UTF-16 strings with single, unpaired surrogate code units'.

Expected vs actual

  • Expected: The text U+FF21 analyzes to the one token y: its rule U+FF21 => y is in the map.
  • Actual: On 10.6.0 with assertions off the token comes back unchanged and Lucene throws nothing: org.junit.ComparisonFailure: term 0 expected:<[y]> but was:<[U+FF21]> (the console prints the fullwidth letter itself). With assertions on, build() stops at java.lang.AssertionError: inputs are added out of order lastInput=[ff21] vs input=[d83c].
