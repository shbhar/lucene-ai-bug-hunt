AI-assisted bug hunt in Apache Lucene

SortedSetDocValues faceting builds its facet tree from the byte order of the encoded paths, so a label or dimension name that equals a sibling's name followed by a character below U+001F (TAB, CR, LF, or the U+001E that FacetsConfig writes when it escapes U+001E/U+001F) moves a label's children under that sibling, or drops a whole dimension or one of its labels

What it shows

You index hierarchical SortedSetDocValues facets, for example cat/shoes/red in one document and cat/'shoes<TAB>' (an untrimmed input) in another, and expect getTopChildren(10, 'cat', 'shoes') to return red=1, as taxonomy faceting does for the same labels. Instead it returns null and the leaf 'shoes<TAB>' reports red=1: the encoded paths sort by byte, a character below the path delimiter U+001F places 'shoes<TAB>' between 'shoes' and 'shoes U+001F red', and the reader state infers parent, child and sibling links only from the order of consecutive ordinals. The same happens for a label that contains U+001F or U+001E (FacetsConfig escapes both with U+001E), and dimension names such as 'd' next to 'd<TAB>' make dimension d disappear or, for a flat multiValued + requireDimCount dimension, lose one label, all with no error.

Expected vs actual

  • Expected: getTopChildren(10, "cat", "shoes") returns red (1) and "shoes<TAB>" has no children; dimension color lists red; tag reports value 2 with b=2, a=1.
  • Actual: shoes returns null while "shoes<TAB>" reports red (1) (the same with "shoes\u001F"); color returns null; tag reports value 1 with only b=2.
