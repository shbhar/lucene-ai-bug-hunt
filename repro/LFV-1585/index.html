AI-assisted bug hunt in Apache Lucene

The javadoc of StandardQueryParser#setEnablePositionIncrements and of CommonQueryParserConfiguration#setEnablePositionIncrements says 'Default: false.'; a StandardQueryParser as its constructors build it has position increments enabled since 4.0.0 (LUCENE-4109), and with a StandardAnalyzer whose stop filter removes 'the' it parses the phrase "quick the fox" to f:"quick ? fox", where the parser with the setter called with false gives f:"quick fox", as run on the 4.0.0 and 10.6.0 release jars, branch_11x and main (documentation defect; the code is the intended side)

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

The javadoc of StandardQueryParser#setEnablePositionIncrements, and of the same method on the interface CommonQueryParserConfiguration, ends with 'Default: false.': you expect, by the javadoc's default, a parser that was never configured to build a phrase query without the position gap of a removed stop word. Instead, since 4.0.0 the parser's constructor enables position increments (LUCENE-4109; deliberate, and listed in the 4.0.0-BETA change list under 'Changes in Runtime Behavior'): a StandardQueryParser built with either constructor returns true from getEnablePositionIncrements(), and with a StandardAnalyzer whose stop filter removes 'the' it parses the phrase "quick the fox" to f:"quick ? fox", where the parser with the setter called with false builds f:"quick fox" (run on the 10.6.0 release jars, branch_11x 262e019500ec and main b5a4546a5964; the 4.0.0 release jars build the same two queries). Nothing runs wrong and the code is the intended side: the defect is the stale javadoc sentence, in two places, and the two queries differed only where a stop filter removed a word before the phrase's last term (a trailing removed word, a phrase without a removed word and the same words outside quotes gave equal queries). Each of the six stock classes that implement the interface returns true when built the plain way (run on the same three builds), and the javadoc of the setter that the classic parser inherits says 'Default: true.'.

Expected vs actual

  • Expected: You expect, by the javadoc's default, a parser that was never configured to build a phrase query without the position gap of a removed stop word.
  • Actual: Since 4.0.0 the parser's constructor enables position increments (LUCENE-4109; deliberate, and listed in the 4.0.0-BETA change list under 'Changes in Runtime Behavior'): a StandardQueryParser built with either constructor returns true from getEnablePositionIncrements(), and with a StandardAnalyzer whose stop filter removes 'the' it parses the phrase "quick the fox" to f:"quick ? fox", where the parser with the setter called with false builds f:"quick fox" (run on the 10.6.0 release jars, branch_11x 262e019500ec and main b5a4546a5964; the 4.0.0 release jars build the same two queries).
