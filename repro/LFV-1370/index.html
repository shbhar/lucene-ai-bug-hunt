Classic Highlighter: QueryScorer weights a term that several clauses name by clause order (the last term clause wins, the first span or phrase clause wins) instead of using the highest weight, so two equal() queries whose clauses differ only in order pick different best fragments (the classic-Highlighter sibling of #15434)

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You highlight a text with the classic Highlighter and QueryScorer using two BooleanQuery objects that are equal() and differ only in clause order: (f:alpha)^5 (f:beta)^3 f:alpha and f:alpha (f:beta)^3 (f:alpha)^5. You expect the same best fragment for both, the one with alpha, because alpha's highest weight 5 beats beta's 3 (the rule that QueryScorer's own WeightedSpanTerm[] constructor, QueryTermScorer and, since #15434, the FastVectorHighlighter follow). Instead WeightedSpanTermExtractor keeps the weight of the term clause it visits last (and of the first span or phrase clause), so alpha gets weight 1 for the first query and its best fragment is the one with beta (' <B>beta</B>' for the repro's text 'alpha beta'), with no error.

Expected vs actual

  • Expected: Both queries give the best fragment <B>alpha</B>.
  • Actual: q1 gives <B>beta</B>: ComparisonFailure: expected:<[<B>alph]a</B>> but was:<[ <B>bet]a</B>>, with no other error.
