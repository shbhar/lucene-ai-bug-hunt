FlatBitVectorsScorer's RandomVectorScorerSupplier.copy() does not copy the vector values, so the copy's scorers read the original ByteVectorValues and the concurrent merge workers of HnswBitVectorsFormat (numMergeWorkers > 1) share one OffHeapByteVectorValues and its IndexInput (regression of #14181, since 10.2.0)

What it shows

You index bit vectors with HnswBitVectorsFormat set up for concurrent merges (numMergeWorkers > 1 and an executor), and each merge worker gets scorerSupplier.copy(), which RandomVectorScorerSupplier documents as 'will copy the underlying vectorValues so the copy is safe to be used in other threads'. Instead, FlatBitVectorsScorer's supplier makes a copy of the values in its constructor (targetVectors) and never uses it: scorer() reads the original vectorValues and copy() wraps that same instance, so all workers read one shared, non-thread-safe OffHeapByteVectorValues and its IndexInput. The one-test repro shows it directly (a scorer from supplier.copy() makes 2 reads on the original values instead of 0, on main with -ea and -da and on 10.2.0 to 10.6.0, while 10.1.0 passes); in a concurrent merge the race gives occasionally wrong build-time scores.

Expected vs actual

  • Expected: The scorer from supplier.copy() reads only its own copy of the values: 0 reads on the original.
  • Actual: java.lang.AssertionError: expected:<0> but was:<2>: both reads, in setScoringOrdinal(0) and score(1), went to the original.
