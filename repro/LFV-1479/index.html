AI-assisted bug hunt in Apache Lucene

Geo3DPoint.newPolygonQuery and Geo3DDocValuesField.newOutsidePolygonSort throw IllegalArgumentException ('give up on tiling') for a valid polygon with a hole whose outer ring cannot be tiled, because Geo3DUtil.fromPolygon still calls the GeoPolygonFactory overload that cannot fall back to GeoComplexPolygon when holes are present

Finding LFV-1479Area: spatial3d / Geo3DPoint polygon queries and Geo3DDocValuesField outside-polygon sort (Geo3DUtil.fromPolygon, GeoPolygonFactory.makeGeoPolygon)Priority: lowImpact: minorNovelty: known upstream

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You build a Geo3DPoint polygon query for a small rectangle with a hole (about 220 m x 110 m at latitude 5, with one more vertex in the middle of its southern edge). You expect to get a query, as for the same rectangle without the hole. Instead Geo3DPoint.newPolygonQuery throws IllegalArgumentException 'Two adjacent edge planes are effectively parallel despite filtering; give up on tiling' while the query is built. Geo3DDocValuesField.newOutsidePolygonSort fails the same way. The same rectangle without the hole works, and so does the polygon with its hole through Geo3DPoint.newLargePolygonQuery: Lucene has a second way to build such a polygon, but the ordinary polygon query cannot switch to it when the polygon has a hole.

Expected vs actual

  • Expected: You expect to get a query, as for the same rectangle without the hole.
  • Actual: Geo3DPoint.newPolygonQuery throws IllegalArgumentException 'Two adjacent edge planes are effectively parallel despite filtering; give up on tiling' while the query is built.
