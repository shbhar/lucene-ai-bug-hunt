Panama minMaxScalarQuantize rounds differently from the default implementation at one boundary value

Finding LFV-071Area: codecs / vectorsPriority: lowImpact: minorNovelty: new

Finding page for LFV-071

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You scalar-quantize vectors with the Panama vector provider. You expect the same bytes as the default implementation. Instead Panama rounds with (int)fma(x, scale, 0.5f), not Math.round, so the two can differ only when fl(scale*x) == 0.49999997f.

The test shows that with the Panama vector provider (>= 256-bit vectors), ScalarQuantizer(0, 1, 8).quantize rounds a value whose scaled offset is 0.49999997f up to byte 1, where Math.round (the default provider, the "nearest byte") gives 0.

Expected vs actual

Expected: dest[0] == 0; actual (-ea and -da, preferredBitSize=256): expected:<0> but was:<1>; on 128-bit hosts or without the vector module the test passes.

The adapted test calls Lucene's internal vectorized method directly, with the arguments the public method passes, and Lucene's test switch tests.vectorsize makes the JVM run it with 256-bit vectors; so adapted, the test fails 1 of 1 with the same message (expected:<0> but was:<1>), with and without assertions, on each of these builds and with the 10.6.0 release jars, and without the switch it passes.
