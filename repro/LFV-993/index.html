AI-assisted bug hunt in Apache Lucene

On main, a field-sorted TopFieldCollectorManager with numHits >= ArrayUtil.MAX_ARRAY_LENGTH (e.g. Integer.MAX_VALUE) throws OutOfMemoryError instead of the IllegalArgumentException that 10.x throws, because since #14873 FieldValueHitQueue.create allocates the numHits-sized sort comparators before the PriorityQueue size check runs (unreleased regression of the SOLR-5661 guard)

Bug LFV-993Area: core / search: field-sorted top-N collection (FieldValueHitQueue, TopFieldCollectorManager)Priority: lowImpact: wrong errorNovelty: new

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You call new TopFieldCollectorManager(sort, Integer.MAX_VALUE, null, 1).newCollector with any sort (a long field, a string field, Sort.RELEVANCE), directly or through SortRescorer.rescore(searcher, topDocs, Integer.MAX_VALUE), and expect the IllegalArgumentException 'maxSize must be >= 0 and < 2147483631' that Lucene 4.7.0 to 10.5.2 and the 10.6 RC throw, and that main's score-ordered TopScoreDocCollectorManager still throws. On main you get OutOfMemoryError 'Requested array size exceeds VM limit' instead ('Java heap space' at 2147483631 with a 1 GB heap). Since #14873, FieldValueHitQueue.create builds the sort comparators, each of which pre-allocates a numHits-sized array, before it calls the PriorityQueue constructor, whose size check exists to prevent exactly this confusing OutOfMemoryError (SOLR-5661).

The test shows that on main new TopFieldCollectorManager(sort, Integer.MAX_VALUE, null, 1).newCollector() with a LONG sort allocates the numHits-sized comparator in FieldValueHitQueue.create before PriorityQueue's size check runs (regression from #14873).

Expected vs actual

Expected: PriorityQueue's IllegalArgumentException ('maxSize must be >= 0 and < 2147483631'), as in 4.7.0-10.5.2. Actual: OutOfMemoryError: Requested array size exceeds VM limit.
