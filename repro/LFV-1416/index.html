FSTCompiler.add passes the input's length where Arrays.mismatch expects an end index, so an IntsRef input with a non-zero offset gets a too-short shared prefix and the compiled FST silently lacks that key (unreleased regression on main from #13924)

Finding LFV-1416Area: util / FST (FSTCompiler.add: the shared-prefix computation)Priority: lowImpact: minorNovelty: new

Finding page for LFV-1416

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You build an FST with FSTCompiler, add "ab" -> 1, then add "ac" -> 2 passed as an IntsRef slice that starts at offset 2 of a larger int[] (new IntsRef(new int[] {0, 0, 'a', 'c'}, 2, 2)), compile, and look up "ac"; IntsRef is documented as a slice (offset + length), add() only requires IntsRef#compareTo order, and 10.6.0 returns 2. On main, add() computes the shared prefix with Arrays.mismatch(lastInput.ints(), 0, lastInput.length(), input.ints, input.offset, input.length), whose last argument is an exclusive end index, so it compares an empty range, freezes the 'a' node of "ab" too early and gives the root a second arc labelled 'a'. With assertions off compile() returns normally and Util.get("ac") returns null ("ab" still answers 1); with -ea an assertion fires inside add().

Expected vs actual

  • Expected: Util.get(fst, "ac") returns 2.
  • Actual: null with assertions off (expected:<2> but was:<null>); an AssertionError inside add() with assertions on.
