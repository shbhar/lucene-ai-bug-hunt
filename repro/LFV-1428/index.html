MutableValue.compareTo orders values of different classes by subtracting the two classes' hash codes, so on a JVM whose identity hash codes can be negative (OpenJ9 by default) the int difference overflows and the order is not transitive; since 4.0.0-alpha

Finding LFV-1428Area: util / mutable values (MutableValue.compareTo: the cross-class branch subtracts Class.hashCode values)Priority: lowImpact: minorNovelty: new

What it shows

You compare MutableValues of different classes, for example a MutableValueBool, a MutableValueDouble and a MutableValueInt, with the public compareTo that MutableValue takes on by implementing Comparable<MutableValue>. You expect a consistent order: compareTo deliberately orders different classes (by class hash code, with a class-name tie-break), and Comparable requires that a < b and b < c imply a < c. On OpenJ9 with default settings, whose identity hash codes are negative or positive, the order can be cyclic instead (Bool < Double < Int, but Bool > Int), because 'c1.hashCode() - c2.hashCode()' overflows int (-1728369406 - 1684571406 = -3412940812 wraps to +882026484); on HotSpot identity hashes are non-negative 31-bit values, so it never fails there.

Expected vs actual

  • Expected: For every triple of the seven values, a < b and b < c imply a < c, so the test passes.
  • Actual: On OpenJ9 it fails in most test JVM runs, e.g. AssertionError: MutableValueBool(class hash -101469850) < MutableValueDouble(class hash 1374148567) < MutableValueInt(class hash -2045993973); on HotSpot it passes.

Run it

  • Tested on Lucene main f794ff5a505c (2026-11-06): reproduced.
  • Run the java command below with the java of an OpenJ9 JDK or JRE 25 (default settings), whose identity hash codes can be negative; the classes may be compiled with any JDK 25. On HotSpot the test passes. Each run gets new class hash codes, so one OpenJ9 run fails about 9 times in 10.
  • How to read the outcome: a failing test is the finding reproducing (the failure message states expected against actual).
  • Seeds: a rerun with the same seed replays the same random choices. Assertions off (-da -dsa -Dtests.asserts=false) is the production-like setting.
# Lucene checkout at the tested commit, built with: ./gradlew --no-daemon assemble   (JDK 25)
LUCENE=/path/to/lucene; V=12.0.0-SNAPSHOT
CP=$LUCENE/lucene/core/build/libs/lucene-core-$V.jar
CP=$CP:$LUCENE/lucene/codecs/build/libs/lucene-codecs-$V.jar
CP=$CP:$LUCENE/lucene/test-framework/build/libs/lucene-test-framework-$V.jar
CP=$CP:randomizedtesting-runner-2.9.2.jar:junit-4.13.2.jar:hamcrest-3.0.jar   # test-framework dependencies (Maven Central)
CP=$CP:junit-platform-console-standalone-6.1.3.jar   # JUnit Platform console launcher (Maven Central)

javac -d classes -cp "$CP" $(find src -name '*.java')

# run 1: assertions on, seed DEADBEEF, default flags
java -ea -esa --add-modules jdk.incubator.vector --enable-native-access=ALL-UNNAMED -Dtests.seed=DEADBEEF \
