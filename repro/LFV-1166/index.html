Outputs.skipFinalOutput's default calls skipOutput, not readFinalOutput as its javadoc says, so an Outputs subclass with its own final-output encoding makes Util.get and FSTEnum.seekExact silently miss keys that are in the FST

Finding LFV-1166Area: util / FST (Outputs.skipFinalOutput default; FST.findTargetArc list-node scan)Priority: lowImpact: minorNovelty: new

Finding page for LFV-1166

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You write an Outputs<Long> that delegates everything to PositiveIntOutputs except writeFinalOutput and readFinalOutput, which store final outputs as a fixed 8-byte long, and you keep skipFinalOutput, whose javadoc says it 'defaults to just calling readFinalOutput and discarding the result'; you build an FST from a=5, ab=3, b=7 with the default FSTCompiler.Builder and call Util.get(fst, "b"). You expect 7, but get null, with or without assertions (BytesRefFSTEnum.seekExact("b") misses the same way). The default body actually calls skipOutput, the regular-output decoder, so the linear scan of the root list node in FST.findTargetArc skips one byte of arc a's 8-byte final output, loses its place in the node and gives up.

Expected vs actual

  • Expected: Util.get(fst, "b") returns 7.
  • Actual: expected:<7> but was:<null>, with assertions on and off.
