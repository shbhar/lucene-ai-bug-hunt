AI-assisted bug hunt in Apache Lucene

MoreLikeThisQuery ignores its moreLikeFields and searches only fieldName, so the XML parser's <LikeThisQuery fieldNames="a,b"> searches only the first field (documents similar through the other fields are silently missed, every release since 6.1.0)

Bug LFV-556Area: queries / mlt (MoreLikeThisQuery.rewrite over MoreLikeThis.like(String, Reader...)) x queryparser / xml (LikeThisQueryBuilder)Priority: mediumImpact: silent wrong resultsNovelty: known upstream

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You build a MoreLikeThisQuery for the text 'zebra quokka' with moreLikeFields {title, body} (or parse <LikeThisQuery fieldNames="title,body">zebra quokka</LikeThisQuery>) on an index where those words occur only in body, and expect the documents whose body contains them, because the javadoc says moreLikeFields are the 'fields used for similarity measure' and the XML DTD calls fieldNames a 'Comma delimited list of field names'. Instead the query rewrites to terms of fieldName only (title, the first listed field on the XML path), here an empty query, so it matches 0 documents instead of 2; the field list changes nothing about matching or scoring (only equals and hashCode), and on the XML path the result depends on the order of the list ('title,body' 0 hits, 'body,title' 2). Up to 6.0.1 each word went to the listed field with the highest document frequency; LUCENE-6954 (6.1) made MoreLikeThis's Reader path use only the field it is given, and MoreLikeThisQuery, which uses that path, was never adapted.

Expected vs actual

  • Expected: The test passes: it asserts the documented behaviour.
  • Actual: The query rewrites to terms of fieldName only (title, the first listed field on the XML path), here an empty query, so it matches 0 documents instead of 2; the field list changes nothing about matching or scoring (only equals and hashCode), and on the XML path the result depends on the order of the list ('title,body' 0 hits, 'body,title' 2).

Run it

  • Tested on Lucene main ea57360912ed (2026-10-24): reproduced.
  • How to read the outcome: a failing test is the bug reproducing (the failure message states expected against actual).
  • Seeds: a rerun with the same seed replays the same random choices. Assertions off (-da -dsa -Dtests.asserts=false) is the production-like setting.
# Lucene checkout at the tested commit, built with: ./gradlew --no-daemon assemble   (JDK 25)
LUCENE=/path/to/lucene; V=11.0.0-SNAPSHOT
CP=$LUCENE/lucene/core/build/libs/lucene-core-$V.jar
