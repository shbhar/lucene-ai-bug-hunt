AI-assisted bug hunt in Apache Lucene

UnifiedHighlighter from the default builder can print its internal value separator U+0000 inside a snippet of a multi-valued field, when a phrase match that runs from the end of one stored value into the next opens the passage (run: values 'one bravo three' and 'four bravo six', position gap 3, phrase "three four" with slop 3: 'one bravo <b>three\u0000four</b>')

Finding LFV-1561Area: highlighter / UnifiedHighlighter passage bounds on multi-valued fields (FieldHighlighter.highlightOffsetsEnums: the end of a passage that a match opens)Priority: lowImpact: minorNovelty: known outside Lucene

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You store two values in one text field, 'one bravo three' and 'four bravo six', and highlight the phrase query "three four" with a UnifiedHighlighter from the default builder; the phrase matches across the two values because its slop of 3 equals the analyzer's position gap (run also with StandardAnalyzer, whose gap is 0, and an exact two-word phrase across the values 'john smith' and 'jones mary'). You expect highlighted text from the stored values, without an internal separator, as in Lucene's own test of the same document, where another match opens the passage and the highlight of the phrase ends at the value end ('one <b>bravo</b> <b>three</b>... four <b>bravo</b> six'). Instead the snippet is 'one bravo <b>three\u0000four</b>' (in the test of the repro folder, which is the StandardAnalyzer run with the values 'john smith' and 'jones mary': 'john <b>smith\u0000jones</b>'): the highlighter joins the values with an internal U+0000, and when the match that opens a passage itself crosses that separator, FieldHighlighter stretches the passage at least to the end of the match, so the default formatter prints the separator inside the highlight tags and, for this document, stops in the middle of the second value. The search itself is not involved (the hit is found before highlighting starts); not new in 11.0 (the 10.6.0 release gives the same snippet); known outside Lucene (an Elasticsearch issue of 2025 shows this output, and that project replaced the separator in its own formatter).
