AI-assisted bug hunt in Apache Lucene

FacetsConfig writes the bare dimension term of a flat multiValued + requireDimCount SortedSetDocValues dimension without escaping it, so a dimension name containing U+001F or U+001E is read back as a different path: the dimension loses one label and reports that label's count as its own, a phantom dimension appears, a name with two U+001F makes facet-state construction throw for the whole field, and (-ea) a name ending in U+001E throws AssertionError

Bug LFV-597Area: facet / SortedSetDocValues faceting (FacetsConfig.processSSDVFacetFields path encoding with DELIM_CHAR U+001F / ESCAPE_CHAR U+001E, decoded by DefaultSortedSetDocValuesReaderState)Priority: mediumImpact: silent wrong resultsNovelty: new

Bug page for LFV-597

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You index three documents under a flat SortedSetDocValues facet dimension named 'color<U+001F>code', configured multiValued and requireDimCount, with labels {x, y}, {x} and {z}, and expect getTopChildren to return value=3 with x=2, y=1, z=1, as taxonomy faceting does for the same name. Instead it returns value=2 with only y=1 and z=1, and getAllDims also shows a phantom dimension 'color' with label 'code'. FacetsConfig escapes U+001F/U+001E in every facet term except this one bare dimension term (FacetsConfig.java:494), while the reader decodes every term as if it were escaped, so the raw term is read back as a different path.

Expected vs actual

  • Expected: For every name: value=3 childCount=3 x=2 y=1 z=1 and getAllDims lists only that dimension, as for the plain name color.
  • Actual: color\u001Fcode: value=2 childCount=2 y=1 z=1, dims [color, color\u001Fcode]; a\u001Fb\u001Fc: IllegalArgumentException; 4 of 5 tests fail, with assertions on and off.
