Monitor HighlightsMatch drops a hit when another hit has the same positions but different offsets (for example shingles or multi-word synonyms), because HighlightsMatch.Hit.compareTo ignores offsets

Bug LFV-915Area: monitor / HighlightsMatch hit set (Hit.compareTo used as TreeSet identity)Priority: lowImpact: silent wrong resultsNovelty: new

Bug page for LFV-915

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You register a query such as wi OR "wi fi" (or the prefix query wi*, or guinea OR cavy with a 'guinea pig => cavy' synonym rule) in a Monitor whose analyzer stacks tokens at one position, match a document with HighlightsMatch.MATCHER, and expect both hits that Weight#matches reports: for 'wi fi' with ShingleFilter(2,2) and unigrams these are 0(0)->0(2) for 'wi' and 0(0)->0(5) for 'wi fi'. Instead HighlightsMatch keeps only one of them and getHitCount is 1, because Hit.compareTo compares start and end positions only and the hits are kept in TreeSets, which treat compareTo == 0 as a duplicate, although Hit's own equals (a record over all four fields) says the two hits differ. Which hit survives depends on clause order, and the same root cause makes getHits(field).contains(...) ignore offsets and lets HighlightsMatch.equals return true for two objects whose hashCodes differ.

Expected vs actual

  • Expected: Both hits at the stacked position: [0(0)->0(2), 0(0)->0(5)] for wi fi and [0(0)->0(6), 0(0)->0(10)] for guinea pig, getHitCount 2; contains and equals respect offsets.
  • Actual: One hit each, [0(0)->0(2)] and [0(0)->0(10)], getHitCount 1; contains ignores offsets, and two different matches are equal with hash codes 4564 and 6480.
