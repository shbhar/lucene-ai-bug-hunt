Automaton.copy while the receiver's current state is still open silently overwrites a copied state's transitions once that state is finished, because finishing it shrinks its block in place and moves the transition write position back into the copied block

Finding LFV-1313Area: util / automaton (Automaton.copy, finishState)Priority: lowImpact: minorNovelty: new

Finding page for LFV-1313

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You build an Automaton by hand: state 0 gets arcs 'a' and 'b' to state 1; while state 0 is still the state being built you append a small automaton x (0 -x-> 1, accepting) with copy, which becomes states 2 and 3, and then add state 1's arc 'c' to state 2, which by the class javadoc finishes state 0. You expect 0 -[a-b]-> 1 -c-> 2 -x-> 3, which accepts "acx", exactly what you get if you call finishState() before copy. Instead the automaton silently rejects "acx": finishing state 0 merges its two arcs into one in place and moves the transition write position back into the copied block, so state 1's new arc overwrites copied state 2's arc (state 2 now reads 2 -c-> 2 and state 3 is unreachable).

Expected vs actual

  • Expected: The automaton is 0 -[a-b]-> 1 -c-> 2 -x-> 3, run("acx") returns true, and the test passes.
  • Actual: run("acx") returns false: AssertionError at line 33 (the assertTrue), with assertions on and off, no exception from Lucene.
