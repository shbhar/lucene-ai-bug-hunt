Document suggester with skipDuplicates=true and an index-time synonym returns fewer than n distinct suggestions (n=2 drops one that n=3 returns), because Util.TopNSearcher drops its queue before the last result although acceptPartialPath can still reject that path, and NRTSuggester sizes the queue from entries per analyzed form, which ignores synonym graph paths

What it shows

You index suggestions through a CompletionAnalyzer with an index-time synonym (b => xb, keeping the original, so 'a b' is indexed as 'a b' and 'a xb'), add a second suggestion 'a xc', and call SuggestIndexSearcher.suggest(prefix 'a', 2, skipDuplicates=true); you expect the two distinct suggestions [a b/10, a xc/3], which n=3 does return. Instead you get only [a b/10]: Util.TopNSearcher sets its queue to null for the last result when maxQueueDepth == topN, assuming the last path always completes, but the duplicate filter (acceptPartialPath) rejects that path when it reaches 'a xb', so the sibling arc that leads to 'a xc' is never queued and the search ends early (called directly, TopNSearcher even reports isComplete=true for such a search). NRTSuggester makes the queue that small because it counts entries sharing one analyzed form, not the analyzed paths per suggestion that its javadoc describes, so a synonym never enlarges it; with two synonyms (b => {xb, yb}) the duplicate paths fill the queue and both n=2 and n=3 lose a suggestion.

Expected vs actual

  • Expected: You expect the two distinct suggestions [a b/10, a xc/3], which n=3 does return.
  • Actual: You get only [a b/10]: Util.TopNSearcher sets its queue to null for the last result when maxQueueDepth == topN, assuming the last path always completes, but the duplicate filter (acceptPartialPath) rejects that path when it reaches 'a xb', so the sibling arc that leads to 'a xc' is never queued and the search ends early (called directly, TopNSearcher even reports isComplete=true for such a search).
