AI-assisted bug hunt in Apache Lucene

UnifiedHighlighter and MatchRegionRetriever throw IllegalArgumentException on a MultiReader whose indexes differ in any field's schema, even only in norms or in an unrelated field, because FieldInfos.getMergedFieldInfos applies the single-index consistency check across the indexes

Finding LFV-602Area: highlighter / uhighlight + matchhighlight: default offset-source choice on composite readers (core index FieldInfos.getMergedFieldInfos)Priority: mediumImpact: crashNovelty: known outside Lucene

AI-assisted finding, confirmed by automated checks, not yet triaged by a human Lucene committer. This site files nothing upstream.

What it shows

You build two indexes in which a field is declared slightly differently, for example 'body' with norms in one and without norms in the other (both with offsets), open them together as new MultiReader(r1, r2), search body:alpha and get both hits. You expect UnifiedHighlighter.highlight("body", query, topDocs) to return both snippets ('<b>alpha</b> beta', '<b>alpha</b> gamma'), as it does when both indexes use the same options or when each index is highlighted on its own. Instead it throws IllegalArgumentException 'cannot change field "body" from omitNorms=false to inconsistent omitNorms=true' (and 'cannot change field "tag" ...' when only an unrelated field differs), because the default offset-source choice builds FieldInfos.getMergedFieldInfos over the whole MultiReader, which applies the per-index field-consistency check across the two indexes; MatchRegionRetriever's default strategies fail the same way.

Expected vs actual

  • Expected: You expect UnifiedHighlighter.highlight("body", query, topDocs) to return both snippets ('<b>alpha</b> beta', '<b>alpha</b> gamma'), as it does when both indexes use the same options or when each index is highlighted on its own.
  • Actual: It throws IllegalArgumentException 'cannot change field "body" from omitNorms=false to inconsistent omitNorms=true' (and 'cannot change field "tag" ...' when only an unrelated field differs), because the default offset-source choice builds FieldInfos.getMergedFieldInfos over the whole MultiReader, which applies the per-index field-consistency check across the two indexes; MatchRegionRetriever's default strategies fail the same way.
