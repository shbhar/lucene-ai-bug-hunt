AI-assisted bug hunt in Apache Lucene

Formal models and scripts: signed-zero-equals-hashcode-remaining-query-valuesource-sort-sites

Tools: Python

These are the working models and scripts this part of the hunt used. Some encode the code as it is (a counterexample is the expected result), others a fixed or correct variant; read the header comment of each file. Paths inside them were replaced by placeholders such as $LUCENE (a Lucene checkout) and $WORK.

Findings

  • spatial3d Vector (and so GeoPoint and the Geo3DPoint distance and box queries), Plane and the longitude-slice and degenerate latitude/longitude shapes compare doubles with == in equals() but hash Double.doubleToLongBits, so objects built with 0.0 and -0.0 are equal yet have different hash codes (since 5.2.0) (finding LFV-1341; repro · finding page)
  • Six function value sources (ConstValueSource, DoubleConstValueSource, LinearFloatFunction, ScaleFloatFunction, RangeMapFloatFunction, ReciprocalFloatFunction) and CommonTermsQuery's minimum-should-match fractions compare float/double parameters with == in equals() but hash their bits, so objects built with 0.0 and -0.0 are equal yet have different hash codes (since 4.0.0) (finding LFV-1335; repro · finding page)
  • BlendedTermQuery.DisjunctionMaxRewrite, LatLonPoint.newDistanceFeatureQuery and XYDocValuesField.newDistanceSort compare float/double parameters with == in equals() but hash their bits, so objects built with 0.0 and -0.0 are equal yet have different hash codes (since 5.3.0) (finding LFV-1337; repro · finding page)
