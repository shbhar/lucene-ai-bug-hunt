The finding in 30 seconds

#

pickBest reserves a queue slot for every passage you might ask for before it looks at a single match. A text with one match can only ever fill one slot, yet Integer.MAX_VALUE asks for 2,147,483,647 slots, and Lucene's PriorityQueue refuses any size from 2,147,483,631 up.

Background: matchhighlight passages

#
  1. MatchHighlighter (package org.apache.lucene.search.matchhighlight) highlights query matches in stored field values. For each field with matches, FieldValueHighlighters.highlighted(maxPassageWindow, maxPassages, ...) asks a PassageSelector for the best passages.
  2. PassageSelector.pickBest(value, markers, maxPassageWindow, maxPassages) centres a window of at most maxPassageWindow characters on each match (a marker), keeps the best candidates in a PriorityQueue, removes overlaps and returns at most maxPassages passages.
  3. Lucene's PriorityQueue has a fixed capacity chosen when it is created: it allocates capacity + 1 slots up front and throws for a capacity of 2,147,483,631 or more.

The finding, step by step

#
  1. Highlight the text lucene search, which has one match (lucene, offsets 0-6): pickBest("lucene search", List.of(new OffsetRange(0, 6)), 20, Integer.MAX_VALUE), with a 20-character window and Integer.MAX_VALUE meant as "all passages".
  2. You expect the one passage 0-13 around the match: maxPassages = 1, 10, 16 and 1000 all return exactly that.
  3. You get IllegalArgumentException: maxSize must be >= 0 and < 2147483631; got: 2147483647. MatchHighlighter with FieldValueHighlighters.highlighted(20, Integer.MAX_VALUE, ...) fails the same way on a field with a match.
  4. Why: before it reads a match, pickBest creates its PriorityQueue with Math.max(16, maxPassages) slots. That queue allocates every slot up front and refuses a size of 2,147,483,631 or more, yet it never receives more than one passage per match.
  5. Large values below that limit return the right passage but allocate for maxPassages, not for the matches: 552 bytes at 10, 4 MiB at 2^20, 64 MiB at 2^24; at 3*10^8 a 1 GiB heap runs out.

Who is affected

#

Applications that highlight with matchhighlight (MatchHighlighter with FieldValueHighlighters.highlighted, or PassageSelector directly) and pass Integer.MAX_VALUE as "all passages", or forward a large count without a bound. Default settings; ordinary counts work. The error is loud and results are never wrong; large accepted values cost memory on every call.

Mechanism, terms and numbers538 words

PassageSelector.pickBest(value, markers, maxPassageWindow, maxPassages) picks the best highlight passages of a field value; MatchHighlighter reaches it through FieldValueHighlighters.highlighted, which passes maxPassages on unchanged. Before it reads a single match, pickBest builds its PriorityQueue with Math.max(16, maxPassages) slots, and PriorityQueue allocates maxSize + 1 slots up front and rejects any maxSize of 2,147,483,631 or more. So maxPassages = Integer.MAX_VALUE (meant as "all passages") throws IllegalArgumentException on every call with a non-empty value and a non-zero window, even for one match, where maxPassages = 10 returns the one passage. Everywhere else in the method maxPassages only caps the result, and the queue never receives more passages than there are (split) matches, so the extra capacity never changes the result. Large values below the limit work but allocate in proportion to maxPassages: 64 MiB per call at 2^24 for one match. The sizing came with the class in 2020, so every release that ships matchhighlight (9.0.0 to 10.6.0) and main is affected. Default settings; the failure is loud and results are never wrong.

The code (main 645d4fe14a20, lucene/highlighter/.../matchhighlight/)

  • Entry points. PassageSelector.pickBest(value, markers, maxPassageWindow, maxPassages) (PassageSelector.java:67-74) delegates to the five-argument overload (:76-84). Neither has javadoc. No argument is validated.
  • The pre-size. After the early return for an empty value or a zero window (:87-89): int pqSize = Math.max(16, maxPassages); (:93), then PriorityQueue<Passage> pq = PriorityQueue.usingComparator(pqSize, passageScorer); (:96), and only then markers = splitOrTruncateToWindows(...) (:98).
  • PriorityQueue. The class javadoc says it "pre-allocates an array of length {@code maxSize+1}" (PriorityQueue.java:34-35; the class is @lucene.internal). The constructor throws IllegalArgumentException("maxSize must be >= 0 and < " + ArrayUtil.MAX_ARRAY_LENGTH + ...) for maxSize >= ArrayUtil.MAX_ARRAY_LENGTH ("Throw exception to prevent confusing OOME", :121-125), otherwise allocates new Object[maxSize + 1] (:129-134). MAX_ARRAY_LENGTH is Integer.MAX_VALUE - NUM_BYTES_ARRAY_HEADER, 2,147,483,631 on the tested JVM.
  • maxPassages is otherwise only a cap. The selection loop makes at most one insertWithOverflow per split marker (:103-166, insert at :158); the result is clamped by last = Math.min(last, maxPassages); (:213); with no candidate, pickDefaultPassage stops at defaultPassages.size() >= maxPassages (:289). So once the queue can hold every split marker, more capacity cannot change the result.

Exposure and likelihood215 words
  • What goes wrong. Integer.MAX_VALUE (anything from 2,147,483,631 up) fails every pickBest call on a non-empty value with a non-zero window, even when nothing matches, and so every MatchHighlighter call on a document with a match in a highlighted field (a field without a match never reaches pickBest). The message names the internal queue size, not the argument the caller passed.
  • Large accepted values. They return the right passages but allocate about 4 bytes per unit of maxPassages on every call (64 MiB at 2^24); with a 1 GiB heap, 3*10^8, 10^9 and 2^31 - 18 end in OutOfMemoryError (3*10^8 and 10^9 pass with 4 GiB; 2^31 - 18 also runs out with 2 GiB). Concurrent calls multiply the allocation.
  • Scale. None needed: one 13-character value with one match. Fixed input, assertions on or off.
  • Workaround. Pass a finite count. Once maxPassages is at least the number of matches (counted after splitting at value boundaries) and the number of field values, a larger value changes nothing.
  • How likely: rare. A code search found no use of matchhighlight's PassageSelector in Solr or Elasticsearch; Integer.MAX_VALUE fails on the first call, so a developer meets it in testing and picks a finite count; no public report was found in the documented searches since the class shipped in 9.0.0.

Why it looks unintended

#
  • Elsewhere maxPassages only caps the result, and the queue never holds more than one passage per match.
  • The same method is meant to accept Integer.MAX_VALUE as its window size; the package documents it as "all" for maxHitsPerField.
  • The sizing was meant to keep queue overhead low (#11990); 64 MiB for one match defeats that, and the fix keeps it.
The full argument338 words
  • Cap semantics. last = Math.min(last, maxPassages) (PassageSelector.java:213) and defaultPassages.size() >= maxPassages (:289) work at Integer.MAX_VALUE; the queue cannot receive more entries than there are split markers (:103-166).
  • The other "max" argument, meant to accept Integer.MAX_VALUE. LUCENE-10135 (#334, Dawid Weiss, 2021, in 9.0.0) fixed an overflow for a huge maxPassageWindow, and the upstream test TestPassageSelector.largeWindow passes Integer.MAX_VALUE as the window (TestPassageSelector.java:159-162). A residual window-shift overflow at that window, for permitted ranges after offset 0, is a separate, already known bug.
  • Package convention. MatchRegionRetriever's maxHitsPerField: "The predicate should return {@link Integer#MAX_VALUE} for all hits to be considered" (MatchRegionRetriever.java:230-233).
  • The module's other passage API. The UnifiedHighlighter documents maxPassages as "The maximum number of top-N ranked passages" (UnifiedHighlighter.java:757) and bounds its queue with Math.min(64, maxPassages + 1) (FieldHighlighter.java:143; its own wrap at Integer.MAX_VALUE is a separate bug).
  • Tests. Upstream TestPassageSelector uses maxPassages from 1 to 100 (100 in checkEmptyExtra, checkOddOverlaps and defaultPassages, TestPassageSelector.java:40, :48, :57, :69, :195; randomIntBetween(1, 10) in its random test, :322); nothing says large values are unsupported.
  • History. The class was created in 2020 with new PriorityQueue<>(maxPassages), when the queue capacity was the only cap on the result. #11990 (Alan Woodward, 2022, 9.5.0) added the explicit clamp at :213. In that review Dawid Weiss wrote that capping the queue at the requested maximum was "a deliberate decision ... so that regardless of how many markers there are, the overhead of the pq remains fairly low" and suggested min(markers.size(), maxPassages * 3); Alan Woodward proposed the floor of 16 instead, and it was merged. Large maxPassages was never discussed.
  • Precedent. LUCENE-2119 (2009), opened by Michael McCandless about IndexSearcher.search(q, Integer.MAX_VALUE): "This trips users up fairly often because they assume our PQ doesn't statically pre-allocate (a reasonable assumption...)". The fix capped the count at maxDoc in the layer that knew the real bound; here pickBest knows it, the number of split markers.
The devil's-advocate check200 words

The strongest case for "works as designed" (a reviewer from another model family and an intended-behaviour devil's advocate): sizing by maxPassages was a deliberate #11990 choice to keep queue overhead low; PriorityQueue documents its pre-allocation, and SOLR-5661 added its size guard on purpose so that impossible sizes fail loudly; core top-N collectors (new TopScoreDocCollectorManager(Integer.MAX_VALUE, ...)) and the classic Highlighter.getBestFragments(..., Integer.MAX_VALUE) fail the same way; and nothing documents maxPassages at all.

Why it fails: the stated goal was low overhead, and the fix is never larger than today's queue; the pre-allocation note sits on a @lucene.internal class that a pickBest caller is not expected to read; for the core collectors, IndexSearcher itself caps the count at Math.max(1, maxDoc) before it builds the collector manager (IndexSearcher.java:588-599; search(q, Integer.MAX_VALUE) returns 1 hit where a direct TopScoreDocCollectorManager(Integer.MAX_VALUE, ...) throws), the layer that knows the bound applies it, and here that layer is pickBest, which already holds every marker; and the same method and package treat Integer.MAX_VALUE as a legal "no limit" value. The argument bears on priority (a Low robustness fix), not on whether the call should work. A maintainer may still prefer a javadoc note (see Suggested fix).

Suggested fix

#

Recommended A. Split the markers first, then size the queue by the split count

Split the markers first, then size the queue by them: Math.max(16, Math.min(maxPassages, markers.size())) (+5/-4 lines in PassageSelector). The queue is never larger than today's, and results are the same for every value that works today. With it, the minimal test and all 723 highlighter tests pass.

markers = splitOrTruncateToWindows(markers, maxPassageWindow, permittedPassageRanges);

// minimum priority queue size of 16 so that small maxPassages values don't
// return too few passages due to subsequent passage merges. At most one passage
// is collected per (split) marker, so the queue never needs to be larger than that.
int pqSize = Math.max(16, Math.min(maxPassages, markers.size()));

// Best passages so far.
PriorityQueue<Passage> pq = PriorityQueue.usingComparator(pqSize, passageScorer);

Three options. Option A was validated with gradle in a scratch worktree at 645d4fe14a20 and by translation validation against the stock class; B and C were not executed. Credit: the shape of A (bound the queue by the marker count) is what Dawid Weiss suggested in the #11990 review; the floor of 16 it keeps is Alan Woodward's.

A. Split the markers first, then size the queue by the split count (validated by the checks) (recommended)

#

In PassageSelector.pickBest, move markers = splitOrTruncateToWindows(...) (:98) above the queue and compute pqSize = Math.max(16, Math.min(maxPassages, markers.size())) instead of Math.max(16, maxPassages) (:93).

markers = splitOrTruncateToWindows(markers, maxPassageWindow, permittedPassageRanges);

// minimum priority queue size of 16 so that small maxPassages values don't
// return too few passages due to subsequent passage merges. At most one passage
// is collected per (split) marker, so the queue never needs to be larger than that.
int pqSize = Math.max(16, Math.min(maxPassages, markers.size()));

// Best passages so far.
PriorityQueue<Passage> pq = PriorityQueue.usingComparator(pqSize, passageScorer);

Trade-offs

  • No change in results for any maxPassages the current code accepts: with capacity at least the number of split markers nothing is ever evicted, and below that the size is unchanged (for valid inputs; by a hand proof, not published).
  • The queue is never larger than today's (unchanged when maxPassages <= markers.size() or when both sizes are the floor of 16, smaller otherwise), so it keeps the low-overhead goal of #11990. The split does the same work, only earlier. No API change.
  • Use the count after the split: a match that crosses value boundaries becomes several markers, and a variant using the caller's markers.size() loses passages.
  • Headroom like the maxPassages * 3 from the #11990 review must avoid int overflow: it wraps negative for maxPassages > 715,827,882.

B. Cap maxPassages in FieldValueHighlighters.highlighted only

#

Clamp the value in the convenience factory before it calls pickBest.

Trade-offs

Fixes the MatchHighlighter path but not direct pickBest callers, and the factory does not know the split marker count. Not recommended; not executed.

C. Document a limit

#

A javadoc note on both pickBest overloads and on highlighted that maxPassages, a positive count, is allocated up front and must stay below 2^31 - 17.

Trade-offs

No behaviour change; turns the "all passages" idiom into a documented error and keeps the memory cost of large values. A fallback if maintainers reject A; not executed.

Downstream note

#

An application that forwards a user-chosen passage count to MatchHighlighter or PassageSelector has to cap it itself, as for any top-N size. A code search found no use of PassageSelector in Solr or Elasticsearch.

How it was found

#

A probe of numeric limits on public highlighter arguments saw pickBest throw at Integer.MAX_VALUE - 1 where 1000 returns two passages. A hand proof showed that the queue size cannot change the result once it holds every match, 31 million generated checks on the stock jar confirmed it, and the case was reduced to one public-API test.

The method in full158 words

Method: executed differential testing with a hand proof (no formal model), in a hunt round on numeric limits of public API arguments, on the stock main jars.

  • First signal. A planning probe called pickBest(value, markers, 20, Integer.MAX_VALUE - 1) on a text with two matches: IllegalArgumentException, where n = 1000 returns 2 passages; n = 10^8 allocated 381 MiB (main a9779ef3c193, 2026-10-28).
  • Proof and check. The finder wrote down why the result cannot depend on the queue capacity once it covers the split markers (at most one insert per marker, the clamp, the default path), then checked it on the stock jar by bounded-exhaustive plus seeded-random translation validation against the fixed variant and three mutants of it: 31,086,300 checks with assertions off, 24,980,382 on, 0 failures, all mutants killed. The Integer.MAX_VALUE failure appeared on all 693,640 inputs with a non-empty value and a non-zero window.
  • Reduction. A public-API JUnit test, later the single test shown here.

LFV-1005, snapshot of 2026-11-03

Registry title
matchhighlight PassageSelector sizes its passage queue by maxPassages before it looks at any match, so maxPassages = Integer.MAX_VALUE ('all passages') throws IllegalArgumentException and a large maxPassages allocates maxPassages + 1 queue slots per call, even for a text with two matches
Area
highlighter / matchhighlight passage selection (PassageSelector.pickBest passage-queue sizing; used by MatchHighlighter through FieldValueHighlighters.highlighted, which passes maxPassages through unchecked)
Priority
Low, rank 620: This is the matchhighlight version of the UnifiedHighlighter maxPassages = Integer.MAX_VALUE row LFV-438; it fails loudly with a clear IllegalArgumentException in a little-used package, so it closes the MAX_VALUE pre-size group after LFV-995.
Impact class
wrong error
Impact note
Applications on any release from 9.0.0 to 10.6.0 or main that highlight with matchhighlight (MatchHighlighter with FieldValueHighlighters.highlighted, or PassageSelector.pickBest directly; default settings, any index, -ea and -da) and pass maxPassages = Integer.MAX_VALUE as 'all passages' (any value >= 2^31 - 17) get IllegalArgumentException 'maxSize must be >= 0 and < 2147483631' for every non-empty value, which fails the whole highlight call, and a large but accepted maxPassages costs one transient allocation of maxPassages + 1 queue slots per call however few matches there are (about 64 MiB at 2^24 for two matches; OutOfMemoryError at 3*10^8 with a 1 GiB heap); results are correct whenever the allocation succeeds, and nothing is written to the index.
Summary
You call PassageSelector.pickBest on a short text with two matches (or MatchHighlighter with FieldValueHighlighters.highlighted) and pass maxPassages = Integer.MAX_VALUE to mean 'all passages', and you expect the same two passages that maxPassages = 10 returns, because maxPassages only caps the result (the method clamps its result to it) and there can never be more passages than matches. Instead pickBest builds its priority queue with Math.max(16, maxPassages) slots before it reads any match, so the call throws IllegalArgumentException 'maxSize must be >= 0 and < 2147483631; got: 2147483647'. A smaller but still large maxPassages succeeds and allocates memory in proportion to maxPassages rather than to the matches: about 64 MiB per call at 2^24.
