Taxonomy getAllDims misorders float dims, and can throw, when one dim's value is NaN

With float taxonomy facets, one dimension whose value is NaN makes getAllDims list the other dimensions out of value order (a=1.0 above c=2.0) and disagree with getTopDims; with 32 or more dimensions it can throw "Comparison method violates its general contract!". Every release since 4.7.0 and main are affected.

The finding in 30 seconds

#

getAllDims sorts the dims with a comparator that answers "tie" whenever NaN is involved and then orders by name. That breaks transitivity, so the sort can return finite dims out of order.

Background: float taxonomy facets

#
  1. Each document carries labels such as a/x; the first component (a) is the dimension, or dim.
  2. TaxonomyFacetFloatAssociations adds up (SUM) or takes the maximum (MAX) of a float per label, from FloatAssociationFacetField weights or a DoubleValuesSource; a dim's value is the aggregate of its labels.
  3. getAllDims(n) returns one result per dim, sorted by value, highest first. getTopDims(k, n) returns the top k dims and is documented to equal the first k entries of getAllDims(n).

The finding, step by step

#
  1. Index three documents, one FloatAssociationFacetField each: dim a with weight 1.0, dim b with NaN, dim c with 2.0. Aggregate them with TaxonomyFacetFloatAssociations and SUM.
  2. You expect getAllDims(10) to list the dims by value, highest first, so c=2.0 before a=1.0, and getTopDims(1, 10) to return its first entry.
  3. Instead getAllDims(10) returns [a=1.0, b=NaN, c=2.0], and getTopDims(1, 10) returns [b=NaN].
  4. Why: the sort tests x > y both ways and falls back to the name. With NaN both tests are false, so b ties with everything: a before b, b before c by name, yet c before a by value. No order satisfies that.
  5. With 32 or more dims the same sort can throw an IllegalArgumentException. NaN needs no NaN input: a clicks / views weight of 0/0, or weights whose SUM overflows to +Inf and -Inf in one dim, do the same.

Who is affected

#

Applications that call getAllDims on float taxonomy facets (float associations or a DoubleValuesSource, SUM or MAX) when one dim aggregates to NaN. Three dims suffice for the wrong order; the exception needs 32 or more, which the documented "sparse faceting" use invites. Hits, counts, drill-down and int facets are unaffected. Rare, but deterministic once such a value is indexed.

Mechanism, terms and numbers713 words

TaxonomyFacets#getAllDims sorts the per-dim results with a.value.doubleValue() > b.value.doubleValue(), then the reverse, and otherwise the dim name (TaxonomyFacets.java:580-590). Every > with NaN is false, so a dim whose value is NaN ties with every value, is placed by name only, and the comparator is no longer transitive. With dims a=1, b=NaN, c=2 (float associations, SUM), getAllDims(10) returns [a=1.0, b=NaN, c=2.0] while getTopDims(1, 10) returns [b=NaN]: getTopDims ranks with the NaN-safe valueComparator (Float.compare, FloatTaxonomyFacets.java:48) since #12966, and its javadoc says it should equal the first entries of getAllDims. With 32 or more dims, List.sort can detect the broken contract and getAllDims throws IllegalArgumentException: Comparison method violates its general contract!. NaN also comes from ordinary inputs: a clicks / views weight with 0/0, or finite weights whose float SUM overflows to +Inf and -Inf inside one dim. Hits, counts, drill-down and int facets are not affected. Released since 4.7.0; the default association path reaches it since 9.11.0. The fix sorts with valueComparator, then the dim name.

Mechanism (Lucene main 645d4fe14a20):

  1. Collect. getAllDims walks the taxonomy root's children and siblings and adds one FacetResult per dim (TaxonomyFacets.java:564-578). The taxonomy lists the youngest child first (TaxonomyIndexArrays.java:253-255, :268-269), so dims added as a, b, c are visited as [c=2.0, b=NaN, a=1.0]. A dim's value is a fold over its labels that starts at 0f (FloatTaxonomyFacets.java:129-150), so one NaN label makes the dim NaN.
  2. Sort. TaxonomyFacets.java:580-590:
// Sort by highest value, tie break by dim:
results.sort(
    (a, b) -> {
      if (a.value.doubleValue() > b.value.doubleValue()) {
        return -1;
      } else if (b.value.doubleValue() > a.value.doubleValue()) {
        return 1;
      } else {
        return a.dim.compareTo(b.dim);
      }
    });
  1. Wrong order. For a=1, b=NaN, c=2 the comparator says a<b (name), b<c (name) and c<a (value): a cycle, so it is not a valid Comparator. On the visiting order [c, b, a], the JDK's ArrayList.sort asks only compare(b, c) = -1 and compare(a, b) = -1, takes the run as strictly descending, reverses it and returns [a=1.0, b=NaN, c=2.0]; it never compares a with c. (Shown with a verbatim copy of the comparator that logs its calls; the real getAllDims returns the same list.)
  2. Exception. From 32 elements the JDK's TimSort merges sorted runs and, on some arrangements, meets the contradiction and throws IllegalArgumentException("Comparison method violates its general contract!"), which List.sort documents for a comparator that breaks its contract. Below 32 elements it never merges and never throws.
  3. getTopDims uses another order. Its queue orders dims by valueComparator, then the name (TaxonomyFacets.java:610-614), and admits dims with it (:652-664). For float facets that is Float.compare (FloatTaxonomyFacets.java:48), a total order that ranks NaN above +Infinity, so it returns [b=NaN, c=2.0, a=1.0]. Int facets compare ints and cannot be NaN.
  4. Where NaN comes from. Nothing checks finiteness: FloatAssociationFacetField stores any float (FloatAssociationFacetField.java:33-40), TaxonomyFacetFloatAssociations.java:151 casts any DoubleValuesSource double to float, SUM is + and MAX is Math.max (AssociationAggregationFunction.java:40-65).

How often a NaN dim breaks the order depends on the arrangement: a simulation of the verbatim comparator (one NaN, distinct values, random order, 100,000 lists per size) misorders finite dims in 5.45% of 3-dim, 21.32% of 10-dim and 39.37% of 32-dim lists, and throws in 0.28% of 32-dim lists.

Exposure and likelihood193 words
  • Who. Users of TaxonomyFacetFloatAssociations over FloatAssociationFacetField weights or a DoubleValuesSource, with SUM or MAX, who call getAllDims, or compare it with getTopDims. These are opt-in facet types, and the facet classes are @lucene.experimental.
  • Settings. Otherwise defaults: default IndexWriterConfig, codec, taxonomy and FacetsConfig on the association path since 9.11.0; the value-source path with the default dim config was run on 9.11.0, 10.6.0 and main, and with multiValued + requireDimCount dims it is affected since 4.7.0.
  • Scale. Three dims for the wrong order; 32 or more dims with hits for the exception. getAllDims is documented for "sparse" faceting "where many different dimensions were indexed" (Facets.java:53-55).
  • Effect. The "top" dim shown can be a lower-valued one; code that truncates or pages getAllDims gets the wrong dims; getTopDims and getAllDims disagree; with many dims the facet call fails. getTopDims does not use this comparator (it ranks dims with valueComparator), but the child lists it returns have a separate NaN issue (LFV-825); nothing is written to the index.
  • Likelihood. Rare: ordinary weights (scores, prices, ratings) do not aggregate to NaN, but computed weights can (0/0), and so can SUM overflow.

Why it looks unintended

#
  • The code says "Sort by highest value, tie break by dim", yet lists 1.0 above 2.0.
  • The javadoc says getTopDims should equal the first entries of getAllDims; here it returns [b=NaN] while getAllDims starts with a=1.0.
  • #12966 moved getTopDims to a NaN-safe order and left getAllDims behind; Lucene accepts NaN weights.
The full argument202 words
  • The code's intent. TaxonomyFacets.java:580: "Sort by highest value, tie break by dim". No rule for where NaN goes explains 1.0 above 2.0.
  • The javadoc. Facets.java:52-57: getAllDims returns dims "sorted by the number of hits that dimension matched"; :59-62: getTopDims is "sorted by the number of hits/aggregated values ... Results should be the same as calling getAllDims and then only using the first topNDims". The base getTopDims is literally getAllDims(topNChildren).subList(0, ...) (:69-72).
  • The tests. TestTaxonomyFacetAssociations.java:327-329, :359-361 and :380-382 assert that getTopDims(10, 10) equals getAllDims(10) for float associations, with finite values only. No facet test uses NaN, and the test helper FacetTestCase#sortFacetResults (:209-221) copies the same comparator.
  • The JDK contract. The exception is List.sort reporting a broken Comparator, not an input check.
  • History. #12966 (2024; 9.11.0 through #13358) added valueComparator and moved getTopDims to it, but left getAllDims on the 2013 comparator; none of its 55 comments and reviews mentions NaN. The same change is the 9.11.0 bug fix "Aggregation facets no longer assume that aggregation values are positive" (lucene/CHANGES.txt:2922).
  • NaN is accepted. The facet module rejects NaN only for range bounds (range/DoubleRange.java:61-69, rangeonrange/DoubleRange.java:43-51, facetset/DimRange.java:62-94); weights are not checked.
The devil's-advocate check188 words

The case for "intended": NaN is garbage in, as with NaN scores in core search (LUCENE-2271); the facet APIs are @lucene.experimental; the getAllDims javadoc speaks of "number of hits" and says nothing about NaN; AssociationAggregationFunction.java:25-28 assumes "valid values are always positive"; and in the minimal test every dim has one hit, so a literal "by hits, then by name" reading would accept [a, b, c].

Why it fails: (1) when c has 2 hits and value 2.0 and a has 1 hit and 1.0, the result is still [a=1.0, b=NaN, c=2.0], wrong under both readings (executed on main, 10.6.0 and 9.11.0); (2) getTopDims and getAllDims disagree wherever NaN goes, against the javadoc's stated expectation ("Results should be the same") and the upstream equality tests (finite inputs); (3) the exception is a Comparator contract violation, which experimental status does not excuse; (4) 0/0 and SUM overflow produce NaN from ordinary inputs, so rejecting explicit NaN does not prevent it; (5) #12966 already chose a NaN-safe order for getTopDims and dropped the positive-values assumption as a bug fix. The cross-model refute review rated the intended argument "weak".

Suggested fix

#

Recommended Sort getAllDims with valueComparator, as getTopDims does

Sort getAllDims with valueComparator.compare(b.value, a.value), then the dim name, the order getTopDims already uses (+4/-6 lines in TaxonomyFacets.java). A NaN dim is then listed first, as in getTopDims. The repro passes, and so do all 307 lucene/facet tests and the format check.

// Sort by highest value, tie break by dim:
results.sort(
    (a, b) -> {
      int cmp = valueComparator.compare(b.value, a.value);
      if (cmp != 0) {
        return cmp;
      }
      return a.dim.compareTo(b.dim);
    });

Trade-offs

  • One order for both methods; a NaN dim is listed first, where getTopDims already puts it.
  • Int facets: Comparator.comparingInt gives today's order. Float facets: Float.compare and > differ only on NaN and on a -0.0/+0.0 pair; the built-in SUM and MAX folds start at +0.0 and cannot produce -0.0 (solver queries; reasoned, not executed).
  • A custom AssociationAggregationFunction (public abstract class) that returns -0.0f would now be ordered below +0.0 instead of by name (read, not run).
  • Scope: this fixes the dim order of getAllDims only (and with it the disagreement with getTopDims and the exception). The child labels inside each dim come from getTopChildren, whose queue can still pick the wrong children when a label is NaN: that is LFV-825, with its own fix.
  • Optional: change the test helper FacetTestCase#sortFacetResults the same way (identical for finite values).

Downstream note

#

A product that lets untrusted documents set float association weights can see one facet call return dims out of order or fail with an exception; hits, counts and the index are unaffected.

How it was found

#

A bounded, exhaustive differential search compared Lucene's facet ordering with an exact reference ordering on small inputs that include NaN and infinities: every failure had a NaN dim, none without one. Solver queries showed the comparator is not transitive once NaN is allowed, and a simulation of the comparator found the 32-dim exception.

The method in full161 words

The hunt targeted NaN and other special values in the facet top-k paths. A sweep over the stock jar (1-4 labels and 4 dims, inputs {1, 2, 3, NaN, +Inf, -Inf, -0.0}, association and value-source facets, SUM and MAX, dense and sparse, 1 or 2 segments, assertions on and off) found 928 getAllDims-order failures and 11,022 getTopDims-vs-getAllDims failures, all with a NaN dim and none without one. SMT queries (cvc5 and z3) showed that the getAllDims order is not transitive with NaN and transitive without it, and that it differs from the getTopDims order only on NaN or a signed-zero pair, which the SUM and MAX folds cannot produce. A pure-Java simulation of the verbatim comparator found that 12,843 of 200,000 random lists throw, the smallest with 32 dims, and a seeded search then reproduced the exception on the stock jar. An independent scan of the compiled classes for comparators without a NaN branch flagged the same site.

History

#

Introduced with the Facets API on the LUCENE-5339 branch in 2013 and first released in 4.7.0 (2014); the default float-association path reaches it since 9.11.0 (#12966). Every release from 4.7.0 to 10.6.0 and main are affected; not fixed upstream.

Versions tested7 rows

5458dbf2484 (2013-11-14, "LUCENE-5339: current patch", Michael McCandless) wrote the first dim sort with > in both directions, in the value-source class; 51265435699d (2013-11-18) moved it, on doubleValue(), into the new base class TaxonomyFacets#getAllDims, today's code site. Both reached a release through the branch_4x commit 7477fde1cb0 (2014-01-04), in 4.7.0. Later edits never handled NaN: on the branch, f8ae207e806 (2013-11-24) replaced the dim-name tie-break that both commits already had with return 0 and 034595f5e9f (2013-12-02) restored it, before any release; after that came a named constant, reformatting, List.sort in #915 and an inlined lambda in #13795. #12966 (9ba4af7b883, 2024; 9.x backport #13358, 9.11.0) stopped dropping labels whose value is not > 0, so a NaN dim reaches getAllDims on the default association path, and moved getTopDims to the NaN-safe valueComparator but not getAllDims. getTopDims exists since 9.2.0, so the disagreement starts there. All runs used JDK 25; the exception needs TimSort, the JDK's default object sort since Java 7. Upstream main, branch_11x, branch_10_6 and the 10.6.0 tag still have the comparator (2026-10-30).

LFV-820, snapshot of 2026-11-04

Registry title
Taxonomy Facets#getAllDims sorts float-valued dims with a NaN-unsafe < / > comparator, so one dim whose value is NaN puts the other dims out of value order, breaks the documented rule that getTopDims equals the first entries of getAllDims, and with 32 or more dims can make getAllDims throw 'Comparison method violates its general contract!' (released since 4.7.0)
Area
facet / taxonomy facets (TaxonomyFacets#getAllDims ordering of float-valued dims: float association and value-source facets)
Priority
Low, rank 566: A NaN float facet value is a rare boundary input that silently misorders dims, makes getTopDims disagree with getAllDims and makes getAllDims throw at 32 or more dims, while hits and counts stay correct; it has the same NaN-boundary profile as LFV-427 but is milder than that row's empty groups.
Impact class
silent wrong results
Impact note
Applications that call Facets#getAllDims on float-valued taxonomy facets (TaxonomyFacetFloatAssociations, fed by FloatAssociationFacetField weights or a DoubleValuesSource, SUM or MAX) silently get the finite dims out of value order (a=1 listed before c=2) and getTopDims(k, n) results that differ from getAllDims(n).subList(0, k), and with 32 or more dims with hits getAllDims can throw IllegalArgumentException, as soon as one dim's aggregate is NaN, which finite inputs can also produce (a float SUM that overflows to +Inf and -Inf inside one dim, or finite doubles beyond the float range on the DoubleValuesSource path); default IndexWriterConfig, codec, taxonomy and FacetsConfig on the association path since 9.11.0, value-source dims set multiValued + requireDimCount since 4.7.0, -ea and -da, no scale needed; getTopDims never throws, hits and drill-down are correct, and nothing is written to the index.
Summary
You aggregate float values per taxonomy dim (FloatAssociationFacetField weights or a DoubleValuesSource) and call getAllDims, documented to sort dims by value, and getTopDims, documented to return the same as the first entries of getAllDims. If one dim's value is NaN (dims a=1, b=NaN, c=2), getAllDims can return [a=1.0, b=NaN, c=2.0], with a ahead of c, while getTopDims(1, 10) returns [b=NaN]; with 32 or more dims, getAllDims can instead throw IllegalArgumentException 'Comparison method violates its general contract!' from List.sort. The getAllDims comparator compares doubleValue() with > in both directions and falls back to the dim name, so NaN ties with every value and the order is not transitive, while getTopDims has used the NaN-safe Float.compare (valueComparator) since #12966 (9.11.0).
Introduced

It reached releases through the trunk merge 9d0b60388da and the branch_4x backport 7477fde1cb0 ('LUCENE-5371, LUCENE-5339: ... simplify facet APIs'); JIRA LUCENE-5339 (GitHub mirror #6403), no PR (svn era).
