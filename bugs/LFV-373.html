Hunspell spell-checker can miss an x|xx triple letter at the second and later joins of a compound

With a dictionary that forbids three identical letters across a compound join (CHECKCOMPOUNDTRIPLE), Hunspell.spell rejects bareeel (bare|eel) but accepts operabareeel (opera + bare|eel): after the first join, half of the check compares a position in the whole word with the length of the rest. Affects 8.9.0 to 10.5.2.

The bug in 30 seconds

#

Hunspell splits a compound left to right and checks each join. For the second and later joins, the "one letter before, two after" half of the triple check compares the join's position in the whole word with the length of only the part being split, so it is skipped once enough letters come before that part.

  1. Load Lucene's own checkcompoundtriple test dictionary: CHECKCOMPOUNDTRIPLE, COMPOUNDFLAG A and four words, foo, opera, eel, bare. spell("bareeel") returns false: bare|eel puts eee across the join, and Lucene's fixture lists it as wrong.
  2. Put another part in front: spell("operabareeel"), opera + bare|eel. You expect false, as for bareeel; C Hunspell 1.3.2 and 1.7.2 return false.
  3. You get true, with no error. foobareeel, barebareeel and eelbareeel are accepted too, while the mirror form operafooopera (opera + foo|opera) is still rejected.
  4. Why: at the second join the part being split is bareeel (it starts at position 5 and has 7 letters), and the join is at position 9 of the whole word. The "one letter before, two after" test checks 9 < 7 - 1, which is false, so it is skipped; the right bound is 5 + 7 - 1 = 11.
  5. Real dictionary: Swedish (sv_SE) rejects musikradiooomskuren but accepts sommarmusikradiooomskuren, the same triple o with one more part in front. Only spell-check verdicts and suggestions change; stemming, indexing and search do not.

Who is affected

#

Only applications that call the opt-in spell-checker (Hunspell.spell; the suggesters use the same check) with a dictionary that sets CHECKCOMPOUNDTRIPLE and allows compounds of three or more parts, such as Swedish sv_SE. Some misspelled compounds are reported as correct. Stemming (HunspellStemFilter), indexing and search are unaffected (by the code path; a stem-filter probe agrees). Every release from 8.9.0 to 10.5.2.

Mechanism, terms and numbers645 words

CHECKCOMPOUNDTRIPLE tells Hunspell to reject a compound when a join puts three identical letters in a row, either two before and one after the join (foo|ox) or one before and two after (xo|oof). Lucene's Hunspell.spell splits a compound left to right and checks each join. From the second join on, the code passes the join as a position in the whole word but the length of only the part still being split, and the "one before, two after" half of the test compares the two (breakPos < length - 1, Hunspell.java:430), while the other half adds the part's offset. Once enough letters precede the current part, that half is skipped. With Lucene's own test dictionary, bareeel is rejected but operabareeel, foobareeel and barebareeel are accepted; with the public Swedish dictionary, sommarmusikradiooomskuren is accepted. C Hunspell rejects all of them. Only the opt-in spell-checker (spelling verdicts and suggestions) is affected, in every release from 8.9.0 to 10.5.2; the fix is one line.

Terms

#
  • Compound checking: when a word is not in the dictionary, Hunspell.spell tries to split it into dictionary words that may be compounded (here, words with the COMPOUNDFLAG). It tries a first part, then splits the rest the same way, recursively, so a word can have several parts (COMPOUNDWORDMAX, the part cap, defaults to unlimited, Dictionary.java:152; the compound flags or rules decide which words may start, continue or end a compound).
  • CHECKCOMPOUNDTRIPLE (hunspell(5)): "Forbid compounding, if compound word contains triple repeating letters (e.g. foo|ox or xo|oof)." Two shapes: xx|x, two equal letters before the join and one after (foo|opera), and x|xx, one before and two after (bare|eel).
  • The part being split: from the second join on, the code works on the rest of the word as a slice of the same array: an offset (where the rest starts) and a length (how many letters it has).

The bug

#
  1. checkCompounds computes the join as a position in the whole word, breakOffset = word.offset + breakPos (Hunspell.java:223), and calls mayBreakIntoCompounds(word.chars, word.offset, word.length, breakOffset) (:224): offset and length of the slice, position in the whole word.
  2. After a part is found, checkCompoundsAfter recurses on the rest, new CharsRef(word.chars, breakOffset, remainingLength) (:284), so from the second join on the offset is greater than 0.
  3. mayBreakIntoCompounds (:427-433) tests breakPos > offset + 1 && chars[breakPos - 2] == chars[breakPos - 1] for xx|x (offset-aware) || breakPos < length - 1 && chars[breakPos] == chars[breakPos + 1] for x|xx (:430): a position in the whole word compared with the slice's own length.
  4. Whenever the join's position is at least the slice length minus 1, the x|xx test is skipped and the join is allowed. The buggy bound is stricter than the right one (offset + length - 1), so it never reads out of bounds; it only skips the check.

Why it is a bug, not intended

#
  • hunspell(5): "Forbid compounding, if compound word contains triple repeating letters (e.g. foo|ox or xo|oof)", with no part limit; the skipped half is exactly xo|oof.
  • The other half of the same test adds the offset (breakPos > offset + 1); this half does not (breakPos < length - 1).
  • C Hunspell 1.3.2 and 1.7.2 reject every affected word tried.
The full argument269 words
  • Contract. hunspell(5): "CHECKCOMPOUNDTRIPLE Forbid compounding, if compound word contains triple repeating letters (e.g. foo|ox or xo|oof)." It sets no limit on the number of parts, and "COMPOUNDWORDMAX ... (Default is unlimited.)". Hunspell.spell returns "whether the given word's spelling is considered correct according to Hunspell rules" (Hunspell.java:71-74). The class "can be used in place of native Hunspell for many languages" (:35-36) and notes that "not all languages are supported yet. For example:" Hungarian, non-BMP characters, the PHONE option (:36-44). Those are examples, not a full list, so they neither include nor exclude this case; nothing in the javadoc, tests or history marks multi-part CHECKCOMPOUNDTRIPLE as unsupported.
  • Tests. Lucene's fixture checkcompoundtriple.wrong lists fooopera and bareeel, run by TestSpellChecking.testCheckCompoundTriple (TestSpellChecking.java:132-134). The fixture, the same as C Hunspell's, has only 2-part compounds, so it never reaches a later join. No test asserts that a later-join triple is accepted.
  • Code. Two halves of one boolean expression use different index spaces, and the verdict for the same join flips with the prefix length. C Hunspell, which the code ports, uses positions inside the rest in both halves; Lucene's breakPos > offset + 1 is the port of its i > 1.
  • History. Both halves were written in one commit (9d45dfe776a2, LUCENE-9710, 2021-02-01); its PR had no review comments, and the issue has no design discussion. CHANGES 8.9.0 (LUCENE-9687) says the work fixed "various behavior differences between Java and C++ implementations" (lucene/CHANGES.txt:5368-5369).
  • Reference. C Hunspell 1.3.2 and 1.7.2 reject all 9 triple words of the independent reproducer's set on the same dictionary.
The devil's-advocate check155 words

The strongest case: the class promises to replace native Hunspell only for many languages, and both the manual's examples and the fixtures show only 2-part compounds, so behaviour for 3 or more parts is unspecified.

Why it fails: the manual states the rule for any compound and sets no part limit; COMPOUNDWORDMAX defaults to unlimited; Lucene enforces the other half (xx|x) at every join, so it treats the rule as applying everywhere; the javadoc's examples of unsupported cases do not name this directive or Swedish (they are only examples, so this point is weak on its own); and nothing explains why the same join is accepted or rejected depending only on how many letters precede it. The fix does change established spell and suggest results, a compatibility cost noted under the fix, not a sign that the current results are intended. Every reviewer rated the intended-behaviour case weak. Verdict: not intended, a defect.

Suggested fix

#

Recommended A: add the part's offset to the bound (one line)

Add the part's offset to the bound, as the other half of the test already does: breakPos < offset + length - 1 (one line, Hunspell.java:430). With it the repros pass, the hunspell test package runs 165 tests with 0 failures and 13 skipped (they need external dictionaries), with assertions on and off, and the module's lint check passes.

Trade-offs

Changes verdicts only for CHECKCOMPOUNDTRIPLE dictionaries, and only to reject words with an x|xx triple at a later join, which C Hunspell rejects too. In the sv_SE words measured, rejected words do the same or fewer lookups than on main (436 vs 465 and 1,371 vs 1,420), and words main wrongly accepts now run the full search before they are rejected (1,350 vs 290 lookups); all took about 4 ms or less per word. Not benchmarked further. Compatibility: it deliberately changes what the public spell() and the suggesters return for such words (operabareeell no longer gets the suggestion operabareeel); applications or tests that rely on the old acceptance would see that, so it is a narrow behaviour fix to note in CHANGES.

Downstream note

#

Elasticsearch, OpenSearch and Solr use Hunspell only through HunspellStemFilter (stemming), per a code search of their default branches (a code search can miss hits), so their indexing and search are not affected; only applications that call the spell-checker API itself are.

How it was found

#

Differential testing: the stock jar's Hunspell.spell was compared with C Hunspell 1.7.2 on words generated from the 131 Hunspell 1.7.2 conformance fixtures, including sampled three-part concatenations. Four three-part words of the checkcompoundtriple fixture were accepted only by Lucene; code reading found the cause, and a search of the Swedish dictionary found real accepted words.

The method in full140 words

Method: differential testing against another implementation (the hunt counts this as testing, not as checking against an exact reference semantics).

  • A generator built word lists from the 131 Hunspell 1.7.2 conformance fixtures: fixture words, every generated form, case variants, edits, all 2-part and sampled 3-part concatenations of roots and forms. A small C driver called Hunspell_spell per word, and the results were compared with the stock Lucene jar.
  • For the checkcompoundtriple fixture, 4 three-part words were accepted only by Lucene: operabareeel, foobareeel, eelbareeel, barebareeel.
  • Code reading of mayBreakIntoCompounds found the mixed index spaces; the finder reduced it to a public-API JUnit and searched the public sv_SE dictionary for accepted triple words (20 found).
  • An independent reproducer, a cross-model stage with its own executed test, a devil's advocate and an adjudication then confirmed it (see the checks).

LFV-373, snapshot of 2026-10-29

Registry title
Hunspell spell-checker: CHECKCOMPOUNDTRIPLE misses an x|xx triple letter (one letter before the boundary, two after) at the second and later boundaries of a compound, so words such as operabareeel (opera + bare|eel) are accepted (absolute break position compared with the tail's relative length)
Area
analysis / hunspell (Hunspell.spell compound checking)
Priority
Low, rank 377: The opt-in Hunspell spell-checker silently accepts some misspelled compounds of three or more parts in a real public dictionary (sv_SE), a rare spelling-verdict error like DirectSpellChecker's LFV-240, so it heads the new Hunspell rows after it.
Impact class
silent wrong results
Impact note
Only applications that call the opt-in Hunspell spell-checker (Hunspell.spell; by code reading also the suggesters, which validate candidates with the same compound check, not executed) with a dictionary that sets CHECKCOMPOUNDTRIPLE and builds compounds of 3 or more parts (sv_SE/sv_FI among the public dictionaries the finder surveyed; per that survey nb_NO has no compoundable root that starts with a doubled letter and hu_HU allows only 2-part compounds) are hit: some misspelled compounds with a triple letter at a later boundary are reported as correctly spelled, with no error; stemming, indexing and search (HunspellStemFilter) are not affected [exec], no scale is needed, and every release from 8.9.0 to 10.5.2 has it.
Summary
You load a Hunspell dictionary with CHECKCOMPOUNDTRIPLE, which hunspell(5) defines as 'Forbid compounding, if compound word contains triple repeating letters (e.g. foo|ox or xo|oof)', and expect Hunspell.spell to reject a compound with a triple letter at any boundary, as C Hunspell 1.3.2 and 1.7.2 do and as Lucene's own checkcompoundtriple fixture requires for bareeel (bare|eel). Instead Lucene rejects bareeel but accepts operabareeel, barebareeel and foobareeel (opera, bare or foo + bare|eel), and with the public Swedish dictionary (sv_SE) it accepts sommarmusikradiooomskuren while it rejects musikradiooomskuren. The cause: Hunspell.mayBreakIntoCompounds receives an absolute break position (the tail's offset in the word plus the relative break) but tests 'breakPos < length - 1' against the tail's relative length, so at the second and later boundaries the x|xx half of the check is skipped whenever the absolute break position is at least the tail length minus 1, while the xx|x half ('breakPos > offset + 1') is offset-aware and still works.
