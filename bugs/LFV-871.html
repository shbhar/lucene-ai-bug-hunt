IndriAndQuery silently accepts MUST, FILTER and MUST_NOT clauses, matches them as SHOULD, and explains some of its own hits as non-matches

IndriAndQuery takes BooleanClauses but ignores MUST, FILTER and MUST_NOT when it matches: +f:a -f:b returns doc 1, the document it should exclude, next to doc 0, and its explain calls doc 1 a non-match. Every release since 8.9.0; a niche API, so a Low-priority hardening bug.

The finding in 30 seconds

#

IndriAndQuery takes clauses that each carry an Occur and accepts any of them. When it matches it treats every clause as SHOULD; its explain still treats MUST and FILTER as required.

IndriAndQuery and Occur in one minute

#
  1. IndriAndQuery (core, org.apache.lucene.search, since 8.9.0) implements the #and operator of the Indri search engine: it combines the scores of its clauses, and a document matches if it matches any clause. No Lucene query parser builds it; applications call its constructor.
  2. Its clauses are BooleanClauses, the type BooleanQuery uses, so each has an Occur: SHOULD (optional), MUST (required and scored), FILTER (required, not scored) or MUST_NOT (excluded).
  3. IndexSearcher.explain(query, doc) explains how a document scored; for a document the search returned, it should say that the document matches.

The finding, step by step

#
  1. Index two documents, doc 0 with f=a and doc 1 with f=b. Build new IndriAndQuery(List.of(new BooleanClause(f:a, MUST), new BooleanClause(f:b, MUST_NOT))). The constructor accepts it, and it prints as +f:a -f:b, like a BooleanQuery.
  2. You expect doc 0 only, which is what the same two clauses give in a BooleanQuery (1 hit), or a rejection, since IndriAndQuery has no required or excluded clauses.
  3. Instead it returns doc 0 and doc 1 (2 hits). Matching never reads Occur, so every clause acts as SHOULD and the query matches the union: the MUST_NOT clause adds the very document it names, and MUST and FILTER clauses narrow nothing.
  4. explain does read Occur: for hit doc 1 it answers "Failure to meet condition(s) of required/prohibited clause(s)" ("no match on required clause (f:a)"). Search and explain of the same query disagree.
  5. On four documents, [MUST f:a, FILTER acl:x] returns all 4 where a BooleanQuery returns 2, and a lone [MUST_NOT f:secret] returns exactly the excluded document. No exception, on every release since 8.9.0.

Who is affected

#

Applications that build an IndriAndQuery (no Lucene parser produces it) with a MUST, FILTER or MUST_NOT clause, on any release since 8.9.0 with default settings. They get more hits instead of fewer, and explanations that contradict the hits. The one downstream user found, an Indri query parser, passes MUST and MUST_NOT clauses for its filter operators (by reading its code).

Mechanism, terms and numbers513 words

IndriAndQuery (core, since 8.9.0) takes a List<BooleanClause>, so every clause carries an Occur, and its public constructor accepts any of them without a check. When it matches, it builds a scorer for every clause and iterates their union, whatever the Occur: MUST and FILTER clauses do not narrow the hits, and a MUST_NOT clause is one more disjunct, so it keeps the documents it names instead of removing them (a lone MUST_NOT clause returns exactly them). Its explain, a trimmed copy of BooleanWeight.explain, does treat MUST and FILTER as required, so IndexSearcher.explain reports some returned hits as non-matches. In the repro, +f:a -f:b over doc 0 {f=a} and doc 1 {f=b} returns both documents (a BooleanQuery returns doc 0) and explains doc 1 as "Failure to meet condition(s) of required/prohibited clause(s)". Matching all clauses as a disjunction is the Indri design for SHOULD clauses; what is wrong is that other Occur values are accepted silently and undocumented, and that explain contradicts the hits.

Exposure and likelihood202 words
  • Who is hit. Applications that build an IndriAndQuery with a MUST, FILTER or MUST_NOT clause. Default codec, writer config, similarity and searcher; any index size; public API only. Queries with SHOULD clauses only are unaffected.
  • What they see. MUST and FILTER clauses do not narrow the hits, a MUST_NOT clause is matched as one more disjunct, so it keeps the documents it names instead of removing them (alone, it returns exactly them), and IndexSearcher.explain reports some returned hits as non-matches. No exception, no index damage.
  • Why someone passes them. The constructor asks for an Occur on every clause, the class is called "And", and toString prints +, # and -. The Lucindri parser (lemurproject/Lucindri, on lucene-core 8.10.0) builds Lucene's IndriAndQuery with Occur.MUST and Occur.MUST_NOT for its #scoreif / #scoreifnot operators, which its README documents as filters (read, not executed); on Lucene's class they would not filter.
  • Diagnostics. Lucene's generic query check asserts, for any query it is given, that each collected hit explains as a match (QueryUtils.check -> CheckHits.checkExplanations -> ExplanationAsserter); IndriAndQuery breaks that agreement through its public constructor.
  • Scale. Every release since 8.9.0 (2021). Low priority: a niche API, and the matching half has no stated contract.

Why it looks unintended

#
  • The class reads Occur itself: explain treats MUST and FILTER as required (IndriAndWeight.java:86) while search ignores them, so one query's hits and explanations disagree.
  • Lucene's generic query check (QueryUtils.check, via CheckHits.checkExplanations) asserts that every hit explains as a match.
  • Nothing documents that Occur is ignored, yet the constructor demands one per clause and toString prints +, # and -.
The full argument148 words
  • Self-inconsistent. explain applies MUST/FILTER (IndriAndWeight.java:86-94); getScorer and IndriDisjunctionScorer do not (IndriAndWeight.java:47-65, IndriDisjunctionScorer.java:36-41). Whatever the design, one of the two halves is wrong.
  • Explain contract. Weight.explain: "An explanation of the score computation for the named document" (Weight.java:97-105); CheckHits.checkExplanations, which QueryUtils.check runs, requires every hit's explanation to "indicate match" (CheckHits.java:607-627).
  • No documentation of ignoring. The javadoc says only "A Query that matches documents matching combinations of subqueries" (IndriAndQuery.java:22); the Occur javadoc gives MUST, FILTER and MUST_NOT a meaning (BooleanClause.java:27, :35, :57-61); IndriQuery.toString prints them (:46).
  • Tests. TestIndriAndQuery uses SHOULD clauses only (:113-114, :130-131); no test covers other values.
  • History. Both behaviours came with the introducing commit 9cc5c9b7983 (LUCENE-9537); the first explain was a copy of BooleanWeight.explain, and the original author's later PR #463 deletes its isRequired branch.
The devil's-advocate check165 words

Strongest case for "intended": IndriAndQuery implements the Indri #and belief operator, which combines all its children and has no required or excluded clauses (Indri filters with other operators); the scorer is documented as "The Indri implementation of a disjunction scorer"; in the original review mikemccand wrote "Normally in Lucene AND implies MUST ... But this query is actually disjunctive, right?" (lucene-solr#2097, r532223725) and the name was kept; and BooleanClause is documented as "A clause in a BooleanQuery", so Occur semantics are BooleanQuery's contract.

Why it fails: that shows the union is right for SHOULD clauses, which nobody disputes. It does not justify accepting MUST, FILTER and MUST_NOT silently and undocumented, printing them as if they meant something, or an explain that applies MUST and FILTER while search does not. The intended-behaviour verifier built exactly this case and still called the explain half a real self-inconsistency; an independent reviewer from another model family (OpenAI GPT-5.6) called the search/explain disagreement "especially difficult to defend as intended".

Suggested fix

#

Recommended A: reject non-SHOULD clauses, drop explain's isRequired branch

Reject non-SHOULD clauses in the IndriAndQuery constructor (IllegalArgumentException, stated in its javadoc) and drop the isRequired branch of IndriAndWeight.explain, the change open PR #463 already makes. Validated: the repro passes with assertions on and off, 37 Indri, BooleanQuery and QueryVisitor tests pass, and :lucene:core:check -x test passes.

public IndriAndQuery(List<BooleanClause> clauses) {
  super(clauses);
  for (BooleanClause clause : clauses) {
    if (clause.occur() != BooleanClause.Occur.SHOULD) {
      throw new IllegalArgumentException(
          "IndriAndQuery only supports SHOULD clauses, got: "
              + clause.occur().name()
              + " "
              + clause.query());
    }
  }
}
// IndriAndWeight.explain: drop the `else if (c.isRequired())` branch and `fail` (as in #463)

A: reject non-SHOULD clauses, drop explain's isRequired branch (validated by the checks) (recommended)

#

The constructor throws IllegalArgumentException for any clause that is not SHOULD, and its javadoc says so and points to an enclosing BooleanQuery for required, filter and excluded clauses. IndriAndWeight.explain loses the else if (c.isRequired()) branch and the fail flag, exactly as PR #463 does (plus the now unused query field and Iterator import). The diff is formatted with ./gradlew tidy.

public IndriAndQuery(List<BooleanClause> clauses) {
  super(clauses);
  for (BooleanClause clause : clauses) {
    if (clause.occur() != BooleanClause.Occur.SHOULD) {
      throw new IllegalArgumentException(
          "IndriAndQuery only supports SHOULD clauses, got: "
              + clause.occur().name()
              + " "
              + clause.query());
    }
  }
}
// IndriAndWeight.explain: drop the `else if (c.isRequired())` branch and `fail` (as in #463)

Trade-offs

  • A behaviour change for callers that pass other Occur values today: they get an exception instead of silently widened hits (by reading, Lucindri's #scoreif / #scoreifnot would start failing loudly). Fine for main; for a 10.x backport a maintainer may prefer C.
  • IndriQuery keeps the caller's list as is (IndriQuery.java:33), so mutating that list after construction bypasses the check; List.copyOf would close that, but getClauses() would then return a copy.

What the checks validated

  • The repro passes with assertions on and off.
  • TestIndri* (TestIndriAndQuery 2 tests and the repro), TestBooleanQuery (30) and TestQueryVisitor (4): 37 tests, 0 failures.
  • :lucene:core:check -x test passes (google-java-format, ecj lint, forbidden APIs) with the fix and the new test.

B: honour Occur by rewriting into a BooleanQuery (not recommended; validated only with replacement classes, not by a build)

#

Rewrite a query with non-SHOULD clauses into a BooleanQuery: MUST and FILTER clauses as FILTER, MUST_NOT clauses as MUST_NOT, plus an IndriAndQuery of the SHOULD and MUST clauses (optional when a MUST/FILTER clause exists, as in BooleanQuery), together with the LFV-875 advance check in explain.

Trade-offs

Gives the Indri operator semantics it does not have in Indri, changes the Indri scores of such queries, and goes against the maintainers' direction of narrowing what Indri queries accept (#11194).

What the checks validated

A replacement-class experiment, not a build: the two replacement classes are compiled alone and put ahead of the core jar. This doc's test passes that way. The finder's bounded check of the real classes, run the same way on main a9779ef3c193, no longer reports a widened hit or a hit explained as a non-match over 60,288 checks, but the run as a whole still fails: its model describes the stock behaviour and it reports 45,392 differences from that model, so it is not a clean validation of B. Not run through gradle.

C: document that Occur is ignored (not validated) (not run)

#

Say in the javadoc that every clause is treated as SHOULD, and drop the isRequired branch of explain (PR #463's change).

Trade-offs

Non-breaking and backportable, and explain then agrees with the hits; but a MUST_NOT clause still matches as one more disjunct instead of excluding, so this doc's test still fails under C.

What the checks validated

Not run.

Downstream note

#

For downstream services: a restriction such as a per-user FILTER or MUST_NOT clause placed inside an IndriAndQuery does not restrict anything; put restrictions in an enclosing BooleanQuery.

How it was found

#

A public-API test that compared IndriAndQuery with a BooleanQuery over the same clauses, written while checking the related Indri bug LFV-299, first showed it. A Z3 model of the matching and explain rules and a bounded-exhaustive check of the real classes (60,288 checks, 0 model mismatches) then pinned down exactly when it widens and when explain disagrees.

The method in full174 words

Method: non-formal first signal, then formal and semi-formal characterization (2026-10-26 to 2026-10-28; the model and the bounded check ran on main a9779ef3c193).

  • An executed public-API JUnit test, written while checking the related bug LFV-299 (IndriAndQuery does not rewrite its clauses; a different root and fix site), found [MUST f:a, FILTER acl:x] returning {0, 1, 2, 3} where the same BooleanQuery returns {0, 2}.
  • A Z3 model of the matching and explain rules proved that IndriAndQuery equals the BooleanQuery over the same clauses when all clauses are SHOULD, is always a superset, widens exactly when a MUST/FILTER clause misses or a MUST_NOT clause matches, and explains a hit as a non-match only when a MUST/FILTER clause is present.
  • A bounded-exhaustive translation validation of the real classes ran 1,884 clause lists (60,288 checks) and found 30,840 widened hits and 18,048 hits explained as non-matches, with 0 mismatches against the model; with the fix-B sketch's replacement classes, it reported neither family (that run still fails as a whole, since its model describes the stock behaviour).

Only applications that build an IndriAndQuery (a niche core API that no Lucene query parser produces) with a MUST, FILTER or MUST_NOT clause are affected: matching treats every clause as a disjunct, which fits the Indri #and design but is undocumented and unvalidated, so such clauses widen instead of restrict the hits, and IndexSearcher.explain reports some returned hits as 'Failure to meet condition(s) of required/prohibited clause(s)'; default codec, writer config and searcher, any index size, every release since 8.9.0; no exception and no index damage.
Summary
You build an IndriAndQuery from BooleanClauses with Occur values other than SHOULD, for example [MUST f:a, FILTER acl:x] or [SHOULD f:a, MUST_NOT f:secret], which the public constructor accepts, and run it. You expect either the meaning that BooleanClause.Occur documents (the same clauses in a BooleanQuery give {0, 2} and {0, 1}) or a rejection, and in any case an explain that agrees with the hits. Instead IndriAndWeight builds one disjunction over all clauses whatever their Occur, so MUST and FILTER clauses do not restrict ({0, 1, 2, 3}), a MUST_NOT clause adds the very documents it names ({0, 1, 2}; a lone MUST_NOT clause returns exactly them), and IndriAndWeight.explain, which does treat MUST/FILTER clauses as required, explains such hits as non-matches.
