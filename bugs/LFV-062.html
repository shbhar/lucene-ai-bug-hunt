Operations.topoSortStates misses self-loop cycles and returns an order instead of throwing

Operations.topoSortStates documents that it "will throw an IllegalArgumentException if a cycle is detected", but it misses a cycle that is a loop from a state back to itself: the 2-state automaton for ab* comes back sorted as [0, 1]. Every release since 9.7.0 is affected; Lucene's own callers pass only acyclic automata.

The finding in 30 seconds

#

The cycle check is a depth-first search with an "on the stack" bit per state. The code sets that bit on the parent when the parent pushes a child, not on the child it pushes. So a state stays unmarked until it pushes something, and a loop from a state that pushes nothing back to itself is never seen.

Background: automata, cycles and topological order

#
  1. An Automaton is a set of numbered states joined by labelled transitions; state 0 is the start. A transition from a state to itself is a self-loop, the shortest possible cycle.
  2. A topological sort lists the states so that every transition points forward. It exists only when there is no cycle: with a loop on state 1, no order can put 1 before itself.
  3. Operations.topoSortStates finds cycles the textbook way: a depth-first search keeps the states on the current path marked, and an edge to a marked state is a cycle.

The finding, step by step

#
  1. Build the 2-state automaton for ab* with the public API: state 0 -a-> state 1 (accepting), and a loop 1 -b-> 1. It accepts a, ab, abb, ..., so it has a cycle.
  2. Call Operations.topoSortStates(a). You expect IllegalArgumentException("Input automaton has a cycle."): the javadoc says it "will throw an IllegalArgumentException if a cycle is detected".
  3. You get [0, 1] and no exception, with assertions on and off. Determinized RegExp("ab*") and RegExp("a+") (3 states each) return [0, 1, 2]; a* and (ab)*c are rejected as they should be.
  4. Why: the search marks a state as "on the current path" only after it steps to a new child. State 1 has none, so it checks its own loop while still unmarked, and the loop looks like an edge to a finished state. Longer cycles, and loops on state 0, are caught.
  5. Of 121,584 cyclic cases (every graph with up to 4 states, in two scan orders), 2,906 slip through, each with only self-loop cycles. Lucene's two callers pass acyclic token graphs, so only code that calls the method itself is affected.

Who is affected

#

Only code that calls the public Operations.topoSortStates itself and relies on its exception to reject cyclic automata, for example as a finiteness check on automata built from patterns like ab* or a+. Not the default: Lucene's two callers pass acyclic token graphs. Effect: a missing exception; no hang, crash or wrong search result.

Mechanism, terms and numbers862 words

Operations.topoSortStates(Automaton) documents that it "will throw an IllegalArgumentException if a cycle is detected". Its iterative depth-first search marks a state as on-stack only when that state pushes a child (it marks the parent, not the pushed child; the two coincide only when a loop 0 -> 0 pushes state 0 again), and pushes state 0 without any mark. A reachable non-initial state whose only remaining edge is a loop to itself therefore scans that loop while unmarked, sees "visited, not on stack", and is emitted. For the 2-state automaton 0 -a-> 1 (accept), 1 -b-> 1 (the language ab*) the method returns [0, 1]; determinized RegExp("ab*") and RegExp("a+") return [0, 1, 2]. Cycles of two or more states and a loop on state 0 are still caught. The gap dates from #12286 (9.7.0), which added the check on purpose, and is in every release up to 10.6.0 and main. Lucene's own callers (ConcatenateGraphFilter, AnalyzingSuggester) pass acyclic token graphs, so only direct callers that rely on the exception are affected. The fix is the textbook marking: mark a state when it is pushed.

The code (main 645d4fe14a20, Operations.java:1396-1432, verbatim)

#
  private static int topoSortStates(Automaton a, int[] states) {
    BitSet onStack = new BitSet(a.getNumStates());
    BitSet visited = new BitSet(a.getNumStates());
    var stack = new ArrayDeque<Integer>();
    stack.push(0); // Assuming that the initial state is 0.
    int upto = 0;
    Transition t = new Transition();

    while (!stack.isEmpty()) {
      int state = stack.peek(); // Just peek, don't remove the state yet

      int count = a.initTransition(state, t);
      boolean pushed = false;
      for (int i = 0; i < count; i++) {
        a.getNextTransition(t);
        if (!visited.get(t.dest)) {
          visited.set(t.dest);
          stack.push(t.dest); // Push the next unvisited state onto the stack
          onStack.set(state);
          pushed = true;
          break; // Exit the loop, we'll continue from here in the next iteration
        } else if (onStack.get(t.dest)) {
          // If the state is on the current recursion stack, we have detected a cycle
          throw new IllegalArgumentException("Input automaton has a cycle.");
        }
      }

      // If we haven't pushed any new state onto the stack, we're done with this state
      if (!pushed) {
        onStack.clear(state); // remove the node from the current recursion stack
        stack.pop();
        states[upto] = state;
        upto++;
      }
    }
    return upto;
  }

The lines that matter (notes, not source comments):

  • :1400 pushes state 0 without setting its visited or onStack bit.
  • :1414 sets the bit of state, the parent on top of the stack, not of the pushed t.dest.
  • :1417-1419 is the only cycle check: a visited successor whose onStack bit is set.
  • :1424-1429 clear, pop and emit a state that pushed nothing in this pass; every peek rescans its edges from the first one (:1407).

The public method reverses the emitted [1, 0] (Operations.java:1378-1383) and returns [0, 1].

  • Why longer cycles are caught. Every state below the top of the stack has pushed a child, so it is marked; a cycle of two or more states ends in an edge to such an ancestor.
  • When a self-loop is missed. A state with a self-loop that also pushes an unvisited child is marked by that push, and its loop is caught when it rescans its edges after the child is done. The miss needs a non-initial state whose other successors are all visited already, or that has none. Transitions are scanned in (min, max, dest) order (Automaton.java:297-298), so the shape and the labels decide.
  • Why a loop on state 0 is caught. State 0 is never marked visited, so an edge back to it (also 0 -> 0) pushes 0 a second time, and the second copy finds a marked state (the study verifier's argument; the exhaustive check agrees).
  • What still holds. visited keeps any state but 0 from being pushed twice, so the method ends, and its stack holds at most the number of states plus one (state 0 can be pushed twice). Memory stays O(numStates), as the javadoc's RAM sentence says (Operations.java:1359-1360).

The numbers

#

Re-run on main for this doc: of 121,584 cyclic cases (every graph with up to 4 states, in two scan orders), 2,906 are sorted instead of rejected; of 97,648 cyclic random graphs with 2 to 40 states, 13,713. Every miss has only self-loop cycles; 0 false alarms and 0 invalid orders on acyclic graphs. Regexp shapes: ab* and a+ (determinized, 3 states) return [0, 1, 2]; a* (loop on state 0), (ab)*c (cycle 0 -> 1 -> 0) and the cycle 1 -> 2 -> 1 throw.

The method sorts only the states reachable from state 0 (Operations.java:1348), so "cycle" here means a cycle reachable from state 0; neither the check nor the fixes look at unreachable states.

Exposure and likelihood187 words
  • Who. Code that calls Operations.topoSortStates (public; the class is @lucene.experimental) and relies on the documented exception to reject cyclic automata, for example before walking or enumerating the automaton's strings. It accepts ab* or a+ and gets an order back; what happens next depends on that code. Core has had no public Operations.isFinite since #11813 (2022); it now lives in the test framework (AutomatonTestUtil.isFinite).
  • Not default, no in-tree path for conforming token streams. The only main-source callers, ConcatenateGraphFilter.replaceSep and AnalyzingSuggester.replaceSep, get TokenStreamToAutomaton output. Its edges run forward from a position to pos + positionLength, and both stock attribute implementations (PackedTokenAttributeImpl, the default, and PositionLengthAttributeImpl) reject positionLength < 1, so for token streams that follow that contract it is acyclic. TokenStreamToAutomaton does not re-check the value; a custom attribute implementation that skips the check was not examined.
  • Effect. A missing exception. The returned array orders the states as if the self-loops were removed. No hang, no out-of-memory, no crash, no wrong search result inside Lucene. FiniteStringsIterator has its own cycle check.
  • Scale. One call on a 2-state automaton; no index.

Why it looks unintended

#
  • The javadoc promises it: the method "will throw an IllegalArgumentException if a cycle is detected"; the helper's @throws is unconditional.
  • #12286 added the check on purpose, replacing "Behavior is undefined if this automaton has cycles", and TestOperations.testCycledAutomaton asserts it.
  • The code means the textbook check but marks the parent, not the pushed state, so self-loops escape.
The full argument200 words
  • Contract. Operations.java:1348-1350: "This method assumes that the automaton does not contain cycles, and will throw an IllegalArgumentException if a cycle is detected." :1359-1360: "as this method detects cycles, it will never attempt to use infinite RAM." :1394: "@throws IllegalArgumentException if the input automaton has a cycle."
  • History. Before #12286 the javadoc said "Behavior is undefined if this automaton has cycles". In the PR description the author asked "Perhaps we should check if the automaton contains cycles, and throw an IllegalArgumentException if it does?"; mikemccand answered "That would be nice, though it really is illegal usage of the API -- can you detect that w/o much added cost in the iterative solution?"; the author added "a BitSet to track whether the current state is already on the stack"; rmuir wrote "the cycle detection is a really nice bonus. thanks for the unit test for that."; and mikemccand's "Since we detect cycles we will never have an 'attempt to use infinite RAM'" became the javadoc of #12292.
  • Test. TestOperations.testCycledAutomaton (TestOperations.java:80-85) expects the exception. Its random automaton's only back edge goes to the initial state (:295-297), which the code catches, so it cannot see this gap.
The devil's-advocate check173 words

Strongest case for "not a bug": the same sentence begins "This method assumes that the automaton does not contain cycles", and its promise is worded "will throw ... if a cycle is detected", which can be read as best-effort detection; mikemccand called cyclic input "illegal usage of the API", so cyclic input breaks a precondition, the exception is best effort, and Operations is @lucene.experimental. A cross-model reviewer (OpenAI GPT-5.6, refute lens) built this argument and rated it moderate.

Why it fails: the helper's @throws has no such condition ("if the input automaton has a cycle"), #12286 replaced "undefined" with that promise and tested it, and #12292's javadoc relies on it; no comment, test or PR remark treats self-loops as acceptable. @lucene.experimental is about API stability, not correctness. The reviewer reproduced the miss with its own RegExp("ab+") input and judged it real with high confidence. The dispute is about how serious the gap is, not whether it happens; the precondition reading is why the impact stays low: no correct in-tree caller hits it.

Suggested fix

#

Recommended A. Mark the pushed state on-stack, and mark state 0 at the start

Mark a state as on-stack when it is pushed, not its parent when the parent pushes, and mark state 0 at the start: the textbook check, +3/-1 lines, same output for acyclic input. Validated: the test fails before and passes after; 352 automaton, analysis and suggester tests pass, and the study's exhaustive check finds 0 misses.

For an acyclic input both code fixes return exactly the same array as today: the changed lines only decide when to throw, and marking state 0 visited only matters when an edge leads back to state 0, which is itself a cycle.

A. Mark the pushed state on-stack, and mark state 0 at the start (validated by the checks) (recommended)

#

In the private helper: after stack.push(0) add visited.set(0) and onStack.set(0); when pushing an unvisited child, call onStack.set(t.dest) and drop onStack.set(state). A state is then marked from its push to its pop, so its own loop, like any back edge, finds it marked.

     stack.push(0); // Assuming that the initial state is 0.
+    visited.set(0);
+    onStack.set(0);
...
         if (!visited.get(t.dest)) {
           visited.set(t.dest);
+          onStack.set(t.dest);
           stack.push(t.dest); // Push the next unvisited state onto the stack
-          onStack.set(state);
           pushed = true;

Trade-offs

  • +3/-1 lines, no extra work per transition; matches the standard DFS cycle check.
  • A back edge to state 0 is now reported at once instead of after pushing state 0 a second time.

Downstream note

#

Downstream code that uses this exception to reject cyclic automata built from user-supplied patterns lets patterns such as ab* or a+ through; Lucene's own query and analysis code does not pass such automata to it, for token streams that follow the attribute contract.

How it was found

#

Semi-formal. An exhaustive check of the real method against an exact reference, over all 2,097,152 automata with 3 states on the letters a and b, flagged 14,616 misses, and a TLA+ model of the search (TLC) produced the 2-state counterexample 0 -> 1, 1 -> 1 in 2 seconds. An independent verifier then reproduced it with its own tests.

The method in full166 words
  • Method. The study's automaton experiment compared Lucene's real topoSortStates with an exact reference over every automaton with 3 states on the letters a and b (2,097,152 automata): 14,616 were sorted instead of rejected.
  • Model. A TLA+ model of the iterative search, with the graph and every successor order chosen freely, and the invariants "no missed cycle", "no false cycle" and "the output is a reverse topological order of exactly the reachable states". TLC found a counterexample trace of 5 TLC states (the initial state and 4 search steps) for 0 -> 1, 1 -> 1 in 2 s; with the fix, no error on all graphs with 3 states in every order and with 4 states in sorted order.
  • Verifier. An independent verifier wrote its own 9 tests (the minimal case, ab*, a+, a self-loop with a visited sibling, 3 controls, and an exhaustive and a random characterization against Kahn's algorithm, a different sorting method): 4 contract failures, 5 passes, every miss self-loop-only.
