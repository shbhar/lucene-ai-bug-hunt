A re-created PersistentSnapshotDeletionPolicy counts its saved snapshots but returns no commits until an IndexWriter opens with it, and no javadoc says so

After a restart, a re-created PersistentSnapshotDeletionPolicy reports getSnapshotCount() = 1, yet getIndexCommit(1) returns null (the only null case its javadoc names is "not currently snapshotted") and getSnapshots() is empty until an IndexWriter opens with it. By design, but no javadoc says so.

The finding in 30 seconds

#

The save file holds only generation and count pairs, so the constructor fills the counts map and builds no commit. For the saved generations, the generation to IndexCommit map is filled in onInit, which an IndexWriter calls when it opens with the policy (snapshot(), the only other path, is refused until then). getSnapshotCount() reads the counts; getSnapshots() and getIndexCommit(gen) read the commits map, empty until then.

Background: snapshot deletion policies

#
  1. A deletion policy decides which old commits an IndexWriter deletes. SnapshotDeletionPolicy wraps another policy and lets you pin a commit with snapshot(), for example while a backup copies its files, and unpin it with release().
  2. Each commit has a generation number (1 for the first commit) and an IndexCommit object that lists its files. When an IndexWriter opens, it hands the policy the commits it finds in the index (onInit).
  3. PersistentSnapshotDeletionPolicy also writes the pinned generations and their counts to a snapshots_N file, so the pins survive a restart: you create the policy again over that file and pass it to a new IndexWriter.

The finding, step by step

#
  1. You snapshot commit generation 1 through a PersistentSnapshotDeletionPolicy and close the writer. The save file now records generation 1 with count 1.
  2. After a restart you create the policy again over that file with OpenMode.APPEND ("initializing the class with the snapshots information") and, before opening an IndexWriter, ask what is snapshotted: getSnapshotCount() is 1.
  3. You expect getIndexCommit(1) to return the commit of generation 1, which is still in the index, and getSnapshots() to list it.
  4. Instead getIndexCommit(1) is null, though the only case its javadoc names for null is "not currently snapshotted", and getSnapshots() is [], with no error. In the same state snapshot() and release(1) do throw IllegalStateException.
  5. Open an IndexWriter with the same policy and everything agrees: the commit of generation 1, a list of 1. The save file holds only generation counts; the commits come from the writer when it opens.

Who is affected

#

Applications using the opt-in, experimental PersistentSnapshotDeletionPolicy that, after a restart, read getSnapshots() or getIndexCommit(gen) before an IndexWriter has opened with the policy, for example a backup tool that lists saved snapshots first. They see none, without an error, and could think a snapshot is gone (possible, not observed). The getters change nothing; once a writer opens, all agree.

Mechanism, terms and numbers626 words

PersistentSnapshotDeletionPolicy saves each snapshotted commit generation and its reference count to a snapshots_N file, so snapshots survive a restart. When the policy is created again over that file, its constructor loads only those counts and builds no IndexCommit; for the saved generations the IndexCommit objects are handed to it later, by the IndexWriter that opens with it (onInit). Until then getSnapshotCount() reports the saved snapshots while getSnapshots() is empty and getIndexCommit(gen) returns null, although the only case its javadoc names for null is "not currently snapshotted". The design is deliberate and nothing is lost: once a writer opens with the policy, the saved commits that are still in the index are protected and every getter agrees. What is missing is documentation: no javadoc, CHANGES or MIGRATE entry says what the getters of a re-created policy return before it has been passed to an IndexWriter, and the constructor's javadoc suggests more ("initializing the class with the snapshots information"). The case for "intended" is strong, so the fix is a few javadoc sentences, not a code change.

The mechanism (main 645d4fe14a20)

#
  1. Two maps. SnapshotDeletionPolicy keeps refCounts ("Records how many snapshots are held against each commit generation", SnapshotDeletionPolicy.java:43-44) and indexCommits ("Used to map gen to IndexCommit", :46-47).
  2. The constructor fills only the first. The PersistentSnapshotDeletionPolicy constructor calls loadPriorSnapshots() (PersistentSnapshotDeletionPolicy.java:99). It reads the header, the entry count and the (generation, count) pairs of the snapshots_N files it finds, keeps those of the newest in refCounts (:215-241), deletes older or broken save files and sets the next save-file number (:253-262). The file holds nothing else (persist(), :161-184), and it may live in a Directory other than the index (:39-42). The constructor is given only that Directory, so without another source of the commit list it cannot in general build the current commits; it builds none.
  3. For the saved generations, onInit fills the second. onInit sets initCalled = true and puts each commit the writer hands over into indexCommits if its generation is in refCounts (SnapshotDeletionPolicy.java:69-81). The only other code that writes the map, incRef (:115-126), is reached from snapshot() and from an error path of release(IndexCommit), both refused before onInit (item 5). IndexWriter calls onInit, through IndexFileDeleter (IndexFileDeleter.java:237), when it opens with the policy (IndexDeletionPolicy.java:46-62: "The writer locates all index commits present in the index directory and calls this method"). onInit is public, so other code could call it; an IndexWriter opening with the policy is the normal path.
  4. The getters read different maps. getSnapshotCount() sums refCounts (SnapshotDeletionPolicy.java:162-170); getSnapshots() (:157-160) and getIndexCommit(long) (:172-178) read indexCommits. Before onInit they give 1, [] and null.
  5. Only the mutators are guarded. snapshot() (SnapshotDeletionPolicy.java:142-146) and releaseGen() (:94-98, reached from release(long), PersistentSnapshotDeletionPolicy.java:156-159) throw IllegalStateException while initCalled is false ("Used to detect misuse", SnapshotDeletionPolicy.java:55-56). The two commit getters have no guard and no caveat.

The numbers

#

One empty document, one commit (generation 1), one snapshot(), writer closed. A policy created again with OpenMode.APPEND (or, since a save file exists, the default two-argument constructor) over the same directory: getSnapshotCount() = 1, getLastSaveFile() is set, DirectoryReader.listCommits(dir) contains generation 1, getSnapshots() = [], getIndexCommit(1) = null; snapshot() and release(1) throw IllegalStateException ("this instance is not being used by IndexWriter; be sure to use the instance returned from writer.getConfig().getIndexDeletionPolicy()"). After new IndexWriter(dir, config with this instance): getIndexCommit(1) is the commit of generation 1, getSnapshots().size() = 1, and release(1) works and is saved. (On a directory without a save file, OpenMode.APPEND throws IllegalStateException "no snapshots stored in this directory", PersistentSnapshotDeletionPolicy.java:101-103; the default constructor does not.)

Exposure and likelihood199 words
  • Who. Applications that opt into PersistentSnapshotDeletionPolicy (@lucene.experimental) and, after a restart, read getSnapshots() or getIndexCommit(gen) from the re-created policy before an IndexWriter has been opened with it: a backup or restore tool that first lists the saved snapshots, or code that uses getIndexCommit(gen) != null as "is this generation still snapshotted?" before releasing it (a check mentioned as a possible workaround on LUCENE-4973).
  • What goes wrong. Without any error they see no snapshotted commits while getSnapshotCount() reports them, and could conclude that a saved snapshot is gone, then for example skip a backup or a release. These are possible consequences, not observed ones; no user report shows them. The getters change nothing: the saved counts are intact, and once a writer opens with the policy, onInit protects the saved commits that are still in the index and every getter agrees.
  • Default vs opt-in. The policy is opt-in; default codec, directory and merge settings are enough. One document and one snapshot; no scale involved.
  • How likely. Rare. The usual flow, and Lucene's own restart test (testExistingSnapshots), open the writer first. No user report or question about this state was found since it appeared in 4.4.0 (2013).

Why it looks unintended

#
  • getIndexCommit(long) "returns null if this IndexCommit is not currently snapshotted", yet generation 1 is counted and still in the index.
  • The class keeps snapshots "across the life of an application"; nothing says a writer must open before the getters work.
  • The code is intended, but only snapshot() and release() guard this state, so the getters answer without an error.
The full argument388 words
  • The getters' own javadoc. getIndexCommit(long): "Retrieve an IndexCommit from its generation; returns null if this IndexCommit is not currently snapshotted" (SnapshotDeletionPolicy.java:172-175). getSnapshots(): "Returns all IndexCommits held by at least one snapshot" (:157). getSnapshotCount(): "Returns the total number of snapshots currently held" (:162). In the repro state generation 1 is counted by the same object and is in DirectoryReader.listCommits(dir). The javadoc of getIndexCommit(long) names no other case for null and does not mention the state before onInit.
  • The persistent class promises the restart. "a persistence layer so that snapshots can be maintained across the life of an application" (PersistentSnapshotDeletionPolicy.java:34-37); the OpenMode parameter: "open an existing index, initializing the class with the snapshots information" (:85-87).
  • Nothing says what the getters return before a writer opens. Not the javadoc of either class, IndexDeletionPolicy, IndexWriterConfig.setIndexDeletionPolicy (IndexWriterConfig.java:207-220), lucene/CHANGES.txt (LUCENE-4973 at :13564, LUCENE-4976 at :13715) or lucene/MIGRATE.md. The general lifecycle is documented: IndexDeletionPolicy is an "Expert" policy set on IndexWriterConfig (IndexDeletionPolicy.java:23-27) whose onInit gets the commits from the writer (:46-62), and the deletion policy "Only takes effect when IndexWriter is first created" (IndexWriterConfig.java:219). The closest thing to a caveat for this state is the exception message of the two mutators.
  • getIndexCommit(gen) was added for applications that persist generations. On LUCENE-4973 (#6037), Shai Erera wrote on 2013-05-01 "pSDP needs to have a getIC(gen) because if the apps persists the gens, it needs a way to obtain their IC instance". On 2013-05-02, asking that releaseGen accept a generation that is not snapshotted, they mentioned as a possible workaround "calling sdp.getIC(gen) and if not null call release". The thread does not discuss a policy that is read before onInit.
  • Early reads happen upstream, but only of the count. Upstream tests read getSnapshotCount() from a re-created policy before attaching it, after every snapshot was released (count 0; TestPersistentSnapshotDeletionPolicy.java:161-164, :178-181). No upstream test reads the commit getters or a positive count in that state.
  • Not claimed. The snapshot() / release(gen) IllegalStateException (the designed misuse guard; its message names the fix), and "getSnapshots() must list what getSnapshotCount() counts" (one counts snapshot references, the other lists commits; they also differ after attachment when a saved generation has no commit left).
The devil's-advocate check289 words

The strongest case for "intended", from the study's devil's advocate and an executing cross-model reviewer (OpenAI GPT-5.6, verdict not real): LUCENE-4973 moved onInit "to build the gen -> IC map" into SnapshotDeletionPolicy on purpose (Michael McCandless, #6037), and LUCENE-4976 "fixed PSDP to detect if you try to snapshot/release when it's not being used by an IW" (#6040). IndexDeletionPolicy is an Expert writer callback whose onInit supplies the commits; snapshot() protects a commit only "as long as this IndexDeletionPolicy is used"; the policy "Only takes effect when IndexWriter is first created"; upstream's restart test attaches first; and the save Directory may differ from the index, so the constructor is not in general able to build the commits. On that reading, commit lookups before attachment are outside the getters' meaningful domain. The cross-model fact check of this doc (OpenAI GPT-5.6) rated this argument "Strong": "A tiny clarification may be welcome; a defect claim is weak."

What it leaves open: it shows the code is intended, which is why this is classed as a documentation gap and not as a code bug. It does not show that the documentation describes this state. A careful reader can infer it by combining the public IndexDeletionPolicy contract (the writer supplies the commits in onInit) with the implementation (for the saved generations, the generation to IndexCommit map is filled there), but no text connects that contract to the getters of a re-created policy. The persistent class's javadoc points the other way, and the guard added on purpose covers only the mutators, so the getters answer without an error where the mutators fail loudly. The executing reviewer conceded "A narrow javadoc clarification could improve usability"; that clarification is the proposed fix, and nothing more is proposed.

Suggested fix

#

Recommended A. Document the lifecycle (recommended)

Document the lifecycle: a re-created policy reads only the snapshotted generations and their counts; until an IndexWriter has been opened with it, getSnapshots() is empty, getIndexCommit(long) returns null, and snapshot() and release(long) throw. No behaviour change. Validated with gradle: the format and javadoc checks and the snapshot and writer suites pass.

Trade-offs

Turns the silent wrong answer into an exception that names the fix, only in the trap state; a fresh or attached policy behaves as before. But it changes behaviour in an experimental API: code that reads these getters on a re-created policy before attaching it and copes with null or [] would now throw. C. Resolve the commits in the constructor (not built)

#

When the save Directory also holds the index, fill indexCommits from DirectoryReader.listCommits(dir) for the loaded generations.

Trade-offs

Works only when the save file sits next to the index (the class allows another Directory), adds index I/O and a new failure path to a constructor that reads one small file, hands out reader-side commits that onInit later replaces with the writer's, and reverses the 2013 design in which commits come only from the writer. Not built or run.

Downstream note

#

Backup or restore layers built on this policy that list snapshots from a re-created policy before opening an IndexWriter would report none; opening the writer first avoids it.

History

#

Introduced in 4.4.0 by LUCENE-4973 (#6037, 30e43c836ab, 2013-05-02), which split the state into counts loaded by the constructor and commits filled in onInit; LUCENE-4976 (#6040) added getSnapshots() a day later. Every release from 4.4.0 to 10.6.0 and main behaves this way; 4.3.1 had an older id-based API. Not fixed upstream.

  • Second ingredient: LUCENE-4976 ("use single file to hold PersistentSnapshotDeletionPolicy state on disk"; #6040, 2013-05-03, efeaac746ae / branch_4x c82d9836349) added List<IndexCommit> getSnapshots() over the same map and the initCalled guard on snapshot() and releaseGen(). Same first release.
  • Before: 3.1.0 to 4.3.1 had an id-based API whose getSnapshots() listed the saved snapshot before attachment; getSnapshot(id) already returned null before attachment there.

LFV-890, snapshot of 2026-11-08

Registry title
A PersistentSnapshotDeletionPolicy re-opened over its save file counts the persisted snapshots, but getSnapshots() is empty and getIndexCommit(gen) returns null until an IndexWriter has opened with it, and no javadoc states this precondition (documentation gap; the behaviour is by design)
Area
index / deletion policies (SnapshotDeletionPolicy and PersistentSnapshotDeletionPolicy restart lifecycle, javadoc)
Priority
Low, rank 1298: This by-design documentation gap in the opt-in experimental PersistentSnapshotDeletionPolicy loses nothing and only misleads early readers.
Impact class
minor
Impact note
Applications that opt into the @lucene.experimental PersistentSnapshotDeletionPolicy and, after a restart, read getSnapshots() or getIndexCommit(gen) from the re-created policy before opening an IndexWriter with it (for example a backup or restore tool that lists the persisted snapshots first) silently see no snapshotted commits while getSnapshotCount() reports them; nothing is deleted, written or corrupted, the getters reflect the persisted snapshots once a writer has opened with the policy, and snapshot()/release(gen) fail loudly with an IllegalStateException that names the fix; default codec and directory, no scale needed.
Summary
You restart an application that uses PersistentSnapshotDeletionPolicy, create the policy again over its save file with OpenMode.APPEND (whose javadoc says this opens the existing snapshots, 'initializing the class with the snapshots information'), and ask it which commits are snapshotted before you open an IndexWriter with it. You expect getSnapshots() and getIndexCommit(gen) to show the persisted snapshot that getSnapshotCount() counts, or the javadoc to say that the policy must first be passed to an IndexWriter. Instead getSnapshotCount() is 1 while getSnapshots() is empty and getIndexCommit(gen) returns null, which its javadoc says means 'not currently snapshotted'; this is by design (the IndexCommit objects come from the writer's onInit call), but no javadoc states the precondition.
