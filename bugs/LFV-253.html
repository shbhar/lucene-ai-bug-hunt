CombinedFieldQuery reports a NaN max score under AxiomaticF2LOG/F2EXP, so top-k search skips the best hits

Under AxiomaticF2LOG or AxiomaticF2EXP, CombinedFieldQuery reports NaN as its highest possible score, so top-k search of it OR a TermQuery skips documents that match only the CombinedFieldQuery: search(q, 10) returns doc 0 (2.20) first, not doc 2000 (6.38). Releases 10.1.0 to 10.5.2 and main; the default BM25 is fine.

The bug in 30 seconds

#

Top-k search skips documents that cannot beat the current k-th hit, using each clause's maximum possible score. CombinedFieldQuery computes that maximum from an infinite term frequency, which AxiomaticF2LOG and AxiomaticF2EXP turn into NaN. The pruning code then treats the query as never good enough on its own.

  1. Index 3,000 documents with AxiomaticF2LOG. Doc 2000 has the word x four times in short fields a and b, doc 0 once in long fields, and the other 2,998 documents only c:y. Search SHOULD CombinedFieldQuery(x on a, b) + SHOULD TermQuery(c:y) with searcher.search(q, 10).
  2. You expect doc 2000 first: the exhaustive search scores it 6.383921, doc 0 2.1975672 and every c:y document 0.00022. You get doc 0 first, then nine c:y documents; doc 2000 is not in the top 10. No error.
  3. Why: to let top-k skip documents, CombinedFieldQuery reports its maximum score as the score of a term that occurs infinitely often, score(+Infinity, 1). The similarity API forbids an infinite frequency; these two similarities compute freq / (freq + ...), and Infinity / Infinity is NaN.
  4. After 1,000 hits the collector only accepts scores above the c:y score, 0.00022233339. The pruning scorer asks whether the CombinedFieldQuery alone can still beat that: NaN >= 0.0002223334 is false. So from then on it makes c:y required and skips the documents that have only x, including doc 2000.
  5. Fix: use score(Float.MAX_VALUE, 1), the bound the API documents (7.31 on this index). One line in each copy of the class; the test and the 2,336 tests of the search package pass.

Who is affected

#

Applications that build a CombinedFieldQuery in code and score with AxiomaticF2LOG or AxiomaticF2EXP, on 10.1.0 to 10.5.2 or main, when exactly one CombinedFieldQuery sits next to another scoring clause, such as a TermQuery or a FeatureField boost. Plain search(q, n) on 3,000 documents is enough, once 1,000 hits are passed. BM25, a lone CombinedFieldQuery and one-per-term disjunctions are fine.

Mechanism, terms and numbers758 words

CombinedFieldQuery's scorer reports simScorer.score(Float.POSITIVE_INFINITY, 1) as the highest score it can produce (CombinedFieldQuery.java:416). SimScorer#score requires a finite, positive freq and documents score(Float.MAX_VALUE, 1) as the bound. For the core similarities AxiomaticF2LOG and AxiomaticF2EXP, which the class javadoc counts as compatible, the infinite freq gives Infinity / Infinity = NaN, so getMaxScore returns NaN. When such a query is one SHOULD clause next to another scoring clause, MaxScoreBulkScorer reads the NaN as "this clause alone can never reach the minimum competitive score", makes the other clause required, and skips every document that matches only the CombinedFieldQuery. On 3,000 documents IndexSearcher#search(q, 10) returns doc 0 (2.1975672) first while the exhaustive search ranks doc 2000 (6.383921) first, and Lucene's own oracle CheckHits.checkTopScores fails. Returned scores are correct and nothing throws with assertions off. Introduced by #13999 (10.1.0, then in the sandbox module); every release from 10.1.0 to 10.5.2 and main is affected; the fix is to pass Float.MAX_VALUE, as MaxScoreCache does. No upstream report was found.

Terms

#
  • CombinedFieldQuery (BM25F): scores a term over several fields as if they were one combined field, with the searcher's similarity. @lucene.experimental, in core since 10.2.0 (a sandbox class in 10.1.0).
  • Max score: Scorer#getMaxScore(upTo) is "the maximum score that documents between the last target ... and upTo" can get (Scorer.java:75-79). Top-k scorers use it to skip documents.
  • Minimum competitive score: once IndexSearcher#search(q, n) has counted more than 1,000 hits (IndexSearcher.java:100), the collector tells the scorer to skip documents scoring below Math.nextUp of the n-th best score so far (TopScoreDocCollector.java:154-164).
  • Essential and required clauses (MAXSCORE): clauses whose summed max scores stay below the minimum are non-essential; a competitive document must match an essential clause. With a single essential clause, if the others cannot add enough, the best non-essential clause becomes required.

The bug (code at ea57360912ed)

#
  1. CombinedFieldScorer sets this.maxScore = simScorer.getSimScorer().score(Float.POSITIVE_INFINITY, 1L); (CombinedFieldQuery.java:416) and returns it from getMaxScore for every upTo (:446-448). Documents are scored with their real, finite freq, so returned scores are right.
  2. AxiomaticF2LOG and AxiomaticF2EXP compute tfln = freq / (freq + s + s * docLen / avgFieldLength) (AxiomaticF2LOG.java:62, AxiomaticF2EXP.java:72): Infinity / Infinity = NaN, and Math.max(0, NaN) stays NaN (Axiomatic.java:107-116).
  3. A TOP_SCORES disjunction of 2 or more SHOULD clauses with minimumShouldMatch <= 1 runs on MaxScoreBulkScorer (BooleanScorerSupplier.java:308-328), and so does one with FILTER clauses and minimumShouldMatch exactly 1 (:233, :345, :364). With FILTER clauses and minimumShouldMatch 0 it runs on ReqOptSumScorer (:176); the security probe found that shape wrong too (mechanism not traced).
  4. partitionScorers makes a clause non-essential only while (float) sumUpperBound(sum, n) < minCompetitiveScore (MaxScoreBulkScorer.java:500-502). A sum with NaN is never less, so the CombinedFieldQuery stays essential; in the window of doc 2000 the TermQuery's max score, 0.00022233339 (from the block impacts), is below the minimum, so there it becomes non-essential. Its bound over the whole segment, 0.0003335001, is above the minimum, and from doc 2818 on it is essential again.
  5. With a single essential clause the loop tests (float) maxPossibleScoreWithoutPreviousClause >= scorable.minCompetitiveScore (:540). For NaN that is false, so the TermQuery becomes required and, in those windows, documents that match only the CombinedFieldQuery are skipped.

Exposure and likelihood368 words
  • Who is exposed. Applications that build a CombinedFieldQuery in code (no stock Lucene query parser creates one) and score with AxiomaticF2LOG or AxiomaticF2EXP, on 10.1.0 (sandbox class), 10.2.0 to 10.5.2, or main. The open PR #14262 would make QueryBuilder build CombinedFieldQuery instances without touching the max-score line, so if merged more applications could reach this (not tested).
  • Which queries. In every executed wrong case exactly one CombinedFieldQuery was among the scoring clauses of a pruned query, next to another scoring clause. That is necessary, not sufficient: hits are lost only where the other clauses' window max score falls below the minimum competitive score, and a DisjunctionMaxQuery parent or a minimumShouldMatch=2 disjunction returned correct hits with -da. Executed wrong: one CombinedFieldQuery as a SHOULD clause next to a TermQuery or a FeatureField query, also with FILTER or MUST_NOT clauses or nested in a MUST conjunction (the security probe: 7 of its 11 shapes gave a wrong top hit with a total-hits threshold of 1). Executed correct: a lone CombinedFieldQuery, one per term (2 or more clauses), a FILTER CombinedFieldQuery, a plain conjunction, a DisjunctionMaxQuery, a minimumShouldMatch=2 disjunction (-da).
  • Default or opt-in. Opt-in on both sides: the default BM25 gives a finite bound, and CombinedFieldQuery is @lucene.experimental. Nothing else is special: default codec, plain IndexSearcher, IndexSearcher#search(q, n).
  • Scale. No large index is needed: 3,000 documents with the default API, which must count more than 1,000 hits before pruning starts (the lost document comes after that); 301 with a total-hits threshold of 1. Single- and multi-segment indexes fail the same way under AxiomaticF2LOG (AxiomaticF2EXP ran on one segment only).
  • What you see. The wrong best hits, correct scores for what is returned, no exception with assertions off. With assertions on, a minimumShouldMatch=2 disjunction trips assert Float.isNaN(maxScore) == false in WANDScorer (WANDScorer.java:91); with -da that shape only loses pruning.
  • Downstream (code reading only): Elasticsearch's combined_fields query rejects every similarity but BM25; OpenSearch's has no similarity check, but no Axiomatic similarity was found in stock OpenSearch; Solr does not use the query.
  • How likely. Plausible (registry likelihood): the pairing is rare, but once chosen the failure is deterministic with ordinary data. Registry priority: Medium.

Why it is a bug, not intended

#
  • SimScorer#score requires a freq that is "finite and positive" and names score(Float.MAX_VALUE, 1) as the bound; every other max-score computation uses it.
  • The class javadoc counts Axiomatic as compatible (default computeNorm); the change that added the line promised "non-infinite maximum scores".
  • AssertingSimilarity asserts a finite freq, and trips on this line even with BM25.
The full argument253 words

The contract, in its own words (at ea57360912ed):

  • SimScorer#score (Similarity.java:201-221): "freq is the document-term sloppy frequency and must be finite and positive"; "the maximum score that this scorer can produce is bound by score(Float.MAX_VALUE, 1)". MaxScoreCache.java:48, the sandbox TermAutomatonScorer.java:364 and BaseSimilarityTestCase.java:382 all use Float.MAX_VALUE.
  • Scorer#getMaxScore (Scorer.java:75-79) returns "the maximum score" of the documents in range; NaN is not a maximum of finite scores.
  • CombinedFieldQuery javadoc (CombinedFieldQuery.java:60-64): compatibility requires additive norms, which "hold for all similarities that don't customize Similarity#computeNorm"; Axiomatic extends SimilarityBase and keeps it. The query "allows other similarities besides BM25Similarity" (:72-75).
  • CHANGES for #13999 (lucene/CHANGES.txt:2087-2088): "CombinedFieldQuery now returns non-infinite maximum scores, making it eligible to dynamic pruning."

Tests. AssertingSimilarity asserts Float.isFinite(freq) (AssertingSimilarity.java:76-77); a probe that wraps the default BM25 in it fails at CombinedFieldQuery.java:416 on every scored search. BaseSimilarityTestCase asserts that score(Float.MAX_VALUE, 1) is not NaN and bounds the score for every core similarity, F2LOG and F2EXP included (BaseSimilarityTestCase.java:382-391), and RandomSimilarity rotates both into random tests (RandomSimilarity.java:126-127).

Why the tests miss it. #13999 added no test, and TestCombinedFieldQuery.randomCompatibleSimilarity() picks only BM25, Boolean, Classic, LMDirichlet and LMJelinekMercer (TestCombinedFieldQuery.java:392-401); for those score(+Infinity, 1) is finite or +Infinity, never NaN.

History. #13999's description: "returning the maximum score that the sim scorer can return, which in the case of BM25 is bounded by the IDF". Its discussion covers a benchmark and a slowdown; nothing about non-finite freqs or other similarities.

The devil's-advocate check218 words

The strongest case for "works as designed": both CombinedFieldQuery and the Axiomatic similarities are @lucene.experimental; the upstream test only covers BM25, Boolean, Classic and the LM similarities; and in 2017, in LUCENE-8083 (#9131), a committer wrote that AxiomaticF2EXP and AxiomaticF2LOG "can't work with maxScore" and should be removed or moved out (#9058).

Why it fails:

  1. @lucene.experimental allows API changes, not wrong top hits.
  2. The upstream test list is test scope, not a documented exclusion; the javadoc's only rule includes Axiomatic.
  3. The 2017 remark was superseded: #9058 (LUCENE-8010) was resolved as fixed in 2018 and the similarities stayed in core, #9131 was closed as invalidated by the indexing of impacts, and today BaseSimilarityTestCase asserts a non-NaN score(Float.MAX_VALUE, 1) bound for them, which TermQuery already prunes with.
  4. The caller breaks the documented precondition, not the similarity.

Conceded: for the 21 probed configurations where score(+Infinity, 1) is +Infinity (Classic, LM, DFI, AxiomaticF1/F3, IB with the log-logistic distribution) the bound is conservative and results stay correct; only pruning is lost, and no pruning ratio is promised. That is a performance remark, not this bug; the bug is the NaN, which is not an upper bound and loses hits.

The devil's advocate, the OpenAI GPT-5.6 reviewers and the adjudication found the case weak. The issue should answer the 2017 remark up front.

Suggested fix

#

Recommended Use score(Float.MAX_VALUE, 1L), in core and in the sandbox copy

Use the documented bound: score(Float.MAX_VALUE, 1L) instead of score(Float.POSITIVE_INFINITY, 1L), as MaxScoreCache does, in core CombinedFieldQuery.java:416 and in the deprecated sandbox copy. The test passes 6 of 6, and so do the closest suites, the sandbox tests and all 2,336 tests of the core search package.

// CombinedFieldQuery.CombinedFieldScorer (core :416 and sandbox :459)
// was: this.maxScore = simScorer.getSimScorer().score(Float.POSITIVE_INFINITY, 1L);
this.maxScore = simScorer.getSimScorer().score(Float.MAX_VALUE, 1L);

Use score(Float.MAX_VALUE, 1L), in core and in the sandbox copy (validated by the checks) (recommended)

#

One line in each copy of CombinedFieldScorer's constructor (core :416, sandbox :459). SimScorer#score promises that this value bounds every score, BaseSimilarityTestCase checks the promise for every core similarity, and MaxScoreCache relies on it for TermQuery.

// CombinedFieldQuery.CombinedFieldScorer (core :416 and sandbox :459)
// was: this.maxScore = simScorer.getSimScorer().score(Float.POSITIVE_INFINITY, 1L);
this.maxScore = simScorer.getSimScorer().score(Float.MAX_VALUE, 1L);

Trade-offs

  • No bound change for BM25 and the 40 DFR configurations: their score(+Infinity, 1) and score(Float.MAX_VALUE, 1) are equal in the finder's probe of 75 configurations, which uses one synthetic set of statistics (an observation, not a proof).
  • For the 21 configurations whose score(+Infinity, 1) is +Infinity (Classic, the 3 LM similarities, the 3 DFI ones, AxiomaticF1/F3, the 10 IB ones with the log-logistic distribution) the bound becomes finite, so pruning can apply to them too; for Classic it is still huge (6.08e19), so little changes there. No benchmark was run.
  • Not covered: CombinedFieldScorer.freq() multiplies term frequencies by field weights in float (:426-428), and weights are only checked to be at least 1, so a weight near Float.MAX_VALUE can make a document's freq +Infinity; the freq < 0 overflow check (:429) cannot catch that. A separate edge, untested.

How it was found

#

Code reading. While modelling the score bounds of three query classes, an AI tool checked each bound against the SimScorer#score contract and saw the infinite freq. A probe of 75 similarity configurations gave NaN for AxiomaticF2LOG and F2EXP, and a JUnit test on the stock jar then showed the wrong top hit. The unit's proofs covered other classes.

The method in full151 words

Method: code reading (the hunt's non-formal tier), a hunt unit (DisjunctionMax, Synonym and CombinedField queries), 2026-10-26.

  • The finder, an AI tool, listed every max-score expression in the three classes and checked each against the SimScorer#score contract ("finite and positive" freq; bound score(Float.MAX_VALUE, 1)). CombinedFieldScorer passes Float.POSITIVE_INFINITY.
  • A probe of score(+Infinity, 1), score(Float.MAX_VALUE, 1) and the maximum over finite freqs for 75 core similarity configurations gave NaN for AxiomaticF2EXP and AxiomaticF2LOG and +Infinity for 21 others (a conservative bound: correct results, only no pruning of that clause).
  • A deterministic public-API JUnit test on the stock main jar then showed the NaN bound and the wrong pruned top hit (2 of 2 fail, 100 of 100 over 50 iterations).
  • The candidate record says it was not found by SMT. The unit's SMT proofs and bounded-exhaustive harnesses covered the DisjunctionMaxQuery bound and SynonymQuery impact merging, not CombinedFieldQuery. Independent checks followed (below).

Bug record

#

LFV-253, snapshot of 2026-10-27

Registry title
CombinedFieldQuery computes its max score as score(+Infinity, 1), which is NaN under AxiomaticF2LOG/F2EXP, so top-k pruning silently drops the best hits
Area
search / CombinedFieldQuery (BM25F) max-score bound under dynamic pruning (CombinedFieldScorer.getMaxScore as used by MaxScoreBulkScorer)
Priority
Medium, rank 56: It has the same profile as LFV-190 (a core similarity whose NaN max-score bound makes top-k pruning silently drop the best hits since 10.1), but only for the rare AxiomaticF2 plus CombinedFieldQuery pairing.
Impact class
silent wrong results
Impact note
Applications that pair CombinedFieldQuery (@lucene.experimental) with the non-default AxiomaticF2LOG or AxiomaticF2EXP similarity, on 10.1.0 (sandbox class) through 10.5.2 or on main, get wrong top hits with no error when exactly one CombinedFieldQuery sits next to another scoring clause in a pruned disjunction (for example SHOULD CombinedFieldQuery plus SHOULD TermQuery or FeatureField query, also with filters or nested in a conjunction): a plain IndexSearcher#search(q, n) is enough once the default total-hits threshold of 1000 is passed, and documents that match only the CombinedFieldQuery are skipped; the default BM25 (and Classic and DFR) is not affected, a lone CombinedFieldQuery and disjunctions of two or more CombinedFieldQuery clauses (the multi-term pattern of the search package docs) gave correct results, and no special scale is needed (3000 documents suffice).
Summary
You score a query with CombinedFieldQuery under the core AxiomaticF2LOG (or AxiomaticF2EXP) similarity, which the class javadoc counts as compatible because it keeps the default computeNorm, put it in a BooleanQuery next to another scoring clause such as a TermQuery, and expect IndexSearcher#search(q, 10) to return the same top hits as an exhaustive search. CombinedFieldScorer reports score(Float.POSITIVE_INFINITY, 1) as its max score, although SimScorer#score requires a finite freq and documents score(Float.MAX_VALUE, 1) as the bound; for the F2 similarities that is Inf/Inf = NaN, and MaxScoreBulkScorer, for which NaN is never below the minimum competitive score, then makes the other clause required. Documents that match only the CombinedFieldQuery are skipped: in a 3000-document index the default search returns doc 0 (score 2.1975672) as the top hit instead of doc 2000 (6.383921), and the upstream oracle CheckHits.checkTopScores fails.
