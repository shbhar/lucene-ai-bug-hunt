SparseFixedBitSet.ramBytesUsed() never subtracts the blocks that clear releases, so set/clear churn inflates it without bound

When clear(int) or clear(int, int) empties a 4096-bit block, SparseFixedBitSet drops the block's array but keeps counting its bytes, and the next set there counts a new array: 1,000 set(0)/clear(0) cycles report 24,088 bytes for an 88-byte set. Only the estimate is wrong; every release since 5.0.0.

The finding in 30 seconds

#

SparseFixedBitSet splits its bits into 4096-bit blocks. A block with no set bit holds no array; the first set in it allocates a small long[], and a clear that empties it drops that array again. ramBytesUsed() returns a counter that tracks these arrays.

  1. You create new SparseFixedBitSet(1): ramBytesUsed() is 88. You call set(0): the set allocates a one-long array for the bit's 4096-bit block and reports 112 (24 bytes more), which is right.
  2. You call clear(0). The block is now empty, so the set drops its array ("release memory, there is nothing in this block anymore"). You expect 88 again, what a fresh set reports and holds.
  3. You get 112: the dropped array's 24 bytes stay counted. Each further set(0)/clear(0) adds 24 more; 1,000 cycles report 24,088 bytes while the set really holds 88.
  4. Why: ramBytesUsed is a running counter. Every allocation adds to it, but neither place that drops an emptied block, clear(int) and the middle blocks of clear(int, int), subtracts. Only the no-argument clear() (since 9.7.0) resets it.
  5. Ranges drift the same way: set(0, 1 << 20) then clear(0, 1 << 20) leaves 138,312 bytes counted for 3,144 bytes held; ten such cycles report 1,354,824. (set(int, int) is public since 10.5.0, #16107; on older releases new SparseFixedBitSet(12288), set(4096), clear(0, 12288) shows the same leak: 136 counted, 112 held.)

Who is affected

#

Code that keeps one SparseFixedBitSet alive, repeatedly empties and refills its blocks, and reads ramBytesUsed(), for example to size a cache. The estimate only grows, so a budget built on it frees or flushes too early; the error is an over-report, and no wrong result was observed. Sets built once by setting bits, the usual use, never drift.

Mechanism, terms and numbers511 words

SparseFixedBitSet keeps ramBytesUsed as a running counter: the constructor and clear() compute it from the arrays, and every block allocation or growth adds to it. When clear(int) empties a 4096-bit block, the class drops that block's long[], and clear(int, int) drops every middle block of its range, but neither subtracts the dropped array's bytes; the next set in that block allocates a new array and adds its bytes again. So ramBytesUsed() grows by at least 24 bytes per release and re-allocation, without bound until clear(), while the set's real footprint stays the same. The reproduced effect is an over-reported Accountable estimate; no wrong search result, hit or index data was observed. Every release from 5.0.0 through 10.6.0 and main is affected; a few lines on the two release paths fix it.

Terms

#
  • Block: SparseFixedBitSet divides its bits into blocks of 4096. Per block it keeps a 64-bit index (which of the block's 64 words are non-zero) and a long[] with only those words; an empty block has index 0 and no array (SparseFixedBitSet.java:24-34, :54-58).
  • The counter: ramBytesUsed is a field, not a computation. ramBytesUsed() just returns it (:806-809).

The bug (file:line at 5adff78bb168)

#
  1. The constructor and clear() set the counter from the arrays: BASE_RAM_BYTES_USED + sizeOf(indices) + shallowSizeOf(bits) (:64-76, :79-87). The no-argument clear() (added in 9.7.0, #12268) is the only place it ever goes down.
  2. Every allocation adds to it: insertBlock adds SINGLE_ELEMENT_ARRAY_BYTES_USED (24 bytes) for a new block's long[1] (:209-215), orLong the same (:309), the or() fast path adds 24 plus 8 per further slot for a copied new block (:600-601), and growth adds 8 bytes per new slot (:240-241, :612-614).
  3. clear(int) reaches removeLong (:274-293). When the block's index becomes 0 it runs // release memory, there is nothing in this block anymore / this.bits[i4096] = null; (:318-320) and leaves the counter alone.
  4. clear(int, int) nulls every middle block, bits[i] = null; (:343-347), and leaves the counter alone; its first and last blocks go through clearWithinBlock and removeLong (:357-371) and leak the same way.
  5. The next set in a released block takes the index == 0 branch and calls insertBlock again (:197-200), adding another 24 bytes.

Exposure and likelihood174 words
  • Opt-in and rare: the class is @lucene.internal (SparseFixedBitSet.java:36). Query-time sets from BitSet.of and the sparse live-docs reader only set bits, so they do not drift.
  • In tree (read, not executed): the only set-and-clear user is the hasNoValue set of single-valued numeric doc-values updates: reset(doc) sets a bit, add(doc, value) clears it, and ramBytesUsed() includes the set (NumericDocValuesFieldUpdates.java:169-192, :205-209). The over-count is per updates object (one per resolved update packet, segment and field); ReadersAndUpdates.addDVUpdate adds each one's ramBytesUsed() to the segment's total, several can be pending (ReadersAndUpdates.java:148-164), and IndexWriter writes doc-values updates once the reader pool's total passes half the RAM buffer (IndexWriter.java:807-864). So by reading, those writes can happen earlier. Nothing more is claimed.
  • No scale needed: one bit in a 1-bit set, one cycle, assertions on or off.
  • Unbounded: at least 24 bytes per release and re-allocation, more for a block that had grown, until the no-argument clear(); before 9.7.0 there was no clear(), so nothing reset it while the set lived.

Why it looks unintended

#
  • Accountable.ramBytesUsed() returns "an estimate of the JVM heap memory used by this object"; the class computes it exactly in its constructor and clear().
  • The release branch's own comment: "release memory, there is nothing in this block anymore".
  • Upstream fixed this counter's opposite drift as a bug: or() not adding new blocks' bytes (#11600, fixed in 9.2.0).
The full argument138 words
  • Contract: Accountable.java:34-40, present tense: the heap this object uses, not every array it ever held.
  • Tests: BaseDocIdSetTestCase.testRamBytesUsed / assertRamBytesUsed compare the measured heap of a BitDocIdSet that wraps a SparseFixedBitSet built with set against that wrapper's ramBytesUsed(), which adds this class's estimate (BaseDocIdSetTestCase.java:102-125, TestSparseFixedBitDocIdSet.java:25-48, BitDocIdSet.java:61-62): indirect coverage, for sets built by set only. No upstream test reads ramBytesUsed() after clear(int) or clear(int, int).
  • History: both release sites came with LUCENE-6021 (#7083, c179a9bf947, 2014-10-24), which added the two clear methods without touching the counter. Three days later LUCENE-6024 (a25c4c77db4) fixed the other counter, nonZeroLongCount, at the same two sites and left ramBytesUsed alone: consistent with an oversight rather than a decision. #11600 (fixed by #882) was reported while debugging a cache that used far more memory than expected.
The devil's-advocate check165 words

The strongest case for "intended": SparseFixedBitSet, BitSet and Accountable are @lucene.internal; ramBytesUsed is documented only as "an estimate"; the class accepts overestimates ("we may slightly overestimate size here, but keep it cheap"); the error is in the safe direction; and the in-tree effect is negligible. An independent reviewer from another model family (OpenAI GPT-5.6) reproduced the bug and agreed on the cause and the fix, but rated it out of contract on these grounds.

Why it fails: @lucene.internal limits API-stability promises, not correctness, and upstream fixed this counter's mirror-image drift (#11600) and a wrong ramBytesUsed() under non-8-byte object alignment (LUCENE-6242, #7304) as bugs. The "slightly overestimate" comments accept bounded slack on a live array, not the bytes of arrays that no longer exist, and this drift has no bound (9.8 times the largest real footprint after ten range cycles). These arguments bound the impact, hence Low; they are not evidence of intent, though a maintainer could still decline the change as low value.

Suggested fix

#

Recommended Subtract exactly what was counted for the released array

Subtract, on both release paths, exactly the bytes the counter added for the dropped array: a one-element array plus 8 bytes per further slot (a 3-line helper and 4 lines at the two release sites). Validated: the repro passes, and the SparseFixedBitSet, FixedBitSet and numeric doc-values update suites and the core lint checks pass.

/**
 * Returns what {@link #ramBytesUsed()} counted for a block's array: a one-element array plus 8
 * bytes per further slot, as every allocation and growth site adds it.
 */
private static long countedBytes(long[] blockBits) {
  return SINGLE_ELEMENT_ARRAY_BYTES_USED + ((long) (blockBits.length - 1) << 3);
}

// removeLong, before this.bits[i4096] = null:
ramBytesUsed -= countedBytes(this.bits[i4096]);
// clear(int, int), middle-block loop, before bits[i] = null:
if (bits[i] != null) {
  ramBytesUsed -= countedBytes(bits[i]);
}
All options and trade-offs3 options · 480 words

Two options were validated with gradle in a scratch worktree of 5adff78bb168; the third is by reading.

Subtract exactly what was counted for the released array (validated by the checks) (recommended)

#

In removeLong (SparseFixedBitSet.java:318-320) and the middle-block loop of clear(int, int) (:343-347), subtract a helper's value before nulling the array. Every add site counts a block's array as SINGLE_ELEMENT_ARRAY_BYTES_USED + 8 * (length - 1) (:214, :241, :309, :601, :614), so this exactly reverses the counter's own charge for the released array; once every block is released the counter is back at its fresh value. The bounded slack the class accepts for live grown arrays is unchanged.

/**
 * Returns what {@link #ramBytesUsed()} counted for a block's array: a one-element array plus 8
 * bytes per further slot, as every allocation and growth site adds it.
 */
private static long countedBytes(long[] blockBits) {
  return SINGLE_ELEMENT_ARRAY_BYTES_USED + ((long) (blockBits.length - 1) << 3);
}

// removeLong, before this.bits[i4096] = null:
ramBytesUsed -= countedBytes(this.bits[i4096]);
// clear(int, int), middle-block loop, before bits[i] = null:
if (bits[i] != null) {
  ramBytesUsed -= countedBytes(bits[i]);
}

Trade-offs

  • Reverses exactly what was counted, under any JVM object alignment: 0 drift with 8-, 16- and 32-byte alignment in a 100-cycle probe of a block grown to 6 slots.
  • The helper must stay in step with the add sites (one formula, next to them).
  • Cost: one subtraction per released block.

What the checks validated

  • Scratch worktree of 5adff78bb168, gradle, OpenJDK 25.0.3: the repro fails stock (assertions on and off, seed DEADBEEF) and passes with this fix (on and off).
  • With the fix: TestSparseFixedBitSet, TestSparseFixedBitDocIdSet, TestFixedBitSet, TestNumericDocValuesUpdates and TestMixedDocValuesUpdates plus the repro pass (106 tests, 1 skipped, 0 failures, seed DEADBEEF).
  • checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the repro in place.

Subtract RamUsageEstimator.sizeOf of the released array (validated by the checks)

#

ramBytesUsed -= RamUsageEstimator.sizeOf(this.bits[i4096]); before nulling in removeLong, and the same for each non-null middle block in clear(int, int) (+4 lines).

Trade-offs

Simpler, and identical to the first option with the default 8-byte object alignment. With -XX:ObjectAlignmentInBytes=16 or 32, sizeOf of a grown array can be smaller than what the add sites counted, so a small drift remains: 8 bytes per cycle for a block grown to 6 slots (800 bytes after 100 cycles, against 0 with the first option).

What the checks validated

Scratch worktree of 5adff78bb168, gradle: the repro and TestSparseFixedBitSet pass with this fix (20 tests, seed DEADBEEF). The alignment numbers come from a plain-Java probe on the main core jar.

Recompute ramBytesUsed() from the live arrays

#

Drop the running counter and sum the arrays on each call.

Trade-offs

Exact, but O(number of blocks) per call on a method that callers poll; the running counter exists to keep it cheap. Not run.

How it was found

#

Semi-formal: a proof-obligation audit of SparseFixedBitSet's contract, here the obligation that the Accountable RAM counter matches the arrays the set holds after every set and clear, checked by reading each path that allocates or drops a block and witnessed by an executable repro on main.

The method in full110 words
  • Obligation: after any sequence of set, clear(int), clear(int, int) and clear(), ramBytesUsed() equals what the constructor-style computation over the live arrays gives (up to the documented slack of a grown array).
  • Audit: every path that allocates or grows a block adds to the counter; the two paths that drop a block do not subtract, so the obligation fails after the first release.
  • Witness: a probe compared the counter with the footprint measured by RamUsageTester at each step (88, 112, 88, 88 measured against 88, 112, 112, 136 counted), then reduced to the one-cycle test (2026-11-03, main 5adff78bb168).
  • Then: independent reproduction and adversarial reviews (see Independent checks).

Summary
You create a SparseFixedBitSet, set one bit and clear it again, so the 4096-bit block that held it becomes empty and the class drops that block's long[]. You expect ramBytesUsed() to return to the value of a fresh set: Accountable documents it as an estimate of the heap the object uses, and the class computes it exactly from its arrays in the constructor and in clear(). Instead the dropped array's 24 bytes stay counted (new SparseFixedBitSet(1) reports 88, and 112 after set(0) and clear(0)), and every later set in that block adds a new array's bytes, so repeating the cycle makes the estimate grow without bound while the set's real footprint stays the same.
