On Lucene 3.4.0 to 10.6.0 SynonymMap.Builder.build() can lose the rule of a well-formed word, or throw, when another key holds an unpaired surrogate (released lines only)

Lucene 3.4.0 to 10.6.0 only, not branch_11x or main: when a synonym key holds an unpaired surrogate, SynonymMap.Builder.build() can hand the FST its keys out of order. With assertions off, another, well-formed word's rule can then never fire, with no error, or (run from 8.4.0) build() can throw.

Background: three pieces

#
  1. A synonym map is built from rules such as a => x. SolrSynonymParser runs each rule word through an analyzer that the application chooses and gives the result to SynonymMap.Builder as a key.
  2. build() stores the keys in an FST, a compact sorted dictionary. The FST compiler must get its keys in sorted order, and here each key is handed over as its code points.
  3. Java strings are UTF-16. A character above U+FFFF, such as an emoji, takes two code units, a surrogate pair (U+D800 to U+DFFF). A filter that cuts a word by code units can keep half of a pair: an unpaired surrogate.

The finding, step by step

#
  1. You load five one-word synonym rules through SolrSynonymParser: a => x, U+FF21 => y (the fullwidth letter A, one UTF-16 code unit) and three emoji rules (U+1F300, U+1F600 and U+1F914, two code units each). The parser's analyzer is WhitespaceTokenizer with TruncateTokenFilter.truncateAfterChars(tokenizer, 1).
  2. The filter cuts each rule word to its first code unit. a and U+FF21 stay as they are. The three emoji become the keys U+D83C, U+D83D and U+D83E: unpaired surrogates.
  3. You analyze the text U+FF21 with the same chain and SynonymGraphFilter. You expect the one token y.
  4. On Lucene 10.6.0 with assertions off you get U+FF21 back unchanged, and nothing throws. With assertions on, build() stops at the FST compiler's internal assertion inputs are added out of order. On main b5a4546a5964 and on branch_11x 262e019500ec (runs of 2026-11-22) you get y.
  5. Why: build() sorts the keys as a, U+FF21, U+D83C, U+D83D, U+D83E, with a comparator that puts an unpaired surrogate behind U+E000 to U+FFFF. It hands the FST their code points, where U+FF21 comes last. The FST node stores its labels out of order, and the lookup of U+FF21 finds nothing.

Who is affected

#

Applications on Lucene 3.4.0 to 10.6.0 whose synonym map gets a key with an unpaired surrogate: through an analyzer that splits a surrogate pair, or through their own Builder.add call. The analyzer is the application's choice; the one the synonym filter factory builds by default splits no pair. The rule words that were run are contrived. No rate was measured.

Mechanism, terms and numbers1,119 words

You load five well-formed synonym rules (for a, the fullwidth letter U+FF21 and three emoji) through SolrSynonymParser with an analyzer that cuts every word to its first UTF-16 code unit (WhitespaceTokenizer and TruncateTokenFilter.truncateAfterChars(1)). You expect the fullwidth letter, which is one code unit long and is never cut, to be replaced by its synonym. On Lucene 10.6.0 with assertions off it comes back unchanged and nothing throws. With assertions on, build() stops at the FST compiler's internal assertion inputs are added out of order. A second set of five rules makes build() throw ArrayIndexOutOfBoundsException with assertions off.

The cut turns the three emoji into keys that are unpaired surrogates. SynonymMap.Builder.build() sorts its keys with a comparator that places such a key behind U+E000 to U+FFFF, but hands the FST the keys' code points, where it belongs in front. So the FST is built from keys that are out of order, and a lookup can miss a key that is stored in it: in the run the root node holds the label of U+FF21 and the lookup of it returns nothing. The FST compiler asks for sorted input and checks the order by an assertion only.

The same rules, in a form adapted to each release's API, fail on each of the 136 releases from 3.4.0 to 10.6.0 that were run (with the stock filter from 4.8.0 on). They pass on 10.6.0 when the filter cuts by code point, so that no pair is split, and when only the sort of build() is replaced by a comparison of code points. branch_11x and main (both unreleased) pass: there build() sorts by code point since #16834 (Alan Woodward, merged 2026-10-13), a removal of the deprecated comparator. The paper that the comparator's own comment links (Markus W. Scherer, "UTF-16 String Comparison in Code Point Order") notes that its fix-up "may yield unexpected results for malformed UTF-16 strings with single, unpaired surrogate code units".

At the 10.6.0 tag (where the code is)

#

SynonymMap.java is in lucene/analysis/common/src/java/org/apache/lucene/analysis/synonym/, CharsRef.java in lucene/core/src/java/org/apache/lucene/util/, FSTCompiler.java and Util.java in lucene/core/src/java/org/apache/lucene/util/fst/.

  1. The keys are sorted with one order. SynonymMap.Builder.build() copies its keys into an array and sorts it: Arrays.sort(sortedKeys, CharsRef.getUTF16SortedAsUTF8Comparator()); (SynonymMap.java:241-243).
  2. The comparator. It compares the first UTF-16 code units that differ. When both are at or above 0xD800 it fixes each one up: a surrogate (0xD800 to 0xDFFF) gets 0x2000 added, a code unit from 0xE000 gets 0x800 subtracted (CharsRef.java:172-209, the fix-up at :188-200). For well-formed UTF-16, where surrogates come in pairs, that gives code-point order. An unpaired surrogate is moved behind U+E000 to U+FFFF, although its code point lies in front. It is also moved behind a well-formed pair with a smaller high surrogate, although the pair's code point is larger. The comment inside the comparator links the paper the algorithm is from (:183).
  3. The keys reach the FST in another order. Each key is added as fstCompiler.add(Util.toUTF32(input, scratchIntsRef), scratch.toBytesRef()); (SynonymMap.java:290). Util.toUTF32 reads with Character.codePointAt (Util.java:742-750), so an unpaired surrogate keeps its own value, 0xD800 to 0xDFFF.
  4. The FST compiler asks for sorted input and checks it by assertions only. Javadoc of FSTCompiler.add (FSTCompiler.java:840-841): "Add the next input/output pair. The provided input must be sorted after the previous one according to {@link IntsRef#compareTo}." The check is an assert with the message inputs are added out of order (:853-854); the labels of one node are checked again in addArc, also by an assert (:1104-1112). In the test, with assertions off, the compiler writes a node whose arcs are out of order.
  5. In the test. The five keys are U+0061, U+FF21, U+D83C, U+D83D and U+D83E. The comparator's order is 61, FF21, D83C, D83D, D83E: its fix-up turns FF21 into F721 and the three surrogates into F83C to F83E. The code-point order is 61, D83C, D83D, D83E, FF21. The two orders differ by one move: U+FF21 goes from the second place to the last, and the three surrogates each stand one place earlier.
  6. The lookup misses a stored label. A node of 5 or more arcs down to depth 3, or of 10 or more below, is written with fixed-length arcs (FSTCompiler.java:76-86, :592-605) and is searched by bisection or addressed directly. In a run for this page on 10.6.0, the root node of the test's map is written for binary search with five arcs, its labels in stored order are 61 FF21 D83C D83D D83E, and FST.findTargetArc(FF21) returns null while the other four are found. The lookup bisects (FST.java:1054-1079): it reads D83C, D83D and D83E, finds each one smaller than FF21, and ends without reading the stored FF21 (by reading, and in a trace of the real call on 10.6.0). On main b5a4546a5964 the stored order is 61 D83C D83D D83E FF21 and all five are found.
  7. The exception. For a node with fixed-length arcs the compiler computes the label range, last label minus first label plus one (FSTCompiler.java:539), and checks it by an assertion only (:540). With the second rule set the keys reach the FST as U+FF71 to U+FF74 and then U+D83D, so the range is -10,035. The writer for direct addressing takes its count of presence bytes from the range (FST.java:573-576; the check there is an assertion too), the buffer offset becomes negative (FSTCompiler.java:737-741), and the array copy throws (writeNodeForDirectAddressingOrContinuous, :750, under addNode, :548, under compile, called from SynonymMap.java:293): java.lang.ArrayIndexOutOfBoundsException: arraycopy: destination index -1224 out of bounds for byte[11]. A range that is not positive does not always throw. In runs for this page on 10.6.0 with assertions off, five one-code-unit keys were handed to Builder.add: four private-use keys and one unpaired low surrogate, with a range of 0, -7, -8 and -16. Each time build() returns, the root node is written for direct addressing, and none of the five keys is found. With a range of -511 build() throws. No analysis chain was run for these sets.

Why it looks unintended

#
  • FSTCompiler.add javadoc: "The provided input must be sorted after the previous one according to {@link IntsRef#compareTo}." build(), the caller, sorts by another order.
  • The key is accepted: the javadoc of Builder.add states one restriction (no empty words); the parser refuses a zero-length token, not an unpaired surrogate.
  • The lost rule belongs to a well-formed word that the filter never changed.
The full argument224 words
  • The contract that decides which side is wrong. FSTCompiler.add (FSTCompiler.java:840-841 at the 10.6.0 tag): "Add the next input/output pair. The provided input must be sorted after the previous one according to {@link IntsRef#compareTo}." The compiler checks that by an assertion only (:853-854). SynonymMap.Builder.build() is the caller that must keep that order; it sorts by another one (SynonymMap.java:243) than the one it feeds (:290).
  • The key is accepted. The javadoc of Builder.add states one restriction: "Empty words (two U+0000s in a row) are not allowed in the input nor the output!" (SynonymMap.java:208-211). The method it calls also refuses an empty input or output and a word count below 1 with IllegalArgumentException (:153-165). Parser.analyze refuses a zero-length token and a position increment other than 1 with IllegalArgumentException (:323-345). None of these refuses a key or a token with an unpaired surrogate. SynonymMap.java at the tag holds neither "surrogate" nor "well-formed".
  • The harm is not confined to the ill-formed key. In the test the rule that is lost belongs to U+FF21, a word of one code unit that the filter never changed.
  • The code that replaced it gives the expected answer on the same input. On main and branch_11x build() sorts by the code points it hands to the FST, and the test passes.
The devil's-advocate check416 words

The strongest case for "not a defect": a token with an unpaired surrogate is malformed text, and what follows from it is its producer's matter. The truncating filter's class javadoc at the 10.6.0 tag says that since Lucene 10.5 the filter truncates after code points, "no longer producing incomplete surrogate pairs", and calls the mode the test uses legacy: "Legacy behaviour is still available with {@link #truncateAfterChars(TokenStream, int)}" (TruncateTokenFilter.java:34-37). The method the test calls says "This may split surrogate pairs" (:53-54), and the deprecated constructor's javadoc names the code-point method "to be unicode conformant" (:64-66). The comparator, its field and its accessor are @Deprecated at the tag with the javadoc "This comparator is only a transition mechanism" (CharsRef.java:153-172), since the commit 7f366cd0da92 ("LUCENE-3590: deprecate dancing comparators", Robert Muir, 2011-11-26). The paper that the comparator's own comment links says that its fix-up "may yield unexpected results for malformed UTF-16 strings with single, unpaired surrogate code units". Lucene's test framework fails a test when the text a MockTokenizer reads holds an unpaired surrogate (MockTokenizer.java:248-273). The synonym classes are marked @lucene.experimental (SynonymMap.java:46). The nearest sentence in Lucene's source is the javadoc of another API, BytesRef(CharSequence): "This must be well-formed unicode text, with no unpaired surrogates." (BytesRef.java:77). And branch_11x and main no longer have the code.

What speaks against it (the call is the maintainers'): none of these says that losing another key's rule is correct. No javadoc of the synonym classes, of CharsRef, of Util.toUTF32 or of the analysis package at the 10.6.0 tag makes well-formed UTF-16 a precondition of a key. The deprecation note calls the comparator a transition mechanism and names no wrong order. The test framework's check is on the text a tokenizer reads, not on the tokens a filter hands on: a comment in TestRandomChains asks for such a check ("also add a unicode validating filter to validate termAtt?", TestRandomChains.java:184-185). By reading, the BytesRef sentence does not govern a key: only a rule's output goes through a UTF-8 conversion (SynonymMap.java:172), the key stays a CharsRef (:186-187). The parser refuses other analyzer outcomes with an IllegalArgumentException and not this one. Before 10.5.0 the filter has one mode and no such sentence, and 9.12.3 fails the same way. What the test shows is damage to a key that is well-formed. Each point bears on whether a maintenance line takes a change, which is a triage question.

Registry title
On Lucene 3.4.0 to 10.6.0 SynonymMap.Builder.build() can hand its keys to the FST out of order when one key holds an unpaired surrogate: the synonym rule of another, well-formed word can then never fire in the map that build() returns, with no error when assertions are off, or build() can throw ArrayIndexOutOfBoundsException (run: five one-word rules behind a filter that cuts every word to its first UTF-16 unit, the stock TruncateTokenFilter from 4.8.0 on, fail with and without assertions on each of the 136 releases that were run; a second set of five rules throws with assertions off on each of the 55 releases from 8.4.0; branch_11x and main, both unreleased, no longer have that code)
Area
analysis-common / synonyms (SynonymMap.Builder.build: the order in which the keys reach the FST; the release lines 3.4 to 10.x)
Priority
Low, rank 867: On the releases from 3.4.0 to 10.6.0 that were run, the synonym rule of a well-formed word can silently fail to fire when another key of the synonym map holds an unpaired surrogate, and on those from 8.4.0 loading the rules can throw an unchecked exception (with assertions off; a second set of rules, not run below 5.0.0). It is Low because every failing key set that was run holds a key with an unpaired surrogate (with well-formed keys the two orders did not disagree in anything that was run), the other keys at the same FST node matter too, the truncation and Polish-stemming chains that were run use contrived rule words (emoji cut after one UTF-16 unit; a word with a supplementary first letter under the Polish stemmer), the truncating filter's javadoc says since 10.5.0 that its UTF-16-unit mode may split surrogate pairs and names a code-point mode, which passes the same rules on 10.6.0, and branch_11x and main no longer have the code: it is in the releases, on the maintenance branch branch_10_6 (the test fails in a build of that branch) and, by reading, on branch_9_12.
Impact class
minor
Impact note
Applications on a release from 3.4.0 to 10.6.0 whose synonym map gets a key that holds an unpaired surrogate can get from build() a map in which the rule of another, well-formed word never fires: with assertions off nothing throws and that word comes back from the synonym filter unchanged, alone and inside a longer text [exec]; or build() can throw ArrayIndexOutOfBoundsException when the rules are loaded (with assertions off, one set of five rules: thrown on each of the 55 releases from 8.4.0 to 10.6.0; on the 53 releases from 5.0.0 to 8.3.1 the same rules build; not run below 5.0.0) [exec]; with assertions on, build() stops at the FST compiler's internal assertion 'inputs are added out of order' instead (the five-rule test on each of the 136 releases; the second set on 10.6.0) [exec]. How such a key got there in the runs: from well-formed rules text through an analyzer that splits a surrogate pair (a filter that cuts by UTF-16 unit on each of the 136 releases: the stock TruncateTokenFilter from 4.8.0 on, a local filter of the same body before, the stock EdgeNGramTokenFilter once on 3.4.0; the Polish stemmer chain on 10.6.0), or handed to SynonymMap.Builder.add directly (10.6.0 and 9.12.3) [exec]. The synonym parsers have no analyzer of their own: the analyzer in front of the parser, or the keys, are the application's choice. The analyzer that SynonymGraphFilterFactory builds when no analyzer and no tokenizer factory is named is WhitespaceTokenizer with an optional LowerCaseFilter, which read and write whole code points and so split no surrogate pair of the rules text [read at the 10.6.0 tag]; the test's five rules loaded through that factory lose nothing on 10.6.0 with and without assertions (run on 2026-11-22 and 2026-11-23) [exec]. A stock analyzer with its defaults that the application picks can reach it: with new PolishAnalyzer() as the parser's analyzer, five rules with contrived rule words (three begin with a supplementary letter) lose the rule of a well-formed fullwidth word on 10.6.0 and 9.12.3 with assertions off (with assertions on, build() stops at the FST compiler's assertion) and lose nothing on main b5a4546a5964 and branch_11x 262e019500ec (run on 2026-11-22 and 2026-11-23) [exec]. No scale is needed (five rules suffice). It also depends on the other keys at the same FST node: in the runs that lost the rule of a well-formed word the unpaired unit stood at the first position where sibling keys differ, against a unit at or above U+E000 (fullwidth and halfwidth forms, compatibility ideographs, presentation forms, private use) or against a supplementary character with a smaller high surrogate; the rule of a well-formed word was lost at a node of five keys that is written for binary search and, in one contrived set of 102 keys, at a node written for direct addressing, where no rule of the map fired; at a node of four keys only the rule of the key with the unpaired surrogate was lost; and of the 1,920 key sets of one differential that hold such a key (subsets of a pool of 11 one-word keys chosen for the purpose, 4 of them with an unpaired surrogate: counts of that pool, not a rate), 80 build a clean map [exec]. Summary
You load five well-formed synonym rules (for 'a', the fullwidth letter U+FF21 and three emoji) through SolrSynonymParser with an analyzer that cuts every word to its first UTF-16 unit (WhitespaceTokenizer and TruncateTokenFilter.truncateAfterChars(1)), and you expect the fullwidth letter, which is one unit long and is never cut, to be replaced by its synonym.
