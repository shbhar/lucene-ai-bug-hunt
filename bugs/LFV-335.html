JapaneseCompletionFilterFactory upper-cases the default mode instead of the configured value, so mode="query" is rejected

Building the Japanese completion filter through its factory with mode="query" fails with IllegalArgumentException: No enum constant ...Mode.query: the factory's toUpperCase is applied to the default name "INDEX", not to your value. Only INDEX and QUERY work, while the Japanese tokenizer factory next to it accepts lower-case modes.

The finding in 30 seconds

#

One parenthesis is in the wrong place: the factory upper-cases its own default instead of the value you configured.

Background: the completion filter and its factory

#
  1. JapaneseCompletionFilter (kuromoji module) adds romanized forms of Japanese tokens for auto-complete. It has two modes: INDEX (simple romanization, used when indexing; the default) and QUERY (Input-Method-aware romanization, used on what the user is typing).
  2. Analysis factories build components from string settings. JapaneseCompletionFilterFactory, SPI name japaneseCompletion, reads the setting mode from its argument map; CustomAnalyzer and analyzer definitions loaded by SPI name pass it that way.
  3. Its neighbour JapaneseTokenizerFactory reads its own mode setting the same way and upper-cases it, so mode="search" and mode="normal" work there.

The finding, step by step

#
  1. Build the japaneseCompletion filter through its factory with mode="query", for example CustomAnalyzer.builder().withTokenizer("japanese", "mode", "normal").addTokenFilter("japaneseCompletion", "mode", "query"): lower case, as the Japanese tokenizer factory accepts in the same call.
  2. You expect a QUERY-mode filter: the factory's mode expression contains a toUpperCase(Locale.ROOT) call, and with QUERY the filter turns the input 東京ｔ, after width normalization (CJKWidthFilter), into the 2 tokens 東京t and toukyout.
  3. Instead the constructor throws IllegalArgumentException: No enum constant ...JapaneseCompletionFilter.Mode.query. The toUpperCase runs on the default, DEFAULT_MODE.name(), which is already "INDEX", so your "query" reaches the case-sensitive Mode.valueOf unchanged.
  4. Only the exact names INDEX and QUERY work. The error is immediate and never selects the wrong mode, and every release from 9.0.0 to 10.6.0 has it.

Who is affected

#

Applications that build the opt-in japaneseCompletion filter through its factory (the Map constructor, TokenFilterFactory.forName, CustomAnalyzer or an analyzer definition loaded by SPI name) and write the mode as query or Query. The analyzer cannot be built; writing QUERY works. Nothing at index or search time is affected.

Mechanism, terms and numbers395 words

JapaneseCompletionFilterFactory (SPI name japaneseCompletion) reads its mode argument with Mode.valueOf(get(args, MODE_PARAM, DEFAULT_MODE.name().toUpperCase(Locale.ROOT))). The toUpperCase is applied to the default, the constant name "INDEX", so it does nothing, and the configured value reaches the case-sensitive Enum.valueOf unchanged: mode="query" throws IllegalArgumentException: No enum constant org.apache.lucene.analysis.ja.JapaneseCompletionFilter.Mode.query from the constructor and through CustomAnalyzer, and only INDEX and QUERY work. The sibling JapaneseTokenizerFactory in the same module uses the same idiom with the parenthesis after get(...) and accepts lower-case modes. The expression has been there since the factory was added (LUCENE-10102, #297, 2021) and is in every release from 9.0.0 to 10.6.0 and on main. No javadoc promises case-insensitive values, so this is a minor consistency defect, not a broken contract: it fails loudly when the analyzer is built, never picks the wrong mode and never affects tokens or an index. Moving .toUpperCase(Locale.ROOT) onto the result of get(...) fixes it.

Terms

#
  • JapaneseCompletionFilter.Mode: an enum with the constants INDEX and QUERY (JapaneseCompletionFilter.java:74-79 at 645d4fe14a20); DEFAULT_MODE = Mode.INDEX (:61).
  • AbstractAnalysisFactory.get(args, name, defaultVal): removes the argument from the map and returns it as given, or the default when it is absent (AbstractAnalysisFactory.java:160-163).
  • Enum.valueOf: case-sensitive; any string that is not exactly a constant name throws IllegalArgumentException: No enum constant ....

The bug

#
  1. The constructor parses the mode (JapaneseCompletionFilterFactory.java:46-51):
mode =
    JapaneseCompletionFilter.Mode.valueOf(
        get(
            args,
            MODE_PARAM,
            JapaneseCompletionFilter.DEFAULT_MODE.name().toUpperCase(Locale.ROOT)));
  1. The closing parenthesis of get(...) comes after the toUpperCase, so the call belongs to the third argument, the default. DEFAULT_MODE.name() is already "INDEX"; upper-casing it can never change anything.
  2. The configured value, for example "query", is returned unchanged and Mode.valueOf("query") throws.
  3. The sibling JapaneseTokenizerFactory puts the call on the configured value: Mode.valueOf(get(args, MODE, JapaneseTokenizer.DEFAULT_MODE.toString()).toUpperCase(Locale.ROOT)) (JapaneseTokenizerFactory.java:122-124); KoreanTokenizerFactory does the same (KoreanTokenizerFactory.java:92-95).

The numbers

#
  • A probe of 19 mode values, each through the constructor and through CustomAnalyzer: only exactly INDEX and QUERY were accepted, each giving its own mode; query, Query, index, ' QUERY' and the others were rejected. On the input 東京ｔ, INDEX gives [東京, toukyou, t, thiー, texiー] and QUERY gives [東京t, toukyout].
  • With the fix the lower- and mixed-case spellings probed (7 ASCII variants such as query, Query, qUERY and iNDEX, plus ındex) give the mode they name, and the other values are still rejected.
Exposure and likelihood135 words
  • Who is hit. Only users of the factory. JapaneseCompletionAnalyzer builds the filter directly, not through the factory, so it is not affected; neither is code that constructs JapaneseCompletionFilter or JapaneseCompletionAnalyzer directly, since their constructors take the Mode enum or pick INDEX when none is given, and never parse a string.
  • What it takes. Writing the query-side mode in lower or mixed case. That is the natural spelling next to the sibling tokenizer: its factory accepts lower case, its upstream test passes "normal", and the Solr reference guide documents lower-case modes for it.
  • What happens. A deterministic IllegalArgumentException when the factory is constructed, naming the enum. It never selects the other mode, never yields wrong tokens and never reaches an index.
  • Scale. Minor: a loud configuration-time nit with a one-word workaround, unreported since 9.0.0 (2021).

Why it looks unintended

#
  • The factory's mode expression does call toUpperCase(Locale.ROOT), but on the default's name(), the already upper-case "INDEX", where it can never change anything.
  • The sibling JapaneseTokenizerFactory puts the same call after get(...), and its upstream test passes lower-case "normal".
  • No javadoc, test, PR review or issue comment makes the case sensitivity deliberate; none promises case-insensitivity either, hence a minor defect.
The full argument156 words
  • The dead call. DEFAULT_MODE.name().toUpperCase(Locale.ROOT) is always "INDEX" (JapaneseCompletionFilterFactory.java:51, JapaneseCompletionFilter.java:61).
  • Sibling convention, same module. JapaneseTokenizerFactory has upper-cased the configured value since at least 2013 (LUCENE-4877, 6de43dea0af, which introduced the get(...).toUpperCase(Locale.ROOT) form); KoreanTokenizerFactory (:92-95) and Word2VecSynonymFilterFactory (:58) do the same.
  • Tests. TestJapaneseTokenizerFactory.testMode passes "normal"; the completion factory's only mode test passes "QUERY" (TestJapaneseCompletionFilterFactory.java:36), and no test asserts that lower case is rejected.
  • History. The factory came in one commit, 4e86df96c03 (LUCENE-10102, #297, by Tomoko Uchida, co-authored by Robert Muir, 2021-09-17), with this exact expression, and the file has never been edited since. None of the PR's review comments or the issue's comments is about the mode argument or its case.
  • Project convention. In LUCENE-4877 (#5942, 2013) Steven Rowe proposed a getEnum(...) helper for factory arguments, "probably case insensitivity could be assumed?", and Robert Muir replied "+1 to all of this". Context only, eight years before this factory.
The devil's-advocate check186 words

The strongest case for "intended" (an intended-behaviour checker, and a read-only reviewer from another model family, OpenAI GPT-5.6, which leaned "not real"): the only documentation is "mode: Completion mode. see JapaneseCompletionFilter.Mode" (JapaneseCompletionFilterFactory.java:30), whose constants are INDEX and QUERY; the upstream test uses QUERY; even JapaneseTokenizerFactory's javadoc example writes mode="NORMAL" (:43); BeiderMorseFilterFactory is case-sensitive (a plain valueOf at :58-59, and its javadoc example uses upper-case values); and the failure is loud, immediate and has a one-word workaround.

Why it fails: it shows there is no broken contract, which is why this is classed as a minor consistency defect, but not that case sensitivity was chosen. BeiderMorseFilterFactory has no toUpperCase call at all, so it is no precedent for a misplaced one; this factory's mode expression does call toUpperCase(Locale.ROOT), and only the call's placement (on the default instead of the configured value) makes it useless. No javadoc, test, CHANGES.txt, MIGRATE.md, review or issue comment says the case sensitivity is deliberate. This is still an inference about intent: a maintainer could reasonably prefer option B or decline.

Suggested fix

#

Recommended A. Upper-case the configured value, not the default (mirrors JapaneseTokenizerFactory)

Move .toUpperCase(Locale.ROOT) from the default onto the result of get(...), exactly as JapaneseTokenizerFactory does. Lower- and mixed-case spellings of INDEX and QUERY then give the mode they name, and other values are still rejected. With it the repro passes with assertions on and off, and the kuromoji module's 196 tests (0 failures) and its check pass.

     mode =
         JapaneseCompletionFilter.Mode.valueOf(
-            get(
-                args,
-                MODE_PARAM,
-                JapaneseCompletionFilter.DEFAULT_MODE.name().toUpperCase(Locale.ROOT)));
+            get(args, MODE_PARAM, JapaneseCompletionFilter.DEFAULT_MODE.name())
+                .toUpperCase(Locale.ROOT));

A. Upper-case the configured value, not the default (mirrors JapaneseTokenizerFactory) (validated by the checks) (recommended)

#

In the constructor (JapaneseCompletionFilterFactory.java:46-51), move .toUpperCase(Locale.ROOT) onto the result of get(...).

     mode =
         JapaneseCompletionFilter.Mode.valueOf(
-            get(
-                args,
-                MODE_PARAM,
-                JapaneseCompletionFilter.DEFAULT_MODE.name().toUpperCase(Locale.ROOT)));
+            get(args, MODE_PARAM, JapaneseCompletionFilter.DEFAULT_MODE.name())

Trade-offs

  • Lower- and mixed-case spellings of INDEX and QUERY are accepted and give the mode they name (7 ASCII variants probed, such as query, Query, qUERY, iNDEX); any other value is still rejected with the same exception type (its message then shows the upper-cased value). Upper-case configurations behave as before; no signature or index-format change, but construction-time parsing becomes more permissive (values rejected today are accepted).
  • As in JapaneseTokenizerFactory, Locale.ROOT upper-casing maps U+0131 (dotless i) to I, so ındex is accepted as INDEX; harmless for a trusted configuration value and independent of the JVM default locale.

What the checks validated

  • Gradle in a scratch worktree of 645d4fe14a20 (2026-11-01): stock, the minimal test fails with assertions on and off; with the fix it passes both ways.
  • With the fix: TestJapaneseCompletion* (analyzer, filter, factory and the repro) 4 classes, 12 tests, 0 failures; the whole kuromoji module 31 classes, 196 tests, 0 failures (7 skipped by the test framework); :lucene:analysis:kuromoji:check -x test passes (formatting, ecjLint, forbiddenApis).
  • Earlier: the same change shadowed into the stock jars passes the hunt's 3-test and 4-test JUnits (which also check the QUERY-mode tokens) and the main() form on 9.0.0.

B. Keep the mode case-sensitive: delete the dead call and document upper-case values

Trade-offs

Downstream note

Elasticsearch and OpenSearch parse the kuromoji_completion mode case-insensitively in their own code and never call this factory, so they are unaffected; products that build analyzers by the SPI name japaneseCompletion are affected.
