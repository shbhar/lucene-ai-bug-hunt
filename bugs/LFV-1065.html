IndexWriter opened from a reader's IndexCommit keeps the reader's segment files open when its constructor fails

If you open an IndexWriter with setIndexCommit(reader.getIndexCommit()) and the constructor fails, for example because your deletion policy's onInit throws, the writer has already taken a reference on each of the reader's segments and never releases it. After you close the reader its segment files stay open (_0.cfs for one segment).

The finding in 30 seconds

#

Background: segment cores and opening a writer from a reader

#
  1. A DirectoryReader has one segment reader per segment. The segment's open files (for a small segment one compound file, _0.cfs) live in a shared core with a reference count; the files close when the count reaches 0.
  2. IndexWriterConfig#setIndexCommit(reader.getIndexCommit()) (Expert) opens a writer at exactly the point an open reader sees, NRT or not.
  3. On that path the writer enrolls its own segment reader for each of the reader's segments in its ReaderPool, sharing the reader's cores: one more reference per core, normally released when the writer closes.

The finding, step by step

#
  1. Index 1 document and close the writer: one segment, stored as the compound file _0.cfs. Open DirectoryReader r on it.
  2. Open a writer from the reader's commit, new IndexWriterConfig().setIndexCommit(r.getIndexCommit()), with a deletion policy whose onInit throws IOException. The constructor throws, as it should.
  3. You expect nothing left behind: you hold only r, so after r.close() the directory should close cleanly, as it does when the commit comes from DirectoryReader.listCommits.
  4. Instead _0.cfs stays open: cannot close: there are still 1 open files: {_0.cfs=1}. Before the policy ran, the constructor put one segment reader per segment into its ReaderPool, each holding a reference on the segment's core; its catch releases the write lock and the merge scheduler, not the pool.
  5. Every failed attempt leaks one more reference per segment (2 files for 2 segments). No public API can release them, and a later successful writer does not either.

Who is affected

#

Applications that open a writer from an open reader's commit (setIndexCommit(reader.getIndexCommit()), Expert, opt-in; NRT and non-NRT readers) whose constructor then fails: a deletion policy whose onInit throws, or an I/O error while the writer reads a commit. One leaked core reference per segment per failed attempt; results stay correct.

Mechanism, terms and numbers669 words

IndexWriterConfig#setIndexCommit documents that a writer can be opened from an open reader by passing reader.getIndexCommit(). On that path the IndexWriter constructor first builds its ReaderPool, which pre-enrolls one SegmentReader per segment of the reader, each sharing the reader's segment core and taking a reference on it. Only then does it build the IndexFileDeleter, which reads every segments_N and calls IndexDeletionPolicy.onInit. If anything throws from then on, the constructor's catch (Throwable) closes the merge scheduler and the write lock but not the pool, and the caller never gets the writer. So after the caller closes the reader, each segment core still holds the pool's reference and its files stay open: with one one-document commit and a policy whose onInit throws, MockDirectoryWrapper reports {_0.cfs=1} still open, with assertions on and off, on main and on every release from 7.4.0 to 10.6.0. The same failing policy with a commit from listCommits, or with no commit, leaves nothing open. An I/O error while the deleter reads a commit leaks the same way with the default policy. The leak arrived as a side effect of LUCENE-8260, which moved the pre-enroll step ahead of the deleter. Results and index files are unaffected. Closing the pool in the catch, as #15675 did for the merge scheduler, fixes it.

Terms

#
  • Segment core (SegmentCoreReaders): the per-segment open files and readers shared by every SegmentReader of that segment. Each sharing reader takes a reference (SegmentReader.java:151-152, core.incRef()); when the count reaches 0 the core closes its files, including the compound-file input (SegmentCoreReaders.java:167-179, opened at :83).
  • Reader commit: DirectoryReader.getIndexCommit() on a standard reader returns a ReaderCommit that carries the reader (StandardDirectoryReader.java:571-574, :644-646); a commit from listCommits is a ReaderCommit built with a null reader (DirectoryReader.java:456, :481; field set at StandardDirectoryReader.java:595), so its getReader() returns null.
  • Pre-enrollment: the ReaderPool constructor's loop that pools one SegmentReader per leaf of that reader, "so any in-memory NRT live docs are correctly carried over, and so NRT readers pulled from this IW share the same segment reader" (ReaderPool.java:90-115).

The bug (main 645d4fe14a20)

#
  1. The constructor takes the write lock (IndexWriter.java:954), enters try (:956) and gets the commit's reader, reader = commit.getReader() (:982-990).
  2. readerPool = new ReaderPool(..., reader, config) (:1148-1158) pre-enrolls one SegmentReader per segment, each adding a reference to the reader's core (ReaderPool.java:96-113).
  3. Only then deleter = new IndexFileDeleter(...) (IndexWriter.java:1166-1182) reads every commit (IndexFileDeleter.java:161) and calls policy.onInit(commits) (:237).
  4. If that throws, catch (Throwable t) (IndexWriter.java:1202-1209), "init: hit exception on init; releasing write lock", runs IOUtils.closeWhileSuppressingExceptions(t, config.getMergeScheduler(), writeLock) (:1206). The pool is not in that list, and it lives in a private final field (:403) of a writer the caller never receives.
  5. r.close() removes the reader's own reference, but the pooled reader's reference stays: the core never reaches 0 and _0.cfs stays open.

The failed writer stays reachable from the config, which stores it through the package-private setIndexWriter in a private SetOnce field (IndexWriter.java:947, IndexWriterConfig.java:119, :126-132), so the exact wording is "cannot be released through any public API".

Exposure and likelihood351 words
  • Who is hit. Writers opened with IndexWriterConfig#setIndexCommit(reader.getIndexCommit()), the Expert path LUCENE-6524 added in 5.3.0 ("IndexWriter can now be initialized from an already open near-real-time or non-NRT reader"), whose constructor fails after the pool is built. Lucene's own RandomIndexWriter takes this path at random in tests (RandomIndexWriter.java:96-104).
  • Default vs opt-in. Opt-in: by default no commit is set ("The default is null which opens the latest commit point", IndexWriterConfig.java:234-241). A commit from listCommits, or none, is not affected.
  • What triggers it. An application IndexDeletionPolicy whose onInit throws the IOException it declares (none of the stock policies throws there); an I/O error while IndexFileDeleter reads a segments_N, with the default policy; or a failure inside the pre-enroll loop (an I/O error on a later segment, or LFV-1062's leaf-sorted reader with segments of unequal size).
  • How much. One segment-core reference per segment per failed attempt, growing with each attempt; a successful retry does not release the earlier one. Open file handles grow per attempt only when each attempt uses a fresh reader: three failed attempts with the same reader leave {_0.cfs=1}, three with a fresh reader each leave {_0.cfs=3}. The write lock and the merge scheduler are released, so a retry can open.
  • At the OS level (one Linux probe, not part of the claim): after the failed open the caller dropped the reader, a normal writer deleted _0.cfs, and 5 System.gc() calls ran. With MMapDirectory, which FSDirectory.open returns on 64-bit JVMs (FSDirectory.java:155-161), the process still had 3 mappings of the deleted _0.cfs (control: 0); they belong to a shared arena that only an explicit close releases, so the file's disk space stays allocated as long as they exist (not measured beyond the probe). With NIOFSDirectory the one leaked file descriptor was reclaimed by garbage collection once the reader and the config were dropped.
  • What does not happen. No wrong results, no index damage, no hang; with an injected I/O error while the deleter reads a commit, the committed file set is unchanged, with no unreferenced or missing files. The constructor fails loudly.

Why it looks unintended

#
  • The constructor's catch exists to release what it acquired: the write lock and, since #15675, the merge scheduler ("MergeScheduler should be closed on IndexWriter init failure").
  • onInit declares throws IOException; an I/O error while reading a commit needs no user code.
  • Lucene's own RandomIndexWriter opens writers from reader commits and, if the constructor fails, closes only the reader.
The full argument254 words
  • The catch is cleanup. Its log line reads "init: hit exception on init; releasing write lock" (IndexWriter.java:1204). LUCENE-2476 (#3550, 2010) added the write-lock release on any constructor exception; #15675 (GITHUB#14971, 2026) added the merge scheduler plus TestConcurrentMergeScheduler#testMergeSchedulerClosedOnIndexWriterInitFailure (:965-987), whose trigger is itself a user error (OpenMode.APPEND on an empty directory). The pool is the one resource holding open files that the catch still misses (the DocumentsWriter and a half-built IndexFileDeleter are not closed either, but hold no open files).
  • The trigger is in contract. public abstract void onInit(List<? extends IndexCommit> commits) throws IOException (IndexDeletionPolicy.java:62), with no "must not throw" note (:46-61). The I/O-error trigger uses the default policy.
  • Lucene's tests assume closing the reader is enough. RandomIndexWriter opens a writer from reader.getIndexCommit() at random and, if the constructor fails, closes only the reader (RandomIndexWriter.java:96-125). TestIndexWriterFromReader#testWithNoFirstCommit (:87) and #testOnClosedReader (:380) close their directory after a failed constructor; their failures come before the pool has enrolled any reader (testOnClosedReader fails at reader.leaves() inside the ReaderPool constructor, ReaderPool.java:94). No test asserts or tolerates the leak.
  • History: a side effect of a refactor. Through 7.3.1 the constructor built the IndexFileDeleter first and pre-enrolled after it, so an onInit or deleter failure found an empty pool (7.3.1 passes the test). LUCENE-8260 (#9307, "Extract ReaderPool from IndexWriter", 2018) moved the loop into the ReaderPool constructor, ahead of the deleter, and kept the handler as it was; the commit message describes only the extraction.
The devil's-advocate check132 words

The strongest case for "intended" (the devil's-advocate verifier and the intended-lens reviewer): setIndexCommit is "Expert" and getIndexCommit is "Expert" and @lucene.experimental (DirectoryReader.java:644-649); no javadoc promises that a failed constructor releases everything (its @throws covers I/O errors only, IndexWriter.java:941-943); and the main trigger is a user policy that throws, which could be called user error.

Why it fails: the catch exists for cleanup, and maintainers already fixed a leak in this exact catch whose trigger was a user error (#15675); onInit declares IOException; the I/O-error trigger needs no user code; Lucene's own test framework closes only the reader after a failed constructor on this path; and the leak came in by accident with a refactor. The argument explains the Low priority, not the leak. All reviewers rated it weak.

Suggested fix

#

Recommended Release the pool when the constructor fails after or while building it (two hunks)

Keep the ReaderPool in a local and add it to the constructor's catch: IOUtils.closeWhileSuppressingExceptions(t, pool, config.getMergeScheduler(), writeLock); also let the ReaderPool constructor drop what it pooled when its pre-enroll loop fails. Validated through gradle: the repro passes with assertions on and off, and 222 tests of the closest suites pass.

Release the pool when the constructor fails after or while building it (two hunks) (validated by the checks) (recommended)

#

Hunk A, IndexWriter: keep the pool in a local, assign the field from it, and add it to the catch's close list (+4/-2). ReaderPool is Closeable and close() drops every pooled reader (ReaderPool.java:45, :233-237, :314-341); the helper ignores null (IOUtils.java:97-106). The snippet above is condensed.

Hunk B, ReaderPool constructor (+30/-18, mostly re-indentation): wrap the pre-enroll loop so a failure inside it releases what was pooled so far, and decRef the reader whose ReadersAndUpdates could not be built. Without it, a failure inside the loop leaves pool null in the writer's catch.

      try {
        for (int i = 0; i < leaves.size(); i++) {
          // ... SegmentReader newReader = new SegmentReader(...) ...
          ReadersAndUpdates rld;
          try {
            rld = new ReadersAndUpdates(/* ... */, newReader, /* ... */, config);
          } catch (Throwable t) {
            IOUtils.closeWhileSuppressingExceptions(t, newReader::decRef);
            throw t;
          }
          readerMap.put(newReader.getOriginalSegmentInfo(), rld);
        }
      } catch (Throwable t) {
        // release the readers pre-enrolled so far: the caller never gets this pool
        IOUtils.closeWhileSuppressingExceptions(t, this::dropAll);
        throw t;
      }

Trade-offs

  • No change on success: one local variable and one try.
  • Coverage. Hunk A alone fixes the minimal repro, the onInit trigger (NRT and non-NRT) and the deleter-read trigger; hunk B alone fixes only the two in-loop triggers; both together pass all 8 tests of the fault-injection matrix.
  • Test. The regression test (the minimal test) exercises hunk A only; hunk B is backed by the fault-injection matrix, which is evidence, not a proposed test.
  • Overlap. LFV-1062's name-pairing fix edits the same loop: the diffs overlap in text but are logically independent (a combined patch was not executed).
  • One edge left in hunk B (the cross-model fact check): if readerMap.put itself throws, in practice only a VM error such as OutOfMemoryError, after the current reader's ReadersAndUpdates was built, that reader is not yet in the map and dropAll() misses it; an "enrolled" flag around the put would close it. Not material in practice.

Downstream note

#

Services that retry a failing writer open from a reader's commit leak one segment-core reference per segment per attempt, and one more open handle per segment file per attempt when each attempt opens a fresh reader; with MMapDirectory one probe still saw a deleted segment file mapped after 5 garbage collections.

How it was found

#

Non-formal: reading the IndexWriter constructor's failure handler showed it never closes the ReaderPool; a small program with a throwing onInit and an injected I/O error confirmed the leak. The hunt reduced it to one public-API JUnit test and checked more triggers with a fault-injection matrix on the stock jar.

The method in full144 words

Method: non-formal. A code-reading probe read the constructor's catch and saw that the pool built before the deleter is never closed (2026-10-30). Its executed main() probe leaked with a throwing onInit and in an I/O-error mode, and was clean in a no-failure control; a separate re-run confirmed it.

  • A hunt unit (2026-11-01) wrote an exception-edge map of the reader-commit branch (file:line mapped) and ran it as a fault-injection matrix on the stock jar: a throwing onInit (non-NRT and NRT reader), MockDirectoryWrapper I/O failures scoped to IndexFileDeleter.<init> and ReaderPool.<init>, LFV-1062's leaf-sorted unequal-size reader, two controls and a deleter file-set check. 5 of 8 fail on stock, 8 of 8 pass with the fix, and each hunk alone fixes only its own triggers.
  • It reduced the lead to the one-test repro, traced the history to LUCENE-8260 and ran the test on releases back to 7.3.1.

History

#

Introduced by LUCENE-8260 (8975692953, branch_7x 1bf56037d17, 2018-04-23), which moved the pre-enroll step ahead of the deleter; first released in 7.4.0 (7.3.1 and the commit's parent pass). Every release through 10.6.0 and main is affected; failures inside the loop leak since 5.3.0. Not fixed upstream.

Versions tested7 rows

Introduced by LUCENE-8260 "Extract ReaderPool from IndexWriter" (#9307, s1monw): 8975692953 on master and the branch_7x backport 1bf56037d17, both author date 2018-04-23 (JIRA era, no apache/lucene PR). It moved the pre-enroll loop into the new ReaderPool constructor, which runs before the IndexFileDeleter; the failure handler kept releasing only the write lock. Built from source, the backport fails the test and its parent 4cd0a0aae32 passes (assertions on and off).

Every local release tag from 7.4.0 to 8.8.1 and 9.0.0 to 10.6.0 builds the pool before the deleter, and the handler (finally with !success up to 10.6.0, catch on main) never names the pool; 8.8.2-8.11.4 by branch ancestry plus the executed 8.11.4. 10.6.0 still has the older handler, which releases only the write lock: #15675 is unreleased (on main and branch_11x, CHANGES 11.0.0 section), not on branch_10_6 or in 10.6.0.

Older leg, not the claimed repro: a failure inside the pre-enroll loop leaks the readers already pooled since LUCENE-6524 added the reader-commit branch (#7582, 2d0ac9bb7f2, 2015-06-28, first released in 5.3.0); a variant that injects an I/O error on the second segment fails on 5.3.0, 7.3.1, 7.4.0 and main. So LUCENE-8260 is the origin of the claimed trigger, not of every leg.

Upstream main f815e679bf6 (2026-11-01), branch_11x and branch_10_6 are unchanged at the catch and the loop.

Finding record

LFV-1065, snapshot of 2026-11-05

Registry title
An IndexWriter opened from a reader's IndexCommit whose constructor then fails (for example the IndexDeletionPolicy's onInit throws, or an I/O error while the deleter reads a commit) never releases the segment readers its ReaderPool pre-enrolled from that reader, so the reader's segment files stay open after the caller closes the reader
Area
core / IndexWriter constructor failure path (reader-commit branch: IndexWriterConfig#setIndexCommit(reader.getIndexCommit()), ReaderPool pre-enrollment; LUCENE-6524, LUCENE-8260)
Priority
Low, rank 1076: When an IndexWriter opened from a reader's commit fails in its constructor, one reference per segment of that reader is never released, so the reader's files stay open, in every release since 7.4.0. It is a bounded leak after a loud failure on an opt-in Expert path, so it is Low.
Impact class
minor
Impact note
Applications that open a writer from a reader's commit (the documented Expert path IndexWriterConfig#setIndexCommit(reader.getIndexCommit()), used for example to roll back to or resume from an open NRT or non-NRT reader) and whose writer constructor then fails after the ReaderPool is built (an application IndexDeletionPolicy whose onInit throws the IOException it declares, an I/O error while IndexFileDeleter reads a segments_N, or a failure inside the pre-enroll loop): the constructor throws loudly and releases the write lock, but one reference per segment on the reader's segment cores is never released by Lucene and cannot be released through any public API, so the reader's segment files stay open after the reader is closed (executed: MockDirectoryWrapper reports {_0.cfs=1} still open; one more reference per segment on every failed attempt, still held after a successful retry); no wrong results, no data loss, any index size.
Summary
You open a DirectoryReader, pass its getIndexCommit() to IndexWriterConfig#setIndexCommit, and the IndexWriter constructor then fails, here because your IndexDeletionPolicy's onInit throws an IOException; you expect the exception and nothing left behind once you close the reader, as the constructor's own catch intends (it releases the write lock and, since #15675, the merge scheduler) and as the same failure with a commit from DirectoryReader.listCommits behaves. Instead the constructor has already built the ReaderPool, which pre-enrolled one SegmentReader per segment, each holding a reference on the reader's segment core, and its catch never closes the pool, so after reader.close() MockDirectoryWrapper still reports the segment's compound file open.
