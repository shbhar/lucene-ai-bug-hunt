SweetSpotSimilarity returns a NaN length norm for fields longer than 2^30 terms

With the default SweetSpotSimilarity, a document whose field has 1,073,741,848 terms or more (one custom term frequency of 1.1 billion is enough) gets a NaN length norm, because lengthNorm adds abs(x-min) + abs(x-max) in int. That document is never returned, and top-k search also skips good hits stored near it.

The finding in 30 seconds

#

lengthNorm does its distance arithmetic in int, so with the default factors it wraps negative and returns NaN from length 2^30 + 1. The NaN norm then drops the document and breaks top-k pruning.

Background: length norms and top-k pruning

#
  1. A TF-IDF similarity multiplies a hit's score by a length norm that shrinks as the field gets longer. SweetSpotSimilarity documents it as 1/sqrt(steepness * (|x-min| + |x-max| - (max-min)) + 1), which is 1/sqrt(x) for the defaults (min = max = 1, steepness 0.5).
  2. The index stores each field's length in one byte. At search time the similarity computes the norm for each of the 255 decoded lengths. Byte 248 is the first above 2^30: it decodes to 1,073,741,848.
  3. Top-k search keeps the best possible score of each 256-document block (and of each 8,192-document range) and skips any block whose best score cannot beat the current k-th hit.

The finding, step by step

#
  1. Score with new SweetSpotSimilarity() and index 10,000 documents with one DOCS_AND_FREQS field: five hold only "a" (score 1.0), the others "a" plus padding (score 0.5), and doc 2000 holds "a" with custom term frequency 1,100,000,000.
  2. You expect doc 2000's length norm to be 1/sqrt of its decoded length (norm byte 248, 1,073,741,848), 3.05e-5, as the javadoc and ClassicSimilarity say. Then it scores 1.0121535 and search(q, 7) returns it first, followed by the five documents that score 1.0.
  3. Instead lengthNorm computes |x-1| + |x-1| in int. From x = 2^30 + 1 the sum passes Integer.MAX_VALUE and wraps negative, so the square root is NaN. Every field length from 1,073,741,848 up gets a NaN norm: doc 2000 scores NaN, and a NaN hit is never collected (collecting every hit returns 9,999 of 10,000).
  4. The NaN also becomes the best possible score of its 256-document block and 8,192-document skip range, and NaN never beats the threshold, so top-k pruning skips them, doc 2000 included: search(q, 7) returns [50, 9000, 0, 1, 2, 3, 4] and misses docs 2010, 3000 and 7000 (score 1.0). No error, with assertions on and off.

Who is affected

#

Only applications that score a normed field with the opt-in SweetSpotSimilarity (lucene/misc; the default factors are affected) and index one document whose field length reaches 1,073,741,848: custom term frequencies summing past a billion on a DOCS_AND_FREQS field, or about a billion tokens. Contrived, but silent when it happens.

Mechanism, terms and numbers765 words

SweetSpotSimilarity (lucene/misc) documents its length norm as 1/sqrt( steepness * (abs(x-min) + abs(x-max) - (max-min)) + 1 ) and says it degrades to 1/sqrt(x) with the default factors (min = max = 1, steepness 0.5). lengthNorm evaluates the sum in int, so with the defaults 2·(x − 1) wraps negative from x = 2^30 + 1 and the norm is NaN.

Through an index, lengthNorm sees only the 255 decoded norm lengths, so every field length of 1,073,741,848 or more (norm bytes 248-255) scores NaN. Lucene accepts such lengths: the indexing chain rejects only an int overflow, and one token with custom term frequency 1.1e9 on a DOCS_AND_FREQS field reaches it (so do about a billion ordinary tokens). The NaN document is never collected, and because a NaN block maximum never passes the competitive check, top-k search also skips competitive documents in the same 256-document postings block and 8,192-document skip range. Computing the distance in long fixes it. The int expression dates from the class's first version (2006); it is silent even with assertions on since 10.1.0. Low impact: an opt-in class and a 2^30-scale field.

The bug, step by step (main 645d4fe14a20)

#
  1. Int arithmetic. SweetSpotSimilarity.lengthNorm (SweetSpotSimilarity.java:110-120): final int l = ln_min; final int h = ln_max; (:112-113), then (float) (1.0f / Math.sqrt((s * (float) (Math.abs(numTerms - l) + Math.abs(numTerms - h) - (h - l))) + 1.0f)) (:116-119). The sum is int; the cast to float comes after it.
  2. It wraps. With the defaults (:36-38) the sum is 2·(x − 1): 2,147,483,646 at x = 2^30 (correct norm), -2,147,483,648 at x = 2^30 + 1, so 0.5 · sum + 1 is negative, Math.sqrt returns NaN and so does lengthNorm.
  3. Decoded lengths. computeNorm stores SmallFloat.intToByte4(length) (Similarity.java:151-161); TFIDFSimilarity.scorer fills normTable[i] = lengthNorm(byte4ToInt(i)) for i = 1..255 (TFIDFSimilarity.java:427-446) and score reads it (:470). Byte 247 decodes to 1,006,632,984 (finite), byte 248 to 1,073,741,848 (NaN), byte 255 to 2,013,265,944 (NaN). A field of exactly 2^30 + 1 terms encodes to byte 247 and is unaffected.
  4. Legal length. IndexingChain sums the field length with Math.addExact (1 per token for DOCS_AND_CUSTOM_FREQS, the custom frequency otherwise) and throws "too many tokens" only on an int overflow (IndexingChain.java:2053-2064). TermFrequencyAttribute names DOCS_AND_FREQS and sets no upper bound (TermFrequencyAttribute.java:23-34).
  5. Not collected. BatchScoreBulkScorer collects only if (score >= scorable.minCompetitiveScore) (BatchScoreBulkScorer.java:53-55): false for NaN.
  6. Block skipped. MaxScoreCache.computeMaxScore takes Math.max over the block's impacts (MaxScoreCache.java:84-88), and Math.max returns NaN if either argument is. ImpactsDISI keeps a block only if (maxScore >= minCompetitiveScore) (ImpactsDISI.java:80-82) and getSkipLevel climbs to the highest level whose maximum fails that test (MaxScoreCache.java:137-158), so the 256-doc block and the 8,192-doc level-1 range of the default postings format (Lucene104PostingsFormat.java:343-351) are skipped. In the 10,000-document example, doc 50 is collected before pruning starts (after 1,000 hits) and doc 9000 lies outside that range; docs 2010, 3000 and 7000 lie inside it. There the raised bar reaches the term scorer at doc 1024 and one skip goes from doc 1024 to doc 8192, so doc 2000 itself is skipped before it is scored; step 5 is what drops it when every hit is collected.

Exactly when the result is wrong

#

int arithmetic wraps consistently, so an intermediate overflow alone is harmless: the result is wrong only when the true value 2·(x − max) (for x ≥ max ≥ min) exceeds Integer.MAX_VALUE, i.e. x ≥ max + 2^30 (executed probe):

For the decoded lengths the wrapped value lies between -2^31 and about -2.7e8, so the norm is NaN for any steepness above about 4e-9; steepness 0 never gives NaN. With the defaults, norm bytes 248-255 are NaN, and bytes 1-247 are finite and match ClassicSimilarity to within one float step (243 of 247 identical; bytes 226, 229, 234 and 241 differ by one float step). Byte 0 is not a legal norm ("norm is never 0", Similarity.java:205); its table entry 1f / normTable[255] is NaN too, but by that contract a scorer never receives norm 0.

Exposure and likelihood223 words
  • Who is hit. Applications that score a normed field with SweetSpotSimilarity and index at least one document whose field length is at least 1,073,741,848 (with the defaults; other factors from max + 2^30). Routes: custom term frequencies on a DOCS_AND_FREQS field (TermFrequencyAttribute, or DelimitedTermFrequencyTokenFilter input such as a|1100000000), or about a billion ordinary tokens (an independent verifier indexed 1,073,741,848 tokens in about 45 s and reproduced it). The 10.5 option DOCS_AND_CUSTOM_FREQS counts tokens instead of summing frequencies, so it closes the custom-frequency route, not the ordinary-token one.
  • What goes wrong. Silently: the long document scores NaN and never appears in scored results (in the example it should be the top hit), and default top-k search (pruning after 1,000 hits) also skips the competitive documents of the same term in its 256-document block and 8,192-document skip range, returning weaker hits in their place. The skipping reach depends on the postings format: on 9.12.3 a different set is lost.
  • Not affected. Non-scoring matching (filters, count(), constant-score queries). The stored norm byte is the encoded length, which is correct, so a fix needs no reindex (since 7.0).
  • Likelihood: contrived. A 2^30-scale length in one field does not happen by accident, and maintainers ask users of custom frequencies to keep "reasonable values" (#11086). Low priority, but a real defect in the documented formula.

Why it looks unintended

#
  • The javadoc formula has no length limit and "degrades to 1/sqrt(x)" with the default factors; ClassicSimilarity returns 3.0517578E-5 for the same length.
  • Lucene accepts the length: indexing rejects only an int overflow, the bound a maintainer set for custom frequencies (#9990).
  • Lucene's similarity tests require finite scores for every norm; TestSweetSpotSimilarity never runs them and checks lengths below 1,000 only.
The full argument224 words
  • The contract. "Implemented as: 1/sqrt( steepness * (abs(x-min) + abs(x-max) - (max-min)) + 1 )" and "This degrades to 1/sqrt(x) when min and max are both 1 and steepness is 0.5" (SweetSpotSimilarity.java:97-102), the defaults (:36-38).
  • The upstream test asserts that equivalence with ClassicSimilarity for lengths 1 to 999 only (@Nightly testSweetSpotComputeNorm, "base case, should degrade", TestSweetSpotSimilarity.java:72-86).
  • Finite scores. BaseSimilarityTestCase checks that "scores are non-negative and finite" for every norm value (LUCENE-6896, -7997, -8010), but TestSweetSpotSimilarity extends LuceneTestCase. SimScorer#score must not decrease when freq increases "for any value of norm that may be produced by computeNorm", and must not increase when the unsigned norm increases "for any legal freq" (Similarity.java:207-213); NaN satisfies neither, since every comparison with NaN is false. TopScoreDocCollector says NaN and NEGATIVE_INFINITY "are not valid scores" (TopScoreDocCollector.java:30-31).
  • Legal input. IndexingChain accepts the length (Math.addExact, :2053-2064). Michael McCandless on #9990 (LUCENE-8947): "users must not try to write too many, too large custom term frequencies such that their sum overflows a Java int in a single field / document"; 1.1e9 is inside that bound. The ordinary-token route needs no custom frequency at all.
  • History. The int expression is in the class's first version (LUCENE-577, 2006); no javadoc, CHANGES entry, test or issue sets a length limit below Integer.MAX_VALUE.
The devil's-advocate check132 words

The strongest case (verifiers and a cross-model review): SweetSpotSimilarity is an expert, legacy class in lucene/misc; a billion-term field is absurd; and custom term frequencies are the user's responsibility: "If you use custom term frequencies (expert feature), then it is your responsibility to have reasonable values. Otherwise, things can easily overflow, break scoring" (Robert Muir, #11086, won't fix). Once a score is NaN, the collector's behaviour is documented.

Why it fails: #11086 is about bypassing the int-sum check, and the same comment names the bound ("less than int32"); this trigger is inside it, and the ordinary-token route needs no expert feature. The NaN arises in the similarity, whose own javadoc promises a finite value that the parent class computes. Rarity lowers the priority; it does not make the NaN intended.

Suggested fix

#

Recommended Compute the distance in long

Compute the distance in long: final long l = ln_min; final long h = ln_max; in lengthNorm (two tokens). Validated on main: the repro passes with assertions on and off; TestSweetSpotSimilarity with its nightly length-norm test, the whole lucene/misc test task and check pass. No reindex needed.

   public float lengthNorm(int numTerms) {
-    final int l = ln_min;
-    final int h = ln_max;
+    // long, not int: abs(x-min) + abs(x-max) can exceed Integer.MAX_VALUE for long fields
+    final long l = ln_min;
+    final long h = ln_max;
     final float s = ln_steep;
All options and trade-offs3 options · 533 words

The recommended fix was run in a scratch worktree of 645d4fe14a20 (OpenJDK 25.0.3), removed afterwards. "Closest suite" means TestSweetSpotSimilarity, the class's own test, run with -Ptests.nightly=true so that its @Nightly length-norm test runs too. LFV-413 (a plateau breaks norm monotonicity in the same method) is a different defect: this fix does not fix it, and its redesign would remove this overflow as a side effect.

Compute the distance in long (validated by the checks) (recommended)

#

Declare l and h as long in lengthNorm, so the whole expression is evaluated in long; numTerms is an int, so abs(x-min) + abs(x-max) stays below 2^33. The cast to float follows as before. Since 7.0 the norm byte stores the encoded length, which was always correct, so the fix changes only the search-time norm table: no reindex.

   public float lengthNorm(int numTerms) {
-    final int l = ln_min;
-    final int h = ln_max;
+    // long, not int: abs(x-min) + abs(x-max) can exceed Integer.MAX_VALUE for long fields
+    final long l = ln_min;
+    final long h = ln_max;
     final float s = ln_steep;

Trade-offs

  • Values. With the fix the default norm table equals ClassicSimilarity at 250 of 255 bytes; bytes 226, 229, 234 and 241 (unchanged from today) and byte 252 (2.49175E-5 vs 2.4917497E-5) differ by one float step, from the existing float conversion of the sum; lengths 1-999 are all identical.
  • Cost: negligible: 255 evaluations when a scorer is built, as today (TFIDFSimilarity.java:442-446); not measured.

What the checks validated

  • Gradle on a scratch worktree of 645d4fe14a20: stock fails the repro with assertions on and off; with the fix it passes with assertions on and off.
  • TestSweetSpotSimilarity with -Ptests.nightly=true: 3 of 3 pass, including the @Nightly testSweetSpotComputeNorm (16 s), which no earlier run had enabled (stock passes it too).
  • The whole lucene/misc test task: 317 tests, 9 skipped, 0 failures (the repro included). :lucene:misc:check -x test passes with the repro in place.
  • With the fixed class shadowed into the jars: the independent reproduction's end-to-end test passes 8 of 8; the 10,000-document example gives the ClassicSimilarity hits; the study's 6-test JUnit and the ordinary-token test passed with the same fix on a9779ef3c193.
  • Not run: other JDKs, x86, the full Lucene test suite.

Compute in double

#

Cast to double before the subtraction, e.g. Math.abs((double) numTerms - l) + ....

Trade-offs

Also overflow-free and closer to the javadoc formula. For the default factors, keeping the sum in double (dropping the (float) cast) reproduces ClassicSimilarity exactly at all 255 bytes and all lengths 1-999, since 0.5 · 2(x − 1) + 1 = x is exact in double; keeping the (float) cast gives the same values as the long fix (a standalone probe of both variants). Neither changes the nightly comparison for lengths 1-999; for other factors a norm may move by about one float step versus today. Not run through gradle.

Reject a non-finite norm in TFIDFSimilarity (defensive, not a fix)

#

TFIDFSimilarity.scorer could throw when lengthNorm returns a non-finite value.

Trade-offs

Catches any subclass with the same kind of bug, but turns silent wrong results into a search-time failure, and still needs the long fix. Not run.

Downstream note

#

Downstream, an application that lets document authors set custom term frequencies (for example with DelimitedTermFrequencyTokenFilter) on a field scored with SweetSpotSimilarity lets one such document drop itself and nearby relevant hits from ranked results; filters and non-scoring queries are unaffected.

How it was found

#

A harness compared Lucene's scoring components with their documented formulas. For SweetSpotSimilarity.lengthNorm it checked the real jar against the javadoc formula, evaluated exactly, over lengths 1 to 1,000 and all 255 decoded norm lengths for 48 factor settings: 305 NaN results, all at norm bytes 248-255. A JUnit then showed the effect end to end.

The method in full124 words

Method: semi-formal (bounded-exhaustive translation validation of the real jar against exact semantics).

  • Harness FormulaTV, part A1: lengthNorm on the stock jar against the javadoc formula evaluated in BigDecimal, for n = 1..1000 and the 255 decoded norm lengths x 8 plateaus x 6 steepness values: 60,240 checks, 334 mismatches, 305 of them NaN, all at norm bytes 248-255; the rest are rounding differences of at most 1.2 ulp. Part A1b ("degrades to 1/sqrt(x)"): 8 mismatches in 1,255, all NaN at bytes 248-255.
  • The finder read the root cause in the code and bridged it end to end with one custom term frequency; an independent reproducer wrote its own test from the claim alone, and a devil's advocate reproduced it with ordinary tokens.

LFV-754, snapshot of 2026-11-08

Registry title
SweetSpotSimilarity.lengthNorm adds abs(x-min) + abs(x-max) in int, so a field of 1,073,741,848 or more terms (reachable with one custom term frequency) gets a NaN norm: the document is never collected, and default top-k search also skips competitive documents in the same postings block and skip range
Area
misc / similarities (SweetSpotSimilarity lengthNorm; NaN effect on impacts-based top-k pruning in core search)
Priority
Low, rank 981: A field of 2^30 terms under the opt-in legacy SweetSpotSimilarity gives NaN norms that drop the document and break top-k pruning, a contrived trigger that one custom term frequency can reach.
Impact class
silent wrong results
Impact note
Hits only applications that score a normed field with the opt-in SweetSpotSimilarity (lucene/misc; the default factors min = max = 1, steepness 0.5 are affected, other factors with steepness > 0 once |x-min| + |x-max| exceeds Integer.MAX_VALUE) and index one document whose field length is at least 1,073,741,848 (the smallest length that encodes to norm byte 248), in practice a custom term frequency of about 1.1e9 on a DOCS_AND_FREQS field or about 1.07e9 ordinary tokens: that document scores NaN and is never collected, and default top-k search silently skips competitive documents in its 256-doc postings block and, on main and 10.5.2, its whole 8192-doc level-1 skip range [exec: main and 10.5.2 with -ea and -da; 8.0.0 to 10.0.0 with -da, where -ea trips Lucene's own collector assertion instead; the NaN norm itself in every release since 2.0.0]; the 10.5 option DOCS_AND_CUSTOM_FREQS counts tokens and so closes the custom-frequency route, not the ordinary-token one.
Summary
You score with SweetSpotSimilarity (default factors) and index one document whose DOCS_AND_FREQS field has a length of at least 1,073,741,848, for example one token with custom term frequency 1.1e9 or about 1.07e9 ordinary tokens, expecting the documented lengthNorm 1/sqrt(x) (about 3.05e-5, the ClassicSimilarity value) and an ordinary, low-ranked hit. Instead lengthNorm's int sum |x-1| + |x-1| wraps negative, so the norm and the score are NaN and the document is never collected (exhaustive collection returns 5,999 of 6,000 matches); because the NaN also makes the postings block's maximum score NaN, default top-k search skips that block and the skip range above it, so search(q, 7) on a 10,000-document index misses three documents that score 1.0 and returns documents that score 0.5 instead. ClassicSimilarity on the same index is correct.
