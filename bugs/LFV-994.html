SortedSetDocValues facets size the child queue from topN, so getTopChildren(Integer.MAX_VALUE, dim) throws where taxonomy facets return every label

On SortedSetDocValues facets, asking for every label with getTopChildren(Integer.MAX_VALUE, dim) throws IllegalArgumentException, even on a dim with 3 labels, because the child priority queue is sized from topN instead of the label count. Taxonomy facets cap the same queue and return the 3 labels.

The finding in 30 seconds

#

The SortedSetDocValues counter sizes its top-children queue by the topN you pass, not by how many labels the dim can have, and Lucene's priority queue refuses 2,147,483,631 slots or more.

Background: two kinds of facets and topN

#
  1. Lucene counts facet labels in two main ways: taxonomy facets keep the labels in a side index; SortedSetDocValues (SSDV) facets keep them in a doc-values field of the main index. Both implement the same Facets API.
  2. getTopChildren(topN, dim) returns the topN labels of a dim with the highest counts. The counter picks them with a priority queue that holds at most topN entries. Some callers, Lucene's own taxonomy tests among them, pass Integer.MAX_VALUE to mean "all children".
  3. Lucene's PriorityQueue allocates its whole array, topN + 1 slots, when it is created, and refuses sizes of 2,147,483,631 or more (Lucene's maximum array length, ArrayUtil.MAX_ARRAY_LENGTH).

The finding, step by step

#
  1. Index 3 documents with one SortedSetDocValues facet label each in dim dim: a, b, c (default FacetsConfig). Count all hits with SortedSetDocValuesFacetCounts.
  2. Ask for every label: getTopChildren(Integer.MAX_VALUE, "dim"). The only topN check rejects topN <= 0, and taxonomy facets answer this call with all labels, so you expect a (1), b (1), c (1), as getTopChildren(10, "dim") returns.
  3. You get IllegalArgumentException: maxSize must be >= 0 and < 2147483631; got: 2147483647, with assertions on and off. getAllDims(Integer.MAX_VALUE), getTopDims(10, Integer.MAX_VALUE) and the concurrent counts fail the same way.
  4. Why: to pick the top labels, the counter creates new TopOrdAndIntQueue(topN) (AbstractSortedSetDocValueFacetCounts.java:325) without capping topN at the 3 labels. Lucene's PriorityQueue allocates all topN + 1 slots up front and refuses 2,147,483,631 or more. Taxonomy facets build the same queue with Math.min(taxoReader.getSize(), topN).
  5. Below that limit the call works but still reserves the slots: getTopChildren(1 << 24, "dim") on the same 3 labels allocates 67,111,104 bytes, against 2,280 bytes at topN = 10 and 1,344 bytes on taxonomy facets. Close to the limit it can run out of heap instead.

Who is affected

#

Code using SortedSetDocValues facets, plain or concurrent, that passes Integer.MAX_VALUE (or any topN from 2,147,483,631) to getTopChildren, getAllDims or getTopDims to mean "all children": every such call on a dim with counts throws, at any index size, since 4.7.0. Large legal values reserve topN + 1 slots per dim.

Mechanism, terms and numbers571 words

SortedSetDocValues (SSDV) facets choose the top children of a dim with a priority queue that they size to the caller's topN, with no cap at the number of labels (AbstractSortedSetDocValueFacetCounts.java:325). Lucene's PriorityQueue allocates topN + 1 slots up front and refuses 2,147,483,631 or more. So getTopChildren(Integer.MAX_VALUE, dim), which Lucene's own taxonomy tests use to ask for every child, throws IllegalArgumentException on a dim with 3 labels as soon as one of its children has a count, and getAllDims(Integer.MAX_VALUE) and getTopDims(.., Integer.MAX_VALUE) fail the same way, in the plain and the concurrent counts. Facets.validateTopN accepts every topN > 0, and taxonomy facets cap the same queue with Math.min(taxoReader.getSize(), topN) and return every label. Below the limit the call returns the right labels but reserves the slots: 67,111,104 bytes for topN = 2^24 on 3 labels; close to the limit it can run out of heap instead. Default configuration, any index size, assertions on and off; 4.7.0 to 10.6.0 and main are affected (18 version points run, the releases in between by reading). Up to 4.6.1 the old API documented Integer.MAX_VALUE as "all children" and SSDV honoured it. The fix is one line: cap the queue at the field's label count, as taxonomy facets do.

The bug

#
  1. getTopChildren checks topN with validateTopN (AbstractSortedSetDocValueFacetCounts.java:57), which rejects only topN <= 0 (Facets.java:80-84), then calls getTopChildrenForPath (:61) and computeTopChildren (:300-301). getAllDims (:112-140) does the same for every dim; getTopDims passes topNChildren the same way (:189-191, :226).
  2. computeTopChildren (:309-339) walks the path's child ordinals and, at the first child with a count, creates the queue: q = new TopOrdAndIntQueue(topN); (:325). Nothing caps topN at the number of children or labels. With no counted child the queue is never built and the call returns normally.
  3. TopOrdAndIntQueue and TopOrdAndNumberQueue pass topN straight to PriorityQueue (TopOrdAndIntQueue.java:24, TopOrdAndNumberQueue.java:42). The PriorityQueue constructor throws IllegalArgumentException for maxSize >= ArrayUtil.MAX_ARRAY_LENGTH (PriorityQueue.java:121-124; Integer.MAX_VALUE - NUM_BYTES_ARRAY_HEADER, 2,147,483,631 here) and otherwise allocates new Object[maxSize + 1] (:129, :134). Its javadoc says it pre-allocates that array (:34); the class is @lucene.internal (:39).
  4. SortedSetDocValuesFacetCounts and ConcurrentSortedSetDocValuesFacetCounts both extend AbstractSortedSetDocValueFacetCounts, so both fail; DrillSideways (executed) and MultiFacets (by reading) hand them out for SSDV dims.
  5. Taxonomy facets build the same queue type as new TopOrdAndIntQueue(Math.min(taxoReader.getSize(), topN)) (TaxonomyFacets.java:250-251), and the other implementations cap too. The bound SSDV needs is at hand: SortedSetDocValuesReaderState.getSize(), "Number of unique labels", is 3 in the repro index.

Exposure and likelihood283 words
  • Who is hit. Callers of getTopChildren, getAllDims or getTopDims(.., topNChildren) on SortedSetDocValuesFacetCounts or ConcurrentSortedSetDocValuesFacetCounts (also through DrillSideways, executed, or MultiFacets, by reading, for SSDV dims) with Integer.MAX_VALUE, or any topN from 2,147,483,631 up. The call throws only when the dim or path has at least one child with a count; with none, the queue is never built (AbstractSortedSetDocValueFacetCounts.java:319-325). Code that moves from taxonomy to SSDV facets with that idiom, or shares it between both, meets it on the first such call.
  • Large but legal topN. Values such as 2^24 or 10^8 used as "all" work and return correct results, but reserve topN + 1 queue slots per dim with hits, per call: 67,111,104 bytes at 2^24 on 3 labels, 381 MiB per dim at 10^8. Values close to 2,147,483,631 can fail with OutOfMemoryError instead, depending on the heap: with a 1 GiB heap the hunt's harness got OutOfMemoryError: Java heap space at topN = 2,147,483,630.
  • Default vs opt-in. Default FacetsConfig, codec and IndexSearcher; no setting is needed. SSDV faceting is an opt-in API marked @lucene.experimental; the trigger is the topN value.
  • Who is not. The child queues of taxonomy facets and the other Facets implementations, which cap topN (taxonomy's getTopDims dimension queue is uncapped: the separate LFV-983). SSDV calls below 2,147,483,631 return the right labels as long as the heap holds topN + 1 slots.
  • Severity. Loud: an exception for that call; no wrong results, nothing written to the index.
  • How likely. Rare: no public SSDV caller with the Integer.MAX_VALUE idiom was found (downstream code uses it on taxonomy and range facets, which cap), and the searches found no public report since 4.7.0 (2014).

Why it looks unintended

#
  • The only topN check, validateTopN, rejects just topN <= 0; no javadoc sets an upper bound.
  • Taxonomy facets cap the same queue at the taxonomy's size, and Lucene's taxonomy tests call getTopChildren(Integer.MAX_VALUE, ...); five more implementations cap too.
  • Up to 4.6.1 the API documented Integer.MAX_VALUE as "all children" and SSDV honoured it; the 4.7.0 rewrite capped only taxonomy.
The full argument296 words
  • The API accepts the value. validateTopN "checks if topN is valid for getTopChildren and getAllDims" and rejects only topN <= 0 (Facets.java:74-84); LUCENE-10467 (#751, 9.2) made that range consistent across implementations. getTopChildren "Returns the topN child labels under the specified path" (Facets.java:40-41).
  • The sibling implementation caps on purpose. Math.min(taxoReader.getSize(), topN) came with the LUCENE-5339 rewrite (189feaacb6f, Michael McCandless), in the same commit that ported the old Integer.MAX_VALUE test to taxonomy getTopChildren(Integer.MAX_VALUE, "dim"); it is still on main (TestTaxonomyFacetCounts.java:556, TestTaxonomyFacetCounts2.java:338, :343). FloatTaxonomyFacets, StringValueFacetCounts, LongValueFacetCounts, RangeFacetCounts, RangeOnRangeFacetCounts and MatchingFacetSetsCounts cap too.
  • A large top-n is the normal way to ask for every child. On #843 Yuting Gan (Yuti-G) wrote that callers keep getting all children "as long as the user specifies a large top-n"; on #974 Greg Miller (gsmiller) wrote that "getAllChildren is not identical behavior as getTopChildren with a huge top-n value", treating the latter as an ordinary call.
  • History. Up to 4.6.1 the FacetRequest javadoc (Shai Erera, LUCENE-5136) said: "If set to Integer.MAX_VALUE, all immediate child categories will be returned", and Michael McCandless's SSDV accumulator (LUCENE-4795) answered any request for at least the dim's label count, so Integer.MAX_VALUE too, as "all available results" without a queue. The LUCENE-5339 rewrite (4.7.0) dropped that for SSDV only; none of its comments (90 in the JIRA record, 89 on the migrated #6403), no CHANGES or MIGRATE entry and no test discusses an uncapped SSDV queue. Executed: 4.6.1 returns all labels, 4.7.0 throws.
  • Core precedent. LUCENE-4938 (#6002) fixed an IndexSearcher queue that was not capped at maxDoc (reported and fixed by Robert Muir; Michael McCandless and Uwe Schindler traced it), and on LUCENE-8542 (#9588) Michael McCandless called pre-allocating the full topN "really unexpected behavior".
The devil's-advocate check185 words

The strongest case for "works as designed": topN is a size the caller chooses; PriorityQueue documents that it pre-allocates and throws on purpose "to prevent confusing OOME"; Facets is @lucene.experimental; getAllChildren exists for "all children"; the sandbox TopnOrdinalIterator also sizes its queue from topN, with a TODO by its author Egor Potemkin (#13568) doubting the taxonomy getSize() cap for very large taxonomies; and the 4.7.0 redesign never repeated the "Integer.MAX_VALUE = all" promise.

Why it fails: validateTopN accepts the value; PriorityQueue is @lucene.internal and its message names an internal maxSize, not topN; getAllChildren is unordered ("Users should make no assumptions about ordering of the children") and has no getAllDims or getTopDims form, and both of those fail too; the same call works on taxonomy facets through a cap added in the same rewrite; and the TODO questions how loose that cap is, which argues for a tighter or lazily growing queue, not for failing. The redesign point is fair, so the history is best presented as a behaviour change in 4.7.0 rather than a broken promise. Verdict: not intended, a defect (low severity).

Suggested fix

#

Recommended A: cap the child queue at the field's label count (validated)

Cap the queue at the field's label count, as taxonomy facets cap theirs at the taxonomy's size: new TopOrdAndIntQueue(Math.min(topN, state.getSize())) at AbstractSortedSetDocValueFacetCounts.java:325. With it the repro and the whole facet module test suite (307 tests) pass. The cap is loose when the field has many labels and the dim few.

if (q == null) {
  // Lazy init, so we don't create this for the
  // sparse case unnecessarily
  // the path cannot have more children than the field has labels:
  q = new TopOrdAndIntQueue(Math.min(topN, state.getSize()));
}
All options and trade-offs4 options · 495 words

Option A was applied in two separate scratch worktrees of 645d4fe14a20 and run with gradle (both removed after the runs); the hunt's checks validated the same diff. Options B and C were not built.

A: cap the child queue at the field's label count (validated) (recommended)

#

One line in computeTopChildren (AbstractSortedSetDocValueFacetCounts.java:325), mirroring TaxonomyFacets.makeTopOrdAndNumberQueue (TaxonomyFacets.java:250-251).

if (q == null) {
  // Lazy init, so we don't create this for the
  // sparse case unnecessarily
  // the path cannot have more children than the field has labels:
  q = new TopOrdAndIntQueue(Math.min(topN, state.getSize()));
}

Trade-offs

  • A path's children are distinct ordinals of the field, so the queue never needs more than state.getSize() slots; results are unchanged for every topN that works today.
  • Loose when the field holds many labels and the dim few: by default all dims share one field, so a 3-label dim in a field with millions of labels still gets a queue of that size for Integer.MAX_VALUE (the same looseness as the taxonomy cap). The cross-model reviewer (OpenAI GPT-5.6) pointed this out.

What the checks validated

  • Gradle, stock 645d4fe14a20 (seed DEADBEEF), in two separate worktrees: the repro fails with -Ptests.asserts=true and false.
  • Gradle with the fix, the whole facet module (:lucene:facet:test, seed C0DE0994, assertions on): 40 classes (39 upstream and the repro), 307 tests, 0 failures, 7 skipped (tests a default run skips, e.g. the nightly group); the repro also passes with assertions off. :lucene:facet:checkGoogleJavaFormat passes on the fix.
  • First run, with the fix: the repro and TestSortedSetDocValuesFacets, TestDrillSideways, TestParallelDrillSideways, TestFacetQuery and TestFacetLabel, assertions on: 62 tests, 0 failures; the repro and TestSortedSetDocValuesFacets with assertions off and nightly tests on: 20 tests, 0 failures, 0 skipped.
  • The executed probe with the fix: Integer.MAX_VALUE returns the 3 labels, and 1 << 24 allocates 2,248 bytes instead of 67,111,104.
  • The hunt's checks: the finder's 6 tests and an independent reproducer's 10 tests pass; 7 upstream facet test classes (82 tests) pass with this fix and the sibling LFV-983 fix; the differential harness's saturation and allocation failures drop to 0.

B: cap at the path's own number of children (not built)

#

For a flat dim, ordRange.end() - ordRange.start() + 1; a hierarchical DimTree exposes only child iterators, so a child count would have to be computed or stored. Prompted by the cross-model reviewer's remark that A is loose.

Trade-offs

Removes the looseness of A; more code, and the hierarchical case needs new bookkeeping.

C: grow the queue lazily up to topN (not built)

#

Start small and grow only as children arrive, instead of allocating topN + 1 slots up front.

Trade-offs

Would help every top-N facet path, but core PriorityQueue has a fixed capacity, so it needs a different structure; larger than the bug needs.

Not recommended: reject large topN in validateTopN

#

Add an upper bound to Facets.validateTopN.

Trade-offs

Turns the working taxonomy call getTopChildren(Integer.MAX_VALUE, ...), and Lucene's own tests of it, into errors.

Downstream note

#

Services that pass a user-chosen facet size straight to SortedSetDocValues facets should cap it: values from 2,147,483,631 up fail, and large values below that reserve heap in proportion to the value.

How it was found

#

AI tools probing numeric limits passed Integer.MAX_VALUE as topN to SortedSetDocValues, taxonomy, string and long facets: only the SortedSetDocValues counts failed to return child labels (taxonomy's huge-topNDims failure is LFV-983). A model-based differential harness confirmed it on 40 random indexes; one minimal test reproduces it.

The method in full171 words

Method: non-formal first signal, then semi-formal checking (an executed probe, then model-based differential testing on the stock jars).

  • A planning AI tool for numeric-limit hunts read the facet code and ran a probe (FacetTopNProbe) on main a9779ef3c193, 10.5.2, 9.12.3 and the 10.6 release candidate: SSDV getTopChildren, getAllDims and getTopDims with Integer.MAX_VALUE threw, and topN = 10^8 allocated 381 MiB per dim.
  • The hunting AI tool wrote a reference model of top-N facet results (saturation: for topN at least the number of children, the result equals the result at topN = 1000; allocation bounded by the labels) and a differential harness over 40 seeded random indexes, 18 Facets constructions and 5 call shapes: 93,485 checks, of which 9,924 saturation and 3,060 allocation checks failed on stock main (including the sibling dim-queue sites, LFV-983) and 0 with both fixes. An SMT solver confirmed that exactly topN from 2,147,483,631 to 2,147,483,647 throws.
  • It reduced the case to a public-API JUnit with a taxonomy control, and later to the one-test repro.

History

#

Introduced by the LUCENE-5339 facet API rewrite (5458dbf2484, 2013-11-14), first released in 4.7.0. 4.3.0 to 4.6.1 return all labels for Integer.MAX_VALUE; 4.7.0 through 10.6.0 and main fail (18 version points run, the releases in between by reading). Only the exception type changes, with core PriorityQueue.

Versions tested9 rows

LUCENE-5339 "Simplify the facet module APIs" (#6403; Michael McCandless; feature-branch commit 5458dbf2484f, 2013-11-14; branch_4x port 7477fde1cb06 and trunk merge 9d0b60388da8, 2014-01-04; SVN-era patches, no PR) built the new SSDV child queue as new TopOrdCountQueue(topN) (renamed TopOrdAndIntQueue in f6cd7fda747). In the same series 189feaacb6f capped every taxonomy queue with Math.min(taxoReader.getSize(), topN) and ported the old Integer.MAX_VALUE test to taxonomy, and 92b1e230715 removed the old SSDV accumulator with its "all available results" branch. LFV-994, snapshot of 2026-11-07

Registry title
SortedSetDocValues facets size the child priority queue from topN instead of the number of labels, so getTopChildren, getAllDims and getTopDims(.., topNChildren) with topN = Integer.MAX_VALUE throw IllegalArgumentException where taxonomy facets return every label, and a large topN allocates topN + 1 queue slots even for a 3-label dim
Area
facet / SortedSetDocValues child queue (AbstractSortedSetDocValueFacetCounts.computeTopChildren, inherited by SortedSetDocValuesFacetCounts and ConcurrentSortedSetDocValuesFacetCounts)
Priority
Low, rank 648: SSDV getTopChildren and getAllDims fail loudly on the Integer.MAX_VALUE 'all children' idiom that taxonomy facets accept, a module bug that never returns wrong results, so it leads the new MAX_VALUE facet rows right after the GroupingSearch row LFV-964.
Impact class
wrong error
Impact note
Applications that call getTopChildren, getAllDims or getTopDims(.., topNChildren) on SortedSetDocValuesFacetCounts or ConcurrentSortedSetDocValuesFacetCounts (also through MultiFacets or DrillSideways for SSDV dims, by reading) with Integer.MAX_VALUE (or any topN >= 2147483631) as 'all children' get IllegalArgumentException 'maxSize must be >= 0 and < 2147483631' on every such call, where the same call on taxonomy facets returns every label, and with a large but legal topN pay a transient allocation of topN + 1 references per dim with hits however few labels exist (64 MiB at 2^24 on 3 labels); default FacetsConfig, codec and searcher, any index size, -ea and -da, every release from 4.7.0 to 10.6.0 and main; results for ordinary sizes are correct and nothing is written to the index.
Summary
You index a SortedSetDocValues facet dim with three labels and call getTopChildren(Integer.MAX_VALUE, dim) to get all of them, expecting the same result as getTopChildren(1000, dim), because Facets.validateTopN accepts every topN > 0 and taxonomy facets return all three labels for exactly this call. Instead AbstractSortedSetDocValueFacetCounts.computeTopChildren builds new TopOrdAndIntQueue(topN) without capping topN at the number of labels, so PriorityQueue throws IllegalArgumentException 'maxSize must be >= 0 and < 2147483631; got: 2147483647', and getAllDims(Integer.MAX_VALUE) and getTopDims(10, Integer.MAX_VALUE) fail the same way. Below that limit the same line pre-allocates topN + 1 slots: getTopChildren(2^24, dim) over 3 labels allocates about 64 MiB to return 3 results.
