All bugs · Lucene bug · LFV-967 · completionweight-scorersupplier-null-bulkscorer-npe

CompletionWeight returns a scorer supplier with a null bulk scorer, so IndexSearcher#search of a CompletionQuery throws NullPointerException on a segment it cannot match

Since 10.0, a CompletionQuery run through the generic IndexSearcher#search throws NullPointerException as soon as one segment has no suggest field or the query's filter excludes a whole segment. In the repro SuggestIndexSearcher#suggest returns 3 suggestions and IndexSearcher#search crashes; 9.12.3 returned the same 3.

The bug in 30 seconds

#

A search asks each segment's query weight for a scorer supplier; null means "skip this segment". The completion query's weight never says null: it hands out a supplier, and only that supplier's bulk scorer is null. SuggestIndexSearcher#suggest checks the bulk scorer; the generic IndexSearcher does not.

Background: how a search visits segments

#
  1. IndexSearcher#search visits each segment and asks the query's Weight for a ScorerSupplier. A null supplier means nothing can match there, and the segment is skipped. The rule: Weight#scorerSupplier "must return null if the scorer is null".
  2. From a non-null supplier it takes a BulkScorer and calls score() on it, which feeds the matches to the collector. It does not expect that bulk scorer to be null.
  3. The document suggester (SuggestField, CompletionQuery) is usually run with SuggestIndexSearcher#suggest, which has its own segment loop. A CompletionQuery can also go through the generic IndexSearcher#search with TopSuggestDocsCollectors; without a query timeout that worked in 9.x.

The bug, step by step

#
  1. Index 3 suggestions (apple0-apple2, weights 1-3) with SuggestField and commit, then 1 document without the suggest field and commit: 2 segments, default IndexWriterConfig.
  2. Run a PrefixCompletionQuery that matches all three through IndexSearcher#search(query, manager) with TopSuggestDocsCollectors. You expect what SuggestIndexSearcher#suggest returns on the same reader: apple2 3.0, apple1 2.0, apple0 1.0. 9.12.3 returns exactly those.
  3. Instead: NullPointerException ... because "scorer" is null. For segment 2 the query's weight still hands out a scorer supplier; only that supplier's bulk scorer is null. IndexSearcher checks the supplier, not the bulk scorer, and calls score() on null.
  4. One segment is enough if the query's filter returns Bits.MatchNoBits for it: suggest() returns 0 hits, IndexSearcher#search throws. With a query timeout set, the NPE comes from TimeLimitingBulkScorer's constructor. suggest() itself is never affected: it skips a null bulk scorer.

Who is affected

#

Applications on 10.0.0-10.5.2, the 10.6 branch or main that run a CompletionQuery through IndexSearcher#search (or SuggestIndexSearcher's inherited search) with TopSuggestDocsCollectors. Once any segment lacks the suggest field, every such search fails. Default settings. Users of suggest() are not affected, and this bug never returns wrong results.

Mechanism, terms and numbers642 words

Weight#scorerSupplier "must return null if the scorer is null" (Weight.java:142 on main 645d4fe14a20), and IndexSearcher#searchLeaf relies on it: it skips a segment only when the supplier is null and otherwise calls score() on the supplier's bulk scorer without a null check (IndexSearcher.java:842-852). CompletionWeight#scorerSupplier returns a supplier for every segment (CompletionWeight.java:93-137); its bulkScorer() returns null when the segment has no terms for the suggest field (:108), has no FST for it (:114), or the query's BitsProducer filter returns Bits.MatchNoBits (:125); the first and third were executed, the no-FST case is by code reading only. So a CompletionQuery run through IndexSearcher#search(Query, CollectorManager) with TopSuggestDocsCollectors, or through the search method SuggestIndexSearcher inherits, throws NullPointerException on such a segment; with a query timeout, TimeLimitingBulkScorer's requireNonNull throws it first (TimeLimitingBulkScorer.java:64-66). SuggestIndexSearcher#suggest, the documented entry point, goes through the Weight#bulkScorer helper and skips the null (SuggestIndexSearcher.java:69-71), so it is not affected. It is a regression in 10.0.0 from #13408 (ddf538d43e9), which moved this weight's three return null lines from the overridden Weight#bulkScorer, which 9.x IndexSearcher null-checked, into ScorerSupplier#bulkScorer: the same call (no query timeout) returns exactly suggest()'s suggestions on 8.11.4 to 9.12.3 and throws on every executed 10.x release, the 10.6 branch and main. The search fails loudly; nothing is corrupted, and this bug returns no wrong results. The fix returns null from scorerSupplier in the three cases.

Terms

#
  • Weight / ScorerSupplier / BulkScorer: a query's per-search Weight gives, per segment, a ScorerSupplier, which gives the BulkScorer that feeds matches to a collector. Weight.java:142: "It must return null if the scorer is null." Weight.java:145: "@return a ScorerSupplier providing the scorer, or null if scorer is null". ScorerSupplier.java:39-46 documents no null from bulkScorer(); its default wraps get(), which "may not return null" (:29).
  • Document suggester: SuggestField indexes suggestions into an FST per segment (a dedicated completion postings format); a CompletionQuery (PrefixCompletionQuery, RegexCompletionQuery, FuzzyCompletionQuery, ContextQuery) finds the top suggestions. An optional BitsProducer filter restricts the documents per segment. CompletionQuery.java:36 recommends SuggestIndexSearcher#suggest to run them.
  • TopSuggestDocsCollector: the only collector CompletionScorer#score accepts (CompletionScorer.java:69-72), so it is what a caller of IndexSearcher#search(Query, CollectorManager) uses.

The bug

#
  1. IndexSearcher.java:842-843: searchLeaf asks weight.scorerSupplier(ctx) and skips the segment only if it is null.
  2. :844-852: otherwise it calls bulkScorer(), wraps it in a TimeLimitingBulkScorer when a timeout is set (:846-848) and calls score() on it (:852). No null check.
  3. CompletionWeight.java:93-137: scorerSupplier always returns new ScorerSupplier() {...} (its get and cost throw UnsupportedOperationException). The supplier's bulkScorer() returns null at :108 (no terms for the field), :114 (no FST, "a segment can have a null suggester") and :125 (the filter returned Bits.MatchNoBits).
  4. So on such a segment searchLeaf calls score() on null: NullPointerException ... because "scorer" is null at IndexSearcher.java:852. With a timeout, TimeLimitingBulkScorer's constructor (Objects.requireNonNull, :64-66) throws first.
  5. SuggestIndexSearcher.java:64-86: suggest loops over the segments itself, calls the final Weight#bulkScorer helper (Weight.java:170-179, which returns null for a null supplier and otherwise scorerSupplier.bulkScorer()), and skips a null result (:71). That is why suggest() works.

The numbers

#

Index: segment _0 with SuggestField("sug", "apple" + i, i + 1) for i = 0..2, segment _1 with one document without the field. suggest(q, 5, false) returns 3: doc 2 apple2 3.0, doc 1 apple1 2.0, doc 0 apple0 1.0. On main, weight.scorerSupplier(leaf) is non-null on both leaves, and supplier.bulkScorer() is a CompletionScorer on leaf 0 and null on leaf 1; IndexSearcher#search(q, manager(5)) throws the NPE at IndexSearcher.java:852. On 9.12.3 the same IndexSearcher#search returns the same 3 suggestions. A one-segment index with a MatchNoBits filter: suggest() returns 0, IndexSearcher#search throws.

Exposure and likelihood270 words
  • Who is exposed. Code that runs a CompletionQuery through IndexSearcher#search(Query, CollectorManager), for example to send every query type through one search entry point, or through the search method SuggestIndexSearcher inherits from IndexSearcher. SuggestIndexSearcher#suggest users are not affected. Elasticsearch and OpenSearch run completion queries through their own per-segment loop with a null check, as suggest() does (read 2026-10-28), so they are not affected; Solr has no CompletionQuery user.
  • Default configuration. Default codec (plus the completion postings format that SuggestField needs), default IndexWriterConfig, a plain IndexSearcher.
  • Deterministic once on that path. Every such search fails once it reaches a segment without a document that has the suggest field (an ordinary index state when only some documents carry suggestions; how common it is in practice was not measured) or a segment for which the query's filter returns Bits.MatchNoBits (possible on a one-segment index; Lucene's own TestSuggestField#testSuggestOnAllFilteredDocuments uses such a filter with suggest()). The third trigger, a segment with the field but no FST, is by code reading only.
  • Upgrade trap. The same code runs without an exception on 9.x (and, without a query timeout, returns exactly suggest()'s suggestions) and fails after upgrading to 10.x.
  • Effect. A NullPointerException from inside IndexSearcher fails that search call. This bug returns no wrong or partial results, corrupts nothing, and nothing persists. (On the same path a query timeout can also make the search repeat suggestions: that is the separate LFV-969.)
  • How likely: plausible but uncommon. No downstream user of this path was found (code search found only copies of SuggestIndexSearcher), and no upstream test runs a CompletionQuery through IndexSearcher#search.

Why it is a bug, not intended

#
  • Weight#scorerSupplier "must return null if the scorer is null" (Weight.java:142); ScorerSupplier#bulkScorer documents no null.
  • A 10.0 regression: 9.12.3 null-checked Weight#bulkScorer and returned the 3 suggestions; #13408 moved the check to the supplier and this weight's return null lines into it.
  • Nothing forbids the call: the javadoc recommends suggest(), and SuggestIndexSearcher's own inherited search crashes too.
The full argument381 words
  • Contract. Weight.java:137-150: "It must return null if the scorer is null. ... @return a ScorerSupplier providing the scorer, or null if scorer is null". ScorerSupplier.java:39-46: bulkScorer() documents no null; its default is new DefaultBulkScorer(get(Long.MAX_VALUE)), and get "may not return null" (:29). The Weight#bulkScorer helper's own javadoc shows the signal: if (scorerSupplier == null) { // No docs match return null; } (Weight.java:152-179). The rule is written for the supplier: no sentence says that a non-null supplier's bulkScorer() is non-null. That follows from the default (which wraps get(), and get() may not return null), and it is what IndexSearcher#searchLeaf and TimeLimitingBulkScorer's requireNonNull rely on. The repro's fourth test checks this reading (a non-null supplier whose bulkScorer() is null), not a null get(): CompletionWeight's get() throws.
  • The rule was stated when the supplier was added. In the #13319 discussion (2024), iamsanjay wrote "scorerSupplier has to be null if scorer is null", and jpountz, reviewing: "Let's return a null ScorerSupplier? Returning null from ScorerSupplier#get is not legal."
  • History. In 9.12.3, CompletionWeight overrode Weight#bulkScorer and returned null in the same three cases (9.12.3 CompletionWeight.java:65-92), and IndexSearcher checked it: BulkScorer scorer = weight.bulkScorer(ctx); if (scorer != null) { (9.12.3 IndexSearcher.java:763-764). #13408 changed IndexSearcher to check only the supplier, made Weight#bulkScorer a final helper, deleted its sentence that it "can return null if this query matches no documents" (from #11897), added the requireNonNull to TimeLimitingBulkScorer, and moved CompletionWeight's three return null lines unchanged into the new ScorerSupplier#bulkScorer. CHANGES (10.0.0, CHANGES.txt:2271-2273): "Weight#bulkScorer() still exists for compatibility, but delegates to ScorerSupplier#bulkScorer()". No CHANGES or MIGRATE entry (MIGRATE.md:1678-1684, the 10.0 Weight contract notes) allows a null bulk scorer; the PR's review comments do not mention null bulk scorers or the suggester.
  • Misuse is reported explicitly elsewhere in the module. CompletionScorer.java:69-72 throws IllegalArgumentException("collector is not of type TopSuggestDocsCollector"), so a generic caller with the right collector was anticipated; an NPE from core is not such a signal.
  • Only direct producer. A scan of main's non-test sources for a literal return null in a ScorerSupplier#bulkScorer() body (the independent reproduction, repeated by the fact check) finds only CompletionWeight and ConstantScoreQuery (ConstantScoreQuery.java:173-176), which only forwards a null from its inner supplier.
The devil's-advocate check203 words

The intended-behaviour checker and the reviews by another model family (OpenAI GPT-5.6) built the strongest case: (1) CompletionQuery.java:36 says "Use SuggestIndexSearcher#suggest(CompletionQuery, int, boolean) to execute any query that provides a concrete implementation of this query"; (2) CompletionWeight is deliberately partial (get/cost throw UnsupportedOperationException, explain returns null under a // TODO); (3) the classes are @lucene.experimental; (4) no upstream test runs a CompletionQuery through IndexSearcher#search; (5) SuggestIndexSearcher refuses an executor because the dedup logic is not thread-safe (SuggestIndexSearcher.java:41-42), and LFV-969 shows the generic path repeating hits under a timeout. So a committer could call the path unsupported.

Why it fails: line 36 recommends suggest() but forbids nothing, and IndexSearcher#search accepts any Query; SuggestIndexSearcher is an IndexSearcher, and its inherited search crashes the same way; the path (without a query timeout) worked from 8.11.4 to 9.12.3; the supplier's null rule is an explicit core contract that #13408 itself relied on when it moved IndexSearcher's check to the supplier; and the mismatch exists whatever the caller (the repro's fourth test checks it directly on each segment). The residual point, an unusual path, bears on priority and wording, not on whether it is a bug.

Suggested fix

#

Recommended Return null from CompletionWeight#scorerSupplier for a segment that cannot match (validated)

In CompletionWeight#scorerSupplier, check the three cannot-match cases (no terms for the field, no FST, filter returns MatchNoBits) and return null there, so the supplier's bulkScorer() always builds a CompletionScorer (one file, +28/-24). The new test passes 4 of 4 and the whole suggest module passes, with assertions on and off.

Return null from CompletionWeight#scorerSupplier for a segment that cannot match (validated) (validated by the checks) (recommended)

#

Move the three checks from the supplier's bulkScorer() into scorerSupplier() itself and return null there; bulkScorer() then only builds the CompletionScorer. One file, +28/-24. The new top of scorerSupplier:

final LeafReader reader = context.reader();
final Terms terms;
final NRTSuggester suggester;
if ((terms = reader.terms(completionQuery.getField())) == null) {
  return null;
}
if (terms instanceof CompletionTerms completionTerms) {
  if ((suggester = completionTerms.suggester()) == null) {
    // a segment can have a null suggester
    // i.e. no FST was built
    return null;
  }
} else {
  throw new IllegalArgumentException(completionQuery.getField() + " is not a SuggestField");
}
BitsProducer filter = completionQuery.getFilter();
final Bits filteredDocs;
if (filter != null) {
  filteredDocs = filter.getBits(context);
  if (filteredDocs.getClass() == Bits.MatchNoBits.class) {
    return null;
  }
} else {
  filteredDocs = null;
}

Trade-offs

  • The terms lookup, suggester() and filter.getBits(context) now run in scorerSupplier(). By code reading, the two in-tree paths that take a bulk scorer from this supplier (IndexSearcher.java:842-845 and the Weight#bulkScorer helper, Weight.java:170-178, used by SuggestIndexSearcher.java:70) call bulkScorer() right after, so their work per segment, or per intra-segment partition, is the same as before; not measured. Weight.java:137-140 allows a supplier to be requested several times per segment; a caller that does so now repeats these checks, a cost that was not reviewed.
  • Weight#scorer (Weight.java:129-135) also calls scorerSupplier(), then get(). With the fix it returns null for a segment that cannot match instead of throwing UnsupportedOperationException from get(); on a segment that can match it still throws that exception, now after the checks.
  • The "is not a SuggestField" IllegalArgumentException moves from bulkScorer() to scorerSupplier(): IndexSearcher#search, suggest() and the Weight#bulkScorer helper throw the same exception and message as before, but Weight#scorer on such a field now throws it instead of UnsupportedOperationException. Both Weight#scorer points were checked with an executed probe on stock main and with the fix (not a regression test).
  • ContextQuery's and FuzzyCompletionQuery's weights extend CompletionWeight without overriding scorerSupplier, so they get the fix too. A "Bug Fixes" CHANGES line would be usual; none is drafted.

How it was found

#

History

#

Introduced in 10.0.0 by #13408 (ddf538d43e9, 2024-05-27), which moved this weight's return null lines from the null-checked Weight#bulkScorer into ScorerSupplier#bulkScorer. Executed: 8.11.4 to 9.12.3 throw no exception and, without a query timeout, return exactly suggest()'s suggestions; every executed 10.x release, the 10.6 branch and main crash.

Versions tested6 rows

LFV-967, snapshot of 2026-10-29

Registry title
CompletionWeight returns a non-null ScorerSupplier whose bulkScorer() is null, so IndexSearcher#search of a CompletionQuery throws NullPointerException on a segment the query cannot match (regression in 10.0 from #13408)
Area
suggest / document (NRT) suggester: CompletionWeight#scorerSupplier vs the Weight/ScorerSupplier contract and IndexSearcher#searchLeaf
Impact class
crash
Impact note
Applications on 10.0.0-10.5.2, the 10.6.0 release-candidate branch or main that run a CompletionQuery through the generic IndexSearcher#search(Query, CollectorManager<TopSuggestDocsCollector, ...>) instead of the documented SuggestIndexSearcher#suggest get a NullPointerException from IndexSearcher#searchLeaf (or from TimeLimitingBulkScorer's constructor when a query timeout is set) as soon as one segment has no document with the suggest field, has no FST for it, or gets Bits.MatchNoBits from the query's BitsProducer filter (the filter case needs only one segment); the search fails, nothing is corrupted and no wrong results are returned; SuggestIndexSearcher#suggest is not affected; the same call worked through 9.12.3; ordinary scale, default codec and IndexWriterConfig.
Summary
You index suggestions with SuggestField and run a PrefixCompletionQuery through IndexSearcher#search with a CollectorManager of TopSuggestDocsCollector, on an index where one segment has no document with the suggest field (or where the query's filter matches no document of a segment). You expect the same suggestions as SuggestIndexSearcher#suggest (3 in the repro), because Weight#scorerSupplier 'must return null if the scorer is null' and IndexSearcher then skips that segment, as 9.12.3 does. Instead CompletionWeight returns a non-null ScorerSupplier whose bulkScorer() returns null, and IndexSearcher#searchLeaf throws NullPointerException ('Cannot invoke BulkScorer.score(...) because "scorer" is null'; with a timeout set, Objects.requireNonNull in TimeLimitingBulkScorer throws it first).
