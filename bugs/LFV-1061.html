DirectoryReader.open and openIfChanged with an ExecutorService leak the segment readers of accepted tasks when a later submit is rejected

If the ExecutorService you pass to DirectoryReader.open or openIfChanged accepts one segment task and rejects the next, as a full bounded pool does, the open fails as it should, but the accepted task's reader is never closed. Its files stay open, and you cannot close it: you never got it.

The finding in 30 seconds

#

Background: opening a reader with an executor

#
  1. A DirectoryReader is a list of segment readers, one per segment. Opening a segment reader opens that segment's files, and closing it closes them.
  2. Since 10.4.0 you can pass an ExecutorService to DirectoryReader.open or openIfChanged. Lucene then opens the segments in parallel, one task per segment, and collects the readers.
  3. An ExecutorService may refuse a task: submit throws RejectedExecutionException, for example when a bounded ThreadPoolExecutor is full or the executor was shut down.

The finding, step by step

#
  1. Commit two documents separately, so the index has two segments, _0 and _1, and call DirectoryReader.open(dir, executor). Lucene submits one task per segment, newest first: _1, then _0.
  2. The executor runs the _1 task, which opens _1's files, then rejects the _0 task with RejectedExecutionException, as a full ThreadPoolExecutor with the default AbortPolicy does.
  3. You expect that exception and nothing left open: no reader was returned to you, and the code's own comment says a failed open closes the readers it created.
  4. Instead the exception leaves the submit loop before any result is collected, so _1's reader is never closed: closing the directory fails with "still 2 open files: {_1.fdx=1, _1.fdt=1}". Every failed attempt leaks again; for openIfChanged, a reused segment reader stays at refCount 2 instead of 1.

Who is affected

#

Applications that pass an executor to DirectoryReader.open or openIfChanged (opt-in, since 10.4.0) that can reject: a full bounded pool with the default AbortPolicy, for example one shared with other work, or a pool shut down during an open. Each rejected attempt leaks the readers of the tasks already accepted. Results stay correct.

Mechanism, terms and numbers665 words

Since 10.4.0, DirectoryReader.open and openIfChanged accept an ExecutorService and open one segment per task (#15428). StandardDirectoryReader.createSegmentReaders submits all tasks in one loop with no try/catch, and closes readers on failure only in its second loop, the one that collects the results. When the executor accepts some tasks and then rejects a submit, as a full bounded ThreadPoolExecutor with the default AbortPolicy does, RejectedExecutionException leaves the method from the first loop: the readers the accepted tasks built are never collected and never closed, and the caller cannot close them because it never receives them. With two one-document segments and an executor that runs the first task and rejects the second, MockDirectoryWrapper then refuses to close: "there are still 2 open files: {_1.fdx=1, _1.fdt=1}". For a refresh, a reused segment reader is left at refCount 2 instead of 1. Interrupting the opening thread while it waits leaks that task's reader the same way. The open fails loudly and search results are unaffected; the leak is silent and repeats on every failed attempt. Every release from 10.4.0 to 10.6.0 and main is affected. A fix that skips tasks that have not started and waits for the running ones passes the test and the closest suites.

Terms

#
  • Executor overloads: eight public DirectoryReader methods take an ExecutorService; six of them can reach StandardDirectoryReader.createSegmentReaders (StandardDirectoryReader.java:187-247): DirectoryReader.open(Directory, ExecutorService) and five siblings (open with a leaf sorter or an IndexCommit, openIfChanged with or without an IndexCommit; DirectoryReader.java:71, :106-107, :164, :217-221, :269-270, :295-296 at 645d4fe14a20), added in 10.4.0 by #15428. The initial open reaches it at :96, a refresh through the reopen factory at :181. The other two, the NRT overloads that also take an IndexWriter (DirectoryReader.java:383-384, :425-429), never use the executor: they return null or call writer.getReader (StandardDirectoryReader.java:444-475). On an NRT reader only openIfChanged with an IndexCommit uses the executor, by reopening to the commit (StandardDirectoryReader.java:420-430, :496-505).
  • Rejection: ExecutorService.submit throws RejectedExecutionException when it cannot take a task, for example a ThreadPoolExecutor whose threads and queue are full, with the JDK's default AbortPolicy, or any executor after shutdown().

The bug

#
  1. The executor branch (:195-228) first submits one task per segment, newest first, in a loop with no try/catch (:197-207, executor.submit at :203). A task opens a new SegmentReader (:292-296) or, for a refresh, takes a reference on the old reader of an unchanged segment ("this reader will be shared between the old and the new one, so we must incRef it", :319-323).
  2. Then it collects the results with Future.get() into readers[] (:208-217). If a task failed it keeps going, "to allow us to close created readers" (:213-214), and the cleanup decRefWhileSuppressingException(firstException, readers) (:221) releases every collected reader.
  3. A RejectedExecutionException from the submit at :203 leaves the method before step 2. The futures of the tasks already accepted are dropped without being awaited, their readers never reach readers[], and the cleanup never runs. The caller gets only the exception.
  4. Second trigger: an InterruptedException from get() is caught together with ExecutionException (:212), and the loop moves on. The task it was waiting for still runs; if it builds a reader, nobody stores or closes it.
  5. The branch without an executor (:229-245) creates readers inside try and releases them on any Throwable (:241-242).

Exposure and likelihood269 words
  • Who is hit. Applications that call one of the six executor overloads that can reach this code with an executor that can reject. No Lucene module passes an executor here itself: IndexWriter uses the NRT open, and the replicator calls the reopen factory with null.
  • Default vs opt-in. Opt-in. Without an executor the sequential branch runs, which cleans up. Common pools such as Executors.newFixedThreadPool queue without bound and do not reject while running.
  • What triggers it. (a) A bounded pool with AbortPolicy that is full when the open submits its tasks: a stock ThreadPoolExecutor(1, 1, 0, ms, new SynchronousQueue<>()) whose worker is busy reproduced it. (b) An executor shut down while an open or refresh is in flight, after it accepted the first task (if it rejects the first submit, nothing leaks). (c) Secondary: the opening thread is interrupted, or cancelled with Future.cancel(true), while it waits.
  • How much. Per failed attempt, the reader of every task accepted before the rejection: its open files and segment core; for a refresh, an extra reference on each reused segment reader, so closing the old reader no longer closes it. Lucene never releases them. From the code, linear in failed attempts (a retry loop was not run) and in accepted tasks (one leaked reader in the minimal test, two in the first finder's three-segment open test); any index with at least two segments. Whether garbage collection later reclaims file handles was not measured.
  • What does not happen. No wrong results, no index change, no hang. The open or refresh fails loudly, and after a failed refresh the old reader keeps working.

Why it looks unintended

#
  • The method's own comment: "we still process the rest of the completed futures to allow us to close created readers".
  • The #15428 author kept a plain ExecutorService "to ensure we could gracefully close out the readers in the event of an exception".
  • Upstream's testExecutorServiceExceptionHandling requires a clean close after a rejecting executor; it rejects only the first submit.
The full argument212 words
  • The code says so. "If there is an exception creating the reader we still process the rest of the completed futures to allow us to close created readers" (StandardDirectoryReader.java:213-214).
  • The author said so. In the #15428 review a reviewer suggested TaskExecutor; the author answered: "I went with an ExecutorService here directly to ensure we could gracefully close out the readers in the event of an exception" (BryceKan3, 2025-11-18).
  • The same method without an executor releases every reader on any Throwable (:229-245).
  • Upstream tests. TestDirectoryReader.testExecutorServiceExceptionHandling (:1300-1316) passes a shut-down executor, expects a RuntimeException, then closes a newDirectory(), which fails on open files. It rejects the first submit, so no task was accepted. testExecutorServicePartialFailure (:1318-1335) fails a task through a failed future, not a rejected submit. Neither covers this path.
  • Ownership. IndexReader.incRef (IndexReader.java:164-174): "Be sure to always call a corresponding decRef, in a finally clause; otherwise the reader may never be closed." The caller cannot do that for readers it never received.
  • Rejection is ordinary. Lucene's own TaskExecutor treats rejecting executors as legitimate: "execute directly on the current thread in case of rejection to ensure a rejecting executor only reduces parallelism and does not result in failure" (search/TaskExecutor.java:58-67, #13622).
The devil's-advocate check133 words

The strongest case for "intended" (the devil's-advocate verifier and the intended-lens reviewer): the javadoc of the executor overloads says only "executorService used to open segment readers in parallel" and @throws IOException (DirectoryReader.java:64-70), and the executor is the caller's own object, so its rejections are the caller's problem.

Why it fails: the caller can release only what it receives, and the failed open returns nothing; the code comment, the author's review answer, the sequential branch and upstream's rejecting-executor test all require cleanup. For the interrupt trigger the case is stronger: FSDirectory (store/FSDirectory.java:77-82) tells applications that use Thread.interrupt() or Future#cancel to switch to RAFDirectory. That note is about channels closed by an interrupt during I/O, while this code catches InterruptedException on purpose and carries on. Verdict: rejection high, interrupt medium.

Suggested fix

#

Recommended B: close what started, never wait for what did not (claim or wait)

Recommended, fix B (validated): give each task a claim flag. Once the open fails, the opener claims every task that has not started, so that task builds nothing and is not waited for; it waits only for running tasks, closes every reader built and rethrows. The minimal test and the 68 tests of the closest suites pass.

All options and trade-offs4 options · 1,644 words

They differ in what a failed open waits for.

Trade-offs

  • Strict and live. When open throws, every reader built has been released. Once the open has failed, the opener never waits for a task that has not started: a full or shut-down pool cannot make a failed open hang, and an interrupted opener returns once the running task finishes. It still waits for tasks that have started, as today's success path does.
  • Cost. One AtomicBoolean and one compareAndSet per segment on the success path. It still calls executor.submit, so executors that override submit (as upstream's createExecutorServiceThatFailsOneTask does) see no change. No API change.
  • Behaviour change. After a failure, still-queued tasks become no-ops. The cross-model reviewer's stock-pool test assumes its accepted task always opens a file; under B the opener may claim that task first, so the test fails that precondition ("accepted worker never opened a segment file") in its 3 iterations and the suite reports the pool threads it left behind; its other 9 runs pass. Not a leak.
  • Scope. Catching RuntimeException also covers the IllegalStateException that getOldSegmentReader (:263-285) can throw inside the submit loop; an Error from submit still skips the cleanup, as today.

Trade-offs

Simplest. But it waits for every accepted task, also tasks that have not started. The independent reproducer's interrupt test, whose queued task can run only after open returns, hangs (timeout after 120 s, the opener parked in FutureTask.get). If the executor drops an accepted task, as shutdownNow() does with queued tasks without completing their futures (probe), a failed open would wait forever where today it throws at once. Today's success path already waits for every accepted task the same way.

What the checks validated

The same gradle runs as B: the minimal test passes with assertions on and off; 68 of 68 at seeds DEADBEEF and 5EED1234; the format check flags only the test's comment line, not the fix. Standalone: the cross-model reviewer's 12 tests (-ea, -da, 3 iterations) and the first finder's three tests pass.

Not recommended: Future.cancel(false) before waiting

#

The study's reviewers suggested cancelling the futures that have not started. The Future API cannot tell "not started" from "running".

Trade-offs

A probe on JDK 25: cancel(false) on a running FutureTask returns true, the task keeps running and produces its value, and get() then throws CancellationException: the value is lost. The reader of a running task would leak in a new way. B gets "cancel only if not started" from its claim flag.

Not run: run a rejected task on the calling thread

#

As TaskExecutor does (search/TaskExecutor.java:58-67): catch the rejection and run the task in the opener's thread, so the open succeeds on a full pool.

Trade-offs

Changes behaviour that upstream's testExecutorServiceExceptionHandling asserts (a shut-down executor makes open throw), and does not fix the interrupt trigger, so it would still need A or B.

Downstream note

#

Services that share one bounded pool between reader refreshes and request work, and retry a failed refresh, leak again on every rejected attempt while the pool stays full.

How it was found

#

Formal: TLA+ model checking (TLC) of Lucene's reader reference counting and its open paths. With the faults "a later submit is rejected" and "the opener is interrupted while it waits", the invariant that no reader leaks fails, and the modelled fix passes. Two code-reading passes found the same spot; a public-API JUnit test confirmed it.

The method in full143 words

Method: formal, TLA+ model checking with TLC (a hunt unit, 2026-10-26), on a model of IndexReader reference counting and the StandardDirectoryReader open paths built from the code with a file:line map.

  • With the faults rejectAt (a later submit is rejected) and interrupt (the opener is interrupted in Future.get), the NoLeak invariant fails; the model with the fix passes. Re-run on 645d4fe14a20 by a hunt unit: rejectAt3 violated at 93 distinct states (fixed: 77, OK), interrupt2 violated at 215 (fixed: 132, OK).
  • The fault edges were added while modelling the code, so a strict reading could call the discovery semi-formal.
  • Found independently by two other hunt units: one by code reading during an exception-path scan (both triggers), one by code reading while modelling commit discovery (interrupt trigger).
  • A later hunt unit re-ran the model and reduced the counterexample to the one-test repro.

LFV-1061, snapshot of 2026-11-03

Registry title
DirectoryReader.open and openIfChanged with an ExecutorService never close the segment readers of tasks the executor already accepted when a later submit is rejected (or when the opening thread is interrupted while it waits), so those segments' files stay open
Area
core / index reader open (StandardDirectoryReader.createSegmentReaders, executor branch behind the ExecutorService overloads of DirectoryReader.open and openIfChanged, #15428)
Priority
Low, rank 948: A bounded reader-open leak on an exception path that happens only with the opt-in executor overload (10.4+) when a submit is rejected or the opening thread is interrupted, and the open fails loudly.
Impact class
minor
Impact note
Applications that open or refresh readers through the opt-in ExecutorService overloads of DirectoryReader.open and openIfChanged (since 10.4.0) and pass an executor that can reject (a bounded ThreadPoolExecutor with the default AbortPolicy that is saturated when the open submits its per-segment tasks, or an executor shut down while an open or refresh is in flight): the open fails loudly with RejectedExecutionException, but the segment readers the already-accepted tasks built (for a refresh, the extra reference on a reused segment reader) are never released, so Lucene keeps their files and segment cores open and the caller cannot release them because it never receives those readers (executed: MockDirectoryWrapper reports the accepted segment's files still open; after a failed refresh the reused segment reader's refCount is 2 instead of 1); it repeats on every failed attempt; interrupting the opening thread while it waits is a second, weaker trigger; search results are unaffected; any index size.
Summary
You call DirectoryReader.open(directory, executor), or openIfChanged with an executor, and the executor accepts the task for one segment but rejects the submit for the next one, as a saturated bounded pool does; you expect the RejectedExecutionException and nothing left behind, as the method's own cleanup comment intends, as the sequential path does and as upstream's rejecting-executor test requires. Instead the exception leaves the submit loop before any future is collected, so the reader the accepted task built is never decRef'd: on a two-segment index, MockDirectoryWrapper then refuses to close because the files of the accepted segment are still open.
