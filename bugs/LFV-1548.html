IndexMergeTool cannot merge source indexes in which a field carries the soft-deletes role (from 7.4.0) or the parent-field role (from 9.10.0): its writer configuration names neither field and the command line has no option for them, so IndexWriter.addIndexes throws IllegalArgumentException and no document is merged

The little-used command-line tool IndexMergeTool (misc module) refuses indexes in which a field carries the soft-deletes or the parent-field role: an IllegalArgumentException names the field and no document is merged. Nothing is lost or damaged; core's IndexWriter.addIndexes merges them when the writer names the field (a few lines of code).

The finding in 30 seconds

#

A few lines of code are a complete workaround for six shapes run with them; the maintainers may read the repair as an improvement of an old tool. Refused in the runs on main 1ae70c6e45b8, branch_11x b98f116b3179 and 10.6.0: two sources with the same role; a role-carrying source beside a default-configuration one; with the tool's options. Default-configuration sources merge.

Background: three pieces

#
  1. IndexMergeTool is a command-line tool of the misc module: IndexMergeTool [OPTION...] <mergedIndex> <index1> <index2> [index3] .... It creates mergedIndex with an IndexWriter and calls IndexWriter.addIndexes with the source directories.
  2. Two opt-in settings of IndexWriterConfig give a field a role. setSoftDeletesField(name): a document with a value in that doc-values field counts as deleted. setParentField(name): the writer adds that field to every root document; it is needed for document blocks together with an index sort. A segment that has the field records the role in its field infos.
  3. IndexWriter refuses, on purpose, a segment whose field infos carry a role that the writer's own configuration does not name (soft deletes since 7.4.0, the parent field since 9.10.0). Those core checks are not in question here.

The finding, step by step

#
  1. Write two indexes, index1 and index2, each with new IndexWriterConfig().setSoftDeletesField("soft"): one addDocument, then one softUpdateDocument of that document. Each index then holds 1 document, and its field infos mark soft as the soft-deletes field.
  2. Run IndexMergeTool merged index1 index2. The usage text says "Merges source indexes 'index1' .. 'indexN' into 'mergedIndex'" and names no condition on how the sources were written, so you expect a merged index with 2 documents.
  3. You get IllegalArgumentException: this index has [soft] as soft-deletes already but soft-deletes field is not configured in IWC, as a command line with exit status 1. No document is merged: the new merged directory holds only write.lock, and the two sources are byte-identical afterwards.
  4. Why: the tool opens the merged index with new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE), which names no soft-deletes field and no parent field, and its three options (-merge-policy, -max-segments, -verbose) cannot name one. IndexWriter.addIndexes refuses a source segment whose field infos carry a role that the writer's configuration does not name. The message asks for a setting ("IWC") that the command line cannot give.
  5. Two indexes written with setParentField("parent") are refused the same way (can't add field [parent] as parent document field; this IndexWriter has no parent document field configured). The same sources merge through IndexWriter.addIndexes into a writer that names the field (2 documents for the soft-deletes pair, 4 for the parent-field pair), and two indexes of the default configuration, two documents each, merge through the tool (4 documents).

Who is affected

#

Someone who runs IndexMergeTool (the command line or its main) on indexes whose writer set setSoftDeletesField and wrote that field, or set setParentField and wrote a document. Both are opt-in in Lucene's API. They meet it on the first attempt, loudly; no document is merged and nothing is lost. IndexWriter.addIndexes into a writer that names the field is the workaround.

Mechanism, terms and numbers1,522 words

Small and loud. IndexMergeTool (org.apache.lucene.misc) is a little-used command-line tool that merges several indexes into one. For the source indexes described here it stops with an IllegalArgumentException that names the field; as a command line it ends with exit status 1. No document is merged, a new destination holds only write.lock, and the sources and an index that was already in the destination are byte-identical afterwards (run). Core merges the same indexes: IndexWriter.addIndexes into a writer whose configuration names the field. So a few lines of code are a complete workaround for six shapes that were run on that route: five pairs of sources with the same role under the same field name, and a soft-deletes source beside a default-configuration source.

The tool builds one writer configuration, new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE) (IndexMergeTool.java:51, lines at main 1ae70c6e45b8), opens the merged index with it and calls writer.addIndexes(indexes) (:115-118). Its option switch knows -merge-policy, -max-segments and -verbose (:64-80). IndexWriter.addIndexes(Directory...) passes every field of every source segment through the writer's field-number map (IndexWriter.java:3176-3181), and that map throws when an incoming field is marked as the soft-deletes field or as the parent field and the writer's configuration names none (FieldInfos.java:414-417, :458-465, :483-490). The two core checks are intended (LUCENE-8335, #12829; core's own tests assert both messages) and are not in question. What this page reports is that the tool, which is built on addIndexes, was not adapted and has no way to name the fields.

The trigger is the role in a segment's field infos, not the setter call: two sources whose writer named a soft-deletes field and never wrote it merge, and so do two sources whose writer named a parent field and wrote no document (both run). Run and refused, on main 1ae70c6e45b8, on branch_11x b98f116b3179 and on the 10.6.0 release jars: two sources with the same role; a role-carrying source beside a default-configuration source, in either position; the soft-deletes role written by softUpdateDocument, by a soft delete through updateDocValues and by an addDocument that carries the field; parent-field sources with one block and with single documents only; with -max-segments 1, with -merge-policy and with the three options together.

The usage text and the class javadoc say that the tool merges the given source indexes and state no condition on how they were written; the javadoc of addIndexes(Directory...) names the write locks, the same Lucene version, MAX_DOCS and the index sort, and neither role (a gap in core's javadoc; it says nothing, either way, about what a tool should do). The expectation is implied by the tool's own description and by core's reference path; it is not promised in so many words. The maintainers may read the repair as an improvement of an old tool with a fixed option list rather than a bug fix, or keep the loud refusal as the safe behaviour of a tool that cannot know the application's merge policy or index sort. Both readings exist, and the label is theirs to choose.

Each half has its own range. The soft-deletes half: the 68 releases from 7.4.0 to 10.6.0 that were run; 7.4.0 is the first release that has soft deletes at all. The parent-field half: the 20 releases from 9.10.0 to 10.6.0 that were run; 9.10.0 is the first release with IndexWriterConfig#setParentField. One change was validated through Lucene's own build (the test, the misc module's tests and its lint): before the writer is opened, the tool reads each source's field infos and names its soft-deletes field and its parent field.

The devil's-advocate check586 words

The strongest case for "intended or accepted" has three parts.

First, the refusal is a deliberate rule that core's tests pin: the caller declares the field. Both messages of this page are asserted word for word, with the tests' own field names, through the IndexWriter constructor (TestIndexWriter.java:3833-3840, :4882-4891), and so is the refusal of a mismatch through addIndexes (TestIndexWriter.java:3857-3864; TestAddIndexes.java:1964-1985). In the review of LUCENE-8335 s1monw asked whether opening a writer that names no soft-deletes field should fail when a field in the field infos has the flag (2018-06-01, on #9382), and in the review of #12829 mikemccand read the parent-field check as the one that catches the addIndexes mismatch (2024-01-05).

Second, a generic tool cannot make that declaration safely. It cannot know the application's retention merge policy or its index sort, so a tool that names the two roles by itself and then merges with its own configuration changes what the merged index holds. The runs of this page show both: with the change of Suggested fix and -max-segments 1 the merged index keeps 0 of the 2 soft-deleted documents that addIndexes and forceMerge(1) keep under the application's configuration, and two sorted parent-field sources end as a segment without a sort, which the application's sorted writer then refuses. A maintainer can take these as the reason to keep a loud refusal, or to prefer an explicit option or a documented limit.

Third, this is an old command-line tool with a short, fixed option list that predates both features (added in 2005; a fixed IndexWriterConfig since 2010). Its options change of 2020 (LUCENE-9206, type task) came after soft deletes had shipped and kept the configuration as it was. The refusal is loud and names the field, and for a Java caller a few lines are a workaround. softUpdateDocument is tagged Expert and @lucene.experimental. Precedents towards "improvement": LUCENE-3296 (#4369, type enhancement: a sibling tool got a caller-supplied configuration), #13125 (BPIndexReorderer made to work with a parent field; CHANGES.txt lists it under "New Features") and LUCENE-9206 (#10246, type task). So: a missing option of an old tool, an improvement and not a bug; or a refusal to keep and to document.

What answers it, and what stays: a list of options says what the tool offers, not which indexes it refuses, and no text limits the tool to indexes of the default configuration. The tool creates the destination itself, the two sources agree with each other, and the tool alone chooses the configuration that core must refuse; each message then asks a command-line user for a writer setting that no argument can give. The soft-deletes half does not rest on the expert method: a soft delete through updateDocValues and a plain addDocument that carries the field reach the same refusal (run). Another functional gap of this same tool was filed and fixed as a bug (LUCENE-7864, #8915; CHANGES.txt lists it under "Bug Fixes"). None of this refutes the first two parts: that the command-line user has no option at all supports an enhancement request as well as a bug report, and the safety argument speaks for an explicit option or a documented limit as much as for the change that was run. What stays is the label and the shape of a repair: the maintainers may call it an improvement, or keep the refusal and say so in the usage text, and that is theirs to choose. It is a classification question, not evidence that the tool's silence was meant.

Suggested fix

#

Recommended Take the two roles from the sources (validated)

Trade-offs

What the change does not do, each run or read:

  • Different field names. Two sources that name different soft-deletes fields stay refused, by core: with the change cannot configure [softy] as soft-deletes; this index uses [softx] as soft-deletes already (the last source read sets the name; run), and on core's own route into a writer that names softx the same refusal with the two names the other way round (run).
  • An index in the destination. The tool opens the destination with OpenMode.CREATE, so a run that succeeds replaces an index that was there (run with the unchanged tool on default-configuration sources). Today's refusal leaves such an index as it was; with the change the same shape merges and the earlier index is gone (run). That is what the tool's open mode does when a run succeeds (no option changes it), not something the change adds.
  • No retention policy. A merge that the tool runs reclaims soft-deleted documents that an application's retention merge policy would keep. Run with the change on sources that retain 1 soft-deleted document each: with -max-segments 1 the merged index retains 0, against 2 for addIndexes and forceMerge(1) under the application's configuration; with no option the segments are copied and 2 stay. The javadoc of setSoftDeletesField says that merges reclaim soft-deleted documents, and -merge-policy needs a class with a no-argument constructor.
  • No index sort. Two sorted parent-field sources go from today's loud refusal to a merged segment without a sort, which the application's sorted writer then refuses (cannot change previous indexSort=null ...): run with the change and -max-segments 1. The second variant avoids that.
  • A mix of sources. A parent-field source that holds one block of two documents beside a source without the field merges with the change (run without -max-segments). The regression test is therefore the test of this page (two sources with the same role), not that mix.
  • By reading. The sources are read before addIndexes takes their write locks; when several sources name a role, the last one read sets it; the writer is still not closed when addIndexes throws (unchanged).

You run the command-line tool IndexMergeTool on two indexes that your application wrote with a soft-deletes field (IndexWriterConfig#setSoftDeletesField and one softUpdateDocument each) and expect one merged index: the tool's usage text says it 'Merges source indexes 'index1' .. 'indexN' into 'mergedIndex'' and names no condition on how the sources were written. Instead the tool stops with IllegalArgumentException, 'this index has [soft] as soft-deletes already but soft-deletes field is not configured in IWC', and merges nothing: it opens the merged index with a writer configuration that names no soft-deletes field, and it has no option to name one. Two indexes written with a parent field (IndexWriterConfig#setParentField) are refused the same way ('can't add field [parent] as parent document field; this IndexWriter has no parent document field configured'), while IndexWriter.addIndexes into a writer that names the same field merges the same indexes.
