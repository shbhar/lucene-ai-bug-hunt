Facet DoubleRange with an exclusive bound at an infinity is not empty: "value > +Infinity" matches the +Infinity documents

A facet DoubleRange for "value > +Infinity" should match nothing, but it counts, and drills down to, every document whose value is +Infinity; "value < -Infinity" likewise matches the -Infinity documents. Every release since 4.4.0 (2013) is affected, 10.6.0 included.

The finding in 30 seconds

#

Facet range classes store inclusive bounds and turn an exclusive bound into the next double inward. At an infinity there is no next double, so the exclusive flag is silently dropped.

Background: how a facet range stores its bounds

#
  1. DoubleRange(label, min, minInclusive, max, maxInclusive) describes one bucket for facet counting (DoubleRangeFacetCounts) and drill-down (getQuery). "price > 7" is (7, false, +Inf, true).
  2. It stores only inclusive bounds: an exclusive bound becomes the next double inward. Math.nextUp(7) is 7.000000000000001, so "> 7" is stored as [7.000000000000001, +Inf].
  3. A range that can match nothing, such as [7, 7), is rejected by the constructor: IllegalArgumentException: range "..." matches nothing.

The finding, step by step

#
  1. Index five documents whose double doc-values field holds -Infinity, -2.5, 1.5, 7 and +Infinity. Count them with DoubleRangeFacetCounts and two ranges: new DoubleRange("> 7", 7, false, +Inf, true) and new DoubleRange("> +Inf", +Inf, false, +Inf, true).
  2. You expect "> 7" to count 1 (the +Infinity document) and "> +Inf" to count 0, because no number is greater than +Infinity, or to be rejected as "matches nothing", like (+Inf, +Inf) and LongRange("> Long.MAX_VALUE").
  3. Instead "> +Inf" also counts 1, and its drill-down query returns 1 hit, the +Infinity document. No error.
  4. Why: the constructor turns an exclusive bound into the next double, Math.nextUp(min), and Math.nextUp(+Infinity) is +Infinity. So "> +Inf" is stored as [+Inf, +Inf], and the only emptiness check, min > max, does not fire.
  5. The same step is copied into the range-on-range DoubleRange (a "> +Inf" range intersects an indexed [5, +Inf]) and DimRange.fromDoubles / fromFloats.

Who is affected

#

Code that builds a facet double range from a computed bound: "value > threshold" when the threshold is +Infinity (the minimum of no values), an overflow bucket after a +Infinity boundary, or range-on-range against indexed [x, +Inf] ranges. Default codec and settings, any index size. Rare: an always-empty range such as "> +Infinity" is unlikely to be written on purpose.

Mechanism, terms and numbers645 words

The facet range classes take explicit minInclusive / maxInclusive flags and store inclusive bounds: an exclusive min becomes Math.nextUp(min) and an exclusive max Math.nextAfter(max, -Inf) (range/DoubleRange.java:64-74 on main 645d4fe14a20). Math.nextUp(+Infinity) is +Infinity and Math.nextAfter(-Infinity, -Infinity) is -Infinity, so an exclusive bound that is the infinity on its own side silently becomes inclusive: "value > +Infinity", new DoubleRange(label, +Inf, false, +Inf, true), is stored as [+Inf, +Inf], and the only emptiness check, minIn > maxIn (:76-78), does not fire. The range then counts, and its drill-down query matches, every +Infinity document; the mirror [-Inf, -Inf) matches the -Infinity documents. Every other empty range in the class is rejected with "matches nothing", and LongRange rejects the same case for Long.MAX_VALUE since LUCENE-5371 (4.7.0). The same step is copied into rangeonrange.DoubleRange and DimRange.fromDoubles / fromFloats. Present since the API was added in 4.4.0; every executed release through 10.6.0 and main fails. A 2 x 3-line guard per constructor that rejects these inputs fixes it; the repro and the facet module's checks pass with it. Only this degenerate, always-empty shape is affected, so the priority is low.

The mechanism (main 645d4fe14a20)

#
  1. The constructor (range/DoubleRange.java:61-78; the NaN checks are left out here):
   if (!minInclusive) {
     minIn = Math.nextUp(minIn);                                // :64-66
   }
   if (!maxInclusive) {
     // Why no Math.nextDown?
     maxIn = Math.nextAfter(maxIn, Double.NEGATIVE_INFINITY);   // :71-74
   }
   if (minIn > maxIn) {
     failNoMatch();                                             // :76-78
   }

Math.nextUp(+Inf) is +Inf and Math.nextAfter(-Inf, -Inf) is -Inf. For (+Inf, false, +Inf, true) both stored bounds are +Inf, so minIn > maxIn is false and the range is built.

  1. Matching is inclusive on the stored bounds. accept(value) is value >= min && value <= max (:85-87). DoubleRangeFacetCounts.getLongRanges() counts with an inclusive LongRange over doubleToSortableLong(min/max) (DoubleRangeFacetCounts.java:255-270); the drill-down getQuery(...) (:335) matches values.advanceExact(approximation.docID()) && range.accept(values.doubleValue()) (:194-196); for a multi-valued source (:351) the query calls the same range.accept per value (:299).
  2. Only the half-open shapes reach it. (+Inf, +Inf) is rejected, because the exclusive max steps down to Double.MAX_VALUE; [x, +Inf) excludes +Inf for the same reason. A Z3 model of the scalar range.DoubleRange constructor and accept proved that, for that class, the two cases (+Inf, +Inf] with x = +Inf and [-Inf, -Inf) with x = -Inf are the only mismatches between accept and the requested predicate, with no false negatives. The copies below are not in that model; they were tested separately.
  3. Copies. rangeonrange.DoubleRange repeats the constructor's bound handling: the same NaN checks, nextUp / nextAfter steps, "Why no Math.nextDown?" comment and min > max check (rangeonrange/DoubleRange.java:43-60, written minInclusive == false instead of !minInclusive); a "> +Inf" query range then INTERSECTS every indexed range whose upper end is +Inf. DimRange.fromDoubles (facetset/DimRange.java:60-81) and fromFloats (:84-104) use Math.nextUp / Math.nextDown with the same min > max check.
  4. The long siblings guard it. LongRange calls failNoMatch() for an exclusive Long.MAX_VALUE min or Long.MIN_VALUE max (range/LongRange.java:58-72), as do rangeonrange.LongRange and DimRange.fromLongs (DimRange.java:34-49, IllegalArgumentException("Invalid min input: ...")).

Exposure and likelihood227 words
  • Who can hit it. Code that computes a bound and builds "value > threshold" as DoubleRange(label, threshold, false, +Inf, true), or the mirror "value < threshold", when the threshold is the infinity on that side. Natural sources: the minimum of no values is +Infinity (new DoubleSummaryStatistics().getMin()), and "value > min" then matched the +Infinity documents in an executed probe; a bucket list whose last boundary is +Infinity plus an overflow bucket "> last boundary" (an executed test with left-open buckets over {0, 10, +Inf} counted the +Infinity document in (10, +Inf] and again in the overflow bucket); for range-on-range, any indexed open-ended range [x, +Inf] is matched by a "> +Inf" query range.
  • What it takes. The standard facet range API with its own inclusive flags; default codec, configuration and searcher; no opt-in setting; one +Infinity document suffices. The classes are marked @lucene.experimental.
  • Effect. Silent wrong results: a range that should be empty counts, and drill-down matches, exactly the documents at that infinity. No exception, no hang, no false negatives. The extra matches are only documents whose value is exactly that infinity, still within the hits the application's query collects and the drill-down's other clauses.
  • How likely. Rare: it needs an exclusive bound that is itself an infinity and documents at that infinity. The recorded searches found no public report since 4.4.0 (2013).

Minimal repro

#

One JUnit test method in lucene/facet, public API, no index: build "value > +Infinity" as new DoubleRange("x", +Inf, false, +Inf, true) and ask accept(+Inf). It passes if the constructor rejects the range or the range does not accept +Inf. Deterministic, one thread; the same with assertions on and off.

Expected
The constructor throws IllegalArgumentException ("matches nothing"), or accept(+Inf) returns false.
Observed
The range is built as [+Inf, +Inf] and accept(+Inf) returns true: AssertionError: (+Inf, +Inf] should match nothing, but accept(+Inf) returned true.

All files of this repro: repro/LFV-313/

More files, environment, full output307 words

The test accepts either correct outcome: the constructor rejects the empty range (what the fix does, and what the class already does for (+Inf, +Inf)), or the range does not accept +Inf. accept() is the predicate the class documents as "True if this range accepts the provided value"; the facet count and the drill-down use the same stored bounds, so the end-to-end symptom follows from it. No index and no randomness; the seed only feeds the test runner.

Left out on purpose: the mirror case [-Inf, -Inf) and the two copies (rangeonrange.DoubleRange, DimRange.fromDoubles / fromFloats) are the same idiom at parallel fix sites; the fix covers all of them. The copy in src/ is the same test with the Apache license header and two lint fixes that ./gradlew check asks for (a comment line shortened to 100 columns, the unused catch parameter written as _). The unnamed _ needs Java 22 or later: fine on main (Java 25), but branch_10_6 has minJava = "21", and its ecj lint, like main's, rejects an unused named catch parameter, so a 10.x backport needs another form of the test (for example one that asserts the caught exception's message); none was written or built there.

Why it looks unintended

#
  • The constructors take explicit inclusive flags, and "value > +Infinity" matches no double.
  • The class rejects every other empty range (testUselessRange; (+Inf, +Inf) throws "matches nothing"), and LongRange rejects the same case for Long.MAX_VALUE since LUCENE-5371.
  • +Infinity is an ordinary value here: [1.5, +Inf) excludes the +Infinity document.
The full argument279 words
  • Contract. The constructors own the exclusive meaning: rangeonrange.DoubleRange documents "@param minInclusive if the minimum is inclusive" and "@param maxInclusive if the maximum is inclusive" (rangeonrange/DoubleRange.java:35, :37). An exclusive min of +Infinity means "value > +Infinity".
  • Empty ranges are an error in this package. Range.failNoMatch() is "Invoke this for a useless range" (range/Range.java:37-40); testUselessRange asserts that new DoubleRange("useless", 7.0, true, 7.0, false) throws (TestRangeFacetCounts.java:288-295).
  • The upstream oracle is strict. testRandomDoublesSingleValued expects values[i] > min for an exclusive min and values[i] < max for an exclusive max (TestRangeFacetCounts.java:1166-1174; multi-valued :1346, :1351). Its bounds are nextDouble() values in [0, 1) or earlier boundaries, never an infinity, which is why the tests miss it.
  • History. LUCENE-4965 (3d60bd10d48d, 2013) also wrote LongRange with the integer form of the same saturation, if (!minInclusive && min != Long.MAX_VALUE) min++;. LUCENE-5371 (8e1879225a35; branch_4x merge 7477fde1cb06, first release 4.7.0) replaced it with failNoMatch() and, in the same commit, gave DoubleRange only the min > max check. Executed: LongRange (MAX, MAX] is accepted on 4.4.0-4.6.1 and rejected from 4.7.0; DoubleRange (+Inf, +Inf] is accepted on every release run. The recorded searches and our code reading found no javadoc, CHANGES entry, test, issue or PR that calls the double case intended.
  • What this does not settle. The evidence shows the membership is wrong; it does not settle whether the constructor should throw. The scalar constructor's javadoc is only "Create a DoubleRange." (range/DoubleRange.java:51); only rangeonrange.DoubleRange documents the inclusive flags. Throwing follows the package's convention for empty ranges; matching nothing is a defensible alternative a maintainer may prefer (see the fixes).
The devil's-advocate check222 words

The strongest case for "intended": Lucene's documented recipe for exclusive float/double bounds is to step to the next value and accept saturation. DoublePoint.newRangeQuery says "Ranges are inclusive. For exclusive ranges, pass nextUp(lowerValue)" (core document/DoublePoint.java:210), TestPointQueries pins DoublePoint.nextUp(+Inf) == +Inf (TestPointQueries.java:2401), and on LUCENE-7092 (#8148, 2016) Robert Muir wrote "The range facets in lucene are also inclusive too" and "If its float/double use Math.nextUp/nextDown". So the facet DoubleRange could be called "consistent with core".

Why it does not hold, in our reading: in core the caller does the stepping and the helper's return value is what is pinned; these constructors instead take an exclusive flag and promise the exclusive meaning themselves, reject every other empty range, and LUCENE-5371 removed the identical saturation for longs; the LUCENE-7092 remark was about the idiom in general, not an exclusive bound that is itself an infinity. As the cross-model intended-lens review put it, "the helper's saturation being intentional does not make the resulting membership semantics intentional." A sentinel reading (+Inf = "unbounded") does not apply either: the class excludes +Inf from [x, +Inf), and "> unbounded" has no meaning. The core convention is still real evidence for a maintainer who would rather document the degenerate input as unsupported; it does not justify silently including an excluded value. Verdict: not intended, a defect.

Suggested fix

#

Recommended Reject an exclusive bound at the infinity on its own side

Reject an exclusive +Infinity min and an exclusive -Infinity max before stepping: failNoMatch() in both DoubleRange constructors, IllegalArgumentException in DimRange.fromDoubles / fromFloats, as LongRange and DimRange.fromLongs already do (3 files, +24 lines). The repro and all 307 facet tests pass with assertions on and off, and :lucene:facet:check passes.

 if (!minInclusive) {
+  if (minIn == Double.POSITIVE_INFINITY) {
+    failNoMatch(); // nothing is > +Infinity (Math.nextUp(+Infinity) == +Infinity)
+  }
   minIn = Math.nextUp(minIn);
 }
 ...
 if (!maxInclusive) {
+  if (maxIn == Double.NEGATIVE_INFINITY) {
+    failNoMatch(); // nothing is < -Infinity
+  }
   // Why no Math.nextDown?
   maxIn = Math.nextAfter(maxIn, Double.NEGATIVE_INFINITY);
All options and trade-offs3 options · 471 words

One option was built and run in a scratch worktree of 645d4fe14a20; the two alternatives are not recommended. The bug is the wrong membership; throwing is the recommended trade-off, not the only correct reaction, and a maintainer may prefer an empty range (option 2).

Reject an exclusive bound at the infinity on its own side (validated by the checks) (recommended)

#

The finder's fix, two 3-line guards per constructor or factory. range.DoubleRange and rangeonrange.DoubleRange call failNoMatch(); DimRange.fromDoubles and fromFloats throw IllegalArgumentException("Invalid min input: " + min) / ("Invalid max input: " + max), the messages fromLongs uses. Trade-offs

  • Matches LongRange, rangeonrange.LongRange, DimRange.fromLongs and the package's "a useless range throws" convention. No per-document matching or counting cost: the checks run once per range construction.
  • Behaviour change: code that today builds (+Inf, +Inf] or [-Inf, -Inf) from computed bounds gets an IllegalArgumentException instead of a (wrong) count, so a CHANGES note is appropriate.
  • The sandbox facet cutters of #13568 read DoubleRange's adjusted bounds, so they are covered too (by reading; not run).

Keep accepting the input, but make it match nothing

#

Represent the empty range explicitly (a flag, or bounds that accept() and the counters treat as empty). Not built.

Trade-offs

Avoids the behaviour change for callers that compute bounds from data, but contradicts the package convention that an empty range throws (testUselessRange), and DoubleRangeFacetCounts converts every range to an inclusive LongRange, which itself rejects min > max, so it touches more code.

Document it

#

A javadoc note that an exclusive bound at the infinity on its own side is not supported.

Trade-offs

Leaves the silent wrong result in place.

Downstream note

#

If an application uses a computed "value > threshold" drill-down as a filter and the threshold comes out as +Infinity, the filter lets the +Infinity documents through instead of matching nothing.

How it was found

#

A Z3 floating-point model of the range constructor and accept: the safety claim "accept equals the requested predicate whenever the constructor does not throw" was expected to hold, and the solver returned a counterexample at -Infinity. A second query proved the two infinity cases are the only mismatches; a public-API JUnit then confirmed it.

The method in full151 words

Method: SMT (Z3) floating-point model checking of the facet range classes, a hunt unit (facet taxonomy and ranges), over raw 64-bit patterns. Obligation O2a, "DoubleRange.accept equals the requested IEEE predicate whenever the constructor does not throw", was posed as an expected-UNSAT safety proof; the solver returned SAT with the counterexample [-Inf, -Inf), x = -Inf. Obligation O2a2 then proved (UNSAT) that the mismatch set is exactly (min = +Inf exclusive, x = +Inf) or (max = -Inf exclusive, x = -Inf). A bounded-exhaustive run over the public API (411,854 checks) found these two infinity classes as the only accept-versus-requested mismatches (its other classes belong to a separate signed-zero candidate). The finder then wrote a public-API JUnit on the stock main jars; the DimRange copy was pointed out by the cross-model refute review and the range-on-range copy came from code reading. This doc's test is a one-method form of it.

LFV-313, snapshot of 2026-11-03

Registry title
Facet DoubleRange, range-on-range DoubleRange and DimRange.fromDoubles/fromFloats do not exclude an exclusive bound that is an infinity: the empty ranges (+Inf, +Inf] and [-Inf, -Inf) are accepted and match the +Infinity / -Infinity documents instead of matching nothing
Area
facet / range, rangeonrange and facetset (exclusive-bound adjustment of double and float ranges: range.DoubleRange, rangeonrange.DoubleRange, facetset.DimRange.fromDoubles/fromFloats)
Priority
Low, rank 547: Facet double ranges with an exclusive infinite bound match the infinity documents instead of nothing, another boundary-value range row next to LFV-310.
Impact class
silent wrong results
Impact note
Applications that build a facet range whose exclusive bound is itself an infinity, 'value > +Infinity' (minInclusive=false, min=+Infinity) or 'value < -Infinity' (maxInclusive=false, max=-Infinity), for example from a threshold computed over empty data (the minimum of no values is +Infinity), get a range that should match nothing but instead counts, and through range.DoubleRange.getQuery drills down to, exactly the documents whose value is that infinity; with range-on-range INTERSECTS it matches every indexed range whose upper end is +Infinity (the documented open-ended form [x, +Inf]; the mirror case every range whose lower end is -Infinity); default IndexWriterConfig, codec and searcher, any scale, -ea and -da alike, every release since 4.4.0 (the DimRange copy since 9.3.0, the range-on-range copy since 9.5.0); the adjudication and all verifiers rate the practical impact low because only this degenerate, always-empty range shape is affected.
Summary
You build a facet range with an exclusive bound that is an infinity, for example new DoubleRange("> +Inf", Double.POSITIVE_INFINITY, false, Double.POSITIVE_INFINITY, true), meaning 'value > +Infinity', or the mirror [-Inf, -Inf) 'value < -Infinity'. No double is greater than +Infinity, so you expect a range that matches nothing, rejected with IllegalArgumentException 'matches nothing' as the class does for other empty ranges and as LongRange and DimRange.fromLongs do for an exclusive Long.MAX_VALUE bound. Instead the constructor makes the bound inclusive with Math.nextUp (or Math.nextAfter / Math.nextDown for the max), which leaves an infinity unchanged, so the range becomes [+Inf, +Inf]: DoubleRangeFacetCounts counts and the drill-down query matches every +Infinity document, and the copies in rangeonrange.DoubleRange and DimRange.fromDoubles/fromFloats count the same documents.
