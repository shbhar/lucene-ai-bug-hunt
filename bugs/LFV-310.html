DoubleRangeFacetCounts does not count -0.0 in a range that starts at an inclusive 0.0, although the range's own drill-down matches it

A facet range such as [0, 1] accepts -0.0 and its drill-down returns the -0.0 document, but DoubleRangeFacetCounts leaves that document out of the count: three documents -0.0, 0.5 and 2.0 drill down to 2 hits and count 1. Every release from 4.7.0 (2014) to 10.6.0 is affected.

The finding in 30 seconds

#

Facet range counting turns doubles into sortable longs, an order in which -0.0 sits just below 0.0. The range's own accept() and drill-down compare plain doubles, where the two zeros are equal. So at a zero bound the count and the drill-down disagree.

Background: range facets and negative zero

#
  1. DoubleRangeFacetCounts counts how many hits fall into each DoubleRange bucket; range.getQuery(...) is the drill-down that returns those hits. The two are meant to agree.
  2. Java doubles have two zeros, 0.0 and -0.0. Plain comparisons treat them as equal (-0.0 == 0.0 is true); Double.compare puts -0.0 first.
  3. NumericUtils.doubleToSortableLong turns a double into a long that sorts like Double.compare: -0.0 becomes -1 and 0.0 becomes 0.

The finding, step by step

#
  1. Index three documents whose DoubleDocValuesField holds -0.0, 0.5 and 2.0. (-0.0 is Java's negative zero; ordinary arithmetic such as Math.ceil(-0.25) produces it.)
  2. Count them with DoubleRangeFacetCounts and the bucket new DoubleRange("[0, 1]", 0.0, true, 1.0, true). You expect 2: range.accept(-0.0) is true, because -0.0 >= 0.0 in Java, and the bucket's drill-down range.getQuery(...) returns 2 hits.
  3. Instead the count is 1, with no error: the -0.0 document is in the drill-down but not in the count.
  4. Why: the counter compares sortable longs (NumericUtils.doubleToSortableLong), where -0.0 is -1 and 0.0 is 0, so -0.0 falls just below the bucket. accept() and getQuery() compare plain doubles, where -0.0 == 0.0.
  5. Same cause: the buckets "< 0" and ">= 0" count a -0.0 document in neither, and the range [+0.0, -0.0], which the constructor accepts, makes counting throw "matches nothing".

Who is affected

#

Applications that range-facet a double field with DoubleRangeFacetCounts (any constructor, single- or multi-valued) and a bucket starting at an inclusive 0.0, such as [0, x), when values can be exactly -0.0. Default codec and settings; one document suffices. Counts are only ever too low; queries and drill-downs are unaffected. Rare.

Mechanism, terms and numbers671 words

DoubleRange defines membership with plain double comparisons: accept(value) is value >= min && value <= max (range/DoubleRange.java:84-87 on main 645d4fe14a20), so -0.0 is inside [0, 1], and both getQuery(...) drill-downs match through accept(). DoubleRangeFacetCounts instead converts each range's bounds and every value with NumericUtils.doubleToSortableLong (DoubleRangeFacetCounts.java:255-270, :182, :225, :231, :273-275) and counts in that long order, where -0.0 (-1) sorts below +0.0 (0). A document whose value is -0.0 is therefore matched by an inclusive-0.0 bucket's own drill-down but not counted (and +0.0 at an inclusive -0.0 upper bound likewise); the split "< 0" + ">= 0" counts it in neither bucket; and the range [+0.0, -0.0], which the constructor's plain minIn > maxIn check accepts, makes counting throw IllegalArgumentException ... matches nothing. Counts are only ever too low and no query result changes. The divergence came with the LUCENE-5371 speed-up (8e1879225a35, first release 4.7.0); 4.6.1 counted with accept(). Every executed release through 10.6.0 and main fails. A 2-file fix that widens an inclusive zero bound in the long conversion passes the repro and the facet module's checks.

The mechanism (main 645d4fe14a20)

#
  1. Membership is a plain comparison. range/DoubleRange.java:84-87:
   /** True if this range accepts the provided value. */
   public boolean accept(double value) {
     return value >= min && value <= max;
   }

Both drill-down queries built by getQuery(...) match through it: values.advanceExact(...) && range.accept(values.doubleValue()) (:195-196) and, multi-valued, if (range.accept(values.nextValue())) return true; (:298-300).

  1. Counting is in sortable-long order. DoubleRangeFacetCounts.getLongRanges() builds new LongRange(label, doubleToSortableLong(range.min), true, doubleToSortableLong(range.max), true) (DoubleRangeFacetCounts.java:255-270), and every counting path maps each value the same way (:182, :225, :231; the field path through mapDocValue, :273-275, of the raw bits that DoubleDocValuesField stores, -0.0 included). doubleToSortableLong follows Double#compareTo (NumericUtils.java:41-42): -0.0 is -1, 0.0 is 0.
  2. Where they split. For [0, 1] the counter starts at 0, so -0.0 (-1) is outside; accept(-0.0) is true. Mirror: +0.0 (0) is outside a counter range that ends at -0.0 (-1). A Z3 model proved that without a signed zero the count and accept() never disagree on the two single-valued paths, and that on the value-source path these two are exactly the mismatches.
  3. The split-at-zero hole. An exclusive max of 0.0 is stored as Math.nextAfter(0.0, -Inf) = -Double.MIN_VALUE (DoubleRange.java:71-74), which is sortable -2. So "< 0" ends at -2, ">= 0" starts at 0, and -0.0 (-1) is in neither.
  4. The throw. The constructor checks minIn > maxIn on doubles (:76-78, and 0.0 > -0.0 is false), so it builds [+0.0, -0.0]; the converted LongRange(0, -1) fails its own check (LongRange.java:74-76) with range "..." matches nothing (Range.java:38-40) when counting starts (RangeFacetCounts.java:65-68). The counter is built lazily, only when there are hits to count, so with no hits nothing is thrown.

Exposure and likelihood242 words
  • Who can hit it. Applications that count range facets over a double with DoubleRangeFacetCounts, through any of its constructors (field, DoubleValuesSource or MultiDoubleValuesSource; single- or multi-valued), with a bucket that starts at an inclusive 0.0. That bucket shape is common: the facet demo's distance buckets are new DoubleRange("< 1 km", 0.0, true, 1.0, false) and so on. The values must include an exact -0.0, which ordinary code produces (Math.ceil(-0.25), -1 * 0.0, Double.parseDouble("-0.0")). The mirror case is +0.0 at an inclusive -0.0 upper bound.
  • What it takes. Public API; default codec, IndexWriterConfig and searcher; no opt-in setting; one document.
  • Effect. Silent wrong results: the bucket's count is one too low for each such document (for a multi-valued document, when none of its other values is in the bucket), while drilling into the bucket shows the document. FacetResult.value is too low as well when no other requested bucket counts the document. Counts are never too high, and deleted or non-hit documents are never counted. The only loud symptom is the [+0.0, -0.0] range, which throws.
  • How likely. Rare: most double fields never hold a negative zero, the randomized range-facet tests never generate one (values from random().nextDouble()), and no public report was found since 4.7.0 (2014). A code search of the default branches found no use of DoubleRangeFacetCounts in Solr, Elasticsearch or OpenSearch (not a full inventory), so the known reach is custom applications built on lucene-facet.

Why it looks unintended

#
  • The count disagrees with the range's own accept() and its drill-down getQuery(), which both match the -0.0 document.
  • Up to 4.6.1 the count called accept(); the 4.7.0 speed-up (LUCENE-5371) changed it silently, with a CHANGES entry about speed only.
  • It follows no single order: the buckets "< 0" and ">= 0" count a -0.0 document in neither.
The full argument225 words
  • Contract. min and max are "Minimum (inclusive)" and "Maximum (inclusive" (DoubleRange.java:45, :48); accept() is "True if this range accepts the provided value" (:84); each getQuery() will "Create a Query that matches documents in this range" (:324, :340). For -0.0 in [0, 1] the count of a range and its own drill-down disagree.
  • The upstream oracle. testRandomDoublesSingleValued computes expected counts with plain >= / <= ("slow but hopefully correct", TestRangeFacetCounts.java:1161-1176) and asserts that the facet count (:1222) and the drill-down count (:1232-1242) both equal it. Its values come from random().nextDouble() (:1090), so -0.0 never occurs.
  • History. Up to 4.6.1 the count loop was if (rangeFR.ranges[j].accept(v)) { counts[j]++; } (4.6.1 RangeAccumulator.java:85-89). LUCENE-5371 (8e1879225a35, 2013-12-18) replaced that loop (if (ranges[j].accept(v)) on its branch) with the sortable-long counter; its CHANGES entry says only "Speed up Lucene range faceting from O(N) per hit to O(log(N)) per hit using segment trees" (lucene/CHANGES.txt:12748-12751), and the issue (#6435, body and 5 comments) never mentions zero or sign. Executed: 4.6.1 counts -0.0 in [0, 1], 4.7.0 does not; the commit's parent is consistent and the commit is not (both built from source).
  • Not documented. No javadoc, package doc, CHANGES or MIGRATE text says that range facet counts treat the two zeros differently.
The devil's-advocate check220 words

The strongest case for "intended": NumericUtils and DoublePoint order doubles by Double.compareTo. NumericUtils defines its encoding by it, DoublePoint range queries are "consistent with Double#compareTo" (DoublePoint.java:213; LUCENE-7594 / #8645 made the points' nextUp / nextDown follow it), DoubleRange.equals uses Double.compare, and the upstream test's own DoublePoint.newRangeQuery(range.min, range.max) drill-down agrees with the counter; both getQuery() javadocs suggest PointRangeQuery as possibly faster for an indexed field; and the three classes are @lucene.experimental, which leaves maintainers room to choose. So the counter is right and accept() is the odd one out.

Why it fails as a defence of today's behaviour: the facet module's own membership API (accept(), both getQuery()s) is the plain comparison, and the facet demo drills into a counted bucket with range.getQuery; the divergence came from a performance rewrite whose release counted -0.0 one version earlier; the counts follow neither order (in the split at zero, plain order puts -0.0 in ">= 0", Double.compare order with DoublePoint.nextDown(0.0) puts it in "< 0", the counter in neither); and equals (Double.compare) and hashCode (Objects.hash) both tell the zeros apart, which is about object identity and says nothing about membership. What the defence does show is that maintainers may prefer to fix the other side. Verdict: not intended, a defect.

Suggested fix

#

Recommended Widen an inclusive zero bound in the long conversion

Widen an inclusive zero bound when converting the range to sortable longs, so both zeros are inside as they are for accept(): DoubleRange.toLongRange() maps a 0.0 min to -0.0 and a 0.0 max to +0.0, and getLongRanges() calls it (2 files, +7/-9). The repro passes, and :lucene:facet:check passes (307 tests).

  LongRange toLongRange() {
+    // accept() uses primitive comparisons (-0.0 == +0.0) but sortable longs order -0.0 < +0.0:
+    // widen a zero bound so that both zeros are inside, as they are for accept()
+    double lo = min == 0.0 ? -0.0 : min;
+    double hi = max == 0.0 ? 0.0 : max;
     return new LongRange(
         label,
-        NumericUtils.doubleToSortableLong(min),
+        NumericUtils.doubleToSortableLong(lo),
         true,
-        NumericUtils.doubleToSortableLong(max),
+        NumericUtils.doubleToSortableLong(hi),
         true);
   }

Widen an inclusive zero bound in the long conversion (validated by the checks) (recommended)

#

The finder's fix. The package-private DoubleRange.toLongRange() already does the conversion but is not called on main; it gains two lines, and DoubleRangeFacetCounts.getLongRanges() replaces its own 7-line new LongRange(...) with longRanges[i] = range.toLongRange();.

  LongRange toLongRange() {
+    // accept() uses primitive comparisons (-0.0 == +0.0) but sortable longs order -0.0 < +0.0:
+    // widen a zero bound so that both zeros are inside, as they are for accept()
+    double lo = min == 0.0 ? -0.0 : min;
+    double hi = max == 0.0 ? 0.0 : max;
     return new LongRange(
         label,
-        NumericUtils.doubleToSortableLong(min),
+        NumericUtils.doubleToSortableLong(lo),
         true,
-        NumericUtils.doubleToSortableLong(max),
+        NumericUtils.doubleToSortableLong(hi),
         true);
   }

Trade-offs

  • Restores the pre-4.7.0 counts; no query, filter or drill-down result changes; no per-document cost (the added work runs once per range, when counting starts; no benchmark was run).
  • Visible count change for buckets with a zero bound (up by the number of zeros of the other sign), so a CHANGES entry is appropriate. [+0.0, -0.0] counts both zeros instead of throwing.
  • Counts still differ from a DoublePoint range query on signed zero, by design of points.
  • The sandbox DoubleRangeFacetCutter repeats the conversion (DoubleRangeFacetCutter.java:74-86, read only) and is not covered; toLongRange() is package-private, so it would need the same two lines or a public helper.

Move membership to Double.compare order instead

#

Make accept() (and so both getQuery()s) compare with Double.compare, reject [+0.0, -0.0] in the constructor, and step exclusive bounds with signed-zero-aware helpers (like DoublePoint.nextUp / nextDown) so the split at zero stays complete. Not built.

Trade-offs

Counts stay as they are and match points; but it changes which documents existing drill-downs match (-0.0 leaves [0, x] buckets) and touches the constructor, accept() and both query classes.

Document it

#

A javadoc note that range facet counts order -0.0 below +0.0 while accept() and getQuery() do not.

Trade-offs

Leaves the miscount, the split-at-zero hole and the [+0.0, -0.0] throw in place.

Downstream note

#

A code search of the default branches found no use of DoubleRangeFacetCounts in Solr, Elasticsearch or OpenSearch (not a full inventory); an application that enforced a quota or allow/deny rule from a range facet count would undercount documents holding -0.0, while its filters still match them.

How it was found

#

A Z3 bit-precise model of how DoubleRangeFacetCounts converts ranges and values to sortable longs. A counterexample search, posed while modelling signed zeros, returned -0.0 against an inclusive +0.0 minimum; further queries proved that a zero of the other sign at a zero bound is the only mismatch. A bounded-exhaustive run and a JUnit confirmed it.

The method in full189 words

Method: SMT (Z3) bit-precise IEEE-754 modelling of the DoubleRange-to-counter pipeline, a hunt unit (facet taxonomy and ranges); tier semi-formal. Obligation O2c, "counter membership in sortable-long space equals DoubleRange.accept", was posed as an expected-SAT counterexample search and returned SAT with value -0.0 and an inclusive min of +0.0; the first logged run already contained the signed-zero refinements, so the hypothesis was formed while modelling and witnessed by the solver. O2h (UNSAT) proves that on the value-source path the mismatch happens exactly for a zero value at an inclusive bound that is the opposite-signed zero, O2e and O2f (UNSAT) that no other mismatch exists on the value-source and raw-bit field paths, and O2d (SAT) gives the [+0.0, -0.0] throw. A bounded-exhaustive public-API harness (11 special values, 34,040 range sequences, 411,854 checks over three counting paths) found only the predicted classes: these two, the throw, and two exclusive-infinity classes that belong to LFV-313. The finder then wrote a public-API JUnit on the stock main jars; the independent reproduction added the multi-valued paths and the intended-behaviour check the split at zero. This doc's test is a one-method form of the finder's.

LFV-310, snapshot of 2026-11-02

Registry title
DoubleRangeFacetCounts orders -0.0 below +0.0 while DoubleRange.accept and getQuery treat the two zeros as equal: a document holding a zero of the opposite sign at an inclusive zero bound (for example -0.0 in [0, 1]) is matched by the range's own drill-down but not counted, and the accepted range [+0.0, -0.0] makes counting throw
Area
facet / range facet counts (DoubleRange bounds and values converted to sortable longs in DoubleRangeFacetCounts, against DoubleRange.accept and getQuery)
Priority
Low, rank 524: DoubleRangeFacetCounts silently undercounts -0.0 values at an inclusive zero bound, the same signed-zero boundary class as LFV-140, which it follows.
Impact class
silent wrong results
Impact note
Applications that range-facet a double field (DoubleRangeFacetCounts over a DoubleDocValuesField, a DoubleValuesSource, a multi-valued field or a MultiDoubleValuesSource) with an inclusive bound at 0.0, such as the common [0, x] or [0, x) buckets, get a count that is silently one too low for every hit whose value is exactly -0.0 (or +0.0 at an inclusive -0.0 upper bound; a multi-valued hit only when none of its other values is in the bucket), and a FacetResult.value that is too low when no other requested range counts the hit, while the range's own accept() and getQuery() drill-down still match that document; default codec, IndexWriterConfig and searcher, no scale needed (one document suffices), every release from 4.7.0 to 10.6.0; counts are only ever too low, queries and filters are unaffected, and the louder secondary symptom (IllegalArgumentException for the range [+0.0, -0.0]) needs both bounds to be opposite-signed zeros.
Summary
You count range facets over a double field with DoubleRangeFacetCounts and a range that starts at an inclusive 0.0, such as new DoubleRange("[0, 1]", 0.0, true, 1.0, true), and some documents hold -0.0 (Java's negative zero, which ordinary arithmetic such as Math.ceil(-0.25) or -1 * 0.0 produces). You expect the count to include every document the range accepts, because DoubleRange.accept and the range's own drill-down query getQuery() compare with primitive >= and <=, treat -0.0 as equal to 0.0, and match those documents. Instead the counter converts bounds and values with NumericUtils.doubleToSortableLong, where -0.0 sorts below +0.0, so those documents are silently left out of the count (likewise +0.0 at an inclusive -0.0 upper bound), and the range [+0.0, -0.0], which the DoubleRange constructor accepts, makes DoubleRangeFacetCounts throw IllegalArgumentException 'matches nothing'.
