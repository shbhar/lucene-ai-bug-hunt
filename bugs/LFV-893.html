ValueSource#asDoubleValuesSource and #asLongValuesSource never call createWeight, so a ValueSource that keeps per-query state throws NullPointerException

asDoubleValuesSource() and asLongValuesSource() skip a ValueSource's per-query setup step, createWeight, so sources that compute something there (ttf, sttf, or your own) throw NullPointerException in FunctionScoreQuery and in sorts, on every release run from 6.4.0 to 10.6.0. One document is enough: boosting by ttf(text, test) should score 2 and throws instead.

The finding in 30 seconds

#

The adapters that let a ValueSource stand in for a DoubleValuesSource or LongValuesSource skip the source's per-query setup, so sources that need that setup fail.

Background: the two function-source APIs

#
  1. A ValueSource (the older function API, used by FunctionQuery) runs in two steps: createWeight(context, searcher) once per query, where it may compute per-query numbers and store them in a context map, then getValues(context, segment) for each segment, which reads them back.
  2. A DoubleValuesSource (the newer API, used by FunctionScoreQuery, boostByValue and sorts) has no such step: the caller calls rewrite(searcher) once, then getValues per segment. asDoubleValuesSource() and asLongValuesSource() wrap a ValueSource as one; this page calls them the bridge.
  3. ttf(field, term) (TotalTermFreqValueSource) is one number per query: how often the term occurs in the whole index. It computes that number in createWeight.

The finding, step by step

#
  1. Index one document whose text is "test test", so ttf(text, test), the term's total frequency in the index, is 2. Boost a match-all query by it: FunctionScoreQuery.boostByValue(new MatchAllDocsQuery(), ttf.asDoubleValuesSource()).
  2. You expect 1 hit with score 2: match-all scores 1, times 2. new FunctionQuery(ttf) on the same index scores 2.0.
  3. You get NullPointerException: ... "this.val$fv" is null at ValueSource.java:210, with assertions on and off.
  4. Why: a ValueSource runs in two steps, createWeight once per query (ttf counts the term there and stores the 2 in a context map), then getValues per segment, which reads it back. The bridge builds a fresh map for each segment and calls only getValues, so ttf finds nothing and returns null.
  5. The same happens for sttf, functions that contain ttf or sttf, any custom ValueSource that keeps state from createWeight, explain, and asLongValuesSource() sorts. Fields, constants, the score and maxdoc() work.

Who is affected

#

Code that passes a ValueSource keeping per-query state in createWeight through the bridge: in-tree ttf and sttf (@lucene.internal) or functions containing them, or a custom source that follows the createWeight javadoc. Default configuration, any index size, every release run since 6.4.0; the query fails loudly at its first matching document. Fields, constants, the score and maxdoc() work.

Mechanism, terms and numbers644 words

ValueSource#asDoubleValuesSource() and #asLongValuesSource() wrap a ValueSource so it can be used where Lucene expects a DoubleValuesSource or LongValuesSource, for example in FunctionScoreQuery.boostByValue, the documented replacement for the removed BoostedQuery, or in a sort. A ValueSource is used in two steps: createWeight(context, searcher) once per query, where it "can optionally store weight info in the context", then getValues(context, segment), which gets "the context that was previously passed to createWeight()". The wrappers build a fresh context for every segment and call getValues without ever calling createWeight, although their rewrite(searcher) receives the searcher that call needs. TotalTermFreqValueSource (ttf) and SumTotalTermFreqValueSource (sttf) compute their number in createWeight and return context.get(this) from getValues, so through the wrappers they return null and the search throws NullPointerException; a custom ValueSource written the way the javadoc describes finds its state missing too. One document is enough, with a default IndexWriterConfig and a plain IndexSearcher, assertions on or off. No version of the bridges has called createWeight since they appeared in 6.4.0 (2017), and every release run, 6.4.0 to 10.6.0, fails, as does main; the boostByValue form used here exists from 7.3.0, and older releases fail through a sort or new FunctionScoreQuery.

The bug

#
  1. asDoubleValuesSource() returns new WrappedDoubleValuesSource(this, null) (ValueSource.java:183-186).
  2. FunctionScoreQuery.createWeight rewrites its source with the searcher (FunctionScoreQuery.java:121); boostByValue wraps the source in MultiplicativeBoostValuesSource (:84-86), whose rewrite rewrites the bridge (:315-317). The bridge's rewrite only returns a new wrapper that holds the searcher (ValueSource.java:243-246). No createWeight.
  3. Per segment, FunctionScoreWeight.scorerSupplier calls getValues (FunctionScoreQuery.java:239). The bridge builds newContext(searcher), a fresh map that holds only "searcher" (ValueSource.java:200), adds "scorer" (:203) and calls in.getValues(context, ctx) (:205), with no in.createWeight(context, searcher) before it.
  4. TotalTermFreqValueSource.getValues is return (FunctionValues) context.get(this); (TotalTermFreqValueSource.java:59-62); only its createWeight (:65-81) sums the term's frequency over all segments and stores that entry. So the bridge's fv is null. SumTotalTermFreqValueSource is the same (:51-54, :57-74).
  5. Scoring the document goes through FunctionScoreQuery.java:244-245 and :299 and DoubleValues.java:79 to fv.doubleVal(scorer.docId) (ValueSource.java:210): NullPointerException.
  6. asLongValuesSource() has the same shape (:126-133; the NPE comes from fv.exists(doc), :144), and so has the bridge's explain (:235-240).

The native consumers do it right: FunctionQuery.FunctionWeight (FunctionQuery.java:70-71), FunctionRangeQuery (FunctionRangeQuery.java:148-149) and ValueSourceSortField.rewrite (ValueSource.java:379-382) each build one context and call createWeight(context, searcher) before any getValues.

The numbers

#
  • Minimal repro, one document "test test": expected score 2; actual NullPointerException ("this.val$fv" is null). On the same index new FunctionQuery(ttf) scores 2.0 and boostByValue over IndexReaderFunctions.totalTermFreq scores 2.0.
  • Two documents ("test test x", "test y"): ttf is 3 and sttf is 5 through FunctionQuery; through the bridge, FunctionScoreQuery with ttf, boostByValue with sttf and a sort on ttf.asLongValuesSource().getSortField(false) all throw.
  • A custom source that stores numDocs in createWeight: 2 through FunctionQuery; through FunctionScoreQuery and through an asLongValuesSource() sort its getValues sees a context its createWeight never filled (0 calls).
  • ProductFloatFunction(const 2, ttf): 6 through FunctionQuery (on the devil's advocate's 3-document index, where ttf is 3), NullPointerException through boostByValue; FunctionQuery makes 1 createWeight call, the bridge 0. searcher.explain through the bridge throws too.

Not affected, and not claimed

#
  • Stateless sources (fields, constants, arithmetic on them), the score, and statistics that need only the searcher or the top-level reader work through the bridge: maxdoc() and docfreq() read the "searcher" entry that newContext adds, and numdocs() reads the top-level reader.
  • QueryValueSource and ScaleFloatFunction do not crash, because they compute their state lazily when it is missing; that they redo the work per segment through the bridge is code reading only.
  • A custom source that silently falls back to a default when its state is missing would give wrong scores instead of an exception; that variant was not tested.
Exposure and likelihood278 words
  • Who is hit. Code that passes such a source through asDoubleValuesSource() into FunctionScoreQuery (scoring, boostByValue, explain), or through asLongValuesSource() (or asDoubleValuesSource()) into a sort. In-tree: TotalTermFreqValueSource (ttf), SumTotalTermFreqValueSource (sttf) and any function containing them. Outside the tree: any custom ValueSource that stores state in createWeight, as its javadoc describes.
  • On the documented migration path. MIGRATE.md:1377-1381 says BoostedQuery "may be replaced by calls to FunctionScoreQuery.boostByValue()". BoostedQuery called createWeight on its ValueSource; boostByValue reaches a ValueSource only through asDoubleValuesSource().
  • Default vs opt-in. A default new IndexWriterConfig() and a plain IndexSearcher; the trigger is the opt-in combination of a stateful source with the bridge. Under Lucene's test framework the codec is randomized (the gradle runs used Asserting(Lucene104)); the codec plays no part, because ttf's term lookup lives in the createWeight that is never called, so the bridge throws before ttf reads anything.
  • Scale. One document is enough. At any index size a search throws as soon as it evaluates the source for a matching document, with assertions on and off; a query that matches nothing in a segment never reaches the bridge there (FunctionScoreQuery.java:236-237; explain of a non-match returns at :177-178). The failure is loud, only that query fails, and nothing is written to the index.
  • Downstream (read, not run). Apache Solr builds ttf() and sttf() from these classes, and its boost parsers wrap the boost function with asDoubleValuesSource() through boostByValue. That end-to-end path was not run.
  • How likely. Rare: ttf and sttf are per-term constants, seldom useful as a per-document boost or sort key, custom stateful sources are uncommon, and the bug has gone unreported since 6.4.0 (2017).

Why it looks unintended

#
  • getValues gets "the context that was previously passed to createWeight()" (ValueSource.java:44), and the bridge promises to "Expose this ValueSource", unrestricted.
  • FunctionQuery, FunctionRangeQuery, getSortField and the removed BoostedQuery all call createWeight first; boostByValue, the documented replacement, takes a ValueSource only through this bridge.
  • A custom source written as the createWeight javadoc says fails through public API alone.
The full argument271 words
  • The contract. getValues "Gets the values for this reader and the context that was previously passed to createWeight()" (ValueSource.java:43-47); createWeight: sources "can optionally store weight info in the context. The context object will be passed to getValues() where this info can be retrieved" (:65-69). The bridge is itself a caller of in.getValues and breaks that precondition; its javadoc promises to "Expose this ValueSource" (:111, :183) with no restriction.
  • The bridge has what it needs. DoubleValuesSource's class javadoc tells clients to call rewrite(IndexSearcher) against the top-level searcher before getValues (DoubleValuesSource.java:34-36); FunctionScoreQuery does, and the bridge keeps the searcher. Core's DoubleValuesSource.fromQuery does its per-query setup in rewrite, building its Weight there (:776-780).
  • Every other consumer calls it: FunctionQuery.java:71, FunctionRangeQuery.java:149, ValueSource.java:381, and the removed BoostedQuery (boostVal.createWeight(fcontext,searcher);, 7.2.0 BoostedQuery.java:74). LUCENE-8099 removed BoostedQuery and MIGRATE.md:1377-1381 maps it to boostByValue(), which reaches a ValueSource only through asDoubleValuesSource(); none of the 35 comments on #9147 discusses losing the call.
  • Tests. Upstream tests call createWeight before getValues (TestValueSources.java:697-701, :935-940) and use the bridge only with sources that need no createWeight; no test asserts that the bridge skips it.
  • History. The bridges were born without the call (LUCENE-7610, 2017), and no later change says it is skipped on purpose: not LUCENE-7736 (which gave the bridge the searcher), LUCENE-8726, LUCENE-10252 or #15406. In LUCENE-5335 (#6399, 2013) Yonik Seeley gave state keyed by this as an intended use of the context: 'SumTotalTermFreqValueSource is one example of where "this" is very conveniently used as a key'.
The devil's-advocate check258 words

The strongest case for "works as designed": the DoubleValuesSource protocol has no createWeight step; ttf and sttf are @lucene.internal, and LUCENE-7736 (#8787) added IndexReaderFunctions.totalTermFreq and sumTotalTermFreq so that such statistics work in FunctionScoreQuery; the facet code the bridge replaced also skipped createWeight; QueryValueSource and ScaleFloatFunction cope with a skipped createWeight, so robust sources should too; the bridge's javadoc is one line; and open issue #16820 proposes deprecating ValueSource in Lucene 11.

Why it fails: the replacement argument covers ttf and sttf only, not a custom source that follows the createWeight javadoc and fails through public API alone; nothing limits the bridges to sources that ignore createWeight, while the getValues javadoc makes it a precondition; LUCENE-7736 put the searcher into the bridge's context, so sources that read it (such as maxdoc()) work through the bridge, and it neither added nor ruled out createWeight-dependent sources (reading it as a sign that the bridge is meant to serve them is an inference); every native consumer and the removed BoostedQuery call it; two lazy fallbacks are defensive code, not a relaxed contract; and #16820 is a proposal, while 6.4.0 to 10.6.0 are affected. No reviewer accepted the intended case: the cross-model reviews rated it weak, the devil's advocate is highly confident it is not intended, and the independent reproducer and the adjudication found the call promised by the javadoc. Verdict: not intended, a defect. Expect "use IndexReaderFunctions" and "ValueSource is being deprecated" as replies; the custom-source case and the BoostedQuery migration answer both.

Suggested fix

#

Recommended B: call createWeight once in rewrite, copy the context per segment (validated)

Call in.createWeight(context, searcher) once in the bridges' rewrite(searcher), keep that context, and give each segment its own copy in getValues and explain (+20/-11 lines in ValueSource.java). The repro then scores 2 and the queries module's 512 upstream tests run with 0 failures (5 skipped); the bridge makes one createWeight call per query, like FunctionQuery.

Trade-offs

  • One createWeight per query, like FunctionQuery. Each segment gets its own copy of the map, so getValues may add entries ("scorer", lazily built state) without writing to a shared map: the bridge itself writes the shared map only during rewrite, which avoids the one-context-shared-by-concurrent-slices problem of the native consumers for entries added in getValues. The copy is shallow: objects that createWeight stores (for example QueryValueSource's Weight) are shared across segments, as in FunctionQuery, and a source that keeps a reference to the createWeight map and writes to it later still shares it. Whether the context must be read-only after createWeight, copied deeper, or documented as holding shareable values is a maintainer decision.
  • A caller that calls getValues without rewrite behaves as today, so stateful sources still fail there. The DoubleValuesSource javadoc requires rewrite first (DoubleValuesSource.java:34-36); consumers that skip it are separate bugs with fixes in those consumers.
  • rewrite now does the per-query work (ttf and sttf loop over all segments once). Its javadoc says "Implementations should assume that this will only be called once" (DoubleValuesSource.java:94), and fromQuery already builds its Weight there (:776-780).
  • That work, and any exception a custom createWeight throws, now happens when FunctionScoreQuery.createWeight rewrites the source (FunctionScoreQuery.java:121), before it is known whether the inner query matches anything; today the bridge is reached only for segments where the inner query has a scorer (:236-239).
  • The rewritten wrapper's context holds the searcher; the rewritten wrapper held it before too (LUCENE-8726).
  • By code reading only: QueryValueSource would find its Weight in the context instead of rebuilding it once per segment. No benchmark was run.

A: call createWeight on each per-segment context (the study's sketch; validated)

#

In each of the three methods, take the rewrite-time searcher (or, if the wrapper was never rewritten, a new top-level IndexSearcher), build the context from it and call in.createWeight(context, s) before in.getValues.

IndexSearcher s = searcher != null ? searcher : new IndexSearcher(ReaderUtil.getTopLevelContext(ctx));
Map<Object, Object> context = newContext(s);
in.createWeight(context, s);

Trade-offs

  • Simplest, and also covers callers that skip rewrite; that fallback builds a new IndexSearcher per segment and deserves its own review.
  • Repeats the per-query work per segment: 2 createWeight calls for 2 segments (executed), and ttf and sttf loop over all segments inside createWeight, so O(segments^2) term lookups per query (code reading).

Downstream note

#

The failure is a loud exception for that one query; a search server whose query language puts ttf() or sttf() inside a boost, as Apache Solr's boost parsers allow (read, not run), would answer such requests with an error.

How it was found

#

A bounded-exhaustive check of the createWeight contract over the queries module: 22 composites times 8 consumer entry points (176 checks), with probe children that flag getValues on a context their createWeight never saw. Under both bridges every composite's children broke it; under the native consumers only RangeMapFloatFunction (LFV-886) and the three vector similarity functions did.

The method in full264 words

Method: semi-formal (bounded-exhaustive translation validation of a documented contract on the stock jar, then an executed public-API test).

  • A hunt unit sweeping public APIs that no earlier hunt had named (core and queries) took the ValueSource#createWeight javadoc as a contract: every consumer must call createWeight on a context before calling getValues with it, and composites must propagate it.
  • An AI finder wrote a checker that, by reflection, enumerates the 46 concrete ValueSource classes of lucene-queries, builds the 22 composites (including anonymous subclasses of the public abstract composite bases) over strict probe children, and drives each through 8 consumer entry points: 176 checks. A probe child fails when getValues receives a context its createWeight never saw.
  • Under FunctionQuery, FunctionRangeQuery and ValueSource#getSortField (4 entry points) only the children of RangeMapFloatFunction's target and default sources (the sibling bug LFV-886) and of the three vector similarity functions (which do not override createWeight) saw getValues without createWeight: 8 violations per entry point. LFV-893, snapshot of 2026-11-08

Registry title
ValueSource#asDoubleValuesSource and #asLongValuesSource never call createWeight, so a ValueSource that keeps per-query state in its context (ttf, sttf, or a user ValueSource) fails with NullPointerException through FunctionScoreQuery, its explain, or a LongValuesSource sort
Area
queries / function queries (ValueSource to DoubleValuesSource/LongValuesSource bridge: asDoubleValuesSource, asLongValuesSource)
Priority
Low, rank 633: The ValueSource bridges skip createWeight and throw a loud NPE only for stateful sources, the same missing-call shape as LFV-776, and since the bridges feed FunctionScoreQuery and sorts they rank above the narrower map() sibling LFV-886.
Impact class
crash
Impact note
Hits applications that pass a ValueSource which keeps per-query state in createWeight (in-tree only TotalTermFreqValueSource (ttf) and SumTotalTermFreqValueSource (sttf), both @lucene.internal, or a function that contains them, or any user ValueSource that follows the createWeight javadoc) through asDoubleValuesSource into FunctionScoreQuery (scoring, boostByValue, explain) or through asLongValuesSource into a sort: every such search then throws, with -ea and -da, the default IndexWriterConfig and a plain IndexSearcher, at any index size (2 documents suffice), in every release from 6.4.0 to 10.6.0 and on main; the failure is loud and only that query fails, while stateless sources and the searcher-only statistics (maxdoc(), numdocs(), docfreq()) work through the bridge [exec].
Summary
You expose a ValueSource as a DoubleValuesSource with asDoubleValuesSource() and score with it through FunctionScoreQuery (for example FunctionScoreQuery.boostByValue, the documented replacement for the removed BoostedQuery), or sort by asLongValuesSource().getSortField(), and expect the per-document values the same ValueSource gives through FunctionQuery or its own getSortField (3 for ttf(text, test) in the repro). Instead the bridge builds a fresh context in getValues and explain and calls in.getValues without ever calling in.createWeight, so ttf and sttf, which compute their statistic in createWeight and return context.get(this) from getValues, throw NullPointerException ('this.val$fv' is null at ValueSource.java:210 or :144), and a user ValueSource that stores per-query state in createWeight, as the ValueSource javadoc describes, finds its context entry missing. FunctionQuery, FunctionRangeQuery and ValueSource#getSortField all call createWeight first, and the bridge's rewrite(searcher) already holds the searcher such a call needs.
Introduced
713b65d1dcc (master) / a238610bab1 (branch_6x backport), 'LUCENE-7610: Deprecate ValueSource methods in facets module' (issue LUCENE-7610, now #8661; pre-GitHub-PR era, patch on the issue) [read: git blame -w -C -C -M of main ValueSource.java:126-134 and :198-206 attributes the method skeletons to 713b65d1dcc (the in.getValues line to the LUCENE-7723 refactor 1a278ae89be, explain :235-241 to LUCENE-7741 fb24d451cc9); exec: 6.3.0 has no such API (compile error) and 6.4.0 fails]; not a regression: the bridge has never called createWeight, and none of the 77 tagged releases 6.4.0-10.5.2 adds the call (2017-01-06 (author date of 713b65d1dcc and a238610bab1; committed 2017-01-07); first released in 6.4.0)
