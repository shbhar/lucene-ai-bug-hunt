UniformSplit postings formats fail to flush or merge a field when deltaNumLines > targetNumBlockLines / 3, a setting the constructor accepts

A UniformSplit (or SharedTermsUniformSplit) postings format built with deltaNumLines above a third of targetNumBlockLines, a setting its constructor accepts, cannot write some fields: under (4, 2), committing a field of 3 terms throws and closes the IndexWriter. The defaults (32, 3) are safe; every release since 8.3.0 is affected.

The finding in 30 seconds

#

To end a block, the writer looks back over the last 2 × delta terms for a split point. That window must start at index 1 or later: ordinary splits guarantee it, the splits at a field's end do not whenever 3 × delta > target. The constructor accepts such settings, so the flush throws.

Background

#
  1. Blocks of terms. UniformSplit writes a field's sorted terms in blocks of about targetNumBlockLines terms, give or take deltaNumLines (default 32 ± 3).
  2. Where a block ends. When a block reaches target + delta terms, the writer looks back over its last 2 × delta terms and starts the next block at the term with the shortest distinguishing prefix, which keeps the terms dictionary small.
  3. The last block. When the field's terms run out, the leftover terms go through the same split, unless there are at most target − delta of them: those are written as one block. The split repeats on whatever it leaves until no terms are left.

The finding, step by step

#
  1. You build new UniformSplitPostingsFormat(4, 2, null, null, false): blocks of 4 ± 2 terms. The constructor accepts it, because the documented rule is only 0 <= deltaNumLines < targetNumBlockLines.
  2. You add one document with the 3 values a, b, c in field f and commit. You expect one block of 3 terms, inside the promised 2 to 6.
  3. Instead the commit throws: AssertionError: blockLines size: 3 with assertions on, IndexOutOfBoundsException: Index -1 out of bounds for length 3 with them off. The IndexWriter closes and loses everything since the last commit.
  4. Why: at the end of a field the writer writes the leftover terms as one block only if there are at most 4 − 2 = 2. With 3 it looks back over the last 2 × 2 = 4 terms for a split point, starting at index 3 − 4 = −1.
  5. Every setting with 3 × delta > target can hit it: under (32, 12), any field whose end needs a split of 21 to 24 terms, either as the whole leftover or after a first split of a leftover of up to 43, in flushes and merges and for both formats. The defaults (32, 3) and formats loaded by name cannot fail.

Who is affected

#

Applications that build either format with deltaNumLines > targetNumBlockLines / 3; no such user is known. Then any flush, commit or merge can hit it, at any scale: the writer closes and uncommitted documents are lost; the last commit stays intact. Just past the boundary only 1 to 5 random fields in 400 fail, so tests can miss it.

Mechanism, terms and numbers1,241 words

UniformSplitPostingsFormat and STUniformSplitPostingsFormat (codecs module, opt-in) take targetNumBlockLines and deltaNumLines in their public constructors; the javadoc asks only 0 <= deltaNumLines < targetNumBlockLines and promises blocks of target ± delta terms, and validateSettings enforces exactly that. When the writer finishes a field, it writes the leftover terms as one block only if there are at most target − delta of them; otherwise it looks for a split point in the last 2 × delta terms, starting at index numLines − 2 × delta, and only asserts that this is at least 1. For a split of target − delta + 1 to 2 × delta terms, a range that exists exactly when 3 × delta > target, the start is 0 or negative; at a field's end such a split is either the whole leftover or what a first split of a larger leftover (up to target + delta − 1 terms) leaves. The flush, commit or merge then throws (AssertionError with assertions on; IndexOutOfBoundsException with them off, at exactly 2 × delta terms only for some terms), the IndexWriter closes through its tragic-event path and everything buffered since the last commit is lost; the last commit stays intact and passes CheckIndex. The smallest case is one document with 3 values under (4, 2). The defaults (32, 3) cannot fail. The code is unchanged since the formats were added (LUCENE-8753, 8.3.0).

The code (main 645d4fe14a20)

#
  1. Ordinary splits. BlockWriter.addLine appends one line per term and calls splitAndWriteBlock once the block holds targetNumBlockLines + deltaNumLines lines (BlockWriter.java:137-139). There the window starts at (target + delta) − 2 × delta = target − delta >= 1.
  2. The end of a field. UniformSplitTermsWriter.writeFieldTerms calls finishLastBlock after the last term ("Flush remaining terms.", UniformSplitTermsWriter.java:333-334), which loops splitAndWriteBlock while lines remain (BlockWriter.java:147-153); the leftover has 1 to target + delta − 1 lines. When the first call splits normally (deltaStart >= 1), it leaves at most 2 × delta lines, and the loop splits those again.
  3. The split. splitAndWriteBlock (BlockWriter.java:161-191) writes numLines <= target − delta as one block (:165-169); otherwise int deltaStart = numLines - deltaNumLines * 2; (:170), assert deltaStart >= 1 : "blockLines size: " + numLines; (:171), then blockLines.get(i) for i from deltaStart (:175-176), keeping the last line with the shortest prefix (<= at :178), and writes subList(0, minMdpEndIndex) (:184). A call with target − delta + 1 to 2 × delta lines has deltaStart <= 0. At a field's end it comes either directly (the leftover r has that many lines) or second: for a leftover r of 2 × delta + 1 to target + delta − 1 lines, the first call ends the block at the last shortest-prefix line k of the window and leaves r − k lines, which land in that range when k < r − (target − delta). With 3 × delta <= target every remainder is at most 2 × delta <= target − delta and is written as one block.
  4. What is thrown. Assertions on: the assert fails. Assertions off, deltaStart < 0: blockLines.get(deltaStart) throws at :176 (here Index -1). Assertions off, deltaStart == 0 (a call of exactly 2 × delta lines): the loop picks index 0 only when line 0 has the strictly shortest prefix, and then addBlockKey's blockLines.get(0) on the empty sub-list throws (BlockWriter.java:278-282); otherwise (last shortest prefix at k >= 1) the split writes a valid block of k lines, but finishLastBlock splits the remaining 2 × delta − k lines again, and that split throws (Index -k at :176) when k < 3 × delta − target, possible when 3 × delta >= target + 2, e.g. (6, 4) or (32, 12); otherwise the field is written. The fact check ran this under (6, 4) with one 8-value field: a to h commits, a, aa … ag throws Index 0, a, b, ba, bb, bc, bd, be, bf throws Index -1 out of bounds for length 7; with assertions on all three throw blockLines size: 8, and with the fix all three commit. So with assertions off the failures are a strict subset of those with assertions on: each follows a call with deltaStart <= 0.
  5. Both formats. STBlockWriter.finishLastBlock only calls super (STBlockWriter.java:86-90).
  6. Validation lets it through. validateSettings (UniformSplitTermsWriter.java:238-260), called by the constructor (UniformSplitPostingsFormat.java:105), checks only target > 0, delta >= 0, delta < target and target + delta <= 1,000.
  7. Why the writer closes. A flush failure is recorded as aborting, abort() runs and the exception is passed to IndexWriter.onTragicEvent (DocumentsWriterPerThread.java:585-589, :594-605; IndexWriter.java:453-454), the same for both exceptions; prepareCommitInternal then rolls the writer back (IndexWriter.java:3879-3883, :6098-6106). A merge failure calls tragicEvent(t, "merge") (IndexWriter.java:5109-5113).

Exposure and likelihood286 words
  • Who. Applications that build UniformSplitPostingsFormat or STUniformSplitPostingsFormat through the public 5-argument constructors, or through a subclass and the protected constructors, with deltaNumLines > targetNumBlockLines / 3. The formats are opt-in (codecs module, @lucene.experimental) and the setting is non-default. Default-constructed and SPI-loaded instances use (32, 3) and cannot fail.
  • No known user. A code search found no code that builds these formats with non-default settings (only copies of Lucene's own default-settings test), and Solr selects postings formats by SPI name, which uses the defaults. The search is not exhaustive.
  • What it costs. The flush, commit or merge throws and the IndexWriter closes; everything buffered since the last commit is lost, including other threads' documents, since it is a writer-wide rollback (this follows from the rollback; all runs were single-threaded). The committed index stays consistent and CheckIndex-clean, and in the executed checks every assertions-off flush that did not throw read back all its terms. It is not index corruption.
  • Merges stay blocked. A merge whose output field needs such a split fails again in each new writer session until the setting is changed; switching the field back to the defaults recovers (forceMerge(1) succeeds, CheckIndex clean).
  • Scale. None needed: one document with 3 values under (4, 2). With a wide window failures are frequent: about a third of fields, e.g. 143 of 400 random fields under (32, 16) with assertions off. Just past the boundary failures are rare on ordinary data. With assertions off: 1 of 400 random fields under (32, 11), 4 of 400 under (64, 22), 5 of 400 under (100, 34), 26 of 400 under (32, 12).
  • How likely: rare. Loud, and limited to a non-default setting nobody is known to use.

Why it looks unintended

#
  • The constructor accepts any 0 <= deltaNumLines < targetNumBlockLines, promises blocks of target ± delta terms and says the defaults "can be tuned".
  • Writing the failing split's terms (at most 2 × delta < target + delta) as one block keeps that promise.
  • No javadoc, test or design discussion limits delta further; the internal assert is the only trace.
The full argument309 words
  • The settings are inside the documented contract. The constructor javadoc (UniformSplitPostingsFormat.java:73-76, the same at UniformSplitTermsWriter.java:169-172): deltaNumLines "Must be greater than or equal to 0 and strictly less than {@code targetNumBlockLines}. The block size will be {@code targetNumBlockLines}+-{@code deltaNumLines}." The class javadoc: "Each block size (number of terms) is {@code targetNumBlockLines}+-{@code deltaNumLines}" (UniformSplitTermsWriter.java:48-50) and "A good sweet spot for the target block size is 32 with delta of 3 (10%) (default values). This can be tuned in the constructor." (:70-71). The range is loose at a field's end even today: the stock end-of-field split can write a block below target − delta (e.g. 24 lines for a 30-line leftover under the defaults (32, 3), BlockWriter.java:165-185); the defect is the exception on accepted settings, not the block size.
  • Validation accepts them. validateSettings (UniformSplitTermsWriter.java:238-260) checks exactly the documented rule; (4, 2), (32, 11), (32, 12) and (64, 22) pass.
  • A valid result exists. A failing split has at most 2 × delta < target + delta terms, so one block keeps the promised range, and the reader needs no block-size setting: with the fix every value reads back and CheckIndex is clean.
  • Nothing limits delta further. No javadoc, test, CHANGES.txt or MIGRATE.md entry. Upstream tests use only (32, 3) (TestUniformSplitPostingFormat.java:43-48, TestSTUniformSplitPostingFormat.java:32-37) and BlockWriter(..., 10, 2, ...) (TestBlockWriter.java:45), all with 3 × delta <= target. The design discussion (#9798, lucene-solr #633, #676, #828) never discusses delta bounds or the last block, and git log -L on the body of splitAndWriteBlock finds only the introducing commit (with its javadoc, also a reformatting); the file's other commits do not touch the method.
  • Sibling practice. BlockTree's validateSettings rejects settings its splitter cannot handle: "maxItemsInBlock must be at least 2*(minItemsInBlock-1)" (Lucene103BlockTreeTermsWriter.java:354-360). UniformSplit accepts the settings and then fails at flush.
The devil's-advocate check189 words

The strongest case: these are @lucene.experimental formats in the codecs module; the javadoc calls 10% the sweet spot and the design describes delta as an "allowed delta variation (10%)"; the assert records the author's precondition; and nobody uses such settings.

Why it fails: @lucene.experimental warns that the API may change, not that documented arguments may crash the writer. The 10% is a recommended default, never a stated limit, and the same javadoc says the defaults can be tuned. The assert is internal, invisible to users and false for every accepted setting with 3 × delta > target. Low reach bears on priority, not on whether it is a bug. If large deltas are unwanted, the fix is to reject them in validateSettings, not to fail the flush and close the writer. The reading-only GPT reviews rated the intended-behaviour case "weak"; a later cross-model fact check rated it "moderate" (experimental, opt-in, an artificial setting, a loud failure that keeps the last commit) and noted that maintainers may reasonably prefer rejecting such settings in validation. That bears on which fix to lead with, not on whether the flush should throw.

Suggested fix

#

Recommended Write the leftover as one block when the window would start below 1 (validated)

In BlockWriter.splitAndWriteBlock, when the look-back window would start below index 1 (only possible for a field's last block), write the leftover terms as one block instead of asserting (+8/−1 lines). The repro passes with assertions on and off, and so do the uniformsplit tests, the whole codecs test module (693 tests) and lint.

int deltaStart = numLines - deltaNumLines * 2;
if (deltaStart < 1) {
  // Only reachable from finishLastBlock, for the last lines of a field, when
  // 3 * deltaNumLines > targetNumBlockLines: write them as one block (numLines <= 2 *
  // deltaNumLines < targetNumBlockLines + deltaNumLines, so the block size stays in range).
  writeBlock(blockLines, dictionaryBuilder);
  blockLines.clear();
  return;
}

Write the leftover as one block when the window would start below 1 (validated) (recommended)

#

Replace the assert deltaStart >= 1 in BlockWriter.splitAndWriteBlock (BlockWriter.java:171) with a branch that writes the remaining lines as one block and returns. addLine always splits at target + delta lines, where deltaStart >= 1, so the branch is reached only from finishLastBlock, directly or on its second call, and the blocks written before it are unchanged; settings with 3 × delta <= target behave exactly as today.

int deltaStart = numLines - deltaNumLines * 2;
if (deltaStart < 1) {
  // Only reachable from finishLastBlock, for the last lines of a field, when
  // 3 * deltaNumLines > targetNumBlockLines: write them as one block (numLines <= 2 *
  // deltaNumLines < targetNumBlockLines + deltaNumLines, so the block size stays in range).
  writeBlock(blockLines, dictionaryBuilder);
  blockLines.clear();
  return;
}

Trade-offs

  • Block size. The last block then has target − delta + 1 to 2 × delta lines, inside the promised target ± delta; its split point is not chosen by the shortest-prefix rule, which affects only the dictionary key of one block per field.
  • No format change. The reader needs no setting; with the fix every value reads back (iteration and seekExact), merges succeed and CheckIndex is clean.
  • It drops the assert; the condition it guarded is now handled.

Clamp the window start to 1 (run by the study)

int deltaStart = Math.max(1, numLines - deltaNumLines * 2); and no assert.

Trade-offs

The finder's 4-case test (which includes the repro's (4, 2) 3-term case), the settings sweep (0 of 3,120 flushes fail) and the 7 upstream uniformsplit test classes pass. But, as the study's refute reviewer noted, it can write a 1-line block that is not the last block of the field (when the shortest prefix is at index 1). Reject 3 × deltaNumLines > targetNumBlockLines in validateSettings (not run)

#

Add the check to validateSettings and the constructor javadoc, like BlockTree's 2*(minItemsInBlock-1) rule.

Trade-offs

Simple and fails fast at construction. But it narrows a documented and accepted range: applications whose data happens to avoid the window today (under (32, 11) about 1 field in 400 fails) would fail at construction after an upgrade; existing indexes stay readable, because the reader does not use the settings. The minimal test would have to expect an IllegalArgumentException from the constructor instead of a successful commit.

Downstream note

#

No downstream product is known to build these formats with non-default settings; Solr loads them by name, which uses the safe defaults.

How it was found

#

While building small-block UniformSplit test fixtures, (4, 2), for a differential test of automaton term intersection, the finder hit the writer's own assertion. Code reading of the last-block split, an exhaustive sweep of all 78 accepted settings with target up to 12, and a public-API JUnit on the stock jars confirmed it.

The method in full128 words

Method: semi-formal. An assertion failure seen while building fixtures for another hunt unit (a codec differential of automaton term intersection), outside that unit's target files; then code reading of BlockWriter.splitAndWriteBlock.

  • Bounded-exhaustive sweep. All 78 settings with targetNumBlockLines <= 12 that the constructor accepts, every field size 1..40, on the stock jar: 1,164 of 3,120 flushes fail with assertions off, every one with 3 × delta > target and none otherwise; 0 with either fix sketch.
  • Widening. An independent reproducer found the merge path and that the assertions-off failures are a subset; a devil's-advocate verifier reached it from another package through production API; the follow-up measured failure rates on random data just past the boundary.
  • The minimal repro above is the smallest case: 3 terms under (4, 2).

History

#

Introduced with the formats by b963b7c3dbe (LUCENE-8753, 2019-09-06), first released in 8.3.0. Fails on every sampled release from 8.3.0 to 10.6.0 and on main; 8.2.0 and older lack the formats. Not fixed upstream.

Finding record

#

LFV-166, snapshot of 2026-11-05

Registry title
UniformSplit postings formats fail to flush or merge a field when deltaNumLines > targetNumBlockLines/3, a setting validateSettings accepts
Area
codecs / UniformSplit postings formats (BlockWriter last-block split; UniformSplit and SharedTermsUniformSplit)
Priority
Low, rank 688: A UniformSplit postings format built with deltaNumLines above targetNumBlockLines/3, which validation accepts, fails flushes and merges and closes the writer, loud and limited to a non-default setting nobody is known to use.
Impact class
crash
Impact note
Only applications that build UniformSplitPostingsFormat or STUniformSplitPostingsFormat (opt-in formats in the codecs module) with a non-default deltaNumLines > targetNumBlockLines/3, which validateSettings accepts, are hit: a flush, commit or merge that writes a field whose last block has between target-delta+1 and 2*delta lines throws (AssertionError with -ea, IndexOutOfBoundsException with -da; with -da the exact-2*delta case throws only for some term sets), the IndexWriter closes through its tragic-event path and buffered uncommitted documents are lost, while the last commit stays intact and passes CheckIndex; the defaults (32,3), SPI-loaded instances and every setting with 3*delta <= target cannot fail; no scale needed.
Summary
You build a UniformSplit (or SharedTermsUniformSplit) postings format with targetNumBlockLines=4 and deltaNumLines=2, which the constructor accepts because its documented rule is only 0 <= delta < target, and commit a field with 3 terms. You expect the commit to succeed and the blocks to hold target +- delta lines. Instead the flush throws (AssertionError 'blockLines size: 3' with assertions on, IndexOutOfBoundsException 'Index -1 out of bounds for length 3' with them off) and the IndexWriter closes, because the code that splits a field's last block assumes its look-back window of 2*delta lines starts at line 1 or later, which is false whenever 3*delta > target and the last block has between target-delta+1 and 2*delta lines.
