Geo3dShape.relate swaps WITHIN and CONTAINS for rectangles the Geo3d factory did not build

In the Geo3d spatial context, relating a shape to a plain spatial4j rectangle, such as the world bounds or a PackedQuadPrefixTree cell, swaps WITHIN and CONTAINS. A 10-degree circle claims to contain the whole world, and a PackedQuad search for a half-degree circle returns a point about 97 degrees away.

The bug in 30 seconds

#

relate() picks a helper by the other shape's class and maps its spatial3d answer with one shared switch. The Geo3d-shape helper and the rectangle helper ask the question from opposite sides, so the switch is right for one and backwards for the other.

  1. You use the Geo3d spatial context and ask how a 10-degree circle at (0, 0) relates to ctx.getWorldBounds() and to a 2x2 degree RectangleImpl at its centre.
  2. You expect WITHIN (the circle lies inside the world) and CONTAINS (the circle covers the small box). Those are the answers for the same two boxes built by ctx.getShapeFactory().rect(...).
  3. You get the reverse, CONTAINS and WITHIN. So SerializedDVStrategy IsWithin(world bounds) finds 0 of 1 indexed circles, and Contains(world bounds) finds it.
  4. PackedQuadPrefixTree cells are plain rectangles too. A quarter-world cell that contains a half-degree query circle is taken to lie inside it, so Intersects(circle(1, 1, 0.5)) matches a point at (100.3, 37.7). 20 such queries over 20,000 points return 99,972 hits; the exact answer is 3, the fixed build returns 5.
  5. Why: the rectangle helper asks spatial3d how this shape relates to the rectangle, then applies the mapping written for the opposite question. No error. A regression since 7.1.0 (2017); 7.0.1 answers correctly.

Who is affected

#

Users of the opt-in Geo3d spatial context who also use PackedQuadPrefixTree (wrong cells for small and medium circles and polygons), run SerializedDVStrategy IsWithin or Contains with the world bounds or a hand-built rectangle, or call relate() with one. The common setup (geohash, quad or S2 trees, factory or WKT shapes, Intersects) was not shown to be affected.

Mechanism, terms and numbers760 words

In the opt-in Geo3d spatial context (Geo3dSpatialContextFactory, @lucene.experimental), relating a Geo3d shape to a spatial4j Rectangle that is not itself a Geo3d shape returns WITHIN where the answer is CONTAINS and CONTAINS where it is WITHIN; DISJOINT and INTERSECTS are right. A 10-degree circle at (0, 0) is CONTAINS ctx.getWorldBounds() and WITHIN a 2x2 degree RectangleImpl at its centre, while the same boxes built by the Geo3d shape factory give WITHIN and CONTAINS. Geo3dShape.relate(Shape) maps the answers of two helpers with one switch, but the two helpers ask spatial3d the question from opposite sides. Lucene builds such rectangles itself (the Geo3d context's world bounds, every PackedQuadPrefixTree cell), so SerializedDVStrategy IsWithin / Contains queries with the world bounds return the opposite set (and CompositeSpatialStrategy IsWithin misses), and RecursivePrefixTreeStrategy over PackedQuadPrefixTree returns documents far outside small query circles and polygons. Nothing throws. It came in with LUCENE-7951 in 7.1.0 (2017) and fails on every release tested since and on main.

Terms

#
  • Spatial context: spatial4j's SpatialContext decides how shapes are built and related. Geo3dSpatialContextFactory (opt-in, @lucene.experimental) makes one whose shapes wrap spatial3d (Geo3d) shapes in Geo3dShape.
  • a.relate(b): how a relates to b: WITHIN (a lies inside b), CONTAINS (a covers b), INTERSECTS or DISJOINT. SpatialOperation.IsWithin and Contains test indexedShape.relate(queryShape) for WITHIN and CONTAINS (SpatialOperation.java:84, 134).
  • Plain rectangle: a spatial4j RectangleImpl, not built by the Geo3d shape factory. The Geo3d context's ctx.getWorldBounds() is one, and so is every PackedQuadPrefixTree cell (PackedQuadPrefixTree.java:400). ctx.getShapeFactory().rect(...) and WKT envelopes build a Geo3dRectangleShape instead, which is a Geo3dShape.

The bug

#
  1. Geo3dShape.relate(Shape) (Geo3dShape.java:54-75) sends a Geo3dShape argument to one helper (:58), any other Rectangle to a second (:59) and a Point to a third (:60), then maps the helper's spatial3d GeoArea constant with one switch (:66-74): GeoArea.CONTAINS -> WITHIN for non-points, GeoArea.WITHIN -> CONTAINS.
  2. spatial3d's contract (GeoArea.java:34-38, 46-50): CONTAINS = "The referenced shape CONTAINS this area"; getRelationship(shape)'s "return value is how the GeoShape relates to the GeoArea, not the other way around".
  3. The Geo3d-shape helper returns shape.getRelationship(s.shape) (:77-79): the area is this shape and the answer describes the other one. "The other contains this" means "this is WITHIN the other", so the switch is right.
  4. The rectangle helper builds a GeoArea from the rectangle and returns geoArea.getRelationship(shape) (:81-92): the area is the rectangle and the answer already describes this shape. The same switch turns it around: WITHIN and CONTAINS come back swapped.
  5. For a shape that is neither a point nor a rectangle, spatial4j's RectangleImpl.relate(shape) returns shape.relate(this).transpose() (spatial4j 0.8), so rectangle.relate(circle) is swapped too.

What it does to queries

#
  • Exact predicates. SerializedDVStrategy checks IsWithin / Contains for every document, so with ctx.getWorldBounds() or a hand-built rectangle as the query shape it returns the opposite set. CompositeSpatialStrategy checks them only for the candidates of an RPT query: its IsWithin(world bounds) matched 0 of 3 documents, while its Contains(world bounds) gave the correct 0, because it narrows Contains with an RPT Contains query first (CompositeSpatialStrategy.java:139-142).
  • PackedQuad prefix tree. When indexing, a cell reported WITHIN the shape becomes a leaf (PackedQuadPrefixTree.java:476-483); when querying, IntersectsPrefixTreeQuery collects every document under a cell reported WITHIN the query shape (IntersectsPrefixTreeQuery.java:71-73). A quarter-world cell that really contains a small circle or polygon is reported WITHIN it, so a 1-degree circle document is indexed as that one quarter-world cell instead of 351 cells, and a half-degree query circle matches every point in its quarter of the world. Rectangles from the Geo3d factory or WKT are not affected: spatial4j relates a cell to any Rectangle with its own rectangle code (a factory rectangle query of the same extent gave 0 false hits).
  • Not affected, as tested. Geohash and quad trees build their cells with the Geo3d factory, so RPT over them in the Geo3d context is right (the geohash control gives 0 false hits). No effect was shown for S2 trees or heatmaps, whose world cell and default input shape are ctx.getWorldBounds().

Why it is a bug, not intended

#
  • The same box gives CONTAINS from the Geo3d factory and WITHIN as a RectangleImpl; point sampling agrees with the factory.
  • Both contracts allow only a weaker answer (INTERSECTS, OVERLAPS) in place of WITHIN or CONTAINS, never the opposite one.
  • Before 7.1.0 the same call was mapped the right way: the same test sources pass on 7.0.1 and fail on 7.1.0.
The full argument289 words
  • Self-contradiction. For a 10-degree circle at (0, 0), the boxes (-1..1, -1..1), (-30..30, -30..30) and the world give CONTAINS, WITHIN, WITHIN from the Geo3d factory and WITHIN, CONTAINS, CONTAINS as RectangleImpl, on SPHERE and WGS84; disjoint and crossing boxes agree. The factory path agrees with exact point membership (0 contradictions in 10,000 random pairs).
  • Contracts. spatial4j Shape.relate: "Describe the relationship between the two objects. For example: this is WITHIN other, this CONTAINS other ...", with INTERSECTS the only allowed approximation of WITHIN or CONTAINS. GeoArea.getRelationship (GeoArea.java:46-60): the "return value is how the GeoShape relates to the GeoArea, not the other way around"; OVERLAPS may replace WITHIN "if the shape intersects with the area at even a single point" and CONTAINS only for a shape made of several overlapping subshapes; the opposite nested answer is "not permissible". IsWithin and Contains are documented as OGC CoveredBy and Covers (SpatialOperation.java:75, 124).
  • History. Before LUCENE-7951 (035523ba7a8), relate(Rectangle) made the same geoArea.getRelationship(shape) call and mapped WITHIN to WITHIN and CONTAINS to CONTAINS. The commit added the Geo3d-shape helper and one shared mapping written for it, and in the same change moved the rect-relation tests to the Geo3d context, whose rectangles take the other branch.
  • On purpose. On lucene-solr#246 the author wrote "I have added the possibility to relate no geo3d rectangles. I was trying to avoid that but I see that for the time being it is necessary.", and on #9000 noted that the Geo3d world bounds are a spatial4j RectangleImpl.
  • Tests. No spatial-extras test relates a Geo3d shape to a RectangleImpl or the world bounds, and TestGeo3dRpt uses only geohash, quad and S2 grids. No test, CHANGES entry or discussion accepts the swapped answer.
The devil's-advocate check138 words

The strongest case for "intended" (an intended-behaviour checker): every class involved is @lucene.experimental; the Geo3d context is meant to produce only Geo3d shapes, so a RectangleImpl is foreign input; getWorldBounds() is documented only as the coordinate extent, so it could be read as metadata rather than a query shape; and both contracts allow approximate answers.

Why it fails: experimental status covers API changes, not reversed answers; Lucene creates these rectangles itself (PackedQuad cells, the world bounds, the S2 world cell, the heatmap default input), and the rectangle branch was added for them; getWorldBounds() is a public, non-deprecated Rectangle that Lucene's heatmap code uses as a shape; both approximation clauses allow only a weaker answer, never the opposite nested one. Verdict: not intended, a defect (the adjudication and independent checks; the cross-model reviewer rated the intended-behaviour argument weak).

Suggested fix

#

Recommended A: transpose the answer in relate(Rectangle)

In relate(Rectangle), transpose spatial3d's answer (CONTAINS to WITHIN, WITHIN to CONTAINS) into the direction the shared mapping expects, as before 7.1.0: +8/-1 in Geo3dShape.java. The repros, the spatial-extras module checks and the differential family that found the bug pass. PackedQuad indexes built with the bug keep the wrong cells until reindexed (code reading).

    // geoArea.getRelationship(shape) says how this shape relates to the rectangle; the caller
    // expects how the rectangle relates to this shape (as relate(Geo3dShape) returns): transpose.
    final int relationship = geoArea.getRelationship(shape);
    return switch (relationship) {
      case GeoArea.CONTAINS -> GeoArea.WITHIN;
      case GeoArea.WITHIN -> GeoArea.CONTAINS;
      default -> relationship;
    };
All options and trade-offs3 options · 630 words

Two options were built and validated in a scratch worktree at a9779ef3c193 with gradle (JDK 25) and with the standalone runner against this page's test, the finder's, the independent reproducer's and the devil's advocate's repros and differential family G1 (patched class shadowed). They gave the same answer on 40,000 random shape and box pairs; that is a sample, not a proof, since the two directions of getRelationship may legitimately differ where the contract allows OVERLAPS. Either needs a regression test; this page's test is one.

A: transpose the answer in relate(Rectangle) (validated by the checks) (recommended)

#

Keep the spatial3d computation of 7.0 and earlier (GeoBBox.getRelationship(shape)) and swap CONTAINS and WITHIN before the shared mapping, so both helpers hand it an answer about the other shape. The finder's fix, with the comment shortened to fit the line limit.

    // geoArea.getRelationship(shape) says how this shape relates to the rectangle; the caller
    // expects how the rectangle relates to this shape (as relate(Geo3dShape) returns): transpose.
    final int relationship = geoArea.getRelationship(shape);
    return switch (relationship) {
      case GeoArea.CONTAINS -> GeoArea.WITHIN;
      case GeoArea.WITHIN -> GeoArea.CONTAINS;
      default -> relationship;
    };

Trade-offs

  • Smallest change; restores the 7.0 answers exactly (a 7.1.0 port makes the history tests pass there).
  • Leaves two helpers that ask from opposite sides, so the class still needs the comment to stay right.
  • Indexes built on Geo3d plus PackedQuad while the bug was present keep their over-coarse cells until reindexed (code reading, not run): worth a CHANGES or MIGRATE line.

B: ask from the same side as the Geo3d-shape helper (validated by the checks)

#

Build a GeoBBox from the rectangle and return shape.getRelationship(bbox), the computation a Geo3dRectangleShape already gets, so the same box gives the same answer in both forms by construction. +5/-5 (GeoAreaFactory.makeGeoArea with four bounds is GeoBBoxFactory.makeGeoBBox anyway, so its import goes).

    GeoBBox bbox =
        GeoBBoxFactory.makeGeoBBox(
            shape.getPlanetModel(),
            r.getMaxY() * DistanceUtils.DEGREES_TO_RADIANS,
            r.getMinY() * DistanceUtils.DEGREES_TO_RADIANS,
            r.getMinX() * DistanceUtils.DEGREES_TO_RADIANS,
            r.getMaxX() * DistanceUtils.DEGREES_TO_RADIANS);

    return shape.getRelationship(bbox);

Trade-offs

  • Removes the second direction from the class; plain rectangles use the path the existing rect-relation tests cover.
  • Switches plain rectangles from GeoBBox.getRelationship(shape) to shape.getRelationship(bbox). Both gave the same answer on all 40,000 random pairs of a comparison probe (circles and convex polygons, SPHERE and WGS84), but that is a sample, not a proof; B would want broader testing (degenerate and composite shapes) before it is called equivalent.
  • The same reindex note as A.

What the checks validated

  • Gradle, the same worktree and test: :lucene:spatial-extras:check passes: 27 suites, 121 tests, 5 skipped, 0 failures, and the format, ecjLint and forbiddenApis checks.
  • Standalone, fix shadowed: the same repros all pass (4/4, 3/3, 4/4, 1/1, 2/2); family G1 of the differential harness gives 0 contradictions.

C: give each helper its own mapping (not built)

#

Let each helper return a SpatialRelation, as before 7.1.0, instead of sharing one switch.

Trade-offs

Larger diff, same behaviour as A; makes the direction explicit per branch.

Downstream note

#

An application that used an IsWithin or PackedQuad Intersects result as a region boundary, for example for visibility, would include documents far outside the region; other filter clauses and deletions still apply.

How it was found

#

Randomized differential testing of the spatial4j bridge: a harness checked each relate() answer against exact spatial3d membership of 2,000 sampled points. With a Geo3d shape as the argument 0 of 10,000 pairs contradicted; with the world bounds 999 of 1,000 and with plain rectangles 179 of 2,863, every one a WITHIN or CONTAINS answer.

The method in full157 words

Method: randomized differential and model-based testing (non-formal; the finder tagged it semi-formal), in a hunt unit on the spatial4j bridge to spatial3d.

  • The harness Geo3dBridgeDiff (family G1) generated random and boundary shapes on SPHERE and WGS84 (seed 5EED220) and required that A.relate(B) never contradict exact spatial3d membership of 2,000 sampled points per pair. B was a Geo3d shape, the same box as a plain RectangleImpl, or ctx.getWorldBounds().
  • On stock main: 0 contradictions on the Geo3d-shape path, 999 of 1,000 against the world bounds and 179 of 2,863 against plain rectangles, all WITHIN or CONTAINS; 0 with the fix. Re-run for this doc with the same numbers.
  • Reading Geo3dShape.relate gave the cause. The swap had been noted earlier, untriaged, as a side lead in the verification of a different spatial3d bug.
  • Verifiers widened the reach: an independent reproducer found the PackedQuad false positive, and the devil's advocate showed the flip with rectangles that Lucene itself creates.

spatial-extras / spatial4j bridge to spatial3d (Geo3dShape.relate(Rectangle) and its shared GeoArea-to-SpatialRelation mapping), reached through SpatialOperation IsWithin/Contains on SerializedDVStrategy and CompositeSpatialStrategy, RecursivePrefixTreeStrategy cell traversal over PackedQuadPrefixTree, and any spatial4j relate() against ctx.getWorldBounds()
Priority
Medium, rank 178: Geo3dShape.relate silently swaps WITHIN and CONTAINS, but it needs the opt-in Geo3d context plus a second uncommon choice such as PackedQuadPrefixTree, so it follows the broader buffered-line row LFV-678.
Impact class
silent wrong results
Impact note
Applications that use the opt-in, @lucene.experimental Geo3d spatial context (Geo3dSpatialContextFactory), or that wrap spatial3d shapes in Geo3dShape inside the standard spatial4j geo context as code written before 7.1 did, get WITHIN and CONTAINS swapped with no error whenever a Geo3d shape is related to a spatial4j rectangle that the Geo3d shape factory did not build: with RecursivePrefixTreeStrategy over the non-default PackedQuadPrefixTree small and medium circle and polygon queries and documents are affected, not rectangles from the Geo3d factory or WKT (20 random half-degree circle queries over 20,000 points returned 99,972 hits where the exact answer is 3), SerializedDVStrategy IsWithin/Contains queries with ctx.getWorldBounds() or a hand-built rectangle return the opposite set (CompositeSpatialStrategy IsWithin matched 0 of 3; its Contains gave the correct 0), and direct relate() calls are wrong; the common setup (the Geo3d context with the default geohash tree, or quad or S2, WKT- or factory-built shapes, the Intersects predicate) was not shown to be affected, DISJOINT and INTERSECTS answers are correct, nothing throws, ordinary scale, every release tested from 7.1.0 to 10.5.2.
Summary
You use the Geo3d spatial context and relate a Geo3d shape to a spatial4j rectangle that the Geo3d shape factory did not build, for example a 10-degree circle against the context's own ctx.getWorldBounds(), or run a SerializedDVStrategy IsWithin(ctx.getWorldBounds()) query over that circle, and expect WITHIN (the circle lies inside the world) and one hit. Instead relate() returns CONTAINS and the query matches nothing, while Contains(world bounds) matches the circle: Geo3dShape.relate(Rectangle) asks spatial3d how this shape relates to the rectangle but then applies the mapping written for the opposite question (how the other shape relates to this one), so the two nested answers come out swapped, whereas the same box built by the Geo3d factory relates correctly. Lucene builds such rectangles itself, so RecursivePrefixTreeStrategy over PackedQuadPrefixTree, whose cells are plain spatial4j rectangles, treats a cell that contains a small query circle as lying inside the circle and returns every document in that cell, for example a point at (100.3, 37.7) for a half-degree circle at (1, 1).
