JapaneseTokenizer and KoreanTokenizer keep emoji and other punctuation outside the BMP despite discardPunctuation

With the default discardPunctuation=true, kuromoji's JapaneseTokenizer and nori's KoreanTokenizer drop 、 and ★ but keep 𐄀 (U+10100) and emoji such as 😀 as tokens, because the punctuation test reads only the first UTF-16 half of a character outside the BMP. Affected since 3.6.0 (kuromoji) and 7.4.0 (nori).

The bug in 30 seconds

#

With discardPunctuation=true both tokenizers should drop every punctuation or symbol token. They do for characters inside the BMP, but not for the same kinds of characters above U+FFFF, such as emoji.

  1. You tokenize 日本 、 日本 and 日本 𐄀 日本 with JapaneseTokenizer, or 한국 ★ 한국 and 한국 😀 한국 with KoreanTokenizer(); discardPunctuation=true is the default. 、 (U+3001) and 𐄀 (U+10100) are both Unicode punctuation (Po); ★ (U+2605) and 😀 (U+1F600) are both symbols (So).
  2. Both tokenizers drop a token whose character is punctuation or a symbol by Unicode category. You expect [日本, 日本] and [한국, 한국] for all four inputs.
  3. Instead only the BMP characters are dropped: you get [日本, 𐄀, 日本] and [한국, 😀, 한국]. Java stores 𐄀 and 😀 as two 16-bit halves, and the test checks only the first half, a surrogate, which is in no punctuation category.
  4. Measured on main, 10.5.2 and 9.12.3: kuromoji keeps 24 of 24 supplementary cases (three modes, with and without n-best), nori 8 of 8, and every BMP control is dropped. The default KoreanAnalyzer indexes 😀 as a term; the default JapaneseAnalyzer drops it later but leaves a position gap (+2 instead of +1). No error.

Who is affected

#

Users of JapaneseTokenizer or KoreanTokenizer with the default discardPunctuation=true, every mode: bare tokenizers, factory chains without a part-of-speech stop filter and the default KoreanAnalyzer keep emoji and other supplementary symbols as terms; the default JapaneseAnalyzer shows only a position gap. In the tested inputs, one extra token per character, no error.

Mechanism, terms and numbers608 words

Kuromoji's JapaneseTokenizer and nori's KoreanTokenizer drop punctuation and symbol tokens when discardPunctuation=true, the default of the two KoreanTokenizer constructors without the flag (KoreanTokenizer.java:92-94, :104-110), both tokenizer factories, KoreanAnalyzer and JapaneseAnalyzer (every JapaneseTokenizer constructor takes the flag explicitly). They decide with a private isPunctuation(char) that switches on Character.getType(char) over Unicode categories such as Po, So and Sm, and they pass it the token's first UTF-16 char. For a character above U+FFFF that char is a high surrogate, whose type is SURROGATE, so emoji such as U+1F600 and punctuation such as U+10100 (Po) stay in the output as tokens, while BMP characters of the same category (U+2605 So, U+3001 Po) are dropped. Every kuromoji mode, the n-best output and nori's default path (outputUnknownUnigrams=false) are affected; the default KoreanAnalyzer indexes the character as a term, the default JapaneseAnalyzer removes it later with its part-of-speech stop filter and leaves a position increment of 2. Present since kuromoji's first release (3.6.0, 2012) and nori's (7.4.0, 2018); testing the code point in the discard tests and stepping the unknown-word grouping by code point fixes it.

Terms

#
  • Supplementary character, surrogate pair: Java strings are UTF-16. Characters above U+FFFF, the BMP's end, take two chars: a high surrogate (U+D800-U+DBFF) and a low surrogate (U+DC00-U+DFFF). Most emoji (😀 is U+1F600), many historic scripts' punctuation (𐄀 U+10100) and math alphanumerics (𝛁 U+1D6C1) are supplementary. Character.getType(char) of either half is SURROGATE; Character.getType(int) of the code point gives its real category.
  • discardPunctuation: "true if punctuation tokens should be dropped from the output" (the javadoc of both tokenizers). Default true.
  • Unknown word: when the dictionary has no entry, both tokenizers group the following chars of the same character class (kuromoji) or script (nori) into one word, split where "is punctuation" changes.

The bug

#
  1. The predicate isPunctuation(char ch) (ja/ViterbiNBest.java:705-727; nori's copy ko/Viterbi.java:416-446) returns true for Zs, Zl, Zp, Cc, Cf, Pd, Ps, Pe, Pc, Po, Sm, Sc, Sk, So, Pi and Pf. SURROGATE is not in the list.
  2. The discard sites pass the token's first UTF-16 char: kuromoji's backtrace !isPunctuation(fragment[offset]) (:465), n-best registerNode !isPunctuation(fragment[left]) (:639) and EXTENDED-mode unigrams !isPunctuation(fragment[offset + i]) (:448); nori's shouldFilterToken, isPunctuation(token.getSurfaceForm()[token.getOffset()]) (:412-414).
  3. The EXTENDED loop just above (:440-445) deliberately steps back over a surrogate pair so the unigram is the whole emoji, then classifies only its high half.
  4. Grouping has the same blind spot (ja/ViterbiNBest.java:122-150, ko/Viterbi.java:79-127): every surrogate half is "not punctuation", so 😀𠮷 (emoji + Extension B letter) becomes one word, where ★吉 splits and drops ★.
  5. Scope: nori's default path, outputUnknownUnigrams=false, where the symbol's token goes through shouldFilterToken (ko/Viterbi.java:248-250). With outputUnknownUnigrams=true the unigram branch (:214-236) adds unknown-word unigrams without calling shouldFilterToken at all, so it keeps unknown-word punctuation from either plane; that is a separate bug with its own cause, not this one.

Exposure and likelihood327 words
  • Who is exposed. JapaneseTokenizer in NORMAL, SEARCH and EXTENDED mode and with n-best output, and japanese factory chains without the part-of-speech stop filter: the character becomes a token. KoreanTokenizer(), the korean factory with defaults and the default KoreanAnalyzer: the character becomes a token tagged SY, which is not a default stop tag, and is indexed: in an in-memory index, a TermQuery for 😀 finds the 한국 😀 한국 document (executed). (The factories by code: they build the same tokenizers with the same default.) KoreanTokenizer and KoreanAnalyzer are @lucene.experimental.
  • The default JapaneseAnalyzer hides it. The kept token is tagged 記号-一般 (symbol, general), a default stop tag, so the stop filter removes it; it keeps the position, so 日本😀日本 gives increments +1, +2 where 日本★日本 gives +1, +1.
  • What changes for the user. Emoji and other supplementary symbols become searchable terms while ★, ♥ or ∇ in the same text do not; positions after such a character shift, so an exact phrase across it stops matching: the phrase "日本 日本" with JapaneseAnalyzer and "한국 한국" with KoreanAnalyzer match the ★ and 、 texts but not the 😀 or 𐄀 texts, and all of them match with the fix (executed; proximity queries were not run). Supplementary punctuation proper (Po, used in historic and minority scripts) is kept, which the javadoc rules out word for word.
  • How likely. Emoji are common in user-written Japanese and Korean text, and each one is kept every time; supplementary Po characters are rare in CJK text. The visible harm per character is small, and nobody reported it since 2012.
  • Scale (the repeated-input probe). 1,200,000 chars of 😀 give 400,000 tokens through either tokenizer, one per emoji, where ★ gives 0. No hang, no cost amplification beyond ordinary text, every term well-formed UTF-16. This covers the tested default paths, not user dictionaries, non-default nori modes or mixed supplementary text: next to a supplementary letter the emoji stays inside that word (😀𠮷).

Why it is a bug, not intended

#
  • The javadoc: "true if punctuation tokens should be dropped from the output", with no BMP limit; U+10100 and U+1E95E are Unicode punctuation (Po).
  • The EXTENDED-mode loop deliberately steps over a surrogate pair, then tests only its first half.
  • ★ (So) and ∇ (Sm) are dropped, the same categories above U+FFFF kept; nothing exempts them.
The full argument224 words
  • The contract. JapaneseTokenizer.java:109, KoreanTokenizer.java:119 and KoreanTokenizerFactory.java:61: "true if punctuation tokens should be dropped from the output". A grep of both modules for supplementary, surrogate and BMP finds no restriction. For U+10100 and U+1E95E (Po) the sentence applies word for word; for emoji (So) and math symbols (Sm) it rests on the implementation's own category list, under which ★ and ∇ are dropped.
  • Maintainers state the behaviour upstream: "Punctuations are removed by default" (#10020) and "The tokenizer removes punctuations so it's expected that some characters are filtered ..." (#9739).
  • The same code handles surrogate pairs on purpose. The EXTENDED unigram loop steps over the pair (it descends from 685035575b3, 2012, "LUCENE-3305: don't split surrogates in extended mode (unless the input is already screwed, GIGO)"), and kuromoji's testSurrogates2 is a "random test ensuring we don't ever split supplementaries". Classifying only the high half right after stepping over the pair reads as an oversight.
  • No exemption anywhere. No javadoc, comment, test, CHANGES or MIGRATE entry or upstream discussion exempts supplementary characters; the modules' only supplementary test characters are Extension B letters (Lo), which the predicate does not touch.
  • Precedents. Lucene fixed char-wise handling of supplementary characters as bugs elsewhere: LUCENE-8325 (smartcn) and #15899 / #15900 (TruncateTokenFilter), both under Bug Fixes in CHANGES. Earlier, CharTokenizer moved to code points as a 3.1 new feature (LUCENE-2183).
The devil's-advocate check161 words

The strongest case (the intended-behaviour checker and the cross-model reviewer): both tokenizers inherit MeCab-style character tables (a 65,536-entry CharacterDefinition; MeCab's char.def has no supplementary ranges), so supplementary characters are simply not modelled; emoji may be worth keeping (StandardTokenizer and ICUTokenizer emit <EMOJI> tokens: LUCENE-8527 and LUCENE-8125); KoreanTokenizer is @lucene.experimental; JapaneseTokenizerFactory calls the flag an "Expert option" in a code comment; in #10430 maintainers leaned towards a token filter instead of this flag.

Why it fails: the discard test is Lucene's own Unicode-category predicate, not a char.def feature, and Java gives the category per code point; the module handles surrogate pairs deliberately elsewhere; neither "experimental" nor "Expert option" documents an input restriction, and the flag defaults to true wherever it has a default (both analyzers, both factories, the two KoreanTokenizer constructors without the flag). Whether emoji should be kept decides the fix direction, not whether the same category treated differently by plane is a defect. Verdict: not intended, a defect.

Suggested fix

#

Recommended Classify by code point in the discard tests and the unknown-word grouping, with a cap guard

Test the code point, not the first char, at the discard sites (kuromoji's three, nori's shouldFilterToken), step the unknown-word grouping loops by code point, and add a guard so a surrogate pair never crosses the 1,024-char cap. The repro passes, and so do the whole kuromoji (198 tests) and nori (89 tests) test tasks, assertions on and off.

// discard tests (kuromoji :448, :465, :639; nori shouldFilterToken): the code point, not the first char
!isPunctuation(Character.codePointAt(fragment, offset, offset + length))
private static boolean isPunctuation(int ch) { switch (Character.getType(ch)) { ... } }

// unknown-word loops (kuromoji processUnknownWord, nori processUnknownWord): step by code point
final int len = codePointLenAt(posAhead);
if (unknownWordLength + len > MAX_UNKNOWN_WORD_LENGTH) {
  break; // the cap would split a surrogate pair: end the word before it
}
if (... && isPunctuation(codePointAt(posAhead)) == isPunct) {
  unknownWordLength += len;
  posAhead += len;
}

Trade-offs

  • Behaviour change by design. Supplementary punctuation and symbols are now dropped, as their BMP analogues are, so emoji stop being searchable through these tokenizers with the default flag; existing indexes need a reindex to be consistent. Keeping emoji would then need discardPunctuation=false, which keeps all punctuation. Worth a CHANGES or MIGRATE note.
  • Unknown-word scan by code point. The loop steps by code point and tests punctuation (nori: also script and digit) on the code point, so it splits an unknown word where a supplementary symbol meets a supplementary letter (😀𠮷 -> [𠮷]), and nori now uses the real script and digit property of a supplementary character instead of UNKNOWN / not-a-digit for its high half. That matches the BMP. It does not make all of the grouping code-point based: the character-class and group lookups in the 65,536-entry CharacterDefinition still read one UTF-16 char, as on stock code. Beyond the module tests and the probes, mixed supplementary text was not surveyed.
  • The guard keeps the 1,024-char cap strict when the loop steps by two chars, so a pair is never split at the cap (without it the word could reach 1,025 chars). It covers the coupled cap-split bug in these loops too; one guard is enough if both are fixed. That bug's EXTENDED-mode test expects the emoji kept as a token with discardPunctuation=true and fails with this fix; it would need discardPunctuation=false or a supplementary letter.
  • The patch keeps the hunt's helper style (codePointLenAt, codePointAt); a PR could fold them into one codePointAt plus Character.charCount. The extra buffer reads per char were not measured.

Downstream note

#

Search servers that expose these tokenizers with the default discard setting inherit the behaviour: an emoji or other supplementary symbol in a document or query becomes a searchable term, where a BMP symbol of the same category is dropped.

How it was found

#

Semi-formal. A scan of the main jars' bytecode for calls of char-only Character methods, which cannot see characters above U+FFFF, flagged both isPunctuation(char) sites. A metamorphic probe then checked that word X word tokenizes the same whether X, of a given Unicode category, is in the BMP or not. It does not.

The method in full140 words
  • Scan. The hunt unit on supplementary-plane handling scanned the class files of the main jars for calls of the char overloads of Character (such as Character.getType(C)), which classify one UTF-16 char and so cannot see a supplementary character. It listed ja.ViterbiNBest.isPunctuation and ko.Viterbi.isPunctuation, among others.
  • Metamorphic probe. LFV-749, snapshot of 2026-10-29

Registry title
JapaneseTokenizer and KoreanTokenizer with discardPunctuation=true (the default) keep punctuation and symbols outside the BMP (U+10100, U+1E95E, emoji such as U+1F600) as tokens, because isPunctuation classifies a single UTF-16 unit (the high surrogate), while BMP characters of the same general category are dropped (released since 3.6.0 and 7.4.0)
Area
analysis / kuromoji and nori Viterbi tokenizers, discardPunctuation (ja.ViterbiNBest.isPunctuation and its three discard sites, ko.Viterbi.shouldFilterToken)
Priority
Low, rank 428: The default kuromoji and nori tokenizers keep supplementary-plane punctuation and emoji as tokens, costing only an extra term and a position shift that JapaneseAnalyzer hides.
Impact class
silent wrong results
Impact note
Hits every user of JapaneseTokenizer or KoreanTokenizer with the default discardPunctuation=true (constructors, factories and the default KoreanAnalyzer; every Mode and the n-best output; any scale; -ea and -da) whose text holds a supplementary-plane punctuation or symbol character, in practice mostly an emoji: the character comes out as an extra token (Korean POS SY, which the default KoreanPartOfSpeechStopFilter keeps), so it becomes a searchable term and shifts later positions by one, while BMP characters of the same Unicode category (U+3001, U+2605, U+2207) are dropped; with the default JapaneseAnalyzer the token is removed later by its part-of-speech stop filter (POS 記号-一般), and only a position increment of 2 instead of 1 remains; nothing throws and no other token changes.
Summary
You tokenize '日本 😀 日本' or '한국 𐄀 한국' (U+1F600, U+10100) with JapaneseTokenizer or KoreanTokenizer and discardPunctuation=true, the default, and expect [日本, 日本] and [한국, 한국], because the javadoc says punctuation tokens are dropped and both tokenizers drop every BMP character of the same Unicode general category (Po U+3001, So U+2605, Sm U+2207). Instead the supplementary character is kept as a token ([日本, 😀, 日本], [한국, 𐄀, 한국]): isPunctuation(char) calls Character.getType on the high surrogate alone, whose type is SURROGATE, so the discard test at the token start never sees the real category. No error is raised; the default KoreanAnalyzer indexes the extra token, and the default JapaneseAnalyzer removes it only later, through its part-of-speech stop filter, which leaves a position gap.
