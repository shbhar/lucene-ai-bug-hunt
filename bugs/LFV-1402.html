A throwing OneMerge.mergeFinished for a merge aborted before it starts its work leaves the merge "running", so rollback() and deleteAll() hang

If a merge policy's OneMerge.mergeFinished throws for a merge that rollback() aborted before the merge began its real work, IndexWriter never crosses that merge off its list of running merges, and rollback() waits for it until its thread is interrupted. deleteAll() hangs the same way, in releases since 8.6.0.

The finding in 30 seconds

#

One failing callback in a merge's cleanup leaves IndexWriter believing the merge is still running, so rollback() and deleteAll() wait for it until their thread is interrupted. It needs an abort that lands after the scheduler took the merge and before the merge began its real work.

Background: how IndexWriter tracks a running merge

#
  1. The merge scheduler takes a merge from IndexWriter (getNextMerge()), which puts it in a set, runningMerges. rollback() and deleteAll() mark every running merge aborted, then wait until that set is empty.
  2. When a merge ends without success, IndexWriter.merge's finally closes the merge, which calls the merge policy's public OneMerge.mergeFinished callback (declared throws IOException), and then calls mergeFinish, which removes it from runningMerges (for these merges nothing else does; addIndexes(CodecReader...) merges have their own remover).
  3. If the merge failed or was aborted during its real work (mergeMiddle), mergeMiddle has already closed it, so the finally only removes it.

The finding, step by step

#
  1. Flush 2 one-document segments. The merge policy returns 1 OneMerge over both, whose mergeFinished throws IOException. Call maybeMerge(): the scheduler takes the merge, and the writer's list of running merges now holds 1 merge.
  2. Before the merge begins its real work, another thread calls rollback(). It marks the merge aborted and waits until the list of running merges is empty.
  3. The merge sees the abort and stops. Its cleanup first closes the merge, which calls mergeFinished, and only then crosses it off the list. mergeFinished throws, so the crossing-off is skipped. maybeMerge() reports the IOException, as expected.
  4. You expect rollback() to close the writer; with the fix the test passes in 0.1 s. Instead the list stays at 1 merge, and rollback() re-checks it once a second until its thread is interrupted. The test gives up after 10 s.
  5. The latch in the test only makes the timing deterministic: with the default ConcurrentMergeScheduler, maybeMerge() followed at once by rollback() hung in 40 of 40 runs, and 0 of 40 without the throw. A second, test-framework-based probe hung 0 of 30, so the rate depends on timing and environment.

Who is affected

#

Applications whose merge policy returns its own OneMerge (directly or through OneMergeWrappingMergePolicy) with a mergeFinished that can fail; no in-tree policy does. Then rollback() and deleteAll() block until their thread is interrupted. No scale is needed: one default-scheduler probe hit the window 40 of 40 times, another 0 of 30. The last commit is untouched.

Mechanism, terms and numbers663 words

When a merge ends without success, IndexWriter.merge's outer finally first calls closeMergeReaders(merge, true, false) and then mergeFinish(merge), with no nested finally. closeMergeReaders closes the merge through OneMerge.close, which runs the merge policy's public mergeFinished(boolean, boolean) callback, declared throws IOException, and lets its exception through; for a merge from the merge policy, mergeFinish is the only code that removes it from runningMerges. On most failure paths mergeMiddle has already closed the merge, so this finally only removes it. But when rollback() or deleteAll() aborts a merge after the scheduler has taken it and before mergeMiddle's first abort check, this finally is the first to close it: a throwing callback skips mergeFinish, the merge stays in runningMerges, and abortMerges waits for that set to drain until its thread is interrupted. The code's own comment warns of exactly this hang. It needs a merge policy whose OneMerge.mergeFinished can fail, which no in-tree policy has; once that holds, the default ConcurrentMergeScheduler hit the window in 40 of 40 runs of one probe (0 of 30 in a second one). A nested try/finally fixes it.

Why other failure paths are fine

#

A failure or abort inside mergeMiddle's try closes the merge in mergeMiddle's own finally. The outer closeMergeReaders then sees hasFinished() and skips the callback (:5396), so mergeFinish runs. In the fault-injection probe, its two "abort inside mergeMiddle" cells with a throwing callback did not hang on main, 10.6.0, 9.0.0 and 8.11.4 (on the 9.x and 8.11.4 jars the deleteAll() cell threw AlreadyClosedException instead of returning). These two cells do not control where the abort lands: rollback() or deleteAll() starts on a new thread as soon as the merge is registered, with the stock ConcurrentMergeScheduler, so the abort can also land before mergeMiddle. On 9.12.3 the rollback() cell hung in abortMerges too. The cells that force the abort before mergeMiddle hang on all five versions. By code reading (not run), the lines of mergeMiddle before its try (:5467-5481, e.g. the scheduler's wrapForMerge at :5470) are outside it as well, so a failure there would also reach the outer finally with the merge not yet closed.

The deleteAll route

#

deleteAll() aborts running merges through the same abortMerges() (:2771). The fault-injection probe hung it the same way on main, 10.6.0, 9.12.3, 9.0.0 and 8.11.4, and it returned with the fix. It is not part of the repro.

What else stays stuck (by code reading)

#

rollback() waits inside synchronized (commitLock) (:2589) and never reaches the release of the write lock (:2684). Interrupting the waiting thread ends it with ThreadInterruptedException (:5868-5869), as the test does.

Exposure and likelihood319 words
  • Who is hit. A merge policy whose OneMerge subclass does work in mergeFinished that can fail. The pattern exists: Lucene's own TestDemoParallelLeafReader has a mergeFinished that rethrows decRef failures (TestDemoParallelLeafReader.java:654-669), and during LUCENE-8962 an in-tree mergeFinished threw IllegalStateException after a failed merge (#10005, a comment of 2020-03-04; fixed in the override). Downstream, elastic/elasticsearch#164591 (an open proof of concept) forwards mergeFinished in that project's OneMerge wrappers.
  • Opt-in. The default mergeFinished is empty (MergePolicy.java:282); the only non-test override in core, the merge-on-commit wrapper (IndexWriter.java:3968-4028), delegates to the wrapped merge's callback.
  • The window can be hit without test hooks once the callback throws. rollback() holds the writer's monitor while it sets the abort, and the merge thread needs that monitor in _mergeInit (IndexWriter.java:5271) before it reaches mergeMiddle (by code reading). A probe (not the repro) with the stock ConcurrentMergeScheduler, maybeMerge() then rollback() at once on one thread, hung 40 of 40 runs on main with assertions off, 20 of 20 with assertions on and 20 of 20 on 10.6.0; 0 of 40 without the throw, 0 of 20 with the fix. A second, test-framework-based probe hung 0 of 30, so the rate depends on timing and environment.
  • With the default scheduler the callback's exception shows only as an uncaught MergePolicy.MergeException on the merge thread, and rollback() hangs.
  • Scale. None: 2 one-document segments, 1 merge; assertions on or off.
  • Not affected. Search, and the last commit on disk: rollback() is stuck before it deletes anything (by code reading).
  • Sibling. LFV-1339 is the same callback and the same missing finally at another site (AddIndexesMergeSource.merge, the addIndexes(CodecReader...) path). LFV-1339's page notes this site with a route that needs two failures; here one failing callback suffices after an abort. LFV-1339's fix leaves this bug's tests failing, and this fix leaves LFV-1339's hang (the fault-injection probe's addIndexes cell) in place, so they are two fix sites.

Why it looks unintended

#
  • mergeFinished is public and declared throws IOException; its javadoc sets no limit on throwing.
  • The code's own comment says mergeFinish must run first, "else we hang waiting for our merge thread to be removed from runningMerges" (IndexWriter.java:5109-5110).
  • rollback() is documented to close the writer without committing; nothing documents a permanent wait.
The full argument145 words
  • Contract. mergeFinished (MergePolicy.java:276-282): "Called by IndexWriter after the merge is done and all readers have been closed", declared throws IOException. OneMerge.close already wraps the callback in try/finally so the readers are released anyway (:292-298).
  • The invariant is written down. The comment at IndexWriter.java:5109-5110 came with LUCENE-6579 (926397824e9); mergeInit likewise calls mergeFinish in its own catch (:5260-5267), and the merge-on-commit cleanup in preparePointInTimeMerge already guards the same pair: try { abortOneMerge(merge); } finally { mergeFinish(merge); } (:4099-4103). rollback(): "Close the IndexWriter without committing any changes" (:2566-2574).
  • History. The closeMergeReaders call ahead of mergeFinish came with LUCENE-8962 so that every failed or aborted merge gets closed and its callback runs. Its review (apache/lucene-solr#1617) never discusses a throwing callback in this caller. No javadoc, test, CHANGES or MIGRATE entry says mergeFinished must not throw.
The devil's-advocate check149 words

The strongest case, made by an executed cross-model review (an independent reviewer from another model family, OpenAI GPT-5.6): MergePolicy and OneMerge are @lucene.experimental (MergePolicy.java:69, :189), the trigger needs an application callback that fails, and the repro forces the abort window.

Why it fails: the annotation is about API stability, not a license to hang; the method is declared to throw IOException; Lucene's own test override rethrows; and the window is reached without test hooks once a callback throws (40 of 40 runs in one default-scheduler probe, 0 of 30 in a second probe). The reviewer rated the argument moderate in its refutation review and weak in its intended-behaviour review, and the bug real in both. It limits reach (hence Low), not validity. One qualification: no javadoc promises recovery after every exception from a custom callback, so "not intended" is a conclusion from the contracts above.

Suggested fix

#

Recommended A. Nested try/finally in IndexWriter.merge's finally (recommended; validated)

In IndexWriter.merge's finally, wrap the closeMergeReaders(..) call in try { .. } finally { mergeFinish(merge); }, so the merge always leaves the running set; the callback's exception is neither caught nor replaced. Validated through gradle: the repro passes with assertions on and off, and 12 closest suites pass (271 tests, 0 failures).

        synchronized (this) {
          // Readers are already closed in commitMerge if we didn't hit
          // an exc:
          try {
            if (success == false) {
              closeMergeReaders(merge, true, false);
            }
          } finally {
            mergeFinish(merge);
          }
All options and trade-offs3 options · 381 words

Not run: the full upstream suite. Open draft PR #16846 moves this finally into a new finishMerge method with the same body; if it lands first, the same change applies there. LFV-1339 needs the same hardening at AddIndexesMergeSource.merge; this fix alone does not fix LFV-1339, and LFV-1339's fix alone does not fix this one (both executed). Scope: A fixes this one finally. Other close-then-unregister sequences without a nested finally exist, e.g. the pending-merge loop in abortMerges (abortOneMerge(merge); mergeFinish(merge);, IndexWriter.java:2825-2834); they were not analysed here.

A. Nested try/finally in IndexWriter.merge's finally (recommended; validated)

#

At IndexWriter.java:5090-5093, the if (success == false) closeMergeReaders(merge, true, false); moves into a try whose finally calls mergeFinish(merge). 1 file, 6 insertions, 3 deletions.

        synchronized (this) {
          // Readers are already closed in commitMerge if we didn't hit
          // an exc:
          try {
            if (success == false) {
              closeMergeReaders(merge, true, false);
            }
          } finally {
            mergeFinish(merge);
          }

Trade-offs

  • Behaviour kept. The exception still reaches the same place (the maybeMerge() caller with a serial scheduler, the merge thread with ConcurrentMergeScheduler) and still triggers the existing tragicEvent. Only the bookkeeping becomes exception-safe, as the comment at :5109-5110 already demands.
  • Small and local. One finally, no API change.

B. Suppress the callback's exception in closeMergeReaders when suppressExceptions is true (not validated)

#

Catch the callback's exception there and record it, for example as suppressed on the merge's error.

Trade-offs

Hides an application failure that today reaches the caller; A is smaller and keeps behaviour.

C. Document that mergeFinished must not throw (not recommended)

#

Say in the javadoc that a OneMerge must not throw from mergeFinished.

Trade-offs

Contradicts the throws IOException signature and still leaves a writer whose rollback() can hang.

Downstream note

#

Products whose own merge policies do fallible work in OneMerge.mergeFinished can get a writer whose rollback() does not return until its thread is interrupted; with the default ConcurrentMergeScheduler the only sign is an uncaught merge-thread exception.

How it was found

#

Fault injection: a probe crossed where an abort or a failure lands in a merge's life with whether mergeFinished throws. The cells that force the abort after checkout and before mergeMiddle hung with a throwing callback, for rollback() and for deleteAll(), on every version run. A deterministic JUnit test then reproduced it.

The method in full148 words

The site was first noted, by code reading only and without a test, in the audit of the sibling LFV-1339. The probe's six cells: an I/O failure inside the merge (the writer closes, no hang), rollback() or deleteAll() aborting a merge inside mergeMiddle (no hang on main, 10.6.0, 9.0.0 and 8.11.4; on 9.12.3 the rollback() cell hung too, because these two cells do not control where the abort lands), rollback() or deleteAll() aborting a merge forced after checkout and before mergeMiddle (both hang, only when mergeFinished throws, on main, 10.6.0, 9.12.3, 9.0.0 and 8.11.4), and a control for LFV-1339's addIndexes(CodecReader...) route. Each cell ran with and without the throw; every no-throw control returned. The code reading behind it: on that one path, IndexWriter.merge's finally is the first to close the merge, and the close and the removal sit in the same block without a nested finally.

Impact note
Hits applications whose merge policy returns its own OneMerge (directly or as a OneMergeWrappingMergePolicy wrapper) with a mergeFinished(boolean, boolean) override that can throw (the method is public and declared throws IOException), when rollback() or deleteAll() aborts a merge that the scheduler has already checked out but that has not yet reached mergeMiddle: the hook's exception is reported on the merge thread, and then rollback() (or deleteAll()) waits forever in abortMerges until a thread interrupt ends it; executed with the stock SerialMergeScheduler and ConcurrentMergeScheduler, -ea and -da alike, no scale, every release from 8.6.0 through 10.6.0 and main; no in-tree OneMerge throws there, and the index is not damaged.
Summary
You give IndexWriter a merge policy that returns its own OneMerge whose mergeFinished(boolean, boolean) override throws an IOException (the method is public and declared to throw it), let a merge start, and call rollback() before the merge thread reaches mergeMiddle. You expect rollback() to close the writer without committing, as documented, after the merge thread has reported the hook's exception. Instead IndexWriter.merge's finally calls closeMergeReaders, which runs mergeFinished, before mergeFinish(merge) with no nested finally, so the merge is never removed from runningMerges and rollback() waits forever in abortMerges; deleteAll() hangs the same way.
