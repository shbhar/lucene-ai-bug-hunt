FunctionRangeQuery over ValueSource.fromDoubleValuesSource compares in float, so double and long ranges silently gain or lose hits near a bound

FunctionRangeQuery over ValueSource.fromDoubleValuesSource(...) compares in float, not double: over epoch milliseconds time <= 1700000000000 also returns an event one minute later, and an exact-id filter on 1000000000 matches 65 ids, with no error. LongFieldSource, DoubleFieldSource and FunctionMatchQuery are exact; affected since 7.0.0.

The bug in 30 seconds

#

ValueSource.fromDoubleValuesSource wraps a DoubleValuesSource for the function-query API. Its values keep the exact double, but it does not override getRangeScorer, the range test FunctionRangeQuery uses, so it inherits the generic one that compares in float.

  1. You store event times as epoch milliseconds in a long doc-values field time: t − 1 ms, t and t + 60,000 ms (one minute later), with t = 1,700,000,000,000. You wrap it for the function-query API: ValueSource.fromDoubleValuesSource(DoubleValuesSource.fromLongField("time")).
  2. You filter time <= t with new FunctionRangeQuery(source, null, t, true, true) and expect the first two events, which is what LongFieldSource("time") and FunctionMatchQuery return.
  3. Instead all three match, with no error. The bridged values inherit the generic range test of FunctionValues: it parses the bound with Float.parseFloat and compares each value cast to float. Floats near 1.7e12 are 131,072 apart, so every value from t − 26,623 ms to t + 104,447 ms counts as equal to t.
  4. The same happens wherever two numbers share a float: [1000000000 TO 1000000000] over ids matches the 65 ids 999,999,968 to 1,000,000,032; [1.0 TO 1.0] over a double field also matches 0.9999999999999999 and 1.0000000000000002; [* TO 1e300] matches 1e301, because 1e300 becomes Infinity.

Who is affected

#

Code that range-filters a DoubleValuesSource through ValueSource.fromDoubleValuesSource with FunctionRangeQuery (experimental): doc-values fields, LongValuesSource.toDoubleValuesSource(), or compiled expressions, whose only route to a ValueSource is this bridge. Long ids above 2^24 and epoch timestamps hit it with ordinary values; doubles only right next to a bound or beyond the float range. No Lucene production code calls the bridge.

Mechanism, terms and numbers620 words

ValueSource.fromDoubleValuesSource(DoubleValuesSource) adapts a DoubleValuesSource (a double or long doc-values field, LongValuesSource.toDoubleValuesSource(), a compiled expression) to the function-query ValueSource API. Its FunctionValues keeps the exact double in doubleVal but does not override getRangeScorer, so it inherits the generic default, which parses both bounds with Float.parseFloat and compares each value cast to float. FunctionRangeQuery, the only production caller of getRangeScorer, therefore range-filters the bridged source in float: any value that rounds to the same float as a bound counts as equal to it, and a bound or value too large for a float becomes infinite. Over epoch milliseconds [* TO 1700000000000] also returns an event one minute later (the window runs from t − 26,623 ms to t + 104,447 ms); [1000000000 TO 1000000000] matches 65 ids; [1.0 TO 1.0] matches 0.9999999999999999 and 1.0000000000000002; [* TO 1e300] matches 1e301. No error is raised. The same field through DoubleFieldSource / LongFieldSource, or FunctionMatchQuery over the same DoubleValuesSource, returns the exact hits. The bridge came in LUCENE-7737 (7.0.0) without a range override; it is affected from 7.0.0 on (executed on 11 versions up to main). Building the bridged values on DoubleDocValues, as the typed double sources do, fixes it (+3/−9 lines in ValueSource.java).

Terms

#
  • The bridge: ValueSource.fromDoubleValuesSource(in) (ValueSource.java:267-272). It unwraps a source that came from ValueSource.asDoubleValuesSource() (since #15406, 10.4.0) and otherwise returns new FromDoubleValuesSource(in). It has no javadoc.
  • FunctionRangeQuery: keeps its Number bounds as strings ("declared as strings because FunctionValues.getRangeScorer takes String args and parses them", FunctionRangeQuery.java:48-49) and asks the source's FunctionValues for a range scorer (:170-172), the only production caller of getRangeScorer.
  • The float default: FunctionValues.getRangeScorer (FunctionValues.java:224-293). Typed values override it: DoubleDocValues compares doubles (DoubleDocValues.java:86-147), LongDocValues longs (LongDocValues.java:90-125).

The bug

#
  1. FromDoubleValuesSource.getValues returns new FunctionValues() {...} (ValueSource.java:302) with floatVal = (float) inner.doubleValue() (:308-314), doubleVal = the exact inner.doubleValue() (:316-322) and exists = inner.advanceExact(doc) (:324-327), and no getRangeScorer.
  2. So FunctionRangeQuery gets the default, which parses the bounds with Float.parseFloat (FunctionValues.java:245, :250) and compares floatVal(doc) (:261, :270, :279, :288) after exists(doc).
  3. "1700000000000" becomes the float 1,700,000,038,912; t − 1, t and t + 60,000 all cast to that float, so <= holds for all three. "1.0E300" becomes Infinity, and (float) 1e301 is Infinity too.
  4. DoubleFieldSource and LongFieldSource return typed values with their own range test, and FunctionMatchQuery applies its predicate to the exact double: over the same data they return the exact hits.

Exposure and likelihood368 words
  • Who. Code that combines FunctionRangeQuery (or its own getRangeScorer call) with ValueSource.fromDoubleValuesSource(...) of a DoubleValuesSource that did not start as a ValueSource: DoubleValuesSource.fromDoubleField/fromLongField, LongValuesSource.toDoubleValuesSource(), an expressions-module source. For expressions this is the only route into the ValueSource API since 7.0.0; up to 6.3, Expression.getValueSource returned values with an exact double range test (executed on 6.3.0), which LUCENE-7609 removed in 6.4.0.
  • When. Deterministically, and only next to a bound: a value that differs from a bound but rounds to the same float counts as equal to it, so an inclusive bound admits it from just outside the range and an exclusive bound drops it from just inside; a value on the correct side of an inclusive bound is still judged right. The window is one float step wide (2^-24 to 2^-23 of the magnitude) around the bound's float: ±32 around 1e9; about 131 s around any epoch-ms bound from 2004 to 2039, placed differently per bound (t − 26,623 to t + 104,447 ms for t = 1.7e12). Numbers too large for a float (from about 3.4028236e38) become ±Infinity, so a bound and a value beyond it can compare equal; at exact float midpoints a value equal to a bound can round apart from it. Rare for ordinary doubles; ordinary for id- and timestamp-scale longs (65 ids match a point query near 1e9; at t = 1.7e12 a "published before t" cut-off admits items up to 104 s late).
  • What goes wrong. A wrong hit set with no error: extra hits for inclusive bounds, missing hits for exclusive bounds, both at exact float midpoints. Query-time only; the index is not touched.
  • Default vs opt-in. Default IndexWriterConfig, codec and searcher; the trigger is the API pair. No Lucene production code calls fromDoubleValuesSource, and FunctionRangeQuery is @lucene.experimental (FunctionRangeQuery.java:42). Since 10.4.0 (#15406) a typed ValueSource converted to a DoubleValuesSource and back is unwrapped and exact.
  • Size of the check. A bounded-exhaustive sweep of about 30 range, exact and set query paths against an exact reference (983,164 double, 268,692 int and 483,557 long checks) found this path as the only one with unexplained mismatches on double, int and long fields (5,997, 606 and 1,528).

Why it is a bug, not intended

#
  • Over the same data, DoubleFieldSource, LongFieldSource and FunctionMatchQuery return the exact hits; only the bridge differs.
  • The bridge's own doubleVal is exact; the typed double, long and int values override the float default, whose comment says ranges need "different behavior depending on the type of fields".
  • Nothing in Lucene documents or tests float matching for the bridge.
The full argument242 words
  • Two public paths over the same data disagree. FunctionRangeQuery over DoubleFieldSource("d") and FunctionMatchQuery(DoubleValuesSource.fromDoubleField("d"), v -> v >= 1.0 && v <= 1.0) return {1.0}; over fromDoubleValuesSource(DoubleValuesSource.fromDoubleField("d")) the same range returns three documents.
  • The values are doubles. doubleVal is exact (ValueSource.java:316-322) and floatVal is a narrowing of it (:308-314). The comment above the default says a range "needs different behavior depending on the type of fields" (FunctionValues.java:228-229); the ValueFiller javadoc asks implementations to define their own "if their value is not a float" (:137-140).
  • The typed double, long and int values override it. DoubleDocValues, LongDocValues and IntDocValues define their own getRangeScorer, as do DocTermsIndexDocValues (over term ordinals) and EnumFieldSource's values; FloatDocValues (whose values are floats), BoolDocValues and StrDocValues keep the float default. LUCENE-5247 ("expressions should use DoubleDocValues not FunctionValues directly", 9db7442d648, 2013, by rmuir) moved the typed range scorers into Int/Long/DoubleDocValues; its motivation was an UnsupportedOperationException, so it is the pattern, not a precision decision.
  • Nothing in Lucene documents float semantics for the bridge. fromDoubleValuesSource has no javadoc; FunctionRangeQuery "matches docs in which the values in the value source match a configured range" (FunctionRangeQuery.java:32-33); upstream tests use the bridge only for scores, sorting and the round trip; no CHANGES or MIGRATE entry mentions range precision. Downstream reliance on today's float matching cannot be ruled out. The bridge is maintained API: #14654 and #15406 (2025) fixed other methods.
The devil's-advocate check239 words

The strongest works-as-designed case (built by the intended-behaviour devil's advocate and a review by a model from another family, OpenAI GPT-5.6): FunctionValues is float-centric by heritage (the default parses floats, objectVal "by default return[s] a Float()", FunctionRangeQuery says "The score is the float value" and is @lucene.experimental); the adapter began in the LUCENE-7737 patch as a Solr-side helper that wrapped spatial distance sources for sorting and scoring, and that discussion called ValueSource "being phased out (or moved to Solr)"; no Lucene production code calls the bridge; FunctionMatchQuery is the modern exact alternative; and SOLR-6562 (2014, resolved Invalid) called float precision in Solr's sum/sub function math working as designed.

Why it fails: float scores do not imply float filtering; the bridged value is an exact double and only the range test narrows it (in SOLR-6562 the values themselves were computed in float); the typed double and long sources compare in their own type; nothing in Lucene documents the float behaviour; and results such as [* TO 1e300] matching 1e301, or an inclusive point query missing the document with exactly that value, are not "values between the specified range". A maintainer may still answer "use FunctionMatchQuery", or prefer the narrow fix B or a documented limitation; the reply is that this public adapter silently returns wrong hits and the fix is small and leaves the range test's per-document cost unchanged. Lead the issue with the cross-path comparison.

Return a DoubleDocValues from FromDoubleValuesSource.getValues (validated by the checks) (recommended)

#

ValueSource.java only (+3/−9): import DoubleDocValues, replace new FunctionValues() with new DoubleDocValues(this) and drop the hand-written floatVal, which DoubleDocValues derives as (float) doubleVal. The range test is then DoubleDocValues.getRangeScorer (Double.parseDouble, doubleVal), as for DoubleFieldSource and, since LUCENE-5247, expressions.

Trade-offs

  • Scores, explain, toString(doc) and exists do not change (floatVal stays (float) doubleVal, 0 when missing); the range test does the same work per document as today (exists, then one value read).
  • Float bounds over a float-valued source change (also with B): FunctionRangeQuery keeps 0.3f as "0.3", so over a FloatDocValuesField holding 0.3f, bridged with DoubleValuesSource.fromFloatField, [* TO 0.3f] and [0.3f TO 0.3f] match it today (as FloatFieldSource does) and not with the fix: the value is (double) 0.3f = 0.30000001192092896 > Double.parseDouble("0.3") (executed). FloatFieldSource stays the float-exact path. Name it in CHANGES.
  • The other projections change from the FunctionValues defaults to DoubleDocValues: objectVal returns a Double (null when missing) instead of a Float; getValueFiller fills a MutableValueDouble with exists; byteVal, shortVal, intVal and longVal return casts, strVal returns Double.toString(doubleVal) and boolVal doubleVal != 0, where today they throw UnsupportedOperationException; bytesVal, which calls strVal, starts working; the values become an instanceof DoubleDocValues. A downstream that prints objectVal can see it.
  • Cost: objectVal and the ValueFiller now call exists and doubleVal (advanceExact twice for a document with a value) where today they call floatVal once.
  • Unchanged (read): documents without a value and NaN values never match; a missing exclusive bound still excludes an infinite value.
  • ValueSource.java starts importing from queries.function.docvalues, which already imports from queries.function.

Make the FunctionValues default compare doubles (not recommended)

#

Change FunctionValues.getRangeScorer itself.

Trade-offs

FunctionValues.doubleVal throws UnsupportedOperationException by default (FunctionValues.java:60-62), so every float-only implementation that relies on the default would break.

Downstream note

#

By code reading only, Solr's {!frange} reaches this path for configured expression functions, geodist() on spatial-strategy fields and a few other wrappers. As a scale comparison, the geodist() float window (±0.24 mm at 5 km) is far smaller than LatLonPoint's 4.66 mm latitude step, so expressions over date or large-id fields look like the realistic case.

How it was found

#

A bounded-exhaustive cross-path check ran about 30 range, exact and set query paths over every bound combination of a type-limit value alphabet on the real jars, against an exact reference. The bridged FunctionRangeQuery was the only unexplained mismatch class on double, int and long fields; a Z3 floating-point model then characterised the window.

The method in full189 words

Method: bounded-exhaustive cross-path translation validation on the stock jars (semi-formal tier), in a hunt unit on range-bound handling across query paths.

  • The harness built every (lower, upper, includeLower, includeUpper) over a type-limit value alphabet, ran each through about 30 range, exact and set query paths and compared each hit set with an exact Java reference: 983,164 double, 268,692 int and 483,557 long checks; the float sweep (729,052 checks) had no unexplained class.
  • The bridged path was added to the sweep after code reading showed that FromDoubleValuesSource has no range override. It left 5,997 double, 606 int and 1,528 long mismatches; every other mismatch was attributed to a registered or documented class.
  • A Z3 floating-point model characterised when the float and double tests disagree. Its one assumption, parseFloat(Double.toString(b)) == (float) b, fails at exact float midpoints, which the independent reproducer then executed in both directions.
  • The class was reduced to a public-API JUnit (found 2026-10-26 on main ea57360912ed), then checked by an independent reproducer, an intended-behaviour devil's advocate, reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history and prior-report follow-up and a credibility audit.

FunctionRangeQuery over ValueSource.fromDoubleValuesSource(...) compares bounds and values as floats, not doubles, so double and long ranges silently gain or lose hits near a bound and beyond Float.MAX_VALUE
Area
queries / function queries (the ValueSource.fromDoubleValuesSource bridge: its FunctionValues inherits the float default FunctionValues.getRangeScorer that FunctionRangeQuery calls)
Priority
Medium, rank 224: FunctionRangeQuery over a bridged DoubleValuesSource compares in float and so silently adds or drops hits on ordinary id-scale and timestamp-scale longs, but the API pair is rare with no in-tree caller, so it closes the narrow deterministic silent rows just above the loud LFV-100.
Impact class
silent wrong results
Impact note
Applications that filter with lucene/queries FunctionRangeQuery (or another FunctionValues.getRangeScorer caller) over ValueSource.fromDoubleValuesSource(...) of a DoubleValuesSource that did not start as a ValueSource (a double or long doc-values field via DoubleValuesSource.fromDoubleField/fromLongField, LongValuesSource.toDoubleValuesSource, or an expressions-module source, the only ValueSource route for expressions since 7.0) get wrong hit sets with no error for values that differ from a bound but round to the same float (a relative window of about 2^-24: about 64 ids near 1e9, about -27 s to +104 s near today's epoch milliseconds; integers below 2^24 and float-exact bounds are unaffected) and for values or bounds beyond +-Float.MAX_VALUE; default IndexWriterConfig, codec and searcher, one document suffices, every release from 7.0.0 to 10.5.2 and main; no Lucene production code calls the bridge, and since 10.4.0 (#15406) a round-tripped typed ValueSource is unwrapped and therefore exact.
Summary
You index DoubleDocValuesField("d") values 0.9999999999999999, 1.0 and 1.0000000000000002 and search new FunctionRangeQuery(ValueSource.fromDoubleValuesSource(DoubleValuesSource.fromDoubleField("d")), 1.0, 1.0, true, true), expecting only the document whose value is 1.0, as you get with new DoubleFieldSource("d") or with FunctionMatchQuery over the same DoubleValuesSource. Instead all three match, because the bridged FunctionValues keeps the exact double in doubleVal but does not override getRangeScorer, so it inherits the FunctionValues default that parses both bounds with Float.parseFloat and compares the value cast to float. Likewise {1.0 TO ] misses 1.0000000000000002, [ TO 1e300] matches 1e301, [16777217 TO 16777217] on a long field also matches 16777216, and [* TO 1700000000000] over epoch milliseconds also matches 1700000060000, all without an error.
