If IndexWriter's InfoStream throws while deleteAll() discards a buffered in-memory segment, the discarded buffer stays in the writer's pool and the writer stays open, so documents added afterwards can be missing from later commits that return normally (every release from 8.6.0 to 10.6.0, branch_11x and main)

A narrow case: IndexWriter's InfoStream (a debugging facility, off by default) must be on and must throw once, at one logging call inside deleteAll(). deleteAll() fails loudly, but the writer stays open: the next addDocument() and commit() return normally and the commit lacks that document, unless you call rollback() first.

The finding in 30 seconds

#

Why it is a finding all the same: the writer stays open and, with assertions off, every later call that was run returns normally while documents whose add returned are not in the commits; it is a regression against 8.5.2 at one commit (LUCENE-9304, 2602269f3ec); and the fix is two statements in the other order.

How small this is: four limits

#
  1. The InfoStream is a debugging facility and is off by default. Its javadoc reads "Debugging API for Lucene classes such as IndexWriter and SegmentInfos." and carries the tag @lucene.internal, which the javadoc build renders as "NOTE: This API is for internal purposes only and might change in incompatible ways in the next release." No stock InfoStream throws by itself: it takes an application's own one, or a stock one over a target of the application's that throws an unchecked exception. A plain java.io.PrintStream swallows an IOException of its target, so a log file that cannot be written does not do it. And it must throw at this one call: a one-time throw at one of the three other log lines made on the way loses no later document (run).
  2. deleteAll() fails loudly. A maintainer's answer of 2019 on a related report names the remedy for such exceptions: "a user could always call rollback() to go back the the last known safe-point / previous commit" (Simon Willnauer on #9738, 2019-03-06). It works here: rollback() right after the failed call leaves the index at the last commit (run on main 9965d34e3c77, branch_11x 9d2b5a15427a and the 10.6.0 jars).
  3. A second deleteAll() right after the failed one also clears it (run with assertions off), but only right after: once a commit, a flush or a near-real-time reader came first, a second deleteAll() no longer clears it, and rollback() returns to a last commit that lacks the documents added in between (run). With assertions on, from 10.0.0 on, most shapes end with the writer closing itself: a commit, a flush, a near-real-time reader, rollback() or a second deleteAll() after the failed call throws an AssertionError and the writer is closed (before 10.0.0 an AssertionError does not close the writer; run on 8.6.0 to 9.12.3). Only an add or an update as the next call still loses its document without an error.
  4. A logging failure that lasts does not trigger it. When it lasts for the whole deleteAll() call, the call fails at its first log line, before anything is discarded, and nothing is lost. When it begins at the stall update and is not over by the writer's next log line, the buffers stay locked and an add from another thread blocks: another state, not this finding, which the fix that was run does not remove (run on main 9965d34e3c77, as a boundary).

The finding, step by step

#
  1. Switch IndexWriter's InfoStream on (IndexWriterConfig.setInfoStream), add document 1 and call deleteAll(). In the test the stream throws IllegalStateException once, at one logging call that Lucene makes while it discards the buffered document.
  2. deleteAll() throws that exception. The writer stays open: isOpen() is true and there is no tragic exception.
  3. You keep using the writer: addDocument(doc2) returns 2 and commit() returns 3. You expect document 2 in the index: docFreq(id:2) = 1.
  4. You get docFreq(id:2) = 0 and numDocs() = 0, with no error.
  5. Why: Lucene updates its stall state, which makes the logging call, one line before it takes the discarded buffer out of the writer's pool. The exception skips that step, so the next add is written into the discarded buffer and dropped with it. With the two statements in the other order the commit returns 4 and has document 2.

Who is affected

#

Only an application that has switched the InfoStream on, whose stream throws an unchecked exception once, at this one logging call, and that keeps using the writer after deleteAll() threw. Documents added after the failed call can then be missing from commits that return normally: in the runs with one buffer in the pool (one indexing thread), the next document added (on 8.6.0 to 8.6.3 that add throws instead) or, with assertions off, every document added afterwards when a commit, a flush or a near-real-time reader comes before the next add. Documents committed before it are not touched by the failed call; changes made to them afterwards can be lost as well (the update of 2026-11-21 under Exposure and likelihood).

Mechanism, terms and numbers1,579 words

Small. It needs two things at once. The application has switched IndexWriter's InfoStream on: a debugging facility that is off by default; its javadoc reads "Debugging API for Lucene classes such as IndexWriter and SegmentInfos." and carries the tag @lucene.internal. And that stream throws an unchecked exception once, at one particular logging call inside deleteAll(). No stock InfoStream throws by itself: it takes an application's own InfoStream, or a stock one over a target of the application's that throws an unchecked exception (a plain java.io.PrintStream swallows an IOException of its target, so a log file that cannot be written does not do it). And the failure has to be over by the writer's next logging call.

deleteAll() then fails loudly: it throws the stream's exception. A maintainer's recorded answer of 2019 on a related report (#9738, Simon Willnauer, 2019-03-06) names rollback() as the remedy after such an exception, and it works here: rollback() right after the failed call leaves the index at the last commit. A second deleteAll() also clears it with assertions off, but only right after the failed call. With assertions on, from 10.0.0 on, most shapes end with the writer closing itself.

What makes it a finding all the same: the writer stays open and, with assertions off, every later call that was run returns normally while documents whose add returned are not in the commits. deleteAll() discards the buffered documents, and DocumentsWriterFlushControl.doOnAbort updates the stall state before it takes the discarded buffer out of the writer's pool (DocumentsWriterFlushControl.java:401-403, lines at main 9965d34e3c77). The stall update can call the InfoStream. When that call throws, the buffer stays in the pool. With one indexing thread, as in the test, the next addDocument() is indexed into the discarded buffer and dropped with it; commit() returns a sequence number that covers the add, and the committed index does not contain the document (with assertions on too; the writer's close() then fails an assertion). If a commit, a flush or a near-real-time reader comes before the next add, then with assertions off every document added afterwards is missing from the later commits.

Every release from 8.6.0 to 10.6.0 has it, and so do the builds of branch_11x 9d2b5a15427a and main 9965d34e3c77 that were run (on 8.6.0 to 8.6.3 the add right after the failed call throws; there a document is lost without an error only when a commit, a flush or a near-real-time reader comes first, with assertions off). It is a regression against 8.5.2 at one commit: 2602269f3ec (LUCENE-9304, 2020; 83b34d47900 on branch_8x), which put the pool step after the stall update. The fix that was run is two statements in the other order (one line moves).

deleteAll() discards the documents that are buffered in memory. For each in-memory buffer it marks the buffer aborted and then calls DocumentsWriterFlushControl.doOnAbort, which updates the stall state and takes the buffer out of the writer's pool, in that order. The stall update can call the InfoStream. If that call throws, the second step never runs.

Why it looks unintended

#
  • commit() documents that every sequence number up to the one it returns is in the commit: the add returned 2, the commit 3.
  • The code's own comments say an aborted buffer leaves the pool and is never reused.
  • 8.5.2 passes the same test: the order came with a refactoring in 2020.
The full argument357 words
  • commit()'s contract (IndexWriter.java:4239-4241): "@return The sequence number of the last operation in the commit. All sequence numbers <= this value will be reflected in the commit, and all others will not." The add returned 2, the commit returned 3, and the commit does not hold the document (run).
  • The class javadoc names the defence for damaged state (IndexWriter.java:164-167): "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself. This is a defensive measure in case any internal state (buffered documents, deletions, reference counts) were corrupted." Here the writer stays open.
  • deleteAll()'s javadoc (IndexWriter.java:2730-2750) says nothing about a failed call. It mentions rollback() only as the way to undo the call: "This method can be rolled back using {@link #rollback()}."
  • The code's own rule is the opposite. The comment "Take it out of the loop this DWPT is stale" stands in doOnAbort's try block (DocumentsWriterFlushControl.java:399) with no statement under it. "If it is aborted, we shouldn't allow it to be reused" (DocumentsWriter.java:437). marksAsFreeAndUnlock asserts that no aborted buffer enters the free list (DocumentsWriterPerThreadPool.java:139-149).
  • History: a regression of one refactoring. Before 2602269f3ec (LUCENE-9304, 2020-04-11) the try block ended with that comment and the statement perThreadPool.reset(state);, and the finally held updateStallState(); alone: a throw from the stall update came after the buffer had been detached from its pooled slot. The commit removed the statement under the comment and put the pool step after the stall update. The description of its pull request (apache/lucene-solr#1397) states the rule: "the pool semantics have changed slightly such that DWPT need to be _checked-out_ in the pool once they need to be flushed or aborted". Nothing in it or in the review is about the order of the two statements or about a failure between them. 8.5.2 passes the test (run).
  • A precedent in the same class. #6053 (LUCENE-4989, 2013): an exception during a buffer's abort skipped a cleanup step of the flush control. Michael McCandless: "This looks bad ... we should fix for 4.3.1?" (2013-05-16). It was closed as fixed.
The devil's-advocate check500 words

The strongest case for "works as designed": an InfoStream is an internal debugging API and should not throw, and after an exception from deleteAll() the application is expected to roll back. The second part is a maintainer's recorded statement. On #9738 (LUCENE-8692, "IndexWriter.getTragicException() may not reflect all corrupting exceptions (notably: NoSuchFileException)", open), Simon Willnauer wrote on 2019-03-06, after listing getReader(), deleteAll(), addIndexes(), flushNextBuffer(), prepareCommitInternal(), doFlush() and startCommit():

"Those methods might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback() to go back the the last known safe-point / previous commit. Now we can debate if we want to change this and we can, in-fact I am all for making it even more strict especially since it's inconsistent with what we do if addDocument fails with an aborting exception."

Five days later, on 2019-03-11, they added in the same thread:

"I agree with you here, I personally question the purpose of rollback since all the cases I have seen a missing rollback would simply mean dataloss. if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss. I can't think of a reason why you would want to do it."

and on 2019-03-12, in their last comment there: "I mean we can keep rollback but bet more strict about exceptions during the commit and friends?"

rollback() does work here: right after the failed call it leaves the index at the last commit (run on main 9965d34e3c77, branch_11x 9d2b5a15427a and the 10.6.0 jars).

Why this does not make the state intended:

  1. The statement is 13 months older than the code. On the release before the change (8.5.2) the same failure loses nothing afterwards (run).
  2. The thread names no mechanism and no call site. It does say what to expect of an application that goes on after a failed call without rollback() (inconsistency or loss), and in all three comments it favours making the writer stricter, up to closing it automatically; the issue is still open and labelled a bug.
  3. No javadoc tells the caller to roll back after deleteAll() threw, and the writer gives no sign: it is open, has no tragic exception, and with assertions off every later call that was run returns.
  4. The fix restores the order of the two steps that the code had until 2020 and changes nothing when the stream does not throw.

What stays true of the argument: the trigger is contrived, the remedy works, and the maintainer's words cover an application that goes on without rollback(). That is why the finding is rated Low. "Do not throw from an InfoStream" and "roll back after a failed deleteAll()" are fair answers, and a documentation change would be a fair outcome too. One executed second opinion called it not a bug on this ground alone, while it reproduced the lost document and agreed with the mechanism.

Registry title
If IndexWriter's InfoStream throws while deleteAll() discards a buffered in-memory segment, the discarded buffer stays in the writer's pool and the writer stays open, so documents added afterwards can be missing from later commits that return normally (every release from 8.6.0 to 10.6.0, branch_11x and main)
Area
index / IndexWriter deleteAll (DocumentsWriter.lockAndAbortAll, DocumentsWriterFlushControl.doOnAbort, the pool of in-memory segment buffers)
Priority
Low, rank 353: If the opt-in InfoStream throws an unchecked exception at one logging call while deleteAll() discards a buffered segment, deleteAll() throws and the writer stays open, and if the application keeps using it, documents added afterwards can be missing, without an error, from commits that return normally, in every release since 8.6.0 (on 8.6.0 to 8.6.3 only when a commit, a flush or a near-real-time reader is called first, with assertions off). It is Low because the trigger is contrived: no shipped InfoStream throws there by itself, an Error at that call closes the writer (before 10.0.0 only a VirtualMachineError such as an OutOfMemoryError), a logging failure that lasts for the whole deleteAll() call loses nothing, and with assertions off rollback() right after the failed call returns the index to the last commit.
Impact class
minor
Impact note
Hits an application that turns on IndexWriter's InfoStream (off by default) and calls deleteAll(), or deleteDocuments with a MatchAllDocsQuery, while documents are buffered, when the InfoStream throws an unchecked exception once, at the logging call of the stall update that is made while a buffer is discarded, and that then keeps using the writer [exec]. deleteAll() throws that exception and the writer stays open with no tragic exception [exec]. With one buffer in the pool (one indexing thread) the next addDocument() and commit() return normally, the commit's sequence number covers the add, and the commit does not hold the document [exec, -ea and -da; on 8.6.0 to 8.6.3 the add throws FileAlreadyExistsException instead]; with two buffers in the pool the next add can get the other buffer, and then no document added afterwards is in a later commit [exec on main, -da]. Summary
You turn on IndexWriter's InfoStream, add a document and call deleteAll(); while Lucene discards the buffered document, one logging call throws an exception, so deleteAll() throws it and the writer stays open. You expect an open writer to keep what it acknowledges: you add document 2 and commit, both calls return normally and the commit's sequence number covers the add, so document 2 should be in the index. Instead the discarded buffer was never taken out of the writer's pool, document 2 is indexed into it and dropped, and the committed index does not contain it; if a commit, flush or NRT reader comes first, then with assertions off every document added afterwards is missing from every later commit for the rest of that writer's life.
