GroupingSearch's second-pass cache without scores throws NullPointerException with the default within-group sort or includeMaxScore

With GroupingSearch's cache turned on without scores, setCaching(10, false), search() throws NullPointerException whenever there are hits and the cache holds them all: they are replayed without a scorer into a second pass that needs scores by default. It is in every release since 4.0.0; cacheScores = true avoids it.

The finding in 30 seconds

#

Grouping runs two passes over the same query. The cache lets the second pass reuse the first pass's hits, and cacheScores = false keeps only their doc ids.

How GroupingSearch's cache works

#
  1. Grouping runs in two passes: the first finds the top groups, and the second collects the top documents inside each of those groups.
  2. setCaching(n, cacheScores) (or setCachingInMB(mb, cacheScores)) keeps the first pass's hits in memory and replays them into the second pass, so the query runs once. With cacheScores = false only the doc ids are kept, 4 bytes per hit instead of 8.
  3. If the hits do not fit within the limit, the cache is dropped and the second pass re-runs the query.

The finding, step by step

#
  1. Index one document in group A and run new GroupingSearch("g").setCaching(10, false).search(searcher, new MatchAllDocsQuery(), 0, 10), every other setting at its default.
  2. You expect 1 group with its 1 document, the same as without the cache or with setCaching(10, true). The javadoc calls the cache an optimisation of the second pass and cacheScores just "Whether to cache the scores".
  3. Instead search() throws NullPointerException: ... because "this.scorer" is null. The cache holds doc ids only. The second pass sorts each group by relevance and records its max score (both defaults), and a replay without scores never sets a scorer.
  4. It depends on the hit count: with 6 hits, setCaching(3, false) overflows the cache, the query is re-run with a live scorer and the same search succeeds. Field sorts alone do not help. Only a score-free within-group sort plus setIncludeMaxScore(false) works.

Who is affected

#

Applications that turn on GroupingSearch's opt-in cache with cacheScores = false (setCaching or setCachingInMB). Every non-empty search whose hits all fit in the cache then fails under the default within-group sort or the default includeMaxScore; one document is enough. Larger result sets overflow the cache and succeed. It fails loudly (no wrong results seen), and cacheScores = true avoids it.

Mechanism, terms and numbers521 words

GroupingSearch can cache the hits of its first pass and replay them into the second pass, so the query runs only once. setCaching(maxDocs, cacheScores) and setCachingInMB(mb, cacheScores) let the caller choose whether scores are cached too. With cacheScores = false, search() throws NullPointerException: Cannot invoke "Scorable.score()" because "this.scorer" is null on every search that has hits and whose hits all fit in the cache, as long as the within-group sort uses scores (the default Sort.RELEVANCE) or includeMaxScore is true (the default). GroupingSearch passes the caller's flag to CachingCollectorManager unchanged, but it builds the second pass itself from those score-needing defaults, and a replay without cached scores never sets a Scorer. When the hits overflow the cache, the cache is dropped, the query is re-run and the same search succeeds. The bug is as old as GroupingSearch (4.0.0, 2012) and is still on main.

The mechanism (main 5adff78bb168)

#
  1. Defaults that need scores. groupSort = Sort.RELEVANCE, sortWithinGroup = Sort.RELEVANCE (GroupingSearch.java:51-52) and includeMaxScore = true (:56).
  2. The caller's flag, as given. groupByFieldOrFunction builds the cache as new CachingCollectorManager<>(firstRoundManager, cacheScores, maxCacheRAMMB, maxDocsToCache) (:169-173).
  3. A second pass that GroupingSearch builds itself. The TopGroupsCollectorManager is built from sortWithinGroup and includeMaxScore (:197-205). The cache is replayed into it whenever every slice's cache held (:208-209); otherwise the query is re-run (:211).
  4. A replay without a scorer. CachingCollectorManager.replay replays each slice into a fresh second-pass collector (CachingCollectorManager.java:118-130). The score-less NoScoreCachingCollector calls getLeafCollector, collect and finish, but never setScorer (CachingCollector.java:98-118), as its javadoc says: "If this instance does not cache scores, then Scorer is not set on other.setScorer" (:345-347). The score-caching variant sets a CachedScorable (:144-155).
  5. A second pass that needs one. The second pass needs scores iff getMaxScores || withinGroupSort.needsScores() (TopGroupsCollector.java:127-128). With Sort.RELEVANCE each group gets a TopScoreDocCollector (:129-136). With a field sort it gets a TopFieldCollector, plus a MaxScoreCollector when includeMaxScore is true (:138-146). SecondPassGroupingCollector reports ScoreMode.COMPLETE in that case (SecondPassGroupingCollector.java:76-79) and would pass the scorer on in setScorer (:81-85, GroupReducer.java:77-80), but nobody calls it.
  6. The crash. The first replayed document that belongs to a selected group calls scorer.score() on null: TopScoreDocCollector.java:95 with the default relevance sort, or TopGroupsCollector.java:102 (MaxScoreCollector.collect) with field sorts and the default includeMaxScore.

The exact trigger

#

A bounded-exhaustive differential ran 5,760 GroupingSearch configurations, each against the same search without the cache. The variables were the group sort, the within-group sort, includeMaxScore, cacheScores, three cache modes, allGroups, allGroupHeads, term and ValueSource selectors, sequential and 2-thread searchers, and 1 and 2 segments. The predicate !cacheScores && (includeMaxScore || sortWithinGroup.needsScores()) && every slice's hits fit in the cache predicted 1,536 throws, and exactly those threw. The other 4,224 were identical to the uncached search, so no silent wrong results were found. Every tested search had hits: a search with no hits returns before the replay (GroupingSearch.java:193-195) and does not throw. With fix A, all 5,760 matched with 0 exceptions.

Exposure and likelihood187 words
  • Who is hit. Code that uses GroupingSearch with its second-pass cache and passes cacheScores = false, the obvious choice for saving RAM: 4 bytes per cached hit instead of 8 (CachingCollector.java:308-312).
  • Default vs opt-in. The cache is off by default, and cacheScores = false is a further choice. Once it is made, the default within-group sort and the default includeMaxScore make every non-empty cached search fail. Switching both sorts to field sorts still fails through includeMaxScore = true. With a term or ValueSource group selector, the only combination that works is a score-free within-group sort plus setIncludeMaxScore(false).
  • Scale. None needed: one document is enough. Small result sets, the ones the cache holds, fail. Large ones overflow it and succeed, so a quick test with large results can miss it.
  • How likely. Rare. Every caller found caches scores: the upstream grouping tests, the package example and Solr's grouping, which derives the flag. The failure is loud enough to show up in a first test run.
  • Severity. A loud, deterministic exception, with no wrong results in the tested configurations. Workaround: cacheScores = true.

Why it looks unintended

#
  • The javadoc calls the cache an optimisation and cacheScores just "Whether to cache the scores", with no precondition.
  • The defaults need scores, so cacheScores = false fails on every non-empty search the cache holds, yet succeeds once the hits overflow it.
  • The class computes score needs on its doc-block path (:231); grouping tests and the package example only cache scores.
The full argument242 words
  • Contract. GroupingSearch.java:240-272: "Enables caching for the second pass search. ... The cache is filled during the first pass searched and then replayed during the second pass searched. If the cache grows beyond the specified limit, then the cache is purged and not used in the second pass search", and @param cacheScores Whether to cache the scores. The package doc (package-info.java:53-58) presents the cache as a way to "only run the query once, but you pay a RAM cost".
  • Composition. GroupingSearch builds both the cache and the second pass, and it knows the second pass's score needs. Its own doc-block path computes groupSort.needsScores() || sortWithinGroup.needsScores() (:231). Solr's grouping sets cacheScores = withinGroupSort == null || withinGroupSort.needsScores() (or needScores) before creating its CachingCollector (Solr Grouping.java:304-312).
  • Grouping tests and the package example. TestGroupingSearch.java:216 (setCachingInMB(4.0, true)), TestGrouping.java:1136 (new CachingCollectorManager<>(firstRoundManager, true, maxCacheMB, null)) and the package example (package-info.java:89) all cache scores. No test, CHANGES or MIGRATE entry, or review limits cacheScores = false to particular sorts.
  • History. The behaviour came in with the class (LUCENE-3778, 2012). The LUCENE-3778 review discusses the cache only in passing (the setter names, and that caching suits a local index); nothing in it relates cacheScores to what the second pass needs. The #16247 review never mentions cacheScores.
  • Behaviour. Whether a search fails depends on whether its hits fit in the cache. No designed behaviour looks like that.
The devil's-advocate check195 words

The argument. CachingCollector.replay documents that a score-less replay sets no Scorer (CachingCollector.java:345-347). In #4175 (LUCENE-3102, 2011) Michael McCandless wrote that a caller "could mess up (pass cacheScores = false but then pass a collector that calls .score())". GroupingSearch is @lucene.experimental. So the user should match cacheScores to the second pass.

Why it fails.

  • In GroupingSearch, the party that passes "a collector that calls .score()" is GroupingSearch itself, which builds the second pass from its own defaults. The user never sees that collector.
  • The remark asked for the mistake to be detected ("it'd be nice if we could \"verify\" that the collector agrees we don't need scores"), not accepted. It also predates GroupingSearch (March 2012).
  • @lucene.experimental allows API changes. It does not make an NPE from documented setters an accepted outcome.

A maintainer may still reasonably keep cacheScores literal and choose a documented precondition plus a clear error (fix B) over silently overriding an explicit false (fix A). Either way the NPE goes.

Two executed reviews by another model family (OpenAI GPT-5.6) rated this argument weak (works-as-designed lens) and moderate (refute lens), and both still called the bug real with high confidence.

Suggested fix

#

Recommended A: cache the scores whenever the second pass needs them (validated)

Cache the scores whenever the second pass needs them: pass cacheScores || includeMaxScore || sortWithinGroup.needsScores() to CachingCollectorManager, which is how Solr's grouping sets the flag. Validated: the repro passes with assertions on and off, and the whole grouping module and :lucene:grouping:check pass.

     if (maxCacheRAMMB != null || maxDocsToCache != null) {
+      // A replay without cached scores sets no Scorer, so cache the scores whenever the second pass
+      // needs them (a within-group sort by score, or max scores).
+      boolean secondPassNeedsScores = includeMaxScore || sortWithinGroup.needsScores();
       cachingManager =
           new CachingCollectorManager<>(
-              firstRoundManager, cacheScores, maxCacheRAMMB, maxDocsToCache);
+              firstRoundManager,
+              cacheScores || secondPassNeedsScores,
+              maxCacheRAMMB,
+              maxDocsToCache);

A: cache the scores whenever the second pass needs them (validated) (recommended)

#

In GroupingSearch.groupByFieldOrFunction, compute includeMaxScore || sortWithinGroup.needsScores() and pass cacheScores || secondPassNeedsScores to CachingCollectorManager. This is the same rule TopGroupsCollector uses for its own score needs (:128), and the way Solr's grouping sets the flag. Optionally, add to the cacheScores javadoc that scores are cached anyway when the second pass needs them.

     if (maxCacheRAMMB != null || maxDocsToCache != null) {
+      // A replay without cached scores sets no Scorer, so cache the scores whenever the second pass
+      // needs them (a within-group sort by score, or max scores).
+      boolean secondPassNeedsScores = includeMaxScore || sortWithinGroup.needsScores();
       cachingManager =
           new CachingCollectorManager<>(
-              firstRoundManager, cacheScores, maxCacheRAMMB, maxDocsToCache);
+              firstRoundManager,
+              cacheScores || secondPassNeedsScores,
+              maxCacheRAMMB,
+              maxDocsToCache);

Trade-offs

It quietly overrides an explicit false. Each cached hit then costs 8 bytes instead of 4, and with setCachingInMB the same budget holds about half as many hits per slice, so larger result sets fall back to re-running the query (still correct). The first pass now computes scores even when only includeMaxScore needs them.

What the checks validated

Repro passes (assertions on and off), :lucene:grouping:test 57/57, :lucene:grouping:check -x test passes; earlier, 5,760 of 5,760 differential configurations match.

B: reject the combination with a clear exception (not run)

#

At search time, throw IllegalArgumentException (or IllegalStateException) when cacheScores is false and the second pass needs scores, and name the settings. The check cannot go in the setters, which can be called in any order.

Trade-offs

It keeps the user's RAM choice explicit, and a maintainer may reasonably prefer it to A's silent override of an explicit false. It also turns the searches that succeed today, because their hits overflow the cache, into errors.

What the checks validated

Not run.

C: re-run the query instead of replaying (not run)

#

When the second pass needs scores and none were cached, skip replay and call searcher.search(query, secondPassManager).

Trade-offs

Always correct, but the cache then saves nothing for that configuration.

What the checks validated

Not run.

D: hardening in the replay (combinable with A) (not run)

#

CachingCollector.replay(Collector other) throws IllegalArgumentException when no scores are cached and other.scoreMode().needsScores(). CachingCollectorManager.replay takes a CollectorManager, which has no score mode, but it replays each slice through cache.replay(secondCollector) (CachingCollectorManager.java:124-126), so it gets the same check. This is the check #4175 wished for.

Trade-offs

Direct callers get a clear message instead of an NPE. On its own it does not make GroupingSearch work.

What the checks validated

Not run.

Downstream note

#

A service that builds GroupingSearch with setCaching(n, false) or setCachingInMB(mb, false) gets an exception on its small grouped searches until it switches to cacheScores = true.

How it was found

#

Semi-formal: while modelling which collector hands a scorer to which consumer when grouping's cache is replayed into the second pass, a score-less replay into a scoring second pass stood out, and a public-API probe on main threw the NPE. One JUnit test and a bounded-exhaustive differential of 5,760 configurations then pinned the exact trigger.

The method in full186 words

Method: semi-formal (a hypothesis formed while modelling, then witnessed by a tool), on main, 2026-10-26 to 2026-11-01.

  • Modelling. A bounded-exhaustive translation validation of two-pass grouping modelled the replay protocol: which collector calls setScorer on which consumer. The score-less replay path has no setScorer call, and the second pass GroupingSearch builds by default needs one.
  • Witness. A public-API probe on the stock main jars showed that the default relevance sorts and includeMaxScore = true throw, while the cached-scores mode works. It was re-run with assertions on and off.
  • Reduction and scope. The probe was reduced to one JUnit test. A bounded-exhaustive differential of 5,760 GroupingSearch configurations against the same search without the cache confirmed the exact trigger: 1,536 predicted throws, all observed, and 0 silent mismatches. A vacuity control (the predicate turned off) flagged all 1,536. A release sweep ran from 4.0.0 to 10.6.0.
  • Checks. An independent reproducer wrote its own test. An executed review by another model family (OpenAI GPT-5.6) wrote its own tests with a refute and a works-as-designed lens, and a devil's-advocate verifier argued intended behaviour. An adjudication re-ran the repro and the fix.

History

#

Born with GroupingSearch (LUCENE-3778, 89b55566d83, 2012-03-22). It fails when executed on every release from 4.0.0-alpha to 10.6.0 and on main; 3.6.2 has no GroupingSearch. Not fixed upstream.

Versions tested8 rows

Introduced: 89b55566d83, LUCENE-3778 "Added a grouping utility class that makes it easier to use result grouping for pure Lucene apps" (now #4851), Martijn van Groningen, 2012-03-22 (svn era, no PR). At that commit GroupingSearch already passed cacheScores straight to CachingCollector.create, replayed whenever the cache held, and defaulted to score-needing settings (a null within-group sort, meaning relevance, and includeMaxScore = true). It is not a regression.

Later changes kept it:

  • LUCENE-6900 (0442747f05d, 5.5.0) made Sort.RELEVANCE the default within-group sort.
  • LUCENE-7701 (caf329717ef, 7.0.0) refactored grouping onto GroupSelector.
  • #16247 (3afffeef5a8, 2026-07-08, in 10.6.0) introduced CachingCollectorManager. The same NPE now comes through its replay.

Not fixed upstream: upstream main f72004515ec (2026-11-03) has no commit to the fix-site files after #16247 (checked 2026-11-04).

The release sweep ran a version-agnostic main() form on every release: the same GroupingSearch settings (setCaching(10, false), all defaults) on two documents and a TermQuery, because the org.apache.lucene.tests packages only start in 9.1.0. This exact one-document test was also run on 10.6.0, 10.5.2 and 9.12.3 (assertions off): all three fail. 4.0.0-alpha ran on a plain classpath with SHA-1-checked release jars.

LFV-1068, snapshot of 2026-11-10

Registry title
GroupingSearch.setCaching(n, false) and setCachingInMB(mb, false) throw NullPointerException with the default within-group sort or the default includeMaxScore, because the score-less cache is replayed into a second pass that needs scores
Area
grouping / GroupingSearch second-pass cache (score-less CachingCollector / CachingCollectorManager replay into the TopGroups second pass)
Priority
Low, rank 739: GroupingSearch's opt-in second-pass cache without scores throws NullPointerException on every search whose hits fit in the cache when the within-group sort or includeMaxScore is left at its default, in every release since 4.0.0. The failure is loud enough to show up in a first test run, with no wrong results and an easy workaround, so it is Low.
Impact class
minor
Impact note
Applications that turn on GroupingSearch's opt-in second-pass cache without scores (setCaching(n, false) or setCachingInMB(mb, false)) and keep the default within-group sort Sort.RELEVANCE, sort within groups by score, or keep the default includeMaxScore=true get a NullPointerException from search() on every search whose hits fit in the cache, with -ea and -da, in every release from 4.0.0 to 10.6.0 and on main; no scale is needed, it fails loudly and never returns wrong results (0 silent mismatches over 5,760 configurations), and cacheScores=true avoids it.
Summary
You turn on GroupingSearch's documented second-pass cache without cached scores, new GroupingSearch("g").setCaching(10, false), and run an ordinary grouped search over two documents in groups A and B; you expect the same groups as without the cache, because the javadoc presents the cache as an optimisation that the second pass replays. Instead search() throws NullPointerException ('Cannot invoke Scorable.score() because this.scorer is null'): GroupingSearch builds the cache with the caller's cacheScores flag but replays it into a second pass that it builds itself from its defaults (within-group sort Sort.RELEVANCE, includeMaxScore=true), and both need scores, while a score-less replay never sets a Scorer. Whether a search fails depends on the hit count: when the hits overflow the cache, the cache is dropped, the query is re-run and the search succeeds.
