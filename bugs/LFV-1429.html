Full-precision rescoring fails on a segment that lists the vector field but holds no vectors

On Lucene main and branch_11x (unreleased), RescoreTopNQuery.createFullPrecisionRescorerQuery throws UnsupportedOperationException when its inner query matches a document in a segment whose vector documents were all deleted and merged away. 10.6.0 returns that document with score 0; no release is affected.

The finding in 30 seconds

#

The rescorer now asks each segment's vector values for a copy(). For a segment that lists the field but stores no vectors, the codec hands out a special empty vector-values object, and its copy() throws.

Full-precision rescoring, in one minute

#
  1. kNN search often runs on compressed (quantized) vectors. RescoreTopNQuery.createFullPrecisionRescorerQuery(inner, target, field, n) takes the hits of any inner query, re-scores them with the exact stored vectors and keeps the top n.
  2. A hit whose document has no vector in that field gets score 0. A segment that never had the field gets no values at all, with the same result.
  3. Since #16705 (main and branch_11x, unreleased) the rescorer reads ahead: for each segment it calls copy() on the field's vector values, to get a second view it can prefetch from while it scores with the first.
  4. When all of a segment's vector documents are deleted and merged away, the merged segment keeps the field in its field list but stores 0 vectors. For such a field the codec returns an empty vector-values object.

The finding, step by step

#
  1. Index 2 documents with the default codec: one with the 2-dimensional vector {1, 0} in field v, one with no fields.
  2. Delete the vector document and run forceMerge(1). The one segment still lists field v but holds 0 vectors: getFloatVectorValues("v").size() is 0.
  3. Search createFullPrecisionRescorerQuery(MatchAllDocsQuery.INSTANCE, {1, 0}, "v", 1). You expect 1 hit, the document without a vector, with score 0: that is how RescoreTopNQuery scores a match without a vector, and what 10.6.0 returns.
  4. Instead IndexSearcher.search throws UnsupportedOperationException. Since #16705 the rescorer asks every segment's non-null vector values for a copy(), a second view to prefetch from, before it checks for a scorer, and the codec's empty vector values throw from copy().
  5. The whole query fails, not just that segment's part, whenever its inner query matches a document in such a segment. Float16 vectors and the Lucene104 scalar-quantized formats fail the same way.

Who is affected

#

Applications on main (12.0.0-SNAPSHOT) or branch_11x (the future 11.0.0) that use opt-in full-precision rescoring with a keyword, filter or hybrid inner query, on the default codec or the Lucene104 scalar-quantized formats. It takes a segment whose vector documents were all deleted and merged away; a query then fails whenever its inner query matches a document in that segment.

Mechanism, terms and numbers515 words

Full-precision rescoring re-scores the hits of another query with the exact stored vectors (RescoreTopNQuery.createFullPrecisionRescorerQuery, float32 and float16, or the public FullPrecision{Float,Float16}VectorSimilarityValuesSource). Since #16705 (main and branch_11x, not released) the shared value source calls copy() on every segment's non-null vector values, to get a second view it can prefetch from, before it checks for a scorer. When every document with a vector in a segment has been deleted and merged away, the segment still lists the field but holds 0 vectors, and the default codec returns its empty vector values for it, whose copy() throws UnsupportedOperationException. So a rescoring query whose inner query matches any document in such a segment fails as a whole, where 10.6.0 returns that document with score 0. Two documents reproduce it; the Lucene104 scalar-quantized formats fail the same way. kNN-only inner queries are not affected, because they match nothing in such a segment.

  • Before the copy, getValues returns early only when the leaf has no vector values object at all (DoubleValues.EMPTY) or the dimension differs (an exception). A segment that lists the field with 0 vectors gets a non-null empty view of size 0, so it reaches copy(). The scorer check that would return DoubleValues.EMPTY for that view comes only after the copy (:68-72, the path createFullPrecisionRescorerQuery takes; the empty view's scorer() returns null, OffHeapFloatVectorValues.java:333-335). The exception leaves RescoreTopNQuery.rewrite (:79), so IndexSearcher.search fails.
  • The same throwing copy() is in the other empty views: lucene95 float16 (OffHeapFloat16VectorValues.java:114, throw at :318) and byte (OffHeapByteVectorValues.java:329), and lucene104 OffHeapScalarQuantizedFloatVectorValues.java:389, OffHeapScalarQuantizedFloat16VectorValues.java:385, OffHeapScalarQuantizedVectorValues.java:528.   • Not affected: a kNN-only inner query (it matches nothing in such a segment, so weight.scorer(leaf) is null and the leaf is skipped, RescoreTopNQuery.java:136-138, read); a segment without the field (DoubleValues.EMPTY). The byte empty view throws too, but there is no full-precision byte rescoring source today.

Why it looks unintended

#
  • KnnVectorValues#copy() names no unsupported case, and RescoreTopNQuery "can work with any type of Query", scoring a match without a vector 0.
  • Upstream's testDeleteAllVectorDocs builds this exact index and asserts that "knn search doesn't fail" on it.
  • #16705 itself fixed the same throw in ExitableDirectoryReader because rescoring "failed outright"; 10.6.0 returns the document with score 0.
The full argument243 words
  • Contract. KnnVectorValues#copy(): "Creates a new copy of this KnnVectorValues. This is helpful when you need to access different values at once" (KnnVectorValues.java:95-99). No unsupported case is named.
  • Outcome in the code and tests. The RescoreTopNQuery javadoc says it "can work with any type of Query" (RescoreTopNQuery.java:30-31); its code (rescoreInto, :224-231) gives a match without a value score 0, though no javadoc states that score. Upstream tests assert it for a rescoring field absent from the index: "Score must be 0 for missing DoubleValues" (TestRescoreTopNQuery.java:186, :271). The core point is that the search must not throw on this legal index state.
  • Legal state. BaseKnnVectorsFormatTestCase#testDeleteAllVectorDocs indexes a document with a vector and one without, deletes the first, runs forceMerge(1), asserts non-null values of size 0 and "assert that knn search doesn't fail on a field with all deleted docs" (:893-929).
  • Upstream already treats a throwing copy() on this path as a bug. goankur on #16705 (2026-09-25): "ExitableDirectoryReader also throws from copy(), and prefetching uses a second copy() view, so rescoring through a reader with a timeout failed outright rather than just losing the prefetch." The PR fixed that wrapper but not the codec's empty views; open PR #16986 does the same for SortingCodecReader.
  • Precedent for the fix. FloatVectorValues.fromFloats(...) already returns this from copy() (FloatVectorValues.java:126-127).
  • Regression. 10.6.0 returns the document with score 0 on the same index.
The devil's-advocate check143 words

"copy() is optional." About 20 KnnVectorValues implementations throw from it, and the #13779 PR description says some KnnVectorValues methods have default implementations that throw UnsupportedOperationException, "enabling subclasses to provide partial implementations and relying on testing to catch missing required methods". The API is also @lucene.experimental.

Why it fails: that note is about default methods in general, and copy() itself is abstract (KnnVectorValues.java:99). It also treats a missing method that a caller needs as a test gap to close, not as a contract callers must work around. These empty views are what the default codec returns through the public LeafReader API, #16705 fixed the same kind of throw in ExitableDirectoryReader when it added the second view, and @lucene.experimental is about API stability, not a licence to crash. The cross-model reviews and the intended-behaviour devil's advocate rated this case weak.

A: the empty views' copy() returns this (validated by the checks) (recommended)

#

In lucene95 OffHeapFloatVectorValues, OffHeapFloat16VectorValues, OffHeapByteVectorValues and lucene104 OffHeapScalarQuantizedFloatVectorValues, OffHeapScalarQuantizedFloat16VectorValues, OffHeapScalarQuantizedVectorValues, replace the throw in EmptyOffHeapVectorValues.copy() with return this;. The three lucene104 ones change the declared return type to EmptyOffHeapVectorValues.

     @Override
     public EmptyOffHeapVectorValues copy() {
-      throw new UnsupportedOperationException();
+      return this;
     }

Trade-offs

  • An empty view has no vectors and no shared read position (iterator() makes a new iterator on each call), so returning itself is safe, as FloatVectorValues.fromFloats already does.
  • Fixes every caller at once: both rescoring overloads, FunctionScoreQuery, the filter readers and the BPReorderingMergePolicy merge. Fixing only the two lucene95 float views passes this test but leaves the Lucene104 scalar-quantized formats failing.
  • Not built or run: the backward-codecs empty views (lucene92, lucene94, lucene99 quantized, lucene102 binarized) also throw from copy() (read only), so an older index in the same state might fail the same way (not executed); the same one-line change would apply there.

What the checks validated

  • Runs for this page: the table above (gradle, scratch worktree).
  • Earlier: the repro with the change shadowed, assertions on and off; all probe cases; 200 upstream tests in the 8 of 10 requested classes that ran tests, 0 failures, the same as stock.

B: skip the copy when the segment has no vectors

#

In AbstractFullPrecisionVectorSimilarityValuesSource.getValues, return DoubleValues.EMPTY (or skip the prefetch copy) when vectorValues.size() == 0.

Trade-offs

One file, in the code #16705 added. Fixes the rescoring paths only: the merge path and any later copy() caller stay exposed (open PR #16871 adds a per-segment copy() at merge time; open issue #16902 proposes a byte rescoring source that prefetches the same way). Can be combined with A as an early exit. Not built.

How it was found

#

Not from a formal method. The owner knew from their earlier work on vector rescoring that the codec's empty vector values throw from copy(). A differential test of full-precision rescoring then showed that RescoreTopNQuery on main reaches that throw; it was cut down to one JUnit test and checked across codecs, readers and releases.

The method in full129 words

Method: non-formal, on main f794ff5a505c, 2026-11-09.

  • Known part. The owner knew from their earlier vector-rescoring work that copy() throws on the codec's empty off-heap vector values.

Low, rank 726: Full-precision rescoring (float32 and float16) fails the whole query with UnsupportedOperationException, on every such query until the segment is merged away, when its inner query matches a document in a segment that lists the vector field but holds no vectors; it is only in unreleased code (main and branch_11x), so no shipped version is affected. It is Low because rescoring is opt-in, it needs a non-kNN inner query and a segment whose vector documents were all deleted and merged away, and the failure is loud with nothing written wrong.
Impact class
crash
Impact note
Applications on main (12.0.0-SNAPSHOT) or branch_11x (the future 11.0.0) that use full-precision rescoring (opt-in: RescoreTopNQuery.createFullPrecisionRescorerQuery with float[] or short[], or the public FullPrecision{Float,Float16}VectorSimilarityValuesSource in a DoubleValuesSource consumer such as FunctionScoreQuery) with a lexical, filter or hybrid inner query get an UnsupportedOperationException from IndexSearcher.search, on the default codec and on the Lucene104 scalar-quantized formats, whenever the inner query matches a document in a segment that lists the vector field but holds 0 vectors (every vector document of that segment deleted and merged away); the whole query fails, on every such query, until that segment is merged away; 2 documents suffice [exec]; kNN-only inner queries are not affected [read]; no release is affected (10.6.0 passes) [exec].
Summary
You index two documents, only the first with a KnnFloatVectorField "v", delete the first and forceMerge(1), so the one segment still lists "v" but holds no vectors, and you search RescoreTopNQuery.createFullPrecisionRescorerQuery(new TermQuery(id:1), {1, 0}, "v", 1). You expect the matching document back with score 0, which is what RescoreTopNQuery gives a match without a vector and what 10.6.0 returns. Instead IndexSearcher.search throws UnsupportedOperationException: since #16705 AbstractFullPrecisionVectorSimilarityValuesSource.getValues always calls vectorValues.copy() to get a separate prefetch view, and the default codec's EmptyOffHeapVectorValues (what LeafReader.getFloatVectorValues returns for such a segment) throws from copy().
