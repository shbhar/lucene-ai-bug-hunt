SearcherTaxonomyManager.close() leaves the taxonomy reader open when closing the index reader throws

If closing the index reader throws an IOException while SearcherTaxonomyManager.close() releases its pair of readers, the taxonomy reader's release is skipped: it stays open at refCount 1, a second close() does nothing, and the manager can no longer release it (since 4.3.0).

The finding in 30 seconds

#

SearcherTaxonomyManager.decRef releases the index reader, then the taxonomy reader, with no try/finally. If the first release throws, the second never runs. On close() the manager has already dropped the pair, so it cannot release the taxonomy reader later.

Background in three steps

#
  1. SearcherTaxonomyManager (facet module) hands out a matched pair: an IndexSearcher over the main index and a DirectoryTaxonomyReader over the taxonomy index. Both readers are reference-counted and close when their count reaches 0.
  2. Releasing a pair (release(), a refresh that replaces it, or close()) calls the manager's decRef, which decrements both readers.
  3. An IndexReader's final decRef may throw IOException, from closing its files or from a reader-closed listener. Since LUCENE-5553 (4.7.1) the reader is closed even then.

The finding, step by step

#
  1. You build a SearcherTaxonomyManager from an already-opened index reader (1 document) and taxonomy reader. Each reader has refCount 1, owned by the manager.
  2. You call close(), and the index directory throws IOException while the index reader closes its files (a disk error; the test simulates one).
  3. You expect close() to throw that IOException but still release both readers, to refCount 0 and 0: the constructor says "the incoming readers will be closed when you call close".
  4. Instead the index reader ends at 0 but the taxonomy reader stays at 1: decRef releases the index reader first, with no try/finally, so the exception skips the taxonomy release.
  5. A second close() does nothing, because the manager dropped the pair before releasing it. The manager can no longer release the taxonomy reader: it stays open until another holder of a handle closes it, or the process exits. Search results are not affected.

Who is affected

#

Applications that use SearcherTaxonomyManager (any constructor, default settings) when the final release of a pair throws: an I/O error while the index reader closes its files, or their own reader-closed listener throwing. Each failed close() leaks one taxonomy reader, still open with its internal index reader; search and facet results are not affected.

Mechanism, terms and numbers547 words

SearcherTaxonomyManager manages a pair of readers, one for the main index and one for the taxonomy. Its decRef releases the index reader and then the taxonomy reader, with no try/finally. If the index reader's release throws an IOException (an I/O error while it closes its segment files, or a reader-closed listener that throws), the taxonomy reader's release is skipped. On close() the manager has already dropped its reference to the pair, so a second close() does nothing: the manager can no longer release the DirectoryTaxonomyReader, which stays open with its internal index reader until another holder of a handle closes it, or the process exits.

The already-opened-readers constructors promise the opposite: "the incoming readers will be closed when you call close". The code dates from the class itself (4.3.0); since LUCENE-5553 (4.7.1 / 4.8.0) a failing IndexReader close still closes that reader, so the pair now ends half released. The fix is one line in decRef (IOUtils.close over both releases).

The bug

#
  1. ReferenceManager.close() (ReferenceManager.java:133-142) runs swapReference(null) only if (current != null). swapReference (:53-58) sets current = null before it releases the old pair through release() and decRef (:262-265).
  2. SearcherTaxonomyManager.decRef (SearcherTaxonomyManager.java:161-173) calls ref.searcher.getIndexReader().decRef() (:163) and then ref.taxonomyReader.decRef() (:172), with no try/finally. Its comment (:165-171) reasons only about the second call failing.
  3. IndexReader.decRef (IndexReader.java:215-232) sets closed = true at refCount 0 and then runs doClose() inside try (Closeable _ = this::notifyReaderClosedListeners) (:222-227). An IOException from doClose() or a ClosedListener (:141-145, declared throws IOException) escapes after the index reader is closed.
  4. So :172 never runs: the taxonomy reader keeps refCount 1, and its doClose() (DirectoryTaxonomyReader.java:158-164, which closes its internal index reader) never runs.
  5. current is already null, so every later close() is a no-op (ReferenceManager.java:135) and acquire() throws AlreadyClosedException (:95-96). Only a caller that kept its own handle to the taxonomy reader could still close it.

What stays behind (executed)

#

After the failing close(): index reader refCount 0, taxonomy reader refCount 1; after a second close() still 1. The executed call path of the IOException (intermediate frames omitted) is MockIndexInputWrapper.close <- SegmentCoreReaders.decRef <- SegmentReader.doClose <- StandardDirectoryReader.doClose <- IndexReader.decRef <- SearcherTaxonomyManager.decRef (:163) <- ReferenceManager.release <- swapReference <- close.

Before LUCENE-5553 (4.3.0 to 4.7.0), IndexReader.decRef put the count back when doClose failed, so on this I/O path both readers stayed at refCount 1 (executed on 4.3.0). An unchecked exception from a reader-closed listener, which then ran after a successful doClose, could already leave the index reader at 0 and skip the taxonomy release (read: 4.3.0 IndexReader.java:220-244).

Same code, other paths (read, not executed): the same decRef runs when release() drops the last reference to a pair and when a refresh releases the old pair (ReferenceManager.java:172 through swapReference, and :181). If that final release throws during a refresh, the old pair's taxonomy reader stays open, and a later close() releases only the new current pair. The repro covers close() only.

Related rows, other sites: LFV-1296 (MultiReader.close() stops at the first sub-reader whose close throws, the same release-in-sequence shape), LFV-1290 (ReferenceManager.close() skips afterClose() when the release throws) and LFV-497 (the stale IndexReader.decRef javadoc).

Exposure and likelihood205 words
  • Who: any application that uses SearcherTaxonomyManager (taxonomy facets), with any of its three constructor families (writers, directories, already-opened readers) and default settings.
  • Trigger: the final release of a pair throws: an IOException while the index reader closes its segment files (the repro's trigger, no application callback), or an application reader-closed listener that throws IOException (ClosedListener is @lucene.experimental; a second, fully deterministic test with this trigger also fails). An unchecked exception or an Error thrown there skips the taxonomy release in the same way (read).
  • Effect: close() reports the IOException, but the manager can no longer release the DirectoryTaxonomyReader: it stays open with its internal index reader and the files that reader holds until another holder closes it (normally only a caller of the already-opened-readers constructors has a handle) or the process exits; a second close() cannot release it.
  • Not affected: search and facet results, and the contents of either index.
  • Likelihood: rare. Closing an input seldom fails on a local file system, and the leak matters only in a process that keeps running after the failed close(), for example one that closes and reopens managers while serving. No matching public report was found in the searches listed under Prior reports.

Why it looks unintended

#
  • Both already-opened-readers constructors promise "the incoming readers will be closed when you call close".
  • The 2013 review (#4859) and the code comment considered only the taxonomy release failing second.
  • Since LUCENE-5553 a failing close still closes the reader; this class already uses IOUtils.close for the same hazard in refresh.
The full argument202 words
  • The constructor's promise. "Note that the incoming readers will be closed when you call {@link #close}" (SearcherTaxonomyManager.java:127-130, :137-140). Nothing says one may be abandoned when the other fails. (The writer and directory constructors carry no such sentence, but they share the same decRef.) ReferenceManager.close() "should be closed if the reference to the managed resource should be disposed" and may throw "if the underlying reader of the current reference could not be closed" (ReferenceManager.java:118-131): the exception is allowed, abandoning half the pair is not described.
  • The 2013 review covered only the other order. LUCENE-3786 (#4859) added this code. @shaie asked to incRef the searcher's reader again "if taxoReader.decRef() failed", and @mikemccand kept the two plain calls; the comment records that reasoning. Nobody discussed the index reader's release throwing first. In the same review @shaie flagged the same hazard at another site, refreshIfNeeded ("leave behind a dangling TR"), handled there with IOUtils.close(newReader, tr) (SearcherTaxonomyManager.java:217), but not in decRef.
  • Lucene's later rule. LUCENE-5553 (#6615, 4.7.1 / 4.8.0) made IndexReader mark itself closed and notify every listener even when doClose throws. LUCENE-8244 (#9291, 2018) fixed a reader leak in refreshIfNeeded of this same class as a bug.
The devil's-advocate check207 words

The strongest case for "intended": cleanup after an exception is best effort; close() does report the IOException; ReferenceManager, TaxonomyReader and ClosedListener are @lucene.experimental; and when the code was written, IndexReader.decRef put the count back on a failed close (its javadoc still says "If an exception is hit, the refCount is unchanged", IndexReader.java:209), so on the I/O path skipping the taxonomy release then left the pair consistent, if leaked; and a caller of the already-opened-readers constructors still holds its own taxonomy reader handle and can close it.

Why it fails: the 2013 trade-off was about the taxonomy release failing second, not this order; since LUCENE-5553 the index reader really is closed when the exception escapes, so the pair ends half released (index 0, taxonomy 1) with no way to finish through the manager; the constructor promises both readers are closed, and closing the taxonomy reader by hand is a workaround it does not ask for (with the writer and directory constructors the manager opens the taxonomy reader itself); and the repro's trigger is a plain I/O failure, not application code. The stale javadoc is a separate documentation row (LFV-497); fixing it does not fix this leak. The argument bears on severity (Low), not intent.

Suggested fix

#

Recommended A. Release both with IOUtils.close (validated)

Release both readers with IOUtils.close(ref.searcher.getIndexReader()::decRef, ref.taxonomyReader::decRef) in SearcherTaxonomyManager.decRef: both releases always run, the first exception is rethrown and a second one is added as suppressed. The repro passes with assertions on and off, and the facet module's 307 tests run with 0 failures (7 skipped).

@Override
protected void decRef(SearcherAndTaxonomy ref) throws IOException {
  // Release both readers even if the first decRef throws: a final IndexReader.decRef that hits
  // an IOException has still closed the index reader, so the taxonomy reader must be released
  // too. IOUtils.close rethrows the first exception and adds a later one as suppressed.
  IOUtils.close(ref.searcher.getIndexReader()::decRef, ref.taxonomyReader::decRef);
}

A. Release both with IOUtils.close (validated) (recommended)

#

Replace the body of decRef (SearcherTaxonomyManager.java:161-173), one line plus a comment; IOUtils is already imported:

@Override
protected void decRef(SearcherAndTaxonomy ref) throws IOException {
  // Release both readers even if the first decRef throws: a final IndexReader.decRef that hits
  // an IOException has still closed the index reader, so the taxonomy reader must be released
  // too. IOUtils.close rethrows the first exception and adds a later one as suppressed.
  IOUtils.close(ref.searcher.getIndexReader()::decRef, ref.taxonomyReader::decRef);
}

Trade-offs

  • The smallest change; nothing changes when no release throws. The class already uses the same pattern in refreshIfNeeded (IOUtils.close(newReader, tr), :217).
  • It keeps the original exception; IOUtils.close also catches a RuntimeException or Error from the first release and still runs the second.
  • It drops the 2013 comment about putting the index reader's count back if the taxonomy release fails; that case (taxonomy fails second) behaves as before.
  • CHANGES: a Bug Fixes entry.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: the whole :lucene:facet:test, 40 classes (the module's 39 plus the repro), 307 tests, 0 failures, 7 skipped (among them the @Nightly TestSearcherTaxonomyManager.testNRT).
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/facet pass with the fix and the test.
  • The full Lucene test suite was not run.

B. Plain try/finally (validated by the checks)

#

try { ref.searcher.getIndexReader().decRef(); } finally { ref.taxonomyReader.decRef(); }, with the comment kept in the finally.

Trade-offs

If both releases throw, the taxonomy reader's exception replaces the index reader's, so the first failure is lost.

What the checks validated

The repro and TestSearcherTaxonomyManager pass with it (7 tests, 1 skipped @Nightly); earlier shadowed-class checks: the other reproductions' tests pass too.

Downstream note

#

Downstream, a long-running service that closes and reopens SearcherTaxonomyManager instances should not assume that a close() which threw released the taxonomy reader.

#
