The finding in 30 seconds

#

Two automata with the same empty language, both with 0 states: one answers false, the other throws. Only how big their internal arrays happen to be differs.

Background: automata and the empty language

#
  1. An Automaton is a set of numbered states with labelled transitions. State 0 is the start; reading the input character by character, you follow transitions, and you match if you end in an accept state.
  2. Operations.run(a, s) does exactly that walk for a deterministic automaton and returns true or false. It is a convenience method; RunAutomaton is the fast version.
  3. An automaton that matches nothing has the empty language. Lucene usually represents it with no states at all: Automata.makeEmpty() returns one, and so do operations whose result matches nothing, such as repeating the empty language.

The finding, step by step

#
  1. Build an automaton that matches nothing with documented operations: Automaton a = Operations.repeat(Automata.makeEmpty(), 2, 2); (two repetitions of the empty language). It is deterministic and has 0 states.
  2. Ask Operations.run(a, "x"). You expect false: the javadoc promises a boolean for any deterministic automaton, and Operations.run(Automata.makeEmpty(), "x"), the same empty language, returns false.
  3. Instead it throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0, with assertions on and off. run starts at state 0 and reads states[0] without checking that the automaton has a state.
  4. Why one empty automaton works and the other throws: new Automaton(), behind makeEmpty(), sizes its state array for 2 states, so slot 0 holds zeros that read as "no transitions". Automaton.Builder.finish(), which repeat uses, sizes it exactly: 0 states, length 0.
  5. Only code that calls Operations.run itself is hit: queries go through CompiledAutomaton, which replaces a 0-state automaton first. All 108 releases from 5.0.0 to 10.6.0 and main fail.

Who is affected

#

Only applications that call the public Operations.run themselves on an automaton that came out empty through Automaton.Builder, such as a never-matching bounded repeat like #{2}. No Lucene code outside tests calls run, and queries are guarded by CompiledAutomaton. The call fails loudly: no wrong answer, nothing written. No setting is involved; rare.

Mechanism, terms and numbers469 words

Operations.run(Automaton, String) and run(Automaton, IntsRef) (lucene-core, public static, @lucene.experimental class) answer whether a deterministic automaton accepts an input; the javadoc's only precondition is "The input must be deterministic" (Operations.java:882). Both start at state = 0 and call a.step(0, label) without checking a.getNumStates() (:890-892, :911-913), and Automaton.next reads states[2 * state] (Automaton.java:694). Lucene's empty language normally has 0 states. Automata.makeEmpty() is backed by new Automaton(), which reserves 2 zero-filled state slots, so run returns false. Automaton.Builder.finish() allocates exact-size arrays (:891-894), so a 0-state automaton built through it, for example Operations.repeat(Automata.makeEmpty(), 2, 2), new RegExp("#{2}").toAutomaton() or new RegExp("(a&b){2}").toAutomaton(), has a state array of length 0 and run(a, "x") throws ArrayIndexOutOfBoundsException, with assertions on and off. The exact-size allocation came with LUCENE-5959 (2014-09-18), so every release from 5.0.0 to 10.6.0 is affected. A getNumStates() == 0 guard in both overloads fixes it (validated). Low impact: no Lucene code outside tests calls run, and queries are guarded by CompiledAutomaton.

The bug

#
  1. run(Automaton, String) (Operations.java:888-899) sets int state = 0; (:890) and calls a.step(state, cp) for the first character (:892). There is no a.getNumStates() check. run(Automaton, IntsRef) (:909-920) is the same, step at :913.
  2. Automaton.step calls next(state, 0, label, null) (Automaton.java:657-658). next asserts only state >= 0 and label >= 0, then reads states[2 * state] (:690-694).
  3. new Automaton() ("creates an automaton with no states", :79-82) calls this(2, 2), so its state array has room for 2 states and is zero-filled. Automata.makeEmpty() is new Automaton() plus finishState() (Automata.java:55-60). Reading slot 0 gives "0 transitions", step returns -1 and run returns false.
  4. Automaton.Builder.finish() ("Create automaton with the correct size.", :891) calls new Automaton(numStates, numTransitions) (:894), which allocates states = new int[numStates * 2] (:92). With 0 states that is a zero-length array, so states[0] throws.

How the repro gets there

#

Operations.repeat(a, 2, 2) concatenates two copies of a; concatenate returns makeEmpty() for an empty operand (Operations.java:79-82). repeat then copies that into a Builder and returns removeDeadStates(builder.finish()) (:322); removeDeadStates returns its input unchanged when every state is live (:1010, here 0 of 0). RegExp turns {n,m} into the same call (RegExp.java:672-674), and new RegExp(String) enables # (the empty language) and & by default, so #{2} and (a&b){2} take the same path.

The numbers

#

Throw, with assertions on and off: repeat(makeEmpty(), 2, 2), repeat(makeEmpty(), 1, 1), RegExp("#{2}"), RegExp("(a&b){2}"), new Automaton.Builder().finish(). Return false: makeEmpty() and RegExp("(a&b){2,}"), also 0 states, with spare capacity. run(a, "") returns false for all of them, because no step is taken; any non-empty input throws. The IntsRef overload behaves the same.

Exposure and likelihood187 words
  • Who is hit. Code that calls Operations.run(Automaton, String) or run(Automaton, IntsRef) on an automaton whose language is empty in its exact-size 0-state form: Operations.repeat of an empty operand, a RegExp with a bounded repeat of an empty sub-expression (#{2}, (a&b){2}), or an empty Automaton.Builder.
  • Who is not hit. Lucene itself: no Lucene code outside tests calls Operations.run (grep of lucene/*/src/java), so analyzers and index files never reach it. AutomatonQuery, RegexpQuery, WildcardQuery, PrefixQuery and TermRangeQuery build a CompiledAutomaton, which replaces a 0-state automaton with a 1-state one first (CompiledAutomaton.java:154-157).
  • What happens. One ArrayIndexOutOfBoundsException in the caller's thread, from inside Automaton, instead of false.
  • What does not happen. No wrong answer, no hang, no memory growth, no index involvement; the automaton is not changed.
  • Default vs opt-in, scale. No setting is involved; the trigger is exactly "0 states, built through Builder.finish()", independent of data size. Deterministic, the same with -ea and -da.
  • How likely. Rare: an empty language is an edge case, and no report of this failure was found in the searches below.

Why it looks unintended

#
  • The javadoc's only precondition is "The input must be deterministic.", and the automaton is deterministic.
  • 0 states is Lucene's normal empty language: run returns false for Automata.makeEmpty(), and Lucene's own TestAutomaton asserts exactly that; only the exact-size copy throws.
  • Precedent: LUCENE-6054 fixed a 0-state failure in Operations.repeat, and #13721 added a 0-state guard to FiniteStringsIterator.
The full argument258 words
  • Contract. Operations.java:882: "Returns true if the given string is accepted by the automaton. The input must be deterministic." isDeterministic() is true for the repro automaton, and the -ea assert at :889 passes.
  • A documented value. Automata.makeEmpty(): "Returns a new (deterministic) automaton with the empty language." (Automata.java:55), with 0 states; new Automaton(): "creates an automaton with no states" (Automaton.java:79).
  • Operations already handles 0 states elsewhere: concatenate (Operations.java:79), repeat(a) (:202), intersection (:396-399), union (:492), isEmpty ("Common case: no states", :800-801) and topoSortStates (:1366).
  • Capacity, not language, decides. makeEmpty() answers false; the equal automaton from repeat(makeEmpty(), 2, 2) throws.
  • Precedent. LUCENE-6054 (#7116, 54156c042d4, 2014, "allow repeating the empty automaton") fixed a 0-state failure (an AssertionError) in Operations.repeat. #13721 (4c27bccac54, 2024) added assert state < getNumStates() to Automaton.getNumTransitions and, in the same commit, a 0-state guard in FiniteStringsIterator.
  • Lucene's own test expects false. TestAutomaton.testMakeBinaryIntervalRandom (TestAutomaton.java:1478-1512) runs Operations.run(a, IntsRef) on intervals from Automata.makeBinaryInterval, which returns makeEmpty() (0 states) for an empty interval (Automata.java:315-324, :340-342), and asserts false for every term (:1511). A copy of that loop got a 0-state automaton in 64 of 100 iterations: 32,000 run calls, all false, with -ea and -da. It passes only because makeEmpty() has spare slots. No upstream test was found that runs an exact-size (Builder-built) 0-state automaton through run, and the introducing issue (#7021, LUCENE-5959) never discusses 0-state automata.
The devil's-advocate check191 words

The strongest case for "not a bug": the Automaton class javadoc says "State 0 is always the initial state" (Automaton.java:37-38), so an automaton with no states has no start and could be read as outside run's domain; run is a convenience method ("for full performance, use the RunAutomaton class", Operations.java:886) with no production caller; Operations is @lucene.experimental (:56); and maintainers recently deprecated a helper in Operations and copied it to the test utilities (#15755, "Deprecate Operations.minus() and move to test utilities"; minus is still at Operations.java:375-376, marked @Deprecated), so they might answer "move run to the test utilities".

Why it fails: no javadoc makes "has a state" a precondition of run; Lucene's own documented empty automaton has no states, and run already answers false for it; an answer that flips on hidden array capacity is not a design. The other points lower the severity, not the validity. Moving run is a legitimate fix choice (option D), and the repro accepts it; a maintainer could also reasonably ask for one 0-state policy across the automaton consumers instead of a fix in run alone.

Suggested fix

#

Recommended Guard both run overloads

Return false from both run overloads when a.getNumStates() == 0 (3 lines each). Validated: the test then passes with assertions on and off, the 239 tests of org.apache.lucene.util.automaton (0 failures) and TestTermsEnum2 pass, and the format check is clean.

  public static boolean run(Automaton a, String s) {
    assert a.isDeterministic();
    if (a.getNumStates() == 0) {
      return false;
    }
    int state = 0;
    // ... unchanged; the same three lines go into run(Automaton, IntsRef)
All options and trade-offs4 options · 491 words

Four options. A was run; B, C and D were not. A fixes only Operations.run. B (a guard in Automaton's private next) or C would also cover the same input shape in the RunAutomaton constructor (LFV-029). LFV-865 (AutomatonToTokenStream) fails on makeEmpty() as well: it sizes its own indegree[] from the state count and reads indegree[0] without calling step or next (AutomatonToTokenStream.java:52-61), so it needs its own guard. Operations.getSingleton (Operations.java:1207-1237) has the same missing guard; that half was reported downstream (elastic/elasticsearch#128813, worked around in #128895).

Guard both run overloads (validated by the checks) (recommended)

#

In run(Automaton, String) and run(Automaton, IntsRef), return false before the first step when the automaton has no states (+6 lines in Operations.java). It matches how Operations already treats 0 states (isEmpty, concatenate, topoSortStates) and how #13721 fixed FiniteStringsIterator.

  public static boolean run(Automaton a, String s) {
    assert a.isDeterministic();
    if (a.getNumStates() == 0) {
      return false;
    }
    int state = 0;
    // ... unchanged; the same three lines go into run(Automaton, IntsRef)

Trade-offs

One int comparison per call. Fixes only Operations.run; the RunAutomaton constructor (LFV-029), AutomatonToTokenStream (LFV-865) and getSingleton keep their own failures.

Guard in Automaton's private next

#

Return -1 from the private next(int, int, int, Transition) (Automaton.java:690) when state >= getNumStates(). Both step and the public next(Transition, int) (:675-677) go through it.

Trade-offs

Would also cover the RunAutomaton constructor (LFV-029), which fails at next:694 <- next:676 <- RunAutomaton.<init>:80; a guard in step alone would not. It does not reach AutomatonToTokenStream (LFV-865). Adds a branch to a shared accessor and hides reads of a state that does not exist. Not run.

Give Builder.finish() the spare capacity of new Automaton()

#

Allocate at least 2 state slots in Automaton(int, int) or in Builder.finish().

Trade-offs

Makes every exact-size 0-state automaton behave like makeEmpty(), which also fixes the RunAutomaton constructor (LFV-029); AutomatonToTokenStream (LFV-865) fails on makeEmpty() too and is not helped. It only hides the read of a nonexistent state and changes a shared constructor for an Operations problem. Not run.

Document the precondition, or move run to the test utilities

#

Say "the automaton must have at least one state" in the javadoc, or move run to the test utilities as #15755 did for minus() (deprecated in Operations, copied to the test utilities).

Trade-offs

Smallest code change, but leaves a public method that throws an index error on Lucene's own empty automaton (javadoc), or removes a public API (move). Not run.

Downstream note

#

An application that runs a user's regular expression through RegExp and then calls Operations.run itself gets an exception instead of "no match" for a pattern like #{2}; a downstream search engine hit the same missing guard in the sibling Operations.getSingleton this way (elastic/elasticsearch#128813).

How it was found

#

Semi-formal: a proof-obligation check of the Operations contract. run must answer true or false for every deterministic automaton, and the empty language is a documented deterministic automaton with 0 states; the failed obligation was then shown with an executable test on the stock main jars.

The method in full91 words

Method: semi-formal, a proof-obligation check of the Operations contract, witnessed by an executable repro (2026-11-03, main 5adff78bb168).

  • The obligation: run's javadoc requires only determinism and promises a boolean, so run must be defined on every deterministic automaton, including the documented 0-state empty language.
  • Discharging it against the code fails: both overloads read state 0 unconditionally, and whether that read is safe depends on the array capacity, which Builder.finish() makes exact.
  • The witness is the one-test repro above, run on the stock main jars with assertions on and off.
