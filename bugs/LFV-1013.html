Four Lucene test methods never run: their names start with "tes" or "Test" instead of "test"

Four methods in Lucene's own tests are spelled tes... or Test... instead of test..., so the runner silently skips them (the TestXYRectangle pair in every release since 8.5.0). Two would fail if run: they expect 5 > 4, but XYRectangle says 5.0 > 4.0, so its reversed-bounds check has no running test.

The finding in 30 seconds

#

Lucene's test runner decides what is a test from the method name alone.

  1. TestXYRectangle declares 7 public no-arg test methods, all with assertions. Two are spelled tesInvalidMinMaxX and tesInvalidMinMaxY: one t short.
  2. Run ./gradlew :lucene:core:test --tests org.apache.lucene.geo.TestXYRectangle. You expect 7 tests; gradle runs 5. Asking for TestXYRectangle.tesInvalidMinMaxX by name ends with "no tests matched the provided --tests filters".
  3. Why: Lucene's runner takes only public no-arg methods whose names start with lowercase test, or that carry @Test. Two more methods miss it: TestOperations.TestOptionalOptionalAcceptsState0 (23 of 24 run) and TestCommonGramsFilter.TestFirstAndLastStopWord (10 of 11).
  4. Rename the two XYRectangle methods and both fail: they check the message for 5 > 4, but new XYRectangle(5, 4, 3, 4) reports minX must be lower than maxX, got 5.0 > 4.0 because the bounds are floats. The library is right; the checks were stale from the day they were written (2020).
  5. The cost: no running test builds an XYRectangle with reversed bounds, so a regression in that check would go unnoticed. The other two dead methods repeat checks that running tests already make.

Who is affected

#

Only Lucene's own test suite: normal test runs, local or CI, skip the four methods: the TestXYRectangle pair in every release since 8.5.0, TestOptionalOptionalAcceptsState0 since 10.2.0 and TestFirstAndLastStopWord since 4.0.0-alpha. No shipped jar, API or index is affected. The real loss is coverage of XYRectangle's reversed-bounds IllegalArgumentException, which no running test checks.

Mechanism, terms and numbers462 words

Lucene's test runner treats a method as a test only if it is public, non-static, takes no arguments and its name starts with lowercase test, or if it carries @Test. Four methods in Lucene's own test sources miss that by one letter: TestXYRectangle.tesInvalidMinMaxX and tesInvalidMinMaxY, TestOperations.TestOptionalOptionalAcceptsState0 and TestCommonGramsFilter.TestFirstAndLastStopWord. Every test run skips them silently: gradle runs 5, 23 and 10 tests for the three classes instead of 7, 24 and 11. Renamed, the two TestXYRectangle methods fail, because they look for 5 > 4 in a message that reads minX must be lower than maxX, got 5.0 > 4.0. No shipped code is wrong; the real loss is that XYRectangle's reversed-bounds IllegalArgumentException has had no running test since it was added in 2020.

How Lucene finds tests

#

LuceneTestCase registers two method providers, @TestMethodProviders({LuceneJUnit3MethodProvider.class, JUnit4MethodProvider.class}) (LuceneTestCase.java:114). The first keeps a method only if m.getName().startsWith("test"), it is public and non-static, and it takes no parameters (LuceneJUnit3MethodProvider.java:39-42); the second keeps @Test methods. The class javadoc says the same: "Any test method with a testXXX prefix is considered a test case. Any test method annotated with [org.junit.Test] is considered a test case." (LuceneTestCase.java:90-91). Anything else is silently ignored.

Why the two XYRectangle checks are stale

#

XYRectangle(float minX, float maxX, float minY, float maxY) throws new IllegalArgumentException("minX must be lower than maxX, got " + minX + " > " + maxX) (and the minY twin) from a plain if (XYRectangle.java:36-44). Java prints the float 5 as 5.0, so the message is got 5.0 > 4.0 and contains("5 > 4") is false. LUCENE-9218 made the bounds floats in the same commit that added the exception and these two tests, so the checks never matched in any version.

Why nothing catches it

#

Lucene's build turns off error-prone's JUnit3TestNotRun ("we don't use junit3") and JUnit4TestNotRun ("noisy") (ErrorPronePlugin.java:542, :548); per error-prone's documentation the former looks only at junit.framework.TestCase subclasses anyway, and whether the latter would flag these methods under Lucene's RandomizedRunner is unknown (neither was tested). The JUnit 5 base class checks test* methods for @Test (LuceneTestCaseJupiter.java:608-634), but only for Jupiter tests and only for names that already start with test.

Exposure and likelihood236 words
  • Who. Lucene developers and CI. No user configuration or API is involved, and test sources are not in the released jars.
  • What is lost. The two TestXYRectangle methods are the only tests that build an XYRectangle with reversed bounds; every other new XYRectangle(...) in the test trees passes ordered bounds. If that check regressed (for example back to an assert, as it was before 8.5.0), no running test would notice.
  • What is not lost. TestFirstAndLastStopWord ("the of" gives ["the_of"]) repeats the case that the running testCommonGramsQueryFilter already checks with two common words in the other order ("of the" gives ["of_the"], TestCommonGramsFilter.java:105). TestOptionalOptionalAcceptsState0 adds nothing beyond the running testOptionalAcceptsState0 and testOptionalOptional. Both dead bodies pass when run under new names, so they hide no product bug.
  • Scale. Two name scans find exactly these four: the finder's over every lucene/**/src/test tree, sandbox included (public no-arg void methods whose names start with tes, tset, tets, tst, Test, TEST or Tset but not with test), and an independent verifier's over the non-sandbox trees (Test[A-Z]*, tes[^t]*, tset*, tets*, tst*, est[A-Z]*). They look for near-miss spellings only. Public no-arg methods that never run on purpose do exist, for example the compile-only TestAnalyzers._testStandardConstants (LUCENE-1150 comment, @SuppressWarnings("unused")).
  • Library behaviour. Correct: XYRectangle rejects reversed bounds with assertions on and off; Operations.optional and CommonGramsQueryFilter work.

More files, environment, full output359 words

The test compiles the checkout's own, unmodified TestXYRectangle, TestOperations and TestCommonGramsFilter and calls Request.aClass(c).getRunner().getDescription() for each: that builds Lucene's RandomizedRunner (from LuceneTestCase's @RunWith) and lists the tests it would run, without running them. Every declared public, non-static, no-arg method that is not in that list is reported. Apart from their test methods the three classes declare no public no-arg instance methods, so the list should be empty (true for these three classes; it is not a general rule). d.isSuite() covers -Dtests.iters > 1, where the runner groups each method's repetitions under a suite named after the method (checked with 5 iterations).

The test classes of two modules are compiled together, so the command runs outside gradle, against the checkout's built jars of lucene-core, -codecs, -test-framework and -analysis-common plus junit 4.13.2, randomizedtesting-runner 2.9.2 and hamcrest 3.0 ($DEPS, the versions in gradle/libs.versions.toml).

No separate regression test is suggested: once renamed, the four methods are running tests themselves. The minimal test passes with the fix.

Why it looks unintended

#
  • Written as tests: javadoc such as "maxX must be gte minX", assertion-only bodies, no callers, no @Ignore or @AwaitsFix.
  • Misnamed at creation, next to correctly named siblings: #14218 split a running testOptional into four methods and named one TestOptional....
  • Lucene's JUnit 5 base class checks test* methods "so that they're not silently ignored".
The full argument216 words
  • Written as tests. tesInvalidMinMaxX / Y carry the javadoc "maxX must be gte minX" / "maxY must be gte minY"; TestFirstAndLastStopWord carries "Test CommonGramsQueryFilter when first and last words are stopwords."; all four bodies are assertions only (expectThrows, assertMinimalDFA, assertTokenStreamContents), and no code calls them. Lucene's test code disables tests on purpose with 49 active @AwaitsFix / @Ignore annotations; none of the four has a marker.
  • History shows typos. LUCENE-9218 (4a54ffb553ad, apache/lucene-solr#1252, 2020) created TestXYRectangle with the two tes methods next to four correctly named siblings (testNaN, testPositiveInf, testNegativeInf, testEqualsAndHashCode). #14218 (de1ed71261d5, 2025, "Clean up more dead states creation by Automata/Operations"; its commit message lists "split some large tests into smaller tests for easier management") split the running testOptional into four methods; three got test, one got Test. TestFirstAndLastStopWord came with SOLR-1674 (2009) and kept its name through the move into Lucene (LUCENE-2413, 2010) and the 2021 class rename (LUCENE-8626).
  • Precedent. LUCENE-2037 (db067550e89, 2010) added a check because "i found lots of tests that simply forgot to add @Test and were never ran"; a 2010 commit (d1ecb22f8a9) renamed tesStopwordsParsing to testStopwordsParsing; LuceneTestCaseJupiter enforces @Test on test* methods "so that they're not silently ignored" (LuceneTestCaseJupiter.java:610).
The devil's-advocate check154 words

Strongest case for "not a bug": the runner and XYRectangle work exactly as documented; LuceneTestCase never promises to run every public no-arg method, and a public method may be a helper; the exact exception text is not a contract; two of the four methods are redundant. The first cross-model reviewer (refute lens) returned "not real" on these grounds, at medium confidence and partly on procedure (it could not run Java).

Why it fails: nobody claims the runner is wrong; the defect is in the test sources. The same reviewer wrote that "static review nevertheless strongly indicates accidental test-name typos" and that the renames and message fixes "look appropriate". A helper would not carry test javadoc and assertion-only bodies, and nothing marks the methods as disabled. The exact text matters only because the tests' own assertion checks it. Redundancy narrows the impact but does not make the names intended. Verdict: a minor, test-only defect (adjudication).

How it was found

#

Code reading, no formal method. While an AI tool was checking XYRectangle's input validation in a sweep of assert-only input checks, it noticed the tes prefix; two independent name scans of the test trees found the same four. Runs of the unmodified and the renamed classes confirmed it.

The method in full163 words
  • Context. A hunt unit swept Lucene for input checks that exist only as assert. Reading TestXYRectangle to see how XYRectangle's bounds checks are tested, the finder noticed that tesInvalidMinMaxX and tesInvalidMinMaxY cannot run.
  • Widening. The finder's scan of every lucene/**/src/test tree, sandbox included, for public no-arg void methods whose names start with tes, tset, tets, tst, Test, TEST or Tset but not with test found exactly four. An independent verifier's scan of the non-sandbox test trees with its own patterns (Test[A-Z]*, tes[^t]*, tset*, tets*, tst*, est[A-Z]*) found the same four. Both match name patterns only.
  • Confirmation. The unmodified classes ran 5, 23 and 10 tests with none of the four; renamed copies ran 42 tests with only the two XYRectangle checks failing; the corrected checks passed.
  • Tier. Non-formal: the first signal was reading a test and the widening was a text scan; no model or bounded check was involved.
