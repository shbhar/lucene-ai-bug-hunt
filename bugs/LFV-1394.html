QueryBitSetProducer ignores in-place doc-values updates, so a reused block-join sort child filter keeps its old children

QueryBitSetProducer caches each segment's bit set under the segment's core key, which an in-place doc-values update does not change, and never asks Weight#isCacheable. So a ToParentBlockJoinSortField child filter on an updated field keeps its old children after a reopen: parents sort B A instead of A B, silently.

The finding in 30 seconds

#

QueryBitSetProducer.getBitSet looks up and stores each segment's bit set under the core key and returns a hit as is. It never calls Weight#isCacheable, which for a doc-values query is false once the field has been updated, and which LRUQueryCache checks for exactly this reason. So the reopened segment gets the old children.

Background: block-join sorting and QueryBitSetProducer

#
  1. Block join stores each parent right after its children in one segment. ToParentBlockJoinSortField sorts parents by a child field: each parent takes the lowest (or highest) value among the children that the child filter selects.
  2. The filters are BitSetProducers. QueryBitSetProducer, the only one Lucene ships, runs a query once per segment and caches the bit set of matching documents, keyed on the segment's core.
  3. An in-place doc-values update (updateNumericDocValue) changes one doc-values-only field without rewriting the segment. The reopened reader shares the old segment core, so the core key stays the same.

The finding, step by step

#
  1. Index parent A with children a1 (price 10, in stock) and a2 (price 1, out of stock), and parent B with child b1 (price 5, in stock). Sort parents by their lowest in-stock child price: ToParentBlockJoinSortField with the child filter new QueryBitSetProducer(newSlowExactQuery("stock", 1)). A = 10, B = 5, so B A.
  2. Put a2 back in stock with updateNumericDocValue(id:a2, stock=1), commit, reopen with DirectoryReader.openIfChanged, and search again with the same Sort.
  3. You expect A B: A's lowest in-stock price is now 1.
  4. You get B A. The reopened segment keeps its core key, so the producer returns the bit set it cached for the old reader. It never asks the query's Weight, which says "not cacheable" once the field has been updated.
  5. No error. A new producer, or a reader opened fresh from the directory, gives A B; with the reused producer the old order stays until the segment is merged away.

Who is affected

#

Applications that reuse a QueryBitSetProducer over a query on a doc-values-only field across an in-place update of that field and a reopen (commit + openIfChanged, NRT or SearcherManager). Inside Lucene that is the experimental ToParentBlockJoinSortField child filter: parents sort wrongly on every search until a merge; direct getBitSet calls get the same stale bits. Parents filters are unaffected.

Mechanism, terms and numbers574 words

QueryBitSetProducer caches each segment's bit set under reader.getCoreCacheHelper().getKey() (QueryBitSetProducer.java:63-68, :84-86). An in-place doc-values update (IndexWriter#updateNumericDocValue, updateBinaryDocValue, updateDocValues) does not change that key: LeafReader#getCoreCacheHelper says readers with different doc-values updates may be considered equal and points to getReaderCacheHelper for that case (LeafReader.java:65-70). The query that reads the updated field knows it: its Weight#isCacheable is false once the field has updates (SortedNumericDocValuesRangeQuery.java:119-120, DocValues.java:340-346), and LRUQueryCache asks (LRUQueryCache.java:816, :903). QueryBitSetProducer never asks, so after an update and a reopen that shares the segment core it returns the bit set computed before the update.

Inside Lucene the visible effect is in the experimental ToParentBlockJoinSortField, whose childFilter "defines which child documents participates in sorting": parents are sorted by the pre-update children, silently, on every search, until the segment is merged or the application builds a new producer; a direct getBitSet call (the minimal test) gets the same stale bits. It has been so since QueryBitSetProducer was created in 5.3.0 (2015). The recommended fix keeps today's fast path on leaves without doc-values updates and asks the Weight only on leaves with them.

  • The key does not see updates. LeafReader#getCoreCacheHelper: "Two readers that have the same data but different sets of deleted documents or doc values updates may be considered equal. Consider using getReaderCacheHelper if you need deletions or dv updates to be taken into account" (LeafReader.java:65-70). An independent reproduction asserted on an NRT reopen that the reopened leaf keeps the same core key; the fact check asserted the same after commit + openIfChanged.
  • The query says "do not cache". NumericDocValuesField.newSlowExactQuery is a SortedNumericDocValuesRangeQuery (NumericDocValuesField.java:144-146) whose Weight returns DocValues.isCacheable(ctx, field) (SortedNumericDocValuesRangeQuery.java:119-120), false once the field has a doc-values generation (DocValues.java:340-346). SegmentCacheable.java:30-32: "Objects that depend on doc values should return DocValues#isCacheable ... Updated doc values fields are not suitable for caching."
  • Of the two caches here, only LRUQueryCache asks. Both LRUQueryCache and QueryBitSetProducer key on the core; LRUQueryCache checks in.isCacheable(context) before using its cache (LRUQueryCache.java:816, :903); QueryBitSetProducer does not.
  • Where the stale bits land. ToParentBlockJoinSortField calls childFilter.getBitSet(context) for every leaf (ToParentBlockJoinSortField.java:224, :248, :278, :304, :343). The sort values themselves are read fresh, so updates of the sort field alone are never stale; only updates of a field the child filter reads are.
  • Only queries that read doc values can filter on such a field. In-place updates are allowed only for fields "indexed with doc values only" (IndexWriter.java:1951-1953), so a filter on such a field reads its doc values, for example: a slow doc-values query (newSlowExactQuery, newSlowRangeQuery, newSlowSetQuery); a FieldExistsQuery (whose Weight also returns DocValues.isCacheable for a doc-values field, FieldExistsQuery.java:277-286); a function query such as FunctionMatchQuery over DoubleValuesSource.fromLongField (its Weight returns source.isCacheable(ctx), FunctionMatchQuery.java:112-113, which is DocValues.isCacheable, DoubleValuesSource.java:610) or FunctionRangeQuery (never cacheable, FunctionRangeQuery.java:177-178); or a query that wraps one of them.
Exposure and likelihood336 words
  • All four conditions are needed: (1) a QueryBitSetProducer over a query on a doc-values-only field. Inside Lucene the only consumer that can be hit is a ToParentBlockJoinSortField (@lucene.experimental) child filter; an application that calls getBitSet directly (as the minimal test does) or passes the producer to its own code gets the same stale bits. (2) An in-place update of that field. (3) A reopen that shares the segment core: commit + openIfChanged, NRT openIfChanged(reader, writer) and SearcherManager were all executed. (4) The same producer kept across the reopen, which is natural for the sort because it is built once with the Sort. Default IndexWriterConfig, codec, directory and searcher.
  • Effect (sort): a wrong parent order, deterministic, on every search once the conditions hold, until the segment is merged into a new one or the application builds a new producer or opens a new reader from the directory. No error. QueryBitSetProducer caches every segment on first use, with no size or frequency policy, so unlike the query cache the stale result is not limited to large or frequently used segments.
  • Measured scope: a bounded-exhaustive run of the real jar over every index of 2 blocks with 1-2 children each (price in {1, 2, 3}, stock in {0, 1}) and every single in-place update, 19,656 cases: the reused producer gives a stale order in exactly the 2,196 of 6,552 child-filter-field updates whose correct order changes, and never for updates of the sort field; 0 stale with either fix.
  • Not affected: every other BitSetProducer consumer in Lucene (ToParentBlockJoinQuery, ToChildBlockJoinQuery, ParentChildrenBlockJoinQuery, ParentsChildrenBlockJoinQuery, CheckJoinIndex, the diversifying-children kNN queries) takes a parents filter, which is structural: an in-place update cannot meaningfully change which documents are block parents.
  • Downstream (read only, not executed): Elasticsearch and OpenSearch use QueryBitSetProducer only in test code and do not use ToParentBlockJoinSortField. Solr is a plausible route (see the downstream note).
  • No matching report was found in the searches below (the class has existed since 5.3.0, 2015).

Why it looks unintended

#
  • BitSetProducer#getBitSet must return "a BitSet matching the expected documents on the given segment"; on the reopened segment those are different documents.
  • SegmentCacheable: "Updated doc values fields are not suitable for caching"; LRUQueryCache follows it, and TestLRUQueryCache#testDocValuesUpdatesDontBreakCache asserts it.
  • LUCENE-8017/8042 (7.2.0) added that rule for the query cache and four join queries, but left QueryBitSetProducer's own cache unchanged.
The full argument193 words
  • Contract: BitSetProducer.java:27-30: "Produce a BitSet matching the expected documents on the given segment". childFilter: "Filter that defines which child documents participates in sorting" (ToParentBlockJoinSortField.java:63, also :83, :110, :147), a selection, not a structure.
  • The rule is general: SegmentCacheable.java:30-32; LeafReader.java:65-70 tells cache writers to use the reader key when doc-values updates matter.
  • Tests: TestLRUQueryCache#testDocValuesUpdatesDontBreakCache (TestLRUQueryCache.java:2222) asserts that the core-keyed query cache stops serving a segment after a doc-values update ("second segment no longer cached due to DV update"). TestBlockJoinSorting uses subset child filters (PrefixQuery on field2 at :215, filter_1:T at :285-286). No test under lucene/join/src/test performs an in-place update.
  • History: LUCENE-8017 (#9065) and LUCENE-8042 (#9090) introduced Weight#isCacheable, SegmentCacheable and DocValues.isCacheable because core-keyed caching of doc-values queries goes stale after an update; their commits (master a886a001a4c / 276e317e942, first released in 8.0.0; in 7.2.0 through the branch_7x commits 6f522dd66fe / 6e4f9a62e7c, which change the same files) changed LRUQueryCache and four join-module Weights (GlobalOrdinalsQuery, ParentChildrenBlockJoinQuery, PointInSetIncludingScoreQuery, TermsIncludingScoreQuery), not QueryBitSetProducer. No javadoc, CHANGES entry, test or discussion limits the class to data that cannot change.
The devil's-advocate check197 words

The strongest case for "intended": the class javadoc only promises to cache "per segment" (QueryBitSetProducer.java:35); the class was built (LUCENE-6649) for structural parents filters, where the core key is safe; the core key is documented to ignore doc-values updates; the sort field is experimental; and no report of it was found in eleven years.

Why it fails: "per segment" does not say results may go stale, and the interface contract is about the documents that match; the LeafReader note is advice to cache writers, not a documented limit of this class; the childFilter parameter is documented as a selection and upstream tests use it that way; QueryBitSetProducer is the only BitSetProducer Lucene ships, so users are steered to it; and the 7.2.0 work treated exactly this staleness as a defect for the query cache. Verdict: not intended. Remaining risk: maintainers may prefer a javadoc warning, because every fix costs something (the simplest a Weight per call; the recommended one a per-call FieldInfos loop and a Weight per call on updated leaves, which include leaves with soft-deleted documents); and the 7.2.0 work may have left this class alone on purpose: no record found says either way.

Suggested fix

#

Recommended Ask the Weight only on leaves with doc-values updates

Keep today's core-keyed fast path while the leaf has no doc-values updates; on a leaf with updates, build the Weight and use the cache only if weight.isCacheable(context), as LRUQueryCache does (1 file, +33/-9). Validated with gradle: the test passes with assertions on and off, and so does the whole join test suite (105 tests, 3 skipped).

// The core cache key does not change when doc values are updated in place. On a leaf with such
// updates, only use the cache if the weight says its result is cacheable, like LRUQueryCache.
Weight weight = null;
boolean cacheable = cacheHelper != null;
if (cacheable && hasDocValuesUpdates(reader)) {   // any FieldInfo with getDocValuesGen() != -1
  weight = createWeight(context);
  cacheable = weight.isCacheable(context);
}
// then look up and store only if cacheable; on a miss, build the Weight if not built yet
All options and trade-offs4 options · 630 words

Four options. A was applied in a scratch worktree of 5adff78bb168 and validated with gradle. B was validated earlier with standalone JUnit runs (the class shadowed) and the bounded-exhaustive run, not with gradle and not with the full join suite.

Ask the Weight only on leaves with doc-values updates (validated by the checks) (recommended)

#

Before the lookup, check whether any FieldInfo of the leaf has getDocValuesGen() != -1. If so, build the Weight first and use the cache only when it says the leaf is cacheable; otherwise keep the current path.

// The core cache key does not change when doc values are updated in place. On a leaf with such
// updates, only use the cache if the weight says its result is cacheable, like LRUQueryCache.
Weight weight = null;
boolean cacheable = cacheHelper != null;
if (cacheable && hasDocValuesUpdates(reader)) {   // any FieldInfo with getDocValuesGen() != -1
  weight = createWeight(context);
  cacheable = weight.isCacheable(context);
}
// then look up and store only if cacheable; on a miss, build the Weight if not built yet

Trade-offs

  • A loop over the leaf's FieldInfos on every call. On a leaf with updates, a rewrite and a Weight per call, and any filter whose Weight is not cacheable there is rebuilt on every call: the updated child filter, but also, for example, a BooleanQuery with more than 16 clauses, which reports not cacheable as a query-cache policy (BooleanWeight.java:273-280).
  • Soft deletes count as doc-values updates: with setSoftDeletesField, a segment with soft-deleted documents has a doc-values generation on the soft-deletes field (executed by the fact check), so it takes this slower path for every producer, parents filters included; the cache is still used where the Weight is cacheable.
  • Bit sets cached before the update stay in the map under the old key until the core closes. Leaves without updates behave exactly as today. No benchmark was run.

What the checks validated

  • The test fails before the change and passes after it, assertions on and off (gradle, seed DEADBEEF).
  • With the change, the whole :lucene:join:test passes: 17 classes, 105 tests, 3 skipped, 0 failures, assertions on and off.
  • :lucene:join:checkGoogleJavaFormat: clean for the change (it flags only the test's comment line).
  • An earlier, unformatted form of the same change also passed the sort-level test and the bounded-exhaustive run (0 stale of 19,656 cases).

Always build the Weight first and use the cache only if it is cacheable (validated by the checks)

#

The simplest change: move the rewrite and createWeight above the lookup and guard both lookup and store with cacheHelper != null && weight.isCacheable(context).

Trade-offs

Adds a rewrite and a Weight to every call, cache hits included, and stops caching on every leaf for any filter whose Weight says not cacheable for reasons unrelated to doc values (the BooleanQuery case above), so such a parents filter would be rebuilt on every query.

What the checks validated

Validated earlier with standalone JUnit runs (the class shadowed), not with gradle: it passes the minimal test, the sort-level test, TestQueryBitSetProducer, TestBlockJoinSorting, TestBlockJoin and TestCheckJoinIndex, assertions on and off, and the bounded-exhaustive run (0 stale), assertions off.

On leaves with doc-values updates, key the cache on the reader key (not run)

#

Use getReaderCacheHelper().getKey() instead of the core key when the leaf has doc-values updates.

Trade-offs

Correct for any query without a per-call Weight, but every producer, parents filters included, rebuilds its bit set once per reopen of an updated leaf (also after deletes). Keying on the reader key everywhere is worse: every delete would rebuild the parents bit sets.

Javadoc only

#

Document that QueryBitSetProducer does not see in-place doc-values updates and that a new producer is needed per reader.

Trade-offs

Leaves the trap in place; only if maintainers reject A on cost.

Downstream note

#

Solr's childfield() sort keeps QueryBitSetProducer instances across searchers in its perSegFilter cache (as configured in Solr's _default configset, with solr.NoOpRegenerator), so a Solr collection that sorts by a child filter on a field it updates in place may hit this (read from Solr's code, not run).

How it was found

#

Semi-formal: a bounded comparison of block-join sort order with a reused and a fresh QueryBitSetProducer across an in-place update and a reopen, against a reference order, flagged it. A bounded-exhaustive run of the real jar (19,656 cases) then found the reused producer stale in exactly the cases whose correct order changes, and never with a fix.

History

#

Introduced with the class by LUCENE-6649 (10392b47024 on branch_5x, 2919e13adc7 on trunk, 2015-07-06), first released in 5.3.0. Fails on every release tried from 5.3.0 to 10.6.0 and on main; LUCENE-8017/8042 (7.2.0) added isCacheable but left this cache unchanged. Not fixed upstream.

Versions tested9 rows

Introduced by LUCENE-6649 "Remove dependency of lucene/join on Filter" (Adrien Grand, 2015-07-06; JIRA patch workflow, migrated as #7707, whose thread does not discuss doc-values updates): 2919e13adc7 on trunk and its branch_5x twin 10392b47024, in 5.3.0. It created QueryBitSetProducer with the per-segment cache keyed on reader.getCoreCacheKey(); git show -M --summary 2919e13adc7 records the file as a rename of BitDocIdSetCachingWrapperFilter at 51% similarity, whose cache it kept (the branch_5x twin records a new file). LUCENE-7410 (df6f8307230, 7.0.0) changed the key to getCoreCacheHelper().getKey(); LUCENE-8017/8042 (master a886a001a4c / 276e317e942; in 7.2.0 through the branch_7x commits 6f522dd66fe / 6e4f9a62e7c) added isCacheable and made LRUQueryCache ask, but did not change this class.

Older routes: the same staleness existed through the classes it replaced: BitDocIdSetCachingWrapperFilter in 5.0.0-5.2.1 and a user-chosen caching child filter from 4.6.0, the first release with in-place doc-values updates.

Not fixed upstream: QueryBitSetProducer.java is byte-identical on main b3b320e4f05; its last change is 804b5a1ba59 (#14297, 2025-02-26), a bit-set refactor; the only open PR that edits it (#16847) keeps the cache as is.

LFV-1394, snapshot of 2026-11-10

Registry title
QueryBitSetProducer caches each segment's bit set under the segment core key without asking Weight#isCacheable, so a reused ToParentBlockJoinSortField child filter keeps its old child selection after an in-place doc-values update and a reopen that shares the core: parents sort 'B A' instead of 'A B', with no error; since 5.3.0
Area
join / QueryBitSetProducer per-segment cache (the childFilter of ToParentBlockJoinSortField) and the SegmentCacheable contract
Priority
Low, rank 366: Parents come back in the wrong sort order with no error on every search once the trigger holds (the hits and counts stay correct), with default settings and no query cache, in every release since 5.3.0 and on main. The reach is narrow: it needs the experimental ToParentBlockJoinSortField with a child filter on a doc-values-only field that is updated in place, and the same QueryBitSetProducer kept across a reopen that shares the segment core, and no user report of it was found.
Impact class
silent wrong results
Impact note
Applications that sort parents with the experimental ToParentBlockJoinSortField, pass a child filter that reads a doc-values-only field (a QueryBitSetProducer over a slow doc-values query such as NumericDocValuesField.newSlowExactQuery, newSlowRangeQuery or newSlowSetQuery, or FieldExistsQuery on that field), update that field in place (IndexWriter#updateNumericDocValue, updateBinaryDocValue or updateDocValues) and keep the same producer across a reopen that shares the segment core (openIfChanged after a commit, NRT openIfChanged(reader, writer), SearcherManager) get parents ordered by the child selection from before the update, silently and on every search once these conditions hold (the producer caches every segment on first use, with no size or frequency policy), until the segment is merged into a new one or a new producer or a newly opened reader is used; default IndexWriterConfig, codec, directory and searcher; ordinary scale; parents filters (structural) and every other BitSetProducer consumer in Lucene are not affected; Solr's childfield() sort is a plausible route by reading only (not executed).
Summary
You sort parent documents with ToParentBlockJoinSortField by the lowest price among in-stock children, using new QueryBitSetProducer(NumericDocValuesField.newSlowExactQuery("stock", 1)) as the child filter, then put one child back in stock with IndexWriter#updateNumericDocValue, commit and reopen with DirectoryReader.openIfChanged. You expect the reopened searcher to sort by the new selection ('A B': A's cheapest in-stock child now costs 1, B's costs 5), because the child filter defines which children take part and a query that reads updated doc values is not cacheable (SegmentCacheable). Instead QueryBitSetProducer returns the bit set it cached for the old reader under the segment core key, which an in-place doc-values update does not change, and never asks the Weight whether the result may be cached, so the parents still sort 'B A'; a fresh producer or a newly opened reader gives 'A B'.
