A FuzzyQuery wrapped in SpanMultiTermQueryWrapper is not capped at the clause limit, so it throws TooManyNestedClauses

FuzzyQuery keeps at most IndexSearcher#getMaxClauseCount terms (1024 by default) even when maxExpansions is larger, but wrapped in SpanMultiTermQueryWrapper it keeps up to maxExpansions terms, because the span rewrite's cap is Integer.MAX_VALUE, and the search throws TooManyNestedClauses. Every release since 9.0.0 has it; results are never wrong, the query just fails.

The finding in 30 seconds

#

One clause limit, two top-terms rewrites: the plain FuzzyQuery rewrite caps its terms at the limit, the span rewrite that SpanMultiTermQueryWrapper picks for it does not.

Background: the clause limit and top-terms rewrites

#
  1. IndexSearcher has one clause limit, getMaxClauseCount(), 1,024 by default. Since 9.0, IndexSearcher.rewrite counts every clause of the rewritten query, span terms included, and throws TooManyNestedClauses above it.
  2. A FuzzyQuery expands to the indexed terms close to its term. Its default rewrite keeps only the best min(maxExpansions, clause limit) terms, so it never trips the limit on its own.
  3. SpanMultiTermQueryWrapper lets a multi-term query such as FuzzyQuery be used inside span queries (SpanNearQuery, SpanFirstQuery, ...). For a top-terms rewrite it copies the size into its own span rewrite, TopTermsSpanBooleanQueryRewrite(size).

The finding, step by step

#
  1. Index 676 documents whose field f holds 1,326 different terms, all within two edits of abcde. Build new FuzzyQuery(new Term("f", "abcde"), 2, 0, 2000, true): up to 2,000 expansions.
  2. Search with it as is. FuzzyQuery documents that a maxExpansions above the clause limit (1,024 by default) is replaced by the limit, so it keeps the best 1,024 terms and counts 676 documents.
  3. Wrap the same query in SpanMultiTermQueryWrapper, for example to use it inside a SpanNearQuery. You expect the same 1,024 terms: the span rewrite's javadoc says it "will not overflow the boolean max clause count".
  4. Instead it keeps all 1,326 terms, and the search throws IndexSearcher$TooManyNestedClauses ("maxClauseCount is set to 1024"). The span rewrite's TopTermsRewrite delegate caps its size with getMaxSize(), which returns Integer.MAX_VALUE; the core top-terms rewrites return the clause limit there.
  5. Same with the default FuzzyQuery (50 expansions) once the application lowers the limit below 50: at limit 32 the plain query keeps 32 terms and runs, the wrapped one keeps 50 and throws.

Who is affected

#

Applications that use a span-wrapped FuzzyQuery (or another top-terms query) with maxExpansions above the clause limit, that lower the limit below the expansion size (below 50 even the default FuzzyQuery fails), or that set an explicit span top-N size above it. That request throws; results are never wrong. Opt-in shapes, rare.

Mechanism, terms and numbers501 words

FuzzyQuery documents that a maxExpansions above IndexSearcher#getMaxClauseCount is replaced by the limit, and its default top-terms rewrite does exactly that (TopTermsRewrite.rewrite keeps min(size, getMaxSize()) terms, and the core rewrites' getMaxSize() is the clause limit). SpanMultiTermQueryWrapper turns a top-terms rewrite into TopTermsSpanBooleanQueryRewrite(size) with the same size, documented as "will not overflow the boolean max clause count", but its TopTermsRewrite delegate returns Integer.MAX_VALUE from getMaxSize(), so it keeps up to maxExpansions terms. Since 9.0 (LUCENE-8811) IndexSearcher.rewrite counts every SpanTermQuery of the resulting SpanOrQuery and throws IndexSearcher$TooManyNestedClauses. So a FuzzyQuery(abcde, 2, 0, 2000, true) that keeps 1,024 of 1,326 matching terms and counts 676 documents on its own throws once span-wrapped; under a lowered limit (32) even the default FuzzyQuery (50 expansions) fails once wrapped. FrequentTermsSpanBooleanQueryRewrite (new in 10.6.0) has the same gap. The cap dates from 2010, when SpanOrQuery had no clause limit; the exception from 9.0.0. No wrong results, no index effect. The fix is two lines.

Terms

#
  • Clause limit: IndexSearcher.getMaxClauseCount(), 1,024 by default (IndexSearcher.java:80, :251-261). IndexSearcher.rewrite visits the rewritten query and throws TooManyNestedClauses when the clause count goes over it (:878, :916-920).
  • Top-terms rewrite: TopTermsRewrite keeps the best maxSize = Math.min(size, getMaxSize()) terms (TopTermsRewrite.java:64). The three core subclasses return the clause limit from getMaxSize() (MultiTermQuery.java:167-168, :212-213, :260-261). FuzzyQuery's default rewrite is one of them, TopTermsBlendedFreqScoringRewrite(maxExpansions) (FuzzyQuery.java:60-62; default maxExpansions 50, :56).
  • Span rewrites: SpanMultiTermQueryWrapper maps any TopTermsRewrite to new TopTermsSpanBooleanQueryRewrite(getSize()) (SpanMultiTermQueryWrapper.java:70-78). FrequentTermsSpanBooleanQueryRewrite(n) (#16484, 10.6.0) can be set explicitly.

The bug

#
  1. TopTermsSpanBooleanQueryRewrite's delegate overrides getMaxSize() with return Integer.MAX_VALUE; (SpanMultiTermQueryWrapper.java:208-211). TopTermsRewrite.rewrite then computes min(maxExpansions, Integer.MAX_VALUE): the clause limit is never applied, and the rewrite returns a SpanOrQuery of up to maxExpansions SpanTermQuerys.
  2. FrequentTermsSpanBooleanQueryRewrite keeps the best terms in PriorityQueue.usingComparator(maxSize, order) (:312-314) and turns its own clause check off (:326-329). No clause cap either.
  3. IndexSearcher.rewrite visits the SpanOrQuery (SpanOrQuery.java:87-93); each SpanTermQuery calls consumeTerms (SpanTermQuery.java:98-101), which counts one clause and throws TooManyNestedClauses once the count is over the limit (IndexSearcher.java:916-920). The check runs before the increment, so limit + 1 clauses pass and limit + 2 throw (open #10339, not part of this bug).
  4. The sibling default rewrite still states the 2010 premise: "we accept all terms as SpanOrQuery has no limits" (:169-171). Since 9.0 that is no longer true.

The numbers

#

Default limit 1,024; 676 documents with 1,326 distinct terms within two edits of abcde; FuzzyQuery(abcde, 2, 0, 2000, true): plain, 1,024 terms and 676 hits; span-wrapped, 1,326 span terms and TooManyNestedClauses. Limit 32, default FuzzyQuery: plain 32 terms; wrapped 50 terms, throws. maxExpansions 1024, 1025, 1026, 2000: plain always 676 hits; wrapped 676, 676, throws, throws. Explicit TopTermsSpanBooleanQueryRewrite(2000) and FrequentTermsSpanBooleanQueryRewrite(2000) on a 1,352-term prefix throw; a size equal to the limit works. Minimal repro: limit 2, four terms one edit from abcd: plain 2 hits, wrapped throws.

Exposure and likelihood187 words
  • Who is hit. Code that uses SpanMultiTermQueryWrapper around a FuzzyQuery or another top-terms multi-term query and either sets maxExpansions above the clause limit (relying on FuzzyQuery's documented cap), lowers the limit with IndexSearcher.setMaxClauseCount below the expansion size, or sets TopTermsSpanBooleanQueryRewrite(n) / FrequentTermsSpanBooleanQueryRewrite(n) with n above the limit.
  • What it takes. The expansion must really match more terms than the limit (+1, because of #10339). Ordinary span-wrapped fuzzy queries (50 expansions, default limit 1,024) are not affected.
  • What happens. Search, count and any other entry point that rewrites the query throw IndexSearcher$TooManyNestedClauses for that request, where the same query unwrapped runs with the capped expansion.
  • What does not happen. No wrong results; nothing in the index or the searcher is changed; the clause limit still holds.
  • Default vs opt-in. Default writer, codec and searcher settings, but every trigger needs a non-default size or a lowered limit on the spans API. No in-tree query parser builds this shape: no main source under lucene/queryparser names SpanMultiTermQueryWrapper or either span top-N rewrite (grep at 645d4fe14a20). Likelihood: rare; no user report was found in the nearly five years since 9.0.0.

Why it looks unintended

#
  • FuzzyQuery documents the cap ("the maxClauseCount will be used instead"); both span top-N rewrites say they "will not overflow the boolean max clause count".
  • Integer.MAX_VALUE dates from 2010, when SpanOrQuery had "no limits"; LUCENE-8811 began counting span clauses in 9.0 without touching spans.
  • The upstream test testFuzzy2 asserts that the wrapper honours maxExpansions.
The full argument306 words
  • Contract, in four javadocs. FuzzyQuery, @param maxExpansions: "the maximum number of terms to match. If this number is greater than IndexSearcher#getMaxClauseCount when the query is rewritten, then the maxClauseCount will be used instead." (FuzzyQuery.java:79-81). TopTermsRewrite constructor, which the span rewrite's delegate extends (the class is @lucene.internal, TopTermsRewrite.java:34): "NOTE: if IndexSearcher#getMaxClauseCount is smaller than size, then it will be used instead." (TopTermsRewrite.java:43-44). TopTermsSpanBooleanQueryRewrite: "only uses the top scoring terms so it will not overflow the boolean max clause count" (SpanMultiTermQueryWrapper.java:196-197). FrequentTermsSpanBooleanQueryRewrite, written in 2026: "retains only the most frequent terms so it will not overflow the boolean max clause count" (:258-259; also lucene/CHANGES.txt:519-521). On main BooleanQuery.Builder.add checks IndexSearcher.maxClauseCount (BooleanQuery.java:82): the only clause limit is IndexSearcher's.
  • Long-standing intent. Lucene 1.9's CHANGES: "FuzzyQuery can no longer throw a TooManyClauses exception. If a FuzzyQuery expands to more than BooleanQuery.maxClauseCount terms only the BooleanQuery.maxClauseCount most similar terms go into the rewritten query" (lucene/CHANGES.txt:21672-21675).
  • Upstream test. TestSpanMultiTermQueryWrapper.testFuzzy2 ("maximum of 1 term expansion") asserts that the wrapper honours a FuzzyQuery's maxExpansions (TestSpanMultiTermQueryWrapper.java:96-103).
  • History. Integer.MAX_VALUE comes from the wrapper's introduction (ac71ebc2371, LUCENE-2754, 2010), when SpanOrQuery had no clause limit ("we accept all terms as SpanOrQuery has no limits", 1d0515124e2, LUCENE-2757, still at :169-171). LUCENE-8811 (53f56fb7ad4, 9.0) made IndexSearcher count every clause, span terms included, and touched no span file; spans are not mentioned in #9855. That the check reaches span expansions is by design: on #9855 Alan Woodward asked to run the count after rewriting because "some multi-term queries can end up expanding into very large boolean combinations, and we should try and catch that". What was not revisited is the span top-N rewrites' own cap, which the core top-terms rewrites apply before the check.
The devil's-advocate check270 words

The strongest case for "intended" (rated moderate by the cross-model reviewers, partial by the study's intended-behaviour verifier): IndexSearcher.rewrite documents TooManyClauses for any query over the limit (IndexSearcher.java:868-869); LUCENE-8811 meant that check to catch large multi-term expansions; the span constructors promise only "at most size terms" (SpanMultiTermQueryWrapper.java:204, :305); the wrapper deliberately replaces FuzzyQuery's own rewrite with a span rewrite, so FuzzyQuery's cap describes a rewrite that does not run; TopTermsRewrite is @lucene.internal (TopTermsRewrite.java:34), so its NOTE is not part of the public span rewrite's contract, and its getMaxSize() javadoc says "for boolean rewrites" (:55-58); Integer.MAX_VALUE was a deliberate 2010 choice; and "boolean max clause count" could be read as BooleanQuery's only.

Why it fails: for the lead trigger the user never asks for more than the limit: they pass a maxExpansions that FuzzyQuery documents as capped, and the wrapper copies that size into its span rewrite (:72-74), which testFuzzy2 relies on. The two public span javadocs, not only the internal NOTE, say the rewrite "will not overflow", and on main there is no other "boolean max clause count" than IndexSearcher's. The check catching the expansion is intended; the span rewrite not capping before it is what differs from the core rewrites. The 2010 choice rested on "no limits", which 9.0 removed without revisiting spans. The argument keeps real weight for explicit span sizes above the limit, where a javadoc fix is a fair alternative (option C): a separate decision, not an equal defect. Verdict: not intended, a defect. Not security: the limit still holds and fails closed.

Suggested fix

#

Recommended A. Cap both span top-N rewrites at the clause limit, at rewrite time (two lines)

Make the span top-terms rewrite's getMaxSize() return IndexSearcher.getMaxClauseCount(), as the three core top-terms rewrites do, and cap the FrequentTermsSpanBooleanQueryRewrite queue the same way: two lines. With it the repro passes with assertions on and off, the 233 span tests run with 0 failures (2 skipped by the suite's own assumeTrue), and the queries module's static checks pass.

Trade-offs

  • Matches the three core top-terms rewrites exactly; a span-wrapped FuzzyQuery keeps the same top maxClauseCount terms as the plain one.
  • Explicit TopTermsSpanBooleanQueryRewrite(n) / FrequentTermsSpanBooleanQueryRewrite(n) with n above the limit now keep maxClauseCount terms instead of throwing: what their "will not overflow" javadoc promises, but still a behaviour change.
  • Parity with core, no more: a span-wrapped FuzzyQuery inside a SpanNearQuery with sibling clauses can still exceed the limit, exactly as BooleanQuery(a, b, fuzzy) does in core.
  • Backport to branch_10_6: the same getMaxSize() line (:210); its FrequentTerms queue is new PriorityQueue<>(maxSize) {...} (:313), so cap that argument.

Downstream note

#

Search servers that let end users send span queries with a fuzzy or top_terms_N multi-term clause return an error instead of results when the expansion size is above the clause limit.

How it was found

#

Semi-formal: an AI tool listed the documented clause limits and the paths that reach them, then built a bounded-exhaustive checker comparing 18 entry points with their javadoc at clause limits 1 to 8. 48 mismatches, all in the three span top-N entry points, none in 14 others; a record-only check of the default span rewrite logged 8 (known off-by-one, #10339).

The method in full278 words

Method: bounded-exhaustive boundary translation validation of the stock jar against each entry point's javadoc, public API only (study unit on documented resource limits, main a9779ef3c193, 2026-10-27).

  • Inventory: a grep of javadoc sentences that name a numeric limit with a consequence (TooManyClauses, maxExpansions, "at most", ...) over core, queries, suggest, analysis-common and queryparser, then a reading of every call site that reaches the limited computation; the span rewrites' Integer.MAX_VALUE was flagged there.
  • Checker: 915 checks: clause limit L = 1..8, n in {L - 1, L, L + 1} matching terms, sizes {L - 1, L, L + 1, 2L}, 18 entry points (BooleanQuery.Builder, SynonymQuery, the core top-terms and scoring rewrites, FuzzyQuery, the span rewrites, QueryBuilder, the classic parser, ...), expected outcome per entry point from its javadoc.
  • Result: 48 mismatches, all in the span-wrapped FuzzyQuery, TopTermsSpanBooleanQueryRewrite and FrequentTermsSpanBooleanQueryRewrite (they keep L + 1 terms at n = L + 1 where the core rewrites keep L), 0 in 14 others. The 18th entry, a record-only check of the unbounded default span rewrite (SCORING_SPAN_QUERY_REWRITE, out of scope: #7571, #10339), logged 8 more: at n = L + 1 it lets L + 1 terms through where the javadoc model expects a throw, the known clause-visitor off-by-one. A mutant that adds one to the core rewrites' getMaxSize() gives 16 mismatches per core entry point, so the checker is not vacuous; the fix removes every span top-N mismatch and leaves the 8 record-only rows.
  • A scale probe at the default limit 1,024 gave the lead trigger; the finder then wrote the public-API JUnit, and the one-test minimal repro was reduced from it.

Finding record

LFV-733, snapshot of 2026-11-06

Registry title
SpanMultiTermQueryWrapper's top-N span rewrites (TopTermsSpanBooleanQueryRewrite, FrequentTermsSpanBooleanQueryRewrite) do not cap their size at IndexSearcher#getMaxClauseCount, so a span-wrapped FuzzyQuery that works unwrapped throws TooManyNestedClauses
Area
queries / spans: SpanMultiTermQueryWrapper top-N rewrite methods vs the core IndexSearcher clause limit
Priority
Low, rank 1126: A span-wrapped FuzzyQuery that works unwrapped fails loudly with TooManyNestedClauses, but only when maxExpansions or an explicit span top-N size is above the clause limit.
Impact class
crash
Impact note
Applications that wrap a FuzzyQuery (or another top-terms multi-term query) in SpanMultiTermQueryWrapper with maxExpansions above IndexSearcher#getMaxClauseCount (1024 by default), that lower the clause limit below the expansion size (below 50 even the default FuzzyQuery fails once wrapped), or that pass an explicit TopTermsSpanBooleanQueryRewrite / FrequentTermsSpanBooleanQueryRewrite size above the limit get IndexSearcher$TooManyNestedClauses from search or count as soon as the expansion matches more terms than the limit, where the unwrapped query is capped and runs; a clean per-request exception with no wrong results and no index effect, default writer, codec and searcher settings, no scale needed, every release since 9.0.0.
Summary
You wrap new FuzzyQuery(term, 2, 0, 2000, true) in SpanMultiTermQueryWrapper (for example to use it inside a SpanNearQuery) and search an index where more than 1024 terms are within two edits. FuzzyQuery documents that a maxExpansions above IndexSearcher#getMaxClauseCount is replaced by the limit, and the span top-N rewrites say they 'will not overflow the boolean max clause count', so you expect the same capped expansion the plain FuzzyQuery gets (it runs with 1024 terms). Instead the span rewrite keeps up to maxExpansions terms (TopTermsSpanBooleanQueryRewrite.getMaxSize() returns Integer.MAX_VALUE, and FrequentTermsSpanBooleanQueryRewrite sizes its queue with the caller's size only), and IndexSearcher.rewrite throws IndexSearcher$TooManyNestedClauses ('maxClauseCount is set to 1024').
Introduced
53f56fb7ad44afab9c78fab2e89737438093247f (LUCENE-8811 'Move max clause checks to IndexSearcher', apache/lucene#9855, committed by romseygeek with patches by atris, 2019-06-26, first released in 9.0.0) is where the failure starts: IndexSearcher.rewrite began to count every clause of the rewritten query with a QueryVisitor, span terms included, and the commit did not touch SpanMultiTermQueryWrapper. The missing cap it exposes is older: TopTermsSpanBooleanQueryRewrite.getMaxSize() returning Integer.MAX_VALUE and the mapping of a TopTermsRewrite (FuzzyQuery's) to new TopTermsSpanBooleanQueryRewrite(size) come from ac71ebc23716 (LUCENE-2754, apache/lucene#3828, uschindler, 2010-11-14; 3.x backport 7d137513808), written when SpanOrQuery had no clause limit (sibling comment 'we accept all terms as SpanOrQuery has no limits', 1d0515124e2, LUCENE-2757). The FrequentTermsSpanBooleanQueryRewrite half is 156fb97fd33 on main and 3572e2c03f0 on branch_10x / branch_10_6 (apache/lucene#16484, 2026-08-18, first released in 10.6.0). [read: git blame -w -C -C -M and git log; exec: release sweep, exception from 9.0.0 on] (2019-06-26 (53f56fb7ad4; first released in 9.0.0, 2021-12); latent cap omission 2010-11-14 (ac71ebc2371); FrequentTerms half 2026-08-18 (#16484, first released in 10.6.0))
