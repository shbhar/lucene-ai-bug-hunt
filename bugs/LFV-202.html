IndexSearcher rejects any reader that contains an empty leaf

Since 10.0, IndexSearcher throws IllegalArgumentException: minDocId is greater than than maxDoc: [0] > [0] for any reader with a leaf of 0 documents, such as new ParallelLeafReader() with no sub-readers. 9.12.3 searches the same reader and counts 0 hits.

The finding in 30 seconds

#

One empty leaf makes a whole reader unsearchable, because a bounds check added for partition ranges also runs on the whole-leaf range.

Leaves, slices and partitions

#
  1. A reader is a list of leaves (segments). A leaf's maxDoc() is its number of document ids, and it can be 0: new ParallelLeafReader() with no sub-readers is a stock leaf with maxDoc() 0.
  2. IndexSearcher groups the leaves into slices, the units of work it runs, in parallel when it has an executor.
  3. Since 10.0 a slice holds partitions: a leaf plus a doc-id range. A whole leaf gets the range [0, NO_MORE_DOCS); intra-segment search can also split a big leaf into real sub-ranges such as [0, 500) and [500, 1000).

The finding, step by step

#
  1. Build a reader whose one leaf has no documents: new ParallelLeafReader(true) with no sub-readers has maxDoc() 0. Run new IndexSearcher(reader).count(new MatchAllDocsQuery()).
  2. You expect 0, as on 9.12.3. Put the same empty leaf next to a real 5-document index in a MultiReader and you expect 5.
  3. Instead the IndexSearcher constructor throws IllegalArgumentException: minDocId is greater than than maxDoc: [0] > [0], with assertions on or off. The MultiReader with 5 real documents fails the same way.
  4. Why: since 10.0 slicing wraps every leaf in a partition with the range [0, NO_MORE_DOCS), and the partition constructor rejects minDocId >= maxDoc(). The check also runs on that whole-leaf range, and for an empty leaf it reads 0 >= 0.
  5. Indexes that IndexWriter writes never contain an empty leaf, so in practice only readers assembled in memory hit it. It always fails loudly and never returns a wrong result.

Who is affected

#

Applications that build a reader in memory with an empty leaf: a ParallelLeafReader with no sub-readers (alone, wrapped or inside a MultiReader) or a custom LeafReader whose maxDoc() is 0. Every searcher with Lucene's own slicing fails over that reader, with or without an executor. Readers over indexes that IndexWriter wrote are not affected.

Mechanism, terms and numbers456 words

Since 10.0.0 IndexSearcher's own slicing wraps every leaf of its reader in a LeafReaderContextPartition, a leaf plus a doc-id range; a whole leaf gets [0, NO_MORE_DOCS) from createForEntireSegment. The partition constructor throws IllegalArgumentException when minDocId >= leaf.maxDoc(), a check that intra-segment concurrency (#13542) added to the partition constructor at a reviewer's request. It runs for the whole-leaf partition too, and for a leaf with maxDoc() == 0 it reads 0 >= 0. So a reader that contains an empty leaf cannot be searched: new IndexSearcher(new ParallelLeafReader(true)) throws where 9.12.3 counts 0, and a MultiReader of a 5-document index plus that leaf throws where 9.12.3 finds 5. A reader with no leaves at all is special-cased and works. Indexes that IndexWriter writes never contain an empty leaf, so in practice only readers assembled in memory hit it. Every release from 10.0.0 to 10.6.0 and main is affected; 9.x is not.

The code path (main 645d4fe14a20, IndexSearcher.java)

#
  1. new IndexSearcher(reader) (:189-191) delegates to IndexSearcher(IndexReaderContext, Executor) (:218-232). Without an executor it builds its one slice at once: leafContexts.isEmpty() ? new LeafSlice[0] : new LeafSlice[] {LeafSlice.entireSegments(leafContexts)} (:226-231). A reader with no leaves is special-cased; a leaf with no documents is not.
  2. LeafSlice.entireSegments wraps every leaf with LeafReaderContextPartition.createForEntireSegment(ctx) (:1021-1028).
  3. createForEntireSegment always passes minDocId 0 and maxDocId DocIdSetIterator.NO_MORE_DOCS (:1097-1100).
  4. The private constructor (:1068-1094) checks minDocId >= maxDocId, minDocId < 0 and minDocId >= leafReaderContext.reader().maxDoc() (:1081-1088). For an empty leaf the third reads 0 >= 0 and throws "minDocId is greater than than maxDoc: [0] > [0]" (the message says >; the check is >=).
  5. Every other stock slicing path reaches the same constructor: executor searchers lazily through getSlices() and computeAndCacheSlices() (:537-543, :545-565) on the first count() or search(), and the public static slices(leaves, maxDocsPerSlice, maxSegmentsPerSlice, allowSegmentPartitions) (:341-390) with partitions off (:385) and on (:422; an empty leaf always fits in a slice).

Before #13542 a slice held plain leaves and nothing was checked per leaf, so 9.x searched the empty leaf and found nothing in it.

The trigger

#

ParallelLeafReader's constructor accepts zero readers and then sets this.maxDoc = this.numDocs = 0 (ParallelLeafReader.java:96-98). Any custom LeafReader whose maxDoc() is 0 does the same. Wrapping it, nesting it or putting it in a MultiReader next to real indexes does not help: every leaf is wrapped.

Where it throws

#

On 10.0.0 the no-executor constructor still computed slices lazily, so the first count() or search() throws; from 10.1.0 (#13893) the constructor throws, and from 10.2.0 (#14343) through LeafSlice.entireSegments. With an executor it throws from getSlices() in every affected version.

Exposure and likelihood271 words
  • Who is hit: applications that assemble a reader in memory with an empty leaf. One empty leaf makes the whole MultiReader unsearchable, its non-empty leaves included.
  • Default vs opt-in: the default IndexSearcher, no setting involved; what is opt-in is the reader composition.
  • Scale: none; one empty leaf is enough and no index is needed.
  • Severity: a loud, deterministic IllegalArgumentException on every attempt. Nothing is persisted, no wrong result is ever returned, nothing hangs and no search task is submitted (executed probe).
  • Not hit: readers over indexes that IndexWriter wrote. IndexWriter never writes a 0-doc segment (LUCENE-5173: "Lucene never writes segments with 0 documents anymore", lucene/CHANGES.txt:13437), and CheckIndex rejects one (CheckIndex.java:1011-1013). A hand-written 0-doc segment does open (a fact-check probe: DirectoryReader.open gives one leaf with maxDoc() 0 and IndexSearcher throws the same exception), but CheckIndex rejects it as illegal and index files are trusted input (SECURITY.md:30-34). A fully hard-deleted segment kept by the merge policy, a fully soft-deleted segment (SoftDeletesDirectoryReaderWrapper drops the leaf) and a FilterDirectoryReader that hides every document through live docs all keep maxDoc() > 0 and search fine (executed). A ParallelCompositeReader with no readers has no leaves; MemoryIndex and TermVectorLeafReader report maxDoc() 1.
  • Downstream: a read-only code search found no readerless ParallelLeafReader in Elasticsearch, OpenSearch or Solr; Solr's one ParallelLeafReader always has inputs and feeds a merge. A spot check, not proof.
  • Exposure so far: 13 releases over two years (10.0.0 to 10.6.0) and no report found.
  • Workaround: leave zero-doc leaves out of the reader. Overriding the protected slices(List) cannot help the no-executor constructor, which builds its slice directly (IndexSearcher.java:226-231).

Why it looks unintended

#
  • IndexSearcher(IndexReader) states no precondition, IndexReader#maxDoc has no lower bound, and LeafReader says any subclass "is searchable".
  • ParallelLeafReader handles zero sub-readers on purpose, and IndexSearcher itself special-cases a reader with no leaves.
  • 9.12.3 searches these readers; no CHANGES or MIGRATE entry announces a restriction.
The full argument260 words

The contract is implied, not stated outright.

  • IndexSearcher(IndexReader): "Creates a searcher searching the provided index." (IndexSearcher.java:188-191): no precondition, not @lucene.experimental.
  • IndexReader#maxDoc: "Returns one greater than the largest possible document number." (IndexReader.java:300-305): no lower bound.
  • LeafReader: "Search of an index is done entirely through this abstract interface, so that any subclass which implements it is searchable." (LeafReader.java:31-34)
  • ParallelLeafReader handles zero sub-readers on purpose (ParallelLeafReader.java:96-98); the upstream test TestParallelReaderEmptyIndex builds one (:49-50, LUCENE-1918), though only for addIndexes.
  • IndexSearcher special-cases a reader with no leaves (IndexSearcher.java:227-229).
  • 9.12.3 searches these readers correctly (executed). The 10.0.0 CHANGES entry for #13542 (lucene/CHANGES.txt:2332) and MIGRATE's six #13542 items say nothing about empty leaves, and no upstream test asserts the rejection.

History of the check. In the #13542 review jpountz asked (2024-07-31, on the private constructor that both factories share): "Can you add validation, e.g. minDocId >= 0, maxDocId > minDocId, minDocId < context.reader().maxDoc(), etc?", and javanna answered (2024-08-26) "good with the proposed validation", keeping NO_MORE_DOCS as the upper bound when targeting the entire segment. None of the PR's 30 comments, 99 review comments and 77 reviews mentions empty or 0-doc leaves.

Precedent. LUCENE-5045 (#6109, 2013): DrillSideways threw IllegalArgumentException on an empty reader; the report says "there's nothing technically wrong from running a search against an empty index", and it was fixed as a bug. In #15803 (2026-03-10) mikemccand wrote "Lucene tries hard to never produce a 0-doc segment" and still asked for an explicit test with 0-doc segments.

The devil's-advocate check163 words

The strongest case for "intended" (rated moderate by the cross-model reviewers, weak to moderate by the devil's-advocate verifier): the check is deliberate and is literally what the reviewer asked for ("minDocId < context.reader().maxDoc()"); LeafReaderContextPartition is @lucene.experimental; and Lucene never writes 0-doc segments (LUCENE-5173; CheckIndex rejects maxDoc <= 0), so an empty leaf is an unusual, synthetic reader.

Why it fails: the failure surfaces through the stable IndexSearcher(IndexReader) constructor, not the experimental partition API; the review was about partition bounds, and nobody discussed what the check does to the whole-leaf partition of an empty leaf; LUCENE-5173 and CheckIndex govern segments written to disk, while ParallelLeafReader is a public reader that handles zero inputs on purpose; and a fix that keeps the validation for real partitions leaves search working, with 0 hits in the empty leaf and correct counts beside it. That the effect on the empty whole-leaf partition was overlooked is an inference, not something the PR says. Verdict: not intended; rare.

Suggested fix

#

Recommended Range-check only true partitions (C, recommended, validated)

Range-check only true partitions: move the constructor's three checks into createFromAndTo, since createForEntireSegment's range is the whole leaf by construction. It passes the repro and the slicing suites, and keeps working if open PR #16952 changes the whole-leaf range to (0, maxDoc), where the one-condition alternative stops working.

public static LeafReaderContextPartition createFromAndTo(
    LeafReaderContext ctx, int minDocId, int maxDocId) {
  assert maxDocId != DocIdSetIterator.NO_MORE_DOCS;
  // only a true partition needs a range check: the entire-segment partition is valid for any
  // leaf, including one with no documents
  if (minDocId >= maxDocId) { throw ... }            // moved from the constructor, unchanged
  if (minDocId < 0) { throw ... }                    // moved, unchanged
  if (minDocId >= ctx.reader().maxDoc()) { throw ... } // moved, unchanged
  return new LeafReaderContextPartition(ctx, minDocId, maxDocId, maxDocId - minDocId);
}

Range-check only true partitions (C, recommended, validated)

#

The change is +21/-20 lines in IndexSearcher.java: the three checks move, unchanged, from the private LeafReaderContextPartition constructor into createFromAndTo, the only factory that takes caller-supplied bounds. createForEntireSegment passes no check, because its range is the whole leaf, whatever the leaf's size.

public static LeafReaderContextPartition createFromAndTo(
    LeafReaderContext ctx, int minDocId, int maxDocId) {
  assert maxDocId != DocIdSetIterator.NO_MORE_DOCS;
  // only a true partition needs a range check: the entire-segment partition is valid for any
  // leaf, including one with no documents
  if (minDocId >= maxDocId) { throw ... }            // moved from the constructor, unchanged
  if (minDocId < 0) { throw ... }                    // moved, unchanged
  if (minDocId >= ctx.reader().maxDoc()) { throw ... } // moved, unchanged
  return new LeafReaderContextPartition(ctx, minDocId, maxDocId, maxDocId - minDocId);
}

Trade-offs

  • True partitions keep exactly the same checks and messages; only the whole-leaf partition, whose bounds the code chooses itself, is no longer checked.
  • It survives #16952 (open, opened 2026-10-30), which makes createForEntireSegment pass (0, maxDoc): there an empty leaf would otherwise fail the first check (0 >= 0).
  • It moves about 20 lines, so it conflicts textually with draft #16847, which edits the third check.
  • No behaviour change for any leaf with at least one document.

Skip empty leaves when slicing (not run)

#

Leave leaves with maxDoc() == 0 out of LeafSlice.entireSegments and slices(...).

Trade-offs

Collectors would never see the leaf, the slices would no longer cover every leaf of the reader, and the public static slices() would return different slices. A reader whose only leaf is empty would get no slice at all, and search() asserts leafContexts.isEmpty() in that case (IndexSearcher.java:764), so that would need changing too. More invasive than C for no gain.

Downstream note

#

No downstream engine is known to build such a reader: a read-only code search found no readerless ParallelLeafReader in Elasticsearch, OpenSearch or Solr.

How it was found

#

A hunt on concurrent collector managers and slicing checked the public static IndexSearcher.slices(...) on the real jar against its own properties over every small leaf layout. "Does not throw for a legal reader" failed in 31,176 of 178,996 layouts: exactly those with a 0-doc leaf. It was then reduced by hand to a public-API test.

The method in full173 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier) of the public static IndexSearcher.slices(leaves, maxDocsPerSlice, maxSegmentsPerSlice, allowSegmentPartitions) in a hunt on concurrent collector managers and slicing, run on the real main jar (ea57360912ed).

LFV-202, snapshot of 2026-11-06

Registry title
IndexSearcher throws IllegalArgumentException for any reader that contains a leaf with maxDoc() == 0 (for example a ParallelLeafReader with no sub-readers): the whole-segment LeafReaderContextPartition of that leaf fails a bounds check added for partition ranges (regression in 10.0.0)
Area
search / IndexSearcher slicing (LeafSlice, LeafReaderContextPartition)
Priority
Low, rank 785: Since 10.0.0 IndexSearcher rejects any reader that contains a 0-doc leaf (for example an empty ParallelLeafReader), loud and in practice only for readers assembled in memory.
Impact class
crash
Impact note
Hits only applications that assemble a reader in memory with a leaf whose maxDoc() is 0 (a ParallelLeafReader with no sub-readers, alone, wrapped or inside a MultiReader, or a custom LeafReader reporting maxDoc() == 0); for them every searcher over that reader fails with a clean IllegalArgumentException, in the no-executor constructor (10.1.0 on) or on the first count()/search() (executor searchers, and 10.0.0), with -ea and -da; readers over indexes that IndexWriter wrote never contain such a leaf (a hand-written 0-doc segment, which CheckIndex rejects, does open and fails the same way), no scale is needed, nothing is persisted and no wrong result is ever returned; affected since 10.0.0 (9.x not affected).
Summary
You build an IndexSearcher over a reader that contains an empty leaf, for example new ParallelLeafReader() with no sub-readers, possibly next to a real index inside a MultiReader, and you expect searches to work and simply find no hits in the empty part, as they do on 9.12.3. Instead the searcher throws IllegalArgumentException 'minDocId is greater than than maxDoc: [0] > [0]', because slicing wraps every leaf in a whole-segment partition that starts at doc 0 and the partition constructor rejects a start that is not below the leaf's maxDoc(). In the repro, a MultiReader of a 5-doc index plus an empty ParallelLeafReader cannot be searched at all instead of returning 5 hits.
