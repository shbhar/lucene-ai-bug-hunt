Analyzer.normalize never closes the CharFilter its normalization hook returns

Analyzer.normalize, which query parsers call for prefix, wildcard, fuzzy, regexp and range terms, never closes the CharFilter returned by initReaderForNormalization, although analysis closes the same CharFilter. Only custom CharFilters that free something in close() are hit; Lucene's own free nothing there (every release since 6.2.0).

The finding in 30 seconds

#

Two Lucene terms first

#
  1. A CharFilter is a Reader that rewrites characters before tokenizing (for example folding full-width letters). It wraps another Reader, and its close() closes the Reader it wraps.
  2. An Analyzer adds CharFilters in initReader (analysis) and in initReaderForNormalization. The second is used by normalize(field, text), which query parsers call to normalize a partial word such as the foo of foo* without tokenizing it.

The finding, step by step

#
  1. You give an Analyzer a CharFilter for normalization by overriding initReaderForNormalization, and its close() frees something of yours, as the CharFilter javadoc allows ("be sure to call super.close() when overriding"). The test's close() just sets a flag.
  2. A query parser normalizes a term: for f:foo* it calls analyzer.normalize("f", "foo"). You expect foo back and close() called once, as when the same CharFilter analyzes text: there Tokenizer.close() closes it.
  3. Instead you get foo, but close() is called 0 times: normalize puts only its own StringReader in try-with-resources, reads the CharFilter to the end and drops it.
  4. Whatever your close() would free is not freed by Lucene, once per normalize call (a range [a TO c] makes 2). With Lucene's own CharFilters nothing leaks, and terms, index and results are unchanged.

Who is affected

#

Only applications whose own normalization CharFilter or Reader frees something in close(), such as a pooled buffer, a lease or a native or file handle. That close() is skipped once per normalize call. Lucene's own CharFilters free nothing there, so stock setups lose nothing and results never change.

Mechanism, terms and numbers456 words

Query parsers call Analyzer.normalize(field, text) to normalize the text of prefix, fuzzy, regexp, wildcard and range terms. The method lets the analyzer wrap the text in CharFilters through the protected hook initReaderForNormalization, reads that Reader to the end, and closes only the StringReader it created itself. The CharFilter the hook returned is never closed, although the same CharFilter returned from initReader is closed on the analysis path by Tokenizer.close(). An application CharFilter that frees something in close() therefore never gets that call from Lucene during query normalization. It is latent: no CharFilter shipped with Lucene frees anything in close() beyond its input, which normalize already closes, so nothing leaks with Lucene's own components, and the bug changes no term, index or search result. Present since 6.2.0; the fix is a two-line change.

Mechanism (main 5adff78bb168)

#
  1. normalize(String, String) is public final (Analyzer.java:213). It opens try (Reader reader = new StringReader(text)) (:217), calls Reader filterReader = initReaderForNormalization(fieldName, reader) (:218), reads filterReader to EOF (:221-227) and leaves the block. Only reader is a resource; filterReader never leaves the method, so no caller gets it back to close it, and no API gives the hook implementer a point at which to close it (an implementation could keep its own reference and close it later itself, but nothing documents or suggests that).
  2. The hook's javadoc (:279-286): "Wrap the given Reader with CharFilters that make sense for normalization. This is typically a subset of the CharFilters that are applied in initReader". Nothing about closing.
  3. On the analysis path the initReader result becomes the Tokenizer's input (components.setReader(r), :160 and :197), and Tokenizer.close() runs input.close() (Tokenizer.java:63-69): the outermost CharFilter is closed and closes the chain below it (CharFilter.java:58-61).
  4. So a CharFilter class used in both places is closed at index time and never at query-normalization time. CustomAnalyzer has the same shape: its hook chains charFilter.normalize(reader) (CustomAnalyzer.java:152-158), and CharFilterFactory.normalize invites factories to "delegate to create" (CharFilterFactory.java:101-108). TestCustomAnalyzer.testNormalization runs this route with a factory whose normalize() delegates to create() (TestCustomAnalyzer.java:460-470, :523-542) and passed with the fix, but it checks values only: no test tracked close() through CustomAnalyzer.

The numbers

#

One normalize("f", "foo") call: the value is foo (correct), the CharFilter's close() count is 0 (expected 1). By reading the classic query parser: 1 call per prefix, fuzzy or regexp term (QueryParserBase.java:712, :729, :683), 1 per non-wildcard chunk of a wildcard term (chunks are split at *, ? and escaped characters, :635-659), and 1 per bounded end of a range: up to 2 per range, 1 when one end is * (:547-557).

Exposure and likelihood205 words
  • Who. An initReaderForNormalization override, or a custom CharFilterFactory whose normalize() delegates to create() inside CustomAnalyzer, that returns a CharFilter or Reader with real work in close().
  • How often. Once per Analyzer.normalize call. The classic parser calls it once per prefix, fuzzy or regexp term, once per non-wildcard chunk of a wildcard term and once per bounded end of a range (up to twice per range). The flexible parser's WildcardQueryNodeProcessor, FuzzyQueryNodeProcessor, RegexpQueryNodeProcessor and TermRangeQueryNodeProcessor call it when an analyzer is configured (the range processor only for bounds that do not parse as dates). SimpleQueryParser calls it for fuzzy and prefix terms, once per configured field, when those operators are enabled (SimpleQueryParser.java:573, :605).
  • Not affected. Lucene's own CharFilters. Of the shipped, non-sandbox CharFilter subclasses only HTMLStripCharFilter overrides close() (HTMLStripCharFilter.java:5828), and it only resets scanner state and closes its input (:5974-5979), which here is the StringReader normalize already closes. With Lucene's shipped CharFilters the fix changes no normalized term, index or search result (for a custom close() that throws, see the fix trade-offs).
  • Default vs opt-in. Opt-in: it needs application code with work in close().
  • Likelihood. Rare; the recorded searches found no public report since 2016.

Why it looks unintended

#
  • normalize is final and the hook's Reader never leaves it, so no caller can close it.
  • CharFilter.close() is the documented release point ("be sure to call super.close() when overriding"), and the analysis path closes the same chain through Tokenizer.close().
  • Nothing documents the gap; the try-with-resources closes the inner end of the chain, not the outer.
The full argument229 words
  • The only Lucene code that holds the Reader. normalize is final, gets the Reader from the hook, is its only reader, and the Reader never escapes, so no caller can close it. A hook implementation could keep its own reference and close it later, but no API or javadoc suggests that.
  • Documented release point. CharFilter.close(): "Closes the underlying input stream. NOTE: The default implementation closes the input Reader, so be sure to call super.close() when overriding this method." (CharFilter.java:52-57). Overriding close() is anticipated.
  • Often the same classes on both paths. The hook's result is "typically a subset of the CharFilters that are applied in initReader" (Analyzer.java:280-282), and initReader's result is closed by Tokenizer.close(); so the same CharFilter classes commonly appear on both paths (a usual pattern, not a guarantee).
  • The inner end is closed. The try-with-resources at :217 shows that normalize is meant to close the Reader it opens; it closes the inner StringReader, not the wrapper the hook returns, against the usual Closeable practice of closing the outermost wrapper. The introducing commit says nothing about who owns that wrapper.
  • Nothing documents the gap. No javadoc, CHANGES.txt or MIGRATE.md entry, and no test (TestDelegatingAnalyzerWrapper and kuromoji's TestJapaneseCompletionFilter override the hook, TestCustomAnalyzer reaches it through CharFilterFactory.normalize; all check only values); the 34 comments on LUCENE-7355 (#8409) never discuss it.
The devil's-advocate check144 words

The case (rated moderate by the cross-model reviewer and the cross-model fact check; found unconvincing by the intended-behaviour review and the adjudication): the hook documents only the transformation, not who closes its result; CharFilter.close() is documented as "Closes the underlying input stream", which normalize already does; every shipped CharFilter is therefore fine; and the code has been unchanged since 2016 with no complaint.

Why it fails: none of this shows intent, only that the gap is harmless for Lucene's own classes. The CharFilter javadoc expects subclasses to do more in close(), the analysis path honours that, and normalize leaves the hook implementer no documented place to release anything. Neither the code nor its history proves the author's intent about the wrapper, so this is a latent lifecycle inconsistency. What remains is impact, not intent: Low, and a maintainer may call the fix hygiene.

Suggested fix

#

Recommended The hook's Reader as a second try-with-resources resource (recommended)

Declare the hook's Reader as a second try-with-resources resource in normalize (a two-line change). It closes first and closes the StringReader through CharFilter.close(); the second close of the StringReader is a no-op. Validated: the repro passes, and so do the core analysis, CustomAnalyzer and query parser suites.

-      try (Reader reader = new StringReader(text)) {
-        Reader filterReader = initReaderForNormalization(fieldName, reader);
+      try (Reader reader = new StringReader(text);
+          Reader filterReader = initReaderForNormalization(fieldName, reader)) {
All options and trade-offs3 options · 399 words

With Lucene's own CharFilters all three options keep the normalized value unchanged. A also covers AnalyzerWrapper, DelegatingAnalyzerWrapper and CustomAnalyzer, because they reach the hook only through the final normalize.

The hook's Reader as a second try-with-resources resource (recommended) (validated by the checks)

#

Resources close in reverse order, so the hook's Reader closes first; for a CharFilter that also closes the StringReader, whose second close has no effect (java.io.Reader.close(): "Closing a previously closed stream has no effect"). If the hook throws, the StringReader is still closed.

-      try (Reader reader = new StringReader(text)) {
-        Reader filterReader = initReaderForNormalization(fieldName, reader);
+      try (Reader reader = new StringReader(text);
+          Reader filterReader = initReaderForNormalization(fieldName, reader)) {

Trade-offs

A two-line change (one more resource), no API change. It changes what a custom close() that fails can do, since before it never ran: an IOException from it now surfaces as the method's existing IllegalStateException("Normalization threw an unexpected exception") (Analyzer.java:229-230), as a failing read() already does; an unchecked exception propagates as is; and after a failed read() a close() failure is attached as a suppressed exception. So for such a CharFilter a normalize call that returned a term can now throw. With the default hook (input returned unchanged) the same StringReader is closed twice, a no-op.

What the checks validated

Yes (scratch worktree of 5adff78bb168, gradle, 2026-11-05): the repro fails before and passes after, assertions on and off; with the fix, the repro plus every core org.apache.lucene.analysis suite (169 tests), TestCustomAnalyzer (26) and the classic, flexible and simple query parser suites TestQueryParser, TestStandardQP and TestSimpleQueryParser (165) pass: 26 classes, 360 tests, 0 failures, 0 skipped; lucene/core's checkGoogleJavaFormat, ecjLint and forbiddenApis checks pass with the fix and the test.

Only the hook's Reader as the resource (not run)

#

try (Reader filterReader = initReaderForNormalization(fieldName, new StringReader(text))).

Trade-offs

Equally short, but it relies on the hook's Reader closing its input, and if the hook throws the StringReader is not closed (harmless for a StringReader, less tidy than A).

What the checks validated

Not run.

Document the current behaviour instead

#

Javadoc on normalize and initReaderForNormalization: the returned Reader is not closed, so it must not hold anything released only in close().

Trade-offs

No code change, but it keeps the asymmetry with initReader and contradicts CharFilterFactory.normalize's advice to delegate to create. Not recommended.

Downstream note

#

Downstream, a normalization CharFilter should not count on its close() running at query time on any release from 6.2.0 to 10.6.0.

How it was found

#

A semi-formal proof-obligation audit of Analyzer's contract: normalize is the only user of the Reader its hook returns, so it must close it, as the analysis path does through Tokenizer.close(). The obligation failed on reading the code, and a one-test repro on the stock main jars confirmed it.

The method in full70 words

The obligation checked: normalize(String, String) is the only user of the Reader its protected initReaderForNormalization hook returns, so it must close it, as the tokenStream path does through Tokenizer.close(). The code discharges it for analysis but not for normalize, which closes only its own StringReader. A JUnit test with a close-recording Reader returned from the hook witnessed it on main 5adff78bb168 (2026-11-04), with assertions on and off.
