DisjunctionMaxQuery and the LatLon distance feature query accept NaN and produce NaN scores

new DisjunctionMaxQuery(clauses, Float.NaN) and LatLonPoint.newDistanceFeatureQuery(..., Double.NaN) (or a +Infinity pivot) are accepted, although both reject every other out-of-range value, because their range checks are false for NaN. Their hits then score NaN and the query is not equal to itself; in every release since 8.0.0 and on main.

The finding in 30 seconds

#

Both range checks are written as "reject if out of range", and every comparison with NaN is false, so NaN slips through; the NaN then flows into the score formula and into equals.

Background: the two queries

#
  1. DisjunctionMaxQuery is used to search one word in several fields: a document scores its best field's score plus tieBreakerMultiplier times the other matching fields' scores. The tie-breaker must be in [0, 1], typically 0.1.
  2. LatLonPoint.newDistanceFeatureQuery boosts nearby documents: score = weight × pivot / (pivot + distance), so a score between 0 and weight, and weight/2 at the pivot distance. The pivot must be > 0.

The finding, step by step

#
  1. Index doc 0 with x in title and body, doc 1 with x in title only, and search DisjunctionMaxQuery([title:x, body:x], 0.1f): doc 0 scores 0.2267, doc 1 scores 0.2136.
  2. Pass Float.NaN as the tie-breaker instead (a computed 0/0, a config value "NaN", or tieBreaker="NaN" in the XML query parser). You expect IllegalArgumentException: tieBreakerMultiplier must be in [0, 1], which -0.01, 1.01 and Infinity get.
  3. You get no error. The check is x < 0 || x > 1, and every comparison with NaN is false. Both hits score NaN, doc 1 too, because its score is max + 0 × NaN; q.equals(q) is false because equals compares with ==.
  4. The distance feature query has the same flaw: its check pivot <= 0 also lets NaN and +Infinity through. Points that score 1.0, 0.0063 and 0.00064 with a 1,000 m pivot all score NaN, although the javadoc promises scores in [0, weight].
  5. Only scores and equality break: in the study's probe on main (11 query shapes) the same documents matched as with a finite value, and nothing is written. Older releases were worse: 8.0.0 and 8.11.4 return no top-k hits at all for the NaN dis-max query.

Who is affected

#

Applications that let a NaN reach the dis-max tie-breaker (computed, parsed config or request values, XML query text) or a NaN or +Infinity reach the distance pivot. That query's ranking becomes meaningless and pruning stops; the matching documents did not change in 11 tested query shapes. Rare: no prior report found.

Mechanism, terms and numbers728 words

DisjunctionMaxQuery throws IllegalArgumentException("tieBreakerMultiplier must be in [0, 1]") for -0.01, 1.01 and +/-Infinity, and LatLonPoint.newDistanceFeatureQuery throws "pivotDistance must be > 0" for 0 and -1. Both checks are written as "reject if out of range" (x < 0 || x > 1, x <= 0), and every comparison with NaN is false, so NaN passes both; +Infinity <= 0 is false too, so the pivot check also accepts +Infinity.

The query is then built and its hits score NaN: the dis-max score is max + others * tie, NaN even for a document that matches one clause (in segments where at least two clauses have a scorer), and the distance score weight * pivot / (pivot + distance) is NaN for a NaN or +Infinity pivot, although its javadoc promises a score in [0, weight]. A NaN query is not equal to itself, because equals compares the value with ==, so a query cache cannot reuse an entry for an equal copy of a NaN dis-max filter, and top-k pruning stops raising its threshold. The tie-breaker is reachable from XML query parser text (tieBreaker="NaN"). In the study's probe on main (11 query shapes) the match set never changed and nothing was written; 8.x releases returned no top-k hits for the NaN dis-max query. It is in every release since 8.0.0 and on main. Adding Float.isNaN(x) || to the two tie-breaker checks and Double.isFinite(pivot) == false || to the pivot check fixes it; it passes the repro, the closest suites and check.

The bug, step by step (main 645d4fe14a20, under lucene/core/src/java/org/apache/lucene/)

#
  1. The checks. if (tieBreakerMultiplier < 0 || tieBreakerMultiplier > 1) throw new IllegalArgumentException("tieBreakerMultiplier must be in [0, 1]"); (search/DisjunctionMaxQuery.java:65-67; the same check in the package-private DisjunctionMaxScorer constructor, search/DisjunctionMaxScorer.java:49-51). if (pivotDistance <= 0) throw new IllegalArgumentException("pivotDistance must be > 0, got " + pivotDistance); (document/LatLonPointDistanceFeatureQuery.java:58-60), right after GeoUtils.checkLatitude/checkLongitude on the origin (:54-55), which do reject NaN. For NaN every comparison is false, so the value passes; +Infinity <= 0 is false too, while +Infinity > 1 is true, so only the pivot check accepts +Infinity.
  2. The dis-max score. With at least two clauses that have a scorer in a segment, the weight builds a DisjunctionMaxScorer (search/DisjunctionMaxQuery.java:158); with one, it returns that clause's scorer unchanged (:145-146), so scores stay finite in such segments. DisjunctionMaxScorer.score returns (float) (scoreMax + otherScoreSum * tieBreakerMultiplier) (search/DisjunctionMaxScorer.java:60-73). For a document matching one clause otherScoreSum is 0, and 0 * NaN is NaN. explain uses the same formula (search/DisjunctionMaxQuery.java:239).
  3. The distance score. (float) (boost * (pivotDistance / (pivotDistance + distance))) (document/LatLonPointDistanceFeatureQuery.java:280; :130 in explain): NaN for a NaN pivot, and Infinity / Infinity = NaN for a +Infinity pivot. The factory's weight is not a second gap: when it is not 1 it goes through BoostQuery (document/LatLonPoint.java:373-374), which rejects non-finite and negative boosts (search/BoostQuery.java:40).
  4. equals is not reflexive. tieBreakerMultiplier == other.tieBreakerMultiplier (search/DisjunctionMaxQuery.java:353) and pivotDistance == other.pivotDistance (document/LatLonPointDistanceFeatureQuery.java:80) are false for NaN, while hashCode uses the bit pattern (:365, :89): two identical NaN queries have the same hash code and are never equal. A +Infinity pivot query stays equal to itself.
  5. Query text path (dis-max only). The XML query parser reads tieBreaker with DOMUtils.getAttribute(e, "tieBreaker", 0.0f), which is Float.parseFloat (lucene/queryparser/.../xml/builders/DisjunctionMaxQueryBuilder.java:46, xml/DOMUtils.java:124-127), and passes it to new DisjunctionMaxQuery (:59). tieBreaker="NaN" parses to (f:a | f:b)~NaN, not equal to itself, while boost="NaN" and tieBreaker="2" in the same element are rejected. The pivot has no parser path.
  6. A third, unchecked site. BlendedTermQuery.DisjunctionMaxRewrite(float) stores the tie-breaker with no check, compares it with == (search/BlendedTermQuery.java:165-172, 180) and later builds new DisjunctionMaxQuery with it; DisjunctionMaxRewrite(NaN) is not equal to itself.

Exposure and likelihood425 words
  • Who is hit. An application that lets a NaN reach the tie-breaker (a computed value such as 0f/0f, a configuration or request value "NaN" read with Float.parseFloat, or XML query text tieBreaker="NaN"), or a NaN or +Infinity reach the pivot (for example a pivot computed by dividing by zero). Default IndexWriterConfig, codec and searcher; DisjunctionMaxQuery is a mainstream core query.
  • What goes wrong. No exception, then: the hits of that query score NaN (for the dis-max query, in segments where at least two clauses have a scorer), so its ranking is meaningless; top-k pruning mostly stops, because once the top-k heap holds NaN Math.nextUp(NaN) > minCompetitiveScore is false and the threshold is never raised (TopScoreDocCollector.java:160-161): in the study's probe the distance query alone counted all 200,000 matches instead of 1,169, and across the 11 query shapes the slowest NaN shape took about 8x the control's time (a dis-max of the distance query and a term, 41 vs 5 ms) while some ran faster, on a loaded host; a NaN dis-max query is not equal to any other instance, and IndexSearcher consults the query cache only when scores are not needed (IndexSearcher.java:979), so where it runs as a filter the cache cannot reuse an entry for an equal copy (the same instance still hits through the identity check, so only misses, never a wrong hit, LRUQueryCache.java:1341); the distance query is never cached (isCacheable returns false, LatLonPointDistanceFeatureQuery.java:113-114); with assertions on, a NaN dis-max inside a minimumShouldMatch disjunction trips assert Float.isNaN(maxScore) == false (WANDScorer.java:91).
  • Limits. In the study's probe on main (200,000 documents in 4 segments, 11 query shapes, assertions on and off) the set of matching documents was always the same as a finite control's, no hit escaped a FILTER clause, nothing hung and nothing was written. That covers the tested shapes, not every composition. Segments where only one dis-max clause has a scorer keep finite scores.
  • Older releases were worse (NaN tie-breaker, 2 matching documents): 8.0.0 and 8.11.4 return 0 top-k hits (on 8.11.4 count() is 2); 9.12.3 with assertions off returns sentinel ScoreDocs (doc 2147483647, score -Infinity) in place of one or both hits. Their mechanism was not traced, and TopScoreDocCollector says it "will not properly collect hits" with NaN scores (TopScoreDocCollector.java:30-31), so how hits are collected once NaN is accepted is not a stable contract.
  • Likelihood: rare. Normal code passes constant tie-breakers such as 0.1 and fixed pivots; the recorded search found no prior report since 8.0.0 (2019).

Why it looks unintended

#
  • Both checks reject every other out-of-range value (-0.01, 1.01, Infinity; 0, -1).
  • NaN breaks stated contracts: distance scores are documented to lie in [0, weight], Lucene's top-k collector says NaN is not a valid score, and equals must be reflexive for caching.
  • Sibling checks reject NaN: BoostQuery, FeatureField, LogOddsFusionQuery, and GeoUtils in the same LatLon constructor.
The full argument252 words
  • The checks enforce a stated range for every other value. -0.01, 1.01, +/-Infinity and -Float.MIN_VALUE are rejected for the tie-breaker; 0, -0.0, -1 and -Infinity for the pivot (executed controls).
  • The documented score range. LatLonPoint.newDistanceFeatureQuery: "score = weight * pivotDistanceMeters / (pivotDistanceMeters + distance), ie. score is in the [0, weight] range" (LatLonPoint.java:357-368).
  • NaN is not a valid score. TopScoreDocCollector: "The values Float#NaN and Float#NEGATIVE_INFINITY are not valid scores. This collector will not properly collect hits with such scores." (TopScoreDocCollector.java:30-31); the test framework's AssertingScorer asserts !Float.isNaN(score) (AssertingScorer.java:129).
  • equals must work for caching. Query.equals: "This is required so that QueryCache works properly" (Query.java:96-97), and Object.equals must be reflexive. Lucene's own AssertingIndexSearcher rejects a NaN dis-max query in QueryUtils.checkEqual (executed).
  • The NaN-rejecting convention. BoostQuery: Float.isFinite(boost) == false || ... (BoostQuery.java:40; LUCENE-7996, a8a63464e7d, by the same committer 20 days before the dis-max check). FeatureField: pivot <= 0 || Float.isFinite(pivot) == false with the message "pivot must be > 0" (FeatureField.java:700-701). LogOddsFusionQuery: Float.isNaN(alpha) || alpha < 0 || alpha > 1 for the same [0, 1] range (LogOddsFusionQuery.java:82). GeoUtils.checkLatitude, called in the same LatLon constructor: Double.isNaN(latitude) || ... (geo/GeoUtils.java:85-86).
  • Never designed. The dis-max check came as a side change of LUCENE-8097 (maxScore on disjunctions); the pivot check was copied from the long recency feature query (LUCENE-8340), where NaN cannot occur. Neither issue mentions NaN, and no upstream test passes NaN to either constructor.
The devil's-advocate check90 words

The strongest case: no constructor documents @throws, the DisjunctionMaxQuery javadoc states no range at all, and the caller passed NaN, so garbage in, garbage out. The cross-model review rated this argument moderate.

Why it fails: the checks clearly mean to enforce the range their messages state, since they reject every other out-of-range value; the codebase rejects NaN in the sibling checks and tests it; and NaN breaks two stated contracts (the [0, weight] score range, equals reflexivity). It is a good reason for low priority, not for keeping NaN.

Suggested fix

#

Recommended Reject NaN in both tie-breaker checks and a non-finite pivot (3 lines)

Reject NaN first, as the sibling checks do: Float.isNaN(x) || x < 0 || x > 1 in DisjunctionMaxQuery and DisjunctionMaxScorer, and Double.isFinite(pivot) == false || pivot <= 0 for the distance pivot. Validated on main: the repro passes with assertions on and off, the closest core suites (203 tests) and the XML parser suite pass, and check passes.

Trade-offs

  • A caller that passes NaN (or a +Infinity pivot) now gets an exception instead of NaN scores; no valid value changes. Constructor-time cost only.
  • "pivotDistance must be > 0, got Infinity" reads oddly; "must be finite and > 0" would be clearer (cosmetic, not run).
  • BlendedTermQuery.DisjunctionMaxRewrite(float) has no check: with this fix a NaN rewrite method fails later, when rewrite calls new DisjunctionMaxQuery (BlendedTermQuery.java:170-172). The same check in its constructor (:165-167) would fail where the value is set (not run).

Downstream note

#

Downstream, Solr's dismax tie and Elasticsearch's tie_breaker request parameters are parsed with Float.parseFloat and not range-checked before new DisjunctionMaxQuery, so a request with NaN gets NaN scores for that request only (read, not tested).

How it was found

#

A bytecode scan of Lucene's concrete Query classes flagged float fields that equals compares with ==. An SMT solver (Z3) then checked each constructor's range check over IEEE floats: NaN is the only value that passes while out of range. An equality harness and a JUnit test on the real jar confirmed it.

The method in full160 words

Method: semi-formal (recorded so because the Z3 queries confirmed a hypothesis written down beforehand).

  • The unit's bytecode scan (JDK 25 ClassFile API) of all 142 concrete Query classes flagged float and double fields that equals compares with primitive == while hashCode uses the bit pattern, among them DisjunctionMaxQuery.tieBreakerMultiplier and LatLonPointDistanceFeatureQuery.pivotDistance.
  • Z3 obligations over IEEE binary32/binary64 (12, all as expected; two of them concern a BayesianScoreQuery check that is not part of this finding): NaN is the only value that passes each range check while outside its stated range, the negated in-range form of the dis-max check admits no such value, and NaN is a witness that equals by == is not reflexive, while equality by bit pattern is.
  • The unit's bounded-exhaustive equality harness on the stock jar reported NONREFLEXIVE for both classes; the finder reduced it to a public-API JUnit, and an independent reproducer wrote its own and found the NaN scores, the +Infinity pivot and the older-release symptoms.

History

#

Both checks came in 8.0.0 (2019): the dis-max one with LUCENE-8097 (e3f90385b49), the pivot one with LUCENE-8482 (10060a6237c). Executed on 8.0.0 through 10.6.0 and main; never fixed. Older releases were worse: 8.x returned no top-k hits for the NaN dis-max query.

Versions tested9 rows

Introduced by e3f90385b49 "LUCENE-8097: Implement maxScore() on disjunctions." (Adrien Grand, 2017-12-26; JIRA patch, issue now #9145), which added the [0, 1] check to DisjunctionMaxQuery and DisjunctionMaxScorer; and 10060a6237c "LUCENE-8482: Added feature query in LatLonPoint to boost results by distance" (Ignacio Vera, 2018-09-19; issue now #9528), which created the class with the > 0 check and the == equals. Both were first released in 8.0.0.

Before 8.0.0 DisjunctionMaxQuery had no range check at all (1.9.1 to 7.7.3 accept every value; == in equals since 2005), and the distance API did not exist. Both lines are unchanged in every 8.x, 9.x and 10.x tag, 10.6.0, branch_10_6 and upstream main 2f424fd428d (2026-10-30).

LFV-304, snapshot of 2026-11-01

Registry title
DisjunctionMaxQuery and LatLonPoint.newDistanceFeatureQuery accept a NaN tie-breaker or pivot distance (the pivot also +Infinity) because their range checks are false for NaN, so hits score NaN and a NaN query is not equal to itself
Area
core / search and document: query parameter validation (DisjunctionMaxQuery, LatLonPoint distance feature query)
Priority
Low, rank 774: DisjunctionMaxQuery and the distance feature query accept a NaN tie-breaker or pivot and then score NaN, a boundary-value validation gap like the +Infinity finding LFV-113, which it follows.
Impact class
wrong error
Impact note
Applications that pass a NaN tie-breaker to new DisjunctionMaxQuery (from code, or as query text through the XML query parser attribute tieBreaker='NaN') or a NaN or +Infinity pivot to LatLonPoint.newDistanceFeatureQuery get no IllegalArgumentException, and on main and 10.5.2 that query's hits then score NaN (for the dis-max query in every segment where at least two disjuncts have a scorer, including documents that match only one of them), a NaN query is not equal to itself so it never reuses a query-cache entry, and top-k pruning mostly stops; default IndexWriterConfig, codec and searcher, any index size; query-time only, on main the match set is unchanged and nothing is written to the index; released since 8.0.0, and older releases show worse symptoms with a NaN tie-breaker (8.0.0 and 8.11.4 return no top-k hits, 9.12.3 without assertions returns a sentinel ScoreDoc in place of a hit).
Summary
You build a DisjunctionMaxQuery with tieBreakerMultiplier NaN (for example a computed value, or the XML query parser text tieBreaker='NaN'), or a LatLonPoint.newDistanceFeatureQuery with pivotDistance NaN or +Infinity, and expect the IllegalArgumentException that both constructors already throw for every other out-of-range value ('tieBreakerMultiplier must be in [0, 1]', 'pivotDistance must be > 0'). Instead the value is accepted, because the checks are written as 'x < 0 || x > 1' and 'x <= 0', which are false for NaN (and '<= 0' is false for +Infinity): on main the hits come back with NaN scores, although the distance feature javadoc promises scores in [0, weight], and for a NaN value q.equals(q) is false because equals compares the field with ==. Older releases are worse: with a NaN tie-breaker, 8.0.0 and 8.11.4 return no top-k hits while count() finds them, and 9.12.3 with assertions off returns a sentinel ScoreDoc (doc 2147483647, score -Infinity) in place of a hit.
Introduced
Two sites, both first released in 8.0.0 [read: git log -S/-G, blame, tag --contains and merge-base --is-ancestor in the full-history clone; release boundary executed]. (1) DisjunctionMaxQuery: e3f90385b492 'LUCENE-8097: Implement maxScore() on disjunctions.' (jpountz; JIRA patch, no GitHub PR; issue now apache/lucene#9145) added 'if (tieBreakerMultiplier < 0 || tieBreakerMultiplier > 1) throw IAE' to the DisjunctionMaxQuery constructor and the same check to the package-private DisjunctionMaxScorer constructor. Not a regression in the usual sense: before it the class had no validation at all, and equals has compared the float with == since the class was added (3c10854e00f, LUCENE-323, 2005, Lucene 1.9) [exec: 1.9.1, 6.6.6, 7.2.0 and 7.7.3 accept every value]. (2) LatLonPointDistanceFeatureQuery: 10060a6237cc 'LUCENE-8482: Added feature query in LatLonPoint to boost results by distance' (iverase; JIRA patch; issue now apache/lucene#9528) created the class with 'if (pivotDistance <= 0) throw IAE' and the == equals, together with LatLonPoint.newDistanceFeatureQuery; the check was copied from the long-valued recency feature query (LUCENE-8340), where NaN cannot occur. Neither issue discusses NaN. (2017-12-26 (DisjunctionMaxQuery check, e3f90385b492); 2018-09-19 (LatLon pivot check, 10060a6237cc))
