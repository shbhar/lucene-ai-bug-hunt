FSTCompiler.Builder: a very negative directAddressingMaxOversizingFactor turns direct addressing on instead of off

The javadoc says a negative directAddressingMaxOversizingFactor disables direct addressing, but Float.NEGATIVE_INFINITY, or any value below a node-dependent flip point (-1.07e8 for 5 arcs, -4,270 for 100,000 sparse arcs), overflows the int size arithmetic and enables it. Five BYTE4 keys then take 131,085 bytes, not 24; lookups stay correct.

The finding in 30 seconds

#

directAddressingMaxOversizingFactor decides how fixed-length FST nodes are stored. A negative value is documented to mean binary search only; a very negative value overflows the size comparison and selects direct addressing instead.

Background: two ways to store an FST node

#
  1. An FST node with many arcs (at least 5 near the root, or at least 10 anywhere) is stored with fixed-length arcs (unless allowFixedLengthArcs is turned off), so a lookup can jump to the right arc instead of scanning them all.
  2. Binary search keeps one slot per arc: 5 arcs of 4 bytes are 20 bytes. Direct addressing keeps one presence bit for every label between the lowest and the highest: for labels 0 to 1,048,576 that is 131,073 bytes, but a lookup only tests the label's bit and counts the set bits before it.
  3. FSTCompiler.Builder#directAddressingMaxOversizingFactor says how much bigger direct addressing may be than binary search (default 1). Its javadoc: a negative value (e.g. -1) disables direct addressing.

The finding, step by step

#
  1. Build an FST with FSTCompiler.Builder (BYTE4 labels, NoOutputs) and set directAddressingMaxOversizingFactor(Float.NEGATIVE_INFINITY), because the javadoc says a negative value disables direct addressing. Add the keys 0, 1, 2, 3 and 1,048,576 (2^20).
  2. You expect a binary-search root node, 5 arcs of 4 bytes, and a 24-byte FST: exactly what the default factor, -1 or -1e8 give.
  3. Instead the root uses direct addressing, one presence bit for every label from 0 to 1,048,576, and the FST takes 131,085 bytes, the same as with +Infinity. All 5 keys are still found.
  4. Why: allowedOversize = (int) (20 * -Infinity) stops at -2,147,483,648. Then expansionCost = 131,079 - allowedOversize is too big for an int and wraps to -2,147,352,569, and a cost <= 0 means "use direct addressing".

Who is affected

#

Code that builds FSTs itself with FSTCompiler.Builder and turns direct addressing off with a large negative value: Float.NEGATIVE_INFINITY, or a finite value below the node's flip point (about -1.07e8 for 5 arcs, -4,270 for 100,000 sparse arcs). The default and -1 work; no in-tree production code sets the factor. Lookups stay correct; only size grows.

Mechanism, terms and numbers502 words

FSTCompiler.Builder#directAddressingMaxOversizingFactor(float) is documented with "Setting this factor to a negative value (e.g. -1) effectively disables direct addressing, only binary search nodes will be created." (FSTCompiler.java:321-322 at 5adff78bb168), and the setter stores any float. shouldExpandNodeWithDirectAddressing compares the two node sizes in int: allowedOversize = (int) (sizeForBinarySearch * factor) and expansionCost = sizeForDirectAddressing - allowedOversize, and picks direct addressing when expansionCost <= 0 (:631-647). For a very negative factor the cast stops at Integer.MIN_VALUE, the subtraction wraps to a negative value, and the node is written with direct addressing: for the repro the "off" setting gives the same root encoding and FST size as +Infinity. With five BYTE4 keys 0, 1, 2, 3 and 2^20 and Float.NEGATIVE_INFINITY, the FST takes 131,085 bytes instead of 24; every key is still found. Present since the factor was added in 8.4.0 (LUCENE-8920); no in-tree production code sets the factor, so only code that builds FSTs itself with a large negative value is hit.

The bug, step by step (main 5adff78bb168)

#
  1. The node. The repro's root has 5 arcs with labels 0, 1, 2, 3 and 1,048,576: fixed-length (FSTCompiler.java:601-606), not contiguous, so addNode asks shouldExpandNodeWithDirectAddressing which layout to use (:547-555).
  2. The two sizes (:623-627). Binary search: sizeForBinarySearch = 20. Direct addressing: getNumPresenceBytes(1,048,577) = 131,073 presence bytes (FST.java:573-576) plus 6 bytes, sizeForDirectAddressing = 131,079 (printed by an instrumented copy of the method).
  3. Allowed oversize (:631). 20 * -Infinity is -Infinity, and Java's float-to-int cast saturates, so allowedOversize = -2,147,483,648 (Integer.MIN_VALUE).
  4. The wrap (:632). 131,079 - (-2,147,483,648) = 2,147,614,727 exceeds Integer.MAX_VALUE (2,147,483,647), so expansionCost is -2,147,352,569.
  5. The choice (:642-647). expansionCost <= 0 selects direct addressing and adds 2,147,352,569 to the compiler's expansion credit (the probe reads credit=2147352569). The FST is 131,085 bytes, the same as with +Infinity.

Where it flips. For this node every factor down to -1.07367624e8 keeps binary search and every factor from -1.0736763e8 down selects direct addressing (bisected): that is where 131,079 - allowedOversize first exceeds Integer.MAX_VALUE. In general the wrap starts below about -(Integer.MAX_VALUE - sizeForDirectAddressing) / sizeForBinarySearch, so bigger nodes flip at smaller factors. Bisected on main: about -536,838 for a 1,000-arc BYTE4 root (4,005 bytes become 132,080) and about -4,270 for a sparse 100,000-arc root (500,006 bytes become 12,599,884); an independent BYTE2 test flips between -1.43e8 and -1.44e8. -Float.MAX_VALUE and -Infinity always flip. NaN casts to 0 and keeps binary search.

For ordinary negative factors the code is right. Without the wrap, expansionCost is at least sizeForDirectAddressing, and the credit branch needs sizeForDirectAddressing <= allowedOversize * 1.66, which a non-positive bound never allows (:642-645), so binary search wins, as documented. This assumes the node's sizes are themselves positive: for a label range within 7 of Integer.MAX_VALUE, getNumPresenceBytes overflows too (FST.java:573-576), whatever the factor. That separate overflow is not part of this bug (read, not run; not claimed).

Exposure and likelihood230 words
  • Who is hit. Callers of the public FSTCompiler.Builder (its enclosing class FSTCompiler is @lucene.experimental, FSTCompiler.java:68) that pass Float.NEGATIVE_INFINITY, -Float.MAX_VALUE, or a finite value below the node's flip point: about -1.07e8 for the repro's 5-arc node, about -536,838 for a 1,000-arc node, about -4,270 for a sparse 100,000-arc node (bisected on main). The default (1) and the documented -1 work. The only in-tree setter calls are tests (TestUtil.java:111 passes -1f; TestFSTDirectAddressing.java:180, :329 pass test parameters); no codec, suggester or analyzer sets the factor.
  • What happens. A silent change of encoding, not a wrong result: every key is found. Each affected node costs one presence bit per label between its lowest and highest label. BYTE1 labels span at most 256 values, so there it is a small layout change; sparse BYTE2 or BYTE4 labels (code points, numeric ids) make it large: 24 bytes to 131,085 bytes for a 2^20 span (the repro), 34 bytes to 33,554,447 bytes for a 2^28 span, 19 bytes to 7,513 bytes for a sparse BYTE2 node. A 40-key probe with eight such nodes ran out of a 512 MB heap.
  • Narrow reach. It needs direct FSTCompiler use and a factor far below the documented -1 (how far depends on the node); GitHub code search found no caller passing NEGATIVE_INFINITY, and the recorded searches found no report since 8.4.0 (2019).

Why it looks unintended

#
  • The javadoc: "a negative value (e.g. -1) effectively disables direct addressing, only binary search nodes will be created"; the setter accepts any float.
  • For every negative value that does not overflow, the code does exactly that; after the overflow, "off" behaves like +Infinity.
  • The sentence and the int arithmetic came in together (LUCENE-8920); neither its issue nor its PR discusses huge or non-finite factors.
The full argument164 words
  • Contract. "Setting this factor to a negative value (e.g. -1) effectively disables direct addressing, only binary search nodes will be created." (FSTCompiler.java:321-322). Float.NEGATIVE_INFINITY and -Float.MAX_VALUE are negative values, -1 is introduced with "e.g.", and the setter stores any float with no check (:330-333). The sibling setter suffixRAMLimitMB rejects mb < 0 (:282-283) and documents Double.POSITIVE_INFINITY as a sentinel (:267), so an infinite value is a natural "for sure" choice in this Builder, whose javadoc asks callers to "Read parameter documentation carefully." (:239-240).
  • Code and javadoc agree until the overflow. For the repro's node the probe keeps binary search down to -1e8; after the wrap the root encoding and FST size equal those of +Infinity, the opposite of the setting.
  • History. LUCENE-8920 (068b6babac3, apache/lucene-solr#980 by bruno-roustant, 2019; issue #9963) added the setter, the sentence and the arithmetic at once. Nobody in the issue or the PR discusses very large or non-finite factors.
The devil's-advocate check215 words

The argument. The documented value is -1, the one in-tree caller that disables direct addressing passes -1f (TestUtil.java:111), and a comment on #10326 (LUCENE-9286) advises "set ... directAddressingMaxOversizingFactor(-1) - that should disable the direct addressing". "Effectively" may mean the disabling is a side effect meant for ordinary values, the API is @lucene.experimental, and "only binary search nodes" is already loose: contiguous nodes get the continuous encoding even with -1 (FSTCompiler.java:542-546).

Why it is weak as a reading of the javadoc. The sentence covers "a negative value" and gives -1 only as an example. Finite values fail too: -Float.MAX_VALUE, for this node any value below about -1.074e8, and for a sparse 100,000-arc node any value below about -4,270, so it is not about infinity. The result is not slightly off but the opposite of the setting. @lucene.experimental concerns API stability, not silently inverting a setting. Continuous nodes carry no presence bits, which is why the test uses a non-contiguous node.

What survives. The trigger is narrow, lookups stay correct and the recorded searches found no report since 2019, so a maintainer may reasonably answer "use -1" and treat a fix as hardening, or prefer to document what is supported (option C). The guard costs one comparison per fixed-length node.

Suggested fix

#

Recommended A. Return binary search for a negative factor before the arithmetic (recommended)

In shouldExpandNodeWithDirectAddressing, return false (binary search) when the factor is negative, before the int arithmetic. That matches the javadoc for every negative value and changes nothing for negative factors that do not overflow today. The repro passes with assertions on and off, and the 38 FST tests pass.

     int maxBytesPerArcWithoutLabel,
     int labelRange) {
+    // A negative factor disables direct addressing (see the Builder javadoc). Return before the
+    // int arithmetic below, which overflows for very negative factors.
+    if (getDirectAddressingMaxOversizingFactor() < 0) {
+      return false;
+    }
     // Anticipate precisely the size of the encodings.
     int sizeForBinarySearch = numBytesPerArc * nodeIn.numArcs;
All options and trade-offs3 options · 431 words

Option A is a five-line guard that keeps today's behaviour everywhere except the overflow. B and C are alternatives for maintainers who prefer to handle the value in the setter or the javadoc.

A. Return binary search for a negative factor before the arithmetic (recommended) (validated by the checks)

#

Check getDirectAddressingMaxOversizingFactor() < 0 at the top of shouldExpandNodeWithDirectAddressing and return false.

     int maxBytesPerArcWithoutLabel,
     int labelRange) {
+    // A negative factor disables direct addressing (see the Builder javadoc). Return before the
+    // int arithmetic below, which overflows for very negative factors.
+    if (getDirectAddressingMaxOversizingFactor() < 0) {
+      return false;
+    }
     // Anticipate precisely the size of the encodings.
     int sizeForBinarySearch = numBytesPerArc * nodeIn.numArcs;

Trade-offs

One comparison per fixed-length node. On a node whose sizes are positive, every negative factor that does not wrap already gets binary search, so nothing else changes; the default, positive factors and NaN are untouched. On a node whose own size arithmetic overflows (label range within 7 of Integer.MAX_VALUE) it also sends negative factors to binary search, a case that is broken anyway (read, not run). It also covers a second route found by reading and not run (not claimed): with -1 the subtraction is sizeForDirectAddressing + sizeForBinarySearch, which wraps once the sum exceeds Integer.MAX_VALUE, for example on a fixed-length node of about 1.5 GB.

What the checks validated

  • Gradle in scratch worktrees at 5adff78bb168, seed 5EED0001: the repro fails without the guard (assertions on, and -Ptests.asserts=false) and passes with it (both).
  • With the guard: :lucene:core:test --tests 'org.apache.lucene.util.fst.*' passes (9 classes, 38 tests, 5 skipped, 0 failures; includes TestFSTDirectAddressing, TestFSTs, TestUtil), and :lucene:core:checkGoogleJavaFormat passes.
  • Independently, the same guard a few lines lower passes the hunt's tests, the cross-model reviewers' tests and upstream TestFSTDirectAddressing (2 of 2).

B. Normalize in the setter (not run)

#

Store -1 for any negative factor in Builder#directAddressingMaxOversizingFactor.

Trade-offs

Same effect for this bug, but getDirectAddressingMaxOversizingFactor() then returns -1 instead of the value passed, and the 1.5 GB route above stays.

What the checks validated

Not run.

C. Document or reject a range (not run)

#

Say "use -1" and that very negative or non-finite values are unsupported, or reject them in the setter.

Trade-offs

No fixed numeric bound is safe for every node: the flip point depends on the node's size (about -4,270 already for a sparse 100,000-arc node). Documentation alone keeps the silent inversion; rejecting only non-finite values misses finite ones such as -1e9, or -5000 on such a node.

What the checks validated

Not run (documentation only).

Downstream note

#

Downstream code that builds its own FSTs and passes a large negative factor to switch direct addressing off can get FSTs orders of magnitude larger than expected; no in-tree production code sets the factor.

How it was found

#

A proof-obligation audit of the directAddressingMaxOversizingFactor contract: since the javadoc promises binary search for every negative value, shouldExpandNodeWithDirectAddressing must return false for all of them. The obligation holds while the int arithmetic does not overflow and fails once it does; a one-method JUnit test on the public API then witnessed it.

The method in full96 words

The audit took the Builder javadoc's promise as the obligation for shouldExpandNodeWithDirectAddressing over all float values of the factor and checked each step of the size comparison: the float product, the saturating cast and the int subtraction. The obligation fails exactly where the subtraction can wrap, which needs a very negative factor.

An executable one-test repro witnessed it on main with assertions on and off. An independent reproducer, two executed cross-model reviews (OpenAI GPT-5.6, refute and intended lenses), a devil's-advocate verifier and an adjudication then confirmed it, and a version sweep placed its start in 8.4.0.
