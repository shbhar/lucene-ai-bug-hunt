LMSimilarity's default collection model is documented as ttf / (T + 1) but computes (ttf + 1) / (T + 1), so the javadoc's p(w|C) is off by up to 2x (scores are correct)

LMSimilarity.DefaultCollectionModel, the default for Lucene's language-model similarities, is documented as P = occurrences / (tokens + 1) but computes (occurrences + 1) / (tokens + 1): a term seen once among 9 tokens gets 0.2, not the documented 0.1. Scores are correct; only the javadoc is stale (since 4.0.0).

The finding in 30 seconds

#

The default collection model is documented as count / (tokens + 1), but it adds 1 to the count as well.

Background: the language-model similarities

#
  1. LMDirichletSimilarity and LMJelinekMercerSimilarity score a term in a document by comparing how often it occurs there with how common it is in the whole field.
  2. How common it is, P = p(w|C), comes from a CollectionModel, from the term's total count in the field (ttf) and the field's total number of tokens (T). Both scores divide by P.
  3. Unless you pass your own model, the constructors install LMSimilarity.DefaultCollectionModel.

The finding, step by step

#
  1. You score with new LMDirichletSimilarity() (or LMDirichletSimilarity(mu), LMJelinekMercerSimilarity(lambda)), which use the default collection model, and want to check a score by hand. Both scores divide by P = p(w|C), the term's probability in the field as a whole.
  2. Take a term that occurs once (ttf = 1) in a field of 9 tokens (T = 9). The DefaultCollectionModel javadoc says P = ttf / (T + 1), so you expect 1 / 10 = 0.1; the LMSimilarity class javadoc even says ttf / T = 1 / 9.
  3. Lucene computes (1 + 1) / (9 + 1) = 0.2, twice the documented value: computeProbability adds 1 to the count too, and explain prints that P (0.25 for a term seen once among 7 tokens, where the javadoc gives 0.125).
  4. The code is intended (the + 1 was added in 2011 and Lucene's tests pin it); only the two javadoc sentences were never updated. A P computed from the DefaultCollectionModel sentence is off by (ttf + 1) / ttf: 2x for a term seen once, 1.1x for one seen 10 times.

Who is affected

#

Developers using LMDirichletSimilarity or LMJelinekMercerSimilarity with the default model (not Lucene's default similarity) who compute P from the javadoc: to predict or reproduce scores, compare toolkits, or write a similar model. Against the DefaultCollectionModel sentence their P is off by (ttf + 1) / ttf: 2x for a term seen once. Lucene's scores, rankings and explain output are correct.

Mechanism, terms and numbers496 words

LMDirichletSimilarity and LMJelinekMercerSimilarity divide their scores by P = p(w|C), which LMSimilarity.DefaultCollectionModel computes unless the application passes its own CollectionModel. Its javadoc says P is "the number of occurrences of the term in the collection, divided by the total number of tokens {@code + 1}" = ttf / (T + 1), and the LMSimilarity class javadoc says ttf / T, but computeProbability returns (ttf + 1) / (T + 1). For ttf = 1 and T = 9 that is 0.2 instead of the documented 0.1. The code is the intended side: LUCENE-3430 (2011) added the numerator + 1 so that terms with ttf = 0 do not get P = 0, and TestSimilarityBase pins it; it changed only the code, after LUCENE-3357 had kept the javadoc exact a month earlier. Lucene's scores, rankings and explain values are correct; a developer who computes P from the DefaultCollectionModel sentence is off by (ttf + 1) / ttf (from the class sentence, by ((ttf + 1) * T) / (ttf * (T + 1))). The fix is javadoc only (+4/-4 lines).

Mechanism (Lucene main f794ff5a505c, LMSimilarity.java)

#
  • Nested javadoc of DefaultCollectionModel (:141-142): "Models p(w|C) as the number of occurrences of the term in the collection, divided by the total number of tokens + 1." = ttf / (T + 1).
  • Class javadoc (:33-35): DefaultCollectionModel "computes the term probability as the number of occurrences of the term in the collection, divided by the total number of tokens." = ttf / T. The two sentences also disagree with each other.
  • Code (:151): return (stats.getTotalTermFreq() + 1D) / (stats.getNumberOfFieldTokens() + 1D); = (ttf + 1) / (T + 1).
  • fillBasicStats (:69-73) stores that value as the collection probability; LMDirichletSimilarity.score (LMDirichletSimilarity.java:76-82) and LMJelinekMercerSimilarity.score (LMJelinekMercerSimilarity.java:68-74) divide by it; their explain methods print its value as "P, probability that the current term is generated by the collection" (LMDirichletSimilarity.java:89-92, LMJelinekMercerSimilarity.java:82-85), never its formula.
  • Who gets the default model: LMSimilarity() (:55-58), hence LMDirichletSimilarity() (LMDirichletSimilarity.java:71-73), LMDirichletSimilarity(mu) (:57), LMJelinekMercerSimilarity(lambda) (LMJelinekMercerSimilarity.java:60) and IndriDirichletSimilarity(mu) (IndriDirichletSimilarity.java:54-56).

The example, step by step

#
  1. A term with ttf = 1 in a field with T = 9 tokens.
  2. Nested javadoc: 1 / (9 + 1) = 0.1. Class javadoc: 1 / 9 = 0.111.
  3. Code: (1 + 1) / (9 + 1) = 0.2 (the minimal repro's observed value).
  4. End to end (the independent reproducer's test): two documents rare common common and common common common common indexed with new LMDirichletSimilarity(); rare has ttf = 1, the field T = 7. explain shows P = 0.25 = (1 + 1) / (7 + 1); the nested javadoc gives 1 / 8 = 0.125.

Related, not claimed here

#

IndriDirichletSimilarity.IndriCollectionModel (IndriDirichletSimilarity.java:101-113) carries the same sentence, ttf / (T + 1), while its code returns ttf / T (by reading, not run). A javadoc fix could cover it too.

Exposure and likelihood256 words
  • Who. Users of the language-model similarities built without an explicit CollectionModel (the no-argument, mu and lambda constructors; also IndriDirichletSimilarity(mu)) who read the javadoc to work out P. LMSimilarity, LMDirichletSimilarity and LMJelinekMercerSimilarity are @lucene.experimental (IndriDirichletSimilarity extends LMSimilarity but has no tag of its own); none is the default similarity.
  • What they see. From the DefaultCollectionModel sentence, ttf / (T + 1), a P that differs from Lucene's by (ttf + 1) / ttf: 2x for ttf = 1, 1.1x for ttf = 10, about 1.001x for ttf = 1000, so rare terms are where it shows. From the class sentence, ttf / T, the factor is ((ttf + 1) * T) / (ttf * (T + 1)): 1.8x in the example. That is the factor in P; how far a score predicted from it is off depends on the model and its parameters (both scores take a log).
  • User impact evidence. A java-user@ question of 2016-12-20 ("Explain Scoring function in LMJelinekMercerSimilarity Class") asks whether P is col_freq / col_size in order to reproduce scores; it was not answered on that point. It shows the impact; it is not a report of this mismatch.
  • Not affected. Lucene's scores, rankings, matching and explain values; nothing throws; assertions on and off behave the same.
  • Downstream (by reading, not run): Elasticsearch and OpenSearch build their LM similarities with new LMDirichletSimilarity(mu) and new LMJelinekMercerSimilarity(lambda), i.e. with this default model.
  • Likelihood: plausible. Anyone who reproduces query-likelihood scores from the docs hits it, but no report of it since 4.0.0 was found.

Why it looks unintended

#
  • LUCENE-3357 (2011) changed the code to ttf / (T + 1) and added the "+ 1" to this javadoc in the same diff: it was the exact formula.
  • Weeks later LUCENE-3430 added + 1 to the numerator and left both javadocs unchanged; TestSimilarityBase pins the new code.
  • Nothing else states the formula; explain prints only P's value.
The full argument152 words
  • The nested sentence was exact once. 93bf76506b4 (LUCENE-3357, 2011-08-20) changed computeProbability from ttf / T to ttf / (T + 1) and, in the same hunk, added {@code + 1} to the DefaultCollectionModel javadoc.
  • Then only the code changed. 156a5c89ee8 (LUCENE-3430, Robert Muir, 2011-09-12, "fix some sims with SpanQueries (which sometimes score terms with df=0/ttf=0/...)") changed the return line to (ttf + 1F) / (T + 1F), updated the test gold values and touched neither javadoc; the issue thread (#4503) does not discuss the javadoc.
  • The code is the intended side. TestSimilarityBase.testLMDirichlet and testLMJelinekMercer (:379-398) compute their gold values with (TOTAL_TERM_FREQ + 1) / (NUMBER_OF_FIELD_TOKENS + 1.0f). So the fix is to the text, not the code.
  • No other statement of the formula. MIGRATE.md and CHANGES.txt have no entry for it; the package javadoc (package-info.java:55-56) only names the models; explain prints P's value without a formula.
The devil's-advocate check93 words

The strongest defence: these are @lucene.experimental expert classes, the + 1s are smoothing details (the open #9071, LUCENE-8023, calls them formula hacks that could be removed), and the class-level sentence reads as a conceptual summary. That fits the class sentence at best. The nested sentence carries an explicit {@code + 1} and was kept exact once (LUCENE-3357), and @lucene.experimental warns of future API change, not of a wrong formula today. The cross-model reviews rated the defence moderate and rejected it, and the independent devil's-advocate check found it holds only for the class sentence.
