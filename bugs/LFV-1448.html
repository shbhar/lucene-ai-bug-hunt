MultiTermQuery.getTermsEnum's javadoc says the enum is already on the first matching term, but it is unpositioned

MultiTermQuery.getTermsEnum's javadoc says the returned TermsEnum is already on the first matching term, but it is unpositioned and Lucene always calls next() first. So a custom MultiTermQuery that positions its enum as told silently skips its first term in every segment: 1 hit instead of 2 in the repro.

The finding in 30 seconds

#

Two sentences in the MultiTermQuery javadoc promise a positioned enum. The code returns an unpositioned one, as TermsEnum's own contract says, and every consumer calls next() first. Code that trusts the sentences is off by one term.

Background: how a multi-term query expands

#
  1. A TermsEnum walks one field's terms in sorted order. A new enum sits before the first term; next() moves to the first term and then to each following one (TermsEnum class javadoc).
  2. A MultiTermQuery (prefix, wildcard, fuzzy, range, ...) finds its terms per segment: it calls getTermsEnum, then loops while ((term = termsEnum.next()) != null) and collects each term's documents.
  3. To add your own multi-term query, the class javadoc says: subclass MultiTermQuery and implement getTermsEnum(Terms, AttributeSource), usually returning a FilteredTermsEnum.

The finding, step by step

#
  1. You write your own MultiTermQuery, here a PrefixQuery for f:b. Its getTermsEnum(Terms, AttributeSource) javadoc says "The TermsEnum must already be positioned to the first matching term", so you call next() once on the enum before you return it.
  2. You index 2 documents, f = banana and blueberry, and expect IndexSearcher.count to be 2, like the stock PrefixQuery f:b*.
  3. You get 1, with no error. Lucene's rewrite calls next() itself before it reads the first term, so it starts at blueberry and the banana document is lost. This happens in every segment.
  4. The public getTermsEnum(Terms) makes the same promise: reading term() before next() gives the empty term '', not banana. The code is right; only these two sentences are wrong.

Who is affected

#

Only application code that follows these two sentences: a hand-written MultiTermQuery subclass that positions its enum, or a direct getTermsEnum caller that reads term() first. The stock queries and every Lucene consumer are correct. Opt-in expert API, default codec, no scale needed; every release since 4.0.0.

Mechanism, terms and numbers581 words

MultiTermQuery is the base class of PrefixQuery, WildcardQuery, FuzzyQuery and friends, and its class javadoc tells you to subclass it and implement getTermsEnum(Terms, AttributeSource) to add your own multi-term query. That method's javadoc says "The TermsEnum must already be positioned to the first matching term" (MultiTermQuery.java:297), and the public wrapper getTermsEnum(Terms) says "The returned TermsEnum is positioned to the first matching term" (:306).

Both are wrong. Like every new TermsEnum ("unpositioned when you first obtain it", TermsEnum.java:34-35), the enum starts before the first term, and every consumer calls next() to get the first term (TermCollectingRewrite.java:65, AbstractMultiTermQueryConstantScoreWrapper.java:175). So a subclass that positions its enum as told loses that term in every segment, silently, with assertions on and off: a PrefixQuery f:b subclass over banana and blueberry counts 1 document where the stock query counts 2. A caller of the public method who reads term() first gets the empty term '' (on a plain DirectoryReader).

The unpositioned enum is the intended design (LUCENE-2110, #3186, 2009), and the stock queries and every in-tree consumer are correct. The sentence was true on the flexible-indexing branch before that change, reached the main line stale with the flex merge (b679816a700, 2010, first released in 4.0.0), and was copied onto the then newly public method in 8.4.0 (LUCENE-8983). The fix is javadoc only.

Why the subclass loses a term

#

In both rewrite consumers next() is the call that yields the first term. An enum the subclass already moved to banana is moved on to blueberry before anything is collected. getTermsEnum is called once per segment, so the first matching term of every segment is lost, with all documents that match only that term (read from the per-segment code path; the repro has one segment). Nothing checks for it, so there is no error with -ea or -da; the stock query on the same index counts 2. The scoring boolean rewrite loses the term the same way (an independent check counted 1 there too).

The public method

#

new PrefixQuery(new Term("f", "b")).getTermsEnum(terms).term() over apple, banana, blueberry returns '' on a plain DirectoryReader, with no error; next() then returns banana. The same holds for WildcardQuery, RegexpQuery, TermRangeQuery, FuzzyQuery and TermInSetQuery. With -da docFreq() on that enum is 0. With assertions on, the test framework's AssertingLeafReader rejects the call (a Java assert: "term() called on unpositioned TermsEnum", AssertingLeafReader.java:378 in lucene/test-framework), which shows that Lucene treats it as misuse of the enum, contrary to the javadoc.

Exposure and likelihood167 words
  • Who: developers who add their own multi-term query the documented way (subclass MultiTermQuery, implement getTermsEnum) and position the enum as its javadoc requires; and developers who call the public getTermsEnum(Terms) and read term() before next(), as its javadoc describes.
  • What happens: silent wrong results. The subclass misses every document that matches only its first term in a segment. The direct caller takes '', a term the query does not match, as its first expansion.
  • Not affected: the stock queries (PrefixQuery, WildcardQuery, RegexpQuery, TermRangeQuery, FuzzyQuery, TermInSetQuery, AutomatonQuery) and every in-tree consumer. The Elasticsearch, OpenSearch and Solr code that was checked also calls next() first and returns unpositioned enums.
  • How likely: rare. TermsEnum's own class javadoc points the right way, the usual idiom calls next() first, and no report of it since 4.0.0 (2012) was found.
  • How long: the extension point's sentence in every release from 4.0.0 to 10.6.0 and main; the public method's since 8.4.0.

Why it looks unintended

#
  • Both sentences are the most specific statements about these methods and say the opposite of what the code does; nothing in the history defends them.
  • LUCENE-2110 (#3186, 2009) made the enum unpositioned on purpose and switched the loops to next() first, but left this sentence.
  • No test asserts the positioned form; the in-tree example subclasses all return unpositioned enums.
The full argument220 words
  • Contract. MultiTermQuery.java:297: "The TermsEnum must already be positioned to the first matching term." :306: "The returned TermsEnum is positioned to the first matching term." The class javadoc sends subclass authors to exactly this method (:34-36).
  • Design. LUCENE-2110 (#3186, reported and committed by Uwe Schindler, 2009): "FilteredTermsEnum is confusing as it is initially positioned to the first term. It should instead work like an uninitialized TermsEnum for a field before the first call to next() or seek()." LUCENE-2784 (#3858) restates that a TermsEnum must be unpositioned initially, before next().
  • History. The promise was written on the flexible-indexing branch (LUCENE-1458, 2009-10-13) while it was true: the rewrite loops then read term() first. LUCENE-2110 changed the loops and the enum, not the sentence. The flex merge b679816a700 (LUCENE-2370, 2010-04-06) brought it to the main line, in the same commit as a rewrite loop that already calls next() first. LUCENE-8983 (8485b5a939c, 2019) made getTermsEnum(Terms) public and copied the promise onto it.
  • Context. When making the method public was discussed, Uwe Schindler wrote on apache/lucene-solr#889 (2019-11-15) that "we should clearly define how this method must be called". The sentence that was then added defines it wrongly.
  • Tests. No test asserts the positioned form. The in-tree example subclasses return a fresh FilteredTermsEnum (TestPrefixRandom.java:89-90, TestRegexpRandom2.java:122-123, TestMultiTermQueryRewrites.java:173-174).
The devil's-advocate check202 words

The intended-behaviour check built the strongest not-a-bug case: TermsEnum's class javadoc already says every new enum is unpositioned; FilteredTermsEnum seeks lazily on the first next(); the test framework rejects term() before next() when assertions are on; TermsEnum itself is @lucene.experimental (TermsEnum.java:37); every consumer in Lucene and the downstream code checked is next()-first; custom subclasses are expert; the sentence has stood unreported for 16 years. It also noted that the same paragraph asks for TermsEnum.EMPTY when nothing matches, and EMPTY.term() throws (TermsEnum.java:243-244), so the sentence could never have worked as a contract on its own.

Why it fails: all of this shows the code is intended, which nobody disputes. None of it defends the two sentences (no commit, test, issue or list thread found in the searches does), and a reader who trusts a method's own javadoc over the general class javadoc gets silent wrong results. Verdict: a documentation defect; fix the javadoc, not the code. Every check agreed, including the reviews by a model from another family. A maintainer may still read the term()-first call on the public method as plain misuse of an iterator and prefer to just delete the sentences (option B).

How it was found

#

The method in full103 words
  • Obligation: if getTermsEnum returns an enum already on the first matching term, every consumer must read term() before its first next().
  • Check: the stock implementations (CompiledAutomaton.getTermsEnum, FilteredTermsEnum) return unpositioned enums, and both rewrite consumers (TermCollectingRewrite, AbstractMultiTermQueryConstantScoreWrapper) call next() first, so the obligation fails for both sentences.
  • Witness: a JUnit test on main f794ff5a505c (public method: term() is '', not banana) and probes over 8 stock queries (6 query classes) and a subclass written to the javadoc (1 hit instead of 2), with assertions on and off.
