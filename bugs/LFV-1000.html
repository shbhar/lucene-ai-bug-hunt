On main, LRUQueryCache's statistics callbacks run concurrently, but its javadoc still says "under a lock"

The finding in 30 seconds

#

A documentation defect on main: the concurrency is intended, but the callback javadoc still describes the old single lock.

Background: the query cache and its statistics callbacks

#
  1. LRUQueryCache caches the documents that a filter clause matches, per segment. For finer statistics its javadoc says to override protected callbacks and recommends onCacheEntryInserted / onCacheEntryEvicted, which fire per entry; onClear() fires when the cache is cleared.
  2. Up to 10.x the whole cache had one lock. Every insertion, eviction and clear callback ran under it, one at a time, and a search that found the lock busy simply skipped the cache.
  3. On main (#15558, in no release) the cache is split into partitions, 16 by default, each with its own lock. A query's partition is query.hashCode() & 15.

The finding, step by step

#
  1. You subclass LRUQueryCache to keep your own statistics, as its javadoc suggests: entries++ in onCacheEntryInserted, entries-- in onCacheEntryEvicted, with a plain int field, and you search from several threads.
  2. You expect one callback at a time, as on 10.x: there one lock for the whole cache covered every insertion, eviction and clear callback, so a plain counter stayed exact. The javadoc still says they are "called synchronously and under a lock".
  3. On main the cache has 16 partitions, each with its own lock, picked by the query's hash. Two searches whose queries land in different partitions insert at the same time: the repro sees 2 insertion callbacks running at once.
  4. With 4 search threads and no latches or sleeps, a plain counter ends off in 4 of 5 rounds (489 against getCacheSize() 492, up to 3 callbacks at once); on 10.6.0 in 0 of 5. And clear() calls onClear() holding none of the cache's locks.
  5. Search results and the cache's own counters stay correct; only the subclass's numbers drift. The concurrency is intended; the javadoc and MIGRATE.md just never say so.

Who is affected

#

Only main and branch_11x (the coming 11.0). It takes an application-installed LRUQueryCache subclass that keeps statistics in the insertion, eviction or clear callbacks with plain fields, the pattern the 10.x base class itself used; the query cache is off by default on main. Ordinary concurrent searches are enough. Results and the cache's own counters stay correct.

Mechanism, terms and numbers682 words

LRUQueryCache invites subclasses to keep "more fine-grained statistics, such as per-index or per-query-class statistics" by overriding its callbacks (onHit, onMiss, onClear and the deprecated per-query and per-DocIdSet hooks; it recommends the newer unified onCacheEntryInserted / onCacheEntryEvicted), and its class javadoc ends: "It is better to not perform heavy computations in these methods though since they are called synchronously and under a lock." Up to 10.6.0 that lock was one lock for the whole cache, so every insertion, eviction and clear callback ran alone, and Lucene's own base callbacks updated plain fields after asserting the lock was held.

On main, #15558 split the cache into partitions (16 by default) with one lock each, and a query goes to the partition picked by its hash. Insertion and eviction callbacks hold only their partition's lock, so callbacks of different partitions run at the same time, and clear() calls onClear() after releasing every partition lock, holding none of the cache's locks. That concurrency is the purpose of the change. The defect is documentation: the sentence was kept, it is false for onClear(), and neither the javadoc nor the MIGRATE.md section for #15558, which shows a subclass overriding these callbacks, says that implementations must now be thread-safe. A subclass that counts with plain fields silently loses updates; search results, the cache's own counters and its memory bound stay correct.

What the javadoc says

#

The class javadoc (LRUQueryCache.java:88-101 at 645d4fe14a20) lists the callbacks for "per-index or per-query-class statistics", onClear among them, and ends: "It is better to not perform heavy computations in these methods though since they are called synchronously and under a lock." The sentence dates from LUCENE-6157 (2015). In every release it described one cache-wide lock: in 10.5.2 the base onQueryCache, onQueryEviction, onDocIdSetCache, onDocIdSetEviction and onClear each start with assert writeLock.isHeldByCurrentThread(); and then do plain += / -= / = 0 (10.5.2 LRUQueryCache.java:229-280), and clear() calls onClear() inside writeLock.lock() (:415-426).

What main does

#
  1. A query goes to partition queryHash & (numberOfPartitions - 1) (:426, :437; 16 partitions by default, :150). Each partition has its own ReentrantReadWriteLock (:956-959).
  2. putIfAbsent takes only that partition's write lock and calls onQueryCache, onDocIdSetCache and onCacheEntryInserted under it (:1100-1131); evictions do the same in remove (:1155-1189). Two queries in different partitions take different locks, so their callbacks run in parallel.
  3. clear() clears partition 0 to 15, each under its own lock, then calls onClear() holding none of the cache's locks (:457-463). So onClear() is not "under a lock" for any number of partitions.
  4. onHit / onMiss run under the partition's shared read lock (:1064-1081); they could already overlap since 9.11.0 (#13306). Only the insertion, eviction and clear overlap is new on main.
  5. The cache's own numbers are kept per partition, under each partition's lock (:1037-1058, :1139-1143), and the memory bound uses them, so Lucene stays correct. Only state a subclass updates from more than one partition is exposed, and the documented per-index statistics normally are such state: they add up many queries, and different queries go to different partitions by hash (all entries of one query stay in one partition, :949-951).

The numbers

#

  • The finder's stress (4 threads x 4,000 searches for 64 random terms over 8 segments, occasional clearQuery() + cleanUp(), no clear(), no latches or sleeps (each callback calls Thread.onSpinWait() once after its update), a plain int counter in onDocIdSetCache / onDocIdSetEviction): the counter ends off in 4 of 5 rounds (489, 491, 493, 499 against getCacheSize() 492, 492, 492, 500), up to 3 callbacks at once; on 10.6.0 0 of 5 rounds, 1 at a time.

Exposure and likelihood233 words
  • Who is hit. Applications on 11.0 (main and branch_11x today) that install their own LRUQueryCache subclass and keep statistics in onCacheEntryInserted, onCacheEntryEvicted, the deprecated per-query / per-DocIdSet hooks or onClear() with plain (non-atomic) fields. Their numbers drift silently: no exception, no assertion.
  • Default vs opt-in. Opt-in: the query cache is off by default on main (IndexSearcher.java:84, DEFAULT_QUERY_CACHE = null; CHANGES.txt:343, #14187), and only a subclass that overrides the callbacks is affected. Lucene's own production code has no such subclass.
  • Scale. Ordinary concurrent searching is enough for the cross-partition part: the stress uses no clear(), no latches and no sleeps (each callback calls Thread.onSpinWait() once after its update) and ends off in 4 of 5 rounds. That shows the race happens; it is not a rate for real workloads. The error per round is small (off by 1 to 3 of about 500 in the stress), and Lucene never corrects a subclass's field; later lost updates can add to it or offset it.
  • Not affected. Search results, getCacheSize(), ramBytesUsed(), the base class's hit/miss counts (LongAdder, LRUQueryCache.java:124-125) and the memory bound.
  • No release has the insertion, eviction or clear overlap, 10.6.0 included: #15558 was not backported. Only onHit / onMiss overlapped before, under the shared read lock since 9.11.0 (#13306), with the same missing thread-safety note; the documentation fix covers them too.

Why it looks unintended

#
  • The javadoc offers these callbacks for per-index statistics and says they run "under a lock"; onClear() now runs under none.
  • On 10.x Lucene's own callbacks did plain += under the asserted cache lock; #15558 edited this paragraph and kept the sentence.
  • MIGRATE.md shows a subclass overriding them with no thread-safety note; QueryCachingPolicy states that duty.
The full argument221 words
  • The contract text (LRUQueryCache.java:91-101): "In case you would like to have more fine-grained statistics, such as per-index or per-query-class statistics, it is possible to override various callbacks: ... and {@link #onClear}. ... they are called synchronously and under a lock." onClear() is in the list and runs with no cache lock held (:458-463).
  • Lucene's reference implementation relied on it. 10.5.2 LRUQueryCache.java:229-280: each base insertion, eviction and clear callback asserts the single write lock and updates plain fields.
  • #15558 edited this paragraph and kept the sentence. Its squash commit d50fb36d9af3 added the "per cache entry, not per unique query" and "Prefer the newer unified callbacks" sentences (:94-99) and the partition sentence (:66-68). Its review never discusses callback concurrency; msokolov summed it up as "segment the cache into blocks that can be updated concurrently, so no functional change expected?".
  • The migration guide is silent. MIGRATE.md:514-542 (#16756) shows MyQueryCache extends LRUQueryCache overriding onCacheEntryInserted / onCacheEntryEvicted, with no thread-safety note.
  • Lucene states such duties where they apply: QueryCachingPolicy.java:24, "Implementations of this class must be thread-safe." (precedent pointed out by the independent cross-model reviewer).
  • Reliance is real. In 2019 Ben Manes read the contract as running these callbacks "under the global lock", so that "implementations may rely on this exclusive read/write access" (#10081 / LUCENE-9038).
The devil's-advocate check259 words

The strongest case for "nothing to fix" (built by the devil's-advocate verifier, and from the refute review's reading): per-partition concurrency is the whole point of #15558, and main documents that "the cache is split into multiple partitions to reduce lock contention" (:66, :155-157); "under a lock" is performance advice that never said "the same lock" and is still true for every callback but onClear(); onHit / onMiss have overlapped under a shared read lock since 9.11.0 (#13306), where, at benwtrent's suggestion, the base class's own hit/miss counters became LongAdder; Lucene's own callback tests count with AtomicLong / AtomicInteger (TestLRUQueryCache.java:991-997, :2727-2736); and every hook is @lucene.experimental.

Why it fails: it defeats a code-bug claim, which is why none is made, and one cache-wide callback lock would be the wrong fix. It does not defeat the documentation defect. onClear() is called with none of the cache's locks held, so the sentence is false for one of "these methods" whatever "a lock" means (shown even with one partition). The documented use, per-index statistics, must keep state across partitions, and nothing tells the author that this state is now updated concurrently, while the 10.x base class showed the plain-field pattern. @lucene.experimental permits the change but does not make stale javadoc correct, and tests are not documentation. The verifier also noted, fairly, that the onHit / onMiss gap already existed on 10.x; the same doc fix covers it. Verdict: a documentation defect, not a code bug. This framing is the cross-model reviewer's and the verifier's.

Suggested fix

#

Recommended A: state the concurrency in the javadoc and MIGRATE.md (recommended, validated)

Documentation only: replace "under a lock" with what main does (callbacks of different partitions, onHit / onMiss, and onClear() may run concurrently, so implementations that keep statistics must be thread-safe), say on onClear() that it holds no lock, and add the same note to the #15558 section of MIGRATE.md.

 * perform heavy computations in these methods though since they are called synchronously, and all
 * of them but {@link #onClear} are called while holding the lock of a cache partition.
 *
 * <p>These callbacks may be called concurrently from several threads: callbacks for entries of
 * different partitions can run at the same time, {@link #onHit} and {@link #onMiss} only hold a
 * shared read lock, and {@link #onClear} is called without holding any lock. Implementations that
 * keep statistics in these callbacks must therefore be thread-safe, for instance by using {@link
 * LongAdder}.

// onClear(): "called by clear() after all partitions have been cleared, without holding any lock"
// MIGRATE.md, #15558 section: the same note for subclasses
All options and trade-offs4 options · 609 words

One option was built and checked (A); B depends on a sibling fix; C and D are listed because they come up and should be avoided.

A: state the concurrency in the javadoc and MIGRATE.md (recommended, validated)

#

The finder's wording, narrowed by the reviewers: the class javadoc's last sentence of the callback paragraph becomes a description of main's locking plus a thread-safety duty; onClear() gets one line; MIGRATE.md's #15558 section gets one paragraph.

 * perform heavy computations in these methods though since they are called synchronously, and all
 * of them but {@link #onClear} are called while holding the lock of a cache partition.
 *
 * <p>These callbacks may be called concurrently from several threads: callbacks for entries of
 * different partitions can run at the same time, {@link #onHit} and {@link #onMiss} only hold a
 * shared read lock, and {@link #onClear} is called without holding any lock. Implementations that
 * keep statistics in these callbacks must therefore be thread-safe, for instance by using {@link
 * LongAdder}.

// onClear(): "called by clear() after all partitions have been cleared, without holding any lock"
// MIGRATE.md, #15558 section: the same note for subclasses

Trade-offs

  • Documents the intended behaviour instead of changing it: no runtime cost, no behaviour change, the partitioning keeps its purpose.
  • It does not help a subclass that already relies on the old lock; such code has to switch to atomics (LongAdder, AtomicLong). The note should not suggest synchronized (this) on the cache: cleanUp() is synchronized on the cache instance (LRUQueryCache.java:1392), the sibling deadlock LFV-1001.
  • If LFV-991's fix lands (clear() calls onClear() under every partition lock), the onClear() clause must be dropped again.
  • Wording caveats: "without holding any lock" means none of the cache's locks (the caller of clear() may hold its own), and "after all partitions have been cleared" does not mean the cache is still empty when onClear() runs: other threads can refill it first (LFV-991).

What the checks validated

  • Stock 645d4fe14a20 (gradle, scratch worktree): the minimal test fails with assertions on (seed DEADBEEF) and off.
  • With A: checkGoogleJavaFormat, ecjLintMain and renderJavadoc for core pass; TestLRUQueryCache passes (40 tests, 3 skipped, 0 failures) with assertions on (seed DEADBEEF) and off (seed C0FFEE).
  • With A the minimal test still fails, with assertions on and off, as expected: A changes no code, and the test encodes the 10.x behaviour.
  • The diff applies cleanly to a pristine 645d4fe14a20.

B: A, plus LFV-991's code fix for clear() (not run)

#

Make clear() take every partition's write lock and call onClear() under them (LFV-991's validated fix), then document only the cross-partition concurrency.

Trade-offs

Makes "under a lock" true again for onClear() and fixes LFV-991's lost statistics, but must land together with LFV-1001's fix (cleanUp() on a private lock) to avoid a lock-order deadlock. The cross-partition overlap stays and still needs A's note: with that fix the finder's cross-partition test still fails.

What the checks validated

Not run (in this doc; LFV-991's doc reports its own validation, and the finder's run with that fix shows that only the onClear test passes).

C: serialize all callbacks with one cache-wide lock (not recommended)

#

Wrap every callback in a single extra lock, so the old sentence becomes true.

Trade-offs

Brings back the cache-wide contention #15558 removed on every insertion and eviction; the reviewers and the devil's-advocate verifier called it the wrong fix. Not run.

D: tell subclasses to synchronize on the cache (not recommended)

#

A one-line javadoc telling implementations to use synchronized methods.

Trade-offs

Deadlocks: cleanUp() holds the cache's monitor while it waits for partition locks, and a search holds a partition lock while its callback waits for the monitor (LFV-1001). Recommend atomics instead.

Downstream note

#

Downstream: Elasticsearch's query-cache subclass says in a code comment that its callbacks need no lock "since it is done in LRUQueryCache", above += updates of its statistics, also on its Lucene 11 branch; whether those statistics drift there was not tested.

How it was found

#

A probe ran a plain-counter stress on the stock main jar and saw lost updates and up to 3 callbacks at once, none on 10.6.0. The finder turned it into deterministic public-API JUnits and a TLA+ model of the partitioned cache; reviewers then narrowed the claim to a documentation defect.

The method in full181 words

Method: non-formal first signal, formal confirmation. A probe for the partitioned query cache ran a latch-free plain-counter stress on the stock jars: on main up to 3 insertion and eviction callbacks ran at once and the counter lost updates in 11 of 15 rounds of a three-fold re-run; on the 10.6 release commit 1 at a time and 0 of 5.

The finder (a hunt unit) turned it into deterministic public-API JUnits (one callback held open by a latch with a bounded wait: does a second callback start?) for two insertions and for onClear() plus an insertion, and wrote a TLA+ model of the partitioned cache. TLC violated the invariant CallbacksSerialized on main in 4 steps (two inserts in two partitions), found no violation for the 10.x single-lock reference (853,774 distinct states, exhaustive), and still violated it with the sibling clear() fix.

The independent cross-model reviewer (OpenAI GPT-5.6, intended lens, read-only) and the devil's-advocate verifier then narrowed the claim: the concurrency is intended, the documentation is not. The minimal repro reduces the evidence to one test of the cross-partition insertion overlap.

LFV-1000, snapshot of 2026-11-05

Registry title
On main, LRUQueryCache's class javadoc still says its statistics callbacks are 'called synchronously and under a lock', but since #15558 the callbacks of different partitions run at the same time and onClear() runs under no lock, and neither the javadoc nor MIGRATE.md tells subclasses that their statistics must now be thread-safe (documentation defect, main only)
Area
search / query cache (LRUQueryCache callback javadoc and MIGRATE.md)
Priority
Low, rank 1265: This main-only stale javadoc and MIGRATE.md gap in the core LRUQueryCache misleads only through its false 'under a lock' sentence, which lets a subclass's own plain-field statistics lose updates while results, cache size and the memory bound stay correct.
Impact class
minor
Impact note
Documentation only, on unreleased main (11.0): an application that subclasses LRUQueryCache, keeps statistics in plain fields in the insertion, eviction or clear callbacks and relies on the javadoc's 'under a lock' (true for these callbacks on every 10.x and earlier release) loses updates under concurrent searches (4 of 5 stress rounds on main, 0 of 5 on the 10.6 RC); search results, the cache's own getCacheSize()/ramBytesUsed() and its memory bound stay correct, the default query cache is off on main, and every release, 10.6.0 (released 2026-10-29) included, is unaffected.
Summary
You subclass LRUQueryCache to keep per-index statistics in its callbacks, as the class javadoc suggests, and trust its sentence that the callbacks 'are called synchronously and under a lock', which on 10.x meant one cache-wide write lock around every insertion, eviction and clear callback, so plain fields were safe. On main, #15558 gave each partition (16 by default) its own lock, so insertion and eviction callbacks of different partitions run at the same time (2 at once in a deterministic JUnit, up to 3 in a stress where a plain counter loses updates), and clear() calls onClear() with no lock held. The partitioning itself is intended; the defect, as the independent cross-model reviewer and a verifier framed it, is that the sentence was kept unchanged (it is now false for onClear()) and that neither the javadoc nor MIGRATE.md says callback implementations must now be thread-safe.
