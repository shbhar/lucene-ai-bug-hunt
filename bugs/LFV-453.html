updateDocuments with an empty block leaks about 33 KB of IndexWriter RAM accounting per update-and-refresh round, until the writer flushes after every new document

An updateDocuments or softUpdateDocuments call with an empty list of documents charges about 33 KB to IndexWriter's RAM total, and the next refresh never gives it back. After about 500 such rounds the default 16 MB buffer looks full for good, and the writer flushes after every new document.

The finding in 30 seconds

#

IndexWriter keeps a running total of the RAM its per-thread buffers use and flushes when the total reaches the RAM buffer. An empty-block update still takes a per-thread buffer and stores the delete key in it. The next refresh finds that buffer with 0 documents and drops it without subtracting its bytes.

Background: how IndexWriter counts buffered RAM

#
  1. New documents and deletes are buffered in per-thread writers (DWPTs); each one becomes a segment when it is flushed.
  2. A flush control adds up the bytes the per-thread writers use. ramBytesUsed() reports that total, and when it reaches the RAM buffer (16 MB by default) the largest writer is flushed.
  3. A refresh (DirectoryReader.open(writer)), commit() or flush() flushes every per-thread writer and subtracts its bytes from the total.

The finding, step by step

#
  1. Open an IndexWriter with the default config (16 MB RAM buffer). Call updateDocuments(new Term("id", "a"), List.of()), meaning "delete key a, add nothing", then refresh with DirectoryReader.open(writer).
  2. You expect the delete to apply and nothing to stay buffered: ramBytesUsed() is 0, as after deleteDocuments(term) or addDocuments(List.of()).
  3. Instead ramBytesUsed() is 33,040. The call took a per-thread buffer and stored the key in it (a 32 KB block); the refresh found that buffer with 0 documents and dropped it without subtracting its bytes.
  4. Every such round adds the same: 20 rounds give 660,800 bytes, 600 rounds give 19,824,000, more than the 16 MB buffer. From then on every added document triggers a flush (single-threaded: 200 small documents, 200 flushes) until the writer is closed.
  5. The delete still applies and no hit is wrong. With assertions on (-ea), close() already fails after one round: netBytes has unexpected value 0 != 33040.

Who is affected

#

Applications that pass a possibly empty list to updateDocuments(term, docs) or softUpdateDocuments, for example "replace key K's documents with this list". The default config is enough. About 500 such refresh rounds in one writer's life make it flush every document separately until it is closed. No hit is wrong; nothing on disk is malformed.

Mechanism, terms and numbers878 words

IndexWriter.updateDocuments(term, block) and softUpdateDocuments(term, block, softField) accept an empty block: delete or soft-delete by key, add nothing. The delete applies, but the call still takes a per-thread writer (DWPT) and stores the key in that writer's private buffer, so the flush control adds 33,040 bytes (32,960 on the soft path) to its running RAM total. The next full flush (an NRT reopen, commit() or flush()) finds the writer with 0 documents and "drop[s] it on the floor" in DocumentsWriterFlushControl.markForFullFlush without subtracting those bytes; every other exit (flush, abort) subtracts them.

So ramBytesUsed() grows by about 33 KB per such round (an empty-block update, then a full flush) and never comes down for the life of the writer, even past the real heap. Once the phantom total reaches the RAM buffer (16 MB by default, about 500 rounds), the flush policy fires after every added document, so in a single-threaded writer each document becomes its own segment, with the merge and I/O work that follows. No hit is wrong and nothing on disk is malformed; closing the writer clears it. With assertions on, one round makes close() fail and, at the buffer, the writer closes itself. It dates from 4.5.0 (2013); since 9.9.0 (and 7.7.0 on the soft path) each round leaks about 33 KB instead of 165-330 bytes. A four-line fix in the drop branch releases the bytes.

The bug, step by step (main 645d4fe14a20)

#
  1. The call. IndexWriter.updateDocuments(Term, Iterable) (IndexWriter.java:1593-1610) wraps the term in a delete node and calls DocumentsWriter.updateDocuments; softUpdateDocuments (:1644-1675) does the same with a doc-values update node. It rejects a null term and missing soft-delete fields (:1667-1672), not an empty block.
  2. A writer is taken anyway. DocumentsWriter.updateDocuments (DocumentsWriter.java:412-454) always calls flushControl.obtainAndLock() (:418).
  3. The key lands in the writer's private buffer. In DocumentsWriterPerThread.updateDocuments (DocumentsWriterPerThread.java:245-301) the loop over the block runs zero times, so the writer keeps 0 documents. finishDocuments (:361-390) adds the delete to the global queue and applies it to the writer's own pendingUpdates with docIdUpTo = 0 (:374-377): it can delete nothing here, but the term is stored. The first term allocates the 32 KB first block of BufferedUpdates.DeletedTerms' ByteBlockPool (BufferedUpdates.java:183-184, ByteBlockPool.BYTE_BLOCK_SIZE = 1 << 15) since #12573 (9.9.0); on the soft path FieldUpdatesBuffer accounts a 32 KB block since LUCENE-8590 (7.7.0). Measured: 33,040 bytes (hard) and 32,960 (soft) per round.
  4. The bytes are charged. DocumentsWriterFlushControl.doAfterDocument (DocumentsWriterFlushControl.java:207-250) skips deltas below 16 KB (:211-215); 33,040 bytes is above that, so it commits them to the writer (:225) and adds them to activeBytes (:236). The writer goes back to the pool with 0 documents.
  5. The full flush forgets them. A refresh, commit or flush calls markForFullFlush (:557). A writer with documents is marked pending, which moves its bytes to flushBytes (:365-376), and doAfterFlush subtracts them once the segment is written (:290-295). A writer with 0 documents takes the branch at :596-602, "In this case we simply remove it from the pool and drop it on the floor": perThreadPool.checkout(next) and nothing else. doOnAbort (:378-389) shows the intended bookkeeping: it subtracts getLastCommittedBytesUsed().
  6. Nobody can take them back. The dropped writer is out of the pool, so no later flush, abort or deleteAll() sees it (executed in the fact check: 33,040 bytes remain after a further commit() and after deleteAll()). No operation on the still-open writer repairs the total; rollback() closes the writer and, under -ea, hits the same netBytes assertion (by reading). ramBytesUsed() (IndexWriter.java:796-799 -> DocumentsWriterFlushControl.java:501-504) keeps the bytes until the writer is closed.
  7. The flush storm. FlushByRamOrCountsPolicy.onChange (FlushByRamOrCountsPolicy.java:34-53) flushes the largest writer when activeRam + deletesRam >= limit (:49-50). Once the phantom bytes alone reach the limit, that holds after every added document, so every document triggers a flush of the largest non-pending writer that holds documents (DocumentsWriterFlushControl.java:749-772). In a single-threaded workload that is the writer holding just the new document: one segment per document. With several indexing threads it can be another, larger writer (by reading).
  8. With -ea. The next empty-block update after that point reaches assert perThread.getNumDocsInRAM() > 0 (FlushPolicy.java:74); IndexWriter treats the AssertionError as tragic and closes itself. The message users see, netBytes has unexpected value 0 != N, is the rollback's own check (DocumentsWriter.java:232-233), which also fails close() after a single round.

Precondition, exactly: the per-thread writer that took the empty update still has 0 documents at the next full flush. In a single-threaded workload a document added before the refresh lands in the same writer and nothing leaks; with concurrent indexing it can leak while other writers hold documents. Several empty updates between two full flushes reuse one writer, so the leak counts full flushes, not calls. Other entry points (executed in the fact check): a zero-row column batch, updateDocuments(Term, ColumnBatch), leaks the same 33,040 bytes through DocumentsWriter.updateBatch. updateDocuments(Query, List.of()) takes the same path, but a delete-by-Query is accounted at about 76 bytes, below the 16 KB granularity skip, so with the default config it leaves 0 bytes (76 per round with setMaxBufferedDocs).

Exposure and likelihood412 words
  • Who is hit. Code that calls updateDocuments(term, block) or softUpdateDocuments(term, block, ...) with a block that can be empty. The default IndexWriterConfig, codec, flush policy and merge policy suffice. The block APIs are @lucene.experimental; softUpdateDocuments is documented as "Expert".
  • Scale. About 33 KB per round (an empty-block update, then a refresh or commit) since 9.9.0 (updateDocuments) and 7.7.0 (softUpdateDocuments): 16,777,216 / 33,040 = 508 rounds fill the default buffer (the -ea failure came at rounds 506-509). Older releases leak 165 or 330 bytes per round: on 4.5.0, 110,000 rounds left 18,150,000 bytes and 200 documents then became 200 segments.
  • Assertions off (the JVM default). ramBytesUsed() over-reports without bound and past the real heap (with a 2 GB buffer: 268,450,000 bytes on a 268,435,456-byte max heap after 8,125 rounds); the bytes are phantom, no heap is held. Past the buffer every added document triggers a flush; in these single-threaded runs, after 600 rounds, 200 small documents caused 200 flushes with the stock merge policy, and with NoMergePolicy 100 documents became 100 segments. Merge and I/O load follow; throughput was not measured. Code that drives its own flushing from ramBytesUsed(), as the flushNextBuffer() javadoc invites (IndexWriter.java:3752-3753), is misled the same way; getFlushingBytes() is not inflated (by reading).
  • Not affected. Deletes and soft deletes still apply, no hit is wrong, segments are written by the normal flush path (by reading; CheckIndex not run), and no hang was found (by reading the stall condition). Closing the writer and opening a new one clears it. By reading (not executed), back-pressure does change: stall control holds indexing threads only while activeBytes is below twice the RAM buffer (DocumentsWriterFlushControl.java:318), so once the phantom bytes alone reach that (about 1,016 rounds at 16 MB), slow flushes can no longer stall indexing for the rest of the writer's life.
  • Assertions on (tests, development). One empty-block update plus a refresh or commit makes close() throw; at the buffer the writer closes itself tragically and loses what was buffered. An application's own tests under Lucene's test framework would see the first symptom.
  • Not hit. In their default indexing paths (read from their source, not run; not a claim about every extension or branch), Elasticsearch and OpenSearch call softUpdateDocuments only for more than one document, and Solr always passes at least the root document. In Lucene no non-test code calls these methods except IndexWriter, and no upstream test passes a literal empty block.

Why it looks unintended

#
  • Nothing forbids an empty block: the javadocs do not require a non-empty one, and addDocuments(List.of()) on the same path leaves 0 bytes.
  • setRAMBufferSizeMB: the writer flushes "whenever buffered documents and deletions use this much RAM"; here nothing is buffered.
  • Lucene's own checks expect 0: close() asserts it, and TestFlushByRamOrCountsPolicy asserts activeBytes() == 0 after close.
The full argument190 words
  • Accepted input. The javadocs of updateDocuments (IndexWriter.java:1593-1604) and softUpdateDocuments (:1644-1663) do not require a non-empty block; softUpdateDocuments validates its other arguments (:1667-1672) but not this one. addDocuments(List.of()) takes the same path with no delete and leaves 0 bytes (executed controls).
  • The RAM buffer's contract. LiveIndexWriterConfig.setRAMBufferSizeMB: "When this is set, the writer will flush whenever buffered documents and deletions use this much RAM" (LiveIndexWriterConfig.java:162-163).
  • Lucene's invariants. DocumentsWriter.abort asserts flushControl.netBytes() == 0 (DocumentsWriter.java:232-233); TestFlushByRamOrCountsPolicy asserts flushControl.activeBytes() == 0 after writer.close() (TestFlushByRamOrCountsPolicy.java:102-103); setFlushPending, doAfterFlush and doOnAbort all subtract a writer's committed bytes. The drop branch is the only exit that does not.
  • The documented slack is bounded and in the other direction. Deletes by Query are under-counted (LiveIndexWriterConfig.java:174-177), and the 16 KB granularity skip is bounded by design: "we'd never be missing more than 64*16kB = 1MB" (DocumentsWriterFlushControl.java:201-202). This is an unbounded, permanent over-count.
  • Precedent. #5464 (LUCENE-4398, 2012): a different accounting leak with the same symptom, "every single document being flushed into its own segment", was treated as a bug and fixed with a test.
The devil's-advocate check239 words

The strongest case for "intended": the block APIs are experimental and softUpdateDocuments is Expert, a pure delete should use deleteDocuments or updateDocValues, the RAM buffer is "just an indicator when to flush" (LiveIndexWriterConfig.java:167-172), the drop branch's comment says a 0-document writer only comes from a concurrent flush, and internal code treats 0-document writers as non-flushable (the setFlushPending javadoc: "must have indexed at least on Document" [sic], DocumentsWriterFlushControl.java:360-364; FlushPolicy.java:74 and DocumentsWriterPerThread.prepareFlush, :428, assert it).

Why it fails: nothing forbids or rejects the empty block, and the experimental tag is about API stability, not about the writer's accounting drifting; the "indicator" sentence says the writer may use more memory than the buffer, not that the total may grow forever, and here it passes the real heap; the comment shows the empty block was not foreseen, it is not a user-facing precondition. The internal assertions are assumptions, not a documented restriction on callers; they are a fair argument for rejecting empty blocks or skipping the writer (the other two options under Suggested fix) rather than for the leak. In 2020 mikemccand asked on apache/lucene-solr#1397, the PR that wrote today's branch, "Hmm why would we ever have nextRam > 0 but next.getNumDocsInRAM() == [0]?" (the [0] is ours; the comment ends at ==), and nobody replied; an empty-block update is one concrete way to reach that state. Every checker rated the case weak: real, minor.

Suggested fix

#

Recommended Release the dropped writer's bytes in markForFullFlush

In markForFullFlush, when a per-thread writer with 0 documents is dropped, subtract its committed bytes from activeBytes (four added lines). Validated: the repro and the finder's 4 tests pass with assertions on and off, 233 tests of the 11 closest suites pass, and the format and lint checks pass.

         } else {
           // it's possible that we get a DWPT with 0 docs if we flush concurrently to
-          // threads getting DWPTs from the pool. In this case we simply remove it from
-          // the pool and drop it on the floor.
+          // threads getting DWPTs from the pool, or after an update with an empty block of
+          // documents. In this case we simply remove it from the pool and drop it on the floor,
+          // releasing whatever RAM it already accounted for.
           boolean checkout = perThreadPool.checkout(next);
           assert checkout;
+          synchronized (this) {
+            activeBytes -= next.getLastCommittedBytesUsed();
+            assert assertMemory();
+          }
         }

Release the dropped writer's bytes in markForFullFlush (validated by the checks) (recommended)

#

In the 0-document branch of DocumentsWriterFlushControl.markForFullFlush (:596-602), subtract next.getLastCommittedBytesUsed() from activeBytes under the flush-control lock, then check assertMemory(). A 0-document writer is never flush-pending (setFlushPending acts only when getNumDocsInRAM() > 0, :367), so its bytes are in activeBytes, and the writer is locked here. The delete itself is unaffected: it is in the global delete queue, and the private copy could only apply to this writer's documents, of which there are none. Because it fixes the drop site, it covers (by reading) any 0-document writer that holds committed bytes, including the zero-row column-batch route (which leaks the same 33,040 bytes, executed in the fact check) and, with setMaxBufferedDocs, the Query routes.

Trade-offs

No correctness cost known. One more short lock section per dropped writer during a full flush, which is rare; not benchmarked. The full ./gradlew check was not run.

Do not take a per-thread writer for an empty block

#

Put the delete or doc-values update only into the global delete queue, as deleteDocuments and updateDocValues do.

Trade-offs

Avoids the 32 KB allocation altogether. But the block is an Iterable: detecting "empty" means taking its iterator before obtaining a writer and handing that same iterator on, plus a second sequence-number path, and the column-batch route needs the same. It leaves the drop branch unguarded for any other source of a 0-document writer with bytes. Not implemented or tested.

Reject an empty block with IllegalArgumentException

#

One check in each API, which also documents the restriction.

Trade-offs

Changes accepted behaviour: addDocuments(List.of()) is accepted today, and callers that pass an empty block to mean "delete only" would start failing. Leaves the drop branch unguarded. Not implemented or tested.

Downstream note

#

A product that forwards a client-supplied, possibly empty list of documents into these calls should map an empty list to deleteDocuments (or updateDocValues for a soft delete) until this is fixed; the default indexing paths of Elasticsearch, OpenSearch and Solr do not pass an empty block (read from their source, not run).

How it was found

#

Non-formal. While extending an executable reference model of soft deletes to softUpdateDocuments edge cases, an AI tool wrote a small probe: an empty-block softUpdateDocuments followed by close() failed under -ea with netBytes has unexpected value 0 != 32960. Further probes measured the RAM growth and the one-segment-per-document flushing with assertions off.

The method in full135 words

Method: non-formal (probes and executed tests; no model checker, solver or proof produced the signal), a hunt unit on soft deletes.

  • The finder was extending a model-based test of soft deletes to softUpdateDocuments edge cases. A probe (softUpdateDocuments(term, List.of(), soft), then close()) failed under -ea in DocumentsWriter.abort.
  • Two more probes then measured, with assertions off, 660,800,000 bytes after 20,000 rounds on a 64 MB heap, and, with a 1 MB RAM buffer and NoMergePolicy, 201 segments for 200 small documents after 100 rounds (2 in the controls).
  • A JUnit test on the stock jars, with assertions on and off, became the candidate; an independent reproducer, a devil's advocate, read-only reviews by another model family and an adjudication then checked it, and the minimal test was cut from the adjudication's test.

History

#

Introduced in 4.5.0 (2013) by LUCENE-5006 (75ab79f0aa35, s1monw). About 33 KB per round since 9.9.0 (#12573) on updateDocuments and since 7.7.0 (LUCENE-8590) on softUpdateDocuments; 165-330 bytes before. Fails on 10.6.0 and main; not fixed upstream.

Versions tested8 rows

Introduced by LUCENE-5006 (#6070), commit "Simplified DW and DWPT synchronization and concurrent interaction with IW" (s1monw, 2013-08-19; trunk 75ab79f0aa35, branch_4x 8003cc782982; pre-GitHub, no PR), first released in 4.5.0. It created the delete slice in the per-thread writer's constructor, so an empty block stopped throwing a NullPointerException, and replaced the in-place re-initialization of a 0-document writer with a reset that zeroes its byte count without subtracting it.

Kept since: LUCENE-6676 (5.3.0) changed the reset call; LUCENE-9304 (apache/lucene-solr#1397; 8.6.0, main 2602269f3ec8) rewrote it into today's "drop it on the floor" branch and added the close-time netBytes assertion. #12198 (9.6.0) hides the 165-byte leak under the default config; #12573 (9.9.0 d3a3391d225, main 8b84f6c0965) and LUCENE-8590 (7.7.0) made each round leave about 33 KB.

Not fixed upstream (2026-10-31): upstream main 2f424fd428d, branch_11x, branch_10_6 and the 10.6.0 tag have the same branch.

LFV-453, snapshot of 2026-11-10

Registry title
IndexWriter.updateDocuments / softUpdateDocuments with an empty block leave about 33 KB of phantom RAM accounting at every refresh or commit that drops the empty per-thread writer, so ramBytesUsed grows without bound and, once it passes the RAM buffer, every later document is flushed into its own segment
Area
index / IndexWriter flush-control RAM accounting (DocumentsWriterFlushControl.markForFullFlush drops a 0-document DocumentsWriterPerThread; reached through updateDocuments and softUpdateDocuments with an empty block)
Priority
Low, rank 1046: Empty-block updateDocuments calls leak RAM accounting until the default writer flushes after every document: a real slowdown with a natural trigger.
Impact class
minor
Impact note
Applications that call updateDocuments(term, block) or softUpdateDocuments(term, block, softField) with an empty block (delete or soft-delete by key, add nothing), with the default IndexWriterConfig: every refresh, commit or flush that finds the per-thread writer that took such a call still holding 0 documents leaves its delete or doc-values buffer (about 33 KB on the updateDocuments path since 9.9.0 and on the softUpdateDocuments path since 7.7.0; 165-330 B on older paths) counted in ramBytesUsed for the rest of the writer's life, and after about 510 such rounds at the default 16 MB buffer the writer flushes after every added document (200 tiny documents -> 200 flushes), with the merge and I/O load that follows; deletes still apply, no hit is wrong, nothing on disk is malformed, closing the writer and opening a new one clears it, and with -ea the writer closes itself with a tragic AssertionError.
Summary
You call IndexWriter.updateDocuments(term, List.of()), or softUpdateDocuments(term, List.of(), softField), to delete a key's documents and add nothing, then refresh or commit; you expect the delete to apply and nothing to stay buffered, so ramBytesUsed() returns to 0 as it does after deleteDocuments(term) or addDocuments(List.of()). Instead the call took a per-thread writer and charged its delete buffer (about 33 KB) to the flush control, and the next full flush throws that 0-document writer away without taking the charge back, so ramBytesUsed() climbs by about 33 KB per round and never comes down (20 rounds with a default config: 660,800 B). Once the phantom total passes the RAM buffer (about 510 rounds at the default 16 MB) the writer flushes after every document, so 200 small documents become 200 segments; with assertions enabled the writer closes itself with an AssertionError instead.
