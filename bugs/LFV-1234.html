An empty OnHeapHnswGraph reports 2 levels, but listing level 1 throws NullPointerException

Build an HNSW graph from 0 vectors with HnswGraphBuilder and the returned OnHeapHnswGraph reports 2 levels, yet listing level 1 throws NullPointerException instead of returning an empty list. Lucene's own indexing never builds an empty graph; every release since 9.9.0 is affected (in four, build(0) already throws).

The finding in 30 seconds

#

An empty graph reports 2 levels because it starts with a placeholder entry node on level 1. Its upper-level node lists are cached and rebuilt only when size() differs from the size at the last rebuild. On a new graph both are 0, so the lists are never built and level 1 reads a null array.

Background: levels and the node-list cache

#
  1. An HNSW graph has levels: level 0 holds every node, each higher level a shrinking subset. numLevels() says how many there are, and getNodesOnLevel(level) lists the nodes on one of them.
  2. OnHeapHnswGraph is the in-memory graph that HnswGraphBuilder builds and a vectors writer then writes level by level. It lists level 0 directly and keeps the lists of the higher levels in a cache that it fills on the first such call.

The finding, step by step

#
  1. Build a graph from 0 vectors: HnswGraphBuilder.create(scorers, 8, 20, 1L).build(0) over an empty 2-dimensional FloatVectorValues. The graph has 0 nodes, and numLevels() returns 2.
  2. List every level it reports, the loop a vectors writer runs when it writes a graph: getNodesOnLevel(0), then getNodesOnLevel(1).
  3. You expect 0 nodes on both levels, which is what HnswGraph.EMPTY returns for any level.
  4. Level 0 lists 0 nodes, but level 1 throws NullPointerException: Cannot load from object array because "this.levelToNodes" is null at OnHeapHnswGraph.java:276, with assertions on and off. getSortedNodes(1) fails the same way.
  5. Why: the graph builds its upper-level node lists on first use and skips that when the node count equals the count at the last build. A new graph has 0 nodes and remembers 0, so the lists are never built.

Who is affected

#

Only code that builds HNSW graphs itself with the public HnswGraphBuilder over a vector set that can be empty, then lists an upper level, such as a custom vectors format or an offline graph tool. Lucene's own writer never builds an empty graph. In 9.12.0, 9.12.1, 10.0.0 and 10.1.0 build(0) itself throws. The failure is loud.

Mechanism, terms and numbers341 words

HnswGraphBuilder.create(...).build(0) over an empty vector set returns an OnHeapHnswGraph with 0 nodes whose numLevels() is 2, because every new graph starts with the placeholder entry node EntryNode(-1, 1) (OnHeapHnswGraph.java:77, :199-202). getNodesOnLevel(0) returns an empty iterator, but getNodesOnLevel(1), and getSortedNodes(1) which calls it, throw NullPointerException at :276. The upper-level node lists are built on first use and counted as up to date whenever lastFreezeSize == size() (:281-283); on a new graph both are 0, so the lists stay null.

On main, Lucene's own vectors writer builds a graph only when a field has vectors, so indexing, merging and search never reach it; only code that drives the public util.hnsw builder itself over a possibly empty vector set is hit. In 9.12.0, 9.12.1, 10.0.0 and 10.1.0 the builder walks every level itself when it finishes (connectComponents()), so there build(0) already throws. The fix is a two-line change in generateLevelToNodes().

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/hnsw/)

#
  1. Two levels on an empty graph. The constructor sets entryNode = new EntryNode(-1, 1) (OnHeapHnswGraph.java:77); numLevels() returns entryNode.get().level + 1 (:199-202), so a graph with 0 nodes reports 2 levels.
  2. A cache keyed on the node count. The upper-level lists levelToNodes are "only generated on demand" (:48-51) and start null; lastFreezeSize starts at its default 0 (:52-54).
  3. The listing call. getNodesOnLevel(level) first checks that the build is complete, size() != maxNodeId() + 1 (:268-271): 0 == -1 + 1, so it passes. Level 0 returns new DenseNodesIterator(size()) (:272-273); any other level calls generateLevelToNodes() and then reads levelToNodes[level] (:275-276).
  4. The early return (the fix site). generateLevelToNodes() returns at once when lastFreezeSize == size() (:281-283). Both are 0, so levelToNodes stays null and :276 throws. getSortedNodes(level > 0) goes through the same call (HnswGraph.java:148-152). The failing call changes no state.

Executed alongside: getSortedNodes(1) of the same graph throws the same exception, while getNodesOnLevel(0) of it and HnswGraph.EMPTY.getNodesOnLevel(1) are empty.

Exposure and likelihood342 words
  • Who. Code that calls HnswGraphBuilder.create(...).build(maxOrd) over a vector set that can be empty and then lists a level from 1 to numLevels() - 1 of the result with getNodesOnLevel or getSortedNodes, for example in a loop over every reported level to write or check the graph. It fails every time the set is empty.
  • Default vs opt-in. Opt-in. On main, the flush path returns no graph unless a vector was added (Lucene99HnswVectorsWriter.java:880-887, node > 0), the merge path builds a graph only for numVectors > 0 (:453, :712-713), and a missing graph is written as 0 levels (:560, :623-625). CheckIndex lists levels of graphs read from the index, not of an OnHeapHnswGraph; Word2VecSynonymProvider can build an empty graph but on main only searches it.
  • Older releases: build(0) itself throws in four of them. In 9.12.0, 9.12.1, 10.0.0 and 10.1.0, HnswGraphBuilder.finish() calls connectComponents(), which walks every level the graph reports and, for level 0, lists level 1 through HnswUtil.components. There build(0) throws the same NPE before it returns a graph: executed on 10.0.0 (getNodesOnLevel at OnHeapHnswGraph.java:247 <- HnswUtil.components <- connectComponents <- finish <- getCompletedGraph <- build), by reading for the other three. In those releases the in-tree Word2VecSynonymProvider, which builds with build(word2VecModel.size()), would hit it in its constructor when given an empty model (by reading; not run). The call is absent in 9.9.x to 9.11.x and commented out in 9.12.2, 9.12.3, 10.2.0 and later and on main (HnswGraphBuilder.java:587); the vectors writer is guarded in those four releases as on main.
  • Effect. A NullPointerException in the caller's thread, with assertions on and off. No wrong result, no change to the graph or to any index.
  • Scale. Zero vectors. For valid (positive) M and beam width, neither they nor the seed play a part (by reading; the runs used M 8 and 16).
  • Workaround. Treat an empty vector set as "no graph", as Lucene's writer does, or check graph.size() == 0 before walking the upper levels.

Why it looks unintended

#
  • numLevels() "Returns the number of levels of the graph"; getNodesOnLevel gets "all nodes on a given level". Neither excludes empty graphs.
  • build(0) returns a completed graph that passes its own completeness check; HnswGraph.EMPTY lists 0 nodes for any level.
  • An accidental interaction: #12651 keyed the cache on size when an empty graph had 1 level; #12660 then gave it 2.
The full argument232 words
  • Contract. HnswGraph.numLevels(): "Returns the number of levels of the graph" (HnswGraph.java:85-86); getNodesOnLevel(level): "Get all nodes on a given level" (:94-101). HnswBuilder.build(maxOrd): "Adds all nodes to the graph up to the provided maxOrd", no positive-only precondition (HnswBuilder.java:32-37); build(0) is accepted.
  • The class's own checks accept the call. build returns getCompletedGraph(), which finishes and freezes the builder (HnswGraphBuilder.java:200-210, :236-242, :583-589), so the javadoc NOTE "calling this method while the graph is still building is prohibited" (OnHeapHnswGraph.java:264) does not apply. The completeness check passes (:268-271), and the same javadoc presents the cache as a speed-up ("only the first non-zero level call will pay the cost", :259-262), not as a precondition.
  • History. #12651 (a1cf22e6a94, 2023-10-16) added the size-keyed cache when an empty graph still had one level (9.8.0: this.numLevels = 1; // Implicitly start the graph with a single level). #12660 (a8c52e2e19c, 2023-10-28) replaced that with EntryNode(-1, 1). Neither review thread discusses empty graphs or the cache key. 9.9.0 with only EntryNode(-1, 0) put back passes the test.
  • Upstream relies on the 2 levels. TestOnHeapHnswGraph.testIncompleteGraphThrow adds nodes to a graph whose entry node was never set and expects getNodesOnLevel(1) to list one node (TestOnHeapHnswGraph.java:37-44); so the level count is relied on, and the broken part is the cache key.
The devil's-advocate check153 words

The strongest case for "not a bug", which the cross-model reviews (OpenAI GPT-5.6) rated moderate before rejecting it: the HnswBuilder interface is @lucene.experimental (HnswBuilder.java:28), and so is the scorer the repro uses (DefaultFlatVectorScorer.java:33); Lucene's codec never builds an empty graph; HnswGraph.EMPTY reports 0 levels; and the package javadoc calls the graph "nominally Hierarchical but currently only has a single layer" (package-info.java:19), so the placeholder level may not read as a promise. Callers, on this view, should not build an empty on-heap graph at all.

Why it does not settle it: HnswGraphBuilder and OnHeapHnswGraph are public, untagged classes in the exported package org.apache.lucene.util.hnsw (module-info.java:50); "experimental" speaks to API stability, not to an NPE on an object the builder itself returns; and the graph reports the very level it then cannot list. A maintainer may still call it too minor, a fair outcome for a Low bug.

Suggested fix

#

Recommended Rebuild when the cache is missing or has the wrong number of levels (fix A)

In generateLevelToNodes(), also rebuild when the cache is missing or has the wrong number of levels, not only when size() changed (a two-line change). With it the repro passes with assertions on and off, and 132 tests of the closest HNSW suites pass.

  private void generateLevelToNodes() {
    int maxLevels = numLevels();
    if (levelToNodes != null && levelToNodes.length == maxLevels && lastFreezeSize == size()) {
      return;
    }
    levelToNodes = new IntArrayList[maxLevels];

Rebuild when the cache is missing or has the wrong number of levels (fix A) (validated by the checks) (recommended)

#

In OnHeapHnswGraph.generateLevelToNodes() (OnHeapHnswGraph.java:280-284), return early only when the lists exist, have numLevels() entries and the size is unchanged.

  private void generateLevelToNodes() {
    int maxLevels = numLevels();
    if (levelToNodes != null && levelToNodes.length == maxLevels && lastFreezeSize == size()) {
      return;
    }
    levelToNodes = new IntArrayList[maxLevels];

Trade-offs

Each upper-level call now reads numLevels() before the check instead of after it and adds a null check and a length check (short-circuited); the rebuild still runs only when the graph changed or the lists were never built. On non-empty graphs behaviour changes only if the level count changed since the last build, and then the lists are rebuilt instead of reused. Scope: fix A covers a missing cache and a changed level count; like the current code, it does not detect a change that keeps both size() and the level count.

Downstream note

#

Downstream products are affected only if their own code builds HNSW graphs with this builder over a possibly empty vector set and (on main) lists its upper levels; in 9.12.0, 9.12.1, 10.0.0 and 10.1.0 build(0) alone throws, which an application could also reach by giving Word2VecSynonymProvider an empty model. How it was found

#

A proof-obligation audit of OnHeapHnswGraph's contract: every level below numLevels() must be listable, including on the empty graph the builder returns. The size-keyed cache check fails that obligation; a public-API JUnit test then witnessed the exception.

The method in full113 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder set the level count of an empty graph against the freshness rule of the upper-level node cache in getNodesOnLevel, and found that the rule treats a never-built cache as fresh when the graph has 0 nodes.
  • The finder then wrote a public-API JUnit test and the two-line fix that makes it pass.
  • An independent reproducer and two executed cross-model reviews reproduced it with their own tests; a devil's-advocate verifier re-ran the finder's test (main with assertions on and off, 10.6.0), and an adjudication re-ran the reproducer's test with a fresh seed ("Prior reports, history and checks").
