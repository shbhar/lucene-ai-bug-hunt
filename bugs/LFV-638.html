Hunspell getAllWordForms returns words that spell() rejects when another affix adds the same text

When one Hunspell affix makes a form that still needs another affix and a second affix adds the same letters, getAllWordForms lists words that spell() rejects and compress suggests entries that miss words. On the public Esperanto dictionary that is 25,554 non-words; spell-checking and search are unaffected.

The bug in 30 seconds

#

Lucene's Hunspell module can list every form of a dictionary word (getAllWordForms, like C unmunch) and suggest dictionary entries for a word list (compress, like munch). A built-in check is meant to keep only forms the spell-checker accepts.

  1. You load a dictionary where class A adds s to foo and its continuation needs one more suffix (NEEDAFFIX): foos is not a word, foosen is. An unrelated class C, used only by bar, also adds s.
  2. You call getAllWordForms("foo") and expect [foo, foosen]: spell("foos") is false, C Hunspell rejects it too, and the generator's check is documented to keep only forms the spell-checker accepts.
  3. You get [foo, foos, foosen]. The check strips s with class C, sees the text foo and accepts; it never asks which affixes it stripped (WordFormGenerator.java:211). Without class C the result is [foo, foosen].
  4. compress([foo, foos, foosen]) suggests foo/AB, which still rejects foos. Lucene's own fixture needaffix5 plus two unused same-text lines generates exactly the 3 words of its .wrong file.
  5. Real dictionaries: Esperanto gives 25,554 rejected words among 14.2 million forms (bare stems like zink), Galician 1,510 in 5,000 roots, and C Hunspell rejects nearly all sampled ones (397 of 400, 300 of 300). Nothing throws; spell-checking, stemming and search are unaffected.

Who is affected

#

Applications that use the Hunspell dictionary-tooling API (getAllWordForms, generateAllSimpleWords, compress) to export word lists or edit dictionaries, with a dictionary where a NEEDAFFIX or CIRCUMFIX affix shares its text with another affix path. Public Esperanto and Galician dictionaries are hit. Spell-checking, suggestions, stemming and search are not. Every release since 9.5.0.

Mechanism, terms and numbers761 words

Hunspell.getAllWordForms(root), and WordFormGenerator.getAllWordForms, generateAllSimpleWords and compress, which share its expansion, keep each affix-derived form only if the check canStemToOriginal passes; its javadoc says the form "is indeed accepted by the spell-checker and analyzed to be the form of the original dictionary entry". The check strips affixes from the form and accepts as soon as any stripping path gives back the stem's text, ignoring which affixes that path removed (WordFormGenerator.java:211 on main a9779ef3c193). When an affix makes a form that is not a word on its own (its continuation carries NEEDAFFIX, or a CIRCUMFIX side is missing), the stemmer skips that path, but any other affix with the same text and strip whose condition matches, even of a class the entry does not have, leads back to the same text and the form is kept. With NEEDAFFIX X, SFX A 0 s/XB, SFX B 0 en, an unrelated SFX C 0 s, foo/A and bar/C, getAllWordForms("foo") returns [foo, foos, foosen] while spell("foos") is false; Lucene's needaffix5 fixture plus two unused same-text lines regenerates exactly its .wrong words; compress suggests foo/AB, which does not accept foos. The public Esperanto dictionary yields 25,554 such words (24,936 of 29,377 roots) and 5,000 Galician roots 1,510. Every release from 9.5.0, the API's first, to 10.5.2 and main is affected. Spell-checking, suggestions, stemming, HunspellStemFilter, indexing and search are not.

Terms

#
  • Affix class: a flag in the .aff file, for example SFX A 0 s/XB . = class A appends s (strips nothing, any condition) and gives the result the continuation flags X and B. An entry foo/A in the .dic may take class A.
  • NEEDAFFIX: a flag (NEEDAFFIX X) that marks a pseudo-form: a form whose flags contain X is not a word until another affix is applied. So foos (foo + A, flags XB) is not a word, but foosen (foos + B) is.
  • canStemToOriginal: the generator's filter. It runs the stemmer backwards on each generated form and keeps the form if the stemmer gets back to the entry's stem.

The bug

#
  1. WordFormGenerator.expand (:233-259) applies each affix and keeps the result only if canStemToOriginal says so (:248); it has no NEEDAFFIX or CIRCUMFIX check of its own (shouldConsiderAtAll, :247, only drops compound, FORBIDDENWORD and ONLYINCOMPOUND continuations; the bare stem is added without the check unless the entry has NEEDAFFIX, :154-160). For a cross-product affix it recurses with the continuation flags (:251-253), which makes foosen.
  2. canStemToOriginal (:184-217) calls Stemmer.removeAffixes (:215) with a processor (:192-214) that receives the ids of the affixes each path removed, but decides on text alone: foundStem |= length == stem.length() && stem.equals(new String(chars, offset, length)); (:211).
  3. The stemmer skips the form's own path because A's continuation needs another affix (needsAnotherAffix, Stemmer.java:610, :693-708). It then tries class C, which also strips s (same strip, matching condition), and offers foo with C's id. The text matches, so foos is kept.
  4. The spell-checker would reject that candidate because foo has no flag C (Stemmer.java:265-269). The generator's check does not look at entry flags (it cannot rely on them, since compress runs it for hypothetical flag sets), and nothing else ties the accepted path to the form's own affixes, which the generator knows (AffixedWord.getPrefixes() / getSuffixes()).

Exposure and likelihood396 words
  • Who is exposed. Callers of Hunspell.getAllWordForms / compress and WordFormGenerator.getAllWordForms / generateAllSimpleWords / compress: word-list export (the javadoc calls it equivalent to unmunch), dictionary editing (compress, equivalent to munch), auxiliary lists built from a dictionary. The Hunspell module is opt-in and this API is a niche part of it.
  • What goes wrong. Silent non-words in the list: 25,554 of 14.2 million Esperanto forms, mostly bare stems. compress can propose an entry that does not accept a word it was asked to cover (foo/AB for foos), so an editing tool that trusts it writes a wrong entry. The javadoc's second promise breaks too: on Esperanto the fix also removes 2,183 forms that spell() accepts only as forms of another entry or with no simple-word analysis.
  • What is not affected. spell, suggest, getRoots / analyzeSimpleWord, HunspellStemFilter, indexing and querying do not call this check; leaked words stay rejected and unstemmed. NGramFragmentChecker overrides the check with return true and is unchanged. In the security probe (which runs spell, analyzeSimpleWord, HunspellStemFilter, indexing and search; suggest and getRoots were read, not run): no exception, no hang, and the same number of affix applications with or without the bug; memory was not measured.
  • What it takes. A dictionary in which an affix makes a form that is not valid on its own (NEEDAFFIX or CIRCUMFIX in its continuation) and another affix path, at the same position, with the same affix text and strip and a matching condition, that leads back to the same stem text. No other configuration, no scale; deterministic.
  • How common. 24 of 191 public .aff files match one conservative syntactic scan (a NEEDAFFIX or CIRCUMFIX entry plus an entry of a different class with the same strip and non-empty text; for example da, de (frami), eo, eu, gl, id, ka, lb, lv, sk). It ignores conditions and the .dic, so it over-counts, and it misses same-class and zero-text collisions such as Esperanto's, so it is not an upper bound. Esperanto and Galician leak at scale. In the sampled Danish and German (frami) runs the fix changed nothing; in Luxembourgish it removed 9 forms that Lucene's spell() rejects but C Hunspell accepts (a separate stemmer difference, so no clean leak). A Basque run did not finish in its time box; the others were not run.

Why it is a bug, not intended

#
  • The check's javadoc promises each kept form "is indeed accepted by the spell-checker and analyzed to be the form of the original dictionary entry".
  • Lucene's TestSpellChecking fails with "Misspelled words generated" on any such word; needaffix5.wrong lists the words that leak.
  • C Hunspell 1.7.2 rejects foos and 397 of 400 Esperanto and 300 of 300 Galician sampled leaks.
The full argument264 words
  • Contract. canStemToOriginal javadoc (WordFormGenerator.java:178-183, added by #11909): "A sanity-check that the word form generated by affixation in getAllWordForms(String, String, Runnable) is indeed accepted by the spell-checker and analyzed to be the form of the original dictionary entry."
  • Test. TestSpellChecking.checkExpansionGeneratesCorrectWords (:378-388), which expandWholeDictionary (:337-355) calls for every .dic line (except empty lines and lines with a backslash) of each fixture that TestSpellChecking runs through doTest, fails with "Misspelled words generated" on any generated word that spell() rejects or analyzeSimpleWord cannot analyse. It came with the generator in #975. Stock fixtures do repeat affix texts (germancompounding.aff, compress.aff), and circumfix.aff has this bug's own shape (CIRCUMFIX X with SFX C 0 obb ., obb/AX and obb/BX): there stock getAllWordForms("nagy") returns nagyobb three times, twice only because the plain obb path strips to the same text. It stays invisible because nagyobb is a real word, and TestCircumfix does not run the expansion check. Among the fixtures that TestSpellChecking expands, the ones that repeat an affix text (base, base_utf, germancompounding, germanManualCase) have neither NEEDAFFIX nor CIRCUMFIX, and needaffix5 repeats no affix text, so the test never fired.
  • Fixture. needaffix5.wrong lists pseudoprefoo, foopseudosuf, pseudoprefoopseudosuf: the three words the generator emits once two unused same-text lines are added.
  • Independent engine. C Hunspell 1.7.2 rejects foos and nearly all sampled real-dictionary leaks.
  • History. The text-only comparison is as old as the generator (#975, d537013e708); none of its 4 conversation and 19 review comments discusses which affix path the check accepts.
The devil's-advocate check186 words

The strongest case for "intended": the method is a protected, overridable sanity check; NGramFragmentChecker overrides it to "overgenerate a bit, but avoid very expensive checks"; getAllWordForms is documented as equivalent to C unmunch, which has no NEEDAFFIX support at all; and the check has to ignore entry flags because compress() runs it for hypothetical flag sets.

Why it fails: the default implementation's own javadoc promises spell-checker acceptance; the override is an explicit opt-out by one other caller, and its comment implies the default is the precise, expensive check; Lucene's own test demands more than unmunch; and the fix compares only the affix ids the stemmer already reports with the form's own affixes, so it stays independent of entry flags (compress keeps working and suggests foo/ABC). An independent reproducer, an intended-behaviour devil's advocate and a reviewer from another model family all rated the intended-behaviour argument weak, and so did the cross-model fact check of this doc, which adds that the argument does not settle which fix is right: fix A's exact-affix-id rule is one reading of the contract. Verdict: not intended, a defect.

Suggested fix

#

Recommended Accept only the form's own affix path in canStemToOriginal

Accept a stem candidate in canStemToOriginal only when the stripped affixes are the form's own: compare the stemmer's affix ids with the derived word's prefixes and suffixes (+13/-1). Validated on these tests and dictionaries (not proven for every affix graph): the repro passes; analysis-common runs 1,913 tests with 0 failures; Esperanto and Galician drop to 0 rejected words, and no form that analyses to the same root is lost.

Accept only the form's own affix path in canStemToOriginal (validated by the checks) (recommended)

Trade-offs

It changes only which forms are kept, never which affixes are applied. The processor now keeps enumerating past text matches from other paths until it reaches the form's own path, so it can do more stemming work per form (not benchmarked), and a FORBIDDENWORD candidate met on the way now rejects a form that stock had already accepted; the check was already order-dependent this way when the forbidden candidate came first (read from the code; no test covers it). A maintainer may prefer another fix site. Fix A requires the exact affix ids, which is stricter than the javadoc's wording: on the stock circumfix.aff fixture it drops the two duplicate nagyobb values from the CIRCUMFIX pseudo-paths obb/AX and obb/BX (the word stays through the plain obb path). It follows the current stemmer: where Lucene's spell() rejects a word that C Hunspell accepts, the fix drops that form too (9 Luxembourgish forms, 3 hyphenated Esperanto E- forms). In the finder's 4,000-dictionary differential this fix alone also changed two other counters (dictionaries the harness could not process 1 to 2, words on which Lucene threw 4 to 3); not investigated. Validated on the listed tests and dictionaries; not proven for every affix graph.

Skip forms that still need another affix in expand()

#

Before keeping a derived form, check whether its own outermost affix still needs another affix (NEEDAFFIX in the appended flags, or a CIRCUMFIX side missing), mirroring Stemmer.needsAnotherAffix.

Trade-offs

Leaves the check untouched, but duplicates the stemmer's rule, which is subtle: a NEEDAFFIX pseudo-suffix is valid once an outer affix follows (prefoopseudosuf is in needaffix5.good). It also would not cover other forms the stemmer cannot reproduce through their own path but accepts through another one (the finder's cross-product variant, not re-checked). Not run.

Check spell() and analyzeSimpleWord directly

#

Keep a form only if spell(word) is true and analyzeSimpleWord(word) contains an analysis of the same entry, the oracle of checkExpansionGeneratesCorrectWords.

Trade-offs

The most literal statement of the contract for getAllWordForms, but it costs a full spell check per form and does not work for compress(), which generates forms for hypothetical entries that are not in the loaded dictionary. Not run.

Downstream note

#

Elasticsearch, OpenSearch and Solr do not call these methods (read-only code search); their hunspell token filters use the stemmer, which this bug does not affect.

How it was found

#

Differential testing of Lucene's Hunspell word-form generator against C Hunspell 1.7.2 on 4,000 generated micro-dictionaries (plus 1,069 fixture cases) found 18 generated words that Lucene's own spell() rejects, in 15 of the micro-dictionaries, and 0 with this fix alone. A public-API JUnit then reproduced it on the stock jar.

The method in full179 words

Method: cross-implementation differential testing (the hunt's non-formal tier): a hunt unit compared Lucene's getAllWordForms, spell and analyzeSimpleWord with C Hunspell 1.7.2 (libhunspell spell and stem) and the hunspell-tools unmunch.

  • Inputs: 4,000 seeded, grammar-built micro-dictionaries (per dictionary, every candidate word reachable by at most 3 affix rules) and 1,069 per-root cases from the Hunspell 1.7.2 and Lucene test fixtures.
  • Root causes were separated with switchable shadow fixes: with this fix alone, the 18 self-inconsistent words in 15 dictionaries fell to 0 (the finder's counts; the verifiers did not re-run the 4,000 dictionaries).
  • The finder wrote the foo/A + bar/C JUnit; an independent reproducer added the needaffix5 variant and the compress effect; a credibility audit measured the Esperanto and Galician reach.
  • Found 2026-10-27 on main a9779ef3c193; then checked by an independent reproducer, an intended-behaviour devil's advocate, two executed reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history and prior-report follow-up, a security screen and the audit. This doc added the gradle runs, the fix validation and the same-root check on Esperanto and Galician.

Bug record

LFV-638, snapshot of 2026-10-29

Registry title
Hunspell getAllWordForms, generateAllSimpleWords and compress return words that spell() rejects: the sanity check canStemToOriginal accepts any affix path that strips a form back to the stem text, so with 'NEEDAFFIX X', 'SFX A 0 s/XB', an unrelated 'SFX C 0 s' and foo/A, getAllWordForms("foo") returns foos
Area
analysis / hunspell (WordFormGenerator: canStemToOriginal, getAllWordForms, generateAllSimpleWords, compress)
Priority
Low, rank 385: The tooling API's sanity check leaks words that spell() rejects only on a rare affix collision that sampled real dictionaries never hit.
Impact class
silent wrong results
Impact note
Only applications that call Lucene's opt-in Hunspell dictionary-tooling API (Hunspell.getAllWordForms and compress, WordFormGenerator.getAllWordForms, generateAllSimpleWords and compress) with a dictionary in which an affix gives a form that is not valid on its own (a NEEDAFFIX or CIRCUMFIX continuation [exec]; per the finder also a cross-product mismatch, not re-checked) and another affix class has the same affix text and strip are hit: the word list contains words that the same dictionary's spell() rejects, with no error, and compress() can suggest an entry that does not accept a requested word (kat/PQ for [kat, kater, katern]) [exec]; spell-checking, stemming, suggestions, HunspellStemFilter, NGramFragmentChecker (it overrides the check), indexing and search are not affected [exec, security probe]; no scale is needed; every release from 9.5.0 through 10.5.2 and main [exec]; real dictionaries are hit: the credibility audit found 25,554 leaked words in the public LibreOffice Esperanto dictionary (24,936 of 29,377 roots) and 1,510 in 5,000 sampled Galician roots, all removed by the fix, with C Hunspell 1.7.2 rejecting 397/400 and 300/300 sampled leaks [exec]; sampled da_DK, de_DE_frami and lb runs found none.
Summary
You load a Hunspell dictionary with 'NEEDAFFIX X', 'SFX A 0 s/XB' (so foos needs one more suffix), 'SFX B 0 en' and an unrelated class 'SFX C 0 s', with the entries foo/A and bar/C, and call Hunspell.getAllWordForms("foo"). You expect [foo, foosen]: spell() rejects foos (C Hunspell 1.7.2 does too), and the generator's check canStemToOriginal is documented to keep only forms that are 'accepted by the spell-checker and analyzed to be the form of the original dictionary entry'. Instead you get [foo, foos, foosen], because canStemToOriginal accepts as soon as any affix-stripping path gives back the stem text, here class C, which foo does not even have, and ignores which affixes were stripped (WordFormGenerator.java:211); generateAllSimpleWords leaks the same words, and compress([kat, kater, katern]) suggests kat/PQ, which does not accept kater.
