The finding in 30 seconds

#

Lucene limits a stored string by its length in characters, but reads it back with a JDK call limited by its length in UTF-8 bytes. For 3-byte characters the byte limit comes at half the character limit.

Background: how a stored string is kept

#
  1. A stored field keeps the original value, so you can fetch it with your search hits through StoredFields#document.
  2. Lucene writes a stored string as UTF-8: a byte count, then the bytes. ASCII takes 1 byte per character, accented Latin and Cyrillic 2, Chinese, Japanese and Korean 3.
  3. IndexWriter rejects a stored string longer than MAX_STORED_STRING_LENGTH, about 715.8 million characters, so that its UTF-8 form always fits in one byte array.

The finding, step by step

#
  1. Store one text field made of 357,913,941 copies of 一 (U+4E00, 3 bytes in UTF-8): 1,073,741,823 bytes. IndexWriter's limit, MAX_STORED_STRING_LENGTH, is about 715.8 million characters, so the document is accepted and the commit succeeds.
  2. You expect storedFields().document(0) to return the string, as it does with one character fewer (1,073,741,820 bytes).
  3. Lucene turns the stored bytes back into a String with the JDK's new String(bytes, UTF_8). For non-Latin-1 text the JDK sizes its buffer by the byte count and refuses 1,073,741,823 (2^30 - 1) or more, although the result would have only 357.9 million characters.
  4. So every full load of that document throws OutOfMemoryError: UTF16 String size is 1073741823, should be less than 1073741823, with a 4 GB or a 10 GB heap alike.
  5. Anything else that decodes it fails too: an addIndexes merge that copies fields one by one closes IndexWriter, and with an index sort the commit() that flushes it fails, closes the writer and loses the uncommitted documents.

Who is affected

#

Any application on the default codec that stores one text field of at least 2^30 - 1 UTF-8 bytes containing some non-Latin-1 text, for example about 358 million CJK characters. No crafting is needed, but it takes about 1 GiB in one field and several GB of heap to index; common request-size caps keep it out. Rare.

Mechanism, terms and numbers837 words

IndexWriter limits a stored string by its length in characters: it rejects only strings longer than IndexWriter.MAX_STORED_STRING_LENGTH, about 715.8 million chars, a bound derived from the worst-case UTF-8 encode buffer. Reading the field back goes through DataInput.readString, which calls the JDK's new String(bytes, 0, length, UTF_8). Since JDK 9 that constructor sizes its UTF-16 buffer by the UTF-8 byte count, and on JDK 21 and 25 it refuses 2^30 - 1 or more with OutOfMemoryError before it allocates the UTF-16 buffer (it has only copied the input bytes).

So a stored field of 357,913,941 CJK chars (1,073,741,823 bytes, about half of the accepted maximum) is indexed and committed, and then every StoredFields#document call on that document throws java.lang.OutOfMemoryError: UTF16 String size is 1073741823, should be less than 1073741823, with a 4, 6 or 10 GB heap alike; one char fewer reads back. A visitor-path merge (executed: addIndexes into an index with other field numbers) and, with an index sort, the flush of the segment that holds the document decode the field too, throw the same Error and close IndexWriter. The bytes on disk are valid: a read-side fix in DataInput.readString that decodes large values with Lucene's own UnicodeUtil.UTF8toUTF16 makes existing indexes of the default stored-fields format readable. It needs about 1 GiB in one field with some non-Latin-1 text, so it is rare; every release run on JDK 25, 5.5.5 to 10.6.0 and main, fails.

The bug, step by step (main 645d4fe14a20)

#
  1. The write check counts chars. IndexingChain throws IllegalArgumentException("stored field ... is too large (... characters) to store") only when storedValue.getStringValue().length() > IndexWriter.MAX_STORED_STRING_LENGTH (IndexingChain.java:1491-1503). The constant is ArrayUtil.MAX_ARRAY_LENGTH / UnicodeUtil.MAX_UTF8_BYTES_PER_CHAR (IndexWriter.java:260-262), 715,827,877 on these JVMs: the largest string whose worst-case UTF-8 form fits in one byte[]. It is an encode-side bound.
  2. The writer stores UTF-8. Lucene90CompressingStoredFieldsWriter.writeField(FieldInfo, String) calls bufferedDocs.writeString(value) (Lucene90CompressingStoredFieldsWriter.java:323-328). bufferedDocs is a ByteBuffersDataOutput (:95, :124), whose writeString override (ByteBuffersDataOutput.java:414-451) writes the format DataOutput.writeString documents (DataOutput.java:263-270): a vInt byte length (:437-438), then the UTF-8 bytes from UnicodeUtil.UTF16toUTF8 (for a value this long through writeLongString, :446, :567-581). A 1,073,741,823-byte value is written and committed without error.
  3. Every read in the default format decodes with the JDK constructor. readField handles a STRING field with visitor.stringField(info, in.readString()) (Lucene90CompressingStoredFieldsReader.java:295-296), so the value is decoded before any visitor sees it; a visitor can only avoid that by answering NO or STOP in needsField (:706-718). DataInput.readString returns new String(bytes, 0, length, StandardCharsets.UTF_8) (DataInput.java:226-231). The non-default SimpleText codec decodes on its own with the same JDK constructor (SimpleTextStoredFieldsReader.java:165; not run).
  4. The JDK refuses by byte count. For a result with non-Latin-1 chars, JDK 25's UTF-8 constructor calls StringUTF16.newBytesFor(length) with the UTF-8 byte count, and StringUTF16.newBytesLength throws OutOfMemoryError when that is >= Integer.MAX_VALUE >> 1 (2^30 - 1), before it allocates the UTF-16 buffer; by then it has only copied the input bytes (JDK 25 String.java:568 copies, :597 calls newBytesFor, StringUTF16.java:53-60 throws; the executed stack shows the frames at :597 and in StringUTF16). The decoded string, 357,913,941 chars, would itself fit. JDK 8 decoded into a char[len] and had no such cap.
  5. Where it surfaces. StoredFields#document; visitor-path merges (MergeStrategy.VISITOR when field numbers differ, Lucene90CompressingStoredFieldsWriter.java:678-684, used at :637-640; executed for addIndexes(CodecReader), other merge configurations read from the code); the index-sort flush, which re-reads every stored field of the new segment through a CopyVisitor that loads every field (SortingStoredFieldsConsumer.java:109-139, :199-200); and CheckIndex's stored-field check. IndexWriter treats any Error as tragic and closes itself (class javadoc IndexWriter.java:162-165; doFlush :4428-4431; addIndexes(CodecReader...) :3391; prepareCommit :3879-3881, the path of the executed sorted commit()).

Which text triggers it

#

At least 2^30 - 1 UTF-8 bytes, at least one non-Latin-1 char, and (to stay under the char limit) more than 1.5 UTF-8 bytes per char on average: for example about 358M CJK chars, or about 537M Cyrillic chars (arithmetic, not run). Latin-1-only text above the boundary reads back: 536,870,912 x U+00E9 (1,073,741,824 bytes) passes, while the same text with one U+4E00 (1,073,741,825 bytes) fails.

Exposure and likelihood288 words
  • Who can be hit. Any application on the default codec and IndexWriterConfig that stores one text field (StoredField(String); a stored TextField holds the same value, not run, while a StringField this large is already rejected as an immense term) of at least 2^30 - 1 UTF-8 bytes containing a non-Latin-1 char and averaging more than 1.5 bytes per char. Large natural CJK text is enough.
  • Scale. About 1 GiB in one field, and several GB of heap at index time (the test indexes it with a 4 GB heap). Near-GB stored fields do occur: LUCENE-7538 (#8589) started from an 800 MB field, and in the same thread (2017) a user reported files "which are 1GB huge". Common ingestion caps keep it out in practice (for example Elasticsearch's 100 MB default HTTP body limit), and nobody has reported it since JDK 9.
  • What goes wrong. An Error on a document Lucene accepted, not a wrong answer. Unsorted index: the document is committed and stays unreadable; a search that loads all stored fields of its hits fails whenever it is among them; a visitor-path merge closes the writer. Index sort: the flush of the segment that holds it throws, commit() fails, the writer closes and every uncommitted document is lost (the last commit stays intact). CheckIndex does not see it at its default level; -level 2 -exorcise drops the whole segment, other documents included.
  • Default vs opt-in. Default codec and configuration, no special API; the index-sort path is opt-in. 6.x to 8.x are hit only on a JDK 9+ runtime; 9.0.0 and later on every JDK they support (on JDK 11 and 17 from 2^30 bytes rather than 2^30 - 1; source reading, only JDK 25 was run).

Why it looks unintended

#
  • MAX_STORED_STRING_LENGTH is documented as the "Maximum length string for a stored field"; this one is about half.
  • That limit was added so a too-large field fails up front "instead of a cryptic exception that closes your IndexWriter"; here a visitor merge or a sorted flush closes it.
  • The decoded string fits in a Java String; Lucene's own UnicodeUtil.UTF8toUTF16 decodes it.
The full argument263 words
  • The contract. MAX_STORED_STRING_LENGTH: "Maximum length string for a stored field." (IndexWriter.java:260). StoredFields#document "Returns the stored fields of the n-th Document" and declares only CorruptIndexException and IOException (StoredFields.java:48-62). DataOutput.writeString and DataInput.readString are documented as a pair (@see, DataOutput.java:263-270, DataInput.java:221-225): the writer side accepts what the reader side refuses.
  • The limit's purpose. LUCENE-7538 (#8589, 6.4.0): "Asking IndexWriter to store a too-massive text field now throws IllegalArgumentException instead of a cryptic exception that closes your IndexWriter" (lucene/CHANGES.txt:8734-8736). In the same issue Michael McCandless answered a user asking for the size limit: "see IndexWriter.MAX_STORED_STRING_LENGTH for the limit; you'll have to either not store that huge file, or break it up across several documents." The visitor merge and the sorted flush here end in the writer-closing outcome that change replaced with an up-front exception.
  • The format's documented limit is larger. The default stored-fields format excludes only documents larger than 2^31 - 2^14 bytes (Lucene90StoredFieldsFormat.java:96-99); this document is about 2^30 bytes. No javadoc names a lower, content- or JDK-dependent limit.
  • No test covers it. The only near-limit test, TestIndexWriter.testMassiveField, is @Ignore("requires running tests with biggish heap") and checks only the rejection above the limit (TestIndexWriter.java:3066-3095).
  • History. The limit was chosen in 2016, when Lucene ran on Java 8, whose decoder had no 2^30 cap; JDK 9's compact strings halved the maximum size of a non-Latin-1 String (JDK-8190429, Won't Fix). The two limits stopped matching then; nothing in the history shows the gap was considered (the Java 8 reading is an inference, not executed).
The devil's-advocate check229 words

The strongest case (the verification reviewers rated it weak; the later fact check by another model family rated it moderate, mainly because a 1 GiB field is operationally extreme): this is a JDK limit, not a Lucene bug; the constant bounds the encode buffer and never promised that every accepted string reads back; gigabyte stored fields are unreasonable (in #8589, Erick Erickson wrote "I question whether it's reasonable to even try to index documents this large"); and IndexWriter's javadoc says it closes itself on any Error.

Why it fails: Lucene chooses both the bound it accepts and the decode call. The cap is a fixed property of every JDK that main supports and, once the heap holds the bytes, does not depend on the heap size, so the failure is deterministic, not an occasional resource problem. The decoded 357.9M-char string is representable (the writer held it) and UnicodeUtil.UTF8toUTF16 decodes it (see the fix). The committer who added the constant presented it to users as the limit of what can be stored; "unreasonable" is an opinion in a comment, not documentation, and the user in that thread answered that their 1 GB files are a valid use case. "Closes on any Error" explains the second symptom, not the first Error. The extreme trigger lowers the priority, which its Low rating reflects; it does not make the behaviour correct.

Suggested fix

#

Recommended Decode large values with UnicodeUtil.UTF8toUTF16 into an exact-size char[]

In DataInput.readString, for 2^30 - 1 or more bytes, count the UTF-16 characters, decode with Lucene's own UnicodeUtil.UTF8toUTF16 into a char[] of that size and build the String from it. Shorter strings keep today's path, and existing indexes of the default stored-fields format become readable. It passes the repro, 996 tests of the closest suites and :lucene:core:check.

All options and trade-offs3 options · 837 words

Two read-side fixes were run through gradle in a scratch worktree of 645d4fe14a20 (OpenJDK 25.0.3, seed DEADBEEF, gradle's default test JVM arguments). Both change only DataInput.readString and only for byte lengths of 2^30 - 1 or more. Every stored-string read of the default stored-fields format goes through readString, so they fix all of its executed paths at once (StoredFields#document, the visitor merge, the index-sort flush, CheckIndex) with no format change. They do not touch the non-default SimpleText codec, which decodes on its own (SimpleTextStoredFieldsReader.java:165), and were tested on the default codec only. The closest suites never reach the new branch (nothing in them is near 1 GiB); the repro and the shadow runs do.

Decode large values with UnicodeUtil.UTF8toUTF16 into an exact-size char[] (validated by the checks) (recommended)

#

In DataInput.readString (DataInput.java:226-231), plus import org.apache.lucene.util.UnicodeUtil;. One counting pass over the bytes finds the UTF-16 length (one unit per lead byte, two for a 4-byte sequence), then Lucene's decoder fills a char[] of exactly that size.

     readBytes(bytes, 0, length);
-    return new String(bytes, 0, length, StandardCharsets.UTF_8);
+    if (length < (Integer.MAX_VALUE >> 1)) {
+      return new String(bytes, 0, length, StandardCharsets.UTF_8);
+    }
+    // String(byte[], UTF_8) sizes its UTF-16 buffer by the byte count and refuses 2^30 - 1 or
+    // more units, although the decoded string is shorter: count the UTF-16 units, then decode
+    int numChars = 0;
+    for (int i = 0; i < length; i++) {
+      final int b = bytes[i] & 0xff;
+      if ((b & 0xc0) != 0x80) { // a lead byte; 4-byte sequences decode to a surrogate pair
+        numChars += b >= 0xf0 ? 2 : 1;
+      }
+    }
+    final char[] chars = new char[numChars];
+    return new String(chars, 0, UnicodeUtil.UTF8toUTF16(bytes, 0, length, chars));
   }

Trade-offs

  • One extra pass over the bytes, only on this rare path. The temporary char[] is 716 MB for this value, next to the 1 GiB byte[] that readString already allocates. Latin-1-only values of 2^30 - 1 or more bytes, which read back today, take the new branch too, so their temporary memory changes as well (a char[] at 2 bytes per char instead of the JDK's own copies); that case was not run with this fix and its heap use was not measured.
  • UnicodeUtil.UTF8toUTF16 does not validate UTF-8 and can throw on invalid input (its javadoc), unlike the JDK decoder, which substitutes malformed input. Lucene's own writers produce valid UTF-8 (the stored-fields writer's ByteBuffersDataOutput.writeString encodes with UnicodeUtil.UTF16toUTF8, which writes unpaired surrogates as U+FFFD) and index files are trusted. But readString is a public DataInput method, so malformed input of that size from any other source (a corrupt file, or data another writer produced) would behave differently.

The hunt's fix: decode into a char[length] temporary (validated by the checks)

#

The same branch in DataInput.readString, without the counting loop.

+    if (length < (Integer.MAX_VALUE >> 1)) {
+      return new String(bytes, 0, length, StandardCharsets.UTF_8);
+    }
+    final char[] chars = new char[length];
+    final int numChars = UnicodeUtil.UTF8toUTF16(bytes, 0, length, chars);
+    return new String(chars, 0, numChars);

Trade-offs

Simplest, but the char[length] temporary costs 2 bytes per UTF-8 byte, 2 GiB for this value. Under gradle's default test JVM arguments (-XX:+UseParallelGC) the repro then runs out of heap at 6g and needs 8g.

What the checks validated

Gradle: the repro passes at -Ptests.heapsize=8g with assertions on and off; the same closest suites pass (38 classes, 996 tests, 0 failures, 26 skipped); :lucene:core:check -x test passes. Shadowed onto the stock jars it passed the hunt's 3 tests, the refute reviewer's own repro, and the minimal test at 6 GB with the standalone runner.

Reject the value at index time (not run)

#

Check the UTF-8 byte length in IndexingChain (only for strings longer than 357,913,940 chars, so normal strings pay nothing), or lower MAX_STORED_STRING_LENGTH to 357,913,940 chars.

Trade-offs

Gives the up-front IllegalArgumentException LUCENE-7538 intended, also for the sorted flush, but leaves already written documents unreadable. A plain byte-length rule, or the lower constant, newly rejects Latin-1 or ASCII strings that read back today; an exact rule would mirror a JDK implementation detail. Complementary to a read-side fix, which alone removes every executed failure.

Downstream note

#

Not a Lucene security issue; downstream, a service that stores user-supplied text should cap field sizes well below 1 GiB, as common request-size limits already do.

How it was found

#

Found by execution, not by a model: while validating a fix for a separate stored-fields writer bug, a 2.1 GB stored string failed to read back in DataInput.readString. The boundary was then measured on stock jars (1,073,741,820 bytes read back, 1,073,741,823 fail), and independent checkers reproduced it with their own tests.

The method in full117 words

Method: non-formal (found by execution), a hunt unit on the compressing stored-fields format.

  • A separate finding of the same unit, an int overflow in the stored-fields writer's slice loop for chunks over about 2^31 bytes (LFV-186), was being validated with a patched writer that stored a 2.1 GB String. The read-back failed in DataInput.readString with the JDK's "UTF16 String size" error.
  • An AI tool then measured the boundary on the stock jars and wrote a deterministic JUnit with a control on each side: 357,913,940 chars (1,073,741,820 bytes) read back, 357,913,941 chars (1,073,741,823 bytes) fail.
  • The unit's Z3 model of the stored-fields chunk arithmetic (an obligation on MAX_STORED_STRING_LENGTH) gives context only; it did not produce this signal.

History

#

Not bisectable: every release run on JDK 25 fails, 5.5.5 to 10.6.0 and main. The 2008 decode call broke when JDK 9 halved the maximum non-Latin-1 String; the 2016 limit (LUCENE-7538, 6.4.0) states the contract it breaks. Not fixed upstream.

Versions tested7 rows

No Lucene commit introduced the failure. It needs three ingredients from different changes:

  1. Stored strings are decoded with the JDK's String(byte[], ..., UTF-8) constructor since LUCENE-510 (8af3598b74d, 2008, first released in 2.4.0); the decode site moved with LUCENE-5989 (5.2.0) and LUCENE-8805 (5a694ea26ff, 9.0.0, into DataInput.readString), each time keeping the same constructor.
  2. JDK 9+ compact strings size the UTF-16 buffer by the byte count and refuse about 2^30 or more units (JDK 21 and 25 from 2^30 - 1; JDK 11 and 17 above it; from the OpenJDK sources, only JDK 25 run). -XX:-CompactStrings does not avoid it (that branch calls the same newBytesFor(length), JDK 25 String.java:606). JDK 8 had no such cap.
  3. LUCENE-7538 (2902727a157 / be47009ce76, 2016-11-10, first released in 6.4.0) added MAX_STORED_STRING_LENGTH, the limit the bug violates. It did not create the failure: 6.3.0, without the limit, fails identically.

From 5.2.0 (LUCENE-5989) to 8.x a StoredFieldVisitor received the raw bytes (5.1.x and earlier passed a decoded String), so an application could decode the field itself; LUCENE-8805 moved the decode into the codec reader, and from 9.0.0 on no visitor can avoid it. readString is unchanged on upstream main 2f424fd428da (2026-10-30), and was identical on branch_10x, branch_10_6, branch_10_5 and branch_9_12 on 2026-10-26.

LFV-172, snapshot of 2026-11-07

Registry title
IndexWriter accepts a stored string of 2^30 - 1 or more UTF-8 bytes of non-Latin-1 text (from about half of its own MAX_STORED_STRING_LENGTH up), but DataInput.readString can never decode it, so StoredFields#document, visitor-path merges and index-sorted flushes throw OutOfMemoryError
Area
core store + index / stored string fields (DataInput.readString decode, IndexWriter.MAX_STORED_STRING_LENGTH check)
Priority
Low, rank 968: A stored string of at least 2^30-1 UTF-8 bytes of non-Latin-1 text is accepted but can never be read back (OutOfMemoryError, and a tragic flush under index sorting), reachable with one ~1 GiB field.
Impact class
crash
Impact note
Any application on the default codec and configuration that stores one text field of at least 2^30 - 1 UTF-8 bytes containing a non-Latin-1 character (for example about 358M CJK chars, roughly half of IndexWriter.MAX_STORED_STRING_LENGTH of about 715.8M chars) is hit: the document is accepted and committed, but every full stored-field load of it throws java.lang.OutOfMemoryError whatever the heap size, CheckIndex -level 2 flags its whole segment, and visitor-path merges (addIndexes into an index with other field numbers [exec]; SortingCodecReader [read]) and, with an index sort, the next flush [exec] throw the same Error and close IndexWriter, losing uncommitted documents while the last commit stays intact; extreme scale (about 1 GiB in one field, several GB of heap at index time), JDK 9+ runtimes, executed on JDK 25 only.
Summary
You store a text field of 357,913,941 CJK characters (1,073,741,823 UTF-8 bytes, about half of what IndexWriter's own length check, MAX_STORED_STRING_LENGTH, allows) with the default codec, and IndexWriter accepts and commits it. You expect StoredFields#document to return it, as it does for a string one character shorter. Instead every read throws java.lang.OutOfMemoryError 'UTF16 String size is 1073741823, should be less than 1073741823', whatever the heap, because DataInput.readString decodes with new String(bytes, 0, length, UTF_8), which on JDK 9 and later sizes its UTF-16 buffer by the byte count and refuses 2^30 - 1 or more units; merges that copy the document through a visitor, and flushes of an index-sorted writer, throw the same Error and close IndexWriter.
