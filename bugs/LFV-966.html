Flexible query parser: a processor put on the pipeline through listIterator(), subList() or replaceAll() gets no config

A processor put on the flexible query parser's QueryNodeProcessorPipeline through listIterator(), subList() or replaceAll() does not get the pipeline's config, unlike with add or set. A fresh PointQueryNodeProcessor swapped in that way makes n:5 silently find 0 of 1 matching documents; 9 of the 21 stock processors throw NullPointerException instead.

The bug in 30 seconds

#

A QueryNodeProcessorPipeline hands its config to every processor you put on it with add or set. Put one on through listIterator(), subList() or replaceAll() and it gets none: point queries then match nothing, field boosts and the default phrase slop vanish, or parsing throws NullPointerException.

Background: how the flexible query parser processes a query

#
  1. StandardQueryParser parses the text into a tree of query nodes, runs the tree through a pipeline of processors, then builds the Lucene Query from the tree.
  2. The pipeline, QueryNodeProcessorPipeline, is a java.util.List of processors (21 in StandardQueryParser). Each processor reads its settings, such as which fields hold points, field boosts, the default phrase slop or the analyzer, from one shared config object, the QueryConfigHandler.
  3. A processor finds that config through its own getQueryConfigHandler(); the pipeline is the one that hands it to each processor on it.

The bug, step by step

#
  1. Configure StandardQueryParser so field n holds int points and field f has boost 2, index one document with IntPoint n = 5, and take the parser's pipeline of 21 processors.
  2. Swap its PointQueryNodeProcessor for a fresh one (in real code: your subclass) with the usual loop: if (it.next() instanceof PointQueryNodeProcessor) it.set(new PointQueryNodeProcessor());.
  3. You expect what pipeline.set(6, p) gives: n:5 becomes the point query n:[5 TO 5] and finds the 1 document. The class says it hands its config to all processors on it, and its own add and set do.
  4. You get n:5 as a TermQuery: 0 hits, no error. The iterator writes straight into the pipeline's private ArrayList, so the new processor's config stays null and it skips its work.
  5. The same through subList(..).set, replaceAll or Collections.replaceAll (from 11 processors, on JDK 25): f:foo loses its boost of 2, the default phrase slop is dropped, and 9 of the 21 stock processors throw NullPointerException at parse.

Who is affected

#

Opt-in and rare: code that edits a flexible parser pipeline through ListIterator.add/set, subList, replaceAll or Collections.replaceAll, such as StandardQueryParser's own pipeline after a cast, and does not re-set the config afterwards. Swapped this way, 9 of the 21 stock processors throw on the first parse and 4 (point, point range, boost, default slop) fail silently. Every release since 3.1.0.

Mechanism, terms and numbers805 words

QueryNodeProcessorPipeline, the processor chain of the flexible query parser, implements java.util.List and promises to set its QueryConfigHandler "on all processor on pipeline". Its own add, add(int), addAll, addAll(int) and set do that for each processor they put on the pipeline. But listIterator(), listIterator(int) and subList() return the views of its private ArrayList, and replaceAll is not overridden, so a processor put on the pipeline through ListIterator.add/set, subList(..).add/set, List.replaceAll, Collections.replaceAll on a pipeline of 11 or more processors, or Collections.copy of 10 or more processors into it (JDK 25's thresholds) is not given the pipeline's handler: a fresh processor keeps null. Nothing hands it out again before parsing.

Four stock processors check for a null handler and silently do nothing: on StandardQueryParser with n configured as an int point field, a PointQueryNodeProcessor swapped in through listIterator().set leaves n:5 a TermQuery that finds 0 of the 1 matching document, a swapped BoostQueryNodeProcessor drops field boosts, and the point-range and default-slop processors lose their work too. Nine others throw NullPointerException at parse. It is opt-in (only code that edits a pipeline this way), present since 3.1.0, and the workaround is to call setQueryConfigHandler again after editing. The fix wraps the two views so their add and set hand out the handler.

Terms

#
  • Pipeline: QueryNodeProcessorPipeline implements QueryNodeProcessor, List<QueryNodeProcessor> (QueryNodeProcessorPipeline.java:39). It keeps the processors in a private ArrayList (:41) and runs them in order (process, :75-82). It is not RandomAccess.
  • Config: the QueryConfigHandler. Class javadoc: "When a QueryConfigHandler object is set on a QueryNodeProcessorPipeline, it also takes care of setting this QueryConfigHandler on all processor on pipeline" (:36-37). setQueryConfigHandler loops over the processors (:93-99).
  • Views: java.util.List hands out a ListIterator and a subList view that can add and replace elements; the List default replaceAll and the Collections helpers are built on them.

The bug

#
  1. Every method the pipeline overrides to put a processor on it also hands it the config: add (:105-113), add(int) (:119-122), addAll (:128-136), addAll(int) (:142-150), set (:268-276): processor.setQueryConfigHandler(this.queryConfig).
  2. listIterator() (:220-222), listIterator(int) (:228-230) and subList (:290-292) return the private ArrayList's own views. Their add and set write straight into the ArrayList, so the processor keeps the config it had: none, for a fresh one.
  3. The pipeline does not override replaceAll; JDK 25's default is ListIterator li = this.listIterator(); while (li.hasNext()) li.set(operator.apply(li.next())); (List.java:437-443). Collections.replaceAll uses the list iterator on a list that is not RandomAccess and has 11 or more elements, Collections.copy when it copies 10 or more elements (Collections.java:111-112, :587, :870); StandardQueryParser's pipeline has 21. These thresholds are JDK 25 implementation choices, not part of the List contract; another JDK may differ. reversed() inherits the gap through its list iterator and replaceAll; reversed().set calls the pipeline's set and is fine.
  4. Nothing repairs it before the parse: QueryParserHelper.parse just calls process (QueryParserHelper.java:213-223). Only setQueryConfigHandler (:185-192), setQueryNodeProcessor (:100-103) and the helper's constructor (:71-73) hand the config out. Calling a setter such as setPointsConfigMap again does not help: it only writes into the config.
  5. PointQueryNodeProcessor (:65-67), PointRangeQueryNodeProcessor (:61-63), BoostQueryNodeProcessor (:47-49) and DefaultPhraseSlopQueryNodeProcessor (:51-53) check if (config != null) and otherwise do nothing. Others dereference it, for example AnalyzerQueryNodeProcessor.process (:82), and throw NullPointerException.

Exposure and likelihood305 words
  • Who is exposed. Code that customises a flexible query parser pipeline through these paths: editing StandardQueryParser's pipeline in place after a cast of getQueryNodeProcessor() (the in-tree idiom in TestQPHelper.java:163-167, and the advice in java-user threads of 2010 and 2014, which use add), or a pipeline built with new QueryNodeProcessorPipeline(config) and used directly (like TestSpanQueryParserSimpleSample.java:98-103, which uses add). The package docs invite this ("select your favorite query processors and build a pipeline", standard/package-info.java:55-58), and LUCENE-1937 added the List API "if you want to extend or modify an existing pipeline".
  • Natural idioms reach it. "Insert my processor after X" is the ListIterator.add loop; "swap X for my subclass" is replaceAll(p -> p instanceof X ? new MyX() : p) or Collections.replaceAll(pipeline, old, new MyX()).
  • Not affected. An unedited parser; edits through the pipeline's add, add(int), addAll, set, addFirst/addLast; moves and removals (Collections.swap, reverse, rotate, shuffle, sort, remove); Collections.replaceAll on 10 or fewer processors; a pipeline edited before it is installed with setQueryNodeProcessor or the parser helper's constructor, which hand the config to every processor.
  • Loud vs silent. In the stock differential (each of the 21 stock processors swapped through the 6 view paths, 22 queries), 9 processors give a NullPointerException on the first parse that reaches them and 8 give the same result. Swapping the other 4, the point, point-range, boost or default-slop processor, or inserting a custom processor that tolerates a missing config, gives silently wrong queries: point queries that match nothing, lost boosts (ranking changes), lost default slop (fewer phrase matches).
  • Scale. None: one edit and one query reproduce it, with assertions on or off.
  • Workaround. After editing, call qp.setQueryConfigHandler(qp.getQueryConfigHandler()), pipeline.setQueryConfigHandler(...) or qp.setQueryNodeProcessor(pipeline), or edit with add(k, p) / set(k, p).

Why it is a bug, not intended

#
  • The class promises its config "on all processor on pipeline"; its own five insert and replace methods and the old addProcessor keep that.
  • add(k, p) and listIterator(k).add(p) are the same List operation yet parse differently; Collections.replaceAll differs between 10 and 11 processors.
  • LUCENE-1937 added the List API so users could edit a pipeline, for example insert after a processor.
The full argument225 words
  • The class states the rule and keeps it everywhere else. The javadoc promises the pipeline "takes care of setting this QueryConfigHandler on all processor on pipeline" (QueryNodeProcessorPipeline.java:36-37). Each of the five overriding mutators that put a processor on it calls processor.setQueryConfigHandler(this.queryConfig) (:105-150, :268-276), and so did the original single entry point, addProcessor, before LUCENE-1937. The views are the only way in that skips it; no exemption for them was found in the checked source and javadocs, tests, CHANGES/MIGRATE or prior-art searches.
  • Same operation, different result. java.util treats add(k, p) and listIterator(k).add(p), or set(k, p) and listIterator().set(p), as the same element operation; here they parse differently. Collections.replaceAll sets the config on a pipeline of 10 processors and not on one of 11.
  • The API exists for this edit. #3012 (LUCENE-1937): the pipeline was "not very flexible when the user wants to extend/modify an already created pipeline", and the proposed method was insertAfter(processor, newProcessor), the ListIterator.add idiom. CHANGES 3.1: "QueryNodeProcessorPipeline now implements the List interface, this is useful if you want to extend or modify an existing pipeline."
  • Tests. No queryparser test uses listIterator, subList or replaceAll on a pipeline; in-tree edits use add (TestQPHelper.java:163-167, TestSpanQueryParser.java:102-111, TestSpanQueryParserSimpleSample.java:98-103). No CHANGES or MIGRATE entry mentions the views. With the fix every upstream queryparser suite passes.
The devil's-advocate check236 words

The strongest case for "intended" (built by the devil's-advocate verifier; the cross-model reviews rated it weak): read literally, the javadoc promises propagation only "when a QueryConfigHandler object is set on" the pipeline, not on each insertion; the mutators' javadocs are bare @see List#add and promise nothing; QueryNodeProcessor says the handler "should be set using ... setQueryConfigHandler(QueryConfigHandler) before ... process(QueryNode) is invoked" (QueryNodeProcessor.java:32-34), which puts the duty on the caller; java.util.List does not require views to go through overridden methods; editing StandardQueryParser's pipeline needs a cast; stock processors tolerate a missing config on purpose; and the workaround is one call.

Why it fails: here the pipeline has a config and every neighbouring processor carries it, and the processor arrives through the pipeline's own public List API, so the pipeline is the caller that owes it the config, as its five mutators and addProcessor show. The same failure happens on new QueryNodeProcessorPipeline(config) with no cast. The null tolerance is meant for a pipeline without a config; here it turns a missing config into silently wrong queries. Calling the documented setters again does not repair it, only re-setting the handler does, and none of the checked documentation says so. A maintainer could choose to document a limitation (fix option D), but that is not evidence of intent. Do not frame it as a java.util.List contract violation; frame it as the views bypassing the class's own rule.

Suggested fix

#

Recommended Wrap listIterator() and subList() so their add and set hand out the config

Wrap the two views: listIterator(int) and subList return thin wrappers around the backing list's own views whose add and set also call processor.setQueryConfigHandler(queryConfig), so they stay fail-fast. The repro and the whole queryparser module (538 tests, 0 failures) pass, with assertions on and off.

@Override
public ListIterator<QueryNodeProcessor> listIterator(int index) {
  return new ConfiguringListIterator(this.processors.listIterator(index));
}

@Override
public List<QueryNodeProcessor> subList(int fromIndex, int toIndex) {
  return new ConfiguringSubList(this.processors.subList(fromIndex, toIndex));
}

/** Sets this pipeline's handler on a processor that a view put on the pipeline. */
private void configure(QueryNodeProcessor processor) {
  processor.setQueryConfigHandler(this.queryConfig);
}

Wrap listIterator() and subList() so their add and set hand out the config (validated by the checks) (recommended)

#

listIterator(int) returns a ConfiguringListIterator around this.processors.listIterator(index): it forwards every method and does in.set(p); configure(p); and in.add(p); configure(p);. subList returns a ConfiguringSubList extends AbstractList<QueryNodeProcessor> implements RandomAccess around this.processors.subList(from, to): get and size forward; set, add(int, p) and remove(int) call the backing sub list, plus configure(p) for set and add and modCount++ for add and remove, so AbstractList builds its iterators, nested sub lists, addAll and replaceAll on them. listIterator() delegates to listIterator(0); replaceAll and the Collections helpers are fixed through it. Because both wrappers delegate to the ArrayList's own views, a stale view still throws ConcurrentModificationException after a direct pipeline.add or remove.

Trade-offs

  • About 120 lines of plain delegation (two private nested classes).
  • The view's set hands out the config even when it writes the same processor back (the pipeline's own set skips that case), so List.sort, which rewrites every element through listIterator().set, re-sets each processor's config to the pipeline's. That only matters to code that gave one processor a different config on purpose.
  • Like today, insertions through a view do not go through a subclass's override of add or set.
  • The sub list stays RandomAccess, as ArrayList's sub list is.

Hand the config out again in process() (validated by the checks)

#

Three lines in QueryNodeProcessorPipeline.process (:77-79): before running each processor, set the pipeline's handler on it if it differs.

for (QueryNodeProcessor processor : this.processors) {
  if (processor.getQueryConfigHandler() != this.queryConfig) {
    processor.setQueryConfigHandler(this.queryConfig);
  }
  queryTree = processor.process(queryTree);
}

Trade-offs

Covers every insertion path, including future ones, with the smallest change. But it overrides a config that code set on one processor on purpose, writes to processors on every parse, and leaves the state wrong between the edit and the first parse: an inserted processor still reports a null config until then.

Route view edits through the pipeline's own add/set/remove, or make the pipeline extend AbstractList (validated by the checks)

#

The hunt's sketch returns a fresh AbstractList view per call whose set, add and remove call the pipeline's own methods. A variant the verifiers and the audit suggested: let QueryNodeProcessorPipeline extend AbstractList and bump modCount in its own mutators.

Trade-offs

The sketch loses fail-fast: an independent reproducer showed (executed) that a stale listIterator or subList no longer throws after a direct pipeline.add or remove, and the stale sub list silently returns elements. The AbstractList variant would keep fail-fast but changes equals/hashCode from identity (the pipeline overrides neither today) to element equality.

What the checks validated

The sketch passes the finder's and the reproducer's tests, the history probe, the model-based test (0 violations), the stock differential (147 equal) and 150 upstream flexible-parser tests; its fail-fast check fails 2 of 2. The AbstractList variant was not run.

Document that only the pipeline's own add and set hand out the config

#

Add a note to the class and view javadocs, and point to the workaround.

Trade-offs

No code change, but it keeps the silent cases and undercuts the List API that LUCENE-1937 added for editing pipelines.

Downstream note

#

Applications and search servers that customise the flexible parser's pipeline in place should edit it with add/set or re-set the config afterwards; a query string alone cannot trigger it.

History

#

Introduced in 3.1.0 by LUCENE-1937 (6f66858572c, 2010-10-19), which made the pipeline a List with raw views. It fails on every release tried from 3.1.0 to 10.5.2, on branch_10_6 and on main; 2.9.4 and 3.0.3 have no List API. Not fixed upstream.

Versions tested8 rows

Bug record

#

LFV-966, snapshot of 2026-10-29

Registry title
QueryNodeProcessorPipeline's listIterator()/subList() views, and replaceAll / Collections.replaceAll built on them, put processors on the pipeline without its QueryConfigHandler, so the flexible query parser silently skips point, boost and default phrase slop handling or throws NullPointerException
Area
queryparser / flexible core: QueryNodeProcessorPipeline (java.util.List views and default methods)
Impact class
silent wrong results
Impact note
Opt-in only: applications that edit a flexible query parser processor pipeline (their own QueryNodeProcessorPipeline, or StandardQueryParser's through getQueryNodeProcessor()) with ListIterator.add/set, subList(..).add/set, List.replaceAll or Collections.replaceAll/copy (the last two only on pipelines of 11 or more processors; StandardQueryParser's has 21) and do not call setQueryConfigHandler again get silent wrong queries from 4 stock processors (Point, PointRange, Boost, DefaultPhraseSlop: a point query matches nothing, field boosts and the default phrase slop are lost) and a NullPointerException at parse from 9 others; an unedited StandardQueryParser and edits through add/set are not affected; ordinary scale.
Summary
You customise a flexible query parser pipeline, for example StandardQueryParser's, by inserting or replacing a processor through the pipeline's java.util.List API: pipeline.listIterator() then add or set, subList(..).set, pipeline.replaceAll or Collections.replaceAll. You expect the processor to receive the pipeline's QueryConfigHandler, as it does with add(k, p) or set(k, p), because the class says it 'takes care of setting this QueryConfigHandler on all processor on pipeline'. Instead those paths write through the private ArrayList's own views and leave the processor with a null handler, so a replaced PointQueryNodeProcessor turns n:5 into a TermQuery that finds 0 of 1 matching documents, a replaced BoostQueryNodeProcessor drops field boosts, and most other stock processors throw NullPointerException at parse.
