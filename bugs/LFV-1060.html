IndexWriter.hasUncommittedChanges() can return false for an uncommitted delete while another thread flushes

While another thread flushes or opens an NRT reader, hasUncommittedChanges() can return false for a still-uncommitted delete: it reads the change counter before the in-RAM buffers, and the flush moves the delete between them. The next call returns true; code that commits only on true skips a commit.

The finding in 30 seconds

#

The method checks two places, one after the other: first the change counter, then the RAM buffers. A flush moves a delete the other way, from the buffers into the counter. If the move happens between the two checks, the method sees the old counter and empty buffers, and answers false.

Background

#
  1. The change counter. IndexWriter counts applied changes in changeCount, and commit() remembers the value it committed. A new in-memory segment or an applied delete increments it.
  2. Buffered deletes. deleteDocuments records the delete in RAM and the counter does not move (unless buffered deletes use too much heap; then they are applied at once). A flush (flush(), opening or refreshing an NRT reader, a full RAM buffer) applies it to the segments, and only then does the counter go up. A flush does not commit.
  3. hasUncommittedChanges(). True if the counter differs from the last commit's value, or if RAM still holds changes. Its javadoc lists cases of a spurious true, none of a false.

The finding, step by step

#
  1. Add a document id:1 and commit(): the last commit holds 1 document. Then deleteDocuments(new Term("id", "1")). The delete waits in RAM and the change counter does not move, so hasUncommittedChanges() is true only because of its RAM check.
  2. Thread B calls hasUncommittedChanges(). It first compares the change counter with the last commit's value: equal. Before B looks at RAM, thread A runs flush(), which applies the delete, increments the counter and then empties the buffers. It does not commit.
  3. You expect true: the delete was acknowledged before B's call, no commit ran, and a commit() now still writes it.
  4. Instead B finds the buffers empty and returns false; the next call returns true. The test forces this order and fails with assertions on and off, 10 of 10 seeds.
  5. Without hooks, two threads busy-polling during 19,211 flush rounds in 10 s made 302 wrong calls among about 2.56 billion, in 238 of the rounds; one call per flush round got 0 of 61,904. A caller that commits only on true skips that commit.

Who is affected

#

Applications that call hasUncommittedChanges() on one thread while another flushes, opens or refreshes an NRT reader, default config, every release since 4.5.1. The false is transient and the writer keeps the delete; only code that commits only on true skips a commit. Not seen with one check per flush (0 of 61,904); observable for a busy-polling caller.

Mechanism, terms and numbers861 words

IndexWriter.hasUncommittedChanges() evaluates changeCount.get() != lastCommitChangeCount || hasChangesInRam() without a lock: first the change counter, then the in-RAM buffers. A buffered delete is visible only to the second check, because deleteDocuments does not increment the counter (unless buffered deletes use too much heap; then they are applied at once). A flush (flush() and an NRT reader open were run; a refresh or a RAM-triggered apply takes the same path) applies the delete, increments the counter in checkpoint(), and only then removes the delete from the buffered-updates stream. A call that reads the counter before that checkpoint() and the buffers after the delete left them returns false, although the delete was acknowledged before the call and is still not committed. The next call returns true. The writer still holds the delete and the next commit() or close() writes it, so the impact is Low: only code that decides whether to commit from this method skips a commit, and the delete is lost only if rollback() or a crash comes first. The read order dates from LUCENE-5289 (2013) and is in every release from 4.5.1 through 10.6.0 (read in all 114 release tags; 13 of them were run and fail). Reading the counter again after an empty RAM check fixes the demonstrated case without adding a lock.

The code (main 645d4fe14a20)

#
  1. The method. IndexWriter.java:4225-4227, no lock: return changeCount.get() != lastCommitChangeCount || hasChangesInRam();. changeCount is an AtomicLong, lastCommitChangeCount a volatile long (:272-273). hasChangesInRam() is docWriter.anyChanges() || bufferedUpdatesStream.any() (:4230-4232): documents in RAM, the delete queue (read under its globalBufferLock), the flush tickets and the full-flush flag (DocumentsWriter.java:344-357, :376-378; DocumentsWriterDeleteQueue.java:181-196), then bytesUsed != 0 of the buffered-updates stream (BufferedUpdatesStream.java:108-110).
  2. A delete only buffers (for a small delete like the repro's). deleteDocuments(Term...) hands the term to the delete queue (IndexWriter.java:1864-1872); the diagram probe prints changeCount 4 = lastCommitChangeCount 4 after the delete. When buffered deletes use too much heap, DocumentsWriter.applyDeleteOrUpdate freezes them at once and deleteDocuments applies them before it returns (DocumentsWriter.java:153-186, IndexWriter.java:6345-6350); that is not the case shown here. An added document is different: creating its in-memory segment increments changeCount at once (:2173-2179), which explains why add-only changes were not seen to fail (0 of about 17,000 hook-free rounds; the tested case, not a proof for every add path).
  3. A flush moves the delete stage by stage. flush() runs doFlush (IndexWriter.java:4403-4413): flushAllThreads() freezes the delete into a flush ticket; publishFlushedSegments(true) pushes the frozen packet to the buffered-updates stream (IndexWriter.java:2928-2947), then lowers the ticket count (DocumentsWriterFlushQueue.java:99-105); processEvents(false) runs the packet's apply event, tryApply(packet). If another thread already holds the packet, tryApply returns and that thread applies it (IndexWriter.java:6491-6500); flush() then waits for all packets (:4417-4419, :4440-4452). Whoever applies it runs forceApply (:6508): updates.apply(segStates) (:6592), then finishApply (:6597) calls checkpoint() because a document was deleted (:6721-6724), which increments changeCount (:2923-2926); then bufferedUpdatesStream.finished(updates) (:6640) subtracts the packet's bytes (BufferedUpdatesStream.java:152-167). A delete packet that matches no document is finished with no checkpoint() (:6721; or it reaches no segment, :6562-6567, :6661-6664); that delete leaves nothing to commit. The NRT path getReader runs the same steps (IndexWriter.java:584-593).
  4. Each hop overlaps the next. The ticket count goes up before the freeze (DocumentsWriterFlushQueue.java:39: "first inc the ticket count - freeze opens a window for #anyChanges to fail"), the packet reaches the stream before the ticket count goes down, and the counter goes up before the packet leaves the stream. A reader that looks at the stages in the order the change travels (RAM first, then the counter) always finds a delete that matches a document.
  5. The method reads the other way round. It reads the last stage, the counter, first. If checkpoint() runs after that read and finished() before its stream read, it sees neither. The caller does not have to straddle a whole flush, only the short gap between checkpoint() and finished(), which is why a busy-polling caller can hit it.
  6. The sibling is safe. nrtIsCurrent (IndexWriter.java:6140-6146) is synchronized on the writer, like checkpoint() and the finished() call, so it cannot fall into this gap.

The numbers

#

The minimal test (one committed document, one delete, one flush()) returns false with assertions on and off, 10 of 10 random seeds. A TLA+ model of the two reads against one full flush gives a 16-state counterexample for the stock order and passes exhaustively for both fixes (105 and 117 distinct states); "exhaustively" holds for that model only (one matching delete, no buffered documents, one full flush; no commits, non-matching packets, merge retries or doc-values updates). Hook-free public-API runs with busy-polling threads, default config: 47 of 8,753 flush rounds in 10 s (adjudication, 63 wrong calls among about 2.94 billion); with 2 polling threads 238 of 19,211 flush rounds (302 wrong calls among about 2.56 billion) and 173 of 20,962 NRT-open rounds, 0 with the re-read fix; one call per flush round 0 of 61,904.

Exposure and likelihood289 words
  • Who. Code that calls hasUncommittedChanges() on one thread while another thread runs flush() or DirectoryReader.open(writer) (both run), or openIfChanged, SearcherManager.maybeRefresh or a RAM-triggered apply of deletes (the same path by reading, not run); default IndexWriterConfig. IndexWriter is documented as "completely thread safe, meaning multiple threads can call any of its methods, concurrently": that promises safe concurrent calls, not an atomic snapshot of the writer's state.
  • What breaks. A transient false for an acknowledged, uncommitted delete. Code that commits only when the method returns true (a periodic "commit if dirty" task, a shutdown step, a replication trigger) skips that commit.
  • What does not break. The writer still holds the delete: the next commit() or close() (commitOnClose defaults to true) writes it, a newly opened NRT reader already sees it, and searches are correct. The delete is lost only if the skipped commit was the last one before rollback() or a crash; otherwise a skipped commit only delays durability. No wrong search result, corruption or downstream incident was shown. In Lucene itself the only non-test caller is an assert in IndexUpgrader.
  • How often. Not seen with one check per flush: 0 of 61,904 rounds. Observable under sustained busy polling while another thread flushes: 47 of 8,753 rounds in 10 s; with NRT opens, 173 of 20,962 rounds. Each such round had at least one wrong call among billions of tight-loop calls (302 among about 2.56 billion in the tie-break flush run), so these are not rates for a periodic poller.
  • Scope. Deletes are shown; doc-values updates take the same path but were not executed, so they are not claimed. Add-only changes were not seen to fail (0 of about 17,000 rounds; the tested case, not a proof).

Minimal repro

#

One JUnit test, one method, default config, no sleeps. Concurrency is the bug, so it forces the order instead of racing: it holds the delete queue's lock, which is package-private for tests, so thread B waits between its two reads while thread A runs flush(). A hook-free public-API program shows the same false answer.

Why it looks unintended

#
  • The javadoc lists only false positives (it "may return true when there are no actual 'real' changes"), never a false for an uncommitted change.
  • LUCENE-5289 (2013) fixed this same false for a buffered delete as a bug; its fix created the read order.
  • Lucene fixed the same in-transit window in nrtIsCurrent as bugs (LUCENE-3546, LUCENE-3551).
The full argument256 words
  • The contract. IndexWriter.java:4218-4224: "Returns true if there may be changes that have not been committed. There are cases where this may return true when there are no actual "real" changes to the index, for example if you've deleted by Term or Query but that Term or Query does not match any documents. Also, if a merge kicked off ... this method may return true right after you had just called commit." Every listed exception is a false positive.
  • The test. TestIndexWriter.testHasUncommittedChanges asserts true right after a buffered deleteDocuments (TestIndexWriter.java:2418-2419), sequentially.
  • The history. LUCENE-5289 (#6353) fixed the sequential form of this false as a bug and was backported to 4.5.1 because "Solr's replication depends on this feature" (Shalin Shekhar Mangar on #6353). Michael McCandless explained there: "It was failing to take into account any buffered changes that hadn't yet been 'resolved' (which increments the changeCount)." The fix (f9f0cdd56fd) added the RAM checks after the counter test. The javadoc's two "may"s both describe false positives: the merge caveat ("this method may return true right after you had just called commit") was added on the day of the fix (e1d5edea421, 2013-10-17, released in 4.5.1), and the hedge "there may be changes" with the no-match delete example came in a3c48b5ac41 ("improve javadocs", 2014-01-17, first in 4.7.0).
  • Precedent. LUCENE-3546 (#4620) and LUCENE-3551 (#4625, "Yet another race in IW#nrtIsCurrent") fixed the same kind of in-transit "no change" window in nrtIsCurrent; the comment at DocumentsWriterFlushQueue.java:39 comes from that work (Simon Willnauer's "window for #anyChanges" reasoning).
The devil's-advocate check261 words

The strongest case: the method is a deliberately cheap predicate that takes no writer lock. In LUCENE-5079 (#6143), which added it, Uwe Schindler argued for synchronized; Yonik Seeley chose a volatile read because it "might be nice to have on a GUI display", and Michael McCandless agreed ("volatile is best"). The javadoc says "may", and "thread safe" does not promise a linearizable answer. In a 2014 java-user thread Michael McCandless gave "Just history :)" and "maybe also paranoia/defensive" as the reasons commit() does not consult the method, and asked what the application was doing "that it so strongly relies on knowing whether commit() would do anything".

Why it fails: the cheap-read choice was made for a single comparison, changeCount != lastCommitChangeCount, which cannot give this answer; the two-source read came later, and neither fix adds a lock. Both "may"s describe false positives only. No linearizability is needed: in the case shown (a delete that matches a document, acknowledged before the call, no concurrent commit) the delete existed and stayed uncommitted for the whole call, so false matches no state the writer was in during the call. The same 2014 reply calls a wrong answer "a bug in hasUncommittedChanges", and LUCENE-5289 was fixed because downstream code gates commits on it. Verdict: not intended; it supports the Low impact, not "works as designed". A cross-model fact check rated the intended case moderate: the javadoc lists no false-negative exception but does not promise an atomic answer either, so the issue is best framed as a question (is the stronger behaviour wanted?).

Suggested fix

#

Recommended Re-read changeCount after an empty RAM check

Read the counter again after an empty RAM check: changeCount.get() != lastCommitChangeCount || hasChangesInRam() || changeCount.get() != lastCommitChangeCount. For a delete that matches a document, when the RAM check finds it gone the counter has already gone up. No added lock, and the cheap counter-first path stays. Validated: the repro passes, and so do 209 tests in 8 closest suites.

  public final boolean hasUncommittedChanges() {
    // a flush moves a change from RAM to changeCount (checkpoint) before it leaves RAM, so check
    // changeCount again after an empty RAM check
    return changeCount.get() != lastCommitChangeCount
        || hasChangesInRam()
        || changeCount.get() != lastCommitChangeCount;
  }
All options and trade-offs3 options · 475 words

Two one-statement fixes were validated in a scratch worktree of 645d4fe14a20. Both close the demonstrated case: for a delete that matches a document, checkpoint() increments the counter before the packet leaves the buffered-updates stream. A delete that matches no document is finished without a checkpoint(); a false is then not wrong, because that delete leaves nothing to commit. Neither was proven for concurrent commit(), rollback(), close or tragedy paths, merge retries or doc-values updates. A third option is not needed.

Re-read changeCount after an empty RAM check (validated by the checks) (recommended)

#

One file, +5/-1 in IndexWriter.hasUncommittedChanges(). Preferred by the adjudication and the intended-lens reviewer.

  public final boolean hasUncommittedChanges() {
    // a flush moves a change from RAM to changeCount (checkpoint) before it leaves RAM, so check
    // changeCount again after an empty RAM check
    return changeCount.get() != lastCommitChangeCount
        || hasChangesInRam()
        || changeCount.get() != lastCommitChangeCount;
  }

Trade-offs

One extra volatile read, only when the method is about to return false. It keeps the counter-first fast path, so no delete-queue lock is taken when the counter already differs, and it adds no lock (no writer lock; the RAM check takes the delete queue's lock as it does today), in line with the cheap read LUCENE-5079 chose.

Read the RAM state first (validated by the checks)

#

return hasChangesInRam() || changeCount.get() != lastCommitChangeCount;: it reads the stages in the order the change travels.

Trade-offs

Always evaluates hasChangesInRam() first, which takes the delete queue's lock whenever no document is buffered, even when the counter alone would answer. The cost was not measured.

What the checks validated

  • With the swap: the minimal test passes with assertions on and off (same gradle run; closest suites not re-run for this option).
  • Earlier evidence: TLC passes exhaustively for the model (105 distinct states); the independent reproduction's looped race 0 of 22,150 rounds; testHasUncommittedChanges* still pass (refute review).
  • Same limits as the re-read fix.

Not needed: make the method synchronized

#

Like nrtIsCurrent, this would close the window.

Trade-offs

LUCENE-5079 chose a cheap read without the writer lock on purpose ("there is IO that happens when 'this' is locked", Michael McCandless on #6143), and neither fix above adds one.

Downstream note

#

Solr's update handler and the Elasticsearch and OpenSearch engines call hasUncommittedChanges() when deciding whether to commit; whether their own locking leaves this window open was not checked, and no downstream report of a skipped commit was found.

How it was found

#

A code-reading lens on read-order and check-then-act sites in IndexWriter flagged the order of the two reads. A choreographed probe and a hook-free race showed the false answer on main, 10.6.0 and 10.5.2; a TLA+ model and one deterministic JUnit followed.

The method in full138 words

Method: code reading, then executed checks (the study's "non-formal" tier: the first signal was a code-reading lens, the TLA+ model came after).

  • A lens on IndexWriter's check-then-act and read-order sites proposed that hasUncommittedChanges() reads its two sources in an order that a flush can slip between.
  • A choreographed probe (the checker parked between its two reads while another thread's flush ran) and a hook-free public-API race witnessed the false answer on main, the 10.6.0 RC1 and 10.5.2 (flush: 32 of 67,775 rounds; NRT open: 42 of 75,992; 0 with the fix).
  • A TLA+ model of the read sequence against one full flush (TLC): a 16-state counterexample for the stock order; exhaustive passes for the swapped order (105 distinct states) and the re-read (117).
  • The finder reduced it to one deterministic JUnit; independent checks then reproduced it (below).

History

#

Introduced by LUCENE-5289 (f9f0cdd56fd, Michael McCandless, 2013-10-17), which fixed a sequential false by adding the RAM checks after the counter test; first released in 4.5.1. Every release from 4.5.1 through 10.6.0 has the read order (read in all 114 release tags), and the 13 releases that were run fail; not a regression. Not fixed upstream as of 2026-10-31.

Registry title
IndexWriter.hasUncommittedChanges() can return false for an acknowledged, uncommitted delete while another thread flushes or refreshes an NRT reader, because it reads changeCount before the in-RAM state (every release since 4.5.1)
Area
index / IndexWriter (hasUncommittedChanges: changeCount vs. buffered deletes in flight)
Priority
Low, rank 759: A default-config IndexWriter status-predicate race present since 4.5.1 whose wrong false is transient and only matters to callers that decide whether to commit from it.
Impact class
minor
Impact note
Applications that call hasUncommittedChanges() on one thread while another thread's flush(), NRT reader open or refresh, or RAM-triggered flush applies a buffered delete, default config: the call can return false although an acknowledged delete is still uncommitted; the next call returns true and the writer still holds the delete, so the next commit() or close() (commitOnClose defaults to true) commits it, and only an application that commits only when the method returns true skips that commit (the delete is then lost only if rollback() or a crash follows before a later commit); a single call per concurrent flush hit the window 0 times in 61,904 rounds, a caller that polls during flushes hits it regularly (47 of 8,753 rounds in 10 s); outside tests, only an assert in IndexUpgrader calls the method.
Summary
You delete a committed document with deleteDocuments, do not commit, and call hasUncommittedChanges() while another thread calls flush() or refreshes an NRT reader; you expect true, because the delete was acknowledged and is not in the last commit, and the javadoc allows only false positives. Instead the method reads changeCount first (still equal to the last commit's) and the in-RAM state second, and if the flush applies the delete, increments changeCount and empties the delete buffers between those two reads, it returns false; the next call returns true. A caller that commits only when the method returns true skips that commit.
