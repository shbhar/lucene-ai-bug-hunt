ConditionalTokenFilter loses a trailing stop-word hole when the last token went through the wrapped filters

Behind a StopFilter, ProtectedTermFilter and CustomAnalyzer when() branches report a final position increment of 0 instead of 1 for abc the when abc went through the wrapped filters. The next value of a multi-valued field starts one position early, so "abc def" matches ['abc the', 'def'] (since 7.4.0).

The bug in 30 seconds

#

A filter that removes tokens records the positions it skipped at the end of the stream, in end(), so the next value of the field starts after them. ConditionalTokenFilter loses that number when the last token went through its wrapped filters.

  1. You analyse text with WhitespaceTokenizer, then StopFilter({"the"}), then a ProtectedTermFilter around LowerCaseFilter (or the CustomAnalyzer chain stop, whenTerm(...), lowercase, endwhen()). ABC the gives the token abc; the removed the leaves a hole of 1 position at the end.
  2. You expect end() to report that hole as a final position increment of 1, as the same chain without the condition does, and as ProtectedTermFilter does when the last word is protected (x the: 1).
  3. You get 0 whenever the last token went through LowerCaseFilter, which never touches positions. Even a condition around a filter that does nothing (in -> in) gives 0; abc the the gives 0 instead of 2.
  4. With Lucene's default position increment gap of 0, the field values abc the and def put def at position 1 instead of 2, and PhraseQuery("f", "abc", "def") finds the document: 1 hit instead of 0.
  5. Why: the wrapped filters read from an internal stream whose end() imitates a tokenizer and resets the increment to 0, and end() keeps their result instead of adding the input's increment. In the middle of the stream the class does add it.

Who is affected

#

Users of ProtectedTermFilter (or its protectedTerm factory), CustomAnalyzer when()/whenTerm(), or another ConditionalTokenFilter placed after a StopFilter. Values ending in a removed word shift the next value of a multi-valued field, so cross-value phrase queries over- or under-match; token automata and downstream shingles lose the hole too. Opt-in, deterministic, any index size.

Mechanism, terms and numbers816 words

A StopFilter that removes a value's last word records the gap in end(): abc the gives the token abc and a final position increment of 1, so the next value of the same field starts one position later. Put a ConditionalTokenFilter after it (ProtectedTermFilter, or a CustomAnalyzer when()/whenTerm() branch) and that 1 becomes 0 whenever the last token went through the wrapped filters, even when they never touch positions (LowerCaseFilter, or in -> in). The cause: end() keeps the wrapped chain's end state, and that chain ends on the internal OneTimeWrapper, whose end() imitates a tokenizer, resets the increment to 0 and restores only the final offset. In the middle of the stream the same class adds the wrapped filters' end increment instead. With the default gap of 0, the multi-valued field ['abc the', 'def'] indexes def at position 1 instead of 2 and the phrase "abc def" matches (1 hit instead of 0); TokenStreamToAutomaton and a downstream ShingleFilter lose the trailing hole too. It fails on all ten versions run, from 7.4.0 (2018, the class's first release) to 10.5.2 and main, and the file's history shows no release in between with a different end-of-stream path. Handing the input's final increment to the wrapped filters (a few lines in the class) fixes it; the recommended fix also covers a related end-of-stream case (a removed stacked last token adds a position), and the analysis module's tests and TestRandomChains pass with it.

Terms

#
  • Trailing hole: StopFilter on abc the emits abc and, in end(), a final position increment of 1 for the removed the (FilteringTokenFilter.java:72-75; TokenStream.java:152-154).
  • Conditional filter: ConditionalTokenFilter sends each token through some wrapped filters only if shouldFilter() is true. ProtectedTermFilter does that for every token that is not in its protected set (ProtectedTermFilter.java:51-54); CustomAnalyzer's when() and whenTerm() build one.
  • Who reads the final increment: IndexingChain adds it to the field position before the next value of the same field (IndexingChain.java:2105-2109, then the gap at :2122; the default gap is 0, Analyzer.java:296-311). TokenStreamToAutomaton turns it into trailing HOLE arcs (TokenStreamToAutomaton.java:212-239), ShingleFilter into trailing filler shingles (:379-382).

The bug

#
  1. The wrapped filters are built on an internal stream, OneTimeWrapper, over the same attributes as the input (ConditionalTokenFilter.java:119).
  2. OneTimeWrapper.end() "imitate[s] Tokenizer.end()": it calls endAttributes(), which sets the position increment to 0 (PackedTokenAttributeImpl.java:183-186, the default implementation), and puts back only the final offset (:84-95).
  3. ConditionalTokenFilter.end() first captures the input's end state (increment 1), then, if the last token was filtered, calls delegate.end() and keeps that state (:139-151). The 1 is overwritten with 0, not added.
  4. In the middle of the stream, endDelegating() adds the wrapped filters' end increment to the next token's own increment (:213-230, the addition at :223). So holes in the middle survive, and so does a trailing hole the wrapped filters make themselves; the trailing hole of the input is lost, and only when the last token was filtered.
  5. Related, the other way round. A stacked token (increment 0) that goes to the wrapped filters is handed to them with an increment of 1 (:56-60); mid-stream the class takes that 1 back (:188-192, :224-227), at the end of the stream it does not. So when the wrapped filters remove a stacked last token, a StopFilter among them reports one position too many: tokens x/1, a/0, a condition only for a around StopFilter({"a"}) give a final increment of 1 instead of 0; also with public API only (SynonymGraphFilter x -> a keeping the original, then ProtectedTermFilter({a}, StopFilter({"x"}))). Found by the cross-model fact check of this doc and executed on main; the recommended fix covers it.

Exposure and likelihood413 words
  • Who is exposed. Applications that put a ConditionalTokenFilter behind a filter that leaves a trailing hole (typically StopFilter): ProtectedTermFilter / ProtectedTermFilterFactory (SPI name protectedTerm), CustomAnalyzer when() / whenTerm() branches, and ConditionalTokenFilterFactory subclasses. No stock Lucene analyzer uses the class, so it is opt-in.
  • What it takes. A value that ends in a removed token right after a token that went through the wrapped filters; for ProtectedTermFilter, any value ending in a stop word whose previous word is not protected.
  • What changes. The next value of a multi-valued field starts one position early per lost hole. With the default gap 0, a cross-value phrase query over-matches ("abc def": 1 hit instead of 0) or misses (the phrase built for abc the def, f:"abc ? def", no longer matches the values abc the | def); both directions executed with PhraseQuery. Span and interval queries read the same positions, so they can do the same (by code reading; not run).
  • Token automata and shingles. TokenStreamToAutomaton with its default settings and a ShingleFilter inside or after the condition lose the trailing hole, also on a single value (so a shingle field's terms change). What a suggester sees depends on its settings: AnalyzingSuggester turns on finalOffsetGapAsHole (AnalyzingSuggester.java:317-321), which can hide a single lost hole such as abc the's. No suggester was run end to end.
  • What does not change. For a chain where nothing inside or after the condition reads the final increment (LowerCaseFilter, in -> in): terms, offsets and positions inside a value (executed), and, by code reading, a single-valued field's index content, since the final increment only moves where a next value starts. Also: the queries QueryBuilder and Intervals.analyzedText build, MemoryIndex, and CheckIndex (clean). With a gap of 100, as common search servers configure, a cross-value phrase result changes only at slop 100 for one lost hole and 100-101 for two (executed over slops 0-250).
  • Not assessed end to end. Other readers of the final increment, such as FreeTextSuggester.lookup() and highlighters that re-analyse multi-valued fields.
  • Scale and versions. Deterministic, any index size, no error. Fails on every version run (ten, from 7.4.0 to 10.5.2, and main); by the file's history every release in between is affected too.
  • How likely. Rare: the wrong number is common, but it shows only with a small gap and a cross-value positional query, or a shingle or suggester consumer; nobody has reported it since 2018.

Why it is a bug, not intended

#
  • TokenStream#end names stop-filter holes as what the final increment carries; components "must put accurate values" at the end of the field.
  • A condition around a do-nothing filter, or a ProtectedTermFilter protecting nothing, turns 1 into 0; with the last word protected it stays 1.
  • Mid-stream the class adds the wrapped filters' end increment; only this branch drops it.
The full argument335 words
  • The contract. TokenStream#end: "any skipped positions (such as those removed by a stopfilter) can be applied to the position increment" (TokenStream.java:152-154). The core analysis package docs, "End of Input Cleanup": components "must put accurate values into the token attributes to reflect the situation at the end of the field" (package-info.java:276-281). LUCENE-3849 made end() carry the increment "so we can handle trailing holes" (lucene/CHANGES.txt:13337-13340).
  • The class's own promise. "If it returns false, then the wrapped filter(s) will be skipped" (ConditionalTokenFilter.java:31-33); CustomAnalyzer.when(): the conditional filters "will only be used if the current token matches the condition" (CustomAnalyzer.java:463-465). So a condition around in -> in should change nothing, and ProtectedTermFilter with nothing protected should equal its wrapped filter. Only the final increment differs (1 vs 0).
  • It flips with the last token. The same chain gives 1 when the last token is protected and 0 when it is not, although LowerCaseFilter never touches positions.
  • The class adds mid-stream (endDelegating(), :223); the end of the stream has no such addition.
  • Stated intent, kept mid-stream only. The LUCENE-8360 report (#9407, 2018) says the bug was found through this class, "which calls end() on its delegate when it reaches a token that shouldn't have the delegate applied to it, so that things like position increments and position length are preserved". That is the mid-stream path (endDelegating()), which keeps the promise by adding; the end of the stream, where this bug is, does not. LUCENE-8376/8371 (7.5.0 Bug Fixes) already treated wrong end() propagation in this class as a bug, and fixed FixedShingleFilter, which "did not set position increment in end()" (lucene/CHANGES.txt:7198-7200).
  • Nothing pins the current value. No upstream test asserts a final increment on any conditional path; testEndPropagation asserts final offsets only (18 and 20, TestConditionalTokenFilter.java:174-197). The generic check that would have caught it (LUCENE-8361, #9408) was never committed. With fix B the 44 tests of the four closest suites pass.
The devil's-advocate check227 words

The checkers built the strongest case for "intended": (a) TokenStream#end says skipped positions "can" be applied, not "must"; (b) OneTimeWrapper imitates Tokenizer.end() on purpose, and the package docs say "The base method TokenStream#end() sets PositionIncrement to 0, which is required" (package-info.java:283-284); (c) the wrapped chain's end state wins on purpose when the last token was filtered, and testEndPropagation pins that (final offset 18 instead of 20); (d) nobody has reported it since 7.4.0, although TestRandomChains wraps random filters in conditions.

Why it fails: (a) the same package docs require accurate values at the end of the field, and the class javadoc promises that the wrapped filters are skipped or applied, not that the stream's end changes. (b) The "0, which is required" sentence is the base method's starting value; each filter then adds its own, as FilteringTokenFilter.end() does. A tokenizer has nothing upstream; OneTimeWrapper does, and it passes the input's final offset on but not its increment. (c) In testEndPropagation the wrapped filter saw the input's real final offset and changed it; it never sees the input's increment, so "the wrapped chain wins" becomes "the input's hole is erased". (d) Nothing checks the final increment on these paths. The adjudication names (a) as the main filing risk: lead with the identity and nothing-protected equivalences and the additive endDelegating(). Every checker rejected the works-as-designed case.

Suggested fix

#

Recommended B+. Fix B, plus taking back the extra position of a removed stacked last token

Let the wrapped filters see the input's real end: once the input is exhausted, OneTimeWrapper.end() keeps the input's final position increment instead of 0, and end() no longer re-captures endState. Fix B+ also takes back the extra position of a removed stacked last token. The new tests, all analysis-module tests, TestRandomChains and check pass.

#

Bug record

LFV-542, snapshot of 2026-10-30

Registry title
ConditionalTokenFilter (ProtectedTermFilter, CustomAnalyzer when()/whenTerm()) reports a final position increment of 0 when the last token went through the wrapped filters, so a trailing hole from upstream (such as a removed trailing stop word) is lost and the next value of a multi-valued field starts one position too early (since 7.4.0)
Area
analysis / common miscellaneous (ConditionalTokenFilter#end and OneTimeWrapper#end: final position increment on the delegate branch)
Priority
Low, rank 425: ConditionalTokenFilter loses a trailing hole the same way as LFV-354 and LFV-532 in a less used filter.
Impact class
silent wrong results
Impact note
Applications that put a ConditionalTokenFilter (ProtectedTermFilter or its factory, a CustomAnalyzer when()/whenTerm() branch, or a downstream wrapper built on the class) behind a filter that leaves a trailing hole (typically StopFilter) are hit whenever a value ends in a removed word right after a token that went through the wrapped filters (for ProtectedTermFilter, any token that is not protected): end() reports 0 instead of the hole, so in a multi-valued field the next value starts one position early per lost hole and phrase, span and interval queries across the two values over-match or miss (executed with Lucene's default gap 0; with a gap of 100 only slop of 100 or more is affected), and TokenStreamToAutomaton loses the trailing hole (executed at the automaton level; a downstream ShingleFilter by code reading); positions inside one value, single-valued fields, the query side and the index structure are unaffected (CheckIndex clean); deterministic, ordinary scale, -ea and -da, every release from 7.4.0 to 10.5.2 and main.
Summary
You analyse 'abc the' with WhitespaceTokenizer, a StopFilter that removes 'the', and a ProtectedTermFilter that wraps a LowerCaseFilter (or the CustomAnalyzer equivalent whenTerm(...).addTokenFilter("lowercase").endwhen()), and expect end() to report the removed stop word as a final position increment of 1, as the same chain does without the condition and as the class itself does when the last token is protected ('x the' gives 1). Instead it reports 0 whenever the last token went through the wrapped filter, although LowerCaseFilter never touches positions: end() keeps the wrapped chain's end state, and the internal wrapper that feeds that chain resets the increment to 0. In a multi-valued field ['abc the', 'def'] with the default gap 0, 'def' is then indexed at position 1 instead of 2, so the PhraseQuery "abc def" matches the document (1 hit) where the plain chain gives 0 (executed).
