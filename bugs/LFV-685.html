IrishLowerCaseFilter leaves capital letters outside the BMP unchanged, so IrishAnalyzer misses their lower-case form

IrishAnalyzer's lower-case filter maps one 16-bit Java char at a time, so the 282 capitals stored as two chars (Adlam, Osage, Deseret and five more scripts) stay upper-case. A document with Adlam U+1E900 is not found by its lower-case form U+1E922: 0 hits instead of 1, since 3.6.0.

The bug in 30 seconds

#

IrishLowerCaseFilter lower-cases with Character.toLowerCase(chArray[i]), one 16-bit char at a time. A letter outside the BMP is two chars, a surrogate pair; each half alone has no case and comes back unchanged, so the capital letter survives. The loop already advances by code point, like GreekLowerCaseFilter; only the read is per char.

  1. You index the Irish sentence "Tá X anseo" ("X is here") with the default IrishAnalyzer, where X is the Adlam text U+1E900 U+1E923, a capital and a small letter. Each letter is stored as two Java chars, a surrogate pair.
  2. You search for X in lower case, U+1E922 U+1E923, through the same analyzer. You expect 1 hit: the analyzer lower-cases, and LowerCaseFilter maps U+1E900 to U+1E922.
  3. You get 0 hits. The filter passes each char alone to Character.toLowerCase; half of a pair has no case, so the capital is written back unchanged and the indexed term is still U+1E900 U+1E923.
  4. Only the 282 capitals outside the BMP are hit: AB + Osage U+104B0 + C becomes ab U+104B0 c. Exact-case searches still match, nothing throws, and such an index passes CheckIndex.

Who is affected

#

Fields analysed with the stock IrishAnalyzer, or with IrishLowerCaseFilter or the irishLowercase factory in a chain, at index and query time. It needs a capital from one of eight scripts outside the BMP, which Irish text never has, so only mixed-script content such as a quoted Adlam or Osage name is hit; there it happens every time.

Mechanism, terms and numbers558 words

The javadoc of IrishLowerCaseFilter says it "Normalises token text to lower case"; it is the only lower-casing step of IrishAnalyzer, for indexing and in normalize. Its loop passes one UTF-16 char at a time to Character.toLowerCase (IrishLowerCaseFilter.java:55). Letters outside the Basic Multilingual Plane (BMP) are stored as two chars, a surrogate pair, and each half alone has no case, so the 282 such capitals (Adlam, Deseret, Garay, Medefaidrin, Old Hungarian, Osage, Vithkuqi, Warang Citi) stay upper-case while BMP letters in the same token are lower-cased. A document indexed with IrishAnalyzer that contains the Adlam text U+1E900 U+1E923 is found by that exact spelling but not by its lower-case form U+1E922 U+1E923 (0 hits instead of 1). Nothing throws, and an index built from such text passes CheckIndex. Irish text itself has no such letters, so only mixed-script content in an Irish field is affected. The code has been there since the class was added in 3.6.0 (2012); reading the code point instead of the char fixes it.

Terms

#
  • UTF-16 char: Java stores text as 16-bit char values. Most letters, including every Irish one, fit in one char: they are in the Basic Multilingual Plane (BMP).
  • Supplementary character: a code point above U+FFFF, stored as two chars, a surrogate pair (a high and a low surrogate). The Adlam capital alif U+1E900 is the pair U+D83A U+DD00. A surrogate alone is not a letter and has no case.
  • Code point lower-casing: Character.toLowerCase(int) maps a whole code point (U+1E900 to U+1E922). The char overload cannot: the JDK documents that it "cannot handle supplementary characters".

The bug

#
  1. IrishLowerCaseFilter.incrementToken first handles the Irish prefixes (n-eclipsis and t-prothesis: nAthair becomes n-athair), then lower-cases the rest of the term: i += Character.toChars(Character.toLowerCase(chArray[i]), chArray, i); (IrishLowerCaseFilter.java:54-56 on main).
  2. chArray[i] is one char. For U+D83A, Character.toLowerCase returns U+D83A; toChars writes it back and returns 1; the low half U+DD00 goes the same way. The capital letter is unchanged.
  3. The loop is otherwise written for code points: it advances by the number of chars toChars wrote, as GreekLowerCaseFilter does (GreekLowerCaseFilter.java:46, which reads Character.codePointAt(chArray, i, chLen)). LowerCaseFilter lower-cases each code point through CharacterUtils.toLowerCase (CharacterUtils.java:47-63).
  4. IrishAnalyzer runs StandardTokenizer, which keeps words of every script, and this filter is its only lower-casing step (IrishAnalyzer.java:126-135); IrishAnalyzer.normalize, which the classic query parser calls for range, wildcard, regexp, prefix and fuzzy terms (QueryParserBase.java:550-729, read; not run end to end), runs the same filter (:138-142).

Exposure and likelihood295 words
  • Who is exposed. The stock IrishAnalyzer with any constructor (indexing and normalize), any chain with IrishLowerCaseFilter, and the irishLowercase factory (IrishLowerCaseFilterFactory.java:40; its normalize is the same filter, :60-64).
  • What it takes. An upper-case letter of Adlam (a living script for Fulani), Osage, Deseret, Old Hungarian, Warang Citi, Medefaidrin, Vithkuqi or Garay in an Irish-analysed field. Irish orthography has none, so it takes mixed-script content: a quoted name or word, or a historic-script passage.
  • What changes for the user. The capitalised and the lower-case spellings become two different terms, so a case-insensitive search misses in both directions (0 hits instead of 1 in the repro). In the intended-behaviour check's probe, "Tá X agus Y anseo" analysed to [tá, U+1E900 U+1E923, U+104B0, anseo] with capital Adlam and Osage words and [tá, U+1E922 U+1E923, U+104D8, anseo] with lower-case ones. Exact-case matches still work.
  • What does not happen. No exception, no change in term length, valid UTF-16 terms and no index damage: an index built by the stock IrishAnalyzer from such text passes CheckIndex in two segments and after forceMerge(1), and every term decodes as strict UTF-8 (assertions on and off). BMP letters in the same token are lower-cased.
  • Scale. Deterministic, with assertions on or off, at any index size: every occurrence of such a capital is indexed (and queried) unchanged.
  • JDK dependence. The affected set follows the JDK's Unicode tables: 282 code points with JDK 25. Deseret letters exist in every JDK Lucene supports; scripts added in later Unicode versions (Osage and Adlam in 9.0, Garay in 16.0) need a newer JDK. Only JDK 25 was run.
  • How likely. Rare: no public report of it was found (searches of 2026-10-27 and 2026-10-28), and the trigger needs mixed-script text in an Irish field.

Why it is a bug, not intended

#
  • The javadoc says "Normalises token text to lower case", with no BMP limit; LowerCaseFilter lower-cases these letters.
  • Lucene made LowerCaseFilter handle supplementary characters in 3.1 (LUCENE-2069), before this class was added in 3.6.0.
  • The loop already advances by code point; only the read is per char. TruncateTokenFilter's same defect was fixed as a bug (#15899).
The full argument278 words
  • Contract. "Normalises token text to lower case, handling t-prothesis and n-eclipsis (i.e., that 'nAthair' should become 'n-athair')" (IrishLowerCaseFilter.java:24-27, word for word as in 3.6.0). No script or BMP restriction; LowerCaseFilter's javadoc is nearly the same ("Normalizes token text to lower case.", LowerCaseFilter.java:22) and it lower-cases these letters.
  • Policy before the class existed. lucene/CHANGES.txt:17927-17928 (3.1.0): "LUCENE-2069: Added Unicode 4 support to LowerCaseFilter. Due to the switch to Java 5, supplementary characters are now lowercased correctly." TurkishLowerCaseFilter (LUCENE-2102, 2009) and GreekLowerCaseFilter (LUCENE-2463, 2010) map code points. In 3.6.0, the release that added this filter, LowerCaseFilter already mapped by code point: the 3.6.0 jar lower-cases U+10400, U+104B0 and U+1E900 (executed on JDK 25). Of these, only Deseret U+10400 (Unicode 3.1) was in the JDKs of 2012; Osage and Adlam entered Unicode in 9.0 (2016).
  • Same defect class treated as a bug. lucene/CHANGES.txt:1198-1200 (10.5.0): "GITHUB#15899, GITHUB#15900: Improve TruncateTokenFilter to truncate on codepoints not chars and no longer produce half surrogates". On #15899 uschindler wrote "We modified all other similar filters in the past (like ngrams), they all work correctly". That is precedent for treating char-wise handling as a bug, not proof of a complete audit: CapitalizationFilter (LFV-533) is still char-wise too.
  • Nothing presents it as a choice. The class was new in 3.6.0 with no legacy switch; the upstream tests assert expected output only for BMP input (TestIrishAnalyzer.testRandomStrings feeds random text but checks only token-stream consistency, not case); the LUCENE-3883 thread (#4956, 25 comments) never mentions supplementary characters; the loop is written in the code-point idiom (i += Character.toChars(...)) but reads a char, and the JDK documents that the char overload "cannot handle supplementary characters".
The devil's-advocate check234 words

The strongest case for "intended" (the intended-behaviour check and the cross-model reviewer): the constructor says it "normalises Irish token text" (IrishLowerCaseFilter.java:31), Irish is written in Latin script with no supplementary letters, so Adlam or Osage text is out of scope; and the factory says "this will 'mostly work', except for special cases, just like most other filters" (IrishLowerCaseFilterFactory.java:60).

Why it fails: the class javadoc promises lower case without restriction; IrishAnalyzer tokenises every script and has no other lower-casing step; the filter does lower-case non-Irish BMP scripts (Greek, Cyrillic, Armenian, executed by the intended-behaviour check), so the only gap is the supplementary planes, which comes from the char API, not from a choice of domain; TurkishLowerCaseFilter uses the same wording ("Normalizes Turkish token text to lower case", TurkishLowerCaseFilter.java:25) and maps code points; and the factory comment came with 44695f0f3f5 ("LUCENE-3883: add multitermaware to the irish case filter") and is about multi-term normalisation, not supplementary characters. Every verifier rejected the intended-behaviour argument, and the cross-model reviewer rated it weak twice. A later cross-model fact check of this doc rated it moderate: domain scope, BMP-only tests, the reindex cost and the factory comment give it some weight, although no evidence shows that the BMP limit was considered and chosen. What survives is the narrow reach and the reindex cost: reasons for low priority and a CHANGES note, not for keeping the behaviour.

Suggested fix

#

Recommended A: read the code point, not the char (one statement)

Read the code point instead of the char: Character.toLowerCase(Character.codePointAt(chArray, i, chLen)) at IrishLowerCaseFilter.java:55. The repro then passes, assertions on and off, and so does the whole analysis-common test task (1,913 tests). Only the 282 affected capitals change, so a CHANGES note should mention reindexing.

A: read the code point, not the char (one statement) (validated by the checks) (recommended)

#

The finder's one-line fix, wrapped by google-java-format. The loop already advances by the number of chars written, so nothing else changes.

Trade-offs

  • Changes output only for the 282 supplementary capitals: every BMP code point already matched, and no lower-case mapping crosses the BMP boundary, so the term length never changes.
  • Indexed terms change for text with these letters: indexes built with IrishAnalyzer need reindexing for exact consistency. For TruncateTokenFilter the project added factory parameters for the old behaviour (#15900); an option seems unnecessary here, but that is the maintainers' call.

Downstream note

#

Search servers built on Lucene that configure an Irish field type with this filter, as the factory's javadoc example text_ga does, inherit the behaviour and the same missed case-insensitive matches.

How it was found

#

Semi-formal. A bounded-exhaustive comparison checked the stock Greek, Irish and Turkish lower-case filters against a reference written from their javadoc (lower case per code point, as LowerCaseFilter) on every code point alone, 1,112,064 per filter. Irish differed on exactly 282, all capitals outside the BMP; a public-API JUnit then confirmed it end to end.

The method in full155 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier). The finder wrote a reference for each language lower-case filter from its javadoc and listed mappings: lower case means Character.toLowerCase(int) per code point, as LowerCaseFilter does, plus each filter's documented special rules. It compared the stock Greek, Irish and Turkish filters with the reference:

  • on every code point 0..0x10FFFF alone (1,112,064 checks per filter): Greek 0 and Turkish 0 mismatches, Irish 282, all supplementary upper-case letters;
  • on 12 Latin, Greek and combining blocks in alone, initial, medial, final, after-n, after-t and after-I positions (15,984 checks per filter): Irish 0 mismatches, so the n-eclipsis and t-prothesis rules and every BMP letter behave as documented.

A public-API JUnit on the stock main jar then showed the effect through the filter and through an IrishAnalyzer index and search (found 2026-10-27). IrishLowerCaseFilter was one of the rule-table classes in the hunt unit's scope; the bug came from its every-code-point sweep.

LFV-685, snapshot of 2026-10-29

Registry title
IrishLowerCaseFilter lower-cases one UTF-16 unit at a time, so IrishAnalyzer leaves upper-case letters outside the BMP (Adlam, Osage, Deseret and others) unchanged
Area
analysis-common / ga (IrishLowerCaseFilter and IrishAnalyzer case mapping)
Priority
Low, rank 438: IrishAnalyzer leaves supplementary-plane capitals unlowered, which only rare mixed-script text in an Irish field hits, so it joins the low surrogate-handling analysis rows after LFV-545.
Impact class
silent wrong results
Impact note
Hits applications that analyse a field with the stock IrishAnalyzer (or put IrishLowerCaseFilter or its 'irishLowercase' factory in a chain) when the field holds upper-case letters of one of the eight cased scripts encoded outside the BMP (Adlam, Deseret, Garay, Medefaidrin, Old Hungarian, Osage, Vithkuqi, Warang Citi; 282 code points in the JDK 25 tables): those letters stay upper-case at index time and at query time (IrishAnalyzer.normalize too), deterministically with -ea and -da, at any scale and on every release since 3.6.0, so a capitalised word is not found by its lower-case form; BMP letters in the same token are lower-cased, nothing throws, the index is not damaged, and Irish text itself has no such letters, so only mixed-script content in an Irish field is affected.
Summary
You index text with IrishAnalyzer (or put IrishLowerCaseFilter in a chain), whose filter is documented to 'normalise token text to lower case', and expect a capitalised word to match its lower-case form, as it does with LowerCaseFilter. For letters outside the BMP it does not: the Adlam capital U+1E900 stays U+1E900 instead of becoming U+1E922 (the Deseret capital U+10400 likewise stays, also after n-eclipsis), so a document holding the Adlam word U+1E900 U+1E923 is not found by U+1E922 U+1E923 (0 hits instead of 1). The loop at IrishLowerCaseFilter.java:55 passes one UTF-16 char to Character.toLowerCase, which returns a surrogate unit unchanged; BMP letters in the same token are lower-cased and nothing is thrown.
