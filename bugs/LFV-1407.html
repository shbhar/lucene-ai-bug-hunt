forceMerge(n) can return normally although its merge failed in mergeInit

When the merge that forceMerge(1) started fails early, in mergeInit (for example a full disk while it writes doc-values updates made during the force merge), forceMerge can return normally instead of throwing. A moment later the writer closes itself and drops its uncommitted changes.

The finding in 30 seconds

#

A failure in the first step of a merge is reported in the wrong order: the merge is marked finished, which wakes the waiting forceMerge, before the failure is recorded. A forceMerge that looks in that gap sees a clean finish.

Background: how forceMerge waits for its merge

#
  1. forceMerge(1) flushes, registers the merges it needs and hands them to the merge scheduler. With the default ConcurrentMergeScheduler each merge runs on its own thread.
  2. forceMerge then waits on the writer. Each time it wakes it checks, in this order: did the writer hit a tragic error (throw), did a forced merge record a failure (throw), is a forced merge still pending or running (wait again)? If none holds, it returns.
  3. A merge thread runs IndexWriter.merge: mergeInit (set-up, which writes pending doc-values updates of the merging segments), then mergeMiddle (the merge itself). On failure, merge() records it, calls mergeFinish (wake the waiters, remove the merge from the running list) and only then closes the writer.

The finding, step by step

#
  1. Index 2 documents in 2 committed segments, with a numeric doc-values field, and call forceMerge(1) with the default ConcurrentMergeScheduler. It registers 1 merge and waits for it.
  2. Before the merge starts, another write adds a document, sets document 0's doc value to 42 and flushes. The merge must write that update first, in mergeInit, and the disk is full there.
  3. You expect forceMerge(1) to throw, as it does when the same disk-full hits one step later, in mergeMiddle.
  4. Instead mergeInit's error path first marks the merge finished, which wakes forceMerge and takes the merge off the running list; the failure is recorded only after that. forceMerge finds no error and no running merge, and returns normally.
  5. A moment later the writer rolls back on the failure and closes: the update and the added document are gone and the index keeps only its 2 committed documents; a close() called after that returns normally. A separate hold-free test of the same scenario returned normally in 63 of 200 runs.

Who is affected

#

Applications that call a blocking forceMerge(n) with the default ConcurrentMergeScheduler and update doc values (or soft deletes) while it runs, when the merge then hits an I/O error such as a full disk in mergeInit. The caller is told the merge succeeded while the writer rolls back its uncommitted changes. The last commit stays intact.

Mechanism, terms and numbers512 words

IndexWriter.forceMerge(n) registers a merge and waits until no forced merge is pending or running, throwing if a forced merge recorded a failure or the writer hit a tragic error. When the merge fails with an exception from _mergeInit (the set-up step inside IndexWriter.mergeInit's try), the catch there calls mergeFinish(merge) before it rethrows: mergeFinish wakes every waiter and removes the merge from runningMerges. Only afterwards does IndexWriter.merge record the failure (handleMergeException) and close the writer (tragicEvent). A forceMerge that wakes in that gap sees nothing to report and returns normally; the writer then rolls back everything since the last commit, and a close() called after that is a no-op that also returns normally (a close() called at once usually throws the tragedy). The real trigger is an I/O error, such as a full disk, while the merge writes doc-values or soft-delete updates that another thread made during the force merge, under the default ConcurrentMergeScheduler; a merge policy whose OneMerge.mergeInit throws is the other. Since 4.1.0, when IndexWriter.merge became the only caller of mergeInit, the early mergeFinish repeats what merge()'s own finally does.

Exposure and likelihood348 words
  • Who is hit. A blocking forceMerge(n) under the default ConcurrentMergeScheduler whose own merge fails with an exception from _mergeInit (the set-up step inside mergeInit's try). The real I/O there is writing doc-values or soft-delete updates that were made and flushed after forceMerge's own flush (IndexWriter.java:5304-5311); forceMerge's flush writes the earlier ones. A merge policy whose OneMerge.mergeInit throws (MergePolicy.java:268-272, public, throws IOException) is the other way in.
  • Defaults. The trigger needs no opt-in setting and no scale: 2 one-document segments suffice, assertions on or off. The test's scheduler subclass, InfoStream hold and flushNextBuffer call only order the threads and stand in for another indexing thread.
  • What goes wrong. forceMerge returns normally while its merge failed and the writer is about to roll back everything since the last commit. Once the writer has closed itself, a close() returns normally and the next modifying call (commit(), addDocument) throws AlreadyClosedException. A close() called at once usually throws instead: IllegalStateException "this writer hit an unrecoverable error", caused by the disk full, in 399 of 400 held runs; of 115 hold-free false successes it threw in 109, returned normally with the changes lost in 3 and returned normally with everything committed in 3. So most callers that keep using the writer do find out, and getTragicException() holds the cause.
  • How likely. Rare. It needs the early failure, concurrent updates and a lost race: with its hold disabled, this page's test returned normally in 5 of 200 runs (default test JVM) and 43 of 200 (-XX:ActiveProcessorCount=3), 0 of 200 with fix A; a separate hold-free test returned normally in 63 of 200 (0 of 200 with either fix). Small synthetic tests, not field rates. No public report found since 4.1.0.
  • Not affected. SerialMergeScheduler, forceMerge(n, false), failures in mergeMiddle, the last commit on disk.
  • Sibling. LFV-590 has the same symptom for a merge that forceMerge adopts (already pending or running at the call), at different lines with an independent fix; both of its fixes leave this test failing.

Why it looks unintended

#
  • The forceMerge javadoc names disk full and declares @throws IOException; its wait loop exists to forward forced-merge failures to the caller.
  • The same failure one step later, in mergeMiddle, is reported, and so is this one under SerialMergeScheduler.
  • LUCENE-1376 (#2450, 2008) fixed an optimize() that failed to forward a background merge failure as a bug.
The full argument158 words
  • Contract. "If an Exception is hit, for example due to disk full, the index will not be corrupted and no documents will be lost" and @throws IOException (IndexWriter.java:2213-2225); "Forward any exceptions in background merge threads to the current thread" (:2293-2294); ensureOpen() "so the calling thread will know merging did not complete" (:2314-2318).
  • History. LUCENE-1376 (#2450, "sometimes if a BG merge hits an exception, optimize() will fail to forward the exception") and LUCENE-1397 (#2471, which moved the recording into merge()'s catch, before its finally calls mergeFinish) both treated a force merge that hides its merge's failure as a bug, in 2008.
  • Tests. No test asserts the false success: TestIndexWriterExceptions.testForceMergeExceptions tolerates a normal return only because random I/O failures may miss, testExceptionOnMergeInit (LUCENE-1210) checks only that the writer does not hang, and testMergeExceptionIsTragic checks only the tragedy and the close. No javadoc or MIGRATE entry says a mergeInit failure may go unreported.
The devil's-advocate check221 words

The strongest case: the early mergeFinish is a deliberate fix (LUCENE-1210, #2287, 2008, "fix deadlock case on hitting exception in mergeInit"), and OneMerge.mergeInit is an experimental hook.

Why it fails: in 2008 ConcurrentMergeScheduler called mergeInit itself, outside IndexWriter.merge, so nothing else cleaned up. LUCENE-4544 (#5610, 4.1.0) removed those calls ("removed the synchronous IW.mergeInit"); since then merge() is the only caller and calls mergeFinish in its finally too, unless a throwing mergeFinished hook skips it (see fix A; the removal was checked with git grep at the 4.0.0 and 4.1.0 tags), so on this error path the early call's only remaining effect is the early wake-up. LUCENE-1210's own regression test still passes without it. The trigger that matters is not the hook but a full disk while writing doc-values updates. An independent reviewer from another model family (OpenAI GPT-5.6) rated the argument weak in both its reviews and the bug real. Qualifications: no javadoc spells out that every background failure of a forced merge is forwarded, so "not intended" is a conclusion from the contracts and history above; and a later read-only fact check by the same reviewer family rated the intended-behaviour case moderate (no explicit rethrow promise in forceMerge or close(), later calls do fail, getTragicException() keeps the cause), so a "won't fix: commit after forceMerge" answer is plausible.

Suggested fix

#

Recommended A: drop the early mergeFinish in mergeInit's catch (recommended)

Drop the early mergeFinish(merge) from mergeInit's catch (1 line): merge() already records the failure and then calls mergeFinish in its finally. Land it with LFV-1402's nested try/finally, or use the standalone option B (record the failure first). With A the whole :lucene:core:test passes (8,923 tests).

Two fixes, both validated with the repro; the recommended one also with the whole :lucene:core:test. Neither has been reviewed upstream.

A: drop the early mergeFinish in mergeInit's catch (recommended) (validated by the checks)

#

The root cause: since 4.1.0 IndexWriter.merge is the only caller of mergeInit, and its catch records the failure (handleMergeException) before its finally calls mergeFinish (IndexWriter.java:5083-5093). Removing the early call restores that order on this path. Executed on 4.1.0 and main: with the call removed, the old probes report the failure. Land it together with LFV-1402's nested try/finally (see the trade-off), or use B.

--- a/lucene/core/src/java/org/apache/lucene/index/IndexWriter.java
+++ b/lucene/core/src/java/org/apache/lucene/index/IndexWriter.java
@@ -5263,7 +5263,8 @@
       if (infoStream.isEnabled("IW")) {
         infoStream.message("IW", "hit exception in mergeInit: " + t);
       }
-      mergeFinish(merge);
+      // merge() records the failure and then calls mergeFinish in its finally block; calling
+      // mergeFinish here first woke a waiting forceMerge before the failure was recorded
       throw t;
     }
   }

Trade-offs

  • After a mergeInit failure, merge()'s finally then calls closeMergeReaders (and so the policy's OneMerge.mergeFinished) before mergeFinish, with no nested finally. If a custom mergeFinished throws, the merge stays in runningMerges and rollback() hangs: LFV-1402's hazard, now reachable on this path too (by reading, not executed). Land A together with LFV-1402's nested try/finally, or use B.
  • The mergeFinish comment about being called twice after a mergeInit exception (:5380) can then be updated.

B: keep the early call, record the failure first (standalone) (validated by the checks)

#

Under the writer's lock, set the exception on the merge and add it to mergeExceptions before mergeFinish wakes the waiters. handleMergeException later sets the same exception again, and addMergeException skips the duplicate (IndexWriter.java:5818-5823).

-      mergeFinish(merge);
+      synchronized (this) {
+        // record the failure before mergeFinish wakes threads that wait for this merge
+        merge.setException(t);
+        addMergeException(merge);
+        mergeFinish(merge);
+      }

Trade-offs

Duplicates the recording logic of handleMergeException, which records a merge abort the same way (its setException and addMergeException run before its abort check, IndexWriter.java:5039-5042). In the held runs the waiter got IOException "background merge hit exception"; since the wait loop checks the tragedy first (:2286-2290), a waiter that wakes after the tragedy is published gets IllegalStateException instead. Does not change LFV-1402's exposure.

Downstream note

#

Products that report "force merge done" from forceMerge's return value can tell their users so while the writer has rolled back and closed.

How it was found

#

Model-based testing: a harness ran bounded sequences of writer calls (several forceMerge waiters, merge threads held at fixed points, one injected failure) on the real IndexWriter and checked each outcome against a model. "forceMerge returned normally although its merge failed" tripped only with the failure in mergeInit. A deterministic JUnit test followed.

The method in full85 words

The oracle tripped in 40 of 1,440 runs over four configurations on main, all with the injected failure in mergeInit and two or more forceMerge calls in flight; the same calls with the failure in mergeMiddle gave 0 of 10. Replays with both LFV-590 fixes still tripped, so it was a different defect. A direct probe then showed a single forceMerge(1) returning normally (1 of 20 runs), reading mergeInit gave the window, and the window was turned into the one-method test with a deterministic hold.

History

#

Introduced in 4.1.0 (released January 2013) by LUCENE-4544 (6b8ff34021e / 89cbd54e086, 2012), which made IndexWriter.merge the only caller of mergeInit, so the older early mergeFinish (LUCENE-1210, 2008) began to wake forceMerge first. Executed for a single forced merge: 4.0.0 reports the failure; sampled releases 4.1.0 through 10.6.0 and main do not. Not fixed upstream.

Versions tested6 rows

LUCENE-4544 (#5610; branch_4x 6b8ff34021e, trunk 89cbd54e086, Michael McCandless, 2012-11-11, "fix off-by-one in max number of CMS merge threads") removed ConcurrentMergeScheduler's own calls to mergeInit ("removed the synchronous IW.mergeInit"). Up to 4.0.0 the one merge of forceMerge(1) was initialized on forceMerge's own thread, so the failure reached the caller. 4.1.0 was released in January 2013. The early mergeFinish dates from LUCENE-1210 (#2287, fa4d10baf9c, 2008, released in 2.3.2 and 2.4.0, a close() hang fix); LUCENE-1335 (#2412, 4b9a3007301, 2008; its commit message says "LUCENE-1135") moved notifyAll into mergeFinish; LUCENE-7868, LUCENE-8269 and #14668 (0a4a76f0a86, 2025) edited mergeInit and kept the call. Upstream main f794ff5a505c (2026-11-06) is unchanged at this site. The release runs used two probes that keep the test's shape but inject the failure at IndexWriter's own startMergeInit test point, as LUCENE-1210's test does; the JUnit test itself needs 8.x APIs. Releases between the sampled ones (including 5.0-5.4) were not run. For a cascaded forced merge (three segments, two merges) the probe returns normally already on 2.4.0 and 4.0.0, through a different path (the merge thread's follow-on mergeInit, whose failure nothing recorded); on 4.1.0 the cascade goes through this race and reports the failure with the early call removed (executed). So 4.1.0 is where this ordering path begins, not the first version in which a forced merge can hide a mergeInit failure; the older path is context, not part of this bug.

IndexWriter.forceMerge(n) can return normally although the merge it registered failed, when the failure happens in IndexWriter.mergeInit (for example a full disk while the merge writes pending doc-values updates): mergeInit's catch calls mergeFinish, which wakes forceMerge, before IndexWriter.merge records the failure (4.1.0 to main)

index / IndexWriter forced merge (mergeInit failure path, mergeFinish, forceMerge wait loop, tragic events)
Priority
Low, rank 297: In every release since 4.1.0, a blocking forceMerge on the default merge scheduler can return normally when its own merge fails inside mergeInit, and a close() called once the writer has closed itself also returns normally, although the tragic rollback has thrown away every change since the last commit. It is Low because it needs an I/O failure such as a full disk at the moment that merge writes doc-values or soft-delete updates another thread flushed during the force merge (or a merge-policy hook that throws), plus a timing race the waiting call must win, and the next modifying call fails loudly while the last commit stays intact.
Impact class
wrong error
Impact note
Hits applications that call a blocking forceMerge(n) with the default ConcurrentMergeScheduler when the merge it registered fails inside IndexWriter.mergeInit, which in practice means an I/O error such as a full disk while that merge writes doc-values (or soft-delete) updates that another thread made and flushed during the force merge, or a merge policy whose OneMerge.mergeInit throws; no special setting or scale is needed (SerialMergeScheduler and forceMerge(n, false) are not affected), and without test delays the waiting call must also win a short race (63 of 200 hold-free runs in a small synthetic test, not a field rate): forceMerge then returns normally instead of throwing, the tragic rollback closes the writer a moment later, and a close() called after that also returns normally (a close() called at once usually throws the tragedy: 399 of 400 held runs, 109 of 115 hold-free false successes), so 'forceMerge(1); close()' can report success while every change since the last commit is lost; once the writer has closed, the next modifying call throws AlreadyClosedException, and the last commit stays intact.
Summary
You call forceMerge(1) and the merge it starts fails early, inside IndexWriter.mergeInit, for example because the disk is full while the merge writes doc-values updates that another thread made during the force merge. You expect forceMerge to throw, as it does when the same failure happens one step later inside the merge itself. Instead it can return normally: mergeInit's error path calls mergeFinish, which wakes the waiting forceMerge before IndexWriter.merge has recorded the failure, and only afterwards does the failure close the writer and roll back its uncommitted changes.
