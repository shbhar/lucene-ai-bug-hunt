tryDeleteDocument and tryUpdateDocValue during commit() are numbered after the commit, yet land in it

If another thread calls tryDeleteDocument or tryUpdateDocValue while commit() is flushing, the call returns sequence number 8 and the commit returns 7, yet the change is in that commit, although commit() promises that higher numbers are not. rollback() keeps such a change; every release since 6.2.0 has it.

The bug in 30 seconds

#

Every IndexWriter change returns a sequence number, and commit() returns the number that splits all changes into "in this commit" and "not in it".

  1. A writer holds document a (v=1), visible in an NRT reader nrt, plus one newly buffered document. Thread 1 calls commit(); it fixes its sequence number and starts writing the buffered document's segment.
  2. Meanwhile thread 2 calls tryDeleteDocument(nrt, a), or tryUpdateDocValue(nrt, a, v=42). The call returns 8; the commit returns 7.
  3. You expect commit 7 to leave a alone: commit() promises "All sequence numbers <= this value will be reflected in the commit, and all others will not." deleteDocuments(Term) in the same moment also gets 8, and it does stay out.
  4. Instead commit 7 already has a deleted, or v=42. The try call took its number from the new delete queue the commit had just started, but wrote its change into the segment the commit was about to snapshot.
  5. No error, CheckIndex is clean in the rollback probe, and rollback() keeps the change: in a rollback variant, a soft-deleted document un-deleted this way (seqNo 9, commit 8) stays visible to searches after the rollback.

Who is affected

#

Applications that call the expert try* methods while another thread commits, and use the commit's number as an exact cut: rollback(), log replay, replication or reconciliation. Default settings otherwise. Under concurrency it is common (3,417 of 5,981 try deletes mislabelled in one stress run), but it only adds changes: in every run nothing at or below the commit was lost.

Mechanism, terms and numbers822 words

Every IndexWriter change returns a sequence number, and commit() promises that all numbers at or below its own are in the commit and all others are not. tryDeleteDocument and tryUpdateDocValue, the expert calls that change one document by its docID in an NRT reader, break that promise when they run while another thread is inside commit(): in the repro they return 8, the commit returns 7, and the change is in commit 7. The term-based deleteDocuments(Term), deleteDocuments(Query) and updateNumericDocValue(Term) in the same window also get 8 and correctly stay out. The cause is that the shared tryModifyDocument takes its number from the new delete queue that the commit's full flush has already swapped in, and applies the change straight to the pooled segment reader, which the commit then writes into its snapshot. Applications that use the commit's number as an exact cut (rollback, replay, replication) get a wrong cut; with rollback() such a change survives. It is over-inclusion only: in every run, nothing numbered at or below a commit was missing, and CheckIndex was clean where it ran. Every release since 6.2.0 (7.4.0 for tryUpdateDocValue) and main have it.

Terms

#
  • Sequence number (seqNo): every IndexWriter method that changes the index returns one. The class javadoc says it "expresses the effective order in which each change was applied", and commit() returns one "describing which changes are in the commit point and which are not" (IndexWriter.java:117-119).
  • try\* methods: tryDeleteDocument(reader, docID) and tryUpdateDocValue(reader, docID, fields) change one document by its docID in an NRT reader of this writer. They return a seqNo, or -1 when they cannot apply the change. tryDeleteDocument also returns a number when the document was already deleted. The tryUpdateDocValue javadoc says a null value can be used to un-delete a soft-deleted document.
  • Full flush: what commit() (and an NRT reopen, and flush()) does first: it fixes the commit's seqNo, starts a new delete queue whose numbers are higher, and writes the documents buffered at that moment to segments.

The mechanism (main ea57360912ed)

#
  1. The commit fixes its number and swaps the queue first. prepareCommitInternal takes fullFlushLock (IndexWriter.java:3806) and calls flushAllThreads() (:3809). Under the DocumentsWriter monitor (DocumentsWriter.java:674-682) this runs markForFullFlush (DocumentsWriterFlushControl.java:557-575): fullFlush = true, and resetDeleteQueue (DocumentsWriter.java:588-598) makes the old queue's maximum the commit's number and installs a new queue that starts above it (DocumentsWriterDeleteQueue.java:616-630).
  2. Then it flushes without holding the writer's monitor. It writes the buffered segments and, at the end of the flush, publishes them (DocumentsWriter.java:580 → IndexWriter.java:449; :3819 publishes any leftover), then applies deletes (:3825). It holds fullFlushLock throughout, and the writer's monitor only briefly to publish each segment (:2953), until it takes it for the snapshot at :3826.
  3. A try\* call runs in that gap. Both methods are synchronized on the writer (:1688, :1721) and share tryModifyDocument (:1791-1827). It applies the change directly to the pooled segment reader (:1823) and returns docWriter.getNextSequenceNumber() (:1824), which now comes from the new queue: 8, above the commit's 7. It never takes fullFlushLock and never checks whether a full flush is running, so any try\* call that returns after the queue swap and before :3826 is caught.
  4. The commit then snapshots the change. Back under the writer's monitor (:3826) it calls writeReaderPool(true) (:3827), which writes the pooled readers' pending deletes and doc-values updates, the try\* change included, and clones the segment infos into the commit point (:3850). The comment there places the clone so that partial compound changes (a delete without the add of an updateDocument) cannot "sneak into the commit point" (:3845-3849).
  5. Why the term-based calls are fine. They go through DocumentsWriter.applyDeleteOrUpdate (DocumentsWriter.java:153-165), synchronized "to make sure we don't replace the deleteQueue while applying this update / delete": number and change land in the same new queue, which this commit does not freeze.

The window runs from the queue swap to the commit's final take of the writer's monitor (:3826) and includes writing the buffered segments, so it is wide: a stress test without any hook hits it constantly.

Exposure and likelihood467 words
  • Who is hit. Applications that call tryDeleteDocument or tryUpdateDocValue while another thread runs commit() or prepareCommit(), and that act on the commit's number. LUCENE-7302 added sequence numbers so that callers "can know exactly which operations made it into the commit and which did not". Typical cuts: aborting with rollback(), documented to return to "the state ... when commit() was last called" (IndexWriter.java:2567-2571); replaying a transaction log from the commit's number; reconciling a replica or a system of record at that cut. Sequence numbers are transient and valid only within one IndexWriter instance (IndexWriter.java:119-121), so the cut matters while that writer lives. prepareCommit() shares the code path (read from the source; no executed test calls it directly).
  • What goes wrong (executed on main with assertions on and off, 10.5.2 and 9.12.3). After rollback(), a tryDeleteDocument numbered 9 above a commit numbered 8 is still applied, so a document the application believes live is gone; a tryUpdateDocValue un-delete of a soft-deleted document (9 against 8) survives, so the document is visible to searches. Before/after controls behave; CheckIndex is clean.
  • What does not go wrong. Idempotent replay from the commit's number still converges (it re-applies a change that is already there). In every run, no operation numbered at or below a commit was missing from it, and CheckIndex found no corruption where it ran. rollback() itself does what its javadoc says; what is wrong is the number that labels the change as outside the commit.
  • Default or opt-in. No explicit codec or directory override: the portable probe ran with the normal default codec and a plain NIOFSDirectory, and the JUnit with the test framework's randomized codec and directories (for example Asserting(Lucene104)). The repro only sets NoMergePolicy, which keeps the try\* javadoc's success condition (the segment "has not been merged away") true; merges (and with them the merged-away -1 path) were not exercised, while fully deleted segments that the try delete drops were (the finder's one-document repro, the independent reproduction's stress test). The opt-in is the expert try\* API. Read-only code reads (default branches, not exhaustive): Elasticsearch's engine writer fails tryDeleteDocument only when assertions are enabled (otherwise it calls through to Lucene), OpenSearch's engine writer always rejects it, and an OpenSearch sandbox plugin calls it but checks only for -1 and never uses the sequence number; no tryUpdateDocValue caller was found in Elasticsearch, OpenSearch or Solr; custom applications were not surveyed.
  • How often. Two documents suffice, and the repro failed on every run (40 of 40 try\* runs over 20 seeds). Without hooks, a stress test that commits in a loop while another thread try-deletes mislabelled 3,417 of 5,981 successful try deletes in one run and 14,698 of 20,992 over five runs; every mislabelled call overlapped its commit in wall-clock time.

Why it is a bug, not intended

#
  • commit(): "All sequence numbers <= this value will be reflected in the commit, and all others will not." The try* javadoc makes no exception for concurrent commits.
  • In the same window, term-based deletes and doc-values updates also get 8 and stay out of the commit.
  • deleteAll takes fullFlushLock for "point in time semantics"; the try* path skips that coordination.
The full argument359 words
  • The contracts. commit() (IndexWriter.java:4203-4205): "it returns the sequence number such that all indexing operations prior to this sequence will be included in the commit point, and all other operations will not"; @return (:4208-4210, repeated for prepareCommit() at :3730-3732): "All sequence numbers <= this value will be reflected in the commit, and all others will not." The class javadoc (:117-119) covers "each method that changes the index". The try\* javadoc (:1680-1681, :1710-1711) promises "a valid (> 0) sequence number". IndexWriter is "completely thread safe, meaning multiple threads can call any of its methods, concurrently" (:167-168). CHANGES.txt:8925-8927 (LUCENE-7302): methods that change the index "now return a long "sequence number" indicating the effective equivalent single-threaded execution order".
  • Upstream tests. TestIndexingSequenceNumbers checks exactly this boundary under concurrent commits, for the queue-based operations only; it never calls a try\* method. Seven test classes call try\* (TestTryDelete, TestRollingUpdates, TestIndexWriter, TestIndexWriterDelete, TestInfoStream, TestSoftDeletesRetentionMergePolicy, TestMixedDocValuesUpdates); none compares a try\* number with a commit's, and the two that run try\* alongside commits use the number only to retry on -1.
  • History and precedent. LUCENE-7302 (2016) turned tryDeleteDocument from boolean into this seqNo; the violated javadoc came three days later in the same series, before any release. Maintainers fixed full-flush seqNo inconsistencies as bugs before: LUCENE-9304 (2020, which changed this very return line while fixing getMaxCompletedSequenceNumber) and the seqNo races of #13127 and #13571, fixed by #13169 (first in 9.11.0) and #13627 (first in 9.12.0). On java-user@ in 2016 the LUCENE-7302 author wrote: "all sequence numbers <= the sequence number returned from IW.commit "made it" into the index, and all other ops did not make it."
  • The code's own guards. DocumentsWriter.applyDeleteOrUpdate (DocumentsWriter.java:153-165) is synchronized "to make sure we don't replace the deleteQueue while applying this update / delete"; deleteAll takes fullFlushLock for "point in time semantics" (IndexWriter.java:2757, :2764); prepareCommitInternal clones while it holds fullFlushLock and the monitor so that partial compound changes cannot "sneak into the commit point" (:3845-3849; a comment about operations such as updateDocument, not a general rule).
The devil's-advocate check278 words

The strongest case for "intended", built by the devil's-advocate check: try\* is a best-effort expert API; LUCENE-4521 (2012) deliberately made a successful try delete reach the next commit; LUCENE-1335 (2008) declined API promises about concurrent commit, close and addIndexes; the try\* javadoc does not link the #sequence_number anchor; and the open #7444 (2015) calls tryDeleteDocument "a trap" and proposes removing it.

Why it fails: inclusion in the commit is fine, but returning a number that says "not in this commit" for a change that is in it is not; the try\* numbers come from the same counter as every other operation, and nothing says they are weaker. LUCENE-1335 predates sequence numbers and try\, names admin methods only, and is not in today's docs; the 2016 javadoc is exactly such a promise about concurrent commits. LUCENE-7302 gave try\ its number, and its CHANGES entry covers every method that changes the index. #7444 is about rare false returns before sequence numbers existed: it may shape the fix (deprecation), not whether this is a bug. Verdicts: devil's advocate "real, high"; the cross-model works-as-designed review rated the intended argument "weak"; the adjudication "confirmed, high", for the commit/prepareCommit boundary only.

How strong the case still is: a read-only fact check by OpenAI GPT-5.6 rated it moderate overall and weak under the literal javadocs. It is strongest for tryDeleteDocument (an expert, best-effort API; LUCENE-4521 made inclusion in the next commit intentional; the index state matches the serial order "try, then commit", only the number does not) and weaker for tryUpdateDocValue, whose javadoc advertises the soft-delete un-delete. Maintainers may raise these points; the answer is the explicit @return contract and the same-window asymmetry.

Suggested fix

#

Recommended B: wait for a running full flush (take fullFlushLock before the writer's monitor)

Make the try* methods wait for a running full flush: take fullFlushLock before the writer's monitor, as commit does (+22/-5 in IndexWriter.java). The try call then gets 8 and stays out of commit 7. Validated: the repro and all 8,870 core and 315 misc tests pass. Cost: a try call can block while a flush runs.

public long tryDeleteDocument(IndexReader readerIn, int docID) throws IOException { // was synchronized
  return tryModifyDocumentOutsideFullFlush(readerIn, docID, (leafDocId, rld) -> { /* unchanged */ });
}
// tryUpdateDocValue: the same; buildDocValuesUpdate stays under synchronized (this)

private long tryModifyDocumentOutsideFullFlush(
    IndexReader readerIn, int docID, DocModifier toApply) throws IOException {
  assert Thread.holdsLock(this) == false : "fullFlushLock must be taken before the IW monitor";
  synchronized (fullFlushLock) { // same order as commit, getReader and deleteAll
    return tryModifyDocument(readerIn, docID, toApply); // still synchronized on the writer
  }
}
All options and trade-offs4 options · 756 words

Two code fixes were built and validated in a scratch worktree of ea57360912ed (removed afterwards); two more options are documented. Taking fullFlushLock inside the synchronized try* methods would invert the existing lock order, so both code fixes avoid that.

B: wait for a running full flush (take fullFlushLock before the writer's monitor) (validated by the checks) (recommended)

#

Drop synchronized from tryDeleteDocument and tryUpdateDocValue and route both through a helper that takes fullFlushLock and then calls the still-synchronized tryModifyDocument. A try call that arrives during a commit, NRT reopen or flush() waits for it to end, then gets a number above the commit's and is not in it. Patch: +22/-5 in IndexWriter.java.

public long tryDeleteDocument(IndexReader readerIn, int docID) throws IOException { // was synchronized
  return tryModifyDocumentOutsideFullFlush(readerIn, docID, (leafDocId, rld) -> { /* unchanged */ });
}
// tryUpdateDocValue: the same; buildDocValuesUpdate stays under synchronized (this)

private long tryModifyDocumentOutsideFullFlush(
    IndexReader readerIn, int docID, DocModifier toApply) throws IOException {
  assert Thread.holdsLock(this) == false : "fullFlushLock must be taken before the IW monitor";
  synchronized (fullFlushLock) { // same order as commit, getReader and deleteAll
    return tryModifyDocument(readerIn, docID, toApply); // still synchronized on the writer
  }
}

Trade-offs

  • A try call now blocks for the rest of a running full flush (writing the buffered segments). Not benchmarked.
  • A caller that calls try* while holding the writer's monitor (the class javadoc already says not to synchronize on the writer) would now risk a deadlock; the added assertion catches it under -ea (with assertions off it would deadlock against a full flush), and no in-tree test trips it. One callback passed: TestSoftDeletesRetentionMergePolicy calls tryDeleteDocument from a merged-segment warmer and is among the 18 closest suites; broader callback and full-flush interactions were not evaluated.
  • The public methods lose the synchronized modifier; they still take the monitor inside.

What the checks validated

  • The repro passes 5 of 5 with assertions on and off and 50 of 50 with tests.iters=10, through gradle and the harness: both try calls return 8 and stay out of commit 7.
  • All of :lucene:core:test: 748 classes, 8,870 tests, 322 skipped, 0 failures. All of :lucene:misc:test (includes TestIndexRearranger): 315 tests, 9 skipped, 0 failures. The 18 closest core suites also with assertions off: 359 tests, 0 failures. :lucene:core:check -x test passes.
  • A hook-free stress test (commits back to back while another thread try-deletes): 0 mislabelled in five runs, with 1 to 6,667 successful try deletes per run, the same range as stock.

A: return -1 while a full flush runs (validated by the checks)

#

Take the seqNo first, atomically with the start of a full flush (a new DocumentsWriter method, synchronized like the queue swap, returns -1 while isFullFlush()), and apply the change only if a number was given. -1 is already the documented outcome that sends callers to delete by Term or Query; the javadoc gains "or while a commit, NRT reopen or flush is flushing all buffered documents". Patch: +13 in DocumentsWriter.java, +18/-8 in IndexWriter.java.

// DocumentsWriter
synchronized long getNextSequenceNumberOutsideFullFlush() {
  if (flushControl.isFullFlush()) {
    return -1;
  }
  return deleteQueue.getNextSequenceNumber();
}
// IndexWriter#tryModifyDocument, inside synchronized (bufferedUpdatesStream)
final long seqNo = docWriter.getNextSequenceNumberOutsideFullFlush();
if (seqNo == -1) {
  return -1;
}
toApply.run(docID, rld);
return seqNo;

Trade-offs

  • Measured: in the hook-free stress test with back-to-back commits, two of five runs had 0 successful try deletes and the others 226 to 3,945. Under frequent commits or NRT reopens many calls fall back to the term path, and a caller that retries on -1, as the tryUpdateDocValue javadoc suggests, could spin for the length of a flush.
  • It also refuses during NRT reopens, which make no seqNo exclusion promise. A narrower variant (not tested) would refuse only during a commit's full flush.
  • IndexRearranger treats -1 as "should never happen"; it does not commit concurrently, so it is not hit.

What the checks validated

  • The repro passes (both try calls return -1 and change nothing) with assertions on and off and 50 of 50 iterations.
  • The 18 closest core suites (359 tests) and TestIndexRearranger pass. The full suites were not run with A.

C: document it

#

Say in the try* javadoc (or in the commit() @return) that a try* change made while a commit runs may be in that commit even though its number is higher.

Trade-offs

Cheapest, no behaviour change; leaves the rollback and cut problems to applications. Not tested.

D: deprecate the try* methods

#

The direction of the open #7444 ("remove or fix IndexWriter.tryDeleteDocument").

Trade-offs

Larger API change; maintainers may prefer to answer there. Not tested.

Downstream note

#

Why: rollback() returns to the last commit, but a try* change numbered after it survives. With the soft-delete un-delete that the tryUpdateDocValue javadoc describes, a document the application meant to keep deleted stays searchable. Only the application's own calls and commit timing trigger it, so it is out of scope of Lucene's threat model; no concrete exploit is known.

How it was found

#

TLA+ model checking (TLC) of DocumentsWriter's flush control and delete queue. The plan asked for "a commit with sequence number s contains exactly the operations numbered <= s"; the finder added tryDeleteDocument to the model, TLC found a 20-state counterexample, and a public-API test reproduced it on the real jars.

The method in full199 words

Method: TLA+ model checking (TLC), a hunt unit (2026-10-26), on main ea57360912ed.

  • The unit's plan asked for a TLA+ model of DocumentsWriterFlushControl, the per-thread writer pool, the delete queue (slices, seqNo assignment, queue swap on full flush) and the flush queue, with indexing threads, an NRT refresher and a committer, and for the invariant "an NRT reader or commit with seqNo s contains exactly the ops with seqNo <= s (the commit javadoc)". It did not name the try\* methods; its dedup list named two other try\* rows (LFV-009, LFV-010).
  • The finder's model (DWFlush.tla, about 500 lines with a file:line map) added tryDeleteDocument as an action that takes its number from the current queue under the writer's monitor only. With configuration MC_D_try (two indexers, one try delete on a published document, NRT reopen and commit), TLC found the invariant violated in a 20-state trace (112,706 states generated, 38,380 distinct).
  • The finder replayed the trace as a public-API JUnit on the stock jars (two schedules: an InfoStream message and a FilterDirectory#createOutput hook), which failed with 8 against 7. Independent checks followed (see Checks), and this doc added the minimal five-test version and the fix validation.

History

#

Introduced in 6.2.0 by LUCENE-7302 (#8356, 7ee1f422458, 2016), which made tryDeleteDocument return a sequence number with no coordination with the commit's full flush; tryUpdateDocValue (LUCENE-8297, 7.4.0) shares the code. All 89 releases 6.2.0-10.5.2 and main are affected.

It changed tryDeleteDocument from boolean to the current delete queue's next number. The javadoc it violates came in 5361d67996a (2016-05-27), same series, before any release. tryUpdateDocValue came with LUCENE-8297 (#9344, @s1monw, 48a2138e899, 2018-05-05), with the same behaviour and the shared tryModifyDocument, the fix site on main. The behaviour itself is older (on 6.0.0-6.1.0 a try delete inside the commit's flush already lands in that commit); what 6.2.0 added is the promise it breaks. Not fixed: upstream main 49483e82b357 (2026-10-26) has IndexWriter.java unchanged, and the finder's test still fails on main a9779ef3c193.

Bug record

#

LFV-471, snapshot of 2026-10-27

Registry title
tryDeleteDocument / tryUpdateDocValue running while commit() flushes returns a sequence number above the commit's, yet its change is in that commit
Area
index / IndexWriter sequence numbers (tryDeleteDocument, tryUpdateDocValue vs commit)
Priority
Medium, rank 93: A tryDeleteDocument or tryUpdateDocValue that runs during a commit gets a sequence number above the commit's while its change is in the commit; this happens easily under concurrency, but it only hurts expert try* users who use the commit's number as an exact cut (for example with rollback), and it only adds changes, never loses them, so it is narrower than its sibling LFV-014.
Impact class
silent wrong results
Impact note
Default IndexWriterConfig, codec and directory, but only applications that call the expert tryDeleteDocument or tryUpdateDocValue while another thread is in commit() or prepareCommit() and that treat the commit's sequence number as an exact cut (rollback() to discard later changes, a point-in-time, replication or reconciliation cut) are hurt; the error is over-inclusion only (a change numbered above the commit is durable in it, and no operation numbered at or below it was ever missing), idempotent replay from the commit's number still converges, nothing is corrupted (CheckIndex clean), the scale is tiny (two documents), and it is in every release from 6.2.0 (tryUpdateDocValue: 7.4.0) through 10.5.2 and main.
Summary
You call tryDeleteDocument or tryUpdateDocValue with an NRT reader while another thread is inside commit(), after the commit has fixed its sequence number and before it snapshots its segments. You expect what the commit javadoc promises ('All sequence numbers <= this value will be reflected in the commit, and all others will not'): a change whose returned number is above the commit's is not in that commit. Instead the call returns the commit's number plus one (8 against 7), yet the delete or doc-values update is already in the commit point, while deleteDocuments(Term), deleteDocuments(Query) and updateNumericDocValue(Term) in the same window get 8 too and correctly stay out.
