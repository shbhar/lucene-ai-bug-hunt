One transient read failure makes checkFooter(in, priorException) report a healthy file as corrupt

On NIOFSDirectory and other BufferedIndexInput-based inputs, one transient read failure can leave bytes the read already consumed out of a file's checksum. CodecUtil.checkFooter(in, priorException) then calls the healthy file corrupt ("checksum failed (hardware problem?)") instead of rethrowing the IOException, in every release since 8.6.0.

The finding in 30 seconds

#

The checksum wrapper adds bytes to the CRC only after a read returns (BufferedChecksumIndexInput.java:43-47), but BufferedIndexInput.readBytes has already used up its buffered bytes when the rest of the read fails (BufferedIndexInput.java:99-103, :127). Those bytes are then missing from the CRC, and checkFooter makes the mismatch the main exception (CodecUtil.java:507-509).

Checksummed reads and checkFooter, in one minute

#
  1. Every Lucene index file ends with a 16-byte footer that holds a CRC32 of all bytes before it. Directory.openChecksumInput returns a BufferedChecksumIndexInput that feeds every byte it reads into a running CRC.
  2. Readers of metadata files (segments_N, .fnm, .dvm, ...) read inside try/catch and finally call CodecUtil.checkFooter(in, priorException). It skips to the footer and compares the CRCs: a mismatch means the file is corrupt and becomes the main exception; a match rethrows the read error with the note "checksum passed".
  3. NIOFSDirectory reads through BufferedIndexInput, which keeps a 1 KiB buffer. A large readBytes first copies what is left in the buffer, then reads the rest straight from the file.

The finding, step by step

#
  1. Write a 3,029-byte file through NIOFSDirectory: a 13-byte codec header, 3,000 bytes and the 16-byte footer. Open it with openChecksumInput and read the header: the 1 KiB read buffer now holds 1,011 unread bytes.
  2. Call readBytes for 3,000 bytes. It copies the 1,011 buffered bytes, then its read of the other 1,989 bytes from the file fails once with an IOException, as on a flaky disk or network store.
  3. You expect CodecUtil.checkFooter(in, thatException) to rethrow the IOException: the file is intact, and the same failure with an empty buffer does give it back, noted "checksum passed".
  4. Instead it throws CorruptIndexException: checksum failed (hardware problem?) : expected=73689b45 actual=3fabad1f. The checksum wrapper adds bytes only after a read succeeds, so the 1,011 bytes the failed read used up never reached the CRC.

Who is affected

#

Users of BufferedIndexInput-based inputs: NIOFSDirectory (chosen explicitly, or the default on 32-bit JVMs), the misc RAFDirectory, BufferedIndexInput.wrap and subclasses over remote storage; not MMapDirectory, the 64-bit default. It takes one transient read failure inside a read that crosses the buffer end of a checksummed file. Nothing is read wrongly, but a healthy file is called corrupt.

Mechanism, terms and numbers443 words

Directory.openChecksumInput returns a BufferedChecksumIndexInput, which adds bytes to a running CRC32 only after the delegate read returns. BufferedIndexInput.readBytes, the read path of NIOFSDirectory, the misc RAFDirectory, BufferedIndexInput.wrap and third-party subclasses, first hands out the bytes left in its 1 KiB buffer and moves past them, and only then reads the rest from the file. When that second read throws a transient IOException, the file pointer already counts the handed-out bytes but the CRC never saw them. CodecUtil.checkFooter(in, priorException), the documented way to check a file after a read failed, then skips to the footer, compares a CRC that misses those bytes, and since LUCENE-7822 (8.6.0) throws the mismatch as the main CorruptIndexException: checksum failed (hardware problem?), with the real IOException only suppressed. The same failure when the buffer happens to be empty correctly gives back the IOException with "checksum passed". Nothing is read wrongly, and the default MMapDirectory is not affected; but callers are told a healthy file is corrupt.

The numbers in the repro

#

The file is 3,029 bytes: header 13 (CodecUtil.headerLength("test") = 9 + 4), payload 3,000, footer 16. After checkHeader the buffer holds bytes 0-1023 and the file pointer is 13. readBytes(3000) copies bytes 13-1023 (1,011 bytes); the other 1,989 bytes are at least the 1,024-byte buffer size, so they go to a direct readInternal, which fails. The file pointer is now 1024 and the CRC covers bytes 0-12. checkFooter(in, priorException) skips bytes 1024-3012 into the CRC (CodecUtil.java:481-491), so the CRC misses bytes 13-1023, and checkFooter(in) throws "checksum failed (hardware problem?) : expected=73689b45 actual=3fabad1f" (:433-446), which :507-509 makes the main exception. An independent reproducer's probe (22-byte header) showed getFilePointer() moving from 22 to 1024 across the failed read while getChecksum() stayed the same.

The same happens on the refill() path (:105-116) and in readShort/readInt/readLong when the value straddles the buffer end; whatever the delegate consumed before throwing is missing from the CRC.

Exposure and likelihood281 words
  • Who. Inputs built on BufferedIndexInput: NIOFSDirectory (chosen explicitly, or what FSDirectory.open returns on 32-bit JVMs, FSDirectory.java:155-161), the misc module's RAFDirectory (RAFIndexInput extends BufferedIndexInput), BufferedIndexInput.wrap and third-party subclasses, for example over remote storage. MMapDirectory, the 64-bit default, is not affected: its inputs are not BufferedIndexInputs (MemorySegmentIndexInput extends IndexInput), so this path does not arise there.
  • When. One read of a checksummed file fails transiently, inside a read that crosses the 1 KiB buffer end, and the input stays readable. 35 main-source files in core, codecs and backward-codecs read with the checkFooter(in, priorE) pattern, including SegmentInfos.readCommit (SegmentInfos.java:367-375) and the field-infos reader (Lucene94FieldInfosFormat.java:245).
  • At index level. A model-based fault-injection run opened a healthy 12-segment index on NIOFSDirectory 326 times, each time failing one different file read once (the injected FileChannel.read throws before it transfers any byte). With a refill fix for the related bug LFV-492 applied, 109 opens still reported corruption (segments_N, .fnm, .dvm); with the checksum-wrapper fix (option A) too, none. On stock main 217 did. These are counts over the enumerated failure points, not a measured failure rate.
  • Effect. The caller is told a healthy file is corrupt ("hardware problem?"), and the transient cause is only a suppressed exception. Callers or operators that go by the main exception's type or message (and then stop using the index, restore a copy or run CheckIndex) are misled. Nothing is read wrongly and the index is not changed.
  • How likely. Expected to be rare: transient read failures on healthy storage are uncommon, and the read must cross the buffer end. How often it happens in production was not measured.

Why it looks unintended

#
  • checkFooter(in, priorException) exists to check a file after a read failed, and makes corruption the main exception only "If we have evidence of corruption".
  • The same failure with nothing consumed gives "checksum passed"; with 11 bytes consumed first it gives "checksum failed".
  • #16788: "a transient I/O failure, is no evidence of corruption and must propagate as-is".
The full argument215 words
  • Contract. CodecUtil.java:452-454: "this method will add a suppressed exception indicating whether the checksum for the stream passes, fails, or cannot be computed"; its javadoc example (:456-469) catches a Throwable from reads and then calls checkFooter on the same input; the code comment (:477-480) puts corruption first only "If we have evidence of corruption". Here the file is intact.
  • Tests. TestCodecUtil.testCheckFooterValid (TestCodecUtil.java:107-129) asserts that a valid file plus a prior exception gives the prior back with "checksum passed"; its prior exceptions never come from the input, so no test covers a failed read.
  • Recent intent. #16788 (merged 2026-10-21) in SegmentInfos.java:415-416: "a transient I/O failure, is no evidence of corruption and must propagate as-is".
  • History. LUCENE-7822 (#8873, 8.6.0) made the mismatch the main exception. Adrien Grand's rationale there was that it "guarantees that we verify the checksum of the exact bytes that we just read"; the discussion never considers a CRC that misses bytes after a failed read.
  • Control pair (executed on main with assertions on and off, and on 10.6.0): the same one-shot failure at an exactly drained buffer gives the IOException with "checksum passed (a00304c0). possibly transient resource issue, or a Lucene or JVM bug"; with 11 buffered bytes consumed first it gives "checksum failed (hardware problem?)".
The devil's-advocate check217 words

"An IndexInput is in an undetermined state after any IOException." That is Uwe Schindler's open documentation proposal #16951 ("If any read or seek throws an IOException (including EOFException), then the stream is in an undetermined [state] and it is recommended to close it"). LUCENE-7822's CHANGES entry also says checkFooter "now throws a CorruptIndexException if checksums mismatch or if checksums can't be verified", and the IOException is still attached as a suppressed exception.

Why it fails. The code that reads on after the failure is Lucene's own checkFooter(in, priorException), built for exactly this. Today's javadoc names only seeking past EOF as leaving the stream in an undetermined state (IndexInput.java:68-73) and states no general rule for failed reads. Even under #16951 the honest answer is "cannot be computed", never "checksum failed" for a healthy file. The "can't be verified" case of CHANGES is the remaining < footerLength() branch (CodecUtil.java:482-488), not a CRC that silently misses bytes. Every reviewer rejected the works-as-designed case; the independent reproducer and two executed reviews by another model family (OpenAI GPT-5.6, refute and intended lenses) rated it weak. A later fact-check review by the same model family rated it moderate: the false "checksum failed" stays wrong, but a maintainer could reasonably prefer "checksum status indeterminate" or a documentation-only answer.

Suggested fix

#

Recommended B: move the delegate back to where the failed read started

Fix B: when a delegate read throws, BufferedChecksumIndexInput seeks the delegate back to where the read started, so the CRC again matches the file pointer and checkFooter re-reads those bytes; if that seek fails, getChecksum() throws ("indeterminate"). Validated: the repro passes, two neighbouring cases stay right, and 2,414 upstream store and codecs tests and :lucene:core:check -x test pass.

  private void rewind(long start, Throwable t) {
    try {
      if (main.getFilePointer() != start) {
        main.seek(start);
      }
    } catch (Throwable e) {
      digestUnknown = true; // getChecksum() then throws
      t.addSuppressed(e);
    }
  }

B: move the delegate back to where the failed read started (validated by the checks) (recommended)

#

Each multi-byte read (readBytes, readShort, readInt, readLong, readLongs) remembers main.getFilePointer(); if the delegate throws, a small rewind seeks it back before rethrowing. If the seek fails too, a flag makes getChecksum() throw, so checkFooter reports "checksum status indeterminate" (+61/-6 in BufferedChecksumIndexInput.java).

  private void rewind(long start, Throwable t) {
    try {
      if (main.getFilePointer() != start) {
        main.seek(start);
      }
    } catch (Throwable e) {
      digestUnknown = true; // getChecksum() then throws
      t.addSuppressed(e);
    }
  }

Trade-offs

Keeps the "checksum passed" note and keeps real corruption a CorruptIndexException. One extra getFilePointer() per multi-byte read (no benchmark run). After a failed read the caller sees the position where the read started instead of a partly advanced one (no contract covers either). Relies on the delegate's seek after a failed read, with "indeterminate" as the fallback. readByte is unchanged: a one-byte read cannot hand out part of its result. Not tested: an injected failure inside readShort/readInt/readLong/readLongs, a delegate that transfers part of the bytes and then throws, and a delegate whose seek also fails (the fallback); the repro and both side checks go through readBytes only.

What the checks validated

Repro passes with assertions on and off; both side checks pass; org.apache.lucene.store.* and org.apache.lucene.codecs.* of :lucene:core:test (79 upstream suites, 2,414 tests, 0 failures; 81 suites and 2,417 tests with the two added classes) and :lucene:core:check -x test pass.

A: refuse to give a checksum after any failed delegate read (the finder's sketch) (validated by the checks)

#

Every read records that the delegate threw, and getChecksum() then throws, so checkFooter takes its existing catch-all and rethrows the prior with "checksum status indeterminate: unexpected exception" (+47/-7). It matches the "undetermined state" rule of #16951.

Trade-offs

Loses the "checksum passed" note when the failed read consumed nothing (side check 1), and turns a really corrupt file whose read past EOF consumed buffered bytes into a main EOFException instead of a CorruptIndexException (side check 2; first found by an independent reviewer's executed check).

What the checks validated

Repro passes with assertions on and off; the five closest suites (91 tests) pass; both side checks fail, as the trade-offs say. In the index-level model, together with LFV-492's refill fix, no false report remains.

C: make BufferedIndexInput.readBytes give back the copied bytes when the rest of the read throws

#

Restore buffer.position() when the direct readInternal throws after the buffered bytes were copied.

Trade-offs

Fixes only BufferedIndexInput delegates and only the direct-read path: on the refill() path the buffer state is already replaced before readInternal runs (the separate bug LFV-492). Not built.

Not recommended: keep the prior as the main exception on a mismatch

#

Change checkFooter(in, priorException) back to the pre-8.6.0 order.

Trade-offs

Undoes LUCENE-7822 for real corruption, and the wrong CRC would still produce a misleading suppressed "checksum failed" note.

Downstream note

#

A product that treats every CorruptIndexException as permanent corruption, for example by marking a store corrupt, may act on this false report after one transient read error.

How it was found

#

Differential model-based testing with fault injection. A model of the store inputs made one assumption explicit, that a read that throws has consumed nothing; a harness then failed each NIOFSDirectory file read once, over 10 file sizes and 9 read patterns, through openChecksumInput and checkFooter(in, priorE). One JUnit test on main confirmed it.

The method in full146 words

Method: semi-formal, differential model-based testing with fault injection, on main f794ff5a505c, 2026-11-09.

  • Model. A model of the store input family after a failed read listed the assumptions each layer makes about the layer below. One of them, "a delegate read that throws has consumed nothing", is what BufferedChecksumIndexInput relies on, and BufferedIndexInput breaks it by design.
  • Harness. A checksum-leg harness failed every single FileChannel.read of a NIOFSDirectory input once, over 10 file sizes and 9 read patterns (216 runs), read the file through openChecksumInput and checkFooter(in, priorE), and compared stock main with fix variants: 212 false corruption reports on stock, 0 with both this fix and the refill fix of LFV-492. An index-level harness did the same for DirectoryReader.open (326 runs).
  • Confirmation. A one-test JUnit failed on stock main with assertions on and off; released jars bracketed the change to 8.5.2 / 8.6.0.

History

#

Introduced in 8.6.0 by LUCENE-7822 (583499243a2, 2020-05-07), which made a footer mismatch the main exception of checkFooter(in, priorException). The wrong CRC itself is older (5.0.0) but before 8.6.0 only added a suppressed note. 8.5.2 passes; every tested release from 8.6.0 to 10.6.0, and main, fails.

LFV-1431, snapshot of 2026-11-09

Registry title
After one transient read failure, BufferedChecksumIndexInput's CRC misses the buffered bytes that the failed read already consumed, so CodecUtil.checkFooter(in, priorException) reports a healthy file as 'checksum failed' corruption instead of rethrowing the IOException (every release since 8.6.0)
Area
store / BufferedChecksumIndexInput and codecs / CodecUtil.checkFooter(in, priorException) (BufferedIndexInput-based inputs: NIOFSDirectory, misc RAFDirectory, BufferedIndexInput.wrap)
Priority
Low, rank 801: In every release since 8.6.0, one transient read failure on a BufferedIndexInput-based directory such as NIOFSDirectory can make Lucene's own footer check report a healthy file as 'checksum failed (hardware problem?)' corruption instead of rethrowing the IOException, for example while opening an index. It is Low because an exception is due anyway (only its type and message are wrong), the default MMapDirectory is not affected, and it needs a transient storage failure inside a read that crosses the buffer end.
Impact class
wrong error
Impact note
Hits only inputs built on BufferedIndexInput (NIOFSDirectory, the misc RAFDirectory, BufferedIndexInput.wrap and third-party subclasses over remote storage; not MMapDirectory, which FSDirectory.open returns on 64-bit JVMs), and only when one read of a checksummed file fails transiently after it has already consumed the bytes left in the input's buffer (a read that crosses the 1 KiB buffer end) while the input stays readable: Lucene's own checkFooter(in, priorException) then throws CorruptIndexException 'checksum failed (hardware problem?)' for the healthy file, with the real IOException only suppressed [exec -ea and -da]; an exception is due either way, so nothing is read wrongly, but callers and people that act on CorruptIndexException are told the file is corrupt; in the finder's index-level model, with LFV-492's fix applied, one transient failure while opening a healthy 12-segment index was still reported as corruption in 109 of 326 failure positions (segments_N, .fnm, .dvm), and in none with this fix too; no scale is needed.
Summary
You read a checksummed file through a BufferedIndexInput-based directory such as NIOFSDirectory, one read fails with a transient IOException after it has already handed out the bytes left in the input's 1 KiB buffer, and you then call CodecUtil.checkFooter(in, priorException) as its javadoc shows; you expect the IOException back, with a note that the checksum passed or could not be computed. Instead the checksum wrapper adds bytes to its CRC only after a read succeeds, so the bytes the failed read consumed never reach the CRC, and checkFooter throws CorruptIndexException 'checksum failed (hardware problem?) : expected=73689b45 actual=3fabad1f' as the main exception, calling the healthy file corrupt. The same failure at an empty buffer correctly gives back the IOException with 'checksum passed ... possibly transient resource issue'.
