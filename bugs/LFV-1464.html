Sandbox numeric multi-range query throws NoSuchElementException when every range is empty

SortedNumericStabbingBuilder("f").add(3, 1).add(9, 7) should match nothing, because the query drops reversed ranges (lower > upper here), but with two or more ranges and none left, search throws NoSuchElementException. Every release since 10.3.0; zero ranges or one empty range correctly give 0 hits.

The finding in 30 seconds

#

The sandbox builder SortedNumericStabbingBuilder turns a list of numeric ranges into one query that matches their union. With two or more ranges, the query it builds drops reversed ranges (lower bound above upper bound, judged by the sign of lower - upper), and then assumes at least one range is left.

Background

#
  1. A range [lower, upper] with lower > upper is empty: no value lies in it. Lucene's single-range queries match nothing for it.
  2. SortedNumericStabbingBuilder.build() picks a query by the number of ranges: none gives MatchNoDocsQuery, one gives the core newSlowRangeQuery, two or more give SortedNumericDocValuesMultiRangeQuery.
  3. That query's constructor sorts and merges the ranges and drops the reversed ones.

The finding, step by step

#
  1. Index one document with SortedNumericDocValuesField("f", 5).
  2. Count new DocValuesMultiRangeQuery.SortedNumericStabbingBuilder("f").add(3, 1).add(9, 7).build(): two ranges, both empty because lower > upper.
  3. You expect 0 hits: the query drops empty ranges on purpose, .add(3, 1) alone counts 0, and .add(3, 1).add(5, 5) counts 1.
  4. Instead IndexSearcher.count throws java.util.NoSuchElementException, with assertions on and off.
  5. Why: both ranges are dropped, so the query's range set is empty (it prints f:[]), and scorerSupplier reads its first element without checking.

Who is affected

#

Users of the sandbox builder SortedNumericStabbingBuilder whose query has two or more ranges, all empty: for example ranges from user filters with "from" above "to", or exclusive ranges written with the Math.addExact idiom of newSlowRangeQuery's javadoc, where (5, 6) becomes [6, 5]. Loud: one failed search; wrong hits only through a contrived hash-code collision with a cached query.

Mechanism, terms and numbers620 words

DocValuesMultiRangeQuery.SortedNumericStabbingBuilder (sandbox, @lucene.experimental) builds one query for a union of numeric ranges. With two or more ranges it creates a SortedNumericDocValuesMultiRangeQuery, whose constructor drops reversed ranges on purpose (} // else drop reverse ranges; it tests the sign of lower - upper, which for ordinary bounds such as [3, 1] means lower > upper). When every range is dropped, the range set is empty and MultiRangeWeight.scorerSupplier calls sortedClauses.getFirst() with no check, so IndexSearcher.count and search throw java.util.NoSuchElementException on each segment whose field infos contain the field, with assertions on and off, on NUMERIC and SORTED_NUMERIC fields, with and without a skip index. The same builder returns no hits for zero ranges and for one empty range, and the SortedSet sibling returns no hits for two. It has been in every release since the class arrived in 10.3.0. A rewrite override (+9 lines with its import) that returns MatchNoDocsQuery for an empty set passes the repro and the sandbox search tests. The failure is loud (nothing is cached or written; it returns wrong hits only through a contrived hash-code collision with a cached query), the API is sandbox-only, and every range must be dropped, so it is Low.

The bug (main f794ff5a505c)

#
  1. The builder counts raw ranges. SortedNumericStabbingBuilder.build() (DocValuesMultiRangeQuery.java:174-184): no range -> MatchNoDocsQuery.INSTANCE (:175-177); one range -> SortedNumericDocValuesField.newSlowRangeQuery (:178-182), whose rewrite turns lower > upper into MatchNoDocsQuery (SortedNumericDocValuesRangeQuery.java:94-96); two or more -> new SortedNumericDocValuesMultiRangeQuery (:183, :186-188). Neither add() (:169-172) nor LongRange (:83-86) checks the order of the bounds.
  2. The constructor drops reversed ranges. resolveOverlaps (SortedNumericDocValuesMultiRangeQuery.java:88-148, called at :57) computes long cmp = r.lower - r.upper (:98) and adds a point for cmp == 0, two edges for cmp < 0 and nothing otherwise (:99-106; } // else drop reverse ranges at :105). For ordinary bounds cmp > 0 means lower > upper; for bounds far apart the subtraction overflows and the sign is wrong (LFV-1463). Here cmp is 2 for both [3, 1] and [9, 7]: no edge, so it returns an empty TreeSet (:147) and toString prints f:[] (:150-153).
  3. Nothing catches the empty set. The class does not override rewrite. MultiRangeWeight.scorerSupplier (:210-215) returns null only when the segment lacks the field (:211-213), then reads sortedClauses.getFirst().lower (:214), and TreeSet.first() throws. This happens before any doc values are read, so codec, skip index and field type do not matter. IndexSearcher.searchLeaf asks for the scorer supplier unless the collector ends the segment first in getLeafCollector (IndexSearcher.java:834-842); count and search(q, 10) reach it (executed).
  4. The sibling has the guard. SortedSetDocValuesMultiRangeQuery ignores empty ranges too (// otherwise ignore, SortedSetDocValuesMultiRangeQuery.java:124) but returns an empty scorer when none is left (:196-198).

The numbers

#

One document, f = 5, default IndexWriterConfig. .add(3, 1).add(9, 7): NoSuchElementException at scorerSupplier:214, assertions on and off. Controls on a one-document index with f = 5: .add(3, 1) alone counts 0; .add(3, 1).add(5, 5) counts 1; the SortedSet builder with two empty ranges counts 0; a BooleanQuery of two empty LongPoint ranges counts 0.

Same class, separate roots

#
  • LFV-1463: half-open ranges such as [Long.MIN_VALUE, 10] are dropped as if reversed, because the sign test lower - upper overflows (:98). When every range of a query overflows, the set is empty and search hits this bug's missing guard. Fixing either root alone leaves the other.
  • LFV-1462: with a skip index, a document without a value is judged by a later document's values (matches(), :237).
Exposure and likelihood283 words
  • Who is hit. Code that builds this sandbox query (@lucene.experimental) from computed or user-supplied bounds without filtering out empty ranges, when a query has two or more ranges and all of them are dropped (for ordinary bounds: all empty), on a segment whose field infos contain the field.
  • A natural trigger. newSlowRangeQuery's javadoc says "For exclusive ranges, pass Math.addExact(lowerValue, 1) or Math.addExact(upperValue, -1)" (SortedNumericDocValuesField.java:93-94). The exclusive ranges (5, 6) and (7, 8) then become [6, 5] and [8, 7], and that query throws too (executed).
  • Default vs opt-in. Opt-in API (sandbox); otherwise the default codec and config, NUMERIC and SORTED_NUMERIC fields with and without a skip index, assertions on or off. One document is enough.
  • Effect. One failed search request with a message-less exception instead of 0 hits, and no index change. Nothing is cached: on a cache miss the query cache calls the wrapped scorerSupplier before it stores anything (LRUQueryCache.java:811-874).
  • One contrived case returns wrong hits instead. The query cache looks a query up before it asks the wrapped weight (LRUQueryCache.java:834, :878-888; for a count :921-924), and the empty query equals any multi-range query on the same field (upperBoundWiseEquals, :183-193). If one with the same hash code is already cached, the empty query gets its hits: on main, with a cache-every-query policy, after f:[-1..31] (hash code 4123, like the empty query) was counted, the empty query counted 32 instead of 0; with fix (a), 0 (executed).
  • What avoids it. A query in which at least one range survives the constructor (for ordinary bounds: at least one non-empty range). Wide ranges that the overflow drops wrongly are LFV-1463.

Why it looks unintended

#
  • No javadoc requires lower <= upper, and the class drops empty ranges on purpose (// else drop reverse ranges).
  • Zero ranges or one empty range give 0 hits; the SortedSet sibling gives 0 for two.
  • The sibling's review (#13974) asked that an empty set never reach the scorer; the numeric class lacks that guard.
The full argument213 words
  • No contract excludes the input. No javadoc says lower <= upper. The builder's javadoc says "For the single range it behaves like SortedNumericDocValuesField#newSlowRangeQuery" (DocValuesMultiRangeQuery.java:156-160), and that query matches nothing for lower > upper. The class javadoc is "A union multiple ranges" (SortedNumericDocValuesMultiRangeQuery.java:44-48); a union of empty ranges is empty.
  • The class accepts empty ranges on purpose. It drops them (:105); beside one non-empty range the query works (.add(3, 1).add(5, 5) counts 1, executed).
  • Only the number of ranges changes the outcome. Zero ranges: no hits; one empty range: no hits; two or more, all empty: exception (executed).
  • Upstream tests feed empty ranges. TestSortedDvMultiRangeQuery.testNumericEquals builds [5,3] beside [7,9] (TestSortedDvMultiRangeQuery.java:186); no test has every range empty.
  • History. In the review of the SortedSet sibling (#13974, 2024-12-19), gsmiller asked "Can we make sure rangeClauses is never empty at this point? Ideally we would want to have returned a null scorer supplier if this was the case. But I think you have this already covered elsewhere in your builder logic?"; that design keeps an empty union away from the scorer. The numeric class (#14404) kept the builder's empty check but re-creates the empty set in its constructor, after that check. Its PR thread never discusses empty ranges.
The devil's-advocate check176 words

Strongest case for "not a bug": empty ranges are caller errors in an experimental sandbox API. The points sibling LongPointMultiRangeBuilder.add rejects them with IllegalArgumentException("Upper value of range should be greater than lower value of range") (LongPointMultiRangeBuilder.java:47-51), so an exception is the right answer, and a loud one is better than silently matching nothing.

Why it fails: nothing documents empty ranges as illegal here; this class accepts and drops them and matches nothing for one of them; and a message-less NoSuchElementException from TreeSet.first, thrown lazily per segment at search time and only for two or more ranges, is not an argument check. @lucene.experimental covers API stability, not exceptions on accepted input. Rejecting reversed bounds at add() or build() (fix option b) is at least as defensible as fix (a), as a deliberate change of the contract; a maintainer may well prefer it. The intended-behaviour verifier found that no "works as designed" argument survives; the cross-model reviews rated the case weak, and a later cross-model fact check of the brief (OpenAI GPT-5.6) rated it moderate.

Suggested fix

#

Recommended (a) Rewrite an empty range set to MatchNoDocsQuery (recommended, validated)

Override rewrite to return MatchNoDocsQuery.INSTANCE when no range is left (+9 lines). The repro then passes with assertions on and off, and the two multi-range suites, the whole sandbox search test package (115 tests; these with assertions on) and the format check pass.

  @Override
  public Query rewrite(IndexSearcher indexSearcher) throws IOException {
    if (sortedClauses.isEmpty()) {
      return MatchNoDocsQuery.INSTANCE; // every clause was reversed and dropped
    }
    return super.rewrite(indexSearcher);
  }
All options and trade-offs3 options · 473 words

One fix was validated with gradle; (b) rejects empty ranges instead; (c) was tried and rejected.

(a) Rewrite an empty range set to MatchNoDocsQuery (recommended, validated)

#

The diff: a rewrite(IndexSearcher) override in SortedNumericDocValuesMultiRangeQuery (+9 lines).

  @Override
  public Query rewrite(IndexSearcher indexSearcher) throws IOException {
    if (sortedClauses.isEmpty()) {
      return MatchNoDocsQuery.INSTANCE; // every clause was reversed and dropped
    }
    return super.rewrite(indexSearcher);
  }

Trade-offs

  • Keeps today's semantics (empty ranges are dropped) and matches the builder's zero- and one-range paths and the SortedSet sibling.
  • IndexSearcher rewrites before it creates weights (IndexSearcher.java:495-528, :871-880), so through its search and count methods the empty query never reaches scorerSupplier or the query cache.
  • It acts only through rewrite: a caller that calls createWeight on the query without rewriting it first, which the usual IndexSearcher flow never does, would still reach getFirst() at :214.
  • MatchNoDocsQuery.INSTANCE also exists on 10.6.0 (read; the diff was not applied there).

What the checks validated

  • Clean scratch worktree of f794ff5a505c, gradle, OpenJDK 25.0.3, 2026-11-09: the repro fails on stock with assertions on and off and passes with the fix, on and off.
  • With the fix, in runs with assertions on: TestSortedDvMultiRangeQuery 10 of 10; TestMultiRangeQueries 12 run, 1 @Nightly skipped; the whole org.apache.lucene.sandbox.search test package (15 suites with the new test, 115 tests, 5 skipped by upstream @Nightly annotations, 0 failures); :lucene:sandbox:checkGoogleJavaFormat with the fix and the test in place.
  • Earlier: composed with the fixes of LFV-1463 and LFV-1462 it passed all three bugs' tests (assertions on and off; for this bug the finder's equivalent test with ranges [10,0] and [20,15], not the repro above); with LFV-1463's fix the bounded-exhaustive check found 0 mismatches in 102,900 cases.

(b) Reject empty ranges in SortedNumericStabbingBuilder.add()

#

Throw IllegalArgumentException for lower > upper, as LongPointMultiRangeBuilder.add does.

Trade-offs

  • A behaviour change: one empty range, which matches nothing today, would throw; testNumericEquals (:186) builds [5,3] and would need changing; the Math.addExact exclusive-range idiom would fail at add(); the SortedSet builder would differ. Not run.

(c) Return a null ScorerSupplier for an empty set (rejected)

#

Passes the repro, but the empty query then runs normally and can be cached.

Trade-offs

  • equals (upperBoundWiseEquals, :183-193) is true whenever one of the two range sets is empty, so with a caching policy that caches every query, f:[-1..31] (same hash code, 4123) counted 0 instead of 32 after the empty query (executed probe). Option (a) avoids this because the empty query is rewritten away before caching.
  • Related observation, not claimed separately: on stock code that equals behaviour shows only through a hash-code collision with an already cached query on the same field, and then the empty query is served that query's hits (32 instead of 0, executed; see Who is affected). Fix (a) closes that path; a size check in upperBoundWiseEquals is cheap defence in depth.

Downstream note

#

Elasticsearch and Solr do not use these classes, and OpenSearch uses only the SortedSet builder, which already returns no hits for an empty set (code search, 2026-11-09, not exhaustive).

How it was found

#

A bounded-exhaustive check compared the query with a plain union-of-ranges reference on every query of one or two ranges over ten extreme and small values, and of three ranges over five, on four index shapes (102,900 cases). With LFV-1463's overflow fixed, the only mismatches left were all-empty queries; reading scorerSupplier found the missing check.

The method in full109 words

Method: semi-formal translation validation. The value domain was Long.MIN_VALUE, MIN_VALUE + 1, -3, -2, -1, 0, 1, 2, MAX_VALUE - 1 and Long.MAX_VALUE for one- and two-range queries, and MIN_VALUE, -2, 0, 1 and MAX_VALUE for three-range queries; the index shapes were NUMERIC and SORTED_NUMERIC fields, each with and without a skip index. The check was run to validate the fix of LFV-1463: with that fix in place, the only remaining mismatch class was "every range really empty -> NoSuchElementException" (12,100 of the 102,900 cases, every shape). Code reading of scorerSupplier located the missing check, and a one-test JUnit on the public API witnessed it.

Registry title
Sandbox numeric multi-range doc-values query whose clauses are all reversed (lower > upper) throws NoSuchElementException at search time instead of matching nothing (SortedNumericStabbingBuilder("f").add(3, 1).add(9, 7) on an index where f has a value); since 10.3.0
Area
sandbox / doc-values multi-range query (DocValuesMultiRangeQuery.SortedNumericStabbingBuilder -> SortedNumericDocValuesMultiRangeQuery: empty clause set after every reversed clause is dropped)
Priority
Low, rank 662: The sandbox numeric multi-range query throws NoSuchElementException at search time instead of matching nothing when every one of its two or more ranges is empty, in every release since 10.3.0. It is Low because the failure is loud and nothing is written (wrong hits only through a contrived hash-code collision with an already cached query), the API is sandbox-only, and an all-empty set of ranges is an uncommon input.
Impact class
crash
Impact note
Only users of the sandbox (@lucene.experimental) builder DocValuesMultiRangeQuery.SortedNumericStabbingBuilder are hit, and only when a query has two or more ranges and every one of them is empty (lower > upper, for example ranges computed from user input, or empty exclusive ranges written with the Math.addExact idiom of newSlowRangeQuery's javadoc): IndexSearcher.count and search then throw java.util.NoSuchElementException on each segment whose field infos contain the field, with -ea and -da, the default codec and config and no scale, on NUMERIC and SORTED_NUMERIC fields with and without a skip index [exec]; a query with at least one range that survives the constructor (for ordinary bounds: one non-empty range), a single empty range and the SortedSet sibling all work, and the failure is loud (nothing cached or written; wrong hits only through a contrived hash-code collision with an already cached query, executed).
Summary
You index one document whose field f holds 5 (SortedNumericDocValuesField) and count new DocValuesMultiRangeQuery.SortedNumericStabbingBuilder("f").add(3, 1).add(9, 7).build(), a union of two empty ranges (lower > upper); you expect 0 hits, because the query drops reversed ranges on purpose and the same builder returns no hits for no range or for one reversed range. Instead IndexSearcher.count throws java.util.NoSuchElementException: once every clause is dropped the query's clause set is empty (it prints f:[]), and MultiRangeWeight.scorerSupplier reads its first element (sortedClauses.getFirst()) with no empty check.
