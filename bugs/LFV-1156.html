LatLonPoint, XYPointField and the range fields accept setBytesValue, then their typed setters ignore the BytesRef offset and the new value is not indexed

After setBytesValue installs a slice of a larger array, LatLonPoint.setLocationValue writes the new point at index 0, not at the slice's offset, so the new point is silently not indexed; XYPointField and the five range fields do the same. IntPoint rejects that setBytesValue call; affected: 6.1.0 to 10.6.0, and main.

The finding in 30 seconds

#

Lucene lets you reuse one field instance for many documents by changing its value with a setter. LatLonPoint has a typed setter, setLocationValue, and also inherits the raw Field.setBytesValue(BytesRef). A BytesRef may point into the middle of a larger array: it is a slice, offset + length.

  1. Build LatLonPoint f = new LatLonPoint("p", 10, 20), copy its 8 encoded bytes into bytes 8-15 of a 16-byte buffer, and install that slice: f.setBytesValue(new BytesRef(buffer, 8, 8)). The field accepts it; IntPoint would throw here.
  2. Reuse the field: f.setLocationValue(-30, -40), then index one document with it. You expect the document at (-30, -40).
  3. Instead a box query around (-30, -40) counts 0 and a box around (10, 20) counts 1, with no error, assertions on or off. f.toString() even prints (-30, -40).
  4. Why: the setter takes the slice's whole array and writes the new point into bytes 0-7, ignoring the offset. Indexing reads the slice, bytes 8-15, which still hold (10, 20). Your buffer's bytes 0-7 are overwritten. (With an offset below 8 the write also covers the start of the slice, and a mix of old and new bytes is indexed.)
  5. XYPointField.setLocationValue and setRangeValues of IntRange, LongRange, FloatRange, DoubleRange and InetAddressRange do the same: an IntRange [1, 2] reset to [100, 200] still matches [1, 1], not [150, 150].

Who is affected

#

Code that reuses one LatLonPoint, XYPointField or range field, installs a correctly sized slice at a non-zero offset with the Expert setBytesValue (for example points pre-encoded into one buffer), and later calls the typed setter on the same instance. Default config, any index size; no Lucene code makes these calls, so the trigger is contrived.

Mechanism, terms and numbers793 words

Field.setBytesValue(BytesRef) is a public Expert setter that stores the caller's BytesRef uncopied, and a BytesRef may be a slice (offset + length) of a larger array. IntPoint, LongPoint, FloatPoint, DoublePoint and InetAddressPoint override it to throw, but LatLonPoint, XYPointField, IntRange, LongRange, FloatRange, DoubleRange and InetAddressRange accept it. Their typed setters (setLocationValue, setRangeValues) then take the slice's whole backing array and encode the new value at index 0, ignoring the offset, while indexing reads the slice at its offset. So after a correctly sized slice at a non-zero offset, the typed setter's value is silently not indexed: when the offset is at least the encoding's length (as in the example, offset 8 of a 16-byte array), the old value stays indexed and the caller's array is overwritten outside the slice; with a smaller offset a mix of old and new bytes is indexed. The four numeric range classes' getMin and toString also read from index 0 of the array, and getMax from its middle. LatLonPoint did this from 6.1.0 on (6.0.x allocated a fresh BytesRef per call); the other six classes from their first release. Affected: every release from 6.1.0 through 10.6.0, and main. The trigger is contrived (the raw setter with a non-zero-offset slice, then the typed setter, on one reused instance), so a maintainer may see the fix as API hardening: these classes accept a setter they cannot honour, while the sibling point types reject it.

  • toString reads bytes 0 and 4 the same way (LatLonPoint.java:153-156), so it shows the new value that was not indexed.
  • The same pattern: XYPointField.setLocationValue (XYPointField.java:77-89, :83), setRangeValues of IntRange, LongRange, FloatRange and DoubleRange (:84-106, :103, then verifyAndEncode(min, max, bytes) from index 0) and of InetAddressRange (InetAddressRange.java:78-87, :84).
  • The four numeric range classes' getters ignore the offset too: getMin decodes from index 0 of the array and getMax from b.length / 2 of the whole array (IntRange.java:164-166, :175-177, :188; FloatRange and DoubleRange the same lines, LongRange.java:156-158, :167-169, :180), which for the 16-byte array with offset 8 happens to be the slice's start; toString uses the same decoders. InetAddressRange has no public getters, and its toString (Field.toString) honours the offset.
  • Length is checked, offset is not: a BytesRef of the wrong length fails loudly, at addDocument (PointValuesWriter.java:78-86) or, when its array is shorter than the encoding, already in the typed setter (ArrayIndexOutOfBoundsException). Only a correctly sized slice at a non-zero offset is silent.
  • The offset decides what is indexed instead: when it is at least the encoding's length (8 here), the write lands entirely outside the slice and the old value stays indexed; with a smaller offset the write also covers the start of the slice and a mix of old and new bytes is indexed (see the table).

Exposure and likelihood277 words
  • Who is hit. Code that reuses one LatLonPoint, XYPointField, IntRange, LongRange, FloatRange, DoubleRange or InetAddressRange instance, installs a correctly sized slice at a non-zero offset through the inherited setBytesValue, and later calls the typed setter on the same instance. From that typed call on, the field indexes whatever the slice's bytes hold when the document is added (they are not copied), not the typed value, until the next setBytesValue.
  • What happens. A silently wrong indexed value: queries for the new value miss the document. With an offset of at least the encoding's length (8 for LatLonPoint), the old value stays indexed and the first bytes of the caller's own array, outside the slice, are overwritten in bounds; with a smaller offset a mix of old and new bytes is indexed. The four numeric ranges' getMin and toString read from index 0 of the array and getMax from its middle (IntRange reports [100 : 1] after setRangeValues([100], [200])).
  • Not affected: a raw slice used on its own (indexed correctly at its offset), an offset-0 BytesRef of the exact length, and the typed setters on a field that never saw setBytesValue.
  • Default vs opt-in. Default IndexWriterConfig, codec and searcher; assertions on or off. The trigger needs the Expert setBytesValue on a typed geo or range field; no code in the Lucene repository calls it on these classes.
  • Scale. One document is enough; index size does not matter.
  • How likely. Contrived: three unusual choices on one instance (the raw setter on a typed field, a non-zero offset, then the typed setter). Nobody has reported it since 6.1.0 (2016).

Why it looks unintended

#
  • setLocationValue says "Change the values of this field"; after the call, the indexed value did not change.
  • IntPoint, LongPoint, FloatPoint, DoublePoint and InetAddressPoint reject setBytesValue (TestField asserts it for the numeric ones); these seven classes never got that override.
  • In 6.0.0 and 6.0.1 the same calls indexed (-30, -40): each setLocationValue allocated a fresh BytesRef.
The full argument312 words
  • The setters' contract. setLocationValue: "Change the values of this field" (LatLonPoint.java:108-109, XYPointField.java:71-72); setRangeValues: "Changes the values of the field." (IntRange.java:77-78 and the three siblings), "Change (or set) the min/max values of the field." (InetAddressRange.java:72-73).
  • The accepted input is valid. setBytesValue accepts the slice and documents only that it is not copied (Field.java:329-334); BytesRef is "a slice (offset + length) into an existing byte[]" (BytesRef.java:21-22), and indexing honours the offset (PointValuesWriter.java:93). Nothing documents "offset 0 only" or "do not mix with the typed setter".
  • Lucene's design for typed points is to reject the raw setter. IntPoint, LongPoint, FloatPoint, DoublePoint (the guard dates from LUCENE-6917, 7da175b0b6b, 2015, in the classes that LUCENE-6975 renamed to IntPoint and its siblings) and InetAddressPoint (LUCENE-7043, 54216c6f650, 2016) throw "cannot change value type from <type> to BytesRef" (IntPoint.java:75-78, LongPoint.java:75-78, FloatPoint.java:99-102, DoublePoint.java:99-102, InetAddressPoint.java:127-130; the sandbox BigIntegerPoint and HalfFloatPoint too). TestField asserts this for the numeric points (testIntPoint, TestField.java:175-192, with trySetBytesValue and trySetBytesRefValue, :896-910) and has no case for the seven classes. No test asserts the current behaviour.
  • It worked before. 6.0.0 and 6.0.1 allocated a fresh byte[8] and BytesRef in every setLocationValue; LUCENE-7240 (45c48da54ad2) switched to reusing the current array as a side change its commit message and issue do not discuss.
  • The reuse was questioned once. In the 2016 review that created the range field (#8434, LUCENE-7381), Adrien Grand (jpountz) asked: "The reuse of fieldsData in setRangeValues worries me a bit, is it safe? Other fields do not seem to do that?" Nick Knize (nknize) answered: "We did this in LatLonPoint. I don't think its any less safe than creating a new BytesRef (but more efficient?)". No failure, setBytesValue or offset was named, and nothing changed.
The devil's-advocate check112 words

The case: setBytesValue is an inherited Expert setter that does not copy, these classes own an internal encoding, and a correct raw route exists (new Field(name, bytes, LatLonPoint.TYPE)), so mixing a raw slice with the typed setter is caller misuse.

Why it fails: nothing documents that restriction; the call is accepted and the stale value is indexed silently; the sibling point types reject exactly this call, and TestField treats that rejection as the contract for the numeric points; 6.0.x handled the same calls correctly. Every reviewer rated the misuse case weak or moderate and rejected it. A maintainer may still call the fix API hardening rather than a bug fix.

Suggested fix

#

Recommended Reject setBytesValue in the seven classes, as the sibling points do (validated)

Override setBytesValue(BytesRef) in the seven classes to throw "cannot change value type from <class> to BytesRef", as IntPoint and the other points do (+36 lines). Validated: the regression form of the test passes with assertions on and off, and 620 tests of the closest suites pass. Code that uses offset-0 setBytesValue on these classes today gets an exception.

  @Override
  public void setBytesValue(BytesRef bytes) {
    throw new IllegalArgumentException("cannot change value type from LatLonPoint to BytesRef");
  }

Reject setBytesValue in the seven classes, as the sibling points do (validated) (recommended)

#

One override per class in LatLonPoint, XYPointField, IntRange, LongRange, FloatRange, DoubleRange and InetAddressRange, each naming its class. Field.setBytesValue(byte[]) delegates to this method, so it is covered too. The getters and toString can then never see a foreign slice.

  @Override
  public void setBytesValue(BytesRef bytes) {
    throw new IllegalArgumentException("cannot change value type from LatLonPoint to BytesRef");
  }

Trade-offs

A behaviour change: code that calls setBytesValue on these classes today with an offset-0 BytesRef of the exact length, which indexes correctly, gets an exception (worth a CHANGES entry under API changes). No code in the Lucene repository calls it on these classes (downstream code that reuses generic Field objects might); the range doc-values fields, which some tests feed through setBytesValue, are other classes and unchanged. The regression test is the same test with its setBytesValue line wrapped in expectThrows.

Keep accepting setBytesValue, but never write into a BytesRef the field does not own (validated for LatLonPoint only)

#

In each typed setter allocate a fresh exact-size array unless the current BytesRef has offset 0, the exact length and an array of that length; read at offset in toString, getMin and getMax, and compute decodeMax's start from the dimension count instead of bytes.length / 2.

Trade-offs

Keeps the raw route working for every slice, and the existing test is the regression test unchanged. More code (seven setters plus the range getters and toString), one allocation when a typed call follows a foreign slice, and an offset-0 exact-size array the caller passed is still written into by the next typed call.

What the checks validated

Earlier, for LatLonPoint only: the repro passes with the change (assertions off), and stock TestLatLonPoint (1 of 1) and TestLatLonPointDistanceFeatureQuery (8 of 8) pass; the six other classes still fail without their own change.

Always allocate a fresh BytesRef in the typed setters, as 6.0.x did (not run)

#

Replace the reuse of ((BytesRef) fieldsData).bytes with a new exact-size array on every call.

Trade-offs

Smallest change to the setters; costs one small allocation per call, which the 2016 reuse removed; the range getters and toString still read a raw slice from index 0 until the next typed call.

Downstream note

#

Products that feed pre-encoded point or range bytes from a shared buffer into reused field instances should not mix setBytesValue slices with the typed setters: a stale or mixed value is indexed silently.

How it was found

#

Semi-formal: a proof-obligation check asked whether each typed setter of the point and range fields changes what is indexed for every value the field accepts, including one installed by the inherited setBytesValue. It does not when that value is a slice at a non-zero offset. A JUnit test on main turned that into a missed document.

The method in full138 words

Method: semi-formal (a proof-obligation check of the typed point and range fields' setter contract, witnessed by an executable repro, on main 5adff78bb168, 2026-11-02).

  • Obligation. "Change the values of this field" must change what is indexed, for every value the class accepts. Field.setBytesValue(BytesRef) is accepted by these classes, so a slice with any valid offset is such a value.
  • Finding. The setters write into ((BytesRef) fieldsData).bytes from index 0, and indexing reads binaryValue() at its offset; the obligation fails for every non-zero offset. The sibling point types discharge it by rejecting setBytesValue.
  • Witness. A JUnit test on the stock main jars: the box query around the new location counts 0 instead of 1, with assertions on and off. A probe showed the same for all seven classes and the rejection by the five numeric and InetAddress points.

LFV-1156, snapshot of 2026-11-09

Registry title
LatLonPoint, XYPointField and the range fields (IntRange, LongRange, FloatRange, DoubleRange, InetAddressRange) accept the inherited Field.setBytesValue, which IntPoint and the other numeric points reject, but their typed setters write from index 0 of the backing array, so after a BytesRef slice with a non-zero offset setLocationValue/setRangeValues silently leaves the old value indexed
Area
document / typed point and range fields (LatLonPoint, XYPointField, IntRange, LongRange, FloatRange, DoubleRange, InetAddressRange) and the inherited Field.setBytesValue
Priority
Low, rank 895: If an application reuses a LatLonPoint, XYPointField or range field by calling the inherited setBytesValue with an offset slice and then the typed setter, the old value is silently indexed, in every release since 6.1.0. It needs three unusual calls on one reused instance that no Lucene code makes, so the trigger is contrived.
Impact class
minor
Impact note
Applications that reuse one LatLonPoint, XYPointField, IntRange, LongRange, FloatRange, DoubleRange or InetAddressRange instance, install a BytesRef slice with a non-zero offset through the inherited Expert Field.setBytesValue and then call the typed setter on the same instance get the old value indexed, and bytes of their own array outside the slice overwritten, with no error (-ea and -da, default IndexWriterConfig, codec and searcher, any index size, every release since 6.1.0); no Lucene code makes this call sequence, and with an offset-0 BytesRef the indexed value is right. The impact class is minor rather than silent wrong results: the wrong indexed value is silent, but the trigger is a contrived mix of the inherited Expert setBytesValue (with a sliced BytesRef) and the typed setter on one reused instance.
Summary
You build a LatLonPoint at (10, 20), install the same encoded point as a slice of a larger buffer with field.setBytesValue(new BytesRef(buffer, 8, 8)), which the field accepts, then reuse the field with setLocationValue(-30, -40) and index it; you expect the document at (-30, -40), as the setter's javadoc 'Change the values of this field' says, or else an IllegalArgumentException from setBytesValue, which is what IntPoint, LongPoint, FloatPoint, DoublePoint and InetAddressPoint throw. Instead setLocationValue writes the new encoding into buffer[0, 8), outside the slice, while indexing reads the slice at its offset, so the document is indexed at (10, 20) and a box query around (-30, -40) finds nothing, with no error. XYPointField.setLocationValue and the setRangeValues of IntRange, LongRange, FloatRange, DoubleRange and InetAddressRange behave the same way, and after such a slice the ranges' getMin/getMax and toString read outside it too.
