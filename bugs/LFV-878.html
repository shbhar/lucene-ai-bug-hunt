HTMLStripCharFilter drops the last word when the text ends right after an unclosed tag name (a < b)

HTMLStripCharFilter keeps an unclosed < as text, except when the input ends right after the tag name: price a < b is indexed as price a, while price a < b (one more space) keeps b. Reproduced on releases from 3.6.0 to 10.5.2 and on main.

The bug in 30 seconds

#

HTMLStripCharFilter removes tags and keeps the text between them. A < that is never closed by > is not a tag, so it is kept when the text goes on: a < b c stays a < b c. Only when the text ends right after the name is the pending <name thrown away.

  1. Index the text price a < b (a plain comparison, no HTML) through HTMLStripCharFilter and StandardTokenizer.
  2. You expect the tokens [price, a, b]. That is what price a < b (one trailing space) gives, and price a < b c gives [price, a, b, c]: an unclosed < with no > is kept as text.
  3. You get [price, a]: the filter returns price a . A TermQuery for b finds 1 of the 2 documents, with no error.
  4. Why: when the text ends, the scanner is still inside the unfinished tag < b, and its end-of-input switch throws that pending text away. If the text goes on after the name and no > closes the tag, a fallback rule outputs it unchanged.
  5. Other endings lose text the same way: a<b gives a, x <p gives x , a </b gives a , for i<n gives for i, if a < b. gives if a .

Who is affected

#

Anyone who strips HTML with HTMLStripCharFilter, directly, through the htmlStrip factory or a search server's char filter built on it, at default settings and any index size. It hits values or queries that end in < [space] name or </ name, such as a < b or for i<n: the last word silently goes missing from the index.

Mechanism, terms and numbers719 words

HTMLStripCharFilter outputs an unclosed tag-like construct as text: a < b c strips to a < b c, and Lucene's own testMalformedHTML requires <ahref=http:.. and <a href=" at the end of the input to come out unchanged. But when the input ends right after the tag name, with no character after it, the scanner's end-of-input switch drops the pending <name: a < b strips to a , price a < b is analyzed as [price, a] and a TermQuery for b misses the document, while price a < b (one trailing space) gives [price, a, b]. It has been this way since the JFlex rewrite in 3.6.0 (2012); the filter it replaced kept the text. No exception and no offset error was seen; what is lost is the pending <name at the end of a value or query, usually one word. A one-hunk grammar change fixes it; one upstream test input needs a one-character change.

Terms

#
  • Pending segment: when the scanner sees <, it keeps the characters it reads in a buffer until it knows whether they form a tag. A closed tag is removed (or replaced by a newline for block elements); anything else is given back as text.
  • Tag-tail state: the scanner state after < (optionally whitespace or /) and a tag name, waiting for attributes and the closing >. The grammar has six, three after < and three after </ (HTMLStripCharFilter.jflex:48-49); four of them matter here: START_TAG_TAIL_EXCLUDE (inline elements such as a, b), START_TAG_TAIL_SUBSTITUTE (any other name, such as p) and the matching END_TAG_TAIL_EXCLUDE and END_TAG_TAIL_SUBSTITUTE after </. The other two, START_TAG_TAIL_INCLUDE and END_TAG_TAIL_INCLUDE, are for names listed in escapedTags.
  • Name: [:_\p{ID_Start}] [-.:_\p{ID_Continue}]* (HTMLStripCharFilter.jflex:69), so b. and i-n are one name each, and a digit cannot start one (a < 5 is never a tag).

The bug

#
  1. < starts the pending segment (HTMLStripCharFilter.jflex:334-339); whitespace or / may follow (:645-649); a name moves to a tag-tail state (:693-712 for start tags, :591-609 for end tags).
  2. In a tag-tail state the only rule is the tail that ends in > (:714-745, :611-641). If more input follows but no > completes the tag, the shared fallback rule (:914-922) pushes the character back and outputs the pending <name unchanged.
  3. If the input ends while the scanner is still in a tag-tail state, JFlex runs the %eof block (:275-323). It lists the four tag-tail states in its "Exclude" group (:284-288), which clears the pending segment. The generated scanner has the same switch in zzDoEOF() (HTMLStripCharFilter.java:6133-6185).
  4. Name is matched greedily, so a following name character (the . of b.) only makes the name longer. Any other character either completes the tag with a tail ending in > (stripped) or, with no >, triggers the fallback of step 2. So the scanner is still in a tag-tail state at end of input only when the input ends right after the (longest) name: the Exclude grouping changes the output in exactly that case.
  5. The states one step earlier (<, </, < ) and the escaped-tag tails are in the "Include" group (:306-318), which outputs the pending segment. So a < and a < are kept, a < b is not, and a < b is.

A state-table model parsed from the grammar (22 states) finds exactly 5 states whose end-of-input action differs from what they do when more input follows: these 4, and the character-reference tail, whose end-of-input leniency is commented ("At end of file, allow char refs without semicolons", :298) and tested.

Exposure and likelihood313 words
  • Who is exposed. Applications that strip HTML with HTMLStripCharFilter: directly, through the htmlStrip SPI factory (for example in a CustomAnalyzer), or through a search server's char filter built on it (Solr's solr.HTMLStripCharFilterFactory; other servers call theirs html_strip; not run on a downstream product). No Lucene analyzer adds it by default, so it is opt-in, but it is stock and needs no non-default setting.
  • What happens. The last word of the value is not indexed, so a term query for it misses the document. No error, and no offset error was seen (the final offset was right in every case of the hunt's bounded sweeps).
  • What it takes. A field value or query string that ends exactly in < [whitespace] name or </ name with no >: plain-text comparisons (a < b, for i<n, if x<y), or text cut off inside a tag (...<b, where losing the fragment does little harm). By reading (not run), each value of a multi-valued field has its own end, and a query string is hit the same way when it goes through the full analysis chain. Deterministic; index size does not matter, and no non-default setting is needed (a name listed in escapedTags is kept).
  • How much is lost. The pending <name at the very end: one JFlex Name, usually one word. A name may contain -, ., :, _ and digits, so a tokenizer can split it: price a < foo-bar gives [price, a], while price a < foo-bar gives [price, a, foo, bar].
  • Versions. Reproduced on 21 releases and snapshots from 3.6.0 to 10.5.2 plus main, and on a branch_10_6 build; the end-of-input grouping is unchanged in the history between them.
  • How likely. Rare: such endings are a small share of real fields, and no report of it was found.

Why it is a bug, not intended

#
  • Lucene's testMalformedHTML keeps unclosed tags with attributes at the end of the input (<ahref=http:.. stays), yet <ahref is dropped.
  • One space after the name keeps the text, as does a pending < or < at the end.
  • The Solr Reference Guide documents the filter for non-HTML input (if a<b then print a;); its predecessor kept these inputs.
The full argument313 words
  • Lucene's tests keep unclosed tags with an attribute part at end of input. testMalformedHTML maps <a href=" to <a href=" (TestHTMLStripCharFilter.java:194-195) and <ahref=http:.. to <ahref=http:.. (:218-219): unclosed start tags that run to the end of the input, kept. No test covers a bare <name at the end; it is inconsistent with these recovery cases. testCDATA labels its unclosed <! cases "unclosed angle bang - all input is output" (:502, :508; added by SOLR-5983 in 2014, which fixed another end-of-input bug in the same switch).
  • The scanner keeps it in the neighbouring cases. Mid-text the fallback rule outputs the unclosed tag (HTMLStripCharFilter.jflex:914-922); at end of input the Include group outputs a pending <, </ or < (:306-318). Whether the name is dropped depends only on whether the input ends right after it, which is hard to defend for plain text (a committer may still see dropping a truncated <div as useful).
  • Documented for non-HTML input (in the Solr Reference Guide, not in Lucene's javadoc). The Solr Reference Guide's HTMLStripCharFilterFactory section: "TIP: The input need not be an HTML document. The filter removes only constructs that look like HTML. If the input doesn't include anything that looks like HTML, the filter won't remove any input." Its example table maps if a<b then print a; to itself; cut after b, the filter returns if a (if x<y gives if x). The same page documents the one intended end-of-input special case, the optional ; of a final entity reference; nothing similar exists for tags.
  • History. The Solr 3.5.0 filter that the 2012 rewrite (LUCENE-3690) replaced keeps all these inputs. The LUCENE-3690 thread (41 comments on JIRA; 40 in the GitHub mirror) never discusses tags at end of input.
  • No javadoc contract either way. The class only "attempts to strip out HTML constructs".
The devil's-advocate check253 words

The intended-behaviour checker built the strongest case for "intended": (a) the %eof block lists every state by hand, and the Exclude/Include split for tag tails reads like "a tag in progress at end of input is markup: strip it unless escaped"; (b) for < directly followed by a letter, browsers agree: the HTML tokenizer's eof-in-tag rule turns a<b into a, and for HTML cut off mid-tag (<p>Hello</p><div) dropping the fragment avoids a junk token; (c) Lucene treats < X > as a tag by design (x < X > gives x \n; LUCENE-5943, Not A Problem), so "< b is not a tag in HTML" is not Lucene's model; (d) upstream testOffsets passes only because the trailing < X is dropped.

Why it fails: the drop depends only on whether the input ends right after the (longest) name, while Lucene's tests keep the tag when an attribute part follows (<ahref=http:.., <a href="). Browsers also drop <b c and <a href=" at end of input, which Lucene and its tests keep, so browser parity is not the filter's model. LUCENE-5943 is about closed tags. And testOffsets depends on the drop only through its helper, which pairs the n-th output X with the n-th input X: its input predates the rewrite (the old filter output it unchanged), and it passes today only because both the X inside < X > and the trailing < X are removed. Argue from Lucene's own consistency, not from browsers.

Suggested fix

#

Recommended A. Treat the four tag-tail states like their neighbours at end of input

Move the four tag-tail states from the end-of-input "Exclude" group to the "Include" group (one hunk in the grammar), regenerate the scanner, and rename the tag in testOffsets' third input from < X > to < Y >. Validated: the new tests pass, all of :lucene:analysis:common:test passes (1,915 tests, 0 failures) and check -x test passes.

B. Keep the text only when whitespace follows < (not run)

#

In the %eof Exclude branch, output the pending segment when its second character is whitespace (< b, </ b) and keep dropping <b.

Trade-offs

Fixes the plain-text form a < b and keeps today's drop of a truncated <div, which a committer may prefer; the existing tests do not force A over B. It matches browsers for < directly followed by a letter, but keeps the inconsistency the tests contradict (<ahref dropped while <ahref and <ahref=http:.. are kept) and adds a special case to the switch. testOffsets needs the same change, because its trailing < X has a space.

C. Drop unclosed tags at end of input whatever follows the name (not recommended)

#

Make the end of input also consume <name ... when a tail was read.

Trade-offs

Contradicts the testMalformedHTML gold values (<ahref=http:.., <a href="), the "all input is output" rule for unclosed <!, and SOLR-2328 (Won't Fix), where the maintainers declined to strip a mid-text unclosed tag; the shared fallback rule would need to know about end of input.

How it was found

#

A public-API probe of the filter showed a < b turning into a while a < b kept its text. A model of the scanner's end-of-input states, parsed from the grammar, then flagged exactly this case, and a sweep of 70.6 million short strings found violations in exactly the predicted states.

The method in full206 words
  • First signal (a probe, not a formal method). A planning probe on the stock main jar, using only the public API, stripped prefixes of x< notatag more text here and more words and a hand-listed set of inputs, and showed x< not giving x and a < b giving a , while x< notatag m and x < y z were kept.
  • State-table model. A model parsed from the real .jflex covered all 22 exclusive lexical states, with one obligation: a state whose mid-text failure gives the pending input back must also output it at end of input. It flagged exactly 5 states: the 4 tag-tail states and the documented character-reference tail.
  • Bounded-exhaustive sweep. On the stock jar, with a metamorphic oracle (appending " " or " z " must not change the earlier output): 36,012,942 strings over 18 symbols up to length 6, and 34,636,832 strings over a 32-token grammar up to length 5, each stripped 3 times. Violations occurred in exactly those 5 states and in none of the 16 other reached states, with 0 final-offset errors. With the fix, only the character-reference tail remains.
  • The finder then wrote the public-API JUnit, the fix and the version runs; independent checkers followed (see "Independent checks").

History

#

Introduced by the JFlex rewrite LUCENE-3690 (f3a363708ff, 2012-01-22; backport d387ae60fcf), first released in 3.6.0. The same six result lines on every one of the 21 tested targets from 3.6.0 to 10.5.2 and main; the Solr 3.5.0 filter it replaced keeps the text. Not fixed upstream.

Versions tested6 rows

Introduced by LUCENE-3690 (#4764), "Re-implemented HTMLStripCharFilter as a JFlex-generated scanner", by sarowe: trunk f3a363708ff (2012-01-22, svn r1234452) and the branch_3x backport d387ae60fcf (2012-01-24), which shipped in 3.6.0. Svn era, no PR.

Not a recent regression. Present since the first Lucene implementation in 3.6.0 (against the Solr 3.5.0 filter it replaced, it was a behaviour change). The later behaviour fixes #11724 (9.9.0) and #15756 (10.5.0) touch attribute rules only; runs on both sides give the same output. The latest upstream commit to the grammar, 02014a6245d3 (#15756, authored 2026-03-03 UTC), leaves %eof untouched.

Bug record

#

LFV-878, snapshot of 2026-10-29

Registry title
HTMLStripCharFilter drops an unclosed '<name' or '</name' when the input ends right after the name, but outputs the same text when any character follows it, so 'a < b' indexes only 'a'
Area
analysis / HTMLStripCharFilter (JFlex grammar: the %eof end-of-input switch for the start- and end-tag tail states; also the 'htmlStrip' char filter SPI)
Priority
Medium, rank 134: Since 3.6.0, stock HTMLStripCharFilter silently drops the last word of any value or query that ends in an unclosed '<name' or '</name' (such as 'a < b'), but it loses at most that one word and needs an uncommon ending.
Impact class
silent wrong results
Impact note
Applications that strip HTML with HTMLStripCharFilter (directly, through the 'htmlStrip' factory, or through a downstream html_strip char filter; no Lucene analyzer adds it by default), at default settings and at any index size, silently lose the last word of a field value or query string that ends in '<' [whitespace] Name or '</' Name with no '>' (plain-text comparisons such as 'a < b' or 'for i<n', or text cut inside a tag), so a term query for that word misses the document; at most that one trailing word is lost, with no exception and correct offsets.
Summary
You run 'price a < b' through HTMLStripCharFilter and StandardTokenizer and expect [price, a, b], which is what you get for 'price a < b ' (one trailing space) or 'price a < b c'. Instead you get [price, a]: when the input ends right after '<' [whitespace] Name or '</' Name with no '>', the end-of-input handler throws the pending text away, while anywhere else the same unclosed construct is output as text, as the upstream tests require for '<ahref=http:..' at end of input. A TermQuery for 'b' therefore misses the document; other shapes are 'a<b' -> 'a', 'x <p' -> 'x ', 'a </b' -> 'a ' and 'if a < b.' -> 'if a ' ('.' is a name character).
