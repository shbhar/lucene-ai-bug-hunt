ICUFoldingFilter folds the Tajik letter ҷ to the Abkhaz letter ҽ instead of ч, so "Точикистон" does not find "Тоҷикистон"

ICUFoldingFilter should strip the descender from ҷ and give ч, like қ, ҳ and the other WITH DESCENDER letters in its table, but one line maps ҷ to ҽ, a different letter. So "Тоҷикистон" is indexed as "тоҽикистон" and the query "Точикистон" finds nothing, in every release since 3.1.0.

The bug in 30 seconds

#

ICUFoldingFilter folds with a compiled table, utr30.nrm, built from Lucene's DiacriticFolding.txt. A hand-written block of that file strips descenders and strokes from Cyrillic letters: җ to ж, қ to к, ҳ to х, ҹ to ч. One line, 04B7>04BC, sends ҷ to Ҽ (ABKHASIAN CHE) instead, and case folding then makes it ҽ.

  1. You add ICUFoldingFilter with its default settings to the analyzer, at index and query time, and index the Tajik phrase "Ҷумҳурии Тоҷикистон" (Republic of Tajikistan). ҷ is "che with descender", a letter of Tajik and Abkhaz.
  2. You expect the plain-letter spelling "Чумхурии Точикистон" to find it: the filter removes descenders, and in the same phrase ҳ already folds to х, as қ folds to к and ҹ to ч.
  3. Instead the document is indexed as ҽумхурии тоҽикистон and the query as чумхурии точикистон: 0 of 1 documents found. The one-word query "Точикистон" also finds 0.
  4. The cause is one line of the folding table, 04B7>04BC: it maps ҷ to Ҽ (ABKHASIAN CHE), which case folding turns into ҽ. The next line, 04B9>0447, maps ҹ to ч.
  5. No error, and the exact spelling still finds itself. In Abkhaz, which writes ҷ and ҽ as two letters, the two now match each other.

Who is affected

#

Users of the optional analysis-icu ICUFoldingFilter (its default normalizer; no setting needed) who index Tajik or Abkhaz Cyrillic text. A query typed with plain ч misses every document that writes the word with ҷ, and in Abkhaz ҷ and ҽ match each other. Deterministic at any scale, silent, in every release since 3.1.0.

Mechanism, terms and numbers605 words

ICUFoldingFilter (module analysis-icu) folds text for search; its javadoc lists "Diacritic removal (including stroke, hook, descender)". Its data, utr30.nrm, is compiled from Lucene's own folding tables and ICU's NFKC data. One hand-copied line of DiacriticFolding.txt, 04B7>04BC, maps U+04B7 CYRILLIC SMALL LETTER CHE WITH DESCENDER (ҷ, a letter of Tajik and Abkhaz) to U+04BC CYRILLIC CAPITAL LETTER ABKHASIAN CHE, which case folding turns into ҽ U+04BD. Removing the descender gives ч U+0447, which is what every sibling WITH DESCENDER or WITH STROKE line of the same block does (җ to ж, қ to к, ҳ to х, ҹ to ч). So the Tajik phrase "Ҷумҳурии Тоҷикистон" is indexed as "ҽумхурии тоҽикистон", the query "Чумхурии Точикистон" (the same words with plain letters) becomes "чумхурии точикистон", and it finds 0 documents; in Abkhaz, which writes ҷ and ҽ as separate letters, the two fold to one term. There is no error, and the exact spelling still matches itself. The line was copied in 2010 from the 2004 draft data of UTR#30 (since withdrawn) and is in every release from 3.1.0 to 10.5.2 and on main. The fix is a one-line data change plus a regenerated utr30.nrm; it changes indexed terms for these letters.

Terms

#
  • ICUFoldingFilter (module analysis-icu): a token filter for "search term folding". Its normalizer NORMALIZER loads the compiled data file utr30.nrm (ICUFoldingFilter.java:69-77); the one-argument constructor uses it, and so does ICUFoldingFilterFactory (SPI name icuFolding), directly or, with a filter argument, wrapped in a FilteredNormalizer2.
  • utr30.nrm: compiled by the gradle task regenerateUtr30DataFiles from src/data/utr30/*.txt with ICU's gennorm2 and icupkg. The task regenerates the rule-based parts of the tables and keeps the data lines after a # Rule: verbatim marker as written, up to the next # Rule: line.
  • The Cyrillic verbatim block (DiacriticFolding.txt:597-626), headed "Cyrillic script \"composed\" that do not further decompose, so decompose here", "These are from UTR#30 DiacriticFolding.txt", "Rule: verbatim". Each line is source>target in hex.

One letter, step by step (stock jar)

#

Ҷ U+04B6 is case-folded to ҷ U+04B7; line 618 maps ҷ to Ҽ U+04BC; case folding maps Ҽ to ҽ U+04BD. getRawDecomposition(U+04B7) is U+04BC, and normalize gives U+04BD for Ҷ ҷ Ҽ ҽ Ҿ ҿ Ӌ ӌ alike, while Ч and ч give ч. U+04B7 has no NFKC decomposition, so the order in which gennorm2 reads the files (a separate bug, LFV-857) does not matter here.

Not claimed here

#

Eight Cyrillic descender letters added to Unicode after the 2004 draft (GHE, PE, SHHA and EL WITH DESCENDER, small and capital) keep their descender (the capitals are only case-folded). That is a separate completeness gap with a different fix (missing lines, not a wrong one).

Exposure and likelihood197 words
  • Who is exposed. Analysis chains with ICUFoldingFilter: built by hand, with CustomAnalyzer or the icuFolding SPI name, or through a downstream product that wraps the filter. No Lucene analyzer adds it by default. The default normalizer is enough; no option is involved.
  • Which text. Tajik and Abkhaz Cyrillic text: Unicode's NamesList marks U+04B7 "Abkhasian, Tajik". Tajik writes, for example, "Тоҷикистон" (Tajikistan).
  • Effect. Deterministic for every token with ҷ/Ҷ, which folds to ҽ; what a search then gets wrong depends on the query: one typed with plain ч (for example on a keyboard layout without Tajik letters) does not match the indexed term, so the document is missed; in Abkhaz text a word with ҷ and the same word with ҽ become one term, so they match each other. No exception, no index damage, nothing in the logs; the exact spelling still matches itself.
  • How likely. Rare for most indexes, because the text must be Tajik or Abkhaz, but systematic for a Tajik-language search application. No public report was found (see Prior reports), although the line has shipped since 3.1.0 (2011).
  • Fixing it changes indexed terms: fields that contain ҷ/Ҷ need a reindex after the fix.

Why it is a bug, not intended

#
  • The javadoc lists "Diacritic removal (including stroke, hook, descender)"; the block's own comment says "decompose here".
  • The other WITH DESCENDER and WITH STROKE lines keep the base letter, such as 04B9>0447 (ҹ to ч); ABKHASIAN CHE is a separate letter.
  • The 2004 draft it copies contradicts itself (Ҹ to Ҽ, ҹ to ч); Lucene already departs from it for Ҹ.
The full argument283 words
  • Contract. ICUFoldingFilter.java:33: "Diacritic removal (including stroke, hook, descender)". The module overview: search term folding "removes distinctions (such as accent marks) between similar characters".
  • The block's stated purpose. "Cyrillic script \"composed\" that do not further decompose, so decompose here" (DiacriticFolding.txt:597). ABKHASIAN CHE is not a decomposition of CHE WITH DESCENDER: the Unicode name gives the base letter CHE, and the Unicode 1.0 names were "CHE WITH RIGHT DESCENDER" for U+04B7 and "IE HOOK" for U+04BD.
  • The siblings. Every other WITH DESCENDER or WITH STROKE line of the block keeps the base letter of the character's name, including CHE WITH VERTICAL STROKE (:619, to ч) and ABKHASIAN CHE WITH DESCENDER (:620, to ABKHASIAN CHE); the only other line that sends a different letter to ABKHASIAN CHE is :625 (KHAKASSIAN CHE, same origin).
  • The copied source is inconsistent and withdrawn. The UTR#30 draft data ("DRAFT 1 - 2004-07-14 ... Subject to change") maps capital Ҹ U+04B8 to ABKHASIAN CHE but small ҹ U+04B9 to CHE. Lucene copied only the small-letter lines, so it already folds Ҹ to ч, not to ҽ. The report defines diacritic removal as mapping to "related base characters", so that users can "search for words with accented characters in them by supplying the equivalent word spelled in base letters only"; the Unicode site lists the draft as withdrawn.
  • No test or decision records it. No upstream test asserts any Cyrillic folding, and no javadoc, CHANGES or MIGRATE entry or issue discusses ҷ. LUCENE-1343 (#2420), which added the table, lists five intended differences from ASCIIFoldingFilter, none Cyrillic. In LUCENE-10238 (#11274) the verbatim sections are called "basically hacks" and edited: maintained data, not a frozen copy.
The devil's-advocate check247 words

The strongest case for "intended": the block says "These are from UTR#30 DiacriticFolding.txt" and "Rule: verbatim", and line 618 has the same mapping as the draft (which maps both U+04B6 and U+04B7 to U+04BC). The javadoc names a category, not a promise per character; eight newer Cyrillic descender letters keep their descender. ҷ is a letter of its own in Tajik, so a maintainer may prefer not to fold it, and any change forces a reindex.

Why it fails: Lucene does not reproduce the draft anyway (it differs for Ҹ, and the draft maps a case pair to two different letters); the block's stated job is to decompose, and the target is a third letter that Abkhaz uses next to ҷ, which no reading of "descender removal" yields. "Do not fold ҷ" is a fair position, so the issue should leave it open and argue only that if ҷ is folded, it must fold to ч, like its siblings. No current normative Unicode source mandates U+0447 (UTR#30 is a withdrawn draft), so do not claim one; ask the maintainers to choose between ч and not folding ҷ, since either removes the merge with ҽ. Reindexing is the normal cost of a change to this data; every ICU upgrade regenerates utr30.nrm. Framing note from the independent reproducer: a plain-ч query would also miss ҷ if ҷ were left unfolded, so the distinctive harm of today's line is the merge with ҽ and the break from its siblings.

Workaround for users today

#

Map ҷ to ч and Ҷ to Ч before the filter (for example with a MappingCharFilter), or exclude them with the factory's filter argument (a UnicodeSet of the characters to fold). Not run.

Trade-offs

Both change indexed terms too, so they also need a reindex; with filter, the excluded letters are not case-folded either. The filter route only removes the merge with ҽ: a plain-ч query still misses, as with not folding ҷ; only the char-filter mapping fixes that.

How it was found

#

An exhaustive check compared, for each of the 1,467 Unicode letters named "<base> WITH ..." whose base letter exists, the filter's output with the fold of the base letter, 5 fold to a different base letter, and for 2 of them, CHE WITH DESCENDER (U+04B6/U+04B7), the wrong mapping comes from one of Lucene's hand-written lines.

The method in full243 words

Method: bounded-exhaustive translation validation of the folding data (semi-formal tier), in a hunt unit that checked the UTR#30 verbatim tables against Unicode character names and the compiled .nrm.

  • An independent model of the source tables (gennorm2's precedence by sorted file name, recursive mapping, canonical reordering) agreed with the shipped utr30.nrm and with gennorm2's own combined output on all 1,114,112 code points (0 mismatches); a mutation of lines 618 and 625 in the model was flagged at exactly the affected code points (U+04B7 and U+04CC in the raw mapping; U+04B6, U+04B7, U+04CB and U+04CC after recursion), and a gennorm2 rebuild of the unchanged sources is byte-identical to the shipped file.
  • A name oracle (ICU4J 78.3, Unicode 17) took the 1,467 letters named "<base> WITH ..." whose base letter exists: 1,050 fold to the base letter's fold, 355 are left unfolded, 57 give the base plus something, and 5 fold to a wrong base letter. Two of the five are U+04B6/U+04B7, from line 618; the other three (U+06C0 and two presentation forms) follow Unicode's own canonical decomposition of U+06C0 into U+06D5 plus hamza above (Lucene's line 637 then removes the hamza as a diacritic), not a wrong Lucene line.
  • The finding was reduced to a public-API JUnit and checked by an independent reproducer, reading-only reviews by a model from another family (OpenAI GPT-5.6), an intended-behaviour devil's advocate, an adjudication, a history, prior-report and security follow-up, and an audit. Bug record

LFV-855, snapshot of 2026-10-29

Registry title
ICUFoldingFilter folds the Tajik/Abkhaz letter CHE WITH DESCENDER (ҷ U+04B7, Ҷ U+04B6) to the different letter ABKHASIAN CHE (ҽ U+04BD) instead of to CHE (ч U+0447), so Tajik text is not found by the same words typed with plain ч
Area
analysis / icu (ICUFoldingFilter UTR#30 folding data: the hand-written 'Rule: verbatim' Cyrillic block of DiacriticFolding.txt, compiled into utr30.nrm)
Priority
Medium, rank 151: ICUFoldingFilter's default configuration has silently folded the Tajik/Abkhaz letter ҷ to a different letter in every release since 3.1.0, and fixing it needs a reindex, but analysis-icu is opt-in and little text is in these languages.
Impact class
silent wrong results
Impact note
Applications that use the optional analysis-icu ICUFoldingFilter or ICUFoldingFilterFactory (its default normalizer, no setting needed) and index Tajik or Abkhaz Cyrillic text silently miss documents with ҷ/Ҷ when the query spells the word with plain ч ('Чумхурии Точикистон' does not find 'Ҷумҳурии Тоҷикистон'), and in Abkhaz text the three separate letters ҷ, ҽ and ҿ match each other; the exact spelling still matches itself, nothing throws, no scale is needed, every release from 3.1.0 to 10.5.2, branch_10_6 (10.6.0) and main are affected, and a fix changes indexed terms, so affected fields need a reindex.
Summary
You index Tajik text such as 'Ҷумҳурии Тоҷикистон' with ICUFoldingFilter, whose javadoc lists 'Diacritic removal (including stroke, hook, descender)', and expect the same words typed without the Tajik letters, 'Чумхурии Точикистон', to find it, as they do for ҳ, қ and the other WITH DESCENDER letters. Instead the hand-copied line '04B7>04BC' in DiacriticFolding.txt maps CHE WITH DESCENDER to ABKHASIAN CHE, so ҷ and Ҷ are indexed as ҽ while the query's ч stays ч, and the query gets 0 hits. In Abkhaz, which uses ҷ, ҽ and ҿ as three separate letters, all three fold to ҽ and match each other.
