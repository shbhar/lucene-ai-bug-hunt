Merges on commit and getReader never call the merge policy's OneMerge#mergeInit

When commit() or getReader merges small segments (default since 9.3.0), IndexWriter wraps the policy's OneMerge and forwards mergeFinished but not mergeInit. A subclass that overrides mergeInit is told a merge finished, never that it started (in the repro: mergeInit 0 calls, mergeFinished 1); stock Lucene is unaffected.

The finding in 30 seconds

#

Background: merge hooks and merges on commit

#
  1. A merge policy describes each merge as a MergePolicy.OneMerge. A subclass can override public hooks that IndexWriter calls, among them mergeInit when the merge starts and mergeFinished when it is done.
  2. Since 8.6.0, commit() (and since 8.7.0 getReader) can merge small segments before it returns, using MergePolicy#findFullFlushMerges; by default that method returns the policy's ordinary findMerges merges below a size limit. Since 9.3.0 this is on by default: wait up to 500 ms.
  3. For these merges IndexWriter does not run the policy's OneMerge itself: it wraps it in its own OneMerge, which swaps the merged segment into the commit or reader being opened.

The finding, step by step

#
  1. Write a merge policy whose OneMerge subclass overrides the public hooks mergeInit ("the merge started") and mergeFinished ("the merge is done"), for example to time each merge. Keep the default IndexWriterConfig: since 9.3.0 commit() waits up to 500 ms for small merges the policy returns.
  2. Add one document and commit, then add another and commit. The second commit merges the 2 one-document segments into 1 before it returns.
  3. You expect the policy's OneMerge to get mergeInit once and mergeFinished once, as the same class does when it comes from findMerges or forceMerge.
  4. Instead it gets mergeFinished(success=true) once and mergeInit 0 times. For this merge IndexWriter runs its own wrapper OneMerge, which passes mergeFinished and four other hooks on to the policy's merge, but not mergeInit.
  5. The merge itself is fine: the commit has 1 segment. A merge on DirectoryReader.open(writer) behaves the same. Every release from 8.6.0 to 10.6.0 and main is affected; nothing in Lucene overrides mergeInit.

Who is affected

#

Only code with its own OneMerge subclass that overrides mergeInit, for merges inside commit(), prepareCommit() or getReader (on by default since 9.3.0, reached even through a plain findMerges customisation of LogMergePolicy or TieredMergePolicy). It then misses mergeInit on every such merge, deterministically. Nothing in Lucene overrides mergeInit, so stock Lucene, merged segments and search results are unaffected.

Mechanism, terms and numbers718 words

Since 8.6.0, commit() and, since 8.7.0, getReader can merge small segments before they return, using the merges the policy returns from findFullFlushMerges; since 9.3.0 this is on by default with a 500 ms wait. For these merges IndexWriter wraps each policy OneMerge in an anonymous OneMerge (IndexWriter.preparePointInTimeMerge) and runs only the wrapper. The wrapper forwards mergeFinished, onMergeComplete, wrapForMerge, reorder and setMergeInfo to the policy's merge, but has no mergeInit override. So a policy's OneMerge that overrides mergeInit gets mergeFinished with no mergeInit before it on every such merge: mergeFinished(true, false) for a merge that ran and was committed, as in the repro; the same class from findMerges or forceMerge gets both. A policy does not have to override findFullFlushMerges: the default returns its own findMerges merges below maxFullFlushMergeSize(), a limit that LogMergePolicy and TieredMergePolicy set (the base MergePolicy returns 0). Stock Lucene shows no effect, because the skipped default only records the merge thread and nothing in Lucene overrides mergeInit. Main and every release from 8.6.0 to 10.6.0 fail the repro (ported for 8.6.0-9.0.0, 9.1 and 9.2); a 6-line forward fixes it. Low priority.

Terms

#
  • OneMerge hooks: MergePolicy.OneMerge is public (@lucene.experimental). mergeInit() is "Called by IndexWriter after the merge started and from the thread that will be executing the merge"; mergeFinished(success, segmentDropped) is "Called by IndexWriter after the merge is done and all readers have been closed" (MergePolicy.java:268-282).
  • Merge on commit / getReader ("full-flush merges"): findFullFlushMerges (MergePolicy.java:664-714) and IndexWriterConfig#setMaxFullFlushMergeWaitMillis, default DEFAULT_MAX_FULL_FLUSH_MERGE_WAIT_MILLIS = 500 (IndexWriterConfig.java:108).

The bug

#
  1. commit() calls preparePointInTimeMerge(..., MergeTrigger.COMMIT, ...) when the wait is above 0 (IndexWriter.java:3858-3864); getReader calls it with GET_READER (:634-638).
  2. preparePointInTimeMerge (:3950-4110) runs the configured policy through a OneMergeWrappingMergePolicy whose function replaces every merge with new MergePolicy.OneMerge(toWrap) { ... } (:3959-3964). IndexWriter registers and runs only that wrapper.
  3. The wrapper forwards toWrap.mergeFinished (:4027), toWrap.onMergeComplete (:4043), toWrap.wrapForMerge and toWrap.reorder (both commented // must delegate, :4061, :4067) and toWrap.setMergeInfo (:4073). It has no mergeInit override.
  4. IndexWriter.merge -> mergeInit(merge) (:5075) -> _mergeInit -> merge.mergeInit() on the wrapper (:5289). The base method only records the merge thread in the wrapper's own progress object (MergePolicy.java:272-274; the wrapping constructor creates a fresh one, :259-266).
  5. When the merge closes, OneMerge.close calls the wrapper's mergeFinished (MergePolicy.java:285-293), which passes its arguments on as toWrap.mergeFinished(committed, segmentDropped) (:4027); for the repro's merge that is (true, false).

The numbers (the repro)

#

Two commits of one empty document each, with a policy whose findFullFlushMerges returns one counting OneMerge over both segments. After the second commit the commit point has 1 segment and the policy's OneMerge has mergeFinished = 1 and mergeInit = 0. The same counting class handed out by findMerges (an explicit maybeMerge()) or findForcedMerges gets 1 and 1.

Variants that behave the same

#
  • A merge on DirectoryReader.open(writer) (GET_READER), and a merge on commit with the default ConcurrentMergeScheduler: events [finished:true:false] instead of [init, finished:true:false], 10 of 10 iterations each.
  • A policy that overrides only findMerges on a stock LogDocMergePolicy, default settings: the default findFullFlushMerges returns the same objects, which get init=0 finished=1. (The default keeps merges whose segments are below maxFullFlushMergeSize(): minMergeSize in LogMergePolicy, floorSegmentBytes in TieredMergePolicy, 0 in the base MergePolicy, MergePolicy.java:730-736.)

Not claimed

#

IndexWriter does not always pair the two hooks: on rollback, merges that never started get mergeFinished(false, false) without mergeInit (IndexWriter.java:2821-2834, :5133-5136, :5394-5403), which the javadoc allows. Only the success case on this path is the bug. The repro's merge succeeds and keeps its segment, so it gets mergeFinished(true, false); a merge that fails or whose segment is dropped would get success=false or segmentDropped=true, also without mergeInit (code reading). An application can create the same asymmetry on any path with its own code, by installing a OneMergeWrappingMergePolicy whose wrapper forwards mergeFinished but not mergeInit; IndexWriter's other paths run the policy's own merge. By code reading only (untested): because the wrapper has its own progress object, the policy's OneMerge also never sees isAborted() == true, and IndexWriter sets the merge byte counts on the wrapper.

Exposure and likelihood210 words
  • Who is exposed. Applications or libraries whose merge policy hands out a OneMerge subclass that overrides mergeInit, for merges that run inside commit(), prepareCommit() or getReader / DirectoryReader.open(writer). On by default since 9.3.0; opt-in (a full-flush wait above 0) in 8.6.0-9.2.x.
  • What they see. mergeFinished with no mergeInit before it, on every such merge; for a merge that succeeds and keeps its segment, as in the repro, that is mergeFinished(true, false). Anything paired across the two hooks gets out of step: a timer never started, a per-merge resource released without being taken, a running-merge counter that goes negative. What follows is defined by that code, not by Lucene.
  • Scale. None needed: two one-document segments, every time, assertions on and off.
  • Stock Lucene. No observable effect. The skipped base method only writes the private field OneMergeProgress.owner, "for sanity-check purposes only" (MergePolicy.java:106-111), which no code reads except an assert in its own setter, and no class in Lucene overrides mergeInit (at 645d4fe14a20). Merged content, deletes, search results, aborting the running merge and the commit wait bound are unaffected (code reading).
  • How likely. Rare: GitHub code searches found no mergeInit override in Elasticsearch, OpenSearch or Solr (not exhaustive), and nobody has reported it since 8.6.0.

Why it looks unintended

#
  • mergeInit is public, documented as "Called by IndexWriter after the merge started", with no exception for merges on commit.
  • The wrapper forwards the paired mergeFinished and four other hooks but not mergeInit; no other IndexWriter path reports a successful finish without it.
  • Upstream added the missing setMergeInfo forward to this same wrapper in #12622.
The full argument201 words
  • Contract. mergeInit is public and non-final, documented as "Called by IndexWriter after the merge started and from the thread that will be executing the merge" (MergePolicy.java:268-271). No javadoc, CHANGES or MIGRATE entry exempts full-flush merges.
  • Meant to be used. LUCENE-7700 refactored merge throughput control "into a more accessible set of public methods (see MergePolicy.OneMergeProgress, MergeScheduler.wrapForMerge and OneMerge.mergeInit)" (lucene/CHANGES.txt:8405-8409).
  • The wrapper treats the policy's merge as the real one. It forwards mergeFinished, onMergeComplete, setMergeInfo, wrapForMerge and reorder (IndexWriter.java:4027-4073). IndexWriterConfig.java:482-487 says these merges "will still run to completion independent of the commit or getReader call, like natural segment merges".
  • Precedent on this wrapper. #12622 (9.9.0) added the reorder and setMergeInfo forwards. Asked in review "did we have a test that realized that merge.info is missing?", the author answered "Yes, some of the new tests failed ... Let me add dedicated tests for setMergeInfo."; TestIndexWriterMergePolicy.testSetDiagnostics wraps both findMerges and findFullFlushMerges merges.
  • No documented rationale found. The wrapper never had mergeInit (first version 7f352a96659, #1617); no commit in the history contains toWrap.mergeInit; the design threads that were read never discuss it. That is an absence of evidence, not proof that the omission was unintended.
The devil's-advocate check250 words

The strongest case, built by verifiers and the adjudication: IndexWriter executes the wrapper and does call mergeInit on it, which satisfies "called after the merge started"; the base method touches only the wrapper's own progress object. Other in-tree wrappers forward even less (SoftDeletesRetentionMergePolicy only wrapForMerge, BPReorderingMergePolicy neither mergeInit nor mergeFinished), and open PR #16571 adds a FilterOneMerge that forwards neither, with the note "Wrapping creates a new OneMerge, so any behaviour not forwarded is lost." IndexWriter already sends mergeFinished(false, false) without mergeInit on rollback, OneMerge is experimental, and nobody overrides mergeInit.

Why it does not settle it: those wrappers forward no lifecycle hook at all, so their inner merge sees a consistent, empty lifecycle. This wrapper forwards mergeFinished, onMergeComplete and setMergeInfo, so the policy's merge hears that it finished successfully without hearing that it started, which happens on no other IndexWriter path (an application gets it elsewhere only by installing such a wrapper itself). The user never asked for this wrapper: IndexWriter puts it around every merge the policy returns from findFullFlushMerges, so avoiding it means returning no full-flush merges or turning merge on commit off. The rollback case is a merge that never started, which the javadoc allows. The javadoc does not say whether the hooks reach a merge that IndexWriter wraps, so a maintainer can reasonably prefer to document mergeInit as plumbing of the executing merge instead of forwarding it; that remedy question is what remains open. Verdict (adjudication): confirmed, medium.

Suggested fix

#

Recommended A. Forward mergeInit in the point-in-time wrapper

Forward mergeInit in the wrapper in IndexWriter.preparePointInTimeMerge, as it already forwards mergeFinished: super.mergeInit(); toWrap.mergeInit(); (+6 lines). The repro and 12 related core suites (13 suites, 280 tests, assertions on and off), the whole core index test package (1396 tests) and the core lint pass.

@Override
public void mergeInit() throws IOException {
  super.mergeInit();
  toWrap.mergeInit(); // must delegate
}

A. Forward mergeInit in the point-in-time wrapper (validated by the checks) (recommended)

#

Add a mergeInit override to the anonymous OneMerge in preparePointInTimeMerge that calls the wrapper's own base method and then the policy's, next to the existing // must delegate forwards.

@Override
public void mergeInit() throws IOException {
  super.mergeInit();
  toWrap.mergeInit(); // must delegate
}

Trade-offs

  • The policy's mergeInit then runs exactly where it runs for natural merges: inside _mergeInit, under IndexWriter's lock, on the merge thread. If it throws, IndexWriter handles it as for a natural merge: mergeInit(merge) runs its internal mergeFinish(merge) bookkeeping (not OneMerge#mergeFinished) and rethrows (IndexWriter.java:5261-5269); what the policy's merge sees after its own mergeInit throws was not tested.
  • With assertions on, setMergeThread's assert this.owner == null holds for the policy's merge, which has its own progress object.
  • It does not share the two progress objects, so the untested isAborted point stays.
  • Open PR #16571 rewrites the same wrapper on top of a new FilterOneMerge; the same override fits there.

B. Document the behaviour instead (not run)

#

Say in OneMerge#mergeInit and findFullFlushMerges that for merges on commit and getReader IndexWriter runs its own wrapper and forwards only mergeFinished, onMergeComplete, setMergeInfo, wrapForMerge and reorder.

Trade-offs

No behaviour change and cheap, but a successful mergeFinished without mergeInit stays on one path, so every policy author has to handle it.

C. Forward mergeInit and share the progress object (not run)

#

Let the wrapper use the policy merge's OneMergeProgress (a new protected constructor), so abort and pause state are shared as well.

Trade-offs

Also covers the untested isAborted point, but changes the experimental wrapping constructor's semantics; a larger review.

D. Forward lifecycle hooks in #16571's FilterOneMerge (not run)

#

Only if that PR lands: add mergeInit (and mergeFinished) to FilterOneMerge.

Trade-offs

Changes every wrapper built on FilterOneMerge, including ones that today forward no lifecycle hook; option A on the rewritten wrapper is narrower.

Downstream note

#

A code search of Elasticsearch, OpenSearch and Solr found no OneMerge subclass that overrides mergeInit, so only custom merge-policy code in applications or other libraries is exposed.

How it was found

#

A static scan of the compiled Lucene jars listed, for every OneMerge wrapper, which overridable hooks it forwards to the merge it wraps. For IndexWriter's merge-on-commit wrapper it showed mergeFinished, onMergeComplete, wrapForMerge, reorder and setMergeInfo forwarded and mergeInit not; a JUnit test on the stock jars then showed the effect. Semi-formal.

The method in full148 words

Method: a bytecode delegation scan, then JUnit (the hunt's "semi-formal" tier).

  • A hunt unit (merge-policy hooks) extended an earlier unit's delegation-completeness scanner (MergeHookScan.java, JDK 25 java.lang.classfile) to every OneMerge and MergePolicy wrapper and every overridable hook: 6076 classes from 20 module jars, 11 wrappers, 140 matrix rows.
  • It resolves each hook on each wrapper with JVM method selection and records whether the wrapper forwards it to the wrapped object. The gap row IndexWriter$2 mergeInit()V lifecycle/result BASE (the anonymous OneMerge in preparePointInTimeMerge) said that mergeInit resolves to the base default while five sibling hooks forward.
  • Vacuity check: a planted wrapper that drops only mergeInit is flagged and a complete one is not.
  • An exploratory probe and then a public-API JUnit test on the stock jars (merge on commit, merge on getReader, a forceMerge control) confirmed it on main (assertions on and off), 10.5.2 and 9.12.3.

#

Not a regression; no commit on any ref contains toWrap.mergeInit; not fixed on upstream main f815e679bf6c (2026-11-01).

Hits only applications or libraries whose own merge policy hands out a OneMerge subclass that overrides the public mergeInit hook (no class in Lucene does, and none was found in Elasticsearch, OpenSearch or Solr) for a merge that runs inside commit(), prepareCommit() or getReader / DirectoryReader.open(writer): this path is on by default since 9.3.0 (maxFullFlushMergeWaitMillis 500 ms; opt-in in 8.6.0-9.2.x) and is reached even from an ordinary findMerges customisation under a stock LogDocMergePolicy, because the default findFullFlushMerges returns findMerges' OneMerge objects; such a OneMerge then gets mergeFinished(success=true) with no mergeInit before it on every such merge, with -ea and -da and no scale; on stock Lucene nothing observable changes (the skipped default only records the merge thread in a field no code reads), and merged content, deletes, search results, aborting the running merge and the commit wait bound are unaffected.
Summary
You install a merge policy whose OneMerge subclass overrides the public mergeInit hook (for example to start a timer or set up per-merge state that mergeFinished later releases) and let IndexWriter merge on commit or on getReader, which it does by default since 9.3.0. You expect that OneMerge to get mergeInit when the merge starts and mergeFinished when it ends, as the same OneMerge does when it comes from findMerges or forceMerge. Instead IndexWriter wraps the policy's merge in its own OneMerge that forwards mergeFinished and the other hooks but not mergeInit, so the policy's OneMerge sees mergeFinished(success=true) for a merge that ran and committed and never sees mergeInit (in the repro: mergeInit=0, mergeFinished=1 for the merge on commit and on getReader; 1 and 1 for forceMerge).
Introduced
7f352a96659b4d304ae3ef0c7a1b62784ce2a406 (main) and its branch_8x backport 9b1c92809e7 (shipped in 8.6.0): apache/lucene-solr#1617, LUCENE-8962 'Merge small segments on commit' (GitHub issue #10005; author s1monw, co-authors msfroh, msokolov and mikemccand; merged 2020-06-27), which created the wrapper new MergePolicy.OneMerge(toWrap.segments) with mergeFinished and wrapForMerge forwarding ('// must delegate') and no mergeInit override [read: git log -S/-G/-L and git blame in the full-history clone; exec: 8.5.2 has no findFullFlushMerges (compile error) and its pre-feature control passes, 8.6.0 fails]. The defect was there when the wrapper was created, not a later regression: OneMerge#mergeInit had been public since LUCENE-7700 (9540bc37583, 2017, first released 6.5.0 / 7.0.0). Two earlier merge-on-commit attempts were reverted before any release (043c5dff6f4 #1155, whose wrapper forwarded no hook; 972c84022ec #1552, same shape as #1617). Later changes kept the gap: 8294e1ae206 (#1623, 8.7.0) reused the wrapper for getReader as preparePointInTimeMerge and added onMergeComplete forwarding; b5795db0cf5 (LUCENE-10078, 9.3.0) made the full-flush wait 500 ms by default; f7cab164501 (#12622, 9.9.0) switched to the wrapping constructor and added reorder ('// must delegate') and setMergeInfo forwarding; no commit on main or branch_8x has ever contained toWrap.mergeInit (git log -G) (2020-06-27)
