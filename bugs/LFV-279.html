SpanNotQuery with a negative post (or dist) drops every include span after the one that uses up a document's exclude spans, because NO_MORE_POSITIONS - post overflows int

SpanNotQuery with a negative post or dist (documented as allowed overlap) drops every include span after the one that uses up a document's exclude spans: on "b a c", spanNot(a, b, 0, -1) returns 1 of its 2 spans, and nested in spanNear the document is missed.

The bug in 30 seconds

#

SpanNotQuery walks a document's include spans in order, with a cursor on its exclude spans. When the cursor runs past the last exclude span it stays on the document reading NO_MORE_POSITIONS (Integer.MAX_VALUE), and the next check, excludeSpans.startPosition() - post >= candidate.endPosition(), overflows for any negative post.

  1. You index "b a c" (b at 0, a at 1 and 2, c at 3) and run new SpanNotQuery(a, b, 0, -1): keep each "a" that no "b" overlaps, where the negative post is documented to allow some overlap.
  2. You expect both "a" spans, [1,2) and [2,3), exactly what post = 0 returns: the only "b" is at 0 and touches neither "a".
  3. Checking the first "a" moves the exclude cursor past the last "b", where it reads NO_MORE_POSITIONS = 2147483647. For the second "a" the code computes 2147483647 - (-1), which wraps to -2147483648; -2147483648 >= 3 is false, so that "a" is rejected.
  4. You get only [1,2). Nested as spanNear([spanNot(a, b, 0, -1), c], 0, true) ("a" right before "c"), the document no longer matches: 0 hits instead of 1.
  5. new SpanNotQuery(a, b, -1) (dist) fails the same way, and adding another "b" at the end ("b a c b") brings the dropped span back.

Who is affected

#

Java code that builds SpanNotQuery with a negative post or dist, whenever a document has an exclude match before two or more include matches and none after. With ordinary negative values a top-level query keeps its hits but loses spans and score; nested in spanNear or spanPositionRange it loses documents. Lucene's parsers pass 0.

Mechanism, terms and numbers750 words

SpanNotQuery(include, exclude, pre, post) keeps the include spans that no exclude span overlaps within pre tokens before or post tokens after, and its javadoc says negative values "allow a certain amount of overlap to occur". Read as a window, a negative post can only keep more spans than post = 0. In fact it keeps fewer: once checking one include span has moved the exclude cursor past the document's last exclude span, the cursor reads NO_MORE_POSITIONS (Integer.MAX_VALUE), and for every later include span SpanNotQuery.java:210 computes excludeSpans.startPosition() - post, which wraps to a negative int for any post < 0. On "b a c", spanNot(a, b, 0, -1) returns [1,2) instead of [1,2), [2,3), and spanNear([spanNot(a, b, 0, -1), c], 0, true) no longer matches. With ordinary negative values a top-level SpanNotQuery keeps its document set but loses spans and score; nested in a positional query it loses documents. The line came from LUCENE-8034 (7.2.0), which fixed the opposite overflow for a huge positive post; every release from 7.2.0 to 10.5.2 and main is affected. Lucene's query parsers always pass 0 and cannot reach it.

Terms

#
  • Span: a match of a span query inside one document, written [start,end) in token positions. In "b a c" the term "a" has the spans [1,2) and [2,3).
  • SpanNotQuery(include, exclude, pre, post): keeps the include spans that no exclude span overlaps within pre tokens before or post tokens after. A negative post (or dist, which sets both) allows that much overlap (SpanNotQuery.java:51-66), so, read as a window, it can only keep more.
  • NO_MORE_POSITIONS: Integer.MAX_VALUE (Spans.java:32). After the last span of the current document, a Spans iterator's startPosition() and endPosition() return it (Spans.java:34-51).

The bug

#

SpanNotWeight#getSpans wraps the include spans in a FilterSpans whose accept(candidate) runs once per include span, in position order (SpanNotQuery.java:166-216 on main a9779ef3c193):

  1. It catches the exclude cursor up to the candidate's document and, if the cursor has not yet started in this document, moves it to its first span (:175-200).
  2. It skips exclude spans that end before the candidate starts (:202-207). If that runs out of exclude spans, it accepts the candidate: return AcceptStatus.YES; // no more exclude at current doc. (:205). The cursor stays on the document, now reading NO_MORE_POSITIONS.
  3. Otherwise it checks the next exclude span's start: if (excludeSpans.startPosition() - post >= candidate.endPosition()) return YES; else return NO; (:210-214).
  4. For the next include span of the same document, step 2 does nothing (2147483647 <= candidate.startPosition() - pre is false for any ordinary pre) and step 3 computes 2147483647 - post. With post = 0 that is 2147483647 and the span is kept; with post = -1 it is 2^31, which wraps to -2147483648, and -2147483648 >= 3 is false: rejected. Every negative post wraps, because indexed positions are at most Integer.MAX_VALUE - 128 (IndexWriter.java:211).
  5. FilterSpans then asks for the next include span (FilterSpans.java:83-96), which is rejected the same way: every later include span of the document is gone. The next document starts fresh.

The wrap can only reject, never accept, and the include span that used up the exclude spans is itself accepted, so with ordinary negative values a top-level SpanNotQuery keeps its document set. The trigger is a negative post: in a bounded enumeration with pre and post in -2..2, a negative pre with post >= 0 gave 0 mismatches. Windows of about 2^31 tokens hit related corners: post = Integer.MAX_VALUE compares against the sentinel without wrapping and drops the same span, and post = Integer.MIN_VALUE also wraps on real positions, where even a top-level document is lost.

The numbers

#

On "b a c": spanNot(a, b, 0, 0) gives [1,2), [2,3); spanNot(a, b, 0, -1) and new SpanNotQuery(a, b, -1) give [1,2); spanNear([spanNot(a, b, 0, -1), c], 0, true) counts 0 instead of 1. On "b a c b" the same query gives both spans. On "x y y y y y", spanNot(y, x, 0, post) keeps 1 of 5 "y" for post -1, -2 and -3 and all 5 for 0 and 1. A two-phase exclude (spanNear([b, x], 0, true)) is affected too. Every document over {a, b} of 1 to 5 tokens, pre and post in -2..2: 260 mismatches in 6,450 include-span checks, all with post < 0 after the exclude spans were used up.

Exposure and likelihood297 words
  • Who. Java code that calls the 4-argument constructor with post < 0 or the 3-argument constructor with dist < 0, both documented as allowed overlap (SpanNotQuery.java:51-66); rewrite keeps the values (:230). Default codec, IndexWriterConfig and searcher (the executed main() port) and randomized test codecs (the JUnits), assertions on or off, any index size.
  • When. A document has an exclude match before two or more include matches and no exclude match after the include match that uses them up. Ordinary text does this.
  • Top-level query (ordinary negative values). The same documents match, but spans, Matches positions, span frequency and scores are wrong: in one probe 11 of 57 documents score lower with 57 = 57 hits; in another "b a c" scores 0.053059246 instead of 0.070576414 with 4 = 4 hits; Matches reports 1 position instead of 2.
  • Nested query. In spanNear or spanPositionRange, whole documents stop matching (executed).
  • Under a negation. A MUST_NOT over spanNear([spanNot(a, b, 0, -1), c], 0, true) keeps "b a c" ([0, 1] instead of [1]); the same with dist = -1; spanNot(a, spanNot(a, b, 0, -1)) returns [0] instead of [] (executed on main, 10.5.2 and 9.12.3; all pass with the fix).
  • Highlighting. WeightedSpanTermExtractor iterates the same spans, so the span highlighter would mark fewer occurrences (read, not executed).
  • Not reachable through Lucene's query parsers: the XML SpanNotBuilder and ComplexPhraseQueryParser use the 2-argument constructor (SpanNotBuilder.java:45, ComplexPhraseQueryParser.java:359, 417).
  • Cost. Deterministic, per document; no hang or resource blow-up was observed: the filter stays linear and emits fewer spans (one "b" then 50,000 "a": 1 span, milliseconds).
  • Why the tests miss it. No deterministic upstream negative-window test has an include span after the exclude spans are used up (the randomized TestSpanSearchEquivalence uses the 2-argument constructor).

Why it is a bug, not intended

#
  • Read as a window, as LUCENE-7431's tests do, the javadoc's allowed overlap means post = -1 keeps every span post = 0 keeps.
  • An extra "b" after both "a"s ("b a c b") brings the dropped span back.
  • Until 7.1.0 the check was an addition that handles negative post; LUCENE-8034 (7.2.0) rewrote it for a huge positive post.
The full argument252 words
  • The contract. SpanNotQuery.java:51-56 (3-argument): "matching spans from include which have no overlap with spans from exclude within dist tokens of include. Inversely, a negative dist value may be used to specify a certain amount of allowable overlap." :61-66 (4-argument): "... within pre tokens before or post tokens of include. Inversely, negative values for pre and/or post allow a certain amount of overlap to occur."
  • A deliberate feature. lucene/CHANGES.txt:8710-8712 (6.4.0): "LUCENE-7431: Allow a certain amount of overlap to be specified between the include and exclude arguments of SpanNotQuery via negative pre and/or post arguments." That change removed the earlier clamping of negative values to 0.
  • Lucene's own tests use it. TestBasics#testSpanNotWindowNegPost (TestBasics.java:331-352) asserts that post = -1 keeps the 16 hits that testSpanWithMultipleNotSingle (:244) asserts for post = 0, and that post = -2 adds two more; testSpanNotWindowNegPre (:354-375) does the same for pre (-2 keeps the 16, -3 adds the two).
  • History. Until 7.1.0 the check was candidate.endPosition() + post <= excludeSpans.startPosition(), correct for any post <= 0; 7.1.0 returns both spans (executed). LUCENE-8034 (#9082) turned it into the subtraction only to fix an overflow for a huge positive post; its discussion never mentions negative post, and its test uses pre = post = Integer.MAX_VALUE (TestBasics.java:232).
  • Order dependence. The same include span is kept or dropped depending on whether an earlier include span used up the exclude spans, and an extra exclude match after it restores it.
The devil's-advocate check188 words

The strongest works-as-designed case, from the intended-behaviour verifier, a reviewer from another model family (OpenAI GPT-5.6) and the adjudication: testSpanNotWindowNegPost carries the comment "test handling of invalid window < 0" (TestBasics.java:332), so negative windows might be invalid input; SpanNotWeight is @lucene.internal (SpanNotQuery.java:125); no javadoc says what happens after the exclude spans run out; and no bundled parser can produce the trigger.

Why it fails: the comment predates LUCENE-7431, when the test was testSpanNotWindowNeg and the constructor clamped negative values to 0; LUCENE-7431 renamed the test and made it assert that negative windows widen the hits, but kept the comment. The constructors are public and documented; only the weight is internal. Under the window reading that LUCENE-7431's tests assert, the javadoc is monotone (a more negative post never removes spans), and Spans documents the sentinel that accept itself reads. A documented input that only Java callers can pass is still a legitimate trigger. Every verifier and the adjudication rejected the intended argument; the cross-model reviews rated it weak. Open issue #16820 proposes deprecating span queries, which could argue for won't-fix but not for intended behaviour.

Recommended Accept once the exclude spans are used up, and compare in long

Trade-offs

  • One int comparison for each include candidate that gets past the document check at :194-196, whether it is then accepted or rejected; no benchmark run.
  • The check makes the result independent of post once the exclude spans of the document are used up, including post = Integer.MAX_VALUE; the long comparison keeps LUCENE-8034's protection for a huge positive post and also covers a huge negative post on real positions.
  • Not covered and not examined: the loop condition at :202 still computes candidate.startPosition() - pre in int, so an extreme negative pre (about -2^31) is not made safe.

Downstream note

#

Downstream, the Elasticsearch and OpenSearch span_not builders clamp negative pre and post to 0 (read in their source, not run), so only an application's own Java code can build the trigger; one that nests such a query under MUST_NOT removes fewer documents than the rule says (executed probe).

How it was found

#

Bounded-exhaustive translation validation on the stock jars: every document of up to 3 positions over {a, b, c}, with pre and post in -1..1 over 30 child queries, against an exact reference built from the children's own spans and the javadoc. 636 of 510,300 SpanNot checks failed, all with post = -1; reading line 210 then gave the cause.

The method in full168 words

Method: bounded-exhaustive translation validation on the stock jar (semi-formal tier), in a hunt unit on span and interval queries.

  • The harness evaluates the span filters of the real main jars on every document of up to 3 positions over {a, b, c}, with SpanNotQuery pre and post in -1..1 over 30 child queries, and compares each result with an exact reference built from the children's actual Lucene spans and the javadoc semantics.
  • The SpanNot relation failed in 636 of 510,300 checks, all with post = -1, and in 0 of 12,425,400 checks with the unit's fix sketches shadowed onto the jar (larger scopes, run on separate build machines).
  • The root cause was then read from SpanNotQuery.java:210 and reduced to a public-API JUnit. No model checker, SMT solver or prover was involved.
  • Found 2026-10-26 on main ea57360912ed; then checked by an independent reproducer, reviews by a model from another family (OpenAI GPT-5.6), an intended-behaviour devil's advocate, an adjudication, a history and prior-report follow-up, and a credibility audit.

History

#

Introduced by LUCENE-8034 (726ee05240a, 2017-11-22, first release 7.2.0), which turned the correct addition into the subtraction. Executed: 6.4.0 to 7.1.0 pass; 7.2.0, 7.7.3, 8.0.0, 8.11.4, 9.0.0, 9.12.3, 10.0.0, 10.5.2 and main fail. Not fixed upstream.

Versions tested7 rows

Introduced by 726ee05240a65badf6c3499dd1e29daf490a3e48 on master, "LUCENE-8034: use subtraction instead of addition to sidestep int overflow in SpanNotQuery" (a patch attached to the JIRA issue, now #9082, committed by Mike McCandless on 2017-11-22; CHANGES: "(Hari Menon via Mike McCandless)"), backported to branch_7x the same day as 6b328dcd4f9. It replaced candidate.endPosition() + post <= excludeSpans.startPosition(), which is correct for any post <= 0, with excludeSpans.startPosition() - post >= candidate.endPosition(), to fix an overflow for a huge positive post.

Precondition, not the cause: LUCENE-7431 (750da7c5f7a on master, 55ed23168f6 on branch_6x, 2016-11-08, first in 6.4.0 and 7.0.0) removed the clamping of negative pre/post to 0 and documented them as allowed overlap; the addition form was still correct then. The spans moved to the queries module in 9.0.0 without touching the line; SpanNotQuery.java last changed upstream on 2022-10-19 (6cde41c9fd8c), and the line is unchanged on main, branch_10x and branch_10_6. A source scan finds the subtraction in every release tag from 7.2.0 to 10.5.2 (the history clone has no 8.x tags after 8.8.1, so 8.9.0 to 8.11.4 were not scanned; 8.11.4 was executed).

Bug record

LFV-279, snapshot of 2026-10-30

Registry title
SpanNotQuery with a negative post (or dist) drops every include span that follows the last exclude span in a document, because NO_MORE_POSITIONS - post overflows int
Area
queries / span queries (SpanNotQuery: the exclusion filter in SpanNotWeight#getSpans)
Priority
Medium, rank 223: Since 7.2, the documented negative post of a SpanNotQuery drops spans and, once nested, documents.
Impact class
silent wrong results
Impact note
Applications that build a SpanNotQuery in Java with the documented negative post (4-argument constructor) or negative dist (3-argument constructor) get too few spans in every document that has an exclude span before two or more include spans and none after them, with the default codec, IndexWriterConfig and searcher, -ea and -da, at any index size, in every release from 7.2.0 through 10.5.2 and on main: a top-level SpanNotQuery still matches the same documents (the include span that uses up the exclude spans is kept) but reports fewer spans and Matches positions and lower scores (the independent reproduction probe: 11 of 57 documents score lower), and once it is nested in a positional parent such as spanNear or spanPositionRange whole documents stop matching (or, under a MUST_NOT or as the exclude side of another SpanNotQuery, wrongly match); Lucene's bundled query parsers always pass pre = post = 0 and cannot reach it.
Summary
You index the text 'b a c' and run new SpanNotQuery(a, b, 0, -1), whose javadoc says it keeps the 'a' spans that do not overlap a 'b' and that a negative post only allows some overlap; since 'b' at position 0 overlaps neither 'a', you expect both spans [1,2) and [2,3), exactly as with post = 0. Instead you get only [1,2): once the first 'a' has used up the document's exclude spans, the exclude iterator sits at NO_MORE_POSITIONS (Integer.MAX_VALUE) and SpanNotQuery.java:210 computes Integer.MAX_VALUE - post, which wraps to a negative int for any post < 0, so every later 'a' in the document is rejected. Nested as spanNear([spanNot(a, b, 0, -1), c], 0, true), the document no longer matches at all (count 0 instead of 1).
Introduced
726ee05240a65badf6c3499dd1e29daf490a3e48 (master) and its branch_7x backport 6b328dcd4f90f4b61961b1d3a16629b4ae0c3ece, 'LUCENE-8034: use subtraction instead of addition to sidestep int overflow in SpanNotQuery' (issue migrated as apache/lucene#9082; a patch attached to the JIRA issue by JIRA user hshankar, committed by mikemccand; no GitHub PR) [read: git blame and git log -L of SpanNotQuery.java:210 in the full-history clone, no later commit changed the line; exec: 7.1.0 passes, 7.2.0 fails]. It replaced 'candidate.endPosition() + post <= excludeSpans.startPosition()', which is correct for any post <= 0, with 'excludeSpans.startPosition() - post >= candidate.endPosition()', to avoid overflow for a huge positive post. Precondition, not the introducing commit: LUCENE-7431 (750da7c5f7af on master, 55ed23168f6 on branch_6x, 2016-11-08, first released in 6.4.0 and 7.0.0) removed the clamping of negative pre/post to 0 and documented negative values as allowed overlap, which made the trigger legal.
