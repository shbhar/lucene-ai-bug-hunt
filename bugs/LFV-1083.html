A commit() that fails after its pending segments file is synced makes rollback() delete the last commit's files

If the InfoStream throws on the "done all syncs" line of commit(), the commit fails but the writer stays open; the documented recovery, rollback(), then deletes the files of the previous good commit and the index can no longer be opened. Every release since 4.8.0; a 7-line fix is validated.

The finding in 30 seconds

#

commit() protects the new commit's files with one extra reference each, writes pending_segments_N, fsyncs, then logs "done all syncs". A failed fsync is undone; a throw from that log line is not. The commit's cleanup releases the reference, but the half-finished commit stays pending, so rollback() releases it again.

How a commit protects its files, in one minute

#
  1. IndexFileDeleter counts references to every index file: one for each commit point that lists it, one for the writer's current segments, and extra ones a running commit takes. A file whose count reaches 0 is deleted.
  2. commit() first prepares: it takes one extra reference on every file of the new commit, writes pending_segments_N (not yet visible to readers) and fsyncs the files. From then on the extra reference belongs to the pending commit.
  3. Then it finishes: it renames pending_segments_N to segments_N and releases the extra reference. rollback() instead deletes pending_segments_N and releases it. Either way it is released exactly once.

The finding, step by step

#
  1. Give IndexWriterConfig an InfoStream that throws one RuntimeException, on the message starting "done all syncs". Add 1 empty document and commit(): the index is segments_1 plus segment _0 (_0.cfe, _0.cfs, _0.si).
  2. Add 1 more document and commit() again. Lucene writes segment _1 and pending_segments_2, syncs the 6 segment files (Directory.sync) and logs "done all syncs"; the InfoStream throws. commit() fails, isOpen() is true, getTragicException() is null.
  3. You call rollback() and expect its promise: the index as it was at the last commit, segments_1 with 1 document.
  4. Instead rollback() deletes _1.* and then _0.cfe, _0.si and _0.cfs; only segments_1 is left, and DirectoryReader.open fails with NoSuchFileException: _0.si. close() with commitOnClose=false does the same.
  5. Why: the commit took one extra reference on each of its files, and after the failure it is released twice, by the commit's cleanup and again by rollback(), so _0's files lose the reference segments_1 holds. With assertions on, rollback() throws RefCount is 0 pre-decrement instead.

Who is affected

#

Applications that install their own InfoStream (off by default) whose message() can throw a RuntimeException, and that recover from the failed commit with rollback() or close() with commitOnClose=false. One committed document is enough, in memory or on disk. The last commit's files are deleted, so its data is gone unless there is a backup.

Mechanism, terms and numbers925 words

commit() takes one extra reference on every file of the new commit (IndexWriter.java:3857), then startCommit writes pending_segments_N and sets pendingCommitSet = true; pendingCommit = toSync (:5973, :5983-5984): from then on the pending commit owns that reference. After the fsync, still inside the try, it logs "done all syncs" (:6000-6002). If the InfoStream throws there, startCommit's catch releases nothing because pendingCommitSet is true (:6007) and leaves pendingCommit set, prepareCommitInternal's catch releases filesToCommit anyway (:3920-3929), and since the exception is not an Error the writer stays open with no tragic exception. rollback() then releases pendingCommit's files a second time (:2642-2645), so files shared with the last commit lose that commit's reference and the end of rollback() deletes them (:2670-2672): with assertions off the last good commit can no longer be opened; with assertions on rollback() fails on the deleter's RefCount is 0 pre-decrement assertion. Introduced in 4.8.0 by LUCENE-5543; affects every release through 10.6.0 and main. Only an application InfoStream that throws a RuntimeException on that one line reaches it (off by default). Fix: undo the pending commit in startCommit's catch, as a failed fsync already does (7 lines, validated).

Step by step

#
  1. After the first commit each _0.* file has two references: the commit point segments_1 and the writer's current segments (IndexFileDeleter.checkpoint, IndexFileDeleter.java:544-591). Flushing _1 adds the writer's reference on _1.*; prepareCommitInternal adds one more on every file of the new commit, _0.* and _1.* (IndexWriter.java:3857). (These are the repro's counts: with merge-on-commit enabled, preparePointInTimeMerge also moves references, :3993, :4007; the repro does not use it.)
  2. startCommit writes pending_segments_2 and sets pendingCommitSet and pendingCommit (:5973-5984). From here the pending commit holds the extra reference until finishCommit releases it through filesToCommit (:4287-4288) or rollback() through pendingCommit (:2642-2645).
  3. A failing directory.sync resets both fields and deletes the pending file (:5993-5997). The statements after it, the "done all syncs" message (:6000-6002) and testPoint("midStartCommitSuccess") (:6004, a no-op unless test points are enabled, and then it also only calls the InfoStream, :6132-6137), have no such undo. In production only the InfoStream can throw there.
  4. The catch releases filesToCommit only if (!pendingCommitSet) (:6007), so it rethrows with pendingCommit and filesToCommit both still set. Only an Error is tragic (:6031-6033): after a RuntimeException the writer stays open and getTragicException() is null.
  5. prepareCommitInternal's catch sees filesToCommit != null and releases it (:3920-3929): release 1.
  6. rollback() -> rollbackInternalNoCommit deletes pending_segments_2 and releases pendingCommit's files (:2642-2645; IndexFileDeleter.decRef(SegmentInfos) is decRef(files(false)), IndexFileDeleter.java:623-626): release 2 of the same reference. _1.* reach 0 and are deleted (harmless, uncommitted); _0.* are left one reference short.
  7. The checkpoint back to [_0], refresh() and close() (:2670-2672) drop the writer's own references: _0.* reach 0 and are deleted although segments_1 lists them. With assertions on, the checkpoint's release of _1.cfs trips assert count > 0 (FileDeleter.java:276-282) first, so rollback() throws and the old commit survives: not a successful rollback, but a failing one that stops before it deletes _0.*.

A throw before pendingCommitSet = true (for example on the "startCommit: wrote pending segments file" line, :5974-5981) releases the references exactly once: the catch releases filesToCommit and nulls it, and prepareCommitInternal's guard skips its release. That path does not call rollbackCommit, so the pending_segments_N file prepareCommit already wrote is not deleted there (:6005-6018); what happens to it later was not checked and is not part of this bug. An Error at the "done all syncs" line is tragic and keeps the last commit intact.

Exposure and likelihood390 words
  • Who is hit. Applications that install their own InfoStream through IndexWriterConfig.setInfoStream(InfoStream) or setInfoStream(PrintStream) (public, IndexWriterConfig.java:426-446) whose message() can throw a RuntimeException, and that then recover from the failed commit() the documented way: rollback(), or close() with commitOnClose=false (which calls rollback(), IndexWriter.java:1363-1368). Shapes that can throw: a custom subclass writing to its own log (message() cannot throw a checked exception, so an I/O failure surfaces as UncheckedIOException); a PrintStream subclass whose println throws; Lucene's own JavaLoggingInfoStream behind a java.util.logging Handler that throws, or a backend bridged to it that forwards appender failures (Log4j 2 documents ignoreExceptions=false: "logging exceptions will be forwarded to the caller").
  • Default vs opt-in. Opt-in: the default InfoStream.NO_OUTPUT cannot reach the window. Everything else is default: default codec, any directory (the independent reproducer reports the same corruption on an on-disk FSDirectory; that run's output was not kept), one thread.
  • Scale. None: one committed document is enough, and the result is deterministic.
  • What is lost. The last good commit: its segment files are deleted, so DirectoryReader.open and a new IndexWriter both fail (CorruptSegmentInfoException / CorruptIndexException: a segment .si file is missing, _0.si in the repro, _1.si in a larger probe with three segments). With the default KeepOnlyLastCommitDeletionPolicy there is no older commit to fall back to. The failure is loud, at the next open.
  • How likely. Contrived: no shipped InfoStream or mainstream logging backend throws by default, the throw must hit exactly this line after the commit's earlier log lines succeeded, and an Error there (OutOfMemoryError included) is tragic and safe. Our searches found no report of it, although it has been in every release since 4.8.0 (2014). For these reasons the adjudication and the verifiers leaned Low; it is kept at Medium because committed data is lost.
  • Context, not claimed. The failed commit() also leaves a stale pending commit behind: a retried commit() finishes it, then throws NullPointerException ("fileNames" is null) and closes the writer as tragic (if a merge ran in between, the new commit references deleted files); the default close() refuses with "cannot close: prepareCommit was already called with no corresponding call to commit" (IndexWriter.java:1313-1316) although the application never called prepareCommit. A maintainer said on #9738 that continuing after a failed commit is unsupported, so these are context only.

Why it looks unintended

#
  • rollback() promises the index "as it was when commit() was last called"; here it deletes that commit's files.
  • A failed fsync at the same point is undone one statement earlier (IndexWriter.java:5993-5997); the log line after it is not.
  • Lucene's own testExceptionDuringRollback throws a RuntimeException from InfoStream.message (during rollback()) and asserts a good index.
The full argument379 words
  • rollback() promises the last commit. "This removes any temporary files that had been created, after which the state of the index will be the same as it was when commit() was last called or when this writer was first opened. This also clears a previous call to prepareCommit." (IndexWriter.java:2566-2571). prepareCommit: "After calling this you must call either commit() to finish the commit, or rollback() to revert the commit" (:3723-3725).
  • The writer reports its state as intact. The class javadoc reserves self-closing for "an Error, or disaster strikes during a checkpoint ... in case any internal state (buffered documents, deletions, reference counts) were corrupted" (:162-165). Here the writer stays open with getTragicException() null, and its reference counts are wrong.
  • The code already handles the same situation one statement earlier. A failed fsync after pendingCommitSet = true resets both fields and deletes the pending file (:5993-5997); the fix extends exactly that undo to the log line after it.
  • The deleter's own invariant trips. FileDeleter.RefCount.decRef asserts count > 0 ("RefCount is 0 pre-decrement", FileDeleter.java:276-282): with assertions on, rollback() fails on it.
  • Lucene's tests inject the same kind of fault. TestIndexWriterExceptions.testExceptionDuringRollback (LUCENE-5544) installs an InfoStream whose message() throws new RuntimeException("BOOM!") and asserts "even though we hit exception: we are closed, no locks or files held, index in good state" (TestIndexWriterExceptions.java:1980-2048). It throws during rollback(), on "rollback: done finish merges" or the test-point message "rollback before checkpoint" (:1982-1983, :1990-1991), not during commit(): the same kind of fault at a different place, which shows the tests treat a throwing InfoStream as a fault the writer must survive.
  • A maintainer named rollback() as the remedy for these methods. On open #9738 (2019) s1monw listed prepareCommitInternal() and startCommit() among methods whose exceptions "might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback() to go back the the last known safe-point / previous commit". This bug makes that remedy destroy the last safe point.
  • History. 4.7.2 survives the same injected exception (the last commit opens with 1 document); 4.8.0 does not. The difference is a side edit in LUCENE-5543 ("Remove Directory.fileExists") that its issue does not mention.
The devil's-advocate check275 words

The argument: InfoStream is a "Debugging API" marked @lucene.internal (InfoStream.java:23-29), and so is JavaLoggingInfoStream; no javadoc promises that IndexWriter survives an exception from a log callback; the JDK's ErrorManager javadoc tells a Handler to report problems "rather than throwing an Exception back to the issuer of the logging call"; mainstream backends swallow appender failures by default; an executed review by another model family (OpenAI GPT-5.6, refute lens) rated the trigger out of contract; and the same maintainer wrote on #9738 that "if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss". This is a real argument, and a maintainer may accept only a narrow fix because of it.

Why it does not settle the question: IndexWriterConfig.setInfoStream(InfoStream) and setInfoStream(PrintStream) are public, carry no @lucene.internal mark themselves (the InfoStream class they take does, and so does PrintStreamInfoStream, which the PrintStream overload wraps) and require only a non-null argument (IndexWriterConfig.java:426-446). @lucene.internal renders as "This API is for internal purposes only and might change in incompatible ways in the next release": it warns about the API, but it does not say an implementation must not throw, and no Lucene javadoc, CHANGES or MIGRATE text says so. Lucene's own testExceptionDuringRollback injects the same kind of fault (during rollback()) and asserts a good index. The claim is about rollback(), the documented recovery that the same maintainer named, not about continuing after the failure, and no reading of any contract lets a rollback delete the previous commit. The intended-lens review of the same model family and a devil's-advocate verifier both rated it real.

Suggested fix

#

Recommended A: startCommit's catch undoes the pending commit when it is already set

In startCommit's catch, when pendingCommitSet is already true, reset it and pendingCommit and delete the pending segments file (toSync.rollbackCommit), as the failed-fsync path does; the existing code then releases the reference once. 7 lines. Validated: the repro passes on and off; the org.apache.lucene.index tests (1,398) and :lucene:core:check pass.

Why it is enough: after the undo, the existing if (!pendingCommitSet) block releases filesToCommit once and nulls it, so prepareCommitInternal's guard skips its release and rollback() finds no pending commit. rollbackCommit only deletes pending_segments_N, ignoring exceptions (SegmentInfos.java:942-956). The fix clears the stale pending commit and makes rollback() safe. It does not undo everything: startCommit's finally still records the generation (segmentInfos.updateGeneration), as after a failed fsync, so a retried commit() writes segments_3. In a plain main() with the fix, a retried commit() succeeds and stores the current 2 documents, and the default close() commits them (on stock main the retry throws NullPointerException and close() refuses).

A: startCommit's catch undoes the pending commit when it is already set (validated by the checks) (recommended)

#

In IndexWriter.startCommit's catch (Throwable t) (IndexWriter.java:6005), before the existing if (!pendingCommitSet) block: if pendingCommitSet is true, set it to false, set pendingCommit to null and call toSync.rollbackCommit(directory), exactly as the failed-fsync catch does (:5993-5997). 7 lines added, IndexWriter.java only.

} catch (Throwable t) {
  synchronized (this) {
    if (pendingCommitSet) {
      // the pending segments file is written and synced, but we fail before returning: undo
      // it as a failed sync does, so that filesToCommit is released exactly once, below
      pendingCommitSet = false;
      pendingCommit = null;
      toSync.rollbackCommit(directory);
    }
    if (!pendingCommitSet) {
      ... // existing: release filesToCommit once, then null it
    }
  }
  throw t;
}

Trade-offs

A commit whose files were all fsynced is discarded because a log line failed, the same outcome as a failed fsync; the application sees the same exception as today. No cost on the success path.

B: prepareCommitInternal's catch releases only when no commit is pending

if (filesToCommit != null && pendingCommit == null) at IndexWriter.java:3922, leaving the reference to rollback() or finishCommit, as in 4.7.2.

Trade-offs

C: keep a throwing InfoStream out of the window

#

Catch and suppress a RuntimeException from that one message (the way #14668 made onTragicEvent suppress InfoStream exceptions). Moving the line alone is not enough: a throw anywhere after pendingCommitSet = true and before startCommit returns into prepareCommitInternal's try still leaves pendingCommit set while filesToCommit is released (IndexWriter.java:3914-3929, :5961-6035).

Trade-offs

Narrowest: it removes the only known trigger but keeps the asymmetry for any statement later added after pendingCommitSet = true. Not validated.

D: treat any failure after pendingCommitSet = true as tragic

#

In the spirit of the unmerged patch on #9738 that made every Throwable in startCommit tragic.

Trade-offs

Closes the writer because a log line failed; heavier than needed. Not validated.

Downstream note

#

Relevant to products that route IndexWriter's InfoStream into their own logging layer and use rollback() as the recovery after a failed commit: a logging failure on this one line can cost them the last commit.

How it was found

#

A bounded-exhaustive fault-injection sweep threw one exception at each callback call that commit, prepareCommit, NRT reopen and flush make on the calling thread (15,072 cases). A retried commit() failing after a throw at startCommit's "done all syncs" line was the first signal; reading the reference counting then found the rollback() consequence.

The method in full167 words

Method: semi-formal (a bounded-exhaustive single-fault injection sweep of the real lucene-core jar, then code reading witnessed by public-API probes), on main e1faeba08bde, 2026-11-02.

  • The sweep threw one RuntimeException or Error at the k-th call (k = 1..N) of every InfoStream.message and isEnabled call, leaf sorter, IndexSorter, per-field format chooser, ConcurrentMergeScheduler.merge, findFullFlushMerges and IndexWriterEventListener call made on the calling thread by commit, prepareCommit, DirectoryReader.open(writer), openIfChanged, flush and flushNextBuffer, in 6 configurations: 15,072 cases with assertions off.
  • Its first signal: in 24 cases a retried commit() threw NullPointerException ("fileNames is null") after a fault at startCommit's "done all syncs" line. Reading the reference counting of the pending commit then showed the double release and the rollback() consequence, confirmed by public-API probes (rollback, close() with commitOnClose=false, the default close(), a retried commit, a merge in between).
  • The case was reduced to the one JUnit test of this page. With the fix, the sweep shows no failure at startCommit.

LFV-1083, snapshot of 2026-11-10

Registry title
If commit() fails with an InfoStream exception after the pending segments file is synced, the commit's file references are released twice, so a later rollback() (or close() with commitOnClose=false) deletes files of the last commit and the index can no longer be opened
Area
index / IndexWriter commit failure handling (IndexWriter.startCommit, prepareCommitInternal and rollback; IndexFileDeleter reference counts)
Priority
Medium, rank 119: If the opt-in InfoStream throws on one commit log line and the application then calls the documented rollback(), with assertions off the files of the last good commit are deleted, so the index can no longer be opened and committed data is lost, in every release since 4.8.0. The trigger is contrived and the failure shows up loudly at open time, but losing committed data keeps it in Medium.
Impact class
index unusable
Impact note
Hits only applications that install their own InfoStream (off by default: a custom InfoStream subclass, a PrintStream whose println throws, or the shipped JavaLoggingInfoStream behind a logging handler or bridge that passes backend failures to the caller) when it throws a RuntimeException on the one 'done all syncs' line that commit() logs after it has written and fsynced the new pending segments file, and that then call the documented recovery rollback() (or close() with commitOnClose=false): with assertions disabled, as in production, the writer deletes files that the last good commit still references, so DirectoryReader.open and a new IndexWriter fail with CorruptSegmentInfoException or CorruptIndexException (NoSuchFileException _0.si) and the committed data is gone unless the application has a backup; an Error at the same point, OutOfMemoryError included, is tragic and keeps the last commit intact; no scale is needed; every release from 4.8.0 to 10.6.0 and main.
Summary
You enable an InfoStream on an IndexWriter, commit one document, add a second one and call commit() again, and the InfoStream throws a RuntimeException on the 'done all syncs' message that Lucene logs after it has written and fsynced pending_segments_2; commit() fails without closing the writer, so you call rollback(), whose javadoc says the index will then be as it was when commit() was last called. Instead, startCommit has kept the half-finished commit as its pending commit while prepareCommitInternal's catch has already released that commit's file references, and rollback() releases them a second time, so the file deleter removes _0.cfe, _0.cfs and _0.si, which segments_1 still needs. DirectoryReader.open(dir) then fails with CorruptSegmentInfoException (NoSuchFileException _0.si), close() with commitOnClose=false does the same, and with -ea rollback() throws AssertionError 'RefCount is 0 pre-decrement' instead.
