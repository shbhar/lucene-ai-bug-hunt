Monitor's ParallelMatcher and PartitionMatcher lose every match when one query throws an unchecked exception, and ParallelMatcher can hang

With PartitionMatcher or ParallelMatcher, one registered query that throws an unchecked exception (say an IntPoint query on a LongPoint field) makes Monitor.match throw "Interrupted during match" and lose every other match; the serial matcher reports just that query. Once all its workers have died this way and its 1,024-slot queue fills, ParallelMatcher blocks forever.

The finding in 30 seconds

#

Both wrappers run each query on a worker thread inside catch (IOException e). Any other exception ends the worker, and finish() turns it into RuntimeException("Interrupted during match"): Monitor.match returns nothing. ParallelMatcher also hands queries to its workers through a 1,024-slot queue with a blocking put; once all workers are dead, nobody empties it.

How the Monitor runs registered queries

#
  1. A Monitor stores registered queries. For each document, a presearcher picks the queries that might match; a query with no terms, such as a point query, is picked for every document.
  2. A matcher then runs each picked query against the document. The default matchers do this one query at a time; if a query throws, the Monitor records the error in getErrors() and carries on with the next query.
  3. PartitionMatcher and ParallelMatcher wrap such a matcher to run the queries on several threads; the package docs offer them to increase performance.

The finding, step by step

#
  1. Register two queries in a Monitor: long = LongPoint.newExactQuery("num", 5) and int = IntPoint.newExactQuery("num", 5). Match one document with a LongPoint field num = 5, using PartitionMatcher with 2 threads, which the docs offer to speed up matching.
  2. You expect what the default serial matcher returns for the same input: 1 match (long), and the error of int (the field has 8-byte points, the query 4-byte ones) in getErrors().
  3. Instead Monitor.match throws RuntimeException: Interrupted during match, and the match of long is lost too. The worker threads catch only IOException; the serial path catches every Exception.
  4. With ParallelMatcher it can be worse: a dead worker stops emptying a 1,024-slot queue. With 1 thread, 1 failing and 1,100 good queries, Monitor.match was still blocked after 30 s, and stopping it took 77 interrupts.

Who is affected

#

Applications that match with ParallelMatcher or PartitionMatcher (opt-in wrappers of the optional monitor module) and have a registered query that can throw while it runs: a point-width mismatch, a query over IndexSearcher's clause limit, a custom Query. One such query loses the whole batch at any thread count; the hang needs as many failing queries as threads.

Mechanism, terms and numbers595 words

Monitor.match runs every query the presearcher selects through a CandidateMatcher. The default serial path wraps each query in catch (Exception e) { matcher.reportError(id, e); }, so a query that throws is reported in getErrors() and the other matches are returned. The package docs offer PartitionMatcher and ParallelMatcher as wrappers "to increase performance in low-concurrency systems". Their workers catch only IOException. An unchecked exception, such as the IllegalArgumentException an IntPoint query throws on a field indexed as LongPoint, ends the worker; doFinish turns it into RuntimeException("Interrupted during match"), and Monitor.match throws and returns nothing, with a message that names neither the query nor the cause. ParallelMatcher also feeds its workers through a bounded queue of 1,024 tasks with an untimed put: once every worker has died and the queue fills, Monitor.match blocks forever, and each interrupt frees only one blocked put (the recorded runs needed 77 to 79). The code came with the module (LUCENE-8766, 2019); all 58 releases from 8.2.0 to 10.6.0 and main are affected.

The path (file:line at 645d4fe14a20, lucene/monitor/src/java/org/apache/lucene/monitor/)

#
  1. Serial path, the contract. Monitor.match feeds each selected query through StandardQueryCollector.matchQuery and then calls matcher.finish(...) (Monitor.java:218-226). The collector catches Exception and calls matcher.reportError(id, e) (Monitor.java:297-302). CandidateMatcher.reportError(String, Exception) is "Called by the Monitor if running a query throws an Exception" (CandidateMatcher.java:97-100); getErrors() returns a Map<String, Exception>.
  2. PartitionMatcher. matchQuery only queues the task (PartitionMatcher.java:70-73), so the collector's catch never sees a failure. doFinish splits the tasks into threads partitions and runs them with executor.invokeAll (:81-90). Each worker wraps each query in catch (IOException e) only (:116-121). An unchecked exception escapes call(), future.get() (:91) throws ExecutionException, and that becomes RuntimeException("Interrupted during match", e) (:99-100). Monitor.match propagates it: no result at all.
  3. ParallelMatcher. The constructor submits threads workers (ParallelMatcher.java:69-72; the two-argument factory uses availableProcessors(), :180-184). matchQuery puts each task on a LinkedBlockingQueue<>(1024) with an untimed put (:49, :76-84). Each worker loops on queue.take() and catches only IOException (:124-138, catch at :130). doFinish puts one END per worker (:94-96) and calls future.get() (:99), wrapping ExecutionException in RuntimeException("Interrupted during match") (:110-111).
  4. The hang. When every worker has died, nobody takes from the queue. After 1,024 queued tasks the next put (:80) blocks with no timeout (or, if only the END markers overflow it, doFinish's put(END) at :95 does). An interrupt turns that one put into IOException("Interrupted during match") (:81-82), which the collector records as that query's error (Monitor.java:300-301), and the next put blocks again. With 1 thread, 1 failing query first and 1,100 good ones: 1,100 - 1,024 = 76 blocked puts plus the final put(END) = 77 interrupts, as observed.
  5. Precondition of the hang. With 2 threads, 2 failing queries plus 1,100 good ones hang; with 1 failing query (one worker survives and empties the queue) or with only 100 good ones, Monitor.match throws without hanging. QueryDecomposer splits a plain disjunction (no MUST or FILTER clause, minimumNumberShouldMatch at most 1) into one candidate per distinct SHOULD clause; a conjunction or minimumNumberShouldMatch > 1 stays whole, and equal clauses collapse into one candidate (QueryDecomposer.java:77-103). So one registered disjunction with threads distinct failing clauses is enough.
  6. Only the exception type matters. Both wrappers report a checked IOException from a query per query and return the other matches; the same failure thrown as UncheckedIOException loses the batch (tie-break probe).
Exposure and likelihood280 words
  • Who is hit. Applications that match with ParallelMatcher or PartitionMatcher from the optional lucene-monitor module. The default serial matchers are not affected.
  • Ordinary triggers, all accepted by Monitor.register and all reported per query by the serial matcher: a point query whose width does not match the indexed field (it depends on the documents, so it matters where documents and queries come from independent producers); a query that passes each BooleanQuery builder but exceeds IndexSearcher's clause limit at rewrite (two 601-clause disjunctions in a conjunction give TooManyNestedClauses; one classic QueryParser string with default settings is enough); a custom Query that throws a RuntimeException; an UncheckedIOException.
  • Lost batch. One failing query makes the whole Monitor.match call throw, at any thread count, with assertions on or off: every match of every document in the batch is lost, and "Interrupted during match" hides the cause (it is only in the cause chain) and the failing query id (nothing names it). A term-less point query is selected for every document, so it breaks every match whose document has the field with the other point width.
  • Hang (ParallelMatcher only). Needs at least threads failing candidates in one batch (default threads = availableProcessors()) and then roughly 1,024 or more candidates still to queue. The matching thread then blocks forever, and one interrupt (what Future.cancel(true) sends) does not free it.
  • Reach. Rare. Code search found no use of the two wrappers in Elasticsearch, OpenSearch or Solr (Solr's open monitor-integration PR uses its own matcher); private deployments are not visible; nothing has been reported in seven years.
  • No data damage. The call fails loudly or blocks; the query index is not changed.

Why it looks unintended

#
  • The Monitor's serial collector catches every Exception and reports it per query; reportError is "Called by the Monitor if running a query throws an Exception".
  • Both wrappers already report a checked IOException per query; the same failure as UncheckedIOException loses the batch.
  • The docs offer the wrappers only for performance; "Interrupted during match" is raised when nothing was interrupted.
The full argument256 words
  • The serial path reports any Exception per query. The collector that drives every matcher catches Exception (Monitor.java:300); reportError takes an Exception and its javadoc says it is "Called by the Monitor if running a query throws an Exception" (CandidateMatcher.java:97); getErrors() is a Map<String, Exception>. No javadoc states this as a guarantee of the wrappers; it is the behaviour of the code that drives them. All of this dates from the module's first commit.
  • The wrappers report per query too, but for one exception type only. Both workers catch and report an IOException per query (PartitionMatcher.java:119-120, ParallelMatcher.java:130-131), and that works; the same failure as UncheckedIOException loses the batch.
  • Documented as a performance option. The package docs (package-info.java:50-51) and the class javadocs discuss only performance trade-offs; nothing says one failing query aborts the batch or that the caller may block.
  • The module's author stated the intent in the predecessor project. On Luwak #3 (2014), about a query that threw an unchecked exception, they wrote that "this should be dealt with by the error-handling code now ... it will add an error to the final DocumentMatches object". Luwak #1 ("Aborting search after single query fail") led to the per-query error handling. The concurrent matchers came later and never got the same catch.
  • The message shows the path was not foreseen: "Interrupted during match" when nothing was interrupted.
  • Tests. The shared concurrent-matcher tests cover only the no-error path; the two error tests (TestMonitorErrorHandling.testMonitorErrors, TestHighlightingMatcher.testQueryErrors) use serial matchers.
The devil's-advocate check141 words

The strongest case for "not a bug" (the devil's-advocate verifier and the cross-model reviews): CandidateMatcher.matchQuery declares only @throws IOException on IO errors, and both upstream error tests use a query that throws an IOException, so perhaps only I/O errors are meant to be isolated and a RuntimeException is a programming error that should propagate; core also throws IllegalArgumentException for a point-width mismatch on purpose.

Why it fails: throws IOException is the checked-exception declaration Java requires, and the code that calls every matchQuery, the Monitor's collector, catches Exception. Nobody disputes that core throws; the question is how the monitor reports it, and its serial path reports it per query. Even on the narrowest reading (let unchecked exceptions propagate), the misleading message stays a defect, and a matching thread that blocks forever is no defensible outcome. Verdict: not intended.

Suggested fix

#

Recommended A. Catch Exception in both workers (recommended)

Catch Exception instead of IOException in both workers, as the serial collector does; PartitionMatcher reports under a lock, because its workers share one error map. 2 files, +5/-4 lines. The repro, the whole monitor test suite (182 tests) and :lucene:monitor:check pass. An Error can still kill a ParallelMatcher worker; option B would cover that.

// ParallelMatcher.MatcherWorker.call
          } catch (Exception e) {   // was: IOException
            matcher.reportError(task.id, e);
          }
// PartitionMatcher.MatcherWorker.call
        } catch (Exception e) {     // was: IOException
          synchronized (PartitionMatcher.this) {
            PartitionMatcher.this.reportError(task.queryId, e);
          }
        }
// and drop PartitionMatcher's now unused import java.io.IOException

A. Catch Exception in both workers (recommended) (validated by the checks)

#

In ParallelMatcher.MatcherWorker.call and PartitionMatcher.MatcherWorker.call, catch Exception instead of IOException and report it per query, as Monitor's collector does. In PartitionMatcher the report goes into the outer matcher's HashMap, which several workers can write at once, so it is wrapped in synchronized (PartitionMatcher.this); the now unused java.io.IOException import goes (the format check rejects it otherwise).

// ParallelMatcher.MatcherWorker.call
          } catch (Exception e) {   // was: IOException
            matcher.reportError(task.id, e);
          }
// PartitionMatcher.MatcherWorker.call
        } catch (Exception e) {     // was: IOException
          synchronized (PartitionMatcher.this) {
            PartitionMatcher.this.reportError(task.queryId, e);
          }
        }
// and drop PartitionMatcher's now unused import java.io.IOException

Trade-offs

  • Same behaviour as the serial path: the failing query is in getErrors(), all other matches are returned. The changed code (the wider catch and the lock) is reached only when a query throws; the cost was not measured.
  • Not covered: an Error (for example an AssertionError under -ea, or StackOverflowError) still ends a worker. For PartitionMatcher that matches the serial path, which does not catch Error either; for ParallelMatcher enough such workers can still produce the hang (option B).
  • The lock guards a race that exists today on the IOException path; it has no repro and is not claimed separately.

What the checks validated

With the fix: the repro passes with assertions on and off; the whole suite passes (182 tests, 0 failures, 1 skipped); checkGoogleJavaFormat and ecjLintMain of the monitor module pass.
  • With the revised test (its pool built with NamedThreadFactory): the repro passes with assertions on and off, and :lucene:monitor:check passes (format check, ecj lint and forbidden APIs of main and test sources, and the suite: 182 tests, 0 failures, 1 skipped).
  • The same catch change, shadowed into the stock jars, also passed the independent verifier's 7 tests, the devil's-advocate probe (4 of 4: its 4-thread hang test then returns) and the tie-break probe (7 of 7: the 1-thread case returns 1,100 matches plus the error).

B. A, plus never block on a dead ParallelMatcher worker

#

Let ParallelMatcher.MatcherWorker.call catch Throwable around one task, remember it and keep emptying the queue until END before rethrowing it; or make matchQuery and doFinish use queue.offer(task, timeout) in a loop that gives up once every worker future is done.

Trade-offs

Removes the hang for Errors too, at the cost of more code; the timed variant polls. Not built.

C. Variant of A for PartitionMatcher: per-worker error maps

#

Report into each worker's own sub-matcher (matcher.reportError) and copy matches.getErrors() in doFinish, as ParallelMatcher.doFinish already does (ParallelMatcher.java:105-107). This avoids the shared map and the lock.

Trade-offs

Two more lines in doFinish. Not built.

Optional with any option: a truthful message

#

For an ExecutionException, say that a query failed (and keep the cause) instead of "Interrupted during match".

Trade-offs

Cosmetic on its own; with A the path is reached only by an Error.

Downstream note

#

No public downstream project using these wrappers was found (Elasticsearch, OpenSearch, Solr); in a service where users register their own monitor queries, one user's failing query would drop every user's matches in each batch that selects it.

How it was found

#

Code reading of the monitor's concurrent matchers during a review of the monitor module, after exhaustive checks of its presearcher came back clean; a JUnit on the stock main jars then confirmed it.

The method in full84 words

Non-formal. A hunt unit on the monitor module first ran exhaustive presearcher checks (clean), then read the matchers it named. The workers' IOException-only catch, next to the serial collector's catch (Exception e), stood out; the finder wrote a JUnit with a stock trigger (a nested BooleanQuery over IndexSearcher's clause limit), which failed on the stock main jars with assertions on and off, while the serial control passed. Independent verifiers then found the simpler point-width trigger and pinned down the hang's precondition.

LFV-326, snapshot of 2026-11-04

Registry title
Monitor's ParallelMatcher and PartitionMatcher catch only IOException per query: one registered query that throws an unchecked exception at match time makes Monitor.match throw and lose every match of the batch, and ParallelMatcher blocks forever once all its workers have died
Area
monitor / concurrent candidate matchers (ParallelMatcher, PartitionMatcher)
Priority
Low, rank 769: The opt-in Monitor Parallel and PartitionMatcher lose a whole batch loudly when one query fails and hang only with many failing candidates.
Impact class
hang
Impact note
Applications that match with the opt-in ParallelMatcher or PartitionMatcher wrappers of the optional monitor module (the default serial matcher is not affected): one registered query that throws an unchecked exception at match time (a point query of the wrong numeric type, a query over IndexSearcher's clause limit, a custom Query) makes every Monitor.match that selects it throw RuntimeException('Interrupted during match') and lose the other matches of the batch, at any thread count; with ParallelMatcher, once every worker has died (at least threads failing candidates, for example one registered query with that many failing disjuncts) and about 1,024 more candidates still have to be queued, Monitor.match blocks forever and one interrupt does not free it; ordinary scale; released 8.2.0 to 10.6.0.
Summary
You register queries in a Monitor and match documents with ParallelMatcher or PartitionMatcher, which the package docs offer as a performance option, and one registered query throws an unchecked exception at match time, for example an IntPoint range query meeting a field indexed as LongPoint (IllegalArgumentException). You expect what the default serial matcher does: that query is reported in getErrors() and every other match is returned. Instead the worker threads catch only IOException, so Monitor.match throws RuntimeException('Interrupted during match') and the whole batch's matches are lost, and with ParallelMatcher, once every worker has died, the caller blocks forever in LinkedBlockingQueue.put (executed: 4 threads, one registered query with 4 failing disjuncts plus 1,100 other queries, still blocked after 20 s, 77 interrupts to stop).
