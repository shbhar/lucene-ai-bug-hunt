The finding in 30 seconds

#

The scorer has two steps that carry a match across an ANY transition: one for a token of the query, one for the gaps between such tokens. For a position that holds a query term it runs both, so the state after the ANY transition is listed a second time and the match is counted twice.

Background: four pieces

#
  1. TermAutomatonQuery matches documents with an automaton whose transitions are terms. A document matches when a run of consecutive tokens is accepted. An ANY transition (addAnyTransition) accepts any one token.
  2. The score comes from the similarity (BM25 by default). It gets the number of matches in the document as the frequency, as for a phrase query. More matches, higher score.
  3. The scorer reads only the positions of the query's own terms. Positions that hold other tokens are gaps, and a match gets across a gap only on an ANY transition.
  4. A query that is one chain of positions is rewritten to a phrase query (or a multi-phrase query) and never reaches this scorer. An automaton in which two transitions out of one state lead to different states, or in which an accept state has a way on, does. An automaton with a cycle is always of that kind.

The finding, step by step

#
  1. Build a TermAutomatonQuery for comes, any one token, sun, plus a second way comes moon (without it the query is rewritten to a phrase query). Search two documents of three tokens: comes the sun and comes sun sun.
  2. You expect equal scores: each document holds the match exactly once, and both have three tokens.
  3. You get both documents, but comes sun sun scores 0.22790195 and comes the sun 0.16574687, with assertions on and off, on 10.6.0, branch_11x and main alike. The scorer counted the match once for comes the sun and twice for comes sun sun.
  4. Why: after finish() an ANY transition accepts every query term as well. The token sun at position 1 therefore carries the match across the ANY transition by itself. When the next token arrives, the scorer steps position 1 across the ANY transition a second time and lists the same state twice. Both copies reach the accept state.
  5. Second consequence, same cause: with an ANY transition that a match can take repeatedly, the list doubles at every further query term. For a, any number of tokens, b, a document with a 22 times and then b holds 22 matches and is counted as 4,194,303. 25 occurrences still complete in 0.8 to 0.9 s; 26 end the search with OutOfMemoryError at a 1 GB heap (with a 2 GB heap 26 complete and 27 end the same way; larger heaps were not run).

Who is affected

#

Low. Only code that builds a TermAutomatonQuery with an ANY transition, by hand or through TokenStreamToTermAutomatonQuery, and only when rewrite() keeps it (a single chain becomes a phrase query). Which documents match is unchanged; their ranking is off. The heap exhaustion needs a hand-built repeatable ANY transition and a document with 26 occurrences of one query term (1 GB heap).

Mechanism, terms and numbers1,578 words

TermAutomatonQuery (sandbox, @lucene.experimental) matches documents with an automaton whose transitions are terms; addAnyTransition adds a transition that matches any one token. The similarity gets the number of matches in a document as the frequency. When the token under an ANY transition is itself one of the query's terms, the scorer follows the ANY transition for that position twice: once in the step for the token, because finish() made every ANY transition cover every term id (TermAutomatonQuery.java:176-199 at main 781025d6fe32), and once more in the step that bridges gaps, whose loop starts at the position of the token matched last (TermAutomatonScorer.java:260-287). The state it leads to is appended a second time (:380-385), and every copy that reaches an accept state is counted.

The executed example: the query comes, any one token, sun (or comes moon) over comes the sun and comes sun sun. Both documents have three tokens and one match. The scorer counts frequency 1 and 2, and BM25 turns that into 0.16574687 and 0.22790195. The defect does not change which documents match. A query that is a single chain is rewritten to a phrase query and is not affected.

The duplicate doubles again at every further query term that an ANY transition crosses. With a query whose match can take ANY transitions repeatedly (a, any number of tokens, b; or a, up to 40 other tokens, b), a document with a k times and then b is counted as 2^k - 1 matches instead of k. At a 1 GB heap 25 occurrences complete and 26 end the search with OutOfMemoryError: Java heap space; with a 2 GB heap 26 complete and 27 throw, and larger heaps were not run.

Weight: Low. It needs the experimental sandbox query with an ANY transition in an automaton that rewrite() keeps, built by hand or through TokenStreamToTermAutomatonQuery. It is on the released lines: every release from 4.10.0 to 10.6.0, and branch_11x and main by the runs of this page. The 10.6.0 release fails the test as branch_11x does.

The bug (lines at main 781025d6fe32; the same git blob on branch_11x daa54f2e0cd3)

#
  1. Token step (block B in the picture), "Match current token" (:300-312): for the token at position p, each state of p is stepped with the token's term id (:303) and appended to position p+1 (:306); an accept state adds 1 to freq (:309). Since finish() made the ANY transition cover every term id, this step crosses it.
  2. Gap step (block A in the picture), "Maybe advance ANY matches" (:260-287): when the next token arrives at pos, the loop while (lastPos < pos) (:264) starts at lastPos, the position of the token matched last (:332), steps its states with the ANY id (:277) and appends them to the next position (:280). Its first iteration repeats, for the same states, what the token step did.
  3. PosState.add (:380-385) appends and does not look for a duplicate. The ANY successor is listed a second time: as the same state again (the example below), or beside a union state that contains it when the token under the ANY transition also has a transition of its own out of the same state. Every copy goes on, and every copy that reaches an accept state is counted.

The first iteration of the gap step is never needed for a position that held a query term. For the positions without a query term (the gaps) the gap step is the only step, and it is right.

Exposure and likelihood541 words
  • Who. Applications that use the sandbox TermAutomatonQuery with an ANY transition in an automaton that rewrite() keeps: one in which, after determinization, two transitions out of one state lead to different states, or an accept state has a way on.   • Default or opt-in. The class is opt-in, in the sandbox module and marked @lucene.experimental.   • Effect. A document is scored as if it matched more often whenever a query term sits at a position that an ANY transition crosses: a factor of up to 2 in the frequency per such crossing. Which documents match does not change; the ranking among the hits is off.
  • The heap exhaustion: exact trigger and bound. Which documents match: in an earlier run of 2,000,000 generated document cases the hits equal an independent reference in all of them. The devil's-advocate check400 words

The strongest case for "intended": the class is experimental, its javadoc says "This code is very new and likely has exciting bugs!", and on #6877 its author wrote that they "punted" on scoring and that it is 'clearly not "right" since an app could make an automaton that matches wildly different "phrases"'. Two more facts are on that side. First, the author says on the same issue that the matching is knowingly inexact about indexed positions ("the index can't store posLength, so the matching won't be fully correct if any indexed tokens has posLength != 1"), and the scorer's comment says the same (TermAutomatonScorer.java:232-235 at 781025d6fe32). Second, the extra step can stand in for a token the scorer cannot see: where a token that is no query term shares a position with a query term, the full token graph has one more path, and in an earlier run today's code gave the full graph's count in 1,237 of the 5,478 generated cases of that kind, the fixed code in none. The loop's start at lastPos, with its guard lastPos > startLastPos (:263-266), is in the class's first commit. So a maintainer may answer that scores of this class were never promised, may read the extra step as an allowance for a hidden token, and may treat a report as a tolerated limit of experimental code or decline the one-line change.

Why it fails: the author's remark on scoring is about giving different phrases one weight, not about counting one match twice. The count was specified (the class javadoc) and tested upstream (testFreq). With one token per position, where nothing is hidden, the extra step is still taken at every query term under an ANY transition (the example of this page), and in the stacked cases it gives the full graph's count in under a quarter of them, so it is not a consistent approximation either. Whether the token under the ANY transition happens to be a query term cannot change how often the automaton matches, and the class's own rewrite target counts the same match once. A state list that doubles per token is not a scoring choice. The case is moderate for "a tolerated limit of experimental code" and weak for "the double count is deliberate". The experimental status is the reason this is Low; it does not make the behaviour specified.

Trade-offs

  • Scores change for the affected queries: the frequency drops to the number of matches. That is the repair, and it is visible to anyone who compares scores across versions.
  • Tokens that share one position: open, for the maintainers. The scorer reads only the query terms' postings. With the fix it counts the paths over the query's own tokens. A token that is no query term and is stacked on a query term is one more path of the full token graph, which the scorer cannot see. Today's code adds one extra step at every query term whether or not such a token is there: in an earlier run it agreed with the full token graph in 1,237 of 5,478 generated cases of that kind, and the fixed code in none. For one token per position, the usual case, today's code is the one that is wrong.
  • Memory: the fix does not bound the state list. PosState keeps one entry per path and never merges two entries of the same state. With the fix the list no longer doubles for documents with one token per position (a 40 times and then b is counted as 40, in 14 ms). Where several query terms share a position under a repeatable ANY transition, the number of paths itself grows by a factor per position, and the list with it. Run: the query a or a2, an ANY self loop, b over one document whose first k positions each hold both a and a2, then b. Today's code counts 3^k - 1 (4,782,968 at k = 14; main, branch_11x and 10.6.0). The fixed code counts 2^(k+1) - 2, the number of paths through those tokens (k = 1 to 14; main and branch_11x); at a 1 GB heap k = 24 completes (33,554,430) and k = 25 ends with OutOfMemoryError (main). The second option would bound that.
  • Not discussed upstream. It confirms the root and passes the runs listed; it is not a reviewed design.

Keep a count per state instead of one list entry per path (not built)

#

Hold each automaton state once per position, with a multiplicity. Memory per position is then bounded by the automaton's size, also for documents with very many paths (several query terms at one position under a repeatable ANY transition), which the first option leaves as it is.

Trade-offs

It does not repair the count by itself: the multiplicities would still double. A larger change, on top of the first option.

It also merges distinct matches that reach the same state at the same position. Run on main: a, an ANY self loop, b over a k times and then b gives frequency 1 for k = 2 to 6, where the document holds k matches.

How it was found

#

A comparison of match counts over generated sandbox queries met the heap exhaustion first and reduced it to one 41-token document. An independent reference count of the matches, with a second reference that adds exactly the suspected second ANY step, then pinned the cause over 2,000,000 generated document cases per build and gave the two-document test.

The method in full213 words

Method: semi-formal (a differential over generated queries and a model-based reference; no model checking, constraint solving or proof was involved).

  • First signal. A comparison of match counts over generated sandbox queries ran out of heap. It was reduced to the query a, an ANY self loop, b over one document with a 40 times and then b.
  • Reference count. An independent count of the automaton's matches over the positions of the query's terms, read back from the index and written without Lucene's automaton code, and a second reference that models exactly the suspected second ANY step. On the stock builds (branch_11x with assertions on and off, main, 10.6.0) the scorer's frequency equals the second reference in 2,000,000 of 2,000,000 document cases per run (200,000 generated automata, 86,180 with an ANY transition) and differs from the plain reference in 21,806. The hits equal the reference's in all cases. With the one-line change the frequency equals the plain reference in all cases.
  • Reduction. To one test with two documents of three tokens; later reduced further to the form shown on this page, with no random input and one assertion.
  • For this page. The test, the bound of 25 and 26 occurrences and the fix were run again; the reference run was not repeated.

Registry title
Sandbox TermAutomatonQuery counts a match twice when an ANY transition is crossed at a position that holds a query term, so two documents of equal length with one match each score differently, and an ANY transition that a match can take repeatedly doubles the scorer's state list at every such position until the heap is exhausted (26 occurrences of a query term at 1 GB); every release since 4.10.0, branch_11x and main
Area
sandbox / search: TermAutomatonQuery (experimental), TermAutomatonScorer.countMatches
Priority
Low, rank 787: The experimental sandbox TermAutomatonQuery counts a match twice whenever an ANY transition is crossed at a position that holds a query term, so documents with one match each can score differently and the ranking among the hits is off, and a hand-built automaton whose match can take ANY transitions repeatedly (an ANY transition on a cycle, or a long chain of them) ends the search with OutOfMemoryError at a 1 GB heap on one document with 26 occurrences of a query term; every release since 4.10.0 has it. It is Low because the defect does not change which documents match, the class is sandbox code and the defect needs an ANY transition in an automaton that is not a single chain, the heap exhaustion needs the hand-built repeating shape and a document with that many occurrences of a query term, and no report was found in more than ten years.
Impact class
silent wrong results
Impact note
Only applications that use the experimental sandbox TermAutomatonQuery with an ANY transition in an automaton that rewrite() keeps (one in which, after determinization, two transitions out of one state lead to different states, or an accept state has a way on; an automaton with a cycle is always of that kind, and a branch whose alternatives lead into the same next state is rewritten to a MultiPhraseQuery; built by hand, or from a token graph that holds a multi-word synonym and a '*' token) are hit: a document is scored as if it matched more often whenever a query term sits at a position that an ANY transition crosses (the defect does not change which documents match, only the ranking among them is off), and for a hand-built automaton whose match can take ANY transitions repeatedly (an ANY transition on a cycle, or a chain of that many) one document with 26 occurrences of a query term ends the search with OutOfMemoryError at a 1 GB heap (25 complete; with a 2 GB heap 26 complete and 27 throw, and heaps above 2 GB were not run; a document with 40 occurrences that holds no match throws the same), with the default IndexWriterConfig, codec, searcher and similarity, with -ea and -da, at any index size, in every release from 4.10.0 to 10.6.0, on branch_11x and on main.
Summary
You build a TermAutomatonQuery for '"comes", any one token, "sun"' or '"comes moon"' and search two documents of three tokens each, 'comes the sun' and 'comes sun sun'. The duplicate doubles again at every further such position: with the query '"a", any number of tokens, "b"' one document with 'a' 40 times and then 'b' ends the search with OutOfMemoryError at a 1 GB heap (26 occurrences are enough, 25 complete). The defect does not change which documents match, and a query that is a single chain is rewritten to a phrase query and is not affected. Every release since 4.10.0 does it, and branch_11x and main fail the test as the 10.6.0 release does.
