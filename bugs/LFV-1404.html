NRT replica keeps reporting isCopying() == true after a copy job fails to start

In the NRT replicator, when the connection to the primary breaks as a replica's copy job starts, newNRTPoint gives up and returns null, but isCopying() keeps returning true for a job that never ran, until a newer NRT point replaces that job. Every release since 6.0.0 has it.

The finding in 30 seconds

#

newNRTPoint sets curNRTCopy = job (ReplicaNode.java:618) before job.start() (:641). The NodeCommunicationException catch (:642-650) resets the state and returns null but leaves curNRTCopy set. launch() (:654) is skipped, so finishNRTCopy, which clears it for every launched job (:417-419), never runs. isCopying() is curNRTCopy != null (:658-660).

How a replica copies a new NRT point, in one minute

#
  1. The primary tells a replica about a new NRT point (an index version). The replica's newNRTPoint asks its newCopyJob for a CopyJob; in the module's transport, newCopyJob first fetches the primary's copy state: the files of that version.
  2. The replica stores the job in the protected field curNRTCopy, calls job.start() (in the module's SimpleCopyJob, this sends the file list to the primary) and then launch()es it in the background.
  3. When a launched job ends, successfully or not, its callback finishNRTCopy clears curNRTCopy. isCopying() simply returns curNRTCopy != null.

The finding, step by step

#
  1. A replica that searches version 0 gets newNRTPoint(0, 1). Its newCopyJob returns a copy job for a one-file copy state (_0.cfs; the test builds it, while the module's SimpleReplicaNode reads it from the primary), and then the job's start() loses the connection: like the module's own SimpleCopyJob, it cancels itself and throws NodeCommunicationException.
  2. newNRTPoint catches it, logs "ignoring exception starting CopyJob", sets its state back to idle and returns null. So far correct: the point is abandoned.
  3. You expect isCopying() to return false, as it does when the copy job cannot even be created (with no earlier job, as here).
  4. Instead isCopying() returns true. The job was stored in curNRTCopy before start(), and the catch never clears it; the job is never launched, so the completion callback that normally clears it never runs.
  5. The stale job stays in curNRTCopy, so isCopying() stays true, even after close(), until a newNRTPoint with a newer version replaces it. No index file, data or search result changes.

Who is affected

#

Only applications that run the opt-in, @lucene.experimental NRT replicator with their own CopyJob transport, and only code that reads isCopying() or curNRTCopy, when the primary connection breaks during start(). The only in-tree reader is the module's test server, which waits while isCopying() before answering a primary-election request (read, not run). No index data, files or search results change.

Mechanism, terms and numbers359 words

In the opt-in, @lucene.experimental NRT replicator, ReplicaNode.newNRTPoint stores the new copy job in curNRTCopy before it calls job.start(). When start() throws NodeCommunicationException because the primary connection broke, the catch resets the replica to idle and returns null but leaves curNRTCopy set. The job is never launched, so nothing clears the field, and isCopying() (curNRTCopy != null) reports a copy in progress until a later, newer NRT point replaces the job. No index data, files or search results are affected; the only in-tree reader of isCopying() is the module's test server.

How long the wrong value lasts

#
  • A later newNRTPoint with a newer version replaces the job; transferAndCancel skips it because it is already cancelled ("prevJob was already cancelled; skip transfer", CopyJob.java:119-122); if that job's start() fails too, the same happens again.
  • A same or older version returns early without touching the field (ReplicaNode.java:558-574).
  • close() only cancels the job (:676-678) and never sets the field to null, so isCopying() is true after close() too.

Not part of this bug (read, not executed): the merge pre-copy jobs that :620-638 cancelled for this job's files are lost either way, and so are files an earlier, still running job had copied and handed over through transferAndCancel (:613-616), which the self-cancelling start() deletes (CopyJob.java:225-258): lost copy work, not index data. NodeCommunicationException is a RuntimeException, so a plain IOException from start() is not caught at :642; newNRTPoint then throws with the field still set and the state still "syncing".

Exposure and likelihood244 words
  • Who. Applications built on ReplicaNode (@lucene.experimental, ReplicaNode.java:61-63) that implement newCopyJob and CopyJob for their transport and read isCopying() or the protected curNRTCopy. Not default Lucene usage.
  • When. The connection to the primary breaks in the short window after the replica has read the new copy state and while its job starts (in SimpleCopyJob, while it sends its file list); a primary crash is the typical cause. One failed start is enough; no scale is needed.
  • What goes wrong. A copy is reported in progress when none is. The module's test server answers CMD_GET_SEARCHING_VERSION, asked while a new primary is elected, only after while (isCopying() && stop.get() == false), with the comment "if a sync is just finishing up ... we need to wait for it" (SimpleReplicaNode.java:222-237). After a primary crash no newer point arrives until the election ends, so such a replica would not answer before the controller's 30 s socket read timeout (Connection.java:44, test code); TestStressNRTReplication then skips it as a promotion candidate (TestStressNRTReplication.java:402-411). Test-server behaviour only; read, not executed.
  • What does not go wrong. No index file, index data or search-result effect; the field keeps one cancelled CopyJob object reachable (its size was not measured). The replica can still take the next newer NRT point.
  • How likely. Rare: only the replicator, only that window, and only readers of the status. No report of it was found since 6.0.0 (2016).

Why it looks unintended

#
  • curNRTCopy's javadoc: "Non-null when we are currently copying files from a new NRT point"; after the failed start nothing is copying.
  • Sibling exits leave no stale job: a failing newCopyJob returns before the assignment; finishNRTCopy clears the field when a launched job ends.
  • The same catch already abandons the point (idle, return null) for the documented "non-fatal" NodeCommunicationException.
The full argument193 words
  • Contract. "Non-null when we are currently copying files from a new NRT point" (ReplicaNode.java:76); isCopying() returns exactly that field (:658-660).
  • The code's own intent. The start() catch resets state to idle and returns null (:646-649): it gives up on the point. Only the matching reset of curNRTCopy is missing.
  • Consistency. The newCopyJob failure path returns before the assignment (:597-605), so in the same situation (no earlier job) isCopying() stays false; finishNRTCopy clears the field when a launched job ends, on success and on failure (:417-419).
  • Legal trigger. NodeCommunicationException: "Should be thrown by subclasses of PrimaryNode and ReplicaNode if a non-fatal exception occurred while communicating between nodes" (NodeCommunicationException.java:21-22). CopyJob.start() is abstract (CopyJob.java:217); the module's reference SimpleCopyJob.start() calls cancel("exc during start", t) and throws it on any failure (SimpleCopyJob.java:106-108).
  • History. The block is unchanged in substance since the first patch (2016); no commit, test or discussion treats the stale value as wanted. LUCENE-9967 (#11006) fixed another bug in a ReplicaNode exception handler (an NPE in ReplicaNode.start()'s catch on an exception without a message) as a bug.
The devil's-advocate check137 words

"Experimental API, no javadoc on isCopying(), and it heals itself." @lucene.experimental means the API may change, not that a wrong state is accepted, and the value isCopying() returns has a stated contract (the field javadoc). It heals only at a newer version; after a primary failure, the usual cause, none arrives until a new primary is elected.

"The job is kept on purpose, for the next transferAndCancel." No comment says so, and it would do nothing: the job is already cancelled, so transferAndCancel skips it (CopyJob.java:119-122).

"Misuse of the extension point." newNRTPoint catches this exception from start() on purpose, and the reference implementation throws it exactly this way.

Both executed reviews by another model family (OpenAI GPT-5.6; a refutation review and an intended-behaviour review) rated the works-as-designed case weak; the verifiers rejected it.

Trade-offs

Smallest change; mirrors finishNRTCopy's if (curNRTCopy == job) (ReplicaNode.java:417). In ReplicaNode's own code the guard is true here; keep it as a defensive check, because a custom start() could re-enter newNRTPoint on the same thread (the monitor is re-entrant) or a subclass could change the protected field. It relies on start() having cancelled the job itself, as SimpleCopyJob does; for a start() that can throw without cancelling, fix B also cleans up the job's carried-over temp files.

B: cancel the job, then clear curNRTCopy (validated by the checks)

#

Before the reset, call job.cancel("exc during start", nce);. Suggested by the devil's-advocate verifier for a custom CopyJob whose start() throws without cancelling itself: cancel() deletes the temp files that transferAndCancel carried over into this job.

      // Make sure the job is cancelled (no-op if start() already did) and no longer current:
      job.cancel("exc during start", nce);
      if (curNRTCopy == job) {
        curNRTCopy = null;
      }

Trade-offs

CopyJob.cancel() returns at once when the job is already cancelled (CopyJob.java:225-229), so nothing changes for SimpleCopyJob. But cancel() can throw IOException (from forceDeleteFile), and newNRTPoint would then throw instead of returning null.

Downstream note

#

Downstream code that gates an election, failover or health check on isCopying() would see a copy that is not running; nrtsearch, the best-known user of this replicator, does not call isCopying().

How it was found

#

A bounded model-based test of in-JVM NRT replication over the real replicator classes added a step that breaks the primary connection while a copy job starts, with the check that isCopying() must be backed by a launched job. It fired on main and was reduced to one JUnit test.

The method in full164 words

Method: semi-formal, on main 5adff78bb168, 2026-11-08.

  • Model. A bounded model-based test drives in-JVM NRT replication over the real PrimaryNode, ReplicaNode, CopyJob, CopyOneFile and CopyState classes, with a transport that follows the module's socket test code. Before looking for new behaviour, the model re-found already known replicator bugs, as a check that it can see real defects.
  • New step and check. A step breaks the primary connection after the replica has read the copy state, while its job sends the file list; a check requires isCopying() to be backed by a launched job whose callback can clear it.
  • Signal. In an exhaustive enumeration of all call sequences up to length 3 after 11 seed prefixes (445,434 runs on stock main, assertions on), this check was the only signal not explained by an already known bug.
  • Reduction. The finder reduced it to a JUnit test with a real primary and writer; the shipped test is a smaller, deterministic version without either.

Summary
A replica receives a new NRT point; newNRTPoint creates the copy job (reading the primary's copy state) and calls job.start(), which throws NodeCommunicationException because the connection to the primary broke, exactly as the module's reference SimpleCopyJob.start() does after cancelling itself. You expect newNRTPoint to give up on that point and go back to idle, so isCopying() returns false, as it does when the job cannot even be created.
