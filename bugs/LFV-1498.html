The finding in 30 seconds

#

The setter's javadoc sits right above a null check that contradicts it: @param type DocValues type, or null if no DocValues should be stored. (FieldType.java:508), then if (type == null) throw new NullPointerException(...) (:514-516). The getter's javadoc says the default is null (:496); the field is initialised to DocValuesType.NONE (:44).

Background in two steps

#
  1. FieldType describes how a field is indexed: stored or not, its index options, term vectors, and its doc values type. Doc values are per-document values kept in columns, used for sorting, faceting and similar. DocValuesType.NONE means the field has none.
  2. Most code never touches this: Lucene's field classes (TextField, StringField, NumericDocValuesField, ...) come with ready-made types. Only code that builds its own FieldType calls setDocValuesType or reads docValuesType().

The finding, step by step

#
  1. You build your own FieldType and want no doc values on it. The javadoc of setDocValuesType says @param type DocValues type, or null if no DocValues should be stored, so you write new FieldType().setDocValuesType(null).
  2. You expect a field type without doc values.
  3. Instead the call throws NullPointerException: DocValuesType must not be null (FieldType.java:515), with assertions on and off. The field type is unchanged. The value the code wants is DocValuesType.NONE; the message does not name it.
  4. The getter has the same leftover. Its javadoc says "The default is null (no docValues)", but new FieldType().docValuesType() returns DocValuesType.NONE, so the test new FieldType().docValuesType() == null is false.
  5. Why: Lucene 5.0 (LUCENE-6039) replaced null by DocValuesType.NONE on purpose and added the null check to the setter, under the @param sentence, but left both sentences. Up to 4.10.4 the setter accepted null. The fix is two javadoc sentences; no code changes.

Who is affected

#

Only code that builds a FieldType by hand and passes null on purpose, or tests docValuesType() for null. The setter fails at once, changes nothing and names the null, not DocValuesType.NONE. A null test on a type made with new FieldType() and the setter is silently false. Lucene computes nothing wrong. No setting needed. Rare. Every release since 5.0.0.

Mechanism, terms and numbers602 words

This is a documentation defect. The code is intended and must not change.

FieldType#setDocValuesType documents @param type DocValues type, or null if no DocValues should be stored. (FieldType.java:508 on main 781025d6fe32), and FieldType#docValuesType() documents The default is null (no docValues) (:496). Both sentences were written in 2012 and were true in Lucene 4.x. Since 5.0 (LUCENE-6039, #7101) the value for "no doc values" is DocValuesType.NONE: the setter throws NullPointerException("DocValuesType must not be null") for null (:514-516), and the field is initialised to DocValuesType.NONE (:44), so new FieldType().docValuesType() returns DocValuesType.NONE and the setter cannot make it null. That change was deliberate and is recorded in the 5.0.0 CHANGES; it edited the lines around both sentences and left them.

A caller who follows the javadoc gets an immediate exception that names the null but not the value to use, or writes a null test that is false for every FieldType made with new FieldType() and the setter. Lucene itself computes nothing wrong. Every release from 5.0.0 to 10.6.0, branch_11x (11.0) and main carry both sentences. The fix is javadoc only. The neighbouring default sentence of indexOptions() (:280) is stale in the same way; A. Coady pointed that out on Stack Overflow in 2018, and it is not part of this claim.

The mechanism

#
  1. FieldType.java:508: @param type DocValues type, or null if no DocValues should be stored. The method's @throws list (:509) names only IllegalStateException. This is the first stale sentence.
  2. FieldType.java:512-518: setDocValuesType calls checkIfFrozen(), then if (type == null) throw new NullPointerException("DocValuesType must not be null") (:514-516), and only then assigns (:517). So a null argument leaves the field type as it was.
  3. FieldType.java:496: The default is <code>null</code> (no docValues). This is the second stale sentence. The field is declared private DocValuesType docValuesType = DocValuesType.NONE; (:44) and the getter returns it (:502). One path can still bring a null in: the copy constructor FieldType(IndexableFieldType ref) stores ref.docValuesType() unchecked (:64), so a copy of an application's own IndexableFieldType whose docValuesType() returns null returns null (executed). That is not the documented default, and nothing in the Lucene tree returns null there.
  4. The inherited interface text adds nothing: IndexableFieldType.java:86 says only "DocValues DocValuesType: how the field's value will be indexed into docValues." Nothing else rendered for the two methods corrects the stale sentences.
  5. The value to use is documented on the enum: DocValuesType.NONE, "No doc values for this field." (DocValuesType.java:24-25).
  6. The rest of the code agrees with the check: FieldInfo (FieldInfo.java:101, :158, :546), IndexWriter (IndexWriter.java:2087-2091) and DocValuesFieldUpdates (DocValuesFieldUpdates.java:250) also refuse a null DocValuesType.

Executed

#

On main, with assertions on and off: new FieldType().docValuesType() is NONE; new FieldType().setDocValuesType(null) throws; after setDocValuesType(DocValuesType.SORTED) a setDocValuesType(null) throws and the type is still SORTED; setDocValuesType(DocValuesType.NONE) returns and the type is NONE. On a frozen FieldType the same null call throws IllegalStateException: the frozen check (:513) comes first. new FieldType(ref).docValuesType() is null when ref is a field type of the application whose own docValuesType() returns null. Both are the same on branch_11x and on the 10.6.0 jars.

The neighbouring sentence (not part of this claim)

#

FieldType.java:280 says The default is {@link IndexOptions#DOCS_AND_FREQS_AND_POSITIONS}. while the field is initialised to IndexOptions.NONE (:42). A. Coady pointed this out on Stack Overflow in 2018 (answer 48236544): "Although it's documented that DOCS_AND_FREQS_AND_POSITIONS is the default, that's no longer the case." The same javadoc change can correct it.

Exposure and likelihood253 words
  • Who. Application code that builds a FieldType by hand and follows the javadoc: it passes null to setDocValuesType to say "no doc values" (for example to clear the type on a copy of another field type), or it tests docValuesType() == null. FieldType is the public schema class of the core document API; the class carries no internal or experimental tag. (The interface it implements, IndexableFieldType, which declares docValuesType(), is tagged @lucene.experimental.)
  • Not hit. Code that uses Lucene's own field classes, or that passes a real DocValuesType. No Lucene source or test passes null to the setter or treats a null docValuesType() as "no doc values"; the one null test of the getter's result (IndexWriter.java:2087-2091) refuses null. A public code search found no caller of FieldType.setDocValuesType(null).
  • Effect. Setter: one exception at the first run, before any state changes; its message names the null but not DocValuesType.NONE. Getter: a null test that is silently false for every FieldType built with new FieldType() and the setter. No index, search result or stored state is wrong.
  • Scale. No setting, no data size, deterministic, one call. Every release from 5.0.0 to 10.6.0 (108 releases), branch_11x and main. No report of the sentences was found; 5.0.0 is from 2015.
  • Size, stated openly. This is the smallest kind of entry: two stale sentences, a loud and harmless failure, a javadoc-only fix. It is listed because the @param text names null as the value to pass, on a public core class.

Why it looks unintended

#
  • The code is intended: 5.0 replaced null by DocValuesType.NONE on purpose (LUCENE-6039, recorded in CHANGES). Only the two sentences are wrong.
  • That change added the null check to the setter, under the @param sentence, and left both sentences.
  • Nothing else in the two methods' javadoc corrects them: the inherited text is silent on null, NONE and defaults.
The full argument271 words

The claim is only that the two sentences are wrong. Nobody proposes to change the code.

  • The change was deliberate and recorded. The 5.0.0 section of CHANGES (the entry is listed under Bug Fixes): "LUCENE-6039: Add IndexOptions.NONE and DocValuesType.NONE instead of using null to mean not index and no doc values" (lucene/CHANGES.txt:11636).
  • The same commit left the sentences while editing the lines around them. bc41d58cd37 (Michael McCandless, 2014-10-31) added the initialiser = DocValuesType.NO (renamed NONE the same day), added the null check to the setter under the @param sentence and changed the @see line directly under the getter sentence. It changed neither sentence (the getter sentence is an unchanged context line of the hunk that edits the @see line).
  • Its author expected leftovers. On #7101 they wrote: "this is really quite a dangerous change since I could easily (and likely did) miss places in the code that still think null means "not indexed" or "no doc values"." That was said about code; the two javadoc sentences are such places.
  • The sentences were true when written. Getter: 5ba7843db91 (2012-08-27); setter: a4702d3711e (2012-08-30). In 4.10.4 the field is uninitialised and the setter (then setDocValueType) stores null unchecked; a control test with the 4.x names passes on 4.10.4.
  • Nothing current supports the sentences. No upstream test passes null to the setter or expects a null default. MIGRATE.md has no entry about null doc-values types; its one FieldType line already writes FieldType.indexOptions() != IndexOptions.NONE (lucene/MIGRATE.md:1500).
  • Precedent. #9506 (LUCENE-8460) aligned javadoc and null handling in the neighbouring Field and StoredField classes: it changed the null checks and their @throws lines together.
The devil's-advocate check200 words

The strongest case for "not a bug": refusing null is deliberate and twelve years old. The right value is written down where a user can find it: the 5.0.0 CHANGES entry and the javadoc of DocValuesType.NONE. Passing null to an enum setter is ordinarily a caller error, and on #9506 a maintainer called a NullPointerException for a null argument acceptable (Adrien Grand, about the constructors discussed there: "An IllegalArgumentException would be more consistent with other constructors, but a NullPointerException isn't bad either"; the change made for that issue then used IllegalArgumentException). The failure is immediate, names the null and changes nothing. No report was found in twelve years, and no public caller. So it is a cosmetic nit.

Why it fails, and what remains. All of that defends the runtime, which nobody proposes to change. It does not defend the sentences: the @param text names null as the value to pass, so the caller is following the documentation, and the two methods' javadoc pages say nothing else on the subject. What remains is size, not intent. The impact is small, which is why this is at the bottom of Low: a small stale-javadoc cleanup, not a behaviour bug.

A. Correct the javadoc, no code change (validated) (recommended)

#

In FieldType.java, replace null by {@link DocValuesType#NONE} in the getter's default sentence (:496) and in the setter's @param sentence (:508), and, optionally, say that null is refused. One file, javadoc lines only.

The validated diff has a third hunk for the neighbouring sentence, which is not part of this claim (A. Coady pointed it out on Stack Overflow in 2018): :280 becomes The default is {@link IndexOptions#NONE} (not indexed). With it the diff is +5/-3 lines.

-   * <p>The default is <code>null</code> (no docValues)
+   * <p>The default is {@link DocValuesType#NONE} (no docValues)
 ...
-   * @param type DocValues type, or null if no DocValues should be stored.
+   * @param type DocValues type, or {@link DocValuesType#NONE} if no DocValues should be stored.
+   *     Must not be null.
+   * @throws NullPointerException if {@code type} is null.

Trade-offs

  • No behaviour change; the null check and both initialisers stay.
  • The Must not be null. and @throws NullPointerException lines are optional. The @throws line is unconditional as written, but the frozen check (:513) runs before the null check: on a frozen FieldType the null call throws IllegalStateException (executed). Qualify the line or leave it out; the sibling setter setIndexOptions has the same null check and documents no such @throws either (:289-302).
  • Without the two optional lines and without the third hunk, the change is one word in each of the two sentences (by reading, not run).
  • The third hunk is independent of the other two and can be left out or made as a separate change.
  • The wording describes this setter and this default only, not a rule for the whole class: setDocValuesSkipIndexType stores its argument unchecked (:531-534), and the copy constructor copies every value unchecked (:55-76).
  • CHANGES entry optional (documentation fix).

What the checks validated

  • Gradle in a scratch worktree of 781025d6fe32, OpenJDK 25.0.3, seed DEADBEEF: on the stock tree the repro fails with assertions on and off. With the diff it still fails the same way (frame FieldType.java:517, two lines down), as expected for a javadoc-only change.
  • With the diff: TestFieldType (5), TestField (38) and TestDocument (12): 55 tests, 0 failures, assertions on and off. A regression check only; a javadoc change cannot alter them.
  • With the diff: :lucene:core:renderJavadoc passes, and the rendered pages read "or DocValuesType.NONE if no DocValues should be stored. Must not be null.", "The default is DocValuesType.NONE (no docValues)" and "The default is IndexOptions.NONE (not indexed)."
  • With the diff: :lucene:core:check -x test passes (checkGoogleJavaFormat, ecjLint, forbiddenApis).

B. Accept null again (not recommended, not built)

#

Map null to DocValuesType.NONE in the setter.

Trade-offs

It would make the @param sentence true and the repro pass, but it reverses a deliberate, recorded 5.0 decision, and FieldInfo, IndexWriter and DocValuesFieldUpdates would still refuse null. The getter sentence would stay wrong. By reading, not run.

Downstream note

#

Applications that build their own FieldType should pass and compare DocValuesType.NONE, never null: the setter rejects null before it changes anything, and new FieldType().docValuesType() is DocValuesType.NONE, which the setter cannot turn into null.

How it was found

#

A scan read the 5,748 @param texts on public and protected methods and constructors with a body and kept those that allow null while the method body refuses it: 3 hits, 1 real. A one-call JUnit test on the stock main build then showed the exception. The getter sentence was found by reading the method beside it.

History

#

Introduced by LUCENE-6039 (bc41d58cd37, 2014-10-31), first released in 5.0.0; up to 4.10.4 null was the working "no doc values". Every release from 5.0.0 to 10.6.0, branch_11x (11.0) and main carry both sentences. Not new in 11.0. Not fixed upstream.

Versions tested9 rows

Introduced by bc41d58cd37 on trunk, "LUCENE-6039: cutover to IndexOptions.NO/DocValuesType.NO instead of null" (Michael McCandless, 2014-10-31; migrated issue #7101; no pull request in that era). The 5.0 line got the same patch as 29158175b98. In FieldType.java it initialised the field to DocValuesType.NO (renamed NONE the same day) and added the null check to the setter. It changed neither sentence. The code change is intended; what the commit introduced is the mismatch.

The sentences are older and were true when written: getter 5ba7843db91 (2012-08-27), setter a4702d3711e (2012-08-30), both by Robert Muir, for the 4.x convention "null means no doc values".

Later commits on the same lines kept the wording about null: 6bf44e94399 (2014-10-31, NO renamed NONE); b7059e76287 (2014-11-08, setDocValueType renamed setDocValuesType); 8c5115ea9a6 (LUCENE-7145, 2016, from 6.1.0: the message "cannot be null" becomes "must not be null"); 2d6ad2fee6d (LUCENE-9570, 2020, reformatting).

The coming release. branch_11x (daa54f2e0cd3, 11.0.0-SNAPSHOT) has the byte-identical FieldType.java, and the test fails there with assertions on and off, so 11.0 would ship both sentences. It is not new in 11.0: every release since 5.0.0 has them.

Not fixed upstream as of 2026-11-14: the newest commit on the file is #15886 (2026-04-07), on main and on branch_11x.

Registry title
FieldType's javadoc still describes null as 'no doc values': setDocValuesType documents '@param type DocValues type, or null if no DocValues should be stored' but null throws NullPointerException, and docValuesType() documents 'The default is null' but returns DocValuesType.NONE (documentation defect, stale since 5.0.0; the code is intended and must not change)
Area
document / FieldType (javadoc of setDocValuesType and docValuesType(); the null refusal and the NONE default beside them)
Priority
Low, rank 1440: Documentation only: FieldType's javadoc still offers null for 'no doc values' (the setter's parameter and the getter's default), but in every release since 5.0.0 setDocValuesType(null) throws NullPointerException and the default is DocValuesType.NONE. FieldType is a common core class, but only code that passes null or tests the getter for null on purpose is hit, the setter fails at once without changing any state, and Lucene itself computes nothing wrong.
Impact class
minor
Impact note
Documentation only: application code that builds its own FieldType and follows the javadoc, passing null to setDocValuesType to switch doc values off or testing docValuesType() == null for 'no doc values', gets an immediate NullPointerException from the setter, or a null test that is false for every FieldType made with new FieldType() and the setter [exec]; the setter's failure is loud, changes no state and its message names the null (but not DocValuesType.NONE, the value to use); Lucene itself computes nothing wrong, and refusing null is intended (LUCENE-6039) and must not change; no setting or scale is needed, but passing null on purpose is a rare call; every release since 5.0.0.
Summary
You build your own FieldType and call setDocValuesType(null) to switch doc values off, because its javadoc says '@param type DocValues type, or null if no DocValues should be stored', or you test docValuesType() == null because its javadoc says 'The default is null (no docValues)'. You expect a field type without doc values and a null default. Instead the setter throws NullPointerException 'DocValuesType must not be null' and the getter returns DocValuesType.NONE, so the null test is false for every FieldType made with new FieldType() and the setter. Lucene 5.0 replaced null by DocValuesType.NONE on purpose (LUCENE-6039) and left these two sentences, so only the javadoc is wrong (pass DocValuesType.NONE); the stale default sentence of indexOptions() beside them was pointed out by A. Coady on Stack Overflow in 2018 and is not part of this finding.
