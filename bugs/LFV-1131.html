Facet-set DimRange.fromDoubles with an exclusive bound at 0 skips -0.0: [-1, 0) and [0, 1] together count 0 of 1 document

Facet-set ranges [-1, 0) and [0, 1] should together count every value in [-1, 1], but a value of -0.0 is counted by neither: excluding the bound 0 steps to the next double below 0, which jumps over -0.0. Every release since 9.3.0 is affected.

The finding in 30 seconds

#

Facet sets store values as sortable longs, where -0.0 sits directly below +0.0. Making the bound 0 exclusive with Math.nextDown skips that slot.

Background: two zeros and inclusive bounds

#
  1. Java has two zeros. -0.0 == 0.0 is true, but Double.compare(-0.0, 0.0) is -1: -0.0 sorts just below +0.0. It comes from ordinary arithmetic, for example -1 * 0.0 or Math.ceil(-0.25).
  2. A facet set stores each double as a sortable long ordered like Double.compare: -Double.MIN_VALUE (-4.9E-324) is -2, -0.0 is -1, +0.0 is 0.
  3. A DimRange holds inclusive bounds only, so fromDoubles turns an exclusive bound into the neighbouring value inside the range.

The finding, step by step

#
  1. Index one document whose facet set holds -0.0: FacetSetsField.create("f", new DoubleFacetSet(-0.0)). Count it with MatchingFacetSetsCounts and two RangeFacetSetMatchers: [-1, 0) = DimRange.fromDoubles(-1, true, 0, false) and [0, 1] = DimRange.fromDoubles(0, true, 1, true).
  2. You expect the two counts to add up to 1: the ranges meet at 0 with no gap, so -0.0 belongs to [-1, 0) if it sorts below 0, or to [0, 1] if the two zeros are equal.
  3. Instead both counts are 0, with no error. A covering [-1, 1] range still counts the document, and a value of +0.0 is counted by [0, 1] as it should be.
  4. Why: facet sets compare values as sortable longs, where -Double.MIN_VALUE is -2, -0.0 is -1 and +0.0 is 0. To exclude 0, fromDoubles stores Math.nextDown(0.0) = -Double.MIN_VALUE, so [-1, 0) ends at -2 and [0, 1] starts at 0: -0.0, at -1, falls in the gap.
  5. The same step is in fromFloats and the range-on-range DoubleRange, and the mirror case (+0.0 against [-1, -0.0] and (-0.0, 1]) fails the same way. Fix: step with DoublePoint/FloatPoint.nextUp/nextDown, which Lucene added in 2016 for exactly this mismatch.

Who is affected

#

Applications that count DoubleFacetSet/FloatFacetSet values with RangeFacetSetMatcher ranges from DimRange.fromDoubles/fromFloats, or range-on-range DoubleRange buckets, that meet at zero with one exclusive bound. Opt-in, mostly @lucene.experimental APIs; default codec and settings; any index size. Each such value drops out of both buckets; nothing throws. Rare.

Mechanism, terms and numbers494 words

DimRange stores inclusive bounds as sortable longs, and facet sets match values in that long space, whose order is Double.compare order (facetset/DimRange.java:24-25, :79-80; FacetSets.adoc:134-138; NumericUtils.java:41-42). To honour an exclusive bound, DimRange.fromDoubles first moves it to the neighbouring double with Math.nextUp(min) / Math.nextDown(max) (DimRange.java:65-67, :72-74, main 5adff78bb168). In sortable order -Double.MIN_VALUE is -2, -0.0 is -1 and +0.0 is 0, so Math.nextDown(+0.0) = -Double.MIN_VALUE jumps over -0.0: fromDoubles(-1, true, 0, false) ends at -2 while fromDoubles(0, true, 1, true) starts at 0, and a facet set holding -0.0 is counted by neither. fromFloats, the +0.0 mirror (Math.nextUp(-0.0) skips +0.0) and range-on-range DoubleRange behave the same way. Lucene fixed this exact Math.nextUp/nextDown versus Double.compare mismatch for point queries in LUCENE-7594 (#8645, 2016) by adding DoublePoint/FloatPoint.nextUp/nextDown; using them here (plus a Double.compare emptiness check) fixes it, and the repro and the whole facet module pass. Present since facet sets were added in 9.3.0; every executed release through 10.6.0 and main fails.

The mechanism (main 5adff78bb168)

#
  1. Indexing. DoubleFacetSet.getComparableValues() stores each value as NumericUtils.doubleToSortableLong(value) (facetset/DoubleFacetSet.java:40-41). FacetSets.adoc: "the matching of the values occurs in the long space", and the built-in sets pack sortable values (lucene/facet/docs/FacetSets.adoc:134-138). That order "is defined by Double#compareTo" (NumericUtils.java:41-42).
  2. The range (facetset/DimRange.java:60-81):
   if (!minInclusive) {
     min = Math.nextUp(min);        // :65-67
   }
   ...
   if (!maxInclusive) {
     max = Math.nextDown(max);      // :72-74
   }
   if (min > max) { throw ... }     // :76-78, primitive comparison
   return new DimRange(
       NumericUtils.doubleToSortableLong(min), NumericUtils.doubleToSortableLong(max));   // :79-80

Math.nextDown(+0.0) is -4.9E-324 (-Double.MIN_VALUE), sortable -2; Math.nextUp(-0.0) is +4.9E-324, sortable 1. Each step jumps over one encoded value: the other zero.

  1. Matching (facetset/RangeFacetSetMatcher.java:50-58) rejects a value below the stored min or above the stored max. -1 > -2, so [-1, 0) rejects -0.0; -1 < 0, so [0, 1] rejects it too.
  2. The integer sibling is exact. fromLongs moves an exclusive bound by exactly one encoded value (max--, DimRange.java:43-49): applied to the encoded +0.0 it gives -1 and keeps -0.0, where the double path gives -2 (executed probe).
  3. Copies. fromFloats (DimRange.java:84-104; steps at :90, :97). Range-on-range DoubleRange (rangeonrange/DoubleRange.java:39-64): Math.nextUp at :47, and under the comment // Why no Math.nextDown?, Math.nextAfter(maxIn, Double.NEGATIVE_INFINITY) at :55, which also steps from +0.0 to -Double.MIN_VALUE.

Exposure and likelihood230 words
  • Who can hit it. Bucketing that splits at zero with one exclusive bound, such as "below zero" [-1, 0) and "zero and above" [0, 1], over facet-set values that are exactly the zero of the other sign (-0.0 for that pair; +0.0 for [-1, -0.0] and (-0.0, 1]).
  • Default vs opt-in. The default IndexWriterConfig, codec and searcher suffice, but facet sets and range-on-range faceting are opt-in. The facet-set classes are @lucene.experimental (DimRange.java:26, RangeFacetSetMatcher.java:25) and range-on-range DoubleRange extends the experimental Range (rangeonrange/Range.java:24); DoubleRangeOnRangeFacetCounts itself carries no such tag (DoubleRangeOnRangeFacetCounts.java:37), and its constructors take RangeFieldQuery.QueryType, whose class is @lucene.internal (core RangeFieldQuery.java:46).
  • Scale. Per value, at any index size; assertions on and off behave the same.
  • Effect. Counts are only ever too low, by the number of such values, so bucket totals no longer add up; a covering range still counts the value. No exception.
  • Likelihood: rare. -0.0 comes from ordinary arithmetic or parsing (-1 * 0.0, Math.ceil(-0.25), Double.parseDouble("-0")), but most double data never holds one, and no public report was found in the documented searches.
  • Workaround on current releases. Write the lower bucket with an inclusive -0.0 upper bound, DimRange.fromDoubles(-1, true, -0.0, true): next to [0, 1] it counts -0.0 once, and +0.0 still goes to [0, 1] (executed on stock main, assertions on and off).

Why it looks unintended

#
  • DimRange keeps inclusive bounds and takes minInclusive/maxInclusive flags: excluding 0 should drop 0 only, as fromLongs does.
  • Facet sets match on sortable longs ordered like Double.compare; there the value just below +0.0 is -0.0.
  • Under either natural reading of the zeros, -0.0 belongs in one range, not neither; LUCENE-7594 (#8645) fixed this mismatch for point queries.
The full argument181 words
  • Contract. DimRange documents "@param min Inclusive min" and "@param max Inclusive max" (DimRange.java:24-25); fromDoubles(min, minInclusive, max, maxInclusive) takes the exclusive meaning as input (:60-61).
  • Documented order. FacetSets.adoc:134-138 puts matching in the sortable long space; NumericUtils.java:41-42 defines that order by Double#compareTo.
  • Both readings. Under Double.compare order (what the encoding does) -0.0 belongs to [-1, 0); if the zeros are treated as equal (-0.0 == 0.0) it belongs to [0, 1]. Under either of these two natural readings the value belongs in one half; the code puts it in neither.
  • Precedent. LUCENE-7594 (#8645, Dec 2016) says "Math.nextUp/nextDown is not consistent with Double/Float.compare" and added DoublePoint/FloatPoint.nextUp/nextDown (core DoublePoint.java:48-67; lucene/CHANGES.txt:8745-8747). Dawid Weiss, reviewing it, called the behaviour "trappy". Facet sets (2022) came later and never picked the helpers up: no commit has used them in lucene/facet.
  • History and tests. The #841 review discussed only Math.nextAfter(d, -Inf) versus Math.nextDown, never zeros; #11901 copied the range-on-range lines from facet.range.DoubleRange. No upstream test covering this signed-zero boundary behaviour was found.
The devil's-advocate check138 words

Strongest case for intended: the order of the zeros is not spelled out for facet sets, the API is experimental, Math.nextUp/nextDown is the standard idiom, and Lucene's own n-dimensional DoublePoint.newRangeQuery(String, double[], double[]) javadoc still says to pass Math#nextUp(lowerValue[i]) or Math.nextDown(upperValue[i]) (core DoublePoint.java:232-233; the same in FloatPoint.java:232-233).

Why it fails: the module does document its order (sortable longs, Double#compareTo). The n-dimensional paragraph was not updated by LUCENE-7594 (its commit 18d53a43f7b changed only the one-dimensional text) and is inconsistent with the one-dimensional overload just above, which recommends DoublePoint.nextUp/nextDown (:210-211); the n-dimensional javadoc itself says "Range comparisons are consistent with Double#compareTo" (:235). And under either natural reading of the zeros, -0.0 belongs in one of the two ranges. Updating that javadoc is optional and cosmetic, not part of this finding.

Suggested fix

#

Recommended Step with DoublePoint/FloatPoint.nextUp/nextDown and compare with Double.compare

Step an exclusive bound with DoublePoint/FloatPoint.nextUp/nextDown (consistent with Double.compare) instead of Math.nextUp/nextDown, and check emptiness with Double.compare/Float.compare, in DimRange.fromDoubles/fromFloats and range-on-range DoubleRange (+12/-10, 2 files). The repro and all 307 facet tests pass.

Step with DoublePoint/FloatPoint.nextUp/nextDown and compare with Double.compare (validated by the checks) (recommended)

#

In DimRange.fromDoubles/fromFloats and rangeonrange.DoubleRange, replace Math.nextUp/Math.nextDown/Math.nextAfter(x, -Inf) by DoublePoint/FloatPoint.nextUp/nextDown, and the check min > max by Double.compare(min, max) > 0 (Float.compare for floats). Shown for fromDoubles:

 if (!minInclusive) {
-  min = Math.nextUp(min);
+  min = DoublePoint.nextUp(min);
 }
 ...
 if (!maxInclusive) {
-  max = Math.nextDown(max);
+  max = DoublePoint.nextDown(max);
 }
-if (min > max) {
+if (Double.compare(min, max) > 0) {
   throw new IllegalArgumentException("Minimum cannot be greater than maximum");
 }

Trade-offs

  • Reuses the helpers Lucene added for this mismatch (LUCENE-7594); no per-document cost, the change runs once per range construction.
  • The compare change is needed: with the new stepping [0, 0) gives max = -0.0, and the primitive 0.0 > -0.0 is false, so it would slip through as a silently empty range; Double.compare keeps it rejected.
  • Behaviour changes for three signed-zero endpoint pairs (executed, stock and fixed, assertions on and off): the inverted pair fromDoubles(+0.0, true, -0.0, true) (and DoubleRange(label, 0.0, true, -0.0, true)) now throws like any min > max range instead of building a silently empty one; fromDoubles(-0.0, true, +0.0, false) and fromDoubles(-0.0, false, +0.0, true), which stock code rejects (Math.nextDown(+0.0) and Math.nextUp(-0.0) step past the other zero, so the primitive min > max check throws), now build the one-value ranges {-0.0} and {+0.0}, each counting only its own zero; fromFloats and range-on-range DoubleRange change the same way. The suggested test covers none of these. Worth a CHANGES line.
  • A semantics choice: the fix adopts the Double.compare reading, so -0.0 lands in [-1, 0). A maintainer may want to settle it together with the older facet.range.DoubleRange, which has the same stepping lines (range/DoubleRange.java:65, :72-73) and whose own signed-zero mismatch is the separate LFV-310.
  • Does not touch LFV-313: DoublePoint.nextUp(+Inf) is still +Inf.

How it was found

#

Code reading that carried a known bug pattern into the facet module: an exclusive float/double bound stepped with Math.nextUp/nextDown, which skips the other signed zero. An executed public-API probe witnessed it; a Z3 bit-vector model and a bounded-exhaustive replay on the real jar showed it is the only gap at a zero split.

The method in full171 words

Method: non-formal first signal, then a small formal check. A code-reading pass carried the signed-zero bound pattern of two earlier bugs (LFV-059, flexible query parser; LFV-1113, spatial-extras) over to the facet module and ran public-API probes on the stock main jars: -0.0 against [-1, 0) and [0, 1] counted 0 and 0 while the covering [-1, 1] counted 1, and the float, mirror and range-on-range forms did the same.

It was then reduced to the one JUnit above. A Z3 bit-vector model of the stepping, the sortable encoding and the matcher (56 queries, 64- and 32-bit) showed that "every non-NaN value lies in exactly one of two adjacent halves" fails only for the opposite-signed zero at a zero split (this gap) and for the separate exclusive-infinity defect (LFV-313, a double count); with DoublePoint/FloatPoint stepping only the infinity class remains. A bounded-exhaustive replay on the real jar (784 checks: 14 special values as split point and value, 2 split forms, double and float) agreed with the model on every row.

Applications that count DoubleFacetSet or FloatFacetSet values with RangeFacetSetMatcher ranges built by DimRange.fromDoubles/fromFloats (or range-on-range DoubleRange buckets) that meet at zero with one exclusive bound, such as 'below zero' [-1, 0) and 'zero and above' [0, 1], silently undercount every facet set whose value is the zero of the other sign (-0.0 for that pair; +0.0 for [-1, -0.0] and (-0.0, 1]), with the default IndexWriterConfig, codec and searcher, at any index size, -ea and -da alike, in every release since 9.3.0 (range-on-range since 9.5.0); both APIs are @lucene.experimental, counts are only ever too low, a covering range still counts the value, and nothing throws.
Summary
You index one document with a DoubleFacetSet holding -0.0 and count it with two RangeFacetSetMatchers, DimRange.fromDoubles(-1, true, 0, false) and DimRange.fromDoubles(0, true, 1, true), which split [-1, 1] at zero; you expect the two counts to add up to 1, because -0.0 belongs to [-1, 0) if the zeros are ordered as Double.compare orders them (the sortable order the matcher compares in) and to [0, 1] if they compare equal. Instead both counts are 0, with no error, while a covering [-1, 1] range counts the document: fromDoubles turns the exclusive max 0 into Math.nextDown(+0.0) = -Double.MIN_VALUE, which in sortable order lies below -0.0, so -0.0 falls between the two ranges. fromFloats, the mirror case (+0.0 against [-1, -0.0] and (-0.0, 1], where Math.nextUp(-0.0) skips +0.0) and range-on-range DoubleRange behave the same way.
