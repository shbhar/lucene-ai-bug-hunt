Polygon.fromGeoJSON throws NullPointerException instead of ParseException when coordinates is null or an object

Polygon.fromGeoJSON rejects a non-array coordinates with its own ParseException, but when the value is JSON null or an object {}, that check throws NullPointerException while building its error message. The bad input is rejected either way; only the exception type is wrong, in every release since 6.2.0.

The finding in 30 seconds

#

Background: GeoJSON polygons in Lucene

#
  1. GeoJSON writes a polygon as {"type":"Polygon","coordinates":[[[100.0,0.0],[101.0,0.0],[101.0,1.0],[100.0,1.0],[100.0,0.0]]]}: coordinates is an array of rings, each ring an array of [lon, lat] points. A MultiPolygon's coordinates is an array of such polygons.
  2. Polygon.fromGeoJSON(String) in Lucene core turns such text into Polygon objects, instead of building them from double[] coordinates, and declares throws ParseException for text it cannot use.

The finding, step by step

#
  1. Parse {"type":"Polygon","coordinates":"x"} with Polygon.fromGeoJSON: coordinates is a string, not an array. The parser's check rejects it: ParseException: coordinates should be an array, but got: class java.lang.String at character offset 32.
  2. Now pass {"type":"Polygon","coordinates":null} (or "coordinates":{}). You expect the same ParseException, the only exception the method declares.
  3. Instead you get NullPointerException: Cannot invoke "Object.getClass()" because "o" is null. The parser stores JSON null and nested objects as Java null, and the check builds its message with + o.getClass() (line 208).
  4. A MultiPolygon element fails the same way: {"type":"MultiPolygon","coordinates":[{}]} throws at line 90. A catch (ParseException e) misses both, while string, number and boolean values get ParseException.

Who is affected

#

Applications that call Polygon.fromGeoJSON on GeoJSON they did not produce and catch only ParseException, when coordinates is null or an object such as {}: directly, in a Feature geometry, or as a MultiPolygon element, for example from a serializer that writes null for an unset field. Rare; the input is rejected either way, and nothing wrong is returned or indexed.

Mechanism, terms and numbers618 words

Polygon.fromGeoJSON(String) declares throws ParseException and is backed by the package-private SimpleGeoJSONPolygonParser. The parser checks that "coordinates" is an array, and for a MultiPolygon that each element of it is an array, and otherwise throws ParseException("coordinates should be an array, but got: " + o.getClass()) or "elements of coordinates array should be an array, but got: " + o.getClass(). But it stores a JSON null value, and every nested object it skips, as Java null. So for {"type":"Polygon","coordinates":null}, "coordinates":{} or {"type":"MultiPolygon","coordinates":[{}]}, building the message dereferences null and java.lang.NullPointerException: Cannot invoke "Object.getClass()" because "o" is null escapes instead of the ParseException; a catch (ParseException e) does not see it. A string, number or boolean in the same place gets the intended ParseException, and every other message in the class that reports a parsed value concatenates the value itself (+ o, + point, ...), which is null-safe. (An object whose own members trip one of the parser's checks, such as {"type":null}, gets that check's ParseException first.) The input is malformed and is rejected either way: there is no wrong polygon, hang or index effect, only the wrong exception. The two messages came with the parser in LUCENE-7380 (6.2.0, 2016) and are in every release since, including 10.6.0 and main. A null-safe type name in the two messages fixes it.

Terms

#
  • SimpleGeoJSONPolygonParser: the package-private parser behind Polygon.fromGeoJSON (Polygon.java:255-257). It "does minimal parsing of a GeoJSON object, to extract either Polygon or MultiPolygon" (SimpleGeoJSONPolygonParser.java:47-51).
  • o: the Java value the parser builds for each JSON member value: a List for an array, String, Double, Boolean, or null.

The bug

#
  1. In parseObject, a nested object is parsed recursively and then, if that parse throws nothing, dropped as o = null (:146-154); the literal null also gives o = null (:163-165). In parseArray, an object element is added to the list as null (:310-313).
  2. The coordinates check (:205-209) is if (o instanceof List == false) { ... throw newParseException("coordinates should be an array, but got: " + o.getClass()); }. null instanceof List is false, so a null o enters the branch, and o.getClass() (:208) throws before the ParseException is created.
  3. The MultiPolygon element check in parse() (:86-91) does the same with "elements of coordinates array should be an array, but got: " + o.getClass() (:90).
  4. Every other message that reports a parsed value concatenates the value itself, which prints null safely: + o at :177, :182, :189, :231-232 and :239-240; + point at :256; + pointList and + pointList.get(0|1) at :262, :267 and :272.

Exposure and likelihood201 words
  • Who is hit. Callers of Polygon.fromGeoJSON (core; Polygon is @lucene.experimental) that handle bad input with catch (ParseException e), the only exception the method declares. Nothing in Lucene calls the parser on its own.
  • What it takes. Malformed GeoJSON (RFC 7946 requires coordinates to be an array) whose coordinates member is null or an object the parser skips without error (such as {}). No report to the Lucene project since 6.2.0 (2016); likelihood "rare".
  • What happens. The unchecked NullPointerException bypasses the ParseException handler, and its message says nothing about the input; on JDKs without helpful NullPointerException messages (JEP 358, on by default since JDK 15) it has no message at all. The recorded runs with assertions on and off behave the same.
  • What does not happen. No polygon is returned for the bad input, so nothing wrong is indexed or queried; no hang, no resource use, no state left behind (one parser object per call). Valid GeoJSON is not affected.
  • Related, separate fix sites (not part of this bug). Empty Polygon coordinates [] give IndexOutOfBoundsException in parsePolygon (:228, no check there); a bad \u escape gives NumberFormatException (part of LFV-569); deep nesting gives StackOverflowError (a separate finding).

Why it looks unintended

#
  • The check exists for exactly this input (coordinates is not an array, so throw ParseException). It works for strings, numbers and booleans and fails only while building its message for null and {}.
  • Every other message that reports a parsed value concatenates it (null-safe), and TestPolygon expects ParseException for malformed GeoJSON.
  • The introducing issue records "improved the ParseException throwing".
The full argument167 words
  • The branch's only job is the ParseException. SimpleGeoJSONPolygonParser.java:205-209 and :86-91 test "value is not a List" and do nothing but throw ParseException. null and objects are two of the five non-array JSON value kinds; for the other three the branch works.
  • Sibling messages. :177, :182, :189, :231-232, :239-240, :256, :262, :267 and :272 concatenate the value (o, point or pointList), which is null-safe, and those inputs get ParseException.
  • Contract and tests. Polygon.java:255 declares only throws ParseException. TestPolygon.testIllegalGeoJSONExtraCrapAtEnd (:268-281), testIllegalGeoJSONLinkedCRS (:283-302) and testIllegalGeoJSONMultipleFeatures (:305-346) expect ParseException; no test expects a NullPointerException, and none asserts the two messages.
  • Intent. LUCENE-7380 (#8433): the parser "throws an exception otherwise" for inputs it cannot handle, and the author wrote before committing "I added class level javadocs, and improved the ParseException throwing". git blame attributes both messages and the o = null branches to that commit (apart from a reformat).
The devil's-advocate check157 words

The strongest case for "intended" (an intended-behaviour checker, and a read-only reviewer from another model family, OpenAI GPT-5.6, which said "not real"): the inputs are not standard GeoJSON; the javadoc ("Parses a standard GeoJSON polygon string") has no @throws and promises no exception type for malformed input; Polygon is @lucene.experimental and the parser calls itself minimal; a throws clause never excludes unchecked exceptions; and the parser has other unchecked exits on malformed input, so "always ParseException" was never achieved.

Why it fails: the claim does not rest on an outside contract but on the parser's own check, which detects exactly this input and tries to throw ParseException; a slip in the message expression stops it. The refuting reviewer conceded that null "reaches a NullPointerException instead of the intended local ParseException branch" and agreed with the root cause. The other unchecked exits are places with no check at all. The argument limits severity (low), not validity.

Suggested fix

#

Recommended A. A null-safe type name in both messages

Build the two messages with a null-safe type name: a 3-line helper typeName(o) returns "an object or null" for null, else o.getClass(), so string, number and boolean messages are unchanged. With it the repro passes with assertions on and off, and the 18 org.apache.lucene.geo test classes and :lucene:core:check pass.

-              "elements of coordinates array should be an array, but got: " + o.getClass());
+              "elements of coordinates array should be an array, but got: " + typeName(o));
 ...
-          throw newParseException("coordinates should be an array, but got: " + o.getClass());
+          throw newParseException("coordinates should be an array, but got: " + typeName(o));
 ...
+  /** Describes a parsed value for an error message; objects and JSON null are parsed as null. */
+  private static String typeName(Object o) {
+    return o == null ? "an object or null" : o.getClass().toString();
+  }
All options and trade-offs3 options · 519 words

Two options were run through gradle in a scratch worktree of 645d4fe14a20; A is recommended. A fix conflicts textually with open PR #12295, which rewrites the same two checks but keeps getClass().

A. A null-safe type name in both messages (validated by the checks) (recommended)

#

In SimpleGeoJSONPolygonParser (:90, :208), plus a small helper.

-              "elements of coordinates array should be an array, but got: " + o.getClass());
+              "elements of coordinates array should be an array, but got: " + typeName(o));
 ...
-          throw newParseException("coordinates should be an array, but got: " + o.getClass());
+          throw newParseException("coordinates should be an array, but got: " + typeName(o));
 ...
+  /** Describes a parsed value for an error message; objects and JSON null are parsed as null. */
+  private static String typeName(Object o) {
+    return o == null ? "an object or null" : o.getClass().toString();
+  }

Trade-offs

  • Messages for string, number and boolean values stay exactly as they are (class java.lang.String, ...).
  • null and objects both read "but got: an object or null": the parser cannot tell them apart after parsing.
  • Error path only: no change to the public API signature, to successful parses or to performance; only the two messages change for null and object values.

B. Print the value, like the sibling messages (+ o) (validated by the checks)

Replace + o.getClass() by + o at :90 and :208 (two one-token changes).

-          throw newParseException("coordinates should be an array, but got: " + o.getClass());

Trade-offs

The smallest diff and consistent with the rest of the class. But {} then reads "but got: null" (misleading for an object), and string, number and boolean messages change from the class name to the value (for example "but got: x"); no test asserts the old text.

Represent objects by a non-null marker (not tried)

Have parseObject/parseArray keep a marker (for example an empty map) for nested objects so the messages can say "an object".

Trade-offs

Touches the value model that features arrays and parsePolygon rely on: more change than this bug needs. Not tried.

Downstream note

#

An application that validates client GeoJSON with Polygon.fromGeoJSON and catches only ParseException lets this NullPointerException escape its handler, so a bad request may surface as an internal error.

How it was found

#

Non-formal: a randomized differential test, written to compare a fix for a sibling GeoJSON parser bug with the stock parser, saw both parsers throw NullPointerException on documents with "coordinates": {}. Reading the code found the two getClass() messages, and a public-API JUnit test reproduced it.

The method in full150 words

Method: non-formal (randomized differential testing, then code reading and executed tests). On 2026-10-28 the hunt unit for the GeoJSON and WKT parsers (siblings of #16423) was checking its fix for a per-level path-string memory bug in the same parser: a differential test ran random GeoJSON-like documents through the fixed parser and a renamed copy of the stock one. Both threw NullPointerException on documents with "coordinates": {}. That was not a difference between them, but it was a lead: reading SimpleGeoJSONPolygonParser found the two + o.getClass() messages and the o = null value branches. A 4-test public-API JUnit (null, {}, MultiPolygon [{}], a string control) reproduced it on the stock jar; independent checkers then reproduced it with their own tests, and it was cut to the one-test repro. The finder labelled it semi-formal; it is classed as non-formal because no model, proof or bounded-exhaustive check gave the signal.

Searches5 searches

The port that writes it down (read-only GitHub API, 2026-11-01). The public repository huyz0/lucene-rust, a Rust port of Lucene 10.5.0, added its port of this parser in commit 634835d7cb (2026-10-02; the API lists no PR for it). Its module comment says Java's o.getClass() on a null value (NullPointerException) escapes "as Java's runtime exceptions do"; its value type notes that JSON null and a nested object both become null; it returns the Java message Cannot invoke "Object.getClass()" because "o" is null for a null value; and a unit test asserts that {"type": "Polygon", "coordinates": null} gives that error. Its PR #33 (merged 2026-10-28, the day the hunt found the bug) shows the comment as diff context and edits the parity-table row for SimpleGeoJSONPolygonParser, which lists NullPointerException among the exceptions that "escape as Java's". The port copies the behaviour on purpose, calls it Java behaviour rather than a bug, and never reported it to Lucene. The hunt's first searches missed it (code search does not index the repository).

Hits applications that call Polygon.fromGeoJSON (core; Polygon is @lucene.experimental; the method has no production caller in the Lucene tree) on malformed GeoJSON whose "coordinates" member is null or an object (for example {}), directly, inside a Feature's geometry, or as an element of a MultiPolygon's or a FeatureCollection feature's coordinates, and that rely on the declared ParseException to reject bad input: they get an unchecked java.lang.NullPointerException instead, which a catch (ParseException) handler does not see; the input is rejected either way (no polygon is returned), nothing hangs, no index is touched, no setting or scale is involved, with -ea and -da, in every release from 6.2.0 to 10.6.0 and on main.
Summary
You call Polygon.fromGeoJSON on a GeoJSON Polygon whose "coordinates" is null or an object, such as {"type":"Polygon","coordinates":null}, or on a MultiPolygon with an object element, {"type":"MultiPolygon","coordinates":[{}]}, and expect the ParseException that the parser has an explicit check for ('coordinates should be an array, but got: ...', 'elements of coordinates array should be an array, but got: ...'), as you get when coordinates is a string, a number or a boolean. Instead java.lang.NullPointerException ('Cannot invoke "Object.getClass()" because "o" is null') escapes, because SimpleGeoJSONPolygonParser stores JSON null and nested objects as Java null and both checks build their message with + o.getClass(). Every other type check in the class builds its message with + o, which is null-safe.
