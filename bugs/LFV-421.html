BpVectorReorderer turns a zero centroid into NaN when half of a split's vectors cancel out

In unreleased main and branch_11x, BpVectorReorderer scales each half's DOT_PRODUCT or COSINE vector sum to length 1, so a half whose vectors cancel out gets a NaN centroid. With assertions on, reordering throws and a reordering merge closes the IndexWriter; with them off, that split is not refined.

The finding in 30 seconds

#

A half of a split whose vectors cancel out has no direction, but the reorderer still divides its vector sum by the sum's length, which is 0.

How BP vector reordering works

#
  1. BpVectorReorderer (lucene/misc; main and branch_11x, unreleased) renumbers the documents of a segment so that similar vectors get nearby doc IDs. It is opt-in: you call computeDocMap, run its offline tool, or plug it into BPReorderingMergePolicy.
  2. It splits the documents in half by doc ID and gives each half a centroid. For DOT_PRODUCT and COSINE the centroid is the sum of the half's vectors, scaled to length 1.
  3. Each document gets a bias, how much more it prefers the other half's centroid, and documents swap halves by bias for up to 20 rounds. Then each half is split again, until the halves would have fewer than 32 documents.

The finding, step by step

#
  1. Index 64 documents with a 2-dimensional DOT_PRODUCT vector field: docs 0-31 alternate (1, 0) and (-1, 0), docs 32-63 are (0, 1), all unit vectors. Reorder the segment with BpVectorReorderer.computeDocMap, or merge it through BPReorderingMergePolicy.
  2. With the default minPartitionSize of 32 the reorderer splits once, docs 0-31 against docs 32-63, and describes each half by its vector sum scaled to length 1. You expect a doc map, as for any other legal vectors.
  3. Docs 0-31 sum to (0, 0). The scale factor is 1/sqrt(0) = Infinity, and 0 × Infinity makes that half's centroid (NaN, NaN).
  4. With assertions on, Lucene's own finite check fails: AssertionError: not finite: NaN from <[1.0, 0.0],[NaN, NaN]>, and a reordering merge closes the writer. With assertions off nothing throws, but that split stays in doc-ID order.

Who is affected

#

Only unreleased main and branch_11x: applications that opt into BpVectorReorderer on a DOT_PRODUCT or COSINE field, through BPReorderingMergePolicy, computeDocMap or the offline tool. In practice it takes a half of 32 or more vectors that sums to exactly zero, which needs symmetric or synthetic data. The visible failure needs assertions on, as in test suites.

Mechanism, terms and numbers522 words

BpVectorReorderer (lucene/misc; main and branch_11x, unreleased; opt-in) renumbers documents so that similar vectors get nearby doc IDs. For DOT_PRODUCT and COSINE, computeCentroid sums a half's vectors and scales the sum by 1 / (float) Math.sqrt(VectorUtil.dotProduct(centroid, centroid)) with no zero check (BpVectorReorderer.java:279-281). When the vectors of a half cancel out exactly, for example 32 documents alternating (1, 0) and (-1, 0), the sum is (0, 0), the factor is Infinity and the centroid becomes (NaN, NaN). The next dot product with it trips Lucene's own finite-result assertion (VectorUtil.java:68-75): AssertionError: not finite: NaN from <[1.0, 0.0],[NaN, NaN]>. Through BPReorderingMergePolicy that error fails the merge and IndexWriter closes as a tragic event. With assertions off nothing throws and the doc map is a valid permutation, but the NaN biases leave that split in doc-ID order. The inputs are legal unit vectors with default settings; the class comment states no non-zero precondition for the centroid, and upstream fixed a closely related NaN-centroid assertion in another class as a bug (#15209 / #15213, where the centroid had zero samples). Skipping the normalization when the squared norm is 0 fixes it; no release contains the class.

The bug, step by step (main 645d4fe14a20)

#
  1. Split. ReorderTask.compute splits a partition in half when each half has at least minPartitionSize documents (BpVectorReorderer.java:207-215; default 32, AbstractBPReorderer.java:25) and computes one centroid per half (:224-225). With 64 documents there is exactly one split, docs 0-31 against docs 32-63.
  2. Centroid. computeCentroid (:267-283) adds up the half's vectors. EUCLIDEAN and MAXIMUM_INNER_PRODUCT then divide by the count (:278); DOT_PRODUCT and COSINE scale by 1 / (float) Math.sqrt(VectorUtil.dotProduct(centroid, centroid)) (:279-281). For docs 0-31 the sum is (0, 0): the dot product is 0, sqrt(0) is 0, 1/0 is Infinity, and vectorScalarMul (:481-485) multiplies each 0 by Infinity, which gives NaN.
  3. Bias. computeBias (:564-574) returns dotProduct(vector, rightCentroid) - dotProduct(vector, leftCentroid).
  4. Assertions on. VectorUtil.dotProduct(float[], float[]) asserts a finite result (VectorUtil.java:68-75). Doc 0, (1, 0), against the NaN centroid fails it: AssertionError: not finite: NaN from <[1.0, 0.0],[NaN, NaN]>, thrown from computeBias (:571) inside computeDocMap (:591).
  5. On the merge path. BPReorderingMergePolicy catches only NotEnoughRAMException around computeDocMap (BPReorderingMergePolicy.java:133-146), and IndexWriter.merge hands any Throwable to tragicEvent (IndexWriter.java:5109-5113), which closes the writer.
  6. Assertions off. Every bias is NaN, so gain (:324) and scale (:315) are NaN and the stop test 500 * gain <= scale (:336) is false. The selector compares biases with Float.compare, which treats NaN as equal to NaN, and breaks ties on doc ID (:353-357), so the split stays in doc-ID order. Recursion then continues where the halves are large enough (read; in the repro the 32-document halves are too small to split again), and the doc map is always a valid permutation.

The same line is reached after a round of swaps too, because centroids are recomputed from scratch after every round that moved documents (MAX_CENTROID_UPDATES = 0, :88, :240-248; read, not executed separately).

Exposure and likelihood411 words
  • Entry points. BPReorderingMergePolicy (forced merges were executed; natural merges are reordered too, since minNaturalMergeNumDocs defaults to 1, BPReorderingMergePolicy.java:46, read only), the public computeDocMap (executed), and the offline main() / reorderIndexDirectory tool (BpVectorReorderer.java:653-697, read only).
  • What it takes. A half of a split, at least 32 documents with default settings, whose float32 vector sum has a squared norm of 0. In practice that is a sum that is exactly zero: antipodal pairs such as (1, 0) and (-1, 0), or v, v, v, -3v for COSINE. Learned embeddings essentially never cancel exactly; test fixtures and generated vectors can. Strictly, a non-zero sum whose square underflows does it too: 32 COSINE vectors (Float.MIN_VALUE, 0) sum to (4.5E-44, 0), whose squared norm is 0 (arithmetic checked through VectorUtil.dotProduct, not run through the reorderer); the recommended fix covers that too. EUCLIDEAN and MAXIMUM_INNER_PRODUCT divide by the count and are not affected: an executed EUCLIDEAN control passes; for MAXIMUM_INNER_PRODUCT this is from the code.
  • With assertions on (most of Lucene's own test runs, and downstream test suites that enable them): computeDocMap throws, and a reordering merge fails and closes the writer. In an executed probe the 8 documents added after the last commit were lost (116 live documents instead of 124) and a fresh writer failed the same forced merge again; the last commit stayed intact and CheckIndex-clean, so the demonstrated loss is the changes since the last commit.
  • With assertions off (the Java default): nothing throws, the merge succeeds, every document keeps its own vector, deletes stay deleted and CheckIndex is clean. The cancelling split is just not refined. On the repro's own 64 documents stock main (assertions off) and the fixed code both return the identity doc map, so nothing differs there; on another 128-document set (docs 0-63 alternate (0, 1) and (0, -1), the rest are 48 × (0, 1) and 16 × (1, 0)) the mean dot product of adjacent documents is -0.244 on stock main and 0.496 with the fix. The cost in compression or search speed was not measured.
  • Not slower, in one probe. The NaN path stops early: 16,384 64-dimensional antipodal-pair vectors took 15.5 ms against 272 ms for random unit vectors, with 0 documents moved (medians of 3 runs on one machine).
  • How likely. Rare. The searches found no upstream report or CI failure of this kind since the class was added in January 2025; a search cannot prove there is none.

Why it looks unintended

#
  • The class comment sets no non-zero precondition; a zero sum has no direction, so keeping a zero centroid is natural.
  • Lucene's own arithmetic makes the NaN from legal unit vectors and default settings, and it trips Lucene's own finite-result assertion.
  • Upstream fixed a closely related NaN-centroid assertion elsewhere as a bug (#15209 / #15213, a centroid with zero samples).
The full argument330 words
  • The class comment sets no non-zero precondition. BpVectorReorderer.java:57-75 derives the centroid as sum(v) / n. Its last sentence starts with the max-inner-product case and ends: "since all collinear vectors of whatever scale will generate the same partition for these angular scores, we are free to choose any scale and ignore the normalization factor" (:71-74). It says nothing about a zero sum, which has no direction to normalize; keeping it as a zero centroid is a natural convention, though the comment does not settle it.
  • Legal input, default settings. (1, 0), (-1, 0) and (0, 1) are unit vectors, as the DOT_PRODUCT javadoc asks (VectorSimilarityFunction.java:52-58); KnnFloatVectorField's value checks reject non-finite components (KnnFloatVectorField.java:105) and, for COSINE, the all-zero vector (:53-56); its other checks cover null, empty and over-long vectors.
  • The assertion predates the class. The finite-result assertion in VectorUtil.dotProduct came with #12281 (2023); #15213 (2025) only added its "not finite" message. The reorderer was written against it.
  • Upstream treats this symptom as a bug. In #15209 a NaN centroid tripped the same assertion in the scalar-quantization writer. benwtrent wrote "it does smell like a bug. The centroid is nan", and msokolov, who also wrote BpVectorReorderer, answered "Seems like divide by zero when there are no samples. I'll post a fix". #15213 fixed that writer only. The zero centroid there came from an empty sample set, not from cancellation: a close precedent, not the same root cause.
  • The merge policy avoids failing merges over reordering, for low RAM. Its javadoc: when reordering lacks RAM, "it simply skips reordering in order not to fail the merge" (BPReorderingMergePolicy.java:34-39). That covers only the out-of-RAM case: a hint of intent, not a contract for this one.
  • No comment, test or discussion covers a zero sum. The upstream DOT_PRODUCT test uses random angles on the unit circle (TestBpVectorReorderer.java:272-310), so no half cancels; the #14097 review of computeCentroid was about a stray semicolon.
The devil's-advocate check219 words

The strongest case for "not a bug": the failure is an assertion, so production (assertions off) never throws; the doc map is then a valid permutation and the DocMap contract promises no reorder quality; the data is degenerate (an exactly cancelling half of 32 or more vectors); and the class is unreleased and, in its author's words in #15219, "hasn't gotten a lot of real-world testing".

Why it fails: Lucene uses these assertions as invariants and runs most of its own tests with them on (about 75% of seeds by default), so legal input that trips one is a bug, as #15209 / #15213 show for the same assertion with a close mechanism (a centroid normalized with zero samples). The DocMap contract indeed promises no reorder quality, so the case rests on that invariant and on the effect with assertions off, which is not a designed fallback: it works only because Float.compare orders NaN and ties break on doc ID, and it skips refinement that the fixed code performs (-0.244 against 0.496 on the 128-document set). Degenerate but legal data lowers the priority, not the validity. GPT review lenses rated the intended argument weak; a later GPT fact check rated it moderate and still called it a bug, because of the effect with assertions off and the #15213 precedent.

Suggested fix

#

Recommended Skip the normalization when the squared norm is 0

Skip the normalization when the half's squared norm is 0 and keep the zero centroid (a few lines in computeCentroid). The repro then passes with assertions on and off, and the whole lucene/misc test suite passes (317 tests, 0 failures).

case DOT_PRODUCT, COSINE -> {
  float norm2 = VectorUtil.dotProduct(centroid, centroid);
  // vectors that cancel out (e.g. v and -v) have no direction: keep the zero centroid
  // rather than scaling it by 1/0, which turns it into NaN
  if (norm2 > 0) {
    vectorScalarMul(1 / (float) Math.sqrt(norm2), centroid);
  }
}
All options and trade-offs3 options · 551 words

One option was validated with gradle on 645d4fe14a20; a second was run as a data point; a third is a design question.

Skip the normalization when the squared norm is 0 (validated by the checks) (recommended)

#

In computeCentroid, compute the squared norm once and scale only when it is positive, so a half whose vectors cancel keeps the zero centroid. A zero centroid adds 0 to every bias, so documents are placed by the other half's centroid alone and the split is still refined. This is the finder's guard.

case DOT_PRODUCT, COSINE -> {
  float norm2 = VectorUtil.dotProduct(centroid, centroid);
  // vectors that cancel out (e.g. v and -v) have no direction: keep the zero centroid
  // rather than scaling it by 1/0, which turns it into NaN
  if (norm2 > 0) {
    vectorScalarMul(1 / (float) Math.sqrt(norm2), centroid);
  }
}

Trade-offs

  • Nothing changes for a half whose squared norm is positive: the same expression runs.
  • When both halves are zero, gain and scale are 0 and the existing stop test ends the round.
  • Matches the class comment ("free to choose any scale") and the "don't normalize" fix of #15213.
  • Open PR #15430, which moves the class to core, copies the unguarded line and would need the same change.
  • The guard targets a squared norm of 0, including a sum of tiny vectors whose square underflows. A squared norm that overflows to Infinity (very large COSINE vectors) is a separate edge it leaves as it is: with assertions on, VectorUtil.dotProduct(centroid, centroid) itself asserts; with them off the factor is 0 and the centroid becomes zero (arithmetic checked, not run through the reorderer).

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20: the repro fails on stock main with assertions on and passes with this fix, with -Ptests.asserts=true and =false.
  • With the fix: TestBpVectorReorderer 8 tests, 0 failures; the whole lucene/misc suite 24 classes, 317 tests, 0 failures, 9 skipped; :lucene:misc:check -x test passes with the repro test in place once ./gradlew tidy has wrapped its long comment.
  • Earlier runs of the same guard: an independent 4-test reproducer (DOT_PRODUCT, COSINE, merge path, EUCLIDEAN control) 4 of 4 with assertions on, and the merge in the integrity probe completes with assertions on.
  • On the 128-document set it reorders the split that stock main leaves in doc-ID order (mean adjacent dot product 0.496 against -0.244).

Divide by the count for every similarity (validated by the checks)

#

Use sum(v) / n, the centroid the class comment derives, for DOT_PRODUCT and COSINE too. A zero sum then stays zero.

Trade-offs

Changes the centroids, and possibly the order, for DOT_PRODUCT and COSINE inputs whose two halves' mean vectors differ in length: the bias becomes dot(v, sumR / nR - sumL / nL) instead of dot(v, unit(sumR) - unit(sumL)). It would need a reorder-quality benchmark.

What the checks validated

Data point only: with this change the repro passes with assertions on and the 8 upstream TestBpVectorReorderer tests pass (gradle, seed DEADBEEF); no quality comparison was run.

Design question: sum normalized vectors for COSINE

#

Whether COSINE centroids should sum each document's normalized vector, so every document weighs the same, rather than the raw vectors.

Trade-offs

A separate change; untested. It does not remove the zero case by itself, because antipodal unit vectors still cancel.

Downstream note

#

Downstream code on main that enables BpVectorReorderer and runs its tests with assertions on can see reordering and merges fail on symmetric synthetic vectors; with assertions off the index stays intact and only some reordering is lost.

How it was found

#

Semi-formal: a bounded-exhaustive harness ran computeDocMap from the real jar on every segment of up to 7 documents with 1-dimensional vectors (-1, 0 or +1; no 0 for DOT_PRODUCT, COSINE) for all four similarities. With assertions on it hit 12,736 'not finite: NaN' failures; with them off, 0 doc-map violations in 401,744 checks. A JUnit test with default settings followed.

The method in full160 words

Method: bounded-exhaustive translation validation (the study's "semi-formal" tier). The harness enumerated every segment of up to 7 documents, each with no vector or a 1-dimensional vector in {-1, 0, +1} (without 0 for DOT_PRODUCT and COSINE, which ask for unit or non-zero vectors), under all four similarity functions, with minPartitionSize 1 or 2 and maxIters 1 or 20, and checked each computeDocMap result from the stock main jar against the DocMap contract (a permutation of the live documents).

  • With assertions on: 12,736 runs failed with AssertionError: not finite: NaN, for example the DOT_PRODUCT segment (-1), (1), (-1) with minPartitionSize 1, whose second half (1), (-1) sums to 0.
  • With assertions off: 401,744 checks, 0 violations, 0 exceptions. So every doc map in this domain was valid; the defect is the NaN itself.

The finder then wrote a JUnit test with default settings (128 documents, computeDocMap and a reordering merge), which was later reduced to the one 64-document test above.

LFV-421, snapshot of 2026-11-10

Registry title
BpVectorReorderer scales a zero DOT_PRODUCT/COSINE centroid by 1/sqrt(0), so a split whose vectors cancel out gets a NaN centroid: with assertions on, reordering fails and a reordering merge closes the IndexWriter; with assertions off, that split is silently not refined
Area
misc / BP merge-time reordering (BpVectorReorderer centroid arithmetic)
Priority
Low, rank 1234: This unreleased NaN centroid shows only with assertions on, on contrived exactly-cancelling vectors, and the audit downgraded it.
Impact class
minor
Impact note
Only applications on unreleased main and branch_11x (11.0.0-SNAPSHOT) that opt into the lucene/misc BpVectorReorderer (through BPReorderingMergePolicy, computeDocMap or the offline tool) on a DOT_PRODUCT or COSINE float vector field, and only when the vectors of one half of a recursive split (at least minPartitionSize, default 32, documents) sum to exactly zero in float32, as with symmetric or synthetic data such as alternating (1,0)/(-1,0): with Java assertions enabled (-ea, for example test suites) reordering throws AssertionError and a reordering merge closes the IndexWriter as a tragic event, losing the uncommitted documents; with assertions disabled (the production default) nothing throws, the DocMap is a valid permutation and the only effect is that this split stays in doc-ID order; ordinary scale (64 documents suffice).
Summary
You index DOT_PRODUCT or COSINE float vectors and reorder them with BpVectorReorderer, by calling computeDocMap or by merging through BPReorderingMergePolicy, for example 64 legal unit vectors where docs 0..31 alternate (1,0) and (-1,0) and docs 32..63 are (0,1); you expect a valid reordering, as for any other legal vectors. Instead the half whose vectors cancel out sums to the zero vector, computeCentroid normalizes it by 1/sqrt(0) = Infinity and the centroid becomes NaN. With assertions on, VectorUtil.dotProduct then fails with 'AssertionError: not finite: NaN from <[1.0, 0.0],[NaN, NaN]>' and the merge path closes the IndexWriter; with assertions off nothing throws, but the NaN biases leave that split in doc-ID order.
