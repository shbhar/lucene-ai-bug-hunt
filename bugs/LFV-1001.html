On main, LRUQueryCache.cleanUp() deadlocks with subclasses whose statistics callbacks are synchronized

On main, LRUQueryCache.cleanUp() locks the cache object and then waits for a partition lock, while a search holds that lock and calls your statistics callback. If the callback is synchronized, both wait forever and later searches hang behind them; no release is affected.

The finding in 30 seconds

#

Two locks taken in opposite order. cleanUp() holds the cache object's monitor and waits for a partition lock; a search holds that partition lock and, inside your synchronized callback, waits for the monitor.

Background

#
  1. Partitions. On main, LRUQueryCache is split into partitions (16 by default), each with its own read/write lock. A search that looks up a cached entry holds its partition's read lock; one that inserts an entry holds the write lock.
  2. Statistics callbacks. The cache calls onHit, onMiss, onCacheEntryInserted and onCacheEntryEvicted while it holds that partition lock. Subclasses override them to keep their own statistics, as the class javadoc suggests.
  3. cleanUp(). On main, stale entries (of closed segments, or of queries passed to clearQuery()) are not removed right away. cleanUp() removes them, run by a background thread you configure or by your own periodic calls.

The finding, step by step

#
  1. You subclass LRUQueryCache to count cache inserts and make the counter thread-safe the plain Java way: synchronized (this) { inserted++; } in onCacheEntryInserted. On main, stale entries are removed only by cleanUp(), which a background thread or your own code runs.
  2. A search caches a result: Lucene takes the partition's write lock and calls your onCacheEntryInserted. At that moment cleanUp() runs, because 1 query was cleared with clearQuery(). cleanUp() is synchronized, so it holds the cache object's monitor, and it now waits for the partition lock.
  3. You expect both to finish within milliseconds, as the same subclass does on 10.x, where Lucene never locks the cache object.
  4. Instead your callback waits for the monitor that cleanUp() holds, and cleanUp() waits for the lock the search holds. In the repro (1 document, 1 partition, 1 search), after 10 s the search is BLOCKED and cleanUp() is WAITING, and the JVM reports a Java-level deadlock.
  5. It also happens on its own under load: with 3 search threads, background cleanup every 1 s and NRT refresh, 3 of 3 runs hung within 2 s, with the search threads stuck behind the cleanup thread. With cleanUp() on a private lock: 12,978,280 searches in 30 s, no hang.

Who is affected

#

Applications on main / the coming 11.0 that subclass LRUQueryCache and guard callback statistics with synchronized on the cache, while cleanup runs (background or periodic cleanUp(), which main requires). Atomics or a private lock are safe; the query cache is off by default. With the idiom in place, ordinary search load hangs within about 2 s.

Mechanism, terms and numbers685 words

On main, LRUQueryCache.cleanUp() is public synchronized: it holds the cache object's monitor while it takes each partition's read lock in keys() and the write lock in the partition remove(). Searches call the statistics callbacks while they hold a partition lock: onCacheEntryInserted under the write lock, onHit and onMiss under the read lock. A subclass that makes its counters thread-safe with synchronized methods or synchronized (this), the plain Java idiom, therefore takes the two locks in the opposite order to cleanUp(), and the two threads deadlock as soon as cleanUp() has stale entries to remove while a search is in such a callback. The hang is permanent and uninterruptible: every later cleanUp(), every search whose callback needs the monitor, and every other search that looks up or inserts in that partition queue behind it. The class says "This class is thread-safe.", invites callback overrides for statistics, and calls cleanUp() "safe to call concurrently"; on main cleanUp() must run, from a background scheduler or the caller. On 10.x the same subclass is safe, because LRUQueryCache there locks only a private lock. The modifier came with #15558 (2026-04-14), so only main and branch_11x are affected. Moving cleanUp() to a private lock object removes the cycle without changing what the cache stores or evicts; with it the repro passes, and so do 2,339 tests of the org.apache.lucene.search package.

The code (main 645d4fe14a20, LRUQueryCache.java)

#
  1. cleanUp() takes the cache monitor. public synchronized void cleanUp() (:1392). It copies the stale-key sets and returns early if both are empty (:1393-1399). Otherwise, still holding the monitor, it iterates keys() (:1404), which visits every partition (:214-222) and takes each partition's read lock (:1025) just long enough to copy its keys (released at :1029), and then calls the partition remove() for each stale entry (:1410), which takes the write lock (:1156) and fires onCacheEntryEvicted under it (:1183). There is no read-to-write upgrade: the monitor is the only lock cleanUp() holds across these steps.
  2. Stale entries are ordinary. clearQuery() marks a query (:451-455, :1250-1256); a closed segment marks its key through clearCoreCacheKey() (:443-448). On main they are not removed inline: cleanUp() must run, from the scheduler configured with CacheCleanUpParameters (:197-204, scheduleWithFixedDelay(this::cleanUp, ...)) or from the caller (:103-113).
  3. Searches call the callbacks under partition locks. putIfAbsent() takes the write lock (:1100) and calls onCacheEntryInserted (:1126); get() takes the read lock (:1064) and calls onMiss or onHit (:1071-1077).
  4. The cycle. The search holds a partition lock and waits for the cache monitor in the subclass callback; cleanUp() holds the monitor and waits for that partition lock. In the repro cleanUp() parks on the read lock in keys(), blocked by the search's write lock. With synchronized onHit, cleanUp() waits for the write lock in remove() while searches hold read locks; the JVM's deadlock detector does not report that variant, because a read lock has no owner.
  5. The monitor is used nowhere else. No other method locks the cache object (:445 locks keysToClean, :960 is a Collections.synchronizedMap with its own mutex). The second lock exists only because of the modifier, whose job is to serialize concurrent cleanUp() calls. Javadoc does not render synchronized, so the API docs show public void cleanUp().

What happens next

#

Monitor entry and lock() ignore interrupts and timeouts, so the pair never returns. Every later cleanUp() and every search whose callback needs the monitor block behind them, and so do all other searches that look up or insert in that partition and every clearQuery() call (it takes each partition's write lock, :1250-1256), because the stuck search holds that partition's write lock. With synchronized onHit/onMiss, that is every search that consults the cache. Searches that skip the cache (segment not cacheable, not eligible, or without a core cache helper: :816-831) are not blocked. Lucene logs nothing about it; results and the index are not damaged.

Exposure and likelihood303 words
  • Who. Applications on main / 11.0 with an LRUQueryCache subclass whose callbacks synchronize on the cache object (synchronized methods or synchronized (this)), that run cleanUp() while searching, through the background scheduler or their own periodic calls.
  • Opt-in. The query cache is off by default on main (IndexSearcher.java:84, GITHUB#14187), and the stock callbacks use LongAdder. Subclasses with atomics or a private lock are not affected (executed controls).
  • Why the idiom is likely. On main, callbacks of different partitions run at the same time (LFV-1000) and onHit/onMiss run under a shared read lock, so subclasses now need their own synchronization, and synchronized is the default Java choice. The Elasticsearch and OpenSearch subclasses say today "It's ok to not protect these callbacks by a lock since it is done in LRUQueryCache"; neither synchronizes on the cache, so neither is known to hit this.
  • Scale: none needed. The finder's stress (3 search threads, background cleanup every 1, 100 or 1000 ms) hung after about 1 s in 5 of 5 runs, an independent stress in 7 of 7. A workload with nothing waiting inside a callback (16 partitions, cleanup every 1 s, NRT refresh closing merged segments) hung within 2 s in 3 of 3 JVMs, and 3 of 3 with clearQuery() on 1 in 20 searches. Controls, 30 s each: with the fix 12,978,280 searches, with a private-lock subclass on stock main 10,485,017, no hang.
  • Effect. A permanent hang of the cleanup thread and of searches that consult the cache; no wrong results, no index damage.
  • How likely. Rare: none of the four public downstream subclasses surveyed (Elasticsearch, OpenSearch, nrtsearch, mongot) uses the idiom today, and the code is unreleased.
  • Workaround. Keep subclass statistics in atomics or LongAdder, or under a private lock object, never under this.

Why it looks unintended

#
  • The class is "thread-safe", invites callback overrides for statistics, and calls cleanUp() "safe to call concurrently"; nothing names the cache monitor or a lock order.
  • No release takes the cache monitor together with another lock, so the same subclass works on 10.x; #15558 added the modifier without discussing it.
  • A private lock keeps cleanUp() serialized and removes the cycle.
The full argument214 words
  • The contract. "This class is thread-safe." (LRUQueryCache.java:64). The class javadoc invites overriding the callbacks "to have more fine-grained statistics" (:88-101). cleanUp(): "This method is safe to call concurrently." (:1384), and on main it must run (:103-113).
  • Lucene's own migration example for #15558 is a class MyQueryCache extends LRUQueryCache that overrides onCacheEntryInserted and onCacheEntryEvicted, with no locking caveat (lucene/MIGRATE.md:514-542).
  • It worked before. Since LUCENE-7237 (2016, Adrien Grand) the cache has locked only a private lock, a ReentrantReadWriteLock since #13306 (10.5.2 and 10.6.0 LRUQueryCache.java:100-101). In 2015 (LUCENE-6303, releases 5.1 to 6.0) the methods that read or change the cache's state (get, putIfAbsent, eviction, the clear* methods) were synchronized on the cache, its only lock and re-entrant, so no cycle was possible. No release has cleanUp().
  • Nobody decided it. The #15558 PR body, its 22 issue comments and 5 review comments never discuss cleanUp()'s monitor, a lock order or locking in callbacks; #16212 changed cleanUp()'s locking and kept the modifier without comment.
  • Standard Java guidance. For classes designed for inheritance, Effective Java (3rd ed., Item 82) recommends a private lock object, so that a subclass cannot "unintentionally interfere with the operation of the base class, or vice versa".
The devil's-advocate check209 words

The strongest case: the callbacks are Expert / @lucene.experimental, and the class javadoc warns "It is better to not perform heavy computations in these methods though since they are called synchronously and under a lock" (LRUQueryCache.java:99-101), so a subclass that locks inside a callback does so at its own risk, and a maintainer may prefer a javadoc note to a code change. (The independent cross-model reviewer, OpenAI GPT-5.6, raised this case.) In #10081 (LUCENE-9038, 2019) Ben Manes read that contract as: the callbacks "are executed under the global lock. This means implementations may rely on this exclusive read/write access to data structures".

Why it fails: the sentence is advice against heavy work and names no lock or lock order; a counter update is not heavy. It dates from LUCENE-6157 (2015), when "the lock" was the cache's own re-entrant monitor, so a synchronized callback simply re-entered it. Ben Manes' reading is why subclasses never needed a lock before, and why they need one now that main runs callbacks concurrently. @lucene.experimental allows API changes, not a permanent hang. The cycle needs Lucene to reuse the subclass's public monitor as an internal lock, which the rendered javadoc does not even show. Verdict: not intended. A javadoc-only answer stays possible.

Suggested fix

#

Recommended cleanUp() synchronizes on a private lock object

Serialize cleanUp() on a private final Object (synchronized (cleanUpLock)) instead of the cache object, so Lucene never takes the public monitor. Cleanups stay serialized; only code that locked the cache to keep cleanUp() out sees a change. Validated: the repro passes, and so do 2,339 tests of the org.apache.lucene.search package. Land it with LFV-991's clear() fix.

  private final Object cleanUpLock = new Object();

  public void cleanUp() {
    // A private lock, not this object's monitor: subclasses may synchronize on the cache in their
    // hit, miss, insertion and eviction callbacks, run under the partition locks cleanUp() takes.
    synchronized (cleanUpLock) {
      doCleanUp();
    }
  }

  private void doCleanUp() {
    // the former body of cleanUp(), unchanged
  }
All options and trade-offs4 options · 692 words

One fix was validated in a scratch worktree of 645d4fe14a20; the others are directions, not attempted. The cycle needs cleanUp() holding the public cache monitor and a callback that takes that monitor under a partition lock; Lucene controls the first.

cleanUp() synchronizes on a private lock object (validated by the checks) (recommended)

#

One file, +10/-1 in LRUQueryCache.java: a private final Object cleanUpLock, and cleanUp() runs its unchanged body inside synchronized (cleanUpLock). Concurrent cleanUp() calls stay serialized, the modifier's apparent purpose, but Lucene no longer takes the cache object's monitor anywhere, so a subclass's monitor is a leaf lock again, as in every release since 6.1 (2016).

  private final Object cleanUpLock = new Object();

  public void cleanUp() {
    // A private lock, not this object's monitor: subclasses may synchronize on the cache in their
    // hit, miss, insertion and eviction callbacks, run under the partition locks cleanUp() takes.
    synchronized (cleanUpLock) {
      doCleanUp();
    }
  }

  private void doCleanUp() {
    // the former body of cleanUp(), unchanged
  }

Trade-offs

  • No change to what the cache stores, evicts or reports, and cleanups stay serialized; the cleanup body is unchanged.
  • One observable change: code that synchronized on the cache to keep cleanUp() out would no longer exclude it. That was never documented, and the rendered javadoc does not show the modifier; the issue can ask the maintainers whether anyone relies on it.
  • Callbacks of different partitions still run at the same time (LFV-1000, a javadoc matter); subclasses still need their own thread-safety. With this fix, synchronizing on the cache object in a callback no longer deadlocks against cleanUp(); locks a subclass shares with other code remain its own concern.
  • The comment in the diff was reworded after the fact check to name the hit, miss, insertion and eviction callbacks (onClear() runs with no partition lock, :458-463); the code is unchanged, compiles to byte-identical class files, and google-java-format 1.37.0 leaves the patched file unchanged.
  • Land it with LFV-991's clear() fix. In the finder's TLA+ model, that fix alone (all partition locks held while onClear() runs) deadlocks with the synchronized cleanUp() (run M4); both fixes together are clean (run M3, 2,180,461 distinct states; its vacuity probe fails as required).
  • Worth adding to the class javadoc (documentation only): which locks are held during each callback, and that the cache never synchronizes on itself.

No lock in cleanUp() at all (not attempted)

#

Drop the modifier and let concurrent cleanUp() calls run in parallel, each on its own snapshot of the stale sets.

Trade-offs

Smaller in code, but whether two concurrent cleanups stay correct (RAM accounting, eviction callbacks fired once) needs its own analysis and tests; the private lock keeps today's serialization.

Document the monitor (not attempted)

#

State that cleanUp() holds the cache object's monitor and that callbacks must not synchronize on the cache.

Trade-offs

No code change, but the most common Java idiom stays a permanent hang that no release had, and the modifier stays invisible in the rendered API docs.

Fire callbacks after releasing the partition lock (larger, not attempted)

#

Collect callback events under the lock and fire them after releasing it.

Trade-offs

Removes every lock-order hazard with callbacks, but changes the documented "under a lock" behaviour and the exclusive access subclasses may rely on (#10081); a much larger change.

Downstream note

#

Downstream: the Elasticsearch and OpenSearch subclasses do not synchronize on the cache today, so neither is known to hit this. Elasticsearch is adapting to the Lucene 11 cache (elastic/elasticsearch#163523); on Lucene 11 the comment both subclasses carry, that the callbacks are already protected by a lock in LRUQueryCache, no longer holds.

How it was found

#

While building a TLA+ model of the partitioned cache's locks, reading cleanUp() to fill the model's lock table showed the synchronized modifier, a lock the model did not have. TLC found the deadlock as a 4-state trace; a JUnit on the stock jar confirmed it, and independent AI tools reproduced it with their own tests.

The method in full108 words

Method: semi-formal (a hypothesis formed while modelling, then witnessed by execution).

  • The model (LruPartClearMon.tla: the partitioned cache plus the cache monitor) deadlocks on main with a 4-state trace (run M1). It has no deadlock with cleanUp() on a private lock (M2, 491,278 distinct states) or without a monitor-synchronized subclass (M5, 1,237,688). The sibling clear() fix alone deadlocks (M4); both fixes together are clean (M3, 2,180,461), with a vacuity probe (M3v) that fails as required.
  • The finder's three-case JUnit, an independent reproducer's six-case JUnit and two no-latch stresses failed on main; the minimal test here is the insertion case cut down to one method with one partition.

History

#

Introduced by #15558 (d50fb36d9af3, merged 2026-04-14), which added cleanUp() with the synchronized modifier together with the partition locks; not backported to 10.x. Main and branch_11x are affected; no release is (10.6.0 included). Not fixed upstream as of 2026-10-31.

Versions tested5 rows

Introduced by d50fb36d9af3, apache/lucene#15558 "Refactor QueryCache to improve performance" (sgup432, merged by msfroh; design issue #14222). The modifier is already in the PR's first revision (2026-01-08). #16212 (372b1db88a5) later made keys() take every partition's read lock under the monitor, a wider window; #16657 (fadd63e0eb4) changed the partition routing, the cache-key hashCode/equals and the query RAM accounting, but none of the locks in this cycle. The PR author said on #15558 (2026-07-20) that not backporting to 10.x was "a conscious choice".

Before (no release has cleanUp()): 2015 (LUCENE-6303, releases 5.1 to 6.0) the state-changing methods synchronized on the cache, its only lock and re-entrant; 2016 (LUCENE-7237, 6.1 to 9.10) a private ReentrantLock; 2024 (#13306, 9.11 to 10.6) a private ReentrantReadWriteLock. None can form this cycle.

Finding record

LFV-1001, snapshot of 2026-11-02

Registry title
On main, LRUQueryCache.cleanUp() is synchronized on the cache object and takes partition locks while it holds that monitor, so a subclass whose statistics callbacks synchronize on the cache (synchronized methods or synchronized (this)) deadlocks the cleanup thread against a search, and every later search whose callback needs the monitor hangs too; regression from #15558, main only
Area
search / query cache (LRUQueryCache.cleanUp() locking vs the statistics callbacks)
Priority
Low, rank 690: This permanent deadlock blocks every search but is an unreleased main regression that only fires for an LRUQueryCache subclass whose callbacks synchronize on the cache, which no known public subclass does.
Impact class
hang
Impact note
Availability only, on unreleased main (11.0) and branch_11x: an application that installs an LRUQueryCache subclass whose statistics callbacks synchronize on the cache object, and runs cleanUp() while searches run (through the background scheduler it configures with CacheCleanUpParameters, or through its own periodic calls, one of which the class javadoc requires), gets a permanent, uninterruptible hang of the cleanup thread and of every search whose callback needs that monitor; when onHit/onMiss are among the synchronized callbacks, that is every search that consults the cache; stock LRUQueryCache and subclasses that use atomics or a private lock are unaffected, none of the four public downstream subclasses read uses the idiom, the default query cache is off on main (#14187), and every release, 10.6.0 (released 2026-10-29) included, is unaffected.
Summary
You subclass LRUQueryCache to keep your own statistics in the callbacks its javadoc offers (onHit, onMiss, onCacheEntryInserted, onCacheEntryEvicted) and make them thread-safe the plain Java way, with synchronized methods or synchronized (this), and you let the cache clean up stale entries as documented. You expect searches and cleanUp(), which its javadoc calls 'safe to call concurrently', to keep running, as the same subclass does on 10.x, where Lucene never locks the cache object itself; on main, cleanUp() is a synchronized method, so it holds the cache object's monitor while it waits for a partition lock, while a search holds that partition lock and waits for the same monitor inside your callback. Both threads wait for each other forever (the JVM's deadlock detector names the cycle for the insertion callback; for onHit it cannot, because a read-lock holder has no owner), and every later search whose callback needs the monitor, every clearQuery() on that partition and every later cleanUp() block behind them.
