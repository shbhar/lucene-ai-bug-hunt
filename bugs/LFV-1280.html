CharArraySet.toString() drops an empty-string element and the separator after it: {"", "a"} prints [a]

A CharArraySet holding "" and "a" (size 2) prints [a], the same as a set holding only "a": an empty first element vanishes from toString(), and so does the ", " after it. Lookups are correct; only the debug text is wrong, in every release since 3.1.0.

The finding in 30 seconds

#

A two-element set prints like a one-element set when the empty string is its first element, as it always is when it was added first.

Background: how a CharArraySet prints itself

#
  1. CharArraySet is the set Lucene's analyzers use for stop words, keywords and protected words. It stores each word as a char[] in a hash table and iterates the table's slots from 0 upward.
  2. It extends java.util.AbstractSet and overrides toString() so the char[] words print as text, in the usual Java format: [the, a, an].

The finding, step by step

#
  1. Build a set that holds the empty string: new CharArraySet(2, false), then add("") and add("a"). size() is 2.
  2. You expect [, a]: like any Java set, CharArraySet prints its elements in iterator order, in brackets, separated by ", " (the AbstractCollection.toString format it overrides).
  3. Instead toString() returns [a], exactly what the one-element set {"a"} prints. {"", "a", "b"} prints [a, b], and StopFilter.makeStopSet("", "the") prints [the].
  4. Why: before each element the method writes ", " only if the text so far is longer than "[". The empty string adds nothing, so the text is still "[" when "a" comes and no separator is written. "" hashes to 0, so it takes slot 0 and is iterated first unless another word already holds that slot (always when it is added first).
  5. Only the text is wrong: an empty element iterated later prints fine ([h, ]), and a CharArrayMap mapping "" to 1 and "a" to 2 prints {=1, a=2}, while its keySet() prints [a].

Who is affected

#

Anyone who logs, prints or compares the toString() of a CharArraySet whose first element is "": a stop, keyword or protected-word set built in code, or a CharArrayMap.keySet(). A set of 2 reads as a set of 1. Word lists loaded with WordlistLoader skip blank lines, and a source search found no Lucene production code that reads the string.

Mechanism, terms and numbers428 words

CharArraySet, the set behind Lucene's stop-word, keyword and protected-word sets, extends AbstractSet and overrides toString() so its char[] elements print as text in the usual Java format. Before each element it writes ", " only if the builder is already longer than "[", using the length to mean "an element was written". An empty-string element writes nothing, so when it is the first element iterated the next element gets no separator, and the empty element leaves no trace: the two-element set {"", "a"} prints [a], the same text as {"a"}. The empty string hashes to 0, so it takes slot 0 and is iterated first unless another word already holds that slot; it always does when it is added first, as in the repro and StopFilter.makeStopSet("", "the"). The defect leaves contents, size(), contains, iteration, analysis and the index unchanged, and a source search found no Lucene production code that reads the string. Present since 3.1.0 (2010, LUCENE-2247); a first-element flag fixes it.

The bug

#
  1. CharArraySet.toString() (CharArraySet.java:169-181 on main) starts a StringBuilder with "[" (:171). Before each element it runs if (sb.length() > 1) sb.append(", "); (:173), then appends the element (:174-178) and finally ].
  2. The length test stands for "an element was already written". A zero-length element writes nothing, so after "" the length is still 1 and the next element is appended with no separator. The empty element itself is invisible too.
  3. Why "" comes first: CharArrayMap.getHashCode returns 0 for a zero-length key in both case modes (CharArrayMap.java:267-298), getSlot places a key at code & (keys.length - 1) (:137-166), so "" takes slot 0 unless another key already holds it, and the iterator walks the slots upward from 0 (:386-390).
  4. CharArrayMap.toString (:310-318) has the same length test but is not affected: every entry prints as key=value, so it is never empty. Its keySet() is a CharArraySet (:346) and is affected.

Why it looks unintended

#
  • toString() has no javadoc of its own, so the nearest documented format is AbstractCollection.toString's: every element in iterator order, separated by ", ".
  • TestCharArraySet.testToString checks [test] and that two elements print with ", "; before 3.1.0 the inherited method printed [, a] here.
  • "" is a legal member (size() 2), added through public API such as StopFilter.makeStopSet("", "the").
The full argument204 words
  • The contract. CharArraySet.toString has @Override and no doc comment, so the nearest documented behaviour is the inherited AbstractCollection.toString's: "a list of the collection's elements in the order they are returned by its iterator, enclosed in square brackets ("[]"). Adjacent elements are separated by the characters ", " (comma and space)". The override only adds the char[]-to-text conversion and keeps that shape: a strong expectation, not a stability contract.
  • The test. TestCharArraySet.testToString (:374-379) asserts [test] for one element and that the text of a two-element set contains ", ".
  • History. Before LUCENE-2247 (3.1.0) the class inherited AbstractCollection.toString, which prints [, a] (executed on 3.0.3). The override came with the same change, which rebuilt the set on CharArrayMap, made its iterator return char[] keys (for matchVersion 3.1 and later) and was described as "toString() improvements of all views in CAS and CAM" (Uwe Schindler on #3323, 2010-02-02); nothing there says empty elements should be hidden. The same commit's CharArrayMap.toString prints an empty key.
  • The class disclaimer ("implements Set but does not behave like it should in all cases", CharArraySet.java:30-34) lists the deviations it means: Object elements, toString-based add and contains, an Iterator<char[]>. Not the rendering.
The devil's-advocate check164 words

The strongest case: toString is debug output, no production code reads it, no report of this was found in 15 years, an empty stop word is meaningless (Lucene's own TestThaiTokenizer.java:49-50 says an empty dictionary entry "REALLY does not make sense... but don't crash on it"), and on the open PR #16261 mayya-sharipova wrote (2026-06-17) that this "toString() carries no stability contract".

Why a correction is still reasonable: no stability contract lets the format change (that PR appends (ignoreCase=...)), and it weakens the claim that the AbstractCollection format binds; it does not make text that drops a member useful. In the same comment, about that suffix, they say the output "makes the set's behavior unambiguous at a glance"; [a] for a set of 2 is not. The empty string is a legal member reached through documented public API, and the fix is a few lines. Verdict: not intended, a defect, but cosmetic: it stays Low, and a maintainer may fairly call it trivial.

Downstream note

#

Downstream code that logs or displays a CharArraySet, such as an application's stop-word list built in code with a blank entry, shows the set without that entry; lookups and analysis are unaffected.

How it was found

#

A semi-formal proof-obligation audit of CharArraySet's contract: its toString must render the AbstractCollection format, every element in iterator order with ", " between adjacent ones. The length test fails that obligation for an empty element, and a one-test JUnit on the stock jars witnessed it.

The method in full134 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation came from the inherited AbstractCollection.toString javadoc and TestCharArraySet.testToString: every element, in iterator order, separated by ", ".
  • Checking CharArraySet.toString against it: sb.length() > 1 holds only if something non-empty was written, so a zero-length first element breaks the obligation; "" hashing to 0 puts it first whenever it is added first.
  • A public-API JUnit test on the stock main jars witnessed it, and a first-element flag makes it pass. An independent reproducer, a refute-lens cross-model review and a devil's-advocate verifier reproduced it (the first two with their own tests, the verifier with the original test and its own main() probe), and an adjudication re-ran the reproducer's test with a new seed ("Prior reports, history and checks").
