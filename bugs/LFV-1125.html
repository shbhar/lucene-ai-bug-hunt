PerFieldPostingsFormat's "no suffix for format name" check misses equal formats with different names once another field used the second name: the commit succeeds and a field's postings cannot be read

In PerFieldPostingsFormat, two differently named postings formats that compare equal are rejected at commit, unless another field used the second name: then the commit succeeds and one field's postings cannot be read (silently in the repro; with other group numbers the index fails to open). Needs custom codec code.

The finding in 30 seconds

#

Background: per-field postings groups

#
  1. A codec can give each field its own postings format through PerFieldPostingsFormat.getPostingsFormatForField. Fields whose formats compare equal (equals) share one set of files, named after the format and a number per name: EqA_0, EqB_0, EqB_1, ...
  2. Each field stores two attributes: the format's name and the group's number. When reading, Lucene loads the format by that name and opens the field from the files <name>_<number>.
  3. So if two formats with different names compared equal, a field could be written into one group's files while recording the other name. Lucene checks for this at commit and throws no suffix for format name.

The finding, step by step

#
  1. Your codec maps field a to format EqB(2), x to EqA(1) and y to EqB(1). EqA and EqB are your own SPI-registered formats whose equals compares only the number, so EqB(1) equals EqA(1). You index one document with a:v, x:v, y:v and commit.
  2. You expect the commit to throw IllegalStateException: no suffix for format name: EqB, as it does when the document has only x and y; or else docFreq(y:v) to be 1.
  3. Lucene groups fields by equals, so y joins x's file group EqA_0 and its postings are written there. But y records its own format name with that group's number: (EqB, 0), which is a's group.
  4. The check only asks whether any group used the name EqB. Field a did, so it passes and the commit succeeds.
  5. The reader opens EqB_0 for y, which holds only a's terms: docFreq(y:v) is 0 while x:v is found, with assertions on or off, and CheckIndex reports no problems.

Who is affected

#

Only applications whose own codec has two SPI-registered postings formats with different names that compare equal (say, an equals that compares only settings), plus an earlier-sorting field of the second name. No shipped format overrides equals. One document suffices; the loss is silent in the repro's layout, and other group numbers leave an index that fails to open.

Mechanism, terms and numbers709 words

PerFieldPostingsFormat lets a codec choose a postings format per field. Fields whose formats compare equal (PostingsFormat.equals) share one group of files, named after the format and a per-name number (EqA_0, EqB_0, ...). Each field records two attributes, its own format name (getName()) and the matched group's number, and the reader opens the field from the files <name>_<number>. Two equal formats with different names would therefore write a field into one group while its attributes point to another. Lucene guards this with an always-on check (IllegalStateException: no suffix for format name, PerFieldPostingsFormat.java:240-243 at 5adff78bb168), but the check asks whether any group used the field's name, not whether the matched group was created under it. With fields a -> EqB(2), x -> EqA(1), y -> EqB(1) (equal by setting only), y joins x's group, the check passes because a used EqB, and y records a's group: the commit succeeds, docFreq(y:v) is 0 and CheckIndex is clean. That silence needs the recorded (name, number) to name an existing group (here both numbers are 0); with other group numbers the commit also succeeds but the index then fails to open (CorruptIndexException). With only x and y the same mapping is rejected. It needs two SPI-registered formats with different names whose equals treats them as equal; no format shipped in Lucene overrides equals. Every release from 4.0.0 to 10.6.0 has it.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/codecs/perfield/PerFieldPostingsFormat.java)

#

FieldsWriter.buildFieldsGroupMapping (:199-260) is shared by flush (:143) and merge (:181). It visits fields in name order (flush: index/FreqProxFields.java:38, "fields are already sorted by field name").

  1. Groups are found by equals. formatToGroupBuilders is a HashMap<PostingsFormat, ...> (:202); formatToGroupBuilders.get(format) (:219) uses the format's equals and hashCode.
  2. Numbers are counted per name. On a miss, the next number for format.getName() comes from suffixes (:205, :224-230), and the new group writes files <name>_<number> (:232-237).
  3. The only check on a hit is if (!suffixes.containsKey(formatName)) throw new IllegalStateException("no suffix for format name: ...") (:240-243): has any group used this name? This is the fix site.
  4. The field records its own name and the matched group's number: PER_FIELD_FORMAT_KEY = formatName, PER_FIELD_SUFFIX_KEY = groupBuilder.suffix (:217, :248-253).
  5. The reader trusts those attributes: PostingsFormat.forName(formatName) and segment suffix formatName + "_" + suffix (:303-318).

In the repro, a creates group EqB_0, x creates EqA_0, and y's EqB(1) equals EqA(1), so y joins EqA_0 and its postings are written there. The check passes because a already used EqB, and y records (EqB, 0), which is a's group. The reader opens EqB_0 for y; it holds only a's terms, so terms(y) is null. The independent reproducer's probe printed exactly this (formats named ProbeA/ProbeB): files _0_ProbeA_0.* and _0_ProbeB_0.*; attributes a {ProbeB, 0}, x {ProbeA, 0}, y {ProbeB, 0}; terms(y) absent; CheckIndex at level 3 clean. Without field a, the probe's commit throws IllegalStateException: no suffix for format name: ProbeB, expected: 0.

On a group hit the matched group was created under some name N, so suffixes always holds N; the check can fail only when the field's name differs from N. So the only mappings it can reject are equal formats with different names, and it misses the case where another group used the field's name.

Other group numbers. The field records its own name with the matched group's number, so what a reader sees depends on whether that group exists. A fact-check variant on main maps a -> VarB(2), w -> VarA(7), x -> VarA(1), y -> VarB(1) (the same equals): y joins x's group VarA_1, the check passes because of a, and y records (VarB, 1), a group that was never written. The commit succeeds; DirectoryReader.open then throws CorruptIndexException: Problem reading index. (resource=_0_VarB_1.psm), caused by NoSuchFileException, and CheckIndex (level 3) reports clean=false, with assertions on and off. With fix A that commit is rejected: IllegalStateException: no suffix for format name: VarB, expected: 1.

Exposure and likelihood201 words
  • Who. Applications with their own per-field postings mapping (a PerFieldPostingsFormat subclass or a codec's getPostingsFormatForField hook) that use two of their own SPI-registered PostingsFormat classes with different names whose equals treats an instance of one as equal to an instance of the other. A third field whose format has the second name, and is not equal, must sort before the colliding field.
  • Not hit. The default codec and every format shipped in Lucene: none overrides equals, so distinct instances never share a group. Mappings in which equal formats also have equal names.
  • Effect. The commit succeeds and one field's postings cannot be read (they are written into another group's files). In the repro's layout this is silent with assertions on and off: queries on the field match nothing and CheckIndex is clean. With other group numbers it is loud but late: the index fails to open after the commit. With only the two colliding fields the same mistake is rejected at commit.
  • Default vs opt-in. Opt-in custom codec code on @lucene.experimental extension points.
  • Scale and likelihood. One document with three one-term fields; deterministic. Rated contrived: the recorded searches found no public report of anyone hitting even the existing two-field check.

Why it looks unintended

#
  • The always-on check can fail only for equal formats with different names, and rejects this mapping for two colliding fields alone.
  • Format equals overrides are invited (#5162: "optional and a new optimization"; #5165, open); no javadoc requires equal names.
  • The commit succeeds where two fields are rejected: silently in the repro (CheckIndex clean), or the index fails to open.
The full argument131 words
  • The code already treats the mapping as illegal. The check at PerFieldPostingsFormat.java:240-243 can fail only when a field joins a group created under another name (see the mechanism), and it does reject the two-field mapping with IllegalStateException.
  • Contract. The group map became equals-keyed on purpose in LUCENE-4090 (#5162); its author (Robert Muir) wrote there that equals on postings formats is "optional and a new optimization". LUCENE-4093 (#5165, still open) asks for such overrides. No javadoc of PostingsFormat, NamedSPI or the per-field hooks says equal formats must have equal names.
  • Tests. TestPerFieldPostingsFormat2.testSameCodecDifferentInstance and testSameCodecDifferentParams (:262, :279) use same-name instances only; no test combines an equals override with two names.
  • History. LUCENE-5969 (#7031, 98e9122375c) turned the original assert suffixes.containsKey(formatName) into the always-on exception with the same condition.
The devil's-advocate check162 words

The strongest case for "not a bug" (rated moderate by the cross-model reviews and the devil's-advocate verifier): an equals that equates formats whose SPI names differ is broken user code, because the name is what gets written (the private name field is documented as "Unique name that's used to retrieve this format when reading the index", PostingsFormat.java:66); the extension points are @lucene.experimental; no shipped format overrides equals; and LUCENE-5969 turned every assert in the file into a check at once, so the always-on check was not a separate decision about this input.

Why it fails: no contract states the rule; Lucene already rejects this exact mapping, just incompletely; the commit succeeds instead of throwing, and the field is lost (silently with a clean CheckIndex in the repro's layout, or with an index that fails to open for other group numbers); and the fix leaves every valid mapping unchanged. The argument bears on likelihood (hence priority Low), not on correctness.

Recommended Check the matched group's own name, not any group's (fix A)

Remember the format name each group was created with, and on a group hit throw the existing IllegalStateException when the field's name differs (+3/-1 in PerFieldPostingsFormat). Every valid mapping is unchanged. The repro passes with assertions on and off; 290 tests of the perfield suites, TestCodecs and TestAddIndexes pass.

#

In buildFieldsGroupMapping, keep a map from each group's format to the name it was created with, and on a hit compare it with format.getName() instead of asking suffixes.containsKey(formatName). Same exception and message as today's two-field rejection.

Trade-offs

Still a commit-time rejection, as today for two fields, not an error when the codec is configured. The message reads oddly for this case; a final version could name the field and both format names (not run). One extra HashMap per flush or merge, sized by the number of groups. Nothing rejected today becomes accepted: whenever the old check throws (no group used the field's name), the matched group was created under another name, so the new check throws too. Valid mappings are unchanged because the new check throws only on a hit whose group was created under another name. Merges apply the current mapping to the merged field names (PerFieldPostingsFormat.java:171-181), so with the fix, merging segments that an affected version wrote with such a mapping throws the same exception instead of carrying the lost field forward, and new flushes with that mapping are rejected too: the application has to fix its equals (read, not run).

Key groups by name and format

#

Use a composite key (format name, format) for the groups, so equal formats with different names get separate groups, each written under its own name. The mapping then works instead of being rejected.

Trade-offs

Changes today's two-field behaviour from rejection to success, and touches the Map<PostingsFormat, FieldsGroup> that write and merge iterate (PerFieldPostingsFormat.java:143-195). A bigger change than the bug needs; not built.

Document that equal formats must have equal names

#

State the rule where per-field formats compare formats with equals.

Trade-offs

Does not stop the silent loss; worth adding together with A. Not built.

Downstream note

#

Downstream, only products that ship their own postings-format classes with an equals across format names could hit it; documents or queries alone cannot trigger it.

How it was found

#

A proof-obligation audit of PerFieldPostingsFormat's contract: a per-field mapping the writer accepts must give a segment in which every field's postings can be read back, or be rejected. The group lookup, the attributes and the guard were checked against that obligation, and a one-test public-API JUnit then witnessed a lost field.

The method in full132 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: a per-field postings mapping that IndexWriter accepts either writes a segment in which every field's postings can be read back, or is rejected. The audit covered PerFieldPostingsFormat.java:202-205, :217-254 (group lookup by equals, numbering per name, the guard, the attributes) and the reader at :300-320. The guard discharges the obligation only when no other group used the field's format name.
  • A public-API JUnit test then failed on main with assertions on and off and on 10.6.0. The independent reproducer's probe (kept) printed the files, the attributes and a clean CheckIndex.
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

History

#

Present since per-field groups were keyed by equals (LUCENE-4090, Robert Muir, 2012-05-30; first release 4.0.0). LUCENE-5969 (5.0.0) made the guard always-on with the same condition. Every release run, 4.0.0-ALPHA to 10.6.0, and main fail; not a regression and not fixed upstream.

Summary
You give a per-field postings codec two SPI-registered postings formats with different names whose equals() compares only a setting, map field a to the second format with setting 2, field x to the first format with setting 1 and field y to the second format with setting 1, index one document and commit. You expect either the IllegalStateException 'no suffix for format name' that Lucene already throws when only x and y exist, or a segment in which every field's terms can be found. Instead the commit succeeds: y's postings are written into x's group while y's recorded format attributes point to a's group, so a TermQuery on y finds 0 documents and CheckIndex reports the index clean.
