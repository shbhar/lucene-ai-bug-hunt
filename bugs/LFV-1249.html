IndriDirichletSimilarity accepts a negative, NaN or infinite mu that LMDirichletSimilarity rejects

new IndriDirichletSimilarity(-1f) is accepted, while LMDirichletSimilarity and NormalizationH3 reject the same Dirichlet mu with IllegalArgumentException. The mistake shows up only later, as +Infinity, NaN or meaningless finite scores: with mu = -1 the one-term document "a" scores Infinity for the query f:a.

The finding in 30 seconds

#

IndriDirichletSimilarity has five constructors: two use the default mu = 2000, three take mu from the caller. Only those three are affected, and only when the value is negative, NaN or infinite.

Dirichlet smoothing in one minute

#
  1. A language-model similarity scores a term by how likely the document is to produce it. IndriDirichletSimilarity scores log((freq + mu*P) / (docLen + mu)): freq is how often the term occurs in the document, docLen the document's length in terms, P the term's share of the whole collection.
  2. mu acts as mu extra pseudo-terms borrowed from the collection, so a short document is not judged on a handful of words. Lucene's other Dirichlet classes accept it only as a finite value of 0 or more; the default is 2000.

The finding, step by step

#
  1. You configure the non-default IndriDirichletSimilarity with a smoothing value mu from your settings, and the value is wrong: new IndriDirichletSimilarity(-1f) (a typo), or a NaN from a bad parse.
  2. You expect IllegalArgumentException: illegal mu value: -1.0, must be a non-negative finite value. That is what new LMDirichletSimilarity(-1f) and new NormalizationH3(-1f) throw for the same Dirichlet mu.
  3. Instead the similarity is built: all three mu constructors only do this.mu = mu. No error, with assertions on or off.
  4. The mistake surfaces in scores. Index "a" and "a b", search f:a. The score is log((freq + mu*P) / (docLen + mu)) with P = 0.75: for "a" that is log(0.25 / 0) = Infinity, and "a b" gets -1.386. The default value mu = 2000, in the same constructor, gives -0.288 for both; mu = NaN gives NaN for both.

Who is affected

#

Only applications that pick the non-default IndriDirichletSimilarity and pass it a negative, NaN or infinite mu, typically a typo or a bad configuration parse. Instead of failing fast, the setting silently produces Infinity, NaN or meaningless finite scores, far from the cause. Nothing in the index changes; valid values are unaffected. Every release since 8.9.0. Rare, so priority Low.

Mechanism, terms and numbers611 words

IndriDirichletSimilarity takes the Dirichlet smoothing parameter mu, a pseudo-count that its sibling classes accept only as a finite value of 0 or more. Its three mu constructors only do this.mu = mu (IndriDirichletSimilarity.java:44, :50, :55), so a negative, NaN or infinite mu is accepted, while LMDirichletSimilarity (:46-62) and NormalizationH3 (:39-43), which take the same mu, throw IllegalArgumentException("illegal mu value: ..."). The bad value then shows up only in scores and explain(): log((freq + mu*P) / (docLen + mu)) (:68-73) is +Infinity when docLen + mu = 0 (mu = -1 on a one-term document), NaN for a NaN or infinite mu, and otherwise often finite but meaningless. Indri's own javadoc states no range for mu; the expectation comes from LUCENE-7997 ("Add missing range checks for similarity parameters"), whose author named the "smoothing parameter mu" as a parameter to check, and from the sibling classes. It needs an invalid value on a non-default similarity and changes nothing in the index, so it is Low. It has been there since the class was added (LUCENE-9537, first released in 8.9.0) and is on main; copying the sibling's one-line check into the three constructors fixes it.

protected double score(BasicStats stats, double freq, double docLen) {       // :69
  double collectionProbability = ((LMStats) stats).getCollectionProbability();

// LMDirichletSimilarity.java:49-52 (again at :58-61; the same in NormalizationH3.java:40-43)

  throw new IllegalArgumentException(
      "illegal mu value: " + mu + ", must be a non-negative finite value");
}
  1. The constructors store any float. The default constructors pass 2000 (:58-66), so only an explicit mu reaches the gap.
  2. In the example, new IndriDirichletSimilarity(-1f) uses LMSimilarity's default collection model, P = (totalTermFreq + 1) / (fieldTokens + 1) (LMSimilarity.java:150-151) = (2 + 1) / (3 + 1) = 0.75. For "a" (freq 1, docLen 1): (1 - 0.75) / (1 - 1) = 0.25 / 0 = +Infinity. For "a b" (docLen 2): log(0.25) = -1.386, finite but meaningless.
  3. A NaN or infinite mu makes the quotient NaN for every document. mu = -10 gives NaN on short documents (1 and 5 terms in a probe: a negative quotient) and +Infinity at 10 terms.
  4. The explanation's value is score() itself (SimilarityBase.java:134-135), so explain() reports the same values. Of its details, "term weight" (:83-85) uses the same formula, and "document norm" (:87, log(mu / (docLen + mu))) is NaN for both documents at mu = -1. Nothing is written to the index; a valid mu (0 and up) is unaffected.

Exposure and likelihood161 words
  • Who is hit. Applications that build IndriDirichletSimilarity with an explicit mu that is negative, NaN or infinite. Outside the class itself, Lucene uses it only in tests (TestIndriDirichletSimilarity, TestIndriAndQuery) and the test framework's BaseSimilarityTestCase.
  • Default vs opt-in. Opt-in: the similarity must be chosen and given a mu. Assertions on or off make no difference.
  • Effect. No error at construction; ranking becomes meaningless (+Infinity, NaN or finite but meaningless scores and explanations: -1.386 for "a b" at mu = -1). No index change; no crash in the recorded runs.
  • Scale. None needed: one constructor call.
  • Likelihood: rare. An invalid value on a non-default similarity; no report since 8.9.0 (2021).
  • Framing. The effect is non-finite scores and explanations, not lost hits: under this similarity a top-k TermQuery search can already return no hits on 10.3.0 and later even with a valid mu, for a separate reason (negative Indri scores and the bulk scorer's filter).

Why it looks unintended

#
  • LUCENE-7997 added "missing range checks for similarity parameters"; its author named "smoothing parameter mu" as one to keep "non-negative/finite" (Robert Muir, #9045).
  • LMDirichletSimilarity and NormalizationH3 reject the same Dirichlet mu; every other core similarity validates its float parameters.
  • Indri's upstream test treats mu = 0 as the "minimum value".
The full argument212 words
  • Project intent, written down. CHANGES.txt:6857-6860 (LUCENE-7997, under 8.0.0): "Add missing range checks for similarity parameters." On #9045 (2017-10-24) Robert Muir wrote: "for unbounded parameters (such as normalization c, smoothing parameter mu) we treat them the same as BM25's k1 and just ensure non-negative/finite in the range check". Commit 42717d5f4bb added exactly this check to LMDirichletSimilarity and NormalizationH3.
  • The class came later without the check. IndriDirichletSimilarity was added in 2021 (LUCENE-9537). Its upstream test is a copy of TestLMDirichletSimilarity that labels mu = 0 the "minimum value" and uses only 0, Float.MIN_VALUE, Integer.MAX_VALUE and random values in between (TestIndriDirichletSimilarity.java:26-48); BaseSimilarityTestCase.getSimilarity asks for parameters "randomized within valid ranges" (:94), and it exempts Indri only from the non-negative score assertions (:388-390, :417-419, :443-445, :485-487) while still asserting that every score is finite (:387, :416, :442, :484).
  • The only exception in core. BM25Similarity, StableTflSimilarity, LMDirichletSimilarity, LMJelinekMercerSimilarity, Axiomatic and NormalizationH1/H2/H3/Z all throw IllegalArgumentException for invalid float parameters.
  • No decision to the contrary found. In the sources read (the javadoc, CHANGES, MIGRATE, tests, the review of apache/lucene-solr#2097, which asked only what mu means, and #13845, which copied the unchecked body into a third constructor), nothing says invalid mu is accepted on purpose.
The devil's-advocate check137 words

The strongest case: Indri's own javadoc promises no exception and states no range for mu; mu is trusted configuration and a negative pseudo-count is meaningless input, so the caller is wrong; lucene/misc's SweetSpotSimilarity setters do not validate either.

Our answer: this is mostly an argument about severity. No upstream text found says the omission is deliberate, the project's written policy says the opposite for this very parameter, and the failure is silent (non-finite scores), not loud. Still, with no per-class contract, a maintainer could reasonably treat the change as hardening rather than a bug fix. An executed review by another model family (OpenAI GPT-5.6) made this argument (rated "moderate") while agreeing that the bug reproduces, on the root cause and on the fix, and calling the omission accidental. That is why the bug is Low.

Suggested fix

Recommended Copy the sibling's range check into the three mu constructors

Copy LMDirichletSimilarity's check into the three mu constructors: throw IllegalArgumentException("illegal mu value: ...") when Float.isFinite(mu) == false || mu < 0. Validated: the repro passes with assertions on and off; 121 tests (the similarities package, TestIndriAndQuery and the repro), and :lucene:core:check -x test, pass with the fix.

Downstream note

#

Products that let users or tenants set similarity parameters should range-check mu themselves on affected versions, since Lucene treats it as trusted configuration.

How it was found

#

A proof-obligation audit of IndriDirichletSimilarity's constructor contract took the range check that its sibling Dirichlet classes apply to the same mu as an obligation and found that no constructor discharges it. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full103 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.
