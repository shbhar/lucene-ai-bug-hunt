Intervals.atLeast accepts a count of 0, then searches that evaluate it throw NullPointerException

Intervals.atLeast(0, a, b), or the query text fn:atLeast(0 a b), is accepted, but a search that evaluates it then throws an internal NullPointerException (ArrayIndexOutOfBoundsException on a segment without the terms) instead of the 0 being rejected. Every release from 8.0.0 to 10.6.0 and main.

The finding in 30 seconds

#

Intervals.atLeast(n, sources...) returns stretches of text that contain at least n of the sources, for example at least 2 of three words. fn:atLeast(n ...) is the same operator in the flexible query parser's syntax, so the count can come straight from what a user types.

  1. Index one document, "a b c", and build Intervals.atLeast(0, Intervals.term("a"), Intervals.term("b")): at least 0 of the 2 terms. Typing fn:atLeast(0 a b) into the flexible StandardQueryParser builds the same query.
  2. You expect an IllegalArgumentException when the query is built, or a search that runs. The factory already handles the other odd counts: 2 of 2 becomes unordered(a, b), 3 of 2 a source that matches nothing.
  3. You get a query that builds fine; then searcher.count(query) throws NullPointerException: ... the return value of "PriorityQueue.top()" is null. Top-k and sorted search, Weight#matches and explain fail the same way, with assertions on or off.
  4. Why: atLeast keeps the sources it is combining in a queue sized by the count. With 0 that queue can hold nothing; its loop test "queue size == count" reads 0 == 0, true, so it asks the empty queue for its top and gets null. On a segment where neither term occurs, an empty document queue throws ArrayIndexOutOfBoundsException instead.

Who is affected

#

Code that passes 0 to Intervals.atLeast, for example a count computed from a percentage of a short clause list or forwarded from a client, and search boxes on the flexible StandardQueryParser (9.1.0 and later), where anyone can type fn:atLeast(0 ...). Default settings and one document suffice. Each such request fails; no wrong hits, no hang.

Mechanism, terms and numbers760 words

Intervals.atLeast(minShouldMatch, sources...) checks only two special counts: equal to the number of sources (rewritten to unordered) and larger (a source that matches nothing). A count of 0 with one or more sources, passed directly or typed as fn:atLeast(0 a b) into the flexible StandardQueryParser, therefore builds a MinimumShouldMatchIntervalsSource whose queue of active sources has capacity 0. On the first candidate document its nextInterval() loop test proximityQueue.size() == minShouldMatch is true on the empty queue and proximityQueue.top().start() throws NullPointerException; on a segment that holds none of the source terms the iterator, built anyway, throws ArrayIndexOutOfBoundsException from its empty document queue. So count, top-k and sorted search, Weight#matches and explain fail wherever they evaluate it, with an internal exception instead of an argument error when the query is built. A negative count fails late with IllegalArgumentException from PriorityQueue. Default IndexWriterConfig and searcher, one document, assertions on or off; every release from 8.0.0 (query text from 9.1.0) to 10.6.0 and main. Nothing else is affected: no wrong hits, no hang, no result cached for the broken query, nothing written.

Terms

#
  • Interval: a [start, end] range of token positions in one field of one document; Intervals.term("a") gives one per occurrence of a.
  • Intervals.atLeast(minShouldMatch, sources...): "Return intervals that span combinations of intervals from minShouldMatch of the sources" (Intervals.java:563-565). Query text: fn:atLeast(min sources...), where min is "an integer specifying minimum number of sub-interval arguments that must match" (intervalfn/package-info.java:231).
  • Proximity queue: the iterator keeps the minShouldMatch sub-iterators it is combining right now in a priority queue of that capacity, and the rest in a background queue (MinimumShouldMatchIntervalsSource.java:146-156, :186-195).

The mechanism (main 645d4fe14a20)

#
  1. No lower bound. The factory handles minShouldMatch == sources.length (returns unordered(sources), Intervals.java:567-569) and minShouldMatch > sources.length (returns a NoMatchIntervalsSource, :570-576); any smaller count, 0 and negatives included, becomes new MinimumShouldMatchIntervalsSource(sources, minShouldMatch) (:577). Its constructor only does assert minShouldMatch < sources.length (MinimumShouldMatchIntervalsSource.java:46), which 0 satisfies. (With no sources at all, 0 is the == case and goes to unordered().)
  2. An iterator is always built. intervals() returns null only if (iterators.size() < minShouldMatch) (:60), never true for 0 (:51-64).
  3. A queue that holds nothing. The proximity queue is created with capacity minShouldMatch (:186-190); for capacity 0 PriorityQueue allocates a 2-slot heap whose top() returns heap[1], always null (PriorityQueue.java:117-119, :246-251). reset() moves minShouldMatch sub-iterators into it (MinimumShouldMatchIntervalsSource.java:279-288): none.
  4. The NPE. nextInterval() begins while (this.proximityQueue.size() == minShouldMatch && proximityQueue.top().start() == start) (:217-218): 0 == 0, and top() is null. The scorer's two-phase check calls it on the first candidate document (IntervalScorer.java:80-81), so count, search and explain throw there; Weight#matches reaches the same loop through MinimumShouldMatchIntervalsSource.matches, which builds its own iterator and calls nextInterval() (:80-88).
  5. No source term in the segment. Then the iterator has no sub-iterators; its DisiPriorityQueue (the intervals package's own copy) has length 0 (MinimumShouldMatchIntervalsSource.java:175), and the bulk scorer's first docID() reads heap[0] (DisiPriorityQueue.java:56-58): ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0.
  6. Negative counts reach PriorityQueue's check "maxSize must be >= 0" (PriorityQueue.java:121-124), but only when the iterator is created at search time (by the scorer, or by matches for Weight#matches).
  7. Query text. StandardSyntaxParser.jj:411-422 reads <NUMBER> (no sign: digits with an optional fraction, :160) and returns new AtLeast(parseInt(minShouldMatch), sources); AtLeast.toIntervalSource passes the number unchanged to Intervals.atLeast (intervalfn/AtLeast.java:38-44). So 0 can be typed; a negative cannot (fn:atLeast(-1 a b) is a ParseException).

Inside a Boolean OR, a non-scoring count may never ask the atLeast clause once another clause has matched: c OR fn:atLeast(0 a b) counted 1 on "a b c", but top-k search, index-order sorted search, explain and Weight#matches on the same query threw the NPE. Over an empty index there is no segment to evaluate it on, and count returns 0.

Exposure and likelihood342 words
  • Who is exposed. (a) Code that passes a computed or forwarded count to Intervals.atLeast. (b) Applications that hand end-user text to the flexible StandardQueryParser with interval functions (9.1.0 and later; the node calls Intervals.atLeast unchanged, intervalfn/AtLeast.java:38-44). The maintainers foresaw (b) for a sibling case: "I realize the query itself is malformed but such corner cases will happen if intervals are available from the query parser" (Dawid Weiss, on #10783 / LUCENE-9744).
  • Downstream (read, not run). Solr's intervals query parser (apache/solr#4582, SOLR-13764) was released in Solr 10.1.0 (2026-10-27, built on Lucene 10.4.0, which has the same atLeast code) and is also on Solr main. Its at_least rule rejects only min_should_match < 0 and passes 0 to Intervals.atLeast, and the parser is registered by default. Elasticsearch and OpenSearch do not expose atLeast. That says nothing about private code.
  • Default or opt-in. atLeast is an opt-in operator of a package that calls itself experimental (intervals/package-info.java:21). Nothing else is needed: the default IndexWriterConfig and searcher, assertions on or off. Only the seeded test codecs were run; the failing code is in the query's own iterator, not in the codec, so other codecs should behave the same (read, not run).
  • Scale. One document; deterministic.
  • What you see. An unchecked NullPointerException (or ArrayIndexOutOfBoundsException) from count, top-k and sorted search, Weight#matches and explain, where an argument error was due when the query was built. An application that maps IllegalArgumentException to a "bad request" reports an internal error instead; how a downstream reports it is up to it.
  • What does not happen (executed probe): no wrong or extra hits (189 of 189 calls threw, with the clause in MUST, FILTER, MUST_NOT, constant-score and parsed positions on four searchers, including concurrent and always-caching ones), no hang, no result cached for the broken query (a repeat on an always-caching searcher threw again), the index untouched.
  • Likelihood: rare. A constant 0 fails loudly on the first search, so testing catches it; it takes a computed, forwarded or typed 0, and atLeast is a less-used operator.

Why it looks unintended

#
  • Both entry points accept 0; no doc sets a lower bound or an exception, and an internal NPE from an empty queue is no designed outcome.
  • The factory already makes the other odd counts safe (equal: unordered; larger: no match), fixing a sibling NPE, #10783.
  • Elsewhere the package rejects bad numbers up front ("pivot must be > 0").
The full argument252 words
  • The contract. Intervals.atLeast: "Return intervals that span combinations of intervals from minShouldMatch of the sources" (Intervals.java:563-565), with no stated range and no @throws. Parser docs: fn:atLeast "Matches documents that contain at least the provided number of source intervals"; min is "an integer specifying minimum number of sub-interval arguments that must match" (intervalfn/package-info.java:223, :231). No document says 0 must throw either: rejecting it (fix A) or giving it a meaning (fix B) is the maintainers' choice; the bug is that accepted input later fails with an internal exception.
  • Degenerate counts are normalised on purpose. The == and > shortcuts (Intervals.java:567-576) came from LUCENE-9744 (#10783, 8.8.2), "NPE on a degenerate query in MinimumShouldMatchIntervalsSource" (lucene/CHANGES.txt:5445-5446). Its fix was, in Alan Woodward's words, "a fix in the factory method that ensures we don't ever actually get a degenerate min-should-match interval". 0 is the case that fix did not cover.
  • Validation elsewhere in the package. IntervalScoreFunction throws "pivot must be > 0" and "exp must be > 0" when built (IntervalScoreFunction.java:28, :35, :38).
  • The same parser gives 0 a meaning elsewhere. Its Boolean min-should-match operator (a b)@0 parses and counts 1 on "a b c" (executed).
  • Tests. No upstream test uses atLeast with 0 or a negative count; TestSimplifications.testMinShouldMatchSimplifications pins only the == and > rewrites (TestSimplifications.java:115-122).
  • History. The missing bound and the loop guard date from the class's first commit (LUCENE-8622, 2019); the guard was only re-wrapped since (LUCENE-9570).
The devil's-advocate check155 words

The strongest case for "intended" (built by the devil's advocate and reviews by an independent reviewer from another model family, OpenAI GPT-5.6, reading only): atLeast(0, ...) is meaningless, and the LUCENE-9744 reporter themselves called such a query "malformed"; the Intervals factories generally validate little (maxgaps(-1, ...) and extend(a, -1, 0) are accepted, unordered() with no sources throws a raw exception); MinimumShouldMatchIntervalsSource is package-private and its design comment assumes a count of at least 1; negative counts already end in an IllegalArgumentException.

Why it fails: the "malformed" LUCENE-9744 input was fixed anyway, for exactly the query-parser reason; the silently accepted numeric arguments return results, not exceptions, and the zero-source cases cannot be written as query text, while fn:atLeast(0 ...) can; the entry points are public and documented; and the negative value fails late and is not the headline. No checker rated the intended-behaviour argument better than weak. Verdict: not intended; a missing argument check.

Suggested fix

#

Recommended A: reject a count below 1 when the source is built

Reject a count below 1 in Intervals.atLeast with an IllegalArgumentException (3 lines). The repro then passes, and so do all 513 tests of the queries module and the 161 flexible-parser tests. Alternative: treat 0 as "no minimum" and return or(sources), as BooleanQuery does.

Two fixes were run through gradle in a scratch worktree of 645d4fe14a20; both are one-file changes to Intervals.atLeast. A: reject a count below 1 when the source is built (validated by the checks) (recommended)

#

The change is +3 lines in Intervals.java only (the finder's fix, re-made on 645d4fe14a20). One check at the entry point removes all three failures: the NPE, the AIOOBE and the late IllegalArgumentException for negative counts. It follows IntervalScoreFunction's convention and LUCENE-9744's "fix in the factory method".

  if (minShouldMatch < 1) {
    throw new IllegalArgumentException("minShouldMatch must be >= 1, got: " + minShouldMatch);
  }
  if (minShouldMatch == sources.length) {

Trade-offs

  • A few queries that run today would fail when built. Searches with a count of 0 throw today wherever they evaluate it, but a search over an empty index (count 0), or a non-scoring count of a Boolean OR whose other clause already matched (c OR fn:atLeast(0 a b) counted 1 on "a b c"; top-k and sorted search, explain and Weight#matches on it threw), runs today. With fix A both throw when the query is built (executed).
  • Query text. StandardQueryParser.parse("fn:atLeast(0 a b)", "f") then throws a bare IllegalArgumentException instead of a QueryNodeException (executed with the finder's identical fix); a parser-side check (option C) would make it a parse error.
  • No sources. Intervals.atLeast(0) with no sources, which today fails through unordered() ("Cannot make a ConjunctionDISI of less than 2 iterators"), fails with this message instead.
  • A @throws IllegalArgumentException line in the javadoc would document the bound.

B: treat 0 as "no minimum" and return or(sources) (validated by the checks)

#

The change is +7 lines in Intervals.java only: reject negative counts, and for 0 with at least one source return or(sources), as BooleanQuery treats minimumNumberShouldMatch 0 and as the same parser treats (a b)@0.

if (minShouldMatch < 0) {
  throw new IllegalArgumentException("minShouldMatch must be >= 0, got: " + minShouldMatch);
}
if (minShouldMatch == 0 && sources.length > 0) {
  // like BooleanQuery's minimumNumberShouldMatch 0: no minimum, any one source matches
  return or(sources);
}

Trade-offs

Gives 0 a meaning, so the parser needs nothing. But it picks semantics the javadoc does not state: "at least 0 of the sources" read literally is met by any document, which or is not.

What the checks validated

Trade-offs

Downstream note

#

Solr's intervals query parser, released in Solr 10.1.0 (2026-10-27, on Lucene 10.4.0), checks only for a negative min_should_match and passes 0 straight to Intervals.atLeast (code read, not run), so its search clients could hit the same exception.

How it was found

#

A sweep of degenerate arguments: a probe called the Intervals factories with 15 edge values (counts of 0 and -1, negative gaps and widths, no sources) on a small index. atLeast(0, a, b) built fine and then threw at search time; the finder then wrote a public-API test. No model checker or solver was involved.

The method in full184 words

Method: non-formal (a degenerate-argument sweep; no model checker, SMT solver, prover or bounded-exhaustive harness produced the signal).

  • A hunt unit (intervals builder and multi-term sources), 2026-10-26, on main ea57360912ed. While extending the unit's reference semantics to atLeast, the finder, an AI tool, wrote a probe that ran 15 degenerate calls of the Intervals factories against a small index: atLeast(0, a, b), atLeast(-1, a, b), atLeast(1, a), atLeast(0), atLeast(2) with no sources, extend(a, -1, 0), extend(a, 0, -1), maxgaps(-1, ...), maxwidth(-1, a), within(a, -1, b), notWithin(a, -2, b), and unordered(), ordered(), or(), phrase() with no sources.
  • atLeast(0, a, b) was the call that was accepted and then threw NullPointerException at search time; atLeast(-1, a, b) failed late with IllegalArgumentException. The finder read the factory and the iterator, and wrote a deterministic public-API JUnit (direct API and parsed fn:atLeast(0 a b)) and a 3-line fix.
  • Independent checkers then widened it: the ArrayIndexOutOfBoundsException on segments with none of the terms, Weight#matches, nested query text, and every release from 8.0.0.

LFV-469, snapshot of 2026-11-08

Registry title
Intervals.atLeast accepts minShouldMatch 0 (also from query text such as fn:atLeast(0 a b)), and the query then throws NullPointerException or ArrayIndexOutOfBoundsException on every non-empty segment it searches instead of being rejected as an invalid argument
Area
queries / intervals (Intervals.atLeast: MinimumShouldMatchIntervalsSource); queryparser / flexible StandardQueryParser fn:atLeast
Priority
Low, rank 665: Intervals.atLeast(0, ...) and fn:atLeast(0 ...) are accepted and then throw NullPointerException or ArrayIndexOutOfBoundsException on every search, which is loud, fails one request at a time, and needs a value that means nothing for atLeast.
Impact class
wrong error
Impact note
Any application that passes minShouldMatch 0 to Intervals.atLeast, or hands end-user query text containing fn:atLeast(0 ...) to the flexible StandardQueryParser (from 9.1.0), gets a query that builds without error but makes count, top-k and sorted search, Weight#matches (highlighting) and explain throw an unchecked NullPointerException (segment holding a source term) or ArrayIndexOutOfBoundsException (segment holding none) instead of an IllegalArgumentException when the query is built; negative values (Java API only, the parser's number token is unsigned) fail late with IllegalArgumentException from the PriorityQueue constructor; default IndexWriterConfig, codec and searcher, -ea and -da, any index size, every release from 8.0.0 through 10.6.0 and main; the failure is per request only: no hang, no wrong or extra hits, nothing cached or written.
Summary
You build Intervals.atLeast(0, Intervals.term("a"), Intervals.term("b")), or parse 'fn:atLeast(0 a b)' with the flexible StandardQueryParser, and search an index that contains 'a b c'. You expect the 0 to be rejected with an IllegalArgumentException when the query is built (the same factory already handles a count equal to or larger than the number of sources), or else a search that runs. Instead the query is accepted and every search with it throws: NullPointerException in MinimumShouldMatchIntervalIterator.nextInterval, because top() of its empty, capacity-0 queue is null, or ArrayIndexOutOfBoundsException from an empty DisiPriorityQueue on a segment that holds none of the terms.
