Skipped positions are counted in an int: once one term's pending occurrences in a postings block (the skipped documents plus the current one) pass Integer.MAX_VALUE, nextPosition() returns an earlier document's positions

When a postings block's skipped documents plus the current one hold over 2,147,483,647 occurrences of a term, the reader's int skip count wraps and returns an earlier document's positions: PhraseQuery f:"v t" finds 0 hits, not 1. It needs huge documents, such as two with a billion repeats each.

The finding in 30 seconds

#

The reader reads positions lazily: for documents a query passes over, it only adds their frequencies to an int count of positions still to skip. Past 2,147,483,647 that count turns negative, and the skip is silently dropped.

Background: how positions are read lazily

#
  1. For each term, the postings store every document's frequency (how often the term occurs in it) and then its positions, all documents one after another in one position stream.
  2. A phrase query reads positions only for documents that contain all its terms. For documents it passes over, the reader does not decode anything: it adds their frequencies to a count of positions it is behind.
  3. On the next nextPosition(), the reader skips that many positions and reads on. When it moves to the next 256-document block, it normally resets the count from the block's skip data.

The finding, step by step

#
  1. Index three documents into a text field with the default codec and a default IndexWriterConfig: docs 0 and 1 are the token t repeated 2^30 = 1,073,741,824 times, doc 2 is v t. forceMerge(1) puts all three in one postings block of t.
  2. Run PhraseQuery f:"v t". Only doc 2 contains v, so the query jumps to doc 2 and never reads the positions of docs 0 and 1; the reader only notes how many positions it must skip.
  3. You expect 1 hit: in doc 2, t is at position 1, right after v. Lucene 9.12 and 10.0 return it.
  4. Instead the reader adds the frequencies in an int: 1,073,741,824 + 1,073,741,824 + 1 = 2,147,483,649 wraps to -2,147,483,647. A negative count means "skip nothing", so doc 2 gets doc 0's first position, 0 instead of 1.
  5. The query returns 0 hits and no error (assertions off). With assertions on, the reader's own assert posPendingCount > 0 fails. 10.1.0 to 10.6.0 and main are affected; the int dates back to Lucene 2.1.

Who is affected

#

Anyone reading positions on the default codec (phrase, span and interval queries, positional highlighting), once one term's occurrences in the skipped documents of a 256-document postings block, plus the current one, pass Integer.MAX_VALUE. Defaults suffice, but it takes huge documents, such as two that each repeat one term about a billion times, so it is contrived.

Mechanism, terms and numbers647 words

Lucene104PostingsReader.BlockPostingsEnum reads positions lazily. When a consumer passes documents without reading their positions, the reader only adds their frequencies to posPendingCount, the number of positions it is "behind", and skips that many on the next nextPosition(). That count, the helper that sums the frequencies (sumOverRange) and the skip distance (toSkip) are all int. When the skipped documents of one postings block plus the current one hold more than 2,147,483,647 occurrences of the term, the sum wraps negative, the skip is not done, and nextPosition() returns positions from the start of an earlier document.

With assertions off this is silent: in the repro PhraseQuery f:"v t" counts 0 instead of 1. With assertions on, assert posPendingCount > 0 fails. A default IndexWriterConfig and the default codec suffice, and every document is within Lucene's per-document limits, because the trigger is cumulative across documents. It needs huge documents, for example two that each repeat one term about a billion times, so the priority is low. The Lucene912 reader of 9.12.x and 10.0.0 used long and is correct; making the three values long again fixes it.

The bug, step by step (main 645d4fe14a20, Lucene104PostingsReader.java)

#
  1. The count. private int posPendingCount;, commented "how many positions "behind" we are; nextPosition must skip these to "catch up"" (:381-383); set to 0 when the enum is reset to a term (:538).
  2. The catch-up. On the first nextPosition() of a document (:1299-1301), accumulatePendingPositions() (:1263-1274) runs posPendingCount += sumOverRange(freqBuffer, posDocBufferUpto, docBufferUpto): the frequencies of every document of the doc buffer whose positions were not read, plus the current one. It then asserts posPendingCount > 0 (:1268) and calls skipPositions(freq) only if (posPendingCount > freq) (:1270).
  3. All int. sumOverRange sums into int res (:270-276), and skipPositions computes int toSkip = posPendingCount - freq (:1133). In the repro, 2,147,483,649 wraps to -2,147,483,647 inside sumOverRange.
  4. No skip. A negative count is never > freq, so decoding continues where the position stream stands: the start of doc 0's positions (:1306-1310). Payloads and offsets are read in lockstep from the same point (:1276-1290, code reading).
  5. Exact boundary (independent checkers, executed): a sum of exactly Integer.MAX_VALUE reads correctly and Integer.MAX_VALUE + 1 does not; 2^31 - 16 is correct and 2^31 + 48 wrong.
  6. One block. Moving to the next level-0 block while the position stream is behind seeks forward and resets the count from skip data (doMoveToNextLevel0Block, :721-736; seekPosData, :799-815). Only when that block's positions were already decoded does it add the remaining frequencies to the count instead (:735, :814). So from 10.1 on, on the lazy path the repro takes, the overflowing sum must in practice come from one block: 256 documents containing the term in Lucene104 (since 10.4), 128 in Lucene101/103 (code reading). The reset normally also ends the damage at the end of the block; the two carry-over branches were not exercised, so this is not a guarantee.

Exposure and likelihood367 words
  • Who can be hit. Every consumer of PostingsEnum#nextPosition on the default codec: PhraseQuery (executed), MultiPhraseQuery, span and interval queries, highlighters and payload consumers (code reading). Positions are indexed by default for TextField. Old 10.1-10.3 segments are read by the backward-codecs Lucene101/103 readers, which have the same int code.
  • Defaults. A default IndexWriterConfig (16 MB buffer, TieredMergePolicy), the default codec and forceMerge(1) reproduce it. No expert setting is needed.
  • Scale. More than Integer.MAX_VALUE (2^31 - 1) occurrences of one term among the skipped documents of one postings block plus the current one (a pending sum of exactly 2^31 already fails): for example two documents of 2^30 occurrences (about 1 GiB of indexing buffer each; the test needs a 4 GB heap and about 2.5-5 minutes), or about 8.4 million occurrences per document across a full 256-document block (code reading). Positions forbid custom term frequencies, so every occurrence is a real token. One document alone cannot reach it, but not because of IndexWriter.MAX_POSITION, which limits position values: stacked occurrences (position increment 0) get around it, and the per-field token count would allow Integer.MAX_VALUE tokens. What stops one document is the writer's in-memory postings pool, which buffers at least one byte per occurrence and is capped at 2^31 bytes: a document with Integer.MAX_VALUE occurrences of one term fails while indexing with ArithmeticException: integer overflow at ByteBlockPool.nextBuffer (ByteBlockPool.java:199; executed by the fact check). So two large documents are the smallest input.
  • What goes wrong. Assertions off: silent wrong positions for the documents after the trigger documents in that block (executed: a phrase false negative). Code reading only, not executed: false positives when the substituted positions happen to line up; offsets and payloads taken from the earlier, possibly deleted, document; and a merge that skips deleted documents without reading their positions could write wrong positions into the merged segment. Assertions on: an AssertionError from that nextPosition() call.
  • Bounds (code reading): reads stay inside the same term's position data, and the block reset normally ends the damage at the end of the block (the carry-over branches were not exercised); no hang and no memory unsafety, and with the skip dropped the reader does less work, not more.

Why it looks unintended

#
  • PostingsEnum#nextPosition returns the current document's next position; only calling it more than freq() times is undefined.
  • Lucene's limits are per document, and each repro document stays below them; no documentation we found caps the sum across documents (totalTermFreq is a long).
  • The reader asserts posPendingCount > 0 itself, and the 9.12/10.0 reader, with a long, returns the hit.
The full argument206 words
  • The contract. "Returns the next position, or -1 if positions were not indexed. Calling this more than freq() times is undefined." (PostingsEnum.java:85-88). The repro calls it once for doc 2. Skipping other documents' positions is the normal lazy pattern, and PhraseQuery itself relies on it.
  • The documented limits are per document. IndexingChain rejects a position above IndexWriter.MAX_POSITION (IndexingChain.java:2021-2028) and a field length that overflows an int, "too many tokens for field" (Math.addExact, :2054-2064). Each repro document has 2^30 tokens. Test2BPositions indexes "> Integer.MAX_VALUE positions" for one term (Test2BPositions.java:35), and the Lucene104 format's "Limitations" section names only int document numbers (package-info.java:426-436).
  • The code's own assumption. assert posPendingCount > 0 (:1268) says the count is never negative; it fires on this input.
  • History. The Lucene912 reader (9.12.x, 10.0.0, #13585) declared long posPendingCount, long toSkip and a long sumOverRange (backward-codecs Lucene912PostingsReader.java:302, :629, :939) and reads the same index correctly (executed on 9.12.0, 9.12.3 and 10.0.0). #13968 returned to int; its description and reviews never mention overflow.
  • Precedent. LUCENE-4468 / #5534, "Fix rareish integer overflows in Lucene41 postings format" (CHANGES.txt:14734), fixed the same class of bug in file-pointer fields.
The devil's-advocate check115 words

The strongest case for "intended": the scale is absurd, since nobody puts 2^31 occurrences of one term into 256 documents, and the int[] move in #13968 was a deliberate performance choice for more SIMD lanes.

Why it fails: the scale explains the low priority but is not a documented limit, and every input passes Lucene's own validation with default settings. The SIMD motivation covers the int[] buffers, not a scalar counter or a scalar sum, and 9.12.x and 10.0.0 shipped the long version. The checkers that gave a strength rating (the independent reproducer and reviews by another model family, OpenAI GPT-5.6) rated the intended-behaviour argument weak; the devil's advocate also rejected it, without a rating.

Suggested fix

#

Recommended Make the count, the frequency sum and the skip distance long

Make posPendingCount, the frequency sum sumOverRange and toSkip long, as the 9.12/10.0 reader did, and do the same in the backward-codecs Lucene101 and Lucene103 readers. The repro then passes with assertions on and off, and so do the whole core test suite (8,898 tests), those backward-codecs packages, the span and interval tests and check.

Downstream note

#

Not a Lucene security issue; downstream, an application that indexes untrusted documents without size limits would let one writer of such documents change phrase results for neighbouring documents in the same postings block.

How it was found

#

Non-formal: while modelling the Lucene104 postings reader for a differential test harness, an AI tool read its position bookkeeping and saw that the skipped-position count is an int where the 9.12 reader used a long. A test on the stock jar with two documents of about 2^30 occurrences confirmed it; independent checkers then reproduced it with their own tests.

The method in full118 words

Method: non-formal (code reading plus an executed test; no model or solver produced the signal), a hunt unit on the Lucene104 postings reader.

  • The unit built a postings differential harness (0 mismatches at ordinary frequencies, 8 reader mutants killed). While modelling the reader for it, the finder compared the position bookkeeping with the Lucene912 reader and noticed int sumOverRange and int posPendingCount against long.
  • A main() on the stock main jar with two documents of 2^30+1 and 2^30+2 occurrences confirmed it with assertions on and off; it used an expert RAM setting and LogDocMergePolicy.
  • An independent verifier then wrote its own JUnit with a default IndexWriterConfig, which the one-test repro here is cut down from.

History

#

Today's code came with #13968 (10.1.0, 2024-11-01), which returned to an int after the 9.12/10.0 reader's long; the int count itself dates from Lucene 2.1 (2006). Failing runs on releases from 3.6.2 to 10.6.0 and on main; 9.12.0, 9.12.3 and 10.0.0 pass. Not fixed upstream.

Versions tested9 rows

Current code: #13968 "Move postings back to int[] to take advantage of having more lanes per vector." (main cfdd20f5bc8, branch_10x 8ae03d66ad1, 2024-11-01, first release 10.1.0) added the Lucene101 reader with int posPendingCount and int toSkip where the Lucene912 reader had long; #14033 (6c48b404cd4, 2024-12-04, also 10.1.0) made sumOverRange return int. Lucene103 and Lucene104 copied the code.

Older: the default positional readers kept the pending count in an int from LUCENE-687 (c0d330c0417, 2006-10-30, first in 2.1.0) through 9.11.1. Only #13585 (b4a8810b7ae, the Lucene912 reader of 9.12.0-9.12.3 and 10.0.0) used long; no PR discussed overflow, so whether that was meant as a guard is not established.

Trigger by version: in 2.1-3.6 only the documents passed over count (on 3.6.2, one skipped 2^30+1 document is fine, two are not); from 4.0 the current document is added too; in 4.1-9.11 only an advance() skip resets the count, so the documents need not share a block (code reading); from 10.1 a block move resets it. On 9.11.1 the raw positions are wrong but the checker's phrase query matched by coincidence: the Lucene99 reader re-checks the count on every nextPosition(), and the wrapped value came back around for those numbers.

Not fixed upstream (2026-10-31): main 2f424fd428da, branch_11x, branch_10_6 and the 10.6.0 tag still use int. On main the backward-codecs Lucene90, Lucene99, Lucene101 and Lucene103 readers have the same counters (code reading).

LFV-185, snapshot of 2026-11-05

Registry title
Postings readers count skipped positions in an int, so once the skipped occurrences of one term within a postings block pass Integer.MAX_VALUE, nextPosition() returns an earlier document's positions and phrase queries silently miss matches
Area
codecs / postings reader (Lucene104 BlockPostingsEnum position bookkeeping; also the Lucene101, Lucene103, Lucene99 and Lucene90 readers in backward-codecs)
Priority
Low, rank 970: Phrase positions go wrong once one term's skipped occurrences within a postings block pass 2^31, which needs documents repeating a term about a billion times.
Impact class
silent wrong results
Impact note
Hits positional search (PhraseQuery executed; span, interval, highlighting and payload consumers use the same nextPosition() path [read]) on a term with more than 2^31 occurrences among the documents of one postings block whose positions were skipped: with assertions off, a later document of that block gets an earlier document's positions, so matching is silently wrong (executed: a phrase false negative), and with assertions on 'assert posPendingCount > 0' fails the call; default codec and a default IndexWriterConfig suffice, and every release from 2.1.0 [read] / 3.6.2 [exec] to 10.6.0 is affected except 9.12.x and 10.0.0, but only with documents that repeat one term on the order of 2^30 times.
Summary
You index documents that each stay within Lucene's per-document limits but repeat one term about a billion times (the independent reproduction's test: one document with 2^30 - 16 occurrences of t, one with 2^30, then a normal document C with 'v' followed by 64 t's) and run PhraseQuery f:"v t", which only C matches. You expect the postings reader to return C's own positions (101, 102, 103, ...) and the query to find C. Instead the reader adds up the frequencies of the documents whose positions it skipped in an int, the sum 2,147,483,696 wraps negative, the skip is not done, and nextPosition() returns the first skipped document's positions (1, 2, 3), so the query finds 0 hits with assertions off (with assertions on, an internal assertion fails instead).
Introduced
