Word2VecSynonymFilter documents minAcceptedSimilarity as a cosine, but compares it with the score (1 + cosine) / 2

Word2VecSynonymFilter's javadoc calls minAcceptedSimilarity a cosine similarity, but the provider compares it with the score (1 + cosine) / 2, so the real cosine cutoff is 2m - 1: the default 0.8 lets in terms at cosine 0.6. The code looks intended; only the javadoc is wrong.

The finding in 30 seconds

#

Word2VecModel makes every vector unit length, and Word2VecSynonymProvider scores neighbours with DOT_PRODUCT, whose score is (1 + cosine) / 2. It keeps a neighbour when that score is >= minAcceptedSimilarity (Word2VecSynonymProvider.java:94, :99), while the only javadoc of the value calls it a cosine (Word2VecSynonymFilter.java:59-60).

Background: word2vec synonyms in Lucene

#
  1. Word2VecSynonymFilter (analysis-common, @lucene.experimental, since 9.7.0) looks up each token in a word2vec model and adds the model's nearest terms as synonyms at the same position.
  2. How near two terms are is the cosine similarity of their vectors: 1 for the same direction, 0 for unrelated (orthogonal), -1 for opposite.
  3. Lucene's DOT_PRODUCT and COSINE similarities return a score in [0, 1]: for unit vectors DOT_PRODUCT returns (1 + cosine) / 2, so cosine 1 scores 1, cosine 0 scores 0.5 and cosine -1 scores 0.
  4. minAcceptedSimilarity (factory default 0.8) is the cutoff: neighbours below it are not added.

The finding, step by step

#
  1. You add Word2VecSynonymFilter with minAcceptedSimilarity 0.8, the factory default. Its javadoc says the value is the "minimal value of cosine similarity between the searched vector and the retrieved ones".
  2. Your model has two terms, a = (1, 0) and b = (1, 1). Their cosine is 0.707, below 0.8, so you expect the input a to come out alone.
  3. Instead you get [a, b]: the provider compares 0.8 with the DOT_PRODUCT score of the unit-length vectors, (1 + 0.707) / 2 = 0.854.
  4. In general a term passes when (1 + cosine) / 2 >= m, that is when cosine >= 2m - 1. At the default 0.8, terms down to cosine 0.6 become synonyms (0.61 passes, 0.59 does not); at 0.5, unrelated (orthogonal) terms pass; below 0.5, negatively correlated ones.
  5. Nothing fails: the extra synonyms are added silently, at index and at query time, in every release since 9.7.0.

Who is affected

#

Applications that opt in to the experimental filter (constructor or the Word2VecSynonym factory) and set the threshold as a cosine, or keep the default 0.8 believing it means cosine 0.8. They silently get neighbours with cosine in [2m - 1, m) as extra synonyms (within the maxSynonymsPerTerm limit), at index and query time, in every release since 9.7.0.

Mechanism, terms and numbers579 words

The only documentation of Word2VecSynonymFilter's minAcceptedSimilarity is the constructor javadoc: "minimal value of cosine similarity between the searched vector and the retrieved ones". Word2VecModel makes every vector unit length, and Word2VecSynonymProvider scores neighbours with VectorSimilarityFunction.DOT_PRODUCT, whose float score is max((1 + dot) / 2, 0); it keeps a neighbour when that score is >= the threshold. For unit vectors the dot product is the cosine, so the real cosine cutoff is 2m - 1: the factory default 0.8 admits cosine 0.6, 0.5 admits orthogonal terms, and lower values admit negatively correlated terms.

The score-scale code looks deliberate: the factory's range check is (0, 1], the score's range, and a co-author of the filter wrote "the vector similarity score is 0<=x<=1" in #12169. So this is a documentation defect: the proposed fix is a javadoc clarification, with a code change only as an option. It has been there since the filter's first commit and is in every release from 9.7.0 to 10.6.0 and on main.

The mechanism (main 645d4fe14a20)

#
  1. The javadoc says cosine. Word2VecSynonymFilter.java:59-60: "@param minAcceptedSimilarity minimal value of cosine similarity between the searched vector and the retrieved ones". There is no other documentation of the value: Word2VecSynonymProvider.getSynonyms (:70-71) has no javadoc, the factory documents no parameters (Word2VecSynonymFilterFactory.java:29-34), and the package javadoc is one line.
  2. Vectors are unit length. Word2VecModel.java:58-59 calls TermAndVector.normalizeVector(), which applies VectorUtil.l2normalize (TermAndVector.java:34-38). So the dot product of two model vectors is their cosine.
  3. The provider scores with DOT_PRODUCT. Word2VecSynonymProvider.java:45-46 sets SIMILARITY_FUNCTION = VectorSimilarityFunction.DOT_PRODUCT; the query scorer from DefaultFlatVectorScorer returns similarityFunction.compare(...) (DefaultFlatVectorScorer.java:246). VectorSimilarityFunction.java:59-62: DOT_PRODUCT.compare returns normalizeToUnitInterval(dotProduct(v1, v2)), defined as Math.max((1 + value) / 2, 0) (VectorUtil.java:461-463).
  4. The threshold is compared with that score. Word2VecSynonymProvider.java:94 takes topDocs.scoreDocs[i].score; :99 keeps the term when similarity >= minAcceptedSimilarity; :100 returns the same score as the TermAndBoost boost.
  5. So a term is kept when (1 + cosine) / 2 >= m, that is cosine >= 2m - 1. In the repro, b's cosine 0.707 gives the score 0.854 >= 0.8.
  6. The factory fits the score scale. Word2VecSynonymFilterFactory.java:42 sets the default 0.8f; :68-71 rejects values <= 0 or > 1, the range (0, 1] (a NaN, which getFloat parses with Float.parseFloat, is not caught by this check).

What does not change

#

The ranking of neighbours is the same under both readings (the score grows with the cosine); only the cutoff differs. The number of synonyms per token is still bounded by the provider's maxSynonymsPerTerm + 1 search (Word2VecSynonymProvider.java:83-90). The filter does not use the boost (Word2VecSynonymFilter.java:79-88); callers of getSynonyms see the score there.

Exposure and likelihood161 words
  • Who. Users of Word2VecSynonymFilter through its public constructor or the factory (SPI name Word2VecSynonym, parameter minAcceptedSimilarity, default 0.8) who choose the threshold from the javadoc.
  • Default vs opt-in. Opt-in and @lucene.experimental (Word2VecSynonymFilter.java:37, Word2VecSynonymFilterFactory.java:32); no default analyzer uses it.
  • What goes wrong. Weaker neighbours are injected as synonyms, within the maxSynonymsPerTerm limit of the search: at the default, cosines 0.6 to 0.8; at 0.5, unrelated terms. Silent and deterministic. At index time the extra synonyms are written into the index, so correcting the threshold later needs a reindex.
  • Scale and age. Ordinary models and text; every release with the filter (9.7.0 to 9.12.3, 10.0.0 to 10.6.0) and main.
  • Why upstream tests never noticed. Their vectors are either at cosine >= 0.99 or at score <= 0.887, never in the gap [2m - 1, m) where the two readings differ (the study's reading); with the comparison changed to the cosine scale all 21 upstream word2vec tests still pass.

Why it looks unintended

#
  • The only documentation of the value says "minimal value of cosine similarity" (Word2VecSynonymFilter.java:59-60) and never mentions the normalization.
  • Lucene keeps the scales apart elsewhere: VectorUtil.cosine "Returns the cosine similarity", normalizeToUnitInterval turns it into "a normalized score", and the similarity queries call their threshold a "similarity score".
  • The score-scale code looks deliberate, so the fix is the javadoc, not the code.
The full argument246 words
  • The only documentation names the other scale. Word2VecSynonymFilter.java:59-60 calls the value a "minimal value of cosine similarity" and says nothing about normalization; the factory and getSynonyms add nothing.
  • Lucene's own javadoc keeps the two scales apart. VectorUtil.java:96: cosine() "Returns the cosine similarity between the two vectors" (the raw value in [-1, 1]). VectorUtil.java:452-459: normalizeToUnitInterval "Converts a dot product or cosine similarity value to a normalized score in the [0, 1] range ... using the formula: (1 + value) / 2". VectorSimilarityFunction.java:122: compare() "Calculates a similarity score". FloatVectorSimilarityQuery.java:49 (and :76, :92, :105): "similarity score for result collection". No Lucene javadoc calls (1 + cosine) / 2 a "value of cosine similarity".
  • Since the first commit. The javadoc line, the choice of DOT_PRODUCT, the comparison, the 0.8 default and the (0, 1] check all arrived together in 1f4f2bf50957 (#12169). The javadoc text and the comparison line are unchanged since; the code around them was refactored (for example #12434, #12529 and #15704 in the provider), and the DOT_PRODUCT score was clamped at 0 in 9.9.0 (#12727) and later moved into normalizeToUnitInterval (#15036), all without changing the (1 + dot) / 2 scale.
  • The hazard is known in general. In the review of #11946 (a 2022 kNN similarity-threshold PR, closed unmerged, a different API) a reviewer warned: "a dotProduct of 0.7 ... ACTUALLY means they want to limit the scores to .85 ((1 + dotProduct)/2). How is the user supposed to know that?"
The devil's-advocate check234 words

Strongest case for "leave it" (the study's intended-behaviour devil's advocate and a cross-model reviewer, OpenAI GPT-5.6): the score-scale code looks deliberate. The factory's range check (0, 1] is the score's range, not the cosine's [-1, 1]; a co-author (Alessandro Benedetti) wrote "the vector similarity score is 0<=x<=1" in #12169 (2023-03-22, about the boost); the open draft #12433 by the filter's author tests with normalized VectorSimilarityFunction.COSINE.compare values while calling them "the cosine similarity"; and Lucene itself labels VectorSimilarityFunction.COSINE, whose compare() returns the normalized score, "Cosine similarity" (VectorSimilarityFunction.java:77-80). In that vocabulary "cosine similarity" means Lucene's normalized cosine score, the API is experimental, and a committer could call the wording acceptable.

Why it fails: it rules out a code bug, which is why the proposal is a javadoc fix, but not the documentation defect. VectorSimilarityFunction.java:77-80 names a metric and adds "The similarity score is normalised to assure it is positive"; the filter javadoc names a value and never mentions normalization. The (0, 1] range does not tell a reader which scale applies, since it is also a natural range for a raw-cosine synonym cutoff (an independent Go port of the filter documents the 0.8 default as "the default minimum cosine similarity threshold"). The cross-model reviewer itself wrote: "A documentation clarification is warranted even if behavior remains unchanged." Confidence: high that the javadoc misdescribes the compared value, medium that a committer will want the change.

Suggested fix

#

Recommended A. Clarify the javadoc (recommended)

Clarify the javadoc: the value is a similarity score, (1 + cosine) / 2 for the normalized model vectors, so a term is accepted when its cosine is at least 2m - 1 (0.8 means cosine 0.6). No behaviour change. Validated with gradle: the format check and javadoc render pass, and all word2vec tests pass.

A. Clarify the javadoc (recommended) (validated by the checks)

#

Say that the value is a similarity score, (1 + cosine) / 2 for the normalized model vectors, and give the equivalent cosine cutoff.

   * @param maxSynonymsPerTerm maximum number of result returned by the synonym search
-  * @param minAcceptedSimilarity minimal value of cosine similarity between the searched vector and
-  *     the retrieved ones
+  * @param minAcceptedSimilarity minimal similarity score between the searched vector and the
+  *     retrieved ones. The model vectors are normalized and scored as (1 + cosine) / 2, so a term
+  *     is accepted when its cosine similarity is at least 2 * minAcceptedSimilarity - 1 (the
+  *     factory default 0.8 accepts cosine 0.6, 0.5 accepts orthogonal terms, and lower values also
+  *     accept negatively correlated terms)
   */

Trade-offs

  • No behaviour change, so no existing configuration moves; it uses the vocabulary of VectorUtil.normalizeToUnitInterval and of the similarity queries ("similarity score").
  • It does not help users who already set a cosine value; they need (1 + c) / 2 for a cosine cutoff c.
  • Optionally add the same sentence to the factory's class javadoc, where SPI users look, and to getSynonyms (not run).

B. Compare on the cosine scale (an option only) (validated by the checks)

#

In Word2VecSynonymProvider.getSynonyms, compare 2 * similarity - 1 with the threshold, which makes the current javadoc true over the reals.

         // We remove the original query term
-        if (!synonym.equals(term) && similarity >= minAcceptedSimilarity) {
+        // DOT_PRODUCT scores unit vectors as (1 + cosine) / 2; the threshold is a cosine
+        float cosine = 2 * similarity - 1;
+        if (!synonym.equals(term) && cosine >= minAcceptedSimilarity) {
           result.addLast(new TermAndBoost(synonym, similarity));

Trade-offs

  • Silently tightens every existing configuration (the default 0.8 would drop all neighbours between cosine 0.6 and 0.8), against the evident intent of the code; it would need a CHANGES entry as a behaviour change.
  • The factory's range check (0, 1] would then forbid cutoffs at or below cosine 0; the boost stays on the score scale.
  • Float caveat: 2 * similarity - 1 is not exact in float32. For m = 0.8f a dot product of exactly 0.8f scores 0.9f, and 2 * 0.9f - 1 = 0.79999995f < 0.8f, so this option rejects a cosine equal to the threshold (333 of the 1000 values m = i / 1000, in a standalone float check). Comparing the score with (1 + m) / 2 instead accepts that case (not run against Lucene); over the reals the two are the same test.

What the checks validated

  • Same worktree and seed: the minimal test passes with assertions off (1 test), and the word2vec tests including it pass with assertions on (22 tests); checkGoogleJavaFormat passes.
  • A standalone run agrees: with the change applied, the minimal test passes with assertions on and off, and the 21 upstream tests pass (2026-11-01). So no upstream test pins either scale.

Downstream note

#

Products that pass minAcceptedSimilarity through to their own users, for example in an analysis-chain configuration, inherit the misleading cosine wording and the looser cutoff.

How it was found

#

Semi-formal. A hunt unit compared the real filter, over a bounded exhaustive set of small models and thresholds, with a reference written from the javadoc: the cosine oracle failed 3,530,652 of 9,136,266 checks while a score-scale oracle held in all of them. A Z3 proof then gave the closed form, cosine >= 2m - 1.

The method in full138 words
  • Lead. The hypothesis came from code reading: the javadoc says cosine, the provider uses DOT_PRODUCT.
  • Translation validation. W2VExhaustiveTV.java drove the real analysis-common jar over a bounded exhaustive space of small models and thresholds and checked each output against oracles written from the javadoc. "Every synonym has exact cosine >= minAcceptedSimilarity" failed 3,530,652 of 9,136,266 checks; "every synonym has score >= minAcceptedSimilarity" held in all of them. The harness was mutant-checked.
  • Proof. A Z3 script proved accept <=> cosine >= 2m - 1 over the reals and, over float32, that 0.8f accepts exactly the dot products >= 0.6f (10 of 10 queries as expected).
  • Verification. A public-API JUnit, an independent reproducer, an intended-behaviour devil's advocate, an adjudication, a re-verification, a second adjudication and a cross-model reviewer (OpenAI GPT-5.6) followed; all agree on the behaviour and the root cause.

LFV-870, snapshot of 2026-11-02

Registry title
Word2VecSynonymFilter documents minAcceptedSimilarity as a cosine similarity, but Word2VecSynonymProvider compares it with the normalised score (1 + cosine) / 2, so the effective cosine cutoff is 2m - 1 (the default 0.8 accepts cosine 0.6, 0.5 accepts orthogonal terms, values below 0.5 accept negatively correlated terms); documentation defect, the javadoc fix is the default proposal
Area
analysis-common / synonym.word2vec (Word2VecSynonymFilter minAcceptedSimilarity javadoc vs Word2VecSynonymProvider threshold test)
Priority
Low, rank 962: A documentation-only defect in the opt-in experimental Word2VecSynonymFilter whose javadoc leads users to a much looser cosine cutoff and weaker synonyms.
Impact class
minor
Impact note
Only applications that opt in to the @lucene.experimental Word2VecSynonymFilter (constructor or factory) and choose minAcceptedSimilarity as a cosine, as its only javadoc says, are misled: they get the looser cutoff cosine >= 2m - 1 (the factory default 0.8 admits cosine 0.6, 0.5 admits orthogonal terms, values below 0.5 admit negatively correlated terms), so more loosely related synonyms, still at most maxSynonymsPerTerm per token, are injected at index and query time; ordinary scale, no error, every release since 9.7.0; the code does what the authors intended, only the javadoc names the wrong scale.
Summary
You build Word2VecSynonymFilter with minAcceptedSimilarity 0.8 (the factory default), whose only documentation says it is the 'minimal value of cosine similarity between the searched vector and the retrieved ones', so you expect only model terms at cosine 0.8 or more as synonyms. Word2VecSynonymProvider compares the threshold with the DOT_PRODUCT score of the unit-length model vectors, which is (1 + cosine) / 2, so the real cosine cutoff is 2m - 1: at 0.8 a term at cosine 0.65 is emitted, at 0.5 an orthogonal term (cosine 0) is emitted, and at 0.2 a term at cosine -0.5 is emitted. The authors' intent points to the score scale (the factory accepts only (0, 1]), so the fix is a javadoc clarification, not a code change.
