Block-tree TermsEnum.next() after seekExact(term, TermState) on a new enum restarts at the field's first term

Position a brand-new default-codec TermsEnum with seekExact(term, TermState) and next() restarts at the field's first term: terms a, b, c, seek to b, next() gives a, not c. Every release since 4.0 has the same code; no in-tree Lucene query calls next() there, and no wrong search result is known.

The finding in 30 seconds

#

A TermState seek as the first call on a new block-tree enum, then next(): the enum starts over at the field's first term.

Background: TermsEnum and TermState

#
  1. A TermsEnum walks the terms of one field in one segment in sorted order: next() moves to the following term, and the seek methods jump to a given term.
  2. A TermState is a saved position of one term. The block-tree dictionary's seekExact(term, state) jumps straight to it without searching the terms dictionary (the javadoc allows this for low-level implementations). TermQuery builds such states with TermStates.build and applies each one to a new enum of its segment to read the term's postings.
  3. A block-tree enum makes its private copy (clone) of the terms-file input lazily, on the first block of terms it reads. A TermState seek reads no block, so a query that only needs postings never pays for that copy.

The finding, step by step

#
  1. Index three documents whose field f holds a, b and c (one segment, default codec), and take the TermState of f:b with TermStates.build(...), as TermQuery does.
  2. Open a new enum on f and call seekExact("b", state). term() reports b and docFreq() 1, as expected.
  3. Call next(). You expect c: terms come in increasing order, and every other terms dictionary returns the next term after the same calls.
  4. You get a, the field's first term, with no error, assertions on or off. The next calls return b, c, null: the whole field again, including the terms before b.
  5. Why: the TermState seek reads no block of terms, so the enum's private copy of the terms-file input is still null. next() takes a null input to mean "new enum, start at the first term" and skips the catch-up code written for exactly this case.

Who is affected

#

Only code that drives the Expert TermsEnum API itself: it seeks a new enum with a TermState from TermStates, TermQuery.getTermStates() or a saved cursor, then calls next(), and gets wrong terms every time; a paging loop that resumes each page this way makes no progress. Default codec, BlockTreeOrds, 9.x-10.2 indexes. No in-tree query does this.

Mechanism, terms and numbers617 words

TermsEnum.seekExact(BytesRef, TermState) puts an enum on a term from saved state; the block-tree terms dictionaries do this without re-seeking the dictionary (the javadoc allows it for low-level implementations; the generic BaseTermsEnum just seeks the term). TermStates.build and TermQuery.getTermStates() hand out such states, and TermQuery applies them to a new enum of each segment. With the block-tree terms dictionary (the default codec, BlockTreeOrds and the Lucene90 block tree used for 9.x-10.2 indexes), when that seek is the first call on a new enum, term() and docFreq() are right but next() returns the field's first term and the enum then lists the whole field again. The seek leaves the lazily cloned input null, and next() reads a null input as "fresh enum" before its own catch-up branch for TermState seeks can run. Three one-term documents a, b, c: after the seek to b, next() returns a instead of c, silently, with assertions on and off (main and 10.6.0). Every release from 4.0.0-alpha to 10.6.0 has the same code order, and every release that was run fails the same way. No in-tree Lucene query calls next() after a TermState seek and no wrong search result is known; code that drives the Expert TermsEnum API directly is affected.

The bug

#
  1. The SegmentTermsEnum constructor sets currentFrame = staticFrame and does not clone the terms input (SegmentTermsEnum.java:60-69, the root-block load at :68-69 commented out); initIndexInput() clones it lazily (:81-85), when a frame first prefetches or loads a block (SegmentTermsEnumFrame.java:147, :167).
  2. seekExact(BytesRef, TermState) (:1027-1046) sets currentFrame = staticFrame (:1035), copies the state and the term, and loads no block, so in stays null.
  3. next() (:892) first tests if (in == null) { // Fresh TermsEnum; seek to first term (:893) and makes the root frame the current frame in place of staticFrame (:896).
  4. Only then comes if (currentFrame == staticFrame) (:911-922), whose comment says that after seek(TermState), "if they then call next(), this method catches up all internal state so next() works properly". It re-seeks the term (:920), but step 3 already replaced currentFrame, so it never runs and next() returns the first term of the root block.
  5. The same order is in BlockTreeOrds (OrdsSegmentTermsEnum.java:906 before :932) and in the Lucene90 block tree in backward-codecs (SegmentTermsEnum.java:983 before :1008); the sandbox IDVersionSegmentTermsEnum has it too (next() at :1016, its fresh-enum branch at :1018-1019).

The numbers

#
  • Terms a, b, c, seek to b: term() is b and docFreq() 1, then the next() calls return a, b, c, null instead of c, null. A seek to a gives a, b, c, null (expected b, c, null); a seek to c gives a, b, c, null (expected null).
  • Terms kiwi, lemon, mango, olive, peach: for every one of the five targets the first next() returns kiwi; for peach, the last term, it should return null; after the seek to mango the next() calls return kiwi, lemon, mango, olive, peach instead of olive, peach.
  • 3,000 terms over several blocks: targets #0, #1, #1500, #2998 and #2999 all return the first term.
  • An exhaustive check of every set of 1-3 short terms (the writer set to 2 to 3 entries per block) against a sorted-array reference: 10,277 of 10,700 sets mismatch, every mismatch a next() after the TermState seek.
  • Not affected: a state taken from the same enum, an enum positioned once by an ordinary seek or next() first, and term(), docFreq(), totalTermFreq(), postings() and impacts() right after the seek (a probe asserts all five on the default block tree, BlockTreeOrds and the Lucene90 block tree).
Exposure and likelihood385 words
  • Who is hit. Application or library code that drives TermsEnum directly: it positions a brand-new block-tree enum with seekExact(term, state), the state taken from TermStates, TermQuery.getTermStates() or a saved (term, state) pair, and then calls next(), for example to list the terms after a known term or to resume term paging. Such code gets wrong terms every time.
  • What it does. A paging loop that opens a new enum for each page and resumes it from the previous page's last (term, TermState) makes no progress, because each resumed page starts again at the field's first term: capped at 200 pages of 100 it delivered 20,000 terms for a field with 2,706 distinct terms and had not finished; with the fix it finished in 28 pages. A listing that starts at a TermState and stops at an upper bound also returns every term below its start. The wrong listing stays inside the same field and segment and ends after one extra pass.
  • Who is not. Lucene's queries. Every in-tree caller of the TermState seek reads only postings, impacts or statistics afterwards: outside sandbox TermQuery, SynonymQuery, PhraseQuery, MultiPhraseQuery, CombinedFieldQuery, the multi-term constant-score wrappers and SpanTermQuery; in sandbox PhraseWildcardQuery, TermAutomatonQuery and the sandbox CombinedFieldQuery. FuzzyTermsEnum and FilterLeafReader only pass the call on to another enum. 57 queries over the paths outside sandbox, on an index with deletions and with the bug active in 4 of 4 leaves, matched a SimpleText oracle exactly in all hits and their scores, the total hit counts, count(), and the explanation's match flag and value for the top three hits of each query. The downstream code read (Elasticsearch, OpenSearch and its security plugin, Solr; default branches, not exhaustive) has no caller that calls next() after a TermState seek. So no wrong Lucene search result is known; this covers today's in-tree callers, not future or downstream code.
  • Default vs opt-in. Default codec and every block-tree terms dictionary; the trigger is an Expert call sequence on an @lucene.experimental class (TermsEnum.java:37).
  • Scale. One segment and three terms are enough; deterministic.
  • How likely. Rare: the recorded search found no public report since 4.0 (2012), although a 2011 dev@ thread shows a user calling seek(BytesRef, TermState) followed by next(), before block tree existed.

Why it looks unintended

#
  • The javadoc says "Each term in the enumeration is greater than the one before it"; after the seek to b, next() returns the smaller a.
  • next()'s own comment promises that after seek(TermState) it "catches up all internal state so next() works properly".
  • TermQuery applies such states to new enums, and every other terms dictionary returns the next term.
The full argument343 words
  • Order and position. TermsEnum.java:31-32: "Term enumerations are always ordered by BytesRef.compareTo ... Each term in the enumeration is greater than the one before it." :34-35: the enum is unpositioned until you "successfully call next or one of the seek methods". :98: "Expert: Seeks a specific position by TermState".
  • The code promises it. The comment in next() (SegmentTermsEnum.java:912-917) says that if "seek(TermState) was called ... if they then call next(), this method catches up all internal state so next() works properly". The catch-up exists; it is unreachable on a new enum.
  • Lucene uses cross-instance states itself. The NOTE in the same javadoc (TermsEnum.java:105-108) calls states compatible "only iff the source and the target TermsEnum operate on the same field", which only makes sense for two enums. TermStates.build/get and TermQuery.getTermStates() are public and return states whose source enum the caller never sees; TermQuery applies them to a new enum (TermQuery.java:140-141), and so does the test framework's RandomPostingsTester (:1613, :1628).
  • The test framework's state model accepts it. AssertingTermsEnum marks the enum POSITIONED after seekExact(term, state) (AssertingLeafReader.java:454-460) and accepts next() from there (:332-343). It does not check what next() returns, so this shows how Lucene's own wrapper models the sequence, not what the javadoc promises.
  • Every other dictionary returns the successor. After the same calls (seek to banana), FST50, Direct, BlockTerms (two index variants), MemoryIndex and SimpleText return cherry; only the default block tree and BlockTreeOrds return apple. A later fact check found the same for UniformSplit and STUniformSplit.
  • History. On unreleased trunk before LUCENE-3562 (2011) the constructor loaded the root block, so next() reached the catch-up. LUCENE-3562, a performance change, made the input clone lazy and put the "fresh" branch first; nothing in it discusses next(). Stock 4.0.0 fails and 4.0.0 with only that constructor change reverted passes. In 2013 mikemccand wrote on LUCENE-3069 (#4142) that the lazy TermState seek is by design and "We only need to re-load the metadata if the caller then tries to do .next()".
The devil's-advocate check403 words

The strongest case for "works as designed": TermsEnum.java:102-103 says "Seeking by TermState should only be used iff the state was obtained from the same TermsEnum instance." Following it, the bug cannot happen, because taking a state from an enum loads a block; the only upstream test that calls next() after a TermState seek uses the same enum (TestTermsEnum.java:686); and every in-tree cross-instance caller pulls only postings or statistics. A cross-model reviewer called the trigger out of contract on this sentence alone.

Why it is weaker than it looks, though not settled: the sentence is hard to reconcile with Lucene's own use of states. TermStates.build and TermQuery.getTermStates() hand out states built from enums their callers never see, so those states can never meet the sentence, and TermQuery itself applies them to a new enum (a caller can also put its own state into a TermStates through its public constructor or register). A maintainer may still read the sentence as a precondition for calling next() after such a seek, with cross-instance states meant only for postings and statistics. The NOTE right after the sentence speaks of a "source" and a "target" enum and warns that an incompatible state "might leave this TermsEnum in undefined state"; this state meets its compatibility condition (same field, same segment), but the NOTE does not promise that next() works after a seek with another enum's state. The sentence says "should", not "must"; the next() comment promises the opposite; and the sentence came from a 2013 commit titled "javadocs" with no issue or discussion, which replaced the 2011 wording "obtained from the same IndexReader". The same day, 47 minutes before that commit, mikemccand had written on LUCENE-3069 (#4142) that the lazy TermState seek "is normal / by design" and "We only need to re-load the metadata if the caller then tries to do .next()"; only the timestamps are recorded, no link between the two is claimed. Under that wording the repro is in contract, and it already failed on 4.0.0-ALPHA and 4.0.0. None of this settles the question; the maintainers decide it. If they hold the sentence as binding, the outcome is a clearer javadoc and a corrected next() comment; either way the docs and the code disagree today. Our reading: not intended, a defect. The adjudication's confidence is medium because of this sentence, and the maintainers choose between the code fix (A) and a javadoc fix (C).

Suggested fix

#

Recommended A: tell a TermState-positioned enum apart from a fresh one

Add a seekedByTermState flag to the three block-tree enums: the TermState seek sets it, the other seeks clear it, and next() takes its "fresh enum" branch only when it is false. next() then reaches its existing catch-up, and the lazy clone that keeps TermQuery cheap stays. +28/-3 lines; the repro and the closest upstream suites pass.

It was revised after the fact checks: its first version never cleared the flag (see the trade-offs). Options B and C were not built.

A: tell a TermState-positioned enum apart from a fresh one (validated by the checks) (recommended)

#

In the lucene103 SegmentTermsEnum, the Lucene90 copy in backward-codecs and OrdsSegmentTermsEnum: a seekedByTermState field, set in seekExact(BytesRef, TermState), cleared at the start of the other seeks (seekExact(BytesRef) and its two-phase form, seekCeil, and in OrdsSegmentTermsEnum seekExact(long)), and tested in next(). next() then falls through to its existing catch-up, which re-seeks the term and loads its block: the same path an enum takes today when it was positioned once before the TermState seek.

// new field
private boolean seekedByTermState;

// seekExact(BytesRef) (via prepareSeekExact) and seekCeil
seekedByTermState = false;

// next()
if (in == null && seekedByTermState == false) {
  // Fresh TermsEnum; seek to first term:
  ...
}

// seekExact(BytesRef, TermState)
currentFrame = staticFrame;
seekedByTermState = true;

Trade-offs

  • Keeps the lazy clone of LUCENE-3562: a TermState seek followed only by postings or statistics, the TermQuery path, still clones nothing.
  • One boolean per enum, written by each seek; the first next() after a TermState seek pays one term lookup, as an enum positioned before the seek does today. No benchmark was run.
  • Why the other seeks clear the flag: the first version of this fix never cleared it (and reused the positioned flag in OrdsSegmentTermsEnum). That changed a sequence outside the contract, a TermState seek, then a seekExact(BytesRef) that returns false without loading a block, then next() on the now unpositioned enum (AssertingTermsEnum rejects that next()): both SegmentTermsEnum copies then continued after the old TermState term instead of restarting like a new enum, or threw (AssertionError, and ArrayIndexOutOfBoundsException without assertions) when the failed seek ended on a block without terms. The cross-model fact check pointed to this path; with the flag cleared, the sequence behaves as on stock.
  • The sandbox IDVersionSegmentTermsEnum has the same order and is not patched.

B: open the input eagerly in seekExact(BytesRef, TermState) (not built)

#

Call initIndexInput() in the TermState seek, so next() never sees a null input after it.

Trade-offs

One line per copy, but it brings back the per-seek input clone that LUCENE-3562 removed on purpose, on the path every TermQuery takes for every segment. Not run, so it is unknown whether the catch-up handles an enum that has an input but no pushed frames.

C: documentation only (not built)

#

State in the TermsEnum javadoc that next() is not supported after seekExact(term, state) unless the state came from the same enum, and correct the comment in next().

Trade-offs

No code risk, but it leaves a silent wrong listing in a public API, and states from TermStates.build or TermQuery.getTermStates() can never meet that condition. Only if the maintainers hold the "same TermsEnum instance" sentence as binding.

Downstream note

#

No search result changes, but application code that pages through terms by opening a new enum per page and resuming from the previous page's TermState makes no progress (a probe's loop delivered 20,000 terms within its 200-page cap for a 2,706-term field), so such code should apply the fix or position the enum with an ordinary seek first.

How it was found

#

An AI tool was extending a harness that checks the real block-tree writer and reader, operation by operation, against a sorted-array reference. After reading the TermState seek code it added a walk that applies one enum's state to a fresh enum: on stock main, 10,277 of 10,700 small term sets mismatched. It then wrote a JUnit test.

The method in full164 words

Method: semi-formal (bounded-exhaustive translation validation plus code reading).

  • An AI finder was extending a harness that writes term sets with the real block-tree writer, reads them with the real reader and checks every TermsEnum operation against an exact reference (the sorted term array), over every set of 1-3 terms built from short strings and small block sizes.
  • Its TermState walks only reused the same enum. Reading the seek code, the AI tool added a walk that takes the state of a term from one enum, applies it as the first call on a second enum, then runs 12 random operations. On the stock main jar it mismatched on 10,277 of 10,700 term sets, every mismatch a next() after the TermState seek.
  • The AI tool then wrote a deterministic JUnit test that drives only public Lucene APIs, which was later reduced to the one-method test. So this was found by targeted code reading checked by an exhaustive harness, not a blind discovery by a tool.

History

#

Introduced in 2011 by LUCENE-3562 (9e27723b3702), a performance change that made the input clone lazy and put the fresh-enum test first. Every release from 4.0.0-alpha to 10.6.0 has it, and so does main; no release was ever unaffected.

Versions tested8 rows

LUCENE-3562 "stop caching thread-private TermsEnums in Terms" (mikemccand, svn r1203294, 2011-11-17; the JIRA issue is now #4636, before GitHub, no PR) commented out the root-block load in the SegmentTermsEnum constructor, made the input clone lazy "so that consumers that just pull a TermsEnum to seekExact(TermState) don't pay this cost", and added the "Fresh TermsEnum" branch ahead of the catch-up. Later commits moved, copied, forked or restructured the code and kept that order (a 2013 fork and its removal, LUCENE-5675 and the sandbox IDVersion fork in 2014, LUCENE-5819 BlockTreeOrds in 4.10.0, LUCENE-5969 backward codecs in 2014, LUCENE-9705 lucene90 in 2021, #14333 and #14563 lucene103 in 2025, #15712 in 2026). Block tree existed without the bug only on unreleased trunk from 2011-08-20 to 2011-11-17; 3.6.2 has neither the API nor block tree. A static scan of the 123 release tags 4.0.0-alpha to 10.5.2 in the history clone finds the same order in every one, and the 10 releases not tagged there (8.8.2, 8.9.0 to 8.11.4, 10.6.0) were all run: together all 133 releases from 4.0.0-alpha to 10.6.0.

The release rows ran the minimal test (10.6.0), a 9.x port of it (9.12.3), the finder's JUnit (10.5.2, 10.3.0, 10.2.2, 9.12.3) or a portable main() version of the same steps (on 4.0.0-ALPHA, 4.0.0, 4.10.4, 5.5.5, 6.6.6, 7.7.3, 8.11.4, 9.0.0, 9.12.3, 10.0.0, 10.2.2, 10.3.0 and 10.5.2, and on every release from 8.8.2 to 8.11.3); all on OpenJDK 25.0.3, Linux aarch64, release jars SHA-1 checked.

Registry title
Block-tree TermsEnum.next() after seekExact(term, TermState) on a never-positioned enum restarts at the field's first term instead of returning the next term
Area
codecs / block-tree terms dictionary (Lucene103 SegmentTermsEnum; also BlockTreeOrds and the Lucene90 block tree in backward-codecs)
Priority
Low, rank 576: Block-tree TermsEnum.next() after seekExact(term, TermState) on a fresh enum restarts at the field's first term, silent but only for custom code driving that Expert call sequence, under a disputed 'same TermsEnum instance' contract.
Impact class
silent wrong results
Impact note
Application or downstream code that positions a brand-new block-tree TermsEnum (default codec, BlockTreeOrds, or the Lucene90 block tree that was the default in 9.x-10.2) with seekExact(term, TermState), using a state taken from another enum of the same field and segment (typically from TermStates or TermQuery.getTermStates), and then calls next() silently gets the field's first term and a second listing of the whole field, including the terms before the sought one, with -ea and -da; default codec but an Expert/experimental call sequence that no in-tree query and none of the downstream code read performs, so no wrong search result is known; no scale needed.
Summary
You take the TermState of a term (say 'banana') from one TermsEnum, or from TermStates the way TermQuery does, and use it to position a brand-new TermsEnum of the same field and segment with seekExact(term, state); term() and docFreq() then correctly report 'banana'. You expect next() to return the following term ('cherry'), as the comment inside next() promises and as every other terms dictionary does. Instead, with the default block-tree terms dictionary, next() returns the field's first term ('apple') and iteration starts over from the beginning, because next() mistakes the not-yet-loaded enum for a fresh one and throws the TermState position away.
