TeluguNormalizer joins ఒ + ౌ into AU but never folds that AU to OO, so ఔషధం and ఒౌషధం get different terms

Lucene's Telugu normalizer folds AU ఔ to OO ఓ and joins the two-character spelling ఒ + ౌ into ఔ, but never folds the ఔ it joins: without IndicNormalizationFilter in front, ఔషధం ("medicine") becomes ఓషధం, ఒౌషధం becomes ఔషధం. Present since 8.10.0; the stock TeluguAnalyzer is unaffected since 9.10.0.

The bug in 30 seconds

#

Telugu writes the vowel AU as one character, ఔ, or as two, ఒ + ౌ. Lucene's Telugu normalizer folds ఔ to ఓ (OO) and joins ఒ + ౌ into ఔ. Because it reads each word once, left to right, the ఔ it joins is never folded.

  1. Build an analyzer with the teluguNormalization filter and no indicNormalization in front of it, as in the factory's javadoc example (standard tokenizer + Telugu normalization). The filter folds AU ఔ (U+0C14) to OO ఓ (U+0C13), so ఔషధం ("medicine") becomes ఓషధం; an upstream test pins this fold.
  2. AU can also be typed as two characters: the letter ఒ (U+0C12) plus the vowel sign ౌ (U+0C4C). The filter recognizes this pair and joins it into ఔ, so you expect ఒౌషధం to become ఓషధం too, the way its other pair ఒ + ౕ becomes ఓ.
  3. You get ఔషధం. The normalizer reads the word once, left to right: it writes the joined ఔ at the position it is on (TeluguNormalizer.java:104) and never comes back, so the ఔ → ఓ rule (:60-62) never sees it.
  4. With one document per spelling (run on main), each spelling's query finds 1 of 2 documents, and a prefix query typed ఒౌష finds only its own spelling; with the one-line fix every query finds 2 of 2. No error. The stock TeluguAnalyzer already finds 2 of 2, because its IndicNormalizationFilter joins the pair first.

Who is affected

#

Applications that use TeluguNormalizationFilter or the teluguNormalization factory without IndicNormalizationFilter in front, as in the factory's javadoc example, on every release since 8.10.0. Words spelled with ఒ + ౌ do not match the ఔ spelling, at index and query time. The stock TeluguAnalyzer is unaffected since 9.10.0. A fix needs a reindex.

Mechanism, terms and numbers689 words

TeluguNormalizer (package-private since 10.0; used by TeluguNormalizationFilter, the teluguNormalization factory and TeluguAnalyzer) is one left-to-right pass over the term. It folds the long vowel AU ఔ (U+0C14) to OO ఓ (U+0C13) (TeluguNormalizer.java:59-62), a rule an upstream test pins for the filter alone, and it joins the two-character spelling ఒ + ౌ (U+0C12 U+0C4C) into ఔ (:102-106, comment (ఒ + ౌ) -> au (ఔ)). The joined ఔ is written at the current position, which the loop never visits again, so it is never folded: ఔషధం ("medicine") becomes ఓషధం while ఒౌషధం becomes ఔషధం. The class's other pair, ఒ + ౕ, writes ఓ directly. Chains that run the Telugu filter without IndicNormalizationFilter in front, such as the factory javadoc's example, give the two spellings different terms at index and query time; the stock TeluguAnalyzer composes the pair earlier and is unaffected from 9.10.0 on (before that, only its normalize() path was affected). Every release from 8.10.0 to 10.5.2 and main has it (10 releases and main were run; the releases in between have the same rule by the code history). The one-line fix (write ఓ at :104) changes the terms of words spelled with the pair, so those fields need a reindex.

Terms

#
  • ఔ LETTER AU U+0C14 and ఓ LETTER OO U+0C13: independent vowels. The normalizer folds the long vowels to short ones, among them ఔ to ఓ (// long -> short vowels, TeluguNormalizer.java:59-62).
  • ఒ + ౌ (LETTER O U+0C12 + VOWEL SIGN AU U+0C4C): a two-character spelling of AU, which the class joins into ఔ (:102-106). It is not a Unicode canonical equivalent (NFC and NFD keep both spellings); IndicNormalizer's decomposition table, documented as following Unicode 5.2 and a page of graphical decompositions (IndicNormalizer.java:36-37, :71-74), maps it to AU for Telugu (:143-144).
  • ఒ + ౕ (LETTER O + LENGTH MARK U+0C55): a two-character spelling of OO, which the class joins into ఓ (:98-101); an upstream test calls these "two ways to write oo letter" (it runs the full TeluguAnalyzer, where IndicNormalizationFilter joins the pair first; the filter alone also gives ఓ, as the probe shows).
  • TeluguNormalizer: a left-to-right rewrite of each token, one switch (s[i]) case per character. It is package-private (public in 8.10.0-9.12.x) and reached through TeluguNormalizationFilter, the teluguNormalization factory (for analysis and normalize()) and TeluguAnalyzer. Keyword-marked tokens skip it.

The bug

#
  1. case 'ఒ': (TeluguNormalizer.java:96-107): if the next character is ౌ, it writes s[i] = 'ఔ' (:104) and deletes position i + 1.
  2. The loop then continues with i + 1. Position i is never visited again, so case 'ఔ' (:60-62) never sees the ఔ written there. For ఒౌషధం: ఒ ౌ ష ధ ం → ఔ ష ధ ం, done.
  3. A precomposed ఔ always hits case 'ఔ': ఔషధం → ఓషధం. So in a chain with only this filter, the joined ఔ renames the term but never merges it with the precomposed spelling.
  4. The sibling compositions write final forms (ఒ + ౕ → ఓ at :100, ె + ౖ → ై at :92), and the same switch already steps back (i--) after deleting a zero-width joiner (:52-57); the AU branch does neither.
  5. TeluguAnalyzer runs IndicNormalizationFilter first (TeluguAnalyzer.java:120-121, :130-131), which joins ఒ + ౌ into ఔ before the Telugu filter folds it, so the stock analyzer gives one term.

Exposure and likelihood315 words
  • Who is exposed. A CustomAnalyzer, a hand-built Analyzer or a schema with the Telugu filter and no IndicNormalizationFilter before it, for example the factory javadoc's field type (StandardTokenizerFactory + TeluguNormalizationFilterFactory); on 8.10.0-9.12.x also direct callers of the then-public TeluguNormalizer.normalize. No javadoc names Indic normalization as a prerequisite.
  • The stock analyzer. TeluguAnalyzer is unaffected from 9.10.0 on. In 8.10.0-9.9.x its normalize() dropped IndicNormalizationFilter (fixed by GITHUB#13059), so its prefix, wildcard and fuzzy terms hit the bug there (executed on 8.10.0, 8.10.1, 8.11.0, 8.11.4, 9.0.0 and 9.9.2).
  • Why the chain is plausible. In the open issue gh#14659 about a Telugu rule of IndicNormalizer, a maintainer (rmuir) replied "if you have perfect unicode text ... don't use this filter" (the filter under discussion is IndicNormalizationFilter), and a participant proposed making TeluguAnalyzer leave it out by default. Either path leaves the Telugu filter alone with the pair.
  • What the damage looks like. Silent: no error, and identical spellings still match. With one document per spelling (run on main), each spelling's query finds 1 of 2 documents and a prefix query typed with the pair finds only its own spelling; with the fix, 2 of 2. The bug only keeps apart spellings that the fix joins (367,395 pairs over 837,931 short strings) and never joins two that the fix keeps apart.
  • How likely. Rare: it needs the custom chain and text that spells AU with two characters. How often that spelling occurs in real text was not measured.
  • Scale. One word reproduces it; assertions on and off behave the same; the recommended fix does the same write and shift per pair as the stock code, and a timing probe found no material difference between them.
  • Reindex. A fix changes the term of every word spelled with ఒ + ౌ in affected chains, so fields analyzed before the fix keep the old terms until reindexed.

Why it is a bug, not intended

#
  • The class calls the pair AU, // (ఒ + ౌ) -> au (ఔ) (TeluguNormalizer.java:103), and folds every AU to OO; an upstream test pins that fold (ఔఐఆఈఊ → ఓఏఅఇఉ).
  • The sibling pair ఒ + ౕ is written straight as ఓ (:100).
  • No javadoc requires IndicNormalizationFilter first; the fold was added late in the introducing PR.
The full argument329 words
  • The class's own rules. The composition comment names the result AU (TeluguNormalizer.java:103), under the heading // composed oo or au -> oo or au (:96); IndicNormalizer has the same mapping for Telugu (IndicNormalizer.java:143-144). The AU -> OO fold is unconditional (:59-62), and TestTeluguNormalizer.testVowels pins it with the filter alone (check("ఔఐఆఈఊ", "ఓఏఅఇఉ"), :35-40).
  • The sibling composition. ఒ + ౕ is written as ఓ (TeluguNormalizer.java:98-101), and the filter alone gives ఓ for it (probe). TestTeluguAnalyzer.testBasics names the pair: // two ways to write oo letter. checkOneTerm(a, "ఒౕనమాల", "ఓనమాల") (:33-34, and through normalize() at :59); it runs the full TeluguAnalyzer, where IndicNormalizationFilter already joins ఒ + ౕ (IndicNormalizer.java:145-146), so it does not by itself pin the Telugu filter's branch. In the filter alone AU also has two ways, and only one reaches ఓ.
  • No prerequisite documented. The filter "applies TeluguNormalizer to normalize the orthography" (TeluguNormalizationFilter.java:27), and the factory javadoc shows it after the standard tokenizer alone (TeluguNormalizationFilterFactory.java:26-32). If Indic normalization always ran first, the class's own ఒ + ౌ branch would be dead code.
  • Tests. No upstream test has ఒ followed by ౌ; the 16 upstream Telugu tests pass with either fix.
  • History. Both rules arrived in 544dbbea468 (LUCENE-10083, PR #275, 2021-09-02). Inside the PR, the composition to ఔ was in the first commit (c143ef618e, 2021-08-13); the AU -> OO fold came with 6c0c09933f "added long to short vowel conversion" (2021-09-01), which also changed the result of the ె + ౖ composition but left the AU one writing ఔ. The only review was an approval. That this was an oversight is an inference from the commit order; no record says so.
  • What is not claimed. Lucene documents no idempotence rule for its language normalizers, and the class promises to remove only "some differences in spelling variations" (TeluguNormalizer.java:24). The case rests on the class's own rules.
The devil's-advocate check238 words

The strongest "intended" case (the devil's-advocate verifier and the intended-lens review by another model family, rated weak to moderate): Lucene's language normalizers are one-pass, best-effort rewrites with no idempotence promise, and an upstream Sorani test pins an output that a second pass would change (TestSoraniNormalizationFilter.testH, ھ → ه); the comment at :103 literally says the pair becomes "au (ఔ)", which the code does; ఒ + ౌ is not a Unicode canonical equivalent; and the stock TeluguAnalyzer runs IndicNormalizationFilter first and gives one term.

Why it fails: in the Sorani case the class's javadoc names two different letters: ھ (06BE) is the joining form of 'h' and becomes ه (0647), while a word-final ه is a form of the vowel 'e' and becomes ە (06D5) (SoraniNormalizer.java:29-30), so one pass keeps apart what that javadoc describes as different letters. Here the class itself says both spellings are the letter AU; the same method folds AU to OO without condition and an upstream test pins it; the sibling compositions write their final forms; the fold was added later in the same PR without updating the composition; and the filter and factory are public and documented without an Indic prerequisite. Verdict: a defect (adjudication: confirmed, high). What the counter-case gets right: the reach is narrow and the impact low, so the report should frame it as making the class's own rules agree, not as a relevance argument.

How it was found

#

A bounded-exhaustive check of the stock Telugu filter against its own unconditional rules (no character such a rule maps away, such as ఔ, may survive) found 6,286 violations over 837,931 short strings: 2,760 are this bug (ఔ survives exactly where the input has the pair ఒౌ), the rest are related side cases.

The method in full199 words

Method: bounded-exhaustive translation validation on the stock main jars (the study's "semi-formal" tier). A hunt unit, "script normalizers against their documented rules", 2026-10-27.

  • A closure oracle (no character or pair that an unconditional rule rewrites, deletes or joins may survive: the long vowels and long vowel signs, candrabindu, visarga, the zero-width joiners, and the two-character spellings the class joins) ran over all 837,931 strings of length 0 to 4 on a 30-character Telugu alphabet: 6,286 violations. A recount with the same oracle splits them: 2,962 have ఒ and ౌ in the input (2,760 with the adjacent pair, 202 with a visarga or zero-width (non-)joiner between the two); the other 3,324 are side cases (3,138 leave ె + ౖ unjoined, for example U+0C47 U+0C56; 186 leave ఒ + ౕ after a deleted visarga or joiner). Over the same strings, ఔ survives in exactly the 2,760 inputs with the adjacent pair.
  • A residual run that excludes inputs with ఒ, ె or ే (ే folds to ె) found 0, which isolates every violation to the compositions that start at ఒ or ె.
  • Then an AI finder wrote the public-API JUnit, and independent AI tools reproduced, reviewed and judged it (see the checks).

LFV-669, snapshot of 2026-10-29

Registry title
TeluguNormalizer composes ఒ + ౌ (U+0C12 LETTER O + U+0C4C VOWEL SIGN AU) into AU (U+0C14) but never applies its own AU -> OO fold to the result, so in a chain without IndicNormalizationFilter in front the two spellings of AU normalize to different terms
Area
analysis-common / Telugu normalizer (TeluguNormalizer.normalize; TeluguNormalizationFilter and the 'teluguNormalization' factory)
Priority
Low, rank 426: TeluguNormalizationFilter folds the two spellings of AU to different terms, which hurts relevance only, and it needs a chain without IndicNormalizationFilter plus a rare non-canonical spelling while the stock TeluguAnalyzer is unaffected, so it joins the rare script-specific normalization rows right after the kuromoji siblings LFV-605 and LFV-607.
Impact class
minor
Impact note
Relevance quality only, with no error: applications that run TeluguNormalizationFilter or the 'teluguNormalization' SPI factory without IndicNormalizationFilter in front of it (the factory javadoc's own example is StandardTokenizer + teluguNormalization) index and query a word whose AU is spelled with the two characters ఒ + ౌ (U+0C12 U+0C4C) as a different term from the same word spelled with precomposed ఔ (U+0C14), so the two spellings do not match each other, at index time and through Analyzer.normalize (prefix, wildcard and fuzzy terms); the stock TeluguAnalyzer is unaffected from 9.10.0 on (its normalize() path was affected in 8.10.0-9.9.x), no scale is needed, -ea and -da behave the same, and because a fix changes indexed terms, affected fields need reindexing after it.
Summary
You analyze Telugu text with TeluguNormalizationFilter (or the 'teluguNormalization' factory) without IndicNormalizationFilter in front of it, as in the factory javadoc example. The normalizer folds the letter AU (ఔ, U+0C14) to OO (ఓ, U+0C13), a rule the upstream test pins, and it also recognizes the two-character spelling ఒ + ౌ (U+0C12 U+0C4C) as AU, so both spellings of a word such as ఔషధం ('medicine') should give the same term. Instead the composition writes AU at a position that the single left-to-right pass never visits again, so ఒౌషధం keeps AU (term ఔషధం) while ఔషధం becomes ఓషధం, and the two spellings silently stop matching each other.
