LRUQueryCache's MinSegmentSizePredicate overflows maxDoc * 2, so segments of 2^30+ docs are never cached

LRUQueryCache's default rule for which segments to cache doubles the segment's document count in int arithmetic, which overflows from 2^30 (1,073,741,824) documents on, so such a segment is never cached, however large the cache. Results stay correct; only the caching is lost, and the cache statistics do not show it.

The finding in 30 seconds

#

Background: how the query cache picks segments

#
  1. LRUQueryCache remembers, per segment, which documents a filter query matched, so repeating the query on that segment is a lookup instead of a search.
  2. Caching costs memory, so it decides per segment. It skips the whole index if five bit sets of its size would not fit its share of the RAM budget, and it skips segments that are small compared with the others.
  3. With new LRUQueryCache(maxSize, maxRamBytesUsed) the second rule is MinSegmentSizePredicate(10000): cache a segment with at least 10,000 documents and more than half the average number of documents per segment.

The finding, step by step

#
  1. Put 1,073,741,824 (2^30) documents in one segment, for example with forceMerge(1) or IndexWriter.addIndexes, and enable new LRUQueryCache(100, 64 GiB) with a caching policy that caches every query.
  2. You expect the segment to be cached: it has more than 10,000 documents, and as the only segment it is the average, more than the required half of it. The second search should be a cache hit.
  3. Instead the check computes maxDoc * 2 as an int: 1,073,741,824 x 2 = 2,147,483,648 does not fit (the maximum is 2,147,483,647), wraps to -2,147,483,648, and that is not more than 1,073,741,824. The answer is no.
  4. So the segment is never cached: after two searches cacheCount=0 hitCount=0 missCount=0. With one document fewer, 1,073,741,823, the same searches give cacheCount=1 hitCount=1. Every segment from 2^30 documents up to the 2,147,483,519 limit is affected.

Who is affected

#

Users who enable caching with new LRUQueryCache(maxSize, maxRamBytesUsed) and have one segment of 2^30 or more documents, for example after forceMerge(1) of a 1.1 billion document index. The defaults hide it: the budget must admit such an index at all, over 640 MiB on 9.6.0-10.6.0 and over 10 GiB on main.

Mechanism, terms and numbers511 words

LRUQueryCache(int maxSize, long maxRamBytesUsed) installs MinSegmentSizePredicate(10000) as its rule for which segments to cache. Its javadoc says items are cached on leaves that have more than 10k documents and more than half of the average documents per leaf, which "should guarantee that all leaves from the upper TieredMergePolicy tier will be cached". The predicate checks "more than half of the average" as return maxDoc * 2 > averageTotalDocs; with maxDoc an int. For every segment of 2^30 documents or more (a real segment holds at most IndexWriter.MAX_DOCS = 2,147,483,519) the product is negative, so the comparison is false whatever the average, and the segment is never cached, however large the cache. The rule came with #12147 (9.6.0), the fix for #12140, where the largest segments of an index were never cached; the overflow brings that symptom back for the very largest segments. Search results stay correct, and the segment is counted neither as a cache hit nor as a miss. The fix is 2L * maxDoc.

Terms

#
  • Leaf / segment: a part of the index with its own documents, numbered 0 to maxDoc() - 1. An int holds at most 2,147,483,647; IndexWriter.MAX_DOCS is 2,147,483,519.
  • leavesToCache: the Predicate<LeafReaderContext> that LRUQueryCache asks before it caches anything on a segment. The two-argument constructor uses MinSegmentSizePredicate(10000); the four- and six-argument constructors take your own.
  • RAM gate: before the predicate, the cache checks that five dense bit sets for the whole index (maxDoc / 8 bytes each) fit in the budget (on main, in a sixteenth of it, one of 16 partitions).

The bug

#
  1. MinSegmentSizePredicate.test reads the segment's maxDoc as an int, returns false below 10,000, computes averageTotalDocs = topLevel.maxDoc() / leaves.size(), and returns maxDoc * 2 > averageTotalDocs (LRUQueryCache.java:287-294 on main).
  2. For maxDoc from 2^30 on (up to MAX_DOCS for a real segment; any int up to 2^31 - 1 behaves the same) the product 2 * maxDoc is at least 2^31 and wraps to 2 * maxDoc - 2^32, between -2,147,483,648 and -2. The average is never negative, so the answer is always false, whatever the other segments are. It never errs the other way.
  3. CachingWrapperWeight.shouldCache is the RAM gate && this predicate (:804-808). scorerSupplier and count check it (:823, :910) and, when it is false, run the query uncached, before the cache lookup and before the caching policy is asked (:834, :838). No policy can override it, and since no lookup happens, no miss is counted.

The numbers

#

One real segment of exactly 1,073,741,824 documents, built through the public API, LRUQueryCache(100, 64 GiB), an always-cache policy, ConstantScoreQuery(TermQuery) searched twice: 256 of 256 hits (correct) and cacheCount=0 hitCount=0 missCount=0, on main and on 10.5.2, with assertions on and off. With 1,073,741,823 documents (one of the 256 copies has one document fewer): cacheCount=1 hitCount=1 missCount=1. With 2L * maxDoc: cacheCount=1 hitCount=1. Driven directly, the predicate accepts a single segment of 10,000, 2^29 and 2^30 - 1 documents and rejects 2^30, 2^30 + 1, 2,000,000,000 and 2,147,483,519.

Exposure and likelihood245 words
  • Who is hit. Users who enable query caching with LRUQueryCache(int, long), the form in the class javadoc example and in MIGRATE.md ("To enable caching back ..."), and have a segment of 2^30 or more documents. Every otherwise cache-eligible query runs uncached on that segment, on every search: cached filters never help on exactly the biggest, most expensive segment.
  • Default vs opt-in. Main has no default query cache (GITHUB#14187). In 9.6.0-10.6.0 the default is LRUQueryCache(1000, min(32 MiB, heap / 20)), whose RAM gate already refuses any index above 53,687,095 documents. So it takes an opt-in cache with a large budget: for an index of exactly 2^30 documents more than 671,088,640 bytes (640 MiB) on 9.6.0-10.6.0, and at least 10,737,418,256 bytes (just over 10 GiB) on main, where each of 16 partitions gets a sixteenth. Bigger indexes need more.
  • How such a segment arises. forceMerge(1) of a large index (maxNumSegments wins over the merge policy's size cap), addIndexes(CodecReader...) (one merged segment by default), a raised setMaxMergedSegmentMB, or a custom merge policy. The default 5 GiB cap is in bytes, so it only stops this for documents averaging more than about 5 bytes on disk. Lucene's own @Monster test TestIndexWriterMaxDocs.testExactlyAtTrueLimit force-merges MAX_DOCS documents into one segment.
  • Visibility. None: no exception, and the segment adds nothing to the hit, miss and cache counts (they count the whole cache; in the fresh-cache runs all three stay 0).
  • Not affected. Caches built with their own leavesToCache predicate.

Minimal repro

#

One JUnit test in org.apache.lucene.search, because the predicate is package-private (upstream TestLRUQueryCache does the same). A FilterLeafReader over a real one-document segment reports maxDoc() = 2^30; the predicate reads nothing else, so this answers like a real 2^30-document segment. The result does not depend on the seed; the test itself runs in about 0.15 s.

Expected
MinSegmentSizePredicate(10000).test(...) returns true for the only segment (2^30 documents, average 2^30).
Observed
It returns false, because 2^30 * 2 wraps to -2^31 in int; the same with assertions off.

More files, environment, full output260 words

The predicate reads only the leaf's maxDoc(), the top-level reader's maxDoc() and the number of leaves (LRUQueryCache.java:286-294). The wrapped leaf is its own top-level reader, so the average is 2^30: the smallest single-segment input that wraps. The two cache helpers return null only because FilterLeafReader requires them. The same answer was checked on a real single segment of 2^30 documents, built with IndexWriter.addIndexes(CodecReader...) of 256 copies of a 2^22-document segment and searched through LRUQueryCache(100, 64 GiB) (about 6 s and 15 MB of disk), on main and 10.5.2; that probe is evidence, not the proposed test.

As the regression test: the same test, for example as a new method in TestLRUQueryCache.

Why it looks unintended

#
  • The javadoc says the rule "should guarantee that all leaves from the upper TieredMergePolicy tier will be cached"; a lone 2^30-document segment is that tier.
  • The rule came from #12147, the fix for #12140, where the largest segments were never cached.
  • The float-ratio rule it replaced had no cutoff, and 2L * maxDoc restores caching.
The full argument198 words
  • Javadoc of LRUQueryCache(int, long) (LRUQueryCache.java:243-250): "Items will only be cached on leaves that have more than 10k documents and have more than half of the average documents per leave of the index. This should guarantee that all leaves from the upper TieredMergePolicy tier will be cached." A single 2^30-document segment meets both conditions and is the upper tier.
  • History. #12140 (type:bug, by dnhatn) reported an index of 34 segments of 5 GB that was never cached under the old 3% rule. In that thread jpountz proposed the current rule: "maybe it should even be half the average segment size to make sure it includes all segments from the upper tier?" #12147 (type:bug) implemented it; its commit message: "This change adjusts the cache policy to ensure that all segments in the max tier to be cached." Nothing there excludes very large segments.
  • The old rule had no cutoff. 9.5.0 compared (float) maxDoc / topLevelMaxDoc with .03f, which cannot overflow.
  • No documented limit. Nothing in the class, MIGRATE.md or CHANGES.txt mentions a size cap other than the separate RAM gate.
  • No test covers it. Upstream TestLRUQueryCache.testMinSegmentSizePredicate uses segments of at most 55 documents.
The devil's-advocate check228 words

The strongest case for "intended" (a reviewer from another model family, OpenAI GPT-5.6, rated it "moderate"): LRUQueryCache is @lucene.experimental; caching is an optional optimisation, off by default on main; "will only be cached on leaves that ..." is a necessary condition, not a promise that every such leaf is cached, and other gates can reject entries too; and a maintainer could accept extra misses at this scale, "especially for unusually large cache entries". A related practical objection: a dense cached entry for a 2^30-document segment is about 128 MiB and can evict many smaller entries.

Why it fails: the javadoc's next sentence states the design goal ("This should guarantee that all leaves from the upper ... tier will be cached"), and the issue and PR it came from say the same; every stated condition is met here, and the predicate says no only because of the wrap; @lucene.experimental allows the API to change, not the arithmetic to be wrong; the scale is legal and exercised by Lucene's own tests; and entry size already has its own policy, the RAM gate, which admits the index only when its share of the budget has room for five worst-case entries, so the predicate is not the place that limits it. These arguments limit severity, not validity. The same reviewer noted that "the exact signed-overflow boundary has no plausible policy rationale".

Suggested fix

#

Recommended Widen the product to long: 2L * maxDoc

Widen the product to long: return 2L * maxDoc > averageTotalDocs; (one line, no API or format change). With it the repro passes with assertions on and off, a real 2^30-document segment is cached again, and the core test classes that use LRUQueryCache pass.

-      return maxDoc * 2 > averageTotalDocs;
+      return 2L * maxDoc > averageTotalDocs;

Trade-offs

No correctness, API or format trade-off found: the same answer as today for every segment below 2^30 documents and "more than half of the average" for every legal size; one long multiply per segment per caching decision. By design it starts caching on such segments: a dense entry for 2^30 documents is about 128 MiB and can evict other entries, within the existing RAM, entry-count and LRU limits.

Halve the average instead: maxDoc > averageTotalDocs / 2 (validated by the checks)

#

Stays in int and cannot overflow.

-      return maxDoc * 2 > averageTotalDocs;
+      return maxDoc > averageTotalDocs / 2;

Trade-offs

For non-negative integers 2 * m > a holds exactly when m > floor(a / 2), so it gives the same answers as the long product for every input. Slightly less direct to read as "more than half of the average".

What the checks validated

Gradle in the same scratch worktree: the repro and TestLRUQueryCache pass with assertions on (41 tests, 0 failures, 3 skipped as @AwaitsFix). Assertions off, the other suites and the static checks were not run for this option.

Downstream note

#

Only the two-argument constructor's default rule is affected: products that pass their own leavesToCache predicate to LRUQueryCache keep their own behaviour.

How it was found

#

Non-formal: during a formal-verification study of Lucene, a reviewer reading LRUQueryCache while checking other findings noticed the int product. Follow-up tests drove the predicate with reported sizes around 2^30 and end to end through the cache; later a real 2^30-document segment, built through the public API, confirmed it.

The method in full111 words

Method: non-formal (code reading, then executed tests). In the 2026-10-22 study, a verifier saw the int multiplication as a side observation. The study's follow-up wrote three tests: the package-private predicate driven directly with a FilterLeafReader that reports a large maxDoc (single leaf, and a 2^30-document leaf next to a 20,000-document one), and an end-to-end search through LRUQueryCache(100, 64 GB) with an always-cache policy. All three fail with assertions on and off. The hunt then cut it to one test, re-ran it on current main and on release jars, and a tie-breaker built a real single segment of exactly 2^30 documents with IndexWriter.addIndexes to rule out an artefact of the reader wrapper.
