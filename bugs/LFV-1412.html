vectorValue(-1) on the default codec's vector values returns an all-zero vector instead of throwing

On the default codec, FloatVectorValues.vectorValue(-1) returns an all-zero vector instead of the documented IndexOutOfBoundsException: index one vector [1.0, 2.0], ask a fresh values object for ordinal -1, and you get [0.0, 0.0] with no error. Every release since 10.0.0 has it.

The finding in 30 seconds

#

The default codec reads each vector from the index file into one reused array and remembers which ordinal the array holds. The "nothing read yet" value of that memory, -1, is also accepted as an ordinal.

Background

#
  1. In a segment, each document's vector has an ordinal from 0 to size() - 1; FloatVectorValues.vectorValue(ord) returns the vector for an ordinal (random access).
  2. values.iterator() walks the documents; its index() is the current document's ordinal, and it is -1 until nextDoc() or advance() is called.
  3. The default codec's implementation reads a vector into one reused array and keeps the ordinal it holds in lastOrd, so asking for the same ordinal twice reads only once.

The finding, step by step

#
  1. Index one document with the 2-dim vector [1.0, 2.0] using the default codec, and get the field's FloatVectorValues from the reader: size() is 1 and vectorValue(0) returns [1.0, 2.0].
  2. Call vectorValue(-1), for example by mistake as values.vectorValue(iterator.index()) before nextDoc(), while index() is still -1.
  3. You expect IndexOutOfBoundsException: the javadoc says the ordinal "must be in [0, size() - 1], otherwise IndexOutOfBoundsException is thrown".
  4. You get [0.0, 0.0] and no error, with assertions on or off. A new values object uses lastOrd = -1 to mean "nothing read yet", and vectorValue tests lastOrd == targetOrd before anything else, so -1 matches and the never-filled buffer comes back.
  5. Byte vectors behave the same way. vectorValue(1), one past the end, already fails loudly with EOFException; only negative ordinals are silent.

Who is affected

#

Only code that reads vectors by ordinal through this experimental API and passes a negative ordinal by its own mistake, typically an unpositioned iterator's index(). It gets a zero vector instead of an error, so its bug goes unnoticed. Default codec, every directory, assertions on or off; correct callers and Lucene's own code are unaffected.

Mechanism, terms and numbers512 words

FloatVectorValues.vectorValue(int ord) and ByteVectorValues.vectorValue(int ord) document that the ordinal "must be in [0, size() - 1], otherwise IndexOutOfBoundsException is thrown". The default codec's off-heap implementations (lucene95 OffHeapFloatVectorValues, OffHeapByteVectorValues, and on main OffHeapFloat16VectorValues) cache the last vector they read and start with lastOrd = -1 to mean "nothing read yet". vectorValue checks the cache first and has no range check, so on a freshly obtained or copied values object vectorValue(-1) matches the marker and returns the value buffer that was never filled: an all-zero vector, with no exception and no read. -1 is what DocIndexIterator.index() returns before nextDoc(), so the mistake values.vectorValue(iterator.index()) before positioning the iterator gets a plausible-looking zero vector instead of an error. Ordinals at or above size() already fail loudly with EOFException; only negative ordinals are covered here. Every release from 10.0.0 through 10.6.0 and main; Low priority, because only a caller's own ordinal bug reaches it.

The bug (main f794ff5a505c)

#
  1. The marker. OffHeapFloatVectorValues.java:41: protected int lastOrd = -1;; :59: value = new float[dimension]; (all zeros).
  2. The cache test comes first. vectorValue (:78-86):
public float[] vectorValue(int targetOrd) throws IOException {
  if (lastOrd == targetOrd) {
    return value;
  }
  slice.seek((long) targetOrd * byteSize);
  slice.readFloats(value, 0, value.length);
  lastOrd = targetOrd;
  return value;
}

There is no range check. For targetOrd = -1 on an instance that has not read anything yet, the first if returns the untouched array.

  1. Every new values object starts at -1. Lucene99FlatVectorsReader.getFloatVectorValues (:298-322) and getByteVectorValues (:325-335) build a new instance through OffHeap*VectorValues.load(...) on every call, and copy() (OffHeapFloatVectorValues.java:150-153) builds another.
  2. Where -1 comes from. KnnVectorValues.createDenseIterator (KnnVectorValues.java:148-161): doc starts at -1 and index() returns doc.
  3. Siblings. OffHeapByteVectorValues.java:41, :76-82 (if (lastOrd != targetOrd) readValue(...), so -1 skips the read) and OffHeapFloat16VectorValues.java:42, :79-87 (main only, the float pattern with short[]; checked by reading). The same classes' prefetch(ord, count) does check ord < 0 || ord >= size (:90, :86, :91).

What the call returns (evidence probe on the repro's input)

#

index() before nextDoc() = -1; vectorValue(index()) = [0.0, 0.0]; a fresh object's vectorValue(-1) = [0.0, 0.0], vectorValue(0) = [1.0, 2.0], vectorValue(1) throws EOFException. A byte field gives [0, 0, 0, 0] for -1 (a verifier's 4-byte test).

Not part of this report

#

Other negative ordinals, or -1 after another ordinal was read, reach slice.seek with a negative position. A scratch probe saw MMapDirectory throw "seek negative position" while the NIOFS and ByteBuffers directories returned bytes from before the field's slice; that has a different fix site and was not pursued. The lucene104 scalar-quantized off-heap classes use the same lastOrd = -1 cache (read, not run). A field without vectors in the segment gets an empty values object whose vectorValue throws UnsupportedOperationException (OffHeapFloatVectorValues.java:318-319), so the claim is about fields that have vectors. Sparse fields: the sparse subclass inherits the same vectorValue, and its iterator's index() (IndexedDISI.index()) also starts at -1 (IndexedDISI.java:406, :437-439; read, not run).

Why it looks unintended

#
  • The javadoc defines this input: an ordinal outside [0, size() - 1] throws IndexOutOfBoundsException (public API since 10.0.0).
  • The same classes' prefetch(ord, count) rejects ord < 0, and the on-heap FloatVectorValues.fromFloats throws IndexOutOfBoundsException for -1.
  • Out-of-range ordinals otherwise fail loudly (TestField expects an IOException one past the end); a silent zero vector is neither.
The full argument230 words
  • The contract. FloatVectorValues.java:36-37, ByteVectorValues.java:36-37, Float16VectorValues.java:36-37: "Return the vector value for the given vector ordinal which must be in [0, size() - 1], otherwise IndexOutOfBoundsException is thrown." Added by #13779 (6053e1e3137, msokolov, 2024-09-28, first released in 10.0.0), which made vectorValue(int) public and added DocIndexIterator.index().
  • Range checks next door. prefetch(ord, count) returns false for ord < 0 || ord >= size in all three classes (added by #16705).
  • The on-heap factory throws. FloatVectorValues.fromFloats returns vectors.get(targetOrd) (FloatVectorValues.java:121-122), which throws IndexOutOfBoundsException for -1; a cross-model review and the probe behind the diagram ran this control.
  • Tested behaviour is a loud failure. TestField.testKnnVectorField, written in #13779 too, expects IOException for vectorValue(1) on one-vector fields (TestField.java:724, :733).
  • History. The -1 marker came from #12529 (c26b0180bd4, jimczi, 2023, 9.8.0), when the method was only on the HNSW random-access interface RandomAccessVectorValues (@lucene.experimental, reached by casting), whose javadoc was a precondition only ("@param targetOrd a valid ordinal, >= 0 and < size()"). #13779 put the method on the vector values classes with the exception sentence and left the body unchanged (10.0 MIGRATE.md: "Random access works as before, but does not require casting to RandomAccessVectorValues"). The recorded comment search of #13779 found no mention of bounds, range checks or lastOrd, and the prior-art notes on #12529 record no discussion of out-of-range ordinals.
The devil's-advocate check231 words

Strongest case for "not a bug": vectorValue is a hot-path accessor of an @lucene.experimental class, and Lucene often leaves out-of-range input undefined there (Bits.get: "negative or out of bounds values is undefined by this interface, just don't do it!"). The exception sentence came with a refactor that promised no functional change (issue #13778), and its exception type was never implemented for the upper side: TestField pins IOException, and a full Objects.checkIndex fix breaks that test (executed by the intended-behaviour verifier). No in-tree implementation enforces the sentence deliberately: MemoryIndex's float and byte values return null for any ord != 0 (MemoryIndex.java:2379-2385, :2507-2513), SlowCompositeCodecReaderWrapper only asserts ord >= 0 && ord < size (:913, :1013, :1062), and the lucene104 OffHeapScalarQuantized* values share the lastOrd = -1 cache. Only a caller's own bug reaches it, so a maintainer may well answer "fix the javadoc" (option (d)).

Why it still fails for negative ordinals: the public javadoc defines the outcome for exactly this input; the default codec's result is silent, plausible-looking data with assertions off, not a loud failure of the wrong type, and unlike a null it does not fail when used; -1 is what a common ordering mistake produces; and a one-compare fix keeps TestField green. A doc-only fix would have to document that a negative ordinal may return a zero vector.

Suggested fix

#

Recommended (a) Reject negative ordinals before the cache test (recommended, validated)

Reject negative ordinals before the cache test: if (targetOrd < 0) throw new IndexOutOfBoundsException(...) at the top of vectorValue in the three lucene95 off-heap classes (+4 lines each). The repro then passes with assertions on and off, 18 vector, codec and kNN suites (619 tests) and the format check pass, and TestField stays green.

  public float[] vectorValue(int targetOrd) throws IOException {
    if (targetOrd < 0) {
      // lastOrd starts at -1 ("nothing read yet"), so reject negatives before the cache test
      throw new IndexOutOfBoundsException("ordinal must be >= 0, got " + targetOrd);
    }
    if (lastOrd == targetOrd) {
      return value;
    }

(a) Reject negative ordinals before the cache test (recommended, validated)

#

The diff: +4 lines at the top of vectorValue in OffHeapFloatVectorValues, OffHeapByteVectorValues and OffHeapFloat16VectorValues (same code in each).

  public float[] vectorValue(int targetOrd) throws IOException {
    if (targetOrd < 0) {
      // lastOrd starts at -1 ("nothing read yet"), so reject negatives before the cache test
      throw new IndexOutOfBoundsException("ordinal must be >= 0, got " + targetOrd);
    }
    if (lastOrd == targetOrd) {
      return value;

Trade-offs

  • One compare on the hot path that is always false for correct callers.
  • Leaves ord >= size() on its current loud EOFException, so TestField keeps passing; the javadoc's exception type for that side stays inaccurate (see (d)).
  • Also turns every other negative ordinal (which today reaches slice.seek with a negative position) into the documented exception.

For example lastOrd = Integer.MIN_VALUE, together with the check of (a).

Downstream note

#

Downstream code that reads stored vectors by ordinal (for example a custom rescorer or exporter on the default codec) cannot rely on an exception to catch a negative ordinal: it silently gets a zero vector.

How it was found

#

A proof-obligation audit (semi-formal) of the vectorValue contract of the default codec's off-heap vector values: for each documented outcome it asked whether the code guarantees it, found the cache test before any range check, and a one-test JUnit repro on main witnessed the gap.

The method in full106 words

Semi-formal method: the audit listed what FloatVectorValues / ByteVectorValues.vectorValue promise (an ordinal in [0, size() - 1], otherwise IndexOutOfBoundsException) and checked each obligation against OffHeapFloatVectorValues and its siblings. The obligation for a negative ordinal fails on a fresh instance, because lastOrd = -1 is tested before anything else. A one-test JUnit on main witnessed it with assertions on and off, and a scratch probe checked the byte field, copy(), index() before nextDoc() and three directories.

An intended-behaviour verifier then showed that TestField pins IOException one past the end, so the adjudication narrowed the report to negative ordinals and the fix to a negative-only check.

Hits only application or library code that calls the @lucene.experimental FloatVectorValues/ByteVectorValues.vectorValue(int) on the default codec's vector values with a negative ordinal by its own mistake (typically values.vectorValue(iterator.index()) before nextDoc() or advance(), where index() is -1): instead of the documented IndexOutOfBoundsException it silently gets an all-zero vector, so its bug goes unnoticed, with -ea and -da and on every directory, in every release from 10.0.0 through 10.6.0 and on main; correct callers and every in-tree caller are unaffected, and ordinals >= size() already fail loudly (EOFException, an IOException).
Summary
You open a reader on an index whose vector field was written by the default codec and, because of a bug in your own code, ask the field's FloatVectorValues for vectorValue(-1), for example by calling values.vectorValue(iterator.index()) before moving the iterator to a document. The javadoc says an ordinal outside [0, size() - 1] makes the call throw IndexOutOfBoundsException, so you expect an error. Instead you get [0.0, 0.0, 0.0, 0.0] with no error and no read, because a new values object uses lastOrd = -1 to mean 'nothing read yet' and vectorValue(-1) matches that marker and returns the never-filled buffer; the byte vector values behave the same way.
