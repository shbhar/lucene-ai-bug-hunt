With an index sort, a failure while creating the sorted stored-fields or term-vectors writer during flush leaves the temporary files open after IndexWriter closes itself

With an index sort, if creating the sorted stored-fields or term-vectors file fails during a flush (for example on too many open files), IndexWriter closes itself as designed but leaves the 2 temporary files it was copying from open. On the default MMapDirectory they stay mapped even after Directory.close().

The finding in 30 seconds

#

The bug sits in the copy step of a sorted flush: the reader on the temporary files is opened before the code that guarantees it gets closed.

Background: how a sorted flush writes stored fields

#
  1. IndexWriterConfig.setIndexSort(...) makes every new segment store its documents in sort order, for example by timestamp. Documents arrive in any order, so their stored fields (and term vectors) cannot be written in final order as they come.
  2. Lucene writes them in arrival order to temporary files such as _0.fdt__1.tmp and _0.fdx__4.tmp. At flush it opens a reader on those files, creates the segment's real stored-fields files (.fdm, .fdt, .fdx), copies every document across in sorted order, closes both and deletes the temporary files.
  3. A flush that fails with an exception is tragic by design: IndexWriter drops the unflushed documents and closes itself, and the last commit stays as it was.

The finding, step by step

#
  1. Set an index sort on a LONG field, add 1 document with a stored field and call commit(), while creating the segment's .fdm file fails once with an IOException, as it would when the process has run out of file descriptors.
  2. You expect commit() to throw and IndexWriter to close itself, as after any failed flush, with 0 files left open: IndexWriter.close() "Closes all open resources".
  3. Instead 2 files stay open, the temporary _0.fdt__1.tmp and _0.fdx__4.tmp. The flush opened a reader on them to copy the document into sorted order, then failed to create the final writer one line before the try whose finally would close that reader.
  4. Nothing can close them now: the reader was a local variable, and abort() only deletes the files by name. On MMapDirectory the 2 deleted files stay mapped after IndexWriter.close(), Directory.close() and System.gc(), so their disk space is not freed.
  5. Term vectors (.tvd/.tvx) fail the same way. Every release from 6.5.0 to 10.6.0 and main is affected; creating the writer inside the try fixes it.

Who is affected

#

Applications that set an index sort, when creating or opening a file fails during a sorted flush (too many open files, a permission, quota or inode limit, a read-only remount, a throwing Directory or codec). Each failure leaks 2 inputs on deleted files (1 per consumer on 6.5.0 to 7.7.3); no data is lost and the last commit stays intact.

Mechanism, terms and numbers564 words

With IndexWriterConfig#setIndexSort, a segment's stored fields (and term vectors) are first written in arrival order to temporary files. At flush, SortingStoredFieldsConsumer.flush opens a reader on those files, then creates the final sorted writer, and only then enters the try whose finally closes both. If creating the final writer throws, for example because the .fdm file cannot be created when the process has too many open files, the finally never runs and the reader, a local variable, is lost. The flush failure is aborting, so IndexWriter closes itself as designed and abort() deletes the temporary files by name, but nothing closes the 2 inputs on them. SortingTermVectorsConsumer.flush has the same order. A one-document test shows 2 handles still open after close(); on MMapDirectory, the 64-bit default, the 2 deleted files stay mapped after Directory.close() and System.gc(), so their disk space stays allocated. The order dates from LUCENE-7579 (2016): every release from 6.5.0 to 10.6.0 and main is affected. Moving the writer creation into the existing try fixes it.

Terms

#
  • Index sort: IndexWriterConfig#setIndexSort, an opt-in setting that keeps the documents of every segment in sort order.
  • Temporary files: while documents are buffered, SortingStoredFieldsConsumer writes their stored fields uncompressed to temporary files (_0.fdt__1.tmp, _0.fdx__4.tmp) through a TrackingTmpOutputDirectoryWrapper; SortingTermVectorsConsumer does the same for term vectors (.tvd/.tvx).
  • Tragic close: any exception during a flush is aborting; the in-memory segment is discarded and IndexWriter closes itself.

The bug

#
  1. With an index sort the indexing chain uses the two sorting consumers (IndexingChain.java:152, :154).
  2. At flush (IndexingChain.java:345), SortingStoredFieldsConsumer.flush opens the temporary reader (SortingStoredFieldsConsumer.java:111-113; it keeps 2 inputs open), then creates the final writer (:116-117), then enters the try (:118) whose finally runs IOUtils.close(reader, sortWriter) (:136) and deletes the temporary files (:137).
  3. The final writer's constructor creates .fdm and .fdt, two temporary outputs of FieldsIndexWriter, and writes codec headers (Lucene90CompressingStoredFieldsWriter.java:129-162). All of that is inside its own try: when any of it throws, the constructor closes its own outputs (:160) and rethrows; the statements before that block (such as compressionMode.newCompressor(), :120) create no file. The exception leaves flush before the try, so the finally never runs and the reader local is dropped.
  4. DocumentsWriterPerThread.flush treats the exception as aborting (DocumentsWriterPerThread.java:585-589) and fires the tragic event (:602): IndexWriter closes itself. SortingStoredFieldsConsumer.abort (:142-151) deletes the temporary files by name; it has no reference to the reader. The 2 inputs now point at deleted files that nothing will close.
  5. SortingTermVectorsConsumer.flush has the same order: reader :62-64, writer :68-71, try :72, finally :80; abort :97-104.
  6. On MMapDirectory the inputs are mapped in a shared arena (MMapDirectory.java:329, :402-429; RefCountedSharedArena.java:74) that only closing every input releases, so garbage collection and Directory.close() leave the mapping in place.

The numbers

#

One document, the default codec, createOutput of _0.fdm failing once: commit() throws, close(), and MockDirectoryWrapper counts 2 open files, {_0.fdx__4.tmp=1, _0.fdt__1.tmp=1}, the unclosed input opened at SortingStoredFieldsConsumer.flush(SortingStoredFieldsConsumer.java:112). On a real MMapDirectory both deleted files are still listed in /proc/self/maps after the tragic close, after 5 calls to System.gc() and after Directory.close(); on NIOFSDirectory, /proc/self/fd lists both until a System.gc() releases them.

Exposure and likelihood451 words
  • Who is exposed. Applications that set IndexWriterConfig#setIndexSort (opt-in). No scale is needed: one document is enough. Since 8.7.0 every sorted flush opens the temporary stored-fields reader (by code reading, not executed: before the flush StoredFieldsConsumer.finish, StoredFieldsConsumer.java:97-102, called at IndexingChain.java:344, starts every document not yet started, and starting a document creates the temporary writer, :55-57, even when no document has a stored field; the hasStoredFields check at SortingStoredFieldsConsumer.java:129 only skips the per-document reads); the term-vectors reader only when term vectors exist.
  • What it takes. A failure to create or open a file while the flush constructs the final stored-fields or term-vectors writer: too many open files (EMFILE/ENFILE), a permission, quota or inode limit, a read-only remount, or a Directory or codec that throws.
  • Not disk full, normally. On an FSDirectory the constructor's header writes go into an 8 KiB buffer (FSDirectory.java:378, :400; OutputStreamIndexOutput.java:48), so an out-of-space error usually surfaces later, inside the try, where the reader is closed. Running out of inodes or quota can fail the file creation itself (listed above).
  • How often, given such failures. Under upstream's own untargeted open-failure model (MockDirectoryWrapper#setRandomIOExceptionRateOnOpen(0.1) during commit, 300 rounds per arm), 28 of 300 index-sorted rounds leaked (23 the .fdt/.fdx pair, 5 the .tvd/.tvx pair), 0 of 300 unsorted rounds and 0 of 300 with the fix. (The history step's version-portable port, a different harness, counted 56 of 300 on the same commit; the two counts are not comparable.) The failure itself is rare, and nobody has reported the leak since 2017.
  • What happens. Per failed flush, 2 inputs on deleted temporary files stay open (on main and from 8.6.3 on; on 6.5.0 to 7.7.3 one per consumer). On MMapDirectory (the 64-bit default) they are 2 mappings that survive IndexWriter.close(), Directory.close() and System.gc(); while they live, the disk space of those files stays allocated: the uncompressed stored fields (or term vectors) of the one segment that failed to flush. On NIOFSDirectory they are 2 file descriptors, released by System.gc() in one run. The application cannot release them: no API reaches the reader. Process exit does; whether anything earlier does was not tested.
  • What does not happen. No hang, no wrong results, no corruption. The failed segment is discarded by the tragic close, as designed; the last commit stays intact and a new IndexWriter opens it normally. A later writer on the same MMapDirectory does not keep later segments' files mapped (its segments were _1 to _3; MMapDirectory groups mappings by segment name, so whether a later segment again named _0 would stay mapped was not tested). Windows, where open files cannot be deleted, was not tested.

Why it looks unintended

#
  • close() is documented to close "all open resources", and the flush's own finally already closes the reader: only the writer's creation sits outside the try.
  • The review that added this code added abort() to clean up after exceptions here.
  • Lucene's tests fail on files left open after a tragic close; upstream fixed the same create-before-try pattern in #14394 and d16e25518ba.
The full argument371 words
  • The contract. IndexWriter.close(): "Closes all open resources and releases the write lock." (IndexWriter.java:1342). The class javadoc: "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself" (:162-165); nothing says it may then leave files open. This states the intent, not a promise for the tragic path: the writer has already closed itself (IndexWriter.java:6094, :6098-6105), and a later close() does nothing (shutdown and shouldClose, :1319, :1374-1393).
  • The code's own intent. The finally at SortingStoredFieldsConsumer.java:136 closes the reader and the writer together on every path through the try; only the writer's creation was left one statement outside. No comment, commit or PR explains the order, and the fix keeps it.
  • Cleanup after exceptions was designed here. In the LUCENE-7579 review (#8630), mikemccand asked whether an IOException "during the renaming that SortingStoredFieldsConsumer.flush does" (a rename step of that time) could "leave undeleted files"; jimczi added abort() to both consumers in answer. IndexingChain.abort's comment says its finalizer "will e.g. close any open files in the term vectors writer" (IndexingChain.java:531): the abort path closes the files it owns, but nothing on it owns the temporary reader, a local variable of flush. The bug is that ownership gap.
  • Lucene's tests enforce it. MockDirectoryWrapper.close() throws "cannot close: there are still N open files" with no exemption for a tragic close (MockDirectoryWrapper.java:873-887); TestIndexWriterOutOfFileDescriptors accepts a tragic close (:88) and then calls dir.close() (:166). No upstream test combines setIndexSort with failure injection: a coverage gap, consistent with CI never having caught this.
  • Upstream fixes the same pattern as a bug. Two fixes move a create or open call that sat before its try into it: #14394 (9b9fbd44339, 2025: two createTempOutput calls, declared null and assigned inside the try) and d16e25518ba (2026: "the open call was outside the relevant try-catch block"). #12739 (361f0a4524d, 2023) is the same family, not the same shape: it adds a temporary output that was missing from the failure-path close list.
  • The trigger is legal. Directory#createOutput declares IOException (Directory.java:90-92), and MockDirectoryWrapper#setRandomIOExceptionRateOnOpen is upstream's own model of running out of file descriptors.
The devil's-advocate check136 words

Argument: the flush has already failed and the writer is tragically closed, so its state afterwards is best effort; the trigger is an environmental failure in a one-statement window; and the order could be deliberate.

Why it fails: close() is documented to close all open resources, abort() was added precisely to clean up after this kind of exception, Lucene's test framework fails any test that leaves a file open after a tragic close, and every other tragic flush failure the verifiers tried released all handles (the controls, and 0 of 300 unsorted rounds). Nothing documents or explains the order. The leaked inputs are also beyond the application's reach: no API returns them, and on MMapDirectory not even Directory.close() releases them. What the argument does limit is the impact: a minor leak on a rare error path.

Suggested fix

#

Recommended A. Create the final writer inside the existing try

Create the final writer inside the existing try (declare it null first; IOUtils.close ignores nulls) in both consumers, so the finally closes the temporary reader on every path. A. Create the final writer inside the existing try (validated by the checks) (recommended)

Declare the writer as null before the try and assign it as the first statement inside, in both consumers: 10 lines added, 6 removed (formatted by google-java-format). The existing finally then runs IOUtils.close(reader, sortWriter), which ignores a null writer, and deletes the temporary files.

Trade-offs

  • Smallest change, in the same shape upstream used for #14394 (declare null, assign inside the try); the order (reader, then writer) and the finally stay as they are, so the success path is unchanged. It covers exactly the window: if super.flush or the reader's constructor throws, nothing changes.
  • IOUtils.close ignores null arguments (its javadoc: "Some of the Closeables may be null; they are ignored."), so no extra check is needed.
  • It keeps one existing quirk and extends it to the writer's creation: if closing throws in the finally, that exception replaces the one from the try body, so a failure to close the reader would now also hide the writer-creation exception. Option B would change that.

Downstream note

#

Elasticsearch's time_series and logsdb index modes set an index sort by default (read from its source, not tested), so their flushes take this code path.

How it was found

#

Semi-formal: a fault-injection harness made each distinct file-system call of short IndexWriter scripts throw one IOException in turn, checked the outcome against a model and then checked for open files. Throws inside the sorted writer's constructor were tragic, as expected, but left 2 files open; the root cause was then read from the code.

The method in full159 words

Method: semi-formal (exception-point enumeration of the real jar against a model). On 2026-10-26 a hunt unit ran short scripts of document-level IndexWriter operations (add, update, delete, batches, commits, near-real-time readers) under several configurations, one with an index sort. For every operation it enumerated each distinct MockDirectoryWrapper failure site, made it throw one IOException in turn, and classified the outcome against a model as unchanged, applied or tragic; then it checked MockDirectoryWrapper.close() for open files. In its exhaustive 2-operation runs (3 runs, about 14.4 million executions), the injections at createOutput, createTempOutput and the header writes inside the constructor of the sorted stored-fields or term-vectors writer were classified tragic, as expected, and then failed the open-file check (cannot close: there are still 2 open files: {_1.fdt__f.tmp=1, _1.fdx__m.tmp=1}). The root cause was then read from the code and a targeted JUnit written; it was later cut to the one-test repro. It could also be read as model-based randomized testing.

History

#

Present since flush-time index sorting was added (LUCENE-7579, 4ccb9fbd2bb, 2016; first released in 6.5.0), so not a regression. 6.4.2 is clean; every executed release from 6.5.0 to 10.6.0 and main leaks. Since 8.7.0 every sorted flush with stored fields or term vectors reaches it.

Versions tested12 rows

Introduced by LUCENE-7579 "Sorting on flushed segment" (#8630; contributed by jimczi, committed by mikemccand; reviewed on JIRA, no pull request): 4ccb9fbd2bb "LUCENE-7579: sort segments at flush too" on master (2016-12-20, first released in 7.0.0) and the branch_6x backport 7d96f9f7981 (2017-01-17, first released in 6.5.0). The first version of both consumers already had this order. 9 later commits to the stored-fields flush and 7 to the term-vectors flush (#13265, #15001, #15718, #16281 among them) never moved the writer creation into the try.

Scope by version: from 6.5.0 to 8.6.3 only flushes that reorder documents leak, because an already-sorted flush renamed the temporary files and returned before opening a reader; LUCENE-9510 (8.7.0) removed that shortcut, so every sorted flush with stored fields or term vectors now goes through the leaking code.

Method: release jars SHA-1-checked against Maven Central; a version-portable main() port (3 documents in reverse sort order, one targeted failure, plus 300 rounds of upstream's random open-failure model; its counts come from its own script and are not comparable with the intended-behaviour check's 28 of 300) and the JUnit repros where the test framework allows. Not fixed: upstream main 2f424fd428da (2026-10-30) and branch_11x 603af870375 have both files identical to 645d4fe14a20; branch_10_6 7e5aec4370e still creates the writer before the try (it differs only in the term-vectors checkIntegrity() call); branch_10x was decommissioned on 2026-10-29 (#16911, 48cf3f515d6), and 10.x bug fixes now go to branch_10_6.

Finding record

LFV-440, snapshot of 2026-11-05

Registry title
With an index sort, a failure while creating the sorted stored-fields or term-vectors writer during flush leaves the reader on the temporary .fdt/.fdx (.tvd/.tvx) files open after IndexWriter closes itself
Area
index / flush-time index sorting (SortingStoredFieldsConsumer, SortingTermVectorsConsumer)
Priority
Low, rank 1098: With an index sort, a file-open failure during flush leaves two inputs on deleted temporary files open after IndexWriter closes, a bounded exception-path leak like LFV-446.
Impact class
minor
Impact note
Hits applications that set IndexWriterConfig.setIndexSort (opt-in in Lucene; by code reading, Elasticsearch's time_series and logsdb index modes sort by default) when creating or opening a file fails (too many open files, a permission, quota or inode limit, a read-only remount, or a throwing custom Directory or codec) while a flush constructs the final sorted stored-fields or term-vectors writer: IndexWriter closes itself as designed, but two inputs on the already-deleted temporary .fdt/.fdx (or .tvd/.tvx) files stay open, which on MMapDirectory (the 64-bit default) stay mapped after IndexWriter.close, Directory.close and System.gc() and so keep that one segment's uncompressed stored fields or term vectors on disk, and on NIOFSDirectory hold two file descriptors until garbage collection (released in one executed run); no data is lost beyond what the tragic close discards, the last commit stays intact, no scale is needed, and every release from 6.5.0 to 10.6.0 and main is affected.
Summary
You configure an index sort, and while a flush is creating the final sorted stored-fields (or term-vectors) files, creating or opening a file fails with an IOException, for example because the process has too many open files. You expect IndexWriter to close itself, as it does after any failed flush, and to release every file it opened. Instead the reader that the flush had just opened on the temporary .fdt/.fdx (or .tvd/.tvx) files is never closed, because it is opened one statement before the try whose finally closes it, so two inputs on already-deleted temporary files stay open (on MMapDirectory, mapped) after IndexWriter and the Directory are closed.
