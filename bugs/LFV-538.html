WordBreakSpellChecker.suggestWordBreaks can skip better splits once an earlier branch fills its suggestion queue (maxChanges >= 3)

With setMaxChanges(3) or more, WordBreakSpellChecker.suggestWordBreaks can silently return a worse split: over the words a ab b c d e, abcde with one suggestion gives the 4-break a b c d e, not ab c d e (3 breaks). A 9.12.0 full-queue shortcut assumes breadth-first order; the search is depth-first.

The bug in 30 seconds

#

Word-break suggestions split an unknown term into indexed words, ranked by fewest breaks, then word frequency. The search keeps the best N in a bounded queue and, since 9.12.0, stops early when the queue is full. As written, that shortcut assumes a breadth-first search, and this one is depth-first across branches.

  1. Index the words a ab b c d e and ask WordBreakSpellChecker with setMaxChanges(4) (the default is 1) for one word-break suggestion for the unknown term abcde. Two splits exist: ab c d e (3 breaks) and a b c d e (4 breaks).
  2. You expect ab c d e: splits rank by fewest breaks first, and asking for 2 suggestions does return [ab c d e, a b c d e].
  3. You get [a b c d e], with both sort orders and even with an unlimited maxEvaluations. No error. With setMaxChanges(3) you get ab c d e, so raising the limit made the answer worse.
  4. Why: the search follows the branch that starts with a all the way down and queues a b c d e, which fills the one-slot queue. In the branch that starts with ab, a full-queue check added in 9.12.0 returns before cde is split into c d e, assuming everything not yet generated has more breaks.
  5. On real words, the index of Lucene's own word-break test (the English number words 900-1111 and a few more): thousandonehundredeight with maxChanges 4 returns the 4-break thou sand one hundred eight in its top 3 instead of the 3-break thousand one hundred eight. With maxChanges 3, thousandninehundredeight with 2 suggestions gets a lower-frequency second split (highest docFreq 110 instead of 112).

Who is affected

#

Code that calls suggestWordBreaks after setMaxChanges(3) or more, directly or through a downstream word-break spell-check component. The default maxChanges 1, and 2, are not affected, and only splits into 4 or more words can be lost. The wrong split still looks plausible, and raising maxChanges can make it worse. Query matching and the index are not affected.

Mechanism, terms and numbers889 words

WordBreakSpellChecker.suggestWordBreaks splits an unknown term into indexed words and should return the best maxSuggestions splits by Lucene's own order: fewest breaks first, then the highest (or summed) word frequencies. Since 9.12.0 (#12100) it returns early once its result queue is full, on the stated assumption that every split it has not generated yet has more breaks than every queued one. That holds for a breadth-first search, but the search finishes one sibling branch's whole subtree before the next, so the queue can already hold splits with as many or more breaks. With setMaxChanges(3) or more, a better split can then be lost: on the words a ab b c d e, abcde with one suggestion gives a b c d e (4 breaks) instead of ab c d e (3 breaks), while two suggestions give both in the right order and maxChanges 3 gives the right one. It happens with an unlimited evaluation budget, the default maxChanges 1, and 2, are not affected, and only splits into 4 or more words can be lost. The releases run from 9.12.0 to 10.5.2 and main fail (the others in that range carry the same file); 9.11.1 passes. Returning early only when the queue's worst split has fewer words than any deeper split can have fixes it (2 code lines replace 1), and the suggest module's tests pass with it.

Terms

#
  • WordBreakSpellChecker (lucene-suggest, org.apache.lucene.search.spell) suggests splitting an unknown term into words that are in the index (icecream -> ice cream), or combining terms.
  • suggestWordBreaks(term, maxSuggestions, reader, suggestMode, sortMethod) returns at most maxSuggestions splits. A split's score is its number of breaks. BreakSuggestionSortMethod orders them "by Number of word breaks, then by the Maximum [or Sum] of all the component term's frequencies" (WordBreakSpellChecker.java:54-62).
  • setMaxChanges(n) caps the breaks per split (default 1, :37, :441-449). setMaxEvaluations(n) caps the work (default 1000) and "might improve result quality" when raised (:451-459).

The bug

#
  1. The best splits are kept in a bounded priority queue whose head is the worst split; when it overflows the worst is dropped (:91-97, :283-287).
  2. Each call of generateBreakUpSuggestions (:241-330) first queues the two-word splits of its text whose words pass the frequency threshold and records the valid first words (phase 1, :265-290, within the maxEvaluations budget).
  3. Then it returns at once if the queue is full (:299-303), "because any subsequent suggestions are guaranteed to have more changes then anything currently in the queue, and not be competitive" (:295-296).
  4. Otherwise it recurses into the rest of the text after each valid first word, finishing one sibling's whole subtree before the next (phase 2, :305-327).
  5. So when a call that runs after an earlier sibling subtree (its own earlier sibling's or an ancestor's) reaches its check, the queue may hold splits from that subtree with as many or more breaks than the call's own deeper splits. The call returns before it generates them, although they can rank higher.

At the top level the comment is right (only 1-break splits are queued, and everything later has 2 or more). Every call runs its phase 1 before the check, and the top level returns only when its queue is full of 2-word splits, so no competitive split of 2 or 3 words is lost: maxChanges 1 and 2 are not affected (a finite maxEvaluations can still cut any search short, as documented). With maxChanges 3 a split is lost only to one with the same 3 breaks and lower frequency; with 4 or more, also to one with more breaks.

Exposure and likelihood250 words
  • Who. Users of lucene-suggest's WordBreakSpellChecker.suggestWordBreaks with maxChanges 3 or more, set directly or through a downstream component that forwards a configured maxChanges and the request's suggestion count. Upstream TestWordBreakSpellChecker.testBreakingWords itself uses maxChanges 3, 4 and 5.
  • Not affected. The default maxChanges 1, and 2; suggestWordCombinations (no such shortcut; 400,000 combination checks found no wrong result); terms whose competitive splits have at most 3 words. Lucene's query matching and the index are not affected; the immediate effect is the suggestion list.
  • Effect. Silent: no error, and the returned split is still a valid split into indexed words. With maxChanges 3 a split with the same breaks but lower frequencies replaces a better one; with 4 or more, one with more breaks can too. Raising maxChanges can make the answer worse. It happens with an unlimited maxEvaluations too, and needs no minimum index size (one document suffices); the index's words and docFreqs decide whether it triggers.
  • How often. It needs a term whose competitive splits have 4 or more words and an earlier branch that fills the queue first. In an oracle over dense random dictionaries of 1-3-letter words with an unlimited budget, about 0.1-0.3% of checks were wrong at maxChanges 3 and 1.5-3.8% at 4-6. Natural vocabularies were not measured; registry likelihood: rare.
  • Downstream (from reading source, nothing run there). Apache Solr's WordBreakSolrSpellChecker forwards its configured maxChanges and the request's count, and a Solr sample configuration sets maxChanges to 10. GitHub code search found no WordBreakSpellChecker use in Elasticsearch or OpenSearch.

Why it is a bug, not intended

#
  • The code comment claims the shortcut is lossless: later splits are "guaranteed to have more changes ... and not be competitive" (WordBreakSpellChecker.java:295-296); #12100, which added it, says the same.
  • Lucene's own ranking disagrees: with 2 suggestions the dropped split comes first, and 9.11.1 returns it.
  • It fails with an unlimited maxEvaluations, so the budget trade-off does not explain it.
The full argument279 words
  • The order is defined. BreakSuggestionSortMethod: "Sort by Number of word breaks, then by the Sum [Maximum] of all the component term's frequencies" (:54-62); both comparators rank fewer words first, then higher frequency (:461-485), and the queue keeps the best maxSuggestions by that order.
  • The shortcut was meant to be lossless. Code comment: "any subsequent suggestions are guaranteed to have more changes then anything currently in the queue, and not be competitive" (:295-296); the method calls itself a "Two phase breadth first search" (:260). Issue #12100 (hossman): "we know that candidates with fewer NUM_CHANGES... are _always_ better, a breadth first approach can can actually short-circuit and return much earlier then I originally suggested, if the suggestions queue is already "full"".
  • The change promised better matches. CHANGES 9.12.0, Optimizations: "WordBreakSpellChecker.suggestWordBreaks now does a breadth first search, allowing it to return better matches with fewer evaluations". Upstream testSmallMaxEvaluations calls the fewest-changes result "optimal".
  • The behaviour contradicts it. The top 1 is not the head of Lucene's own top 2; 9.11.1 returned the expected top N, by the ranking keys, on every input tried; an unlimited budget fails the same way; raising maxChanges from 3 to 4 makes the answer worse.
  • Why the tests missed it. The two maxEvaluations tests as #12100 left them (it added testSmallMaxEvaluations and rewrote testMaxEvaluations, which #12077 had added) use "plenty" maxSuggestions (maxEvals * 2, maxEvals * 10), so the full-queue return never fires in them, and the maxChanges 3-5 cases of testBreakingWords have no earlier sibling that fills the queue. No upstream test asserts the current output; with the fix every suite in the module passes.
The devil's-advocate check222 words

The strongest works-as-designed case (the cross-model lenses, the independent reproducer, the devil's advocate and the adjudication): the suggestWordBreaks javadoc says only that "a lower score is generally preferred over a higher score" (:64-67); BreakSuggestionSortMethod "Determines the order to list word break suggestions", which could mean the order of the returned list rather than which splits are selected; setMaxEvaluations admits that "A higher value might improve result quality", so quality is openly heuristic; #12100 is filed under Optimizations and changed results on purpose; and maxChanges 3 or more is opt-in.

Why it fails: the loss happens with the budget unused, so the setMaxEvaluations trade-off does not cover it. The only justification the code gives, the comment at :295-296, is false for the committed algorithm, and #12100 argues for the shortcut on exactly the property the repro breaks. The top N is not a prefix of Lucene's own top N+1, and 9.11.1 returned the expected top N. The results #12100 changed on purpose are budget-limited ones; this loss happens with the budget unused, and nothing in #12100 suggests it was known or accepted. Keep the caveat in the issue: the javadoc does not literally promise the best maxSuggestions splits, so rest the case on the code comment and #12100, not on the javadoc alone. Verdict: not intended; a regression of #12100.

Suggested fix

#

Recommended A: return on a full queue only when no deeper split can beat it

Return on a full queue only if its worst split has fewer words than any split this call could still generate: add && suggestions.peek().suggestWords.length <= newNumberBreaks (2 code lines replace 1). It keeps the 9.12.0 pruning wherever it is safe. All 245 suggest-module tests pass with it, the repros included, with assertions on and off.

// if we are about to exceed our maxChanges *OR* we have a full list of
// suggestions that all have fewer words than any deeper suggestion can have
// (at least newNumberBreaks + 1), we can return now.
final int newNumberBreaks = numberBreaks + 1;
if (totalEvaluations >= maxEvaluations
    || newNumberBreaks > maxChanges
    || (suggestions.size() >= maxSuggestions
        && suggestions.peek().suggestWords.length <= newNumberBreaks)) {
  return totalEvaluations;
}

A: return on a full queue only when no deeper split can beat it (validated by the checks) (recommended)

#

In generateBreakUpSuggestions, require that the queue's worst split (suggestions.peek()) has at most newNumberBreaks words before returning on a full queue, and replace the comment that claimed the return is always lossless. 2 code lines replace 1 in WordBreakSpellChecker.java.

// if we are about to exceed our maxChanges *OR* we have a full list of
// suggestions that all have fewer words than any deeper suggestion can have
// (at least newNumberBreaks + 1), we can return now.
final int newNumberBreaks = numberBreaks + 1;
if (totalEvaluations >= maxEvaluations
    || newNumberBreaks > maxChanges
    || (suggestions.size() >= maxSuggestions
        && suggestions.peek().suggestWords.length <= newNumberBreaks)) {
  return totalEvaluations;
}

Trade-offs

  • Why it is right. peek() is the worst queued split (both comparators put more words first, then lower frequency, and the queue polls its head). A recursion from this call yields splits of at least newNumberBreaks + 1 words; if the worst queued split has at most newNumberBreaks words, every deeper split ranks strictly below it and would be dropped at once, so skipping phase 2 loses nothing. With newNumberBreaks + 1 or more words, a deeper split can tie on words and win on frequency, so the bound is tight. "Loses nothing" is by the ranking keys: tied splits have no defined order (both comparators return 0 on equal keys), as on 9.11.1.
  • Keeps #12100's gain where it is valid: at the top level and in every call whose queue holds only shorter splits, it prunes exactly as today.
  • Cost. It explores the subtrees the shortcut wrongly skipped. A docFreq-lookup trace (made with the finder's guard, the same condition) counted 26 lookups with the fix vs 23 stock (21 on 9.11.1) for the minimal case, and 103 vs 90 (102 on 9.11.1) for the number-word top 3; these are lookups, not maxEvaluations units, which count phase-1 split positions. Work stays capped by maxEvaluations and maxChanges. Not benchmarked. With a finite maxEvaluations results stay budget-dependent, as setMaxEvaluations documents; the exhaustive checks used an unlimited budget.
  • Open draft PR #16847 changes only the frequency types, in other hunks of this file, not the shortcut; fix A applies cleanly to the file at its current head (6aea7b57d734, checked 2026-10-28), so the two do not conflict.

How it was found

#

A bounded-exhaustive check of suggestWordBreaks on the stock jar against a brute-force reference: every split of the term into indexed words, ranked by the documented order, over many small random indexes. 984 of 1,224,000 break checks were wrong, all at maxChanges 3 or 4. A search on the upstream test's index then found the number-word example.

The method in full167 words

Method: translation validation against an exact reference (the hunt's "semi-formal" tier).

  • The reference enumerates every split of the term into indexed words with at most maxChanges breaks, applies the documented word-length, frequency and SuggestMode rules, orders the splits by the BreakSuggestionSortMethod keys (ties as sets) and keeps the top maxSuggestions.
  • Bounds: 200 random indexes over the 126 strings of length 1-6 over {a, b}, all 510 queries of length 1-8, 12 random configurations each (maxChanges 0-4, both sort methods, several maxSuggestions and modes, unlimited maxEvaluations): 1,224,000 break checks. 984 were wrong, all at maxChanges 3 or 4, and 0 with the fix shadowed. (A separate maxChanges=0 discrepancy class in the same run is a different question, not part of this bug.) A mutant reference was used to show the check is not vacuous.
  • A second search on the index of upstream TestWordBreakSpellChecker found the natural examples thousandonehundredeight and thousandninehundredeight; the finder turned them and a minimal case into a public-API JUnit test.

Bug record

#

LFV-538, snapshot of 2026-10-29

Registry title
WordBreakSpellChecker.suggestWordBreaks drops better suggestions when maxChanges >= 3: the full-queue early return added in 9.12.0 (GITHUB#12100) assumes a breadth-first order that the depth-first recursion does not follow
Area
suggest / spell (WordBreakSpellChecker word breaks)
Priority
Low, rank 373: WordBreakSpellChecker drops better suggestions only with opt-in maxChanges >= 3 and a small fraction of inputs, a suggestion-quality issue like LFV-240, so it follows LFV-566.
Impact class
silent wrong results
Impact note
Applications on Lucene 9.12.0 through 10.5.2 or main that raise WordBreakSpellChecker.setMaxChanges to 3 or more (the default is 1; directly, or through a downstream word-break spellcheck component's maxChanges setting, which one downstream sample configuration sets to 10) silently get a worse word-break suggestion list for terms whose competitive splits have four or more words, whenever an earlier branch of the search has already filled the maxSuggestions queue: a split with the same number of breaks but a lower frequency (maxChanges >= 3) or with more breaks (maxChanges >= 4) is returned in place of a better one, at any index size and for any maxEvaluations, while maxChanges 1 and 2 and suggestWordCombinations are not affected.
Summary
You index some words and call WordBreakSpellChecker.suggestWordBreaks with setMaxChanges(3) or more, and you expect the maxSuggestions splits of the term that rank best by Lucene's own order (fewest breaks, then highest frequency). Instead, once an earlier branch of the search has filled the queue, a later branch returns before it looks for its own splits, so a better split can be missing: with the index {a, ab, b, c, d, e}, the term 'abcde', maxChanges=4 and maxSuggestions=1 the method returns [a b c d e] (4 breaks) instead of [ab c d e] (3 breaks), while asking for 2 suggestions returns both in the right order. No error is raised, raising maxChanges from 3 to 4 makes the answer worse, and 9.11.1 returns the right split.
