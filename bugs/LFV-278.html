A reordered addIndexes of SortingCodecReader inputs writes vectors onto the wrong documents

Re-sort segments with SortingCodecReader, add them in one addIndexes call to a writer whose merge policy reorders documents (such as BPReorderingMergePolicy), and the documents get other documents' vectors: 8 of 8 in the repro. Nothing throws, CheckIndex reports the index clean, and every 10.x release is affected.

The bug in 30 seconds

#

Three opt-in pieces meet: SortingCodecReader, a re-sorted view that leaves each vector at its original position; one addIndexes call with several inputs; and a merge policy that reorders. To reorder, Lucene joins the inputs into a merged view, and that view counts vectors by position instead of asking each input where its vectors are.

  1. Build two small segments, ids 0-3 and ids 10-13, where each document's vector is {id, 100 - id}, so a vector names its owner. Re-sort each with SortingCodecReader by descending rank, so id 3 comes first.
  2. Add both in one addIndexes(sa, sb) call to a writer with no index sort whose merge policy reorders the merge: BPReorderingMergePolicy, or a custom OneMerge#reorder that returns the identity and moves nothing.
  3. You expect every document to keep its vector: doc 0 (id 3) should hold [3.0, 97.0], as it does when the merge policy does not reorder.
  4. Instead Lucene joins the inputs into one merged view that numbers vectors 0, 1, 2, 3 in the new order but looks number k up at the input's original position k. Doc 0 (id 3) gets id 0's vector [0.0, 100.0]; all 8 documents get another document's float and byte vector.
  5. No error with assertions on or off, CheckIndex is clean, and kNN search ranks by the wrong embeddings until the segment is rebuilt. If id 0 was deleted before the call, its vector still lands on live id 3.

Who is affected

#

Applications that pass two or more inputs, at least one a SortingCodecReader, to one addIndexes(CodecReader...) call on a writer with no index sort whose merge policy reorders addIndexes merges (BPReorderingMergePolicy or a custom OneMerge#reorder). All opt-in; no scale needed. Two safe, tested usage patterns and regular merges over the built-in segment readers are not affected.

Mechanism, terms and numbers730 words

SortingCodecReader's javadoc suggests re-sorting an index by wrapping its readers and passing them to IndexWriter#addIndexes(CodecReader...). When two or more inputs go into one such call (at least one a SortingCodecReader, built from a Sort or from a Sorter.DocMap such as BPIndexReorderer.reorder's output), the target writer has no index sort (and no input has document blocks without a parent field), and the merge policy's OneMerge#reorder returns a DocMap (misc BPReorderingMergePolicy computes one for every addIndexes merge, unless its reorderer runs out of RAM; an identity DocMap is enough), IndexWriter reorders through a merged view, SlowCompositeCodecReaderWrapper. Its vector iterator numbers ordinals by position while its vectorValue(ord) reads in each input's own ordinal space, and a SortingCodecReader keeps its vectors at their original ordinals. So within each re-sorted input the k-th document in sorted order is written with the vector at original ordinal k: in the repro all 8 documents get another document's float and byte vector, and a deleted document's vector lands on a live one. Nothing throws, CheckIndex reports the index clean, and kNN search ranks by other documents' embeddings until the segment is rebuilt. All 12 10.x releases (10.0.0-10.5.2) and main are affected; it was introduced by #13779, and a two-line change (one line changed, one removed) fixes it.

Terms

#
  • Ordinal: a vector's index inside a field's vector values. An iterator's index() gives the ordinal of its current document, and vectorValue(ord) reads that vector.
  • SortingCodecReader: a merge-only view of a segment in a new document order. It does not move the vectors: it visits documents in the new order, and its index() returns each document's original ordinal (its javadoc: "index() may skip around, not increasing monotonically").
  • Reordered addIndexes: when the target writer has no index sort, addIndexes joins all inputs of one merge into a merged view (SlowCompositeCodecReaderWrapper) and asks OneMerge#reorder for a new document order (unless an input has document blocks but no parent field). BPReorderingMergePolicy computes one for every addIndexes merge with a live document, unless its reorderer runs out of RAM.

The bug

#
  1. The merged view's iterator numbers ordinals 0, 1, 2, ... as it walks the documents: ++ord per document (SlowCompositeCodecReaderWrapper.java:342 at ea57360912ed) and ord = current.ordStart - 1 on moving to the next input (:352).
  2. Its vectorValue(ord) looks the ordinal up in the input's own ordinal space, sub.vectorValue(ord - sub.ordStart) (:912-920 float, :1011-1019 float16, :1060-1069 byte), with the comment that this random access exists "to support callers like SortingCodecReader that rely on it". That caller is the SortingCodecReader wrapped around the view (item 4); the comment does not speak to sorted inputs of the view, and nothing excludes them.
  3. The two agree only if each input's index() equals its iteration position. On-disk segments satisfy that; a SortingCodecReader does not: index() returns docToOrd[doc] and vectorValue(ord) reads the wrapped reader at that ordinal (SortingCodecReader.java:265-290, :323-326).
  4. IndexWriter.addIndexesReaderMerge builds SortingCodecReader.wrap(SlowCompositeCodecReaderWrapper.wrap(readers), docMap, null) whenever the writer has no index sort, no input has document blocks without a parent field, and the reorder returns a DocMap (IndexWriter.java:3548-3565). The outer reader records the merged iterator's ordinal for each document, and the codec's merge writes the vector read at that ordinal (current.values.vectorValue(current.index()), KnnVectorsWriter.java:484).
  5. Input A re-sorted descending is visited as ids 3, 2, 1, 0 and gets merged ordinals 0, 1, 2, 3. Ordinal 0 is A's original ordinal 0, id 0's vector. So id 3 is written with id 0's vector, id 2 with id 1's, and so on; input B the same. The reorder itself does not matter: an identity DocMap takes the same path.
  6. The codec merge code written in the same commit reads each input's own ordinal, current.values.vectorValue(current.index()) (KnnVectorsWriter.java:484, :643). Only the merged view assumes positional ordinals.

Exposure and likelihood411 words
  • Who is exposed. An addIndexes(CodecReader...) merge with two or more inputs, at least one a SortingCodecReader (from SortingCodecReader.wrap(reader, Sort), or from a Sorter.DocMap, for example misc BPIndexReorderer.reorder(...), which returns one), into a writer with no index sort whose merge policy's OneMerge#reorder returns a DocMap for the addIndexes merge (misc BPReorderingMergePolicy, or any custom reorder, even the identity). The default findMerges(CodecReader...) puts all inputs in one merge. A tool that re-sorts or imports segments into a writer configured with BPReorderingMergePolicy would hit it; no such tool is known.
  • Executed triggers. Inputs re-sorted by a Sort; two BPIndexReorderer.reorder outputs with no Sort at all; one SortingCodecReader next to a plain input (only the sorted input's vectors move). Float and byte vectors were executed; float16 vectors (main only) use the same iterator and mismatched in the finder's differential harness, but no JUnit covers them.
  • Not affected. Two safe, tested in-tree usage patterns (executed; neither is documented as a requirement): a target writer with the same index sort as the inputs (no reorder runs) and one BPIndexReorderer output per addIndexes call (no merged view is built). Regular segment merges over the built-in segment readers, by code reading: their ordinals are positional, and wrapForMerge may not reorder doc IDs; a custom codec or wrapForMerge wrapper with non-positional vector ordinals was not ruled out.
  • Opt-in. SortingCodecReader and OneMerge#reorder are @lucene.experimental; BPReorderingMergePolicy is a misc-module class. Nothing else is non-default: the tests pin the default codec and use the test framework's randomized directories.
  • Scale and frequency. 8 documents in 2 segments; deterministic (over 10 iterations all 20 bug-test runs failed and all 10 control runs passed). Once on that path, every document with a vector whose input's index() differs from its position in that input's iteration order gets a wrong vector; documents whose ordinal equals their position keep theirs.
  • Silent and lasting. No exception, CheckIndex clean; the wrong vectors are written to the new segment, so kNN search and any code that reads vectors back see them until the segment is rebuilt from source data. A code fix stops new damage only.
  • Intact. Ids, stored fields, postings and doc values; vectors stayed inside their own input in every executed case.
  • Downstream (read, not tested). No BPReorderingMergePolicy in Elasticsearch's code (code search); Solr makes it configurable (apache/solr#2641), but whether any Solr path also feeds SortingCodecReader inputs to addIndexes was not checked; the OpenSearch, Solr and OpenSearch k-NN code searches hit a rate limit.

Why it is a bug, not intended

#
  • index() must return "the value index (aka "ordinal" or "ord") corresponding to the current doc"; the merged view's index() names another document's vector.
  • The merged view's random access is there "to support callers like SortingCodecReader", whose index() "may skip around"; nothing rejects sorted inputs.
  • An identity reorder moves no document, yet the vectors move; 9.9.0-9.12.3 keep them in place.
The full argument369 words
  • The contract. KnnVectorValues.DocIndexIterator.index(): "return the value index (aka "ordinal" or "ord") corresponding to the current doc" (KnnVectorValues.java:140). The merged iterator's index() names another document's vector.
  • The merged view is built to serve SortingCodecReader. "We need to implement fully random-access API here in order to support callers like SortingCodecReader that rely on it" (SlowCompositeCodecReaderWrapper.java:914-915, also :1014-1015, :1063-1064). The caller meant is the SortingCodecReader wrapped around the view, as IndexWriter builds it; the comment does not speak to sorted inputs of the view, but that outer reader only works if the view's ordinals match its vectors, and nothing keeps sorted readers out.
  • SortingCodecReader documents both its ordinals and this use. "index() may skip around, not increasing monotonically as iteration proceeds" (SortingCodecReader.java:265-266), and "This can be used to re-sort and index after it's been created by wrapping all readers of the index with this reader and adding it to a fresh IndexWriter via IndexWriter#addIndexes(CodecReader...)" (:48-50).
  • OneMerge#reorder only renumbers doc IDs. "Extend this method if you wish to renumber doc IDs. This method will be called when index sorting is disabled on a merged view of the OneMerge" (MergePolicy.java:312-313). An identity DocMap renumbers nothing and still moves the vectors.
  • No precondition, no rejection. Nothing documents that addIndexes inputs need positional vector ordinals; validateMergeReader checks an input's sort only when the writer has an index sort (IndexWriter.java:3228).
  • History. #13779 (6053e1e3137, 2024) added both halves in one commit; before it the merged view returned the current input's vector at the current document and 9.x SortingCodecReader copied vectors into the new order. None of its 37 inline review comments is on SlowCompositeCodecReaderWrapper or SortingCodecReader, and none says that an input's ordinals must be positional. The codec merge path of the same commit reads each input's index() (KnnVectorsWriter.java:484, :643).
  • Why tests missed it. TestSortingCodecReader always gives the target the same index sort (no reorder); TestBPReorderingMergePolicy.testReorderOnAddIndexes adds plain inputs and checks stored fields, never vectors; MockRandomMergePolicy does not reorder addIndexes merges.
  • Precedent. Upstream fixed other defects in this merged view as bugs (#14092) and an ordinal-tracking defect of the same kind in KnnVectorsWriter.MergedByteVectorValues (#14992 / #15553).
The devil's-advocate check194 words

The strongest "works as designed" case (the intended-behaviour check, the intended-behaviour devil's advocate, and the cross-model lenses): the merged view is package-private and "primarily targeted at merging, not searching"; SortingCodecReader and OneMerge#reorder are @lucene.experimental; the two in-tree usage patterns are safe (a target with the same index sort, one reordered reader per addIndexes call; executed); the trigger sorts the data twice; and ++ord is correct for every on-disk reader.

Why it fails: the failure happens during a merge, the use the view exists for, and the view names SortingCodecReader as a caller to support (as its wrapper). Experimental status allows API changes, not silently wrong data. Neither safe pattern is documented as required; addIndexes is varargs, the default policy puts all inputs in one merge, BPReorderingMergePolicy deliberately reorders addIndexes merges, and nothing rejects or documents against the combination. An identity reorder sorts nothing and still corrupts. What remains on the other side is rarity: an unusual stack of opt-in APIs (and BPReorderingMergePolicy skips the reorder when its reorderer runs out of RAM) and no report since 10.0.0. The likely reply is "real, niche, fix it", not "by design"; no source supports by design.

Suggested fix

#

Recommended Use each input's own ordinal in the merged iterator (validated)

In MergedDocIterator.nextDoc, take the input's own ordinal, ord = current.ordStart + currentIterator.index(), instead of ++ord, and drop the reset on moving to the next input. With it every repro passes, and so do the default lucene/core and lucene/misc test tasks (with their usual skips), assertions on and off.

if (next != NO_MORE_DOCS) {
  // Use the sub's own ordinal: it need not follow the doc order (a SortingCodecReader
  // sub reports the ordinals of the reader it wraps), and vectorValue(ord) reads there.
  ord = current.ordStart + currentIterator.index();   // was: ++ord
  assert ord >= current.ordStart && ord < current.ordStart + current.sub.size();
  return doc = current.docStart + next;
}
...
current = it.next();
currentIterator = currentIterator();
// removed: ord = current.ordStart - 1;

Use each input's own ordinal in the merged iterator (validated) (validated by the checks) (recommended)

#

SlowCompositeCodecReaderWrapper.MergedDocIterator.nextDoc: ord = current.ordStart + currentIterator.index() instead of ++ord, and remove ord = current.ordStart - 1 (1 changed line, 1 removed line, plus a comment and an assertion). The merged ordinal then names the same vector that the merged vectorValue(ord) reads.

It stays in range: Sorter.DocMap.size() "must be equal to the number of documents" of the reader it sorts, so a SortingCodecReader input reports every ordinal of the reader it wraps and ordStart + index() stays inside the input's [ordStart, ordStart + size()) slot. The added assertion checks that; it held in every run with assertions on. A DocMap that drops documents is outside that contract (flagged by the adjudication, untested); the assertion would catch it.

  // sub reports the ordinals of the reader it wraps), and vectorValue(ord) reads there.

Trade-offs

  • One index() call per vector in a reordered merge, next to the vector read itself; no benchmark was run.
  • Plain inputs and regular merges over the built-in segment readers get the same ordinals as before (index() equals the position there).
  • Prevents new damage only: indexes already written through this path keep the wrong vectors and must be rebuilt.
  • Leaves a separate question open (read, not run): with misc BpVectorReorderer as the reorderer, each reorder thread calls vectors.copy() on the merged view (BpVectorReorderer.java:110, :619-624), which copies every input, and Sorting*VectorValues.copy() throws UnsupportedOperationException (SortingCodecReader.java:345-348); its sparse-field path also counts ordinals by position (:735-770). By code reading that combination ends in the exception, with or without this fix, once the merged view is large enough to be split (:208-217); below that the reorder is the identity and this fix applies.

Make SortingCodecReader expose positional ordinals (not run)

#

Copy or remap vectors into the new order, as 9.x did.

Trade-offs

Turns a memory-light merge-only reader into one that buffers or remaps every vector, and leaves the merged view still assuming positional inputs for any future input with non-positional ordinals (for example the on-disk iterator of open PR #15430, read only). Not recommended.

Refuse or skip the reorder for such inputs (not run)

#

Throw in addIndexes, or skip the reorder, when an input's vector ordinals are not positional.

Trade-offs

Turns silent corruption into an error or a lost reorder, but there is no cheap general way to detect non-positional ordinals, and it blocks a combination the javadocs invite. A stop-gap at most.

Downstream note

#

Out of scope of SECURITY.md: only the application's own configuration reaches this code, and SECURITY.md trusts configuration. Downstream, the effect crosses deletion and access boundaries and lasts: a filtered kNN search returned public documents at score 1.0 computed from a deleted and a private document's embeddings. Filters held; no ids or stored fields leaked.

How it was found

#

Randomized differential testing: the finder, an AI tool, compared the merged reader view that addIndexes uses for reordering against each input's own data and saw vector mismatches only when SortingCodecReader inputs were present. A small Z3 model then stated the hidden assumption, and a public-API JUnit confirmed it on the stock jars.

The method in full208 words
  • Unit and method. A hunt unit (codec-reader wrappers), 2026-10-26. The finder's randomized differential harness compared SlowCompositeCodecReaderWrapper's merged view, and addIndexes through it with an identity reorder, against the per-input data: 3 runs x 150 iterations with SortingCodecReader inputs allowed. It reported float, byte and float16 vector mismatches (for example 7 float, 41 byte and 3 float16 in one run) only in the runs with SortingCodecReader inputs.
  • The model. A small Z3 model of the merged iterator stated the hidden assumption, for inputs of 2 to 4 vectors: with monotone input ordinals no document can be given another document's vector (unsat); with an arbitrary permutation, as a SortingCodecReader allows, one can (sat: a witness exists). The first signal was the random differential, so this counts as a non-formal find.
  • Then. A public-API JUnit on the stock jars; a cross-model review by a reviewer from another model family (OpenAI GPT-5.6, read-only, refute and intended lenses); an independent reproducer with its own tests and a 9.x port; a GPT-5.6 root-cause adversary; an intended-behaviour devil's advocate with reach probes; an adjudication (confirmed, high); a history sweep with commit builds; a prior-report search; a security assessment and probe; a registry re-run with fresh seeds; and this doc's own test and fix validation.

Bug record

LFV-278, snapshot of 2026-10-27

Registry title
SlowCompositeCodecReaderWrapper's merged vector iterator numbers ordinals by position and ignores each input's own index(), so addIndexes of two or more SortingCodecReader inputs through a reordering merge policy writes vectors onto the wrong documents
Area
index / addIndexes reorder path: SlowCompositeCodecReaderWrapper merged vector values (MergedDocIterator) over SortingCodecReader inputs
Priority
Medium, rank 82: Vectors silently land on the wrong document, CheckIndex does not catch it, and it is released since 10.0, but it needs a rare opt-in SortingCodecReader and reordering-merge mix, so it is the last released row before the unreleased rows.
Impact class
data corruption
Impact note
Applications on 10.0.0 through 10.5.2 or main that call IndexWriter.addIndexes(CodecReader...) with two or more SortingCodecReader inputs (re-sorted by a Sort or by a BPIndexReorderer DocMap) into a writer with no index sort whose merge policy reorders addIndexes merges (misc BPReorderingMergePolicy, or any custom OneMerge#reorder, even an identity one) silently get float and byte vectors (and, on main, float16 vectors) persisted on other documents of the same input, so kNN search on the new index ranks documents by other documents' embeddings until the segment is rebuilt; nothing throws with -ea or -da and CheckIndex reports the index clean; every piece is opt-in and experimental, no scale is needed, and regular segment merges (by code reading) and the two documented recipes (a target with the same index sort, or one reordered reader per addIndexes call; executed) are not affected.
Summary
You re-sort two or more segments with SortingCodecReader and pass them to one IndexWriter.addIndexes(CodecReader...) call on a writer that has no index sort but uses a merge policy that reorders addIndexes merges, such as BPReorderingMergePolicy (an identity OneMerge#reorder is enough), and you expect every document to keep the vector it was indexed with, as it does without the reorder. Instead the merged view that IndexWriter builds for the reorder (SlowCompositeCodecReaderWrapper) numbers vectors by iteration position, while each SortingCodecReader input reports and reads vectors by its original ordinal, so in each input the k-th document in sorted order is written with the vector at original ordinal k. Nothing throws, with or without assertions, CheckIndex reports the new index clean, and kNN search then scores documents by other documents' vectors, in an executed probe including the vector of a document deleted before the call.
