The finding in 30 seconds

#

It needs the new opt-in setting above 0 (run with 1, 2 and 4); it is 0 in every constructor that existed before and for a Monitor built without a presearcher. Unreleased: main and branch_11x since 2026-11-23; no release has the setting or the analyzer's negation mode behind it. Rare; how often stored queries have the shape was not measured.

Background: four pieces

#
  1. A Monitor stores queries and reports, for each document, the stored queries that match it. A presearcher first selects the queries that could match; only those are run against the document. It may select too many. A query it does not select is not run and not reported.
  2. TermFilteredPresearcher indexes each stored query under terms taken from it and selects it for a document that has one of them. A query that it cannot index that way goes under a catch-all token and is selected for every document.
  3. New and opt-in: with maxNegativeDisjuncts above 0 a negated term filters too. *:* -flag:true is indexed with a "negative disjunct" flag:true and is selected only for documents without flag:true.
  4. To read a query, the presearcher's analyzer visits it with a QueryVisitor: each clause reports its terms, or itself as a leaf. A clause can also report nothing at all: a TermInSetQuery without terms asks the visitor whether it accepts the field and makes no other call.

The finding, step by step

#
  1. Build a Monitor with new TermFilteredPresearcher(TermWeightor.DEFAULT, List.of(), Set.of(), 1). The last argument is the new setting maxNegativeDisjuncts (MultipassTermFilteredPresearcher has it too): above 0, negated terms filter too. The class javadoc's example: *:* -flag:true is then only selected for documents without flag:true.
  2. Register the query *:* -(+tag:red +id:()): every document except those that have tag:red and an id from a set. The set is a TermInSetQuery without terms, which matches nothing. So the negated group excludes nothing, and the query matches the document {tag: red}: IndexSearcher over a MemoryIndex of it counts 1. You expect Monitor.match to report the query.
  3. Instead getMatchCount() is 0, getQueriesRun() is 0 and getErrors() is empty. Monitor.match returns normally: no exception, with assertions on and off.
  4. Why: the presearcher's analyzer reads the query through a QueryVisitor, and the set without terms reports nothing to it (it asks acceptField and makes no other call). The negated group is built from tag:red alone, so the query is indexed like *:* -tag:red (the same fields and terms) and is not selected for a document that holds tag:red (a document matched alone). For {tag: blue} the same Monitor reports it, and with the setting at 0 it is reported for {tag: red} too.
  5. The shape, as run: a MUST_NOT clause that is a BooleanQuery in which a clause that reports nothing to the QueryVisitor stands among the MUST clauses beside another MUST, FILTER or MUST_NOT clause, or among the FILTER clauses beside another FILTER clause. As the only FILTER clause beside a MUST or a MUST_NOT clause, and with a SHOULD clause as the only other clause of the group, the match was reported. In the set's place seven instances were run and lose the match (a TermInSetQuery without terms, also with the doc-values rewrite; the term ranges tag:[m TO c] and tag:{red TO red}; the regular expressions # and a&b; an AutomatonQuery over an empty automaton). Nine other instances are reported: MatchNoDocsQuery, a BooleanQuery without clauses, a term set of one and of two terms, a TermQuery, a range that is not empty, a wildcard, a prefix, a two-term phrase.

Who is affected

#

An application that builds a term presearcher with the new setting above 0, on unreleased code, and stores a query with this shape. Not the default: with 0, through each constructor that existed before and for a Monitor built without a presearcher, the same builds report the match. Silent. Rare; how often stored queries have the shape was not measured.

Mechanism, terms and numbers1,884 words

TermFilteredPresearcher and MultipassTermFilteredPresearcher have a new constructor argument, maxNegativeDisjuncts (three constructors take it; added on 2026-11-23 by #17032). Above 0 it switches the presearcher's query analyzer into a mode that also reads the clauses under a MUST_NOT clause (TermFilteredPresearcher.java:127; the mode was added on 2026-11-19 by #16998). In that mode the MUST or FILTER group of a negated BooleanQuery gets a builder that combines its negated clauses with OR (QueryAnalyzer.java:141-148, :115-118). A clause that reports nothing to the QueryVisitor (a TermInSetQuery without terms asks acceptField and makes no other call) adds nothing to that builder, so the builder is built from the other clause alone (:173-191, :256-269): *:* -(+tag:red +id:()) is indexed with the negative disjunct tag:red, like *:* -tag:red, and a document that holds tag:red, matched alone, does not select it. The clause that was left out matches nothing, so the group excludes nothing and the query matches the document. The class javadoc of the mode says of negations that cannot be expressed exactly, "such as phrases or wildcards", that they "still select the query for every document" (TermFilteredPresearcher.java:64-66): the documented limits of the mode go towards selecting more, and here a query is selected for fewer documents than it matches. Lines are at main 894d24e9b0c7; lucene/monitor is the same tree on branch_11x 784a2d5d03d4.

Terms

#
  • Presearcher. "A Presearcher is used by the Monitor to reduce the number of queries actually run against a Document" (Presearcher.java:28-32). The package documentation: "Queries that match this disjunction are then run against the document. In this way, the Monitor can avoid running queries that have no chance of matching." (package-info.java:60-61).
  • The catch-all token. QueryTree.anyTerm (QueryTree.java:145-169) indexes a query under __anytokenfield: __ANYTOKEN__, and the query a presearcher builds for a document has that term as an alternative (TermFilteredPresearcher.java:163-166): such a query is selected for every document.
  • Negative disjunct. With the setting above 0 a negated term is indexed under <field>__not_<i> beside the marker __negdisjunct_<i>: __T__ (TermFilteredPresearcher.java:390-428); the query built for a document excludes the stored queries whose negative disjunct holds a term of the document (:338-362).
  • Reports nothing. A clause reports nothing to the QueryVisitor when its visit method makes none of the reporting calls: no terms (consumeTerms, consumeTermsMatching), no leaf (visitLeaf) and no request for a sub-visitor (getSubVisitor). Two stock visit methods do so after they ask acceptField: TermInSetQuery#visit calls consumeTerms for one term, consumeTermsMatching for more, and nothing for none (TermInSetQuery.java:177-188); CompiledAutomaton#visit, which AutomatonQuery#visit calls (AutomatonQuery.java:150-154), has case NONE: break; for a compiled automaton of the type NONE (CompiledAutomaton.java:365-382). TermRangeQuery and RegexpQuery are automaton queries; the five range, regular-expression and automaton instances of this page have that type (run).

The mechanism

#

Lines are at main 894d24e9b0c7; the monitor files are the same on branch_11x 784a2d5d03d4.

  1. The switch. TermFilteredPresearcher.java:127: this.extractor = new QueryAnalyzer(customQueryHandlers, maxNegativeDisjuncts > 0);. With 0 the analyzer hands a MUST_NOT clause QueryVisitor.EMPTY_VISITOR (QueryAnalyzer.java:160-162) and reads nothing under a negation. Above 0 it returns negation() (:163), a builder in negated polarity (:131-133).
  2. A required group under a negation. BooleanQuery#visit (BooleanQuery.java:615-631) asks its visitor for a sub-visitor for the MUST group and sends each MUST clause there; the FILTER, SHOULD and MUST_NOT clauses go to sub-visitors of that one. For a MUST or FILTER group the analyzer returns conjunction() (QueryAnalyzer.java:146-148), a child in the same polarity. By its constructor (:115-118, this.buildsDisjunction = combinesWithOr ^ isNegated;) a negated conjunction combines its clauses with OR: NOT (a AND b) = NOT a OR NOT b.
  3. The two clauses. tag:red calls consumeTerms, and under negation the term is added to the builder's negated terms (:173-191). id:() asks acceptField and makes no other call. The builder now holds one negated term and nothing that stands for NOT id:(), which is "every document".
  4. The build. A negated term becomes a negative disjunct (:256-266). The group holds one entry, so isConjunctive (:220-222) lets mergeNestedNegatedConjuncts (:228-240) move the term to the enclosing conjunction. The fallback that selects every document, QueryTree.anyTerm("NO CLAUSES"), applies only to a builder that holds nothing at all (:267-269). The tree of the whole query is a conjunction of ANY[*:*] and the negative disjunct tag:red: the same tree as for *:* -tag:red (run, printed by a subclass that overrides the protected buildQueryDocument).
  5. The index entry and the two documents. The query is indexed as __negdisjunct_0: __T__, tag__not_0: red, tag__not: red, the same fields and terms as *:* -tag:red (run, through the public Presearcher#indexQuery); with the setting at 0 both are indexed as __anytokenfield: __ANYTOKEN__. For the document {tag: red} the presearcher builds ((#__negdisjunct_0:__T__ -tag__not_0:(red))) __anytokenfield:__ANYTOKEN__ (run, through the public Presearcher#buildQuery): the stored query does not match it and is not run. For {tag: blue} the excluding clause is absent, the query is selected, run and reported.

Why it looks unintended

#

The full argument412 words
  • The javadoc of the mode. The class javadoc of TermFilteredPresearcher (TermFilteredPresearcher.java:63-67 at main 894d24e9b0c7, the same lines at branch_11x 784a2d5d03d4): "With a maximum number of negative disjuncts greater than 0, negated terms filter too: *:* -flag:true is then only selected for documents without flag:true. Negations that cannot be expressed exactly, such as phrases or wildcards, still select the query for every document, and in a batch a term only excludes queries if every document contains it." The sentence names phrases and wildcards, not a clause that reports nothing; it shows which way the documented limits of the mode go: a query may be selected for more documents than it matches. Here NOT (tag:red AND a clause that matches nothing) is "every document", and the group was indexed as NOT tag:red: the query is selected for fewer documents than it matches.
  • What a presearcher is for. Presearcher.java:28-32: "A Presearcher is used by the Monitor to reduce the number of queries actually run against a Document". The package documentation (package-info.java:60-61): "In this way, the Monitor can avoid running queries that have no chance of matching."; and (:73-74): query analysis "will work for all basic term-based queries shipped with Lucene". A query that is not selected is not run, so a missed selection is a missed match.
  • The analyzer's own neighbouring cases. A negated builder that holds nothing at all selects every document (QueryAnalyzer.java:267-269). A negated leaf without an exact negation selects every document (:200-208). A negated group whose negation is not exact selects every document (:142-145).

The devil's-advocate check268 words

The strongest case for "intended": the setting is opt-in and new; the analyzer reads queries through the QueryVisitor, whose consumeTermsMatching is tagged @lucene.experimental (QueryVisitor.java:41-51); a clause that makes no reporting call cannot be seen by a visitor; a presearcher is a heuristic; and the query is degenerate, because its negated group matches no document.

Why it does not hold. The javadoc of the mode names its limits, and both go the other way, towards selecting more: inexact negations select the query for every document, and in a batch a term only excludes queries if every document contains it (TermFilteredPresearcher.java:63-67). A presearcher may select queries that do not match; a query it does not select is not run, so the heuristic has one direction. The two stock visit methods make no reporting call for a set without terms and for an automaton of the type NONE; the analyzer selects every document when a negated builder holds nothing at all (QueryAnalyzer.java:267-269), and loses the clause when another clause shares that builder. Whether the repair belongs in the analyzer or in the two visit methods is the maintainers' call (QueryVisitor#visitLeaf is documented as "Called by leaf queries that do not match on terms", QueryVisitor.java:53-58); in either reading the Monitor misses a match. The same builds report the match with the setting at 0, with MatchNoDocsQuery in the same place and when the clause is alone in the group. The query is accepted by Monitor.register, and a query string with an inverted range reaches the shape through the classic QueryParser.
