Since 9.0, ICUFoldingFilter turns ´ into a space inside the term: the build lets NFKC override Lucene's own folding tables

Since 9.0.0, ICUFoldingFilter indexes O´Brien in a keyword field as o brien instead of obrien, while ` and ^ are still removed. A 2021 build change passes the folding-data files to ICU's compiler sorted by name, so the standard NFKC data now overrides Lucene's own UTR#30 tables on 292 code points.

The bug in 30 seconds

#

The folding data is compiled from ICU's standard NFKC files plus Lucene's own tables, and when two files map the same character, the later file wins. Up to 8.x Lucene's tables came last, so they won. Since 9.0 they come first, so NFKC wins.

  1. You fold a keyword or whitespace-tokenized field with the default ICUFoldingFilter and index O´Brien, with an acute accent ´ (U+00B4) typed as an apostrophe.
  2. You expect the term obrien: Lucene's own table deletes ´ under "Remove diacritics", 8.11.4 gives obrien (older releases built the data in the same order), and the filter still deletes ` and ^, which the same rule lists.
  3. You get o brien, with a space inside the term, so it no longer matches obrien. ¨ ¯ ¸ ˘ ˜ and 23 more spacing accents do the same; through StandardTokenizer, カ゛ becomes カ .
  4. Why: ICU's gennorm2 compiles the folding data from ICU's 3 normalization files (nfc, nfkc, nfkc_cf) and Lucene's 5 tables, and a later file overrides an earlier one. Since 9.0.0 the build sorts the files by name, so Lucene's tables come first and NFKC's ´ -> space + accent wins.
  5. Net effect on main: Lucene's mappings for 292 code points are overridden, and 271 characters fold differently than under the pre-2021 order. About 240 of those are arguably better (modifier letters such as ʰ now fold to h instead of vanishing); the 31 that leave a space are not.

Who is affected

#

Users of the optional ICU module's ICUFoldingFilter, its factory or NORMALIZER with the default data, on 9.0.0 and later. The space appears when the accent stays inside a token: keyword or whitespace fields (O´Brien), or ゛ ゜ even with StandardTokenizer. Modifier letters such as ʰ changed too. Deterministic and silent; rare in practice.

Mechanism, terms and numbers682 words

ICUFoldingFilter folds with utr30.nrm, which the build compiles with ICU's gennorm2 from ICU's nfc.txt, nfkc.txt and nfkc_cf.txt and Lucene's five UTR#30 tables. When two files map the same character, the later file wins. Up to 8.11.4 the build passed the NFKC files first and Lucene's tables last; a 2021 build change (010e3a1ba96, LUCENE-9900, PR #61), meant to make regeneration incremental, sorts the files by name instead, which puts Lucene's tables first. Since 9.0.0 the NFKC mapping wins on all 292 code points both map; on main's data 271 of them fold differently than under the old order. Lucene's "Remove diacritics" rule deletes ´ ¨ ¯ ¸, but NFKC maps them to a space plus a combining mark, so with keyword or whitespace tokenization O´Brien is indexed as o brien, and through StandardTokenizer カ゛ becomes カ , while ` and ^ (no NFKC mapping) are still deleted. About 240 of the 271 changes (modifier letters such as ʰ -> h) are arguably improvements. Silent: no error, no release note, no test pins either behaviour. Restoring the documented order and keeping today's superscript and subscript folds changes 35 characters back and passes the module's tests.

Terms

#
  • utr30.nrm: the binary data behind ICUFoldingFilter.NORMALIZER (ICUFoldingFilter.java:69-77). The build compiles it with ICU's gennorm2 from eight text files in lucene/analysis/icu/src/data/utr30/: ICU's standard nfc.txt, nfkc.txt, nfkc_cf.txt, and Lucene's UTR#30 tables BasicFoldings.txt, DiacriticFolding.txt, DingbatFolding.txt, HanRadicalFolding.txt, NativeDigitFolding.txt.
  • Later file wins: ICU User Guide, "Mappings in one text file can override mappings in previous files of the same gennorm2 invocation." ICU's nfkc.txt:14: "Use this file as the second gennorm2 input file after nfc.txt."
  • The conflict: DiacriticFolding.txt:41 maps ´ to nothing (00B4>, under "## Remove diacritics", rule [:Diacritic:] >); nfkc.txt:24 maps it to space + combining acute (00B4>0020 0301), and the combining acute is then deleted, which leaves the space.

The bug

#
  1. build.gradle:92-94 sorts the inputs by file name ("gennorm generates file order-dependent output, so make it constant here.") and :122 passes them in that order. Upper case sorts first: Lucene's five tables, then nfc, nfkc, nfkc_cf.
  2. So for every character both sides map, NFKC's mapping wins: on main the stored mapping is NFKC's for all 288 conflicts whose two mappings differ (4 are identical); 271 of the 292 fold differently than Lucene's mapping would, 21 the same.
  3. From 2010 (LUCENE-1343) to the first gradle port (LUCENE-9767, February 2021) the build listed ICU's files first (nfkc nfkc_cf, with nfc added in front in 2012) and Lucene's tables last. Commit 010e3a1ba96 (LUCENE-9900, PR #61, 2021-04-02) replaced the list by the sort and committed the regenerated utr30.nrm; it changed no source table.
  4. The regeneration checksums store one hash per file and no order (the same commit created them), and no test asserts any of the changed characters, so nothing noticed.

Exposure and likelihood224 words
  • Who is exposed. ICUFoldingFilter, ICUFoldingFilterFactory (icuFolding) or ICUFoldingFilter.NORMALIZER with the default data, in the optional analysis-icu module, on every release from 9.0.0 to 10.5.2, branch_10_6 and main. Nothing to configure beyond choosing the filter; anything that wraps the filter gets the same terms.
  • Which text. A changed character must stay inside a token: keyword or whitespace tokenization (keyword-normalized fields; the factory's own javadoc example uses WhitespaceTokenizerFactory, ICUFoldingFilterFactory.java:29-35) of an acute typed as an apostrophe (O´Brien, don´t) or another spacing accent between letters; the spacing katakana marks ゛ ゜ even with StandardTokenizer or ICUTokenizer (カ゛ -> カ ); modifier letters (ʰ, ᵉ) with any tokenizer that keeps them in the token (StandardTokenizer and ICUTokenizer do). The default tokenizers split at the Latin spacing accents (O´Brien -> o, brien on main and 8.11.4).
  • What happens. The term differs from the accent-free spelling and from 8.x: a keyword field holding o brien does not match obrien, and an index folded with 8.x disagrees with 9.x query folding on these characters. The same analyzer at index and query time hides most of it.
  • Scale. Deterministic, any index size, no error; each changed code point maps to at most two UTF-16 chars.
  • How likely. Rare: no report was found in the searched sources since 9.0.0 (2021).

Why it is a bug, not intended

#
  • Lucene's own table deletes ´ ¨ ¯ ¸ ("Remove diacritics") and still deletes ` and ^; NFKC now overrides it on 292 code points.
  • Releases 3.1.0 to 8.11.4 passed ICU's files first and Lucene's tables last.
  • The 2021 change was a build cleanup; the only reply on the order came after the merge ("just my guess"); no release note mentions it.
The full argument284 words

Intent is not proven: the points below make an unintended precedence inversion likely, and the committers decide which folding semantics they want.

  • Lucene's table says delete. DiacriticFolding.txt:35-43: "## Remove diacritics", "# Rule: [:Diacritic:] >", 005E>, 0060>, 00A8>, 00AF>, 00B4>, 00B7..00B8>, 02B0..034E>; the javadoc lists "Diacritic removal" (ICUFoldingFilter.java:33). rmuir on LUCENE-1343 (2010): CARET "folds to CIRCUMFLEX ACCENT, which should be deleted as its [:Diacritic:]".
  • The tables were designed to sit on top of NFKC. Headings such as "## Spacing Accents folding (done by kd)" (BasicFoldings.txt:86) and a space rule that leaves out whatever NFKC_CF changes (:83); on LUCENE-3747 rmuir called the "additions to kd" sections "the mappings in utr30 minus what nfkc does".
  • The order was explicit for 11 years. The ant build (LUCENE-1343, 2010; nfc.txt added in front in 2012) and the first gradle port (LUCENE-9767, 2021-02-14) used nfc nfkc nfkc_cf then Lucene's tables.
  • The change was treated as a pure build change. 010e3a1ba96 touched only build files, two new checksum files and the binary (58,720 -> 59,200 bytes), no source table. In PR #61 dweiss asked: "gennorm seems to be order-sensitive - I changed the order to sorted file names ... Is this order somehow important? I can revert to what it was before but this way it's simpler." rmuir replied after the merge: "it is my understanding order doesnt matter ... this may cause a data file change even though semanticw are unchanged? just my guess", about chained mappings, not two files mapping one character.
  • Silent. No CHANGES or MIGRATE entry for 9.0.0; later ICU upgrades (#447, #13239, #14386, #15417) regenerated under the sorted order without mentioning it.
The devil's-advocate check306 words

The strongest case for "intended": the javadoc also lists "Spacing Accents folding", "Subscript folding" and "Superscript folding" and says text "is normalized to NFKC" (ICUFoldingFilter.java:47-49, :57); UTR#30 defines Spacing Accents folding as [KD] (space + mark) for 00AF, 00B4, 00B8, 02D8..02DD, ..., 309B..309C and Superscript folding as [KD] plus modifier letters, so today's output is what those foldings plus accent removal give, and 8.x's Mᵐᵉ -> m contradicted "Superscript folding". The order was discussed in review, and the file was regenerated twice since under the sorted order. Two more points weigh for keeping today's output: the text tables are not the public API and the javadoc specifies no precedence between files (at runtime the shipped utr30.nrm is the contract), and five years of stable 9.x-10.x output (33 release tags) plus the reindex cost make keeping it a legitimate compatibility choice.

What answers it: the PR merged with no answer on the order (its three reviews are comments with empty bodies); the only reply came four hours after the merge and rested on a guess that semantics were unchanged ("just my guess"), while the ICU page linked in that comment says the later file overrides; no comparison of the output is recorded in the PR or the later regenerations; nothing announced a change; the sorted order leaves Lucene's tables unable to override any mapping that NFKC also defines, which defeats their ability to tailor those; and one rule now gives two results (` ^ deleted, ´ ¨ ¯ ¸ -> space). The adjudication, the independent reproducer and the devil's advocate rejected the intended reading; a cross-model reviewer called the contract "genuinely ambiguous" but said a maintainer "cannot convincingly call the 2021 precedence change documented". It survives as a question of fix direction, which the recommended fix answers by keeping the superscript and subscript folds.

Suggested fix

#

Recommended A2. Restore the order and keep today's superscript and subscript folds

Restore the documented gennorm2 order in build.gradle (NFKC files first, Lucene's tables last), and take superscript and subscript letters out of the "Remove diacritics" rule so they keep today's folds. Regenerated with the build's own task: 35 characters change, all back to 8.x; all repros and the 165 ICU module tests pass.

A2. Restore the order and keep today's superscript and subscript folds (validated by the checks) (recommended)

#

Option A's build.gradle change (below), plus one rule line in DiacriticFolding.txt. With Lucene's tables last again, a character they do not map keeps its NFKC mapping, so taking superscript and subscript letters out of the deletion rule leaves them to NFKC, which folds them to their compatibility text (usually the base letter), as UTR#30's "Superscript folding" and "Subscript folding" (both in the javadoc, ICUFoldingFilter.java:48-49) describe. The regeneration rewrote that rule's generated range lines (+8/-12; +9/-13 with the rule line), the checksum file and utr30.nrm (61,776 -> 61,408 bytes).

Trade-offs

  • It edits a generated rule, so it fixes the regression and also settles the superscript direction; reviewers may want the two in separate commits.
  • It is a policy, not only an order repair: it exempts every character whose decomposition type is Super or Sub (some fold to two letters or to punctuation, such as U+107B7 -> ||), and later Unicode versions can add to that set.
  • U+FE4D..FE4F go back to deleted: Lucene's Underline line FE4D..FE4F>005E (BasicFoldings.txt:95, copied from UTR#30) maps them to ^, which is then deleted; changing it to 005F would keep _ (not run). U+037A stays deleted, as in 8.x.
  • Indexed terms change for the 35 characters; no CHANGES entry is drafted.

A. Restore the explicit, documented order only (validated by the checks)

#

B. Keep the NFKC precedence on purpose (not run)

#

Keep NFKC last, sorted or explicit, remove Lucene's mappings for the 292 code points that NFKC overrides, and decide the spacing-accent, U+0345 and U+037A cases explicitly.

Trade-offs

No indexed term changes, which respects five years of stable 9.x-10.x output; but the five current tables (all sorted before nfkc_cf.txt) cannot override any NFKC mapping, so the 31 space-in-term cases would need a new override file that sorts after nfkc_cf.txt, or an explicit order that ends with a Lucene file (ICU lets a later file override an earlier one); and "Remove diacritics" stops meaning what it says for those characters.

Downstream note

#

Search servers that expose this filter inherit the same 9.0 term change, so terms their users indexed before and after moving to Lucene 9 disagree on these characters.

How it was found

#

An exhaustive check of the compiled folding data against Lucene's source tables: a model of the compiler's later-file-wins rule matched the shipped file on every code point (algorithmic Hangul aside) and showed NFKC overriding Lucene's mappings for 292 code points. On main's data the pre-2021 order changes 271 characters; the 2021 commit alone changed 118.

The method in full147 words
  • Method (semi-formal): bounded-exhaustive translation validation of utr30.nrm against its source tables, in the hunt's unit on the UTR#30 data. An independent model of gennorm2's precedence (inputs in the build's sorted order, a later file overrides an earlier one) matched gennorm2's own combined output and the shipped utr30.nrm on all 1,114,112 code points, 0 mismatches (the raw comparison with the shipped file skips the algorithmic Hangul syllables), and showed that 292 code points mapped by Lucene's tables are overridden by the nfc/nfkc/nfkc_cf data.
  • Attribution. The finder rebuilt utr30.nrm with gennorm2 in the sorted order (byte-identical to the shipped file) and in the pre-2021 order, and compared the two over all code points: 271 fold differently, all deleted under the old order. The same comparison of the files on either side of 010e3a1ba96 gives 118.
  • Then a public-API JUnit on the stock jars, and independent checkers (see "Independent checks").

Bug record

#

LFV-857, snapshot of 2026-10-28

Registry title
Since 9.0 the utr30.nrm build passes gennorm2 its inputs sorted by file name, so the standard NFKC data overrides Lucene's own UTR#30 folding tables and ICUFoldingFilter turns spacing accents such as ´ ¨ ¯ ¸ into a space inside the term instead of removing them, while ` and ^ are still removed
Area
analysis / icu (ICUFoldingFilter UTR#30 folding data: the gennorm2 input order of the utr30.nrm regeneration step in lucene/analysis/icu/build.gradle, and the shipped utr30.nrm)
Priority
Low, rank 411: This silent 9.0 folding regression in the opt-in ICUFoldingFilter only shows when a spacing accent.
Impact class
silent wrong results
Impact note
Applications that use the optional analysis-icu ICUFoldingFilter, ICUFoldingFilterFactory or ICUFoldingFilter.NORMALIZER with its default data (no setting needed) get, on 9.0.0 and later, a different folded term than Lucene's own tables specify and than 8.11.x produced for 271 code points: a spacing accent that the tokenizer keeps inside a token (an acute used as an apostrophe in 'O´Brien' with keyword or whitespace tokenization, or the spacing katakana marks ゛ ゜ with StandardTokenizer or ICUTokenizer) becomes a space inside the term ('o brien', 'カ '), so the term no longer matches its accent-free spelling or terms folded by 8.x; nothing throws, no scale is needed, about 240 of the 271 changes (modifier letters such as ʰ -> h) are arguably improvements, and any fix changes indexed terms and needs a reindex note.
Summary
You normalize a keyword field with ICUFoldingFilter and index 'O´Brien' (an acute accent used as an apostrophe); you expect the term 'obrien', because Lucene's own folding table DiacriticFolding.txt deletes U+00B4 along with the other spacing diacritics, as every release up to 8.11.x did and as the filter still does for ` and ^. Since 9.0.0 the term is 'o brien': a 2021 build change (LUCENE-9900) started passing the data files to the gennorm2 compiler sorted by file name, which puts the standard NFKC files last, and in gennorm2 a later file overrides an earlier one, so ´ ¨ ¯ ¸ ˘ ˜ and other spacing accents now become a space and 236 modifier letters fold to their base letter instead of being removed. The change was meant only to make regeneration incremental and its review assumed the order did not matter; 292 entries of Lucene's tables are now dead, and 271 code points fold differently.
