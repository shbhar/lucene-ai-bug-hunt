Hunspell COMPLEXPREFIXES keeps stripping prefixes after the second one: three-prefix words pass and an empty prefix recurses until StackOverflowError

With a COMPLEXPREFIXES Hunspell dictionary (at most two prefixes per word), Lucene keeps stripping prefixes after the second: the three-prefix word cbax is accepted, and an empty prefix makes spell("bbx"), or stemming the correct word bx while indexing, recurse until StackOverflowError, which closes the IndexWriter. A one-line regression since 9.5.0.

The finding in 30 seconds

#

Under COMPLEXPREFIXES a word may carry two prefixes. After the Stemmer strips the second one, it is told to look for another prefix instead of a suffix, so it strips a third one, or the same empty prefix again and again.

Hunspell dictionaries in three steps

#
  1. A Hunspell dictionary is two files: the .dic lists roots with flags (x/A), the .aff lists affix rules per flag (PFX A 0 a . means: a root with flag A may take the prefix a, so x gives ax).
  2. Flags after a slash on a rule are its continuation class: PFX A 0 a/B . lets a prefix of class B go in front of a, so PFX B 0 b . gives bax. A 0 affix is the empty string.
  3. Normally a word may carry two suffixes and one prefix. COMPLEXPREFIXES swaps that: two prefixes and one suffix, never a third prefix.

The finding, step by step

#
  1. You load a dictionary with COMPLEXPREFIXES and chained prefixes: the root x takes a, a allows b in front of it, b allows c. So ax and bax are words; cbax would need three prefixes.
  2. You expect spell("cbax") to be false, as in native Hunspell 1.7.2 and Lucene 9.4.2. Instead it is true, getRoots("cbax") is [x], and the analysis lists two prefixes, c and a: the b silently disappears.
  3. A second dictionary makes the inner prefix empty: PFX A 0 0/B adds nothing and only lets b (PFX B 0 b) go in front. Now x and bx are words. spell("bbx") throws StackOverflowError, and so does getRoots("bx") of the correctly spelled bx, even on a 512 MB stack.
  4. With HunspellStemFilter in the analyzer, addDocument of the text bx throws the same Error: the IndexWriter closes itself, the next addDocument throws AlreadyClosedException, and only the 1 committed document survives.
  5. Why: after the second prefix the Stemmer sets doPrefix = true, under the comment "go look for another suffix", and looks for yet another prefix. A third prefix overwrites the second; an empty prefix leaves the word unchanged, so the same call repeats forever. Up to 9.4.2 the line was false.

Who is affected

#

Only applications that load a custom Hunspell dictionary with COMPLEXPREFIXES and chained prefix rules (spell checking, getRoots, analyzeSimpleWord, HunspellStemFilter); no surveyed public dictionary has that shape. Once it is loaded, ordinary short tokens trigger it: silent over-stemming, or a StackOverflowError that closes the IndexWriter or fails the query parse. Affected: 9.5.0 to 10.6.0 and main.

Mechanism, terms and numbers1,011 words

COMPLEXPREFIXES switches Hunspell to "twofold prefix stripping (but single suffix stripping)" (hunspell(5), 1.7.2): a word may carry at most two prefixes. In Stemmer.applyAffix, the branch that runs after the second prefix has been stripped sets doPrefix = true (Stemmer.java:639-641 on main 645d4fe14a20), although the comment beside it says "we took away the second prefix: go look for another suffix". So removeAffixes looks for yet another prefix. A third prefix overwrites the inner-prefix slot, the recursion depth is recomputed from the slots and stays 1, and the same branch runs again. With prefixes a, b, c chained on root x, spell("cbax") is true and getRoots("cbax") is [x]. With a zero-length prefix (PFX A 0 0/B), stripping it returns the same word, so the call repeats with identical arguments until StackOverflowError: spell("bbx"), and getRoots("bx") of the correctly spelled bx, overflow, also on a 512 MB stack. Inside IndexWriter.addDocument the Error closes the writer. Lucene up to 9.4.2 had doPrefix = false here, and native Hunspell rejects both words without error. The change came with #975 (LUCENE-10626, a feature PR, "add tools to aid dictionary editing"); setting the line back to false fixes both symptoms and keeps all existing hunspell tests green.

Terms

#
  • Outer / inner prefix (Lucene's naming): the outer prefix is written first and stripped first (b in b+a+x); the inner prefix is the one next to the root (a).
  • COMPLEXPREFIXES: hunspell(5) (1.7.2) "Set twofold prefix stripping (but single suffix stripping) eg. for morphologically complex languages with right-to-left writing system"; "Zero stripping or affix are indicated by zero". Lucene's parser maps a 0 affix to the empty string (Dictionary.java:743-746).

Mechanism (main 645d4fe14a20, Stemmer.java)

#
  1. removeAffixes (:390) tries every prefix that matches the start of the word, skipping only the one equal to outerPrefix (:420), and calls applyAffix (:431). stripAffix returns the same array when the rule strips nothing (:524), so an empty prefix leaves word, offset and length unchanged.
  2. applyAffix (:588) stores the first prefix in outerPrefix and every later one in innerPrefix (:603-604), so a third prefix overwrites the second. It looks the rest up as a root (:612), then decides whether to recurse:
int recursionDepth =
    (outerSuffix >= 0 ? 1 : 0) + (innerPrefix >= 0 ? 2 : outerPrefix >= 0 ? 1 : 0) - 1;   // :619-620
if (dictionary.isCrossProduct(affix) && recursionDepth <= 1) {                            // :621
  ...
  } else {
    if (prefix && dictionary.complexPrefixes) {
      doPrefix = true;                                   // :640  the bug
      // we took away the second prefix: go look for another suffix
    } ...
  return removeAffixes(word, offset, length, doPrefix, outerPrefix, innerPrefix, outerSuffix, processor); // :650
  1. After two prefixes the depth is 0 + 2 - 1 = 1; after a third it is still 1, because it is computed from the two slots, not counted. doPrefix = true makes removeAffixes look for another prefix, so the step repeats while some prefix other than outerPrefix matches.
  2. cbax: c becomes the outer prefix, b the inner one, then a overwrites b, leaving x. The root carries the last affix's flag A (:269), and the outer-prefix check (:271-277) is skipped because there is an inner prefix: accepted, reported as prefixes [C, A].
  3. bbx: b is the outer prefix, leaving bx; the empty A is the inner one, word still bx; depth 1, doPrefix = true; the empty A matches again (it is not outerPrefix), strips nothing and calls applyAffix with exactly the same arguments, forever. For bx, the root x is found on the way: spell() stops at the first root (Hunspell.java:179-181), so it returns true, but getRoots and analyzeSimpleWord collect every analysis and overflow.
  4. Before #975 (9.4.2 Stemmer.java:601-623) this branch set doPrefix = false and recursed with an explicit recursionDepth + 1, so after the second prefix only a suffix was tried and depth 2 never recursed again. #975 replaced the explicit depth with the slot formula and flipped the line to true.

A third shape

#

A prefix rule that strips more than it adds (PFX B ab 0: removing it puts ab back) makes the candidate word grow level after level only if it can be stripped again and again, which after the second prefix means as the inner prefix. In the study's simple dictionary of this kind (PFX A 0 0/B, PFX B ab 0) it is not: B becomes the outer prefix, which is never stripped again (:420), so the word stays abx and the stack overflows through the same empty-prefix loop as bbx, at every stack size up to 64 MB (an instrumented copy of the Stemmer measured a longest candidate of 3 characters). The fuzzer-found dictionary has several prefix rules of one class (W), among them PFX W uob 0, which strips letters and adds none; there the word does grow: to 5,042 characters before StackOverflowError on a 1 MB stack, to 55,745 before OutOfMemoryError on an 8 MB stack. On stacks of 8 MB or more it ended in OutOfMemoryError: Java heap space (1 GB heap) in 21 of 22 calls; the 22nd (10.5.2, 8 MB stack) ended in StackOverflowError after 7 s. With the fix every probe returns normally.

Why it looks unintended

#
  • The changed line sits under the comment "go look for another suffix"; up to 9.4.2 it was false.
  • hunspell(5) defines COMPLEXPREFIXES as twofold prefix stripping; native Hunspell rejects cbax and bbx without error.
  • Lucene's own API says two: AffixedWord.getPrefixes() returns "at most two", and the word-form generator from the same PR never produces cbax.
The full argument262 words
  • The comment beside the line. Stemmer.java:639-641: doPrefix = true; // we took away the second prefix: go look for another suffix. git blame gives the comment to LUCENE-5483 (2014) and the true to #975 (2022).
  • The format's contract. hunspell(5) (the 1.7.2 manual page): "COMPLEXPREFIXES Set twofold prefix stripping (but single suffix stripping)". C Hunspell 1.7.2 and 1.3.2 reject cbax and bbx and do not crash.
  • Lucene's own statements of the limit. AffixedWord.getPrefixes(): "@return the list of prefixes applied to the stem, at most two, outermost first" (AffixedWord.java:54, added by the same #975 commit). The generator from #975 refuses a third affix of a kind (if (size == 2) return false;, now WordFormGenerator.java:376): getAllWordForms("x") is [ax, bax, x]. The Dictionary comment: "2-stage prefix+1-stage suffix instead of 2-stage suffix+1-stage prefix" (Dictionary.java:368-370). CHANGES for LUCENE-5483: "COMPLEXPREFIXES now work correctly according to the hunspell algorithm". Robert Muir on #6547 (2014): with COMPLEXPREFIXES "max 2 prefixes, max 1 suffixes".
  • Nothing in #975 points to an intended change in stemming. It is listed under 9.5.0 "New Features" as "Hunspell: add tools to aid dictionary editing: analysis introspection, stem expansion and stem/flag suggestion"; it adds no COMPLEXPREFIXES test, and its review never mentions the Stemmer or doPrefix. The only upstream COMPLEXPREFIXES test (TestComplexPrefix) covers one and two prefixes and passes with and without the fix.
  • Lucene claims native behaviour. Hunspell "can be used in place of native Hunspell for many languages"; its listed exceptions (Hungarian, characters outside the BMP, PHONE) do not include COMPLEXPREFIXES.
The devil's-advocate check117 words

The strongest case for "intended": doPrefix = true was a deliberate step towards longer prefix chains, and the Java API itself never promises a two-prefix limit.

Why it fails: the comment was kept unchanged; the same commit documents "at most two" prefixes in AffixedWord and caps its generator at two; the two slots (outerPrefix, innerPrefix) cannot even represent a third prefix, which is why cbax is reported as [C, A]; native Hunspell rejects these words; and a recursion that never ends on a five-line dictionary cannot be a design choice. An independent reviewer from another model family (OpenAI GPT-5.6) and an intended-behaviour devil's advocate both rated the "intended" case weak. Verdict: a regression.

Trade-offs

  • None known for correct dictionaries; it only removes recursion. No benchmark was run.
  • Dictionaries that relied on three-prefix words since 9.5.0 lose them (native Hunspell never accepted them); an index built with HunspellStemFilter on an affected version keeps such words stemmed until reindexed.
  • It does not fix the sibling LFV-642 (isAffixCompatible, Stemmer.java:566), and LFV-642's fix does not fix this one.

Downstream note

#

A product that lets less-trusted users install their own Hunspell dictionaries and then analyzes other users' text with them would inherit the crash; Lucene treats the dictionary as trusted configuration.

How it was found

#

Coverage-guided fuzzing (Jazzer) of Lucene's Hunspell code with .aff/.dic files built from a grammar: 941,807 runs in about 21 minutes gave 11 crash reports, all in the Stemmer's affix recursion. They were minimised by hand, compared with native Hunspell and turned into a public-API JUnit on the stock jars.

The method in full133 words

Method: coverage-guided fuzzing (the hunt's non-formal tier; the secondary method of the hunspell hunt unit). A Jazzer target built .aff/.dic pairs from a grammar and called spell() and suggest(); a sibling compound-pattern fix was shadowed so that bug would not mask others.

  • 941,807 runs in 1,235 s gave 11 crash reports (10 StackOverflowError, 1 OutOfMemoryError), all in Stemmer.removeAffixes / applyAffix. Replay: 11 of 11 crash without the fix, 0 of 11 with it.

  • While verifying it, the intended-behaviour devil's advocate noticed a second regression from the same commit (spell("cax")), now the separate LFV-642.

LFV-375, snapshot of 2026-11-08

Registry title
Hunspell COMPLEXPREFIXES: after removing the second prefix the Stemmer keeps removing prefixes, so words with three prefixes are accepted and a zero-length prefix recurses until StackOverflowError (also in HunspellStemFilter, where it closes the IndexWriter)
Area
analysis / hunspell (Stemmer affix removal)
Priority
Low, rank 690: With a custom COMPLEXPREFIXES dictionary that chains prefixes, ordinary tokens throw StackOverflowError and close the IndexWriter, the same custom-config writer-closing profile as LFV-121 and LFV-281.
Impact class
crash
Impact note
Only applications whose hunspell dictionary combines COMPLEXPREFIXES with chained prefixes (prefix continuation classes) are hit: with three chained prefixes, spell(), getRoots() and HunspellStemFilter silently accept and stem words that need three prefixes, and with a zero-length chained prefix ordinary tokens (even a correctly spelled word, once it is stemmed) make spell(), suggest(), getRoots(), analyzeSimpleWord() and HunspellStemFilter throw StackOverflowError, which inside IndexWriter.addDocument closes the writer (committed data stays intact, uncommitted documents are lost) and in a query analyzer fails the query parse; no surveyed public dictionary has this shape.
Summary
You load a hunspell dictionary that sets COMPLEXPREFIXES (twofold prefix stripping, meant for morphologically complex right-to-left languages) and chains prefixes through continuation classes, and expect at most two prefixes per word, as hunspell(5), C Hunspell and Lucene up to 9.4.2 do. Instead, after removing the second prefix the Stemmer goes on removing prefixes: with prefixes a, b, c chained on root x, the three-prefix word cbax is accepted by spell() and stemmed to x, and with a zero-length prefix that only passes on a flag (PFX A 0 0/B), the same prefix is removed again and again without shortening the word, so spell("bbx"), getRoots("bx") and HunspellStemFilter throw StackOverflowError. Inside IndexWriter.addDocument that Error closes the writer, and every later addDocument throws AlreadyClosedException.
