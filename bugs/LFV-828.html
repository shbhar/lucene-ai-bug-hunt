All bugs · Lucene bug · LFV-828 · intervals-overlap-filters-skip-disjunction-rewrite

Intervals.overlapping, nonOverlapping and notWithin skip the disjunction rewrite, so a word can be both within and not within n positions of or(york, "new york")

With the default Intervals.or(), containedBy and within check every alternative of an or() reference, but overlapping, nonOverlapping and notWithin see only its minimal matches. So on "visit new york", within(visit, 1, or(york, "new york")) and the same notWithin both match the same word, silently, since 8.1.0.

The bug in 30 seconds

#

An interval query can filter a source by a reference such as or(york, "new york"). Because or() keeps only minimal matches, LUCENE-8477 (8.1.0) made several operators split such a reference into one filter per alternative. containedBy and within split it that way; overlapping, nonOverlapping and notWithin do not.

  1. Index one document, "visit new york" (visit = position 0, new = 1, york = 2), and use the reference R = or(york, "new york"), built with the default Intervals.or.
  2. within(visit, 1, R) finds 1 hit: visit is right before "new york". You expect notWithin(visit, 1, R) to find 0, since the two are documented as opposites; with R = "new york" alone they give 1 and 0.
  3. Instead notWithin(visit, 1, R) also finds 1 hit, the same word [0,0]. Read as one source, the default or() keeps only minimal matches: "new york" [1,2] contains york [2,2] and is dropped, so notWithin sees only york, 2 positions away. within splits R and checks each alternative.
  4. The filters also disagree on "new york": containedBy(new, R) = 1 but overlapping(new, R) = 0 and nonOverlapping(new, R) = 1, while maxgaps(0, overlapping(new, R)), which can only remove intervals, gives 1. With or(false, ...) every relation agrees.

Who is affected

#

Anyone calling overlapping, nonOverlapping or notWithin, or the fn: query-text forms, with a default or() reference whose alternatives contain one another, such as a word and a phrase ending in it. Default settings, every release since 8.1.0. overlapping misses hits; the two exclusion filters keep hits they should drop.

Mechanism, terms and numbers655 words

Intervals queries can filter a source by a reference that is an or() of alternatives. The default Intervals.or() keeps only minimal intervals, so an alternative such as "new york" [1,2] is dropped when it contains another one, york [2,2]. Since LUCENE-8477 (8.1.0), containedBy and therefore within pull such a reference apart and test every alternative; overlapping, nonOverlapping and notWithin were built without that rewrite and read the minimized or(). For one and the same reference the relations then contradict each other: on "visit new york", within(visit, 1, or(york, "new york")) and notWithin(visit, 1, or(york, "new york")) both return visit; on "new york", containedBy(new, R) matches but overlapping(new, R) does not, nonOverlapping(new, R) keeps new, and maxgaps(0, overlapping(new, R)) matches again because the nested form does split the reference. The same happens from fn: query text. With or(false, ...) every relation agrees. Every release from 8.1.0 to 10.5.2, branch_10_6 and main is affected; 8.0.0 is consistent. Rewriting the disjunctions in the three factories (for overlapping on both operands, as its nested form already does) fixes it and passes the queries and queryparser test suites.

Terms

#
  • Interval: the positions a source matches, [start,end]. In "visit new york", york is [2,2] and the phrase "new york" is [1,2].
  • Minimal intervals: the default Intervals.or() drops an interval that contains another interval of the same or(). So or(york, "new york") yields only york [2,2] on "visit new york".
  • Disjunction rewrite (LUCENE-8477, 8.1.0): for operators where that loses matches, Lucene builds one copy of the operator per alternative and ORs the copies (Disjunctions.pullUp). Alternatives with minExtent() 1 are grouped into one or(); extend raises the extent, so within / notWithin with n >= 1 split even an or() of single words. or(false, ...) turns the rewrite off; the javadoc offers it for when you "care more about speed than about accuracy".
  • The relations: within(x, n, r) = containedBy(x, extend(r, n, n)); notWithin(x, n, r) = nonOverlapping(x, extend(r, n, n)); overlapping(x, r) keeps x intervals that overlap an r interval.

On "visit new york" with R = or(york, "new york"):

  1. within(visit, 1, R) tests visit [0,0] against extend(york) = [1,3] and extend("new york") = [0,3]. The second contains it: 1 hit.
  2. notWithin(visit, 1, R) reads extend(R) as one source. The minimized or() yields only york, widened to [1,3], which does not touch visit [0,0]: visit is kept, 1 hit.
  3. On "new york", overlapping(new, R) compares new [0,0] with york [1,1] only: 0 hits, although new overlaps the alternative "new york" [0,1], which containedBy(new, R) finds. nonOverlapping(new, R) and notWithin(new, 0, R) keep new.
  4. maxgaps(0, overlapping(new, R)) asks its source for its alternatives (FilteredIntervalsSource.java:31-36), which splits the reference: 1 hit. A filter that can only remove intervals adds one.
  5. With or(false, ...) nothing is split anywhere, every relation sees york only, and they agree: within 0, notWithin 1, containedBy 0, overlapping 0.

The same holds without a single-word alternative: with or("new york", "new york city") on "new york city hall", within(hall, 1, ...) and notWithin(hall, 1, ...) both match, because "new york city" [0,2] contains "new york" [0,1] and is dropped for notWithin.

  • Who. Callers of Intervals.overlapping, Intervals.nonOverlapping and Intervals.notWithin, and of fn:overlapping, fn:nonOverlapping and fn:notWithin in the flexible StandardQueryParser, whose reference is a default Intervals.or() with alternatives that contain one another: a word and a phrase that starts or ends with it (york / "new york"), or a phrase and a longer phrase ("new york" / "new york city"). Synonym or place-name lists can have this shape.
  • Settings. Default IndexWriterConfig settings and codec and a plain IndexSearcher, with StandardAnalyzer or the test framework's MockAnalyzer; assertions on and off. Every run used one-document indexes; the mechanism works per document, so index size should not matter (reasoning, not run). The rewrite is on by default (Intervals.or(...) = or(true, ...)).
  • Effect. Silent wrong match sets in both directions: overlapping misses documents (0 instead of 1 on "new york"); nonOverlapping and notWithin used as exclusion filters keep documents they should drop (1 instead of 0 on "visit new york" and on "new york city hall"). Adding an alternative to the reference removes overlapping hits and adds nonOverlapping / notWithin hits, and wrapping the filter in maxgaps or phrase adds hits back.
  • Not affected. References with one alternative, or()s of single words (two different single-position intervals never contain one another, so the minimized or() drops nothing: 0 violations in 1,452 relation checks over all 363 documents of up to 5 words, executed), or(false, ...), and within / containedBy themselves.
  • How likely. Rated rare: it needs one of these three filters, a reference whose alternatives contain one another, and text where only the longer alternative decides. No report was found since 8.1.0 (2019). For such a query and document the wrong answer comes every time. The intervals package is marked experimental.
  • Workaround on stock Lucene. Spell the alternatives out with the public factories, the structure the fix builds: or(overlapping(x, york), overlapping(x, "new york")) (1 on "new york"), nonOverlapping(nonOverlapping(x, york), "new york") (0) and notWithin(notWithin(visit, 1, york), 1, "new york") (0 on "visit new york"), all executed on main. Or use or(false, ...) everywhere for consistent minimized answers.
  • Downstream (code and documentation reading only, not executed). Elasticsearch's intervals query builds any_of with Intervals.or and its overlapping / not_overlapping filters with Intervals.overlapping / Intervals.nonOverlapping; Solr's intervals query parser exposes within, not_within, overlapping, not_overlapping and any_of.

Why it is a bug, not intended

#
  • The javadoc: within returns intervals that "appear within" n positions of the reference, notWithin those that "do not appear within" them; LUCENE-8629 added within as the "inverse" of notWithin.
  • The default or() is the mode the javadoc presents as accurate, yet only or(false, ...) answers consistently.
  • Under maxgaps, which rewrites its child, overlapping(new, R) finds the match it misses alone.
The full argument429 words
  • Documented as opposites. Intervals.java:500: within "Returns intervals of the source that appear within a set number of positions of intervals from the reference"; :485: notWithin "Returns intervals of the minuend that do not appear within a set number of positions of intervals from the subtrahend query". fn:notWithin: "Matches intervals of the source that do not appear within the provided number of positions from the intervals of the reference". LUCENE-8629 (#9675) proposed within and overlapping as the "inverse of the already available NOT_WITHIN" and "NOT_OVERLAPPING". The repro uses single-position sources, so the separate question of a partly-near multi-position interval (LFV-830) does not arise.
  • Set logic. containedBy ("appear within intervals of the big query", :554) implies overlapping ("overlap with intervals from another source", :473; fn:overlapping: "overlap with at least one interval of the reference") and excludes nonOverlapping ("do not overlap with intervals from the subtrahend", :462).
  • The default is the mode the javadoc presents as accurate. The class note, written about gap-sensitive sources ("e.g. PHRASE and MAXGAPS"), says the rewrite ensures documents "are matched" and "if you care more about speed than about accuracy you can use" or(false, ...) (:47-54); or(false, ...) "can miss valid hits due to minimization" (:131). LUCENE-8477's CHANGES entry: "Interval disjunctions could miss valid hits if some of the clauses of the disjunction are minimized away". Here the default is the inconsistent path. The note does not promise in so many words that every top-level relation expands its operands; a maintainer may read it that narrowly.
  • The same filter answers differently under a parent. maxgaps(0, overlapping(new, R)) and phrase(overlapping(new, R), york) match "new york" although overlapping(new, R) alone has no interval there. maxgaps and phrase rewrite their child at construction, as documented for gap-sensitive sources, so the difference itself is expected from the design; what it shows is that the module's own expansion finds a hit that the top-level filter misses.
  • Maintainers on the rewrite (#10244): romseygeek, "Intervals automatically rewrite disjunctions (and have done since LUCENE-8477) so that queries behave as your or I would expect them to"; jimczi, "If it's not correct, it's a bug, not a feature".
  • Tests. No upstream test uses these filters with a reference whose alternatives contain one another: TestDisjunctionRewrites has no case for them, and the other uses (in TestIntervals, TestIntervalQuery, the match-highlighter tests and TestStandardQPEnhancements) have a single word, a phrase, an ordered / unordered pair, an extend, or an or() of single words (single words never contain one another, so minimization drops nothing there).
The devil's-advocate check357 words

Intervals use minimal-interval semantics ("These sources implement minimum-interval algorithms", Intervals.java:43), under which or(york, "new york") is york. The rewrite is documented for gap-sensitive sources ("e.g. PHRASE and MAXGAPS"); LUCENE-8477's commit message lists PHRASE, MAXGAPS and the four containment filters, not the overlap filters. In its review jimczi wrote "I am not sure if the rewriting should be the default option since minimum interval semantic is the basis of the paper", and earlier in #9523 "IMO we should document this unintuitive behavior rather than rewriting all queries in a non-optimal form". The fn: docs say "the algorithm is not required to return or highlight all matching interval alternatives", and the package is experimental. Two narrower readings follow: the nested-versus-top-level overlapping difference is the documented construction-time rewrite of gap-sensitive parents at work, and standalone overlapping / nonOverlapping are complementary over the minimized reference.

Why it fails: that explains overlapping or nonOverlapping taken alone, not the contradiction. within itself uses the non-minimized alternatives, so under either reading one of within and notWithin is wrong, and with or(false, ...) everything agrees, so the inconsistency lives only on the default path. romseygeek answered jimczi in the same thread ("I think we still need to make it possible to get accurate hits", "My suggestion is that we automatically rewrite things to match accurately"), and the rewrite was committed that way; #10244 later defends it. The fn: caveat is about which intervals a matching document returns or highlights; this bug changes which documents match, and notWithin returns an extra interval rather than missing one. Both earlier cross-model reviews rated the argument moderate and rejected it, and the intended-behaviour checker built it and rejected it. The cross-model fact check (reading only) rated the intended reading weak for within / notWithin and strong for the two narrower cases taken alone. A maintainer could still choose either consistent fix (rewrite the overlap filters, or minimize in within / containedBy too, which would undo LUCENE-8477), which is why the adjudication's confidence is medium. Lead a filing with the within / notWithin case; bring in the nested-versus-top-level overlapping case as support and present nonOverlapping as a consequence.

Suggested fix

#

Recommended A2. Rewrite the reference in overlapping, nonOverlapping and notWithin, and the source too in overlapping

Rewrite the disjunctions in the three factories: overlapping is built as its nested form already is (one filter per pair of source and reference alternatives, ORed); nonOverlapping / notWithin chain one exclusion per reference alternative (+20/-4 in Intervals.java). The repro, 1,093 upstream tests and a nested-case guard test pass.

A2. Rewrite the reference in overlapping, nonOverlapping and notWithin, and the source too in overlapping (validated by the checks) (recommended)

#

In Intervals.java (+20/-4): overlapping is built exactly as its nested form already is (OverlappingIntervalsSource.pullUpDisjunctions): one OverlappingIntervalsSource per combination of a source alternative and a reference alternative, ORed. So top-level and nested overlapping agree on both operands. nonOverlapping and notWithin become a chain of one NonOverlappingIntervalsSource per reference alternative ("overlaps no alternative"), the AND that the LFV-291 fix also uses for notContainedBy. A reference with nothing to split gives one filter, as before, and or(false, ...) is never split. Trade-offs

  • Like every LUCENE-8477 rewrite it trades speed for accuracy (not benchmarked): overlapping builds one filter per combination of source and reference alternatives, each with its own iterators; the nonOverlapping / notWithin chain builds the minuend iterator once, plus one iterator per reference alternative.
  • Expansion limit: A2's overlapping uses the list pull-up, which throws IllegalArgumentException("Too many disjunctions to expand") above IndexSearcher.getMaxClauseCount() combinations, as the nested form and phrase already do. Top-level overlapping over an or() of 1,025 phrases now throws where stock main builds it (executed; maxgaps(0, ...) of it throws on stock main too). The chain uses the single-source pull-up, which has no limit, like containedBy and notContainedBy today.
  • The chain's order is a hash set's iteration order, so toString, equals and hashCode of the chain depend on it, though results do not (NON_OVERLAPPING(NON_OVERLAPPING(xx,EXTEND(bb,1,1)),EXTEND(aa,1,1)), executed); a PR could sort the alternatives (reasoning, not run).
  • It changes results for existing queries (that is the fix): top-level overlapping with a disjunctive source or reference, nonOverlapping / notWithin with a disjunctive reference. The source side of nonOverlapping / notWithin needs no split at the document level: if a longer source interval overlaps nothing, the shorter one inside it overlaps nothing either (reasoning, not run).

How it was found

#

Semi-formal. An AI tool ran Lucene's real interval sources against relation laws that need no reference implementation (each interval is either within or not within a reference; containedBy implies overlapping) over every document of up to 5 positions, with the known interval fixes shadowed. The remaining violations were reduced by hand to a public-API JUnit.

The method in full186 words

Method: reference-free law checking (translation validation) of the real jar, the hunt's semi-formal tier: no model checker, solver or prover produced the signal.

  • The harness ran real interval sources on an index of all 1,364 documents of up to 5 positions over a 4-letter alphabet and checked laws that need no reference semantics: each minimal interval of X is returned by exactly one of a relation and its negation; containedBy(X, Y) is a subset of overlapping(X, Y); or() is commutative and idempotent.
  • Bounded-exhaustive over a 116-shape pool (116 x 116 pairs), plus 30,000 random depth-3 pairs per random leg, with the known interval fixes shadowed (the LFV-287 and LFV-291 sketches and seven earlier switches), so only new violation classes remained.
  • The residual class "within and notWithin both return an alternative's interval" and the inclusion-law failures were reduced by hand to the public-API JUnit; with the fix added, both classes disappear from every leg.
  • An earlier unit of the hunt had noted the nonOverlapping half alone and judged it a design question; the complement and inclusion laws turn it into a contradiction between documented relations.

LFV-828, snapshot of 2026-10-29

Registry title
Intervals.overlapping, nonOverlapping and notWithin read a disjunctive reference through the minimized or(), while containedBy and within test every alternative, so for the reference or(york, "new york") the same interval is reported both within and not within n positions of it, and containedBy(new, ref) matches 'new york' where overlapping(new, ref) does not
Area
queries / intervals (overlap filters Intervals.overlapping / nonOverlapping / notWithin vs the LUCENE-8477 disjunction rewrite that containedBy and within apply to their reference)
Priority
Low, rank 230: Needs an overlap filter with an or() reference whose alternatives contain one another, a rare query shape.
Impact class
silent wrong results
Impact note
Anyone who calls Intervals.overlapping, Intervals.nonOverlapping or Intervals.notWithin (or writes fn:overlapping / fn:nonOverlapping / fn:notWithin for the flexible StandardQueryParser) with a default Intervals.or() reference whose alternatives contain one another, such as or(york, "new york") or or("new york", "new york city"), with default writer, codec, analyzer and searcher settings, at any index size, with -ea and -da, in every release from 8.1.0 to 10.5.2 and on main and branch_10_6, silently gets match sets that contradict the containment filters over the same reference: overlapping misses hits that containedBy and within find, and nonOverlapping / notWithin keep intervals that lie inside or next to the longer alternative, so an exclusion filter lets through documents it should drop; single-alternative references and or(false, ...) give consistent answers [exec: the controls]; downstream intervals queries that build any_of with Intervals.or and offer overlapping / not_overlapping filters reach the same factories [read by the finder in Elasticsearch's IntervalsSourceProvider; not executed].
Summary
You index 'visit new york' and run within(visit, 1, R) and notWithin(visit, 1, R) with R = or(york, "new york"), and you expect exactly one of them to return 'visit', because the javadoc defines notWithin as the intervals that do not appear within n positions of the reference. Instead both return the same interval [0,0]: within is built on containedBy, which pulls the or() apart (LUCENE-8477) and sees 'new york' right next to 'visit', while notWithin, overlapping and nonOverlapping read the default or() as one minimized source, which drops 'new york' because that interval contains 'york'. In the same way containedBy(new, R) matches 'new york' but overlapping(new, R) does not, and maxgaps(0, overlapping(new, R)) does match, because the nested form does pull the reference apart.
