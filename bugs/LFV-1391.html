A block that IndexWriter rejects at a child leaves deleted children that the next block's parent adopts in block joins

When addDocuments rejects a block at a child, the children it already numbered stay in the segment as deleted documents, and ToParentBlockJoinQuery joins them to the next block's parent. Counting parents of red children then gives 1 instead of 0, from 5.3.0 through main, with default settings.

The finding in 30 seconds

#

A rejected block's already-numbered children stay in the segment as deleted documents, and its parent never gets a doc ID. The next block lands right behind them, and ToParentBlockJoinQuery joins a deleted child to that block's parent because its scorer does not check whether a child is live.

Background in three steps

#
  1. Block join: you index a parent with its children as one block, addDocuments([child, child, parent]). The block gets consecutive doc IDs, children first, the parent last.
  2. ToParentBlockJoinQuery(childQuery, parentsFilter, scoreMode) finds matching children and returns their parents. The parent of child d is the next document after d whose parent bit is set.
  3. addDocuments is atomic: "an external reader will see all or none of the documents". If one document fails, for example with a term longer than 32,766 bytes, it throws IllegalArgumentException and the writer stays open.

The finding, step by step

#
  1. Add block A = [red child, child with a 32,767-byte term, parent]. addDocuments throws the documented IllegalArgumentException; the writer stays open.
  2. Add block B = [blue child, parent], open a reader and count ToParentBlockJoinQuery(color:red, parents, ScoreMode.None). You expect 0: the only red child was in block A, which no reader should see.
  3. You get 1. A's first two documents kept doc IDs 0 and 1 as deleted documents, A's parent never got one, and B took docs 2 and 3. The join maps red child 0 to the next parent, doc 3, without checking that child 0 is live.
  4. The same index gives wrong hits under every ScoreMode when the join is a clause of a BooleanQuery, a block-join sort value of 1 instead of 50, and an index that CheckJoinIndex rejects. It lasts until a merge rewrites the segment.

Who is affected

#

Applications that filter or count parents with ToParentBlockJoinQuery after a block is rejected before its parent's filter term was indexed (usually at a child): a term over 32,766 bytes, a doc-values type conflict, an analyzer or Iterable exception. Default settings suffice. It affects count(), ScoreMode.None, the join inside a BooleanQuery and block-join sort values until a merge.

Mechanism, terms and numbers863 words

IndexWriter.addDocuments promises that a reader sees all or none of a block. When a child of the block fails with a non-aborting exception (the documented IllegalArgumentException for a term longer than MAX_TERM_LENGTH, a doc-values type conflict, an analyzer or Iterable exception), DocumentsWriterPerThread marks the members it had already numbered as deleted but leaves them in the in-memory segment, and the block's parent, which comes last, never gets a doc ID. The next block lands directly behind those deleted documents. ToParentBlockJoinQuery maps a child match to the next parent bit without checking that the child is live, so the rejected block's child is joined to the next block's parent: count() under every ScoreMode, ScoreMode.None searches and the join as a BooleanQuery clause return a parent that has no matching child, ToParentBlockJoinSortField takes the deleted child's value, and CheckJoinIndex rejects the index. A failure at the parent does the same when it comes before the parent's parent-filter term is indexed. Default settings suffice; it lasts until a merge rewrites the segment, and it is present from 5.3.0 through main.

The mechanism (main 5adff78bb168)

#
  1. IndexWriter.addDocuments goes to DocumentsWriterPerThread.updateDocuments, which numbers each block member before indexing it: reserveOneDoc(); ... indexingChain.processDocument(numDocsInRAM++, doc, isLastDoc);, with the comment "Even on exception, the document is still added (but marked deleted)" (DocumentsWriterPerThread.java:283-293).
  2. The second child's term exceeds MAX_TERM_LENGTH (32,766 bytes) and throws IllegalArgumentException (IndexWriter.java:1480-1481). On this non-aborting failure the finally block calls deleteLastDocs(numDocsInRAM - docsInRamBefore) (DocumentsWriterPerThread.java:302-306), which only records doc IDs 0 and 1 as deleted (:399-405). Both stay in the in-memory segment; the parent was never reached, so it has no doc ID and no parent bit.
  3. Block B goes to the same in-memory segment and gets docs 2 and 3.
  4. IndexSearcher.count asks for no scores, so the join runs with ScoreMode.None internally (ToParentBlockJoinQuery.java:98), and ScoreMode.None uses the default bulk scorer over BlockJoinScorer (:167-172). That scorer gets no live docs: "acceptDocs applies (and is checked) only in the parent document space" (:141-142), "the responsibility to not match deleted docs is on the scorer" (:150-151), new BlockJoinScorer(childScorerSupplier.get(leadCost), parents, scoreMode) (:162).
  5. ParentApproximation.advance maps child match d to parentBits.nextSetBit(d + 1) (:261) without checking that d is live: deleted red child 0 maps to parent 3, which is live, so it is counted.
  6. Top-level Avg/Max/Min/Total searches use BlockJoinBulkScorer, which passes acceptDocs to the child bulk scorer (:541), so they skip child 0. Inside a BooleanQuery with other clauses the join is driven through its Scorer (step 5), so all five ScoreModes return doc 3 there.
  7. Sorting takes the same deleted child: QueryBitSetProducer builds the child bit set without a liveness check (QueryBitSetProducer.java:77-82) and ToParentDocValues intersects it with the values (ToParentDocValues.java:214-216), so parent 3's min price is the rejected child's 1, not its live child's 50.

When it happens

#

Results differ when a rejected block numbered a child that matches the child query and left no parent bit, and the next parent in the same in-memory segment belongs to an accepted block with no matching live child. A rejected block leaves no parent bit when its parent was never numbered (the failure came at a child) or when the parent failed before the term the parent filter matches was indexed: IndexingChain.processDocument first checks the schema of all of a document's fields (IndexingChain.java:611-642, where a doc-values type conflict is thrown) and then indexes them in document order (:653-660).

  • Bounded-exhaustive differential: 264 of 12,191 scripts differ, all predicted by this rule, none unpredicted. In its scripts the immense term is always a document's last field, so a failing parent has always indexed its type term first.
  • Avoided: a flush between the two blocks (the fully deleted segment is dropped), or a failure at the parent after its type term was indexed: the deleted parent keeps its parent bit (type:parent postings [1, 3]) and catches its own child (count 0).
  • Also triggers it: a failure at the parent before its type term, when the immense field comes before type:parent (postings [3]) or with a doc-values type conflict at the parent even when type is its first field: count 1, and CheckJoinIndex rejects. Fix A gives 0 in all these cases.
  • Triggers executed at a child: an immense term, an Iterable that yields the red child and then throws, and a doc-values type conflict.
Exposure and likelihood260 words
  • Who is hit. Applications that index nested data as document blocks and filter or count parents with ToParentBlockJoinQuery, when some block is rejected with a non-aborting exception before its parent's parent-filter term was indexed: at a child, or at the parent when the failing field comes before that term or the failure is a doc-values type conflict (caught before any field is indexed). Rejected documents are routine in data-driven indexing; the application deletes nothing and handles the exception as documented.
  • Which queries. count() under every ScoreMode; ScoreMode.None searches (the usual choice for filtering parents by a child condition); the join as a MUST or FILTER clause of a BooleanQuery with another clause, under every ScoreMode; ToParentBlockJoinSortField values. Top-level Avg/Max/Min/Total searches have been right since 9.12.0; up to 9.11.x they were wrong too.
  • Defaults. Default IndexWriterConfig, codec, merge policy and searcher suffice: with 100 accepted blocks before the rejected one, both the NRT reader and the committed reader count 1 (maxDoc=204, numDocs=202), and CheckJoinIndex rejects both. The minimal test pins NoMergePolicy because with the default policy the tiny case is reclaimed before the reader sees it (that reader has maxDoc=2, count 0).
  • Size and duration. Up to one extra parent for each accepted block that lands right behind the deleted documents of rejected blocks (several rejected blocks in a row still add only that block's parent), silently, in every reader of that segment until a merge rewrites it. Only CheckJoinIndex, if the application runs it, notices.

Why it looks unintended

#
  • addDocuments promises "all or none of the documents"; ordinary queries never return the rejected child, but through the join it decides which parent matches.
  • The application deletes nothing: IndexWriter itself builds the layout that CheckJoinIndex rejects, from two legal calls.
  • 5.2.1 counts 0 on the identical index; for one query, count() says 1 while an Avg search finds nothing.
The full argument283 words
  • The contract. addDocuments "Atomically adds a block of documents with sequentially assigned document IDs, such that an external reader will see all or none of the documents" (IndexWriter.java:1496-1497). Ordinary queries honour this: the rejected child is never a hit (count(TermQuery color:red) is 0); through the join it still decides which parent matches, so the breach is indirect. An immense term gets the documented IllegalArgumentException (:1480-1481, in the addDocument javadoc, to which addDocuments refers for exceptions at :1510-1511) and the writer stays usable. Both calls follow the join's rule: blocks added with addDocuments, "the child documents must appear first, ending with the parent document" (ToParentBlockJoinQuery.java:49-52).
  • The rollback's intent. LUCENE-4629 (#5694) made a failing block Iterable delete the members already added; Michael McCandless there (2012-12-13): "+1 to remove entire block if anything goes wrong".
  • Upstream puts the burden on whoever builds the layout. Since LUCENE-6589 (#7647, which added CheckJoinIndex) a live parent with deleted children is an illegal layout. jpountz on #14067: "Block-joins require deletes to be consistent across parent and child documents"; on LUCENE-7674 (#8725), such rules should be enforced at index time. Here no application call makes the layout inconsistent; IndexWriter builds it. TestCheckJoinIndex#testInconsistentDeletes covers only deletes the application makes (TestCheckJoinIndex.java:99-135).
  • History. 5.2.1 counts 0 on the identical index (maxDoc=4, numDocs=2); 5.3.0 counts 1. An earlier window with the same symptom (4.0.0) was fixed in 4.1.0 by LUCENE-4513 (#5579) as a bug: "If a nested doc is deleted is still scored into the parent doc, which I think isn't right."
  • Self-inconsistency. For the same query and index, count() says 1 and a top-level Avg search returns no hit.
The devil's-advocate check276 words

Strongest case for "intended": since 5.3.0 the join deliberately checks parent liveness only, and a live parent with deleted children is a layout CheckJoinIndex rejects; its javadoc says it checks "that the given index is good to use for block joins" (CheckJoinIndex.java:33). The addDocuments WARNING (IndexWriter.java:1499-1504) says block joining will "not work as expected" when documents of a block are deleted; addDocuments itself (IndexWriter.java:1521) and the join API (ToParentBlockJoinQuery.java:66) are @lucene.experimental; the failing document is kept as a deleted document on purpose (DocumentsWriterPerThread.java:283-288); and ordinary search sees none of the rejected block, so the all-or-none promise holds for it. So results on such an index are unspecified. The reviewer from another model family concluded exactly this under its refute lens: its verdict was not a bug (not real, high confidence), although it agreed on the root cause, its own test failed too and fix A fixed it.

Why we still think it is a bug: the WARNING does not say who deletes the documents, and the upstream discussions found (#7647, #14067, #8725) are all about deletes, updates or layouts that the application makes. Here the application deletes nothing, and the block that gives the wrong hit is a different block that was added successfully and never touched. We think a layout that IndexWriter produces on its own, from legal calls and a documented recoverable exception, should not fall outside the contract of Lucene's own block-join consumer. A maintainer may still regard join results on it as unspecified; at most this decides where to fix it. The defect is that the writer builds the inconsistent layout.

Suggested fix

#

Recommended A: BlockJoinScorer skips deleted children (recommended as the small fix, validated; does not repair the layout)

Make BlockJoinScorer skip deleted children, as BlockJoinBulkScorer already does: pass the segment's live docs and add a live-docs check to the child iterator. The repro then passes, and so does the whole join test task. Block-join sort values and CheckJoinIndex need the writer-side option B.

All options and trade-offs3 options · 619 words

Two fix sites are reasonable. A, in the join, is small and validated; B, in the writer, repairs the layout for every block consumer but was not run. Upstream may prefer B. A fixes the join's results but leaves the layout, the sort values and CheckJoinIndex's rejection as they are; B would repair the layout.

A: BlockJoinScorer skips deleted children (recommended as the small fix, validated; does not repair the layout)

#

Pass context.reader().getLiveDocs() from BlockJoinWeight's ScorerSupplier.get (ToParentBlockJoinQuery.java:162) to a new package-private BlockJoinScorer constructor, and wrap the child iterator in a TwoPhaseIterator whose matches() first checks liveDocs.get(doc). The public three-argument constructor delegates with null. This makes the Scorer path do what BlockJoinBulkScorer already does (it passes acceptDocs to the children, :541) and what 5.2.1 did, and stays within jpountz's statement on #14067 that, with consistent deletes, "the implementation should be free to check deletes on child documents or parent documents".

// ScorerSupplier.get
          return new BlockJoinScorer(
              childScorerSupplier.get(leadCost),
              parents,
              scoreMode,
              context.reader().getLiveDocs());

// BlockJoinScorer: childTwoPhase = skipDeletedChildren(childScorer, liveDocs);
    private static TwoPhaseIterator skipDeletedChildren(Scorer childScorer, Bits liveDocs) {
      final TwoPhaseIterator in = childScorer.twoPhaseIterator();
      if (liveDocs == null) {
        return in;
      }
      final DocIdSetIterator approximation =
          in == null ? childScorer.iterator() : in.approximation();
      return new TwoPhaseIterator(approximation) {
        @Override
        public boolean matches() throws IOException {
          return liveDocs.get(approximation.docID()) && (in == null || in.matches());
        }

        @Override
        public float matchCost() {
          return in == null ? 1 : in.matchCost() + 1;
        }
      };
    }

Trade-offs

One extra live-docs check per matching child on the Scorer path of segments with deletions; not benchmarked. It does not repair the layout: ToParentBlockJoinSortField / BlockJoinSelector still take the deleted child's value, and CheckJoinIndex still rejects the index.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, seed DEADBEEF (2026-11-06): the repro fails on stock main with assertions on and off, and passes with the fix.
  • With the fix, the whole :lucene:join test task passes with assertions on and off: 105 tests including the repro, 3 skipped, 0 failures. checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest of :lucene:join pass (forbiddenApisTest was up to date in the final run, after passing on the same test classes in the first run).
  • The BooleanQuery probe gives 0 hits under all five ScoreModes with the fix. Earlier, the same logic passed the nightly TestBlockJoin and TestBlockJoinBulkScorer (21 tests) and the bounded-exhaustive differential with 0 mismatches over 12,191 scripts. A full Lucene test run was not done.

B: writer side, never let a later block land behind a rejected block's numbered documents (not run)

#

When a multi-document block fails non-abortingly after numbering at least one member, mark that DocumentsWriterPerThread flush-pending (or retire it) so the next block starts a new in-memory segment. The rejected documents then end their segment, as in the executed "flush between the blocks" case (count 0, the closest executed case), and merges drop them. It fixes the layout for every block consumer, sorting included.

Trade-offs

An extra small segment per rejected block. deleteLastDocs notes that flushing while handling the exception "gets very messy" (DocumentsWriterPerThread.java:406-414), hence flush-pending rather than an immediate flush. CheckJoinIndex's rule "The last document of a segment must always be a parent" would still reject such a segment until a merge (trailing orphans; LFV-417 is another consumer of them).

Downstream note

#

Products that build nested-document filters on block joins could return an unrelated parent after a rejected block whose child met the filter's condition.

How it was found

#

Bounded-exhaustive differential testing: all scripts of one or two blocks (up to two children) or three blocks (up to one child), each block accepted or rejected, ran on the real jar with and without rejected blocks (12,191 scripts), checked against a model of numbering, rollback and the two join scorer paths. 264 differ, all predicted; reduced to one JUnit.

The method in full262 words

The scripts cover one or two blocks with up to two children and three blocks with up to one child; each block is accepted or rejected by an immense term or by its Iterable throwing, with or without IndexWriter.flush() between blocks. Each script builds two indexes, the real one and the same script without the rejected blocks, and compares ToParentBlockJoinQuery hits and count() under all five ScoreModes (24,382 index builds, 243,820 queries), with assertions on and off.

Result: 264 scripts differ, all predicted by the model, 0 unpredicted, 0 predicted but absent. count() differs under all five modes and ScoreMode.None hits differ in all 264; top-level Avg/Max/Min/Total hits never differ; a flush between the blocks never differs, nor does a failure at the parent: in these scripts the immense term is always a document's last field, so a failing parent's type term is always indexed first (a failure before that term does differ, see "When it happens"). Vacuity checks: the reference against itself gives 0 mismatches, and a model mutant that ignores flush boundaries is rejected (304 predicted but absent).

Checks after that: separate AI tools reproduced it with their own tests (an NRT test with the immense term in another field; a default-configuration test with 100 accepted blocks), an intended-behaviour devil's advocate ran copies of the test on 5.2.1 and 5.3.0, and an independent reviewer from another model family (OpenAI GPT-5.6) reviewed it with its own executed tests on main ea57360912ed: real under the intended-behaviour lens, not a bug under the refute lens.

History

#

Present since 5.3.0 (LUCENE-6553, 2015, after which the join checks parent liveness only); 5.2.1 counts 0 on the identical index. An earlier window in 4.0.0 was fixed in 4.1.0. Not fixed upstream.

Versions tested8 rows
  • The join side of the symptom: LUCENE-6553 "Simplify how live docs are applied" (Adrien Grand, 2015-06-25; issue #7611; no pull request): c00996c54a3 on branch_5x, released in 5.3.0; trunk twin d671dd8d890, first released in 6.0.0. It removed acceptDocs from the scorer API, so 5.2.1's childWeight.scorer(readerContext, readerContext.reader().getLiveDocs()) became a call without live docs, and BlockJoinScorer got no child-liveness check in its place. Per jpountz on LUCENE-6589 this is a design for consistent layouts, not a slip.
  • The writer side is older: the rollback by deletion dates from addDocuments itself (LUCENE-3112, 3.2), and since 4.0 DocumentsWriterPerThread numbers only the members it reached. 5.2.1 and 5.3.0 build the same index (maxDoc=4, numDocs=2).
  • ScoreModes over time: from 5.3.0 through 9.11.x top-level searches return the wrong parent under every ScoreMode; since 9.12.0 (BlockJoinBulkScorer, #13697) top-level Avg/Max/Min/Total searches are right, while count(), ScoreMode.None and the BooleanQuery-clause case are not.
  • Not fixed upstream: none of the 22 commits from 5adff78bb168 to upstream main f794ff5a505 touches lucene/join, DocumentsWriterPerThread.java, DocumentsWriter.java or IndexingChain.java.
  • The 3.x and 4.x copies reject the block by an analysis exception, because before 4.8.0 immense terms were skipped silently instead of rejected. Not run: 5.3.1 to 5.5.4 and 6.0.0.

LFV-1391, snapshot of 2026-11-09

Registry title
A document block that IndexWriter rejects at a child (a documented, non-aborting IllegalArgumentException such as an immense term) leaves the block's already numbered documents in the in-memory segment as deleted documents with no parent after them, and the next accepted block's parent adopts them: ToParentBlockJoinQuery count() under every ScoreMode and ScoreMode.None searches return that parent although none of its live children matches (every release since 5.3.0)
Area
join / block join (ToParentBlockJoinQuery's Scorer path: count() and ScoreMode.None) over index / IndexWriter rollback of a rejected document block (DocumentsWriterPerThread)
Priority
Medium, rank 33: ToParentBlockJoinQuery count() under every score mode and ScoreMode.None searches silently include an extra parent after IndexWriter rejects a block at a child with its documented, recoverable exception, with default settings in every release since 5.3.0, and the wrong parent stays in every reader and commit until a merge rewrites the segment. It is Medium rather than High because it needs a rejected block whose indexed child matches the query, the effect is one extra parent per rejected block in the lucene/join module, and since 9.12 the scoring modes' top hits are right.
Impact class
silent wrong results
Impact note
Hits applications that index document blocks for ToParentBlockJoinQuery (lucene/join) when IndexWriter rejects a block at a child with a documented non-aborting exception (a term longer than 32766 bytes, a doc-values type conflict, an analyzer or Iterable exception) and the next accepted block in the same in-memory segment has no matching child: count() under every ScoreMode and ScoreMode.None searches then return that block's parent, in every NRT reader and commit until a merge rewrites the segment; default IndexWriterConfig, codec, merge policy and searcher (executed with 100 accepted blocks before the rejection), -ea and -da, no scale, every release from 5.3.0 to 10.6.0 and main; Avg/Max/Min/Total top-hit searches have returned the right hits since 9.12.0.
Summary
You add a block [red child, a child with a term longer than MAX_TERM_LENGTH, parent], which IndexWriter rejects with its documented IllegalArgumentException, then add a second block [blue child, parent], commit, and count ToParentBlockJoinQuery(color:red, parents, ScoreMode.None). You expect 0, because addDocuments promises that a reader sees all or none of a block and the only red child was in the rejected block (you do get 0 when that block is never added). Instead count() returns 1: the rejected block's first two documents kept doc IDs 0 and 1 as deleted documents with no parent after them, and the join maps the deleted red child to the next parent, doc 3, which belongs to the accepted block.
