Block grouping's TopGroups.maxScore changes with the index slicing: it can come from a group that is not returned

Since 10.5.0, block grouping on an IndexSearcher with an executor reports TopGroups.maxScore as the best score of all groups that any slice kept, including groups the merge does not return. The same query gives 1.0 sequentially and 2.0 with two slices, while the returned groups and documents are correct.

The finding in 30 seconds

#

Each slice of the index picks its own best groups and reports the best score among them. The merge keeps the largest of those numbers before it decides which groups to return, so a group you never see can set TopGroups.maxScore.

Background

#
  1. Block grouping. When each group's documents are indexed together as one block (IndexWriter.addDocuments), GroupingSearch(Query groupEndDocs) groups the hits in one pass. The result, TopGroups, holds a page of groups and a top-level maxScore.
  2. Slices. An IndexSearcher created with an executor splits the index into slices (by default at most 5 segments each, and a slice closes once it passes 250,000 documents), runs one collector per slice and merges their results. Since 10.5.0 block grouping takes this path, through BlockGroupingCollectorManager.
  3. TopGroups.maxScore is documented as the highest score across all hits. Block grouping before 10.5.0, and two-pass grouping, report the best score among the returned groups.

The finding, step by step

#
  1. You index six one-document groups as six segments, with a numeric field v = 1, 3, 4, 5, 6, 2 that is also each document's score. Block grouping (GroupingSearch(Query groupEndDocs)) sorts groups by v ascending and returns the top 1 group: v = 1, score 1.0.
  2. You run it on new IndexSearcher(reader) and on new IndexSearcher(reader, executor). The default slicing (at most 5 segments per slice; a slice also closes once it passes 250,000 documents) gives the second searcher two slices: v = 1, 3, 4, 5, 6 and v = 2.
  3. You expect the same TopGroups.maxScore both times: 1.0, the returned group's best score, as the executed releases before 10.5.0 (10.4.0 and 9.12.3) report (or 6.0, the javadoc's "highest score across all hits").
  4. Instead the sliced search reports 2.0. Each slice keeps its own top group and reports its score (1.0 and 2.0), and the merge keeps the larger number although it returns only v = 1. Same group, same documents, no warning.

Who is affected

#

Applications that use block grouping (GroupingSearch(Query groupEndDocs) or BlockGroupingCollectorManager, both experimental) with a field group sort and read TopGroups.maxScore. It takes an executor whose default slicing gives more than one slice (more than 5 segments, or segments past the 250,000-documents-per-slice limit), or groupOffset > 0. Groups, documents and hit counts stay correct; the wrong value looks plausible.

Mechanism, terms and numbers758 words

Since 10.5.0, GroupingSearch block grouping (new GroupingSearch(Query groupEndDocs)) runs through BlockGroupingCollectorManager, so on an IndexSearcher with an executor every slice collects its own top groupOffset + topNGroups groups and TopGroups.mergeBlockGroups merges them. Each slice reports a maxScore over the groups it kept, and for a field group sort the merge takes the maximum of those values before its k-way merge decides which groups are returned. A group that one slice kept but the merge drops can therefore set the top-level TopGroups.maxScore, and the value changes with how segments fall into slices.

In the minimal test the same query on the same six-segment index reports 1.0 sequentially and 2.0 with the default two slices, for the same single returned group (best score 1.0); the best hit overall scores 6.0. The executed releases before 10.5.0 (10.4.0 and 9.12.3) report one value with or without an executor, and two-pass grouping takes the maximum over the returned groups. Only this one field is wrong: the groups, their documents and order, each GroupDocs.maxScore and the hit counts are correct. Same root cause, secondary: with groupOffset > 0, block grouping now also counts the skipped groups, even without an executor. All of this is at withinGroupOffset 0; with withinGroupOffset > 0 the sibling bug LFV-230 can also lower a group's value.

  1. Per slice. Each slice's collector keeps its top groupOffset + topNGroups groups, and reduce asks for all of them (offset 0). The slice's TopGroups.maxScore is the maximum over those groups (BlockGroupingCollector.java:339-341), including groups that the merge later drops or skips.
  2. Merge. For a field group sort, mergeBlockGroups takes the maximum of every slice's maxScore while it fills the queue, before the k-way merge picks the page.
  3. Result. A group that some slice kept but the merge does not return can set the value. Which groups a slice keeps depends on which segments share a slice; the default slicing gives more than one slice once there are more than 5 segments (IndexSearcher.java:108, MAX_SEGMENTS_PER_SLICE = 5) or segments that pass the 250,000-documents-per-slice limit (:106, :361-363, :374-378; two segments of 250,001 documents give 1.0 vs 2.0 the same way). Several slices only enable the trigger: the value is wrong when some slice keeps a group that is not returned and scores higher than every returned group.
  4. Contrast. The two-pass merge, TopGroups.merge, takes the maximum over the merged groups (TopGroups.java:290). Before 10.5.0, GroupingSearch ran one BlockGroupingCollector through IndexSearcher.search(Query, Collector), which visits segments in sequence even with an executor.

The merge formula would be exact if every slice reported a true "highest score across all hits" (TopGroups.java:59); its only non-test in-tree call path, BlockGroupingCollectorManager, feeds it BlockGroupingCollector results, which report the maximum over the groups each slice kept. The defect is that mismatch.

Secondary symptom, same cause

#

Because each slice reports with offset 0, the groups before the requested page count even with a single slice. Single-document groups P (sort rank 1, score 5), Q (rank 2, score 1) and R (rank 3, score 9), groupOffset = 1, top 1 returns Q: main and 10.5.2 report 5.0, from the skipped group P; 10.4.0 and 9.12.3 report 1.0. Taken alone this moves towards the javadoc's "across all hits", so it is a behaviour change rather than a second bug.

Not affected: a relevance group sort at groupOffset 0, where the slice holding the top group also holds the best hit (TopGroups.java:419-421).

Exposure and likelihood247 words
  • Who. Applications that index groups as document blocks and use block grouping, GroupingSearch(Query groupEndDocs) or BlockGroupingCollectorManager directly (both @lucene.experimental), with a field group sort, and read the top-level TopGroups.maxScore, for example to normalise scores or to apply a relative score cut-off.
    • With an executor: whenever the default slicing gives more than one slice (more than 5 segments, or segments that pass the 250,000-documents-per-slice limit; two segments of 250,001 documents are enough), and a slice keeps a higher-scoring group that is not on the page; there is no setting to change. A thread pool is not needed: a same-thread executor (Runnable::run) takes the same path.
    • Without an executor: only with groupOffset > 0 (the secondary symptom).
  • Not affected. The groups, their documents and order, GroupDocs.maxScore, totalHitCount and totalGroupedHitCount; two-pass grouping (by field or function); a relevance group sort at groupOffset 0.
  • Silent and unstable. The value is a real score of a matching document, no error is raised, and it can change whenever segments are flushed or merged, so the same query on the same documents can give different numbers over time.
  • No scale needed. Six one-document segments show it.
  • How likely: rare. A code search of the default branches of Solr, Elasticsearch and OpenSearch found no use of block grouping's collector, manager or merge; Lucene itself never reads the field to make a decision; it has shipped since 10.5.0 (June 2026), and no user report was found in the recorded searches.

Why it looks unintended

#
  • Releases before 10.5.0 and two-pass grouping give one value per query and index; 2.0 is neither the returned groups' best (1.0) nor the javadoc's "highest score across all hits" (6.0).
  • #15936 added the merge to parallelise block grouping; its review chose the cross-slice maximum without considering groups the merge drops.
  • No grouping test checks block grouping's TopGroups.maxScore.
The full argument240 words
  • One query, one index, one value. Every existing definition gives a single value: the javadoc's "Highest score across all hits, or Float.NaN if scores were not computed" (TopGroups.java:59; 6.0 in the repro), or the maximum over the returned groups, which two-pass TopGroups.merge computes (TopGroups.java:290) and block grouping reported in 10.4.0 and 9.12.3 (1.0). None allows a number that changes with the executor's slicing (2.0).
  • #15936 was a parallelisation change. lucene/CHANGES.txt:1009, under 10.5.0: "GITHUB#15936: Introduce BlockGroupingCollectorManager to parallelize search when using BlockGroupingCollector." Nothing records a change to maxScore.
  • Intent in the review. On #15936 javanna asked (2026-05-19) "is the maxScore only read once from the first group?", and gaobinlong replied (2026-05-25) "This is really a bug, we need to compute maxScore by iterating on all TopGroups, only for the case of sort by relevance, we can get the maxScore directly from the head of the queue after initialized." That fixed an earlier first-group-only value; nobody said that a slice's maxScore also covers groups the merge drops, or that the value may change with slicing.
  • Grouping maxScore errors have been fixed as bugs before: LUCENE-8996 (#10039, distributed maxScore NaN) and #15872/#15873 (NaN maxScore). TestTopGroups.java:207-215 asserts the exact merged maxScore of merge().
  • Why tests missed it. No grouping test asserts block grouping's TopGroups.maxScore; #15936's tests do not read it, and TestGrouping's per-group check is a commented-out // TODO // assertEquals(expectedGroup.maxScore, actualGroup.maxScore); (TestGrouping.java:1632-1633).
The devil's-advocate check212 words

The strongest case for "intended" (the intended-behaviour check and the cross-model reviewer rated it moderate): the cross-slice maximum was chosen on purpose, and it matches the javadoc's "across all hits". If every slice reported a true all-hits maximum the merge would be exactly right, and the reviewer's direct-input test shows that stock mergeBlockGroups keeps such a value. The javadoc has never held literally for block or two-pass grouping, so maxScore is loosely defined; no test asserts it; the classes are @lucene.experimental; and the finder's first test overrode slices().

Why it fails: the premise is false for the merge's only non-test in-tree caller, BlockGroupingCollectorManager, whose slices report the maximum over an arbitrary, slicing-dependent set of kept groups; the result (2.0) is neither all hits (6.0) nor the page (1.0). "Loosely defined" still means one value per query and index. "Experimental" is about API stability; no javadoc promises that the value is the same for every slicing either, so the fair reading is a likely correctness defect whose intended meaning upstream must pick (the cross-model reviewer's point). The minimal test uses the default slicing, and its scores and sort values are distinct, so ties play no part. Verdict: not intended, a defect; which consistent meaning the fix restores is upstream's call.

Suggested fix

#

Recommended Take maxScore from the returned groups inside the k-way merge

Take TopGroups.maxScore from the groups the merge actually returns, as TopGroups.merge does and as block grouping did before 10.5.0 (+2/-8 lines in TopGroups.mergeBlockGroups). Both searchers then report 1.0, and the repro and all 57 grouping tests pass. Alternative: track an all-hits maximum in the collector (javadoc-literal: 6.0).

while (!queue.isEmpty()) {
  ...
  if (count++ >= groupOffset) {
    groupDocsList.add(currentGroupDocs);
    // like merge(): the maximum over the groups that are returned
    totalMaxScore = nonNANmax(totalMaxScore, currentGroupDocs.maxScore());
    totalGroupedHitCount += (int) currentGroupDocs.totalHits().value();
    ...
All options and trade-offs2 options · 641 words

Both options were applied to a scratch worktree of 645d4fe14a20 and run with gradle (OpenJDK 25.0.3, 2026-10-31). Which one is right is upstream's call: A restores what the executed releases before 10.5.0 (10.4.0, 9.12.3) and two-pass grouping report; B makes the javadoc's "highest score across all hits" literally true. No javadoc says which meaning grouped results should have, so the choice is open.

Trade-offs

  • Matches TopGroups.merge and the pre-10.5 value with and without an executor, and also undoes the groupOffset > 0 change (1.0 again in the P/Q/R case, as on 10.4.0). A relevance group sort at offset 0 keeps its value.
  • Does not make the javadoc's "Highest score across all hits" true (no release did); upstream may want to reword it for grouped results (not drafted).
  • mergeBlockGroups is public: a direct caller whose inputs already carry all-hits maxima would now get the page maximum (the cross-model reviewer's direct-input test: expected 25.0, got 1.0). No in-tree caller passes such inputs.
  • It reads GroupDocs.maxScore, so with withinGroupOffset > 0 and relevance order it inherits the per-group value of the sibling bug LFV-230 until that is fixed (the stock code does too).

Track the maximum over every collected hit in BlockGroupingCollector (validated by the checks)

#

+4/-3 lines in BlockGroupingCollector: a field updated where each hit's score is recorded, and the per-slice maxScore set from it. The existing merge then takes the maximum of true all-hits maxima and is exact.

private float maxScoreAllHits = Float.NaN;   // new field
// collect(): where each hit's score is recorded
pendingSubScores[subDocUpto] = scorer.score();
maxScoreAllHits = TopGroups.nonNANmax(maxScoreAllHits, pendingSubScores[subDocUpto]);
// getTopGroups(): replaces "if (groupSortByRelevance) maxScore = groups[0].maxScore();"
maxScore = needsScores ? maxScoreAllHits : Float.NaN;

Trade-offs

  • Makes TopGroups.maxScore literally "highest score across all hits" and leaves mergeBlockGroups unchanged for direct callers.
  • Behaviour change for every block-grouping user, sequential ones included: the minimal test's value goes from 1.0 (every executed release, sequentially) to 6.0, a score from a group that is not on the page, and the P/Q/R groupOffset = 1 case to 9.0. Applications that normalise by maxScore see different numbers after upgrading.
  • Independent of the per-group sibling bug. One extra max per collected hit when scores are needed; not benchmarked.

What the checks validated

  • With B: the whole grouping module passes: 15 classes, 57 tests, 0 failures, seed DEADBEEF with assertions on and seed C0FFEE with assertions off. The probe gives 6.0 for both searchers. Upstream's suites had not been run with B before.

How it was found

#

A bounded-exhaustive harness ran every grouping configuration over all tiny indexes and compared sequential with concurrent search, and both with a reference written from the javadoc. It flagged a different TopGroups.maxScore for the same returned group; the failing case was then minimised by hand into a public-API JUnit.

The method in full220 words

Method: semi-formal (bounded-exhaustive translation validation: the real jar is checked against exact semantics on every input up to a small scope; no model checker, SMT solver or proof is involved).

  • A hunt unit (grouping) built tiny indexes with groups in {A, B, none} and values {0, 1, 2} used as score and sort key, tried every split into segments and 7 slicings, and every group sort x within-group sort x group page x document page. It compared each result with an exact reference written from the javadoc, with sequential search and with a distributed merge.
  • The first signal, on the stock main jar: kind BSEQ_VS_CONC:TG_MAXSCORE_RET in scope block3 (same returned group, sequential maxScore 1.0, concurrent 2.0, distinct sort values, so not a tie effect). A focused probe then showed the concurrent value matches neither the returned groups nor all hits.
  • Scope block5 (19,683 indexes, 13,988,052 checks, 29 s) reports that kind 155,919 times (raw counts are not split by root cause). With the unit's combined fix sketches shadowed, the sequential-vs-concurrent, reference and distributed maxScore kinds disappear in block5 and block6.
  • The finder wrote a public-API JUnit (three one-document blocks in two segments, one slice per segment); the independent reproduction and the intended-behaviour check showed the default slicing suffices; it was then minimised by hand into the one-test repro above (2026-10-29).

LFV-239, snapshot of 2026-11-03

Registry title
With an executor, block grouping's TopGroups.maxScore includes groups that are not returned, so it changes with the index slicing (and with groupOffset > 0 it counts the skipped groups); regression in 10.5.0
Area
grouping / block grouping (TopGroups.mergeBlockGroups and BlockGroupingCollectorManager.reduce; GroupingSearch(Query groupEndDocs) on a searcher with an executor)
Priority
Low, rank 715: Since 10.5.0 block grouping with a field group sort on a multi-slice searcher takes TopGroups.maxScore over groups that are not returned, so the value changes with the slicing, but only that top-level score field is wrong, nothing in Lucene reads it, and the credibility audit downgraded the row.
Impact class
silent wrong results
Impact note
Hits applications on 10.5.0-10.5.2 and main that use block grouping (GroupingSearch(Query groupEndDocs) or BlockGroupingCollectorManager, both @lucene.experimental) with a field group sort and read the top-level TopGroups.maxScore: on an IndexSearcher with an executor that yields more than one slice (the default slicing does once the index has more than 5 segments) the value can come from a group that is not returned and changes with how segments fall into slices, and with groupOffset > 0 it also counts the skipped groups even without an executor; the returned groups, their documents and order, GroupDocs.maxScore and the hit counts stay correct, a relevance group sort at groupOffset 0 is not affected, and no scale is needed.
Summary
You index each group as a document block and run block grouping (GroupingSearch(Query groupEndDocs)) with a field group sort on an IndexSearcher that has an executor. You expect TopGroups.maxScore to be the same number whether the search runs sequentially or concurrently: sequential block grouping and two-pass term grouping report the best score of the returned groups, and the javadoc says 'Highest score across all hits'. Since 10.5.0 the concurrent value is the maximum over every group that any slice kept, including groups that are not returned, so it changes with the slicing (sequential 1.0, concurrent 5.0 from an unreturned group, best hit 9.0 in the repro), while the returned groups and documents are correct.
