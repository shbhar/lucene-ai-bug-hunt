ThaiTokenizer user dictionary: a word that ends inside a character cluster makes the vowel or tone mark after it disappear

With a ThaiTokenizer user dictionary, a dictionary word ending right before a vowel or tone mark written above or below a letter drops that mark from the index: with {แม่น} ("accurate"), แม่น้ำ ("river") is indexed as แม่น, so searching "river" finds "accurate". Only the new, unreleased user-dictionary feature is affected.

The bug in 30 seconds

#

Thai writes many vowels and all tone marks above or below a consonant; together they form one character cluster. A user-dictionary word that ends inside such a cluster is accepted, and the marks after it are thrown away.

  1. Give ThaiTokenizer the user dictionary {แม่น} ("accurate") and tokenize แม่น้ำ ("river", 6 characters). You expect every character in a token, [แม่น้ำ[0,6)], as without the dictionary.
  2. You get [แม่น[0,4)]: characters 4 and 5, the tone mark U+0E49 and the vowel SARA AM U+0E33, are in no token. "River" and "accurate" are now one term, so the query แม่น้ำ finds 2 documents instead of 1.
  3. Why: the dictionary loop takes แม่น without looking at the next character, a mark that belongs to น. It restarts word splitting at the mark, and an old loop that skips pieces not starting with a letter or digit throws the mark away.
  4. Short everyday entries hit everyday words: {ผล} turns ผลิตภัณฑ์ ("product") into [ผล, ต, ภัณฑ์], {ที} turns ที่นี่ ("here") into [ที, นี่]. A word that ends between two clusters works as intended: {แม่} gives [แม่, น้ำ].
  5. No error, and the index is well formed. Skipping a dictionary match whose next character continues the cluster (13 lines) fixes every tested case, and the 1,914 analysis-common tests run with 0 failures (18 skipped).

Who is affected

#

Only applications that give ThaiTokenizer a user dictionary, through a constructor or the factory's dictionary parameter; the stock ThaiAnalyzer is not affected. Short everyday entries (ที, ผล, สม, แม่น) hit everyday words. Marks vanish and distinct words collapse, at index and query time. Unreleased, so a fix before 10.6.0 keeps it out of every release.

Mechanism, terms and numbers825 words

The new ThaiTokenizer user dictionary (GITHUB#16722, on main, branch_10x and branch_10_6; 10.6.0 would be the first release) accepts a dictionary word as a match even when it ends inside a Thai character cluster, right before a combining vowel or tone mark that belongs to the previous consonant. The tokenizer then restarts its word BreakIterator at that point, the rest of the text starts with the mark, and the old skip loop for segments that do not start with a letter or digit throws the mark away. With {แม่น} ("accurate"), แม่น้ำ ("river") becomes the single token แม่น[0,4), so "river" and "accurate" become the same term; with {ผล}, ผลิตภัณฑ์ ("product") becomes [ผล, ต, ภัณฑ์]. Queries are analyzed the same way, so a search for แม่น้ำ also finds a document that has แม่น but not แม่น้ำ (ยิงแม่นมาก, "shoots accurately"). Nothing throws, Lucene's analysis consistency checks accept the stream and the index is well formed. A 13-line guard in the dictionary loop fixes every tested case, and a character-BreakIterator variant does the same; with either, the analysis-common suite has 0 failures (18 tests skipped).

Terms

#
  • Character cluster: a consonant plus the combining vowels and tone marks written above or below it, such as น้ำ (น + tone mark U+0E49 + SARA AM U+0E33). The marks are Unicode combining marks (category Mn); SARA AM is a letter (Lo) that Unicode's grapheme rules also attach to the cluster before it (Grapheme_Cluster_Break=SpacingMark).
  • User dictionary: the CharArraySet passed to ThaiTokenizer(CharArraySet ...) or loaded by the thai tokenizer factory's dictionary parameter (GITHUB#16722). A dictionary word "takes precedence over default segmentation boundaries" (class javadoc).

The bug (ThaiTokenizer.incrementWord, main ea57360912ed)

#
  1. The dictionary loop (ThaiTokenizer.java:186-207) tries prefix lengths from longest to shortest and takes the first userDictionary.contains(...) hit (:191-192). It never looks at the character after the match.
  2. If the match does not end where the word BreakIterator would end the word, and that point is not a word boundary, it sets reanchor (:200-201). The token [start, start + l) is emitted (:209-212): แม่น for แม่น้ำ.
  3. The re-anchor (:214-218) hands the rest of the sentence to the BreakIterator as new text. For แม่น้ำ the rest is ้ำ, which starts with the tone mark.
  4. On the next call the skip loop (:173-180, from 2014) sees a first segment that starts with U+0E49, not a letter or digit, and skips it whole. At the end of the text that segment is ้ำ, so SARA AM is lost too; mid-text, SARA AM can start the next token (ำเจ้าพระยา), and consonants after a mark survive as one-letter tokens (ต, ด, ง).

Once the re-anchor happens, the rest always starts with the mark, whatever the JDK; how the JDK splits that rest decides only what else is lost. In the tested texts the word BreakIterator put no boundary inside a cluster, so without a dictionary they lose nothing. A separate, older effect, not this bug: without a dictionary, text with no space or sentence break for 1,024 characters is cut where the tokenizer's buffer fills, and a mark right at that cut is dropped too (the same on 10.5.2; neither fix changes it).

Exposure and likelihood373 words
  • Who is hit. Users of the ThaiTokenizer(CharArraySet ...) constructors or of the thai tokenizer factory with dictionary (CustomAnalyzer, factory configs). The stock ThaiAnalyzer builds new ThaiTokenizer() without a dictionary. The feature is on main, branch_10x and branch_10_6 only; none of the downstream engines searched exposes it yet.
  • What triggers it. A dictionary entry that is the beginning of a longer word in the text and is directly followed by a combining vowel or tone mark (or SARA AM), with no longer entry covering that word. Thai above and below vowels and all tone marks are combining marks, so short entries hit common words: ที/ที่, ผล/ผลิต, สม/สมุด, แม่น/แม่น้ำ, เก/เก่ง. Lucene's own 10.6 migration notes list ผล among the "common content words" removed from the default stopwords. Long domain terms (the feature's examples พารากอน, คนขับรถ) should trigger it less often, and a dictionary that also lists the longer words avoids the cut for each word it lists ({ผล, ผลิต} keeps ผลิต); both points are reasoning, not measured on a real dictionary.
  • What goes wrong. Marks disappear from the index; one-letter tokens (ต, ด, ง) and tokens that start with SARA AM (ำเจ้าพระยา) appear; different words collapse into one term (แม่น้ำ and แม่น). Queries go through the same analyzer: a query can over-match ("river" finds "accurate") or miss a word glued after a trigger word; a clipped stopword escapes the stop filter.
  • Silent and deterministic. No exception or warning; Lucene's analysis consistency checks accept the stream, IndexWriter accepts the offsets, CheckIndex with slow checks is clean and stored text is intact (security probe, 13 documents). It happens per token in the analyzer, so it does not depend on the index; seen with -ea and -da.
  • Timing. Unreleased: with a fix before 10.6.0 no released version has it; only users of snapshots or of the branches could have built an index with it.
  • Not more than that. In the security probe: no crash or hang (18 adversarial runs, 6 texts x 3 dictionary settings, one of them no dictionary, each finish in under 0.4 s), nothing from other documents.

Why it is a bug, not intended

#
  • The javadoc lets a dictionary word take "precedence over default segmentation boundaries"; nothing allows dropping text, and the feature exists to stop "single characters" fragments (issue #16721).
  • Neither BreakIterator, word or character, has a boundary at the cut; no upstream dictionary test runs it.
  • Splits between clusters still work with the fix; Lucene fixed mark-dropping as a bug before (LUCENE-3358).
The full argument283 words
  • The contract. ThaiTokenizer.java:31-33: "Supports an optional user dictionary ({@link CharArraySet}) for custom or domain-specific words. When a user dictionary word matches, it takes precedence over default segmentation boundaries." It gives the dictionary power over where words split, not over whether characters are indexed. The contract is implicit, so the issue should say the javadoc "does not cover this case".
  • The goal of the feature. Issue #16721: domain terms "are frequently fragmented into unnatural sub-words or single characters, making exact search matching and phrase queries difficult or imprecise". This bug makes such fragments (ต, ด, ง).
  • No boundary there. At each checked cut point the Thai word BreakIterator and the character BreakIterator both report isBoundary = false; without a dictionary none of the tested texts loses a character (the older buffer-cut loss is a separate path).
  • Untested branch. All four upstream dictionary cases (TestThaiTokenizer, TestThaiTokenizerFactory) end on a word boundary or at the end of the text, so the re-anchor branch is never run by them. TestRandomChains can pass a random dictionary of a-z strings to the constructor, but it checks stream consistency only, which these streams pass. CHANGES and the 10.6 migration notes describe the dictionary as an additive feature, without caveats.
  • The intended part survives a fix. {แม่} on แม่น้ำ gives [แม่, น้ำ] and {ผล} on ผลไม้ gives [ผล, ไม้], with and without either fix.
  • Precedent. CHANGES: "LUCENE-3358, LUCENE-3361: StandardTokenizer and UAX29URLEmailTokenizer wrongly discarded combining marks attached to Han or Hiragana characters". On LUCENE-3358 a committer wrote: "we shouldn't be splitting a base character from its combining mark here". The Kuromoji user dictionary rejects illegal segmentation at load time (LUCENE-8933).
The devil's-advocate check322 words

The case for "intended" (raised by the cross-model reviews, which rated it moderate, and examined in detail by the devil's-advocate verifier; none accepted it): CharArraySet.contains is an exact code-unit match, so แม่น does "match" at the start of แม่น้ำ, and a match takes precedence. The code re-anchors on purpose when a match ends where the BreakIterator has no boundary. The mark is then dropped by the 2014 loop that skips non-letter segments, and ThaiNormalizer also removes dangling marks at a token start. ThaiTokenizer promises no grapheme safety, and a short common word that prefixes other words misuses a dictionary meant for "custom or domain-specific words".

Why it fails:

  • No reading of "precedence" removes text. Even if the split ผล|ิต were allowed, the vowel would have to land in some token; instead it vanishes, and "river" and "accurate" analyze to the same terms.
  • Nothing in the code, the PR or the tests says the re-anchor is meant for ends inside a cluster. The ends it is seen to handle correctly are between clusters (the controls), and those keep working with a fix.
  • The skip loop was written for punctuation and spaces; in the tested texts it sees a word's own mark only because the re-anchor restarts the iterator inside a cluster. ThaiNormalizer's rule is for marks already detached in the input, and in a copy of the ThaiAnalyzer chain it does not repair these tokens (ำเจ้าพระยา survives).
  • Nothing restricts dictionary contents: the factory loads any word list, and Lucene itself lists ผล among common content words. Through the factory, {ผล} breaks the long word ผลิตภัณฑ์ ("product"), which the stock tokenizer keeps whole.

Still open for upstream: whether such a match should be rejected (both fixes) or extended to the end of the cluster is a design choice. Do not claim anything about splits at valid cluster boundaries. Avoid สมิธ and คนึงหา as headline examples: the stock tokenizer already fragments them.

Suggested fix

#

Recommended A: skip a dictionary match whose next character continues the cluster

In the dictionary loop, skip a match whose next character is a combining mark or SARA AM (+13 lines); a shorter entry or the BreakIterator word stands instead. The 1,914 analysis-common tests run with 0 failures (18 skipped). A variant that asks the character BreakIterator for a cluster boundary (+20 lines) gives the same tokens and also passes.

/** true if {@code ch} cannot start a character cluster (combining mark, or Thai SARA AM). */
private static boolean continuesCluster(char ch) {
  int type = Character.getType(ch);
  return type == Character.NON_SPACING_MARK
      || type == Character.COMBINING_SPACING_MARK
      || type == Character.ENCLOSING_MARK
      || ch == '\u0E33';
}

// in incrementWord, at the top of the dictionary loop:
// a dictionary word must not end inside a character cluster (before a combining mark)
if (l < remaining && continuesCluster(buffer[sentenceStart + start + l])) {
  continue;
}

A: skip a dictionary match whose next character continues the cluster (validated by the checks) (recommended)

#

Before testing a candidate length l, look at the character right after it; if it is a combining mark (NON_SPACING_MARK, COMBINING_SPACING_MARK, ENCLOSING_MARK) or SARA AM, try the next shorter length. With no dictionary hit left, the word that the BreakIterator found stands. Every symptom row becomes the no-dictionary or control result, and the intended splits ({แม่} on แม่น้ำ, {ผล} on ผลไม้) are unchanged. This is the finder's patch.

/** true if {@code ch} cannot start a character cluster (combining mark, or Thai SARA AM). */
private static boolean continuesCluster(char ch) {
  int type = Character.getType(ch);
  return type == Character.NON_SPACING_MARK
      || type == Character.COMBINING_SPACING_MARK
      || type == Character.ENCLOSING_MARK
      || ch == '\u0E33';
}

// in incrementWord, at the top of the dictionary loop:
// a dictionary word must not end inside a character cluster (before a combining mark)
if (l < remaining && continuesCluster(buffer[sentenceStart + start + l])) {
  continue;
}

Trade-offs

  • A hand-written rule: three mark categories plus SARA AM, tested per UTF-16 char, so a mark outside the BMP would not be seen (all Thai marks are in the BMP).
  • Cost: one Character.getType per candidate length; not benchmarked.
  • Output change only for dictionary configurations that hit the bug; the feature is unreleased, so no released index needs a reindex.
  • Does not change the older no-dictionary loss at buffer cuts.

How it was found

#

An AI tool ran a seeded property-based check of ThaiTokenizer with random user dictionaries (4,000 iterations, about 156,000 checks) and found characters that ended up in no token. It picked realistic examples by hand and wrote a public-API JUnit. Independent verifiers and a reviewer from another model family (OpenAI GPT-5.6) reproduced it with their own tests.

The method in full233 words

Method: property-based testing with random user dictionaries (the hunt's non-formal tier; no formal tool produced the first signal).

  • The finder's harness built random texts and random dictionaries over a small Thai vocabulary and checked two oracles: every letter or digit of the text lies inside some token, and a token that starts where a dictionary word matches is the longest such match that ends on a character-cluster boundary. On stock main: 25 violations in about 156,000 checks (19 lost characters, 6 precedence; the precedence oracle uses the same cluster rule as the fix, so only the 19 are independent of it). With the fix: none. The harness's dictionaries include truncated non-words; the realistic examples were then chosen by hand.
  • An independent reviewer from another model family (OpenAI GPT-5.6, refute lens) ran its own test ({ผล} on ผลิต) on main with -ea and -da over seven seeds, with two controls, and the fix. A second GPT-5.6 review (works-as-designed lens) could only read the code; the pipeline re-ran the finder's JUnit for it.
  • Claude verifiers wrote their own tests: the independent reproduction (ที่นี่, เก่ง, คนึงหา, กล้ำกลืน, แม่น้ำ; 5 of 7 fail) and the intended-behaviour check, a devil's advocate, whose intent probe recorded 11 facts on main, including the factory case and that no BreakIterator has a boundary at the cut. An adjudication re-ran both with fresh seeds.

Bug record

#

LFV-229, snapshot of 2026-10-27

Registry title
ThaiTokenizer with a user dictionary silently drops the vowel or tone marks that follow a dictionary word ending inside a character cluster (with {แม่น}, 'แม่น้ำ' (river) is tokenized as just [แม่น] (accurate)), because the match is accepted at a non-boundary and the remainder, which now starts with a mark, is skipped
Area
analysis / Thai (ThaiTokenizer#incrementWord user-dictionary loop and re-anchor, GITHUB#16722; ThaiTokenizerFactory 'dictionary')
Priority
Medium, rank 87: The new ThaiTokenizer user dictionary accepts a match that ends inside a character cluster, so short everyday entries such as แม่น or ผล silently drop the following vowel or tone marks and collapse distinct words into one term on ordinary Thai text, opt-in and language-specific, and a fix before the release avoids any reindex.
Impact class
silent wrong results
Impact note
Only applications that opt into the new, unreleased ThaiTokenizer user dictionary (the ThaiTokenizer(CharArraySet ...) constructors or the ThaiTokenizerFactory 'dictionary' parameter, GITHUB#16722, first release would be 10.6.0; the stock ThaiAnalyzer passes no dictionary and is not affected) are hit, whenever a dictionary entry is a prefix of the text at a token start and is directly followed by a combining vowel or tone mark (or SARA AM) with no longer entry covering it, which is easy with short everyday entries (ผล, สม, คน, ที, แม่น) and rarer with long domain terms: the marks vanish from the token stream, single-letter or mark-initial garbage tokens appear, and distinct words can collapse to one term on both the index and the query side, deterministically at any size, with -ea and -da, with no exception and a well-formed index.
Summary
You configure ThaiTokenizer with a user dictionary that contains an ordinary short word such as แม่น ('accurate') or ผล ('result') and expect it to change only where words split. Instead, when the dictionary word is followed in the text by a combining vowel or tone mark, as in แม่น้ำ ('river') or ผลิต ('produce'), the tokenizer cuts the character cluster and throws the mark away: แม่น้ำ becomes the single token แม่น, and ผลิต becomes [ผล, ต]. Because queries are analyzed the same way, a search for แม่น้ำ also matches documents that only contain แม่น, with no error.
