SimplePatternTokenizer and SimplePatternSplitTokenizer join an unpaired high surrogate with the next character, so a space after it no longer separates two words

When a string holds half an emoji (a lone high surrogate, U+D83D) followed by more text, both simple-pattern tokenizers glue that half to the next character: hi\uD83D yo gives one token instead of hi\uD83D and yo, so a search for yo misses the document.

The finding in 30 seconds

#

Both tokenizers match their pattern one Unicode code point at a time. On a high surrogate they always join it with the next UTF-16 unit, without checking that this unit is the matching low surrogate. A lone U+D83D followed by a space becomes U+11820, so the pattern never sees the space.

  1. Tokenize the 6-char text hi\uD83D yo (h, i, a lone U+D83D as left by cutting a string inside an emoji, a space, y, o) with SimplePatternTokenizer("[^ ]+") or SimplePatternSplitTokenizer(" ").
  2. You expect two tokens, hi\uD83D [0,3) and yo [4,6): String.split(" "), PatternTokenizer and WhitespaceTokenizer all give exactly that.
  3. You get one token, hi\uD83D yo [0,6). The tokenizer reads U+D83D and the space as one code point, U+11820, which is not in the text: [^ ]+ accepts it, and the one-space separator pattern does not match it.
  4. Indexed, the term is hi\uFFFD yo (IndexWriter stores U+FFFD for the lone half), and a TermQuery for yo finds 0 documents instead of 1. With a letters-only pattern a letter is lost instead: [a-z]+ on \uD83Dab gives b, not ab. The tokenizer does not throw.
  5. A valid pair (an emoji) and a lone low surrogate at the same spot tokenize correctly. Every release since 6.5.0 (2017) has the bug.

Who is affected

#

Only users who pick these opt-in, experimental tokenizers (factory names simplePattern, simplePatternSplit) and whose text holds a lone high surrogate followed by more text, such as a value cut inside an emoji and then joined to more text. The next word or letter is then silently lost from the index, at any scale.

Mechanism, terms and numbers541 words

SimplePatternTokenizer and SimplePatternSplitTokenizer step their automaton over Unicode code points, and read them with nextCodePoint(). On a high surrogate that method returns Character.toCodePoint((char) ch, (char) nextCodeUnit()) without checking that the next unit is a low surrogate (SimplePatternTokenizer.java:249, SimplePatternSplitTokenizer.java:259). So an unpaired high surrogate swallows the well-formed character after it: in hi\uD83D yo, U+D83D and the space become U+11820, which [^ ]+ accepts and the one-space separator pattern does not match, so both classes emit one token hi\uD83D yo [0,6) instead of hi\uD83D [0,3) and yo [4,6). With [a-z]+, the letter after the surrogate is lost: \uD83Dab gives b. The index stores the term hi\uFFFD yo, a TermQuery for yo finds nothing, and the tokenizer does not throw. String.split, PatternTokenizer and WhitespaceTokenizer treat the lone surrogate as a code point of its own and give two tokens, and Lucene's own CharacterRunAutomaton.run rejects the emitted token for [^ ]+. The line dates from the classes' first commit (LUCENE-7465, 6.5.0) and fails on every release run up to 10.6.0 and on main. A fix that pairs only with a real low surrogate (+20/-2) passes the repro and the whole analysis-common test module.

What an unpaired high surrogate is

#

Java strings are UTF-16. An emoji such as 😀 is two chars, the high surrogate U+D83D and the low surrogate U+DE00. A string cut by char count inside the emoji (String.substring) keeps only U+D83D; joined to more text, it gives values like hi\uD83D yo. A JSON \ud83d escape in mid-string can decode to the same thing. Java reads such a lone unit as a code point of its own (String.codePointAt(2) is U+D83D), and so do CharTokenizer and CharacterRunAutomaton.run.

The code (main f794ff5a505c)

#
  • SimplePatternTokenizer.java:242-253, nextCodePoint(): :248-249 if (Character.isHighSurrogate((char) ch)) { return Character.toCodePoint((char) ch, (char) nextCodeUnit()); }. The next unit is consumed and never checked with isLowSurrogate.
  • SimplePatternSplitTokenizer.java:252-263: the same code at :258-259.
  • Callers: SimplePatternTokenizer.java:116 and :134 (token start and lookahead), SimplePatternSplitTokenizer.java:112 and :134 (separator match); each result goes to runDFA.step (:121, :138). The comment above them says "The runDFA operates in Unicode space, not UTF16 (java's char)" (SimplePatternTokenizer.java:114, SimplePatternSplitTokenizer.java:111).
  • nextCodeUnit() appends every unit to the term buffer (SimplePatternTokenizer.java:212-240), so the token text keeps the original units and the offsets are right; only the matching is wrong.

So [^ ]+ keeps matching to the end and the token is hi\uD83D yo [0,6). The split tokenizer's separator automaton for the one-space pattern dies on U+11820, so it never finds the separator. With [a-z]+ (the probe built it as an Automaton and determinized it; it is deterministic anyway), U+D83D + a becomes U+11861, which the pattern rejects, so a cannot start a token: \uD83Dab gives b [2,3).

Controls (executed): a real pair, hi😀 yo, gives hi😀 [0,4) and yo [5,7); a lone low surrogate, hi\uDE00 yo, gives hi\uDE00 [0,3) and yo [4,6).

Exposure and likelihood199 words
  • Who is exposed. Applications that use SimplePatternTokenizer or SimplePatternSplitTokenizer directly, through their factories (SPI names simplePattern and simplePatternSplit, for example in CustomAnalyzer or a Solr schema), or through downstream tokenizers built on them.
  • Opt-in. Both classes and factories are @lucene.experimental, and no Lucene analyzer uses them by default. Most patterns are hit, but not, for example, .+, where both readings match: the made-up code point is in a different class than the real next character for most patterns.
  • What it takes. An unpaired high surrogate followed by at least one more character in a field value or query. Well-formed UTF-16, emoji included, never triggers this bug (LFV-545, a separate bug in the same classes, can hit some valid pairs). How often such values occur in real data was not measured; the likelihood is rated rare by judgement.
  • Effect. Silent, per value, with assertions on or off: two words become one term, or a letter vanishes from a token, so a term search for the word misses the document. The stored value is not affected by this bug (IndexWriter stores it as with any analyzer, the lone surrogate as U+FFFD); other values and documents are not affected.

Why it looks unintended

#
  • The javadoc promises separators "like String.split", which gives hi\uD83D and yo.
  • The token fails the tokenizer's own pattern: Lucene's CharacterRunAutomaton over [^ ]+ rejects hi\uD83D yo and accepts hi\uD83D.
  • The damage hits the well-formed space, not the bad unit; a lone low surrogate there works, and IndexWriter documents that it accepts such text.
The full argument191 words
  • Contract. "The provided regex should match valid token characters (not token separator characters, like String.split). The matching is greedy: the longest match at a given start point will be the next token" (SimplePatternTokenizer.java:33-35); the split class: "the pattern should make valid token separator characters, like String.split" (SimplePatternSplitTokenizer.java:33-34).
  • Lucene's own reading of the same automaton. CharacterRunAutomaton.run decodes with codePointAt (CharacterRunAutomaton.java:31-49): over [^ ]+ it accepts hi\uD83D and rejects hi\uD83D yo. CharTokenizer (CharTokenizer.java:196) reads the lone unit the same way, and UnicodeUtil's UTF-16 to UTF-8 conversion (UnicodeUtil.java:156-177) pairs only with a real low surrogate and otherwise writes U+FFFD for the lone unit, without consuming the next one.
  • Indexing accepts such text on purpose. CHANGES, LUCENE-510: "If any text, either stored fields or a token, has illegal UTF-16 surrogate characters, these characters are now silently replaced with the Unicode replacement character U+FFFD" (lucene/CHANGES.txt:20082-20086).
  • Tests and history. No upstream test of either class feeds an unpaired surrogate, and the LUCENE-7465 thread (#8517, 31 comments) never discusses them. It looks like an unconsidered edge case; no source says either way.
The devil's-advocate check260 words

The strongest case for "intended" is garbage in, garbage out: the input is ill-formed UTF-16, both classes are @lucene.experimental, no javadoc mentions surrogates, MockTokenizer throws on any unpaired surrogate, high or low (MockTokenizer.java:249-275), TestUtil's random Unicode generator documents valid UTF-16 (TestUtil.java:628), and a 2012 Kuromoji commit by Robert Muir says "unless the input is already screwed, GIGO" (685035575b3, LUCENE-3305).

Why it fails: no Tokenizer or pattern-package javadoc states a well-formed-UTF-16 precondition; the damage lands on the next, well-formed character, not on the bad unit; the rest of Lucene handles the lone unit on its own and never consumes the next character (CharacterRunAutomaton and CharTokenizer read it as a code point of its own; UnicodeUtil, and so IndexWriter, replaces just that unit with U+FFFD); and a lone low surrogate at the same spot works. Half surrogates are ordinary input: as Uwe Schindler put it on #15900 (about TruncateTokenFilter), they happen "exactly the same like if you use String#substring(n,m) ... You have to be prepared for that." A maintainer who would rather drop or replace the lone unit (StandardTokenizer gives a, b on a\uD83D b) would still get yo as its own token. Two executed reviews by another model family (OpenAI GPT-5.6, refute and intended lenses) rated the intended case moderate and rejected it. The claim is narrow: behaviour on ill-formed UTF-16 is not specified anywhere, so whether the lone unit is kept, replaced or dropped is the maintainers' call; the bug is that the next, well-formed character is swallowed.

Suggested fix

#

Recommended Pair only with a real low surrogate (validated)

In nextCodePoint(), join a high surrogate only with a real low surrogate; otherwise push the next unit back and return the lone surrogate as a code point of its own, as Character.codePointAt does (+20/-2 over both classes). The repro, the 29 tests of both classes and the whole analysis-common test module pass with it.

if (Character.isHighSurrogate((char) ch)) {
  int lo = nextCodeUnit();
  if (lo != -1 && Character.isLowSurrogate((char) lo)) {
    return Character.toCodePoint((char) ch, (char) lo);
  }
  if (lo != -1) {
    // unpaired high surrogate: it is a code point of its own; re-read lo next time
    pushBack(1);
    tokenUpto--; // SimplePatternSplitTokenizer: sepUpto-- (its pushBack moves tokenUpto)
  }
  return ch;
}

Pair only with a real low surrogate (validated) (recommended)

#

The same change in both classes' nextCodePoint(); the split class decrements sepUpto instead of tokenUpto, because its pushBack already moves tokenUpto. Condensed below: the comment on the tokenUpto-- line is not in the diff.

if (Character.isHighSurrogate((char) ch)) {
  int lo = nextCodeUnit();
  if (lo != -1 && Character.isLowSurrogate((char) lo)) {
    return Character.toCodePoint((char) ch, (char) lo);
  }
  if (lo != -1) {
    // unpaired high surrogate: it is a code point of its own; re-read lo next time
    pushBack(1);
    tokenUpto--; // SimplePatternSplitTokenizer: sepUpto-- (its pushBack moves tokenUpto)
  }
  return ch;
}

Trade-offs

  • Well-formed text takes the same path as today, plus one isLowSurrogate check per high surrogate.
  • The lone unit is read as Character.codePointAt and CharacterRunAutomaton.run read it, so a pattern can still match it (for example [^ ]+ keeps it in hi\uD83D).
  • It also handles a lone high surrogate as the very last character (stock pairs it with (char) -1); that case is not claimed or tested here.

Downstream note

#

Elasticsearch's and OpenSearch's simple_pattern and simple_pattern_split tokenizers are built on these classes, so their users would get the same merged tokens for such text (read in their sources, not run there).

How it was found

#

Bounded-exhaustive translation validation: every string of up to 6 characters over {a, b, space, U+D83D, U+DE00}, with 14 patterns and 2 reader modes (1,093,736 checks), went through both tokenizers and an independent reference scanner over the same automaton. Every mismatch left after the fixes of two related bugs had an unpaired high surrogate; this fix removed them all.

The method in full139 words
  • The reference. An independent longest-match scanner over the same determinized automaton, which decodes code points as java.lang.String does, compared token by token (text, offsets, final offset) with the real tokenizers on the stock jars.
  • Separating the classes. With the fixes of LFV-525 (end-of-input lookahead) and LFV-545 (false-alarm retry inside a pair) applied, 197,904 mismatches remained, every one on an input with an unpaired high surrogate; adding this fix gave 0. This fix alone leaves only LFV-545's class (9,136). On an {a, b, c} alphabet (131,160 checks), the three fixes together also give 0.
  • A second signal. A separate sweep of edge-case texts flagged SimplePatternSplitTokenizer with a whitespace separator on hello \uD83D world: world was not a token of its own.
  • The finding was then reproduced with JUnit tests on main and on releases, and reviewed (see the checks).

Impact note
Hits only applications that choose SimplePatternTokenizer or SimplePatternSplitTokenizer (directly, through the simplePattern / simplePatternSplit factories, or a downstream simple_pattern / simple_pattern_split tokenizer) and index or query a value that holds an unpaired high surrogate followed by more text (a string cut inside an emoji and then joined to more text, or a JSON \ud83d escape in mid-string): the character after the surrogate is fused into a made-up supplementary code point, so whenever the pattern treats that character differently (a separator space, a letter for a letters-only pattern) two words are indexed as one term or a letter is lost and the word is not found by its own term, at any scale, with -ea and -da and no exception; well-formed UTF-16, emoji included, and an unpaired low surrogate are not affected [exec].
Summary
You tokenize 'a' U+D83D ' b' (an unpaired high surrogate, as left by cutting a string inside an emoji, then a space and 'b') with SimplePatternTokenizer('[^ ]+') or SimplePatternSplitTokenizer('[ ]+') and expect two tokens, 'a'+U+D83D [0,2) and 'b' [3,4): that is what String.split("[ ]+"), PatternTokenizer and WhitespaceTokenizer give, and what the tokenizers' own automaton accepts under CharacterRunAutomaton.run. Instead both emit one token 'a'+U+D83D+' b' [0,4), because nextCodePoint() pairs the high surrogate with whatever unit follows it without checking for a low surrogate, so the space becomes part of the made-up code point U+11820 and stops being a separator; with a letters-only pattern the next letter is lost the same way (SimplePatternTokenizer('[a-z]+') on U+D83D 'ab' gives 'b' [2,3) instead of 'ab' [1,3)), and nothing throws.
