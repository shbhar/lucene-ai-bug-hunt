A rejected over-long delete term stays in IndexWriter's delete queue, so later adds, deletes and the next commit fail

Since 9.9.0, a deleteDocuments or updateDocument call with a term over 32,766 bytes throws but stays in IndexWriter's delete queue: later adds and deletes and the next commit fail, and the documents buffered before it are lost. Up to 9.8.0 the same call was a harmless no-op.

The finding in 30 seconds

#

IndexWriter queues a delete first and applies it second. Since 9.9.0 the apply can reject an over-long term, but the delete is already in the shared queue, and the queue drops entries only after they applied without error, so the same entry fails again on later adds and deletes and the next commit.

Background

#
  1. Buffered deletes. deleteDocuments(term) does not touch the index right away. It appends an entry to the writer's shared delete queue; a global buffer and each indexing thread later copy the entries they have not seen yet into their own buffer of pending deletes.
  2. Slices. Each reader of the queue keeps a slice, from the last entry it copied to the newest one. It moves the start of its slice forward only after it copied every entry in the slice without an error.
  3. The term limit. No indexed term can be longer than IndexWriter.MAX_TERM_LENGTH, 32,766 bytes. Since 9.9.0 (#12573) the buffer of pending delete terms is a BytesRefHash, which has the same 32,766-byte limit for its keys.

The finding, step by step

#
  1. Open an IndexWriter with default settings, add one document (id:1), then call deleteDocuments(new Term("id", t)) where t is 32,767 bytes, one byte over the 32,766-byte term limit.
  2. You expect that delete to match nothing (no indexed term can be that long; up to 9.8.0 it was a no-op) or to be rejected on its own, and commit() to store the 1 document.
  3. Instead the delete throws MaxBytesLengthExceededException after it was already linked into the writer's shared delete queue, and nothing takes it out again.
  4. Later steps re-apply it and fail: the next addDocument and any other delete throw the same exception, and commit() throws IllegalStateException: Can't close queue unless all changes are applied, which leaves the writer open (with assertions on, an AssertionError that closes the writer).
  5. The documents buffered before the bad delete are lost either way: rollback() discards everything since the last commit, and a commit retried after the failed one succeeds but leaves them out.

Who is affected

#

Any application on 9.9.0 to 10.6.0 or main that deletes or updates by a term it does not length-check, such as an id taken from a request, through deleteDocuments(Term...), updateDocument(s)(Term, ...) or the monitor module's deleteById. Default settings; one call is enough. Committed data stays intact.

Mechanism, terms and numbers702 words

IndexWriter.deleteDocuments(Term...), updateDocument(Term, ...) and updateDocuments(Term, ...) link the delete into the writer's shared delete queue before they apply it. Since #12573 (9.9.0) applying it stores the term in a BytesRefHash, which rejects keys over 32,766 bytes, the same limit IndexWriter.MAX_TERM_LENGTH puts on indexed terms. A delete by a 32,767-byte term therefore throws MaxBytesLengthExceededException after it is queued, and because the queue's slices are reset only after a fully successful apply, the bad entry is applied again, and fails again, by the next addDocument, delete, commit, NRT reopen or close(). The documents buffered before it are lost: rollback() discards everything since the last commit, and a commit retried after the failed one succeeds without them; committed data stays intact. Up to 9.8.0 the same call was a no-op, and on main the same term as deleteDocuments(new TermQuery(term)) still is. Default settings, one call, one thread; every release from 9.9.0 to 10.6.0 and main are affected.

The code (main 645d4fe14a20)

#
  1. Queued before it is checked. deleteDocuments(Term...) (IndexWriter.java:1864-1872) reaches DocumentsWriterDeleteQueue.addDelete, which does long seqNo = add(new TermArrayNode(terms)); tryApplyGlobalSlice(); (DocumentsWriterDeleteQueue.java:129-133): the entry is linked at the tail of the shared queue and gets a sequence number first.
  2. The apply throws. tryApplyGlobalSlice (:198-215) applies the global slice; DeleteSlice.apply (:348-367) calls each entry's apply; TermArrayNode.apply (:480-485) calls BufferedUpdates.addTerm, which ends in deleteTerms.put(term, docIDUpto) (BufferedUpdates.java:131) -> DeletedTerms.put (:210-221) -> BytesRefHash.add (:325-327) -> BytesRefBlockPool.addBytesRef, which throws MaxBytesLengthExceededException: bytes can be at most 32766 in length; got 32767 (BytesRefBlockPool.java:83-90).
  3. Never dropped. DeleteSlice.apply calls reset() only after its loop finished (DocumentsWriterDeleteQueue.java:366). The exception skips it, so the global slice, and every per-thread slice that later reaches the entry, starts before it again next time and throws at the same entry.
  4. Later calls. The next addDocument applies its thread's slice in DocumentsWriterPerThread.finishDocuments (:380-383) and throws; the next delete or updateDocument applies the global slice again (DocumentsWriterDeleteQueue.java:131, :168 -> tryApplyGlobalSlice, :209) and throws.
  5. Commit. DocumentsWriter.flushAllThreads (:667-715) swaps in a new queue and flushes. DocumentsWriterPerThread.prepareFlush (:427-438) first extends the thread's slice to the queue's tail (DocumentsWriterDeleteQueue.java:229-232; the global slice is not applied again there, since the failed apply already set its tail to the bad entry, :264, :296-300) and then applies that slice (DocumentsWriterPerThread.java:434), which reaches the bad entry and throws. The finally then calls close() on the old queue (DocumentsWriter.java:704-708), which sees unapplied changes and throws IllegalStateException: Can't close queue unless all changes are applied (DocumentsWriterDeleteQueue.java:317-321), replacing the original exception; with assertions off the writer stays open. With assertions on, the commit ends in an AssertionError ("Can not replace a full flush queue if the queue is not closed", DocumentsWriter.java:647-649), which prepareCommitInternal treats as tragic (IndexWriter.java:3879-3881), and the writer closes itself.

What a probe shows (assertions off, plain program)

#

Document a committed, b added, then the 32,767-byte delete: the delete and addDocument(c) throw MaxBytesLengthExceededException, an NRT reopen throws the IllegalStateException, and after that the old queue has been dropped, so commit() and close() return normally. The committed index holds 1 document, a; b is lost (c was rejected), and hasUncommittedChanges() stays true. With nothing committed before, 0 of 3. The same at the 10.6.0 release commit. On 9.8.0 the same sequence commits all 3. close() right after the bad delete throws the same IllegalStateException and closes the writer without committing b (1 of 2).

All runs were single-threaded. The global apply runs only when its lock is free (DocumentsWriterDeleteQueue.java:199), so with concurrent writers the bad call itself may return normally and a later call, or the next commit, hit the entry instead (by code reading).

Why 9.8.0 was fine

#

Up to 9.8.0 BufferedUpdates kept delete terms in a HashMap<Term, Integer> with no key-length limit, so applying a term entry could not throw for this reason. The queue behaviour (append before apply; reset only after a full apply) is from 2011 (LUCENE-2956) and 2016; #12573 gave a legal public call a way to make that step throw.

Exposure and likelihood285 words
  • Trigger. One call of deleteDocuments(Term...), updateDocument(Term, ...) or updateDocuments(Term, ...) with a term of at least 32,767 bytes. Default codec and IndexWriterConfig, any directory (reproduced on ByteBuffersDirectory, FSDirectory and the test framework's directory); one thread. In the monitor module, Monitor.deleteById passes the id straight to deleteDocuments(new Term(query_id, id)): after deleteById of a 32,767-character id the next register() and Monitor.close() throw on main, while 9.8.0 registers both queries.
  • Effect. Later adds and deletes throw and the next commit, NRT reopen or close() fails. The documents buffered before the bad delete are lost: rollback() discards all uncommitted work, and a commit retried after the failed one succeeds without them (after that failed commit the writer works again). The failure is loud (every affected call throws). With assertions off the writer is not marked tragic; with assertions on the failed commit closes it. Committed data is not damaged: the committed index opens and a new writer opens on it in every probe. A secondary consequence: the dropped per-thread writer keeps its 4 stored-fields files open, still after rollback() and Directory.close().
  • Not affected. The doc-values update APIs (updateNumericDocValue, updateBinaryDocValue, updateDocValues; executed), whose buffer has no such key limit; softUpdateDocument(s), which uses that same buffer (executed: softUpdateDocument with the 32,767-byte term and then commit() both succeed); deleteDocuments(Query...) with a TermQuery of the same term (executed: a no-op).
  • Versions. Every release from 9.9.0 to 10.6.0, and main.
  • Likelihood: rare. Real ids are never that long, so it takes an unvalidated oversized key; but a single such call breaks the writer's next adds, deletes and commit and loses its buffered documents, for every client of that writer, not just the bad request.

Why it looks unintended

#
  • The delete and update APIs state no length limit. On indexed terms Lucene enforces it with a clean IllegalArgumentException, and testWickedLongTerm asserts the writer stays usable.
  • Up to 9.8.0 the same call was a no-op; on main, deleteDocuments(new TermQuery(term)) with the same term still is.
  • It came from #12573, a sort-speed optimization whose review never discusses term length.
The full argument262 words
  • No precondition. deleteDocuments(Term...): "Deletes the document(s) containing any of the terms", documenting only CorruptIndexException and IOException (IndexWriter.java:1855-1863); updateDocument likewise (:1901-1911). Term's constructors call only a null field or null bytes "undefined behavior" (Term.java:47-48).
  • Where the limit is documented, the rejection is contained. MAX_TERM_LENGTH: "If a term arrives from the analyzer longer than this length, an IllegalArgumentException is thrown" (IndexWriter.java:252-258); addDocument: "each term in the document can be no longer than MAX_TERM_LENGTH in bytes, otherwise an IllegalArgumentException will be thrown" (:1480-1481). TestIndexWriter#testWickedLongTerm, after that rejection: "Make sure we can add another normal document" (TestIndexWriter.java:1548-1565).
  • The writer's failure contract. "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself" (IndexWriter.java:162-165). A RuntimeException from one call is neither, yet here it makes later, unrelated calls fail. commit(): "Commits all pending changes (added and deleted documents, ...)" (:4189).
  • Consistency. The same term as deleteDocuments(new TermQuery(term)) is a no-op on main, and the same call is a no-op on 9.7.0 and 9.8.0 (all executed; earlier releases use the same HashMap buffer).
  • History. #12573 ("Use radix sort to speed up the sorting of deleted terms") is listed under 9.9.0 "Optimizations"; its description covers sort time and memory, and its review never mentions term length. We found no test in Lucene's test sources that deletes or updates by a term over 32,766 bytes (searched for MAX_TERM_LENGTH, BYTE_BLOCK_SIZE and MaxBytesLengthExceededException); TestBufferedUpdates#testDeletedTerms, added by #12573, uses keys of 1-3 bytes.
The devil's-advocate check198 words

The strongest case: 32,766 bytes is "the absolute hard maximum length for a term" and Lucene's SECURITY.md makes length limits on untrusted input the application's job, so a 32,767-byte delete term is garbage in. And continuing after a failed commit can lose documents, with rollback() as the remedy (as Simon Willnauer said on LUCENE-8692, #9738), so the later loss is not a bug of its own. Lucene also documents no general promise that a call that throws leaves the writer unchanged.

Why it fails: no delete or update API states the limit, and where the limit applies Lucene rejects the call cleanly and keeps the writer usable. Here the bad call is itself rejected, yet unrelated later calls (a normal addDocument, a 3-byte delete) fail too, which breaks failure atomicity rather than being garbage in, garbage out. The same term through TermQuery, and through this API up to 9.8.0, is harmless, and the change came from a performance PR that never considered term length. The LUCENE-8692 point covers only the secondary symptom. Without a general failure-atomicity promise, the specific contracts still apply: the add path shows what Lucene does at the same limit. Verdict: not intended.

Suggested fix

#

Recommended Reject the term with IllegalArgumentException before it is queued (validated)

Reject a delete or update term over 32,766 bytes with an IllegalArgumentException before it enters the delete queue (+21 lines in DocumentsWriterDeleteQueue), as addDocument does for an immense term. The repro and 197 tests of seven core index suites pass with it. Skipping such a term instead, which restores 9.8.0's no-op, passes the same tests.

private static void checkDeleteTerm(Term term) {
  if (term.bytes().length > IndexWriter.MAX_TERM_LENGTH) {
    throw new IllegalArgumentException(
        "delete term in field=\"" + term.field() + "\" is longer than "
            + IndexWriter.MAX_TERM_LENGTH + " bytes: " + term.bytes().length);
  }
}
// called first in addDelete(Term... terms), for each term, and in newNode(Term term)

Reject the term with IllegalArgumentException before it is queued (validated) (recommended)

#

In DocumentsWriterDeleteQueue, check every term in addDelete(Term...) and in newNode(Term) (which builds the delete entry of all updateDocument(s)(Term, ...) overloads) before the entry is created, so the call fails on its own and nothing is queued. The check could equally sit in the four public IndexWriter methods; this class is the one place they all pass through.

private static void checkDeleteTerm(Term term) {
  if (term.bytes().length > IndexWriter.MAX_TERM_LENGTH) {
    throw new IllegalArgumentException(
        "delete term in field=\"" + term.field() + "\" is longer than "
            + IndexWriter.MAX_TERM_LENGTH + " bytes: " + term.bytes().length);
  }
}
// called first in addDelete(Term... terms), for each term, and in newNode(Term term)

Trade-offs

  • Same exception type addDocument uses for an immense term; the writer stays usable, as testWickedLongTerm expects on the add path.
  • A behaviour change against 9.8.0, which accepted such a delete silently (9.9.0 and later already throw, just with the wrong consequences); callers that catch MaxBytesLengthExceededException see IllegalArgumentException instead.
  • updateDocument(longTerm, doc) now rejects the whole update, document included, which matches the update's atomic contract. The javadoc of the delete and update methods should then state the limit.

Skip the term in BufferedUpdates.addTerm (validated)

#

In BufferedUpdates.addTerm, return early when term.bytes().length > ByteBlockPool.BYTE_BLOCK_SIZE - 2: such a delete can match no indexed term (+6 lines, with a comment).

public void addTerm(Term term, int docIDUpto) {
  if (term.bytes().length > ByteBlockPool.BYTE_BLOCK_SIZE - 2) {
    // No indexed term can be longer than IndexWriter.MAX_TERM_LENGTH, so this delete matches
    // nothing; skip it instead of failing in the BytesRefHash, which would leave the node in
    // the shared delete queue and fail every later apply.
    return;
  }
  ...

Trade-offs

  • Restores the 9.8.0 outcome (the delete is a no-op), at the place the limit lives, for every path that buffers a delete term; consistent with deleteDocuments(new TermQuery(term)) on main.
  • Silent: a caller passing a bogus key gets no signal.
  • Not the 9.8.0 state: 9.8.0 put the term in its map, counted it and charged its bytes to the RAM accounting; this fix returns before all of that.

  • The minimal test passes with the fix with assertions on and off (standalone runner; also in an independent reviewer's check).
  • Not run: the full core suite, nightly tests, the format check.

Make DeleteSlice.apply failure-atomic (untested)

#

Drop or skip an entry whose apply throws instead of keeping it for every later apply. This would also cover other ways an entry can throw, such as the delete-buffer overflow addressed by open PR #16867.

Trade-offs

Not built. The entry is shared by the global slice and every per-thread slice, a multi-term entry may have applied some terms before it throws, and simply resetting the slice on a throw would silently drop the deletes of the entries after it. It needs a design discussion; A or B fixes this trigger without it.

Downstream note

#

A service that deletes or updates by an id taken unchecked from a client request lets one id over 32,766 bytes make that writer's next adds, deletes and commit fail and lose its buffered documents; capping ids at 32,766 bytes avoids it.

How it was found

#

Code reading while reviewing how Lucene handles maximum-length terms: the buffer of delete terms has a 32,766-byte key limit that is checked only after the delete is queued. A step-by-step probe confirmed it on main, the 10.6.0 release commit (then its RC1), 10.5.2, 9.9.0 and 9.8.0; it was then reduced to one JUnit test and checked by independent reviewers.

The method in full143 words

Method: code reading, then execution. A hunt unit on maximum-length terms was working through the operation "deleteDocuments(Term...) on long terms" and noticed that since #12573 the delete-term buffer is a BytesRefHash with a 32,766-byte key limit, applied only after the delete is enqueued.

  • A plain step probe (add, commit, add, over-long delete, add, NRT reopen, flush, commit, close) on main, the 10.6.0 release commit (then its RC1), 10.5.2, 9.9.0 and 9.8.0 showed the later failures and the lost buffered documents, with 9.8.0 clean; two more probes covered close() right after the delete and the update APIs.
  • The sequence was then reduced to the one-method JUnit; the history check ran it, in an earlier 50-line version, on every release from 9.7.0 to 10.5.2 and on 9.8.0 with only #12573's change applied; the fact check ran the final test on the 10.6.0 release.

History

#

Introduced in 9.9.0 by #12573 (merged 2023-09-22), which moved buffered delete terms into a BytesRefHash with a 32,766-byte key limit. 9.8.0 passes and 9.8.0 plus only that change fails; all 22 releases from 9.9.0 to 10.5.2, the 10.6.0 release and main fail.

Versions tested7 rows

Introduced by #12573 "Use radix sort to speed up the sorting of deleted terms" (gf2121; merged 2023-09-22, approved by jpountz; milestone 9.9.0): 8b84f6c0965 on main and the branch_9x backport d3a3391d225, both authored 2023-09-22. It replaced BufferedUpdates' Map<Term, Integer> delete-term buffer with per-field BytesRefHash maps on a shared ByteBlockPool. The queue behaviour that keeps a failing entry is older (LUCENE-2956, 2011; the sequence-number change, 2016) and was harmless while applying a term entry could not throw. Not fixed upstream on 2026-10-30.

Finding record

LFV-1046, snapshot of 2026-11-07

Registry title
A deleteDocuments or updateDocument(s) call with a term over 32,766 bytes is rejected but stays in IndexWriter's shared delete queue, so every later add and delete and the next commit, NRT reopen or close() fail until rollback() (regression in 9.9.0; up to 9.8.0 such a delete was a no-op)
Area
index / IndexWriter buffered delete terms (DocumentsWriterDeleteQueue.DeleteSlice.apply, BufferedUpdates.DeletedTerms)
Priority
Medium, rank 18: A released 9.9.0 regression on the default IndexWriter path where one delete or update term over 32,766 bytes leaves the writer unusable until rollback() and drops buffered documents; the trigger is rare and the failure is loud, but the lost buffered documents on the default path keep it in Medium.
Impact class
index unusable
Impact note
Any application on the default IndexWriterConfig, codec and directory of 9.9.0 through 10.6.0 and main that passes one delete or update term longer than 32,766 bytes to deleteDocuments(Term...), updateDocument(Term, ...) or updateDocuments(Term, ...) (also reached through Monitor.deleteById) loses the use of its writer: later adds and deletes throw and the next commit, NRT reopen or close() fails until rollback(), which discards everything buffered since the last commit; committed data stays intact and no scale is needed.
Summary
You add a document, call deleteDocuments(new Term("id", t)) with t longer than 32,766 bytes, and commit. No indexed term can be that long, so you expect the delete to match nothing (as it did up to 9.8.0) or to be rejected, and the commit to contain the document. Instead the delete throws BytesRefHash.MaxBytesLengthExceededException after it was already queued and is never removed from the queue, so every later addDocument and delete throws the same exception and commit() fails (with assertions off an IllegalStateException 'Can't close queue unless all changes are applied', with -ea an AssertionError that closes the writer); the only clean way out is rollback().
Introduced
8b84f6c0965dda01514c196126ed10e57cb6d01a (apache/lucene#12573 'Use radix sort to speed up the sorting of deleted terms', gf2121, approved by jpountz; branch_9x backport d3a3391d225e737126428669bb54630d6c93298e) [exec: commit-level A/B, 9.8.0 passes and 9.8.0 plus only the backport's production change fails with the same messages as 9.9.0]. It replaced BufferedUpdates' Map<Term,Integer> delete-term buffer (no key-length limit) with per-field BytesRefHash maps on a shared ByteBlockPool, which reject keys over BYTE_BLOCK_SIZE - 2 = 32766 bytes. The queue behaviour that keeps a failing node (append before apply; DeleteSlice.apply resets only after every node applied) dates to LUCENE-2956 (e95097a7c8d, 2011) and 058970e72bd (2016) and did no harm while applying a term node could not throw (2023-09-22 (author date of 8b84f6c0965 on main, 00:33:01 -05:00; PR merged 2023-09-22T05:33:01Z; backport authored 01:22:15 -05:00 the same day))
