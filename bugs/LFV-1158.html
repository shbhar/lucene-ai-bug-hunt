ByteBuffersDirectory.rename that fails with IllegalStateException still leaves the file under its new name

When two threads rename the same file in a ByteBuffersDirectory, rename("a", "x") and rename("a", "y"), the losing call throws IllegalStateException but keeps the file under its new name, so listAll() shows [x, y] after the call has failed. It affects 7.5.0 to 10.6.0 and main; the fix is one line.

The finding in 30 seconds

#

Before its throw at :189, rename makes three map calls: read the file under source, publish it under dest, then remove source only if it still holds that file, else throw. Two renames of one source both publish; the loser's removal fails and it throws, but nothing takes its dest back out.

  1. A ByteBuffersDirectory holds one file, a. Two threads rename it at the same time: thread 1 calls rename("a", "x"), thread 2 calls rename("a", "y").
  2. You expect one winner and a loser that leaves nothing behind: the file under exactly one name. Run one after the other, the second call throws NoSuchFileException and only the winner's name remains; on NIOFSDirectory (this JDK and platform) the same two threads kept one name in 20,000 of 20,000 rounds.
  3. rename first publishes the file under the new name, then removes a only if a still holds that file, else it throws. Both calls publish (x and y differ), and only one removal of a can succeed.
  4. Instead the loser throws IllegalStateException: File was unexpectedly replaced: a and never takes its new name back: listAll() is [x, y] until something deletes one of the names. Real threads hit it in 20 of 20 test runs.
  5. The fix is one line: files.remove(dest, file) before the throw.

Who is affected

#

Only applications that, without their own lock, change a file name on a ByteBuffersDirectory (opt-in, @lucene.experimental) while another thread renames it; executed: two renames of one file, as in a claim-by-rename work queue. The loser fails loudly; the extra name is silent for everyone else. No Lucene component does this: IndexWriter's only rename runs under its write lock.

Mechanism, terms and numbers406 words

ByteBuffersDirectory.rename(source, dest) reads the entry under source, publishes it under dest with putIfAbsent, and then removes it from source with the identity-checked remove(source, file); if that remove finds nothing, it throws IllegalStateException("File was unexpectedly replaced: " + source) without taking dest back out (ByteBuffersDirectory.java:181-189 on main). When two renames of the same source run together, both publish their own dest, only one checked remove succeeds, and the loser throws with its dest still bound: the same file stays listed under both new names after the call has failed, until something deletes one of them, although one of the renames reported failure. Run one after the other, the second call throws NoSuchFileException and one name remains, and NIOFSDirectory keeps one name under the same two-thread program. The code shape came from RAMDirectory's rename (LUCENE-7345, 2016) and has been in ByteBuffersDirectory since the class was added (LUCENE-8468, 2018): every release from 7.5.0 to 10.6.0 and main are affected. No Lucene component is known to trigger it. The fix is files.remove(dest, file); before the throw; it belongs in the same patch as LFV-836, the other one-line defect in this method.

Terms

#
  • ByteBuffersDirectory: Lucene's heap-resident Directory. Every file is an entry in one ConcurrentHashMap<String, FileEntry> files (ByteBuffersDirectory.java:93); listAll() lists its keys (:126). FileEntry has no equals (:226), so map removals by value are by identity.
  • rename(source, dest) (:178-192) moves an entry to a name that must not exist yet.

The bug

#
  1. FileEntry file = files.get(source) (:181).
  2. files.putIfAbsent(dest, file) (:185): the file is now visible under both names, which the rename javadoc allows "temporarily" (Directory.java:125-126).
  3. if (!files.remove(source, file)) throw new IllegalStateException("File was unexpectedly replaced: " + source) (:188-189). On this path nothing removes dest.
thread 2: rename("a", "y")              thread 1: rename("a", "x")
  get("a")             -> F
  putIfAbsent("y", F)  -> ok              get("a")             -> F
                                          putIfAbsent("x", F)  -> ok
                                          remove("a", F)       -> true   (returns normally)
  remove("a", F)       -> false
  throw IllegalStateException             <- "y" still maps to F
listAll() = [x, y]

The race needs only that both calls read a before the winner removes it. The message is also misleading here: a was moved by the other call, not replaced. The trailing files.remove(source) at :191 is a different defect (LFV-836) with a different fix; its fix alone leaves this one in place (the independent reproducer's test still fails with it).

Exposure and likelihood288 words
  • Who is exposed. Applications that, with no lock of their own, change one source name on a ByteBuffersDirectory from another thread while a rename of it runs. The executed case is two rename calls with the same source, for example workers that claim a job file by renaming it and expect one winner; a rename racing with deleteFile plus createOutput of its source leaves dest behind the same way by reading, but was not executed. No setting, index size or data shape is needed, and it fails with assertions on and off.
  • Opt-in class. ByteBuffersDirectory is not the default and is @lucene.experimental (:48); its javadoc says MMapDirectory "is nearly always a better choice" (:43-46), and MIGRATE.md calls it "discouraged in favor of the default MMapDirectory".
  • What the caller sees. The losing call throws an unchecked IllegalStateException (rename declares only IOException) with a message that misdescribes the case. Everyone else sees the file under a name whose rename failed, in listAll() and, for a closed file as here, with its complete, correct content through openInput (by reading; a file still open for writing makes openInput throw AccessDeniedException, :241-245), until someone deletes it; a later createOutput("y") gets FileAlreadyExistsException (:158-159, by reading). File contents are never wrong.
  • Lucene's own paths are not known to be affected. IndexWriter's only rename is pending_segments_N to segments_N (SegmentInfos.java:1005), under the write lock, on a name nothing else touches. Most test directories are wrapped in MockDirectoryWrapper, whose rename is synchronized (MockDirectoryWrapper.java:221), and BaseDirectoryTestCase.testRename is single-threaded, so the tests never saw it.
  • Likelihood: contrived. No matching report was found in the recorded searches, although the class has shipped since 7.5.0 (2018).

Minimal repro

#

One JUnit test, single thread, deterministic. rename has no hook between its map calls, so the test swaps the private files map (reflection) for one whose putIfAbsent("y", ...) runs the competing rename("a", "x") right after y is published: exactly where a second thread's rename can land. A forced interleaving; real threads hit it too.

rename("a", "y") throws and leaves nothing behind: listAll() is [x].
Observed

Why it looks unintended

#
  • Directory.rename allows both names only "temporarily"; here a name outlives the call, owned by a call that reported failure.
  • No serial order gives [x, y]: one after the other, the second call throws NoSuchFileException; NIOFSDirectory keeps one name.
  • Lucene's own failure convention removes dest: copyThroughCreateOutput says "On failure, deletes the file named dest".
The full argument288 words
  • The contract. "Renames source file to dest file where dest must not already exist"; "It is permitted for this operation to not be truly atomic, for example both source and dest can be visible temporarily in listAll()" (Directory.java:121-133). On the natural reading, an extra name that outlives the call, held by a call that threw, is not "temporarily"; the javadoc does not spell out rollback or failure atomicity, so this is a reading of the contract, not an explicit guarantee.
  • No serial order gives [x, y]. Sequentially, the second rename("a", ...) finds no a and throws NoSuchFileException (:181-183); the cross-model review executed this control. FSDirectory.rename moves the file with one Files.move(..., ATOMIC_MOVE) (FSDirectory.java:265, after its pending-delete checks), and the devil's-advocate verifier's two-thread program on NIOFSDirectory kept exactly one name in 20,000 of 20,000 rounds (behaviour on this JDK and platform, not a documented Directory requirement).
  • Lucene removes dest when an operation fails. copyThroughCreateOutput: "On failure, deletes the file named dest" (Directory.java:184-185). SegmentInfos.finishCommit deletes dest itself when the step after a successful rename fails (:1006-1013); when rename itself throws, its catch deletes only pending_segments_N (:1014-1017) and does not clean up dest.
  • The check exists to detect interference on source. The identity-checked remove at :188 notices that source no longer holds the file, and the author chose to fail; a half-published dest goes against that choice.
  • History. The shape (publish dest, checked remove, throw) came from LUCENE-7345 (#8399, 2016, "RAMDirectory now enforces write-once as well"), whose discussion never mentions the failure branch; LUCENE-8468 (#9514, 2018) copied it. Nothing in the history says a failed rename was meant to keep dest.
The devil's-advocate check143 words

The strongest case (the devil's-advocate verifier and the review by another model family, OpenAI GPT-5.6, which rated it "moderate"): Directory promises no failure atomicity or linearizability for two conflicting renames of one name; its class javadoc tells applications that need external synchronization to use their own lock (Directory.java:43-45); the class is experimental; and the loser does throw, an unchecked fail-fast check that arguably promises nothing about the state it leaves.

Why it fails: the javadoc's relaxation is both names "temporarily", not an extra name that outlives a failed call; no documented precondition is broken (public API, fresh dest names); Lucene's own failure convention removes dest; and the rollback is one identity-checked line on the failure path. What survives is a severity argument: the loser is loud, the trigger is an application-level race, nothing in Lucene triggers it. Hence priority Low.

Suggested fix

#

Recommended Withdraw dest before the throw (one line)

Add files.remove(dest, file); before the throw at ByteBuffersDirectory.java:189; the identity check leaves a different file under dest alone. Validated: the repro passes (assertions on and off), 29 store suites (778 tests) and :lucene:core:check -x test pass. A combined patch with LFV-836's one-line fix in the same method is validated too.

     if (!files.remove(source, file)) {
+      files.remove(dest, file); // withdraw the publication of a rename that did not happen
       throw new IllegalStateException("File was unexpectedly replaced: " + source);
     }
All options and trade-offs3 options · 564 words

Both built options were validated with gradle in a clean scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-03). Workaround until fixed: do not rename one source name from two threads without your own lock (not on the Directory instance, Directory.java:43-45), delete the dest of a rename that threw, or use FSDirectory / MMapDirectory.

Withdraw dest before the throw (one line) (validated by the checks) (recommended)

#

Undo this call's own publication when its checked remove fails. FileEntry uses identity, so a different file that someone put under dest meanwhile is left alone; the check cannot tell this call's binding apart from a later re-binding of the same entry to dest (see the trade-offs). Single-threaded behaviour is unchanged: the branch is reached only under interference.

     if (!files.remove(source, file)) {
+      files.remove(dest, file); // withdraw the publication of a rename that did not happen
       throw new IllegalStateException("File was unexpectedly replaced: " + source);
     }

Trade-offs

One line on a failure path only, scoped to the race shown here (two renames of one source). The identity check cannot tell this call's binding from a later re-binding of the same entry, so in one longer interleaving, traced by reading and not executed, it removes a binding it did not make: rename("s", "d") publishes d; another thread renames d to z; a third deletes s and creates a new s; the second renames z back to d; the first call's checked remove of s then fails and the fix removes the second thread's successful d, leaving the file with no name, where stock code keeps it under d. It needs four interleaved operations, including a delete-and-recreate of the source (raised by the cross-model fact check of this doc).

Also throw NoSuchFileException when the source is gone (not built)

Downstream note

#

Downstream products that use ByteBuffersDirectory only through IndexWriter are not exposed; only application code that changes one file name from two threads while it is being renamed is.

How it was found

#

A proof-obligation audit of ByteBuffersDirectory against the Directory.rename contract asked what a rename that throws leaves behind, and found the failure branch throws after dest is published. A two-thread public-API JUnit then witnessed the leftover name on the real jar; the forced-order one-test repro was cut from it.

The method in full129 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder, an AI tool, read rename against Directory.rename (Directory.java:121-133): dest may be visible early, but only "temporarily"; the audit's obligation was that a call that fails leaves no lasting effect. The branch at ByteBuffersDirectory.java:188-189 throws after putIfAbsent(dest) has published the file, so that obligation is not met when the checked remove fails.
  • A two-thread public-API JUnit then showed it on the real jar: one call throws, both names stay (main, assertions on and off; 20 of 20 runs; 10.6.0, 9.12.3). An independent reproducer, an executed review by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier wrote their own tests from the claim alone. The single-thread, forced-order repro was cut on 2026-11-02.

LFV-1158, snapshot of 2026-11-03

Registry title
ByteBuffersDirectory.rename throws IllegalStateException without removing the dest it has already published, so two concurrent renames of one source leave the file listed under both new names
Area
store / ByteBuffersDirectory (rename failure path: two concurrent renames of one source)
Priority
Low, rank 841: Two concurrent renames of one source file on a ByteBuffersDirectory leave the file listed under both new names, and the losing call throws a misleading IllegalStateException, in every release since 7.5.0. It needs the experimental heap directory and unsynchronized concurrent renames of the same name, which no Lucene component does, so it is contrived.
Impact class
minor
Impact note
Only applications that call rename on one ByteBuffersDirectory (the non-default, @lucene.experimental heap directory) from two threads with the same source name are hit: the losing call fails loudly with an unchecked IllegalStateException whose message ('File was unexpectedly replaced') misdescribes what happened, but it leaves its dest name bound to the file for good, so every later listAll() and openInput() sees the complete file under a name whose rename reported failure; no scale is needed, it fails with -ea and -da, every release from 7.5.0 to 10.6.0 and main is affected, and no Lucene component is known to trigger it (IndexWriter's only rename, pending_segments_N to segments_N, runs under the write lock on a name nothing else touches).
Summary
Two threads call rename on one ByteBuffersDirectory with the same source and different destinations, rename('a', 'x') and rename('a', 'y'); you expect one call to win and the other to fail and leave nothing behind, which is what happens when the calls run one after the other (the second throws NoSuchFileException) and on FSDirectory. Instead both calls first publish the file under their own dest, then only one of them can remove 'a', and the loser throws IllegalStateException('File was unexpectedly replaced: a') without withdrawing its dest. Afterwards listAll() shows the same file as both 'x' and 'y', permanently, although one of the two renames reported failure.
