All bugs · Lucene bug · LFV-792 · tessellator-cure-adds-triangle-twice

Tessellator.cureLocalIntersections adds each triangle it cuts off twice, so LatLonShape and XYShape index that triangle twice and the shape doc-values centroid counts its area twice

When the Tessellator's cure step cuts a triangle off a self-crossing ring, it stores it twice: POLYGON((6 3, 0 6, 4 0, 3 4, 5 1, 3 2, 6 3)) is indexed as 4 triangles for 3, and its doc values count that triangle twice. No result changed in box-query sweeps; a one-line slip since 8.3.0.

The bug in 30 seconds

#

Background: LatLonShape and XYShape store a polygon as the triangles of its tessellation, one indexed field and one doc-values entry per triangle. When ear clipping cannot find an ear, the Tessellator's cure step looks for a small local self-intersection, cuts that triangle off and carries on.

  1. You index the ring POLYGON((6 3, 0 6, 4 0, 3 4, 5 1, 3 2, 6 3)) with XYShape.createIndexableFields (or LatLonShape, lat = y, lon = x). Its edge (4,0)-(3,4) crosses the edge (5,1)-(3,2). The Polygon and internal Tessellator javadocs exclude self-crossing rings, but the default checkSelfIntersections = false accepts it.
  2. Lucene stores a polygon as triangles. Ear clipping gets stuck on this ring, so a clean-up step ("cure") cuts off the small triangle at a crossing, (3,2) (4,0) (3,4) with area 1, and clips the rest into 2 more: 3 triangles, areas summing to 9.5. You expect 3 indexed triangles.
  3. You get 4: the cure step calls the same tessellation.add(...) twice in a row, with only a comment between the two calls, so (3,2) (4,0) (3,4) is stored twice (areas summing to 10.5). No error.
  4. The shape doc values follow the duplicate: numberOfTerms() is 4 for 3 triangles, and getCentroid() is (3.0, 3.254), which weights that triangle twice, instead of (2.965, 3.386), the area-weighted centroid of the 3 distinct triangles. No search result changed: 129,472 box queries give the same counts with and without the duplicate.
  5. On valid polygons, non-zero-area duplicates were found only together with another Tessellator bug (a hole touching the outer ring, LFV-210), whose fix removes them. Every release since 8.3.0 is affected; 8.2.0 added the triangle once. Deleting the first call fixes it.

Who is affected

#

Applications that index polygons with LatLonShape or XYShape on the default path (checkSelfIntersections = false) and receive self-intersecting rings; on valid polygons, non-zero-area duplicates were found only together with LFV-210. Each cured triangle is indexed twice, and the experimental shape doc values over-count it in numberOfTerms() and getCentroid(). No search result changed in the sweeps run.

Mechanism, terms and numbers724 words

LatLonShape and XYShape index a polygon as the triangles that Tessellator.tessellate returns: one indexed Triangle field and one doc-values triangle per list entry. When ear clipping gets stuck on a ring that crosses itself a little, the Tessellator's cure step, cureLocalIntersections, cuts off the small triangle at the crossing and continues. It appends that triangle with two identical tessellation.add(...) calls (Tessellator.java:890 and :892, only a comment between them), so the shape is indexed with one triangle twice. The ring POLYGON((6 3, 0 6, 4 0, 3 4, 5 1, 3 2, 6 3)), accepted by the default checkSelfIntersections = false, is tessellated into 3 distinct triangles but indexed as 4, because (3,2) (4,0) (3,4) is stored twice; XYShapeDocValuesField.numberOfTerms() is 4 and getCentroid() is (3.0, 3.254), the area-weighted centroid of the 4 entries with the cut-off triangle counted twice, instead of (2.965, 3.386), that of the 3 distinct triangles. No query result changed in the executed box-query sweeps (129,472 queries, the same counts with and without the duplicate). The second call was left by a 2019 edit (LUCENE-8620, first released in 8.3.0); 8.2.0 added the triangle once, as earcut, which the class ports, does. On valid polygons, non-zero-area duplicates were found only together with LFV-210 (a hole touching the outer ring), whose fix removes them; with it fixed, 3 of about 12 million valid lattice polygons still store a zero-area cure triangle twice, through LFV-793. Deleting line 890 fixes it: the repro passes, and the geo and shape test suites pass with assertions on and off.

Terms

#
  • Tessellation: Tessellator.tessellate cuts a polygon into triangles by ear clipping: it repeatedly cuts off a corner triangle (an ear) that lies inside the ring. Each triangle becomes one indexed Triangle field (createIndexableFields) and one doc-values triangle (createDocValueField).
  • Cure step: when no ear is found, the Tessellator first filters points and retries, then calls cureLocalIntersections (Tessellator.java:671-679), which looks for a node whose previous edge intersects the edge after the next node (a crossing, or some touching configurations), cuts off that small triangle, removes the two nodes in between and lets ear clipping continue. It is meant for rings with small self-crossings.

The bug

#
  1. In cureLocalIntersections (Tessellator.java:854-903), for a = node.previous, nextNode = node.next, b = nextNode.next, edge (a, node) crosses edge (nextNode, b) (:862-878). For the example a = (4,0), node = (3,4), nextNode = (5,1), b = (3,2): edge (4,0)-(3,4) crosses (5,1)-(3,2) at (3.571, 1.714), one of the ring's 3 crossings.
  2. It computes the three edge flags (:880-889) and then adds the triangle (a, node, b) twice:
   tessellation.add(new Triangle(a, abFromPolygon, node, bcFromPolygon, b, caFromPolygon));   // :890
   // Return the triangulated vertices to the tessellation                                      // :891
   tessellation.add(new Triangle(a, abFromPolygon, node, bcFromPolygon, b, caFromPolygon));   // :892

Nothing changes between the calls; a traced copy of the class shows the list growing to 1 at line 890 and to 2 at line 892.

  1. It removes (3,4) and (5,1) (:895-896), and ear clipping finishes the ring (3,2) (6,3) (0,6) (4,0) with 2 more triangles.
  2. createIndexableFields and createDocValueField turn every list entry into one stored triangle (XYShape.java:93-130, LatLonShape.java:95-132), so the cut-off triangle is stored twice. ShapeDocValues weights each triangle's centroid by its area (ShapeDocValues.java:428-453, :262-290) and writes the centroid into the doc value at index time (:491-493).

The 3 triangles are (0,6) (3,2) (6,3) with area 7.5, (0,6) (4,0) (3,2) with area 1 and (3,2) (4,0) (3,4) with area 1. LatLonShape gives the same 4 fields for 3 triangles. Because the ring crosses itself, (3,2) (4,0) (3,4) and (0,6) (3,2) (6,3) overlap by 6/13, so 9.5 is a sum of triangle areas, not the area of one region. With checkSelfIntersections = true the ring is rejected ("Polygon self-intersection at lat=1.7142857142857142 lon=3.5714285714285716").

Exposure and likelihood555 words
  • Who. Applications that index polygons through LatLonShape or XYShape createIndexableFields or createDocValueField (the overloads without the flag pass checkSelfIntersections = false; default IndexWriterConfig and codec; one document is enough) and receive self-intersecting rings (a small self-crossing, or a ring that touches or overlaps itself). That is the input the cure step exists for: in #11767 a maintainer wrote "Small self intersections are a reality" and called the step a "best effort" clean-up.
  • Effect. Per cured triangle: one extra indexed triangle (PointValues.size one higher), ShapeDocValuesField.numberOfTerms() one higher, and that triangle's area counted twice in getCentroid(). No exception, and no search result changed in the executed sweeps: 129,472 box queries on this ring, and the finder's 57,800 point-index plus 43,350 doc-values box queries over two other witnesses, give identical counts with and without the duplicate. Only XY box queries were run; the duplicate is an exact copy of a triangle that is already indexed, so every per-triangle relation it produces is one its twin already produces, and no other query is expected to change.
  • Default vs opt-in. Indexing is the default path. The doc-values effects need createDocValueField; ShapeDocValuesField is @lucene.experimental, exists since 9.4.0, and nothing else in Lucene reads its getCentroid().
  • Valid input. Non-zero-area duplicates on valid input were found only together with LFV-210 (a hole touching the outer ring makes the hole bridge pick the wrong vertex): POLYGON((4 2, 3 0, 1 2, 0 0, 0 4, 4 2), (2 1, 3 2, 2 2, 2 1)) indexes 8 triangles, 7 distinct, with (0,0) (3,0) (2,1), which lies outside the polygon, twice, also with checkSelfIntersections = true. LFV-210's one-line fix alone makes this and all 9 known valid witnesses exact, with no cure triangle. Its centroid error is mostly LFV-210's (exact (1.6667, 2.0222); stock (1.5833, 1.4722); duplicate removed (1.5714, 1.6349)). With LFV-210's fix and two other Tessellator fix sketches applied, 3 of about 12 million valid lattice polygons still store a zero-area cure triangle twice (one extra entry and term, no centroid effect); all 3 hit LFV-793, where the filterPoints call after a hole merge drops a vertex copy that the next hole needs. These are search results, not a proof.
  • Scale. No cure triangle occurred in the upstream geo test corpus: 411 polygons (real-world polygons from issues included), each tessellated with checkSelfIntersections off and on (822 tessellations), entered the cure step 43 times and never had a triangle cut off. That corpus is a test set, not prevalence data. Common in synthetic data: of 300,000 random hole-free rings on a 7x7 lattice, main accepts 66,208 and 5,524 of those index a triangle twice; 8.2.0, on the same seeded inputs, stores none twice (it accepts 64,940; the accepted counts differ for other reasons). Hole-free valid rings never reached it: in the exhaustive bound of 64,962,384 small lattice rings, all 1,241,798 rings with a cure triangle are JTS-invalid (self-intersecting; not all self-crossing: 12,696 self-touching rings with no proper crossing reach it too). Each cure triangle takes two nodes out of the ring, and splits and hole bridges add two node copies each, so the number of cure triangles stays linear in the polygon's size.
  • Persistence. The duplicate triangle and the centroid are written at index time; documents indexed before a fix keep them until reindexed, which is harmless for searches.

Why it is a bug, not intended

#
  • Until 8.2.0 the cure step added the triangle once; the 2019 edit LUCENE-8620 added a second, identical call.
  • Earcut, which the class ports, adds it once; numberOfTerms() is documented to count "tessellated triangles".
  • The cure step exists for self-intersecting rings; "unexpected behavior" for them does not cover storing a triangle twice.
The full argument285 words
  • History: a regression from a copy/paste edit. Until 8.2.0 the method ended with // Return the triangulated vertices to the tessellation and tessellation.add(new Triangle(a, node, b));. LUCENE-8620 (apache/lucene-solr#771, 62001b9b965 on master, 252421bb77c on branch_8x, 2019-09-09) added edge flags; in this method it inserted a new add above the comment and rewrote the old add below it into the same call. None of the PR's review comments touches the cure step. Instrumented 8.2.0 and 8.3.0 Tessellators cut off the same triangles, with 1 and 2 adds each.
  • The algorithm it ports adds it once. The class is "inspired by mapbox's earcut algorithm" (Tessellator.java:34); earcut's cureLocalIntersections pushes the cut-off triangle once (read in the earcut source by the devil's advocate, the follow-up and the fact check, which read earcut's current src/earcut.js).
  • The contract is a mesh. "Computes a triangular mesh tessellation for a given polygon" (Tessellator.java:32); numberOfTerms() returns "the number of terms (tessellated triangles) for this shape" (ShapeDocValuesField.java:84); getCentroid() "retrieves the centroid location for the geometry" (:97). Upstream TestTessellator.checkPolygon asserts that the tessellation's area equals the polygon's (TestTessellator.java:1016-1019); in the upstream geo test corpus the cure step never cuts off a triangle, and #11767 and #756 note that the method is not exercised by the tests, so no test could notice.
  • The cure step exists for this input. It cuts off a triangle only where the edge before a node and the edge after the next node intersect (Tessellator.java:865-878; linesIntersect also counts some touching configurations); for hole-free rings every such case found is invalid, self-intersecting input. The default path accepts such rings, and #11767 defends the step as a best-effort clean-up of them.
The devil's-advocate check292 words

The strongest case (the devil's advocate and the adjudication): the only standalone trigger is an invalid, self-intersecting ring, which the javadoc excludes ("No self intersections", Tessellator.java:45; "The polygon must not be self-crossing, otherwise may result in unexpected behavior", Polygon.java:34), and checkSelfIntersections = true rejects rings with a proper crossing such as this one; upstream tests even expect some self-crossing rings to be rejected with the flag off (TestTessellator.java:137-151, 823-861); in #11767 a maintainer proposed removing the method ("As we claim we only support valid polygons, I think it is safe to remove the method entirely"); on valid input the duplicate only doubles one of LFV-210's wrong triangles (or, with LFV-210 fixed, a zero-area one in polygons that hit LFV-793); and no search result changed in the sweeps. The strict flag does not reject every invalid ring that reaches the cure step: a self-overlapping ring POLYGON((4 4, 1 1, 4 1, 2 0, 0 1, 2 1, 4 4)) and 202 small lattice rings with no proper edge crossing, such as POLYGON((0 0, 1 1, 1 3, 0 0, 1 2, 2 0, 0 0)), are accepted with checkSelfIntersections = true and still store a triangle twice (the fact check's runs).

Why it fails as an intent argument: "unexpected behavior" leaves the region of a self-intersecting ring open, not whether the output lists one triangle twice, which is wrong under any reading (4 terms for 3 distinct triangles, and a centroid that weights one triangle twice). Nothing in the code, the history or earcut gives a reason for two adds, and the method added one from 7.5.0 to 8.2.0. What survives is impact: minor, rare in the data tested, no search change observed. Verdict: a defect, low priority.

Suggested fix

#

Recommended Delete the first of the two identical adds

Delete the first of the two identical tessellation.add(...) calls in Tessellator.cureLocalIntersections (line 890, -1 line), which restores the 8.2.0 behaviour. The repro passes, and the geo and shape test suites pass with assertions on and off (366 tests in 45 suites, none failing). Shapes indexed before the fix keep the duplicate until reindexed; searches are unaffected either way.

Trade-offs

  • None for searches: the 129,472-query sweep gives the same counts with and without the duplicate.
  • Existing indexes keep the duplicate triangle and the stored centroid until reindexed; worth one CHANGES line.
  • It does not fix LFV-210, which owns the valid-input trigger (a different line); fixing either leaves the other.

Downstream note

Downstream relevance: a product that aggregates shape doc-values centroids or triangle counts over user-supplied polygons counts the cured triangle twice for that shape; no search result changed in the executed sweeps, and other documents are unaffected.

How it was found

#

While modelling which inputs reach the Tessellator's cure and split stages, the finder read the cure step and saw two identical add calls. Exhaustive and random polygon searches (about 65 million small lattice rings, millions of valid polygons with touching holes) then showed who reaches it: self-intersecting rings and, for a non-zero-area duplicate, valid polygons only together with LFV-210.

The method in full199 words

Method: code reading inside a reachability model, witnessed by bounded search (semi-formal tier).

  • The finder of a hunt unit built a probe harness on the Tessellator's monitor hook to model which inputs reach its CURE and SPLIT stages, and noticed the two identical tessellation.add calls while reading cureLocalIntersections (2026-10-27).
  • Witnesses and reach came from tools: every ring with 4 or 5 vertices on 3x3 and 4x4 lattices, 6 on 4x4 and 5x5, and 7 on 4x4 (64,962,384 rings; every one that has a cure triangle is JTS-invalid, and not all are self-crossing: 12,696 self-touching rings reach it too), random JTS-valid lattice polygons with touching holes (about 4 million on stock, 12 million with the known Tessellator fixes applied), 1.3 million valid floating-point LatLon polygons, the upstream geo test corpus (411 polygons, 822 tessellations) and an exact rational area and centroid oracle. A reduction harness shrank the valid witness.
  • The follow-up's history stage found this ring, which every release from 8.2.0 on accepts, with a seeded search over random hole-free rings.
  • Then an independent reproducer with its own witnesses, reviews by a model from another family (OpenAI GPT-5.6, reading only), an intended-behaviour devil's advocate, an adjudication and a credibility audit.

History

#

Introduced by LUCENE-8620 (apache/lucene-solr#771, 2019-09-09), first released in 8.3.0; 8.2.0 added the triangle once. A version-independent check fails on 37 releases from 8.3.0 to 10.5.2 (36 of them with this ring) and on main, and passes on 8.2.0. The doc-values effects exist since 9.4.0. Not fixed upstream.

Versions tested5 rows

Introduced by LUCENE-8620 "Update Tessellator logic to label if triangle edges belongs to the original polygon" (apache/lucene-solr#771 by iverase, merged 2019-09-09; 62001b9b965 on master, 252421bb77c on branch_8x), first released in 8.3.0. In cureLocalIntersections it inserted a new add above the comment and rewrote the old single add tessellation.add(new Triangle(a, node, b)) below it into the same call. The cure step itself dates from LUCENE-8396 (2018: b5ef13330f1 on master, first released in 8.0.0; the branch_7x commit bc29580378d shipped in 7.5.0) and added the triangle once until 8.2.0. The LUCENE-9570 reformat (2d6ad2fee6d, 2020) made the two lines byte-identical.

The boundary is at release level: the only Tessellator commit between the 8.2.0 and 8.3.0 tags is 252421bb77c, and instrumented 8.2.0 and 8.3.0 Tessellators cut off the same triangles with 1 and 2 adds each. All 47 release tags from 8.3.0 to 10.5.2 carry both adds; 7.5.0 to 8.2.0 carry one. In 8.3.x and 8.4.x the classes lived in lucene-sandbox, in lucene-core from 8.5.0. The release runs (a sample of the tags: 8.3.0, 8.3.1, 8.4.0, 8.4.1, 8.5.0, 8.5.2, 8.6.3, 8.7.0, 8.8.2, 8.9.0, 8.10.1, 8.11.0, 8.11.4, 9.0.0, 9.1.0, 9.2.0, 9.3.0, 9.4.0, 9.4.2, 9.5.0, 9.6.0, 9.7.0, 9.8.0, 9.9.2, 9.10.0, 9.11.1, 9.12.0, 9.12.3, 10.0.0, 10.1.0, 10.2.2, 10.3.2, 10.4.0, 10.5.0, 10.5.1 and 10.5.2, plus 8.6.0 with an earlier version of the main()) used JDK 25, outside the JDKs the 8.x releases support; the failing path is plain Java, and 8.2.0 and the control pass on the same JVM. Not fixed: upstream main 20ced71c1e6e (2026-10-27), branch_10x and branch_10_6 still have both adds.

Bug record

LFV-792, snapshot of 2026-10-29

Registry title
Tessellator.cureLocalIntersections adds each triangle it cuts off twice, so LatLonShape and XYShape index that triangle twice and the shape doc-values centroid counts its area twice
Area
geo / Tessellator cure step (polygon indexing for LatLonShape and XYShape, shape doc values)
Priority
Low, rank 368: This Tessellator duplicate-triangle bug has a rare trigger and leaves query results unchanged, only adding one triangle to the index and skewing the experimental ShapeDocValues centroid, and it needs either an out-of-contract self-crossing ring or a polygon already hit by LFV-210.
Impact class
minor
Impact note
Hits applications on 8.3.0 to 10.5.2 and main that index polygons through the default LatLonShape or XYShape createIndexableFields or createDocValueField (default codec and IndexWriterConfig, no scale) whenever the Tessellator's cure step cuts off a triangle, which on its own happens only for self-crossing rings (excluded by the Polygon and Tessellator javadoc, but accepted with the default checkSelfIntersections=false) and on valid polygons only together with the registered bug LFV-210 (a hole touching the shell, whose one-line fix removes it); the effect is one extra indexed triangle per cured triangle, ShapeDocValuesField.numberOfTerms one too high and that triangle's area counted twice in the experimental getCentroid(), while query results are unchanged (57,800 box queries gave identical counts with and without the duplicate, finder's check) [exec on main, 10.5.2, 9.12.3 and 36 releases from 8.3.0].
Summary
You index a polygon with LatLonShape or XYShape (createIndexableFields or createDocValueField) and expect each triangle of its tessellation to be stored once. When the Tessellator's cure step (cureLocalIntersections) cuts off a triangle to repair a small local self-intersection, it appends that same triangle twice (two identical tessellation.add calls at Tessellator.java:890 and :892, left by LUCENE-8620 in 8.3.0), so the shape carries one extra indexed triangle, ShapeDocValuesField.numberOfTerms is one too high and getCentroid() counts that triangle's area twice; query results do not change. On its own the cure step fires only for self-crossing rings, which the javadoc excludes but the default checkSelfIntersections=false path accepts (for example POLYGON((6 3, 0 6, 4 0, 3 4, 5 1, 3 2, 6 3)), duplicated on every release from 8.3.0), and a valid polygon reaches it only when it already hits LFV-210 (a hole touching the shell), whose fix removes it.
