The finding in 30 seconds

#

A multi-term interval source answers "where is caf*?" in two ways that disagree when two of its terms share a position: the search side says once, matches() says twice. A repeated source turns that into a match that is not there.

Background

#
  1. Stacked tokens. Some analysis chains index two terms at one position: ASCIIFoldingFilter(preserveOriginal=true) indexes café and cafe both at position 0; keyword-repeat stemming, synonyms and n-grams do the same.
  2. Interval queries. Intervals.prefix("caf") stands for any term starting with caf. Intervals.unordered(a, b) needs both a and b; when a and b are the same source it needs two separate occurrences (LUCENE-9099).
  3. Matches. Weight#matches(leaf, doc) tells where a query matched a document and is null when it does not match. The default UnifiedHighlighter builds its highlights from it.

The finding, step by step

#
  1. Index one document whose only word is café, with its folded form cafe stacked at position 0 (ASCIIFoldingFilter with preserveOriginal does this; the test uses two canned tokens).
  2. Search unordered(prefix("caf"), prefix("caf")), "two words that start with caf". count is 0, as LUCENE-9099 intends: the document has one word.
  3. You expect Weight#matches for that document to be null. You get a match at position [0,0], with assertions on and off.
  4. Why: the search side lists position 0 once for caf*, but matches() lists it once per term (café, cafe), and the repeat counts those 2 entries as 2 words.
  5. Effect: on café bar, for bar OR unordered(caf*, caf*) (a hit through bar), the default UnifiedHighlighter returns <b>café</b> <b>bar</b> instead of café <b>bar</b>.

Who is affected

#

Applications that read Weight#matches (or IntervalsSource#matches) or highlight with the default UnifiedHighlighter or the matchhighlight package, for an interval query that repeats one multi-term source (prefix, wildcard, regexp, range, fuzzyTerm), on a field that stacks two matching terms at one position. They get a highlight on a word that did not cause the hit. Hits, counts and scores stay right.

Mechanism, terms and numbers432 words

Some analysis chains index two terms at one position, for example ASCIIFoldingFilter(preserveOriginal=true) indexes café and cafe at position 0. Intervals.prefix("caf") is the disjunction of all terms that start with caf. Its search side, intervals(), merges the expanded terms with the minimising DisjunctionIntervalIterator and reports position 0 once; its matches() merges them with MatchesUtils.disjunction, which keeps one entry per term and reports position 0 twice. Intervals.unordered(caf, caf) and ordered(caf, caf) turn the two equal sources into a RepeatingIntervalsSource that needs two occurrences: the search side sees one and does not match (count 0), the Matches side counts two entries and returns a match. So Weight#matches is non-null for a document the query does not match, and the default UnifiedHighlighter marks café in a hit that matched through another clause. LUCENE-9099 (8.5.0) added the repeat handling and fixed this same iterator-versus-Matches mismatch for Intervals.or only. Every release from 8.5.0 to 10.6.0 and main is affected; a fix that reports each position once passes the repro and the intervals and highlighter tests.

The bug (main f794ff5a505c)

#
  1. Search side: one entry per position. MultiTermIntervalsSource.intervals() merges the per-term iterators with DisjunctionIntervalIterator (MultiTermIntervalsSource.java:76). Its nextInterval() pops and advances every sub-iterator whose interval contains the current one (DisjunctionIntervalsSource.java:222-247), so café and cafe at position 0 give one interval [0,0].
  2. Matches side: one entry per term. matches() collects one TermIntervalsSource.matches per expanded term (:86-97) and merges them with MatchesIterator mi = MatchesUtils.disjunction(subMatches); (:98), a DisjunctionMatchesIterator that keeps duplicates ("Matches may overlap, or be duplicated", DisjunctionMatchesIterator.java:36-38): [0,0] for café and [0,0] for cafe.
  3. The repeat counts entries. unordered(x, x) and ordered(x, x) become RepeatingIntervalsSource(x, 2) (UnorderedIntervalsSource.java:33-57, OrderedIntervalsSource.java:29-57). Its search side wraps x.intervals() (RepeatingIntervalsSource.java:66-72) and finds one occurrence: no match, count 0. Its Matches side takes two copies of x.matches() (:74-86); DuplicateMatchesIterator.build advances the first copy by one entry and the second by two and returns null only when a copy runs out (:237-248). Two entries at one position are enough: non-null.
  4. The sibling is right. Intervals.or builds its Matches over the same minimising iterator (DisjunctionIntervalsSource.java:85-105), so unordered(or(cafe, café), or(cafe, café)) gives null Matches on the same document.

The numbers

#

One document, tokens café (position 0, offsets 0-4) and cafe (position increment 0, offsets 0-4). prefix(caf): intervals() gives [0,0] once, matches() gives [0,0] twice. unordered(caf, caf): count 0, Weight#matches non-null with one match [0,0]. Document café bar, query bar OR unordered(caf*, caf*): 1 hit, highlight <b>café</b> <b>bar</b> (with the fix: café <b>bar</b>).

Why it looks unintended

#
  • Weight#matches must be null "if the document does not match the parent query"; here count is 0 for the same document.
  • The intervals module's own test helper asserts that matches() returns exactly the iterator's intervals, and null when there are none.
  • LUCENE-9099 fixed this same mismatch for Intervals.or, whose equivalent query gives null Matches here.
The full argument128 words
  • The contract. Weight#matches: "Returns Matches for a specific document, or null if the document does not match the parent query" (Weight.java:67-69). IntervalsSource#matches iterates "the intervals defined by this IntervalsSource" (IntervalsSource.java:47-51); intervals() exposes "the minimum intervals" (:35-37).
  • Tests. TestIntervals.checkIntervals asserts matches() against the iterator entry for entry and null when there is no interval (TestIntervals.java:129-180). A grep of the intervals and highlighter tests found no test that runs a multi-term interval source on a document with stacked tokens.
  • History. LUCENE-9099 (CHANGES.txt:6102-6107): UNORDERED(foo, foo) must not match a document containing foo once. Its commit aa916bac3c3 says "DisjunctionIntervalIterator minimizes its intervals, while MatchesUtils.disjunction does not, so there was a discrepancy between the two methods" and fixed it for Intervals.or only.
The devil's-advocate check187 words

Strongest case for "intended": generic Matches may hold duplicates. MatchesIterator says "Match intervals may overlap" (MatchesIterator.java:33), DisjunctionMatchesIterator documents duplicated matches (:36-38), core multi-term queries list one entry per term at a stacked position, a 2018 design comment said a MatchesIterator "can return duplicates" (#9333, LUCENE-8286), Matches/MatchesIterator are @lucene.experimental, and Intervals.unordered says "The subsources may overlap" (Intervals.java:432), so two different terms stacked at one position could be read as two witnesses.

Why it fails: that defends the duplicate entries of a single, non-repeated prefix (not claimed on its own), not a non-null Weight#matches for a document the query does not match. Whichever reading of a stacked position is chosen, the search side and the Matches side must give the same one; the search side decides hits and follows LUCENE-9099, so the hit count is the reference. The interval classes carry no experimental tag, and the module chose minimised Matches for or() on purpose. The independent reviewer from another model family (OpenAI GPT-5.6) rated the defence moderate and rejected it; the intended-behaviour verifier found no argument that covers the observable.

Suggested fix

#

Recommended (a) One Matches entry per position, coalescing the expansions there (recommended, validated)

In MultiTermIntervalsSource.matches, replace MatchesUtils.disjunction (line 98) with a small iterator that reports each position once, as intervals() does: offsets span all expansions there and sub-matches list each one. The repro passes, and the intervals (118 tests) and uhighlight/matchhighlight (526 tests) packages pass.

for (IntervalMatchesIterator mi : started ? current : subs) {
  if (advancePast(mi, position)) queue.add(mi); // first entry after this position
}
started = true;
if (queue.size() == 0) {
  position = IntervalIterator.NO_MORE_INTERVALS;
  return false;
}
current.clear();
position = queue.top().startPosition();
while (queue.size() > 0 && queue.top().startPosition() == position) {
  current.add(queue.pop()); // the diff keeps these in offset order
}
return true;

(a) One Matches entry per position, coalescing the expansions there (recommended, validated)

#

The change is +156/-38 lines in MultiTermIntervalsSource.java: matches() returns a MultiTermMatchesIterator, a priority queue over the per-term iterators by position. Each next() reports the next position once; startOffset/endOffset span every expansion at that position, getSubMatches() lists them in offset order (null for one term), and a term indexed twice at one position is skipped past (advancePast). Condensed next():

for (IntervalMatchesIterator mi : started ? current : subs) {
  if (advancePast(mi, position)) queue.add(mi); // first entry after this position
}
started = true;
if (queue.size() == 0) {
  position = IntervalIterator.NO_MORE_INTERVALS;
  return false;
}
current.clear();
position = queue.top().startPosition();
while (queue.size() > 0 && queue.top().startPosition() == position) {
  current.add(queue.pop()); // the diff keeps these in offset order
}
return true;

Trade-offs

  • About 120 more lines than today's wrapper; the per-call cost is a priority queue over the expansions that match in the document, as MatchesUtils.disjunction already uses.
  • Offsets of a stacked position become the union of its expansions (wi-fi and wi at one position highlight as wi-fi).
  • Open #11113 (a NullPointerException through this wrapper after the iterator is exhausted, no stacked tokens) touches the same code; #11113's repro was not run.
  • In the finder's sweep, 114 cases that passed on stock moved into an existing conjunction-offsets class: a stacked token spanning several positions now shows its wider offsets as a sub-match while the enclosing unordered match keeps its first-start..last-end offsets, a rule stock already shows on other documents.

Downstream note

#

Only Matches and highlights inside a document that was returned anyway, or that the application asked about, are wrong; an application that uses Weight#matches to decide something, rather than only to display it, would act on a match that is not there.

How it was found

#

Semi-formal: bounded-exhaustive translation validation of the intervals algebra. A model-based check compared 4,032 interval expressions on 2,139 small documents with stacked tokens against an exact per-token reference; one class of mismatches was a multi-term source listing a stacked position once per term. Code reading found the merge, and it was reduced to the one-test JUnit.

The method in full96 words

Method: enumerate small documents whose tokens may share positions, evaluate every interval expression up to depth 1 both on the real jars (search side and Weight#matches) and on an exact per-token reference, and group the disagreements into classes. On stock main this class had 1,837 cases where Weight#matches and the hit disagree and 103,195 cases where Matches positions differ from the iterator's; with the finder's fix both are 0.

The witness was a public-API probe, then the JUnit with ASCIIFoldingFilter and ordered; a minimal-repro check reduced it to the canned-token unordered test shown here.

Applications that read Weight#matches, or highlight with the default (WEIGHT_MATCHES) UnifiedHighlighter, for an interval query that repeats one multi-term source (Intervals.ordered, unordered or unorderedNoOverlaps of the same prefix, wildcard, regexp, range, fuzzyTerm or multiterm source, maxgaps over such an ordered, or the flexible StandardQueryParser's fn: syntax) over a field whose analysis indexes two terms matching that source at one position (ASCIIFoldingFilter preserveOriginal, KeywordRepeatFilter with a stemmer, WordDelimiterGraphFilter preserveOriginal, EdgeNGramTokenFilter, SynonymGraphFilter with keepOrig) get non-null Matches for documents the query does not match, so the highlighter marks a word that did not cause the hit, with the default codec, IndexWriterConfig and searcher, -ea and -da and no scale; on documents the query does match the finder's sweep also shows extra non-minimal Matches; hits, counts and scores stay right; every release since 8.5.0.
Summary
You index the one-word text 'café' with WhitespaceTokenizer + ASCIIFoldingFilter(preserveOriginal=true), which puts 'café' and 'cafe' at position 0, and run IntervalQuery("f", Intervals.ordered(prefix("caf"), prefix("caf"))), that is two words starting with 'caf'. Search agrees that the document does not match (count 0), so Weight#matches must return null, as its javadoc says and as the same query written with Intervals.or(term("cafe"), term("café")) does. Instead Weight#matches returns a match at [0,0]: MultiTermIntervalsSource.matches merges the two expanded terms with MatchesUtils.disjunction, which lists position 0 once per term while intervals() lists it once, and the repeated source counts the two entries as two occurrences, so the default UnifiedHighlighter marks 'café' in 'café bar' for a hit of 'bar OR ordered(caf*, caf*)' that matched only through 'bar'.
