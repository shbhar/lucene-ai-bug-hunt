UnifiedHighlighter with maxNoHighlightPassages below -1 throws 'Illegal Capacity' when a document's field text has no match, although the javadoc says any value below 0 falls back to maxPassages

The javadoc says any maxNoHighlightPassages below 0 falls back to maxPassages, but the code maps only exactly -1. With -2, any document whose field has text but no match makes the highlight call throw IllegalArgumentException: Illegal Capacity: -2 instead of returning its first sentence.

The finding in 30 seconds

#

When a hit has no match in the highlighted field, the UnifiedHighlighter returns a summary of the field's first sentences; maxNoHighlightPassages says how many. The code turns only exactly -1 into maxPassages. Any other negative value is used as the count itself, and the summary method then asks the JDK for a list with that negative capacity.

Background: the no-match summary

#
  1. The UnifiedHighlighter cuts a field into passages (by default, sentences) and returns the best ones that contain a query match.
  2. If a document is a hit but nothing in the field matches, it returns a summary instead: the field's first sentences. maxNoHighlightPassages sets how many. By the javadoc, any value below 0 (the default is -1) means "as many as maxPassages", 0 means no summary (null), and a positive value is the count.

The finding, step by step

#
  1. Index one document, body = First sentence. Second sentence., and search MatchAllDocsQuery: a hit, but no word in body matches. highlight("body", query, topDocs, 1) with the default maxNoHighlightPassages (-1) returns the summary First sentence. .
  2. Build the highlighter with withMaxNoHighlightPassages(-2). You expect the same First sentence. : the javadoc says any value below 0 means "use maxPassages" (here 1); only 0 means no summary.
  3. You get IllegalArgumentException: Illegal Capacity: -2. -3, Integer.MIN_VALUE, the deprecated setter and a subclass returning -5 fail the same way; in a two-field highlightFields call the field that did match loses its snippet too.
  4. Why: FieldHighlighter.java:93 swaps in maxPassages only for exactly -1, so -2 reaches new ArrayList<>(Math.min(-2, 10)) at line 112, and the JDK rejects a negative capacity. < 0 instead of == -1 fixes it.

Who is affected

#

Code that sets maxNoHighlightPassages to a negative value other than -1, through the builder, the deprecated setter or an override of the protected getter, for example -2 or Integer.MIN_VALUE as "unset". Every highlight call that includes a document whose field has text but no match then fails. The default -1 works, and the failure is loud.

Mechanism, terms and numbers612 words

When a document is a hit but nothing in the highlighted field matches, the UnifiedHighlighter returns a default summary: the field's first sentences. The javadoc of getMaxNoHighlightPassages says how many: "If it's less than 0 (the default) then this defaults to the maxPassages parameter given for each request. If this is 0 then the resulting highlight is null (not formatted)." (UnifiedHighlighter.java:634-639 on main 645d4fe14a20). The code maps only exactly -1, the default: getSummaryPassagesNoHighlight(maxNoHighlightPassages == -1 ? maxPassages : maxNoHighlightPassages) (FieldHighlighter.java:91-93). Any other negative value is used as the sentence count, and in the stock implementation the list allocation at the top of getSummaryPassagesNoHighlight, new ArrayList<>(Math.min(maxPassages, 10)) (:112, right after an assert), throws IllegalArgumentException: Illegal Capacity: -2 from the JDK. With withMaxNoHighlightPassages(-2), Integer.MIN_VALUE, the deprecated setter or an override of the protected getter, every highlight call that includes a document whose field has text but no match fails, with assertions on and off; in a multi-field call the other fields lose their snippets too. Documents with a match are highlighted normally. The check, the capacity line and the javadoc all came in the first UnifiedHighlighter commit (LUCENE-7438, 2016); every release from 6.3.0 to 10.6.0 and main is affected. A one-character change, < 0 instead of == -1, fixes it.

The code (main 645d4fe14a20, lucene/highlighter/.../uhighlight/)

#
  • Where the value comes from. The default is DEFAULT_MAX_HIGHLIGHT_PASSAGES = -1 (UnifiedHighlighter.java:116). Builder#withMaxNoHighlightPassages(int) stores any int, with no check and no javadoc (:401-404), as does the deprecated setMaxNoHighlightPassages (:216-219). The protected getMaxNoHighlightPassages(String field) returns it (:640-642) under the contract quoted above (:634-639), and getFieldHighlighter passes it to each FieldHighlighter (:1138).
  • The sentinel check. FieldHighlighter.highlightFieldForDoc returns null at once for empty content (FieldHighlighter.java:77-79; a document without a stored value is skipped earlier, UnifiedHighlighter.java:968-969); otherwise it scores passages (:86), and when none matched (:89) it calls getSummaryPassagesNoHighlight(maxNoHighlightPassages == -1 ? maxPassages : maxNoHighlightPassages) (:91-93). Only exactly -1 becomes maxPassages.
  • The throw. The stock getSummaryPassagesNoHighlight(int maxPassages) (protected, :109-128) first asserts that the break iterator is at the start (:110; it is on the stock path, and the -ea runs pass it), then allocates new ArrayList<>(Math.min(maxPassages, 10)) (:112). Math.min(-2, 10) = -2, and the JDK's ArrayList(int) throws IllegalArgumentException("Illegal Capacity: -2").
  • Why 0 and positive values work. Math.min(0, 10) = 0 gives an empty list, the loop while (passages.size() < maxPassages) (:115) does not run, and :96-99 returns null, the documented 0 behaviour; positive values collect that many sentences.
  • Reach. highlight and highlightFields end in highlightFieldsAsObjects, whose loop calls highlightFieldForDoc (UnifiedHighlighter.java:987-988) with no per-field or per-document catch, so one unmatched document fails the whole call. highlightWithoutSearcher reaches the same method (:1105-1107).

Exposure and likelihood181 words
  • Who is hit. Code that configures the UnifiedHighlighter with a negative maxNoHighlightPassages other than -1: Builder#withMaxNoHighlightPassages, the deprecated setMaxNoHighlightPassages, or a subclass overriding the protected getMaxNoHighlightPassages hook; for example a developer who reads "less than 0 (the default)" and uses -2 or Integer.MIN_VALUE, or an application that forwards an unchecked configuration value.
  • Default vs opt-in. The default (-1) works; the trigger is a non-default configuration value. Then, with the stock FieldHighlighter, any document whose field has text but no match triggers it, with any index and any offset source.
  • What goes wrong. The call throws instead of returning the summary; in a multi-field call all fields lose their snippets. The message names a JDK list capacity, not the parameter. No wrong results, corruption or hang.
  • Scale. None needed: one document, one call; deterministic, assertions on or off.
  • Workaround. Use -1 for "same as maxPassages".
  • How likely. Rare: someone has to pick a negative value other than -1, the failure is loud on the first unmatched document, and the recorded searches found no report in ten years.

Why it looks unintended

#
  • The javadoc covers every negative value: "If it's less than 0 (the default) then this defaults to the maxPassages parameter given for each request."
  • That sentence and the == -1 check came in the same 2016 commit; no test, changelog or discussion limits the sentinel to -1.
  • Intended rejection looks different: withMaxLength rejects bad values up front, with a message.
The full argument223 words
  • The written contract covers every negative value. getMaxNoHighlightPassages: "If it's less than 0 (the default) then this defaults to the maxPassages parameter given for each request. If this is 0 then the resulting highlight is null (not formatted)." (UnifiedHighlighter.java:634-639). The setters have no javadoc of their own. The highlight javadoc promises the same fallback: "If no highlights were found for a document, the first maxPassages sentences from the field will be returned." (:759-761).
  • Not a later narrowing. The javadoc sentence, the == -1 check and the capacity line all arrived in LUCENE-7438 (722e82712435, 2016-10-04); no test, CHANGES or MIGRATE entry restricts the sentinel to -1, and neither #8490 nor its review discusses other negative values.
  • Intended rejection looks different. withMaxLength and setMaxLength reject bad values up front with "maxLength must be < Integer.MAX_VALUE" (:355-362, :191-199). Here nothing validates; the error is an incidental JDK capacity check, thrown late (only when an unmatched document is reached) and naming neither the parameter nor the cause.
  • The same module treats a documented -1 as "any negative". TokenStreamFromTermVector documents "-1 disables the limit" and implements maxStartOffset < 0 ? Integer.MAX_VALUE : maxStartOffset (TokenStreamFromTermVector.java:83-87).
  • Tests. Upstream tests pass only 0 (TestUnifiedHighlighter.java:843, TestUnifiedHighlighterTermIntervals.java:673) or the default; no test covers another negative value either way.
The devil's-advocate check163 words

The strongest case for "works as designed" (the cross-model lenses, the independent reproducer, the devil's-advocate verifier and the adjudication): the default constant is exactly -1 and the check has been == -1 from the start; Solr's override returns exactly -1 (by code reading); the setters carry no javadoc; UnifiedHighlighter is @lucene.experimental and FieldHighlighter @lucene.internal; a negative sentence count other than -1 has no natural meaning; nobody reported it in ten years.

Why it fails: the only written description of the value explicitly covers every value below 0 and came in the same commit as the check; nothing in the code, tests or history says -1 alone; and even if -1 were meant to be the only sentinel, the result should be a clear up-front rejection, not a late JDK exception that only fires for unmatched documents and takes the other fields of the call down with it. Either reading leaves a defect: the code and the javadoc disagree. Verdict: real, low impact.

Suggested fix

#

Recommended Map every negative value to maxPassages (one character)

Treat every negative value as the default: maxNoHighlightPassages < 0 ? maxPassages : maxNoHighlightPassages at FieldHighlighter.java:93 (one character). -1, 0 and positive values behave as before; -2 now gives First sentence. . With it the repro and all 723 highlighter-module tests pass.

        passages =
            getSummaryPassagesNoHighlight(
                maxNoHighlightPassages < 0 ? maxPassages : maxNoHighlightPassages);
All options and trade-offs2 options · 488 words

Two options. The < 0 check matches the only written contract and was validated with gradle in a scratch worktree at 645d4fe14a20; making -1 the documented sentinel and rejecting other negatives up front is the alternative a maintainer may prefer (not executed). Either way, do not fix only the capacity line (for example Math.max(0, Math.min(maxPassages, 10)) at :112): the loop while (passages.size() < maxPassages) (:115) then never runs for a negative count, so -2 would silently return null, the documented 0 behaviour, still contradicting the javadoc (code reading). A natural combination: the < 0 check plus one sentence of javadoc on Builder#withMaxNoHighlightPassages that repeats the getter's contract.

Map every negative value to maxPassages (one character) (validated by the checks) (recommended)

#

In FieldHighlighter.highlightFieldForDoc, compare with < 0 instead of == -1.

        passages =
            getSummaryPassagesNoHighlight(
                maxNoHighlightPassages < 0 ? maxPassages : maxNoHighlightPassages);

Trade-offs

  • Stock FieldHighlighter: -1 unchanged; every other negative value now gives the first maxPassages sentences, as the javadoc says; 0 and positive values unchanged. No API change.
  • It validates nothing, so a subclass override of the getter returning a negative value is treated as the default too, which is what the javadoc promises.
  • Custom extensions are the one thing to consider: the mapping happens before the protected getSummaryPassagesNoHighlight(int) hook, so a custom FieldHighlighter that overrides that hook and relies on receiving a raw negative value other than -1 would now get maxPassages (upstream's extensibility test subclasses FieldHighlighter from outside the package, TestUnifiedHighlighterExtensibility.java:167-194, :259-284; code reading).
  • It does not cover a negative maxPassages request argument, which has no documented range and is not claimed here: with the default -1 such a value reaches the same line 112, with or without the fix (code reading).

Make -1 the documented sentinel and reject other negatives up front

#

Change the getter javadoc to say -1 (the default), and throw IllegalArgumentException with a message for values below -1 in Builder#withMaxNoHighlightPassages and setMaxNoHighlightPassages, as withMaxLength does. Not executed.

Trade-offs

A clear, early error, consistent with withMaxLength. But it narrows the documented contract, and a subclass that overrides getMaxNoHighlightPassages bypasses the setter check, so FieldHighlighter.java:93 (or getFieldHighlighter) would need a check too.

Downstream note

#

By code reading of one default-branch revision each (not exhaustive), the default implementations of Solr (which passes -1 or 0), Elasticsearch and OpenSearch (which pass 0 or 1 and replace the summary method) do not pass such a value, so the known exposure is applications that set it themselves.

How it was found

#

Bounded-exhaustive translation validation: the highlighter's passage and summary code was compared with a reference written from its javadoc, on every short text up to a size bound. Writing the reference exposed the == -1 check; the exhaustive run then showed every no-match call with -2 throwing, and a public-API test confirmed it.

The method in full146 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier), in a hunt unit on the UnifiedHighlighter's passage layer, run on the stock main jars at ea57360912ed.

  • A reference implementation of passage splitting and the default summary was written from the javadoc (for the summary: N = maxPassages when maxNoHighlightPassages < 0), plus the oracle "no exception on legal input".
  • The harness compared the real jar with it on every text of up to 5 code points over the alphabet {a, b, space, '.', U+1D400, '<', '&'}, 7 break iterators, maxPassages 1 to 3 and maxNoHighlightPassages -2 to 2.
  • The first signal was code reading: the finder noticed the == -1 check while writing the reference. The exhaustive run witnessed it: every no-match call with -2 threw Illegal Capacity: -2 (604,380 per iterator). A hand-written public-API JUnit confirmed it, later reduced to the single test shown here.

Applications on any release from 6.3.0 through 10.6.0 or on main that configure the UnifiedHighlighter with a maxNoHighlightPassages value below -1 (Builder#withMaxNoHighlightPassages, the deprecated setMaxNoHighlightPassages, or an override of the protected getMaxNoHighlightPassages hook), which the getter's javadoc says means 'use maxPassages', get IllegalArgumentException 'Illegal Capacity: N' from the JDK ArrayList constructor instead of the default summary for every document with no match in the highlighted field, and by code reading the whole multi-field call fails; documents with a match are highlighted normally, nothing is corrupted, there is no hang, no index size is needed, and Solr (-1 or 0 only), Elasticsearch and OpenSearch (0 or 1, with their own summary method) never pass such a value (code reading).
Summary
You build a UnifiedHighlighter with withMaxNoHighlightPassages(-2), or any other negative value except -1, relying on the getMaxNoHighlightPassages javadoc: 'If it's less than 0 (the default) then this defaults to the maxPassages parameter given for each request.' For a document with no match in the field you expect the same default summary as with -1, for example 'First sentence. '. Instead FieldHighlighter maps only exactly -1 to maxPassages and passes -2 on to getSummaryPassagesNoHighlight, whose new ArrayList<>(Math.min(-2, 10)) throws IllegalArgumentException 'Illegal Capacity: -2', so the highlight call fails.
