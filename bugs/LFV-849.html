The bug in 30 seconds

#

The completion filter adds romaji tokens to each Japanese word, read row by row from the bundled table romaji_map.txt, so a suggester can match Latin-letter input.

  1. You index 雑誌 (zasshi), 決して (kesshite), マッチ (macchi) and 三つ (mittsu) as suggestions with JapaneseCompletionAnalyzer, plus 一緒 (issho) and 抹茶 (maccha), and query with PrefixCompletionQuery.
  2. You expect zasshi to suggest 雑誌, as issho suggests 一緒: the javadoc lists modified Hepburn, and doubling the consonant is how input methods type a small tsu.
  3. Instead all four return no suggestion, with no error. Of the Latin spellings tried, only the Kunrei ones work (zassi finds 雑誌, mittu finds 三つ); committed kana work too.
  4. Why: 雑誌 is indexed as [雑誌, zassi]. Its table row ッシ,ssi has one spelling, while シ,si,shi has two and the neighbour ッショ,ssyo,ssho doubles sh. ッチ (tti) and ッツ (ttu) are the same.
  5. Input-method users lose it while composing: ざっｓ (zass) finds 雑誌, ざっｓｈ (zassh) finds nothing, the committed ざっし finds it again.

Who is affected

#

Applications using the opt-in JapaneseCompletionAnalyzer or JapaneseCompletionFilter (also exposed by search servers as kuromoji_completion), with the standard INDEX/QUERY configuration, in every release since 9.0.0. Familiar words, for example 雑誌, 決して, マッチ, 三つ, こっち, 抹茶 (how often such words occur was not measured). People typing raw romaji lose the suggestion; input-method users lose it while composing. Committed kana still match.

Mechanism, terms and numbers580 words

Kuromoji's completion analyzer (JapaneseCompletionAnalyzer, JapaneseCompletionFilter) indexes each Japanese word together with its romaji spellings, so an autocomplete can match Latin-letter input. Its bundled table romaji_map.txt gives the small-tsu rows ッシ, ッチ and ッツ a single Kunrei-style spelling (ssi, tti, ttu), although the base rows list shi, chi, tsu and the neighbouring small-tsu rows double the consonant (ssha, ccha, jji). So 雑誌, 決して, マッチ and 三つ are indexed only as zassi, kessite, matti and mittu, and typing the modified-Hepburn or input-method spellings zasshi, kesshite, macchi or mittsu suggests nothing, with no error. It affects every release from 9.0.0 to 10.5.2 and main; the fix is data only.

Terms

#
  • Small tsu (sokuon, ッ / っ): doubles the next consonant. 雑誌 is read ザッシ, za-sshi.
  • Romanizations: modified Hepburn writes シ, チ, ツ as shi, chi, tsu and a small tsu before them as sshi, tchi, ttsu (雑誌 zasshi, 三つ mittsu, 抹茶 matcha); Kunrei-shiki writes si, ti, tu (zassi, mittu). Japanese input methods accept both and type a small tsu by doubling the consonant (ss, cc, tt) or with tch; macchi is such an input-method spelling.
  • JapaneseCompletionFilter: for each word it emits the word itself and every romaji spelling of its katakana reading at the same position. The spellings come from romaji_map.txt, where each row maps a key, mostly a kana unit, to its spellings (for example シ,si,shi); the reading is matched longest key first, and every spelling of every matched row is combined (KatakanaRomanizer.java:103-169). The javadoc lists "(modified) Hepburn-shiki, Kunrei-shiki (Nihon-shiki) and Wāpuro shiki" as supported (JapaneseCompletionFilter.java:41-42).
  • Completion query: PrefixCompletionQuery matches a suggestion when the typed text, after the QUERY-mode analyzer, is a prefix of one of the suggestion's indexed forms. Raw romaji such as zasshi comes out as the single token zasshi; no romaji token is added.

The numbers

#

Index-side tokens on main: 雑誌 → [雑誌, zassi], 決して → [決して, kessite], マッチ → [マッチ, matti], 三つ → [三つ, mittu], こっち → [こっち, kotti]; compare 一緒 → [一緒, issyo, issho] and 抹茶 → [抹茶, mattya, maccha, maccya]. Typed zasshi, kesshite, macchi, matchi, mittsu, matcha: no suggestion, and kocchi is not a prefix of any token of こっち. Typed zassi, kessite, issho, maccha: found. Lucene's Hepburn reading filter (JapaneseReadingFormFilter, useRomaji=true) gives zasshi, kesshite, matchi, mittsu, matcha for the same words.

The code follows the table: romanize() matched a separately coded longest-match model of the same table, bounded-exhaustively, on all 1,830,854 inputs of length up to 3 and on 57,289,761 inputs of length 4 (0 mismatches; a shortest-match mutant was caught). That shows implementation and model agree over the tested domain; the omission itself is in the data rows.

Exposure and likelihood223 words
  • Who. Applications that build Japanese autocomplete with JapaneseCompletionAnalyzer or JapaneseCompletionFilter (also through the analysis SPI as japaneseCompletion; search servers built on Lucene expose it as a kuromoji_completion token filter). Opt-in; it reproduces with the standard INDEX/QUERY configuration, no user dictionary and no custom table.
  • What triggers it. Ordinary words whose reading has ッシ, ッチ or ッツ, typed in modified Hepburn or the way input methods type them: 雑誌 zasshi, 決して kesshite, マッチ macchi / matchi, 三つ mittsu, こっち kocchi, and 抹茶 matcha (the tch gap). No special input, no scale.
  • Two groups of users. People who type romaji directly lose the suggestion completely. Input-method users lose it between the small tsu and the completed kana (ざっｓｈ → zassh, みっｔｓ → mitts); handling such mid-composition strings is a stated goal of the feature (JapaneseCompletionFilter.java:184-188).
  • What still works. Kana committed through an input method (ざっし → zassi) and the Kunrei spellings (zassi, mittu).
  • Silent. No exception, no log line: the suggestion list is just shorter.
  • After a fix the index-side tokens change, so existing suggest fields must be reindexed. The query side needs no code or configuration change; QUERY mode loads the same table, so kana queries gain the new spellings too (with fix C, ざっし → [ざっし, zassi, zasshi]).

Why it is a bug, not intended

#
  • The javadoc lists "(modified) Hepburn-shiki" as supported; zasshi, mittsu and matcha are Hepburn, and Lucene's own Hepburn reading filter emits them.
  • The same table doubles sh, ch, j and f on the neighbouring small-tsu rows (ッショ,ssyo,ssho, ッチャ,ttya,ccha,ccya, ッジ,zzi,jji).
  • In the introducing PR's review, the same kind of gap (no jji on ッジ) was fixed on request: "yes, of course".
The full argument349 words
  • The contract names modified Hepburn. JapaneseCompletionFilter.java:41-42 and romaji_map.txt:3 list "(modified) Hepburn-shiki" as supported. zasshi, kesshite, mittsu and matcha are the modified-Hepburn forms, and JapaneseReadingFormFilter with useRomaji=true emits them.
  • The feature exists to cover more than Hepburn. The introducing issue #11140 says JapaneseReadingFormFilter "supports only modified Hepburn-shiki, so it isn't sufficient to cover all possible romanized forms". For these words the completion filter covers fewer forms than that filter.
  • The disclaimer's example does not explain it. JapaneseCompletionFilter.java:44-48: "This does not strictly comply with the romanization systems listed above, but tries to cover possible keystroke supported by various Input Methods. e.g.: Circumflex / Macron representing Chōonpu (長音符) are not supported." Doubled consonants (ss, cc, tt) and tch are ordinary input-method keystrokes for a small tsu (the open-source Mozc input method maps each to っ), so the disclaimer's stated aim argues for them. Its example ("e.g.") of what is not supported is long-vowel marks; no comment, test or doc names the small-tsu rows. The first wording, replaced a day later by 5dfbef313cf (before 9.0.0), excluded "romanji forms which are official but not commonly used with Japanese Input Methods".
  • The neighbouring rows follow the rule. The table doubles sh, ch, j and f on the neighbouring small-tsu rows (:189-191, :193, :205-207, :218); the base rows シ, チ, ツ list two spellings each. (It is not consistent everywhere: a sibling bug covers two copy errors on other small-tsu rows, :281 ッスォ and :289 ッドゥ.)
  • The same gap was fixed on request. In the review of PR #297, a reviewer (GitHub johtani) asked on the ッジ,zzi row "Should we add jji? I usually use jajji for ジャッジ"; the author (GitHub mocobeta) answered "yes, of course" and added jji, jja, jju, jjo (PR commit fc90e452474), whose diff shows ッチ,tti and ッツ,ttu as unchanged context.
  • Nothing pins the current spellings. No upstream test covers a small tsu before シ, チ or ツ (they cover サッカ, ヒャッカテン, コダッk and サッｋ), and no comment, CHANGES or MIGRATE entry mentions it.
The devil's-advocate check130 words

The strongest case (the cross-model review and the intended-behaviour checker): the table is a curated, best-effort set ("does not strictly comply"), every extra spelling multiplies the completion paths (the expansion behind a separate registry bug), and the document-suggester classes are @lucene.experimental.

Why it fails: the table gives two to four spellings to 123 of its 329 rows and to 56 of the 158 rows whose key starts with ッ (ッファ, ッフィ, ッフェ, ッフォ list four), so bounding the product cannot explain dropping exactly these rows; the review that added jji treated the same gap as an omission; and the defect is in the tokens of the kuromoji filter, which is not marked experimental and feeds any suggester. What remains is a labelling question (bug fix or improvement), not intent.

Trade-offs

  • Every extra spelling multiplies a word's romaji tokens: each ッシ, ッツ or ッヅ in a reading doubles the count, each ッチ, ッヂ, ッヂャ, ッヂュ or ッヂョ triples it, and ッチャ/ッチュ/ッチョ go from 3 to 4 spellings. マッチ goes from [matti] to [matti, macchi, matchi]. That slightly enlarges a separate unbounded-expansion issue (different fix site); the module's random and huge-string tests still pass.
  • The ッヂ/ッヅ part (5 rows) concerns rare kana and is not directly asserted by any test run. For it: the table's own closure check flags these rows, and the finder's standards check finds their Hepburn and Kunrei images missing. Against it: in the saved input-method table the new zzi/jji compose to っじ (not っぢ), zzu to っず (not っづ), and the yōon forms likewise to ジ forms, although the base rows already alias ヂ with ジ and ヅ with ズ. Keep it for consistency, not as a headline, or drop it (the 6-row option).
  • Existing suggest fields must be reindexed to gain the new tokens. The query side needs no code or configuration change (kana queries gain the new spellings too).

How it was found

#

Semi-formal. A self-consistency check of the table (every ッK row should list K's spellings with the first consonant doubled) and a Hepburn standards check flagged these rows; a bounded-exhaustive check showed KatakanaRomanizer implements the table as written (0 mismatches on 59 million inputs). A public-API JUnit then reproduced the missing suggestions.

The method in full219 words
  • First signal. A planning probe checked romaji_map.txt against its own small-tsu rule and flagged ッシ, ッチ, ッツ and the ッヂ/ッヅ rows; its end-to-end probe showed zasshi, kesshite, macchi and mittsu returning no suggestion on the stock main jars.
  • Table laws. A model of the table's rules: the gemination-closure law found 10 violations, 8 of them this bug's rows (the other 2 belong to a sibling copy-error bug).
  • Translation validation (bounded-exhaustive). Part A: romanize() equals an independent longest-match model of the table on all 1,830,854 inputs of length up to 3 and 57,289,761 inputs of length 4 (0 mismatches; a shortest-match mutant: 33,518 mismatches); the Part A counters completed, then that process ran out of memory entering Part B, so Parts B and C ran separately. Part B: the modified-Hepburn, Kunrei and Nihon-shiki images of every sequence of up to 4 kana units, from an independent standards table, isolate the failing small-tsu units. Part C: typing the words through a model input method (the open-source Mozc romaji table) finds the failing composition states っsh, っts and tc.
  • Reduction. A public-API JUnit with the document suggester on the stock main jars (2026-10-28), then this doc's kuromoji-only test.
  • Tier. Semi-formal: the first signal came from a table self-consistency script, not from a solver's or model checker's own output.

LFV-849, snapshot of 2026-10-30

Registry title
Japanese completion suggester (JapaneseCompletionAnalyzer / JapaneseCompletionFilter): words with a small tsu before shi, chi or tsu (雑誌, 決して, マッチ, 三つ) are never suggested for their Hepburn or input-method spellings zasshi, kesshite, macchi/matchi, mittsu, because romaji_map.txt maps ッシ only to 'ssi', ッチ only to 'tti' and ッツ only to 'ttu', while the base rows シ/チ/ツ list shi/chi/tsu and the neighbouring rows ッシャ and ッチャ do double the consonant ('ssha', 'ccha')
Area
analysis / kuromoji completion romanization (romaji_map.txt read by KatakanaRomanizer; JapaneseCompletionFilter, JapaneseCompletionAnalyzer)
Priority
Medium, rank 126: Common words such as 雑誌, 決して, マッチ and 三つ silently get no suggestion in the opt-in kuromoji completion analyzer for their usual Hepburn spellings, and that broad trigger on everyday words puts it in Medium at the end of the opt-in silent analysis rows, while its sibling completion-table rows LFV-850, LFV-848 and LFV-854 stay Low.
Impact class
silent wrong results
Impact note
Applications that build Japanese autocomplete with JapaneseCompletionAnalyzer or JapaneseCompletionFilter (an opt-in kuromoji analyzer, used with its default settings; downstream search servers expose it as a kuromoji_completion filter), in every release from 9.0.0 to 10.5.2 and main: every word whose reading contains ッシ, ッチ or ッツ (雑誌, 決して, 必死, こっち, 一致, 三つ, 四つ) is indexed only with the Kunrei-style romaji (zassi, kessite, matti, mittu), so a query typed in raw romaji with the Hepburn or doubled-consonant spelling (zasshi, kesshite, macchi, matchi, mittsu, and matcha for 抹茶) gets no suggestion; kana committed through an input method still match, and input-method users lose the suggestion only while composing (ざっｓｈ, みっｔｓ); no scale is needed and there is no error; a fix changes the index-side romaji tokens, so existing suggest fields would need reindexing to benefit.
Summary
You index 雑誌 ('magazine'), マッチ ('match') and 三つ ('three') in a document suggester with JapaneseCompletionAnalyzer, whose javadoc lists modified Hepburn among the supported romanizations, and expect typing 'zasshi', 'macchi' or 'mittsu' to suggest them, just as 'issho' suggests 一緒 and 'maccha' suggests 抹茶. Instead nothing is suggested: the bundled romaji_map.txt gives the small-tsu rows ッシ, ッチ and ッツ only the spellings 'ssi', 'tti' and 'ttu', although the base rows シ, チ, ツ list shi, chi, tsu and the neighbouring rows ッシャ and ッチャ list 'ssha' and 'ccha'. Only the Kunrei spellings (zassi, matti, mittu) find these words.
