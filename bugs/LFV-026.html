Flexible StandardQueryParser throws ClassCastException on a range over the field *, such as *>a or *:[a TO *]

The flexible StandardQueryParser throws an unchecked ClassCastException for a range on the field * with an open * bound, such as *>a or *:[a TO *], instead of a query or the QueryNodeException that parse() declares. Every release since 2.9.0 does this.

The finding in 30 seconds

#

An open range bound is written *. On the field * that bound looks exactly like the match-all query *:*, and one processor rewrites it as if it were.

Background: open ranges and the flexible parser

#
  1. A range f:[a TO z] matches the terms of the field f between a and z. Writing * for a side leaves it open: f:[a TO *] means "from a up". The flexible parser also accepts the shorthand f>a, f>=a, f<z and f<=z.
  2. The flexible StandardQueryParser turns the text into a tree of nodes and then runs about twenty processors over it, one after another, before building the Query. One of them turns the query *:* into match-all. parse() declares one checked exception for bad query text: QueryNodeException.

The finding, step by step

#
  1. Parse f>a with new StandardQueryParser(): you get the open range f:{a TO *]. Inside the parser, the open side is a bound whose text is *.
  2. Parse *>a, the same range on a field named *. The parser treats * as an ordinary field elsewhere: in a 2-document index, *:b and *:[a TO c] each find the 1 document that has it. You expect *:{a TO *], or a QueryNodeException.
  3. You get ClassCastException: MatchAllDocsQueryNode cannot be cast to FieldValuePairQueryNode. The open bound reads *:*, so the processor that turns the query *:* into match-all replaces the bound inside the range.
  4. The next processor reads the bound back as a field node, and that cast throws. parse() does not convert it, so code that catches QueryNodeException to report a bad query fails on this input instead.
  5. *:[a TO *], *:[* TO *], *<z and x OR *>a fail the same way, with assertions on and off. All 150 releases fail: the bracket forms since 2.9.0, *>a since 4.0.0-ALPHA added the > syntax. The classic QueryParser returns a range on the field * for the bracket forms (1 hit).

Who is affected

#

Applications that pass user-typed query text to the flexible StandardQueryParser (not the classic QueryParser), default settings, no analyzer needed. Only a range on the field * with a * bound triggers it, or an open range such as [a TO *] when the default field is *. Only the exception type is wrong; no result changes. Rare input.

Mechanism, terms and numbers682 words

The flexible StandardQueryParser declares QueryNodeException as the failure of parse(). Its grammar writes the open side of a range as a bound with the text * (f>a is f:{a TO *]). On the field * that bound is *:*, and MatchAllDocsQueryNodeProcessor, which turns the query *:* into match-all, rewrites every field node *:* without checking whether it is a range bound. OpenRangeQueryNodeProcessor runs next and reads the bound through an unchecked generic cast, so parse("*>a", "f") throws java.lang.ClassCastException: MatchAllDocsQueryNode cannot be cast to FieldValuePairQueryNode.

Every range on the field * with a * bound fails: the </> shorthand, the bracket forms such as *:[a TO *] and *:[* TO *], ranges inside Boolean queries, escaped forms, and [a TO *] with the default field *. Ranges on * without a * bound, ranges on other fields and the query *:* work, and the classic QueryParser returns a TermRangeQuery on the field * for the bracket forms. The bracket forms have failed since 2.9.0 (2009), *>a since cffd01664bc9 (2011), first released in 4.0.0-ALPHA (2012). The failure happens while parsing, so nothing is searched and no result is wrong: a query string is refused with an undeclared exception type. A one-line guard, the one two sibling processors already use, fixes it and is validated with the whole queryparser test suite and check.

The bug, step by step

#
  1. Grammar. A field name is any term, so * is legal (StandardSyntaxParser.jj:339-344). For > and >= the grammar builds the open upper bound as new FieldQueryNode(field, "*", ...) (.jj:767, :773); for < and <= the lower bound (.jj:754, :760). The bracket form builds one FieldQueryNode per bound (.jj:870-873), so [a TO *] has a bound with the text * too. On the field *, that bound has field * and text *.
  2. Order. MatchAllDocsQueryNodeProcessor runs right before OpenRangeQueryNodeProcessor (StandardQueryNodeProcessorPipeline.java:52-53).
  3. The rewrite. if (node instanceof FieldQueryNode fqn) { if (fqn.getField().toString().equals("*") && fqn.getText().toString().equals("*")) { return new MatchAllDocsQueryNode(); } } (MatchAllDocsQueryNodeProcessor.java:44-47). It does not look at the parent, so the bound becomes a match-all node, and QueryNodeProcessorImpl writes it back into the range node (QueryNodeProcessorImpl.java:111-123). The class javadoc is narrower: it "converts every WildcardQueryNode that is "*:*"" (:28-30).
  4. The cast. OpenRangeQueryNodeProcessor reads FieldQueryNode lowerNode = rangeNode.getLowerBound(); FieldQueryNode upperNode = rangeNode.getUpperBound(); (OpenRangeQueryNodeProcessor.java:39-40). The getter is return (T) getChildren().get(1); with T extends FieldValuePairQueryNode<?> (AbstractRangeQueryNode.java:33, :96-99); its erased checkcast to FieldValuePairQueryNode throws, because a MatchAllDocsQueryNode is not one.
  5. Not converted. QueryParserHelper.parse runs the parser, the processors and the builder with no catch (QueryParserHelper.java:213-223). The grammar's own parse rethrows a ParseException (already a QueryNodeParseException) and wraps an Error into one (.jj:99-113), but this exception comes later, from the processor phase.

Exposure and likelihood168 words
  • Who is hit. Applications that pass query text to the flexible StandardQueryParser: default pipeline, no index and no configuration needed. Run with no analyzer and with StandardAnalyzer; the analyzer processor runs only after the one that throws.
  • What goes wrong. Code that catches QueryNodeException to answer "invalid query" gets an unexpected ClassCastException instead. What happens next depends on the application; one that catches nothing else answers that request with a generic server error.
  • When. A user who writes * to mean "any field" (the parser maps *:* to match-all) and adds a range, such as *:[a TO *] or *>5, hits it. So does any open range typed without a field, such as [a TO *], in an application whose default field is *.
  • Limits. Deterministic and immediate. The failure happens while parsing, before any search or index access: no wrong results, no hang, no resource growth. The likelihood is rated rare, and the recorded searches found no matching public report, 17 years after 2.9.0.

Why it looks unintended

#
  • parse() declares only QueryNodeException; * is an ordinary field elsewhere (*:b and *:[a TO c] work), and the classic parser builds *:[a TO *].
  • Three sibling processors skip range bounds on purpose; this one's own javadoc limits it to wildcard nodes.
  • Precedent: #5175, a ClassCastException from another processor touching a node it should skip, was fixed in 2012.
The full argument303 words
  • The declared failure is QueryNodeException: StandardQueryParser#parse (:274) and QueryParserHelper#parse (:211), "if something wrong happens along the three phases". No javadoc or MIGRATE entry mentions ClassCastException for the parser, none of the five ClassCastException entries in CHANGES is about a query parser, and nothing reserves * as a field name for ranges.
  • * is an ordinary field elsewhere. *:b gives TermQuery *:b and *:[a TO c] a TermRangeQuery, 1 hit each. The class javadoc says the syntax is borrowed from the classic parser (StandardQueryParser.java:63-65), which builds working range queries for *:[a TO *], *:[* TO z] and *:[* TO *], and whose testStarParsing asserts that *:foo is a TermQuery on the field * (TestQueryParser.java:275-278).
  • The processor does more than its javadoc says: "converts every WildcardQueryNode that is "*:*"" (MatchAllDocsQueryNodeProcessor.java:28-30), while the code matches any FieldQueryNode (:44). Range bounds are never wildcard nodes: WildcardQueryNodeProcessor skips them (:96-103).
  • Sibling guards. WildcardQueryNodeProcessor: "do not process wildcards for TermRangeQueryNode children ... to reproduce the old parser behavior" (:96-98). AnalyzerQueryNodeProcessor: !(node.getParent() instanceof RangeQueryNode) (:110). PointQueryNodeProcessor: "FieldQueryNodes children of a RangeQueryNode are ignored" (:46, guard :63).
  • The node's own type. TermRangeQueryNode extends AbstractRangeQueryNode<FieldQueryNode>, "a range query composed by FieldQueryNode bounds" (TermRangeQueryNode.java:21-28).
  • History. The 2009 framework commit 343992fcbb4 matched only WildcardQueryNode; 16 days later 565a6d22b5f (LUCENE-1792, about rewrite methods for multi-term queries) widened the test to FieldQueryNode without updating the javadoc, and its 25-comment discussion (#2867) never mentions match-all. Its parent commit passes the probe; the commit fails; the commit with only that hunk reverted passes.
  • Precedent. #5175 (LUCENE-4103), "AnalyzerQueryNodeProcessor throws a class cast exception with the RegexpQueryNode", was fixed in 2012 with a one-line node-type guard (5fb2e4a751e).
The devil's-advocate check130 words

The strongest case for "intended" (the cross-model reviewer's, which it rated weak itself): * in the field position may be a match-all sentinel, so a range over "all fields" is meaningless input, and @throws QueryNodeException does not promise that no unchecked exception escapes.

Why it fails: the parser treats * as a field name everywhere else (*:b, *:[a TO c]), and so do the classic parser and its tests; the documented match-all special case is the whole query *:* (CHANGES, LUCENE-723; TestQPHelper.testMatchAllDocs), which the fix keeps; even for invalid input the answer would be a QueryNodeException, not a ClassCastException from an erased generic cast; and the sibling guards and the 2012 precedent show upstream treats this kind of defect as a bug. Verdict: not intended, a defect.

Suggested fix

#

Recommended MatchAllDocsQueryNodeProcessor leaves range bounds alone (one line plus an import)

Let MatchAllDocsQueryNodeProcessor skip a field node whose parent is a range, the guard its sibling processors already use. *>a then gives *:{a TO *], and *:* stays match-all. Validated: the repro passes, the whole queryparser suite gives 534 tests, 0 failures (1 skipped by @Ignore), and check passes.

All options and trade-offs4 options · 545 words

The recommended fix is the study verifier's; it touches one file and needs no grammar regeneration. The open choice for maintainers is what a range on the field * should give: a range on a field literally named * (the recommended fix, as in the classic parser) or a QueryNodeException (the third option). The repro test accepts either.

Trade-offs

Downstream note

#

Not a Lucene security issue; downstream, a service that catches only QueryNodeException to answer "invalid query" returns a generic server error for such input instead.

How it was found

#

An AI tool wrote and ran a Jazzer fuzzer over Lucene's query parsers that checks each parser throws only its documented exception; it flagged this ClassCastException without a hint. An independent verifier then reproduced it and traced it to the match-all processor by removing that processor from the pipeline and by swapping in one that skips range bounds.

The method in full163 words

Method: non-formal baseline of the study (fuzzing).

  • The fuzzer, QueryParserFuzzer, fed generated strings to the classic, flexible and simple query parsers. Its oracle: each parser may only throw its documented exception, and a parsed query must survive toString, equals, count and rewrite. It ran for 1.5 + 7 + 20 minutes, about 470,000 executions, and produced five query-parser findings; this is one of them.
  • An independent AI verifier (same model family) wrote its own 6-test JUnit class and a version probe: 14 trigger strings failed on main 7cecf79523, and 6 of them on 8.11.4, 9.12.3 and 10.1.0, while the controls parsed; removing MatchAllDocsQueryNodeProcessor from the pipeline removed every exception, and a range-aware replacement made all 14 parse while keeping *:* as match-all.
  • Later checks cut the repro to one test (2026-10-29 noise audit), re-ran it on 645d4fe14a20 and on releases, dated the bug to 2009 by building commits and running all 150 releases, and validated the fix with gradle.

History

#

Introduced in 2.9.0 by 565a6d22b5f (LUCENE-1792, 2009), which widened the match-all test from wildcard nodes to all field nodes. The > shorthand of cffd01664bc9 (2011, first released in 4.0.0-ALPHA, 2012) made *>a a trigger. All 150 releases from 2.9.0 to 10.6.0 were run, and all fail; main fails.

Versions tested8 rows

Introduced by 565a6d22b5f "LUCENE-1792: Fix new query parser to set rewrite method for multi-term queries." (2009-08-19, svn r805633; issue #2867, a JIRA-era patch with no PR). It moved wildcard detection out of the grammar and changed MatchAllDocsQueryNodeProcessor's test from instanceof WildcardQueryNode to instanceof FieldQueryNode. Range bounds were ParametricQueryNode then, a FieldQueryNode subclass, so from 2.9.0 to 3.6.2 the bracket forms fail at ParametricRangeQueryNode.getUpperBound / getLowerBound and *>a gives the declared QueryNodeException (no > syntax yet).

cffd01664bc9 (2011-08-01, LUCENE-3343 and LUCENE-3338) added the <, >, <=, >= shorthand and OpenRangeQueryNodeProcessor right after the match-all processor; from 4.0.0-ALPHA all four probe triggers fail at AbstractRangeQueryNode. The parent of 565a6d22b5f passes, the commit fails, and the commit with only the widened test reverted passes. Not a regression: no release ever shipped without it. The lines on the bug path have changed since only for cleanups; other commits to these files (#14697's toQueryString fix, the 2021-22 interval-function additions) do not touch them. Upstream main 2f424fd428da and branch_11x have the same code; branch_10_6 has the same bug path (its AbstractRangeQueryNode lacks #14697).

LFV-026, snapshot of 2026-11-06

Registry title
Flexible StandardQueryParser throws ClassCastException on the input *>a
Area
queryparser / flexible
Priority
Low, rank 1051: The flexible parser throws ClassCastException instead of a parse error on ranges over the literal field * such as *>a, a wrong error type for unusual input.
Impact class
wrong error
Impact note
Applications that parse untrusted query strings with the flexible StandardQueryParser; one unusual input; in every release since 2.9.0 (all 150 releases executed).
Summary
You parse the query string *>a with the flexible StandardQueryParser. You expect a query or a QueryNodeException for bad syntax. Instead parse() throws an unchecked ClassCastException.
Introduced
565a6d22b5f0f6be56bc1542796ac7c831f838e4 (LUCENE-1792 'Fix new query parser to set rewrite method for multi-term queries', svn r805633, issue #2867; a JIRA-era patch, no PR): it widened MatchAllDocsQueryNodeProcessor's test from instanceof WildcardQueryNode to instanceof FieldQueryNode, so a range bound * on the field * is rewritten to a match-all node [exec: its parent 7700fa36264 passes the probe, the commit fails 3 of 4, and the commit with only that hunk reverted passes]; cffd01664bc9 (2011-08-01, LUCENE-3343 and LUCENE-3338, first released in 4.0.0-ALPHA) added the < and > shorthand, which made *>a a trigger (2009-08-19)
First affected version
2.9.0 [exec, -ea and -da: the bracket forms such as *:[a TO *] throw ClassCastException; *>a fails from 4.0.0-ALPHA, which added the > syntax], the first release with the flexible parser; 2.4.1 has no flexible parser [exec: the probe does not compile]
Affected versions
every release from 2.9.0 to 10.6.0 and main 645d4fe14a20, never fixed [exec: a main() probe on all 150 lucene-queryparser releases on Maven Central (SHA-1-checked jars) fails on each; the minimal JUnit fails on 9.1.0, 10.6.0 and main with -ea and -da]; upstream main 2f424fd428da has the same code [read]
Status
documented (brief, checks and a per-finding doc exist)
Verification
Confirmed in the earlier formal verification study by independent AI checks and a rerun on Lucene main; also a cross-model review that could only read the code (its low-confidence “not real” is procedural); not yet triaged by a person.
Found by
non-formal baseline: fuzzing/PBT
Upstream and prior reports
none found (study searches 2026-10-22; a prior-report search on 2026-11-01, read-only: 158 queries over GitHub issues and PRs, the JIRA archive, the mailing lists, downstream projects and the web, plus the changed files of all 410 open PRs; closest, not this bug: #5175/LUCENE-4103, fixed 2012, a ClassCastException from another processor of the same pipeline, and adsabs/montysolr#159, the same failing cast from that project's own grammar)
Lucene commit tested
main 645d4fe14a20 (gradle and standalone, assertions on and off); the minimal test on the 10.6.0, 10.5.2 and 9.1.0 release jars; a main() probe on all 150 lucene-queryparser releases from 2.9.0 to 10.6.0; commit builds of the introducing commit 565a6d22b5f, its parent, cffd01664bc9 and its parent; the study's runs on main 7cecf79523, b83101cdd2 and a9779ef3c193 and on 8.11.4, 9.12.3 and 10.1.0; the recommended fix in a scratch worktree of 645d4fe14a20.
