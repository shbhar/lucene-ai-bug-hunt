FieldInfos.getMergedFieldInfos accepts or rejects the same two indexes depending on their order in a MultiReader

Put two separately built indexes in one MultiReader: in one, field x is the soft-deletes field; in the other, a plain numeric doc-values field. FieldInfos.getMergedFieldInfos accepts the pair in one order and throws IllegalArgumentException in the other, because a name's soft-deletes role is checked only for its first FieldInfo.

The finding in 30 seconds

#

The merged view checks a field name's soft-deletes role only the first time it sees the name. The second index's x skips the check, so the order of the two indexes decides between accept and throw.

Background in two steps

#
  1. Soft deletes are opt-in: IndexWriterConfig.setSoftDeletesField("x") makes the doc-values field x mark deleted documents. Lucene keeps one role per field name in an index, so x cannot be the soft-deletes field and a regular field at the same time.
  2. MultiReader combines several indexes into one reader. FieldInfos.getMergedFieldInfos(reader) returns one merged FieldInfos for all its leaves; UnifiedHighlighter, MatchRegionRetriever and Luke call it, and IndexWriter's merge code does internally.

The finding, step by step

#
  1. Build index soft with new IndexWriterConfig().setSoftDeletesField("x") and two documents, and index plain with a default config and one document holding a plain NumericDocValuesField("x", 1). Each index is valid on its own.
  2. Call FieldInfos.getMergedFieldInfos on new MultiReader(soft, plain) and on new MultiReader(plain, soft). Same two indexes, so you expect the same answer: both accepted, or both rejected as IndexWriter.addIndexes does.
  3. (soft, plain) is accepted and reports x as the soft-deletes field, now standing for plain's ordinary x too. (plain, soft) throws IllegalArgumentException: cannot configure [x] as soft-deletes; this index uses [x] as non-soft-deletes already. Assertions on or off.
  4. Why: the merged view feeds every leaf into one FieldInfos.Builder. The role check runs only when a name is new to the builder; for a name it already holds, Builder.add runs only verifySameSchema, which ignores the soft-deletes flag. Whichever x comes first decides.

Who is affected

#

Code that calls getMergedFieldInfos (directly, or through UnifiedHighlighter, MatchRegionRetriever or Luke) on a MultiReader over separately built indexes, where one index's soft-deletes field is a regular numeric doc-values field in another. Soft deletes are opt-in; no scale is needed. One order fails loudly, the other sets a flag no in-tree code reads; no search result changes.

Mechanism, terms and numbers463 words

Index A is written with IndexWriterConfig.setSoftDeletesField("x"); index B, built separately, has an ordinary NumericDocValuesField("x"). Both are valid on their own. FieldInfos.getMergedFieldInfos(new MultiReader(A, B)) succeeds and reports x as the soft-deletes field, while getMergedFieldInfos(new MultiReader(B, A)) throws IllegalArgumentException: cannot configure [x] as soft-deletes; this index uses [x] as non-soft-deletes already.

The merged view builds one FieldInfos.Builder over all leaves. Builder.add checks the soft-deletes role only when a field name is new to the builder; for a name it already holds it runs only FieldInfo.verifySameSchema, which does not compare the soft-deletes flag. So the role check sees only the first FieldInfo of each name, and the leaf order decides the outcome. Neighbouring conflicts in the same method (two different soft-deletes fields, a parent-field disagreement) are rejected in both orders, and IndexWriter.addIndexes rejects this pair in both orders. No search result is wrong: one order throws an accurate exception, the other sets a merged flag that no in-tree code reads in such a view.

The mechanism (main 5adff78bb168)

#
  1. index/FieldInfos.java:196-218 getMergedFieldInfos: with 2+ leaves it takes the soft-deletes name from any leaf that has one (:203-208, findAny()), validates the parent field across all leaves up front (getAndValidateParentField, :209, :220-238), creates one new Builder(new FieldNumbers(softDeletesField, parentField)) (:210) and adds every leaf's FieldInfo in leaf order (:211-215).
  2. index/FieldInfos.java:771-782 Builder.add(fi, dvGen): if the name is already in the builder it calls only curFi.verifySameSchema(fi), merges attributes and payloads, and returns curFi. Only a new name reaches globalFieldNumbers.addOrGet(fi) (:788).
  3. index/FieldInfos.java:415-418 FieldNumbers.addOrGet runs verifySoftDeletedFieldName (:459-482): a field named like the configured soft-deletes field but not flagged as soft-deletes throws "cannot configure [x] as soft-deletes; this index uses [x] as non-soft-deletes already" (:474-480).
  4. index/FieldInfo.java:244-269 verifySameSchema compares index options, norms, term vectors, doc-values type and skip index, points and vectors; not isSoftDeletesField() or isParentField(). Both x fields are NUMERIC doc values with IndexOptions.NONE, so it passes.
  5. (soft, plain): soft's x is new and passes the role check; plain's x is an existing name, passes verifySameSchema, and is folded into the soft-deletes FieldInfo. (plain, soft): plain's x is new, so the role check runs on a non-soft-deletes x and throws.

In the accepting order the merged view reports getSoftDeletesField() = "x" and fieldInfo("x").isSoftDeletesField() = true. The same order dependence shows through UnifiedHighlighter, whose default offset-source lookup calls getMergedFieldInfos: over (soft, plain) it highlights both hits, over (plain, soft) it throws the same exception (two probes, executed; one builds both indexes like the test, which itself asserts only that the two orders agree). The public MultiReader(IndexReader[], Comparator, boolean) sorter alone flips the outcome for the same reader array (executed).

Exposure and likelihood271 words
  • Who is hit: code that calls getMergedFieldInfos (directly, or through UnifiedHighlighter, MatchRegionRetriever or Luke) on a MultiReader over separately built indexes, where one index uses a name as its soft-deletes field and another has a regular numeric doc-values field of that name.
  • Default vs opt-in: soft deletes are opt-in (setSoftDeletesField), and combining independently built indexes in one MultiReader is a deliberate choice. No scale: two tiny indexes. The soft-deletes one needs two documents (a document with a value in x counts as soft-deleted, so with only that document no segment is left); the other needs one (executed).
  • Effect: in one order a loud, accurate IllegalArgumentException (for example, highlighting fails on that reader); in the other an accepted merged view whose x is flagged soft-deletes for both indexes. Outside the test framework, Lucene's public routes to the merged view (UnifiedHighlighter, MatchRegionRetriever, Luke) use it only for per-field type and offset-source choices and never read the merged soft-deletes flag. IndexWriter also builds a merged view internally: SlowCompositeCodecReaderWrapper (index/SlowCompositeCodecReaderWrapper.java:95-96), for merges and in addIndexes(CodecReader...) when no index sort is set (index/IndexWriter.java:3561, :5556), which it hands to the experimental MergePolicy.OneMerge.reorder hook (index/MergePolicy.java:312-327). Its inputs are one index's segments or readers already validated (index/IndexWriter.java:3288-3293), so this pair never reaches it.
  • IndexWriter is not affected: addIndexes(Directory...) and addIndexes(CodecReader...) reject the pair in both orders (executed); addIndexes(CodecReader...) verifies every incoming FieldInfo first (index/IndexWriter.java:3288-3293).
  • Severity: Low. The answer of a public method depends on leaf order, but no search hit or index changes, and no in-tree code reads the flag that differs.

Why it looks unintended

#
  • The javadoc promises "the (merged) FieldInfos for a composite reader" and states no order-dependent exception.
  • In the same method, two different soft-deletes fields, or a parent-field disagreement, are rejected in both orders; so is this pair by addIndexes.
  • Since LUCENE-8335 the merged view enforces the soft-deletes role (two different soft-deletes names are rejected), but only for a name's first FieldInfo.
The full argument157 words
  • Contract. "Call this to get the (merged) FieldInfos for a composite reader" (index/FieldInfos.java:189-195). The NOTE says only that field numbers may not match the leaves ("will likely not correspond") and codec attributes are unavailable. MultiReader "reads multiple indexes" (index/MultiReader.java:23) and states no shared-schema precondition.
  • Siblings. Two different soft-deletes fields (x in one index, y in the other) are rejected in both orders, and a parent-field disagreement is rejected up front in both orders (both executed). IndexWriter.addIndexes rejects this very pair in both orders.
  • History. Since LUCENE-8335 (2018) the merged view's FieldNumbers carries the soft-deletes name, so the merged view does enforce the role (two different soft-deletes names are rejected), but only for a name's first FieldInfo. LUCENE-9334 (d03662c48bf, 9.0.0) later rewrote that existing-name branch as verifySameSchema, which still ignores the flag. The review found no javadoc, CHANGES or MIGRATE entry, test or thread that documents an order-dependent outcome.
The devil's-advocate check130 words

The strongest case for "intended": getMergedFieldInfos is meant for the segments of one index, FieldInfos is @lucene.experimental (index/FieldInfos.java:42), and some merged values depend on leaf order by design: the first FieldInfo of a name keeps its field number, and a codec attribute two leaves set takes the later leaf's value (index/FieldInfos.java:775-777, index/FieldInfo.java:688-694; TestFieldInfos.java:133-135 notes it; executed).

Why it fails: accept versus throw is not a merged value that one leaf wins; the method's other cross-leaf role conflicts are symmetric; MultiReader documents combining multiple indexes; and the same reader array flips outcome under a public sorter. A cross-model reviewer (OpenAI GPT-5.6) rated this argument moderate and rejected it; the intended-behaviour review and the adjudication agreed. Still, the evidence shows an undocumented asymmetry, not a promised invariant.

Suggested fix

#

Recommended A: run the soft-deletes role check for a name the builder already holds (recommended)

Recommended (validated): in Builder.add, when a name already in the builder arrives with a different soft-deletes flag, run the same role check (verifyFieldInfo), so both orders reject with one message, like addIndexes. The repro, the nearest core and highlighter suites and the core lint checks pass. Alternative: stop enforcing the role in the merged view.

// index/FieldInfos.java, Builder.add(FieldInfo, long), existing-name branch
       if (curFi != null) {
         curFi.verifySameSchema(fi);
+        if (curFi.isSoftDeletesField() != fi.isSoftDeletesField()) {
+          // run the soft-deletes role check for every FieldInfo of a name, not only the first
+          globalFieldNumbers.verifyFieldInfo(fi);
+        }
All options and trade-offs3 options · 511 words

The test asserts only that both orders agree, so either direction satisfies it; which one is the maintainers' call. A related issue (highlighters throw on a MultiReader whose indexes differ in a field's schema) may be fixed by making getMergedFieldInfos lenient across independent indexes, which would cover this bug too.

A: run the soft-deletes role check for a name the builder already holds (recommended) (validated by the checks)

#

In Builder.add's existing-name branch (index/FieldInfos.java:771-782), call globalFieldNumbers.verifyFieldInfo(fi) when curFi.isSoftDeletesField() != fi.isSoftDeletesField(). Both orders then throw "cannot configure [x] as soft-deletes; this index uses [x] as non-soft-deletes already" (verifyFieldInfo, :401-408, runs the same verifySoftDeletedFieldName). Inside one index every FieldInfo of a name has already passed this role check against the writer's configured soft-deletes field, so the flags agree there and the new branch fires only for the merged view's cross-index case.

// index/FieldInfos.java, Builder.add(FieldInfo, long), existing-name branch
       if (curFi != null) {
         curFi.verifySameSchema(fi);
+        if (curFi.isSoftDeletesField() != fi.isSoftDeletesField()) {

Trade-offs

A policy choice rather than only a validation repair: strict, like IndexWriter.addIndexes, but MultiReader(soft, plain), which works today (including UnifiedHighlighter's default offset-source lookup), throws too. The original sketch also compared isParentField(); that half cannot be reached through getMergedFieldInfos, because getAndValidateParentField already rejects a parent-field disagreement up front, so it is dropped here (keep it only as a defensive check).

Downstream note

#

Downstream products that open one MultiReader over separately built indexes (for example to highlight across them) meet this only when one index's soft-deletes field name is a regular numeric doc-values field in another; which order throws then depends on how they order the readers.

How it was found

#

Semi-formal: a proof-obligation audit of getMergedFieldInfos's contract, which treats the merged FieldInfos of a composite reader as a function of its leaves, independent of their order. The soft-deletes role check failed that obligation; a one-test JUnit repro on stock main witnessed it.

The method in full81 words
  • Obligation: for the same set of leaves, getMergedFieldInfos gives the same outcome (accept or reject) whatever their order.
  • Finding: Builder.add skips the soft-deletes role check for a name it already holds (index/FieldInfos.java:771-782), and verifySameSchema does not compare the flag (index/FieldInfo.java:244-269), so the check sees only the first FieldInfo of each name.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review, an adjudication and a separate re-run (see Independent checks).

Registry title

Priority
Low, rank 1230: FieldInfos.getMergedFieldInfos accepts or rejects the same pair of indexes depending on leaf order when one uses a name as its soft-deletes field and the other as a regular numeric doc-values field, in every release since 7.4.0. It needs opt-in soft deletes and a MultiReader over separately built indexes, the rejection is loud and accurate, and nothing reads the merged soft-deletes flag.
Impact class
minor
Impact note
Hits only code that calls FieldInfos.getMergedFieldInfos on a MultiReader over separately built indexes in which one index uses a name as its configured soft-deletes field (opt-in) and another index has a regular NumericDocValuesField of that name: MultiReader(A, B) is then accepted and reports the field as the soft-deletes field, MultiReader(B, A) throws an accurate IllegalArgumentException, with -ea and -da and no scale; no search result is wrong, no index is touched, nothing in Lucene reads the merged soft-deletes flag, and IndexWriter.addIndexes rejects the pair in both orders; the highlighters' failure on a MultiReader whose indexes differ in a field's schema is the separate finding LFV-602; in every release from 7.4.0 to 10.6.0 and on main.
Summary
You build index A with IndexWriterConfig.setSoftDeletesField("x") (one document, soft-updated once) and index B with one document holding a plain NumericDocValuesField "x", and call FieldInfos.getMergedFieldInfos on new MultiReader(A, B) and on new MultiReader(B, A). You expect the same outcome for both orders: both accepted, or both rejected as IndexWriter.addIndexes does. Instead (A, B) is accepted and reports x as the soft-deletes field, B's regular field included, while (B, A) throws IllegalArgumentException 'cannot configure [x] as soft-deletes; this index uses [x] as non-soft-deletes already', because FieldInfos.Builder.add checks a name that is already in the builder only with verifySameSchema, which ignores the soft-deletes flag, so the soft-deletes role check runs only for the first FieldInfo of each name.
