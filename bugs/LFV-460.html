IndexWriter#hasDeletions() returns false after a writer restart when the only deletions are committed soft deletes

With a soft-deletes field, a writer reopened on an index whose only deletions are committed soft deletes answers hasDeletions() == false while its own getDocStats() reports maxDoc 2, numDocs 1, because its check of committed segments sees only hard deletes. In every release since 7.4.0; the fix is one line.

The finding in 30 seconds

#

A soft delete marks a document in a doc-values field instead of a live-docs file. For committed segments, IndexWriter#hasDeletions() looks only for a live-docs file, so a writer that has just opened the index, and has loaded none of its segments yet, says "no deletions" while its own getDocStats() counts them.

Background: soft deletes and the reader pool

#
  1. A hard delete (deleteDocuments) marks the document in the segment's live-docs file. A soft delete gives the document a value in a doc-values field you name with IndexWriterConfig#setSoftDeletesField; softUpdateDocument adds the new version and soft-deletes the old one in one call.
  2. The writer treats soft-deleted documents as deleted: its NRT readers hide them and merges reclaim them. Since 7.4.0 each commit stores a per-segment soft-delete count next to the hard-delete count; a soft delete writes no live-docs file.
  3. The writer's reader pool holds the segments it has loaded, for example to open an NRT reader or to apply deletes. A freshly opened writer has loaded none.

The finding, step by step

#
  1. Configure a soft-deletes field (setSoftDeletesField("soft"), NoMergePolicy), add document id=1, then softUpdateDocument it: 2 documents on disk, 1 of them soft-deleted. Close the writer; it commits.
  2. Open a new IndexWriter on the index, as after any restart. Its getDocStats() says maxDoc 2, numDocs 1: it counts the deleted document.
  3. You expect hasDeletions() to be true: its javadoc says "Returns true if this index has deletions", and the writer treats a soft-deleted document "as if it has been hard-deleted".
  4. Instead it returns false. Its checks of buffered changes and of the segments in the writer's reader pool count soft deletes, but a reopened writer has neither; its last check, over committed segments, only asks whether a live-docs file exists, and a soft delete never writes one.
  5. With NoMergePolicy on the reopened writer too, open DirectoryReader.open(writer) and ask again: now true, though the index files did not change. addIndexes(Directory) of such a segment into another writer gives the same false.

Who is affected

#

Applications that configure a soft-deletes field and call IndexWriter#hasDeletions() after a writer restart or addIndexes(Directory) while committed soft-deleted documents are still in the segments: deterministic. Without soft deletes the answer is right. Nothing in Lucene calls the method, so searches, merges, live docs and index files are unaffected, and getDocStats() and NRT readers count correctly.

Mechanism, terms and numbers616 words

IndexWriter#hasDeletions() returns true if buffered changes or segments in the writer's reader pool have deletions (these checks count soft deletes), and otherwise if any committed segment has SegmentCommitInfo#hasDeletions(), which is delGen != -1: the segment has a live-docs file, so only hard deletes count. A soft delete never writes a live-docs file; since 7.4.0 the commit records it as a per-segment soft-delete count instead. A writer opened on an existing index has nothing buffered and nothing pooled, so with a soft-deletes field configured and only soft deletes committed it answers false, while its own getDocStats() counts the deleted documents (maxDoc 2, numDocs 1 in the repro). The answer turns true, with no change to the index, once DirectoryReader.open(writer) loads the segment into the pool (reopened writer with NoMergePolicy; with the default merge policy that open merges the soft-deleted document away), and addIndexes(Directory) of such segments gives the same false. No Lucene code calls the method, so searches, merges, live docs and index files are unaffected: a minor, deterministic wrong answer in a public statistics method, in every release since 7.4.0 and on main. The one-line fix info.getDelCount(softDeletesEnabled) > 0, the count numDeletedDocs(info) already uses, passes the repro and the whole core test suite.

The code (main 645d4fe14a20)

#
// IndexWriter.java:1444-1460
/**
 * Returns true if this index has deletions (including buffered deletions). Note that this will
 * return true if there are buffered Term/Query deletions, even if it turns out those buffered
 * deletions don't match any documents.
 */
public synchronized boolean hasDeletions() {
  ensureOpen();
  if (bufferedUpdatesStream.any() || docWriter.anyDeletions() || readerPool.anyDeletions()) {
    return true;                          // :1451-1452  buffered and pooled: count soft deletes
  }
  for (final SegmentCommitInfo info : segmentInfos) {
    if (info.hasDeletions()) {            // :1455  delGen != -1: hard deletes only
      return true;
    }
  }
  return false;
}

Step by step, on the repro

#
  1. The commit. One segment _0: maxDoc 2, hard-delete count 0, soft-delete count 1, delGen -1 (no live-docs file). SegmentCommitInfo#getDelCount(boolean includeSoftDeletes) adds the two counts (SegmentCommitInfo.java:453-455).
  2. The pooled check counts soft deletes. ReaderPool#anyDeletions() (ReaderPool.java:156-163) is true if a pooled segment has rld.getDelCount() > 0, and PendingDeletes#getDelCount() is info.getDelCount() + info.getSoftDelCount() + numPendingDeletes() (PendingDeletes.java:242-246). A buffered (unflushed) soft-delete update makes the buffered check docWriter.anyDeletions() true.
  3. The committed-segment check does not. SegmentCommitInfo#hasDeletions() is return delGen != -1; under the javadoc "Returns true if there are any deletions for the segment at this commit." (SegmentCommitInfo.java:319-322).
  4. A reopened writer has an empty pool. The probe of the reopened writer prints bufferedUpdatesStream.any()=false docWriter.anyDeletions()=false readerPool.anyDeletions()=false; _0 info.hasDeletions()=false info.getDelCount(true)>0=true, so hasDeletions() returns false.
  5. The same writer counts the delete elsewhere. numDeletedDocs(info) uses info.getDelCount(softDeletesEnabled) for an unpooled segment (IndexWriter.java:891-903, :898), and getDocStats() sums it (:6824-6834): maxDoc 2, numDocs 1.
  6. Pooling flips the answer. After DirectoryReader.open(writer) (reopened writer with NoMergePolicy) the segment is pooled, readerPool.anyDeletions() is true and hasDeletions() returns true; the index files and the commit are unchanged. With the default merge policy, the probe saw the segment merged away while the reader opened (new segment _1, maxDoc 1, the soft-deleted document reclaimed), and then false is correct.
  7. addIndexes(Directory) copies the segment as it is, without pooling it: the receiving writer reports maxDoc 2, numDocs 1 and hasDeletions() false.

Exposure and likelihood241 words
  • Who is hit. Applications that configure a soft-deletes field (opt-in, IndexWriterConfig#setSoftDeletesField) and call IndexWriter#hasDeletions() on a writer opened on an existing index whose committed segments still hold soft-deleted documents (as after a restart), or after addIndexes(Directory...) of such segments. No timing and no scale are needed; assertions on or off.
  • Default config is not affected. Without soft deletes every deletion writes a live-docs file and the committed-segment check is right; the hard-delete control passes on every version run.
  • What goes wrong. A public statistics method gives a wrong answer, and the answer for an unchanged index changes when an NRT reader is opened (with NoMergePolicy on that writer). An application that asks it after a restart whether deletes need attention (reclaiming them, reporting them) is told there are none.
  • What does not go wrong. No Lucene main code calls IndexWriter#hasDeletions() (the other hasDeletions() calls are reader- or SegmentCommitInfo-level). Searches, live docs, merges and index files are unchanged; soft-deleted documents stay hidden from writer readers and from SoftDeletesDirectoryReaderWrapper. Upstream tests call the method only without soft deletes (TestTryDelete, TestTieredMergePolicy, and an assert in TestFunctionRangeQuery in lucene/queries).
  • Not affected either: the writer that made the soft delete keeps the segment pooled and answers true, even with setReaderPooling(false), after a merge that retains the soft-deleted document, and for a document added already soft-deleted.
  • Impact class: minor (a wrong return value with no in-tree effect); priority low.

Why it looks unintended

#
  • The javadoc promises "true if this index has deletions" and documents only false positives (buffered deletes that match nothing).
  • setSoftDeletesField: a soft-deleted document "is treated as if it has been hard-deleted through the IndexWriter API"; the method's pooled check and getDocStats() count it.
  • LUCENE-8341 made the neighbouring checks soft-aware in 2018 and left this loop; nothing found calls that intended.
The full argument236 words
  • Contract. IndexWriter.java:1445-1447: "Returns true if this index has deletions (including buffered deletions). Note that this will return true if there are buffered Term/Query deletions, even if it turns out those buffered deletions don't match any documents." The only approximation it documents is a false positive.
  • Soft deletes are deletes for the writer. IndexWriterConfig.java:544-547: "If a document is marked as soft-deleted, the document is treated as if it has been hard-deleted through the IndexWriter API ... index readers obtained from the IndexWriter will reflect all deleted documents in its live docs." CHANGES.txt:7388-7389 (LUCENE-8233): "Soft deletes are accounted for inside the index writer".
  • The method disagrees with itself. Its buffered and pooled checks count soft deletes, the committed-segment loop does not, so for one unchanged index the answer depends on whether a reader happened to be pooled. No javadoc says so.
  • The same writer disagrees. getDocStats() and numDeletedDocs(info) count the soft delete for the same unpooled segment.
  • History: an oversight. LUCENE-8233 (2018) made the writer account for soft deletes and did not touch the method. LUCENE-8341 (2018) changed its pooled check (readerPool.anyPendingDeletes() to readerPool.anyDeletions()) and the unpooled branch of numDeletedDocs (info.getDelCount() to info.getDelCount(softDeletesEnabled)), but left the loop; its commit message says the point is that "the number of document can be read from commit points without opening a full blown reader". The discussions of #9280, #9388 and #9247 never mention hasDeletions.
The devil's-advocate check209 words

Strongest case for "intended": hasDeletions means hard (live-docs) deletions, like SegmentCommitInfo#hasDeletions() and a plain DirectoryReader.open(dir), which shows soft-deleted documents as live; and the writer does the same on purpose in numDeletesToMerge: // if we don't have a pooled instance let's just return the hard deletes, this is safe! (IndexWriter.java:6454), a fallback a reviewer on #13324 also called deliberate.

Why it fails:

  1. The method's own pooled and buffered checks already count soft deletes, so "hard only" does not describe the method.
  2. numDeletesToMerge returns a merge-policy-dependent count (a retention policy keeps soft-deleted documents) that needs a reader to compute, so under-counting is its safe direction. hasDeletions depends on no policy, its javadoc documents only false positives, and the exact soft count has been in the commit, readable in constant time, since LUCENE-8341.
  3. A writer without the soft-deletes field cannot even open such an index (IllegalArgumentException), so every writer that can see the segment is soft-aware.
  4. No javadoc, test, CHANGES or MIGRATE entry, issue, PR or list thread found calls this behaviour intended.

What remains are impact arguments (no in-tree caller), not intent arguments. Verdict: not intended, a minor defect; maintainers may still prefer a javadoc change or deprecation (option C) to the one-line fix.

Suggested fix

#

Recommended A. Count soft deletes in the committed-segment loop (one line)

In the loop over committed segments, replace info.hasDeletions() with info.getDelCount(softDeletesEnabled) > 0 (IndexWriter.java:1455), the count numDeletedDocs(info) already uses. It reads the commit's counters and loads no reader. The repro passes, as do the 8 closest suites (233 tests with the repro, assertions on and off) and all 8,898 core tests.

How it was found

#

Model-based randomized testing of soft deletes: random operation scripts on the real jars, checked after every step against an exact executable model of live, soft-deleted and hard-deleted documents. After each writer reopen it compares hasDeletions() with the model; the mismatch fired 1,341 times in 1,500 scripts and was reduced to one public-API JUnit test.

The method in full138 words
  • Method (non-formal): model-based randomized testing in a hunt unit on soft deletes. Random scripts of soft updates, doc-values soft deletes, hard deletes, flushes, NRT reopens, commits, forced merges, addIndexes, writer reopens and rollbacks ran on the stock jars; after each observation an exact executable reference model of live, soft-deleted, hard-deleted and retained documents was compared with the writer.
  • Signal. After a writer reopen the model expects hasDeletions() true whenever a deleted document is committed; the note "hasDeletions-after-reopen expected=true got=false anyHard=false" fired 86 times in the first 150 scripts and 1,341 times in 1,500. A later bounded-exhaustive run hit it too.
  • Reduction. The finder wrote a public-API JUnit (3 tests, one control); it was later minimized to the one test above.
  • The finder labelled it semi-formal; the registry records non-formal, because the first signal came from random scripts.

Registry title
IndexWriter#hasDeletions ignores committed soft deletes in segments the writer has not pooled, so a writer reopened on an index whose only deletions are soft deletes (or one that took such segments through addIndexes(Directory)) answers false, and true once an NRT reader is opened
Area
index / IndexWriter statistics (soft deletes)
Priority
Low, rank 720: IndexWriter#hasDeletions always answers false after a restart when the only deletions are committed soft deletes, but no Lucene code calls it and getDocStats and NRT readers give the right answer.
Impact class
minor
Impact note
Only applications that configure a soft-deletes field and call IndexWriter#hasDeletions are hit, and only for segments the writer has not pooled: after a writer is opened on an existing index whose only deletions are committed soft deletes (any restart), or after addIndexes(Directory) of such segments; the same writer's getDocStats() and NRT readers count the deletes, and the answer turns true once DirectoryReader.open(writer) pools the segment; no Lucene code calls the method, so no search result, merge decision or index file changes; opt-in feature, any index size, every release since 7.4.0.
Summary
You configure a soft-deletes field, soft-delete a document (softUpdateDocument, or updateDocValues on that field), commit, close, and open a new IndexWriter on the index; you expect hasDeletions() to return true, because its javadoc says 'Returns true if this index has deletions', IndexWriterConfig#setSoftDeletesField says a soft-deleted document 'is treated as if it has been hard-deleted through the IndexWriter API', and the same writer's getDocStats() counts the deleted document (maxDoc 2 and numDocs 1 in the repro). Instead it returns false, with -ea and -da, until DirectoryReader.open(writer) puts the segment into the reader pool; after that the same call on the unchanged index returns true.
