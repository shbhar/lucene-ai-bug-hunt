k-NN classifiers score their training filter query, so a filter that removes nothing can change the class

The k-NN classifiers document their training query as a filter but add its score to every neighbour's similarity. On three documents, a filter that keeps all three (MatchAllDocsQuery or a year range) flips the answer from Y to X on main; every release since 4.6.0 scores the filter.

The bug in 30 seconds

#

Lucene's classification module can train on part of an index: the classifiers take a training query, documented as "a Query to eventually filter the docs used for training the classifier, or null if all the indexed docs should be used". The k-NN classifiers then vote among the k most similar labelled documents, weighting each vote by its score.

  1. Index three labelled documents: "aa bb" (class Y), "aa" (X), "aa" (X). Classify "aa bb bb" with KNearestNeighborClassifier, k = 3, minDocFreq 1, minTermFreq 1: with no training query you get Y (Y 0.333, X 0.309).
  2. Pass a training query that keeps all three documents: MatchAllDocsQuery, or IntPoint.newRangeQuery("year", 2020, 2025). The javadoc calls it "a Query to eventually filter the docs used for training", so, read as a filter, you expect Y again.
  3. You get X (X 0.417, Y 0.333). No error, with assertions on or off. The same filter with score 0, new BoostQuery(q, 0f), gives Y.
  4. Why: the filter is added as a scoring MUST clause, so each neighbour's score gains 1.0 ("aa bb" 2.30 to 3.30, each "aa" 1.07 to 2.07). Votes are weighted by score / top score, so each X vote grows from 0.46 to 0.63 and two X votes beat one Y vote.
  5. A filter whose score varies, such as a term on a text field, can even swap the nearest neighbour (k = 1: "aa", class X, becomes "aa bb", class Y). The fuzzy, document and perceptron classifiers are hit too; Occur.FILTER fixes it.

Who is affected

#

Applications that pass a training query to KNearestNeighborClassifier, KNearestNeighborDocumentClassifier, KNearestFuzzyClassifier or BooleanPerceptronClassifier (opt-in, @lucene.experimental). In a 300-document probe the class scores moved in 590 to 705 of 800 cases; the class flipped in 0 of 800 for constant-score filters and up to 320 of 800 for text-scored ones.

Mechanism, terms and numbers826 words

KNearestNeighborClassifier, KNearestNeighborDocumentClassifier, KNearestFuzzyClassifier and BooleanPerceptronClassifier take a training query, documented as "a Query to eventually filter the docs used for training the classifier, or null if all the indexed docs should be used". The k-NN classifiers add it, and the class-field restriction WildcardQuery(class:*), to their similarity search as scoring Occur.MUST clauses, so the filter's score is added to every neighbour's score; each vote is then weighted by score / top score. A filter that keeps every document can therefore still change the class scores (from 5.3.0 for constant-score filters), and the class whenever the shift outweighs the similarity gap: on three documents, MatchAllDocsQuery or a year range turns Y (Y 0.333, X 0.309) into X (X 0.417, Y 0.333). A filter whose score varies between documents can also change which documents are the nearest neighbours, and the perceptron, which trains in the score order of the same kind of query, can learn a different model. The filter still restricts which documents are used. Every release from 4.6.0 to 10.5.2 and main is affected; Occur.FILTER for the training query fixes it, and new BoostQuery(q, 0f) (same matches, no score) is a workaround.

Terms

#
  • Training query: a constructor argument of KNearestNeighborClassifier, KNearestNeighborDocumentClassifier, KNearestFuzzyClassifier and BooleanPerceptronClassifier: "a Query to eventually filter the docs used for training the classifier, or null if all the indexed docs should be used" (KNearestNeighborClassifier.java:82-83; the same in the other three). For example, train only on the training split, one tenant or one time window.
  • k-NN vote: the classifier searches for the k labelled documents most similar to the input (MoreLikeThis, or NearestFuzzyQuery for the fuzzy variant). Each neighbour votes for its class with weight score / maxScore, its score divided by the top hit's score (KNearestNeighborClassifier.java:195, :207); a class's score is the sum of its neighbours' weights divided by k (:219-225).
  • MUST and FILTER: in a BooleanQuery, a MUST clause must match and adds its score; FILTER is "Like MUST except that these clauses do not participate in scoring" (BooleanClause.java:35).

The bug

#
  1. knnSearch adds the similarity query as SHOULD (MUST in the fuzzy classifier, so there a neighbour must match at least one fuzzy term), then WildcardQuery(class:*) as MUST and the training query as MUST (KNearestNeighborClassifier.java:171-178; KNearestFuzzyClassifier.java:141-145; KNearestNeighborDocumentClassifier.java:144-151).
  2. So every hit's score is its similarity plus 1.0 for the class-field clause plus the training query's score. MatchAllDocsQuery and point ranges add a constant 1.0; a term on a text field adds a BM25 score that varies with field length.
  3. The vote divides each score by the top score. Adding the same number to every score pulls every weight towards 1, which favours the class with more, weaker neighbours; a varying addition can also reorder the top k.
  4. BooleanPerceptronClassifier builds the same two MUST clauses and trains over the hits in score order (BooleanPerceptronClassifier.java:130-140). Without a training query every hit scores 1.0 (doc-id order), and a constant-score filter keeps that order; a text-scored filter can reorder the training. The weights change only for a document the current model misclassifies (:155), and with batch size 1 each change takes effect at once (:162), so the model depends on the order.

The numbers

#
  • k = 3, documents "aa bb" (Y), "aa" (X), "aa" (X), input "aa bb bb". Similarity: "aa bb" 1.3037, each "aa" 0.0676. With the class-field +1.0: 2.3037 and 1.0676, weights 1.0 and 0.4634, so X = 2 x 0.4634 / 3 = 0.3090 < Y = 0.3333. With MatchAllDocsQuery (another +1.0): 3.3037 and 2.0676, weights 1.0 and 0.6258, so X = 0.4172 > Y = 0.3333. An IntPoint year range over all three documents gives the same numbers; KNearestNeighborDocumentClassifier flips the same way; KNearestFuzzyClassifier keeps X, 0.4997 becomes 0.5554.
  • k = 1, documents "aa" (X, tags "train news sports 2024") and "aa bb" (Y, tags "train"), input "aa", training query TermQuery(tags:train). Similarity: "aa" 0.0960, "aa bb" 0.0729. The tag term scores 0.1098 on the one-word tags field and 0.0665 on the four-word one, so "aa bb" ranks first (1.1828 against 1.1625) and the answer changes from X to Y.
  • BooleanPerceptronClassifier (batch size 1, bias 1.5) on two "aa" documents labelled true (tags "train pad") and false (tags "train"): "aa" is false without and true with TermQuery(tags:train).
  • Control everywhere: new BoostQuery(q, 0f) matches the same documents with score 0, and for these filters, which keep every document, it gives exactly the no-query answer, so the cause is the filter's score, not its matches.
  • Secondary: with no training query at all, the class-field clause's 1.0 still gives neighbours that share no term with the input a non-zero vote (in the text and document classifiers; the fuzzy classifier requires a fuzzy term match). The vote formula is not documented, so this is a side effect of the same MUST clauses, not a contract break.
Exposure and likelihood326 words
  • Who is exposed. Users of the opt-in lucene/classification module (the four classes are @lucene.experimental) who pass a training query, for example to train on one split, tenant or time window. Callers that pass null get only the secondary class-field effect.
  • How often. On a 300-document, 3-segment index (283 live) with four filters that select the same 168 documents, the class list differed from the zero-score control in 590 to 705 of 800 cases per classifier and filter (a case is one of 5 values of k and one of 160 input texts; each calls getClasses and assignClass). The assigned class changed in 0 of 800 cases for the two constant-score filters (a StringField term, an IntPoint range) and in 40 to 320 of 800 for the two whose score varies (a text-field term, a text-scored BooleanQuery). That probe ran the three k-NN classifiers on main only. In the finder's bounded-exhaustive run over 3,717,152 tiny cases, MatchAllDocsQuery changed the KNearestNeighborClassifier scores in 2,185,012 cases and the class in 15,617; an all-matching text-field term changed the class in 31,412.
  • Scale. None needed: three documents flip the class. The shift depends on the filter's score next to the similarity scores: MatchAllDocsQuery and point ranges add 1.0, while a StringField term every document has adds very little (a verifier saw X 0.31893 become 0.32096, no flip).
  • Silent. Nothing fails, and there is no unfiltered baseline to compare with; the scores look plausible.
  • Not affected. Which documents are used: in 9,600 filtered cases (19,200 filtered calls) there were 0 neighbours from outside the filter and 0 deleted documents. The naive-Bayes classifiers' MUST sites only count hits. BM25NBClassifier adds the training query as MUST too, and a verifier's probe shows MatchAllDocsQuery moving its class scores (Y 0.680 / X 0.320 to Y 0.561 / X 0.439); it is not part of the confirmed claim.
  • Versions. Every release from 4.6.0 (2013) to 10.5.2 and main; constant-score filters matter from 5.3.0.

Why it is a bug, not intended

#
  • Every constructor calls it "a Query to eventually filter the docs used for training the classifier"; null means all docs.
  • Occur.FILTER is "Like MUST except that these clauses do not participate in scoring"; these MUST clauses predate FILTER (2013).
  • No javadoc, test or issue says the filter should score; the same all-matching filter with score 0 gives the unfiltered answer.
The full argument302 words
  • Contract. KNearestNeighborClassifier.java:82-83: "@param query a Query to eventually filter the docs used for training the classifier, or null if all the indexed docs should be used"; the field javadoc (:69-72): "a Query used to filter the documents that should be used from this classifier's underlying LeafReader". The same wording in KNearestFuzzyClassifier.java:65, :79, KNearestNeighborDocumentClassifier.java:58 and BooleanPerceptronClassifier.java:72. Read as a filter, a query that keeps every document should give the null result. The javadoc does not say in so many words that the score is ignored, so this is the natural reading of the contract rather than its literal text; Lucene's CHANGES entries say the same about filtering in general: LUCENE-6227 added FILTER "to filter documents without participating in scoring (on the contrary to MUST)" (lucene/CHANGES.txt:10935-10936, 5.1.0), and LUCENE-6301 asks for "the BooleanClause.Occur.FILTER clause in order to let Lucene know that a Query should be used for filtering but not scoring" (:9931-9934, 5.4.0).
  • Tests. TestKNearestNeighborClassifier#testBasicUsageWithQuery (:145-159) and the matching fuzzy, perceptron, naive-Bayes and document tests check only the assigned class on one sample index. No test compares a filtered and an unfiltered run, and both fixes keep the whole module suite green, so no test pins the scored behaviour.
  • History. LUCENE-5284 (#6348, commit e60f7af1d16, 2013-10-17, "added method for training with a Query filter") added the query as a MUST clause; Occur.FILTER arrived only with LUCENE-6227 (a70006f2f5f, 2015-02-10, 5.1.0). LUCENE-5338 (#6402, debb363f6e3, "avoid considering unlabeled documents for training") added the class-field clause, also as a filter. LUCENE-6654 (#7712, 35810f4c77d, 5.3.0) added the score / maxScore vote because "the MLT score the documents accordingly" and tested only with a null query. The document (2015) and fuzzy (2017) classifiers copied the clauses; no commit ever used FILTER in the module.
The devil's-advocate check349 words

The strongest "intended" case: a Query normally scores and MUST keeps the score on purpose; FILTER already existed when LUCENE-6654 added the score-weighted vote and kept MUST; later classes copied the pattern; BM25NBClassifier uses a scored MUST clause (the class term) as its signal; the module is @lucene.experimental; and a zero-boost workaround exists. The cross-model reviewer rated this argument moderate in both of its lenses. The later fact check by a reviewer from the same family adds: callers may have used the query's score as a secondary ranking signal, so a fix changes results that have shipped since 4.6.0; the class-field constant gives every admitted neighbour a vote, much like the count vote before 5.3.0; and an online perceptron depends on example order anyway.

Why the bug reading is still the stronger one for the k-NN classifiers: every javadoc and the introducing issue call the parameter a filter, with null meaning "all the indexed docs", Lucene's CHANGES entries tell users to use FILTER when a query should filter but not score, and nothing anywhere says its score should shift the similarity or the votes (an absence, not proof). The MUST clauses predate FILTER and were carried over unchanged; no commit, issue or comment discusses the choice, and LUCENE-6654 attributes the ranking to the MoreLikeThis score. An ordinary year-range filter that keeps every document flips the class. The BoostQuery(q, 0f) workaround is undocumented; for such a filter it gives exactly the unfiltered result. @lucene.experimental allows API changes, not results that contradict the javadoc. Narrower points stand: the javadoc never says in so many words that the score is ignored; the class-field constant is a weaker finding because the vote formula is undocumented; and the perceptron's training order is undocumented. Every reviewer rated the bug real; the adjudication confirmed it with high confidence. The fact-check reviewer rated the intended case moderate for the training query and the class field and strong for the perceptron order, and suggests filing it as a documented-filter ambiguity and likely k-NN bug, with the class-field and perceptron parts as separate hardening or design questions.

Suggested fix

#

Recommended Make the training-query clause a FILTER (fix B)

Add the training query as Occur.FILTER instead of Occur.MUST in the four classifiers, one word each. A filter that keeps every document then gives exactly the no-query result, and callers without a training query see no change. The new test, the closest suites and the whole lucene/classification suite pass with it, assertions on and off.

All options and trade-offs3 options · 853 words

The training query still decides which documents can be neighbours or training examples; it just adds no score. Fix B leaves the class-field clause as a scoring MUST, so maxScore stays at least 1 and no division by zero can appear; fix A, the hunt's original proposal, also turns that clause into FILTER, which changes results for callers without a training query too. Until a fix ships, pass new BoostQuery(query, 0f) as the training query: it stays a required clause that matches the same documents, with score 0, so it acts as a non-scoring filter (for a filter that keeps every document, exactly the unfiltered result). Nothing is stored wrong, so no reindex is needed. Fix B changes results for callers that pass a training query, so it needs a CHANGES entry. Either way, add a test that a filter keeping every document gives the null result for each classifier. BM25NBClassifier has the same training-query MUST (BM25NBClassifier.java:216, :227); if it is included, change only those clauses, because its class TermQuery score is the intended signal there.

Trade-offs

Implements the natural, non-scoring reading of the documented filter with the smallest change, and changes nothing without a training query. Callers that pass one get different scores, neighbours and sometimes classes than current releases give (the scored behaviour has shipped since 4.6.0), so it needs a CHANGES entry. It leaves the secondary class-field constant as it is (the independent reproducer's class-field test still fails with it), and the perceptron's initial weights and default bias still come from the whole index (BooleanPerceptronClassifier.java:99-124).

Trade-offs

  • Also removes the class-field constant, so the vote becomes pure similarity weighting: in the lead case the no-query result becomes Y 0.3333, X 0.0346 instead of X 0.3090.
  • Changes class scores for every caller, including those without a training query, and sometimes the class: on the lead data the fuzzy classifier with no training query answers Y (0.3333 against X 0.3321) instead of X (0.4997).
  • The maxScore > 0 fallback (an unweighted vote) is a design choice for maintainers; neighbours with score 0 still fill the top k.

Workaround: wrap the training query with a zero boost

#

Pass new BoostQuery(query, 0f) (or new BoostQuery(new ConstantScoreQuery(query), 0f)) as the training query.

Trade-offs

It keeps the query's matches and adds no score, the same effect as fix B; a selective query still removes the documents it does not match. Every executed control used a filter that keeps every document, and there it gave exactly the unfiltered result. Every caller has to know about it; it is undocumented and not a fix.

Downstream note

#

Solr's classification update processor passes its knn.filterQuery setting to KNearestNeighborDocumentClassifier as this training query, so Solr setups that use that setting get the shifted scores too.

How it was found

#

An AI finder compared the four classifiers with a small reference k-NN that weights votes by similarity alone, over 3.7 million tiny indexes per classifier, plus two checks that a training query keeping every document leaves the answer unchanged. Both checks failed thousands of times, and the finder reduced the signal to a public-API JUnit test.

The method in full184 words

Method: semi-formal, bounded-exhaustive translation validation: the real classifiers against an independently written reference, over every case in a small bounded space.

  • The reference is a weighted k-NN over the MoreLikeThis or NearestFuzzyQuery similarity alone. Two metamorphic relations: training query MatchAllDocsQuery against none, and a text-field TermQuery that every document matches against none.
  • Scope: a 4-word vocabulary; every training set of 1 to 3 documents over 2 classes (2-document sets also with each document deleted); 3,000 seeded sets of 4 to 6 documents over 2 or 3 classes; every query text of 1 to 3 words; k = 1 to 4: 3,717,152 cases per classifier.
  • KNearestNeighborClassifier: MatchAllDocsQuery changed the scores in 2,185,012 cases and the class in 15,617; the all-matching term changed the class in 31,412. The document variant equalled the text variant in every case.
  • With fix A, a reduced run of 527,680 cases showed 0 differences of any kind: the independently written reference equals the fixed code.
  • The finder then wrote the 4-test JUnit; the independent reproducer, a cross-model reviewer, a devil's advocate and an adjudication each re-ran or rewrote it.

History

#

Introduced in 4.6.0 by LUCENE-5284 (2013), which added the training query as a scoring MUST clause. Since 5.3.0 (LUCENE-6654, score-weighted votes) constant-score filters change results too. All 121 releases from 4.6.0 to 10.5.2 and main were run and are affected; not fixed upstream.

Versions tested8 rows

Introduced by LUCENE-5284 (#6348, "Make it possible to filter classification training by Query"): trunk e60f7af1d16 (@tteofili, 2013-10-17, "added method for training with a Query filter"); the branch_4x backport 3df19e13b2d (LUCENE-5290, the same day) put it into 4.6.0 (2013-11-22). LUCENE-5338 (debb363f6e3 / a8a8242f50f, 2013-11-11, also 4.6.0) added the class-field MUST clause and moved the training query next to the similarity clauses. LUCENE-6654 (35810f4c77d / 2ddb06f6087, 2015-08-03, 5.3.0) added the score / maxScore vote, from which point constant-score filters matter. BooleanPerceptronClassifier is affected from 5.0.0, KNearestNeighborDocumentClassifier from 6.0.0 and KNearestFuzzyClassifier from 7.0.0, each from its first release. Similarity changes (BM25 in 7.0, its 8.0 revision) move the exact numbers between eras, but in every release from 4.6.0 at least one probe check changes the result.

Bug record

#

LFV-684, snapshot of 2026-10-30

Registry title
KNearestNeighborClassifier, KNearestFuzzyClassifier, KNearestNeighborDocumentClassifier and BooleanPerceptronClassifier add their documented training filter query (and the class-field restriction) as scoring Occur.MUST clauses, so a training query that filters out nothing changes the k-NN class scores and can flip the assigned class, the nearest neighbours or the learned perceptron model (released since 4.6.0)
Area
classification / k-NN classifiers and BooleanPerceptronClassifier (training query)
Priority
Low, rank 294: In the experimental, little-used classification module.
Impact class
silent wrong results
Impact note
Applications that use the opt-in, @lucene.experimental lucene/classification module and pass a training query to KNearestNeighborClassifier, KNearestFuzzyClassifier, KNearestNeighborDocumentClassifier or BooleanPerceptronClassifier get silently different results, with -ea and -da alike and no error: any training query with a non-zero score shifts the k-NN class scores on most calls (since 5.3.0; the class list changed in 590 to 705 of 800 calls in the security probe), a query whose score varies between documents (for example a term on a text field) also changes which documents are the nearest neighbours and, for the perceptron, the training order and so the model, and the assigned class flips whenever the shift outweighs the similarity gap (security probe on a 300-document index: 0 of 800 calls for two constant-score filters, 40 to 320 of 800 for two varying-score filters; the finder's 3-document repro flips with MatchAllDocsQuery); no scale is needed, the training query still restricts which documents are used, and every release from 4.6.0 through 10.5.2 and main is affected.
Summary
You index three labelled documents ('aa bb' as Y, 'aa' as X, 'aa' as X), build KNearestNeighborClassifier with k = 3 once with no training query and once with MatchAllDocsQuery (the parameter is documented as 'a Query to eventually filter the docs used for training the classifier', and this one removes nothing), and expect the same answer for 'aa bb bb'. Instead the answer flips from Y (class scores Y 0.333, X 0.309) to X (X 0.417, Y 0.333), because the training query and the class-field WildcardQuery are added as scoring Occur.MUST clauses, so their scores are added to every neighbour's MoreLikeThis score before each vote is weighted by score / maxScore; a training query whose score differs between documents, such as TermQuery(split:train) on a text field every document has, even replaces the nearest neighbour (k = 1: 'aa', class X, becomes 'aa bb', class Y). KNearestFuzzyClassifier and KNearestNeighborDocumentClassifier return different class scores in the same way, and BooleanPerceptronClassifier, which trains in the score order of the same kind of query, learns a different model ('aa' answers true instead of false).
