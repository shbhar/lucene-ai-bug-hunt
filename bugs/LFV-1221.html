A failed refresh makes ReferenceManager close its own current reference

When maybeRefresh() installs a new reference and releasing the old one throws, ReferenceManager also releases the new reference it has just made current. From then on every acquire() throws an IllegalStateException that blames the caller, until the manager is rebuilt; every release since 3.5.0 is affected.

The finding in 30 seconds

#

maybeRefresh() swaps in a new reference in two steps: make it current, then release the old one. A cleanup finally releases the new reference whenever the swap did not return normally. If the second step throws, the new reference is already current, so the cleanup closes the manager's own current reference.

  1. A ReferenceManager holds reference A with count 1, its own count. You call maybeRefresh(): it acquires A (count 2) and gets a new reference B (count 1).
  2. swapReference makes B current, then releases A, and that decRef throws an IOException, which the decRef contract allows.
  3. You expect maybeRefresh() to throw that IOException and B to stay current with count 1, so the next acquire() returns B.
  4. Instead a cleanup finally, written for a B that was never installed, releases B as well: B drops to count 0, which the manager treats as closed, while it is still current.
  5. Every later acquire(), and so every later uncontended maybeRefresh(), throws IllegalStateException: The managed reference has already closed - this is likely a bug when the reference count is modified outside of the ReferenceManager.

Who is affected

#

Only applications with their own ReferenceManager whose decRef can throw before the final release, or a SearcherManager (by reading, also a ReaderManager) whose beforeRefresh listener calls maybeRefresh() again while a reader close fails. Stock managers with ordinary listeners stay usable. The failure is loud, with no wrong results, but the manager must be rebuilt. Contrived, so priority Low.

Mechanism, terms and numbers518 words

ReferenceManager.swapReference makes the new reference current first and releases the old one second (ReferenceManager.java:56-57 on main). doMaybeRefresh marks the refresh as done only after swapReference returns (:172-173), and its finally releases the new reference whenever that mark is missing (:174-178). That finally came with LUCENE-3476 (2011) for a new reference the swap never installed, because the manager was closed during the refresh. When releasing the old reference throws instead (the abstract decRef is documented to throw IOException, :60-65), the new reference is already current, and the finally drops the manager's own count on it and closes it. maybeRefresh() throws the IOException; then every acquire() throws IllegalStateException "The managed reference has already closed - this is likely a bug when the reference count is modified outside of the ReferenceManager" (:112-113), and every later uncontended maybeRefresh() fails the same way in its own acquire() (:164). The application has to build a new manager. It needs a custom ReferenceManager whose decRef throws on a non-final release, or a SearcherManager (by reading, also a ReaderManager) whose beforeRefresh listener calls maybeRefresh() again while a reader close fails; the stock managers with ordinary listeners stay usable. Every release from 3.5.0 to 10.6.0 and main is affected (before 4.7.0 acquire() loops forever instead). The fix decides whether the new reference was installed before swapReference can throw.

Terms

#
  • ReferenceManager: the base class of SearcherManager and ReaderManager. It keeps one current reference and holds one count on it; acquire() adds a count for the caller, release() takes it back, and the reference closes when its count reaches 0. maybeRefresh() opens a newer reference and swaps it in.
  • The swap: swapReference (ReferenceManager.java:53-58) sets current = newReference (:56), then releases the old reference (:57), which calls the subclass's decRef.

Exposure and likelihood220 words
  • Who is hit. (a) A custom ReferenceManager subclass (public, @lucene.experimental) whose decRef can throw on a non-final release: the repro. (b) A stock SearcherManager whose RefreshListener.beforeRefresh calls maybeRefresh() on the same manager, while closing the intermediate reader throws (executed with a throwing IndexReader.ClosedListener); there close() of the manager then throws AlreadyClosedException: this IndexReader is closed too. The stock ReaderManager inherits the same refresh code and listeners, so it can reach the state the same way (by reading; not run).
  • Why the stock path is safe otherwise. doMaybeRefresh holds its own count on the old reference (:164), so the release inside the swap is never the final one, and IndexReader.decRef throws IOException only when the count reaches 0, from doClose() or the reader-closed listeners (IndexReader.java:222-227). A reader close failure then surfaces at the outer release (:181) and the manager stays usable (two controls passed).
  • Effect. One IOException, then every acquire() and every later uncontended maybeRefresh() throws until the application builds a new manager. The message says the caller changed the count, which points debugging the wrong way. No search returns wrong hits and nothing is written to the index.
  • Scale. None: one manager, one refresh, single thread, assertions on or off.
  • Likelihood: contrived. No public report of it was found since 2011.

Why it looks unintended

#
  • acquire()'s own comment says a closed current reference "can only happen if somebody outside of the RM decrements the refcount"; here the manager does it.
  • decRef is documented to throw IOException with no limit to the final release, and nothing forbids calling maybeRefresh() from a listener.
  • The cleanup was added (LUCENE-3476) for a new reference the swap never installed.
The full argument190 words
  • The manager's own invariant. acquire()'s comment (ReferenceManager.java:103-111): "This can only happen if somebody outside of the RM decrements the refcount without a corresponding increment since the RM assigns the new reference before counting down the reference." The exception message (:112-113) blames the caller.
  • The contract allows the trigger. decRef: "@throws IOException if reference decrement on the given resource failed" (:60-65). RefreshListener (:296-306) sets no rule against re-entry; the refreshLock is a ReentrantLock (:43) and doMaybeRefresh's comment allows the same thread to lock again (:155-160); IndexReader.ClosedListener.onClose declares IOException (IndexReader.java:141-145).
  • History. The finally came with LUCENE-3476 (#4550, 2011), "SearcherManager misses to close IR if manager is closed during reopen": the swap threw AlreadyClosedException (then from an inline null check, today from ensureOpen(), :54) and the new searcher was never installed. None of #4550, #4834 (LUCENE-3761) or #6499 (LUCENE-5436) discusses a failing release of the old reference.
  • Tests. TestSearcherManager.testReferenceDecrementIllegally (TestSearcherManager.java:331) expects this IllegalStateException only after a decRef made outside the manager. No test makes the old reference's release fail during a refresh.
The devil's-advocate check167 words

The strongest case: every in-tree manager's decRef fails only on the final release (IndexReader.decRef: "@throws IOException in case an IOException occurs in doClose()", IndexReader.java:208-213; its reader-closed listeners run there too, :222-227), and during a normal refresh the swap's release is never final. A decRef that fails earlier, or calling maybeRefresh() from inside its own beforeRefresh, could be called misuse.

Why it fails: it explains why the bug is rare, not why releasing the reference the manager has just made current would be correct. The abstract decRef contract does not limit failures to the final release, nothing forbids re-entry, and no javadoc, test, CHANGES entry or discussion says a failed refresh may leave a closed reference current; the code comment says the opposite. The cross-model review (OpenAI GPT-5.6) rated the intended-behaviour case weak; a later cross-model fact check rated it moderate and noted that a maintainer could reasonably close the issue as too contrived. What survives is a severity argument, hence priority Low.

Downstream note

#

Downstream products are exposed only if they ship their own ReferenceManager subclass whose decRef can fail before the final release, or call maybeRefresh() from a refresh listener; no query, document or index input can trigger it.

How it was found

#

A proof-obligation audit of ReferenceManager's refresh path checked each release of the new reference against the invariant stated in acquire(), and found the cleanup also runs after the swap has installed it. A public-API JUnit test then witnessed it on main; independent checks reproduced it with their own tests.

The method in full118 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: doMaybeRefresh may release the new reference only if the swap did not install it, because acquire() relies on the manager never leaving a closed reference current (:103-111). The finally (:174-178) keys on refreshed, which is still false when swapReference throws after current = newReference (:56-57), so the obligation is not met.
  • A one-test JUnit witnessed it on main with assertions on and off. An independent reproducer, an executed review by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier wrote their own tests from the claim alone, including two routes through the stock SearcherManager.

Priority

Impact note

Summary

Every later acquire() then throws IllegalStateException 'The managed reference has already closed - this is likely a bug when the reference count is modified outside of the ReferenceManager', blaming the caller for a state the manager created itself.
