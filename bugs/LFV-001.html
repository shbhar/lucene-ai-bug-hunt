openIfChanged returns null and isCurrent() stays true after a flush when the only changes are doc-values updates

If the only changes since an NRT reader opened are doc-values updates and the writer flushes, isCurrent() is true and openIfChanged returns null, although a fresh reader shows the change. SearcherManager keeps serving old values; it fails with the default config on every release from 7.4.0 to 10.5.2 and main.

The bug in 30 seconds

#
  1. Index two documents with a numeric doc-values field val = 1 and open an NRT reader r = DirectoryReader.open(w). It records the writer's version: 3.
  2. Call w.updateNumericDocValue(new Term("id", "1"), "val", 2), then w.flush(), then DirectoryReader.openIfChanged(r, w).
  3. You expect r.isCurrent() to be false and a new reader with val = 2. That is what happens without the flush(): the reopen shows val = 2 at version 4.
  4. Instead r.isCurrent() is true and openIfChanged returns null, so SearcherManager keeps the stale searcher. A fresh DirectoryReader.open(w) shows val = 2 yet reports version 3: flush() wrote the update without bumping the version.
  5. No error, and it lasts until something bumps the version. A soft delete made with updateDocValues (if the segment keeps a live document) and a forceMerge(1) with nothing to merge do the same, and with a writeAllDeletes=true reader the reopen returns null although isCurrent() is false; hasUncommittedChanges() can return false for an update the next commit() still writes.

Who is affected

#

Applications that make doc-values-only changes (updates, or updateDocValues soft deletes that leave the segment a live document) and refresh NRT readers with openIfChanged, SearcherManager, ReaderManager or PrimaryNode, when flush(), a no-op forceMerge, a writeAllDeletes=true reader or reader-pool RAM pressure writes the changes. Searches silently read old values. Elasticsearch and OpenSearch are not exposed on their normal paths (from reading code).

Mechanism, terms and numbers869 words

Suppose the only changes since an NRT reader was opened are doc-values updates, or soft deletes made with updateDocValues that leave the segment at least one live document. If flush(), a forceMerge that has nothing to merge, or a writeAllDeletes reader writes those changes to disk, the reader is then reported current and DirectoryReader.openIfChanged(reader, writer) returns null. A fresh reader shows the change, yet SearcherManager keeps serving the old values.

It is deterministic and needs only the default config and a single document. The filed case fails on every tested release from 7.4.0 through 10.5.2 and on main. The same gap makes hasUncommittedChanges() return false for an update that the writer has applied but not yet written, since 7.0.0. The owner filed it as #16900. A three-file fix that records the change in IndexWriter.finishApply passes the repro and the full core test suite (one seed).

What you do

#

You keep a near-real-time (NRT) reader open on an IndexWriter and refresh it with DirectoryReader.openIfChanged(reader, writer). SearcherManager.maybeRefresh() ends in the same code: it calls openIfChanged(reader, commit) with a null commit by default, and for an NRT reader that also goes to the writer (StandardDirectoryReader.java:412-413). You change documents in place with doc-values updates, for example updateNumericDocValue, and at some point the writer is flushed.

A tiny example, executed on main

#
  1. Set up. Index two documents, id 1 and id 2, each with a numeric doc-values field val = 1. Open r = DirectoryReader.open(w). The reader records the writer's version number: 3.
  2. Update. Call w.updateNumericDocValue(new Term("id", "1"), "val", 2).
  3. Without a flush, it works. r.isCurrent() is false, and openIfChanged(r, w) returns a new reader that shows val = 2, at version 4.
  4. With a flush, it fails. Do the same, but call w.flush() before reopening:
    • r.isCurrent() says true.
    • openIfChanged(r, w) returns null, which means "nothing changed".
    • A fresh DirectoryReader.open(w) shows val = 2 and also reports version 3, the same number as the stale reader r.

The same happens in these cases:

  • Soft delete, then flush. The soft delete is made with updateDocValues on the soft-deletes field. The deleted document stays visible: the old reader counts 2 documents, a fresh one 1. This needs the segment to keep a live document (here id 2). A soft delete of a segment's last live document makes the writer drop the empty segment with a version bump, and the reopen works.
  • A merge that has nothing to merge: forceMerge(1) on an index that already has one segment.
  • A reader opened with writeAllDeletes = true, that is DirectoryReader.open(writer, true, true). No flush is needed; that reopen itself returns null.
  • SearcherManager. maybeRefresh() returns true, which its javadoc defines as "either refreshed or that there were no changes to refresh"; it returns true in the working case too. The symptom is that acquire() keeps returning the stale searcher.

Why: one version number, two ways to write

#
  • The version is the reader's change stamp. isCurrent() and openIfChanged answer "nothing changed" when the writer's version equals the reader's and nothing is pending in the writer (IndexWriter.nrtIsCurrent, IndexWriter.java:6140-6146).
  • A doc-values update goes through three stages. It is buffered, then applied (resolved to document numbers and parked in the writer's per-segment state, the reader pool), then written to a new doc-values file on disk.
  • Applying it does not bump the version. finishApply bumps it only when documents were deleted, or when it drops segments whose documents are all deleted (IndexWriter.java:6721-6724, :6726-6734). A doc-values-only packet does neither. While the update is parked, it counts as pending (readerPool.anyDocValuesChanges()), so the reader is correctly not current.
  • The normal reopen bumps it. It writes the parked update and calls checkpoint(), which raises the version (IndexWriter.java:608, :4123-4126). That is step 3.
  • Three other paths write it without a bump. flush(), a forceMerge with nothing to merge, and a writeAllDeletes=true reader all write the parked update through ReaderPool.commit and then checkpointNoSIS(), which "does NOT bump segmentInfos.version" (IndexWriter.java:4119-4122, :4424, :2913-2916). The comment in ReaderPool.commit says the bump "was done previously (after we invoked BDS.applyDeletes)" (ReaderPool.java:363-369). That is true for deletes, not for doc-values updates.
  • After such a write, nothing is pending and the version is still 3. So the writer reports the reader as current, and doOpenFromWriter returns null (StandardDirectoryReader.java:462, :469-472). That is step 4.
  • Second symptom. The missing step also leaves the writer's change counter untouched. Commit, set a tiny RAM buffer so the update is applied at once, and update: hasUncommittedChanges() returns false, yet the next commit() writes val = 2 (IndexWriter.java:4225-4232).
  • A fourth path, with no flush at all. Under reader-pool RAM pressure, writeSomeDocValuesUpdates writes parked updates with checkpointNoSIS() too (IndexWriter.java:854-859). It needs at least two update packets: the probe committed 200,000 documents, then, with a 0.5 MB buffer, sent one update matching all of them and 100,000 updates matching nothing. There isCurrent() is false, yet openIfChanged returns null, because the reader it opens has the same version as the old one and is discarded (StandardDirectoryReader.java:469-472), as in the writeAllDeletes case.
Exposure and likelihood420 words
  • Silent wrong results. There is no exception. Searches keep reading old doc-values, so anything built on them sees old values, such as sort keys, scoring signals, facets and doc-values filters (inferred from the stale values, not run feature by feature). Documents soft-deleted with updateDocValues stay visible. The stale state lasts until something bumps the version: an add, a hard delete that actually removes a document, a real merge or a commit. A delete that matches nothing does not end it, and repeated reopens keep returning null.
  • Default configuration. The owner's filed steps exactly (the default IndexWriterConfig, one document, no threads) return null on every release from 7.4.0 to 10.5.2, on branch_10_6 and on main. The hunt test fails 20 of 20 derived seeds for each of its 5 bug tests. The reopen forms were run only on one- and two-document indexes and in a 200,000-document RAM-pressure probe; nothing in the mechanism depends on size, but that is read from the code. The soft-delete form uses the opt-in soft-deletes field. The writeAllDeletes form uses the expert open(writer, true, true).
  • Who is exposed. Applications that make doc-values-only changes and then do one of these:
    • call flush();
    • call forceMerge(1) or forceMergeDeletes() when there is nothing to merge;
    • open, anywhere on the same writer, a reader with writeAllDeletes=true. This makes even a different, plain NRT reader stale;
    • send updates that hit reader-pool RAM pressure. That takes at least two update packets; the probe used one update matching 200,000 documents plus 100,000 that matched nothing, with a 0.5 MB buffer.
  • NRT helpers inherit it.
    • SearcherManager and ReaderManager keep the stale reader.
    • ControlledRealTimeReopenThread.waitForGeneration returns true although the update is not visible.
    • The replicator's PrimaryNode opens its manager with writeAllDeletes=true (PrimaryNode.java:125). In the study, its flushAndRefresh() did not publish a doc-values-only change ("version 3 -> 3").
  • "Commit only if dirty" can lose updates. The study's sequence: tiny buffer, update, if (hasUncommittedChanges()) commit(), then rollback(). The commit was skipped and the update was lost. With the default 16 MB buffer, updating 1.5 million distinct documents once each made hasUncommittedChanges() false after update 1,470,089.
  • Downstream, from reading code only. Elasticsearch and OpenSearch are not exposed on their normal paths. They do not call IndexWriter.flush() on the indexing path, they open readers with writeAllDeletes=false, and every soft delete also adds a document. Applications built on PrimaryNode that use updateDocValues are possibly exposed. Solr in-place updates followed by an optimize or expungeDeletes that merges nothing were only simulated at the Lucene level.

Why it is a bug, not intended

#
  • Javadoc: openIfChanged returns null only "if there are no new changes"; isCurrent() checks for "any new uncommitted changes" via the writer.
  • An extra call hides a change: without flush() the update is seen; a hard delete plus flush() is detected.
  • 7.3.1 returns the new reader; it flipped at LUCENE-8290, a soft-deletes change. Similar misses (#6050, #6353) were fixed as bugs.
The full argument355 words
  • The contracts say otherwise (DirectoryReader.java at ea57360912ed):
    • openIfChanged(reader, writer) returns a reader "searching both committed and uncommitted changes from the writer" (:304-306), and null only "if there are no new changes" (:334-335).
    • For an NRT reader, isCurrent() "checks if either a new commit has occurred, or any new uncommitted changes have taken place via the writer" (:633-634).
    • getVersion() "is advanced every time a change is made with IndexWriter" (:620-621).
    • IndexWriter.hasUncommittedChanges() "Returns true if there may be changes that have not been committed". Its javadoc documents false positives and names no case where it returns false with uncommitted changes, though it does not promise that in so many words (IndexWriter.java:4219-4224). Here the next commit() does write the update, and LUCENE-5289 (#6353) fixed a false negative of this method as a bug.
  • The code's own comment assumes the bump happened. ReaderPool.commit says the version bump "was done previously (after we invoked BDS.applyDeletes)" (ReaderPool.java:363-369). That holds for deletes only.
  • An extra call makes a change less visible. Without flush() the update is seen. A hard delete followed by flush() is detected (version 3 to 4). So is tryUpdateDocValue followed by flush(), because that method calls changed() (IndexWriter.java:1780-1782).
  • It used to work. On 7.3.1 the same steps return a new reader with val = 2 at version 4. The behaviour flips exactly at LUCENE-8290, a change about soft deletes whose issue never discusses isCurrent, openIfChanged or the version.
  • No test or document covers it. The two randomized stress tests that reopen readers accept a null reopen without comparing it with a fresh reader (TestNumericDocValuesUpdates.java:1370-1374, TestMixedDocValuesUpdates.java:263-267), and they never flush after a doc-values update. Other tests do flush after doc-values updates (TestMixedDocValuesUpdates.java:531-546, :658-662), but then open a fresh DirectoryReader.open(writer) (:560, :675) instead of reopening an existing reader, so they cannot see the staleness. No javadoc, CHANGES or MIGRATE entry describes it.
  • Precedents were fixed as bugs. #6050 (LUCENE-4986): an NRT reader missed tryDeleteDocument. #6353 (LUCENE-5289): hasUncommittedChanges() returned false for a pending delete-by-term.
The devil's-advocate check270 words

The strongest case for "intended" was built by the independent reviewer:

  • Writer-based NRT is @lucene.experimental, with "no hard guarantee on how quickly you can get a new reader" (DirectoryReader.java:313-314).
  • The IndexWriter class javadoc says flushed changes "are not visible to IndexReader until either commit() or close is called" (IndexWriter.java:131-133).
  • getVersion() first says it "returns the version recorded in the commit that the reader opened" (DirectoryReader.java:620), and only then that it "is advanced every time a change is made".
  • Lucene's own randomized tests tolerate a null reopen.

Why it fails:

  • The latency caveat is about how fast a reopen happens, not about a reopen that reports "no changes" and never sees them.
  • The flush sentence is unqualified, so it does conflict with the NRT contracts; the issue should acknowledge that rather than explain it away. It predates them: it was added in 2008 (LUCENE-1194, 5b113c8af63), a year before writer-based NRT readers (LUCENE-1516, 3c91517add2, 2009), and its wording is the same today apart from formatting. The NRT javadocs are the more specific promise, and Lucene itself does not follow the flush sentence here: a fresh NRT DirectoryReader.open(writer) does see the change, and a hard delete across the same flush() is detected. Only isCurrent() and openIfChanged disagree with the fresh reader.
  • @lucene.experimental weakens API stability, not the stated meaning of null.

The reviewer rated the argument "moderate" and the bug "real" with high confidence. One caution for the issue: the same javadoc still says "(though, the current implementation never returns null)" (DirectoryReader.java:306-307). That line is stale, so do not rely on it.

#

Recommended Fix B: record the change when doc-values updates are applied (finishApply)

In IndexWriter.finishApply, call checkpoint() when an applied packet resolved doc-values updates and deleted nothing, as deletes already do (3 files, +16/-2, package-private). It fixes every trigger and hasUncommittedChanges(). The repro, the 16 closest suites, the full core suite (8,871 tests, one seed) and the nightly replicator tests pass. Fix B: record the change when doc-values updates are applied (finishApply) (validated by the checks) (recommended)

#

What it does:

  • FrozenBufferedUpdates sets a flag on the segment state when it adds a resolved update (:355).
  • closeSegmentStates returns that flag in ApplyDeletesResult.
  • finishApply calls checkpoint() when doc-values updates were resolved and nothing was deleted.

Three files, +16/-2, all package-private.

if (result.anyDeletes()) {
  maybeMerge.set(true);
  checkpoint();
} else if (result.anyDocValuesUpdates()) {
  // Resolved doc values updates are a new NRT-visible change, just like deletes: bump the SIS
  // version now, because the flush/commit/RAM-pressure paths that later write them to disk
  // (ReaderPool#commit, writeSomeDocValuesUpdates) only call checkpointNoSIS():
  checkpoint();
}

Trade-offs

  • Reach. It fixes every trigger (flush(), no-op forceMerge, writeAllDeletes readers, RAM pressure) and the hasUncommittedChanges() symptom, because it fixes the step they share.
  • Cost. One extra checkpoint() (an IndexFileDeleter checkpoint) per applied packet that resolved doc-values updates, the same cost deletes already pay. Not benchmarked.
  • Version timing. The version now also moves when updates are applied. Reopen frequency should not change, because a parked update already makes nrtIsCurrent false. That is reasoning from the code, not a measurement.
  • Two bumps per update on the normal reopen path. The version moves once when the packet is applied and again when writeReaderPool(false) writes the update and calls checkpoint() (IndexWriter.java:4123-4126). A probe on main shows it: an update and a reopen without flush give version 4 unpatched and version 5 with Fix B (with -ea and -da). The reader-side checks compare versions for equality (IndexWriter.java:6143, StandardDirectoryReader.java:469), so the gap is probably harmless; no other user of the version was checked.

Fix A: inside writeReaderPool(true), write the doc-values updates with a version bump first

#

Six lines, which restore what getReader did before 7.4. Before readerPool.commit, call readerPool.writeAllDocValuesUpdates() and then checkpoint().

if (writeDeletes) {
  if (readerPool.writeAllDocValuesUpdates()) {
    checkpoint();
  }
  if (readerPool.commit(segmentInfos)) {
    checkpointNoSIS();
  }
}

Trade-offs

  • Fixes flush(), no-op forceMerge and writeAllDeletes.

  • Not re-run at ea57360912ed.

Downstream note

#

Not attacker-driven: the application itself issues the updates, soft deletes and flushes, so the screen rates it outside Lucene's threat model, and it is already public as #16900. It can still matter downstream: if an application uses soft deletes for authorization, retention or privacy erasure, a stale reader keeps serving the "deleted" documents with no error.

The method in full304 words

Found by AI-assisted randomized model-based testing, without formal tools. A randomized test of a hash-based postings format under development, written and run with AI, failed on some seeds; the failures traced back to this reopen behaviour, and the owner filed #16900 on 2026-10-23.

Re-found by the 2026-10-22 study with 14 methods. None of these finds was blind: the task texts named the bug-note file pattern or listed the classes, so the area was hinted.

  • Fastest. A bug-agnostic stateful fuzzer found it in under a second. A TLA+ model of the version protocol (NrtVersion.tla) gave a 2-step trace for flush() and another for writeAllDeletes. The same model later found the hole in Fix A.
  • Missed. Five static analyzers: none of about 2,170 index-package reports pointed at it.
  • What every success had in common. An oracle that states the freshness contract ("null or isCurrent() implies the same content as a fresh reader"). An operation set with a doc-values-only change plus a flush, a no-op forceMerge or a writeAllDeletes reader. And, in the models, checkpoint and checkpointNoSIS kept as separate steps.
  • Second symptom. The hasUncommittedChanges() form was reached first by Alloy and TLC model checking in sessions that had no hint of this symptom (the area itself was hinted). In the study's votes Alloy called it a new bug and TLA+ the same root cause; a follow-up adjudicated it as a second symptom of the same root cause: one fix at finishApply removes both.

History

#

Introduced in 7.4.0 by LUCENE-8290 (#9337, 2018), which made flush() and writeAllDeletes readers write parked updates without a version bump. The gap underneath dates from LUCENE-7868 in 7.0.0 (RAM-pressure path, hasUncommittedChanges()); LUCENE-7976 (7.5.0) widened it by making forceMerge(1) of a lone segment a no-op. 6.6.6 is clean; each commit was checked against its parent.

Versions tested10 rows

Introduced by LUCENE-8290 "Keep soft deletes in sync with on-disk DocValues" (#9337). The master commit is 591fc6627ac and the branch_7x backport 8fdd3d7584b, authored 2018-05-02 and first released in 7.4.0. It made doFlush write parked updates through writeReaderPool(applyAllDeletes) (true for flush()), which ends in checkpointNoSIS(). It also replaced getReader's unconditional writeAllDocValuesUpdates() + checkpoint() with writeReaderPool(writeAllDeletes), so writeAllDeletes=true readers lost the bump; a default reopen still bumps.

The gap underneath is older. LUCENE-7868 (#8919, 58105a203a1, 2017-06-21, first released in 7.0.0) began parking applied updates in the reader pool without a version bump. It also added the RAM-pressure writer and the hasUncommittedChanges() symptom.

Two later changes only widened exposure. LUCENE-7976 (9c4e315c1cb, 7.5.0) made forceMerge(1) of a lone segment a no-op. LUCENE-8590 (eaf840867fa, 7.7.0) changed when a long update loop reaches the hasUncommittedChanges() gap.

All of these were found by running the same probe on lucene-core built at each commit and at its parent.

Bug record

#

LFV-001, snapshot of 2026-10-29

Registry title
openIfChanged returns null and isCurrent() stays true after a flush when the only changes are doc-values updates
Area
index / IndexWriter NRT
Priority
High, rank 1: Top of High: the widest-reaching silent bug in the set, in the default NRT path since 7.x, where apps that do doc-values updates or updateDocValues soft deletes and reopen after a flush, a no-op forceMerge, a writeAllDeletes reader or an automatic RAM-pressure write keep a stale searcher that still shows soft-deleted docs (filed as #16900, local fix exists).
Impact class
silent wrong results
Impact note
Anyone using NRT reopen (openIfChanged, SearcherManager, the replicator's PrimaryNode) with doc-values updates or soft deletes followed by flush(), a no-op forceMerge or a writeAllDeletes reader; default configuration, ordinary scale, released since 7.0.0/7.4.0.
Summary
You open an NRT reader, update a doc-values field (or soft-delete through updateDocValues), and then call flush(), a no-op forceMerge(1), or open readers with writeAllDeletes=true. You expect DirectoryReader.openIfChanged(reader, writer) to return a reader that sees the change. Instead it returns null and reader.isCurrent() is true, so SearcherManager keeps the stale searcher, and hasUncommittedChanges() can also return false while updates are uncommitted.
Introduced
LUCENE-8290 591fc6627ac (flush, no-op forceMerge and writeAllDeletes paths); LUCENE-7868 58105a203a19 (RAM-pressure path and the hasUncommittedChanges symptom, commit-level bisect) (2018-05-02 (LUCENE-8290, authored); 2017-06-21 (LUCENE-7868))
First affected version
7.0.0 (RAM-pressure path and hasUncommittedChanges); 7.4.0 (flush and writeAllDeletes paths)
Affected versions
flush and open(w,true,true): every release 7.4.0-10.5.2 plus branch_10_6 and main [exec]; no-op forceMerge(1) variant from 7.5.0 with the default config [exec]; RAM-pressure path and hasUncommittedChanges: 7.0.0+ [exec]; 7.3.1 and earlier correct for the flush case
Status
filed (filed upstream by the owner)
Verification
Confirmed in the earlier formal verification study by independent AI checks and a rerun on Lucene main; also a cross-model review that agreed; not yet triaged by a person.
Found by
non-formal baseline: randomized/MBT; also reached by TLA+/TLC
