VectorUtil.l2normalize returns the zero vector when the float32 sum of squares overflows

VectorUtil.l2normalize({1e19f, 1e19f, 1e19f, 1e19f}) should give {0.5, 0.5, 0.5, 0.5} but silently returns all zeros: the sum of squares is added up in 32-bit float, overflows to infinity, and every component is divided by it. It needs components of about 1.8e19/sqrt(dim) or more and affects 9.8.0 through 10.6.0 and main.

The finding in 30 seconds

#

l2normalize gets a vector's length from the float32 dot product of the vector with itself. When the sum of squares is bigger than the largest float it becomes infinity; the method divides every component by it and hands back zeros, with no error.

Floats and normalization in one minute

#
  1. A 32-bit float holds values up to about 3.4e38. A bigger result becomes Infinity, and a finite number divided by Infinity is 0.
  2. To normalize v, l2normalize computes its length (the square root of the sum of the squared components) and divides each component by it. The result has length 1.
  3. The squares can each be fine while their sum is not: 1e19 squared is 1e38, but four of them add up to 4e38.

The finding, step by step

#
  1. Take a finite, non-zero vector with large components: v = {1e19f, 1e19f, 1e19f, 1e19f}. Each square is 1e38 and the true length is 2e19, both ordinary floats (the largest float is about 3.4e38).
  2. Call VectorUtil.l2normalize(v). Its javadoc promises to make v unit length and to throw only for a zero vector.
  3. You expect {0.5, 0.5, 0.5, 0.5}. Lucene 9.7.0 returns exactly that.
  4. Instead the sum of squares, 4e38, is added up in 32-bit float and becomes infinity. Only an exactly zero sum is checked, so every component is divided by an infinite length and v becomes {0.0, 0.0, 0.0, 0.0}.
  5. No exception and no assertion: on main with -ea and -da (Panama provider) and -da (default scalar provider), and on the 9.8.0 and 10.6.0 release jars.

Who is affected

#

Callers of the public VectorUtil.l2normalize, which KnnFloatVectorField recommends for DOT_PRODUCT vectors, and the COSINE paths of the opt-in scalar-quantized formats. Only vectors with components of about 1.8e19/sqrt(dim) or more are hit (5.8e17 at 1024 dimensions); typical embeddings are far smaller (not measured here), so it is rare.

Mechanism, terms and numbers432 words

VectorUtil.l2normalize(float[]) promises to make its argument unit length and to throw only for a zero vector. Both vectorization providers take the squared norm from the float32 dotProduct(v, v) and test only for an exact zero. For a finite, non-zero vector whose sum of squares exceeds Float.MAX_VALUE (about 3.4e38) the sum is +Infinity, every component is divided by an infinite norm, and the method returns the zero vector without an error, with assertions on or off. Four components of 1e19 should become 0.5 each and become 0.0. It needs components of about 1.8e19/sqrt(dim) or more (5.8e17 at 1024 dimensions), far above typical embedding values (not measured here). 9.7.0 handled this input; #12518 (9.8.0) moved the sum to float32. A vector with a single component above about 1.84e19 has given zeros since the method was added in 9.0.0.

Step by step in the repro

#
  1. v = {1e19f, 1e19f, 1e19f, 1e19f}. Each square is about 1e38, below Float.MAX_VALUE (3.4028235e38).
  2. dotProduct(v, v) adds them in float (float res = 0f, DefaultVectorUtilSupport.java:41-42; Panama :116-130): 1e38, 2e38, 3e38, then 4e38, which is above the largest float, so the sum is +Infinity.
  3. +Infinity == 0 is false and isUnitVector(+Infinity) is false, so the method goes on to divide.
  4. sqrt(+Infinity) is +Infinity, and 1e19 / Infinity is 0. The array is now {0.0, 0.0, 0.0, 0.0}; the true answer is {0.5, 0.5, 0.5, 0.5}.
  5. VectorUtil.dotProduct asserts a finite result (VectorUtil.java:68), but l2normalize calls the provider directly, so nothing fires under -ea.

The threshold

#

For d equal components c, the float32 sum overflows when d * c^2 > 3.4e38, i.e. c > 1.84e19 / sqrt(d): about 9.2e18 at 4 dimensions and 5.8e17 at 1024. Before 9.8.0 each square was computed in float and summed in double, so only a single component above about 1.84e19 overflowed.

Exposure and likelihood263 words
  • Public API. KnnFloatVectorField's javadoc says DOT_PRODUCT values must "be unit-length, which can be enforced using VectorUtil#l2normalize(float[])" (KnnFloatVectorField.java:94). The field checks only that components are finite (:105), so it accepts the zeroed result: an executed probe built KnnFloatVectorField(DOT_PRODUCT, l2normalize({3e19f, 4e19f})) and got the value [0.0, 0.0] without complaint.
  • Selected callers inside Lucene (by reading): the COSINE paths of the opt-in scalar-quantized formats normalize the query (Lucene104ScalarQuantizedVectorScorer.java:116, ScalarQuantizedVectorScorer.java:49), each vector at merge time (NormalizedFloatVectorValues.java:51) and the centroid (Lucene104ScalarQuantizedVectorsWriter.java:631, :655, :818). The default HNSW float format does not call it. What a zeroed query, vector or centroid does to scores there was not run.
  • What users see. The zero vector instead of a unit vector, no exception, assertions on or off. Whatever is computed from it (scores, quantization) uses a zero vector; the effect on scores was not executed end to end.
  • How likely. Contrived: typical embeddings are far below this magnitude (not measured here), and the searches found no report since 9.0.0. Hence priority Low.
  • Native provider. The opt-in native provider (NativeVectorUtilSupport.java:589-607) calls a native lucene_l2normalize when the loaded library exports one, and otherwise delegates to the Panama or default code, which has the same bug. The in-tree C source declares that function (lucene/misc/src/c/dotProduct.h:72) but dotProduct.c does not define it. A library that does export it was not checked, and fix A does not change that path.

Why it looks unintended

#
  • The javadoc promises a unit vector, throwing only for zero vectors (VectorUtil.java:201-202); this input is finite, non-zero, and {0.5, 0.5, 0.5, 0.5} is representable.
  • 9.7.0 gets it right; #12518 (9.8.0) narrowed the range for speed, saying nothing about overflow.
  • Counter: vector math is float32 by design (#12281). But l2normalize is what brings such vectors into range, and fails silently.
The full argument130 words
  • Contract. l2normalize(float[]): "Modifies the argument to be unit length, dividing by its l2-norm. IllegalArgumentException is thrown for zero vectors." (VectorUtil.java:201-202). l2normalize(float[], boolean): "@throws IllegalArgumentException when the vector is all zero and throwOnZero is true" (:221-226). No javadoc, CHANGES.txt or MIGRATE.md entry sets a magnitude limit.
  • Tests. TestVectorUtil.testNormalize checks unit length on random vectors of ordinary magnitude (TestVectorUtil.java:113-118) and testNormalizeZeroThrows the zero case (:120-123). No test pins down large magnitudes either way.
  • History. 9.0.0 to 9.7.x squared each component in float and summed in double, so this input worked. #12518 ("Use panama vector for l2normalize", 2023, first in 9.8.0) replaced the loop with IMPL.dotProduct(v, v); its discussion is about speed only. The history records no intent to narrow the range.
The devil's-advocate check279 words

The case for "out of range": on #12281 uschindler wrote "The change to double is out of discussion now ... We are a search engine that calculates float scores" and, in the comment that asks for a separate overflow issue, "I strongly disagree to use double math". VectorUtil.dotProduct and cosine assert finite results; #12373's 1e17 component cap was closed with "no consensus to impose this limit"; and the org.apache.lucene.util package doc says "APIs in this package are primarily internal and may change between releases" (package-info.java:35). Such a vector already breaks the float similarity functions: for {3e19, 4e19} the DOT_PRODUCT self-score is Infinity and the COSINE score NaN (executed probe). The cross-model review lenses rated this argument moderate; the intended-behaviour advocate found that it does not hold (real, Low).

Why it fails: l2normalize is exactly the tool that makes such a vector usable (afterwards every component is at most 1 and the similarity math is finite), and it answers with silent zeros, not an error. The fix needs no double math on the similarity hot path: fix A uses double only after the float32 sum has overflowed (9.0.0 to 9.7.x summed every call's squares in double), and option D uses none. The package note does not make this a private method: KnnFloatVectorField's javadoc sends users to it. On #12281 uschindler also asked for a separate issue for "vectors where the float overflows (infinity) leading to infinite scores", i.e. treated overflow as a problem. #12373 was a general cap on all vectors and says nothing about this method. Verdict: not intended, a defect (Low). A documented limit with an exception would also remove the silent part (option D).

Suggested fix

#

Recommended A: fall back to double only when the float32 squared norm is infinite (both providers)

Fix A: in both vectorization providers, when the float32 squared norm is infinite, redo the norm and the division in double (+24 lines). The test passes, and so do TestVectorUtil, TestVectorUtilSupport and the Lucene104 scalar-quantized format tests (489 tests). The normal path gains one branch.

if (Double.isInfinite(squaredNorm)) {
  // the float32 sum of squares overflowed, although v may be finite: redo it in double
  return l2normalizeInDouble(v);
}

static float[] l2normalizeInDouble(float[] v) {
  double squaredNorm = 0;
  for (float x : v) squaredNorm += (double) x * x;
  double l2norm = Math.sqrt(squaredNorm);
  for (int i = 0; i < v.length; i++) v[i] = (float) (v[i] / l2norm);
  return v;
}

A: fall back to double only when the float32 squared norm is infinite (both providers) (validated by the checks) (recommended)

#

Right after the zero check in DefaultVectorUtilSupport.l2normalize and PanamaVectorUtilSupport.l2normalize, call a package-private helper DefaultVectorUtilSupport.l2normalizeInDouble(v) that sums (double) x * x, takes Math.sqrt and sets v[i] = (float) (v[i] / l2norm).

if (Double.isInfinite(squaredNorm)) {
  // the float32 sum of squares overflowed, although v may be finite: redo it in double
  return l2normalizeInDouble(v);
}

static float[] l2normalizeInDouble(float[] v) {
  double squaredNorm = 0;
  for (float x : v) squaredNorm += (double) x * x;
  double l2norm = Math.sqrt(squaredNorm);
  for (int i = 0; i < v.length; i++) v[i] = (float) (v[i] / l2norm);
  return v;
}

Trade-offs

  • One extra branch per call on the normal path. The fallback (two scalar passes) runs only when the float32 squared norm is infinite: for a finite vector, exactly where the old code returned zeros; a vector with an infinite component also takes it and gets the same result as before (NaN for that component). No benchmark was run.
  • Squares in double cannot overflow for any float input (at most about 1.2e77), so it also fixes vectors whose single squares overflow, such as {3e19, 4e19}.
  • It does not cover a native library that exports lucene_l2normalize (that path calls the library directly). It also leaves the opposite, underflow edge: a tiny non-zero vector whose float32 squared norm rounds to 0 is treated as zero-length (it throws or is returned unchanged, DefaultVectorUtilSupport.java:481-486, PanamaVectorUtilSupport.java:1619-1624); related: LFV-046, about such COSINE vectors passing field validation.

B: the same fallback in VectorUtil.l2normalize (validated by the checks)

#

Compute IMPL.dotProduct(v, v) in VectorUtil.l2normalize(float[], boolean) and fall back to double when it is infinite, before delegating to the provider.

Trade-offs

Simpler (one file), but computes the dot product twice on every call, including the per-query and per-vector merge-time normalizations.

What the checks validated

By the finder and the minimal-repro check: the four-component repro passes with assertions on and off, the two-component {3e19f, 4e19f} test passes under both providers, and TestVectorUtil (42 tests) passes.

C: scale before summing

#

Divide by the largest absolute component before summing the squares, as BLAS nrm2 does.

Trade-offs

Also handles the opposite, underflow edge (a tiny non-zero vector treated as zero-length), but adds a pass on every call unless it is gated on a zero or infinite float32 result. Not run.

D: throw for a non-finite squared norm and document the limit

#

Throw IllegalArgumentException when the float32 squared norm is not finite, and say so in the javadoc.

Trade-offs

Removes the silent zeros but rejects vectors whose unit vector is representable, and changes the contract. Not run.

Downstream note

#

A product that normalizes raw, user-supplied vectors with l2normalize gets a silent zero vector for components of about 1.8e19/sqrt(dim) or more; bounding vector magnitudes on input avoids it.

How it was found

#

A proof-obligation check of VectorUtil.l2normalize's documented postcondition (a unit vector for every finite, non-zero input) found that only an exactly zero squared norm is handled, not an infinite one. An executable JUnit test then showed the zero vector coming back.

The method in full111 words

Method: semi-formal (2026-11-04, main 5adff78bb168).

  • The obligation: for every finite, non-zero v, l2normalize(v) leaves a vector of length 1 or throws only when v is all zero (VectorUtil.java:201-202, :221-226). The providers discharge it only if the float32 squared norm is finite; they test == 0 and nothing else (DefaultVectorUtilSupport.java:480-481, PanamaVectorUtilSupport.java:1618-1619).
  • Witness: a public-API JUnit test, {3e19f, 4e19f} must become {0.6, 0.8}, which fails with [0.0, 0.0]. Later checks moved to inputs whose single squares are finite (64 x 1e19, then 4 x 1e19), which also showed that 9.7.0 handled them and 9.8.0 does not. The repro here is the four-component test.

Callers of the public VectorUtil.l2normalize (KnnFloatVectorField's javadoc recommends it for preparing DOT_PRODUCT vectors) and, inside Lucene, the COSINE paths of the opt-in Lucene104 scalar-quantized format (query normalization, merge-time NormalizedFloatVectorValues, centroids) get the zero vector back with no error, with -ea and -da alike, but only for raw vectors with components of about 1.8e19/sqrt(dim) or more (about 5.8e17 at 1024 dimensions; real embeddings are of order 1); the default HNSW float format does not call it [read]; every release from 9.8.0 through 10.6.0 (from 9.0.0 when a single component's square overflows).
Summary
You call VectorUtil.l2normalize on a finite, non-zero float vector with large components, for example 64 components of 1e19 (each square, 1e38, and the norm, 8e19, are finite floats). You expect the unit vector, 64 components of 0.125, because the javadoc says it 'Modifies the argument to be unit length, dividing by its l2-norm' and throws only for zero vectors. Instead it returns normally and leaves 64 zeros: the squared norm is summed in float32 and overflows to +Infinity, only an exactly-zero norm is checked, and every component is divided by Infinity.
Introduced

Widened by #12518 ('Use panama vector for l2normalize', by benwtrent; d1c35311615 on main, bb7e43be5a2 on branch_9x), which takes the squared norm from the provider's float32 dotProduct, so finite squares whose float32 sum overflows (the shipped four-component repro, 4 x 1e19, and the earlier 64 x 1e19 repro) also give zeros [exec: 9.7.0 passes both, 9.8.0 fails both, -da]. Later changes (#12726, #13615, #15043, #15721) do not change how the squared norm is accumulated [read]. (2020-12-09 (af3e12265fe, author and commit date); widened 2023-08-29 (#12518, author date))
