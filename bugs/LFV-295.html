Payload-filtered Intervals.term sources compare equal whatever their filter, so ordered, or, BooleanQuery and the query cache merge them

Intervals.term("a", filter) sources compare equal whenever the term is the same, whatever the payload filter, so duplicate removal merges different filters: ordered(a|x, a|y) finds 0 hits on a document it matches, and or, BooleanQuery and the query cache give missing or extra hits, silently. Since 9.9.0; payload-filter users only.

The finding in 30 seconds

#

Intervals.term(term, payloadFilter) matches a term only where its payload passes your filter. Lucene simplifies queries by dropping parts that equals calls the same, and this source's equals ignores the filter.

Background in 3 steps

#
  1. A payload is a few bytes stored with one occurrence (position) of a term, for example a part-of-speech tag or a label.
  2. Intervals.term("a", filter) matches a only at positions whose payload passes filter. Two filters on the same term can match different positions and different documents.
  3. While it builds and rewrites a query, Lucene removes duplicates by equals/hashCode: ordered and unordered turn equal neighbours into one repeated source, or keeps a set, BooleanQuery keeps FILTER and MUST_NOT clauses in sets, and the query cache looks queries up by equality.

The finding, step by step

#
  1. Index one document whose field f holds the word a twice: the first a carries payload x, the second payload y. Intervals.term("a", x::equals) and Intervals.term("a", y::equals) each match it, at positions 0 and 1.
  2. Search ordered(term("a", x::equals), term("a", y::equals)), that is "an a|x followed by an a|y". You expect 1 hit.
  3. You get 0 hits and no error. equals and hashCode of the two sources look only at the term a, so they are equal, and ordered() rewrites the pair into "a|x twice", which the document does not have.
  4. Every other duplicate check merges them the same way. In a 3-document test, or() of the two filters returns 2 of the 3 matching documents, two FILTER clauses return 2 documents where 1 matches both, MUST one + MUST_NOT the other returns 0 instead of 1, and a query cache serves the first filter's hits for the second.

Who is affected

#

Applications that call the payload-filter overload of Intervals.term with two different filters on the same term, in one query (default settings, any index size) or behind a query cache (default on 9.9.0 to 10.6.0, opt-in on main). No Lucene query parser builds these sources, and a public code search found only one-argument Intervals.term calls in Elasticsearch, OpenSearch and Solr.

Mechanism, terms and numbers744 words

Intervals.term(String|BytesRef, Predicate<BytesRef>) returns a source that matches the term only at positions whose payload passes the filter. Its hashCode is Objects.hash(term) and its equals compares only the term, so two sources on the same term with different filters are equal, and so are the IntervalQuery objects built from them.

Lucene removes "duplicate" parts by equality while it builds and rewrites queries, so the two filters are merged silently: ordered() and unordered() turn the pair into a repeat of the first filter, Intervals.or keeps one of them, BooleanQuery collapses two FILTER (or MUST) clauses into one and rewrites MUST x + MUST_NOT y to MatchNoDocsQuery, DisjunctionMaxQuery uses the first filter for both disjuncts, and a query cache serves one filter's hits for the other. Results are wrong in both directions, with default settings and any index size; the smallest case is one document on which ordered(a|x, a|y) finds 0 hits instead of 1.

The term-only equality dates from LUCENE-8694 (8.1.0, 2019), written with a wrong cast, so up to 9.8.0 the same calls threw ClassCastException. #12827 (9.9.0) fixed the cast only, which made the wrong equality reachable. Affected: 9.9.0 to 10.6.0 and main. Only applications that use the payload-filter overload with two different filters on one term are hit; no Lucene query parser builds these sources.

The mechanism (main 645d4fe14a20)

#
  1. The filter decides which positions match. Intervals.term(BytesRef, Predicate<BytesRef>) returns new PayloadFilteredTermIntervalsSource(term, payloadFilter) (Intervals.java:86-92; the String overload at :78-84 delegates to it). Its interval iterator skips every position whose payload fails the filter: } while (filter.test(pe.getPayload()) == false); (PayloadFilteredTermIntervalsSource.java:117-126; the matches iterator at :202-212).
  2. Equality ignores the filter. hashCode() is Objects.hash(term) (:256-259) and equals ends in return Objects.equals(term, that.term); (:261-267). toString() is PAYLOAD_FILTERED(a) for both (:269-272), so the merge is invisible in a printed query too.
  3. ordered() turns equal neighbours into a repeat. OrderedIntervalsSource.deduplicate groups consecutive sources with current.get(0).equals(source) and replaces each group with RepeatingIntervalsSource.build(current.get(0), n) (OrderedIntervalsSource.java:29-57). ordered(a|x, a|y) becomes "two occurrences of a|x"; the document has one, so 0 hits. Repeats exist so that "multiple iterators do not match on a single term" (RepeatingIntervalsSource.java:33-41), which is right only for sources that match the same positions.
  4. The same equality is used everywhere else. unordered() counts sources in a LinkedHashMap (UnorderedIntervalsSource.java:44-57); Intervals.or collects them in a HashSet (DisjunctionIntervalsSource.java:43-68); IntervalQuery.equals/hashCode delegate to the field and source (IntervalQuery.java:134-146); BooleanQuery keeps FILTER and MUST_NOT clauses in HashSets (BooleanQuery.java:126-140), drops duplicates on rewrite (:343-362), returns MatchNoDocsQuery("MUST clause also in MUST_NOT") (:364-381), removes a FILTER equal to a MUST (:387-394), merges duplicate MUST clauses (:450-455, deduplicateClauses at :714) and duplicate SHOULD clauses only when minimumShouldMatch is at most 1 (:442-447); two SHOULD clauses with minimumShouldMatch 2 are first rewritten to two MUST clauses (:577-588) and then merged. DisjunctionMaxQuery keeps its disjuncts in a Multiset (DisjunctionMaxQuery.java:47) that keeps the first of two equal keys with a count of 2 (Multiset.java:41-66, :79-84), so its weights use the first filter twice (DisjunctionMaxQuery.java:115-117). A query cache looks entries up by equality.

Adding the filter to equals/hashCode, and nothing else, makes the repro and every other executed shape pass, so the equality is the cause.

Exposure and likelihood280 words
  • Silent, both directions. Missing hits (ordered, unordered, or, MUST + MUST_NOT, DisjunctionMaxQuery) and extra hits (two FILTERs, two MUSTs, SHOULD with minimumShouldMatch 2, the cache), with no exception.
  • Default settings, any size. The in-query shapes need no cache and no configuration: default IndexWriterConfig under Lucene's randomized test framework, a plain IndexSearcher, one document. The minimal test fails in 20 of 20 iterations with derived seeds in one run (a random directory each time, one class-level codec) and with seed DEADBEEF under another codec.
  • The cache shape. 9.9.0 to 10.6.0 ship a default LRUQueryCache; it was executed on stock 9.9.0, 9.12.3 and 10.5.2 searchers (a 12,000-document segment, the query seen 8 times), and 10.6.0 has the same default (read). By reading 10.5.2, the default cache skips segments under 10,000 documents and its policy caches such a query after 5 sightings. On main caching is off by default (IndexSearcher.java:82-84, GITHUB#14187), so the application must install a cache.
  • Who is exposed. The payload-filter overload is opt-in. A natural trigger is or(term("bank", isNoun), term("bank", isVerb)), or the same term filtered per request. The flexible query parser's interval functions use only the one-argument Intervals.term, and no in-tree code outside tests calls the overload. A read-only public code search (2026-10-26) found only one-argument Intervals.term calls in Elasticsearch, OpenSearch and Solr. The #12827 author wrote that they could not wrap payload-filtered sources in a MinimumShouldMatchIntervalsSource because UnorderedIntervalsSource.deduplicate() called this equals, so such combinations do occur; whether their filters differed is not stated.
  • Likelihood: rare. The recorded public searches found no report of wrong results since 9.9.0. The intervals package "contains experimental classes" (package-info.java:21).

Why it looks unintended

#
  • Query#equals exists "so that QueryCache works properly"; equal queries typically have identical "document-filtering properties". These two equal queries match different documents.
  • The term-only equals is a 2019 copy with a wrong cast that threw ClassCastException; #12827 fixed only the cast, which exposed the wrong equality.
  • SpanPayloadCheckQuery, the span counterpart, compares its payloads in equals; FunctionMatchQuery compares its predicate.
The full argument241 words
  • The query contract. Query#equals is "required so that QueryCache works properly", and "Typically a query will be equal to another only if it's an instance of the same class and its document-filtering properties are identical" (Query.java:95-107).
  • The factory contracts. term(term, payloadFilter) is "filtered by the value of the term's payload at each position" (Intervals.java:78-92); ordered "Returns intervals in which the subsources all appear in the given order" (:418); or returns "the disjunction of a set of sub-sources" (:118-152). The results contradict these for legal inputs.
  • History. LUCENE-8694 (#9740, romseygeek, 2019) wrote equals/hashCode as a copy of TermIntervalsSource's, with a leftover cast to TermIntervalsSource, so for two distinct instances equals threw and never returned true. #12827 (eumus, 2023) changed only that line. Commit-level A/B: 9.8.0 jars plus the #12827 class give the 9.9.0 wrong results; 9.9.0 jars with #12827 reverted give 6 ClassCastExceptions.
  • Precedents. LUCENE-8694 calls the class "the intervals equivalent of SpanPayloadCheckQuery", whose equals/hashCode compare its payload criteria and its wrapped query (SpanPayloadCheckQuery.java:264-280). There, LUCENE-7808 (#8859, 2017) fixed "incomplete .equals and .hashCode methods, causing caching issues": the wrapped span query had not been compared. FunctionMatchQuery compares its DoublePredicate with Objects.equals (FunctionMatchQuery.java:119-129), and FilteredIntervalsSource compares its name (FilteredIntervalsSource.java:142-154).
  • Nothing documents it. No javadoc says that filters are ignored by equality or that two filters on one term must not be combined.
The devil's-advocate check157 words

The strongest case for "intended": the upstream test testPayloadFilteredTermIntervalsSourceEquals (#12827) asserts that two separately written (_) -> true filters give equal sources (TestPayloadFilteredInterval.java:93-101); Java lambdas have no value equality, so for lambda filters a term-only equals is what lets rebuilt queries hit the cache and be recognised as repeats (a Predicate class with a value equals could do it too); repeat detection deliberately relies on equality (romseygeek in LUCENE-10140, #11177); and the package is experimental.

Why it fails: the #12827 test covers only two filters that behave the same, and #12827 never discussed filters that select different positions; equality of two distinct instances never worked before #12827 (it threw), so no earlier release relied on it; repeat detection is right only for sources that match the same positions; "experimental" warns about API changes, not wrong matches. Verdict: not intended, a defect (the independent reproduction, the cross-model review, the intended-behaviour check and the adjudication, high confidence).

Suggested fix

#

Recommended A: include the filter in equals/hashCode

Add the filter to equals and hashCode (Objects.equals(filter, that.filter), Objects.hash(term, filter)), as FunctionMatchQuery does, and change the #12827 test to share one Predicate instance. The repro passes, and so do all 513 lucene/queries tests. Trade-off: separately built identical lambdas are no longer equal, so they are no longer treated as a repeat.

  @Override
  public int hashCode() {
    return Objects.hash(term, filter);
  }

  @Override
  public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    PayloadFilteredTermIntervalsSource that = (PayloadFilteredTermIntervalsSource) o;
    return Objects.equals(term, that.term) && Objects.equals(filter, that.filter);
  }
All options and trade-offs4 options · 619 words

One fix was built and validated through gradle on 645d4fe14a20. Because Java lambdas have no value equality, any fix that compares the filter must change the upstream test from #12827.

A: include the filter in equals/hashCode (validated by the checks) (recommended)

#

+2/-2 in PayloadFilteredTermIntervalsSource.java, plus the #12827 test testPayloadFilteredTermIntervalsSourceEquals changed to share one Predicate instance and to assert that a different filter is not equal (+8/-2 in TestPayloadFilteredInterval.java). For a lambda Objects.equals is identity; a Predicate class with value equals keeps value equality. FunctionMatchQuery compares its predicate the same way.

  @Override
  public int hashCode() {
    return Objects.hash(term, filter);
  }

  @Override
  public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    PayloadFilteredTermIntervalsSource that = (PayloadFilteredTermIntervalsSource) o;
    return Objects.equals(term, that.term) && Objects.equals(filter, that.filter);
  }

Trade-offs

  • Two separately built but identical lambdas are no longer equal: rebuilt queries miss the query cache and are not de-duplicated (no wrong result).
  • They are also no longer recognised as a repeat: on documents single = a x and double = a a, unordered(term(a, f), term(a, f')) with two separately built "payload is pos: 0" filters returns [double, single] with the fix and [] on main; with one shared always-true Predicate instance (p -> true), main and the fix both give [double], as plain unordered(term(a), term(a)) does (measured by the intended-behaviour check on main ea57360912ed). That is how unordered treats any two different sources that can match the same position ("The subsources may overlap", Intervals.java:432), but it changes behaviour for callers who rebuild the same filter; the CHANGES entry should say "reuse one immutable Predicate instance".
  • The fix is only as sound as the predicate's own equals: a Predicate class with a wrong value equals, or a predicate whose behaviour changes after the query is built, can still merge different filters or serve stale cache entries.
  • The upstream test from #12827 must change: with the source fix alone it fails (2 tests, 1 failure).
  • No in-tree code outside tests uses the overload.

B: an explicit filter key that takes part in equality

#

An overload such as Intervals.term(term, String filterName, Predicate<BytesRef>) whose name goes into equals/hashCode, as FilteredIntervalsSource does with its name (FilteredIntervalsSource.java:77-89, :142-154). Not built.

Trade-offs

Keeps cache hits and repeat detection for rebuilt filters with the same name; callers must name distinct filters distinctly. An API addition; the existing overload still needs A or deprecation.

C: a value-based payload filter

#

A factory that takes the accepted payload values, as SpanPayloadCheckQuery takes its payload list and match operation and compares them in equals. Not built.

Trade-offs

Exact equality, but covers fewer cases than a Predicate; an API change.

Not a fix: document the current equality

#

Say in the javadoc that filters are ignored by equality.

Trade-offs

It would document wrong results for ordered, or and BooleanQuery. Until a fix ships, users can keep two payload-filtered sources on the same term out of one query and out of a shared query cache (for example a QueryCachingPolicy that never caches IntervalQuery).

Downstream note

#

Not a Lucene security issue, but an application that stores access labels as payloads and builds one filter per user on the same term would silently lose a restriction or be served another user's cached hits (executed on a stock 10.5.2 searcher).

How it was found

#

A bytecode scan of query components listed fields that the matching code reads but equals/hashCode do not, and flagged this filter. An exhaustive equality check over small queries on a 12-document index then found equal IntervalQuery pairs that match different documents. An AI tool reduced it to a public-API JUnit; no model checker or solver was involved.

The method in full149 words

Method: semi-formal (a hunt unit, query object contracts).

  • A bytecode scan of the stock main jars (JDK 25 ClassFile API) compared, for each query component, the fields read by its matching code with the fields read by equals/hashCode. It reported EQ-MISS PayloadFilteredTermIntervalsSource.filter, read by the interval iterators' nextInterval and next but not by equals.
  • A bounded-exhaustive equality-congruence harness then tried every ordered pair of each query family over a small parameter domain on a fixed 12-document index, and witnessed equal IntervalQuery pairs with different matched documents (payload pos: 0 vs pos: 1: documents 0 1 3 6 10 vs 1 4 8).
  • The finder, an AI tool, wrote the 7-test public-API JUnit; the one-test repro was cut from it on 2026-10-29. The finder tagged the find "formal"; the registry records it as semi-formal because no TLC, SMT or proof output produced the signal.

queries / intervals (PayloadFilteredTermIntervalsSource equality; IntervalQuery dedup and cache keys)
Priority
Low, rank 855: Payload-filtered Intervals.term sources compare equal whatever their filter, so dedup and caching silently merge them, but no parser or downstream engine uses that overload, so it follows LFV-321.
Impact class
silent wrong results
Impact note
Applications that call the public Intervals.term(String|BytesRef, Predicate<BytesRef>) with two filters that select different positions on the same term, either in one query (Intervals.or/ordered/unordered/atLeast, BooleanQuery FILTER, MUST, MUST_NOT or minimum-should-match clauses, DisjunctionMaxQuery) or in two queries behind a shared query cache, silently get wrong matches in both directions (missing hits and extra hits), with -ea and -da, default writer, codec and searcher settings and any index size; the in-query shapes need no cache, the cache shape happens with a stock IndexSearcher on 9.9.0-10.5.2 (default LRUQueryCache: segments of at least 10000 docs, after about 5 uses; executed) and needs an application-installed cache on main (GITHUB#14187); no Lucene query parser and, by public code search, no Elasticsearch, OpenSearch or Solr code builds payload-filtered intervals; 8.1.0-9.8.0 throw ClassCastException on the same calls instead; nothing is written to the index.
Summary
You index a field with a payload at each position and build two sources on the same term with different payload filters, for example a@0 = Intervals.term("a", payload is 'pos: 0') and a@1 = Intervals.term("a", payload is 'pos: 1'), which on their own match different documents. You expect Intervals.or(a@0, a@1) to match both sets, ordered(a@0, a@1) to match the document 'a a', FILTER a@0 + FILTER a@1 to match only that document, and a query cache to keep the two queries apart. Instead PayloadFilteredTermIntervalsSource.equals/hashCode compare only the term, so the two sources are equal: or() keeps one of them, ordered() and unordered() become 'a@0 twice' and match nothing, the two FILTER clauses collapse into one (extra hits), MUST a@0 + MUST_NOT a@1 is rewritten to MatchNoDocsQuery, and a cached searcher returns the first filter's hits for the second, all with no error.
