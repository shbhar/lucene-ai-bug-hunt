RussianAnalyzer does not remove its default stop words when they are written with ё (всё, ещё, её, неё, чём)

The stock RussianAnalyzer removes the stop words все and еще but indexes всё and ещё, the same entries written with ё, because its stop filter runs before the stemmer folds ё to е: "Он всё ещё читает книгу" gives [все, ещ, чита, книг]. Silent; 9.0.0 to 10.6.0 and main.

The finding in 30 seconds

#

Russian text may write ё as е: ещё as еще, всё ("everything") as все.

Two things to know first

#
  1. RussianAnalyzer turns text into terms in this order: lowercase each word, drop it if it is in the stop list (very common words such as "and", "still", "all"), then cut its ending with the Snowball Russian stemmer.
  2. The stop filter removes a word only if it is spelled exactly as listed. Since 9.0 the stemmer first replaces every ё with е, so ёлка and елка both become елк.

The finding, step by step

#
  1. You index Russian text with the stock new RussianAnalyzer(). Its default stop list says "letter ё' is translated to е'" and holds все ("all") and еще ("still") only in their е spelling.
  2. You expect "Он всё ещё читает книгу" ("He is still reading the book") to give [чита, книг], like "Он все еще читает книгу": since 9.0 the analyzer's stemmer folds ё to е, so every other word gets one term for both spellings.
  3. But the stop filter runs before the stemmer and looks the word up exactly. The list holds все, not всё, so всё passes; the stemmer then folds it and indexes все. You get [все, ещ, чита, книг].
  4. Five default stop words behave this way: всё, ещё, её, неё and чём are indexed as все, ещ, е, не and чем. A phrase typed with ё, "всё равно", finds 0 hits on a document "Мне все равно."; the е-typed phrase finds it.
  5. No error, with assertions on or off.

Who is affected

#

Every user of the default RussianAnalyzer() whose documents or queries write всё, ещё, её, неё or чём with ё. Most Russian text prints ё as е, but dictionaries, teaching material and some authors write it, and ordinary text writes всё to tell it from все. Extra terms and phrase misses in one spelling direction; no exception or index damage.

Mechanism, terms and numbers501 words

RussianAnalyzer runs LowerCaseFilter, then StopFilter with the bundled Snowball list russian_stop.txt, then the Snowball RussianStemmer. The list's header says "letter ё' is translated to е'", so it holds only е spellings (все, еще, ее, нее, чем). Since 9.0 the stemmer replaces every ё with е before stemming, so every word that reaches it gets one term for both spellings. The StopFilter sits before that fold and does an exact lookup, so the five stop words whose standard spelling has ё (всё, ещё, её, неё, чём) are removed only when written with е; written with ё they are indexed as все, ещ, е, не and чем. The same sentence then indexes different terms depending on spelling, and a phrase typed with ё misses a document written with е. No error. It came with the Snowball 2.0 upgrade (LUCENE-9220, first released in 9.0.0) and is still on main; a small ё-aware stop lookup in RussianAnalyzer fixes it, and a fix changes indexed terms, so affected fields need reindexing.

The chain

#
  1. RussianAnalyzer.createComponents (RussianAnalyzer.java:109-116): StandardTokenizer -> LowerCaseFilter (:111) -> StopFilter(result, stopwords) (:112) -> optional SetKeywordMarkerFilter (:113) -> SnowballFilter(..., new RussianStemmer()) (:114). The javadoc lists the same order (:104-106); normalize() only lowercases (:118-121).
  2. The default set is russian_stop.txt, loaded with WordlistLoader.getSnowballWordSet (:45, :52-56). Header: "letter ё' is translated to е'." (russian_stop.txt:17); the only ё in the file is in that line. Entries: все (:32), ее (:47), еще (:53), чем (:95), нее (:127). The file's own paradigm notes write её as ее (:187) and the neuter всё as все (:214-216).
  3. StopFilter ("Removes stop words from a token stream", lucene/core/.../StopFilter.java:24) looks the token up exactly as it arrives, so всё is not found.
  4. RussianStemmer.stem() (RussianStemmer.java:399) starts with a loop that replaces every ё (eq_s("\u0451"), :413) with е (slice_from("\u0435"), :426). It runs after the StopFilter, so всё is indexed as все.

Exposure and likelihood276 words
  • Who is hit. new RussianAnalyzer() or RussianAnalyzer(getDefaultStopSet()), no setting needed; assertions on and off behave the same. A custom or factory chain that puts an е-only Russian stop set before the Russian Snowball stemmer has the same gap (from the code, not run), and a fix in RussianAnalyzer does not cover it.
  • How often. ё is optional, and most Russian text prints it as е. Wikipedia ("Yo (Cyrillic)") says that by and large "it is used only in dictionaries and in pedagogical literature"; otherwise ё "occurs only when it is necessary to avoid ambiguity (such as to distinguish between все ('everybody') and всё ('everything') ...)", and marking it throughout "is the preference of some Russian authors and periodicals". Snowball calls it "rarely used". So ё text is the minority, but всё is exactly the case where even ordinary text writes the ё. Frequency was not measured. Their е forms are entries 14 (все), 29 (ее), 35 (еще), 77 (чем) and 109 (нее) of a list its header calls "ranked (commonest to rarest)".
  • What goes wrong. The same sentence indexes different terms depending on spelling, and a phrase typed with ё ("всё равно") misses a document written with е ("все равно"), while the е-typed phrase finds it.
  • What still works. Index and query share the chain, so a document and a query that both use ё still match, and the е spellings are removed as intended.
  • Workaround today (from the code, not run): a custom analyzer that maps ё to е before the stop filter, for example with a MappingCharFilter.
  • Reindexing. Any fix changes the indexed terms of these words, so affected fields need reindexing.

Why it looks unintended

#
  • The stop list says "letter ё' is translated to е'" (russian_stop.txt:17), but the analyzer feeds it unfolded words.
  • Since 9.0 the same analyzer without stop words gives one term for both spellings of every word the stemmer sees.
  • Arabic and Persian place the stop filter by how their lists are normalized; Lucene added missing Romanian spellings (#12172).
The full argument181 words
  • The list is written in ё-folded form. "letter ё' is translated to е'" (russian_stop.txt:17); its paradigm notes write её as ее and the neuter всё as все. Snowball's Russian page says of its algorithm: "The original algorithm here assumed it had already been mapped to е".
  • The chain declares the spellings equal. RussianAnalyzer(CharArraySet.EMPTY_SET) maps both spellings to one term for 5 of 5 stop words and 5 of 5 ordinary words, because RussianStemmer.stem() folds ё first.
  • Arabic and Persian. ArabicAnalyzer: "the order here is important: the stopword list is not normalized!" (ArabicAnalyzer.java:135); PersianAnalyzer: "the stopword list is normalized with the above!" (PersianAnalyzer.java:136-137).
  • Precedent. #12172 (2024) added the comma-below spellings to the Romanian stop list (ro/stopwords.txt:4); #13233 added RomanianNormalizationFilter after its StopFilter and in normalize() "to complete the job" and asked users to reindex. In 2009, LUCENE-1576 (a bug, Brazilian) and LUCENE-1963 (an enhancement, Arabic) moved lowercasing before the StopFilter.
  • Nothing says otherwise. TestRussianAnalyzer has no ё; no javadoc, CHANGES or MIGRATE entry, and no comment on LUCENE-9220's PR or issue, discusses ё.
The devil's-advocate check267 words

The strongest case for "intended" (built by the intended-behaviour verifier and by a reviewer from another model family, OpenAI GPT-5.6; both rated it moderate): the javadoc documents StopFilter before the stemmer, and StopFilter promises only exact matches; the header can be read as provenance, and Lucene regenerates the file verbatim from Snowball (gradle/regenerate/snowball/snowball.sh:55-70); in Snowball's design ё folding is the caller's job; and in the 2012 java-user thread "Two questions on RussianAnalyzer" a maintainer (rmuir) declined to add a ё/е option to RussianAnalyzer ("I dont think so, there are tons of choices here ... So we generally just provide XYZ_Analyzer as an example mostly ... Instead just make your own!") and suggested a TokenFilter in the user's own analyzer.

Why it fails: that reply is from Lucene 3.6, when the stemmer kept ё apart for every word. Since 9.0 the default chain folds ё for every word the stemmer sees, a side effect of the Snowball 2.0 upgrade (no comment on its PR or issue compares the fold with the stop list), so the gap left is the stop words. Points to state carefully: normalize() (multi-term queries) and stem-exclusion keywords still keep ё distinct, so the equivalence holds for words that reach the stemmer; все/всё and чем/чём are different words when ё is written, so the claim is about the spelling that omits ё, which the list's single entry is meant to cover; and since the header can be read as provenance, the change may fairly be seen as an improvement to the default analyzer (the evidence is the same). Verdict: a defect, Low priority.

Suggested fix

#

Recommended A ё-aware stop lookup in RussianAnalyzer (recommended)

Recommended: in RussianAnalyzer, replace the StopFilter with a small package-private filter that also looks up the word with ё folded to е and passes the word on unchanged. Validated on 5adff78bb168: the repro and 18 of 18 Russian and Snowball tests pass. It changes indexed terms, so it needs a reindex note.

// RussianAnalyzer.createComponents: new StopFilter(...) becomes new YoAwareStopFilter(...)
@Override
protected boolean accept() {
  final char[] b = termAtt.buffer();
  final int len = termAtt.length();
  if (stopWords.contains(b, 0, len)) return false;
  int i = 0;
  while (i < len && b[i] != '\u0451') i++;      // no ё: nothing more to check
  if (i == len) return true;
  folded = ArrayUtil.grow(folded, len);
  for (int j = 0; j < len; j++) folded[j] = b[j] == '\u0451' ? '\u0435' : b[j];
  return stopWords.contains(folded, 0, len) == false;  // the token is not changed
}

A ё-aware stop lookup in RussianAnalyzer (recommended) (validated by the checks)

#

Replace new StopFilter(result, stopwords) (RussianAnalyzer.java:112) with a nested package-private FilteringTokenFilter that removes a token when the token, or its spelling with every ё replaced by е, is in the stop set. The token itself passes on unchanged. One file, +41/-1.

// RussianAnalyzer.createComponents: new StopFilter(...) becomes new YoAwareStopFilter(...)
@Override
protected boolean accept() {
  final char[] b = termAtt.buffer();
  final int len = termAtt.length();
  if (stopWords.contains(b, 0, len)) return false;
  int i = 0;
  while (i < len && b[i] != '\u0451') i++;      // no ё: nothing more to check
  if (i == len) return true;
  folded = ArrayUtil.grow(folded, len);
  for (int j = 0; j < len; j++) folded[j] = b[j] == '\u0451' ? '\u0435' : b[j];
  return stopWords.contains(folded, 0, len) == false;  // the token is not changed
}

Trade-offs

Custom stop sets that list a ё spelling keep working (a sketch that folded the token itself broke a custom set {всё}; the cross-model reviews found that). A custom е-only set passed to RussianAnalyzer(CharArraySet) now also removes the ё spellings: a behaviour change, arguably the right one, to call out. The extra lookup is one-way: a custom set {все} now also removes всё, but a custom set {всё} still does not remove все (only ё is folded, never е). normalize() and stem exclusion are unchanged. TestAllAnalyzersHaveFactories skips member classes, so the nested filter needs no factory.

Downstream note

#

Applications and search servers that build on RussianAnalyzer or getDefaultStopSet(), or that chain the same filters in the same order, index the same extra terms; mapping ё to е before the stop filter avoids it.

How it was found

#

A bounded-exhaustive differential check on the stock jars: each default stop word, written with ё in every possible position, went through the default analyzer and through the same analyzer without stop words. The default kept all 72 variants that the stop-free chain treats as the stop word itself (5 real spellings); a Persian control kept 0 of 284.

The method in full132 words

Method: bounded-exhaustive differential checking (semi-formal tier). For every default stop entry of the Russian, German, Serbian and Romanian analyzers and a Persian control, every spelling variant generated from the substitutions a filter after the StopFilter performs (for Russian: every subset of е positions written as ё) was analyzed and compared with the same analyzer built with CharArraySet.EMPTY_SET as the equivalence oracle.

  • Russian: 72 of 72 chain-equivalent variants kept (5 real spellings: её, ещё, всё, неё, чём; 67 mechanical variants that are not spellings of the listed words; the 5 are marked from a fixed list, not a dictionary). With ё folded before the StopFilter: 0 of 72 (vacuity check). Persian control: 0 of 284.
  • Reduced to a public-API JUnit, then to the one-method test above.
  • Found 2026-10-28 on main a9779ef3c193.

Low, rank 441: The stock RussianAnalyzer keeps the ё spellings of five default stop words, a minor analysis-quality bug in the same class as the Telugu and Bengali stop-list rows, and it leads that group because Russian is far more widely used.
Impact class
minor
Impact note
Analysis quality only, with no error: every application that analyzes Russian text with the default RussianAnalyzer() (or its getDefaultStopSet()), on every release from 9.0.0 through 10.6.0 and on main, indexes and queries the five common function words её, ещё, всё, неё and чём of its own default stop list as ordinary terms (е, ещ, все, не, чем) whenever the text writes them with ё, while their е spellings are removed, so the same sentence indexes different terms depending on spelling and a phrase typed with ё ('всё равно') misses a document that writes it with е ('все равно') while the е-typed phrase finds it; no corruption, crash or scale, -ea and -da behave the same, and because a fix changes indexed terms, affected fields need reindexing after it.
Summary
You analyze Russian text with the stock RussianAnalyzer. Its default stop list, the bundled Snowball russian_stop.txt, says in its header that 'letter ё is translated to е', so it lists её, ещё, всё, неё and чём only as ее, еще, все, нее and чем, and since 9.0 the same analyzer without stop words maps the ё and е spellings of every word that reaches its stemmer to one term. But the StopFilter runs before the only step that folds ё to е (the Snowball RussianStemmer), so the е spellings are removed while the ё spellings pass the StopFilter and are indexed as е, ещ, все, не and чем: 'Он все еще читает книгу' gives [чита, книг] but 'Он всё ещё читает книгу' gives [все, ещ, чита, книг], with no error.

It regenerated org.tartarus.snowball.ext.RussianStemmer from Snowball 2.0, whose stem() first replaces every U+0451 with U+0435; it did not touch RussianAnalyzer, and the 159 entries of russian_stop.txt are identical before and after. So the defect is an interaction: the chain order StopFilter before SnowballFilter and the analyzer's use of the Snowball list (added by LUCENE-2206), whose header states the ё-to-е precondition, both date from LUCENE-2055 (a6b7c5552ba, rmuir, 2010-02-05, first released in 3.1.0); from 3.1.0 to 8.11.4 that precondition was already unmet, but the stemmer kept ё distinct for every word too, so stop words were treated like all other words. Nothing in the PR or issue discusses Russian or ё. (2020-02-17 (authored and committed; PR merged 2020-02-17T17:38:02Z; master only, first released in 9.0.0))
