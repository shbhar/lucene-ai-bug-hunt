Automaton.next(Transition, int) returns -1 for a label the state accepts after initTransition

After initTransition(1, t) on 0 -a-> 1 -b-> 2, next(t, 'b') returns -1 although step(1, 'b') is 2: initTransition stores an absolute offset into the transition array, and next() reads it as an index among the state's own arcs. Only direct callers of this experimental API are hit, since 8.5.0.

The finding in 30 seconds

#

A Transition is also a cursor with one position field. initTransition and getNextTransition store and read it as an absolute offset into the automaton's single transition array; next(Transition, int) reads the same field as an index among the state's own arcs. On any state not stored first, next() starts past the arcs it should search.

Background: how an Automaton stores its arcs and looks them up

#
  1. An Automaton keeps every arc in one int[], 3 ints per arc (dest, min, max), one contiguous block per state, sorted by label. For each state it records where its block starts and how many arcs it has.
  2. Two ways to read a state's arcs: initTransition(state, t) followed by getNextTransition(t) iterates them one by one; step(state, label) and next(t, label) look one label up by binary search.
  3. next(t, label) is the reusable form: it starts from the cursor kept in t and leaves the cursor where it stopped, so the next lookup on the same state can continue from there.

The finding, step by step

#
  1. Build 0 -a-> 1 -b-> 2 with addTransition and finishState(). All arcs live in one int[], 3 ints per arc: state 0's arc at ints 0-2, state 1's arc at ints 3-5.
  2. Put a new Transition() on state 1 with initTransition(1, t). It returns 1 (state 1 has one arc) and stores the cursor 3, the offset of that arc in the array.
  3. Call next(t, 'b'). You expect 2, the same as step(1, 'b'): the lookup starts from the Transition's cursor, inclusive, and returns -1 only when no arc matches.
  4. Instead next() reads 3 as "start at state 1's arc number 3". State 1 has only arc 0, so the search range is empty and it returns -1, with no exception, assertions on or off.
  5. With more arcs it is partial: a state with 5 arcs (a c e g i) stored at offset 3 answers -1 for a, c, e and finds g, i. Lucene's own RunAutomaton resets the cursor first and is not affected.

Who is affected

#

Only application code that uses the experimental Automaton cursor API itself: it reuses one Transition, positions it with initTransition on a state whose arcs are not stored first, then calls next(Transition, int), and silently misses arcs. Lucene's only production caller, RunAutomaton, resets the cursor first, so no query, parser or index is affected.

Mechanism, terms and numbers401 words

Transition doubles as a cursor whose position is the package-private field transitionUpto. initTransition(state, t) stores there the absolute offset of the state's first arc in the automaton's single transitions[] array (3 ints per arc), and getNextTransition reads arcs from that offset. The public next(Transition, int), added in 8.5.0, passes the same field to a binary search that treats it as an index among the state's own arcs.

So after initTransition(1, t) on 0 -a-> 1 -b-> 2 the cursor is 3, next(t, 'b') searches state 1's arcs from index 3, finds none (it has one) and returns -1, while step(1, 'b') returns 2. Nothing throws, with assertions on or off. Lucene's only production caller, RunAutomaton, resets the cursor to -1 before each state, so no query, parser or index is affected; only application code that mixes initTransition and next() gets wrong answers. The fix makes next() read and write the same absolute encoding; a javadoc note is the alternative.

Exposure and likelihood317 words
  • Who is hit. Application code that reuses one Transition, positions it with initTransition on a state whose arcs are not stored first (any state other than the first one given arcs, so its block starts past offset 0) and then calls next(Transition, int), for example to build its own RunAutomaton-style transition table without allocating. It silently misses arcs: wrong lookups, wrong tables, wrong matches built on them.
  • Default vs opt-in. Public, @lucene.experimental API (Automaton.java:43); no setting; assertions on or off.
  • Lucene itself is not affected. The only production caller, RunAutomaton, sets transition.source = n and transition.transitionUpto = -1 for each state before calling a.next (RunAutomaton.java:77-80); the test-only MinimizationOperations does the same (:103-106). git grep finds no other caller. So this defect does not reach RegExp, wildcard, fuzzy, prefix or range queries or CompiledAutomaton through next(Transition, int).
  • Outside callers cannot use the in-tree idiom. transitionUpto is package-private, so code outside the package cannot reset it to -1, and initTransition is the only public call that sets the cursor for a state (getTransition(state, index, t) sets source and the arc but leaves the cursor as it was). Elasticsearch's copy of MinimizationOperations notes this in TODO comments ("cannot reset transition.transitionUpto (pkg private)") and allocates a new Transition per state, which is correct (elastic/elasticsearch#119309).
  • Scale. None needed: 3 states, 2 arcs.
  • Likelihood. Rare: no public report found since 8.5.0 (2020; keyword search).
  • The reverse mix (scoped out; read from the code, not run). After a hit next() leaves the index mid in the field (Automaton.java:717), and a following getNextTransition reads it as an offset (:495-497): in the repro's automaton, after a hit on state 1 (index 0), that is state 0's arc, and with assertions on transitionSorted (:493) can fail. Same root cause; fix A removes the wrong-state read (see its trade-offs).

Why it looks unintended

#
  • next()'s javadoc: the lookup starts from the Transition's source and transitionUpto, inclusive; -1 means no arc matches.
  • initTransition initializes the Transition to iterate all of the state's arcs, and is the only public call that sets the cursor for a state.
  • No doc says next() needs a fresh Transition; the second encoding came with next() in 2020.
The full argument214 words
  • The contracts. next(): "The transition to start the lookup from (inclusive, using its Transition#source and Transition#transitionUpto)"; "@return The destination state; or -1 if no matching outgoing transition" (Automaton.java:669-673). initTransition: "Initialize the provided Transition to iterate through all transitions leaving the specified state" (TransitionAccessor.java:22-27). After initTransition(1, t), a lookup that starts from t, inclusive, should find a label state 1 accepts.
  • The field's own comment names initTransition as its initializer: "init to -1 to provoke exception if nextTransition is called without first initTransition" (Transition.java:47-51), and Transition's class javadoc presents the object as the initTransition/getNextTransition cursor (:22-26).
  • Nothing a user can read excludes the mix: no javadoc, package doc, CHANGES.txt (only the LUCENE-9125 line) or MIGRATE.md entry says next() needs a newly allocated Transition.
  • History is consistent with an oversight (an inference; no record states intent). initTransition has stored the absolute offset since LUCENE-5752 (7339f52d921, 2014). 0528621d2fe (LUCENE-9125, 2020) added next(Transition, int) with a per-state index in the same field and, in the same commit, made both in-package callers reset it to -1, so no in-tree code ever mixes the two encodings. The issue (#10166) and the PR (apache/lucene-solr#1160) say nothing about the cursor encoding.
The devil's-advocate check217 words

The strongest case for "intended", made by the cross-model reviewer, who reproduced the -1, agreed on the root cause and found that the fix works: initTransition belongs with getNextTransition ("You must call getNextTransition to get each transition", TransitionAccessor.java:24), next() is meant for a new Transition per state whose cursor stays at -1, as every in-tree caller uses it, next()'s own javadoc calls the field "the latest reached transition index" (Automaton.java:665-666), and Automaton is @lucene.experimental; so mixing them is outside the protocol and at most a javadoc gap.

Why we still call it a bug. The public text is at best ambiguous. The TransitionAccessor sentence was written in LUCENE-5752 (2014), nearly six years before next() existed; it says that initTransition does not itself return an arc, not that next() must not follow it, and "transition index" says what next() stores, not that an initTransition cursor is an invalid start. The fresh-cursor protocol is design intent visible only in package-private code, and outside the package the -1 reset is impossible. @lucene.experimental allows API changes, not silent wrong answers, and the reviewer's own remedy, clarifying the javadoc, concedes that the public text does not exclude the trigger. A tie-breaker confirmed the bug at medium confidence on these grounds; maintainers may still prefer the javadoc fix.

Suggested fix

#

Recommended A. One encoding: next() reads and writes absolute offsets (recommended; validated)

Make next(Transition, int) use the same absolute encoding as initTransition: turn an offset inside the state's block into the index to start from (anything else, such as -1, starts at 0) and write back absolute offsets. In-tree callers search exactly the same ranges as today. Validated through gradle: repro, core util.automaton and automaton-query tests pass; formatter clean.

Trade-offs

For RunAutomaton and MinimizationOperations nothing changes, not even the ranges searched: their -1 starts at index 0, a hit continues from the matched arc, and a miss past the last arc writes the end offset, which maps back to the arc count, so later labels still return -1 at once. No public API changes (the field is package-private). The cursor now means one thing everywhere, so next() after initTransition or getNextTransition continues from where the iteration stands. One difference stays: after a hit next() leaves the cursor on the matched arc (as today's index does), while getNextTransition leaves it after the arc it returned, so a getNextTransition right after a next() hit returns the matched arc again. A state with no arcs (start -1, count 0) maps to index 0 and returns -1 without reading the array. Both are read from the diff; no run tests mixed next/getNextTransition sequences.

Still unsupported, as today: reusing a Transition by setting only source; a cursor left exactly at the start of the next state's block reads as this state's end. A variant with < instead of <= makes every cursor outside the state's own block start at 0, so setting only source always works, at the cost of a full binary search for labels past a state's last arc in RunAutomaton's construction loop; it passes the same repro and 148 upstream automaton tests. The javadoc's "transition index" (:665-666) could then say "position".

B. Document the protocol on next(Transition, int)

#

A javadoc note: the Transition must be a new one per source state with only source set, and must not be positioned with initTransition or advanced with getNextTransition.

Trade-offs

Not validated (no code change). The trap stays silent, and outside code that wants to reuse one Transition across states has no way to reset the package-private cursor.

Downstream note

#

Downstream code outside the package cannot reset the package-private cursor, so until a fix ships it should give each source state a new Transition with only source set (as Elasticsearch's copy of MinimizationOperations does), never one positioned by initTransition.

How it was found

#

A semi-formal proof-obligation check of next()'s documented contract against the cursor encoding initTransition uses: a lookup that starts from an initialized cursor must reach every arc of the state, and that obligation fails for any state not stored first. A public-API JUnit test witnessed the -1 on stock main.

The method in full97 words

The obligation comes from next()'s javadoc (start from source and transitionUpto, inclusive; -1 only when nothing matches) and initTransition's (initialize the Transition to iterate through all of the state's transitions). The check compared the two writers and readers of transitionUpto and found two encodings: an absolute offset (initTransition, getNextTransition) and a per-state index (next). An executable JUnit test on the stock main build confirmed the -1, and an independent reproducer, a cross-model review, an intended-behaviour devil's advocate, an adjudication and a tie-breaker then checked it (see the checks below).
