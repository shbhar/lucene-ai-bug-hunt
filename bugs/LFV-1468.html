CoveringQuery reports itself cacheable without asking its clauses, so a query cache keeps old hits after an in-place doc-values update

CoveringQuery tells the query cache it is cacheable by asking only its minimum-match field, never its clauses. If a clause reads a doc-values field that you update in place, the cache keeps the old hits (a count of 1 instead of 0 in the repro); affected since 7.2.0.

The finding in 30 seconds

#

CoveringQuery matches a document when at least N of its clauses match, with N read from a per-document field. Before reusing a cached result on a segment, the query cache asks the query whether that is still safe; this query answers for its N field only, never for its clauses.

Background: three pieces

#
  1. CoveringQuery(clauses, minimumNumberMatch) in the sandbox module matches a document when at least minimumNumberMatch of clauses match it. The minimum can be read per document, for example from a numeric doc-values field with LongValuesSource.fromLongField.
  2. A query cache (LRUQueryCache) stores a query's matching documents per segment, keyed on the query and the segment's core data. Before it reuses an entry it asks the query's Weight isCacheable(segment). A Weight that reads doc values must say no once those doc values were updated in place.
  3. IndexWriter#updateNumericDocValue changes a doc-values field without rewriting the segment. The reopened segment keeps its cache key (it does in the repro), so, for the same query, that isCacheable answer is the safeguard against serving old matches.

The finding, step by step

#
  1. Index one document with numeric doc values x = 1 and min = 1. Count new CoveringQuery(List.of(NumericDocValuesField.newSlowExactQuery("x", 1)), LongValuesSource.fromLongField("min")) ("at least min of these clauses") through a query cache: 1.
  2. Change x to 2 in place with updateNumericDocValue and reopen the reader. You expect 0: the clause no longer matches, and an uncached search on the new reader returns 0.
  3. Instead the cached count is still 1. Before reusing the cached result, the cache asks the query whether it may (isCacheable). CoveringQuery checks only its min field, which did not change, and never asks the x clause, which would say no. The update kept the segment's cache key, so the old entry is served.
  4. It also works the other way: a document updated to x = 1 is missing (0 instead of 1). It lasts until the old segment core is closed, the entry is evicted or the cache is cleared. On released versions the default IndexSearcher cache is enough once a segment has at least 10,000 documents and the query has been repeated (10.6.0, one 12,000-document segment, 10 counts: 1 instead of 0); main has no default cache.

Who is affected

#

Applications that build the sandbox CoveringQuery with a per-document minimum around a doc-values clause, update that field in place, and keep a query cache across reopens: the default IndexSearcher cache on 7.2.0-10.6.0, an installed one on main. Rare: nothing in Lucene builds such a query, and its tests use term and phrase clauses only.

Mechanism, terms and numbers513 words

CoveringQuery(Collection<Query> queries, LongValuesSource minimumNumberMatch) (sandbox, public constructor, @lucene.experimental) matches a document when at least N of its clauses match, N read per document. Its Weight builds every segment's result from all clause Weights (scorerSupplier, CoveringQuery.java:238-253 on main f794ff5a505c), but its isCacheable asks only the minimum (return minimumNumberMatch.isCacheable(ctx);, :255-258). LRUQueryCache trusts Weight#isCacheable and keys entries on the query plus the segment's core cache key, which an in-place doc-values update leaves unchanged. So when a clause reads a doc-values field that is updated in place, the entry cached before the update keeps being served after the reopen: a count of 1 instead of 0 in the one-document repro, a document that starts matching is missing in the other direction, and 1 instead of 0 with a plain IndexSearcher on 10.6.0 (12,000 documents, no cache code). The clause's own Weight, and a BooleanQuery over it, correctly say "not cacheable". Introduced by LUCENE-8042 (276e317e942, 7.2.0), which replaced a never-cacheable "TODO delegate to LongValuesSource?" with the minimum-only check. The fix ANDs every clause Weight's answer in, as BooleanWeight does.

Terms

#
  • CoveringQuery: "A Query that allows to have a configurable number or required matches per document" (CoveringQuery.java:46), @lucene.experimental (:49), public constructor taking any Collection<Query> and a LongValuesSource (:69). A constant minimum is rewritten to a BooleanQuery with minimumNumberShouldMatch (:128-142); a per-document minimum goes through CoveringWeight.
  • Query cache: LRUQueryCache checks the top Weight's isCacheable(leaf) (LRUQueryCache.java:816 for scorers, :903 for count) and then looks the entry up by query and the segment's core cache helper (:827-834, :914-921).
  • In-place doc-values update: IndexWriter#updateNumericDocValue, updateBinaryDocValue and updateDocValues change doc-values fields without rewriting the segment. "Two readers that have the same data but different sets of deleted documents or doc values updates may be considered equal" (LeafReader.java:66-68); in the repro the reopened segment keeps its core key.

The bug

#
  1. createWeight builds one Weight per clause (CoveringQuery.java:166-172); scorerSupplier combines all of them with the per-document minimum (:238-253), so the per-segment result depends on every clause.
  2. isCacheable returns minimumNumberMatch.isCacheable(ctx) only (:255-258). For fromLongField("min") that is DocValues.isCacheable(ctx, "min") (LongValuesSource.java:269-271): true, min was never updated.
  3. The clause newSlowExactQuery("x", 1) is a SortedNumericDocValuesRangeQuery whose Weight returns DocValues.isCacheable(ctx, "x") (SortedNumericDocValuesRangeQuery.java:119-121): false once x has a doc-values generation (DocValues.java:339-346). Nobody asks it.
  4. The cache sees "cacheable", finds the entry stored before the update under the same core key, and returns its count.

The numbers

#

One document, x = 1, min = 1, an LRUQueryCache that caches every query: count 1; after updateNumericDocValue(id 0, x, 2) and openIfChanged the cached count is still 1, uncached 0. The other way (x = 2 updated to 1): cached 0, uncached 1. On the reopened segment the clause's Weight says not cacheable, the CoveringQuery's Weight says cacheable. With the 10.6.0 defaults (plain new IndexSearcher, 12,000 documents in one segment, the query counted 10 times): 1 instead of 0.

Exposure and likelihood284 words
  • Who. The "at least min of these clauses" use with a per-document minimum (for example LongValuesSource.fromLongField) and a clause that reads a doc-values field (NumericDocValuesField.newSlowExactQuery, newSlowRangeQuery or any other doc-values query), where that field is updated in place (updateNumericDocValue, updateBinaryDocValue, updateDocValues). Any other clause whose Weight reports isCacheable false is ignored the same way.
  • Both directions, no error. Documents that stopped matching are returned, documents that started matching are missing, until the old segment core is closed (when no reader holds it any more; closing only the old reader is not enough while the reopened one shares the core), the entry is evicted or the cache is cleared (LRUQueryCache.java:1133-1136, :442-447).
  • 7.2.0 to 10.6.0: the default configuration. IndexSearcher has a default LRUQueryCache with UsageTrackingQueryCachingPolicy (7.2.0 IndexSearcher.java:118-124); that cache skips segments under 10,000 documents or not above half the average segment size, and the policy caches a query like this one after 5 uses (10.6.0 LRUQueryCache.java:175-177, :180-198; UsageTrackingQueryCachingPolicy.java:122-137). With one force-merged 12,000-document segment and the query counted 10 times, a plain new IndexSearcher(reader) on 10.6.0 counts 1 after the update where an uncached searcher counts 0.
  • main: opt-in. No default cache since #14187 (IndexSearcher.java:84, MIGRATE.md "Query caching is now disabled by default"; unreleased), so the same program is correct on main; an installed cache reproduces it.
  • Not affected. A constant minimum (rewritten to a BooleanQuery since 9.1.0, LUCENE-10367); clauses that read only postings; Weight#matches and IndexSearcher#explain, which do not use the cache (LRUQueryCache.java:788-790; IndexSearcher.java:941-944, :979-980).
  • Likelihood: rare. In Lucene only TestCoveringQuery builds the query, with term and phrase clauses; no report of it was found.

Why it looks unintended

#
  • The cache contract says doc-values readers must be uncacheable once those fields are updated (SegmentCacheable.java:30-32); a core test: "all composites referring to it should be uncacheable".
  • BooleanWeight and DisjunctionMaxQuery have asked every clause since cacheability was added (LUCENE-8017); a week later this line's author fixed the same omission in FunctionScoreQuery.
  • Nothing restricts the clauses: the constructor takes any Collection<Query>.
The full argument247 words
  • Contract. SegmentCacheable.java:30-32: "Objects that depend on doc values should return DocValues#isCacheable(LeafReaderContext, String...), which will check to see if the doc values fields have been updated. Updated doc values fields are not suitable for caching." Weight implements SegmentCacheable. QueryCache.java:28-30: the caching wrapper "will only be equivalent if scores are not needed"; the repro only counts.
  • Upstream test. TestSegmentCacheables.java:84: "after field3 is updated, all composites referring to it should be uncacheable".
  • Core composites. BooleanWeight.java:273-286 (the loop at :281-284) and DisjunctionMaxQuery.java:200-212 (:208-210) return false as soon as one clause is not cacheable; a BooleanQuery over the same clause through the same cache is correct.
  • History. LUCENE-8017 (a886a001a4c, 2017-11-03) added per-Weight cacheability: it already made BooleanWeight and DisjunctionMaxQuery combine every clause's answer (getCacheHelper(context, weights) returns null, not cacheable, unless every clause Weight returns the same helper) and made this Weight never cacheable: return null; // TODO delegate to LongValuesSource?. LUCENE-8042 (276e317e942) moved the composites' rule over to isCacheable (an AND over the clauses) but resolved CoveringQuery's TODO with the minimum alone; neither #9065 nor #9090 mentions CoveringQuery. In 2a4dd499bbd (LUCENE-7736, committed 2017-11-15) the same author changed FunctionScoreQuery from valueSource.isCacheable(ctx) to inner.isCacheable(ctx) && valueSource.isCacheable(ctx).
  • A committer's rule. David Smiley (@dsmiley) on #8398 (LUCENE-7344, 2020-12-22), about Weight#isCacheable: "This method must return false if there are any DocValue dependent clauses in the Query."
  • No javadoc, CHANGES or MIGRATE entry, and no test, says CoveringQuery may ignore its clauses' cacheability.
The devil's-advocate check96 words

The strongest case for "intended": CoveringQuery is a sandbox, @lucene.experimental query whose javadoc says it is "typically useful" for query terms; Lucene's own tests use only term and phrase clauses; the old TODO suggests the author saw the minimum as the only reader-dependent input; and main has no default cache. It fails because "experimental" allows API changes, not wrong answers; the constructor accepts any query and "typically" is not a restriction; the SegmentCacheable contract is explicit and every core composite follows it; and on 10.6.0 a plain new IndexSearcher(reader) returns the stale count with no configuration.

Suggested fix

#

Recommended Ask the minimum and every clause Weight (validated)

In CoveringQuery's Weight, also ask every clause: return false if the minimum or any clause Weight is not cacheable (the BooleanWeight rule, one method). The test passes and the whole lucene/sandbox module passes, with assertions on and off.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  if (minimumNumberMatch.isCacheable(ctx) == false) {
    return false;
  }
  for (Weight w : weights) {
    if (w.isCacheable(ctx) == false) {
      return false;
    }
  }
  return true;
}

Ask the minimum and every clause Weight (validated) (recommended)

#

A one-method change in CoveringQuery.CoveringWeight (1 file, +9/-1), the rule BooleanWeight and DisjunctionMaxQuery already follow.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  if (minimumNumberMatch.isCacheable(ctx) == false) {
    return false;
  }
  for (Weight w : weights) {
    if (w.isCacheable(ctx) == false) {
      return false;
    }
  }
  return true;
}

Trade-offs

  • On a segment where a clause's field was updated in place, the query is no longer cached until that segment is merged away; a BooleanQuery over the same clause is already treated that way, so no correct result is lost.
  • Caching is also lost when a clause is not cacheable for another reason (for example a BooleanQuery clause with more than 16 clauses): correct, but a change in what gets cached.
  • It does not copy BooleanWeight's 16-clause cap (BooleanWeight.java:274-280); that cap is a cache-policy choice, not correctness, but a reviewer may ask for it (next option).
  • One isCacheable call per clause per cache check.

What the checks validated

  • Scratch worktree of f794ff5a505c, gradle: the test fails on the stock tree and passes with the fix, with assertions on and off; TestCoveringQuery with -Ptests.nightly=true (5 tests, its 2 nightly random tests included) passes on the stock tree and with the fix; the whole lucene/sandbox module (37 suites with the new test, 426 tests, 0 failures, 72 skipped by the framework) passes with assertions on and off; :lucene:sandbox:check -x test (format, ecjLint, forbiddenApis) passes.
  • Standalone runner with the fixed CoveringQuery.java compiled ahead of the jars (a shadow class, not a rebuilt jar): the test passes on main (-ea, -da); on the 10.6.0 release jars the default-searcher program counts 0, as an uncached search does (a shadow-class run, not a patched 10.6.0 build).
  • Not run: a benchmark.

Downstream note

#

An application that hides documents through a doc-values clause inside this query keeps showing them after the field changes, and misses newly visible ones, until the stale cache entry goes.

How it was found

#

Semi-formal: a review of isCacheable overrides against the SegmentCacheable contract flagged it, and a bounded-exhaustive model-based harness that compares cached and uncached search after every step of every sequence of up to 3 index operations confirmed it. It was then reduced to one public-API JUnit test.

The method in full183 words

Method: semi-formal.

  • Contract check. Every isCacheable override was read against SegmentCacheable (a Weight whose result depends on doc values must say not cacheable once they are updated). CoveringWeight answers from its minimum source alone although its result depends on every clause; executed public-API probes showed the stale count.
  • Model-based harness. A bounded-exhaustive, every-step harness ran every operation sequence of length up to 3 over 13 operation types (adds, deletes, soft deletes, three kinds of in-place doc-values update, reopens, merges, four kinds of cache-filling search and closing the old reader), and after every step compared each query's cached result with the uncached one: 2,379 sequences and 317,757 cached-versus-uncached checks per arm. On the stock jars the checks of a CoveringQuery over a doc-values clause, alone and inside a BooleanQuery filter, failed in 47 sequences each, the shortest being [in-place numeric update, reopen]; with the fix both were clean.
  • JUnit. The shortest sequence was reduced to a two-document public-API JUnit test and checked by independent reproducers, cross-model reviews and an adjudication (Independent checks); the one-document test of the repro section was cut from it later.

History

#

Introduced in 7.2.0 by LUCENE-8042 (276e317e942, 2017), which replaced a never-cacheable "TODO delegate to LongValuesSource?" with a minimum-only answer. Every executed release from 7.2.0 to 10.6.0 and main is stale; 7.1.0 is stale for an older, general reason.

Versions tested6 rows

Introduced by 276e317e942 on master, "LUCENE-8042: Add SegmentCachable interface" (Alan Woodward, @romseygeek; authored 2017-11-07, committed 2017-11-10; JIRA patch workflow, migrated as #9090), in 7.2.0 through the branch_7x commit 6e4f9a62e7c. It replaced LUCENE-8017's never-cacheable getCacheHelper (return null; // TODO delegate to LongValuesSource?, a886a001a4c, 2017-11-03, never released) with minimumNumberMatch.isCacheable(ctx). git log -L of the method shows only these two commits; the file's last upstream commit is d0d2aa274fb5 (2024-06-06), and upstream main e0a3a951e7ef (2026-11-09) still has the line.

7.1.0 also returns a stale count, but for an older, general reason: the cache then could not see doc-values updates for any query, so a BooleanQuery over the same clause is stale too; on 7.2.0 that control is correct. CoveringQuery itself dates from 7.1.0 (LUCENE-7621). A constant minimum was affected from 7.2.0 to 9.0.0 by reading and is rewritten to a BooleanQuery since 9.1.0 (LUCENE-10367). Releases between the executed ones were not run; the method is unchanged in between.

Sandbox CoveringQuery's Weight#isCacheable asks only its minimumNumberMatch source and ignores its sub-weights, so a query cache keeps serving hits computed before an in-place doc-values update of a field one of its clauses reads (since 7.2.0)
Area
sandbox / search: CoveringQuery (CoveringWeight#isCacheable) and the query cache
Priority
Low, rank 372: After an in-place doc-values update, a query cache keeps serving the sandbox CoveringQuery's hits from before the update (extra and missing documents, no error) in every release since 7.2.0, where the default searcher cache is enough, and on main with an installed cache. It is Low because it needs a hand-built CoveringQuery with a per-document minimum over a doc-values clause, in-place updates of that field and the same query repeated across reopens, a combination with no known user.
Impact class
silent wrong results
Impact note
Applications that build the sandbox (@lucene.experimental) CoveringQuery with a per-document minimum (a LongValuesSource such as fromLongField; a constant minimum is rewritten to a BooleanQuery and is not affected) over a clause that reads a doc-values field, update that field in place (IndexWriter#updateNumericDocValue, updateBinaryDocValue or updateDocValues) and keep a query cache across reopens get the per-segment hits from before the update, with no error: a document that stopped matching is still returned and one that started matching is missing, for as long as the entry stays cached (its key is the segment core, which an in-place update does not change); any other clause whose weight reports isCacheable false is ignored the same way; on the released versions the default IndexSearcher query cache is enough (zero-configuration witness executed on 10.6.0 with a 12,000-document segment and the query repeated), on main only an application-installed cache (main has no default query cache); ordinary scale.
Summary
You build new CoveringQuery(List.of(NumericDocValuesField.newSlowExactQuery("x", 1)), LongValuesSource.fromLongField("min")), count it through a query cache, then change x for one document in place with IndexWriter#updateNumericDocValue and reopen the reader. You expect the reopened searcher to see the new value, because a query whose result depends on updated doc values must report itself not cacheable (SegmentCacheable), and both the clause's own weight and a BooleanQuery over the same clause do. Instead CoveringWeight#isCacheable asks only the minimumNumberMatch source, the segment keeps its core cache key, and the cache keeps serving the result from before the update (count 1 instead of 0 in the one-document repro; in the opposite direction a document that starts matching is missing).
