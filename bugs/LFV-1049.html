An index-sort range query on an int-sorted field silently misses or adds documents when a bound is Long.MIN_VALUE, Long.MAX_VALUE or any other value outside the int range

On an index sorted by an int field, IndexSortSortedNumericDocValuesRangeQuery cuts its long bounds to int, so "f <= 10" written as [Long.MIN_VALUE, 10] is searched as [0, 10] and silently returns 1 of the 2 matching documents. Every core release since 9.5.0 has it, 10.6.0 included.

The finding in 30 seconds

#

The query takes long bounds, but on an int sort it narrows them with a plain (int) cast before its binary search: setTopValue((int) topValue) on the doc-values path, IntPoint.pack((int) bound) on the 4-byte points path. A bound outside the int range keeps only its low 32 bits, so the search returns the wrong doc-ID range.

Background: the index-sort range shortcut

#
  1. An index can be sorted by a field (IndexWriterConfig.setIndexSort). Each segment then stores its documents in that field's order, so the documents that match a range on the field sit next to each other.
  2. IndexSortSortedNumericDocValuesRangeQuery uses this: it binary-searches the first and the last matching document and returns the doc-ID range between them, instead of checking every document. When the shortcut does not apply, it runs the fallback query you pass in, which must match the same documents.
  3. Its bounds are inclusive longs. The doc-values range queries write an open end as Long.MIN_VALUE or Long.MAX_VALUE, and this class's own rewrite() does the same.

The finding, step by step

#
  1. Sort the index by new SortField("f", SortField.Type.INT) and add three documents whose doc value f is -5, 3 and 20.
  2. Ask for "f <= 10": new IndexSortSortedNumericDocValuesRangeQuery("f", Long.MIN_VALUE, 10, fallback), writing the open lower end as Long.MIN_VALUE, the way the doc-values range queries document it. You expect 2 hits, -5 and 3, the same as the fallback NumericDocValuesField.newSlowRangeQuery("f", Long.MIN_VALUE, 10).
  3. You get 1 hit, and count() says 1: the document with -5 is missing. No error.
  4. Why: the query binary-searches the sorted doc values, and for an int sort it hands each bound to the comparator as (int) bound. (int) Long.MIN_VALUE is 0, so it searches 0 <= f <= 10. (int) Long.MAX_VALUE is -1, so "f >= 0" written as [0, Long.MAX_VALUE] finds nothing (0 instead of 2).
  5. An IntField (4-byte points) takes the same cast on its points path: the same wrong counts, extra hits for some bounds, or an IllegalArgumentException. A bound inside the int range is not changed by the cast.

Who is affected

#

Applications that sort the index by an int field (SortField.Type.INT, or SortedNumericSortField with Type.INT on an IntField) and build this query themselves with a bound outside the int range, most naturally Long.MIN_VALUE or Long.MAX_VALUE as an open end. Default codec, three documents suffice. IntField.newRangeQuery, LONG sorts in the setups SortField.Type.LONG allows, and in-range bounds are not affected.

Mechanism, terms and numbers687 words

IndexSortSortedNumericDocValuesRangeQuery takes long bounds and, when the index is sorted by the queried field, binary-searches the doc-ID range of the matches instead of running its fallback query. When that sort is SortField.Type.INT (or a SortedNumericSortField with Type.INT), the doc-values binary search narrows the bound with fieldComparator.setTopValue((int) topValue), and when the field has 4-byte points (IntField) the points binary search packs IntPoint.pack((int) lowerValue) / IntPoint.pack((int) upperValue) (lines 633 and 461-462 on main 645d4fe14a20). A bound outside the int range keeps only its low 32 bits: (int) Long.MIN_VALUE is 0 and (int) Long.MAX_VALUE is -1, the documented open ends of the doc-values range queries this class wraps. The search then covers the wrong doc-ID range: [Long.MIN_VALUE, 10] over the values -5, 3 and 20 returns 1 document instead of 2, [0, Long.MAX_VALUE] returns 0 instead of 2, count() agrees with the wrong result, other bounds add documents, and on the points path some bounds throw IllegalArgumentException. The class javadoc requires the same documents as the fallback, and no documented int-range precondition was found. Every core release from 9.5.0 to 10.6.0 and main are affected; matching nothing when the range lies outside the int range and clamping the bounds otherwise fixes it.

The bug

#

All lines are IndexSortSortedNumericDocValuesRangeQuery.java on main 645d4fe14a20.

  1. Entry. scorerSupplier (:160-168, through getDocIdSetIteratorOrNull, :517-545) tries the points binary search first (getDocIdSetIteratorOrNullFromBkd, :430-515), then, for an INT or LONG primary sort on the field, the doc-values binary search (getDocIdSetIterator, :559-619). Only when neither applies does the fallback run. Weight#count (:177-226) uses the points search only when every document has a point (:193), and the doc-values search only when that holds or the sort's missing value lies outside the range (:214-215); otherwise it returns the fallback's count (:225). In the minimal test neither holds, and the fallback's count is -1 there (no doc-values skip index), so IndexSearcher.count counts the documents the query's scorer returns, which come from the wrong range.
  2. Doc-values path. getDocIdSetIterator binary-searches the first document with value >= lower (:569-583) and the first with value > upper (:585-602). Each probe compares against a comparator from loadComparator (:626-646), which for Type.INT does fieldComparator.setTopValue((int) topValue) (:632-633): the int comparator needs an Integer, and the cast keeps the low 32 bits of the long.
  3. Points path. For 4-byte points, :460-462 pack IntPoint.pack((int) lowerValue) and IntPoint.pack((int) upperValue) and then binary-search the point tree (:479-504). A wrapped upper end below the wrapped lower end can make the start doc greater than the end doc, and DocIdSetIterator.range then throws "minDoc must be < maxDoc" (DocIdSetIterator.java:47-50).
  4. The repro's numbers. In index-sort order the documents are -5, 3, 20. (int) Long.MIN_VALUE = 0, so the first document with value >= 0 is the one with 3, and the first with value > 10 is the one with 20: the returned range holds one document.

Which bounds

#

rewrite() turns [Long.MIN_VALUE, Long.MAX_VALUE] into a FieldExistsQuery (:131-133), so only one open end at a time reaches the binary search. A bound inside the int range survives the cast unchanged. A bounded-exhaustive check (14 bound values, 8 inside and 6 outside the int range, both long extremes included; values Integer.MIN_VALUE, -5, 0, 3, Integer.MAX_VALUE; forward and reverse sort; with and without a document missing the field; three missing values) against a brute-force count found, on the three supported INT-sort setups (NumericDocValuesField, SortedNumericDocValuesField, IntField), 2,382 wrong results in 7,056 checks, every one with a bound outside the int range (0 wrong of the 2,304 in-range checks). search() and count() are wrong together, or throw together (138 cases, all on the points path). Examples on the IntField path: [Long.MIN_VALUE, -2147483649] should match nothing and returns 3 documents; [Long.MIN_VALUE, -6] throws. With the fix, 0 of all 14,112 checks are wrong. (The run also covers IntField under a LONG sort, 798 more wrong results; SortField.Type.LONG requires LongPoint, so those are left out of the claim.)

Exposure and likelihood226 words
  • Who is hit. Applications that (a) sort the index by an int field, either SortField.Type.INT on a NumericDocValuesField or SortedNumericSortField with Type.INT on an IntField, and (b) construct IndexSortSortedNumericDocValuesRangeQuery themselves with a long bound outside the int range. The natural case is an open end written as Long.MIN_VALUE / Long.MAX_VALUE, the convention of the long-typed doc-values range factories this query wraps.
  • Default vs opt-in. The index sort is opt-in configuration, and the query is an expert @lucene.experimental class built by hand. Within that: default codec, no scale, assertions on or off, single thread.
  • What is wrong. Silently missed and extra documents, and a wrong count() / totalHits; on the points path some bounds throw IllegalArgumentException. Deterministic for a given index and bound.
  • Not affected. IntField.newRangeQuery (it passes int bounds), any LONG sort in a setup that SortField.Type.LONG allows (doc values only, or LongPoint / LongField), and bounds inside the int range (the cast leaves them unchanged). An IntField under a LONG sort, a setup SortField.Type.LONG rules out, does take the 4-byte points cast. The INTEGER field mappers of two major downstream search servers pass int bounds too.
  • How likely: rare. It needs the hand-built query; no matching public report was found in the recorded searches (2026-10-29, re-checked 2026-10-30); the code shipped in 9.2.0 (sandbox, the doc-values cast) and 9.5.0 (core).

Why it looks unintended

#
  • The javadoc lists SortField.Type.INT as supported and says the fallback "should produce the same documents": here the fallback finds 2, the query 1.
  • The constructor takes long bounds unchecked; its own rewrite() and the doc-values range factories use Long.MIN_VALUE / Long.MAX_VALUE as open ends.
  • No documented int-range precondition was found; the upstream INT-sort test only uses the Integer extremes.
The full argument281 words
  • Contracts. The class javadoc (IndexSortSortedNumericDocValuesRangeQuery.java:43-58): the optimization applies when "The sort field is of type SortField.Type.LONG or SortField.Type.INT", and "This fallback must be an equivalent range query -- it should produce the same documents and give constant scores". Its example builds the query directly from long bounds (:59-65). The constructor takes long bounds and checks nothing (:81-85); the superclass is "A Query over a range of long values" (NumericDocValuesRangeQuery.java:22). rewrite() treats Long.MIN_VALUE / Long.MAX_VALUE as open ends (:131-133) and says "This query matches the same documents as its fallback" (:136).
  • The fallback's convention. NumericDocValuesField.newSlowRangeQuery, the natural fallback for a doc-values-only int field: "You can have half-open ranges ... by setting lowerValue = Long.MIN_VALUE or upperValue = Long.MAX_VALUE" (NumericDocValuesField.java:94-95; the same in SortedNumericDocValuesField.java:90-91).
  • A legal setup. SortField.Type.INT: "Fields must either be not indexed, or indexed with IntPoint" (SortField.java:76-80); the repro's field has doc values only.
  • No precondition found. No int-range precondition was found in the javadocs, CHANGES or MIGRATE entries, tests or review threads that were read (#11502 / #749, #687, #12078, #14732).
  • History. The doc-values cast came with LUCENE-10466 (#11502 / PR #749), whose stated expectation was that the query "should not fail with class cast but correctly convert the numeric values". Its review discussed which sort types to support, not bounds; #687 (the points-path cast) did not discuss bounds either.
  • Tests. The upstream INT-sort test testSameHitsAsPointRangeQueryIntSort uses Integer.MIN_VALUE / Integer.MAX_VALUE as its open ends (TestIndexSortSortedNumericDocValuesRangeQuery.java:106-150), while the LONG tests use the long extremes as open ends (:93-95, :780-782): the case is untested, not asserted.
The devil's-advocate check160 words

The strongest case for "caller error": with an INT sort the values are ints (SortField.Type.INT: "Sort values are Integer"), IntField.newRangeQuery only ever passes int bounds, the upstream INT tests use Integer sentinels, the class is @lucene.experimental, a maintainer wrote in 2022 that it "should no longer be exposed to users" (jpountz on #749, 2022-03-30), and its deprecation was floated on #16699 (romseygeek, 2026-09-22).

Why it fails: the class is public in core, its javadoc shows users constructing it from long bounds, the constructor accepts any long, no documented int-range precondition was found, and the class's own rewrite() and its natural fallback use the long extremes as open ends. Narrow use and a possible future deprecation limit the impact, not the correctness: today the query silently returns other documents than the fallback the javadoc says it must equal. The intended-behaviour reviewer from another model family rated the argument moderate, the devil's-advocate check moderate-to-weak; both called the bug real.

Suggested fix

#

Recommended Match nothing outside the int range, else clamp

On the INT doc-values path and the 4-byte points path, match nothing when the whole range lies outside the int range, and otherwise clamp each bound to [Integer.MIN_VALUE, Integer.MAX_VALUE] before the cast (+17/-3, one file). The test then passes, and so do the 161 tests of the closest suites.

// 4-byte points path, and the same early return for Type.INT in getDocIdSetIterator:
if (lowerValue > Integer.MAX_VALUE || upperValue < Integer.MIN_VALUE) {
  return IteratorAndCount.empty(); // no int value can be in the range
}
queryLowerPoint = IntPoint.pack(clampToInt(lowerValue)).bytes;
queryUpperPoint = IntPoint.pack(clampToInt(upperValue)).bytes;
// loadComparator:
fieldComparator.setTopValue(clampToInt(topValue));

private static int clampToInt(long value) {
  return (int) Math.max(Integer.MIN_VALUE, Math.min(Integer.MAX_VALUE, value));
}

Match nothing outside the int range, else clamp (validated by the checks) (recommended)

#

IndexSortSortedNumericDocValuesRangeQuery.java, +17/-3: an early IteratorAndCount.empty() on the 4-byte points path and, for Type.INT, at the top of getDocIdSetIterator; a clampToInt helper in place of the three casts.

// 4-byte points path, and the same early return for Type.INT in getDocIdSetIterator:
if (lowerValue > Integer.MAX_VALUE || upperValue < Integer.MIN_VALUE) {
  return IteratorAndCount.empty(); // no int value can be in the range
}
queryLowerPoint = IntPoint.pack(clampToInt(lowerValue)).bytes;
queryUpperPoint = IntPoint.pack(clampToInt(upperValue)).bytes;
// loadComparator:
fieldComparator.setTopValue(clampToInt(topValue));

private static int clampToInt(long value) {
  return (int) Math.max(Integer.MIN_VALUE, Math.min(Integer.MAX_VALUE, value));
}

Trade-offs

  • It assumes the field's values are ints, which is what an INT sort sorts (SortField.Type.INT: "Sort values are Integer"; the sort's missing value is an Integer). For int values, clamping a bound to the int range does not change which documents match, and a range that misses the int range entirely matches none. The assumption is not enforced: NumericDocValuesField accepts any long, and the fix was not tested with stored values outside the int range under an INT sort (the setup of the separate LFV-779, where the sort compares only the low 32 bits). Ask the maintainers to confirm it, or pick the fallback option.
  • Keeps the index-sort shortcut for open-ended bounds; a few comparisons per segment (the range check once, and one clamp each time the binary search loads a comparator, O(log maxDoc) times), nothing per document.

Clamp only

#

Replace the three casts with a clamp and nothing else. An independent reproducer's shadow class did exactly this and its test passed.

Trade-offs

Incomplete: a range entirely above the int range, such as [2^31, 2^32], clamps to [Integer.MAX_VALUE, Integer.MAX_VALUE] and matches the document whose value is exactly Integer.MAX_VALUE; the same at the low end. Executed with a clamp-only shadow on 645d4fe14a20, on the IntField and the doc-values path: [2^31, 2^32] returns the Integer.MAX_VALUE document, [-2^32, -2^31-1] and [Long.MIN_VALUE, -2147483649] the Integer.MIN_VALUE document, instead of none; the recommended fix returns none.

Run the fallback when a bound does not fit in an int (not built)

#

Return null from the two binary-search helpers for an INT sort or 4-byte points when a bound is outside the int range, so the equivalent fallback runs.

Trade-offs

Correct by the class's own contract and the smallest change in behaviour: for a bound outside the int range the result is the fallback's, whatever the stored values (no int-value assumption). But open-ended long bounds, the common case, lose the shortcut.

Deprecate the class (discussed on #16699, undecided)

#

romseygeek suggested on #16699 (2026-09-22) moving the index-sort shortcut into the point and doc-values range queries and deprecating this class as redundant; HoustonPutman, the PR's author, agreed and is aiming for 11.0 (the PR's milestone is 11.0.0); the PR is labelled Stale and nothing has landed.

Trade-offs

Does not fix 9.x and 10.x, where the class stays public; can be combined with the first option.

Downstream note

#

An application that uses such a range as a restriction filter, with a bound outside the int range, can let through documents outside the range.

How it was found

#

Code reading while writing a Z3 model of how the point and doc-values range queries handle their bounds: the model's obligations were satisfiable for both casts and unsatisfiable once the bounds are restricted to the int range. A second hunt found the same root through count(); a one-method JUnit and a bounded-exhaustive check confirmed it.

The method in full115 words

Method: semi-formal. The hunt's hunt on point and doc-values query equivalence (2026-10-25) raised it from code reading while writing a Z3 translation-validation model of the bound handling; the model's obligations were satisfiable for both casts and unsatisfiable once the bounds are restricted to the int range, and a bounded-exhaustive detector on the stock jar and replayed witnesses confirmed it.

  • A second hunt, on count() and totalHits shortcuts (2026-10-25), found the same root while modelling the count shortcuts with a bit-precise Z3 check; both findings are collapsed into this one.
  • An adjudication unit reduced the earliest finder's five tests to the one-method test, ran the 14,112-check bounded-exhaustive differential against a brute-force count, and wrote the fix.

LFV-1049, snapshot of 2026-11-04

Registry title
IndexSortSortedNumericDocValuesRangeQuery casts its long bounds to int on an INT index sort, so Long.MIN_VALUE / Long.MAX_VALUE open ends (or any bound outside the int range) silently return wrong hits and counts
Area
search / IndexSortSortedNumericDocValuesRangeQuery (index-sort range shortcut: INT sort comparator path and 4-byte points path)
Priority
Medium, rank 82: Both give deterministic silent wrong hits and counts in a rare index-sort setup, and the natural Long.MIN_VALUE/Long.MAX_VALUE open-end idiom makes this more than the type mistake behind LFV-779, but it needs the expert query built by hand.
Impact class
silent wrong results
Impact note
Hits applications that sort the index by an int field (SortField.Type.INT, or SortedNumericSortField with Type.INT over an IntField) and build IndexSortSortedNumericDocValuesRangeQuery directly with a bound outside the int range, most naturally Long.MIN_VALUE or Long.MAX_VALUE as an open end: search() and count() silently miss or add documents (on the 4-byte points path some bounds throw IllegalArgumentException 'minDoc must be < maxDoc' instead); default codec, no scale, -ea or -da; IntField.newRangeQuery passes int bounds and is not affected, nor are LONG sorts or bounds inside the int range.
Summary
You sort the index by SortField("f", SortField.Type.INT), index the values -5, 3 and 20 in a NumericDocValuesField, and search new IndexSortSortedNumericDocValuesRangeQuery("f", Long.MIN_VALUE, 10, fallback), where the fallback is NumericDocValuesField.newSlowRangeQuery("f", Long.MIN_VALUE, 10) (f <= 10, written with the open-end convention that the fallback documents). You expect the 2 documents the fallback returns, as the class javadoc requires. You get 1: the doc-values binary search narrows the bound with (int) Long.MIN_VALUE, which is 0, so -5 is missed; (int) Long.MAX_VALUE is -1 in the same way, and the 4-byte points path has the same cast.
