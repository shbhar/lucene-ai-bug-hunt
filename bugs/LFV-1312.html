DocBaseBitSetIterator over an empty bit set with a non-zero docBase throws instead of returning NO_MORE_DOCS

A DocBaseBitSetIterator over an empty bit set should simply be empty, but with a non-zero docBase its first nextDoc() throws ArrayIndexOutOfBoundsException instead of returning NO_MORE_DOCS. Every release since 9.1.0; no valid index makes Lucene build this shape, so in practice only code that constructs the iterator itself is hit.

The finding in 30 seconds

#

The iterator shifts every bit by docBase, and its "am I done?" check, target >= bits.length() + docBase, does not cover targets below docBase when the set is empty. Those targets reach nextSetBit(0) on a zero-length set, which throws.

Background in three steps

#
  1. A DocIdSetIterator walks the documents of a set in order; nextDoc() returns the next one, or NO_MORE_DOCS (2147483647) when there are none left.
  2. DocBaseBitSetIterator stores a window of documents as a FixedBitSet plus a docBase: bit i means document docBase + i. Lucene uses it for BKD (points) leaves whose doc IDs are stored as a bit set.
  3. FixedBitSet.nextSetBit(i) requires i < length() and does not check it for speed; callers check first. BitSetIterator does: it returns NO_MORE_DOCS whenever the target is past the end of its set.

The finding, step by step

#
  1. DocBaseBitSetIterator walks a FixedBitSet whose bit 0 stands for document docBase (a multiple of 64). Build one for the window starting at document 64 in which nothing matched: new DocBaseBitSetIterator(new FixedBitSet(0), 0, 64). The constructor accepts it.
  2. Call nextDoc(). You expect NO_MORE_DOCS: the set is empty, and the same call with docBase 0, or on a BitSetIterator over an empty set, returns it.
  3. advance(0) stops early only when the target is at least bits.length() + docBase = 0 + 64 = 64. Target 0 is below that, so it asks the empty set for nextSetBit(0).
  4. nextSetBit requires the index to be inside the set, and a zero-length set has none, so you get ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 (AssertionError: index=0, numBits=0 with assertions on).

Who is affected

#

Only code that builds its own DocBaseBitSetIterator over an empty window with a non-zero docBase and then iterates it, directly or through FixedBitSet.or. Lucene's only producer, the BKD bit-set leaf reader, always gets at least one word from a Lucene-written leaf, so no valid index or query is affected. The failure is a loud exception, never a wrong result.

Mechanism, terms and numbers438 words

DocBaseBitSetIterator is a DocIdSetIterator over a FixedBitSet whose bit 0 stands for document docBase, a multiple of 64. Its public constructor accepts an empty set with any such docBase, a legal compact way to represent a 64-aligned window of documents in which nothing matched. With docBase 0 the first nextDoc() returns NO_MORE_DOCS; with docBase 64 it throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 (AssertionError: index=0, numBits=0 with assertions on), because advance() returns early only when target >= bits.length() + docBase and otherwise calls bits.nextSetBit(0) on the zero-length set.

BitSetIterator, which the class javadoc says it is "like", returns NO_MORE_DOCS for an empty set. Every release since 9.1.0 is affected. Lucene's only producer of the class, the BKD bit-set leaf reader, never builds an empty set from a valid index, so no valid index or query is affected; only code that constructs the iterator itself is hit, and it fails loudly with no wrong result.

The mechanism (main 5adff78bb168)

#
  1. The constructor (DocBaseBitSetIterator.java:34-45) validates only cost >= 0 (:35) and (docBase & 63) == 0 (:38), then sets length = bits.length() + docBase (:42). For new FixedBitSet(0), which holds a long[0] (FixedBitSet.java:146-150), and docBase 64, length is 64.
  2. nextDoc() is advance(doc + 1) (:66-69); on a fresh iterator doc is -1, so it calls advance(0).
  3. advance (:71-82) returns NO_MORE_DOCS only if target >= length (:73). 0 < 64, so it calls bits.nextSetBit(Math.max(0, target - docBase)), which is nextSetBit(0) (:76). This is the fix site.
  4. FixedBitSet.nextSetBit (:351-356) calls nextSetBitInRange(0, numBits = 0) (:411-417): the assert start >= 0 && start < numBits fails (:413), or, with assertions off, bits[0] is read from the empty array (:416-417).
  5. Only the empty set can make it throw: when bits.length() > 0 and target < length, 0 <= max(0, target - docBase) < bits.length(). (If bits.length() + docBase overflows an int, length is negative and no target reaches nextSetBit at all; that separate edge is under Suggested fixes.) BitSetIterator.advance (BitSetIterator.java:93-98) has the same target >= length check, but its length is the set's own length, so an empty set always returns NO_MORE_DOCS.
  6. Other entry points: any advance(target) with target < docBase, and FixedBitSet.or(DocIdSetIterator) (FixedBitSet.java:455-460), which calls iter.nextDoc() first (a probe on main: advance(10) and new FixedBitSet(256).or(it) both throw). The or route exists since 10.2.0 (#14139); from 9.1.0 to 10.1.0 or() special-cased this class and OR-ed its words directly.
Exposure and likelihood211 words
  • Who: an application, plugin or collector that cuts the doc ID space into 64-aligned windows and wraps each window's matches in this iterator. When a window has no matches, its operation fails with an exception instead of seeing an empty iterator.
  • Not hit: valid indexes. The only in-tree producer is DocIdsWriter.readBitSetIterator (util/bkd/DocIdsWriter.java:273-285); the writer always writes at least one word (totalWordCount = bits2words(max - offsetBits + 1), :206-218, and the final writeLong, :235). The only other in-tree constructor call is a test (TestFixedBitSet.java:502). Only a corrupt or crafted points file could give the reader zero words at a non-zero offset; the reader would then build this shape and readBitSet would iterate it (:303-309). Index files are trusted, so that is corruption, not a separate trigger.
  • Effect: ArrayIndexOutOfBoundsException (or AssertionError with -ea) on the first call. No wrong result, nothing written, no index damage.
  • Near miss upstream: open #16649 proposes a new producer of this class (a MemoryAccountingBitsetCollectorManager result). For the empty result it keeps the #16452 padding (a length-1 set, docBase 0), so iterator().nextDoc() returns NO_MORE_DOCS; a producer that dropped the padding and kept the window's docBase would hit this bug.
  • Since: 9.1.0, when the class was added.

Why it looks unintended

#
  • DocIdSetIterator.nextDoc returns NO_MORE_DOCS "if there are no more docs in the set", and the constructor accepts the empty set.
  • The class says it is "like BitSetIterator", which returns NO_MORE_DOCS for an empty set, and so does this class with docBase 0.
  • FixedBitSet.nextSetBit leaves the bounds check to callers on purpose (LUCENE-3449, LUCENE-6427); this class is that caller.
The full argument226 words
  • Contract. DocIdSetIterator.nextDoc: "Advances to the next document in the set and returns the doc it is currently on, or NO_MORE_DOCS if there are no more docs in the set." (DocIdSetIterator.java:126-134).
  • The class's own word and behaviour. Javadoc: "A DocIdSetIterator like BitSetIterator but has a doc base in order to avoid storing previous 0s." (DocBaseBitSetIterator.java:23-26). The doc base is a storage offset; it should not change whether an empty set can be iterated.
  • The input is legal. The constructor validates its arguments and accepts this one. DocBaseBitSetIterator is public in an exported package (module-info.java:53) and carries no @lucene.internal tag; new FixedBitSet(0) is a legal set.
  • Where the check belongs. On LUCENE-3449 (#4523, still open) Michael McCandless argued against adding the check: "performance trumps convenience here for these low level APIs". On LUCENE-6427 (#7486) Adrien Grand suggested that callers write bitSet.length() == 0 || bitSet.nextSetBit(0) == NO_MORE_DOCS. In the review of #16452 (2026-08-12), javanna flagged new FixedBitSet(0) followed by nextSetBit(0) throwing ArrayIndexOutOfBoundsException in another class as a bug, and it was fixed.
  • History. The advance() body came with the class in LUCENE-10233 (#438) and never changed. The review did not discuss empty sets, no test covers one (the only test use, TestFixedBitSet.java:502, always gives the set a length of at least 1) and no CHANGES entry documents the throw.
The devil's-advocate check230 words

"FixedBitSet and BitSetIterator are @lucene.internal, the util package says its 'APIs ... are primarily internal and may change between releases', the class exists only for BKD leaves and its only producer never builds an empty set from a valid index; so this is not a bug. And #16452 shows the Lucene way is to pad the producer." (FixedBitSet.java:29, BitSetIterator.java:30, util/package-info.java:35.) An independent reviewer from another model family (OpenAI GPT-5.6) made the first part of this argument (the internal tags, the package doc, the BKD-only producer and no valid index building the shape) its reason for "not real", after reproducing the failure with its own test (docBase 128), agreeing on the root cause and checking that the fix fixes it. The #16452 part is added here to give the argument its strongest form.

Why it fails: the tags limit API stability, not correctness, and DocBaseBitSetIterator itself has no tag (its parameter type FixedBitSet has one, so this is not a strong external contract either). The constructor accepts the input, and the class already handles the empty set at docBase 0. Padding each producer leaves the iterator's contract broken for the next one (#16649 has to special-case its empty result). The argument is about impact, and a maintainer may reasonably treat the fix as hardening of an internal helper, which is why the priority is Low.

Suggested fix

#

Recommended A. Return NO_MORE_DOCS when the start index is past the end of the set (validated)

In advance(), compute start = Math.max(0, target - docBase) and return NO_MORE_DOCS when start >= bits.length(), before calling nextSetBit (+5/-1). The repro passes with assertions on and off; TestFixedBitSet, TestBitSetIterator, TestDocIdsWriter, TestBKD and the lint checks pass.

if (target >= length) {
  return doc = NO_MORE_DOCS;
}
int start = Math.max(0, target - docBase);
if (start >= bits.length()) {
  return doc = NO_MORE_DOCS;
}
int next = bits.nextSetBit(start);
All options and trade-offs2 options · 400 words

Two options. A was validated with gradle in a scratch worktree of 5adff78bb168; B is by reading. Padding producers (the #16452 approach) or documenting a non-empty precondition is not a fix: the iterator's DocIdSetIterator contract would stay broken for direct callers.

A. Return NO_MORE_DOCS when the start index is past the end of the set (validated) (recommended)

#

In DocBaseBitSetIterator.advance (:71-82), +5/-1:

if (target >= length) {
  return doc = NO_MORE_DOCS;
}
int start = Math.max(0, target - docBase);
if (start >= bits.length()) {
  return doc = NO_MORE_DOCS;
}
int next = bits.nextSetBit(start);

Trade-offs

  • One more int comparison per advance()/nextDoc() on BKD bit-set leaves. For a non-empty set it is never taken (mechanism, step 5); not benchmarked.
  • The existing target >= length check stays; it also short-circuits NO_MORE_DOCS targets before the subtraction.
  • Mirrors BitSetIterator, which checks before calling nextSetBit.
  • Scope: neither fix changes a separate edge. The constructor does not check that bits.length() + docBase fits in an int (and it accepts negative multiples of 64). A set that reaches past doc ID Integer.MAX_VALUE makes length negative, and the first nextDoc() returns NO_MORE_DOCS at once, with or without fix A (a probe on main, -ea and -da: 64 bits at docBase 2147483584, and 256 bits at docBase 2147483456, both with bit 0 set). Lucene's producer sizes the set to the leaf's largest doc ID (DocIdsWriter.java:209-213), below IndexWriter.MAX_DOCS (index/IndexWriter.java:208), so it never builds such a set. It is a separate, possible follow-up.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: on stock the repro fails with assertions on and off; with fix A it passes, on and off.
  • With fix A: TestFixedBitSet 34 of 34, TestBitSetIterator 11 of 11, bkd.TestDocIdsWriter 5 of 5, bkd.TestBKD 23 of 25 (2 nightly tests skipped, none failed) and the repro: 76 tests, 0 failures.
  • checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest for lucene/core pass.
  • Not run: the full lucene/core suite.

B. Reject the shape in the constructor

#

Throw IllegalArgumentException when bits.length() == 0 && docBase != 0.

Trade-offs

No cost on the hot path, but it turns an empty window, a legal input today, into an error that every producer must special-case (as #16649 already special-cases its empty result), and stays inconsistent with docBase 0 and with BitSetIterator. By reading, not run.

Downstream note

#

Relevant downstream only to code that builds this iterator itself over windows that can be empty; such code cannot rely on an empty window returning NO_MORE_DOCS.

How it was found

#

Semi-formal: a proof-obligation audit of DocBaseBitSetIterator's contract checked that every input the constructor accepts gives an iterator honouring DocIdSetIterator.nextDoc. The empty set with a non-zero docBase passes validation but misses the end check, and a one-test JUnit repro on stock main witnessed the exception.

The method in full103 words
  • Obligation: for every FixedBitSet and docBase the constructor accepts, and every target, advance either returns a set document at or after the target or NO_MORE_DOCS, and calls nextSetBit only with an index inside the set (FixedBitSet.java:413).
  • Finding: the guard target >= length (DocBaseBitSetIterator.java:73) implies 0 <= max(0, target - docBase) < bits.length() only when the set is non-empty; for an empty set and docBase > 0, targets below docBase reach nextSetBit(0) (:76).
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Summary
You build a DocBaseBitSetIterator over an empty bit set with a non-zero doc base, for example new DocBaseBitSetIterator(new FixedBitSet(0), 0, 64), the shape you get for a 64-aligned window of documents that turned out to have no matches. You expect its first nextDoc() to return NO_MORE_DOCS, as the same class does with docBase 0 and as BitSetIterator, which its javadoc says it is 'like', does for an empty set. Instead nextDoc() throws ArrayIndexOutOfBoundsException 'Index 0 out of bounds for length 0' (AssertionError 'index=0, numBits=0' with -ea), because advance() returns early only when target >= bits.length() + docBase and otherwise calls bits.nextSetBit(0) on the zero-length set.
