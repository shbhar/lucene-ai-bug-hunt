RegExp accepts a syntax flag in match_flags next to a match flag, and negative flag words, instead of throwing IllegalArgumentException

new RegExp("a&b", NONE, INTERSECTION) throws "Illegal match flag", but new RegExp("a&b", NONE, CASE_INSENSITIVE | INTERSECTION) is accepted and parses & as intersection, because the constructor checks its flag words by value, not by bit. Negative words pass too; affected: 8.7.0 to 10.6.0, and main.

The finding in 30 seconds

#

Two flag words, two kinds of bit: syntax flags live in bits 0x01-0xff, match flags in 0x100 and up. The constructor checks each word's value; the parser reads single bits.

  1. RegExp takes two flag words: syntax flags turn on optional syntax (INTERSECTION = 0x0001 enables &; all fit in 0xff), match flags turn on match options (CASE_INSENSITIVE = 0x0200). Put a syntax flag in the match word by mistake, new RegExp("a&b", RegExp.NONE, RegExp.INTERSECTION): it throws IllegalArgumentException: Illegal match flag, as intended.
  2. Now OR a match flag into the same word: new RegExp("a&b", RegExp.NONE, RegExp.CASE_INSENSITIVE | RegExp.INTERSECTION), a match word of 0x0201 = 513. You expect the same "Illegal match flag".
  3. Instead it is accepted and the stray bit takes effect: & is parsed as intersection (kind REGEXP_INTERSECTION) although the syntax word is NONE. Without the stray bit, (NONE, CASE_INSENSITIVE), a&b is a plain string.
  4. Why: the checks compare values (match_flags > 0 && match_flags <= 0xff, syntax_flags > 0xff), but the parser tests single bits of syntax_flags | match_flags. 513 is above 0xff, so its low bit slips through. A negative word passes both tests: new RegExp("A", -1) is accepted and matches "a".

Who is affected

#

Only code that passes a hand-built flag word: a syntax constant ORed into the match word next to a match constant (RegExp, RegexpQuery), or a negative int such as -1 (also via RegexCompletionQuery). The mistake goes unnoticed and switches on optional syntax or case-insensitive matching for that caller's own pattern. Lucene's query parsers are unaffected.

Mechanism, terms and numbers602 words

RegExp(String, int syntax_flags, int match_flags) validates its two flag words: a syntax flag alone in match_flags throws "Illegal match flag" and a match flag in syntax_flags throws "Illegal syntax flag". Both checks compare value ranges (syntax_flags > ALL, match_flags > 0 && match_flags <= ALL, with ALL = 0xff), while the parser later tests single bits of the merged word flags = syntax_flags | match_flags. So a non-negative match word that also carries a match bit (value above 0xff) keeps any syntax bits below 0x100, and a negative word passes both tests. The malformed word is accepted silently instead of raising the exception the check exists for, and its stray bits take effect on the caller's own pattern: new RegExp("a&b", NONE, CASE_INSENSITIVE | INTERSECTION) parses & as intersection, and new RegExp("A", -1) matches "a".

Only callers who put a constant in the wrong word or pass a negative int are affected; Lucene's own query parsers pass RegExp.ALL and 0. It is a missing IllegalArgumentException, not wrong results for well-formed input: the caller did set the bit, only in the wrong word. Every release from 8.7.0 (LUCENE-9386, which added match_flags and both checks) through 10.6.0 and main is affected; #16968, merged on 2026-11-04, edits the same constructor but keeps both range checks. A two-line bit-mask fix makes the repro pass and keeps the automaton and RegexpQuery suites green.

The constants are grouped as syntax ( <= 0xff ) and matching ( > 0xff <= 0xffff ), and each word is documented as a "boolean 'or'" of its own kind. The class javadoc says "The productions marked [OPTIONAL] are only allowed if specified by the syntax flags passed to the RegExp constructor".

The checks and the merge

#
if (syntax_flags > ALL) throw new IllegalArgumentException("Illegal syntax flag");                 // RegExp.java:536
if (match_flags > 0 && match_flags <= ALL) throw new IllegalArgumentException("Illegal match flag"); // :540
flags = syntax_flags | match_flags;                                                                 // :543
private boolean check(int flag) { return (flags & flag) != 0; }                                     // :1224-1226

Worked example: the match word CASE_INSENSITIVE | INTERSECTION is 0x0201 = 513. 513 > 0 && 513 <= 255 is false, so nothing is thrown, flags is 0x0201 and check(INTERSECTION) (:1234) is true. The same bit alone is 1, and 1 <= 255 throws. A negative word, -1 = 0xFFFFFFFF, passes -1 > 255 (false) as a syntax word and -1 > 0 (false) as a match word, and then carries every bit.

RegexpQuery(Term, int) passes its one word as the syntax word with match word 0; RegexpQuery(Term, int, int) and the five-argument constructor pass both words unchanged. RegexCompletionQuery(Term, int flags, ...) uses flags as the syntax word only and has no match word.

Why it looks unintended

#
  • The constructor already rejects wrong-kind words, and TestRegExpParsing asserts it; yet the same syntax bit is rejected alone and accepted next to a match bit.
  • The class javadoc allows [OPTIONAL] syntax only "if specified by the syntax flags"; here & works with NONE.
  • #16968 (merged 2026-11-04) makes a removed bit "fail loudly instead of being silently ignored".
The full argument283 words
  • Existing validation and tests. TestRegExpParsing.testIllegalSyntaxFlags expects new RegExp("bogus", Integer.MAX_VALUE) to throw and testIllegalMatchFlags expects new RegExp("bogus", RegExp.ALL, 1) to throw (:816-830). A check that rejects INTERSECTION alone but accepts INTERSECTION | CASE_INSENSITIVE and then applies it has no coherent reading.
  • Class contract. [OPTIONAL] productions are "only allowed if specified by the syntax flags" (RegExp.java:341-342); each word is a "boolean 'or'" of its own kind (:531-532).
  • Original intent. In the review of LUCENE-9386 (apache/lucene-solr#1541), which added match_flags and both checks, jimczi asked: "should we ensure that the flag is not used in the syntax_flags since we merge the two internally?" (2020-06-25). An earlier revision of that PR masked the syntax word (syntax_flags & 0xff), which the author kept for back-compat; jpountz replied "I don't think we need to maintain bw compat for this" (2020-07-07), and the last revision replaced the mask with the throwing syntax_flags > ALL, which a negative word passes.
  • Current maintainers. On #16968, javanna wrote "I am not a fan of 3)" (silently ignoring the removed raw value 0x0100) and proposed to "throw a runtime error when 0x0100 is provided in the constructor"; cbuescher implemented it, and the merged javadoc (14f80c3ebe6) says the bit "stays reserved so that passing it as a raw value fails loudly instead of being silently ignored". Its new test testRemovedAsciiCaseInsensitiveRawFlag expects the bad bit to be rejected also next to a valid one (0x0100 | CASE_INSENSITIVE). The discussion was about that one removed bit only.
  • Precedent. #12251 ("RegExp.parseRepeatExp is not fully checked", type:bug) was addressed by #12277 (merged 2023-11-02; #12251 itself is still open), which added missing input validation to RegExp.
The devil's-advocate check245 words

A reviewer from another model family (OpenAI GPT-5.6, refute lens, executed; every fact reproduced, root cause and fix agreed) judged it not a bug, with high confidence: the javadoc defines each word as an "or" of its own kind, and the constant groups are commented as value ranges (( <= 0xff ), ( > 0xff <= 0xffff )), so a mixed or negative word is outside the documented domain; @exception promises IllegalArgumentException only for parse errors; RegExp is @lucene.experimental (RegExp.java:352); the tests lock only two invalid values; so the mask change is hardening, and rejecting words that are accepted today is a compatibility change for a low-impact caller mistake.

Why it does not settle the question: the constructor already rejects wrong-kind words, so this validation is part of its behaviour, and the current check rejects a bit alone but accepts and applies it next to another bit. Read as the valid range of a whole word, the range comments would make 0x0201 a valid match word whose syntax bit the parser still applies, against the class javadoc. On #16968 the maintainers chose, for the removed raw value 0x0100, that it should fail loudly rather than be silently ignored; the same reasoning applies to a syntax bit in the match word. It remains fair to call the change hardening of an argument check, and a maintainer could reasonably close it as working as intended or prefer the silent mask for compatibility.

Suggested fix

#

Recommended Test bits instead of value ranges (two lines)

Test bits instead of ranges: (syntax_flags & ~ALL) != 0 throws "Illegal syntax flag" and (match_flags & ALL) != 0 throws "Illegal match flag". Every valid word behaves as before; the repro passes, and 250 automaton and RegexpQuery tests stay green.

    if ((syntax_flags & ~ALL) != 0) {   // was: syntax_flags > ALL
      throw new IllegalArgumentException("Illegal syntax flag");
    }
    if ((match_flags & ALL) != 0) {     // was: match_flags > 0 && match_flags <= ALL
      throw new IllegalArgumentException("Illegal match flag");
    }

Test bits instead of value ranges (two lines) (validated by the checks) (recommended)

Replace syntax_flags > ALL with (syntax_flags & ~ALL) != 0 and match_flags > 0 && match_flags <= ALL with (match_flags & ALL) != 0; keep both messages.

    if ((syntax_flags & ~ALL) != 0) {   // was: syntax_flags > ALL

    if ((match_flags & ALL) != 0) {     // was: match_flags > 0 && match_flags <= ALL

Trade-offs

  • Every valid word (syntax bits only in the syntax word, bits 0x100 and up only in the match word) behaves as before, and both existing flag tests still pass.
  • Newly rejected: a negative syntax word, and a match word with any bit of 0xff, negative or not. Code that passes -1 or ALL | CASE_INSENSITIVE today gets an exception: a compatibility change for callers outside the documented domain, worth a CHANGES entry, and a reason a maintainer may prefer the silent mask or no change.
  • Match bits above 0xff that no flag uses (for example 0x10000) stay accepted, as today; so does the sign bit alone, i.e. a negative match word with no bit in 0xff such as Integer.MIN_VALUE.
  • Composes with #16968's new 0x0100 check: on 14f80c3ebe6 the same two lines apply as they are.

Downstream note

#

Products that copy a user-supplied integer straight into these flag words should validate it themselves: a negative or mixed word is accepted today and switches on optional syntax or case-insensitive matching for that user's query.

How it was found

#

Semi-formal: a proof-obligation check of RegExp's constructor contract, under which syntax bits belong only in syntax_flags and match bits only in match_flags, as its own checks intend. The obligation fails for a match word that carries both kinds of bit, and for a negative word. A JUnit test on main turned that into a missing exception.

The method in full148 words

Method: semi-formal (a proof-obligation check of the RegExp(String, int, int) contract, witnessed by an executable repro, on main 5adff78bb168, 2026-11-04).

  • Obligation. For every pair of words the constructor accepts, the syntax bits that reach the parser are exactly those of syntax_flags, and the match bits exactly those of match_flags; otherwise it throws, as it already does for a wrong-kind word on its own.
  • Finding. The checks are value comparisons, but flags = syntax_flags | match_flags is read bit by bit, so the obligation fails for any match word above 0xff that also has a low bit, and for any negative word.
  • Witness. A one-test JUnit on the stock main jars: no exception for (NONE, CASE_INSENSITIVE | INTERSECTION), with assertions on and off; a probe on main, 10.6.0, 9.12.3 and 8.7.0 showed match words 0x101, 0x201 and 0x1ff accepted with & enabled, and -1 accepted.

Registry title
RegExp(String, int, int) validates its two flag words with signed range comparisons instead of bit masks, so a syntax bit in match_flags next to a match bit (CASE_INSENSITIVE | INTERSECTION) or a negative flag word is accepted, and its stray bits take effect, instead of IllegalArgumentException (every release since 8.7.0)

Priority

It needs a caller mistake in a hand-built flag word; the documented constants and Lucene's query parsers are unaffected and no index data is involved.
Impact class

Impact note
Only callers of the public RegExp(String, int[, int]) or RegexpQuery(Term, int[, int, ...]) constructors that put a syntax constant into the match word next to a match constant, or pass a negative int as either word, are hit: the malformed word is accepted without the IllegalArgumentException the constructor's own check is there to raise, and its stray bits take effect on that caller's own pattern (optional syntax such as '&', '#', '@', '<n-m>' or case-insensitive matching is switched on); callers who pass the documented constants in the right word, and Lucene's own query parsers (RegExp.ALL and 0), are never affected; no index data and no other query is involved; -ea and -da alike; every release from 8.7.0 through 10.6.0 and main.
Summary
You build new RegExp("a&b", RegExp.NONE, RegExp.CASE_INSENSITIVE | RegExp.INTERSECTION), with the syntax flag INTERSECTION put into the match-flags word by mistake. You expect IllegalArgumentException 'Illegal match flag', which the constructor throws for new RegExp("a&b", RegExp.NONE, RegExp.INTERSECTION), the same syntax bit alone. Instead no exception is thrown and '&' is parsed as intersection although syntax_flags is NONE, because the checks compare ranges ('match_flags > 0 && match_flags <= ALL', 'syntax_flags > ALL') instead of testing bits, so a match bit or the sign bit hides the stray bits, which then take effect through 'flags = syntax_flags | match_flags' (likewise new RegExp("a", -1) is accepted and matches "A").
