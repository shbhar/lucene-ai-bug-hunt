The finding in 30 seconds

#

Both tests need their documents in one segment and assert that before their first read. Their writer config is random by design: for some seeds the writer starts a new segment after every 2 to 6 documents (2 to 5 for six documents). Then the assertion fails. The failure comes from the tests' set-up, not from the code under test.

Background: three pieces

#
  1. Lucene's tests are randomized. Each run draws a seed, and helpers of the test framework pick settings from it. A failing run prints its seed, so the run can be repeated.
  2. newIndexWriterConfig() is such a helper: "create a new index writer config with random defaults". For half of its draws it sets maxBufferedDocs, rarely to a value of 2 to 15.
  3. maxBufferedDocs makes the writer flush a new segment after that many documents. NoMergePolicy never merges segments. Both are documented and do what they say.

The finding, step by step

#
  1. You run Lucene's own tests in a checkout of main or of branch_11x (to become 11.0.0). Two tests are new there (#14397, merged 2026-11-19 and backported to branch_11x the same day): TestCompressingStoredFieldsFormat.testDictionaryReuse adds seven documents, TestCompressingTermVectorsFormat.testDictionaryReuse six. Each uses a writer made with newIndexWriterConfig() and NoMergePolicy, and asserts assertEquals(1, reader.leaves().size()) before its first read of a stored value or a term vector.
  2. You expect both to pass unless the code they test is wrong.
  3. With the seed 8621B64601478ADE both fail at that assertion: expected:<1> but was:<3> (stored fields) and expected:<1> but was:<2> (term vectors), with assertions on and off. With the seed DEADBEEF both pass (runs of 2026-11-19 on main 1ae70c6e45b8; the same on 2026-11-20 on main f2b061406c4b and on branch_11x 75eea467ac52).
  4. Why: newIndexWriterConfig() makes a config "with random defaults". For some seeds it sets maxBufferedDocs to a value of 2 to 15, and the writer then flushes a segment after that many documents. With 2 to 6 the seven documents become 4, 3, 2, 2 or 2 segments (with 2 to 5 the six documents become 3, 2, 2 or 2), and NoMergePolicy keeps them.
  5. How often: by the code about 1 master seed in 560 fails the stored-fields test with default settings, about 1 in 70 with nightly settings. Measured in Lucene's build with one master seed, 2,000 iterations per method: 4 and 4 failures; with nightly settings 27 and 22 (main f6e694652c3d, 2026-11-19). With one added line per test, .setMaxBufferedDocs(100), the same seeds pass and the same iterations have 0 failures.

Who is affected

#

Only people and build machines that run Lucene's own tests on main or branch_11x: the two methods are test sources and in no library jar. A default run can hit it, seldom: by the code about 1 master seed in 560 fails the stored-fields test, about 1 in 70 with nightly settings. The failure is loud and prints its seed.

Mechanism, terms and numbers1,013 words

TestCompressingStoredFieldsFormat.testDictionaryReuse and TestCompressingTermVectorsFormat.testDictionaryReuse were added to Lucene's own test suite on main with #14397 (a4c11a89a5e9, merged 2026-11-19) and on branch_11x with its backport (15b6826d849f, 2026-11-19). Each builds its writer with newIndexWriterConfig() and NoMergePolicy, adds seven documents (stored fields) or six (term vectors) and asserts assertEquals(1, reader.leaves().size()) before its first read of a stored value or a term vector (TestCompressingStoredFieldsFormat.java:65-67, :85; TestCompressingTermVectorsFormat.java:62-64, :76, on main 1ae70c6e45b8). newIndexWriterConfig() is the test framework's helper for a config "with random defaults"; for some seeds it sets maxBufferedDocs to a value of 2 to 15 (LuceneTestCaseParent.java:1752-1755). With 2 to 6 the seven documents are flushed into 4, 3, 2, 2 or 2 segments, with 2 to 5 the six documents into 3, 2, 2 or 2, NoMergePolicy keeps them, and the assertion fails with expected:<1> but was:<2> (or 3, and 4 for the stored-fields test).

This is a defect of the two tests, not of a shipped class. That the writer flushes every maxBufferedDocs documents and that NoMergePolicy keeps the segments is documented behaviour. A failing run is a false alarm of a randomized build, and it checks nothing of the change the tests were written for, because the assertion stands before the first read. The failures do not come from the code under test: the same seeds pass once the tests pin maxBufferedDocs (run with .setMaxBufferedDocs(100) on the two writer configs). That the dictionary reuse of #14397 has no defect of its own is not claimed here. The tests exist on main (12.0.0-SNAPSHOT) and, since the backport 15b6826d849f of 2026-11-19, on branch_11x (11.0.0-SNAPSHOT, to become 11.0.0), where the two test files are the same as on main. On branch_11x 75eea467ac52 both tests fail with the seed 8621B64601478ADE, with assertions on and off (run on 2026-11-20). The branch before the backport (b98f116b3179, a commit of 2026-11-18) and the 10.6.0 release do not have them.

Why it looks unintended

#
  • The helper the tests call says what it does: a config "with random defaults". A test that needs one segment has to pin what decides the segment count.
  • Upstream repairs this pattern as a test bug: seven repair commits from 2018 to 2026, among them #15946 and #16075.
  • The expectation is practice, not a written rule.
The full argument418 words
  • No written rule. No file of the tree says that a test passes for each seed. The nearest sentences are in help/tests.md (line 110: the build picks "a random global tests.seed"), in CONTRIBUTING.md (line 57: the tests and validations should succeed before a patch is made) and in the javadoc of LuceneTestCase (lines 104-105: a test that uses the framework's random source "should be fully reproducible", which is about repeating a run with its seed, not about passing for each seed). The expectation is upstream's practice.
  • The practice. Upstream treats this pattern as a test bug and repairs it. Seven repair commits: dd39128eaee (2018-04-18, "[TEST] Ensure IW doesn't autoflush since test relies on it producing a single segment"), 50d65889df3 (2019-06-11, LUCENE-8815), ee0695eda8b (2021-09-08, LUCENE-10092, "fix test bug by forceMerging the index down to one segment"), 7ca782c6deb (2026-04-09, #15946: "The test assumes we have a single segment, but randomization can sometimes give us more than that"; it closed the issue #15943), 64c7fccde7eb (2026-05-18, #16075: "newIndexWriterConfig() randomizes maxBufferedDocs. When multiple writes (addBatch or addDocument) exceed the flush threshold, an auto-flush occurs mid-sequence producing more than one segment."), 5ad4a06082f (2026-06-03, #16169) and d4c8858ee18 (2026-11-13, #17023; that test assumed that each flushed segment holds enough documents, not one segment, and its repair is the line of the second option under Suggested fix). Counted another way, nine upstream items since 2021 name the pattern in other tests (Prior reports); seven of the nine have a merged repair, and five of those repairs are among the commits above (the other two are 7baa01b3c2f, #12138, and 88f79193b18, #16315).
  • The helper says what it does. newIndexWriterConfig() is documented as "random defaults", and the low range carries the comment // crazy value (LuceneTestCaseParent.java:1687, :1754).
  • The tests' own text. The assertion and the comment after it state one segment as a precondition of the reads. Nothing in the set-up guarantees it: for most draws the documents are one segment (the seed DEADBEEF passes both tests), for some they are not.
  • The pull request. The thread of #14397 has no sentence about segments, seeds or maxBufferedDocs, and no comment after its merge (read on 2026-11-19).
  • History. a4c11a89a5e9 added both methods whole. newIndexWriterConfig() has drawn maxBufferedDocs at random since 2010 and from 2 to 15 since LUCENE-3667 (2011). The two tests are what is new, not the test framework.
  • What is documented and not claimed against. The writer flushes every maxBufferedDocs documents (LiveIndexWriterConfig.java:213-214), and NoMergePolicy keeps the segments (NoMergePolicy.java:24-25).
The devil's-advocate check157 words

The strongest case for "intended": several segments are documented behaviour of the writer, NoMergePolicy keeps them by design, and the assertion is a deliberate guard that states the tests' precondition.

Why it fails: all of that is true of IndexWriter and is not what is claimed. A guard that is meant to skip a run is an assumption (assumeTrue); this is assertEquals, which fails the build. The thread of #14397, read whole, has no sentence that defends that two tests fail a build for some seeds without a fault in the code they test, and upstream repairs the pattern when it meets it.

A second argument is fair and limits the weight: a flaky test that was a few hours old on main when it was found (2026-11-19) is everyday business, not a finding about Lucene. That is why this is Low and says in its first words that it is about two tests.

How it was found

#

Right after #14397 was merged, its two new tests were run in Lucene's own build with fixed seeds and with 2,000 iterations each. Some iterations failed at the segment-count assertion. A probe that records the drawn maxBufferedDocs and the segment count of each iteration showed the cause, and the rate was then computed from the test framework's code.

The method in full144 words
  • Method. Non-formal: code reading and randomized runs of Lucene's own tests.
