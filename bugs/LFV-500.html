AttributeSource.removeAllAttributes() leaves the cached State chain in place, so captureState(), copyTo() and hashCode() still see the removed attributes

After removeAllAttributes() on an AttributeSource that was already used, the source says it is empty, yet captureState(), copyTo(), hashCode(), toString() and clearAttributes() still act on the removed attributes: restoring its own captured state throws IllegalArgumentException. The method clears the two attribute maps but not the cached list those methods walk.

The finding in 30 seconds

#

How an AttributeSource keeps its attributes

#
  1. Every token stream is an AttributeSource. It holds attributes such as CharTermAttribute (the term text), and the tokenizer, its filters and the consumer share these objects.
  2. The source registers its attributes in two maps. hasAttribute(), getAttribute(), equals() and restoreState() look them up there.
  3. For speed it also caches the attribute objects as a linked list, built the first time a method walks them. clearAttributes(), captureState(), copyTo(), hashCode() and toString() walk this list; addAttribute() drops it when the set changes, so it is rebuilt.

The finding, step by step

#
  1. Create a new AttributeSource, add a CharTermAttribute, call clearAttributes() (as a tokenizer is documented to do for each token) and set the term to "foo".
  2. Call removeAllAttributes(). Now hasAttributes() is false and the source equals a new AttributeSource, so you expect it to behave like one: captureState() null, hashCode() 0, nothing printed.
  3. Instead restoreState(captureState()) throws IllegalArgumentException, reflectAsString(false) prints term=foo,bytes=[66 6f 6f], hashCode() is 110307 instead of 0, and copyTo(target) overwrites the target's term "keep" with "foo".
  4. Why: the source keeps its attributes in two maps and also caches a linked list of them, built the first time something walks them. addAttribute() drops that list whenever the set changes; removeAllAttributes() clears the maps but keeps the list.
  5. The next addAttribute() drops the stale list. Nothing in Lucene calls removeAllAttributes(), and there is no index or search effect; the fix is one line.

Who is affected

#

Only code that calls removeAllAttributes() on a source that was already used, then captures, copies, hashes, prints, iterates or clears it before adding an attribute again. Nothing in Lucene calls the method, and at its only known caller every consumer checked adds an attribute before it looks. No setting and no scale needed; no index or search effect. Rare.

Mechanism, terms and numbers582 words

AttributeSource, the base class of every TokenStream, keeps its attributes in two maps and caches the attribute instances as a linked State chain. addAttributeImpl() drops the chain whenever the attribute set changes. removeAllAttributes() clears both maps but not the chain, so once something has walked the chain (for example clearAttributes(), which tokenizers are documented to call per token), the methods that walk it keep seeing the removed instances until the next addAttribute().

With one CharTermAttribute set to "foo": restoreState(captureState()) on the same source throws IllegalArgumentException, copyTo(new AttributeSource()) throws, copyTo(target) overwrites the target's term "keep" with "foo", reflectAsString(false) prints term=foo,bytes=[66 6f 6f], and hashCode() is 110307 although equals() says the source equals a new AttributeSource (hash 0). Nothing in Lucene calls the method; at the only known caller, every consumer checked adds an attribute before it looks, so the impact is small. Present since the method was added in 5.5.0; the fix is one line, currentState[0] = null, the same invalidation addAttributeImpl() does.

The code (main 645d4fe14a20, AttributeSource.java)

#
  • :62-66: "These two maps must always be in sync!!!": attributes (interface to instance), attributeImpls (class to instance), and private final State[] currentState, the cached chain. AttributeSource(AttributeSource input) shares all three with its input (:79-85), so a filter and its tokenizer see the same chain.
  • :252-266: getCurrentState() returns currentState[0] as is whenever it is non-null (:253-255); it rebuilds the chain from attributeImpls only when the cache is null and hasAttributes() is true.
  • :188-202: addAttributeImpl() sets this.currentState[0] = null for every new interface, with the comment "invalidate state to force recomputation in captureState()" (:196-197).
  • :288-292: removeAllAttributes() is attributes.clear(); attributeImpls.clear();. currentState[0] is kept.
  • Chain walkers, which see the removed instances: getAttributeImplsIterator() (:116), clearAttributes() (:272-276), endAttributes() (:282-286, called by TokenStream.end()), captureState() (:300-303), hashCode() (:335-341), reflectWith() (:418-422, behind reflectAsString() and toString()), copyTo() (:457-468).
  • Map-based methods, which are right: hasAttributes(), hasAttribute(), getAttribute(), addAttribute(); equals() checks hasAttributes() first (:350, :372); cloneAttributes() is guarded by hasAttributes() (:434).
  • restoreState(captureState()) throws because captureState() clones the stale chain and restoreState() looks each impl up in the now empty map (:322-327). restoreState() itself is fine.

The window

#

It opens when any chain walker ran before removeAllAttributes(), and closes at the next addAttribute(), or at an addAttributeImpl() that registers at least one Attribute interface: after the removal every interface is new, so the first one added nulls the chain. An impl that implements no Attribute sub-interface registers nothing and leaves the stale chain (:149-169, :193-200). If nothing walked the chain before the removal, the source behaves like an empty one.

Exposure and likelihood253 words
  • Trigger. Any chain walker (clearAttributes(), endAttributes(), captureState(), hashCode(), toString()/reflection, the impls iterator) before removeAllAttributes(), then any chain walker before the next addAttribute(). A filter built on the source with AttributeSource(input) shares the window.
  • Not on any Lucene path. The only references to removeAllAttributes() in Lucene's sources are its declaration and TestAttributeSource.testRemoveAllAttributes. A read-only code search found no caller in Elasticsearch or OpenSearch. The only known caller is the pre-analyzed field tokenizer of Solr 9.x. Its parsers add attributes again for any value that has tokens (a value with no token list adds none), and every consumer that was checked adds an attribute before it observes the stream, which closes the window; Solr main removed that field type (SOLR-17839).
  • Default versus opt-in. No setting is involved: an explicit call to a rarely used method plus a legal call order.
  • Scale. None. One attribute and one clearAttributes() before the removal are enough.
  • Effect. Wrong return values and an IllegalArgumentException on that in-memory source; copyTo() can write removed values into another source. No index, query or search effect: indexing runs gave the same outcome with and without the fix, and CheckIndex was clean.
  • The hashCode() symptom needs non-default values. If the attributes are cleared right before the removal, the stale impls hash to 0 and the mismatch hides; the restoreState() and copyTo() failures do not depend on the values.
  • Likelihood: rare. The usual remove-then-re-add pattern closes the window at once, and nobody has reported it since 2016.

Why it looks unintended

#
  • The javadoc says it removes "all attributes and their implementations", and captureState()'s result can restore "this ... AttributeSource"; here that throws.
  • addAttributeImpl() drops the cache whenever the set changes; removeAllAttributes() is the one method that skips it.
  • equals() matches a new AttributeSource, but hashCode() is 110307, not 0. LUCENE-3042 fixed a missed reset of this cache in 2011.
The full argument288 words
  • The method's own javadoc: "Removes all attributes and their implementations from this AttributeSource" (AttributeSource.java:288). Afterwards the impls iterator, reflection and toString() still list the removed implementation.
  • captureState(): "The return value can be passed to restoreState to restore the state of this or another AttributeSource" (:294-297). On the same emptied source that throws.
  • copyTo(): "The given instance has to provide all Attributes this instance contains" (:450-452). The source contains none, yet copyTo(new AttributeSource()) throws and a matching target receives the removed values.
  • clearAttributes(): "Resets all Attributes in this AttributeSource" (:268-271); it resets instances that are no longer in it.
  • Object contract: equal objects must have equal hash codes; at the same moment the source equals a new AttributeSource but hashes to 110307, not 0.
  • The cache is meant to follow the attribute set: addAttributeImpl() invalidates it (:196-197). It has done so since LUCENE-1693 (31a5f0edcc4, Michael Busch, 2009; the comment at :196); LUCENE-3042 (49ab81b316c, Uwe Schindler, 2011) made the cache a shared State[1] array and changed the reset to this.currentState[0] = null (:197).
  • Precedent: LUCENE-3042 (#4115, fixed 2011) was this same cache missing an invalidation on another path (attributes added to an already consumed chain). Its CHANGES entry calls it "This bug", and it was backported to 2.9, 3.0 and 3.1.
  • Intent of the method: SOLR-4619 added it "to support reuse of token streams with variable attributes, like PreAnalyzedTokenizer", listed under New Features for 5.5.0. Neither the discussion nor the patch mentions the cache; the only test, TestAttributeSource.testRemoveAllAttributes (TestAttributeSource.java:214-264), checks hasAttribute() and hasAttributes() only.
  • Nothing says otherwise: no javadoc, test, CHANGES or MIGRATE entry accepts the stale state.
The devil's-advocate check206 words

The strongest case for "intended": the org.apache.lucene.util package-info says "APIs in this package are primarily internal and may change between releases"; the TokenStream javadoc says attributes "must be added during instantiation", and committers called a tokenizer with no attributes before reset() "a bug really" (Robert Muir, SOLR-4619) and adding an attribute in incrementToken() "completely wrong" (Alan Woodward, LUCENE-8610 / #9656); nothing in Lucene calls the method; and the intended use, remove then re-add, never sees the stale chain.

Why it fails: the package-info sentence was added in 2026 by a javadoc-only change (#15719), long after the method shipped as a public, final, unmarked New Feature; the repro uses a plain AttributeSource, which the TokenStream rule does not cover, and no AttributeSource javadoc forbids using the source after the removal; the ordinary reading of the method's one-sentence javadoc and of captureState()'s strongly implies that the cache follows the attribute set, and the Object contract is explicit (the defect is that equal objects have unequal hash codes at the same moment, not that a mutable object's hash changes). These points argue for low impact, which the rating already reflects, not for intended behaviour. Every verifier, the cross-model lenses and the adjudication rated the intended argument weak.

Suggested fix

#

Recommended Invalidate the cached chain in removeAllAttributes() (validated)

Add this.currentState[0] = null; to removeAllAttributes(), the same invalidation addAttributeImpl() does; sources built with AttributeSource(input) share the array, so they are fixed too. Validated on main: the repro passes with assertions on and off, as do TestAttributeSource and the 21 core analysis test classes (175 tests, two seeds).

   public final void removeAllAttributes() {
     attributes.clear();
     attributeImpls.clear();
+    // invalidate the cached state chain, as addAttributeImpl() does when the attribute set changes
+    this.currentState[0] = null;
   }

Trade-offs

How it was found

#

Code reading of AttributeSource, in a hunt over attribute and char-array contracts, spotted that removeAllAttributes() skips the cache reset that addAttributeImpl() does. A randomized contract checker (3,000 random attribute sets, 134,973 checks) then reported violations of only this root cause, and a public-API test confirmed it.

The method in full122 words

Method: non-formal (code reading, then a randomized contract checker and executed tests).

  • Finder. The hunt unit for attribute and char-array contracts read AttributeSource and noticed that removeAllAttributes() changes the attribute set without the currentState[0] = null that addAttributeImpl() performs.
  • Contract checker. The unit's randomized property-based checker built 3,000 random attribute sets over 3 attribute factories and ran 134,973 contract checks. It reported 4 distinct violations, all after removeAllAttributes() and all this root cause: captureState() non-null, the impls iterator non-empty, reflection non-empty, and equals() true while hashCode() differs.
  • Repro. A public-API JUnit test then failed on main with assertions on and off and on 10.5.2, and passed with the one-line fix; the later minimal repro keeps one of its four checks, restoreState(captureState()).
