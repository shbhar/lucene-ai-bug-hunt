ByteWritesTrackingDirectoryWrapper(dir, true) makes every merge fail: its temp outputs report a decorated getName()

With ByteWritesTrackingDirectoryWrapper(dir, true), a temp file named _2_..._4.tmp reports getName() as ByteTrackingIndexOutput{_2_..._4.tmp}. The default stored-fields writer reopens its temp files by that name, so every merge fails with NoSuchFileException, and a writer with an index sort, or any writer indexing a field with term vectors, hits a tragic exception on its first flush; every release since 9.5.0 is affected.

The finding in 30 seconds

#

With trackTempOutput=true, the wrapper's temp outputs report a name that is not the file's name: ByteTrackingIndexOutput{_2_..._4.tmp} instead of _2_..._4.tmp. The stored-fields writer reopens and deletes its temp files by getName(), so it asks for a file that does not exist.

Background: temp files are found again by their name

#
  1. Directory.createTempOutput(prefix, suffix, context) creates a file with a generated, unique name such as _2_Lucene90FieldsIndex-doc_ids_4.tmp. Its javadoc says that name is "accessible via IndexOutput#getName()".
  2. Code that writes a temp file keeps only the output, then reopens and deletes the file with getName(). The default stored-fields format does this for two temp files in every merge.
  3. ByteWritesTrackingDirectoryWrapper (lucene-misc) counts bytes written by flushes and merges; with trackTempOutput=true it also counts temp files by wrapping their outputs.

The finding, step by step

#
  1. Wrap a directory in new ByteWritesTrackingDirectoryWrapper(dir, true) to count flushed and merged bytes, temp files included. Commit two segments of one empty document each and call forceMerge(1).
  2. You expect one merged segment with 2 documents, as with trackTempOutput=false: the option only adds counting.
  3. The merge's stored-fields writer creates the temp file _2_Lucene90FieldsIndex-doc_ids_4.tmp. The wrapper wraps its output, and that output's getName() returns ByteTrackingIndexOutput{_2_Lucene90FieldsIndex-doc_ids_4.tmp}.
  4. The writer reopens the file by that name, and forceMerge(1) throws NoSuchFileException: ByteTrackingIndexOutput{_2_Lucene90FieldsIndex-doc_ids_4.tmp}. Every merge fails this way, even without stored fields; with an index sort, or with a field that stores term vectors, the first commit() fails and closes the writer.

Who is affected

#

Only lucene-misc users who build the wrapper with the non-default trackTempOutput=true; no known application does. For them every merge throws, and a writer with an index sort, or any writer indexing a field with term vectors, closes on its first flush and loses its uncommitted documents. Committed data stays readable; with false or the fix everything works.

Mechanism, terms and numbers519 words

ByteWritesTrackingDirectoryWrapper (lucene-misc) counts the bytes Lucene writes during flushes and merges. With the non-default trackTempOutput=true it also wraps every flush- and merge-context temp output in a ByteTrackingIndexOutput, whose constructor passes "ByteTrackingIndexOutput{" + out.getName() + "}" as the output's name. Directory#createTempOutput documents that the temp file name is "accessible via IndexOutput#getName()", and the default stored-fields writer relies on it: FieldsIndexWriter reopens and deletes its two temp files by getName(). So every merge throws NoSuchFileException: ByteTrackingIndexOutput{_2_Lucene90FieldsIndex-doc_ids_4.tmp}, also for documents without stored fields, and a writer with an index sort, or any writer indexing a field with term vectors, hits a tragic exception on its first flush. Committed data stays readable, and trackTempOutput=false is unaffected. Every release from 9.5.0 to 10.6.0 has it; a one-line fix passes the delegate's name.

The numbers

#

Two commits of one empty document each, default codec, SerialMergeScheduler, forceMerge(1): the merged segment _2 creates _2_Lucene90FieldsIndex-doc_ids_4.tmp and _2_Lucene90FieldsIndexfile_pointers_5.tmp; the first reopen asks for ByteTrackingIndexOutput{_2_Lucene90FieldsIndex-doc_ids_4.tmp} and fails, and the cleanup's two deletes fail the same way (suppressed). A probe shows the gap directly: createTempOutput("seg", "x", merge context) returns getName() = ByteTrackingIndexOutput{seg_x_0.tmp} while listAll() = [seg_x_0.tmp]. With an index sort on a LONG doc-values field and one document, commit() throws NoSuchFileException: ByteTrackingIndexOutput{_0_Lucene90FieldsIndex-doc_ids_5.tmp}, getTragicException() is that exception and isOpen() is false. With no index sort and one document whose indexed, not stored text field stores term vectors, commit() throws NoSuchFileException: ByteTrackingIndexOutput{_0_Lucene90TermVectorsIndex-doc_ids_2.tmp}, the exception is tragic and isOpen() is false; without term vectors, or with false, the commit succeeds.

Exposure and likelihood207 words
  • Who is hit. Applications that wrap their directory in ByteWritesTrackingDirectoryWrapper and pass trackTempOutput=true to count temp-file bytes. A public code search found no application that does (only copies of Lucene's sources). The default false and the one-argument constructor are clean.
  • Default vs opt-in. Opt-in twice: a lucene-misc wrapper, and a non-default constructor flag. No public report of it was found since 9.5.0 (2023).
  • What breaks. Every merge, whether forceMerge or one the merge policy picks, so the index stops merging. With an index sort, or with any field that stores term vectors, the first flush fails: the first commit() or NRT refresh is a tragic exception, the writer closes, and its uncommitted documents are lost.
  • Scale. None: two one-document segments; the documents need no fields.
  • Not affected. Search and the committed index: turning the option off, or the fix, makes the index mergeable again. Unsorted flushes of documents without term vectors work (they write stored fields with IOContext.DEFAULT, which the wrapper does not wrap).
  • Ironic detail. In #11796 jpountz noted that "Some temporary files are also not necessarily short-lived, like the ones we create for stored fields when index sorting is enabled": the traffic the option was meant to measure, and exactly the writes that fail.

Why it looks unintended

#
  • Directory#createTempOutput says the temp file name is "accessible via IndexOutput#getName()" and ends in .tmp; the wrapper's name does not.
  • Lucene's conformance test BaseDirectoryTestCase.testCreateTempOutput fails on the wrapper with true and passes with the fix.
  • Every other FilterIndexOutput subclass in Lucene's sources passes out.getName() as the name.
The full argument188 words
  • The contract. Directory#createTempOutput: "The temporary file name (accessible via {@link IndexOutput#getName()}) will start with {@code prefix}, end with {@code suffix} and have a reserved file extension {@code .tmp}" (Directory.java:98-99). IndexOutput#getName: "Returns the name used to create this {@code IndexOutput}. This is especially useful when using {@link Directory#createTempOutput}" (IndexOutput.java:53-55).
  • The conformance test. BaseDirectoryTestCase.testCreateTempOutput reopens each temp output by getName() and compares the names with listAll() (BaseDirectoryTestCase.java:1290-1313). Against the wrapper with true it fails with NoSuchFileException: ByteTrackingIndexOutput{foo_bar_2.tmp} (54 tests, 1 failure); with the fix 54 of 54 pass. TestByteWritesTrackingDirectoryWrapper.getDirectory builds the wrapper with the default false (:122-125), and testRandomTempOutput uses true but never reopens a temp file (:72-106).
  • The siblings. RateLimitedIndexOutput.java:40, EndiannessReverserIndexOutput.java:27, MockIndexOutputWrapper.java:40, CorruptingIndexOutput.java:34 and ThrottledIndexOutput.java:69 all pass out.getName().
  • Documented as metrics only. "@param trackTempOutput if true, will also track temporary outputs created by this directory" (ByteWritesTrackingDirectoryWrapper.java:41); CHANGES 9.5.0: "Add ByteWritesTrackingDirectoryWrapper to expose metrics for bytes merged, flushed, and overall write amplification factor" (lucene/CHANGES.txt:3816-3817). No javadoc, MIGRATE entry or test says the option cannot be used with an IndexWriter.
The devil's-advocate check205 words

The strongest case for "intended": the decorated name was a conscious choice. In #11796 the author wrote "super#getName() and super#toString() would give us the name and String representation of this class. I made these in case someone wants the access the wrapped class's name" (about the getWrappedName() / getWrappedToString() accessors), and vigyasharma noted "Parent class getName() and toString() get overridden to the ByteTrackingIndexOutput values". FilterIndexOutput is @lucene.internal and takes the name as an argument; uschindler wrote "If the filter directory is just for debugging purposes, we can of course go with the full atomic implementation" (about the cost of the byte counter); and the failure is loud.

Why it fails: the choice was about a descriptive label, which toString() (the resource description) already carries; nobody tied the name to reopening or deleting a file. FieldsIndexWriter has reopened its temp files by getName() since LUCENE-9147 (136dcbdbbce, 2020), before the wrapper existed, so the option failed with any merging writer from the day it was added, and getWrappedName() (removed in #11958) could not have helped, because codec code calls getName(). Both executed cross-model reviews rated the intended-behaviour argument moderate and judged the bug real; the intended-behaviour devil's advocate rejected it. Verdict: a defect.

Suggested fix

#

Recommended A. Pass the delegate's name (recommended; validated)

In ByteTrackingIndexOutput's constructor, pass out.getName() as the name and keep the descriptive text in the resource description, as every other FilterIndexOutput subclass in Lucene's sources does. Validated through gradle: the repro passes with assertions on and off, the six misc.store test classes pass (245 tests) and the formatter check is clean.

B. Make FilterIndexOutput#getName() delegate

#

Override getName() in FilterIndexOutput to return out.getName(), the change #15469 carried (commit 667ca7d74f by dweiss) before its revert on 2026-01-12.

Trade-offs

Covers future subclasses too, but changes a core @lucene.internal class for every wrapper and re-opens a reverted change. Not run here; A can land first.

C. Track temp names in the consumers (not recommended)

#

Have FieldsIndexWriter and others remember the generated name themselves.

Trade-offs

Works around one wrapper by changing every user of the documented contract (FieldsIndexWriter, OfflineSorter, OfflinePointWriter and others read getName()). The wrapper is what breaks the contract.

Downstream note

#

Services that report write amplification through this wrapper should keep trackTempOutput off until the fix ships: with it on, the first merge fails.

How it was found

#

A semi-formal proof-obligation audit of ByteWritesTrackingDirectoryWrapper's contracts. The obligation: a temp output's getName() is the name of the file the directory created, as Directory#createTempOutput documents. Public-API tests witnessed the violation, and Lucene's own BaseDirectoryTestCase, run against the wrapper with trackTempOutput=true, failed testCreateTempOutput.

The method in full69 words

The obligation comes from the createTempOutput and getName() javadoc. Executable public-API probes witnessed its violation, ending in forceMerge(1) failing at FieldsIndexWriter.finish, and were re-run on stock main. A differential run of Lucene's own Directory conformance suite, BaseDirectoryTestCase (54 tests), against ByteWritesTrackingDirectoryWrapper(new ByteBuffersDirectory(), true) failed exactly testCreateTempOutput (NoSuchFileException: ByteTrackingIndexOutput{foo_bar_2.tmp}) and passed 54 of 54 with the one-line fix. The repro was then reduced to one test method.
