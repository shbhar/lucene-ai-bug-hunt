Dequantized FLOAT16 vectors overflow to Infinity when the raw vectors are dropped

With a scalar-quantized FLOAT16 field whose raw vectors were dropped, Lucene rebuilds vectors from the compressed bytes without capping them at the float16 limit, so a stored -65504 comes back as -Infinity. Full-precision rescoring can then rank an exact match last.

The finding in 30 seconds

#

Background: float16 vectors and the dropped-raw fallback

#
  1. A float16 value is stored in a short. The largest finite one is 65504; Float.floatToFloat16 maps 65519 to 65504 and anything of magnitude 65520 or more to Infinity.
  2. Lucene104ScalarQuantizedVectorsFormat stores each vector twice: the raw float16 values, and a compressed copy of small integers (1 to 8 bits per component) with an interval [lower, upper] measured from the centroid, the field's mean vector in that segment.
  3. A read-only index may drop the raw copy to save space; upstream's tests do it by rewriting the vector files. Reads then rebuild each component as centroid + lower + q x step, "with some precision loss".

The finding, step by step

#
  1. Index two FLOAT16 vectors, (65504, -65504, 0) and (0, 0, 0), EUCLIDEAN, with Lucene104ScalarQuantizedVectorsFormat (default 8-bit encoding). 65504 is the largest finite float16 value, and the field accepts it.
  2. Drop the raw vectors after the writer closes, as the format's own tests do, so reads rebuild each vector from its compressed copy. You expect doc 0 back as roughly (65504, -65504, 0).
  3. Instead vectorValue(0) returns (65472, -Infinity, 85.625). The quantization interval reaches 42.8 past the data, so the second component rebuilds as -65546.8, and Float.floatToFloat16 turns anything of magnitude 65520 or more into Infinity.
  4. Whatever uses the rebuilt vector sees an infinite distance. In an 8-dimensional variant, full-precision rescoring of doc 0's own vector gives doc 0 the score 0.0 and ranks the zero vector first; with assertions on, VectorUtil.squareDistance fails its finiteness check. No error with assertions off.

Who is affected

#

Only unreleased main (and branch_11x): a FLOAT16 field on the opt-in scalar-quantized format whose raw vectors were removed by rewriting index files, with EUCLIDEAN or MAXIMUM_INNER_PRODUCT and components at or near +-65504 (tens of thousands for 1-2 bit encodings). vectorValue() and full-precision rescoring return wrong values; plain kNN search is unaffected.

Mechanism, terms and numbers678 words

Lucene104ScalarQuantizedVectorsFormat quantizes FLOAT16 vectors (since #16473). For read-only indexes whose raw float16 vectors were dropped to save storage, getFloat16VectorValues returns OffHeapScalarQuantizedFloat16VectorValues, which rebuilds each vector "with some precision loss relative to the original float16 vectors". It calls OptimizedScalarQuantizer.deQuantize(byte[], short[], ...), which narrows xi + centroid[h] with Float.floatToFloat16 and no clamp (OptimizedScalarQuantizer.java:294). The optimized interval can reach a little past the data, so a component at the fp16 limit rebuilds just beyond it and becomes Infinity: (65504, -65504, 0) reads back as (65472, -Infinity, 85.625) with the default 8-bit encoding. Full-precision rescoring then gives the document an infinite EUCLIDEAN distance (score 0.0), so an exact match can rank last; with -ea, VectorUtil.squareDistance trips its finiteness assert. The FLOAT32 sibling view stays finite on the same data. It needs the opt-in quantized format, raw vectors dropped by a file rewrite (as upstream's tests do), EUCLIDEAN or MAXIMUM_INNER_PRODUCT and components near +-65504 (tens of thousands for 1-2 bit encodings); plain kNN search is unaffected. Unreleased main and branch_11x only; saturating to +-65504 before narrowing fixes it.

The bug (main 645d4fe14a20)

#
  1. Lucene104ScalarQuantizedVectorsReader.getFloat16VectorValues: when the raw float16 vectors have size 0 (:327), it returns the dequantized view paired with the quantized values (:331-343).
  2. At index time OptimizedScalarQuantizer.scalarQuantize centres the vector on the centroid (:205), clamps the initial interval to the centred vector's [min, max] (:217-218), then optimizeIntervals (:219, defined at :336) can move an end past [min, max].
  3. The view's vectorValue (:105-127) calls deQuantize(byte[], short[], ...) (:117-123), which computes xi = q * step + lowerInterval (OptimizedScalarQuantizer.java:293) and Float.floatToFloat16((float) (xi + centroid[h])) with no clamp (:294). Its javadoc: "narrowing each reconstructed value to float16" (:272-273). The view is its only production caller.
  4. A rebuilt value of magnitude 65520 or more becomes +-Infinity. VectorUtil.squareDistance(short[], short[]) asserts a finite result (VectorUtil.java:144-151, assert :149); with assertions off, EUCLIDEAN scores the infinite distance as 1 / (1 + Infinity) = 0.0.
  5. Affected readers: Float16VectorValues#vectorValue and #rescorer on the view, so RescoreTopNQuery.createFullPrecisionRescorerQuery(Query, short[], String, int) (RescoreTopNQuery.java:302-306) and, by code reading, the queries module's Float16KnnVectorFieldSource (:71). Plain kNN search scores in quantized space and was executed unaffected.

Exposure and likelihood314 words
  • Who is hit. Applications on unreleased main and branch_11x that index FLOAT16 vectors with Lucene104ScalarQuantizedVectorsFormat or Lucene104HnswScalarQuantizedVectorsFormat (both executed) and then drop the raw vectors for a read-only searcher index. No IndexWriter API does that today; open #15630 / #13158 would make the writer produce such files.
  • Similarities. EUCLIDEAN and MAXIMUM_INNER_PRODUCT (both executed). COSINE vectors are scaled to unit length before quantization (Lucene104ScalarQuantizedVectorsWriter.java:903-905), so they never come near the limit. DOT_PRODUCT is documented to need unit-length vectors (VectorSimilarityFunction.java:53-57), but nothing enforces that; it was not tested.
  • How large. There is no simple threshold: it depends on the optimized interval end, the centroid and the code a component gets. What the probes saw: with the default 8-bit encoding, 40 of 40 random 22-dimensional segments with about 25% of components at exactly +-65504 overflowed, and 0 of 200 with gaussian values of sigma 15000 capped at 60000 did. With 1 and 2 bits, values in the tens of thousands were enough (60000 at 1 bit, -50944 at 2 bits). All 5 encodings overflow on a witness at +-65504. Values exactly at 65504 arise, for example, when an application saturates float32 values while converting them to fp16.
  • What happens. vectorValue() returns an infinite component with no error. Full-precision rescoring gives the document an infinite EUCLIDEAN distance (score 0.0), so an exact match can rank last; under MAXIMUM_INNER_PRODUCT the scores became NaN or +Infinity and moved such documents into the top 3. With -ea the rescore ends in an AssertionError.
  • What does not happen. No index damage, no hang, no change to the inner query's match set; plain kNN search returns identical hits and scores with raw vectors kept and dropped.
  • Scale. Opt-in on every axis. A single affected document is enough, in a segment that also holds other vectors; a one-document segment reads back exactly, because its centroid is the vector itself.

Why it looks unintended

#
  • The view promises the stored vectors back "with some precision loss"; upstream's test of this mode asserts the quantization error bound.
  • The field accepts only finite values, and VectorUtil.squareDistance asserts a finite result.
  • The FLOAT32 view rebuilds the same data finitely and ranks the exact match first.
The full argument260 words
  • The view's contract. "reconstructs float16 values by dequantizing them, with some precision loss relative to the original float16 vectors" (OffHeapScalarQuantizedFloat16VectorValues.java:43-45; the "relative to the original" wording came from a review suggestion by msokolov in #16473).
  • Upstream tests assert an error bound in this mode. testReadQuantizedFloat16VectorWithEmptyRawVectors "asserts they stay within the quantization error bound" (TestLucene104ScalarQuantizedVectorsFormat.java:444-449, added by #16473); the shared base test says formats "maintain accuracy within expected error bounds even when the original raw vector file is empty" (BaseKnnVectorsFormatTestCase.java:2187-2189). Both use small random vectors, far from 65504: the fp16 test unit-length vectors (TestLucene104ScalarQuantizedVectorsFormat.java:461), the base test unit-length vectors for COSINE and otherwise components in [0, 1) (BaseKnnVectorsFormatTestCase.java:2202-2204, :1903-1915).
  • Finite in, finite out. KnnFloat16VectorField rejects non-finite values (checkFiniteFloat16, KnnFloat16VectorField.java:72); VectorUtil.squareDistance(short[], short[]) asserts a finite result (:149).
  • The FLOAT32 sibling. On the finder's 1-bit data with raw vectors dropped, OffHeapScalarQuantizedFloatVectorValues rebuilds doc 0 as [73820.7, 33820.707, 1171.291, 1171.291] and ranks it first; on the repro's two documents it reads doc 0 back as [65461.168, -65546.8, 85.625], finite. For this data the difference that matters is that it keeps the float reconstruction, while the FLOAT16 view narrows it without saturating.
  • A supported mode. CHANGES.txt: #14792 (introduced the fallback), #15476 ("Enforce fallback support for float vector retrieval in quantized KNN vector formats"), #16415 ("Fix scoring on scalar-quantized indexes whose raw float vectors have been dropped", 10.5.1).
  • No sign of intent. None of the 41 #16473 PR texts mentions overflow, infinity, 65504, saturation, clamping, range or finiteness.
The devil's-advocate check266 words

The reviews by a reviewer from another model family (OpenAI GPT-5.6) voted not real on these grounds, while reproducing the bug and agreeing on the cause and the fix: (a) deQuantize(byte[], short[], ...) is a public static method documented as "narrowing each reconstructed value to float16", and TestOptimizedScalarQuantizer#testDeQuantizeFloat16MatchesFloat asserts equality with Float.floatToFloat16 of the float overload, so Infinity is the helper's specified result; (b) the trigger state exists only after rewriting index files ("The raw vector file is emptied below, which CheckIndex rightly rejects", BaseKnnVectorsFormatTestCase.java:2275), the view is @lucene.internal, and SECURITY.md calls modified index files undefined behaviour; (c) 65504 is extreme.

Why it fails: (a) only decides where the clamp goes; the helper's only production caller is the view, whose contract is an approximation, and the helper's own test (values in [0, 1)) passes with the clamp. (b) The quantized data is exactly what IndexWriter wrote; only the raw-vector files are rewritten (.vec emptied, its metadata .vemf set to 0 vectors; .veq and .vemq untouched), which is the mode's purpose, and upstream tests, documents and bug-fixes that mode. The quoted CheckIndex comment is in a FLOAT32 test: on the repro's index CheckIndex reports no problem before or after the drop, and its vector test covers 0 fields, because at main it skips FLOAT16 vector fields (CheckIndex.java:2864-2867; see LFV-089). (c) The values are legal input the field accepts, and the FLOAT32 path handles them. Verdict: a defect; a maintainer may still call it hardening of an opt-in internal mode, which is why fix A pairs the clamp with a javadoc sentence.

Suggested fix

#

Recommended A. Saturate to +-65504 in deQuantize(byte[], short[], ...), with a javadoc sentence

Saturate the rebuilt value to +-65504 before narrowing in OptimizedScalarQuantizer.deQuantize(byte[], short[], ...), and say so in its javadoc (+7/-2 lines). With it the repro passes with assertions on and off, the 6 closest core test classes (149 tests) pass, and :lucene:core:check -x test passes.

Trade-offs

  • A value at the limit rebuilds as 65504 instead of Infinity: an error no larger than the float reconstruction's own (42.8 in the repro).
  • In-range values are unchanged bit for bit, so the helper's equality test still passes.
  • It changes the documented behaviour of a public static method of an @lucene.experimental class (hence the javadoc sentence); the view is its only production caller.
  • Cost: one clamp per component on the fallback read path. No on-disk change; existing indexes are fixed on read.

Downstream note

#

No release has this code; until a fix lands, a service on main that drops raw FLOAT16 vectors should not trust vectorValue() or full-precision rescoring for vectors with components near the fp16 limit.

How it was found

#

Formal: a Z3 floating-point query over the quantizer's float16 read path showed that a legal float16 component inside the quantization interval can rebuild to a non-finite value, at 1, 4 and 8 bits. A probe of the real quantizer gave a witness, and a JUnit test on a real index confirmed it with assertions on and off.

The method in full143 words
  • Method: floating-point SMT precondition chaining (Z3), the hunt's formal tier, in the hunt unit on optimized scalar quantization. The obligation "the fp16 reconstruction of a legal in-interval fp16 component is finite" was refuted for 1, 4 and 8 bits (its violation is satisfiable); two more queries proved that fp16 narrowing overflows iff |y| >= 65520 and that a clamp keeps values finite.
  • Witness: a real-jar probe of scalarQuantize + deQuantize(short[]) over random fp16 vectors hit +-Infinity for 1, 2, 4, 7 and 8 bits; then a JUnit test on a real index with the raw vectors dropped (read-back and rescoring) failed 2/2 with -ea and -da, and the clamp made it pass.
  • Later: an independent reproducer, an intended-behaviour devil's advocate, cross-model reviews and an adjudication checked it (2026-10-25); the test was reduced to one method (2026-10-29) and re-verified on main 645d4fe14a20.

LFV-084, snapshot of 2026-11-09

Registry title
FLOAT16 vectors read back from a quantized index whose raw vectors were dropped can contain +-Infinity, so full-precision rescoring ranks an exact match last
Area
codecs / vectors
Priority
Low, rank 1192: FLOAT16 vectors read back from a quantized index with raw vectors dropped can be +-Infinity, which needs file surgery plus values near the fp16 limit, in unreleased code.
Impact class
silent wrong results
Impact note
Users of unreleased main and branch_11x (11.0.0) with a FLOAT16 field on the opt-in Lucene104 scalar-quantized format whose raw vectors were dropped (the read-only fallback, made by rewriting index files after IndexWriter closes), EUCLIDEAN or MAXIMUM_INNER_PRODUCT, and components near the fp16 limit (default 8-bit encoding: at or within about one quantization step of +-65504; 1-2 bit: tens of thousands are enough); ordinary scale; plain kNN search is unaffected.
Summary
You index finite FLOAT16 vectors with large components (for example 60000) in the Lucene104 scalar-quantized format, then drop the raw vectors the way the format's own tests do (simulateEmptyRawVectors), so reads go through the dequantized fp16 view. You expect getFloat16VectorValues().vectorValue() to return an approximation of each stored vector, and full-precision rescoring with a document's own vector to rank that document first. Instead OptimizedScalarQuantizer.deQuantize(byte[], short[], ...) narrows a slightly out-of-range float reconstruction to fp16 without saturating, so 60000 comes back as Infinity, and rescoring gives the exact match the score 0.0 and ranks it last (with -ea, an AssertionError in VectorUtil.squareDistance).
