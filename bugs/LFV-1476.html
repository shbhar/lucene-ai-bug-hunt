ReplicaNode.close() after a failed start() throws NullPointerException and keeps the index write lock

In the experimental NRT replicator, closing a ReplicaNode whose start() failed, or was never called, throws NullPointerException before it frees the index write lock, so, with the default lock factory, no IndexWriter or replica can open that index again until the JVM restarts. In every release since 6.0.0.

The finding in 30 seconds

#

close() assumes start() succeeded: it first closes the searcher manager, which only a successful start() creates, and frees the write lock only at its very end. After a failed start() that first step throws NullPointerException, so the lock is never freed, and the private lock field leaves no other Lucene API to free it.

Background: NRT replication in one minute

#
  1. The optional lucene-replicator module has an experimental near-real-time (NRT) replication: a primary node indexes with an IndexWriter, and replica nodes copy its new index files and search them.
  2. An application writes its own replica class by extending ReplicaNode and supplying the calls to the primary (sendNewReplica, newCopyJob, launch).
  3. Creating a replica locks its index directory with write.lock, as an IndexWriter does, so that no writer can change the files under it.
  4. start() brings the replica's index in line with the primary and, at its end, opens the searcher manager that serves searches. close() should undo all of this and free the lock.

The finding, step by step

#
  1. Create a ReplicaNode subclass on an FSDirectory path. Its constructor takes the path's write.lock, just as an IndexWriter would.
  2. Call start(0) on the empty index; it fails because sendNewReplica() throws IOException("primary unreachable"). The node's searcher manager is created only near the end of start(), so it is still null.
  3. Call close(). You expect it to free write.lock, as IndexWriter does when its own constructor fails.
  4. Instead close() throws NullPointerException ("this.mgr is null") at its first clean-up step, line 683; the lock release at line 699 never runs, and the test framework reports 1 leaked write.lock handle.
  5. The lock field is private and close() is its only release path, so with the default NativeFSLockFactory every new IndexWriter or ReplicaNode on that path fails with LockObtainFailedException: Lock held by this virtual machine until the JVM exits.

Who is affected

#

Only applications of the opt-in, experimental NRT replicator that run a replica inside a long-lived JVM. After a failed start (an I/O error, an unreachable primary, a failing searcher factory) or a shutdown before start, closing the node and reopening the same index in that JVM fails until restart. One-node-per-JVM deployments that exit on failure are not affected.

Mechanism, terms and numbers548 words

ReplicaNode's constructor takes the index write lock (ReplicaNode.java:103 on main f794ff5a505c), because the replica "act[s] like" an IndexWriter (:101-102). The node's SearcherManager (mgr) is created only near the end of start() (:318), and close() calls mgr.close() first (:683) and frees the lock only at its end, in IOUtils.close(writeFileLock, dir) (:699). So when start() fails before mgr is assigned at :318 (an IOException from the replica's Directory, from sendNewReplica(), from the start-up copy after a primary change, or from the SearcherFactory), or is never called, close() throws NullPointerException and the lock stays held. The lock field is private (:80), so close() is its only release path, and the default NativeFSLockFactory keeps the path in a JVM-wide set (NativeFSLockFactory.java:68): every later IndexWriter or ReplicaNode on that path fails with LockObtainFailedException: Lock held by this virtual machine until the JVM exits. A start() that fails after :318, in the commit() that follows a primary change (:320-325), leaves mgr set and does not take this path. Only the opt-in, @lucene.experimental NRT replicator is affected, in every release from 6.0.0 through 10.6.0 and on main, with assertions on and off.

The code (main f794ff5a505c, ReplicaNode.java)

#
  1. Constructor (:88-113): writeFileLock = dir.obtainLock(IndexWriter.WRITE_LOCK_NAME) (:103); the field comment says "We hold this to ensure an external IndexWriter cannot also open on our directory" (:79-80, private final). Then state = "init" (:105).
  2. start(long) (:119, protected synchronized): finds the last commit and lists the directory (:129, :137), reads that commit if there is one (:156), may sync from the primary (newCopyJob, CopyJob.start), calls sendNewReplica() (:315), and only then creates mgr = new SegmentInfosSearcherManager(...) (:318) and sets state = "idle" (:329).
  3. start()'s catch (:330-338) logs and rethrows. It frees nothing and leaves state at "init", so start() can be called again. Its "replica cannot start" branch closes only the Directory (:335).
  4. close() (:670-703): sets state = "closing", calls mgr.close() (:683), runs the file-deleter clean-up, and only then IOUtils.close(writeFileLock, dir) (:699). With mgr == null the NullPointerException skips the release.
  5. NativeFSLockFactory, the FSDirectory default, records the path in a static set when the lock is taken (NativeFSLockFactory.java:68, :108) and removes it only when the lock is closed (:212); a new lock on a recorded path throws "Lock held by this virtual machine" (:119).

Triggers (same fix line)

#

Any start-up step that can fail before mgr is assigned at :318: a Directory call (listAll, readCommit, the deletion of unknown files, the start-up copy's writes and renames), newCopyJob or CopyJob.start during the start-up sync after a primary change, sendNewReplica(), or the SearcherFactory that :318 itself calls. Also a node that is closed without ever calling start(): the same NullPointerException, the same held lock (executed). A start() that fails after :318, in the commit() that follows a primary change (:320-325), is not affected: mgr is then set and close() gets past :683.

Exposure and likelihood228 words
  • Who is hit. Applications that use the NRT replicator (lucene-replicator, package org.apache.lucene.replicator.nrt, @lucene.experimental: ReplicaNode.java:61, Node.java:42) with their own ReplicaNode subclass, keep the replica inside a long-lived JVM, and after a failed start, or a shutdown before start, close the node and open the same path again in that JVM. Plain IndexWriter users are not affected.
  • Not hit. Deployments that run one node per JVM and exit on a failed start, as the module's own tests do (TestNRTReplication starts each node in a child JVM): with the default NativeFSLockFactory the lock goes away when the process exits.
  • Effect. A loud exception from close() and an index path that cannot be reopened until restart. close() throws before its file clean-up, so it changes no index file; the repro's index is empty, and what a failed start-up copy after a primary change leaves on disk is not examined here. No scale is needed: one failed start is enough.
  • Lock factories. These statements hold for the default NativeFSLockFactory, which the repro uses. FSDirectory accepts another LockFactory (FSDirectory.java:84-85); SimpleFSLockFactory keeps write.lock as a file on disk, and its javadoc says such a lock may have to be removed by hand when it was not released (SimpleFSLockFactory.java:30-36; read, not executed).
  • How likely. Rare: no report of it since 6.0.0 (2016) was found.

Why it looks unintended

#
  • ReplicaNode's own constructor calls close() on a node that has not started, as best-effort clean-up: the class itself expects close() to run before start() succeeds.
  • Node implements Closeable and the lock field is private: close() is the only way to free the lock.
  • IndexWriter, which the replica imitates, frees its lock when its constructor fails.
The full argument141 words
  • The class itself closes nodes that have not started. When the constructor body fails, ReplicaNode calls close() on the node as best-effort clean-up (IOUtils.closeWhileSuppressingExceptions(t, this), ReplicaNode.java:107-108, which suppresses close()'s exceptions). That is no written contract, but it shows that close() is expected to run on a node that never started.
  • close() is the only release path. Node implements java.io.Closeable (Node.java:44), whose close() "releases any system resources associated with it", and writeFileLock is private (ReplicaNode.java:80).
  • The lock mirrors IndexWriter's, and IndexWriter frees it when its constructor fails ("init: hit exception on init; releasing write lock", IndexWriter.java:1202-1209).
  • Lucene's own test framework flags it: its file-handle leak check fails the suite on the write.lock channel (executed).
  • No javadoc, test, CHANGES or MIGRATE entry says that a failed or never-started node may not be closed.
The devil's-advocate check136 words

The argument. The replicator is experimental, start() is protected, no javadoc promises that close() works after a failed start(), and the module's tests never hit it because each node runs in its own JVM. Keeping the lock after a failed start() is also defensible: the node stays in state "init", start() can be retried, and a retried start then runs holding the lock (executed).

Why it fails. That justifies start() keeping the lock, not close() throwing a NullPointerException and keeping it for the life of the JVM. The class itself closes nodes that have not started (:108), Closeable has no "only after start" precondition, and no Lucene API other than close() frees the private lock (a subclass can work around it, see Suggested fix). That is why the fix touches only close().

Suggested fix

#

Recommended A. Null guard on the searcher manager in close() (recommended, validated)

Recommended: in ReplicaNode.close(), close the searcher manager only if it exists (if (mgr != null) mgr.close();), so close() reaches the lock release. start() stays as it is: it can be retried and should keep the lock meanwhile. Validated: the repro passes, the 13 nightly TestNRTReplication tests pass and the formatter check is clean.

     synchronized (this) {
       message("top: close mgr");
-      mgr.close();
+      // mgr is null if start() failed or was never called
+      if (mgr != null) {
+        mgr.close();
+      }
 
       message("top: decRef lastNRTFiles=" + lastNRTFiles);
       deleter.decRef(lastNRTFiles);

Option A was built and checked in a scratch worktree of f794ff5a505c; B was not run; C was executed by the intended-behaviour devil's advocate and shown unsafe.

Workaround for users until a fix ships (executed). mgr is a protected field of Node (Node.java:71), so a ReplicaNode subclass can override close() to assign a no-op ReferenceManager when mgr is null and then call super.close(); the lock is then released and a new IndexWriter opens (fact check probe, assertions on).

Trade-offs

One line of logic. On a node that never got a searcher, close() then runs its remaining clean-up as for a started node (on the repro's empty index it has nothing to do) and frees the lock. It keeps today's start() behaviour: a failed start() still holds the lock while the node stays in "init" and may be retried. It does not free the lock if a later step of close() throws (option B). Checked on the repro's empty index and, in the fact check's probe, on a 3-document index whose start(0) failed in sendNewReplica(): close() returns and a new IndexWriter still sees 3 documents. Not checked after a failed start-up copy that followed a primary change, where close()'s deleter clean-up (:686-695) would run on whatever the copy left.

What the checks validated

Gradle, scratch worktree of f794ff5a505c: the repro fails before and passes after, assertions on and off; :lucene:replicator:test passes (16 tests, 15 skipped: every other test of the module is @Nightly or runs only as a child process); TestNRTReplication with -Ptests.nightly=true: 13 tests, 0 failures; checkGoogleJavaFormat clean. B. Free the lock in a finally block of close() (not run)

#

Together with A, wrap the body of the second synchronized block of close() in try { ... } finally { IOUtils.close(writeFileLock, dir); }.

Trade-offs

Also frees the lock when a later clean-up step of close() throws. A larger diff that this bug does not need.

What the checks validated

Not run.

C. Free the lock in start()'s catch (not recommended) (validated by the checks)

#

Release writeFileLock in the catch of start() (:330).

Trade-offs

start() leaves the node in "init" and can be retried after a failure. With this change a retried, live replica runs without its write lock, which breaks the field's stated purpose (:79). It would need a terminal "failed" state, a design choice for the maintainers.

What the checks validated

Executed by the intended-behaviour devil's advocate: with this change the lock was free while a retried replica was running.

Downstream note

#

A search server that runs replicas in-process and, after a failed replica start, closes that replica and opens a new replica or writer on the same index in the same process (instead of restarting the process) cannot open that index again until the process restarts.

How it was found

#

A bounded-exhaustive single-fault enumeration over the real NRT replication classes (one injected failure at every step of 14 replication scripts, 292 runs per assertion mode, plus 12 runs with failing start-up callbacks) showed a replica restart failing with LockObtainFailedException. Code reading found the cause, and the finding was reduced to one JUnit test.

The method in full112 words

Semi-formal: the enumeration ran an in-JVM replication harness over the real ReplicaNode, CopyJob, CopyOneFile, ReplicaFileDeleter and SegmentInfosSearcherManager classes and injected one failure at a time at every fault position, then checked the cluster after each step. Its first signal was a replica restart that failed with LockObtainFailedException. With the finder's first fix sketch (the null guard plus a lock release in start()'s catch, options A and C together) no run showed a held lock; the enumeration was not re-run with A alone, which the minimal repro and the probes checked. The root cause was confirmed by reading the code and reduced to one JUnit test (found 2026-11-10).

Registry title
ReplicaNode.close() throws NullPointerException and never releases the index write lock when start() failed or was never called, so the index stays write-locked for the rest of the JVM (since 6.0.0)
Area
replicator / NRT replication: ReplicaNode start() failure and close() cleanup (index write lock)
Priority
Low, rank 1140: In the opt-in, experimental NRT replicator, ReplicaNode.close() after a failed or missing start() throws NullPointerException and keeps the index write lock, so reopening the same path in the same JVM fails until restart, in every release since 6.0.0. It needs a start-up failure inside the process followed by a reopen in the same JVM, which deployments that run one node per JVM and exit on failure never see, and the failure is loud with nothing written wrong.
Impact class
minor
Impact note
Applications that use the opt-in, @lucene.experimental NRT replicator (their own ReplicaNode subclass) are hit when a replica's start() fails (an I/O error on the replica's Directory, or a start-up step such as sendNewReplica, newCopyJob or CopyJob.start during the start-up sync after a primary change, or SearcherFactory.newSearcher, throwing), or when a node is closed before start() was ever called, and the application then closes the node and reopens the same index path in the same JVM: close() throws NullPointerException and the write lock the constructor took stays held, so every later IndexWriter or ReplicaNode on that path fails with LockObtainFailedException 'Lock held by this virtual machine' until the JVM exits [exec, -ea and -da]; deployments that run one node per JVM and exit on a failed start (as the module's own tests do) do not see the held lock; no scale needed; every release since 6.0.0.
Summary
You subclass ReplicaNode (as the module's SimpleReplicaNode does), call start() and, when it fails with an IOException (in the minimal repro sendNewReplica() throws its declared IOException; in an earlier test the replica Directory's first listAll() throws), close the node, then open a new IndexWriter on the same FSDirectory path. You expect close() (Node implements java.io.Closeable) to release the write lock that ReplicaNode's constructor took 'since we act like an IndexWriter', as IndexWriter releases its own lock when its constructor fails, so the path can be opened again. Instead close() throws NullPointerException ('Cannot invoke ReferenceManager.close() because this.mgr is null') at its first step, because the SearcherManager is created only near the end of start(), so it never reaches IOUtils.close(writeFileLock, dir), and once that exception is caught a new IndexWriter on the path fails with LockObtainFailedException 'Lock held by this virtual machine'; a node that is closed without ever calling start() hits the same NullPointerException and held lock.
