A synonyms file saved as UTF-8 with a byte order mark silently loses its first rule

If a synonyms file starts with a UTF-8 byte order mark, the invisible mark sticks to the first word: with couch, sofa on line 1, a search for couch misses a document about a sofa, and a commented-out first rule becomes live. Every release from 3.4.0 to 10.5.2 and main.

The bug in 30 seconds

#

The synonym factories read the synonyms file themselves. The word-list factories (stop words and the like) read their files through a shared line loader that drops a leading byte order mark; the synonym path keeps it on line 1.

Two things to know first

#
  1. A byte order mark (BOM) is the three bytes EF BB BF that some editors write at the start of a UTF-8 file. Java decodes them into one invisible character, U+FEFF (ZERO WIDTH NO-BREAK SPACE). It is not whitespace, so trim() keeps it.
  2. A synonyms file in the default Solr format has one rule per line: couch, sofa makes two words equivalent, tv => television maps one to the other, and lines starting with # are comments.

The bug, step by step

#
  1. You save synonyms.txt with two rules, couch, sofa and tv, television, in an editor that writes UTF-8 with a byte order mark: 30 bytes instead of 27, starting EF BB BF, which Java decodes to the invisible character U+FEFF.
  2. You load it with SynonymGraphFilterFactory and its defaults, and expect what the same file without the mark gives: couch expands to [sofa, couch], and a search for couch finds the one document a red sofa.
  3. You get [couch]: the first rule is stored as \uFEFFcouch, sofa, so the token couch never matches it, and the search finds 0 of 1 documents. Line 2 still works (tv gives [television, tv]). No error, and printed tokens look right because U+FEFF is invisible.
  4. A commented-out first line is hit too: #couch, sofa now starts with U+FEFF, not #, so it becomes a live rule and sofa expands to \uFEFF#couch. The Apache license header that opens Lucene's own test synonyms files has a comma, so with a mark it becomes a rule as well.
  5. Why: the synonym factories decode the file with their own reader. The word-list factories (stop words, keep words, stemmer overrides, char-filter mappings, type files) read through WordlistLoader.getLines, which drops a leading mark ("skip initial bom marker"), and so did the synonym factory until its 3.4.0 rewrite.

Who is affected

#

Anyone who loads a synonyms file saved as UTF-8 with a byte order mark through SynonymGraphFilterFactory or the deprecated SynonymFilterFactory; the default settings are affected. One rule per file goes wrong, silently. The synonym filter is opt-in (no stock analyzer uses it); indexes keep wrong expansions until reindexed.

Mechanism, terms and numbers793 words

SynonymGraphFilterFactory and the deprecated SynonymFilterFactory decode the synonyms file with their own strict UTF-8 reader and pass it to SolrSynonymParser (the default format) or WordnetSynonymParser. Some editors save UTF-8 with a byte order mark, the bytes EF BB BF, which Java decodes to the invisible character U+FEFF. Nothing on the synonym path drops it: the Solr parser treats a line as a comment only if its first character is #, and trim() and the default whitespace rule tokenizer keep U+FEFF, so it stays glued to the first term of the first line. With couch, sofa on line 1, couch gets no synonym and sofa gains the invisible synonym \uFEFFcouch; a commented-out first line #couch, sofa becomes a live rule; in WordNet format the first word leaves its synset. With the default settings only the first line of each file is affected, and no error is raised. The word-list factories (stop words, keep words, stemmer overrides, char-filter mappings, type files) read through WordlistLoader.getLines, which skips a leading mark (SOLR-1865, 2010), and the synonym factory did too in 3.1 to 3.3; the 3.4.0 rewrite (LUCENE-3233) gave it its own reader without the skip. Every release from 3.4.0 to 10.5.2, branch_10_6 and main is affected (10 releases executed, the rest inferred from the unchanged code). Skipping one leading U+FEFF where the factories decode each file fixes it.

Terms

#
  • Synonyms file: the synonyms parameter of SynonymGraphFilterFactory and the deprecated SynonymFilterFactory (one file or a comma-separated list), parsed by SolrSynonymParser (format=solr, the default) or WordnetSynonymParser (format=wordnet).
  • Byte order mark (BOM): the bytes EF BB BF at the start of a UTF-8 file. Java's UTF-8 decoder keeps them as the character U+FEFF; Character.isWhitespace(0xFEFF) is false and "\uFEFF".trim() has length 1.

The bug

#
  1. SynonymGraphFilterFactory.loadSynonyms (SynonymGraphFilterFactory.java:168-194) builds a strict UTF-8 decoder and, for each file, calls parser.parse(new InputStreamReader(loader.openResource(file), decoder)) (:191). The deprecated SynonymFilterFactory.loadSynonyms (SynonymFilterFactory.java:171-199) does the same (:194-196). The decoded first line of the example is \uFEFFcouch, sofa, 12 characters.
  2. SolrSynonymParser.addInternal skips a line only if it is empty or its charAt(0) is # (SolrSynonymParser.java:85; javadoc :33: "Blank lines and lines starting with '#' are comments"). It splits the line on => and ,, and each piece goes through unescape(...).trim() and the rule analyzer (:96-118), by default a WhitespaceTokenizer (SynonymGraphFilterFactory.java:146), which does not split on U+FEFF. So the first term is \uFEFFcouch, and a # first line is parsed as a rule; it only has a visible effect when it contains , or =>.
  3. WordnetSynonymParser.parse reads the synset id from fixed columns, line.substring(2, 11) (WordnetSynonymParser.java:53-54): with the mark, line 1 gives (10000000 instead of 100000001, so the first word starts a synset of its own.
  4. The factories that read word lists and line files through AbstractAnalysisFactory.getLines / getWordSet go through WordlistLoader.getLines, which drops a leading U+FEFF before the # test: // skip initial bom marker (WordlistLoader.java:302-304). Stop words, keep words and common-grams words in the default wordset format, stemmer overrides, char-filter mappings and type lists get the skip. Not every resource loader does: the snowball words format (AbstractWordsFileFilterFactory.java:89-90 -> AbstractAnalysisFactory.getSnowballWordSet, its own reader), ICU tokenizer rule files and the Japanese and Korean user dictionaries keep the mark too (separate reports).

Exposure and likelihood333 words
  • Who is exposed. Applications that configure SynonymGraphFilterFactory or the deprecated SynonymFilterFactory with a synonyms file: directly, through CustomAnalyzer, or through a search server's schema (the factory javadoc example is a schema snippet). The factories' defaults are affected: format=solr, the whitespace rule tokenizer, expand=true. The component is opt-in: no stock Lucene analyzer uses it; SynonymGraphFilterFactory and both parsers are @lucene.experimental, and SynonymFilterFactory is deprecated.
  • What it takes. A synonyms file saved as UTF-8 with a byte order mark, which the 2010 CHANGES entry for the shared loader's skip describes as "often created by editors such as Windows Notepad", whose first line is a rule, or a # line with , or =>. A re-saved copy of a file that starts with the Apache license header qualifies: that header line has a comma.
  • What happens. The first rule silently stops matching its first term (missed expansions: the couch query finds 0 of 1 documents), and its other terms gain an invisible synonym that matches nothing; a first explicit mapping never fires; a commented-out first rule becomes active and adds expansions the user disabled; in WordNet format the first word loses its synonyms. With the default settings, no error or warning (with the non-default StandardTokenizerFactory as the rule tokenizer, a mark before a blank first line makes loading fail).
  • Scale. Deterministic and independent of index size: one line per file. If the filter runs at index time, terms indexed with the wrong rules stay until reindexing.
  • Versions. Every release from 3.4.0 to 10.5.2, branch_10_6 and main (10 releases executed, the rest inferred from the code).
  • How likely. Rare: a file saved with a mark is needed, only its first line goes wrong, and no public report was found in 15 years. The WordNet half is the weaker one (WordNet prolog files are machine-generated), so the Solr-format symptoms lead.
  • Workarounds. Save the file without a mark, or start it with a blank line or a comment line without , or =>.

Why it is a bug, not intended

#
  • The format says "lines starting with '#' are comments", yet a commented-out first rule becomes live.
  • Lucene's shared line loader has dropped a leading mark on purpose since 2010; the synonym factory did too until its 3.4.0 rewrite removed it without a word.
  • The equivalent hunspell change was filed under Bug fixes; nothing says synonyms files must be BOM-free.
The full argument269 words
  • The file's own comment rule. "Blank lines and lines starting with '#' are comments" (SolrSynonymParser.java:33). A user who writes #couch, sofa on line 1 sees a line that starts with #; with a mark, Lucene makes it a rule.
  • Lucene's shared line loader drops the mark on purpose. SOLR-1865 (2010) added the skip with the CHANGES entry "SolrResourceLoader.getLines ignores Byte Order Markers (BOMs) at the beginning of input files, these are often created by editors such as Windows Notepad"; LUCENE-4257 moved it into WordlistLoader.getLines (WordlistLoader.java:302-304). Every factory that reads its file through getLines or getWordSet gets it: the same resource loader and the same bytes give a different result for synonyms.
  • The synonym factory had it and lost it silently. In 3.1 to 3.3, SynonymFilterFactory read its rules with SolrResourceLoader.getLines, skip included. LUCENE-3233 (3.4.0) replaced that with a plain InputStreamReader. Its issue (41 comments), its CHANGES entries ("Improved memory usage, build time, and performance of SynonymFilterFactory"; "Added SynonymFilter ... with parsers for wordnet and solr formats") and the upgrade notes say nothing about BOM or encoding handling. Executed: 3.3.0 clean, 3.4.0 affected, 3.4.0 with luceneMatchVersion 3.3 (the old loader) clean.
  • Hunspell's equivalent was a bug fix. "LUCENE-5505: HunspellStemFilter ignores BOM markers in dictionaries" is listed under "Bug fixes" (lucene/CHANGES.txt:12543, :12554); Dictionary.java:351-352: "ignore any BOM marker on first line".
  • Valid input, no documented exclusion. A file with a mark is valid UTF-8, and the factories' strict decoder accepts it. No javadoc, test, CHANGES or MIGRATE entry says synonyms files must be BOM-free, and no synonym test uses a mark.
The devil's-advocate check290 words

The checkers built the strongest case for "intended": (a) SynonymMap.Parser.parse takes a Reader, i.e. characters, and the Solr grammar exempts only lines whose first character is #; U+FEFF is a real character (ZERO WIDTH NO-BREAK SPACE). (b) SynonymGraphFilterFactory and the parsers are @lucene.experimental. (c) Committers have said Reader-level parsers do not deal with encodings: "If you use Lucene directly, the stopword file parser does not care about encodings at all, it simply takes a java.io.Reader" (uschindler, SOLR-1860, 2010), and "if you have a byte order mark in your character input (reader) then your conversion from bytes is screwed up somewhere before" (dweiss, LUCENE-7785, 2017, about a char-filter mapping: an analogy). (d) In the 2010 user-list thread behind the skip, rmuir answered "No." to whether a file with a mark is a bug, then proposed skipping it "to be more user-friendly"; SOLR-1865 is typed Improvement. (e) Nobody reported it in 15 years.

Why we think it fails: (a) to (c) describe the Reader-level parser; users configure the factory with a file name, and the factory itself turns the bytes into characters, so by the reasoning of (c) the factory is where the mark should go (the recommended fix). (d) was about whether to handle marks at all; the project then did, in the very loader the synonym factory used until 3.4.0, and the rewrite dropped it without a word. (e) shows rarity, not intent. The cross-model reviews rated the works-as-designed case moderate (the intended-lens review: "not ultimately persuasive"; the refute-lens review: "not conclusive"), and the devil's advocate rated it weak to moderate. The literal reading (a) stays arguable: expect "improvement, not bug", and frame the issue as an unannounced 3.4.0 regression and an inconsistency with the shared loader.

Suggested fix

#

Recommended F. Skip the mark where the factories decode each file (SynonymGraphFilterFactory and SynonymFilterFactory)

Skip one leading U+FEFF where both factories decode each synonyms file (loadSynonyms), as the shared line loader does: read the first character through a PushbackReader and push it back unless it is U+FEFF. Validated: the repro, an on-disk test, all upstream synonym suites and the whole analysis-common module pass, and so does the module's format and lint check.

     for (String file : files) {
       decoder.reset();
-      parser.parse(new InputStreamReader(loader.openResource(file), decoder));
+      try (PushbackReader reader =
+          new PushbackReader(new InputStreamReader(loader.openResource(file), decoder), 1)) {
+        // skip initial bom marker, as WordlistLoader.getLines does for other resource files
+        int first = reader.read();
+        if (first != -1 && first != '\uFEFF') {
+          reader.unread(first);
+        }
+        parser.parse(reader);
+      }
     }

F. Skip the mark where the factories decode each file (SynonymGraphFilterFactory and SynonymFilterFactory) (validated by the checks) (recommended)

#

In both loadSynonyms methods (SynonymGraphFilterFactory.java:191, SynonymFilterFactory.java:194-196), wrap the decoding reader in a PushbackReader of size 1, read one character and push it back unless it is U+FEFF, then parse as before, inside a try-with-resources. +19/-4 lines over the two files (one import each; the deprecated factory drops its unused java.io.Reader import).

What it changes. Only the factory path: one U+FEFF at the very start of each synonyms file is dropped before the parser sees it, the case getLines covers for the word-list factories. It covers every parser the factory loads, including a custom SynonymMap.Parser named in format. Files without a mark are read unchanged. SynonymGraphFilterFactory now also closes each reader itself, as the deprecated factory already did; the parser's own close() makes the second close a no-op. A decoding error in the first character is now raised by the factory's read() rather than inside parse: the same MalformedInputException, an IOException, either way (read, not run).

Trade-offs

  • A direct caller of SolrSynonymParser.parse(Reader) or WordnetSynonymParser.parse(Reader) that builds its own Reader from a marked file still gets the glued term. That matches the committers' view that Reader-level parsers are encoding-agnostic, but such callers exist downstream (engines that read synonyms files with their own UTF-8 reader; checked by reading only) and would need their own skip.
  • Like getLines, it cannot tell a mark from a file whose first character is meant as a ZERO WIDTH NO-BREAK SPACE (not a realistic synonym).
  • Open PR #13054 (synonym map off-heap) rewraps loadSynonyms, so the two may conflict.
  • Indexes built with the wrong rules keep their terms until reindexed. No CHANGES entry is drafted.

#

Downstream note

#

Search servers that load synonyms files through these factories inherit it whenever an operator saves the file in an editor that writes a byte order mark; engines that pass their own UTF-8 reader to the parsers see the same (by reading their code, not run).

How it was found

#

A bounded-exhaustive metamorphic check of the real factories: every synonyms file of 1 to 3 lines over a small alphabet must analyze the same with and without a leading byte order mark. Solr format: 456 of 620 checks differed per factory; WordNet: 112 of 336; three loaders that use the shared line loader: 0.

The method in full221 words
  • First signal. On 2026-10-27 a probe in the hunt's unit on factory resource-file formats (the unit that found the snowball words-file case) printed <BOM>foo,bar : foo -> [foo] for the synonym factory and recorded it as a lead for another unit; a planning probe re-ran it (8 checks, 6 failing).
  • Method (semi-formal): bounded-exhaustive metamorphic check on the stock main jars, in the hunt's unit on synonym and user-dictionary loaders. Law: loading F and loading BOM+F give the same analysis of every probe text (terms, position increments, position lengths) or the same exception class. Inputs: every file of 1 to 3 lines over a 5-line Solr alphabet (equivalence, explicit mapping, comment with a comma, blank, multi-word) and a 4-line WordNet alphabet, with LF and CRLF line ends and expand true and false, through both synonym factories, plus three controls that read through the shared line loader (stop filter, stemmer override, mapping char filter).
  • Signal. Solr format: 456 of 620 checks mismatch for each factory (372 with a term glued to U+FEFF, 84 where a first mapping never fires); WordNet: 112 of 336 for each factory; the three controls: 0. With the parser fix shadowed, every family: 0.
  • The finder then traced it to the factories' own reader, checked the 3.4.0 history and wrote the public-API JUnit; independent checkers followed (see "Independent checks").

History

#

A regression in 3.4.0: LUCENE-3233 (015ecfa0a02, 2011-07-11) gave the synonym factory its own reader and bypassed the BOM-skipping line loader it used in 3.1 to 3.3. Executed: 3.3.0 clean, every tested release from 3.4.0 to 10.5.2 and main affected. Never fixed.

Versions tested8 rows

Introduced by LUCENE-3233 "HuperDuperSynonymsFilter" (#4306), by rmuir: trunk 015ecfa0a02 and the branch_3x backport a52015db05f, both 2011-07-11 ("LUCENE-3233: improve ram/perf of SynonymFilter, add wordnet parsing, nuke contrib/wordnet"), no PR. It added FSTSynonymFilterFactory, which passes new InputStreamReader(loader.openResource(file), decoder) straight to the new SolrSynonymParser and WordnetSynonymParser, and made SynonymFilterFactory use it for luceneMatchVersion 3.4 and later. Before, SynonymFilterFactory.loadRules read the rules with SolrResourceLoader.getLines, which had skipped a leading U+FEFF since SOLR-1865 (2010-05-08).

Reach over time. 3.4.0 to 3.6.2: Solr's factory with luceneMatchVersion 3.4 or later (the value the 3.4.0 example config ships); a lower value kept the old loader until 5.0.0 removed it. The factories moved into Lucene's own jars in 4.0.0-beta (LUCENE-4044); SynonymGraphFilterFactory (same loader) exists since 6.4.0. Bug record

LFV-956, snapshot of 2026-10-30

Registry title
SynonymGraphFilterFactory and SynonymFilterFactory keep a UTF-8 byte order mark at the start of a synonyms file, so the file's first rule silently stops working and a commented-out first line that contains a comma becomes a live rule
Area
analysis-common / synonym file loading (SynonymGraphFilterFactory and the deprecated SynonymFilterFactory loadSynonyms -> SolrSynonymParser, WordnetSynonymParser)
Priority
Low, rank 436: This is the same kept-BOM class as LFV-718 and LFV-719, but the synonym factories are the most widely used of the affected file loaders and the first rule silently stops working, so it leads the BOM rows right after LFV-857.
Impact class
silent wrong results
Impact note
Every user of SynonymGraphFilterFactory or the deprecated SynonymFilterFactory whose synonyms file was saved as UTF-8 with a byte order mark, in every release since 3.4.0 and with the factory's default settings (solr format, whitespace rule tokenizer): only the first line of each such file is affected, but there the first rule silently stops matching because its first term carries an invisible U+FEFF, a first line that starts with '#' and contains ',' or '=>' (such as the Apache license header of the example synonyms files) becomes a rule, and in WordNet format the first word leaves its synset; no error is raised, the index is not damaged and no scale is needed.
Summary
You configure SynonymGraphFilterFactory (or SynonymFilterFactory) with a synonyms file that an editor saved as UTF-8 with a byte order mark (bytes EF BB BF) and expect the same rules as from the file without the mark, because Lucene's shared resource-line loader skips a leading BOM for the word-list factories that read through it (WordlistLoader.getLines, 'skip initial bom marker', SOLR-1865) and the synonym factory itself skipped it until 3.4.0. Instead the factory decodes the file with its own UTF-8 reader and SolrSynonymParser keeps U+FEFF glued to the first line: with the first rule 'foo, bar' the text 'foo' is no longer expanded (and 'bar' gains the invisible synonym '\uFEFFfoo'), a first rule 'baz => qux' never fires, and a first line '#couch, sofa' is no longer a comment, so 'sofa' expands to '\uFEFF#couch'. In WordNet format the fixed-column synset id (substring(2, 11)) is shifted by one character, so the first word ends up in a synset of its own; nothing reports an error.
Introduced
015ecfa0a0255f053682bb2436b2b8dec5cb8283 (LUCENE-3233 'HuperDuperSynonymsFilter', apache/lucene#4306; trunk svn r1145158, author rmuir, message 'LUCENE-3233: improve ram/perf of SynonymFilter, add wordnet parsing, nuke contrib/wordnet'; no pull request, Subversion era) with the branch_3x backport a52015db05f790613906a9858531ff16e3d78b8a (r1145178), the one released in 3.4.0. The commit added FSTSynonymFilterFactory, which passes new InputStreamReader(loader.openResource(file), decoder) straight to the new SolrSynonymParser and WordnetSynonymParser, and made SynonymFilterFactory use it for luceneMatchVersion >= 3.4; before, SynonymFilterFactory.loadRules read the rules with SolrResourceLoader.getLines, which had skipped a leading U+FEFF before the '#' comment test since SOLR-1865 (f3c25f02d587, 3.x backport 7aaf7ed9a20, 2010-05-08). So this is a regression; no issue comment (body and 41 comments read), CHANGES entry or upgrade note mentions BOM or encoding handling, so the drop looks unintended (not provable).
