An un-delete with tryUpdateDocValue that returned success is dropped by the next merge while another thread's older delete is still being applied

With soft deletes, tryUpdateDocValue can un-delete a document and return success before any merge exists. If another thread is still applying an older delete, the next merge of that segment misses the un-delete and drops the document: the next commit has 0 hits for it (7.4.0 to 10.6.0, main).

The finding in 30 seconds

#

IndexWriter numbers every delete or update packet with a delete generation and tracks the highest one up to which all packets have finished. Before a merge reads its segments, it writes their pending doc-values updates to disk only up to that number. An un-delete made while an older packet is still open sits above it and is not written.

Background: soft deletes, the un-delete and delete generations

#
  1. With setSoftDeletesField("soft"), a document that has a value in the soft doc-values field counts as deleted, but it stays in its segment until a merge leaves it out. tryUpdateDocValue(reader, docID, soft = null) removes the value: the documented un-delete.
  2. Every delete or update gets a delete generation (delGen) and is applied as a packet, often by another indexing thread. IndexWriter tracks completedDelGen, the highest delGen up to which every packet has finished.
  3. Before a merge reads its segments, merge init writes their pending doc-values updates to disk, but only those with delGen <= completedDelGen. Updates above it are left for later.

The finding, step by step

#
  1. Turn on soft deletes, index a and b into one segment, soft-delete a with updateDocValues(id:a, soft = 1) and open an NRT reader: 1 of 2 documents is live.
  2. Another thread runs deleteDocuments(id:nothing). While its delete packet is still being applied, un-delete a with tryUpdateDocValue(reader, 0, soft = null). It returns 9; no merge exists yet.
  3. A merge of that segment starts. You expect a to stay live and to be in the next commit: the javadoc returns -1 only when the segment was already merged away.
  4. Instead the merge writes pending doc-values updates to disk only up to delete generation 2, the last one with no unfinished packet before it. The un-delete is generation 5, behind the other thread's still-open packet 3, so it stays in memory: the merge reads a as deleted and keeps only b.
  5. commit() returns 10, above the un-delete's 9, yet the committed index has 0 hits for a. No error. With the other thread finished first, the same steps keep a.

Who is affected

#

Applications that turn on soft deletes (off by default) and restore documents with the Expert tryUpdateDocValue null reset, without a retention policy that keeps them, while other threads delete or update concurrently. Serial and concurrent merge schedulers both lose it; 3 documents suffice. The loss is silent and survives commit. Rare: no caller found in Elasticsearch, OpenSearch or Solr.

Mechanism, terms and numbers714 words

With a soft-deletes field, IndexWriter#tryUpdateDocValue(reader, docID, <soft-deletes field = null>) is the documented way to un-delete a soft-deleted document, and its javadoc says the update succeeds (> 0) if the segment "has not been merged away", else it returns -1. If another indexing thread is at that moment still applying an older global packet (a delete by term or query, a doc-values update, softUpdateDocument), the un-delete is finished out of order: IndexWriter's completed delete generation stays below it. A merge of the document's segment that initializes next waits only for packets older than its segments, so it does not wait for that packet, and it writes pending doc-values updates to disk only up to the completed generation, so the un-delete stays in memory. The merge reads the document as soft-deleted and leaves it out, and the merge carry-over cannot re-apply the reset to a document that no longer exists. The next commit persists the loss, with no error.

In the repro the call returns 9, the merged segment keeps 1 of 2 documents, and commit() returns 10 with 0 hits for the document; without the other thread's open packet the same steps keep it. It needs the opt-in soft-deletes field, the Expert un-delete and concurrent indexing, so it is rare, but it is silent data loss of an acknowledged write since 7.4.0 (LUCENE-8298, 2018): it fails on 7.4.0, seven sampled later releases through 10.6.0 and main. Making merge init also wait for the older packet fixes the repro and keeps the core org.apache.lucene.index tests green.

The bug, step by step (main 5adff78bb168; numbers from a diagnostic copy of the repro)

#
  1. The un-delete is finished out of order. tryUpdateDocValue (IndexWriter.java:1721) takes a new delGen (bufferedUpdatesStream.getNextGen(), :1729), records the reset (:1770), adds it to the segment's pending updates (rld.addDVUpdate, :1775) and marks that delGen finished at once (finishedSegment(nextGen), :1778). It returns sequence number 9.
  2. The completed generation only moves over a gap-free run. finishedSegment advances completedDelGen while completedDelGen + 1 is finished (BufferedUpdatesStream.java:340-350). The other thread's delete packet, delGen 3, is still being applied, so the log says "finished packet delGen=5 now completedDelGen=2".
  3. Merge init does not wait for that packet. mergeInit (IndexWriter.java:5255-5258) calls waitApplyForMerge, which waits only for packets with delGen <= the merging segments' bufferedDeletesGen, because those "apply to a subset of the segments being merged" (BufferedUpdatesStream.java:178-194). The other thread's packet is newer than the segment: "waitApplyForMerge: 0 packets, 1 merging segments".
  4. Merge init writes only up to the completed generation. _mergeInit says "Must move the pending doc values updates to disk now, else the newly merged segment will not see them" and calls writeDocValuesUpdatesForMerge (IndexWriter.java:5304-5311), which passes completedDelGen as the limit (ReaderPool.java:265-276); ReadersAndUpdates.writeFieldUpdates writes only updates with delGen <= maxDelGen (:872). 5 > 2, so the un-delete stays in memory: no "now write ... pending numeric DV updates" line.
  5. The merge drops the document. The merge readers (rld.getReaderForMerge, IndexWriter.java:5487) see a's on-disk soft value, so a is deleted for the merge: merged maxDoc 1, only b.
  6. The carry-over cannot bring it back. At merge commit the reset is kept as a finished residual update (IndexWriter.java:4581-4595), but each residual is mapped through the merge's doc map and documents mapped to -1 are skipped (:4643-4645). a maps to -1.
  7. The commit persists it. commit() returns 10 and writes the merged segment without a: 2 live documents (b, and c from the other thread), 0 hits for id:a.

Control. With the other thread's packet finished before the un-delete, completedDelGen reaches 5, merge init writes "1 pending numeric DV updates for field=soft", the merged segment keeps 2 documents and the commit has 1 hit for a.

Only the un-delete is lost. A numeric update, a hard delete or a soft delete of a live document in the same window survive: the merge keeps that document and the carry-over remaps the change (devil's-advocate probe, main and 10.6.0).

What hides it. A default DirectoryReader.open(writer) inside the window waits for the in-flight packet ("waitApply: 1 packets") and writes the reset first; the document then survives the merge.

Exposure and likelihood321 words
  • Opt-in. Soft deletes are off by default (IndexWriterConfig.java:561); tryUpdateDocValue is marked "Expert" (IndexWriter.java:1708). The recorded GitHub code searches (default branches) found no caller of tryUpdateDocValue in Elasticsearch, OpenSearch or Solr.
  • What it takes. A tryUpdateDocValue null reset of a soft-deleted document while another thread's older global packet (a delete by term or query, a doc-values update, softUpdateDocument) is still being applied, then a merge of the document's segment that initializes before any default NRT reader open or commit. Concurrent deletes make such packets common; a slow delete-by-query widens the window.
  • Not a test artefact. ConcurrentMergeScheduler loses the document too, with assertions on and off. An independent test with no InfoStream hook, where the other thread's delete-by-query is slow to rewrite, fails on main and 10.6.0 while its control passes. Limit: every executed variant asks for the merge explicitly (maybeMerge() with a merge policy that merges on request); a merge picked by the default policy during ordinary indexing was not run, and it would have to start inside the same window.
  • Silent and durable. The call reports success, nothing reports the loss, and after the commit no copy of the document is left in the current commit point. The application must re-index it from its own source, if it notices.
  • Sequence numbers. commit() documents that "All sequence numbers <= this value will be reflected in the commit" (IndexWriter.java:4207-4209); here the commit is 10 and the un-delete 9.
  • How likely. Rated rare: the API is niche, and the recorded searches found no report of the loss since 7.4.0.
  • Workarounds. A SoftDeletesRetentionMergePolicy whose query keeps every document the application may un-delete (a retain-all control keeps a), or an NRT reader open right after an un-delete, before a merge of that segment can start (run); a commit at that point should work too, since it waits for all packets (IndexWriter.java:3825, by reading, not run).

Why it looks unintended

#
  • Javadoc: if the segment "has not been merged away" the call succeeds (> 0), "else, it returns -1". No merge existed; it returned 9.
  • _mergeInit's own comment: pending updates must reach disk "else the newly merged segment will not see them".
  • commit() returned 10, promising every sequence number <= 10 is reflected; the un-delete (9) is not.
The full argument290 words
  • Contract. tryUpdateDocValue (IndexWriter.java:1707-1715): "If the provided reader is an NRT reader obtained from this writer, and its segment has not been merged away, then the update succeeds and this method returns a valid (> 0) sequence number; else, it returns -1 ... This can be used to un-delete a soft-deleted document since this method will apply the field update even if the document is marked as deleted."
  • The feature's own limit. CHANGES 7.4, LUCENE-8298 (lucene/CHANGES.txt:7460-7463): "This allows to undelete a soft-deleted document unless it's been claimed by a merge." Nothing had claimed a when the call returned.
  • The invariant in the code. _mergeInit: "Must move the pending doc values updates to disk now, else the newly merged segment will not see them" (IndexWriter.java:5304-5305).
  • Sequence numbers. "All sequence numbers <= this value will be reflected in the commit, and all others will not" (IndexWriter.java:4207-4209).
  • Upstream's own use. TestSoftDeletesRetentionMergePolicy#testUndeleteDocument un-deletes with the null reset under a plain LogDocMergePolicy (the second setMergePolicy, :605, replaces the retention policy), and its helper doUpdate retries only on -1, "retry if we just committing a merge" (:781-792). No test, CHANGES entry or javadoc says a successful un-delete may later be reverted.
  • Caller-invisible condition. The outcome depends only on whether an unrelated thread's older packet has finished, which the caller can neither see nor control.
  • History. The write horizon and waitApplyForMerge come from LUCENE-7868 (2017, #8919), which planned to carry updates above the horizon over to the merged segment. That works for a value update of a document the merge keeps, not for a reset that decides whether the merge keeps it. The reset arrived a year later (LUCENE-8298) without a change to merge init.
The devil's-advocate check278 words

The strongest case for "intended": IndexWriterConfig#setSoftDeletesField still says "Currently there is no API support to un-delete a soft-deleted document. In order to un-delete a document, it must be re-indexed using softUpdateDocument" (IndexWriterConfig.java:557-559); without a retention policy any merge may reclaim soft-deleted documents, so an un-delete is best-effort; "claimed by a merge" is informal; the API is Expert; and the repro opens the window through the @lucene.internal InfoStream.

Why it fails: the IndexWriterConfig sentence came with LUCENE-8233 (main ecc17f90233, 2018-04-04), a month before LUCENE-8298 (main a3c86373e47, 2018-05-07) added the feature and the contradicting tryUpdateDocValue sentence, so it is stale (worth fixing with the bug). The CHANGES limit and the commit message's "unless it's merged away" read most naturally as a merge that claimed the document before the call; here the merge was registered afterwards, when the document was already live again, and drops it only because an unrelated packet is unfinished. Neither text formally defines that before/after boundary; the control does not depend on it (the same steps keep the document when the unrelated packet has finished). The InfoStream hook parks the other thread inside its normal in-flight interval, after its apply and before its finish (IndexWriter.java:6612). While parked it holds no IndexWriter monitor, only its own packet's apply lock (taken at :6508, released at :6681), as during a slow apply; a slow delete-by-query reaches the same state with public API only.

What a maintainer could still say: "use SoftDeletesRetentionMergePolicy if you want to restore documents". The answer: the call returned success before any merge existed, and the same steps keep the document unless an unrelated packet is in flight.

Suggested fix

#

Recommended A: merge init also waits for older packets behind a merging segment's pending updates (validated)

Make merge init also wait for in-flight packets older than a merging segment's newest pending update (+25/-3 in two files). Then completedDelGen covers the un-delete and _mergeInit writes it before the merge reads the segment. The repro passes; 14 nearby suites and the core index package (1,398 tests) stay green. Trade-off: merge init may wait behind an unrelated slow packet.

// IndexWriter.mergeInit (condensed): also wait for packets older than a merging segment's
// newest pending doc-values update, so _mergeInit can write that update first
long maxPendingGen = Long.MIN_VALUE;
synchronized (this) {
  for (SegmentCommitInfo info : merge.segments) {
    ReadersAndUpdates rld = getPooledInstance(info, false);
    if (rld != null) {
      for (List<DocValuesFieldUpdates> l : rld.getPendingDVUpdatesSnapshot().values()) {
        for (DocValuesFieldUpdates u : l) maxPendingGen = Math.max(maxPendingGen, u.delGen);
      }
    }
  }
}
bufferedUpdatesStream.waitApplyForMerge(merge.segments, this, maxPendingGen);
All options and trade-offs4 options · 736 words

Four options. A was validated by running the repro and the nearest suites in a scratch worktree of 5adff78bb168; C ran only as an experiment; B and D were not run. Each needs a real patch to also fix the stale IndexWriterConfig#setSoftDeletesField sentence.

A: merge init also waits for older packets behind a merging segment's pending updates (validated) (recommended)

#

mergeInit computes the highest delGen among the merging segments' pending doc-values updates and passes it to a new waitApplyForMerge(..., alsoBelow) overload, which also waits for every in-flight packet with delGen <= alsoBelow. Once those packets finish, completedDelGen reaches the un-delete and _mergeInit writes it to disk before the merge readers are opened, as its comment intends. The old waitApplyForMerge delegates with Long.MIN_VALUE. The scan covers every pending (not yet written) doc-values update of the merging segments, finished or added by a packet still being applied, not only un-deletes; the diff's comment names the motivating case and a real patch should word it to match the code.

// IndexWriter.mergeInit (condensed): also wait for packets older than a merging segment's
// newest pending doc-values update, so _mergeInit can write that update first
long maxPendingGen = Long.MIN_VALUE;
synchronized (this) {
  for (SegmentCommitInfo info : merge.segments) {
    ReadersAndUpdates rld = getPooledInstance(info, false);
    if (rld != null) {
      for (List<DocValuesFieldUpdates> l : rld.getPendingDVUpdatesSnapshot().values()) {
        for (DocValuesFieldUpdates u : l) maxPendingGen = Math.max(maxPendingGen, u.delGen);
      }
    }
  }
}
bufferedUpdatesStream.waitApplyForMerge(merge.segments, this, maxPendingGen);

Trade-offs

  • Waiting. Merge init can wait behind an unrelated in-flight packet, for example a slow delete-by-query, whenever a merging segment has any pending, unwritten doc-values update newer than the segment (finished or still being applied), not only an un-delete; today it waits only for packets older than the segments. Throughput impact not measured; the suites check correctness only.
  • Deadlocks. None found by reading, not proven: the extra wait uses the same waitApply path as the existing one, and mergeInit holds no IndexWriter monitor while waiting (assert Thread.holdsLock(this) == false); the scan of pending updates takes the monitor briefly before the wait. Concurrency stress tests and a maintainer's review are still needed.
  • Scope. It covers an un-delete made before merge init, not one made while the merge is already running (the sibling bug LFV-451, which stays failing with this fix).

  • This repro: fails on stock and passes with the fix, through gradle with -Ptests.asserts=true and false (seed DEADBEEF).

  • The whole core org.apache.lucene.index.* test package with the fix (assertions on): 215 suites, 1,398 tests, 56 skipped, 0 failed (gradle's own count).

B: write finished updates above the horizon at merge init (not run)

#

Let _mergeInit write a merging segment's finished pending updates even above completedDelGen, instead of waiting for the older packet.

Trade-offs

No waiting, but the horizon keeps doc-values updates reaching disk in delete-generation order relative to packets still being applied (LUCENE-7868); writing past it would need that ordering argued or re-checked. Not explored.

C: commit-time guard: abort a merge that dropped a restored document (experiment) (validated by the checks)

#

commitMerge aborts a merge that dropped a document which is live in its source's latest state (on-disk soft value, then finished pending soft-field updates in delGen order). The source segments and the un-delete then stay. It is the only option here that also covers LFV-451 (an un-delete while the merge runs).

Trade-offs

Wastes the aborted merge's work and the merge must run again; scans every merging segment's documents at merge commit when soft deletes are on; interacts with forceMerge and abort handling.

What the checks validated

Experiment only, in standalone runs with the classes shadowed: this repro passes with assertions on and off, and LFV-451's document survives in a fresh NRT reader and the commit. No suites run.

D: documentation only (not run)

#

Say in tryUpdateDocValue that an un-delete can be lost to a later merge unless a retention policy keeps the document.

Trade-offs

Cheapest, but callers who trust > 0 still lose data silently.

Downstream note

#

Products that let users restore soft-deleted records through tryUpdateDocValue while indexing concurrently can lose a restore their own API already confirmed, with no error to report.

How it was found

#

A bounded-exhaustive model-based test ran every ordered pair of 63 merge carry-over operations on the real IndexWriter, with another thread's update packet held in flight, against a reference model. The held schedule lost the un-delete in 200 of 200 runs, the unheld one in none; it was then minimised to one JUnit test.

The method in full142 words
  • Method (semi-formal). A bounded-exhaustive component model-based test of the merge carry-over on the real IndexWriter: every ordered pair over 63 operation instances in 5 merge slots, in 12 configurations, with an executable reference model compared after every step, and an actor that keeps another thread's update packet in flight. The schedule with the held packet failed 200 of 200 runs; the same schedule without the held packet passed 200 of 200.
  • Minimisation. Minimised (no automated minimiser) to a latch-driven JUnit test (two threads, no sleeps), then cut to one segment and one method with a soft-deletes-aware final count.
  • Checks. An independent reproducer wrote its own test from the claim with a different trigger (a slow delete-by-query, no InfoStream); a per-step IndexWriter trace confirmed the delete-generation numbers; a same-fix matrix separated it from LFV-451 and LFV-596 and from six open PRs.

History

#

Introduced in 7.4.0 by LUCENE-8298 (2018; branch_7x 0c65af048b3, main a3c86373e47), which added the null reset that makes an un-delete possible but left merge init writing only up to the completed generation (LUCENE-7868, 2017). The loss was run and seen on 7.4.0, seven sampled later releases through 10.6.0 and main; 7.3.1 lacks the API.

Versions tested5 rows
  • Introduced by LUCENE-8298 "Allow DocValues updates to reset a value" (#9345, a migrated JIRA issue; no GitHub PR), by Simon Willnauer: main a3c86373e47d and the branch_7x change 0c65af048b3a (the one in the 7.4.0 tag), authored 2018-05-07, committed 2018-05-09. LFV-1399, snapshot of 2026-11-10

Registry title
An un-delete through IndexWriter#tryUpdateDocValue that returned > 0 before any merge existed is dropped by the next merge of its segment when another thread's older update packet is still being applied at merge init, and the next commit persists the loss (every release since 7.4.0)
Area
index / soft deletes (tryUpdateDocValue un-delete vs. merge init behind an in-flight update packet: IndexWriter.mergeInit, BufferedUpdatesStream.waitApplyForMerge, ReaderPool.writeDocValuesUpdatesForMerge)
Priority
Medium, rank 23: A tryUpdateDocValue un-delete that returned success is silently dropped by the next merge of its segment, and the next commit makes the loss permanent, in every release since 7.4.0 and on main. Reach is narrow: it needs the opt-in soft-deletes field, the rarely used Expert un-delete API with no retention policy that keeps the document, and both the un-delete and the start of that merge must happen while another indexing thread is still applying an older delete or update, with no NRT reopen or commit in between.
Impact class
data corruption
Impact note
Hits applications that enable the opt-in soft-deletes field and restore soft-deleted documents with the Expert IndexWriter#tryUpdateDocValue (soft-deletes value null, the documented un-delete), without a retention query (SoftDeletesRetentionMergePolicy) that keeps those documents, when another of their indexing threads is still applying an older global update packet (a delete by term or query, a doc-values update, softUpdateDocument) while a merge of the document's segment initializes after the un-delete and before any default NRT open or commit: the call returns a sequence number > 0, no error follows, the merge drops the document and the next commit persists the loss, with -ea and -da, under SerialMergeScheduler and ConcurrentMergeScheduler, at ordinary scale, in every release from 7.4.0 to 10.6.0 and on main [exec].
Summary
With a soft-deletes field, you soft-delete document a, open an NRT reader and restore a with tryUpdateDocValue(reader, docID, <soft-deletes field = null>) while another thread is still applying an older delete packet; no merge exists yet, and the call returns a sequence number > 0. You expect what the javadoc promises: the update succeeded (otherwise it would have returned -1), so a stays live through any later merge and is in the next commit. Instead the merge of a's segment that starts next, while the other thread's packet is still unfinished, does not write the un-delete to disk first, reads a as deleted and drops it, so the next commit no longer contains a (count(id:a) = 0) and nothing reports an error.
Introduced
a3c86373e47 on main (which became 8.0) and its branch_7x change 0c65af048b3 (first released in 7.4.0): LUCENE-8298 'Allow DocValues updates to reset a value' (s1monw; a JIRA patch migrated as apache/lucene#9345, no GitHub PR) [read: git log -S/-L and blame in the full-history clone; no commit-level build] [exec at release level: on 7.3.1 the probe does not compile because the API is absent, on 7.4.0 it loses the un-delete]. It added the null reset that makes the un-delete possible, and a merge carry-over that applies a reset only when the document survives the merge (mappedDoc != -1), but it did not make merge init write a finished, unwritten reset before the merge reads the segment. Required ancestors in the same release: LUCENE-8297 b0b32931b28 (IndexWriter#tryUpdateDocValue, #9344) and LUCENE-8233 ecc17f90233 (soft-deletes field, #9280). The write horizon it falls through is older and unchanged in substance: LUCENE-7868 58105a203a19 (mikemccand, 2017-06-21, #8919: waitApplyForMerge waits only for packets with delGen <= the merging segments' bufferedDeletesGen, merge init writes pending doc-values updates only up to completedDelGen), with writeDocValuesUpdatesForMerge named by LUCENE-7888 eaf1d45a1ca (#8939), first released in 7.0.0; before 7.4.0 a deferred update could only target a document that survives the merge or one that stays deleted, so nothing was lost (2018-05-09 (committed on main and branch_7x; authored 2018-05-07))
