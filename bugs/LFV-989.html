The TokenStream API tutorial in the analysis package overview has seven examples that do not compile

Seven code examples in Lucene's TokenStream API tutorial, the org.apache.lucene.analysis package overview, do not compile on any release since 6.0.0: they use constructors removed in 4.4 and 5.0, subclass the final StandardAnalyzer and omit reflectWith. Documentation only: no Lucene code behaves differently, and every failure is loud.

The finding in 30 seconds

#

Lucene's core analysis package overview teaches the TokenStream API with code you are meant to copy. Most of it dates from Lucene 3 and 4; later API changes broke seven examples, and no edit since has fixed the stale calls.

Background: the analysis API in one minute

#
  1. An Analyzer turns text into tokens: a Tokenizer splits the text (WhitespaceTokenizer splits at spaces) and TokenFilters change or drop tokens (LengthFilter(source, 3, Integer.MAX_VALUE) drops tokens shorter than 3 characters). Each token carries attributes, such as its text, implemented by AttributeImpl classes.
  2. Until 4.x most of these constructors took a Version argument. Lucene 5.0 removed it (LUCENE-5859), and since 6.0 every AttributeImpl must implement reflectWith (LUCENE-6651).

The finding, step by step

#
  1. You open the org.apache.lucene.analysis package overview, where TokenStream's javadoc sends you for example code, and copy its "Adding a LengthFilter" step: new WhitespaceTokenizer(matchVersion) and new LengthFilter(true, source, 3, Integer.MAX_VALUE).
  2. You expect it to compile and print what the page shows: the input "This is a demo of the TokenStream API" without the words of 2 or fewer characters.
  3. Instead javac rejects both lines: WhitespaceTokenizer lost its Version constructor in 5.0, and LengthFilter's only constructor is now (TokenStream, int, int); the page's (true, source, ...) form went in 4.4.
  4. All seven examples fail to compile: besides these two calls, StandardAnalyzer(Version) is gone, StandardAnalyzer is final, the LengthFilter listing calls the removed super(version, in), and the custom attribute does not implement reflectWith. Every release since 6.0.0 ships all seven broken.
  5. Rewritten against today's API (no Version argument, a small Analyzer instead of a StandardAnalyzer subclass, reflectWith, a final tagging filter), all seven compile, and the tutorial prints its outputs, such as This demo the TokenStream API.

Who is affected

#

Everyone who learns to write an Analyzer, TokenFilter or Attribute from this page and copies an example: javac rejects it, with no setting involved. A 2016 Stack Overflow question shows a user hitting example 1. The errors are loud and at compile time, and no Lucene code behaves differently; the cost is developer time.

Mechanism, terms and numbers505 words

The org.apache.lucene.analysis package overview (core package-info.java) is Lucene's tutorial for writing analyzers, token filters and attributes, and TokenStream's javadoc points readers to it for example code. Seven of its examples do not compile on main or on any release since 6.0.0: they call StandardAnalyzer(Version), WhitespaceTokenizer(Version) and FilteringTokenFilter(Version, TokenStream), removed in 5.0, and new LengthFilter(true, source, 3, Integer.MAX_VALUE), a signature gone since 4.4; one subclasses StandardAnalyzer, which is final; and the custom PartOfSpeechAttributeImpl lacks reflectWith(AttributeReflector), abstract since 6.0. The APIs changed on purpose, and no edit of the page since has fixed the stale calls. Written against the current API (no Version argument, new LengthFilter(source, 3, Integer.MAX_VALUE), a small Analyzer instead of a StandardAnalyzer subclass, a reflectWith method, and a final tagging filter so the tutorial also runs with assertions on), every example compiles and the tutorial prints the page's outputs.

Why it looks unintended

#
  • The page presents runnable code ("In this example we will create a WhiteSpaceTokenizer ...") and prints each step's output; there is no disclaimer.
  • Each break is a deliberate API change that left the calls stale: LUCENE-1987/2372 (3.x), LUCENE-4963, LUCENE-5859, LUCENE-6651 (its MIGRATE note requires reflectWith).
  • No Version value makes the removed constructors exist, and nobody can subclass a final class.
The full argument274 words
  • The page presents working code. "In this example we will create a WhiteSpaceTokenizer and use a LengthFilter to suppress all words that have only two or fewer characters" (package-info.java:597-598); "In this easy example a simple white space tokenization is performed. ... Here is the output:" (:647-649); "Now let's take a look at how the LengthFilter is implemented:" (:689). No "pseudo-code" or "illustrative" disclaimer anywhere on the page.
  • Deliberate API changes that left the example calls stale. LUCENE-5859 (9938a39a872, 2014, "Remove Version from Analyzer constructors") did not touch it. LUCENE-4963 (8a7f2b6cc45, 2013) edited the page's listings but left both LengthFilter(true, ...) calls. LUCENE-6651 (4accc254774, 2015) made reflectWith abstract; its MIGRATE entry: "If you have implemented your own attribute, make sure to add the required method sigature [sic]. See the Javadocs for an example."
  • No later edit fixed the stale calls. LUCENE-5392 (2b822c846a8, 2014-01-10) rewrote the three whitespace calls to new WhitespaceTokenizer(matchVersion), which matched trunk's API at the time, before LUCENE-5859 removed that constructor; later commits such as LUCENE-7318 (2016, the page's StandardAnalyzer link), #36 (2021, an enum modifier in the custom-attribute example) and LUCENE-9570 (reformatting) left the stale calls as they were; the last three (#14199, #14734, #15573, the last on 2026-01-15) are typo, grammar and markup fixes.
  • Precedent. Upstream fixes stale javadoc examples: LUCENE-9046 (TermInSetQuery) and #16385 (per its CHANGES entry, the grouping package info) were merged; #16821 and #16823 (open issues) and #16904 (an open PR) report the same kind of defect in other package docs; LUCENE-8488 (#9534, open) asks for javadoc examples to be compiled.
The devil's-advocate check132 words

The strongest case: these are illustrative fragments without imports; Version.LUCENE_XY is an explicit placeholder that tells the reader to adapt the code; and in 2012, on #4740 (LUCENE-3666), Uwe Schindler (in an IRC log posted there) advised leaving reflectWith out to keep the attribute example minimal ("too much information", "a minimum example would be ideal").

Why it fails: a reader adds missing imports and the code compiles, but no import and no Version value makes the removed constructors exist, and a final class cannot be subclassed. reflectWith was optional only while AttributeImpl had a reflection-based default; LUCENE-6651, also by Uwe Schindler, removed it, and its MIGRATE note requires the method. The page prints the output its code should produce. All verifiers and the adjudication rejected the intended-behaviour case. Verdict: a documentation defect.

Suggested fix

#

Recommended A. Rewrite the seven examples against the current API (javadoc only)

Rewrite the seven examples against today's API: drop Version; new StandardAnalyzer(), new WhitespaceTokenizer(), new LengthFilter(source, 3, Integer.MAX_VALUE); a small Analyzer for the gap example; super(in); add reflectWith; make the tagging filter final. Validated: the fixed page compiles, runs with -ea and prints its outputs; format, lint, javadoc and the core analysis tests pass.

Trade-offs

  • Javadoc only, so no Lucene code changes.
  • The gap example no longer shows StandardAnalyzer itself. With the default settings its index-time tokens are the same as StandardAnalyzer()'s, but it is not the same class: no setMaxTokenLength (both default to 255), no StopFilter (the default stop set is empty) and no normalize override, which matters only for query-time normalization. Replies on LUCENE-3055 (#4128) by Robert Muir and Uwe Schindler recommend writing your own Analyzer instead of subclassing StandardAnalyzer.

LFV-989, snapshot of 2026-11-05

Registry title
The org.apache.lucene.analysis package overview (the TokenStream API tutorial) has seven code examples that do not compile on any release since 6.0: they call StandardAnalyzer(Version), WhitespaceTokenizer(Version) and FilteringTokenFilter(Version, TokenStream), removed in 5.0, and LengthFilter(boolean, TokenStream, int, int), gone since 4.4, subclass the final StandardAnalyzer, and define a custom AttributeImpl without reflectWith, abstract since 6.0 (documentation defect)
Area
core / analysis (org.apache.lucene.analysis package overview, package-info.java: the TokenStream API tutorial)
Priority
Low, rank 1184: The core analysis tutorial's seven examples fail loudly at compile time with no runtime effect, and it is the most-read of the pages with broken examples.
Impact class
minor
Impact note
Documentation only, with no runtime effect: anyone who learns the TokenStream API from the core analysis package overview and copies one of its examples (the analysis workflow, the position-gap analyzer, the whitespace analyzer, adding a LengthFilter, the LengthFilter listing, the custom part-of-speech attribute, the final part-of-speech chain) gets compile errors and has to rewrite it against the current constructors; no configuration, scale or special input is involved, and all seven examples have been broken together in every release since 6.0.0 (the oldest one since 3.0.0).
Summary
You open the org.apache.lucene.analysis package overview, Lucene's tutorial for writing analyzers, token filters and attributes, and copy one of its examples, expecting it to compile as shown (the page even prints the output the code should produce). Seven examples do not compile on main or on any release since 6.0.0: they call StandardAnalyzer(Version), WhitespaceTokenizer(Version) and FilteringTokenFilter(Version, TokenStream), all removed in 5.0, and new LengthFilter(true, source, 3, Integer.MAX_VALUE), a signature gone since 4.4; one subclasses StandardAnalyzer, which is final; and the custom PartOfSpeechAttributeImpl lacks reflectWith(AttributeReflector), which has been abstract since 6.0. The APIs changed on purpose and the page was never updated: written against the current API (no Version argument, LengthFilter(source, 3, Integer.MAX_VALUE), a custom Analyzer or AnalyzerWrapper instead of a StandardAnalyzer subclass, and a reflectWith method) every example compiles.
