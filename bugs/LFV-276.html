All bugs · Lucene bug · LFV-276 · offsetsfromtokens-ignores-multiterm-queries

MatchRegionRetriever's default OffsetsFromTokens strategy ignores consumeTermsMatching, so multi-term queries get no hit regions on fields without positions

On a field indexed without positions (for example a stored StringField), MatchRegionRetriever and MatchHighlighter find no hit region for prefix, wildcard, regexp, range and multi-term set queries (unless the query names a single term), although the document matches: ba* on foo bar gives {} instead of [4,7). Search results are correct; every release since 9.0.0 is affected.

The bug in 30 seconds

#

Without positions, the highlighter re-analyzes the stored values and keeps the tokens whose terms the query names. A term query names its term (consumeTerms). A prefix or wildcard query instead hands over an automaton that describes its terms (consumeTermsMatching), and OffsetsFromTokens never listens on that channel, so it keeps nothing.

  1. You index one document whose stored field tags holds foo bar, indexed without positions (DOCS_AND_FREQS; every StringField has no positions either), and search PrefixQuery(tags:ba): 1 hit, doc 0.
  2. You ask MatchRegionRetriever (or MatchHighlighter), with its default strategies, where the match is. Without positions it re-analyzes foo bar into foo [0,3) and bar [4,7) and keeps the tokens whose terms the query reports.
  3. You expect {tags=[[4,7)]}: TermQuery(tags:bar), FuzzyQuery(baz~1), the same prefix with SCORING_BOOLEAN_REWRITE, and the same prefix on a field with positions all give that.
  4. Instead you get {}, no hit region, and MatchHighlighter treats the field as unmatched (with skipRemaining() it drops it). The same for WildcardQuery(b?r), RegexpQuery(ba.), TermRangeQuery [b TO c] and the two-term TermInSetQuery(bar, qux). Hits and scores are correct.
  5. Why: the default strategy, OffsetsFromTokens, listens only to QueryVisitor#consumeTerms. These queries report their terms as an automaton through consumeTermsMatching, so its term set stays empty and no token is kept.

Who is affected

#

Applications that highlight a field without positions (a stored StringField, or any DOCS, DOCS_AND_FREQS or DOCS_AND_CUSTOM_FREQS field) with MatchRegionRetriever or MatchHighlighter and their default strategies, and run prefix, wildcard, regexp, range or multi-term set queries on it. It hits every such query (unless it names a single term) on every matching document, since 9.0.0; search results are unaffected.

Mechanism, terms and numbers722 words

For a field indexed without positions (DOCS, DOCS_AND_FREQS or DOCS_AND_CUSTOM_FREQS, for example a stored StringField), MatchRegionRetriever and the MatchHighlighter built on it use OffsetsFromTokens by default: it re-analyzes the stored values and keeps the tokens whose terms the matching query reports to a QueryVisitor. Its visitor overrides only consumeTerms. Constant-score multi-term queries report their terms through consumeTermsMatching (an automaton): PrefixQuery, WildcardQuery, RegexpQuery and TermRangeQuery with their default rewrite whenever their automaton accepts more than one term (a degenerate one that names a single term reports it through consumeTerms and highlights), and TermInSetQuery with two or more distinct terms. So the term set stays empty and the field gets no hit region, although the document is a hit and Weight#matches reports a match on that field. The outcome depends on how a query reports its terms, not on what matched: a one-term TermInSetQuery is highlighted and a two-term one is not; PrefixQuery with SCORING_BOOLEAN_REWRITE is highlighted and with the default rewrite it is not. Search results are correct; only the hit regions are missing. Depending on its chain, MatchHighlighter then omits the field, shows it unhighlighted or throws. Present since the package was added (9.0.0). The fix collects the consumeTermsMatching automata for the field too, once per distinct query.

Terms

#
  • Hit regions: MatchRegionRetriever returns, per document and field, the character ranges (OffsetRange) that the query matched; MatchHighlighter turns them into snippets. For each field it picks an offset strategy from the field's index options (MatchRegionRetriever.java:488-505).
  • OffsetsFromTokens: the default strategy for fields indexed DOCS, DOCS_AND_FREQS or DOCS_AND_CUSTOM_FREQS (no positions; every StringField is DOCS). It re-analyzes the stored values and keeps the tokens whose terms the query "hinted at when passed a QueryVisitor" (:498-501).
  • QueryVisitor's two channels: consumeTerms is "Called by leaf queries that match on specific terms"; consumeTermsMatching is "Called by leaf queries that match on a class of terms" and passes an automaton (QueryVisitor.java:33-51).

The bug

#
  1. highlightDocument asks weight.matches(...) (MatchRegionRetriever.java:405), skips a field only when its MatchesIterator is null or MATCH_WITH_NO_TERMS (:411-416), calls the strategy (:434), and drops the field when the strategy returns no ranges (:435-437).
  2. With their default rewrite (CONSTANT_SCORE_BLENDED_REWRITE, PrefixQuery.java:32-34; also the classic query parser's default, QueryParserBase.java:83-84), PrefixQuery, WildcardQuery, RegexpQuery, TermRangeQuery and TermInSetQuery match through a constant-score wrapper whose matches() returns DisjunctionMatchesIterator.fromTermsEnum(context, doc, q, ...) (AbstractMultiTermQueryConstantScoreWrapper.java:203-212): every sub-match's getQuery() is the multi-term query itself (DisjunctionMatchesIterator.java:94, 132, TermMatchesIterator.java:73-75).
  3. Visited, that query reports through consumeTermsMatching: AutomatonQuery.visit delegates to CompiledAutomaton.visit (AutomatonQuery.java:150-154), which uses consumeTermsMatching for NORMAL and ALL automata and consumeTerms only for a SINGLE term (CompiledAutomaton.java:365-382); TermInSetQuery uses consumeTerms for 1 distinct term and consumeTermsMatching for 2 or more (TermInSetQuery.java:182-187). So a degenerate automaton query that accepts exactly one term (WildcardQuery(lucene) without wildcard characters, RegexpQuery(lucene), TermRangeQuery [lucene TO lucene]) does highlight, while the match-all WildcardQuery(*) does not (executed).
  4. OffsetsFromTokens.get visits each match's getQuery() with a visitor that overrides only consumeTerms (OffsetsFromTokens.java:56-70) and keeps a token only if matchTerms.contains(...) (:82). The set stays empty, no token is kept, and step 1 drops the field.

Why the controls work: a TermQuery reports consumeTerms; SCORING_BOOLEAN_REWRITE and FuzzyQuery's default rewrite end in TermQuery clauses; a field with positions uses OffsetsFromPositions (MatchRegionRetriever.java:492-493), which uses the match positions instead of the term set.

Exposure and likelihood287 words
  • Who. Users of the matchhighlight package (MatchRegionRetriever with its default strategies, or MatchHighlighter) who highlight a field indexed without positions, typically a keyword-style StringField (the upstream test calls such fields "often useful for multivalued 'keyword-like' fields", TestMatchRegionRetriever.java:686), and run a prefix, wildcard, regexp, term-range or multi-term set query on it.
  • Default vs opt-in. Nothing to opt into: the default-strategy constructors (MatchRegionRetriever.java:107-109, MatchHighlighter.java:187-192), a field without positions, and a multi-term query with its default rewrite, which is also what the classic query parser builds for tag:luc* (read). TermInSetQuery with two or more distinct terms reaches this defect from 9.6.0 (before that, sets of up to 16 terms were rewritten into term clauses and highlighted, while larger sets lost their regions by another route; see History), DOCS_AND_CUSTOM_FREQS fields from 10.5.0.
  • Effect. Silent missing highlights; hits, counts and scores are correct and the Matches API reports the match. In MatchHighlighter the field takes the application's no-match path: omitted with skipRemaining(), shown as leading text with maxLeadingCharacters(...), and with no no-match highlighter in the chain the call throws RuntimeException: No field highlighter could be matched to field (MatchHighlighter.java:301-308), as stock Lucene already does for a queried field without a match (executed on main and 10.5.2).
  • Scale. Deterministic, with assertions on and off, at any index size: one document is enough, and it fails on every document such a query returns.
  • How likely. Rare: GitHub code search found the package used in none of Solr, Elasticsearch and OpenSearch (partly rate-limited; that says nothing about use elsewhere); TextField, the usual full-text field, is indexed with positions (TextField.java:36, 40) and is not affected; the searches made found no report since 9.0.0.

Why it is a bug, not intended

#
  • The package promises "hit areas for a given Query"; the default strategy keeps the terms the query "hinted at" via a QueryVisitor, and consumeTermsMatching is how these queries hint.
  • The answer follows the reporting channel, not the match: a 1-term TermInSetQuery highlights, a 2-term one does not.
  • LUCENE-9462 gave these queries matches on such fields; the UnifiedHighlighter honours that channel.
The full argument331 words
  • Contract. Package javadoc: MatchRegionRetriever "can be used to retrieve hit areas for a given Query" (package-info.java:22-23); class javadoc: "compute a list of 'match regions' for a given query" (MatchRegionRetriever.java:57-58); OffsetsFromTokens "works for fields where we know the match occurred" (OffsetsFromTokens.java:35-36); the default-strategy comment keeps the terms "that the query hinted at when passed a QueryVisitor" (MatchRegionRetriever.java:498-501); consumeTermsMatching is for "leaf queries that match on a class of terms" (QueryVisitor.java:42).
  • The channel decides, not the match. On the same document, a 1-term TermInSetQuery highlights and a 2-term one (equivalent to a TermQuery disjunction that does highlight) does not; the default and the scoring rewrite of the same PrefixQuery disagree (executed). TermInSetQuery moved to consumeTermsMatching for a performance reason (LUCENE-9349: "to enable queries that build large automata to provide them lazily", CHANGES.txt:5695-5698).
  • The Matches change was made for this path. LUCENE-9462, "Fields without positions should still return MatchIterator" (CHANGES.txt:4700-4701; 6244383e0d5, same day and authors as the component, an ancestor of it), removed the hasPositions() == false fallback from TermQuery, SynonymQuery and the multi-term constant-score wrapper, so that these queries, multi-term ones included, return real matches iterators on these fields.
  • Sibling and goal. The UnifiedHighlighter in the same module consumes consumeTermsMatching (uhighlight/MultiTermHighlighting.java:82-85). The umbrella issue #10501 / LUCENE-9461 asked that "highlights should be accurate for all sorts of queries: fuzzy, phrase, prefix, Boolean, spans, etc."
  • Tests and history. Upstream tests run prefix, range and fuzzy queries only on fields with positions (TestMatchRegionRetriever.java:219-291) and the no-positions field only with a TermQuery (:683-707). No javadoc, test, CHANGES or MIGRATE entry, or design thread (#10479 / LUCENE-9439, apache/lucene-solr#1721, LUCENE-9461 to 9464) says multi-term queries are unsupported here; consumeTermsMatching (2019) predates the component (2020).
  • Legal trigger. Public API, the default-strategy constructor, a query rewritten against the searcher, an analyzer that reproduces the indexed tokens (as the constructor javadoc requires, MatchRegionRetriever.java:115-117), ordinary queries with their default rewrites.
The devil's-advocate check272 words

The strongest "works as designed" case (the cross-model review, the intended-behaviour check, the refute review): the OffsetsFromTokens javadoc says it returns tokens "that are also returned by the query's term collector" (OffsetsFromTokens.java:38-39), and QueryVisitor.termCollector collects consumeTerms only (QueryVisitor.java:86-98); consumeTermsMatching is @lucene.experimental; MatchHighlighter calls itself "An example highlighter" and advises assembling your own (MatchHighlighter.java:38-43); the default-strategy comment says "possibly" and names alternative strategies (MatchRegionRetriever.java:498-504); in the design review the author wanted the no-positions path minimal, a corner case.

Why it fails: the javadoc phrase does not name termCollector and the code does not call it; termCollector's own javadoc promises "all terms that may match a query" (QueryVisitor.java:87), so its blindness to automata is a gap, not a documented exclusion. The strict reading makes the output depend on the rewrite method and on the number of terms in a set, which points to an accidental dependency on the reporting channel rather than a design choice (no design statement says either way). @lucene.experimental is about API stability, and the example status of MatchHighlighter does not cover MatchRegionRetriever's default strategy. No reviewer found the intended case convincing: the adjudication and the cross-model lenses rated it moderate, the intended-behaviour check found that it does not hold up, and the independent reproduction noted only that maintainers might file the fix as an improvement.

What it does not settle: maintainers may still label the fix an improvement rather than a bug fix (judge confidence medium). Framing it as "the default fallback ignores consumeTermsMatching" and leading with the two inconsistency pairs pre-empts the "term collector" reading.

Suggested fix

#

Recommended Also honour consumeTermsMatching, once per distinct query (validated)

In OffsetsFromTokens, also collect the consumeTermsMatching automata for the field, visiting each distinct match query once, and keep tokens that any of them accepts (+34/-3). The repro, the hunt's tests and the whole highlighter module (728 tests) pass; lint, format and javadoc pass. Without the deduplication the cost explodes (112.6 s for one document).

Set<Query> visited = Collections.newSetFromMap(new IdentityHashMap<>());
while (matchesIterator.next()) {
  Query q = matchesIterator.getQuery();
  if (visited.add(q) == false) continue; // a multi-term query repeats itself per term
  q.visit(new QueryVisitor() {
    // consumeTerms(...) unchanged: adds exact terms to matchTerms
    @Override
    public void consumeTermsMatching(Query query, String queryField, Supplier<ByteRunnable> automaton) {
      if (field.equals(queryField)) matchAutomata.add(automaton.get());
    }
  });
}
// per re-analyzed token:
if (matchTerms.contains(token) || acceptedByAny(matchAutomata, token)) { ranges.add(...); }

Trade-offs

  • Cost. Each re-analyzed token of the field is tested against the distinct automata of the query on that field (one per multi-term clause), the same order as the UnifiedHighlighter's multi-term highlighting (read; not benchmarked with many distinct clauses). The security probe's cost case, one document with 20,000 values in a DOCS field, half matching, WildcardQuery(a*z) over 32-character tokens: stock 51 ms, this fix 59 ms (best of 3, shared loaded host, orders of magnitude only).
  • Limits (read). The deduplication works within one get(...) call, so once per document and field; nothing is cached across documents. An automaton query's supplier returns the automaton it already compiled (CompiledAutomaton.java:369, 486-492), but TermInSetQuery's builds a new automaton over the whole term set on every call (TermInSetQuery.java:186, 190-195, "pretty heavy-weight" in its own comment), so a large set pays that once per highlighted document. Deduplication is by object identity: Lucene's wrapper passes one query object to every term match, but a custom MatchesIterator returning new, equal query objects would not be deduplicated. The visitor keeps the default acceptField; overriding it would skip other fields' clauses earlier.
  • Why the deduplication matters. The hunt's first draft added the automaton on every matchesIterator.next() (once per matching term) and ran every copy against every non-matching token: 112,571 ms on that same document. Do not propose the draft as is.
  • Tokens are still matched only if the re-analysis analyzer reproduces the indexed terms, as before.

Downstream note

How it was found

#

A bounded-exhaustive translation-validation harness compared MatchRegionRetriever on a field indexed DOCS with every occurrence of the query's terms, over 1,295 enumerated documents and a 121-query catalogue on the stock jars. 8,720 of 11,280 multi-term checks came back empty, for all 7 constant-score queries; the finder then wrote a public-API JUnit.

The method in full158 words

Method: bounded-exhaustive translation validation on the real jars (semi-formal tier), in a hunt unit on highlighter offset sources.

  • A harness compared the highlighters' offset sources with an exact reference semantics and the Matches API on every document of a small enumerated document language (1,295 single-valued documents of up to 4 positions) and a 121-query catalogue, on the stock main jars. Introduced by 150a8dacb59 (LUCENE-9463 "Query match region retrieval component, passage scoring and formatting", apache/lucene-solr#1750, author dweiss, merged 2020-08-14), which added OffsetsFromTokens with its consumeTerms-only visitor as the default for DOCS and DOCS_AND_FREQS fields; later commits only reformatted or refactored it (6faa4f98e04, 2c1f9381390, 755de5aae33 / #12881). The companion 6244383e0d5 (LUCENE-9462, same day, an ancestor) gave multi-term queries real matches iterators on fields without positions; the symptom needs both. consumeTermsMatching is older (bed694ec881, LUCENE-9062, 2019-11-27).

Variants. From 9.6.0 every TermInSetQuery with two or more distinct terms reaches the defect, since #12156 (3809106602a, backport fa1d050df1d) made it a MultiTermQuery. Before that its visit already used consumeTermsMatching for two or more terms, but sets of up to 16 terms were rewritten into TermQuery clauses and highlighted (executed: the two-term case on 9.5.0 and 9.0.0), while larger sets stayed a TermInSetQuery whose matches() on a field without positions fell back to MATCH_WITH_NO_TERMS, so they lost their regions by another route (read: 9.5.0 TermInSetQuery.java:79, 115-128, 242-246, Weight.java:78-94). The 9.6.0 change of the default rewrite (#12055) left the prefix, wildcard, regexp and range outcomes unchanged (executed). Other variants: DOCS_AND_CUSTOM_FREQS fields in 10.5.0 (#15584, read). Not fixed on main or branch_10x; no open PR touches the file; branch_10_6 (10.6.0, unreleased) is source-confirmed affected but not executed: the same consumeTerms-only visitor and switch (2763db11b0a, 2026-10-24).

Bug record

LFV-276, snapshot of 2026-10-29

Registry title
MatchRegionRetriever's default OffsetsFromTokens strategy ignores QueryVisitor#consumeTermsMatching, so prefix, wildcard, regexp, term-range and multi-term TermInSetQuery matches on fields without positions get no hit regions
Area
highlighter / matchhighlight (MatchRegionRetriever default offset strategy OffsetsFromTokens for fields indexed without positions; MatchHighlighter on top of it)
Priority
Medium, rank 259: It is deterministic and highlighting-only (no hit regions for prefix, wildcard, range and set queries on position-less fields), and the matchhighlight package has no known major downstream user, so it ends the highlighting rows.
Impact class
silent wrong results
Impact note
Applications on 9.0.0 through 10.5.2 or main that highlight with MatchRegionRetriever or MatchHighlighter and its default offset strategies a field indexed without positions (DOCS, DOCS_AND_FREQS or DOCS_AND_CUSTOM_FREQS, for example a stored StringField re-analysed with a keyword analyzer) silently get no hit regions for that field whenever the query reaches it as a default-rewrite PrefixQuery, WildcardQuery, RegexpQuery or TermRangeQuery, or (from 9.6.0) a TermInSetQuery with two or more terms; only highlighting is affected (hits, counts and scores are correct and the Matches API reports the match), it is deterministic at any index size with -ea and -da, and the matchhighlight package is far less used than the UnifiedHighlighter (code search found it in none of Solr, Elasticsearch and OpenSearch).
Summary
You index a stored field without positions (one document 'foo bar', IndexOptions DOCS_AND_FREQS, or a StringField), run a PrefixQuery('ba') that matches it, and ask MatchRegionRetriever (or MatchHighlighter) with its default strategies for the hit regions; you expect the region [4,7) for 'bar', which a TermQuery('bar') on the same field, a FuzzyQuery('baz'~1) and the same PrefixQuery on a field with positions all give. Instead the field gets no hit regions at all ({}), although the document is a hit and Weight#matches reports a match on that field. The default strategy for such fields, OffsetsFromTokens, collects the query's terms only through QueryVisitor#consumeTerms, while constant-score multi-term queries report theirs through consumeTermsMatching, so its term set stays empty and no re-analysed token is kept.
Introduced
150a8dacb59712c731e66db1a56068326a0439f4 (LUCENE-9463 'Query match region retrieval component, passage scoring and formatting', apache/lucene-solr#1750, author dweiss, merged 2020-08-14) [read: git log --follow and git blame in the full-history clone; exec: fails on 9.0.0, does not compile on 8.6.1 and 8.11.4]. It added OffsetsFromTokens with a QueryVisitor that overrides only consumeTerms and made it the default for DOCS and DOCS_AND_FREQS fields; the visitor is unchanged on main apart from reformatting (6faa4f98e04) and refactors (2c1f9381390, 755de5aae33). The symptom also needs the companion commit 6244383e0d5 (LUCENE-9462, apache/lucene-solr#1749, same author, same day, an ancestor of 150a8dacb59), which made constant-score multi-term queries return real MatchesIterators on fields without positions; QueryVisitor#consumeTermsMatching predates both (bed694ec881, LUCENE-9062, 2019-11-27). The TermInSetQuery form starts with #12156 (3809106602a, backport fa1d050df1d, 9.6.0), which made TermInSetQuery a MultiTermQuery. Not a regression (2020-08-14)
