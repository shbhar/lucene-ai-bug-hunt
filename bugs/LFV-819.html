The bug in 30 seconds

#

ASCIIFoldingFilter replaces each non-ASCII character using one big switch of case labels; a character without a label is copied unchanged. The table folds the Latin ligatures ﬀ ﬁ ﬂ ﬃ ﬄ and ﬆ and the long s ſ, but has no label for ﬅ U+FB05, whose Unicode decomposition is "st" like ﬆ's.

  1. You index three documents that spell "fast" three ways, "faſt" (long s ſ), "faﬆ" (ligature ﬆ, U+FB06) and "faﬅ" (ligature ﬅ, U+FB05), with StandardTokenizer, LowerCaseFilter and ASCIIFoldingFilter at index and query time. A user types "fast".
  2. You expect 3 hits: Unicode decomposes both ligatures to "st", and the filter already folds ſ to s and ﬆ to st.
  3. The fold table has a case for every Latin ligature from U+FB00 to U+FB06 except ﬅ, so ﬅ is copied unchanged: "faſt" and "faﬆ" are indexed as fast, "faﬅ" as faﬅ.
  4. The query "fast" finds 2 of 3 documents, with no error. preserveOriginal=true also gives 2 of 3: nothing was folded, so no extra token is added.

Who is affected

#

Applications that add ASCIIFoldingFilter (opt-in; no Lucene analyzer includes it) and whose text contains the precomposed ligature ﬅ, mostly transcriptions of early-modern printing or text extracted from documents set with historical ligatures. There every word with ﬅ is silently missed by ASCII queries, in every release since 2.9.0.

Mechanism, terms and numbers691 words

ASCIIFoldingFilter converts non-ASCII characters "into their ASCII equivalents, if one exists", and its javadoc lists the Alphabetic Presentation Forms block. Its table folds every Latin ligature of that block, ﬀ ﬁ ﬂ ﬃ ﬄ (U+FB00-FB04) and ﬆ (U+FB06 to st), and the long s ſ (U+017F to s), but it has no case label for ﬅ U+FB05 LATIN SMALL LIGATURE LONG S T, whose Unicode compatibility decomposition (NFKD) is "st" like U+FB06's. ﬅ therefore falls to the default: branch and is copied unchanged: "faﬅ" is indexed as faﬅ, and the ASCII query "fast" finds the documents spelled "faſt" and "faﬆ" but not "faﬅ", with no error. The table never had the entry (LUCENE-1390, 2008), so every release from 2.9.0 to 10.5.2 and main is affected. For users of the filter it replaced it was an unnoticed regression: ISOLatin1AccentFilter folded U+FB05 (to ft), and U+FB05 is the only one of its 72 mappings that ASCIIFoldingFilter lacks. The fix is one case label plus the matching entry of the generated test; it changes indexed terms for text with ﬅ.

Terms

#
  • The fold table: foldToASCII(char[], int, char[], int, int) (public static, tagged @lucene.internal, ASCIIFoldingFilter.java:188-190) is one switch (c) (:200). Each block lists case labels, each with a comment // <char> [UNICODE NAME], and then writes the output characters. incrementToken() (:105) calls it through foldToASCII(char[], int) (:122, :146) for every token that has a character at or above U+0080.
  • NFKD: the Unicode compatibility decomposition. It turns ﬆ and ﬅ into "st" and ſ into "s" (the JDK's java.text.Normalizer).

How a search misses

#
  • With StandardTokenizer, LowerCaseFilter and ASCIIFoldingFilter at index and query time, "faſt" and "faﬆ" are indexed as fast and "faﬅ" as faﬅ. The query "fast" (body:fast) counts 2 of 3 documents; the query "faﬅ" still finds the third.
  • preserveOriginal=true adds the original token only when folding changed it (needToPreserve, :166). For "faﬅ" nothing changed, so the index still holds only faﬅ, and "fast" again finds 2 of 3.
  • The CustomAnalyzer chain "standard", "lowercase", "asciiFolding" gives the same 2 of 3.

How isolated the gap is

#

An exhaustive fold of all 65,536 BMP code units through the stock jar took, in the 16 blocks the javadoc lists, every letter or digit whose NFKD (nonspacing marks removed) is ASCII: 631 code points, 583 folded, 48 not. 47 of the 48 have an explanation other than an oversight. 39 are whole classes the table never covers: 2 ordinal indicators (ª º) and 37 MODIFIER LETTER forms (the table has no ORDINAL or MODIFIER LETTER entry). 8 are subscripts U+2095-209C, added in Unicode 6.0 (2010), after the table was generated from "the Unicode 5.1 version of UnicodeData.txt" in 2008; the older subscripts U+2090-2094 are folded (:272, :273, :540, :1058, :1490). U+FB05 is the only gap that already existed when the table was made (Unicode 1.1, like U+FB06) and has a folded sibling of the same shape in its block. An independent scan of U+FB00-FB4F finds U+FB05 as the only unfolded letter there with an ASCII NFKD.

Exposure and likelihood233 words
  • Who is exposed. Analysis chains that use ASCIIFoldingFilter: built by hand, with CustomAnalyzer, or through the asciiFolding SPI factory; no analyzer shipped with Lucene includes it. The text (documents or queries) must contain the precomposed ligature ﬅ U+FB05.
  • Which text. U+FB05 appears mainly in transcriptions and digitizations of early-modern long-s printing and in text extracted from documents set with historical ligatures. Ordinary text writes "st" with two letters or uses U+FB06.
  • Effect. Deterministic for every token that contains ﬅ: the ASCII query term (fast) does not match the indexed term (faﬅ), while the same word written with ﬆ or ſ is found. A query that itself contains ﬅ still matches. No exception, no index damage, nothing in the logs.
  • Settings. Assertions on or off make no difference, and preserveOriginal=true does not help.
  • How likely. Rare: nobody has reported it in the 17 years since 2.9.0. But systematic in collections where the ligature occurs.
  • Also affected. Code that calls the public static foldToASCII(...) directly (tagged @lucene.internal, so not a supported contract), and the copies of the table outside Lucene (see the downstream note).
  • Workarounds today. ICUFoldingFilter instead of ASCIIFoldingFilter, or core CaseFoldingFilter (new in the unreleased 10.6.0; it maps U+FB05 to U+FB06) in front of ASCIIFoldingFilter: both find 3 of 3 on the example. Either changes the analysis chain, so it needs a reindex too.

Why it is a bug, not intended

#
  • The table's own rows say st: ſ folds to s, ﬆ to st, and every other Latin ligature of the block is folded.
  • Unicode (NFKD), Lucene's ICU folding and core SimpleCaseFolding all treat ﬅ as st.
  • The filter it replaced as a documented superset, ISOLatin1AccentFilter, folded ﬅ: the only one of its 72 mappings dropped.
The full argument498 words
  • The table's own rows set the rule. It folds ſ U+017F to s (:1224), ﬆ U+FB06 to st (:1255-1258) and every other Latin ligature of the block (:575-596). By its own standard st is a "reasonable ASCII alternative" for ﬅ, which is ſ + t. U+FB05 is the only hole among U+FB00-FB06.
  • Unicode and Lucene's other folding code agree on st. NFKD(U+FB05) = NFKD(U+FB06) = "st" (JDK Normalizer, executed). Lucene's ICU folding data maps both to "st" (utr30/nfkc_cf.txt:3031, FB05..FB06>0073 0074), and core SimpleCaseFolding maps U+FB05 to U+FB06 (:459-460).
  • A silent regression for users who migrated. LUCENE-1351 (2.4.0, filed under "Bug fixes": "ISOLatin1AccentFilter now cleans additional ligatures") added U+FB05 -> ft to ISOLatin1AccentFilter. Four months later LUCENE-1390 added ASCIIFoldingFilter and deprecated the old filter "in favor of ASCIIFoldingFilter which covers a superset of Latin 1"; from 2.9.0 to 3.6.2 the new javadoc said "The set of character conversions supported by this class is a superset of those supported by Lucene's ISOLatin1AccentFilter". The CHANGES entry on main still says the old filter "handles a subset of this filter", a contributor wrote in the issue: "This class includes all of ISOLatin1AccentFilter.", and in February 2011 a co-author repeated on the dev list that "ASCIIFoldingFilter provides a superset of it mappings". Of the old filter's 72 mappings, 71 are identical in the new table and U+FB05 is the only one missing; a scan of the 3.6.2 jars finds U+FB05 as the only character the old filter folds and the new one leaves unchanged. What migrating users lost was a match on "faft" (the old filter gave ft); the query "fast" has never matched "faﬅ" through either filter. The superset promise covered 2.9.0-3.6.2 only, so for current versions the case rests on the table's own consistency, not on a broken guarantee.
  • No record of a decision. The issue thread never mentions U+FB05, long s or ligatures; the final patch in the JIRA archive already lacks the entry; no test, CHANGES or MIGRATE entry, issue or list mail found says it was left out on purpose. No upstream test asserts that U+FB05 passes through (testUnmodifiedLetters covers only § ¦ ¤), and testAllFoldings was generated from the table by a Perl script (TestASCIIFoldingFilter.java:150-151), so it mirrors the table. The contributor called the table generated from UnicodeData.txt "and then moved things around to the appropriate places by hand. I guess this is one weakness of this patch: it's large enough that manual verification is tough."
  • Why it was left out is not recorded. One plausible mechanical cause (an inference, not documented): U+FB05's one-level decomposition is U+017F U+0074, which is not ASCII, while U+FB06's is U+0073 U+0074.
  • What not to claim. The current javadoc does not promise this mapping: the superset sentence left together with ISOLatin1AccentFilter in 4.0 (a58c26978f5, LUCENE-2781, 2010-11-30). Present it as a one-entry gap and a historical regression, not as a broken current guarantee.
The devil's-advocate check318 words

The intended-behaviour checker built the strongest case for "intended": the javadoc says "only those characters with reasonable ASCII alternatives are converted", so the table is a curated selection with no completeness promise; the ICU module calls ICUFoldingFilter "a more thorough replacement for ASCIIFoldingFilter and LowerCaseFilter that applies the same ideas to many more languages", so gaps are expected and the remedy is to switch filters; the table has not changed since 2008 and any change alters indexed terms; and the contributor's rule, to "convert characters to those that look like them in ASCII", makes ﬅ ambiguous between ft (what it looks like, and what the old filter produced) and st (what it is).

Why it fails: the table already chose meaning over look for the long s (ſ, ẜ U+1E9C and ẝ U+1E9D fold to s) and folds ﬆ to st, so st is reasonable by its own standard, and NFKD, ICU folding and core case folding agree. Nothing indicates the omission was a choice: the 2.9.0-3.6.2 javadoc promised a superset of the old filter, which folded ﬅ, and U+FB05 is the only break. The ICU note says the ICU filter is broader, not that the table leaves a Latin presentation form of a block its javadoc lists out on purpose. The table is stable in practice (no mapping has changed since 2008, not even ẛ U+1E9B to f, called a bug in #2420 in 2010), but no freeze policy was found in the code, CHANGES, MIGRATE or the issue threads examined; back-compat is a real cost (a reindex note) and a likely review question, not evidence of intent. Verdict: the evidence favours an accidental omission; nothing found shows U+FB05 was left out on purpose. What survives is a priority argument (a committer may answer "use ICUFoldingFilter") and the ft versus st question: propose st and say plainly that the old filter gave ft.

Trade-offs

  • Reindexing. Indexed terms change for text with ﬅ: documents indexed before the fix keep faﬅ, new queries produce fast. Suggest a CHANGES entry that says affected fields need a reindex; whether it goes to 10.x or only 11.0 is the committers' call. No mapping of this table has changed since 2008, so expect a back-compat question.
  • The value. st matches NFKD, the ICU folding data, core SimpleCaseFolding and the table's own ſ and ﬆ rows; the old ISOLatin1AccentFilter produced ft. Say so in the issue and let the reviewers decide.
  • No API change. No performance effect is expected (one more label in the same switch, a two-character output like U+FB06's, within the 4 x length buffer); not benchmarked.
  • Copies of the table outside Lucene need the same line separately.

Downstream note

How it was found

#

An exhaustive check folded all 65,536 BMP characters through the real jar and compared each with its Unicode decomposition, in the blocks the javadoc lists. Of 48 letters left unfolded although their decomposition is ASCII, 47 belong to classes the table never covers or were added to Unicode after the table; ﬅ is the only isolated gap.

The method in full255 words

LFV-819, snapshot of 2026-10-29

Registry title
ASCIIFoldingFilter folds the ligature ﬆ (U+FB06) to 'st' but has no entry for its sibling ﬅ (U+FB05 LATIN SMALL LIGATURE LONG S T, NFKD 'st'), so 'faﬅ' is indexed unchanged and the ASCII query 'fast' does not find it
Area
analysis-common / ASCIIFoldingFilter mapping table (foldToASCII switch)
Priority
Low, rank 438: ASCIIFoldingFilter is opt-in, the miss only affects relevance, and it involves one presentation-form ligature seen mostly in transcriptions of historical long-s printing, which matches the older-orthography profile of LFV-607.
Impact class
minor
Impact note
Relevance only, no error: applications whose analysis chain uses ASCIIFoldingFilter (opt-in: no Lucene analyzer ships it; it is added by hand, through CustomAnalyzer or through the 'asciiFolding' SPI factory) and whose documents or queries contain the precomposed ligature ﬅ U+FB05 index and query such tokens unfolded, so ASCII-typed queries silently miss them while the same word spelled with ﬆ U+FB06 or with long s ſ U+017F is found; no scale is needed, -ea and -da behave the same, preserveOriginal=true does not help, every release since 2.9.0 has it, ICUFoldingFilter used instead or core CaseFoldingFilter (new in the unreleased 10.6.0) in front of ASCIIFoldingFilter avoid it today, and because a fix changes indexed terms, affected fields need reindexing after it.
Summary
You fold text with ASCIIFoldingFilter, whose javadoc says it converts characters 'into their ASCII equivalents, if one exists' and lists the Alphabetic Presentation Forms block, and you search in plain ASCII. You expect 'faﬅ' (with the long-s-t ligature U+FB05, whose NFKD is 'st') to be indexed as 'fast', just as 'faﬆ' (U+FB06) and 'faſt' (long s U+017F) are; instead the table has cases for U+FB00-FB04 and U+FB06 but none for U+FB05, so the character passes through unchanged, the term stays 'faﬅ' and the query 'fast' finds nothing. The fix is one case label (U+FB05 added to the U+FB06 'st' group) plus the matching row of the generated testAllFoldings array.
Introduced
