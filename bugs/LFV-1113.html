BBoxStrategy and PointVectorStrategy miss a shape on a query edge at 0 when one zero is -0.0 and the other +0.0, so BBoxStrategy finds a point Intersecting a rectangle but not Within it

A point at longitude -0.0 (for example from WKT POINT(-0 5)) lies on the west edge of the rectangle from 0 to 10, yet BBoxStrategy IsWithin and PointVectorStrategy silently miss it while BBoxStrategy Intersects finds it. Every release that ships the strategies has it (PointVectorStrategy since 4.0.0, BBoxStrategy since 4.10.0); a zero bound covering both zeros fixes it.

The finding in 30 seconds

#

Both strategies turn the query rectangle into DoublePoint range queries. An inclusive bound is passed unchanged, and DoublePoint sorts -0.0 just below +0.0, so an edge at one zero leaves out a coordinate at the other zero, although spatial4j treats the two as the same coordinate.

Background: two zeros, two orders

#
  1. A Java double has two zeros, +0.0 and -0.0. The primitive comparison -0.0 == 0.0 is true, but Double.compare(-0.0, 0.0) is negative: in that order -0.0 comes first.
  2. spatial4j's relate of a rectangle and a point, which SpatialOperation.Intersects and IsWithin evaluate through for this pair, compares coordinates with primitive operators, so a point at x = -0.0 lies on a rectangle edge at x = 0.0. (spatial4j's equals uses Double.compare; see "Not part of this finding" below.)
  3. BBoxStrategy and PointVectorStrategy (module lucene/spatial-extras) index coordinates as DoublePoint fields and answer queries with DoublePoint.newRangeQuery, whose ranges are inclusive and "consistent with Double#compareTo".

The finding, step by step

#
  1. Index one point at longitude -0.0, latitude 5 with BBoxStrategy and PointVectorStrategy, for example parsed from WKT POINT(-0 5). Java has two zeros, and -0.0 == 0.0 is true.
  2. Query the rectangle minX = 0, maxX = 10, minY = 0, maxY = 10. The point is on its west edge, and SpatialOperation.Intersects and IsWithin both evaluate to true. You expect 1 hit from each of the four queries.
  3. You get [1, 0, 0, 0]: only BBoxStrategy Intersects finds the point, with no error. Stored at +0.0, the same point is found by all four.
  4. Why: both strategies pass the edge 0.0 unchanged as an inclusive DoublePoint range bound, and DoublePoint sorts like Double.compareTo, where -0.0 comes just before +0.0, so -0.0 falls outside [0.0, 10]. BBoxStrategy Intersects uses only exclusive bounds, moved with Math.nextUp/nextDown, which treat both zeros alike.
  5. The same happens on the equator, in non-geo contexts, the other way round (+0.0 stored, -0.0 edge), for BBoxStrategy Contains and for PointVectorStrategy circles. Hits are only lost, never added.

Who is affected

#

Applications that use BBoxStrategy (IsWithin, Contains) or PointVectorStrategy (rectangle or circle queries), both @lucene.experimental, with default config. It needs a shape exactly on a query edge at x = 0 or y = 0 (prime meridian, equator, tile boundary) whose coordinate is -0.0 from caller data, such as WKT POINT(-0 5). Missed hits only; rare.

Mechanism, terms and numbers847 words

BBoxStrategy and PointVectorStrategy (module lucene/spatial-extras, both @lucene.experimental) answer a spatial query with DoublePoint range queries on the stored coordinates. An inclusive bound taken from the query rectangle is passed to DoublePoint.newRangeQuery unchanged, and DoublePoint ranges follow Double#compareTo, where -0.0 sorts just below +0.0. spatial4j, whose relate decides SpatialOperation.evaluate for a point and a rectangle, compares coordinates there as primitives, where -0.0 == 0.0. So a shape exactly on a query edge at x = 0 or y = 0 whose coordinate is the other zero silently drops out: a point stored at (-0.0, 5) against Rect(0.0, 10, 0, 10) gives hits [BBox Intersects 1, BBox IsWithin 0, PointVector Intersects 0, PointVector IsWithin 0] instead of [1, 1, 1, 1]. BBoxStrategy's Intersects uses only exclusive bounds, moved with Math.nextUp/Math.nextDown, which give the same double for both zeros, so it still finds the point: BBoxStrategy contradicts itself. The same miss affects BBoxStrategy Contains, PointVectorStrategy circle queries, the Y axis, non-geo contexts and the reverse direction. Only missed hits, never extra ones. Every release that ships the strategies has it (PointVectorStrategy since 4.0.0, BBoxStrategy since 4.10.0) through 10.6.0 and main. Widening a zero bound to [-0.0, +0.0] before the range query is built fixes it.

The mechanism (main e1faeba08bde, lucene/spatial-extras/.../spatial/)

#
  1. The contract. SpatialStrategy.makeQuery builds "a Query based principally on SpatialOperation and Shape" (SpatialStrategy.java:116). SpatialOperation's predicates are explained by "the source implementation of evaluate", and "Lucene-spatial makes no distinction of shape boundaries" (query/SpatialOperation.java:30-35). Intersects is relate(...).intersects() (:89-95); IsWithin is "CoveredBy ... (boundary-neutral)", relate == WITHIN || equals (:124-136).
  2. BBoxStrategy, inclusive bounds. makeWithin (bbox/BBoxStrategy.java:523) states "docMinX >= queryExtent.getMinX() ... docMaxX <= queryExtent.getMaxX()" (:526-527) and builds inclusive ranges (:531-532, :546-547); makeContains (:283) is the mirror (:286-287, :291-292, :304-305).
  3. BBoxStrategy, the range helper makeNumericRangeQuery (:651-672): a null bound becomes ±infinity (:654-660); an exclusive lower bound becomes Math.nextUp(min) (:663), an exclusive upper bound Math.nextDown(max) (:667), then DoublePoint.newRangeQuery(fieldname, min, max) (:670). An inclusive bound is passed unchanged. Fix site. Every caller passes its null side as exclusive, so that side ends at -/+Double.MAX_VALUE.
  4. BBoxStrategy Intersects is "has an envelope AND NOT disjoint" (makeIntersects, :473, :491-494), and makeDisjoint (:366) uses only exclusive bounds, e.g. docMaxX < query minX (:393). For the edge 0.0 that range is [-Double.MAX_VALUE, -4.9E-324] (printed bbox__maxX:[-1.7976931348623157E308 TO -4.9E-324]), which holds neither zero, so the point is not disjoint and is found. Math.nextUp/nextDown return the same double for -0.0 and +0.0.
  5. PointVectorStrategy. makeQuery (vector/PointVectorStrategy.java:188-205) answers both Intersects and IsWithin of a rectangle with makeWithin(bbox) (:194), and a circle with makeWithin(circle.getBoundingBox()) plus a distance filter (:196-198). makeWithin (:209-222) adds MUST ranges on x and y via rangeQuery (:228-238), which passes the bounds unchanged to DoublePoint.newRangeQuery (:238). Fix site.
  6. The order. DoublePoint.newRangeQuery: "Ranges are inclusive ... Range comparisons are consistent with Double#compareTo(Double)" (lucene/core/.../document/DoublePoint.java:210-213). So [0.0, 10] excludes a stored -0.0, and [-10, -0.0] excludes a stored +0.0.

Worked example (the repro)

#

Point (-0.0, 5), query Rect(minX=0.0, maxX=10, minY=0, maxY=10):

  • BBox IsWithin needs docMinX in [0.0, Double.MAX_VALUE] (printed bbox__minX:[0.0 TO 1.7976931348623157E308]): -0.0 sorts below 0.0, so 0 hits.
  • PointVector, both operations, needs x in [0.0, 10.0]: 0 hits.
  • BBox Intersects needs the point to be outside every disjoint range, e.g. docMaxX in [-Double.MAX_VALUE, -4.9E-324] or docMinX in [10.000000000000002, Double.MAX_VALUE]: -0.0 is in none of them, so 1 hit.

More executed views

#
  • Same point, other zero (control, default IndexWriterConfig, main and 10.6.0): makePoint(0.0, 5) gives [1, 1, 1, 1]; makePoint(-0.0, 5) and WKT POINT(-0 5) give [1, 0, 0, 0].
  • Parsed query strings: a point at longitude -0.0, latitude 51.5 is missed by IsWithin(ENVELOPE(0, 180, 90, -90)) (the eastern hemisphere) in both strategies and by Intersects(ENVELOPE(0, 20, 60, 0)) in PointVectorStrategy; RecursivePrefixTreeStrategy finds it. The western neighbour cell still finds the point, so it drops out on one side only.
  • Circles: Circle(Pt(5, 0), 5 deg) has a spatial4j-computed bounding box with west edge +0.0; PointVectorStrategy misses a point at (-0.0, 0) that lies on the circle.
  • Bounded-exhaustive sweep (exhaustive over a small domain: coordinates {-10, -0.0, +0.0, 10}, 121 query rectangles, 137 shapes, 5 operations, 4 strategies, geo and non-geo; plus 7 selected circles; 439,082 checks): 6,120 zero-sign defects, all missed matches (per context BBox IsWithin 1,184, BBox Contains 1,313, PointVector Intersects 276 and IsWithin 276, circles 5-6 per operation); 0 for BBox Intersects / IsDisjointTo / IsEqualTo, RecursivePrefixTreeStrategy and SerializedDVStrategy; 0 with the fix.

Exposure and likelihood394 words
  • Who is hit. Applications that index points or rectangles with BBoxStrategy and query with IsWithin or Contains, or with PointVectorStrategy and query a rectangle (Intersects or IsWithin) or a circle. Both strategies are @lucene.experimental (BBoxStrategy.java:71, PointVectorStrategy.java:80); otherwise default codec, IndexWriterConfig and searcher, any index size, geo and non-geo contexts.
  • When. A shape exactly on a query edge at x = 0 or y = 0 (the prime meridian, the equator, a hemisphere or tile boundary, or a 0 bound in a non-geo context), with -0.0 on one side and +0.0 on the other. The query edge is usually an ordinary +0.0; -0.0 comes from caller data, for example WKT or text such as -0 or -0.0, a negated 0.0 (a 0-degree "W" longitude stored as -lon), or Math.ceil of a small negative number. The WKT reader keeps the sign, in POINT(-0 5) and in ENVELOPE(-10, -0, 10, 0). In the hunt's producer search none of 4,114 spatial4j circle bounding boxes had a -0.0 edge, but spatial4j's pointOnBearing returned x = -0.0 in 88 of 82,280 calls, all from 8 start points on longitude 180 (2 of them the poles), e.g. from (180, 10) with bearing 0 and distance 90: another way -0.0 can reach caller data.
  • Size of the error. Only missed matches, never extra ones: a raw inclusive bound at one zero only leaves out a coordinate at the other zero, and every inclusive range sits in MUST or SHOULD clauses (BBoxStrategy's only MUST_NOT clauses, :390, :398, :494, hold term queries on ±180 and the exclusive-only disjoint query; PointVectorStrategy has none). In the sweep all 6,120 zero-sign defects were misses. The shape drops out on one side of the edge only; the neighbouring cell still finds it.
  • Silent. No exception and no assertion, with assertions on and off.
  • Other strategies are fine. In the point-on-edge cases tested, RecursivePrefixTreeStrategy and SerializedDVStrategy in the same module return the hit, and so do the core geo queries: the XYShape and LatLonShape box queries and the XYPointField polygon query (48 checks, 0 mismatches), and LatLonPoint.newBoxQuery, LatLonPoint.newPolygonQuery and XYPointField.newBoxQuery (32 checks, 0 mismatches, run by this doc's fact check).
  • Likelihood: rare. It needs an exact -0.0 on exactly a zero edge, in two experimental strategies; the searches recorded on 2026-11-02 found no report of it since 4.0.0 (2012).

Why it looks unintended

#
  • For a point, Intersects and IsWithin a rectangle are the same question, yet BBoxStrategy answers 1 and 0 for the same document.
  • The strategies promise SpatialOperation predicates, defined by evaluate(), which is true here and is the oracle of the module's own tests.
  • RecursivePrefixTreeStrategy, SerializedDVStrategy and the core geo point and shape queries all find such a point.
The full argument214 words
  • Contract. BBoxStrategy "supports all SpatialOperations" (BBoxStrategy.java:47), qualified at :57 as "Supports most SpatialOperations but not Overlaps", and its makeQuery maps Intersects, IsWithin and Contains to their own queries (:265-271); PointVectorStrategy: "Intersects and IsWithin is supported" (PointVectorStrategy.java:63-64). The query is built "principally on SpatialOperation" (SpatialStrategy.java:116), whose predicates are defined by evaluate() and are boundary-neutral (SpatialOperation.java:30-35, :124). BBoxStrategy's own comments state the Within and Contains conditions as plain comparisons, docMinX >= queryExtent.getMinX() (:526-527, :286-287), which hold for -0.0 against 0.0. Nothing says -0.0 is a different position from 0.0.
  • Tests. StrategyTestCase.testOperation asserts operation.evaluate(indexedShape, queryShape) == match before it searches (StrategyTestCase.java:233), and RandomSpatialOpStrategyTestCase uses operation.evaluate as truth (prefix/RandomSpatialOpStrategyTestCase.java:103). TestBBoxStrategy.testAlongDatelineOppositeSign and testWithinBugDatelineEdge require IsWithin to match when one edge is written as +180 and as -180 (bbox/TestBBoxStrategy.java:154, :126): the same kind of equivalence. No test in the module uses -0.0.
  • History. The strategies built inclusive ranges from raw bounds from the start (2012). LUCENE-7094 (#8150, 2016-03-30) moved them to DoublePoint ranges and to Math.nextUp/nextDown for exclusive bounds, which created the Intersects-vs-Within split; its discussion never mentions zeros. LUCENE-7594 (#8645, 2016-12-21), nine months later, set the Double.compare guidance for core point ranges and never mentions spatial-extras.
The devil's-advocate check195 words

The strongest "intended" case (built by the intended-behaviour verifier; an intended-lens cross-model review, OpenAI GPT-5.6, rated it moderate): DoublePoint documents Double#compareTo order on purpose, and LUCENE-7594's reporter wrote that Float/Double points "are supposed to be consistent with Double/Float.compare, so +0 is supposed to compare greater than -0"; both strategies say they are built on DoublePoint ranges; spatial4j's RectangleImpl.equals is sign-sensitive too; the strategies are experimental, and callers could normalize -0.0.

Why it fails: DoublePoint order is the encoding the strategies use, not the contract they promise. Users call SpatialOperation, whose predicates are evaluate(), and the module's tests use evaluate as truth; RPT, SerializedDV and the core geo queries find a point on the zero edge. The sign-sensitive equals is why IsEqualTo is not part of this finding; a point against a rectangle goes through relate, which compares primitives. "Experimental" allows API changes, not missed hits, and nothing documents a normalization rule while the WKT reader keeps -0.0. Decisive: BBoxStrategy answers Intersects and IsWithin of a point differently for the same document. Switching its exclusive bounds to DoublePoint.nextUp would remove the contradiction only by making Intersects miss too. Verdict: not intended, a defect.

Suggested fix

#

Recommended Widen a zero bound to [-0.0, +0.0] (fix A)

Make a zero range bound cover both zeros, right before DoublePoint.newRangeQuery in BBoxStrategy.makeNumericRangeQuery and PointVectorStrategy.rangeQuery: if (min == 0) min = -0d; if (max == 0) max = 0d;. The repro then passes, and so do the whole lucene/spatial-extras test suite (118 tests) and :lucene:spatial-extras:check -x test.

      // spatial4j compares coordinates as primitives (-0.0 == 0.0) but DoublePoint orders -0.0
      // below 0.0, so a zero bound must cover both zeros
      if (min == 0) {
        min = -0d;
      }
      if (max == 0) {
        max = 0d;
      }

      return DoublePoint.newRangeQuery(fieldname, min, max); // fieldName in PointVectorStrategy

Widen a zero bound to [-0.0, +0.0] (fix A) (validated by the checks) (recommended)

#

The same lines in both methods, just before the return DoublePoint.newRangeQuery(...). min and max are Double, so min == 0 unboxes and is true for both zeros; a lower bound of either zero becomes -0.0 and an upper bound +0.0, so a zero edge includes both. Exclusive bounds were already moved off zero by nextUp/nextDown, so they are unaffected. The exact-match path used by IsEqualTo and the dateline clauses is left alone.

      // spatial4j compares coordinates as primitives (-0.0 == 0.0) but DoublePoint orders -0.0
      // below 0.0, so a zero bound must cover both zeros
      if (min == 0) {
        min = -0d;
      }
      if (max == 0) {
        max = 0d;
      }

      return DoublePoint.newRangeQuery(fieldname, min, max); // fieldName in PointVectorStrategy

Trade-offs

Results change only on a zero edge: on the inclusive range paths the patch changes, a -0.0 input now gets the answer of its +0.0 twin (the exact-term path used by IsEqualTo is unchanged and still tells the zeros apart, as spatial4j's equals does), so BBoxStrategy's documented bounding-box extra hits for non-rectangles under Contains also appear for those twins (no new kind of mismatch). No index-format change; documents already stored with -0.0 are found without reindexing. One comparison per bound (two per range query) at query-build time.

Normalize -0.0 to +0.0 at index and query time

#

Add 0.0 to every indexed coordinate in createIndexableFields and to every query bound (x + 0.0 turns -0.0 into +0.0).

Trade-offs

Fixes new documents only: those already indexed with -0.0 stay invisible on a 0 edge until reindexed, and it touches more code paths (stored values, doc values, distance sources). Not validated.

Make the exclusive bounds follow Double.compare

#

Use DoublePoint.nextUp/nextDown instead of Math.nextUp/nextDown in BBoxStrategy.makeNumericRangeQuery, as LUCENE-7594 recommends for core ranges.

Trade-offs

Not recommended: it removes the contradiction only by making Intersects miss the point too, so both strategies would still disagree with SpatialOperation.evaluate, RPT and SerializedDV. Not validated. A side note: DoublePoint's 1-D newRangeQuery javadoc names DoublePoint.nextUp/nextDown for exclusive ranges (DoublePoint.java:210-211), while the n-dimensional overload's javadoc still says Math#nextUp / Math.nextDown (:232-233).

Document that coordinates must not be -0.0

#

State the restriction in the class javadocs.

Trade-offs

Not recommended: it legitimises silent missed hits that a small change removes, and the WKT reader produces -0.0 from ordinary input. Not validated.

How it was found

#

A Z3 query asked which doubles are equal under == but sort apart under Double.compare; the only answers are the two zeros. A grep for code that hands spatial4j bounds to DoublePoint ranges found these two strategies, and executed probes on main and 10.6.0 showed the missed hits. The hunt unit that judged it then widened and confirmed it.

The method in full170 words

Method: semi-formal (a Z3 witness for a generic fact about doubles, which became a Lucene lead through a caller grep and an executed probe).

  • Round 22 of the hunt ran a numeric-casts lens with Z3. One of its queries asked for non-NaN doubles x <= q under primitive comparison (the semantics spatial4j's relate uses) whose DoublePoint order is x > q; the only witnesses are x = +0.0, q = -0.0. A grep for callers that pass spatial4j bounds straight to DoublePoint ranges found only BBoxStrategy and PointVectorStrategy outside the lucene/sandbox module and the query parsers. Public-API probes on main and 10.6.0 (2026-11-02) showed the missed hits, and a core-geo control showed none.
  • The round's skeptic re-ran it. History

#

As old as the strategies: PointVectorStrategy since 4.0.0 (2012), BBoxStrategy since 4.10.0. Every executed release fails: 4.x and 5.x miss all four queries (legacy trie order); LUCENE-7094 (#8150, 6.0.0) moved to DoublePoint and made BBox Intersects find the point, creating the split. Versions tested7 rows

LFV-1113, snapshot of 2026-11-04

Registry title
BBoxStrategy and PointVectorStrategy miss a shape on a query edge at 0 when the shape's coordinate and the edge are zeros of opposite sign (-0.0 vs +0.0), so BBoxStrategy finds a point Intersecting a rectangle but not Within it
Area
spatial-extras / BBoxStrategy and PointVectorStrategy query construction (inclusive DoublePoint range bounds taken unchanged from spatial4j rectangles: BBoxStrategy.makeNumericRangeQuery, PointVectorStrategy.rangeQuery)
Priority
Low, rank 412: In every release that ships them, the experimental BBoxStrategy and PointVectorStrategy silently miss a shape that lies exactly on a query edge at 0 when the coordinate and the edge are zeros of opposite sign. It needs a -0.0 coordinate exactly on such an edge, a rare boundary value, so it is Low.
Impact class
silent wrong results
Impact note
Applications that index points or rectangles with the @lucene.experimental BBoxStrategy (IsWithin, Contains) or PointVectorStrategy (rectangle Intersects and IsWithin, and circle queries through their bounding box) silently lose a document that lies exactly on a query edge at x = 0 or y = 0 (the prime meridian, the equator, or a 0 bound in a non-geo context) when the document's coordinate and the edge are zeros of opposite sign, one -0.0 (from caller data such as WKT 'POINT(-0 5)' or a negated 0.0) and the other +0.0, at any index size with the default IndexWriterConfig, codec and searcher, in geo and non-geo contexts, in every release that ships them (PointVectorStrategy since 4.0.0, BBoxStrategy since 4.10.0); only missed matches, never extra ones.
Summary
You index a point stored at longitude -0.0 (for example parsed from 'POINT(-0 5)') with BBoxStrategy and PointVectorStrategy and query the rectangle Rect(minX=0.0, maxX=10, minY=0, maxY=10); you expect the point to match Intersects and IsWithin in both strategies, because SpatialOperation.evaluate says it lies on the rectangle's west edge (spatial4j compares coordinates as primitives, so -0.0 == 0.0). Instead BBoxStrategy finds it for Intersects but not for IsWithin, and PointVectorStrategy finds it for neither, with no error. Both strategies pass the rectangle's 0.0 edge unchanged as an inclusive DoublePoint range bound, and DoublePoint orders -0.0 below +0.0; BBoxStrategy's Intersects uses only exclusive bounds, which it moves with Math.nextUp/Math.nextDown, and those give the same result for both zeros.
