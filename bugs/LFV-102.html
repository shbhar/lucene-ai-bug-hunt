Test framework: CheckHits.checkTopScores can falsely fail on correct minimum-should-match queries

The test-framework helper CheckHits.checkTopScores rejects a correct query: on two docs, (f:a f:b f:c)~2 gives the same hit and score in both score modes, yet it throws expected:<1> but was:<0>. It demands that both modes' scorers propose the same candidate docs, which no documented contract promises.

The finding in 30 seconds

#

In short: the checker walks the two modes' candidate lists side by side and requires them to stop on the same docs (CheckHits.java:751, again at :838). Lucene only promises that each list contains all the matches, and with minimum-should-match above 1 the top-k list can hold an extra doc that does not match.

Background: score modes and candidate lists

#
  1. A query can be scored in COMPLETE mode (score every match) or in TOP_SCORES mode (skip docs that cannot reach the top k, using per-block score bounds). Both must return the same top hits.
  2. Many scorers work in two phases: a cheap approximation proposes candidate docs, and matches() confirms each one. The approximation only has to be a superset of the matches.
  3. CheckHits.checkTopScores is a public test-framework helper that runs a query in both modes and checks the top hits, the scores and the score bounds.
  4. For a BooleanQuery with minimumNumberShouldMatch above 1, both modes use WANDScorer. It may set aside up to msm - 1 clauses (and, in TOP_SCORES, clauses whose summed score bound is below the competitive threshold): a doc that only those clauses contain is not a candidate.

The finding, step by step

#
  1. In a test, index two docs, doc 0 = c and doc 1 = a b, and query (f:a f:b f:c) with setMinimumNumberShouldMatch(2). Only doc 1 matches, with score 0.5545178.
  2. Call CheckHits.checkTopScores(random(), query, searcher). Its first stage compares an exhaustive (COMPLETE) and a top-k (TOP_SCORES) search: both return doc 1 with 0.5545178, so you expect a pass.
  3. Its second stage walks both scorers' candidate lists side by side and requires them to stop on the same docs. COMPLETE proposes [1]; TOP_SCORES proposes [0, 1], and its matches() correctly rejects doc 0, which holds only c.
  4. You get AssertionError: expected:<1> but was:<0> at CheckHits.java:751, with assertions on and off, although a candidate list only has to contain all the matches and both do.

Who is affected

#

Tests only, in Lucene or downstream: any checkTopScores call on a BooleanQuery with minimumNumberShouldMatch above 1 can fail falsely on a suitable index, with ordinary settings and assertions on or off. Search results agreed in every recorded run. None of the 24 upstream call sites uses minimum-should-match, so Lucene's build stays green. Present since 8.8.0.

Mechanism, terms and numbers779 words

CheckHits.checkTopScores is the public test-framework helper that runs a query in COMPLETE and in TOP_SCORES mode and checks that the top hits agree and that the score bounds are valid. Its second part, doCheckMaxScores, walks both scorers' two-phase approximations (their candidate lists) side by side and asserts after each step that they are on the same doc. No documented contract promises that: an approximation only has to be a superset of the matching documents. With minimumNumberShouldMatch above 1, both scorers the checker builds are WANDScorers, which choose candidates differently per mode, so the TOP_SCORES list can contain a doc that the COMPLETE list skips and that matches() then rejects.

On two docs (doc 0 = c, doc 1 = a b), (f:a f:b f:c)~2 matches only doc 1, with score 0.5545178 in both modes; the COMPLETE candidates are [1], the TOP_SCORES candidates [0, 1], and the checker fails with expected:<1> but was:<0>. The assertion dates from 2018 (8.0.0) and has been reachable since 8.8.0. Only tests are affected, and none of Lucene's own calls of the checker uses minimum-should-match. We think the fix belongs in CheckHits; a maintainer may instead read the lockstep as an intended efficiency check (see the counter-case below).

Why the two modes propose different docs

#
  • BooleanScorerSupplier.java:589-590 returns a WANDScorer for any minShouldMatch > 1, in both modes. That is the scorer path doCheckMaxScores uses (CheckHits.java:719-727); nothing here is claimed about the bulk scorers IndexSearcher.search may use.
  • WANDScorer parks clauses in its "tail" (WANDScorer.java:601): up to minShouldMatch - 1 of them and, in TOP_SCORES, also clauses whose summed score bound is below the competitive threshold (0 when this repro fails). A doc that only parked clauses contain is never a candidate. The candidate is the top of the "head" (:300-319).
  • COMPLETE has no score bounds (scaling factor 0, :195), so it parks clauses by cost only (:674-687). In the 2-doc index it parks c; a and b sit on doc 1, so its candidates are [1].
  • TOP_SCORES, on entering a new block (:307-312), recomputes the score bounds and moves parked clauses back while their summed bound is at least the competitive threshold (:479-485). The threshold starts at 0 (:163) and this loop has no minimum-should-match term, so the parked clause, c, comes back and doc 0 becomes a candidate. matches() rejects it (freq + tailSize < minShouldMatch, :342-344).
  • A probe on the 2-doc index (exploration only; it calls setTopLevelScoringClause() in both modes and never setMinCompetitiveScore) shows exactly this: COMPLETE head docs [1, 1] with one parked clause, TOP_SCORES head docs [0, 1, 1] with none; all three clauses have the same max score, 0.6931472. The diagram's probe, which builds both scorers exactly as doCheckMaxScores does, prints the same candidate lists.

Not one cause in WANDScorer

#

Making the tail loop at WANDScorer.java:481 respect minimum-should-match makes the 2-doc test pass. But the same change still fails two larger inputs of an independent check on 645d4fe14a20: a 300-doc pattern (expected:<111> but was:<110>) and a boosted (a b c^10)~2 (expected:<7> but was:<6>). That verifier's reading: TOP_SCORES parks clauses by score bound and COMPLETE by cost, so the two lists differ for other reasons too. So the tested variant does not restore the lockstep for the larger inputs; no other scorer-side change was tried, so one is not ruled out.

Why it looks unintended

#
  • TwoPhaseIterator#approximation promises only "a superset of the matching documents"; checkTopScores has no javadoc or precondition, and its loop says it checks "when iterating all matches".
  • The query is correct: the checker's own first stage and IndexSearcher.search give the same hit and score.
  • Precedent: #13069, #13088 and #13122 fixed other COMPLETE vs TOP_SCORES differences inside CheckHits.
The full argument201 words
  • The contract. TwoPhaseIterator.java:88-90 allows any superset of the matches. checkTopScores (CheckHits.java:690) states no precondition on the query; the class javadoc says only "Utility class for asserting expected hits in tests." (:57), and the first loop calls itself a check "when iterating all matches" (:717).
  • The query is right. In the same test the checker's own first stage (doCheckTopScores, top 1 and top 10) passes, and IndexSearcher.search returns the same single hit, doc 1, score 0.5545178.
  • Precedent. In #13069 / #13088 (2024) another COMPLETE vs TOP_SCORES structural difference (a null TOP_SCORES scorer) broke doCheckMaxScores, and the change went into CheckHits; jpountz (on #13069) asked for a follow-up assertion "to make sure that both scorers produce the same hits", which became #13088. #13120 / #13122 did the same for the advance loop; on #13120 Chris Hegarty wrote "I believe that this is a test bug."
  • Latent, then reachable. The lockstep came with checkTopScores in LUCENE-8135 (2018, 8.0.0) and held while both modes used MinShouldMatchSumScorer for msm > 1. LUCENE-9346 (8.8.0) moved TOP_SCORES to WANDScorer, and suitable inputs have failed ever since. The assumption was never written down; it was simply never exercised.
The devil's-advocate check300 words

The strongest case for "intended": the lockstep is a deliberate white-box check that TOP_SCORES never visits a candidate COMPLETE skips. In the lucene-solr#2141 review (comment r550807975, 2021-01-01) jpountz kept a filter in WANDScorer's approximation "so that the approximation doesn't return documents knowing that no match is possible", so a reviewer may ask whether WANDScorer should change instead. The lockstep is also one-sided: TOP_SCORES may skip COMPLETE candidates (if they score below the threshold) but may not add its own, which reads as a coherent pruning invariant; a maintainer could call the extra TOP_SCORES candidate a minor WANDScorer inefficiency and decline to relax CheckHits (this doc's cross-model fact check).

Why we still think it is not intended: no javadoc, comment, CHANGES or MIGRATE entry states such an invariant, and TwoPhaseIterator promises only a superset. #13996 (10.1.0, by the same author) then moved that approximation-side filter into matches() on purpose ("moves work from advance(int target) to TwoPhaseIterator#matches()"). And the one scorer-side change we tried, an msm-aware tail loop, fixes the 2-doc input, but two larger inputs still fail. Ratings of the counter-case: weak (cross-model); moderate (the cross-model refute review and this doc's cross-model fact check); the independent reproduction, the intended-behaviour check and the adjudication rejected it without a strength label. Our verdict: not intended, a test-framework defect; the open question is whether checkTopScores should require equal candidate lists, or only agreeing hits, scores and score bounds.

Noise call (contested): the cross-model fact check also argues that this is noise rather than a bug, because its whole effect is a false test failure. It stays confirmed here: the defect is the behaviour of a public test-framework API that downstream test suites call directly, and it fails with JVM assertions on and off; it is not a Java assert tripping inside Lucene.

Suggested fix

#

Recommended B. Keep walking the candidate lists; accept extra TOP_SCORES candidates that do not match

Recommended (B): in both loops, when TOP_SCORES proposes a doc the COMPLETE list skipped, require that it does not match, instead of assertEquals(doc1, doc2). Simplest alternative (A): walk the matching docs. Both validated: the test fails before and passes after, and all 128 tests of the 8 classes that call checkTopScores pass with nightly tests on.

All options and trade-offs2 options · 1,171 words

Not recommended:

  • Changing only WANDScorer (for example making the tail loop at WANDScorer.java:481 respect minimum-should-match): the variant we tried makes the 2-doc test pass, but larger inputs still fail. Downstream note

#

Downstream relevance only: test suites built on Lucene's test framework that call checkTopScores on minimum-should-match queries can fail falsely; nothing changes for a deployed application.

How it was found

#

Differential testing. A scripted-scorer fuzzer compared WANDScorer's results and score bounds with an exact brute-force reference on scripted scorers. Once CheckHits.checkTopScores was added to it, the checker failed on every query with minimum-should-match above 1 while the reference passed. It was reduced by hand to a plain term disjunction, later to two documents.

The method in full121 words
  • Harness. A hunt unit (WAND and block-max score bounds) built a scripted-scorer fuzzer with an exact dyadic brute-force oracle and a score-bound recorder. With CheckHits.checkTopScores added as a second oracle, it failed on every query with a nested or top-level minimumNumberShouldMatch > 1 WANDScorer while the exact oracle passed.
  • Reduction. The finder minimised it by hand to (f:a f:b f:c)~2 over a 300-doc pattern on the stock jars, and the hunt later reduced that to the 2-doc, one-method test (2026-10-29).
  • Verification. An independent reproducer (own tests, from the claim only), cross-model lenses (OpenAI GPT-5.6, refute and intended), an intended-behaviour devil's advocate and an adjudication all called it real; the version-history runs placed the first affected release; a credibility audit kept it.

LFV-102, snapshot of 2026-11-10

Registry title
CheckHits.checkTopScores (test framework) fails on correct minimum-should-match disjunctions because it walks the COMPLETE and TOP_SCORES two-phase approximations in lockstep
Area
test-framework / search checkers (CheckHits)
Priority
Low, rank 1300: CheckHits.checkTopScores falsely fails on correct minimum-should-match disjunctions, a test-framework-only problem that no current caller exercises.
Impact class
minor
Impact note
Test code only: any test, in Lucene or downstream, that calls the public test-framework checker CheckHits.checkTopScores on a query that WANDScorer runs with minimumNumberShouldMatch > 1 (an ordinary BooleanQuery of term clauses with setMinimumNumberShouldMatch(2); a handful of docs, the default IndexWriterConfig, codec and searcher, -ea or -da suffice); search results are correct in both score modes, so nothing outside tests is affected; none of the 24 upstream checkTopScores call sites sets minimumNumberShouldMatch, so Lucene's own tests do not hit it; released 8.8.0-10.6.0.
Summary
In a test you call the test framework's CheckHits.checkTopScores on a BooleanQuery of three term clauses with setMinimumNumberShouldMatch(2), for example (f:a f:b f:c)~2. You expect it to pass, because the query returns the same matching docs with the same scores in COMPLETE and TOP_SCORES mode (checked in the same test). Instead it throws AssertionError 'expected:<1> but was:<0>' in CheckHits.doCheckMaxScores (CheckHits.java:751): the checker requires the two scorers' two-phase approximations, which only have to be supersets of the matches, to stop on the same docs, and the TOP_SCORES WANDScorer legitimately stops on doc 0 (it holds only 'c'), which matches() then rejects.
Introduced
c2493283a58 (LUCENE-9346 'Support minimumNumberShouldMatch in WANDScorer', apache/lucene-solr#2141, main) and its branch_8x backport 74c0a978148, which shipped first, in 8.8.0 [exec, commit level: 8.7.0 with 74c0a978148's Boolean2ScorerSupplier, MinShouldMatchSumScorer, ScorerUtil and WANDScorer shadowed fails like 8.8.0, and 8.8.0 with the parent's three files shadowed passes, 20 derived seeds each way; read: it is the only commit between the 8.7.0 and 8.8.0 tags that touches those classes, BooleanWeight or CheckHits]: from it on, TOP_SCORES with minimumNumberShouldMatch > 1 uses WANDScorer, whose approximation can stop on docs that the COMPLETE approximation skips. The failing lockstep assertion itself is older and was latent until then: 4fb7e3d02c6 (LUCENE-8135 'Implement block-max WAND', 2018-02-15, first released in 8.0.0) [read: git log -S, -G and -L]. LUCENE-9346 is a legitimate scorer change that exposed the checker's assumption, not a scorer bug. Later: LUCENE-9668 (7f4d4dfdbf6, backport d266a09ff4c, 8.9.0) kept the failure, and #13996 (a67120e1754, 10.1.0) re-exposed the plain unboosted input after it had passed on 9.12.0-10.0.0 [exec] (2021-01-11 (LUCENE-9346 merge and branch_8x backport); the latent assertion dates from 2018-02-15 (LUCENE-8135))
