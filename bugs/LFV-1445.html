KnnVectorsReader.search javadoc says acceptDocs may be null; since 10.3.0 null throws NullPointerException

The javadoc of KnnVectorsReader.search still says to pass null as acceptDocs when all documents may match, but since 10.3.0 the parameter is an AcceptDocs that the default HNSW reader dereferences, so following it throws NullPointerException on the first search. Lucene's own kNN queries always pass a value; the fix is javadoc only.

The finding in 30 seconds

#

KnnVectorsReader.search is the per-segment kNN search under KnnFloatVectorQuery; its acceptDocs argument says which documents may match. Up to 10.2 it was a Bits, and null meant every document. In 10.3.0 it became an AcceptDocs object, but the javadoc kept the old sentence.

  1. Index one document with the 2-dimension vector {1, 0} in field v with the default codec, and get its KnnVectorsReader through the public codec SPI (a FilterCodec whose vectors format keeps the reader that fieldsReader opens).
  2. Call search("v", {1, 0}, new TopKnnCollector(1, Integer.MAX_VALUE), null), because the javadoc says acceptDocs may be null "if they are all allowed to match".
  3. You expect an unfiltered search that collects the one document: 1 hit.
  4. Instead the default reader calls acceptDocs.cost() on the null: NullPointerException: Cannot invoke "org.apache.lucene.search.AcceptDocs.cost()" because "acceptDocs" is null, with assertions on and off.
  5. Since 10.3.0, "all documents" is written AcceptDocs.fromLiveDocs(null, maxDoc), and passing that returns the 1 hit. Up to 10.2.2 the parameter was a Bits and null worked as documented.

Who is affected

#

Code that calls the codec-level KnnVectorsReader.search itself with null (a custom or delegating reader, a custom codec, a tool on CodecReader.getVectorReader()), and a searchNearestVectors caller passing null against its own javadoc. The kNN queries and CheckIndex always pass a value. The default HNSW reader fails loudly on the first search, never with wrong results, in 10.3.0 to 10.6.0 and main.

Mechanism, terms and numbers394 words

KnnVectorsReader.search(field, target, knnCollector, acceptDocs) is the codec-level kNN search that CodecReader.searchNearestVectors, and through it KnnFloatVectorQuery and KnnByteVectorQuery, call per segment for an approximate search. On all three overloads (float[], byte[] and, on main, short[]) its javadoc says acceptDocs is "{@link Bits} that represents the allowed documents to match, or {@code null} if they are all allowed to match". That was true up to 10.2, when the parameter was a Bits. #15011 (10.3.0) made the parameter an AcceptDocs, which the default HNSW reader dereferences, and "all documents" became AcceptDocs.fromLiveDocs(null, maxDoc); it updated four of LeafReader's @params and CheckIndex's search(..., null) calls but left this text. A caller who passes null as documented gets NullPointerException: Cannot invoke "org.apache.lucene.search.AcceptDocs.cost()" because "acceptDocs" is null on the first search of a non-empty field, with the default codec and assertions on or off, in every release from 10.3.0 to 10.6.0 and on main. The runtime behaviour matches #15011's change; the fix is the @param text.

The contract and the code (main f794ff5a505c)

#
  • KnnVectorsReader.java:118-119, :147-148, :176-177, the @param of the float[], byte[] and short[] overloads: {@link Bits} that represents the allowed documents to match, or {@code null} if they are all allowed to match., on a parameter of type AcceptDocs. Neither the class nor search is tagged @lucene.internal or @lucene.experimental.
  • PerFieldKnnVectorsFormat.java:329: the default codec's per-field reader forwards acceptDocs unchanged.
  • Lucene99HnswVectorsReader.java:369-370: Math.min(acceptDocs.cost(), graphSize) and acceptDocs.bits(), with no null check; only the early return for an empty field or k == 0 (:359-361) comes first. Lucene104ScalarQuantizedVectorsReader.java:377 calls acceptDocs.bits() the same way. A flat format's search does nothing with it (FlatVectorsReader.java:51-66).
  • AcceptDocs.java:67-77: fromLiveDocs(Bits bits, int maxDoc), where "A {@code null} instance is interpreted as matching all documents". That is how "all documents" is written now.
  • LeafReader.java:272, :316, :407, :465: #15011 rewrote these @param acceptDocs of searchNearestVectors to "{@link AcceptDocs} that represents the allowed documents to match", with no null clause; the short[] overloads at :360 and :436 were added later by #16383 with the same wording.

A literal null still compiles against AcceptDocs, so code written to the javadoc, or carried over from 10.2, fails only at run time: the same test source compiles on 10.2.2, where it passes, and on main, where it throws.

Exposure and likelihood230 words
  • Who the javadoc misleads: code that calls KnnVectorsReader.search directly: a custom or delegating KnnVectorsReader that forwards what its caller gave it, a codec that searches a reader opened through KnnVectorsFormat.fieldsReader, or a tool that calls CodecReader.getVectorReader() (CodecReader.java:80-85, "Expert" and @lucene.internal).
  • Also hit, but against its own javadoc: a caller of LeafReader.searchNearestVectors on a CodecReader that passes null: CodecReader.searchNearestVectors forwards its caller's value unchanged (CodecReader.java:294), so it gets the same NPE, but LeafReader's @param no longer allows null.
  • Who is not: the kNN queries always build a non-null AcceptDocs (AbstractKnnVectorQuery.java:253 with fromLiveDocs, :257-258 with fromIteratorSupplier); CheckIndex passes AcceptDocs.fromLiveDocs(null, maxDoc) since #15011. One Lucene test still passes null, to a flat reader whose search does nothing (see Fixes).
  • Config: the default codec, no setting; one document is enough; assertions on and off give the same NPE.
  • Symptom: with the default HNSW reader, a non-empty field and k > 0, loud and immediate on the first search. Never a wrong result, filter bypass or index damage; the message names the argument, and the workaround is one call.
  • Reader authors are misled too: the text tells implementers to accept null; open sandbox PR #16709's new reader null-guards acceptDocs. A downstream vector plugin copied the sentence onto its own overrides.
  • How likely: rare. No report since 10.3.0 (2025-09) surfaced in the searches.

Why it looks unintended

#
  • #15011's merged change is consistent with a non-null contract: a review question about forbidding null got no reply, and CheckIndex's search(..., null) calls became AcceptDocs.fromLiveDocs(null, maxDoc).
  • It rewrote LeafReader's @param acceptDocs texts without the null clause; only this text was left.
  • The text still names {@link Bits} for an AcceptDocs parameter: it dates from the 2021 signature.
The full argument159 words
  • #15011's merged change is consistent with a non-null contract. In its review jpountz asked (2025-07-30) "Should we set the contract of this method so that acceptDocs is not allowed to be null?"; the question got no reply, and the thread does not state the contract. The merged commit 310ef63d827 makes Lucene99HnswVectorsReader dereference acceptDocs, rewrote LeafReader's @params without the null clause and changed CheckIndex's two search(..., null) calls to AcceptDocs.fromLiveDocs(null, codecReader.maxDoc()). It left only the KnnVectorsReader text.
  • The sentence is from the old signature. It was written in 6993fb9a998 (LUCENE-10040, #239, 2021) when the parameter was a Bits and the reader handled null; it still names {@link Bits}.
  • Nothing else documents the change for this method. No AcceptDocs javadoc, CHANGES or MIGRATE entry says null is forbidden; the 10.3.0 CHANGES entry for #15011 names only LeafReader#searchNearestVectors.
  • It spread. #16383 (fp16 vectors, 2026-07-27, main only) copied the sentence onto the new short[] overload.
The devil's-advocate check170 words

Strongest case: the API is expert. The shortest route to the reader, CodecReader.getVectorReader(), is @lucene.internal; AcceptDocs itself is @lucene.experimental (AcceptDocs.java:33); the {@link Bits} makes the text look stale to a careful reader; and the NPE is the intended behaviour.

Why it fails: the repro reaches the reader through the public codec-extension SPI (FilterCodec and KnnVectorsFormat.fieldsReader) and uses nothing @lucene.internal. FilterCodec (FilterCodec.java:44, protected constructor), like AcceptDocs, is @lucene.experimental, and so are the SegmentReadState, SegmentWriteState and TopKnnCollector the test touches; KnnVectorsReader, KnnVectorsFormat and Codec are untagged, and TestUtil.getDefaultCodec() is a test-framework helper. So this is the expert codec-extension route, not a stable application API. Still, the @param is the only documentation of this argument and it names null as allowed; null compiles and was the in-tree idiom up to 10.2 (CheckIndex). The intended runtime is why the fix is in the javadoc. The expert reach sets the priority to Low; it does not make the text right.

Suggested fix

#

Recommended Correct the javadoc (recommended)

Correct the @param on the three search overloads: acceptDocs is an AcceptDocs and must not be null; to allow all documents, pass AcceptDocs.fromLiveDocs(null, maxDoc). Javadoc only: the default reader and Lucene's production callers already work this way.

-   * @param acceptDocs {@link Bits} that represents the allowed documents to match, or {@code null}
-   *     if they are all allowed to match.
+   * @param acceptDocs {@link AcceptDocs} that represents the allowed documents to match; must not
+   *     be {@code null}. To allow all documents, pass {@link AcceptDocs#fromLiveDocs(Bits, int)
+   *     AcceptDocs.fromLiveDocs(null, maxDoc)}.

Trade-offs

No code changes; it states the non-null contract that #15011's code and its other javadoc edits imply, which Lucene's production callers follow. It sets a stricter base-class contract than some implementations enforce (a flat reader's search ignores the argument). Optional, with the same fix: Lucene's backward-codecs test TestLucene99ScalarQuantizedVectorsFormat.testSearch (:104) still calls search("f", new float[] {1, 0}, null, null), which works only because a flat format's search does nothing (FlatVectorsReader.java:51-54); under the corrected javadoc that call is off-contract (not changed or run).

Downstream note

#

Downstream code that calls or wraps KnnVectorsReader.search (custom codecs, vector plugins; one plugin copied this sentence onto its own overrides) should pass AcceptDocs.fromLiveDocs(null, maxDoc) for all documents, never null.

How it was found

#

A proof-obligation audit of KnnVectorsReader.search's contract (semi-formal) checked each documented input against what the readers do with it. The documented null for acceptDocs is not handled: the default reader calls acceptDocs.cost() unconditionally. A one-document JUnit test on main confirmed it.

The method in full85 words

The audit took each documented input of the codec SPI method and checked it against the code that consumes it. Here the obligation is that search with acceptDocs == null behaves as "all documents allowed". In Lucene99HnswVectorsReader.search (:369-370) the first use of the argument is acceptDocs.cost() with no null check, and PerFieldKnnVectorsFormat forwards the value unchanged, so the obligation fails for every input. An executable JUnit test on main f794ff5a505c witnessed it, and passing AcceptDocs.fromLiveDocs(null, maxDoc) instead made the search return the document.

Summary
You take the default codec's vectors reader through the public codec SPI (a FilterCodec whose KnnVectorsFormat keeps the reader that fieldsReader opens) and call search("v", query, collector, null), because the @param acceptDocs of every KnnVectorsReader.search overload says '{@link Bits} that represents the allowed documents to match, or {@code null} if they are all allowed to match'. You expect an unfiltered search that collects the segment's one document. Instead Lucene99HnswVectorsReader.search throws NullPointerException ('Cannot invoke "org.apache.lucene.search.AcceptDocs.cost()" because "acceptDocs" is null'): since #15011 (10.3.0) the parameter is an AcceptDocs that the readers dereference and 'all documents' is AcceptDocs.fromLiveDocs(null, maxDoc), but the javadoc still describes the old nullable Bits.
