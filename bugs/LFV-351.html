FacetSets.adoc says each facet-set matcher counts documents, but MatchingFacetSetsCounts counts matching facet sets

The facet-set guide says MatchingFacetSetsCounts counts how many documents each matcher matches, but the code adds 1 per matching facet set: one document with (Thriller, 2020) and (Thriller, 2021) gives a "Thriller 2020-2022" matcher 2, while the total is 1. Tests pin the per-set count; the docs need fixing.

The finding in 30 seconds

#

For each hit document, MatchingFacetSetsCounts decodes every facet set and asks every matcher about it; a matcher that accepts k sets of one document gets k. The total, FacetResult.value, counts that document once. Nothing remembers that a matcher already counted the document.

Background: facet sets

#
  1. A facet set is a tuple of dimension values, such as (genre, year). A FacetSetsField stores a list of them in one document; the guide's motivating example is one document per actor, whose (genre, year) combinations it indexes as facet sets (FacetSets.adoc:36-38, :123-124).
  2. At search time MatchingFacetSetsCounts takes a list of matchers: an ExactFacetSetMatcher accepts one tuple, a RangeFacetSetMatcher a box of ranges, such as genre Thriller and years 2020 to 2022.
  3. It returns a FacetResult: value is the number of matching documents, plus one label value per matcher.

The finding, step by step

#
  1. You index one actor document whose FacetSetsField holds two (genre, year) facet sets, (Thriller, 2020) and (Thriller, 2021), genre encoded as 1: the guide's movie-actors example, indexed as facet sets as the guide itself assumes.
  2. You count with MatchingFacetSetsCounts and one RangeFacetSetMatcher "Thriller 2020-2022". FacetSets.adoc says it "counts how many documents are matched by each of a list of FacetSetMatcher", so you expect 1.
  3. You get 2 for the matcher, while FacetResult.value, the number of matching documents, is 1. The bundled demo does the same: 2 city documents give "Eighty to Hundred Degrees" 4.
  4. Why: for each document the code loops over its facet sets and adds 1 to every matcher that accepts the set (counts[j]++), but adds 1 to the total only once per document.
  5. The per-set count looks intended: the class javadoc says "counts for each given FacetSet" and the demo test asserts 4 for 2 documents. So the text is what should change, not the code.

Who is affected

#

Facet-set users whose hit documents hold two or more sets one matcher accepts: a range matcher when a document has several sets inside its ranges, as in the demo, or an exact matcher on a repeated set. Read as documents, as the guide says, the value is too high; hits and total are right. Opt-in, @lucene.experimental.

Mechanism, terms and numbers525 words

The facet-set user guide, lucene/facet/docs/FacetSets.adoc, which the package javadoc points to, says MatchingFacetSetCounts is "A Facets implementation which counts how many documents are matched by each of a list of FacetSetMatcher, in addition to counting the total number of documents that were matched", and its motivating table counts actors, one document each. The code adds 1 to a matcher's count for every facet set of a hit document that the matcher accepts, and adds 1 to the total (FacetResult.value) once per document. So one document holding (Thriller, 2020) and (Thriller, 2021) gives a "Thriller 2020-2022" range matcher 2 while FacetResult.value is 1. The bundled demo shows the same, 4 for 2 city documents, under a javadoc that says "Counting documents", and its upstream test asserts the 4. The per-set count is pinned by upstream tests and very likely intended, so this is a documentation defect: the guide and the demo javadoc should say that each matcher counts matching facet sets. It has been so since facet sets first shipped in 9.3.0.

The numbers

#
  • The repro: one document with (1, 2020) and (1, 2021), matcher "Thriller 2020-2022": label value 2, FacetResult.value 1.

Exposure and likelihood228 words
  • Who: users of MatchingFacetSetsCounts with ExactFacetSetMatcher, RangeFacetSetMatcher or a custom matcher. Several sets per document is the documented shape (FacetSets.adoc:98-99: a field "which lets you index a list of FacetSet"; FacetSetsField.java:23-26). A matcher that accepts at most one set of each hit document gives the document count (the controls of the independent reproducer and of the executed cross-model review pass).
  • Default vs opt-in: opt-in, experimental module API; no codec, flag or scale condition. The smallest case is one document with two sets.
  • Effect: silent. A facet UI that labels the matcher's value as actors or documents shows a number larger than the number of documents the matcher matched whenever a hit document has two or more sets it accepts; with one matcher it is then also larger than FacetResult.value.   • No stock alternative: the constructors take only the field, the hits, the decoder, an optional fastMatchQuery and the matchers (MatchingFacetSetsCounts.java:52-85), so an application that needs per-document counts must write its own Facets.
  • Likelihood: plausible but limited. Facet sets are niche; a GitHub code search for the class name found no use of MatchingFacetSetsCounts in the Elasticsearch, OpenSearch or Solr repositories (2026-10-26, repeated 2026-11-01; a control query returned hits), and the prior-report searches found no report since 9.3.0 (2022).

Why it looks unintended

#
  • The guide states the quantity: "counts how many documents are matched by each of a list of FacetSetMatcher", and its example table counts actors.
  • The demo javadoc says "Counting documents" directly above code whose upstream test asserts 4 for 2 documents.
  • Other facet counters count a multi-valued document at most once per label (FacetResult.value, the range counters, LongValueFacetCounts).
The full argument236 words
  • The guide: the ordinary reading of FacetSets.adoc:119-120 is a count of distinct documents per matcher, which a value larger than the number of matched documents contradicts. Its motivating table counts actors (:27), one document per actor (:13-23), whose (genre, year) combinations the guide indexes as facet sets (:36-38, :123-124). The automotive-parts motivation counts parts too: aggregating on sub-fields "will lead to a wrong count of 2 (in the above example) instead of 1" (:66-69).
  • The demo: CustomFacetSetExample.java:206 says "Counting documents which match a certain degrees value for any date"; TestCustomFacetSetExample.java:54, :57 assert value 2 and label 4.
  • Other facet counters: FacetResult.value: "If a document contains multiple values for the same path, it will only be counted once in this value" (FacetResult.java:30-35); the range counters roll multi-valued counts up per document "so that counts don't get double-counted" (range/OverlappingLongRangeCounter.java:211-216); LongValueFacetCounts skips a value repeated within one document, "do not increment the count for duplicate values" (LongValueFacetCounts.java:263-276, :271; #191). Association facets aggregate weights, not counts, and are not compared here.
  • The authors described it both ways: in the #841 design discussion shaie wrote that the class "counts how many documents each matcher matched as well as how many documents matched overall" (2022-05-31); in #11664 (2022-07-12) mdmarshmallow, the PR's author, described counting matching "points". Nobody discussed several matching sets in one document.
The devil's-advocate check194 words

Strongest case (the study's intended-behaviour verifier and cross-model reviews, OpenAI GPT-5.6): the per-set count is the intended, tested semantics. The class javadoc says "Returns the counts for each given FacetSet" (MatchingFacetSetsCounts.java:36); a matcher evaluates one set at a time; TestRangeFacetSetMatcher adds 1 per matching set to its expected child counts and 1 per document to its expected value (TestRangeFacetSetMatcher.java:66-94, :123); the demo test pins 4 for 2 documents; the API is @lucene.experimental; the adoc line is a loose summary.

Why it fails: it succeeds against calling this a counting bug, which is why it is classed as a documentation defect. It does not make the documentation right: the guide names a different quantity (documents) from the one computed (sets), a matcher that accepts several of one actor's facet sets (a year range, or a repeated set) would report more than the number of actors the guide's table counts, and the demo javadoc says "documents" right above the asserted 4 for 2. The per-set semantics are strongly supported but not proven to be what the authors meant (shaie's #841 comment says documents), so the maintainers may pick either meaning.

Suggested fix

#

Recommended A. Say that each matcher counts facet sets (recommended)

Fix the text, not the code: FacetSets.adoc (and the demo javadoc) should say that each matcher counts the matching facet sets of the matching documents, so one document can add more than 1 and a matcher's count can exceed the total. Text only; the facet-set and demo tests pass. Per-document counting is the maintainers' alternative; it breaks 7 upstream tests.

B. Count each document at most once per matcher (maintainers' alternative) (validated by the checks)

#

Keep a boolean[] per document in MatchingFacetSetsCounts.count and skip a matcher that already matched an earlier set of the same document (+5/-1 lines).

if (matchedInDoc[j] == false && facetSetMatchers[j].matches(dimValues)) {
  // count each document at most once per matcher
  matchedInDoc[j] = true;
  counts[j]++;
  shouldCountDoc = true;
}

Trade-offs

  • Makes the guide's sentence true and matches the range facets' once-per-document rule.
  • Changes the results of an API shipped since 9.3.0 and reverses semantics the tests pin: 7 upstream tests need new expected values, plus a CHANGES/MIGRATE note.
  • Per-set counts may be what some users want ("how many readings were in range"); an opt-in per-document mode (a flag or a separate class) is a third way, not written or run here.
  • As written it stops calling a matcher's matches() for the later sets of a document once that matcher has matched. The stock matchers are stateless, so results do not change, but FacetSetMatcher does not promise that a custom matcher has no side effects (FacetSetMatcher.java:49-54); calling matches() for every set and gating only counts[j]++ avoids that (not run here).
