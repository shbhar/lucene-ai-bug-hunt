STRING sort pruning reports a terms/doc-values mismatch with false counts

A pruned STRING sort on a field whose terms index has fewer terms than its SORTED doc values throws the intended IllegalStateException, but prints one loop counter as both counts: 1 term against 3 reads "Terms have more than 1 unique terms while doc values have exactly 1 terms". Only the text is wrong, since 9.4.0.

The finding in 30 seconds

#

The check that throws is right: the data breaks a documented requirement. The two numbers it prints are not.

Background: how a STRING sort skips documents

#
  1. A STRING sort reads each document's value from SORTED doc values: a sorted dictionary of the field's distinct values, numbered 0, 1, 2, ... (ordinals).
  2. Once the top-N queue is full and enough hits are counted, only values that sort before the queue's worst one can still compete. If the field is also indexed, Lucene reads the postings of just those terms from the terms index and skips every other document.
  3. To collect those postings it seeks the first competitive doc-values term in the terms index and steps forward one term per ordinal. That only works when both hold the same values, which SortField documents as a requirement.

The finding, step by step

#
  1. Index 3 documents. Each has StringField("f", "a"), so the terms index of f holds 1 term. Their SortedDocValuesField("f", ...) values are c, a and b, so the doc values hold 3. (SortField requires both to hold the same data; this breaks it on purpose.)
  2. Sort all documents on f as STRING, top 1, total-hits threshold 1. At the second hit Lucene starts pruning: it finds doc-values term a (ordinal 0) in the terms index and steps forward one term per ordinal.
  3. You expect the documented reaction, an IllegalStateException, saying the terms index ran out of terms before the doc values: 1 term against 3.
  4. You get the exception with "Terms have more than 1 unique terms while doc values have exactly 1 terms". The step to ordinal 1 found no next term, and the code printed that ordinal, 1, for both counts. Same with assertions on and off.

Who is affected

#

Only applications that sort on a field whose terms and SORTED doc values hold different data, for example raw terms next to lowercased doc values for case-insensitive sorting (#12067). They get an exception either way; this one quotes counts that are not the index's and can point at the wrong side. Default codec and pruning, every release since 9.4.0.

Mechanism, terms and numbers661 words

When a STRING sort prunes non-competitive hits on a field that is indexed both as terms and as SORTED doc values, TermOrdValComparator's PostingsBasedCompetitiveState.init seeks the doc-values term of the first competitive ordinal in the terms index and then calls terms.next() once per further ordinal. If the terms index has no next term while the doc values still have ordinals to match, it throws IllegalStateException("Terms have more than " + ord + " unique terms while doc values have exactly " + ord + " terms") (TermOrdValComparator.java:644-649 on main 5adff78bb168). Both numbers are the loop variable. The doc values still have ordinal ord at that point, so "exactly ord" is false on every throw; with 1 term against 3 the first half is false too, and the message points at the wrong side. The exception itself is intended: SortField documents that this pruning relies on the terms index and doc values holding the same data. Introduced with the feature in 9.4.0; still on upstream main. A reworded message fixes it (validated).

Mechanism (TermOrdValComparator.java at 5adff78bb168)

#
  1. With pruning on (the default), a STRING sort on a field that has indexed terms uses PostingsBasedCompetitiveState when the segment qualifies for skipping, for example when every document has a term (:254-282, shouldEnableSkipping at :295-306). With pruning off there is no competitive state (:254-256).
  2. When the queue is full and the hit count passes the threshold (totalHits > totalHitsThreshold, TopFieldCollector.java:72), updateCompetitiveIterator computes the competitive ordinal range [minOrd, maxOrd] (:417-497), asserts maxOrd < termsIndex.getValueCount() (:498) and calls update (:499); for a range of at most min(1024, maxClauseCount) ordinals, update calls init (:598-607).
  3. init (:629-659) seeks the doc-values term of minOrd in the terms index; if it is missing it throws the sibling message "Term ... exists in doc values but not in the terms index" (:636-638), which is correct. Then for each ord from minOrd + 1 to maxOrd it calls terms.next() (:642).
  4. Fix site. When terms.next() returns null it throws "Terms have more than " + ord + " unique terms while doc values have exactly " + ord + " terms" (:644-649).
  5. Why it is false. The doc values still have ordinal ord (ord <= maxOrd < getValueCount()), so they hold at least ord + 1 terms: "exactly ord" is false on every throw. The terms index ran out after ord - minOrd terms counted from the term of minOrd, so "more than ord" is false in the repro (1 term) but can be true in other shapes.

The repro, step by step

#

Doc values a (0), b (1), c (2); terms index a. The first hit, c, fills the top-1 queue. At the second hit pruning starts with minOrd = 0 (the field is dense, :436-437). init finds a; at ord = 1 terms.next() returns null: "Terms have more than 1 unique terms while doc values have exactly 1 terms".

Other data shapes (a probe on main, assertions off, default codec)

#
  • Terms {a, b}, doc values {a, b, c, d, e} (2 and 5): "more than 2 ... exactly 2".
  • Raw terms {Mango, Zebra, apple} next to lowercased doc values {apple, mango, zebra} (3 and 3, the shape of #12067): "more than 1 ... exactly 1"; here the first half happens to be true, the second is still false.
  • Terms {x}, doc values {a, b, c}: the correct sibling message.

The opposite mismatch (an extra term in the terms index inside the range) is caught only by the assert on the next line (:651), without a message. With assertions off the loop then adds that term's postings under ord (:652) and the search goes on; what that does to the results was not examined here, and it is outside this bug.

Exposure and likelihood179 words
  • Who is hit. Code that indexes different data into a field's terms and its SORTED doc values and sorts on that field with pruning on (the default, SortField.java:219): raw StringField terms next to lowercased doc values (#12067), or a custom analyzer on the indexed side (a downstream project met the sibling message that way, JanusGraph/janusgraph#4992). Which of the two messages appears depends on the data.
  • What they lose. Debugging time. On this path no result is wrong, nothing is written, and the exception is thrown with or without this bug.
  • Scale. 3 documents with threshold 1. With IndexSearcher.search(Query, int, Sort) the threshold is 1000 (IndexSearcher.java:100, :733), so pruning cannot start before more than 1000 hits are counted (it also needs a full queue and a competitive state).
  • No path with consistent data was found. A devil's-advocate check tried to reach this branch with consistent data (a document rejected half-way through indexing is rolled back completely) and could not.
  • Workaround. SortField.withoutPruning (SortField.java:215-226), or a separate field for the sort key, as suggested on #12067.

Why it looks unintended

#
  • The exception is intended (SortField documents the same-data requirement); its message exists to describe exactly this case.
  • "doc values have exactly N terms" is false on every throw: the doc values still have ordinal N.
  • The sibling check a few lines up states its case correctly; this text was never discussed, tested or edited.
The full argument213 words
  • Contract. SortField.java:46-48: the SORTED(_SET) optimization "relies on the assumption that the same data is stored in these term index and doc values". Adrien Grand (@jpountz) wrote on #11669 (LUCENE-10633, 2022-07-27) that "this optimization will lead to runtime errors if this assumption isn't met". So an error is the designed outcome; this report accepts it and the repro expects it.
  • The message is a claim about the data. It names a count for the terms index and one for the doc values, and both are the loop variable.
  • The sibling check gets it right. :636-638 names the doc-values term that is missing from the terms index. The two checks were written together in eb7b7791ba6.
  • Tests and history. No test in lucene/ asserts either message (a grep of all .java files under lucene/ finds both texts only in TermOrdValComparator.java). #1023 has no reviews, review comments or issue comments (re-checked on GitHub 2026-11-06), and git log -S/-G find no edit since.
  • Likely slip. The subjects look swapped: in the repro, "doc values have more than 1 term while the terms index has exactly 1" would be true. Swapping alone is still wrong in the #12067 shape (3 and 3), because the loop counts terms only from the term of minOrd on.
The devil's-advocate check90 words

"The data breaks a documented requirement, the IllegalStateException is the intended outcome, and no javadoc or test fixes the wording; the message still says terms and doc values disagree." This was the cross-model reviewer's position (OpenAI GPT-5.6); it reproduced the message and agreed on the cause.

Why it fails: it defends the exception, which this report accepts. It cannot defend the text, whose only job is to describe this misuse and which prints the loop counter as both counts. It does bear on impact: hence Low, and a one-line fix.
