DoubleMetaphoneFilter drops the alternate code of a token that already equals its primary code, so "JR" gets only JR while "jr" gets JR and AR

DoubleMetaphoneFilter drops the alternate (secondary) code of any token whose text already equals its primary code: "jr" is indexed as JR and AR, but "JR" only as JR. A search on AR finds 1 of the 2 documents "jr" and "JR", in every release since Solr 1.4.0 and Lucene 3.6.0.

The bug in 30 seconds

#

One repeated condition: the check that rightly skips a primary code equal to the token is also part of the alternate's condition, so a token that already is its own primary code never gets its alternate.

Double Metaphone in three lines

#
  1. The encoder turns a word into two upper-case sound codes, a primary and an alternate: "Kuczewski" gives KSSK and KXFS, "jr" gives JR and AR. Codes are cut to maxCodeLength (default 4).
  2. DoubleMetaphoneFilter replaces each token with its codes (inject=false), or keeps the token and adds the codes at the same position (inject=true, the factory default).
  3. A document and a query whose words share either code then match.

The bug, step by step

#
  1. You analyse a field with DoubleMetaphoneFilter, here the factory's documented chain: whitespace tokenizer, then doubleMetaphone with its defaults (inject=true, maxCodeLength 4), no lower-casing. You index two documents, "jr" and "JR".
  2. You expect both to get the codes JR and AR: the encoder ignores letter case and returns primary JR and alternate AR for either spelling. A search on either code should find 2 documents.
  3. You get "jr" indexed as jr, JR, AR, but "JR" only as JR. TermQuery JR finds 2 documents; TermQuery AR finds 1.
  4. Why: the filter skips a primary code equal to the token text (right: the token already is that term), but the alternate's condition repeats the same check, !primaryPhoneticValue.equals(v) (DoubleMetaphoneFilter.java:90), so the different code AR is dropped too.
  5. Hit: upper-case tokens spelled exactly like their own code, such as J, JR, JFK and SMS (206 of 18,278 upper-case strings of length 1-3), in both inject modes. The primary code is still indexed, and nothing throws.

Who is affected

#

Chains that run DoubleMetaphoneFilter (constructor or doubleMetaphone factory, any settings) on text that is not lower-cased first, such as the factory's own example and Solr's _default phonetic_en field type. Only tokens spelled like their own code are hit, mostly upper-case initials and acronyms; they keep the primary code and lose only alternate-only matches.

Mechanism, terms and numbers637 words

DoubleMetaphoneFilter is documented as "supporting secondary codes": for each token it asks the commons-codec encoder for a primary and an alternate sound code and emits both, replacing the token (inject=false) or next to it (inject=true). The encoder ignores letter case, so "jr" and "JR" both have primary JR and alternate AR. The filter skips a primary code equal to the token text, because the kept token already is that term; but the alternate's condition repeats that check (DoubleMetaphoneFilter.java:90), so a token that already equals its primary code never gets its alternate. "jr" is indexed as JR and AR, "JR" only as JR, and a search on AR finds 1 of the 2 documents. Only tokens spelled exactly like their own code are hit, in practice upper-case initials and acronyms such as J, JR, JFK and SMS; no lower-case string was hit in a probe of every A-Z string of length 1-3. The primary code is always kept, nothing throws and the index is not damaged. The check came with a 2009 rewrite (SOLR-1359), before the first release that shipped the class, so Solr 1.4.0 and Lucene 3.6.0 to 10.5.2 and main are affected. Deleting only the check is not a fix (replace mode would lose the primary); keeping the token as the primary and stacking the alternate on it is.

Terms

#
  • Primary and alternate code: Double Metaphone gives a word two codes for its two most likely pronunciations; for many words they are equal. The commons-codec encoder returns them through doubleMetaphone(v) and doubleMetaphone(v, true); it upper-cases internally, so letter case does not change the codes.
  • inject: inject=true keeps the original token and adds the codes at position increment 0; inject=false replaces the token with its codes.
  • maxCodeLength: codes are cut to this length (factory default 4).

The bug

#
  1. incrementToken computes primaryPhoneticValue and alternatePhoneticValue for the token text v (DoubleMetaphoneFilter.java:68-69).
  2. The primary branch runs only when the primary is non-empty and !primaryPhoneticValue.equals(v) (:75-77). That skip is right: when the token already equals its primary code, the kept token carries that term.
  3. The alternate branch requires a non-empty alternate that differs from the primary, and again !primaryPhoneticValue.equals(v) (:87-90). For "JR" the primary JR equals the token, so the alternate AR is skipped although it is a different code.
  4. Nothing was queued, so the token is returned unchanged (:102-104): "JR" becomes [JR] in both modes, while "jr" becomes [JR, AR] (inject=false) or [jr, JR, AR] (inject=true).
  5. The term is load-bearing in replace mode: with inject=false the token is not captured before the alternate overwrites the term, so deleting only the term turns "JR" into [AR] and loses the primary (executed). A fix must keep the token as the primary and stack the alternate on it.

Exposure and likelihood308 words
  • Who is exposed. Any chain with the public DoubleMetaphoneFilter constructor or the doubleMetaphone factory (DoubleMetaphoneFilterFactory.java:40), with the defaults (inject=true, maxCodeLength=4) or any other settings, on text that is not lower-cased first. The factory's own javadoc example has no lower-casing filter (:26-32). The filter is opt-in: no stock Lucene analyzer uses it.
  • Downstream defaults (read on 2026-10-28, not run): Solr's _default configset field type phonetic_en (dynamic fields *_phon_en) is the standard tokenizer + doubleMetaphone inject="false"; the Elasticsearch analysis-phonetic plugin builds this filter for the encoder double_metaphone, with replace defaulting to true (inject=false) and max_code_len to 4; the follow-up read the same for OpenSearch. Whether a user's chain lower-cases first is up to them.
  • What it takes. A token whose exact text equals its own primary code: upper-case, consonant-heavy initials and acronyms no longer than maxCodeLength (J, JR, JFK, SMS). For such a token it happens every time at index time, at any index size, with assertions on or off. A query analysed by the same chain runs the same filter code, so it loses the alternate too (reasoned from the code; no query parser was run).
  • What changes for the user. Every match through the primary code still works (TermQuery JR finds both documents). Only matches that go through the alternate code alone are lost (TermQuery AR: 1 of 2). For acronyms such a match is mostly a weak phonetic one: words whose only code is AR include "air" and "year".
  • What does not happen. No exception, no extra or changed term, no position or offset change, no index damage.
  • Workaround. A lower-casing filter before DoubleMetaphoneFilter: no lower-case string was hit in the probe (0 of 18,278 A-Z strings of length 1-3; other characters were not probed exhaustively), and lower-case words get both codes.

Why it is a bug, not intended

#
  • Documented as "supporting secondary codes"; SOLR-813 added the filter to emit the alternate when it differs from the primary.
  • The encoder ignores case, yet "jr" keeps AR and "JR" loses it, and "JFK" loses its alternate only from maxCodeLength 3 on.
  • The check came with a 2009 rewrite about skipped tokens (SOLR-1359); before it, "J" gave J and A.
The full argument360 words
  • Contract (implicit). Class javadoc: "Filter for DoubleMetaphone (supporting secondary codes)" (DoubleMetaphoneFilter.java:28). SOLR-813 (2008), which added the filter, says the existing PhoneticFilter "ignores the alternate encodings that the encoder provides for some words"; its contributor wrote that the new filter "checks to see if there is an alternate encoding for the token, and adds that to the stream as well, if it's different then the default encoding. This is part of the strength of the DoubleMetaphone implementation". The Solr Reference Guide says PhoneticFilter "will not provide the second (\"alternate\") encoding that is generated by the Double Metaphone Filter for some tokens". No sentence covers a token equal to its code.
  • Tests. TestDoubleMetaphoneFilter.testAlternateInjectFalse expects "Kuczewski" -> KSSK, KXFS (:42-46); no upstream test has a token equal to its own primary code.
  • No documented exception for upper-case or code-shaped tokens in the javadoc, the factory, CHANGES or MIGRATE; the factory's example chain does not lower-case.
  • History. Before SOLR-1359 the alternate was emitted whenever it was non-empty and different from the primary: the previous file version (572d84c9c27) gives "J" -> J, A (executed). The rewrite 551e52f899a (2009-08-13, "DoubleMetaphone filter could skip or reorder tokens, fix and update to new API") added !primaryPhoneticValue.equals(v) to both branches. In the primary branch it removes a real duplicate (inject mode had given "J" -> [J, J, A]); in the alternate branch it removes a different code. The commit, the JIRA issue, the 2009 solr-dev@ thread "DoubleMetaphone bugs?" and CHANGES discuss only skipped or reordered tokens and keeping the original token "if there are no phonetic alternatives"; the commit added no test.
  • A poor fit for a deliberate rule. The result flips with letter case, although the encoder ignores case, and with maxCodeLength; codes that are not fixed points of the encoder are still re-encoded ("XMT" -> SMT, "KSSK" -> KSK); in inject=true mode the term is not needed to keep the token (it is captured first anyway) and only suppresses the alternate and the state captures that emitting it takes. An equality test behaves like this by nature, so these points make a deliberate "already phonetic" rule less likely, not impossible.
The devil's-advocate check231 words

The strongest case for "intended" (the cross-model reviewer's intended lens, the independent reproduction and the intended-behaviour check): a token that already is its own code is treated as already phonetic and passed through untouched. PhoneticFilter has a similar identity check (PhoneticFilter.java:74), the same committer fixed PhoneticFilter's duplicate tokens (SOLR-1360) the same day, the term is load-bearing in replace mode, the class promises only "supporting secondary codes", and alternates of acronyms are arguably noise.

Why it is weaker than it looks: the check compares the primary with the token, not the alternate, so in the alternate branch it never prevents a duplicate; PhoneticFilter's check drops only an output equal to the input; an equality test recognises only codes that are fixed points of the encoder at the chosen length, so it separates "JR" from "jr" and still re-encodes "XMT", a poor fit for an "already phonetic" rule (though it does not rule one out); no commit, issue or comment states such a rule; and the fix meets the replace-path concern without dropping the alternate. The cross-model reviewer rated the argument moderate, and so did the later cross-model fact check, which called this rebuttal partly fair but incomplete; the independent reproduction, the intended-behaviour check, the adjudication and the credibility audit rejected it. What survives is the narrow reach and the implicit contract: reasons for low priority, not for keeping the behaviour.

Suggested fix

#

Recommended A: keep the token as the primary, stack the alternate on it

Keep the token as the primary code and stack the alternate on it at position increment 0: drop the repeated check from the alternate's condition and add a branch for a token equal to its primary (+5/-2). A: keep the token as the primary, stack the alternate on it (validated by the checks) (recommended)

The finder's fix, rebased on a9779ef3c193. When the token equals its primary code it is kept as is, and the alternate (when non-empty and different) follows at position increment 0, the same codes as the lower-case spelling. Tokens whose primary differs from their text take exactly the old path.

Trade-offs

  • Only tokens that equal their primary code and have a different alternate change: they gain the alternate. Indexes built before the fix lack these terms until reindexed. Plain positive term matching on a rebuilt index only gains matches, but a negated clause (MUST_NOT) on the alternate code now excludes such documents, scores and top-k shift, and a mix of old and new segments (or an old index with the new query analysis) sees a partial change. A CHANGES entry should say so.
  • Input that already is a code changes too: a stand-alone "JR" now gives JR and AR, so a pipeline that knowingly feeds codes, or a chain that runs the filter twice, gets the alternate of such a code as well.
  • Cost on an affected token: two captureState() calls and one more output token (stock makes no capture there; the lower-case spelling costs as much or more, by reading the code). Performance was not measured.

B: workaround, lower-case before the filter (no code change)

#

Add LowerCaseFilter (factory lowercase) before DoubleMetaphoneFilter. No lower-case token was hit in the probe: 0 of 18,278 lower-case A-Z strings of length 1-3 lose their alternate (other characters were not probed exhaustively), and the test's controls show lower-case words get both codes.

Trade-offs

With inject=true the kept original token becomes lower case; it does not help existing indexes or the Solr _default schema, and the library stays inconsistent.

Downstream note

#

Solr's _default configset (phonetic_en: standard tokenizer + doubleMetaphone, inject=false, no lower-casing) and the Elasticsearch analysis-phonetic plugin (encoder double_metaphone) build this filter, so upper-case acronyms in such fields lose their alternate code too.

How it was found

#

Semi-formal. A bounded-exhaustive comparison ran the phonetic filters against the commons-codec encoders called directly, on every token of up to 3 characters over a 17-character alphabet plus fixed words (a smaller set for BeiderMorseFilter), alone and in random streams (1,641,300 checks). The only filter-side mismatches were DoubleMetaphoneFilter on "J"; reading the code then located the condition.

The method in full164 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier). The finder's harness compared each phonetic filter's output with the output computed from the encoder library called directly:

  • filters: PhoneticFilter with 14 encoder configurations and both inject modes, DoubleMetaphoneFilter at maxCodeLength 1, 2, 4 and 8 in both modes, DaitchMokotoffSoundexFilter, and BeiderMorseFilter in 32 configurations (on a smaller term set: length up to 2 over 14 characters, 3 fixed words and 200 sampled terms);
  • inputs: every token of length up to 3 over a 17-character alphabet plus fixed words, alone and in random streams of 1-4 tokens with position increments 0, 1 and 2, position lengths 1 and 2, and the keyword flag on or off;
  • result on stock main: 1,641,300 checks, 16 mismatches, all DoubleMetaphoneFilter on the token "J" (expected J and A, got J); with the fix, 0 mismatches in 1,641,332 checks.

Reading the filter then located the repeated condition, and a JUnit test confirmed it on the stock main jars (found 2026-10-26).

LFV-477, snapshot of 2026-10-29

Registry title
DoubleMetaphoneFilter drops the alternate (secondary) code of a token whose text already equals its primary code, so 'JR' gets only JR while 'jr' gets JR and AR
Area
analysis / phonetic (DoubleMetaphoneFilter#incrementToken alternate-code branch; DoubleMetaphoneFilterFactory, SPI name doubleMetaphone)
Priority
Low, rank 438: The opt-in DoubleMetaphoneFilter drops the alternate code of upper-case acronyms when input is not lower-cased first, losing only matches that depend on that weak alternate code, so it joins the rare-input analysis rows after LFV-459.
Impact class
minor
Impact note
Only analysis chains that run DoubleMetaphoneFilter (an opt-in analysis-phonetic filter, through its constructor or the 'doubleMetaphone' factory, at default or any other settings) on text that is not lower-cased first are hit, and only for tokens whose exact text equals their own primary code, in practice upper-case, consonant-only initials and acronyms no longer than maxCodeLength such as J, JR, JFK or SMS: the token keeps its primary code but loses its alternate, so it no longer matches text that shares only the alternate code; no scale is needed, and there is no exception and no index damage.
Summary
You run text through DoubleMetaphoneFilter, documented as 'supporting secondary codes', and expect the token 'JR' to get the same codes as 'jr', because the encoder is case-insensitive and gives both the primary code JR and the alternate code AR. Instead, when a token's text already equals its own primary code, the filter keeps the token as the primary but never emits the alternate: 'jr' gives JR and AR, 'JR' gives only JR, in both inject modes and at every maxCodeLength where the token equals its code. A document containing 'JR' is then missed by a query that matches only through AR (executed: TermQuery AR matches the document 'jr' but not the document 'JR'), while matches through the primary code still work.
