The .cfe grammar in the Lucene90CompoundFormat javadoc leaves out the footer and misstates what FileName holds

The javadoc of the default compound file format describes the .cfe table of contents without the 16-byte checksum footer the writer appends, and says each entry holds the file's name, while the writer stores it without the segment name (.fnm for _0.fnm). Documentation only: Lucene reads its own files correctly.

The finding in 30 seconds

#

The class javadoc that documents the default compound file's table of contents leaves out a part the writer writes, and misdescribes another.

Background: compound files

#
  1. To save file handles, Lucene by default packs a newly flushed segment's files (and a merged segment's, if it is small enough) into one compound file: _0.cfs holds the bytes of _0.fnm, _0.fdt and the others one after another (each start aligned to 64 bytes), and _0.cfe is its table of contents, one entry per file (name, start offset, length).
  2. Like every index file, .cfe starts with an IndexHeader (magic, codec name, version, the 16-byte segment id and a suffix) and ends with a 16-byte codec footer (magic, algorithm id, CRC32 checksum).

The finding, step by step

#
  1. You index one empty document with the default codec and compound files on (the default for new segments). Lucene packs the segment's 4 files into _0.cfs and writes their 150-byte table of contents, _0.cfe.
  2. You decode _0.cfe as the Lucene90CompoundFormat javadoc says: Header (49 bytes), FileCount (4), then 4 entries of FileName, DataOffset, DataLength (21 bytes each). You expect the file to end at byte 134, and the names to be _0.fnm, _0.fdx, _0.fdt, _0.fdm.
  3. You get 16 more bytes after the last entry: the codec footer (c0 28 93 e8, algorithm id, CRC32 checksum). The .cfs line right above lists its Footer; the .cfe line does not.
  4. And the names read .fnm, .fdx, .fdt, .fdm: the writer strips the segment name _0, and Lucene's reader adds it back. Lucene reads its own files fine; only a tool written from the javadoc goes wrong, on every .cfe file since 5.0.0.

Who is affected

#

People who read, inspect or re-implement the .cfe format from this javadoc: format inspectors, ports, recovery or extraction tools. The default codec's overview links this page for the details. Every .cfe file since 5.0.0 is affected, with no setting involved. Lucene's writer and reader agree, so indexing, merging, CheckIndex and search are unaffected.

Mechanism, terms and numbers788 words

A compound segment is two files: .cfs holds the bytes of all the segment's files and .cfe is its table of contents. The class javadoc of Lucene90CompoundFormat, linked from the default codec's file-format overview as "Compound File", gives Compound (.cfs) --> Header, FileData^FileCount, Footer (Lucene90CompoundFormat.java:49 on main 645d4fe14a20) and Compound Entry Table (.cfe) --> Header, FileCount, <FileName, DataOffset, DataLength>^FileCount (:50-51), with no Footer on the .cfe line, and says each entry holds "a String with that file's name" (:65-66). The writer appends a 16-byte codec footer to .cfe (:107) and stores each name with the segment name stripped (:153), for example .fnm for _0.fnm. A decoder that follows the text stops 16 bytes before the end of every .cfe file, and a lookup by the names it read, taken as file names, fails (the segment name is missing). Lucene's reader checks the footer (Lucene90CompoundReader.java:133) and adds the segment name back (:222), so only the javadoc is wrong: the footer part in every release from 5.0.0 to 10.6.0 and on main, the FileName part from 4.0.0 on. The unused Checksum on the type line (:54) belongs to the linked CodecFooter grammar; removing it is cleanup.

The documented grammar (main 645d4fe14a20, Lucene90CompoundFormat.java:49-67)

#
Compound (.cfs) --> Header, FileData^FileCount, Footer
Compound Entry Table (.cfe) --> Header, FileCount, <FileName, DataOffset, DataLength>^FileCount

  Header --> IndexHeader                     (CodecUtil#writeIndexHeader)
  FileCount --> VInt
  DataOffset,DataLength,Checksum --> UInt64
  FileName --> String
  FileData --> raw file data
  Footer --> CodecFooter                     (CodecUtil#writeFooter)

Notes: ... Each directory entry contains a long pointer to the start of this file's data section,
the files length, and a String with that file's name. ...

The .cfe production has no Footer, although Footer is defined (:57) and used on the .cfs line (:49). Checksum (:54) is used by neither production: it is the last element of the linked CodecFooter grammar (CodecUtil.java:396).

What the writer writes (write, :95-109; writeCompoundFile, :113-157)

#
  • CodecUtil.writeIndexHeader(entries, ENTRY_CODEC, ...) (:102), entries.writeVInt(numFiles) (:117).
  • Per file, in ascending size order: entries.writeString(IndexFileNames.stripSegmentName(file)), writeLong(startOffset), writeLong(length) (:153-155). stripSegmentName returns "the filename with the segment name removed" (IndexFileNames.java:133-144); it cuts at the second _ or else the first . (:119-127), so _0.fnm is stored as .fnm, while a per-field file keeps the _ of its suffix (the history probe saw _Lucene50_0.doc stored on 5.0.0-7.7.3).
  • Then CodecUtil.writeFooter(entries) (:107), right after CodecUtil.writeFooter(data) for the .cfs (:106).
  • The reader mirrors it: readMapping reads the string as an id (Lucene90CompoundReader.java:144), CodecUtil.checkFooter verifies the footer (:133), lookups strip the segment name from the requested name (:171, :235), and listAll adds it back (:222).

The bytes of the repro's file (_0.cfe, 150 bytes, main)

byte  49       FileCount = 4 (VInt)
bytes 50-70    FileName ".fnm"  DataOffset 64   DataLength 61    (21 bytes: 1 + 4 + 8 + 8)

The segment id and the checksum differ per run; this one-document index's layout does not. CodecUtil.checkFooter accepts the 16 left-over bytes. The compound directory lists the sub-files as _0.fnm, _0.fdx, _0.fdt, _0.fdm. In the hunt's sweep the same holds for all 87 .cfe files of 91 generated indexes (16 bytes left over in each) and all 1720 entries (stripped names).

How it went stale

#
  • Footer. LUCENE-2446 added writeFooter to both compound files in one change. On trunk (c189d0fb74d, 2014-04-01) the javadoc got , Footer on the .cfs line only, plus Checksum on the type line; the branch_4x backport (819eda82e33, 2014-04-02) put , Footer on the .cfe line instead, so 4.8.0-4.10.4 documented the .cfe footer. The LUCENE-5944 bulk backport (55594bad9b0, 2014-09-18) replaced the branch_5x text with the trunk text, so from 5.0.0 the .cfe line has no Footer. LUCENE-5969 and LUCENE-9705 copied the text into Lucene50CompoundFormat and Lucene90CompoundFormat.
  • FileName. Up to 3.0.x the writer stored the full name and "with that file's name" was right. LUCENE-2455 (d6dd2e234e1, 2010, 3.1) started storing the stripped name, so that entries stay valid when a segment is renamed, and the sentence was not updated; 25a59d8902e (2012-06-11) moved it into the public format docs (4.0.0).
Exposure and likelihood223 words
  • Who is hit. Anyone who decodes a .cfe file without Lucene, or checks one by hand, following the class javadoc. The default codec's overview (lucene104/package-info.java) says it "defines the index file formats used in this version of Lucene" (:50), links this class as "Compound File" (:237) and says "Details on each of these are provided in their linked pages" (:188). Two outside .cfe parsers exist (a 2021 draft format description and a 2018 script); both worked around the text without reporting it.
  • Default vs opt-in. The default codec; compound files are the default for new segments (IndexWriterConfig.java:96-99, DEFAULT_USE_COMPOUND_FILE_SYSTEM = true) and for small segments (package-info.java:195). Every .cfe file Lucene90CompoundFormat writes shows both parts; no setting changes its layout (a segment that is not compound has no .cfe at all).
  • Scale. No runtime effect. The symptom is confined to code written from the text: a decoder stops 16 bytes early and looks for .fnm where the compound directory has _0.fnm; a tool that wrote .cfe files by the text would produce files Lucene's reader rejects at checkFooter (read, not executed). A careful reader who cross-checks the overview's footer note and the reader code can work it out, which keeps the impact minor.
  • Rating. Impact class minor, likelihood plausible, priority low.

Why it looks unintended

#
  • The .cfs line right above lists its Footer; so does every explicit whole-file production in the core codecs but .liv.
  • 4.8.0-4.10.4 listed the .cfe Footer; a 2014 bulk backport replaced that line with trunk text that lacked it.
  • "That file's name" was true until 3.1 (LUCENE-2455), when the writer started stripping the segment name; the sentence was not updated.
The full argument177 words
  • The line above. .cfs --> Header, FileData^FileCount, Footer (:49), with its own Footer type line (:57); both files get a footer in the same method (:106-107).
  • Convention. Every other explicit whole-file production ((.ext) --> ...) in the core codecs names its Footer, for example the norms metadata and data files (Lucene90NormsFormat.java:46, :71), .tvd/.tvx (Lucene90TermVectorsFormat.java:82, :157), .fnm, .si, the terms dictionary, postings and segments_N; the only other production without it is .liv (LFV-970). Formats documented in prose or as file lists (doc values, points, stored fields, vectors) have no such production to compare.
  • History. 4.8.0-4.10.4 listed the Footer on the .cfe line; it was lost when LUCENE-5944 replaced the 4.x text with the trunk text, which had it on the .cfs line instead. No issue or review discusses it.
  • FileName. The sentence describes the pre-3.1 writer, which stored the full name; LUCENE-2455 changed the writer and not the sentence.
  • The contract. lucene104/package-info.java:50 and :188 (quoted under "Who is affected").
The devil's-advocate check304 words

Strongest case for "intended" (made by the refute reviewer, the intended-lens reviewer and the devil's-advocate verifier; the cross-model reviewers rated it moderate): the overview's History says "checksum footers were added to the end of each index file" since 4.8 (package-info.java:381-383), dev-docs/file-formats.md:80-84 says to add headers and footers to all files and TestAllFilesHaveChecksumFooter checks every file, .cfe included, so a per-file grammar need not repeat the footer; the overview calls itself "a high-level definition" (:54); the reader calls the stored string an id (Lucene90CompoundReader.java:144); and CompoundFormat is @lucene.experimental (CompoundFormat.java:28). The .cfs production is not byte-complete either: the 64-byte alignment padding between sub-files is only in the Notes prose. Under the generous footer reading the documented grammar parses all 87 .cfe files of the hunt's sweep.

Why it fails: under that reading the .cfs Footer on the line above would be redundant too, and the explicit whole-file productions in the core codecs do not leave the footer out; the explicit .cfs line invites a literal reading of the .cfe line. "High-level" allows leaving detail to prose, as the .cfs alignment is, not a production that ends 16 bytes early with no prose mentioning those bytes. The id reading conflicts with the plain words "that file's name", which date from when the full name was stored, and the FileName part does not depend on the footer convention at all. @lucene.experimental is about API stability. Committers edited this block twice (LUCENE-10019, #15341) and only touched the alignment note, so that is not an acceptance decision. The generous reading lowers the severity of the footer part; it does not make the text right. The final verdicts of all verifiers and the adjudication kept the defect (the cross-model review with medium confidence), with the intended argument rated moderate by the cross-model reviewers.

Downstream note

#

Not security-sensitive; it matters only to third-party tools that read or write .cfe files themselves from this javadoc, which would stop 16 bytes early or look up the wrong names.

How it was found

#

Semi-formal: a grammar check extracted the .cfe production and its type list from the javadoc and interpreted it over the bytes of 87 real .cfe files from 91 generated default-codec indexes, with each segment's compound directory as the oracle. All 87 ended 16 bytes early and all 1720 entries held the stripped name; the writer's real layout parsed all 87.

The method in full169 words
  • The check extracts the .cfe and .cfs productions and the shared type list mechanically from the javadoc source, checks them for well-formedness (it reports the unused definition Checksum) and interprets them over the real bytes of each compound segment. The oracle is the segment's CompoundDirectory: entry count, every FileName resolving to an inner file, DataLength equal to the inner file length, 64-byte aligned DataOffset.
  • Inputs: 91 indexes (11 fixed and 80 seeded random configurations), 87 compound segments, the same results with assertions on and off.
  • Positive control: the writer-layout grammar (the proposed fix text) parses all 87 .cfe files. Vacuity: 3 of 3 layout mutants (footer dropped, DataLength dropped, DataOffset/DataLength swapped) are killed. The .cfs production parses all 87 .cfs files. Fix check: the corrected text parses 38 of 38 files in a second sweep.
  • The unit's starting lead was a probe that saw 16 bytes after the documented grammar. This is a differential grammar check of documentation against real output, not model checking or a proof.

LFV-971, snapshot of 2026-11-09

Registry title
The file-format javadoc of the default compound format (Lucene90CompoundFormat) gives an incomplete .cfe entry-table grammar: it leaves out the codec footer the writer appends (the .cfs line beside it lists one), and it says each entry holds the file's name although the writer stores the name with the segment name stripped (documentation defect; the writer and reader agree)
Area
codecs / compound files (Lucene90CompoundFormat .cfe file-format javadoc vs the Lucene90CompoundFormat writer / Lucene90CompoundReader)
Priority
Low, rank 1324: The .cfe grammar leaves out the footer, which the package-level footer rule partly covers, and misstates the stored names; it is documentation only.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so indexing, merging, CheckIndex and search are unaffected in every configuration; the people misled are those who read, inspect or re-implement the .cfe format from this class javadoc (the default codec's file-format overview links it as the Compound File format), and a parser that follows the text stops 16 bytes before the end of every .cfe file and takes stored names such as '.nvd' for full file names (executed); compound files are written by default (IndexWriterConfig.DEFAULT_USE_COMPOUND_FILE_SYSTEM = true), the footer has been missing from the grammar in every release since 5.0.0 and the FileName wording has been wrong since 4.0.0, and no scale or special setting is needed.
Summary
You decode the compound entry table (.cfe) of a default-codec segment by following the Lucene90CompoundFormat javadoc, which says the file is Header, FileCount and then FileCount entries of FileName, DataOffset, DataLength, each holding 'a String with that file's name'. The writer also appends a 16-byte codec footer (the .cfs line just above lists its Footer, the .cfe line does not) and stores each name with the segment name stripped, for example '.nvd' for _0.nvd, so a parser built from the text ends 16 bytes early (byte 134 of 150 in the minimal repro, byte 502 of 518 in the hunt's 20-document test) and cannot find the sub-files by the names it read. Lucene's own reader checks the footer and puts the segment name back, so nothing breaks at runtime; only the documentation is wrong (the type line also lists an unused 'Checksum', which belongs to the linked CodecFooter grammar, so dropping it is cleanup).
Introduced

It reached the release line with 55594bad9b07af90de4ab2a2fb0bac8e8c2b0b3c (branch_5x, LUCENE-5944 bulk backport of trunk, apache/lucene#7006), which replaced the 4.x text with the trunk text; carried forward by LUCENE-5969 (apache/lucene#7031, 5893b1da299, Lucene50CompoundFormat) and LUCENE-9705 (apache/lucene-solr#2268, eafeb664340, Lucene90CompoundFormat).
