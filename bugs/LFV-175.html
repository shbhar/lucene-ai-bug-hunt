StoredFieldDataInput(ByteArrayDataInput) takes the input's end position as its length, so a slice or a partly read input stores extra bytes or closes the IndexWriter

new StoredFieldDataInput(new ByteArrayDataInput(bytes, 4, 8)) gets length 12, not 8: ByteArrayDataInput.length() is where the input ends, not how many bytes it holds. The stored value silently gains the 4 bytes after the slice or, at the array's end, addDocument throws and the IndexWriter closes; since 10.2.0.

The bug in 30 seconds

#

StoredFieldDataInput stores a binary field from a DataInput plus a byte count. Its ByteArrayDataInput constructor takes that count from ByteArrayDataInput.length(), which is the input's end position (offset + len). Only when the input is at position 0 is the end position also the number of bytes, so every other input stores too many.

  1. Take a 16-byte array 01 02 ... 10 and store bytes 4 to 11 as a binary field: new StoredField("f", new StoredFieldDataInput(new ByteArrayDataInput(buf, 4, 8))). Plain defaults are enough: new IndexWriterConfig(), the default codec.
  2. You expect field f to hold those 8 bytes, 05 ... 0c, and getLength() to return 8.
  3. Instead getLength() returns 12 and the document stores 12 bytes: the slice plus 0d 0e 0f 10, with no error. ByteArrayDataInput.length() is the end position, 4 + 8 = 12, and the writer copies 12 bytes starting at position 4.
  4. The 12 bytes survive commit and forceMerge(1), CheckIndex reports the index clean, and a fixed Lucene still returns them for that document. An input whose 4-byte header was read first is hit the same way: 16 bytes stored instead of the 12 unread ones.
  5. If too few bytes follow (the same 8-byte slice of a 12-byte array), the copy runs off the array: ArrayIndexOutOfBoundsException, and the IndexWriter rolls back to its last commit and closes, dropping the documents not yet committed (one, in the probe).

Who is affected

#

Applications that store binary values with this @lucene.experimental constructor from a ByteArrayDataInput that is not at position 0: a slice of a larger buffer, or an input partly read first. Plain default settings are enough; every such document. No Lucene code outside tests calls the constructor, and public code search found no downstream caller.

Mechanism, terms and numbers646 words

StoredFieldDataInput (#14213, 10.2.0, @lucene.experimental) stores a binary field straight from a DataInput and a byte count. Its convenience constructor StoredFieldDataInput(ByteArrayDataInput) takes that count from ByteArrayDataInput.length(), which returns the input's end position (offset + len), not the bytes it holds. Both copy implementations (the default codec's writer and the base method other formats inherit) then copy that many bytes from the input's current position, so an input that is not at position 0 (a slice at a non-zero offset, or an input partly read first) stores as many extra bytes from the caller's array as its position, silently: the value survives merges and CheckIndex reports the index clean. When too few bytes follow, the copy throws ArrayIndexOutOfBoundsException inside the stored-fields write, which is an aborting exception, and the IndexWriter closes and rolls back to its last commit. Every release from 10.2.0 to 10.5.2 and main is affected; a one-line fix (length() - getPosition()) passes the repro and the closest test suites.

Terms

#
  • StoredFieldDataInput: a record (DataInput in, int length), "A fixed size DataInput which includes the length of the input", with @param length the length of the data input (StoredFieldDataInput.java:22-29, @lucene.experimental). new StoredField(name, value) stores it as a binary field (StoredField.java:116-122). It was added in 10.2.0 by #14213.
  • ByteArrayDataInput: a DataInput over a byte[] with a read position pos and an end limit. new ByteArrayDataInput(bytes, offset, len) and reset(bytes, offset, len) set pos = offset and limit = offset + len (ByteArrayDataInput.java:39-41, :65-69). length() returns limit (:71-73): an end position, deliberately so since 2011, and Lucene's own readers use it that way (while (in.getPosition() < in.length())).

The bug

#
  1. The convenience constructor is this(byteArrayDataInput, byteArrayDataInput.length()) (StoredFieldDataInput.java:32-34): the end position becomes the byte count.
  2. The default codec's writer writes getLength() as the stored length and copies that many bytes from the input's current position (Lucene90CompressingStoredFieldsWriter.java:312-320). Formats that keep the base method do the same with readBytes (StoredFieldsWriter.java:76-82; SimpleText executed). These are the only two copy implementations in Lucene; the test framework's wrapper writers delegate to them, and index sorting first writes through a temporary default-codec writer. ByteArrayDataInput.readBytes is a plain System.arraycopy that ignores limit (ByteArrayDataInput.java:135-140).
  3. So Lucene copies [pos, limit + pos) instead of [pos, limit): pos bytes too many.
  4. If those bytes exist in the caller's array, they are stored with no error and read back as part of the value (the reader trusts the stored length, Lucene90CompressingStoredFieldsReader.java:293).
  5. If not, arraycopy throws ArrayIndexOutOfBoundsException inside the stored-fields write. IndexingChain treats any exception there as aborting (IndexingChain.java:1504-1509), which becomes a tragic event: the IndexWriter rolls back to its last commit and closes (IndexWriter.java:6098-6106).

Exposure and likelihood355 words
  • Who is exposed. Callers of new StoredField(name, new StoredFieldDataInput(in)) where in is a ByteArrayDataInput built with new ByteArrayDataInput(bytes, offset, len) or reset(bytes, offset, len) with offset > 0 (for example from a BytesRef with a non-zero offset, or a slice of a pooled buffer), or an input that was partly read before wrapping (a header). Every such document is hit.
  • Settings. Plain defaults are enough: a probe with new IndexWriterConfig() (default codec, default merge policy) stores the 12 bytes. The JUnit pins the default codec and takes the rest of its configuration from the test framework's randomized newIndexWriterConfig(). Other stored-fields formats are hit through the base writer method: SimpleText fails the same way (executed with the hardened upstream test).
  • Silent and lasting. In the common case nothing fails: the value is pos bytes too long, made of whatever follows in the caller's array (the next record of a shared buffer, or a previous request's leftovers in a reused one, in a probe). It survives commit and merges, CheckIndex reports the index clean, and a fixed Lucene still returns the extra bytes for segments already written (executed: an index written by unfixed main, opened with the fix, returns 12 bytes for the old document and 8 for a new one).
  • Loud variant. When fewer than pos bytes follow, addDocument throws ArrayIndexOutOfBoundsException and the IndexWriter rolls back to its last commit and closes. A rollback discards every change since the last commit (IndexWriter.rollback() javadoc); the probe shows one buffered, uncommitted document lost besides the bad one (the committed index keeps 1 of the 2 documents added before it), and the next addDocument throws AlreadyClosedException.
  • Bounded. At most pos extra bytes per value, never outside the caller's own array; no query-side effect.
  • How likely. Plausible but narrow. Slicing a buffer is a natural way to build the input (the introducing PR's own test builds it from value.offset), but no non-test Lucene code calls this constructor, and public code search found no downstream caller in the repositories searched (the only hit outside Lucene, a codec wrapper, only delegates writeField; private code is not visible).

Why it is a bug, not intended

#
  • The record documents length as a byte count, and StoredFieldVisitor says readers "must read StoredFieldDataInput#length bytes".
  • The introducing PR's own test builds the input from value.offset and expects exactly value back; it passes only because that offset is always 0, and fails at offset 3.
  • No javadoc asks for an input at position 0.
The full argument264 words
  • Contract. StoredFieldDataInput: "A fixed size DataInput which includes the length of the input", @param length the length of the data input, and getLength() "Returns the length of the data input" (StoredFieldDataInput.java:22-29, :41-44). StoredFieldVisitor.binaryField(FieldInfo, StoredFieldDataInput): "Implementors of this method must read StoredFieldDataInput#length bytes" (StoredFieldVisitor.java:43-45). The reader builds the record with a byte count (Lucene90CompressingStoredFieldsReader.java:293).
  • The author's test. #14213 added to BaseStoredFieldsFormatTestCase.testMergeFilterReader a field b2 = new StoredFieldDataInput(new ByteArrayDataInput(value.bytes, value.offset, value.length)) and asserts it equals value (:687-693, :724-726). value is a fresh BytesRef with offset 0. The same pattern at offset 3 fails: "b2 must equal b expected:<[61 62 63 64]> but was:<[61 62 63 64 7 7 7]>"; with a random offset of 1-5 it fails in the Lucene90 and SimpleText format tests.
  • Same PR, same intent. testNullStoredDataInputField, "test a null data input value doesn't abort the entire segment", asserts no tragic exception and that the earlier document survives (TestIndexWriterExceptions.java:1757-1783). (There the null is rejected by the StoredField constructor before indexing, so it shows intent, not this path.)
  • No precondition anywhere. The constructor's javadoc is "Creates a StoredFieldDataInput from a ByteArrayDataInput" (StoredFieldDataInput.java:31). The #14213 discussion never mentions offsets, slices or length(); CHANGES has only "GITHUB#14213: Allowing indexing stored-only StoredField directly from DataInput" under 10.2.0 (lucene/CHANGES.txt:1920).
  • Effect. Silently wrong stored bytes, or a closed IndexWriter with lost documents, for a valid input built with public constructors.
  • Precedent. LUCENE-4423 (2012), an offset/length bug on the read side of binary stored fields, was fixed as a bug.
The devil's-advocate check309 words

The strongest case for "works as designed": ByteArrayDataInput.length() returning the end position is deliberate and old (LUCENE-3224, 2011, changed limit = len to limit = offset + len; length() returns limit since LUCENE-3030), and Lucene code uses it as an end bound (Lucene104PostingsReader.java:1451). Both classes are @lucene.experimental; ByteArrayDataInput "omits all low-level checks" and even warns that rewind() "sets pos to 0, which is not right if you had called reset w/ non-zero offset!!" (ByteArrayDataInput.java:23-24, :51-55). The canonical constructor StoredFieldDataInput(DataInput, int) handles slices. So the convenience constructor just copies length(), and slice users should pass the length.

Why it fails: the record's length is documented and consumed as a byte count, nothing tells callers the convenience constructor needs position 0, and the introducing PR's own test builds the input from an offset and expects exactly len bytes back. The quirks of ByteArrayDataInput lower the severity; they do not make silently wrong stored data or a closed writer intended. Verdict: a defect in the convenience constructor, not in ByteArrayDataInput. The independent reproduction and the cross-model reviews rated the intended-behaviour argument weak; the intended-behaviour check and the adjudication rejected it without a strength rating.

The partly read input is the weaker half. The cross-model fact check of the brief (2026-10-27, reading only) rates the argument weak for a fresh slice but moderate for an input read partly before it is wrapped: for an input that starts at 0, length() as its total extent is more defensible, and no upstream test wraps a partly consumed input (the #14213 test covers only the slice form). There a documentation-only answer or removing the convenience constructor is a more plausible maintainer response. Still against it: the record's length is consumed as a byte count from the current position, and no javadoc says the input must be unread.

Suggested fix

#

Recommended Use the bytes remaining in the convenience constructor

In the convenience constructor, use the bytes left in the input: byteArrayDataInput.length() - byteArrayDataInput.getPosition(). One line: it fixes slices and partly read inputs and changes nothing at position 0. Values already written keep their extra bytes. It passes the repro and 226 tests of the closest suites.

-  /** Creates a StoredFieldDataInput from a ByteArrayDataInput */
+  /**
+   * Creates a StoredFieldDataInput from a ByteArrayDataInput, holding the bytes from its current
+   * position to its end
+   */
   public StoredFieldDataInput(ByteArrayDataInput byteArrayDataInput) {
-    this(byteArrayDataInput, byteArrayDataInput.length());
+    // ByteArrayDataInput#length() is the end position of the input, not the number of bytes left
+    this(byteArrayDataInput, byteArrayDataInput.length() - byteArrayDataInput.getPosition());
   }

Until a fix ships, pass the length explicitly, new StoredFieldDataInput(in, len), or wrap a fresh ByteArrayDataInput at position 0 over an array that holds exactly the value. A fix does not rewrite segments already written: users who used the pattern need to check and reindex.

Trade-offs

  • Unchanged for every input at position 0, which covers all of Lucene's own callers (TestBinaryDocument, TestDirectoryReader, BaseStoredFieldsFormatTestCase).
  • Does not repair values already written; the issue should say so.
  • Expected cost: one accessor call and one subtraction when the record is built; not benchmarked. The same line is on branch_10x and branch_10_6 (read), so the diff should apply there; the fix ran against the 10.2.0 jars, not the branch heads.
  • Unchanged by the fix: the record wraps the live input and takes its length once, at construction. Moving the input after wrapping makes the count stale, and adding the same Document twice re-reads a consumed input. The diff's javadoc "holding the bytes" is loose on this; "whose length is the number of bytes from its current position to its end when it is created" is closer.
  • Edge cases (read, not executed): pos == limit gives an empty value; pos > limit (possible via the unchecked setPosition and skipBytes) gives a negative length, which the base writer rejects with NegativeArraySizeException and the default codec's writer, with assertions off, writes as a negative vInt with no bytes. The record does not validate an explicit negative length either. Throwing IllegalArgumentException in the constructor when getPosition() > length() would close this before addDocument, without aborting the writer.

What the checks validated

On stock main it fails in TestLucene90StoredFieldsFormat and, through the base StoredFieldsWriter.writeField, in TestSimpleTextStoredFieldsFormat (ArrayIndexOutOfBoundsException: arraycopy: last source index 38 out of bounds for byte[33] for seed DEADBEEF), with assertions on and off; with option A all stored-fields format suites above pass. Why it fails on stock for any seed: with offset o (1-5) and padding p (0-5), stock reads up to index 2o + len of an array of o + len + p, so p < o throws and p >= o stores o extra bytes, which the read-back check catches; the DEADBEEF message fits o = 5, p = 0 and a 28-byte value.

Deprecate or remove the convenience constructor

#

The API is experimental, so it may change. Not built.

Trade-offs

API churn for the whole-array case, which works today; callers must compute the length themselves.

Not recommended: a bounds check in ByteArrayDataInput.readBytes

Throw when a read passes limit.

Trade-offs

The class deliberately "omits all low-level checks" on a hot path, and an exception inside the stored-fields write would still abort it and close the writer.

Downstream note

#

No downstream caller of this constructor is known; an application that slices shared or pooled buffers this way would persist, and later return to readers of the document, whatever bytes follow each slice, such as a neighbouring record.

How it was found

#

Code reading. While modelling the chunk arithmetic of the compressing stored-fields writer, a finder read the stored-field write paths and saw that the convenience constructor copies ByteArrayDataInput.length(); a JUnit on the stock jars confirmed it. The model did not cover this class, so this is not a formal finding.

LFV-175, snapshot of 2026-10-30

Registry title
StoredFieldDataInput(ByteArrayDataInput) takes the input's end position as its length, so a ByteArrayDataInput that does not start at position 0 (a slice at a non-zero offset, or a partly read input) silently stores extra trailing bytes, or makes addDocument fail and close IndexWriter
Area
index / stored fields (StoredFieldDataInput: DataInput-backed StoredField values, #14213)
Priority
Medium, rank 218: Since 10.2.0 the experimental StoredFieldDataInput(ByteArrayDataInput) constructor persists extra trailing bytes (or closes IndexWriter) for any input not at position 0, but no Lucene or downstream caller is known.
Impact class
silent wrong results
Impact note
Applications that store a binary value through the @lucene.experimental StoredFieldDataInput(ByteArrayDataInput) convenience constructor with an input whose position is not 0 (new ByteArrayDataInput(bytes, offset, len) or reset(bytes, offset, len) with offset > 0, or an input partly read before wrapping) are hit on every such document with the default codec and settings, in every release since 10.2.0: the stored value silently carries as many extra trailing bytes from the caller's array as the start position (persisted, kept through merges, CheckIndex clean), or, when fewer bytes than that follow the slice, addDocument throws ArrayIndexOutOfBoundsException and IndexWriter closes, losing uncommitted documents; no non-test Lucene code calls this constructor, and code search found no downstream caller.
Summary
You add new StoredField(name, new StoredFieldDataInput(new ByteArrayDataInput(bytes, offset, len))) and expect the stored value to be exactly those len bytes, because the record's length is documented as 'the length of the data input'. The convenience constructor copies ByteArrayDataInput.length(), which is the end position offset + len, so for an 8-byte slice at offset 4 of a 16-byte array the document stores 12 bytes, the slice plus the next 4, with no error. If fewer bytes than the offset follow the slice, the stored fields writer reads past the array, addDocument throws ArrayIndexOutOfBoundsException and IndexWriter closes itself.
