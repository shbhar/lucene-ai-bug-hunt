MultiCollectorManager wrapping exactly one composite manager hands that manager the wrong collectors in reduce

new MultiCollectorManager(new MultiCollectorManager(top1, top2)) gives the inner manager's second child the first child's collector at the end of the search: the top-2 list comes back with 0 hits instead of 2, and a top-k plus hit-count pair throws ClassCastException. A regression since 9.0.0.

The finding in 30 seconds

#

MultiCollectorManager must give each child manager back exactly the collectors that child created. With exactly one child whose collector is itself a MultiCollector, it unwraps that collector as if it were its own wrapper and hands the child the wrong ones.

Collector managers in three steps

#
  1. A CollectorManager makes one Collector per search slice (newCollector()) and, after the search, turns those collectors into a result (reduce(collectors)). TopScoreDocCollectorManager(k, ...) returns the top-k hits.
  2. MultiCollectorManager(m1, m2, ...) combines managers: its collector feeds every child's collector, and its result is an Object[] with one entry per child.
  3. MultiCollector.wrap(c1, c2, ...) combines collectors into a MultiCollector; given a single collector, it returns that collector as is, without a wrapper.

The finding, step by step

#
  1. You combine two top-k managers, inner = new MultiCollectorManager(top-1, top-2). Searched directly on 2 matching documents, it returns 1 and 2 hits.
  2. Your code builds its manager list dynamically and this time wraps only that one manager: searcher.search(q, new MultiCollectorManager(inner)).
  3. You expect the same 1 and 2 hits: MultiCollectorManager is a composite "akin to how MultiCollector wraps Collector instances" and accepts any non-null managers.
  4. You get 0 hits for top-2, with no error. With one child, newCollector() returns inner's own MultiCollector unwrapped, and reduce mistakes it for its own wrapper: it hands inner only the top-1 collector, so top-2 reads that collector after top-1 has already emptied it.
  5. With a top-5 child next to a hit-count child, the count's reduce throws ClassCastException instead. Two outer children work, and 8.11.4 works; 9.0.0 to 10.6.0 and main fail.

Who is affected

#

Applications that wrap exactly one manager in a MultiCollectorManager when that manager is itself composite (a nested MultiCollectorManager, or a custom manager returning MultiCollector.wrap(...)), typically code that adds facet or count managers only on request. Default settings, every search. No in-tree non-sandbox caller does this; the sandbox FacetOrchestrator with no facet builders does. Rare.

Mechanism, terms and numbers716 words

MultiCollectorManager runs several collector managers in one search and returns one result per manager. Since 9.0.0 its newCollector() returns MultiCollector.wrap(collectors), and wrap returns a single collector unchanged. So when the manager has exactly one child whose collector is itself a MultiCollector (a nested MultiCollectorManager with two or more children, or a custom manager that returns MultiCollector.wrap(...)), the outer manager's collector is the child's own MultiCollector. reduce cannot tell the two apart: it unwraps every MultiCollector it receives and hands the child only the first sub-collector. The inner manager then reduces its first child correctly and every later child over the first child's collector: on 2 matching documents, new MultiCollectorManager(new MultiCollectorManager(top-1, top-2)) returns 0 hits for top-2 instead of 2, and children of different types throw ClassCastException inside a well-typed reduce. The mix-up happens on every search, with default settings, assertions on and off, in every slicing. Two outer children work, and 8.x works: LUCENE-10000 (#196) introduced it in 9.0.0, and 9.0.0 to 10.6.0 and main are affected. Reach is narrow (no in-tree non-sandbox caller builds the shape); the fix is to pass the collectors through unchanged when there is one child.

The bug (main 645d4fe14a20)

#
  1. newCollector() wraps with MultiCollector.wrap (MultiCollectorManager.java:49-56): one collector per child, returned as MultiCollector.wrap(collectors) (:55).
  2. wrap of one collector returns it unwrapped, as documented: "If the input contains 1 real collector (i.e. non-null), it is returned" (MultiCollector.java:47; the n == 1 branch at :68-77). The constructor is private (:93), so every MultiCollector has two or more sub-collectors.
  3. So with one child the outer collector is the child's own. For outer = MCM(inner), inner = MCM(A, B): outer.newCollector() is wrap([inner.newCollector()]), which is inner's MultiCollector{a, b}. Collection is right: a and b both see every hit.
  4. reduce unwraps any MultiCollector (MultiCollectorManager.java:58-76): for child i, if (collector instanceof MultiCollector mc) reducibleCollector.add(mc.getCollectors()[i]); else reducibleCollector.add(collector); (:64-72). Its comment gives the reason: "MultiCollector will not actually wrap the collector if only one is provided, so we check the instance type here" (:65-66). That is the manager's own single-collector shortcut; the type check cannot tell it apart from a child's own MultiCollector. With one child, outer takes inner's MultiCollector for its own and passes inner.reduce the list [a].
  5. inner.reduce([a]) runs the same loop: a is not a MultiCollector, so child 0 gets [a] (right) and child 1 also gets [a] (wrong); b is never reduced.
  6. Why top-2 is empty. TopScoreDocCollectorManager.reduce calls topDocs() on each collector and merges (TopScoreDocCollectorManager.java:103-110). TopScoreDocCollector keeps its hits in a heap (TopScoreDocCollector.java:36, :44), and topDocs() (TopDocsCollector.java:94-99) pops that heap (populateResults, TopScoreDocCollector.java:188-193). After the top-1 manager popped a's only entry, topDocsSize() (:177-185) is 0, so topDocs returns newTopDocs(null, 0) (TopDocsCollector.java:148-149): an empty hit list that still reports totalHits = 2 (TopScoreDocCollector.java:51-55). From 9.0.0 to 10.2.x the collector kept its hits in a HitQueue instead; the repro fails the same way on 9.10.0, 9.12.3 and 10.0.0.
  7. Why a mixed pair throws. A child typed CollectorManager<TotalHitCountCollector, Integer> receives a TopScoreDocCollector through the raw (CollectorManager[]) cast (MultiCollectorManager.java:46), and its own reduce throws ClassCastException.
  8. Why two outer children work. wrap then builds a real MultiCollector with one slot per outer child, so getCollectors()[i] is child i's collector even when that collector is itself a MultiCollector.

Other triggers (executed)

#
  • A custom manager whose newCollector() returns MultiCollector.wrap(c1, c2) and whose reduce casts back to MultiCollector, the pattern LUCENE-10244 (9.1.0) made public and that Lucene's own TestCollectorManager.CompositeCollectorManager uses (TestCollectorManager.java:127-147), wrapped alone: ClassCastException on main, 9.1.0 and 10.5.2.
  • The sandbox FacetOrchestrator with no facet builders wraps the caller's main manager alone (FacetOrchestrator.java:66-82); with MCM(top-5, hit count) as the main manager it throws ClassCastException on main.
  • MCM(MCM(top-5, TotalHitCountCollectorManager)) on 10 matching documents: TopScoreDocCollector cannot be cast to class org.apache.lucene.search.TotalHitCountCollector.

It is in MultiCollectorManager itself: an independent reproducer saw it calling newCollector()/reduce() directly, without IndexSearcher, with one and with two collectors, and the finder's harness saw it in every slicing of every index of 1-3 segments x 1-6 documents, sequentially and with a thread pool.

Exposure and likelihood208 words
  • What goes wrong. For an affected composition every search hands the inner manager's second and later children the first child's collectors. What they return then depends on the children: with top-k children, an empty top-k list with no error whenever the query has hits; a value computed from the first child's collectors, which can happen to be right (two hit-count children return the right count, and a query with no hits returns the right empty lists, executed); or a ClassCastException for that request when the children's collector types differ. Nothing is persisted.
  • Configuration. Default settings; assertions on and off; any slicing or executor. No index content or scale is needed: the repro has 2 empty documents.
  • In-tree callers. GroupingSearch can build a one-child MultiCollectorManager (GroupingSearch.java:149-165), but its child produces plain collectors; the facet module and DrillSideways always pass two managers. The sandbox FacetOrchestrator builds the shape when there are no facet builders.
  • Downstream. None of the downstream projects read for this (Solr, Elasticsearch, OpenSearch and four others; code reading only) builds the shape; Solr keeps its own copy of the pre-9.0 design.
  • Likelihood. Rare: no report was found since 9.0.0 (tagged 2021-12-06). The workaround is trivial: do not wrap a single manager, or flatten the tree.

Why it looks unintended

#
  • Documented as a composite "akin to how MultiCollector wraps Collector instances" and tested with a single child; MCM(MCM(A, B), C) works, only MCM(MCM(A, B)) breaks.
  • The code's own comment explains the type check only by the manager's own single-collector shortcut.
  • A regression: 8.11.4 passes, 9.0.0 fails; #196 aimed at early-termination parity, not at limiting composition.
The full argument310 words
  • The contract. CollectorManager: newCollector() "must return a NEW collector which will be used to collect a certain set of leaves", and reduce "will be used to reduce the results of individual collections into a meaningful result" (CollectorManager.java:28-32); reduce is typed by the manager's own collector type (T reduce(Collection<C> collectors), :55). Here a child receives another child's collector, and a well-typed child throws ClassCastException.
  • The class promises composition. "A composite CollectorManager which wraps a set of CollectorManager instances, akin to how MultiCollector wraps Collector instances" (MultiCollectorManager.java:24-27), and MultiCollector itself nests fine. The constructor accepts any non-null managers, at least one (:34-47). TestMultiCollectorManager.testCollection tests "only wrapping one of the collector managers" (TestMultiCollectorManager.java:58-63), with a plain child.
  • The comment at MultiCollectorManager.java:65-66 explains the type check by the manager's own single-collector shortcut. It does not mention a child that returns its own MultiCollector, and the check cannot tell the two apart.
  • Inconsistent by arity. MCM(MCM(A, B), C) works and MCM(MCM(A, B)) does not (executed on main, 9.0.0 and 10.5.2).
  • Regression. From 6.4.0 to 8.11.4, newCollector() returned an object of the manager's own Collectors class (a public inner class with a private constructor) and reduce indexed collectors.collectors[i] with no type test, so nesting was unambiguous. #196's CHANGES entry is about CollectionTerminatedException and setMinCompetitiveScore parity (CHANGES.txt:4923-4924, 9.0.0), and its review never discusses nesting.
  • The second trigger uses public API added later. LUCENE-10244 (9.1.0) made MultiCollector#getCollectors public, "allowing users to access the wrapped collectors" (CHANGES.txt:4344-4345; package-private in 9.0.0). Since then a manager can return MultiCollector.wrap(...) and unwrap it in its own reduce, as Lucene's TestCollectorManager.CompositeCollectorManager does. That makes the pattern public API; it does not mean every way of nesting it was considered.
  • Nothing documents a restriction. No javadoc, test, CHANGES or MIGRATE entry declares the shape unsupported.
The devil's-advocate check193 words

The strongest case for "intended" (a works-as-designed cross-model review and a devil's-advocate verifier): CollectorManager is @lucene.experimental (CollectorManager.java:42); wrap's single-collector shortcut is documented and the reduce comment shows the author knew it; nesting was never promised; and wrapping a single manager is redundant, so a maintainer could call it an unsupported, degenerate composition with a trivial workaround.

Why it fails: experimental status allows API changes, not silently wrong results; the restriction is written nowhere; one-child MultiCollectorManagers arise from dynamic construction (GroupingSearch, whose child cannot trigger the bug, and the sandbox FacetOrchestrator, whose caller-supplied main manager can); the nested-manager composition worked in 8.x (the custom-manager route needs getCollectors, public only since 9.1.0); and a two-child outer manager with the same nested child works today. The refute review, the independent reproducer, the devil's-advocate verifier and the adjudication rated the case weak; the works-as-designed review still called the bug real (medium). The cross-model fact check of this doc (OpenAI GPT-5.6) rated the case moderate: "won't fix" or "document the restriction" would be a plausible maintainer answer for a real but narrow, easily avoided regression. Verdict: not intended, a regression.

Suggested fix

#

Recommended Pass the collectors through unchanged when there is one child (recommended, validated)

In reduce, when there is exactly one child, pass the collectors through unchanged (+6 lines in MultiCollectorManager.java). That mirrors newCollector(), which returns the single child's collector unwrapped. Validated: the repro passes; 2,340 core search tests, the grouping, facet, join, sandbox-facet and demo modules and the core lint checks pass.

final Object[] results = new Object[collectorManagers.length];
if (collectorManagers.length == 1) {
  // newCollector() returned the single child's own collector (MultiCollector.wrap does not wrap
  // a single collector), even if it is itself a MultiCollector: pass it through unchanged
  results[0] = collectorManagers[0].reduce(reducibleCollectors);
  return results;
}
All options and trade-offs2 options · 470 words

One fix was validated through gradle in a scratch worktree of 645d4fe14a20; it is the finder's fix with a reworded comment. The alternative was suggested by the reviewers and not built. Whichever is chosen, the invariant is: a child's reduce must receive exactly the collectors its own newCollector() returned.

Pass the collectors through unchanged when there is one child (recommended, validated)

#

With one child, newCollector() returns that child's collector as is, so reduce hands the same objects back instead of guessing from their runtime type. The multi-child loop is unchanged.

final Object[] results = new Object[collectorManagers.length];
if (collectorManagers.length == 1) {
  // newCollector() returned the single child's own collector (MultiCollector.wrap does not wrap
  // a single collector), even if it is itself a MultiCollector: pass it through unchanged
  results[0] = collectorManagers[0].reduce(reducibleCollectors);
  return results;
}

Trade-offs

  • Smallest change, no hot-path cost: reduce runs once per search, after collection.
  • The loop's comment ("MultiCollector will not actually wrap the collector if only one is provided ...", :65-66) then describes a case the loop no longer sees for one child; a committer may want to reword it.
  • Not covered and not claimed: a child manager whose newCollector() returns null would shift indices in the multi-child path because wrap drops nulls, but CollectorManager does not allow null collectors.

Make newCollector() always return a composite that reduce can recognise as its own (not built)

#

Return the manager's own wrapper even for one child (as before 9.0, or through a package-private MultiCollector factory that always wraps), so reduce never has to guess from the runtime type.

Trade-offs

For one child it adds a delegation layer on every collected hit that wrap currently avoids. The factory variant touches MultiCollector (its constructor is private, MultiCollector.java:93). A manager-owned wrapper, as before 9.0, stays in MultiCollectorManager.java, but it must re-implement the CollectionTerminatedException, setMinCompetitiveScore and score-caching handling that #196 got by delegating to MultiCollector, not just bring back the old type. Suggested by the reviewers as what a committer might prefer; not built or run.

Downstream note

#

Downstream code that derives its manager list from the request around a composite main manager would get empty hit lists or a ClassCastException whenever only that manager is left; none of the downstream projects read builds this shape.

How it was found

#

While writing a bounded-exhaustive harness that runs Lucene's real collector managers on every small index and slicing, the finder read reduce's instanceof MultiCollector check, suspected it cannot tell its own wrapper from a child's, and added nested-manager specs. The harness then saw the wrong result in every slicing; the finder reduced it to a public-API JUnit.

The method in full171 words

Method: semi-formal (bounded-exhaustive translation validation, then public-API JUnit tests).

  • A hunt unit on concurrent collector managers wrote a harness that runs the real collector managers on every index of 1-3 segments x 1-6 documents (258 shapes) under every distinct IndexSearcher slicing (3,750), sequentially and with a 3-thread pool, and compares each result with the inner manager searched directly.
  • Reading MultiCollectorManager.reduce's instanceof MultiCollector check while writing it, the finder suspected the check cannot tell the manager's own wrapper from a child's MultiCollector, and added nested specs. So the hypothesis came from code reading; the harness confirmed it: MultiCollectorManager(MultiCollectorManager(top-1, top-3)) gave a wrong result in every slicing (30,000 times with assertions on and with them off; 0 with the fix), while the two-child nested spec passed.
  • The finder reduced it to a one-segment public-API JUnit. A cross-model review (OpenAI GPT-5.6), an independent reproducer, a works-as-designed review, a devil's-advocate verifier and an adjudication checked it; the follow-up added the history, prior-art and security checks, and the repro was minimized to one test.

History

#

Introduced by #196 (LUCENE-10000, ad7746d6e31, merged 2021-07-23), which switched newCollector() to MultiCollector.wrap and added the unwrap in reduce. First released in 9.0.0; 9.0.0 to 10.6.0 and main fail, 8.x passes, and swapping only this file (on 8.11.4 together with the getter #196 added to MultiCollector) flips the result both ways. Not fixed upstream.

Versions tested7 rows

Introduced by apache/lucene#196, "LUCENE-10000: Make MultiCollectorManager consistent with MultiCollector" (Greg Miller, gsmiller; approved by jpountz), merged 2021-07-23 as ad7746d6e31 (issue #11039). It replaced the manager's own Collectors wrapper (a public inner class with a private constructor) with MultiCollector.wrap in newCollector() and added the instanceof MultiCollector unwrap to reduce. The single-collector shortcut of wrap is older (2010); it became a problem only when #196 relied on it. The file's two later commits, #14100 (2025) and #15874 (2026), are cosmetic.

First affected release: 9.0.0 (tag 2021-12-06). The 8.x line never received #196: 8.10.0 to 8.11.4, released after the merge from branch_8x, keep the old design. 6.4.0 to 7.7.3 have the old design too (read, not run); 6.3.0 and earlier have no MultiCollectorManager.

Commit-level check: swapping only MultiCollectorManager.java to its pre-#196 version turns the failure into a pass on 9.0.0, 9.12.3, 10.5.2 and main; swapping the #196 version into 8.11.4 (together with 8.11.4's MultiCollector.java plus the package-private getter #196 added, so that it compiles) turns the pass into the same failure. Upstream main 2f424fd428da (2026-10-30) has the same file.

LFV-198, snapshot of 2026-11-02

Registry title
MultiCollectorManager wrapping exactly one manager whose collectors are MultiCollectors (for example a nested MultiCollectorManager) hands that manager the wrong collectors in reduce, so its second and later sub-managers return silently wrong results or throw ClassCastException
Area
search / MultiCollectorManager (composition of CollectorManagers)
Priority
Low, rank 745: A MultiCollectorManager around exactly one composite manager reduces its later children over the first child's collectors (empty top-k or ClassCastException), deterministic but a rare composition with no in-tree non-sandbox caller.
Impact class
silent wrong results
Impact note
Hits applications that wrap exactly one CollectorManager in a MultiCollectorManager when that one manager itself produces MultiCollector instances (a nested MultiCollectorManager with two or more children, a custom manager that returns MultiCollector.wrap(...) as LUCENE-10244 made possible, or the sandbox FacetOrchestrator with no facet builders around a composite main manager); for them it fires on every search, with default settings, with -ea and -da and in every slicing: the inner manager's first sub-manager is reduced correctly and every later sub-manager is reduced over the first one's collectors, so a top-k list comes back empty (0 of 5 hits in the finder's test) or a well-typed reduce throws ClassCastException; nothing is persisted, no scale is needed, no in-tree non-sandbox caller builds this shape, and the workaround is not to wrap a single manager.
Summary
You wrap one collector manager in a MultiCollectorManager, for example new MultiCollectorManager(new MultiCollectorManager(top1, top5)) from code that builds the manager list dynamically, and expect the same results as searching with the inner manager directly. Instead, because MultiCollector.wrap returns a single collector unwrapped, the outer manager's reduce takes the inner manager's own MultiCollector for its wrapper and unwraps it, so the inner manager's second child is reduced over the first child's collectors. In the finder's test the top-5 list comes back with 0 hits instead of 5, and with a top-k child next to a hit-count child the count manager's reduce throws ClassCastException (TopScoreDocCollector cannot be cast to TotalHitCountCollector).
