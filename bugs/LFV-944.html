FrequentTermsSpanBooleanQueryRewrite sizes its queue from maxSize before collecting any term, so Integer.MAX_VALUE fails every search and large caps cost heap on every rewrite

FrequentTermsSpanBooleanQueryRewrite, new in the unreleased 10.6.0, reserves room for maxSize terms before it collects any. So Integer.MAX_VALUE as "no limit" makes every search throw IllegalArgumentException even when 3 terms match, and a cap of 2^26 costs about 268 MB of heap per query.

The bug in 30 seconds

#

SpanMultiTermQueryWrapper lets a prefix, wildcard or fuzzy query sit inside span queries by rewriting it into a SpanOrQuery of the matching terms. The new rewrite keeps only the maxSize most frequent of them, but it sizes its queue by maxSize instead of by the terms it finds.

Background: how a span multi-term rewrite keeps its terms

#
  1. SpanMultiTermQueryWrapper wraps a multi-term query such as PrefixQuery(f:aa). At search time a rewrite method expands it into a SpanOrQuery with one SpanTermQuery per kept term.
  2. FrequentTermsSpanBooleanQueryRewrite(maxSize), new in 10.6.0, keeps the maxSize terms with the highest document frequency. It first collects every matching term, then keeps the best maxSize in a priority queue.
  3. Lucene's internal PriorityQueue allocates its whole array, maxSize + 1 slots (2 for a size of 0), when it is created, and rejects sizes of 2,147,483,631 and above (Lucene's ArrayUtil.MAX_ARRAY_LENGTH, Integer.MAX_VALUE minus an array-header allowance).

The bug, step by step

#
  1. Index 3 documents with the terms aa1, aa2 and aa3. Wrap PrefixQuery(f:aa) in SpanMultiTermQueryWrapper and pick the new FrequentTermsSpanBooleanQueryRewrite(Integer.MAX_VALUE), meaning "keep every matching term". The constructor accepts it.
  2. You expect a count of 3: the rewrite "keeps at most maxSize terms", and its sibling TopTermsSpanBooleanQueryRewrite(Integer.MAX_VALUE) returns 3 on the same index.
  3. Instead every search throws IllegalArgumentException: maxSize must be >= 0 and < 2147483631; got: 2147483647, even when no term matches. The rewrite creates its priority queue with room for maxSize terms before it has collected a single term, and Lucene's queue refuses an array that large.
  4. A large cap that is legal pays on every query instead: maxSize 67,108,864 (2^26) allocates about 268 MB to keep 3 terms and runs out of memory with a 256 MB heap. The small caps tried (8 and 1,024) are fine.

Who is affected

#

Only applications that opt in to the new rewrite, not yet in any release (main and the 10.6.0 release candidate), with a huge maxSize: Integer.MAX_VALUE fails every query at once; a cap in the millions costs about 4 MB of heap per million on every rewrite. The small caps tried (8 and 1,024) work, and results are never wrong.

Mechanism, terms and numbers503 words

SpanMultiTermQueryWrapper.FrequentTermsSpanBooleanQueryRewrite, added for 10.6.0 by #16484, turns a span-wrapped multi-term query into a SpanOrQuery of the maxSize matching terms with the highest document frequency. It is built on ScoringRewrite, which collects every matching term first, but its builder is a PriorityQueue of capacity maxSize, and ScoringRewrite.rewrite creates the builder before it collects any term (ScoringRewrite.java:107 vs :109 on main 645d4fe14a20; the queue at SpanMultiTermQueryWrapper.java:313). Lucene's internal PriorityQueue allocates maxSize + 1 slots up front and rejects maxSize >= 2,147,483,631 (PriorityQueue.java:121-134). So Integer.MAX_VALUE, which the constructor accepts and the sibling TopTermsSpanBooleanQueryRewrite handles, makes every search throw IllegalArgumentException, with 3 matching terms or none, and a large legal cap such as 2^26 allocates about 268 MB on every rewrite. Main and the 10.6.0 release candidate are affected; no release has the class. Sizing the queue by the terms actually collected fixes both and, in every case tested, leaves the kept terms unchanged.

The code (main 645d4fe14a20)

#
  1. The constructors store maxSize unchecked (SpanMultiTermQueryWrapper.java:301-308) and delegate to an anonymous ScoringRewrite<PriorityQueue<ScoreTerm>> whose builder is
   @Override
   protected PriorityQueue<ScoreTerm> getTopLevelBuilder() {
     return PriorityQueue.usingComparator(maxSize, order);
   }

(:311-314). addClause calls insertWithOverflow for each term (:331-339), build pops the queue into a SpanOrQuery (:316-324), and checkMaxClauseCount is a no-op because "the priority queue already bounds the number of retained terms" (:326-329).

  1. ScoringRewrite.rewrite calls getTopLevelBuilder() (ScoringRewrite.java:107) before collectTerms (:109). The number of matching terms is known only afterwards, col.terms.size() (:111).
  2. PriorityQueue.usingComparator builds new PriorityQueue<>(maxSize, lessThan) (PriorityQueue.java:61-64). The constructor throws IllegalArgumentException for maxSize < 0 or maxSize >= ArrayUtil.MAX_ARRAY_LENGTH (:121-125; Integer.MAX_VALUE - NUM_BYTES_ARRAY_HEADER, 2,147,483,631 on the test JVM), else allocates new Object[maxSize + 1] (:129, :134). The class is @lucene.internal and documents the pre-allocation only there (:34-39).

So the queue is sized by the cap, not by the terms found: at maxSize >= 2,147,483,631 every rewrite throws, and below that every rewrite with a positive maxSize allocates maxSize + 1 references (2 for maxSize 0) (4 bytes each with compressed references), for any number of matching terms.

The sibling

#

TopTermsRewrite.rewrite takes Math.min(size, getMaxSize()) and collects into a growing java.util.PriorityQueue (TopTermsRewrite.java:64-65). TopTermsSpanBooleanQueryRewrite uses it with getMaxSize() = Integer.MAX_VALUE (SpanMultiTermQueryWrapper.java:205-216), so it accepts Integer.MAX_VALUE and allocates the same small amount at every size tried.

Exposure and likelihood226 words
  • Opt-in. The wrapper's default rewrite is SCORING_SPAN_QUERY_REWRITE, or TopTermsSpanBooleanQueryRewrite for a top-terms query such as FuzzyQuery (SpanMultiTermQueryWrapper.java:65-77); an application must call setRewriteMethod(new FrequentTermsSpanBooleanQueryRewrite(n)). No Lucene code outside the class and its test builds it. Within that usage the default writer, codec and searcher suffice, and 3 documents are enough.
  • Loud, not silent. A huge cap fails on the first query with a clean IllegalArgumentException (the constructor accepted it). A cap in the millions costs maxSize + 1 slots of heap on every rewrite, up to OutOfMemoryError on a small heap. No wrong results, no index effect.
  • The clause limit. Under the default IndexSearcher clause limit (1024), keeping more than 1,025 terms already fails with TooManyNestedClauses (related bug LFV-733): the clause check tests numClauses > maxClauseCount before it counts the clause, so it lets 1,025 clauses through and throws on the 1,026th (IndexSearcher.java:907-921; the off-by-one is tracked upstream as #10339). So caps far above 1024 matter once the limit is raised. The Integer.MAX_VALUE failure does not depend on the clause limit.
  • Releases. None yet: the class first ships in 10.6.0, whose release candidate is affected. Fixing it before 10.6.0, or in 10.6.1, means it never ships broken.
  • Likelihood: rare. The class exists to bound expansion, so most callers pass small caps; a GitHub code search on 2026-10-28 found no downstream user.

Why it is a bug, not intended

#
  • The constructors promise only "keeps at most maxSize terms" (SpanMultiTermQueryWrapper.java:300); no bound is documented, and any int is accepted.
  • The class's own comment says it collects every term first; its sibling TopTermsSpanBooleanQueryRewrite(Integer.MAX_VALUE) works on the same index.
  • LUCENE-504 fixed this pattern in 2009, moving FuzzyQuery to a growing queue to support Integer.MAX_VALUE "without exhausting all memory".
The full argument169 words
  • Contract. "Create a rewrite that keeps at most maxSize terms" (SpanMultiTermQueryWrapper.java:300, :305). The class javadoc defines the class by its ranking difference to TopTermsSpanBooleanQueryRewrite (:261-263). The bound and the pre-allocation are documented only on the @lucene.internal PriorityQueue (PriorityQueue.java:34-39, :121-125).
  • The class's design. "ScoringRewrite first collects every matching term ... and this rewrite then retains the maxSize most frequent" (:268-274): the size of the set is known before the queue is needed.
  • The sibling. TopTermsSpanBooleanQueryRewrite(Integer.MAX_VALUE) keeps the 3 terms with the default and with a raised clause limit.
  • Precedent. LUCENE-504 (#1581), fixed by Uwe Schindler in 15743fc1793 (2009-11-06), changed FuzzyQuery to use java.util.PriorityQueue, "which grows dynamically to support BooleanQuery.maxClauseCount(Integer.MAX_VALUE) without exhausting all memory" (the commit subject itself spells the class java.utilPriorityQueue). TopTermsRewrite keeps that design today. IndexSearcher.searchAfter likewise caps numHits at Math.max(1, reader.maxDoc()) before sizing its collector (IndexSearcher.java:587-599).
  • Why tests missed it. The class's only upstream test uses size 8; #16484's review did not discuss sizes.
The devil's-advocate check186 words

Strongest case: pre-allocating a queue sized by the caller's N is a deliberate Lucene pattern (TopScoreDocCollectorManager and TopFieldCollectorManager document "pre-allocate a full array of length numHits"), and the PriorityQueue exception is a deliberate guard against a confusing OutOfMemoryError (4c646dab3fb, 2018). The class exists to bound expansion, so "no limit" goes against its purpose; SCORING_SPAN_QUERY_REWRITE already keeps every term; and under the default clause limit (1024) more than 1,025 terms fail anyway (the clause check throws on the 1,026th clause).

Why it fails: those collectors document the pre-allocation on their public API; this class does not, and fails late, at search time, from an internal class, after its public constructor accepted the value. The sibling it is defined against accepts Integer.MAX_VALUE; with a raised clause limit, keeping every matching term is a legal result; and LUCENE-504 already settled the question for multi-term rewrites. Even if huge caps were unsupported, the constructor should reject them. The intended-behaviour check: real, high confidence for the exception, medium for the allocation on its own, so the allocation is filed as a consequence, not as a second bug.

Suggested fix

#

Recommended A. Allocate the queue only when its size is known

Allocate the queue lazily (SpanMultiTermQueryWrapper.java, +57/-8): collect terms into a small list until more than maxSize arrive, then switch to a queue of maxSize; otherwise size the queue by the terms collected. Kept terms and their order are unchanged in every case tested. The test and all 513 lucene/queries tests pass.

void add(ScoreTerm st) {            // once per matching term
  if (queue == null) {
    if (pending.size() < maxSize) {
      pending.add(st);
      return;
    }
    queue = newQueue(maxSize);       // more than maxSize terms: allocate now
  }
  queue.insertWithOverflow(st);
}
// build(): finish() makes newQueue(pending.size()) if the queue was never needed
All options and trade-offs4 options · 690 words

Three fixes were built and run in a scratch worktree of 645d4fe14a20; capping or rejecting the size alone is not recommended.

A. Allocate the queue only when its size is known (validated by the checks) (recommended)

#

A private builder TopFrequentTerms replaces the queue as the ScoringRewrite builder. It keeps terms in a pending list while fewer than maxSize have arrived; on the first term beyond maxSize it allocates a queue of maxSize slots, moves the pending terms in and continues with insertWithOverflow; if that never happens, build() allocates a queue of exactly the collected count. Terms are offered in the same order as before. The constructor also rejects a negative maxSize (optional hardening; today a negative size fails at search time with the same exception).

void add(ScoreTerm st) {            // once per matching term
  if (queue == null) {
    if (pending.size() < maxSize) {
      pending.add(st);
      return;
    }
    queue = newQueue(maxSize);       // more than maxSize terms: allocate now
  }
  queue.insertWithOverflow(st);
}
// build(): finish() makes newQueue(pending.size()) if the queue was never needed

Trade-offs

About 50 lines and a new private class. When more than maxSize terms match, the peak at the switch is the pending list (maxSize terms, plus the ArrayList's spare capacity) plus the new queue (maxSize + 1 slots); the list is dropped right after the move. The branch_10_6 line reads new PriorityQueue<>(maxSize) { lessThan }, so a backport needs the 10.x queue API.

What the checks validated

  • Stock + test: fails with assertions on and off; + fix: passes with assertions on and off (gradle).
  • + fix: the whole lucene/queries module, 513 tests with the new test, 0 failures, assertions on and off; :lucene:queries:check -x test (format, ecjLint, forbiddenApis) passes.
  • + fix: the finder's 3 tests pass, including the 2^26 allocation test, also with -Xmx256m (stock: OutOfMemoryError).
  • The finder's exhaustive harness (0-4 matching terms): 60,960 cases, 0 mismatches with the fix and results identical to stock for every size stock accepts; a Z3 model: the fix cannot throw for maxSize >= 0 and its queue array never has more than max(n + 1, 2) slots (the model does not cover the pending list).
  • Not run: the full Lucene test suite, nightly tests, branch_10_6.

B. Collect into a list and size the queue in build() (validated by the checks)

#

The builder becomes a List<ScoreTerm>; build() creates PriorityQueue.usingComparator(Math.min(maxSize, builder.size()), order), offers every collected term with insertWithOverflow in the same order, then pops as before (+14/-12).

Trade-offs

Smallest and easiest to review, but it keeps a ScoreTerm and its Term for every matching term until build(), where today the queue drops the overflow at once. ScoringRewrite already holds every matching term's bytes and TermStates for the whole rewrite, so memory stays linear in the matching terms, with a larger constant when far more terms match than maxSize.

What the checks validated

The test passes; the whole lucene/queries module passes (513 tests); check -x test passes after a formatting fix; the finder's 3 tests and the -Xmx256m test pass.

C. A plus the clause-limit cap, to file together with LFV-733 (validated by the checks)

#

Option A with builder capacity Math.min(maxSize, IndexSearcher.getMaxClauseCount()), as the core top-terms rewrites cap their size (+59/-8). Related bug LFV-733 changes the same line for the clause limit.

Trade-offs

It also changes LFV-733's case: an explicit maxSize above the clause limit then keeps at most the limit instead of failing with TooManyNestedClauses; argue that in LFV-733's issue.

What the checks validated

The whole lucene/queries module passes (513 tests); check -x test passes; the finder's 3 tests pass, including the raised-clause-limit case.

Not recommended alone: cap at the clause limit, or reject huge sizes in the constructor

#

Capping the eager queue at IndexSearcher.getMaxClauseCount() hides the bug only at the default limit: with setMaxClauseCount(Integer.MAX_VALUE) the exception is back, and the allocation becomes min(maxSize, limit) + 1 slots (executed by the finder and the independent reproduction). Rejecting large sizes in the constructor and documenting the pre-allocation fails fast, but keeps the per-rewrite allocation for every cap below the edge and diverges from the sibling, which accepts Integer.MAX_VALUE.

Downstream note

#

A GitHub code search on 2026-10-28 found no downstream user of the new rewrite; an application that takes maxSize from a request should cap it, as with any expansion limit.

How it was found

#

A planning probe compared the sizes the two span top-N rewrites accept and saw only the new one throw at Integer.MAX_VALUE. The finder reduced it to a public-API test, found the cause by reading ScoringRewrite, and checked the rewrite exhaustively on small indexes against a reference written from its javadoc.

The method in full172 words

Method: differential testing, then bounded-exhaustive translation validation and a Z3 model (semi-formal).

  • A planning probe on main a9779ef3c193 (2026-10-28) ran FrequentTermsSpanBooleanQueryRewrite and TopTermsSpanBooleanQueryRewrite at the same sizes: only the new rewrite threw, at 2,147,483,631 and Integer.MAX_VALUE, and it took 154 ms at 2^26 against 1 ms.
  • The finder reduced it to a public-API JUnit (6 documents, 3 terms) and found the cause by reading ScoringRewrite.rewrite while modelling it.
  • A harness compared the rewrite with a reference written from its javadoc on every small case: 60,960 cases, 0-4 matching terms, 1 or 2 segments, sizes -1, 0..n+1, 4096, 2,147,483,631 and Integer.MAX_VALUE, both built-in orders. The only mismatches were the 12,440 exception cases at the two edge sizes; a deliberately wrong reference is caught.
  • A Z3 bit-vector model of the queue sizing confirmed that the stock code can throw or allocate over 10^6 slots for at most 3 terms, and that the lazy fix cannot (6 of 6 queries as expected).
  • This doc's one-method test is a reduction of the finder's test.

LFV-944, snapshot of 2026-10-29

Registry title
SpanMultiTermQueryWrapper.FrequentTermsSpanBooleanQueryRewrite (new in 10.6.0) sizes its priority queue from maxSize before collecting any term, so maxSize >= 2147483631 (for example Integer.MAX_VALUE as 'no limit') makes every rewrite throw IllegalArgumentException, and a large maxSize allocates a (maxSize + 1)-slot array on every rewrite
Area
queries / spans (SpanMultiTermQueryWrapper.FrequentTermsSpanBooleanQueryRewrite queue sizing; core ScoringRewrite creates the top-level builder before collecting terms; util PriorityQueue pre-allocates maxSize + 1 slots)
Priority
Low, rank 874: This is a loud crash at the Integer.MAX_VALUE boundary in the unreleased FrequentTermsSpanBooleanQueryRewrite, a sibling of LFV-733's span top-N size problem.
Impact class
crash
Impact note
Applications that install the new (10.6.0) FrequentTermsSpanBooleanQueryRewrite on a SpanMultiTermQueryWrapper with a very large maxSize are hit: Integer.MAX_VALUE (a natural 'no limit' value that the sibling TopTermsSpanBooleanQueryRewrite accepts) or any value >= 2147483631 makes every search or rewrite of that query throw IllegalArgumentException from the internal PriorityQueue, even on a field with 3 matching terms and with IndexSearcher.setMaxClauseCount raised, and a large legal cap such as 2^24 or 2^26 makes each rewrite allocate a (maxSize + 1)-slot array (about 67 MB or 268 MB on the test JVM, OutOfMemoryError under -Xmx256m) whatever the number of matching terms; default writer, codec and searcher, 6 documents suffice, small caps (8-1024) are unaffected, and no release has it (main and the 10.6.0 release-candidate head only).
Summary
You wrap a PrefixQuery in SpanMultiTermQueryWrapper, call setRewriteMethod(new FrequentTermsSpanBooleanQueryRewrite(Integer.MAX_VALUE)), whose javadoc promises only that it 'keeps at most maxSize terms' (ranked by document frequency instead of boost, unlike TopTermsSpanBooleanQueryRewrite), and expect it to keep all 3 matching terms, as TopTermsSpanBooleanQueryRewrite(Integer.MAX_VALUE) does on the same index. Instead the constructor accepts the value and every search then throws IllegalArgumentException 'maxSize must be >= 0 and < 2147483631; got: 2147483647', because getTopLevelBuilder() returns PriorityQueue.usingComparator(maxSize, order) and ScoringRewrite.rewrite calls it before it collects any term, so the internal queue pre-allocates maxSize + 1 slots (or rejects a size it cannot allocate) instead of being sized by the terms actually found; for the same reason a large legal cap such as 2^26 allocates about 268 MB per rewrite for 3 terms. Sizing the queue lazily, by min(maxSize, collected terms), as the sibling TopTermsRewrite does with a growing queue, fixes both and leaves every result unchanged.
