IndexWriter.hasDeletions() returns false for a buffered delete while another thread's commit, flush() or NRT open writes a segment

IndexWriter.hasDeletions() returns false for a buffered delete while another thread's commit(), flush() or NRT open writes a segment, then true again. The flush holds the delete in a flush ticket the method never reads; nothing in the index is wrong, and every release since 4.0.0 has it.

The finding in 30 seconds

#

hasDeletions() looks in four places: published delete packets, the current delete queue, the reader pool and the committed segments. A flush first moves the buffered deletes into a flush ticket and hands the ticket to the writer only after the segment is written. During that write the delete is in none of the four places.

How a delete travels through a commit, in one minute

#
  1. deleteDocuments buffers the delete in the writer's current delete queue; it is applied later, at a flush.
  2. A commit, flush() or NRT open runs a full flush. It swaps in a fresh, empty delete queue, packs the old queue's deletes into a flush ticket, writes the in-RAM documents as a new segment, and then publishes the ticket: its deletes go to the writer's published-deletes stream and the segment joins the index.
  3. The segment write does not hold the writer's lock (publishing the ticket does), so other threads can call IndexWriter methods while the segment is written.

The finding, step by step

#
  1. Add two documents, id:a and id:b, and call deleteDocuments(new Term("id", "a")). Nothing is committed yet, and hasDeletions() returns true, as its javadoc promises for buffered deletions.
  2. Another thread calls commit(). Its flush first packs the buffered delete into a flush ticket, then writes the new segment, and only then hands the ticket to the writer.
  3. You expect hasDeletions() to stay true during the commit: the delete is pending the whole time.
  4. Instead, while the segment is written, hasDeletions() returns false. It reads the published deletes, the current (new, empty) delete queue, the reader pool and the committed segments, and the ticket is in none of them.
  5. After the commit it is true again: the new segment has 1 deleted document of 2. Only the answer during the segment write was wrong.

Who is affected

#

Applications that call IndexWriter.hasDeletions() while another thread commits, flushes or refreshes an NRT reader, on an index with no other deletion (any deleted document elsewhere makes it true). Default configuration. One wrong false for the length of a segment write; nothing in the index is wrong. No production code in Lucene calls this method (only tests do). Priority Low.

Mechanism, terms and numbers484 words

IndexWriter.hasDeletions() is documented to return true for buffered deletions (IndexWriter.java:1444-1448). It reads bufferedUpdatesStream.any(), docWriter.anyDeletions(), readerPool.anyDeletions() and each SegmentCommitInfo.hasDeletions() (:1449-1460), and DocumentsWriter.anyDeletions() reads only the current delete queue (DocumentsWriter.java:376-378). A commit, flush() or NRT open runs a full flush outside the writer's monitor: it swaps in a fresh delete queue (:680), freezes the buffered deletes into a flush ticket (:534-536) and then writes the segment "concurrently without locking" (:540-541); the ticket's deletes reach BufferedUpdatesStream only when it is published (IndexWriter.java:2953). For the whole segment write the delete is in none of the places the method reads, so it returns false, then true again after the commit. It shows only while the index holds no other deletion, nothing persisted or searched is wrong, and no production code in Lucene calls it (only tests do): priority Low. The sibling anyChanges() has guarded this window since LUCENE-3551 (2011); letting anyDeletions() also read the unpublished tickets closes the reproduced window (a second, shorter gap after the queue swap needs option B). Every release from 4.0.0 through 10.6.0 and main is affected.

The read set

#

hasDeletions() (IndexWriter.java:1449-1460, synchronized) returns true if bufferedUpdatesStream.any() || docWriter.anyDeletions() || readerPool.anyDeletions() (:1451) or any SegmentCommitInfo.hasDeletions() (:1454-1458). DocumentsWriter.anyDeletions() is return deleteQueue.anyChanges(); (DocumentsWriter.java:376-378): the current delete queue only.

What a full flush does

#
  1. commit() runs docWriter.flushAllThreads() under fullFlushLock, not the writer's monitor (IndexWriter.java:3806-3809). flushAllThreads swaps in a fresh delete queue (DocumentsWriter.java:680).
  2. doFlush adds a ticket: ticketQueue.addTicket(() -> new FlushTicket(dwpt.prepareFlush(), true)) (:534-536). prepareFlush freezes the old queue's buffered deletes (DocumentsWriterPerThread.java:429).
  3. The segment is written "concurrently without locking" (DocumentsWriter.java:540-541).
  4. The ticket is published under the writer's monitor (publishFlushedSegment, IndexWriter.java:2953): the frozen packet goes into BufferedUpdatesStream (:2969-2971) and the segment into segmentInfos.

During step 3 the new queue is empty, the ticket is unpublished, no reader is pooled and (in the repro) no segment exists yet, so hasDeletions() returns false. Any segment with deletions, pending reader-pool deletes or a published delete packet would make it true anyway, so the wrong answer shows only on an index with no other deletion.

A second, shorter gap (not in the repro)

#

Between the queue swap (step 1) and the freeze (step 2) the delete sits in the swapped-out queue, which anyDeletions() does not read either. It was seen only with a polling diagnostic and probes. It is the same state as the separate finding LFV-1264 (anyChanges()), and fix option B closes both (by reading). Both gaps give the same symptom in the same getter.

Why 3.x was not affected

#

There every flush ran inside private synchronized doFlush, the monitor hasDeletions() also takes, so the call waited for the flush to end (executed: 3.1.0 and 3.6.2 pass).

Exposure and likelihood219 words
  • Who is hit. Applications that call IndexWriter.hasDeletions() on one thread while another thread runs commit(), flush() or an NRT reader open, after a delete by term or query buffered before that flush started, and while the index has no other deletion (for example an append-mostly index).
  • Default vs opt-in. Default IndexWriterConfig and public API only, assertions on or off. The repro adds NoMergePolicy only so its after-commit check is unambiguous: a merge could reclaim the half-deleted segment and make false correct after the commit.
  • Effect. One wrong false for as long as the segment write lasts; it heals when the ticket is published. No data loss, no wrong search result, no change to what is committed.
  • Scale. None needed: 2 documents, 1 delete.
  • Callers. No production code in Lucene calls IndexWriter.hasDeletions(), only tests do (TestTryDelete, TestTieredMergePolicy, TestFunctionRangeQuery; every hasDeletions() call in lucene/*/src/java is on a reader or a SegmentCommitInfo). A code search found downstream code that logs an error when hasDeletions() is false right after deleteDocuments(query) (OrientDB's Lucene engine) and code that runs forceMergeDeletes() only when it is true (JabRef); neither was executed.
  • Likelihood: rare. It needs a caller of this getter, a concurrent flush and an index with no other deletion, and the documented searches found no public report of it.

Why it looks unintended

#
  • The javadoc counts buffered deletions with no concurrency caveat, and IndexWriter is documented as safe to call from many threads.
  • The sibling anyChanges() checks the ticket queue on purpose, with a comment naming this window (LUCENE-3551); anyDeletions() never got that check.
  • No sequential order gives false: the delete is counted before the flush moves it and after publication.
The full argument218 words
  • Contract. "Returns true if this index has deletions (including buffered deletions). Note that this will return true if there are buffered Term/Query deletions, even if it turns out those buffered deletions don't match any documents." (IndexWriter.java:1444-1448). IndexWriter instances "are completely thread safe, meaning multiple threads can call any of its methods, concurrently" (:167-168).
  • The code names this window. anyChanges(): "if we currently flush deletes and / or dwpt there could be a window where all changes are in the ticket queue before they are published to the IW. ie we need to check if the ticket queue has any tickets" (DocumentsWriter.java:345-351, check at :355). addTicket counts the ticket first because "freeze opens a window for #anyChanges to fail" (DocumentsWriterFlushQueue.java:39). LUCENE-3551 (#4625, 73dec384b40, 2011) added the check for nrtIsCurrent/anyChanges only; no commit since has changed what anyDeletions() reads (LUCENE-9304, 2602269f3ec, 2020, only dropped its public modifier).
  • No sequential state makes false right. The method counts the delete in the current queue before the freeze and the same frozen packet in bufferedUpdatesStream after publication (IndexWriter.java:1451); the unpublished ticket is the one stage it skips.
  • Nothing accepts it. Every IndexWriter.hasDeletions() assertion in the test trees is sequential; #4625 and LUCENE-3023 (#4097) never mention hasDeletions.
The devil's-advocate check188 words

The argument (a fair one): status getters are best-effort snapshots and need not be exact while another thread runs a multi-stage flush; a delete frozen into a ticket is "no longer buffered, it is being applied". The class doc lets many threads call any method concurrently, but no javadoc promises a linearizable snapshot, so this is the central interpretation question. A fact check by another model family (OpenAI GPT-5.6) rated the argument moderate.

Why we still read it as a bug: the javadoc has no such caveat; the only hedged sibling, hasUncommittedChanges(), hedges toward false positives only (IndexWriter.java:4217-4223); the method counts the same frozen packet once it is published, so it does treat it as buffered; the answer flips back to true with no user action in between; and Lucene fixed the same window for anyChanges() as a bug (LUCENE-3551). An independent reproducer, an executed review by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier all rejected the argument, and the fact check still found Low priority right. Read fairly, it is a low-impact gap in the getter's contract with a concrete false negative.

Suggested fix

#

Recommended A: anyDeletions() also reads the deletes held by unpublished flush tickets (the smaller patch, for the reproduced window)

Let DocumentsWriter.anyDeletions() also return true when a queued flush ticket that is not yet published carries deletes or updates (a short synchronized scan in DocumentsWriterFlushQueue). It closes the reproduced window; option B also closes the shorter queue-swap gap. Validated: the repro passes with assertions on and off; the whole org.apache.lucene.index test package (1398 tests) and :lucene:core:check -x test pass.

// DocumentsWriter
boolean anyDeletions() {
  return deleteQueue.anyChanges() || ticketQueue.anyDeletions();
}

// DocumentsWriterFlushQueue (the diff uses braces)
synchronized boolean anyDeletions() {
  for (FlushTicket ticket : queue) {
    if (ticket.frozenUpdates != null && ticket.frozenUpdates.any()) return true;
    FlushedSegment s = ticket.segment;
    if (s != null && (s.delCount > 0 || s.segmentUpdates != null)) return true;
  }
  return false;
}
All options and trade-offs2 options · 605 words

Option A closes the gap the repro shows (the whole segment write). Option B also closes the shorter gap between the queue swap and the freeze, and with it, by reading (not run), the separate finding LFV-1264, because anyChanges() calls anyDeletions(). The diff for A adds 17 lines and removes 1, in two files.

A: anyDeletions() also reads the deletes held by unpublished flush tickets (the smaller patch, for the reproduced window) (validated by the checks) (recommended)

#

DocumentsWriter.anyDeletions() becomes deleteQueue.anyChanges() || ticketQueue.anyDeletions(), and DocumentsWriterFlushQueue gets a synchronized method that returns true if a queued ticket has non-empty frozen updates, or a flushed segment with deleted documents or segment updates. By reading: the freeze and the enqueue run together under the ticket queue's monitor (DocumentsWriterFlushQueue.java:38-52); on the flush paths a ticket leaves the queue only after its publication step (:99-107; after a failed segment write its frozen deletes are still published, IndexWriter.java:6272-6274), and publication runs under the writer's monitor, which hasDeletions() holds. So for a queued ticket on a flush path one of the reads sees the delete from the freeze until publication. Only the abort in deleteAll() (DocumentsWriter.java:266-276) drops queued tickets unpublished, while it deletes every document anyway. It covers the reproduced ticket window only; option B also covers the queue-swap window.

// DocumentsWriter
boolean anyDeletions() {
  return deleteQueue.anyChanges() || ticketQueue.anyDeletions();
}

// DocumentsWriterFlushQueue (the diff uses braces)
synchronized boolean anyDeletions() {
  for (FlushTicket ticket : queue) {
    if (ticket.frozenUpdates != null && ticket.frozenUpdates.any()) return true;
    FlushedSegment s = ticket.segment;
    if (s != null && (s.delCount > 0 || s.segmentUpdates != null)) return true;
  }
  return false;
}

Trade-offs

One more monitor acquisition per call, on a queue that holds at most one ticket per flushing segment plus delete-only tickets. anyChanges() also calls anyDeletions(), where the scan is redundant with ticketQueue.hasTickets(); putting the ticket read into hasDeletions() instead avoids that. Counting doc-values updates matches bufferedUpdatesStream.any(), which hasDeletions() already reads. Lock order checked by reading only (callers hold the writer's or the DocumentsWriter monitor, then the ticket queue's; nothing under the ticket queue's monitor takes either); no stress or performance run. It leaves the shorter queue-swap gap open (option B).

  • TestIndexWriterDelete, TestIndexWriter, TestIndexWriterNRTIsCurrent, TestIndexWriterReader, TestDocumentsWriterDeleteQueue: 179 tests, 0 failures, 8 skipped.
  • The whole org.apache.lucene.index test package with the repro: 1398 tests, 0 failures, 56 skipped (215 test classes).
  • :lucene:core:check -x test (google-java-format, ecj lint, forbidden APIs) passes.
  • In a TLA+ model of one delete through one successful full flush (TLC; no abort or failure paths), this read set holds in the ticket window (218 states) and fails only in the queue-swap window.

B: A plus a read of the queue a running full flush swapped out (validated by the checks)

#

Keep the swapped-out queue in a new volatile field (set before markForFullFlush, cleared in finishFullFlush) and let anyDeletions() read it before the tickets. currentFullFlushDelQueue cannot be reused: it is set only inside an assert (DocumentsWriter.java:681).

Trade-offs

More state and an ordering subtlety: in the TLA+ model, reading the tickets first, or setting the field after the swap, fails; the stated order holds over all 220 states. By reading (not run against that finding's repro), it also closes LFV-1264's gap, so it overlaps that finding's fix.

What the checks validated

Run earlier, not in the gradle runs for this page: the repro passes with assertions on and off; TestIndexWriterDelete plus TestIndexWriter pass (141 run, 0 failed, 7 skipped).

Downstream note

#

Downstream code that acts on hasDeletions() right after a delete (a code search found one engine that logs an error when it is false, and one application that runs forceMergeDeletes() only when it is true) can act on the transient false once; a call after the commit gets the right answer.

How it was found

#

Found while modelling IndexWriter's flush path: the places a buffered delete passes through during a full flush were compared with what hasDeletions() reads, and the unpublished flush ticket was the one it skips. Probes on the stock jar showed the false; a TLA+ model (TLC) confirmed it and the fix; then it was reduced to one JUnit test.

The method in full159 words

A component model of IndexWriter's write path tracked where an acknowledged delete sits during a full flush (current queue, swapped-out queue, flush ticket, published-deletes stream, reader pool, segment) against the read set of each status getter. For hasDeletions() two places were missing from the read set, the swapped-out queue and the unpublished ticket. main() probes and a JUnit test on the stock main jar showed the false.

A TLA+ model (HasDelWindow.tla, TLC 1.8.0) then followed one delete through one full flush, with the writer and ticket-queue monitors. With the stock read set the invariant "hasDeletions() returns true" fails in both gaps; with fix B it holds over all 220 states, with non-vacuity checks; two reordered variants of the fix fail; the ticket-only read set (fix A) holds in the ticket gap (218 states) and fails only in the queue-swap gap. The model covers one delete and one full flush, no merges and no other deletion.

Impact note
Hits an application with the default configuration that calls IndexWriter.hasDeletions() on one thread while another thread's commit(), flush() or NRT reader open writes a segment, after a delete by term or query that was buffered before that flush started, and only while the index holds no other deletion (any segment with deletions, pending reader-pool deletes or a published delete packet makes the method return true anyway [read]): the method then returns false for as long as the segment write lasts and is true again once the flush ticket is published; nothing in the index, the committed state or search results is wrong, no scale is needed, and no production code in Lucene calls the method (downstream, the intended-behaviour check found one project that logs an error when it is false right after deleteDocuments and one that runs forceMergeDeletes only when it is true [read]).
Summary
You add documents a and b, delete a with deleteDocuments(new Term("id", "a")), and hasDeletions() returns true; then another thread calls commit(). You expect hasDeletions() to stay true while that commit runs, because its javadoc counts buffered deletions and the delete is either still buffered or already applied at every moment (the method is true before the commit and true after it). Instead, while the commit writes the new segment, hasDeletions() returns false: the flush has frozen the delete into a flush ticket that is not yet published, and DocumentsWriter.anyDeletions() reads only the new, empty delete queue.
