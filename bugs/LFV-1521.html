The finding in 30 seconds

#

ExitableDirectoryReader puts a time limit on a reader: when the limit is up, reads stop with ExitingReaderException. Since 9.11.0 one kind of vector work no longer asks that limit. The search still gives the right hits; it only stops later than it did before.

Background: three pieces

#
  1. ExitableDirectoryReader.wrap(reader, timeout) wraps what a query reads from the index. The wrapped pieces ask timeout.shouldExit() from time to time and throw ExitingReaderException when it says yes. The javadoc promises only a periodic check; in today's code the wrapped vector iterator asks each time the document ID has moved on by 1,000.
  2. A kNN query with a filter does not always use the HNSW graph. When the filter accepts no more documents than the query's per-segment k, or when the graph search is cut short or finds too few hits, it scores the segment's accepted vectors one by one. This is the exact scan.
  3. IndexSearcher#setTimeout is a second, separate way to limit a search. The exact scan asks that limit as well, and that part works.

The finding, step by step

#
  1. Wrap a reader with a time limit: ExitableDirectoryReader.wrap(reader, timeout). The index is one segment of 2,000 documents, each with a vector and the term color:red.
  2. Run a KnnFloatVectorQuery with the filter color:red and k = 2,000. The filter accepts no more documents than k, so Lucene skips the HNSW graph and scores the 2,000 accepted vectors one by one: the exact scan. The time limit runs out as that scan starts.
  3. You expect the scan to stop with ExitingReaderException at the wrapper's next check. The releases 9.2.0 to 9.10.0 stopped it there. The wrapper's own vector iterator over the same segment does stop: with the limit up it throws at its first step.
  4. Instead the scan asks the reader's limit 0 times. All 2,000 vectors are scored and the search returns its 2,000 hits, the same hits as without the wrapper. Why: since 9.11.0 the scan walks a scorer that the wrapper hands out unchecked.
  5. Each such scan is bounded by the documents the filter accepts in its segment. With two such segments on one thread the first segment's 2,000 vectors are still scored, then the search ends with ExitingReaderException at the next segment's filter terms. When no checked read follows (the last scan, some filters), the search returns instead. The same limit set with IndexSearcher#setTimeout stops the scan at its first check.

Who is affected

#

Applications that use ExitableDirectoryReader as their time limit and run filtered kNN queries, DiversifyingChildren kNN queries, vector similarity queries or the similarity values source. The wrapper is opt-in; with it, the default codec and stock queries are enough. Every release from 9.11.0 to 10.6.0. Each unchecked scan is bounded by its segment's accepted documents; no time was measured.

Mechanism, terms and numbers1,356 words

ExitableDirectoryReader.wrap(reader, timeout) makes reads from the index ask timeout.shouldExit() from time to time and throw ExitingReaderException when it returns true. For vectors it wraps the graph search and the vector values' iterator() (ExitableDirectoryReader.java:443-465, :531-534, :650-703 on main 01deb8e63e0b). scorer(target) of the same three wrapper classes is a plain forward, return vectorValues.scorer(target); (:538, :588, :638): the scorer it hands out is the format's own, and neither its iterator nor its bulk scorer asks the reader's limit. Since #13181 (first released in 9.11.0) the exact search of a filtered kNN query walks that scorer (AbstractKnnVectorQuery.java:369, :378); before, it advanced the reader's wrapped, checked vector values. So once the reader's limit is up, an exact scan that is running goes on to its end (with a searcher that has an executor: the scan of each segment being searched at that moment). The search then ends with ExitingReaderException at the next read the wrapper checks, if there is one, and otherwise returns as if no limit were set, as in a one-segment index.

This is a late stop and nothing more. The hits and scores are right, every scan ends, each unchecked scan covers at most the documents the filter accepts in its segment, and a limit set with IndexSearcher#setTimeout is still asked by the scan (AbstractKnnVectorQuery.java:383). It is not a broken documented guarantee: the class javadoc says only that the limit is "checked periodically". The expectation rests on the releases 9.2.0 to 9.10.0, which stopped this scan, on the wrapper's own checked iterator(), and on the project's record: the commit message of #11843 kept the check on advance and names the exact scan, and #12423 fixed a gap of the same kind as a bug. Every release from 9.11.0 to 10.6.0, branch_11x and main behave the same; nothing in 11.0 adds or changes it.

The bug

#
  1. KnnFloatVectorQuery.createVectorScorer takes the reader's vector values and returns vectorValues.scorer(target) (KnnFloatVectorQuery.java:124-132).
  2. Under the wrapper those values are the wrapper's, and their scorer(target) is a plain forward: return vectorValues.scorer(target); (ExitableDirectoryReader.java:538, :588, :638). The scorer is the format's own; its iterator() and bulk(...) do not know the reader's limit.
  3. exactSearch walks that scorer: vectorScorer.bulk(acceptIterator) (AbstractKnnVectorQuery.java:369, :378). No call in the loop reaches the wrapper's checked iterator.
  4. Before #13181 (9.10.0 and earlier) the scan was acceptIterator.nextDoc() plus vectorScorer.advanceExact(doc), and that old scorer advanced the reader's vector values, under the wrapper the checked ones. That is why 9.2.0 to 9.10.0 stop the scan.

Exposure and likelihood538 words
  • Who. An application whose time limit is ExitableDirectoryReader (and not, or not only, IndexSearcher#setTimeout) and that runs a filtered kNN query, a DiversifyingChildren kNN query, a vector similarity query or the similarity values source.
  • Opt-in, then default. It needs the wrapper. With it, the default codec and the stock query classes are enough, at any size, with assertions on and off.
  • What is lost. The check inside the exact scan. A scan that is running when the reader's limit runs out goes on to its end: one scan at a time with the default searcher, every scan in flight with a searcher that has an executor. What follows depends on the next read that the wrapper checks. If there is one, the search ends there with ExitingReaderException: with a TermQuery filter it is the filter's terms in the next segment, or the same terms when the query's second pass re-enters a segment. If there is none, the search returns its complete result as if no limit were set: a one-segment index, a limit that runs out during the last scan, or a filter that reads nothing the wrapper checks between the scans (FieldExistsQuery on a text field), where every later scan runs unchecked as well. All of these were run (see the table above).
  • How much work. Each unchecked scan is at most the documents the filter accepts in its segment. For the kNN query's first entry that is at most the per-segment k, because the entry is taken only when the filter accepts no more than that: k in a one-segment index, otherwise the segment's share of k plus a margin, which for small k is several times the share (its largest value is 30 for k = 10, 144 for k = 100 and 1,060 for k = 1,000; computed from the formula in the code). The fall-back entry scans the filter's accepted documents after a graph search that was allowed that many visits plus one. How many scans run unchecked: the one that is running (each one in flight with an executor) when a checked read follows, and otherwise every scan the search still makes; the query searches a segment at most twice. The longer walks are in the other consumers of the scorer (the similarity queries, the similarity values source, the join module's exact path).
  • What it is not. No wrong hit or score, no search that does not return, no effect on a limit set with IndexSearcher#setTimeout. No time cost was measured.
  • Likelihood: plausible. A user sees it only when the reader's limit runs out while an exact scan is still long.
  • Also lost, by reading only (not run). Every check of the wrapper also throws ExitingReaderException when the searching thread was interrupted, and the 9.10.0 wrapper's vector check did the same. Since 9.11.0 an interrupt therefore does not end this scan either, until the next checked read. A filter clause that the searcher's query cache serves reads nothing from the reader, so it brings no checked read between the scans.
  • Downstream (read, not run). Apache Solr's main branch wraps every searcher's reader in this class; its 9.x branch does so only when the system property solr.useExitableDirectoryReader is set.

The devil's-advocate check432 words

The strongest case for "intended": the javadoc promises only a periodic check and names no operation, and a search that is checked again at its next checked read is still "checked periodically". The wrapper never covered everything: postings are left unchecked on purpose (Adrien Grand on #11580, 2022: "there are likely users who rely on the fact that ExitableDirectoryReader doesn't wrap postings in order to get good performance"); they also wrote that they would like the wrapper "to become mostly implementation details" with "proper support directly on IndexSearcher", and on #11875 that they hope to document it as "a very expert class that is only useful when consuming index readers directly as opposed to through an IndexSearcher". Since the same release 9.11.0 the exact scan asks the limit of IndexSearcher#setTimeout (#13202), and MIGRATE names that method as the way to time out queries. VectorScorer is experimental and was made so that a format can score in its fastest way: the commit message of #13181 says "The scorer contains a copy of the originating iterator and allows for iteration and scoring the most optimized way the provided codec can give", and the 9.11.0 javadoc of scorer() said that the scorer's iterator "is not the same instance as the iterator for this FloatVectorValues. It is a copy" (the sentence is gone from today's javadoc). Each unchecked scan is bounded, and no report was found since 2024.

Why it does not carry, as a reading of the record: nothing documents an exemption and no decision to drop the check is on record. The only design statements on record about this scan say the check stays (#11843), a gap of the same kind was fixed as a bug (#12423), and #13181 has no word on time limits (its statement about the scorer's own iterator is about scoring speed). Silence in a record does not show what was considered. The plan to let the wrapper fade is not carried out: its javadoc is unchanged and #11677 is still open. The use that comment keeps for the wrapper, reading a reader directly, is unchecked too (the direct walk of scorer(target).iterator() above). The searcher's limit is another mechanism with another contract, and an application that puts its limit on the reader only is legal. The cost of a check is a question for the fix (the wrapper's check is sampled), not evidence of intent. What the argument does carry is the weight: Low, and no claim of a violated guarantee. A maintainer may still answer that IndexSearcher#setTimeout is the supported limit; then a javadoc line is what remains.

A. Return a checked scorer from the three scorer(target) overrides (validated on the query paths; one known limit) (recommended)

#

One file, ExitableDirectoryReader.java, +69/-3. The three forwards become return exitableScorer(vectorValues.scorer(target));. exitableScorer returns a VectorScorer whose

  • score() is the wrapped scorer's;
  • iterator() is the wrapped scorer's iterator behind createExitableIterator, the same sampled check that iterator() of the vector values has. It stays a KnnVectorValues.DocIndexIterator, because the seeded and the optimistic kNN collectors map documents to vector ordinals through it (AbstractKnnVectorQuery.java:457-474). An IndexedDISI, which sparse fields of older formats hand out, is first viewed through IndexedDISI.asDocIndexIterator, as those collectors do themselves (:459-461);
  • bulk(matchingDocs) is the format's own bulk scorer, fed with the matching documents behind a sampled check, so the format keeps its own scoring.

It is an earlier fix sketch of this finding with two changes: the IndexedDISI view (a gap that an earlier check found in the sketch) and the wrapper's vector message for the plain-iterator check.

Trade-offs

  • Cost, not measured. No benchmark was run. The iterator path adds one comparison per document, as the vector values' iterator() already has. In the bulk path the wrapped matching-docs iterator hides a bit-set iterator from the conjunction's fast path. A variant that leaves matchingDocs alone and checks once per returned batch would avoid that; it was not built.
  • bulk(null), and a limit of this fix. bulk(null) is served as bulk(all documents). On a scorer whose iterator is unpositioned that scores the same documents (run: 2,000 through the plain reader, the unchanged wrapper and the fix). On a scorer whose iterator was advanced first it does not: after iterator().advance(100) the plain reader and the unchanged wrapper score documents 100 to 1999, and with the fix bulk(null) throws IllegalArgumentException ("Sub-iterators of ConjunctionDISI are not on the same document!"), assertions on and off. No caller in Lucene's sources does this: the one call of bulk in the main sources is the exact scan, with the filter's iterator, and the one test that calls bulk(null) uses an unpositioned scorer. The repair is the variant named under "Cost": hand matchingDocs, null included, to the format's bulk scorer unchanged and check once per returned batch. It was not built. bulk(null) with deleted documents or on a sparse field was not run.
  • An import of org.apache.lucene.codecs.lucene90.IndexedDISI in the index package, which maintainers may prefer to avoid (AbstractKnnVectorQuery already imports it).
  • It does not touch rescorer(target) (LFV-1381). If both repairs go into one change, the rescorer forward should go through the same exitableScorer, so that the rescoring walk is checked as well. The two were not built together.
  • No maintainer has looked at this fix, and the whole core test suite and the other modules' tests were not run with it.

B. Document it

#

State in the class javadoc that scans through scorer(target) (the exact part of kNN and similarity queries) are not checked by the wrapper, and that IndexSearcher#setTimeout is the limit for them.

Trade-offs

Small and safe, but it makes today's behaviour the contract and leaves an application that limits by the reader alone with a late stop. It is what remains if maintainers answer that the searcher's limit is the supported one. Not built.

C. Repair exactSearch only (not suggested)

#

Add a check of the reader's limit to the exact scan of the kNN query alone.

Trade-offs

The query does not see the reader's limit, and the other consumers of the same scorer (the join module's queries, the similarity queries, the similarity values source, direct callers) would stay unchecked. Not built.

Downstream note

#

Apache Solr's main branch wraps every searcher's reader in this class, and its 9.x branch does so only when a system property is set (read in its source, not run); no downstream product was run for this page.

Registry title

Area
index / ExitableDirectoryReader (vector values) and search / kNN queries (exact scan)
Priority
Low, rank 791: Since 9.11.0 the exact scan of a filtered kNN query over the opt-in ExitableDirectoryReader no longer checks the reader's time limit, so once the limit is up a scan that is running still goes on to its end, in every release through 10.6.0 and on both unreleased branches. It is Low because the results are right, each unchecked scan is bounded by the documents the filter accepts in its segment, a limit set with IndexSearcher#setTimeout is still honoured and the check is not a documented guarantee.
Impact class
minor
Impact note
Applications that use ExitableDirectoryReader as their time limit get a late stop: once the limit is up, the exact scan of the segment being searched by a filtered kNN query (and, in this finding's runs, by a DiversifyingChildren kNN query, a vector similarity query or the similarity values source) runs to its end (with a searcher that has an executor: the scan of each segment being searched at that moment), each scan at most the documents the filter accepts in its segment, before the search ends with ExitingReaderException at the next read the wrapper checks or, when there is none (a one-segment index, a limit that runs out during the last scan, a filter that reads nothing the wrapper checks, where every later scan runs unchecked as well), returns as if no limit were set; it needs the opt-in wrapper and nothing else (default codec and query classes, no scale); the results are right, the scan ends, no time cost was measured, and a limit set with IndexSearcher#setTimeout is not affected.
Summary
You wrap a reader with ExitableDirectoryReader and a QueryTimeout and run a kNN query with a filter that makes it score a segment's accepted vectors one by one (the filter accepts no more documents than the query's per-segment k, or the approximate search was cut short or found too few hits), and the time limit runs out as that scan starts. You expect the scan to stop with ExitingReaderException at the wrapper's next check, as it did on 9.2.0 to 9.10.0 (in today's code the wrapper's own vector iterator checks the limit each time the document ID has moved on by 1,000). Instead the scan never asks the reader's limit: since 9.11.0 the wrapper returns the wrapped values' own scorer from scorer(target) and the exact search scores through that scorer, so all 2,000 vectors of the test are scored and the search returns as if no limit were set. Not new in 11: the 10.6.0 release behaves as the 11.0 branch does; nothing is wrong in the results and the scan ends.
