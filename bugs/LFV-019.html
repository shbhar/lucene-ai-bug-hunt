RegExp no longer parses an escaped range start such as [\.-z] as a range

Since Lucene 10.2.0, RegExp reads a class with an escaped range start, such as [\.-z], as three single characters (., -, z) instead of the range . to z. RegexpQuery and the classic query parser's /.../ syntax silently match other terms: 3 instead of 5 in a six-term index.

The bug in 30 seconds

#
  1. Write [\.-z], escaping the reserved . as the RegExp javadoc asks ("also in character classes"), and run it as a RegexpQuery over six one-character terms: a m z . - /.
  2. You expect the range . to z (77 of the 95 printable ASCII characters) and 5 hits, as on 10.1.0 and in java.util.regex.
  3. Since 10.2.0 you get three single characters, ., - and z: 3 hits, no error. 75 of the 77 characters are missing, and - is added.
  4. The cause: a branch that #14227 added to RegExp.parseCharClasses() adds an escaped character (other than an ASCII letter or \) on its own and never checks for a following -. Unescaped starts ([.-z]) and escaped ends ([a-\~]) still work.
  5. Other escaped starts break too: [\!-\~] matches 3 characters instead of 94, [\0-\9] (how RegExp.toString() prints [0-9]) 3 instead of 10, and [\!--] throws IllegalArgumentException.

Who is affected

#

Anyone who passes RegExp a class range whose start is an escaped character other than an ASCII letter or \ (new RegExp(...), RegexpQuery, the classic query parser's /.../ syntax) on 10.2.0 to 10.5.2 or main. It is the default, with no flag. The javadoc's escaping rule leads to such patterns; how common they are is unknown.

Mechanism, terms and numbers808 words

Write the character class [\.-z] and you mean every character from . to z: 77 of the 95 printable ASCII characters. Since Lucene 10.2.0, RegExp reads it as just three characters, ., - and z. So RegexpQuery and the classic query parser's /.../ syntax silently match other terms (3 instead of 5 in a six-term index), and a valid pattern such as [\!--] throws. Lucene 10.1.0, java.util.regex and the grammar in the RegExp javadoc all read [\.-z] as a range. The cause is a parser branch that #14227 added: it never checks for a - after an escaped character.

What you write

#

You want terms made of one character between . and z. Since . is a reserved character, the RegExp javadoc tells you to escape it, and to do so "also in character classes". So you write:

new RegexpQuery(new Term("f", "[\\.-z]"));   // regex text: [\.-z]

What you expect

#

The range from . (U+002E) to z (U+007A): 77 of the 95 printable ASCII characters, including /, the digits, A-Z and a-z. It does not include - (U+002D), one code point below the dot.

What you get, since 10.2.0

#

Exactly three characters: ., - and z. 75 of the 77 characters you wanted are missing, and -, which is outside the range, is added. Index six one-character terms a m z . - / and count the hits:

queryLucene 10.1.0Lucene 10.2.0 to main
[.-z] (no backslash)55
[\.-z] (escaped start)53 (. - z): no error

Other spellings behave the same way (printable ASCII characters accepted, on 10.1.0 against 10.5.2 and main):

  • [\!-\~], meaning "printable ASCII without space": 94 on 10.1.0, 3 (! - ~) now.
  • [\+-0]: 6 (+ , - . / 0), now 3 (+ - 0).
  • [\!--], the range ! to -: 13, now IllegalArgumentException: expected ']' at position 6.
  • [\0-\9], which is what RegExp.toString() prints for [0-9]: 10, now 3 (0 - 9).
  • Unchanged: [.-z] (unescaped start), [a-\~] (escaped end) and [\-] (an escaped dash on its own).

java.util.regex agrees with 10.1.0 on every row above that it accepts (it rejects \0).

Why: one missing check

#

RegExp.parseCharClasses() reads a class one item per loop round (RegExp.java:1312-1348 at ea57360912ed).

  • Unescaped item. It reads a character (1326) and then asks "is the next character -?" (match('-'), 1328). If so, it builds a range up to the character after the dash (1333-1334).
  • Escaped item. After a backslash (1314), a character that is not a letter or \ goes to a separate branch (1318-1323, comment "escaped character, don't parse it"). That branch adds the character as a single item and never asks about the dash.

So for [\.-z] (positions 0-5 hold [ \ . - z ]):

roundwhat the parser doesitem added
1\ matched (1314); . is not a letter (1315); c = next() (1320). on its own; the - at position 3 is never checked
2reads - as a plain character (1326); the next character is z, not - (1328)- on its own
3reads z (1326); the next character is ]z on its own
endthe loop stops at ] (1348); ] is matched (1303)the class {., -, z}

For [\!--], round 2 reads the first -, sees the second -, and builds a range from - to the next character, which is the closing ]. Nothing is left to close the class, so the parser throws "expected ']' at position 6" (1303).

An escaped range end still works. The end is read by parseCharExp() (1502-1505), which accepts an optional backslash, so [a-\~] is still a range.

What 10.1.0 did

#

parseCharClass() (lines 1203-1212 at releases/lucene/10.1.0) consumed the backslash, read the character with parseCharExp(), and then ran the same match('-') range check for both spellings (1209-1210). #14193 (fe42efc5918, 2025-02-06) rewrote this into the parseCharClasses loop, where an escaped non-letter still reached the range check by falling through to the next loop round. #14227 (19be0e5fd11, 2025-02-13) then added the branch above. Both were first released in 10.2.0.

Which escapes are hit: a backslash followed by any character that is not an ASCII letter and not \. That covers digits, punctuation, space and non-ASCII characters, all executed: [\0-\9] gives 3 characters instead of 10, [\ -z] (escaped space) 3 printable ASCII characters instead of 91, and [\é-ü] only é, - and ü instead of the 20 characters from U+00E9 to U+00FC. An escaped backslash as the start ([\\-z]) was never a range, not even in 10.1.0; that older quirk is separate.

Exposure and likelihood370 words
  • Who is hit. Any code that passes such a pattern to RegExp:
    • new RegExp(...) itself;
    • RegexpQuery, whose default constructor uses RegExp.ALL (RegexpQuery.java:54-55);
    • the classic QueryParser /.../ syntax: /[\.-z]/ counts 3 instead of 5 on ea57360912ed [exec];
    • not run: the flexible StandardQueryParser, other AutomatonQuery users and downstream engines.
  • Default, not opt-in. No flag is involved: the escaped branch is unconditional. [\.-z] misses a with RegExp.ALL and with RegExp.NONE [exec].
  • Why people write escaped starts.
    • The javadoc requires escaping reserved characters "also in character classes" (RegExp.java:342-345), so following the docs gives [\.-z].
    • RegExp.toString() itself prints [0-9] as [\0-\9] (on 10.1.0, 10.5.2 and main [exec]). On 10.2.0 and later that string re-parses to 3 characters. Upstream does not promise that toString() output can be re-parsed (rmuir in #14493), so this is only a side effect.
  • Silent. No error, and the matched set is wrong in both directions: most of the range is dropped, and a literal - is added. An exception is raised only in a few shapes, such as a range that ends in -.
  • Breadth. The candidate's bounded-exhaustive differential tried the 1,867 two-endpoint classes [\s-e] that java.util.regex accepts, with s one of the 31 ASCII punctuation characters other than \, and e >= s a printable ASCII character other than [, ], \ and &. On main and 10.5.2, 1,852 give a different language from java.util.regex, 13 throw, and the 2 that agree do so by coincidence. On 10.1.0: 0 and 0. Space and digit starts are not in that set (java.util.regex rejects \0 to \9); they were run separately and are affected too (see "Which escapes are hit" above).
  • Scale. None needed: a six-character pattern triggers it.
  • Released. Every release from 10.2.0 to 10.5.2, and main. Moving from 10.1.0 or an older release changes results with no CHANGES or MIGRATE entry. The clean releases that were run are 9.12.2, 9.12.3, 10.0.0 and 10.1.0; by code reading, 7.0.0, 8.0.0 and 9.0.0 have the same range check for an escaped start.
  • How common. Unknown. No report was found in the roughly 18 months since 10.2.0. Patterns with an unescaped range start are unaffected, which limits the reach.

Why it is a bug, not intended

#
  • The RegExp javadoc grammar makes an escaped character a charexp and a range charexp - charexp, and requires escaping reserved characters "also in character classes".
  • 10.1.0 and java.util.regex read [\.-z] as a range. #14227 fixed [\] without a CHANGES entry; no test covers a dash after an escape.
  • Escaped range ends still work: [a-\~] is a range, [\!-\~] is not.
The full argument323 words

The contract, in its own words. These are the RegExp class javadoc lines at ea57360912ed; the same text is in 10.1.0.

  • RegExp.java:198-201: charclass ::= charexp - charexp, "(character range, including end-points)".
  • RegExp.java:335-336: charexp ::= ... | \ <Unicode character>, "(a single character)".
  • RegExp.java:342-345: "The reserved characters used in the (enabled) syntax must be escaped with backslash (\) or double-quotes ("..."). (In contrast to other regexp syntaxes, this is required also in character classes.)"

By this grammar [\.-z] is charexp('\.') - charexp('z'), a range. The escaped form is also the documented way to write a reserved range start.

History.

  • #14227 ("Fix failure found by TestOperations.testGetRandomAcceptedString", rmuir, approved by dweiss, merged 2025-02-13) fixed a lenient parse of [\].
  • Its commit message says: "When we consume an escape, either it matches the predefined special logic, or we emit range for next(), no other logic: it is an escape."
  • Its new tests cover [\-] (a literal dash), [] and [\]. None of them has a - after an escaped character.
  • CHANGES.txt has no #14227 entry, and MIGRATE.md says nothing about escapes or ranges in classes.
  • In #15182 (2025-09-12) a committer (rmuir) wrote that the syntax "should continue to match https://www.brics.dk/automaton/". The study found that the brics grammar has the same productions.

Tests. No Lucene test builds an escaped range start: TestRegExp.testCoreJavaParity never generates one. With fix option A, every test that was run still passes, including testEscapedDashCharClass: all of util.automaton, search.TestRegexp* and search.TestAutomatonQuery* (266), the queryparser module (533), and 96 tests in 7 other core classes that use RegExp. Tests in other modules that use it (highlighter, monitor, queries, memory, analysis) were not run with the fix.

An independent cross-model review (an independent reviewer from another model family, OpenAI GPT-5.6) was asked to refute the claim. It returned the verdict "real" with high confidence, and it rated the intended-behaviour argument "weak".

The devil's-advocate check405 words

The strongest case for "intended":

  • The author deliberately wrote "escaped character, don't parse it" and "no other logic: it is an escape".
  • testEscapedDashCharClass pins [\-] as a literal.
  • RegExp is @lucene.experimental (RegExp.java:352).
  • On 10.5.2 and main, [\.-] gives {., -}, as in java.util.regex; 10.1.0 throws on it.
  • Just before #14227, escaped range starts worked only by accident: after #14193 (fe42efc5918) rewrote the class parser into a loop, expandPreDefined consumed nothing for a non-letter such as ., so the next loop round re-read it through parseCharExp() and did the range check. #14227 replaced that fall-through, so it may have meant to remove it.

So an escape would make a character an opaque literal, and a dash after it would be a literal too.

Why it fails:

  1. "Emit range for next()" describes the one-character item for the escaped character itself. Neither the PR nor its tests mention a following -.
  2. The grammar in the same file still defines \ <char> as a charexp and a range as charexp - charexp, and it requires escaping reserved characters in classes. Under the "opaque" reading there would be no documented way to start a range at a reserved character.
  3. The parser is not consistent with that reading either. A range end still accepts an escape, so [a-\~] is a range while [\!-\~] is not.
  4. No CHANGES or MIGRATE entry announces a change of meaning, and the PR fixed a different input. Being experimental allows API changes, but this silently changed what an existing, documented pattern matches.
  5. Fix option A keeps [\-] a literal, and every existing test that was run with it passes (scope under "Tests").
  6. The accidental fall-through never reached a release: #14193 and #14227 were merged a week apart and both first released in 10.2.0. Every release up to 10.1.0 had an explicit range check for an escaped start, and #14227's tests and description concern [\], not a range.

A question the owner may get. The grammar also lists \d, \s and \w as a charexp, yet [\d-z] is {0-9, -, z} on both 10.1.0 and main (executed). So charexp - charexp was never applied literally to predefined classes. That does not weaken the claim: the \ <Unicode character> production is explicitly "(a single character)", and it was a range start through 10.1.0.

Verdict: not intended; a regression.

Suggested fix

#

Recommended A: let an escaped character fall through to the shared range check

In parseCharClasses, send an escaped character that is not an ASCII letter or \ through the shared match('-') range check. All 15 pattern-table rows match 10.1.0; the repro, 266 automaton and regexp core tests and 533 queryparser tests pass (other modules not run). It also fixes LFV-022 (escaped characters skipping CASE_INSENSITIVE). [\.-] and [\~-!] throw again, as in 10.1.0.

All options and trade-offs3 options · 699 words

One fix was validated with the gradle build in a scratch worktree at ea57360912ed: option A, the study's idea, restructured. The others are design alternatives and were not run.

A: let an escaped character fall through to the shared range check (validated by the checks) (recommended)

#

In parseCharClasses, an escaped character that is not a letter or \ sets c = next() and then goes through the same match('-') range check, case-insensitive handling and single-character code as an unescaped one. The predefined-class branch ends with continue, which in a do-while goes to the loop condition, as before. The patch is +21/-22 lines in one method, mostly re-indentation.

do {
  int c;
  if (match('\\')) {
    if (peek("\\ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz")) {
      expandPreDefined(starts, ends); // \d \s \w ..., \\, or throws for other letters
      continue;
    }
    c = next(); // escaped character: taken literally, but it can still start a range
  } else {
    c = parseCharExp();
  }
  if (match('-')) { /* range or CASE_INSENSITIVE_RANGE, unchanged */ }
  else if (check(ASCII_CASE_INSENSITIVE | CASE_INSENSITIVE)) { /* case forms, unchanged */ }
  else { /* single character, unchanged */ }
} while (more() && !peek("]"));

Trade-offs

  • Restores 10.1.0 behaviour: all 15 rows of the pattern table match 10.1.0 exactly.
  • Also fixes registry bug LFV-022 (CASE_INSENSITIVE skipped for an escaped character in a class), because escaped characters now take the shared path: its repro goes from 6 of 7 failing to 7 of 7 passing. Mention it in the issue or the CHANGES entry, or file the two together.
  • The same case-folding change applies under the deprecated ASCII_CASE_INSENSITIVE flag: the shared code checks ASCII_CASE_INSENSITIVE | CASE_INSENSITIVE (RegExp.java:1336), and the flag's javadoc says it now behaves like CASE_INSENSITIVE (418-425). It matters only for escaped characters with other case forms, in practice escaped non-ASCII letters such as \é, since escaped ASCII letters go to expandPreDefined. Not run with that flag.
  • Some patterns that 10.5.2 and main accept throw again, as in 10.1.0. [\.-] gives {., -} today and throws "expected ']' at position 5" with the fix, as [.-] already does on main. [\~-!] gives {!, -, ~} today and throws "invalid range" with the fix. This deserves a CHANGES line.
  • An escaped backslash as the start ([\\-z]) stays a non-range, as in 10.1.0; out of scope.

B: check for a dash inside the escaped branch only

#

Copy the match('-') range and CASE_INSENSITIVE_RANGE handling into the else branch at RegExp.java:1318-1323.

Trade-offs

The smallest behavioural change: escaped single characters still skip case folding, so LFV-022 stays open. It duplicates the range code in two places. Not run.

C: keep the 10.2+ behaviour and document it (not recommended)

#

Amend the javadoc to say that an escaped character cannot start a range.

Trade-offs

It contradicts the grammar and the escaping rule in the same javadoc, and the brics grammar a committer wants to keep. It leaves no documented way to start a range at a reserved character, and it keeps the silent change for everyone who upgraded from 10.1 or earlier.

Downstream note

#

A pattern that reaches RegExp (from an application, an administrator's allow or deny patterns, or an end user's query) can match a different set than written; a deny or exclusion pattern that matches less widens what is allowed. No affected real pattern is known. Lucene's SECURITY.md leaves untrusted input to the application, so this is normally a correctness bug.

How it was found

#

Bug record

LFV-019, snapshot of 2026-10-29

Registry title
RegExp no longer parses an escaped range start such as [\.-z] as a range
Area
util / automaton
Priority
Medium, rank 31: A default-syntax RegExp regression since 10.2 silently changes what a character-class range starting with an escaped character such as [\.-z] matches (an Elasticsearch role pattern could widen access), with a cheap parser fix, but such ranges are rare.
Impact class
silent wrong results
Impact note
Anyone whose regular expression starts a character-class range with an escaped character (RegexpQuery, RegExp, policy patterns written as Lucene regexes); default syntax; released since 10.2.0.
Summary
You write a RegexpQuery or RegExp whose character class starts a range with an escaped character, such as [\.-z]. You expect it to match the range from '.' to 'z', as in 10.1 and java.util.regex. Instead, since 10.2.0, it is parsed as the three characters '.', '-' and 'z', so the query silently matches different terms.
Introduced
19be0e5fd11 (#14227), commit-level bisect (2025-02-13)
First affected version
10.2.0
Affected versions
10.2.0, 10.5.2 and main wrong; 9.12.2 and 10.1.0 correct [exec]
Status
documented (brief, checks and a per-bug doc exist)
Verification
Confirmed in the earlier formal verification study by independent AI checks and a rerun on Lucene main; also a cross-model review that agreed; not yet triaged by a person.
