GroupingSearch never rewrites its group sort or within-group sort against the searcher, unlike IndexSearcher#search

GroupingSearch#search gets the searcher but, unlike IndexSearcher#search(query, n, sort), never rewrites its group and within-group sorts against it. Sorts that need the searcher then throw, and a legacy QueryValueSource sort on a ClassicSimilarity searcher silently lists a group as doc0 (0.147), doc1 (0.125) instead of doc1 (1.0), doc0 (0.894).

The finding in 30 seconds

#

GroupingSearch#search(searcher, query, ...) hands its group sort and within-group sort to the grouping collectors without Sort#rewrite(searcher), the step IndexSearcher#search(query, n, sort) takes first. Sorts whose fields need the searcher then throw, or, for a legacy QueryValueSource view, score with the default Similarity.

Background in three steps

#
  1. A Sort can hold fields that need the searcher before they can sort, such as a function sort from ValueSource#getSortField or a query-score sort from DoubleValuesSource.fromQuery. Sort#rewrite(searcher) binds them to it.
  2. Since 7.2.0, IndexSearcher#search(query, n, sort) calls sort.rewrite(this) itself, so callers can pass such a Sort as it is.
  3. GroupingSearch orders the groups by a group sort and the documents inside each group by a within-group sort, and runs its collectors on the searcher passed to search.

The finding, step by step

#
  1. You index two documents in one group g: doc 0 = a a a a a a a a x x, doc 1 = a. The searcher uses ClassicSimilarity, and you sort the documents inside each group by the score of body:a: new Sort(new QueryValueSource(body:a, 0).asDoubleValuesSource().getSortField(true)).
  2. You expect new GroupingSearch("group").setSortWithinGroup(sort) to list the group as searcher.search(matchAll, 10, sort) does for the same Sort: doc1 (1.0), then doc0 (0.894). IndexSearcher gets there by calling sort.rewrite(this) first.
  3. Instead the group comes back as doc0 (0.147), doc1 (0.125): the scores of the default BM25 Similarity, in the opposite order. GroupingSearch never rewrites its Sorts, so the score source has no searcher, and QueryValueSource scores body:a with a fresh default IndexSearcher.
  4. Most sorts that need the searcher fail loudly instead, and only in GroupingSearch: a ValueSource#getSortField sort throws "SortField needs to be rewritten ...", a DoubleValuesSource.fromQuery sort "This DoubleValuesSource must be rewritten". Group order and group heads go wrong the same way.

Who is affected

#

GroupingSearch users who sort groups or group documents by a function or a query score. Usually it throws on the first grouped search although IndexSearcher accepts the sort; the silent wrong order needs a legacy QueryValueSource sort and a non-default Similarity. Field sorts and relevance are unaffected. Any index size, since 7.2.0.

Mechanism, terms and numbers493 words

GroupingSearch takes a group sort and a within-group sort and runs its collectors on the searcher passed to search(searcher, query, ...). Since 7.2.0, IndexSearcher#search(query, n, sort) binds a Sort to the searcher with sort.rewrite(this) before sorting; GroupingSearch never does, although it rewrites its own groupEndDocs query against that searcher. A sort that works in IndexSearcher#search therefore throws in GroupingSearch ("SortField needs to be rewritten ..." for a ValueSource#getSortField sort, "This DoubleValuesSource must be rewritten" for a DoubleValuesSource.fromQuery sort), and a sort on a legacy QueryValueSource through asDoubleValuesSource() silently scores with the default Similarity: on a ClassicSimilarity searcher a two-document group comes back as doc0=0.147, doc1=0.125 (default-BM25 scores) instead of doc1=1.0, doc0=0.894. Group order and group heads go wrong the same way; the set of matching documents never changes. Every release from 7.2.0 to 10.6.0 and main is affected. Rewriting both Sorts at the start of the two grouping methods (4 added lines) fixes every case; all 56 existing grouping tests stay green.

The mechanism (main 5adff78bb168)

#
  1. IndexSearcher binds the Sort. searchAfter, which search(Query, int, Sort) uses, does final Sort rewrittenSort = sort.rewrite(this); and builds its TopFieldCollectorManager from it (IndexSearcher.java:730-733). Sort.rewrite rewrites each field and returns this when nothing changes (Sort.java:88-99). It is the only Sort.rewrite call in the non-test sources under lucene/.
  2. GroupingSearch does not. groupByFieldOrFunction passes the field groupSort to FirstPassGroupingCollectorManager (GroupingSearch.java:148), sortWithinGroup to AllGroupHeadsCollectorManager (:160) and both to TopGroupsCollectorManager (:201-202). groupByDocBlock rewrites its groupEndDocs query with searcher.rewrite(this.groupEndDocs) (:223) and then passes both Sorts as given to BlockGroupingCollectorManager (:228, :233). The collector managers take only a Sort and never see the searcher.
  3. Loud path. The collectors build comparators with SortField.getComparator (FirstPassGroupingCollector.java:116, AllGroupHeadsCollector.java:241, BlockGroupingCollector.java:237). A Type.REWRITEABLE field, which ValueSource#getSortField returns (ValueSource.java:369-384), throws "SortField needs to be rewritten through Sort.rewrite(..) and SortField.rewrite(..)" (SortField.java:555-557); a DoubleValuesSource.fromQuery source throws "This DoubleValuesSource must be rewritten" until it is rewritten (DoubleValuesSource.java:768).
  4. Silent path. ValueSource#asDoubleValuesSource() returns a wrapper with no searcher (ValueSource.java:184-185); its values get a function context whose searcher is null (:198-200), and only rewrite(searcher) returns a wrapper that carries the searcher (:244-245). QueryValueSource then finds no searcher and scores its query with new IndexSearcher(ReaderUtil.getTopLevelContext(readerContext)) (QueryValueSource.java:116-123): the same reader, the default Similarity.
  5. What does not change. The collectors only see documents the caller's query matched on the caller's searcher (GroupingSearch.java:173, :175, :211, :237): the matching documents and groups are the same; only order, sort values and group heads differ, or the request throws.

The numbers of the example

#

On ClassicSimilarity, body:a scores sqrt(tf)/sqrt(length) with idf 1 (both documents match): doc 1 gets sqrt(1)/sqrt(1) = 1.0 and doc 0 gets sqrt(8)/sqrt(10) = 0.894. A plain IndexSearcher over the same reader (default BM25) scores them 0.14679137 and 0.12456752, and those are exactly the sort values GroupingSearch returns.

Exposure and likelihood201 words
  • Who is hit. Applications that group with GroupingSearch (field, function or doc-block grouping) and sort groups or the documents inside a group by a queries-module function sort (ValueSource#getSortField), a query-score sort (DoubleValuesSource.fromQuery) or an IndexReaderFunctions sort that needs the searcher, such as docFreq or sumTotalTermFreq (all loud), or by a legacy QueryValueSource through asDoubleValuesSource() (silent when the Similarity is not the default).
  • Default vs opt-in. Sort.RELEVANCE (the default) and field sorts are unaffected. The silent form also needs a searcher Similarity other than the default BM25: ClassicSimilarity, BooleanSimilarity and BM25 with other parameters were all executed. No codec, analyzer or index setting is involved; assertions on or off.
  • Scale. Any index size (two documents are enough); deterministic: every grouped search with such a sort.
  • Silent vs loud. The loud forms fail on the first grouped search with a message that names the rewrite. The silent form returns plausible but wrong orderings, sort values and group heads with no signal.
  • How likely. Rare: upstream grouping tests and docs use only field sorts and relevance, and nobody has reported it since 7.2.0 (2017).
  • Workaround. setGroupSort(sort.rewrite(searcher)) and setSortWithinGroup(sort.rewrite(searcher)), once per searcher: on the example it gives doc1=1.0, doc0=0.894.

Why it looks unintended

#
  • GroupingSearch#search is handed the searcher and rewrites its own groupEndDocs query with it (GroupingSearch.java:223), but not its Sorts.
  • Since 7.2.0 the class that holds the searcher rewrites the Sort (IndexSearcher.java:730); a consumer missed then was fixed as a bug.
  • No javadoc asks callers to pre-rewrite, and an upstream test expects agreement with IndexSearcher#search for the same Sort.
The full argument261 words
  • The class that holds the searcher rewrites. LUCENE-7736 (7.2.0) moved the rewrite into IndexSearcher (IndexSearcher.java:730); its author wrote that Sort.rewrite() "wasn't being called by IndexSearcher or SortRescorer" (#8787, 2017-04-10). A consumer left behind then was fixed as a bug: "LUCENE-7736: CoveringQuery needs to rewrite its ValuesSource." (6b621ea659b on branch_7x and 3f0b240853d on master, 2017-11-22). Earlier, Solr fixed another consumer that holds the searcher in the same way: SOLR-6118, "expand.sort bug for function queries; needed to sort.rewrite(searcher)" (6ffdda4545e, 2014).
  • GroupingSearch holds the searcher. search(searcher, query, ...) is given the IndexSearcher, and groupByDocBlock rewrites its groupEndDocs query against it (GroupingSearch.java:223). Only the Sorts are left out.
  • No precondition is documented. The class javadoc (:41-45), search (:115-129), setGroupSort ("Specifies how groups are sorted", :285-294) and setSortWithinGroup (:296-305) say nothing about pre-rewriting; neither do the package docs, MIGRATE.md or CHANGES.txt.
  • An upstream test expects agreement. BaseGroupSelectorTestCase#testSortGroups sets the same Sort on GroupingSearch and on searcher.search(topLevel, 1, sort) and asserts (assertArrayEquals, :118) what its code comment states: "The top group should have sort values equal to the sort values of the top doc of a top-level search sorted by the same Sort" (BaseGroupSelectorTestCase.java:83-121, comment :112-114); it uses field sorts only.
  • No consistent semantics explains the current answers. One Sort object gives one order through IndexSearcher#search and another through GroupingSearch; a sort IndexSearcher accepts throws in GroupingSearch; and in the silent case the grouped order depends on a Similarity the application never chose.
The devil's-advocate check171 words

The strongest case for "works as designed": callers rewrite Sorts. That was the rule when GroupingSearch was written (LUCENE-3778, 2012, when IndexSearcher did not rewrite either); the REWRITEABLE javadoc and the error message tell you to call Sort.rewrite; upstream TestFunctionQuerySort still calls sf.rewrite(searcher) itself (TestFunctionQuerySort.java:65); Solr's grouping weights its sorts before building the collectors; the low-level collector managers have no searcher; #5619 describes caller-side rewriting as the status quo; and GroupingSearch is @lucene.experimental.

Why it fails: unlike the collector managers, GroupingSearch#search is handed the searcher and already rewrites its own query with it; since 7.2.0 the Lucene class that holds the searcher rewrites, and a missed consumer was fixed as a bug; no documentation states the precondition; and a silent fallback to a different Similarity is not a plausible design. The argument does fairly make the loud forms an API-consistency defect rather than corruption. Two devil's-advocate reviews (one by an independent reviewer from another model family, OpenAI GPT-5.6) rated it moderate and not persuasive; the adjudication agreed.

Suggested fix

#

Recommended A. Rewrite both Sorts at the start of the two grouping methods (validated)

Rewrite both Sorts against the searcher at the start of groupByFieldOrFunction and groupByDocBlock, into local variables (4 added lines in GroupingSearch.java), so a reused GroupingSearch keeps its configured Sorts. The repro passes with assertions on and off, all 57 grouping-module tests pass, and the loud sorts stop throwing.

// groupByFieldOrFunction, before the first collector manager; groupByDocBlock, after endDocsQuery
final Sort groupSort = this.groupSort.rewrite(searcher);
final Sort sortWithinGroup = this.sortWithinGroup.rewrite(searcher);
All options and trade-offs4 options · 517 words

Four options. A was built and validated on main 5adff78bb168; B to D were not built. Workaround until a fix ships: setGroupSort(sort.rewrite(searcher)) and setSortWithinGroup(sort.rewrite(searcher)) once per searcher.

A. Rewrite both Sorts at the start of the two grouping methods (validated) (recommended)

#

In groupByFieldOrFunction, before the collector managers are built, and in groupByDocBlock, after the groupEndDocs rewrite, add two local variables that shadow the fields. The rest of both methods is unchanged. One file, +4 lines.

// groupByFieldOrFunction, before the first collector manager; groupByDocBlock, after endDocsQuery
final Sort groupSort = this.groupSort.rewrite(searcher);
final Sort sortWithinGroup = this.sortWithinGroup.rewrite(searcher);

Trade-offs

  • Cost: Sort.rewrite returns this when no field changes, so field sorts and relevance get no new objects; a function sort is rewritten once per search, as in IndexSearcher#search. Already-rewritten Sorts are unaffected (a second rewrite is harmless).
  • The returned TopGroups#groupSort / withinGroupSort then hold the rewritten SortFields, as TopFieldDocs#fields does after IndexSearcher#search.
  • GroupingSearch then shares the path IndexSearcher uses for these sorts, with its two defects listed on this site: LFV-770 (a rewritten toSortableLongDoubleValuesSource() sorts on (long) casts) and LFV-567 (a ValueSource sort context shared across the slices of an executor search). Fix LFV-770 with or before this.
  • Subclasses that override the protected grouping methods do not get the rewrite.

B. Document that callers must pass rewritten Sorts

#

Javadoc on setGroupSort and setSortWithinGroup: "rewrite the Sort against the searcher first".

Trade-offs

No code change, but it keeps the silent trap, ties a configured GroupingSearch to one searcher, and leaves it inconsistent with IndexSearcher#search.

C. Make QueryValueSource fail instead of falling back to a default searcher

#

Throw when the function context has no searcher, instead of creating a default-Similarity IndexSearcher (QueryValueSource.java:116-123).

Trade-offs

Turns the silent form into a loud one everywhere, not only in GroupingSearch, but changes behaviour for callers that rely on the fallback and does nothing for the loud forms. A separate question for maintainers.

D. Rewrite inside the grouping collector managers

#

The generic direction of #5619: every consumer rewrites.

Trade-offs

The managers take only a Sort and never see a searcher, so this needs an API change in every grouping manager; much broader than A.

Downstream note

#

A product that used the group order or group head of a query-function sort as a selection rule would pick a different, still matching document; no such use is known.

How it was found

#

Semi-formal. A bytecode scan of the stock jars found the grouping collectors' sort-comparator calls with no Sort rewrite on the path from GroupingSearch#search. A bounded-exhaustive comparison then ran 23 Sort consumers with the raw Sort and with it pre-rewritten, over every index of 1-3 tiny documents, 3 Similarities and 18 value sources; GroupingSearch differed, IndexSearcher never did.

The method in full214 words

Method: semi-formal (bounded-exhaustive translation validation) of the APIs that consume a Sort or a values source.

  • A ClassFile scan of the stock jars listed the grouping collectors' getComparator sites (FirstPassGroupingCollector:116, the TopGroups/SearchGroup comparators, AllGroupHeadsCollector:241, BlockGroupingCollector:237) with no Sort rewrite on the path from GroupingSearch#search.
  • A test program on the stock main jars (assertions off) then enumerated every index of 1-3 documents over a 12-value per-document alphabet, in all 1-2 segment splits and deletion masks (42,648 index configurations), x 3 searcher Similarities (BM25, Classic, Boolean) x the 282 applicable pairs of 18 values sources and 23 consumer APIs (some consumers take only double or only long sources): 36,080,208 runs of a consumer fed the raw Sort or source, compared with the same consumer fed it pre-rewritten against the searcher.
  • The GroupingSearch group-sort and within-group consumers were silent (different results, no error) under Classic and Boolean similarity for every legacy query() function source (group heads: under Boolean), and loud (an exception) for fromQuery sources and for the IndexReaderFunctions sources that need the searcher (docFreq, sumTotalTermFreq; termFreq gave the same result either way). The IndexSearcher#search control was never silent.
  • The case was reduced to a 3-test public-API JUnit test (2026-10-27), which failed with assertions on and off.

History

#

Introduced in 7.2.0 by LUCENE-7736 (03afeb7766a, committed 2017-11-15), which made IndexSearcher#search rewrite Sorts but did not touch GroupingSearch, which has used its Sorts as given since 2012. 7.1.0 is consistent; every release run from 7.2.0 to 10.6.0 and main diverges. Not fixed upstream.

Versions tested8 rows

Introduced by LUCENE-7736, "Expose some IndexReader stats via DoubleValuesSources" (commit subject "IndexReaderValues"; apache/lucene#8787; a JIRA patch, no PR; author romseygeek, authored 2017-03-28, committed 2017-11-15): 03afeb7766a on branch_7x (first released in 7.2.0) and 2a4dd499bbd on master (8.0.0). It added sort.rewrite(this) to IndexSearcher (7.1.0's IndexSearcher has none, 7.2.0's has it at line 545) and made DoubleValuesSource sort fields and the asDoubleValuesSource() view get their searcher only through rewrite. GroupingSearch was not changed.

The defect site is older. GroupingSearch has passed its Sorts as given since LUCENE-3778 (89b55566d83, 2012-03-22, first in 4.0.0-alpha), when every consumer, IndexSearcher included, needed a caller-rewritten Sort. Its only rewrite ever is of the groupEndDocs query.

Masking caveat for 7.2.0 to 7.7.1 and 8.0.0. There a Sort that an earlier IndexSearcher#search had rewritten kept that searcher (removed by LUCENE-8726 in 7.7.2 and 8.1.0), which hides the group-order failure when the same Sort object is reused; with separately built Sorts it fails there too. The minimal repro runs GroupingSearch first.

Not fixed upstream: GroupingSearch.java was last changed by 3afffeef5a8d (#16247, 2026-07-08, unrelated); upstream main f72004515ec2 (2026-11-03) has the code of 5adff78bb168.

LFV-816, snapshot of 2026-11-04

Registry title
GroupingSearch#search never rewrites its group sort or within-group sort against the searcher, unlike IndexSearcher#search(Query, int, Sort): sorts that need a rewrite throw, and a legacy query() function sort silently orders groups, group documents and group heads with the default Similarity
Area
grouping / GroupingSearch (convenience API)
Priority
Medium, rank 216: GroupingSearch has had the same missing Sort rewrite since 7.2 (a loud failure, silent only on the rare legacy values-source bridge), so it gets the same Medium tier as LFV-815 and LFV-814.
Impact class
silent wrong results
Impact note
Applications that group with GroupingSearch and sort the groups or the documents inside a group by a Sort that needs the searcher are hit at any index size, in every release from 7.2.0 to 10.6.0: in the narrow silent case (a legacy QueryValueSource viewed through asDoubleValuesSource() on a searcher with a non-default Similarity such as ClassicSimilarity or BooleanSimilarity) the group order, group sort values, within-group order and all-group-heads follow default-BM25 scores with no error, and in the loud cases (ValueSource#getSortField, DoubleValuesSource.fromQuery and IndexReaderFunctions sorts) every grouped search throws a 'needs to be rewritten' / 'must be rewritten' error although IndexSearcher#search accepts the same Sort; field sorts, Sort.RELEVANCE and default-Similarity searchers are unaffected, and callers can work around it with setGroupSort(sort.rewrite(searcher)) and setSortWithinGroup(sort.rewrite(searcher)) per searcher.
Summary
You group with GroupingSearch and set a group sort or within-group sort that depends on the query or the searcher, for example a sort on new QueryValueSource(q, 0).asDoubleValuesSource(), and expect the groups and their documents in the order IndexSearcher#search(query, n, sort) gives for the same Sort on the same searcher, because IndexSearcher rewrites the Sort and GroupingSearch#search is handed that searcher. Instead GroupingSearch passes both Sorts to its collectors as given (GroupingSearch.java:148, 160, 201-202, 228-233): on a ClassicSimilarity searcher the documents of one group come back as doc0=0.101, doc1=0.088, doc2=0.088 (default-BM25 scores) instead of doc1=1.0, doc2=1.0, doc0=0.894, the first group is g0 instead of g1, and ValueSource sort fields or fromQuery sorts throw. Rewriting both Sorts against the searcher at the start of groupByFieldOrFunction and groupByDocBlock fixes every case.
Introduced
03afeb7766a39996de3c85e8a6ab24d2a352dd1c on branch_7x (the copy first released, in 7.2.0); master equivalent 2a4dd499bbd2f5ed1f481e17eeaee4f32b927185. LUCENE-7736 'Expose some IndexReader stats via DoubleValuesSources' (apache/lucene#8787; JIRA patch, no GitHub PR; author romseygeek) made IndexSearcher#search(Query, int, Sort) call sort.rewrite(this) (IndexSearcher.java:730 on main) and gave DoubleValuesSource sort fields and ValueSource#asDoubleValuesSource() views their searcher only through rewrite, but did not touch GroupingSearch. A consumer left behind, not a line added to GroupingSearch: its Sort-as-given code dates from LUCENE-3778 (89b55566d83, 2012-03-22, first released in 4.0.0-alpha), when every consumer, IndexSearcher included, needed a caller-rewritten Sort; GroupingSearch's only rewrite in its whole history is of the groupEndDocs query (LUCENE-8242) [exec: release-level bisection, 7.1.0 consistent and 7.2.0 divergent, including with separately built Sort objects, plus the candidate fix applied to the 7.2.0 GroupingSearch, which passes all 4 history tests; no build at the parent commit] (2017-11-15 (LUCENE-7736 committed on master and branch_7x; author date 2017-03-28); first released in 7.2.0 (tag 2017-12-19).
