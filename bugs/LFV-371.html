S2PrefixTree: a Contains query for a point misses the document stored at that same point when the point lies on an S2 cell edge, such as the equator

With the experimental S2 prefix tree, Contains(Point(10, 0)) finds 0 documents for a document stored at Point(10, 0), while Intersects finds 1: a point exactly on an S2 cell edge (the equator, some meridians, (0,0)) is missed. Every release since 7.3.0 is affected; a small query-side fix needs no reindexing.

The bug in 30 seconds

#

S2PrefixTree cuts the globe into cells, level by level. A point exactly on the border between two cells is stored under one of them, but a Contains query looks in every cell that touches the point and requires the document to be in all of them.

  1. You index one document at Point(10, 0), on the equator, with RecursivePrefixTreeStrategy over new S2PrefixTree(ctx, 8) in the Geo3d spatial context, and count an Intersects and a Contains query for that same point.
  2. You expect 1 and 1: Contains means OGC "Covers", and a point covers itself. The geohash and quad trees return 1, and so does the S2 tree for (10, 0.5), just off the equator.
  3. You get 1 and 0. The same at every S2 cell edge point tried: on the equator, on longitudes 0, ±45, ±90, ±135 and 180 near the equator, and at (0,0).
  4. Why: the equator is the border between two S2 cells. Indexing stores the point under just one of them, here the northern one, one cell per level.
  5. But the Contains query takes every cell the point touches, here both, and keeps only documents found in all of them. The other cell holds nothing, so the document drops out. The geohash and quad trees take only the cell the point is stored in.

Who is affected

#

Applications on the opt-in, experimental S2PrefixTree (Geo3d context only; Solr can select it with prefixTree="s2") that run Contains with a point, through RecursivePrefixTreeStrategy or CompositeSpatialStrategy. Every document stored at exactly that point is silently lost when the point is on a cell edge. The rectangles and circles tested, Intersects and IsWithin are fine.

Mechanism, terms and numbers896 words

With RecursivePrefixTreeStrategy over the experimental S2PrefixTree (Geo3d spatial context), a Contains query whose shape is a point P misses every document indexed as exactly P when P lies on an S2 cell edge: Contains(Point(10, 0)) returns 0 hits for a document at Point(10, 0), while Intersects returns 1, and the geohash and quad trees return 1. Indexing stores a point under one cell per level (S2CellId.fromLatLng), but S2PrefixTreeCell.getNextLevelCells has no point case and returns every child cell that touches P (2 on an edge, 4 at (0,0)); ContainsPrefixTreeQuery ANDs the documents of those children, and the child P was not stored under has none. It affects every release from 7.3.0 to 10.5.2 and main, also through CompositeSpatialStrategy. A point case in getNextLevelCells that returns the one child P is stored under, as LegacyCell already does for the other trees, fixes it without reindexing.

Terms

#
  • Prefix tree (RPT): RecursivePrefixTreeStrategy indexes a shape as the grid cells it covers, one term per cell, from coarse to fine levels. A query walks the same grid from the top and looks the cells up.
  • S2 cells: S2PrefixTree uses S2 geometry: the sphere is projected onto the 6 faces of a cube, the 6 faces are the first level, and each further level splits a cell into 4 children (16 or 64 with arity 2 or 3), the first split running along the face's centre lines. So on the four equatorial faces the face borders (longitudes ±45 and ±135) are cell edges from the first level on, the equator and longitudes 0, ±90 and 180 from the second level on, and (0,0), the centre of face 0, is a corner where 4 cells meet.
  • Contains: SpatialOperation.Contains, the OGC "Covers" predicate: the indexed shape covers the query shape, boundary included; equal shapes count.

Step 1: indexing stores a point under one cell per level

#

S2PrefixTree.getTreeCellIterator (S2PrefixTree.java:141-155 at a9779ef3c193) handles a Point by computing S2CellId.fromLatLng(S2LatLng.fromDegrees(lat, lon)).parent(...) and emitting that cell and its ancestors: exactly one cell per level. For a point on an edge, fromLatLng puts it into one of the touching cells.

Step 2: the Contains query ANDs the children it is given

#

For Contains, RecursivePrefixTreeStrategy.makeQuery builds a ContainsPrefixTreeQuery (RecursivePrefixTreeStrategy.java:199-201). Its visitor asks cell.getNextLevelCells(queryShape) (ContainsPrefixTreeQuery.java:120) and computes "the AND of all child results" (:111): a child with no indexed term makes the result empty and stops the loop (:123-124, :137); otherwise the next child is searched only among the documents found so far (:138).

Step 3: the S2 query side has no point case

#

S2PrefixTreeCell.getNextLevelCells (S2PrefixTreeCell.java:156-173) builds all children and returns new FilterCellIterator(cells.iterator(), shapeFilter). FilterCellIterator keeps every cell whose relation to the filter intersects() (FilterCellIterator.java:48-53), and a closed cell whose border passes through the point intersects it. The geohash and quad trees special-case a point and return only the sub-cell it falls in (LegacyCell.java:134-143):

if (shapeFilter instanceof Point point) {
  LegacyCell cell = getSubCell(point);
  cell.shapeRel = SpatialRelation.CONTAINS;
  return new SingletonCellIterator(cell);
}

Step 4: the result

#

Of the touching children, only the one the point was stored under has terms for the document, so the AND is empty. For Point(10, 0) this happens at the second level, where the equator splits face 0 into a northern and a southern half: the query side gets 2 children there. A probe with the arity-1 S2 tree at its maximum depth (31 levels) measured 2 children for 11 points on the equator, the face borders and the face-centre meridians and 4 for (0,0); all 12 miss with Contains and are found by Intersects, while (1,10), (46,20), (10,0.001) and (91,10) get 1 child per level and are found by both. A trace of the stock visitor on the repro's index shows it asks the world cell, face 0 and the .0 side down to level 7 for children and never .1 or anything below it: after .0's leaf term the term enumeration is used up, so seek(.1) is false and the loop breaks (ContainsPrefixTreeQuery.java:144-145, :123-124, :137).

What is not affected

#
  • Intersects: for a point query makeQuery takes the grid-aligned fast path (RecursivePrefixTreeStrategy.java:185-187): with pointsOnly a single TermQuery on the indexing cell (:218-229), else a visiting query that ORs over the cells it visits, so extra cells only add hits.
  • IsWithin: RPT passes no buffer (queryBuffer -1, :191-198), so the query walks the cells with no point filter (WithinPrefixTreeQuery.java:74).
  • Rectangle and circle documents (the area shapes tested): one that covers P is indexed under every cell it intersects, including all the touching ones, so it is still found. Polygons, lines and shape collections were not tested.
  • Shallow trees: the edge must exist at the tree's depth. With new S2PrefixTree(ctx, 1) (faces only) the equator is not an edge yet and (10, 0) and (0, 0) are found; from 2 levels on they are missed. (45, 20), on a face edge, is missed from 1 level on.
  • The two sides disagree: the index stores an edge point under one cell, the query follows every touching cell. The recommended fix makes the query side follow the index side, so it needs no reindexing; changing the index side instead is the other option.
Exposure and likelihood323 words
  • Who. Applications that use RecursivePrefixTreeStrategy, or CompositeSpatialStrategy (which pre-filters Contains with RPT's own Contains query, CompositeSpatialStrategy.java:139-142), over S2PrefixTree, and run Contains (alias "Covers") with a point as the query shape.
  • Opt-in. S2PrefixTree is @lucene.experimental and works only with a context whose shape factory is an S2ShapeFactory, i.e. the Geo3d context (constructor check, S2PrefixTree.java:83-85; CHANGES for LUCENE-8126: "It can only be used currently with Geo3D spatial context"). SpatialPrefixTreeFactory defaults to geohash for a geo context and selects S2 for prefixTree="s2"; Solr's RPT field types build their tree through that factory and parse Contains (code reading, not run). A GitHub code search found no use of S2PrefixTree in Elasticsearch or OpenSearch.
  • What is lost. Documents indexed as exactly the query point, when that point lies on an S2 cell edge that exists at the tree's depth: on the equator, and in the band around the equator on the face borders (longitudes ±45, ±135) and the face-centre meridians (0, ±90, 180), and (0,0), a common placeholder coordinate (all of these tried; multi-valued documents not tested). Continuous coordinates rarely land exactly on an edge; round-number and placeholder data does. With CompositeSpatialStrategy, a point document and a rectangle around it, Contains(p) returns 1 of the 2 true matches.
  • Silent, deterministic, false negatives only. No exception, the same with assertions off, per document, so at any index size. In 600 random Contains(point) queries (300 per tree, 2 trees, 400 random documents per tree), the stock hits were always a subset of the fixed hits.
  • How likely. Contains(point) against point data is an equality test that users would usually write as Intersects; the realistic case is a mixed-shape field asked "which shapes cover this location" when the location equals a stored point on a cell edge. No prior report was found in the recorded searches, although the code dates from 7.3.0 (2018); the registry rates the likelihood rare and the priority low.

Why it is a bug, not intended

#
  • Contains is documented as OGC "Covers", Contains.evaluate(p, p) is true, and RPT has an explicit Contains branch (LUCENE-4645).
  • The tree disagrees with itself: indexing stores a point in one cell per level, the query follows every touching cell. Other trees special-case points.
  • Upstream's random RPT test fails on any missed Contains match, but runs only quad and geohash trees.
The full argument289 words
  • Contract. SpatialOperation.Contains: "Meets the 'Covers' OGC definition (boundary-neutral)", evaluate = indexedShape.relate(queryShape) == CONTAINS || indexedShape.equals(queryShape) (SpatialOperation.java:75-87). ContainsPrefixTreeQuery: "Finds docs where its indexed shape CONTAINS the query shape. For use on RecursivePrefixTreeStrategy". RecursivePrefixTreeStrategy.makeQuery has an explicit Contains branch and throws UnsupportedSpatialOperation only for other operations (:199-203). CHANGES: "LUCENE-4645: Added support for the 'Contains' spatial predicate for RecursivePrefixTreeStrategy".
  • Approximation may only add matches. SpatialArgs: the error "effectively inflates the size of the shape but should not shrink it", and it is 0 for a point.
  • Upstream tests assert this for the other trees. TestRandomSpatialOpFuzzyPrefixTree.testContains ensures "true-positive matches (if the predicate on the raw shapes match then the search should find those same matches)", sometimes queries with "an existing indexed shape" (when it is a point or a rectangle), and uses power-of-two boundaries for "the prospect of edge conditions we want to test"; it runs only the quad and geohash trees. The only S2 RPT test, TestGeo3dRpt, runs only Intersects.
  • The tree disagrees with itself. Its index side stores a point in one cell per level; its query side follows every touching cell. In LUCENE-8126 (#9174) the tree's author wrote that S2 "Cells at the same level are disjoint" (in a comment about leaf pruning, not about queries). The legacy trees make the query side follow the index side for points (LegacyCell.java:134-143).
  • History. The introducing commit added the S2 cell class without the point case and tested S2 with Intersects only; no review or JIRA comment discusses Contains or edge points.
  • Precedent. LUCENE-4770 (#5835): a false negative from an index-side versus query-side cell mismatch in the legacy trees' Intersects (TermQueryPrefixTreeStrategy over indexed non-point shapes), fixed as a bug in 4.2.
The devil's-advocate check225 words

The strongest case for "works as designed" (the reading-only cross-model reviews rated it moderate; one of them, the refute lens, returned "not real" at low confidence for a procedural reason, as it could not run the repro, while its static analysis agreed on the root cause): PrefixTreeStrategy's class javadoc, which RPT inherits, says "Only SpatialOperation#Intersects is supported" (PrefixTreeStrategy.java:52-53); S2 cells are closed, so a point on an edge really does touch several cells, and Cell#getNextLevelCells only promises the cells "optionally filtered by shapeFilter"; and S2PrefixTree, RPT and ContainsPrefixTreeQuery are all @lucene.experimental.

The answer: the "Only Intersects" sentence was written on 2012-09-24 (84c5a4addeb), six months before LUCENE-4645 added Contains to RPT (8b573c413d4, 2013-04-03), and makeQuery, the ContainsPrefixTreeQuery javadoc and the CompositeSpatialStrategy javadoc ("All predicates are supported except for the BBox* ones, and Disjoint") all say Contains works. Closed cells would justify "several touching cells" only if the index side did the same, and it does not. @lucene.experimental is about API stability, not missing results. A maintainer could still prefer an index-side fix, a Contains-only fix or a documentation change. Verdict: not intended (the intended-behaviour devil's advocate, high confidence, and the adjudication). Expect the "Only Intersects" sentence to be quoted back; answer with LUCENE-4645 and the dates, and consider fixing that sentence in the same patch.

Suggested fix

#

Recommended Point case in S2PrefixTreeCell.getNextLevelCells (one method, no reindexing)

Give S2PrefixTreeCell.getNextLevelCells a point case that returns the one child the point is indexed under (the same S2CellId.fromLatLng cell as indexing), as LegacyCell does for the geohash and quad trees. One method, no reindexing. The repro and the whole spatial-extras test suite pass with it.

   @Override
   public CellIterator getNextLevelCells(Shape shapeFilter) {
+    if (shapeFilter instanceof Point point) {
+      // A point gets the one child cell it is indexed under (see S2PrefixTree.getTreeCellIterator),
+      // not every child that touches it: on a cell edge 2 to 4 children touch the point.
+      int childLevel = cellId == null ? 0 : cellId.level() + tree.arity;
+      S2CellId child =
+          S2CellId.fromLatLng(S2LatLng.fromDegrees(point.getY(), point.getX())).parent(childLevel);
+      S2PrefixTreeCell cell = new S2PrefixTreeCell(tree, child);
+      cell.shapeRel = SpatialRelation.CONTAINS;
+      return new SingletonCellIterator(cell);
+    }
     S2CellId[] children;

Point case in S2PrefixTreeCell.getNextLevelCells (one method, no reindexing) (validated by the checks) (recommended)

#

For a point filter, return a SingletonCellIterator of the child cell S2CellId.fromLatLng(point).parent(childLevel) with shapeRel CONTAINS: the cell the index side uses, and the pattern of LegacyCell. This is the finder's fix rewritten with imports instead of fully qualified names and with a comment; the logic is the same (+12 lines). It changes every S2 traversal that filters by a point, not only Contains (see the trade-offs); faceting with a point shape was not tested.

   @Override
   public CellIterator getNextLevelCells(Shape shapeFilter) {
+    if (shapeFilter instanceof Point point) {
+      // A point gets the one child cell it is indexed under (see S2PrefixTree.getTreeCellIterator),
+      // not every child that touches it: on a cell edge 2 to 4 children touch the point.
+      int childLevel = cellId == null ? 0 : cellId.level() + tree.arity;
+      S2CellId child =
+          S2CellId.fromLatLng(S2LatLng.fromDegrees(point.getY(), point.getX())).parent(childLevel);
+      S2PrefixTreeCell cell = new S2PrefixTreeCell(tree, child);
+      cell.shapeRel = SpatialRelation.CONTAINS;
+      return new SingletonCellIterator(cell);
+    }
     S2CellId[] children;

Trade-offs

  • No reindexing, no format change: the index side already writes the single fromLatLng path.
  • The other point callers take the single path too: the visiting queries (AbstractVisitingPrefixTreeQuery.java:245), i.e. RPT's Intersects without pointsOnly, the Intersects pre-filter of CompositeSpatialStrategy and PrefixTreeFacetCounter with a point shape. They then visit 1 cell per level instead of 2 to 4. An area document that covers the point is still indexed under that cell: in the probe the Intersects answers did not change. The facet counter with a point shape was not probed. Indexing never passes a point, and IsWithin passes no filter.
  • Tests: the upstream tests never ran Contains on S2, so their passing shows only that nothing else broke; add the repro (or an S2 grid in a Contains test) with the fix.
  • Javadoc: consider fixing PrefixTreeStrategy's stale "Only SpatialOperation#Intersects is supported" sentence in the same patch.
  • Valid depths assumed: like the index side, the point case computes parent(childLevel) and assumes a depth S2 supports; S2PrefixTree does not check maxLevels against getMaxLevels(arity) (the base constructor only asserts it is positive, SpatialPrefixTree.java:38-42). This predates the patch.

Point case in ContainsPrefixTreeQuery (not run)

#

For a point query, descend only the cells of getTreeCellIterator.

Trade-offs

Fixes Contains for any tree, but changes a query shared by all trees to work around one tree's cell iterator, and leaves the S2 Intersects traversal visiting extra cells.

Index a point under every cell it touches (not run)

#

Make the index side match the query side instead.

Trade-offs

Gives the index side closed-cell semantics, but needs reindexing and writes up to 4x the terms for edge points. The pointsOnly Intersects fast path would still work: it looks up the single getTreeCellIterator cell (RecursivePrefixTreeStrategy.java:218-229), which stays among the indexed terms.

Workaround for users today: query Intersects(P) instead of Contains(P) for a point (not a fix) (validated by the checks)

#

In the OGC sense "covers P" and "intersects P" are the same predicate for a point: a shape covers a point exactly when the point lies in the closed shape.

Trade-offs

Only for point query shapes; checked on the probe's shapes only.

What the checks validated

In the scope probe, with point, rectangle and circle documents, the two predicates had identical sets of true document-query pairs in all 8 configurations, and stock Intersects missed none of them.

Downstream note

#

Downstream engines that expose the S2 tree with Contains (Solr can select it with prefixTree="s2", by code reading) inherit the miss; it only ever drops matches.

How it was found

#

A randomized differential test compared RecursivePrefixTreeStrategy's hits with the exact spatial predicate over random points, rectangles and circles, and, among other findings, flagged Contains on the point (160, 0) with the S2 tree only. Probes then showed that the tested points exactly on S2 cell edges miss while nearby off-edge points are found; reading getNextLevelCells gave the cause.

The method in full187 words

Method: a randomized differential test (non-formal tier; the finder tagged it semi-formal) in a hunt unit on spatial-extras.

  • The harness indexed random rectangles, circles and points snapped to a 5- or 10-degree grid (150 documents and 60 queries in each of two S2 configurations) and reported every document that SpatialOperation.evaluate says should match but the query missed. Among its findings it flagged Contains, indexed Point(160, 0), query the same point, on S2PrefixTree only; the same run also reported other S2 Within and area-shape Contains misses, which are not part of this report.
  • A point probe then showed that S2 Contains misses the tested points on S2 cell edges ((160,0), (10,0), (45,20)), while off-edge points and the geohash and quad trees find them; the finder found the cause by reading S2PrefixTreeCell.getNextLevelCells and confirmed it with a public-API JUnit on the stock main jar.
  • It was then checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history, prior-report and security follow-up, and an audit. Found 2026-10-26 on main ea57360912ed; re-checked on a9779ef3c193.

LFV-371, snapshot of 2026-10-29

Registry title
S2PrefixTree: a Contains query whose shape is a point P misses a document indexed with that same point P when P lies on an S2 cell edge (the equator, an S2 face edge, (0,0)), because the query side follows every child cell that touches P while indexing puts P in one cell per level
Area
spatial-extras / prefix trees (S2PrefixTree and S2PrefixTreeCell under RecursivePrefixTreeStrategy; Contains through ContainsPrefixTreeQuery)
Priority
Low, rank 352: The experimental S2 tree silently misses a point that lies exactly on a cell edge, and only for Contains(point) queries.
Impact class
silent wrong results
Impact note
Applications that use RecursivePrefixTreeStrategy, or CompositeSpatialStrategy (which pre-filters with it), over the @lucene.experimental S2PrefixTree, which works only with the Geo3d spatial context (Solr's RPT field types can select it with prefixTree="s2", by code reading), and run a Contains query whose shape is a point silently lose every document indexed as exactly that point when the point lies on an S2 cell edge, such as any point on the equator, (45,20) on a face edge, (90,10) on a face-centre meridian or the common placeholder (0,0), at any index size and with every arity, depth, planet model, pointsOnly and pruneLeafyBranches setting tried; released since 7.3.0; false negatives only, while Intersects, IsWithin and indexed area shapes that cover the point are unaffected.
Summary
You index a document with point P through RecursivePrefixTreeStrategy over S2PrefixTree in the Geo3d spatial context and search with SpatialOperation.Contains and the same point P, expecting the document, because Contains is documented as the OGC 'Covers' predicate and its evaluate(P, P) is true, RecursivePrefixTreeStrategy builds a ContainsPrefixTreeQuery for it, a point query is resolved at full precision, and the geohash and quad trees do return the document. When P lies exactly on an S2 cell edge, for example Point(10, 0) on the equator, Contains finds 0 documents while Intersects finds 1. Indexing puts P in one cell per level (S2PrefixTree.getTreeCellIterator, from S2CellId.fromLatLng), but at query time S2PrefixTreeCell.getNextLevelCells has no point case and returns every child cell that touches P (2 on an edge, 4 at (0,0)), and ContainsPrefixTreeQuery requires the document to be in all of them.
