A negative cache limit makes grouped search silently return groups with no hits

GroupingSearch.setCaching(-1, true), for example meant as "no limit", is accepted, caches nothing and still reports the cache as complete, so the grouped search returns its 3 groups with 0 hits and totalHitCount 0 instead of 20, with no error. Silent since 9.8.0; 5.0.0 to 9.7.0 threw at replay.

The bug in 30 seconds

#

With caching on, a grouped search keeps the first pass's hits in a CachingCollector and replays them into the second pass instead of running the query again. The cache has a size limit, and isCached() says whether it kept every hit. A negative limit keeps nothing, yet isCached() still says yes.

  1. Index 20 documents that all match body:match, by 3 authors (7, 7 and 6 documents). Group them by author with GroupingSearch, no caching: totalHitCount 20, 3 groups with 7, 7 and 6 hits.
  2. Turn on first-pass caching with setCaching(-1, true), for example meaning "no limit". You expect an IllegalArgumentException, or the same 20 hits: the javadoc says a cache over its limit is purged and not used, so the query is run again.
  3. You get the same 3 groups with 0 hits each and totalHitCount 0, and no error, with assertions on or off. setCachingInMB(-1.0, true) does the same, and a CachingCollector created with limit -1 reports isCached() true but replays 0 of 20 documents.
  4. Why: -1 is the cache's own "already purged" marker. With it, no segment is cached, so the only code that would clear the "cached" flag never runs. The flag starts true, so the second pass replays an empty cache instead of re-running the query.
  5. A limit of 0 works: the cache overflows at the first hit and the query is re-run. From 5.0.0 to 9.7.0 a negative limit threw an exception at replay; 9.8.0 made it silent.

Who is affected

#

Only applications that turn on first-pass caching (GroupingSearch.setCaching or setCachingInMB, or CachingCollector / CachingCollectorManager directly: experimental, off by default) with a negative limit, such as -1 meant as "no limit". Then every hit is lost at any index size (in GroupingSearch: field or function grouping, once a group matches). Limits of 0 or more do not trigger it.

Mechanism, terms and numbers631 words

GroupingSearch can cache the hits of its first pass in a CachingCollector and replay them into the second pass instead of running the query again. The caller gives the cache a size limit, and isCached() tells whether the cache kept every hit; if not, the query is re-run. A negative limit, for example setCaching(-1, true) meant as "no limit" or a computed RAM budget that went negative, is accepted without a check, but -1 is also the collector's own internal "purged" marker: no segment gets a caching collector, nothing is cached, and the flag that isCached() returns, which starts true and is cleared only by a caching segment collector, stays true. The second pass replays an empty cache: on 20 matching documents the grouped search returns its 3 groups with 0 hits each and totalHitCount 0, with no error, with assertions on or off. The same goes for setCachingInMB(-1.0, true), CachingCollector.create(.., -1) and the new CachingCollectorManager; through GroupingSearch it takes field or function grouping and a query that finds at least one group. Limits of 0 or more do not trigger it. The defect dates from LUCENE-5527 (5.0.0); until 9.7.0 it threw at replay, and #12380 (9.8.0) made it silent. Rejecting negative limits with an IllegalArgumentException turns the silent loss into an immediate error: this doc's test, the finder's test, the caching tests of the core module and every upstream grouping test pass with it.

Terms

#
  • Two-pass grouping: GroupingSearch first finds the top groups (first pass), then collects the top documents inside those groups (second pass). Each pass normally runs the query.
  • First-pass cache: with setCaching(maxDocsToCache, cacheScores) or setCachingInMB(maxMB, cacheScores), the first pass goes through a CachingCollector (since #16247 one per slice, through CachingCollectorManager) that records the matching doc ids per segment. If the cache stayed within its limit, isCached() is true and the second pass is fed by replay(); otherwise the cache is purged and the query is run again.

The bug

#
  1. The cache flag starts true (CachingCollector.java:337). Only a caching segment collector clears it, when a hit would go over the limit (:178-182, :189-199). Its finish() then sets the collector's remaining limit to -1, the internal "purged" state, so later segments are not cached (:92-96, :214-221).
  2. getLeafCollector creates a caching segment collector, and records the segment, only when the limit is >= 0 (:79-90); for -1 it hands back the wrapped collector untouched.
  3. Nothing checks the sign of a caller's limit: create(.., int) and create(.., double) (:307-330; -1.0 MB becomes -262144 documents, or -131072 when scores are cached, :312), the CachingCollectorManager constructor (CachingCollectorManager.java:73-75, only "exactly one limit") and the GroupingSearch setters (GroupingSearch.java:250-272).
  4. So a caller's -1 starts in the purged state with the flag still true. No segment is cached and nothing can clear the flag: isCached() is true, and replay() (:106-118) loops over an empty segment list and returns normally. GroupingSearch replays whenever isCached() is true (GroupingSearch.java:208-209).

Exposure and likelihood264 words
  • Who is exposed. Code that enables first-pass caching with a negative limit. Caching is off by default (both limits start null, GroupingSearch.java:58-59), and all three classes are @lucene.experimental. Through GroupingSearch only field or function grouping is affected: the cache is built only in groupByFieldOrFunction (:128-137, 167-176); doc-block grouping does not use the cache limits.
  • How a negative limit gets there. Most plausibly -1 meant as "no limit": IndexWriterConfig uses -1 (DISABLE_AUTO_FLUSH) as the "off" value of its RAM-MB and document-count flush limits. Or a computed budget (for example "free heap minus a reserve") that went negative. 0, NaN and tiny negative MB values (above about -3.8e-6) truncate to 0 and work. A limit of 0 or more cannot trigger it: the effective document limit then stays >= 0 (CachingCollector.java:312); tested were 0, 1000, Integer.MAX_VALUE, 1.0 MB and 4.0 MB.
  • Effect. Every second-pass hit is lost: groups without documents, totalHitCount and totalGroupedHitCount 0. Nothing is added; the top groups themselves are right. No exception since 9.8.0, with assertions on or off. It needs a first pass that finds at least one group: a query that matches nothing returns its (correct) empty result before the replay decision (GroupingSearch.java:193-195).
  • Scale. None needed: 20 documents in one segment; an independent repro used 21 documents in 3 segments.
  • How likely. Low. A negative limit is a mistake, the documented searches found no report of either form, and Solr's grouping, the one downstream caller the checks read, only creates the cache when its computed limit is > 0.

Why it is a bug, not intended

#
  • CachingCollector javadoc: if isCached() is true, "you can use replay", else re-run the search. Here it is true, and the replay is empty.
  • GroupingSearch.setCaching: an over-limit cache "is purged and not used in the second pass search". A limit of 0 does that; -1 does not.
  • No javadoc or test gives negative limits a meaning; -1 is an internal marker.
The full argument300 words
  • Class contract (CachingCollector.java:25-30): "Once the collection is done, call isCached. If this returns true, you can use replay(Collector) against a new collector. If it returns false, this means too much RAM was required and you must instead re-run the original search." isCached() (:340): "Return true is this collector is able to replay collection." replay() (:349-350): "@throws IllegalStateException if this collector is not cached (i.e., if the RAM limits were too low for the number of documents + scores to cache)."
  • Limit contract. create(..) (:304-305, :323-324): "If the collector exceeds the threshold, no documents and scores are cached." GroupingSearch.setCaching / setCachingInMB (GroupingSearch.java:241-244, 258-261): "If the cache grows beyond the specified limit, then the cache is purged and not used in the second pass search." CachingCollectorManager's example re-runs the query when isCached() is false.
  • Tests. No test uses a negative limit. TestCachingCollectorManager expects a limit of 0 to give isCached() false and replay to throw IllegalStateException, and already expects IllegalArgumentException for a wrong combination of limits.
  • History. The >= 0 gate, the -1 marker and the cached = true start came with LUCENE-5527 (2014), whose discussion never mentions the limits. #12380 (2023) made the failure silent as a side effect of an unrelated refactoring; no review comment mentions CachingCollector. #16247 (2026) added the manager's "exactly one limit" check without the sign.
  • Maintainers prefer a loud failure here. In LUCENE-4372 (#5438, open since 2012) the worry was a too-small limit silently dropping hits; it was settled because replay() throws: "I don't have any concerns if you are gonna get an exception." A negative limit gets around exactly that exception. Nearby APIs validate similar values (TopScoreDocCollectorManager: "numHits must be > 0"; PhraseQuery: "Slop must be >= 0").
The devil's-advocate check173 words

The strongest case for "works as designed" (the cross-model reviews rated it moderate): a maximum document count or RAM size has an implicit non-negative domain, so -1 is invalid input; the classes are @lucene.experimental; disableCaching() exists for "no cache"; Solr guards its own call with > 0; negative limits never worked (they threw from 5.0.0 to 9.7.0) and no report of it was found.

Why it fails: an implicit domain the API does not enforce is what argument validation is for. Nothing documents a range or a meaning for negative values, the setters accept them silently, and the result breaks the class's own contract (isCached() true means the replay is usable) with silently wrong results instead of the exception the maintainers relied on in #5438. Verdict: not intended; the remaining doubt is about impact and wording, so frame the issue as missing argument validation. What the case does get right: rejecting negative limits changes behaviour for the few such calls that return correct results today (see the fix trade-offs).

Suggested fix

#

Recommended Reject negative (and NaN) limits, also eagerly in the GroupingSearch setters

Reject a negative (or NaN) limit with an IllegalArgumentException in CachingCollector.create, the CachingCollectorManager constructor and the two GroupingSearch setters (+23 lines, plus regression checks in 3 test classes). This doc's test passes, and so do the core caching tests and every upstream grouping test, with assertions on and off.

// CachingCollector.create(Collector, boolean, int); likewise CachingCollectorManager, GroupingSearch.setCaching
if (maxDocsToCache < 0) {
  throw new IllegalArgumentException("maxDocsToCache must be >= 0, got " + maxDocsToCache);
}
// CachingCollector.create(Collector, boolean, double); likewise CachingCollectorManager; setCachingInMB checks maxCacheRAMMB
if (maxRAMMB >= 0 == false) { // also rejects NaN
  throw new IllegalArgumentException("maxRAMMB must be >= 0, got " + maxRAMMB);
}
All options and trade-offs4 options · 780 words

Three shapes were run on main. The recommended one reports the mistake where it is made; the core-only shape is the finder's patch; the alternative keeps today's API and makes a negative limit behave like 0.

Reject negative (and NaN) limits, also eagerly in the GroupingSearch setters (validated by the checks) (recommended)

#

fix-reject-negative.diff (+23 lines in 3 files): the two CachingCollector.create factories, the CachingCollectorManager constructor and GroupingSearch.setCaching / setCachingInMB throw IllegalArgumentException("... must be >= 0, got ..."), with @throws lines in their javadoc. fix-reject-negative-tests.diff (+36 lines) adds the checks to TestCachingCollector, TestCachingCollectorManager.testConstructor and TestGroupingSearch.

  throw new IllegalArgumentException("maxDocsToCache must be >= 0, got " + maxDocsToCache);
}
// CachingCollector.create(Collector, boolean, double); likewise CachingCollectorManager; setCachingInMB checks maxCacheRAMMB
if (maxRAMMB >= 0 == false) { // also rejects NaN
  throw new IllegalArgumentException("maxRAMMB must be >= 0, got " + maxRAMMB);

Trade-offs

  • A call with a negative limit now throws: a behaviour change, not only a bug fix. Most such calls give wrong results today (or threw at replay before 9.8.0), but some give correct results and would now fail too: a grouped search whose first pass finds no group returns before the replay (GroupingSearch.java:193-195), and a direct CachingCollector user that never calls isCached() / replay() gets the wrapped collection only.
  • NaN, which truncates to 0 and works by accident today, now throws; check maxRAMMB < 0 instead to keep accepting it.
  • With the setter checks the error comes from setCaching itself; without them (next option) it comes from GroupingSearch.search. Code that sets -1 and expects only the search to fail sees it earlier: the independent reproducer's 2 GroupingSearch tests call the setter outside their try and so fail with the rejection's IllegalArgumentException, an outcome their oracle accepts only inside the try.
  • Argument checks only, outside the collection loop: no performance effect; no benchmark was run. A PR would add a CHANGES entry.

What the checks validated

  • Gradle on main, assertions on and off: TestCachingCollector* in core (2 classes, 9 tests) and the whole grouping suite (14 upstream classes, 57 tests) pass, and so do this doc's test (4 of 4), the finder's (5 of 5) and the independent reproducer's manager test (3 of 3). The only 2 failures are that reproducer's 2 GroupingSearch tests, which get the setter's new exception outside their try (see the trade-offs).
  • On stock main the same selection fails only in the repro classes (14 of 29 grouping tests), with assertions on and off.
  • :lucene:core:check -x test and :lucene:grouping:check -x test pass with the patch, its tests and this doc's test (google-java-format, ecj lint, forbidden APIs).

Treat a negative limit as "cache nothing": clear the flag in create() (validated by the checks)

#

fix-negative-as-purged.diff (+9/-3 lines in CachingCollector.create(Collector, boolean, int)): when the limit is negative, set cached = false on the new collector before returning it. A negative limit then behaves like 0: isCached() is false, GroupingSearch re-runs the query, and replay() throws IllegalStateException as documented.

CachingCollector collector =
    cacheScores
        ? new ScoreCachingCollector(other, maxDocsToCache)
        : new NoScoreCachingCollector(other, maxDocsToCache);
if (maxDocsToCache < 0) {
  // a negative limit leaves room for no document: cache nothing and report the cache as purged
  collector.cached = false;
}
return collector;

Trade-offs

No new exception, so it is the gentlest backport. But the mistake stays hidden: a caller who meant -1 as "no limit" silently gets no caching at all and runs every grouped query twice.

What the checks validated

Gradle on main, assertions on: core 8 of 8 and the whole grouping suite 75 of 75; every repro passes because the right result comes back.

Give -1 the meaning "no limit"

#

Read a negative limit as unbounded, like IndexWriterConfig's -1.

Trade-offs

A new feature rather than a fix, and it removes the RAM guard the limit exists for (4 or 8 bytes per hit, which the class javadoc warns can be "a very substantial amount of RAM"). Not run.

Downstream note

#

A product that lets its users set a grouping cache limit should reject negative values itself until Lucene does; the effect is lost results for that request, never extra documents.

How it was found

#

While modelling GroupingSearch's cache limit with an SMT solver, an AI tool wrote the limit's domain as >= 0. Reading the code for that precondition showed that -1 is the cache's own "purged" marker; a probe and then a public-API JUnit test on the stock main jars confirmed the empty replay.

The method in full132 words

Method: semi-formal (a model's precondition, then code reading and executed tests).

  • Hunt (2026-10-28). A hunt on another question (does GroupingSearch apply its cache limit per slice since #16247?) wrote an SMT model of the cache bound in which the limit's domain is D >= 0. Checking that precondition against the code showed that D = -1 is CachingCollector's own "invalidated" state and that no API rejects it.
  • The finder then ran a probe and a public-API JUnit test (TestCachingNegativeLimit, 4 of 5 fail on main, assertions on and off; the limit-0 control passes), a version-agnostic main() over 12 releases from 8.0.0 to 10.5.2 (silent from 9.8.0, an exception before), and the reject-negative fix.
  • Independent checks followed (see below); the history step extended the sweep to 135 releases from 3.2.0.

LFV-908, snapshot of 2026-10-29

Registry title
A negative cache limit (GroupingSearch.setCaching(-1, ..) / setCachingInMB(-1.0, ..), CachingCollector.create(.., -1), CachingCollectorManager) is accepted and caches nothing, yet isCached() stays true, so replay() delivers no documents and grouped search silently returns groups with no documents and totalHitCount 0 (since 9.8.0; from 5.0.0 to 9.7.0 replay threw instead)
Area
search / CachingCollector first-pass caching (CachingCollector, CachingCollectorManager) x grouping GroupingSearch two-pass caching
Priority
Low, rank 327: It silently drops every replayed hit, but only when someone passes a clearly invalid negative limit (such as -1 meant as 'no limit') to the opt-in, experimental first-pass caching, so it closes the accepted-degenerate-setting group after LFV-442.
Impact class
silent wrong results
Impact note
Hits only applications that opt into first-pass caching (GroupingSearch.setCaching/setCachingInMB, CachingCollector.create or the new CachingCollectorManager, all @lucene.experimental) and pass a clearly negative limit, for example -1 meant as 'no limit' or a computed budget that went negative; every non-negative limit works (0, and NaN or tiny MB values that round to 0, are purged correctly), no scale is needed, and since 9.8.0 the loss of all replayed hits is silent with -ea and -da, while 5.0.0 to 9.7.0 failed loudly at replay.
Summary
You enable caching for a grouped search (or wrap a first-pass collector in CachingCollector or CachingCollectorManager) with a negative limit, for example setCaching(-1, true) meant as 'no limit', and expect either an IllegalArgumentException or the documented fallback for a cache over its limit: isCached() false and the query re-run. Instead the limit is accepted and nothing is cached (a negative count is the collector's own internal 'purged' marker), but isCached() stays true, so replay() delivers none of the collected documents and GroupingSearch returns its top groups with no documents and totalHitCount 0 instead of 20 in the repro, with no error. From 5.0.0 to 9.7.0 the same input failed at replay with an AssertionError (-ea) or IndexOutOfBoundsException (-da).
