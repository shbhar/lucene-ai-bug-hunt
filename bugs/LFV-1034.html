ConcurrentQueryLoader's javadoc example uses QueryError and a (Monitor, List) constructor that no Lucene release has had

The only usage example in the ConcurrentQueryLoader javadoc declares List<QueryError> errors and calls new ConcurrentQueryLoader(monitor, errors), but no Lucene release has had that type or that constructor; both are Luwak leftovers from the 2019 port. Copied as shown, it does not compile on any release from 8.2.0 to 10.6.0.

The finding in 30 seconds

#

The example sits in a <pre><code> block of the class javadoc. Javadoc does not compile such blocks, so when the port removed the error list and QueryError, nothing failed, and Lucene's own test already used new ConcurrentQueryLoader(monitor).

Background

#
  1. The lucene-monitor module matches documents against a set of stored queries: you register MonitorQuery objects with a Monitor, then call match with documents.
  2. ConcurrentQueryLoader is a helper that registers many queries on several threads, for faster Monitor startup: you add() each query to it, and close() normally waits until all are registered.

The finding, step by step

#
  1. You load your stored queries into a Monitor at startup and copy the six-line "Use as follows:" example from the ConcurrentQueryLoader javadoc: List<QueryError> errors = new ArrayList<>();, then try (ConcurrentQueryLoader loader = new ConcurrentQueryLoader(monitor, errors)) { for (MonitorQuery mq : getQueries()) { loader.add(mq); } }.
  2. You expect it to compile and load the queries on several threads, with any load errors collected in errors.
  3. Instead javac stops at the first line: cannot find symbol: class QueryError. Give it a QueryError of your own and it stops at the second: no suitable constructor found for ConcurrentQueryLoader(Monitor,List<...>). The class has only 2 constructors, (Monitor) and (Monitor, int, int).
  4. Both lines are Luwak API that the 2019 port removed on purpose, and the example was not updated: today the loader keeps the IOExceptions that Monitor.register throws, and close() rethrows them as suppressed exceptions of one IOException. Written as new ConcurrentQueryLoader(monitor) without the list, it compiles; that is the form Lucene's own test uses.

Who is affected

#

Users of the lucene-monitor module who bulk-load stored queries with the opt-in ConcurrentQueryLoader and start from its only example: one compile error, every time, on 8.2.0 to 10.6.0 and main. Documentation only: nothing runs differently, and the constructor javadoc shows the working form.

Mechanism, terms and numbers548 words

ConcurrentQueryLoader (lucene-monitor) registers many queries with a Monitor on several threads, "to speed up startup times for a Monitor". Its class javadoc says "Use as follows:" and shows six lines: List<QueryError> errors = new ArrayList<>();, then try (ConcurrentQueryLoader loader = new ConcurrentQueryLoader(monitor, errors)) { for (MonitorQuery mq : getQueries()) { loader.add(mq); } }. Lucene has no QueryError type, and the class has only the constructors (Monitor) and (Monitor, int, int). Copied into a project with monitor and getQueries() supplied, the example fails with cannot find symbol: class QueryError; with QueryError replaced by a real type, javac reports no suitable constructor found for ConcurrentQueryLoader(Monitor,List<...>). Load errors are not collected in a caller's list either: the loader keeps the IOExceptions that Monitor.register throws in its threads, and close() normally rethrows them as suppressed exceptions of one IOException (unchecked exceptions are not collected). The two lines are the API of Luwak, the project the module was ported from; a commit on the port branch removed QueryError and the list constructors in April 2019 and left the example as it was. Written as new ConcurrentQueryLoader(monitor) without the list, the example compiles, and that is the form Lucene's own TestConcurrentQueryLoader uses. It has been broken in every release that has the module, 8.2.0 to 10.6.0, and on main. Nothing in Lucene behaves wrongly; only the example is stale.

The real API

#
  • Constructors: ConcurrentQueryLoader(Monitor monitor) (line 70), which uses one thread per available processor and a queue of DEFAULT_QUEUE_SIZE = 2000 (lines 63, 71), and ConcurrentQueryLoader(Monitor monitor, int threads, int queueSize) (line 81). Nothing else.
  • Errors: a private List<IOException> errors (line 61). A worker adds an IOException thrown by monitor.register(...) (lines 141, 144-145); close() normally waits for the workers (if the closing thread is interrupted, it stops waiting, lines 110-114) and then throws one new IOException with every collected one as a suppressed exception (lines 115-118). Only IOExceptions are collected: an unchecked exception from register ends its worker and close() does not report it.
  • On main, QueryError occurs in lucene/ only on line 43 and in an unrelated test method name (TestHighlightingMatcher.testQueryErrors); no commit on any ref of the Lucene history ever added such a class (only the never-merged port PR's branch, in the author's fork, had one). A bytecode scan of every build with the class (8.2.0 to 10.5.2, and main) finds no QueryError and only the two constructors.

Why nothing caught it

#

Javadoc does not compile <pre> blocks, and the example has no {@link} that javadoc would check. Lucene's only test of the class, TestConcurrentQueryLoader.testLoading, uses new ConcurrentQueryLoader(monitor) and loads 200 queries (2000 nightly).

Not claimed

#

Any runtime defect; the free example names monitor and getQueries() (normal for a fragment). Side observation: line 51, "The Monitor's MonitorQueryParser must be thread-safe for this to work correctly", names a MonitorQueryParser type that Lucene does not have either (a Luwak interface); a fix may reword it.

Exposure and likelihood197 words
  • Who. Readers of the ConcurrentQueryLoader class javadoc who copy its example. No query, document or index file reaches it.
  • Default vs opt-in. The loader is an opt-in helper; nothing in Lucene uses it by default. No configuration or special input is involved: the copied example always fails.
  • Scale. Every release that has the monitor module, 8.2.0 to 10.6.0 (the six lines are identical in all 49 release tags with the file and in the sources jars of the untagged 8.x releases), and main.
  • Effect. A compile error, not wrong behaviour. The example also implies that load errors land in a list the caller passes in; in the real API, IOExceptions thrown by Monitor.register in the loader threads come out of close() as suppressed exceptions of one IOException (on the normal path), so a reader may look for them in the wrong place.
  • Priority. Low; the same kind of defect as other stale javadoc examples (for example LFV-1029, LFV-984, LFV-1018 to LFV-1021, LFV-1026).
  • Separate bug in the same class. LFV-513 (workers exit at the first exception from Monitor.register; add() can then block forever and close() never reports) is a runtime defect with a different fix site.

Why it looks unintended

#
  • The block says "Use as follows:", is tagged as Java code, and nothing marks it as pseudo-code.
  • The 2019 port removed QueryError and the list constructors on purpose and left the example as it was; no record says it was kept on purpose.
  • Lucene's own test uses new ConcurrentQueryLoader(monitor).
The full argument198 words
  • Offered as working code. The example is the class's only usage sample, under "Use as follows:" and, since #15573 (2026-01-15), in <code class="language-java">.
  • History of the port. In Luwak, ConcurrentQueryLoader(Monitor monitor, List<QueryError> errors) and a QueryError class existed, with this same example. On the never-merged port branch (apache/lucene-solr#648) the "Initial commit" 266d913136e (2019-04-14) imported them, so the example matched. d58aa35f5b8 (2019-04-19, "Refactor the Monitor to take Query objects rather than string representations") deleted QueryError.java, replaced the constructors with (Monitor) and (Monitor, int, int), made close() throw the collected IOExceptions and removed the @param errors lines, but did not touch the example. On #9811 (LUCENE-8766) the author, Alan Woodward, wrote "I've spent a bit of time cleaning up the API and reducing its surface area" (2019-04-16).
  • The checked records do not accept the old form. package-info.java, MIGRATE.md and CHANGES.txt (the three places checked) say nothing about the loader's error API or about the example being illustrative.
  • Precedent. A stale class-javadoc example was fixed upstream as an ordinary doc fix before: issue #12666 (the Analyzer "Simple example") was closed by PR #12693, merged by msokolov on 2023-10-18. LUCENE-8488 (#9534) asks for compile-checked examples in general.
The devil's-advocate check183 words

Strongest case for "intended" or "noise": Lucene does not compile-check javadoc examples (#9534 is open), and in #15225 (2025-10-25) rmuir wrote that "Code examples need to be kept extremely minimal in the rare cases where it does make sense: the maintenance cost is very high and we don't have great validation for these." The block already leaves monitor and getQueries() undeclared, so QueryError could be read as a placeholder; the failure is loud, and the constructor javadoc and the test show the real usage. The cross-model reviews rated this "weak" as an intended-behaviour argument.

Why it fails: a reader supplies context such as monitor, but no context makes a constructor that does not exist compile; even with a QueryError of the reader's own, new ConcurrentQueryLoader(monitor, errors) fails. The block is prescriptive and is the class's only example, and the history shows the example left unchanged during a deliberate API change. rmuir's remark argues for few, minimal examples: it supports fixing or deleting this one, not keeping it broken. Every verifier and the adjudication called it real; the adjudication kept it at Low.
