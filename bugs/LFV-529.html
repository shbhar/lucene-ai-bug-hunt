TaxonomyFacetLabels returns ancestor labels a document was never given when its dimension is multi-valued

TaxonomyFacetLabels is documented as a way to read a document's facet labels back instead of storing them. For a dimension configured multi-valued and hierarchical, a document given only Date/2010/10 reads back as [Date/2010, Date/2010/10]: FacetsConfig indexes the ancestor on purpose for counting, and the javadoc never says so.

The finding in 30 seconds

#

Background: how a document's facet labels are stored

#
  1. The taxonomy gives every path a number, its ordinal: Date, Date/2010 and Date/2010/10 each get one.
  2. FacetsConfig.build stores the ordinals of a document's labels in a doc-values field; facet counting reads them.
  3. TaxonomyFacetLabels reads a document's stored ordinals and turns each one back into its path.

The finding, step by step

#
  1. Mark Date hierarchical and multi-valued (FacetsConfig.setHierarchical, setMultiValued) and index one document with new FacetField("Date", "2010", "10").
  2. Read its labels with TaxonomyFacetLabels, whose javadoc says it lets you "skip also adding stored fields for these values". You expect the one label you added, [Date/2010/10]; without setMultiValued that is what you get.
  3. Instead you get [Date/2010, Date/2010/10]. For multi-valued dimensions FacetsConfig stores every ancestor with the document so counts are right, and the reader turns every stored entry back into a label.
  4. With setRequireDimCount the bare dimension comes back too: a multi-valued Author given Author/Bob returns Author and Author/Bob. Counts, drill-down and the index are correct; nothing throws.

Who is affected

#

Applications that show per-hit facet labels from TaxonomyFacetLabels instead of stored fields, as its javadoc suggests, for a dimension set multi-valued plus hierarchical (categories, folder paths) or multi-valued plus requireDimCount. A path with d components below the dimension comes back as d labels. Default single-valued dimensions, counts and (default) drill-down are unaffected. Every release since 8.7.0.

Mechanism, terms and numbers480 words

TaxonomyFacetLabels (since 8.7.0) is documented as a way to "retrieve previously indexed facet labels, allowing you to skip also adding stored fields for these values". For a dimension configured multi-valued plus hierarchical, it also returns every ancestor of each added path (Date/2010/10 reads back as [Date/2010, Date/2010/10]), and for multi-valued plus requireDimCount the bare dimension (Author). FacetsConfig indexes these on purpose so that multi-valued counts are right, and after dedup they cannot be told apart from labels the user added, so this is a documentation/contract defect: the index and the counts are correct, and the fix is a javadoc note.

Terms

#
  • Hierarchical dimension (FacetsConfig.setHierarchical): paths may have more than one component below the dimension, such as Date/2010/10.
  • Multi-valued dimension (setMultiValued): "this dimension may have more than one value per document" (FacetsConfig.java:180). requireDimCount (setRequireDimCount): "you require accurate counts of the dimension" (:190-193). All three default to false (:113-124).

The bug

#
  1. For multiValued && (hierarchical || requireDimCount), FacetsConfig.processFacetFields adds the ordinal of every ancestor of each added path ("Add all parents too"), and removes the dimension's own ordinal unless requireDimCount is set (FacetsConfig.java:386-398). It then sorts and dedupes the ordinals (:403-415).
  2. This is intended: TaxonomyFacets.rollup adds child counts into parents only for hierarchical single-valued dims (TaxonomyFacets.java:272), because a document with Date/2010/10 and Date/2010/11 would be counted twice at Date/2010. Multi-valued dims store each ancestor once per document instead (LUCENE-5339, 4.7.0).
  3. FacetLabelReader.nextFacetLabel(docId) returns taxoReader.getPath(ord) for every stored ordinal, with no filter (TaxonomyFacetLabels.java:111-140). The reader receives no FacetsConfig (constructor :45-48), and the ordinals carry no record of who added them.
  4. So the ancestors come back as labels. The dim-filtered nextFacetLabel(docId, dim) keeps proper descendants of the dimension (:142-150, :207-213): it returns the ancestors too, but never the bare dimension.
  5. After dedup, a document given only Date/2010/10 and one given Date/2010 and Date/2010/10 store identical ordinals (executed), so no general reader-side filter can drop only the implicit ones. The dimension setting alone triggers it: the repro's document has one value.

Exposure and likelihood170 words
  • Who. Code that lists a hit's labels (breadcrumbs, tag lists) from this class on a dimension configured setMultiValued plus setHierarchical or plus setRequireDimCount. A document given only a deeper path, such as Date/2010/10, shows ancestors it was never given, deterministically, with assertions on and off; a document that also added those ancestors explicitly sees no difference.
  • Opt-in. Every trigger needs non-default FacetsConfig settings, and the class is @lucene.experimental. The default codec, IndexWriterConfig and taxonomy suffice.
  • Scale. Date/2010/10 returns 2 labels, Category/Electronics/Phones/Android 3; requireDimCount adds the dimension; shared ancestors of several values come back once.
  • Not affected. Counts; drill-down with the default DrillDownTermsIndexing.ALL (DrillDownQuery matches the ancestor in both configurations); the index; single-valued dims. With a non-default drill-down indexing that skips sub-paths, such as FULL_PATH_ONLY, a DrillDownQuery on a returned ancestor label matches nothing (executed). In the Lucene tree only tests use the class; GitHub code search of the default branches of Elasticsearch, OpenSearch and Solr found no use of TaxonomyFacetLabels, DirectoryTaxonomyReader or DirectoryTaxonomyWriter (2026-11-01).

Why it looks unintended

#
  • The javadoc offers the class to "skip also adding stored fields for these values", and stored fields return exactly what was added.
  • Upstream tests use only single-valued dims and expect exactly the added labels; flipping only setMultiValued changes the labels.
  • The ancestors are indexed on purpose and indistinguishable after dedup, so the defect is the missing documentation, not the code.
The full argument191 words
  • Contract. Class javadoc (TaxonomyFacetLabels.java:27-29). CHANGES 8.7.0: "LUCENE-9444: Add utility class to retrieve facet labels from the taxonomy index for a facet field so such fields do not also have to be redundantly stored". Issue #10484: "A facet field may be included in the list of fields whose values are to be returned for each hit"; a comment by mikemccand (2020-08-01): "We want to make it easy for users to get back their originally indexed facet labels."
  • Tests. TestTaxonomyFacetLabels.testBasic sets only setHierarchical and asserts exactly 10 labels for 5 documents with 2 each; TestTaxonomyFacetCounts.testRandom uses a plain FacetsConfig and expects exactly the added labels. No test, review comment or decision covers multi-valued hierarchical or requireDimCount dims.
  • Metamorphic. For one document, flipping only setMultiValued (documented as "may have more than one value per document") turns [Category/Electronics/Phones] into [Category/Electronics, Category/Electronics/Phones] (executed).
  • Through FacetField, the bare dimension is never a user label: new FacetField("Author") throws "path must have at least one element", so in a field built by FacetsConfig it comes only from requireDimCount. Code that bypasses FacetsConfig (TaxonomyWriter.addCategory(new FacetLabel("Author")) plus its own SortedNumericDocValuesField) can still index one on purpose.
The devil's-advocate check146 words

Strongest case for "works as designed": the javadoc says previously indexed, and the ancestors are indexed; the demo user guide says "Multi value support requires storing all parent category ordinals in the category list field for accurate counting"; the reader takes no FacetsConfig; ordinals carry no record of who added them; the class is @lucene.experimental.

Why it fails for the documentation: it defeats a code-bug framing, which is why this is classed as a documentation defect, but not the gap itself. The guide sentence is about counting, lives in the demo module, is not linked from TaxonomyFacetLabels and says nothing about the dimension ordinal; a user who picks the class over stored fields cannot learn that the labels differ from what they added. Cross-model reviews (OpenAI GPT-5.6) split the same way: not a code bug (refute lens), a real documentation defect (works-as-designed lens).

Suggested fix

#

Recommended A. Document the ancestor and dimension labels in the class javadoc

Document it: a TaxonomyFacetLabels javadoc note that multi-valued hierarchical (or requireDimCount) dimensions also return the ancestor labels, and the dimension, indexed for counting, indistinguishable from added ones; also fix the stale BinaryDocValues @param. Validated: format, lint and javadoc pass, TestTaxonomyFacetLabels passes.

All options and trade-offs3 options · 667 words

No general reader-side filter can remove only the implicit ancestors: after dedup they are indistinguishable from ancestors the user added, and the reader receives no FacetsConfig. An application that never adds ancestors explicitly can filter them itself, or keep stored fields for those dims.

Trade-offs

  • A behaviour change in an experimental API that someone might rely on (for example to list a document's dims); it fixes only the requireDimCount half.
  • It changes the generic meaning of a public reader and would also hide a bare dimension that code bypassing FacetsConfig indexed on purpose; passing the facet suite does not show it is compatible for such callers.

What the checks validated

On top of A: format, ECJ lint and javadoc pass; the whole :lucene:facet:test suite passes (306 tests, 7 skipped); the independent reproducer's requireDimCount test ([Color, Color/blue, Color/red] on stock main) passes, while its three ancestor tests and the minimal test still fail, as expected.

Not recommended: a leaf-only filter, or recording explicitly added ordinals

#

A leaf-only filter would silently drop ancestors the user added (indistinguishable after dedup). Recording which ordinals were added explicitly needs an index-format change and extra storage, out of proportion for an experimental utility. Workaround, not a Lucene fix: an application that never adds ancestors explicitly can apply the leaf-only filter itself.

Downstream note

#

Downstream code that shows these labels to users displays ancestors that a document given only a deeper path was never tagged with; an application that indexes untrusted, very deep paths into such a dimension should cap the depth, since a path with d components below the dimension reads back as d labels.

How it was found

#

Non-formal: model-based metamorphic testing of the facet API. One relation says the labels TaxonomyFacetLabels returns for a document equal the FacetField paths added to it; 400 random iterations (327,122 checks) reported 3,010 mismatches. Independent verifiers reproduced it with their own tests.

The method in full101 words
  • Method. A random model-based harness indexed random documents under random dimension configurations and checked the public facet API against a reference model written from the javadoc, independent of the implementation. Relation F7: the labels returned for a document equal the paths added to it. Run on main: 400 iterations, seed 2, 327,122 checks, 3,010 F7 mismatches (extra ancestor and dimension labels).
  • Verification. The finder's public-API JUnit, an independent reproducer (7 tests), cross-model reviews (OpenAI GPT-5.6, reading only), a devil's advocate with probes, an adjudication re-run and a follow-up with a release matrix; the minimal repro then cut it to one method.

Summary
You add FacetField("Author", "Bob") and FacetField("Publish Date", "2010", "10", "15") to a document and read its labels back with TaxonomyFacetLabels, whose javadoc offers it as a way to skip stored fields for these values, so you expect [Author/Bob, Publish Date/2010/10/15]; that is what you get when both dimensions are single-valued. With Publish Date configured multi-valued and hierarchical you get [Author/Bob, Publish Date/2010, Publish Date/2010/10, Publish Date/2010/10/15], and with Author configured multi-valued with requireDimCount you get [Author, Author/Bob, Publish Date/2010/10/15]. FacetsConfig deliberately indexes those ancestor (and dimension) ordinals so that multi-valued counts are right, and the reader turns every indexed ordinal back into a label; the javadoc never says so.
