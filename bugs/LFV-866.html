Word2VecSynonymFilter: maxSynonymsPerTerm = Integer.MAX_VALUE passes validation, then every in-model word throws

Word2VecSynonymFilterFactory accepts any positive maxSynonymsPerTerm, but the provider asks its HNSW search for maxSynonymsPerTerm + 1 hits, in int and never capped at the model size. At Integer.MAX_VALUE that wraps to -2,147,483,648, so every word with a vector throws, even in a 2-word model; huge values exhaust the heap.

The finding in 30 seconds

#

To find a word's k synonyms, the provider asks the HNSW search for k + 1 hits (the word is its own nearest hit). It adds the 1 in int, never caps it at the model size, and the search reserves queues for every hit up front. So Integer.MAX_VALUE wraps to a negative size; huge values exhaust the heap.

Background: how the word2vec synonym filter finds synonyms

#
  1. You give the filter a word2vec model: a list of words, each with a vector. For every token that is in the model, the filter adds the model's most similar words as synonyms at the same position.
  2. Two settings limit that: minAcceptedSimilarity (default 0.8), how similar a synonym must be, and maxSynonymsPerTerm (default 5), the most synonyms per token.
  3. The similar words come from an HNSW nearest-neighbour search over the model's vectors. The search keeps its candidates in two priority queues sized for the number of hits it is asked for.

The finding, step by step

#
  1. Build a CustomAnalyzer with the Word2VecSynonym filter over a 2-word model, alpha = (1, 0) and beta = (0.9, 0.1), and set maxSynonymsPerTerm to 2,147,483,647 (Integer.MAX_VALUE): "no count cap, the similarity threshold decides". The factory accepts it; it rejects only values <= 0.
  2. You expect alpha to analyse to [alpha, beta]: beta scores 0.9969 against alpha (the provider uses (1 + cosine) / 2, and the cosine is about 0.994), above the default threshold 0.8, and that is what the default maxSynonymsPerTerm of 5 gives.
  3. Instead the analyzer builds, and analysing alpha throws IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: -2147483648. To find k synonyms the provider searches for k + 1 hits (the word is its own nearest hit), and 2,147,483,647 + 1 wraps in an int to -2,147,483,648.
  4. The search reserves two queues of k + 1 entries before it starts, and nothing caps k + 1 at the model's 2 words. So values just below fail too: from 2,147,483,630 with the same exception, and from about 100 million at a 1 GiB heap with OutOfMemoryError.
  5. It fails at index and at query time, with assertions on and off, in every release that has the filter (9.7.0 to 10.6.0) and on main. Words without a vector, the default 5 and ordinary values never fail.

Who is affected

#

Applications that opt in to the experimental Word2VecSynonymFilter and set maxSynonymsPerTerm to Integer.MAX_VALUE (meant as "no cap") or to about 100 million or more (heap-dependent). Any model size, at index and at query time, from the first token that has a vector. The failure is loud: no wrong results, no index damage. The default 5 and ordinary values never fail.

Mechanism, terms and numbers670 words

Word2VecSynonymFilter (@lucene.experimental, since 9.7.0) adds, for every token that has a vector in a word2vec model, the model's most similar words as synonyms, at most maxSynonymsPerTerm of them (default 5) and only above minAcceptedSimilarity (default 0.8). Its factory rejects only maxSynonymsPerTerm <= 0, so Integer.MAX_VALUE, meant as "no count cap, let the threshold decide", builds an analyzer without complaint. On the first token that has a vector, Word2VecSynonymProvider.getSynonyms asks HnswGraphSearcher.search for maxSynonymsPerTerm + 1 hits (the query word is its own nearest hit). The sum is int arithmetic and is never capped at the model size, and the search allocates two queues of that many entries before it starts. At Integer.MAX_VALUE the + 1 wraps to -2,147,483,648 and the queue throws IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: -2147483648; values from 2,147,483,630 throw the same exception without overflowing, and values from about heap-bytes/16 (1e8 at a 1 GiB heap) throw OutOfMemoryError, even for a 2- or 3-word model. The failure is loud and immediate, with no wrong results. It is in every release with the filter, 9.7.0 to 10.6.0, and on main 645d4fe14a20. Capping the search size at the model size, computed in long, fixes it; validated with gradle on 645d4fe14a20.

The bug (main 645d4fe14a20)

#
  1. Validation. Word2VecSynonymFilterFactory reads the value with getInt(args, "maxSynonymsPerTerm", DEFAULT_MAX_SYNONYMS_PER_TERM) (Word2VecSynonymFilterFactory.java:53; the default is 5, :41) and rejects only <= 0: "maxSynonymsPerTerm must be a positive integer greater than 0. Found: ..." (:72-76). The factory is @lucene.experimental and registered under the SPI name Word2VecSynonym (:32-33, :39), so CustomAnalyzer and settings-driven analyzers reach it by name.
  2. Per token. Word2VecSynonymFilter.incrementToken calls getSynonyms(term, maxSynonymsPerTerm, minAcceptedSimilarity) for every token (Word2VecSynonymFilter.java:95-96).
  3. The search size. Only a term that has a vector searches (Word2VecSynonymProvider.java:78-79). Then HnswGraphSearcher.search(scorer, maxSynonymsPerTerm + 1, hnswGraph, null, Integer.MAX_VALUE) (:83-90), under the comment "The query vector is in the model. When looking for the top-k it's always the nearest neighbour of itself so, we look for the top-k+1" (:85-86). The + 1 (:87) is plain int addition (the shipped bytecode is iload_2, iconst_1, iadd), and nothing compares it with word2VecModel.size().
  4. Eager allocation. The static HnswGraphSearcher.search (HnswGraphSearcher.java:177-186) builds new TopKnnCollector(topK, visitedLimit, null) (:180) and new NeighborQueue(topK, true) (:183) before it searches; both create a TernaryLongHeap(topK) (TopKnnCollector.java:45, NeighborQueue.java:59-60).
  5. The heap. TernaryLongHeap throws IllegalArgumentException for a capacity < 1 or >= ArrayUtil.MAX_ARRAY_LENGTH ("Throw exception to prevent confusing OOME", TernaryLongHeap.java:57-63); otherwise it allocates new long[initialCapacity + 1] (:66-68). Two such queues cost about 16 bytes per unit of maxSynonymsPerTerm, whatever the model size.

Exposure and likelihood242 words
  • Who is hit. Users of the @lucene.experimental Word2VecSynonymFilter who configure maxSynonymsPerTerm as Integer.MAX_VALUE, the "no cap" value analysis-common itself uses as the default of CapitalizationFilter's maxWordCount and maxTokenLength (CapitalizationFilter.java:34-35), or as any value from about 100 million up (heap-dependent). The default 5 and ordinary values (the upstream tests use at most 10) never fail. There is no evidence that anyone configures it this way (no public report).
  • Where. Index time and query-parse time, on the first token that has a vector, whatever the model size. Analyzers built by SPI name (CustomAnalyzer, settings files) pass the value to the factory unchanged.
  • How it shows. An IllegalArgumentException that names an internal heap and a negative capacity rather than the setting, or an OutOfMemoryError; both only after the analyzer was built without complaint. No wrong results and nothing written to the index.
  • A cost even when it works. Below the failure range every in-model token still allocates two queues sized by the setting rather than by the model: 1e7 is about 160 MB per token (arithmetic); one token took 46 ms on a 3-word model (a single timing that includes building the analyzer). The fix removes that too.
  • How likely: rare (registry likelihood rare, priority low): only extremely large values trigger it (near Integer.MAX_VALUE, or from about 100 million up, heap-dependent), and it shows on first use. No public report since 9.7.0 (2023) in a bounded search.

Why it looks unintended

#
  • The factory checks this setting and accepts any value above 0; the javadoc calls it the "maximum number of result returned", nothing more.
  • Lucene caps requested counts at what exists: LeafReader.searchNearestVectors does k = Math.min(k, size) before sizing the same collector.
  • Upstream tests pass 10 for 4- and 8-word models; nobody discussed large values when the + 1 was added.
The full argument222 words
  • Contract. The factory states the accepted domain in its own check: "maxSynonymsPerTerm must be a positive integer greater than 0" (Word2VecSynonymFilterFactory.java:72-76); TestWord2VecSynonymFilterFactory asserts only the rejection of 0 and -1. The filter javadoc: "@param maxSynonymsPerTerm maximum number of result returned by the synonym search" (Word2VecSynonymFilter.java:58), a cap on results, with no upper bound. package-info.java, CHANGES.txt:3610 (GITHUB#12169, the only entry) and MIGRATE.md say nothing more.
  • A cap above the model size is an ordinary, tested input. TestWord2VecSynonymFilter passes 10 for an 8-word and a 4-word model (TestWord2VecSynonymFilter.java:85-97, :115-123).
  • Lucene caps requested counts, in the same kind of call. LeafReader.searchNearestVectors does k = Math.min(k, floatVectorValues.size()) before new TopKnnCollector(k, ...) (LeafReader.java:288, :332, :376); IndexSearcher caps numHits (IndexSearcher.java:597, :729). Where a setting drives an allocation, analysis code rejects too-large values when it is set: StandardTokenizer.setMaxTokenLength throws above MAX_TOKEN_LENGTH_LIMIT (StandardTokenizer.java:98-99).
  • History. The + 1 is in the first version (#12169, 1f4f2bf5095, 2023); the 38 comments, 33 review comments and 5 review summaries (15 reviews, 5 with a summary) of #12169 do not discuss an upper bound, large values or overflow.
  • Why the tests never hit it. The word2vec tests use limits of at most 10, and TestRandomChains draws random int constructor arguments from [-50, 50] only (TestRandomChains.java:176-179).
The devil's-advocate check276 words

The strongest "works as designed" case (the study's intended-behaviour checker, and the cross-model reviewer, which rated it "moderate"): the value is trusted configuration on an experimental filter; Integer.MAX_VALUE is not documented as an "unlimited" sentinel; maintainers have called a huge, eagerly allocated HNSW k a pattern to avoid (benwtrent on #11946: the queue "eagerly allocates a new long[heapSize]. This is VERY costly"; jpountz on #12679: k = Integer.MAX_VALUE "will not only run in O(maxDoc) time but also use O(maxDoc) memory. I don't think we should do this"); TestRandomChains bounds int arguments because the full range "could cause huge ram usage ... (e.g. allocate enormous arrays)"; and the failure is loud.

Why it fails: trust decides security, not validity (SECURITY.md:46: out-of-scope issues "are still valid bug reports and hardening suggestions"). A cap needs no sentinel: as a maximum, Integer.MAX_VALUE simply means no cap. The two maintainer remarks are about Lucene's own designs and about exactly the eager allocation the clamp removes; neither speaks to an accepted value overflowing into a negative capacity. The TestRandomChains TODO records a test gap (its neighbour TODO for char says "fix any filters that care to throw IAE instead"). And the error arrives at analysis time, after the analyzer was built, naming an internal heap. Verdict: not intended; the case reduces to severity, which is why the bug is Low priority.

Contested. An independent fact check by a reviewer from another model family (OpenAI GPT-5.6, reading only) judged it noise ("needs absurd parameters and then fails loudly"), at most low-priority hardening. The tie-breaker kept it: as a cap, Integer.MAX_VALUE is the plain "no cap" value, not an absurd one.

Suggested fix

#

Recommended Cap the HNSW search size at the model size, computed in long

Cap the search size at the model size and add the 1 in long: (int) Math.min(maxSynonymsPerTerm + 1L, word2VecModel.size()), a one-line change in Word2VecSynonymProvider. Validated with gradle: the repro passes with assertions on and off, the word2vec tests and the whole analysis-common test task pass, and so does check once the test's unused catch parameter is named _.

              (int) Math.min(maxSynonymsPerTerm + 1L, word2VecModel.size()),

One fix was built and validated; two alternatives were considered and not built.

Cap the HNSW search size at the model size, computed in long (validated by the checks) (recommended)

#

In Word2VecSynonymProvider.getSynonyms (Word2VecSynonymProvider.java:87), pass (int) Math.min(maxSynonymsPerTerm + 1L, word2VecModel.size()) instead of maxSynonymsPerTerm + 1. The search can never return more hits than the model has words, so output is unchanged whenever maxSynonymsPerTerm + 1 fits in the model, and above that the extra queue room could never be filled. It removes the overflow and the allocation sized by the setting. The same pattern as LeafReader.searchNearestVectors (k = Math.min(k, size)).

              // The query vector is in the model. When looking for the top-k
              // it's always the nearest neighbour of itself so, we look for the top-k+1
              // never more than the model holds (also avoids int overflow of the + 1)
              (int) Math.min(maxSynonymsPerTerm + 1L, word2VecModel.size()),

Trade-offs

  • Large models. With the clamp, Integer.MAX_VALUE means "every word above the threshold", so each in-model token of a large model searches for the whole model: two queues of model-size entries (about 16 bytes per word) and a walk over most of the graph (arithmetic, not executed). Correct, but slow for models with millions of words; it is the cost of the request itself, and the same as setting the value to the model size today.
  • The sibling bug LFV-862 (the provider can return k + 1 synonyms when the query word is missing from its own hits) is not fixed by this; its fix caps the result loop, a different line, and the two compose.

Reject too-large values in the factory, with a message that names the setting

#

Not built. Gives a configuration-time error instead of an analysis-time one.

Trade-offs

The factory constructor does not know the model size (the model is loaded later, in inform), so the bound would be a fixed constant such as ArrayUtil.MAX_ARRAY_LENGTH - 2: that removes only the IllegalArgumentException range, not the OutOfMemoryError one, and it does not protect code that builds Word2VecSynonymFilter or calls getSynonyms directly (neither validates the value). Rejecting values above the model size instead would turn a sensible "no cap" setting into an error. Possible as an addition to the clamp, not instead of it.

Grow the HNSW search queues lazily in core

#

Not built. Start the TopKnnCollector and NeighborQueue heaps small and let them grow.

Trade-offs

Would replace the up-front allocation sized by k with growth bounded by what the search actually collects, for every caller of HnswGraphSearcher.search (on a large graph the queues can still grow large), but would not fix the overflow at Integer.MAX_VALUE (the capacity is already negative when it arrives), and it touches the kNN hot path, so it needs benchmarks. Out of proportion for this bug.

Downstream note

#

How it was found

#

While building a check that compares the provider's HNSW synonyms with an exact cosine reference, the finder read getSynonyms and saw the + 1 with no cap. A boundary probe through the factory confirmed it (5 and 1,000,000 work; 2,147,483,646 and 2,147,483,647 throw), and a public-API JUnit failed on the stock main jars.

The method in full130 words

Method: non-formal (a hunt unit for the word2vec synonym provider, 2026-10-28, main a9779ef3c193).

  • Context. The unit built a translation-validation harness: the provider's HNSW-based synonyms against an exact cosine ranking over the same model.

LFV-866, snapshot of 2026-11-02

Registry title
Word2VecSynonymFilterFactory accepts any positive maxSynonymsPerTerm, but Word2VecSynonymProvider sizes its HNSW search as maxSynonymsPerTerm + 1 with no clamp to the model size, so very large values (Integer.MAX_VALUE, where the + 1 overflows) make every in-model token throw IllegalArgumentException or OutOfMemoryError
Area
analysis-common / synonym.word2vec (Word2VecSynonymProvider.getSynonyms search size; Word2VecSynonymFilterFactory validation)
Priority
Low, rank 769: Integer.MAX_VALUE as the 'no limit' maxSynonymsPerTerm makes the experimental opt-in Word2VecSynonymFilter fail loudly on the first in-model token, the same MAX_VALUE-as-limit loud boundary class as LFV-182.
Impact class
crash
Impact note
Only applications that opt in to the @lucene.experimental Word2VecSynonymFilter and set maxSynonymsPerTerm very large are hit (Integer.MAX_VALUE, for example meant as 'no count limit', or roughly heap-bytes/16 and up): the analyzer builds, then every analysis of a token that has a model vector, at index time or query-parse time, throws IllegalArgumentException (values near Integer.MAX_VALUE, from 2147483630 on the JVM measured) or OutOfMemoryError (measured from 1e8 at a 1 GiB heap, 1.5e8 at 2 GiB, 3e8 at 4 GiB, on a 3-term model); the failure is loud, not silent; every release since 9.7.0.
Summary
You configure Word2VecSynonymFilterFactory with maxSynonymsPerTerm=2147483647 (Integer.MAX_VALUE), which its validation accepts ('must be a positive integer greater than 0'), to keep every synonym above minAcceptedSimilarity, and you expect those synonyms or a rejection at configuration time. The analyzer builds, but Word2VecSynonymProvider.getSynonyms passes maxSynonymsPerTerm + 1 (int arithmetic) as topK to HnswGraphSearcher.search, which wraps to Integer.MIN_VALUE, so the first token with a model vector throws IllegalArgumentException 'initialCapacity must be > 0 and < 2147483630; got: -2147483648' from TernaryLongHeap (on 9.7.0 to 10.3.2: 'maxSize must be > 0 ...' from LongHeap). Because the search size is never clamped to the model size and the search allocates its queues of topK entries up front, values close to Integer.MAX_VALUE fail the same way and values from roughly heap-bytes/16 up (1e8 at a 1 GiB heap) throw OutOfMemoryError, even for a 3-term model.
