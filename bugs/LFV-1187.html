SegmentOrder: two concurrent reorder() calls on one shared instance can throw NullPointerException

Since 10.4.0, a numeric SegmentOrder from fromSort() sorts every reorder() call with one shared comparator whose cache is a plain HashMap. Two threads calling reorder() on the same instance at once can make a lookup return null, and reorder() throws NullPointerException (20 of 20 rounds in the repro on main).

The finding in 30 seconds

#

A numeric SegmentOrder keeps one hidden cache, shared by every reorder() call, with no lock.

Background: what SegmentOrder does

#
  1. A reader holds one leaf per index segment, and a search visits the leaves in order. A sorted search that can stop early does less work when the segment with the best values comes first.
  2. SegmentOrder.fromSort(sort).reorder(reader) (new in 10.4.0) returns a view of the same segments in that order: for a descending numeric sort, by each segment's max value; for an ascending one, by its min. The segments' own data is untouched.

The finding, step by step

#
  1. Index 1,000 one-document segments, each with a LongPoint f = 0 ... 999, and open one DirectoryReader. Build one SegmentOrder.fromSort(new Sort(new SortField("f", SortField.Type.LONG, true))) and keep it for every search, as you would keep a Sort.
  2. Two search threads call order.reorder(reader) at the same moment. You expect two views of the 1,000 segments in the order one thread gets: f = 999 first, f = 0 last.
  3. Instead at least one call throws NullPointerException: ... the return value of "java.util.Map.get(Object)" is null at SegmentOrder.java:141: 20 of 20 rounds with assertions on, 19 of 20 with them off.
  4. Why: every reorder() of that instance sorts with the same comparator, which caches each segment's max f in one plain HashMap (containsKey, put, get, no lock). For example, while one thread's put resizes the map, the other thread's get can miss an entry it has just added, and the null is unboxed to long.
  5. The map is written only for segments not cached yet, so it hits mostly the first concurrent searches on a newly opened or refreshed reader; after a lost race, a few later calls on that instance can fail too, even from one thread. A SegmentOrder per query, or one never used by two threads at once, never hits this race.

Who is affected

#

Applications on 10.4.0 to 10.6.0 or main that share one numeric SegmentOrder across concurrent search threads. Some searches fail with an exception, mostly the first ones on a new or refreshed reader; after a lost race a few later calls can fail too. No wrong results were seen. One instance per query avoids it; no outside caller is known.

Mechanism, terms and numbers623 words

SegmentOrder.fromSort(sort) (new in 10.4.0) returns a helper whose reorder(reader) gives a view of the reader with its segments ordered so that the best hits for the sort come first. For an INT, LONG, FLOAT or DOUBLE primary sort, numericSorter() builds one NumericFieldReaderContextComparator (SegmentOrder.java:91-92 at 5adff78bb168) and every reorder() hands that same instance to the view's constructor (:96-98), which sorts the leaves with it (BaseCompositeReader.java:76). The comparator caches each segment's sort value in a plain HashMap (:115) through containsKey, put and get with no lock, and unboxes the result (:138-141). When two threads call reorder() on the same instance and meet segments that are not cached yet, a get() can return null, and reorder() throws NullPointerException. The one-test repro fails through gradle on main in 20 of 20 iterations with assertions on and 19 of 20 with them off; building the comparator inside reorder() (+3/-2 lines) removes it. No wrong results, index damage or hang were seen. Opt-in helper, no known caller outside Lucene's own test; priority Low.

The bug

#
  1. fromSort with an INT, LONG, FLOAT or DOUBLE primary sort (or a SortedNumericSortField of one) returns numericSorter(...) (SegmentOrder.java:42-77). Other sort types return a no-op strategy (:79-85), which is not affected.
  2. numericSorter creates one NumericFieldReaderContextComparator outside reorder() (:91-92); every reorder() passes it to new BaseCompositeReader<>(leaves, comparator) (:95-98), whose constructor runs Arrays.sort with it on the calling thread (BaseCompositeReader.java:74-76).
  3. The comparator's getSortValue (:136-142) caches values in private final Map<Object, Long> cachedSortValues = new HashMap<>() (:115) keyed by the leaf's core cache key: if (containsKey(key) == false) put(key, loadSortValue(reader)); then return cachedSortValues.get(key); (:141), unboxed to long. No lock and no eviction.
  4. Two threads that fill one HashMap can lose or hide entries, or corrupt its structure (JDK 25 HashMap.java): an empty bucket is written with a plain store (tab[i] = newNode(...), :638), so one of two concurrent puts into it can be lost; and resize() publishes the new, empty table (table = newTab, :712) before it moves the old buckets (:714-717), so a get() meanwhile can miss a key just put. Either way :141 unboxes null.
  5. Every thread computes the same value for a given segment (loadSortValue, :144-172, reads that segment's own doc-values skipper or point min/max), so a lost or hidden entry shows up as the NullPointerException: that is the failure in all but one of the failed iterations recorded for this bug. The race can also corrupt the map's internal structure. In the fact check's re-run of the gradle command (assertions on), 1 of 20 failures was an AssertionError from HashMap's own tree-bin check (HashMap.java:2009, under the put at SegmentOrder.java:139). A probe that kept calling reorder() from one thread on an instance that had lost the race saw later calls fail too, in 5 of 670 failed rounds (three NullPointerExceptions in a row, then success; once a ClassCastException inside HashMap.TreeNode, HashMap.java:1995). Every successful call returned the correct order (897 race calls, 3,587 later calls) and none hung, so no wrong order, wrong hits or hang is claimed.

The numbers

#

1,000 one-document segments with f = 0 ... 999 and one descending LONG sort: one thread, or the same instance reused serially, gets f = 999, 998, ..., 0. Two threads at once: 20 of 20 rounds fail with assertions on and 19 of 20 with them off (gradle, main). With default settings, 1,000 puts grow the map 7 times, from 16 to 2,048 buckets, so each reorder() over 1,000 new segments has many windows.

Exposure and likelihood213 words
  • Who is hit. Applications that cache one SegmentOrder (for example one per Sort, like a cached Sort or Query) and call reorder() from several search threads.
  • When. The map is written only for segment cores the instance has not cached yet (SegmentOrder.java:138-139), so the risk is while concurrent calls insert new cores: mostly the first concurrent searches on a newly opened or refreshed reader, whenever a flush or merge adds segments. A call whose own segments are all cached can still fail if another thread is inserting at that moment, and after a lost race a few later calls on that instance can fail too, even from one thread (fact-check probe).
  • Effect. The failing reorder() call throws (almost always NullPointerException), so that search fails. Loud; no index damage, and no wrong results were seen.
  • Default vs opt-in. SegmentOrder is opt-in; nothing in Lucene calls it outside TestSegmentReordering. Once used, the default IndexWriterConfig, codec and directory suffice, with assertions on or off. A GitHub code search found no downstream caller (it indexes only part of GitHub).
  • Scale. The repro's 1,000 one-document segments only widen the window. It is a two-thread race, so real hit rates depend on how many new segments a call meets and on timing.

Why it looks unintended

#
  • fromSort() is a static factory over an immutable Sort; nothing says the instance holds state or must not be shared.
  • Lucene marks non-shareable helpers (StoredFields; HnswGraphBuilder: "cannot be shared across threads"); SegmentOrder has no such note.
  • The cache lives on the instance, which only pays off across calls (a per-call cache would serve one sort as well).
The full argument298 words
  • The API looks stateless. fromSort: "Builds a SegmentSorter that will reorder segments based on a given numeric Sort" (SegmentOrder.java:36-41); reorder: "Produces a new view over an IndexReader by re-ordering the reader's segments" (:33-34). No word on threads, reuse or a cache anywhere in the file.
  • Lucene documents the opposite case explicitly. StoredFields.java:29-30 ("This class is not thread-safe and should only be consumed in the thread where it was acquired"), HnswGraphBuilder.java:45 ("This class is NOT thread safe, it cannot be shared across threads"); a verifier counted 24 such notes in core. SegmentOrder is built from a Sort, which is immutable (lucene/MIGRATE.md:1638, "Sort is immutable (LUCENE-9325)"), and it carries no such note.
  • The design suggests reuse. The cache key is reader.getCoreCacheHelper().getKey() (:137), stable across reader reopens, and the cache is owned by the instance. A per-call cache would still serve the many comparisons inside one sort; keeping it on the instance, rather than per call, pays off only across calls. #15436 (closed) built a comparator per search with a cache keyed by LeafReaderContext.ord; #15591's first commit moved the comparator up into numericSorter and switched to the core key. No review comment on either PR discusses threads, sharing or the cache's lifetime.
  • The fix is expected to be cheap, but it is not benchmarked. On main, since #16388 (1593f87193b), a segment's skipper and point min/max are available without IO (:144-172); fix A gives up only the reuse of sort values across calls. For context, in #15436 (a comparator per search) its author measured a fixed per-search overhead of the whole re-sorting path (TermDTSort -37.2% QPS) and wrote "Given the fixed overhead of segment sorting, I think having this as something that happens automatically isn't viable".
The devil's-advocate check153 words

Strongest case for "intended": no document promises thread safety, Java's usual rule is that an undocumented class is not thread-safe, the PR title says "per-query segment re-ordering", CHANGES says "re-order segments at query time" (lucene/CHANGES.txt:1426), and the only caller (TestSegmentReordering.java:382) builds one per use. The cross-model reviewer stopped at "uncertain" for this reason.

Why it does not settle it: "per query" says when the application chooses to reorder, not how long the object lives; the object exposes no state, so a user has no hint that sharing is unsafe; and keeping the cache on the instance, rather than per call, only pays off across calls. A caveat against the bug reading: the core key may simply have been forced by the comparator receiving LeafReaders (no ord available), so it is weak evidence of intended reuse; the case rests on the API shape. Hence medium confidence and Low priority.

Suggested fix

#

Recommended Build the comparator inside reorder() (A)

Build the comparator, and so its cache, inside reorder() instead of once per SegmentOrder (+3/-2 lines, one file): the instance then holds no mutable state. With it the repro passes 20 of 20 and 50 of 50, TestSegmentReordering passes, and format, ecj and forbidden-API checks pass.

        // a fresh comparator (and sort-value cache) per call: the strategy holds no mutable state

Trade-offs

Each reorder() loads the sort value once per distinct segment core it sees (a skipper or point min/max read) instead of reusing values from earlier calls; expected to be cheap on main, but no benchmark was run. Each call's map is then used only by the calling thread (Arrays.sort is sequential), so the race cannot occur. It also ends the cache's growth across calls (one small entry per segment core ever seen; not claimed as a bug). It does not touch the getCoreCacheHelper().getKey() call (:137), so LFV-296 stays.

Downstream note

#

Relevant only to products that cache one SegmentOrder per sort and share it across search threads: there, some searches fail right after a reader is opened or refreshed; queries or documents alone cannot create that sharing.

How it was found

#

A proof-obligation audit of SegmentOrder's contract: reorder() of an instance built from an immutable Sort should depend only on its reader argument and share no state across calls. The audit found one comparator cache shared by every call; a two-thread public-API JUnit test then witnessed the NullPointerException.

The method in full127 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: a strategy from fromSort() exposes no state, so each reorder(reader) should be a function of reader alone. numericSorter (SegmentOrder.java:89-111) breaks it: one comparator with a mutable, unsynchronized cache is captured by every call.
  • The finder wrote a public-API JUnit test (two readers of 400 one-document segments, one shared SegmentOrder, two threads) that fails in most iterations on main, 10.6.0 and 10.4.0, and the per-call-comparator change that makes it pass.
  • An independent reproducer, a cross-model reviewer, a devil's-advocate verifier and an adjudication re-ran it or wrote their own tests ("Prior reports, history and checks"). The adjudication chose the shared-reader shape as the one repro.

Impact note
Only applications that keep one SegmentOrder from SegmentOrder.fromSort with an INT, LONG, FLOAT or DOUBLE primary sort (the opt-in helper added in 10.4.0; nothing in Lucene outside its own test calls it) and call reorder() on it from two or more threads at the same time, on segment cores that strategy has not cached yet (for example the first concurrent searches on a freshly opened or reopened reader), get a NullPointerException out of some of those reorder() calls, so those searches fail; the failure is loud, no wrong results or index damage were observed or are claimed, a SegmentOrder built per query never fails, and released 10.4.0 to 10.6.0 are affected with the default IndexWriterConfig, codec and directory, -ea or -da.
Summary
You build one SegmentOrder with SegmentOrder.fromSort(new Sort(new SortField("f", SortField.Type.LONG, true))) and share it between searches, as you would a Sort or a Query, so two threads call order.reorder(reader) on the same freshly opened reader at the same time. You expect each call to return a re-ordered view: the strategy is built from an immutable Sort, its API exposes no state, and its javadoc says nothing about threads. Instead every reorder() of that strategy sorts the leaves with one comparator whose per-segment memo is a plain HashMap filled with containsKey/put/get and no lock, so a concurrent put or resize can make Map.get return null and reorder() throws NullPointerException 'Cannot invoke "java.lang.Long.longValue()" because the return value of "java.util.Map.get(Object)" is null' at SegmentOrder.java:141.
