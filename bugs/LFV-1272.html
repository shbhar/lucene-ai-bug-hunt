CheckIndex.checkImpacts compares each impact only with the level's first impact, so unsorted impact lists pass

CheckIndex's check that each level of impacts is sorted compares every entry only with the first one, so an unsorted list such as (1,1),(3,3),(2,2) passes. Lucene's own postings formats always write sorted impacts; the gap only lets a broken custom or future format pass CheckIndex and the codec test framework.

The finding in 30 seconds

#

The check that each impacts list is sorted only looks at the first entry, so most unsorted lists pass.

Background: impacts and their order

#
  1. For each block of a term's postings, a postings format reports impacts: a short list of (freq, norm) pairs that bound the scores of the documents in that block, so top-k search can skip blocks that cannot compete.
  2. Each list must be sorted by increasing freq and increasing norm, for example (1,1),(2,2),(3,3); there can be one list per skip level.
  3. CheckIndex.checkImpacts checks this rule and throws "Impacts are not ordered or contain dups, got (prev) then (cur)". CheckIndex and Lucene's codec test framework both use it to vet postings formats.

The finding, step by step

#
  1. Give CheckIndex.checkImpacts one level of impacts, as (freq, norm) pairs, in the wrong order: (1,1),(3,3),(2,2). Freq drops from 3 to 2.
  2. You expect CheckIndexException: Impacts are not ordered or contain dups, got (3,3) then (2,2). That is what the method throws once the bug is fixed.
  3. You get no error. The loop sets its "previous entry" to (1,1) once and never moves it on. So (3,3) is compared with (1,1), which is fine, and (2,2) is also compared with (1,1) instead of (3,3).
  4. Only a list with a later entry whose freq or norm is at or below the first entry's is caught, for example (1,1),(1,2). The fix is two lines at the end of the loop: prevFreq = freq; prevNorm = norm;.
  5. The same method backs CheckIndex.testPostings (level 2 and up), AssertingLeafReader and RandomPostingsTester. Every release since 8.0.0 has the gap.

Who is affected

#

Authors of custom or future postings formats who rely on CheckIndex (checkIndex() at level 2 or 3, testPostings) or Lucene's codec test framework to catch unsorted impacts. Lucene's own formats always write sorted impacts, so no index Lucene writes and no search result is affected. Some unsorted lists are still caught by other checks.

Mechanism, terms and numbers383 words

Impacts.getImpacts documents that each level's impacts are "sorted by increasing frequency and increasing unsigned norm", and CheckIndex.checkImpacts exists to enforce it ("Impacts must be in increasing order of norm AND freq"). Its loop sets prevFreq and prevNorm to the first entry and never updates them, so each entry is compared with entry 0 only. An unsorted list such as (1,1),(3,3),(2,2) passes; only a later entry whose freq or norm is at or below the first entry's, such as (1,1),(1,2), is caught. The method is what CheckIndex.testPostings (from level 2), AssertingLeafReader and RandomPostingsTester call, so CheckIndex and the codec test framework miss this shape of malformed impacts. Lucene's own postings formats always write sorted impacts, so no index Lucene writes and no search result is affected. Every release since 8.0.0 has it; the fix is two lines.

The loop (CheckIndex.java:2613-2631)

#
// Impacts must be in increasing order of norm AND freq
int prevFreq = firstFreq;
long prevNorm = firstNorm;
for (int i = 1; i < perLevelImpacts.size; ++i) {
  int freq = perLevelImpacts.freqs[i];
  long norm = perLevelImpacts.norms[i];
  if (freq <= prevFreq || Long.compareUnsigned(norm, prevNorm) <= 0) {
    throw new CheckIndexException("Impacts are not ordered or contain dups, got (" ...); // message abbreviated
  }
  // missing: prevFreq = freq; prevNorm = norm;
}
  1. Entry 1, (3,3), is compared with (1,1): 3 > 1 and 3 > 1, no error.
  2. Entry 2, (2,2), should be compared with (3,3), which fails (2 <= 3). It is compared with (1,1) instead: 2 > 1 and 2 > 1, no error.
  3. So the loop only proves that entry 0 is the strict minimum in both freq and norm. Later entries may come in any order, and may repeat (for example (1,1),(2,2),(2,2)), as long as each is above entry 0, although the message says "or contain dups".
  4. The cross-level scan right below (:2632-2676) reuses the names prevFreq and prevNorm but assigns them on every step (:2648-2649), so updating them in this loop does not change it.

Who calls it

  • CheckIndex.testPostings (:2128, :2173, :2215), which checkIndex() runs from level 2 on (:1114-1125).

Exposure and likelihood285 words
  • Who. Anyone who vets a postings format with CheckIndex or with the codec test framework. checkIndex() checks postings only at level 2 or higher (CheckIndex.java:1114-1125). At level 2 the impacts checks run only for terms with more than 1024 docs and for every 1024th term (:2090-2094), and only the :2173 and :2215 calls, since the :2128 call needs level 3 (:2108). The command-line default level is 1 (:4673, :4748), and a programmatic CheckIndex has level 0 until setLevel (:499, :505-508). testPostings(CodecReader, PrintStream) runs at level 3 (:2681-2683). The test framework calls the method from AssertingLeafReader and RandomPostingsTester, and TestUtil.checkIndex and checkReader run CheckIndex at level 3 (TestUtil.java:303, :353).
  • Why the order matters. Readers of impacts assume it: for example SynonymQuery merges impact lists by norm (SynonymQuery.java:534-561), and the cross-level scan in this same method relies on it. No search or scoring effect is claimed here.
  • Not affected. Indexes Lucene writes: every postings format that stores impacts builds them with CompetitiveImpactAccumulator, whose getCompetitiveFreqNormPairs returns them "ordered by increasing freq and norm" (CompetitiveImpactAccumulator.java:101-123); formats that store none, such as DirectPostingsFormat, return the single entry of SlowImpactsEnum (SlowImpactsEnum.java:105-108). Lucene104PostingsReader.readImpacts decodes freq as strictly increasing (:1447-1470). Indexing and search are unchanged.
  • Partly covered elsewhere. CheckIndex's slow pass takes the last entry as the max freq (CheckIndex.java:2129-2131) and reports a document whose freq is above it; RandomPostingsTester's coverage assertion does a binarySearch by freq (RandomPostingsTester.java:1269-1280), whose result on an unsorted list is undefined and may or may not trip.
  • Scale. None needed: one level with three entries.

Why it looks unintended

#
  • Impacts.getImpacts documents each level as "sorted by increasing frequency and increasing unsigned norm"; the check's own comment says the same.
  • The names prevFreq/prevNorm and the message "got (prev) then (cur)" describe a pairwise check; only the update line is missing.
  • The update was never written (2018), a 2025 rewrite (#15151) kept the gap, and nothing documents a first-entry-only check.
The full argument108 words
  • The contract is written down twice: the Impacts.getImpacts javadoc (Impacts.java:39-40) and the check's comment (CheckIndex.java:2613).
  • The code says pairwise: a check against entry 0 alone is neither "increasing order" nor a dups check beyond entry 0, yet the error text is "got (prev) then (cur)" (:2619-2629).
  • Nothing chose it: af680af77f3 (LUCENE-8142, 2018) wrote Impact previous = first; with no previous = impact in the loop; #15151 (2dcfd89123e, 2025) rewrote the loop over arrays and again left it out. No javadoc, CHANGES or MIGRATE entry, upstream test or review comment in #9190 or #15151 accepts a first-entry-only check.
The devil's-advocate check143 words

checkImpacts is package-private, "For use in tests only" and @lucene.internal (CheckIndex.java:2562-2567); CheckIndex promises no exhaustive validation; and an unsorted list can only come from a producer that already breaks the Impacts.getImpacts contract, which no Lucene format does. An independent reviewer from another model family (OpenAI GPT-5.6) called it not real on these grounds, while agreeing on the root cause and the fix and calling the change "a legitimate hardening opportunity".

Why it fails: a validator exists to reject producer output that breaks the documented rule, so "the input already breaks the contract" is circular here. The method's verdict is CheckIndex.testPostings's verdict and the test framework's verdict for every postings format under test, and the check visibly tries to do this job but gets it right only for the second entry. Verdict: a real Low bug, a validator false negative.

How it was found

#

A proof-obligation audit of CheckIndex.checkImpacts against the order that Impacts.getImpacts documents. The obligation, that each entry is compared with the one before it, fails because the loop never moves its previous entry on; a one-test JUnit repro witnessed it.

The method in full83 words

Semi-formal method: a proof-obligation audit of CheckIndex.checkImpacts against its contract, the per-level order that Impacts.getImpacts documents. The obligation is that the loop rejects any level whose entries are not strictly increasing in freq and in unsigned norm; as written, the loop meets it only for the second entry, because the previous entry stays at entry 0. An executable JUnit repro on main witnessed it, and an independent reproducer, an intended-behaviour devil's advocate, a cross-model review and an adjudication then re-ran or challenged it.
