The finding in 30 seconds

#

The filter rewrites the token's buffer in place, on the assumption that a folded character takes as many UTF-16 units as the original. Unicode 18's U+1DF95 to ß is the first fold that takes fewer (2 units to 1). The loop steps by what it wrote, and nothing shortens the term.

Background: three pieces

#
  1. Java text is a row of UTF-16 units. Most characters take one. Characters above U+FFFF take two, a high and a low surrogate, which are only valid as a pair.
  2. CaseFoldingFilter (opt-in, since 10.6.0) replaces every character of a token by its Unicode simple case fold, so that spellings that differ only in case give the same term. The folds come from a table generated from Unicode's data.
  3. A token's text lives in a buffer with a length. The filter folds the buffer in place and leaves the length as it was.

The finding, step by step

#
  1. On main or on branch_11x (both unreleased; branch_11x from 9d2b5a15427a on), analyze the word Ma + U+1DF95 + e with WhitespaceTokenizer and CaseFoldingFilter. U+1DF95 (LATIN SMALL LIGATURE LONG S WITH DESCENDER S, new in Unicode 18) takes two UTF-16 units, so the token has 5: 004D 0061 D837 DF95 0065.
  2. The fold table of both maps U+1DF95 to ß (U+00DF), as Unicode 18 does. You expect the term maße, 4 units: 006D 0061 00DF 0065.
  3. You get 5 units: 006D 0061 00DF DF95 0065. The fourth is the second half of the old letter, left behind. That is not valid UTF-16, and the index stores the term as maß + U+FFFD + e. The filter throws nothing.
  4. Why: CharacterUtils.simpleCaseFold folds in place with one position. At position 2 it reads the letter (2 units), writes ß (1 unit) and moves on by 1, the number it wrote. At position 3 it finds the left-over DF95 and keeps it. The method returns no new length and the filter never sets one.
  5. On 10.6.0, and on branch_11x before 9d2b5a15427a, the table does not have the letter, the filter leaves it alone and the repro test passes. Two limits: Maße did not find this word before either, and StandardTokenizer, with its grammar as it is, splits the word at the letter, so the filter does not get it there.

Who is affected

#

Only applications on unreleased main or branch_11x that chose CaseFoldingFilter (factory name caseFolding) behind a tokenizer that keeps the letter inside a token, such as WhitespaceTokenizer, and whose text contains U+1DF95. Behind WhitespaceTokenizer, three placeholder queries (Ma?e, /ma.e/, Mate~1) found the word on 10.6.0 and no longer do; a query for the word itself still does. The filter throws nothing.

Mechanism, terms and numbers1,103 words

Main and branch_11x, both unreleased; new in 11.0. CaseFoldingFilter (opt-in, since 10.6.0) folds a token's buffer in place with CharacterUtils.simpleCaseFold and never sets the term length (CaseFoldingFilter.java:44 on main 01deb8e63e0b). The loop of simpleCaseFold has one index for reading and writing and advances it by the UTF-16 units it wrote (CharacterUtils.java:85-89). That is right as long as every fold takes as many units as its source. Since #17010 (merged to main on 2026-11-16 as 01deb8e63e0b and committed to branch_11x the same day as 9d2b5a15427a; its milestone reads 11.0.0) the generated fold table of both is from Unicode 18 and has case 0x1DF95: return 0x00DF; (SimpleCaseFolding.java:555-556): the letter takes two units and ß takes one. The loop writes ß, moves by one and reads the letter's old low surrogate as a character of its own. So Ma + U+1DF95 + e (004D 0061 D837 DF95 0065) becomes 006D 0061 00DF DF95 0065 where 006D 0061 00DF 0065 (maße) is due; the term is not valid UTF-16 and the index stores it as maß + U+FFFD + e. The fold and the filter throw nothing, with assertions on or off. The table entry is right (Unicode 18.0.0: 1DF95; S; 00DF); the two classes that consume it are unchanged since 10.6.0. Exactly 1 of 1,112,064 scalar values is affected (counted through UnicodeUtil.foldCase on JDK 25.0.3). The test fails on builds of main 01deb8e63e0b and 9965d34e3c77 and of branch_11x 9d2b5a15427a; it passes on the 10.6.0 release and on the two branch_11x builds from before that commit (daa54f2e0cd3, a40bef9a7870), so 11.0.0 would be the first release with it as the branch stands on 2026-11-16; 10.5.2 and 9.12.3 do not have the filter. Two limits: the word did not match its sharp-s spelling before either (the older tables leave the letter alone), and only a tokenizer that keeps the letter inside a token reaches the filter (not StandardTokenizer, whose grammar is generated from Unicode 12.1 data and splits the word at the letter). A validated fix reads and writes with two positions, returns the new limit and lets the filter set the term length; keeping such folds out of the generated table is the other choice.

Why it looks unintended

#
  • The javadoc promises Unicode simple case folding, and the same commit's table folds U+1DF95 to ß. The term is neither the folded word nor the unchanged one.
  • CharTermAttribute.buffer() says to call setLength after altering the buffer. TurkishLowerCaseFilter does.
  • Nothing documents that folds keep their UTF-16 length. For lower-casing, Robert Muir called the same kind of assumption version-dependent in 2009 (LUCENE-1689).
The full argument557 words
  • The javadocs promise the fold of each code point. CaseFoldingFilter: "Normalizes token text by applying Unicode simple case folding.", with a link to Unicode's latest CaseFolding.txt (CaseFoldingFilter.java:22-28). simpleCaseFold: "Applies Unicode simple case folding to each codepoint starting at the given offset." (CharacterUtils.java:72-78). foldCase: "Returns the Unicode simple case folding of {@code codepoint}." (UnicodeUtil.java:690). The table of the same commit carries the fold.
  • The attribute's contract. CharTermAttribute.buffer(): "After altering the buffer be sure to call {@link #setLength} to record the number of valid characters that were placed into the termBuffer." (CharTermAttribute.java:34-42). After the fold four units are valid and the length stays five. A sibling whose mapping can shorten the term sets it: TurkishLowerCaseFilter.java:66 (delete in place) and :87 (termAtt.setLength(length)).
  • Nothing states the assumption. No javadoc or CHANGES entry, and no review comment of the change that added the filter (#16371, with its 10.x copy #16444), says that a fold keeps its UTF-16 length. The generator covers every code point (GenerateSimpleCaseFolding.groovy:17 loops to Character.MAX_CODE_POINT), and the table at 01deb8e63e0b has 42 supplementary source entries of 247. What the thread of #16371 does hold is the first scope of the change. Its description (opened 2026-07-07) says: "Performs simple case folding for ~1200 BMP codepoints ... Supplementary codepoints (> U+FFFF) fall back to Character.toLowerCase()." The generator's loop was for (int c = 0; c < 0x10000; c++) until a review comment of 2026-07-29 on the generator, "why not go to real end of unicode? I'd use Character.MAX_CODE_POINT", answered the same day with "Done. Recreated the file and found a few more cases." The change was merged on 2026-07-31, and the 10.6.0 table has 22 supplementary sources. Neither text says what should happen for a fold that changes the UTF-16 length, and no table before the Unicode 18 one has such a fold.
  • The same kind of assumption was called version-dependent long ago, for lower-casing (as Robert Muir wrote on LUCENE-1689, #2763, in June 2009): the in-place code "depends upon the knowledge that no surrogate pairs lowercase to BMP codepoints", and "I do not think it guarantees this for all future unicode versions ... it should be documented that this could possibly change in some future version." Those remarks are about lower-casing, and for lower-casing the assumption still holds: 0 of the 4,562 simple upper, lower and title mappings of Unicode 18.0.0 cross the BMP boundary. The fold loop of 2026 took over the same kind of assumption for case folding, and there Unicode 18 is the first version in which it does not hold.
  • Upstream's tests cannot see it. TestCharacterUtils.testFoldIdempotent stops at U+FFFF (:129-130), and testSimpleCaseFoldRandom checks only that folding twice equals folding once (:143-152), which the malformed result satisfies. There is no test class for CaseFoldingFilter.
  • Related CHANGES entries. 10.5.0, Bug Fixes: "Improve TruncateTokenFilter to truncate on codepoints not chars and no longer produce half surrogates" (#15899, #15900; CHANGES.txt:1316-1318). 7.4.0, Bug Fixes: "Fixed the smartcn tokenizer to not split UTF-16 surrogate pairs" (LUCENE-8325; CHANGES.txt:7597). Other filters and other causes.
  • What is not claimed. No javadoc says in so many words that a term must be valid UTF-16. The claim rests on the three folding javadocs, on the setLength sentence and on the table itself.
The devil's-advocate check339 words

The strongest case for "intended": the header of Unicode's CaseFolding.txt says the data supports "implementations that require simple case foldings (where string lengths don't change)". Simple folding was chosen for the filter because it is cheap, and the loop has the shape of toLowerCase's loop in the same class (CharacterUtils.java:54-70). So an in-place fold without a length looks like the design, and a simple fold looks length-preserving by definition. And the outcome for a malformed term is documented: the javadoc of IndexWriter#addDocument says "it's possible to create an invalid Unicode string in java if a UTF16 surrogate pair is malformed. In this case, the invalid characters are silently replaced with the Unicode replacement character U+FFFD" (IndexWriter.java:1485-1487).

Why it fails: "string lengths" there counts code points, one code point to one code point; it is not a statement about encoded length. In UTF-8 the same sentence already stood over 212A; C; 006B (KELVIN SIGN to k, three UTF-8 bytes to one; both are one UTF-16 unit). In UTF-16, the form of this buffer, no simple fold changed the length before 18.0.0 (0 of the 1,512 lines of 17.0.0); 1DF95; S; 00DF is the first, and it is Unicode's own data, under the same sentence. The recorded design goal is speed for a correct simple fold; no text accepts a wrong term for it. The IndexWriter javadoc says what the writer does with a malformed string it is given; here the input is well-formed, it is the filter that makes the term malformed, and with or without the replacement the term is not the fold. And the filter does not leave the letter alone: it writes the ß and keeps half of the letter. What a maintainer can fairly say is about weight (one new letter, an opt-in filter, unreleased code, which since 9d2b5a15427a includes the 11.0 release branch), and this page says that first. They may also prefer to keep the loop and leave such folds out of the table (Suggested fix, option B).

Suggested fix

#

Recommended A. Two positions in the loop, the new limit returned, the filter sets the term length (validated)

Let the fold shorten the term: simpleCaseFold reads and writes with two positions and returns the new limit, and the filter sets the term length to it (2 files, 14 lines added, 6 removed). Validated: the test passes, and 169 core analysis tests and the module's lint pass. It changes a void method of an internal class to return int.

// CharacterUtils.simpleCaseFold, the code-point loop (the method now returns int)
int out = i; // write position: falls behind the read position when a fold is shorter
while (i < limit) {
  final int cp = Character.codePointAt(buffer, i, limit);
  final int folded = UnicodeUtil.foldCase(cp);
  assert Character.charCount(folded) <= Character.charCount(cp);
  i += Character.charCount(cp);
  out += Character.toChars(folded, buffer, out);
}

A. Two positions in the loop, the new limit returned, the filter sets the term length (validated) (recommended)

#

CharacterUtils.simpleCaseFold keeps a read position and a write position. It advances the read position by the units it read and the write position by the units it wrote, and returns the write position as the new limit (the old limit when the text is all ASCII). CaseFoldingFilter.incrementToken passes that value to termAtt.setLength. Two files, 14 lines added and 6 removed.

// CharacterUtils.simpleCaseFold, the code-point loop (the method now returns int)

Trade-offs

  • Signature. It changes the return type of a public static method of a class marked @lucene.internal (CharacterUtils.java:26), void to int: source-compatible for callers that ignore the result, not binary-compatible.
  • Callers must use the result. A caller that ignores the returned limit still sees the old units behind it. In the tree the only other caller outside the tests is a JMH benchmark; upstream's TestCharacterUtils calls the method too and ignores the result (it passes with the fix).
  • Shorter only. It handles folds that take fewer units than their source, not folds that would need more. None exists in Unicode 18, and the assert states the precondition; such a fold would overwrite the next unread unit.
  • Not benchmarked. The loop does the same work per code point with two more local variables.

B. Keep folds that change the UTF-16 length out of the generated table (not built as a patch)

#

The generator (GenerateSimpleCaseFolding.groovy:17-37) would skip an entry whose fold has another UTF-16 length than its source, and the javadoc of foldCase and of the filter would say so. The in-place loop then stays as it is.

Not validated. A stand-in was run: the table of 01deb8e63e0b with the one entry removed by hand, put in front of the built jars. The test passes, assertions on and off, because it takes the due term from foldCase. The generator was not changed and the module's tests were not run for this option.

  • For that one letter UnicodeUtil.foldCase would differ from Unicode's simple case folding, and the letter would not match ß. (Unicode's full fold of the letter is ss.)

How it was found

#

Semi-formal. When the Unicode 18 tables arrived, the regenerated fold table was read against the in-place loop. A differential check then compared the filter with the fold of each code point over every Unicode scalar value (1,112,064): exactly one differs, U+1DF95. A small solver model of the loop shows it is right whenever folds keep their UTF-16 length.

The method in full252 words

Method: semi-formal (a differential check against a reference over the whole input space, plus a solver model of the loop; no proof of the Java code itself).

  • Signal. Reading the regenerated table against the loop of simpleCaseFold gave the hypothesis: an entry whose fold is shorter in UTF-16 than its source leaves a unit behind.
  • Differential check. Reference: the folded text of a string is UnicodeUtil.foldCase of each of its code points, in order. Every scalar value was put through CaseFoldingFilter (alone, between two letters, doubled) and through simpleCaseFold on main 01deb8e63e0b, an older main, branch_11x daa54f2e0cd3 and 10.6.0. On 01deb8e63e0b exactly one code point differs, U+1DF95, and it is the only one whose fold has another UTF-16 length; 0 on the other three builds. The table equals ICU's simple fold for every code point on each build. Run again after the table reached the branch: branch_11x 9d2b5a15427a gives the lines of main (exactly one code point, U+1DF95), and a40bef9a7870, the commit before it, none.
  • Solver model. An SMT model (Z3, bit-vectors) of the loop over every well-formed input of up to four units (11 shapes): the loop equals the reference for every mapping that keeps the UTF-16 length; it gives witnesses as soon as one code point gets shorter, and also for a mapping that gets longer; the vacuity query is satisfiable.
  • Reduction. First to one JUnit test with the word behind a whitespace tokenizer, then to the one code point as a single token, which is the repro.

Summary

You expect the folded term 'maße', because the filter promises Unicode simple case folding and the fold table of main and branch_11x maps U+1DF95 to ß (U+00DF), as Unicode 18 does.
