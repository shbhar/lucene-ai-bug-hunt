With format="snowball", a UTF-8 byte order mark stays glued to the first word of a stop, keep or common-words file

With format="snowball", a stop-words file saved with a UTF-8 byte order mark and starting with a word loses that word: the invisible mark sticks to it, so the set holds \uFEFFthe and the cat keeps the. The default wordset format skips the mark; affected since 4.0.0-BETA.

The bug in 30 seconds

#

Words files for these factories come in two formats: wordset (the default, one word per line, # comments) and snowball (several words per line, | comments). Only wordset skips a leading byte order mark.

  1. You save stopwords.txt with the, a, an, one per line, in an editor that writes UTF-8 with a byte order mark: 12 bytes that start with EF BB BF, which decode to the invisible character U+FEFF. One word per line is valid in both formats.
  2. With the default format="wordset", StopFilterFactory loads [the, a, an] and the cat becomes [cat]. You switch to format="snowball" (several words per line, | comments) and expect the same set.
  3. You get [a, \uFEFFthe, an]: the mark is glued to the, so the cat stays [the, cat]. No error, and the printed set looks right, because U+FEFF is invisible.
  4. Why: the wordset loader drops a leading U+FEFF ("skip initial bom marker"). The snowball path decodes the file itself and splits on whitespace, and U+FEFF is not whitespace.
  5. Same with the other factories: with keep words apple, banana, KeepWordFilterFactory turns apple cherry banana into [banana]; the common-grams and suggest-stop factories lose their first word too. A file that starts with a | comment loses no word: the bundled English list re-saved with a mark loads 175 entries instead of 174, the extra one \uFEFF.

Who is affected

#

Users who give StopFilterFactory, KeepWordFilterFactory, CommonGramsFilterFactory, CommonGramsQueryFilterFactory or SuggestStopFilterFactory their own words file with the opt-in format="snowball", saved with a byte order mark and starting with a word. Built-in analyzers are not affected: no bundled list has a mark. Deterministic, any index size, no error.

Mechanism, terms and numbers683 words

StopFilterFactory, KeepWordFilterFactory, CommonGramsFilterFactory, CommonGramsQueryFilterFactory and SuggestStopFilterFactory read a words file in one of two formats: wordset, the default (one word per line, # comments), or the opt-in snowball (several words per line, | comments). Some editors save UTF-8 with a byte order mark, the bytes EF BB BF, which decode to U+FEFF. The wordset loader drops a leading U+FEFF, on purpose since 2010 (SOLR-1865). The snowball path does not: the factory decodes the file with its own reader and the parser splits on \s+, which does not match U+FEFF, so the mark stays glued to the first word. A file <BOM>the a an | articles gives the stop set [a, \uFEFFthe, an], and the cat is analyzed to [the, cat] instead of [cat]. The first keep word, common word and suggest stop word are lost the same way; when the first line is a comment or blank, or the mark is followed by a space or tab, the words survive and the set gains a stray \uFEFF entry. No error is raised. The snowball path has skipped no mark since it was added (SOLR-1860, 2012), so every Lucene release from 4.0.0-BETA to 10.5.2 and main is affected. Skipping one leading U+FEFF where the factory decodes the file fixes it.

Terms

#
  • Words file: the words parameter of StopFilterFactory, KeepWordFilterFactory, CommonGramsFilterFactory, CommonGramsQueryFilterFactory and SuggestStopFilterFactory; format says "how the words file will be parsed" (AbstractWordsFileFilterFactory.java:38-54).
  • Byte order mark (BOM): the bytes EF BB BF that some editors write at the start of a UTF-8 file. Java's UTF-8 decoder keeps them as the character U+FEFF, which is invisible when printed.

The bug

#
  1. wordset goes through AbstractAnalysisFactory.getWordSet and WordlistLoader.getLines, which decodes the bytes itself and drops a leading U+FEFF from each line it reads while no word has been added yet (lines.isEmpty()), so a BOM at the start of the file is skipped: // skip initial bom marker (WordlistLoader.java:297-314, :302-304).
  2. snowball goes through AbstractAnalysisFactory.getSnowballWordSet, documented as the "same as getWordSet(ResourceLoader, String, boolean), except the input is in snowball format" (AbstractAnalysisFactory.java:304-307). It builds its own strict UTF-8 InputStreamReader (:317-322) and hands it to WordlistLoader.getSnowballWordSet(Reader, CharArraySet) (:323).
  3. That parser cuts each line at | and splits it on \s+ (WordlistLoader.java:193-207). \s matches ASCII whitespace only, so the first piece of the first line is \uFEFFthe; when the first line is a comment or blank, or the mark is followed by a space or tab, the piece is \uFEFF alone and becomes an entry of its own while the word survives (<BOM> the a an gives [the, a, an, \uFEFF]).
  4. The factory loops over a comma-separated words list (AbstractAnalysisFactory.java:316-325), so every file's own mark is kept.

Exposure and likelihood304 words
  • Who is exposed. Applications that configure one of the five factories with an explicit words file and format="snowball": directly, through CustomAnalyzer, or through a search server's schema (the factories' javadoc examples are schema snippets). The default format is wordset, so it is opt-in.
  • What it takes. A words file saved as UTF-8 with a byte order mark, which the 2010 CHANGES entry that introduced the skip describes as "often created by editors such as Windows Notepad", and a word on its first line.
  • What happens. A stop word is indexed and searched like any other word; a keep word's tokens are dropped; a common word forms no bigrams; a suggest stop word is not treated as one. With a comment or blank first line, or a space or tab after the mark, no word is lost and the set gains a \uFEFF entry. Nothing fails, and a printed set looks right because U+FEFF is invisible.
  • Scale. Deterministic and independent of index size. The wrong set is used for every document and query analyzed with that analyzer, so any text that contains the affected word is analyzed differently. Indexes built with the wrong set keep their terms until reindexed.
  • Built-in analyzers. Not affected: all 15 bundled Snowball lists start with a | From https://snowballstem.org/... comment line, and none of the 147 bundled resource files starts with EF BB BF. A copy re-saved with a mark loses no word and only gains the stray entry.
  • Versions. Every release from 4.0.0-BETA to 10.5.2 and main; SuggestStopFilterFactory from 5.0.0, when it was added, and KeepWordFilterFactory from 8.11.0, when it got the format parameter.
  • How likely. Rare: it needs the opt-in format, a file saved with a mark and a word on the first line, and the searches found no prior report (see "Prior reports").

Why it is a bug, not intended

#
  • format is documented as how one words file is parsed, the snowball loader as the "same as getWordSet ... except the input is in snowball format"; getWordSet skips the mark.
  • The default words-file loader has skipped a leading mark on purpose since 2010; the snowball path (2012) never got it.
  • Nothing says snowball files must not carry a mark.
The full argument277 words
  • One parameter, two parse modes of the same file. format "defines how the words file will be parsed", with wordset and snowball as the two values; neither says the file must not carry a mark (AbstractWordsFileFilterFactory.java:38-54, StopFilterFactory.java:44-60). A file with one word per line is valid in both formats, yet the same marked file gives [the, and] in one and [\uFEFFthe, and] in the other.
  • Documented as the same loader except for the format. AbstractAnalysisFactory.java:304-307: "same as getWordSet(ResourceLoader, String, boolean), except the input is in snowball format". The mark belongs to the encoding, not to either format, and on this path Lucene's own code does the decoding.
  • Deliberate in the default loader. SOLR-1865 (2010) added the skip with the CHANGES entry "SolrResourceLoader.getLines ignores Byte Order Markers (BOMs) at the beginning of input files, these are often created by editors such as Windows Notepad"; LUCENE-4257 moved it into WordlistLoader.getLines. LUCENE-5505 did the same for hunspell dictionaries ("HunspellStemFilter ignores BOM markers in dictionaries"). In 2010, rmuir listed that the Solr stopword loading code "ignores BOM markers" among the reasons it was better than Lucene's own loader. It is not a rule of every Lucene resource loader: the same hunt saw other loaders keep a mark.
  • An omission. The snowball factory path came two years after the rule (SOLR-1860, 2012) with its own reader, and its tests use a file without a mark. No test, javadoc, CHANGES entry or issue says snowball files must not carry one; in the tests of core, analysis-common and suggest, the only input that starts with a mark is hunspell's (core's TestStandardAnalyzer lists U+FEFF only as a word-break format character).
The devil's-advocate check317 words

The checkers built the strongest case for "intended": (a) read literally, the snowball grammar names only whitespace and | comments, so U+FEFF is part of the first word; (b) WordlistLoader is @lucene.internal, and its generic getWordSet(Reader) keeps a mark too; (c) the wordset skip is a code comment plus a CHANGES entry, not javadoc; (d) committers have said that, used directly, "the stopword file parser does not care about encodings at all" (uschindler, 2010) and that a mark in a Reader means "your conversion from bytes is screwed up somewhere before" (dweiss, 2017, reviewing a char-filter mapping that deleted U+FEFF from analysis input: an analogy, not a remark on resource files); (e) in the 2010 user-list thread behind the skip, rmuir answered "No." to whether a marked file is a bug, and then: "we can ignore them for the first line of the file to be more user-friendly"; SOLR-1865 is typed Improvement, and users can simply save the file without a mark.

Why we think it fails: (a) to (c) describe the internal parser; the user-facing contract is the factory's format parameter, whose two values are documented as parse modes of the same file, and the factory itself turns the bytes into chars, so by the reasoning of (d) the factory is where the mark should go (the recommended fix). (e) was about whether to handle marks at all; in the same thread Yonik Seeley called it "a Java bug" and added "we should fix if it's practical to do so, rather than passing the buck", the default words-file loader then skipped them, and snowball is the only words-file format of these factories that does not. The literal reading (a) stays arguable. Expect "improvement, not bug" as an answer, and frame the issue as an inconsistency between the two formats. Every checker rejected the works-as-designed case; the cross-model reviews rated it moderate, the devil's advocate weak.

Suggested fix

#

Recommended B. Skip the mark where the factory decodes the file (AbstractAnalysisFactory)

Skip one leading U+FEFF where the factory decodes each words file (AbstractAnalysisFactory.getSnowballWordSet), as the wordset loader already does: read one char through a BufferedReader and reset unless it is U+FEFF. Validated: the repro, the factory suites and the whole analysis-common module pass, and so does :lucene:core:check.

-        try (Reader reader = new InputStreamReader(loader.openResource(file.trim()), decoder); ) {
+        try (BufferedReader reader =
+            new BufferedReader(new InputStreamReader(loader.openResource(file.trim()), decoder))) {
+          // skip initial bom marker, as the wordset format does (WordlistLoader.getLines)
+          reader.mark(1);
+          if (reader.read() != '\uFEFF') {
+            reader.reset();
+          }
           WordlistLoader.getSnowballWordSet(reader, words);
         }

B. Skip the mark where the factory decodes the file (AbstractAnalysisFactory) (validated by the checks) (recommended)

#

In AbstractAnalysisFactory.getSnowballWordSet (AbstractAnalysisFactory.java:322), wrap the decoding reader in a BufferedReader, read one char and reset() unless it is U+FEFF, then parse as before. WordlistLoader.getSnowballWordSet reuses a reader that is already a BufferedReader, so nothing is buffered twice.

What it changes. Only the factory path used by the five factories: one U+FEFF at the very start of each file is dropped, the case getLines covers for wordset (unlike getLines, it does not look at later lines). Files without a mark are read unchanged; an empty file still gives no words; malformed UTF-8 still fails with the same MalformedInputException (checked with a copy of this reader setup on the stock jars). The internal WordlistLoader API and the built-in analyzers are untouched.

-        try (Reader reader = new InputStreamReader(loader.openResource(file.trim()), decoder); ) {
+        try (BufferedReader reader =
+            new BufferedReader(new InputStreamReader(loader.openResource(file.trim()), decoder))) {
+          // skip initial bom marker, as the wordset format does (WordlistLoader.getLines)
+          reader.mark(1);
+          if (reader.read() != '\uFEFF') {
+            reader.reset();
+          }
           WordlistLoader.getSnowballWordSet(reader, words);
         }

Trade-offs

  • Fixes the factory path only: a caller of the internal WordlistLoader.getSnowballWordSet(Reader) who passes a Reader that still carries the mark gets the glued word, which matches the committers' view that the Reader-level parser is encoding-agnostic.
  • The parser's try-with-resources and the factory's both close the same BufferedReader; the second close() does nothing.
  • About 6 lines plus an import change (BufferedReader in, the unused Reader out).
  • Indexes built with the wrong set keep their terms until reindexed. No CHANGES entry is drafted.

Downstream note

#

Search servers that build analyzers from these factories inherit it whenever an operator edits a snowball-format words file in an editor that adds a byte order mark.

How it was found

#

A bounded-exhaustive check of the real factories: every words file of 1 to 3 lines over a small alphabet, each line-end style, with and without a leading byte order mark, compared with reference parsers from the javadoc (plus one unstated rule: drop a leading mark). All 43,380 snowball files with a mark differed; the same files in wordset, none.

The method in full215 words
  • Method (semi-formal): bounded-exhaustive translation validation of the resource-file formats that analysis factories load, on the stock main jars, in the hunt's unit on factory resource-file formats. Every words file of 1 to 3 lines over a per-format line alphabet, with LF, CRLF or CR line ends, with and without a trailing line end, with and without a leading mark, with ignoreCase on and off, loaded through StopFilterFactory from an in-memory ResourceLoader.
  • Oracle: independent reference parsers written from the format javadoc, without BufferedReader, trim or split, plus one rule no javadoc states: both drop one leading mark first (dropBom), taken from the default format's behaviour.
  • Signal. Snowball with a mark: all 43,380 generated files differ (28,548 with ASCII whitespace only, 14,832 with other whitespace, compared with the ASCII-whitespace reading that the same files without a mark match). Wordset with a mark, and snowball without one: 0 of those 43,380. Two-file lists: 35 of 35 for snowball, 0 of 35 for wordset. In a run that shadowed the parser fix together with a fix for an unrelated finding, every snowball class with a mark drops to 0.
  • The finder then traced it to the separate reader of the snowball path and wrote the public-API JUnit; independent checkers followed (see "Independent checks").

History

#

Introduced with the snowball format itself, SOLR-1860 (c880ef06478, 2012-02-05), which read the file with its own reader; in Lucene's jars since 4.0.0-BETA. A probe shows it on 132 of 132 targets from 4.0.0-BETA to 10.5.2 and main. Not fixed upstream.

Versions tested6 rows

Introduced by SOLR-1860 "support snowball format in stoplists" (JIRA "improve stopwords list handling"), by rmuir: trunk c880ef06478 and branch_3x 1a752ccc41f, both 2012-02-05, no PR. It added getSnowballWordSet(ResourceLoader, String, boolean) to Solr's factory base class with its own UTF-8 reader and wired it into the stop and common-grams factories. The default format's line loader had skipped a leading mark since SOLR-1865 (f3c25f02d58, 2010-05-08).

Into Lucene's jars. LUCENE-2510 / LUCENE-4044 moved the factory base class (2012-05-08, 0bad718d589) and the stop and common-grams factories (branch_4x 2012-07-25, 677846e6a0f; trunk 142d3c788fa); LUCENE-4257 moved getLines, skip included, into WordlistLoader the next day. First release 4.0.0-BETA (2012-08-10), first GA 4.0.0. SuggestStopFilterFactory (LUCENE-5820) joined in 5.0.0, KeepWordFilterFactory got format in 8.11.0 (LUCENE-10008). Outside Lucene's jars the same code first shipped in Solr 3.6.0 (read).

Not fixed upstream. Later commits to either method are moves, clean-ups and API changes (among them LUCENE-2564, LUCENE-4877, LUCENE-10003 and LUCENE-10349); none adds BOM handling. The cited files are unchanged through upstream main c5ab3e57b9ba (2026-10-28).

Bug record

LFV-718, snapshot of 2026-10-29

Registry title
With format="snowball", StopFilterFactory, KeepWordFilterFactory, CommonGramsFilterFactory and SuggestStopFilterFactory keep a leading UTF-8 byte order mark glued to the first word of the words file, so that word silently stops matching, while the default "wordset" format of the same factories strips the mark
Area
core + analysis-common + suggest / words-file factories (format="snowball" loader: AbstractAnalysisFactory.getSnowballWordSet, WordlistLoader.getSnowballWordSet)
Priority
Low, rank 414: With the opt-in format="snowball" and a words file that starts with a BOM, the first word silently stops matching, but the bundled lists lose no word, so it joins the rare analysis-factory drift rows right after LFV-510.
Impact class
silent wrong results
Impact note
Users who configure one of these factories with the opt-in format="snowball" and a words file that an editor saved with a UTF-8 byte order mark, and whose first line starts with a word, silently lose that word (a stop word is kept in the index, a keep word's tokens are dropped, a common word is not treated as common); a file that starts with a '|' comment line, as every bundled Snowball list does, loses no word and only gains a stray U+FEFF entry; no scale is needed and no error is raised.
Summary
You configure StopFilterFactory (or KeepWordFilterFactory, CommonGramsFilterFactory, CommonGramsQueryFilterFactory or SuggestStopFilterFactory) with format="snowball" and a UTF-8 words file that begins with a byte order mark, and expect the same words that the default "wordset" format reads from such a file, because that format skips a leading BOM (WordlistLoader.getLines, 'skip initial bom marker', a rule recorded in SOLR-1865). Instead the snowball loader keeps the invisible U+FEFF glued to the first word, so the set holds "\uFEFFthe" instead of "the" (getStopWords() = [a, \uFEFFthe, an]): StopFilter no longer removes 'the', KeepWordFilter drops the tokens of the first keep word, CommonGrams does not treat it as common, and a BOM before a comment or blank first line adds a stray "\uFEFF" entry. No error is raised.
Introduced
c880ef064789401f1351af56755ea165b3e04444 (SOLR-1860 'support snowball format in stoplists', trunk r1240784, rmuir) with its branch_3x twin 1a752ccc41f38c92d3cbf82f6341fb1d9a378cd3 (r1240791). It added the factory method getSnowballWordSet(ResourceLoader, String, boolean) (then in Solr's BaseTokenStreamFactory), which decodes each words file with its own UTF-8 InputStreamReader and passes it to WordlistLoader.getSnowballWordSet(Reader, CharArraySet). The default format went through ResourceLoader.getLines, which had skipped a leading BOM since SOLR-1865 (f3c25f02d58, 2010-05-08).
