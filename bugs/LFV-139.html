Dense FILTER/MUST + MUST_NOT queries silently drop every match in the last 4096-doc window of a segment near MAX_DOCS (int overflow in ReqExclBulkScorer)

On a segment of more than 2,147,479,552 documents, a MUST_NOT query whose dense FILTER/MUST side is bulk-scored in 4096-doc windows silently loses the last doc IDs: +*:* -b:y on a full MAX_DOCS segment counts 2,147,479,551 instead of 2,147,483,518. An int overflow in unreleased 10.6 code (#16669); a one-line fix.

The bug in 30 seconds

#

The bug is one line: WindowBits.applyMask adds the window start and 4096 in an int. For a window that starts at 2,147,479,552 or later, the sum passes 2^31 and wraps negative, so the method treats the window as empty and clears it.

Background: how a MUST_NOT query is scored in windows

#
  1. Doc IDs in a segment run from 0 to maxDoc - 1. One index holds at most IndexWriter.MAX_DOCS = 2,147,483,519 documents, just below 2^31 = 2,147,483,648, the first number a Java int cannot hold.
  2. For required -excluded with FILTER/MUST clauses (no SHOULD clause) that match more than 0.3% of the segment, ReqExclBulkScorer works in windows of 4096 doc IDs. For each window it marks the excluded documents, flips that into an "allowed" mask, and passes the mask to the required clause's scorer as its acceptDocs.
  3. The required clause's scorer (for *:*, or a constant-score filter such as a term or range) collects its own matches of a 4096-doc window into a bit set and calls acceptDocs.applyMask(bits, windowStart) to drop the documents that are not allowed.

The bug, step by step

#
  1. Index IndexWriter.MAX_DOCS = 2,147,483,519 documents into one segment with default settings; one of them has b:y.
  2. Count +*:* -b:y (MatchAllDocsQuery as FILTER, TermQuery b:y as MUST_NOT) with a plain IndexSearcher (query cache off). You expect 2,147,483,518: every document but one.
  3. You get 2,147,479,551 and no error: all 3,967 documents from doc 2,147,479,552 to the end are missing.
  4. Why: Lucene scores this query in windows of 4096 doc IDs and masks each window with the documents that are not excluded. The mask code adds the window start and 4096 in an int: 2,147,479,552 + 4,096 = 2,147,483,648 = 2^31, which wraps to -2,147,483,648. The window then looks empty, and all its matches are cleared.
  5. Only unreleased code has it: main and the 10.6 branch (10.6.0 RC1), since #16669. 10.5.2 returns the right count. A one-method test over the last 100 doc IDs of such a segment shows it in a second: 0 hits instead of 99.

Who is affected

#

Only an index with one segment of more than 2,147,479,552 documents, queried with MUST_NOT plus FILTER/MUST clauses that Lucene routes to the windowed bulk scorer (cost above 0.3% of the segment, no SHOULD clause) and bulk-scores with a constant-score scorer, such as *:*. Default settings. Counts, full collection and exact-count top-k are silently wrong. Unreleased: main and 10.6.

Mechanism, terms and numbers733 words

Since #16669 (merged 2026-09-24, unreleased), ReqExclBulkScorer scores required -excluded in windows of 4096 doc IDs and hands the required clause's bulk scorer a WindowBits mask of the documents that are not excluded. WindowBits.applyMask computes the end of the caller's 4096-bit set as Math.min(DocIdSetIterator.NO_MORE_DOCS, offset + bitSet.length()) in int (ReqExclBulkScorer.java:125 on main 645d4fe14a20). For a window that starts at 2,147,479,552 (2^31 - 4096) or later the sum wraps negative, the method sees an empty range and clears every bit. On a segment with more than 2,147,479,552 documents, a BooleanQuery that BooleanScorerSupplier routes to ReqExclBulkScorer (a MUST_NOT clause, a supplier cost above 0.3% of maxDoc, which for a single required clause is that clause's cost, and FILTER/MUST clauses with no SHOULD clause) and whose required side is bulk-scored by DenseConjunctionBulkScorer or ConstantScoreBulkScorer (for example *:*) therefore silently loses up to the last 3,967 doc IDs: end to end, +*:* -b:y on one segment of IndexWriter.MAX_DOCS documents counts 2,147,479,551 instead of 2,147,483,518, with assertions on and off. main, branch_10x and branch_10_6, including the 10.6.0 RC1 revision, are affected; 10.5.2 and every older release are correct. MathUtil.unsignedMin(DocIdSetIterator.NO_MORE_DOCS, offset + bitSet.length()) fixes it.

Terms

#
  • ReqExclBulkScorer: the bulk scorer for "required minus excluded". Since #16669 it collects the excluded documents of each 4096-doc window into a bit set, flips it into an accept mask, and passes a WindowBits (a Bits over that mask) as acceptDocs to the required clause's bulk scorer (ReqExclBulkScorer.java:54-93, :86). Its own window end is computed in long: (int) Math.min((long) max, (long) windowMin + WINDOW_SIZE) (:61).
  • Bits#applyMask(FixedBitSet bitSet, int offset): clears bit i of bitSet when document offset + i is not accepted (util/Bits.java:39-72).
  • When the bulk path is used: BooleanScorerSupplier.java:203-207 returns no bulk scorer when there is a MUST_NOT clause and the supplier's cost() is at most 3L * maxDoc / 1000 (then the iterator-based ReqExclScorer runs and is correct). That cost is the supplier's estimate for the positive side (with required clauses and no minShouldMatch, the cost of the cheapest required clause, :82-101); for a single required clause it is that clause's cost. Otherwise, if the clause shape has a positive bulk scorer (FILTER/MUST clauses get requiredBulkScorer only with no SHOULD clause and minShouldMatch 0, :235-236), :265 returns new ReqExclBulkScorer(positiveScorer, prohibitedScorer). The bug then needs that bulk scorer to call applyMask on a window at 2^31 - 4096 or later; not every MUST_NOT query with a dense required side meets both conditions.
  • The callers: constant-score clauses get DenseConjunctionBulkScorer when they match at least 1/32 of maxDoc, else ConstantScoreBulkScorer when scores are not needed (ConstantScoreScorerSupplier.java:78-99); MatchAllDocsQuery (MatchAllDocsQuery.java:48), TermQuery without scores (TermQuery.java:168-173), PointRangeQuery, FieldExistsQuery and the multi-term constant-score wrapper use it. Both scorers call acceptDocs.applyMask(windowMatches, windowBase) on a 4096-bit set (ConstantScoreBulkScorer.java:142, DenseConjunctionBulkScorer.java:283).

The bug

#

ReqExclBulkScorer.java:124-145:

  1. :125 int bitSetEnd = Math.min(DocIdSetIterator.NO_MORE_DOCS, offset + bitSet.length()); With offset = 2,147,479,552 and length 4096 the sum is 2,147,483,648 = 2^31, which wraps to -2,147,483,648. Math.min with NO_MORE_DOCS (Integer.MAX_VALUE) cannot change an int, so it does not guard anything.
  2. :127 from = Math.max(windowBase, offset) is about 2.1 billion; :128 to = Math.min(windowEnd, bitSetEnd) is negative.
  3. :129-131 if (from >= to) { bitSet.clear(); return; } clears all 4096 bits: every match of that window is gone.

A Z3 bit-vector (32-bit) model of the bounds gives 2,147,479,552 as the smallest failing offset for a 4096-bit set. Under the model's preconditions (a set of 1 to 4096 bits, 0 <= windowBase <= offset < windowEnd <= MAX_DOCS) it proves that the upper bound to equals the exact min(windowEnd, offset + bitSet.length()) whenever offset + bitSet.length() <= Integer.MAX_VALUE, and that the overflow case takes the bitSet.clear() branch although the window is not empty. The model covers the bounds only, not the clear and andRange part of the method.

The numbers

#

Only doc IDs 2,147,479,552 to MAX_DOCS - 1 = 2,147,483,518 can be lost: 3,967 per segment and query at most. Over *:* the windows start at multiples of 4096 (the last at 524,287 x 4,096 = 2,147,479,552), so all 3,967 are lost: the end-to-end count is 2,147,479,551 instead of 2,147,483,518. A ConstantScoreBulkScorer window starts at its first match, so it loses the matches of any window that starts at 2,147,479,552 or later; a window that starts below that is correct.

Exposure and likelihood260 words
  • Who is exposed. An index with one segment of more than 2,147,479,552 documents. IndexWriter.MAX_DOCS = 2,147,483,519 limits the whole index (IndexWriter.java:201-208), so such a segment leaves room for at most 3,966 documents in all other segments together.
  • Which queries. A BooleanQuery that BooleanScorerSupplier routes to ReqExclBulkScorer (a MUST_NOT clause, a supplier cost() above 3L * maxDoc / 1000, which for a single required clause is that clause's cost, and a positive bulk scorer, such as FILTER/MUST clauses with no SHOULD clause), and whose FILTER or MUST side is bulk-scored by DenseConjunctionBulkScorer or ConstantScoreBulkScorer. Executed with *:* as FILTER and as MUST. By code reading also a single constant-score filter such as a term, point range or exists query (not executed).
  • Default configuration. Default IndexWriterConfig, codec and IndexSearcher; assertions on or off; single thread, no race.
  • What is wrong. Counting and exhaustive collection, and an exact-count top-10 search (TopScoreDocCollectorManager(10, Integer.MAX_VALUE) with MUST *:*: totalHits 2,147,479,551 instead of 2,147,483,518). Silent: no exception. The query itself never returns an excluded or deleted document; the method only clears bits.
  • Not affected. A sparse required side (the iterator-based ReqExclScorer runs): a legal end-to-end run with FILTER a:x on the last 100 documents passes. Every release.
  • Not tested. IndexSearcher#count, and the other applyMask callers that could receive a WindowBits (MaxScoreBulkScorer.java:246, BooleanScorer.java:149).
  • How likely: contrived. The trigger needs a single segment within 3,966 documents of the limit, which is expected to be rare. The point of fixing it now is that 10.6.0 would otherwise ship it.

Why it is a bug, not intended

#
  • MUST_NOT means "must not appear in the matching documents" and FILTER is "Like MUST", so +*:* -b:y must match all documents without b:y.
  • Math.min(NO_MORE_DOCS, offset + 4096) does nothing on an int: it looks like an overflow cap missing its widening.
  • #14750 added MathUtil.unsignedMin for exactly this window overflow; both callers here use it for their own window ends.
The full argument323 words
  • Contracts. BooleanClause.java:58: MUST_NOT is for clauses that "must not appear in the matching documents"; :35: FILTER is "Like MUST except that these clauses do not participate in scoring". Bits#applyMask (Bits.java:39-63) requires a non-negative offset and that set bits map below length(), and "Apart from that, this should behave the same way as the default implementation", which clears bit i only when document offset + i is not accepted. The failing calls meet both preconditions (offset 2,147,479,552; every set bit below MAX_DOCS).
  • The limit. IndexWriter.MAX_DOCS = Integer.MAX_VALUE - 128, "Hard limit on the maximum number of documents that may be added to the index" (IndexWriter.java:201-208). The end-to-end index was built with default settings inside it.
  • The code appears to cap the sum. Math.min(DocIdSetIterator.NO_MORE_DOCS, x) cannot change an int x. The otherwise redundant cap at :125 is consistent with an intended overflow guard missing its long widening; this is an inference, since the #16669 discussion never mentions overflow. score() in the same class widens its own window end (:61).
  • The project fixes this pattern elsewhere. #14750 (2025-06-03) added MathUtil.unsignedMin because dividing the doc-ID space into windows "is prone to integer overflows if the size of the window is greater than Integer.MAX_VALUE - windowStart". BitSetDocIdStream.java:34 uses it on the same expression, MathUtil.unsignedMin(Integer.MAX_VALUE, offset + bitSet.length()), and so do both callers here for their own window ends (ConstantScoreBulkScorer.java:132, DenseConjunctionBulkScorer.java:198, :214).
  • History. #16669 ("Use intoBitSet to speed up ReqExclBulkScorer with dense exclusions", the PR title, also the title of performance issue #16668 and of its CHANGES.txt entry under 10.6.0; the commit subject drops "with dense exclusions") is a speed-up. Its 9 comments, 2 reviews and 4 review comments never mention overflow, and its test testWindowBitsApplyMask uses offsets 96 to 108 (TestReqExclBulkScorer.java:263-293). The parent commit and the seven releases run return the right result; no release contains WindowBits.
The devil's-advocate check119 words

The strongest case for "not a bug": the classes are package-private, Bits is @lucene.experimental (Bits.java:24), and nobody runs a segment within 3,967 documents of 2^31, so this is an unsupported corner.

Why it fails: the observable contract is the public BooleanQuery semantics, not the internal class; the trigger is a legal index built with defaults, inside the only documented limit; and the code points to an intended cap (the otherwise no-op Math.min, the long at :61, the unsignedMin siblings; an inference). The argument limits impact, not correctness. The reviewers from another model family rated the intended-behaviour case weak; the independent reproducer, the devil's advocate and the adjudication reached the same conclusion without giving a rating.

Suggested fix

#

Recommended MathUtil.unsignedMin (validated)

Compute the end in unsigned arithmetic, as the sibling scorers do: int bitSetEnd = MathUtil.unsignedMin(DocIdSetIterator.NO_MORE_DOCS, offset + bitSet.length()); in WindowBits.applyMask, plus the import. The test then passes, and so do the 2,340 tests of org.apache.lucene.search.

    public void applyMask(FixedBitSet bitSet, int offset) {
      int bitSetEnd = MathUtil.unsignedMin(DocIdSetIterator.NO_MORE_DOCS, offset + bitSet.length());

Guard at the callers (not recommended, not built)

Make ConstantScoreBulkScorer and DenseConjunctionBulkScorer avoid sets that reach past 2^31.

Trade-offs

Downstream note

#

On its own the query only loses matches, but a result reused as an exclusion turns that around: in a partial check, a +A -B deny clause cached by an application-configured LRUQueryCache and used as MUST_NOT let through 3,967 documents it should hide (the default cache does not cache such a segment).

How it was found

#

Code reading while modelling the Bits#applyMask contract across its implementations (bit sets, live docs, acceptDocs). A Z3 bit-vector model of the bounds found the smallest failing window start, 2,147,479,552, and proved the bound exact below it, under the model's preconditions. A same-package JUnit and a legal end-to-end run on a MAX_DOCS segment confirmed it.

The method in full201 words

Method: semi-formal (the hunt's hunt unit on bit sets, live docs and acceptDocs, main ea57360912ed, 2026-10-25).

  • Lead. Reading the Bits#applyMask implementations against the contract: WindowBits adds offset + bitSet.length() in int. (The intended-behaviour checker later confirmed that the other implementations cannot overflow: FixedBitSet computes length() - offset, and DenseLiveDocs and SparseLiveDocs compute maxDoc - offset.)
  • Z3. A 32-bit bit-vector model of the bounds, under the preconditions of a set of 1 to 4096 bits and 0 <= windowBase <= offset < windowEnd <= MAX_DOCS: O3 is a counterexample with the smallest failing offset 2,147,479,552 for a 4096-bit set; O3s proves that the bound to equals the exact min(windowEnd, offset + n) whenever offset + n <= Integer.MAX_VALUE; O3c proves the overflow case takes the bitSet.clear() branch although the window is not empty. The model does not cover the clear and andRange part of the method.
  • Execution. A same-package unit test (the required clause on the last 100 doc IDs, controls 8192 docs lower pass) and a legal end-to-end run on one segment of IndexWriter.MAX_DOCS documents, both with -ea and -da. A sparse end-to-end run that takes the ReqExclScorer path passes, as the code predicts.

Checks and verdicts343 words

LFV-139, snapshot of 2026-10-30

Registry title
ReqExclBulkScorer.WindowBits.applyMask adds offset + bitSet.length() in int, so FILTER/MUST + MUST_NOT queries silently drop every match in a 4096-doc window based at doc 2^31-4096 or above (up to the last 3,967 doc IDs of a segment near IndexWriter.MAX_DOCS)
Area
search / BooleanQuery MUST_NOT bulk scoring (ReqExclBulkScorer)
Priority
Low, rank 779: An unreleased regression from #16669 silently drops the last 4096-doc window of dense MUST_NOT queries, but only on segments within 3,967 docs of MAX_DOCS; worth fixing before 10.6 ships but practically unreachable.
Impact class
silent wrong results
Impact note
Holders of one segment with more than 2,147,479,552 documents (within 3,967 docs of IndexWriter.MAX_DOCS, for example a full index force-merged to one segment) who run a BooleanQuery with a MUST_NOT clause and a FILTER/MUST side that costs more than 0.3% of maxDoc and is bulk-scored by ConstantScoreBulkScorer or DenseConjunctionBulkScorer (for example +: -b:y; counting and exhaustive collection, and per the independent reproduction also an exact-count top-k search) silently lose the matches of the last 4096-doc window (all 3,967 docs end to end) with the default IndexWriterConfig, codec and IndexSearcher, under -ea and -da; extreme scale; an unreleased regression from #16669 (main, branch_10x, branch_10_6; 10.5.2 is correct).
Summary
You index one segment of IndexWriter.MAX_DOCS (2,147,483,519) documents with default settings, one of which has b:y, and count the matches of +: -b:y (MatchAllDocsQuery as FILTER plus a MUST_NOT term query) with a plain IndexSearcher; you expect 2,147,483,518. Instead you get 2,147,479,551: all 3,967 documents of the last window [2,147,479,552, MAX_DOCS) are silently missing, because ReqExclBulkScorer's WindowBits.applyMask computes Math.min(NO_MORE_DOCS, offset + bitSet.length()) in int, the sum wraps negative for a 4096-bit window based at 2^31-4096 or above, and the method then clears the whole window. Only segments with more than 2,147,479,552 documents and required clauses denser than 0.3% of maxDoc are affected, and only unreleased code (main and the 10.x / 10.6 branches since #16669) has the bug.
