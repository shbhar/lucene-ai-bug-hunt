Classic Highlighter returns null for text that contains the query term when QueryScorer or QueryTermScorer was given an IndexReader without documents: the IDF weight is -Infinity for maxDoc 0 (1.9 to 10.6.0, branch_11x and main)

An old corner of the classic Highlighter: given a scorer whose optional IndexReader holds no document, getBestFragment returns null for text that contains the query term, with no exception. A reader with any document is not affected, so highlighting the stored text of that reader's hits cannot reach it.

The finding in 30 seconds

#

The scorer multiplies each query term's weight by an IDF factor computed from the reader. For a reader without documents the factor is log(0) + 1, which is -Infinity. The fragment then scores -Infinity, and the Highlighter drops every fragment whose score is not above 0.

Background: three pieces

#
  1. The classic Highlighter takes a text and a query. It splits the text into fragments, scores each fragment by the query terms found in it and returns the best one with the terms marked up: <B>alpha</B> beta.
  2. The scores come from a scorer, QueryScorer or the older QueryTermScorer. Each query term has a weight, and a fragment's score is the sum of the weights of the query terms it contains. Without a reader the weight of a plain term is 1.0.
  3. Both scorers take an optional IndexReader. With it, each weight is multiplied by an IDF factor, so that terms that are rare in the index count more. maxDoc() counts the documents in the reader's segments; docFreq is how many of them contain the term.

The finding, step by step

#
  1. Create an index and add no document. Open a reader on it: maxDoc() is 0. Build new Highlighter(new QueryScorer(query, reader, "f")) for a TermQuery on alpha. The reader argument is optional: it asks for IDF weights, so that rare terms count more.
  2. Call getBestFragment(analyzer, "f", "alpha beta"). You expect <B>alpha</B> beta. The same call returns it without the reader argument, and with a reader that holds one document.
  3. You get null. No exception, with assertions on or off. QueryTermScorer(query, reader, "f") gives the same.
  4. Why: the scorer multiplies the term's weight by log(maxDoc / (docFreq + 1)) + 1. With maxDoc 0 and docFreq 0 that is log(0 / 1) + 1 = -Infinity. The weight 1.0 becomes -Infinity, so does the fragment's score, and Highlighter keeps only fragments with a score above 0.
  5. With one document in the reader the factor is 1.0 (the document does not contain alpha) or 0.30685282 (it does), and the fragment is returned. So only a reader without documents is affected. A search hit implies a document in its reader, so highlighting a hit's stored text with that reader cannot reach this.

Who is affected

#

Only applications that pass the optional reader to the classic Highlighter's scorer and highlight text while that reader holds no document (maxDoc() 0): a new index, an index whose documents were all deleted, an empty MultiReader. One document of any content ends it. The highlight is missing: no exception, no wrong search result, nothing lost.

Mechanism, terms and numbers1,035 words

Small and old. The classic Highlighter (org.apache.lucene.search.highlight) scores text fragments with a scorer, QueryScorer or the older QueryTermScorer. Both have constructors that take an optional IndexReader, documented as the source of IDF weights. With a reader, each query term's weight is multiplied by idf = log(reader.maxDoc() / (docFreq + 1)) + 1: the same statement at WeightedSpanTermExtractor.java:558 (behind QueryScorer) and at QueryTermExtractor.java:79 (behind QueryTermScorer), lines at main 9965d34e3c77. For a reader without documents maxDoc() and docFreq are 0, the factor is log(0 / 1) + 1 = -Infinity, and the term's weight (1.0 for a plain term), the score of the matching token and the score of every fragment that holds a matching token are -Infinity (other tokens and fragments score 0). SimpleHTMLFormatter, the default formatter, leaves a token without mark-up when its score is not above 0, and Highlighter keeps only fragments with a score above 0 (Highlighter.java:145, :302). So getBestFragment returns null and getBestFragments an empty array, although the text contains the query term and getBestFragment is documented to return null only "if no terms found". Nothing is thrown, with assertions on or off. The trigger is exactly maxDoc() == 0: a new index (an application may call it an empty shard), an index whose documents were all deleted (under the default configuration fully deleted segments are dropped, so no merge call is needed; also through a near-real-time reader) or that was cleared with deleteAll, an empty MultiReader. With one or more documents the factor is at least log(1/2) + 1 = 0.30685282, because docFreq <= maxDoc in Lucene's readers, and the fragment is returned; so text that is the stored field of a hit of the same reader cannot reach it. The one test fails on builds of main 9965d34e3c77, of branch_11x 9d2b5a15427a and daa54f2e0cd3 and on the 10.6.0 release jars, and earlier runs cover every release from 1.9.1 on: the option and the defect are the same age (2004, first released in 1.9). The code comment at both statements says the formula is ClassicSimilarity's; that class has used log((docCount + 1) / (docFreq + 1)) + 1 since 6.0.0, with docCount the number of documents that have the field; it is 1.0 when both counts are 0. Two small remedies were run: a guard for maxDoc() 0, or the similarity's expression, with maxDoc in it, at both statements.

Which readers have maxDoc() 0 (each run on main 9965d34e3c77, both scorers: null)

#
  • a new index: IndexWriter with the default IndexWriterConfig, closed without a document;
  • new MultiReader(), a reader without sub-readers;
  • an index whose two documents were both deleted by term, default configuration, no merge call: the near-real-time reader and the reader after the commit;
  • an index that held two documents and was cleared with IndexWriter.deleteAll.

An application may call the first of these an empty shard: the same state, not run under that name. A segment that is kept although its documents are all deleted still counts in maxDoc() and does not trigger (run with a merge policy that never merges and keeps such segments, which is not the default: maxDoc() 1, numDocs() 0, factor 0.30685282, the fragment is returned).

Why it looks unintended

#
  • getBestFragment is documented to return null "if no terms found". Here the term is in the text.
  • The reader is documented as a source of weights ("to use for quasi tf/idf scoring"). Without it, or with one document, the same call highlights.
  • Lucene's own test for LUCENE-1355 (2008) asserts the fragment where deletes once gave a non-positive idf and null.
The full argument396 words
  • The return value's contract (javadoc read at 9965d34e3c77). Highlighter.java:71 and :92: "@return highlighted text fragment or null if no terms found". The text alpha beta contains the query term alpha.
  • The reader's documented role. QueryScorer.java:74 and :82: "@param reader {@link IndexReader} to use for quasi tf/idf scoring". QueryTermScorer.java:64-65: "@param reader used to compute IDF which can be used to a) score selected fragments better b) use graded highlights eg set font color intensity" (QueryTermExtractor.java:66-67 has the same sentence, ending "eg changing intensity of font color"). Weights for ranking fragments and for graded mark-up; nothing says that adding the reader can remove the highlight.
  • No precondition is documented. No javadoc of the two scorers, the two extractors, Highlighter or the package asks for a reader with documents or ties the text to the reader. The text is a String or a TokenStream.
  • The same call without the reader, or with one document, highlights (run): QueryScorer(query, "f") returns <B>alpha</B> beta, and so does QueryScorer(query, reader, "f") for a reader with one document.
  • Lucene treated this consequence as a bug before, for another input. LUCENE-1355 (#2432, 2008, fixed in 2.4), as Mark Miller reported it: with deletes the document count could be lower than docFreq, and "this causes the idf to be negative and the fragment to score < 0". Its regression test is still there: TestHighlighter.testWeightedTermsWithDeletes (TestHighlighter.java:2139-2188) carries the comment "This scorer can return negative idf -> null fragment" (:2174) and asserts the fragment (:2185). LUCENE-4289 (#5357, 2012, fixed in 3.6.2 and 4.0) then replaced numDocs by maxDoc at both statements.
  • The formula's source was made finite for a count of 0. The comment at both statements reads "IDF algorithm taken from ClassicSimilarity class". LUCENE-6758 (#7816, 2015, fixed in 6.0) changed that class's formula to log((docCount + 1) / (docFreq + 1)) + 1 (CHANGES: "Use docCount+1 for DefaultSimilarity's IDF, so that queries containing nonexistent fields won't screw up querynorm"; ClassicSimilarity.java:67-71). There the count is the number of documents that have the field, which is 0 for a field no document has, and the issue is about the query norm: an analogy in the arithmetic, not the same defect. The expression is 1.0 when both counts are 0. The highlighter's two copies kept the older form.
The devil's-advocate check284 words

The strongest case for "works as designed": the reader is opt-in weighting against a corpus, and an IDF over no documents has no meaning, so a caller who asks for it gets an undefined weight. The classes are written for search hits (QueryScorer.java:36: "only those terms that participated in generating the 'hit' on the document"), and a hit implies a document. Highlighter drops fragments without a positive score on purpose, and null is a documented return value. And on LUCENE-6758 Robert Muir wrote: "Previously maxDoc was used, which was always assumed to be a positive integer... but docCount can be zero."

Why it fails: none of this is a documented precondition. The words about a hit also stand on the two extractor methods that take no reader (WeightedSpanTermExtractor.java:493, :507), which highlight any text without any index; they describe the usual use and restrict nothing. Null is documented for "no terms found", and here the term is found. The sentence of 2015 is the reason the similarity's formula was changed in that same issue, so that a count of 0 gives a finite value. And Lucene's own test pins it for one input (deletes): there a non-positive idf must not turn a match into null. No test states a general rule. What is left of the argument is about weight, not about correctness: the state is rare and the loss is a highlight. A maintainer may answer that nobody highlights against an index without documents, that this class is "Lucene's original Highlighter; there are others" (Highlighter.java:35), and that a caller can leave the reader out; that would be a fair answer, and this page says the limit first.

Suggested fix

#

Recommended A. A guard for a reader without documents: factor 1 when maxDoc() is 0 (validated)

Guard the reader without documents at the two IDF statements: when maxDoc() is 0, keep the query weight (factor 1). 2 files, 10 lines added, 2 removed. Validated: the test passes, and the 731 tests of the highlighter module and its lint pass. The other option, the similarity's expression with maxDoc, was run too. The choice is the maintainers'.

Trade-offs

  • Smallest change. No weight changes for any reader that holds a document.

  • Not benchmarked. One comparison per query term: once per highlighted text behind QueryScorer, once per scorer behind QueryTermScorer, which computes its weights in its constructor.

How it was found

#

Not formal. Entry points of Lucene's modules were being run on a reader without documents and compared with the same call on a reader that holds documents. An inventory of the public signatures that take an IndexReader, made by scanning the built jars, named the two scorers. The IDF line was read, run and reduced to one test.

The method in full111 words

Method: non-formal (a static scan confirmed by running, inside a differential sweep; no formal tool was involved).

  • Signal. An inventory of the public signatures of Lucene's modules that take an IndexReader, made by scanning the built jars, named the two reader-taking scorers.
  • Differential sweep. Module entry points were called on degenerate index shapes: a reader without a segment against the same call on a reader with three documents.
  • Reading, then running. The IDF statement was read, a small program confirmed null and the weight -Infinity from the public QueryTermExtractor.getIdfWeightedTerms for a term, a phrase and a boolean query with both scorers, and the case was reduced to one JUnit test.

Registry title
Classic Highlighter returns no fragment (null) for text that contains the query term when QueryScorer or QueryTermScorer was given an IndexReader without documents: the IDF weight log(maxDoc / (docFreq + 1)) + 1 is -Infinity for maxDoc 0, so every fragment that holds the term scores -Infinity and no fragment is kept; every release from 1.9 to 10.6.0, branch_11x and main
Area
highlighter / classic Highlighter (IDF-weighted term scoring: QueryScorer and QueryTermScorer with an IndexReader)
Priority
Low, rank 591: The classic Highlighter silently returns null instead of the highlighted fragment while the IndexReader given to QueryScorer or QueryTermScorer for IDF weighting holds no document at all, in every release since 1.9. It is Low because the reader argument is optional and the trigger is exactly an empty reader, so highlighting a hit of the same reader cannot reach it, and nothing is lost or wrong beyond the missing highlight.
Impact class
minor
Impact note
Applications that give the classic Highlighter's QueryScorer or QueryTermScorer an IndexReader for IDF weighting get no highlight (null, no exception) for any text while that reader holds no document at all (maxDoc() 0): a newly created index (an application may call it an empty shard), an index whose documents were all deleted (under the default configuration fully deleted segments are dropped, so no merge call is needed; also through a near-real-time reader) or that was cleared with deleteAll, or an empty MultiReader; it needs the default configuration, the optional reader argument of the scorer and no scale, and is the same with -ea and -da [exec]; a reader with one or more documents is not affected, so highlighting the stored text of a hit of the same reader cannot reach it, and nothing is lost, thrown or wrong beyond the missing highlight.
Summary
You create a Highlighter with new QueryScorer(query, reader, field), or new QueryTermScorer(query, reader, field), where the reader is an index that holds no document, and call getBestFragment on the text 'alpha beta' for a TermQuery on alpha. You expect '<B>alpha</B> beta', which the same call returns without the reader argument or with a reader that holds a document: the reader is documented as the source of IDF weights for scoring fragments, and getBestFragment is documented to return null only 'if no terms found'. Instead it returns null, with no exception: for maxDoc() 0 the IDF factor log(maxDoc / (docFreq + 1)) + 1 is -Infinity, so the term's weight and the score of every fragment that holds the term are -Infinity, and Highlighter keeps only fragments with a score above 0. Every release since 1.9 does it, and it shows only while the reader holds no document at all.
