MoreLikeThis keeps its lowest-scoring selected terms when its query hits the boolean clause limit

When MoreLikeThis selects more terms than a BooleanQuery may hold (1024 by default), it truncates the query but keeps the lowest-scoring terms: of 1100 selected terms, the 76 it drops are exactly the 76 best. A silent regression since 4.10.0 that needs maxQueryTerms above the clause limit.

The bug in 30 seconds

#

MoreLikeThis turns a text into a query made of its most interesting terms. When it picks more terms than a BooleanQuery may hold, it shortens the query instead of failing, but it cuts off the wrong end.

  1. Run MoreLikeThis.like(...) on a like-text of 1100 words that all have the same idf: 76 words occur twice (score 2), the other 1024 once (score 1). Set maxQueryTerms to 1100; the clause limit stays at its default, 1024.
  2. The query can hold only 1024 clauses, so 76 terms must go. You expect the 76 weakest to go and all 76 score-2 words to stay. With maxQueryTerms 1024 that is what you get.
  3. You get 1024 clauses and none of the 76 score-2 words: the terms left out are exactly the best ones. No error. MoreLikeThisQuery and the XML LikeThisQuery do the same.
  4. Why: the term queue hands out the lowest score first. createQuery adds one clause per term in that order and stops at the first TooManyClauses, so everything still in the queue, the best terms, is dropped.
  5. Each step of maxQueryTerms above 1024 drops one more of the best terms: 75 kept at 1025, 50 at 1050, none from 1100 on. Up to 4.9.1 the queue was best-first and the same stop kept the best terms.

Who is affected

#

Applications that set maxQueryTerms above the clause limit (1024) and run MoreLikeThis on long texts, through MoreLikeThis, MoreLikeThisQuery or the XML LikeThisQuery, or that lower the global clause limit. The defaults (25, 5 and 20 terms) never reach it. Every such call is hit, silently; only relevance changes.

Mechanism, terms and numbers537 words

MoreLikeThis builds a query from the most interesting terms of a text: it scores each candidate by tf*idf and keeps the best maxQueryTerms in a priority queue. A BooleanQuery may hold at most IndexSearcher.getMaxClauseCount() clauses (1024 by default), so when more terms are selected, createQuery catches TooManyClauses and returns the clauses it has. It fills the query by popping the queue, and since 4.10.0 the queue pops the lowest score first, so the clauses that fit are the weakest terms and the best ones are dropped. With 1100 selected terms, 76 of them scoring twice the others, the 1024-clause query holds none of the 76; with maxQueryTerms 1024 it holds all of them. It happens through MoreLikeThis.like(...), MoreLikeThisQuery and the XML query parser's LikeThisQuery, with assertions on and off, and only when more terms are selected than the clause limit (the defaults, 25 terms and 1024 clauses, never reach it). LUCENE-5795 (2014) flipped the queue order for a faster top-N selection and kept the old loop, which up to 4.9.1 kept the best terms. Skipping the lowest-scoring terms that cannot fit before building the query (+11 lines) fixes it, and the whole queries module passes with that change.

Terms

#
  • MoreLikeThis (lucene-queries, org.apache.lucene.queries.mlt) finds documents similar to a source: a like-text, a document id or a field map. It scores every candidate term of the source by tf * idf and keeps the best maxQueryTerms (default 25) as SHOULD clauses of a BooleanQuery.
  • The clause limit: a BooleanQuery.Builder refuses more than IndexSearcher.getMaxClauseCount() clauses (1024 by default) and throws IndexSearcher.TooManyClauses.

The bug

#
  1. createQueue keeps the top min(maxQueryTerms, #eligible terms) terms (eligible: passing the minTermFreq, minDocFreq and maxDocFreq filters) in a bounded priority queue whose top is the lowest score (MoreLikeThis.java:624-677, comparator at :628-629). The selection is right.
  2. createQuery pops that queue, so it sees the terms lowest score first, and adds a SHOULD TermQuery per term (:593-616).
  3. After 1024 clauses the builder throws (BooleanQuery.java:82-84), and createQuery does catch (IndexSearcher.TooManyClauses _) { break; } (:611-613). Every term still in the queue, the highest-scoring ones, is dropped.
  4. So whenever more terms are selected than the clause limit, the query loses the best #selected - limit terms. No exception, no warning.

Up to 4.9.1 the queue popped the best term first (FreqQ.lessThan returned fa > fb), so the same break kept the best terms. LUCENE-5795 (4.10.0) made the queue lowest-first to bound it cheaply and kept the loop.

Exposure and likelihood277 words
  • Who. Applications that let MoreLikeThis select more terms than the global clause limit: maxQueryTerms above 1024 on a source with more than 1024 eligible terms, through MoreLikeThis.setMaxQueryTerms, MoreLikeThisQuery.setMaxQueryTerms (rewritten by IndexSearcher) or the XML query parser's LikeThisQuery, whose maxQueryTerms attribute comes from the query text; or a global limit lowered below the selection size (IndexSearcher.setMaxClauseCount is public).
  • Not by default. The defaults are 25 terms (MoreLikeThis), 5 (MoreLikeThisQuery) and 20 (XML LikeThisQuery). The other in-tree users, the classification module's k-nearest-neighbour classifiers and Luke, never set maxQueryTerms, so they are reached only if the global limit is below 25.
  • Eligible terms. By default a term must occur at least twice in the source and in at least 5 documents, and a field without term vectors is parsed up to 5,000 tokens, so the trigger needs long sources, several fields (the queue counts terms over all fields) or relaxed filters.
  • Effect. Every such call returns a query built from the least interesting selected terms; the best #selected - 1024 terms are lost. The result is non-monotonic: asking for more terms makes the query worse. The query can give worse "more like this" relevance (no relevance benchmark was run): other terms change which documents match as well as how they rank, and MoreLikeThisQuery also sets minimumNumberShouldMatch from the clause count. Nothing fails, nothing is corrupted, and the query never exceeds the clause limit.
  • How likely. Rare: large maxQueryTerms values are unusual, and no report was found since 4.10.0 (2014). Anyone configured that way is hit on every long source without any sign, so the absence of reports is weak evidence.

Why it is a bug, not intended

#
  • Up to 4.9.1 the same loop kept the best terms; LUCENE-5795 (4.10.0) flipped the queue order for speed, without discussing the clause limit.
  • The class aims to "maximize a tf*idf score" and truncates on purpose, so the truncated query should keep the best terms.
  • Asking for more makes it worse: maxQueryTerms 1024 keeps all 76 best terms, 1100 none.
The full argument267 words
  • Purpose. The class javadoc: "Since you're trying to maximize a tf*idf score, you're probably most interested in terms with a high tf" (MoreLikeThis.java:63-64), and "return a set of representative terms" (:79).
  • Best-first wording. The private retrieveTerms(Reader, String) returns "the most interesting words in the document ordered by score, with the highest scoring, or best entry, first" (:875-876), the order the createQuery loop was written for; stale since LUCENE-5795. retrieveInterestingTerms: "we just want to return the top words" (:895, :920).
  • The limit was anticipated. DEFAULT_MAX_QUERY_TERMS: "Return a Query with no more than this many terms." with @see IndexSearcher#getMaxClauseCount (:225-232); createQuery catches TooManyClauses and returns the query it has (:609-615).
  • History. From the first check-in (2005) to 4.9.1 the queue popped best-first; LUCENE-5795 is listed under 4.10.0 "Optimizations": "MoreLikeThisQuery now only collects the top N terms instead of collecting all terms from the like text when building the query." (lucene/CHANGES.txt:11932-11934). Its 9 comments discuss the bounded queue, its struct, the added test and the commits; none mentions the pop order or the clause limit. Swapping only MoreLikeThis.java flips the result both ways on 4.9.1 and 4.10.0.
  • Core precedent. TopTermsScoringBooleanQueryRewrite "only uses the top scoring terms so it will not overflow the boolean max clause count" and caps its size at getMaxClauseCount() (MultiTermQuery.java:146-169).
  • Tests. No lucene/queries test reaches TooManyClauses in MoreLikeThis; testTopN uses 25 terms under 1024. testSmallSampleFromCorpus asserts the lowest-first clause order and testCustomFrequency relies on the lowest-score boost normalisation; the recommended fix keeps both, and both pass with it.
The devil's-advocate check315 words

The strongest works-as-designed case (the independent reproducer, the devil's advocate, the cross-model reviews and the adjudication): setMaxQueryTerms promises only a maximum ("the maximum number of query terms that will be included in any generated query"), and DEFAULT_MAX_QUERY_TERMS points at getMaxClauseCount, which could mean "keep maxQueryTerms at or below the clause limit". The catch could be just a heap backstop: BooleanQuery.Builder.add says its check exists "to prevent run-away 'rewriting' of bad queries from creating BQ objects that might eat up all the Heap". @jpountz wrote in #8931 (LUCENE-7880, a thread asking to allow more clauses per query): "I think of the max clause count as something that should never be changed. What is the use-case for having more than 1024 clauses?" That question arguably applies to the main trigger itself (maxQueryTerms above 1024). And upstream tests encode the ascending clause order.

Why it fails: no javadoc says values above the limit are unsupported, the setter accepts them, and the code chooses to return a truncated query. Up to 4.9.1 the same code kept the best terms, and the change came with an optimisation whose discussion never covered it. Asking for 1100 terms instead of 1024 removes all 76 best ones, which is hard to defend for a class that exists to choose the most interesting terms. The #8931 remark is about changing the limit at all, in a thread about raising it; this bug needs neither: the main trigger leaves the limit at its default, the query stays at 1024 clauses, and createQuery deliberately truncates instead of rejecting, so the only question is which 1024 terms survive. Clause order does not change matching, and the fix keeps it anyway. Verdict: not intended; a regression from LUCENE-5795. The issue should say that the expectation comes from the class's purpose, the pre-4.10 behaviour and the best-first javadoc, not from an explicit promise about the clause-limit path.

Suggested fix

#

Recommended A: skip the lowest-scoring terms that cannot fit (createQuery)

In createQuery, first pop and skip the lowest-scoring terms that cannot fit under the clause limit, then build the query as today (+11 lines). Clause order and boosts do not change. The whole queries module passes with it (520 tests), the repros included, with assertions on and off.

float bestScore = -1;

// q pops the lowest score first. If more terms were selected than the clause limit allows,
// skip the lowest-scoring ones so that the best terms are kept (clause order and boost
// normalisation do not change).
int skip = q.size() - IndexSearcher.getMaxClauseCount();
while (skip-- > 0) {
  scoreTerm = q.pop();
  if (boost && bestScore == -1) {
    bestScore = scoreTerm.score;
  }
}

while ((scoreTerm = q.pop()) != null) {
All options and trade-offs4 options · 640 words

Two fixes were built and run in a scratch worktree at a9779ef3c193. A changes only how the query is built and is recommended; B limits the selection itself.

A: skip the lowest-scoring terms that cannot fit (createQuery) (validated by the checks) (recommended)

#

Before the build loop, pop and discard q.size() - getMaxClauseCount() terms, which are the lowest-scoring ones, still seeding the boost normaliser from the lowest selected score. +11 lines in MoreLikeThis.java; the finder's change (+10) with a reworded, 3-line comment.

float bestScore = -1;

// q pops the lowest score first. If more terms were selected than the clause limit allows,
// skip the lowest-scoring ones so that the best terms are kept (clause order and boost
// normalisation do not change).
int skip = q.size() - IndexSearcher.getMaxClauseCount();
while (skip-- > 0) {
  scoreTerm = q.pop();
  if (boost && bestScore == -1) {
    bestScore = scoreTerm.score;
  }
}

while ((scoreTerm = q.pop()) != null) {

Trade-offs

  • Only the truncating case changes: a query that fits is built exactly as today. Clauses stay in ascending order, and with setBoost(true) a kept term gets the boost it would get in the untruncated query.
  • retrieveInterestingTerms and createQueue are untouched; the catch (TooManyClauses) stays as a backstop, no longer reached unless another thread lowers the global clause limit while the query is built.
  • Cost: on the truncating path only. The skip loop pops #selected - limit terms; stock already pops one term that does not fit, so the net extra is #selected - limit - 1 pop() calls (O(log n) each). Not benchmarked.
  • It edits the same bestScore lines as the fix for the sibling boost-normalisation bug (a selected score of 0 gives NaN boosts); if both are filed together, the skip loop needs the same positive-score rule.

B: clamp the selection to the clause limit (createQueue) (validated by the checks)

#

limit = min(maxQueryTerms, #terms, IndexSearcher.getMaxClauseCount()) in createQueue (+6/-2 lines). maxQueryTerms above the limit then behaves exactly like maxQueryTerms equal to the limit, and the queue never holds entries that cannot be used.

Trade-offs

retrieveInterestingTerms(...) also goes through createQueue, so it would return at most getMaxClauseCount() terms although it builds no query; keeping it unchanged needs the clamp on the like(...) paths only. With setBoost(true) the boosts of a truncated query are normalised by the lowest kept score instead of the lowest selected one. When several terms tie at the cut, fix A and fix B can keep different ones of them (the comparator has no tie-breaker); both keep a top-scoring set.

Downstream note

#

Elasticsearch's and OpenSearch's own copies of this class (XMoreLikeThis) have the same loop over a lowest-first queue, so a Lucene fix will not reach them; this is from reading their source, not from a run.

How it was found

#

The hunt plan flagged the pop order from code reading. A random comparison of the real class with a reference model written from the javadoc then failed its top-terms check (R3) in 851 of 118,800 checks, all at the clause limit; a small exhaustive model confirmed the exact condition, and the finder wrote a public-API JUnit test.

The method in full182 words

Method: bounded random translation validation against a reference semantics (the hunt's "semi-formal" tier).

  • The hunt plan noted from code reading that createQuery adds clauses in the pop order of the score queue and stops at the first TooManyClauses, and its oracle asked whether MoreLikeThis keeps a lower-scoring term while dropping a higher-scoring one, "incl. at the clause limit". So the lead came from reading; the comparison confirmed it by execution.
  • The finder wrote a reference model of MoreLikeThis's term selection from its javadoc and compared it with the real queries jar on random inputs over the like(int), like(Map) and like(String, Reader) entry points: check R3, "the kept terms are the top-scoring eligible terms", failed 851 times in 118,800 checks (seed DEADBEEF), all at the clause limit and none elsewhere.
  • A bounded-exhaustive model of createQueue/createQuery (61,208 cases) confirmed the condition: a failure exactly when the clause limit is below min(maxQueryTerms, #terms) and a dropped term outscores a kept one (18,480 cases); a best-first mutant fails none.
  • The finder then wrote the public-API JUnit test, and independent checkers reproduced it.

History

#

Introduced in 4.10.0 by LUCENE-5795 (1427d574d3d on branch_4x, 173a44e67c7 on trunk, 2014-07-10), which made the term queue lowest-first. 4.9.0 and 4.9.1 pass the repro; 4.10.0 through 10.5.2 and main fail. Swapping only MoreLikeThis.java flips the result both ways.

Versions tested8 rows

Introduced by LUCENE-5795 "More Like This: ensures selection of best terms is indeed O(n)" (#6857; an SVN-era JIRA patch committed by @s1monw, CHANGES credits Alex Ksikes and Simon Willnauer): 173a44e67c7c3c1a9ffbe7259ea8b45f1f53b015 on trunk (first in 6.0.0) and 1427d574d3dae460d638b8d6584116baf4756214 on branch_4x (first in 4.10.0), both 2014-07-10. It bounded the queue to min(maxQueryTerms, #terms), flipped FreqQ.lessThan from fa > fb to a.score < b.score, and removed createQuery's own maxQueryTerms stop, but kept the pop-and-break loop that dates from the first check-in (7952217cea6, 2005-01-17). Later edits kept the behaviour: LUCENE-6570, LUCENE-6590, LUCENE-8811 (the limit moved to IndexSearcher in 9.0), #14761 (2025, main only: PriorityQueue.usingComparator, still ascending). Upstream branch_10_6 and branch_10x have the same lowest-first queue (still the FreqQ class) and the same pop-and-break loop; nothing has fixed it.

LFV-571, snapshot of 2026-10-28

Registry title
MoreLikeThis keeps the lowest-scoring selected terms when the query reaches the boolean clause limit, so the truncated query silently drops the most interesting terms (regression since 4.10.0)
Area
queries / MoreLikeThis query construction (MoreLikeThis.createQuery truncation at IndexSearcher.getMaxClauseCount)
Priority
Low, rank 374: MoreLikeThis keeps the lowest-scoring terms only when maxQueryTerms exceeds the clause limit, a rare setting that degrades relevance rather than matching, so it ends the suggestion and relevance-quality rows.
Impact class
silent wrong results
Impact note
Applications whose MoreLikeThis selects more terms than IndexSearcher.getMaxClauseCount() allows (maxQueryTerms set above the global clause limit, defaults 25 and 1024, on a like-text or source document with more eligible terms than the limit, or a lowered global clause limit) get, on every such call, with -ea and -da, the default codec and searcher and no scale, a query made of the lowest-scoring getMaxClauseCount() selected terms and no error, through MoreLikeThis.like(...), MoreLikeThisQuery rewritten by IndexSearcher and the XML query parser's LikeThisQuery maxQueryTerms attribute; the effect is worse relevance that is non-monotonic in maxQueryTerms (in the independent reproduction's test, raising it from 1024 to 1100 removed all 50 top words), not corruption, an exception or a hang.
Summary
You let MoreLikeThis select more terms than the global boolean clause limit, for example setMaxQueryTerms(2000) on a long text under the default limit of 1024, and call like(...). You expect the query, which createQuery deliberately truncates to the clause limit instead of failing, to keep the 1024 most interesting (highest tf*idf) of the selected terms, as it did up to 4.9.1. Instead createQuery pops its queue lowest score first and stops at the first TooManyClauses, so the query holds the 1024 lowest-scoring selected terms and none of the best ones (in the repro, 0 of the 76 top words survive).
