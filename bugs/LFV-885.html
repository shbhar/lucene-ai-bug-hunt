MultiIndexMergeScheduler is a 10.3.0 New Feature, but the class is package-private, so applications cannot construct it through the public API

Lucene 10.3.0 announces MultiIndexMergeScheduler as "a production multi-tenant merge scheduler" and its javadoc says to create one per index, but the class is declared without public: new MultiIndexMergeScheduler(dir) in application code does not compile. That holds in every release that has it, 10.3.0 to 10.6.0.

The finding in 30 seconds

#

One missing public hides an advertised class from every package except Lucene's own.

Background: merge schedulers and package-private classes

#
  1. IndexWriter hands merges to the MergeScheduler set with IndexWriterConfig.setMergeScheduler. The default, ConcurrentMergeScheduler, runs them in background threads, with limits on how many merges and threads run at once.
  2. MultiIndexMergeScheduler (10.3.0, #15015) is a thin per-index wrapper: every instance forwards its merges to one shared, JVM-wide CombinedMergeScheduler, so many indexes share one pool of merge threads.
  3. In Java, a class declared without public is package-private: code in any other package cannot name it or call its constructor, even a public one; only unsupported tricks such as deep reflection get around that, and only on the class path.

The finding, step by step

#
  1. You run many indexes in one JVM and want them to share one pool of merge threads. The 10.3.0 release notes list "MultiIndexMergeScheduler: a production multi-tenant merge scheduler", and its javadoc says: create one instance per index and use it like a ConcurrentMergeScheduler.
  2. In your own package you write iwc.setMergeScheduler(new MultiIndexMergeScheduler(dir)). You expect it to compile, as the same line with new ConcurrentMergeScheduler() does.
  3. Instead javac stops with 2 errors, at the import and at the new: "MultiIndexMergeScheduler is not public in org.apache.lucene.index; cannot be accessed from outside package". Plain reflection on the public constructor throws IllegalAccessException.
  4. The cause is one missing word: line 36 says class MultiIndexMergeScheduler, not public class, although its constructor ("use this one") and its getters are public. Lucene's only test of it sits in the same package, so Lucene's own build never saw the error.

Who is affected

#

Only applications that opt in to this experimental scheduler, typically ones hosting many indexes per JVM, and that follow the release notes or javadoc: every attempt through the public API fails at compile time. Nothing breaks at runtime, and the default scheduler is unaffected. GitHub code search found no user outside Lucene's own test.

Mechanism, terms and numbers548 words

Lucene 10.3.0 lists MultiIndexMergeScheduler under New Features as "a production multi-tenant merge scheduler", and the release announcement advertises it. Its javadoc tells users to create one instance per index and use it like a lone ConcurrentMergeScheduler, and its public constructor is "The main MultiIndexMergeScheduler constructor -- use this one". But the class itself is declared class MultiIndexMergeScheduler extends MergeScheduler, without public, so application code in any other package cannot import it or call that constructor through the public API: javac reports "MultiIndexMergeScheduler is not public in org.apache.lucene.index; cannot be accessed from outside package". It has been so in every release that has the class (10.3.0 to 10.6.0) and on main. It is a documentation/API-visibility mismatch, not a runtime defect: the failure is a loud compile error, the feature is opt-in and experimental, and nothing returns wrong results or damages an index. Adding public alone is not enough, because the shared scheduler behind every instance is never given its merge and thread limits, so the documented usage would then stall at the first merge.

Mechanism (Lucene main 645d4fe14a20)

#
  • MultiIndexMergeScheduler.java:36: class MultiIndexMergeScheduler extends MergeScheduler {, no access modifier. The package is exported (module-info.java:39, exports org.apache.lucene.index;), but Java still hides a package-private type from every other package.
  • The members are written as public API: the "use this one" constructor (:41-42), getDirectory() (:55-57), getCombinedMergeScheduler() (:59-61), setInfoStream(InfoStream) (:87-89) and CombinedMergeScheduler.peekSingleton() (:126-128). Only the test constructor (:48-49, "for unit testing") is package-private on purpose. The nested CombinedMergeScheduler (:100) is package-private too, although the public getter returns it.
  • The javadoc (:30-32): "The multi-tenant merge scheduling can be used easily by creating a MultiIndexMergeScheduler instance for each index and then using each instance normally, the same way you would use a lone ConcurrentMergeScheduler."
  • The only test, TestMultiIndexMergeScheduler, is in package org.apache.lucene.index; (line 17), so it compiles and the visibility gap stays invisible to Lucene's build. It also configures the shared scheduler by hand (:47, :121), so it never meets the first-merge stall either.
  • Lucene renders javadoc with -protected (RenderJavadocPlugin.java:464), so the class has no page in the published API docs (the 10.3.0 page returns 404 while the ConcurrentMergeScheduler page returns 200, checked 2026-11-01); the CHANGES entry (lucene/CHANGES.txt:1581, under "Lucene 10.3.0" / "New Features", lines 1555 and 1579) and the release announcement are the user-visible promise.

What an application sees

#
  • javac: 2 errors, "MultiIndexMergeScheduler is not public in org.apache.lucene.index; cannot be accessed from outside package", at the import and at new MultiIndexMergeScheduler(dir).
  • Plain reflection through the public constructor: IllegalAccessException ("cannot access a member of class org.apache.lucene.index.MultiIndexMergeScheduler with modifiers \"public\"").
  • javap on the lucene-core jars of 10.3.0 to 10.5.2, 10.6.0 and main prints class org.apache.lucene.index.MultiIndexMergeScheduler (no public) with a public (Directory) constructor.
  • Precision: two unsupported routes construct it, both only on the class path: code an application places inside org.apache.lucene.index (a split package), and deep reflection (setAccessible(true) on the public constructor). Both fail on the module path, because lucene-core is a named module that owns the package and does not open it: javac reports "package exists in another module", and setAccessible throws InaccessibleObjectException. So it cannot be used through supported means.
Exposure and likelihood123 words
  • Who is hit. Anyone who wants what #15015 delivers, multi-tenant merge scheduling (many indexes in one JVM sharing one pool of merge threads; the original request is #13883, "A multi-tenant ConcurrentMergeScheduler"), and writes the code the javadoc describes.
  • Opt-in. The default merge scheduler is ConcurrentMergeScheduler (LiveIndexWriterConfig.java:137), and the class is @lucene.experimental (MultiIndexMergeScheduler.java:34).
  • Scale. Unusable through supported means in all 8 releases that ship it, 10.3.0 (2025-09-13) to 10.6.0 (2026-10-29), and on main. No runtime harm: no wrong results, hang, data loss or index damage.
  • How likely. Every developer who tries it hits it at once, but the class has no published javadoc page and GitHub code search finds no user outside Lucene's own test, so few have realistically tried.

Why it looks unintended

#
  • The 10.3.0 CHANGES list it under New Features as "a production multi-tenant merge scheduler", and its javadoc says to create one per index.
  • Its "use this one" constructor and getters are public; #15015 narrowed only the test constructor, and its review discusses what users will call.
  • Its only test shares its package: the blind spot open issue #10750 describes.
The full argument297 words
  • The promise. lucene/CHANGES.txt:1581 (10.3.0, New Features): "GITHUB#15015: MultiIndexMergeScheduler: a production multi-tenant merge scheduler". The 10.3.0 announcement on dev@ and java-user@: "Adds a MultiIndexMergeScheduler – a multi-tenant wrapper that allows sharing a common merge scheduler across multiple instances". Javadoc :30-32 and :41 as quoted above.
  • Deliberate narrowing went only to the second constructor. The reviewer (vigyasharma) wrote: "make it pkg private for testing (not exactly safe but makes the intent explicit)" (review comment 2262089375), and PR commit 7a6ee719bb ("package private alternate constructor") did exactly that; the main constructor stayed public.
  • The review assumes users reach the class (indirect evidence). The quotes below are all replies in one review thread, rooted at vigyasharma's "Should we make this class private static?" (2248892958) on the nested CombinedMergeScheduler; they discuss how users configure the shared scheduler behind a MultiIndexMergeScheduler, which presumes users hold one, and none is about the top-level modifier. vigyasharma: "users get access to the configuration setters" (2250080260), "I think it is okay to let users directly work with public APIs for the underlying CMS" (2253329820), "It's fine to keep it public too. We probably need it to let people create index groups that share a CMS?" (2257747066, about the nested CombinedMergeScheduler, in the thread on whether to make it private static). The author (corecursion): "the user needs access to the shared CMS for calling configuration functions" (2248960412). No comment asks to hide the top-level class.
  • History. Package-private from the PR's first commit ad8cf7b6aa (2025-07-30) through all 17 PR commits and the merge cfb407bb0080; the declaration was never edited since.
  • Precedent. #10750 (LUCENE-9711, open), "gradle precommit no longer catches accidental package-private APIs?": its example was a new API "accidentally package private, missing its public modifier", hidden because its tests live in the same package.
The devil's-advocate check209 words

The strongest case for "not a bug" (rated moderate by the cross-model reviews): a package-private type is outside the public API by definition; its javadoc is not even published; it is @lucene.experimental; and made public as written, it would stall at the first merge, so maybe it was kept hidden until ready.

Why it fails: CHANGES and the release announcement, which are published, present it as a usable "production" feature, so the published promise and the code disagree whatever the intent. Nothing in the 17 PR commits or the review records a decision to hide the class, and the review discusses what users will call. @lucene.experimental renders as "WARNING: This API is experimental and might change in incompatible ways in the next release." (RenderJavadocPlugin.java:502), a stability warning for public API, not a visibility marker. The stall argues about how to fix it, not whether the mismatch is intended. The cross-model reviews said "not real" with low confidence; neither could run code. The works-as-designed review called its own verdict procedural and agreed on the root cause; the refute review's rested on its inability to run code and on the point that a package-private type is not public API, the case answered here. Neither disputed the root cause.

Suggested fix

#

Recommended Make it public, initialize the shared scheduler, document 3 methods (validated)

If the feature stays: make the class public, give the shared scheduler its default limits in acquireSingleton() (setDefaultMaxMergesAndThreads(false)) and add javadoc to its 3 public methods. public alone stalls the documented usage at the first merge. Validated: repro, TestMultiIndexMergeScheduler, a merging check, lint. Stopping the advertisement instead is the other option (not run).

Trade-offs

  • Why the second hunk. IndexWriter calls initialize() only on the scheduler it was given (IndexWriter.java:960); for this class that is MergeScheduler.initialize (MergeScheduler.java:79), which only stores the info stream; the source comment at MultiIndexMergeScheduler.java:84-86 says "We don't need the initDynamicDefaults() part". The shared scheduler is created with a plain new (MultiIndexMergeScheduler.java:107-113), so maxMergeCount stays -1 (ConcurrentMergeScheduler.java:66, 88), and maybeStall loops while a merge is pending and mergeThreadCount() >= maxMergeCount (ConcurrentMergeScheduler.java:611), which 0 >= -1 always satisfies; the indexing thread waits until a merge is no longer pending or someone changes the shared scheduler's limits. A lone CMS avoids that through initialize -> initDynamicDefaults (ConcurrentMergeScheduler.java:533-535, :442-444). Lucene's test configures the shared scheduler by hand (TestMultiIndexMergeScheduler.java:47, 121), and the #15015 author noted in review that it needs that setup (corecursion, comment 2248960412). The review settled on that hand configuration through the getter (2253329820); corecursion also asked whether the shared scheduler "should come with reasonable defaults that are usable for most people" (2253039480), which is what this hunk does. It is one reasonable design: documenting the hand setup, or forwarding initialize(), would also close the gap.
  • Why the javadocs. Once the class is public, :lucene:core:renderJavadoc fails with 3 errors, "MultiIndexMergeScheduler.getDirectory (method): javadocs are missing" and the same for getCombinedMergeScheduler and setInfoStream.
  • setDefaultMaxMergesAndThreads(false) picks the SSD defaults once per shared scheduler (maxThreadCount = max(1, cores / 2), maxMergeCount = maxThreadCount + 5, ConcurrentMergeScheduler.java:166-192); the singleton is dropped when the last instance closes (MultiIndexMergeScheduler.java:115-124) and the next one gets the defaults again, so an explicit setMaxMergesAndThreads made earlier is lost with it; on a live singleton an explicit setMaxMergesAndThreads still overrides the defaults. The formula is the code's: the AUTO_DETECT_MERGES_AND_THREADS javadoc (ConcurrentMergeScheduler.java:62-64) says max(1, min(4, cpuCoreCount/2)), but the code (:190) has no cap of 4.
  • This hunk does not create the shared scheduler's intra-merge executor, which initialize() also does (ConcurrentMergeScheduler.java:536-538); that looks harmless, because MultiIndexMergeScheduler does not override getIntraMergeExecutor, so IndexWriter (IndexWriter.java:3558, 5542) gets MergeScheduler's same-thread executor (MergeScheduler.java:38, 65-67). Alternatives, not run: forward initialize() from MultiIndexMergeScheduler to the shared scheduler (same package, so it can override the package-private method; it would also pass on IndexWriter's info stream and create that executor; whether to forward getIntraMergeExecutor too is a separate choice); and return ConcurrentMergeScheduler from getCombinedMergeScheduler(), as the reviewer first proposed (comment 2250080260). Today's return type is package-private, so mims.getCombinedMergeScheduler().setDefaultMaxMergesAndThreads(false) does not compile in application code even with public class ("is defined in an inaccessible class or interface"); only assigning the result to a ConcurrentMergeScheduler variable first does.
  • A public class gets a published javadoc page and becomes API that back-compat reviews cover.

Stop advertising it

#

Remove the class and its test, or keep it package-private and reword the javadoc so it no longer tells users to create instances, with a CHANGES note that the 10.3.0 feature is not available through the public API.

Trade-offs

Drops an announced feature that, as far as GitHub code search shows, nobody outside Lucene uses. The released 10.3.0 CHANGES text cannot be changed. Others are removing unused classes right now (#16873 merged on main, #16862 and #16880 open), so committers may prefer this. Not run.

LFV-885, snapshot of 2026-11-08

Registry title
MultiIndexMergeScheduler is listed under Lucene 10.3.0 New Features as 'a production multi-tenant merge scheduler' and its javadoc says to create one instance per index, but the class is package-private, so application code cannot compile against it or construct it through supported means
Area
core / index merge scheduling (MultiIndexMergeScheduler visibility)
Priority
Low, rank 1268: The docs advertise MultiIndexMergeScheduler, but its visibility makes it unusable, which fails loudly at compile time and damages nothing.
Impact class
minor
Impact note
Hits every application that tries the opt-in 10.3.0 feature as the release notes and the class javadoc describe it (10.3.0 to 10.6.0 and main): the source does not compile ('MultiIndexMergeScheduler is not public in org.apache.lucene.index; cannot be accessed from outside package') and reflective construction throws IllegalAccessException, so the failure is loud and at build time, with no wrong results, hang or index damage, and the advertised feature is simply unusable through supported means.
Summary
You read the Lucene 10.3.0 release notes ('MultiIndexMergeScheduler: a production multi-tenant merge scheduler') and the class javadoc ('can be used easily by creating a MultiIndexMergeScheduler instance for each index'), and write iwc.setMergeScheduler(new MultiIndexMergeScheduler(dir)) in your application, using the public constructor the javadoc calls 'The main MultiIndexMergeScheduler constructor -- use this one'. You expect it to compile, as the same line with ConcurrentMergeScheduler does. Instead javac rejects it because the class itself is declared 'class MultiIndexMergeScheduler' without 'public' (MultiIndexMergeScheduler.java:36), and it has been package-private in every release that contains it, so only code inside org.apache.lucene.index (in practice Lucene's own test) can use it.
