SortedDoubleDocValuesStats reads DoubleField values as raw IEEE bits, so negative values give a silently wrong min, sum and mean

SortedDoubleDocValuesStats (lucene/misc) decodes sorted-numeric doubles as raw IEEE bits, but core's DoubleField stores them in a sortable bit layout, so every negative value is misread: DoubleField values -5.0 and 3.0 give min -0.8749999999999999 and sum 2.125 instead of -5.0 and -2.0, with no error. Every release since 9.5.0 has it.

The finding in 30 seconds

#

DoubleField writes its doc values with NumericUtils.doubleToSortableLong, which flips every bit except the sign of a negative number. SortedDoubleDocValuesStats decodes each stored long with Double.longBitsToDouble, the inverse of the raw layout instead. For a positive number both layouts are the same bits, so only values with the sign bit set go wrong.

Background: doc-values statistics and the sortable layout

#
  1. DocValuesStats (module lucene/misc) computes count, min, max, sum, mean, variance and stdev of a doc-values field over the documents a query matches. SortedDoubleDocValuesStats is the variant for a sorted-numeric (multi-valued) field of doubles; you run it with DocValuesStatsCollectorManager (or the older DocValuesStatsCollector).
  2. A double is 64 bits: one sign bit, then exponent and fraction. Read as a signed long, these raw IEEE bits order positive numbers correctly but negative numbers backwards.
  3. So NumericUtils.doubleToSortableLong flips all bits but the sign bit of a negative number; then the longs sort like the doubles. DoubleField stores its doc values this way and reads them back with NumericUtils.sortableLongToDouble. DoubleDocValuesField (single-valued) stores raw bits instead.

The finding, step by step

#
  1. Index two documents, DoubleField("f", -5.0, Field.Store.NO) and DoubleField("f", 3.0, Field.Store.NO), and collect new SortedDoubleDocValuesStats("f") over MatchAllDocsQuery with DocValuesStatsCollectorManager.
  2. You expect min -5.0, max 3.0, sum -2.0 and mean -1.0.
  3. You get min -0.8749999999999999, sum 2.125 and mean 1.0625 (max 3.0 is right), with no error, with assertions on and off.
  4. Why: DoubleField stores -5.0 as the sortable long 0xbfebffffffffffff (every bit but the sign flipped, so the longs sort like the doubles). The stats class reads that long as a plain IEEE double, which is -0.8749999999999999.
  5. Positive values have the same bits in both layouts, so all-positive data, like the upstream test's, looks fine. Every negative value is misread, sometimes larger, sometimes smaller: -0.5 comes back as -7.999999999999999.

Who is affected

#

Applications that compute SortedDoubleDocValuesStats over core's DoubleField, or over a sorted-numeric field written with the documented NumericUtils recipe, whenever a matching value is negative (signed amounts, deltas, temperatures). Default settings, any index size; with the two documents -5.0 and 3.0, min, sum, mean, variance and stdev all come out wrong, silently. The class is an opt-in, rarely used misc utility.

Mechanism, terms and numbers711 words

DocValuesStats.SortedDoubleDocValuesStats in lucene/misc computes count, min, max, sum, mean, variance and stdev of "a sorted-numeric field storing double values" over the documents a query matches, and names no encoding. Core's DoubleField (since 9.5.0) writes exactly such a field, in the NumericUtils sortable layout, and core's SortedNumericDocValuesField javadoc recommends that layout for doubles. The stats class decodes each stored long as raw IEEE bits (Double.longBitsToDouble). The two layouts agree exactly when the sign bit is clear, so positive values are exact and every negative value is read as a different number: DoubleField -5.0 and 3.0 give min -0.8749999999999999, sum 2.125 and mean 1.0625 instead of -5.0, -2.0 and -1.0, silently, with default settings. The upstream test writes positive values only, so it cannot see it. Every release from 6.4.0 (documented recipe) and 9.5.0 (DoubleField) to 10.6.0 and main is affected. Decoding with NumericUtils.sortableLongToDouble fixes it; it changes results for anyone who wrote negative values as raw bits, so it needs a migration note (or a decoder argument).

The mechanism (main 5adff78bb168)

#
  1. The sortable layout. NumericUtils.doubleToSortableLong(value) is sortableDoubleBits(Double.doubleToLongBits(value)) (NumericUtils.java:47-48), and sortableDoubleBits(bits) is bits ^ (bits >> 63) & 0x7fffffffffffffffL (:84-85): for a negative number it flips every bit except the sign, for a non-negative number it changes nothing. The inverse is sortableLongToDouble (:56-57).
  2. What the field writes. DoubleField sets DocValuesType.SORTED_NUMERIC (DoubleField.java:52), stores NumericUtils.doubleToSortableLong(value) (:73, and :105 in the setter) and reads its own value back with sortableLongToDouble (:90).
  3. What the stats class reads (fix site). SortedNumericDocValuesStats opens getSortedNumericDocValues(field) (DocValuesStats.java:297); SortedDoubleDocValuesStats.doAccumulate reads docValueCount() values per document and decodes each with double val = Double.longBitsToDouble(sndv.nextValue()); (:436). Max, min, sum, the running mean and the variance all use that value (:437-450).
  4. The NUMERIC sibling is right. DoubleDocValuesStats decodes Double.longBitsToDouble(ndv.longValue()) (:256), which matches DoubleDocValuesField, documented as encoding "via Double#doubleToRawLongBits" (DoubleDocValuesField.java:20-21, :39). The sorted-numeric class uses the same decode for a field type whose core writer is sortable.

The numbers

#

-5.0 has raw bits 0xc014000000000000 and sortable bits 0xbfebffffffffffff; read as raw bits, 0xbfebffffffffffff is -0.8749999999999999. 3.0 is 0x4008000000000000 in both layouts. So for DoubleField -5.0 and 3.0 the class sees -0.8749999999999999 and 3.0.

A Z3 bit-vector/FP64 model over all 2^64 bit patterns proves: the two layouts coincide exactly when the sign bit is clear; every negative non-NaN value is read as a different number; the order among normal negatives is reversed; -0.0 and every negative subnormal but the largest-magnitude one are read as NaN (that one as -Infinity), and -Infinity as a negative subnormal; the bit flip sortableDoubleBits is its own inverse on all 2^64 patterns, so the sortable decode returns exactly the bits doubleToSortableLong started from (Double.doubleToLongBits, which canonicalises NaN).

Effects

#
  • Executed: DoubleField -5.0 and 3.0 give min -0.8749999999999999, max 3.0, sum 2.125, mean 1.0625, variance 3.75390625 and stdev 1.9375 (expected -5.0, 3.0, -2.0, -1.0, 16.0 and 4.0). A SortedNumericDocValuesField written with the javadoc recipe NumericUtils.doubleToSortableLong gives the same wrong values. Raw bits (Double.doubleToRawLongBits, what the upstream test writes) give the right values. A SortedNumericSortField(DOUBLE) on the same DoubleField sorts -5.0, 3.0 correctly.
  • Executed (an independent reviewer's test): DoubleField -2.5, 7.25 and -0.5 give min -7.999999999999999 instead of -2.5: a misread negative can come out smaller or larger than the true value.
  • Executed (this doc's diagram probe, main, assertions on and off): DoubleField -0.0 and 3.0 give max NaN, sum NaN, mean NaN and min 3.0, because -0.0 is read as NaN.

Not part of this finding: the facet module's MultiDoubleValuesSource.fromDoubleField, which reads these fields the same way (another module and fix site), a wrong max() (with a positive maximum it is right unless a -0.0 or a negative subnormal is present, which can be read as NaN, as in the -0.0 case above; when every value is <= 0 it is wrong for another reason: LFV-155, the Double.MIN_VALUE seed at DocValuesStats.java:429), and the variance denominator (a separate question, not run: the sorted-numeric variance() divides by the document count(), :312-315, while doAccumulate adds one term per value, :445-450; the upstream test computes its expected value the same way, and the repro has one value per document).

Exposure and likelihood211 words
  • Who is hit. Users of SortedDoubleDocValuesStats (through DocValuesStatsCollectorManager, since 10.5.0, or DocValuesStatsCollector) whose field is a DoubleField or a SortedNumericDocValuesField written with NumericUtils.doubleToSortableLong, and whose matching documents hold any negative value: each one is decoded as a different number.
  • Default vs opt-in. Default IndexWriterConfig, codec and searcher, public API only; two documents suffice. The class itself is opt-in: a lucene/misc utility, rarely used. It is final with a one-argument constructor, so it offers no decoder choice; the workaround is to write one's own subclass of the public abstract SortedNumericDocValuesStats (protected constructor and state) with a sortable decode, which both collector entry points accept.
  • Silent, and hidden by positive data. No exception, with assertions on and off. All-positive data gives exact results, so tests with positive data, like upstream's, never see it.
  • Scale. Any index size. With a single negative value among the matches, min() is always wrong; in ordinary data sum, mean, variance and stdev are wrong too, and the two-document repro gets all five wrong. (Rounding, or a set that holds both a value and its mis-read image, such as -5.0 and -0.8749999999999999, can leave an aggregate unchanged.)
  • Likelihood: plausible. Deterministic on the first negative value once the setup is used; the setup itself is rare.

Why it looks unintended

#
  • Documented as statistics for "a sorted-numeric field storing double values", with no encoding named; DoubleField is core's sorted-numeric double field.
  • Core's documented recipe for sorted-numeric doubles is the sortable layout, and core's readers (sorting, selectors) decode it so.
  • The upstream test writes only 1, 2, 3, ..., where both layouts are identical.
The full argument318 words
  • Contract. "Holds DocValues statistics for a sorted-numeric field storing double values" (DocValuesStats.java:421); min(): "The minimum value of the field. Undefined when count() is zero." (:111). No encoding precondition appears in the class, the package docs, the misc overview, CHANGES or MIGRATE.
  • Core's recipe. "Note that if you want to encode doubles or floats with proper sort order, you will need to encode them with NumericUtils" (SortedNumericDocValuesField.java:33-37), there since the sorted-numeric type was added in 2014, before this class.
  • Core's readers. SortedNumericSelector ("undo the numericutils sortability", :74-89), which SortedNumericSortField uses for every comparator (:282-368), decodes sorted-numeric doubles as sortable; so do the index sorter and Luke's doc-values view. No non-test, non-sandbox Lucene code writes raw-bit sorted-numeric doubles.
  • Raw bits are stated where meant. DoubleDocValuesField ("encoding doubles as NumericDocValues via Double#doubleToRawLongBits", :20-21) and DoubleRangeFacetCounts ("This assumes that the field was indexed with DoubleDocValuesField", :53-54). DocValuesStats has no such sentence.
  • Tests. TestDocValuesStatsCollector.testDocsWithMultipleDoubleValues writes Double.doubleToRawLongBits(nextVal) with nextVal = 1, 2, 3, ... (:274-290). For these values both layouts are the same bits, so the test passes 8 of 8 on stock and with the fix. No misc test runs these stats on a DoubleField.
  • History. The raw decode is from LUCENE-7590 (2016, 6.4.0), whose thread never discusses the encoding. DoubleField came with #11997 (9.5.0), which did not touch DocValuesStats; there jpountz wrote that multi-valued floats and doubles "should use NumericUtil#doubleToSortableLong to present ordering within a document", proposed "only supporting multi-valued fields, so that there is a single encoding in doc values", pushed that change and wrote (quoted as written): "These new fields not only support indexing sorted numeric doc values, so that queries do not have to specify whether floats/doubles are indexed via their raw bits or as sortable ints/longs". So the doc-values type is SORTED_NUMERIC only; the fields also index a point.
The devil's-advocate check283 words

The strongest "intended" case (built by the devil's-advocate verifier and the cross-model reviews; the refute-lens review rated it strong, the others moderate): LUCENE-7590 added the raw decode together with a raw-bit test, so the author meant the class as the multi-valued twin of DoubleDocValuesStats/DoubleDocValuesField, which are raw bits. In 2016 core had no sorted-numeric double field, so the encoding was the user's choice, and the javadoc recipe is conditional ("if you want ... proper sort order"), an order that matters only within a document, which the statistics ignore. The facet module's MultiDoubleValuesSource.fromDoubleField reads sorted-numeric doubles as raw bits too. The class is exact for raw-bit writers, negatives included (doubleToRawLongBits -5.0 and 3.0 give min -5.0, sum -2.0), and sorted-numeric doc values carry no encoding tag, so a decode switch changes results for them. A maintainer could answer "document that it expects raw bits".

Why it fails: nothing documents raw bits for this class, while Lucene states raw bits where it means them. Core's only sorted-numeric double field and core's recipe are sortable, core's readers of such fields decode sortable, and #11997 made the new fields sortable on purpose. The upstream test pins nothing observable. Core's standard double field gets wrong statistics today, with no warning. The argument bears on how to fix it (a migration note, or a decoder argument), not on whether DoubleField users get wrong numbers. Verdict: a defect for DoubleField users, an undocumented mismatch between core's sortable writer and this reader; whether the class's contract becomes sortable or raw (documented) is the maintainers' call, and the residual risk that they prefer documenting raw bits is why the priority sits in the lower part of Medium.

Suggested fix

#

Recommended Decode sortable, and say so in the javadoc (fix A)

Decode the stored longs with NumericUtils.sortableLongToDouble instead of Double.longBitsToDouble (one line), and state the expected encoding in the class javadoc. The repro, the whole lucene/misc test task and :lucene:misc:check -x test pass. It changes results for anyone who wrote negative values as raw bits, so it needs a migration note.

Trade-offs

  • Behaviour change. Applications that wrote raw IEEE bits of negative values into a SortedNumericDocValuesField (what the upstream test does, with positive values only) have their negative values decoded exactly today and misread after the fix, symmetric to the bug, so their statistics can change: an independent reviewer's raw-bit -2.5, 7.25 and -0.5 give min -7.999999999999999 under the fix (executed). Non-negative raw-bit data is unaffected. Needs a CHANGES entry and a MIGRATE note; whether to ship it on a release branch is a maintainer call.
  • Optionally switch the upstream test's Double.doubleToRawLongBits to NumericUtils.doubleToSortableLong and add a negative value.
  • Cost: still one decode per value, no allocation; the sortable decode adds a fixed XOR, shift and mask per value. No benchmark was run.

How it was found

#

A probe that carried the pattern of an earlier finding (a join reading DoubleField as raw bits) to other readers of sorted-numeric doubles gave min -0.8749999999999999 for DoubleField -5.0 and 3.0, while a raw-bit control was right. The hunt unit that judged it reduced it to one test; a Z3 model proved which values are affected.

The method in full213 words

Method: non-formal (an executed differential probe; the Z3 bit-vector model only proved the trigger set afterwards).

  • Round 23 of the hunt planned pattern-transfer checks: take the shape of a confirmed bug (LFV-1111, a numeric join that reads sortable DoubleField values as raw bits) and test the property "one logical type stored in two doc-values encodings must decode to the same value on every consumer" on other readers. Its own probe (2026-11-02, main e1faeba08bde, assertions on and off, also 10.6.0) fed the same values -5.0 and 3.0 to SortedDoubleDocValuesStats through three writers: DoubleField and the javadoc recipe gave min -0.8749999999999999, the raw-bit control the right -5.0. A second pattern-transfer probe found it again.
  • The hunt unit that judged it reduced it to a public-API JUnit, ran it on main, 10.6.0 and 9.5.0, modelled the trigger set in Z3 (the raw decode of the sortable layout is the identity exactly when the sign bit is clear) and checked the fix against the upstream test; a history step traced it to LUCENE-7590 and #11997.
  • An independent reproducer, cross-model reviews (OpenAI GPT-5.6), a devil's-advocate verifier, an adjudication, an audit and a final repro check then re-ran it.
  • An earlier sighting (2026-10-26, while LFV-155 was being verified) noticed this mis-decode, but it was not followed up then.

LFV-1129, snapshot of 2026-11-09

Registry title
SortedDoubleDocValuesStats (lucene/misc) reads core DoubleField values as raw IEEE bits, so negative values give a silently wrong min, sum and mean (DoubleField -5.0 and 3.0 give min -0.8749999999999999)
Area
misc / DocValuesStats: SortedDoubleDocValuesStats decode of sorted-numeric double doc values (core DoubleField)
Priority
Medium, rank 188: SortedDoubleDocValuesStats in lucene/misc returns a wrong min, sum and mean, and so a wrong variance and stdev, every time a matching value is negative. This holds for core DoubleField (since 9.5.0) and for the documented sortable-double encoding, with default settings in every release since 6.4.0. The class is opt-in and rarely used, so it sits in the lower part of Medium, but the trigger is ordinary signed data.
Impact class
silent wrong results
Impact note
Applications that compute DocValuesStats.SortedDoubleDocValuesStats (lucene/misc, through DocValuesStatsCollectorManager or the older DocValuesStatsCollector) over core's DoubleField, or over a SortedNumericDocValuesField written with the NumericUtils.doubleToSortableLong recipe that class's javadoc gives, get a silently wrong min, sum and mean (and the variance and stdev derived from them) when the matching values include negative numbers: every value with the sign bit set (negative numbers, -0.0, -Infinity) is read back as a different number, for example -5.0 as -0.8749999999999999 and -0.0 as NaN; default IndexWriterConfig, codec and searcher, -ea and -da, any index size; positive values are exact because their sortable and raw bits are identical, which is why the upstream test (positive values only) does not see it; DoubleField trigger in every release from 9.5.0 through 10.6.0 and main, the javadoc-recipe trigger since 6.4.0.
Summary
You index two documents with DoubleField("f", -5.0) and DoubleField("f", 3.0) and search MatchAllDocsQuery with new DocValuesStatsCollectorManager<>(() -> new SortedDoubleDocValuesStats("f")); you expect min() = -5.0 (sum -2.0, mean -1.0), because the class 'Holds DocValues statistics for a sorted-numeric field storing double values' and DoubleField is core's sorted-numeric double field. You get min() = -0.8749999999999999 (sum 2.125, mean 1.0625) with no error: DoubleField stores NumericUtils.doubleToSortableLong(value), but SortedDoubleDocValuesStats decodes each stored long as raw IEEE bits (Double.longBitsToDouble, DocValuesStats.java:436). Positive values are unaffected because their sortable and raw bits are the same.
