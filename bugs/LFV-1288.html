With reader pooling off, a failed reader open while deletes are applied leaks a reader-pool reference, so the segment stays pooled and a later reader keeps its files open until merge, close or rollback

With setReaderPooling(false), if opening a segment's reader fails while a flush() applies deletes, IndexWriter never gives back the pool reference it took for it. The segment stays pooled (refCount 2), and the reader opened for it later keeps _0.cfs open until a merge, close() or rollback() (since 4.0.0).

The finding in 30 seconds

#

To apply deletes, openSegmentStates takes a pool reference for each segment, then opens its reader. If the open throws, the cleanup closes the states already built, but the failed one's reference belongs to none of them. With pooling off, an entry leaves the pool only when its count is back to 1, so this one never leaves.

Background in three steps

#
  1. IndexWriter keeps a reader pool with one entry per segment, which holds the segment's reader and pending deletes. Whoever uses an entry takes a reference and must release it; the pool holds one reference of its own.
  2. With setReaderPooling(false) (the default is true), an entry is dropped and its reader closed as soon as only the pool's own reference is left (count 1).
  3. Deletes are applied in packets. A flush() or commit() also applies packets that are still pending, including one another thread just published.

The finding, step by step

#
  1. Turn reader pooling off, add 2 documents and commit(): one segment, _0. With pooling off, the writer does not pool the readers it opens for deletions and merging: here it opens _0's reader to apply a delete, then drops it from its reader pool.
  2. Delete document 1 and flush(). A second thread's flush() applies that delete, and opening _0's reader fails once with an IOException. That flush() throws; the writer stays open and the main thread's flush applies the delete.
  3. You expect, after commit(), the same end state as without the error: 1 live document, _0 gone from the reader pool, none of its files open.
  4. Instead _0 stays pooled with refCount 2. openSegmentStates took a pool reference before it opened the reader, and its cleanup releases only the readers it actually opened. The reader the next apply opens stays too, holding _0.cfs open until _0 is merged away or the writer closes.
  5. Search results and committed data are correct, nothing stays open after close(), and default pooling is not affected.

Who is affected

#

Only applications that call setReaderPooling(false) and open no NRT reader, when an I/O error (too many open files, a storage error) hits a segment-reader open during a concurrent flush() or commit(). Each failure keeps one segment's reader and files until merge, close or rollback: no more than default pooling holds. No wrong results, no data loss.

Mechanism, terms and numbers581 words

With IndexWriterConfig.setReaderPooling(false), IndexWriter does not pool the segment readers it opens for deletions and merging: it opens one when it needs it, for example to apply buffered deletes or doc-values updates, and drops it afterwards. To apply a delete packet, IndexWriter.openSegmentStates takes a reader-pool reference for each segment (getPooledInstance(info, true)) and passes it straight into the SegmentState constructor, which opens the segment reader. If that open throws, for example an IOException from the directory, the constructor never returns, and the method's catch closes only the states it already built: the reference taken for the failed one is never released.

An unpooled entry leaves the pool only when its reference count falls back to the pool's own 1, so the segment stays pooled with refCount 2, and the reader the next successful apply opens for it, with its open files, stays too, until the segment is merged away or the writer closes or rolls back. Since 7.0.0 the repro reaches it through a flush() that applies a packet another thread published (in the publishing thread's own apply the same error is tragic and closes the writer); in 4.0.0-6.6.6 a single-threaded commit() was enough. No wrong results, no data loss. The fix releases the reference when the constructor throws.

The bug

#
  1. IndexWriter.openSegmentStates (IndexWriter.java:6777-6800) builds one state per segment with segStates.add(new BufferedUpdatesStream.SegmentState(getPooledInstance(info, true), this::release, info)) (:6784-6786). getPooledInstance (:6476-6479) calls ReaderPool.get(info, true), which increments the entry's count for the caller ("Return ref to caller", ReaderPool.java:425-428; javadoc: "If create is true, you must later call release", :391-393).
  2. The SegmentState constructor (BufferedUpdatesStream.java:274-282) then opens the reader, reader = rld.getReader(IOContext.DEFAULT) (:278), which creates the SegmentReader on first use (ReadersAndUpdates.java:188-198). If that throws, no SegmentState exists.
  3. The catch (Throwable t) (IndexWriter.java:6790-6797) closes only segStates; each SegmentState.close() releases its reader and its pool reference (BufferedUpdatesStream.java:290-292). The reference taken for the failed constructor is in no state, so nothing releases it.
  4. With pooling off, ReaderPool.release drops an entry only when its count is back to 1 (ReaderPool.java:202), and only then calls dropReaders() and removes it (:221-223). The extra reference keeps the count at 2 after every later apply, so the entry stays, and with it the SegmentReader that the next successful apply opens into it.

Why the writer stays open (and why the repro uses two threads)

#

The failing thread reaches openSegmentStates from flush() through doFlush -> applyAllDeletesAndUpdates (IndexWriter.java:4416-4417, :4439-4451) -> BufferedUpdatesStream.waitApplyAll (BufferedUpdatesStream.java:128-136, :233, :242) -> forceApply (IndexWriter.java:6490-6500, :6507, :6559). doFlush's catch makes only an Error tragic (:4427-4429), so the IOException goes back to the caller and the writer stays usable. On the other path, the apply event queued by publishFrozenUpdates (:2928-2946), any Throwable is tragic: the writer closes, closing drops the whole pool, and nothing is left behind. In 4.0.0-6.6.6 a single-threaded commit() reached the non-tragic path.

What clears it

#

A merge that drops the segment (ReaderPool.drop, ReaderPool.java:132-141), a fully deleted segment, and close() or rollback() (dropAll, :314). Commits write the live docs but do not drop entries. At most one reader is kept per segment: once the entry holds a reader, the constructor does no I/O for it. Each failed open before that leaves one more reference on the same entry; the one failure in the repro leaves refCount 2.

Exposure and likelihood223 words
  • Who: applications that call setReaderPooling(false) (the default is true, IndexWriterConfig.java:85-90) and never open an NRT reader from the writer (that turns pooling on), when an I/O error such as "too many open files" or a transient storage error hits while a segment reader opens to resolve deletes or doc-values updates, and (since 7.0.0, on the path the repro shows) the failing thread is a flush() or commit() resolving a packet another thread published. IndexWriter is documented as thread safe (IndexWriter.java:167-170).
  • Effect: per failure, one segment's pool entry, and later its SegmentReader with its open files and heap, stay until that segment is merged away or the writer closes or rolls back. That is no more than default pooling keeps for every segment anyway: with pooling on, release never drops an entry (ReaderPool.java:202). A public-API probe saw _0.cfs still open after the commit in the failure run only, on main and on 10.6.0.
  • Not affected: search results, committed data (the other thread re-applies the packet; numDocs is right after the commit), anything after IndexWriter.close(), and writers with default pooling or an NRT reader.
  • Scale: none needed; one 2-document segment shows it.
  • Likelihood: rare: a non-default setting, an I/O error at one exact step and (since 7.0) a concurrent flush; the documented searches found no matching public report.

More files, environment, full output316 words

The test sits in org.apache.lucene.index and uses internals in three places: it reads the pool through package-private IndexWriter.getPooledInstance(info, false) and newestSegment() (as TestReaderPool reads ReaderPool directly), its injected failure checks the stack for the package-private BufferedUpdatesStream.SegmentState, and its latches key on the text of two internal InfoStream messages. A helper thread's flush() is held at the "now apply all deletes" message; the main thread deletes id:1 and flushes, and its "finishFullFlush" message lets the helper go and waits for it, so the helper applies the main thread's packet on the non-tragic path. The failure fires only on the helper thread and only under SegmentState.<init>.

Two threads are needed only to reach the non-tragic path; the latches fix the order, so there is no race. They wait without a timeout, so if those log messages changed the test would hang rather than fail. Why it looks unintended

#
  • ReaderPool.get: "If create is true, you must later call release"; the method's own catch releases every state it built.
  • TestReaderPool asserts that with pooling off a released entry leaves the pool; without the I/O error the same steps drop it.
  • The failure is not tragic, and Lucene's own testErrorAfterApplyDeletes (pooling off) retries commit() after a failed one.
The full argument214 words
  • The reference contract: ReaderPool.get's javadoc, "If create is true, you must later call release" (ReaderPool.java:391-393).
  • The method's own cleanup: the catch of openSegmentStates closes every state it built and adds secondary failures as suppressed (IndexWriter.java:6790-6797, shaped by LUCENE-8215 and LUCENE-8269); the reference of the state that failed to build is simply outside segStates.
  • The pooling-off behaviour: setReaderPooling's javadoc: IndexWriter "does not pool the SegmentReaders it must open for deletions and merging, unless a near-real-time reader has been obtained" (IndexWriterConfig.java:316-320; the sentence still opens with "By default,", stale since the default became true in 7.0.0); DEFAULT_READER_POOLING's comment says false "is still supported" (:85-89); TestReaderPool.testPoolReaders asserts that with pooling off release(get(info, true)) leaves get(info, false) null (TestReaderPool.java:88-90).
  • Continuing is expected: the class javadoc ties corrupted "reference counts" only to an Error or a failed checkpoint, after which the writer closes itself (IndexWriter.java:162-165); this path is neither. TestIndexWriterDelete.testErrorAfterApplyDeletes (@Ignored, setReaderPooling(false), TestIndexWriterDelete.java:802-963) retries: "The commit above failed, so we need to retry it" (:942).
  • History: no commit, CHANGES entry, test or issue accepts the leak. LUCENE-3855 added the reference count but kept the reader open before the try that releases it; later moves kept the gap.
The devil's-advocate check160 words

The strongest case for "intended": on the open #9738 (LUCENE-8692, 2019), Simon Willnauer (s1monw) said flush and commit exceptions are left non-tragic "since a user could always call rollback()", and (2019-03-11) that whoever continues after a failed commit, prepareCommit or reopen "will end up with inconsistency and / or dataloss"; a rollback clears this leak, and rolling back after a failed flush or commit is a plausible way to operate. Add that the effect is no larger than default pooling, and that it needs a non-default setting, an I/O error and concurrency.

Why it fails: the remark is one maintainer's opinion in an unresolved issue (they also wrote "Now we can debate if we want to change this"), not a documented contract; in the reproduced scenario continuing is safe (the other thread re-applies the packet and numDocs is right after the commit); Lucene's own test retries after such a failure; and size and preconditions are impact and likelihood, not intent.

Suggested fix

#

Recommended A. Release the reference when the constructor throws (validated)

Take the reference first, build the SegmentState inside a try, and if the constructor throws, release the reference (suppressing any secondary failure) and rethrow: +10/-3 in IndexWriter.openSegmentStates. The repro passes with assertions on and off; 10 nearby core test classes (161 tests) and the format and lint checks pass.

ReadersAndUpdates rld = getPooledInstance(info, true);
BufferedUpdatesStream.SegmentState state;
try {
  state = new BufferedUpdatesStream.SegmentState(rld, this::release, info);
} catch (Throwable t) {
  // the state was not built, so give back the reference we took for it
  IOUtils.closeWhileSuppressingExceptions(t, () -> release(rld));
  throw t;
}
segStates.add(state);

A. Release the reference when the constructor throws (validated) (recommended)

#

In IndexWriter.openSegmentStates (IndexWriter.java:6784-6786), +10/-3:

ReadersAndUpdates rld = getPooledInstance(info, true);
BufferedUpdatesStream.SegmentState state;
try {
  state = new BufferedUpdatesStream.SegmentState(rld, this::release, info);
} catch (Throwable t) {
  // the state was not built, so give back the reference we took for it
  IOUtils.closeWhileSuppressingExceptions(t, () -> release(rld));
  throw t;
}
segStates.add(state);

Trade-offs

  • Local to the one method that takes the reference; nothing changes on success.
  • A failure in release is added to the original exception as suppressed, the idiom IndexWriter already uses (e.g. :716); if release threw an Error while the original is not one, that Error is thrown instead, with the original suppressed (IOUtils.java:124-135); the outer catch still closes the states already built.
  • release asserts the IndexWriter lock, which forceApply holds here (:6547-6559).
  • CHANGES: a Bug Fixes entry under the next release.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: TestReaderPool, TestIndexWriterDelete, TestIndexWriterExceptions, TestIndexWriterExceptions2, TestIndexWriterWithThreads, TestIndexWriterOnDiskFull, TestBufferedUpdates, TestFrozenBufferedUpdates, TestNumericDocValuesUpdates, TestBinaryDocValuesUpdates and the repro: 11 classes, 161 tests, 0 failures, 10 skipped (8 @Nightly, 1 @Monster, 1 @Ignore).
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test (the log notes that the optional eclint check was not configured and Error Prone was skipped).
  • Earlier shadowed-class checks: the same change written with a nested try/catch made the original witness test and an independent reproduction's test pass. The full lucene/core suite was not run.

B. Make the SegmentState constructor release on failure

#

Catch around rld.getReader(...) (BufferedUpdatesStream.java:278) and call onClose.accept(rld) before rethrowing.

Trade-offs

The constructor would then own a reference it did not take, an unusual convention every caller must know. Not run.

C. Document "roll back after a failed flush or commit"

#

State in the javadoc that callers must call rollback() after a failed flush() or commit().

Trade-offs

Does not fix the leak, and contradicts the non-tragic design of this path and Lucene's own retry test. Not recommended.

Downstream note

#

Downstream, a service that turns reader pooling off and keeps using its writer after a failed flush() or commit() can hold one extra segment reader and its file handles per such failure until a merge, close() or rollback(); rolling back after the failure clears it.

How it was found

#

Semi-formal: a proof-obligation audit of IndexWriter.openSegmentStates' reference contract, that every reference taken with getPooledInstance(info, true) is released on every path, also on failure. The exception path out of the SegmentState constructor fails the obligation, and a JUnit test on stock main witnessed it.

The method in full93 words
  • Obligation: every reader-pool reference that openSegmentStates takes with getPooledInstance(info, true) is released on every path, normal or exceptional, as ReaderPool.get's javadoc requires (ReaderPool.java:391-393).
  • Finding: the normal path discharges it (each built SegmentState releases its reference in close()); on the exception path out of the constructor the reference is in no state, and the catch (IndexWriter.java:6790-6797) cannot reach it.
  • Witness: a JUnit test with an injected IOException on the non-tragic flush() path, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Summary
You turn reader pooling off (IndexWriterConfig.setReaderPooling(false)) and delete a document; while one flush() applies that delete, opening the segment's reader fails with an IOException, so that flush throws, the writer stays open, and another flush or commit applies the delete successfully. You expect the writer to give back every reader-pool reference it took, so that, as without the I/O error, the segment is no longer pooled once the delete is applied and committed. Instead IndexWriter.openSegmentStates never releases the reference it took for the SegmentState whose constructor threw: the segment stays in the pool with refCount 2, and the SegmentReader (with its open files) that the next apply opens is kept until the segment is merged away or the writer closes.
