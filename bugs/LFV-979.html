Suggest Lookup.load(): a load that throws leaves the lookup half-loaded, with the new count and part of the new model

When a suggester's load() throws part-way, the lookup keeps what it had read: a new TSTLookup loading a 2-word stored copy that is 1 byte short throws, yet reports getCount() 2 instead of 0, suggests "a" and throws NullPointerException for "b". Every model-reading load() assigns fields while still reading.

The finding in 30 seconds

#

TSTLookup.load() sets the entry count, replaces its tree with a new, empty one and reads the stored tree into it node by node, so each part is live as soon as it is read. When the stream ends or fails part-way, load() throws, but the new count and the half-built tree stay behind.

Background: how a suggester is saved and loaded

#
  1. A Lookup is one of the suggest module's autocomplete structures, built from words with weights. Six of them (TSTLookup, AnalyzingSuggester, FuzzySuggester, FreeTextSuggester, FSTCompletionLookup, WFSTCompletionLookup) can save their model to a stream and load it back; the infix suggesters cannot (their store() and load() return false).
  2. store() writes it to a stream: the entry count first, then the model (a ternary search tree, or an FST plus a few settings).
  3. load() reads such a copy back: "Discard current lookup data and load it from a previously saved copy". It throws IOException when the read fails and says nothing about the state it leaves then. A common pattern is to load into a new instance and swap it in.

The finding, step by step

#
  1. Build a TSTLookup from two words, a and b (weight 1 each), and store() it: a 30-byte copy, the count 2 and then the tree. The copy ends up 1 byte short, as when a store() is cut off by a crash.
  2. Load it into a new TSTLookup(). load() throws EOFException and you catch it. You expect the new lookup to stay empty: getCount() 0, no suggestions.
  3. Instead getCount() is 2, lookup("a") returns a/1 from the half-read copy, and lookup("b") throws NullPointerException. An IOException in the middle of a complete copy does the same.
  4. Why: load() sets the count first, then swaps in a new, empty tree and fills it node by node as it reads. The stream ended inside b's weight, so node b has its word but no weight. The other suggesters' load() methods also assign fields as they read.

Who is affected

#

Applications that store() and load() the suggest Lookups and keep using an instance after its load() threw: a stored copy cut short, an I/O error while a valid copy is read, or a FreeTextSuggester model saved with other settings. Opt-in classes, default settings, any size, deterministic. Rare: no public report since 2011.

Mechanism, terms and numbers798 words

The six suggest Lookups that implement store()/load() (TSTLookup, AnalyzingSuggester, FuzzySuggester, FreeTextSuggester, FSTCompletionLookup, WFSTCompletionLookup) can save their model to a stream and load it back; the infix suggesters' store()/load() just return false, so they are not affected. Lookup.load is documented as "Discard current lookup data and load it from a previously saved copy" and throws IOException "when fatal IO error occurs" (Lookup.java:246-252 on main 645d4fe14a20); it says nothing about the state after a throw. Each of the five load() methods (FuzzySuggester inherits one) assigns its fields one after another while it reads: TSTLookup.load sets count, replaces the tree with a new empty root and only then reads the tree into that live root (TSTLookup.java:276-278). So a load() that throws part-way (a stored copy cut short, an IOException while a valid copy is read, or FreeTextSuggester rejecting a model saved by a FreeTextSuggester with other grams or separator settings) leaves a mix of the old or initial state and the new model. A new TSTLookup loading a 2-word copy that is 1 byte short reports getCount() 2 instead of 0, suggests a/1 and throws NullPointerException for "b"; for most other classes only getCount() is wrong, with narrower payload and score mixes and a narrow window in which a new AnalyzingSuggester or FuzzySuggester throws NoSuchElementException from some lookups. TSTLookup has done this since its first load() (SOLR-2375, 3.1.0, 2011), all six classes since LUCENE-5404 (4.7.0, 2014). Reading into locals and assigning at the end fixes it (5 methods, +30/-16).

Terms

#
  • TSTLookup: a suggester on a ternary search tree. Each node (TernaryTreeNode.java:28-48) holds one character (splitchar), an optional token and val (the word and its weight) and up to three children. getCount() is "the number of entries the lookup was built with" (Lookup.java:172-176).
  • Stored copy: store() writes count as a VLong and then the tree in pre-order: per node its character, a flag byte, then the token and an 8-byte weight when the node has them (TSTLookup.java:241-272). For {a, b} that is 30 bytes; the last byte belongs to b's weight.

The bug

#
  1. load(InputStream) wraps the stream, calls load(DataInput) and closes the stream in a finally block, also when the load fails (Lookup.java:150-157).
  2. TSTLookup.load (TSTLookup.java:275-280): count = input.readVLong(); (:276), root = new TernaryTreeNode(); (:277), readRecursively(input, root); (:278). The count and the new, empty root are live before a single node is read.
  3. readRecursively (:218-239) reads a node's character, flags, token and weight, then allocates each child and recurses. With the copy 1 byte short, readLong() for b's weight (:225) hits the end: EOFException. Node b exists with its token but val == null.
  4. lookup() collects every node with a token (TSTAutocomplete.java:97-148) and unboxes its weight, ((Number) ttn.val).longValue() (TSTLookup.java:199, :205): "a" gives a/1, "b" throws NullPointerException.
  5. The other load() methods assign in stream order too: AnalyzingSuggester.java:614-619 (count, fst, maxAnalyzedPathsForOneInput, hasPayloads; FuzzySuggester inherits it), FreeTextSuggester.java:363-379 (count before its own separator and grams checks, totTokens before the FST), FSTCompletionLookup.java:304-308 and WFSTCompletionLookup.java:145-146 (count before the FST). In a new AnalyzingSuggester or FuzzySuggester whose stream ends or fails right after the FST, the new FST is live while maxAnalyzedPathsForOneInput is still 0, and some lookups throw NoSuchElementException. Nothing restores a field on the exception path.

Exposure and likelihood285 words
  • Who is hit. Code that keeps using a Lookup after its load() threw, including a new instance it meant to swap in. Solr's SolrSuggester.init loads the stored file into the lookup it will serve, catches the IOException, logs "Loading stored lookup data failed, possibly not cached yet" and continues with that instance (it catches only IOException, so this does not cover FreeText's IllegalStateException); its build() stores straight into the target file, so a store cut short by a crash leaves exactly this input for the next start.
  • Default or opt-in. Opt-in: the suggest module's Lookups, with default settings (TSTLookup and FSTCompletionLookup have no-argument constructors; the others take an analyzer and/or a temporary directory). Lookup and five of the six classes are @lucene.experimental (TSTLookup carries no tag).
  • Effect. After an exception the caller saw: TSTLookup serves part of the new tree and some lookups throw NullPointerException, also in a new instance. For FSTCompletionLookup, WFSTCompletionLookup, a new FreeTextSuggester, the FreeText rejected-model case and most Analyzing/Fuzzy cut points only getCount() is wrong. Analyzing/Fuzzy cut in their last 1-2 bytes after a model with the other payload setting glue the payload to the key or return the key as the payload (an AssertionError with -ea). A new Analyzing/Fuzzy instance whose stream ends or fails right after the FST throws NoSuchElementException from some lookups. FreeTextSuggester over a built model scores the old FST with the new token total.
  • Scale. None needed: 2 entries, one thread, assertions on or off.
  • How likely: rare. It needs a load() that throws and continued use of that instance; upstream tests load only complete copies, and the recorded search found no report since 2011.

Why it looks unintended

#
  • The new-instance swap #5558 describes is the repro: that instance ends neither empty nor loaded, and lookup() throws.
  • An IOException while a valid copy is read is what load() declares; nothing says the instance is unusable afterwards.
  • FreeTextSuggester changes getCount() before its own check rejects a model; LUCENE-10292 fixed the build-side twin as a bug.
The full argument259 words
  • A new instance is left half-loaded too. #5558 (LUCENE-4492, open) describes loading a new instance and swapping it in as today's way to reload a suggester (the issue is about safe publication of that swap). In the repro that instance ends with getCount() 2, one suggestion and a NullPointerException: neither its previous (empty) state nor the stored model.
  • The trigger is in contract. An IOException while a valid copy is read is what load() declares (Lookup.java:250). These classes have no closed or unusable state.
  • FreeTextSuggester's validation is out of order. Its first load() (LUCENE-5214, b50a2edbb23, 2013) checked separator and grams before assigning any field; LUCENE-5404 (b5926da2d67, 2014) put count = input.readVLong() ahead of those checks (FreeTextSuggester.java:363), so a model it rejects with its own IllegalStateException still changes getCount().
  • Lucene reloads in place itself. TestAnalyzingSuggester calls suggester.load(is) on the instance it just built and stored (TestAnalyzingSuggester.java:1048, :1099, :1147, :1187). The module's 6 load() calls in tests all read complete copies, so no test asserts or contradicts any post-failure state.
  • The build side was fixed as a bug. LUCENE-10292 (#11328, 9.2.0, "Bug Fixes"): "Fix other FST based suggesters so that getCount() returned results consistent with lookup() during concurrent build()" (lucene/CHANGES.txt:4289-4291). load() was not touched.
  • Lucene's newer suggester already loads this way. NRTSuggester.load (the document suggester, NRTSuggester.java:309-327) reads every field into locals and constructs the object at the end, and CompletionsTermsReader.suggester() assigns it in one step (:64-69): the shape of the recommended fix.
The devil's-advocate check330 words

The intended-behaviour checker, a reviewer from another model family (OpenAI GPT-5.6) and the adjudication built the strongest case: Lookup.load promises nothing after it throws, and "fatal IO error" can be read as "the instance is unusable afterwards"; Lookup is @lucene.experimental; a cut stream is not "a previously saved copy", a trigram model is not a copy for a bigram suggester, and every damaged stream is detected; #5558 describes a new instance and a swap; on #6467 (LUCENE-5404) McCandless (they) called loading a previously built suggester and then building a new one over it "strange", and wrote about the repro's own pattern: "it's sort of weird to 1) create a new suggester class, and 2) call its load API; it's more natural to create the suggester, passing in a Dir/File where it should load its state from"; on #11328 dweiss (they) said the Lookups "seemed to be designed with a single-thread model in mind"; and for most classes only getCount() is wrong.

Why it fails: the classes define no unusable state, and the first consumer of TSTLookup.load (Solr's Suggester.init, added by the same SOLR-2375 commit) caught the exception and kept the instance; the "not a saved copy" point does not cover an IOException while a valid copy is read, and the FreeText rejection is the suggester's own check; the new-instance pattern is the repro, and that instance is not left empty; Lucene's own tests reload in place. The "sort of weird" remark is an API-design opinion, and the API as shipped is built for construct-then-load: FSTCompletionLookup's no-argument constructor is documented "This constructor should only be used to read a previously saved suggester." (FSTCompletionLookup.java:105), TestPersistence (:86-87) and TestFreeTextSuggester (:90-91) load into a new instance, and so does Solr's SolrSuggester.init. The count-only point is true and is why the priority is low, but TSTLookup throws from lookup(). What remains supports a low priority and possibly an "improvement" label, not "works as designed".

Suggested fix

#

Recommended Read into locals, assign after the whole stream was read and checked

In each of the five load() methods, read every field into locals and assign them only after the whole stream was read and checked (+30/-16; FuzzySuggester inherits it). Validated: the repro passes with assertions on and off, the whole suggest module's tests (237) pass, and check -x test passes once the test's long comment line is wrapped.

   public synchronized boolean load(DataInput input) throws IOException {
-    count = input.readVLong();
-    root = new TernaryTreeNode();
-    readRecursively(input, root);
+    long newCount = input.readVLong();
+    TernaryTreeNode newRoot = new TernaryTreeNode();
+    readRecursively(input, newRoot);
+    root = newRoot;
+    count = newCount;
     return true;
   }

Read into locals, assign after the whole stream was read and checked (validated by the checks) (recommended)

#

Five load() methods (TSTLookup, AnalyzingSuggester, FreeTextSuggester, FSTCompletionLookup, WFSTCompletionLookup) read into locals and assign the fields at the end; FuzzySuggester inherits it. In FreeTextSuggester this also puts the separator and grams checks back before any assignment. Lucene's document suggester already loads this way (NRTSuggester.load). The TSTLookup part:

   public synchronized boolean load(DataInput input) throws IOException {
-    count = input.readVLong();
-    root = new TernaryTreeNode();
-    readRecursively(input, root);
+    long newCount = input.readVLong();
+    TernaryTreeNode newRoot = new TernaryTreeNode();
+    readRecursively(input, newRoot);
+    root = newRoot;
+    count = newCount;
     return true;
   }

Trade-offs

  • Several plain field writes at the end, as the build side does since LUCENE-10292: not one atomic snapshot for a thread that looks up while load() publishes.
  • TSTLookup keeps the old tree until the new one is read, so peak memory during a load is old + new tree (today the old tree is dropped first); the FST classes already hold the old FST until their assignment.
  • No stored-format change and no cost on the lookup path.

  • With the fix and the test, the whole lucene/suggest module passes with assertions on and off: 32 suites, 237 tests, 7 skipped, 0 failures (TestPersistence, TestAnalyzingSuggester, TestFuzzySuggester, TestFreeTextSuggester, TestFSTCompletion, TestWFSTCompletion included).
  • :lucene:suggest:check -x test flagged one line only, the test's 101-character comment (google-java-format); with it wrapped onto two lines (no code change) check passes, so the five fixed sources are clean. Wrap that comment before the test goes into a PR; the assertions-off module run used the wrapped copy.
  • Earlier, the finder's 8 tests and an independent reproducer's 7 tests passed with the same change, and the exhaustive fault-injection check found 0 mixed states in 6,210 checks.
  • An independent fact check repeated the stock and fixed gradle runs, the module tests and the check in its own scratch worktree, with the same results.

Fix only TSTLookup.load

#

The same change in TSTLookup alone. Not built.

Trade-offs

Removes the broadest throwing symptom, TSTLookup's NullPointerException at most failure points, but leaves the narrow window in which a new AnalyzingSuggester or FuzzySuggester throws NoSuchElementException from some lookups, and the count-only and the score and payload mixes of the other five classes.

Reset to the empty state when load() throws

#

Catch, clear every field, rethrow. Not built.

Trade-offs

Matches "Discard current lookup data" literally, but drops the previous model a caller may still want and needs a per-class reset that is easy to get wrong.

Document that the instance must be discarded after load() throws

#

Javadoc only. Not recommended alone.

Trade-offs

Changes no behaviour: a caller that swaps in a new instance already discards it, and one that does not still serves the half-loaded state. A maintainer may still prefer it: #16951 (open, 2026-10-29) proposes the same kind of answer one level down, a javadoc saying that an IndexInput is in an undetermined state after any IOException while reading.

Verify the stored copy before using it (complement)

#

#6493 (LUCENE-5430, open) proposes a header check before loading; a checksum footer would also catch a cut copy. Not built.

Trade-offs

Does not cover an IOException in the middle of a valid copy, and FreeTextSuggester already checks its header yet assigns count early, so it would sit on top of the recommended fix, not replace it.

Downstream note

#

Solr's SolrSuggester loads its stored file at startup, logs a failed load and keeps serving that same lookup, and it stores without a temporary file, so a store cut short by a crash leads straight to this half-loaded state.

How it was found

#

An exception-safety planning probe loaded stored suggester models cut at every length and found all seven Lookup configurations left mixed. The hunt then injected a cut or an IOException at every byte of every stored model into loaded, built and new instances (6,210 checks, 78 violating configurations, 0 with the fix) and reduced it to a JUnit.

The method in full162 words

Method: non-formal first signal, then semi-formal: a planning probe followed by a bounded-exhaustive fault-injection check (the hunt's hunt unit for suggest lookups whose failed build or load leaves mixed state, 2026-10-28, main a9779ef3c193).

  • Lead. A planning probe for exception safety loaded a stored model cut at every prefix length into a built instance on the stock jars (assertions on and off): all 7 Lookup configurations were left mixed (for example TSTLookup 68 of 69 prefixes, AnalyzingSuggester 87 of 88); the same on the branch_10_6 RC jars.
  • Exhaustive check. A translation-validation harness on the stock jar: 6 Lookups x payload flags x previous state (loaded, built, new) x every cut length and an IOException at every byte; 6,210 checks per assertion mode, the oracle accepting the previous or the empty state: 78 violating configurations, 0 silent loads, 0 violations with the fix.
  • JUnit. Reduced to an 8-test public-API JUnit; the hunt's repro-minimisation step reduced it further to the one test above.

History

#

Introduced in 3.1.0 by SOLR-2375 (e71e6823520, 2011), which gave TSTLookup its first load(); widened to all six Lookups in 4.7.0 by LUCENE-5404 (b5926da2d67, 2014), which made the count the first field every model-reading load() sets. Fails on every executed release that has the API, 3.1.0 to 10.6.0 (the branch_10_6 RC jars), and on main; not a regression.

Versions tested8 rows

Introduced by e71e6823520 (trunk; branch_3x merge ab2691c7740), "SOLR-2375 Store & Load functionality for Suggester Lookup implementations" (Andrzej Bialecki, 2011-03-01; a Solr JIRA issue from before GitHub PRs, not migrated). Its TSTLookup.load replaces the tree and then fills it from the stream. First release 3.1.0 (TSTLookup then in solr-core; first Lucene artifact lucene-spellchecker 3.3.0).

Widened by b5926da2d67 (branch_4x fdf4595051a), LUCENE-5404 = #6467 (Areek Zillur, 2014-02-07, first released in 4.7.0): getCount() and a leading count = input.readVLong() in every model-reading load() (in FreeTextSuggester right after its codec header check). That made FSTCompletionLookup and WFSTCompletionLookup (until then one stream read before any assignment) mixed and put FreeTextSuggester's count ahead of its checks. Per site in between: AnalyzingSuggester's trailer fields from 4.1.0 (LUCENE-4481) and its payload flag from 4.3.0 (LUCENE-4820); FreeTextSuggester's totTokens-before-FST order with the class in 4.6.0 (LUCENE-5214). The repro's symptom (getCount()) applies from 4.7.0; the partial tree and the NullPointerException are older.

LFV-979, snapshot of 2026-11-07

Registry title
Suggest Lookup.load() assigns its count and model fields while it is still reading the stream, so a load that throws (a stored copy cut short, a read failure, or FreeTextSuggester rejecting a model saved with other settings) leaves a mix of the previous and the new model: TSTLookup serves part of the new tree and some lookups throw NullPointerException, AnalyzingSuggester/FuzzySuggester can decode the new FST with the old payload flag, FreeTextSuggester scores the old FST with the new token total, and FST/WFSTCompletionLookup report the new count over the old FST
Area
suggest / Lookup persistence (load() failure atomicity: TSTLookup, AnalyzingSuggester, FuzzySuggester, FreeTextSuggester, FSTCompletionLookup, WFSTCompletionLookup)
Priority
Low, rank 495: A failed Lookup.load() leaves mixed old and new suggester state with some NullPointerException lookups, a minor keep-using-after-failure bug of the same class as LFV-784, so it follows that sibling.
Impact class
minor
Impact note
Applications that use the opt-in suggest Lookups with store()/load() (default constructors and settings, any size, -ea and -da alike) and keep using an instance after its load() threw (a stored copy cut short, for example by an interrupted store(), an I/O error while a valid copy is read, or a FreeTextSuggester model saved with another grams or separator setting) get a state that is neither the previous model nor an empty lookup: for FST/WFSTCompletionLookup, FreeTextSuggester loaded into a fresh instance, the FreeText rejected-model case and most AnalyzingSuggester/FuzzySuggester cut points only getCount() is wrong, while TSTLookup serves part of the new tree and throws NullPointerException on some prefixes (also when the load went into a new instance), AnalyzingSuggester/FuzzySuggester cut in their last 1-2 bytes, after a model with the other payload setting, return the payload glued to the key or the key as the payload (AssertionError with -ea), and FreeTextSuggester loaded over a built model scores the old FST with the new token total; load() does throw first, and a later successful load() assigns every field again [read]; every release from 3.1.0 (TSTLookup) and from 4.7.0 (all six classes) through 10.6.0.
Summary
You build a TSTLookup from {aa, ab, ba, bb, cア}, then call load() with a stored copy of another model that is cut short or whose stream throws IOException part-way, and catch the exception. You expect the lookup to hold either its previous data or no data, but it reports the new model's getCount() and serves part of the new tree, and some lookups throw NullPointerException; the same happens when you load into a newly constructed TSTLookup. The other Lookups do the same in their own way, because each load() assigns count and model fields one after another as it reads: AnalyzingSuggester/FuzzySuggester can decode the new FST with the old payload flag (payload glued to the key), FreeTextSuggester scores the old FST with the new token total and changes getCount() even when it rejects a complete model saved with other grams/separator settings, and FST/WFSTCompletionLookup report the new count over the old FST.
