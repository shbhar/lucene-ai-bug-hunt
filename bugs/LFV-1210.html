ConcurrentMergeScheduler throws NullPointerException when merge logging is switched on during updateMergeThreads

If merge logging is switched on while ConcurrentMergeScheduler.updateMergeThreads runs, the method throws NullPointerException: its first "is logging on?" check said no, so it never created its log buffer, and a later check says yes and uses it. setForceMergeMBPerSec(10.0) fails this way on main and in every release checked since 5.0.0.

The finding in 30 seconds

#

updateMergeThreads asks "is merge logging on?" at three places in one call (the second once per running merge). It creates its log buffer only if the first answer is yes, but uses the buffer whenever a later answer is yes. A no-then-yes sequence dereferences null.

Background: merge-scheduler logging

#
  1. IndexWriterConfig.setInfoStream installs an InfoStream, Lucene's debug log (default: NO_OUTPUT, always off). Before building a message, code asks isEnabled(component); the merge scheduler asks for "MS" through verbose().
  2. The answer may change while the writer runs: JavaLoggingInfoStream answers Logger.isLoggable(level), so raising a java.util.logging level switches merge logging on.
  3. ConcurrentMergeScheduler.updateMergeThreads re-applies the IO rate of every running merge and logs one message per call. It runs in the three IO-throttle setters, at every merge start and finish, and on close.

The finding, step by step

#
  1. Give IndexWriterConfig an InfoStream that follows a log level, such as Lucene's JavaLoggingInfoStream, with merge-scheduler logging (component "MS") off, and use a ConcurrentMergeScheduler.
  2. Switch merge logging on while the writer is open. If the switch lands inside one updateMergeThreads call (it runs in setForceMergeMBPerSec, enableAutoIOThrottle, disableAutoIOThrottle and at every merge start and finish), you expect the call to finish and logging to start, as with a constant InfoStream and as in 4.10.
  3. Instead the call asked twice: at line 354 the answer was false, so the log buffer stayed null; at line 437 it was true, so it calls message.toString(): NullPointerException ... because "message" is null. In the repro setForceMergeMBPerSec(10.0) throws after storing 10.0, with assertions on and off.
  4. At a merge start the same exception makes merge() hand back the merge that is already running. A probe then saw a second merge of the same segments and a tragic writer close; that hand-back is LFV-208's mechanism, which this bug can trigger.

Who is affected

#

Only applications with a non-default InfoStream whose answer changes at runtime (Lucene's JavaLoggingInfoStream or a logger-backed one of their own) that switch merge logging on while the writer runs, and only when the switch lands inside one short call. The default InfoStream is never affected. Present since 5.0.0.

Mechanism, terms and numbers358 words

ConcurrentMergeScheduler.updateMergeThreads builds one log message per call in a StringBuilder. It creates the builder only if its first verbose() check is true and sets it to null otherwise (ConcurrentMergeScheduler.java:353-364 at 5adff78bb168), then calls verbose() again before appending one line per running merge (:391-397) and before logging the message (:437-438). verbose() re-reads infoStream.isEnabled("MS") on every call (MergeScheduler.java:93-95). If merge logging is switched on between the first check and a later one, for example by raising a log level under Lucene's own JavaLoggingInfoStream, the later check dereferences the null builder and the call throws NullPointerException. It is reachable from the public setters setForceMergeMBPerSec, enableAutoIOThrottle and disableAutoIOThrottle and from every merge start and finish. The window is one short call, so it is rare. The shared builder came with LUCENE-6119 (5.0.0); in 4.x each check guarded its own log call, and the same scenario returns normally on 4.10.3 and 4.10.4.

The bug, step by step (main 5adff78bb168)

#
  1. setForceMergeMBPerSec stores the value and calls updateMergeThreads() (ConcurrentMergeScheduler.java:199-202); enableAutoIOThrottle (:214-218) and disableAutoIOThrottle (:225-228) do the same. merge() calls it right after newMergeThread.start() (:590-591), runOnMergeFinished in its finally block (:691-697), and merge(CLOSING) at :544-547.
  2. Check 1 (:354): if (verbose()) { message = new StringBuilder(); ... } else { message = null; } (:363). Logging is off, so message is null.
  3. Merge logging is switched on now.
  4. Check 2 (:391, once per running merge thread): if (verbose()) is true, then message.append('\n') (:397): NPE, before that merge's rateLimiter.setMBPerSec(newMBPerSec) (:435); with the switch before the loop, this pass sets no merge's new rate.
  5. Check 3 (:437, reached even with no merge thread, as in the repro): if (verbose()) is true, then message(message.toString()) (:438): NPE.

True to false is harmless: the builder exists and is just not logged. Each check on its own follows the documented idiom if (verbose()) { message(...) } (MergeScheduler.java:83-92); the method breaks it by creating its data under one answer and using it under another.

Exposure and likelihood333 words
  • Who is hit. Applications that install an InfoStream whose isEnabled("MS") answer can change: Lucene's JavaLoggingInfoStream (advertised in MIGRATE.md) or their own logger-backed one, with merge logging switched on while the writer is open. The default NO_OUTPUT (always false) and PrintStreamInfoStream (always true) are not affected.
  • Window. The switch must land inside one updateMergeThreads call, a narrow window (its duration was not measured; the method is synchronized, but that only orders the scheduler's own calls, not a Logger.setLevel on another thread); the call runs at every merge start and finish, on close, and in the three setters. A supporting probe with an unmodified JavaLoggingInfoStream and another thread that keeps toggling the "MS" logger's level hit the NPE after 34 setter calls; that toggling rate is not realistic, so it only shows reachability.
  • Setter. A loud NPE after the value is stored. With merges running, the merges the loop had not yet reached (all of them if logging switched on before the loop) keep their old rate until the next updateMergeThreads call.
  • Merge start. The NPE lands in merge()'s catch (Throwable t) { mergeSource.onMergeFinished(merge); throw t; } (:592-594), which hands back a merge whose thread already runs. A supporting probe then saw a second merge of the same segments registered and a tragic writer close (-ea: AssertionError at IndexWriter._mergeInit; -da: NPE at IndexWriter.closeMergeReaders). A tragic close rolls the writer back (IndexWriter.java:6097-6103), which discards changes since the last commit; that is read from the code, the probe did not check documents. That hand-back is LFV-208's mechanism, with its own root cause and fix site; this bug is one more trigger for it.
  • Merge finish. The NPE skips notifyAll() and ends the merge thread through handleMergeException after the merge completed; stalled indexing threads wait at most 250 ms per round (doStall), so nothing hangs.
  • Likelihood. No scale or index content is involved, and no public report of it was found since 2015: rare.

Why it looks unintended

#
  • isEnabled promises no stable answer, and Lucene ships JavaLoggingInfoStream, whose answer follows a runtime log-level change.
  • isEnabled was added (#4672) so logging can be switched on and off "live"; only the caller can read the answer once per call.
  • In 4.x each check guarded its own log call; 4.10.3 and 4.10.4 pass the same scenario.
The full argument189 words
  • Contract. InfoStream.isEnabled is documented only as "returns true if messages are enabled and should be posted to message" (InfoStream.java:53-54). verbose() is documented as "usually used in conjunction with message(String)", with the paired if (verbose()) { message(...) } idiom (MergeScheduler.java:83-92). IndexWriterConfig.setInfoStream(InfoStream) is public and accepts any non-null InfoStream (IndexWriterConfig.java:430).
  • Design history. LUCENE-3598 (#4672, 2011) introduced isEnabled for logging that "is enabled or disabled dynamically": "Using this you could enable/disable logging live by e.g. the log4j management console" (Uwe Schindler, in the issue description, answering a request by Shai Erera). Robert Muir supported it because "it makes it possible for someone to turn on/off infostream \"live\" themselves".
  • Tests. The 15 isEnabled overrides in Lucene's test sources (14 in lucene/core/src/test, for example TestConcurrentMergeScheduler.java:801-803, and 1 in lucene/test-framework/src/test) and the 4 InfoStreams in the test framework's own code (RandomIndexWriter, BaseMergePolicyTestCase, NullInfoStream, FailOnNonBulkMergesInfoStream) each answer a fixed value per component, so no test switches logging during a call and nothing asserts the current behaviour.
  • History. The shared builder came with LUCENE-6119 (#7181, 2015); its 28 comments never discuss it.
The devil's-advocate check200 words

The argument (an independent reviewer from another model family, OpenAI GPT-5.6, which reproduced the NPE and agreed on the root cause, still judged it not real, "not a supported Lucene API defect"): InfoStream is @lucene.internal, a "Debugging API" (InfoStream.java:23-28), and so is Lucene's own JavaLoggingInfoStream (JavaLoggingInfoStream.java:30); MergeScheduler is @lucene.experimental. A public setter that takes an internal type does not by itself make a stable contract, and nothing promises support for an isEnabled answer that changes within one call. In #4672 Robert Muir also said implementers "are responsible for their own implementation (if they want to make stuff volatile or synced, good for them)".

Why it does not settle it. Lucene ships JavaLoggingInfoStream and points users to it (MIGRATE.md:1162-1163), and its answer follows Logger.setLevel; live switching is the stated purpose of isEnabled; and an InfoStream cannot keep its answer stable across a call whose start and end it cannot see. Volatile or synchronized state inside the InfoStream does not help a caller that asks twice. What survives: both types are internal, so a maintainer may well call the change a defensive cleanup rather than a bug; the fix is the same.

Suggested fix

#

Recommended A. Read verbose() once per call (recommended)

Read verbose() once at the top of updateMergeThreads into final boolean verbose and use that local at all three check sites (one file, +4/-3). The repro then passes with assertions on and off, and TestConcurrentMergeScheduler and TestMergeSchedulerExternal pass (24 of 24 tests).

-    if (verbose()) {
+    if (verbose) {
       message = new StringBuilder();
 ...
-      if (verbose()) {
+      if (verbose) {
         long mergeStartNS = merge.mergeStartNS;
 ...
-    if (verbose()) {
+    if (verbose) {

All options and trade-offs3 options · 351 words

Option A is the smallest change and keeps the documented idiom per call. B is equivalent in behaviour; C trades the null for extra work or a headless message. None of them changes LFV-208: its fix (do not hand back a merge whose thread already started) is separate and it has other triggers.

At the top of updateMergeThreads, final boolean verbose = verbose();, and if (verbose) at the allocation (:354), the per-thread lines (:391) and the final log call (:437).

Trade-offs

Logging switched on mid-call starts with the next call, so one updateMergeThreads message is not logged; logging switched off mid-call still logs that call's one message, which today's code would drop. One isEnabled call per invocation instead of N+2 (N = running merges).

B. Guard the later uses with message != null (not run)

Replace the two later if (verbose()) checks with if (message != null).

Trade-offs

Same behaviour as A, including the switch-off case (the builder doubles as the flag); slightly less obvious, because the guard no longer says "is logging on".

Trade-offs

Avoids the null, but the method then either formats its header on every call with logging off, or logs a message without its header after a mid-call switch. Not recommended.

Downstream note

#

Downstream products that bridge Lucene's InfoStream to their logging framework and let operators change log levels at runtime could see this exception from merges or IO-throttle settings; queries, documents and index files cannot reach it.

How it was found

#

A proof-obligation audit of updateMergeThreads: every use of its log buffer must be guarded by the same "is logging on?" answer that created it. The method asks verbose() again before each use, so the obligation fails when the answer turns from no to yes mid-call. A one-method JUnit test that calls only public methods then witnessed the NPE.

The method in full101 words

The audit took the logging idiom that MergeScheduler documents (if (verbose()) { message(...) }) and checked updateMergeThreads, which splits one message across several checks. In updateMergeThreads the buffer is created under the first answer and dereferenced under later, separately read answers, and verbose() re-reads isEnabled("MS") each time, so nothing ties them together.

An executable repro that calls only public methods witnessed it on main with assertions on and off. An independent reproducer, an executed cross-model review (OpenAI GPT-5.6, refute lens), a devil's-advocate verifier and an adjudication then checked it, and a version sweep placed it in LUCENE-6119 (5.0.0).
