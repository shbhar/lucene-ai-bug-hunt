Bulk BinaryDocValues#binaryValues sizes its buffer in int

The default codec's bulk BinaryDocValues#binaryValues, new in 10.6, sizes its buffer in int: one call for 2 GiB or more fails; from 4 GiB, a contiguous call with assertions off can return other documents' bytes. CheckIndex at level 2 or 3 can call healthy indexes of huge fixed-length values broken.

The bug in 30 seconds

#
  1. Index three documents with a 1 GiB binary doc value each on the default codec, and forceMerge(1) them into one segment.
  2. Fetch docs 0 and 2 in one bulk call, binaryValues(2, {0, 2}, values), as CheckIndex does on a 3-document segment. You expect the per-value loop's result, first bytes 0 and 2.
  3. Instead the codec sizes one shared array for both values as an int: 2 x 2^30 wraps to -2,147,483,648, and the call throws NegativeArraySizeException.
  4. The branch_10_6 or main CheckIndex -level 2, on such an index written by 10.5.2, prints docvalues ERROR [-2147483648] and "1 broken segments" and exits 1, where 10.5.2's finds no problems; with -exorcise, the branch_10_6 one dropped the segment and all 3 of its documents.
  5. From 4 GiB the size can wrap to a small positive number: one contiguous call for docs 0 to 31, 32 values of 138,547,333 bytes, with assertions off, returns normally with 31 of the 32 values wrong.

Who is affected

#

CheckIndex at level 2 or 3 (not the default 1) and callers of the new bulk API on the default codec via a plain DirectoryReader or SegmentReader. Rare: one call on a dense field must total 2^31 - 2 bytes or more; for CheckIndex, fixed-length values of 128 MiB or more. Older-release indexes are flagged too. Unreleased until 10.6.0.

Mechanism, terms and numbers584 words

On the default codec, the bulk read of binary doc values that is new in 10.6 puts the requested values of a dense field into one shared array whose size is computed as a Java int. One call that asks for 2 GiB or more fails; at 4 GiB or more the size can wrap and, with assertions off, the call can return other documents' bytes. CheckIndex at level 2 or 3 makes such calls itself, so it can report a healthy index as broken.

Binary doc values store one byte string per document, column-wise (BinaryDocValuesField). A field is dense when every document has a value, and fixed length when all values have the same length. The writer accepts values of up to ArrayUtil.MAX_ARRAY_LENGTH bytes each (2,147,483,631 on this JVM), and segments may hold far more than 2 GiB in total.

#16286 added a bulk read, BinaryDocValues#binaryValues(size, docs, values), new in 10.6.0. Its javadoc says the result "behaves as if implemented as below, which is the default implementation": a loop of advanceExact(doc) plus BytesRef.deepCopyOf(binaryValue()). It states no size limit.

The default codec stores doc values with Lucene90DocValuesFormat, and for dense fields it overrides the bulk method. It reads all requested values into one shared byte[], and every returned BytesRef is a window into it. The array size is a Java int (at most 2^31 - 1 = 2,147,483,647), and larger values wrap around by 2^32:

  • fixed length: byte[] bulk = new byte[size * length]; (main Lucene90DocValuesProducer.java:1347), computed before the contiguity check, so non-contiguous requests use it too;
  • variable length, consecutive doc ids: int totalBytes = (int) (lastEnd - firstStart); then new byte[totalBytes] (main :1393-1394);
  • the window offsets use the same int arithmetic (:1352, :1356, :1399).

The wrong-bytes case

#

32 documents of 138,547,333 bytes, one call for docs 0 to 31: T = 4,433,514,656 wraps to 138,547,360, so the array holds doc 0 plus the first 27 bytes of doc 1. With assertions off the call returns normally and 31 of the 32 values differ from the per-value API. Doc 0's window is correct. Doc 31's offset, 31 x 138,547,333 = 4,294,967,323, wraps to 27: its window is in bounds and passes isValid(), but it holds doc 0's bytes from position 27 on. The other 30 windows are out of bounds. With -ea the call throws IllegalStateException: offset+length out of bounds from the BytesRef constructor's assertion.

CheckIndex

#

#16286 also made CheckIndex call the bulk API (checkBulkFetchBinaryDocValues, main CheckIndex.java:4193-4234): checkIndex() runs it at level 2 or higher, and the public static CheckIndex.testDocValues runs it with no level gate. It asks in batches of up to 16 documents with gaps (0, 2, 5, 9, ...). A batch of two or more documents is never contiguous, so only fixed-length fields are affected. When one batch totals at least 2^31 - 2 bytes, CheckIndex prints test: docvalues...........ERROR [...] and "1 broken segments", and exits 1. Following its advice, -exorcise dropped the segment and every document in it.

Exposure and likelihood337 words
  • Who is exposed. Callers of the new bulk API on the default codec that hold the codec's own iterator (a plain DirectoryReader or SegmentReader). Wrapping readers skip the override, because FilterBinaryDocValues does not forward binaryValues (for example ExitableDirectoryReader), and no query, collector or sort in Lucene calls it. The one in-tree production caller is CheckIndex at -level 2 or -level 3; the default CLI level 1 is not affected.
  • Symptoms. Usually loud: an OutOfMemoryError or NegativeArraySizeException. Silent wrong bytes need at least 4 GiB in one contiguous call with assertions off; the wrong bytes always belong to other documents in the same call, field and segment.
  • CheckIndex reports a valid index as broken. It is a read-side bug: indexes written by the released 10.5.2 and 9.12.3 jars are flagged as soon as the 10.6 CheckIndex reads them at level 2. Smallest triggering shapes: a 3-to-5-document segment of equal values of at least 2^30 - 1 bytes (about 3 GiB), or 40 or more documents of at least 128 MiB (5 GiB). -exorcise then removes the segment; opening an IndexWriter afterwards deletes its files for good.
  • Scale. Rare: one call must total at least 2^31 - 2 bytes, for example 2 x 1 GiB or 32,768 x 64 KiB. Typical binary values are small.
  • Test suites. TestUtil.checkIndex and the BaseDirectoryWrapper check on close (both at level 3), and TestUtil.checkReader (through the ungated CheckIndex.testDocValues), reach it only when the doc values are not wrapped by the Asserting codec, whose AssertingBinaryDocValues runs the default loop. Downstream test suites with such data can fail with some random codecs; Lucene's randomized tests with the Asserting codec cannot catch it.
  • Unreleased. The API ships first in 10.6.0 unless fixed; releases 9.0.0 to 10.5.2 do not have it. The existing bulk tests use 512 documents of 8 bytes, or of 1 to 32 bytes. The large tests written for this bug (local branches, not upstream) are @Monster, which is off by default, and no in-repo workflow enables it.

Why it is a bug, not intended

#
  • The javadoc's contract is the per-value loop with no size limit; that loop is correct in every failing case.
  • The writer accepts values up to MAX_ARRAY_LENGTH bytes, Lucene90 documents no read limit, and CheckIndex users cannot choose the batch.
  • The numeric sibling longValues checks its size as a long and falls back above Integer.MAX_VALUE; this int buffer arrived in review.
The full argument234 words
  • The contract is the per-value loop. The javadoc (BinaryDocValues.java:39-82) defines the result as the default loop and states only that doc ids are ascending with no duplicates. That loop, run through FilterBinaryDocValues, returns correct values in every failing case, and so does the per-value API on the same documents.
  • No documented limit. The writer accepts each value up to MAX_ARRAY_LENGTH, and Lucene90 documents no read-side limit. The expected objection is DocValuesType.BINARY's "different codecs may enforce their own limits"; Lucene90 enforces its limit at write time, on single values, and the same values read back correctly one at a time.
  • History shows an accident, not a design. The PR's first codec commit (5d5ad9b85d, 2026-06-23) allocated one array per value and could not overflow. After a reviewer asked on 2026-06-26 for something more compact than BytesRef[], commit d26fd36beb "Improve SIMD implementation by reducing allocations" added new byte[size * length] and the (int) cast. No comment or review in the PR mentions a size limit.
  • The numeric sibling has a guard. NumericDocValues#longValues (#16129, same author, shipped in 10.5.0) computes the byte count as a long and falls back to the default when it exceeds Integer.MAX_VALUE (main Lucene90DocValuesProducer.java:676-679), and #16286's description opens with "Mirrors NumericDocValues#longValues for binary fields".
  • Lucene's own caller cannot avoid it. CheckIndex chooses the batch size, and it reports as broken an index that 10.5.2 reports clean.
The devil's-advocate check161 words

The intended-behaviour checker argued the other side. The best case for "intended or acceptable": Java arrays are int-sized; this is a performance API where the caller picks size (the PR benchmarked 8-128 byte values in batches of 1024); DocValuesType.BINARY allows codec limits; SECURITY.md makes limits on unbounded input the caller's job; and the API is unreleased.

Why that case fails: the javadoc contract is the per-value loop with no size precondition; Lucene90 documents no read limit and accepts the values at write time; CheckIndex picks the batch, so a -level 2 user cannot avoid it; calls of 4 GiB or more silently return wrong bytes, which no reading of the contract allows; and the int buffer arrived with a review-time allocation optimization. Verdict: not intended and not documented; a real bug that is hard to reach. Not a security issue: the size is chosen by the caller and the JVM's bounds checks hold, so a public issue is the right channel.

Suggested fix

#

Recommended Fall back to the per-value default above ArrayUtil.MAX_ARRAY_LENGTH

Before each allocation, compare the total, as a long, with ArrayUtil.MAX_ARRAY_LENGTH; above it, fall back to the documented per-value loop (super.binaryValues). Two guards, 10 lines plus one import, on local unpushed branches. With the fix, the lucene90 codec, CheckIndex and doc-values tests (844 on branch_10_6, 861 on main) have 0 failures; CheckIndex levels 1-3 are clean.

if ((long) size * length > ArrayUtil.MAX_ARRAY_LENGTH) {          // fixed length, before new byte[]
  // too many bytes for a single array
  super.binaryValues(size, docs, docsOffset, values, valuesOffset);
  return;
}
...
if (lastEnd - firstStart > ArrayUtil.MAX_ARRAY_LENGTH) {          // variable length, before the cast
  // too many bytes for a single array
  super.binaryValues(size, docs, docsOffset, values, valuesOffset);
  return;
}

Trade-offs

  • Behaviour changes only when one call totals more than MAX_ARRAY_LENGTH bytes. Between 2,147,483,632 and 2,147,483,645 bytes the old code worked; the fix now takes the slower, correct per-value path there.
  • Cost: one long multiply and compare per call (SECURITY.md asks that robustness fixes not slow hot paths). The fallback allocates the same total bytes, one array per value.
  • The CHANGES entry has GITHUB#TBD placeholders and says "2GB": write "2 GiB" or name the real cap. Open PR #16832 edits the same variable-length loop and keeps the int cast; the two patches apply in either order. #16896 fixes a different overflow in the same file.

A lower cap

#

Fall back earlier, to avoid single arrays of nearly 2 GiB.

Trade-offs

More calls take the per-value path; the cut-off is a judgement call.

Chunk the read into several arrays

#

Keep the bulk read but split it across arrays that each stay under the limit.

Trade-offs

More code in a hot path; the returned windows then point into several arrays.

Allocate the shared array only on the contiguous fixed-length path

#

Non-contiguous fixed-length requests would read value by value without the shared array.

Trade-offs

A complement to the guard, not a fix on its own: a contiguous request over 2 GiB still overflows.

Integer.MAX_VALUE as the cap, like longValues

#

Mirror the numeric sibling's guard exactly.

Trade-offs

Leaves the 2-byte band (2^31 - 2 and 2^31 - 1) where the JVM refuses the array with an OutOfMemoryError, so MAX_ARRAY_LENGTH is safer.

How it was found

#

An AI tool built a CodeQL inventory of 602 int multiplications and left shifts, ranked it by git blame age and turned the method at Lucene90DocValuesProducer.java:1347 into Z3 bit-vector checks, which gave counterexamples; a JUnit repro followed. The task had named the area, integer arithmetic that breaks only at scale. A separate AI verifier found the CheckIndex consequences.

Method: a CodeQL inventory of integer arithmetic, then bit-vector SMT checks of the transcribed method (the study's "formal" tier: the solver's counterexample came first). Run 3 of the study, experiment "overflow-at-scale" (2026-10-22, main 7cecf79523):

  1. An AI tool built a CodeQL 2.27.3 inventory of non-constant int multiplications and left shifts in a list of packages that includes codecs/lucene90: 602 rows. The query also includes x * C and drops products that CodeQL's range analysis can bound.
  2. It ranked the rows by git blame age. The row Lucene90DocValuesProducer.java:1347 binaryValues array-size dated from 2026-06-30, about four months old.
  3. It transcribed the method into Z3 4.12.2 bit-vector obligations: B1 "the int product is exact" gave a counterexample; B1w, the witness size = 2, length = 2^30, gives a negative size; B2, the variable-length narrowing cast (not a CodeQL row; the AI tool added it while transcribing), gave a counterexample. cvc5 1.4.2 later returned sat on all three.
  4. It wrote a JUnit repro on main (2 x 1 GiB). Order by file times (UTC): CodeQL 05:35, blame 05:43, first Z3 run 05:57, JUnit repro 06:14, final Z3 run and cvc5 06:59.

That AI tool believed, wrongly, that CheckIndex reaches only the per-document branch.
