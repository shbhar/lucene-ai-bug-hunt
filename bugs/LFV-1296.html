MultiReader.close() leaves later sub-readers open when closing an earlier one throws an unchecked exception

If closing one sub-reader of a MultiReader throws an unchecked exception, for example from a reader-closed listener, close() rethrows it but never closes the sub-readers after it, and a second close() cannot release them. Every release since 1.4; ParallelLeafReader and ParallelCompositeReader have the same loop.

The finding in 30 seconds

#

MultiReader.doClose() closes its sub-readers in a loop that catches only IOException, so it can keep going and rethrow the first failure. An unchecked exception from one sub-reader's close is not caught: it ends the loop, and the sub-readers after it are never closed.

Background in three steps

#
  1. A MultiReader combines several readers into one view. The varargs constructor closes its sub-readers when the MultiReader is closed; with closeSubReaders = false it only releases the reference it took on each.
  2. An application can register closed listeners on a reader (getReaderCacheHelper().addClosedListener(...)), for example to evict cache entries. They run when that reader closes.
  3. Since LUCENE-5553 (2014), a reader whose close or listener throws still finishes closing and then rethrows the first exception. Lucene's TestIndexReaderClose checks this with an IllegalStateException.

The finding, step by step

#
  1. You open two readers, r1 and r2, on an empty index and give r1 a reader-closed listener that throws IllegalStateException. You wrap them as new MultiReader(r1, r2), which closes its sub-readers when it is closed.
  2. You call close(). You expect both readers to be closed and the exception rethrown, which is what happens when the listener throws an IOException instead, and what the javadoc says: "all subreaders are closed if this Multireader is closed".
  3. Instead close() rethrows the exception after closing r1 only: r2.getRefCount() is still 1. r2 stays open, so on a non-empty index its segment files stay open, and any closed listeners on it do not run.
  4. The cause: doClose() wraps each sub-reader's close in a try that catches only IOException, so the unchecked exception ends the loop.
  5. A second close() does nothing, because the MultiReader already counts as closed, so it cannot release r2; code that kept its own reference to r2 still can.

Who is affected

#

Applications whose own code makes a sub-reader's close throw an unchecked exception: a reader-closed listener that throws (for example an UncheckedIOException), or a Filter*Reader whose doClose throws. No Lucene code outside its tests was found to do this. Every later sub-reader keeps its files open; close() still throws, and no wrong-result or index-damage mechanism was found.

Mechanism, terms and numbers599 words

MultiReader.doClose() closes (or decRefs) its sub-readers one by one and catches only IOException, so that it can keep going and rethrow the first failure. A RuntimeException or Error from one sub-reader's close is not caught: it ends the loop, and every later sub-reader stays open. The source is application code: for example a reader-closed listener that throws an unchecked exception, such as an IllegalStateException or an UncheckedIOException. The MultiReader already counts as closed by then, so a second close() does nothing and cannot release the skipped readers.

The sibling StandardDirectoryReader.doClose() was changed in 2012 to keep going on any Throwable and now uses IOUtils.applyToAll; MultiReader, ParallelLeafReader and ParallelCompositeReader never were. Every release since 1.4 is affected. The fix is IOUtils.applyToAll in the three doClose methods.

The bug

#
  1. MultiReader.doClose() (MultiReader.java:96-112) loops over getSequentialSubReaders() and calls r.close() (closeSubReaders = true, the default of the varargs constructor, :49-51) or r.decRef() inside try { ... } catch (IOException e) { if (ioe == null) ioe = e; } (:100-108), then rethrows the first (// throw the first exception, :110-111). Nothing catches a RuntimeException or an Error.
  2. When a sub-reader's refCount drops to 0, IndexReader.decRef() (IndexReader.java:215-232) sets closed = true, runs doClose() and then the closed listeners (try (Closeable _ = this::notifyReaderClosedListeners), :224-227). When doClose() completes normally, as in the repro, a listener's unchecked exception propagates after that sub-reader is fully closed; when doClose() itself throws, that exception propagates and the listener's is added to it as suppressed.
  3. That exception leaves the MultiReader loop at the first sub-reader. r2 and any later sub-readers are never closed or decRef'd.
  4. The MultiReader was closed through the same decRef(), which set its own closed = true before doClose() ran (IndexReader.java:224). IndexReader.close() returns at once when closed is set (:351-356), and getContext() calls ensureOpen() (CompositeReader.java:93-94). So the MultiReader's public API cannot release the skipped readers any more; only code that kept its own reference to them can (or a subclass, through the protected getSequentialSubReaders(), which does not check ensureOpen(), CompositeReader.java:90). That a second close() does nothing holds since LUCENE-5553 (4.7.1, 2014): before it, a failed doClose() put the refCount back (IndexReader.java:229-239 at the 4.7.0 tag).

What stays behind (executed)

#

In the repro, r2.getRefCount() is 1 after MultiReader.close() has thrown. Controls by an independent reproduction: a checked IOException from the same listener lets the loop close r2; an UncheckedIOException from the listener, a FilterDirectoryReader sub-reader whose doClose throws IllegalStateException, and the closeSubReaders = false (decRef) path all leave r2 open (with false, the reference the MultiReader took is never released, so the owner's own close() later does not close it either). The closed-listener API is @lucene.experimental (IndexReader.java:138); the wrapper trigger needs no experimental API.

The same loop in two other readers

#

ParallelLeafReader.doClose() (ParallelLeafReader.java:377-393) and ParallelCompositeReader.doClose() (ParallelCompositeReader.java:169-185) have the identical IOException-only loop over completeReaderSet, an identity-hash set, so which later member stays open is unspecified. A probe for this doc (two sub-readers that both throw on close, so whichever is visited first stops the loop) leaves one of the two open in each reader on stock main and closes both with fix A.

Exposure and likelihood178 words
  • Who: applications that close a MultiReader (or a ParallelLeafReader / ParallelCompositeReader) while one sub-reader's close throws an unchecked exception. That needs the application's own code: a closed listener that throws, for example by wrapping an I/O failure in UncheckedIOException, or a FilterDirectoryReader / FilterLeafReader subclass whose doClose throws. No Lucene code outside its tests was found to do this (Lucene's own TestIndexReaderClose does it on purpose). Otherwise default settings; no scale needed.
  • Effect: every sub-reader after the failing one stays open: its files stay open and its closed listeners (for example cache eviction) do not run. With closeSubReaders = false, the reference the MultiReader took is never released, so the owner's later close() does not close the reader either.
  • What is not lost: close() does throw, so the failure is visible; what is lost silently is the release of the later readers. No wrong-result or index-damage mechanism was found; the cost is the leaked readers and the files they keep open.
  • Likelihood: rare: the searches found no public report since MultiReader was added in 2004.

Why it looks unintended

#
  • The javadoc: "Note that all subreaders are closed if this Multireader is closed" (MultiReader.java:45); the loop itself keeps going after an IOException and rethrows the first.
  • Lucene's TestIndexReaderClose#testCloseUnderException throws IllegalStateException from a listener and from doClose and requires the close to finish.
  • The identical loop in StandardDirectoryReader was changed in 2012 to handle any Throwable and now uses IOUtils.applyToAll.
The full argument214 words
  • The javadoc promises it. The varargs constructor: "Note that all subreaders are closed if this Multireader is closed" (MultiReader.java:45); closeSubReaders "indicates whether the subreaders should be closed when this MultiReader is closed" (:57-58).
  • The loop is written to keep going. It collects the first IOException, closes the rest and rethrows it (:98-111); it only misses the unchecked case.
  • Lucene tests the unchecked case for a single reader. LUCENE-5553 (#6615, a8b93f272f7, 2014) made a failing close still close the reader and run every listener. Its TestIndexReaderClose#testCloseUnderException throws IllegalStateException from a listener (FaultyListener, TestIndexReaderClose.java:166-172) and from doClose (:60-68) and requires the close to finish (:88-102).
  • The sibling loop was fixed. StandardDirectoryReader.doClose() had the same IOException-only loop; it was changed to catch Throwable and keep going in a97703f1dfc (Michael McCandless, 2012-10-03, "handle Throwable not just IOE when closing"). That commit dropped the caught exception (if (t == null) firstExc = t;); 4a41604dcad (Robert Muir, LUCENE-4456, 2012-10-04) corrected it to keep the first one. The loop moved to IOUtils.applyToAll in LUCENE-8215 (#9262, 2e35ef2b3da, 2018), under the comment "try to close each reader, even if an exception is thrown" (StandardDirectoryReader.java:564-566). MultiReader and the two Parallel* readers were not touched.
The devil's-advocate check175 words

The strongest case for "intended": ClosedListener.onClose is @lucene.experimental and declares only throws IOException (IndexReader.java:135-146), doClose declares only IOException, the declared exception is handled correctly, no Lucene listener outside its tests throws unchecked, and the caller does see the exception, so a listener that throws IllegalStateException is an application bug. An independent reviewer from another model family (OpenAI GPT-5.6) rated this argument "moderate". Two related points a reviewer may raise: closing the other readers after an Error is a policy choice (see Fixes), and before LUCENE-5553 a failed close put the refCount back, so the "a second close() does nothing" part is newer than the loop.

Why it fails: Lucene's own close test throws exactly such an IllegalStateException from a listener and from doClose and requires everything to be closed, and the identical sibling loop was changed on purpose to handle any Throwable. The argument bears on severity (Low), not on intent. Not claimed: calling decRef on a sub-reader the caller already closed (with closeSubReaders = false), which is caller misuse.

Suggested fix

#

Recommended A. IOUtils.applyToAll in all three doClose methods (validated)

Replace each of the three doClose loops with IOUtils.applyToAll(..., closeSubReaders ? close : decRef), the idiom StandardDirectoryReader already uses: it closes every sub-reader, rethrows the first exception and suppresses the rest. The repro and a probe of both Parallel* readers pass, and so do 13 nearby core test classes.

// MultiReader.doClose()
IOUtils.applyToAll(
    getSequentialSubReaders(), closeSubReaders ? IndexReader::close : IndexReader::decRef);
// ParallelLeafReader.doClose()
IOUtils.applyToAll(completeReaderSet, closeSubReaders ? LeafReader::close : LeafReader::decRef);
// ParallelCompositeReader.doClose()
IOUtils.applyToAll(
    completeReaderSet, closeSubReaders ? IndexReader::close : IndexReader::decRef);
All options and trade-offs3 options · 403 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B is the change the finding was first checked with; C is by reading.

A. IOUtils.applyToAll in all three doClose methods (validated) (recommended)

#

In MultiReader.java:96-112, ParallelLeafReader.java:377-393 and ParallelCompositeReader.java:169-185, replace the loop with one call, plus import org.apache.lucene.util.IOUtils; (11 lines added, 42 removed):

// MultiReader.doClose()
IOUtils.applyToAll(
    getSequentialSubReaders(), closeSubReaders ? IndexReader::close : IndexReader::decRef);
// ParallelLeafReader.doClose()
IOUtils.applyToAll(completeReaderSet, closeSubReaders ? LeafReader::close : LeafReader::decRef);
// ParallelCompositeReader.doClose()
IOUtils.applyToAll(
    completeReaderSet, closeSubReaders ? IndexReader::close : IndexReader::decRef);

Trade-offs

  • The smallest change; nothing changes when no sub-reader throws, and the close order is the same iteration.
  • It also improves a mixed case: today, if the first sub-reader throws IOException and a later one an unchecked exception, the unchecked one escapes and the IOException is lost; with the fix the first is rethrown and the later one suppressed.
  • An Error is still rethrown, but only after the other readers are closed. That matches IOUtils.close and StandardDirectoryReader.doClose() today, but it is a policy choice: a reviewer may prefer not to keep closing after an Error such as OutOfMemoryError.
  • CHANGES: a Bug Fixes entry.

  • A probe of ParallelCompositeReader and ParallelLeafReader (two sub-readers that both throw on close): stock, 2 of 2 fail with one sub-reader left open; with the fix, 2 of 2 pass.
  • With the fix and the repro: TestIndexReaderClose, TestReaderClosed, TestParallelCompositeReader, TestParallelLeafReader, TestParallelReaderEmptyIndex, TestParallelTermEnum, TestDirectoryReader, TestDirectoryReaderReopen, TestFilterDirectoryReader, TestFilterLeafReader, TestPointValues, TestIndexSearcher, TestTermQuery and the repro: 14 classes, 147 tests, 0 failures, 1 skipped (an assumption in TestIndexSearcher that needs two documents in one segment).

Downstream note

#

Downstream, a service whose reader-closed listeners (for example cache eviction hooks) can throw an unchecked exception should not assume that closing a MultiReader released every sub-reader.

How it was found

#

Non-formal: reading MultiReader's close path against the close-under-exception contract IndexReader has had since LUCENE-5553 (a failing close still closes everything and rethrows the first exception). The IOException-only catch breaks that contract for unchecked exceptions; a one-test JUnit witnessed it on stock main.

The method in full73 words
  • Contract: IndexReader.decRef() closes a reader and runs its listeners even when one of them throws (LUCENE-5553, TestIndexReaderClose#testCloseUnderException), and MultiReader's javadoc says all sub-readers are closed with it.
  • Finding: MultiReader.doClose() catches only IOException (MultiReader.java:106), so an unchecked exception from one sub-reader's close ends the loop.
  • Witness: one JUnit test with a throwing closed listener, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Impact class
minor
Impact note
Only applications whose own code makes a sub-reader's close throw an unchecked exception are hit: a reader-closed listener (IndexReader.CacheHelper#addClosedListener) that throws, e.g. IllegalStateException or UncheckedIOException, or a FilterDirectoryReader/FilterLeafReader subclass whose doClose throws; no Lucene listener or reader does this. Summary
You wrap two DirectoryReaders in a MultiReader (the one-argument constructor closes its sub-readers on close) and the first reader has a reader-closed listener that throws an unchecked exception such as IllegalStateException. You expect MultiReader.close() to close both sub-readers and rethrow the first failure, which is what it does when the failure is an IOException and what IndexReader's own close does under unchecked exceptions. Instead doClose catches only IOException, so the loop stops after the first reader: the second reader is never closed (its refCount stays 1), and because the MultiReader already counts as closed, it can no longer be closed through the MultiReader.
