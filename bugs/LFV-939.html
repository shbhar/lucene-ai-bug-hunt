The default terms dictionary's file-format javadoc misplaces the postings header and still lists a root code

The javadoc of Lucene103BlockTreeTermsWriter, the reference for the default codec's terms files, describes a .tmd/.tim byte layout the writer does not produce: a parser that follows it reads 63 fields in a one-field index. Documentation only: Lucene's own writer and reader agree, so nothing breaks at runtime.

The finding in 30 seconds

#

A javadoc that documents the byte layout of the default codec's terms files lists one element that is never written and leaves out one that is.

Background: the block-tree terms files

#
  1. The default codec stores each field's terms in a block tree: .tim holds the term blocks, .tip a trie index into them, and .tmd small per-field metadata (term counts, statistics, where each field's trie lives).
  2. Each file starts with a header (codec magic, name, version, segment id and suffix) and ends with a checksum footer. The postings format also writes a small header of its own, the PostingsHeader, into one of these files.
  3. The Lucene103BlockTreeTermsWriter class javadoc gives each file's layout as a grammar, element by element, with VInt/VLong types. Lucene104PostingsFormat sends readers there for the details.

The finding, step by step

#
  1. You write a reader for the default codec's terms metadata file (.tmd) from the Lucene103BlockTreeTermsWriter javadoc: Header, NumFields, then per field FieldNumber, NumTerms, RootCodeLength, the root code bytes, SumTotalTermFreq, ...
  2. You index one document with one text field and expect NumFields = 1 right after the 55-byte header.
  3. You read 63. That is 0x3F, the first byte of the postings format's own header (codec magic 0x3FD76C17, name Lucene104PostingsWriterTerms, block size 256), which the writer puts here, once. The javadoc instead puts this PostingsHeader at the start of every field in .tim, where nothing writes it.
  4. Skip that header and the next stale element follows: with 3 documents ("a a a b", "b c", "c d e"), the documented RootCodeLength reads 9, which is really SumTotalTermFreq, and after 9 bytes of "root code" the documented SumTotalTermFreq reads 82, the first byte of the .tip file length. The trie terms index of 10.3.0 writes no root code.
  5. Lucene's own reader follows the writer, so indexing, merging and search are fine. Only the documentation is wrong: since 8.6.0 for the header, since 10.3.0 for the root code.

Who is affected

#

People who read or re-implement the default codec's .tim/.tmd format from this javadoc: format inspectors, ports, recovery tools. Every .tmd file the default codec writes shows it at NumFields, on 8.6.0 to 10.6.0 and main. Lucene itself, and every application using its API, is unaffected; no public report was found.

Mechanism, terms and numbers718 words

The class javadoc of Lucene103BlockTreeTermsWriter describes the default codec's terms files as typed element lists (a grammar), and Lucene104PostingsFormat sends readers there for the format details. Two parts no longer match the writer. The .tmd grammar says Header, NumFields, <FieldStats>^NumFields, ..., but the writer puts the postings writer's header (an IndexHeader plus the packed block size, 256) between the header and NumFields; the javadoc instead documents that PostingsHeader at the start of every .tim field, where nothing writes it (stale since LUCENE-9353 moved it to the new .tmd file in 8.6.0). And each FieldStats still lists RootCodeLength, Byte^RootCodeLength, which the trie terms index of 10.3.0 no longer writes: #14333 replaced the FST elements after IndexStartFP (FSTHeader, FSTMetadata) with TrieRootNodeFp, IndexEndFp and kept the root code lines. A parser that follows the text reads NumFields as 63, the first byte of the codec magic, and, with that header skipped, takes SumTotalTermFreq for RootCodeLength. Lucene's reader follows the writer, so only the documentation is wrong. Minor: the headers are documented as CodecHeaders but are IndexHeaders. Separate and much older: the .tim term-block productions are simplified, not byte-exact; this page and the suggested fix do not cover them.

The bytes (executed)

#
  • .tmd, right after its header: 3f d7 6c 17 1c 'Lucene1...', the codec magic and the 28-character name of the postings writer's header; then the block size 256 and NumFields 1.
  • FieldStats for the 3 documents "a a a b", "b c", "c d e": 00 05 09 07 03 01 61 01 65 38 00 42 | 52 00 .. = FieldNumber 0, NumTerms 5, SumTotalTermFreq 9, SumDocFreq 7, DocCount 3, MinTerm a, MaxTerm e, IndexStartFP 56, TrieRootNodeFp 0, IndexEndFp 66, then TermIndexLength 82. Read with the javadoc, 9 becomes RootCodeLength and 82 SumTotalTermFreq.
  • .tim, right after its header, continues with the first term block (0b 2c 61 62 63 64 65 ...); the codec magic occurs once in .tim, in its own header. (The block is not read as documented either: its first VInt 0b = 11 is five entries plus the last-block flag, 5 << 1 | 1 (:735-742), not an EntryCount of 11; see Suggested fix.)

Root cause

#

LUCENE-9353 (8.6.0) changed postingsWriter.init(termsOut, state) to init(metaOut, state), moving the header from .tim to the new .tmd, and left the javadoc as it was. #14333 (10.3.0) created Lucene103BlockTreeTermsWriter from Lucene90BlockTreeTermsWriter and swapped the FST elements of FieldStats (FSTHeader, FSTMetadata, after the IndexStartFP it kept) for TrieRootNodeFp, IndexEndFp, but kept RootCodeLength, Byte^RootCodeLength.

Exposure and likelihood271 words
  • Who is hit. Anyone decoding .tim/.tmd bytes from the documentation. Lucene sends them there: Lucene104PostingsFormat.java:97 ("See {@link Lucene103BlockTreeTermsWriter} for more details on the format") and :149 for .tip. The file-format overview links its "Term dictionary" item (lucene104/package-info.java:154, "Details on each of these are provided in their linked pages", :188) and the .tim and .tip rows of its extension table (:258-265) to Lucene104PostingsFormat, which sends readers on here. .tmd is not in that table at all, so this javadoc is the only place its layout is given.
  • Default vs opt-in. The default postings format: its block-tree writer calls postingsWriter.init(metaOut, state) unconditionally in its constructor (:332) and Lucene104PostingsWriter.init always writes the header (:223-227), so every .tmd file written this way has it before NumFields (read in the code; seen in all 125 .tmd files of the hunt's sweep). No setting or scale is needed. Other postings formats plugged into the block tree write their own PostingsHeader there; not run.
  • How it shows. Not subtle (63 fields, garbage statistics), but the text gives no hint where the extra bytes come from: Lucene104PostingsFormat describes the PostingsHeader under its .tim heading, so a reader looks in the wrong file.
  • What it does not do. No wrong results, no runtime path, no index change: Lucene's code never reads the javadoc grammar. Lucene's TestTrie (4 tests) and TestLucene104PostingsFormat (34 tests, 3 skipped) pass (this doc's gradle run, with the javadoc-only fix applied; the refute reviewer also ran one method of each).
  • How many. A small audience; the searches found no public report since 8.6.0 (2020).

Why it looks unintended

#
  • The .tmd grammar is a short, typed element list, and it lists an element no version writes: Lucene103 has one format version, without a root code.
  • Its own note calls the PostingsHeader "arbitrary per-file data": one per file, as written in .tmd, not one per .tim field.
  • Committers fixed this grammar before: #90 (2021) rewrote it after .tmd was introduced.
The full argument182 words
  • Contract text. Every .tmd element has a primitive type linked to a DataOutput method (Lucene103BlockTreeTermsWriter.java:157-161). "This document defines the index file formats used in this version of Lucene" (lucene104/package-info.java:50); "Details on each of these are provided in their linked pages" (:188).
  • Self-contradiction. "PostingsHeader and TermMetadata are plugged into by the specific postings implementation: these contain arbitrary per-file data (such as parameters or versioning information) and per-term data" (:136-138).
  • No version writes a root code. VERSION_START = VERSION_CURRENT = 0 (Lucene103BlockTreeTermsReader.java:73-76); the FieldStats line lists the FST-era RootCode next to its trie replacement TrieRootNodeFp.
  • Precedent. #90 ("LUCENE-9353: revise format documentation of Lucene90BlockTreeTermsWriter", 2021) rewrote this grammar after LUCENE-9353; its review discussed which FieldStats element is the optional one, and it was approved as a fix ("Thank you @mocobeta for fixing this!"). #823 (2022) restructured the .tim line. #15619 / #15625 (2026-01) fixed a stale block-size sentence in Lucene104PostingsFormat.
  • Nothing in the materials reviewed (the related PRs, JIRA issues and review threads, and CHANGES) says the grammar is meant to be approximate.
The devil's-advocate check291 words

Strongest case for "intended" (the refute reviewer, the GPT intended lens and this doc's cross-model fact check: moderate, not decisive; the intended-behaviour verifier: weak): the codec classes are @lucene.experimental (Lucene103BlockTreeTermsWriter.java:209); the overview "attempts to provide a high-level definition" (package-info.java:54), the policy of LUCENE-2946 (#4020, 2012, "change file format documentation from bit-for-bit to highlevel"); PostingsHeader/TermMetadata are italic plug-in placeholders, so their position could be schematic; and the page is not bit-exact elsewhere either: the .tim term-block productions leave out flag bits, a suffix-lengths section and the compression and run-length coding the writer uses (see Suggested fix; pointed out by the cross-model fact check of this doc).

Why it fails: "high-level" allows leaving detail out or simplifying an encoding (the .tip trie is deliberately {trie<byte[]>} with a TODO; the .tim blocks are simplified); it does not cover listing elements that no writer of this format writes, or leaving out a header that every .tmd file of the default codec carries. The LUCENE-2946 thread does not settle it: rmuir found exact docs fine "for the simple metadata files" and wanted a high-level explanation for the terms dictionary; that .tmd, added in 2020, is a small metadata file of the first kind is this page's reading. The placeholder reading does not explain the .tim position either: the current block-tree writer always passes the .tmd output to postingsWriter.init (:332), so a header written there lands once in .tmd, never in a per-field slot of .tim (the base class still names that argument termsOut and says implementations "typically" write a header, PostingsWriterBase.java:45-49). @lucene.experimental warns that the format may change between releases, not that the current page may be wrong. Every verifier and the adjudication rejected the "intended" reading.

Trade-offs

  • Keeps the class's typed style and fixes the two .tmd items, the misplaced .tim PostingsHeader and the header wording. The existing note (:136-138, "arbitrary per-file data") already explains the PostingsHeader and now matches where it sits; it stays in the .tim notes (moving that half to the .tmd notes is optional, not run).
  • PostingsHeader stays an italic placeholder, because the block tree is postings-format agnostic; for the default codec it is "Header, PackedBlockSize" (Lucene104PostingsFormat.java:103), so the corrected .tmd line is exact for the default postings writer; other postings formats define their own. IndexHeader is spelled as Lucene104PostingsFormat already spells it (:106).
  • Left as is, and older than this defect: the .tim term-block productions (:113-124) are simplified, not byte-exact. EntryCount is written as numEntries << 1 | isLastInFloor (:735-742), so the block 0b 2c 61 62 63 64 65 ... holds 5 entries, not 11; SuffixLength is a VLong token with the total suffix bytes, a leaf bit and a compression code (:920-925); the suffix bytes may be compressed (:883-930); the per-term suffix lengths are a section of their own (:934-946); singleton stats are run-length coded (:520-538). The flag bits were packed this way already in 4.10.4, the rest came with LUCENE-4702 (8.5.0). Describing that encoding exactly is a separate, larger javadoc change (not drafted, not run); fix A covers only the .tmd items, the misplaced header and the header wording.
  • Left out, could be added separately: that TrieRootNodeFp is relative to IndexStartFP (FieldReader.java:80-87), and the missing comma in TrieIndex^NumFields Footer (:186).

Downstream note

#

Downstream relevance is limited to tools that decode .tim/.tmd bytes by hand from this javadoc (inspectors, ports, recovery tools); Lucene's own reader and every application using its API are unaffected.

How it was found

#

Semi-formal: a differential grammar check. Each default-codec file's grammar was transcribed from its javadoc and, separately, from its writer; one interpreter parsed the real bytes of 64 generated indexes under both and compared every value with Lucene's own reader. Under the javadoc grammar, all 125 .tim and 125 .tmd files diverged.

The method in full135 words
  • The check made 1,114 file checks (all file types) per run over 64 indexes (4 fixed and 60 seeded random feature configurations), run once with assertions on and once off.
  • Positive control: the writer's layout grammar parses every .tmd file exactly to its footer and, for every .tim, finds the postings header in .tmd rather than after the .tim header (0 failures; it does not parse the .tim term blocks). Vacuity check: 14 of 14 layout mutants with one element dropped are caught.
  • A JUnit test written from the result, then independent tests by verifiers, a reviewer from another model family (OpenAI GPT-5.6) and an adjudication reproduced it; 37 version-portable probe runs from 4.10.4 to main dated each element.
  • This is a differential check of documentation against bytes, not model checking or a proof.

LFV-939, snapshot of 2026-11-04

Registry title
The file-format javadoc of the default terms dictionary (Lucene103BlockTreeTermsWriter) gives a wrong .tim/.tmd grammar: each .tmd FieldStats still lists RootCodeLength and root-code bytes, which the trie-based terms index no longer writes, and the PostingsHeader is documented at the start of every .tim field although it is written once in .tmd, before NumFields (documentation defect; the writer and reader agree)
Area
codecs / terms dictionary (Lucene103BlockTreeTermsWriter .tim/.tmd file-format javadoc vs its writer and reader)
Priority
Low, rank 1170: The default terms dictionary .tim/.tmd grammar has two stale elements going back to 8.6 and covers a central per-field file.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so indexing, merging, CheckIndex and search are unaffected in every configuration; the people misled are those who read, inspect or re-implement the default terms dictionary format from this class javadoc (Lucene104PostingsFormat sends readers there for the format details), and a parser that follows the text misreads NumFields in every .tmd file the default codec writes and finds no PostingsHeader in .tim (executed); the PostingsHeader placement has been wrong since 8.6.0 (2020) and the root-code leftover since 10.3.0 (2025); no scale or special setting is needed.
Summary
You decode the terms metadata (.tmd) and terms dictionary (.tim) files of the default codec by following the Lucene103BlockTreeTermsWriter javadoc, which says .tmd is Header, NumFields, FieldStats... with a RootCodeLength and root-code bytes in each FieldStats, and that every .tim field starts with a PostingsHeader. The writer instead puts the postings writer's header (an IndexHeader plus the block size) once into .tmd, right after its own header and before NumFields, writes no PostingsHeader into .tim and, since the trie terms index of 10.3.0, writes no root code; a parser built from the text reads NumFields as 63 (the first byte of the codec magic) and, even with that header skipped, takes SumTotalTermFreq for RootCodeLength. Lucene's own reader matches the writer, so nothing breaks at runtime; only the documentation is wrong.
