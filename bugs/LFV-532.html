NGramTokenFilter and EdgeNGramTokenFilter end() throw away the input's final position increment, so a trailing stop-word hole is lost

NGramTokenFilter and EdgeNGramTokenFilter lose the hole StopFilter leaves for a removed last word: abc the ends with a final position increment of 0, not 1. The next value of a multi-valued field then starts one position early, so the phrase abc def matches across the values abc the and def.

The bug in 30 seconds

#

A token stream reports positions skipped after its last token in end(), as the final position increment; IndexWriter adds it before the next value of the field. The two n-gram filters replace their input's value instead of adding to it.

  1. You index a text field through a whitespace tokenizer, StopFilter("the") and EdgeNGramTokenFilter(1, 3) or NGramTokenFilter(3, 3), a common autocomplete chain, and analyze abc the.
  2. StopFilter removes the and reports the skipped position at the end of the stream: a final position increment of 1. The n-gram filter drops nothing here, so you expect it to report 1 too.
  3. You get 0. The filter's end() first fetches the input's 1, then overwrites it with the positions of the tokens it dropped itself, 0. For abc x the, where it also drops the short x, you get 1 instead of 2.
  4. IndexWriter adds that number to the field position before the next value. With the values abc the and def and the default gap 0, def lands at position 1, not 2: the phrase abc def finds the document (1 hit; 0 without the n-gram filter), and the phrase that keeps the hole (abc at 0, def at 2) misses.

Who is affected

#

Users who put StopFilter (or any filter that can drop the last tokens of a value) before NGramTokenFilter or EdgeNGramTokenFilter on a multi-valued field with positions. Phrase, span and interval queries across a value boundary then match or miss wrongly with a small gap (Lucene's default is 0). Terms, scores and single-valued fields are unaffected.

Mechanism, terms and numbers653 words

TokenStream#end is where a token stream reports the positions it skipped after its last token. StopFilter reports the removed last word of abc the as a final position increment of 1, and IndexWriter adds that number to the field position before the next value of a multi-valued field. NGramTokenFilter and EdgeNGramTokenFilter call super.end(), which leaves the input's value in the attribute, and then replace it with the increments of only the tokens they dropped themselves (shorter than minGram). So behind either filter abc the ends with 0 instead of 1, and abc x the with 1 instead of 2. With Lucene's default position increment gap of 0, the second value def of ["abc the", "def"] is indexed at position 1 instead of 2: the phrase abc def matches (1 hit, against 0 for the same chain without the n-gram filter) and the phrase that keeps the hole misses. Terms, scores, single-valued fields and the first value of the field are unchanged; a gap of 100 hides it from ordinary exact phrases. It came with LUCENE-8360 in 7.4.0, which fixed the opposite case; adding instead of replacing, as FilteringTokenFilter.end() and FixedShingleFilter.end() do, fixes it.

Terms

#
  • Position increment: how many positions a token moves on from the previous one. A removed word leaves a hole: StopFilter gives the next token an increment of 2 instead of 1.
  • Final position increment: holes after the last token have no next token to carry them, so the stream reports them in end() ("any skipped positions (such as those removed by a stopfilter) can be applied to the position increment", TokenStream.java:152-154). StopFilter reports the removed last word of abc the as 1.
  • Multi-valued field: several values of one field in one document. IndexWriter adds each value's final increment, then the analyzer's position increment gap (0 by default), before the next value (IndexingChain.java:2105-2109, :2121-2122; Analyzer.java:300-311).

The bug

#
  1. Both filters count, in curPosIncr, the increments of input tokens they drop themselves (shorter than minGram, without preserveOriginal), hand the sum to the next emitted token (a gram, or the preserved original) and reset it (NGramTokenFilter.java:108, :113-114, :132-133; EdgeNGramTokenFilter.java:100, :104-105, :117-118).
  2. end() calls super.end(), which runs the input's end() and leaves the input's final increment in the attribute, and then posIncrAtt.setPositionIncrement(curPosIncr) (NGramTokenFilter.java:157-161, EdgeNGramTokenFilter.java:146-150). That replaces the input's hole with the filter's own drops.
  3. The two counts are disjoint (curPosIncr only sees tokens the filter received), so the right value is their sum, as in FilteringTokenFilter.end() (FilteringTokenFilter.java:72-75).
  4. Only end() is wrong: grams, their order, offsets, per-token increments, position lengths, types and keyword flags match a reference on all 24,106,264 generated inputs of the hunt's exhaustive harness, and a hole in the middle of the stream (abc the def) is kept.

Other readers of the final increment, by code reading only: TokenStreamToAutomaton turns it into trailing-hole states (TokenStreamToAutomaton.java:212-239), as used by ConcatenateGraphFilter for completion fields (with its default preservePositionIncrements=true); AnalyzingSuggester sets setFinalOffsetGapAsHole(true) (AnalyzingSuggester.java:320), which restores one lost trailing hole from the offset gap. Exposure and likelihood344 words
  • Who is exposed. Chains with a filter that can remove the last tokens of a value (StopFilter, or another FilteringTokenFilter such as LengthFilter, CodepointCountFilter, TypeTokenFilter or KeepWordFilter) before NGramTokenFilter or EdgeNGramTokenFilter, built with the constructors, the nGram / edgeNGram factories or CustomAnalyzer, on a multi-valued field that indexes positions.
  • What changes. Each later value of the field in the same document starts early by the trailing holes lost in the earlier values: normally one position per removed trailing word (precisely, the summed increments of the removed tokens, FilteringTokenFilter.java:58), and the shift adds up over successive values. Phrase, span and interval queries across that boundary match or miss differently from the same chain without the n-gram filter, in both directions (executed for phrases). At gap 0, phrases across a value boundary match by design (Analyzer.java:300-303), so the change is which cross-value phrases match, not whether any do.
  • What does not change (executed on 300 random multi-valued documents, both filters, gaps 0 and 100): terms, frequencies, norms and BM25 term-query scores; single-valued fields and the first value of a multi-valued field (only later values move; a hole lost at the end of the last value has no effect); CheckIndex is clean.
  • The gap. Lucene's Analyzer default is 0. The factories' own javadoc example and common search servers use 100 for text fields, which hides it from ordinary exact phrases (executed at gap 100 for the adjacent and the one-hole phrase). def is still at 101 instead of 102, so a phrase with explicit positions across the gap, or a sloppy, span or interval query that reaches that far, could still differ (not executed).
  • Default vs opt-in. The n-gram filters are optional analysis-common components; once configured, ordinary text that ends in a stop word triggers it.
  • Scale and versions. Deterministic, any index size, no error. Every release from 7.4.0 to 10.5.2 and main.
  • How likely. Rare in visible results: n-gram fields are usually term-matched for autocomplete, and no report since 2018 was found in the recorded searches.

Why it is a bug, not intended

#
  • The analysis package docs say every component "must" put accurate values into the attributes at the end of the field, and TokenStream#end names stop-filter holes as what goes there.
  • Sibling filters such as FilteringTokenFilter and FixedShingleFilter add to the input's value in end() instead of replacing it.
  • No test pins the overwrite: with the fix all module tests pass.
The full argument247 words
  • The docs. "End of Input Cleanup": the components "must put accurate values into the token attributes to reflect the situation at the end of the field" (package-info.java:274-284). TokenStream#end: "any skipped positions (such as those removed by a stopfilter) can be applied to the position increment" (TokenStream.java:152-154). LUCENE-3849 added end() increments for exactly this: "TokenStreams now set the position increment in end(), so we can handle trailing holes" (CHANGES.txt:13337-13340).
  • The class javadoc. NGramTokenFilter "emits all n-grams for the same token at the same position" (NGramTokenFilter.java:30). With 3-character tokens and grams of 3 it emits exactly its input, yet it changes indexed positions.
  • Sibling filters add. FilteringTokenFilter.end() (:74) and FixedShingleFilter.end() (FixedShingleFilter.java:176-179, fixed this way by #16577, merged 2026-08) add to the input's value; per a verifier's grep, every other end() override in core and analysis-common that calls setPositionIncrement keeps or adds to it.
  • The same filters keep mid-stream holes: abc the def keeps def two positions after abc. Only the trailing hole is lost.
  • History and tests. LUCENE-8360 ("did not correctly set position increments in end()", CHANGES.txt:7498-7499) wrote the assignment to fix the opposite case, the filter's own dropped trailing tokens. Its tests (TestNGramTokenFilter.java:214-222, TestEdgeNGramTokenFilter.java:281-289) feed a whitespace tokenizer whose final increment is 0, so they cannot tell "set" from "add"; the issue's comments never mention the input's increment. With the fix all module tests pass (1,912, 18 skipped).
The devil's-advocate check197 words

The checkers built the strongest case for "intended": (a) TokenStream#end only says skipped positions "can be" applied, which is permissive, and no javadoc states that the sum of increments must be preserved; (b) LUCENE-8360 wrote the assignment on purpose and its CHANGES entry calls the result correct; (c) in its motivating caller, ConditionalTokenFilter, the n-gram filter's input is a wrapper whose end() calls endAttributes(), so the input's increment there is always 0 and overwrite equals add; (d) n-gram fields are mostly single-valued and term-matched.

Why it fails: (a) the package docs say "must", and LUCENE-3849 exists to carry trailing holes; (b) the 8360 tests cannot distinguish the two behaviours and nothing in that issue discusses discarding the input's value; (c) explains why the change looked right there, not why a stop-word hole from a plain chain should vanish; the fix behaves identically in that caller; (d) is about severity, not intent. The open LUCENE-8361 position-preservation check never names the n-gram filters: its saved patch checks every chain, and only its discussion raises exceptions, for filters that summarise the whole stream and for truncating filters. Every checker rejected the case; the cross-model reviews rated it weak.

Suggested fix

#

Recommended A. Add the filter's own drops to the input's final increment (NGramTokenFilter and EdgeNGramTokenFilter)

Add instead of replace: in both end() methods, posIncrAtt.setPositionIncrement(posIncrAtt.getPositionIncrement() + curPosIncr), the same shape as FilteringTokenFilter.end() and FixedShingleFilter.end(). It cannot double count, and an input whose final increment is 0 gives today's result. Validated: the new tests pass, as do all module tests and check.

   @Override
   public void end() throws IOException {
     super.end();
-    posIncrAtt.setPositionIncrement(curPosIncr);
+    // keep the input's final increment (e.g. a trailing stop-word hole) and add the positions of
+    // the tokens this filter dropped after the last emitted token
+    posIncrAtt.setPositionIncrement(posIncrAtt.getPositionIncrement() + curPosIncr);
   }
All options and trade-offs3 options · 503 words

Option A was applied in a scratch worktree of main a9779ef3c193 and run through gradle with assertions on and off; option B is complementary and was not run.

A. Add the filter's own drops to the input's final increment (NGramTokenFilter and EdgeNGramTokenFilter) (validated by the checks) (recommended)

#

In NGramTokenFilter.end() (NGramTokenFilter.java:160) and EdgeNGramTokenFilter.end() (EdgeNGramTokenFilter.java:149), replace setPositionIncrement(curPosIncr) by adding curPosIncr to the value super.end() left in the attribute.

Why it cannot double count. curPosIncr only accumulates increments of tokens that input.incrementToken() returned; the input's final increment exists only after input.end(), inside super.end().

What it changes. Only the final increment, and only when the input reports one. With an input whose final increment is 0 (a plain tokenizer, or ConditionalTokenFilter's wrapper) the result is the same as today; the LUCENE-8360 case (seventeen one two three four, grams 8..8) still gives 4.

   @Override
   public void end() throws IOException {
     super.end();
-    posIncrAtt.setPositionIncrement(curPosIncr);
+    // keep the input's final increment (e.g. a trailing stop-word hole) and add the positions of
+    // the tokens this filter dropped after the last emitted token
+    posIncrAtt.setPositionIncrement(posIncrAtt.getPositionIncrement() + curPosIncr);
   }

Trade-offs

  • Indexes built before the fix keep the old positions for later values until reindexed, so phrase results across value boundaries change after an upgrade and reindex; that is the fix.
  • No API change; negligible cost: one attribute read and one addition per end() call.

B. Also check end increments generically in the test framework (complementary, not run)

#

LUCENE-8361 (#9408, open since 2018) proposes that TestRandomChains check that the sum of position increments, the final one included, is preserved through a chain. Its saved patch checks every chain, with no exemption list; its discussion raises exceptions for filters that summarise the whole stream and for truncating filters. By reading its patch, it would probably flag this bug; whether it also flags the sibling bugs in ConditionalTokenFilter, ConcatenatingTokenStream and WordDelimiterGraphFilter was not checked.

Trade-offs

Larger scope: any exemptions must be agreed, and it finds bugs rather than fixing them; not a substitute for option A.

C. Document the overwrite as intended (not recommended)

#

Say in the class javadocs that the filters reset the final increment to their own drops.

Trade-offs

Contradicts the package docs' "must", TokenStream#end and the sibling filters that add, and keeps the wrong positions in multi-valued fields.

Downstream note

#

Search servers that expose these filters inherit the shifted positions; their usual gap of 100 for text fields hides it from ordinary exact phrase queries.

How it was found

#

A bounded-exhaustive check of the real filters against references written from their javadocs and the TokenStream#end contract, on 24,106,264 generated inputs. The only mismatch was the final position increment, in exactly the inputs whose source reported a trailing hole; reading end() then gave the cause.

The method in full212 words
  • Method (semi-formal): bounded-exhaustive translation validation of the stock main jar, in the hunt's unit on analysis filters against their javadoc. References written from the class javadocs and the TokenStream#end contract were compared token by token, and on the end-of-stream state, with the real NGramTokenFilter and EdgeNGramTokenFilter.
  • Inputs. 12,053,132 generated inputs per filter: every term of up to 4 code points over 5 code points (including a supplementary character and a combining mark), and every sequence of up to 3 tokens over 7 terms with position increments 0/1/2, position lengths 1/2, the keyword flag, a source final increment of 0 or 1 and several gram parameter sets. These are synthetic streams; some, such as an empty term or a first token with increment 0, no real chain produces.
  • Signal. 6,026,566 mismatches per filter, all in the final increment and exactly the inputs whose source reported 1; grams, order, offsets, increments, position lengths, types and keyword flags all matched. The harness killed three planted n-gram mutants: two that change the generated grams (by its exhaustive suite) and one that skips the curPosIncr reset (by its separate reuse check).
  • Root cause by reading the two end() overrides; the finder then wrote the public-API JUnit and the fix, and independent checkers followed (see "Independent checks").

History

#

Introduced by LUCENE-8360 (d1dc874d90bc, 2018-06-17), first released in 7.4.0; 7.3.1 keeps the hole. Fails on every executed release from 7.4.0 to 10.5.2 and on main. Not fixed upstream.

Versions tested6 rows

Introduced by LUCENE-8360 (now #9407, "NGramTokenFilter doesn't set posIncAttribute correctly in end()"; commit subject "NGram filters should set posIncAtt in end()"), by @romseygeek with a +1 from @jpountz: master d1dc874d90bc (2018-06-17), branch_7_4 b03b527a312 (what 7.4.0 ships) and branch_7x a045344b254, committed from a JIRA patch (no PR). Precondition. So for NGramTokenFilter 7.4.0 is a plain regression; for EdgeNGramTokenFilter it traded one end() defect for another.

Not fixed upstream. Upstream main ffa9d816eeb4 (2026-10-26) and c5ab3e57b9ba (2026-10-28) still have the overwrite at NGramTokenFilter.java:160; later commits on the files only reformat, fix javadoc or remove final modifiers. LFV-532, snapshot of 2026-10-28

Registry title
NGramTokenFilter and EdgeNGramTokenFilter end() overwrite the input's final position increment instead of adding to it, so a trailing hole (such as a removed trailing stop word) is lost and the next value of a multi-valued field starts too early (released since 7.4.0)
Area
analysis / common n-gram token filters (NGramTokenFilter, EdgeNGramTokenFilter: final position increment in end())
Priority
Low, rank 402: NGram and EdgeNGram filters lose a trailing position hole, the same cross-value-boundary class as LFV-354 that rarely changes results but in widely used filters.
Impact class
silent wrong results
Impact note
Applications that index a multi-valued text field through StopFilter (or another filter that removes the last tokens of a value, such as LengthFilter or KeepWordFilter) followed by NGramTokenFilter or EdgeNGramTokenFilter, a common autocomplete chain, with a small position increment gap (Lucene's Analyzer default is 0): every value that ends in removed tokens makes the next value start one position early per removed trailing token, so phrase, span and interval queries across the value boundary match or miss differently from the same chain without the n-gram filter (executed: a phrase false positive and, for the phrase that keeps the stop-word hole, a false negative at gap 0); term queries, scores, single-valued fields and the last value are unchanged (executed); consumers of the trailing hole such as TokenStreamToAutomaton (suggesters) see 0 (code reading); deterministic, ordinary scale, every release from 7.4.0 to 10.5.2 and main; with the gap of 100 that common search servers use for text fields, exact phrases are unaffected (executed).
Summary
You analyse 'abc the' with a whitespace tokenizer, StopFilter and then NGramTokenFilter(3,3) or EdgeNGramTokenFilter(1,3); StopFilter reports the removed trailing 'the' as a final position increment of 1 in end(), and because the n-gram filter drops nothing here you expect end() to still report 1. Instead both filters call super.end() and then replace that value with only the increments of tokens they dropped themselves, so end() reports 0 ('abc x the' gives 1 instead of 2) and the trailing hole is lost. In a multi-valued field with Lucene's default gap 0, the second value 'def' of ['abc the', 'def'] is then indexed at position 1 instead of 2, and PhraseQuery('abc','def') matches the document (1 hit) where the same chain without the n-gram filter gives 0 hits (executed).
