One binary doc-values update that matches many documents overflows an int-sized buffer at commit, and IndexWriter closes itself

One updateBinaryDocValue whose term matches many documents copies its value once per document into one int-sized buffer when it is applied: at 2 GiB (for example 2,100 documents x 1 MiB) commit() throws and IndexWriter closes itself, losing the update and all uncommitted documents. Affected: 4.8.0 to 10.5.2 and main.

The bug in 30 seconds

#

IndexWriter buffers a doc-values update as one term and one value. When it applies the update, it writes the value into a per-segment buffer once for every document the term matches. For binary values that buffer is a single Java byte[], whose length is an int and cannot reach 2^31 bytes.

  1. Commit 2,100 documents that share the term group:g (one segment), add one more document, late, and call updateBinaryDocValue(new Term("group", "g"), "payload", value) once with a 1 MiB value. IndexWriter buffers only the term and that value, with no per-document copies.
  2. You expect commit() to give all 2,100 documents the new value and keep late: about 2.2 GB of binary doc values, which a fixed build commits fine.
  3. Instead, applying the update appends a full 1 MiB copy per matched document to one byte[]. Copy 2,048 would end at byte 2^31, the int length wraps to -2,147,483,648, and commit() throws ArrayIndexOutOfBoundsException (with -ea, an AssertionError: "likely integer overflow?").
  4. The apply runs where every exception is tragic: IndexWriter closes itself, and the update and late are lost. The last commit stays readable and a new writer opens on it.
  5. Since 7.7.0 a lone update is applied twice (a separate bug), so 1,100 documents x 1 MiB already fail. Ordinary sizes fail too: 530,000 documents x 4 KiB.

Who is affected

#

Applications that update a binary doc-values field by a term many documents share, such as a per-tenant or per-category blob, on the default configuration. It takes gigabytes of copies in one segment: 2,100 or 1,100 documents x 1 MiB, or 530,000 x 4 KiB. No RAM or heap setting prevents it, and uncommitted documents are lost.

Mechanism, terms and numbers654 words

IndexWriter.updateBinaryDocValue(term, field, value) buffers one term and one value (stored twice when it is the field's first update in the packet, on 7.7.0 and later). When the update is applied (at commit(), and by code reading also at a flush or NRT reopen that applies the packet), Lucene calls BinaryDocValuesFieldUpdates.add(doc, value) once for every document the term matches in a segment, and each call appends a full copy of the value to one int-sized byte[]. At 2^31 bytes the length wraps: ArrayIndexOutOfBoundsException (an AssertionError "likely integer overflow?" with assertions on). The apply runs inside an event that treats any Throwable as tragic, so IndexWriter closes itself and the update and every uncommitted document are lost; the last commit stays readable. 2,100 documents x 1 MiB fail, and so do 530,000 x 4 KiB; since 7.7.0 a lone update is applied twice (LFV-837), so 1,100 x 1 MiB fails too. With a one-method fix the same commit succeeds. Every tested release from 4.8.0 to 10.5.2 is affected, and main (13 versions executed; the releases in between keep the same per-document append).

Terms

#
  • Doc-values update: updateBinaryDocValue(term, field, value) (also updateDocValues(term, BinaryDocValuesField)) changes a binary doc-values field in place on every document that contains term. IndexWriter buffers the request and applies it later, at a commit, flush or NRT reopen, by looking up the term in each segment.
  • Packet: the buffered updates that are applied together. Applying a packet builds one BinaryDocValuesFieldUpdates per field and segment, which records (doc, value) for every matched document before it is written out.
  • Tragic event: an error after which IndexWriter closes itself and discards everything not committed, because its internal state may be inconsistent.

The bug

#
  1. FrozenBufferedUpdates.applyDocValuesUpdates creates one BinaryDocValuesFieldUpdates per field and segment (FrozenBufferedUpdates.java:307-308) and, for each document the update's term matches, calls update.add(doc, binaryValue) with the same BytesRef (:319, loop :336-345). The numeric path keeps one value for all documents in this case (SingleValueNumericDocValuesFieldUpdates, :288-295); the binary path does not.
  2. BinaryDocValuesFieldUpdates.add appends a full copy every time: offsets.set(index, values.length()); lengths.set(index, value.length); values.append(value); (BinaryDocValuesFieldUpdates.java:94-99), into values = new BytesRefBuilder() (:80), one byte[].
  3. BytesRefBuilder.append computes the new length as ref.length + len, an int (BytesRefBuilder.java:77-80). With 2,047 copies of 1 MiB stored (2,146,435,072 bytes), copy 2,048 needs 2^31 bytes and the sum wraps to -2,147,483,648. ArrayUtil.grow asserts minSize >= 0 ("likely integer overflow?", ArrayUtil.java:446); without assertions it returns the array unchanged and System.arraycopy throws (BytesRefBuilder.java:79). (1 MiB and 4 KiB divide 2^31; for lengths where a multiple lands between ArrayUtil.MAX_ARRAY_LENGTH and Integer.MAX_VALUE, such as any length up to 16 bytes, ArrayUtil.oversize throws IllegalArgumentException instead, ArrayUtil.java:145-152, by code reading; the writer closes the same way.)
  4. The apply runs as an event that catches any Throwable and calls onTragicEvent(t, "applyUpdatesPacket") (IndexWriter.java:2935-2943). commit() first flushes the buffered documents to a new segment (:3809, :3819; here doc late becomes segment _1, written but in no commit) and then applies the packet in processEvents(false) (:3821), as an executed infoStream probe shows. prepareCommitInternal then closes the writer through maybeCloseOnTragicEvent() -> rollbackInternal() (its finally at :3883 with assertions off; its catch (Error) at :3879-3881 with assertions on; :6098-6105), which drops segment _1 too.
  5. Nothing bounds the expansion: the per-segment updates are built privately during the apply and enter IndexWriter's RAM accounting only when published (ReadersAndUpdates.java:153-161), and only the entry count has an explicit guard (DocValuesFieldUpdates.java:375-379).

By code reading the count that matters is the sum, over all binary updates of one field in one packet, of the documents each matches in one segment times its value length; only the one-update case was executed. Since 7.7.0 the first update of a field in a packet is applied twice (LFV-837), so a lone update fails at 2^30 bytes.

Exposure and likelihood329 words
  • Who is hit. Callers of updateBinaryDocValue, updateDocValues(term, BinaryDocValuesField) or softUpdateDocument(s) with a binary doc-values field (the last two by code reading), when the term matches many documents of one segment.
  • Default vs opt-in. Default IndexWriterConfig and codec (executed). The tests use ByteBuffersDirectory; an FSDirectory variant fails the same way (executed), since the overflow happens in a heap buffer, before the update is written. Binary doc-values updates are an optional but mainstream public API; no RAM-buffer or heap setting bounds the expansion.
  • Scale. 2,100 x 1 MiB; 1,100 x 1 MiB when the update is its field's first in the packet (any lone update, 7.7.0 and later); 530,000 x 4 KiB. Controls with 100 or 1,000 x 1 MiB and 200,000 x 4 KiB succeed. The failing apply needs about 4 GB of heap; with a 3 GB heap it ends in OutOfMemoryError instead, with the same close. The 530,000-document test forces one segment with forceMerge(1); in practice the trigger needs large segments and a term that many of their documents share.
  • Effect. Loud: commit() throws and the writer is closed. The update and every acknowledged uncommitted document are lost; the last commit stays readable and a new writer opens on it (executed). Before 7.0.0 the writer stays open but stuck: a second commit() and close() throw the same exception and late is missing after reopening (executed on 4.8.0, 4.10.4, 5.5.5, 6.6.6); by code reading every later commit fails too and close() rolls back.
  • No way to apply it. A bigger heap does not help, since the limit is the int length; only keeping documents matched per segment times value length, summed over the field's binary updates in one packet, under 2^31 bytes avoids it: fewer matched documents, a smaller value or fewer updates per packet (by code reading).
  • Likelihood. Rare: binary updates by a widely shared term are uncommon (most in-place updates are numeric or by primary key), and nobody has reported it since 4.8.0 (2014).

Why it is a bug, not intended

#
  • The javadoc sets no size limit and "replaces the existing value of all affected documents"; a fixed build commits the 2.2 GB update.
  • Lucene's own check calls it a "likely integer overflow?"; the entry count has a guard, the byte length none.
  • A numeric value shared by a packet's updates is stored once (LUCENE-8593); binary values never are.
The full argument236 words
  • Contract. updateBinaryDocValue (IndexWriter.java:1981-1995): "NOTE: this method currently replaces the existing value of all affected documents with the new value", with @param term the term to identify the document(s) to be updated; no size limit. updateDocValues (:2059-2063): "Each field update is applied to the set of documents that are associated with the Term to the same value."
  • A legal result. The indexing-time BinaryDocValuesWriter stores values in PagedBytes and allows each value up to ArrayUtil.MAX_ARRAY_LENGTH (BinaryDocValuesWriter.java:40-45, 61, 81-83); with the fix the same 2.2 GB update commits in one segment and all values read back (executed).
  • Lucene's own check flags it. ArrayUtil.grow: "size must be positive (got -2147483648): likely integer overflow?" (ArrayUtil.java:446). The entry count has an explicit guard, "cannot support more than Integer.MAX_VALUE doc/value entries" (DocValuesFieldUpdates.java:375-379); the byte length has none.
  • History. The per-document append came with the feature (LUCENE-5513, #6576, 2014); in that issue @shaie, who implemented it, notes that the update "makes all affected documents identical", and no comment discusses the size of the in-heap buffer the apply builds. LUCENE-8593 (b4e1fe4393b, 2018) gave the numeric path a single-value specialisation; the binary path never got one.
  • Tests and precedent. No test, javadoc, CHANGES or MIGRATE entry accepts the failure. #8589 (LUCENE-7538), an 800 MB stored field whose int overflow closed the writer, was fixed by rejecting the input with a clear error.
The devil's-advocate check246 words

The strongest intended-behaviour case, built by a dedicated checker: "the limits on IndexWriter are 2GB" (a maintainer on #15330), and IndexWriterConfig documents another sub-2 GB limit, the per-thread RAM hard limit (IndexWriterConfig.java:373-385); BinaryDocValuesField says values "are stored directly with no sharing" (BinaryDocValuesField.java:26-28); the class is @lucene.experimental; the writer closing after a failed apply is an intended fail-safe since LUCENE-7868; and the IndexWriter class NOTE ("if you hit an Error ... IndexWriter will close itself", IndexWriter.java:162-165) covers the AssertionError of an -ea run and the OutOfMemoryError of a small heap.

Why it fails: the #15330 remark is about an indexing buffer that the RAM settings bound, and the per-thread limit is a setting checked with a clear error, while here one 1 MiB value is buffered and the 2 GiB appear at apply time with no check; "no sharing" is storage advice, and only NUMERIC, SORTED_NUMERIC and BINARY fields can be updated (IndexWriter.java:2106-2124), so BINARY is the only updatable byte type; the experimental tag is on the internal class, not on updateBinaryDocValue; the close is intended, which is why the overflow, not the close, is the defect; the class NOTE explains the close for Errors but sets no limit on the update, and with assertions off (the production default) and an 8 GB heap the failure is an ArrayIndexOutOfBoundsException, which no document covers. Verdict: not intended. File it citing the updateBinaryDocValue javadoc, not the class NOTE.

Suggested fix

#

Recommended Keep one copy of a repeated value (validated)

In BinaryDocValuesFieldUpdates.add, append the value only when it differs from the last appended one and point the document at the stored copy (+20/-2 lines). Validated with gradle: the repros pass with and without assertions, and 221 tests in 16 classes pass. For many distinct values, the int-addressed buffer of the buffered updates is the earlier limit (code reading).

All options and trade-offs3 options · 836 words

One fix was built and validated in a clean scratch worktree at a9779ef3c193 (removed afterwards); it is the finder's sketch with java.util.Arrays imported. Fixing the separate bug LFV-837 alone only restores the 2 GiB threshold. Workaround today (by code reading, not executed): keep each packet under the limit, for example by splitting the term into parts and committing after each part, or keep the shared value in a separate document. Both have limits: splitting needs an indexed term the application can partition, and a separate document changes the application's data model.

Keep one copy of a repeated value (validated) (validated by the checks) (recommended)

#

In BinaryDocValuesFieldUpdates.add (:94-99), remember the offset and length of the last appended value; when the new value has the same bytes, point the document's offset at that copy instead of appending again. One update's documents arrive consecutively with the same value (FrozenBufferedUpdates.java:336-345), including the duplicate pass of LFV-837, so each update is stored once.

  // plus: import java.util.Arrays;
  private int lastOffset = -1;
  private int lastLength = -1;

  @Override
  public synchronized void add(int doc, BytesRef value) {
    int index = add(doc);
    if (value.length != lastLength
        || Arrays.equals(values.bytes(), lastOffset, lastOffset + lastLength,
                value.bytes, value.offset, value.offset + value.length) == false) {
      lastOffset = values.length();
      lastLength = value.length;
      values.append(value);
    }
    offsets.set(index, lastOffset);
    lengths.set(index, value.length);
  }

Trade-offs

  • Also removes the heap blow-up: one 1 MiB copy instead of 2.2 GB while applying, and the published update's ramBytesUsed() (:135-143) no longer counts N copies.
  • Compares with the stored copy, not the caller's BytesRef, so a reused or re-filled BytesRef is safe; swap() moves offsets and lengths together (:101-112), so shared offsets survive the sort in finish().
  • Distinct values (by code reading): with the fix one apply buffer holds at most one copy per buffered update of the field, so no more value bytes than the packet buffered for that field, and those already sit in an int-addressed structure (FieldUpdatesBuffer.byteValues, a BytesRefArray with int offsets over a ByteBlockPool that advances with Math.addExact; FieldUpdatesBuffer.java:87, 111, 207-210, BytesRefArray.java:34-36, 64-72, ByteBlockPool.java:187-199). So about 2 GiB of distinct values for one field in one packet reaches that buffering limit at the same scale, before any apply; buffering that much takes a RAM buffer above 2 GB or flushing by document count only (FlushByRamOrCountsPolicy.java:34-52). The merge carry-over path (IndexWriter.java:4640-4687) also fills the buffer document by document, where the fix only shares a copy between consecutive equal values; not analysed further.
  • Cost: one byte comparison per matched document, the size of the copy it replaces, inside the synchronized add(), so it lengthens the locked section; no performance or concurrency benchmark was run. A cheaper first check (same array, offset and length as the last call) is possible but untested.
  • The end-to-end test needs 8-12 GB of heap (at most a @Monster test, like Test2BBinaryDocValues); the small-heap unit test TestBinaryDocValuesFieldUpdatesSharedValue suits CI.

Page the value bytes with long offsets (not built)

#

Store the values as BinaryDocValuesWriter does, in PagedBytes with long offsets.

Trade-offs

Still holds one copy per document (2.2 GB for the repro) while applying, and the iterator (:35-71, one BytesRef and int offsets) has to change. On its own it moves the limit to the heap; for many distinct values it would only matter if the buffering structure were made long-addressed too (by code reading). The first option alone fixes the executed failure.

Fail with a clear message (not recommended alone)

#

Check the byte length in add and throw a descriptive exception, like the entry-count guard (DocValuesFieldUpdates.java:375-379).

Trade-offs

A guard inside add() still throws inside the apply event, so the writer still closes and the data is still lost; only the message improves. Rejecting the update cleanly would need a check outside the tragic event path, which is hard because the number of matched documents is known only during the apply, not when the update is buffered.

Downstream note

#

Not a Lucene security issue (the application controls the update); a service that lets its users trigger binary doc-values updates by a shared term should bound documents matched times value size until this is fixed.

How it was found

#

While building a grid-based translation-validation check of the doc-values update buffers against a simple model (randomized values, 2,393,731 checks, no mismatch), the finder noticed that the value buffer is one int-sized array whose limit no small-scale check can reach. It then drove one public-API update to that limit, and the commit failed and closed the writer.

The method in full140 words

Method: semi-formal. In a hunt unit on packed, mutable and paged structures, the finder wrote a grid-based translation-validation harness (randomized operations and values) for the doc-values update buffers on the real jar: BinaryDocValuesFieldUpdates offsets, lengths and values checked against a TreeMap model, up to 4,097 updates per buffer and values up to 306 bytes, 2,393,731 checks, 0 mismatches.

  • While modelling it, the finder noted that the value buffer is one BytesRefBuilder with an int length, a bound no small-scale check can reach, and that applying one update calls add once per matched document with the same value.
  • The hypothesis was witnessed with a public-API JUnit on the stock main jar (2,100 documents x 1 MiB), then on 10.5.2, 9.12.3, 8.11.4, 8.0.0 and 7.6.0. No model checker or prover found the overflow itself; the model only pointed at the unchecked bound.

History

#

Every release executed from 4.8.0 to 10.5.2, and main, fails; before 7.0.0 the writer stays open but stuck instead of closing, and from 7.7.0 a lone update fails at half the size.

Versions tested7 rows

Bug record

#

LFV-838, snapshot of 2026-10-29

Registry title
A binary doc-values update whose term matches many documents copies its value once per matched document into one int-sized buffer when it is applied, so at 2^31 bytes in one segment (about 2^30 for the first update of a field in a packet) commit throws ArrayIndexOutOfBoundsException (AssertionError with -ea) and IndexWriter closes itself, losing the update and every uncommitted document (every release since 4.8.0)
Area
index / IndexWriter doc-values updates (BinaryDocValuesFieldUpdates value buffer, FrozenBufferedUpdates apply, applyUpdatesPacket tragic close)
Priority
Medium, rank 112: Since 4.8.0, on default config, a core binary doc-values update that matches many documents always closes IndexWriter at commit and loses every uncommitted document; it is loud, does not corrupt the index and needs the uncommon shared-term pattern at gigabyte scale.
Impact class
crash
Impact note
Applications that call updateBinaryDocValue, updateDocValues or softUpdateDocument(s) with a binary doc-values field, with the default configuration, are hit when the documents one buffered update matches in one segment times the value length reach 2^31 bytes (2^30 for the first update of its field in a packet, which is the case for a lone update, through the linked double-buffering bug), for example 1 MiB on 1,100 documents or 4 KiB on 530,000 documents [exec]: the commit (or flush or NRT open) that applies it throws, the writer closes itself and the update plus every acknowledged uncommitted document is lost, while the index is not corrupted and a new writer opens on the last commit [exec]; no RAM-buffer setting prevents it, because only the one value is buffered and the gigabytes arise at apply time.
Summary
You commit 2,100 documents that share the term group:g, add one more document, call updateBinaryDocValue(group:g, field, a 1 MiB value) once and commit; the javadoc sets no size limit and says the value replaces the value of all affected documents, and the resulting 2.1 GB of binary doc values is an index Lucene can hold (a build with the fix sketch commits it). Instead, applying the update appends a full copy of the value for every matched document to one int-addressed BytesRefBuilder, which overflows at 2^31 bytes: commit throws ArrayIndexOutOfBoundsException (with -ea, AssertionError 'size must be positive (got -2147483648): likely integer overflow?'), IndexWriter treats it as a tragic event and closes itself, and both the update and the extra uncommitted document are gone. On 7.7.0 and later a lone update fails at half that size (1,100 documents x 1 MiB) because of the linked bug that applies the first update of a field twice, and ordinary value sizes suffice too (530,000 documents x 4 KiB).
