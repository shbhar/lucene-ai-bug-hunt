Growing StandardTokenizerImpl's buffer after a yypushback to the buffer start drops a supplementary character

If you drive the generated scanner StandardTokenizerImpl directly, push a token back to the buffer start with yypushback and grow the buffer with setBufferSize, the next read overwrites half of an emoji it was holding back: the character vanishes and the next offsets are one short. StandardTokenizer and StandardAnalyzer are unaffected.

The finding in 30 seconds

#

The scanner keeps half of an emoji aside when it lands in the buffer's last slot, and puts it back only when it shifts the buffer. Growing the buffer and restarting the scan at slot 0 skips that shift, so the next read writes new text over the kept half.

Background: how the scanner keeps half an emoji aside

#
  1. An emoji such as U+1F600 is two Java chars, a high and a low surrogate; the scanner must see both together.
  2. StandardTokenizerImpl reads text into a fixed buffer. When a read ends with a high half in the last slot, it marks that half as not read yet, so the next read can bring its partner.
  3. It counts the half as read again only when a later read first moves the unread text to the front of the buffer, and that move happens only when the current token does not start at slot 0.

The finding, step by step

#
  1. Scan ab😀cd with StandardTokenizerImpl and a 3-char buffer. The text is 6 Java chars: the emoji is a high and a low surrogate at positions 2 and 3. The first read fills the 3 slots with a, b and the high half; the scanner holds that half back until its partner fits, and returns the token ab.
  2. Call yypushback(2), so that ab is read again, then setBufferSize(8). Both calls are public, and each one alone keeps the tokens intact.
  3. You expect ab@0, 😀@2, cd@4 (token@offset), as with only one of the two calls or with an 8-char buffer from the start.
  4. Instead you get ab@0, cd@3. Because the scan restarts at slot 0, the next read skips the buffer shift, the only step that puts the held half back, and writes the rest of the text from slot 2, over the held high half. The emoji is gone and cd is one char early; no error is raised.

Who is affected

#

Only code that drives StandardTokenizerImpl or UAX29URLEmailTokenizerImpl itself, pushes back a token that starts at buffer slot 0 and grows the buffer before the next read. StandardTokenizer, StandardAnalyzer, UAX29URLEmailTokenizer and every other Lucene component never make that call sequence. The loss is silent.

Mechanism, terms and numbers831 words

When a refill fills StandardTokenizerImpl's buffer and its last char is a high surrogate, zzRefill holds that char back (--zzEndRead; zzFinalHighSurrogate = 1, StandardTokenizerImpl.java:782-786 at 5adff78bb168); the field javadoc says it then sits in "the final zzBuffer position" (:642-648). The held char re-enters the input only when a later refill shifts the buffer, which happens only if zzStartRead > 0 (:756-758). setBufferSize copies the buffer into a larger array but keeps zzEndRead and zzFinalHighSurrogate (:712-718). After yypushback of a token that starts at buffer index 0 and a growth (in either order), the next refill does not shift, computes requested > 0 (:769) and reads new input at zzBuffer[zzEndRead] (:773), over the held char: one supplementary character silently disappears, with assertions on and off. The offsets after it are one short until the next buffer shift, which folds in one stale NUL char that is dropped but can split a word in two; offsets after that are right again. JFlex's own growth branch puts the held char back before it reads; LUCENE-5897 (4.10.0) removed that branch from these scanners and added setBufferSize without that step. UAX29URLEmailTokenizerImpl has the same code and fails the same way. No Lucene tokenizer, analyzer or factory makes this call sequence, so only direct users of the public generated scanners are hit. Putting the held char back in zzRefill before reading, in Lucene's no-expansion skeleton, fixes it. Priority Low.

The mechanism (main 5adff78bb168, StandardTokenizerImpl.java, generated)

#
  1. Hold-back. The first refill asks for 3 chars and gets a, b and the emoji's high half. The read filled the request and its last char is a high surrogate, so zzRefill does --zzEndRead; zzFinalHighSurrogate = 1 (:782-786): zzEndRead = 2, and the high half waits in slot 2, the last slot. The field javadoc: "When a lead/high surrogate has been read from the input stream into the final zzBuffer position, this will have a value of 1" (:642-648).
  2. Put back only on a shift. The held char re-enters the input only in if (zzStartRead > 0) { zzEndRead += zzFinalHighSurrogate; zzFinalHighSurrogate = 0; ... } (:756-758). With the buffer unchanged and a token that starts at 0, the next refill finds requested = 3 - 2 - 1 = 0 and returns (:769-771): the token is chopped at the buffer size, as designed. That is how the first getNextToken() returns ab.
  3. The growth keeps the hold-back (the fix site). setBufferSize(8) copies the 3 chars into a new char[8] and leaves zzEndRead = 2, zzFinalHighSurrogate = 1 (:712-718, source StandardTokenizerImpl.jflex:151-156). The held char is now in slot 2 of 8, not in the final slot.
  4. Pushback to slot 0. yypushback(2) sets zzMarkedPos = 0 (:946-950), so the next scan starts with zzStartRead = 0. It re-reads a, b, reaches zzEndRead and refills: no shift, so nothing is put back; requested = 8 - 2 - 1 = 5 (:769), and zzReader.read(zzBuffer, 2, 5) (:773) writes the low half, c and d into slots 2-4, over the held high half.
  5. Outcome. The lone low half is not a token, so the emoji is lost, and cd sits one slot early: yychar() 3 instead of 4. zzFinalHighSurrogate is still 1, so the next shift (:756-759) also counts the never-written slot right after the new text as input: one stale NUL char. It is dropped, but it can split a word that straddles it, and the offsets after it are right again. In the repro it falls at the end of the input, so the end offset still comes out as 6 (executed control). With the same calls on ab😀cd efgh ijkl mnop, the tokens after the re-read ab are [cd@3, e@6, fgh@8, ijkl@12, mnop@17] instead of [😀@2, cd@4, efgh@7, ijkl@12, mnop@17], and ab😀cdefgh gives [cdef@3, gh@8] instead of [😀@2, cdefgh@4] (executed, assertions on and off; fix A gives the correct streams).

Why scanners on JFlex's default skeleton are not affected. Lucene's no-expansion skeleton has no growth branch (skeleton.disable.buffer.expansion.txt:80-102). JFlex's default skeleton grows inside zzRefill and does zzEndRead += zzFinalHighSurrogate; zzFinalHighSurrogate = 0 right there, before it reads (skeleton.default.txt:97-105).

Wider trigger. Any pushed-back token that starts at buffer index 0 works, not only the first token of a stream: in z abcd😀xy with a 5-char buffer, pushing back the second token abcd after a shift and growing to 16 gives [z@0, abcd@2, abcd@2, xy@7], without the emoji. Growing first and pushing back second fails the same way.

Same code elsewhere. UAX29URLEmailTokenizerImpl (analysis-common, public final) has the same setBufferSize (UAX29URLEmailTokenizerImpl.java:33585-33590) and the same put-back-on-shift (:33631) and fails the same way. ClassicTokenizerImpl is not affected: it is package-private, its setBufferSize throws UnsupportedOperationException, and its JFlex growth branch puts the held char back.

Exposure and likelihood251 words
  • Who. Code that uses one of the two public generated scanners directly, calls yypushback back to buffer index 0 while a high surrogate is held in the last slot, and grows the buffer with setBufferSize before the next refill (in either order).
  • Default vs opt-in. Not on any Lucene path. StandardTokenizer keeps its scanner private (StandardTokenizer.java:39-40), never calls yypushback, and calls setBufferSize only from setMaxTokenLength (:95-105). Raising the max token length mid-stream there works: 3 raised to 8 after the first token gives [ab@0, 😀@2, cd@4], because between two tokens the scan position is past slot 0 and the refill shifts first. UAX29URLEmailTokenizerImpl calls yypushback only inside lexer actions that keep scanning in the same call (UAX29URLEmailTokenizerImpl.jflex:283, :286, :289); WikipediaTokenizer calls it from outside (WikipediaTokenizer.java:251, :294) on a scanner without setBufferSize.
  • Effect. One supplementary code point (an emoji, a CJK Extension B ideograph, ...) is lost, and the offsets after it are one short until the next buffer shift. That shift folds in one stale NUL char: it is dropped, but it can split a word in two (in ab😀cd efgh ijkl mnop, efgh comes out as e@6 and fgh@8), and offsets after it are right again. No exception; the same with assertions on and off.
  • Scale. A 6-char input is enough; it needs a supplementary character that straddles the end of the buffer.
  • Likelihood. Contrived: no public report in the twelve years since 4.10.0.

Why it looks unintended

#
  • The scanner's javadoc puts a held-back high surrogate in the buffer's final slot; a growth breaks that, yet the next read is sized as if it held.
  • JFlex's own buffer growth puts the held char back first; the 2014 change that brought setBufferSize dropped that step.
  • Both scanners are public, unmarked API; each call alone keeps the tokens intact.
The full argument203 words
  • The invariant is written in the class. The zzFinalHighSurrogate javadoc puts the held char in "the final zzBuffer position" (StandardTokenizerImpl.java:642-648). The read size zzBuffer.length - zzEndRead - zzFinalHighSurrogate (:769) is safe only while that holds.
  • JFlex's growth keeps it. The default skeleton's growth branch does zzEndRead += zzFinalHighSurrogate; zzFinalHighSurrogate = 0 before reading (skeleton.default.txt:97-105). acf92428507 (LUCENE-5897) deleted that branch, these two lines included, from both scanners and added setBufferSize without them; the LUCENE-5897 thread (#6959) shows the deleted hunk and nobody discusses the step.
  • Public API, each call fine alone. Both classes are public final (StandardTokenizerImpl.java:45, UAX29URLEmailTokenizerImpl.java:49) in exported packages (lucene/core/src/java/module-info.java:24 exports org.apache.lucene.analysis.standard, lucene/analysis/common/src/java/module-info.java:43 exports org.apache.lucene.analysis.email) with no @lucene.internal or @lucene.experimental mark. yypushback requires only number <= yylength() (:939-950); setBufferSize ("Sets the scanner buffer size in chars", :712) states no precondition and copies the live buffer, so a resize is meant to keep the input. Pushback only gives [ab@0, ab@0, 😀@2, cd@4] (the first token, then the re-read one); growth only gives [ab@0, 😀@2, cd@4].
  • yypushback's promise ("They will be read again") is kept: ab is read again. The lost char is the one after it.
The devil's-advocate check149 words

The strongest case for "unsupported use": the class is generated plumbing. StandardTokenizer keeps it in a private field and its javadoc tells users with other needs to copy the grammar (StandardTokenizer.java:28-40); yypushback is a JFlex lexer-action API that this grammar never uses; setBufferSize first appeared on StandardTokenizerInterface, marked @lucene.internal (acf92428507), which LUCENE-6000 removed (947a05c9c1a, 2014-10-09) without marking the Impl's method. A maintainer may fairly answer "do not drive the generated scanner yourself".

Why it fails: none of that is written on the public class; Lucene's own WikipediaTokenizer pushes back from outside between two getNextToken() calls (WikipediaTokenizer.java:251, :294); and the failure is a silent loss of input, not a rejected call. It does justify priority Low and framing the report as a robustness fix, not as a broken supported-API contract; the verifiers and the cross-model reviewer rated this argument moderate.

Suggested fix

#

Recommended Put the held char back in zzRefill before reading when the buffer has room after it (fix A)

In Lucene's no-expansion JFlex skeleton, add one if block to zzRefill that puts a held-back high surrogate back into the input before it reads whenever the buffer has room after it, as JFlex's own buffer growth does; then regenerate both scanners. The repro then passes, and the 138 existing standard and email analysis tests still pass (1 skipped).

    /* a held-back high surrogate has room after it again once setBufferSize grew the buffer:
       put it back into the input before reading more, as the default skeleton's growth branch does */
    if (zzFinalHighSurrogate == 1 && zzEndRead + 1 < zzBuffer.length) {
      zzEndRead++;
      zzFinalHighSurrogate = 0;
    }

Put the held char back in zzRefill before reading when the buffer has room after it (fix A) (validated by the checks) (recommended)

#

In gradle/regenerate/jflex/skeleton.disable.buffer.expansion.txt (used by exactly these two scanners), insert the block after the shift, right before /* fill the buffer with new input */, then regenerate StandardTokenizerImpl.java and UAX29URLEmailTokenizerImpl.java and their checksums (regenerateStandardTokenizer, regenerateUAX29URLEmailTokenizer).

    /* a held-back high surrogate has room after it again once setBufferSize grew the buffer:
       put it back into the input before reading more, as the default skeleton's growth branch does */
    if (zzFinalHighSurrogate == 1 && zzEndRead + 1 < zzBuffer.length) {
      zzEndRead++;
      zzFinalHighSurrogate = 0;
    }

Trade-offs

A hold-back always leaves zzEndRead == zzBuffer.length - 1, so the new condition is true only after a growth since the hold-back; every other refill runs as today, and the regular StandardTokenizer path puts the char back in the shift branch first. It edits generated code shared by two scanners, and the open #14645 may replace the skeleton altogether.

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, seed DEADBEEF: without the fix the repro fails with assertions on and off, and so do the same steps on UAX29URLEmailTokenizerImpl (a check file, not part of the repro).
  • The skeleton edit was regenerated with the build's own JFlex (regenerateStandardTokenizer, regenerateUAX29URLEmailTokenizer): each regenerated .java gains only this block, and the two checksum files change.
  • With the fix the repro passes with assertions on and off; with assertions on, every core org.apache.lucene.analysis.standard test and every analysis-common org.apache.lucene.analysis.email test pass (including TestStandardAnalyzer, TestUAX29URLEmailTokenizer and the sibling check): 140 tests, 0 failures, 1 skipped. The generated-sources checksum checks and :lucene:core:checkGoogleJavaFormat pass. The analysis-common format check and the full module suites were not run.

Apply a resize only at the next yyreset (fix B)

#

Store the new size and let yyreset allocate the buffer. It would also fix LFV-1202 (a mid-stream shrink that throws).

Trade-offs

Changes a call order that works today: raising StandardTokenizer.setMaxTokenLength mid-stream would take effect only at the next stream. Not run.

Put the held char back inside setBufferSize (not enough)

#

Count the held char as read when setBufferSize grows the buffer.

Trade-offs

Does not fix it: the scanner then decodes the high half by itself before any refill brings the low half, so the emoji is still lost ([ab@0, cd@4], an executed check with a patched class by the independent reproducer).

Downstream note

#

Downstream products are affected only where their own code drives the generated scanner with yypushback and setBufferSize; text sent through Lucene's tokenizers, analyzers or factories cannot trigger it.

How it was found

#

A proof-obligation audit of StandardTokenizerImpl's contract: a pushback and a buffer resize must not change the input the scanner reads. setBufferSize keeps a held-back high surrogate that only a buffer shift puts back, and a public-API JUnit test then witnessed the lost character.

The method in full174 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligations were the javadoc of yypushback (the chars are read again by the next scan), setBufferSize without a precondition, and the scanner invariant that JFlex's own growth keeps (a held-back high surrogate is put back before the buffer gets room past it).
  • A public-API JUnit test (abcd + U+1F600 + xy, buffer 5 grown to 16) failed on main and on the 10.6.0 and 9.12.3 jars, and a probe showed that each call alone keeps the tokens, both orders of the two calls lose the char, and StandardTokenizer's mid-stream growth is correct.
  • An independent reproducer (with a smaller input, ab + U+1F600 + cd, buffer 3 grown to 8, which became the repro), an executed cross-model review (with its own input, mno + U+1F680 + pq, buffer 4 grown to 13) and a devil's-advocate verifier (with the first test's input and a second-token variant, z abcd😀xy) reproduced it, and an adjudication re-ran them.

Only code that drives the public generated scanner StandardTokenizerImpl (or UAX29URLEmailTokenizerImpl) directly is hit: after a token that starts at buffer index 0 while a high surrogate is held in the buffer's last slot, it must call yypushback and grow the buffer with setBufferSize (in either order) before the next refill, and then one supplementary character (for example an emoji) silently disappears from that stream, the offsets after it are one short until the next buffer shift, and that shift folds in one stale NUL char that is dropped but can split a word in two; StandardTokenizer, StandardAnalyzer, UAX29URLEmailTokenizer and every other Lucene component are not affected (none of them calls yypushback on these scanners from outside, and their mid-stream growth through setMaxTokenLength is correct); -ea and -da, small inputs, every release from 4.10.0 through 10.6.0 and main.
Summary
You drive StandardTokenizerImpl directly on "ab" + U+1F600 + "cd" with setBufferSize(3), read the first token "ab", push it back with yypushback(yylength()) and grow the buffer with setBufferSize(8). You expect the scan to go on with ab@0, U+1F600@2, cd@4, as it does with only the pushback or only the growth. Instead it returns ab@0, cd@3: the first refill held the emoji's high surrogate back in the last slot of the 3-char buffer (zzFinalHighSurrogate), the growth keeps that hold-back, and because the pushback left the scan at buffer index 0 the next refill skips the shift that would fold the held char back in and reads new input over it, so the emoji is lost and the next offsets are one short (on longer input a later buffer shift folds in one stale NUL char, which is dropped but can split a word, and the offsets after it are right again).
