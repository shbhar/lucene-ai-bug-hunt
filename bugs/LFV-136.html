MultiDocValues numeric, binary and norms views throw NullPointerException from advance() after advanceExact() landed on a segment without the field

On the merged numeric, binary and norms doc-values iterators of MultiDocValues, advance() after an advanceExact() that returned false in a segment without the field throws NullPointerException instead of returning the next document with a value. A custom OneMerge#reorder gets the same iterators; 7.0.0 through 10.6.0 are affected.

The finding in 30 seconds

#

Two calls on one merged iterator are enough, on an index where one segment lacks the field.

Background: merged doc-values iterators

#
  1. A Lucene index is a list of segments. Each segment has its own doc-values iterator per field; a segment in which no document has the field has none (null).
  2. MultiDocValues.getNumericValues(reader, field) stitches the segments' iterators into one iterator over the whole index. IndexWriter hands the same stitched iterators to a custom MergePolicy.OneMerge#reorder during a merge.
  3. Besides nextDoc(), a doc-values iterator can jump forward in two ways: advance(t) jumps to the first document at or after t that has a value; advanceExact(t) moves to exactly t and returns whether t has a value. Both are legal on one iterator, as long as targets never go backwards.

The finding, step by step

#
  1. Index two segments: segment 0 holds docs 0 and 1 without the numeric doc-values field f, segment 1 holds doc 2 with f = 42. Open one merged iterator over both: MultiDocValues.getNumericValues(reader, "f").
  2. Call advanceExact(0). It returns false, correctly: doc 0 has no value. The iterator now sits on doc 0.
  3. Call advance(1). You expect 2, the next document with a value: nextDoc() from the same spot returns 2, and the sorted-numeric view gives 2 for the same layout.
  4. Instead it throws NullPointerException: ... because "this.currentValues" is null. advanceExact recorded "segment 0 has no values" as a null per-segment iterator, and advance uses that iterator without a check while the target stays in segment 0.
  5. The binary and norms views fail the same way, with assertions on or off, in every release from 7.0.0 to 10.6.0. It never returns a wrong value, and no Lucene code calls the two methods in this order.

Who is affected

#

Only application code that reads these merged iterators itself (direct MultiDocValues use, or a custom OneMerge#reorder from 9.9.0) and calls advance() after a false advanceExact() on a sparse field; no Lucene caller does. Always a loud exception, never a wrong value. Uncaught inside reorder, it closes the IndexWriter (with merge-on-commit, uncommitted documents are rolled back).

Mechanism, terms and numbers569 words

MultiDocValues.getNumericValues, getBinaryValues and getNormValues return one doc-values iterator over all segments of a reader. When advanceExact(target) lands in a segment that has no values for the field, it returns false (correct) and remembers that segment as a null per-segment iterator while marking the segment as loaded. A following advance(t) with t in the same segment skips its "load the segment" branch and calls currentValues.advance(...) on that null: NullPointerException at MultiDocValues.java:263 (numeric), :396 (binary) or :130 (norms). The same happens for advance(NO_MORE_DOCS) after advanceExact landed in a field-less last segment. The call sequence is legal under the DocValuesIterator and DocIdSetIterator contracts, and the sorted, sorted-set and sorted-numeric views of the same class return the right document because they substitute empty iterators for missing segments. IndexWriter hands the same views to a custom MergePolicy.OneMerge#reorder (9.9.0+), where an uncaught exception closes the writer. It came with advanceExact in 7.0.0 (LUCENE-7462, 2016) and is unchanged on main. The result is always a loud exception, never a wrong value, and no Lucene caller mixes the two calls. A three-line guard in each advance() fixes it.

Terms

#
  • Merged view: the anonymous NumericDocValues / BinaryDocValues classes returned by MultiDocValues.getNumericValues, getBinaryValues and getNormValues when a reader has two or more segments. Each keeps currentLeaf, currentValues (the current segment's own iterator, or null) and nextLeaf (the next segment to load).
  • Field-less segment: a segment in which no document has the field, so LeafReader#getNumericDocValues(field) returns null. Normal for optional or sparse fields, or a field added to the schema later.

The bug

#
  1. Numeric advanceExact(target) (MultiDocValues.java:274-296) loads the target's segment if it is not loaded yet (readerIndex >= nextLeaf, :283): currentValues = currentLeaf.reader().getNumericDocValues(field) (:288), which is null for a field-less segment, and nextLeaf = readerIndex + 1 (:289). It sets docID = targetDocID (:291) and returns false (:292-293).
  2. Numeric advance(target) (:241-271) reloads only when the target lies in a segment not loaded yet (if (readerIndex >= nextLeaf), :250); inside that branch it already handles a field-less segment (:259-261). For a target in the segment that advanceExact just loaded, readerIndex < nextLeaf, so it skips the branch and calls currentValues.advance(targetDocID - currentLeaf.docBase) (:263) on null.
  3. ReaderUtil.subIndex never returns leaves.size() (ReaderUtil.java:74-94): a target >= maxDoc maps to the last segment. So after advanceExact lands in a field-less last segment, advance(NO_MORE_DOCS) throws too; the readerIndex == leaves.size() check at :251 cannot fire.
  4. Binary (advance :374-404, NPE at :396; advanceExact :407-429) and norms (advance :108-138, NPE at :130; advanceExact :141-163) have the same code.
  5. The sorted, sorted-set and sorted-numeric views fill an array of per-segment iterators up front with DocValues.empty*() for a field-less segment (sorted-numeric :463-473), so their currentValues is never null for a loaded segment, and they return the right document for the same calls.

The numbers

#

Two segments, [doc 0, doc 1: no field] [doc 2: f = 42]: advanceExact(0) = false, then advance(1) throws NullPointerException at MultiDocValues$2.advance:263; expected 2. nextDoc() from the same state and the sorted-numeric view both give 2. The hunt's exhaustive harness found the NPE in 827 of the 70,662 call sequences of length up to 3 for each of the numeric, binary and norms views, and 0 mismatches for the sorted views.

Exposure and likelihood264 words
  • Who is hit. Code that holds a merged numeric, binary or norms view and calls advance(t) after advanceExact(e) returned false, with e and t in a segment without the field (or t >= maxDoc after landing in a field-less last segment). Two entry points: MultiDocValues.getNumericValues / getBinaryValues / getNormValues (public class, tagged @lucene.experimental and @lucene.internal), and, since 9.9.0, the merged CodecReader that IndexWriter passes to a custom MergePolicy.OneMerge#reorder (@lucene.experimental), whose norms, numeric and binary doc values are these views (SlowCompositeCodecReaderWrapper.java:291, :412, :417).
  • No Lucene caller is affected. DocumentDictionary uses advance only; the infix suggesters open a fresh view per hit; Luke uses advanceExact only; the in-tree reorderers and merge consumers iterate.
  • Ordinary data. Default codec and config; 2 segments and 3 documents are enough. A field-less segment is normal for optional or sparse fields.
  • What happens. A NullPointerException at the first such advance(), with assertions on and off. No wrong value, no hang, nothing written.
  • Inside reorder it closes the writer (executed on main and 10.5.2). If the exception escapes a reorder override, IndexWriter treats it as a tragic merge failure and closes: forceMerge(1) throws, a reopened writer retries the same merge and closes again, and with merge-on-commit (on by default) commit() fails and the documents added since the last commit are rolled back. The committed index stays intact (CheckIndex clean). With the fix the merge completes.
  • How likely. Rare: code that mixes the two calls fails on ordinary sparse data, so it would most likely surface during development. No prior public report since 7.0.0 (2017).

Why it looks unintended

#
  • The contract allows it: after advanceExact(0), docID() is 0, and advance(t) is defined for any t > docID().
  • The sorted views of the same class and the per-segment codec iterators return 2 for the same calls.
  • advance() was written before advanceExact() existed (2016); the new method created a null state the old checks never covered.
The full argument305 words
  • Contract. DocValuesIterator#advanceExact (DocValuesIterator.java:24-33): "After this method returns, docID() returns target"; the only calls it declares illegal after a false return are intoBitSet and docIDRunEnd (:30-31). DocIdSetIterator#advance (DocIdSetIterator.java:137-163) is undefined only for target <= current or after exhaustion; for target > current it "behaves as if written" as a nextDoc() loop (:144-153), and it "may be called with NO_MORE_DOCS" (:157-159). The repro obeys both. Nothing in MultiDocValues' javadoc narrows this.
  • Same class, right answer. The sorted, sorted-set and sorted-numeric views return 2 for the same calls, and so do single-segment codec iterators. The numeric view's own reload branch handles a field-less segment (:259-261), so field-less segments are meant to work.
  • Tests treat the mix as legal. The test framework's AssertingNumericDocValues.advance asserts only target > in.docID() (AssertingLeafReader.java:791-801). Upstream TestIndexedDISI calls nextDoc() right after a false advanceExact() (:595-600). Upstream TestMultiDocValues never mixes the two on one iterator (testRandomAdvance :424-437, testRandomAdvanceExact :439-448 run on separate iterators), and its numeric and binary tests put the field in every document, which is why no test caught it.
  • History. advance() came from LUCENE-7407 (f7aa200d406, 2016-09-21), when a loaded segment always had a non-null iterator. A month later LUCENE-7462 (9aca4c9d560) added advanceExact(), which can leave currentValues null for a loaded segment. git log -G 'currentValues == null' lists only these two commits; no javadoc, CHANGES.txt or MIGRATE.md entry, test or discussion restricts the mix.
  • A committer has seen the null state, in a different, illegal call: in the 2020 review of apache/lucene-solr#1733 (LUCENE-9450), mikemccand traced an NPE from binaryValue() to currentValues being null "since .advanceExact was not yet called" (a value accessor on an unpositioned iterator, misuse) and suggested an assert. Not a report of this bug.
The devil's-advocate check138 words

The strongest case for "intended" (the refute-lens cross-model reviewer and the devil's advocate): MultiDocValues is @lucene.experimental and @lucene.internal, its javadoc says "This is very costly" and steers users to per-leaf access, and no Lucene caller mixes the two calls, so the sequence is out of contract or not worth fixing.

Why it fails: @lucene.internal is an API-stability label ("might change in incompatible ways in the next release", RenderJavadocPlugin.java:506), not permission to throw on a sequence the returned type's own contract allows. The same iterators also reach the public experimental OneMerge#reorder hook as ordinary NumericDocValues / BinaryDocValues of a CodecReader, with nothing that warns the hook's author. The tag lowers priority, not validity. Verdict: not intended; a low-priority robustness bug. Residual risk: a maintainer may answer "internal API, use per-leaf access"; the reorder path answers that.

Suggested fix

#

Recommended A. Guard the same-segment path in advance()

Add one branch after the reload block of each advance(): if the segment was loaded by advanceExact and has no values (currentValues == null), return nextDoc(), which continues in the next segment. Three lines per view; the repro then passes with assertions on and off, and 18 related core test classes, the suggest module and the core static checks pass.

         if (readerIndex >= nextLeaf) {
           ...
           if (currentValues == null) {
             return nextDoc();
           }
+        } else if (currentValues == null) {
+          // positioned by advanceExact on a leaf that has no values for this field
+          return nextDoc();
         }
         int newDocID = currentValues.advance(targetDocID - currentLeaf.docBase);

A. Guard the same-segment path in advance() (validated by the checks) (recommended)

#

In advance() of the numeric (:250-263), binary (:383-396) and norms (:117-130) views. Numeric shown; the other two are identical.

         if (readerIndex >= nextLeaf) {
           ...
           if (currentValues == null) {
             return nextDoc();
           }
+        } else if (currentValues == null) {
+          // positioned by advanceExact on a leaf that has no values for this field
+          return nextDoc();
         }
         int newDocID = currentValues.advance(targetDocID - currentLeaf.docBase);

Trade-offs

  • Correct by construction: currentValues == null with a target in the current segment means advanceExact found no values there, so the next document with a value is in a later segment, where nextDoc() starts (nextLeaf).
  • Covers advance(NO_MORE_DOCS) on a field-less last segment too (nextDoc() returns NO_MORE_DOCS).
  • No change for any call sequence that works today; one null check per advance() call.

B. Take the reload branch also when currentValues is null (validated by the checks)

#

An independent verifier's alternative: if (readerIndex >= nextLeaf || currentValues == null) { in each advance().

-        if (readerIndex >= nextLeaf) {
+        if (readerIndex >= nextLeaf || currentValues == null) {

Trade-offs

One condition per view, but it asks the segment for its doc values again (one extra getNumericDocValues / getBinaryDocValues / getNormValues call), which again returns null and falls into the existing return nextDoc(). Reads less directly than A.

What the checks validated

Gradle, same worktree: the repro passes with B, with assertions on and off; the independent verifier's 7-test class passes 7/0.

C. Never store null: substitute an empty iterator, as the sorted views do

#

Use DocValues.emptyNumeric() / DocValues.emptyBinary() for a field-less segment, like the sorted views (:463-473).

Trade-offs

Removes the null state from all methods at once, but touches nextDoc(), advance() and advanceExact() of three views: a larger diff. Not tested.

Downstream note

#

Downstream code that reads these merged iterators itself, such as a custom OneMerge#reorder, gets a loud exception on this call order, never wrong data; until a fix ships it should avoid the mix or catch the exception, because an uncaught one inside reorder closes the IndexWriter.

How it was found

#

Semi-formal: a bounded-exhaustive harness compared every MultiDocValues view with the per-segment iterators placed end to end, over every legal sequence of up to 3 calls on 1-3 segments (70,662 sequences for each of six views). The numeric, binary and norms views threw an NPE; the smallest case was two calls on two segments. Independent reproducers then confirmed it.

The method in full198 words

Method: semi-formal (bounded-exhaustive translation validation). A hunt unit auditing the callers of ReaderUtil.subIndex wrote a harness that builds every small index layout (which documents of which segment have a value) and checks each MultiDocValues view, on the stock jar, against the concatenation of the segments' own iterators, over every legal nextDoc / advance / advanceExact sequence: length up to 3 on 1-3 segments (258 layouts, 70,662 sequences per view, 423,972 sequence checks over the six views), and length up to 4 on up to 2 segments (42 layouts, 10,790 sequences per view, 64,740 checks).

It reported a NullPointerException bucket for the numeric, binary and norms views (827 sequences each in the run of length up to 3) with the minimal witness: segments [(00)(1)], calls [advanceExact(0), advance(1)]. The sorted, sorted-set and sorted-numeric views had 0 mismatches. A run past maxDoc added the advance(NO_MORE_DOCS) case. The same harness found the sibling norms bug LFV-142; with both fixes it reports no mismatches.

The finding was turned into JUnit tests (direct and through OneMerge#reorder), reviewed by a reviewer from another model family (OpenAI GPT-5.6) in three sessions, reproduced independently, judged, and cut to the one-test repro on 645d4fe14a20.

Low, rank 1008: The MultiDocValues numeric, binary and norms views throw an NPE from advance() after advanceExact() lands on a segment without the field; never a wrong value, and only custom code on internal views or a custom reorder reaches it (likely caught during development).
Impact class
minor
Impact note
Only application code that holds a merged numeric, binary or norms doc-values view, either from MultiDocValues.getNumericValues/getBinaryValues/getNormValues (a class tagged @lucene.experimental and @lucene.internal) or, since 9.9.0, from the merged reader that IndexWriter passes to a custom MergePolicy.OneMerge#reorder (@lucene.experimental), and that calls advance(t) after advanceExact(e) returned false, with e and t in the same segment and that segment without values for the field (or t = NO_MORE_DOCS after advanceExact landed in a last segment without the field); default codec and config, with -ea and -da, ordinary scale (2 segments, 3 docs in the repro); the result is always a loud NullPointerException, never a wrong value, and no Lucene caller mixes the two calls on these views; if the exception escapes a reorder override, IndexWriter treats it as a tragic merge failure and closes itself, and with merge-on-commit (the default) commit() fails and the documents added since the last commit are rolled back, while the committed index stays intact (CheckIndex clean); released 7.0.0 through 10.6.0 (10.6.0 executed: the one-test minimal repro fails on the release jars with -ea and -da, 2026-11-01).
Summary
You read a merged doc-values view over an index with several segments (MultiDocValues.getNumericValues, getBinaryValues or getNormValues, or the merged reader that IndexWriter hands to a custom OneMerge#reorder), call advanceExact(0), which returns false because doc 0's segment has no values for the field, and then call advance(1). You expect advance(1) to return the next document that has a value (doc 2 in the repro), as the sorted-numeric view of the same index and the per-segment codec iterators do. Instead it throws NullPointerException ('this.currentValues is null'): advanceExact stored a null per-segment iterator for the segment without the field, and advance() assumes that iterator is non-null as long as the target stays in the same segment.
