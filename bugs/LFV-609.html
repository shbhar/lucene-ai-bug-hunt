matchhighlight PassageFormatter closes crossing highlights in the wrong order, so per-highlight end tags cross

With a separate end tag per highlight, matchhighlight's PassageFormatter closes crossing highlights (overlapping, not nested) outer first: foo bar baz with [0,7) as <a> and [4,11) as <b> gives <a>foo <b>bar</a></b><b> baz</b>, not <a>foo <b>bar</b></a><b> baz</b>. Every release since 9.0.0 has it; one shared end tag hides it.

The finding in 30 seconds

#

The formatter wraps each highlight in a start and an end string; where two highlights overlap, it closes and re-opens the inner one so the markup stays nested, but it writes the two end strings in the wrong order.

Background: how the formatter handles overlapping highlights

#
  1. The matchhighlight package finds where queries match in a field value as character ranges, picks passages, and PassageFormatter wraps every range in a start and an end string, for example <b> and </b>. The strings can be one pair for all ranges or computed per range, for example one tag per query.
  2. Two ranges can overlap without one containing the other: foo bar = [0,7) and bar baz = [4,11) share bar. Wrapping each one as is would cross the tags.
  3. So the formatter keeps a stack of open ranges. Where a range ends, it closes the ranges opened after it, closes the range itself and re-opens the others, which splits bar baz into bar inside foo bar and baz after it.

The finding, step by step

#
  1. You give each highlight its own tags with new PassageFormatter("...", startFn, endFn) and format foo bar baz with two overlapping highlights: [0,7) = foo bar as <a>...</a> and [4,11) = bar baz as <b>...</b>.
  2. At offset 7, where <a> ends, <b> is still open inside it. You expect the formatter to write </b>, then </a>, then re-open <b>: <a>foo <b>bar</b></a><b> baz</b>.
  3. Instead you get <a>foo <b>bar</a></b><b> baz</b>: </a> comes before </b>, so the tags cross and an XML parser rejects the passage. The text and the highlighted characters are right; no error is raised.
  4. The same happens end to end: MatchHighlighter with the phrase queries foo bar and bar baz and one tag per query returns <q1>foo <q2>bar</q1></q2><q2> baz</q2>.
  5. Why: at each highlight's end, the loop that closes the highlights opened after it walks them outer first instead of inner first. With one shared end tag both orders print the same bytes, which is why Lucene's own callers and tests never show it.

Who is affected

#

Applications that build their own highlighter from matchhighlight and give highlights different end strings through the public Function constructor, for example one tag per query (the 'different colors' use case). It takes two matches in one passage that overlap without nesting, such as phrases foo bar and bar baz. The String constructor and every caller in Lucene are unaffected.

Mechanism, terms and numbers613 words

PassageFormatter, the matchhighlight package's passage formatter, takes the start and end strings either as constants or as functions of each highlight (PassageFormatter(String, Function<OffsetRange,String>, Function<OffsetRange,String>)). When two highlights in a passage overlap without one containing the other, it keeps the output nested: where the first one ends, it closes the second, closes the first and re-opens the second. It closes them in the wrong order, outer first, so foo bar baz with [0,7) as <a> and [4,11) as <b> comes out <a>foo <b>bar</a></b><b> baz</b> instead of <a>foo <b>bar</b></a><b> baz</b>, which an XML parser rejects.

The text, the highlighted characters and the balance of start and end strings are right; only the order of the end strings where highlights cross is wrong (two in this example; a chain of three crossing highlights puts three in opening order). With one shared end string, which every Lucene caller and test uses, both orders print the same bytes, so Lucene's own callers and tests cannot show the defect, and have not since the class was added in 9.0.0. A one-line change, closing from the top of the stack down, fixes it and leaves shared-end-string output byte-identical.

The code (main 645d4fe14a20, lucene/highlighter/.../matchhighlight/PassageFormatter.java)

#
  1. format(StringBuilder, CharSequence, Passage) (:110-135) handles 0 and 1 markers inline and sends 2 or more to multipleMarkers ("Multiple markers, possibly overlapping or nested.", :127-131).
  2. slicePoints (:175-201) makes a START and an END point per marker, sorted by offset; at one offset ends come before starts (END(1), START(2), :204-206), "Longer start slice points come first" (:190) and "Shorter end slice points come first" (:193): the inner marker ends first.
  3. multipleMarkers (:138-173) keeps markerStack, the open markers in opening order. START (:147-150) pushes the marker and appends its start string. END (:152-161):
int markerIndex = markerStack.lastIndexOf(currentMarker);          // :153
for (int k = markerIndex; k < markerStack.size(); k++) {           // :154  bottom-up: outer first
  b.append(markerEnd.apply(markerStack.get(k)));
}
markerStack.remove(markerIndex);                                   // :157
for (int k = markerIndex; k < markerStack.size(); k++) {           // :158  re-open, bottom-up (correct)
  b.append(markerStart.apply(markerStack.get(k)));
}

The markers above markerIndex were opened after the ending marker and are still open: they sit above it on the stack ([4,11) starts inside [0,7) but is not contained in it). Closing and re-opening them keeps the output nested only if they are closed top of the stack down. The re-open loop correctly runs bottom-up; the close loop runs bottom-up as well, and that is the bug.

When it shows

#
  • Only for crossing markers: a nested marker is on top of the stack when it ends, so the close loop runs once. Longer crossing chains put more end strings out of order: abcdefghi with [0,5) as <a>, [2,7) as <b> and [4,9) as <c> gives <a>ab<b>cd<c>e</a></b></c><b><c>fg</b></c><c>hi</c>, three end strings in opening order at offset 5; with the fix <a>ab<b>cd<c>e</c></b></a><b><c>fg</c></b><c>hi</c> (executed, assertions on and off).
  • Only when end strings differ: the String constructor (:42-44) maps every marker to the same end string, and the same strings in another order are the same bytes. With a shared <m>/</m> the crossing case prints <m>foo <m>bar</m></m><m> baz</m>, well nested and identical with the fix (executed).

With inline highlight tags (four sweeps, 76,744 of the passages), HTML parsing (jsoup's HTML parser; no browser run) recovers the intended highlighting when every marker has its own tag name (0 differences in 19,215 passages); with one tag per query, where several markers share a tag name, part of one highlight is lost in 135 of 19,205 (em/mark) and 309 of 19,132 (mark/span) passages, and in none of 19,192 (b/i). Why it looks unintended

#
  • The public constructor takes an end string per highlight; the Passage javadoc says markers "can be overlapping or nested".
  • Closing and re-opening the inner highlight only serves nesting: if crossed tags were fine, <a>foo <b>bar</a> baz</b> would do.
  • The re-open loop and the slice-point order already put the inner highlight first; the close loop does not.
The full argument250 words
  • The API invites per-marker end strings. PassageFormatter(String, Function<OffsetRange, String> markerStart, Function<OffsetRange, String> markerEnd) (PassageFormatter.java:46-53), present since the class was added (150a8dacb59), with no restriction anywhere that end strings be equal.
  • Crossing markers are legal input. Passage.java:23-24: "The markers can be overlapping or nested, but they're always contained within the passage." PassageFormatter.java:128: "Multiple markers, possibly overlapping or nested."; :137: "Handle multiple markers, possibly overlapping or nested."
  • The class resolves overlaps. PassageFormatter.java:29-33: "Formats a collection of passages over a given string, cleaning up and resolving restrictions concerning overlaps, ..."; "Passages are demarcated with constructor-provided ellipsis and start/end marker sequences."
  • The design is nesting. The re-open loop runs bottom-up, the order that keeps nesting, and the slice-point comparator puts the inner marker's end first when two ends fall on one offset ("Shorter end slice points come first", :193). TestPassageSelector#checkOddOverlaps (TestPassageSelector.java:64-72) pins the close-and-re-open shape, foo >bar >baz<<> abc< xyz, with one shared end string, so it cannot see the order.
  • Stated intent. The class's author wrote on LUCENE-9439 (#10479, 2020-07-31) that hit ranges go to the "passage selector and a simple test-only formatter - these clean up potential overlaps and nesting problems (which is useful for HTML, for example)", with constant >/< markers. LUCENE-9461 (#10501) asks for several queries highlighting the same content "with different colors".
  • History. No issue, PR, test or CHANGES entry records the order as intended, and the loop has not changed since it was written.
The devil's-advocate check133 words

Strongest case (a cross-model refute review and an intended-behaviour devil's advocate): no sentence promises well-nested output; the marker strings are opaque; MatchHighlighter calls itself "An example highlighter" (MatchHighlighter.java:38); and every in-tree caller and test shares one end string, so the order cannot be observed in documented usage. A committer could call per-marker end strings over crossing markers unspecified.

Why it fails: the per-marker Function constructor exists to vary the strings and says nothing against it; crossing markers are explicitly allowed; the close-and-re-open step only makes sense for nesting, and its own re-open loop and comparator follow the nesting order; and the fix changes nothing for users with one shared end string. No documented valid-HTML or XML guarantee exists; the case rests on the constructor, the Passage javadoc and the close-and-re-open design.

Suggested fix

#

Recommended Close innermost first: reverse the close loop (validated)

Close the markers opened after the ending one from the top of the stack down: one changed for line in PassageFormatter.multipleMarkers. Same strings and count, new order only where markers cross (for side-effect-free marker functions); shared-end-string output is byte-identical. Validated on main: the repro passes, all 723 highlighter tests pass, lint is clean.

         case END:
           int markerIndex = markerStack.lastIndexOf(currentMarker);
-          for (int k = markerIndex; k < markerStack.size(); k++) {
+          // Close the markers opened after this one first (innermost first), then this one.
+          for (int k = markerStack.size() - 1; k >= markerIndex; k--) {
             b.append(markerEnd.apply(markerStack.get(k)));
           }
           markerStack.remove(markerIndex);

Close innermost first: reverse the close loop (validated) (recommended)

#

In the END branch of multipleMarkers (PassageFormatter.java:154), run the close loop from markerStack.size() - 1 down to markerIndex. The re-open loop stays bottom-up. The comment line is optional.

         case END:
           int markerIndex = markerStack.lastIndexOf(currentMarker);
-          for (int k = markerIndex; k < markerStack.size(); k++) {
+          // Close the markers opened after this one first (innermost first), then this one.
+          for (int k = markerStack.size() - 1; k >= markerIndex; k--) {
             b.append(markerEnd.apply(markerStack.get(k)));
           }
           markerStack.remove(markerIndex);

Trade-offs

  • None found for marker functions without side effects (every in-tree one, and every one in the probes). The same strings are appended the same number of times; only their order changes, and only where markers cross and end strings differ.
  • Output with one shared end string, the String constructor and every in-tree use, is byte-identical, so no in-tree caller or test sees a change.
  • The order in which markerEnd is called at a crossing changes too; only a stateful marker function could notice.
  • The regression test's exact expected string pins this option's close-and-re-open shape; removing crossings before formatting would need a different expected string.

Document the restriction instead (not validated)

#

State in the javadoc that crossing markers come out with crossed end strings unless all end strings are equal.

Trade-offs

  • No behaviour change, but per-marker end strings stay unusable for overlapping matches, the use case LUCENE-9461 names, and the close-and-re-open step keeps doing work that no longer achieves anything.

Remove crossings before formatting (not validated)

#

Merge crossing markers, as LUCENE-8446 (#9492) did for the unified highlighter's DefaultPassageFormatter, or emit non-overlapping fragments, the (AAA)(C)(BBB) shape Dawid Weiss sketched on LUCENE-8401 (#9448, 2018).

Trade-offs

  • A larger change: it would also change the output for constant markers, whose close-and-re-open shape TestPassageSelector#checkOddOverlaps pins, and merging into today's single-range markers loses which query matched the overlap unless the merged marker keeps both.

Downstream note

#

No use of the matchhighlight package was found in Solr, Elasticsearch or OpenSearch; an application that puts these passages into XML or XHTML gets output that a strict parser rejects.

How it was found

#

An exhaustive small-input check: every passage of a value up to 10 characters with 1-3 highlights, against a reference formatter. Text, coverage and balance never failed; nesting failed in 500,214 of 1,228,656 calls with one tag per highlight (one of three label schemes), and never in a copy with the close loop reversed. Then cut to a public-API JUnit.

The method in full251 words
  • Method. Bounded-exhaustive translation validation of the real formatter on the stock jars: every passage of a value of up to 10 characters and every ordered list of 1-3 markers inside it (overlapping, nested, duplicate), under three label schemes (constant strings, one label per marker, one label per query). Five relations were checked against an exact reference: F1 stripping the markers gives the passage text, F2 every end string closes the most recently opened still-open marker, F3 the open labels at each character equal the markers covering it, F4 (soft) no empty element, F5 nothing left open.
  • Result. At length up to 10, 3,685,968 calls (three label schemes, 1,228,656 each): F1, F3 and F5 never failed; F2 failed 500,214 times (one label per marker) and 369,226 times (one label per query). A copy of the formatter with only the close loop reversed had 0 F2 failures in 1,671,813 calls (length up to 9), which shows both that the check can pass and that the one-line fix is enough for nesting. An end-to-end tier (1,641 documents x 21 queries through MatchHighlighter) showed the same nesting failure in 168,206 and 159,602 passages (position gap 0 and 1), over 5,684,424 highlighted document results each.
  • Origin. The close order was first suspected by reading the code while writing the reference; the exhaustive check then witnessed it. The hunt classes this as semi-formal.
  • Reduction. The hunt reduced it to a deterministic public-API JUnit (2026-10-26); the minimal-repro step cut that to the one-method test shown here (2026-10-29).

LFV-609, snapshot of 2026-11-03

Registry title
matchhighlight PassageFormatter closes crossing markers in opening order instead of innermost first, so per-marker end strings come out mis-nested (e.g. '<a>one <b>two</a></b><b> three</b>' instead of '<a>one <b>two</b></a><b> three</b>')
Area
highlighter / matchhighlight: PassageFormatter multi-marker formatting (crossing markers with per-marker end strings; also end to end through MatchHighlighter, FieldValueHighlighters.highlighted and MatchHighlighter.QueryOffsetRange)
Priority
Low, rank 932: Matchhighlight's PassageFormatter mis-nests crossing markers only when per-marker end strings differ and two matches cross in this little-used package, so it is cosmetic output only.
Impact class
minor
Impact note
Hits applications that use the matchhighlight PassageFormatter through its public PassageFormatter(String, Function, Function) constructor with end strings that differ per marker (for example one tag per query via MatchHighlighter.QueryOffsetRange, the multi-query 'different colors' use case named in LUCENE-9461) whenever two crossing (overlapping, not nested) markers fall in one passage, for example the phrase queries 'one two' and 'two three' over 'one two three'; default codec, writer, analyzer and searcher suffice, no scale is needed, and -ea and -da behave the same; the text, the covered characters and the start/end balance stay correct and only the order of end strings at one offset is wrong, so strict XML/XHTML parsers reject the passage, while HTML parsing recovers the intended highlighting when every marker has its own tag name but can drop part of one highlight when two crossing markers share a tag name (135 and 309 of about 19,000 random passages in two such setups, HTML-standard parser, no browser run); with constant end strings (the String constructor, every in-tree caller and upstream test, including TestMatchHighlighter's per-query "<span class='...'>" example with a shared '</span>') the output is byte-identical to the correct one, and no use of the package was found in Solr, Elasticsearch or OpenSearch.
Summary
You format the passage 'one two three' with two crossing markers, [0,7) written as <a>...</a> and [4,13) as <b>...</b>, using PassageFormatter's Function constructor, or you highlight the crossing phrase queries 'one two' and 'two three' with MatchHighlighter.highlight(topDocs, q1, q2) and one tag per query. You expect well-nested output, '<a>one <b>two</b></a><b> three</b>', because when a marker ends the formatter closes and re-opens the markers opened after it precisely to resolve the overlap into nested markup (Passage javadoc: markers 'can be overlapping or nested'). Instead it closes those markers in opening order rather than innermost first and returns '<a>one <b>two</a></b><b> three</b>' (end to end '<q1>one <q2>two</q1></q2><q2> three</q2>'), which an XML parser rejects.
