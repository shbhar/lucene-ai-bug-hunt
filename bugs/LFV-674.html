Geo3dDistanceCalculator.within returns the opposite answer: a point 1 degree away is not within 10 degrees

With the Geo3d spatial context, ctx.getDistCalc().within(from, x, y, limit) answers backwards: 1 degree away is "not within 10 degrees", 50 degrees away is "within". Lucene never calls within() itself; only application code that does (directly or through a hand-built CircleImpl) is hit, in every release since 7.1.0.

The finding in 30 seconds

#

A spatial context bundles a shape factory and a distance calculator. The Geo3d context's calculator measures distances correctly, but its yes/no question "is this point within d of that one?" compares the two numbers the wrong way round.

Background in 3 steps

#
  1. lucene/spatial-extras uses spatial4j's SpatialContext: a shape factory plus a DistanceCalculator. The usual context is SpatialContext.GEO; Geo3dSpatialContextFactory is an opt-in, experimental alternative backed by Lucene's spatial3d geometry.
  2. A DistanceCalculator has distance(from, toX, toY), in degrees, and within(from, toX, toY, distance), documented as "Returns true if the distance between from and to is <= distance".
  3. new Geo3dSpatialContextFactory().newSpatialContext() installs Geo3dDistanceCalculator as ctx.getDistCalc() unless you configure another calculator.

The finding, step by step

#
  1. Create the Geo3d spatial context: new Geo3dSpatialContextFactory().newSpatialContext(). Its distance calculator, ctx.getDistCalc(), is a Geo3dDistanceCalculator, and distance() from (0, 0) to (1, 0) is 1.0 degree.
  2. Ask within(origin, 1, 0, 10): is (1, 0) within 10 degrees of (0, 0)? The spatial4j DistanceCalculator contract says within is true when the distance is <= the limit, so you expect true.
  3. You get false, with no error. within(origin, 50, 0, 10) gives true although that point is 50 degrees away, and a point is not even within distance 0 of itself.
  4. The method body is return (distance < distance(from, toX, toY));. The parameter distance is the limit, so it tests limit < actual distance, the exact opposite of actual distance <= limit, for every finite distance and non-NaN limit.
  5. Lucene's indexing, queries and distance sorts make 0 within() calls (measured over eight spatial strategies), so this bug does not change search results built from the context's own shapes (on RPT over PackedQuadPrefixTree those shapes over-match through a separate bug, LFV-673). Only code that calls within() itself, or builds spatial4j's CircleImpl by hand with this context, gets wrong answers.

Who is affected

#

Only applications that opt into the experimental Geo3d spatial context and call ctx.getDistCalc().within(...) themselves; for them every call with a non-NaN distance and limit is wrong, silently. Lucene's own indexing, queries and distance sorts never call it. The one search-result path found is a hand-built CircleImpl queried on RPT over the non-default PackedQuadPrefixTree: 419 hits where 7 are inside.

Mechanism, terms and numbers694 words

Geo3dSpatialContextFactory.newSpatialContext() installs a Geo3dDistanceCalculator as the context's distance calculator. Its within(from, toX, toY, distance) is return (distance < distance(from, toX, toY));: the parameter distance is the limit, so the line returns "limit < actual distance", the exact negation of spatial4j's documented "true if the distance between from and to is <= distance". Every answer with a finite distance and a non-NaN limit is inverted: from (0, 0), the point (1, 0) at 1.0 degree is "not within 10", the point (50, 0) at about 50 degrees is "within 10", and within(p, p, 0) is false.

The reach is narrow. No Lucene code calls DistanceCalculator.within: a counting calculator recorded 0 calls while indexing 2,000 points into eight strategies and running 63 queries and 7 distance sorts, so this bug does not change search results with shapes from the Geo3d shape factory, and no index data depends on it. (Those factory shapes do over-match on RPT over PackedQuadPrefixTree, 419 hits where 7 are inside, but through the separate Geo3dShape.relate bug LFV-673, which this fix does not change.) Applications that call ctx.getDistCalc().within(...) themselves get the opposite answer whenever neither the distance nor the limit is NaN. The one search-result path found needs application code that hand-builds spatial4j's CircleImpl with the Geo3d context: as a query on RPT over the non-default PackedQuadPrefixTree, such a circle matched 419 documents where 7 are inside.

The line has been there since the class was written (LUCENE-7951, 2017-09-20, first released in 7.1.0). Affected: 7.1.0 to 10.6.0 and main; not fixed upstream. Fix: return distance(from, toX, toY) <= distance; (one line).

The mechanism (main 645d4fe14a20)

#
  1. The Geo3d context installs this calculator by default. The factory constructor sets the Geo3d shape factory and binary codec (Geo3dSpatialContextFactory.java:39-42). newSpatialContext() defaults the planet model to PlanetModel.SPHERE (:33, :46-48) and, when no calculator is configured, sets distCalc = new Geo3dDistanceCalculator(planetModel) (:49-51). The configuration path (SpatialContextFactory.makeSpatialContext with spatialContextFactory set to this class) ends in the same method; initCalculator also installs it for distCalculator=geo3d (:78-88).
  2. distance() is right. distance(Point from, double toX, double toY) returns the planet model's surface distance in degrees (Geo3dDistanceCalculator.java:54-72): 1.0 for (0, 0) to (1, 0) and 49.99999999999999 for (0, 0) to (50, 0). In an independent check its distances agreed with spatial4j's geodesic calculator to about 1e-14 degrees.
  3. within() compares the wrong way round (:74-77):
@Override
public boolean within(Point from, double toX, double toY, double distance) {
  return (distance < distance(from, toX, toY));
}

The parameter distance is the limit and distance(from, toX, toY) the method of step 2, so the line returns "limit < actual distance". When neither the distance nor the limit is NaN, that is the logical complement of "actual distance <= limit", the boundary actual == limit included. When either is NaN, both the stock line and the fix return false. The released bytecode (7.1.0 and main jars) is the same comparison; spatial4j's AbstractDistanceCalculator.within returns distance(from, toX, toY) <= distance.

  1. Nothing in Lucene calls it. The in-tree main-source users of ctx.getDistCalc() call only distance() (SpatialStrategy.java:135-140, SpatialArgs.java:69, DistanceToShapeValueSource.java:76, ShapeFieldCacheDistanceValueSource.java:72-74, DistanceValueSource.java:75); the tests also call pointOnBearing, and nothing under lucene/, test or main, calls within on a calculator. In spatial4j 0.8 the only caller is CircleImpl.contains(double, double), used by CircleImpl.relate; the Geo3d shape factory's circle(...) returns a Geo3dCircleShape (Geo3dShapeFactory.java:176-196, :200-202), never a CircleImpl.

Changing only that line to return distance(from, toX, toY) <= distance; makes the repro pass on main, 10.5.2 and 7.1.0, so the comparison is the whole cause.

Exposure and likelihood334 words
  • Silent, every call. For a direct caller every answer with a finite distance and a non-NaN limit is the opposite one, with no exception.
  • Who is exposed. Applications that chose the opt-in Geo3d spatial context (Geo3dSpatialContextFactory, @lucene.experimental; the usual spatial4j context is SpatialContext.GEO) and call ctx.getDistCalc().within(...). Solr exposes the Geo3d context through its spatialContextFactory="Geo3D" alias (SOLR-11382). A read-only GitHub code search found no call of getDistCalc().within other than spatial4j's own CircleImpl and copies of it.
  • This bug does not change Lucene's own search results for shapes built by the Geo3d shape factory. A counting subclass installed as the context's calculator recorded 0 within() calls while indexing 2,000 points into eight strategies (RPT over Geohash, Quad, PackedQuad and S2, PointVector, BBox, SerializedDV, Composite), and across 63 queries and 7 distance sorts. No index data depends on within(), so nothing needs reindexing after the fix.
  • Not this bug: factory shapes on PackedQuad. In the same probe, factory circles on RPT over PackedQuadPrefixTree do over-match: circle(40, 40, 5) matched 419 documents where 7 are inside, and circle(-100, -30, 20) 428 where 49 are, with 0 within() calls. This fix leaves both numbers unchanged; only the fix of the sibling bug LFV-673 (Geo3dShape.relate with a plain rectangle) brings them to 7 and 51. The two bugs are separate.
  • The one search-result path found (uncommon). Application code that bypasses the shape factory with new CircleImpl(center, radius, geo3dCtx) gets inverted contains/relate answers. As an Intersects query on RPT over PackedQuadPrefixTree, CircleImpl(40, 40, 5) matched 419 documents where 7 are inside (7 with the fix), and CircleImpl(-100, -30, 20) matched 428 where 49 are inside (52 with the fix, the normal grid approximation): every live document of one quarter-world cell. RPT over Geohash, Quad and S2, SerializedDV and Composite reject a CircleImpl with a clean exception, and BBox with an UnsupportedOperationException, with or without the fix; PointVector filters by distance() and is exact.
  • Likelihood: rare. No report since 7.1.0 (2017).

Why it looks unintended

#
  • spatial4j documents within as "true if the distance between from and to is <= distance", and its own base class does exactly that.
  • The Lucene class calls itself the "Geo3d implementation of DistanceCalculator", yet says a point is not within distance 0 of itself.
  • Nothing documents or accepts the inversion; the methods the class does not support throw instead.
The full argument162 words
  • The contract is explicit and has not changed. spatial4j DistanceCalculator.within: "Returns true if the distance between from and to is &lt;= distance." (DistanceCalculator.java:29-30 in spatial4j 0.8). In 0.6 and 0.7, which 7.1.0 to 8.11.4 shipped with, AbstractDistanceCalculator.within has the same bytecode (checked in the binary jars; their javadoc text was not checked). AbstractDistanceCalculator.within is return distance(from, toX, toY) <= distance; (:23-25).
  • The Lucene class claims that contract. Its javadoc is "Geo3d implementation of {@link DistanceCalculator}" (Geo3dDistanceCalculator.java:30-34) and gives within no other meaning. The 7.1.0 CHANGES entry for LUCENE-7951 says spatial-extras now implements "Spatial4j abstractions: SpatialContextFactory, ShapeFactory, BinaryCodec, DistanceCalculator" (lucene/CHANGES.txt:7883-7885).
  • The boundary case is wrong too. within(p, p, 0) is false at distance 0.
  • Nothing documents or accepts it. No test, CHANGES or MIGRATE entry mentions within on this class. The introducing review (#9000 and lucene-solr#246) discussed other methods. The methods the class does not support throw UnsupportedOperationException (:104-117); within returns a value.
The devil's-advocate check168 words

The strongest case for "intended" (the intended-behaviour check and the cross-model reviews): both classes are @lucene.experimental ("This API is experimental and might change in incompatible ways in the next release"); the package says it holds "Spatial4j stuff that ideally belongs in Spatial4j (isn't related to Lucene)"; the calculator is partly unimplemented; the contributor wrote on #9000 that "the DistanceCalculator needs to be reviewed"; nothing in Lucene calls within(); and nobody has complained in nine years.

Why it fails: experimental warns that the API may change, not that a method may return the opposite of its interface's documented result; the code ships in the regular spatial-extras module and CHANGES advertises it as a DistanceCalculator; "needs review" shows the calculator was unreviewed, not that the inversion was meant; no caller and no complaints limit the impact, which is why the class is minor. Verdict: not intended, a defect (the independent reproduction, the intended-behaviour check, the refute-lens and intended-lens cross-model reviews and the adjudication; the adjudication with high confidence).

Suggested fix

#

Recommended A: compare actual distance <= limit

Compare the right way round: return distance(from, toX, toY) <= distance;, exactly what spatial4j's base class does (one line). The repro passes with assertions on and off, all 118 lucene/spatial-extras tests pass, and so do the module's lint checks. A NaN distance still gives false.

  @Override
  public boolean within(Point from, double toX, double toY, double distance) {
-    return (distance < distance(from, toX, toY));
+    return distance(from, toX, toY) <= distance;
  }
All options and trade-offs4 options · 422 words

One option was built and validated through gradle on 645d4fe14a20; three alternatives are listed, not built.

A: compare actual distance <= limit (validated by the checks) (recommended)

#

1 line in Geo3dDistanceCalculator.java, the same body as spatial4j's AbstractDistanceCalculator.within.

  @Override
  public boolean within(Point from, double toX, double toY, double distance) {
-    return (distance < distance(from, toX, toY));
+    return distance(from, toX, toY) <= distance;
  }

Trade-offs

None known. No Lucene code calls within(), so nothing in Lucene changes behaviour. An application that worked around the inversion by negating the result would have to drop its negation; none is known.

Shadowed into the 7.1.0 and 10.5.2 sources, it turns the repro from fail to pass.

B: A, plus a clearer parameter name (not built)

#

Name the parameter maxDistance (return distance(from, toX, toY) <= maxDistance;). It removes the shadowing of the method name distance that makes the inverted line easy to misread; Java allows a different parameter name in an override.

Trade-offs

Cosmetic only.

C: extend spatial4j's AbstractDistanceCalculator and drop the override (not built)

#

AbstractDistanceCalculator already implements within with <=.

Trade-offs

Changes the superclass of a public, if experimental, class to fix one line; A is smaller.

D: make within() throw, or deprecate it, instead of fixing it (not built)

#

For an experimental, partly unimplemented class a maintainer may prefer to make within throw UnsupportedOperationException, as area(...) and calcBoxByDistFromPt_yHorizAxisDEG already do (Geo3dDistanceCalculator.java:104-117), or to deprecate it.

Trade-offs

Throwing turns the silent wrong answer into a loud failure, but also makes a hand-built CircleImpl with this context throw from contains and relate (spatial4j's CircleImpl.contains calls within) and breaks any caller that uses within today; deprecating alone leaves the wrong answers in place. A is just as small and keeps the interface contract.

Downstream note

#

Lucene itself never calls within(); application code that calls it directly, for example to decide whether a point lies within some radius, gets every answer inverted, while other filter clauses and deletions in its queries are still honoured.

How it was found

#

A randomized consistency check of the spatial4j bridge classes asked, for random point pairs on the sphere and the WGS84 ellipsoid, whether within(from, to, limit) agrees with distance(from, to) <= limit, with the limit just above or just below the distance. All 10,000 checks failed; with the one-line fix none did. No model checker or solver was involved.

The method in full121 words

Method: non-formal (a hunt unit, a differential check of the spatial4j-to-spatial3d bridge; the finder tagged it semi-formal, the registry records it as non-formal).

  • The harness checked self-consistency properties of the Geo3d bridge. Family G4a: within(from, to, lim) must equal distance(from, to) <= lim, with lim just above or just below the measured distance, on SPHERE and WGS84 (seed 5EED220): 5,000 of 5,000 failures per model on stock main, 0 with the fix. The sibling family G4b, distance(from, pointOnBearing(from, d, b)) equals d, was clean.
  • The finder, an AI tool, then wrote a public-API JUnit on the stock jar. Independent reproducers wrote their own tests from the claim alone; the one-test repro was cut from the finder's test on 2026-10-29.

You create a spatial context with Geo3dSpatialContextFactory and ask its distance calculator whether the point (1, 0) is within 10 degrees of (0, 0), with ctx.getDistCalc().within(from, 1, 0, 10), and expect true: distance() returns 1.0 degree, and the spatial4j DistanceCalculator contract says within() is true when the distance is <= the limit. Instead it returns false, and within(from, 50, 0, 10) returns true although the distance is 50 degrees. The method body is 'return (distance < distance(from, toX, toY));', the exact negation of the contract, so every answer with a finite distance is inverted, including within(p, p, 0).
