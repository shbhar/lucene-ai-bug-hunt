Concurrent doc-values updates can make a merge throw NullPointerException and close the IndexWriter

A merge that starts while another thread applies a doc-values update of a field the merging segments lack, when the segment holds a pending update of another doc-values field, throws NullPointerException and closes the IndexWriter, losing every uncommitted change. Rare, but every tested release since 7.0.0 has it.

The bug in 30 seconds

#

Lucene applies a doc-values update in two steps: apply it to each segment, then mark it finished. A merge that starts between the two steps can see a field that has a type but no values.

  1. Commit segments _0 = {a} and _1 = {b}, both with a NUMERIC doc-values field num. Thread 1 sets a.num = 7, adds document c, the only one with a BINARY doc-values field tag, and flushes: c lands in segment _2.
  2. Thread 2 calls updateBinaryDocValue(a, "tag", "a-tag"), adds d and flushes; it applies its update to _0 itself. In the moment before it marks the update finished, thread 1 merges _0 and _1.
  3. You expect the merge to succeed: 4 documents, a.num = 7, a.tag = a-tag. Without the overlap you get exactly that; the controls with the second update on num, or with no first update, also merge cleanly, each with the values its own updates set.
  4. Instead the merge first writes _0's finished update (num = 7) but also lists tag as a BINARY field of _0, with no values behind it. No merging segment has data for tag, and DocIDMerger throws NullPointerException: ... "this.current" is null.
  5. The writer treats it as tragic and closes (isOpen() is false): documents c and d and both updates are lost. The last commit, 2 documents, is intact.

Who is affected

#

Applications that update two different doc-values fields on one segment (soft deletes count as one) while merges run on another thread, for example a background merge. Default codec; default configuration by code reading. Rare, 0.05-0.2% of runs in a race built to collide; but when it hits, the writer closes and every change since the last commit is lost.

Mechanism, terms and numbers840 words

Lucene applies a doc-values update packet in two steps: it applies the packet to each segment, then marks it finished. A merge that starts between the two steps waits only for older packets. Before merging it writes the segment's finished updates, and in that step one loop of ReadersAndUpdates.writeFieldUpdates also adds the unfinished update's field to the segment's field list, typed BINARY or NUMERIC but with no values (doc-values generation -1). If no segment in the merge has that field, the merge builds a DocIDMerger over an empty list and throws NullPointerException; IndexWriter treats it as tragic and closes, and every change since the last commit is lost. It needs updates of two different doc-values fields on the same segment (a soft delete counts as one), one of them new to every merging segment, and a merge that starts inside the window. It is rare (0.05-0.2% of runs in a two-thread race built to collide) but present in every release tested from 7.0.0 to 10.5.2 (18) and on main; a 12-line fix passes all of :lucene:core:test.

Terms

#
  • Doc-values update: updateNumericDocValue, updateBinaryDocValue, updateDocValues, or a soft delete (softUpdateDocument / softUpdateDocuments, or updateDocValues on the soft-deletes field). The writer buffers it and later freezes it into a packet with a generation number, delGen.
  • Applying a packet: since 7.0.0 the thread that flushes resolves the packet itself, without holding the writer lock, adds the updates to each segment's in-memory ReadersAndUpdates, and only then marks the packet finished. Updates of finished packets are later written to disk as a new doc-values generation of the segment, together with a new generation of its field list (.fnm).
  • Merge start: before merging, mergeInit waits for the packets the merging segments depend on, then writes their finished updates to disk, so the merged segment sees them.

The bug, in the repro

#
  1. Thread 2 applies the packet with tag to _0 (FrozenBufferedUpdates.java:355, called from IndexWriter.java:6592 without the writer lock). It marks it finished only later (IndexWriter.java:6640).
  2. In between, thread 1's merge of _0 and _1 starts. waitApplyForMerge waits only for packets with delGen <= the merging segments' highest delete generation (BufferedUpdatesStream.java:188); thread 2's packet is newer, so the merge does not wait.
  3. The merge writes _0's pending updates up to the completed generation (IndexWriter.java:5310, ReaderPool.java:272), which covers thread 1's num update but not thread 2's tag update.
  4. In ReadersAndUpdates.writeFieldUpdates, the "anything to write" check (:872) and handleDVUpdates (:315, "nothing to apply yet" at :322) both skip updates above that generation. The loop "create new fields with the right DV type" (:914-930) does not: it adds tag to _0's field list through constructFieldInfo (:925), typed BINARY with doc-values generation -1 (FieldInfos.java:678). The new field list is written (:944).
  5. A field with generation -1 and no overlay (the overlay branch, SegmentDocValuesProducer.java:77-81, does not apply) is read from the segment's original doc-values file (:83-86), which never had tag, so getBinary returns null (PerFieldDocValuesFormat.java:322-325), although DocValuesProducer promises "The return value is never {@code null}".
  6. The merge drops the null producer (DocValuesConsumer.java:336); _1 has no tag either, so DocIDMerger.of gets an empty list, its current is null (DocIDMerger.java:116), and next() throws (:123). handleMergeException swallows nothing but a MergeAbortedException of a non-external merge (IndexWriter.java:5030-5058), so the NPE reaches the outer catch of IndexWriter.merge, which calls tragicEvent(t, "merge") (:5109-5113), and the writer closes.

With a soft delete as the second update, the soft-deletes field takes the place of tag and the merge fails in the numeric path (DocValuesConsumer.java:218, :234). An NRT reader opened inside the window with DirectoryReader.open(writer, false, false) shows _0 with tag typed BINARY, generation -1 and getBinaryDocValues("tag") == null, and CheckIndex.testDocValues on it throws NullPointerException ("it1" is null). Ordinary reads on that reader: getBinaryDocValues("tag") on _0 returns null and MultiDocValues.getBinaryValues returns only c's value, exactly what the same reader shows with the fix, while the DocValues.getBinary helper throws a misleading IllegalStateException: unexpected docvalues type BINARY for field 'tag' (expected=BINARY) (DocValues.java:214-230,262-268). This symptom needs only tag to be new to _0: with tag also in _1, the merge succeeds, but the NRT reader in the window still fails CheckIndex. With the fix the reader passes CheckIndex.

Found by reading and not run: under doc-values RAM pressure the applying thread itself calls writeSomeDocValuesUpdates() (IndexWriter.java:6600) before it marks its packet finished (:6640); that calls writeFieldUpdates with the completed generation (:854-858), so the same bad field list can be written without any merge (by reading, until the next write after the packet is finished). An NRT reader opened in the window and passed to another writer's addIndexes(CodecReader...) may reach the same null producer.

All line numbers are Lucene main ea57360912ed, lucene/core/src/java/org/apache/lucene/.

Exposure and likelihood479 words
  • Who is hit. Applications that update two or more different doc-values fields (updateNumericDocValue, updateBinaryDocValue, updateDocValues, or soft deletes plus one other updated field) where one field is missing from some segments, while merges run on another thread. The merge can be a background ConcurrentMergeScheduler merge: a no-hook race with CMS hit 39 merge NPEs in 20,000 runs. The stress harness that found it used ordinary operations (adds, updates, deletes, doc-values and soft updates, flush, commit, forceMerge(1), CMS or the serial scheduler).
  • Default or opt-in. The default codec is enough: the JUnit fails under Lucene104, the default codec, and under the randomized test codecs. The default IndexWriterConfig is very likely enough too, but that is from the code, not from a run: every executed repro and race sets a one-shot merge policy, disables doc-count auto-flush and uses a 256 MB RAM buffer (all but the CMS race also use SerialMergeScheduler), only to pin which segments merge, on which thread, and when flushes and doc-values writes happen; none of these settings appears in the code path. The stress harness that found it used a random configuration. Doc-values updates are a regular public API; soft deletes are opt-in (setSoftDeletesField). A custom codec whose producer returns an empty instance instead of null might avoid the NPE, but the segment would still list the field with no values (not run).
  • Not hit. Applications that update only one doc-values field, for example soft deletes alone (that field's finished update gives it a real generation; the study's control with both updates on tag passes), and merges where the updated segment already has the late field (control testControlLateUpdateOfExistingField) or another merging segment has it (the fact check's probe C: the merge succeeds, but an NRT reader opened in the window still fails CheckIndex).
  • Consequence. The writer closes itself; later calls throw AlreadyClosedException; every document and update since the last commit is lost, including flushed but uncommitted segments, so applications without their own transaction log lose acknowledged writes. The last commit stays intact (CheckIndex clean after the tragedy). The merge failure is loud and no committed data is corrupted; an NRT reader opened inside the window shows the broken field (see What happens).
  • Scale and frequency. Any index size (the repro has 4 documents). The window is the time one thread spends between applying a packet and marking it finished. The original stress hunt hit it with 1 seed in 15,000 runs; that seed repeated 3,000 times hit it 18-23 times on main and 64-67 times on 10.5.2, 9.12.3 and 8.11.4; two-thread races with a random 0-100 microsecond merge delay hit it 20 (binary update), 9 (soft delete) and 39 (CMS) times per 20,000 runs on main, and 53 per 20,000 at the introducing commit. These rates come from scenarios built to collide, not from production incidence.

Why it is a bug, not intended

#
  • IndexWriter is documented as "completely thread safe"; nothing documents that legal concurrent calls can fail a merge and close it.
  • DocValuesProducer.getBinary: "The return value is never {@code null}"; here it returns null for a field the segment lists as BINARY.
  • The method's two other loops skip not-yet-applicable updates ("nothing to apply yet"); only the field-creation loop does not.
The full argument372 words
  • Thread safety. IndexWriter javadoc: "IndexWriter instances are completely thread safe, meaning multiple threads can call any of its methods, concurrently" (IndexWriter.java:167-168), and the writer closes itself "if you hit an Error, or disaster strikes during a checkpoint" (:162-165). Closing on a failed merge is deliberate too (:5109-5113; getTragicException gives "disk full while flushing a new segment" as an example, :6108-6111), but nothing documents that legal concurrent calls can make a merge fail: this NPE comes from a broken internal invariant, not from the environment.
  • Every call is legal. updateBinaryDocValue: "You can only update fields that already exist in the index, not add new fields through this method. You can only update fields that were indexed only with doc values" (IndexWriter.java:1983-1984); tag exists in _2, doc values only. A field missing from a segment is a handled case ("the field is not present in this segment so we clone the global field (which is guaranteed to exist)", ReadersAndUpdates.java:922-923), and the no-window control passes on that path.
  • The producer contract. DocValuesProducer.java:45,52: "The return value is never {@code null}". In LUCENE-10357 (#11393) jpountz stated the rule: "On doc values and norms, we require that codec APIs return non-null empty instances on fields that have the feature turned on on their FieldInfo". CheckIndex relies on it (CheckIndex.java:3792-3795) and fails on such a reader.
  • The method's own intent. "nothing to apply yet" (ReadersAndUpdates.java:322), "not yet applied" (:973) and the filtered "any" check (:872) all skip updates above the completed generation.
  • History. Before LUCENE-7868 (6.6.x) packets were applied under the writer lock and the loop only saw resolved updates. LUCENE-7868 moved the work off the lock and filtered two of the three loops; LUCENE-7888 (#8939, fixed in 7.0.0) treated a similar merge-versus-update race from the same change (lost updates when a merge completes) as a bug. No javadoc, CHANGES entry or test says a merge may fail this way.
  • Controls. The same window with the late update on a field _0 already has, with no earlier update, or with the packet finished before the merge: each merges cleanly and ends with the values its own updates set.
The devil's-advocate check231 words

The strongest case for "not a bug": the deterministic test parks a thread inside an InfoStream callback (InfoStream is @lucene.internal) and uses expert calls (flushNextBuffer, a one-shot merge policy), so the interleaving looks artificial. The cross-model refute review raised exactly this and rejected it itself, rating the intended-behaviour argument "weak".

Why it fails: without any hook the race still happens: 20, 9 and 39 merge NPEs per 20,000 runs in the study's no-hook races; 53 per 20,000 at the introducing commit and 47 on 7.0.0, against 0 on 6.6.6 and the parent; the reviewer's own hook-free test hit the NPE in 5 of 6 runs of 20,000 attempts (first hit at attempt 244 to 3,282) and passed all 20,000 attempts in each of 5 runs with the fix. The bug was first found by a hook-free stress harness. The hook only widens a window that normal scheduling hits.

The NRT/CheckIndex symptom alone is easier to argue as intended: the reader is opened with applyAllDeletes=false while thread 2's call has not returned, and LeafReader.getBinaryDocValues may return null "if no binary doc values were indexed for this field" (LeafReader.java:176-180). But the segment's field list says BINARY while its producer returns null, which DocValuesProducer forbids, and the DocValues.getBinary helper then throws a misleading IllegalStateException; the merge NPE does not depend on that reader. Verdict: a defect.

Suggested fix

#

Recommended Skip fields with no applicable update in the field-creation loop (validated)

In the field-creation loop of ReadersAndUpdates.writeFieldUpdates, skip a field when none of its pending updates is applicable yet (delGen <= maxDelGen), as the method's two other loops already do (+12 lines). The test passes (60 of 60 with tests.iters=10), and so do all 8,871 tests of :lucene:core:test and :lucene:core:check -x test.

for (List<DocValuesFieldUpdates> updates : pendingDVUpdates.values()) {
  DocValuesFieldUpdates update = updates.get(0);
  boolean applicable = false;
  for (DocValuesFieldUpdates u : updates) {
    if (u.delGen <= maxDelGen) {
      applicable = true;
      break;
    }
  }
  if (applicable == false) {
    continue; // handleDVUpdates skips it too: no DV type without a dvGen
  }
  ... // unchanged: existing field, or constructFieldInfo(...)

Compute the applicable updates once per field

#

Refactor writeFieldUpdates so the "any" check, the field-creation loop and handleDVUpdates share one per-field list of updates with delGen <= maxDelGen.

Trade-offs

Same behaviour as the recommended fix and removes the duplicated filter that let the three loops drift apart; a larger diff. Not run.

Hardening only: let SequentialDocIDMerger handle an empty list

Return null from next() when there is no sub.

Trade-offs

Stops this NPE, but the segment still lists a typed field whose producer returns null: CheckIndex on an NRT reader opened in the window still fails and the DocValuesProducer contract stays broken. Could accompany the fix, not replace it. Not run.

Trade-offs

How it was found

#

A plain multi-threaded stress test with a contract oracle (reader linearizability, sequence numbers, no unexpected exception) hit it with 1 seed in 15,000 runs. A systematic concurrency tester (Fray) ran the same scenario about 4,079 times without a hit. An independent verifier then wrote a deterministic test, a hook-free race and the fix.

The method in full193 words

Method: non-formal stress testing (the 2026-10-22 study, experiment "concurrency-tools", main 7cecf79523).

  • The experiment ran concurrency tools on Lucene (Fray, Lincheck, JCStress, Java PathFinder) next to a custom NRT harness: 2-3 writer threads doing adds, updates, deletes, doc-values and soft updates, addIndexes, flush, commit and forceMerge(1), 1-2 reader threads, and a random IndexWriterConfig. Its oracle used API contracts only: linearizability of reader observations, the sequence-number contract, and no unexpected exception.
  • With two other bugs masked, 15,000 plain stress runs hit one seed (101651) whose writer closed with this NPE. Repeated 3,000 times, that seed hit it 18-23 times on main and 64-67 times on 10.5.2, 9.12.3 and 8.11.4. Fray ran the same scenario about 4,079 times (POS, PCT and SURW schedulers) without a hit.
  • An independent AI verifier wrote its own deterministic JUnit (an InfoStream hold), a no-hook race, version-portable programs (7.0.0 to main) and the one-class fix, and showed with a double dissociation that it is a different bug from LFV-001. The 2026-10-26 hunt derived the 6-test JUnit, ran a cross-model refute review, bisected the introducing commit and searched for prior reports; this doc validated the fix through gradle.

History

#

Introduced in 7.0.0 by LUCENE-7868 (58105a203a19, 2017-06-21), which moved doc-values update application off the writer lock. Every release run from 7.0.0 to 10.5.2 (18) and main fails; 6.6.0, 6.6.6 and the commit's parent pass.

Versions tested7 rows

Introduced by LUCENE-7868, commit 58105a203a19 ("use multiple threads to concurrently resolve deletes and DV udpates", by mikemccand, 2017-06-21; a JIRA patch, migrated issue #8919). Before it, packets were applied under the writer lock and a merge applied all pending packets before it started, so it could never meet a half-applied packet. The commit's new field-creation loop already lacked the generation filter that its other two loops have. Later rewrites of the loop (LUCENE-9300 in 2020, LUCENE-9334 in 2021) kept the gap. The soft-delete trigger exists from 7.4.0, the first release with soft deletes. Releases older than 6.6.0 were not run.

Bug record

LFV-013, snapshot of 2026-10-30

Registry title
Concurrent doc-values updates can make a merge throw NullPointerException and close the writer
Area
index / doc-values updates
Priority
Medium, rank 99: A default-config race between doc-values updates on a field new to a segment and a merge throws NPE and tragically closes the writer, losing uncommitted docs, but it is loud and very rare (1 seed in 15,000 stress runs) and soft-delete-only users such as Elasticsearch and OpenSearch are unaffected.
Impact class
crash
Impact note
Default configuration; a race between doc-values updates on a field new to a segment and a concurrent merge of that segment (found by one seed, 101651, in a 15,000-run stress hunt); released since 7.0.0.
Summary
You update a doc-values field that is new to a segment while that segment is being merged. You expect the merge to finish. Instead writeFieldUpdates records the not-yet-applicable field as NUMERIC with dvGen=-1, the merge throws NullPointerException in DocIDMerger, and the IndexWriter closes tragically.
Introduced
LUCENE-7868 (58105a203a19) (2017-06-21)
First affected version
7.0.0
Affected versions
every release run from 7.0.0 to 10.5.2, and main [exec]
Status
documented (brief, checks and a per-bug doc exist)
Verification
Confirmed in the earlier formal verification study by independent AI checks and a rerun on Lucene main; also a cross-model review that agreed; not yet triaged by a person.
Found by
non-formal baseline: stress
Upstream and prior reports
none found (study searches 2026-10-22); the open merge-NPE reports #11637 (LUCENE-10601) and #9834 (LUCENE-8790) have different frames and mechanisms (verifier)
