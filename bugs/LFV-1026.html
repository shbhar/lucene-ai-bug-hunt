The BulkScorer#score javadoc example calls Scorer.advance() and nextDoc(), which Scorer has not had since 5.5.0

The only code example in the BulkScorer#score javadoc calls scorer.advance(min) and scorer.nextDoc(), but since Lucene 5.5.0 a Scorer hands out its iterator through scorer.iterator(). Copied into code, the example fails with two compile errors on every release from 5.5.0 to 10.6.0 and on main; only the javadoc is wrong.

The finding in 30 seconds

#

BulkScorer.java:57 calls scorer.advance(min) and :63 calls scorer.nextDoc(). Today Scorer extends Scorable and offers docID() and iterator(), but no advance or nextDoc: those live on the DocIdSetIterator that scorer.iterator() returns.

Background: Scorer and BulkScorer

#
  1. A Scorer walks the documents that match a query in one segment, in increasing doc id order, and scores them.
  2. A BulkScorer scores a whole range of doc ids at once: score(collector, acceptDocs, min, max) must ignore docs before min and return a value >= max. Lucene wraps a default one around every Scorer; only queries with a faster way to score a range write their own.
  3. Up to 5.4, a Scorer was itself a doc id iterator, with advance(target) and nextDoc(). Since 5.5.0 it hands one out instead: scorer.iterator().

The finding, step by step

#
  1. You write a custom BulkScorer and start from the example in the score() javadoc ("a Scorer-based implementation could look like below"), adding the constructor its comment names.
  2. You expect it to compile and to honour the window: on a 20-doc index where docs 0, 3, 6, ..., 18 match, score(collector, null, 4, 13) should collect docs 6, 9 and 12 and return a value >= 13.
  3. Instead javac stops with 2 errors on variable scorer of type Scorer: cannot find symbol: method advance(int) and cannot find symbol: method nextDoc().
  4. Why: the example dates from early 2015, when Scorer extended DocIdSetIterator. Lucene 5.5.0 (LUCENE-6919) moved iteration to scorer.iterator() and updated a link in this same file, but not the example.
  5. With scorer.iterator().advance(min) and scorer.iterator().nextDoc() the example compiles and collects 6, 9, 12, then 15, 18 and NO_MORE_DOCS.

Who is affected

#

Developers who write a custom BulkScorer, an expert extension point, and start from this example: two compile errors on every release since 5.5.0, about ten years. Nothing in Lucene runs the example, so no search result, index or default path changes.

Mechanism, terms and numbers437 words

The javadoc of BulkScorer#score(LeafCollector, Bits, int, int) states the window contract (ignore documents before min, return a value >= max) and then shows "a Scorer-based implementation" in 16 lines of Java. Two of them call scorer.advance(min) and scorer.nextDoc(). Scorer has had neither method since LUCENE-6919 (5.5.0) made it expose iterator() instead of extending DocIdSetIterator, so the example fails with two cannot find symbol errors on every release from 5.5.0 to 10.6.0 and on main.

The example was valid when it was written: up to 5.4.1 Scorer extended DocIdSetIterator (compiled here at 5.4.1). LUCENE-6919 changed one line of BulkScorer.java, the cost() javadoc link, and left the example, whose block ends 12 lines above that link, as it was. Nothing runs the example, so no search result changes; the fix changes two lines: scorer.iterator().advance(min) and scorer.iterator().nextDoc().

The example (main 645d4fe14a20, BulkScorer.java:48-67, &lt; decoded)

#
// :48  "For instance, a {@link Scorer}-based implementation could look like below:"
private final Scorer scorer; // set via constructor

public int score(LeafCollector collector, Bits acceptDocs, int min, int max) throws IOException {
  collector.setScorer(scorer);
  int doc = scorer.docID();
  if (doc < min) {
    doc = scorer.advance(min);          // :57  Scorer has no advance(int)
  }
  while (doc < max) {
    if (acceptDocs == null || acceptDocs.get(doc)) {
      collector.collect(doc);
    }
    doc = scorer.nextDoc();             // :63  Scorer has no nextDoc()
  }
  return doc;
}
  • What Scorer offers today. public abstract class Scorer extends Scorable (Scorer.java:28). Scorable has score(), smoothingScore(int), setMinCompetitiveScore(float) and getChildren(); Scorer adds docID() (:31) and iterator() (:43), among others, but no advance(int) and no nextDoc(). iterator() documents that "The returned iterator is a view: calling this method several times will return iterators that have the same state" (:40-41).
  • Why it compiled once. At the 5.4.1 tag Scorer.java:42 reads public abstract class Scorer extends DocIdSetIterator; at the 5.5.0 tag it reads public abstract class Scorer, with public abstract DocIdSetIterator iterator() at :123. The example text is the same in both.
  • How it was missed. LUCENE-6919 (ddb3a97678f) changed exactly one line of BulkScorer.java: {@link Scorer#cost()} became {@link DocIdSetIterator#cost()} in the cost() javadoc. The configured checks did not reject the example: doclint validates {@link} targets but does not compile code inside <pre>, and ErrorProne's InvalidSnippet check is about {@snippet} tags, which this block does not use (an intended-behaviour checker's reading of the build configuration, not a run).
  • Nothing else depends on it. No other source under lucene/ calls scorer.advance(...) or scorer.nextDoc(); the only other text hit is a code comment in FunctionRangeQuery.java:155.
Exposure and likelihood169 words
  • Who. BulkScorer is public with no @lucene.internal or @lucene.experimental tag; it is what Weight#bulkScorer returns (Weight.java:170-178) through the public, overridable ScorerSupplier#bulkScorer() (ScorerSupplier.java:44). The class javadoc says only queries that "have a more optimized means of scoring across a range of documents need to override this" (BulkScorer.java:23-26), and the package docs call custom queries "an expert level task" (package-info.java:388-391). The audience is small and expert.
  • Default vs opt-in. No runtime path: no Lucene code runs the example, and Lucene's own Scorer-backed bulk scorers use the iterator (Weight.java:240, :265-271; BatchScoreBulkScorer.java:45-46).
  • Scale and age. Every release from 5.5.0 (released 2016-02-22) to 10.6.0, branch_10x and main. The failure is deterministic and loud: two javac errors that name the missing methods.
  • What a reader loses. This is the only code in the score() javadoc that shows how to honour min, max and acceptDocs together, and it teaches an API shape (a Scorer that is its own iterator) that no longer exists.

Why it looks unintended

#
  • The javadoc introduces it as "a Scorer-based implementation" and gives the exact signature of the method it documents.
  • It was valid when written (Scorer extended DocIdSetIterator up to 5.4.1); LUCENE-6919 updated the cost() link in this same file, but not the example.
  • Lucene's own code uses the iterator: BatchScoreBulkScorer writes scorer.iterator().advance(min). Upstream has fixed stale examples before (LUCENE-6112, #12693).
The full argument168 words
  • The text presents it as an implementation. "For instance, a {@link Scorer}-based implementation could look like below:" (BulkScorer.java:48), then a <pre><code class="language-java"> block with real Lucene types and the exact signature of the abstract method (:53 vs :76).
  • It was correct when written. LUCENE-6184 (#7246) added it on 2015-01-19 while Scorer extended DocIdSetIterator (trunk cb3ec682d41; the same-day branch_5x backport 5c9b5e7ea4e is the commit released in 5.1.0); LUCENE-6553 (#7611) added the acceptDocs lines (trunk d671dd8d890, branch_5x c00996c54a3, first in 5.3.0).   • The rest of Lucene teaches iterator(). Scorer's class javadoc ("A Scorer exposes an iterator() over documents"); the package docs (package-info.java:404-406, :473-475); BatchScoreBulkScorer.java:46; CHANGES.txt:9706-9708 records LUCENE-6919 as an API change in 5.5.0.
  • Precedent. CHANGES.txt:11625 "LUCENE-6112: Fix compile error in FST package example code" (as the cross-model intended-lens review pointed out); 6fde1db2281 (#12693, Analyzer example); d1163450b6a (LUCENE-9046, TermInSetQuery example); 62f55c073c2 (LUCENE-8957, CustomAnalyzer examples).
The devil's-advocate check152 words

Strongest case for "leave it" (a separate intended-behaviour checker and a cross-model reviewer, OpenAI GPT-5.6): "could look like below" marks an illustrative sketch; the block already omits its class, constructor and cost(); BulkScorer is an expert extension point most queries never implement, since the default bulk scorer does this job; Lucene does not compile javadoc snippets; and the error is loud, so nobody is misled at run time.

Why it fails: the omitted parts are the ones the reader is meant to supply (the comment says where the field comes from); the two broken lines are the core of what the example teaches and name methods that do not exist. It went stale by oversight in a commit that edited the same file, and upstream has fixed the same kind of example before. The cross-model lenses rated the argument weak; every verifier and the adjudication called it a real documentation defect.

A. Call the iterator in place (validated by the checks) (recommended)

#

Two changed lines in the BulkScorer#score javadoc example.

   *   if (doc &lt; min) {
-  *     doc = scorer.advance(min);
+  *     doc = scorer.iterator().advance(min);
   *   }
   *   while (doc &lt; max) {
   *     if (acceptDocs == null || acceptDocs.get(doc)) {
   *       collector.collect(doc);
   *     }
-  *     doc = scorer.nextDoc();
+  *     doc = scorer.iterator().nextDoc();
   *   }

Trade-offs

  • The smallest change, and the same form as BatchScoreBulkScorer.java:46. In contract: Scorer#iterator() says repeated calls return views with the same state (Scorer.java:40-41).
  • It calls iterator() once per document; fine for an example, while a real implementation would cache it, as option B and Weight.DefaultBulkScorer do.

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20, seed DEADBEEF: the minimal test fails before the change and, with its example regenerated mechanically from the patched BulkScorer.java (byte-identical to the hunt's fix check), passes after it, with -Ptests.asserts=true and false.
  • TestBooleanScorer (20 tests, covers the default bulk scorer) passes; :lucene:core:checkGoogleJavaFormat and :lucene:core:renderJavadoc pass on the patched file, and the rendered BulkScorer.html shows the two corrected calls.
  • Semantics: the hunt unit's control runs the corrected example on a 20-doc index (window [4, 13) collects 6, 9, 12, then 15, 18 and NO_MORE_DOCS) with assertions on and off; a cross-model reviewer's own semantic test passed too.
  • Not run: gradlew check or other modules (the change is inside a javadoc comment).

B. Keep the iterator in a local variable (validated by the checks)

#

Four changed lines: DocIdSetIterator iterator = scorer.iterator(); after collector.setScorer(scorer);, then iterator.docID(), iterator.advance(min) and iterator.nextDoc().

   *   collector.setScorer(scorer);
-  *   int doc = scorer.docID();
+  *   DocIdSetIterator iterator = scorer.iterator();
+  *   int doc = iterator.docID();
   *   if (doc &lt; min) {
-  *     doc = scorer.advance(min);
+  *     doc = iterator.advance(min);
   *   }
   ...
-  *     doc = scorer.nextDoc();
+  *     doc = iterator.nextDoc();

Trade-offs

Reads like Lucene's own Weight.DefaultBulkScorer (Weight.java:240, :265-271), which keeps the iterator instead of calling iterator() per document. A style choice, not a correctness one (an intended-behaviour checker and the adjudication said the same). The cross-model fact check of this doc preferred B: it mirrors DefaultBulkScorer, avoids an iterator() call on every pass and reads better as teaching code.
