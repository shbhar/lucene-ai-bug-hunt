ParentsChildrenBlockJoinQuery's Weight#matches ignores the join, so parents and children of the wrong parents get Matches

ParentsChildrenBlockJoinQuery finds the right child documents, but its Weight#matches says "match" for any document its parent query or child query matches on its own: parents, children of the wrong parents, children over the limit. So +x -join loses its highlights, and Lucene Monitor reports documents the query does not match.

The bug in 30 seconds

#

Lucene answers two questions for a query: which documents match (the scorer) and, for one document, did it match and where (Weight#matches). For this join the scorer applies the parent condition and the per-parent limit; matches() applies neither.

  1. You index two parent/child blocks: docs 0 "size small" and 1 "size large" are children of parent doc 2 "red shirt"; doc 3 "size small" is the child of parent doc 4 "blue shirt". The join asks for children with "size" whose parent has "red".
  2. The search is right: docs 0 and 1. You expect Weight#matches, which highlighters and BooleanQuery use to ask "does this one document match?", to say yes for docs 0 and 1 only.
  3. Instead it says yes for docs 0, 1, 2 and 3: it asks the parent query and the child query about the same document, so the red parent (doc 2) and the blue parent's child (doc 3) count too. With a limit of 1 per parent the search returns only doc 0; the answer stays 0 to 3.
  4. A query that excludes the join breaks: +text:size -join finds the right documents, but Weight#matches says they do not match (doc 3 with no limit; docs 1 and 3 with a limit of 1). The default UnifiedHighlighter then returns doc 1 as size large instead of <b>size</b> large.
  5. Lucene Monitor's HighlightsMatch matcher decides matches with Weight#matches, so for a stored "children of public parents" query it reports docs 0, 1, 2 and 3 where the plain matcher reports 0 and 1. This bug never changes search hits, counts or scores.

Who is affected

#

Users of the experimental ParentsChildrenBlockJoinQuery (10.4.0 on) who read its Matches beyond its own hits: the join as a MUST_NOT clause under the default UnifiedHighlighter, Lucene Monitor's HighlightsMatch matcher, or code that calls Weight#matches on other documents. For them it happens every time such a document is asked about; no special setting is needed.

Mechanism, terms and numbers690 words

ParentsChildrenBlockJoinQuery (new in 10.4.0, @lucene.experimental) returns the child documents that match childQuery and whose block parent matches parentQuery, at most childLimitPerParent per parent. Its scorer implements that join; its Weight#matches(context, doc) does not. It returns the union of parentWeight.matches(context, doc) and childWeight.matches(context, doc) for the same document and never checks the parent bit set, the document's own block parent or the limit. So matches() is non-null for documents the query does not match: a parent that matches parentQuery, a child that matches childQuery under a parent that does not match (or with no parent), and a child over the limit.

This bug does not change search hits, counts or scores (a separate advance() issue can, see the fix trade-offs), and the join's own hits get the right Matches. The damage shows wherever something asks Weight#matches about a document that is not a hit. As a MUST_NOT clause the spurious Matches make BooleanWeight#matches null for the enclosing query's real hits, so +text:size -join loses its Matches and the default UnifiedHighlighter its highlights; as a SHOULD clause it can satisfy minimumNumberShouldMatch on documents it does not match; Lucene Monitor's HighlightsMatch.MATCHER reports parents, children of non-matching parents, lone children and over-limit children as matches. The test framework's own CheckHits.checkMatches rejects +text:size -join and, on an index of two red-parent blocks, the join used alone. The method has been this way since the class was added (#14728); a block-local check in matches() (+30/-13, one method) fixes it.

Terms

#
  • Blocks: a parent and its children are indexed together with IndexWriter#addDocuments, children first, parent last. A BitSetProducer (here QueryBitSetProducer(type:parent)) marks the parents.
  • ParentsChildrenBlockJoinQuery(parentFilter, parentQuery, childQuery, childLimitPerParent) (10.4.0, experimental): "returns the matching child documents for matching parent documents indexed together in the same block", at most childLimitPerParent per parent (class javadoc, ParentsChildrenBlockJoinQuery.java:43-51 on main a9779ef3c193).
  • Weight#matches(context, doc): for one document, returns Matches (which fields and positions matched) or null "if the document does not match the parent query", the parent query being the Weight's own query (Weight.java:61, :68-69). BooleanWeight#matches, the UnifiedHighlighter (on by default), Lucene Monitor's HighlightsMatch and the test framework's CheckHits rely on it.

The bug

#
  1. The join lives in the scorer. ParentsChildrenBlockJoinScorer (:265-452) walks the parent and child iterators together: nextDoc() (:314-347) counts the children returned for the current parent (childDocCount against childLimitPerParent) and alignParentAndChildIterator() (:384-404) keeps the child inside the block of a matching parent, using the parent bit set. Parents are never returned.
  2. matches() skips all of it. ParentsChildrenBlockJoinWeight#matches (:248-262) asks parentWeight.matches(context, doc) and childWeight.matches(context, doc) about the same doc id, returns null only when both are null ("Neither matches"), and otherwise returns MatchesUtils.fromSubMatches of the non-null ones ("Combine non-null matches"). Nothing looks at the parent bit set, the doc's block parent or the limit.
  3. What the union does. For a valid parentQuery (it matches only parents; the scorer throws when it lands on a parentQuery match that is not a parent, validateParentDoc, :425-429) parentWeight.matches is null on every child, so on the join's own hits the union is just the child's Matches, which is right. Its only effect is "match" for non-hits: a parent that matches parentQuery (doc 2), a child that matches childQuery under a parent that does not match or with no parent in the segment (doc 3), a child over the limit (doc 1 with limit 1).
  4. Who believes it. BooleanWeight#matches (BooleanWeight.java:134-164) returns null for a document when a prohibited clause's matches() is non-null (:142-146) and counts every non-null SHOULD clause toward minimumNumberShouldMatch (:153-162). The UnifiedHighlighter uses Weight#matches by default (UnifiedHighlighter.java:110, :518-527) and collects no offsets when it is null (FieldOffsetStrategy.java:143-150). Monitor's HighlightsMatch.MATCHER calls matches() for every document of the batch and records a match whenever it is non-null (HighlightsMatch.java:44-62).
  5. The sibling does it right. ToParentBlockJoinQuery's weight advances its own scorer to the document and returns MATCH_WITH_NO_TERMS (ToParentBlockJoinQuery.java:200-219): "The default implementation would delegate to the joinQuery's Weight, which matches on children. We need to match on the parent instead".
Exposure and likelihood363 words
  • Highlighting. With the join as a MUST_NOT clause, the enclosing query's real hits get null Matches, so the default UnifiedHighlighter returns them unhighlighted (size large instead of <b>size</b> large; the withWeightMatches(false) control highlights) [executed on main, 10.5.2 and 10.4.0]. As a SHOULD clause under minimumNumberShouldMatch the join can be counted on documents it does not match [executed through Monitor].
  • Lucene Monitor. HighlightsMatch.MATCHER differs from QueryMatch.SIMPLE_MATCHER in all 7 probe cases. Four use the stored join "children with body:size of acl:public parents": alone, with childLimitPerParent 1, and for one-document batches of a lone parent or a lone child. Three put body:size next to a join whose childQuery is type:child: of acl:public parents as a FILTER clause and as a SHOULD clause under minimumNumberShouldMatch 2, of acl:restricted parents as a MUST_NOT clause (true matches dropped) [executed on main, 10.5.2 and 10.4.0].
  • Other Weight#matches callers. Code that asks about documents not known to be hits, for example to label which named clause matched (NamedMatches), gets the same wrong answer [read, not executed].
  • Settings. No special setting is needed: a plain main() probe with the default IndexWriterConfig, the default codec and a plain IndexSearcher gives the same Weight#matches answers on main (assertions on and off), 10.4.0 and 10.5.2. The JUnit repros run under LuceneTestCase, which picks a randomized test codec (Asserting(Lucene104) in the recorded runs). Default highlighter flags. The mechanism does not depend on index size, but a visible effect needs a document that matches parentQuery or childQuery but not the join, and a caller that asks Weight#matches about it; the executed indexes have up to 5 documents.
  • Not hit. Search hits, counts and scores (this bug does not touch the scorer; a separate advance() issue can return an over-limit hit in a conjunction, see the fix trade-offs); the Matches of the join's own hits; the join alone or as a required clause, highlighted on its hits (no visible symptom, although on some indexes CheckHits rejects the join alone).
  • Reach. The class is @lucene.experimental, new in 10.4.0 and built programmatically (no query parser makes it); a code search found no use in Elasticsearch, OpenSearch or Solr. Likelihood: rare.

Why it is a bug, not intended

#
  • Weight#matches returns null "if the document does not match"; this query's hits are children of matching parents, up to the limit.
  • Lucene's own CheckHits.checkMatches fails on +text:size -join and, on an index of two red-parent blocks, on the join alone, where ToParentBlockJoinQuery passes.
  • The sibling ToParentBlockJoinQuery overrides matches() for exactly this reason: "We need to match on the parent instead".
The full argument248 words
  • The contract. Weight.java:68-69: "Returns Matches for a specific document, or null if the document does not match the parent query", the parent query being the Weight's own query (@param query the parent query, :61). The class javadoc (ParentsChildrenBlockJoinQuery.java:43-51) defines the hits as matching children of matching parents, at most childLimitPerParent per parent.
  • Lucene's own oracle. CheckHits.MatchesAsserter (CheckHits.java:646-688, run by QueryUtils.check) requires non-null Matches on each hit and, for each hit after the first one collected whose previous document was not a hit, null on that previous document (the message names the hit). It fails on +text:size -join ("Unexpected null Matches object in doc3") and, on an index of two red-parent blocks, on the join alone ("Unexpected non-null Matches object in non-matching doc2", about the red parent doc 1), while ToParentBlockJoinQuery passes on that index [executed].
  • The sibling. ToParentBlockJoinQuery gives up child terms and returns MATCH_WITH_NO_TERMS from its own scorer rather than report Matches the join does not produce (LUCENE-8229, #9276; ToParentBlockJoinQuery.java:200-219).
  • The rule, stated by the committer who merged #14728. In #15469 (comment of 2026-01-13): "Weight#scorerSupplier() and Weight#matches() are expected to be semantically the same". It was said about FilterWeight subclasses in general and names no class.
  • Nothing accepts the union. No test, javadoc, CHANGES or MIGRATE entry describes it. The class's only test, TestParentsChildrenBlockJoinQuery, never calls matches(), CheckHits or QueryUtils.check; #14728's conversation and review comments and the issue #14565 never discuss matches().
The devil's-advocate check180 words

The strongest case for "intended": the comment "Combine non-null matches" (:257) shows the union was written on purpose; the class and Weight#matches are @lucene.experimental; the union has a use, since with the default highlighter a join query also highlights the non-hit parent (<b>red</b> shirt) and keeps highlights on join hits that a correct matches() loses on the highlighter's one-document reader; and a correct matches() costs more and must not call this Weight's own scorerSupplier() twice per leaf (LFV-167).

Why it fails: the union is taken on the same doc id, so it never adds the parent's terms to a child hit; its only effect is answering "match" for non-hits, against the explicit null-for-non-match contract that BooleanWeight, Monitor and CheckHits depend on. Highlighting a parent the query does not match is not something the query promises, and Lucene already chose correctness over extra highlights in the sibling. "Experimental" allows API changes, not a method that contradicts its own javadoc. Every reviewer of the claim, including two from another model family, rated the intended-behaviour case weak.

Suggested fix

#

Recommended Check the join for the document's own block

In matches(), check the join for the document's own block: null for parents, for children whose block parent does not match parentQuery and for children past the first childLimitPerParent matching ones; otherwise the child's Matches (+30/-13, one method). The repro, the join module with the hunt's tests (115 tests) and the highlighter and Monitor tests pass.

All options and trade-offs3 options · 1,139 words

One fix was applied in a scratch worktree at a9779ef3c193 and run through gradle (seed DEADBEEF); the finder's alternative was validated in the hunt and re-run here with its class shadowed; the third option was not run.

Check the join for the document's own block (validated by the checks) (recommended)

#

Replace the body of ParentsChildrenBlockJoinWeight#matches (+30/-13, also removing the three imports the union used). It mirrors the scorer's definition of a hit (the block parent matches parentQuery, the child matches childQuery and is among the first childLimitPerParent matching children of its block) and returns the child's own Matches for hits, so hits keep exactly the Matches they get today. It builds the parent and child scorers directly, as ToParentBlockJoinQuery#matches builds its own, so it does not use up this Weight's single scorerSupplier() call per leaf (LFV-167). Work per call: one parentFilter.getBitSet call (cached per segment by QueryBitSetProducer; a custom BitSetProducer need not cache), two fresh sub-scorers, one advance on each, a walk over the matching children of one block and, for a hit, childWeight.matches. Not benchmarked.

final BitSet parentBits = parentFilter.getBitSet(context);
if (parentBits == null || parentBits.get(doc)) {
  return null; // parent documents are never hits
}
final int parentDoc = parentBits.nextSetBit(doc);
if (parentDoc == DocIdSetIterator.NO_MORE_DOCS) {
  return null; // no parent after this doc
}
final Scorer parentScorer = parentWeight.scorer(context);
if (parentScorer == null || parentScorer.iterator().advance(parentDoc) != parentDoc) {
  return null; // the block's parent does not match parentQuery
}
final Scorer childScorer = childWeight.scorer(context);
if (childScorer == null) {
  return null;
}
final int firstChild = parentBits.prevSetBit(parentDoc - 1) + 1;
final DocIdSetIterator childIt = childScorer.iterator();
int matchingChildren = 0;
for (int child = childIt.advance(firstChild); child <= doc; child = childIt.nextDoc()) {
  if (++matchingChildren > childLimitPerParent) {
    return null; // over the per-parent limit
  }
  if (child == doc) {
    return childWeight.matches(context, doc);
  }
}
return null; // doc does not match childQuery

Trade-offs

  • Known gap, a separate defect. In the hunt's bounded-exhaustive harness (every block layout of up to 4 documents), 40 of 108,336 checks of +text:a +join still differ with the fix, all with childLimitPerParent 1 or 2: the conjunction moves the join with advance(), which does not count the block's earlier children, so the search itself returns a child that nextDoc() order puts over the limit, and the fixed matches() says no. That lives in the scorer's advance() (ParentsChildrenBlockJoinQuery.java:350-382) and is not in the registry. Lead the issue with the parent and wrong-parent cases, which do not depend on it.
  • Highlighting interplay. With any correct matches(), join hits whose parentQuery uses the highlighted field lose highlights that today's union produces by accident. The join is an opaque leaf to the highlighter (ParentsChildrenBlockJoinQuery.java:116-117), so a postings offset source falls back to analysis (UnifiedHighlighter.java:1253-1272); with analysis (and term vectors) the default UnifiedHighlighter evaluates Weight#matches on a reader whose highlighted field holds only the hit document, where the hit's parent cannot match. The POSTINGS_WITH_TERM_VECTORS source uses a different reader and was not tested. Hunt harness, highlighter oracle, every block layout of up to 3 documents on one segment, two highlighted fields: all 294 such checks per field pass on stock main and all 294 per field fail with this fix; the finder's fix gave the same, and 144 of 144 per field on two segments. That highlighter defect is registered separately as LFV-505 (novelty "known": a partial downstream overlap with elastic/elasticsearch#96068), established for the tested block joins whose condition uses the highlighted field; mention it in the PR.
  • Nested joins [read, not executed]. It calls parentWeight.scorer(context) and childWeight.scorer(context) on every call. If a sub-query is or contains a ParentsChildrenBlockJoinQuery, that inner Weight's one-scorerSupplier()-per-leaf guard (:191-197, LFV-167) throws on the second outer matches() call for a leaf, or on the first one after the inner Weight already scored it; today's union calls only the sub-weights' matches(). Option B has the same exposure.
  • No parent-query validation [read]. Like today's matches(), it does not repeat the scorer's validateParentDoc check (:425-429): with an invalid parentQuery that also matches children, the scorer may throw while matches() just answers for the block's real parent.
  • Add a CheckHits.checkMatches (or QueryUtils.check) call to TestParentsChildrenBlockJoinQuery; no test of the class calls matches() today.

Re-run the join's own scorer from the start of the segment (the finder's fix) (validated by the checks)

#

Build a ParentsChildrenBlockJoinScorer from fresh parent and child scorers and call nextDoc() until it reaches doc; return the child's Matches only on a hit.

Trade-offs

Every call walks the segment up to doc, so a caller that asks about every document (Monitor's HighlightsMatch.MATCHER) does quadratic work per batch (not measured). It decides membership with nextDoc(), so it shares the advance() gap of option A, and it calls the sub-weights' scorer() like option A, with the same nested-join exposure [read]. Its diff leaves ArrayList, List and MatchesUtils imported but unused.

What the checks validated

In the hunt on ea57360912ed: the finder's, the highlighter, the reproducer's and the Monitor tests pass, and the join-module run gives the same result as without it (104 tests found, 101 successful, 3 aborted because the nightly test group was off, 0 failed). On a9779ef3c193, shadowed: the finder's tests 3 of 3 and the Monitor probe 7 of 7 pass.

The ToParentBlockJoinQuery pattern: advance this Weight's own scorer

#

Call scorer(context) and advance(doc), as the sibling does.

Trade-offs

Not viable as is: any call after this Weight has already supplied a scorer for the leaf (the second matches() call of a fresh Weight, or the first one after it scored the leaf) trips the one-scorerSupplier()-per-leaf guard (ParentsChildrenBlockJoinQuery.java:191-197, LFV-167), and advance() ignores the limit (the gap above). Not run.

Downstream note

#

Code that decides matches with Weight#matches, such as Lucene Monitor's HighlightsMatch.MATCHER, reports documents that the join's parent condition or child limit excludes, which matters downstream only where such a match routes or delivers documents; no downstream use of this query was found in Elasticsearch, OpenSearch or Solr.

How it was found

#

A bounded-exhaustive differential test of Lucene's block joins on the real jar: every block layout of up to 5 documents, comparing Weight#matches with the hits of a fresh scorer. It flagged this join alone and in every wrapper query; a public-API JUnit then confirmed it. No model checker, solver or prover was involved.

The method in full213 words

Method: bounded-exhaustive translation validation on the stock jar (the semi-formal tier).

  • First signal: a block-join hunt compared the real join jar with an independent brute-force join over every small index. Its Weight.matches check reported 3,512, 3,460 and 3,456 mismatches for childLimitPerParent 1, 2 and unlimited at up to 4 documents (about 1.3 million each at up to 7). It was recorded as an unpromoted lead; a second hunt on explain/score coherence noted the same defect as a lead.
  • A later hunt on Matches coherence across module queries promoted it with its own harness: oracle M1, Weight#matches non-null exactly for the documents in a fresh scorer's match set, over every block layout of up to 5 documents with every text from {"", a, b, "a b"}, on 1 and 2 segments, for the query alone and inside +a +Q, *:* -Q and msm=2(Q, b). For example 446,600 of 1,091,376 checks failed for the join alone on one segment; ToParentBlockJoinQuery and the older ParentChildrenBlockJoinQuery had 0. The finder then wrote a public-API JUnit on the stock main jar.
  • Found 2026-10-26 on main ea57360912ed; then checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a security screen and a credibility audit.

Bug record

#

LFV-508, snapshot of 2026-10-29

Registry title
ParentsChildrenBlockJoinQuery's Weight#matches ignores the join and returns Matches for documents the query does not match (parent documents, children of non-matching parents, children over childLimitPerParent), so as a MUST_NOT clause it strips the Matches and highlights of real hits, and Lucene Monitor's HighlightsMatch matcher reports the wrong documents
Area
join / block join Weight#matches (ParentsChildrenBlockJoinQuery; consumers BooleanWeight#matches, UnifiedHighlighter, Monitor HighlightsMatch)
Priority
Medium, rank 255: ParentsChildrenBlockJoinQuery#matches ignores the join, losing highlights and misreporting Monitor HighlightsMatch, but the class is experimental (10.4+).
Impact class
silent wrong results
Impact note
Applications that use the experimental ParentsChildrenBlockJoinQuery (new in 10.4.0) and read Matches from it get non-null Matches for documents the join does not return, with the default codec, IndexWriterConfig and IndexSearcher, -ea and -da, at any index size: the join alone already fails the test framework's CheckHits.checkMatches oracle; as a MUST_NOT clause it makes BooleanWeight#matches return null for the enclosing query's real hits, so the default UnifiedHighlighter returns those hits without highlights; and Lucene Monitor's HighlightsMatch.MATCHER reports parent documents, children of non-matching parents, children without their parent and over-limit children as matches where QueryMatch.SIMPLE_MATCHER does not (and, with the join as a MUST_NOT clause, drops true matches); search hits, counts and scores are correct, and the join's own hits get correct Matches.
Summary
You index parent/child blocks, build a ParentsChildrenBlockJoinQuery (children that match childQuery and whose parent matches parentQuery, at most childLimitPerParent per parent) and ask its Weight for Matches, directly, inside a BooleanQuery, through the default UnifiedHighlighter or through Lucene Monitor, and you expect non-null Matches exactly for the join's hits, as Weight#matches documents ('or null if the document does not match the parent query'). Instead matches() returns the union of the parent query's and the child query's Matches on the same document without checking the join, so it is non-null for the parent document itself, for children of parents that do not match and for children over the limit (in the finder's test the only hit is doc 0, but docs 0, 1, 2 and 3 get Matches). Searches stay correct, but a query such as +text:size -join loses the Matches and highlights of its real hits, and Monitor's HighlightsMatch matcher reports documents the stored query does not match.
