MemoryIndex ignores TermFrequencyAttribute, so FeatureField values and custom term frequencies are indexed as frequency 1

MemoryIndex ignores TermFrequencyAttribute, so FeatureField values and custom term frequencies become 1: a FeatureField worth 10 scores 4.5918E-41 instead of 10.0 (linear), or exactly 0.0, "no match", instead of 0.5 (saturation with the pivot 10), although the document matches. Lucene Monitor inherits it for single documents (since 8.6.0).

The bug in 30 seconds

#

FeatureField and any TokenStream that sets TermFrequencyAttribute tell Lucene how often a term occurs instead of repeating it. IndexWriter keeps that number. MemoryIndex, the one-document in-memory index, ignores it and counts each token once.

  1. You put one document with FeatureField("features", "pagerank", 10f) into a one-document IndexWriter index and into MemoryIndex.fromDocument. FeatureField stores the value as a term frequency: 10f becomes 33344.
  2. You search FeatureField.newLinearQuery("features", "pagerank", 1f) and expect the score 10.0 from both, as for ordinary fields. IndexWriter gives 10.0.
  3. MemoryIndex never reads the frequency attribute and counts the token once. Frequency 1 decodes to 4.5918E-41, so the score is 4.5918E-41. With newSaturationQuery (pivot 10) it is exactly 0.0 instead of 0.5, which MemoryIndex.search documents as "no match", while count() says the document matches.
  4. Custom frequencies on text fields shrink the same way: a DOCS_AND_FREQS term a with frequency 7 gets freq 1, sumTotalTermFreq 2 instead of 8, norm 2 instead of 8, and BM25 0.1308 instead of 0.2456.
  5. Lucene Monitor (since 8.6.0) matches one document on a MemoryIndex and two or more on an IndexWriter reader: the same document scores 10.0 in a batch of two and 4.5918E-41 alone, and a saturation query with the pivot 10 is not reported for it at all.

Who is affected

#

Code that scores FeatureField queries or reads term statistics of custom-frequency fields on a MemoryIndex: Lucene Monitor with ScoringMatch matching single documents (since 8.6.0), callers of MemoryIndex.search (whose documented match test is score > 0), and DelimitedTermFrequencyTokenFilter or DOCS_AND_CUSTOM_FREQS fields. Default settings, opt-in custom frequencies, every time; for the tested queries the matching documents stay the same.

Mechanism, terms and numbers756 words

FeatureField stores its value as a term frequency, and any TokenStream can set a custom frequency through TermFrequencyAttribute (for example DelimitedTermFrequencyTokenFilter on a|7, or a DOCS_AND_CUSTOM_FREQS field since 10.5.0). For DOCS_AND_FREQS and DOCS_AND_CUSTOM_FREQS fields IndexWriter indexes that frequency; MemoryIndex.storeTerms never reads the attribute and adds 1 per token to the postings frequency, sumTotalTermFreq and the field length. A document put into a MemoryIndex (fromDocument, addField(IndexableField, Analyzer), or Lucene Monitor matching one document) therefore counts each such token as frequency 1: FeatureField("features", "pagerank", 10f) is frequency 33344 in an IndexWriter index and 1 in a MemoryIndex, which decodes to 4.5918E-41. FeatureField.newLinearQuery scores 4.5918E-41 instead of 10.0, and newSaturationQuery with the pivot 10 scores exactly 0.0 instead of 0.5 although the document matches; 0.0 is what MemoryIndex.search documents as "no match". Since 8.6.0, Monitor scores the same document 10.0 in a two-document batch and 4.5918E-41 alone, and drops a stored saturation query with the pivot 10 for the single document. For the tested queries the set of matching documents (IndexSearcher.count) is unchanged; only score-based match tests lose the match. Every release checked from 7.0.0 to 10.5.2 is affected; the validated fix reads the attribute where IndexWriter honours it and rejects overflow as IndexWriter does.

Terms

#
  • TermFrequencyAttribute: a token attribute that "Sets the custom term frequency of a term within one document"; the field must be indexed with DOCS_AND_FREQS (TermFrequencyAttribute.java:24-26 on main a9779ef3c193). DelimitedTermFrequencyTokenFilter sets it from text like a|7; since 10.5.0 a DOCS_AND_CUSTOM_FREQS field treats it as a per-term score, adding 1 per term to the field length.
  • FeatureField: a rank-feature field (pagerank, learned-sparse term weights). "Feature values are internally encoded as term frequencies" (FeatureField.java:47): the value becomes Float.floatToIntBits(value) >>> 15 (:185-186; 10f gives 33344), set through the attribute (:222) on a DOCS_AND_FREQS field (:114). Its queries decode the frequency back with Float.intBitsToFloat(freq << 15) (:240-249).
  • MemoryIndex: a single-document index held in memory, "a replacement/substitute for RAM-resident Directory implementations" (MemoryIndex.java:106). Lucene Monitor uses one for a one-document batch and an IndexWriter-built reader for larger batches (DocumentBatch.java:44-62, 105-113).

The bug

#
  1. IndexWriter uses the attribute, for DOCS_AND_FREQS and DOCS_AND_CUSTOM_FREQS fields. FreqProxTermsWriterPerField.getTermFreq (FreqProxTermsWriterPerField.java:208-219) takes it as the postings frequency, and IndexingChain adds it to the field length (1 per term for DOCS_AND_CUSTOM_FREQS) with Math.addExact (IndexingChain.java:2053-2064). A DOCS field keeps no frequencies (distinct terms read as 1 on both paths), and a positional field throws "cannot index positions while using custom TermFrequencyAttribute" (:210-216).
  2. MemoryIndex does not. storeTerms (MemoryIndex.java:991-1053) asks the stream only for the term, position-increment, offset and payload attributes (:1002-1007) and per token does info.numTokens++ (:1012), info.sliceArray.freq[ord]++ (:1025) and info.sumTotalTermFreq++ (:1027). The norm is computed from numTokens (:1380-1393). TermFrequencyAttribute appears nowhere in the file.
  3. Frequency 1 decodes to almost nothing. Float.intBitsToFloat(1 << 15) is 4.5918E-41, a subnormal float below the smallest value FeatureField accepts (Float.MIN_NORMAL, FeatureField.java:162-171). The linear function returns it. The other functions depend on their parameters (executed): saturation weight * (1 - pivot / (f + pivot)) (:450) with the pivot 10 rounds 10f / (10f + 4.5918E-41f) to 1.0 and returns exactly 0.0, and so does sigmoid with the pivot 10 (:531); log with scalingFactor 1 (:356) is always 0.0, because 1f + 4.5918E-41f is 1f. Saturation without a pivot takes the pivot from the index statistics (:408-415, :725-738), which on a one-document MemoryIndex decode to the same 4.5918E-41, so it scores 0.5 as on IndexWriter; tiny explicit pivots give positive but wrong scores.
  4. 0.0 is "no match". MemoryIndex.search returns "0.0 indicating no match" (MemoryIndex.java:1105-1106; the class example tests score > 0.0f, :153-157), and Monitor's ScoringMatch reports a match only when score > 0 (ScoringMatch.java:37). That convention was already imperfect: a FILTER-only query and a boost-0 query match but score 0.0 on both paths (executed); this bug adds matching documents that score 0.0 only because their frequency was dropped.
  5. The hit set is unchanged for the tested queries. Every term is still indexed for the document. The follow-up's probe ran 12 query shapes (five FeatureField function settings, two term queries, FILTER and two MUST_NOT combinations, two zero-score controls): IndexSearcher.count was the same on both paths for all 12 (executed). A query that itself depends on frequencies could still differ; none was tested.
Exposure and likelihood232 words
  • Monitor. With ScoringMatch and FeatureField queries, a single document scores differently from the same document in a batch (10.0 vs 4.5918E-41), and a stored query whose only scoring parts round to 0.0 (saturation or sigmoid with an explicit pivot such as 10, log with scalingFactor 1) is not reported at all for a single document (executed: saturation on main and 10.5.2; sigmoid and log in the fact checks' Monitor runs on main). The no-pivot saturation query keeps its match (0.5 on both paths). Monitor matches a single document on MemoryIndex only since 8.6.0 (LUCENE-9314): in 8.2.0 to 8.5.2 match(Document) went through the IndexWriter-based batch (read).
  • Direct MemoryIndex.search. Its javadoc makes score > 0.0f the match test; the same query shapes report "no match" for a matching document (executed).
  • Custom-frequency text fields. Postings frequency, totalTermFreq, sumTotalTermFreq, the norm and BM25 scores are wrong for DOCS_AND_FREQS fields fed by DelimitedTermFrequencyTokenFilter or a custom stream, and for DOCS_AND_CUSTOM_FREQS fields (10.5.0+) (executed).
  • Default vs opt-in. Default MemoryIndex, Monitor and similarity settings; the trigger is the opt-in custom-frequency feature.
  • Scale. Any document, deterministic, every time.
  • Silent. No exception, and for the tested queries no change in which documents match, so only code that reads frequencies, term statistics, norms or scores notices (including score-based match tests); no report was found in the nine years since 7.0.0, so the registry rates the likelihood "rare".

Why it is a bug, not intended

#
  • TermFrequencyAttribute sets "the custom term frequency of a term within one document"; FeatureField values "are internally encoded as term frequencies". MemoryIndex accepts both and drops the number.
  • MemoryIndex is a documented "substitute" for an index; its duel test checks norms, hit counts and term-vector frequencies against IndexWriter.
  • No limitation is documented; ignoring omitNorms was fixed as a bug (LUCENE-7679).
The full argument361 words
  • The attribute's contract. TermFrequencyAttribute.java:24-26: "Sets the custom term frequency of a term within one document. If this attribute is present in your analysis chain for a given field, that field must be indexed with IndexOptions#DOCS_AND_FREQS." FeatureField and the DOCS_AND_FREQS repro field meet that precondition word for word. DOCS_AND_CUSTOM_FREQS (10.5.0) is newer than that sentence and not named in it; IndexOptions.java:53-54 calls it "Like DOCS_AND_FREQS except the "custom freqs" are treated as scores", and IndexWriter honours the attribute for it, so it is a parity case. DelimitedTermFrequencyTokenFilter states the same precondition: "DOCS_AND_FREQS but no positions or offsets" (DelimitedTermFrequencyTokenFilter.java:31-32).
  • FeatureField's contract. FeatureField.java:47: "Feature values are internally encoded as term frequencies." Its query functions read the value back from the frequency.
  • MemoryIndex's role. MemoryIndex.java:106: "a replacement/substitute for RAM-resident Directory implementations"; :129: "Arbitrary Lucene queries can be run against this class". Monitor swaps it in for a one-document IndexWriter index only for speed (DocumentBatch.java:101-102: "MemoryIndex benchmarks as better performing than RAMDirectory for this case"), since 8.6.0, when LUCENE-9314 fixed "Single-document monitor runs were using the less efficient MultiDocumentBatch implementation" (CHANGES.txt:5804-5805).
  • Tests. TestMemoryIndexAgainstDirectory duels MemoryIndex against an IndexWriter index: equal norms (:200-207), equal hit counts (:259-268), and in testDuelMemoryIndexCoreDirectoryWithArrayField equal term-vector frequencies, positions and offsets (:714-800). Its postings and sumTotalTermFreq checks (:210-250) compare the MemoryIndex reader with its own term vectors, not with IndexWriter (:193-196). Its analyzers never set the attribute. No test in lucene/memory or lucene/monitor uses TermFrequencyAttribute or FeatureField, and none asserts frequency 1.
  • History. LUCENE-7854 (d276acfbbcb8, 2017) added the attribute in 14 files, none in lucene/memory; #15584 (DOCS_AND_CUSTOM_FREQS, 10.5.0) changed one MemoryIndex line without adding support. Neither discussion mentions MemoryIndex or Monitor.
  • Precedents. LUCENE-7679 / #8730 (type:bug, Bug Fixes in 6.5.0, CHANGES.txt:8442-8443): "MemoryIndex was ignoring omitNorms settings on passed-in IndexableFields", which also made its scores differ from IndexWriter's. LUCENE-8756 / #9801 (type:bug): "MLT queries ignore custom term frequencies", the same omission in MoreLikeThis; 8.1.0's CHANGES lists the fix under "Changes in Runtime Behavior" (CHANGES.txt:6564, entry :6578-6579).
The devil's-advocate check209 words

The strongest works-as-designed case, built by the verifiers and a reading-only review by a model from another family (rated "moderate"): MemoryIndex does not mirror index options. createFieldInfo always declares DOCS_AND_FREQS_AND_POSITIONS[_AND_OFFSETS] (MemoryIndex.java:759-763), TestMemoryIndex.testKeywordWithoutTokenStream (:1093) accepts occurrence counts with positions for DOCS-only keyword fields, and IndexWriter rejects custom frequencies together with positions ("cannot index positions while using custom TermFrequencyAttribute", FreqProxTermsWriterPerField.java:208-219). The attribute's javadoc names only DOCS_AND_FREQS, and Monitor's use of MemoryIndex is a speed optimization, not a stated promise of full equivalence. So custom frequencies may never have been part of MemoryIndex's model.

Why it fails: MemoryIndex accepts these stock fields without complaint and then returns wrong scores, including a documented "no match" for a matching document. The caller met the attribute's precondition; it is MemoryIndex that overrides the index options. Nothing in javadoc, CHANGES, MIGRATE or tests documents a limitation (compare GITHUB#15334, whose CHANGES entry says "MemoryIndex does not support nearest neighbor search"). Honouring the frequency or rejecting the field would both remove the silent wrong score. The argument does hold for addField(String, TokenStream), which always indexes positions (it uses defaultFieldType, MemoryIndex.java:476-479, :728; its javadoc does not say so): lead the issue with FeatureField through fromDocument or Monitor.

Suggested fix

#

Recommended Honour the frequency where IndexWriter does, reject overflow as IndexWriter does

In MemoryIndex.storeTerms, read TermFrequencyAttribute on DOCS_AND_FREQS and DOCS_AND_CUSTOM_FREQS fields (where IndexWriter honours it), add it to the frequency, sumTotalTermFreq and field length, and reject int overflow with IndexWriter's "too many tokens for field" (+40/-8, one file). The repro passes with assertions on and off, and the whole memory, monitor and highlighter test suites pass (73 classes, 991 tests).

final boolean customFreqs =
    indexOptions == IndexOptions.DOCS_AND_FREQS || indexOptions == IndexOptions.DOCS_AND_CUSTOM_FREQS;
final boolean termDoc = indexOptions == IndexOptions.DOCS_AND_CUSTOM_FREQS;
TermFrequencyAttribute termFreqAtt =
    customFreqs ? stream.addAttribute(TermFrequencyAttribute.class) : null;
// per token:
final int termFreq = termFreqAtt == null ? 1 : termFreqAtt.getTermFrequency();
info.numTokens = addTokens(info, info.numTokens, termDoc ? 1 : termFreq); // was ++
info.sliceArray.freq[ord] = addTokens(info, info.sliceArray.freq[ord], termFreq); // was ++
info.sumTotalTermFreq += termFreq; // was ++

Honour the frequency where IndexWriter does, reject overflow as IndexWriter does (validated by the checks) (recommended)

#

storeTerms gets the field type's IndexOptions. For DOCS_AND_FREQS and DOCS_AND_CUSTOM_FREQS it reads TermFrequencyAttribute and adds the frequency to the postings frequency, maxTermFrequency, sumTotalTermFreq and the field length (1 per term for DOCS_AND_CUSTOM_FREQS, as IndexingChain does). Positional field types, including every addField(String, ...) path and the highlighters' re-analysis, keep today's one-per-token counting. Int sums go through Math.addExact and throw IllegalArgumentException("too many tokens for field ...") like IndexingChain. MemoryPostingsEnum.nextPosition returns -1 once the stored positions run out (a frequency of 33344 has one stored position), which is what PostingsEnum returns when positions are not indexed. Trade-offs

  • The positional view stays inconsistent. MemoryIndex still declares positions (hasPositions true) while a FeatureField posting now has frequency 33344 and one stored position: later positions read as -1, term vectors report frequency 33344, and toStringDebug prints "positions=33344" next to one real position (executed). -1 is what PostingsEnum returns when positions are not indexed, but this reader says they are, so a positional query on a FeatureField runs instead of throwing as on an IndexWriter index. Making createFieldInfo follow the field type would fix it, but changes what testKeywordWithoutTokenStream asserts.
  • Not validated for position consumers. No test runs a phrase, span or other positional query, or CheckIndex, against a fixed custom-frequency field; apart from this doc's own tests the upstream memory and monitor suites have no FeatureField or TermFrequencyAttribute case. A PR should add such tests, or stop advertising positions for these fields.
  • Positional fields stay lenient. A TextField analysed with DelimitedTermFrequencyTokenFilter makes IndexWriter throw "cannot index positions while using custom TermFrequencyAttribute"; MemoryIndex keeps counting 1. Throwing there too could break highlighting of such fields, which re-analyses text into a MemoryIndex through addField(String, TokenStream) (MemoryIndexOffsetStrategy.java:112, WeightedSpanTermExtractor.java:411-413).
  • DOCS fields stay lenient. For a repeated term with a frequency other than 1, IndexWriter throws "must index term freq while using custom TermFrequencyAttribute" (FreqProxTermsWriterPerField.java:147-152); the fix does not read the attribute for DOCS, so MemoryIndex accepts it.
  • No duplicate-term check for DOCS_AND_CUSTOM_FREQS. IndexWriter rejects the document with "Document update skipped due to duplicate termdoc term" (IndexingChain.java:2095-2097, caused by "has duplicate term" at FreqProxTermsWriterPerField.java:193-194); MemoryIndex adds the two frequencies (executed). The hunt's harness counted 432 such cases; a separate parity gap that can go in the same PR.
  • The overflow exception leaves the MemoryIndex partly updated, like any exception in the middle of a TokenStream (IndexWriter marks the document deleted). Not benchmarked: per token one attribute read and two checked additions.

Reject custom frequencies

#

Throw IllegalArgumentException when a token's frequency is not 1 ("MemoryIndex does not support custom term frequencies"). Not run.

Trade-offs

Small and removes the silent wrong score, but every document with a FeatureField that goes through a MemoryIndex (a single-document Monitor match, the percolator path) would start failing, even when no query reads the field; Monitor batches of two or more use IndexWriter and are not affected. Given MemoryIndex's always-positional design, maintainers may well prefer this option.

Document the limitation

#

Say in the MemoryIndex class javadoc that custom term frequencies are counted as 1. (GITHUB#15334 stated its kNN limitation only in its CHANGES entry, CHANGES.txt:1476-1477; MemoryIndex.java has no such javadoc.) Not run.

Trade-offs

Makes the behaviour a documented limitation, but leaves the wrong scores and the "no match" for matching documents in place.

The hunt's first sketch (do not use as is)

#

Reads the attribute for every field type and adds it with plain +=. It passes the repros and the 51 upstream memory tests.

Trade-offs

With 50,000 tokens of frequency Integer.MAX_VALUE the field length wraps and the field vanishes from the reader (MemoryIndex hides fields with numTokens <= 0, MemoryIndex.java:1834, 1842), executed; with the recommended fix the same input throws "too many tokens for field".

Downstream note

#

Downstream percolators that build a MemoryIndex from the document, such as Elasticsearch's and OpenSearch's with rank_feature (a FeatureField), score such queries wrong (by code reading); they decide matches by hit existence, so the matched queries do not change.

How it was found

#

Bounded-exhaustive translation validation on the real jar: the same tiny document (every stream of up to two tokens with custom frequencies 1, 2 and 7, plus FeatureField with four values and four query functions, 1,836 cases) built once with IndexWriter and once with MemoryIndex, then compared through the public API. Every case with a frequency other than 1 differed.

The method in full162 words

Method: bounded-exhaustive translation validation on the stock jar (semi-formal tier), in a hunt unit on MemoryIndex equivalence.

  • The harness builds each case twice, with a one-document IndexWriter index and with MemoryIndex, and compares the postings frequency, totalTermFreq, sumTotalTermFreq, the norm and query scores through LeafReader and the query API. Scope CF: one field, DOCS_AND_FREQS and DOCS_AND_CUSTOM_FREQS, omitNorms on and off, every stream of at most two tokens over {a, b} with custom frequencies {1, 2, 7}, plus FeatureField with 4 values and 4 query functions: 1,836 cases, 4,220 comparisons.
  • Mismatches in every class (for example 1,120 DOCS_AND_FREQS and 800 DOCS_AND_CUSTOM_FREQS score mismatches, and all 16 FeatureField query scores); 0 mismatches with the fix sketch shadowed.
  • Found 2026-10-26 on main ea57360912ed; then turned into public-API JUnits and checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by an independent reviewer from another model family (OpenAI GPT-5.6), an adjudication and a follow-up with history and prior-report searches.

History

#

An omission since custom frequencies exist: LUCENE-7854 (d276acfbbcb8, 2017-06-06; first release 7.0.0) taught IndexWriter the attribute but not MemoryIndex. FeatureField (7.4.0) and DOCS_AND_CUSTOM_FREQS (10.5.0) widened the reach. Ten releases from 7.0.0 to 10.5.2 and main were run: all fail; not fixed upstream.

Versions tested10 rows

Introduced by d276acfbbcb8 (2017-06-06), "LUCENE-7854: enable indexing custom term frequencies" (@mikemccand; GitHub issue #8905; committed from a JIRA patch). It added TermFrequencyAttribute and made DefaultIndexingChain, FreqProxTermsWriterPerField and TermVectorsConsumerPerField honour it, in 14 files, none in lucene/memory. The one-per-token counting in storeTerms is older (current lines from LUCENE-7091, cf3eea264066, 2016), so this is an omission, not a regression.

Later commits widened the reach without touching it: 5844ed4ac953 (DelimitedTermFrequencyTokenFilter, 7.0.0), LUCENE-8197 (FeatureField, 7.4.0; main commit 710993435f36, backport 70cc7b68783), LUCENE-8031 (29e5b8abcee8, edited storeTerms, 8.0.0) and #15584 (DOCS_AND_CUSTOM_FREQS, 10.5.0; main commit 5158a52a082b, backport 3a55cc9ac5e; one MemoryIndex line changed). Lucene Monitor arrived in 8.2.0, but its single-document match uses MemoryIndex only since 8.6.0 (LUCENE-9314, 633ae90d7d9): in 8.2.0 to 8.5.2 match(Document) went through match(new Document[] {doc}) and the IndexWriter-based MultiDocumentBatch (read). 10.6.0 is unreleased; on branch_10_6 (2763db11b0a, 2026-10-24) storeTerms still counts one per token (source only, not run). MemoryIndex.java never mentions the attribute at any of the 65 local release tags 7.0.0 to 10.5.2; the local clone has no tags for 8.8.2 to 8.11.3, which were neither read nor run (8.8.1 and 8.11.4 on either side are affected).

Bug record

#

LFV-333, snapshot of 2026-10-28

Registry title
MemoryIndex ignores TermFrequencyAttribute, so FeatureField values and custom term frequencies are indexed as frequency 1 and their postings frequencies, term statistics, norms and scores differ from IndexWriter's (Lucene Monitor's single-document matching included)
Area
memory / MemoryIndex term inversion (custom term frequencies: FeatureField, TermFrequencyAttribute streams, DOCS_AND_CUSTOM_FREQS); reached in-tree through monitor single-document batches
Priority
Medium, rank 290: Since 7.0, MemoryIndex ignores custom term frequencies, so FeatureField scores collapse while matching is unchanged for the tested queries, a silent scoring error like the norms row LFV-105, which it follows.
Impact class
silent wrong results
Impact note
Anyone who puts a FeatureField (rank feature) or another field whose TokenStream sets TermFrequencyAttribute (a DOCS_AND_FREQS custom-frequency stream, DelimitedTermFrequencyTokenFilter input, or since 10.5.0 a DOCS_AND_CUSTOM_FREQS field) into a MemoryIndex, directly, through fromDocument/addField(IndexableField, Analyzer) or through Lucene Monitor's one-document batches (since 8.6.0), counts each such token as frequency 1, so FeatureField query scores collapse (linear 10.0 becomes 4.5918E-41; saturation or sigmoid with an explicit pivot such as 10, and log with scalingFactor 1, become exactly 0.0, which MemoryIndex.search documents as 'no match' and which makes Monitor's ScoringMatch drop the match) and term statistics, norms and BM25 scores of custom-frequency fields are wrong; for the tested queries, which documents match is unchanged; default settings otherwise, opt-in custom-frequency feature, any scale, every release checked since 7.0.0.
Summary
You add a document with FeatureField("features", "pagerank", 10f), or a tokenized DOCS_AND_FREQS field whose TokenStream sets TermFrequencyAttribute (for example DelimitedTermFrequencyTokenFilter on 'a|7'), to a MemoryIndex and expect its postings, statistics and scores to equal those of the same document in a one-document IndexWriter index, as they do for ordinary fields. Instead MemoryIndex.storeTerms never reads the attribute and counts every token as frequency 1: FeatureField.newLinearQuery scores 4.5918E-41 instead of 10.0, newSaturationQuery with the pivot 10 scores exactly 0.0 (MemoryIndex.search's 'no match' value) for a document that matches, and a term with custom frequency 7 reports freq 1, sumTotalTermFreq 1 and a lower BM25 score. Lucene Monitor inherits it (since 8.6.0): the same FeatureField document scores 10.0 in a two-document batch (IndexWriter path) and 4.5918E-41 when matched alone (MemoryIndex path).
