Hunspell: a REP, MAP, ICONV/OCONV, COMPOUNDRULE, BREAK or CHECKCOMPOUNDPATTERN table cut short at the end of the .aff file throws NullPointerException instead of a parse error

If a hunspell .aff file ends inside a REP, MAP, ICONV/OCONV, COMPOUNDRULE, BREAK or CHECKCOMPOUNDPATTERN table that holds fewer lines than its count, loading fails with a bare NullPointerException naming no table or line. A PFX/SFX table cut short gets ParseException: Premature end of rules for SFX A Y 2.

The finding in 30 seconds

#

Background: counted tables in a hunspell .aff file

#
  1. A hunspell dictionary is two files: the .dic word list and the .aff file with rules. Lucene's Dictionary reads both, for stemming (HunspellStemFilter) and spell checking.
  2. Many .aff rules come as counted tables: a header line says how many entry lines follow. REP 2 announces two replacement entries such as REP a b and REP c d. PFX/SFX (prefix and suffix rules), MAP, ICONV/OCONV, COMPOUNDRULE, BREAK and CHECKCOMPOUNDPATTERN work the same way.
  3. The parser reads exactly the announced number of lines after the header. If the file ends sooner, there is no next line: Java's readLine() returns null.

The finding, step by step

#
  1. Load a hunspell dictionary whose .aff file is two lines, REP 2 then REP a b: a replacement table that announces 2 entries, holds 1, and the file ends there (a cut-off download, or an entry deleted without fixing the count).
  2. You expect a parse error. Lucene documents that a wrong REP count gives a ParseException by default, and the same mistake in a suffix table (SFX A Y 2, then one rule) gives ParseException: Premature end of rules for SFX A Y 2.
  3. Instead the parser asks for the second entry, gets null because the file has ended, and splits it: NullPointerException: Cannot invoke "String.split(String)" because "line" is null. No table name, no line number, and HunspellStemFilterFactory's "Unable to load hunspell data!" wrapper is skipped.
  4. MAP, ICONV, OCONV, COMPOUNDRULE, BREAK and CHECKCOMPOUNDPATTERN fail the same way. Add one blank line after REP a b and the same mistake gives ParseException: Invalid syntax. Every release since 4.8.0 (ICONV/OCONV) or 8.9.0 (the other five) has it, up to 10.6.0 and main.

Who is affected

#

Users of the opt-in hunspell component, through any Dictionary constructor or HunspellStemFilterFactory, whose .aff file ends inside one of these six tables with fewer lines than announced: a cut-off download or a hand edit. Rare: a well-formed file never triggers it, and the damaged file is refused either way; only the error is wrong.

Mechanism, terms and numbers617 words

Several hunspell .aff directives are counted tables: a header such as REP 2 announces how many entry lines follow. Dictionary.readAffixFile reads those lines with reader.readLine() and passes the result straight to a string method, with no end-of-file check, for REP, MAP, CHECKCOMPOUNDPATTERN, COMPOUNDRULE, BREAK and ICONV/OCONV. When the file ends before the announced lines are all there, readLine() returns null and splitBySpace (or the CheckCompoundPattern constructor) throws NullPointerException: Cannot invoke "String.split(String)" because "line" is null. So the two-line affix file REP 2 / REP a b makes every Dictionary constructor throw an NPE that names no table and no line, and HunspellStemFilterFactory lets it escape unwrapped. The PFX/SFX parser has had the check since #12468 (9.8.0) and throws ParseException: Premature end of rules for ..., and since #14079 (10.2.0) the tolerateRepRuleCountMismatches() javadoc says a wrong REP count gives a ParseException by default. The unchecked reads date from each parser's first commit (ICONV/OCONV in 4.8.0, the other five in 8.9.0 and 9.0.0), and every release since, including 10.6.0, and main are affected. The file is refused either way; only the error is wrong. The same null check that PFX/SFX have, at the six table reads, fixes it.

Terms

#
  • Counted table: a header <DIRECTIVE> <count> followed by <count> entry lines, for example REP 2 / REP a b / REP c d (replacement suggestions), MAP (groups of similar characters), ICONV/OCONV (input and output conversions), COMPOUNDRULE, BREAK (word-break characters), CHECKCOMPOUNDPATTERN, and the prefix/suffix tables PFX/SFX.
  • Strict mode: the default. tolerateRepRuleCountMismatches() and tolerateAffixRuleCountMismatches() return false unless a subclass overrides them; the other five tables have no tolerant mode.

The bug

#
  1. readAffixFile reads the file line by line (Dictionary.java:350 at 645d4fe14a20), trims each line, skips blank ones (:355-356) and dispatches on the first word.
  2. Each counted-table branch parses the count and then reads that many lines itself, passing reader.readLine() straight on: REP splitBySpace(reader, reader.readLine(), 3, Integer.MAX_VALUE) (:411), MAP parseMapEntry(reader, reader.readLine()) (:419), CHECKCOMPOUNDPATTERN new CheckCompoundPattern(reader.readLine(), ...) (:462), COMPOUNDRULE and BREAK singleArgument(reader, reader.readLine()) (:621, :633), ICONV/OCONV splitBySpace(reader, reader.readLine(), 3) (:825).
  3. At end of file readLine() returns null. splitBySpace starts with line.split("\\s+") (:610) and CheckCompoundPattern's constructor with unparsed.split("\\s+") (CheckCompoundPattern.java:32); neither checks for null, so both throw NullPointerException.
  4. If any line follows the short table, even a blank one, the loop takes it as the missing entry (the blank-line skip of step 1 does not apply inside a table) and splitBySpace throws ParseException("Invalid syntax: ..."), or CheckCompoundPattern throws IllegalArgumentException("Invalid pattern: ..."). A following line that happens to fit the entry syntax is silently taken as an entry (read, not executed); that older leniency is not part of this bug.
  5. The PFX/SFX parser parseAffix already checks: if (line == null) { ... throw new ParseException("Premature end of rules for " + header, reader.getLineNumber()); } (:703-709, added by #12468).

Exposure and likelihood294 words
  • Who is hit. Users of the opt-in hunspell analysis component that load an .aff file through any Dictionary constructor (both sorting strategies) or HunspellStemFilterFactory (SPI name hunspellStem, for example in CustomAnalyzer). The failing strict mode is the default.
  • What it takes. One of the six tables must be the very last content of the file, with a count higher than the lines present: a download or copy cut off inside the table, or an entry deleted without lowering the count. The layout itself is ordinary: 17 of the 97 .aff files in Lucene's own hunspell test package end with one of these tables. A well-formed file never triggers it, so it is rated rare.
  • What happens. The load fails with an exception that does not say what is wrong or where: "line" is null means "your REP table announces more lines than the file has". HunspellStemFilterFactory.inform wraps only ParseException into its Unable to load hunspell data! [dictionary=...,affix=...] IOException (HunspellStemFilterFactory.java:115-118), so factory users do not get the affix file name either.
  • What does not happen. No wrong stems, no silent acceptance, no hang, nothing written: the load fails at once even when a table announces 2,000,000,000 lines, and writes no temp files; HunspellStemFilterFactory closes the streams it opened and removes its temp directory (a direct Dictionary caller closes its own streams, as the constructor javadoc asks). Well-formed files are not affected; REP's opt-in tolerant mode loads the truncated REP file, as documented.
  • Related, separate fix sites (not part of this bug). In default mode a REP count that is too low gives NumberFormatException from parseNum, which also contradicts the REP javadoc; and the COMPOUNDRULE count sizes an array up front (Dictionary.java:619), so an absurd count gives OutOfMemoryError.

Why it looks unintended

#
  • The javadoc of the REP count option: "False by default: a ParseException will happen."
  • PFX/SFX tables got exactly this check in #12468 (9.8.0), with an upstream test case that cuts an SFX table short at the end of the file.
  • One blank line after the short table already gives ParseException; the exception type should not depend on a trailing newline.
The full argument224 words
  • REP contract (10.2.0 and later). tolerateRepRuleCountMismatches(): "Whether incorrect REP rule counts will be silently ignored. False by default: a {@link ParseException} will happen." (Dictionary.java:1178-1184). #14079 (Robert Muir, 2024-12-18) added it "Similar to support for tolerating PFX/SFX count mismatches", with the PFX/SFX wording (:1170-1176).
  • PFX/SFX precedent. #12468 (Peter Gromov, 2023-07-29, "hunspell: check for aff file wellformedness more strictly", 9.8.0) added the readLine() == null check to parseAffix only (:703-709) and extended the existing TestDictionary.testInvalidData (:145-164) with five broken .aff files, each expected to give ParseException; one of them, broken_extraAffRule_last.aff, is an SFX table that announces 4 rules and holds 3 at the end of the file. Up to 9.7.0 that SFX case was an NPE too.
  • Constructors. @throws ParseException Can be thrown if the content of the files does not meet expected formats (:187, :204, :224). Nothing documents an NPE for a malformed file.
  • Position dependence. The same short table followed by a blank line gives ParseException: Invalid syntax: (executed).
  • Maintainer intent. LUCENE-3976 (#5049, 2012) was closed with the preference to find the exceptions malformed affix files cause and "fix them at their source", "on a per-error basis"; #12468 and #16919 (2026-10-28: in AffixCondition an internal AssertionError became an IllegalStateException, and Throwable is no longer caught) continue that work.
The devil's-advocate check172 words

The strongest case for "intended" (the study's intended-behaviour checkers, the tie-break and the refute-lens reviewer): the parser was never hardened and ParseException was never exhaustive. Other malformed content already escapes as NumberFormatException (non-numeric count), IllegalArgumentException (bad CHECKCOMPOUNDPATTERN, COMPOUNDRULE or FLAG line), ArrayIndexOutOfBoundsException (short PFX header) or IllegalStateException (duplicate ICONV mapping, documented at :1186-1192); "can be thrown" is permissive; the .aff file is trusted configuration and is refused either way.

Why it fails: it limits how strongly one may say "must be ParseException", not whether this is a defect. Nothing makes an NPE from dereferencing readLine()'s null intended: the REP javadoc names ParseException for this very mistake, the same class already handles the identical case for PFX/SFX, and a blank line after the table already gives ParseException. The REP javadoc is itself loose for a REP count that is too low (NumberFormatException), so it shows the intent, not a complete list of exceptions. Hence "wrong error" at low priority: the case is for a descriptive parse error.

Suggested fix

#

Recommended B. Check each table read for end of file and throw "Premature end of rules for <header>" (as PFX/SFX do)

Check each table read for end of file and throw ParseException("Premature end of rules for " + header, line), as PFX/SFX do: REP 2 / REP a b then gives Premature end of rules for REP 2, and likewise for the other five tables. B. Check each table read for end of file and throw "Premature end of rules for <header>" (as PFX/SFX do) (validated by the checks) (recommended)

#

A small helper readTableLine(reader, header) replaces the six reader.readLine() arguments (REP, MAP, CHECKCOMPOUNDPATTERN, COMPOUNDRULE, BREAK, ICONV/OCONV); parseCompoundRules and parseConversions get the header line as a new parameter. 26 lines added, 10 removed, all in Dictionary.java.

+  private static String readTableLine(LineNumberReader reader, String header)
+      throws IOException, ParseException {
+    String line = reader.readLine();
+    if (line == null) {
+      throw new ParseException("Premature end of rules for " + header, reader.getLineNumber());
+    }
+    return line;
+  }

   // REP, and the same at MAP, CHECKCOMPOUNDPATTERN, COMPOUNDRULE, BREAK, ICONV/OCONV:
-  String[] parts = splitBySpace(reader, reader.readLine(), 3, Integer.MAX_VALUE);
+  String[] parts =
+      splitBySpace(reader, readTableLine(reader, line), 3, Integer.MAX_VALUE);

Trade-offs

  • The load still fails, now with the same exception and wording as PFX/SFX: ParseException: Premature end of rules for REP 2 (and ... for MAP 2, ... for ICONV 2, ...), which names the table and carries a line number. HunspellStemFilterFactory then wraps it in its IOException("Unable to load hunspell data! [dictionary=...,affix=...]"), which names the affix file (the dictionary= part prints the stream objects, not file names).
  • It touches six call sites and two private signatures, so it conflicts textually with the open refactor PR #16422.
  • The reported offset is the reader's line number at end of file: 2 for REP 2 / REP a b with and without a final newline on JDK 25. #10121 (LUCENE-9079, 2019) records that an early-access JDK of the time numbered an unterminated last line differently, so do not assert an exact offset.
  • No API or format change; the only added work is one null check per table line while the file loads (not measured).

Downstream note

#

Products that load user-supplied hunspell dictionaries and catch only ParseException around the load, as HunspellStemFilterFactory does, see this NullPointerException escape instead.

How it was found

#

Non-formal: a static-analysis sweep (SpotBugs) flagged readLine() results that Dictionary uses without a null check; a search for the same pattern added the other tables, and a public-API JUnit test reproduced all six.

The method in full98 words

Method: non-formal (static analysis, then executed tests). On 2026-10-26 a hunt unit ran SpotBugs 4.10.5 (-effort:max -low) over the non-sandbox module jars. Its NP_DEREFERENCE_OF_READLINE_VALUE check flagged Dictionary.parseConversions and two reads in readAffixFile (REP and CHECKCOMPOUNDPATTERN). A grep for readLine() passed straight as a call argument, over all non-sandbox modules, added the COMPOUNDRULE, BREAK and MAP reads in the same file. A 7-test JUnit through the public constructor (six truncated tables plus a truncated-SFX control) failed 6 of 7; independent checkers then reproduced it with their own tests, and it was cut to the one-test REP repro.

LFV-345, snapshot of 2026-11-04

Registry title
Hunspell Dictionary throws NullPointerException instead of a parse error when a REP, MAP, ICONV/OCONV, COMPOUNDRULE, BREAK or CHECKCOMPOUNDPATTERN table at the end of the .aff file has fewer lines than its count
Area
analysis / hunspell (Dictionary affix-file parsing)
Priority
Low, rank 992: Hunspell throws NullPointerException instead of a parse error only for a truncated or hand-damaged .aff file whose last table is short, a loud wrong-error case in config parsing.
Impact class
wrong error
Impact note
Only applications that build a hunspell Dictionary (directly or through HunspellStemFilterFactory) from a malformed .aff file whose last content is a counted table with too few lines are hit, and they get a bare NullPointerException with no directive name or line number instead of the ParseException that the same mistake gives in a PFX/SFX table; the dictionary is refused either way, so there are no wrong results, no hang and nothing persisted, and a well-formed file never triggers it.
Summary
You load a hunspell dictionary whose .aff file ends with a REP, MAP, ICONV/OCONV, COMPOUNDRULE, BREAK or CHECKCOMPOUNDPATTERN table that announces more lines than it holds (for example 'REP 2' followed by a single REP line, as a cut-off download or a careless hand edit leaves it), and expect the parse error that the Dictionary constructors document (ParseException), which is what Lucene already throws for a PFX/SFX table cut short ('Premature end of rules') and, since 10.2.0, what the tolerateRepRuleCountMismatches() javadoc promises for a wrong REP count by default. Instead the parser passes the null that readLine() returns at end of file straight into a string method and throws NullPointerException ('Cannot invoke "String.split(String)" because "line" is null'), with no directive or line number, which also bypasses HunspellStemFilterFactory's 'Unable to load hunspell data!' wrapping of ParseException. The file is refused either way; only the error is wrong.
Introduced
Two introduction points, one root cause: each counted-table parser passed reader.readLine() to a string method without an end-of-file check from its first commit.
