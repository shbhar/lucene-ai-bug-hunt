BBoxStrategy's overlap-ratio explanation shows the document's ratio where the query's ratio belongs

Explaining a BBoxStrategy overlap-ratio score shows the document's overlap ratio (1.0) under queryFactor, where the query's ratio (0.125) belongs. The score, 0.5625, is right; the one-token slip dates from a 2015 API rewrite and is in every release since 5.2.0.

The finding in 30 seconds

#

Background: overlap-ratio relevance and explain

#
  1. BBoxStrategy (the spatial-extras module) indexes one rectangle per document. makeOverlapRatioValueSource(queryBox, p) turns the overlap between that rectangle and a query rectangle into a relevance score.
  2. The score mixes two shares of the overlap: queryRatio, the part of the query box it covers, and targetRatio, the part of the document box it covers, weighted p and 1 - p.
  3. IndexSearcher.explain or DoubleValuesSource.explain returns a tree that shows how a score was computed: one node per term, with the values that went into it as children.

The finding, step by step

#
  1. Index one document whose box is x 10..30, y 0..10 (area 200) with BBoxStrategy, and score it with makeOverlapRatioValueSource for the query box x 0..40, y -20..20 (area 1,600) and weight 0.5. The document box lies inside the query box, so the overlap is 200.
  2. The score is queryFactor + targetFactor: queryRatio = 200 / 1,600 = 0.125 times 0.5 gives 0.0625, and targetRatio = 200 / 200 = 1.0 times 0.5 gives 0.5. Lucene scores the document 0.5625, which is correct.
  3. You call explain() and expect the queryFactor node (0.0625) to show its ratio, 0.125, next to the query box's area, 1,600.
  4. Instead it shows 1.0 = ratio: the document's ratio, the same number as under targetFactor. The query's ratio appears nowhere in the tree.
  5. Why: line 255 of BBoxOverlapRatioValueSource passes targetRatio where queryRatio belongs: the same line as the targetFactor one, written in the 2015 Explanation API rewrite (LUCENE-6446), where the code before it had queryRatio. 5.1.0 still showed the right number.

Who is affected

#

Anyone who reads explain() output for BBoxStrategy's overlap-ratio relevance, an opt-in, experimental feature of the spatial-extras module, for example while tuning spatial ranking; by code reading, Solr's BBoxField with score=overlapRatio builds the same class. Wrong whenever the two ratios differ, e.g. for boxes that overlap by a positive area and differ in area; scores, ranking and matching are correct.

Mechanism, terms and numbers533 words

BBoxStrategy.makeOverlapRatioValueSource(queryBox, p) scores a document by how much its box and the query box overlap: score = queryRatio x p + targetRatio x (1 - p), where queryRatio is the overlap divided by the query box's area and targetRatio the overlap divided by the document box's area, as the class javadoc defines it. The score is computed correctly, but the explanation puts targetRatio under the queryFactor node (BBoxOverlapRatioValueSource.java:255), next to the query box's area, so a match tree shows the document-side ratio twice and the query-side ratio never. For a 20 x 10 document box inside a 40 x 40 query box at p = 0.5 it prints 1.0 = ratio under 0.0625 = queryFactor, where queryRatio is 0.125; the score 0.5625 is right. The slip came from the mechanical Explanation API rewrite LUCENE-6446 in 2015: 5.1.0 shows queryRatio, every release from 5.2.0 to 10.6.0 and main shows targetRatio (113 releases executed: a 112-release sweep 4.10.0-10.5.2, plus 10.6.0). Changing the one token back to queryRatio fixes it and passes the whole spatial-extras test suite. Low priority: explain output only, in an opt-in, experimental relevance function.

Mechanism (Lucene main 645d4fe14a20)

#
  • The class javadoc defines queryRatio = intersectionArea / queryArea, queryFactor = queryRatio * queryTargetProportion, targetFactor = targetRatio * (1 - queryTargetProportion) and score = queryFactor + targetFactor (BBoxOverlapRatioValueSource.java:39-48).
  • score(Rectangle, AtomicReference<Explanation>) computes the two ratios (:208-230) and the score exactly that way (:236-238).
  • Only when a holder is passed (exp != null) does it build the tree (:240-262). The queryFactor node is Explanation.match((float) queryFactor, "queryFactor", Explanation.match((float) targetRatio, "ratio"), Explanation.match((float) queryArea, "area of " + queryExtent ...)) (:252-256): line 255 passes targetRatio. The targetFactor node (:257-261) passes targetRatio too, which is correct there.
  • The scoring path, BBoxSimilarityValueSource.getValues, calls score(rect, null) (BBoxSimilarityValueSource.java:75), so the tree is never built while scoring. Only explain (:112-129) passes a holder; FunctionScoreQuery's weight explain reaches it (FunctionScoreQuery.java:175-190).

The tree on main, for the repro's boxes

(The <- comment is added; the rest is the program's output.) With the fix the node shows 0.125 = ratio and every other line is identical.

Neither ratio needs to be 1: for a partial overlap (query x 0..20, y 0..10; document x 10..40, y 5..15; p = 0.3) the tree shows 0.16666667 = ratio (targetRatio) under 0.075 = queryFactor, where queryRatio is 0.25. It is invisible only when the two ratios are equal: for boxes with an area and no minimum side length, both ratios divide the same overlap, so they are equal exactly when the overlap is zero (boxes that only touch: 0.0 = ratio under both factors) or the document box has the same area as the query box. With a minimum side length the padded areas decide, and point and line boxes use their own ratios (:208-230).

Exposure and likelihood247 words
  • Who. Callers of IndexSearcher.explain (for example on a FunctionScoreQuery) or DoubleValuesSource.explain on a source from makeOverlapRatioValueSource or the public BBoxOverlapRatioValueSource constructor. They are told the wrong reason for a score: the query-side share of the overlap is never shown.
  • Default or opt-in. Opt-in: BBoxStrategy and BBoxOverlapRatioValueSource are @lucene.experimental in the optional spatial-extras module, and explain is a diagnostic call. Everything else is default (SpatialContext.GEO, BBoxStrategy.newInstance, codec, IndexWriterConfig, searcher). One document is enough.
  • Scale. Every explained hit whose two ratios differ, which for boxes with an area (and no minimum side length) means every document box that overlaps the query box by a positive area and whose area differs from the query box's. In a random sample (including point and line boxes), 655 explained hits got a full tree (boxes that intersect, touching included) and 396 of them showed a wrong value.
  • Downstream (code reading, not run). Solr's BBoxField (score=overlapRatio) and its legacy BBoxStrategy copy construct this class, so Solr's debug explain output would show the same number. A code search for the class name in the elastic and opensearch-project organisations found no use.
  • Not affected. Scores, sort values, ranking, matching and the index: main and the fix gave identical ranked lists and score bits over 60 queries x 300 documents.
  • Likelihood: plausible. A reader of the tree meets it at once, but few read it closely; no report of it was found, although it has been there since 5.2.0 (2015).

Why it looks unintended

#
  • The javadoc defines queryFactor = queryRatio * queryTargetProportion; targetRatio plays no part in it.
  • The 2014 code showed queryRatio here; the 2015 change was an API-only rewrite that never discussed spatial code.
  • Lucene fixes wrong explain values as bugs, e.g. GITHUB#13691, an explain-only fix in SigmoidFunction (9.12.0).
The full argument205 words
  • The contract. BBoxOverlapRatioValueSource.java:39-48 defines the formula and :236 computes it. Explanation.match documents its details as "sub explanations that contributed to this explanation" (Explanation.java:27-33).
  • The node is about the query side. Its other child is area of <query box>; the targetFactor node mirrors it with targetRatio and area of <document box>.
  • History. The original code (trunk 7e0aff8dabc, LUCENE-5714/LUCENE-5779, by dsmiley, 2014; backported to branch_4x as c608265684c, first released in 4.10.0) had e.addDetail(new Explanation((float)queryRatio, "ratio")) under queryFactor. LUCENE-6446 (c6821e1a194, by jpountz, 2015) replaced it with Explanation.match((float)targetRatio, "ratio"), the same line as in the targetFactor block. Its issue (#7505) and its 16 comments discuss the API change, and none of them mentions spatial code, BBox or the ratios.
  • The tree was meant to be read. On LUCENE-7737 (#8788, 2017) dsmiley called this explanation "very very useful" when it was at risk of being lost. LUCENE-7741 (#8792, fb24d451cc9, 2017-05-10) added DoubleValuesSource.explain in response, so the explanation was kept when the class moved (the LUCENE-7737 commit 2f2e00ffe23); it was never removed. The captured discussion does not examine the ratio values.
  • Precedent. lucene/CHANGES.txt lists explain-only value errors under Bug Fixes: GITHUB#13691 (SigmoidFunction exponent, 9.12.0) and LUCENE-6042 (CustomScoreQuery explain, 5.0.0).
The devil's-advocate check123 words

The strongest case for "not a bug": both classes are @lucene.experimental; Explanation is an Expert diagnostic API; the child is only labelled "ratio", so it does not say which ratio; the bbox tree is not a strict expression tree (the proportion sits under IntersectionArea); no test checks the explanation; the score is right; and no complaint was found in eleven years.

Why it fails: experimental marks API stability, not a licence for wrong output. The javadoc names the quantity, the sibling node shows the pattern, the 2014 code showed queryRatio, and the change came from a refactoring that set out to change no displayed value. The rest argues for Low priority, which is how it is classed, not for intent.

Suggested fix

#

Recommended Show queryRatio under queryFactor (one token)

Pass queryRatio instead of targetRatio to the ratio child of the queryFactor node (BBoxOverlapRatioValueSource.java:255, one token). Scores and the tree's shape do not change. The repro and the whole spatial-extras test suite (118 tests) pass, with assertions on and off.

             Explanation.match(
                 (float) queryFactor,
                 "queryFactor",
-                Explanation.match((float) targetRatio, "ratio"),
+                Explanation.match((float) queryRatio, "ratio"),
                 Explanation.match((float) queryArea, "area of " + queryExtent + minSideDesc)),
