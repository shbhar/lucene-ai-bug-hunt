TemporalMergePolicy with maxThreshold Integer.MAX_VALUE: forceMergeDeletes() throws OutOfMemoryError

TemporalMergePolicy.setMaxThreshold accepts Integer.MAX_VALUE as "no limit", but forceMergeDeletes() then sizes a list to that many slots and throws OutOfMemoryError: Requested array size exceeds VM limit, even for two 2-document segments, and expunges nothing. Affects 10.5.0 to 10.6.0 and main; a one-line capacity bound fixes it.

The finding in 30 seconds

#

TemporalMergePolicy groups segments into time windows and merges at most maxThreshold of them at once per window. For forceMergeDeletes() it collects each window's segments into batches of maxThreshold, and it allocates the batch list at that full size before adding a single segment.

  1. Configure new TemporalMergePolicy().setTemporalField("ts").setMaxThreshold(Integer.MAX_VALUE). The setter only checks that the value is at least minThreshold (4), and its javadoc says larger values merge more aggressively. Natural merges and forceMerge(1) work with it.
  2. Index 4 documents with the same timestamp, committing after every 2: one time window now holds two 2-document segments. Delete one document in each, 50% of each segment, above the default forceMergeDeletesPctAllowed of 10%.
  3. Call forceMergeDeletes(). You expect one merged segment with 0 deleted documents, which is what the default maxThreshold of 8 gives for the same index.
  4. Instead it throws java.lang.OutOfMemoryError: Requested array size exceeds VM limit (on the tested OpenJDK 25 HotSpot JVM, with a 256 MB and a 4 GB heap), with assertions on and off. Nothing is merged and both deletes stay; the writer stays usable unless the JVM is set to exit on OutOfMemoryError.
  5. Why: for each window with 2 or more such segments, buildSequentialMerges first creates new ArrayList<>(maxThreshold) (TemporalMergePolicy.java:957), an array of 2,147,483,647 slots for 2 segments, which the JVM refuses outright.

Who is affected

#

Only applications that opt in to the experimental TemporalMergePolicy (new in 10.5.0), set maxThreshold too large to allocate (Integer.MAX_VALUE at any heap size; huge finite values on a small heap) and call forceMergeDeletes(). Every such call fails once one window has two segments with enough deletes. The deletes stay; a JVM with -XX:+ExitOnOutOfMemoryError exits.

Mechanism, terms and numbers492 words

TemporalMergePolicy (@lucene.experimental, first released in 10.5.0) merges segments only within time windows, at most maxThreshold at once. setMaxThreshold rejects only values below minThreshold (TemporalMergePolicy.java:246-249 at 5adff78bb168) and says "Larger values allow more aggressive merging", so Integer.MAX_VALUE is accepted, and natural merges and forceMerge(1) work with it. But IndexWriter.forceMergeDeletes() sends every time window with two or more segments over forceMergeDeletesPctAllowed to buildSequentialMerges, which first allocates new ArrayList<>(maxThreshold) (:957). The JVM refuses an array of 2^31-1 slots, so the call throws java.lang.OutOfMemoryError: Requested array size exceeds VM limit (on the tested HotSpot JVM at any heap size), for two 2-document segments, before any merge is registered, and the deletes stay. The writer is not tragic and stays usable, unless the JVM runs with -XX:+ExitOnOutOfMemoryError, which then exits. Huge finite values fail too when the heap is too small. A one-line fix bounds the capacity by the number of candidates.

The bug, step by step

#
  1. Setter (TemporalMergePolicy.java:245-252 at 5adff78bb168): setMaxThreshold throws only when maxThreshold < minThreshold (:246-249; minThreshold defaults to 4, :103). Integer.MAX_VALUE is stored.
  2. Forced-deletes merges (findForcedDeletesMerges, :528-597): segments whose share of deleted documents is strictly above forceMergeDeletesPctAllowed (default 10, :111; the test at :555) are grouped by time window (:568; the window comes from each segment's min and max LongPoint value of the temporal field, read from the segment files, :615-622, :675-707, so equal timestamps share a window); windows with fewer than two are skipped (:573); the rest go to buildSequentialMerges(bucketSegments) (:582).
  3. Batching (buildSequentialMerges, :951-978): List<SegmentCommitInfo> batch = new ArrayList<>(maxThreshold); (:957) runs before any candidate is added. Then each candidate is added, a merge is emitted when batch.size() == maxThreshold (:961), and a final merge takes any rest of two or more (:970).
  4. The JVM limit: new ArrayList<>(Integer.MAX_VALUE) asks for an Object[] of length 2^31-1, above HotSpot's maximum array length, so the JVM throws OutOfMemoryError: Requested array size exceeds VM limit without trying to allocate. On the tested OpenJDK 25 HotSpot JVM the heap size does not matter (independent checks got the same Error with a 256 MB and a 4 GB heap); other JVMs were not tested.
  5. To the caller: IndexWriter.forceMergeDeletes asks the policy inside synchronized (this) before registering anything (IndexWriter.java:2358-2359), so the Error propagates and no merge runs.

Every other use of maxThreshold in the merge code is a bound or a comparison: Math.min at :495 and :935, loop and equality bounds at :878, :890 and :961 (the remaining uses are the field, the setters' checks and store, the getter and toString: :108, :191, :246, :250, :260, :605). That is why natural merges and forceMerge(1) work with the same setting; :957 is the only place that turns the value into an allocation size.

Exposure and likelihood352 words
  • Opt-in only. TemporalMergePolicy is not a default and is @lucene.experimental (:94); the default maxThreshold is 8 (:108). forceMergeDeletes() is documented as "often a horribly costly operation; rarely is it warranted" (IndexWriter.java:2413).
  • No scale needed. Two 2-document segments in one window trigger it, on every such call (a second call on the same writer fails again; independent check).
  • Effect. An Error, not an IOException, so a caller that catches Exception does not catch it. No merge runs and the deletes stay until a later merge picks up those segments: a natural merge looks at a window only once it holds at least minThreshold (default 4) segments (:833-835), so for a two-segment window it may never come, while an explicit forceMerge(1) does merge them (independent side check). In a JVM that is not set to exit on OutOfMemoryError, the writer is not tragic: getTragicException() is null, isOpen() is true, and it accepts more documents and a commit (independent side checks). A JVM run with -XX:+ExitOnOutOfMemoryError exits with code 3 (independent checks: a plain new ArrayList<>(Integer.MAX_VALUE), and the full forceMergeDeletes() path). A JVM with -XX:+HeapDumpOnOutOfMemoryError writes a heap dump on the first such Error (HotSpot dumps once per JVM: three failing calls in one JVM wrote one dump). Lucene's own test JVM, which uses that flag, wrote one of about 50 MB per run here; in a service the dump size follows the heap in use (not measured).
  • Not affected. Natural merges and forceMerge(1) with the same setting, and every maxThreshold small enough to allocate (such as the default 8).
  • Huge finite values. :957 sizes the list by any value. On the tested JVM, with the repro's index: Integer.MAX_VALUE - 1 gives the same "Requested array size exceeds VM limit" with a 256 MB and a 4 GB heap; Integer.MAX_VALUE - 2 and - 8 give OutOfMemoryError: Java heap space even with 4 GB; 10^8 and 10^9 give Java heap space with 256 MB and work with 4 GB; 8 works with both (independent check). Only values near Integer.MAX_VALUE fail whatever the heap.

Why it looks unintended

#
  • The setter checks only a lower bound and says "Larger values allow more aggressive merging"; there is no documented "no limit" value.
  • Everywhere else in the merge code maxThreshold is a bound, so natural merges and forceMerge(1) work with it (executed); only :957 allocates by it.
  • Upstream fixed the same shape before: LUCENE-4938 (min(maxDoc, n), tested with Integer.MAX_VALUE) and LUCENE-504.
The full argument198 words
  • Contract. setMaxThreshold (TemporalMergePolicy.java:234-244): "Sets the maximum number of segments to merge at once within a time window. Larger values allow more aggressive merging (reducing segment count faster) but increase the cost of individual merge operations." and "Must be at least equal to setMinThreshold". Only that lower bound is enforced (:246-249); values below minThreshold are rejected, so there is no documented "no limit" value. A finite value above any segment count a window can reach would act as one, but nothing says how large is safe.
  • Idiom. Lucene itself uses Integer.MAX_VALUE as a merge-policy "no limit": LogMergePolicy.DEFAULT_MAX_MERGE_DOCS = Integer.MAX_VALUE (LogMergePolicy.java:57).
  • Tests and review. No javadoc, CHANGES or MIGRATE entry mentions the pre-allocation. The upstream tests use maxThreshold 3, 4 and 10. The review of #15620 (17 issue comments, 21 review comments, 14 reviews) discussed the default thresholds, never an upper bound or the batch capacity.
  • Precedent. LUCENE-4938 (#6002, 2013): IndexSearcher pre-allocated by n when sorting and was fixed with min(maxDoc, n); Robert Muir asked for "simple tests ... that tests with Integer.MAX_VALUE". LUCENE-504 (15743fc1793, 2009): FuzzyQuery's queue was changed to grow dynamically "to support BooleanQuery.maxClauseCount(Integer.MAX_VALUE) without exhausting all memory".
The devil's-advocate check163 words

The strongest case for "intended": no index has 2^31 segments in one window, so Integer.MAX_VALUE is not a real segment count; the javadoc warns that larger values cost more; the class is experimental and new; forceMergeDeletes is rarely warranted; and the failure is loud. So it is an absurd setting and the user's problem.

Why it fails: the setter accepts the value, invites larger values and documents no other "no limit" value; the same setting works on the other merge paths (natural merges and forceMerge(1), executed); the failure is an OutOfMemoryError from two tiny segments, not a validation error that names the argument; and upstream treated the same pre-size-by-a-huge-limit shape as a bug (LUCENE-4938, LUCENE-504). Having no upper bound is not a promise that every extreme value is cheap, but a list for two segments should not need 2^31-1 slots: what remains is mainly an impact argument, which is why it is Low. Verdict: a real Low bug with a one-line fix.

Suggested fix

#

Recommended A. Bound the initial capacity by the number of candidates (validated)

Size the batch list by what it can hold: new ArrayList<>(Math.min(maxThreshold, candidates.size())) at TemporalMergePolicy.java:957. The repro passes with assertions on and off, and the existing TemporalMergePolicy tests pass. A plain new ArrayList<>() would also avoid it (not run); an upper bound in the setter is not recommended.

     MergeSpecification spec = null;
-    List<SegmentCommitInfo> batch = new ArrayList<>(maxThreshold);
+    List<SegmentCommitInfo> batch = new ArrayList<>(Math.min(maxThreshold, candidates.size()));

A. Bound the initial capacity by the number of candidates (validated) (recommended)

#

One line at TemporalMergePolicy.java:957. A batch never holds more than min(maxThreshold, candidates.size()) segments, so nothing else changes.

     MergeSpecification spec = null;
-    List<SegmentCommitInfo> batch = new ArrayList<>(maxThreshold);
+    List<SegmentCommitInfo> batch = new ArrayList<>(Math.min(maxThreshold, candidates.size()));

Trade-offs

None in behaviour: the capacity is only a sizing hint, and the merges emitted are the same for every maxThreshold that worked before.

What the checks validated

  • The repro passes with assertions on and off (gradle, seed 5EED1213).
  • With the fix, TestTemporalMergePolicy (7 tests) and TestTemporalMergePolicyAcrossBuckets (4 tests) pass, 0 failures, with assertions on and, in a separate run, off.
  • :lucene:core:checkGoogleJavaFormat passes with the fix and the test file.
  • Independent checks shadowed the same change and got the same result with their own tests.

B. No capacity hint

#

new ArrayList<>(); the list grows as needed and is reused after clear().

Trade-offs

Equally small; a few extra array copies for windows with more than 10 candidates. Not run for this doc.

C. An upper bound in setMaxThreshold (not recommended)

#

Reject values above some limit with an IllegalArgumentException.

Trade-offs

It rejects a "no limit" setting that the other merge paths handle (natural merges and forceMerge(1), executed), and any bound is arbitrary; unless the bound is low, large finite values below it would still over-allocate.

Downstream note

#

A product that lets its users set this merge-policy threshold and passes Integer.MAX_VALUE through would see every forced-deletes call that finds two eligible segments in one time window fail; a modest value such as the default 8 avoids it.

How it was found

#

A proof-obligation audit of TemporalMergePolicy's setMaxThreshold contract: the setter admits every value from minThreshold up to Integer.MAX_VALUE, so every path that uses maxThreshold must work for all of them, and buildSequentialMerges allocates by it, which fails for the top value. A one-method JUnit test on the public API then witnessed it.

The method in full73 words

The obligation came from the setter's own validation (lower bound only) and its javadoc ("Larger values allow more aggressive merging"), checked against each use of the field in the class: every use is a bound or a comparison except one, :957, which is an allocation size. The witness test (an earlier, equivalent variant of the repro above) fails on main with assertions on and off and on the 10.6.0 and 10.5.0 jars.

You expect the two segments to be merged into one with no deleted documents left, as happens with the default maxThreshold of 8, and as natural merges and forceMerge do with the same setting. Instead buildSequentialMerges creates its batch list with new ArrayList<>(maxThreshold) before adding anything, so forceMergeDeletes() throws java.lang.OutOfMemoryError: Requested array size exceeds VM limit at any heap size, no merge is registered and the deleted documents stay.
