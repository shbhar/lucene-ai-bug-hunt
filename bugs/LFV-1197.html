InitializedHnswGraphBuilder.fromGraph allows null initializedNodes, but addGraphNode then throws NullPointerException

InitializedHnswGraphBuilder.fromGraph says its initializedNodes bit set "can be null if not tracking", but the returned builder's addGraphNode reads that bit set without a null check, so the first vector you add throws NullPointerException. Lucene's own merges never insert through such a builder; 10.4.0 to 10.6.0 and main have it.

The finding in 30 seconds

#

fromGraph copies a graph into a builder; an optional bit set marks the copied nodes so that later addGraphNode calls skip them. With null there is no bit set, but addGraphNode still looks the new node up in it and throws.

Background: continuing an HNSW graph

#
  1. An HNSW graph is Lucene's index for kNN vector search: each vector is a node, linked to a few nearby nodes.
  2. InitializedHnswGraphBuilder.fromGraph copies an existing graph into a new builder, so more vectors can be inserted with addGraphNode instead of rebuilding the graph from scratch. It was written for segment merges, but Lucene's own merges now use it only to copy or repair a graph; their insertions go through other builders.
  3. Its initializedNodes bit set marks the copied nodes, so that inserting them again is skipped.

The finding, step by step

#
  1. Take two 2-d vectors, [1, 0] and [0, 1], and build an HNSW graph of the first one only: 1 node.
  2. Copy it into a new builder with InitializedHnswGraphBuilder.fromGraph(scorer, 100, 42L, graph, new int[] {0}, null, 2). The null is the bit set of copied nodes, which the javadoc allows: "can be null if not tracking".
  3. Call addGraphNode(1). You expect a 2-node graph, which is what you get when you pass a bit set marking node 0 instead of null.
  4. Instead it throws NullPointerException: Cannot invoke "org.apache.lucene.util.BitSet.get(int)" because "this.initializedNodes" is null, with assertions on and off. The graph keeps 1 node.
  5. Why: addGraphNode first asks the bit set whether the node was copied, so it can skip it, and never checks that there is a bit set (InitializedHnswGraphBuilder.java:489). The same method in HnswConcurrentMergeBuilder's private worker class does check.

Who is affected

#

Only code that calls the experimental fromGraph itself with a null bit set and then inserts, such as a custom graph merger or an offline graph tool. IndexWriter, merges and search never insert through such a builder. It fails loudly on the first insertion, before the graph changes; passing a bit set of the copied nodes avoids it.

Mechanism, terms and numbers431 words

InitializedHnswGraphBuilder.fromGraph copies an existing HNSW graph into a new builder so that more vectors can be inserted. Its initializedNodes bit set marks the copied nodes, which later addGraphNode calls skip; the @param says it "can be null if not tracking" (InitializedHnswGraphBuilder.java:109-110 at 5adff78bb168), and the factory returns the builder "ready for additional operations" (:99-101). But addGraphNode starts with if (initializedNodes.get(node)) return; and no null check (:489), so with null the first insertion throws NullPointerException, with assertions on and off, before the graph changes. #15003 (first released in 10.4.0) added the "can be null" wording and the first in-tree null caller, initGraph, which never inserts, but left the older read unguarded; the same override in HnswConcurrentMergeBuilder's private ConcurrentMergeWorker already guards it (HnswConcurrentMergeBuilder.java:561). Lucene's own merges never insert through a builder created with null, so only code that uses this @lucene.experimental builder directly is hit. A one-line guard fixes addGraphNode; rejecting null and correcting the javadoc is the alternative. Priority Low.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/hnsw/)

#
  1. Null is documented as legal. @param initializedNodes bit set marking which nodes are already initialized (can be null if not tracking) (InitializedHnswGraphBuilder.java:109-110). Both public overloads (:120, :150) pass it unchecked to the private constructor, which stores it (:232).
  2. The bit set is a skip list for insertion. Field javadoc: the copied nodes "will be skipped during subsequent addGraphNode(int) calls" (:58-61).
  3. The skip check has no null check (the fix site). addGraphNode (:487-493) begins if (initializedNodes.get(node)) { return; } (:489), so a null bit set throws before super.addGraphNode(node) touches the graph. build(maxOrd) reaches the same line through addVectors (HnswGraphBuilder.java:208).
  4. The sibling guards it. The private ConcurrentMergeWorker nested in HnswConcurrentMergeBuilder (HnswConcurrentMergeBuilder.java:493) has the same override as if (initializedNodes != null && initializedNodes.get(node)) (HnswConcurrentMergeBuilder.java:559-565).
  5. Why Lucene itself never hits it. The in-tree null callers never insert: initGraph passes null (:203) and returns only builder.getGraph() (:206); the package-private pruneGraph (:249-270) passes null (:263) and is used for repair and rebalancing only; ConcurrentHnswMerger builds its own FixedBitSet for insertion (ConcurrentHnswMerger.java:78).

In the repro the copied graph has 1 node and room for 2. With a bit set marking node 0, addGraphNode(1) inserts node 1 and the graph has 2 nodes, linked to each other (an executed control with the repro's exact inputs, assertions on and off). With null it throws at :489 and the graph keeps 1 node.

Exposure and likelihood161 words
  • Who. Code that calls the public fromGraph with initializedNodes = null, as the javadoc allows, and then inserts with addGraphNode (or build). The class is public and final in an exported package (InitializedHnswGraphBuilder.java:56, module-info.java:50) and tagged @lucene.experimental (:54).
  • Default vs opt-in. Not on any default path: IndexWriter, serial and concurrent merges and search never insert through a builder created with null.
  • Effect. One NullPointerException on the first insertion, with only the JVM's null-dereference text and no Lucene error message. The read is the first statement of addGraphNode(int), so it throws before super.addGraphNode touches the graph: the graph stays as copied, and the caller gets an exception, not a wrong or partial graph.
  • Workaround. Pass a bit set of the copied ordinals, as Lucene's own tests do (HnswGraphTestCase.java:700-715, :737-754).
  • Scale and likelihood. One copied node and one insertion are enough. Rare: the documented searches found no report since 10.4.0.

Why it looks unintended

#
  • The public fromGraph javadoc allows null ("can be null if not tracking") and returns the builder "ready for additional operations"; the class advertises "incremental addition of new nodes".
  • HnswConcurrentMergeBuilder's private worker has the same override and treats null as "nothing to skip".
  • The exception is incidental: no explicit check, no Lucene error message, no test or discussion expecting it.
The full argument172 words
  • Contract. @param initializedNodes ... (can be null if not tracking) (InitializedHnswGraphBuilder.java:109-110) places no limit on later use; the factory returns the builder "ready for additional operations" (:99-101); the class javadoc lists "Allows incremental addition of new nodes while preserving initialized nodes" (:45); HnswBuilder.addGraphNode "Inserts a doc with a vector value to the graph" (HnswBuilder.java:39).
  • Sibling. The same override in HnswConcurrentMergeBuilder's private ConcurrentMergeWorker guards the same read (HnswConcurrentMergeBuilder.java:493, :561).
  • Tests. Every upstream fromGraph test passes a bit set (HnswGraphTestCase.java:701, :738); no test passes null or expects an exception.
  • History. The read dates from #12657 (ea272d0eda1 on main; shipped in 9.9.0 through its branch_9x copy 18bb826564b), when the @param read "a bitset of nodes that are already initialized in the initializerGraph", so null was caller misuse. #15003 (ef10476d98a, 10.4.0) added "(can be null if not tracking)" and the first null caller without guarding the read; its body, comments and review comments never discuss null tracking.
The devil's-advocate check160 words

The strongest case for "intended": the same commit wrote the initGraph javadoc, "create a fully initialized on-heap HNSW graph without tracking initialized nodes. This is useful when you just need the resulting graph structure without planning to add additional nodes incrementally" (InitializedHnswGraphBuilder.java:171-173). MergingHnswGraphBuilder uses null to mean "all nodes should be already initialized" and then inserts nothing (MergingHnswGraphBuilder.java:89-90, :167). And with the guard alone, build(maxOrd) on a builder created with null would quietly re-insert the copied nodes. So "not tracking" may have meant "copy only".

Why it fails: that sentence describes initGraph's use case, not a precondition of the public fromGraph, whose @param is what a caller reads; for a new node "not tracking" has one obvious meaning, which HnswConcurrentMergeBuilder's worker implements. It does make a reject-null fix as reasonable as the guard. The devil's-advocate verifier judged that it weakens but does not refute the claim; the cross-model reviewer rated it moderate.

Suggested fix

#

Recommended Skip the bit-set lookup when there is no bit set (fix A)

Guard the read as HnswConcurrentMergeBuilder does: if (initializedNodes != null && initializedNodes.get(node)) (one line). The repro then passes with assertions on and off, and all 139 tests of the HNSW package and TestHnswMergeAbort pass. Alternative: make null an explicit copy-only mode that rejects insertion.

  @Override
  public void addGraphNode(int node) throws IOException {
    if (initializedNodes != null && initializedNodes.get(node)) {
      return;
    }
    super.addGraphNode(node);
  }

Skip the bit-set lookup when there is no bit set (fix A) (validated by the checks) (recommended)

#

In InitializedHnswGraphBuilder.addGraphNode (:489), test for null first, exactly as HnswConcurrentMergeBuilder.java:561 does. Null then means "nothing to skip"; a sentence in the @param ("if null, no node is skipped") would make that explicit.

  @Override
  public void addGraphNode(int node) throws IOException {
    if (initializedNodes != null && initializedNodes.get(node)) {
      return;
    }
    super.addGraphNode(node);
  }

Trade-offs

With the guard alone, build(maxOrd) on a builder created with null no longer throws but re-inserts the copied nodes and replaces their copied level-0 neighbour arrays (the devil's-advocate verifier ran build(3) after copying a 2-node graph: 3 nodes, each linked to the other two at level 0, with node 0's copied neighbour array replaced, so the copy is wasted). If open PR #16815 lands first, its new fromGraph overload needs the same care.

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, seed DEADBEEF: the repro fails without the fix (assertions on and off) and passes with it (assertions off).
  • With the fix and assertions on: every org.apache.lucene.util.hnsw test (11 classes plus the repro, including TestHnswFloatVectorGraph, TestHnswByteVectorGraph and TestHnswFloat16VectorGraph) and TestHnswMergeAbort: 139 tests, 0 failures, 3 skipped. checkGoogleJavaFormat passes. The full core suite was not run, and only OpenJDK 25.0.3 on Linux aarch64 was used.
  • Earlier: the hunt's shadowed runs of the same diff pass the repro (assertions on and off) and TestHnswFloatVectorGraph (32 tests); the cross-model reviewer's test and its bit-set control both pass with it.

Make null an explicit copy-only mode (not run)

#

Keep null for the internal copy-only paths (initGraph, pruneGraph), but throw IllegalStateException("builder was created without initializedNodes; it cannot add nodes") in addGraphNode when the bit set is null, or require a non-null bit set in the public fromGraph and give initGraph its own path; correct the @param to match.

Trade-offs

Matches the initGraph javadoc and MergingHnswGraphBuilder's reading of null, and keeps build() from silently re-inserting. It turns the documented call into a documented error instead of making it work, and is a slightly larger change. An independent fact check of the brief (OpenAI GPT-5.6) preferred this fix as the default, because it makes the copy-only reading explicit and does not silently change what build(maxOrd) does. The regression test would assert the IllegalStateException.

Downstream note

#

Downstream products are affected only where their own code builds graphs with fromGraph and a null bit set; documents, vectors and queries cannot make Lucene take this path.

How it was found

#

A proof-obligation audit of InitializedHnswGraphBuilder's contract (the fromGraph javadoc and addGraphNode): the null initializedNodes that the javadoc allows must leave the builder usable for addGraphNode. It does not, because addGraphNode reads it unguarded; a public-API JUnit test then witnessed the exception.

The method in full155 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder treated the fromGraph javadoc and the field and class javadoc as obligations on the returned builder: the null that the @param allows must be safe for a later addGraphNode. addGraphNode dereferences it with no check, while the same override in HnswConcurrentMergeBuilder's private ConcurrentMergeWorker guards it.
  • The finder then wrote a public-API JUnit test, ran it on main and on the 10.6.0 and 10.4.0 jars, and checked the one-line guard against it and TestHnswFloatVectorGraph. A supporting probe on a 50-node graph showed that with the guard, addGraphNode(50) on a builder created with null gives the same graph size (51) and the same level-0 degree for the new node (3) as the bit-set control.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").
