The Lucene 10.6.0 documentation front page says "how to migrate code from Lucene 0.x": the build hands the major version to the page template as text, so "10" minus 1 becomes "0"

The Lucene 10.6.0 documentation front page says the Migration Guide covers migrating "from Lucene 0.x" instead of 9.x. The template computes "major version minus 1", but the build now passes the major version as the text "10", and Groovy's "10" - 1 deletes the first "1" (main: "12" becomes "2").

The finding in 30 seconds

#

One sentence of the documentation front page names a Lucene version that does not exist. The link next to it and the Migration Guide itself are correct.

Background: how the front page is made

#
  1. ./gradlew :lucene:documentation:createDocumentationIndex turns lucene/documentation/src/markdown/index.template.md into index.html, the first page of the documentation (docs/index.html in the binary release).
  2. Groovy's SimpleTemplateEngine fills in the template: each ${...} is a Groovy expression over values the build supplies, here project.version and project.majorVersion.
  3. In Groovy, - on a number subtracts, but - on a String removes the first occurrence of the right-hand text: 12 - 1 is 11, "12" - 1 is "2".

The finding, step by step

#
  1. You open the documentation front page, docs/index.html of the Lucene 10.6.0 binary release, and read the "Migration Guide" entry.
  2. You expect "What changed in Lucene 10; how to migrate code from Lucene 9.x.", as 10.5.2 says: the page template writes ${project.majorVersion-1}, the major version minus 1.
  3. Instead it says "... how to migrate code from Lucene 0.x." A build of main says "Lucene 12; ... from Lucene 2.x", branch_11x "Lucene 11; ... from Lucene 1.x". The build prints no warning.
  4. Why: since a 2025 build refactor (backported to 10.x in 2026), the major version reaches the template as the text "10", not the number 10. The template engine is Groovy, where "10" - 1 removes the first "1" from the text: "10" becomes "0", "12" becomes "2". With the number, 10 - 1 = 9.

Who is affected

#

Anyone reading the 10.6.0 documentation front page (in the binary release now; on the website if that page is published from the same build), and every documentation build of main, branch_11x and branch_10_6. Default build, no opt-in, no warning. Only one descriptive sentence is wrong: the link works, and nothing in code, indexes or APIs changes.

Mechanism, terms and numbers459 words

The front page of the 10.6.0 documentation (docs/index.html in the binary release, line 38) reads "What changed in Lucene 10; how to migrate code from Lucene 0.x." It should say 9.x, as 10.5.2 did. The template line is What changed in Lucene ${project.majorVersion}; how to migrate code from Lucene ${project.majorVersion-1}.x. (index.template.md:51-52), evaluated by Groovy's SimpleTemplateEngine. Since #14862 (main, 2025-07-01), and on the 10.x line since the build-infra backport #16592 (2026-09-05), the build's majorVersion is a String (LuceneBuildGlobalsExtension.java:51), and DocumentationConfigPlugin.java:233 binds it unchanged. For a String, Groovy's - removes the first occurrence of the operand's text: "10" - 1 is "0", "12" - 1 is "2". Through 10.5.2 the template called a closure that returned an int, ${project.majorVersion()-1}. Main builds print "Lucene 12; ... from Lucene 2.x.", branch_11x "Lucene 11; ... from Lucene 1.x.". Only this sentence is wrong: the link opens the correct Migration Guide and nothing in code, indexes or APIs changes. Binding Integer.parseInt(buildGlobals.majorVersion) restores "9.x" (main: "11.x"); the rebuilt page changes in that one line only.

The claim

#
  • The 10.6.0 binary release's docs/index.html, line 38: <li><a href="MIGRATE.html">Migration Guide</a>: What changed in Lucene 10; how to migrate code from Lucene 0.x.</li>. 10.5.2's page has "... from Lucene 9.x." on the same line. The 10.6.0 website copy of the page is not published yet (HTTP 404 on 2026-11-02, while 10_6_0/MIGRATE.html is live).
  • A build of main e1faeba08bde prints "What changed in Lucene 12; how to migrate code from Lucene 2.x."; branch_11x "Lucene 11; ... 1.x."; branch_10_6, the 10.6.1 line, "Lucene 10; ... 0.x.".

The mechanism (main e1faeba08bde)

#
  1. RegisterBuildGlobalsPlugin.java:149-152 returns the major version as the regex group of the version string, a String; :128 stores it: globals.majorVersion = majorVersion;. LuceneBuildGlobalsExtension.java:50-51: /** Major Lucene version ({@code x} in {@code x.y.z}). */ public String majorVersion;. A Gradle init script on the real build printed majorVersion=12 type=java.lang.String.
  2. DocumentationConfigPlugin.java:227-233 binds it unchanged: Map.entry("majorVersion", buildGlobals.majorVersion) (line 234 at the 10.6.0 tag).
  3. DocumentationConfigPlugin.java:331-336 evaluates the template with new SimpleTemplateEngine(); index.template.md:51-52: What changed in Lucene ${project.majorVersion}; how to migrate code from Lucene ${project.majorVersion-1}.x.
  4. Groovy's String.minus(Object) removes the first "1": String "10" gives 0, "11" gives 1, "12" gives 2; Integer 10 gives 9, Integer 12 gives 11 (executed with Groovy 4.0.33, the version the main build's Gradle 9.8.1 ships, by checkers independently; a cross-model review got the same result for "11" and Integer 11 with Groovy 6.0.0 jars).

Through 10.5.2 the value came from an int closure (build.gradle:71: // "majorVersion" is an integer with just the major version. Compute it.; :77: return m[0][1] as int), and the template called ${project.majorVersion()-1}. The build has no other reader of buildGlobals.majorVersion at e1faeba08bde.

Exposure and likelihood189 words
  • Who meets it: anyone reading the documentation front page of the 10.6.0 binary release, or the website page if it is published from that build; a later 10.6.x or 11.x release built from the current branches before a fix would carry it too. The page is the documentation's entry page.
  • What they get: a sentence naming a version that does not exist ("0.x", "1.x", "2.x"). The link next to it opens the correct guide, so nobody is sent to the wrong one.
  • What does not happen: no effect on code, indexes, APIs, queries or results.
  • Scale: one line of one generated page, but deterministic on every documentation build of the affected branches, and it would repeat for later majors while the value stays a String.
  • How much it matters: little. The link works and readers will likely see "0.x" as a glitch. Still, it is a build-code regression (a type change in a refactor that expected no functional change), not a typo; it is in a released artifact; the fix is one line; and this page is already being fixed for 10.6.1 (#16939, #16941).

Why it looks unintended

#
  • The template's arithmetic, ${project.majorVersion-1}, exists to name the previous major; every release from 9.0.0 to 10.5.2 printed it right (10.5.2: "from Lucene 9.x").
  • Through 10.5.2 the build documented the value as "an integer with just the major version" (return m[0][1] as int).
  • The String came with #14862, a build refactor whose PR description says "no functional changes are expected".
The full argument300 words
  • The sentence and its arithmetic came with LUCENE-9321 (06df50e759a, "Port markdown task to Gradle (#1477)", Uwe Schindler, 2020-05-17, first released in 9.0.0), which added the template line ${project.majorVersion()-1} together with the int closure (// "majorVersion" is an integer with just the major version., return m[0][1] as int). Before that, the Ant build's index.xsl hard-coded the sentence for each major (since LUCENE-4008, a20aa3e0c99, 2012); LUCENE-9577 (2020-10-09) only moved the template.
  • The build's own contract: 10.5.2 build.gradle:71: // "majorVersion" is an integer with just the major version. Compute it.; :77: return m[0][1] as int.
  • History of the type (four steps; commit-level builds): through 10.5.2 majorVersion was a closure returning an int, called as ${project.majorVersion()-1}. #14764 (42123980c25, 2025-06-14) evaluated the closure eagerly, so it became an int property, and switched the template to the property form; harmless: a build of 6071569926f (#14879, the parent of #14862, which already has #14764's template and eager int) prints "Lucene 11; ... from Lucene 10.x.". #14862 (a7fc3d0ae83, 2025-07-01, "Gradle plugins to java, batch 1" by dweiss; PR description: "no functional changes are expected") introduced public String majorVersion; its build prints "... from Lucene 1.x.". #15350 (a0bd3c5f3c6) carried the String into the Java documentation task, and #16592 (f6fce7e42c5, 2026-09-05, a broad backport of main's build-infra changes) brought both to the 10.x line (parent "9.x", commit "0.x"). The searches found no discussion of the type or the sentence in these PRs.
  • What the link covers: 10.6.0's MIGRATE.md:102 is "## Migration from Lucene 9.x to Lucene 10.0".
  • No test or release check reads the sentence: no test in the main tree reads it, and the release smoke test only checks that the MIGRATE and CHANGES files exist.
The devil's-advocate check145 words

Strongest case for leaving it (the intended-behaviour devil's advocate and the cross-model lenses): String is the declared type of the build global (javadoc "Major Lucene version ({@code x} in {@code x.y.z})"), Groovy's String.minus does exactly what it is documented to do, and the sentence is cosmetic: the link works.

Why it fails: the consumer is Lucene's own template, whose arithmetic only makes sense on a number and was written when the build documented the value as an integer; the String came from a refactor that expected no functional change; and "from Lucene 0.x" has no intended reading. Being cosmetic does not make it intended; it keeps the priority Low, while the false version still ships in a released artifact and comes from a build-code regression. An independent reviewer from another model family (OpenAI GPT-5.6) rated the "intended" case weak in both of its lenses.

How it was found

#

Non-formal. A finder compared the 10.5.2 Groovy documentation build item by item with its Java port and diffed the shipped 10.5.2 and 10.6.0 front pages: "from Lucene 9.x" against "from Lucene 0.x". A Gradle init script on the real build then printed the template's value: majorVersion=12, type java.lang.String.

The method in full95 words
  • Lead: the hunt unit started from another defect on the same page (the API Javadocs list links benchmark-jmh, now LFV-1087) and swept the rest of the Groovy-to-Java port of the documentation build (gradle/documentation/*.gradle at 10.5.2 against DocumentationConfigPlugin.java, 15 items).
  • Differential: the shipped 10.5.2 and 10.6.0 front pages differ in the Migration Guide sentence ("9.x" against "0.x").
  • Build model: a Gradle init script printed the template binding on main, branch_11x and branch_10_6 (String every time) and on main with the fix (Integer).
  • No model checker, SMT solver or prover was involved.

Documentation only, with no code, index or API effect: every reader of the documentation front page (docs/index.html) of the 10.6.0 binary release, and of every documentation build of main, branch_11x and branch_10_6, reads a Migration Guide description that names a nonexistent previous version ('0.x' for 10, '1.x' for 11, '2.x' for 12); the standard build prints no warning, the MIGRATE.html link and the guide itself are correct, and the 10.6.0 site page, still unpublished on 2026-11-02, will carry the same text once published.
Summary
You open the documentation front page of Lucene 10.6.0 (docs/index.html) and read the Migration Guide entry. You expect 'What changed in Lucene 10; how to migrate code from Lucene 9.x.', as 10.5.2 says, because the template computes the previous major as ${project.majorVersion-1}; instead it says 'how to migrate code from Lucene 0.x.' (a main build says 'Lucene 12; ... from Lucene 2.x.'). Since the build's version globals became Java (#14862 on main, backported to 10.x in #16592), the template gets majorVersion as the String '10', and Groovy's String minus 1 deletes the first '1' character instead of subtracting; binding the value as an int restores 'from Lucene 9.x' (main: '11.x').
