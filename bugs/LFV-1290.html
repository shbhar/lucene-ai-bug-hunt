ReferenceManager.close() skips afterClose() when releasing the current reference throws

If releasing the current reference throws during ReferenceManager.close(), the subclass cleanup hook afterClose() is skipped, and because the manager already counts as closed, a second close() does nothing: the manager never runs the hook, and whatever it would free is left open (every release since 3.6.0).

The finding in 30 seconds

#

close() runs swapReference(null); afterClose(); with no try/finally. swapReference sets current = null before it releases the old reference, so when that release throws, afterClose() is skipped, and the current != null guard turns every later close() into a no-op.

Background in three steps

#
  1. A ReferenceManager (SearcherManager, ReaderManager, or your own subclass) shares one current reference, usually a reader, across threads. close() is final and drops that reference.
  2. Subclasses free their own resources in the protected hook afterClose(), "Called after close(), so subclass can free any resources".
  3. Releasing a reader for the last time may throw IOException (IndexReader.decRef, from doClose() or a reader-closed listener); close() documents that it then throws.

The finding, step by step

#
  1. You write a ReferenceManager subclass whose afterClose() frees your own resources, as its javadoc invites: "Called after close(), so subclass can free any resources". The test just counts the calls.
  2. You call close(), and the final release of the current reference throws IOException: in an application, a reader whose close fails or whose closed-listener throws (the test's decRef simply throws). close() documents that it then throws.
  3. You expect close() to throw that IOException and still run afterClose() once, during that call (a second close() is allowed and has no effect).
  4. Instead afterClose() runs 0 times, even after a second close(): close() calls it only if the release returns normally, and the release has already set current = null, so the second close() returns at once.
  5. The manager never frees what afterClose() would free (a Directory, an executor): it stays open unless the application frees it some other way. Search results and the index are not affected.

Who is affected

#

Code with its own ReferenceManager subclass that frees something in afterClose(), such as the Directory it opened, when the final release fails during close(): an I/O error while the reader closes its files, or its own reader-closed listener throwing. Lucene's SearcherManager and ReaderManager keep the empty default. Search results and the index are not affected.

Mechanism, terms and numbers429 words

ReferenceManager gives subclasses one hook for their own cleanup, afterClose(), "Called after close(), so subclass can free any resources". close() is final and runs swapReference(null); afterClose(); with no try/finally. swapReference sets current = null before it releases the old reference, so when that release throws an IOException (the reader's close fails, or a reader-closed listener throws), close() throws before it reaches afterClose(). The manager already counts as closed, so a second close() returns at once: the manager never runs the hook, and whatever it would free stays held unless the application frees it some other way.

Only custom subclasses that override afterClose() are hit; Lucene's own SearcherManager and ReaderManager keep the empty default. The code dates from the hook itself (LUCENE-3776, 2012; first release 3.6.0). The fix replaces the two calls in close() with one IOUtils.close(...) call (plus an import).

The bug

#
  1. close() (ReferenceManager.java:133-142): if (current != null) { swapReference(null); afterClose(); } (:135, :139, :140), with no try/finally.
  2. swapReference (:53-58) sets current = newReference, here null (:56), before release(oldReference) (:57), which calls the subclass's decRef (:262-265).
  3. For a reader, IndexReader.decRef (IndexReader.java:215-232) brings the count to 0, sets closed = true (:224) and runs doClose() inside try (Closeable _ = this::notifyReaderClosedListeners) (:225-227). An IOException from doClose() or a ClosedListener (:141-145, declared throws IOException) escapes after the reader is closed. (The same javadoc still says "If an exception is hit, the refCount is unchanged", :208-209, which is stale for this path: the count is already 0.)
  4. The exception leaves swapReference at :139, so afterClose() at :140 never runs.
  5. current is already null, so every later close() stops at the guard (:135), and acquire() throws AlreadyClosedException (:95-96). close() is final, so no close() path can run the hook again (the subclass's own code could still call the protected afterClose(), but the manager never will).

What stays behind (executed)

#

After a failing close() and a second close(): afterClose() calls 0 (expected 1). The same with a stock DirectoryReader over a one-document index as the current reference, when a ClosedListener on it throws: the reader is closed, acquire() throws AlreadyClosedException, and a hook that closes the Directory never runs. Related rows, other sites: LFV-1296 (MultiReader.close() stops at the first sub-reader whose close throws) and LFV-1324 (SearcherTaxonomyManager.close() leaves the taxonomy reader open when releasing the index reader throws) have the same release-on-failure shape, each with its own fix.

Exposure and likelihood193 words
  • Who: applications or libraries with their own ReferenceManager subclass that frees something in afterClose(): the Directory it opened (Michael McCandless suggested exactly this use on java-user, 2016-02-09), an executor, a side reader. SearcherManager and ReaderManager are final and keep the empty default; on main no Lucene class overrides afterClose(). In 3.6.0 to 4.3.1, NRTManager.afterClose() woke waitForGeneration callers (read, not executed; removed in 4.4.0 by LUCENE-4967).
  • Trigger: the final release of the current reference throws during close(): an I/O error while the reader closes its files (possible by the API: doClose() may throw IOException; not executed), or a ClosedListener the application registered that throws (ClosedListener is @lucene.experimental; this path was executed with a stock reader).
  • Effect: close() reports the IOException, but the manager never frees what the hook would free; it stays held unless the application frees it some other way, and calling close() again (allowed, and a no-op once the manager is closed, :135-138) cannot recover it.
  • Not affected: search results and index contents.
  • Likelihood: rare. It needs both a custom hook and a failing final release; no public report was found (see Prior reports).

Why it looks unintended

#
  • The hook's javadoc: "Called after close(), so subclass can free any resources", with no exception for a failed release; close() documents that very failure in its own @throws.
  • close() is final, so afterClose() is a subclass's only close-time cleanup (chosen in LUCENE-3776, #4849).
  • Lucene fixed the same kind of skipped cleanup in IndexReader as a bug (LUCENE-5553, #6615, 2014).
The full argument220 words
  • The hook's contract. "Called after close(), so subclass can free any resources." (ReferenceManager.java:148) No exception is made for a failed release, and close() documents that exact failure as a normal outcome: "@throws IOException if the underlying reader of the current reference could not be closed" (:131).
  • The only close-time hook. In LUCENE-3776 (#4849) @shaie asked to "keep close() final, and introduce a new protected closeResource()/closeInternal() that NRTManager can override", so that subclasses "won't accidentally override close() and forget to call super.close()"; @mikemccand replied "Good idea... I'll add afterClose (matches afterRefresh)". What should happen when the release throws was not discussed.
  • The Closeable contract. java.io.Closeable.close(): "It is strongly advised to relinquish the underlying resources and to internally mark the Closeable as closed, prior to throwing the IOException." ReferenceManager marks itself closed (:56) but never lets the subclass relinquish its resources.
  • Precedent. LUCENE-5553 (#6615, a8b93f272f7, 2014), Bug Fixes: "IndexReader#ReaderClosedListener is not always invoked ... If an exception is thrown during internal close or on any of the close listeners some or all listeners might be missed. This can cause memory leaks". Fixed with a finally, the same shape as here.
  • Nothing accepts it. No test under lucene/ mentions afterClose; no javadoc, MIGRATE.md or CHANGES.txt entry says the hook may be skipped.
The devil's-advocate check165 words

The strongest case for "intended" (rated "moderate" by the cross-model reviewer): "Called after close()" means after a normal return, the way afterMaybeRefresh() is skipped when a refresh throws; the caller does get the IOException; ReferenceManager is @lucene.experimental; and no Lucene class overrides afterClose().

Why it fails: an ordinary failed refresh (refreshIfNeeded throws) leaves the manager open on its old reference, so the next maybeRefresh() tries again (LFV-1221, a failing release inside the refresh swap, is the exception), while a failed close marks the manager closed and turns every later close() into a no-op, so the manager's call of the hook is lost for good; the subclass cannot wrap its own cleanup around the release because close() is final; and the failing release is the case close() itself documents. Admittedly the javadoc implies, rather than states, that the hook also runs when the release fails. What remains is impact, not intent: it stays Low, and a maintainer may call the fix hardening.

Suggested fix

#

Recommended A. Run both steps with IOUtils.close (validated)

In close(), replace swapReference(null); afterClose(); with IOUtils.close(() -> swapReference(null), this::afterClose): afterClose() always runs, the release failure stays the thrown exception and a later afterClose() failure is added as suppressed. Validated: the repro passes with assertions on and off, and 207 tests of the nearest core suites pass (the full test suite was not run).

if (current != null) {
  // make sure we can call this more than once
  // closeable javadoc says:
  // if this is already closed then invoking this method has no effect.
  // swapReference marks this manager closed before it releases the current reference, so
  // afterClose() must run even if that release throws: a later close() would be a no-op.
  // IOUtils.close rethrows the first exception and adds a later one as suppressed.
  IOUtils.close(() -> swapReference(null), this::afterClose);
}

Two options; both were run against the repro in a scratch worktree of 5adff78bb168, A also against the nearest core suites.

A. Run both steps with IOUtils.close (validated) (recommended)

#

In close() (ReferenceManager.java:139-140), plus import org.apache.lucene.util.IOUtils;:

if (current != null) {
  // make sure we can call this more than once
  // closeable javadoc says:
  // if this is already closed then invoking this method has no effect.
  // swapReference marks this manager closed before it releases the current reference, so
  // afterClose() must run even if that release throws: a later close() would be a no-op.
  // IOUtils.close rethrows the first exception and adds a later one as suppressed.
  IOUtils.close(() -> swapReference(null), this::afterClose);
}

Trade-offs

  • Nothing changes when the release does not throw: same order, same exceptions.
  • It keeps the first failure; IOUtils.close also runs afterClose() after a RuntimeException or Error from the release; whether cleanup should also run after an Error is the maintainers' call.
  • It is the idiom Lucene already uses for "close everything, rethrow the first" (IOUtils.java:71-95).
  • CHANGES: a Bug Fixes entry (or Improvements, if maintainers call it hardening).

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix, the repro plus the 9 core unit-test suites that use a ReferenceManager (TestSearcherManager, TestControlledRealTimeReopenThread, TestLiveFieldValues, TestLRUQueryCache, TestTryDelete, TestDemoParallelLeafReader, TestSoftDeletesRetentionMergePolicy, TestKnnGraph, TestIndexWriter; the standalone IncrementalDocValuesUpdatesBenchmark, not a unit test, was not run): 207 tests, 0 failures, 5 skipped.
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test.
  • The full Lucene test suite was not run.

B. Plain try/finally (validated by the checks)

#

try { swapReference(null); } finally { afterClose(); } in close().

Trade-offs

If both the release and afterClose() throw, the afterClose() exception replaces the release failure, so the first error is lost.

What the checks validated

The repro and the 12 TestSearcherManager tests pass with it (13 tests, gradle, assertions on); the earlier shadowed-class checks of the same form passed the other reproductions' tests too.

Downstream note

#

Downstream, a custom ReferenceManager whose afterClose() frees resources should not count on that hook having run after a close() that threw.

How it was found

#

Semi-formal: a proof-obligation audit of ReferenceManager's contract. The obligation is that afterClose() runs once close() has been called, also when releasing the current reference fails; the path where the release throws breaks it. A one-test repro on stock main witnessed it.

The method in full112 words
  • Obligation: from the afterClose() javadoc (:148), close()'s @throws (:131) and its "no effect" rule for a repeated call (:136-138): once close() has been called, the hook runs exactly once.
  • Check: each path through close(); on the path where release throws inside swapReference, current is already null and afterClose() is never reached, now or on a later call.
  • Witness: a JUnit test with a decRef that brings a count to 0 and then throws, then the minimal test shown here.
  • Checks: an independent reproduction, an adversarial review by a model from another family (OpenAI GPT-5.6), an intended-behaviour review and an adjudication (see Independent checks).

Impact note

Summary
You write a ReferenceManager subclass that frees its own resources in afterClose(), which the javadoc describes as 'Called after close(), so subclass can free any resources', and you close it while the final release of the current reference throws an IOException (for example a reader's ClosedListener fails). You expect close() to report the IOException and still run afterClose(), or at least to let a second close() run it. Instead close() throws without calling afterClose(), and because it has already set the current reference to null, every later close() returns at once, so the hook never runs and its resources are never freed.
