The finding in 30 seconds

  • Seen only with an arranged order. The test holds the merge with a merge scheduler and the older update with a slow delete-by-query in its packet. Background: three pieces

#
  1. updateNumericDocValue changes one doc-values field of an existing document without indexing the document again. The writer buffers the update, later resolves it to document numbers (it is then pending on the segment), and a commit or a near-real-time reader open writes it.
  2. Updates travel in packets. A packet applies its deletes before its doc-values updates, so a slow delete-by-query in the same packet delays the update. Since 7.0.0 a newer packet can be resolved while an older one is still being applied.
  3. A merge takes one reader of each source segment and merges what that reader shows. An update that is resolved while the merge runs must reach the merged segment too. On the affected releases (on 10.6.0 with its default overlays setting) the writer keeps such updates in an in-heap list per source segment and applies the list to the merged segment when the merge commits.

The finding, step by step

#
  1. Document a (the one whose id is "a") has the doc-values field n = 0. Thread 1 calls updateNumericDocValue(id:a, "n", 1) in one packet with a slow delete-by-query, so the packet with this older update is still being applied. Thread 2 then calls updateNumericDocValue(id:a, "n", 2). Both calls have returned, thread 2's with the higher sequence number (11, after 9).
  2. A merge of a's segment is initialized at this moment: the older update's packet is still being applied, the newer update is already resolved. The test holds the merge here, before it takes the segment's reader.
  3. The older update finishes, and commit() writes both updates. You expect n = 2, and a reader of this commit shows 2.
  4. The merge is released, takes its reader and finishes. commit() again. You expect 2 and get 1, with no exception, with assertions on or off. In a control run of the same order CheckIndex finds this commit clean, and a fresh reader reads 1. On main f2b061406c4b and on branch_11x 75eea467ac52 (runs of 2026-11-20) both commits show 2.
  5. Why: the merge keeps an in-heap list of the updates that arrive while it runs and applies them to the merged segment at the end. The list starts when the merge is initialized, but the reader is taken later. The older update is in the list and, through the commit, already accounted for in what the merge read, which shows 2. It is applied again, on top of 2.

Who is affected

#

Applications on a release from 7.0.0 to 10.6.0 (the 75 that were run) or on a build of the 10.6 maintenance branch that update one doc-values field of one document from two threads while merges run (the shape that was run). On 10.6.0 the test sets only its merge scheduler and the default codec. Judged rare; no rate is known.

Mechanism, terms and numbers1,251 words

Two threads update the same doc-values field of the same document with IndexWriter.updateNumericDocValue, first to 1 and then to 2, while a merge of that document's segment is starting, and you commit. Both calls have returned, the second with the higher sequence number, so you expect 2 in that commit and in the commits after it. On Lucene 10.6.0 the commit made before the merge finishes shows 2 and the commit made after the merge shows 1, with no exception, with and without assertions. The index stays well-formed (CheckIndex finds that commit clean); one value is an older one.

This was run with a forced order: the older update shares its packet with a slow delete-by-query and is still being applied when the merge is initialized, and the merge is held until a commit has written both updates.

The merge keeps an in-heap list of updates to carry over to the merged segment. The list starts when the merge is initialized, while each segment's reader is taken later. An update that entered the list and was consumed by a write before the reader was taken is applied again, over the newer one. Shai Erera's code comment of 2013 in ReadersAndUpdates.getReaderForMerge named a re-application through such a gap as a hazard, and the code of that time set the mark and took the reader in one step. The change of 2017 for LUCENE-7888 separated them. Will Zhang asked on the dev list on 2022-08-30, without a reply, whether the two calls should be atomic.

The same order of events, in a main() form for each API, fails on each of the 75 releases from 7.0.0 to 10.6.0 that were run. branch_11x at 75eea467ac52 and main at f2b061406c4b, both unreleased, pass the test and no longer have the list.

At the 10.6.0 tag (where the code is)

#

IndexWriter.java, ReadersAndUpdates.java, ReaderPool.java, BufferedUpdatesStream.java and FrozenBufferedUpdates.java are in lucene/core/src/java/org/apache/lucene/index/.

  1. The list starts at merge init. IndexWriter._mergeInit calls readerPool.writeDocValuesUpdatesForMerge (IndexWriter.java:5429). For every source segment that has a pooled ReadersAndUpdates it writes what can be written and then calls rld.setIsMerging() (ReaderPool.java:265-277, the call at :273). A write takes the updates up to the completed generation (the early check at ReadersAndUpdates.java:896, the filter at :339) and leaves the later ones pending (:1001), so an update whose older neighbour is still running stays pending.
  2. From then on an update that resolves against that segment is listed twice. ReadersAndUpdates.addDVUpdate puts it into pendingDVUpdates and, while isMerging is set and maxDocValuesOverlays is 0, also into mergingDVUpdates (ReadersAndUpdates.java:166-188, :180-186). The field's comment: "Holds resolved (to docIDs) doc values updates that were resolved while this segment was being merged; at the end of the merge we carry over these updates" (:93-96).
  3. The reader is taken later. mergeMiddle calls mergeScheduler.wrapForMerge (IndexWriter.java:5593) and then takes the readers one source at a time, each after another setIsMerging() call, which changes nothing when the mark is set, and inside its own synchronized (this) block (:5606-5613).
  4. A write in between prunes one list only. writeFieldUpdates writes the pending updates up to the completed generation and removes them from pendingDVUpdates (ReadersAndUpdates.java:992-1014). mergingDVUpdates keeps them. Run with commit() as that write; the main() form of the range check also ran a near-real-time reader open and flush() as that write (see "Which write" under Exposure and likelihood). By reading, other writes reach the same method: the write that follows an applied packet when the buffered updates are large (IndexWriter.java:6742, :810) and, with reader pooling off, the release of a segment's reader (ReaderPool.java:202-220). None of them touches mergingDVUpdates.
  5. getReaderForMerge appends and never removes. It appends the still-pending updates to mergingDVUpdates and then takes the reader and returns it (ReadersAndUpdates.java:1138-1169, :1146-1155, :1157). Its own comment says why (:1141-1145): "We must carry over any still-pending DV updates because they were not successfully written, e.g. because there was a hole in the delGens, or they arrived after we wrote all DVs for merge but before we set isMerging here." That is about updates that are still pending when the reader is taken, and for those the append is right (one that was listed after the mark is then listed twice, and the merge commit folds the two by generation). The other case is not in it: an update that was listed after the mark and written since is now in the reader the merge reads and still in the list. The comment still says "before we set isMerging here": it came with 58105a203a19 in 2017, when the mark was set in this method, and the introducing commit moved the mark to merge init and left the comment.
  6. The merge commit applies the list to the merged segment. With maxDocValuesOverlays 0, the default of 10.6.0 (IndexWriterConfig.java:116), commitMergedDeletesAndUpdates takes the carry-over from buildMappedDVUpdatesFromMerging (the list's packets that have finished, mapped to the documents of the merged segment) and adds it to the merged segment as pending updates (IndexWriter.java:4571-4589, :4612-4676). In the test the next commit writes it.
  7. Why the older one wins. The newer update resolved before the mark, so it is not in the list. It was pending at merge init and could not be written then, because the older packet was still running. The commit writes both; for one document the larger generation wins (DocValuesFieldUpdates.mergedIterator), and the reader shows 2. The list holds the older update alone, and it lands on top.
  8. Merge init does not wait for a later packet, by design. waitApplyForMerge waits only for packets up to the largest buffered-deletes generation of the sources (BufferedUpdatesStream.java:178-207). A packet applies its deletes before its doc-values updates (FrozenBufferedUpdates.java:170-172), which is why a slow delete-by-query holds the older update.

Why it looks unintended

#
  • IndexWriter javadoc: a sequence number "expresses the effective order in which each change was applied"; the update to 2 has the higher one.
  • The commit made before the merge ends shows 2; no update follows; the next commit shows 1.
  • A 2013 code comment by Shai Erera named this re-application a hazard; the code of that time excluded it.
The full argument428 words
  • The contract. IndexWriter class javadoc (IndexWriter.java:116-120 at the 10.6.0 tag, :119-123 on main): "Each method that changes the index returns a long sequence number, which expresses the effective order in which each change was applied. commit also returns a sequence number, describing which changes are in the commit point and which are not." In the test the newer call has the higher sequence number (the test checks it), a commit shows the newer value, no update follows, a merge finishes, and the next commit shows the older value.
  • The change list. CHANGES.txt, LUCENE-7302: "IndexWriter methods that change the index now return a long "sequence number" indicating the effective equivalent single-threaded execution order".
  • Lucene's own test of the rule for doc-values updates under concurrency is TestIndexingSequenceNumbers.testStressConcurrentDocValuesUpdatesCommit (:345 at the 10.6.0 tag; "this commit point should reflect all operations <= this seqNo" at :452). It is @Nightly and forces no interleaving.
  • The list's own comments describe a carry-over of updates that resolved while the segment was being merged. Updates "that were resolved while this segment was being merged; at the end of the merge we carry over these updates" (ReadersAndUpdates.java:93-96); "Carry over the doc-values updates that resolved while merging" (IndexWriter.java:4571). The older update of the test did resolve while its segment was marked as merging. What the comments do not foresee is that a write puts it into the source segment before the merge takes that segment's reader. The merge's reader then already accounts for it, and nothing takes it out of the list: getReaderForMerge only appends (ReadersAndUpdates.java:1146-1155).
  • The comment inside getReaderForMerge is about the neighbouring case. It explains the append for updates that are still pending when the reader is taken (ReadersAndUpdates.java:1141-1145, quoted in the mechanism above). An update that was listed after the mark and written before the reader is taken is not in it.
  • The hazard was named in this method. The comment that stood in getReaderForMerge until 2017 (Shai Erera, 2013; read at the 6.6.6 tag, ReadersAndUpdates.java:611-615): "must execute these two statements as atomic operation, otherwise we could lose updates if e.g. another thread calls writeFieldUpdates in between, or the updates are applied to the obtained reader, but then re-applied in IW.commitMergedDeletes (unnecessary work and potential bugs)". The code of that time set the mark and returned the reader in one synchronized method (:609-618).
  • Nothing found documents that an older update may win after a merge. The change lists treat a wrong order of doc-values updates as a defect (LUCENE-7301, LUCENE-8595).
The devil's-advocate check330 words

The strongest case for "intended": the test pauses a merge through wrapForMerge of its own MergeScheduler and calls flushNextBuffer(), and both the class MergeScheduler and the method flushNextBuffer are marked @lucene.experimental. The test's scheduler also does not do what the javadoc of MergeScheduler.merge describes ("Run the merges provided by MergeSource#getNextMerge()"): its merge() only stores the MergeSource, the test's main thread calls getNextMerge(), and a thread of the test calls MergeSource.merge. Every method it overrides or calls is public; MergeSource is marked @lucene.experimental too. #16570 described the replacement of the list with "Behavior is unchanged." A maintainer may read the list as a deliberate at-least-once mechanism, and may answer that the 11.x line no longer has it.

What speaks against it (the call is the maintainers'): the experimental mark is a statement about API stability, not about the order of updates. The holds only fix an order that the writer allows by itself: merge init does not wait for a later packet, and the readers are taken in a later synchronized block. In earlier runs a timing probe with an untouched IndexWriterConfig and the stock ConcurrentMergeScheduler read the older value (the writer's log of its logging run shows the same order), and an independent reproduction held the merge through a subclass of the stock scheduler that waits and then calls the stock code. Lucene's own TestMergeCarryOverFromDisk (10.6.0) also "blocks a merge mid-flight", and with overlays disabled it runs this in-heap carry-over; it holds the merge after the readers are taken, through a directory wrapper, so it does not reach the window of this finding. At-least-once holds for the same packet twice, since the merge commit folds packets by delete generation; it does not hold for an older packet over a newer value. What remains are two limits, both stated on this page: it is judged rare, and the code is left only on released lines (the releases and their maintenance branches; branch_10_6 and branch_9_12 were read).

Downstream note

#

An application that keeps a version, a flag or the soft-deletes marker in an updatable doc-values field can see the older value come back after a merge.

How it was found

#

Semi-formal: a seeded model-based test of IndexWriter ran the same call sequences on the 10.6.0 release jars, on branch_11x and on main. Some sequences lost an update on 10.6.0 where branch_11x did not. That was reduced to one test; the range and the introducing change were then established by runs.

The method in full204 words

Method: semi-formal (the real jars are checked against a reference model; no model checking, SMT solving or proof tool was involved). By a strict reading that counts seeded model-based testing as the baseline method, it is the baseline.

  • The first signal (2026-11-19) came from a seeded model of the writer's doc-values update path that checks the index after every step, run over 192 configurations, with the 10.6.0 release jars in their default configuration as a second reference beside branch_11x and main. A few of its sequences lost an update on 10.6.0 where the branch did not.
  • Reduction. The difference was reduced to one JUnit test with the default IndexWriterConfig apart from its merge scheduler (and the default codec set explicitly); the older update is held by a slow delete-by-query of the application.
  • Range and origin. A plain main() form of the schedule was run on each of the 75 releases from 7.0.0 to 10.6.0, and the introducing commit and its parent were built from source and run.
  • A second model. The schedule was replayed as a sequence of an earlier model of the merge carry-over. Its 12 failing sequences of this root on 10.6.0 pass with the one added statement of the fix section.

Area
index / IndexWriter merge (the in-heap carry-over of doc-values updates into a merged segment: ReadersAndUpdates, ReaderPool, IndexWriter.commitMergedDeletesAndUpdates; the release lines 7.x to 10.x)
Priority
Medium, rank 22: An acknowledged doc-values update can be replaced by an older one after a merge, silently and durably (the commit made after the merge shows the older value), in the releases from 7.0.0 to 10.6.0, with no setting needed on 10.6.0 and with or without assertions.
