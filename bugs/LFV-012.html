A rolled-back NRT reader can call different index content "current"

A kept NRT reader of a rolled-back IndexWriter can silently report isCurrent() true after a new writer commits to the same directory, while showing 3 rolled-back documents and no new ones: the closed-writer isCurrent() compares only version numbers, which the new writer reuses. Every executed release since 3.1.0 has it.

The bug in 30 seconds

#

Two writer sessions on one directory, one kept NRT reader, and one version number, 10, used by both.

  1. Writer 1 adds doc A and commits (segments_1, version 4), then adds W1-1, W1-2 and W1-3, refreshing an NRT reader after each. The reader is at version 10 with 4 documents.
  2. Writer 1 ends without committing (rollback(), close() with setCommitOnClose(false), or a tragic I/O error), so the index is back to segments_1, version 4. You keep the reader; the javadoc allows it.
  3. A new writer opens the directory, counts again from version 4 and commits W2-1 (segments_2, version 7), then W2-2 (segments_3, version 10). You expect the old reader's isCurrent() to be false after each: new commits occurred, and it misses the new documents.
  4. Instead it returns true after the second commit. With its writer closed, isCurrent() compares only the version numbers, 10 and 10, not which commit they belong to.
  5. No error, and nothing on disk is wrong; the next commit (version 13) makes it false again. It needs an exact match: in a sweep over 1 to 8 refreshes on main, only 3 and 6 collide.

Who is affected

#

Applications that keep an NRT reader after its writer ends without committing (rollback(), close() with setCommitOnClose(false), or a tragic I/O error), then open a new IndexWriter on the same directory and ask the old reader isCurrent() whether to open a fresh one. No special configuration: a plain new IndexWriterConfig() fails the same way. SearcherManager refreshes with openIfChanged, not isCurrent().

Mechanism, terms and numbers917 words

Keep a near-real-time (NRT) reader after its IndexWriter is rolled back, open a new IndexWriter on the same directory and commit: the old reader's isCurrent() can return true, although it still shows 3 documents that were never committed and none of the new ones. The new writer hands out the same SegmentInfos version numbers again, and once the reader's writer is closed, isCurrent() compares only that number. It needs no special configuration (it also fails with a plain new IndexWriterConfig()), and every executed release since 3.1.0 reproduces it; silent and transient, no corruption. A small extra check in StandardDirectoryReader.isCurrent() fixes it and passes all of :lucene:core:test (one seed; nightly tests not run).

What you do

#

You index with an IndexWriter and search through a near-real-time (NRT) reader that you refresh from the writer, so new documents become searchable before they are committed. Then the writer ends without committing: you call rollback() to discard a failed batch, or close() with setCommitOnClose(false), or the writer hits an I/O error during a refresh and closes itself. Lucene allows you to keep using the last reader ("Once the writer is closed, any outstanding readers may continue to be used"). Later a new IndexWriter opens the same directory (plainly, or on an explicit commit point from DirectoryReader.listCommits) and commits new documents. To decide whether to switch to a fresh reader, you ask the old one isCurrent().

It should say false: new commits have happened, and the old reader shows documents that were rolled back. Sometimes it says true.

Two terms

#
  • Version: a counter in SegmentInfos that "counts how often the index has been changed". The writer adds to it on every change and stores it in each commit. An NRT reader remembers the writer's counter at the moment it was opened, including changes that were never committed.
  • Commit (segments_N): each commit is a new file with a larger N. It is the only place the counter is saved.

The mechanism (main ea57360912ed)

#
  1. An NRT reader carries an uncommitted version. It clones the writer's live SegmentInfos (StandardDirectoryReader.java:126). SegmentInfos.changed() does version++ (SegmentInfos.java:1106-1107); the writer calls it when it names a new segment (IndexWriter.java:2179), on other changes (:2923-2925) and once more on a commit with changes (:3828-3835). These are the bumps this repro hits; others exist, e.g. deleteAll (:2799), setLiveCommitData (:4171) and advanceSegmentInfosVersion (:1417-1423).
  2. Rollback keeps no record of it. Rollback restores the committed segment list (IndexWriter.java:2655) and closes the writer; nothing on disk remembers version 10. close() with commitOnClose=false calls rollback() (:1363-1368); a tragic error closes the writer through rollbackInternal() (:6098-6105).
  3. A new writer counts again from the last commit. It reads the latest commit (IndexWriter.java:1085) and keeps its version, 4, so its commits climb through the same range again (7, 10, 13, ...). Opening on an explicit commit point (setIndexCommit) reads the same latest commit and keeps its version plus one (:1077-1104); its "preserve write-once" comment (:1088-1092) is about newer commits on disk, not about versions a discarded session gave only to NRT readers, and it collides too (the fact check's probe: k = 2, 5 and 8). Only opening from an NRT reader of the old writer, i.e. on the orphan's own commit point, copies the old writer's version over "so we remain write-once" (:1062-1071).
  4. The closed-writer check compares only the number. isCurrent() (StandardDirectoryReader.java:529-544): if the reader's writer is closed (:531), it reads the latest commit and returns sis.getVersion() == segmentInfos.getVersion() (:540). It never asks which commit: the reader's SegmentInfos still names segments_1, the latest commit is segments_3.

Why only some commits

#

In these runs each add-and-refresh moves the version by 2 and each add-and-commit by 3. The old reader sits at 4 + 2k after k refreshes, and writer 2's commits land on 7, 10, 13, ... In a sweep over k = 1 to 8 with 8 one-document commits, k = 3 (version 10) and k = 6 (version 16) collide; the other six values never do. Other workloads step differently: in the study, a writer-2 commit that only set commit user data landed on the old reader's version 4 too.

Exposure and likelihood387 words
  • Who is exposed. Applications that keep an NRT reader after its writer ends without committing, open a new IndexWriter on the same directory, and ask the old reader isCurrent() to decide when to open a fresh one.
  • Three triggers, all public API, all executed: rollback() (ByteBuffersDirectory); close() with setCommitOnClose(false) (FSDirectory); and a tragic event: an IOException ("simulated disk full") from createOutput during an NRT refresh makes the writer close itself (isOpen() false, getTragicException() set), with no rollback call by the application. Writer 2 may be opened plainly or on an explicit commit point from DirectoryReader.listCommits (executed in the fact check); only opening it on the old reader's own commit point avoids the collision.
  • No opt-in. The minimal repro fixes NoMergePolicy to keep the numbers stable; a plain new IndexWriterConfig() (default merge policy and scheduler) gives the same wrong answer at version 10 (second test). No scale needed: one document per commit.
  • Silent. No exception and no log line. The application is told that a reader showing 3 never-committed documents, and missing the newly committed ones, is current, so it keeps serving that view.
  • Limits. The wrong answer lasts only while the latest commit's version equals the old reader's; the next commit ends it. It needs that exact match (2 of 8 values of k in the sweep); how often real workloads align was not measured. Nothing on disk is wrong. The old reader cannot be reopened anyway (AlreadyClosedException, documented), so the application must open a new reader. One that knows a rollback or tragic close happened can do that unconditionally; one that asks the old reader isCurrent() to decide gets the wrong answer.
  • Reach through Lucene's helpers. SearcherManager refreshes with openIfChanged, not isCurrent(), and its isSearcherCurrent() is package-private (SearcherManager.java:232). FilterDirectoryReader passes isCurrent() through (FilterDirectoryReader.java:152-153), so wrapped readers are affected.
  • Same root, another symptom (study only). Two readers of different writer sessions can share a version with different content; the study showed SearcherLifetimeManager.record() then throwing IllegalArgumentException ("the provided searcher has the same underlying reader version yet the searcher instance differs from before", SearcherLifetimeManager.java:156-158). Not re-run in this hunt.
  • Released. Every release since 3.1.0 (2011) contains the change, as far as the history clone's tags show; the 16 releases that were run all reproduce.

Why it is a bug, not intended

#
  • Per its javadoc, isCurrent() checks whether "a new commit has occurred"; two did.
  • Keeping the reader is documented ("outstanding readers may continue to be used"); a Lucene test expects an NRT reader kept after a commit-on-close to stay non-current across a new session.
  • For replication only, PrimaryNode forces versions forward, else "versions can be illegally reused but show different results".
The full argument519 words
  • The javadoc. DirectoryReader#isCurrent (DirectoryReader.java:631-635): for a near real-time reader "this method checks if either a new commit has occurred, or any new uncommitted changes have taken place via the writer". Two new commits occurred. It has no caveat for readers whose writer has closed, and adds (:637-638) "if this returns false, you should call openIfChanged to get a new reader that sees the changes".
  • Keeping the reader is supported. DirectoryReader.java:330-332: "Once the writer is closed, any outstanding readers may continue to be used. However, if you attempt to reopen any of those readers, you'll hit an AlreadyClosedException."
  • The docs are not airtight here either way. getVersion() "returns the version recorded in the commit that the reader opened" (DirectoryReader.java:620), which does not literally describe an NRT reader's uncommitted version, and the advice to call openIfChanged when isCurrent() is false cannot work for an orphan (it throws). Neither text says that such a reader may be reported current after new commits.
  • Lucene's own test expects a kept NRT reader to stay non-current across a new session. TestIndexWriterReader.testUpdateDocument (:132-200) keeps NRT reader r2 after writer.close() and asserts assertFalse(r2.isCurrent()) after that close (:177, :181), then again after a new IndexWriter adds a document (:189) and commits on close (:194). This is indirect: r2 is already non-current before the new writer opens. Before LUCENE-6523 (2015), which made a commit itself a change for NRT readers, :177, :181 and :189 were assertTrue and :194 already asserted false once the new writer had committed a new document: a direct check that a new writer's commit makes a kept reader non-current. testIsCurrent asserts false after the writer's close (:232-233). All of this covers close-with-commit only, where versions keep increasing.
  • Lucene's replication layer treats version reuse as invalid. PrimaryNode.java:116-119 (replicator): "We forcefully advance the SIS version to an unused future version. This is necessary if the previous primary crashed and we are starting up on an "older" index, else versions can be illegally reused but show different results." It works around this with the @lucene.internal advanceSegmentInfosVersion (IndexWriter.java:1412-1423), for replication only. The comment is about the replication protocol, which needs unique versions, not a ruling on core SegmentInfos.version. In core, only opening a writer from an NRT reader carries the old writer's version over (:1062-1071).
  • History. The closed-writer branch came with LUCENE-1976 (#3051, 052e1f5630d, 2009), an issue titled "isCurrent() and getVersion() on an NRT reader are broken". LUCENE-2805 (#3879, 6c9052d2311, 2010) turned the bug on while aiming for a correct isCurrent() inside one writer session; its discussion does not mention rollback or a new session. The testIsCurrent that LUCENE-2802 added in 2010 asserted true for an NRT reader after a commit-on-close that committed exactly what it showed; LUCENE-6523 changed that to false in 2015. Under either meaning of "current" the orphan should be non-current: its content differs and new commits occurred.
  • Effect size. The answer is a boolean and it is wrong, for a reader 3 of whose 4 documents were rolled back.
The devil's-advocate check240 words

The strongest case for "intended" came from one of the study's verifiers (P-model), and the cross-model reviewer rated the same case "moderate": versions are only promised to advance ("This version is advanced every time a change is made with IndexWriter", DirectoryReader.java:617-623), never to be unique across writer sessions; LUCENE-3672 (#4746, 2012) removed, on purpose, the timestamp that a new index's version started from; callers that need uniqueness, such as replication, are expected to force the version forward; opening NRT readers is @lucene.experimental; and an old reader cannot be reopened, so its isCurrent() is only a hint.

Why it fails: this report does not ask for unique versions; it is about the documented answer of isCurrent(), which has no such caveat. Keeping the reader is explicitly allowed, and Lucene's own test expects a kept reader to stay non-current across a new session. The timestamp seed never made versions unique across writer sessions: it applied only to a new index, and 3.1.0 to 3.6.2, which still have it, reproduce this bug with timestamp-sized versions. @lucene.experimental is about API stability, not about wrong answers. P-model verifier itself reproduced the isCurrent() consequence and called it a javadoc violation; it classed only the version scheme as by design. The validated fix needs no unique versions. Verdict: not intended, a defect of low-to-moderate severity. Frame the issue around isCurrent(), cite PrimaryNode up front, and do not present version reuse as a discovery.

Suggested fix

#

Recommended In the closed-writer branch, also check that no newer commit exists (reader side)

For an NRT reader whose writer is closed, StandardDirectoryReader.isCurrent() also requires the latest commit's segments file name to equal the reader's own; one file, no format change. Both repro tests then pass, and :lucene:core:test passes (8,872 tests, one seed, nightly tests not run). It does not stop the version reuse itself.

// we loaded SegmentInfos from the directory
if (sis.getVersion() != segmentInfos.getVersion()) {
  return false;
}
// An NRT reader can hold an uncommitted version. If its writer ended without committing, a
// later writer starts again from the last commit's version and can commit that same number
// with different content, so also require that no newer commit exists:
return writer == null || sis.getSegmentsFileName().equals(segmentInfos.getSegmentsFileName());

In the closed-writer branch, also check that no newer commit exists (reader side) (validated by the checks) (recommended)

#

For an NRT reader (writer != null) whose writer is closed, require the latest commit's segments file name to equal the one in the reader's SegmentInfos, in addition to equal versions. Readers opened from a commit keep today's check. Same logic as the candidate's sketch, reformatted for google-java-format.

// we loaded SegmentInfos from the directory
if (sis.getVersion() != segmentInfos.getVersion()) {
  return false;
}
// An NRT reader can hold an uncommitted version. If its writer ended without committing, a
// later writer starts again from the last commit's version and can commit that same number
// with different content, so also require that no newer commit exists:
return writer == null || sis.getSegmentsFileName().equals(segmentInfos.getSegmentsFileName());

Trade-offs

  • One file, no format change; it costs one string comparison. It can only turn true into false, and only when a commit newer than the reader's exists, which the javadoc counts as a change (since LUCENE-6523 a commit is a change for an NRT reader even when the content is the same), so those false answers are right by contract.
  • Using the segments file name as the commit's identity has a precedent in the same class: doOpenNoWriter treats an equal getSegmentsFileName() as "no change" (StandardDirectoryReader.java:487-489). The reopen path of commit readers, which calls isCurrent() (:480), is unchanged.
  • It does not stop the version reuse itself, so other code that treats "same version" as "same state" (the SearcherLifetimeManager case) is not covered.
  • It relies on an NRT reader's SegmentInfos naming the last commit its writer saw. That holds in every run here, including the control with a legitimately current reader of a closed writer, but it was not proven for every path.
  • The segments file name comes from the commit generation (SegmentInfos.java:250-253), which keeps growing in a directory that Lucene manages; if the directory is erased or replaced outside Lucene, a name could repeat. No focused test was run for an NRT reader without an initial commit, prepareCommit or OpenMode.CREATE; the explicit-commit-point path was run (below).

Never hand out a version that an earlier session gave to a reader (writer side)

#

Make a new IndexWriter start above every version a discarded session handed out. Not tried.

Trade-offs

Would cover every consumer of the version, not only isCurrent(). But a new writer cannot learn those versions: rollback() leaves the index "the same as it was when commit() was last called" (IndexWriter.java:2566-2571) and writes nothing. Seeding each new session from the clock or a random offset would be a new mechanism: the clock seed that LUCENE-3672 removed in 2012 applied only to new indexes and did not prevent this bug in 3.x (3.1.0 to 3.6.2 reproduce). Needs a maintainer's view.

Application workaround: open a fresh reader after any rollback

#

After a rollback or a tragic close, open a new reader from the directory or the new writer instead of asking the old reader isCurrent(); it cannot be reopened anyway. A replication-style alternative is to call advanceSegmentInfosVersion(oldReader.getVersion()) on the new writer, as PrimaryNode does. Not executed.

Trade-offs

No Lucene change, but every application has to know about it; advanceSegmentInfosVersion is @lucene.internal.

Document the limitation

#

Add a caveat to isCurrent() for readers whose writer ended without committing.

Trade-offs

Leaves the wrong answer in place; the weakest option.

How it was found

#

A semi-formal LLM proof-obligation audit: an AI tool wrote invariants of the NRT bookkeeping, checked one obligation per state-changing operation by hand, found that "new IndexWriter(dir) after rollback" fails, and wrote a Java repro. Model-based randomized testing found it later; TLA+ model checking (TLC) and the Alloy solver re-found it blind.

The method in full251 words

Method: an LLM proof-obligation audit (semi-formal), in run 1 of the study (2026-10-22, main 7cecf79523). The study's contamination note lists this finding among those its task text did not hint at.

  • An AI tool wrote down invariants of the NRT bookkeeping and discharged one obligation per mutator by hand. Invariant I4: after the writer is closed, a reader whose version equals the latest commit's version shows that commit's content. Obligation O-X7, "new IndexWriter(dir) after rollback", failed: the new writer restarts numbering at the last commit's version, below versions already shown to the old session's NRT readers. The AI tool wrote a Java repro; Z3 and KeY were used only afterwards, to mechanise the argument.
  • Model-based randomized testing found the same failure later, without formal tools.
  • TLA+ model checking (TLC) re-found it blind as a counterexample of property IsCurrentSound (an 11-state trace: write, NRT open, rollback, new writer, commit at the reader's version), and the Alloy solver re-found it (finding E, property ClosedWriterReaderCurrentSound, 8 steps), both translated into failing Java tests.
  • Study verifiers then checked it: 8 classed it a new bug, 1 classed the version scheme itself as intended (P-model verifier, which still reproduced the isCurrent() consequence), and 1 as the same root cause in a variant. In this hunt it was re-run on main and 10.5.2, reviewed by an independent reviewer from another model family (OpenAI GPT-5.6), tie-broken, bisected and searched for prior reports; this page was then fact-checked twice and its diagram checked once.

Every executed release from 3.1.0 to 10.5.2 and main reproduces; 2.9.4 and 3.0.3 do not. In executed releases from 5.5.5 on, only some refresh counts collide (LUCENE-6523). Not fixed upstream.

Versions tested8 rows

Introduced by LUCENE-2805, "SegmentInfos shouldn't blindly increment version on commit" (JIRA, migrated as #3879): trunk 6c9052d2311 on 2010-12-07, backported to branch_3x as 0196fb48869 on 2010-12-08. Before it, the version moved only when a segments_N file was written, so NRT refreshes after a commit did not move the version past the last recorded one. The closed-writer branch of isCurrent() is older (LUCENE-1976, 2009) and harmless on its own: 2.9.4 and 3.0.3 have it and pass. First affected release: 3.1.0.

From 3.1.0 to 5.0.0 writer 2 steps by 2 like the old reader, so every k collides. LUCENE-6523, first released in 5.2.1, adds one more bump per commit; from 5.5.5, the next executed release, only some k collide (k = 3 and 6 with this cadence). It changes which readers collide, not whether they can.

Every release tag from 3.1 to 10.5.2 in the full-history clone (131 tags) contains the change; the clone has no 8.x tags after 8.8.1, but the executed 8.11.4 jar reproduces. Releases between the executed points were not run.

Bug record

#

LFV-012, snapshot of 2026-10-29

Registry title
An orphaned NRT reader can report isCurrent() true for different index content after a new writer session
Area
index / IndexWriter NRT
Priority
Low, rank 711: A stale NRT reader can report isCurrent() for different content after an uncommitted writer session and an exact version collision, transient until the next commit and an unusual sequence.
Impact class
silent wrong results
Impact note
Default configuration; applications that keep an NRT reader after its writer is rolled back or closed and then open a new writer on the same directory; released (6.6.6+).
Summary
You keep an NRT reader after its writer is rolled back or closed, then open a new writer on the same directory and change the index. You expect reader.isCurrent() to return false. Instead SegmentInfos.version restarts in each writer session and the closed-writer branch of isCurrent compares only versions, so the stale reader reports true for different content.

LUCENE-2805 (6c9052d2311 on trunk, 0196fb48869 on branch_3x) [exec: commit-vs-parent runs] (2010-12-07)
