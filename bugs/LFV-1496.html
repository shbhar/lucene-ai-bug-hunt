PlainTextDictionary(Path) has no close(): a spell-index or suggester build that fails early leaves the word-list file open until garbage collection

new PlainTextDictionary(path) opens the word-list file at once, and the class has no close(). If SpellChecker.indexDictionary or Lookup.build fails before it has read the words to the end, the file stays open, one descriptor per failed call, until garbage collection.

The finding in 30 seconds

#

PlainTextDictionary turns a word-list file into a dictionary for SpellChecker or a suggester. Its Path constructor opens the file and keeps the reader private. The reader is closed only inside the entry iterator, at the end of the input or on a failed read. The class has no close(), so a build that stops earlier leaves the file open.

Background: three pieces

#
  1. SpellChecker.indexDictionary(dictionary, config, fullMerge) builds an n-gram spell index. It first opens an IndexWriter on the spell index, then reads the dictionary word by word.
  2. PlainTextDictionary is a dictionary backed by a text file with one word per line. You can create it from a Path, an InputStream or a Reader. Only the Path form opens the file itself.
  3. An open file costs the process one file descriptor. Java releases it on close(). If nobody closes the stream, the descriptor stays until the stream object is garbage-collected (as run on OpenJDK 25; the JDK does not guarantee that release).

The finding, step by step

#
  1. You build a spell index from a word list dict.txt: spellChecker.indexDictionary(new PlainTextDictionary(path), new IndexWriterConfig(), false). The PlainTextDictionary constructor opens dict.txt at once.
  2. The build fails before it reads a word. In the test another IndexWriter holds the spell index's write lock, so the call throws LockObtainFailedException. That is right. You expect that nothing of the failed call stays open: you hold no handle on dict.txt.
  3. Instead dict.txt stays open. Lucene's own handle tracker reports file handle leaks: [InputStream(.../dict.txt)]. Three failed calls leave 1, 2, 3 descriptors on the file, and still 3 after the SpellChecker and its Directory are closed.
  4. Why: the dictionary closes its reader only when the words are read to the end, or when a read fails. A build that fails for any other reason reaches neither, and PlainTextDictionary has no close() that anyone could call.
  5. The descriptors go away only after the garbage collector has freed the abandoned dictionary: 0 after a requested collection (System.gc(), run on OpenJDK 25). A build that succeeds leaves 0. No suggestion is wrong and no data is lost.

Who is affected

#

Applications that build a spell index or a suggester from a word-list file through PlainTextDictionary(Path), in the opt-in suggest module, and only when that build fails early. Minor: the build fails loudly as it should and no suggestion is wrong. One descriptor per failed call stays until garbage collection. The Reader and InputStream constructors are not affected.

Mechanism, terms and numbers776 words

PlainTextDictionary (lucene-suggest) turns a word-list file, one word per line, into a Dictionary for the n-gram SpellChecker or for a suggester. Its Path constructor opens the file at once (PlainTextDictionary.java:49-51 on main 781025d6fe32) and keeps the reader in a private field. The class implements only Dictionary (:40), so it has no close(). The reader is closed in two places, both inside the entry iterator: at the end of the input (:89) and when a read throws (:93). A build that fails for any other reason before the words are read to the end reaches neither. SpellChecker.indexDictionary creates its IndexWriter (SpellChecker.java:496) before it asks the dictionary for its iterator (:513), so a LockObtainFailedException there leaves the file open without one line having been read. Lookup.build(Dictionary) (Lookup.java:145-147) has the same gap. With the inline call indexDictionary(new PlainTextDictionary(path), ...) the caller holds no reference, and the descriptor stays, one per failed call, until the abandoned dictionary is garbage-collected. The JDK then releases it through a cleaner on the underlying file channel: an implementation detail of the JDK, not a documented guarantee, and run on OpenJDK 25 only. The build fails loudly as it should, no suggestion is wrong and, in 3.6.0 and later, a successful build is not affected. No javadoc promise is broken: no javadoc says who releases the dictionary. The defect is as old as the class (2004, first released in 1.9); the Path constructor dates from 5.0.0. Making the class Closeable and opening the file on first use fixes the repro.

The pieces

#
  • The open. PlainTextDictionary(Path) runs in = Files.newBufferedReader(path, StandardCharsets.UTF_8); (PlainTextDictionary.java:49-51). in is a private field (:42) with no accessor.
  • No close. public class PlainTextDictionary implements Dictionary (:40). Dictionary has one method, getEntryIterator() (Dictionary.java:26-34). Neither is Closeable.
  • The only two closes are inside FileIterator.next() (:76-97): IOUtils.close(in) when readLine() returns null (:89), and IOUtils.closeWhileSuppressingExceptions(t, in) when a read throws (:93).

What goes wrong

#
  1. SpellChecker.indexDictionary (SpellChecker.java:491-552) runs ensureOpen() (:494) and then new IndexWriter(dir, config) (:496). When the write lock is held, that line throws LockObtainFailedException.
  2. dict.getEntryIterator() comes later (:513), then the loop (:517-536). The finally (:537-539) releases the searcher only. Nothing touches the dictionary when the call fails.
  3. So the iterator's next() never ran, neither close was reached, and there is no close() to call. A failure inside the loop, for example writer.addDocument (:535) rejecting a word over 32,766 bytes, leaves the rest of the file unread in the same way.
  4. Lookup.build(Dictionary) (Lookup.java:145-147) is build(dict.getEntryIterator()); with no cleanup, so a suggester build that fails in the middle has the same gap.
  5. With the inline form indexDictionary(new PlainTextDictionary(path), ...) the caller holds no reference to the dictionary. Nothing on the dictionary or the reader releases the descriptor. It goes away through a cleaner that the JDK registers on its internal file channel, some time after a garbage collection has found the dictionary, and with it the reader, the stream and the channel, unreachable. That is an implementation detail of the JDK (read in the JDK 25 source, sun.nio.ch.FileChannelImpl), not a documented guarantee.

The probe requests it up to ten times, 200 ms apart, until the count is 0; a separate run with exactly one request also gives 0, and 3 s without a request release nothing;
  • one SpellChecker and no other writer: a first build over a file whose second line has 40,000 characters fails with IllegalArgumentException and leaves 1 descriptor on that file. Its IndexWriter is never closed (LFV-549), so each retry fails with LockObtainFailedException and leaves one more: 1, 2, 3;
  • AnalyzingSuggester.build(dictionary) over a PlainTextDictionary(path) on the same file fails with IllegalArgumentException and leaves 1 (the probe keeps the dictionary in a local variable);
  • the Reader constructor: 1 while the caller's reader is open, 0 after the caller closes it; the InputStream constructor gives the same two numbers in a separate run;
  • a caller that kept a reference to the dictionary: 1 after the failed build, 0 after it read the dictionary to its end.
Exposure and likelihood367 words
  • Who. Applications that call SpellChecker.indexDictionary or Lookup.build(Dictionary) with a PlainTextDictionary created from a Path. Default settings; one word is enough.
  • Only on a failed build. A build that succeeds reads the file to its end and leaves 0 descriptors (in 3.6.0 and later; before the two closes of 2012 a successful build left the reader open too).
  • Triggers that were run. The spell index's write lock is held by another writer (in the runs a second IndexWriter in the same JVM; in an application it can be another process or another SpellChecker on that directory, which were not run). Or, with one SpellChecker only: a first build fails on an over-long word, its IndexWriter is never closed (LFV-549), and every retry then fails on the lock and leaves one more descriptor. Or a suggester build (AnalyzingSuggester) that fails in the middle of the dictionary.
  • Effect. One file descriptor on the word-list file per failed call. It is still there after the SpellChecker and its Directory are closed and goes away after the abandoned dictionary is garbage-collected. The build fails loudly with its own exception. No suggestion is wrong and no data is lost.
  • Not affected. The InputStream and Reader constructors: the caller owns that stream and closes it. That is also the workaround today: open the reader in a try-with-resources and pass it to new PlainTextDictionary(reader). A dictionary whose read fails is closed by the iterator.
  • Downstream (read, not run). Solr's FileBasedSpellChecker uses the InputStream and Reader constructors, so it does not reach the Path constructor. The Lucene tree itself has no caller of the Path constructor: only the javadoc example and a test with a StringReader create the class.
  • Likelihood: rare. It needs a build that fails early, and the leak then hides behind the loud failure until the next garbage collection. It shows under a handle tracker, or in an application that retries a failing build many times between collections. The recorded searches found no public report since the class was first released in 1.9 (2006).
  • Not checked. Windows (whether the open handle blocks replacing or deleting the word-list file). The release by garbage collection on a JDK other than 25.

Why it looks unintended

#
  • The library opens the file itself and gives the caller nothing to close.
  • The class already closes its reader on the two paths it sees (LUCENE-3807, 2012); a failing build is the one that change missed.
  • Lucene fixes this kind of leak as a bug (#3184, #8598, #14719), and its test framework rejects a file handle left open.
The full argument334 words

This is a resource leak through a missing close(). It is not a broken javadoc promise: no javadoc of PlainTextDictionary, Dictionary, SpellChecker.indexDictionary (SpellChecker.java:482-490) or Lookup.build (Lookup.java:140-144) says who releases the dictionary.

  • The library opens the file and hands the caller nothing to close. The Path constructor creates the reader inside the class; the class is not Closeable; the reader is a private field.
  • The class's own closes show the intent. The iterator closes the reader at the end of the input (:89) and on a failed read (:93). LUCENE-3807 (#4880, 2012) added both; before it the reader was never closed. A consumer that fails before the end is the case that change left open.
  • The documented usage keeps no reference. The class javadoc of SpellChecker shows spellchecker.indexDictionary(new PlainTextDictionary(new File("myfile.txt"))); (SpellChecker.java:61). The example is stale: it calls the one-argument indexDictionary, which no longer exists (reported in #5553 and #9020), and it still says new File. It does show the inline form.
  • Lucene's test framework treats an open handle as a failure. LeakFS.onClose() throws file handle leaks: ... (LeakFS.java:54-65). Upstream's only test of the class uses a StringReader (TestPlainTextDictionary.java:30), so that check never sees the Path constructor.
  • The same kind is fixed as a bug elsewhere. #3184 (LUCENE-2108, 2009): a file descriptor leak of this package, fixed by adding SpellChecker.close(). #8598 (LUCENE-7547, 2016): "JapaneseTokenizerFactory opens dictionary file but never closes it again". #14719 with #14727 (2025): a stream left open when loading a dictionary fails.
  • The ownership rule in a maintainer's words. Uwe Schindler wrote on LUCENE-4165 (#5237, 2012, about another class): "the general contract in Java is, that methods getting streams or readers don't close. [...] Behavior in APIs is different for methods taking file names, of course. They close their internal streams." This is Uwe Schindler's opinion on that issue, not javadoc; it is the reason only the Path constructor is claimed here.
The devil's-advocate check217 words

The strongest case for "intended": Dictionary and InputIterator are minimal producer interfaces without a lifecycle. No ownership transfer is documented, so a callee does not close its caller's argument. The build has already failed loudly, garbage collection reclaims the descriptor, and a caller who wants deterministic cleanup can pass a Reader and close it. FileDictionary, in the same module, has the same single-use shape and also closes its reader only at the end of the input; it has only InputStream and Reader constructors, so it never opens a file itself.

Why it fails as to intent: nothing documents that the dictionary must be read to its end, and nothing recommends the stream constructors. The Path constructor creates the resource inside the library with no way to close it, and an ordinary failure that the method's declared IOException covers (its javadoc says only "If there is a low-level I/O error"; LockObtainFailedException is an IOException) strands it before the first line is read. The class's own two closes show that it means to release the file.

What survives is size, not intent: one descriptor until garbage collection, after a build that already failed. A maintainer may still answer "pass a Reader and close it yourself". That is why this bug is rated at the bottom of Low.

Suggested fix

#

Recommended Closeable, and open the file on first use (validated)

Make PlainTextDictionary implement Closeable and open the file on first use: one class, +21/-2 lines. A build that fails before iterating never opens the file; callers get a close(). Validated with the test and the suggest module's tests and checks. Caveat: a missing file is then reported inside the build, so pair it with the LFV-549 fix (the unclosed IndexWriter).

  private final Path path; // non-null when created from a Path: the file is opened on first use
  private BufferedReader in;

  public PlainTextDictionary(Path path) throws IOException {
    this.path = Objects.requireNonNull(path);
  }

  @Override
  public InputIterator getEntryIterator() throws IOException {
    if (in == null) {
      in = Files.newBufferedReader(path, StandardCharsets.UTF_8);
    }
    return new InputIterator.InputIteratorWrapper(new FileIterator());
  }

Closeable, and open the file on first use (validated) (recommended)

#

PlainTextDictionary implements Closeable. The Path constructor keeps the path, and the file is opened on the first getEntryIterator(). close() closes the reader if it was opened. A build that fails before it asks for the iterator never opens the file, so the repro's case leaves nothing. For a failure in the middle of the iteration the caller now has a close(), for example through try-with-resources. One file, +21/-2 lines. The excerpt leaves out close(), the two stream constructors and the javadoc.

  private final Path path; // non-null when created from a Path: the file is opened on first use
  private BufferedReader in;

  public PlainTextDictionary(Path path) throws IOException {
    this.path = Objects.requireNonNull(path);
  }

  @Override
  public InputIterator getEntryIterator() throws IOException {
    if (in == null) {
      in = Files.newBufferedReader(path, StandardCharsets.UTF_8);
    }
    return new InputIterator.InputIteratorWrapper(new FileIterator());
  }

Trade-offs

  • A missing or unreadable file is reported later, by getEntryIterator() instead of the constructor. In indexDictionary that is after the IndexWriter was created, so while LFV-549 is unfixed the spell index stays write-locked after such a call (executed: the constructor throws and the lock is free on the stock code; indexDictionary throws and the lock is held with this fix). With the rollback sketch of LFV-549 added the lock is free again (executed). So the two changes belong together, or the constructor keeps an existence check (not built).
  • The time of the check moves as well: a file that is replaced or removed between the constructor and the first getEntryIterator() is seen in its later state, where today the constructor opens the file that exists when the dictionary is created (read, not run).
  • A failure in the middle of the iteration still leaves the file open until garbage collection when the caller uses the inline form and never calls close() (executed: 1 descriptor after a build that fails on an over-long word; 0 after the caller's close()).
  • The constructor keeps throws IOException in its signature but no longer throws. A close() before the first getEntryIterator() does not prevent a later open: the sketch has no closed flag.

Closeable, and the two consumers close the dictionary when they fail (validated more lightly)

#

PlainTextDictionary gets a close(), and SpellChecker.indexDictionary and Lookup.build(Dictionary) catch a failure, close the dictionary if it is Closeable and rethrow. The file is released on every failing path, the inline form included, and the constructor still reports a missing file. Three files, +36/-2 lines.

Trade-offs

  • A consumer closes an argument it did not open. With the Reader constructor the failed build closes the caller's reader (executed: 0 descriptors while the caller's try block is still open). That is against the first half of the ownership rule quoted above, although the class already closes a caller-supplied reader at the end of the input.
  • A dictionary that the caller kept cannot be read after the failed build (executed: IOException).
  • The sketch reaches beyond this class: it closes every Dictionary that is Closeable, a caller's own implementation included, and it catches Throwable.
  • Two earlier independent reviews objected to this point: a callee normally does not close its caller's argument.

Closeable only: the caller closes the dictionary

#

The class gets a close() and nothing else changes. Callers write try (PlainTextDictionary dict = new PlainTextDictionary(path)) { spellChecker.indexDictionary(dict, config, false); }. The SpellChecker javadoc example would be updated to that form.

Trade-offs

The smallest change: no existing call behaves differently (the class does gain the type Closeable, which an instanceof check or generic cleanup code can see), and there is no ownership question. But the inline form still leaves the file open on a failed build, existing callers must change their code to benefit, and the test as written still fails: it would be rewritten with try-with-resources. Not built on its own.

Workaround today: pass your own Reader (validated by the checks)

#

Open the reader yourself and use the Reader constructor: try (Reader r = Files.newBufferedReader(path, StandardCharsets.UTF_8)) { spellChecker.indexDictionary(new PlainTextDictionary(r), config, false); }.

Trade-offs

Not a fix: the Path constructor still leaves its file open on a failed build.

What the checks validated

Executed in the evidence probe: 1 descriptor while the caller's reader is open after the failed build, 0 after the caller closes it.

How it was found

#

Semi-formal. A probe injected a fault at each of the 166 file-system calls of SpellChecker.indexDictionary over a PlainTextDictionary(Path) and checked one invariant: a failed call leaves no file handle open. It broke at 15 of them, whenever the call failed before the dictionary was read to its end. The case was reduced to one public-API test without any injected fault.

The method in full206 words

Method: semi-formal (bounded-exhaustive fault injection on the real jars against a stated invariant; no model checking, solver or proof tool was involved).

  • The fault probe. A wrapper around the file system made one call fail per run: each of the 166 file-system calls (stat, open, mkdir, list, map, write, delete, sync, move) that a SpellChecker.indexDictionary over a PlainTextDictionary(Path) makes on main.
  • The invariant. After a failed call no file handle is left open.
  • First signal. FD_LEAK [InputStream(dict.txt)] at 15 of the 166 positions: every position where the call failed before the dictionary had been read to its end (taking the write lock, listing and reading the spell index's commit, creating the first index files).
  • Without a fault. A public-API program then showed the same with no injected fault: three indexDictionary calls that fail with LockObtainFailedException leave 1, 2, 3 descriptors on the dictionary file. History

As old as the class: first commit 2004, first released in 1.9. The Path constructor dates from 5.0.0 (LUCENE-5945). A 2012 change (LUCENE-3807) closed the reader at the end of the input, but not when the build fails earlier. The test fails on main, on the 11.0 branch (11.0.0-SNAPSHOT) and on 10.6.0. An old defect, not a regression.

PlainTextDictionary(File) opens the file in its constructor, the class has no close(), and nothing closes the reader on any path. First released in 1.9 (2006): the class is in the source tags 1.9-rc1 and 1.9; the earliest published lucene-spellchecker artifact on record, and the oldest one that was run, is 1.9.1.

LFV-1496, snapshot of 2026-11-22

Registry title
PlainTextDictionary(Path) opens the dictionary file in its constructor and has no close(), so a SpellChecker.indexDictionary or Lookup.build that fails before reading it to the end leaves the file open until garbage collection (the Path constructor since 5.0.0; the File constructor before it since 1.9)
Area
suggest / spell: PlainTextDictionary (a word-list file as a Dictionary) under SpellChecker.indexDictionary and Lookup.build(Dictionary): release of the dictionary file when the build fails
Priority
Low, rank 1232: In every release that has the class (through the Path constructor since 5.0.0), a spell-index or suggester build over PlainTextDictionary(path) that fails before the dictionary is read to its end leaves the dictionary file open, one file descriptor per failed call, until garbage collection. It is Low because the suggest module is opt-in, the leak shows only on a build that already fails loudly with its own exception, and no suggestion or data is wrong.
Impact class
minor
Impact note
Hits applications that build a spell index (SpellChecker.indexDictionary) or a suggester (Lookup.build(Dictionary)) from a word-list file through PlainTextDictionary(Path), with default settings and no scale, and only when that build fails before the dictionary has been read to its end (the spell index's write lock is held by another writer, including the writer that LFV-549 leaves behind after an earlier failed build; a dictionary word over 32,766 bytes; a suggester build that fails early): the build fails loudly with its own exception, as it should, but each such failed call leaves one file descriptor open on the dictionary file until the abandoned dictionary object is garbage-collected (the release by garbage collection was executed on JDK 25 only); no suggestion is wrong, no data is lost, a successful build is unaffected, and the InputStream and Reader constructors are not affected (the caller owns that stream and can close it); the releases that have the class, branch_11x and main [exec on 18 of the releases and on both branches, see Affected versions; the others by reading the source]; on main, branch_11x and 10.6.0 the same with -ea and -da.
Summary
You build a spell index from a word-list file with spellChecker.indexDictionary(new PlainTextDictionary(path), ...), and the call fails, for example with LockObtainFailedException because another writer holds the spell index. You expect that nothing of the failed call stays open once you have closed the SpellChecker and its Directory: the library opened the dictionary file itself and you hold no handle on it. Instead the file stays open, one file descriptor per failed call, until the garbage collector reclaims the abandoned dictionary object, because PlainTextDictionary has no close() and closes its reader only when the iteration reaches the end of the file or a read fails; the same happens when Lookup.build(Dictionary) fails early.
