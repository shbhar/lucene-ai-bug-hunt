HnswBitVectorsFormat: one float vector document closes the IndexWriter and rolls back everything since the last commit

The finding in 30 seconds

#

HnswBitVectorsFormat indexes byte vectors only and rejects float vectors with IllegalArgumentException. The indexing chain treats some failures as "aborting": the in-memory segment may be broken, so the writer drops it and closes itself. This rejection is raised inside such an aborting step.

Background: a rejected document vs an aborting exception

#
  1. IndexWriter buffers new documents in memory until a flush or commit; a near-real-time (NRT) reader can already see them. Only commit() makes them durable.
  2. A bad document normally gets an IllegalArgumentException from addDocument: only that document is dropped and the writer carries on. A vector over the format's dimension limit is rejected this way.
  3. Some failures are "aborting": they can strike while segment files are being written, so Lucene discards the whole in-memory segment and closes the writer as a tragic event, back to the last commit.
  4. The first time a field appears in a segment, the indexing chain registers the field and then asks the vectors format for a per-field writer (addField). Any exception from that call is treated as aborting.

The finding, step by step

#
  1. You route fields named bits* to HnswBitVectorsFormat, which indexes byte vectors only. You commit doc 1, add doc 2 (an NRT reader now sees 2 documents), then add doc 3 with KnnFloatVectorField("bits_f", {1, 2}), a field the index has not seen yet.
  2. You expect addDocument to reject doc 3 and nothing else. The format's own test expects exactly that exception, and a 1025-dimension vector in the same field (over the format's 1024 limit) is rejected that way: doc 4 and a commit then leave 3 documents.
  3. You get the expected IllegalArgumentException, but it is also the writer's tragic exception: isOpen() is false, doc 4 throws AlreadyClosedException, and the index holds 1 document. Doc 2, already visible to NRT search, is gone. CheckIndex is clean.
  4. Why: the format rejects the field in addField, which IndexingChain calls only after it has registered the field, inside a catch (Throwable) that treats every failure as aborting. The dimension limit is checked before registration, so it does not abort.
  5. It needs a float (on main also float16) field that is not yet registered as BYTE; a field already registered as BYTE gets an ordinary rejection. Affected: all 19 releases from 9.11.0 to 10.6.0, and main.

Who is affected

#

Only applications that opt in to HnswBitVectorsFormat (lucene-codecs) and send it a float vector by mistake, on a field not yet registered as BYTE. One such document closes the shared writer and discards every caller's uncommitted documents, including NRT-visible ones; re-sending it closes the next writer too. The committed index stays intact.

Mechanism, terms and numbers536 words

HnswBitVectorsFormat (lucene-codecs, @lucene.experimental) indexes byte vectors only. Its writer rejects any other encoding in addField with IllegalArgumentException("HnswBitVectorsFormat only supports BYTE encoding"). IndexingChain#initializeFieldInfo calls addField the first time a vector field appears in a segment, after it has registered the field's FieldInfo, inside catch (Throwable th) { onAbortingException(th); throw th; }. So the per-document rejection is also recorded as an aborting exception: the in-memory segment is aborted, the exception becomes the writer's tragic exception, and IndexWriter rolls back to the last commit and closes itself. The caller receives the IllegalArgumentException it expected; the next addDocument or commit throws AlreadyClosedException. Buffered documents, documents already visible to near-real-time search and documents that other threads added successfully are all lost, and a fresh writer closes again if the application re-sends the document. The committed index stays intact and CheckIndex-clean.

The same format's other per-field limit, getMaxDimensions, is checked before the field is registered and is an ordinary rejection; the format's own test expects only the exception. Since 9.11.0, in all 19 releases that ship the format, and on main. A small pre-registration hook on KnnVectorsFormat fixes it and passes the codecs module's tests.

Exposure and likelihood321 words
  • Who is hit. Applications on 9.11.0 or later that configure HnswBitVectorsFormat, codec-wide or per field through PerFieldKnnVectorsFormat, and send it a KnnFloatVectorField (on main also a KnnFloat16VectorField) whose field name is not yet registered as BYTE: a new field, or a field committed as FLOAT32 under another format and routed to the bit format in a later session. The format is opt-in (lucene-codecs, not the default codec) and @lucene.experimental. Any index size; one document.
  • What goes wrong. Every later indexing or commit call on the writer throws AlreadyClosedException until the application opens a new one (getTragicException(), isOpen(), close() and rollback() still answer), and every document since the last commit is lost: buffered documents, documents an NRT reader already showed, and a document that a second thread had added successfully (measured; in-flight documents of a concurrent thread were not measured). The caller's IllegalArgumentException looks like an ordinary per-document rejection, so a caller that catches it and moves on finds out only on its next indexing or commit call.
  • Repeats. The rolled-back segment takes the field registration with it, so re-sending the same document to a fresh writer closes that writer too.
  • Not affected. The committed index stays intact and CheckIndex-clean; nothing is exposed. A field already registered as BYTE (earlier in the session or in a committed segment) gets an ordinary schema rejection and the writer stays open.
  • How likely. Low: it takes the opt-in, experimental format plus a float field sent to it by mistake, and that mistake usually shows on the first such document in testing. Elasticsearch ships its own bit-vector format; no use of Lucene's class was found in Solr, OpenSearch or the OpenSearch k-NN plugin (code search of default branches, not exhaustive).
  • Workaround. Send the format only KnnByteVectorField values (check the element type before addDocument). Once the field is committed as BYTE, a float document is an ordinary rejection.

Why it looks unintended

#
  • The format's own test, testFloatVectorFails, expects only an IllegalArgumentException from addDocument.
  • The same format's dimension limit is checked before the field is registered, a placement maintainers chose in #12436, and leaves the writer open.
  • LUCENE-5662 fixed this pattern as a bug; Robert Muir's reason: an aborting input check makes you "lose other unrelated documents in IndexWriter's buffer".
The full argument356 words
  • The format's test. TestHnswBitVectorsFormat#testFloatVectorFails (TestHnswBitVectorsFormat.java:54-63) adds a 4-dimension KnnFloatVectorField through IndexWriter.addDocument and expects an IllegalArgumentException. It checks nothing about the writer, and its message check at :61 is a no-op (contains is not asserted).
  • #12436 (2023). jpountz first suggested a dimension check inside KnnVectorsWriter#addField; mayya-sharipova objected that by then the FieldInfo is already in the global FieldInfos (review comment r1275409313); jpountz then liked "retaining the property that the field info doesn't even get created if its number of dimensions is above the limit" (r1275939419), and uschindler welcomed that the check runs in addDocument() rather than while indexing or flushing. That thread named the poisoned-FieldInfo hazard, not the writer closing, and predates the bit format.
  • Lucene's tests. TestIndexWriterExceptions#testNullStoredField (:1592-1614, "test a null string value doesn't abort the entire segment") asserts getTragicException() is null after an input IllegalArgumentException and that the earlier document survives. BaseKnnVectorsFormatTestCase#testIllegalDimensionTooLarge (:779-795) and TestPerFieldKnnVectorsFormat#testMaxDimensionsPerFieldFormat (:217-244) keep using the writer after a codec's per-field rejection.
  • Precedent. LUCENE-5662 (#6724, Robert Muir): missing null checks in Field aborted segments, "This is bad because you lose other unrelated documents in IndexWriter's buffer"; fixed under "Bug fixes" in 4.8.1 (CHANGES.txt:12384-12385). LUCENE-5611 made doc-values and term-vector setting errors non-aborting. LUCENE-5987 defines an aborting exception as "an exception that would otherwise cause silent data loss" (CHANGES.txt:11577-11579).
  • Nothing documents the close. The IndexWriter class javadoc names "an Error, or disaster strikes during a checkpoint" (IndexWriter.java:162-165; not a complete list); addDocument says that after an Exception "the index will be consistent, but this document may not have been added" (:1465-1466); getTragicException gives "disk full while flushing a new segment" as its example (:6108-6112). No javadoc, comment at the catch, CHANGES or MIGRATE entry says this rejection closes the writer.
  • History. The aborting catch came with #992 (LUCENE-10592, 2022), with no comment about input checks. In the #13288 review the author said the wrapper writer exists because "it validates only BYTE vectors are written" and jimczi replied "Ah thanks, I missed the addField validation": meant as validation; nobody discussed that it aborts.
The devil's-advocate check243 words

The case (from the cross-model reviewer and the study's devil's advocate): a float vector is outside the domain of a byte-only, experimental format, so this is application misconfiguration. On 2024-06-05, asked on #13288 whether the format "was more a prototype and not intended for production use", its author answered yes. IndexingChain marks every Throwable from addField aborting on purpose, and addDocument promises a consistent index, not an open writer; the commit does survive.

Why it fails: the format answers this input with a deliberate IllegalArgumentException that its own test expects from addDocument, so the input is handled, not undefined; the problem is that the rejection also discards unrelated documents, the case LUCENE-5662 fixed as a bug. It does not merely fail loudly: the bad call gets its exception, but the documents discarded with it were added by calls that had already returned successfully, and those calls never report an error. The aborting catch protects against codec failures that may already have changed state, and the same IndexingChain checks the codec's dimension limit before registration: it was placed there in #12436 so that no FieldInfo is created for a rejected field and so that the check runs in addDocument rather than during indexing or flush, and that placement is why that rejection does not abort. @lucene.experimental marks an unstable API, not permission to lose writes. The argument lowers the impact and makes an "improvement" label likely; it does not make the close intended.

Suggested fix

#

Recommended A pre-registration encoding hook on KnnVectorsFormat, called next to getMaxDimensions

Add a checkVectorEncoding(fieldName, encoding) hook to KnnVectorsFormat (default: accept every encoding), delegate it in PerFieldKnnVectorsFormat, override it in HnswBitVectorsFormat, and call it in IndexingChain next to the dimension check, before the field is registered. The test, the codecs module (694 tests) and core vector suites (807) pass.

// KnnVectorsFormat: the default accepts every encoding
public void checkVectorEncoding(String fieldName, VectorEncoding encoding) {}

// HnswBitVectorsFormat
@Override
public void checkVectorEncoding(String fieldName, VectorEncoding encoding) {
  if (encoding != VectorEncoding.BYTE) {
    throw new IllegalArgumentException("HnswBitVectorsFormat only supports BYTE encoding");
  }
}

// IndexingChain#initializeFieldInfo, right after validateMaxVectorDimension(...)
vectorsFormat.checkVectorEncoding(pf.fieldName, s.vectorEncoding);

A pre-registration encoding hook on KnnVectorsFormat, called next to getMaxDimensions (validated by the checks) (recommended)

#

4 files, +31 / -3. KnnVectorsFormat gets public void checkVectorEncoding(String fieldName, VectorEncoding encoding) {} with javadoc (the default accepts every encoding, so no other format changes); PerFieldKnnVectorsFormat delegates it to getKnnVectorsFormatForField(fieldName), like getMaxDimensions; HnswBitVectorsFormat overrides it with the same IllegalArgumentException it throws today; IndexingChain#initializeFieldInfo calls it right after validateMaxVectorDimension, before fieldInfos.add. FlatBitVectorsWriter#addField keeps its check as a backstop.

// KnnVectorsFormat: the default accepts every encoding
public void checkVectorEncoding(String fieldName, VectorEncoding encoding) {}

// HnswBitVectorsFormat
@Override
public void checkVectorEncoding(String fieldName, VectorEncoding encoding) {
  if (encoding != VectorEncoding.BYTE) {
    throw new IllegalArgumentException("HnswBitVectorsFormat only supports BYTE encoding");
  }
}

// IndexingChain#initializeFieldInfo, right after validateMaxVectorDimension(...)
vectorsFormat.checkVectorEncoding(pf.fieldName, s.vectorEncoding);

Trade-offs

  • API addition: a new public, non-abstract method on KnnVectorsFormat; backwards compatible and backportable to 10.x, but the maintainers must want it. A boolean supportsVectorEncoding(...) would mirror getMaxDimensions more closely, at the cost of a generic message composed in IndexingChain, which does not know the per-field format's name.
  • Message: in the bug case the exception type and message stay as today. For a field already registered as BYTE in an earlier segment, HnswBitVectorsFormat only supports BYTE encoding replaces today's cannot change field "v" from ... vector encoding=BYTE ... to inconsistent ... vector encoding=FLOAT32 ...; both are non-aborting (fact-check probe, stock and with the fix).
  • Wrappers: a format that wraps another and delegates getMaxDimensions must delegate this too; in Lucene's main sources that is only PerFieldKnnVectorsFormat (AssertingKnnVectorsFormat wraps the default format, which accepts everything).
  • Indexing path only: FlatBitVectorsWriter#mergeOneField has no encoding check, so addIndexes or a merge that brings float segments under the bit format is a separate, untested question.
  • Future formats: open PR #16092's PreconditioningKnnVectorsFormat throws from addField for non-FLOAT32 fields (read from the diff); it could override the same hook.

Make the rejection non-aborting at the catch around addField

#

Catch IllegalArgumentException from addField without calling onAbortingException. Not executed; not recommended.

Trade-offs

By then the field is registered as FLOAT32 in the segment and the global field numbers, carries per-field attributes, and the segment's vectors writer may have opened files; later BYTE documents in that field would fail the schema check for the rest of the session (the hazard named in #12436), and a blanket catch could hide real codec failures.

How it was found

#

Found by reading how IndexingChain classifies exceptions as aborting or not, while modelling its exception paths, then confirmed with a JUnit on the stock jars. No model artifact or formal tool witnessed it. An independent reproducer, cross-model reviews, a devil's advocate, an adjudication and a tie-breaker confirmed it.

LFV-121, snapshot of 2026-11-09

Registry title
A float vector field routed to HnswBitVectorsFormat is rejected inside an aborting step of the indexing chain, so the one rejected document closes the IndexWriter and rolls back every document added since the last commit
Area
codecs / HnswBitVectorsFormat x index / IndexingChain aborting-exception classification
Priority
Low, rank 685: Moved down from Medium: one float vector sent to the opt-in, experimental HnswBitVectorsFormat closes the IndexWriter and rolls back every thread's uncommitted docs, severe but loud, caused by an application programming error, and the committed index stays intact.
Impact class
crash
Impact note
Applications on 9.11.0 and later that use the opt-in, @lucene.experimental HnswBitVectorsFormat from lucene-codecs (codec-wide or per field) and send it a KnnFloatVectorField (on main also a KnnFloat16VectorField) whose field name is not yet registered as BYTE in the index: that one document throws the format's IllegalArgumentException and also closes the IndexWriter as a tragic event, so every document added since the last commit is rolled back (measured: buffered documents, documents already visible to an NRT reader, and a document another thread had added successfully), and a fresh writer closes again on the same document; -ea and -da, ordinary scale; the committed index stays intact and CheckIndex-clean, and a field already registered as BYTE gets an ordinary rejection that leaves the writer open.
Summary
You use HnswBitVectorsFormat, which accepts only byte vectors, and by mistake add a document with a float vector field (KnnFloatVectorField) that is new to the index. You expect addDocument to reject that one document with IllegalArgumentException and the writer to stay open, as the format's own test TestHnswBitVectorsFormat#testFloatVectorFails expects the exception and as happens for the same codec's dimension limit and for a vector dimension mismatch. Instead the check sits in KnnVectorsWriter#addField, which IndexingChain calls after registering the field and treats as an aborting step, so the exception also becomes the writer's tragic exception: IndexWriter closes itself, the next call throws AlreadyClosedException, and the documents added since the last commit are gone (the repro ends with 1 committed document instead of 3).
