The benchmark quality package overview's TREC sample calls a 4-argument QualityBenchmark.execute that no release has ever had

The benchmark quality package overview's only sample calls qrun.execute(maxResults, judge, submitLog, logger), but QualityBenchmark has only execute(judge, submitLog, logger) plus setMaxResults(int). The API changed in 2008, before the package's first release, so the copied sample fails to compile on every release from 2.3.0 to 10.6.0.

The finding in 30 seconds

#

The sample is a plain code block in the package javadoc, which javadoc never compiles. When the result count moved from an execute argument to setMaxResults, the same commit fixed the two other callers but not this page; a 2012 edit of the sample kept the call and added the : typo.

  1. You want to measure search quality on TREC topics, open the org.apache.lucene.benchmark.quality package overview and copy its "sample code used to run the TREC 2006 queries 701-850". It sets int maxResults = 1000; and calls qrun.execute(maxResults, judge, submitLog, logger).
  2. You expect it to compile and run each query with up to 1000 results.
  3. Instead javac rejects the call: required: Judge,SubmissionReport,PrintWriter; found: int,Judge,SubmissionReport,PrintWriter. Copied verbatim, it stops one line earlier still: DirectoryReader.open(directory): ends with : instead of ;.
  4. The 4-argument execute existed only on trunk, from July 2007 to January 2008: before the 2.3.0 release, the result count moved to setMaxResults(int); QueryDriver and the tests were updated, the overview never was. With qrun.setMaxResults(maxResults); followed by qrun.execute(judge, submitLog, logger) the sample compiles.

Who is affected

#

Developers who start a TREC-style evaluation from the opt-in benchmark module's quality package overview: the copied sample fails to compile every time, on every release since 2.3.0. Documentation only: nothing in Lucene runs differently, and javac names the correct signature.

Mechanism, terms and numbers466 words

The overview of org.apache.lucene.benchmark.quality (an exported package of the published benchmark module) introduces its only code block as "a sample code used to run the TREC 2006 queries 701-850 on the .Gov2 collection". The block sets int maxResults = 1000; and calls qrun.execute(maxResults, judge, submitLog, logger). QualityBenchmark has only execute(Judge, SubmissionReport, PrintWriter) and takes the result count from setMaxResults(int) (default 1000). Copied into a project, the call fails with one javac error, "method execute in class QualityBenchmark cannot be applied to given types; required: Judge,SubmissionReport,PrintWriter; found: int,Judge,SubmissionReport,PrintWriter", on main and on every release from 2.3.0 to 10.6.0. Copied verbatim, javac stops even earlier, because the DirectoryReader.open(directory) line ends with :.

The API change was deliberate: LUCENE-1116 (January 2008; its issue description speaks of moving "control over max-docs-to-retrieve from benchmark constructor to a setter method", though in the code the count was the first argument of execute) added setMaxResults(int) and updated QueryDriver and TestQualityRun, but not the page. 2.3.0, the package's first release, already had the change, so no release ever shipped a compiling sample. A 2012 pass that fixed out-of-date API usage in the sample rewrote its reader lines, left the call and introduced the :. Nothing in Lucene behaves wrongly; only the page is stale.

The API

#

QualityBenchmark has one execute: public QualityStats[] execute(Judge judge, SubmissionReport submitRep, PrintWriter qualityLog) (line 96). It searches with the field maxResults (line 106), documented "maximal number of results to collect for each query. Default: 1000." (lines 63-64) and set by setMaxResults(int) (line 167). A class-file scan of 22 release benchmark jars (2.3.0 to 10.5.2) and main finds no execute(int, ...); all 142 release tags that have the package (2.3.0 to 10.6.0) carry the stale line.

The correct usage in tree

#

trec/QueryDriver.java:96-98 and TestQualityRun.java:82-86: construct the QualityBenchmark, call qrun.setMaxResults(maxResults), then qrun.execute(judge, submitLog, logger).

Why nothing caught it

#

Javadoc does not compile <pre><code> blocks, and the block has no {@link} that javadoc would check. The tests use the current API.

Not claimed

#

Any defect of the API itself; the free name directory, normal for a fragment. The sample's 1000 happens to equal the default, so deleting the first argument alone gives the intended count by accident; for any other value the reader must find setMaxResults.

Exposure and likelihood123 words
  • Who. Readers of the quality package overview who copy its sample. A 2009 java-user@ reply pointed a user to this page as the package's usage documentation. No query, document or index file reaches it.
  • Default vs opt-in. The benchmark module is a separate, opt-in artifact. No configuration or special input is involved: the copied sample always fails.
  • Scale. Every release from 2.3.0 (2008) to 10.6.0, and main (executed on 9 releases and main; the source of all 142 release tags read); no release ever shipped a compiling sample.
  • Effect. A compile error, not wrong behaviour. javac names the 3-argument signature, and setMaxResults is in the class's method list.
  • Not claimed. Runtime defects of the same package are separate findings (LFV-935, LFV-936, LFV-937, LFV-940).

Why it looks unintended

#
  • The page presents the block as "a sample code used to run" the TREC benchmark; it is the overview's only example, and nothing marks it as pseudo-code.
  • The 2008 change that removed the 4-argument execute (LUCENE-1116) updated QueryDriver and TestQualityRun but missed this page.
  • Lucene's own code calls setMaxResults(maxResults) and then the 3-argument execute.
The full argument217 words
  • Offered as working code. "Here is a sample code used to run the TREC 2006 queries 701-850 on the .Gov2 collection" (line 36), the package overview's only code block, with no pseudo-code marker.
  • History. 98fa2d898d1 (LUCENE-836, #1911, 2007-07-27) added the package and the sample together, and the sample matched the then-existing execute(int maxResults, Judge, SubmissionReport, PrintWriter); it compiles at that commit. 9e65cd554f2 (LUCENE-1116, #2193, 2008-01-03), whose issue description (not the commit message) lists "move control over max-docs-to-retrieve from benchmark constructor to a setter method (API change)" (in the parent's code the count was the first argument of execute, not a constructor argument), introduced setMaxResults(int) and the 3-argument execute, and updated QueryDriver and TestQualityRun, not the page. The sample compiles at the parent 40eb1cd53fd and fails at 9e65cd554f2.
  • A later fix pass missed it too. 647b5091697 (2012-09-12, "code snippet improvements: fix out of date api usage ...", on trunk; its branch_4x twin d8d5bf5e07d is the one in 4.0.0) rewrote the sample's reader lines for 4.0, kept the execute call and introduced the :.
  • No record accepts the old form. The recorded searches (as of 2026-11-01) found no issue, PR, list thread or Q&A post that uses or defends the 4-argument call; Stack Overflow answers about the package use the 3-argument execute.
The devil's-advocate check129 words

Strongest case for "not a bug": the block is illustrative; it uses an undeclared directory and has the : typo, so nobody can expect it to compile as is. The API change was deliberate, the error is loud and names the right signature, and the module is a developer tool whose real entry point is QueryDriver.

Why it fails: the undeclared directory is context a reader supplies, but no context makes a removed signature compile. A deliberate API change that leaves the package's only sample stale is a documentation defect, not intended behaviour; the same change updated the two other call sites. The packages are exported and published, and the page has no disclaimer. Every verifier and the adjudication called it real; it stays a Low documentation defect.

Suggested fix

Recommended Fix the two lines of the sample (validated)

Edit the sample (javadoc only): end the DirectoryReader.open(directory) line with ;, and replace the call with qrun.setMaxResults(maxResults); followed by qrun.execute(judge, submitLog, logger), as QueryDriver does. Validated by the recorded checks: the whole patched block compiles on main and 10.6.0, TestQualityRun passes, and the javadoc renders.

  • First signal. A probe compiled the page's sample (only the : read as ;) with javac against the stock main 645d4fe14a20 and 10.5.2 jars and got one error, the execute call (2026-10-29).
