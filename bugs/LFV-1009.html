FacetSetsField.create sizes its buffer from the first facet set, so a later, larger custom set can throw ArrayIndexOutOfBoundsException

FacetSetsField.create sizes its buffer from the first facet set, so a custom compressed FacetSet that packs larger than the first can crash it: sets of 2 and 7 bytes get 8 bytes for 13 and throw ArrayIndexOutOfBoundsException. Swapped, they work; built-in sets are fixed-size and safe.

The finding in 30 seconds

#

All the facet sets of one field go into one byte array. create sizes that array from the first set alone, but every set then writes as many bytes as it needs.

Background: facet sets in one minute

#
  1. A FacetSet is a small tuple of values per document, for example (year, month). FacetSetsField.create(name, sets...) packs the sets it is given into one binary doc-values field; a field of that name can be added to a document only once.
  2. Each set writes its own bytes with packValues(buf, start), which returns how many it wrote, and reports its size with sizePackedBytes(). The built-in Int/Float and Long/DoubleFacetSet always use 4 or 8 bytes per value.
  3. You may write your own FacetSet with your own encoding, for example a compressed one, plus a matching FacetSetDecoder that MatchingFacetSetsCounts uses to count.

The finding, step by step

#
  1. Write a one-dimension FacetSet that compresses its value: one length byte plus the value's significant bytes, with sizePackedBytes() returning that exact size. The value 7 packs to 2 bytes, the value 2^40 to 7 bytes.
  2. Build the field for a document with both: FacetSetsField.create("f", set(7), set(2^40)). You expect a field of 4 + 2 + 7 = 13 bytes: same class, same dimensions, so none of create's documented errors applies.
  3. Instead create allocates 4 + 2 × 2 = 8 bytes, sized from the first set only, while each set writes its own bytes. The second set's write reaches byte 8: ArrayIndexOutOfBoundsException: Index 8 out of bounds for length 8.
  4. Swap the order and it works: create("f", set(2^40), set(7)) allocates 4 + 7 × 2 = 18 bytes, keeps 13, and the document indexes and counts 1 and 1. In general it fails whenever the sets' average size exceeds the first set's.

Who is affected

#

Only applications with their own FacetSet whose packed size differs per instance (a compressed or variable-length encoding, which the docs invite) that pass a smaller set before a larger one. That document cannot be built in that order; nothing wrong is written. Every release since 9.3.0, any codec, assertions on or off. No such public FacetSet was found.

Mechanism, terms and numbers676 words

FacetSetsField.create(name, sets...) packs the facet sets of one field into one binary doc-values value. It allocates Integer.BYTES + facetSets[0].sizePackedBytes() * facetSets.length bytes (FacetSetsField.java:55 on main 645d4fe14a20) and then advances its write offset by what each set's packValues really writes (:74). FacetSet.sizePackedBytes() is per instance ("the size of the packed values in this facet set"; an upper limit is allowed when the size is unknown in advance, FacetSet.java:52-58), and FacetSets.adoc:137-139 invites custom encodings "e.g. by compressing them". So a custom compressed set that packs larger than the first set can overrun the buffer: create("f", set(7), set(2^40)) with sets of 2 and 7 bytes allocates 8 bytes for 13 and throws ArrayIndexOutOfBoundsException: Index 8 out of bounds for length 8, while the same two sets with the larger first pack, index and count correctly. Packing fails exactly when the sets' mean packed size exceeds the first set's (726 of 1,554 lists of 1-4 sets of 1-6 bytes, checked exhaustively on the real jar). The built-in Int/Long/Float/DoubleFacetSet are fixed-size and cannot trigger it. The exception is thrown while the field is built, so nothing wrong is indexed. Present since facet sets were added in 9.3.0 (#841); a fix that sums every set's size (a four-line loop) passes the repro and the whole facet module.

Terms

#
  • FacetSet (FacetSet.java, @lucene.experimental): a set of dims values per document. packValues(byte[] buf, int start) "Packs the dimension values into the given byte[] and returns the number of packed-values bytes ... you can override to implement your own scheme" (:39-43). sizePackedBytes(): "Returns the size of the packed values in this facet set. If the value is unknown in advance (e.g. if the values are compressed), this method can return an upper limit." (:52-58).
  • FacetSetsField (FacetSetsField.java): a BinaryDocValuesField whose value is the number of dimensions (an int, 4 bytes) "followed by each set's values" (:23-27). create requires that all sets "must have the same number of dimensions" and throws IllegalArgumentException "if the field name is null or the given facet sets are invalid" (:32-39); the code also requires the same class (:66-73).
  • FacetSetDecoder / MatchingFacetSetsCounts: at search time a decoder reads one set and "returns the number of bytes read" (FacetSetDecoder.java:54-58); the counter advances by that value (MatchingFacetSetsCounts.java:124-125). So counting already handles sets of different sizes, given a matching decoder; the stock decodeLongs and decodeInts are fixed-width, like the built-in sets (FacetSetDecoder.java:37-52).

The bug

#
  1. FacetSetsField.java:55: byte[] buf = new byte[Integer.BYTES + facetSets[0].sizePackedBytes() * facetSets.length]; sizes the buffer from the first set only.
  2. :74: offset += facetSet.packValues(buf, offset); advances by what each set really wrote.
  3. The writes need 4 + sum(sizes) bytes; the buffer has 4 + n * sizes[0]. It overflows exactly when sum(sizes) > n * sizes[0], that is when the sets' mean size exceeds the first set's; for two sets, when the second is larger.
  4. The buffer is a fresh Java array, so the JVM's bounds check throws ArrayIndexOutOfBoundsException from inside the set's packValues, out of create, before any document reaches IndexWriter.

The numbers

#

Bytes printed by an executed probe on main: the dims int is 80 00 00 01, set(7) packs 01 07, set(2^40) packs 06 01 00 00 00 00 00. Smaller first: buffer 8 bytes, holds 80 00 00 01 01 07 06 01, and the next write, at index 8, throws. Larger first: buffer 18 bytes, the field keeps 13 (80 00 00 01 06 01 00 00 00 00 00 01 07), and MatchingFacetSetsCounts counts 1 document for each value. With three sets of 2, 2 and 7 bytes the buffer is 10 bytes and the write fails at index 10. A bounded-exhaustive check (1 to 4 sets, sizes 1 to 6, 3,108 checks) found 726 of 1,554 lists failing, exactly those the formula predicts, and 0 failures when all sizes are equal or every set returns one class-wide bound.

Exposure and likelihood283 words
  • Who is exposed. Applications that write their own FacetSet subclass whose packed size differs from one instance to the next (compressed, varint or length-prefixed) and return each set's exact size from sizePackedBytes(), as the javadoc describes. The four built-in sets (IntFacetSet, FloatFacetSet: dims * 4; LongFacetSet, DoubleFacetSet: the default dims * 8) and the demo's TemperatureReadingFacetSet (a constant size, CustomFacetSetExample.java:353-355) cannot trigger it.
  • Opt-in API. Facet sets are an @lucene.experimental part of the facet module. Within it the failure does not depend on IndexWriterConfig, the codec or assertions: it happens while the field is built.
  • Effect. The field cannot be built with its sets in that order, so the document cannot be indexed with it. The field "can be added to a document only once, so you will need to construct all the facet sets in advance" (FacetSets.adoc:98-99), so all the sets for that field go through this one call (an application may still add other FacetSetsFields under other names). The exception comes from a fresh, bounds-checked Java array while the field is built, before anything reaches IndexWriter: no corrupt data, no wrong counts.
  • Scale. Any create call with two or more sets whose mean packed size exceeds the first set's: in the bounded check, 726 of 1,554 lists of 1 to 4 sets.
  • Workarounds today. Pass the largest-packing set first (then n * sizes[0] >= sum(sizes)), or return one bound valid for every instance from sizePackedBytes().
  • How likely: rare. A public code search for sizePackedBytes "extends FacetSet" found 39 files, all copies of Lucene's own sets; no outside variable-size FacetSet was found, and nobody has reported it since 9.3.0.

Why it looks unintended

#
  • sizePackedBytes() is per instance, "the size of the packed values in this facet set", and may be an upper limit "if the value is unknown in advance"; nothing requires a class-wide bound.
  • The docs invite compressed encodings; counting advances by each set's decoded length.
  • create documents only a same-dimensions rule, yet the same two sets work or crash by order.
The full argument400 words
  • Contract. FacetSet.java:52-58: "Returns the size of the packed values in this facet set. If the value is unknown in advance (e.g. if the values are compressed), this method can return an upper limit." An instance method about "this facet set". It permits an upper limit when the size is unknown in advance; it does not say that a set whose exact size is known must return a bound shared by its whole class. Its own example of an unknown size is compressed values, which a maintainer may read as pointing to such a bound (see the strongest case below). packValues "returns the number of packed-values bytes ... you can override to implement your own scheme" (:39-43).
  • The docs invite variable sizes. FacetSets.adoc:137-139: "If you implement your own FacetSet and choose to encode the values differently (e.g. by compressing them), you should provide a corresponding implementation of a FacetSetDecoder." The class javadoc of FacetSetsField describes the value as the dimensions "followed by each set's values" (:23-27), with no uniform per-set size.
  • The generic path handles variable sizes. The field keeps only the bytes written (new BytesRef(buf, 0, offset), :76); FacetSetDecoder.decode returns "the number of bytes read" and MatchingFacetSetsCounts advances by it (:124-125). The stock decoders are fixed-width, like the built-in sets, so a variable-size set brings its own decoder, as FacetSets.adoc:137-139 says. Inside create, only :55 assumes that every set has the first set's size.
  • No documented precondition. create documents the same-dimensions rule and an IllegalArgumentException for invalid sets (:32-39). A size rule would be checked there, not left to an order-dependent array overrun inside the user's packValues.
  • No test pins it. The facet-set tests use only the fixed-size built-in sets; no CHANGES.txt entry or MIGRATE.md note mentions sizes.
  • History. The line and the javadoc arrived together in f6bb9d218c0e (#841, 2022-06-25). Inside #841, PR commit 40e2992e25 (shaie, 2022-06-15) summed every set's size, new byte[4 + Arrays.stream(facetSets).mapToInt(FacetSet::sizePackedBytes).sum()]; PR commit ab0d4e1624 ("Finish FacetSets.adoc", shaie, 2022-06-19) replaced it with today's line, in the same hunk that added the same-class check. So :55 has been in tension with a per-instance reading of the javadoc from the start. The only review remark on the line (gsmiller, 2022-06-15: "Maybe use Integer.BYTES instead of 4 here?") predates the switch; nobody discussed it (25 commits, 169 review comments, 62 issue comments read).
The devil's-advocate check188 words

Strongest case for "works as designed". The switch from the per-set sum to first-set-times-count was a deliberate edit, made together with the same-class check, so the authors pictured "one class, one size". Read that way, the "upper limit" clause is the hook for compressed encodings: a compressed set should return a class-wide worst case. Every shipped set is fixed-size, and the API is experimental.

Why we still read it as a bug. None of that is written down. The javadoc speaks of "this facet set" and offers an upper limit "if the value is unknown in advance"; it does not require a class-wide bound, so a set that knows its exact size and returns it is a natural reading. create documents no size rule and checks none, the same two sets work in one order and crash in the other with an undocumented ArrayIndexOutOfBoundsException, the generic counting loop advances per set, and the PR's own first version summed per-set sizes.

How strong the other reading is: moderate. The compressed-values example in the same javadoc sentence does support a class-wide-bound reading, and the switch in #841 was deliberate.

Suggested fix

#

Recommended Size the buffer by the sum of every set's sizePackedBytes()

Size the buffer as 4 plus the sum of every set's sizePackedBytes() (a four-line loop with Math.addExact), the per-set-sum strategy of an earlier #841 commit by Shai Erera. Validated: the repro passes, and so do the whole facet module (307 tests) and its static checks.

int sizePackedBytes = 0;
for (FacetSet facetSet : facetSets) {
  sizePackedBytes = Math.addExact(sizePackedBytes, facetSet.sizePackedBytes());
}
byte[] buf = new byte[Integer.BYTES + sizePackedBytes];
All options and trade-offs3 options · 690 words

One fix was built and validated with gradle; two alternatives were not built. A maintainer may prefer option C, which documents a class-wide bound instead.

Size the buffer by the sum of every set's sizePackedBytes() (validated by the checks) (recommended)

#

Replace line 55 of FacetSetsField.java with a loop that adds up every set's sizePackedBytes(). This restores the per-set-sum strategy of #841 PR commit 40e2992e25 by Shai Erera (shaie; it used Arrays.stream(...).sum()), with overflow-checked accumulation: Math.addExact turns an int overflow of the sum into an ArithmeticException. A cross-model review suggested checked accumulation; Math.addExact is the finder's way of doing it.

int sizePackedBytes = 0;
for (FacetSet facetSet : facetSets) {
  sizePackedBytes = Math.addExact(sizePackedBytes, facetSet.sizePackedBytes());
}
byte[] buf = new byte[Integer.BYTES + sizePackedBytes];

Trade-offs

  • One extra pass of n sizePackedBytes() calls per document, negligible next to packing; not measured.
  • For the fixed-size built-in sets the allocation is byte-for-byte the same as today (n equal sizes sum to n * size).
  • Sets that return an upper limit still work: the field keeps only the written bytes.
  • The final Integer.BYTES + sizePackedBytes addition is not checked, so a sum above Integer.MAX_VALUE - 4 still wraps to a negative array size. Today's unchecked sizes[0] * n can wrap too: at the same point when all sizes are equal, and never later for a list that works today (those have n * sizes[0] >= sum).
  • The new loop calls every set's sizePackedBytes() before the existing same-dimensions and same-class checks (:59-73). Valid lists behave as described; for an invalid mixed list, an unusual sizePackedBytes() of a set of another class (negative, or large enough to overflow) could now throw before the documented IllegalArgumentException. Running the checks in the summing loop would keep today's order (not built).
  • It still trusts each set: a negative sizePackedBytes(), or a packValues that writes more bytes than its sizePackedBytes() reports, still fails, as it does today.
  • A "Bug Fixes" CHANGES.txt line would be usual; none is drafted.

Grow the buffer before each set (not built)

#

Start from 4 + sizes[0] and call buf = ArrayUtil.grow(buf, offset + facetSet.sizePackedBytes()) before :74.

Trade-offs

One pass and also correct, but more code and possibly several array copies for many sets; no advantage over the sum for the small set counts facet sets are meant for.

Document a class-wide bound and validate it (not built)

#

Change the sizePackedBytes() javadoc to require a bound that holds for every instance of the class, and in toPackedValues throw IllegalArgumentException when a set's sizePackedBytes() exceeds the first set's.

Trade-offs

Keeps today's allocation and turns the order-dependent crash into the documented exception, but narrows a documented extension point and still rejects lists the sum accepts; compressed encodings would have to return their worst case.

Downstream note

#

Downstream products that feed end-user values into their own variable-length FacetSet could see a user's document fail to index depending on the order of its values; Lucene's built-in sets cannot trigger it.

How it was found

#

Code reading while checking multi-dimension doc-values fields that trust their first element (siblings of #16919): create sizes everything from facetSets[0]. A closed-form model (it fails iff the sizes sum to more than n times the first) was checked exhaustively on the real jar, 3,108 cases with 0 disagreements, then reduced to one JUnit.

The method in full161 words

Method: semi-formal (the hunt's hunt unit for binary doc-values multi-dimension fields that trust the first element's shape, 2026-10-29, main 645d4fe14a20).

  • Lead. While modelling the unit's "trusts facetSets[0]" pattern, the finder read that line 55 sizes the buffer from the first set while line 74 advances by each set's real size.
  • Model. Writes are cumulative and every size is positive, so packing overflows iff sum(sizes) > n * sizes[0].
  • Bounded-exhaustive translation validation on the stock main jar: n = 1 to 4 sets, packed sizes 1 to 6, two size policies (exact per-instance size; one class-wide upper limit), 3,108 checks. With exact sizes, 726 of 1,554 javadoc-legal lists throw, and the observed failure set equals the model's (0 disagreements). Vacuity: 0 failures with the class-wide limit and 0 when all sizes are equal; assertions on and off identical.
  • Reduction. A public-API JUnit with a failing test and a larger-first control (index, commit, count), then minimized to the single failing test.

LFV-1009, snapshot of 2026-11-02

Registry title
FacetSetsField.create sizes its buffer from the first FacetSet's sizePackedBytes(), so a list of custom variable-size facet sets (e.g. compressed, which the FacetSet javadoc and FacetSets.adoc allow) throws ArrayIndexOutOfBoundsException when a later set packs to more bytes than the first, and whether a document can be built depends only on the order of its sets
Area
facet / facet sets (FacetSetsField packing of custom FacetSet encodings)
Priority
Low, rank 599: A loud ArrayIndexOutOfBoundsException that needs a hand-written variable-size FacetSet in the experimental facet-sets module, so it sits with LFV-606, where a custom implementation the javadoc permits causes a crash.
Impact class
crash
Impact note
Only applications that write their own FacetSet subclass whose packed size differs from one instance to the next (a compressed or variable-length encoding, invited by FacetSets.adoc, with sizePackedBytes() returning each set's exact size) and pass a smaller-packing set before a larger-packing one to FacetSetsField.create hit it, on every release from 9.3.0 to 10.5.2, on 10.6.0 (by reading) and on main, with any IndexWriterConfig or codec and with -ea or -da; the exception is thrown while the Field is built, so that document cannot be indexed in that order, but nothing wrong is written and the built-in Int/Long/Float/DoubleFacetSet are not affected.
Summary
You write a FacetSet subclass that compresses its value (one length byte plus the value's significant bytes, so sizePackedBytes() is 2 for the value 7 and 7 for 2^40) with a matching FacetSetDecoder, and you expect FacetSetsField.create("f", set(7), set(2^40)) to work just like the same call with the two sets swapped. Instead create allocates 4 + the first set's sizePackedBytes() times the number of sets (8 bytes) and then writes each set's own packed bytes (13 needed), so the second set's packValues throws ArrayIndexOutOfBoundsException 'Index 8 out of bounds for length 8'. With the larger set first the same two sets pack, index and count correctly.
