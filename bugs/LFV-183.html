The postings writer stores a level-1 block's impacts length in a signed short: custom norms wider than a byte corrupt a term's postings

With a custom Similarity whose norms do not fit in a byte, a term's skip-data impact list can pass 32,767 bytes, but the default postings writer stores its length in a signed short. The segment is written without error; that term's postings throw or read back wrong (since 9.12.0).

The finding in 30 seconds

#

Each 8,192-document block of a term's postings starts with a list of its competitive (freq, norm) pairs. The writer stores the list's byte length in a 16-bit signed field, which holds at most 32,767.

Background in three steps

#
  1. A norm is one long value per document and field, computed at index time by the Similarity. Lucene's built-in similarities pack the field length into one byte; a custom Similarity may store any non-zero long.
  2. Impacts: for each block of a term's postings, the codec stores the (freq, norm) pairs that could give the best score, so a top-k search can skip blocks that cannot compete.
  3. The default postings format writes impacts at two levels: every 256 documents (level 0) and every 8,192 documents (level 1).

The finding, step by step

#
  1. Set a Similarity whose norm is the field length (as Lucene's own TestCustomNorms does) and index 8,192 documents, each with one token t whose custom term frequency is 1 + 8,193 x i (1, 8,194, ... 67,108,864). Default codec, one segment.
  2. Every 8,192 documents the writer lists the block's competitive (freq, norm) pairs, so searches can skip blocks. Here all 8,192 pairs are competitive: the list takes 49,147 bytes.
  3. You expect the postings to read back as indexed.
  4. Instead the length goes into a signed short: (short) 49,147 = -16,389. With assertions off flush succeeds, the first nextDoc() throws numBytes must be >= 0, got -16389, and CheckIndex at its default level says the index is clean. With assertions on, flush fails an assertion.
  5. With norm = length << 24 the list is 73,724 bytes, stored as +8,188: nextDoc() raises no exception but returns 26 wrong postings (doc 0 with freq 71,321,599 instead of 1) out of 8,192, and a top-3 TermQuery throws.

Who is affected

#

Applications with a custom Similarity whose norms do not fit in a byte (raw length, wider encodings), on a field with frequencies and norms, and a term in 8,192+ documents of one segment (4,096 before 10.4) with many distinct (freq, norm) pairs. No built-in Similarity can trigger it. Merging valid segments can create the bad block.

Mechanism, terms and numbers571 words

Every 8,192 documents of a term's postings (one level-1 block), the default postings writer writes a skip header that lists the block's competitive (freq, norm) pairs, the impacts, and stores their byte length with writeShort((short) numImpactBytes). With byte norms, which every Similarity shipped with Lucene uses, the list stays small. With a custom Similarity whose norms do not fit in a byte, CompetitiveImpactAccumulator keeps every competitive pair, up to one per document, and the list can pass 32,767 bytes. Then flush fails an assertion with -ea; with -da the segment is written without error, its checksums are valid and CheckIndex at its default level reports no problem, but reading that term's postings in the segment then throws (numBytes must be >= 0) or, when the length wraps to a positive value, iterating them returns postings decoded from the wrong bytes without an error (a scored search still throws). Merging valid segments can create the bad block. Since 9.12.0 (#13585); the 8,192-document block of 10.4.0 (#15160) made exact field-length norms enough. Not fixed upstream; a writer-only change (+15/-3 lines) fixes it without a format change.

The mechanism (main 5adff78bb168)

#
  1. Impacts per level-1 block. flushDocBlock calls writeLevel1SkipData() every 32 blocks of 256 documents (Lucene104PostingsWriter.java:486-487; LEVEL1_NUM_DOCS, Lucene104PostingsFormat.java:348-351). It takes the block's competitive pairs (:501) and encodes them with writeImpacts (:505): per pair a vint of the freq delta and, unless the norm grew by exactly 1, a zlong of the norm delta (:540-556).
  2. How many pairs. CompetitiveImpactAccumulator folds norms in -128..127 into a 256-slot array, but keeps pairs "for norm values that fall outside of -128..127" in a TreeSet with no cap (CompetitiveImpactAccumulator.java:32-35, :64-71). When freq and norm grow together, every document's pair is competitive.
  3. The short. The only guard is assert numImpactBytes <= Short.MAX_VALUE, under the comment "There are at most 256 impacts, that require at most 2 bytes each" (:523-524). Then the header length and the impact length are written with docOut.writeShort((short) ...) (:527-528).
  4. The reader. skipLevel1To reads both back as signed shorts (Lucene104PostingsReader.java:696-697) and skips the impacts with docIn.skipBytes(numImpactBytes) (:702). A negative length throws IllegalArgumentException; a positive wrap leaves the file pointer inside the impact list, and the reader decodes skip data and doc blocks from the wrong bytes.
  5. Only level 1. Level 0 writes the same kind of length with writeVLong (Lucene104PostingsWriter.java:407) and reads it with readVInt (Lucene104PostingsReader.java:746).

The numbers

#

One token per document on a DOCS_AND_FREQS field, so the field length, and with it the norm, equals the term frequency (IndexingChain.java:2054-2059). Freq and norm both grow by 8,193 per document: the first pair takes 1 byte and each of the other 8,191 takes 6 (3 for each delta), 49,147 bytes in all, stored as (short) -16,389. Overflow needs at least 4 bytes per pair on average at 8,192 documents (more than 32,767 bytes in all), at least 8 at 4,096. With norm = length << 24 each pair takes 9 bytes: 73,724 bytes, stored as +8,188. A Z3 integer program over the encoder's byte sizes bounds one list at 53,150 bytes for norm = length at 8,192 documents, 28,638 at 4,096 and 1,792 for byte norms, shows that exact-length norms can only wrap negative, and its byte counts match both repro sizes exactly.

Exposure and likelihood338 words
  • Who is hit. A custom Similarity whose computeNorm returns values outside -128..127 (the raw length, a wider length encoding, the bits of a double) on a field indexed with frequencies and norms, and one term in at least 8,192 documents of one segment (4,096 on 9.12.x-10.3.x) whose (freq, norm) pairs are mostly competitive with wide deltas. Weighted-term fields with large custom term frequencies (TermFrequencyAttribute, DelimitedTermFrequencyTokenFilter) fit this shape. Default codec; the Similarity is opt-in.
  • Not hit. Every Similarity shipped with Lucene (byte norms: at most 1,792 bytes per list), fields without norms or frequencies, and terms with fewer than 8,192 documents in a segment.
  • What goes wrong with assertions off (production). No error at flush or commit. For that term in that segment: with a negative wrap, nextDoc() throws at the first call and a top-3 TermQuery throws IndexOutOfBoundsException, while IndexSearcher#count still says 8,192; with a positive wrap (norm = length << 24), nextDoc raises no exception but returns 26 documents, all with wrong ids or freqs, then ends, and a top-3 TermQuery throws IndexOutOfBoundsException.
  • Hard to notice. The segment's checksums are valid, and CheckIndex at its default level (1 for the command-line tool, 0 for an API instance without setLevel) reports the index clean (neither level reads postings: CheckIndex.java:499, :1114, :4748, :4754); levels 2 and 3 report the exception.
  • Merges spread it. Eight flushed segments of 1,024 documents each read back correctly; forceMerge(1) writes the bad block and the merged segment throws the same way. From reading only (not run): a natural merge that reads such a segment would fail.
  • Custom term frequencies are not required. A plain TextField where document i holds the token t i + 1 times, with norm = Double.doubleToLongBits(length), fails the same way (got -6127).
  • How likely. Rare: the executed triggers are constructed shapes (8,192 distinct growing frequencies up to 67,108,864); nobody has reported it from real data. With assertions on (tests), flush or merge fails an assertion instead.

Why it looks unintended

#
  • The Similarity javadoc: Lucene "makes no assumption about what is in this norm"; CompetitiveImpactAccumulator has an uncapped TreeSet for norms outside -128..127.
  • Level 0 of the same writer stores this length as a varint, as did the pre-9.12.0 format.
  • The only guard is an assertion commented "at most 256 impacts", true only for byte norms.
The full argument256 words
  • The norm contract allows it. "Lucene makes no assumption about what is in this norm" (Similarity.java:47-48); single-byte encoding "might not be suitable for all purposes" (:52); computeNorm only requires that greater unsigned norms do not score higher and that 0 is not used (:140-145), and SimScorer.score must not decrease when the frequency grows (:207-209); the repro's scorer follows both. Lucene's own TestCustomNorms and TestNorms index with computeNorm returning state.getLength() (TestCustomNorms.java:104, TestNorms.java:107).
  • The codec has a dedicated path for wide norms. CompetitiveImpactAccumulator keeps the pairs of norms outside the byte range in a separate, uncapped TreeSet (:32-35); Impact.norm is a long.
  • The format documents no limit. "ImpactLength is the total length of CompetitiveFreqDelta and CompetitiveNormDelta pairs" (Lucene104PostingsFormat.java:222-223), with no width. Level 0 stores it as a vlong (Lucene104PostingsWriter.java:407), and the format before #13585 (Lucene99, up to 9.11.x) wrote it as a VInt.
  • The only guard is a byte-norm assertion. "There are at most 256 impacts, that require at most 2 bytes each" (:523) holds only for byte norms. It came with #13585 as "at most 128 impacts"; #15160 changed the number; later block-size comment fixes on the same writer left it unchanged (#16491, merged; issue #15670 and its PRs #15671 and #15672, closed without merging). No review comment on #13585 or #15160 discusses the width.
  • Accepted, then unreadable. Nothing rejects wide norms or large frequencies at index time; with assertions off the failure appears only on read.
The devil's-advocate check130 words

The strongest case for "intended": Similarity and computeNorm are @lucene.experimental (Similarity.java:89, :147); every built-in Similarity uses byte norms; the writer's comment states the assumption; #10196 has been open since 2020, so wide norms are a niche configuration; and the triggering inputs are constructed.

Why it fails: "experimental" says the API may change, not that legal values may corrupt the index; the same writer handles the same quantity at level 0 with a varint, and the previous format did too; a niche configuration justifies a lower priority, not silent corruption; at the very least the writer should fail loudly instead of writing an unreadable segment. The cross-model refute review rated the intended-behaviour case weak, and the devil's-advocate verifier found that no intended-behaviour, documented-limit, misuse or unreachability argument survives.

Suggested fix

#

Recommended A. Fall back to one dominating pair when the list would not fit (validated)

When a level-1 impact list would not fit the short, write one pair (greatest freq, least norm) that dominates the whole block: +15/-3 lines in Lucene104PostingsWriter, no format change. The repro passes with assertions on and off, and so do the lucene104 codec and norms tests. Trade-off: looser score bounds for blocks that hit it.

List<Impact> impacts = level1CompetitiveFreqNormAccumulator.getCompetitiveFreqNormPairs();
writeImpacts(impacts, scratchOutput);
if (scratchOutput.size() > MAX_LEVEL1_IMPACT_BYTES) { // Short.MAX_VALUE - 64
  // Norms that do not fit in a byte can make up to LEVEL1_NUM_DOCS pairs competitive, too
  // many to encode with a short length: write one pair that dominates all of them instead.
  scratchOutput.reset();
  impacts = List.of(new Impact(impacts.get(impacts.size() - 1).freq, impacts.get(0).norm));
  writeImpacts(impacts, scratchOutput);
}
All options and trade-offs4 options · 571 words

Four options. A was built and validated on main 5adff78bb168; B, C and D were not built. None repairs segments already written by 9.12.0-10.6.0: those need reindexing.

A. Fall back to one dominating pair when the list would not fit (validated) (recommended)

#

Encode the level-1 impacts first; if they exceed Short.MAX_VALUE - 64 bytes (the margin leaves room for the position and payload fields that share the header-length short, at most 26 bytes), write a single pair (greatest freq, least norm) instead. That pair dominates every document of the block, which is all Impacts#getImpacts promises: impacts that "trigger scores that are greater than or equal to the impacts that actually appear in postings" (Impacts.java:41-43). Old readers read it unchanged. The diff (+15/-3) also adds the constant, moves the maxNumImpactsAtLevel1 update after the fallback and replaces the "at most 256 impacts" assertion with numImpactBytes <= MAX_LEVEL1_IMPACT_BYTES.

List<Impact> impacts = level1CompetitiveFreqNormAccumulator.getCompetitiveFreqNormPairs();
writeImpacts(impacts, scratchOutput);
if (scratchOutput.size() > MAX_LEVEL1_IMPACT_BYTES) { // Short.MAX_VALUE - 64
  // Norms that do not fit in a byte can make up to LEVEL1_NUM_DOCS pairs competitive, too
  // many to encode with a short length: write one pair that dominates all of them instead.
  scratchOutput.reset();
  impacts = List.of(new Impact(impacts.get(impacts.size() - 1).freq, impacts.get(0).norm));
  writeImpacts(impacts, scratchOutput);
}

Trade-offs

  • For a block that hits the fallback, block-max pruning gets a looser bound, so more documents of that 8,192-document range are scored. Only blocks whose impact list exceeds 32,703 bytes are affected: every block that is corrupted today, plus lists of 32,704-32,767 bytes, which read back correctly today with assertions off and would also get the single pair. No benchmark was run.
  • The repro and the exploration program exercise the fallback on a DOCS_AND_FREQS field only; no test covers it with positions, payloads or offsets (their header fields, at most 26 bytes, fit the 64-byte margin by arithmetic).
  • Backports would need the same change in Lucene912PostingsWriter (9.12.x and 10.0.x), Lucene101PostingsWriter (10.1.x-10.2.x) and Lucene103PostingsWriter (10.3.x).

  • The closest suites pass: org.apache.lucene.codecs.lucene104.*, TestCustomNorms, TestNorms, TestTermScorer and TestCompetitiveFreqNormAccumulator: 13 classes with the repro, 193 tests, 0 failures, 6 skipped.
  • :lucene:core:check -x test (google-java-format, ecj lint, forbidden APIs) passes.

B. Merge pairs down to a bound (#10196's idea)

#

"One idea would be to merge all impacts pairwise, taking the maximum term frequency and the minimum norm, until their number is under some hard-coded limit, e.g. 8" (#10196).

Trade-offs

Tighter bounds than A, and it also bounds space and decode time, which is what #10196 asked for. More code; applied to every block it changes scoring efficiency for all wide-norm users.

C. Variable-length lengths (format change)

#

Write ImpactLength and Skip1NumBytes as vints, as level 0 does.

Trade-offs

Exact bounds and no fallback, but it needs a format version bump and reader support for both encodings.

D. Fail loudly

#

Replace the assertions with a real check that throws at flush or merge.

Trade-offs

Stops silent corruption, but rejects legal documents and can abort merges; a stop-gap only.

Downstream note

#

Downstream products that let users plug in their own Similarity inherit the exposure; the Elasticsearch, OpenSearch and Solr similarities checked all use byte or constant norms and cannot trigger it.

How it was found

#

Semi-formal. Reading the field widths of the level-1 skip header while building a Z3 model of the postings skip layout raised the question; a Z3 integer program over the impact encoder's byte sizes then showed that wide norms can pass 32,767 bytes, and its byte counts match both repro sizes exactly. A JUnit test on the real jars confirmed it.

The method in full136 words

Method: semi-formal. The hypothesis came from code reading of the level-1 skip header's field widths while modelling the Lucene104 postings skip layout; the solver did not give the first signal on its own.

  • A Z3 integer program over the byte-size classes of writeImpacts bounds one level-1 impact list: with norm = field length, up to 53,150 bytes at 8,192 documents (overflow) but at most 28,638 at 4,096 (no overflow); with byte norms at most 1,792 bytes.
  • It shows that with exact field-length norms only negative wraps occur (loud failures); silent misreads need wider norm deltas.
  • Its byte counts match both repro inputs exactly: 49,147 bytes, stored as -16,389, and 73,724 bytes, stored as +8,188. The executed failures show the same values.
  • A JUnit test on the stock main jars then failed with assertions on and off.

History

#

Introduced in 9.12.0 by #13585 (merged 2024-07-31), which stored the length in a short; #15160 (10.4.0) doubled the block to 8,192 documents, so plain field-length norms became enough. Every release from 9.12.0 to 10.6.0 fails, and so does main; 9.11.1 passes. Not fixed upstream.

Finding record

#

LFV-183, snapshot of 2026-11-10

Registry title
Since 9.12.0 the default postings writer stores the byte length of a level-1 block's competitive impacts in a signed short, so with a custom Similarity whose norms do not fit in a byte, a term with 8,192 or more postings in one segment (4,096 before 10.4) can need more than 32,767 bytes: flush fails an assertion with -ea, and with -da the segment is written but that term's postings then throw when read or are read back wrong
Area
codecs / postings writer and reader (Lucene104 level-1 skip data, ImpactLength; the same field in the Lucene912, Lucene101 and Lucene103 formats)
Priority
Medium, rank 156: Since 9.12.0 a level-1 impact length stored in a signed short makes postings unreadable or silently misread with -da, but only under an opt-in Similarity with norms wider than a byte (none built in) and a term with thousands of competitive impacts per block.
Impact class
data corruption
Impact note
Hits only applications that set a custom Similarity whose norms do not fit in a byte (for example norm = field length, as Lucene's own TestCustomNorms does, or a wider encoding) on a field indexed with frequencies and norms, and that index one term into at least 8,192 documents of one segment (4,096 on 9.12.x-10.3.x) whose (freq, norm) pairs are mostly competitive with wide deltas (large custom term frequencies, or ordinary repeated tokens under a wide norm encoding), by flush or by merge; default codec, every release since 9.12.0; no Similarity shipped with Lucene can trigger it (byte norms bound the level-1 impacts at 1,792 bytes); with assertions off the bad segment is written without error, and that term's postings in it then throw on search and merge (CheckIndex reports them only at level 2 or 3; its default level reports the index clean), or are silently misread.
Summary
You index with the default codec and a custom Similarity whose norm is the field length (or another value that does not fit in a byte), and one term appears in 8,192 documents of a segment with growing frequencies, for example through Lucene's DelimitedTermFrequencyTokenFilter. You expect the term's postings to read back exactly as indexed. Instead the writer stores the length of the level-1 skip block's impact list, which here exceeds 32,767 bytes, in a signed short: with assertions on, flush fails; with assertions off, the segment is written and reading the term's postings throws 'numBytes must be >= 0', or, with wider norms, decodes wrong data (doc 0 with freq 1,602,871,807 instead of 1,000, and most documents missing).
