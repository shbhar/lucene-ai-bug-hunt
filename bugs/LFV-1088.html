An index-sorted segment still reads its points after an earlier segment crossed the hits threshold (main and branch_11x since #16857)

Since #16857 (unreleased: main and branch_11x), a segment that Lucene stops early by its index sort still reads its points once an earlier segment crossed the 1,000-hit threshold: 512 point doc IDs in the repro, up to about 1/7 of the segment's matching docs; 10.6.0 reads 0. Hits stay correct.

The finding in 30 seconds

#

Where a segment's index sort matches the search sort, Lucene stops early and should skip all points work there. Since #16857 the only off-switch is a call the wrapper does not forward, but the comparator reads a threshold flag that all segments share, so an earlier segment switches the work back on.

Background: two ways a sorted search saves work

#
  1. search(query, n, sort) counts hits exactly up to a threshold, 1,000 by default. Past it, Lucene may skip documents that cannot enter the top n.
  2. Points-based skipping: for a numeric sort field indexed with points, the comparator asks the points (BKD) index which documents can still beat the current n-th value and visits only those. It does so only when that cuts the documents to visit at least 8x.
  3. Index-sort early termination: in a segment already stored in the search's sort order, Lucene simply stops at the first document that cannot compete. Points-based skipping is then wasted work, and since 10.6.0 Lucene has switched it off per segment.

The finding, step by step

#
  1. Search a MultiReader over two indexes for the top 10 by a long field f. Index A has no index sort: 2,000 docs, f = 100 to 2,099. Index B is index-sorted by f: 4,096 docs, f = 0 to 4,095.
  2. A is searched first. Its 2,000 hits cross the default threshold of 1,000, and the top 10 so far is f = 100 to 109.
  3. You expect B to do no points work: it is stored in f order, so Lucene stops after 11 docs, and #16857's own IndexSortedLeafFieldComparator calls building iterators from points there "redundant work". 10.6.0 opens B's point tree 0 times.
  4. Instead, B's comparator sees the threshold flag that A set on the comparator all segments share. It estimates f <= 108 as selective (under 4,096 / 8 = 512 docs) and intersects B's BKD tree: 2 point-tree opens, 512 point doc IDs, and the iterator is never used. The top 10 (f = 0 to 9) is still right.
  5. How much is wasted depends on where A's bottom falls in B; only the ceiling grows with the segment, at most about 1/7 of its matching docs. A 1,000,000-doc B reads 512 point doc IDs after this A, 125,440 when A's top 10 starts at f = 124,700 and 136,192 after a spread top 10; indicatively 1.3x to 3x slower searches on that shape.

Who is affected

#

Users of main or branch_11x (11.0.0 unless fixed) who sort by the leading field of an index sort, a numeric points field, when an earlier segment of the same search is not terminated early and has over 1,000 hits: a MultiReader over differently sorted indexes, block and non-block segments, or a constant leading index-sort field. Results are correct.

Mechanism, terms and numbers687 words

Since #16857 ("Consolidate Sort pruning logic", merged 2026-10-29 to main and branch_11x, in no release), a segment whose index sort starts with the search sort gets its comparator wrapped in the new IndexSortedLeafFieldComparator (FieldValueHitQueue.java:190-191 at e1faeba08bde). When not paging, the wrapper avoids the delegate's skipping work, which its own comment calls "redundant work: it measurably slows down index-sorted searches" (IndexSortedLeafFieldComparator.java:31-33), only by hiding competitiveIterator() and not forwarding setHitsThresholdReached() (:86-97). But NumericComparator keeps hitsThresholdReached and queueFull on the comparator that every leaf shares (comparators/NumericComparator.java:59-60). Once an earlier segment of the same slice that is not terminated early has crossed the threshold, the wrapped segment's points builder passes its gate (:222-228) on the forwarded setScorer and setBottom calls, estimates the competitive range and, when it is selective, intersects the BKD tree (:426-445). The iterator is never used. 10.6.0 called disableSkipping() on such segments, which dropped the builder. Performance only: the hits are correct.

Terms

#
  • Hits threshold: IndexSearcher#search(query, n, sort) counts hits exactly up to TOTAL_HITS_THRESHOLD = 1,000 (IndexSearcher.java:100). The 1,001st hit makes countHit() call comparator.setHitsThresholdReached() (TopFieldCollector.java:64-77); a leaf collector created after that is told in its constructor (:56-59).
  • Competitive iterator: once the threshold is reached and the queue is full, NumericComparator's PointsCompetitiveDISIBuilder estimates how many points fall in the range that can still enter the top n and, when that is under iteratorCost >>> 3 (8x fewer than the query matches), intersects the BKD tree and hands the collector an iterator over the result (comparators/NumericComparator.java:363-446).
  • Index-sort early termination: FieldValueHitQueue.getLeafComparator wraps the comparator of each segment whose index sort starts with the search sort in IndexSortedLeafFieldComparator (FieldValueHitQueue.java:177-194, decided per segment, :202-214). It throws CollectionTerminatedException at the first non-competitive document once the threshold is reached (IndexSortedLeafFieldComparator.java:59-69).

The bug

#
  1. When not paging, the wrapper returns null from competitiveIterator() (IndexSortedLeafFieldComparator.java:86-89) and does not forward setHitsThresholdReached() (:91-97). Its comment explains why (:31-33): "Otherwise collection terminates anyway and the delegate's skipping, e.g. building iterators from points, is redundant work: it measurably slows down index-sorted searches." It still forwards setBottom (:53-56) and setScorer (:81-84); it has to, because compareBottom needs the bottom and other comparators of a multi-field sort need the scorer.
  2. The points builder's gate reads fields of the top-level comparator, protected boolean hitsThresholdReached; protected boolean queueFull; (NumericComparator.java:59-60), shared by every leaf comparator: if (hitsThresholdReached == false) return; and if (leafTopSet == false && queueFull == false) return; (:222-228).
  3. An earlier segment that is not terminated early sets both: countHit() -> NumericLeafComparator.setHitsThresholdReached() (:153-159) and setBottom() (:131-137).
  4. In the index-sorted segment, the forwarded setScorer() reaches PointsCompetitiveDISIBuilder.setScorer(), which takes the query's cost and runs the segment's first update, "update an iterator when we have a new segment" (:345-355); each forwarded setBottom() runs another. The gate passes, the estimate walks the tree (:426-429) and, when the range is selective, pointValues.intersect(visitor) builds an iterator (:441-445) that the wrapper never exposes.

Before #16857, 10.6.0's TopFieldCollector said "Early termination handles this segment; skipping work in the comparator is redundant." and called comparator.disableSkipping() on each such segment (TopFieldCollector.java:69-74 at 10.6.0), which set competitiveDISIBuilder = null (comparators/NumericComparator.java:110-114 at 10.6.0). #16857 removed disableSkipping (CHANGES 11.0.0, MIGRATE.md:31-32). queueFull being search-wide is legitimate; the comparator-wide hitsThresholdReached is what defeats the wrapper's only off-switch.

The numbers

#

Repro data (2,000 unsorted docs with f = 100 to 2,099, then 4,096 docs index-sorted by f, top 10 by f): when the sorted segment starts, the bottom is f = 109, so the competitive range is f <= 108. Its estimate is under 4,096 / 8 = 512, so it intersects one 512-point BKD leaf. The segment stops after 11 of its 4,096 docs. On main the test counts 2 point-tree opens (the estimate's tree and the one inside intersect), and the earlier counting version of the test counts 512 point doc IDs; 10.6.0 and main before #16857: 0.

Why it looks unintended

#
  • #16857's new wrapper says points work in such a segment "is redundant work: it measurably slows down index-sorted searches".
  • 10.6.0 switched it off per segment on purpose (disableSkipping, GITHUB#14399); #16857 removed that switch as a consolidation.
  • Not forwarding one call cannot stop work gated by a flag that every segment shares.
The full argument250 words
  • The PR's own words. IndexSortedLeafFieldComparator.java:31-33 (#16857, e1faeba08bde): "When paging, docs before the top value never fill the queue, so only the delegate can skip them. Otherwise collection terminates anyway and the delegate's skipping, e.g. building iterators from points, is redundant work: it measurably slows down index-sorted searches."
  • The released design. 10.6.0's LeafFieldComparator#disableSkipping javadoc (LeafFieldComparator.java:115-122 at 10.6.0): "Called by TopFieldCollector when the search sort is a prefix of this segment's index sort, so the collector can already terminate early and any extra skipping work in the comparator is redundant. This is a per-segment decision: a MultiReader may combine segments with different index sorts." CHANGES 10.6.0 (GITHUB#14399): "...so document skipping can be disabled per segment."
  • Older precedent. LUCENE-9599 (#10639, 2020): "As the early termination in this case is already handled in TopFieldCollector, we need to disable sort optimization in comparators."
  • A consolidation, not a policy change. The 11.0.0 CHANGES entry #16857 added (CHANGES.txt:39-47, labelled GITHUB#14399, the same issue number as 10.6.0's disableSkipping entry) says the pruning decisions are "consolidated into FieldValueHitQueue, and early termination through examining index sorts is handled by a new IndexSortedLeafFieldComparator class"; MIGRATE.md:31-32 lists disableSkipping as removed. The PR's review is about document blocks; mixed segments and the shared flag never come up.
  • No test covers it. TestTopFieldCollectorEarlyTermination.testMultiReaderWithDifferentIndexSorts (:283) and testQueueFilledInEarlierSegment (:548) check hits only.
  • Precedent for the class of bug. #13498, "Avoid performance regression by constructing lazily the PointTree in NumericComparator", is listed under Bug Fixes in 9.11.1 and 10.0.0.
The devil's-advocate check129 words

The strongest case for "intended" (built by an intended-behaviour checker): the flags are comparator-wide on purpose (since LUCENE-9449, 2020), and upstream TestNumericComparator sets comparator1.hitsThresholdReached = true before creating a leaf comparator to emulate a later leaf; the wrapper is package-private and its @param paging javadoc only says what is "passed through" when paging; no public javadoc promises "no points work"; the cost is bounded.

Why it fails: the shared flag was harmless while an early-terminated segment had no points builder (10.6.0 dropped it per segment). #16857 replaced that switch with a mechanism, not forwarding one call, that works only if the delegate's state is per segment, and its own comment states the goal it then misses. Bounded cost and the missing javadoc promise lower the priority, not the verdict.

Suggested fix

#

Recommended A per-leaf threshold flag in NumericLeafComparator (validated)

Give NumericLeafComparator its own threshold flag, set in its setHitsThresholdReached(), and gate the points update on it (3 lines). Since #16857 every normal leaf is told at construction; a wrapped leaf never is. Validated with gradle: the repro passes and 217 search test classes pass; one unit test that writes the shared field needs a small adaptation.

A per-leaf threshold flag in NumericLeafComparator (validated) (recommended)

#

In comparators/NumericComparator.java: NumericLeafComparator records whether it was told itself, and CompetitiveDISIBuilder.updateCompetitiveIterator() tests that instead of the comparator-wide field. Since #16857, TopFieldLeafCollector tells every leaf at construction once the threshold was crossed earlier (TopFieldCollector.java:56-59) and countHit() tells it when it crosses it (:70-75), and MultiLeafFieldComparator forwards the call to the first comparator of a multi-field sort (MultiLeafFieldComparator.java:95-99), so in Lucene's own TopFieldCollector paths every normal leaf keeps its pruning; only a wrapped, non-paging leaf, which the wrapper never tells, stops doing points work. Code that writes the protected field directly is the first trade-off. The same gate also guards the doc-values-skipper builder.

     private final CompetitiveDISIBuilder competitiveDISIBuilder;
+    // Whether this leaf was told that the hits threshold is reached. A leaf that terminates early
+    // by its index sort is not told (IndexSortedLeafFieldComparator), so it does no points work.
+    private boolean leafHitsThresholdReached;
@@ NumericLeafComparator.setHitsThresholdReached()
       hitsThresholdReached = true;
+      leafHitsThresholdReached = true;
@@ CompetitiveDISIBuilder.updateCompetitiveIterator()
-      if (hitsThresholdReached == false) {
+      if (leafComparator.leafHitsThresholdReached == false) {
         return;
       }

Trade-offs

  • It changes what the protected comparator-wide field means for the gate. Upstream TestNumericComparator.testEmptyCompetitiveIteratorOptimization sets comparator1.hitsThresholdReached = true directly (TestNumericComparator.java:215 and three siblings) and fails with the fix, expected:<2147483647> but was:<0>; the adaptation makes those four helpers call leafComparator.setHitsThresholdReached() instead, "as TopFieldCollector does for a leaf that starts after the threshold was reached". Subclasses outside Lucene that set the field directly would need the same change.
  • It relies on #16857's constructor-time call to tell later normal leaves. LFV-1057's fixes keep that (a cost guard) or move it into setScorer(); both combine with this fix (both repros pass).
  • Scope: it covers NumericComparator only. TermOrdValComparator (STRING sort) has its own comparator-wide hitsThresholdReached (comparators/TermOrdValComparator.java:110, set at :318, read at :418), so the STRING analogue (not part of this finding) would remain; it could get the same per-leaf flag.
  • Open PR #16163 (search_after with the doc-values skipper) rewrites the same gate line into if (hitsThresholdReached == false && leafTopSet == false) {, so the two conflict as text; they appear to compose as if (leafComparator.leafHitsThresholdReached == false && leafTopSet == false) { (not built or tested: rebase onto its current head and run both changes' tests).

Restore a per-segment skip switch (not validated)

#

Give LeafFieldComparator back a hook like 10.6.0's disableSkipping() (default no-op; NumericLeafComparator drops its builder; MultiLeafFieldComparator forwards it) and have IndexSortedLeafFieldComparator call it on its delegate when not paging.

Trade-offs

Keeps the protected field's meaning and needs no test change; it is the 10.6.0 behaviour. But it re-adds a method #16857 removed on purpose (CHANGES 11.0.0, MIGRATE.md:31-32), and since the wrapper and the comparators live in different packages the hook has to be public (perhaps @lucene.internal).

Stop forwarding setScorer/setBottom in the wrapper (not viable)

#

The wrapper could hide the calls that drive the builder.

Trade-offs

compareBottom needs the bottom set by setBottom, and other comparators of a multi-field sort need the scorer, so this breaks sorting.

Downstream note

#

Downstream engines on Lucene 11 or 12 snapshots (branch_11x, main) that combine differently sorted indexes or segments in one sorted search can pay this extra CPU, under the conditions above, until it is fixed; the hits are unaffected.

How it was found

#

While reviewing newly merged upstream code, reading the #16857 diff raised the question whether the new wrapper really stops the comparator's points work after a mixed segment. A probe counting point reads showed 10,752 vs 0 point doc IDs with the same top 10. It was reduced to one test, modelled in TLA+ and checked with an exhaustive multi-leaf harness.

The method in full243 words

Method: non-formal (the first signal came from code reading and an executed probe; the formal model came later).

  • Lead. A review of newly merged upstream code read the #16857 diff.
  • Probe. A differential count through the public FilterLeafReader API with a counting PointValues/PointTree wrapper, on upstream main, on main before #16857 and on 10.6.0, identical top 10 in every run: in the MultiReader and block/non-block shapes 10,752 point doc IDs on main vs 0 before #16857 and on 10.6.0; in the no-op leading-field shape 10,752 on main vs 0 with the fix (before #16857 that segment is not terminated early, so its 10,752 there is real pruning; not run on 10.6.0).
  • Reduction. One JUnit test, run on main and the commit bracket with assertions on and off, and on three releases (10.6.0 with assertions on and off, 10.5.2 and 9.12.3 with assertions off); a later review replaced it with the one-method test above.
  • Model. A TLA+ model of the per-leaf collector/comparator protocol with leaf kinds and the wrapper (TLC): the invariant NoETWork (no points work in a leaf the index sort terminates, when not paging) is violated by upstream main and holds for the code before #16857 and for every per-leaf-flag variant; the properties that no first update is lost and that paging keeps its updates hold everywhere.
  • Exhaustive harness. A bounded-exhaustive multi-leaf harness with a per-leaf points-work counter: 0 wrong results; points work in wrapped, non-paging leaves on main only.

LFV-1088, snapshot of 2026-11-03

Registry title
Since #16857 (upstream main and branch_11x, unreleased), a segment that its index sort terminates early can still build an unused points-based competitive iterator when an earlier segment of the same field-sorted search crossed the hits threshold without early termination: NumericComparator keeps hitsThresholdReached on the comparator that all leaves share, so IndexSortedLeafFieldComparator's not forwarding setHitsThresholdReached() no longer stops the delegate's BKD work (512 point doc IDs read in the repro, up to about cost/7 per segment, where 10.6.0 reads 0; performance regression, results correct)
Area
search / field sorting: index-sort early termination (IndexSortedLeafFieldComparator) + NumericComparator points-based sort pruning (competitive iterator)
Priority
Low, rank 929: Performance only, with correct results, in unreleased main and branch_11x. With an index sort, a field-sorted search wastes up to about cost/7 point reads in each segment the sort terminates early, but only after an earlier segment without early termination crossed the hits threshold. That mixed-leaf layout is uncommon, and the bug can be fixed before 11.0.0.
Impact class
minor
Impact note
Performance regression only, on upstream main and branch_11x since #16857 (no release has it; fixable before 11.0.0): a field-sorted IndexSearcher#search(query, n, sort) with the default codec and searcher, sorted by the leading index-sort field (a numeric field indexed with points), reads points in each segment that its index sort terminates early once an earlier segment of the same slice, not terminated early, has crossed the default 1,000-hit threshold (a MultiReader over indexes with different or no index sorts, a parent-field index mixing block and non-block segments, or an (k, f) index sort with a constant k in some segments); the iterator it builds is never used, the waste is bounded by about cost/7 point doc IDs per such segment (each intersection must cut the current cost 8x) and depends on where the earlier segment's bottom falls (512 in the repro; 512, 125,440 or 136,192 for different earlier top 10s in a 1,000,000-doc segment that collects 11 documents), indicative timings on a shared host were about 1.3x on a typical shape and 2.7-3x with a bottom just under cost/8, and the top hits are identical in every executed shape.
Summary
You search a MultiReader over two indexes for the top 10 by a long field f: the first index has no index sort and 2,000 hits, so the default 1,000-hit threshold is crossed there, and the second (4,096 documents) is sorted by f, so the search stops in it after a few documents. You expect that sorted segment to read no points: the new IndexSortedLeafFieldComparator says the comparator's skipping work, 'e.g. building iterators from points, is redundant work' there, and 10.6.0 reads 0. Instead, since #16857 the comparator still sees the threshold flag that the first segment set on the comparator shared by all segments, so it walks the sorted segment's BKD tree and builds a points iterator that nobody uses (512 point doc IDs here, up to about cost/7 per segment); the top 10 is still right, only the work is wasted.
