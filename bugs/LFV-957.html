The Lucene 10.6.0 release notes credit the CheckIndex .si change to GITHUB#17820, an issue that does not exist, instead of GITHUB#7820

In the Lucene 10.6.0 release notes, the entry "CheckIndex now reports which segment's .si file could not be read" cites GITHUB#17820 instead of GITHUB#7820, so its link on the published Changes page is a 404. The extra digit came in with the 10.x backports of #16788; main is correct.

The finding in 30 seconds

#

One digit in one line of the 10.6.0 release notes: the number of the issue the change belongs to.

Background: issue numbers in the release notes

#
  1. lucene/CHANGES.txt lists each release's changes. By convention every entry starts with the number of its issue or pull request, written GITHUB#XXX (CONTRIBUTING.md).
  2. When the docs are built, changes2html.pl turns every GITHUB#N into a link to https://github.com/apache/lucene/issues/N. It does not check that N exists.
  3. Main keeps a copy of each stable release's section. After a release, the release manager copies the released section back to main by hand, in an editor (release wizard step "Synchronize CHANGES.txt").

The finding, step by step

#
  1. You open the Lucene 10.6.0 Changes page (or lucene/CHANGES.txt in the 10.6.0 source release) and find the Improvements entry "CheckIndex now reports which segment's .si file could not be read".
  2. You expect its issue link to lead to #7820, "CheckIndex cannot "fix" indexes that have individual segments with missing or corrupt .si files ...": the issue that the feature commit, CheckIndex.java and main's copy of the entry all name.
  3. Instead the entry says GITHUB#17820, and the GitHub issue page for 17820 returns 404. The newest issue or PR is #16959 (2026-11-01), so 17820 cannot exist yet.
  4. Why: on 2026-10-22 the backports of #16788 to branch_10x and branch_10_6 rewrote this entry to add #16788's wording and, in the same hunk, turned GITHUB#7820 into GITHUB#17820. Main's commit of the same PR kept 7820. 10.6.0 shipped from branch_10_6.

Who is affected

#

Readers of the 10.6.0 notes who follow this entry's issue link get a 404 instead of #7820. Nothing else: no code, index or search effect, and the entry text still leads to the change. Unfixed, it stays in branch_10_6's 10.6.0 section, and the manual release-time sync could copy it into main.

Mechanism, terms and numbers486 words

The 10.6.0 Improvements entry reads "* GITHUB#17820: CheckIndex now reports which segment's .si file could not be read, rather than only that a commit point was unreadable. SegmentInfos throws CorruptSegmentInfoException, carrying the segment name and the underlying failure, when a .si file is missing or corrupt; other I/O failures, such as transient ones, propagate unchanged. (Gokul Manoj, Serhiy Bzhezytskyy, Alex Reelsen)". The change belongs to issue #7820 (open, "CheckIndex cannot "fix" indexes that have individual segments with missing or corrupt .si files because sanity checks will fail trying to read the index initially. [LUCENE-6762]"): the feature commit, CheckIndex.java, TestCheckIndex and main's copy of the entry all name 7820. Issue 17820 does not exist, so the link on the published 10.6.0 Changes page returns 404. The extra digit came in on 2026-10-22 with the direct-push backports of #16788 to branch_10x and branch_10_6, which rewrote the entry to add #16788's wording; main's commit of the same PR kept 7820. It is a documentation defect with no code, index or search effect. The fix is a one-character edit on branch_10_6, ideally before the release-time CHANGES sync, a manual edit in which the release manager copies the 10.6.0 section back to main.

The claim

#
  • At the 10.6.0 tag, CHANGES.txt:6 is the Lucene 10.6.0 heading and CHANGES.txt:112 starts the entry: * GITHUB#17820: CheckIndex now reports which segment's .si file could not be read, rather than only that. The published 10.6.0 Changes page, line 293, links it to the GitHub issue page for 17820 (HTTP 404) and has no link to issues/7820. The page is byte-identical to the staged RC1 page (same sha256).

The right number is 7820

#
  • The feature commit f30bd1b9b4f: "GITHUB#7820: report which segment's .si could not be read (#16476)"; its CHANGES hunk adds * GITHUB#7820:.
  • CheckIndex.java:639 on main (:603 at 10.6.0): // https://github.com/apache/lucene/issues/7820: also attempt to open any older commit; TestCheckIndex.java:249 (:255 at 10.6.0) cites the same issue.
  • Main's copy of the entry, CHANGES.txt:562 at 645d4fe14a20: * GITHUB#7820: .... Main's commit of #16788 itself, 330ee57b167, kept * GITHUB#7820:.

How the digit got in

#
  1. 2026-10-05: #16476 adds the entry on main and on branch_10x (f30bd1b9b4f, 6758e9c3c5c) as GITHUB#7820. 2026-10-14: branch_10_6 is cut and inherits it.
  2. 2026-10-21: #16788 (by spinscale; merged by romseygeek per the PR's GitHub record) extends the wording on main and keeps 7820. 2026-10-22: the changelog sync 7cecf795236 copies branch_10_6's text of that moment (older wording, 7820) into main's 10.6.0 section.
  3. 2026-10-22: the direct-push backports of #16788 to branch_10x (081f0abb6e3) and branch_10_6 (1b61ada0305) change -* GITHUB#7820: to +* GITHUB#17820: in the same hunk that adds the #16788 wording and credit. git log -S'GITHUB#17820' on branch_10_6 finds only 1b61ada0305.
  4. 2026-10-26: RC1 4ae946e5a9b, released as 10.6.0 on 2026-10-29. changes2html.pl:28, 574-576 turns the number into the dead link; neither it nor the checks the verifiers inspected (the disabled changelog workflow, smokeTestRelease.py) validate link targets.
Exposure and likelihood294 words
  • Who meets it: readers of the 10.6.0 notes (CHANGES.txt in the source release, the published 10.6.0 Changes page) who follow this one entry's issue link. It is not tied to any setting or API.
  • What they get: a 404 when they follow the link, a routine way to learn more about a change. The entry text and CheckIndex.java still lead to #7820, so the cost is a detour.
  • What does not happen: no effect on code, indexes, queries or results.
  • Scale: one line in one release line (10.6.x). Unfixed, it stays in branch_10_6's retained 10.6.0 section (already below the new 10.6.1 section), so later 10.6.x CHANGES files would repeat it. Main has the right number. The release wizard's "Synchronize CHANGES.txt" step asks the release manager to copy the released section back to main (releaseWizard.yaml:1399-1404); it is a manual edit in an editor followed by a "Sync CHANGES" commit (:1424-1443), not a mechanical copy. Main has had no such commit for 10.6.0 yet, so main's 7820 could become 17820 if the section is copied as it is; the release manager may equally reconcile it by hand (an inference from the documented step).
  • Projection, not an observation: once the tracker reaches 17820 the link would point to an unrelated item; the tracker is at #16959.
  • How much it matters. For it: readers who follow the published link get a 404, the fix is one character, and Lucene has merged this kind of fix before. Against it: main is already right, a branch_10_6 edit cannot repair the published 10.6.0 files, and the entry text and CheckIndex.java still lead to #7820. Whether a dead link counts as user impact is a judgement call, not a demonstrated software defect.

Why it looks unintended

#
  • Every other source names #7820: the feature commit, CheckIndex.java, TestCheckIndex, and main's commit of the same #16788 change.
  • CONTRIBUTING.md: an entry "should start with the issue or pull request number GITHUB#XXX"; 17820 is neither.
  • Lucene has fixed wrong CHANGES numbers before, e.g. GITHUB#2472 -> GITHUB#12472 (2023) and "Fix up PR number in changes entry for #16428" (2026).
The full argument147 words
  • The convention. CONTRIBUTING.md:107 (10.6.0: line 101): "A CHANGES entry should start with the issue or pull request number GITHUB#XXX that is followed by the description of the change and contributors' name."
  • Main and the branch are meant to agree. dev-tools/scripts/diff_lucene_changes.py:24-29: "It's best to keep these 1) identical and 2) matching what changes were actually backported to be honest to users".
  • Most likely an accidental extra digit (an inference; nothing records why). The backport hunk changes the number next to the intended wording change, the commit message does not mention renumbering, and no comment on #16788, #16476, #7820 or the backport commits mentions 17820.
  • Precedent. 18a71043c80 "Fix up PR number in changes entry for #16428" (2026-08-03, GITHUB#16408 -> GITHUB#16428); 51ade888f32 "Update wrong PR number in CHANGES.txt" (2023-09-19, GITHUB#2472 -> GITHUB#12472) and its siblings ac62c58d46c, f5d5dc289ed; 367cd2ea95b "Associate correct PR with DrillSideway change in CHANGES" (2022).
The devil's-advocate check188 words

Strongest case for leaving it (the intended-behaviour devil's advocate): CHANGES is curated prose that the release manager reworks into the release notes (the wizard's draft-release-notes step says to edit its contents "into a more concise format for public consumption", releaseWizard.yaml:606; that step writes the wiki release notes and does not edit CHANGES.txt); CONTRIBUTING only says "should"; a wrong link is no reason to respin a release; and main's wording differs anyway, so the entry is in flux until the release sync.

Why it fails: each point is about severity or process, not intent. Nothing in code, tests, PRs or lists treats 17820 as meaningful, the published 10.6.0 page links a 404, and the project has corrected exactly this kind of slip before. The fix is a text edit, not a respin. An independent reviewer from another model family (OpenAI GPT-5.6, reading only) rated the 'intended' argument weak; the earlier refute review (reading only, so it could not run code) returned a procedural "not real" (it expected a failure on main, which is correctly unaffected) and it called the release text "a genuine, minor documentation typo".

How it was found

#

Non-formal. While re-reading the 10.6.0 release notes, a finder resolved all 110 distinct GITHUB# numbers of the section through the issue tracker: 109 matched their entries and 17820 did not exist. An offline check of the numbers and git history then traced the digit to the #16788 backports.

The method in full141 words
  • Tracker check (a hunt unit): every GITHUB# number of the RC's 10.6.0 section (110 distinct, 112 occurrences) was looked up through the GitHub issues API and its title compared with the entry; 109 match, 17820 is a 404.
  • Offline check: no number may be newer than every issue or PR the release branch's commit subjects name (max #16910 on the RC branch); it fails on the RC text and passes on main's text and on the fixed text. Its known limit: it false-fails on 9.12.3, whose commit subjects omit a valid number.
  • Verification: an independent reproducer with its own oracle (tracker maximum, and the entry), an independent reviewer from another model family (OpenAI GPT-5.6) and an intended-behaviour devil's advocate all called it real; an adjudication confirmed it (high). The repro was then reduced to one test with one assertion.

You expect it to lead to GITHUB#7820, the issue the feature commit, CheckIndex.java and main's copy of the entry all name; instead the entry says GITHUB#17820 and its GitHub issue link (number 17820) returns 404.
