FSTCompiler.add can drop a key passed as an IntsRef slice at a non-zero offset

On main, FSTCompiler.add passes an IntsRef's length where Arrays.mismatch expects an end index, so a key added as a slice at offset 2 or more can silently go missing: add "ab" -> 1, then "ac" -> 2 at offset 2, and Util.get(fst, "ac") returns null. Unreleased: main and branch_11x.

The finding in 30 seconds

#

Before adding a key, add() counts the leading labels it shares with the previous key, using Arrays.mismatch(a, aFrom, aTo, b, bFrom, bTo). It passes the slice's length as bTo, which is an end index. For "ac" at offset 2, length 2, the compared range is empty, so 0 shared labels instead of 1, and the shared 'a' node is duplicated.

Background

#
  1. An FST is built by adding keys in sorted order; each key is a sequence of int labels, for example 'a', 'c'.
  2. IntsRef is a window into an int[]: the key is ints[offset, offset + length). add() takes only IntsRef.
  3. For each new key the compiler keeps the nodes it shares with the previous key and freezes (compiles) the previous key's remaining nodes, so the shared-prefix length must be right.

The finding, step by step

#
  1. Build an FST with the default builder: add "ab" -> 1 as an ordinary IntsRef, then "ac" -> 2 passed as a slice, new IntsRef(new int[] {0, 0, 'a', 'c'}, 2, 2) (offset 2, length 2), and compile.
  2. You expect Util.get(fst, "ac") to return 2, as it does on 10.6.0 and on main when the same key starts at offset 0.
  3. You get null with assertions off: compile() succeeds and "ab" still returns 1, but "ac" is not in the FST. With assertions on, add() fails with arc[numArcs-1].label=97 new label=97 numArcs=1.
  4. Why: to count the labels "ac" shares with "ab", add() calls Arrays.mismatch(..., input.ints, input.offset, input.length). The last argument is an end index, so it compares ints[2, 2), which is empty, and finds 0 shared labels instead of 1. The 'a' node is frozen too early and the root gets a second 'a' arc.
  5. Any slice at offset 2 or more loses its key when it shares more than length minus offset labels with the previous key; an offset larger than the length makes add() throw IllegalArgumentException.

Who is affected

#

Only code that calls the expert FSTCompiler.add itself with IntsRef slices at offset 2 or more, or re-adds one input at a non-zero offset with a merging Outputs. No Lucene production code does; one test tool re-adds harmless offset-1 refs. Two keys suffice, silently with assertions off. Unreleased: a fix before 11.0 removes it.

Mechanism, terms and numbers497 words

FSTCompiler.add(IntsRef, T) first counts how many leading labels the new input shares with the previous one. Since #13924 it calls Arrays.mismatch(lastInput.ints(), 0, lastInput.length(), input.ints, input.offset, input.length); the last argument of Arrays.mismatch is an exclusive end index, so for an input at offset o only length - o labels are compared. When the true prefix is longer, it comes out too short: the compiler freezes a node the new key still needs and gives its parent a second arc with the same label. With assertions off compile() returns normally and the FST lacks the key ("ab" -> 1, then "ac" -> 2 at offset 2: Util.get("ac") is null); with assertions on an assert fires inside add(). No Lucene production caller passes such a slice, and no release has the bug: 10.6.0 and older use a loop that honours the offset.

Terms

#
  • Shared prefix: the number of leading labels the new input has in common with the previous one. "ab" and "ac" share 1 ('a').
  • Arrays.mismatch(a, aFromIndex, aToIndex, b, bFromIndex, bToIndex): the JDK method returns the first index where the two ranges differ; both to-indexes are exclusive, and it throws IllegalArgumentException when a from-index is larger than its to-index.

The bug (main f794ff5a505c)

#
  1. The call. FSTCompiler.java:873-876: Arrays.mismatch(lastInput.ints(), 0, lastInput.length(), input.ints, input.offset, input.length). The 6th argument should be input.offset + input.length.
  2. The numbers. The previous input "ab" is compared over [0, 2); the new input's range is [2, 2), empty. mismatch returns 0, so pos = 0 and prefixLenPlus1 = 1 instead of 2 (:876, :878).
  3. Frozen too early. freezeTail(1) (:890) compiles every node of "ab" from depth 1 on, including the 'a' node that "ac" should extend.
  4. Duplicate arc. The loop at :893-895 adds the new input's arcs from depth 1: the root gets a second arc labelled 'a'. The only check is the assert in UnCompiledNode.addArc (:1110), so with assertions off nothing stops it. A lookup of "ac" takes the first 'a' arc, whose node has only 'b', and returns null, while "ab" still answers 1.
  5. Only this line. The rest of add() reads input.ints[input.offset + ...] (:894, :909, :919, :937).

Which slices go wrong

#

The computed prefix is min(true prefix, length - offset):

  • offset 1 is harmless for distinct sorted keys (their true prefix is at most length - 1); copying an FST through IntsRefFSTEnum, whose refs have offset 1, comes out right (executed probe);
  • offset 2 or more loses a key whose true prefix is longer than length - offset (the repro);
  • offset larger than length: add() throws IllegalArgumentException: fromIndex(3) > toIndex(2) for a valid input (executed probe, offset 3, length 2);
  • the same input added twice in a row, which add() allows with a merging Outputs, breaks already at offset 1: with ListOfOutputs the lookup gives 1 instead of the merged [1, 2] (executed probe).
Exposure and likelihood188 words
  • Who is hit. Applications that build FSTs themselves and pass keys as slices of a shared int[] (for example many keys packed into one buffer), or re-add an input at a non-zero offset with a merging Outputs. Packing alone is not enough: such a caller loses, deterministically, each key whose true shared prefix with the previous key is longer than length - offset.
  • No in-tree production caller. Term-index codecs, synonym and char maps, hunspell and CJK dictionaries and suggesters pass offset-0 refs from IntsRefBuilder or Util. The one in-tree place found that passes offset refs is a test-class tool, TestFSTDirectAddressing.recompile (TestFSTDirectAddressing.java:325-337, reached only from that class's main()): it re-adds IntsRefFSTEnum's offset-1 refs, which is harmless for distinct sorted keys, so it never tripped the bug.
  • Default vs opt-in. Default builder settings, but FSTCompiler is an expert @lucene.experimental API (FSTCompiler.java:68) that the application drives directly.
  • Silent. With assertions off, as in production, compile() succeeds and the key is missing; only with assertions on does add() fail.
  • Timing. On main and branch_11x only: 11.0.0 would be the first release with it.

Why it looks unintended

#
  • add() documents one precondition, IntsRef#compareTo order, and compareTo honours the offset; IntsRef is defined as a slice (offset + length).
  • The rest of add(), and every other Arrays.mismatch over a Ref slice in core, uses offset + length.
  • Through 10.6.0 the loop started at input.offset; #13924 was a refactor that announced no behaviour change.
The full argument205 words
  • The contract. add() javadoc: "The provided input must be sorted after the previous one according to IntsRef#compareTo" (FSTCompiler.java:841-842); compareTo compares [offset, offset + length) (IntsRef.java:106-114). IntsRef: "Represents int[], as a slice (offset + length) into an existing int[]" (IntsRef.java:21-25). Nothing asks for offset 0.
  • Consistency. add() reads input.ints[input.offset + ...] at :894, :909, :919, :937. The other Arrays.mismatch calls over Ref slices pass offset + length: IntSequenceOutputs.java:48-54, CharSequenceOutputs.java:48-54, ByteSequenceOutputs.java:49-55, StringHelper.java:45-51.
  • History. From LUCENE-2792 (994aaec2ef5, 2010) to 10.6.0 the prefix loop started at int pos2 = input.offset. #13924 replaced it: empty description, one approving review ("the change does look clearer and simpler"), no CHANGES entry.
  • Lucene emits offset refs itself. IntsRefFSTEnum sets current.offset = 1 (IntsRefFSTEnum.java:46), and a test-class tool feeds those refs straight back into add() (TestFSTDirectAddressing.java:325-337).
  • Precedent. An ignored Ref offset was fixed as a bug before: #258 (LUCENE-10052, "FSTTermsReader.IntersectEnum was illegally ignoring BytesRef.offset", merged 2021-08-25).
  • Tests. No upstream test method passes a triggering slice to add(), and no test asserts an offset-0 rule; the only test source that passes offset refs (the offset-1 tool above) cannot trigger it.
The devil's-advocate check202 words

Strongest case for "not a bug": IntsRef is @lucene.internal and FSTCompiler @lucene.experimental; every Lucene production caller found passes offset-0 refs, and IntsRefBuilder.get() asserts "Modifying the offset of the returned ref is illegal" (IntsRefBuilder.java:111). A maintainer could answer "pass offset-0 refs"; one executed cross-model review took this view on scope alone, while it reproduced the failure and agreed with the root cause and the fix.

The tags render as "WARNING: This API is experimental and might change in incompatible ways in the next release." (@lucene.experimental) and "NOTE: This API is for internal purposes only and might change in incompatible ways in the next release." (@lucene.internal) (RenderJavadocPlugin.java:502, :506); "for internal purposes only" does give a maintainer room to call this unsupported usage. Why it still fails: neither tag states an input rule; IntsRef is the only input type of the public add() (FSTCompiler.java:848, no other overload); add()'s only stated precondition is IntsRef#compareTo order; the method honours the offset at :894, :909, :919 and :937; the IntsRefBuilder assert guards the builder's own ref; and the offset was handled from 2010 until #13924. The fix is one argument either way.

Suggested fix

#

Recommended (a) Pass input.offset + input.length as the end index (recommended, validated)

Pass the end index: at FSTCompiler.java:875 change the last Arrays.mismatch argument from input.length to input.offset + input.length. With it the repro passes (assertions on and off), the whole org.apache.lucene.util.fst test package passes (38 tests, 5 skipped, 0 failures) and the core format check passes.

      int mismatch =

              lastInput.ints(),
              0,

              input.ints,
              input.offset,
              input.offset + input.length);

How it was found

#

Code reading of FSTCompiler.add's shared-prefix computation against what add() and compile() promise: the Arrays.mismatch end index ignores the offset, unlike every other use of the input in the method. A one-test JUnit on main witnessed it, and running it on builds of the introducing commit and its parent pinpointed #13924.

The method in full104 words

Non-formal method: code reading of FSTCompiler (what add() and compile() promise and what the code relies on) checked the prefix computation against Arrays.mismatch's signature. Plain-program probes then mapped which offsets fail (0 and 1 right for distinct keys, 2 losing the key, 3 with length 2 throwing), and the one-test JUnit became the repro.

The history step built lucene-core, lucene-codecs and lucene-test-framework for a2483062d67 and its parent from the full history with plain javac and ran the same test on both, using current main's outside test jars (randomizedtesting, junit, hamcrest) rather than each commit's own: a parent/child check, not a bisection search.
