The default compound reader's listAll() returns its file names unsorted, although Directory.listAll() requires sorted order

listAll() on the default codec's compound-file reader returns the right names in HashMap order, [_0.fnm, _0.fdx, _0.fdt, _0.fdm] for a one-document segment, although every Directory must return them sorted. No Lucene production code lists a compound reader, so only outside code that relies on the order is hit; every release since 6.0.0.

The finding in 30 seconds

#

Every Lucene Directory promises sorted names from listAll(). The reader for the default codec's compound files is a Directory too, but returns its names in hash-map order.

Background in two steps

#
  1. A compound file packs a segment's small files (_0.fnm, _0.fdt, ...) into one .cfs data file plus a .cfe table of contents. Flushed segments use it by default (IndexWriterConfig.DEFAULT_USE_COMPOUND_FILE_SYSTEM = true).
  2. Lucene reads the sub-files through a read-only Directory view of that file, a CompoundDirectory, which the codec returns from compoundFormat().getCompoundReader(dir, si).

The finding, step by step

#
  1. Index one empty document with the default codec. With the default compound-file setting, segment _0 is stored as one compound file holding 4 sub-files.
  2. Open it as the codec does, si.getCodec().compoundFormat().getCompoundReader(dir, si), and call listAll(). The reader is a Directory.
  3. You expect [_0.fdm, _0.fdt, _0.fdx, _0.fnm]: Directory.listAll() says "The output must be in sorted ... order", and ByteBuffersDirectory, FSDirectory and SimpleText's compound reader all sort.
  4. Instead you get [_0.fnm, _0.fdx, _0.fdt, _0.fdm], the reverse, with no error: the reader keeps the names in a HashMap and returns its key order.
  5. Code that trusts the order is silently wrong: Arrays.binarySearch on this listing finds only _0.fdx and reports the other 3 names, which are there, as missing.

Who is affected

#

Only code outside Lucene that opens a compound reader through the expert codec API and relies on listAll() order (a binary search, merge-join or diff of listings). Default codec and settings, silent. Lucene's indexing, search, merges and CheckIndex open sub-files by name; its tests that list one ignore the order.

Mechanism, terms and numbers385 words

Directory.listAll() must return file names in sorted (String#compareTo) order. The default codec's compound reader, Lucene90CompoundReader (the CompoundDirectory that CompoundFormat.getCompoundReader(dir, si) returns for a segment stored as a .cfs/.cfe compound file), returns the right names in HashMap iteration order instead: [_0.fnm, _0.fdx, _0.fdt, _0.fdm] for a one-document segment, where the sorted listing is [_0.fdm, _0.fdt, _0.fdx, _0.fnm]. No error is raised. Every other in-tree Directory that holds files sorts, SimpleText's compound reader included (wrappers such as FilterDirectory pass the wrapped listing through). No Lucene production code lists a compound reader, so indexing, search, merging and CheckIndex are unaffected, and Lucene's tests that list one do not depend on the order; outside code that binary-searches, merge-joins or diffs a compound listing gets a silently wrong answer. Present since 6.0.0, when LUCENE-6835 made sorted output part of the contract and sorted the other implementations. The fix is one Arrays.sort call.

Mechanism (main 5adff78bb168)

#
  1. Opening the compound file, Lucene90CompoundReader.readMapping stores each sub-file id (the name without the segment name, such as .fnm) in HashMap.newHashMap(numEntries) (Lucene90CompoundReader.java:141).
  2. listAll() (:214-225) copies entries.keySet() into an array, prepends the segment name and returns it, with no sort. This is the fix site. The order is the HashMap's iteration order: the same for the same names on the same JDK, but unspecified.
  3. Lucene90CompoundReader extends CompoundDirectory extends Directory. Directory.listAll() says "Returns names of all files stored in this directory. The output must be in sorted (UTF-16, java's String#compareTo) order." (Directory.java:52-58). CompoundDirectory ("A read-only Directory that consists of a view over a compound file", CompoundDirectory.java:26-32, @lucene.experimental) makes the write methods final: deleteFile and rename are documented to throw UnsupportedOperationException (:45-63), copyFrom, createOutput, createTempOutput, sync and obtainLock throw it without javadoc, and syncMetaData does nothing. It neither overrides nor re-documents listAll().

The numbers

#

One empty document, default codec, compound file on: listAll() returns [_0.fnm, _0.fdx, _0.fdt, _0.fdm]; sorted would be [_0.fdm, _0.fdt, _0.fdx, _0.fnm]. With a text field and a doc-values field the segment has 16 sub-files and the listing starts with _0_Lucene104_0.doc instead of _0.fdm. On the 4-name listing, Arrays.binarySearch returns 1 for _0.fdx and a negative "not found" index for each of _0.fnm, _0.fdt and _0.fdm.

Exposure and likelihood231 words
  • Who: code outside Lucene that calls si.getCodec().compoundFormat().getCompoundReader(dir, si) and then relies on listAll() being sorted. Default codec, default compound-file setting, any segment written as a compound file; no misuse needed. Downstream projects do call getCompoundReader (code search found calls in Elasticsearch, OpenSearch and Solr), but the callers looked at open sub-files by name or compare listings as sets (e.g. elastic/elasticsearch#148316); none was found that depends on the order.
  • Not hit: Lucene itself. The production callers of getCompoundReader (IndexWriter.java:1254, SegmentCoreReaders.java:83, PendingSoftDeletes.java:229, TemporalMergePolicy.java:669) open sub-files by name; the listAll() calls in org.apache.lucene.index list the index directory. Lucene's tests do list compound readers, but only to check a length or to iterate over the names, never relying on the order (BaseCompoundFormatTestCase.java:68, 140, 221, TestAllFilesHaveChecksumFooter.java:69, TestAllFilesHaveCodecHeader.java:74, TestIndexWriterForceMerge.java:247).
  • Effect: the set of names is right; only order-dependent logic gives a wrong answer, with no error.
  • Scale and age: no special input is needed: the order is the HashMap's slot order of the sub-file names, so any compound segment with two or more sub-files can list out of order. A particular set may come out sorted by chance; every set tested came out unsorted (the 4-name and 16-name sets on main, and the listing on each release). Present in every release since 6.0.0 (2016); no public report was found in the searches of 2026-11-03. Hence Low.

Why it looks unintended

#
  • Directory.listAll(): "The output must be in sorted (UTF-16, java's String#compareTo) order". CompoundDirectory relaxes only its write methods, not listAll().
  • LUCENE-6835 (6.0.0) made sorting universal on purpose ("I'll add sort to listAll across the board"); its sorted-listing test never runs on compound readers.
  • Every other Directory that holds files sorts, SimpleText's compound reader included; FSDirectory cites the javadoc as the reason.
The full argument254 words
  • The contract is unconditional: "Returns names of all files stored in this directory. The output must be in sorted (UTF-16, java's String#compareTo) order." (Directory.java:52-58). CompoundFormat.getCompoundReader calls its result "a Directory view (read-only)" (CompoundFormat.java:182).
  • It was made universal on purpose: in LUCENE-6835 (#7893) rmuir asked to make the sort "a change to the Directory API", and mikemccand answered "I'll add sort to listAll across the board". The commits on the LUCENE-6835 branch sorted RAMDirectory (dd6379c05fa, which also changed the javadoc), FSDirectory (845eec10367; 85c546b742b later reworded its comment to cite the javadoc), FileSwitchDirectory and NRTCachingDirectory, and added BaseDirectoryTestCase.testListAllIsSorted (both in 3c15c3f03df). That test never runs against compound readers, and BaseCompoundFormatTestCase checks no order, which is likely how this one was missed. LUCENE-8415 (7.5.0: 9dc6cff38a2 on the 7.x branch; 8892c0d9aff on the main branch, first released in 8.0.0) tightened the wording to "must be".
  • Every other implementation that holds files complies: FSDirectory sorts with the comment "Directory.listAll javadocs state that we sort the results here" (FSDirectory.java:185-187); ByteBuffersDirectory (:124-127), NRTCachingDirectory (a TreeSet) and FileSwitchDirectory (:139) sort; SimpleText's compound format sorts the names when it writes them (Arrays.sort(names) in write(), SimpleTextCompoundFormat.java:165) and its reader returns them in that order ("files must be unique and in sorted order", :93). Wrappers such as FilterDirectory (FilterDirectory.java:58-61) return the wrapped directory's listing.
  • Nothing allows it: no javadoc, test, CHANGES or MIGRATE entry says a compound listing may be unsorted.
The devil's-advocate check214 words

The strongest not-a-bug case: CompoundDirectory and CompoundFormat are @lucene.experimental; the reader is a read-only view that no Lucene production code lists (Lucene's tests list it, but none depends on the order); the reader's own javadoc says only "Returns an array of strings, one for each file in the directory" (Lucene90CompoundReader.java:214); the LUCENE-6835 CHANGES entry gives the reason "to not leak platform-specific behavior", and a HashMap's order does not depend on the file system; and SimpleText may keep its names sorted only for its Arrays.binarySearch lookup (SimpleTextCompoundFormat.java:109).

Why it fails: experimental status does not relax a "must" the class inherits; the reader's javadoc is, word for word, the Directory.listAll() javadoc from before LUCENE-6241 (04e297adee3, 2015, which changed "file" to "entry"; LUCENE-6835 then added the order), so it says nothing about order and is no carve-out, and the class is package-private, so users see only the Directory contract; HashMap iteration order is unspecified by the JDK, an implementation detail leaking through the abstraction; and the other directories sort to honour the javadoc, as FSDirectory says. What remains is the impact argument (no Lucene production code lists it), which is why this is Low: it is a contract fix with a one-line change, and Lucene itself is not affected.

Suggested fix

#

Recommended A. Sort in listAll() (validated)

Sort before returning: add Arrays.sort(res); at the end of Lucene90CompoundReader.listAll() (+3 lines with the import and a comment). The repro then passes, and so do the compound-format suites. On the 10.x branch, add the same line to the backward-codecs Lucene50CompoundReader.listAll().

for (int i = 0; i < res.length; i++) {
  res[i] = segmentName + res[i];
}
// Directory.listAll must return sorted names; entries is a HashMap
Arrays.sort(res);
return res;
All options and trade-offs3 options · 304 words

Three ways to meet the contract; A is the smallest and was validated.

A. Sort in listAll() (validated) (recommended)

#

In Lucene90CompoundReader.listAll() (Lucene90CompoundReader.java:214-225), add import java.util.Arrays; and sort the array after the segment-name prefix:

for (int i = 0; i < res.length; i++) {
  res[i] = segmentName + res[i];
}
// Directory.listAll must return sorted names; entries is a HashMap
Arrays.sort(res);
return res;

Trade-offs

An O(n log n) sort of a few dozen short strings per call, on a method no Lucene read path calls; lookups (openInput, fileLength) keep the HashMap. On the 10.x branch the backward-codecs Lucene50CompoundReader.listAll() has the same unsorted body (read at 10.6.0, not run) and needs the same line; it no longer exists on main.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: TestLucene90CompoundFormat (the default format's BaseCompoundFormatTestCase suite), TestCompoundFormat, TestAllFilesHaveChecksumFooter, TestAllFilesHaveCodecHeader and TestIndexWriterForceMerge: 48 tests, 0 failures, 0 errors, 2 skipped by their annotations (@Nightly, @AwaitsFix).
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass. The full lucene/core suite was not run.

B. Keep the names sorted at open

#

Store the entries in a TreeMap, or sort the names once in the constructor and return a copy from listAll().

Trade-offs

Same result as A. A TreeMap makes every openInput/fileLength lookup O(log n); a cached array costs a small String[] per open segment. Not run.

C. Document the exception in CompoundDirectory

#

Say in CompoundDirectory that its listAll() may be unsorted.

Trade-offs

Reverses LUCENE-6835's "across the board" decision for one class while SimpleText's compound reader already sorts, and leaves callers to sort. Not recommended.

Downstream note

#

Downstream, only products whose own code lists a segment's compound reader and depends on sorted order are affected; the names come from Lucene's own codec, not from documents or queries.

How it was found

#

Semi-formal: a proof-obligation audit of the default compound reader against the contract of the Directory class it extends. The obligation that listAll() returns sorted names has nothing in the code that could discharge it, and a JUnit test on stock main witnessed the failure.

The method in full73 words
  • Obligation: every Directory.listAll() returns names in String#compareTo order (Directory.java:52-58), and Lucene90CompoundReader is a Directory through CompoundDirectory, which relaxes only its write methods.
  • Finding: listAll() returns entries.keySet() of a HashMap with the segment name prepended and no sort (Lucene90CompoundReader.java:141, :214-225).
  • Witness: a one-test JUnit check on a one-document segment, then this minimal test, an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
