SimpleWKTShapeParser.parseExpectedType accepts any geometry when GEOMETRYCOLLECTION is the expected type

Ask SimpleWKTShapeParser.parseExpectedType for a GEOMETRYCOLLECTION and give it POINT (1 2): you get the point back as double[]{1.0, 2.0} instead of the ParseException every other expected type gives for a mismatch. The reason is that GEOMETRYCOLLECTION is also the parser's internal "don't check" value.

The finding in 30 seconds

#

parse(wkt) is parseExpectedType(wkt, null): null means "any geometry". Any other type means "this geometry or a ParseException".

  1. Call SimpleWKTShapeParser.parseExpectedType("POINT (1 2)", ShapeType.GEOMETRYCOLLECTION): you require a geometry collection and pass a single point.
  2. You expect ParseException: Expected geometry type: [GEOMETRYCOLLECTION], but found: [POINT], as for any other mismatch: the same point with POLYGON expected throws Expected geometry type: [POLYGON], but found: [POINT].
  3. Instead you get double[]{1.0, 2.0} and no error; casting it to Object[], what a non-empty collection parses to, throws ClassCastException. LINESTRING, POLYGON and BBOX text also come back as their own non-array types, and MULTI* text as an array of its parts (MULTIPOINT a double[][], which is an Object[] in Java).
  4. Why: the parser reads a collection's first member with GEOMETRYCOLLECTION as its internal "don't check" value (later members get null), so the type check skips GEOMETRYCOLLECTION, and a caller who asks for a collection hits that skip.

Who is affected

#

Only code that calls parseExpectedType(text, ShapeType.GEOMETRYCOLLECTION) to require a collection and then gets other WKT. The check it asked for does nothing; for POINT, LINESTRING, POLYGON or BBOX text a later cast to Object[] fails with ClassCastException. parse(String) is unaffected, no index or query is involved, and no such caller is known in Lucene or downstream.

Mechanism, terms and numbers447 words

SimpleWKTShapeParser.parseExpectedType(wkt, type) parses WKT text and throws ParseException("Expected geometry type: [X], but found: [Y]") when the text's geometry keyword is not the requested one. For ShapeType.GEOMETRYCOLLECTION it does no check at all: POINT (1 2) comes back as double[]{1.0, 2.0}, a LINESTRING as a Line, a POLYGON as a Polygon. The cause is that GEOMETRYCOLLECTION doubles as an internal marker: parseGeometryCollection parses a collection's first member with it to mean "no check" (null does the same for later members), so parseGeometry checks only when shapeType != null && shapeType != GEOMETRYCOLLECTION. It has been there since the class was added in 7.6.0 (LUCENE-8538) and is on main; a two-line fix adds the missing check.

How the check works

#
  1. parseExpectedType passes the caller's type to parseGeometry (SimpleWKTShapeParser.java:69), which reads the first keyword and compares it with that type by exact WKT name (:78-84). No subtypes are accepted: with MULTIPOINT expected, POINT is rejected; with POINT expected, MULTIPOINT and GEOMETRYCOLLECTION (POINT (1 2)) are rejected.
  2. A collection's members go through the same parseGeometry, unchecked, because a collection may hold any geometry. The first member is told "unchecked" with ShapeType.GEOMETRYCOLLECTION (:274), every later member with null (:276); both act the same way. The check at :79 is shapeType != null && shapeType != ShapeType.GEOMETRYCOLLECTION, which lets the first one through; the code strongly suggests that is why the exemption is there (no comment or commit message says so).
  3. When the caller passes ShapeType.GEOMETRYCOLLECTION, :79 therefore skips the check, the switch (:86-105) parses whatever keyword the text starts with, and that geometry is returned.
if (shapeType != null && shapeType != ShapeType.GEOMETRYCOLLECTION) {   // :79  the skip
  if (type.wktName().equals(shapeType.wktName()) == false) {
    throw new ParseException("Expected geometry type: [" + shapeType + "], but found: [" + type + "]", ...);
  }
}

The numbers

#

With GEOMETRYCOLLECTION expected, on main: POINT (1 2) returns double[]{1.0, 2.0}, LINESTRING (1 2, 3 4) a Line, POLYGON ((0 0, 1 0, 1 1, 0 0)) a Polygon, BBOX (0, 1, 1, 0) a Rectangle; the multi types return arrays of their parts (MULTIPOINT (1 2, 3 4) a double[2][], MULTILINESTRING a Line[], MULTIPOLYGON a Polygon[]); a real GEOMETRYCOLLECTION (POINT (1 2)) returns Object[], and GEOMETRYCOLLECTION EMPTY returns null. Casting the point's result to Object[] throws ClassCastException: class [D cannot be cast to class [Ljava.lang.Object;; the same cast succeeds for the multi types, whose arrays are Object[] instances in Java.

Exposure and likelihood226 words
  • Who is hit. Application code that requires a collection, for example to validate a stored or user-supplied value before iterating it as Object[]. Nothing in the Lucene tree calls parseExpectedType with a type: the three tests that use the parser (TestSimpleWKTShapeParsing, TestTessellator, TestShapeDocValues) call parse. A code search found no Elasticsearch or OpenSearch caller that passes a collection type; both have their own parsers.
  • Default vs opt-in. No setting, codec or index: one call to a public static helper in lucene-core (org.apache.lucene.geo is exported, module-info.java:38). Deterministic, assertions on or off.
  • Effect. A missing ParseException. The returned value is the correct parse of the text, but not a collection. For POINT, LINESTRING, POLYGON and BBOX text it is a non-array (double[], Line, Polygon, Rectangle), so a later cast to Object[] fails with ClassCastException. For MULTIPOINT, MULTILINESTRING and MULTIPOLYGON text it is an array of the parts (double[][], Line[], Polygon[]), which passes that cast and iterates like a collection of those parts. A caller that only stores the value keeps a non-collection it meant to reject. Lucene itself indexes and corrupts nothing; what a downstream caller does with the value is up to it.
  • Likelihood: rare. No known caller; no public report found since 7.6.0 (2018).

Why it looks unintended

#
  • Every other expected type is enforced exactly: POINT (1 2) with POLYGON or MULTIPOINT expected throws ParseException.
  • The skip serves one internal call, a collection's first member; later members and parse(String) use null instead.
  • The same author's earlier Elasticsearch method documents that it "throws an exception if the parsed geometry type does not match the expected shape type".
The full argument289 words
  • The method's own check. For every other ShapeType it rejects a different keyword with "Expected geometry type: [X], but found: [Y]" (SimpleWKTShapeParser.java:79-84), with exact matching and no subtype leniency. Apart from the skip itself at :79, no doc, test, comment or review gives callers a "match anything" meaning for GEOMETRYCOLLECTION.
  • One internal call accounts for the skip. :274 is the only place that passes GEOMETRYCOLLECTION; :276 and :51 pass null for the same purpose. This strongly suggests why the skip exists (no comment or commit message says so). With null at :274 the skip is no longer needed.
  • The return type. With GEOMETRYCOLLECTION expected, POINT, LINESTRING, POLYGON and BBOX text comes back as a non-array, never as the Object[] a non-empty collection parses to (LUCENE-8538's own list in #9584: "GEOMETRYCOLLECTION -> Object[]"). This does not cover MULTI* text: its arrays of parts are Object[] instances in Java, and whether a MULTIPOINT counts as a collection is the OGC-subtype question the fix section leaves open.
  • The same author's earlier Elasticsearch method. Elasticsearch's GeoWKTParser.parseExpectedType, added with the same skip and marker by the same author in elastic/elasticsearch#27692 (opened 2017-12-06, merged 2018-01-15, nine months before LUCENE-8538), carries the javadoc "throws an exception if the parsed geometry type does not match the expected shape type", still present in Elasticsearch main; its only test expects POINT to be rejected when POLYGON is expected. Lucene's class has the same method name, check and message, but not the javadoc. That it was modelled on that code is an inference from the same author and structure; no commit message or #9584 comment says so.
  • Tests. No Lucene test calls parseExpectedType; the 14 tests of TestSimpleWKTShapeParsing call parse.
The devil's-advocate check152 words

The strongest case: a geometry collection may hold any geometry, so "expect a collection" could mean "accept anything"; the skip is written out explicitly, is as old as the class and was never changed; Lucene documents no contract for the method; and the parser was added as a helper "useful for simple tests, but also helps for benchmarking" (#9584).

Why the evidence favours fix A: under that reading the caller still gets a bare double[] or Line, not a collection, so it gets neither the check nor the type it asked for; null already is the "accept anything" value; and the code strongly suggests the skip is there so the first collection member can be parsed unchecked. This does not settle the intended semantics of an undocumented helper: what remains is severity (Low). Both executed reviews by another model family (OpenAI GPT-5.6) rated the intended-behaviour argument "moderate" and the bug real.

How it was found

#

A proof-obligation audit of SimpleWKTShapeParser's contract took the method's own check as the obligation: for every expected type, return only that geometry or throw ParseException. The guard discharges it for every type except GEOMETRYCOLLECTION. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full128 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: parseExpectedType(wkt, t) with t != null returns only a geometry whose keyword is t, else throws ParseException (the method's own check and message, SimpleWKTShapeParser.java:79-84). The guard shapeType != null && shapeType != GEOMETRYCOLLECTION discharges it for every t except GEOMETRYCOLLECTION, and the enum value is public.

Priority

Impact note
