All bugs · Lucene bug · LFV-227 · join-sv-min-avg-drops-zero-score

JoinUtil's single-valued term join forgets a from-document that scored exactly 0, so ScoreMode.Min and ScoreMode.Avg give too-high, order-dependent scores

JoinUtil's single-valued term join forgets a from-document scoring exactly 0 (for Avg, only a leading run of zeros) when another with the same join value follows: scores 0 and 2 give 2 for both ScoreMode.Min and ScoreMode.Avg, not 0 and 1. It reads a running score of 0 as "not seen yet" (Avg since 4.0, Min since 5.2).

The bug in 30 seconds

#

The single-valued term join keeps one running score per join value, and uses "the running score is exactly 0" to mean "I have not seen this join value yet". A from-document that really scores 0 trips that test for the next document: for Min after any 0, for Avg while every earlier score of that join value was 0.

  1. You join with JoinUtil.createJoinQuery("join", false, "ref", fromQuery, searcher, ScoreMode.Min). Two from-documents share the join value x, and fromQuery scores them 0 (it matches only a FILTER clause) and 2, in that order.
  2. You expect the to-document with ref:x to score min(0, 2) = 0, or (0 + 2) / 2 = 1 with ScoreMode.Avg: the ScoreMode javadoc says "the min of all child scores" and "the average of all child scores", and the multi-valued join returns exactly 0 and 1 on the same documents.
  3. Instead both modes return 2. The single-valued collector keeps one running score per join value and treats "running score == 0" as "first document for this value". After the 0, the next document looks like the first: Min overwrites the 0, and Avg, while every earlier score of that join value was 0, restarts its sum and count.
  4. It depends on order: [2, 0] gives the right 0 and 1, [3, 0, 5] gives Min 5, [0, 0, 5] gives Min 5 and Avg 5 instead of 1.67. Which documents match never changes; Max, Total and the other join variants are correct.

Who is affected

#

Applications that call JoinUtil.createJoinQuery(fromField, false, ...) with ScoreMode.Min or Avg and a from query that scores some documents exactly 0: FILTER-only matches next to SHOULD clauses, FunctionScoreQuery over a 0 or missing value, a zero boost. Default settings, any index size. Scores and ranking come out silently too high; matches are unchanged.

Mechanism, terms and numbers739 words

JoinUtil.createJoinQuery(fromField, multipleValuesPerDocument=false, toField, fromQuery, fromSearcher, scoreMode) aggregates the scores of all from-documents that share a join value into one score for the matching to-documents. The single-valued collectors (TermsWithScoreCollector.SV and SV.Avg) keep one running score per join value and test Double.compare(existing, 0.0d) == 0 to decide "this is the first from-document for this join value". But 0 is a legal score: a document that matches only a FILTER clause next to SHOULD clauses scores 0, and so does a FunctionScoreQuery over a value that is 0 or missing. After such a document, the next from-document with the same join value is treated as the first: ScoreMode.Min overwrites the stored 0, and ScoreMode.Avg, while every earlier score of that join value was 0 (a leading run of zeros), restarts the sum and the count. With from scores 0 and 2 both modes return 2, where the ScoreMode javadoc and the multi-valued join on the same documents give 0 and 1. Which documents match does not change; only scores, and so ranking, are wrong, with legal non-negative scores always too high and never above the join value's Max score, and they depend on collection order. Max, Total and None are correct (apart from the sign of a zero), and the multi-valued, numeric and global-ordinals joins are not affected. Avg has been wrong since the scoring join was added in 4.0.0-ALPHA (2012), Min since it was added in 5.2.0 (2015), with assertions on or off. Using BytesRefHash.add's "new value" result as the first-occurrence signal fixes it (+4/-3).

Terms

#
  • Query-time join: JoinUtil.createJoinQuery(fromField, multipleValuesPerDocument, toField, fromQuery, fromSearcher, scoreMode) runs fromQuery, collects the join values of the matching from-documents from the doc values of fromField, and returns a query that matches the documents whose toField holds one of those values. With a ScoreMode other than None, each join value also gets one score aggregated from its from-documents, and a to-document gets the score of its join value.
  • Single-valued path: multipleValuesPerDocument=false reads SortedDocValues and uses TermsWithScoreCollector.SV (Min, Max, Total) or SV.Avg; true reads SortedSetDocValues and uses MV / MV.Avg (GenericTermsCollector.java:38-52, :116-130). The package example uses false for a single-valued from field (package-info.java:94).

The bug

#
  1. One slot per join value. SV.collect adds the from-document's value to a BytesRefHash (TermsWithScoreCollector.java:120); add returns an id >= 0 exactly when the value is new (BytesRefHash.java:314-316). New Min slots are filled with +Infinity, Max slots with -Infinity (TermsWithScoreCollector.java:127-131); Total and Avg slots start at 0 (:126, :183-184).
  2. The first-document test uses the score. SV.collect reads existing = scoreSums[ord] and, if Double.compare(existing, 0.0d) == 0 (:136-137), stores the current score as if it were the first (:138); otherwise it applies Total, Min (if (current < existing), :144-148) or Max. SV.Avg.collect does the same at :189-192 and resets the count to 1; the score is sum / count (:203).
  3. Min: the slot starts at +Infinity, so the test does not fire for the first document. It fires once the stored minimum is exactly 0, and the next score replaces it.
  4. Avg: with non-negative scores a sum of exactly 0 means every earlier score was 0, so a leading run of zeros is forgotten; a zero after a positive score is counted.
  5. Max, Total: 0 is their neutral value, so overwriting it changes nothing, apart from the sign of a zero: a +0.0 then a -0.0 (legal: AssertingScorable asserts only score >= 0) leaves -0.0, where Math.max, addition and the multi-valued join give +0.0 (executed); only Float.compare, which HitQueue uses to order hits (HitQueue.java:76), tells them apart. The test is a plain if, so -da changes nothing either.
  6. The multi-valued collectors in the same file have no such test: they take min/max directly against the ±Infinity fill or add (:236-250) and count every score (:277-278).

Exposure and likelihood360 words
  • Who is hit. Callers of JoinUtil.createJoinQuery(fromField, false, toField, fromQuery, fromSearcher, ScoreMode.Min | ScoreMode.Avg) on a SORTED doc-values from field, which is what the package example uses for a single-valued field (package-info.java:94). Default codec, IndexWriterConfig and IndexSearcher; any index size; assertions on or off.
  • When. The from query scores a from-document exactly 0, and that document is collected before another from-document with the same join value (for Avg, before any positive score of that join value). Lucene produces 0 on purpose: FILTER clauses "do not participate in scoring" (BooleanClause.java:35); FunctionScoreQuery returns 0 for a "missing value, negative value or NaN" (FunctionScoreQuery.java:243-251); BoostQuery accepts a boost of 0 (BoostQuery.java:40-42). For example "rank products by their worst review" with a rating that is 0 or missing. Typical text-relevance from queries, for example a TermQuery under the default BM25 similarity, do not score exactly 0 and are unaffected.
  • What happens. Silent wrong scores, with legal non-negative scores always too high and never above the join value's Max score, so to-documents rank too high and a score threshold on the join lets the wrong ones through. Which documents match, deletions and FILTER / MUST_NOT restrictions are unchanged (the follow-up's probe: the match set always equalled a brute-force set). A concrete flip from the probe: product P has reviews [0, 0], Q has [3, 3, 3], and P ranks below Q. After one more review of P with rating 5, P's correct Min and Avg are 0 and 1.67 (the multi-valued join's values), but the single-valued join returns 5 for both, so P ranks above Q (3).
  • Order-dependent. Collection order is segment order, then document id, so the same from-documents indexed in another order give different scores.
  • Downstream (code reading, not run): Solr's score join passes multipleValuesPerDocument=true for term joins; Elasticsearch and OpenSearch has_child/has_parent use the global-ordinals variant; Yelp's nrtsearch CrossIndexQuery can reach the affected collector when a client picks a min or avg score mode on a single-valued field.
  • How common. A rarely used combination; the documented searches found no report since the code was added in 2012. For its users it is deterministic.

Why it is a bug, not intended

#
  • The ScoreMode javadoc: "the min of all child scores", "the average of all child scores"; 0 is a legal score.
  • The multi-valued collectors in the same class count a 0, and TestJoinUtil checks both paths against one model.
  • The result flips with order: [0, 2] gives Min 2, [2, 0] gives 0.
The full argument253 words
  • The contract. ScoreMode.java:25-26: Avg is "Parent hit's score is the average of all child scores"; :34-35: Min is "Parent hit's score is the min of all child scores".
  • 0 is legal. AssertingScorable asserts score >= 0 (AssertingScorable.java:36); in the #13697 review a committer wrote "0 is a legal score (but negative values are not legal scores)".
  • The two paths are meant to agree. TestJoinUtil uses the multi-valued join at random for single-valued data, "single val can be handled by multiple-vals" (TestJoinUtil.java:1535-1536), against one reference model, JoinScore, which starts Min at +Infinity and counts every score for Avg (:2046-2081). The numeric and global-ordinals joins count a 0 too (the devil's-advocate check ran all four on the same data).
  • History shows a leftover marker. In LUCENE-4043 (2012) the score arrays started zeroed and 0 meant "not set yet". LUCENE-6389 (2015) added Min and pre-filled its slots with +Infinity, which only makes sense for a true minimum, but kept the 0 test in front of the switch.
  • Why tests never caught it. TestJoinUtil's term-join tests use TermQuery from queries (the random ones on value, TestJoinUtil.java:1524), which are not built to score 0, and no test mixes zero and positive scores for one join value on the single-valued term path. Its only from query meant to produce zeros, testMinMaxScore's score = price with price = random().nextInt(1000) (:508-585, :539), runs the global-ordinals join (:560-562, :572-574), which counts the 0.
The devil's-advocate check213 words

The strongest case for "intended": the JoinUtil javadoc says "only the score from the first encountered join value originating from the 'from' side is mapped into the 'to' side" (JoinUtil.java:68-74).

Why it fails: that sentence is about multipleValuesPerDocument=true and a document with several join values, not about adding up the from-documents of one join value, and this bug is on the false path. @lucene.experimental (JoinUtil.java:54) allows the API to change, not wrong arithmetic. "0 means it did not really match" fails too: a FILTER-only document is a match, and the zero is kept when it comes last. Weaker arguments fail too: the 2012 code may have assumed strictly positive scores, but no javadoc says so and Lucene produces exact zeros by design; ScoreMode speaks of parent and child hits because the block join shares it, while JoinUtil says it "Instructs how scores from the fromQuery are mapped to the returned query" (JoinUtil.java:86); exact zeros are rare and the code is old, which explains why nobody noticed, not that it is meant; the multi-valued path is a workaround, not a contract. The cross-model reviews and the independent reproducer rated the intended case weak; the devil's-advocate check and the adjudication found no intended argument that survives. Verdict: a defect.

Suggested fix

#

Recommended First occurrence from BytesRefHash.add (validated)

Use BytesRefHash.add's result as the first-occurrence signal: it is >= 0 exactly when the join value is new. In SV and SV.Avg, replace Double.compare(existing, 0.0d) == 0 with that flag (+4/-3 in TermsWithScoreCollector.java). The repro passes, and so do the 104 existing lucene/join tests.

How it was found

#

AI-assisted code reading of the join module's score collectors, while checking a recent change to their accumulation precision, then a public-API JUnit with the multi-valued join as the reference. No formal tool flagged it, and no upstream test mixes zero and positive from scores on the single-valued term path.

Bug record

#

LFV-227, snapshot of 2026-10-29

Registry title
JoinUtil's single-valued term join forgets a from-document that scored exactly 0, so ScoreMode.Min and ScoreMode.Avg give too-high, order-dependent scores
Area
join / JoinUtil query-time term join (TermsWithScoreCollector.SV and SV.Avg, ScoreMode Min/Avg)
Priority
Medium, rank 299: Since 4.0 JoinUtil's single-valued term join with ScoreMode Min or Avg forgets a from-document that scored exactly 0, silently raising scores in an order-dependent way, natural for its users but a rarely used combination that the big downstreams avoid.
Impact class
silent wrong results
Impact note
Applications that call JoinUtil.createJoinQuery(fromField, multipleValuesPerDocument=false, toField, fromQuery, fromSearcher, ScoreMode.Min or ScoreMode.Avg) on a SORTED doc-values from field get too-high scores, and therefore wrong ranking, for to-documents whose join value has a from-document scoring exactly 0 that is collected before another from-document with the same value (a FILTER-only match next to SHOULD clauses, a FunctionScoreQuery over a field that is 0 or missing, a zero boost), with the default codec, IndexWriterConfig and IndexSearcher, -ea and -da, at any index size, in every release since 4.0.0-ALPHA (Avg) and 5.2.0 (Min); which documents match is unchanged, Max, Total and None are correct, and the multi-valued, numeric and global-ordinals joins are not affected; Solr's score join, Elasticsearch and OpenSearch has_child/has_parent use unaffected variants (code reading).
Summary
You build JoinUtil.createJoinQuery("join", false, "ref", fromQuery, searcher, ScoreMode.Min) where two from-documents share the join value x and fromQuery scores them 0 and 2 (one matches only a FILTER clause), and expect the to-document with ref x to score min(0, 2) = 0, or (0 + 2) / 2 = 1 with ScoreMode.Avg, because the ScoreMode javadoc says 'the min of all child scores' and 'the average of all child scores' and the multi-valued join returns exactly that on the same documents. Instead both modes return 2: the single-valued collector uses an accumulated score of exactly 0 to mean 'this join value has not been seen yet', so after a from-document that scored 0, the next from-document with the same value overwrites the stored minimum (Min) or restarts the sum and count (Avg). Which documents match does not change; only scores and ranking are wrong, and they depend on collection order (scores [0, 2] go wrong, [2, 0] come out right).
Introduced

ScoreMode.Min since 07beb24d93cdc70d6c1f6934faf8387c5cd07ed7 (LUCENE-6389, #7449, 'Added ScoreMode.Min', 2015-04-19; branch_5x backport 87da9f4c64e), which pre-filled the Min slots with +Infinity but kept the 0.0 test in front of the switch [read: git log --follow, git log --all -S and git blame in the full-history clone; exec: the scoring join API is absent in 3.6.2 (compile error) and the bug is present from 4.0.0-ALPHA; Min first fails in 5.2.0]. The multi-valued collectors lost the same test as a side effect of the LUCENE-4765 SortedSetDocValues rewrite (f2798476cd1, merged to branch_4x as bb1f4d0c61b, 2013, first released in 4.2.0), which is why the two paths disagree today (2012-05-29 (ScoreMode.Avg, LUCENE-4043); 2015-04-19 (ScoreMode.Min, LUCENE-6389))
