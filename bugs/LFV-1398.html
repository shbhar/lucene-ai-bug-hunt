While deleteAll() runs, hasUncommittedChanges() and NRT isCurrent() report no changes despite a pending delete

While IndexWriter.deleteAll() runs, another thread can get hasUncommittedChanges() == false and an NRT reader's isCurrent() == true despite an earlier, uncommitted delete: deleteAll() drops buffered deletes before it counts its own change. It heals when deleteAll() returns; every release since 4.3.1 has it.

The finding in 30 seconds

#

deleteAll() works in two steps: lockAndAbortAll() drops the buffered deletes, then, after merges are aborted and segments cleared, it bumps the change count. Between the two steps nothing a status check reads shows any change.

How IndexWriter answers "is anything uncommitted?", in one minute

#
  1. Deletes by term or query and doc-values updates first sit in an in-memory buffer, the delete queue; nothing is counted yet.
  2. hasUncommittedChanges() is true when the change count differs from the one the last commit saw, or when that buffer is not empty. It takes neither the writer's monitor nor fullFlushLock.
  3. An NRT reader's isCurrent() asks the writer (nrtIsCurrent()): same index version and empty buffers mean "current". openIfChanged() returns null when the reader is current.

The finding, step by step

#
  1. Add document id:1 and commit(). Open an NRT reader r = DirectoryReader.open(w), then call w.deleteDocuments(new Term("id", "1")). Now w.hasUncommittedChanges() is true and r.isCurrent() is false.
  2. Start w.deleteAll() on a second thread. While it runs, ask both questions again from the first thread.
  3. You expect true and false again: before deleteAll() the delete is pending, after it deleteAll()'s own change is.
  4. Instead you get false and true (and DirectoryReader.openIfChanged(r) returns null): deleteAll() has already dropped the buffered delete but has not yet counted its own change.
  5. Once deleteAll() returns, hasUncommittedChanges() is true again and nothing is lost by itself. A caller that commits only when it says true commits one polling round later, and in a probe with ControlledRealTimeReopenThread, waitForGeneration(6) for the delete's sequence number 6 returns true while the searcher still finds id:1.

Who is affected

#

Applications that call deleteAll(), or deleteDocuments(MatchAllDocsQuery) which routes to it, while another thread polls hasUncommittedChanges() or refreshes NRT readers, with a delete or doc-values update buffered since the last commit. Default config. The wrong answer lasts from microseconds to as long as running merges take to abort, then heals.

Mechanism, terms and numbers496 words

IndexWriter.deleteAll() first drops everything buffered in memory, including deletes and doc-values updates the application already made, and only at its end records that the index changed. A thread that asks in between hears "no uncommitted changes" from hasUncommittedChanges() and "current" from an NRT reader's isCurrent() (openIfChanged() returns null), although an earlier delete is neither committed nor visible to that reader. The answers are correct again once deleteAll() returns. It has been so since 4.3.1, when LUCENE-5002 moved the drop out of the writer's monitor to fix a deadlock.

Step by step

#
  1. DocumentsWriter.lockAndAbortAll() (DocumentsWriter.java:266-311) runs deleteQueue.clear() at :295 and :302, skips sequence numbers (:305) and prints "finished lockAndAbortAll success=true" (:310).
  2. hasUncommittedChanges() is changeCount.get() != lastCommitChangeCount || hasChangesInRam() (IndexWriter.java:4224-4231). The count has not moved, and docWriter.anyChanges() (DocumentsWriter.java:344-356) and bufferedUpdatesStream.any() see empty buffers: false.
  3. nrtIsCurrent() (IndexWriter.java:6139-6145) is synchronized, but the writer monitor is free right after lockAndAbortAll() returns and while abortMerges() waits for running merges (doWait(), :2860). Same version, empty buffers: true. An NRT reader's isCurrent() calls it (StandardDirectoryReader.java:542) and openIfChanged() returns null on it (:462-464).
  4. ControlledRealTimeReopenThread: a refresh in the window opens no reader, but afterRefresh still copies the generation recorded before the refresh (the writer's max completed sequence number, ControlledRealTimeReopenThread.java:96) into searchingGen (:102). The delete completed before deleteAll() started, so that number already covers it, and waitForGeneration() needs only searchingGen >= targetGen (:161, :171). The sequence-number skip of step 1 only makes it 7 rather than 6.
  5. The window closes at :2798-2799. A buffered addDocument is not affected (taking a segment name already bumped the count, IndexWriter.java:2178), nor is tryDeleteDocument (it counts its change at once).

The numbers

#

One document id:1, committed; an NRT reader; deleteDocuments(new Term("id", "1")): hasUncommittedChanges() true, isCurrent() false. Read while deleteAll() is paused after lockAndAbortAll(): false and true. A probe on main: the delete gets sequence number 6; a refresh in the window leaves openIfChanged() at null, sets searchingGen to 7, waitForGeneration(6) returns true, and the acquired searcher still counts id:1 as 1. An enumeration that paused deleteAll() at each of its own log messages (7 to 9 per kind of buffered change, 44 checks over 6 kinds) found 15 wrong answers on stock main and 0 with sketch B (changed() added first, the late count kept; fix A was validated with gradle): delete-by-term, delete-by-query and doc-values update, at the 5 points from the end of lockAndAbortAll() to the change count.

Exposure and likelihood264 words
  • Who. deleteAll() or deleteDocuments(MatchAllDocsQuery) (routed to deleteAll(), IndexWriter.java:1886-1890) on one thread; on another, hasUncommittedChanges(), an NRT reader's isCurrent()/openIfChanged(), SearcherManager.maybeRefresh() or a ControlledRealTimeReopenThread refresh; a buffered delete-by-term, delete-by-query or doc-values update since the last commit. Default IndexWriterConfig, codec and directory. deleteAll() and hasUncommittedChanges() are stable public API; the NRT faces go through writer-backed reader APIs marked @lucene.experimental: DirectoryReader.open(IndexWriter) (DirectoryReader.java:120, the repro's own entry point), the writer overloads of openIfChanged (:338, :381, :401), ReferenceManager, SearcherManager and ControlledRealTimeReopenThread.
  • What goes wrong. A caller that commits only when hasUncommittedChanges() is true skips that round and commits on its next poll. A commit() in the window would have waited on fullFlushLock (IndexWriter.java:3806) until deleteAll() returned, and deleteAll() removes that document anyway, so the effect is a commit one polling round later, not a separate way to lose data. A refresh keeps the stale reader one more round. waitForGeneration(deleteSeqNo) returns true while the searcher still finds the deleted document, until the next refresh.
  • Why nothing is lost by itself. commit(), getReader() and flush() wait on fullFlushLock during the window, and close() commits by default.
  • How long. Microseconds with no merges running; while abortMerges() waits for running merges to abort, the writer monitor is free, so the window lasts as long as that takes.
  • How likely. Rare: deleteAll() during live serving is uncommon, and no in-tree production code gates commit() on hasUncommittedChanges() (only an assert in IndexUpgrader.java:203). Downstream, Solr decides whether to commit from it (apache/solr#906); no impact is claimed there.

Why it looks unintended

#
  • IndexWriter is documented as safe for concurrent calls to any method; hasUncommittedChanges() admits only false positives; NRT isCurrent() reports new changes.
  • No serial order of the calls gives "no changes": no API promises a linearizable answer, but this one matches neither the pre- nor the post-deleteAll() state.
  • Upstream fixed such wrong answers as bugs: LUCENE-3551 (#4625), LUCENE-3546 (#4620), LUCENE-5289 (#6353).
The full argument299 words
  • Contracts. "IndexWriter instances are completely thread safe, meaning multiple threads can call any of its methods, concurrently" (IndexWriter.java:167-168). hasUncommittedChanges(): "Returns true if there may be changes that have not been committed. There are cases where this may return true when there are no actual \"real\" changes" (:4218-4219). NRT isCurrent() "checks if either a new commit has occurred, or any new uncommitted changes have taken place via the writer" (DirectoryReader.java:631-634); openIfChanged() returns "null if there are no changes" (:242). ControlledRealTimeReopenThread.waitForGeneration "Waits for the target generation to become visible in the searcher" (:132).
  • The code's own claim. The deleteAll() comment says lockAndAbortAll "also guarantees \"point in time semantics\"" (IndexWriter.java:2756-2757). The javadoc names only MergeAbortedException for concurrent forceMerge/addIndexes/forceMergeDeletes callers (:2743-2745).
  • Even the synchronized check is wrong. nrtIsCurrent() holds the writer monitor, but deleteAll() does not hold it after lockAndAbortAll() returns or while abortMerges() waits.
  • Not an artefact of the test hook. The repro pauses deleteAll() with an InfoStream (@lucene.internal, InfoStream.java:28) at a message it prints anyway. A hook-free test that holds a running merge in a FilterDirectory.createOutput, so deleteAll() waits in abortMerges(), also fails on stock main and passes with sketch B (changed() added first, the late count kept; fix A was validated with gradle). It polls in a loop and its logging helper reads package-private state, so it is evidence, not the shipped test.
  • Tests and precedents. No upstream test reads a status answer during a concurrent deleteAll(): TestIsCurrent.testDeleteAllIsCurrent is single-threaded and TestControlledRealTimeReopenThread.testDeleteAll waits only for deleteAll()'s own generation. TestIndexWriterNRTIsCurrent asserts isCurrent() is false under concurrent changes. LUCENE-3551 (#4625, "Yet another race in IW#nrtIsCurrent"), LUCENE-3546 (#4620) and LUCENE-5289 (#6353) were fixed as bugs.
The devil's-advocate check238 words

The argument (a moderate case): in LUCENE-5002 (#6066, 2013), the issue whose fix opened this window, s1monw wrote before the fix that "concurrent access to IW while IW#deleteAll() is called is entirely broken IMO", and mikemccand: "I think stop-the-world is perfectly fine here" and "I even think it'd be fine if concurrent indexing threads hit strange exceptions, and we document that you should not use other methods while deleteAll is invoked in one thread, as long as we can guarantee this never leads to index corruption." #6070 (LUCENE-5006, open) asks to "define the allowed concurrent behavior eg when an app calls deleteAll while other threads are indexing". No API promises a linearizable status read during deleteAll(), the hasUncommittedChanges() javadoc says "may", commit() and getReader() wait on fullFlushLock anyway, the NRT faces go through @lucene.experimental APIs (DirectoryReader.open(IndexWriter), SearcherManager, ControlledRealTimeReopenThread), the repro uses an internal hook, the answer heals when deleteAll() returns, and no report of it was found since 2013.

Why it still reads as a bug: the suggested "do not use other methods" note was never documented: the deleteAll() javadoc names only MergeAbortedException (IndexWriter.java:2743-2745) and the class javadoc still allows any method concurrently (:167-168). LUCENE-8785 (#9829) later fixed concurrent indexing during deleteAll() as a bug. The stable hasUncommittedChanges() is wrong too, and so is the synchronized nrtIsCurrent(); the hook only fixes the schedule (the hook-free test fails too).

Trade-offs

A deleteAll() that throws after the count leaves one counted change: hasUncommittedChanges() says true, a false positive the javadoc allows; by reading it also covers the failure path of LFV-452, where the change is never counted (executed only with B). changed() takes the writer monitor briefly under fullFlushLock, the order deleteAll() already uses, and releases it before lockAndAbortAll(), so the LUCENE-5002 deadlock does not return. With the fix, openIfChanged() and refreshes in the window wait for deleteAll(), as getReader() already does. A commit captures the count under fullFlushLock (:3851), so none can capture it mid-deleteAll(). Not stress- or performance-tested.

Downstream note

#

Products that decide to commit or replicate from hasUncommittedChanges(), or wait on ControlledRealTimeReopenThread, while a deleteAll() may run can commit one round later or return before a delete is visible.

How it was found

#

A bounded model-based test of IndexWriter's change and version accounting flagged deleteAll(). A two-thread JUnit test on the stock jar pinned the window, and an enumeration that paused deleteAll() at each of its own log messages, for 6 kinds of buffered change, found 15 wrong answers in 44 checks on main and 0 with fix sketch B.

The method in full172 words

Method: semi-formal, on main 5adff78bb168, 2026-11-07/08.

  • First signal. A bounded exhaustive model-based test of IndexWriter's version protocol (generated call scripts checked against a reference model of when a change must be visible) reported a wrong status answer around deleteAll() in 882 of 98,304 runs.
  • Witness. A two-thread JUnit test on the stock jars parks deleteAll() with latches at an InfoStream message it prints anyway and reads hasUncommittedChanges() and isCurrent() from the other thread.
  • Bounded enumeration. For each of 6 kinds of buffered change (none, delete-by-term, delete-by-query, doc-values update, addDocument, tryDeleteDocument) and every InfoStream message deleteAll() prints on its own thread (7 to 9 per kind, 44 points in all), another thread read both answers: 15 wrong answers on stock main (assertions on and off, and with five open index-package PRs, #16923, #16996, #17003, #17006 and #16988, applied), 0 with sketch B. The none case sees false before the count, which is correct and not counted.
  • Reach probes confirmed openIfChanged() returning null and ControlledRealTimeReopenThread.waitForGeneration() returning early in the window.

History

#

Introduced by LUCENE-5002 (#6066, 2013-05-21, 3f5be788054 in 4.3.1), which moved the buffer drop out of the writer's monitor to fix a deadlock while the count stayed at the end. Executed: 4.3.0 passes; 4.3.1 through 10.6.0 and main fail (hasUncommittedChanges() from 4.5.1). Never fixed.

Versions tested7 rows

Introducing commit. LUCENE-5002, "Fix Deadlock when IW#deleteAll() is called concurrently to a flushing DWPT" (s1monw, 2013-05-21; a JIRA patch, no PR): trunk c0e7a50ab8e, branch_4x c99affac352, lucene_solr_4_3 3f5be788054 (in the 4.3.1 tag). It turned public synchronized void deleteAll() into synchronized (fullFlushLock) { docWriter.lockAndAbortAll(); synchronized (this) { ...; ++changeCount; segmentInfos.changed(); } }. From 2.9.0 (LUCENE-1705) through 4.3.0 the drop and the count happened in one hold of the writer monitor.

Second face. hasUncommittedChanges() arrived in 4.4.0 (LUCENE-5079) but read only the change count, so it was false for any buffered delete until LUCENE-5289 (00e4c287e87, 4.5.1) made it read the in-memory state. By reading, the waitForGeneration face exists since 4.4.0, where ControlledRealTimeReopenThread arrived (LUCENE-4967): before 6.2.0 it set refreshStartGen from the writer's generation counter and copied it to searchingGen even when no reader was opened (6.1.0 ControlledRealTimeReopenThread.java:89-96, :243-245). Executed on main only.

Later commits. None of the 25 later non-merge commits that touch deleteAll() moved the count ahead of the abort. 10.6.0's deleteAll() differs from main in comments, the #14668 success-flag refactor and the name of the try-with-resources variable (Closeable finalizer there, Closeable _ on main); none of these changes behavior.

Finding record

LFV-1398, snapshot of 2026-11-09

Registry title
While IndexWriter.deleteAll() runs, another thread can get hasUncommittedChanges() == false and an NRT reader's isCurrent() == true (openIfChanged() returns null) despite an acknowledged, uncommitted delete, because deleteAll discards the buffered deletes and doc-values updates before it counts its own change (since 4.3.1)
Area
index / IndexWriter.deleteAll change accounting vs. concurrent status and NRT observers (DocumentsWriter.lockAndAbortAll, IndexWriter.hasUncommittedChanges / nrtIsCurrent, DirectoryReader.isCurrent / openIfChanged, ControlledRealTimeReopenThread)
Priority
Low, rank 767: On the default configuration, while another thread's deleteAll() runs with a delete or doc-values update still buffered since the last commit, an NRT reader's isCurrent()/openIfChanged() can report no changes (every release since 4.3.1), hasUncommittedChanges() can return false (since 4.5.1), and ControlledRealTimeReopenThread.waitForGeneration can return before that delete is visible. The wrong answer lasts only until deleteAll() returns and nothing is lost from the index by itself, so the harm is one skipped commit by an application that commits only when hasUncommittedChanges() is true, or one stale refresh, and calling deleteAll() during live serving is uncommon.
Impact class
minor
Impact note
Hits an application with the default configuration that calls deleteAll() (directly or through deleteDocuments(MatchAllDocsQuery)) on one thread while another thread polls hasUncommittedChanges(), checks isCurrent()/openIfChanged() on an NRT reader or runs a SearcherManager/ControlledRealTimeReopenThread refresh, with a buffered delete-by-term/query or doc-values update pending since the last commit; the wrong answer lasts only until deleteAll() returns (from microseconds up to as long as running merges take to abort) and nothing is lost from the index by itself, so the visible effects are one skipped commit by a caller that commits only when hasUncommittedChanges() is true, a refresh that keeps a stale reader one more round, and a ControlledRealTimeReopenThread.waitForGeneration(deleteSeqNo) that returns true while the acquired searcher still finds the deleted document.
Summary
You add and commit document 1, open an NRT reader with DirectoryReader.open(writer), call deleteDocuments(new Term("id", "1")) (hasUncommittedChanges() is now true and the reader's isCurrent() false), and start deleteAll() on another thread. You expect any thread that asks while deleteAll() runs to still hear 'there are uncommitted changes' and 'this reader is stale', because before deleteAll the delete is pending and after it deleteAll's own change is. Instead, for a stretch of every deleteAll() call, hasUncommittedChanges() returns false and the reader's isCurrent() returns true (openIfChanged() returns null): DocumentsWriter.lockAndAbortAll() has already thrown the buffered delete away, and deleteAll() counts its own change only at its very end.
Introduced
c0e7a50ab8e on trunk (2013-05-21), with the same change as c99affac352 on branch_4x and 3f5be788054 on lucene_solr_4_3 (the commit that shipped in 4.3.1): LUCENE-5002 'Fix Deadlock when IW#deleteAll() is called concurrently to a flushing DWPT' (migrated issue apache/lucene#6066, by s1monw; a JIRA patch, no GitHub PR) [exec: 4.3.0 passes, 4.3.1 fails; read: git log -L and blame in the full-history clone]. It turned 'public synchronized void deleteAll()' into synchronized(fullFlushLock) { docWriter.lockAndAbortAll(); synchronized(this) { ...; ++changeCount; segmentInfos.changed(); } }, so the buffered deletes are cleared without the IndexWriter monitor while the change is still counted at the end. The hasUncommittedChanges() face became observable with LUCENE-5289 (mikemccand, 2013-10-17, 00e4c287e87, in 4.5.1), which made the method read the in-RAM state; none of the 25 later non-merge commits that touch deleteAll moved the change count ahead of the abort (2013-05-21 (author date = commit date, SVN era: trunk c0e7a50ab8e 10:28 UTC, branch_4x c99affac352 10:41 UTC, lucene_solr_4_3 3f5be788054 11:02 UTC))
