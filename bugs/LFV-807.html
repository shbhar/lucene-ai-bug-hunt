Intervals.ordered(X, X) lets the two copies of X overlap when X's own intervals can share a position

When an ordered interval query gets the same piece twice in a row and that piece's matches can share a position, Lucene lets the two copies share it: "a near b, twice" matches a b a, which has one b. An equivalent but unequal second copy correctly finds nothing.

The bug in 30 seconds

#

An ordered interval query must not let its parts overlap. When two adjacent parts are equal, Lucene takes a shortcut that skips that rule, which matters only when the part's own intervals can share a position: it spans several positions and can overlap itself, or it is a term stacked twice at one position.

  1. You search for "a near b, twice, in order": Intervals.ordered(ab, ab) with ab = Intervals.unordered(a, b), default settings, on a one-document index holding a b a (positions 0, 1, 2).
  2. You expect 0 hits: the text has one b, and the two copies may not share it. The query parser's fn:ordered docs say "Source intervals must not overlap".
  3. Instead you get 1 hit, interval [0,2]. The two arguments are equal, so Lucene merges them into one repeat source that joins two consecutive matches of a single ab iterator, [0,1] and [1,2], without checking that both use the b at position 1.
  4. Write the second copy as an equivalent but unequal source, or(ab, zzz) with zzz in no document, and you get the correct 0; Lucene 8.4.1 also gave 0. The phrase a a twice, ordered(phrase(a, a), phrase(a, a)), likewise matches a a a, and ordered(cat, cat) matches the one word cat when the analysis chain indexes it twice at one position.
  5. Matching documents get wrong intervals: on a b a b the query reports [0,2] and [1,3] instead of [0,3], and Weight#matches reports the same. Affected: every release from 8.5.0 to 10.5.2, and main.

Who is affected

#

Anyone whose Intervals.ordered / unorderedNoOverlaps query (or fn: string) repeats back to back a piece whose own matches can share a position: a near pair, a phrase with a repeated word, a nested operator, or a word stacked twice at one position. Default settings, any index size. Single words with one token per position are not affected.

Mechanism, terms and numbers823 words

Intervals.ordered(X, X) asks for X and then X again, and as in every ordered interval query the two parts must not overlap. When the two arguments are equal (by equals(), so also two identically built sources), OrderedIntervalsSource.build replaces them with one RepeatingIntervalsSource, the repeat handling LUCENE-9099 added in 8.5.0. Its iterator joins consecutive intervals of a single X iterator, [first start, last end], and never checks that they are disjoint. For a single term with one token per position that is harmless, since its consecutive intervals are different positions; but when X spans several positions and can overlap itself, the copies share a position: ordered(unordered(a, b), unordered(a, b)) matches a b a (one b), ordered(phrase(a, a), phrase(a, a)) matches a a a, and the same happens through Intervals.unorderedNoOverlaps(X, X) and the query parser's fn:ordered and fn:unorderedNoOverlaps. A term stacked twice at one position (position increment 0) overlaps the same way: ordered(cat, cat) matches the one-word document cat indexed through KeywordRepeatFilter and a stemmer that leaves the word unchanged. Matching documents get wrong intervals too ([0,2], [1,3] instead of [0,3]), and Weight#matches reports them. With an equivalent but unequal second argument the query correctly finds nothing, and so did 8.4.1. Every release from 8.5.0 to 10.5.2 and main are affected with default settings. Dropping the deduplication from OrderedIntervalsSource.build fixes it; the repro and the queries, queryparser and highlighter suites pass with it.

Terms

#
  • Interval: a span of positions [start, end] in a field where a sub-query matches. Intervals.term("a") on a b a gives [0,0] and [2,2]; Intervals.unordered(a, b) ("a and b in any order, as close as possible") gives [0,1] and [1,2], which share position 1; Intervals.phrase("a", "a") on a a a gives [0,1] and [1,2].
  • Stacked token: two tokens at one position (position increment 0), for example a word and its unchanged stem from KeywordRepeatFilter and a stemmer. If both are a, the postings keep both and Intervals.term("a") gives [0,0] twice.
  • ordered(X, Y): an interval that contains an X interval followed by a Y interval that starts after the X interval ends. fn:ordered in StandardQueryParser maps to it; unorderedNoOverlaps(X, Y) is built as or(ordered(X, Y), ordered(Y, X)).

The bug

#
  1. OrderedIntervalsSource.build calls deduplicate (OrderedIntervalsSource.java:29-38), which turns each run of consecutive equals() sub-sources into RepeatingIntervalsSource.build(source, runLength) (:40-57); a single run is returned on its own, renamed "ORDERED" (:53-55).
  2. RepeatingIntervalsSource.intervals wraps one iterator of the sub-source in a DuplicateIntervalIterator (RepeatingIntervalsSource.java:66-72). It caches n consecutive intervals of that iterator and reports the first cached start and the last cached end (:145-154, :172-200). Nothing compares one cached interval's start with the previous one's end.
  3. For ab = unordered(a, b) on a b a the cache holds [0,1] and [1,2], so ordered(ab, ab) reports [0,2]: 1 hit with a single b.
  4. For unequal sub-sources each gets its own iterator, and OrderedIntervalIterator advances each one while currentStart <= prevEnd (OrderedIntervalsSource.java:144-151), so the copies can never share a position. That is why ordered(ab, or(ab, zzz)) gives 0.
  5. RepeatingIntervalsSource.matches combines the sub-matches the same way (:75-86), so Weight#matches reports the same wrong interval (executed); highlighters built on it would show it too (read, not run).
  6. A single term is safe only while each position holds it once. TermIntervalsSource returns every posting position (TermIntervalsSource.java:114-120, 127-135), so a term stacked twice at position 0 yields [0,0] twice, the cache joins them into [0,0], and ordered(a, a) matches a document with a single position.

Exposure and likelihood337 words
  • Who. Users of Intervals.ordered or Intervals.unorderedNoOverlaps (Java API since 8.5.0) or of StandardQueryParser's fn:ordered / fn:unorderedNoOverlaps (query text since 9.1.0) whose query gives the same sub-source twice in a row, where that sub-source spans several positions and its consecutive intervals can share one: a near pair (unordered(a, b)), a phrase whose words repeat (phrase(a, a); phrase(ha, ha) on ha ha ha also matches), or a nested ordered / unordered. ordered(X, X) is a direct way to ask for "X twice". Also anyone who repeats a single word that their analysis chain stacks twice at one position, for example KeywordRepeatFilter before a stemmer that leaves the word unchanged, without RemoveDuplicatesTokenFilter: ordered(cat, cat) then matches the one-word document cat.
  • Effect. Silent extra hits, and wrong intervals on documents that do match. Weight#matches returns the same wrong positions (executed), which can carry over into match-based highlighting and enclosing interval filters; of those only maxgaps was tested directly (containing, containedBy, notContaining follow from the intervals, read). No exception, no hang, nothing written to the index.
  • Default vs opt-in. Nothing to enable: a plain IndexWriterConfig with the default codec, the default searcher, any index size, assertions on and off (executed by the probes); the JUnit tests use the test framework's randomized config and fail the same way.
  • Not affected. Repeats of single words when each position holds the word once (ordered(a, a) on a a a), phrases that cannot overlap themselves (phrase(new, york): not by this overlap, though their gaps are still wrong through LFV-306), and unordered(P, P) matching a a a, which is correct because unordered sources "may overlap" (Intervals.java:432).
  • How likely. It needs that query shape and a document where two of its intervals share a position; for such a pair the false hit happens every time. The trigger is structurally narrow and no report was found although it has shipped since 8.5.0 (2020); how often it happens in practice is unknown.

Why it is a bug, not intended

#
  • The fn:ordered docs say "Source intervals must not overlap"; unorderedNoOverlaps says its sources "do not overlap".
  • An equivalent but unequal second copy, or(X, zzz) with zzz in no document, gives 0 hits; only equal arguments take the overlapping path.
  • A regression: 8.4.1 gives 0, 8.5.0 gives 1. LUCENE-9099 added the shortcut for repeated single-position sources.
The full argument266 words
  • The contract. fn:ordered: "Source intervals must not overlap", with the example fn:ordered(fn:phrase(brown fox) fn:phrase(fox jumps)) "(Sources overlap, no matches.)" (intervalfn/package-info.java:328-356, LUCENE-10223, 9.1.0); upstream TestMatchHighlighter asserts no hit for it and for fn:unorderedNoOverlaps of the same phrases (TestMatchHighlighter.java:396-397). Intervals.unorderedNoOverlaps: "Returns intervals in which both the subsources appear and do not overlap" (Intervals.java:440-447).
  • The cited algorithm. The Intervals class javadoc says "These sources implement minimum-interval algorithms taken from the paper Efficient Optimally Lazy Algorithms for Minimal-Interval Semantics" (Boldi and Vigna, Intervals.java:43-45); there the ordered operator is the "ordered non-overlapping conjunction operator" and "the intervals must be nonoverlapping".
  • Design note. LUCENE-8828 (#9872, 2019, by the later author of LUCENE-9099): "NO_OVERLAPS(a, a) will end up as ORDERED(a, a)".
  • Self-consistency. ordered(ab, or(ab, zzz)) (0) and ordered(ab, ab) (1) differ on a b a though their sub-intervals are the same; ordered(a, a, a, a) gives 0 on a a a; the span analogue (SpanNearQuery in order over two near(a a)) gives 0.
  • History. No evidence was found that LUCENE-9099 (#10141, lucene-solr#1097, 7c1ba1aebee) considered this case. It fixed two term cases: ORDERED(a, a, b) returning an extra interval and UNORDERED(a, a) matching a single a. Its CHANGES entry says "repeated subterms", the class javadoc "repeated terms within an unordered interval", and every test it added repeats a single-position source: a term, or in testMaxGapsWithOnlyRepeats the disjunction or(pease, hot) (TestIntervals.java:739-749). One approving review, no inline comments; nothing relaxes the no-overlap rule. 8.4.1 gives 0, 8.5.0 gives 1, and 8.5.0 with only the deduplicate() call removed gives 0 again.
The devil's-advocate check137 words

The intended-behaviour checker, the second cross-model review and the adjudication built the strongest "intended" case: the Intervals.ordered javadoc alone says only "intervals in which the subsources all appear in the given order" (Intervals.java:415-421), not "non-overlapping"; LUCENE-9099 sent equal sources through RepeatingIntervalsSource on purpose, which could mean "N consecutive occurrences of X" with its own semantics; and the package is experimental.

Why it fails: the paper the class javadoc cites, the fn:ordered docs, the unorderedNoOverlaps javadoc and LUCENE-8828 all state the no-overlap rule; the equal and unequal forms of one query disagree; no record shows LUCENE-9099 discussing sub-sources whose intervals can overlap each other; and "experimental" is about API stability, not wrong results. Verdict: not intended, a regression. Expect the bare ordered javadoc to come up first; answer with the fn:ordered sentence and the unequal-copy control.

Suggested fix

#

Recommended Drop the deduplication in OrderedIntervalsSource.build (validated)

Drop the deduplication from OrderedIntervalsSource.build (+4/-24): the ordered iterator already gives every sub-source its own iterator and never lets two of them overlap. With it the 7 repro tests pass (assertions on and off, 10 iterations), as do the queries, queryparser and highlighter suites (1,774 tests) and the lint, format and javadoc checks.

  static IntervalsSource build(List<IntervalsSource> sources) {
    if (sources.size() == 1) {
      return sources.get(0);
    }
    // No deduplication: OrderedIntervalIterator gives every sub-source its own iterator and never
    // lets two sub-intervals overlap, so equal sub-sources need no special handling. Merging them
    // into a RepeatingIntervalsSource would let the copies of a multi-position source overlap.
    return new OrderedIntervalsSource(new ArrayList<>(sources));
  }
All options and trade-offs5 options · 715 words

One fix was applied in a scratch worktree at a9779ef3c193 and run through gradle; the alternatives were not run. Land it before, or together with, the fix for the repeat width sign (LFV-306): that one-line fix alone makes maxgaps(0, ordered(P, P)) match a a a, because the overlapping interval's gaps turn from 3 to -1.

Drop the deduplication in OrderedIntervalsSource.build (validated) (validated by the checks) (recommended)

#

deduplicate() goes away; build returns new OrderedIntervalsSource(new ArrayList<>(sources)) for two or more sources. Equal sub-sources then get separate iterators like unequal ones. UnorderedIntervalsSource keeps its own use of RepeatingIntervalsSource. The copy keeps what the old code passed (a fresh list, not the caller's varargs view). The hunt's version passed sources directly: the same results in every run, but it keeps the Arrays.asList view of the caller's array (Intervals.java:422-424), so changing that array later would change the query. The code comment's "multi-position source" could also name a term stacked at one position.

  static IntervalsSource build(List<IntervalsSource> sources) {
    if (sources.size() == 1) {
      return sources.get(0);
    }
    // No deduplication: OrderedIntervalIterator gives every sub-source its own iterator and never
    // lets two sub-intervals overlap, so equal sub-sources need no special handling. Merging them
    // into a RepeatingIntervalsSource would let the copies of a multi-position source overlap.
    return new OrderedIntervalsSource(new ArrayList<>(sources));
  }

Trade-offs

  • ordered(t, t) of a term now opens two postings iterators instead of one (small, not benchmarked). toString stays ORDERED(...), and TestSimplifications (unorderedNoOverlaps(term, term) equals ordered(term, term)) still passes.
  • LUCENE-9099's own examples keep their answers: ordered(a, a, b) on a a b gives only [0,2], and containing(ordered(x, y), ordered(a, a, b)) on a x a b y gives 0.
  • It also removes the ordered() half of LFV-306 (repeat width sign) and the ordered manifestations of three sibling findings in the same class (minExtent, nested width, disjunction rewrite); their unordered() halves need their own fixes.
  • A PR also needs a CHANGES entry; no benchmark was run.

Keep the repeat source only for single-position sub-sources (not run)

#

A serious alternative a committer may prefer: deduplicate only sub-sources whose intervals are always one position wide, such as terms, keeping the one-iterator saving for ordered(a, a). On its own it does not fix the stacked-term case, whose intervals are one position wide: the repeat iterator would also have to skip a cached interval that starts at or before the previous one ends.

Trade-offs

Needs a reliable "single-position" test; minExtent() is only a lower bound (or(a, phrase(b, c)) has minExtent 1 and two-position intervals), plus the same-position skip. More code for a small saving.

Make DuplicateIntervalIterator skip overlapping intervals (not run)

#

Advance the shared iterator until the next cached interval starts after the previous one ends.

Trade-offs

With one shared iterator it cannot go back to an interval it skipped, which the next match may need, so it would need a buffer: a re-implementation of what OrderedIntervalIterator already does with separate iterators.

Document that equal sub-sources may overlap (not run)

#

A javadoc note on Intervals.ordered.

Trade-offs

Contradicts the fn:ordered docs and the unorderedNoOverlaps javadoc, and keeps the equal-vs-unequal disagreement.

Workaround today

#

Make the second copy unequal but equivalent: ordered(X, or(X, term-that-never-occurs)) (executed as the control in every test).

Trade-offs

Downstream note

#

Products that build Intervals.ordered or unorderedNoOverlaps from user-written rules inherit this whenever a rule repeats the same self-overlapping piece back to back (a multi-position piece, or a word their analysis chain stacks at one position); no downstream product was read or run for this doc.

How it was found

#

A bounded-exhaustive comparison ran Lucene's real interval iterators against an independently written reference semantics on every short document and thousands of interval expressions with repeated arguments. Extra intervals for ordered queries over equal arguments pointed at the deduplication; public-API JUnit tests on the stock jar confirmed it.

The method in full258 words

Method: bounded-exhaustive translation validation on the real jar (semi-formal tier), in two hunt units on interval queries.

  • First signal (2026-10-26): a unit on span and interval queries ran the stock main jar's interval iterators against an independently written reference semantics on every small document and recorded extra and missing intervals for ordered with repeated arguments as a lead: "ordered(X, X) is built as a RepeatingIntervalsSource, which lets the two X intervals overlap".
  • Reduction (2026-10-27, main a9779ef3c193): a second unit wrote its own reference and harness: 6,856 expressions of depth up to 3 over term, ordered, unordered, or, phrase, maxgaps(0|1) and atLeast(2 of 3) with repeated arguments, on every document of up to 6 positions over a 3-letter alphabet, with switchable fixes for every suspected fix site. At 4 positions (about 1.1 million checks per run) the mismatches fell from 3,596 to 1,098 when this fix was added to the others, and to 0 with all of them; at 6 positions (11,287,592 checks) 0 remained with all seven fixes.
  • Then a public-API JUnit test on the stock jar, controls first; checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by a model from another family (OpenAI GPT-5.6) and an adjudication, then a history sweep and a prior-report search.
  • The stacked-term case (2026-10-28) came from a cross-model fact check of this doc, which inferred it from the code; a public-API probe then executed it on main, 8.4.1, 8.5.0 and 10.5.2. The harness's documents hold one token per position, so it could not reach this case.

Bug record

#

LFV-807, snapshot of 2026-10-29

Registry title
Intervals.ordered(X, X) with two equal sub-sources that span several positions lets the two copies of X overlap, so ordered(phrase(a, a), phrase(a, a)) matches 'a a' and ordered(unordered(a, b), unordered(a, b)) matches 'a b a' (one b), while the same query with an equivalent but unequal second source finds nothing
Area
queries / intervals (Intervals.ordered and unorderedNoOverlaps with equal consecutive sub-sources: OrderedIntervalsSource.deduplicate, RepeatingIntervalsSource)
Priority
Medium, rank 228: A new silent over-match in every release since 8.5.0 that needs ordered or unorderedNoOverlaps to get the same multi-position self-overlapping source twice, so it joins the rare-input interval wrong-result rows after LFV-293 and above LFV-306, which also needs maxgaps.
Impact class
silent wrong results
Impact note
Anyone whose interval query gives Intervals.ordered (or unorderedNoOverlaps, which is built from ordered) the same sub-source twice in a row, where that sub-source spans several positions and its consecutive intervals can share a position (a phrase with a repeated word such as phrase(ha, ha), an unordered or ordered pair such as unordered(a, b), or a nested ordered), through the Java factories or StandardQueryParser fn:ordered / fn:unorderedNoOverlaps strings, with default writer, codec, analyzer and searcher settings, at any index size, with -ea and -da, in every release since 8.5.0, gets extra matching documents and wrong match intervals (also seen by Weight#matches, highlighting and enclosing interval filters); repeats of single terms, the common case, and phrases that cannot overlap themselves are not affected, and nothing is written to the index.
Summary
You ask for two occurrences of X in order with Intervals.ordered(X, X), for example X = unordered(a, b) ('a near b', twice) or X = phrase(a, a), and expect the usual ordered rule that the sub-intervals do not overlap (the fn:ordered documentation says 'Source intervals must not overlap'). Instead, because the two arguments are equal, OrderedIntervalsSource.build merges them into a RepeatingIntervalsSource, which joins consecutive intervals of a single sub-iterator without checking that they are disjoint, so ordered(unordered(a, b), unordered(a, b)) matches 'a b a', which has only one b, and ordered(phrase(a, a), phrase(a, a)) matches 'a a'. The same query with an equivalent but unequal second source, ordered(X, or(X, a term that occurs nowhere)), correctly finds nothing, and so did Lucene 8.4.1.
