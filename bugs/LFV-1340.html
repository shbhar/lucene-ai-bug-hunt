addIndexes(CodecReader...) silently adds nothing when wrapForMerge pushes the document count past Integer.MAX_VALUE

On an index-sorted writer, a merge policy whose wrapForMerge brings back deleted documents can push an addIndexes(CodecReader...) merge past about 2.1 billion documents; instead of the documented IllegalArgumentException, addIndexes returns success and adds nothing, because MergeState adds up the wrapped counts in an int that wraps negative.

The finding in 30 seconds

#

addIndexes checks the limit before your merge policy's wrapForMerge runs. MergeState then adds up the wrapped readers' counts in an int without a check, so a wrapper that brings back more than about 2.1 billion documents wraps the total negative, and Lucene skips the merge as empty.

Background: addIndexes(CodecReader...) and wrapForMerge

#
  1. addIndexes(CodecReader...) copies documents from readers you pass in into the writer's index, as one or more merges.
  2. Before merging, it counts the readers' live documents in a long and throws IllegalArgumentException if the index would exceed MAX_DOCS (2,147,483,519).
  3. An expert merge policy can override findMerges(CodecReader...) and return a OneMerge whose wrapForMerge wraps each reader to "add/remove fields or documents", for example to keep deleted documents (soft-deletes retention does this on regular merges).
  4. With an index sort, the wrapped readers go straight to the merger; without one, a merged view over them is built first, and that view also checks the total.

The finding, step by step

#
  1. Open an IndexWriter with an index sort and a merge policy whose findMerges(CodecReader...) returns a OneMerge with a wrapForMerge that makes every document live again, deleted ones included.
  2. Call addIndexes(a, b), where each input has 1,100,000,000 doc IDs and 1 live document. The limit check counts live documents, 2, far below MAX_DOCS (2,147,483,519), so the call is admitted.
  3. The wrapper turns them into 2 x 1,100,000,000 = 2,200,000,000 documents. You expect IllegalArgumentException, which addIndexes documents for going past MAX_DOCS.
  4. Instead MergeState adds the wrapped counts in an int: 2,200,000,000 wraps to -2,094,967,296. The merger sees a non-positive maxDoc, takes the merge for an empty one and skips it, so addIndexes returns normally and the writer holds 0 documents.
  5. Without an index sort the same call does throw, because a merged view checks the total first; so only index-sorted writers (and, since 9.11.0, block inputs without a parent field) get the silent no-op.

Who is affected

#

Only applications with a custom merge policy whose findMerges(CodecReader...) merge revives or adds documents in wrapForMerge, on an index-sorted writer, with inputs above about 2.1 billion doc IDs. No merge policy that Lucene ships does this. They are told the call succeeded when nothing was added; the destination index stays valid.

Mechanism, terms and numbers565 words

IndexWriter.addIndexes(CodecReader...) checks the document limit with a long sum, but only over the readers you pass in (IndexWriter.java:3278-3296, again at :3496-3518). It then hands every reader to the merge policy's OneMerge#wrapForMerge (:3542-3546), whose javadoc allows a wrapper to "add/remove fields or documents" (MergePolicy.java:302), and MergeState adds up the wrapped readers' numDocs() in an int and stores it unchecked (MergeState.java:127, :170, :173).

When a wrapper brings the total above Integer.MAX_VALUE (2 x 1.1 billion in the repro), the sum wraps to -2,094,967,296, SegmentMerger.shouldMerge() (maxDoc > 0) is false, and addIndexesReaderMerge returns before writing a segment (IndexWriter.java:3579-3581). addIndexes reports success having added nothing, where it documents IllegalArgumentException (:3272-3273). Without an index sort, a merged view built first rejects the total loudly (:3548-3566, BaseCompositeReader.java:82-108), so only index-sorted writers (and, from 9.11.0, block inputs without a parent field) are hit. It needs an expert, experimental merge-policy extension and more than 2.1 billion doc IDs; no merge policy that Lucene ships wraps readers on this path. Present since 9.9.0. Fix: a long sum and a limit check in MergeState.

Around the repro

#
  • With an identity wrapper the same inputs add their 2 live documents.
  • Without an index sort the merged view's check rejects such inputs with IllegalArgumentException (the cross-model reviewer's no-sort control).
  • From 9.11.0, unsorted writers given block inputs without a parent field also skip the view and reach the same silent return (executed on main by an independent reproducer).
  • A regular forceMerge with a count-inflating wrapper fails loudly instead (invalid softDelCount=0 (maxDoc=-2094967296)).
  • The padded input is not a valid segment, but the outcome does not depend on it: a follow-up test that passes a real one-document input twice, with a wrapper that consistently serves 1,100,000,000 empty documents for each (no fields, empty stored fields), also returns normally on main and gets the exception with the fix.
Exposure and likelihood180 words
  • Who is hit. Applications that call addIndexes(CodecReader...) through a custom merge policy whose findMerges(CodecReader...) returns a OneMerge with a wrapForMerge that revives or adds documents, on an index-sorted writer (or, from 9.11.0, with block inputs that have no parent field), with inputs whose wrapped document count exceeds Integer.MAX_VALUE while their live documents fit the limit.
  • Default vs opt-in. Opt-in only. No merge policy that Lucene ships (non-test source at 5adff78bb168) wraps readers on this path: OneMergeWrappingMergePolicy (and so SoftDeletesRetentionMergePolicy) does not override findMerges(CodecReader...), and BPReorderingMergePolicy only forwards the inner merge's wrapForMerge.
  • What goes wrong. A call that must fail reports success. An application that treats a successful addIndexes as "the documents are in" (for example, then deletes its source) loses them. No segment is written, so the destination index stays consistent; this is not index corruption.
  • Scale. More than about 2.1 billion doc IDs across the inputs. The repro reaches it with synthetic readers; a real-data run of that size was not executed.
  • Likelihood. Contrived: an expert, experimental extension plus billions of doc IDs. Priority Low.

Why it looks unintended

#
  • addIndexes(CodecReader...) documents "@throws IllegalArgumentException if addIndexes would cause the index to exceed MAX_DOCS"; the only documented drop is for empty segments.
  • wrapForMerge is documented as the place to "add/remove fields or documents".
  • The same method already sums in long "so we can detect int overflow", but before wrapping; without an index sort the same call throws.
The full argument272 words
  • The contract. addIndexes(CodecReader...): "@throws IllegalArgumentException if addIndexes would cause the index to exceed MAX_DOCS" (IndexWriter.java:3272-3273); MAX_DOCS: "If you try to add more than this you'll hit IllegalArgumentException" (:202-203). The only documented drop is "empty segments are dropped by this method" (:3262); this merge is not empty.
  • The extension point invites it. wrapForMerge: "Wrap a reader prior to merging in order to add/remove fields or documents" (MergePolicy.java:302). Reviving deleted documents is what SoftDeletesRetentionMergePolicy does in its wrapForMerge on regular merges (SoftDeletesRetentionMergePolicy.java:64-71, which calls applyRetentionQuery; the revival is at :123-140).
  • The code already guards this overflow, one step too early. addIndexes and addIndexesReaderMerge sum in long "so we can detect int overflow" (IndexWriter.java:3278, :3496), before wrapping; the unsorted path is protected by the merged view's check. The outcome depends only on whether that view is built: an index sort (or, from 9.11.0, block inputs without a parent field) skips it.
  • History. #12622 (9.9.0) started merging the wrapped readers on this path, kept the checks on the unwrapped counts and built the checking view only without an index sort; its review does not discuss the document limit or an overflow of the merged count (its only numDocs remark is about computing it lazily), and no CHANGES entry names it. Upstream intent elsewhere is to refuse indexes above the limit (#6905 / LUCENE-5843, #7360 / LUCENE-6299), and open PR #16847 adds the same wrapped-count guard to mergeMiddle.
  • No acceptance anywhere. No javadoc, test, CHANGES or MIGRATE entry, issue, PR or list thread accepts a silent no-op here.
The devil's-advocate check180 words

The strongest case against: MergePolicy and OneMerge are @lucene.experimental (MergePolicy.java:69, :189); findMerges(CodecReader...) is documented for controlling concurrency (:605-616); no in-tree policy reaches the path; the repro's input claims 1.1 billion doc IDs over a one-document segment (CheckIndex would reject it, since it reads stored fields of deleted documents too, CheckIndex.java:3592-3597); and more than two billion doc IDs is an absurd scale. The independent cross-model reviewer argued this and rated the bug not real.

Why it fails: @lucene.experimental allows API changes, not a silent wrong success. The repro's wrapper keeps maxDoc and only revives documents, the pattern Lucene itself uses. The padded input is not a valid segment (only its counts and live docs are padded), but the outcome does not depend on it: a wrapper that consistently serves 1.1 billion empty documents per real one-document input gets the same silent no-op. A huge input that fails loudly would be defensible; this one fails silently, and the documented outcome at this scale is an exception. What remains is likelihood, which is why it is Low.

Suggested fix

#

Recommended Sum in long in MergeState and throw above the limit

Sum the wrapped readers' numDocs() in a long in MergeState and throw IllegalArgumentException above IndexWriter.getActualMaxDocs() before setMaxDoc (MergeState.java:127-173). One place covers addIndexes and regular merges. With it the repro passes, and so do the closest suites (155 tests) and the whole core org.apache.lucene.index test package (1,398 tests).

Trade-offs

  • One place covers both merge paths: addIndexes and regular merges, where a count-inflating wrapper today fails later with invalid softDelCount=0 (maxDoc=-2094967296) (by reading, not executed, it would get this exception instead). One comparison per merge.

  • It does not reconcile the writer's reserved document count when a wrapper adds documents but stays under the limit; that is a different defect, not claimed here.

How it was found

#

A semi-formal proof-obligation check of MergeState's constructor: the merged document count must fit in an int. IndexWriter establishes that only for the readers before wrapForMerge, so the check pointed at the unchecked sum of the wrapped counts, and a one-method public-API test then witnessed the silent no-op on main.

The method in full142 words

Method: semi-formal proof-obligation check, witnessed by an executable repro (2026-11-04, main 5adff78bb168).

  • The obligation: the MergeState constructor stores the sum of its readers' numDocs() as the new segment's maxDoc, so that sum must fit in an int and stay within MAX_DOCS.
  • What the check found: on the addIndexes(CodecReader...) path the callers establish the bound only for the unwrapped readers (IndexWriter.java:3278-3296, :3496-3518), while MergeState receives the readers after wrapForMerge, which may add documents; with an index sort no other check runs.
  • The finding was then witnessed by a JUnit test and checked by an independent reproducer (real), an independent cross-model reviewer (reproduced the no-op and agreed on the cause, but rated it not real), an intended-behaviour devil's advocate (real) whose maxDoc-preserving reviving wrapper is the repro shown here, and an adjudication (confirmed); see Independent checks.

#

Summary
You open an index-sorted IndexWriter whose merge policy's findMerges(CodecReader...) returns a OneMerge whose wrapForMerge revives deleted documents (its javadoc allows a wrapper to 'add/remove fields or documents'), and call addIndexes(CodecReader...) with inputs whose live documents fit under MAX_DOCS but whose revived documents total more than Integer.MAX_VALUE; you expect the IllegalArgumentException that addIndexes documents for exceeding MAX_DOCS. Instead addIndexes returns normally and adds nothing: IndexWriter checked the limit only on the unwrapped readers, MergeState sums the wrapped readers' numDocs() in an int that wraps negative (-2,094,967,296 for 2 x 1.1 billion), SegmentMerger.shouldMerge() is then false, and addIndexesReaderMerge returns before writing a segment. Without an index sort, the merged view that IndexWriter builds first rejects the same total with IllegalArgumentException, so only index-sorted writers (and writers given block inputs without a parent field) get the silent no-op.
