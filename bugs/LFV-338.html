MappingCharFilter.reset() keeps the first read's offset corrections, so offsets are wrong after a re-read

Rewind a MappingCharFilter with reset() and read it again, and its offsets come out wrong: for a->xy over "a", correctOffset(2) is 1 on the first read and 0 on the second. reset() rewinds the input but keeps the first read's offset corrections, and the second read builds on them.

The finding in 30 seconds

#

How a char filter maps offsets back

#
  1. A char filter rewrites text before the tokenizer. MappingCharFilter with the map a->xy turns a b into xy b.
  2. Tokens need positions in the original text, for example for highlighting. So the filter records correction points while it reads, and correctOffset(n) maps an output offset back: offset 2 (the end of xy) becomes 1 (the end of a).
  3. Each correction point is computed from the one before it: a running total of how far output and input have drifted apart. The first read starts that total at 0.

The finding, step by step

#
  1. Map a to xy and read a MappingCharFilter over "a" to the end. The output is xy, and correctOffset(2) is 1: the end of xy maps back to the end of a.
  2. Call reset() and read again. MappingCharFilter overrides reset() so it can be re-read, and Lucene's own test does this. The output is xy again, so you expect correctOffset(2) = 1 again.
  3. Instead you get 0. Through a WhitespaceTokenizer over "a b", the re-read gives the tokens xy[0,0] b[1,2] instead of xy[0,1] b[2,3].
  4. Why: reset() rewinds the reader but keeps the list of corrections. The second read starts from the first read's running total (-1, not 0), so it appends the entry (2, -2) after (1, -1), and offset 2 now maps to 0.
  5. Deleting maps are worse: b->"" over "ba" gives correctOffset(1) = 3 for a 2-character input with assertions off, and an AssertionError inside read() with them on. When the re-read completes, the characters and terms are right; only the offsets are wrong.

Who is affected

#

Only application code that calls reset() on a MappingCharFilter itself and reads it again. With assertions off, the offsets it then uses (correctOffset(), token offsets for highlighting) are wrong; with assertions on, the second read() can throw. No Lucene path resets a char filter. A one-character input is enough; terms and matching stay right when the re-read completes. Rare.

Mechanism, terms and numbers530 words

MappingCharFilter overrides Reader.reset() so that it can be rewound and read again. reset() rewinds the input and the read position, but not the list of offset corrections the filter inherits from BaseCharFilter. On the second read every length-changing match computes its correction from the first read's last running total and appends it to the old list.

So after reset() and a re-read, correctOffset() is wrong: for a->xy over "a" it maps the end of the output to 0 instead of 1, and a tokenizer over "a b" gives xy[0,0] b[1,2] instead of xy[0,1] b[2,3]. For deleting or shrinking maps, offsets come out too large, often past the end of the input (assertions off); with assertions on, BaseCharFilter's ordering assertion can fire inside read() and the second read never finishes. When the re-read completes, characters, terms and matching are right. No Lucene code path resets a char filter, so only application code that calls reset() itself and reads again is hit. The fix is to clear the list in reset() (8 added lines), or to drop reset() support.

The code (main 645d4fe14a20)

#
  • BaseCharFilter.java:31-33: the correction list is private int[] offsets; private int[] diffs; private int size. It is private, and BaseCharFilter has no method that clears it.
  • BaseCharFilter.java:55-57: getLastCumulativeDiff() returns diffs[size - 1], the running total of the last entry.
  • MappingCharFilter.java:142-157: for a match whose replacement has a different length, prevCumulativeDiff = getLastCumulativeDiff() (:145), and the new entries are placed and valued relative to it (:148 for a shorter replacement, :153-156 for a longer one).
  • MappingCharFilter.java:62-68: reset() is input.reset(); buffer.reset(input); replacement = null; inputOff = 0;. The list is kept.
  • BaseCharFilter.java:59-67: addOffCorrectMap documents that each offset "will not be smaller than the offset given at the previous invocation"; :77-87 asserts it. correct() binary-searches the list (:46), which needs it sorted.

Walk-through, a->xy over "a" (executed)

#
pass 1   running total  0   adds (off 1, diff -1)    list [(1,-1)]          correctOffset(2) = 2-1 = 1
reset()  input rewound, inputOff = 0                 list [(1,-1)]   kept
pass 2   running total -1   adds (off 2, diff -2)    list [(1,-1),(2,-2)]   correctOffset(2) = 2-2 = 0

For b->"" over "ba": pass 1 adds (0, +1), so correctOffset(0..1) = [1,2]. Pass 2 starts from +1 and computes (-1, +2), an offset that goes backwards. With assertions on, addOffCorrectMap throws AssertionError: Offset #1(-1) is less than the last recorded offset 0 from inside read(); with them off the list [0,-1] is unsorted, the binary search for 1 lands on the entry (-1, +2), and correctOffset(1) = 1 + 2 = 3, past the end of the 2-character input.

The characters stay right whenever the re-read completes: the characters read() returns depend only on state that reset() rewinds (input, buffer, replacement, inputOff) and on the immutable map. The stale list is read by correct() and, inside read(), by getLastCumulativeDiff(), whose value only goes into new corrections; those go through addOffCorrectMap, so with assertions on its ordering assertion can throw from inside read() (the b->"" case) before the second read finishes.

Exposure and likelihood339 words
  • Trigger. An explicit reset() on a MappingCharFilter over a reader that can rewind (such as StringReader), a second read (with assertions on, that read can already throw), and then offsets. The use reset() support was added for in 2009 was exactly this: show the normalized text, rewind, tokenize the same reader.
  • Not on any Lucene path. Analyzer calls initReader for every value (Analyzer.java:155, :191), MappingCharFilterFactory.create builds a new filter each time (MappingCharFilterFactory.java:91), and Tokenizer never rewinds its reader. MappingCharFilter is the only CharFilter in the source tree that overrides reset(); the others inherit java.io.Reader.reset(), which throws.
  • Scale. No special setting; a one-character input is enough. Only inputs on which a length-changing mapping fires are affected (an empty input, or one the map never matches, is not), and whether a wrong value shows depends on the input, the read style, the assertion mode and the offset asked for. Over all 1,092 strings of length 1 to 6 on {a, b, ' '}, the re-read gave wrong offsets for 966 (a->xy), 602 (b->"") and 363 (ab->x) of them with assertions off.
  • Effect. With assertions off, offsets too small for a longer replacement (a->xy) and too large for deleting or shrinking maps, often past the end of the input: over the same 1,092 strings, b->"" gives 516 too-large values inside the input and 774 past the end, ab->x 429 and 371, a->xy only too-small values (for example b->"" over "baa": correctOffset(1) = 3 instead of 2). With assertions on, the second read() instead throws BaseCharFilter's ordering AssertionError on 966 (b->""), 484 (ab->x) and 516 (a->xy) of those inputs. When the re-read completes, terms and matching are right.
  • Likelihood. Rare: nothing in Lucene resets a char filter, and the recorded searches found no report since 2009.

Why it looks unintended

#
  • MappingCharFilter overrides reset() on purpose, Lucene's own testReaderReset re-reads after it, and java.io.Reader allows reset() without mark().
  • A CharFilter is a Reader "with additional offset correction", yet after reset() offsets even land past the end of the input.
  • In LUCENE-4321 a committer called this tested reset() support fine; BaseCharFilter's own assertion fires inside read() after it.
The full argument239 words
  • Deliberate support. MappingCharFilter.reset() (MappingCharFilter.java:62-68) was added by LUCENE-3830 (2012) to rewind the buffer, replacement and inputOff. LUCENE-1734 (2009) first made reset() work, because its reporter wanted "to call reset() to rewind reader in SOLR-1256", and added TestMappingCharFilter.testReaderReset (TestMappingCharFilter.java:65-79), which re-reads after reset() and checks characters only. Its input "x" matches none of the mappings in setUp() (TestMappingCharFilter.java:41-63), so it records no corrections and could not catch this bug even if it checked offsets.
  • Legal Reader use. The java.io.Reader.reset() javadoc: "If the stream has not been marked, then attempt to reset it in some way appropriate to the particular stream, for example by repositioning it to its starting point. ... some support reset() without supporting mark()".
  • Offsets are the point. CharFilter.java:22-25: "They can be used as java.io.Reader with additional offset correction"; MappingCharFilter.java:29-33: "correcting the resulting changes to the offsets".
  • Lucene's own precondition breaks. BaseCharFilter.addOffCorrectMap documents and asserts non-decreasing offsets (BaseCharFilter.java:59-67, :77-87); MappingCharFilter violates it from a plain read() after reset().
  • A committer called it supported. LUCENE-4321 (#5388, 2012), Robert Muir: "If someone (like MappingCharFilter) wants to support reset() and has tests for it (like MappingCharFilter), then thats fine" and "it supports reset() but not mark(), (only if also its input supports reset()) which is allowed". The outcome kept MappingCharFilter.reset().
  • Nothing says otherwise. No javadoc, test, CHANGES or MIGRATE entry says offsets are invalid after reset().
The devil's-advocate check210 words

The strongest case for "intended": CharFilter does not document reset(), markSupported() is false (inherited from Reader), and java.io.Reader.reset() says nothing about a subclass's offset metadata, so a maintainer can call the second-pass offset semantics underspecified. In the same LUCENE-4321 thread Uwe Schindler wrote that Lucene does not use those methods at all and that implementing them correctly with offsets is too heavy. The only test checks characters, on an input that no mapping matches.

Why it fails: the Reader contract only shows that calling reset() is legal, not what the offsets must be; the stronger evidence is the class's purpose (offset correction), its override that rewinds every other read coordinate, and its own tripped ordering assertion. The remark argues for not supporting reset() unless it is done right, not for supporting it with wrong offsets, and the thread then kept MappingCharFilter's reset() as supported (Robert Muir, above). Offsets past the input length and a tripped internal assertion are not a defensible behaviour. Upstream may fairly prefer to drop reset() support instead of fixing it; that is a choice of fix, not evidence that the behaviour is intended. The intended-behaviour devil's advocate and the adjudication rejected the argument, and the cross-model reviewers rated their own intended-behaviour argument weak.

Suggested fix

#

Recommended Clear the correction list on reset() (validated)

Clear the correction list in reset(): add a protected BaseCharFilter.clearOffCorrectMap() (sets offsets and diffs to null and size to 0) and call it from MappingCharFilter.reset(), 8 added lines. Validated on main: the repro passes with assertions on and off, as do the 64 charfilter tests (two seeds) and the whole analysis-common module.

   // BaseCharFilter
+  /** Removes all recorded offset corrections, e.g. when a subclass rewinds its input in reset(). */
+  protected void clearOffCorrectMap() {
+    offsets = null;
+    diffs = null;
+    size = 0;
+  }

   // MappingCharFilter.reset()
     inputOff = 0;
+    clearOffCorrectMap();
   }

Clear the correction list on reset() (validated) (recommended)

#

A protected clearOffCorrectMap() in BaseCharFilter, called at the end of MappingCharFilter.reset(). 2 files, +8 lines.

   // BaseCharFilter
+  /** Removes all recorded offset corrections, e.g. when a subclass rewinds its input in reset(). */
+  protected void clearOffCorrectMap() {
+    offsets = null;
+    diffs = null;
+    size = 0;
+  }

   // MappingCharFilter.reset()
     inputOff = 0;
+    clearOffCorrectMap();
   }

Trade-offs

  • Adds a protected method to the public abstract BaseCharFilter; the name and shape are upstream's call. A package-private method would also work (both classes are in the same package), but subclasses in other modules could not use it. A downstream subclass may already declare a clearOffCorrectMap(): the call from reset() is virtual and would dispatch to it (or the subclass stops compiling if the signatures clash). final, a package-private method or another name avoids that; @lucene.internal only documents intent.
  • A first read is unchanged; only code that calls reset() sees different offsets, now the same as a fresh filter's.
  • A bare size = 0 (the approach of the unmerged 2010 LUCENE-2788 patch) is not enough on main: offsets stays non-null, so getLastCumulativeDiff() would read diffs[-1] (BaseCharFilter.java:55-57).
  • Out of scope: if the underlying reader was mark()ed mid-stream before it was wrapped, input.reset() returns to the mark while inputOff restarts at 0.
  • Not run: a MappingCharFilter over another MappingCharFilter. By reading the source, the fix handles it (the outer input.reset() resets the inner filter, which clears its own list, and CharFilter.correctOffset chains the two, CharFilter.java:71-77), and no other state stays stale (replacementPointer is unused once replacement is null; the buffer, the FST reader and scratchArc are reset or overwritten), but no executed test checks it.

Drop reset() support (not run)

#

Remove the override, so reset() throws IOException("reset() not supported") from java.io.Reader, like every other CharFilter. Precedent: LUCENE-4072 (#5144), where reset() support was removed from ICUNormalizer2CharFilter before it was committed.

Trade-offs

Smallest change, but it removes behaviour that has worked for characters since 2009 and deletes testReaderReset; a breaking change, so main (11.0) with a MIGRATE note.

Document the limitation (not recommended)

#

State that offsets are not valid after reset().

Trade-offs

Leaves the wrong offsets and the AssertionError inside read() in place.

How it was found

#

A bounded-exhaustive check compared MappingCharFilter's output and offsets with a reference model for every small map and input. Its reset obligation (read, reset(), read again: same output and offsets) failed 248 of its 640 reset checks (in 960 runs) at the smallest scope, while the single-pass checks held on 81 million runs. A public-API test then confirmed it.

The method in full240 words

Method: semi-formal (bounded-exhaustive translation validation, then an executed test).

  • Finder. The hunt unit for analysis char filters, stemmers and tokenizers wrote a reference model of MappingCharFilter and checked the real filter against it for every map of 1 to 3 keys (keys of up to 3 characters over {a, b}, values "", x, xy, xyz) and every input of length up to 6 over {a, b, c}: output characters, correctOffset() at every position, two chunkings of the underlying reader and two read styles. The single-pass obligations held on 81,345,432 runs.
  • Reset obligation. Read to the end, reset(), read again: same output and same offsets. At the smallest scope (one 1-character key, inputs over {a, b, c} of length at most 3) it failed 248 of the 640 reset checks with assertions off and 300 of 640 with them on (the ordering AssertionError); the scope has 960 runs, and the reset is checked on 2 of each input's 3 read styles. Every violation it printed was an offset mismatch, never an output mismatch.
  • Confirmation. A public-API JUnit (a->xy over "a") failed on main with assertions on and off and on 9.12.3; a main() probe failed on releases back to 4.0.0.
  • Hunt. Independent reproduction, cross-model reviews, an adjudication, the version-history runs, a prior-art search, a security screen, a credibility audit and a one-test minimal repro followed (see the checks below).

History

#

The root cause dates from LUCENE-1734 (6a3752feb8f, 2009), first released in 2.9.0, which made reset() rewind the input without clearing the list. LUCENE-3830 (4.0.0) added the current override; from then on the simple repro fails. All 18 releases run, from 2.9.0 to 10.6.0, fail; releases in between were not run.

Versions tested7 rows

Root cause introduced by 6a3752feb8f "LUCENE-1734: CharReader should delegate reset/mark/markSupported" (Uwe Schindler, 2009-07-06, svn era, a JIRA patch; the issue is now #2808). Before it, MappingCharFilter.reset() threw "mark/reset not supported"; after it, reset() rewound the input and kept the correction list. Nothing has cleared that list since.

Current code: LUCENE-3830 (3e9b5a9893c, Michael McCandless, 2012-05-06, #4903, first release 4.0.0) added the reset() override that rewinds the read state but not the list; LUCENE-4321 (568156b710a) changed super.reset() to input.reset() without changing behaviour (git blame of MappingCharFilter.java:62-67; the closing brace at :68 blames to 675597141b7f, an unrelated 2010 repository move, LUCENE-2326).

Before 4.0 a second stale counter mostly hid the bug on a plain read to the end (0 to 9 of 960 probe cases fail in 2.9.0 to 3.6.0; 134 to 135 of 960 for reads that stop before the end); 3.6.1 and 3.6.2 fail 133 of 960; from 4.0.0 on 569 of 960 fail with assertions on. On 2.9.0 sources, also clearing the list on reset gives 0 of 2,880 failures.

LFV-338, snapshot of 2026-11-08

Registry title
MappingCharFilter.reset() rewinds the input but keeps the offset corrections recorded on the first pass, so after a reset and re-read correctOffset() (and the token offsets a Tokenizer derives from it) are wrong, or BaseCharFilter's ordering assertion fires
Area
analysis / char filters (MappingCharFilter, BaseCharFilter offset correction)
Priority
Low, rank 1064: MappingCharFilter.reset() keeps stale offset corrections, which affects only direct reset-and-reread callers and only offsets.
Impact class
minor
Impact note
Only application code that calls Reader.reset() directly on a MappingCharFilter (over a resettable reader such as StringReader), reads it again and then uses offsets (correctOffset(), or token offsets from a Tokenizer over the re-read filter) is hit, at any input size and with no setting needed, on every release from 2.9.0 to 10.6.0 and on main: offsets come out too small or, with -da, past the end of the input, and with -ea BaseCharFilter's ordering assertion fires inside read(); the characters produced, the terms and matching are unaffected, and no Lucene code path (Analyzer, MappingCharFilterFactory, Tokenizer) ever resets a char filter.
Summary
You read a MappingCharFilter to the end, call reset() to rewind it (MappingCharFilter overrides reset() for this, and upstream TestMappingCharFilter.testReaderReset re-reads after it), read it again and expect correctOffset() to map the second pass's output back to the input exactly as on the first pass. Instead reset() rewinds the input and the filter's read state but not the offset-correction map it inherits from BaseCharFilter, so the second pass appends new corrections computed from the first pass's last cumulative diff: for the map a->xy over "a", correctOffset(2) returns 0 instead of 1, and a WhitespaceTokenizer over the re-read filter for "a b" gives xy[0,0] b[1,2] instead of xy[0,1] b[2,3]. For deleting or shrinking maps, with -ea the second read() trips BaseCharFilter's 'Offset ... is less than the last recorded offset' assertion, and with -da it returns offsets past the end of the input (b->'' over "ba": correctOffset(1) = 3 for a 2-character input).
