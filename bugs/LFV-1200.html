CharArrayMap and CharArraySet iterators never throw NoSuchElementException; on entrySet(), next() past the end returns a phantom entry

Calling next() once more after the last element of a CharArrayMap.entrySet() iterator throws nothing: it returns a fake entry whose getKey() throws ArrayIndexOutOfBoundsException, and CharArraySet iterators throw that exception instead of NoSuchElementException. Every release since 3.1.0; Lucene's own hasNext() loops are not affected.

The finding in 30 seconds

#

next() is goNext(); return new MapEntry(lastPos), with no hasNext() check. After the last key the position equals the table size, 8, so one more call builds an entry for slot 8, and its accessors read keys[8] or values[8]. The set, keySet() and values() iterators read the key or value inside next(), so they throw at once.

Background in two steps

#
  1. CharArraySet and CharArrayMap hold an analyzer's stop words, keywords and stem overrides as char[] keys in an open hash table of at least 8 slots. A CharArraySet is a view over a CharArrayMap, and its iterator walks the map's table.
  2. Java's Iterator contract: hasNext() says whether elements remain, and next() after the last one must throw NoSuchElementException. JDK helpers rely on it: Collections.max calls next() first and lets that exception report an empty collection.

The finding, step by step

#
  1. Put one key in a CharArrayMap (the hash table behind CharArraySet stop-word and keyword sets): new CharArrayMap<>(1, false), put("a", 1). Its table has 8 slots.
  2. Iterate its entrySet(): next() returns a=1, and hasNext() is now false.
  3. Call next() once more. You expect NoSuchElementException: Iterator.next() requires it, and a HashMap iterator throws it.
  4. Instead next() returns a fake entry for slot 8, one past the table. Its getKey(), getValue() and toString() throw ArrayIndexOutOfBoundsException: Index 8 out of bounds for length 8, later, wherever it is used.
  5. On CharArraySet.iterator() (also CharArraySet.EMPTY_SET) and the map's keySet() and values(), the same call throws that exception at once; so does Collections.max of an empty CharArraySet.

Who is affected

#

Only application code that calls next() on an exhausted CharArraySet or CharArrayMap iterator: a next()-first loop, code that catches NoSuchElementException to find the end, or Collections.max/min on an empty stop-word set. The Lucene loops over these iterators that were reviewed all check hasNext(). Default classes, no setting, every release since 3.1.0; the map is never damaged.

Mechanism, terms and numbers487 words

CharArrayMap.EntryIterator, a public class implementing java.util.Iterator, is behind CharArrayMap.entrySet(), keySet(), values() and every CharArraySet.iterator(). Its next() and nextKey() never check hasNext(). So calling next() after the last element does not throw the NoSuchElementException that Iterator.next() requires.

On the entrySet() iterator nothing is thrown: next() returns a Map.Entry for a slot past the end of the table, and its getKey(), getValue() and toString() throw ArrayIndexOutOfBoundsException when it is used. On CharArraySet.iterator() (including CharArraySet.EMPTY_SET) and the keySet() and values() iterators the same call throws ArrayIndexOutOfBoundsException: Index 8 out of bounds for length 8 at once. JDK helpers that call next() first hit it on an empty set: Collections.max(CharArraySet.EMPTY_SET, cmp) throws that exception, and Collections.max over an empty map's entrySet() returns the fake entry.

No unsafe use was found in Lucene's own source (the loops over these iterators that were reviewed all check hasNext()), so the callers at risk are in application code, with default classes and no setting. The code dates from CharArrayMap's introduction (LUCENE-2247, first released in 3.1.0). The fix is a hasNext() guard at the top of next() and nextKey().

The mechanism

#
  1. A CharArrayMap keeps keys and values in two arrays of at least 8 slots (INIT_SIZE = 8, CharArrayMap.java:38; constructor :54-62). new CharArrayMap<>(1, false) and the empty map behind CharArraySet.EMPTY_SET (CharArraySet.java:39, CharArrayMap.java:609-612) have 8.
  2. EntryIterator (:376) walks the slots. goNext() (:386-390) does lastPos = pos; pos++; and skips empty slots; hasNext() is pos < keys.length (:393-395).
  3. next() (:423-426) is goNext(); return new MapEntry(lastPos, allowModify); and nextKey() (:398-401) is goNext(); return keys[lastPos];. Neither checks hasNext(): the fix site.
  4. After the last key, pos is 8. One more next() sets lastPos = 8 and returns MapEntry(8) (then 9, 10, ... on further calls). MapEntry.getKey() is keys[pos].clone() (:447), getValue() is values[pos] (:452), and setValue() and toString() (:455-468) index the same arrays, so its key, value and string accessors throw ArrayIndexOutOfBoundsException (setValue() on an unmodifiable map throws UnsupportedOperationException first, :457; the inherited equals/hashCode do not touch the arrays). nextKey() reads keys[8] directly and throws at once.
  5. CharArraySet.iterator() is map.originalKeySet().iterator() (CharArraySet.java:162-167), AbstractMap's key-set view over entrySet() (CharArrayMap.java:336-338), whose next() is i.next().getKey(); values() is AbstractMap's view with i.next().getValue() (JDK 25 AbstractMap.java:918, :925). CharArrayMap.keySet() is a CharArraySet over the same map (:346-373). On those paths the exception comes out of next() itself.
  6. Collections.max and min begin with coll.iterator().next() (JDK 25 Collections.java: min :623-633, with a comparator :659-672; max :696-706 and :732-745) and document NoSuchElementException "if the collection is empty". Collections.max(CharArraySet.EMPTY_SET, cmp) throws ArrayIndexOutOfBoundsException; Collections.max over an empty map's entrySet() returns a CharArrayMap$MapEntry; on an empty HashSet it throws NoSuchElementException (earlier probes on main, assertions off).
Exposure and likelihood218 words
  • Who: application code that calls next() on an exhausted iterator of a CharArraySet (stop-word, keyword and protected-word sets; StopwordAnalyzerBase.getStopwordSet() returns "an empty set if the analyzer has no stopwords", StopwordAnalyzerBase.java:39-41) or of a CharArrayMap entrySet(), keySet() or values() view. That means a next()-first pattern, code that catches NoSuchElementException to detect the end, or an empty set passed to a JDK helper that calls next() first, such as Collections.max/min. Default classes, no setting, assertions on and off.
  • Not hit: Lucene itself, as far as the source review found. The loops over these iterators that were reviewed check hasNext() (the for-each loops in CharArrayMap.toString() :313 and CharArraySet.toString() :172, DutchAnalyzer.java:126-131, the one non-test caller of EntryIterator.nextKey() outside the class, and TestCharArrayMap.java:118-127, a while (hasNext()) loop), and no Lucene source, sandbox included, calls Collections.max/min.
  • Effect: on the entrySet() path the call itself succeeds: the caller gets an object that looks like an entry and fails later, at first use, away from the cause. On the other paths the failure is immediate, but the ArrayIndexOutOfBoundsException escapes a catch (NoSuchElementException e). The map is never modified (setValue throws before the store) and nothing is read outside the arrays.
  • Scale and likelihood: one call; rare. No public report of it was found since 3.1.0 (2011).

Why it looks unintended

#
  • EntryIterator is a public java.util.Iterator; Iterator.next(): "@throws NoSuchElementException if the iteration has no more elements".
  • Lucene's TestUtil.checkIterator rejects exactly this as "broken iterator (allows next() when hasNext==false)"; FilterIterator.next() has the guard the fix adds.
  • CharArraySet's "does not behave like it should in all cases" note is about element types, not the end of iteration; CharArrayMap has no such note.
The full argument198 words
  • The contract: public class EntryIterator implements Iterator<Map.Entry<Object, V>> (CharArrayMap.java:375-376, "public iterator class so efficient methods are exposed to users"), and CharArraySet.iterator() overrides Set.iterator(). Iterator.next(): "@throws NoSuchElementException if the iteration has no more elements" (JDK 25 Iterator.java:72).
  • Lucene's test framework calls it broken: TestUtil.checkIterator (test-framework TestUtil.java:190-243) requires that an iterator throws NoSuchElementException when next is called after hasNext returns false, else it fails with "broken iterator (allows next() when hasNext==false)" (:209, :238). A probe of it on CharArrayMap{a=1}.entrySet().iterator() fails with exactly that message, on CharArraySet[a].iterator() with the ArrayIndexOutOfBoundsException; the JDK controls (unmodifiable HashMap and HashSet views) pass.
  • Lucene's other public iterators follow it: FilterIterator.next() is if (!hasNext()) throw new NoSuchElementException(); (util/FilterIterator.java:51-54); MergedIterator (util/MergedIterator.java:105) and PriorityQueue's iterator (util/PriorityQueue.java:387) throw it too.
  • The change that wrote this code promised it: LUCENE-2247 (#3323), which added CharArrayMap and EntryIterator, describes "correct iterators (returning the native char[])".
  • Nothing allows it: no javadoc, test, CHANGES or MIGRATE entry says these iterators may be called past the end. CharArrayMap's class javadoc (:27-32) lists what it does not do (remove items, shrink the table), not this.
The devil's-advocate check233 words

The strongest case for "intended": CharArraySet's javadoc says "This class implements Set but does not behave like it should in all cases" (CharArraySet.java:30-34); both classes say they are "not a general purpose class"; calling next() after hasNext() is false is a caller bug; the set, keySet() and values() paths fail loudly anyway; and no public report of it was found since 3.1.0 (2011). One other Lucene iterator, the anonymous one of GraphTokenStreamFiniteStrings.getFiniteStrings() (util/graph/GraphTokenStreamFiniteStrings.java:149-157), has no NoSuchElementException check either.

Why it fails: the GraphTokenStreamFiniteStrings iterator is not a precedent but a second instance of the same defect, tracked separately as LFV-1254. The CharArraySet note names the deviations it means, the Set<Object> type, the toString() conversion and the char[] elements; it comes from LUCENE-1989 (#3064), which was about generics, and CharArrayMap, whose entrySet() iterator is the silent path, has no such note. "Not a general purpose class" is followed by its examples (no removal, no shrinking). The Iterator contract says exactly what the "caller bug" call must do, and JDK helpers such as Collections.max/min make that call on an empty collection by design. The entrySet() path does not fail loudly: it hands back a fake entry. What remains is an impact argument (a rare call pattern, no data damage), which is why this is Low. An independent reviewer from another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak.

Suggested fix

#

Recommended A. A hasNext() guard in next() and nextKey() (validated)

Add if (!hasNext()) throw new NoSuchElementException(); at the top of EntryIterator.next() and nextKey() (+7 lines in CharArrayMap.java, with the import). The set, keySet(), values() and nextKeyString() paths all go through these two. The repro passes with assertions on and off; the core analysis tests, TestDutchAnalyzer and the format and lint checks pass.

@Override
public Map.Entry<Object, V> next() {
  if (!hasNext()) {
    throw new NoSuchElementException();
  }
  goNext();
  return new MapEntry(lastPos, allowModify);
}
// and the same three-line guard at the top of nextKey()

A. A hasNext() guard in next() and nextKey() (validated) (recommended)

#

In CharArrayMap.EntryIterator (CharArrayMap.java:398-401, :423-426), add import java.util.NoSuchElementException; and:

@Override
public Map.Entry<Object, V> next() {
  if (!hasNext()) {
    throw new NoSuchElementException();
  }
  goNext();
  return new MapEntry(lastPos, allowModify);
}
// and the same three-line guard at the top of nextKey()

Trade-offs

  • One int comparison per call; for-each loops already call hasNext() before each next().
  • lastPos is not advanced by the failing call, so currentValue() and setValue() afterwards still refer to the last returned key.
  • The same pattern as FilterIterator.next().
  • CHANGES: a Bug Fixes entry under the next release.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: every test class of lucene/core's org.apache.lucene.analysis packages (TestCharArrayMap, TestCharArraySet, TestStopFilter, TestWordlistLoader, the standard and token-attribute tests and the repro): 22 classes, 169 tests, 0 failures, 0 skipped; TestDutchAnalyzer (whose analyzer calls nextKey()): 8 tests, 0 failures.
  • The repro asserts only the entrySet() path. With the fix, a probe saw NoSuchElementException on every other path too: nextKey(), nextKeyString(), keySet(), values(), CharArraySet (including EMPTY_SET) and Collections.max/min on an empty set; currentValue() still returns the last value.
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test.
  • The full lucene/core and lucene/analysis suites were not run.

B. One guard in goNext()

#

if (pos >= keys.length) throw new NoSuchElementException(); at the top of goNext() (:386). The constructor's first call starts at pos = -1, so it never trips there.

Trade-offs

Equivalent behaviour from one site, but the check is less visible in the public methods. By reading, not run.

C. Document that these iterators must not be called past the end

#

Say in the javadoc that next() past the end is undefined.

Trade-offs

Contradicts the Iterator contract the classes declare and TestUtil.checkIterator, and leaves the silent fake entry. Not recommended.

How it was found

#

Semi-formal: a proof-obligation audit of CharArrayMap's iterator against the java.util.Iterator contract, that next() after the last element throws NoSuchElementException. EntryIterator.next() has no check that could discharge it, and a JUnit test on stock main witnessed the failure.

The method in full79 words
  • Obligation: next() on an iterator whose hasNext() is false throws NoSuchElementException (Iterator.next(); also required by Lucene's TestUtil.checkIterator).
  • Finding: EntryIterator.next() and nextKey() advance with goNext() and never consult hasNext(), so past the end they index one slot beyond the table; every view built on the iterator inherits it.
  • Witness: a JUnit test on an empty CharArraySet, then this entry-set test, an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
