Classic Highlighter: QueryScorer weights a repeated term by clause order, so equal queries can pick different best fragments

When a query boosts the same term differently in several clauses, the classic Highlighter's QueryScorer keeps the last term clause's boost, not the highest, so two equal() queries that differ only in clause order can show different snippets. Every release since 2.9.0; marked words and search results stay correct.

The finding in 30 seconds

#

The classic Highlighter keeps one weight per query term. When clauses repeat a term with different boosts, it keeps the one it saw last (for phrases, the first that matches), not the highest.

How the classic Highlighter picks a snippet

#
  1. Highlighter cuts the text into fragments; SimpleFragmenter(n) makes pieces of about n characters.
  2. QueryScorer gives every query term one weight, taken from the query's boosts (alpha^5 gives 5; with an IndexReader it is also multiplied by a per-term IDF factor), and scores a fragment by adding the weights of the distinct query terms in it.
  3. getBestFragment returns the highest-scoring fragment with the query terms marked (<B>...</B> by default); each word's score also goes to the Formatter.

The finding, step by step

#
  1. You highlight the two words alpha beta with new Highlighter(new QueryScorer(q, "f")) and SimpleFragmenter(6), which cuts them into the fragments alpha and beta. A fragment's score is the sum of the weights (boosts) of the query terms in it.
  2. You do it for q1 = alpha^5 beta^3 alpha and for q2 = alpha beta^3 alpha^5 (all SHOULD clauses). q1.equals(q2) is true: BooleanQuery ignores clause order.
  3. You expect the same snippet for both, <B>alpha</B>: alpha's highest weight, 5, beats beta's 3.
  4. Instead q1 gives <B>beta</B>. Each term clause overwrites the term's weight, so alpha ends at 1, the weight of the last alpha clause, and beta wins 3 to 1. q2 ends at 5 and gives <B>alpha</B>. No error.
  5. Two phrases that share a term go the other way: the boost of the first phrase that matches wins. QueryScorer's own array constructor, QueryTermScorer and, since #15434, the FastVectorHighlighter keep the highest weight.

Who is affected

#

Applications that build snippets with the classic Highlighter and its default QueryScorer for queries that boost the same term differently in several clauses: parsed alpha^5 beta^3 alpha, a boosted term next to a synonym query that contains it, or two boosted phrases sharing a term. Only the chosen snippet and the formatter's scores change. Rare.

Mechanism, terms and numbers572 words

The classic Highlighter's QueryScorer gives every query term one weight, taken from the query's boosts (with an IndexReader, also multiplied by a per-term IDF factor), and scores a fragment by adding the weights of the distinct query terms in it. When several clauses name the same term with different boosts, WeightedSpanTermExtractor keeps the weight of the last term clause it visits (and of the first span or phrase clause that matches the text) instead of the highest. Two BooleanQuery objects that are equal() and differ only in clause order therefore give that term different weights and can pick different best fragments, with no error: for alpha^5 beta^3 alpha the weight of alpha is 1, for alpha beta^3 alpha^5 it is 5. QueryScorer(WeightedSpanTerm[]), QueryTermScorer and, since #15434, the FastVectorHighlighter use the highest weight. Only snippet choice and the token scores given to the Formatter change; the highlighted words and the search results stay correct. It is in every release from 2.9.0 through 10.6.0 and on main, and it is Low: it needs the same term boosted differently in several clauses.

The mechanism (main 5adff78bb168)

#
  1. QueryScorer.initExtractor (QueryScorer.java:202-213) asks WeightedSpanTermExtractor.getWeightedSpanTerms for one WeightedSpanTerm per term text, kept in a PositionCheckingMap (WeightedSpanTermExtractor.java:513-526). The repro uses QueryScorer(Query, String), so the weight is the boost; the constructors that take an IndexReader (QueryScorer.java:76-88) multiply each weight by a per-term IDF factor after the extraction (WeightedSpanTermExtractor.java:540-559), which scales both orders alike.
  2. extract multiplies in BoostQuery boosts (:131-132) and walks the BooleanQuery clauses in list order (:133-138). A TermQuery or SynonymQuery goes to extractWeightedTerms (:170-171), a span query or phrase to extractWeightedSpanTerms (:139-163, :172-173), and each DisjunctionMaxQuery clause back through extract (:183-186).
  3. extractWeightedTerms replaces. It builds new WeightedSpanTerm(boost, text) and puts it (:376-377), dropping any earlier entry: the last term clause wins.
  4. extractWeightedSpanTerms keeps. When an entry exists it only adds positions (:343-354): the first span or phrase clause that matches the text wins (one with no match returns before it touches the map, :336-338).
  5. PositionCheckingMap.put (:631-638) merges only the positionSensitive flag (javadoc :619-622: "the position insensitive one wins"), never the weight.
  6. QueryScorer.getTokenScore (QueryScorer.java:142-164) gives every occurrence that one weight; the fragment score adds it once per distinct term (:158-161, reset per fragment at :231-234); each token score goes into the TokenGroup that the Formatter receives (Highlighter.java:234, :215, :248).
  7. BooleanQuery compares SHOULD and MUST clauses as a multiset (BooleanQuery.java:126-141, "used for equals/hashCode"), so the two queries are equal().

Shapes

#

The same order dependence shows for a boosted exact term next to a SynonymQuery that contains it (weight 1 versus 5, different best fragments) and for two phrases that share a term (weight 5 versus 1; in the checked text only the fragment scores change, 10/6 versus 6/2, and the best fragment stays the same) in a scratch check, for an equal pair of DisjunctionMaxQuerys (an independent reproducer), and for classic QueryParser input alpha^5 beta^3 alpha versus alpha beta^3 alpha^5 (an intended-behaviour check).

Not claimed: "a boosted phrase loses its boost when its terms are also plain clauses" (alpha beta "alpha beta"^5). Both clause orders give the same result there, which fits the PositionCheckingMap javadoc; Elasticsearch described it as a plain-highlighter limitation in 2013 (elastic/elasticsearch#4351).

Exposure and likelihood189 words
  • Who. Users of the classic Highlighter with its standard QueryScorer (the default scorer since 2.9.0; no non-default setting) whose query names the same term of the highlighted field in two or more clauses with different boosts.
  • What changes. Which fragment is best, the order of getBestFragments, and the token score passed to the Formatter (for example GradientFormatter's colour intensity). The highlighted words are still the right ones; search hits and scores are untouched; nothing is thrown, with assertions on or off.
  • Scale. Any index size: the repro highlights two words.
  • Partly masked by rewriting. IndexSearcher.rewrite before highlighting merges duplicate TermQuery SHOULD clauses into (f:alpha)^6 and hides the pure term shape; the SynonymQuery shape still diverges after the rewrite.
  • Likelihood. Rare: for one application the clause order is fixed, so users see a plausible snippet that is not the highest-weighted one. No public report was found.
  • Not affected. QueryTermScorer, the UnifiedHighlighter, the FastVectorHighlighter on main, MemoryIndex search and IndexSearcher scores: in a bounded check of 336 clause orders only QueryScorer varied on main (on 10.6.0 and 9.12.3 the FastVectorHighlighter varied too: the defect #15434 fixed for 11.0).

Why it looks unintended

#
  • QueryScorer's own QueryScorer(WeightedSpanTerm[]) constructor: "if a term is defined more than once, always use the highest scoring weight"; QueryTermScorer does the same.
  • A 2005 commit fixed exactly this ("previously selected last weight in list") in the scorer that was QueryScorer until 2.9.0.
  • #15434 (merged 2026-01-05) fixed the same last-wins shape in the FastVectorHighlighter with Math.max.
The full argument193 words
  • The class states the rule. QueryScorer(WeightedSpanTerm[]) (QueryScorer.java:101-113): "if a term is defined more than once, always use the highest scoring weight" (:108-109); QueryTermScorer(WeightedTerm[]) has the same rule (QueryTermScorer.java:76-79).
  • It was fixed once before. Mark Harwood's commit c00b260ecf7 (2005-09-06): "the highest weight is used for scoring that term (previously selected last weight in list)". LUCENE-1685 (2009) made the span-aware scorer the default QueryScorer and renamed the old one QueryTermScorer; the span extractor never had the rule, so the default scorer went back to last-wins in 2.9.0 (2.4.1 passes, 2.9.0 fails).
  • Upstream fixed the twin. #15434 (lucene/CHANGES.txt:363, 11.0.0: "Don't override boost of conflicting expanded phrases by taking the max boost in markTerminal for FVHighlighter") made the FastVectorHighlighter use this.boost = Math.max(this.boost, boost) (vectorhighlight/FieldQuery.java:431).
  • Order dependence in this map was called a bug. LUCENE-1285 (#2362, 2008): with the same term in different query types "the results of term extraction are unpredictable and depend on the order of clauses"; its fix covered only the positionSensitive flag. This bug is the weight half.
  • No test pins last-wins, and the whole highlighter module passes with either fix.
The devil's-advocate check164 words

The strongest case for "intended", built by an intended-behaviour check and by an independent reviewer from another model family (OpenAI GPT-5.6): QueryScorer(Query) documents no rule for repeated terms; Query.equals is about matching, not about every consumer's output; one weight per term is an approximation anyway; the PositionCheckingMap javadoc could be read to cover weights; a maintainer called the classic Highlighter legacy on #15442; and rewriting the query first hides the simplest shape.

Why it fails: the rule is written in the same class, on its other input path, and the predecessor scorer was fixed to it in 2005. The best fragment is the highlighter's output for a query, so equal queries should get it. The PositionCheckingMap rule decides between a positional and a plain entry; two plain term clauses are both plain, so it does not decide between them. The maintainer who said "legacy" later approved and merged #15434 (2025-12-26 and 2026-01-05). Rewriting does not cover the SynonymQuery shape. Verdict: a real Low bug.

Suggested fix

#

Recommended A. Keep the highest weight among clauses of the same kind (recommended, validated)

Recommended: when the term already has an entry, keep the higher weight, for two term clauses and for two span or phrase clauses; a term clause still wins over a phrase, as today. About 10 lines in WeightedSpanTermExtractor; the repro and all 723 highlighter tests pass. Always taking the highest weight also works but gives bare words a phrase's boost.

// extractWeightedTerms (replaces lines 376-377)
WeightedSpanTerm existing = terms.get(queryTerm.text());
if (existing != null && existing.positionSensitive == false) {
  existing.setWeight(Math.max(existing.getWeight(), boost)); // several term clauses
} else {
  terms.put(queryTerm.text(), new WeightedSpanTerm(boost, queryTerm.text()));
}
// extractWeightedSpanTerms, when the entry already exists
if (weightedSpanTerm.positionSensitive) {
  weightedSpanTerm.setWeight(Math.max(weightedSpanTerm.getWeight(), boost)); // several spans
}
All options and trade-offs2 options · 519 words

Both options were applied in a scratch worktree at 5adff78bb168 and run through gradle (seed DEADBEEF, no nightly tests, not the full Lucene suite). A scratch check (not the repro) printed the weight of alpha and the fragment scores for both clause orders of four query shapes, on stock main and with each fix. Workaround today: QueryTermScorer uses the highest weight but ignores phrase positions; or deduplicate the clauses before highlighting (rewriting merges duplicate TermQuery clauses, not the SynonymQuery shape).

A. Keep the highest weight among clauses of the same kind (recommended, validated)

#

In WeightedSpanTermExtractor: extractWeightedTerms raises an existing plain (position-insensitive) entry to max(existing, boost) instead of replacing it; extractWeightedSpanTerms raises an existing span entry to max(existing, boost). A term clause still replaces a span entry, and a span clause still keeps a term entry's weight (the "position insensitive one wins" rule), as today in both orders.

// extractWeightedTerms (replaces lines 376-377)
WeightedSpanTerm existing = terms.get(queryTerm.text());
if (existing != null && existing.positionSensitive == false) {
  existing.setWeight(Math.max(existing.getWeight(), boost)); // several term clauses
} else {
  terms.put(queryTerm.text(), new WeightedSpanTerm(boost, queryTerm.text()));
}
// extractWeightedSpanTerms, when the entry already exists
if (weightedSpanTerm.positionSensitive) {
  weightedSpanTerm.setWeight(Math.max(weightedSpanTerm.getWeight(), boost)); // several spans
}

Trade-offs

By reading the code the result no longer depends on clause order for term, span and mixed clauses (executed on four shapes). A weight changes only where two clauses of the same kind give the term different boosts, which are exactly the cases where today's weight depends on clause order. A boosted phrase still cannot raise the weight of a term that is also a plain clause (the unclaimed, order-independent limitation).

What the checks validated

The repro fails before and passes after, assertions on and off; :lucene:highlighter:test: 723 tests, 0 failures (the repro included); :lucene:highlighter:checkGoogleJavaFormat passes. Scratch check: equal weights for both orders in the term, synonym and two-phrase shapes (alpha 5 in each), and the terms + boosted phrase shape unchanged from stock main.

B. Always keep the highest weight (validated)

#

extractWeightedTerms raises any existing entry to max(existing, boost) and marks it position-insensitive (a plain term matches anywhere); extractWeightedSpanTerms raises any existing entry to max(existing, boost). This is the fix proposed during verification and the same highest-weight rule as QueryScorer(WeightedSpanTerm[]), QueryTermScorer and #15434; unlike the array constructor it also marks a merged entry position-insensitive.

Trade-offs

It also changes a common shape that is order-independent today: plain terms plus a boosted phrase of the same terms. With one weight per term, every bare occurrence of a phrase term then gets the phrase's boost. In the scratch check, for alpha beta gamma^3 "alpha beta"^5 on "alpha beta xx gamma yy alpha", the best fragment moves from xx <B>gamma</B> yy (3) to the phrase match <B>alpha</B> <B>beta</B> (10), but the lone <B>alpha</B> at the end now scores 5 instead of 1, above the gamma fragment. A reviewer may object to that change for every phrase-boost user; it is what QueryTermScorer already does.

What the checks validated

The same runs as A, all pass: the repro (assertions on and off), 723 module tests with 0 failures, the formatter check.

Downstream note

#

A product that builds snippets from user queries with this highlighter may show a different, still correctly marked snippet for equal queries; nothing else.

How it was found

#

Semi-formal: after the FastVectorHighlighter fix #15434 (keep the highest boost of a repeated phrase), the classic Highlighter's weight extraction was read for the same pattern. A bounded metamorphic check then highlighted 336 clause orders of equal queries, with QueryTermScorer and the FastVectorHighlighter as references: on main only QueryScorer's snippet changed.

The method in full95 words

The relation checked: if q1.equals(q2), Highlighter.getBestFragment with QueryScorer gives the same fragment. The generator permuted the clauses of BooleanQuery (SHOULD) and DisjunctionMaxQuery objects built from 6 base clause lists, 336 permutations in all, and compared 17 outputs per permutation (consumers times documents: the classic Highlighter with QueryScorer and with QueryTermScorer, the FastVectorHighlighter, the UnifiedHighlighter, MemoryIndex search and IndexSearcher scores). On main only QueryScorer varied; on 10.6.0 and 9.12.3 the FastVectorHighlighter varied too (the #15434 defect), which shows the check can see such a change. The witness was then reduced to one JUnit test.

Registry title

Impact note

Summary
You highlight a text with the classic Highlighter and QueryScorer using two BooleanQuery objects that are equal() and differ only in clause order: (f:alpha)^5 (f:beta)^3 f:alpha and f:alpha (f:beta)^3 (f:alpha)^5. You expect the same best fragment for both, the one with alpha, because alpha's highest weight 5 beats beta's 3 (the rule that QueryScorer's own WeightedSpanTerm[] constructor, QueryTermScorer and, since #15434, the FastVectorHighlighter follow). Instead WeightedSpanTermExtractor keeps the weight of the term clause it visits last (and of the first span or phrase clause), so alpha gets weight 1 for the first query and its best fragment is the one with beta (' <B>beta</B>' for the repro's text 'alpha beta'), with no error.
