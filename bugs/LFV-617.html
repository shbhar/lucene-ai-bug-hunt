Upgrading an index with a single old segment drops the soft-deleted documents SoftDeletesRetentionMergePolicy keeps

Upgrade a soft-deletes index with IndexUpgrader and a SoftDeletesRetentionMergePolicy around the default TieredMergePolicy that keeps every soft-deleted document, and a lone old segment of 13 documents (3 of them soft-deleted) comes out with 10, with no error. Releases 7.4.0 to 10.5.2 and main are affected.

The bug in 30 seconds

#

SoftDeletesRetentionMergePolicy keeps soft-deleted documents through merges, for example as change history. IndexUpgrader rewrites old segments in the current format by wrapping your merge policy in UpgradeIndexMergePolicy and calling forceMerge(1). Together they should rewrite every old segment and keep every retained document.

  1. Your config keeps soft-deleted documents: setSoftDeletesField("soft") and new SoftDeletesRetentionMergePolicy("soft", MatchAllDocsQuery::new, new TieredMergePolicy()). An index written by 10.5.2 has one segment with 13 documents: 10 visible and 3 soft-deleted, which the policy keeps.
  2. Upgrade it on main with new IndexUpgrader(dir, config, false).upgrade(). You expect the segment rewritten in the current format with all 13 documents, which is what happens when the same index has two old segments.
  3. IndexUpgrader wraps your policy in UpgradeIndexMergePolicy, which first asks your policy to merge the old segment. TieredMergePolicy sees one segment with no hard deletes and answers "already merged".
  4. So UpgradeIndexMergePolicy rewrites the segment with a plain merge of its own. The retention policy only decorates merges it returns itself, so it never sees this one, and the merge copies only the 10 live documents.
  5. You get 10 documents: the 3 retained ones are gone from the index (the upgrade keeps only its new commit), with no error. Searches that hide soft-deleted documents still return the same 10.

Who is affected

#

Applications that keep soft-deleted documents with SoftDeletesRetentionMergePolicy and upgrade with IndexUpgrader(dir, config, ...), or with UpgradeIndexMergePolicy around the retention policy. With the default TieredMergePolicy as the delegate, every lone old segment without hard deletes is hit (7.5.0 and later), such as a force-merged index. The retained documents are lost from the index; the visible documents do not change.

Mechanism, terms and numbers888 words

SoftDeletesRetentionMergePolicy "allows to carry over soft deleted documents across merges"; applications use it to keep recently deleted or updated documents, for example as change history. Upgrading such an index with new IndexUpgrader(dir, config, false).upgrade(), or with UpgradeIndexMergePolicy wrapped around the retention policy as that class's javadoc recipe shows, drops every soft-deleted document of an old segment that the delegate merge policy declines to merge. With TieredMergePolicy as the delegate (the default, and the one in the example), that is always so on 7.5.0 and later for a lone old segment without hard deletes, the usual shape of a force-merged index. An index written by 10.5.2 with 13 documents (10 visible, 3 soft-deleted and retained by a match-all query) comes out with 10; with two old segments it keeps all 13. There is no error, and the upgrade keeps only its new commit, so only a backup made before the upgrade still has them; the visible documents, as seen by readers that apply soft deletes, do not change. Cause: UpgradeIndexMergePolicy.findForcedMerges rewrites the old segments its delegate did not select with its own new OneMerge(newInfos), and OneMergeWrappingMergePolicy, the base class of the retention policy, only wraps merges it returns itself. Data loss since 7.4.0, when soft deletes arrived; the leftover merge itself dates from 2011.

Terms

#
  • Soft deletes: with IndexWriterConfig.setSoftDeletesField("soft"), softUpdateDocument, or updateDocValues on the soft-deletes field, hides a document by giving it a doc value in that field instead of marking it deleted. Readers obtained from the IndexWriter, and SoftDeletesDirectoryReaderWrapper, skip it (a plain DirectoryReader does not); a merge drops it unless the merge policy keeps it.
  • SoftDeletesRetentionMergePolicy: a OneMergeWrappingMergePolicy that wraps each merge so that soft-deleted documents matching a retention query stay in the merged segment (SoftDeletesRetentionMergePolicy.java:36-46).
  • OneMergeWrappingMergePolicy: "A wrapping merge policy that wraps the OneMerge objects returned by the wrapped merge policy" (OneMergeWrappingMergePolicy.java:23-25). Its four segment-based merge-selection methods return wrapSpec(in.find*Merges(...)) (:44-83); findMerges(CodecReader...), the addIndexes path, is inherited from FilterMergePolicy unwrapped, a separate gap not claimed here.
  • UpgradeIndexMergePolicy and IndexUpgrader: the upgrade policy turns forceMerge into "rewrite every segment written by another version"; IndexUpgrader.upgrade() installs it around the configured policy (IndexUpgrader.java:180), keeps only the last commit (:181), runs forceMerge(1) (:196) and commits (:204).

The bug

#
  1. The delegate is asked first. UpgradeIndexMergePolicy.findForcedMerges collects the old segments (UpgradeIndexMergePolicy.java:86-93) and asks its delegate, here the retention policy around TieredMergePolicy, to merge them (:101-102).
  2. The delegate (TieredMergePolicy) declines a lone old segment without hard deletes. On the writer the upgrade has just opened, the segment is not pooled yet, so IndexWriter.numDeletesToMerge returns only hard deletes ("this is safe!", IndexWriter.java:6449-6455); TieredMergePolicy sees one segment with no deletes and returns nothing (logging "already merged" only with an InfoStream, TieredMergePolicy.java:835-847). With a retain-all query it would decline even with exact counting, so this estimate is not the defect; for a query that keeps only some soft-deleted documents it is a second ingredient, since exact counting would leave reclaimable deletes and TieredMergePolicy would merge (and the wrapper wrap) the segment itself (code reading).
  3. The upgrade policy merges the leftovers itself. It logs "does not want to merge all old segments, merge remaining ones into new segment" (:117-125, only with an InfoStream) and adds spec.add(new OneMerge(newInfos)) (:136), a plain merge created outside the delegate. Its other methods still delegate; only the wrapForMerge decoration of this merge is bypassed.
  4. The retention wrapper never sees it. Only merges returned through wrapSpec are wrapped. IndexWriter.mergeMiddle calls merge.wrapForMerge(reader); the plain merge returns the reader unchanged, and soft-deleted documents are kept only for a wrapped reader (IndexWriter.java:5497-5501). The new segment holds the live documents only.

With two old segments, TieredMergePolicy merges them itself, that merge comes back through wrapSpec, and every retained document survives. A probe logged the delegate's view (numDeletesToMerge=0 delCount=0 softDel=3), the plain MergePolicy$OneMerge returned for the segment, and maxDoc=10 soft=0 after the upgrade.

Exposure and likelihood309 words
  • Who. Applications that keep soft-deleted documents with SoftDeletesRetentionMergePolicy (opt-in; for example change history for replication or recovery, or recent versions for a time window) and upgrade the index format with IndexUpgrader(dir, config, deletePriorCommits), or with UpgradeIndexMergePolicy around the retention policy and forceMerge. Main's MIGRATE.md (11.0) suggests UpgradeIndexMergePolicy to "upgrade segment formats immediately". For a soft-deletes index the config constructor is the only way to run IndexUpgrader: the default constructors and the command line cannot open it.
  • Trigger. Deterministic once an old segment has no hard deletes and the delegate does not select it. With TieredMergePolicy as the delegate (the default) that is always so on 7.5.0 and later for a lone old segment (a force-merged or small one-segment index), and for a partially upgraded index that holds one such segment; on 7.4.0 only for a non-compound-file one. With a LogMergePolicy delegate only a lone compound-file old segment is declined. Any retention query that matches at least one soft-deleted document can be affected, not only match-all; for partial retention the fresh writer's hard-deletes-only estimate is part of the trigger. No scale, concurrency or special data.
  • Effect. Silent loss of the documents the retention policy exists to keep, permanent for the index: the upgrade keeps only its new commit, so the previous commit is deleted; only a backup or copy made before the upgrade still has them. The visible documents (through readers that apply soft deletes) and the hard deletes are unchanged and the index is consistent; no deleted document comes back. Anything that later reads the retained history, including a plain DirectoryReader search, which does not apply soft deletes, finds it missing.
  • How rare. A judgement, not measured: the combination is uncommon, IndexUpgrader is optional, no Lucene test combines these classes, and Elasticsearch and OpenSearch (default branches, code reading) do not call Lucene's IndexUpgrader or UpgradeIndexMergePolicy.

Why it is a bug, not intended

#
  • IndexUpgrader puts the upgrade policy around yours while saying it upgrades "using the given config"; for a soft-deletes index that is the only way to run it.
  • Same tool, config and documents: two old segments keep 13 documents, one keeps 10.
  • The leftover merge predates merge wrapping and soft deletes; no test combines them.
The full argument288 words

No javadoc sentence literally promises that an upgrade keeps retained soft deletes; the case rests on consistency.

  • Contracts. SoftDeletesRetentionMergePolicy: "allows to carry over soft deleted documents across merges ... allows to control when soft deletes are claimed by merges" (SoftDeletesRetentionMergePolicy.java:37-42). UpgradeIndexMergePolicy: "All other methods delegate to the base MergePolicy given to the constructor", "forceMerge does no longer really merge; it is just used to 'forceMerge' older segment versions away", and its recipe iwc.setMergePolicy(new UpgradeIndexMergePolicy(iwc.getMergePolicy())) puts the configured policy inside (UpgradeIndexMergePolicy.java:27-31, :36-42). IndexUpgrader(Directory, IndexWriterConfig, boolean) upgrades "using an IndexWriter using the given config" (IndexUpgrader.java:154-158) and its class javadoc expects a user policy ("The MergePolicy set by IndexWriterConfig may also reorder documents", :51-52). IndexUpgrader is not @lucene.experimental.
  • The inconsistency. With the same tool, config and documents, two old segments keep 13 and one keeps 10; a lone segment with one hard delete keeps all its soft-deleted documents and one without loses them. With a LogMergePolicy delegate the outcome also depends on whether the lone old segment is a compound file.
  • History. The leftover merge is from LUCENE-3082 (2011, trunk 600a50bb2ae; 3.2 via 535d974518b), six years before OneMergeWrappingMergePolicy (LUCENE-7688, 2017, master 6f9acb51549; 6.5.0 via 180614c1491) and seven before soft deletes (LUCENE-8233, 2018, 7.4.0); none of LUCENE-8233's 15 comments mentions upgrading. No evidence was found that this interaction was considered or later addressed.
  • Tests. No upstream test combines IndexUpgrader or UpgradeIndexMergePolicy with SoftDeletesRetentionMergePolicy; TestUpgradeIndexMergePolicy runs the generic merge-policy tests over a plain TieredMergePolicy.
  • Upstream remark. On LUCENE-8264 (#9311) a committer (@s1monw) pointed to UpgradeIndexMergePolicy for upgrades and to OneMergeWrappingMergePolicy "similar to what we do in the soft delete case in SoftDeletesRetentionMergePolicy", presenting them as composable.
The devil's-advocate check253 words

The intended-behaviour verifier built the strongest case for "not a bug": OneMergeWrappingMergePolicy only promises to wrap the merges its delegate returns, so the leftover merge was never in scope; IndexWriterConfig.setSoftDeletesField says documents are retained "if the merge policy modifies the live docs of a merge reader" (IndexWriterConfig.java:551-552), and the writer's top policy, UpgradeIndexMergePolicy, does not; a direct user can put the retention policy outermost, which works; @mikemccand wrote on #8574 that the upgrade policy "was really designed for one-off usage via the IndexUpgrader tool"; the merge-policy classes involved are @lucene.experimental; and only invisible documents are lost.

Why it fails: IndexUpgrader forces the losing nesting itself while saying it uses the given config, and its default constructor and command line cannot open a soft-deletes index, so the tool offers no safe way; the UpgradeIndexMergePolicy recipe nests the same way; the IndexWriterConfig sentence refers to the policy the user configured, not one the tool put around it; "one-off usage via the IndexUpgrader tool" is exactly this case; and @lucene.experimental permits API changes, not silently dropping documents a configured policy keeps. The verifier, the independent reproducer and cross-model reviews rated the case moderate. The cross-model fact check found this rebuttal mostly fair but noted that "using the given config" and "All other methods delegate" carry limited contractual weight (IndexUpgrader already replaces the merge and deletion policies); the strongest argument is the behavioural inconsistency. Verdict: a defect, best filed as an inconsistency; a maintainer may still call it a composition gap.

Suggested fix

#

Recommended B: a MergePolicy.wrapMerge(OneMerge) hook for merges created by a wrapping policy

Let the delegate decorate UpgradeIndexMergePolicy's own merge too: a small MergePolicy.wrapMerge(OneMerge) hook, implemented by OneMergeWrappingMergePolicy and called for the leftover merge (+22/-1, four files). The three repros pass, and so do 450 tests (76 skipped) in 17 classes: the repros and the 14 closest upstream classes. A variant without an API change passes the same tests.

// MergePolicy: by default a policy does not decorate merges created around it
public OneMerge wrapMerge(OneMerge merge) { return merge; }
// FilterMergePolicy
@Override public OneMerge wrapMerge(OneMerge merge) { return in.wrapMerge(merge); }
// OneMergeWrappingMergePolicy (and so SoftDeletesRetentionMergePolicy)
@Override public OneMerge wrapMerge(OneMerge merge) { return wrapOneMerge.apply(in.wrapMerge(merge)); }
// UpgradeIndexMergePolicy.findForcedMerges, the leftover merge
spec.add(in.wrapMerge(new OneMerge(newInfos)));   // was: spec.add(new OneMerge(newInfos))

B: a MergePolicy.wrapMerge(OneMerge) hook for merges created by a wrapping policy (validated by the checks) (recommended)

#

MergePolicy.wrapMerge returns the merge unchanged by default ("decorates a merge that a policy wrapping this one created itself"); FilterMergePolicy delegates it; OneMergeWrappingMergePolicy applies its operator after its delegate's; UpgradeIndexMergePolicy passes its leftover merge through it. Patch: optionB-mergepolicy-wrapmerge-hook.diff, +22/-1 in four files.

// MergePolicy: by default a policy does not decorate merges created around it
public OneMerge wrapMerge(OneMerge merge) { return merge; }
// FilterMergePolicy
@Override public OneMerge wrapMerge(OneMerge merge) { return in.wrapMerge(merge); }
// OneMergeWrappingMergePolicy (and so SoftDeletesRetentionMergePolicy)
@Override public OneMerge wrapMerge(OneMerge merge) { return wrapOneMerge.apply(in.wrapMerge(merge)); }
// UpgradeIndexMergePolicy.findForcedMerges, the leftover merge
spec.add(in.wrapMerge(new OneMerge(newInfos)));   // was: spec.add(new OneMerge(newInfos))

Trade-offs

  • A new public expert method on the @lucene.experimental MergePolicy; any decorating policy can opt in. BPReorderingMergePolicy (misc) would need its own override, not written here, to reorder this merge.
  • MergePolicy is widely subclassed: experimental status lowers compatibility expectations, but a clash with an existing downstream method of the same name, and the order in which mixed custom decorators apply, deserve review; the 450 tests cover no outside policies.
  • No CHANGES entry, javadoc build or full check was run; no performance effect expected (one call per upgrade merge).

A: wrap the leftover merge like the delegate chain would (no API change) (validated by the checks)

#

UpgradeIndexMergePolicy walks its FilterMergePolicy chain and applies each OneMergeWrappingMergePolicy's operator to its own merge, innermost first, as wrapSpec does for returned merges; OneMergeWrappingMergePolicy gets a package-private wrapOneMerge(OneMerge). Patch: optionA-wrap-leftover-merge-like-delegate.diff, the finder's sketch, +24/-1 in two files.

private OneMerge wrapLikeDelegate(OneMerge merge) {
  ArrayDeque<OneMergeWrappingMergePolicy> wrappers = new ArrayDeque<>();
  for (MergePolicy p = in; p instanceof FilterMergePolicy f; p = f.in) {
    if (p instanceof OneMergeWrappingMergePolicy w) wrappers.push(w);
  }
  while (wrappers.isEmpty() == false) merge = wrappers.pop().wrapOneMerge(merge);
  return merge;
}
// findForcedMerges: spec.add(wrapLikeDelegate(new OneMerge(newInfos)));

Trade-offs

  • No public API change, but it only reaches OneMergeWrappingMergePolicy subclasses through FilterMergePolicy.in; another decorator in the chain, such as BPReorderingMergePolicy, stays bypassed (by reading only). It reaches into another class's operator, which a maintainer may find too clever.

What the checks validated

  • The three repro classes 11 of 11 pass (assertions on); the same 17 classes, 450 tests, 76 skipped, 0 failures. Earlier the finder's build passed its 2 tests and 19 upstream merge-policy tests, and the independent reproducer's and the adjudication's runs passed 6 of 6 and 2 of 2 with it.

Workaround: retention policy outermost, without IndexUpgrader (validated by the checks)

#

Open an IndexWriter with new SoftDeletesRetentionMergePolicy(field, query, new UpgradeIndexMergePolicy(new TieredMergePolicy())), run forceMerge(1) and commit (IndexUpgrader also sets KeepOnlyLastCommitDeletionPolicy, which is already the default deletion policy; set it only if your config uses another one). The retention wrapper then also wraps the upgrade policy's own merge.

Trade-offs

  • Users must know about it; IndexUpgrader itself cannot be configured this way.

What the checks validated

  • testRetentionPolicyOutermost and the independent reproducer's and devil's advocate's controls keep all 13 documents (and 12 or 11 under partial retention).

C: document the limitation

#

Warn in IndexUpgrader and UpgradeIndexMergePolicy that decorating delegates do not see the leftover merge and that a retention policy must be outermost.

Trade-offs

  • Cheapest, but IndexUpgrader still cannot upgrade such an index safely. Not a fix either: counting soft deletes for unpooled segments in numDeletesToMerge, since with a retain-all query TieredMergePolicy would still decline the segment.

Downstream note

#

Elasticsearch and OpenSearch, the large soft-deletes users, do not call Lucene's IndexUpgrader or UpgradeIndexMergePolicy (default branches, code reading), but Elasticsearch 7.17 and OpenSearch main have their own upgrade merge policies that add a merge of their own around a nested retention policy in a similar way (code reading, nothing run).

How it was found

#

Code reading, not a formal method. While modelling which index tools may change which documents for a round-trip test of the index tools, the finder read UpgradeIndexMergePolicy.findForcedMerges and saw that it merges leftovers itself. A public-API JUnit on indexes written by released 10.5.2 and 9.12.3 confirmed it; the randomized round-trip test never could, as it builds no old segments.

The method in full161 words

Method: code reading (non-formal tier), in a hunt unit that compares Lucene's index tools by round-tripping indexes through them (a randomized differential test).

  • While modelling the IndexUpgrader leg (which tools may change which documents), the finder read UpgradeIndexMergePolicy.findForcedMerges and noticed that the merge it creates for old segments its delegate declines is a plain OneMerge, which a wrapping delegate never sees.
  • It wrote fixture indexes with the released 10.5.2 and 9.12.3 jars (13 documents, 3 soft-deleted, one or two segments) and a public-API JUnit around new IndexUpgrader(dir, config, false): one segment loses the 3 retained documents, two keep them. A shadow build with the fix sketch passed.
  • The randomized differential itself did not find it: it builds no old-version segments and no retention policies.
  • Found 2026-10-26 on main a9779ef3c193; then checked by an independent reproducer, a devil's-advocate verifier, reviews by a model from another family (reading only), an adjudication, a follow-up (history, prior reports, security) and an audit.

History

#

Data loss since 7.4.0 (LUCENE-8233, 2018, which added soft deletes and the retention policy); the leftover merge itself is from 2011 (LUCENE-3082). Executed on releases from 7.4.0 to 10.5.2 and on main: one old segment loses the documents, two keep them. Never fixed.

Versions tested7 rows

Data loss introduced by LUCENE-8233 "Add support for soft deletes to IndexWriter" (@s1monw, 2018-04-04; branch_7x 02fa5a0b059, master ecc17f90233; a JIRA patch, migrated as #9280), which added SoftDeletesRetentionMergePolicy as a OneMergeWrappingMergePolicy whose wrapper is the only thing that keeps retained documents through a merge. The defective line is older: spec.add(new OneMerge(newInfos)) comes from LUCENE-3082 (trunk 600a50bb2ae, 2011; 3.2 via 535d974518b), and it has bypassed OneMergeWrappingMergePolicy since that class appeared (LUCENE-7688, master 6f9acb51549; 6.5.0 via 180614c1491) without losing data before soft deletes. LUCENE-7976 (2018-06-15, 9c4e315c1cb / 2519025fdaf, 7.5.0) widened the trigger: before it, TieredMergePolicy merged a lone compound-file old segment itself.

The first ordinary major upgrade, 7.7.3 to 8.0.0, loses the documents. 7.4.0 is affected, but its ordinary trigger is unusual (an index written before 7.4 that started soft-deleting under 7.4, with a non-compound-file old segment); the first routine upgrade of an index that already had soft deletes is 7.4.0 to 7.5.0. Releases between the executed ones share the unchanged code path (read). No commit on main or branch_10x changes it; the unreleased branch_10_6 and branch_10x heads have the same code (read, not run).

Bug record

LFV-617, snapshot of 2026-10-30

Registry title
UpgradeIndexMergePolicy rewrites the old segments its delegate declines with its own plain OneMerge, which a wrapping delegate never sees, so IndexUpgrader (or UpgradeIndexMergePolicy) with a SoftDeletesRetentionMergePolicy inside silently purges the soft-deleted documents the retention policy must keep
Area
core index / UpgradeIndexMergePolicy and IndexUpgrader with OneMergeWrappingMergePolicy delegates (SoftDeletesRetentionMergePolicy)
Priority
Low, rank 276: Needs the unusual composition of soft-deletes retention with IndexUpgrader or UpgradeIndexMergePolicy, which the large soft-deletes users do not call.
Impact class
silent wrong results
Impact note
Applications that keep soft-deleted documents with SoftDeletesRetentionMergePolicy (for example as change history for replication or recovery) and upgrade the index format with new IndexUpgrader(dir, config, deletePriorCommits), or with UpgradeIndexMergePolicy wrapped around the retention policy as its javadoc recipe shows, lose every retained soft-deleted document of an old segment that the delegate declines to merge; with TieredMergePolicy as the delegate (the default) that is always the case on 7.5.0 and later for a lone old segment without hard deletes (the usual shape of a force-merged index) and also for a partially upgraded index that holds one such old segment (a LogMergePolicy delegate declines only a lone compound-file old segment, fact-check probe); the loss is permanent for the index (the upgrade keeps only its new commit) and silent, the visible documents (through readers that apply soft deletes) stay the same, it needs the opt-in soft-deletes retention plus the upgrade tool's config constructor (the command-line form cannot open a soft-deletes index at all), and no scale is needed.
Summary
You configure soft deletes with SoftDeletesRetentionMergePolicy("soft", MatchAllDocsQuery::new, new TieredMergePolicy()), which must keep every soft-deleted document, and upgrade a one-segment index written by Lucene 10.5.2 (10 visible plus 3 soft-deleted documents) with new IndexUpgrader(dir, thatConfig, false).upgrade(). You expect the segment to be rewritten in the current format with all 13 documents, exactly as happens when the same index has two old segments. Instead TieredMergePolicy treats the lone segment as already merged, UpgradeIndexMergePolicy rewrites it with its own 'merge remaining ones into new segment' OneMerge that the retention policy never wraps, and the 3 retained documents are purged with no error (maxDoc 13 -> 10; partial retention queries lose their documents the same way).
Introduced
02fa5a0b0593 (branch_7x; master ecc17f902330), LUCENE-8233 'Add support for soft deletes to IndexWriter' (JIRA patch, no GitHub PR; migrated issue apache/lucene#9280). It added SoftDeletesRetentionMergePolicy as a OneMergeWrappingMergePolicy whose OneMerge wrapper (wrapForMerge -> applyRetentionQuery) is the only thing that keeps retained soft-deleted documents through a merge, and nothing routes UpgradeIndexMergePolicy's own merge through it [read: git log, git blame and git log -S in the history clone; exec: 7.3.1 lacks the API (compile error), 7.4.0 loses the documents]. The defective line spec.add(new OneMerge(newInfos)) (UpgradeIndexMergePolicy.java:136) is older: LUCENE-3082 (600a50bb2ae8, 2011-05-09, first release 3.2). It has bypassed OneMergeWrappingMergePolicy wrapping since that class appeared (LUCENE-7688, 6.5.0) but lost no data before soft deletes [exec on 6.5.0 and 7.3.1 with a merge-counting wrapper]. LUCENE-7976 (branch_7x 9c4e315c1cb3, master 2519025fdafe, 7.5.0) widened the trigger from a lone non-compound-file old segment to any lone old segment without deletes [exec]. (2018-04-04 (LUCENE-8233 committed to branch_7x and master); the defective line 2011-05-09 (LUCENE-3082); trigger widened 2018-06-15 (LUCENE-7976))
First affected version
7.4.0 [exec, -ea and -da], the first release with soft deletes and SoftDeletesRetentionMergePolicy. On 7.4.0 the lone old segment must not be a compound file (a lone compound-file old segment is merged by TieredMergePolicy itself, wrapped, and kept [exec]), and the only IndexUpgrader trigger is an index written by an older release that started soft-deleting under 7.4.0 [exec]. 7.5.0 is the first release in which an ordinary upgrade of a soft-deletes index (written by 7.4.0) loses the documents, compound file or not [exec]. 7.3.1 and earlier: the API is absent [exec: compile error].
Affected versions
Every release from 7.4.0 to 10.5.2, and main a9779ef3c193; never fixed. Executed (retain-all policy, one old segment without hard deletes, 13 -> 10 documents) on 7.4.0 (-ea and -da), 7.5.0, 7.7.3, 8.0.0, 8.11.4, 9.0.0, 9.12.3, 10.0.0, 10.5.2 (-ea and -da) and main (-ea and -da) with official release jars and JDK 25 [exec]; the two-old-segment control keeps all 13 documents on 7.4.0, 7.5.0, 8.0.0, 9.0.0, 9.12.3, 10.0.0, 10.5.2 and main [exec]; the releases in between share the unchanged code path [read]. The unreleased branch_10_6 and branch_10x heads have the same code [read, not executed]. The 7 commits on main since the hunt's previous base do not touch any of the files involved. Not affected: 7.3.1 and earlier (no soft deletes) [exec].
