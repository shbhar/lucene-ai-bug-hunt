SoraniNormalizer keeps invisible format characters from outside the BMP, so a Sorani word with one no longer matches

SoraniAnalyzer deletes invisible formatting characters such as the right-to-left mark, but checks one 16-bit Java char at a time, so the 127 format characters stored as two chars, such as U+E0001, stay in the word: کوردستان with U+E0001 inside no longer matches the plain word. Since 4.7.0.

The bug in 30 seconds

#

SoraniNormalizer deletes a char when Character.getType(s[i]) == Character.FORMAT (SoraniNormalizer.java:121). A format character outside the BMP is two chars, a surrogate pair, and each half alone has type SURROGATE, so nothing is deleted. The test is the whole Cf category, and every BMP format character, directional or not, is removed.

  1. You index کوردستان ("Kurdistan") three times with the default SoraniAnalyzer, each copy with one invisible format character: the right-to-left mark U+200F inside the word, the language tag U+E0001 at the same spot, and U+E0001 at the end.
  2. You search for the plain word through the same analyzer. You expect 3 hits: the normalizer's javadoc says formatting characters are removed, and it does remove the right-to-left mark.
  3. You get 1 hit. Java stores U+E0001 as two chars, U+DB40 U+DC01. The normalizer asks Character.getType about each char alone, which answers SURROGATE, never FORMAT, so neither is deleted and the indexed term keeps the character; at the end of the word it also blocks stemming.
  4. All 43 format characters inside the BMP are removed, all 127 outside it are kept, and nothing throws with these inputs. Emoji flags, the best-known source of such characters, are tokenized on their own, so it takes stray or constructed input.

Who is affected

#

Fields analysed with the stock SoraniAnalyzer, SoraniNormalizationFilter or the soraniNormalization factory, at index and query time. It needs an invisible format character from outside the BMP glued to a Sorani word; emoji flags are tokenized on their own, so in practice only stray or constructed input hits it. Then it happens every time, with no error.

Mechanism, terms and numbers558 words

SoraniAnalyzer, SoraniNormalizationFilter and the soraniNormalization factory delete invisible formatting characters (Unicode general category Cf), as SoraniNormalizer's javadoc says: "Harakat, tatweel, and formatting characters such as directional controls are removed." The test reads one UTF-16 char at a time, Character.getType(s[i]) == Character.FORMAT (SoraniNormalizer.java:121). A format character outside the Basic Multilingual Plane (BMP), such as U+E0001 LANGUAGE TAG or a tag character U+E0020..U+E007F, is stored as a surrogate pair, and each half has type SURROGATE, so it is never deleted: all 43 BMP Cf code points are removed and all 127 supplementary ones (JDK 25) are kept. With the default SoraniAnalyzer, the word کوردستان with U+E0001 inside or at the end is not found by the plain word (1 of 3 documents found; the right-to-left-mark spelling is), and a trailing such character also blocks stemming. With these inputs nothing throws. Sorani letters and marks are all BMP characters, and emoji flags are tokenized separately, so only stray or constructed input hits it. The code is as old as the analyzer (4.7.0, 2014); testing the code point and deleting its chars fixes it.

Terms

#
  • UTF-16 char: Java stores text as 16-bit char values. Every Sorani letter and mark fits in one char: they are in the Basic Multilingual Plane (BMP).
  • Supplementary character: a code point above U+FFFF, stored as two chars, a surrogate pair. U+E0001 LANGUAGE TAG is the pair U+DB40 U+DC01. A surrogate alone is not a character; its general category is SURROGATE.
  • Format character (Cf): an invisible character that affects layout or processing, such as the right-to-left mark U+200F, the soft hyphen U+00AD or the tag characters U+E0020..U+E007F. Character.getType(int) returns FORMAT for them; the char overload cannot, and its javadoc says it "cannot handle supplementary characters".

The bug

#
  1. SoraniNormalizer.normalize walks the term one char at a time and switches on the char: explicit cases fold letters and delete harakat, tatweel and ZWNJ (SoraniNormalizer.java:72-119).
  2. Every other char reaches the default branch: if (Character.getType(s[i]) == Character.FORMAT) { len = delete(s, i, len); i--; } (:120-124).
  3. For U+E0001 the two halves U+DB40 and U+DC01 arrive one by one; getType returns SURROGATE (19) for each, not FORMAT (16), so neither is deleted and the character stays in the term.
  4. SoraniNormalizationFilter "applies {@link SoraniNormalizer}" (SoraniNormalizationFilter.java:24). SoraniAnalyzer runs it right after StandardTokenizer, which keeps U+E0001 and U+E0067 inside the word token (word-break rule WB4), and again in normalize (SoraniAnalyzer.java:113-130).

Exposure and likelihood322 words
  • Who is exposed. The stock SoraniAnalyzer with any constructor (indexing and normalize), any chain with SoraniNormalizationFilter, and the soraniNormalization factory (SoraniNormalizationFilterFactory.java:40; its normalize is the same filter, :60-63).
  • What it takes. One of the 127 supplementary format characters inside or at the end of a word in a Sorani-analysed field. Sorani letters and marks are all BMP characters, so Sorani text has no need of them. The best-known real source, emoji subdivision flags (a black flag followed by tag characters), does not reach a Sorani word: StandardTokenizer emits the flag as its own <EMOJI> token, with or without a space, and the word token stays clean and is stemmed. So it takes a bare stray tag character, a deprecated language tag or another exotic format control glued to a word: garbled or deliberately constructed input.
  • What changes for the user. The word with the character and the plain word become different terms, so a search for the plain word misses the document (1 of 3 found in the repro); a trailing such character also blocks stemming. Analyzer.normalize keeps the character too, so wildcard, prefix and fuzzy terms built from such text keep it (read from the query parser; not run end to end).
  • What does not happen. With the inputs run, no exception; the surrogate pair stays intact, so the term is valid UTF-16; other tokens, fields and documents are unaffected; the run time stays small (about 1,200,000 chars of such words in 67-137 ms; one input size, no scaling measured).
  • Scale. Deterministic, with assertions on or off, at any index size.
  • JDK dependence. The affected set follows the JDK's Unicode tables (127 with JDK 25); U+E0001 and the tag characters have been Cf since Unicode 3.1, so every JDK Lucene supports shows it. Only JDK 25 was run.
  • How likely. Contrived for accidental hits; the documented searches found no report in the 12 years since 4.7.0.

Why it is a bug, not intended

#
  • The javadoc says formatting characters "such as directional controls" are removed; the code tests the whole Cf category and removes all 43 BMP ones.
  • The public filter "applies {@link SoraniNormalizer}", public through 9.12.3; upstream's vocabulary test needs this branch for U+202E.
  • The JDK says getType(char) cannot handle supplementary characters; LUCENE-6914 fixed the same mistake in DecimalDigitFilter, in this chain.
The full argument295 words
  • Contract. "Harakat, tatweel, and formatting characters such as directional controls are removed." (SoraniNormalizer.java:33, unchanged since 4.7.0). Directional controls are an example; the code's criterion is Character.FORMAT, and every BMP Cf character is removed (ZWNJ by its own case, the other 42 by this branch), including the soft hyphen, ZWJ, the BOM and U+0600..U+0605. Only the UTF-16 encoding decides which Cf characters survive.
  • The contract is public. SoraniNormalizationFilter: "A {@link TokenFilter} that applies {@link SoraniNormalizer} to normalize the orthography." SoraniNormalizer was a public class from 4.7.0 through 9.12.3, and Lucene's javadoc builds document protected members (-protected; javadoc.access=protected in the 4.x ant build), so the release javadoc builds included the sentence (build settings read, not the published pages); 10.0.0 made the class package-private (LUCENE-10561), changing only modifiers.
  • Nothing presents it as a choice. The only upstream test that reaches the FORMAT branch is TestSoraniStemFilter.testVocabulary: 11 words of its Sorani vocabulary end in U+202E RIGHT-TO-LEFT OVERRIDE, a BMP format character no switch case matches, and their expected stems lack it, so upstream relies on this branch to remove a BMP directional control (with the branch disabled, that test fails; executed by the fact check). No upstream test uses a supplementary format character. TestSoraniNormalizationFilter.testRemove covers tatweel, harakat and ZWNJ, all explicit cases. The issue that added the analyzer (#6442, LUCENE-5379) never mentions format or supplementary characters, and no comment, CHANGES or MIGRATE entry limits the removal to the BMP.
  • Precedent. lucene/CHANGES.txt:8852: "LUCENE-6914: Fixed DecimalDigitFilter in case of supplementary code points." DecimalDigitFilter runs two filters after this one in SoraniAnalyzer. #2763 (LUCENE-1689, 2009) set the rule that "supplementary character support should be fixed for code that works with char/char[]", and TurkishLowerCaseFilter makes the same kind of category test by code point.
The devil's-advocate check180 words

The strongest case for "intended" (the intended-behaviour check and the cross-model reviewers): this is a Sorani orthographic normalizer, Sorani text only needs BMP marks, the removal sentence sits on a package-private class, and keeping tag characters preserves emoji flags.

Why it fails: the code tests the general Cf category, not a list of Sorani marks, and already removes non-directional BMP Cf characters; the public filter links the class as what it applies, and the class was public with this javadoc through 9.x; there is no emoji-preservation intent, because the same branch already strips the BMP ZWJ from ZWJ emoji sequences ([U+1F468 U+200D U+1F469 U+200D U+1F467] becomes [U+1F468 U+1F469 U+1F467]), and flags survive only because their tags are supplementary; and the JDK documents that getType(char) cannot classify these characters. Every verifier rejected the argument, and the cross-model reviews rated it weak. What survives is plausibility, not intent: such input is rare, which lowers the priority but does not make the behaviour intended. No record states the 2014 authors' intent either way; changing indexed terms is the maintainers' compatibility call.

Suggested fix

#

Recommended A: test the code point, delete all its chars

Test the code point and delete all its chars: Character.getType(Character.codePointAt(s, i, len)), then deleteN(s, i, len, Character.charCount(cp)) (SoraniNormalizer.java:121, +4/-2). The repro then passes, assertions on and off, and so does the whole analysis-common test task. Side effect: emoji subdivision flags fold to the bare black flag; affected fields need a reindex.

-          if (Character.getType(s[i]) == Character.FORMAT) {
-            len = delete(s, i, len);
+          final int cp = Character.codePointAt(s, i, len);

All options and trade-offs3 options · 502 words

One fix was built and validated in a scratch worktree at a9779ef3c193; the hunt had already checked an equivalent version. Two alternatives are listed for the maintainers' discussion.

A: test the code point, delete all its chars (validated by the checks) (recommended)

#

In the default branch, read the code point with Character.codePointAt(s, i, len), test Character.getType(int), and delete Character.charCount(cp) chars with the existing StemmerUtil.deleteN. BMP chars take the same path as before; a low surrogate of a kept supplementary character is looked at again on the next step, but alone it is SURROGATE, so nothing else changes.

         default:
-          if (Character.getType(s[i]) == Character.FORMAT) {
-            len = delete(s, i, len);
+          final int cp = Character.codePointAt(s, i, len);
+          if (Character.getType(cp) == Character.FORMAT) {
+            len = deleteN(s, i, len, Character.charCount(cp));
             i--;
           }

+import static org.apache.lucene.analysis.util.StemmerUtil.deleteN;

Trade-offs

  • Changes output only for the 127 supplementary Cf code points.
  • Emoji flags fold. Emoji subdivision-flag tokens (U+1F3F4, tag characters, U+E007F) lose their tags, so the Scotland and England flags both become the term U+1F3F4. The stock branch already folds ZWJ emoji sequences the same way (the family emoji loses its ZWJs), so the two become consistent, but a reviewer may raise it.
  • Indexed terms change for text with these characters, so affected fields need reindexing; a CHANGES entry should say so.
  • If the fix for LFV-668 (word-final HEH before a direction mark, same method) goes in too, its isWordFinal helper should read code points as well, or HEH followed by a supplementary format character keeps this bug there.

What the checks validated

  • Stock main: the paste-ready test fails 3 of 4, assertions on and off; the 30 upstream Sorani tests pass.
  • With fix A, org.apache.lucene.analysis.ckb.*: 6 classes, 34 tests, 0 failures, assertions on and off.
  • With fix A, the whole :lucene:analysis:common:test task: 340 classes, 1,913 tests, 0 failures, 18 skipped (skips not examined).
  • ecjLintMain, ecjLintTest and checkGoogleJavaFormat of the module pass.
  • The standalone runner with the fixed class first on the classpath: the test passes on main with -ea and -da, and so do the independent reproduction's test over all 127 supplementary Cf code points (4 of 4) and the finder's test (3 of 3).
  • The hunt's two equivalent sketches passed the finder's, the independent reproduction's and the cross-model review's tests; 28 upstream Sorani tests pass with and without the finder's.

B: fix A, but keep the tag characters (not validated)

#

Exempt U+E0020..U+E007F (and perhaps U+E0001) from removal, so emoji flags keep their identity.

Trade-offs

Not built or run. It leaves up to 97 of the 127 supplementary Cf code points in Sorani words, contradicts the javadoc's general rule and is inconsistent with the ZWJ removal; only worth it if maintainers object to the flag folding.

C: keep the code and document the BMP-only limit (not recommended)

#

A javadoc note that only BMP formatting characters are removed.

Trade-offs

Cheap, but contradicts the documented rule and the project's own fixes of char-wise analysis code (LUCENE-6914, LUCENE-1689) for no benefit.

Downstream note

#

Search servers built on Lucene that configure a Sorani field type with this filter, as the factory's javadoc example text_ckbnormal does, inherit the behaviour; whether an invisible character that changes a term matters beyond search quality, for example in a term-based word filter, depends on that product.

How it was found

#

Semi-formal. A bytecode scan of the main jars listed every call of the char overloads of Character category tests, which cannot classify a supplementary character. SoraniNormalizer.normalize:121 was one, and the only FORMAT removal in the analysis modules; a probe with 7 BMP and 7 supplementary format characters, then a public-API JUnit, confirmed it.

The method in full141 words

Method: a bytecode call-site inventory (the hunt's semi-formal tier), in a hunt unit about supplementary-plane characters in parsers and char-wise filters. A scanner built on the JDK 25 ClassFile API read the 27 non-sandbox, non-test module jars of main a9779ef3c193 and listed every call of the char overloads of Character category tests (getType, isLetter, ...), which cannot classify a supplementary character. One row was SoraniNormalizer.normalize:121 Character.getType(C).

Code reading found it to be the only Character.FORMAT removal site in the analysis modules. A probe put 7 BMP Cf characters (U+200F, U+200E, U+202B, U+2066, U+FEFF, U+00AD, U+061C) and 7 supplementary ones (U+E0001, U+E0067, U+E007F, U+1BCA0, U+1D173, U+110BD, U+13430) into a Sorani word: all BMP ones were removed, none of the supplementary ones. A public-API JUnit on the stock main jars then confirmed it through SoraniNormalizationFilter and SoraniAnalyzer (found 2026-10-27).

SoraniNormalizer tests for format characters one UTF-16 char at a time, so format characters outside the BMP (U+E0001, the tag characters U+E0020..U+E007F, U+1BCA0..U+1BCA3, U+1D173..U+1D17A and others) are kept in the term, while BMP ones such as RLM and LRM are removed
Area
analysis-common / Sorani normalizer (SoraniNormalizer.normalize; SoraniNormalizationFilter, SoraniAnalyzer and the 'soraniNormalization' factory)
Priority
Low, rank 456: The stock SoraniAnalyzer keeps supplementary format characters, but only garbled or constructed input puts one inside a Sorani word, which is more contrived than the Adlam and Osage text behind LFV-533, so it closes the low surrogate-handling analysis rows.
Impact class
silent wrong results
Impact note
Search quality only, with no error: applications that analyze Sorani Kurdish text with SoraniAnalyzer (default constructor included), SoraniNormalizationFilter or the 'soraniNormalization' factory, on every release from 4.7.0 through 10.5.2 and on main, index and query a word that carries an invisible format character from outside the BMP (any of the 127 supplementary Cf code points of JDK 25, for example a tag character or U+E0001; StandardTokenizer keeps it inside the word token) as a different term from the same word without it, so a search for the plain word misses it, through the token stream and through Analyzer.normalize alike, and such a character at the end of a word also blocks stemming; no scale is needed, -ea and -da behave the same, such characters are very rare in real Sorani text, and because a fix changes indexed terms, affected fields need reindexing after it.
Summary
You analyze Sorani Kurdish text with the stock SoraniAnalyzer or SoraniNormalizationFilter. The normalizer's javadoc says formatting characters are removed, and it does remove BMP ones such as the right-to-left mark, so کورد + X + ستان should become کوردستان for any invisible format character X. Instead it calls Character.getType on one UTF-16 char at a time, so a format character outside the BMP (for example U+E0001 or a tag character), which Java stores as two surrogate chars, is never recognized: it stays in the term, and the word no longer matches the same word without it, with no error.
