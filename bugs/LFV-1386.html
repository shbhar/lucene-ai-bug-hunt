A hyphenation grammar with a DOCTYPE cannot be loaded as hyph_ø.xml: the factory passes the file name to the XML parser as a URI

Give the hyphenationCompoundWord filter a grammar with the standard DOCTYPE named hyph_ø.xml and the analyzer fails to build: Lucene passes the file name to the JDK's XML parser as a URI, and ø is not allowed in one. The same file named hyph_o.xml loads; every release since 4.0.0-BETA has it.

The finding in 30 seconds

#

The factory gives the parser the file's name as the document's address. For a grammar with the standard DOCTYPE, a name with a non-ASCII letter or %, [, {, \ makes the JDK parser fail before Lucene's DTD resolver runs.

Background: hyphenation grammars and an XML document's address

#
  1. HyphenationCompoundWordTokenFilter splits compound words (for example German ones) at hyphenation points. It needs a grammar: an XML file in the FOP format, named by the factory's hyphenator setting.
  2. Grammars in the classic FOP format, such as OFFO 1.x and Lucene's own test grammars, carry <!DOCTYPE hyphenation-info SYSTEM "hyphenation.dtd">, a reference to a DTD file; the OFFO 2.x releases (2010 to 2016) leave it out. Lucene ships that DTD and hands it to the parser itself, through an entity resolver.
  3. An XML parser resolves a relative reference like hyphenation.dtd against the document's own address, its system id. A system id is a URI, so a character such as ø, % or [ is not allowed in it unencoded.

The finding, step by step

#
  1. Save a well-formed 2-line hyphenation grammar with the standard <!DOCTYPE hyphenation-info SYSTEM "hyphenation.dtd"> as hyph_ø.xml and build CustomAnalyzer.builder(dir).withTokenizer("whitespace").addTokenFilter("hyphenationCompoundWord", "hyphenator", "hyph_ø.xml").
  2. You expect the analyzer to build: the setting is documented as the path to the grammar, and the same file named hyph_o.xml loads.
  3. Instead addTokenFilter(...) throws URI$MalformedURIException: Path contains invalid character: ø, with assertions on and off. The JDK-internal message names neither the file nor the setting.
  4. Why: after opening the file, the factory also hands its name to the XML parser as the document's own address, which must be a URI (is.setSystemId(hypFile)). To find hyphenation.dtd, the JDK parser resolves it against that address and rejects ø before Lucene's resolver can supply the bundled DTD.
  5. Names with %, [, {, \ or CJK letters also fail, and so does an absolute path through a directory such as jörg/. Grammars without the DOCTYPE, such as the current OFFO 2.x ones, load under any name. With Apache Xerces on the class path the file loads; renaming it is the workaround.

Who is affected

#

Apps that configure the opt-in hyphenation decompounder by name (CustomAnalyzer, the factory SPI, a Solr schema) on the JDK's built-in XML parser, with a DOCTYPE grammar whose name or path holds a non-ASCII letter or %, [, {, \. The build fails loudly; nothing is silently wrong. Rare (current OFFO grammars have no DOCTYPE); renaming the file works around it.

Mechanism, terms and numbers598 words

HyphenationCompoundWordTokenFilterFactory (analysis-common, SPI name hyphenationCompoundWord) loads the grammar named by its hyphenator setting, documented as "path to the FOP xml hyphenation pattern" (HyphenationCompoundWordTokenFilterFactory.java:38). inform() opens it through the ResourceLoader (:115), wraps the stream in an InputSource (:116) and then calls is.setSystemId(hypFile) with the raw name (:118), under the comment "TODO: Broken, because we cannot resolve real system id" (:113). A SAX system id is a URI. Classic FOP grammars, such as OFFO 1.x and Lucene's own test grammars, carry <!DOCTYPE hyphenation-info SYSTEM "hyphenation.dtd"> (the OFFO 2.x releases carry none and are not hit); for those the JDK's built-in parser resolves that reference against the base before it asks PatternParser.resolveEntity (PatternParser.java:236-250), which would supply the bundled DTD, and its strict URI parse of hyph_ø.xml throws URI$MalformedURIException: Path contains invalid character: ø. The same file loads as hyph_o.xml, or without the DOCTYPE. Names with %, [, {, \ or CJK letters, and absolute paths through a non-ASCII directory, fail too; with Apache Xerces on the class path the repro passes. The line came with LUCENE-2732 (2010), so every Lucene release with the factory, 4.0.0-BETA to 10.6.0, is affected. A fixed base, "urn:java:" + HyphenationTree.class.getName(), fixes it (validated). Low: a loud configuration-time failure in an opt-in filter, with a rename as the workaround.

The bug

#
  1. HyphenationCompoundWordTokenFilterFactory.java:38 documents the setting: "hyphenator (mandatory): path to the FOP xml hyphenation pattern."
  2. inform(ResourceLoader) (:107-123) opens the grammar with loader.openResource(hypFile) (:115), wraps the stream in new InputSource(stream) (:116), then calls is.setSystemId(hypFile) (:118) with the raw name, under "TODO: Broken, because we cannot resolve real system id" (:113-114), and passes it to HyphenationCompoundWordTokenFilter.getHyphenationTree(is) (:119).
  3. That runs HyphenationTree.loadPatterns and PatternParser.parse(InputSource) (HyphenationCompoundWordTokenFilter.java:180, HyphenationTree.java:105, PatternParser.java:95) on a parser from SAXParserFactory.newInstance() (PatternParser.java:106-110): the JDK's built-in parser unless another SAX parser, such as Apache Xerces, is configured or on the class path.
  4. The parser meets the DOCTYPE and expands hyphenation.dtd against the base hyph_ø.xml (XMLEntityManager.expandSystemId -> expandSystemIdStrictOff1). Its strict URI parse of the base throws URI$MalformedURIException.
  5. PatternParser.resolveEntity (:236-250) would return the bundled DTD for any system id matching hyphenation.dtd (:239-242), but it is never asked. parse(InputSource) catches only SAXException (:96-97), and MalformedURIException is an IOException, so it escapes unchanged from CustomAnalyzer.Builder.addTokenFilter.

Which names fail

#

On main, the JDK parser, with the DOCTYPE: ø, %, [, {, \, a CJK letter (U+6570) and a supplementary letter (U+10428) in the name fail through the factory; a space and # load; without the DOCTYPE every name loads (a 60-cell differential, assertions on and off); an OFFO 2.2 grammar, which has no DOCTYPE, loads as hyph_ø.xml, an OFFO 1.2 one fails. An ASCII file name given as an absolute path under a directory named with ö fails the same way. With Apache Xerces 2.12.2 on the class path the repro passes.

Second trigger, same root

#

getHyphenationTree(String) ("@param hyphenationFilename the filename of the XML grammar to load", HyphenationCompoundWordTokenFilter.java:162) and PatternParser.parse(String) ("@param filename the filename", PatternParser.java:80) pass the file name as new InputSource(name) (:167, :84), a system id: a non-ASCII name fails the same way with the DOCTYPE, %, [, {, \ throw MalformedURLException: no protocol, and a # in a directory name opens a truncated path (FileNotFoundException). This half is softer: LUCENE-2732 made these loaders take a system id on purpose.

Exposure and likelihood255 words
  • Who is hit. Users of HyphenationCompoundWordTokenFilterFactory (CustomAnalyzer, the factory SPI, Solr-style schemas) on the JDK's built-in XML parser (what JAXP falls back to when no other SAX parser, such as Apache Xerces, is configured or on the class path), whose grammar carries the standard DOCTYPE (OFFO 1.x, Lucene's own test grammars, self-made ones) and whose grammar name, or a directory in its absolute path, holds a non-ASCII letter or one of %, [, {, \.
  • What happens. The analyzer, and any schema or field type using it, fails to build with a JDK-internal URI$MalformedURIException that names neither the file nor the setting.
  • What does not happen. No wrong tokens, nothing indexed differently, no hang; the failure is at configuration time.
  • Default vs opt-in, scale. The filter is in no stock Analyzer and needs a grammar file. No data size or load is involved; deterministic, the same with -ea and -da.
  • Who is not hit. Grammars without the DOCTYPE, such as the current OFFO 2.x releases (an OFFO 2.2 grammar copied as hyph_ø.xml loads); callers of getHyphenationTree(InputSource) with a stream and no system id; and factory users with Apache Xerces on the class path (there the two String loaders still fail for such characters in an absolute path).
  • How likely. Rare: it takes both a grammar with the DOCTYPE and a non-ASCII or reserved character in its name or directory; the current OFFO grammars (2.x) carry no DOCTYPE, and no report was found since the line landed in 2010.

Why it looks unintended

#
  • Documented as "path to the FOP xml hyphenation pattern"; nothing limits the name to URI-safe ASCII, and the file opens fine.
  • The commit that added the line gave the (deprecated) Reader loader a fixed, valid base; the factory never got one.
  • A LUCENE-4570 commit fixed this failure class in the old File loaders ("directories with non-ascii path names").
The full argument213 words
  • Contract. "hyphenator (mandatory): path to the FOP xml hyphenation pattern" (HyphenationCompoundWordTokenFilterFactory.java:38). ResourceLoader.openResource opens such a name fine; no javadoc restricts the characters. The user never touches SAX: it is Lucene that turns the name into a system id.
  • The code knows the base is fake. "TODO: Broken, because we cannot resolve real system id" (:113). It does not say that ordinary names should fail.
  • History. LUCENE-2732 (#3806, 819344aeab0, 2010-10-31, Uwe Schindler) added the line and, in the same commit, gave the (deprecated) getHyphenationTree(Reader) loader of that time the fixed base "urn:java:" + HyphenationTree.class.getName() with the comment "some parsers still want to have a base URL (Crimson)" (LUCENE-2731, #3805). LUCENE-2781 (a58c26978f5) later removed that loader; the factory kept the raw name.
  • Precedent. A commit under LUCENE-4570 (#5636, the forbidden-APIs issue; 0a68fa66ac0, 2013-01-18, the same author) changed the old File loaders from toURL() to toURI().toASCIIString(): "Fix deprecated API usage (otherwise may lead to bugs if Hyphenation filters load files from directories with non-ascii path names)". It did not touch the factory or the String loaders; LUCENE-5945 (3eb66fb19ca, 2014) removed the File loaders.
  • Tests. TestHyphenationCompoundWordTokenFilterFactory loads only the ASCII name da_UTF8.xml; TestCompoundWordTokenFilter loads grammars from class-path URLs. Nothing tests or asserts other names.
The devil's-advocate check149 words

The strongest case for "not a bug": SAX defines a system id as a URI, and LUCENE-2732 deliberately changed the String loaders from new File(name) to new InputSource(name), so a non-URI is caller misuse; the TODO marks the base as a known limitation; and the JDK parser is stricter here than Apache Xerces, which accepts the same input.

Why it fails for the factory: its caller passes a documented path, not a system id; Lucene does the conversion, wrongly; the TODO admits brokenness but documents no restriction; the LUCENE-4570 commit said the same symptom "may lead to bugs"; and a valid base (a fixed urn:, or none) works on the same JDK parser, so it is not a JDK bug. Where it partly holds: for the two String loaders a maintainer may answer "they take a system id" and fix only their javadoc, so those stay secondary.

Suggested fix

#

Recommended A. Fixed, always-valid base in the factory

Give the factory a fixed, always-valid base, is.setSystemId("urn:java:" + HyphenationTree.class.getName()), the base Lucene already gave its (deprecated) Reader loader in 2010. Validated: the test then passes with assertions on and off, all 26 tests of the compound package pass, and the format check is clean.

A. Fixed, always-valid base in the factory (validated by the checks) (recommended)

#

Replace the raw name with the base LUCENE-2732 gave the (deprecated) getHyphenationTree(Reader) loader. The DTD still comes from PatternParser.resolveEntity, which keeps rejecting every other external entity (#16135). For the standard grammar only the base changes; any other relative system id would also be expanded against the urn: base before resolveEntity rejects it (read; only the standard grammar was tested).

+      // did) instead of the raw resource name, which is not a URI
+      is.setSystemId("urn:java:" + HyphenationTree.class.getName());

Trade-offs

The base is not the file's real location, as it is not today either (the TODO stays true). One line; no API change.

What the checks validated

In a scratch worktree at 5adff78bb168 (2026-11-05): the test fails through gradle before the change and passes after it, with -Ptests.asserts=true and =false; with the change, ./gradlew :lucene:analysis:common:test --tests 'org.apache.lucene.analysis.compound.*' -Dtests.seed=DEADBEEF -Ptests.asserts=true passes all 5 test classes (26 tests, 0 failures) and :lucene:analysis:common:checkGoogleJavaFormat passes. The fix shadowed into the stock jars passes with assertions on and off. The full analysis-common suite was not run.

B. Also convert plain paths in the two String loaders (optional) (validated by the checks)

#

In getHyphenationTree(String) and PatternParser.parse(String), pass a string that starts with a URI scheme of two or more characters through (a one-letter scheme is taken as a Windows drive letter, so x:foo becomes a path) and turn anything else into a file URI with Path.of(name).toUri().toASCIIString(), as LUCENE-4570 did for the old File loaders. Alternative: keep the code and correct their javadoc to say they take a system id (a URI).

Trade-offs

Changes behaviour for callers who pass relative URI references that are not file paths, or one-letter schemes; a PR would need tests for URI inputs, relative references and platform path forms (not exercised). A maintainer may prefer the javadoc correction, since LUCENE-2732 chose system-id semantics on purpose.

What the checks validated

With A and B together (2026-11-05, same worktree): the 26 tests pass and the format check passes. Earlier, the 60-cell loader differential dropped from 33 mismatches to 0 with them.

C. Set no system id at all

#

Drop the setSystemId call, as Elasticsearch and OpenSearch do.

Trade-offs

On the JDK parser a grammar with the DOCTYPE then loads, also from a working directory named with ø (probe). But LUCENE-2731 added a base because some parsers (Crimson) would not load the DTD without one; other parsers were not tried.

D. Let the ResourceLoader supply a real URL

#

What the TODO asks for: a method that returns the resource's URL, used as the base.

Trade-offs

A real base, but a new API on every ResourceLoader; much larger than the bug. Not run.

Downstream note

#

Solr uses this factory directly, so a Solr schema whose hyphenator file name has such a character would fail the same way (by reading; Solr was not run), while Elasticsearch and OpenSearch build the parser input from a stream without a file name and do not hit this trigger.

How it was found

#

Semi-formal: a bounded differential test of Lucene's three public grammar loaders against a reference load from the file's URI, over a small alphabet of file-name characters, with and without the standard DOCTYPE. The factory failed for ø, %, [, {, \ and CJK names on the JDK parser, and the case was reduced to one JUnit test.

The method in full146 words

Method: semi-formal, a bounded differential (2026-11-05, main 5adff78bb168).

  • The loaders under test: the factory through CustomAnalyzer, getHyphenationTree(String) and PatternParser.parse(String). The reference: getHyphenationTree(new InputSource(fileUri)), which loads every valid file.
  • The bounded input space: file names over an alphabet of ASCII, space, #, %, [, {, \, Latin-1 and CJK letters, each with and without the standard DOCTYPE, on the JDK's built-in parser and on Apache Xerces 2.12.2 (the Xerces evidence kept is a separate one-test control).
  • Re-run as 60 cells on the JDK parser (10 names including a supplementary letter, DOCTYPE on and off, 3 loaders), assertions on and off: 33 mismatches, 7 of them on the factory. Reading the history, guided by the LUCENE-4570 fix of the sibling File loaders, came second (non-formal).
  • The factory mismatch was then reduced to the one public-API JUnit test above.

History

#

Introduced by LUCENE-2732 (819344aeab0, 2010-10-31), which added is.setSystemId(hypFile); the factory first shipped in Lucene 4.0.0-BETA with the line. Every release run from 4.0.0-BETA to 10.6.0 fails, and main.

Versions tested7 rows

LFV-1386, snapshot of 2026-11-08

Registry title
HyphenationCompoundWordTokenFilterFactory passes the raw 'hyphenator' file name to the XML parser as the base system id (a URI), so with the JDK's built-in parser a valid hyphenation grammar named e.g. hyph_ø.xml, or with '%', '[', '{' or '\' in its name, fails to load with MalformedURIException
Area
analysis-common / compound: hyphenation grammar loading (HyphenationCompoundWordTokenFilterFactory.inform; also HyphenationCompoundWordTokenFilter.getHyphenationTree(String) and PatternParser.parse(String))
Priority
Low, rank 1077: In every release since 4.0.0-BETA, a valid hyphenation grammar fails loudly at analyzer build time when its file name or path holds a non-ASCII letter or one of '%', '[', '{', '\', and the exception does not name the cause. Nothing is silently wrong, renaming the file works around it, and only the opt-in hyphenation decompounder is affected, on the JDK's built-in XML parser (the default when Xerces is absent).
Impact class
minor
Impact note
Hits applications that use the opt-in hyphenation decompounder through the 'hyphenationCompoundWord' factory (CustomAnalyzer, Solr-style schemas) on the JDK's built-in XML parser (the default when Apache Xerces is not on the classpath) whenever the grammar's resource name, or the directory part of an absolute path, holds a non-ASCII letter or one of '%', '[', '{', '\' and the grammar carries the standard FOP DOCTYPE: the analyzer fails to build with an exception that does not name the cause; nothing is silently wrong, renaming the file works around it, -ea and -da behave the same, no scale is needed, and every Lucene release since 4.0.0-BETA is affected.
Summary
You configure HyphenationCompoundWordTokenFilterFactory with hyphenator=hyph_ø.xml, a valid FOP grammar with the standard DOCTYPE, and expect the analyzer to build, as it does when the same file is named hyph_o.xml. Instead, with the JDK's built-in XML parser, the build throws URI$MalformedURIException 'Path contains invalid character: ø': the factory hands the raw resource name to the parser as the base system id, which must be a URI, and the parser fails while resolving the DOCTYPE's relative 'hyphenation.dtd' against it, before Lucene's entity resolver gets the chance to supply the bundled DTD. The public getHyphenationTree(String) and PatternParser.parse(String), documented to take a file name, pass it as a URI the same way.
Introduced

Before it, the unreleased Solr factory (SOLR-1984, c5bc95a3577) set no system id.
