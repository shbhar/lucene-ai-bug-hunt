Sandbox multi-range and phrase-wildcard builders: adding to the builder after build() changes the query you already built

The sandbox point multi-range builders and PhraseWildcardQuery.Builder give the built query the builder's own list, so a later add() silently rewrites it: pt in [0,0] starts matching pt=3, and "x b*" becomes "x b* z". Affects every release since 8.3.0; on 10.6.0 a query cache that caches every query served stale hits.

The finding in 30 seconds

#

build() does not copy: the built query keeps a reference to the builder's own list of ranges (or phrase terms). Every later add() on that builder therefore also lands in every query already built from it; in the runs shown that changed its matches, toString, equals and hashCode.

Background

#
  1. Query builders. A Lucene query is meant to stay fixed once built. Its builder collects clauses, and build() returns a new query. Core builders (BooleanQuery.Builder, PhraseQuery.Builder, MultiPhraseQuery.Builder) copy what they collected, so one builder can go on to build the next, larger query.
  2. The query cache (LRUQueryCache) keeps, per segment, the documents a query matched, and finds them again through the query's hashCode and equals. It assumes a cached query never changes.

The finding, step by step

#
  1. Build q with IntPointMultiRangeBuilder("pt", 1): add([0,0]), then build(). On an index with one document, pt=3, q is pt:{[0 TO 0]} and matches 0 documents.
  2. Add [3,3] to the same builder, for example to build the next, wider query. You expect q to stay pt:{[0 TO 0]} with 0 hits, as a query from BooleanQuery.Builder does: core builders copy their clauses on build().
  3. Instead q prints pt:{[0 TO 0]},{[3 TO 3]} and matches 1 document: build() handed q the builder's own ArrayList, and add() appended to it. PhraseWildcardQuery.Builder does the same: "x b*" becomes "x b* z" and matches 0 instead of 1 on x bb.
  4. The query cache files q's cached hits under q's hash code, which has now moved. If q was cached while it was [0,0] and is searched again after the add (index pt=0, pt=3), 10.6.0 and 9.12.3 then answer q2 = [0,0]+[3,3] from q's old cached result: 1 hit instead of 2. On main, and on 10.6.0 without that second search, the old entry is orphaned instead: lookups miss, and clearQuery(q) cannot remove it (on main the new hash also picks another partition).

Who is affected

#

Applications that keep a query built by one of these sandbox builders and then add more ranges or terms to the same builder, for example growing a range set or a phrase step by step and keeping each step as a filter, an exclusion or a cache key. Each earlier query silently changes; default settings, one document is enough.

Mechanism, terms and numbers505 words

The four sandbox point builders (IntPoint, LongPoint, FloatPoint, DoublePointMultiRangeBuilder) collect ranges in MultiRangeQuery.Builder's own ArrayList and pass that list to the query they build, whose protected constructor stores it as is; PhraseWildcardQuery.Builder.build() does the same with its phrase terms. Every later add(), addTerm() or addMultiTerm() on the builder therefore also lands in each query built from it before; in the runs shown that changed its matches, toString, equals and hashCode. On one document pt=3, q = [0,0] is built, [3,3] is added to the builder, and q matches 1 document instead of 0; "x b*" becomes "x b* z" and matches 0 instead of 1 on x bb. This contradicts build()'s javadoc ("Create a new MultiRangeQuery based on the parameters that have been set on this builder") and PhraseWildcardQuery's "Immutable." and "can be used safely as a key of the query cache", and differs from core's query builders (BooleanQuery, PhraseQuery, MultiPhraseQuery, SynonymQuery), which copy on build(). Because the hash code moves under a cached entry, the query cache goes wrong too: on 10.6.0 and 9.12.3 it served stale hits; on main the entry is orphaned. Every release from 8.3.0 (8.4.0 for PhraseWildcardQuery) to 10.6.0 and main is affected; copying the list in the MultiRangeQuery constructor and in PhraseWildcardQuery.Builder.build() fixes it and passes the sandbox search tests.

The bug (main f794ff5a505c)

#
  1. The builder's list. MultiRangeQuery.Builder keeps protected final List<RangeClause> clauses = new ArrayList<>() (MultiRangeQuery.java:87); add() appends to it (:106-116).
  2. build() hands it over. Each point builder's build() returns new MultiRangeQuery(field, numDims, bytesPerDim, clauses) {...} (IntPointMultiRangeBuilder.java:33; the LongPoint, FloatPoint and DoublePoint builders identical at :33), and the protected "Expert" constructor stores it: this.rangeClauses = rangeClauses; (MultiRangeQuery.java:145-158, the assignment at :157).
  3. The query reads it every time. Matching (:319-323), count (:392), hashCode (:429-436), equals (:439-448) and toString (:451-460) all read rangeClauses. rewrite() never writes to it: it returns this, or a clone with a new merged list when merging removes ranges (:172-188, :197-238), so only the builder's later add() changes the list.
  4. PhraseWildcardQuery, same pattern. Builder.build() passes the builder's own phraseTerms (PhraseWildcardQuery.java:669-673; created at :615, appended at :636 and :656); the constructor stores it (:105); equals/hashCode read it (:324-334).

More executed consequences (the finder's public-API witness, main and 10.6.0, two documents with the values 0 and 3, one point field per builder type)

#
  • All four point builders count 2 instead of 1 for the earlier [0,0] query.
  • "New ranges only" (q2 SHOULD, q1 MUST_NOT, both from one builder) counts 0 instead of 1, because q1 now holds q2's ranges too.

Not claimed: RangeClause and Builder.add(byte[], byte[]) keep the caller's byte arrays without copying; core PointRangeQuery's protected constructor does the same, so that is a separate, defensible convention.

Exposure and likelihood589 words
  • What goes wrong. Extra hits for a range set, missing hits for a phrase, a wrong "new ranges only" result, a moved hash code; with a query cache that caches every query, stale hits on 10.6.0 and 9.12.3 or an orphaned entry on main. No error, assertions on or off.
  • The query cache, plainly. The cache files a query's matching documents under that query's hashCode and finds them through equals. Here the cached key is the very object the builder still writes into: after b.add([3,3]) the key's contents and hash describe [0,0]+[3,3], while the entry still holds the documents of [0,0], filed under the old hash.
    • 10.6.0 and 9.12.3: stale hits. Documents pt=0 and pt=3, an explicit cache that caches every query: q1 = [0,0] is searched (1 hit, cached); the builder adds [3,3] and builds q2; q1 is searched again (2 hits); then q2 returns 1 hit through the cache and 2 without one. The 10.6.0 cache keeps one table that maps each distinct query to a stored instance by hashCode/equals (uniqueQueries, LRUQueryCache.java:94, :137, used at :303, :323) and, per segment, a table from that instance to its documents by object identity (IdentityHashMap, :706, :711). Searching the changed q1 misses the first table under the new hash, so q1 is registered again, but the segment table keeps the old [0,0] documents for the same object (:339, :733-741). q2, equal to the changed q1, then reads them. With the constructor copy the same run gives 2 hits.
    • Main: an orphaned entry; no stale hit for this add. Main's cache was rewritten on main only (#15558, #16657); neither change is in 10.6.0, which was released from the 10.x branch. It files each entry under (segment, query, hash at insertion) (QueryCacheKey, LRUQueryCache.java:1309-1343) in a partition picked by the hash (:426, :1277-1279). The changed q1 misses under its new hash and is recomputed into a new entry; q2 then hits that entry (2 hits, correct), so for this probe's add, which changes the hash, no stale hit was observed. The old entry stays: clearQuery(q1) plus cleanUp() always leaves it (1 entry left in the witness and the diagram probe, where q1 is not searched again), because cleanUp() routes the removal by the current hash (:1404-1411; -2057188341 and 501375853 fall in partitions 11 and 13 of 16; a new hash in the same partition would let the removal find the entry, :1158); on 10.6.0 clearQuery also leaves 1 entry. After LRU eviction, main's ramBytesUsed stays 32 bytes high (232 vs 200), because releaseQuery looks the query up by its new hash (:1006-1017, :1178).
    • Scope. A deliberately forced cache path: IntPointMultiRangeBuilder, a one-segment index, an application-installed LRUQueryCache with a policy that caches every query, and searches wrapped in ConstantScoreQuery. PhraseWildcardQuery.Builder has the same mechanism (not run for the cache). The default IndexSearcher cache of 9.x and 10.x (IndexSearcher.java:95-99 on 10.6.0; disabled on main, IndexSearcher.java:82-84) applies its own size and usage rules; that path was not run.
  • Default vs opt-in. Default codec, IndexWriterConfig and searcher; the classes are opt-in sandbox code (@lucene.experimental).
  • Reach. Latent in Lucene's own tree: TestMultiRangeQueries and TestPhraseWildcardQuery build every query with a fresh builder, and no Lucene caller reuses these builders. Downstream code uses the multi-range builder (for example OpenSearch PR #16391, for IP masks); no report of reuse was found.

Why it looks unintended

#
  • build() is documented to "Create a new MultiRangeQuery"; PhraseWildcardQuery says "Immutable." and safe "as a key of the query cache".
  • Core builders copy on build() (BooleanQuery uses List.copyOf), and the PR that added MultiRangeQuery called its builder "much like BooleanQuery".
  • #8120 fixed the same aliasing in MultiPhraseQuery.Builder in 2016; nothing says these builders are single-use.
The full argument241 words
  • The javadoc. MultiRangeQuery.Builder.build(): "Create a new MultiRangeQuery based on the parameters that have been set on this builder." (MultiRangeQuery.java:118-122). PhraseWildcardQuery: "Immutable." (PhraseWildcardQuery.java:83); the PhraseTerm javadoc: the query "is immutable and light itself and can be used safely as a key of the query cache" (:676-680).
  • The Query contract. equals/hashCode are "required so that QueryCache works properly" (Query.java:95-112).
  • Core builders copy. BooleanQuery.Builder.build() uses List.copyOf(clauses) (BooleanQuery.java:116-121); PhraseQuery.Builder and MultiPhraseQuery.Builder copy into arrays (PhraseQuery.java:157-161, MultiPhraseQuery.java:142-146), and MultiPhraseQuery's javadoc says build() "returns the fully constructed (and immutable) MultiPhraseQuery" (:52). TestBooleanQuery.java:542-559 builds, adds a clause and builds again; the sandbox's own TestSortedDvMultiRangeQuery does the same with the sibling doc-values multi-range builders (:428-446, :471-483), whose queries copy the list (SortedSetDocValuesMultiRangeQuery.java:68; SortedNumericDocValuesMultiRangeQuery.java:57 builds its own sorted set).
  • Design intent. The PR that added MultiRangeQuery (apache/lucene-solr#794, 2019-07-18) described its builder as "much like BooleanQuery", whose build() copies.
  • Precedent. #8120 (LUCENE-7064, 2016) caught the same aliasing in MultiPhraseQuery.Builder during review ("I pass the arrays from the builder to the query as is without copying them, so any modification to the builder modifies the query as well") and fixed it so that "modifying a Builder no longer affects already created queries".
  • Nothing says single-use. No javadoc, CHANGES or MIGRATE entry; Lucene says so where it means it (PackedLongValues.Builder.build(): "This operation is destructive.", PackedLongValues.java:207-211).
The devil's-advocate check231 words

Strongest case for "intended": the constructor that keeps the list is protected and labelled "Expert" (MultiRangeQuery.java:145-153) and MultiRangeQuery never says "immutable"; Builder has no reset() and every upstream test of these builders uses a fresh builder per query, which suggests one build() per builder; both classes are sandbox and @lucene.experimental; and LRUQueryCache's own message blames "a query which has been modified after having been put into the cache" (LRUQueryCache.java:1234-1243), i.e. the caller.

Why it fails: the list is the builder's own state. The user calls only the public add() and build(), never the Expert constructor, and never touches a mutable object, so "Expert, keeps what you pass" does not cover Lucene's own builder keeping what it passed. A missing reset() explains fresh builders in tests, not a reuse ban, and core tests do reuse builders. @lucene.experimental is about API stability, not wrong results, and the code ships in released jars since 8.3.0. PhraseWildcardQuery says "Immutable." outright. The two faces are not equally strong: the "intended" case is plausible for MultiRangeQuery (no immutability promise, an Expert constructor) and much weaker for PhraseWildcardQuery ("Immutable.", safe "as a key of the query cache"). An independent reviewer from another model family (OpenAI GPT-5.6, lenses) and the intended-behaviour verifier rated the "intended" case weak; a cross-model fact check of this page rated it moderate overall, for the MultiRangeQuery reasons.

Suggested fix

#

Recommended (a) Copy the list in the MultiRangeQuery constructor and in PhraseWildcardQuery.Builder.build() (recommended, validated)

Copy the list where the query takes it: this.rangeClauses = new ArrayList<>(rangeClauses) in the MultiRangeQuery constructor (covers all four point builders) and List.copyOf(phraseTerms) in PhraseWildcardQuery.Builder.build() (+6/-2). The repro passes, as do TestMultiRangeQueries, TestPhraseWildcardQuery and the sandbox search tests (116).

// MultiRangeQuery constructor (one site for all four point builders and any subclass)
this.rangeClauses = new ArrayList<>(rangeClauses);

// PhraseWildcardQuery.Builder.build()
return new PhraseWildcardQuery(
    field,
    List.copyOf(phraseTerms),
    slop,
    maxMultiTermExpansions,
    segmentOptimizationEnabled);

(a) Copy the list in the MultiRangeQuery constructor and in PhraseWildcardQuery.Builder.build() (recommended, validated)

#

// MultiRangeQuery constructor (one site for all four point builders and any subclass)

Trade-offs

  • One list copy per build() (n ranges or terms), as BooleanQuery does.
  • Subclasses that call the protected constructor with their own list now get a copy, which is what a query needs.
  • The copy is of the list only: RangeClause and its byte arrays stay shared (MultiRangeQuery.java:51-58), as in core PointRangeQuery, so the fix does not make every constructor input immutable.

What the checks validated

  • Clean scratch worktree of f794ff5a505c, gradle, OpenJDK 25.0.3, 2026-11-10: the repro fails 2 of 2 on stock with assertions on and off and passes 2 of 2 with the fix, on and off.
  • With the fix: TestMultiRangeQueries (13 tests, 1 skipped) and TestPhraseWildcardQuery (11), on and off; the org.apache.lucene.sandbox.search package, 15 classes, 116 tests (5 skipped), 0 failures; :lucene:sandbox:checkGoogleJavaFormat passes.
  • The cache probe with the constructor copy: q1 stays [0,0] (1 hit) and q2 gets 2 hits through the cache, on main and on the 10.6.0 jars.
  • Earlier checks of the same change: the finder's model-based test and witness are clean.

Downstream note

#

Downstream only: a restriction or exclusion filter kept from one of these builders widens or narrows when the application reuses the builder, so only the application's own code can trigger it.

How it was found

#

Semi-formal: a public-API probe of query builders showed the effect, then a bounded-exhaustive differential model-based test ran every add/build/search sequence up to length 6 (5 for PhraseWildcardQuery), comparing each built query with a fresh replay of its build-time prefix. Only these two builder families failed; five copying builders stayed clean.

The method in full82 words

Method: differential model-based testing, bounded and exhaustive. Each built query was compared with a query freshly built from the same build-time prefix of operations, on equals, hashCode, toString and the hit count.

  • On stock main: IntPointMultiRangeBuilder failed 15,993 of 22,461 checks and PhraseWildcardQuery.Builder 4,476 of 7,465.
  • Controls, all clean: BooleanQuery.Builder, PhraseQuery.Builder, MultiPhraseQuery.Builder, the sandbox SortedNumeric doc-values multi-range builder and CombinedFieldQuery.Builder.
  • With the fix, everything is clean. The finding was then reduced to the JUnit shown here.

LFV-1469, snapshot of 2026-11-10

Registry title
Sandbox MultiRangeQuery point builders (IntPoint, LongPoint, FloatPoint, DoublePointMultiRangeBuilder) and PhraseWildcardQuery.Builder hand the built query the builder's own list, so adding to the builder after build() silently changes the earlier query's hits, equals/hashCode and toString (since 8.3.0)
Area
sandbox / search: MultiRangeQuery point builders and PhraseWildcardQuery.Builder (build() hands over the builder's own list)
Priority
Low, rank 914: Adding ranges or terms to a sandbox MultiRangeQuery point builder or PhraseWildcardQuery.Builder after build() silently changes the hits and hash code of the query already built, every time, in every release since 8.3.0 (8.4.0 for PhraseWildcardQuery) and on main. It is Low because it needs these sandbox builders reused after build(), a pattern no Lucene caller uses; no report of it was found. With a query cache that caches every query, the moved hash code also served stale hits on 10.6.0 and 9.12.3 and left an orphaned cache entry on main.
Impact class
silent wrong results
Impact note
Only applications that keep a query built by one of the sandbox (@lucene.experimental) IntPoint/LongPoint/FloatPoint/DoublePointMultiRangeBuilder or PhraseWildcardQuery.Builder and then call add(), addTerm() or addMultiTerm() on the same builder again are hit: the earlier query silently takes on the later ranges or terms (extra hits for a range set, missing hits for a phrase; 'q2 SHOULD, q1 MUST_NOT' built from one builder matches nothing instead of the pt=3 document) and its hashCode moves under any query-cache entry stored for it (with a cache that caches every query, 10.6.0 and 9.12.3 then served stale hits, 1 instead of 2, and main kept an entry that can no longer be found or removed); default settings, two documents, no scale needed; no Lucene caller reuses these builders; every release from 8.3.0 (PhraseWildcardQuery.Builder from 8.4.0) through 10.6.0 and main.
Summary
You create one IntPointMultiRangeBuilder, add the range [0,0], build q1, then add [3,3] and build again. You expect q1 to keep matching only pt=0, since build() is documented to 'Create a new MultiRangeQuery based on the parameters that have been set on this builder' and the core query builders (BooleanQuery, PhraseQuery, MultiPhraseQuery) copy their state on build(). Instead build() gives q1 the builder's own clause list, so the later add() changes q1 too: it prints pt:{[0 TO 0]},{[3 TO 3]}, counts 2 instead of 1 and its hashCode changes; PhraseWildcardQuery.Builder does the same with its term list although that class is documented 'Immutable.' and safe as a query-cache key.
