Polygon.fromGeoJSON keeps a copy of the key path for every nesting level, so a valid 752 KB GeoJSON Feature runs out of a 512 MiB heap

The finding in 30 seconds

#

Lucene's GeoJSON parser remembers where it is with a text address, and makes a new, longer copy of it at every nesting level.

  1. You call Polygon.fromGeoJSON on a valid GeoJSON Feature: a 4-point Polygon geometry, and properties with one member whose key is 750,000 chars long and whose value is 900 nested empty arrays [[[...]]]. The text is 751,925 chars.
  2. You expect the one polygon back: properties do not change the polygon (the parser only walks through them). With a 2 GiB heap, or with the same 900 levels under a 1-char key, that is what you get.
  3. At Lucene's default 512 MiB test heap you get OutOfMemoryError: Java heap space, with assertions on and off.
  4. Why: to know where it is, the parser carries a text address such as properties.kkk….[].[] and makes a new, longer copy at every level, keeping each copy until that level is done, so all 900 are alive at once. 900 copies of a 750,000-char address are 676 million chars, about 645 MiB. Yet the parser only compares the address with five short constants and a crs prefix.

Who is affected

#

Only applications that pass GeoJSON they do not control to Polygon.fromGeoJSON, an experimental API that no other Lucene code calls. Shallow GeoJSON with short keys is not at risk. But the usual input limits do not protect: the repro is 752 KB and 902 levels deep, and 1 MB of 1,000 nested objects with 1,000-char keys also exhausts 512 MiB.

Mechanism, terms and numbers595 words

SimpleGeoJSONPolygonParser, behind Polygon.fromGeoJSON, tracks its position with a path String (path + "." + key for an object member, path + ".[]" for an array element), and every recursive frame keeps its own copy alive until it returns, so live memory is about nesting depth times path length. A valid Feature whose properties hold one 750,000-char key over 900 nested empty arrays (751,925 chars, 902 levels) needs about 676 million chars of path strings at once and fails with OutOfMemoryError: Java heap space at Lucene's default 512 MiB test heap, with assertions on and off; it parses at 2 GiB, and the same nesting under a short key, or the same text as a string value, parses at 512 MiB. The path is only ever compared with five short constants and a crs prefix, so keeping its first 21 chars gives identical behaviour with linear memory. Present since the API was added in 6.2.0; ordinary, shallow GeoJSON with short keys is not at risk.

How the parser tracks its position

#
  • parseObject(String path) (SimpleGeoJSONPolygonParser.java:100; comment at :99: "path is the \"address\" by keys of where we are, e.g. geometry.coordinates"). parse() starts with "" (:65).
  • For a member whose value is an array or object it builds a new String, newPath = path + "." + key (:143, :151; just key at the top, :141, :149), and recurses with it (parseArray(newPath) at :145, parseObject(newPath) at :153).
  • parseArray(String path) (:283) passes path + ".[]" to every nested array (:309) or object (:312).
  • Each frame still needs its path while its child runs: parseArray uses it again for the next element (inside the loop), parseObject after the child returns (:174, :186, :205). So at depth d all d Strings are live at once.

What the path is used for (the complete list)

#

path.equals("crs.properties") (:125, :174), path.startsWith("crs") (:186), path.equals("features.[]") || path.isEmpty() (:197), isValidGeometryPath (:192, :194, :205) = isEmpty() || equals("geometry") || equals("features.[].geometry") (:222-224), and path.length() == 0 (:140, :148). The longest constant is 20 chars. Error messages quote the input, not the path.

The numbers

#

In the repro the first array's path is properties. + key = 750,011 chars, and each deeper level adds .[]. 900 such Strings total 900 x 750,011 + 3 x 899 x 900 / 2 = 676,223,550 chars; the JDK stores these Latin-1 Strings at one byte per char, so about 645 MiB, roughly 900 times the input. In general: about d x K + 1.5 d^2 bytes for d nested arrays under a K-char key, and about K x d^2 / 2 for d nested objects each under a K-char key. The hunt's model predicted the heap threshold of three shapes with the same d x K product (250 x 1 MiB, 500 x 512 KiB, 1,000 x 256 KiB) at 252-253 MiB; bisection on the stock jar measured 255 MiB for all three (serial collector). Exact thresholds depend on the JVM, the collector and the heap settings: with G1 at -Xmx512m on this JDK (1 MiB regions) each of these ~750 KB Strings is a humongous object that takes a whole region, which raises the need here by about a third (measured on the standalone runner, assertions off: the repro parses from -Xmx704m with the serial collector and from -Xmx928m with G1, and fails at 672m and 896m).

Exposure and likelihood261 words
  • Who. Applications that pass GeoJSON they do not control to Polygon.fromGeoJSON, for example to build a polygon filter from a request. Polygon is @lucene.experimental (Polygon.java:41) and advertises fromGeoJSON in its class javadoc (:25); outside tests (TestPolygon, TestTessellator) no Lucene code calls it.
  • No setting involved. The parser has no options. The trigger scales with the heap: at 2 GiB the repro parses, and a proportionally longer key or deeper nesting fails there too (an independent reproducer's scaling run: depth 500 under a 200,000-char key fails at 96 MiB and parses at 112 MiB, while the same text as a string value parses at 32 MiB).
  • Usual size and depth limits do not prevent it. The repro is 752 KB with 902 levels, below the 1,024-level default that #16423 chose for the expressions parser. A second witness, 1,000 nested property objects with 1,000-char keys (1,005,143 chars), also exhausts 512 MiB (standalone runner, G1). So a 1 MiB input limit plus a 1,000-level depth limit still lets a failing input through. Size and depth limits together do bound the memory, but only when chosen for the heap budget; an application may also need a key-length (or path-length) limit.
  • Effect. A VM error instead of the polygon or the declared ParseException. No wrong polygon is returned and no index is touched.
  • Realistic input is not at risk. Real GeoJSON is shallow (a MultiPolygon's coordinates are four arrays deep) and uses short keys, so its paths stay short (the formula above); no report in ten years.

Why it looks unintended

#
  • The javadoc accepts a Polygon inside a Feature and declares only ParseException; properties may hold any JSON.
  • The parser only compares the path with five short constants and a crs prefix, so the full string is never needed.
  • #16423 (10.6.0) set the newer bar: parsers should not throw VM errors on nested input.
The full argument193 words
  • Contract. Polygon.java:248-255: "Parses a standard GeoJSON polygon string. The type of the incoming GeoJSON object must be a Polygon or MultiPolygon, optionally embedded under a \"type: Feature\"." It declares only throws ParseException and links the GeoJSON spec, where the value of a Feature's properties is any JSON object (or null).
  • The parser's own example (SimpleGeoJSONPolygonParser.java:24-38) is a Feature whose properties hold a nested object, and TestPolygon.testGeoJSONPolygonFeature (:176) tests that shape.
  • Properties are meant to be passed over. LUCENE-8964 (#10007, 8.3.0) changed the parser so that string arrays in properties parse instead of failing (TestPolygon.testPolygonPropertiesCanBeStringArrays, :348).
  • Nothing needs the full path. A 21-char prefix gives the same answer to every path test; a 600,000-document differential confirmed it, and caps of 20 and 12 chars were caught as different.
  • Recent maintainer stance. #16423 (10.6.0, lucene/CHANGES.txt:551): the expressions parser "could throw StackOverflowError on deeply nested expressions ... The new code allows to add a hard limit for nesting (default is 1024) and no longer throws virtual machine errors."
  • Nothing found treats the growth as intended (the file's history and tests, #8433, #10007, and the prior-report searches below).
The devil's-advocate check183 words

The strongest case for "intended" (built by the intended-behaviour checker and rated moderate by a works-as-designed reviewer, OpenAI GPT-5.6): the parser is deliberately "simplistic" (#8433) and does "minimal parsing" (SimpleGeoJSONPolygonParser.java:47-51), Polygon is @lucene.experimental, nothing promises a memory bound, SECURITY.md leaves limits on untrusted input to the application, the comment at :311 ("This is only used when parsing the \"features\" in type: FeatureCollection") suggests deep content elsewhere was not expected, and LUCENE-6156 (#7218) is a precedent of a maintainer refusing a guard for a recursion error on huge input.

Why it fails: the input is in the documented domain and modest (752 KB; it parses at 2 GiB); the cost comes from a private detail that buys nothing; the usual limits an application would set (about 1 MiB of input, about 1,000 levels) do not prevent it; SECURITY.md itself calls such issues "valid bug reports and hardening suggestions"; LUCENE-8964 answers the :311 comment; and #16423 is eleven years newer than LUCENE-6156. These points bear on severity and labelling, not on whether it is a defect. Verdict: not intended, a minor defect.

Suggested fix

#

Recommended Keep at most the first 21 chars of the path

Cap the path: a childPath() helper keeps at most the first 21 chars, one more than the longest constant compared (features.[].geometry), so every path test gives the same answer and memory stays linear. Validated: the repro passes, and org.apache.lucene.geo (core) gives 194 tests, 0 failures (7 nightly/awaitsfix skipped) with two seeds; the two nightly GeoJSON tessellator tests also pass.

All options and trade-offs3 options · 636 words

One fix was validated in a scratch worktree of 645d4fe14a20; the context-value alternative was not run. A depth guard (the sibling LFV-949's fix) complements it but does not fix this on its own.

Keep at most the first 21 chars of the path (validated by the checks) (recommended)

#

A childPath(path, key) helper replaces the four concatenations (:139-153, :309, :312) and keeps at most MAX_PATH_CHARS = 21 chars, one more than the longest constant compared (features.[].geometry, 20 chars). The finder's diff applies unchanged to 645d4fe14a20 (+28/-16 in SimpleGeoJSONPolygonParser.java).

static final int MAX_PATH_CHARS = 21;

/** Returns the (capped) path of a child: key == null means an array element. */
private static String childPath(String path, String key) {
  if (path.length() >= MAX_PATH_CHARS) {
    return path; // already capped; appending does not change the kept prefix
  }
  String full;
  if (key == null) {
    full = path + ".[]";
  } else if (path.length() == 0) {
    full = key;
  } else {
    full = path + "." + key;
  }
  return full.length() > MAX_PATH_CHARS ? full.substring(0, MAX_PATH_CHARS) : full;
}

Trade-offs

  • Same answers. A path of 21 chars or more equals none of the constants either way, and startsWith("crs") and isEmpty() depend only on the kept prefix. It must be 21, not 20: at 20, features.[].geometryx would be cut to features.[].geometry (the differential's cap-20 mutant shows exactly that).
  • Memory becomes at most 21 chars per level plus the keys themselves, linear in the input. A long key under a short path is still concatenated in full once and then cut (a short-lived copy, not one kept per level).
  • Cost of the shortcut: the constant is tied to the longest compared path; a future, longer constant would need the cap raised (the field's javadoc states the 20-char bound it relies on; a PR could add the features.[].geometryx reason for 21 rather than 20).

Nesting-depth guard (complement, not a fix for this)

#

The sibling LFV-949's fix throws ParseException beyond 1,000 levels, as #16423 did for expressions.

Trade-offs

Fixes the StackOverflowError sibling but not this: with only the guard, this repro and the finder's 900-level test still fail with OutOfMemoryError. Ship it together with the path cap.

Downstream note

#

Applications that build polygons from user-supplied GeoJSON cannot rely on usual request-size and nesting limits here (an input under 1 MiB and 1,000 levels still fails at 512 MiB): until a fix ships they need limits chosen for their heap budget, possibly including a key-length limit.

How it was found

#

Semi-formal. A planning probe saw the path memory grow with depth squared at 20,000 nested arrays on a 4 GB thread stack. A Z3 model of the live path strings then found the bounded-depth, long-key input, and heap bisection on the stock jar matched its predictions within 3 MiB. Independent checks confirmed it.

The method in full183 words

Method: semi-formal (an executed probe first, then a solver model that produced the witness).

  • Lead. A hunt planner, looking for siblings of the expressions-parser nesting fix #16423, probed the GeoJSON parser: OutOfMemoryError at 20,000 nested arrays (40 KB) with a 512 MiB heap and at 40,000 (80 KB) with 1 GiB, on a 4 GB thread stack, the depth-squared signal of the path strings. On a default stack the sibling StackOverflowError comes first, so that form is not reachable by default.
  • Model. A hunting unit wrote a Z3 model of the live path strings (closed-form lower bound d(75+K) + 3d(d-1)/2 bytes). Its queries found a witness at depth 1,000 or less (Q1), showed that a 1,024-level depth guard does not bound the memory (Q2), that a path-free fix does (Q3, unsat) and a vacuity check (Q4). This produced the long-key, bounded-depth input that separates it from the recursion bug.
  • Validation. Heap-threshold bisection on the stock jar matched the model (predicted 253/252/252/103 MiB, measured 255/255/255/105 MiB). The unit reduced it to a public-API JUnit, which was later minimized to the one-test repro shown here.

Hits only applications that pass GeoJSON text to Polygon.fromGeoJSON (core; Polygon is @lucene.experimental; no non-test caller in the Lucene tree) with a valid Feature whose properties combine hundreds of nesting levels with long keys: the heap need is about nesting depth x key length (d*K + 1.5*d^2 bytes), so 900 nested arrays under a 745,654-char key (747,598 chars of text) or 1,000 nested objects with 1,000-char keys (1,005,143 chars) exhaust a 512 MiB heap with OutOfMemoryError: Java heap space, roughly 500 to 1,000 times the input size, while the same text as a string value, a flat array under the long key, or 900 levels under a short key all parse; no setting is involved, ordinary request-size caps and a 1,000-level depth cap do not bound it, realistic GeoJSON (shallow, short keys) is unaffected, no wrong polygon is returned and no index is touched; thresholds depend on the collector (SerialGC bisection; G1 humongous strings need about twice as much); with -ea and -da, in every release from 6.2.0 to 10.6.0 and on main.
Summary
You call Polygon.fromGeoJSON on a valid GeoJSON Feature whose properties hold one member with a very long key (about 745,000 chars) above 900 nested arrays, or 1,000 nested objects each under a 1,000-char key (about 1 MB of text), and expect the polygon back. Instead the call fails with OutOfMemoryError: Java heap space in a 512 MiB heap, because SimpleGeoJSONPolygonParser builds a new full key path (path + "." + key, path + ".[]") for every nesting level and each recursive frame keeps its copy alive, so live memory grows with depth times path length, although the parser only ever compares the path with five short constants and a "crs" prefix. The same text as a string value, or the same nesting under a short key, parses fine, so neither a size cap nor a usual depth cap protects the caller.
