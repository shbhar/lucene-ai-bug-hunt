hasUncommittedChanges() returns false after IndexWriter applies a hard delete of an already soft-deleted document

With soft deletes, hard-deleting an already soft-deleted document is a real change that the next commit() writes. But once IndexWriter has applied that delete, for example at an NRT reader open, hasUncommittedChanges() returns false: IndexWriter only checks whether the segment's total delete count (hard plus soft) grew.

The finding in 30 seconds

#

IndexWriter records an applied delete as a change only if the segment's delete count, hard plus soft, grew. Hard-deleting a soft-deleted document moves it from the soft column to the hard column: the total stays the same, so nothing is recorded, although the next commit writes the new hard delete.

Background: soft deletes and hasUncommittedChanges()

#
  1. With setSoftDeletesField("soft"), a document is soft-deleted when it has a value in that doc-values field. Readers from the IndexWriter hide it, but it stays in its segment until a merge reclaims it; SoftDeletesRetentionMergePolicy can keep it longer, as history.
  2. You can still hard-delete such a document with deleteDocuments, for example to purge that history. It then counts as hard-deleted, no longer as soft-deleted.
  3. hasUncommittedChanges() is true when IndexWriter has recorded a change since the last commit or still buffers changes in RAM. Its javadoc allows only false positives.

The finding, step by step

#
  1. Turn on soft deletes (setSoftDeletesField("soft"), NoMergePolicy), index a and b, soft-delete a with updateDocValues(id:a, soft=1) and commit().
  2. Purge a for good: deleteDocuments(new Term("id", "a")), then DirectoryReader.open(writer), which applies the delete.
  3. You expect hasUncommittedChanges() to return true: there is a change to commit.
  4. You get false. IndexWriter compares the segment's delete count before and after: hard 0 + soft 1 = 1, then hard 1 + soft 0 = 1. It did not grow, so no change is recorded.
  5. Yet commit() writes a new commit (generation 1 to 2), and a plain reader of it sees 1 document instead of 2. An application that commits only when the method returns true skips it; after a rollback() the last commit still holds a (and, by inference, after a crash).

Who is affected

#

Only applications with soft deletes (opt-in) that purge documents already soft-deleted and still in their segment, with a delete matching nothing else. Harm needs an application that commits only when hasUncommittedChanges() is true: the purge waits for an unrelated change, and a rollback() in between (or, by inference, a crash) keeps it out of the last commit.

Mechanism, terms and numbers584 words

With a soft-deletes field configured, you can still hard-delete a document that is already soft-deleted, for example to purge retained history (IndexWriterConfig#setSoftDeletesField: "documents can still be hard-deleted. Hard-deleted documents won't be considered as soft-deleted"). When IndexWriter applies such a delete outside flush()/commit(), at an NRT reader open or when a large delete batch exceeds the RAM buffer, it decides whether anything changed only by checking whether the segment's total delete count, hard plus soft, went up (IndexWriter.java:6745, :6773). Turning one soft delete into one hard delete leaves that total unchanged (PendingSoftDeletes.java:50-66), so finishApply skips checkpoint() and hasUncommittedChanges() returns false.

The next commit() still writes the purge: a new segments_N, and a plain reader of it sees 1 document instead of 2. commit(), close() and the soft-deletes-aware search view are correct; only an application that commits only when hasUncommittedChanges() is true is hurt, and only until some other change is committed. The bug came with soft deletes in 7.4.0 (LUCENE-8233) and is in every release through 10.6.0 and main. The fix is to also count a change in the segment's hard-delete count.

It starts with a full flush, which publishes the delete packet and queues an event that applies it (publishFrozenUpdates, IndexWriter.java:2928-2947, tryApply(packet) at :2939); processEvents(false) runs that event at once (:593), before applyAllDeletesAndUpdates() (:596). A probe printed the closeSegmentStates call stack: it goes through getReader at :593, for open(w) and for open(w, false, false). Then writeReaderPool(false) (:608) writes only doc-values updates (:4122-4125). Nothing else bumps changeCount, so afterwards both terms of hasUncommittedChanges() are false.
  • Why commit() is still right: prepareCommitInternal calls writeReaderPool(true) (IndexWriter.java:3827), which writes the pending hard delete and calls checkpointNoSIS() (:4118-4121; changeCount++ at :2918). flush() does the same (:4423), so flush() in place of the NRT open leaves the method true.
  • The delete packet's own counter does see the purge: FrozenBufferedUpdates counts every rld.delete(docID) that returns true (FrozenBufferedUpdates.java:412-413, :420-421, :484-485), and PendingSoftDeletes.delete returns true here. Only the net-count check in closeSegmentStates misses it.
  • Same root, no separate claim: the NRT version is not bumped either, so openIfChanged on an NRT reader opened before the purge returns null and its isCurrent() stays true (executed). A fresh NRT reader has the same live documents and numDocs (1) as that old one, since a was already hidden; SegmentReader#getHardLiveDocs is where they differ (a set in the old reader, cleared in the fresh one).

  • Effect: a wrong false from a public method, deterministic in every single-threaded run (the 2-document cases, the 200,000-document case and the bounded enumeration). In an application that gates commit() on it, a rollback() in that window (and, by inference, a crash) leaves the purged documents in the last commit, still soft-deleted: hidden from soft-deletes-aware readers, visible to plain readers of the commit (a probe with SoftDeletesRetentionMergePolicy: commit only if hasUncommittedChanges(), then rollback(): plain numDocs 2).
  • Reach: no in-tree production code gates commits on the method (its only non-test caller is an assert in IndexUpgrader.java:203). A commit-gating pattern exists downstream (Solr's DirectUpdateHandler2#shouldCommit, apache/solr#906), but no downstream use combined with soft-delete purges was found and none is claimed. No user report was found since 7.4.0.

Why it looks unintended

#
  • The javadoc lists only false positives; here commit() does write a new commit.
  • IndexWriter counts the same purge on every other path: flush(), commit(), close() and tryDeleteDocument.
  • The "count grew" check predates soft deletes and was exact for hard deletes only; LUCENE-8233 added the net-zero soft-to-hard move without revisiting it.
The full argument212 words
  • Contract: "Returns true if there may be changes that have not been committed", followed only by false-positive cases, a delete that matches nothing and a merge after commit() (IndexWriter.java:4217-4223). Here there is a change: commit() writes a new segments_N, while a true no-op (re-deleting an already hard-deleted document) gives false and commit() returns -1 with no new generation.
  • IndexWriter counts the same purge everywhere else: flush(), commit(), close(), DirectoryReader.open(w, true, true) and tryDeleteDocument, whose changed() carries the comment "Must bump changeCount so if no other changes happened, we still commit this change" (IndexWriter.java:1700-1702, LUCENE-4521, c898b447223, 2012).
  • Soft to hard is a real state change: "If soft-deletes are enabled, documents can still be hard-deleted. Hard-deleted documents won't be considered as soft-deleted" (IndexWriterConfig.java:561-563); the retention policy keeps soft-deleted but not hard-deleted documents across merges.
  • Tests and precedent: TestIndexWriter#testHasUncommittedChanges asserts that a deleteDocuments(Term) is an uncommitted change (TestIndexWriter.java:2418-2419). LUCENE-5289 (#6353, 2013) fixed an earlier false negative for deletes ("returns false if there are pending delete by term only").
  • History: the net-count test predates soft deletes (LUCENE-6161, f5f2b285412, 2015). LUCENE-8233 (#9280, ecc17f90233, 2018) added PendingSoftDeletes with its net-zero soft-to-hard delete; none of the 15 comments on #9280 mentions change accounting.
The devil's-advocate check143 words

The strongest case for "not a bug": a soft-deleted document already "is treated as if it has been hard-deleted" (IndexWriterConfig.java:544-545), so the purge deletes nothing new; commit() is defensive and does not rely on the method (as mikemccand said on java-user@ in 2014, asking why an application would rely on it); DirectoryReader.open(IndexWriter) and SoftDeletesRetentionMergePolicy are @lucene.experimental; and the javadoc says "there may be changes", so it does not state in so many words that false means nothing to commit (that reading rests on it naming only false-positive cases, and on the tests).

Why it fails: the same javadoc says hard-deleted documents are no longer soft-deleted; IndexWriter itself commits the purge and counts it on every other path; the RAM-buffer path needs no NRT reader at all; and the defect is in the non-experimental hasUncommittedChanges(). It lowers impact, not validity.

Suggested fix

#

Recommended Also report a change when the hard-delete count moved

In IndexWriter.closeSegmentStates, also report a change when the segment's hard-delete count moved, recorded when IndexWriter starts applying the packet (5 files, +21/-1). Also report a change when the hard-delete count moved (validated by the checks) (recommended)

#

Record the hard-delete count when the SegmentState is created (BufferedUpdatesStream), add getHardDelCount() to PendingDeletes (overridden in PendingSoftDeletes to count hard deletes only) and ReadersAndUpdates, and report anyDeletes in closeSegmentStates when the total grew or the hard-delete count changed.

...

// a hard delete of a soft-deleted document does not change getDelCount():
anyHardDeletes |= segState.rld.getHardDelCount() != segState.startHardDelCount;
...
return new BufferedUpdatesStream.ApplyDeletesResult(
    totDelCount > 0 || anyHardDeletes, allDeleted);

// PendingDeletes (PendingSoftDeletes returns hardDeletes.getHardDelCount())
int getHardDelCount() {
  return info.getDelCount() + pendingDeleteCount;
}

Trade-offs

One more int per SegmentState and a second counter that must stay in step with getDelCount(). The purge now goes through checkpoint(), which also bumps the SegmentInfos version, so openIfChanged returns a new reader and isCurrent() is false (executed with the fix).

Use the delete packet's own count (not run)

#

FrozenBufferedUpdates already counts the purge (every rld.delete(docID) that returns true); forceApply could pass "term or query deletes > 0" to finishApply.

Trade-offs

More plumbing; the value apply returns also includes doc-values updates and is a running total across retry passes (FrozenBufferedUpdates.java:171-175), so it would need its own per-call counter.

Downstream note

#

Products that gate commits on hasUncommittedChanges() and purge retained soft-deleted history, for example to remove data on request, can leave the purged documents in the last commit until some other change is committed.

How it was found

#

Semi-formal: a bounded replay of soft-delete operation sequences flagged it; a bounded-exhaustive enumeration then ran every script of 1 to 5 of 9 IndexWriter operations under 4 merge-policy configurations (265,716 scripts) on the real jar, checking that a false hasUncommittedChanges() means the next commit() writes nothing: 405 broke it, all of one shape; 0 with the fix.

The method in full141 words
  • First signal: a bounded replay of soft-delete operation sequences on the real code showed an NRT reader reopen that missed a new hard delete, and flush() versus an NRT open behaving differently.
  • Enumeration: the 9 operations are a soft delete of a or b with updateDocValues, softUpdateDocument, deleteDocuments by Term, TermQuery and FieldExistsQuery(soft), an NRT open, flush() and commit(); the 4 configurations are NoMergePolicy and TieredMergePolicy, each with and without SoftDeletesRetentionMergePolicy. Oracle: hasUncommittedChanges() == false implies the next commit() writes no new segments_N. Every divergent script has the shape: soft delete, commit, hard delete of only soft-deleted documents, NRT open. Without a retention policy and with TieredMergePolicy, 0 diverge (the merge reclaims the document first).
  • Minimal repro: cut to the one-method test shown here; fails on main with assertions on and off.

History

#

Introduced with soft deletes by LUCENE-8233 (ecc17f90233, 2018-04-04), first released in 7.4.0. Fails on every release tried from 7.4.0 to 10.6.0 and on main; 7.3.1 has no soft-deletes API. Not fixed upstream.

Introduced by LUCENE-8233 "Add support for soft deletes to IndexWriter" (Simon Willnauer, s1monw; ecc17f90233 on main and its branch_7x backport 02fa5a0b059, both 2018-04-04; migrated issue #9280, reviewed on a fork pull request). LFV-1393, snapshot of 2026-11-07

Registry title
With a soft-deletes field configured, IndexWriter.hasUncommittedChanges() returns false after IndexWriter applies a deleteDocuments(Term|Query) that hard-deletes only documents that are already soft-deleted (for example at an NRT reader open), although the next commit() writes that delete (since 7.4.0)
Area
index / IndexWriter delete-apply change accounting with soft deletes (IndexWriter.closeSegmentStates / finishApply, PendingSoftDeletes.delete, PendingDeletes.getDelCount)
Priority
Low, rank 757: In every release since 7.4.0 with the opt-in soft-deletes field, hasUncommittedChanges() deterministically returns false once an NRT reader open or a large delete batch applies a delete that only hard-deletes already soft-deleted documents. commit() and close() still write that delete and searches do not change, so the only harm is to an application that commits only when the method returns true and then crashes or rolls back before another change: the purged documents stay in the last commit as soft-deleted documents.
Impact class
minor
Impact note
Hits only applications that set a soft-deletes field (opt-in) and purge documents that are already soft-deleted and still in their segment (kept by SoftDeletesRetentionMergePolicy, or not merged away yet) with a deleteDocuments(Term|Query) that matches only such documents, when IndexWriter applies that delete outside flush()/commit() (an NRT reader open, or a delete batch larger than the RAM buffer); it is deterministic at any index size, but the visible harm needs an application that commits only when hasUncommittedChanges() is true: the purge then stays uncommitted until some other change, and a crash or rollback in that window leaves the purged documents in the last commit as soft-deleted documents; commit() and close() themselves are correct, and the soft-deletes-aware search view does not change.
Summary
You configure a soft-deletes field, soft-delete document a (updateDocValues on the soft-deletes field), commit, then hard-delete a with deleteDocuments(new Term("id", "a")) and open a near-real-time reader with DirectoryReader.open(writer), which applies the delete. You expect hasUncommittedChanges() to return true, because the next commit() does write that delete (a new segments_N in which a is hard-deleted; a plain reader's numDocs goes from 2 to 1) and the javadoc allows only false positives. Instead it returns false: when IndexWriter applies the delete it only checks whether the segment's total delete count (hard plus soft) grew, and turning a soft delete into a hard delete leaves that total unchanged, so the change is never counted.
