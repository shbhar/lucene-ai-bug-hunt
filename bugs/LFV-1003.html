AnalyzingSuggester: num x analyzed forms overflows an int, so with synonyms a large num silently returns fewer suggestions

With a synonym analyzer, AnalyzingSuggester and FuzzySuggester size their search queue as num x the most analyzed forms of any entry, in an int. With 3 forms, lookup("a", false, 1431655766) wraps that queue to 2 paths and silently returns 2 of the 3 matches; other values throw NoSuchElementException.

The finding in 30 seconds

#

The suggester caps its FST search queue at num x k, where k is the most analyzed forms of any entry (3 when ab also indexes as x and y). The product is an int, so past Integer.MAX_VALUE it wraps: to a small cap that drops wanted paths, to 0, which throws, or below 0, which fails the completeness assert.

Background: how AnalyzingSuggester finds its suggestions

#
  1. At build time each entry goes through your index-time analyzer, and every analyzed form is stored in a weighted FST that maps the form to the entry.
  2. A synonym analyzer can give one entry several forms (ab, x, y); the suggester remembers the largest count of any entry, k.
  3. A lookup walks the FST best-first with a capped queue of candidate paths. Since one suggestion can appear once per form, the cap is num x k, so no wanted suggestion can be squeezed out.

The finding, step by step

#
  1. Build an AnalyzingSuggester from ab (weight 1), ac (2) and ad (3) with a synonym analyzer that also indexes ab as x and y, so ab has 3 analyzed forms. Call lookup("a", false, 1431655766): num is documented only as the "maximum number of results to return".
  2. You expect all three, [ad, ac, ab], as num = 100 returns.
  3. Instead you get [ad, ac], with no error. The FST search keeps num x 3 candidate paths, room for every form of each wanted suggestion, but multiplies in an int: 1,431,655,766 x 3 = 4,294,967,298 = 2^32 + 2, which wraps to 2, so the search throws away paths it still needs.
  4. Other values wrap to 0 and throw NoSuchElementException: num = 2^30 with 4 forms, or num = 65,536 when one 16-word entry has a synonym per word (2^16 forms). With assertions on, the class's own assert completions.isComplete fails, typically also at Integer.MAX_VALUE, where production results are right.
  5. It is in every release since 4.1.0 (2013), in 10.6.0 and main; FuzzySuggester inherits it. One-form analyzers and ordinary num values are not affected.

Who is affected

#

Applications whose suggester analyzer gives some entry 2 or more forms (synonyms, a token graph) and that pass a num above Integer.MAX_VALUE / k. Default constructor arguments; three entries suffice. A short list needs num in a narrow window, and Integer.MAX_VALUE is right in production, so it is contrived; one-form analyzers are not affected.

Mechanism, terms and numbers811 words

AnalyzingSuggester (and FuzzySuggester, which inherits lookup) finds the top num completions with a best-first search over its FST, Util.TopNSearcher, whose candidate queue is capped at maxQueueDepth. When the index-time analyzer turns one entry into several analyzed forms (synonyms or any token graph), a suggestion can be reached once per form, so the class sizes the queue as num * maxAnalyzedPathsForOneInput, the largest number of forms of any one entry: in Michael McCandless's words on LUCENE-4481 (#5547), "topN * M where M is the max number of analyzed forms we ever saw for any surface form". That product is a plain int (AnalyzingSuggester.java:786 on main 645d4fe14a20), and num is documented only as the "maximum number of results to return". With three entries and 3 forms on one of them, lookup("a", false, 1431655766) wraps the depth to 2 and silently returns 2 of the 3 matches; with the finder's 8 entries the same num returns 3 of 8 and skips three higher-weighted ones. A depth that wraps to 0 throws NoSuchElementException (num = 2^30 with 4 forms, or num = 65,536 with one 2^16-form entry), and a negative one keeps results right but fails the class's own assert completions.isComplete, typically at Integer.MAX_VALUE. The product is in every release from 4.1.0 to 10.6.0 and main. Multiplying in long and saturating at Integer.MAX_VALUE fixes it, validated with gradle on 645d4fe14a20.

The bug (main 645d4fe14a20)

#
  1. Contract. Lookup.lookup(key, onlyMorePopular, num): "@param num maximum number of results to return" (Lookup.java:190). AnalyzingSuggester.lookup checks only assert num > 0 (AnalyzingSuggester.java:670). Both classes are @lucene.experimental (:98; FuzzySuggester.java:64); FuzzySuggester extends AnalyzingSuggester and does not override lookup (FuzzySuggester.java:66).
  2. Graph analyzers are supported. "If SynonymFilter is used to map wifi and wireless network to hotspot then the partial text "wirele..." could suggest "wifi router"" (AnalyzingSuggester.java:78-79); "At index time, complex analyzers can safely be used" (FuzzySuggester.java:59-62). The 3- and 4-argument constructors pass maxGraphExpansions = -1, "no limit" (AnalyzingSuggester.java:170-195, :207-208; FuzzySuggester.java:98-127).
  3. The path count. "Highest number of analyzed paths we saw for any single input surface form" (AnalyzingSuggester.java:153-157), set by build as Math.max(maxAnalyzedPathsForOneInput, finiteStrings.size()) (:484) and stored with the suggester (:607, :618).
  4. The product, in int. new Util.TopNSearcher<>(fst, num - results.size(), num * maxAnalyzedPathsForOneInput, weightComparator) (:783-786). Java int arithmetic wraps modulo 2^32: 1,431,655,766 x 3 = 4,294,967,298 is 2; 1,073,741,824 x 4 = 2^32 is 0; 2,147,483,647 x 2 is -2.
  5. Small positive depth. TopNSearcher keeps at most maxQueueDepth paths ("the maximum size of the queue of possible top entries", Util.java:186): once full, a new path that does not beat the worst is dropped, else it is added and the worst removed (Util.java:215-249). With room for 2, paths whose completions belong in the result are dropped and lookup returns what is left.
  6. Depth 0. The first addIfCompetitive sees queue.size() == maxQueueDepth (0 == 0) and calls queue.last() on the empty TreeSet (Util.java:215-216): NoSuchElementException.
  7. Negative depth. The queue size never equals it, so nothing is pruned and the results are right; but search() returns isComplete = rejectCount + topN <= maxQueueDepth (Util.java:409), false, and AnalyzingSuggester.java:823-824 asserts it. If the search rejects a duplicate path, rejectCount + topN overflows too and the check passes, so the assert fires typically, not always.

Exposure and likelihood289 words
  • Who is hit. Callers of AnalyzingSuggester.lookup or FuzzySuggester.lookup whose index-time analyzer gives some entry 2 or more analyzed forms, with a num above Integer.MAX_VALUE / k. One-form analyzers (k = 1) and ordinary counts are not affected. No large dictionary is needed: three entries are enough for the short list.
  • Default or opt-in. Default constructor arguments (including maxGraphExpansions = -1, no limit); the graph analyzer is the application's choice, but a documented use of the class.
  • What goes wrong. In production: at specific values, a silently incomplete list that can skip higher-weighted suggestions, or a NoSuchElementException from inside the FST search. With assertions on (tests): the class's own completeness assert, also at Integer.MAX_VALUE, the value Lucene's own TestFSTCompletion passes to mean "all results" on the separate FSTCompletion API (TestFSTCompletion.java:157, :165).
  • Scale. Normally num must be in the hundreds of millions to billions. But k has no default limit: one 16-word entry with one synonym per word has 2^16 forms, and num = 65,536 then throws in production.
  • Workaround. Pass a finite num no larger than Integer.MAX_VALUE / k (in practice no more than getCount(), which for a graph analyzer counts analyzed paths, not entries, the hunt's LFV-431: the repro's 3 entries give getCount() = 5, so it is still a safe upper bound on the results), or bound k with maxGraphExpansions.
  • How likely: contrived for the short list (registry likelihood contrived, priority low): with 3 forms the wrapped depth is 3 x num - 2^32, so a list is short only for num within about (paths needed) / 3 of 1,431,655,766, and the natural Integer.MAX_VALUE is right in production. The NoSuchElementException leg is merely rare. No public report since 4.1.0 (2013).

Why it looks unintended

#
  • num is the "maximum number of results to return" (Lookup.java:190); nothing bounds it.
  • The cap is meant as a sound bound, "topN * M where M is the max number of analyzed forms" (Michael McCandless, LUCENE-4481); the class asserts its search was complete.
  • A queue depth too small for the data was treated as a bug here before (LUCENE-4533).
The full argument372 words
  • Contract. num is a maximum (Lookup.java:190); nothing bounds it or says it is multiplied.
  • An admissible bound, by design. On LUCENE-4481 (#5547) Michael McCandless found the earlier topN-sized queue unsound for token graphs and planned to "bound the queue using topN * M where M is the max number of analyzed forms we ever saw for any surface form". A wrapped product is no longer that bound. Util.java:465-466 states the rule for shortestPaths: "All paths are kept, so we can pass topN for maxQueueDepth and the pruning is admissible".
  • The completeness assert is deliberate. On LUCENE-5519 (#6582) Robert Muir proposed returning a boolean saying whether the top-N is complete; Michael McCandless asked that callers "do the assert on that returned boolean; else, it means there's a serious bug (the search pruning is not admissible)" and suggested the name isComplete; Simon Willnauer implemented and committed it (803a9907d39, 4.8.0). That is the assert at AnalyzingSuggester.java:824 that fires here. LUCENE-5519 itself was opened to make depth enforcement optional for callers that accept an inexact top N (Simon Willnauer: "I am ok with a top N that is not 100% exact"; Robert Muir: "the current assert is bogus"). AnalyzingSuggester is not such a caller: the same commit gave it assert completions.isComplete (:755, :824), while NRTSuggester, which does accept an inexact bound, says "search admissibility is not guaranteed" and leaves the assert commented out (NRTSuggester.java:257-259).
  • Precedent: a too-small depth was a bug. LUCENE-4533 (#5599, 2012), "if you pass dups (same surface form) to AnalyzingSuggester it can fail to return enough results": Michael McCandless's failing test "trips the assert in TopNSearcher that detects a too-small maxQueueDepth", and it was fixed.
  • The neighbouring product is guarded. The document suggester computes topN * (long) maxAnalyzedPathsPerOutput and clamps it with Math.min (NRTSuggester.java:294, :301). Reviewing that code (LUCENE-6339, #7400), Michael McCandless asked whether it "could possibly overflow int? Maybe use long, and then cast back to int after the Math.min?"; the long multiplication now there came from Robert Muir's error-prone "narrow calculation" change (#11923).
  • Tests. TestAnalyzingSuggester and TestFuzzySuggester use graph analyzers (for example testGraphDups) but only small num values; no test, javadoc or CHANGES entry accepts the wrap.
The devil's-advocate check173 words

The strongest "works as designed" case (first raised by the refute-lens reviewer from another model family, OpenAI GPT-5.6, then argued in full by the devil's advocate): no autosuggest UI asks for a billion suggestions; both classes are @lucene.experimental; maxGraphExpansions exists to bound k; TopNSearcher deliberately supports bounded queues that may give an inexact top N (LUCENE-5519); and at Integer.MAX_VALUE production results are right, so only a test-time assert fires.

Why it fails: that bears on likelihood and priority, not on correctness. No doc bounds num; the depth is meant to be a sound bound and the class asserts that it is (the inexact mode is for callers such as NRTSuggester that say so, not for AnalyzingSuggester); with the default maxGraphExpansions one heavily expanded entry makes num = 65,536 throw; @lucene.experimental is about API stability. The adjudication (confirmed, high confidence, priority low), the independent reproducer, the intended-lens reviewer and the devil's advocate treat it as a real defect; the refute-lens review's "not real" (low) was procedural, as it could not run Java.

Suggested fix

#

Recommended Multiply in long and saturate at Integer.MAX_VALUE

Compute num x k in long and saturate it at Integer.MAX_VALUE before passing it as the queue depth (+5/-2 in AnalyzingSuggester.lookup), the pattern the document suggester already uses. Validated with gradle: the repro, TestAnalyzingSuggester, TestFuzzySuggester, the whole suggest module (237 tests) and check pass, with assertions on and off.

// AnalyzingSuggester.lookup, before the main TopNSearcher (line 783):
// Multiply in long and saturate: in int, num * maxAnalyzedPathsForOneInput wraps for a large
// num, and a wrapped queue depth makes the pruning inadmissible
int maxQueueDepth =
    (int) Math.min((long) num * maxAnalyzedPathsForOneInput, Integer.MAX_VALUE);
Util.TopNSearcher<Pair<Long, BytesRef>> searcher;
searcher =
    new Util.TopNSearcher<>(fst, num - results.size(), maxQueueDepth, weightComparator) {
All options and trade-offs3 options · 607 words

One fix was built and validated; two alternatives were considered and not built, and one caveat concerns TopNSearcher itself.

Multiply in long and saturate at Integer.MAX_VALUE (validated by the checks) (recommended)

#

Below Integer.MAX_VALUE / k nothing changes. Above it the depth is Integer.MAX_VALUE, a queue the search never fills, so it prunes nothing: what a negative wrap already does in production today, and admissible. isComplete (rejectCount + topN <= Integer.MAX_VALUE) is then true. It mirrors the document suggester's queue size (NRTSuggester.java:294, :301: a long product clamped with Math.min), the shape Michael McCandless suggested for that product on LUCENE-6339 (#7400): "use long, and then cast back to int after the Math.min".

// AnalyzingSuggester.lookup, before the main TopNSearcher (line 783):
// Multiply in long and saturate: in int, num * maxAnalyzedPathsForOneInput wraps for a large
// num, and a wrapped queue depth makes the pruning inadmissible
int maxQueueDepth =
    (int) Math.min((long) num * maxAnalyzedPathsForOneInput, Integer.MAX_VALUE);
Util.TopNSearcher<Pair<Long, BytesRef>> searcher;
searcher =
    new Util.TopNSearcher<>(fst, num - results.size(), maxQueueDepth, weightComparator) {

Trade-offs

  • No pruning above the threshold. For such a num the search keeps every candidate path, like an unbounded search; that is the cost of a correct answer for a huge num and the same as today's negative-wrap case. It does not make huge result counts cheap.
  • The completeness sum. Util.java:409 adds rejectCount + topN in int too (a remark of the devil's advocate). With the saturated depth the flag comes out right; switching that sum to long as well would, with topN and the depth both at Integer.MAX_VALUE, report "incomplete" after one rejected duplicate although nothing was pruned (arithmetic, not executed). Changing TopNSearcher alone does not fix this bug, since the wrap happens in the caller; nor is the clamp the only possible fix.
  • The exact-first searcher (AnalyzingSuggester.java:729-735) has a similar int product, count * maxSurfaceFormsPerAnalyzedForm, which needs about 8.4 million exact-match prefix paths to wrap; a patch could saturate it too.

Fail loudly with Math.multiplyExact (not built)

#

Throw ArithmeticException instead of returning a short list.

Trade-offs

Honest, but it rejects a legal request (num is only a maximum) that the saturating fix answers correctly.

Clamp num to getCount() first (not built)

#

num = (int) Math.min(num, getCount()) before sizing the search: no more than count suggestions can come back (duplicate surface forms are removed by the searcher's seen set). count is at least the number of entries; for a graph analyzer it counts analyzed paths (AnalyzingSuggester.java:419, :590, the hunt's LFV-431), so it is still a safe upper bound on the results.

Trade-offs

Keeps the depth small for small dictionaries, but count * k can still overflow for a large dictionary with many forms, so it still needs the long product; best as an addition to the saturating fix.

Downstream note

#

Solr passes the request parameter suggest.count unchanged to lookup as num, and its Analyzing and Fuzzy lookup factories default maxGraphExpansions to -1, so a Solr deployment with a synonym-expanded dictionary has to bound suggest.count itself.

How it was found

#

A numeric-limits probe ran every suggester with growing num and flagged this class: with a 2-form synonym analyzer, num = Integer.MAX_VALUE failed its completeness assert. A 32-bit SMT model of the product then found the values that fail in production (1,431,655,766 with 3 forms, 2^30 with 4), and each was executed on the stock jars.

The method in full197 words

Method: non-formal first signal, then a small formal model (a hunt unit for suggester num sizes, 2026-10-28, main a9779ef3c193).

  • First signal. A differential probe ran the Lookup implementations at growing num on the stock main jars: AnalyzingSuggester with a 2-form synonym analyzer threw AssertionError at Integer.MAX_VALUE with assertions on, where num = 1000 returns 8; with assertions off it returned the right 8.
  • Model. A Z3 32-bit bit-vector model of the queue-depth product found the production-mode witnesses the probe had not shown: the smallest num with a wrapped depth between 0 and topN is 1,431,655,766 for 3 forms (depth 2) and 2^30 for 4 forms (depth 0), and none exists for 2 forms; it proved that num = Integer.MAX_VALUE makes isComplete false for every k from 2 to 2^20 with no rejected path. An exhaustive count over every num followed.
  • Execution. Each witness ran on the stock jars, then became a JUnit; a probe over 1-4 forms x 14 num values on both suggesters failed only where the model predicted. An independent verifier later found a moderate trigger: one entry with 2^16 forms and num = 65,536. The minimal-repro step reduced it all to one method.

LFV-1003, snapshot of 2026-11-03

Registry title
AnalyzingSuggester and FuzzySuggester compute the top-N queue depth num * maxAnalyzedPathsForOneInput in int, so with a synonym (token graph) analyzer a large num wraps it: lookup silently returns too few suggestions and skips higher-weighted ones, or throws NoSuchElementException, and with assertions on lookup(key, false, Integer.MAX_VALUE) typically fails 'assert completions.isComplete'
Area
suggest / analyzing: AnalyzingSuggester and FuzzySuggester lookup (FST top-N queue depth)
Priority
Low, rank 833: The analyzing and fuzzy suggesters' queue-depth int overflow only gives a silent short list for contrived num values near 2^32/k with a token-graph analyzer, while the natural Integer.MAX_VALUE works in production and only trips an -ea assertion, so it is weaker than LFV-387's MAX_VALUE silent drop.
Impact class
silent wrong results
Impact note
Applications that build an AnalyzingSuggester or FuzzySuggester with an index-time analyzer that gives some entry two or more analyzed paths (synonyms or another token graph) and call lookup with a num above Integer.MAX_VALUE / maxAnalyzedPathsForOneInput are exposed: in production (-da) only specific num values fail, with a silently short list (num 1431655766 with 3 paths returns 3 of 8) or a NoSuchElementException (when the product is a multiple of 2^32: num 2^30 with 4 paths, or num 65536 with one 2^16-path entry), while the natural 'all results' value Integer.MAX_VALUE returns the right list and only trips the class's own assertion under -ea; one-path analyzers and ordinary num values are not affected, and no large dictionary is needed.
Summary
You build an AnalyzingSuggester (or FuzzySuggester) whose index-time analyzer expands one entry into several analyzed forms, for example a SynonymGraphFilter that also indexes 'lucene' as 'search' and 'find', and call lookup("luc", false, num) with a large num; num is documented as the 'maximum number of results to return', so you expect the 8 suggestions that num = 1000 returns. Instead the search's queue depth num * maxAnalyzedPathsForOneInput is computed in int (AnalyzingSuggester.java:786) and wraps: with 3 paths and num = 1431655766 it becomes 2, the top-N search prunes paths it still needs, and lookup returns [lucas, lucifer, lucid] with no error, skipping the higher-weighted luck, lucent and lucerne (FuzzySuggester: 5 of 8), and with 4 paths and num = 2^30 it becomes 0 and lookup throws NoSuchElementException. With assertions enabled, lookup(key, false, Integer.MAX_VALUE) on a suggester with 2 or more paths typically fails 'assert completions.isComplete' (:824), although the same call without assertions returns the right list.
