hasUncommittedChanges() and NRT isCurrent() can briefly miss an acknowledged empty-block delete during a concurrent full flush

If an empty-block updateDocuments delete finishes while a concurrent commit or NRT open is swapping delete queues, hasUncommittedChanges() briefly returns false and an older NRT reader briefly says it is current. Nothing is lost; by code reading every release since 4.5.0 has it.

The finding in 30 seconds

#

hasUncommittedChanges() and NRT isCurrent() both ask DocumentsWriter.anyChanges(). During a full flush, a delete can land in the old delete queue after the flush noted "no changes" and before it hands that queue on. For that gap anyChanges() looks everywhere except there.

How IndexWriter tracks pending changes, in one minute

#
  1. Indexing threads work through pooled per-thread writers. Each writer is bound to the delete queue that was current when it was taken, and its deletes go into that queue.
  2. A commit or an NRT open runs a full flush: it notes whether anything is pending (pendingChangesInCurrentFullFlush), swaps in a fresh delete queue, waits for the writers of the old queue, drops empty ones, and finally turns the old queue's deletes into a "ticket" that is applied to the index.
  3. anyChanges() answers "is anything pending?" from four places: buffered documents, the current delete queue, the ticket queue and the noted flag.

The finding, step by step

#
  1. One document id:1 is committed. During that commit an empty addDocuments(List.of()) ran, which leaves a pooled per-thread writer holding 0 documents. hasUncommittedChanges() is false, as it should be.
  2. Thread U deletes the document with updateDocuments(new TermQuery(id:1), List.of()). While U is inside the call, the main thread opens an NRT reader. Its full flush first notes "no pending changes", then swaps in a fresh delete queue. U's delete lands in the old queue and U returns sequence number 5.
  3. You expect hasUncommittedChanges() to be true from now on: the delete is acknowledged and not committed, and the javadoc names only false positives as exceptions.
  4. Instead it is false until the flush hands the old queue on as a "ticket": DocumentsWriter.anyChanges() checks the document count (0 for an empty block), the new queue, the tickets and the flag noted before the swap, and none shows the delete. An NRT reader opened earlier says isCurrent() true in the same gap.
  5. A moment later the answer is true again, the new reader has the delete applied (numDocs 0) and the next commit persists it.

Who is affected

#

Applications that delete with an empty block (updateDocuments(term or query, List.of())) while other threads commit or refresh NRT readers. A caller that commits only when hasUncommittedChanges() is true skips one commit; an NRT refresher skips one refresh. No data is lost, and the answer is right again once the flush adds its ticket. Contrived: priority Low.

Mechanism, terms and numbers677 words

A commit or an NRT reader open runs a full flush. DocumentsWriter.flushAllThreads first records pendingChangesInCurrentFullFlush = anyChanges() (DocumentsWriter.java:675), then markForFullFlush swaps in a fresh delete queue (:680) and waits for the per-thread writers bound to the old one. A thread that already holds such a writer still adds its delete to the writer's own, now swapped-out queue (DocumentsWriterPerThread.java:374-378) and returns its sequence number. anyChanges() reads only the buffered document count, the new queue (:376-378), the ticket queue and the flag (:352-356). After an empty-block updateDocuments none of them shows the delete, and reusing a pooled writer does not bump changeCount either, so hasUncommittedChanges() (IndexWriter.java:4224-4231) returns false and nrtIsCurrent() (:6139-6145) reports an older NRT reader as current, until the flush turns the old queue into a ticket (DocumentsWriter.java:691-698). The flush in progress applies the delete and the answer is right again once it adds its ticket, so no data is lost. It takes an empty-block call during an earlier full flush (in the repro an InfoStream hook makes it on the committing thread), an empty-block delete that straddles a later full flush's queue swap, and a status call in the gap: contrived, priority Low. By code reading present in every release from 4.5.0 (4.5.1 for hasUncommittedChanges()) through 10.6.0 and on main; letting anyChanges() also check the swapped-out queue while the full flush runs fixes it.

Step by step

#
  1. U's updateDocuments takes the pooled 0-document per-thread writer, still bound to the current queue (DocumentsWriterFlushControl.java:538-549), and starts consuming its empty block.
  2. The NRT open computes the flag (false) and swaps the queue. markForFullFlush then waits for every writer bound to the old queue (DocumentsWriterFlushControl.java:592-594) and drops a 0-document one (:608-612).
  3. U finishes its block: finishDocuments adds the delete to the writer's own queue, the swapped-out one (DocumentsWriterPerThread.java:374-378), and U returns sequence number 5.
  4. Now anyChanges() is false: no document was buffered, the new queue is empty, there is no ticket and the flag was computed before the delete existed. changeCount did not move either, because reusing a pooled writer allocates no new segment name (IndexWriter.java:2169-2181 bumps it only for a new writer). So hasUncommittedChanges() and nrtIsCurrent() both report no change.
  5. The gap closes at addTicket (:698), which counts the ticket before freezing the queue because "freeze opens a window for #anyChanges to fail" (DocumentsWriterFlushQueue.java:38-40).

Why the pooled 0-document writer matters

#

A fresh writer would bump changeCount and hide the gap. A 0-document writer stays in the pool only if an empty-block call ran during an earlier full flush, after its swap; a 0-document writer created outside a full flush is dropped by the next one (DocumentsWriterFlushControl.java:608-612). In the repro that earlier call is the addDocuments(List.of()) at the commit's "now apply all deletes" step (IndexWriter.java:4443-4446), which runs before the commit records its change count (:3851).

The numbers

Exposure and likelihood256 words
  • Who is hit. Applications that delete through the block API with an empty block (updateDocuments(term or query, List.of()); by reading also softUpdateDocuments) while other threads commit or refresh NRT readers. A caller that commits only when hasUncommittedChanges() is true skips one commit until its next poll. An NRT refresher sees "no change" once: in a supporting probe, a reader opened before the delete reported isCurrent() true and openIfChanged() returned null inside the gap while it still showed the deleted document; after the flush isCurrent() was false and the new reader had numDocs 0 (main, assertions on and off). In that probe hasUncommittedChanges() was already true for an earlier, unrelated change, so only the reader-side symptom shows there.
  • Default vs opt-in. No writer options besides the InfoStream (new IndexWriterConfig(); the test framework still picks a random codec, and the code involved does not depend on it); assertions on or off make no difference. The block APIs are @lucene.experimental and have no non-empty precondition.
  • Effect. A transient wrong answer, no data loss: the full flush in progress applies the delete and the next commit persists it.
  • Scale. None: one document, two empty blocks.
  • Likelihood: contrived. It needs an earlier empty-block call inside a previous full flush (to leave the pooled 0-document writer), a second empty-block call that straddles another flush's queue swap, and a status call in the gap before that flush adds its ticket. No public report was found (see prior reports). Whether any downstream project issues empty-block updates was not checked.

Why it looks unintended

#
  • hasUncommittedChanges()'s javadoc names only false positives; an NRT reader's isCurrent() must see "any new uncommitted changes".
  • The code says the gap must not exist: the flag is there because "NRT Readers otherwise suddenly return true from isCurrent while there are actually changes".
  • Upstream fixed earlier gaps of this kind as bugs: LUCENE-3551 (#4625), LUCENE-5289 (#6353), LUCENE-10190 (#640).
The full argument261 words
  • The contract names only false positives. hasUncommittedChanges(): "Returns true if there may be changes that have not been committed. There are cases where this may return true when there are no actual "real" changes ..." (IndexWriter.java:4217-4223). IndexWriter instances "are completely thread safe" (:167). For NRT readers isCurrent() "checks if either a new commit has occurred, or any new uncommitted changes have taken place via the writer" (DirectoryReader.java:631-634), and openIfChanged(reader, writer) returns a reader with "all changes made so far by this IndexWriter instance, or null if there are no new changes" (:334-335).
  • The code states the no-gap intent. The flag exists because "NRT Readers otherwise suddenly return true from isCurrent while there are actually changes ..." (DocumentsWriter.java:97-103); anyChanges() checks the ticket queue because changes can sit there during a flush (:345-351); addTicket counts the ticket before freezing because "freeze opens a window for #anyChanges to fail" (DocumentsWriterFlushQueue.java:39).
  • Upstream fixed windows of this family as bugs. LUCENE-3546 (#4620, 2011), LUCENE-3551 (#4625, 2011, Simon Willnauer: added the flag, computed before the swap, commit 73dec384b40), LUCENE-5289 (#6353, 2013: a sequential hasUncommittedChanges() false negative; its reporter noted that Solr's replication depends on the method) and LUCENE-10190 (#11227 / PR #640, 2022, Nhat Nguyen: "Ensure changes are visible before advancing seqno", another anyChanges() false negative after a sequence number was handed out).
  • No test, CHANGES/MIGRATE entry or discussion accepts this gap. TestIndexWriter.testHasUncommittedChanges (TestIndexWriter.java:2385) and TestIndexWriterNRTIsCurrent assert the documented contract; neither covers a delete added to the swapped-out queue.
The devil's-advocate check202 words

The argument: the predicate is advisory ("may") and is not documented as an atomic snapshot under concurrent calls, the block APIs are @lucene.experimental, the delete already belongs to the flush in progress, the answer is right again a moment later, and the repro reaches the gap only through InfoStream hooks, one of which makes the first empty-block call on the committing thread, from inside its own commit.

Why it fails: the hedge covers only false positives; the code comments above say the gap must not exist; a sequence number was returned while anyChanges() was false, which is exactly what LUCENE-10190 fixed; the reader-side contract (isCurrent / openIfChanged) breaks in the same gap; and each hook either parks a thread or makes a public IndexWriter call that another application thread could make at that moment, at a point the threads pass anyway (the independent test and the isCurrent() probe make the empty addDocuments from a separate thread). Upstream's TestIndexWriter.testEnsureMaxSeqNoIsAccurateDuringFlush (TestIndexWriter.java:4442) also fixes a flush schedule by parking a thread in an InfoStream callback. An executed review by another model family (OpenAI GPT-5.6) rated this counter "moderate": it bears on priority, not on whether the answer is wrong.

Suggested fix

#

Recommended A: anyChanges() also checks the swapped-out queue while the full flush runs

Keep the queue a running full flush has swapped out in a volatile field (set before the swap, cleared in finishFullFlush), and let anyChanges() also return true when that queue has changes. Validated: the repro passes with assertions on and off; the whole org.apache.lucene.index test package (1398 tests) and :lucene:core:check -x test pass.

private volatile DocumentsWriterDeleteQueue fullFlushDeleteQueue; // swapped-out queue, else null

boolean anyChanges() {
  ... || pendingChangesInCurrentFullFlush
      || anyFullFlushDeletions();
}

private boolean anyFullFlushDeletions() {
  final DocumentsWriterDeleteQueue queue = fullFlushDeleteQueue;
  return queue != null && queue.anyChanges();
}
// flushAllThreads(), before markForFullFlush():  fullFlushDeleteQueue = flushingDeleteQueue;
// finishFullFlush(), in the finally block:       fullFlushDeleteQueue = null;
All options and trade-offs2 options · 444 words

Validated with gradle in a clean scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-03): the repro fails stock with assertions on and off, and passes with fix A, on and off. With fix A and the repro in place, :lucene:core:test --tests 'org.apache.lucene.index.*' passes (1398 tests, 0 failures, 56 skipped, in 215 test classes: 214 per-class reports plus TestClassloadingDeadlock, which gradle reports in its run-level report) and so does :lucene:core:check -x test.

Why fix A closes the gap: the field is set before the swap, so a delete added to the old queue is visible to DocumentsWriterDeleteQueue.anyChanges() from the moment it is added; the old queue is emptied only by a freeze inside addTicket (DocumentsWriter.java:180, :535-536, :698), which counts the ticket first (DocumentsWriterFlushQueue.java:39-40); and the field is cleared in finishFullFlush, after the ticket queue holds or has published the changes. anyChanges() on the closed old queue does not throw (DocumentsWriterDeleteQueue.java:181-196). This is reasoning from the source plus the test runs above; no stress, deadlock or performance run was made.

A: anyChanges() also checks the swapped-out queue while the full flush runs (validated by the checks) (recommended)

#

In DocumentsWriter, add private volatile DocumentsWriterDeleteQueue fullFlushDeleteQueue; set it to the old queue in flushAllThreads just before markForFullFlush, clear it in finishFullFlush's finally, and add || anyFullFlushDeletions() to anyChanges(). 15 lines added and 1 removed, DocumentsWriter.java only.

private volatile DocumentsWriterDeleteQueue fullFlushDeleteQueue; // swapped-out queue, else null

boolean anyChanges() {
  ... || pendingChangesInCurrentFullFlush
      || anyFullFlushDeletions();
}

private boolean anyFullFlushDeletions() {
  final DocumentsWriterDeleteQueue queue = fullFlushDeleteQueue;
  return queue != null && queue.anyChanges();
}
// flushAllThreads(), before markForFullFlush():  fullFlushDeleteQueue = flushingDeleteQueue;
// finishFullFlush(), in the finally block:       fullFlushDeleteQueue = null;

Trade-offs

One more volatile read per call and, only while a full flush runs, one lock on the old queue. anyChanges() is called only by hasUncommittedChanges(), nrtIsCurrent() and flushAllThreads itself, so nothing else changes behaviour. Not stress- or performance-tested.

B (not recommended, not run): recompute the flag after markForFullFlush returns

After markForFullFlush, set pendingChangesInCurrentFullFlush |= flushingDeleteQueue.anyChanges().

Trade-offs

Smaller, but it leaves a narrower gap: U's call returns as soon as U releases its writer, which can be before markForFullFlush returns and the flag is recomputed. The repro would not see that residual gap, because it reads at a later step.

Downstream note

#

Products that gate commits or replication on hasUncommittedChanges(), or refresh searchers on isCurrent(), can skip one commit or refresh when they delete with empty blocks during concurrent flushes; a poll after the flush adds its ticket gets the right answer.

How it was found

#

A proof-obligation audit of DocumentsWriter.anyChanges() took its contract (true while an acknowledged change is still pending) as an obligation at every point of a full flush. The point after the queue swap and before the old queue's ticket does not meet it for a delete added to the old queue. A one-test JUnit witnessed it on main.

The method in full160 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: after an operation has returned its sequence number and before a commit, anyChanges() (and with it hasUncommittedChanges() and nrtIsCurrent()) is true. Walking flushAllThreads step by step, the flag is computed before the swap, the old queue can still receive a delete from a writer taken before the swap, and anyChanges() reads only the new queue until addTicket.
  • A one-test JUnit fixed that schedule and failed on main with assertions on and off; a probe printed DocumentsWriter.anyChanges() = false in the gap. An independent reproducer wrote its own test (it makes the first empty addDocuments from a separate thread) and a probe of the isCurrent() / openIfChanged() symptom; an executed review by another model family (OpenAI GPT-5.6) wrote its own test plus a sequential control; a devil's-advocate verifier and an adjudication re-ran the tests and the fix.

LFV-1264, snapshot of 2026-11-04

Registry title
IndexWriter.hasUncommittedChanges() and NRT isCurrent()/openIfChanged() can briefly report no changes for an acknowledged empty-block updateDocuments delete that lands in the delete queue a concurrent full flush has just swapped out, because DocumentsWriter.anyChanges() reads only the new queue until that flush adds its ticket
Area
index / IndexWriter full flush (DocumentsWriter uncommitted-change tracking)
Priority
Low, rank 725: IndexWriter's hasUncommittedChanges() and NRT isCurrent()/openIfChanged() may briefly miss an acknowledged empty-block delete that lands in a delete queue a concurrent full flush has just swapped out, in every release since 4.5.0. It needs the experimental empty-block delete, a pooled empty per-thread writer and a status call inside a short window, no data is lost and the next poll repairs it, so it is contrived.
Impact class
minor
Impact note
Only applications that delete through the @lucene.experimental block API with an empty block (updateDocuments(term or query, List.of()) [exec], or softUpdateDocuments [read]) while other threads commit or open NRT readers are hit, and only when that call runs on a pooled per-thread writer with 0 documents (left by an earlier empty-block call during a previous full flush), straddles a second full flush's delete-queue swap, and the status call lands before that flush adds its ticket: hasUncommittedChanges() then returns false once (a caller that commits only on true skips one commit until its next poll), and an NRT reader opened before the delete reports isCurrent() true while openIfChanged() returns null once; no data is lost (the full flush in progress applies the delete and the next commit persists it), with the default IndexWriterConfig and no scale, in every release from 4.5.0 through 10.6.0 and main.
Summary
A committed document has id:1 and the writer holds a pooled per-thread writer with no documents; thread U deletes the document with updateDocuments(new TermQuery(id:1), List.of()) while thread R opens an NRT reader, and U's call returns its sequence number before R's full flush has finished. You expect hasUncommittedChanges() to return true from then on, because the delete is acknowledged and not committed and the javadoc names only false positives. Instead it returns false until R's flush turns the old delete queue into a ticket: R computed its 'changes pending' flag before swapping delete queues, U's per-thread writer appended the delete to the old queue after that, and DocumentsWriter.anyChanges() looks only at the new queue, the buffered document count (0 for an empty block), the ticket queue and that flag; once R finishes the answer is true again and R's reader has the delete applied.
Introduced
No single commit. The defect at the fix site: e95097a7c8d (LUCENE-2956 'Support updateDocument() with DWPTs', @s1monw, realtime_search branch; on trunk with LUCENE-3023 'Land DWPT on trunk' 2a969f828c1) introduced the per-thread-writer delete queue and its full-flush cut-over, with anyChanges() reading only the current queue; 73dec384b40 (LUCENE-3551, @s1monw, trunk) added pendingChangesInCurrentFullFlush, computed once before the swap, which closes the cut-over window for changes present at the swap but not for a delete appended to the swapped-out queue afterwards. Both precede the first 4.0 release. Made reachable by 8003cc78298 (LUCENE-5006 on branch_4x; trunk 75ab79f0aa3): before it, the empty-block updateDocuments that appends such a delete threw a NullPointerException. Visible through hasUncommittedChanges() from 00e4c287e87 (LUCENE-5289 on the 4.5 branch; branch_4x a80e7e93243, trunk f9f0cdd56fd), which made that method read docWriter.anyChanges() (2011-04-13 (e95097a7c8d, author date = commit date) and 2011-11-04 (73dec384b40); reachable from 2013-08-19 (8003cc78298); hasUncommittedChanges symptom from 2013-10-17 (00e4c287e87))
