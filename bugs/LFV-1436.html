MultiTerms.getTermPostingsEnum(reader, field, term) javadoc promises null when positions were not indexed; it returns an enum whose nextPosition() is -1

The javadoc of MultiTerms.getTermPostingsEnum(reader, field, term) says it returns null when the field was indexed without positions. Since 5.1.0 it returns a normal PostingsEnum whose nextPosition() is -1, so code that trusts the null reads -1 as every position; the code is right, only the sentence is wrong.

The finding in 30 seconds

#

The 3-argument helper forwards to the 4-argument one with PostingsEnum.ALL. That one returns null only for a missing field or term; otherwise it returns TermsEnum.postings(...), which is never null. A field without positions therefore gives a normal enum whose nextPosition() is -1, not the promised null.

Background: postings and positions

#
  1. For each term, Lucene stores postings: the documents that contain it and, depending on the field's IndexOptions, how often (freq()) and where (nextPosition()).
  2. A field indexed with DOCS or DOCS_AND_FREQS stores no positions. StringField, for example, indexes DOCS only.
  3. MultiTerms.getTermPostingsEnum(reader, field, term) is a shortcut that finds the term across all segments of a reader and returns its postings, asking for everything (PostingsEnum.ALL).

The finding, step by step

#
  1. You index one document whose field f holds a with IndexOptions.DOCS_AND_FREQS (documents and frequencies, no positions) and call MultiTerms.getTermPostingsEnum(reader, "f", new BytesRef("a")).
  2. Its javadoc says it "will return null if the field or term does not exist or positions were not indexed". So you expect null, and your code may use that null to skip its position logic.
  3. You get a normal PostingsEnum: nextDoc() is 0 and nextPosition() is -1. For a term that occurs twice in the document, freq() is 2 and both positions read -1. No error, with assertions on and off, on main and 10.6.0.
  4. Why: the method asks TermsEnum.postings for PostingsEnum.ALL, and since 5.1.0 (LUCENE-6271, on purpose) that method "will not return null"; nextPosition() documents the -1. Only this sentence was never updated.

Who is affected

#

Only code that calls this 3-argument helper on a field indexed without positions (on purpose), takes its null to mean "no positions" and then uses the -1 values. No special codec or writer configuration; every release since 5.1.0. No caller that clearly relies on the null was found; one downstream caller's code (lupyne) would show the symptom.

Mechanism, terms and numbers386 words

MultiTerms.getTermPostingsEnum(IndexReader, String, BytesRef) is a public static convenience helper of the @lucene.experimental class MultiTerms. Its javadoc says: "This will return null if the field or term does not exist or positions were not indexed." (MultiTerms.java:96-97).

The method calls the 4-argument overload with PostingsEnum.ALL (:103), which returns termsEnum.postings(null, flags) for an existing term (:119-120) and null only for a missing field or term (:109-110, :123). TermsEnum.postings "will not return null" (TermsEnum.java:160-161), and PostingsEnum.nextPosition() returns "-1 if positions were not indexed" (PostingsEnum.java:85). So for a field without positions the caller gets a normal enum with the right documents and frequencies and -1 for every position.

That behaviour is intended: LUCENE-6271 (#7333, 5.1.0) made postings() never return null, removed the same clause from the 4-argument overload's javadoc, and flipped TestOmitPositions to assertNotNull for exactly this call (TestOmitPositions.java:52). The 3-argument overload kept the clause, and LUCENE-7875 later moved it to MultiTerms unchanged. The fix is one javadoc sentence; no code changes.

Exposure and likelihood333 words
  • Who: callers of MultiTerms.getTermPostingsEnum(reader, field, term) that rely on the documented null to detect a field without positions (instead of checking Terms.hasPositions() up front) and then use the -1 values without noticing. Fields without positions are common (StringField indexes DOCS only), but the reliance on the null is what matters.
  • How bad: silent, and only in the caller's own code: no exception, and code that reads positions after a non-null result gets -1 for each one instead of taking its no-positions branch. That is a caller pattern shown by the repro, not a failure observed in a real application. Lucene's own indexing and search are not affected: its positional queries refuse such a field (IndexOptions.java:38-39: with DOCS_AND_FREQS, PhraseQuery "and other positional queries will throw an exception").

Why it looks unintended

#
  • The method's own javadoc names the return value outright: "null if ... positions were not indexed" (MultiTerms.java:96-97).
  • LUCENE-6271 (#7333, 5.1.0) made postings() never null on purpose, removed this clause from the 4-argument overload and flipped TestOmitPositions to assertNotNull for this call.
  • So the fix is javadoc only, like the sibling TermsEnum.postings leftover fixed in 79c29885472 (2018).
The full argument167 words
  • Contract. The sentence is the method's own javadoc, its most specific contract, and it names a concrete return value for a concrete case.
  • History. The clause was true when written (b679816a700, LUCENE-2370, 2010, then as "may return null if the term does not exist or positions were not indexed"; the current wording came in 5244693ebf9, LUCENE-4273, 2012): up to 5.0.0 the method returned a DocsAndPositionsEnum, which was null without positions (executed on 5.0.0: null). a411d8af6cd (Ryan Ernst, 2015-02-25, "postings() funcs switched over to not return null") removed the clause from the 4-argument overload only; the landing commits (3f98f20d4ef, 72c10717156, 1052ae1c48c) carry the same edit. b9f4e664369 (2015-03-31) flipped TestOmitPositions to assertNotNull for this call.
  • A sibling leftover was fixed. David Smiley noted on #7333 (2018-02-26) that the same change had left the TermsEnum.postings javadoc allowing null and fixed it in 79c29885472; this overload was not mentioned. LUCENE-7875 (fd9164801e7, #8926, 2018-10-18) then moved it to MultiTerms unchanged.
The devil's-advocate check140 words

The case: every value the caller gets is documented elsewhere (TermsEnum.postings never null, nextPosition() -1, and the @see target gives null only for a missing field or term); Robert Muir wrote on #7333 that Terms.hasPositions() and its siblings "should be used for these checks up-front"; MultiTerms is @lucene.experimental; no caller is known to clearly rely on the null; no report was found since 2015.

Why it fails: all of that defends the code, which stays as it is, not the sentence. The method's own javadoc states a return value that has been false since 5.1.0, and a reader who trusts it gets -1 positions where it was promised null, with legal input and every codec that was run. @lucene.experimental is about API stability, not about wrong docs today. Every reviewer agreed: real, with a javadoc-only fix.

Downstream note

#

Whether it applies is decided by the application: it chooses the field's index options, calls this helper and decides what a null means. Input (for example a query term) only decides whether the term exists, and for a missing term the javadoc and the code agree (null). No use of this helper was found in Elasticsearch, OpenSearch or Solr.

How it was found

#

Semi-formal: each statement in the javadoc of MultiTerms's static postings helpers was treated as a proof obligation and checked against the code. The "null if positions were not indexed" promise does not follow from a body that returns TermsEnum.postings(...), which is never null. A public-API JUnit test on main witnessed it; independent checks reproduced it.

The method in full66 words
  • Obligation: for an existing term of a field without positions, getTermPostingsEnum(reader, field, term) returns null (MultiTerms.java:96-97).
  • Code: the overload forwards PostingsEnum.ALL (:103); the callee returns termsEnum.postings(null, flags) (:120), which "will not return null" (TermsEnum.java:160-161); so the obligation fails.
  • Witness: the one-test repro fails on main with assertions on and off.
  • Tier: semi-formal (contract reasoning plus an executed test).

You index a field without positions (IndexOptions.DOCS_AND_FREQS) and call MultiTerms.getTermPostingsEnum(reader, field, term) for a term that exists. Its javadoc says 'This will return null if the field or term does not exist or positions were not indexed', so you expect null and could use that null to learn that positions are unavailable. Instead you get a non-null PostingsEnum whose nextPosition() returns -1 for every occurrence: the method asks TermsEnum.postings for PostingsEnum.ALL, and that method has never returned null since 5.1.0 (LUCENE-6271, on purpose), so only the sentence is wrong.
