Sequential DrillSideways never returns on a segment of more than 2,147,481,600 documents

On a segment of more than 2,147,481,600 documents (Lucene allows 2,147,483,519), a DrillSideways search without an executor never returns: its int chunk end overflows before it reaches the segment size, so the loop spins forever and the last chunk's hits are never collected. Every release since 4.2.0 is affected.

The finding in 30 seconds

#

The union and drill-down-advance loops of DrillSidewaysScorer keep their chunk end in an int. Above 2,147,481,600 documents the exit test nextChunkStart >= maxDoc can never become true, because the step wraps negative first.

How a sequential drill-sideways search walks a segment

#
  1. DrillSideways.search returns the hits of a drill-down query plus, for each drilled dimension, the facet counts as if that dimension were not drilled ("sideways"). Without an executor it does this in one pass, with a bulk scorer named DrillSidewaysScorer.
  2. Unless the base query is about 10 times cheaper than the drill-downs, that scorer walks the doc IDs in fixed chunks of 2,048: it gathers each chunk's matches, collects them, then moves the chunk end on by 2,048.
  3. It stops after the chunk whose end is at or past the segment's maxDoc.

The finding, step by step

#
  1. Index IndexWriter.MAX_DOCS = 2,147,483,519 documents with the default config and forceMerge(1) them into one segment; Lucene allows this, and its own @Monster test does the same. The last 3 documents have body:x and the facet dim=a.
  2. Run a DrillSideways search without an executor (the default): a DrillDownQuery on body:x with add("dim", "a"), top 10. You expect the 3 hits, as with 2,147,481,600 documents, where the same search returns in 0.029 s.
  3. Instead it never returns (stopped after 300 s; with the fix it returns the 3 hits in 0.033 s). The scorer walks the segment in chunks of 2,048 doc IDs and stops once the chunk end, an int, reaches the segment size: 2,048, 4,096, ..., 2,147,481,600.
  4. 2,147,481,600 is the largest multiple of 2,048 an int can hold, and it is still below 2,147,483,519. Adding 2,048 overflows to -2,147,483,648, so the counter cycles forever without reaching the size, and the last 1,919 doc IDs, where the 3 hits are, are never collected.

Who is affected

#

Only applications that run DrillSideways without an executor (the default) on an index with one segment of more than 2,147,481,600 documents: within 1,918 documents of Lucene's hard limit, for example an index at the limit force-merged to one segment. There each search that takes the union or drill-down-advance loop hangs a search thread. Smaller segments are safe.

Mechanism, terms and numbers746 words

DrillSidewaysScorer, the bulk scorer behind a DrillSideways search without an executor, walks a segment in chunks of CHUNK = 2048 doc IDs in its union and drill-down-advance strategies. The chunk end is an int nextChunkStart = CHUNK; after each chunk the loop exits when nextChunkStart >= maxDoc and otherwise does nextChunkStart += CHUNK. The largest multiple of 2,048 an int can hold is 2,147,481,600 (2^31 - 2048). On a segment with maxDoc from 2,147,481,601 to IndexWriter.MAX_DOCS = 2,147,483,519 (1,919 legal sizes) the exit test fails there and the next step overflows to Integer.MIN_VALUE; no later value ever reaches maxDoc, so the search never returns, keeps a thread busy, and never collects the hits from doc 2,147,481,600 up. Through the public API on a real force-merged segment of MAX_DOCS documents the stock search did not return within 300 s, while the fixed build returned its 3 hits in 0.033 s and a segment of 2,147,481,600 documents returned them in 0.029 s. It needs the default sequential mode (scoreSubDocsAtOnce() false) and the union or drill-down-advance strategy, which a pure browse (no base query) takes unless its drill-down clauses together cost more than 10 x maxDoc; the query-first strategy and the concurrent (executor) mode do not use the loop. Every release from 4.2.0 (2013) through 10.6.0, and main, is affected; saturating the step with MathUtil.unsignedMin(nextChunkStart + CHUNK, NO_MORE_DOCS), the helper #14750 added to core to simplify its window-end overflow guards, fixes it.

The loop

#

DrillSidewaysScorer.java on main 645d4fe14a20: CHUNK = 2048 (:60); int nextChunkStart = CHUNK in doDrillDownAdvanceScoring (:353) and doUnionScoring (:566). Each round gathers the matches with while (docID < nextChunkStart), so nextChunkStart is the exclusive end of the current chunk. The exit test and the step, union strategy (:598-603, :689-693; the drill-down-advance copy is :475-480, :535-539):

      if (filledCount == 0) {          // no match in this chunk
        if (nextChunkStart >= maxDoc) {
          break;
        }
        nextChunkStart += CHUNK;
        continue;
      }
      ...                              // score and collect this chunk's matches
      if (nextChunkStart >= maxDoc) {
        break;
      }
      nextChunkStart += CHUNK;         // 2,147,481,600 + 2,048 wraps to -2,147,483,648

The arithmetic

#
maxDocchunk ends triedoutcome
2,147,481,600 (2^31 - 2048)2,048, 4,096, ..., 2,147,481,6002,147,481,600 >= maxDoc: exits
2,147,481,601 ... 2,147,483,519 (1,919 sizes)..., 2,147,481,600, -2,147,483,648, ..., 0, ..., 2,147,481,600, ...never >= maxDoc: spins forever

After the wrap every value is a multiple of 2,048 in int, so at most 2,147,481,600, which is below maxDoc: the exit is unreachable, and no doc ID from 2,147,481,600 up is ever below the chunk end, so those hits are never collected. Both facts were proved with Z3 and cross-checked with cvc5. The counter runs through all 2^21 multiples of 2,048 and starts over. With all hits early in the segment, they are collected first, and then score() still never returns.

What the stuck thread does

#

Each round only reads the iterators' current docID() and does cheap bookkeeping (in union baseIterator.docID(), :574). It calls no nextDoc or advance, no collector and no reader method, checks no interrupt flag and allocates nothing (the 2,048-slot arrays are allocated before the loop), so by reading it keeps one core busy and never ends (what was measured: the real-segment search had not returned after 300 s).

Which searches take the loop

#

score() picks a strategy by cost (:130-147): query-first, which has no chunk loop, if scoreSubDocsAtOnce or baseQueryCost < drillDownCost / 10; else drill-down-advance if there are at least 2 dimensions and the second-cheapest (the dimensions are sorted by cost, DrillSidewaysQuery.java:182) costs less than a tenth of the base query; else union. A pure browse (no base query) uses MatchAllDocsQuery (DrillSideways.java:459), whose cost is maxDoc, so it takes query-first only if its drill-down clauses together cost more than 10 x maxDoc. In the real-segment run the base query and the dimension each match 3 documents, so union ran (the stack shows doUnionScoring).

DrillSideways.search without an executor (executor == null, DrillSideways.java:352-355; every constructor but the 5-argument one passes null) calls searchSequentially, which builds a DrillSidewaysQuery with scoreSubDocsAtOnce() (default false, :248-250) and runs searcher.search(dsq, ...) (:467); its weight's bulkScorer() returns a DrillSidewaysScorer (DrillSidewaysQuery.java:192-194). The concurrent mode runs plain DrillDownQuery searches instead (DrillSideways.java:483-508) and never builds this scorer (by reading, not executed).

Exposure and likelihood348 words
  • Who. Applications that use DrillSideways without an executor (the default; the concurrent mode is opt-in) on an index that has one segment of more than 2,147,481,600 documents. The whole index is capped at IndexWriter.MAX_DOCS = 2,147,483,519, so that is an index within 1,918 documents of the hard limit with almost all of it in one segment, for example an index at the limit after forceMerge(1), which is what Lucene's own @Monster test Test2BDocs builds and then reads.
  • Settings. Default codec, IndexWriterConfig, searcher and DrillSideways mode; DrillSideways itself is an opt-in facet-module API marked @lucene.experimental.
  • Effect. On such a segment a sequential drill-sideways search that takes the union or drill-down-advance strategy never returns, wherever its matches are, and keeps one search thread busy, unless a collector ends collection early by throwing CollectionTerminatedException before the loop wraps; the default DrillSideways collector includes the drill-down FacetsCollector, which never does that, so this takes a custom subclass. By reading, Lucene throws nothing and logs nothing. No Lucene time limit applies, but not because of this bug: sequential DrillSideways already rejects IndexSearcher#setTimeout (its scorer only accepts the full doc-ID range; open issue #12032). Repeated requests can occupy every search thread (an inference, not executed). By reading, the loop allocates nothing (memory was not measured), and the index is not touched.
  • Not affected. Segments of up to 2,147,481,600 documents, the query-first strategy, and the concurrent (executor) mode.
  • Likelihood: contrived. Almost no deployment has a single segment of 2.1 billion documents; one that does would see its faceted browsing hang outright rather than fail now and then.
  • Mitigations until fixed (by reading, not executed): keep segments at or below 2,147,481,600 documents (for example, do not forceMerge(1) an index at the limit); or subclass DrillSideways and return true from scoreSubDocsAtOnce(), which forces the query-first strategy at "some performance loss". The concurrent mode does not build this scorer, but it was not run at this scale and is not a verified workaround: by reading, its plain drill-down searches go through core scorers whose own behaviour at this size was not checked here.

Why it looks unintended

#
  • IndexWriter.MAX_DOCS (2,147,483,519) is the only documented size limit; Lucene's @Monster test Test2BDocs force-merges that many documents into one segment and reads it.
  • BulkScorer.score must collect the matches in its range and return; this one never returns.
  • The core scorers #14750 touched guard the same window-end arithmetic (long caps, now MathUtil.unsignedMin); this loop has no guard.
The full argument282 words
  • The only documented limit is MAX_DOCS. It is the "Hard limit on the maximum number of documents that may be added to the index" (IndexWriter.java:201-208); LUCENE-5843 added it so that going past it throws "instead of silently creating an unusable index" (CHANGES.txt). No javadoc of DrillSideways, DrillDownQuery, DrillSidewaysQuery, the facet package, MIGRATE.md or CHANGES.txt sets a lower per-segment limit.
  • Lucene's own tests use such a segment. Test2BDocs (@Monster) force-merges MAX_DOCS documents into one segment and walks its postings. TestIndexWriterMaxDocs.testExactlyAtTrueLimit (@Monster) indexes MAX_DOCS documents, asserts that searches return totalHits == MAX_DOCS and force-merges them into one segment (committed only when the writer closes, after its last search).
  • The BulkScorer contract. score "Collects matching documents in a range and return[s] an estimation of the next matching document" (BulkScorer.java:31-32); this one never returns and never collects the last chunk.
  • Core guards the same kind of arithmetic. The core bulk scorers and iterators that #14750 (jpountz, merged 2025-06-03, first released in 10.3.0) touched already guarded their window-end arithmetic with long caps such as (int) Math.min(max, (long) windowMin + WINDOW_SIZE); #14750 replaced them with MathUtil#unsignedMin, added because dividing the doc-ID space into windows "is prone to integer overflows if the size of the window is greater than Integer.MAX_VALUE - windowStart". It simplified guards that were already overflow-safe and was not a bug fix. Today 11 core classes use the helper; no facet class does, and DrillSidewaysScorer's chunk loop has no guard of either kind.
  • Nothing covers the boundary. The facet tests have no test near 2^31 documents, and the LUCENE-4748 discussion mentions CHUNK only for its up-front array cost.
The devil's-advocate check172 words

The strongest case for "not a bug" (the devil's-advocate verifier and a reviewer from another model family, OpenAI GPT-5.6): DrillSideways is @lucene.experimental, the scorer is package-private, the scale is absurd (one segment of 2.1 billion documents), and workarounds exist (scoreSubDocsAtOnce(), smaller segments, possibly the concurrent mode); a custom collector that ends collection early also avoids the hang. A committer could say nobody runs drill sideways there, and that other facet code may have its own int limits at this scale (not checked).

Why it fails: @lucene.experimental is about API stability, not permission to hang; the package-private scorer is what the public default DrillSideways.search builds; the size is legal by Lucene's own documentation and tests, so "absurd" argues for low priority, not for intent; early termination needs a non-default collector setup; and core guards the same kind of window-end arithmetic in the scorers #14750 touched (long caps, simplified to MathUtil.unsignedMin), which this loop lacks. The cross-model reviewer rated the intended-behaviour case weak. A defect, small and low priority.

Suggested fix

#

Recommended Saturate the chunk step at NO_MORE_DOCS with MathUtil.unsignedMin

At the 4 chunk steps, replace nextChunkStart += CHUNK with nextChunkStart = MathUtil.unsignedMin(nextChunkStart + CHUNK, DocIdSetIterator.NO_MORE_DOCS), the helper core's bulk scorers use for the same kind of window-end overflow. The step then ends the last chunk at NO_MORE_DOCS and the loop exits. With it the repro and the whole facet module test suite pass, with assertions on and off.

import org.apache.lucene.util.MathUtil;
...
// at each of the 4 chunk steps, instead of: nextChunkStart += CHUNK;
nextChunkStart = MathUtil.unsignedMin(nextChunkStart + CHUNK, DocIdSetIterator.NO_MORE_DOCS);

Saturate the chunk step at NO_MORE_DOCS with MathUtil.unsignedMin (validated by the checks) (recommended)

#

The 4 steps (DrillSidewaysScorer.java:479, :539, :602, :693) plus one import, +7/-4 lines after google-java-format (the two 8-space-indented sites wrap onto a second line).

import org.apache.lucene.util.MathUtil;
...
// at each of the 4 chunk steps, instead of: nextChunkStart += CHUNK;
nextChunkStart = MathUtil.unsignedMin(nextChunkStart + CHUNK, DocIdSetIterator.NO_MORE_DOCS);

Trade-offs

  • Every chunk end below 2,147,481,600 is unchanged. At 2,147,481,600 the sum wraps to Integer.MIN_VALUE, which is unsigned-greater than NO_MORE_DOCS (2^31 - 1), so the step yields NO_MORE_DOCS: the last chunk ends there, its docID < NO_MORE_DOCS test still stops at an exhausted iterator, and the next exit test fires. Z3 proves the step is then exactly +2,048 or NO_MORE_DOCS and that every document of the last chunk is below it.
  • Cost: one unsigned compare per 2,048-doc chunk; the per-document loops are unchanged.
  • The same helper and pattern as the core bulk scorers since #14750 (for example DisjunctionMaxBulkScorer, ConstantScoreBulkScorer).

What the checks validated

  • Scratch worktree of 645d4fe14a20, gradle, OpenJDK 25.0.3, seed DEADBEEF. Stock: the repro fails with assertions on and off.
  • With the fix: the whole :lucene:facet:test (39 upstream suites plus the repro, including TestDrillSideways, TestParallelDrillSideways and TestDrillDownQuery) runs 307 tests, 0 failures, with assertions on (7 skipped) and off (8 skipped); checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest of :lucene:facet pass.
  • A 4-test JUnit covering both strategies at MAX_DOCS plus two controls at 2^31 - 2048 fails 2 of 4 on stock and passes 4 of 4 with the fixed file, with assertions on and off. On the real MAX_DOCS segment the same cap returned the 3 hits in 0.033 s. Other modules' tests were not run.

Workarounds for users until a fix ships (not fixes)

#

Override DrillSideways#scoreSubDocsAtOnce() to return true (query-first strategy, no chunk loop, "some performance loss"), or keep segments at or below 2,147,481,600 documents. The concurrent mode (an ExecutorService in the constructor) does not build this scorer, but it is not a verified workaround at this scale.

Trade-offs

By reading only, not executed. The first changes performance characteristics; the second limits merging of an index near the hard limit. The concurrent mode was not run at this scale, and its plain drill-down searches go through core scorers whose behaviour at this size was not checked here.

Downstream note

#

A read-only code search found no use of DrillSideways in Elasticsearch, OpenSearch or Solr, so exposure is limited to applications that embed the facet module directly.

How it was found

#

A hunt for integer overflows near Lucene's size limits scanned the bytecode for a constant added to an int that then feeds a comparison, and flagged the +2048 steps in DrillSidewaysScorer. A JUnit on the stock jars failed first; SMT proofs (Z3, cross-checked with cvc5) then showed the loop cannot exit above 2^31 - 2048 documents, and a run on a real segment confirmed it.

The method in full243 words

Method: semi-formal (a bytecode inventory, then a failing JUnit, then SMT obligations and a run on a real segment).

  • Inventory. An abstract interpreter over the bytecode (JDK 25 java.lang.classfile) listed every int addition of a constant of 64 or more whose result flows into an int comparison. One row was iinc 2048 into IF_ICMPGE in DrillSidewaysScorer.doUnionScoring and doDrillDownAdvanceScoring.
  • Witness. A JUnit on the stock jars (the package-private scorer over a reader that reports maxDoc = MAX_DOCS) failed on main with assertions on and off (later also on 10.5.2 and 9.12.3).
  • Obligations, then a run at scale. Z3 bit-vector obligations, cross-checked with cvc5, with maxDoc <= IndexWriter.MAX_DOCS as the precondition: a counterexample for the wrap whose smallest maxDoc is 2^31 - 2047 (DS1); no overflow for maxDoc <= 2^31 - 2048 (DS1b); for larger legal maxDoc no reachable chunk end is >= maxDoc (DS2) and no document of the last chunk is ever below one (DS3); and the saturating fix steps by exactly 2,048 or reaches NO_MORE_DOCS, covering the last chunk (DS4, DS4b). A public-API run on a real force-merged MAX_DOCS segment then did not return within 300 s, while the fixed build returned in 0.033 s.
  • Then an independent reproducer, reviews by a model from another family (OpenAI GPT-5.6; the refute-lens one was never obtained, the intended-lens one was reading-only), a devil's-advocate verifier, an adjudication, a follow-up (history and prior reports), a credibility audit and a repro-minimization step followed.

LFV-383, snapshot of 2026-11-08

Registry title
Sequential DrillSideways never returns on a segment of more than 2^31 - 2048 documents: DrillSidewaysScorer's int chunk start wraps to Integer.MIN_VALUE, so its union and drill-down-advance loops never exit (released since 4.2.0)
Area
facet / DrillSideways (sequential DrillSidewaysScorer, union and drill-down-advance strategies)
Priority
Low, rank 978: In the facet module, sequential DrillSideways hangs forever on a segment within about 1,900 docs of MAX_DOCS, which needs the same 2^31-doc segment as the core BooleanScorer hang LFV-048.
Impact class
hang
Impact note
Applications that run the default sequential DrillSideways (no executor, scoreSubDocsAtOnce() false) on an index with one segment of more than 2,147,481,600 documents (the top 1,919 legal sizes below IndexWriter.MAX_DOCS, for example an index at the hard limit force-merged to one segment) get a search that never returns and pins a thread at 100% CPU whenever the cost heuristic picks the union or drill-down-advance strategy, which every pure browse request (no base query) does, wherever the matches are; default codec, IndexWriterConfig and searcher, every release since 4.2.0, extreme scale; the query-first strategy and the executor-backed concurrent DrillSideways do not use the chunk loop.
Summary
You run a faceted DrillSideways search in the default sequential mode on an index whose single segment holds more than 2,147,481,600 documents, which IndexWriter accepts (MAX_DOCS = 2,147,483,519), and expect it to return its hits as it does on a segment 2,048 documents smaller. Instead DrillSidewaysScorer's union and drill-down-advance loops walk the segment in 2048-document chunks with an int nextChunkStart that wraps from 2^31 - 2048 to Integer.MIN_VALUE before the exit test 'nextChunkStart >= maxDoc' can fire, so the search thread spins forever and the hits of the last chunk are never collected. Through the public API on a real segment of MAX_DOCS documents the stock search did not return within 300 s, while the fixed build returned its 3 hits in 0.033 s.
