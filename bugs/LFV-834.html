A PayloadScoreQuery that wraps another PayloadScoreQuery sees no payloads, and with the 3-argument constructor every matching search throws

Wrap one PayloadScoreQuery in another and the outer payload function never sees a payload: with Max, documents with payloads 3 and 5 both score 1.0, with no error. With the 3-argument constructor every search that matches a document throws instead; 5.3.0 (2015) to 10.6.0 and main are affected.

The finding in 30 seconds

#

PayloadScoreQuery turns the payloads at a span query's matches into a score. It accepts any span query to wrap, including another PayloadScoreQuery. If you do that, the outer query never reads a payload: every hit gets the function's no-payload score (1.0 for the built-in functions), or, with the 3-argument constructor, every matching search throws.

Background in 3 steps

#
  1. A payload is a few bytes stored with one occurrence of a term, for example a weight: x|3 stores 3 with this x.
  2. PayloadScoreQuery(spanQuery, function, decoder, includeSpanScore) scores each match of spanQuery by combining the payloads at the matched positions with function (Max, Min, Sum, Average). With includeSpanScore=true, the default of the 3-argument constructor, it also multiplies in the usual BM25 span score.
  3. Span queries score through a SpanWeight and its SimScorer (the BM25 part). A SpanWeight built without term statistics has no SimScorer, which by its javadoc is meant for searches that need no scores.

The finding, step by step

#
  1. Index two documents whose field f holds one token x, with payload 3 in doc 0 and 5 in doc 1. PayloadScoreQuery(SpanTermQuery(f:x), Max, FLOAT_DECODER, false) scores them 3.0 and 5.0.
  2. Wrap a payload query once more: PayloadScoreQuery(PayloadScoreQuery(f:x, Sum, ..., false), Max, ..., false). A PayloadScoreQuery's spans are the spans of the query it wraps, so you expect 3.0 and 5.0 again.
  3. You get 1.0 and 1.0, the value Max returns when it has seen no payload, and no error. With the 3-argument constructors (span score included, includeSpanScore=true), IndexSearcher.search throws: AssertionError with assertions on, NullPointerException with them off.
  4. Why: the outer query scores with the inner weight's SimScorer, but a PayloadScoreQuery weight never has one (it passes no term statistics to SpanWeight). SpanScorer reads the missing SimScorer as "scores not needed" and stops before it collects any payload.
  5. A same-field FieldMaskingSpanQuery in between fails the same way; any real span query in between, such as SpanFirstQuery, gives the right 3.0 and 5.0. Affected: 5.3.0 to 10.6.0 and main.

Who is affected

#

Java code that builds a PayloadScoreQuery around a span query that already is one, directly or under a same-field FieldMaskingSpanQuery, for example generic code that adds payload scoring to any span query it is given. Deterministic with default settings. No Lucene query parser builds the shape, and the recorded public searches found no earlier report.

Mechanism, terms and numbers650 words

PayloadScoreQuery scores span matches by the payloads stored at the matched positions, and its constructors accept any SpanQuery, including another PayloadScoreQuery. When one wraps another, directly or through a same-field FieldMaskingSpanQuery, the outer weight scores with the inner weight's SimScorer, which is null because a PayloadSpanWeight passes no term statistics to SpanWeight. SpanScorer treats a null SimScorer as "scores not required" and returns before it collects payloads.

So with includeSpanScore=false every hit gets the payload function's no-payload value (1.0 for the built-in functions) instead of its payload score, silently, and with includeSpanScore=true, the 3-argument constructor's default, every search in which that query matches a document throws (AssertionError with -ea, NullPointerException with -da). The match set is unchanged. Only Java code that builds the nested shape itself is hit; no Lucene query parser builds it. 5.3.0 (2015) to 10.6.0 and main are affected (22 releases and main run; all 95 release tags in that range have the two defect lines); a one-file fix is validated.

The mechanism (main 645d4fe14a20)

#
  1. A payload weight exists only when scores are needed. PayloadScoreQuery.createWeight asks the wrapped query for its weight with the same score mode and, when scores are needed, wraps it in a PayloadSpanWeight (PayloadScoreQuery.java:118-125). A nested inner PayloadScoreQuery therefore builds a PayloadSpanWeight too.
  2. That weight has no SimScorer. Its constructor calls super(PayloadScoreQuery.this, searcher, null, boost) (:150). SpanWeight returns a null SimScorer for null term states (SpanWeight.java:98, :104), getSimScorer() returns that field (:160-163), and PayloadSpanWeight does not override it. The SpanWeight javadoc allows null term states only "if scores are not required" (:88-89).
  3. Its scorer borrows the inner weight's SimScorer: new PayloadSpanScorer(payloadSpans, innerWeight.getSimScorer(), norms) (PayloadScoreQuery.java:196). For a SpanTermQuery inner weight that exists; for an inner PayloadSpanWeight it is null.
  4. A null SimScorer skips the payloads. SpanScorer.setFreqCurrentDoc does if (scorer == null) { // scores not required, break out here then freq = 1; return; before spans.doCurrentSpans() (SpanScorer.java:108-113), which is where PayloadSpans collects payloads (PayloadScoreQuery.java:243-245). The function then returns its no-payload value: MaxPayloadFunction.docScore is numPayloadsSeen > 0 ? payloadScore : 1 (MaxPayloadFunction.java:42-43).
  5. With the span score it throws. PayloadSpanScorer.scoreCurrentDoc multiplies by super.scoreCurrentDoc() when includeSpanScore is true (PayloadScoreQuery.java:284-294), which asserts scorer != null : ... " has a null docScorer!" (SpanScorer.java:75) and then calls scorer.score(freq, norm) (:80).
  6. Second trigger. FieldMaskingSpanQuery.createWeight returns the masked query's weight (FieldMaskingSpanQuery.java:88-92), so a same-field mask hands the outer query the same inner PayloadSpanWeight.
  7. Why a real span query in between works. Every other wrapping span weight builds its own SimScorer with scoreMode.needsScores() ? getTermStates(...) : null (SpanPositionCheckQuery.java:70, SpanNearQuery.java:181, SpanOrQuery.java:131, SpanNotQuery.java:116, SpanContainingQuery.java:53, SpanWithinQuery.java:52, SpanPayloadCheckQuery.java:113). PayloadScoreQuery.java:196 is the only main-source line in lucene/queries that scores with another weight's SimScorer.

Exposure and likelihood249 words
  • What goes wrong. With includeSpanScore=false every hit of that query gets the same score (1.0 for the built-in functions): the payload ranking is lost, with no error, and explain() reports the same 1.0. With includeSpanScore=true, the 3-argument constructor's default, every search in which that query matches a document throws (AssertionError with -ea, NullPointerException with -da); a search with no matching document does not, because the null SimScorer is only used to score a hit (and scorerSupplier returns null for a segment without spans, PayloadScoreQuery.java:190-192).
  • Limits. The match set is unchanged; nothing is written to the index; no hang or resource growth was observed in any run.
  • No special setup. Default IndexWriterConfig, codec and searcher; the plain-Java main() fails with the production default codec (Lucene104) and no test framework; the JUnit tests fail under whichever codec the test framework picks (Lucene104 and Asserting(Lucene104) were recorded). Runs used one- and two-document indexes; nothing in the mechanism depends on index size.
  • Reach: rare. No Lucene query parser builds the shape: the XML parser's payload builder always wraps a SpanTermQuery (BoostingTermBuilder.java:38-41), and neither does Solr's payload_score parser. GitHub code search finds no code that nests the constructors. By reading only, a 2021 outside article describes a search-engine plugin whose builder wraps any parsed span query in a PayloadScoreQuery, so a nested request could build the shape there (not run).
  • Context. PayloadFunction is @lucene.experimental (PayloadFunction.java:27), and open issue #16820 proposes deprecating span queries.

Why it looks unintended

#
  • The API accepts it: the constructors take any SpanQuery, and CHANGES for LUCENE-6706 says "use PayloadScoreQuery to wrap any SpanQuery".
  • SpanWeight allows a missing SimScorer only "if scores are not required", yet this weight is built only when they are.
  • Every other wrapping span weight builds its own SimScorer; with SpanFirstQuery in between, the nesting scores 3.0 and 5.0.
The full argument215 words
  • The API accepts it. The constructors take any non-null SpanQuery (PayloadScoreQuery.java:63-83); the class javadoc says it modifies "the score of a wrapped SpanQuery" (:43-47); the package javadoc says "For all terms matched by a SpanQuery, boost the score based on the value of the payload located at those terms" (package-info.java:24-26); CHANGES for LUCENE-6706 says "use PayloadScoreQuery to wrap any SpanQuery" and that it generalises payload scoring "to all Span queries" (CHANGES.txt:9407-9408, :10351-10352).
  • SpanWeight's contract. Null term states "May be null if scores are not required" (SpanWeight.java:88-89); PayloadSpanWeight passes null although it is built only when scores are required (PayloadScoreQuery.java:121-124, :150).
  • Siblings. Every other wrapping span weight builds its own SimScorer. The test sources' delegating AssertingSpanWeight also passes null term states but overrides getSimScorer() to return the wrapped weight's (AssertingSpanWeight.java:41, :58-60); that override came with LUCENE-6845 (2015), from the same author as PayloadScoreQuery, and PayloadSpanWeight never got one.
  • One step away it works. With SpanFirstQuery (or an all-positions SpanPositionRangeQuery) between the two, the outer function sees the payloads and the scores match the non-nested query.
  • Why tests missed it. No upstream test nests PayloadScoreQuery or wraps a FieldMaskingSpanQuery in one; neither did the introducing commit's tests.
The devil's-advocate check180 words

The strongest case for "intended": span queries score only at the top level (LUCENE-8143 removed SpanBoostQuery as "a no-op unless used at the top level of a SpanQuery nested structure", MIGRATE.md:1604-1607), so nesting a payload query is redundant; no javadoc or test says nesting must work; PayloadFunction is experimental; FieldMaskingSpanQuery warns that masking "may lead to exceptions, poor performance, and unexpected scoring behavior" (FieldMaskingSpanQuery.java:63-65); and #16820 proposes deprecating span queries.

Why it fails: the top-level rule explains the inner function being ignored, but here the top-level query loses its own function or every search that matches a document throws; a query the constructors accept should not make IndexSearcher.search throw NullPointerException; the masking warning is about a different field's statistics, while the trigger masks the same field and direct nesting masks nothing; a null SimScorer means "scores not required" in both SpanWeight and SpanScorer, and this weight exists only when scores are required. Verdict: not intended, a defect (finder, an execution-capable cross-model review, the independent reproduction, the intended-behaviour check, the adjudication, the reproducer and the tie-break).

Suggested fix

#

Recommended Delegate getSimScorer() and explain the span score from the same weight (+14/-2)

Give PayloadSpanWeight a getSimScorer() that returns the inner weight's, so an outer payload query gets a real SimScorer, and explain the span part from the weight that owns it. One file, +14/-2. The repro, the earlier tests of this bug and all 513 lucene/queries tests pass; non-nested scores are unchanged.

    @Override
    public SimScorer getSimScorer() {
      return innerWeight.getSimScorer();
    }

    /** Explains the span score, which comes from the innermost non-payload span weight. */
    private Explanation explainSpanScore(LeafReaderContext context, int doc) throws IOException {
      if (innerWeight instanceof PayloadSpanWeight inner) {
        return inner.explainSpanScore(context, doc);
      }
      return innerWeight.explain(context, doc);
    }

Delegate getSimScorer() and explain the span score from the same weight (+14/-2) (validated by the checks) (recommended)

#

In PayloadScoreQuery.PayloadSpanWeight, add the override below, and in explain replace innerWeight.explain(context, doc) (PayloadScoreQuery.java:179-180) with explainSpanScore(context, doc). The override is the same idea as AssertingSpanWeight.getSimScorer(); the explain change keeps the "product of" details equal to the score for nested queries. The fix gives a nested query the scores the same queries get when a real span query separates them; the exact nested score with includeSpanScore=true is undocumented, so this is one reasonable choice for the maintainers.

    @Override
    public SimScorer getSimScorer() {
      return innerWeight.getSimScorer();
    }

    /** Explains the span score, which comes from the innermost non-payload span weight. */
    private Explanation explainSpanScore(LeafReaderContext context, int doc) throws IOException {
      if (innerWeight instanceof PayloadSpanWeight inner) {
        return inner.explainSpanScore(context, doc);
      }
      return innerWeight.explain(context, doc);
    }

Trade-offs

  • In-tree queries that work today take the same code paths, so their scores and explanations are unchanged (executed for the non-nested cross-field FieldMaskingSpanQuery form: 0.2635535/1.1898826 before and after). SpanWeight.getSimScorer() is public, so code outside Lucene that calls it on a PayloadSpanWeight would now get the inner SimScorer instead of null (not checked).
  • The inner query's payload function still contributes nothing to a nested score; the outer function now sees the inner spans' payloads. A maintainer may prefer to forbid nesting instead.
  • Open PR #15819 rewrites the scorerSupplier line (:196), which this fix leaves alone; the two apply together without a textual conflict, in either order. But #15819 takes the span score from the inner weight's new createSpanScorer(), which builds the scorer from the simScorer field, null for an inner PayloadSpanWeight, so whichever change lands second must also cover that path (read, not built). The hunt's fix rewrites :196 and does conflict with #15819.

Downstream note

#

Not a Lucene security issue; downstream, a server plugin that wraps any parsed span query in a PayloadScoreQuery could build this shape from a nested request and then return an error or flat scores for it (by reading another contributor's description, not run).

How it was found

#

A bounded-exhaustive check of payload scoring against a reference model, run on the stock jars. Its harness also wrapped every query shape in a second PayloadScoreQuery, expecting the same scores as the unwrapped query; 12,120,610 nested score checks returned 1.0 and 3,072 nested searches threw. An AI tool then read the root cause in the code.

The method in full151 words

Method: semi-formal (a hunt unit, payload and span queries against a reference semantics).

  • The harness built small indexes with payloads (int, float and string payloads; one and three segments, with and without deletions) and compared Lucene's scores for each query shape with a reference implementation of payload scoring.
  • As one of its checks it ran every shape also as PayloadScoreQuery(PayloadScoreQuery(shape, Sum, decoder, false), fn, decoder, incl), with the reference "same scores as PayloadScoreQuery(shape, fn, decoder, incl)", because a payload query's spans are its wrapped query's spans. So nesting was a deliberate check, not a blind discovery.
  • Out of 76,177,080 payload-score checks, 12,120,610 nested ones returned 1.0 and 3,072 nested searches threw, while the non-nested and SpanPositionRangeQuery-wrapped forms matched the reference exactly.
  • The finder, an AI tool, then read the root cause in the code and wrote a public-API JUnit; the one-test repro was cut from it on 2026-10-29.

LFV-834, snapshot of 2026-11-01

Registry title
A PayloadScoreQuery that wraps another PayloadScoreQuery (directly or through a same-field FieldMaskingSpanQuery) ignores every payload and scores each hit 1.0 with includeSpanScore=false, and with includeSpanScore=true (the 3-argument constructor's default) fails every search with an AssertionError (-ea) or NullPointerException (-da), because the outer weight borrows the inner PayloadSpanWeight's SimScorer, which is null (since 5.3.0, LUCENE-6706)
Area
queries / payloads (PayloadScoreQuery.PayloadSpanWeight SimScorer source; SpanScorer null-SimScorer early return)
Priority
Low, rank 714: Nesting one PayloadScoreQuery inside another silently scores every hit 1.0 (or throws with the default constructor), but only hand-built composition creates that shape and nobody is known to do it.
Impact class
silent wrong results
Impact note
Applications that build a PayloadScoreQuery (lucene-queries) whose wrapped query is itself a PayloadScoreQuery, directly or through a FieldMaskingSpanQuery (whose createWeight returns the inner weight), get for that query every hit scored 1.0 with includeSpanScore=false (payloads ignored, match set unchanged, no error) and an AssertionError (-ea) or NullPointerException (-da) from IndexSearcher.search with includeSpanScore=true, the 3-argument constructor's default; only programmatic composition produces the shape (no Lucene query parser and not Solr's payload_score parser builds it); default IndexWriterConfig, codec and searcher, no scale needed; every release from 5.3.0 (throwing only) and 5.4.0 (silent form) to 10.6.0 and main.
Summary
Wrap a PayloadScoreQuery in another one, for example PayloadScoreQuery(PayloadScoreQuery(SpanTermQuery(f:x), Sum, FLOAT_DECODER, false), Max, FLOAT_DECODER, false), over two documents whose token x carries the payloads 3 and 5. You expect the outer payload function to see those payloads and score the documents 3.0 and 5.0, as PayloadScoreQuery(SpanTermQuery(f:x), Max, FLOAT_DECODER, false) does, because a PayloadScoreQuery's spans are those of the query it wraps. Instead both hits score 1.0, the function's value for 'no payloads seen', and the same query built with the 3-argument constructor (includeSpanScore=true) makes IndexSearcher.search throw an AssertionError ('PayloadSpanScorer has a null docScorer!') with -ea or a NullPointerException with -da.
