SimplePatternTokenizer and SimplePatternSplitTokenizer retry a failed match in the middle of an emoji, so 🔥hot is indexed as U+FFFD + hot and so🔥hot is cut in two

With the pattern 🔥[0-9]+|[^🔥 ]+, SimplePatternTokenizer turns 🔥hot deal into \uDD25hot, deal, so a search for hot misses the document. After a failed match at an emoji, it retries one Java char later, inside the emoji.

The bug in 30 seconds

#

SimplePatternTokenizer tries its pattern at each character and keeps the longest match. An emoji is one character to the pattern but two chars in Java. When a try that started at an emoji fails, the tokenizer should move on to the next character; it moves on by one char and lands inside the emoji.

  1. Index 🔥hot deal with SimplePatternTokenizer (factory name simplePattern) and the pattern 🔥[0-9]+|[^🔥 ]+: 🔥 followed by digits (like 🔥5), or a run of characters other than 🔥 and space. In Java, 🔥 (U+1F525) is two chars, a surrogate pair, at offsets 0 and 1.
  2. You expect hot [2,5) and deal [6,10): no match starts at 🔥 (no digit follows), so the next try starts at h. The same tokenizer gives exactly that with [^🔥 ]+ alone, and so does PatternTokenizer with the same regex.
  3. You get \uDD25hot [1,5) and deal. After the failed try at 🔥 the tokenizer steps back to one char past the start, which is the emoji's second half, and [^🔥 ] accepts that half. The index stores \uFFFDhot, so a TermQuery for hot finds 0 documents instead of 1.
  4. 🔥 x gives an extra token \uDD25 [1,2) before x. SimplePatternSplitTokenizer with the separators [^a-z🔥]+|🔥! cuts so🔥hot now into so\uD83D, hot, now instead of so🔥hot, now. The tokenizers do not throw; they emit these tokens with assertions on or off.

Who is affected

#

Users of the opt-in, experimental simplePattern or simplePatternSplit tokenizers whose pattern can start a longer alternative at an emoji or other supplementary character and also accepts its second half (a negated class that excludes it, or a range reaching into the surrogate block). Text then hits it whenever the character is not followed by the rest of its alternative.

Mechanism, terms and numbers1,002 words

SimplePatternTokenizer and SimplePatternSplitTokenizer read their input one code point at a time, so an emoji is one step of the automaton even though it is two Java chars ("The runDFA operates in Unicode space, not UTF16", SimplePatternTokenizer.java:114). When a match attempt that started at such a character fails after reading further, the false-alarm branch pushes back all but one char of what it read (pushBack(tokenUpto - 1), :155; pushBack(sepUpto - 1), SimplePatternSplitTokenizer.java:166), so the next attempt starts at the emoji's low surrogate, which the reader returns as a code point of its own.

If another part of the pattern accepts that half, typically a negated class that excludes the emoji or a range that reaches into the surrogate block (such as [\u0080-\uFFFF]; the pattern need not name a supplementary character), the tokenizer emits a token that starts inside the pair (\uDD25hot [1,5) instead of hot [2,5)), or an extra token made of half the emoji; the split tokenizer ends a token after the first half (so\uD83D) and loses the word so🔥hot. The index stores the lone halves as U+FFFD, so exact-term searches for the affected words miss. The line is in the classes' first commit (6.5.0) and fails on every release run, up to 10.5.2 and main. The fix changes two lines per class: push back all but the first code point.

How the tokenizer scans

#

SimplePatternTokenizer.incrementToken() (SimplePatternTokenizer.java:104-162 at a9779ef3c193) on 🔥hot deal, whose UTF-16 units are 0:D83D 1:DD25 2:h 3:o 4:t 5:space 6:d 7:e 8:a 9:l:

  1. Read one code point and start the automaton (:116, :121). nextCodePoint() (:242-253) sees the high surrogate and joins it with the next unit (:248-249), so ch = U+1F525 and two units are in the term buffer. step(0, U+1F525) is live (it begins 🔥[0-9]+) but not accepting.
  2. Look ahead (:126-139). h is not a digit, so the automaton dies. Nothing was accepted and the input did not end: the false-alarm branch (:153-156).
  3. The false alarm rewinds by chars. pushBack(tokenUpto - 1) (:155, tokenUpto = 3 units) pushes back U+DD25 and h; the next line, tokenUpto = 0 (:156), discards the high surrogate already read, so the next try starts at offset 1, inside the pair. The comment says "push back all but the first character we scanned", but the first thing scanned was a two-unit code point.
  4. The retry starts inside the pair. The next nextCodePoint() reads U+DD25, which is not a high surrogate, so it is returned as the code point U+DD25 (:248-252). Lucene RegExp negated classes are any code point from 0 to 0x10FFFF minus the listed ones (RegExp.java:1302, Automata.java:105-106), so [^🔥 ] accepts it, and the token is \uDD25hot [1,5) (:141-150).
  5. The other no-match branch does it right. When the first step already fails (state == -1, :158-160), the whole code point is dropped: with [^🔥 ]+ alone both units of 🔥 are skipped and the next try starts at h. So whether 🔥 is stepped over correctly depends on whether some alternative can start with it.

The split tokenizer

#

SimplePatternSplitTokenizer (SimplePatternSplitTokenizer.java:99-170) looks for separators the same way, and every code point that does not start one stays in the pending token (:213-220). On so🔥hot now the try at 🔥 starts 🔥!, dies at h, and pushBack(sepUpto - 1) (:163-167) leaves so\uD83D in the pending token (here the high surrogate is kept). The retry reads U+DD25, which [^a-z🔥]+ accepts as a one-unit separator, so so\uD83D [0,3) is emitted and hot [4,7) starts a new token.

Exact trigger

#

All three are needed; naming a supplementary character is not. (a) An attempt that starts at a supplementary character goes live and then dies after reading further, before the end of the input: some alternative starts with the character, by naming it (🔥[0-9]+, 🔥[a-z]+, 🔥!, 🔥🔥) or through a class that contains it followed by more (.[0-9]+, [^a-z ][0-9]+, [^ ]+!). (b) Nothing was accepted in that attempt: a top-level . or [^ ]+ accepts the whole character, so the longest match is the token and no retry happens (😀ab|. on 😀x and 🔥[0-9]+|[^ ]+ are correct). (c) Another part of the pattern accepts a match that starts with the exposed low surrogate: a negated class that excludes the character ([^🔥 ]), any range that reaches into the surrogate block U+D800-U+DFFF (the common "non-ASCII" [\u0080-\uFFFF], or [\u3000-\uFFEF]), or a hand-built automaton that accepts surrogate code points. (\uXXXX here stands for the character itself, as a Java string literal gives it; Lucene RegExp rejects \u as an escape.)

Executed on main without naming any supplementary character (the doc's fact and diagram checks): .[0-9]+|[\u0080-\uFFFF]+|[a-z]+ on 🔥hot deal gives an extra \uDD25 [1,2) before hot, deal; [^ ]+!|[\u3000-\uFFEF]+ on 🔥中 b gives \uDD25中 [1,3) where PatternTokenizer gives 中 [2,3); the split tokenizer with [\u0080-\uFFFF]+|.! cuts so🔥hot now into so\uD83D, hot now. With the fix the diagram check's cases are correct.

If any of the three fails, the tokens are correct: a retry at the low surrogate that accepts nothing ends at the next code point, as a code-point retry would (:153-160). Executed correct: [^🔥 ]+ alone, 🔥[0-9]+|[^ ]+ and .[0-9]+|[a-z]+. The hunt's 39-pattern pool had no explicit range reaching into the surrogate block (its negated classes contain the block), so its counts say nothing about the range shapes: its 13,741 lone-surrogate mismatches per tokenizer were recorded (one example per class and pattern) only for the 2 pool patterns that meet all three conditions, while 3 more patterns that name the emoji were correct. When the try reaches the end of the input instead, another branch runs (:151-152): that is the sibling bug LFV-525.

Exposure and likelihood309 words
  • Who is exposed. Users of either tokenizer, directly or through the factories (SPI names simplePattern and simplePatternSplit, for example in CustomAnalyzer or a Solr schema), or through downstream tokenizers built on them, whose pattern has the shape above. A typical intent: keep an emoji-plus-something token such as 🔥5, and otherwise strip the emoji from words.
  • Opt-in. Both classes and factories are @lucene.experimental, and no Lucene analyzer uses them by default.
  • What it takes. With such a pattern, ordinary text triggers it every time the character is not followed by the rest of a live alternative and the try does not reach the end of the input: the emoji right before a word (🔥hot) or a space (🔥 x), or inside a word for the split tokenizer (so🔥hot). 🔥5, where the alternative matches, is tokenized correctly.
  • Effect. Silent wrong tokens with offsets inside a surrogate pair, at any index size, with assertions on or off: an extra junk term (U+FFFD), the next word indexed under a U+FFFD-prefixed term (a search for the word misses the document), or a word cut into two terms (a search for the whole word misses, one for its tail matches). IndexWriter replaces lone surrogates with U+FFFD as documented, CheckIndex stays clean, and highlight snippets can contain unpaired surrogates of the document's own text. In the runs only the tokens of the value being tokenized changed. No hang was seen: in the hunt's cost probe (up to 2.4M chars, one aarch64 host) the per-char cost of stock and fixed code did not grow with input size.
  • How likely. Rare, by judgement: it needs all three pattern conditions (the wider shapes found by the doc's checks were not counted), and no report since 6.5.0 (2017) was found in the public sources searched. Real deployments were not surveyed.

Why it is a bug, not intended

#
  • The code says the automaton runs "in Unicode space, not UTF16", reads 🔥 as one code point, and skips it whole when the first step fails.
  • An alternative that matches nowhere changes the output: [^🔥 ]+ gives hot, 🔥[0-9]+|[^🔥 ]+ gives \uDD25hot.
  • PatternTokenizer and String.split keep the pair intact; Lucene fixed the same output as bugs in other analysis components.
The full argument350 words
  • The code works in code points. SimplePatternTokenizer.java:114 and SimplePatternSplitTokenizer.java:111: "The runDFA operates in Unicode space, not UTF16 (java's char)". nextCodePoint() joins surrogate pairs, and the first-step-fails branch (:158-160) skips the whole code point. On well-formed text a lone surrogate exists only because the false alarm rewinds into a code point that was read whole.
  • Contract (no javadoc sentence mentions surrogates, defines where a retry starts or promises code-point-aligned boundaries: that this is not intended is inferred from the code and the comparisons, not from a documented contract). Class javadoc (SimplePatternTokenizer.java:34-35): "The matching is greedy: the longest match at a given start point will be the next token." Factory javadoc (SimplePatternTokenizerFactory.java:41-43): "the longest token matching at a given point is created." The split tokenizer is "just like SimplePatternTokenizer except that the pattern should make valid token separator characters, like String.split" (SimplePatternSplitTokenizer.java:33-34).
  • An unused alternative changes the tokens. Within 🔥hot deal, [^🔥 ]+ and 🔥[0-9]+|[^🔥 ]+ match the same substrings, yet the first gives hot, deal and the second \uDD25hot, deal. The same holds for [^a-z🔥]+ vs [^a-z🔥]+|🔥! on so🔥hot now. No start-point rule allows that.
  • The documented comparisons keep the pair. PatternTokenizer (group 0) gives hot, deal and x; in split mode (group -1) and with String.split, so🔥hot now gives so🔥hot, now.
  • Supplementary input is in scope. Upstream testOneToken and testNoTokens feed TestUtil.randomUnicodeString through both tokenizers (with .*, which never fails a try); no dedicated test uses a failing alternative that starts with a supplementary character. TestRandomChains can build these tokenizers from random regexps that may contain surrogate pairs, but it checks consistency and offsets, not surrogate integrity.
  • Precedent. lucene/CHANGES.txt lists as bug fixes "LUCENE-8325: Fixed the smartcn tokenizer to not split UTF-16 surrogate pairs" and "GITHUB#15899, GITHUB#15900: Improve TruncateTokenFilter to truncate on codepoints not chars and no longer produce half surrogates".
  • History. The false-alarm line is in the first commit (93fa72f77bd, LUCENE-7465) next to the Unicode-space comment; the issue (#8517) never discusses surrogates or where a retry starts.
The devil's-advocate check133 words

The strongest case for "intended": the pattern itself accepts lone surrogate code points ([^🔥 ] does), so the tokenizer only does what the automaton allows; both classes are @lucene.experimental; buffers and offsets count chars; and the comment says "push back all but the first character".

Why it fails: on well-formed text the automaton would never see a lone surrogate if the tokenizer kept the code points it read whole; java.util.regex gives [^🔥 ] the same meaning yet keeps the pair intact on these inputs; the same loop skips whole code points on its other no-match path; and the unused-alternative example shows the output is not a function of the pattern's language. @lucene.experimental marks API instability, not permission for malformed terms. Cross-model reviews (reading only) rated the works-as-designed case weak.

Suggested fix

#

Recommended Push back all but the first code point (validated)

Push back all but the first code point on a false alarm: record Character.charCount(ch) of the attempt's first code point and call pushBack(tokenUpto - firstLen) (sepUpto - firstLen in the split tokenizer). Two lines per class; the repro, the pattern package and the whole analysis-common module (1,914 tests) pass with assertions on and off.

Variant: count the units the first read consumed (a verifier's fix, run)

#

final int firstLen = tokenUpto; (sepUpto in the split tokenizer) right after the first nextCodePoint(), then the same pushBack(... - firstLen). This is the independent fix of verifier: its own 8-test JUnit passes 8 of 8 (-ea, -da) and the upstream suites 29 of 29 on main ea57360912ed, and this doc's repro passes 5 of 5 with it shadowed on main a9779ef3c193 (-ea, -da).

Trade-offs

The same as Character.charCount(ch) on well-formed text. On malformed text (an unpaired high surrogate, which nextCodePoint() joins with the next unit unchecked) it still counts exactly the units read; that is reasoned from the code, not tested.

Workaround without a Lucene change: exclude the surrogate range (validated on stock)

#

For patterns built in Java code, add \uD800-\uDFFF to every negated class, so a retry at a lone half dies at its first step and is skipped whole: 🔥[0-9]+|[^🔥 \uD800-\uDFFF]+ and [^a-z🔥\uD800-\uDFFF]+|🔥! give the expected tokens on all five inputs of this doc on stock main.

Trade-offs

Needs lone surrogate characters in the pattern string, which text configuration formats may not carry (not tried there); every user must know about it.

Downstream note

Elasticsearch and OpenSearch build their simple_pattern and simple_pattern_split tokenizers on these classes, so the same patterns give the same wrong tokens there (read in their sources, not run there).

How it was found

#

A bounded-exhaustive check ran both real tokenizers on every string of up to 6 code points over {a, b, space, -, 😀} with 39 patterns and compared them with the javadoc's longest-match rule. 13,741 runs per tokenizer produced a lone surrogate, all from 2 patterns; reading the code then located the false-alarm push-back.

The method in full183 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier). The checker ran the real SimplePatternTokenizer and SimplePatternSplitTokenizer on all 19,531 strings of up to 6 code points over {a, b, space, -, U+1F600}, for 39 RegExp patterns (4,140,572 checks, including PatternTokenizer controls), against a reference written from the class javadoc: the greedy longest match per start point, with membership decided by java.util.regex. The mismatch class "lone surrogate in token" (13,741 runs per tokenizer) came only from the 2 pool patterns that start an alternative with the emoji and exclude it from a negated class (😀a|[^😀a ]+, 😀😀|[^😀 ]\-). Reading the code then located pushBack(tokenUpto - 1) / pushBack(sepUpto - 1). The pool had no explicit range reaching into the surrogate block, so the check did not cover the range shapes of the trigger that the doc's checks found later.

The finder then wrote a JUnit through the public constructors (2 of 2 fail on main with assertions on and off, 10.5.2 and 9.12.3) and the one-line fix, which removes exactly this class from the check. Independent checks followed (below).

Bug record

#

LFV-545, snapshot of 2026-10-29

Registry title
SimplePatternTokenizer and SimplePatternSplitTokenizer restart a failed match one UTF-16 unit after a supplementary start character, so they can emit tokens that start or end inside a surrogate pair
Area
analysis / pattern tokenizers (analysis-common: SimplePatternTokenizer, SimplePatternSplitTokenizer and their simplePattern / simplePatternSplit factories)
Priority
Low, rank 436: A surrogate pair is split only with a narrow pattern shape in the opt-in simple-pattern tokenizers, a rare-input surrogate-cut analysis row like LFV-459.
Impact class
silent wrong results
Impact note
Hits only applications that choose SimplePatternTokenizer or SimplePatternSplitTokenizer (directly or through the simplePattern / simplePatternSplit factories) with a pattern that starts a longer alternative with a supplementary character (an emoji or other non-BMP literal or range) and elsewhere accepts that character's low surrogate (typically a negated class that excludes the character, '.', or a hand-built automaton): then each attempt that starts at that character and dies before the end of the input restarts inside the surrogate pair, so SimplePatternTokenizer emits an extra lone-surrogate term or glues the low surrogate onto the next word (stored as U+FFFD, offsets inside the pair) and SimplePatternSplitTokenizer cuts a term after the high surrogate and loses the original term, at any scale, with -ea and -da and no exception; patterns that do not name supplementary characters, or whose classes treat the character and its surrogates alike (for example [^ ]+), are not affected.
Summary
You tokenize 'E x', where E is an emoji such as U+1F525, with SimplePatternTokenizer and the pattern E[a-z]+|[^E ]+ (E followed by letters, or a run of characters other than E and space) and expect the single token 'x' [3,4): the attempt at E dies at the space, and the tokenizer, which steps its automaton over code points, should move on to the next code point (PatternTokenizer and java.util.regex give exactly [x]). Instead it also emits a token made of E's lone low surrogate U+DD25 at offsets [1,2), which the index stores as U+FFFD, because the failed-attempt branch pushes back all but one UTF-16 unit and so restarts in the middle of the pair. SimplePatternSplitTokenizer has the same step: separator Ea|[^Ea ]+ on 'Eb' yields the lone high surrogate [0,1) instead of the token 'E' [0,2), and with separator [^a-zE]+|E! the text 'abEcd' becomes 'ab' plus a lone high surrogate, then 'cd', instead of the one token 'abEcd'; nothing throws.
