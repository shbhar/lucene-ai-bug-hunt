CompiledAutomaton.floor throws NullPointerException for empty, match-all and single-term automata, and for non-deterministic ones

CompiledAutomaton.floor should return the largest accepted term <= the input, but for the compact forms the default constructor builds for an empty, match-all or single-term language, and since 10.0.0 for NFA-backed ones, it throws a NullPointerException. Example: new CompiledAutomaton(Automata.makeString("m")).floor("x") should return "m".

The finding in 30 seconds

#

The default constructor stores three easy languages in a compact form with no state machine, and since 10.0.0 runs an automaton that stays non-deterministic in UTF-8 on a separate NFA runner. floor assumes a DFA is always there.

Compiled automata and floor

#
  1. Lucene turns regexp, wildcard and fuzzy patterns into an Automaton and compiles it into a CompiledAutomaton, which matches the UTF-8 bytes of the terms in the index.
  2. With simplify=true, which the one-argument constructor passes, three easy languages get a compact form with no state machine: NONE (matches nothing), ALL (matches everything, when an approximate test recognizes it) and SINGLE (one fixed term, kept in term). Everything else is NORMAL.
  3. A NORMAL instance holds a DFA in runAutomaton, or, since 10.0.0, an NFA runner instead when the input and its UTF-8 form are both non-deterministic. getByteRunnable() returns whichever one exists.
  4. floor(input, output) returns the largest accepted term <= input, or null. Fuzzy queries use it to pick the term to resume from when they move to a smaller edit distance.

The finding, step by step

#
  1. You compile the one-term language {"m"} with the documented one-argument constructor, new CompiledAutomaton(Automata.makeString("m")), and call floor(new BytesRef("x"), new BytesRefBuilder()).
  2. You expect "m": floor returns the largest accepted term <= the input, or null if there is none. The same language compiled with simplify=false does return "m".
  3. You get NullPointerException: ... because "this.runAutomaton" is null, with assertions on and off. The constructor stored {"m"} as type SINGLE, a bare term with no state machine, and floor always steps through the state machine without checking the type.
  4. The empty language (NONE, expected null) and the match-all language (ALL, expected the input) fail the same way, and since 10.0.0 so does an NFA-backed one: new RegExp("(a|ab)c").toAutomaton() should give floor("b") = "ac"; 9.12.3 still returns it.
  5. Only code that calls floor itself is hit, but then on every call; since 10.0.0 RegexpQuery("m").getCompiled() and WildcardQuery("*").getCompiled() hand out failing instances. Lucene's own caller, the fuzzy query, always passes a plain DFA.

Who is affected

#

Only application code that calls the experimental floor itself: on an instance the one-argument constructor built for an empty, match-all or single-term language (every release since 4.0.0), or on any NFA-backed instance (10.0.0 on). Every such call fails. Lucene's own queries never reach it, and the failure is a loud exception, not a wrong result.

Mechanism, terms and numbers655 words

CompiledAutomaton.floor(input, output) promises the largest term the automaton accepts that is <= input, or null. The documented one-argument constructor passes simplify=true, which stores an empty or single-string language, and a match-all one its approximate totality test recognizes, as type NONE, SINGLE or ALL with no state machine (runAutomaton and automaton are null); since 10.0.0 an automaton that is non-deterministic, and still so in UTF-8, stays type NORMAL but runs on an NFARunAutomaton, again with runAutomaton null. floor walks runAutomaton and automaton without checking the type, so for all four forms it throws NullPointerException instead of answering: new CompiledAutomaton(Automata.makeString("m")).floor("x") throws where "m" is expected, with assertions on and off. NONE, ALL and SINGLE have failed since the method was created (LUCENE-3030, first released in 4.0.0); the NFA form is a 9.x-to-10.0 regression (#225), where 9.12.3 returns the right floor. Only application code that calls the experimental floor itself is hit: Lucene's own caller (FuzzyTermsEnum) uses plain DFAs. A fix that answers the three special forms directly and runs NORMAL through the DFA-or-NFA accessors was validated; for an NFA with a dead state it still returns a wrong floor, so it needs the no-dead-states rule the class already states for DFAs.

The bug (main 645d4fe14a20, CompiledAutomaton.java)

#
  1. The default constructor simplifies. public CompiledAutomaton(Automaton automaton): "Create this, passing simplify=true, so that we try to simplify the automaton" (:106-109).
  2. Three special forms keep no state machine. With simplify and a DFA (:160), an empty language becomes NONE (:166-177), a total one ALL when the totality test recognizes it (:181-199; the code comment calls it "only approximate, because automaton may not be minimal") and a single string SINGLE (:203-221). Each branch sets runAutomaton = null and this.automaton = null and returns.
  3. NFAs keep no DFA either (10.0.0 and later). Other input becomes NORMAL (:224). If it and its UTF-8 form are both non-deterministic (:253), with or without simplify, the constructor sets automaton and runAutomaton to null and builds an NFARunAutomaton (:253-257). The class javadoc allows this: the automaton "could either be deterministic or non-deterministic", and an NFA "will be executed using NFARunAutomaton" (:36-40).
  4. floor never checks. floor (:390) calls runAutomaton.isAccept(state) for an empty input (:398), runAutomaton.step(state, label) for each byte (:411), then automaton.getNumTransitions (:433) and addTail, which walks automaton too (:277-339). There is no switch (type) and no null check.
  5. The siblings do check. getTermsEnum (:348-362) and visit (:365-382) switch on the type, and NORMAL consumers such as AutomatonTermsEnum use getByteRunnable() / getTransitionAccessor() (:486-493, :516-523; AutomatonTermsEnum.java:85-86). Where Lucene requires NORMAL it rejects the other forms with IllegalArgumentException: Terms.intersect, which also documents it (Terms.java:58, :79-81), and the AutomatonTermsEnum constructor (AutomatonTermsEnum.java:81-83; its javadoc does not mention it).
  6. Why Lucene itself never hits it. The only non-test caller, FuzzyTermsEnum.getAutomatonEnum (FuzzyTermsEnum.java:185), gets its automata from FuzzyAutomatonBuilder as new CompiledAutomaton(levBuilder.toAutomaton(i, prefix), true, false) (FuzzyAutomatonBuilder.java:63, :73): simplify=false Levenshtein DFAs, always NORMAL with a runAutomaton. Upstream's floor test builds its automata the same way (TestCompiledAutomaton.java:38-60).

Exposure and likelihood224 words
  • Who is hit. Code that calls CompiledAutomaton.floor directly. The failing instances come from ordinary inputs: the documented one-argument constructor on a single-string, empty or any-string automaton, a non-deterministic automaton on 10.x that stays non-deterministic in UTF-8 (for example new RegExp("(a|ab)c").toAutomaton(), since RegExp stopped determinizing in 10.0.0), and AutomatonQuery.getCompiled() of RegexpQuery("m") (SINGLE) and WildcardQuery("*") (ALL), executed on 10.0.0, 10.5.2, 10.6.0 and main.
  • Every call. Once code calls floor on such an instance, it fails deterministically, with assertions on and off. One term is enough; index size does not matter.
  • Default vs opt-in. The trigger is the default constructor with ordinary inputs, but calling floor is an expert, opt-in act: the class is @lucene.experimental.
  • Not hit. Lucene's own query paths: the only in-tree caller, the fuzzy query's terms enum, passes simplify=false Levenshtein DFAs. A code search of the default branches of Elasticsearch, OpenSearch and Solr found no call of floor on a CompiledAutomaton (not exhaustive).
  • What goes wrong. A NullPointerException that does not name the real restriction, instead of the documented result. No wrong result, no hang, no lasting state.
  • Regression for NFAs. On 9.12.3 the constructor and RegExp determinize, so floor("b") of (a|ab)c returns "ac"; from 10.0.0 it throws. In the 10.x releases the default RegexpQuery still holds a DFA; on main (#15939, unreleased) it keeps the NFA, so RegexpQuery("(a|ab)c").getCompiled() fails there too.

Why it looks unintended

#
  • floor's javadoc states no condition, and the documented default constructor is what builds the failing forms.
  • The sibling methods handle these forms; where Lucene really requires NORMAL, as in Terms.intersect, it says so and throws IllegalArgumentException.
  • Upstream fixed this pattern in Terms.intersect as a bug (LUCENE-7576); for NFAs, a call that worked on 9.12.3 throws since 10.0.0.
The full argument301 words
  • The contract is unconditional. "Finds largest term accepted by this Automaton, that's <= the provided input term. ... The returned result is either the provided output, or null if there is no floor term (ie, the provided input term is before the first term accepted by this Automaton)" (CompiledAutomaton.java:384-389). No type, no "NORMAL only".
  • The default constructor produces the failing forms. It is documented as passing simplify=true (:106), so NONE, ALL and SINGLE are what a plain new CompiledAutomaton(a) gives for those languages.
  • NFAs are accepted by the class. The class javadoc accepts non-deterministic automata (:36-40), and an NFA-backed instance has type NORMAL (:224).
  • The NFA migration skipped floor. LUCENE-10010 / #225 (zhaih, 2021) added the NFA runner and moved AutomatonTermsEnum and the codecs' intersect enums to getByteRunnable() / getTransitionAccessor(); floor is not in its diff. visit() was missed too and moved only by #15961 (2026, main only), whose description says "some code paths (especially query visiting/highlighting and equality checks) still assumed a DFA-only representation". "floor" appears 0 times in the discussions of #225, #485, #11049 and #15961.
  • Upstream fixed the same pattern as a bug. LUCENE-7576, CHANGES 6.4.0 "Bug Fixes": "Fix Terms.intersect in the default codec to detect when the incoming automaton is a special case and throw a clearer exception than NullPointerException" (lucene/CHANGES.txt:8691-8693). Michael McCandless wrote there: "This is unfortunately a confusing expert API; other terms dicts were checking that the provided compiled automaton is NORMAL and throwing a clearer exception if not, so I carried that same check over ... I also added a note to the javadocs for Terms.intersect." floor got neither the check nor the note.
  • Nothing pins the current behaviour. No test, javadoc, CHANGES or MIGRATE entry says floor should throw for these forms.
The devil's-advocate check172 words

The strongest case for "intended" (a devil's-advocate verifier, the cross-model reviews, a tie-break): the runAutomaton and automaton fields are documented "only valid for NORMAL" (:69-80); the only in-tree caller and the only test use simplify=false DFAs; the class is @lucene.experimental; MIGRATE.md for 10.0 says "It is the responsibility of the caller to call Operations.determinize() for DFA execution" (lucene/MIGRATE.md:922-926); and floor takes a BytesRefBuilder, which is @lucene.internal.

Why it fails: the "only valid for NORMAL" notes are on fields, not on floor, and an NFA-backed instance is NORMAL. @lucene.experimental means the API may change between releases, not that a public method may throw an undocumented NPE on legal input; LUCENE-7576 treated exactly that as a bug in an equally expert API. The MIGRATE note covers the NFA form at most: the minimal repro (makeString("m")) is already a DFA and fails in every release since 4.0.0. BytesRefBuilder is also a required parameter of public non-internal core APIs, for example Term(String, BytesRefBuilder) (Term.java:63).

Suggested fix

#

Recommended Answer the special forms, run NORMAL on the DFA or the NFA (recommended)

Answer NONE (null), ALL (the input) and SINGLE (the term if <= the input) at the top of floor, and run NORMAL through getByteRunnable() and getTransitionAccessor() (+39/-15). The repro, 2,578 core tests, a 50,000-call differential check and lint pass. An NFA with a dead state still gets a wrong floor, so NFAs need the no-dead-states rule too.

switch (type) {
  case NONE: return null;
  case ALL: output.copyBytes(input); return output.get();
  case SINGLE:
    if (term.compareTo(input) <= 0) { output.copyBytes(term); return output.get(); }
    return null;
  case NORMAL: break;
}
// NORMAL: a DFA or an NFA; the rest of floor and addTail use these instead of the fields
final ByteRunnable runnable = getByteRunnable();
final TransitionAccessor accessor = getTransitionAccessor();

Answer the special forms, run NORMAL on the DFA or the NFA (recommended) (validated by the checks)

#

At the top of floor, answer the three special forms directly; for NORMAL, read the DFA-or-NFA accessors that AutomatonTermsEnum uses (since #225) and visit() uses (since #15961) instead of the runAutomaton and automaton fields, also inside addTail. The rest of the diff renames the field uses to the two locals. Condensed:

  case SINGLE:

    return null;
  case NORMAL: break;

// NORMAL: a DFA or an NFA; the rest of floor and addTail use these instead of the fields
final ByteRunnable runnable = getByteRunnable();
final TransitionAccessor accessor = getTransitionAccessor();

Trade-offs

  • ALL returns the input. Exact for a binary ALL and for valid UTF-8 input. For a unicode ALL and input its UTF-8 form does not accept (for example the byte ff), it returns the input anyway (executed: input [ff] gives [ff]). For such input no largest accepted term exists: any accepted term below it can be extended, for example by a NUL character, and still stays below it. So any answer is a convention a reviewer may want documented. CompiledAutomaton does not keep isBinary, so floor cannot tell the two ALLs apart.
  • NFA path: correct only without dead states. It walks the lazily determinized states of NFARunAutomaton, as AutomatonTermsEnum does, and like the DFA path it assumes every state can still reach an accept state. The class javadoc requires that of DFAs only ("must not have dead states"). An independent reviewer from another model family (OpenAI GPT-5.6) gave a counterexample, which we then ran: the NFA for {"b"} with 0 -[a-b]-> 1 (not accepting, no outgoing transitions) and 0 -b-> 2 (accepting). With the fix, floor("ab") returns "a" (not in the language) with assertions off and throws AssertionError with them on, where null is right; a second NFA with a dead state, {"b", "bc"}, fails the same way. That matches what 9.12.3 returns for the same NFAs (its constructor determinizes and keeps the dead state) and what main returns today for the same language built as a DFA with a dead state and simplify=false. After Operations.removeDeadStates the second NFA is still NFA-backed and the fix gives the right floor for every input tried. So the fix should come with one of: extending the class javadoc's no-dead-states rule to NFAs (the caller then trims, as for DFAs today), or removing dead states in the constructor's NFA branch (not built). Lucene's own caller keeps the unchanged DFA path.
  • Shared scratch field. Like the stock code, the fix uses the per-instance transition field in floor and addTail, although the class javadoc calls the class immutable. It changes nothing about concurrent floor calls on one instance.
  • Cost. One switch per call; no hot path calls floor on these forms.
  • Not covered. The separate non-termination of floor on some infinite languages (another bug in the same method) is unchanged.

Document and reject, as LUCENE-7576 did for Terms.intersect (not built)

#

Trade-offs

History

#

Born with the method in LUCENE-3030 (b7846ffaa1f, 2011; first release 4.0.0) for NONE, ALL and SINGLE. The NFA form came with #225 (c972c6a7754e, 2021; first release 10.0.0; 9.12.3 still determinizes and works). Affected through 10.6.0 and main; not fixed.

Versions tested8 rows

NONE, ALL, SINGLE. Registry title
CompiledAutomaton.floor throws NullPointerException for NONE, ALL and SINGLE automata (what the documented one-argument constructor builds from an empty, any-string or single-string automaton) and, since 10.0.0, for NFA-backed NORMAL automata
Area
util / automaton
Priority
Low, rank 855: CompiledAutomaton.floor throws a loud NPE for ordinary SINGLE, NONE, ALL and NFA automata, but only for direct callers of this experimental method.
Impact class
crash
Impact note
Only application code that calls the experimental CompiledAutomaton.floor itself is hit, but then on every call for instances that the documented one-argument constructor builds from an empty, any-string or single-string automaton (every release since 4.0.0) and for any non-deterministic automaton, for example RegExp("(a|ab)c") or AutomatonQuery.getCompiled() of ordinary RegexpQuery and WildcardQuery inputs (since 10.0.0); Lucene's only in-tree caller, FuzzyTermsEnum, passes simplify=false Levenshtein DFAs and never reaches it, no Lucene query path calls floor on these shapes, and the failure is a loud exception, not a wrong result.
Summary
You build a CompiledAutomaton with the documented one-argument constructor, for example from new RegExp("m").toAutomaton() (type SINGLE), Automata.makeEmpty() (NONE), Automata.makeAnyString() (ALL) or, on 10.x, the non-deterministic RegExp("(a|ab)c").toAutomaton() (type NORMAL, run by NFARunAutomaton), and call floor(input, output). You expect what the javadoc promises, the largest accepted term <= input or null: floor("x") = "m", null, "x", and floor("b") = "ac" (the value the determinized form of the same language returns). Instead floor throws NullPointerException ('Cannot invoke ByteRunAutomaton.step(int, int) because this.runAutomaton is null'), because it always walks runAutomaton and the constructor leaves runAutomaton null for these four shapes.
