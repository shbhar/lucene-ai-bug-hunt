A codec file whose extension contains '_' is recorded under a wrong name, so the first flush fails

A custom codec that names a per-segment file _0.my_ext cannot flush it: SegmentInfo records the non-existent _0_ext, so the flush throws NoSuchFileException: _0_ext and closes the IndexWriter (every release since 5.0.0). On an index with an earlier commit, the file left behind then blocks every new IndexWriter.

The finding in 30 seconds

#

Lucene names a segment's files <segment>(_<suffix>).<extension>. When it records a new segment's files, it cuts the segment name off each name and puts the segment's own name back. It looks for the cut at the first _ and uses the first . only if there is no _, so _0.my_ext is cut inside its extension.

How Lucene names a segment's files

#
  1. All files of a segment start with the segment's name, for example _0.si, _0.fdt, _0_1.liv (a generation) or _0_Lucene104_0.doc (a per-field format suffix).
  2. Codecs build these names with IndexFileNames.segmentFileName(segment, suffix, extension); its javadoc says all custom files should be named with it.
  3. SegmentInfo stores each name as its own segment name plus the rest of the file name (namedForThisSegment), so that file names can follow a segment that gets a new name, for example in addIndexes.

The finding, step by step

#
  1. A custom codec's stored-fields writer also writes one extra file named IndexFileNames.segmentFileName("_0", "", "my_ext"), which is _0.my_ext. CODEC_FILE_PATTERN, which SegmentInfo checks, accepts that name.
  2. Add one document and call commit(). You expect the commit to succeed and the segment to list _0.my_ext, as it lists _0.myext when the extension is myext.
  3. Instead SegmentInfo looks for the end of the segment name at the first _ after position 0, which sits inside the extension: _0.my | _ext. It records _0 + _ext = _0_ext, a file that does not exist.
  4. The flush asks the directory for the size of _0_ext and gets NoSuchFileException: _0_ext, with assertions on and off. The IndexWriter closes as tragic, the document is lost and nothing is committed.

Who is affected

#

Only custom codec code: a format that writes a per-segment file with no segment suffix and a _ in its extension (stored fields, term vectors, norms, points, field infos, or a format used without the per-field wrappers); no in-tree format does. That flush fails, and on an index with an earlier commit the file left behind blocks every new IndexWriter.

Mechanism, terms and numbers416 words

When a segment is flushed, SegmentInfo stores every file name it is given as segmentName + IndexFileNames.stripSegmentName(file). stripSegmentName ends the segment name at the first _ after position 0 whenever the name has one, and uses the first . only when it has none. That is right for every name Lucene records in a segment, but a name whose extension contains _ is cut inside the extension. So a custom format that writes IndexFileNames.segmentFileName(si.name, "", "my_ext") = _0.my_ext, a name CODEC_FILE_PATTERN accepts, gets the non-existent _0_ext recorded instead, and the flush fails in SegmentCommitInfo.sizeInBytes with java.nio.file.NoSuchFileException: _0_ext. The IndexWriter closes as tragic, buffered documents are lost and no commit is written, with assertions on and off, with or without compound files. On an index that already has a commit, the file left behind then makes every new IndexWriter on that index throw NumberFormatException (the same split, in IndexFileDeleter) until someone deletes it by hand; readers still open the last commit. The flush fails in every release from 5.0.0 through 10.6.0 and main; on 4.10.x the same codec committed, but the next IndexWriter open failed on the same split. Using the _ only when it comes before the first . fixes it.

  // If it is a .del file, there's an '_' after the first character

Exposure and likelihood351 words
  • Who is hit. Out-of-tree codec code whose format writes a per-segment file with an empty segment suffix and an extension containing _. By reading, that is reachable through stored fields, term vectors, norms, points and field-infos formats, and through a postings, doc-values or vectors format installed directly as the codec's format. Executed: a stored-fields format (this doc's test), a field-infos format (the independent reproducer) and a postings format installed directly (the cross-model reviewer). Files written through PerFieldPostingsFormat, PerFieldDocValuesFormat or PerFieldKnnVectorsFormat carry a suffix such as _Lucene104_0 whose _ comes before the ., so they split correctly. The default codec is not affected.
  • What they see. A NoSuchFileException that names a file the codec never wrote, on the first flush of a segment that has such a file, with assertions on and off, with or without compound files. The IndexWriter closes as tragic, the buffered documents are lost and nothing new is committed. Nothing points at the extension as the cause.
  • What it leaves behind. No wrong results, and the last commit stays readable. But on an index that already has a commit, the failed flush leaves the codec's file (_1.my_ext) in the directory, and from then on every new IndexWriter on that index, even one with the default codec, throws NumberFormatException: For input string: "1.my" under radix 36 from IndexFileDeleter.inflateGens (IndexFileDeleter.java:291, :300, called by the constructor at :217): the same split, through parseSegmentName, gives the segment name _1.my. That lasts until someone deletes the file by hand; DirectoryReader still opens the last commit (executed probe). With fix A the second commit succeeds.
  • Not only the first commit. A format that writes such a file only for some segments commits the others until a flush writes one. Merged segments and segments added by addIndexes record their files the same way (IndexWriter.java:5622, :3602, :3641, :3676), so a format that writes such a file while merging would hit the same renaming there (by reading, not run).
  • Age. The flush failure is in every release since 5.0.0; not new in 10.6.

Why it looks unintended

#
  • segmentFileName builds the name and says all custom files should be named with it; CODEC_FILE_PATTERN, which SegmentInfo checks, accepts it.
  • The same class treats everything after the first . as the extension (stripExtension, getExtension, parseGeneration).
  • No version handles or rejects it (4.10.x fails at the next IndexWriter open, 5.0.0 on at the flush); nothing forbids _ in an extension.
The full argument267 words
  • The API builds and accepts the name. segmentFileName: "The format of the filename is: <segmentName>(_<name>)(.<ext>)" and "all custom files should be named using this method, or otherwise some structures may fail to handle them properly"; it asserts only that ext does not start with . (IndexFileNames.java:77-106). SegmentWriteState tells new postings-format authors that "any files you write/read must be derived using this suffix (use IndexFileNames#segmentFileName(String,String,String))" (SegmentWriteState.java:64-68). CODEC_FILE_PATTERN _[a-z0-9]+(_.*)?\..*, "All files created by codecs much match this pattern (checked in SegmentInfo)", accepts _0.my_ext (IndexFileNames.java:198-199).
  • Same class, other rule. stripExtension and getExtension define the extension as "anything after the first '.'" (IndexFileNames.java:174-196); parseGeneration strips the extension at the first . before splitting on _ (:146-159).
  • Accept, then record another file. Lucene's own check accepts _0.my_ext and SegmentInfo then records _0_ext; that is not a defensible outcome under any reading.
  • No version handles it, and none rejects it. It is not a regression in the strict sense. 4.10.3 and 4.10.4 commit the same codec and list _0.my_ext, but reopening an IndexWriter on that index throws NumberFormatException: For input string: "0.my" from IndexFileDeleter.inflateGens (4.10.4 IndexFileDeleter.java:297, :300), the same split; with the extension myext the reopen works (executed). Since 5.0.0, when SegmentInfo started renaming files (LUCENE-5412 / LUCENE-5969), the failure comes at the first flush; those threads never discuss a _ inside an extension. Every version accepts the name and then fails with an exception about something else.
  • No recorded intent. No javadoc, package doc, test, CHANGES or MIGRATE entry, or issue says an extension must not contain _.
The devil's-advocate check172 words

Strongest case for "intended" (from the cross-model reviewer, which rated it only moderate itself): IndexFileNames is @lucene.internal (IndexFileNames.java:32); the stripSegmentName javadoc, "removes whatever comes before the first '.', or the second '_'", does not say which boundary wins; every in-tree extension is alphanumeric, and such an extension has never worked end to end (4.10.x fails at the reopen), so _-free extensions may be an unwritten convention.

Why it fails: the failing path runs through SegmentInfo and FilterCodec, public @lucene.experimental extension points; a codec does not even need IndexFileNames to produce the name (si.name + ".my_ext" is the same string); and Lucene's own validation accepts the name before recording another one. Fix B (reject the name with a clear error and document the rule) is as legitimate an answer as fix A if the maintainers see _-free extensions as the rule; what is not defensible is accepting the name and then failing with a NoSuchFileException for a file nobody wrote. The intended-behaviour check and the adjudication rejected the argument.

Suggested fix

#

Recommended A: use the '_' only when it comes before the first '.'

In IndexFileNames.indexOfSegmentName, use the _ only when it comes before the first .. Validated against the repro (passes with assertions on and off) and seven targeted index, directory and compound-file suites (288 tests). Every name Lucene records in a segment splits as before, and existing indexes read the same; no format change.

private static int indexOfSegmentName(String filename) {
  // If it is a .del file, there's an '_' after the first character
  int idx = filename.indexOf('_', 1);
  int dot = filename.indexOf('.');
  if (idx == -1 || (dot != -1 && dot < idx)) {
    // If it's not, or the '_' is in the extension, strip everything that's before the '.'
    idx = dot;
  }
  return idx;
}

A: use the '_' only when it comes before the first '.' (validated by the checks) (recommended)

#

Three lines replaced and one added (+4/-3) in indexOfSegmentName (IndexFileNames.java:118-127), shared by stripSegmentName and parseSegmentName.

private static int indexOfSegmentName(String filename) {
  // If it is a .del file, there's an '_' after the first character
  int idx = filename.indexOf('_', 1);
  int dot = filename.indexOf('.');
  if (idx == -1 || (dot != -1 && dot < idx)) {
    // If it's not, or the '_' is in the extension, strip everything that's before the '.'
    idx = dot;
  }
  return idx;
}

Trade-offs

  • Names that have no _ after position 0, or whose first such _ comes before the first . (_0.si, _0_1.liv, _0_Lucene90_0.dvd, segments_N, pending_segments_N), split exactly as before. Only names with a . before that _ change: stripSegmentName("_0.my_ext") becomes .my_ext, parseSegmentName becomes _0.
  • Lucene itself makes such names only for scratch files while it flushes an index with an index sort: _0.fdm__0.tmp, _0.fdt__1.tmp, _0.fdx__4.tmp (SortingStoredFieldsConsumer.java:97-98, TrackingTmpOutputDirectoryWrapper.java:39, Directory.java:224-227). Stock parseSegmentName gives _0.fdt for them and fix A gives _0; the commit succeeds either way (executed). Harmless: .tmp files never reach SegmentInfo (checkFileNames rejects them) and inflateGens skips them.
  • A stray or foreign file of that shape in the index directory is also split the new way by IndexFileDeleter and by MMapDirectory's grouping.
  • Every name SegmentInfo has recorded since 5.0.0 came from namedForThisSegment, so its first _ after position 0, if it has one, directly follows the segment name, before any .; such names read back the same (by reading).
  • The other callers (compound-file entry names in Lucene90CompoundFormat / Lucene90CompoundReader and in SimpleTextCompoundFormat, IndexFileDeleter.inflateGens, MMapDirectory.GROUP_BY_SEGMENT, the files check in Lucene99SegmentInfoFormat) then also see the right segment name for such files. One extra indexOf per call.

B: reject '_' in an extension with a clear message

#

Throw an IllegalArgumentException that names the file: in segmentFileName (when the codec builds the name, before anything is written) and/or in SegmentInfo.checkFileNames (the backstop for names built by hand; it fires during the flush). Document the rule on segmentFileName and CODEC_FILE_PATTERN.

Trade-offs

Not run. Keeps the parser as is and makes the convention explicit, but such a codec still cannot use the name. It fits if the maintainers see _-free extensions as the rule.

Downstream note

#

Products that let users plug in their own codec or format code should know that a _ in a file extension makes every flush of a segment with such a file fail with a misleading NoSuchFileException; no query, document or analysis input can trigger it.

How it was found

#

A semi-formal proof-obligation check of IndexFileNames' naming contract: stripSegmentName and parseSegmentName must invert segmentFileName for every name CODEC_FILE_PATTERN accepts. _0.my_ext breaks it, and an executable JUnit test on main then showed the flush failure.

The method in full78 words

Method: semi-formal (2026-11-04, main 5adff78bb168).

  • The obligation: for every segment name, suffix and extension that segmentFileName turns into a name CODEC_FILE_PATTERN accepts, stripSegmentName returns the part after the segment name and parseSegmentName the segment name, so that SegmentInfo.namedForThisSegment gives back the same file.
  • An extension containing _ breaks it, because indexOfSegmentName prefers any _ to the first ..
  • Witness: a public-API JUnit test with a FilterCodec that writes one such file, reduced to the one test shown here.

History

#

The flush failure came in 5.0.0 with LUCENE-5412 / LUCENE-5969 (d1a67913d4a, 2014), which made SegmentInfo re-derive every file name; the _-first split itself dates from 2010 (LUCENE-2455). 4.10.x commits the same codec but fails when an IndexWriter reopens the index; 5.0.0 through 10.6.0 and main fail at the flush.

Versions tested7 rows

Introduced (the flush failure) by d1a67913d4a "LUCENE-5969, LUCENE-5412: make .si immutable again, and make ancient writers read-only" (Robert Muir, 2014-09-25; Subversion era, no PR; trunk 250b215c65d and branch_5x 63782355cbe, 2014-09-27), which replaced setFiles = files / addAll(files) / add(file) with setFiles.add(namedForThisSegment(f)). The _-first split came with LUCENE-2455 (#3529, d6dd2e234e1, Shai Erera, 2010, first released in 3.1) and was moved unchanged into indexOfSegmentName by LUCENE-4130 (bc14cec6694, 2012). In 4.10.4 the split was already applied to codec file names when an IndexWriter opens and IndexFileDeleter scans the directory (IndexFileDeleter.java:297), by addIndexes(Directory) (IndexWriter.java:2846-2886) and, symmetrically and so harmlessly, by the compound-file writer and reader (CompoundFileWriter.java:219, :238; CompoundFileDirectory.java:284, :302, :317, :341). So on 4.10.3 and 4.10.4 reopening an IndexWriter on an index holding _0.my_ext fails with NumberFormatException: For input string: "0.my", and on 4.10.4 addIndexes(Directory) of such a segment fails with IllegalArgumentException: invalid codec filename '_0_ext'; 5.0.0 moved the failure to the first flush (not claimed separately). Executed: 4.10.3, 4.10.4, 5.0.0, 8.11.4, 9.12.3, 10.5.2, 10.6.0 and main; the releases in between are affected by reading (every release tag from 5.0.0 on carries d1a67913d4a or 63782355cbe and the same split). Not fixed: upstream main f72004515ec (2026-11-03) has the same code.

No in-tree format uses such a name, the last commit stays readable, and the codec author hits it in the first test; on an index with an earlier commit, the file left behind blocks every new IndexWriter until it is deleted by hand.

Summary
You write a custom codec whose format also writes one per-segment file named with IndexFileNames.segmentFileName(si.name, "", "my_ext"), which gives "_0.my_ext", a name that CODEC_FILE_PATTERN (checked by SegmentInfo) accepts, then add one document and commit. You expect the commit to succeed and the segment's files() to list "_0.my_ext", as it does for the extension "myext". Instead SegmentInfo records the file as "_0_ext", because IndexFileNames.indexOfSegmentName takes the '_' inside the extension as the end of the segment name, so the flush throws NoSuchFileException: _0_ext and the IndexWriter closes itself as tragic, losing the document.
