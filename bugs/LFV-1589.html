The finding in 30 seconds

#

A first registration of such a query is not the finding. No setting or subclass is needed. The test fails on each release from 8.2.0, the first with the monitor module, to 10.6.0 and on main and branch_11x, both unreleased. Not new in 11.0: 10.6.0 fails the same way. Rare; how often this happens in applications was not measured.

Background: three pieces

#
  1. A Monitor stores queries, each under an id, and reports for a document the stored queries that match it.
  2. It keeps a stored query as documents in an index of its own, the query index. A QueryDecomposer first splits the query into parts that can be run separately, such as the clauses of a disjunction; each part becomes one document.
  3. A register call deletes the old documents of each id it adds documents for: that is how a second call with the same id replaces a query. The module has a test named testUpdatesOverwriteOldQueries, which registers one id twice. The javadoc of register says only "Add new queries to the monitor".

The finding, step by step

#
  1. Register a query under an id on a Monitor built with its one-argument constructor: monitor.register(new MonitorQuery("q1", f:apple)). monitor.match for the document f:"apple" reports q1: getMatchCount() is 1.
  2. Register the id again with a new query: monitor.register(new MonitorQuery("q1", -f:pear)). The module's own test testUpdatesOverwriteOldQueries registers one id twice like this, with two term queries. -f:pear is a BooleanQuery with one MUST_NOT clause and matches no document: IndexSearcher over a MemoryIndex of the document counts 0. You expect q1 to answer for the new query, so that nothing is reported.
  3. Instead the call returns normally and monitor.match for the same document still reports q1: getMatchCount() is 1. No exception, with assertions on and off. A Monitor that stores its queries (one configured with an index path and a serializer) keeps returning the old query from getQuery("q1"), also after purgeCache and a reopen (run with -f:pear).
  4. Why: register deletes the old documents of an id only for the ids it is about to add documents for. The QueryDecomposer splits -f:pear into no part, so nothing is added for q1 and its old document stays in the query index. With MatchNoDocsQuery as the new query, which matches the same documents (none) and is one part, the old query is replaced.
  5. The new queries that ran: a BooleanQuery with only MUST_NOT clauses and minimumNumberShouldMatch 0 or 1; a BooleanQuery without clauses; a BoostQuery or a single MUST, FILTER or SHOULD clause around one of the two; a DisjunctionMaxQuery without disjuncts or with a pure negation as its only disjunct; and what the classic QueryParser builds from -pear, NOT pear and, over an analyzer that removes stop words, a string of stop words only. monitor.deleteById("q1") before the second call avoids it (run).

Who is affected

#

An application that changes a stored query by registering its id again, when the new query is of this kind: the caller expects the id to go quiet, and it goes on answering for the old query. No match is lost. Rare; how often applications replace a stored query by such a query was not measured.

Mechanism, terms and numbers1,241 words

You register a query under an id with Monitor.register and later call Monitor.register again with the same id and a new query, as the module's own test testUpdatesOverwriteOldQueries does with two term queries. If the new query is one that the Monitor's QueryDecomposer splits into no part, the call returns normally and the old query stays registered: Monitor.match keeps reporting the id for the documents the old query matches, and a Monitor that stores its queries keeps returning the old query from getQuery, also after purgeCache and after it is closed and reopened (run with -f:pear). The same call with MatchNoDocsQuery as the new query does replace the old one. No match is lost: each query of no part that ran matches no document, so the wrong result is a stale report under the id.

Why it looks unintended

#
  • The javadoc of register says only "Add new queries to the monitor". The code replaces for each id it adds documents for, and a test is named testUpdatesOverwriteOldQueries.
  • MatchNoDocsQuery, which matches the same documents (none), does replace: the form of the new query decides.
  • The call returns normally, without a signal. Maintainers may see more than one right behaviour.
The full argument490 words

What register promises, both sides. The javadoc of both overloads reads "Add new queries to the monitor" and "@param queries the MonitorQueries to add" (Monitor.java:147-151, :168-173 at 894d24e9b0c7). It says nothing about a second call with the same id, and the package documentation has no sentence on it either. That such a call replaces the query is what the code does: commitWithoutNotify deletes the old documents of each id it adds documents for, in the same commit (WritableQueryIndex.java:113-119). The module's own test TestMonitor.testUpdatesOverwriteOldQueries (TestMonitor.java:71-86) is named for the overwrite: it registers query1 with one term, registers query1 again with another term, and asserts that the document of the second term matches and that one query was run. Its two assertions do not check that the old query is gone: in a control run on main with the delete loop (:117-119) taken out of the method, both still hold while the query index holds two documents for the id.

The outcome follows the form of the new query. For the old query f:apple and the document f:"apple", each of these new queries matches no document. MatchNoDocsQuery, f:pear, +f:apple -f:apple, ConstantScoreQuery(-f:pear) and -f:pear with minimumNumberShouldMatch 2 replace the old query. -f:pear and a BooleanQuery without clauses do not (run on the four builds, assertions on and off).

The two base shapes have a defined meaning in core. BooleanQuery.rewrite returns MatchNoDocsQuery("empty BooleanQuery") and MatchNoDocsQuery("pure negative BooleanQuery") (BooleanQuery.java:268-276), and the documentation of the classic query syntax says of a lone NOT that such a search "will return no results" (queryparser/classic/package-info.java:330-333).

No signal. The call returns normally and getErrors() of the next match is empty, with assertions on and off. The update listener is called with the update, as it is for a first registration of such a query: an observation, not a ground.

More than one right behaviour. The test of this page expects the id to go quiet. Refusing such a query with an exception, or storing it as an entry that matches nothing so that getQuery returns it, would also end the silent outcome. Which one is right is the maintainers' call.

Where the structure comes from (read on 2026-11-24, not run). The monitor module is the project Luwak, added to Lucene in 2019. In that project the delete of the old version was issued for each query of an update, by its id, before the query was decomposed, until the commit 18fc64402b88 of 2015-11-06, "Move queryindex deletions into synchronized block". That commit is the change for Case 1 of flaxsearch/luwak#68, a race between one thread's delete and another thread's commit. It moved the delete into commit() and took the ids from the documents to add. Neither the issue (its description and four comments) nor the commit (its message and its diff of one file) has a sentence on a query of no part.

The devil's-advocate check340 words

The strongest case for "intended": the javadoc says register adds queries, so a query of no part adds nothing and the call has done what it says; a first registration of such a query also returns normally and registers nothing; the one test of the module that is named for the overwrite does not assert that the old query is gone; the structure has been the same since the module was added, and in the project it came from since 2015; and a query that can match nothing is an odd thing to store. It does not hold, for four reasons. (1) As a rule, "a query of no part is ignored" would make an update depend on how a query that matches nothing is written: MatchNoDocsQuery, f:pear, +f:apple -f:apple, ConstantScoreQuery(-f:pear) and -f:pear with minimumNumberShouldMatch 2 replace the old query, -f:pear and a BooleanQuery without clauses do not (run). (2) No text states such a rule: the javadoc of register, the package documentation and the module's tests TestMonitor and TestQueryDecomposer were read at 894d24e9b0c7, and none has a sentence or a case on a second register call with a query of no part; the guard in the method also serves deleteQueries and clear. (3) On a Monitor that stores its queries the id keeps a query string that the caller replaced, also after a reopen (run), and the call throws nothing. (4) The shapes are not exotic input: the classic QueryParser builds them from -pear, NOT pear and, over an analyzer that removes stop words, a string of stop words only (run), and its documentation says that a lone NOT "will return no results". That the test does not assert the removal changes nothing in what the code does: for each id it adds documents for, the method deletes the old documents (WritableQueryIndex.java:113-119). What stays open is which behaviour is right. The first registration of such a query, which registers nothing, can be defended and is not part of this finding.

Suggested fix

#

Recommended Take the ids to delete from the updates (a sketch that was run)

A sketch that was run, not a proposal: in WritableQueryIndex#commitWithoutNotify, take the ids to delete from the updates, not from the documents to add. Summary
You register a query under an id with Monitor.register and later call Monitor.register again with the same id and a new query, as the module's own test testUpdatesOverwriteOldQueries does with two term queries. If the new query is one that the Monitor's QueryDecomposer splits into no part, such as a BooleanQuery with only MUST_NOT clauses and minimumNumberShouldMatch 0 or 1 (-f:pear, which the classic QueryParser builds from 'NOT pear') or a BooleanQuery without clauses (which it builds from a string of stop words only when the analyzer removes them), you expect the id to answer for the new query, which matches no document, so that nothing is reported under it any more. Instead the call returns normally and the old query stays registered: Monitor.match keeps reporting the id for the documents the old query matches, and a Monitor that stores its queries keeps returning the old query from getQuery, also after it is closed and reopened, while the same call with MatchNoDocsQuery as the new query does replace the old one (the javadoc of register says only 'Add new queries to the monitor'; the replacement is what the module's code does for each id it adds documents for, and the module has a test named for it).
