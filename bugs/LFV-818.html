The bug in 30 seconds

#

ASCIIFoldingFilter replaces each non-ASCII character using a table of 1,242 entries grouped by output: one block of case labels folds to G, another to g. Six entries sit in the block of the opposite case, although each line's own comment names the letter's real case.

  1. You analyze text with LowerCaseFilter and then ASCIIFoldingFilter, at index and query time, and index the name "naǧib". ǧ is a small g with caron, used for example in Romani, Skolt Sami and Lakota and in romanized Arabic or Persian names.
  2. You expect the term "nagib": the filter folds characters to "their ASCII equivalents", ǧ is a g plus a caron, and in the same chain "ağa" becomes "aga".
  3. The fold table lists ǧ among the letters that become a capital G, so the term is "naGib". The query "nagib" finds 0 of 1 documents. "NAǦIB" is lower-cased to "naǧib" and becomes "naGib" too.
  4. Six entries are placed like this, each against its own Unicode-name comment: ǥ, ǧ → G; ꞅ → S and Ꞅ → s (a swapped pair); Ɐ → a; Ꜿ → c. A field that keeps case gets all six wrong.
  5. No error or warning, and preserveOriginal=true does not help: it only adds the unfolded token. Folding first and lower-casing afterwards hides the bug.

Who is affected

#

Applications that add ASCIIFoldingFilter (opt-in; no Lucene analyzer includes it) after lower-casing, or in a field that keeps case, and index text with ǧ or ǥ (for example Romani, Skolt Sami, Lakota or romanized Arabic names) or a specialist letter. There the ASCII query term silently misses the folded term, in every release since 2.9.0.

Mechanism, terms and numbers767 words

ASCIIFoldingFilter converts non-ASCII characters "into their ASCII equivalents, if one exists". Its mapping table, the switch in foldToASCII with 1,242 case labels, groups the labels by output: one block for G, one for g, and so on. Six labels sit in the block of the opposite case: ǥ U+01E5 and ǧ U+01E7 fold to G, the insular s pair is swapped (small ꞅ U+A785 folds to S, capital Ꞅ U+A784 to s), capital Ɐ U+2C6F folds to a and capital Ꜿ U+A73E to c. Each of these lines carries a comment with the letter's Unicode name, which names the other case; the case partners of four of them (Ǥ, Ǧ, ɐ, ꜿ) sit in the right block, and the insular s pair is swapped. A chain that lower-cases and then folds therefore indexes "naǧib" as "naGib", and the lower-cased ASCII query "nagib" finds nothing, with no error. The entries have been in the table since it was added in 2008 and are in every release from 2.9.0 to 10.5.2 and on main. A seventh entry, ʗ U+0297 LATIN LETTER STRETCHED C (folds to C), is contested and is raised only as a question.

Terms

#
  • The fold table: foldToASCII(char[], int, char[], int, int) (public static since 3.1, tagged @lucene.internal, ASCIIFoldingFilter.java:188-190, called by the filter at :153) is one switch (c) (:200). Each block lists case labels, each with a comment // <char> [UNICODE NAME], and then writes one output, for example output[outputPos++] = 'G'; break;. There are 1,242 case labels.
  • Case partner: the capital or small form of the same letter (Ǧ U+01E6 for ǧ U+01E7).

How a search misses

#
  • Lower-case, then fold: ǧ, ǥ and ꞅ come out as capitals; Ǧ and Ꞅ are lower-cased to ǧ and ꞅ first and then also come out as capitals. Ɐ and Ꜿ are lower-cased to ɐ and ꜿ, which fold correctly, so this order hides those two.
  • Fold only (a field that keeps case, like the factory's own javadoc example, WhitespaceTokenizerFactory + ASCIIFoldingFilterFactory): all six fold to the wrong case.
  • Fold, then lower-case: every result is correct, because the output is lower-cased afterwards.

The numbers

#

On main, WhitespaceTokenizer + LowerCaseFilter + ASCIIFoldingFilter turns "naǧib NAǦIB aǥa ꞅet Ꞅet" into [naGib, naGib, aGa, Set, Set] instead of [nagib, nagib, aga, set, set]; an index of "ağa" and "naǧib" answers the query "aga" with 1 hit and "nagib" with 0. Without lower-casing, ǥ ǧ ꞅ Ꞅ Ɐ Ꜿ fold to G G S s a c instead of g g s S A C, while the controls ğ Ǧ ɐ ꜿ fold to g G a c. An exhaustive fold of all 65,536 BMP code units through the stock jar finds exactly these seven case violations among 891 mapped letters (a check of each letter's JDK case property against the case of its output; letters whose name contains SMALL CAPITAL excluded, see below); with the six-label fix only U+0297 remains, with the seven-label variant none.

Exposure and likelihood298 words
  • Who is exposed. Analysis chains that use ASCIIFoldingFilter: built by hand, with CustomAnalyzer, or through the asciiFolding SPI factory; no analyzer shipped with Lucene includes it. The chain must either lower-case before folding or keep case in the folded field. Lucene's own javadoc shows the lower-case-then-fold order: TruncateTokenFilterFactory recommends TurkishLowerCaseFilterFactory followed by ASCIIFoldingFilterFactory for diacritics-insensitive Turkish search (Turkish itself uses ğ, which folds correctly). Both orders occur: Lucene's own TestCustomAnalyzer folds first and lower-cases afterwards, the order that hides the bug in lower-cased fields, while on LUCENE-7525 (#8576) a committer wrote "So ASCIIFoldingFilter is in most analysis chains the very last filter!"
  • Which text. ǧ and ǥ have documented modern use, for example in Romani, Skolt Sami (ǥ, as in šiõǥǥ "good"), Lakota, Berber Latin, and scholarly romanization of Arabic, Persian and Pashto names (DIN 31635 uses ǧ), per the reference articles the hunt cited. The insular s pair, turned A and reversed C with dot are mainly specialist (medieval or phonetic) letters.
  • Effect. Deterministic for every such token: in the affected chain the ASCII query term (nagib) does not match the indexed term (naGib), so a search on that field misses the document; a query with the same non-ASCII letter still matches. No exception, no index damage, nothing in the logs. preserveOriginal=true keeps the unfolded token next to the wrong one, which does not help an ASCII query.
  • How likely. Rare by accident, because these letters are rare in most corpora, but systematic in collections where they occur (transliterated names in scholarship, Sami or Romani text).
  • Also affected. Code that calls the public static foldToASCII(...) directly (from 3.1; it is tagged @lucene.internal, so not a supported API contract), and the copies of the table outside Lucene (see the downstream note).

Why it is a bug, not intended

#
  • Each misplaced line's comment names the other case: [LATIN SMALL LETTER G WITH CARON] sits in the capital G block.
  • Their partners follow case: Ǥ and Ǧ fold to G, ğ to g, ɐ and ꜿ to lower case; the insular s pair is simply swapped.
  • The test asserting today's outputs was generated from the table by a script.
The full argument329 words
  • The comments were the verification aid. In LUCENE-1390 (#2464) the contributor who added the Unicode-name comments wrote that the mappings were generated by script "and then moved things around to the appropriate places by hand. I guess this is one weakness of this patch: it's large enough that manual verification is tough. It's my hope that adding the Unicode character descriptions will allow for at least improved verifiability." Six of those descriptions name the case opposite to their block.
  • Placement by case was the intent. A later patch revision in the same issue "moves all schwa characters to the 'A' or 'a' depending on their case", and an earlier one "fixes a couple of character mappings that were out of order in the mapped-to-capital-"B" section": hand-placement slips were already being fixed in review.
  • The design rule gives the other answer. The stated rule was to "convert characters to those that look like them in ASCII"; a small ǧ looks like a small g, and capital Ɐ and Ꜿ look like capitals.
  • Contract and tests. The class javadoc promises "their ASCII equivalents" and its one example keeps case ("'à' will be replaced by 'a'"); the hand-written testLatin1Accents asserts both cases ("À" -> "A", "à" -> "a"). ǧ's canonical decomposition is g + combining caron (NFD U+0067 U+030C).
  • The generated test is no evidence of intent. testAllFoldings asserts these outputs, but its comment says "The following Perl script generated the foldings[] array automatically from ASCIIFoldingFilter.java".
  • Precedent, and its limits. In LUCENE-1343 (#2420) a committer listed a self-inconsistent entry (U+1E9B) among the "bugs in ASCIIFoldingFilter that should be fixed", but that entry was never changed (ẛ still folds to f, :564). No mapping in the table has changed since 2008 (it is identical at all 21 revisions of the file), so this would be the first table change. LUCENE-7468 (6.3.0, "Bug Fixes") changed the filter's output only under preserveOriginal=true, where it stopped emitting a duplicate token: a limited precedent.
The devil's-advocate check315 words

The intended-behaviour checker built the strongest case for "intended": the javadoc has no case clause (its predecessor ISOLatin1AccentFilter said "The case will not be altered", and that sentence was not carried over); the table folds all 39 SMALL CAPITAL letters to upper case on purpose ("ᴄat" becomes Cat even after LowerCaseFilter, executed); the generated test has asserted these outputs for almost 18 years, and maintainers may treat it as a compatibility oracle; in LUCENE-1029 (#2105) participants objected to changing the older accent filter, one because it "would break indexes out there that use it", and a committer wrote that its functionality "shouldn't change in a way that wouldn't be b[a]ckward compatible"; and nobody reported these entries in almost 18 years.

Why it fails: the claim is not "case must be preserved" but six entries placed against their own names (and, for four of them, against their correctly placed partners). Small capitals are a uniform, deliberate choice under the look-alike rule; these six are isolated exceptions in blocks that otherwise follow case. The test was generated from the table. The back-compat objection was about deliberate semantics and argues for a CHANGES/MIGRATE note, not for intent, but it is a real cost: no table mapping has ever changed, so propose the fix for 11.0. The 2010 comparison with ICU folding could not see case errors because ICU folding lower-cases its output. Verdict: not intended for the six. The case survives only for ʗ U+0297. For a bug: Unicode gives it General Category Ll (a lower-case letter), which is why the case check flags it. For intent: its name, LATIN LETTER STRETCHED C, has no SMALL/CAPITAL, it has no case partner (upper-casing returns it unchanged), and C fits the look-alike rule like the small capitals. Raise it as a question only. Do not frame the issue as "ASCIIFoldingFilter preserves case": the small capitals refute that at once.

#

Trade-offs

  • Reindexing. Indexed terms change for text with these letters: documents indexed with the old table keep naGib, new queries produce nagib. Expect a back-compat reply: no mapping of this table has changed since 2008 (LUCENE-7468 in 6.3.0 changed only the duplicate token under preserveOriginal), and testAllFoldings has asserted these outputs all along. Suggest the fix for 11.0 with a CHANGES entry and a MIGRATE.md note (reindex fields folded by ASCIIFoldingFilter that may contain ǥ, ǧ, ꞅ, Ꞅ, Ɐ or Ꜿ). A 10.x backport is the committers' call.
  • No API change. No performance effect is expected (the same switch, the same 1,242 labels and the same output lengths); not benchmarked.
  • Copies of the table outside Lucene need the same change separately.

Workaround for users today (not a fix)

#

Put LowerCaseFilter after ASCIIFoldingFilter; that hides all six in lower-cased fields. A field that keeps case can use, for example, a MappingCharFilter override for these letters.

Trade-offs

Not run. Changes the analysis chain, so it also needs reindexing, and it does not help other users of the table.

Downstream note

#

The same table ships unchanged in copies outside Lucene, such as Solr's sample mapping-FoldToASCII.txt and ports of the filter in Lucene.NET and in JavaScript and Python packages, so their users get the same folds.

How it was found

#

An exhaustive check folded all 65,536 BMP characters through the real jar and compared the case of every folded letter with Unicode data, leaving out small capitals, which fold to upper case on purpose. Exactly seven letters fold to the opposite case; six contradict their own name comment, and the seventh, ʗ, is contested.

The method in full240 words

Method: bounded-exhaustive checking of the stock jar against an exact reference (semi-formal tier), in a hunt unit that checked the ASCII folding table against the Unicode Character Database.

  • A planning probe first folded every BMP code unit through the stock jar's public static ASCIIFoldingFilter.foldToASCII and flagged letters whose ASCII output has the opposite Unicode case.
  • The hunt then turned this into a proof by exhaustion over all 65,536 BMP code units on the stock jar, against JDK 25 Unicode data (NFKD, case properties, character names) and ICU4J 78.3 UTR#30 folding, with an independently parsed model of the source table that agrees with the jar on 65,536 of 65,536 code units. The case property (a mapped lower-case letter folds to lower-case ASCII and vice versa; letters whose name contains SMALL CAPITAL excluded as a uniform rule) has exactly 7 violations among 891 mapped letters, one more (U+0297) than the probe listed; with the seven-label fix, 0. This case check is a heuristic (the JDK case property of the letter against the case of a single-case output); that six of the seven sit opposite the case named in their own comments was then read from the source.
  • The finding was reduced to a public-API JUnit and checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history, prior-report and security follow-up, and an audit. Found 2026-10-28 on main a9779ef3c193.

Bug record

#

LFV-818, snapshot of 2026-10-29

Registry title
ASCIIFoldingFilter folds six letters to the ASCII letter of the opposite case (ǥ U+01E5 and ǧ U+01E7 to 'G', insular ꞅ U+A785 to 'S' and Ꞅ U+A784 to 's', Ɐ U+2C6F to 'a', Ꜿ U+A73E to 'c'; stretched ʗ U+0297 to 'C' is contested), so a LowerCaseFilter-then-ASCIIFoldingFilter chain indexes 'naǧib' as 'naGib' and the ASCII query 'nagib' finds nothing
Area
analysis-common / ASCIIFoldingFilter mapping table (foldToASCII switch)
Priority
Low, rank 254: The affected letters (mainly the Romani, Skolt Sami and Lakota letters ǧ and ǥ) are rare in most corpora, in an opt-in filter.
Impact class
silent wrong results
Impact note
Hits applications whose analysis chain uses ASCIIFoldingFilter (opt-in: no Lucene analyzer ships it; it is built by hand, through CustomAnalyzer or through the 'asciiFolding' SPI factory) either after LowerCaseFilter (misses for ǥ, ǧ and, through lower-casing, capital Ǧ, the insular s pair and ʗ) or in a folded field that keeps case (all seven letters), and whose text contains one of these letters, of which only ǧ and ǥ occur in real orthographies (Romani, Skolt Sami, Lakota, Berber Latin, romanized Arabic, Persian and Pashto); such documents are silently not found by ASCII-typed queries, from a single token, also with preserveOriginal=true, with no exception and no index damage, in every release since 2.9.0, while the fold-then-lowercase order hides all seven entries.
Summary
You index and search through a chain that lower-cases and then applies ASCIIFoldingFilter, documented to convert characters 'into their ASCII equivalents', and you type queries in plain ASCII. You expect 'naǧib' and 'NAǦIB' to be indexed as 'nagib', just as 'ağa' becomes 'aga'; instead six entries of the 1,242-entry folding table sit in the output group of the opposite case (ǥ and ǧ in 'G', ꞅ in 'S', Ꞅ in 's', Ɐ in 'a', Ꜿ in 'c', plus the contested ʗ in 'C'), so the term is 'naGib' and the query 'nagib' finds nothing. Each of the six lines carries a source comment that names the other case (for example [LATIN SMALL LETTER G WITH CARON] inside the 'G' group), and the fix is to move these case labels into the group of their own case.
