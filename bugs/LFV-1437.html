Analysis factory lookups are documented as 'from context classpath', but since 7.0 only Lucene's own class loader is searched

The javadocs of TokenizerFactory, TokenFilterFactory and CharFilterFactory say their name lookups search the "context classpath". Since 7.0 Lucene deliberately searches, by default, only its own class loader, so a factory registered only through the thread's context class loader "does not exist"; eight javadoc lines are wrong.

The finding in 30 seconds

#

Each facade's loader is built with no class loader argument, which means the loader that loaded lucene-core. Factory registrations (META-INF/services files) that only the thread's context class loader can see are never scanned, so forName throws "does not exist" and the names list omits them, although the javadoc says the lookup is "from context classpath".

Background: how analysis factories are found by name

#
  1. Each JAR lists its factories in a service file, for example META-INF/services/org.apache.lucene.analysis.TokenFilterFactory; TokenFilterFactory.forName("lowercase", args) maps the name to a registered factory. CustomAnalyzer.Builder.addTokenFilter("lowercase") uses it.
  2. Which service files are seen depends on the class loader that is asked. Application servers and plugin systems often give each web app or plugin its own child loader and set it as the thread's context class loader.
  3. Up to 6.6.6 Lucene asked the context class loader. Since 7.0.0 it asks only its own loader; reloadTokenFilters(ClassLoader) (and the tokenizer and char filter twins) adds another one.

The finding, step by step

#
  1. You register one token filter factory, onlyOnContextLoader, on a child class loader only (a URLClassLoader over a directory that holds just its META-INF/services file; the factory class is on the test classpath), make it the thread's context class loader and call TokenFilterFactory.forName("onlyOnContextLoader", new HashMap<>()).
  2. The javadoc of forName says it "looks up a tokenfilter by name from context classpath". So you expect the factory.
  3. You get IllegalArgumentException: ... with name 'onlyOnContextLoader' does not exist. You need to add the corresponding JAR file supporting this SPI to your classpath, and availableTokenFilters() does not list it. Same on main and 10.6.0, assertions on and off.
  4. Why: since 7.0.0 (LUCENE-7873, on purpose) each facade's loader scans, by default, only the class loader that loaded the facade class. Calling TokenFilterFactory.reloadTokenFilters(loader) first makes the factory visible (global and additive: factories are only ever added); the javadoc never says so.

Who is affected

#

Only applications whose analysis factories are registered only in a child class loader set as the thread's context loader (some web-app, application-server and plugin setups) and that look them up by name or list them without a reload call. Lookups fail at once with advice (add a JAR) that does not help; lists omit the factory. Since 7.0.0; priority Low.

Mechanism, terms and numbers358 words

TokenFilterFactory.forName, lookupClass and availableTokenFilters, the three TokenizerFactory twins, and CharFilterFactory.forName and lookupClass (eight lines: TokenFilterFactory.java:50, :55, :60, TokenizerFactory.java:50, :55, :60, CharFilterFactory.java:50, :55) say the lookup is "from context classpath".

Each facade builds new AnalysisSPILoader<>(X.class) (:35-36). That constructor passes null, which becomes clazz.getClassLoader() (AnalysisSPILoader.java:47-63), so ServiceLoader runs only on the loader that loaded lucene-core, plus any loader added with reloadX(ClassLoader) (:76-80). Nothing in core reads the thread's context class loader, and the build forbids it (defaults.txt:32-34). An unknown name throws "does not exist. You need to add the corresponding JAR file supporting this SPI to your classpath" (:144-159).

That behaviour is intended: LUCENE-7873 (63a40052826, 7.0.0) switched every SPI lookup to the defining class loader because of "serious problems with context class loaders in several frameworks (OSGI, Java 9 Jigsaw)", and rewrote the same statement in SPIClassIterator, but missed these eight lines. The fix is javadoc only.

The chain (main f794ff5a505c)

#
  • TokenFilterFactory.java:35-36: Holder.LOADER = new AnalysisSPILoader<>(TokenFilterFactory.class); the same in TokenizerFactory and CharFilterFactory.
  • AnalysisSPILoader.java:47-63: this(clazz, null); null becomes clazz.getClassLoader(), and reload(classloader) runs ServiceLoader.load(clazz, classloader) (:76-80).
  • AnalysisSPILoader.java:144-159: a name that is not in the map throws IllegalArgumentException "... does not exist. You need to add the corresponding JAR file supporting this SPI to your classpath. The current classpath supports the following names: [...]".
  • TokenFilterFactory.java:74-86: reloadTokenFilters(ClassLoader) adds the factories of the given loader (global and additive: "Only new factories are added, existing ones are never removed or replaced", :79); this is the documented workaround (the 7.x migration guide gave the recipe).
  • CustomAnalyzer.Builder's name-based withTokenizer, addTokenFilter and addCharFilter document their lookup by linking to these forName methods and call them (CustomAnalyzer.java:311-335, :368-392, :431-455; read, not run).

Executed besides forName: a probe of all three facades shows forName and lookupClass of TokenFilterFactory, TokenizerFactory and CharFilterFactory throw, and availableTokenFilters(), availableTokenizers() and availableCharFilters() leave out a registration seen only by the context loader, on main and 10.6.0 with assertions on and off; each reloadX(loader) makes it visible.

Exposure and likelihood170 words
  • Who: Lucene in a parent class loader, factories registered only in a child loader (their META-INF/services file is visible only there) that is the thread's context class loader, lookup by name (forName, lookupClass, CustomAnalyzer.Builder by name) or listing (available*()) without reloadX(ClassLoader). The 7.0 migration note named "certain web applications or components in application servers" as users of the old behaviour.
  • Effect: loud and immediate, usually when the analyzer is built: an IllegalArgumentException that tells the user to add a JAR, although the factory is registered on the context classpath the javadoc names, and available*() lists that silently omit the factory. No index or data effect.
  • Not hit: single-class-loader applications (the usual case) and setups where Lucene and the factories share a loader. Solr registers its own loader through the reload methods by design.
  • How long: every release from 7.0.0 (2017) to 10.6.0, and main; no report found. Not new in 10.6.
  • Priority: Low (documentation only; rare deployment shape; public workaround on the same classes).

Why it looks unintended

#
  • When written in 2012, the lines were literal: the loader was built from the thread's context class loader.
  • LUCENE-7873 (7.0.0) changed that on purpose and fixed the same claim in SPIClassIterator, but missed these eight lines.
  • No javadoc on main says which loader is used; CHANGES 7.0.0 does, but points to a MIGRATE section removed for 8.0.
The full argument154 words
  • Contract. The method javadocs are what users and CustomAnalyzer.Builder's javadoc point to; they state a lookup the code does not do.
  • History. d1ad745f530 (LUCENE-2510, 2012-07-24) added the lines together with getSPILoader(Thread.currentThread().getContextClassLoader()). 63a40052826 (LUCENE-7873, #8924, 2017-06-20) changed the default to null (the defining loader) and rewrote the SPIClassIterator javadoc from "using the context classloader" to "using the same ClassLoader as the argument", without touching the three facades, which looks like an oversight.
  • Documented elsewhere, then lost. No javadoc on main names the loader. CHANGES.txt:8277-8281 (7.0.0) does: the lookup "was changed to only inspect the current classloader that defined the interface class (lucene-core.jar)", "See MIGRATE.txt"; that section, with the reloadX recipe, was removed in 1aa049bb270 (2017-11-10) for 8.0, and main's MIGRATE.md has no 7.0 section (it names reloadTokenizers(ClassLoader) only for the missing-NAME-field error, MIGRATE.md:1428).
  • No test asserts a context-loader lookup, and the build forbids Thread#getContextClassLoader and #setContextClassLoader (defaults.txt:32-34).
The devil's-advocate check134 words

The case: the behaviour is deliberate and announced in CHANGES 7.0.0; the failure is loud; the reload methods are on the same class; "context classpath" is loose wording; no report of it in 8+ years was found. So it is a trivial nit.

Why it fails: all of that defends the code, which stays as it is, not the sentence. The javadoc states the opposite of what the code does, meant exactly the context class loader when it was written, and the authors corrected the same statement elsewhere in the same commit. A user who follows it gets an error telling them to add a JAR, although the factory is registered on the context classpath the javadoc names. It is small, which is why it is Low and why the adjudication's confidence is medium.

Downstream note

#

Downstream products that load analysis plugins in their own class loaders and look factories up by name need the reload* methods; Solr already calls them, so the stale javadoc misleads only code that relies on the context class loader.

How it was found

#

Semi-formal: each statement in the javadocs of the three factory lookups was treated as a proof obligation and checked against the code. "From context classpath" does not follow from a loader built from clazz.getClassLoader() when nothing reads the context loader. A public-API JUnit test witnessed it; independent checks reproduced it.

The method in full69 words
  • Obligation: forName, lookupClass and the names lists find factories registered on the thread's context class loader (TokenFilterFactory.java:50, :55, :60 and the twins).
  • Code: the loader is new AnalysisSPILoader<>(X.class), whose default is clazz.getClassLoader() (AnalysisSPILoader.java:47-63); no core code reads the context loader; so the obligation fails.
  • Witness: the one-test repro fails on main with assertions on and off.
  • Tier: semi-formal (proof-obligation reasoning plus an executed test).
