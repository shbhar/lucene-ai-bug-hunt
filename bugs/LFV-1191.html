SleepingLockWrapper accepts pollInterval 0, then every obtainLock throws ArithmeticException: / by zero

SleepingLockWrapper's constructor accepts a pollInterval of 0 (it rejects only negative values), but obtainLock divides the timeout by it before its first lock attempt, so every obtainLock call, including the one in new IndexWriter(...), throws ArithmeticException: / by zero. Present since 5.3.0; checking <= 0 instead of < 0 fixes it.

The finding in 30 seconds

#

SleepingLockWrapper wraps a Directory; when a lock is busy it retries every pollInterval ms until lockWaitTimeout runs out. Its constructor lets an interval of 0 through, and the retry loop divides by the interval before its first try.

  1. Wrap a directory so that locking is retried: new SleepingLockWrapper(new ByteBuffersDirectory(), 1000, 0), a 1,000 ms timeout and a poll interval of 0 ms. The constructor accepts it: it rejects only negative intervals ("pollInterval must be a non-negative number").
  2. Ask for a lock nobody holds: obtainLock("write.lock"). You expect the lock, or else an IllegalArgumentException from the constructor that names pollInterval.
  3. Instead it throws java.lang.ArithmeticException: / by zero, every time, with assertions on and off, and the wrapped directory is never asked. new IndexWriter(wrapper, config) fails the same way.
  4. Why: before its first lock attempt, obtainLock turns the timeout into a number of sleeps, lockWaitTimeout / pollInterval, here 1000 / 0 (SleepingLockWrapper.java:81). Every timeout fails: -1 (wait forever), 0 or 1000.

Who is affected

#

Only applications that build SleepingLockWrapper(dir, timeout, 0) themselves, for example to mean "retry without sleeping". Lucene never uses the class; positive intervals and the 2-argument constructor work. For those applications no lock can ever be taken: IndexWriter, CheckIndex and addIndexes fail at once. Nothing is written or damaged.

Mechanism, terms and numbers308 words

SleepingLockWrapper wraps a Directory and retries obtainLock, sleeping pollInterval milliseconds between attempts until lockWaitTimeout runs out. Its 3-argument constructor rejects only pollInterval < 0 ("pollInterval must be a non-negative number", SleepingLockWrapper.java:71-74 at 5adff78bb168), so 0 is accepted. Before its first lock attempt (:86), obtainLock computes long maxSleepCount = lockWaitTimeout / pollInterval; (:81). With 0, every obtainLock throws java.lang.ArithmeticException: / by zero, whatever the timeout and even when the lock is free, so new IndexWriter(wrapper, ...), new CheckIndex(wrapper) and addIndexes from such a directory all fail. It needs an explicit 0 on a class Lucene itself never uses, and it fails at once with no index change. Every release since 5.3.0 has it.

The bug, step by step

#
  1. Constructor (SleepingLockWrapper.java:61-75 at 5adff78bb168): lockWaitTimeout must be LOCK_OBTAIN_WAIT_FOREVER (-1) or >= 0 (:65-70); pollInterval is checked with if (pollInterval < 0) (:71-74). 0 passes and is stored.
  2. obtainLock (:79-102) counts sleeps, not elapsed time: it first computes long maxSleepCount = lockWaitTimeout / pollInterval; (:81), then tries in.obtainLock(lockName) (:86), sleeps pollInterval ms (:93) and loops while sleepCount++ < maxSleepCount or the timeout is -1 (:97).
  3. With pollInterval 0 the long division at :81 throws ArithmeticException for every timeout: -1/0, 0/0 and 1000/0 all throw. Directory.obtainLock documents only LockObtainFailedException and IOException (Directory.java:159-167); this exception is unchecked and names no argument.
  4. Callers that take a lock through the wrapper fail the same way (read at 5adff78bb168): new IndexWriter(dir, conf) (IndexWriter.java:954), IndexWriter.addIndexes(Directory...) on such a source directory (acquireWriteLocks, :3063), new CheckIndex(dir) (CheckIndex.java:472) and the replicator's ReplicaNode (ReplicaNode.java:103). Opening a reader takes no lock and is unaffected. An independent check executed the IndexWriter path: the exception surfaces from IndexWriter.<init>(IndexWriter.java:954).
Exposure and likelihood201 words
  • Opt-in only. Lucene's own code never uses the class; its only in-tree user is TestSleepingLockWrapper. The 2-argument constructor uses DEFAULT_POLL_INTERVAL (1000 ms) and works.
  • Reach. The class is public, final and not deprecated, and carries no @lucene.internal tag of its own; its superclass FilterDirectory and the Lock it returns are marked @lucene.internal (FilterDirectory.java:31, Lock.java:34), which a maintainer may weigh. LUCENE-6525 named it as the replacement for IndexWriterConfig's write-lock timeout (5.3.0 IndexWriterConfig.java:91-92: "@deprecated Use {@link SleepingLockWrapper} if you want sleeping."). The devil's-advocate verifier's GitHub code search for new SleepingLockWrapper recorded two downstream callers, neither passing 0: Hibernate Search (new SleepingLockWrapper( directory, 2000, 20 )) and an older Elasticsearch shared-filesystem path (the 2-argument constructor, timeout 5000); not re-checked for this doc. No public report of a zero interval was found since 2015.
  • Before 10.2.0 DEFAULT_POLL_INTERVAL was a mutable public static (10.1.0 SleepingLockWrapper.java:36), so setting it to 0 reached the same division through the 2-argument constructor (read, not executed). #14221 made it final.
  • Effect. 100% of lock attempts on such a wrapper fail, deterministically, with an unchecked exception that callers catching IOException or LockObtainFailedException do not expect. No hang, no lock taken, no index change.

Why it looks unintended

#
  • The constructor's own check and message say "pollInterval must be a non-negative number"; 0 is inside that range.
  • No javadoc, test or discussion says 0 is invalid; the class's own test only draws 2-10 ms.
  • Even if 0 is misuse, it should be rejected up front, not fail on every later lock with / by zero.
The full argument101 words
  • Contract. @param pollInterval poll once per this interval in milliseconds until {@code lockWaitTimeout} is exceeded. (SleepingLockWrapper.java:58-59); the constructor rejects only negative values (:71-74).
  • Tests. TestSleepingLockWrapper draws pollInterval from TestUtil.nextLong(random(), 2, 10) (TestSleepingLockWrapper.java:30), so 0 was never exercised. No CHANGES or MIGRATE entry mentions a zero interval.
  • History. The < 0 check and the division were written together in fe6c3dc9397 (LUCENE-6508, 2015). Both expressions are unchanged since; the only later edit beside them is the 2020 reformat 2d6ad2fee6d (LUCENE-9570), which rewrapped the message line; none of the 58 comments on #7567 discusses a zero poll interval.
The devil's-advocate check122 words

The strongest case for "intended": a zero interval is a busy retry loop; the class javadoc says "This is not a good idea." (:26); and the pollInterval < 0 check looks copied from the lockWaitTimeout check beside it, where 0 does mean something (no waiting). So the author probably meant "positive", and 0 is misuse.

Why it fails: that argues for rejecting 0 in the constructor with an IllegalArgumentException, which is the suggested fix. It does not justify accepting 0 and then failing on every lock attempt with an exception that names no argument. "Not a good idea" discourages the class, but it stays public and was the named replacement API. Verdict: a validation off-by-one, a real Low bug.

Suggested fix

#

Recommended A. Reject 0 in the constructor (validated)

In the constructor, reject pollInterval <= 0 instead of < 0, with "pollInterval must be a positive number". The repro passes with assertions on and off, and TestSleepingLockWrapper and the org.apache.lucene.store tests pass. Alternative: define 0 as "retry without sleeping", which needs a time-based loop.

-    if (pollInterval < 0) {
+    if (pollInterval <= 0) {
       throw new IllegalArgumentException(
-          "pollInterval must be a non-negative number (got " + pollInterval + ")");
+          "pollInterval must be a positive number (got " + pollInterval + ")");
     }
All options and trade-offs2 options · 276 words

Option A was applied in scratch worktrees at 5adff78bb168 and checked with gradle; option B was not built.

A. Reject 0 in the constructor (validated) (recommended)

#

Change the check at SleepingLockWrapper.java:71-74 from < 0 to <= 0 and the message to "must be a positive number". Optionally say "must be positive" in the @param pollInterval javadoc too.

-    if (pollInterval < 0) {
+    if (pollInterval <= 0) {
       throw new IllegalArgumentException(
-          "pollInterval must be a non-negative number (got " + pollInterval + ")");
+          "pollInterval must be a positive number (got " + pollInterval + ")");
     }

Trade-offs

Code that passes 0 today cannot take any lock already, so no working lock path breaks; the error moves to construction and names the argument. One narrow behaviour change: a wrapper built with 0 and used only for reading (no lock taken) works today and would fail at construction.

What the checks validated

  • The repro passes with assertions on and off (gradle, seed 5EED1191).
  • With the fix, TestSleepingLockWrapper passes (6 tests, 1 skipped by a seed-dependent assumption) and org.apache.lucene.store.* passes (29 classes, 778 tests, 0 failures; the new test included), with assertions on and, in a separate run, off.
  • :lucene:core:checkGoogleJavaFormat passes with the test file added.

B. Keep 0 and define it as "retry without sleeping"

#

Special-case 0 in obtainLock: skip the division and the Thread.sleep.

Trade-offs

Needs a decision on what the timeout means with 0, because the loop counts sleeps, not elapsed time (:81, :97): it would need a time-based deadline, and a 0 interval spins a CPU while another process holds the lock. Not built or tested.

Downstream note

#

A product that lets users set this poll interval and passes 0 through would fail to open every index writer on that directory; keeping the value at 1 ms or more avoids it.

How it was found

#

A proof-obligation audit of SleepingLockWrapper's contract: the constructor's check admits every non-negative pollInterval, so obtainLock must work for each of them, and before its first lock attempt it divides by the interval, which fails for 0. A one-method JUnit test on the public API then witnessed it.

The method in full61 words

The obligation came from the class's own validation and message ("non-negative") and the @param pollInterval javadoc, checked against the only use of the field, the division and the sleep in obtainLock. The witness test (an earlier variant of the repro above, with the same trigger) fails on main with assertions on and off and on the 10.6.0 and 9.12.3 jars.
