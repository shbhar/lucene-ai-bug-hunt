FreeTextSuggester accepts a token that contains its separator byte when the token has no neighbours, and some later lookups throw NullPointerException

FreeTextSuggester promises an IllegalArgumentException for a token that contains its separator byte, but build() only counts separators inside n-grams, so the lone token foo\u001ebar passes as if it were the 2-gram "foo bar". With a word-splitting query analyzer (for example UnicodeWhitespaceAnalyzer), lookup("foo ") then throws NullPointerException (AssertionError with assertions on).

The finding in 30 seconds

#

At build time FreeTextSuggester never looks at the analyzer's tokens. It counts the separators in each stored n-gram and rejects only an n-gram that seems to have more than grams words. A token that contains one separator looks exactly like a 2-gram, so with the default bigram model a lone foo␞bar passes; with a neighbour it is caught.

Background: how FreeTextSuggester stores n-grams

#
  1. FreeTextSuggester builds an n-gram model from text. With the default grams = 2 it stores every word (unigram) and every pair of neighbouring words (bigram) with its count in one FST.
  2. A bigram is stored as its two words joined by a separator byte: foo and bar become foo␞bar. The separator is U+001E by default (any 7-bit byte if configured); no analyzed token may contain it.
  3. lookup("foo ") (a trailing space means "predict the next word") finds the bigrams starting with foo␞ and scores each by count(foo bar) / count(foo). So every bigram's first word must also be stored as a unigram.

The finding, step by step

#
  1. Build a FreeTextSuggester with the defaults (bigrams, separator U+001E, written ␞ below) and KeywordAnalyzer or UnicodeWhitespaceAnalyzer, which keep ␞ inside a token, over the single entry foo\u001ebar.
  2. You expect IllegalArgumentException: the javadoc says "No input tokens should have this byte, otherwise IllegalArgumentException is thrown", and the upstream test asserts it for foo\u001ebar baz.
  3. You get a successful build. The check counts separators in each stored n-gram: foo␞bar has one, so it counts as 2 words, which a bigram model allows. With the neighbour baz, the n-gram foo␞bar␞baz counts 3 and is rejected: the only reason the upstream test passes.
  4. The model now holds the "bigram" foo-bar but no word foo. With UnicodeWhitespaceAnalyzer (it splits the query into words), lookup("foo ") looks up the count of foo and throws NullPointerException (AssertionError with assertions on); lookup("f") suggests foo␞bar (score 1.00 for this single entry, as in the diagram; 0.50 after a build over foo␞bar and hello world).

Who is affected

#

Users of the opt-in, @lucene.experimental FreeTextSuggester whose analyzer keeps the separator inside a token: KeywordAnalyzer or UnicodeWhitespaceAnalyzer with the default U+001E, or a custom separator the tokenizer keeps, such as a space with a comma tokenizer. StandardAnalyzer, WhitespaceAnalyzer and SimpleAnalyzer split on U+001E and are safe. Every release since 4.6.0.

Mechanism, terms and numbers838 words

FreeTextSuggester builds an n-gram model: ShingleFilter joins neighbouring tokens with a separator byte (U+001E by default, any 7-bit byte if configured) and every unigram and n-gram goes into one FST. Its 4-arg constructor javadoc says "No input tokens should have this byte, otherwise IllegalArgumentException is thrown" (FreeTextSuggester.java:179-180 on main 645d4fe14a20). build() never inspects the tokens, though: it reads the shingled terms back from a temporary index and throws only if a term's separator count implies more than grams words (:305-306). A token that itself contains k separators therefore looks like a (k+1)-gram; it passes whenever every shingle it ends up in still counts at most grams (with bigrams and no position gaps: a token with one separator passes whenever it is the only token of its entry). With the default bigram model the one-token entry foo\u001ebar is accepted, while the upstream test input foo\u001ebar baz is rejected only because its shingle foo␞bar␞baz counts 3. The token is stored as the bigram (foo, bar) without a unigram foo; lookup("foo ") with a word-splitting analyzer then throws AssertionError at :576 (-ea) or NullPointerException in decodeWeight at :724 (-da, as in production), and the token can come back from the no-context (1-gram) search with a wrong score. Only the opt-in, @lucene.experimental FreeTextSuggester with an analyzer that keeps the separator inside a token is affected (KeywordAnalyzer, UnicodeWhitespaceAnalyzer, or a custom separator the tokenizer keeps); StandardAnalyzer, WhitespaceAnalyzer and SimpleAnalyzer split on U+001E. The check reads the same in every release from 4.6.0 (2013) to 10.6.0 and on main (12 releases and main executed, the rest read from source or inferred).

The code (main 645d4fe14a20, lucene/suggest/.../analyzing/FreeTextSuggester.java)

#
  • Contract. DEFAULT_SEPARATOR = 0x1e: "The input tokens produced by the analyzer must not contain this character" (:147-151). The 4-arg constructor: the separator "must be an ascii (7-bit-clean) byte. No input tokens should have this byte, otherwise IllegalArgumentException is thrown" (:176-181); the other constructors delegate to it (:157-174).
  • Shingling. Unless grams == 1, both analyzers get a ShingleFilter(stream, 2, grams) with the separator as token separator (:185-186, :214-235). It emits each token and each run of 2 to grams neighbouring tokens joined by the separator.
  • Build. Each entry is indexed in a temporary index (:276-284); the terms are read back and countGrams(term), 1 + the number of separator bytes (:414-423), is compared with grams: only ngramCount > grams throws "tokens must not contain separator byte" (:305-313). Only terms with count 1 add to the unigram total (:315-317); every term goes into the FST (:319-320). A term read back from an index carries no position length, so the build cannot tell the token foo␞bar from the shingle of foo and bar.
  • When it misses. The separator check in build() throws exactly when some emitted term has countGrams(term) > grams (build() also throws for payloads, contexts and an empty term set, :247-252, :287-290). For an entry without position gaps and with one separator-carrying token, a token with k separators passes when k + 1 <= grams and it has at most grams - 1 - k neighbours: with bigrams, an entry that is that single token; with grams = 3, a token with one separator next to one other token. Several such tokens in one shingle add up, and across a position gap ShingleFilter inserts its filler token _ (ShingleFilter.java:46), which adds one more join.
  • Lookup checks exactly. For each query token it compares countGrams with the ShingleFilter position length (// Safety: make sure the recalculated count "agrees", :459-468).
  • Lookup fails. For "foo " the last token becomes the context foo␞ (:494-509). That prefix exists in the FST (from foo␞bar), so lookup fetches the count of foo: Util.get returns null and assert output != null fails (:575-576); without assertions decodeWeight(null) unboxes null (:724).

Exposure and likelihood346 words
  • Reach. The default U+001E reaches it with KeywordAnalyzer, UnicodeWhitespaceAnalyzer (U+001E is not Unicode White_Space) or a keyword- or pattern-style tokenizer. A custom separator (any 7-bit byte; in Solr a FreeTextLookupFactory setting next to any analyzer field type) reaches it whenever the tokenizer keeps it inside words. StandardAnalyzer, WhitespaceAnalyzer and SimpleAnalyzer split the token and are unaffected with the default separator: WhitespaceTokenizer because Character.isWhitespace(0x1E) is true, SimpleAnalyzer's LetterTokenizer because U+001E is not a letter, StandardTokenizer by its UAX #29 word-break rules.
  • What goes wrong. The documented IllegalArgumentException is not thrown, so a model the API means to reject is built. With a query analyzer that splits the key into words, lookups whose last complete word is the token's part before the separator (foo for foo␞bar: "foo ", "foo b", "x foo "), when that word never occurs on its own in the build text, then throw on every such request until the model is rebuilt (also after store()/load()). Lookups on the part after it ("bar ", "x bar ") return nothing, and with KeywordAnalyzer on both sides these lookups do not throw; the probes' unrelated lookups kept working. The token can also come back from the no-context (1-gram) search with an inflated score.
  • What it takes. With bigrams, an entry that is that single token (for example one-word query-log lines); with grams >= 3, few enough neighbours. The lookup failure also needs the token's part before the separator to be absent as a standalone word, and a query analyzer that splits the key into words (with KeywordAnalyzer on both sides, foo␞bar yields only the stray completion, because the query foo stays one token).
  • Cost. Deterministic, no scale. The application's index is never touched: build writes only to its own temporary index, which it always deletes (after rolling it back when the build succeeds). No hang (a failing lookup takes a few microseconds).
  • Workaround. Strip or replace the separator byte in the build text, or pick a separator the analyzer always splits on.

Why it looks unintended

#
  • The javadoc states the consequence: "No input tokens should have this byte, otherwise IllegalArgumentException is thrown" (FreeTextSuggester.java:179-180).
  • Upstream testIllegalByteDuringBuild asserts it for foo\u001ebar baz; without baz the same token passes. A rejection that depends on neighbours and on grams is an accident.
  • Lookup checks every token exactly (:459-468) and asserts that each context word exists (:576).
The full argument196 words
  • Contract. DEFAULT_SEPARATOR: "The input tokens produced by the analyzer must not contain this character" (:147-150). The 4-arg constructor promises the IAE (:179-180), and the build's error message names exactly this condition: "tokens must not contain separator byte" (:308).
  • Test. testIllegalByteDuringBuild (TestFreeTextSuggester.java:121-134), with the comment "no input token is allowed to contain it", asserts the IAE at build time for foo\u001ebar baz. It passes only because of the neighbour baz.
  • Code. Where the position length is available (lookup), the check is exact (:459-468), and lookup asserts the model invariant that every context exists (:576). Sibling suggest code checks reserved characters one by one and throws an IAE: SuggestField and ContextSuggestField document it in their javadoc (SuggestField.java:75-76, ContextSuggestField.java:62-63); AnalyzingSuggester throws it, with a message but no javadoc, for a lookup key and, with payloads, for a surface form at build.
  • History. The promise, the check, countGrams, the lookup assert and the test came in one commit (LUCENE-5214, 2013). Its issue (#6278, 12 comments) never calls the build check partial or best-effort, and no comment, CHANGES or MIGRATE entry does.
The devil's-advocate check182 words

The strongest case for "works as designed" (the cross-model lenses and the intended-behaviour checker): separator-free tokens are a caller precondition ("should", "must not"), so behaviour after violating it is unsupported; the class is experimental; checking each unique indexed term may have been chosen as a cheap safeguard rather than complete validation; and SOLR-11139 even asks for a more lenient build. Also conceded: the javadoc does not say when the IAE is thrown (at build or at lookup).

Why it fails: the same javadoc sentence promises the IAE for exactly this violation and the upstream test asserts it at build; here it is thrown neither at build nor at lookup; nothing records the check as best-effort; a per-token check is one byte scan per token, the same work lookup already does for every token; and under any reading the outcome is wrong, with a word-splitting query analyzer, a later NullPointerException on a lookup key that itself contains no separator, instead of the documented IAE. SOLR-11139 is about the fix direction (reject or skip), not evidence that silent acceptance is wanted. Verdict: a defect.

Suggested fix

#

Recommended Reject a separator-containing token before shingling (matches the javadoc)

Check the tokens, not the n-grams: in addShingles, put a small token filter before ShingleFilter that throws IllegalArgumentException for any token containing the separator byte (+31/-1 lines). The minimal test and the whole suggest suite pass. Trade-off: such inputs now fail the whole build, as documented; that is stricter than today and the opposite of what SOLR-11139 asks.

TokenStream checked = new SeparatorCheckFilter(components.getTokenStream(), separator);
ShingleFilter shingles = new ShingleFilter(checked, 2, grams); // was: (components.getTokenStream(), 2, grams)

private static final class SeparatorCheckFilter extends TokenFilter {
  ...
  public boolean incrementToken() throws IOException {
    if (input.incrementToken() == false) return false;
    BytesRef term = termAtt.getBytesRef();
    for (int i = 0; i < term.length; i++)
      if (term.bytes[term.offset + i] == separator)
        throw new IllegalArgumentException("tokens must not contain separator byte; got token=" + term);
    return true;
  }
}
All options and trade-offs3 options · 646 words

Three options. The per-token check was validated with gradle in a fresh scratch worktree at 645d4fe14a20 (assertions on, whole suggest suite); the other two were not executed. Whatever the choice, the token has to be treated the same with or without neighbours.

Reject a separator-containing token before shingling (matches the javadoc) (validated by the checks) (recommended)

#

In FreeTextSuggester.addShingles, wrap the wrapped analyzer's token stream in a private SeparatorCheckFilter and feed that to ShingleFilter. The filter scans each token's bytes and throws IllegalArgumentException("tokens must not contain separator byte; got token=..."). It applies to the index and the query analyzer; with grams == 1 there is no shingling and the existing build check is already exact.

TokenStream checked = new SeparatorCheckFilter(components.getTokenStream(), separator);
ShingleFilter shingles = new ShingleFilter(checked, 2, grams); // was: (components.getTokenStream(), 2, grams)

private static final class SeparatorCheckFilter extends TokenFilter {
  ...
  public boolean incrementToken() throws IOException {
    if (input.incrementToken() == false) return false;
    BytesRef term = termAtt.getBytesRef();
    for (int i = 0; i < term.length; i++)
      if (term.bytes[term.offset + i] == separator)
        throw new IllegalArgumentException("tokens must not contain separator byte; got token=" + term);
    return true;
  }
}

Trade-offs

  • Builds that succeed today with such a token now fail as a whole, as the javadoc says. That is stricter, and the opposite of SOLR-11139's request.
  • Cost: one byte scan per analyzed token at build and lookup (lookup already counts separators per token); not benchmarked.
  • A lookup key whose token contains the separator still gets an IllegalArgumentException (now from the filter), so upstream testIllegalByteDuringQuery keeps passing.
  • The existing n-gram check stays. It still fires in one case the new filter cannot see: across a position gap ShingleFilter inserts its filler token _, so with separator _ a legal entry such as the foo (stop word the) is rejected, on main today and with the fix alike.
  • Constructor order is safe: addShingles() runs before this.separator is assigned, but the wrapper builds its token stream only when the analyzer is first used, after construction, and the new line reads the suggester's final field separator, as the existing setTokenSeparator line does.

Skip or drop separator-containing tokens (the SOLR-11139 direction)

#

Drop such tokens (or the entries that contain them) before shingling instead of failing the build, and change the javadoc to say so. Not executed.

Trade-offs

Lenient, and it resolves SOLR-11139 too, but it contradicts the current javadoc and test, so it is an API behaviour change; silently dropping input can hide a misconfigured separator. The check must still be per token, or the hole stays.

Document the check as best-effort (doc-only)

#

Say in the javadoc that only tokens whose separators push an n-gram past grams are rejected. Not executed (documentation only).

Trade-offs

No behaviour change, but the lookup NullPointerException and the stray completions stay; not recommended.

Downstream note

#

In Solr the separator is a free FreeTextLookupFactory setting next to any analyzer field type, so a configuration whose analyzer keeps the separator inside words reaches this; the separator and the analyzer are operator configuration, not user input.

How it was found

#

A bounded-exhaustive check of the documented separator rule on the stock jar: 8,712 builds (two separators, three analyzer types, grams 1 to 3, every tiny dictionary) and 528,216 lookups. 2,536 builds accepted a token that contains the separator, no legal input was rejected, and every lookup failure followed such a build.

The method in full179 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier), in a hunt unit on in-band separators and reserved symbols, run on the stock main jars at ea57360912ed (FreeTextSuggester.java is unchanged since).

  • Property P1: build() throws IllegalArgumentException if and only if an analyzer token contains the separator byte. Property P2: after a successful build, lookup() throws nothing but IllegalArgumentException.
  • Inputs: separators U+001E and _; keyword, space-splitting and standard analyzers; grams 1 to 3; every 1-entry dictionary of strings of length <= 3 and every 2-entry dictionary of strings of length <= 2 over {a, b, space, separator}; every lookup key of length <= 3 over {a, b, space}, with 1 and 5 results.
  • Result: 2,536 accepted-illegal builds, 0 legal inputs rejected; lookup failures only after accepted-illegal builds (3,564 AssertionError with -ea, 2,820 NullPointerException with -da), none after legal builds.
  • The hypothesis came from reading the build check while listing the reserved in-band constants; the harness then witnessed and bounded it, and the finding was reduced to a public-API JUnit test, later to the single test shown here.

LFV-600, snapshot of 2026-11-07

Registry title
FreeTextSuggester.build accepts a token that contains the separator byte whenever the shingled term stays within the gram limit, although its javadoc promises an IllegalArgumentException; later lookups whose last complete word occurs only inside that token throw AssertionError (-ea) or NullPointerException (-da)
Area
suggest / FreeTextSuggester (n-gram model joined with an in-band separator byte; build-side separator check)
Priority
Low, rank 640: The experimental FreeTextSuggester accepts a token containing its separator instead of throwing the documented exception, and later lookups then fail loudly.
Impact class
wrong error
Impact note
Only applications that use the opt-in, @lucene.experimental FreeTextSuggester with an analyzer that keeps the separator byte inside a token are hit (the default U+001E with UnicodeWhitespaceAnalyzer, KeywordAnalyzer or a keyword- or pattern-style tokenizer, or a custom separator, any 7-bit byte and a Solr configuration parameter, that the tokenizer keeps inside words), and then only for a token whose separator count plus neighbours stays within grams (with the default bigram model: an entry that is that single token): build() succeeds instead of throwing the documented IllegalArgumentException, later lookups whose last complete word occurs nowhere else as a standalone token throw AssertionError (-ea) or NullPointerException (-da, as in production), and the token can surface among single-word completions with an inflated score; StandardAnalyzer, WhitespaceAnalyzer and SimpleAnalyzer split on U+001E, so they are unaffected with the default separator; no scale is needed, and the index and other lookups are unaffected.
Summary
You build a FreeTextSuggester with the default bigram model and separator U+001E over the single entry 'foo\u001ebar' (the upstream test input 'foo\u001ebar baz' without its neighbour 'baz'), using an analyzer that keeps it as one token such as UnicodeWhitespaceAnalyzer, and expect build() to throw IllegalArgumentException, as the constructor javadoc promises and as it does for 'foo\u001ebar baz'. Instead build() succeeds, because it only rejects an indexed shingle whose separator count implies more than grams words, so the token is stored as if it were the bigram (foo, bar) with no unigram 'foo'. A later lookup('foo ') then fails inside the suggester with AssertionError at FreeTextSuggester.java:576 (-ea) or NullPointerException in decodeWeight (-da), and lookup('f') returns the token itself with a wrong score.
