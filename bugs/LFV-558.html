DirectoryTaxonomyWriter's constructor leaves the taxonomy write-locked when a file read fails after it opened its IndexWriter

If new DirectoryTaxonomyWriter(dir) hits a file read error (not a flush failure such as a full disk) after opening its internal IndexWriter, it throws without closing that writer. You get no object to close, so the taxonomy stays write-locked: every later new DirectoryTaxonomyWriter(dir) in that JVM fails with LockObtainFailedException, in every release since 3.4.0.

The finding in 30 seconds

#

The constructor takes the write lock first, then does more I/O, and has no cleanup if that I/O fails.

Background: the taxonomy writer and its lock

#
  1. Taxonomy facets keep their category labels in a separate Lucene index, the taxonomy. DirectoryTaxonomyWriter writes it through an internal IndexWriter that it creates in its constructor and closes in its own close().
  2. An IndexWriter holds the directory's write.lock until it is closed or rolled back. With FSDirectory's default NativeFSLockFactory, the JVM also records held locks in a static set, so a second writer on the same directory in the same JVM fails at once with LockObtainFailedException.
  3. In Java, when a constructor throws, the caller receives no object. Only the constructor itself can release what it already acquired.

The finding, step by step

#
  1. Open an existing taxonomy with new DirectoryTaxonomyWriter(dir). The constructor first opens an internal IndexWriter, which takes the directory's write.lock, then reads the latest commit to get the taxonomy's epoch.
  2. That read fails once: one IOException while opening segments_N (injected in the repro; in practice, say, "Too many open files"). The constructor throws it, as it should.
  3. You retry once the error is gone and expect it to work: a constructor that throws gives you nothing to close, so it must release what it took, as IndexWriter's own constructor does.
  4. Instead the retry, and all 200 retries in a probe, fail with LockObtainFailedException ("Lock held by this virtual machine" on FSDirectory). That JVM keeps the lock recorded as held until it exits; other processes are locked out only until its garbage collector closes the unreachable writer's lock channel.
  5. Nothing is lost: readers still see every committed category with its ordinal, and after a JVM restart (default lock factory) the writer opens. A new taxonomy fails the same way when opening the reader for its root category fails.

Who is affected

#

Applications using taxonomy facets with the default DirectoryTaxonomyWriter, every release since 3.4.0, when a read or open error (not a full disk) hits the constructor after its writer opened and they retry in the same process. Writes to that taxonomy from that JVM stay blocked until it exits; no data was lost in any tested scenario.

Mechanism, terms and numbers590 words

DirectoryTaxonomyWriter's constructor opens its internal IndexWriter first (DirectoryTaxonomyWriter.java:145), which takes the taxonomy directory's write.lock, and only then reads the latest commit of an existing taxonomy (:158) or, for a new one, adds the root category through a near-real-time reader (:185). Nothing after :145 is inside a try, so when one of those reads throws an IOException the constructor throws with the writer still open. The caller gets no object, so neither close() nor rollback(), the only releases, can ever run, and NativeFSLockFactory keeps the lock path in a static JVM-wide set until the lock is closed. Every later new DirectoryTaxonomyWriter(dir) in that JVM then fails with LockObtainFailedException ("Lock held by this virtual machine"), other processes are locked out only until that JVM's garbage collector closes the leaked lock channel, and with SimpleFSLockFactory the stale write.lock survives even a normal exit. No data was lost or corrupted in any tested scenario, and readers keep working. IndexWriter's own constructor releases its lock on any failure; this one never did. A history probe reproduced it on 20 releases from 3.4.0 to 10.5.2 and on main; 10.6.0 and upstream main have the same file. Low priority: it needs an I/O error inside a short window and an in-process retry.

  1. openIndexWriter (:215-218) returns new IndexWriter(directory, config), which obtains write.lock (IndexWriter.java:954). If IndexWriter's own constructor fails, it releases the lock itself (IndexWriter.java:1202-1208, "init: hit exception on init; releasing write lock").
  2. Path A, existing taxonomy: SegmentInfos.readLatestCommit(dir) (:158) reads segments_N again, under the lock, for the index.epoch entry. An IOException there propagates.
  3. Path B, new taxonomy: addCategory(new FacetLabel()) (:185) adds the root document (:468), then getTaxoArrays() (:475, :665-683) calls initReaderManager(), which opens a near-real-time reader (new ReaderManager(indexWriter, false, false), :252). An IOException while that reader opens a segment file propagates; a reader manager already built leaks too.
  4. The exception leaves the constructor. The only releases, close() (:288-294) and rollback() (:861-865), are instance methods of an object the caller never got.
  5. NativeFSLockFactory adds the lock path to its static LOCK_HELD set when it obtains the lock (NativeFSLockFactory.java:68, :108) and removes it only when the lock is closed (:145-150); a later attempt throws "Lock held by this virtual machine" (:119). Garbage collection does not help in that JVM (an independent reproducer's probe: still held after five System.gc() rounds); it only closes the leaked file channel, which lets other processes in (see Who is affected). There is no unlock API (removed in 5.0, LUCENE-6060).

Kept out of the claim (by reading only, not executed): the indexExists edge (:154); a NumberFormatException at :165, which needs a malformed index.epoch entry (crafted files or misuse); the -ea-only merge-policy assert at :148. Other steps after :145 could throw too (getDocStats() at :174 calls ensureOpen(); any Error); only the two paths above were executed, and the fix's catch (Throwable) covers them all.

Exposure and likelihood353 words
  • Who. Applications that use taxonomy facets (the opt-in facet module) with DirectoryTaxonomyWriter: its default constructor, IndexWriterConfig, codec and FSDirectory suffice. In-tree, the facet demo examples and the benchmark's taxonomy tasks construct it.
  • When. A non-aborting I/O error in the short window after the constructor opened its writer (the commit read of an existing taxonomy, or the reader open for the root category of a new one), and a retry in the same process. Likelihood is rated rare: the searches found no public report of it since 2011.
  • What goes wrong (executed probe on main with assertions on and off, 10.5.2 and 9.12.3): every later writer open on that taxonomy in the failed JVM fails fast with LockObtainFailedException until that JVM exits; 200 retries all failed. Another process is locked out only until that JVM's garbage collector closes the leaked lock channel: NativeFSLockFactory opens the lock with FileChannel.open (NativeFSLockFactory.java:132), and OpenJDK 25 registers a Cleaner that closes an unreachable channel's descriptor. A cross-process probe showed it: another JVM was refused ("Lock held by another program"), then after one System.gc() in the failed JVM it opened a writer while the failed JVM was still alive and that JVM's own retry still failed. When that collection happens is up to the JVM. With the non-default SimpleFSLockFactory, write.lock survives even a normal exit and must be deleted by hand. The message says the lock is held, not why, so it looks like a second writer the application does not have.
  • Not a trigger: a disk-full error while the root category is flushed. IndexWriter treats that as tragic and closes itself, so nothing leaks (executed).
  • What it does not do (executed, in the tested fault scenarios): nothing was lost or corrupted. Taxonomy readers return the exact committed label-to-ordinal map, the committed files stay byte-identical, other taxonomies and the main index are unaffected, and after a restart (default lock factory) every ordinal is preserved. The leak is bounded: only the first failure on a taxonomy leaks, one unreachable IndexWriter and its lock descriptor, until garbage collection reclaims them; retries fail before they acquire anything.

Why it looks unintended

#
  • The javadoc documents LockObtainFailedException only "if the taxonomy is locked by another writer"; here the holder is a writer the caller never received.
  • IndexWriter's own constructor releases its lock on any failure; upstream fixed that same symptom there in LUCENE-2476.
  • On LUCENE-3596 (2011), Doron Cohen noted that a check made after this writer opens must close it before throwing.
The full argument209 words
  • The contract. Constructor javadoc: "@throws LockObtainFailedException if the taxonomy is locked by another writer" (DirectoryTaxonomyWriter.java:137). The openIndexWriter javadoc makes the taxonomy writer the owner of the IndexWriter: "the instance this method returns will be closed upon calling to close()" (:206); a failed constructor leaves no object to call close() on.
  • The codebase convention. IndexWriter's constructor catches any Throwable and releases its lock (IndexWriter.java:1202-1208), added after the same symptom in IndexWriter (LUCENE-2476, #3550). In the same module, LUCENE-8244 added a failure-path close to SearcherTaxonomyManager.
  • The principle, stated for this class (as Doron Cohen pointed out on LUCENE-3596, #4670, 2011): a merge-policy check done "after the index was already opened ... must be closed prior to throwing that exception". That check became the :148 assert; the later I/O steps never got the cleanup.
  • History. LUCENE-4532 (#5598, 2012) moved the commit read after openIndexWriter so that it runs under the lock; that explains the order, not why the lock should outlive a failed read, and the issue does not discuss a failing read. No commit ever added or removed cleanup in this constructor (126 release tags checked).
  • Tests. No upstream taxonomy test injects I/O failures at all, so this path was never exercised.
The devil's-advocate check193 words

The strongest "works as intended" case (built by a cross-model reviewer, OpenAI GPT-5.6, and by a devil's-advocate verifier): the class is @lucene.experimental (:76); @throws IOException if another error occurred promises no exception safety; the openIndexWriter javadoc promises closing only through close(); LUCENE-4532 put the read under the lock on purpose; every repro injects its error; and after an I/O error one should restart.

Why it fails: @lucene.experimental is about API stability, not about leaking an unreachable writer. The caller of a failed constructor has no object to close and no unlock API, so only the constructor can release the lock; IndexWriter's constructor shows the expected contract, and LUCENE-3596 states it for this class. An IOException from Directory.openInput is an ordinary declared failure, reached in one check through a plain FSDirectory throwing "Too many open files". Restarting is a workaround, and with SimpleFSLockFactory it does not even work. Both the reviewer and the verifier rated the intended-behaviour argument weak; a later read-only fact check by the same model family rated it moderate, because a subclass may supply its own writer through openIndexWriter and every trigger was injected (see Suggested fix).

Suggested fix

#

Recommended A. try/catch (Throwable) after openIndexWriter: close the reader manager if opened, roll back the writer, rethrow

Wrap the rest of the constructor in try/catch (Throwable t): close the reader manager if it was opened, roll back (not close) the IndexWriter, rethrow t. The repro passes with assertions on and off, the facet module's 307 tests run with 0 failures (7 skipped), and an independent test of both trigger paths passes.

    indexWriter = openIndexWriter(dir, config);
    try {
      // ... the existing constructor body, unchanged ...
    } catch (Throwable t) {
      IOUtils.closeWhileSuppressingExceptions(
          t,
          () -> {
            if (initializedReaderManager) {
              readerManager.close();
            }
          },
          indexWriter::rollback);
      throw t;
    }
All options and trade-offs2 options · 539 words

Option A was run through gradle in a scratch worktree of 645d4fe14a20; B is the shortcut a reviewer may suggest, and why it is worse. Moving the commit read back before openIndexWriter is not a fix: LUCENE-4532 put it under the lock on purpose, and the new-taxonomy path needs the open writer anyway.

A. try/catch (Throwable) after openIndexWriter: close the reader manager if opened, roll back the writer, rethrow (validated by the checks) (recommended)

#

In the constructor (DirectoryTaxonomyWriter.java:145-195): the existing body moves, unchanged and re-indented, into the try; ignoring whitespace the change is +16/-1, the IOUtils import included.

    indexWriter = openIndexWriter(dir, config);
    try {
      // ... the existing constructor body, unchanged ...
    } catch (Throwable t) {
      IOUtils.closeWhileSuppressingExceptions(
          t,
          () -> {
            if (initializedReaderManager) {
              readerManager.close();
            }
          },
          indexWriter::rollback);
      throw t;
    }

Trade-offs

  • Roll back, not close: IndexWriter.close() commits by default (IndexWriter.java:1363-1369), so on the new-taxonomy path it would commit the root category the failed constructor had buffered. rollback() also works on a writer that already closed itself after a tragic error (IndexWriter.java:2576-2582).
  • No virtual call: it does not call closeResources(), a documented subclass hook, on a partially constructed object. Both points came from the cross-model review of the first fix draft.
  • The original exception is rethrown with cleanup exceptions suppressed into it; only if a cleanup step throws an Error while the original is not one is that Error thrown instead, with the original suppressed into it (IOUtils.java:116-136), as in IndexWriter's own constructor (IndexWriter.java:1206). The cache is not closed: the default LruTaxonomyWriterCache is heap-only (its close() only clears a map), and a cache the caller passed in stays with the caller.
  • A subclass that overrides openIndexWriter to supply its own IndexWriter gets that writer rolled back when the constructor fails. The openIndexWriter javadoc already makes the taxonomy writer its owner (:206), but a reviewer may want that stated.
  • The helper exists from 10.4.0 on; a 9.x backport would use IOUtils.closeWhileHandlingException in the same place (not run).

What the checks validated

  • Stock 645d4fe14a20: the repro fails with assertions on and off.
  • With the fix: the repro and TestDirectoryTaxonomyWriter pass with assertions on and off (16 tests, 0 failures, 1 skipped: testHugeLabel is @Nightly); the whole :lucene:facet:test passes with assertions on (40 suites, 307 tests, 0 failures, 7 skipped).
  • The independent reproducer's test, unchanged, passes 4 of 4: the existing taxonomy on ByteBuffersDirectory and on FSDirectory, the new taxonomy whose root-category reader open fails, and the control; no leaked-file report. Its 3 bug tests fail on stock code.
  • ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest pass; checkGoogleJavaFormat passes for the fixed class and, once ./gradlew tidy rewraps two lines of the repro test (line breaks only), for the test too.

B. Call the taxonomy writer's own close() or rollback() in the catch (not recommended, not run)

#

Shorter, but close() commits first (DirectoryTaxonomyWriter.java:288-294), and when they complete normally both close() and rollback() (:861-865) end in the overridable closeResources() (:296-299, :308), which runs subclass code on a partially built object.

Trade-offs

  • Reads naturally, but can commit a half-built taxonomy and runs subclass code too early.

Downstream note

#

A read-only code search found no use of DirectoryTaxonomyWriter in Solr, Elasticsearch or OpenSearch, so the exposure is mainly applications that use Lucene's taxonomy facets directly.

How it was found

#

A static scan of the compiled Lucene jars, which follows exception paths and tracks acquired resources, flagged the writer this constructor holds on its I/O exception edges. A fault-injection sweep that fails one file operation at a time showed the lock leak, and a JUnit test confirmed it.

The method in full128 words

Method: semi-formal static analysis (a custom bytecode abstract interpretation), from a sweep over Lucene's failure paths.

  • The analysis interprets the bytecode of the core, codecs, facet, suggest, misc and replicator jars (3,388 classes, 24,094 methods) with explicit exception edges, a live set of acquired resources and interprocedural summaries. Its vacuity check flagged all 7 planted leaks and none of 8 clean idioms.
  • It reported that the IndexWriter from openIndexWriter (:145) is still held on the exception edges of DirectoryReader.indexExists (:154), SegmentInfos.readLatestCommit (:158) and addCategory (:185).
  • A single-fault sweep with the test framework's MockDirectoryWrapper (2,917 fault events on an existing taxonomy, 5,390 on an empty one) showed lock leaks in both cases; a JUnit test on the stock jars confirmed it.

Impact note
Applications that use taxonomy facets with the default DirectoryTaxonomyWriter (default constructor, IndexWriterConfig and codec, FSDirectory with its default NativeFSLockFactory) are hit when one constructor call fails with a non-aborting I/O error after it has opened its internal IndexWriter (while it reads the latest commit of an existing taxonomy, or opens the near-real-time reader that adds the root category of a new one; for example running out of file handles or a transient read error on a network filesystem) and they then retry in the same process: every later new DirectoryTaxonomyWriter on that directory throws LockObtainFailedException 'Lock held by this virtual machine' until the JVM exits, other processes cannot open a writer on it while that JVM lives, and with the non-default SimpleFSLockFactory the write.lock file survives even a normal exit and must be deleted by hand [exec]; taxonomy readers, the committed taxonomy and its ordinals, the main index and other taxonomies are unaffected, the leak is bounded (one IndexWriter and one lock descriptor per failed path; 200 retries added nothing) [exec], a disk-full error during the root-category flush does not leak (IndexWriter's tragic-event path closes the writer) [exec], and no scale is needed.
Summary
You open a taxonomy with new DirectoryTaxonomyWriter(dir) and the constructor throws an IOException, because a file read failed after it had already opened its internal IndexWriter (while reading the latest commit of an existing taxonomy, or while opening a reader to add the root category of a new one); once the error has passed you try again. You expect the retry to work, because a constructor that throws hands the caller nothing to close and so must release what it acquired, as IndexWriter's own constructor does. Instead the constructor has no cleanup after openIndexWriter, so the unreachable IndexWriter keeps the taxonomy's write lock and every later DirectoryTaxonomyWriter on that directory in the same JVM fails with LockObtainFailedException 'Lock held by this virtual machine'.
