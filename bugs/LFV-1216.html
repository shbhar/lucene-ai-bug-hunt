ByteBuffersDataOutput accepts 31 block bits, its documented maximum, but then cannot store a single byte

ByteBuffersDataOutput documents 31 as its largest allowed block size and accepts it, but a 31-bit block is 2^31 bytes, more than any Java buffer can hold, so the first writeByte throws IllegalArgumentException: capacity < 0. The real limit is 30; the fix is one line.

The finding in 30 seconds

#

A block's size is computed as 1 << blockBits in a 32-bit int. For 30 that is 1,073,741,824 (1 GiB); for 31 it wraps to -2,147,483,648. The constructor only checks that the bits do not exceed 31, so the negative size reaches the allocator at the first write.

Background

#
  1. ByteBuffersDataOutput is Lucene's in-memory DataOutput (used by ByteBuffersDirectory, FST building and many writers). It holds a list of ByteBuffer blocks of 2^bits bytes, starting at minBitsPerBlock and growing up to maxBitsPerBlock; the defaults are 10 and 26 (1 KiB to 64 MiB).
  2. A Java ByteBuffer's capacity is an int, so no buffer can be larger than 2^31 - 1 bytes. The largest power-of-two block is 2^30 bytes, 30 bits.

The finding, step by step

#
  1. ByteBuffersDataOutput keeps its bytes in blocks of 2^bits bytes. Its public constant LIMIT_MAX_BITS_PER_BLOCK is 31, documented as the "Largest maxBitsPerBlock allowed": the expert constructor rejects 32 and accepts 31.
  2. Build new ByteBuffersDataOutput(31, 31, ALLOCATE_BB_ON_HEAP, NO_REUSE) and write one byte. You expect the byte to be stored, or 31 to be rejected up front, as 32 is.
  3. Instead the constructor returns, and the first writeByte computes the block size as 1 << 31 in an int: -2,147,483,648. The allocator rejects it with IllegalArgumentException: capacity < 0: (-2147483648 < 0). Nothing is stored.
  4. A 31-bit block can never exist: a buffer's capacity is an int, at most 2^31 - 1 bytes, so 30 bits (1 GiB) is the largest block. FSTCompiler.getOnHeapReaderWriter(31) fails the same way; Lucene's FST reader already caps the same value at 30.

Who is affected

#

Only code that explicitly asks for 31 block bits: the expert constructor with 31 as the minimum (for example LIMIT_MAX_BITS_PER_BLOCK for both bounds), or FSTCompiler.getOnHeapReaderWriter(31). The defaults use 10 to 26 bits and no in-tree caller passes 31. It fails loudly at the first write, with nothing stored. Every release since 7.5.0.

Mechanism, terms and numbers640 words

ByteBuffersDataOutput stores data in a list of ByteBuffer blocks of 2^bits bytes. Its public constant LIMIT_MAX_BITS_PER_BLOCK = 31 is documented as the "Largest maxBitsPerBlock allowed", and the expert constructor validates against it: 32 is rejected, 31 is accepted. But the class computes a block's size as 1 << blockBits in int, and 1 << 31 is Integer.MIN_VALUE. An output built with 31-bit blocks is therefore created normally and fails at its first write, when ByteBuffer.allocate(-2147483648) throws IllegalArgumentException: capacity < 0.

No Java buffer can hold 2^31 bytes, so no allocator can supply a 31-bit block, and with the default heap allocator 31 fails at the first write. 30 (1 GiB) is the largest block size that can exist, and it is the bound Lucene's FST read side already enforces. FSTCompiler.getOnHeapReaderWriter(31) reaches the same failure. Only code that explicitly asks for 2 GiB blocks is affected, in the reproduced case nothing is stored or lost, and no in-tree caller does it. Present since the class was added (LUCENE-8468, 7.5.0); the fix is LIMIT_MAX_BITS_PER_BLOCK = 30.

Mechanism (Lucene main 5adff78bb168)

#
  1. ByteBuffersDataOutput.java:90-91: /** Largest {@code maxBitsPerBlock} allowed */ public static final int LIMIT_MAX_BITS_PER_BLOCK = 31;. This is the fix site.
  2. The expert constructor (:141-182, "Expert: Creates a new output with custom parameters.") rejects only minBitsPerBlock < 1 (:154), maxBitsPerBlock > LIMIT_MAX_BITS_PER_BLOCK (:162-169, "too large, must not exceed") and min > max (:170-177), so (31, 31) passes; it starts at blockBits = minBitsPerBlock (:179).
  3. The current block starts empty (:118), so the first writeByte calls appendBlock() (:185-187).
  4. appendBlock() (:516-529) computes final int requiredBlockSize = 1 << blockBits; (:524), which is -2147483648 for 31, and passes it to the allocator (:525); the default ByteBuffer::allocate (:43) throws capacity < 0. blockSize() (:512-514) uses the same shift, so toString() reports "block size: -2,147,483,648".
  5. Second public way in: FSTCompiler.getOnHeapReaderWriter(int blockBits) (util/fst/FSTCompiler.java:150-159, class @lucene.experimental) has no range check and builds new ByteBuffersDataOutput(blockBits, blockBits, ALLOCATE_BB_ON_HEAP, NO_REUSE) (util/fst/ReadWriteDataOutput.java:42-48).
  6. The same value is capped at 30 elsewhere in core: OnHeapFSTStore.java:45-48 ("maxBlockBits should be 1 .. 30; got ") and FST.java:413 (DEFAULT_MAX_BLOCK_BITS = 30 on 64-bit JVMs, 28 otherwise).

Executed (probe on main, assertions off)

#
  • (31, 31): accepted, toString() = "0 bytes, block size: -2,147,483,648, blocks: 0"; writeByte throws capacity < 0, size() stays 0; a recording allocator is asked for [-2147483648].
  • FSTCompiler.getOnHeapReaderWriter(31): accepted; its first writeByte throws the same exception.
  • Controls: (1, 32) is rejected ("maxBitsPerBlock (32) too large, must not exceed 31"); (30, 30) holds a byte ("1 bytes, block size: 1,073,741,824, blocks: 1"); new OnHeapFSTStore(31, ..) is rejected ("maxBlockBits should be 1 .. 30; got 31").

Read only, not run, not claimed

#

With maxBitsPerBlock = 31 and a smaller minimum, the block size grows by one bit each time the output holds 100 blocks (:97, :517-518), so the 31-bit step would come only after about 100 blocks of 2^30 bytes, about 100 GiB on heap. If it were reached, rewriteToBlockSize(31) would take the first block off the list (blocks.pollFirst(), :540) before the new 31-bit output's first allocation throws (:542, via writeBytes :220-221 and appendBlock :524-525), so that block would be dropped while blockBits and ramBytesUsed keep their old values (:549-551 never run).

An allocator that ignores the requested size and returns a smaller buffer gets past :525, but then fails the capacity assertion at :526 with assertions on; with assertions off its blocks are not 31-bit blocks either, and size() multiplies by the negative blockSize() (:349-357). The default heap allocator, and any allocator that returns the capacity it is asked for, fails at the first write.

Exposure and likelihood169 words
  • Who: application code that passes 31 as the minimum block bits of the expert constructor, or calls FSTCompiler.getOnHeapReaderWriter(31).
  • Not default: the defaults are 10 to 26 bits (ByteBuffersDataOutput.java:82, :85, :137-139); the size-hint constructor caps at 26 (:128-134, :554-564); FSTCompiler's default on-heap output uses 15 (FSTCompiler.java:354) and FST's empty output 10 (FST.java:464); the FST read side never exceeds 30. git grep finds no in-tree caller that passes 31, and a public code search for the constant found only copies of Lucene's own source.
  • Effect: the output is unusable, and the error arrives late, at the first write, as a JDK "capacity < 0" message that does not name the setting. In the reproduced (31, 31) case nothing is stored, lost or wrong, and no scale is needed: one byte. A (x, 31) output would reach 31 bits only after about 100 GiB and would then fail and, by reading, drop a block (see the read-only note above).

Why it looks unintended

#
  • The constant's javadoc calls 31 the "Largest maxBitsPerBlock allowed"; the constructor rejects 32 and accepts 31.
  • A 31-bit block can never exist: no Java buffer holds 2^31 bytes, and the int shift hands the allocator -2,147,483,648.
  • Lucene caps the same value at 30 elsewhere (OnHeapFSTStore), and no test builds an output at the limit.
The full argument144 words
  • The contract: "Largest {@code maxBitsPerBlock} allowed" (ByteBuffersDataOutput.java:90), and the constructor's validation (:162-169), which treats anything above 31 as illegal and 31 as legal.
  • Arithmetic: a 2^31-byte ByteBuffer cannot exist, and the class's own shift produces the negative size (a recording allocator received -2147483648).
  • Lucene says 30 elsewhere: OnHeapFSTStore.java:45-48 and FST.java:413.
  • Tests: TestByteBuffersDataOutput.testIllegalMaxBitsPerBlock (:107-117) only checks that LIMIT_MAX_BITS_PER_BLOCK + 1 is rejected; no test builds an output at the limit.
  • History: the check maxBitsPerBlock > 31 and the shift came with the class (LUCENE-8468, 2018); LUCENE-10155 (#360, 2021) named the bound and kept the value. In the #360 review, Robert Muir (rmuir) wrote that "the defaults should be fast, but the permissible values should be ones that work correctly". No javadoc, CHANGES or MIGRATE entry, commit message or thread says 31 is meant to be accepted but unusable.
The devil's-advocate check127 words

The constructor is labelled "Expert:" and FSTCompiler is @lucene.experimental; 31 can be read as the largest shift still computable, leaving the real limit to the allocator, which does reject it with an IllegalArgumentException; asking for 2 GiB blocks is arguably a misuse; it fails loudly at once, nothing is lost, and no report of it was found since 7.5.0.

Why it fails: "Expert" does not change what the constant's javadoc says ("allowed"); the negative size comes from the class's own arithmetic, and no allocator can supply a 2^31-byte block; the same codebase already caps the value at 30. What remains is an impact argument, which is why this is Low: it is an off-by-one in a documented limit with a one-line fix, not a crash.

How it was found

#

Semi-formal: a proof-obligation audit of ByteBuffersDataOutput against its documented limit, that every block-bits value the constructor accepts gives a block that can be allocated. The obligation fails at 31, where 1 << 31 is negative in an int, and a JUnit test on stock main witnessed the failure.

The method in full59 words
  • Obligation: for every blockBits the constructor accepts (up to LIMIT_MAX_BITS_PER_BLOCK), the block size 1 << blockBits is a valid ByteBuffer capacity.
  • Finding: at the documented maximum, 31, the int shift gives Integer.MIN_VALUE (ByteBuffersDataOutput.java:524), which no allocator can satisfy.
  • Witness: the one-test JUnit repro, then an independent reproduction, an intended-behaviour review and an adjudication (see Independent checks).
