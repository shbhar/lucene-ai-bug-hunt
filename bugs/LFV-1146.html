Range and shape doc-values fields keep reporting their old value after setBytesValue

If you reuse a LongRangeDocValuesField with setBytesValue, the index stores the new range but getMin/getMax keep returning the old one: built for [1, 2] and given [10, 20], getMin(0) still returns 1. The other range doc-values fields and the shape doc-values getters do the same.

The finding in 30 seconds

#

A Lucene field holds its value as bytes, and Field.setBytesValue swaps those bytes so one field object can be reused for many documents. The range doc-values fields also keep the arrays they were built from, and their getters answer from those arrays, not from the bytes.

  1. You build new LongRangeDocValuesField("r", new long[] {1}, new long[] {2}) and reuse it for the next document: setBytesValue with the encoding of [10, 20] from LongRange.verifyAndEncode. This is the reuse idiom Field documents and Lucene's own facet tests use on this class.
  2. You expect getMin(0) = 10 and getMax(0) = 20. The index does get [10, 20]: a doc-values query for [15, 15] matches the document, one for [1, 2] does not.
  3. Instead getMin(0) returns 1 and getMax(0) returns 2. The constructor kept its min/max arrays, the getters read only those, and setBytesValue replaces only the bytes.
  4. Int/Float/DoubleRangeDocValuesField do the same. A LatLonShapeDocValuesField built for a point and given a 3-point line's bytes still reports type POINT, 1 term and the point's centroid, instead of LINE, 2 terms and the line's centroid.

Who is affected

#

Applications that reuse a range or shape doc-values field through setBytesValue and then read that object's getters, for example to log the value or derive another field. No setting is involved. The indexed doc value is correct, and no Lucene code reads these getters, so it is rare and minor.

Mechanism, terms and numbers463 words

Field.setBytesValue is the documented way to reuse one field object for many documents, and the only reuse path the range doc-values fields have. After it, Long/Int/Float/DoubleRangeDocValuesField.getMin/getMax still return the constructor's range while the index stores the new one: built for [1, 2] and given the bytes of [10, 20], getMin(0) returns 1 and getMax(0) returns 2. LatLon/XYShapeDocValuesField likewise keep the old shape's centroid, bounding box, term count and dimension type. The indexed doc value, the only thing these fields index, takes the new bytes (an executed control reads it back and runs a slow intersects query), and no Lucene code reads these getters, so only applications that read the getters of a reused field object are hit. In every release since 8.2.0 (range) and 9.4.0 (shape).

Mechanism (main 5adff78bb168)

#
  1. The constructor keeps the arrays. LongRangeDocValuesField(String, long[], long[]) encodes min/max into the bytes it passes to the base class and also keeps the caller's arrays in final fields, by reference (LongRangeDocValuesField.java:27-29, :32-38).
  2. The getters read only those arrays. getMin/getMax ("Get the minimum/maximum value for the given dimension") return min[dimension] / max[dimension] (:40-56, the fix site). Int/Float/Double are identical.
  3. setBytesValue replaces only the bytes. Neither the four classes nor their package-private base BinaryRangeDocValuesField (:22-37) override it, so the inherited Field.setBytesValue(BytesRef) sets fieldsData = value and nothing else (Field.java:335-346).
  4. Indexing reads the bytes. The doc-values writer takes field.binaryValue() (IndexingChain.java:1741-1742), which is fieldsData (Field.java:428-434). So the index gets [10, 20] while the getters say [1, 2]. That binary doc value is all these fields index (BinaryDocValuesField.java:44, ShapeDocValuesField.java:49).
  5. Shapes, same pattern. ShapeDocValuesField decodes the shape once into protected final ShapeDocValues shapeDocValues (ShapeDocValuesField.java:43, :54-58). numberOfTerms (:85-87), getHighestDimensionType (:107-109) and the LatLon/XY getCentroid/getBoundingBox (LatLonShapeDocValuesField.java:66-75, XYShapeDocValuesField.java:66-74) read that cached decode; there is no setBytesValue override.

The numbers

#
  • Long range field built for [1, 2], given the bytes of [10, 20]: binaryValue() decodes to 10..20, the indexed doc value decodes to 10..20, a newSlowIntersectsQuery for [15, 15] counts 1 and one for [1, 2] counts 0; getMin(0) = 1, getMax(0) = 2. A field built directly for [10, 20] reports 10 and 20.
  • Int/Float/Double range fields, same steps: 1/2, 1.0/2.0, 1.0/2.0.
  • LatLonShapeDocValuesField for the point (0, 0) given the bytes of a 3-point line (lat 10..12, lon 20..22): type POINT, 1 term, centroid (0, 0), a 0-size bounding box. The line's own field: LINE, 2 terms, centroid about lat 11, lon 21. XYShapeDocValuesField the same.
  • The point-range sibling LongRange, reused the same way, returns 10/20: it decodes its current bytes (LongRange.java:156-170), though from index 0 of the backing array, ignoring the BytesRef offset (:173-181).
Exposure and likelihood170 words
  • Who. Application code that reuses a Long/Int/Float/DoubleRangeDocValuesField or LatLon/XYShapeDocValuesField object through setBytesValue (the documented reuse idiom, and the one Lucene's own TestRangeOnRangeFacetCounts uses on the range classes) and then reads getMin/getMax, getCentroid, getBoundingBox, numberOfTerms or getHighestDimensionType from that object.
  • Default vs opt-in. No setting involved; the trigger is the Expert setter followed by a getter call on the same object.
  • Effect. A public getter silently returns a value that is not the field's value. The indexed doc value, the only thing these fields index, is the new range: the independent reproducer's control test and the diagram probe read it back and run one newSlowIntersectsQuery ([15, 15] matches, [1, 2] does not); no shape query was run. Nothing in lucene/*/src/java reads these getters, and no Lucene test reads the range getters at all.
  • Scale. None: one field, one call.
  • Likelihood. Rare: the application usually still holds the values it just encoded, and the recorded searches found no report since the range classes were added in 2019.

Why it looks unintended

#
  • setBytesValue is documented to "change the value of this field"; the getters to "Get the minimum value for the given dimension". Nothing calls them constructor snapshots.
  • Lucene's own TestRangeOnRangeFacetCounts reuses these exact classes through setBytesValue.
  • Siblings stay consistent: LongRange decodes its current bytes, KeywordField re-syncs in an override, LongPoint rejects the setter.
The full argument170 words
  • Contract. Field.setStringValue: "Expert: change the value of this field. This can be used during indexing to re-use a single Field instance" (Field.java:294-303); setBytesValue(BytesRef) refers to it (:329-334). The getters: "Get the minimum value for the given dimension" (LongRangeDocValuesField.java:40), "retrieves the centroid location for the geometry" (ShapeDocValuesField.java:97).
  • Siblings. The named siblings show three established approaches. Decode the current bytes: LongRange.getMin/getMax (LongRange.java:156-170). Re-sync in a setter override: KeywordField (KeywordField.java:125-132), StringField (StringField.java:108-115). Reject the setter: LongPoint (LongPoint.java:75-78), IntPoint, FloatPoint, DoublePoint.
  • Lucene's own usage. TestRangeOnRangeFacetCounts.java:1543-1561 encodes with LongRange/DoubleRange.verifyAndEncode (public since #11901, 9.5.0) and calls field.setBytesValue(new BytesRef(encodedValue)); it never reads the getters.
  • History. No commit ever overrode setBytesValue in these classes (git log -S setBytesValue). In the review of #11901 (2022-12-09/10) a proposed public LongRangeDocValuesField.setLongRangeValue, which checked and encoded the new range and then changed only the bytes through setBytesValue, was dropped as out of scope; nobody mentioned the getters.
The devil's-advocate check188 words

The strongest case for "intended": setBytesValue is an Expert hook for re-using a Field instance to avoid GC cost (Field.java:294-298); it takes raw bytes unchecked (only a non-null BytesRef is required, :336-344, for the range and shape classes alike); and the typed getters can be read as metadata of the constructed value. The shape classes are also @lucene.experimental and meant to be built through the LatLonShape/XYShape factories (one of which takes an existing BytesRef encoding).

Why the bug reading is better supported for the range classes: the setter is documented to change the field's value, the bytes are valid Lucene encodings, Lucene's own tests use this exact idiom on these classes, and the sibling LongRange returns the new value after the same call. A maintainer could still treat raw byte replacement as deliberately low-level and prefer documenting the getters (option C). The cross-model reviews rated the intended argument moderate, and the devil's-advocate verifier found no surviving intended argument for the range classes; for the shape classes the misuse argument is stronger, so they come second. The argument bears on likelihood, hence priority Low.

Suggested fix

#

Recommended Decode getMin/getMax from the current bytes (fix A)

Make getMin/getMax of the four range fields decode the field's current bytes, as LongRange does, with the dimension check taken from those bytes. The repro passes with assertions on and off, and the closest suites, including the facet tests that reuse these fields, pass: 62 classes, 525 tests, 0 failures.

  public long getMin(int dimension) {
    BytesRef b = binaryValue();
    if (dimension < 0 || dimension >= b.length / (2 * LongRange.BYTES)) {
      throw new IllegalArgumentException("Dimension out of valid range");
    }
    return NumericUtils.sortableBytesToLong(b.bytes, b.offset + dimension * LongRange.BYTES);
  }
  // getMax: the same, at b.offset + b.length / 2 + dimension * LongRange.BYTES
All options and trade-offs4 options · 559 words

Option A was built and checked through gradle on 5adff78bb168; B, C and the shape fix were not run. A first run that changed only the decode and kept the old dimension guard gave the same test results; the guard change is needed because the decode would turn today's off-by-one guard into a silent wrong value.

Decode getMin/getMax from the current bytes (fix A) (validated by the checks) (recommended)

#

In each of Long/Int/Float/DoubleRangeDocValuesField, read binaryValue(), check the dimension against the dimension count of those bytes, and decode the value with the matching point-range class's encoding (unlike LongRange, honouring the BytesRef offset). The other three classes differ only in the decode call.

  public long getMin(int dimension) {
    BytesRef b = binaryValue();
    if (dimension < 0 || dimension >= b.length / (2 * LongRange.BYTES)) {
      throw new IllegalArgumentException("Dimension out of valid range");
    }
    return NumericUtils.sortableBytesToLong(b.bytes, b.offset + dimension * LongRange.BYTES);
  }
  // getMax: the same, at b.offset + b.length / 2 + dimension * LongRange.BYTES

Trade-offs

The guard must change with the decode: today's dimension > 4 || dimension > min.length (LongRangeDocValuesField.java:42, :51) lets dimension == min.length through, which now ends in an ArrayIndexOutOfBoundsException on min[] but would silently read the first max value once the getter decodes the bytes. Each call then decodes one 4- or 8-byte value (a big-endian read and a few bit operations). The getters also stop following later edits to the caller's own arrays, which the constructor keeps by reference (:36-37). The min/max fields become unused and can be dropped. The patch assumes a well-formed encoding: b.length / (2 * BYTES) is the dimension count only when the length is a multiple of 2 * BYTES, and the setter accepts any bytes, so a malformed length gives a misleading half boundary rather than a clean exception; a b.length % (2 * BYTES) != 0 check would close that (not built). The repro is the regression test.

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, seed DEADBEEF: the repro fails without the fix (assertions on and off) and passes with it (on and off).
  • With the fix: the repro, all of org.apache.lucene.document.*, TestRangeFieldsDocValuesQuery and the facet module's TestRangeOnRangeFacetCounts (which reuses these fields through setBytesValue): 62 classes, 525 tests, 0 failures, 0 errors, 26 skipped by their suites. :lucene:core:checkGoogleJavaFormat passes.
  • The repro covers only the Long class. A public-API probe with fix A shadowed in shows Int/Float/Double given the bytes of [10, 20] also return 10/20, 10.0/20.0, 10.0/20.0 (1/2 without the fix), with assertions on and off.

Reject setBytesValue on the range fields (not built)

#

Override setBytesValue in BinaryRangeDocValuesField to throw, as LongPoint does.

Trade-offs

Simple and loud, but it breaks the reuse idiom TestRangeOnRangeFacetCounts relies on and removes the only reuse path these classes have.

Document the getters as constructor values (not built)

#

A javadoc line on getMin/getMax saying they return the constructor's arguments.

Trade-offs

Smallest change, but the object then reports a value it does not index.

Shape fields: re-decode or reject in setBytesValue (not built)

#

Override setBytesValue in ShapeDocValuesField to re-decode shapeDocValues from the new bytes through a small per-subclass decode hook, or to reject the setter.

Trade-offs

shapeDocValues stops being final; the constructor is package-private, so no outside subclass exists. Fits in the same change or a follow-up.

Downstream note

#

Lucene itself never reads these getters, so a downstream product is affected only if its own code reuses such a field through setBytesValue and reads the getters back; downstream code was not surveyed.

How it was found

#

A proof-obligation audit of the range and shape doc-values fields' getters: a getter documented as the field's minimum must follow every documented way of changing the field's value. setBytesValue changes only the bytes while the getters read the constructor's arrays; a one-method public-API JUnit test then witnessed it.

The method in full122 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read the getters of the range and shape doc-values fields against the obligation that they describe the field's current value, and checked every way the value can change: the only one is the inherited Field.setBytesValue, which no class in either family overrides.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off and on the 10.6.0 jars, and a probe that shows the same for the other three range classes and both shape classes.
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").
