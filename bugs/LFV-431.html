AnalyzingSuggester and FuzzySuggester getCount() counts analyzed paths, not entries, when the analyzer makes a token graph

With a synonym rule in the index analyzer, AnalyzingSuggester and FuzzySuggester count each analyzed form of an entry as a separate entry: one entry fast with the rule fast -> {fast, quick} gives getCount() 2. Suggestions are right; only the count is wrong, also after store()/load(), since 5.3.0.

The finding in 30 seconds

#

build() loops over the entries and, for each one, over its analyzed paths, writing every path into the suggester. The entry counter is incremented in the header of that inner loop, so an entry with two paths counts twice. The number is published when the build ends, saved by store(), read back by load() and returned by getCount().

Background: analyzed paths in AnalyzingSuggester

#
  1. AnalyzingSuggester (and its subclass FuzzySuggester) runs each suggestion entry through an index analyzer and stores the analyzed text. A lookup analyzes what the user typed, matches it against the stored text and returns the original entries.
  2. An analyzer can stack tokens at one position. The synonym rule fast -> {fast, quick} turns fast car into a small token graph with two paths, fast car and quick car. The suggester stores both, so typing quick finds fast car.
  3. getCount() reports how many entries the suggester was built from.

The finding, step by step

#
  1. Build an AnalyzingSuggester from one entry, fast, with an index analyzer whose synonym rule is fast -> {fast, quick}. The analyzer turns the entry into two analyzed paths, fast and quick; the suggester indexes both, so typing qu or fa suggests fast.
  2. You expect getCount() to return 1: it is documented as "the number of entries the lookup was built with".
  3. You get 2: build() adds 1 for every analyzed path, not once per entry. Two entries fast car and red car give 3; the single entry wifi wifi wifi with a synonym for wifi gives 8 (2 x 2 x 2 paths).
  4. store()/load() keep the wrong number and FuzzySuggester inherits it. 4.7.0 to 5.2.1 counted entries; a 2015 loop rewrite moved the increment into the per-path loop. Counting once per entry again is a one-line fix.

Who is affected

#

Applications that build AnalyzingSuggester or FuzzySuggester with synonyms or a word-delimiter graph in the index analyzer, a setup the class javadoc describes, and read getCount() to show, log or check the dictionary size. The count is inflated by the number of paths per entry; suggestions, weights and build work are unaffected.

Mechanism, terms and numbers597 words

Lookup#getCount returns "the number of entries the lookup was built with". AnalyzingSuggester.build (inherited by FuzzySuggester) indexes every analyzed path of each entry, and it increments its counter in the header of that per-path loop (AnalyzingSuggester.java:419), so with an index analyzer that stacks tokens (a synonym graph, a word-delimiter graph with PRESERVE_ORIGINAL) each entry counts once per path: one entry fast with the rule fast -> {fast, quick} gives 2, the entries fast car and red car give 3, and the entry wifi wifi wifi with a stacked synonym gives 8. The same per-path increment leaves out an entry that analyzes to no token at all, such as an entry of only stop words. store() writes the number and load() reads it back. Suggestions are correct and no production code in Lucene calls getCount(), so only applications that show or check the count are affected. The count was per entry from 4.7.0, when it was added, to 5.2.1; LUCENE-6365 moved the increment while rewriting the loop, first released in 5.3.0. Every release run from 5.3.0 to 10.6.0 and main is affected, and moving newCount++ before the per-path loop fixes it.

The mechanism (main 645d4fe14a20)

#
  1. One entry, many paths. For each entry build analyzes it into an automaton and iterates its finite strings, at most maxGraphExpansions of them (AnalyzingSuggester.java:415-417). The 3- and 4-argument constructors of both classes pass -1, no limit (:173-176, :182-196; FuzzySuggester.java:98-129). The class knows paths and entries differ: maxAnalyzedPathsForOneInput is the "Highest number of analyzed paths we saw for any single input surface form. For analyzers that never create graphs this will always be 1." (:153-157).
  2. The increment is in the per-path loop header (:415-419; the end-of-line comments are ours):
   for (BytesRef surfaceForm; (surfaceForm = iterator.next()) != null; ) {       // once per entry
     LimitedFiniteStringsIterator finiteStrings =
         new LimitedFiniteStringsIterator(toAutomaton(surfaceForm, ts2a), maxGraphExpansions);

     for (IntsRef string; (string = finiteStrings.next()) != null; newCount++) { // once per path
  1. Published, stored, reloaded. count = newCount at the end of the build (:590); store() writes it (:601), load() reads it back (:614), getCount() returns it (:851-852).
  2. FuzzySuggester extends AnalyzingSuggester (FuzzySuggester.java:66) and overrides neither build nor getCount.

Entries with exactly one analyzed path are counted right. An entry that analyzes to no token (a blank entry, or only stop words) has no path, because the automaton TokenStreamToAutomaton builds reaches an accept state only through a position that a token created (TokenStreamToAutomaton.java:244-255), so the per-path increment leaves it out: 5.2.1 counted it (2 for the, fast car), 5.3.0 does not (1), and the fix counts it again (2). Every lookup checked in these runs returned the right suggestions.

Exposure and likelihood199 words
  • Who. Users of AnalyzingSuggester and FuzzySuggester (both @lucene.experimental) whose index analysis gives an entry several paths, as SynonymGraphFilter with a matching rule and WordDelimiterGraphFilter with PRESERVE_ORIGINAL on a token it splits do in the runs. The class javadoc itself shows a synonym setup (AnalyzingSuggester.java:78-80).
  • Effect. A silently wrong number from getCount(): the inflation factor is the number of analyzed paths per entry, 2x for one matching synonym and, with independent two-way synonym alternatives, 2^k for k matching tokens in one entry (8 for wifi wifi wifi); the default constructors set no cap (maxGraphExpansions -1). Entries that analyze to no token are left out of the count. A suggester saved with store() and reloaded with load() reports the same wrong number until it is rebuilt.
  • Not affected. Suggestions, weights, payloads and build work: every path is indexed whether or not it is counted. No production code in Lucene calls getCount() (store() only writes the field), and Solr's suggester code does not call it either (other downstream code was not surveyed).
  • Likelihood: plausible. Deterministic on every such build, but only applications that read the count notice; the searches found no public report since 5.3.0.

Why it looks unintended

#
  • Lookup#getCount: "Get the number of entries the lookup was built with"; the class tracks analyzed paths separately (maxAnalyzedPathsForOneInput).
  • 4.7.0 to 5.2.1 counted once per entry; the 2015 loop rewrite (LUCENE-6365) moved the increment without discussing counting.
  • Not the internal record count either: dropped duplicates are counted, and the number changes with maxGraphExpansions.
The full argument233 words
  • Contract. Lookup#getCount: "Get the number of entries the lookup was built with" / "@return total number of suggester entries" (Lookup.java:171-176). The field: "Number of entries the lookup was built with" (AnalyzingSuggester.java:166). Lookup.build(Dictionary) feeds dict.getEntryIterator() (Lookup.java:145-146), so the entries are what the dictionary yields.
  • The class separates paths from entries. maxAnalyzedPathsForOneInput counts "analyzed paths ... for any single input surface form" (:153-157); maxGraphExpansions "only matters if your analyzer makes lots of alternate paths (e.g. contains SynonymFilter)" (:144-147).
  • History. LUCENE-5404 (#6467, "Add support to get number of entries a Suggester Lookup was built with and minor refactorings"; b5926da2d67 on trunk and fdf4595051a on branch_4x, which 4.7.0 ships) put count++ after the loop over an entry's paths, so every entry counted once, also one with no path. LUCENE-6365 (#7425, 3d8bfad40b0 and branch_5x 9a3ec6ce777, 2015-07-04, first released in 5.3.0) replaced that loop with an iterator loop and moved the increment into its header; its commit message, CHANGES entry and issue discussion say nothing about counting. LUCENE-10292 (#11328) renamed the counter to newCount and kept it there. That the move was an accident is an inference from this record; nobody upstream has said so.
  • Tests. Every upstream getCount assertion for these classes uses MockAnalyzer, where paths equal entries (TestAnalyzingSuggester.java:181, 193, 1028, 1051; TestFuzzySuggester has none). The whole suggest suite passes with the fix.
The devil's-advocate check172 words

Strongest case (the devil's-advocate verifier and the adjudication): "entries" means the suggester's internal records, the analyzed-form and surface-form pairs it writes into its FST, so counting paths is by design; getCount is loose across lookups anyway (inputs a, a, b give 2 in WFSTCompletionLookup, 3 in TSTLookup and FSTCompletionLookup); and the classes are experimental.

Why it fails: the count is not the record count either. With a keyword analyzer a, a, b gives 3 although the duplicate surface form is dropped from the FST, and fast car twice with the synonym gives 4. A documented "number of entries" that changes with the maxGraphExpansions tuning knob (3 or 2 for the same two entries) is implausible, and #6467 and the 4.7.0 to 5.2.1 code count entries. The per-path count also drops entries that 5.2.1 counted: an entry that analyzes to no token adds 0. Experimental status bears on severity, not on intent. Still, a maintainer who puts compatibility first may prefer to document today's count rather than change a stored statistic.

Suggested fix

#

Recommended Count once per entry, before the per-path loop

Increment newCount once per entry, just before the loop over its analyzed paths, instead of in that loop's header (one file, +2/-1). This restores the 4.7.0 to 5.2.1 count. The repro, TestAnalyzingSuggester, TestFuzzySuggester and the whole suggest test suite pass with it.

        LimitedFiniteStringsIterator finiteStrings =
            new LimitedFiniteStringsIterator(toAutomaton(surfaceForm, ts2a), maxGraphExpansions);

-        for (IntsRef string; (string = finiteStrings.next()) != null; newCount++) {
+        newCount++; // one entry, however many analyzed paths it has
+        for (IntsRef string; (string = finiteStrings.next()) != null; ) {
All options and trade-offs4 options · 575 words

The recommended fix is the finder's one-line change, applied to 645d4fe14a20 in a scratch worktree with git apply and run through gradle. An equivalent placement and two alternatives follow. Fix A changes the stored count once a suggester is rebuilt, so the issue can ask the maintainers whether compatibility makes them prefer documenting the current count (option C).

Count once per entry, before the per-path loop (validated by the checks) (recommended)

#

In AnalyzingSuggester.build, move newCount++ out of the header of the loop over finiteStrings to the line before it.

Trade-offs

  • Restores the 4.7.0 to 5.2.1 meaning: one per input entry, duplicates included, as TSTLookup and FSTCompletionLookup count. Entries with exactly one analyzed path count as today; an entry with several paths counts once instead of once per path, and an entry that analyzes to no token counts once instead of zero times, as in 5.2.1.
  • No format change: store()/load() are untouched. Suggesters saved by affected versions keep their inflated count until rebuilt; worth a CHANGES line.
  • Behaviour change to weigh: once rebuilt, a suggester whose entries have several paths or none reports a different number than before (smaller, or larger), so an application that compares counts across a Lucene upgrade sees a one-time step. A maintainer who puts compatibility first may prefer documenting the current count.
  • No change to suggestions or build work: the loop body is untouched.

Count after the per-path loop (the pre-5.3.0 placement)

#

Put newCount++ after the loop, next to the maxAnalyzedPathsForOneInput update (AnalyzingSuggester.java:484).

Trade-offs

Identical to the recommended fix for every entry, including one with no path: both add 1 once per entry. Executed by the fact check with the fixed class shadowed: the repro passes with assertions off, and every probe value, the zero-token cases included, equals the recommended fix's.

Document the per-path count (not recommended)

#

Say in the field comment and an AnalyzingSuggester#getCount javadoc that the count is of analyzed paths.

Trade-offs

Keeps today's numbers but contradicts Lookup#getCount, makes the number depend on maxGraphExpansions, and is still not the record count (duplicates are counted, entries with no token are not). It is the option for a maintainer who puts compatibility first.

Count the stored records (not recommended)

#

Count the distinct analyzed-form and surface-form pairs written into the FST.

Trade-offs

Also changes the count for analyzers without graphs (a, a, b would give 2) and has no basis in the javadoc.

Downstream note

#

Products that show a suggester's entry count, for example as a dictionary-size statistic, report inflated numbers when their suggest analyzer uses synonyms; the suggestions themselves are unaffected.

How it was found

#

Code reading, no formal tool. While listing what every Lookup implementation counts and comparing it with the getCount javadoc, the finder saw the increment in the header of the per-path loop. A public-API JUnit with the stock SynonymGraphFilter confirmed it, and the git history dated it to 2015.

The method in full123 words

Method: non-formal (code reading plus an executed test), a hunt unit (counts and statistics across modules), 2026-10-26, main ea57360912ed.

  • The finder inventoried what each suggester's getCount() counts and read it against the javadoc; AnalyzingSuggester.java:419 was the one place that counts analyzed paths rather than inputs (the inventory also noted that WFSTCompletionLookup counts distinct keys, an ambiguity it did not file).
  • A JUnit on the stock jars (entries fast car and red car, WhitespaceTokenizer + SynonymGraphFilter, lookups asserted before the count) failed for both suggesters: 3 instead of 2.
  • The history clone (git log -G on the counting line, git show of the four commits that touched it) and release runs from 4.6.1 to 10.5.2 dated the change to LUCENE-6365.

LFV-431, snapshot of 2026-11-05

Registry title
AnalyzingSuggester and FuzzySuggester getCount() counts analyzed paths instead of entries when the analyzer produces a token graph (synonyms, word-delimiter graphs), and store()/load() persist the inflated count
Area
suggest / analyzing suggester (AnalyzingSuggester.build and getCount, inherited by FuzzySuggester)
Priority
Low, rank 631: AnalyzingSuggester and FuzzySuggester getCount() is inflated whenever the analyzer makes token graphs while lookups stay correct, and only apps that display the count notice.
Impact class
minor
Impact note
Only a statistic is wrong: applications that build an AnalyzingSuggester or FuzzySuggester (every release from 5.3.0 to 10.5.2 and main) with an index analyzer that emits stacked tokens, such as SynonymGraphFilter or WordDelimiterGraphFilter with PRESERVE_ORIGINAL, get from getCount(), and from a suggester reloaded with load(), the number of analyzed paths (up to maxGraphExpansions per entry, unlimited in the convenience constructors) instead of the number of entries, on every build and at any scale; suggestions are unchanged, and nothing in Lucene reads the value.
Summary
You build an AnalyzingSuggester or FuzzySuggester from the two entries 'fast car' and 'red car' with an analyzer whose synonym rule maps fast to {fast, quick}, and you expect getCount() to return 2, because Lookup#getCount is documented as 'the number of entries the lookup was built with'. It returns 3: build() increments its counter once for every analyzed path of an entry ('fast car' and 'quick car' here), not once per entry, so each entry counts as often as its token graph has paths (8 for the single entry 'wifi wifi wifi' with one stacked synonym), and store() and load() keep the inflated number. Lookups are correct, and analyzers that produce no token graph give the right count.
