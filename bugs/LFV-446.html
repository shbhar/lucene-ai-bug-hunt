A failed merge-reader refresh leaks the pooled segment reader, so the segment's files stay open after IndexWriter.close

If a merge hits an I/O error while opening a fresh reader for a segment with doc-values updates (or soft deletes), IndexWriter never releases its reference on that segment's pooled reader. In a 2-document repro, 4 files stay open after IndexWriter.close(); every release since 4.6.0 has it.

The finding in 30 seconds

#

A merge takes a reference on a segment's pooled reader, then opens a fresh copy with the latest deletes. If that open throws, the reference is never given back, so Lucene never closes that reader's files.

Background: pooled readers and the merge refresh

#
  1. IndexWriter keeps at most one SegmentReader per segment in a pool (on by default), opened on first use, for example by an NRT reader or a merge. Each user takes a reference (incRef) and gives it back (decRef); a reader closes its files when its count reaches 0.
  2. A doc-values update (soft deletes are one too) writes new files for the segment: a field-infos file of the new generation and doc-values files such as _0_1_Lucene90_0.dvd, which the segment's readers then open.
  3. A merge needs each segment with its latest deletes. If the pooled reader is older than a delete, the merge opens a fresh copy that shares the old reader's core and re-reads the update's field-infos file.

The finding, step by step

#
  1. Index 2 documents, "a" and "b", with a numeric doc-values field, update the field of "a" with updateNumericDocValue, and open and close an NRT reader. The writer now keeps segment _0's reader in its pool.
  2. Delete "b". The pooled reader does not have that delete yet, so a merge of _0 must first open a fresh copy of it; because _0 has a doc-values update, that copy re-reads the update's field-infos file from disk.
  3. Run forceMerge(1) while that file open fails with an IOException. You expect the merge to fail and, once IndexWriter.close() has returned, no index file to be open.
  4. Instead 4 files stay open: the pooled reader's _0.cfs and its three _0_1_Lucene90_0 doc-values files. The merge took a reference on the pooled reader (+1) and gives it back only after the fresh copy opens; when the open throws, nothing gives it back, so the reader's count never reaches 0 and Lucene never closes it.
  5. The same leak happens on a plain commit() with a default config, through merge-on-commit: the commit throws, the writer stays healthy, commits again and closes normally, and 4 files stay open. Search results and deletions stay correct.

Who is affected

#

Applications that use doc-values updates or soft deletes and hit an I/O error (too many open files, a storage or permission error, a throwing Directory) exactly while a merge refreshes such a segment. Each failure leaks one segment reader: its files stay open or mapped after close, and keep their disk space once deleted. Results stay correct.

Mechanism, terms and numbers612 words

When a merge starts, ReadersAndUpdates.getReaderForMerge takes a reference on the segment's pooled SegmentReader. If that reader's live docs are stale, it opens a fresh reader that shares the old one's core and has the latest deletes, and releases the old reader only after that succeeds. For a segment with doc-values updates (soft deletes are doc-values updates too) the fresh reader re-reads the update's field-infos file, so an I/O error can make it throw; then nobody releases the reference. The merge never received the reader, so it cannot release it, and closing the writer drops only the pool's own reference: Lucene never closes that reader's files. In the 2-document repro the segment's compound file and three doc-values files stay open after close; with a default IndexWriterConfig a plain commit() (merge-on-commit) leaks the corresponding 4 files of that segment while the writer keeps working. Results, deletions and later commits stay correct. Introduced in 4.6.0 by LUCENE-5189; every release executed from 4.6.0 to 10.6.0 and main leaks. The fix is one hunk: release the reference when the refresh throws.

Mechanism (Lucene main 645d4fe14a20)

#
// ReadersAndUpdates.getReaderForMerge, condensed
SegmentReader reader = getReader(context);              // :1095  +1 on the pooled reader ("Ref for caller", :195-196)
if (pendingDeletes.needsRefresh(reader) || ...) {       // :1096  pooled live docs are stale
  reader = createNewReaderWithLatestLiveDocs(reader);   // :1100  may throw: nothing releases the +1
}

// ReadersAndUpdates.createNewReaderWithLatestLiveDocs, condensed
SegmentReader newReader = new SegmentReader(info, reader, liveDocs, ...); // :1070-1077  shares the core; does I/O
try {
  pendingDeletes.onNewReader(newReader, info);          // :1079
  reader.decRef();                                      // :1080  the caller's ref is released only here
} catch (Throwable t) {
  newReader.decRef();                                   // :1082  cleans up the NEW reader only
  throw t;
}
  1. Every merge of the writer's own segments gets its readers through getReaderForMerge, from the merge-reader factories in IndexWriter.java:4083-4088 (merge-on-commit and merge-on-refresh) and :5484-5491 (all other merges), via OneMerge.initMergeReaders (MergePolicy.java:465-481); addIndexes(CodecReader...) merges use the caller's readers instead (MergePolicy.java:256).
  2. ReadersAndUpdates.java:1095 takes a reference on the pooled reader. When its live docs are stale (:1096-1097), :1100 calls createNewReaderWithLatestLiveDocs.
  3. The core-sharing SegmentReader constructor (SegmentReader.java:128-162) calls initFieldInfos() and initDocValuesProducer() (:156-157). For a segment with field updates, these read the new generation's field-infos file (:196-203) and set up the doc-values producers of the update generations (:186-187; shared with the pooled reader, opened only if not open yet), so the constructor does I/O and can throw. On failure it closes only what it took (doClose(), :159) and rethrows.
  4. So :1080 never runs and neither method releases the reference from :1095. initMergeReaders keeps only the readers the factory returned (MergePolicy.java:474-479), so the merge's cleanup (IndexWriter.closeMergeReaders, :5394-5425) never sees this one.
  5. When the writer closes (IndexWriter.close(); in the minimal test already the rollback that the tragic failure runs inside forceMerge, IndexWriter.java:2677), ReaderPool.dropAll (ReaderPool.java:314-341) calls ReadersAndUpdates.dropReaders, which releases only the pool's own reference (ReadersAndUpdates.java:213-225). The count stays at 1, so the reader's core (the compound file) and its doc-values producers are never closed.
  6. Without field updates the constructor reuses the core's field infos and the already-open doc-values producer (SegmentReader.java:197-198, :188-190), so plain segments cannot hit this. A second, smaller leak sits on the same path: the two factories take a ReadersAndUpdates reference with getPooledInstance(sci, true) (IndexWriter.java:4085, :5486) and do not release it when getReaderForMerge throws. With fix A alone no file stays open; the only observed effect of this second leak is that the segment's ReadersAndUpdates reference count stays at 1 after close (0 with fix B; read by reflection in a probe of the same test).
Exposure and likelihood389 words
  • Who. Applications that update doc-values fields (updateNumericDocValue, updateBinaryDocValue, updateDocValues) or use soft deletes (once applying them has given the segment a field-update generation, SegmentCommitInfo.hasFieldUpdates), and get an I/O error at the one moment a merge opens the fresh reader of such a segment whose pooled reader has stale live docs. That step only opens and reads files Lucene already wrote, so the errors are those of opening a file: too many open files, a transient storage error, a permission error, or a custom Directory that throws.
  • Default vs opt-in. Doc-values updates and soft deletes are opt-in APIs; the rest is default. Reader pooling is on by default (IndexWriterConfig.DEFAULT_READER_POOLING = true), and merge-on-commit and merge-on-refresh run with a default config (DEFAULT_MAX_FULL_FLUSH_MERGE_WAIT_MILLIS = 500). On those two paths the failure is not tragic and the writer keeps working (merge-on-commit executed on main 645d4fe14a20 with assertions on and off; merge-on-refresh executed on ea57360912ed and 10.5.2). Natural and forced merges reach it too; there the failure is tragic and the writer closes itself, as designed, with the same leak.
  • Scale. None needed: 2 documents. Each failure leaks one reference on the segment's pooled reader. Repeated failures on the same pooled reader leak one more reference each (by code reading), but open no new file or mapping (4 failed attempts in the probe's refresh arms).
  • What stays open (stock main ea57360912ed, real file system; byte counts are the probe's estimates from the sizes of the held files): on MMapDirectory, the 64-bit default, no descriptor is held, but the 4 leaked files, deleted by a later merge, were still mapped after IndexWriter.close(), Directory.close() and five System.gc() calls: 1,069,056 bytes in the refresh arm, 2,138,112 in the force-merge arm. While a deleted file stays mapped, the OS does not free its disk space. The force-merge arm holds twice as much because, by code reading, the per-segment shared arena also keeps later mappings of the same segment's files alive (bounded by its 64 permits). On NIOFSDirectory, 4 descriptors on the deleted files stayed open after IndexWriter.close() and Directory.close() (1,056,459 bytes in the refresh arm, 1,056,460 in the force-merge arm) and were released only after the five System.gc() calls.
  • Not affected. Search results, deletions and later commits: no deleted document became visible in any run.

Why it looks unintended

#
  • IndexWriter.close() "Closes all open resources"; IndexReader.incRef: always pair it with decRef, "otherwise the reader may never be closed".
  • The surrounding code cleans up on failure: the refresh closes the new reader, and the merge keeps partial readers to close them.
  • No tragedy needed: on the default merge-on-commit path the writer stays healthy and closes normally, yet the files stay open.
The full argument311 words
  • Contracts. IndexWriter.close(): "Closes all open resources and releases the write lock." (IndexWriter.java:1342). IndexReader.incRef(): "Be sure to always call a corresponding decRef, in a finally clause; otherwise the reader may never be closed." (IndexReader.java:166-168).
  • The surrounding code is exception-safe. createNewReaderWithLatestLiveDocs releases the new reader when onNewReader fails (ReadersAndUpdates.java:1081-1083); initMergeReaders keeps partly acquired readers "to close them in the case of an exception" (MergePolicy.java:476-479); the constructor closes what it opened (SegmentReader.java:158-160). Only the caller's reference on the old reader is missed.
  • Readers may outlive the writer only when the application holds them. ReaderPool.dropAll: "it is allowed that these decRefs do not actually close the SRs; this happens when a near real-time reader is kept open after the IndexWriter instance is closed" (ReaderPool.java:327-330). The repro closes its NRT reader first.
  • Upstream precedent: tests close a MockDirectoryWrapper after injected failures. TestIndexWriterOutOfFileDescriptors injects IOExceptions on file opens, lets merges fail (tragically, when they hit the merge scheduler), rolls the writer back and closes a MockDirectoryWrapper, which fails on any open file; it uses no doc-values updates and does not target this path, so it is precedent, not a test of it. TestIndexWriterOnError uses doc-values updates, but its failures throw an Error with a 1-in-3000 draw at each failure check while IndexWriter is on the stack. CrankyCodec never fails the reads this step does (its field-infos, doc-values and compound-file readers delegate without injecting).
  • History. The same class of leak was fixed as a bug before: LUCENE-5656 "Fix rare fd leak in SegmentReader when multiple docvalues fields have been updated with IndexWriter.updateXXXDocValue and one hits exception" and LUCENE-5262 "Fixed file handle leaks when multiple attempts to open an NRT reader hit exceptions". In the history and prior-art material reviewed, no commit, comment, test, CHANGES or MIGRATE entry accepts this one.
The devil's-advocate check140 words

Strongest case: the minimal test is a tragic merge failure, and the IndexWriter javadoc says that after an Error or a disaster it closes itself "in case any internal state (buffered documents, deletions, reference counts) were corrupted" (IndexWriter.java:162-165); on #12228 a maintainer said that on a tragedy it is unsafe to delete files.

Why it fails: (1) the leak needs no tragedy: on the default merge-on-commit path getTragicException() is null, the writer commits again and closes normally, and the corresponding 4 files of that segment stay open (executed on 645d4fe14a20); (2) the javadoc note is about an Error or a checkpoint disaster and does not say files may stay open, and TestIndexWriterOutOfFileDescriptors expects every file closed after tragic merge failures from IOExceptions; (3) #12228 is about deleting files, while the fix only releases a reference.

Suggested fix

#

Recommended A. Release the pooled reader in getReaderForMerge when the refresh throws

In getReaderForMerge, release the pooled reader when createNewReaderWithLatestLiveDocs throws (+8/-1, one hunk). The repro passes with assertions on and off, and the whole core module passes (8,898 tests, 0 failures). Option B also releases a second, smaller reference in IndexWriter's two merge-reader factories.

  • The decRef cannot close the reader: the pool still holds its own reference, and the method holds the ReadersAndUpdates lock.
  • The same hunk applies, with line offsets, to the 10.6.0 and 9.12.3 sources (checked with git apply --check, and again by the fact check with patch --dry-run: offsets +62 and -309; not built there).

Downstream note

#

Engines that always use soft deletes and merge on flush make the segment state common, but the trigger is still an I/O error at this one step (read only, nothing executed downstream).

How it was found

#

Fault injection at every I/O point: each index-level IndexWriter operation was run while an IOException was thrown at each distinct file operation, then the test checked that no file stayed open. 68 runs left files open; reading the code found the missing release, and a JUnit test confirmed it.

The method in full130 words

Method: bounded-exhaustive exception-point enumeration on the real jar (the study's semi-formal tier). Each index-level operation was run against an executable reference of its documented outcome while an IOException was injected at every distinct I/O throw point, one-shot and sticky, followed by a check that the MockDirectoryWrapper closes with no open file.

  • 68 runs failed that last check ("cannot close: there are still N open files") after a correctly classified outcome; the first was in a soft-deletes configuration with pooled readers, failing in SegmentReader.initFieldInfos under createNewReaderWithLatestLiveDocs and getReaderForMerge.
  • The root cause was then located by reading the code and confirmed with a shadow fix.
  • A second, independent fault-injection run (random model-based testing, a merge started from updateDocuments with SerialMergeScheduler) found the same root cause through a second trigger path.

History

#

Introduced in 4.6.0 by LUCENE-5189 (doc-values updates, 2013), which made the fresh reader's constructor read files; the take-then-release order was older but harmless. 4.5.1 passes; every release run from 4.6.0 to 10.6.0 and main leaks.

Versions tested9 rows

Introduced by LUCENE-5189 "Numeric DocValues Updates" (apache/lucene#6253; SVN-era patches, no PR; issue author shaie): trunk 1120e46961b2 (2013-09-15) and the branch_4x backport 49684b82701b (2013-11-01), first released in 4.6.0. It turned the core-sharing SegmentReader constructor from one that did no I/O into one that reads the field-infos generation file and opens the doc-values update producers; the caller already took the pooled reference before it and released it only after it returned.

The code moved into ReadersAndUpdates.getReaderForMerge in 7.0.0 (LUCENE-7868, 58105a203a1) and into createNewReaderWithLatestLiveDocs in 7.4.0 (LUCENE-8246: the branch_7x commit e0dcd66ac72, a backport of the main-branch commit e99a19755c7, which first shipped in 8.0.0), keeping the order both times. In 4.6.0-4.10.4 a failed forced merge was not tragic; by 5.5.5 it is. 8.6.0 added the non-tragic merge-on-commit path and 8.7.0 merge-on-refresh through the same code (read). A tag scan finds the same order in every release tag from 4.6.0 to 10.5.2 in the history clone, which lacks the 8.8.2-8.11.4 tags (8.10.1 and 8.11.4 were run from release jars); 10.6.0 was read and run separately.

LFV-446, snapshot of 2026-11-03

Registry title
When a merge fails to open the refreshed reader of a segment with doc-values updates, IndexWriter never releases its reference on the pooled segment reader, so the segment's files stay open after IndexWriter.close
Area
index / IndexWriter merge-reader acquisition (ReadersAndUpdates.getReaderForMerge)
Priority
Low, rank 975: A failed merge-reader refresh leaks one pooled segment reader and its files, a bounded leak that needs an I/O error at one exact step.
Impact class
minor
Impact note
Hits applications that update doc-values fields (updateNumericDocValue, updateBinaryDocValue) or use soft deletes, open NRT readers from the writer (which pools segment readers), and then get an I/O error (too many open files, a transient storage, permission or quota error, a read-only remount, or a throwing custom Directory) at the one moment a merge opens the refreshed reader of such a segment whose pooled reader has stale live docs; a default IndexWriterConfig reaches it through merge-on-commit and merge-on-refresh, where the failure is not tragic and the writer keeps working, and any natural or forced merge reaches it too, where the failure is tragic and the writer closes itself as designed; each failure leaves one pooled segment reader unreleased, so the segment's compound file and doc-values update files are never closed by Lucene: on MMapDirectory (the 64-bit default) they stayed mapped after IndexWriter.close, Directory.close and System.gc() and kept their disk space after a later merge deleted them, and on NIOFSDirectory they held file descriptors until garbage collection; results, deletions and later commits stay correct, no scale is needed, and every release from 4.6.0 to 10.6.0 and main is affected.
Summary
You update a doc-values field (or use soft deletes) and open NRT readers from your IndexWriter, then delete a document, and a merge (a merge-on-commit, a merge-on-refresh, or an ordinary or forced merge) has to open a fresh copy of that segment's pooled reader with the new deletions, and opening it fails with an IOException. You expect the merge to fail cleanly and IndexWriter to give back every reader reference it took, so that once the writer is closed no file of the index is still open. Instead ReadersAndUpdates.getReaderForMerge never releases the reference it took on the pooled reader, so that segment's compound file and doc-values update files stay open after IndexWriter.close, even when the failure was not tragic and the writer went on to commit and close normally.
