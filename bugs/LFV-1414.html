The per-field merge view of FieldInfos throws NullPointerException from fieldInfo(int) for a field number the segment lacks

At a merge, a per-field postings or doc-values delegate gets a FieldInfos view per segment; asking it for a field number that segment lacks throws NullPointerException instead of the documented null. Only custom delegates that look fields up by number are hit, in every release since 6.3.0.

The finding in 30 seconds

#

FilterFieldInfos keeps every field of the segment in its base FieldInfos (to keep field numbers) and checks each lookup against the delegate's field set. fieldInfo(String) checks the name first and returns the base's null for a missing field; fieldInfo(int) reads res.name on the base's result first, so a missing number throws.

Background in three steps

#
  1. A codec can pick a postings or doc-values format per field: PerFieldPostingsFormat and PerFieldDocValuesFormat route each field to the format that the codec's getPostingsFormatForField / getDocValuesFormatForField returns.
  2. Within one IndexWriter, field numbers are handed out in order: the first field gets 0, the next 1. A segment's FieldInfos lists only the fields it has, so asking it for another number is normal and returns null.
  3. At a merge, each per-field delegate gets a MergeState whose FieldInfos, for the merged segment and for every source segment, is a view (PerFieldMergeState.FilterFieldInfos) that admits only the delegate's fields.

The finding, step by step

#
  1. A custom postings format wraps the default one and is installed for every field through the codec's per-field hook. Index document 1 with field a and commit, then document 2 with a and b and commit: two segments, and b is field number 1.
  2. Run forceMerge(1). The merge hands your format one FieldInfos view per source segment, restricted to its fields. For segment 1, fieldInfo("b") correctly returns null.
  3. Your merge then asks segment 1's view for field number 1. You expect null: FieldInfos#fieldInfo(int) documents "null when the given fieldNumber doesn't exist", and segment 1 only knows field 0.
  4. You get NullPointerException: Cannot read field "name" because "res" is null out of forceMerge(1), with assertions on and off: the view reads the name of the missing entry to check it against its field set.

Who is affected

#

Only a custom PostingsFormat or DocValuesFormat that runs as a per-field delegate and calls fieldInfo(int) on its merge view for a number some segment lacks: its merge fails on the first such merge, from two documents up. Lucene's own formats look fields up by name, so stock codecs are not affected.

Mechanism, terms and numbers364 words

At merge time, PerFieldPostingsFormat and PerFieldDocValuesFormat give each delegate format a MergeState whose FieldInfos (mergeFieldInfos and every per-segment fieldInfos[i]) is a PerFieldMergeState.FilterFieldInfos view restricted to that delegate's fields. FieldInfos#fieldInfo(int) is documented to return null when the number does not exist, which is the normal case for a source segment that lacks one of the merged fields, for example a segment committed before any document had that field.

The view's override reads res.name on that null and throws NullPointerException: Cannot read field "name" because "res" is null, so the delegate's merge fails, while the same view's fieldInfo(String) returns null for the same field. Lucene's own formats look fields up by name on this view, so stock codecs are unaffected; only a custom per-field delegate that looks fields up by number is hit, from two documents up, in every release from 6.3.0 through 10.6.0 and on main. The fix is a null check before the field-set check.

The mechanism (main f794ff5a505c)

#
  1. The only callers of PerFieldMergeState.restrictFields are PerFieldPostingsFormat.java:191 and PerFieldDocValuesFormat.java:151; each passes the restricted MergeState to a delegate's merge.
  2. restrictFields (codecs/perfield/PerFieldMergeState.java:44-75) wraps every source segment's fieldInfos[i] (:45-48) and mergeFieldInfos (:56) in a FilterFieldInfos restricted to the delegate's field names.
  3. The view's constructor passes every field of the segment to the base class (:95; comment at :94: "the field numbering must be kept consistent"), so number lookups go to the base FieldInfos, which returns null for a number past the end or in a gap (index/FieldInfos.java:345).
  4. Fix site. The override (PerFieldMergeState.java:214-228) does FieldInfo res = super.fieldInfo(fieldNumber); (:216) and then if (!filteredNames.contains(res.name)) (:217) with no null check.
  5. The sibling fieldInfo(String) (:200-212) checks the name against the delegate's set first and then returns the base result, null for an in-set field the segment lacks. Stock merge code uses exactly that lookup on this view, for example mergeState.fieldInfos[i].fieldInfo(mergeFieldInfo.name) (codecs/DocValuesConsumer.java:212).

In the repro, a is field 0 and b field 1 (index/FieldInfos.java:378, :430-433); segment 1 holds only field 0, so the base returns null for 1 and the view throws.

Exposure and likelihood173 words
  • Who is hit: a custom PostingsFormat or DocValuesFormat (public, @lucene.experimental extension points) that runs as a per-field delegate, for example through Lucene104Codec.getPostingsFormatForField / getDocValuesFormatForField (Lucene104Codec.java:179, :192), and whose merge calls fieldInfo(int) on mergeState.fieldInfos[i] or mergeState.mergeFieldInfos for a number that FieldInfos lacks. That happens on the first merge of any segment that is missing one of the merged fields.
  • Not hit: Lucene's own formats. The in-tree merge code that receives this view looks source fields up by name (DocValuesConsumer.java:212 and six more sites), and the default FieldsConsumer.merge makes no FieldInfos lookup; the in-tree number lookups on merge state (StoredFieldsWriter.java:187, compressing/MatchingReaders.java:56) get the unrestricted MergeState. The recorded downstream code search (Elasticsearch and OpenSearch merge code) found no format that makes the call.
  • Effect: the delegate's merge throws, so the merge fails: a loud failure, not silent wrong data. (If a format catches the exception, what happens next is up to that format.)
  • How likely: rare; the recorded searches (see Prior reports) found no report since 6.3.0 (2016).

Why it looks unintended

#
  • FieldInfos#fieldInfo(int) documents "null when the given fieldNumber doesn't exist" and throws only for a negative number.
  • The same view's fieldInfo(String) returns null for the same field in the same segment; its comment names IllegalArgumentException, not NullPointerException, as the answer to invalid numbers.
  • Lucene's own merge idiom, fieldInfo(fi.number) then other == null || ..., relies on that null.
The full argument233 words
  • Contract. FieldInfos#fieldInfo(int): "@return the FieldInfo object or null when the given fieldNumber doesn't exist. @throws IllegalArgumentException if fieldNumber is negative" (index/FieldInfos.java:334-340). The view is handed to codec code typed as FieldInfos.
  • The view disagrees with itself. For the same segment and field, fieldInfo("b") returns null and fieldInfo(1) throws; the repro uses the first to pick the segment.
  • Designed rejection is IllegalArgumentException. The comment at PerFieldMergeState.java:203 says "Throw IAE to be consistent with fieldInfo(int) which throws it as well on invalid numbers"; the base class throws that only for a negative number (index/FieldInfos.java:342-343).
  • Tests and idiom. TestFieldInfos asserts null for missing numbers (TestFieldInfos.java:80, :88); no upstream test calls fieldInfo(int) on the merge view. Lucene's own merge-time idiom fieldInfo(fi.number) followed by other == null || !other.name.equals(fi.name) (StoredFieldsWriter.java:187-188, compressing/MatchingReaders.java:56-57) treats null as the normal answer for an absent number. Those sites look a source field's number up in mergeFieldInfos (the other direction from the repro) and get the unrestricted MergeState; on the view, the same idiom would throw before reaching its null check whenever the number is absent (PerFieldMergeState.java:216-217).
  • History. The view and this override came with LUCENE-7456 (#8508, 2016). Its discussion is about rejecting fields outside the restricted set; a number missing from the wrapped FieldInfos is not discussed, and the unchecked res.name was in the patch from the start.
The devil's-advocate check186 words

The strongest case for "intended": the view deliberately is not a full FieldInfos (an existing number of a field outside the delegate's set throws IllegalArgumentException where the base returns it); the class is private and MergeState and FieldInfos are @lucene.experimental; looking a merged field's number up in a source segment is fragile, because after addIndexes(Directory) a copied segment keeps its own numbers, so a number can name a different field there (shown by an executed probe); and no Lucene code makes the call.

Why it fails: the deliberate deviation covers only fields outside the set, and b is in the set; the inherited FieldInfos javadoc documents only a non-negative number as a precondition, and the view's class and overrides carry no javadoc of their own; Lucene's own idiom does a number lookup plus a null and name check (in the other direction); "experimental" waives back-compatibility, not documented return values; and "nothing in Lucene calls it" is why this is Low, not why it is intended. The report is the contract violation (an exception where null is documented), not advice to look numbers up across segments.

Suggested fix

#

Recommended A: return null for a number the wrapped FieldInfos does not have (recommended)

Return null when the wrapped FieldInfos has no field with that number, before the field-set check (+4 lines in PerFieldMergeState.java). Validated: the repro passes with assertions on and off, and the per-field, TestFieldInfos and TestSegmentMerger suites (196 tests) and the core format and lint checks pass.

@Override
public FieldInfo fieldInfo(int fieldNumber) {
  FieldInfo res = super.fieldInfo(fieldNumber);
  if (res == null) {
    // same as FieldInfos#fieldInfo(int): null when the number does not exist
    return null;
  }
  if (!filteredNames.contains(res.name)) {
    throw new IllegalArgumentException(...); // unchanged
  }
  return res;
}

A: return null for a number the wrapped FieldInfos does not have (recommended) (validated by the checks)

#

In FilterFieldInfos.fieldInfo(int), return the base's null before checking the name against the delegate's field set. The IllegalArgumentException for an existing number of a field outside the set stays.

@Override
public FieldInfo fieldInfo(int fieldNumber) {
  FieldInfo res = super.fieldInfo(fieldNumber);
  if (res == null) {
    // same as FieldInfos#fieldInfo(int): null when the number does not exist
    return null;
  }
  if (!filteredNames.contains(res.name)) {
    throw new IllegalArgumentException(...); // unchanged
  }
  return res;
}

Trade-offs

None for Lucene's own code (nothing calls it on this view). It matches the base contract and the view's own fieldInfo(String). It does not make a merged field's number a safe key into a source segment: after addIndexes(Directory) a number can name another field there (executed probe), so a caller still checks the name.

How it was found

#

Semi-formal: a proof-obligation audit of FilterFieldInfos, checking that each override keeps the contract of the FieldInfos method it replaces. fieldInfo(int) breaks the documented null result for a number the segment lacks; a one-test JUnit repro on stock main witnessed it.

The method in full94 words
  • Obligation: every override of the restricted view must keep the documented result of the FieldInfos method it replaces, apart from the deliberate rejection of fields outside the delegate's set; for fieldInfo(int) that is "the FieldInfo object or null when the given fieldNumber doesn't exist" (FieldInfos.java:334-340).
  • Finding: fieldInfo(int) dereferences the base result before any null check (PerFieldMergeState.java:216-217), while fieldInfo(String) keeps the null (:200-212).
  • Witness: a JUnit test on stock main, then an independent reproduction, cross-model review lenses, an intended-behaviour review, an adjudication and a minimal-repro check (see Independent checks).
