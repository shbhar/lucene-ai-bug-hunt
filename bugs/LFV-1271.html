LRUQueryCache.setSkipCacheFactor accepts NaN, 0 and values below 1 that the constructor rejects

LRUQueryCache rejects a skip-cache factor below 1 or NaN in its constructor, but the runtime setter added in 10.2.0, setSkipCacheFactor, stores any float without an error. A NaN turns the cache's skip rule off and a 0 stops the caching of every clause that matches documents; search hits never change.

The finding in 30 seconds

#

LRUQueryCache does not cache a clause that costs far more than the query it sits in: it skips when cost / skipCacheFactor > leadCost. The constructor only accepts a factor of at least 1 (the two-argument constructor uses 10).

  1. You create new LRUQueryCache(10, 1 << 20, _ -> true, 10f) and later change the skip-cache factor at runtime from a setting: cache.setSkipCacheFactor(Float.NaN) after a failed parse, or 0 meant as "off".
  2. You expect IllegalArgumentException: skipCacheFactor must be no less than 1, get NaN. The constructor throws exactly that for the same value.
  3. Instead the setter just stores it: no error with assertions on or off, and getSkipCacheFactor() returns NaN.
  4. The cache skips caching a clause when cost / factor > leadCost. On 10,000 docs, +g:rare #f:all (10 hits): factor 10 skips caching f:all (10,000 / 10 = 1,000 > 10). With NaN the cache builds f:all's 10,000-doc set (NaN > 10 is false). 0 caches nothing here, not even #f:all alone (10,000 / 0 = Infinity).
  5. Hits stay 10 and 10,000 in every case: only caching performance changes, silently.

Who is affected

#

Only applications that change the factor at runtime through this expert setter (10.2.0 and later, @lucene.experimental class) and pass NaN, 0 or a value below 1, for example from a failed parse. The default configuration and the constructors are not affected, Lucene never calls the setter itself, and hits never change: only which clauses get cached.

Mechanism, terms and numbers560 words

LRUQueryCache skips caching a clause whose cost is much higher than the cost of the query it is part of: it serves the clause uncached when cost / skipCacheFactor > leadCost (LRUQueryCache.java:850). The constructor keeps the factor at 1 or more and rejects NaN on purpose (if (skipCacheFactor >= 1 == false) { // NaN >= 1 evaluates false, :178-181). setSkipCacheFactor(float), added in 10.2.0 by #14412 to change the factor at runtime, only assigns the field (:239-241), so NaN, 0, negative values and values in (0, 1) are stored silently. NaN or a negative factor turns the skip rule off, 0 stops the caching of every clause that matches documents, and a value in (0, 1) can skip clauses that every legal factor caches. Search hits never change. Every release from 10.2.0 through 10.6.0 and main are affected; the fix is the constructor's check in the setter.

The code (main 5adff78bb168)

#
  • The field. private volatile float skipCacheFactor; (LRUQueryCache.java:123) in a class marked @lucene.experimental (:117).
  • The constructor's check. Both public constructors that take a factor reach the six-argument one (:145-151 delegates), which throws IllegalArgumentException("skipCacheFactor must be no less than 1, get " + skipCacheFactor) when skipCacheFactor >= 1 == false, with the comment // NaN >= 1 evaluates false (:178-181).
  • The setter. setSkipCacheFactor(float) (:233-241): javadoc "This setter enables the skipCacheFactor to be updated dynamically.", a @param that repeats the constructor's description, and the body this.skipCacheFactor = skipCacheFactor;. No check and no @throws.
  • Where the cache uses it. Besides the getter (:229-231), only the caching wrapper's iterator reads the field: if (cost / skipCacheFactor > leadCost) { return supplier.get(leadCost).iterator(); } (:850), i.e. use the clause uncached. It runs on a cache miss, after the segment, cache-helper and caching-policy checks, for a clause whose scorer supplier is not null; a clause with no match in the segment gets an empty cache entry before the test (:838-842).

Executed on main with assertions off: 10,000 documents, f:all on every document, g:rare on 10, a policy that caches every query; +g:rare #f:all, then #f:all alone. Factor 10 and 1: f:all is not cached inside the conjunction, then cached as the top-level query. NaN and -1: f:all is cached already inside the conjunction. 0: nothing is cached at either step. Hits are 10 and 10,000 every time. A second probe confirmed the equivalences in the table, including that NaN and -1 cache exactly what +Infinity and Float.MAX_VALUE cache.

Exposure and likelihood206 words
  • Who is exposed. Callers of setSkipCacheFactor; git grep 'SkipCacheFactor(' finds no caller in Lucene outside tests, and the one in-tree test (TestLRUQueryCache.testSkipCacheFactorWithDynamicValues) uses 1.0 and 3.0.
  • Default vs opt-in. Opt-in only. Caches built through the constructors, including the two-argument one with factor 10, are checked. The cache need not be one the application built: on main caching is off by default (IndexSearcher.java:81-83), but on 10.x IndexSearcher's default cache is an LRUQueryCache with factor 10 (10.6.0 IndexSearcher.java:99), which an application can get through getDefaultQueryCache(), cast and tune with the setter.
  • What goes wrong. A mistake is applied silently instead of failing: NaN or a negative value makes the cache build the full cached doc-id set of expensive clauses under a selective lead (what the legal +Infinity also does); 0 stops the caching of every clause that matches documents; (0, 1) can skip clauses that every legal factor caches.
  • What does not. Search hits, scores and memory bounds: maxSize and maxRamBytesUsed still apply.
  • Scale. The factor is one field per cache (:123), read at each cache-miss admission decision (:850), so one bad value drives every later such decision of that cache until it is set again.

Why it looks unintended

#
  • The constructor rejects these values on purpose: if (skipCacheFactor >= 1 == false) { // NaN >= 1 evaluates false (since 2019).
  • When the PR adding the setter (#14412) loosened that check, the reviewer asked: "Please revert so that we keep rejecting skipCacheFactor=Float.NaN?"
  • The setter's javadoc gives the parameter the same meaning; nothing says it may skip the check.
The full argument178 words
  • A deliberate domain. The >= 1 == false check came with the skip rule itself in LUCENE-9002 (5c536506f99, 2019; #10045, apache/lucene-solr#940). Its comment first read "NaN >= 1 evaluates true"; Adrien Grand (jpountz) corrected it to "evaluates false" two minutes later (c2a0b8275be, "LUCENE-9002: Fix comment.", 2019-11-11). So the reviewer of #14412 is the maintainer who wrote down the NaN case in 2019.
  • Defended in the PR that added the setter. In #14412 the contributor first changed the check to if (skipCacheFactor < 1), which lets NaN through. Adrien Grand (jpountz) asked on 2025-03-28 "Please revert so that we keep rejecting skipCacheFactor=Float.NaN?", and it was reverted. On the setter they asked for javadocs, and on 2025-03-29 for the constructor's description of the factor to be copied into them.
  • Same parameter, same meaning. The setter's @param repeats the constructor's text word for word.
  • No decision the other way. No javadoc, test, CHANGES or MIGRATE entry or review comment says the setter may bypass the check; the only in-tree test of the setter uses legal values.
The devil's-advocate check207 words

The strongest case for "intended": the setter's javadoc names no range and no @throws; the class is @lucene.experimental and the setter an expert knob that the maintainer was reluctant to add ("In general I'm not a fan of exposing tuning knobs just because we can expose them", #14183, 2025-02-01); the reviewer saw the bare setter and asked only for javadocs; and every bad value behaves like some legal setting (NaN or negative like the factor +Infinity, 0 like a never-cache policy for every clause that matches documents), except (0, 1), which can skip clauses that every legal factor caches.

Why it fails: it limits the impact (hence Low), but it shows no intent. The same reviewer, in the same PR, insisted on rejecting NaN for the same field; asking for javadocs on a two-line setter is not a decision that the setter may skip that check. TieredMergePolicy, which the reviewer named as the model for a getter/setter in that PR, checks ranges in its setters (for example setMaxMergedSegmentMB, TieredMergePolicy.java:102-105); that is a range check only (v < 0.0 lets NaN through), so it supports "setters check their range", not a project-wide rule about NaN. Verdict: an omission, not a design decision.

Suggested fix

#

Recommended Apply the constructor's check in the setter

Repeat the constructor's check in the setter: if skipCacheFactor >= 1 == false, throw new IllegalArgumentException("skipCacheFactor must be no less than 1, get " + skipCacheFactor), and add an @throws line. Validated with gradle: the repro passes with assertions on and off, TestLRUQueryCache passes and :lucene:core:check -x test passes.

Apply the constructor's check in the setter (validated by the checks) (recommended)

Add the constructor's >= 1 == false check (NaN-safe) to setSkipCacheFactor and document it with @throws.

Trade-offs

The smallest change, with the constructor's exact message and NaN handling; the check then exists twice. A caller that passes a value below 1 gets an exception instead of a silent change, which is the point. It changes runtime behaviour for such callers, so whether it needs a CHANGES or MIGRATE entry is the maintainers' call.
