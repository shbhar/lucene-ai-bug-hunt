UnifiedHighlighter can fail its own assert when a span clause and another clause match the same word (assertions on only)

With assertions on, the default UnifiedHighlighter throws AssertionError for body:qu* OR spanTerm(body:quick) on the text the quick brown fox; with assertions off it returns the <b>quick</b> brown fox. Both clauses match quick, and an internal assert expects a queue order that the queue's own tie-break does not give.

The finding in 30 seconds

#

The highlighter asks the query for its matches. A span match carries sub-matches, which go into a queue as cached entries; the matches iterator is then moved on and put back. An assert says the iterator must sit behind the cached entries. A second clause that matches the same word can put it in front.

Background: three pieces

#
  1. Since 9.0.0 the UnifiedHighlighter by default takes its offsets from the query itself (Weight#matches, the flag WEIGHT_MATCHES). A match is a start and an end offset plus the clause that produced it. Two clauses that match the same word give two matches with the same offsets.
  2. A span match has sub-matches, one per term. The highlighter wants the terms, so it puts each sub-match into a queue as a cached entry, moves the matches iterator to its next match and puts the iterator back into the same queue.
  3. The queue is sorted by start offset, end offset and then a label. The label is the clause's terms, or the clause's toString() when it reports no terms: quick for the span's term, body:qu* for a prefix clause.

The finding, step by step

#
  1. Build an OR query with two clauses on the field body: PrefixQuery(qu) first, then SpanTermQuery(quick). Highlight the text the quick brown fox with a default UnifiedHighlighter, in a JVM that runs with assertions on (-ea), as test suites do.
  2. You expect the <b>quick</b> brown fox. The same two clauses in the other order return it, and so does a JVM without assertions.
  3. Instead the call throws java.lang.AssertionError at OffsetsEnum.java:216. Both clauses match the word quick at characters 4 to 9, and the highlighter keeps the two matches in a small queue.
  4. The queue sorts by start, end, then a label. The span match leaves a cached entry labelled quick; the prefix match follows with the label body:qu*. Start 4 = 4, end 9 = 9, and b sorts before q, so the prefix match goes to the front. The assert requires it behind the cached entry.
  5. Every release from 9.0.0 to 10.6.0, the 11.0 branch and main fail this way with assertions on (7.5.0 to 8.11.4 only with an opt-in flag). No index, hit or score is affected.

Who is affected

#

Only JVMs with assertions on: Lucene's own tests and the test suites of applications built on it. There, a default highlight call can throw when a span or interval clause follows a prefix, wildcard, terms or range clause of the same field and both match one word; the field name decides. Without assertions it returns the expected snippet. Rare.

Mechanism, terms and numbers801 words

Scope first. The failure needs a JVM that runs with assertions enabled (-ea), as test suites do. With assertions off the same call returns the expected snippet, and no index, hit set or score is wrong.

With its default flags the UnifiedHighlighter takes match offsets from Weight#matches (HighlightFlag.WEIGHT_MATCHES, a default flag since 9.0.0) and wraps the field's MatchesIterator in OffsetsEnum.OfMatchesIteratorWithSubs (FieldOffsetStrategy.java:157 on main 781025d6fe32). When the current match has sub-matches, as every span match has, nextWhenMatchesIterator (OffsetsEnum.java:203-224) caches them in a queue, moves the iterator to its next match, puts the iterator back and asserts pendingQueue.peek() != miOE; // miOE should follow cached entries (:216).

The queue is ordered by OffsetsEnum.compareTo (:49-74): start offset, end offset, then the match label. When another clause of the query matches the same token, the next match ties a cached entry on both offsets and the label decides. A PrefixQuery reports no terms, so its label is its toString(), body:qu* (:246-275), which sorts before the cached label quick. The re-queued iterator is then the head of the queue and the assert is false. For body:qu* OR spanTerm(body:quick) on the quick brown fox the highlight call throws AssertionError with assertions on and returns the <b>quick</b> brown fox with assertions off; the same two clauses in the other order pass in both modes.

The assert is unchanged since the class was added (LUCENE-8286, b19ae942f15, 2018; 7.5.0 behind an opt-in flag). LUCENE-9431 made the flag a default in 9.0.0, so every release from 9.0.0 to 10.6.0, the 11.0 branch and main reach it with a default highlighter. Two fixes were validated: processing the re-queued iterator at once when it lands at the head, and deleting the assert.

The pieces

#
  • The mode. DEFAULT_ENABLE_WEIGHT_MATCHES = true (UnifiedHighlighter.java:111); the flag is applied when the three other default flags are on (:409-419). FieldOffsetStrategy.createOffsetsEnumsWeightMatcher (FieldOffsetStrategy.java:114-160) rewrites the query, calls Weight#matches and wraps the field's MatchesIterator in OffsetsEnum.OfMatchesIteratorWithSubs (:157). highlightWithoutSearcher takes the same path: with this flag the text is analysed into an in-memory index (MemoryIndexOffsetStrategy, UnifiedHighlighter.java:1164-1175) and Weight#matches runs on that (FieldOffsetStrategy.java:62-74).
  • Two matches of one token. A BooleanQuery collects its clauses' matches in clause order and combines them in a DisjunctionMatchesIterator (BooleanWeight.java:134-164, MatchesUtils.java:63-86). Its javadoc: "Matches may overlap, or be duplicated if they appear in more than one of the sub-iterators." (DisjunctionMatchesIterator.java:36-38). Its queue compares positions with <= (:194-207); for the repro the second clause's match comes out first: [4-9 body:quick, has sub-matches] [4-9 body:qu*, no sub-matches]. With the clauses swapped the prefix match comes first. That the second clause wins this tie is how the queue works today; no javadoc promises an order for two matches with equal positions.
  • Sub-matches. A span match reports its terms as sub-matches, one per term, each with the query TermQuery(term) (SpanWeight.java:279-323 at 781025d6fe32).
  • The queue. OfMatchesIteratorWithSubs holds a PriorityQueue<OffsetsEnum> (OffsetsEnum.java:174) with two kinds of entries: the matches iterator itself (OfMatchesIterator) and one-use cached sub-matches (CachedOE). Its order is OffsetsEnum.compareTo (:49-74): start offset, end offset, then the label (:59-70).
  • The label. queryToTerm (:246-275) joins the terms the query reports to a QueryVisitor; if it reports none, the label is Query.toString() (:272-273).

The step that fails

#

nextWhenMatchesIterator (OffsetsEnum.java:203-224), for the repro:

  1. nextPosition() takes the iterator out of the queue and advances it to the span match (:184, :194-198).
  2. The span match has sub-matches: enqueueCachedMatches adds the cached entry (4-9, quick) (:212, :226-240).
  3. miOE.nextPosition() moves the iterator to its next match, the prefix clause's match of the same token (4-9, body:qu*), and pendingQueue.add(miOE) puts it back (:214-215).
  4. compareTo: 4 = 4, 9 = 9, then body:qu* < quick (b is 0x62, q is 0x71). The iterator is the head.
  5. assert pendingQueue.peek() != miOE; // miOE should follow cached entries (:216) is false.

Controls

#
  • The other clause order passes. The prefix match then comes first; it has no sub-matches and stays queued (:219-222). The span match comes second and is the iterator's last match, so nothing is put back (:214).
  • The label decides. The same query on a field named text passes with assertions on: text:qu* sorts after quick.
  • Without assertions. The iterator stays at the head, FieldHighlighter reads it as it is (4-9, body:qu*), the next nextPosition() advances it and the cached entry (4-9, quick) follows. Both clause orders give the passage 4-9:body:qu*, 4-9:quick with score 2.7471035.
  • A TermQuery in place of the span clause and withWeightMatches(false) do not throw.

Why it looks unintended

#
  • No javadoc lets a highlight call throw for this query: highlightWithoutSearcher documents only IOException.
  • Two clauses matching one word is documented input: a disjunction's matches may "be duplicated if they appear in more than one of the sub-iterators".
  • The assert contradicts the queue's own order, which breaks ties by label. Lucene has fixed false assertions as bugs before (LUCENE-9976, LUCENE-2645).
The full argument387 words
  • No javadoc allows the throw. highlightWithoutSearcher documents "@throws IOException if an I/O error occurred during processing" and nothing else (UnifiedHighlighter.java:951-969). The highlight and highlightFields methods add only an IllegalArgumentException for a field that was indexed without offsets (:616-618). Neither covers this query. Builder#withWeightMatches describes the mode ("It's more accurate to the query ... True by default") with no restriction on the query (:233-245).
  • The tie is documented input. DisjunctionMatchesIterator: "Matches may overlap, or be duplicated if they appear in more than one of the sub-iterators." (DisjunctionMatchesIterator.java:36-38). MatchesIterator: "Matches are ordered by start position, and then by end position. Match intervals may overlap." (MatchesIterator.java:33). Nothing orders two matches with equal positions.
  • The assert contradicts the class's own order. The queue breaks a tie on both offsets by label (OffsetsEnum.java:59-70); the comment "miOE should follow cached entries" assumes the opposite. For this input the two cannot both hold, and no caller breaks a documented precondition. Which side to change is the maintainers' call: the assert, the queue's tie-break, or the order in which the disjunction hands out two tied matches.
  • Tests. Lucene's TestUnifiedHighlighterStrictPhrases.testRewriteAndMtq highlights a SpanNearQuery, a PrefixQuery and a PhraseQuery of one field in this mode and has a WEIGHT_MATCHES expectation (TestUnifiedHighlighterStrictPhrases.java:285-318). There the span match and the prefix match are on different words, so the test does not reach the assert. No test of the module does: its 730 tests pass with assertions on.
  • Lucene fixes false assertions as bugs. CHANGES.txt: "LUCENE-9976: Fix WANDScorer assertion error." (:5538); "LUCENE-2645: Fix false assertion error when same token was added one after another with 0 posIncr." (:16499-16501).
  • History. The class, the method and the assert came in one commit (b19ae942f15, LUCENE-8286, 2018). The method and the assert are unchanged since. Elsewhere in the class only queryToTerm, which computes the label, changed (LUCENE-3041, 2019: a QueryVisitor instead of Weight.extractTerms) and one pattern variable in nextPosition (#15842, 2026), besides the reformatting of 2020 (LUCENE-9570). Neither the issue (#9333) nor its pull request discusses a tie. Jim Ferenczi wrote there on 2018-05-02 that "the matches iterator can return duplicates (if the same term is present in multiple clauses)": duplicates were known input when the class was designed.
The devil's-advocate check156 words

The strongest case for "not a bug": it is only an assertion. UnifiedHighlighter is tagged @lucene.experimental (UnifiedHighlighter.java:95) and OffsetsEnum @lucene.internal (OffsetsEnum.java:41); the output is right without assertions; withWeightMatches(false) avoids it; and Passage#getMatchTerms says the label content is "not well defined". Three second opinions from another AI model family rated this argument moderate; the last adds that a maintainer could reasonably close such a report as "won't fix".

Why it fails: the tags speak about API stability, and none permits an AssertionError. The user never touches OffsetsEnum: the path is BooleanQuery, PrefixQuery, SpanTermQuery and the default builder. Duplicate matches are documented input. Lucene treats a false assertion as a defect. And the state the assert names is real: a re-queued match that has sub-matches of its own is handed over unexpanded (Who is affected, last point). A maintainer may still decide that deleting the assert is enough (Suggested fix).

Process the re-queued iterator when it lands at the head (validated) (recommended)

#

When the iterator is the head of the queue after it was put back, handle its current match at once, the way nextWhenMatchesIterator handles any match that reaches the head: a match with sub-matches is expanded into cached entries, a match without sub-matches stays queued. One file, +5/-1.

if (miOE.nextPosition()) {
  pendingQueue.add(miOE);
  if (pendingQueue.peek() == miOE) {
    // The next match has the same offsets as a cached sub-match and a label that sorts
    // first (another clause matches the same token), so it is the head: process it now.
    nextWhenMatchesIterator(miOE);
  }
}

Trade-offs

  • For: it keeps the state the assert names out of the highlighter's sight: whenever nextPosition() returns, the head of the queue is a cached entry or an iterator on a match without sub-matches (by reading the patched method). For the repro's prefix match the extra call changes nothing, so the passage is the same as today without assertions. The two orders of two span clauses on one word then agree: 4-9:quick, 4-9:quick (score 1.6467444) for both, and the same snippet for both.
  • Against: in a JVM without assertions it changes output for ties in which the re-queued match has sub-matches: the labels, the passage score and, with several candidate passages, which passage is returned. No test in Lucene covers that case. It has had no maintainer review.
  • Against: the recursion. The call is recursive, one level per consecutive tied match that has sub-matches and lands at the head. Measured with n clauses spanOr(aNNNNN, quick) on the repro's text: with the default thread stack (2,040 KB on the JVM used) 500 clauses (inside the default clause limit of 1,024) and 20,000 clauses return the snippet, and 50,000 clauses throw StackOverflowError (every count above 512 needs the clause limit raised: each clause has two terms); with a 256 KB stack 1,000 clauses pass and 2,000 overflow. Unmodified main and the other fix, without assertions, return the snippet for 20,000 clauses with the 256 KB stack. A loop in place of the recursive call would remove the limit; that form was not built.

Make the order the assert expects true (not built)

#

Order a cached entry before the matches iterator when both offsets tie, in this class's queue.

Trade-offs

It changes a comparator that other OffsetsEnum users share, or needs a comparator of its own for this one queue. By reading, it would make the assert's statement true without a recursive call. Not built, not run.

Workaround for test suites (not a fix)

#

For the repro's query: put the span clause before the other clause, or build the highlighter with withWeightMatches(false). Both were run and do not throw.

Trade-offs

  • Swapping is not a general rule. When both clauses carry sub-matches the passing order depends on the labels: spanOr(apple, quick) then spanTerm(quick) throws and the other order passes. BooleanQuery.rewrite can reorder repeated clauses, and a single spanOr([brown, quick, quick]) has no clause order to change.
  • withWeightMatches(false) is another highlighting mode, not the same result by another route: its javadoc says the Matches-based mode is "more accurate to the query", marks up a whole phrase instead of each word, and that the passage relevancy can differ (UnifiedHighlighter.java:233-241).

How it was found

#

Semi-formal: a determinism check. The same 400 random queries were run in 8 JVMs that differ only in hash seed and identity-hash mode, and every result line must be identical. With assertions on, one highlight call threw in 7 JVMs and returned a snippet in the eighth. Following that query to its root gave the two-clause example.

The method in full210 words

Method: semi-formal (run-to-run determinism as the oracle; no model checking, solving or proving was involved).

  • Determinism sweep. One fixed workload of 400 random queries, with every observable result on one line, was run in 8 JVMs that differ only in the hash seed (-Dtests.seed) and the identity-hash mode. With assertions off all 4,494 lines are identical. With assertions on two lines differ: for one query the default UnifiedHighlighter threw AssertionError in 7 JVMs and returned a snippet in the eighth.
  • To the root, without the seed. That query was followed down to the two-clause example, which fails in every JVM.
  • Trigger map. A pair table on the real jar (12 clause kinds x 10 other clause kinds x both clause orders; 11 of the 12 kinds are legal queries whose matches can carry sub-matches) mapped which pairs throw (Who is affected).
  • Cross-check. A single-JVM form of the same idea, "the same query with shuffled clauses must give the same results": 1,200 random queries, 1,633 shuffled copies, 82,286 comparisons per mode. With assertions on, the only further observable that differs is the UnifiedHighlighter, and all 322 of its failures are this assert.

Registry title
With assertions enabled, the default UnifiedHighlighter fails an assertion in OffsetsEnum.OfMatchesIteratorWithSubs (its source comment: 'miOE should follow cached entries') when a span clause and another clause of a disjunction match the same token (body:qu* OR spanTerm(body:quick) on 'the quick brown fox'): AssertionError with -ea, the expected snippet without assertions
Area
highlighter / UnifiedHighlighter (Matches-based offsets, HighlightFlag.WEIGHT_MATCHES, the default since 9.0.0)
Priority
Low, rank 1312: With assertions enabled (test suites, not production servers), the default UnifiedHighlighter can throw an AssertionError when a span or interval clause and an earlier prefix, wildcard, terms or range clause of the same query match the same word, in every release since 9.0.0 (and since 7.5.0 behind an opt-in flag). It is Low because a JVM without assertions returns the expected snippet for the repro's query, no hit or score changes, and the same clauses in the other order do not fail.

minor
Impact note
Hits only JVMs that run with assertions enabled (-ea: Lucene's own tests and the test suites of applications and search servers), when the UnifiedHighlighter with its default flags (WEIGHT_MATCHES, a default flag since 9.0.0 and an opt-in flag from 7.5.0 to 8.11.4) highlights a query in which a clause whose matches carry sub-matches (a span or interval clause) and an earlier clause match the same token of one field and the earlier clause's match label sorts before the matched term (a prefix, wildcard, terms or range clause, or a SpanOrQuery whose label sorts first): the highlight call then throws AssertionError; a production JVM (assertions off) returns the expected snippet for this query, no index, hit set or score is affected, and no scale is needed; the releases from 9.0.0 to 10.6.0 by default and main [exec on 9.0.0, 9.1.0, 9.12.3, 10.0.0, 10.5.2, 10.6.0 and main; the other releases by reading the source]. Summary
You highlight the text 'the quick brown fox' with the default UnifiedHighlighter for the query body:qu* OR spanTerm(body:quick), in a JVM that runs with assertions enabled. You expect 'the <b>quick</b> brown fox', which is what the same two clauses in the other order return and what a JVM without assertions returns. Instead the call throws an AssertionError without a message from Lucene's own assert statement, whose source comment reads 'miOE should follow cached entries': both clauses match the token 'quick', and the highlighter's queue puts the prefix clause's match ahead of the span clause's cached sub-match, an order that the queue's comparator allows and the assert rules out. With assertions off, which is how production JVMs run, the same call returns the expected snippet: for this query nothing is wrong there.
