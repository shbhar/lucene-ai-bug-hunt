LockVerifyServer never exits when its accept timeout fires after some clients have connected

Start LockVerifyServer for 2 clients and let only 1 connect: after 30 s it prints "Accept timed out", but the connected client's server thread waits forever, so the server never exits and the client waits until the server is stopped. Every release since 4.8.0; only the lock-verification tools are affected.

The finding in 30 seconds

#

LockVerifyServer.run() starts one thread per client as it connects; each thread waits on a start latch that is released only after the last client has connected. When accept() times out first, nothing releases the latch, so the threads already started wait forever.

Background in three steps

#
  1. To test a lock factory, Lucene ships a tool pair: one LockVerifyServer process and one LockStressTest process per client. The clients take and release a lock in a loop and report each step to the server, which checks that at most one holds it.
  2. You start the server with a client count, for example LockVerifyServer 127.0.0.1 2. It waits up to 30 s for each client to connect and send its id.
  3. When all clients are in, the server sends each one a start signal (the "starting gun") so they begin together; when they finish, it prints "Server terminated." and exits.

The finding, step by step

#
  1. You test a lock factory the way its javadoc suggests: start LockVerifyServer 127.0.0.1 2 (wait for 2 clients) and two LockStressTest clients. Client 0 connects and sends its id; client 1 has a typo in its lock-factory class name and exits before connecting.
  2. You expect the server to give up and exit about 30 s after client 0 connected. The code says "give clients at most 30 secs to connect", and a maintainer kept the timeout "to make sure the server ends if one of the clients does not start".
  3. Instead it prints SocketTimeoutException: Accept timed out and keeps running: 15 s later the server JVM is still alive, and so is client 0, still waiting for the start signal. The server must be stopped by hand; client 0 then ends with "Protocol violation".
  4. The cause: the server started a thread for client 0 that waits on a start latch. The latch is released only after both clients have connected, and the timeout path never releases it, so that non-daemon thread keeps the JVM alive.
  5. With 0 clients connected the same timeout does end the JVM (exit code 1): only the partial case hangs. Lucene's own stress test calls the server in-process, so there it fails with a leaked-thread error instead.

Who is affected

#

Only people who run the lock-verification tools, by hand or in a script, as the LockFactory javadocs suggest, and only when a client fails to start or connect within 30 s after another connected. The server then stays up until stopped by hand, and that client waits until then. Indexing, search and IndexWriter locking are not affected.

Mechanism, terms and numbers491 words

LockVerifyServer is the small server that LockStressTest clients talk to when you test a lock factory, as the LockFactory javadoc suggests. You give it a client count; it waits at most 30 s for each client to connect. If one client connects and another never does, accept() throws SocketTimeoutException: Accept timed out and run() ends, but the thread it already started for the connected client (which has sent its id) stays parked on the start latch, because the latch is counted down only after every client has connected. That thread is a normal (non-daemon) thread, so the standalone server JVM never exits, and the connected LockStressTest client, which reads the start signal with no timeout, waits as long as the server runs. The server has to be stopped by hand; the client then ends with its "Protocol violation" error. With no client connected the same timeout does end the JVM. Every release since 4.8.0 is affected. The fix: on an accept failure, release the latch with a failure mark, close the accepted sockets and join the started threads before rethrowing.

The bug

#
  1. run() (LockVerifyServer.java:43-145) sets the 30 s accept timeout (:46, "give clients at most 30 secs to connect and send bytes"), creates startingGun = new CountDownLatch(1) (:57) and accepts maxClients sockets in a loop (:60-61).
  2. For each accepted socket it starts a thread at once (:62-131). The thread reads the client id (:68) and parks in startingGun.await() (:73).
  3. startingGun.countDown() (:136) and the joins (:139-141) come after the loop. When a later s.accept() throws SocketTimeoutException, nothing catches it: the latch is never counted down, the started threads are never joined, and their sockets stay open (each thread closes its socket only in its own finally, :127).
  4. main() (:147-154) only calls run(...). The main thread dies with the stack trace; the per-client threads are ordinary non-daemon threads, so the JVM keeps running.
  5. A connected LockStressTest client reads the start signal with no read timeout (LockStressTest.java:116; its 3 s timeout covers only connect, :106), so it waits as long as the server lives. When the server JVM ends, that read returns end-of-stream and the client throws "Protocol violation" (:117).

What was run

#
  • Shipped tools on main: LockVerifyServer 127.0.0.1 2, client 0 on NativeFSLockFactory, client 1 with a mistyped factory class (exit code 1 before connecting). The server prints "Accept timed out"; 15 s later its JVM is alive with Thread-0 WAITING on a CountDownLatch, and client 0 is alive in a socket read. Stopping only the server (SIGTERM) then ends client 0 by itself: IOException: Protocol violation, exit code 1.
  • Control: with no client at all, the server JVM exits with code 1 after the timeout.
  • The one-test JUnit (Minimal repro) on main, assertions on and off.
Exposure and likelihood170 words
  • Who: users of the tool pair that the LockFactory, NativeFSLockFactory and SimpleFSLockFactory javadocs suggest for a suspect lock factory ("you can easily test it by using VerifyingLockFactory, LockVerifyServer and LockStressTest"), when one client fails to start or to connect within 30 s after another has connected: a mistyped class name, a slow or crashed start.
  • Effect: the server process stays up until it is stopped by hand, and the connected client waits until then; a script or CI job that waits for them hangs. Nothing is written to any index; search and IndexWriter locking never go through this code.
  • In-process: TestStressLockFactories calls run() directly. There run() throwing fails the test and the test framework's leak checker reports and interrupts the stuck threads, so the test fails with an extra ThreadLeakError instead of hanging. Lucene's CI printed that pair of errors in 22 failure mails between 2020-12-02 and 2024-01-13 (classified by reading the mails).
  • Likelihood: rare; the searches (Prior reports) found no report of the standalone hang since 4.8.0 (2014).

Loopback only, deterministic; the test takes about 35 s. It fails on main with assertions on and off and passes with the fix.

Why it looks unintended

#
  • The code: "give clients at most 30 secs to connect and send bytes" (LockVerifyServer.java:46); the success path joins all threads ("Server terminated.")
  • Uwe Schindler on #12535: "I think the timeout was added to make sure the server ends if one of the clients does not start": this case.
  • With no client, the same timeout ends the JVM (exit code 1).
The full argument221 words
  • The timeout is meant to end the server when a client is missing. The comment at :46 and the success path (:139-143: join every thread, print "Server terminated."). No javadoc or API contract promises that the process exits; the intent comes from the code and the maintainers' words below.
  • A maintainer named this scenario as the reason for the timeout. #12535 first proposed removing it. Uwe Schindler, 2023-09-04: "I think the timeout was added to make sure the server ends if one of the clients does not start at all or fails to start. [...] If one of the client will crush before connecting the server will hang forever, so there should really be a timeout!"; 2023-09-05: "DO NOT remove the server timeout, because a failing client (timeout, OOM, out of file handles,...) will otherwise make the server wait forever for the missing client after accepting connections of all others". The timeout was kept (the merged commit 3c235bb7b43 still has setSoTimeout(30000), although its title says "nor set accept timeout"); the path after it never changed.
  • The command line is a real, documented use. main() is public, three lock-factory javadocs point users to the tools, and the #12535 author, Michael McCandless, checked that use: "I confirmed I could still run the LockVerifyServer and two LockStressTest clients from the command-line".
The devil's-advocate check145 words

The strongest case for "intended": the timeout and the latch were built (LUCENE-5612, 2014) for an automated harness that runs the server in-process, today TestStressLockFactories, and there the intent holds: the test fails and the leak checker reaps the threads, so nothing hangs. The leaked threads were printed in CI 22 times and nobody acted; it is a diagnostic tool with a loud error, no contract promises that the process exits, and Michael McCandless asked on #12535 whether it should leave core ("I don't think this is a tool users often use?").

Why it fails: the standalone server is the documented public entry point, and for it the stated purpose ("the server ends") is not met in the one case the timeout was kept for, a client failing after others connected. The argument bounds the impact (Low); it does not make the behaviour intended.

Suggested fix

#

Recommended A. Release, close and join on an accept failure (validated)

On an accept failure, mark the run failed, count the start latch down, close the sockets accepted so far, join the started threads and rethrow; a released thread sees the mark and returns. 22 lines added, no re-indentation. The repro passes, and so do the six lock test classes, TestStressLockFactories included.

All options and trade-offs3 options · 688 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B is the change the finding was first checked with; C is by reading.

A. Release, close and join on an accept failure (validated) (recommended)

#

In LockVerifyServer.run(), catch the IOException from s.accept(); set lockedID[0] = -2 (the mark the threads already use for "another thread got error"), count the latch down, close the accepted sockets, join the started threads, rethrow. After await(), a thread returns when it sees the mark. 22 lines added, 1 removed:

final Socket[] sockets = new Socket[maxClients];
for (int count = 0; count < maxClients; count++) {
  final Socket cs;
  try {
    cs = s.accept();
  } catch (IOException e) {
    // not all clients connected in time: release, disconnect and end the ones that did
    synchronized (localLock) {
      lockedID[0] = -2;
    }
    startingGun.countDown();
    IOUtils.closeWhileHandlingException(sockets);
    for (int i = 0; i < count; i++) {
      threads[i].join();
    }
    throw e;
  }
  sockets[count] = cs;
  ...
      startingGun.await();
      synchronized (localLock) {
        if (lockedID[0] == -2) {
          return; // the server failed before all clients connected
        }
      }

Trade-offs

  • Nothing changes when all clients connect and send their ids.
  • The connected client now reads end-of-stream, so a LockStressTest client ends with its existing "Protocol violation" error instead of hanging (LockStressTest.java:116-117; the repro checks end-of-stream).
  • Closing the sockets also ends a thread whose client connected but never sent its id (blocked in in.read(), :68); that thread ends with an uncaught RuntimeException wrapping SocketException: Socket closed, printed to stderr (probe).
  • It catches only the IOException from accept(), not a failure to create a thread.
  • CHANGES: a Bug Fixes entry.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off (SocketTimeoutException: Read timed out plus a ThreadLeakError at LockVerifyServer.java:73); with the fix it passes, on and off (about 30 s).
  • With the fix and the repro: TestStressLockFactories (which drives LockVerifyServer with real LockStressTest client processes), TestLockFactory, TestNativeFSLockFactory, TestSimpleFSLockFactory, TestSingleInstanceLockFactory, TestSleepingLockWrapper and the repro: 7 classes, 37 tests, 0 failures, 0 skipped.
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test.
  • Probe of a client that connects but never sends its id (evidence only, not the repro): stock, run() throws after 30 s but the thread stays blocked in in.read(); with the fix, run() throws after 30 s, the client reads -1 and no server thread is left; with option B, run() had not returned after 45 s.
  • The full lucene/core suite was not run.

B. Release and join without closing the sockets (try/catch around the whole loop) (validated by the checks)

#

Wrap the whole accept loop in try { ... } catch (Throwable t); on failure set the mark, count down, join the started threads, rethrow.

Trade-offs

Makes the repro pass. But for a client that connected and never sent its id, join() waits forever on a thread blocked in in.read(), so run() itself never returns, where stock main at least throws after 30 s (probe: run() had not returned after 45 s). The checked diff leaves the loop's indentation alone; formatted to the project's style, it would re-indent the whole loop.

What the checks validated

Applied as a shadowed class: the minimal repro passes (assertions on), the original witness test passes with assertions on and off. Probe of a silent client: fails (run() not returned after 45 s).

C. Daemon threads

#

Call setDaemon(true) on the per-client threads.

Trade-offs

Lets the command-line JVM exit (and with it the client's connection), but in-process callers such as TestStressLockFactories still leak the parked threads. Not run. Optional on top of A: a read timeout on the accepted sockets for the id read would also cover a different case that A leaves as it is: every client connects but one never sends its id; the latch is then released and run() waits forever in the join, because accepted sockets have no read timeout (by reading, :60-68, :139-141). Not run.

Downstream note

#

Lucene.NET's LockVerifyServer has the same accept loop and start latch, with no fix.

How it was found

#

Semi-formal: a proof-obligation audit of LockVerifyServer's contract, the obligation being that the accept timeout ends the server when a client does not start. It fails when some clients have connected, because the start latch is released only on the success path; a one-test JUnit on stock main witnessed it.

The method in full104 words
  • Contract: the comment at LockVerifyServer.java:46 and the success path (join, "Server terminated."), backed by maintainer comments on #12535: the accept timeout makes the server end when a client does not start.
  • Obligation checked: on every path out of run(), each thread run() started ends. It holds when all clients connect and when none does; it fails when the timeout fires after some connected (:73 waits on a latch counted down only at :136).
  • Witness: one JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review that ran the shipped tools, and an adjudication (see Independent checks).
