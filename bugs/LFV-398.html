Flexible query parser: toQueryString prints user@example.com, && and || unescaped, so the printed query does not parse

The flexible parser's toQueryString is documented to return parseable text, but its escaper EscapeQuerySyntaxImpl escapes @ only as a term's first character and ignores && and ||. So the term user\@example.com prints as df:user@example.com, and parsing that throws a syntax error; && and || fail the same way.

The finding in 30 seconds

#

The escaper's tables lag behind the grammar. Since 9.1 an @ is syntax at every position of a term, but the escaper escapes it only at the first; && and || have always meant AND and OR, but only the words are escaped.

Background: how a flexible-parser query tree prints itself

#
  1. The flexible StandardQueryParser first turns the text into a tree of query nodes. A term becomes a FieldQueryNode holding the field and the unescaped text: user\@example.com becomes field df, text user@example.com.
  2. Every node can print itself back as query text with toQueryString(escaper). A term node prints field: followed by its text passed through the escaper (only the text when the field is null or the reserved name _plain).
  3. EscapeQuerySyntaxImpl, the escaper for the standard syntax, puts a backslash before whatever the grammar would read as syntax: characters such as ( or : anywhere in the term, +, - and @ only at its start, and the whole words AND, OR and NOT.

The finding, step by step

#
  1. Parse user\@example.com, an e-mail address written the way the flexible parser requires since 9.1 (an @ inside a term must be escaped). The parser builds one term node: field df, text user@example.com.
  2. Print it with toQueryString(new EscapeQuerySyntaxImpl()), documented to return "a query string understood by the query parser". You expect df:user\@example.com: the escaper already prints a leading @ as \@ and the word AND as \AND.
  3. You get df:user@example.com, and parsing it again throws INVALID_SYNTAX_CANNOT_PARSE. The escaper escapes @ only at position 0, while the grammar rejects an unescaped @ at every position of a term.
  4. The term && (typed \&&) prints as df:&&, which the parser reads as the AND operator: the same syntax error, and || likewise. The escaper's reserved words include AND, OR and NOT, but not && or ||.
  5. Of all 866,495 printable-ASCII texts of 1 to 3 characters, each built as a term node, 18,052 do not survive the round trip, each with an @ after the first character or exactly && / ||; a three-line change to three of the escaper's tables brings that to 0. The Query that parse() builds is not affected.

Who is affected

#

Applications that print flexible-parser node trees back to text with toQueryString(new EscapeQuerySyntaxImpl()), or call EscapeQuerySyntaxImpl.escape themselves, and parse that text again: a term with @ after its first character, such as an e-mail address, or the term && or || gives a syntax error. Default settings; parse() results are unaffected.

Mechanism, terms and numbers715 words

QueryNode#toQueryString(EscapeQuerySyntax) is documented to "convert to a query string understood by the query parser", and EscapeQuerySyntaxImpl is the escaper for the standard syntax. Since 9.1 (LUCENE-10223) the standard grammar rejects an unescaped @ anywhere in a term, so an e-mail address has to be written user\@example.com (or quoted); && and || have been the AND and OR operators since the flexible parser's first release, 2.9.0. The escaper was never updated for either: it escapes @ only as a term's first character, and its reserved words are AND, OR, NOT but not && or ||.

So the term nodes the parser builds from user\@example.com, \&& and \|| print as df:user@example.com, df:&& and df:||, and parsing any of them again throws INVALID_SYNTAX_CANNOT_PARSE. Of all 866,495 printable-ASCII texts of length 1 to 3, each built as a term node, exactly 18,052 fail this round trip; with a three-line change to three of the escaper's tables, none do. The Query that StandardQueryParser.parse() builds is not affected: only code that turns node trees back into text, or calls the escaper itself, and then parses that text. The && / || half is in every release from 2.9.0 to 10.6.0, the inner-@ half in every release from 9.1.0, and main has both.

The mechanism (main 645d4fe14a20)

#
  1. The parser builds the node. A term token becomes new FieldQueryNode(field, discardEscapeChar(term.image), ...) (StandardSyntaxParser.jj:804), so user\@example.com gives a node whose text is user@example.com.
  2. The node prints itself. FieldQueryNode.toQueryString returns field + ":" + getTermEscaped(escaper), or only the escaped term when isDefaultField(field) is true: a null field, the reserved field name _plain, or a node told to ignore fields (FieldQueryNode.java:64-71, QueryNodeImpl.java:35, :206-211); getTermEscaped calls escaper.escape(text, Locale.getDefault(), Type.NORMAL) (:55-58). NORMAL is documented as "for escaping reserved words (like AND) in terms" (EscapeQuerySyntax.java:27-28).
  3. The escaper. escape (EscapeQuerySyntaxImpl.java:166-183) handles wildcards and backslashes, then escapeTerm (:75-87) runs escapeChar and escapeWhiteChar and finally compares the whole term with escapableWordTokens (:83-85). escapeChar (:43-62) escapes each character of escapableTermChars (:32-34) at every position, but checks escapableTermExtraFirstChars = {"+", "-", "@"} (:30) against buffer.charAt(0) only (:53-59). escapableTermChars has no @, and escapableWordTokens (:39-41) is AND, OR, NOT, TO, WITHIN, SENTENCE, PARAGRAPH, INORDER.
  4. The grammar. _TERM_START_CHAR excludes @ (StandardSyntaxParser.jj:131-133) and _TERM_CHAR adds back only - and + (:134). So + and - are legal inside a term, and escaping them only at the start is right, but an unescaped @ is legal nowhere in a term: it appears only as the min-should-match marker after a group, ( ... )@N (:358).
  5. The operators. <AND: ("AND" | "&&")> and <OR: ("OR" | "||")> (:144-145) are declared before <TERM> (:161). For exactly &&, the AND and TERM tokens match the same length and the earlier one wins, so df:&& is a field followed by an operator: a syntax error. &&& and a&&b are longer TERM matches and round-trip.

Worked examples (main, executed)

#
  • \@example.com (control, @ first) prints df:\@example.com and parses back.
  • user\@example.com prints df:user@example.com: syntax error. With the fix: df:user\@example.com, parses.
  • \&& prints df:&&: syntax error (read as AND). With the fix: df:\&&, parses.
  • \|| prints df:||: syntax error (read as OR). With the fix: df:\||, parses.
  • Controls: \AND, &&& and a&&b print df:\AND, df:&&& and df:a&&b and parse back. (Unescaped AND is rejected as input: Syntax Error, cannot parse AND:.)

The same nodes come from the public constructor new FieldQueryNode("f", "user@example.com", 0, 0); hand-built nodes with the texts AND, &&& and a&&b print f:\AND, f:&&& and f:a&&b and parse back. Quoted terms are not affected; they use the STRING escaping path.

Exhaustive check

#

Every printable-ASCII text of length 1 to 3 (95 + 95^2 + 95^3 = 866,495) was built directly as a term node (FieldQueryNode), printed and parsed again: 18,052 fail, exactly the 95 two-character texts x@, the texts && and ||, and 17,955 three-character texts with @ after the first character. With the fix, 0 fail. An independent reproducer repeated the enumeration and got the same count.

Exposure and likelihood274 words
  • Who is hit. Code that turns node trees into text and parses it again, for example to store, log or forward a rewritten query, or that escapes words with EscapeQuerySyntaxImpl.escape. The trigger is any term with an inner @ (e-mail addresses, user@host handles) or a literal && / || term, from escaped input or from hand-built nodes.
  • Default vs opt-in. Default parser settings and the stock escaper, the only implementation in Lucene. The round trip itself is an uncommon API pattern; StandardQueryParser.parse() never re-parses its own output.
  • What goes wrong. For a term printed with a field prefix (df:user@example.com, df:&&, df:||) the printed query is refused with a clean ParseException (INVALID_SYNTAX_CANNOT_PARSE): it fails loudly. A bare || printed without a prefix (a node whose field is null or the reserved name _plain, or a word escaped with EscapeQuerySyntaxImpl.escape and joined into a query) parses again as the OR operator and can change what the query means.
  • The three cases differ. An inner @ (e-mail addresses, handles) is the realistic one and fails since 9.1; a literal && or || term is unusual; only || has a shown change of meaning, and only in text printed without a field prefix.
  • Inside Lucene escaped output only feeds exception messages (QueryTreeBuilder.java:161, BooleanQueryNodeBuilder.java:72, MatchAllDocsQueryNodeBuilder.java:42, MatchNoDocsQueryNodeBuilder.java:42, AllowLeadingWildcardProcessor.java:74), which then show the term unescaped. IntervalQueryNode.toString() also calls toQueryString(new EscapeQuerySyntaxImpl()) (IntervalQueryNode.java:52-55), but its toQueryString ignores the escaper (:47-50).
  • Scale and reach. One term is enough, deterministic. No public report since 9.1.0 (2022) for @ or since 2.9.0 (2009) for && / ||.

Why it looks unintended

#
  • The javadoc says so: toQueryString returns "a query string understood by the query parser".
  • Since 9.1 an inner @ must be escaped, am\@zing, or quoted (Dawid Weiss on #11800); when / became syntax in 2012, the escaper gained / in the same commit.
  • QueryParserUtil.escape escapes & and |, and #7865 fixed unparseable range-node output as a bug in 11.0.0.
The full argument308 words
  • The documentation says the output parses. "convert to a query string understood by the query parser" (QueryNode.java:26); "A query node tree can also generate a query string that can be parsed back by the original text parser, at this point only the standard lucene syntax is supported" (core/nodes/package-info.java:42-43); NORMAL escapes "reserved words (like AND) in terms" (EscapeQuerySyntax.java:27-28). These describe the intended behaviour rather than state a formal round-trip guarantee, but the output here is a syntax error.
  • The inner @ must be escaped by design. On #11800 (2022) Robert Muir called the 9.1 @ parse failure "not a bug", an intended grammar change, and Dawid Weiss wrote "You can escape the at character": am\@zing. So the escaped form is the intended syntax, and the escaper should produce it. Neither mentions toQueryString.
  • The escaper was kept in step with the grammar once before. LUCENE-3981 (167b296353d, 2012) excluded / from term characters and added / to escapableTermChars in the same commit. LUCENE-10223 (f725b27e12a, #429) added @ to the exclusions and did not touch EscapeQuerySyntaxImpl. So the @ half is a missed follow-up in the escaper; the grammar change itself was intended (#11800).
  • The escaper already escapes the word forms (AND prints \AND), and the package's other escaper, QueryParserUtil.escape, escapes & and | (QueryParserUtil.java:172-174), asserted since LUCENE-881 (TestQPHelper.java:923-925).
  • Precedent. CHANGES.txt:296-298, Lucene 11.0.0 Bug Fixes: "GITHUB#7865 AbstractRangeQueryNode#toQueryString(EscapeQuerySyntax) now returns a string which can be parsed back into the original node"; TestAbstractRangeQueryNode asserts the "query string should have expected format and parse into a valid query" (:44-47).
  • Nothing documents the gap. No javadoc, test, CHANGES or MIGRATE entry says these terms may print unparseable; MIGRATE.md:1116-1122 mentions only "the @ character after parentheses". No upstream test pins the escaper's current output.
The devil's-advocate check196 words

The strongest case for "intended" (weak, as every verifier rated it; a later reading-only fact check by another model family rated it moderate): "There has never been a guarantee that going back and forth between a parsed query and its string representation is idempotent" (Erick Erickson, java-user, March 2017, about range nodes), and open #8667 questions toQueryString's design; toQueryString also reads like a display serializer (it takes the escaper as a parameter, and in-tree callers use it for messages).

Why it fails: both quotes are about output that differs from the input, not output that does not parse, and the javadoc describes the output as parseable. In the same 2017 thread Michael McCandless replied "Why don't we fix this in Lucene?", and that line of work ended in the #7865 Bug Fixes entry. A second argument, letting the grammar accept @ inside terms again, reverses the decision on #11800 and leaves && / || unfixed; the escaper fix is the consistent one. One range-node fix (#7865) does not make a general round-trip guarantee, so the claim easiest to accept is the narrow one: FieldQueryNode's term printing is out of step with the current grammar.

Suggested fix

#

Recommended Update three of the escaper's tables

In EscapeQuerySyntaxImpl, move @ from the first-character list to the every-position list, and add && and || to the reserved words (+3/-3, one file). The repro passes with assertions on and off, and so does the whole queryparser test task (535 tests, 1 skipped). Only values with an inner @ or exactly && / || print differently.

Trade-offs

  • Only the printed text of a value with an inner @ or exactly && / || changes. For a term with a field prefix that text did not parse before and now does. A bare || printed without a prefix (a null or _plain field, or escape() on a single word) was read as OR and now stays a term. Range bounds also go through the escaper, and inside brackets @, && and || already parse: [a@b TO c] and [&& TO zz] now print df:[a\@b TO c] and df:[\&& TO zz] and parse back to the same range query (executed). With the fix the study's exhaustive length 1-3 round trip has 0 failures, and its security enumeration gives the intended term query for all 866,495 texts.
  • Exception messages that print nodes now show the escaped text. No upstream test pins the old output.
  • Open PR #16853 edits escapeIgnoringCase in the same file; its diff does not touch these tables.

Escape & and | as characters everywhere

#

Add & and | to escapableTermChars, as QueryParserUtil.escape does.

Trade-offs

A simpler rule, consistent with the other helper, but it also changes the output of terms that round-trip today (a&&b would print a\&\&b). Not run.

Let the grammar accept @ inside terms again

#

Add @ to _TERM_CHAR in StandardSyntaxParser.jj.

Trade-offs

Reverses the intended 9.1 change (#11800), needs the JavaCC parser regenerated, and does nothing for && / ||. Not recommended; not run as a fix.

Downstream note

#

Not a Lucene security issue; downstream, a word that is exactly || and printed without a field prefix (escaped alone with EscapeQuerySyntaxImpl.escape and joined into a query string, or a node whose field is null or the reserved name _plain) is read as the OR operator, which can make a neighbouring clause without + optional.

History

#

&& / || since the flexible parser's first release, 2.9.0 (LUCENE-1567, 2009); the inner @ since 9.1.0, when LUCENE-10223 (#429, 2021) made @ syntax in the grammar but not in the escaper. Executed on all 148 releases from 2.9.0 to 10.6.0 and on main; none is fixed.

Versions tested5 rows

&& / ||: introduced by LUCENE-1567 "New flexible QueryParser framework" (343992fcbb4, Michael Busch, 2009-08-03, svn era, no PR). Its grammar already had && and || as AND and OR, while the escaper listed only the words.

Inner @: introduced by LUCENE-10223 "interval support in standard syntax parser" (PR #429, issue #11259, Dawid Weiss, merged 2021-11-11; main f725b27e12a, branch_9x ff9ee28c603). It added @ to the term-character exclusions for the new ( ... )@N syntax and left the escaper's first-character-only @ rule, which dates from 2009: a missed follow-up in the escaper, while the grammar change itself was intended (#11800). A commit-level check pins it: the 9.1.0 jars with the generated parser of ff9ee28c603 fail the inner-@ case; with the parser of its parent 238cd5fd0c3 they pass.

In the whole history the escape tables changed only once, when LUCENE-3981 (2012) added /.

LFV-398, snapshot of 2026-11-03

Registry title
Flexible query parser: EscapeQuerySyntaxImpl does not escape '@' after the first character of a term or a term that is exactly && or ||, so QueryNode#toQueryString output for such terms does not parse
Area
queryparser / flexible parser term escaping (EscapeQuerySyntaxImpl, as used by QueryNode#toQueryString)
Priority
Low, rank 801: The flexible parser's escaper utility breaks its round-trip contract for an inner '@' or a bare && or ||, while the parse-to-Query path is unaffected.
Impact class
minor
Impact note
A round-trip (contract) defect in a utility method, with no effect on the Query that StandardQueryParser.parse builds: applications that turn flexible-parser node trees (parsed from escaped input such as 'user\@example.com', or built by hand) back into text with toQueryString(new EscapeQuerySyntaxImpl()), or that call EscapeQuerySyntaxImpl.escape themselves, and then parse that text get a syntax error for any term with '@' after its first character (an e-mail address, for example) or a term that is exactly && or ||; inside Lucene the output only feeds exception messages; default parser configuration, any scale, every release since 2.9.0 for && / || and since 9.1.0 for '@'.
Summary
Since 9.1 the standard flexible parser reads an '@' anywhere in a term as syntax (it must be escaped, as in user\@example.com), and && and || are its AND and OR operators, so QueryNode#toQueryString, documented to return 'a query string understood by the query parser', has to escape them. Its escaper EscapeQuerySyntaxImpl escapes '@' only when it is the first character of a term and lists AND, OR and NOT but not && or || as reserved words, so the node for 'user\@example.com' prints 'df:user@example.com' and the nodes for '\&&' and '\||' print 'df:&&' and 'df:||'. Parsing any of these strings again throws INVALID_SYNTAX_CANNOT_PARSE; with a small fix to the escaper's tables every printable-ASCII term of length 1-3 round-trips.
Introduced
Two parts with one fix site. '@' part: f725b27e12a9 on main and its branch_9x backport ff9ee28c6035 (LUCENE-10223, GitHub #11259, PR #429 by dweiss, merged 2021-11-11): it excluded '@' from every term character in StandardSyntaxParser.jj (for the new '(...)@N' min-should-match syntax) but did not change EscapeQuerySyntaxImpl, whose first-character-only '@' rule (escapableTermExtraFirstChars) dates from 343992fcbb4b [exec: commit-level check, 9.1.0 jars with the generated parser of the parent 238cd5fd0c3 pass the inner-'@' test, with the parser of ff9ee28c6035 they fail it; read: git log -G on _TERM_START_CHAR between 9.0.0 and 9.1.0 returns only ff9ee28c6035, and EscapeQuerySyntaxImpl is identical in 9.0.0 and 9.1.0]. && / || part: 343992fcbb4b31249f07354014723f18d0508d8a (LUCENE-1567 'New flexible QueryParser framework', GitHub #2641, SVN r800191; SVN era, no PR): its grammar already defined <AND: "AND" | "&&"> and <OR: "OR" | "||"> while escapableWordTokens listed only the word forms [read: git log -S'"&&"' finds no commit that ever adds && or || to the escaper; exec: 2.9.0 fails]. (2009-08-03 (&& / || part, 343992fcbb4b); 2021-11-11 ('@' part, PR #429 merged))
