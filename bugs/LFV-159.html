HnswGraph.DenseNodesIterator.consume() does not advance: reading HNSW level 0 in chunks returns the first chunk forever

On level 0 of Lucene's in-memory and stored HNSW graphs, NodesIterator.consume(buf) copies the next node ids but never moves the iterator, so chunked reads return the first chunk forever and a while (hasNext()) consume(buf) loop never ends. Lucene never reads level 0 this way; outside code that does is hit, since 9.5.0.

The finding in 30 seconds

#

An HNSW graph hands out one node iterator per level. The level-0 iterator's bulk read, consume(), copies the next ids but forgets to move forward.

Background: HNSW levels and node iterators

#
  1. Lucene's kNN vector index is an HNSW graph per segment and field. Level 0 holds every vector as a node, numbered 0 to size-1; each higher level holds a smaller subset.
  2. HnswGraph#getNodesOnLevel(level) returns a NodesIterator, an ordinary PrimitiveIterator.OfInt over that level's node ids: hasNext() / nextInt() one id at a time, or consume(int[] dest) to take the next batch into an array; it returns how many ids it wrote.
  3. There are three implementations. In Lucene's in-memory and stored graphs, level 0 gets DenseNodesIterator, which simply counts 0, 1, 2, ...; upper levels get ArrayNodesIterator or CollectionNodesIterator. Code outside Lucene gets a stored graph through HnswGraphProvider#getGraph, or an in-memory one from HnswGraphBuilder.

The finding, step by step

#
  1. Index 2,000 vectors with the default codec and open the stored HNSW graph (HnswGraphProvider#getGraph). Level 0 holds every vector: getNodesOnLevel(0) returns an iterator over node ids 0 to 1,999.
  2. Read it in chunks of 7: while (it.hasNext()) { int n = it.consume(buf); ... }. You expect 0-6, then 7-13, and so on up to 1,995-1,999: 286 calls, every id once, then hasNext() is false. Level 1 of the same graph behaves exactly like that.
  3. Instead every call returns 0-6 again and hasNext() stays true: the loop never ends (the test stops it after 286 calls and 2,002 ids). A nextInt() after consume() also starts again at 0. Smallest case: new DenseNodesIterator(4) read twice into an int[2] gives [0, 1] both times.
  4. Why: Lucene's graphs use DenseNodesIterator for level 0, whose consume writes cur, cur+1, ... into the buffer but never adds the count to cur. The two other iterator classes, used for the upper levels, do.
  5. Lucene's only consume() call reads upper levels in one full-size call, so Lucene's indexes and search results are not affected. One line, cur += numToCopy;, fixes it.

Who is affected

#

Only code outside Lucene that reads level 0 with consume() more than once, or mixes it with nextInt() or hasNext(): a custom vectors writer, codec plugin or graph tool. Its loop then hangs or ids repeat. Lucene never does this, so its indexes and searches are fine; the downstream callers that were read make one full-size call on upper levels.

Mechanism, terms and numbers581 words

HnswGraph#getNodesOnLevel(level) returns a NodesIterator, a PrimitiveIterator.OfInt over the node ids of one graph level with a bulk method consume(int[] dest) documented as "Consume integers from the iterator and place them into the dest array", returning the number written. For level 0, which holds every node, every Lucene graph that enumerates level 0 returns a DenseNodesIterator over [0, size): the in-memory OnHeapHnswGraph, the default codec's stored graph (through HnswGraphProvider#getGraph), the lucene91-lucene95 back-compat readers and getSortedNodes(0) (the lucene90 back-compat graphs throw UnsupportedOperationException instead). Its consume (HnswGraph.java:241-251) writes cur, cur+1, ... and returns the count but never runs cur += numToCopy, while nextInt() and hasNext() use the same cur. So a second consume returns the same block, hasNext() stays true, a while (hasNext()) consume(buf) loop never ends, and nextInt() after consume() starts again at 0. The two sibling classes, used for upper levels, advance. Lucene's only production consume() call (Lucene99HnswVectorsWriter.writeMeta) reads upper levels in one full-size call, so the bug is latent: only code outside Lucene that reads level 0 with consume() is hit. It came with consume() in #11860 (9.5.0, 2022) and is in every release up to 10.6.0 and on main. The fix is one line.

Terms

#
  • NodesIterator (HnswGraph.java:161-186): "Iterator over the graph nodes on a certain level"; it implements PrimitiveIterator.OfInt (:166) and declares consume(int[] dest): "Consume integers from the iterator and place them into the dest array. @return The number of integers written to dest" (:179-185).
  • DenseNodesIterator (:230-265): "NodesIterator that enumerates [0, size)", with one cursor cur shared by consume, nextInt (return cur++;) and hasNext (cur < size).
  • Who returns it: getNodesOnLevel(0) of OnHeapHnswGraph (OnHeapHnswGraph.java:272-273), of the default codec's stored graph (Lucene99HnswVectorsReader.java:663-664) and of the back-compat readers (the lucene91, lucene92, lucene94 and lucene95 formats), and HnswGraph#getSortedNodes(0) (HnswGraph.java:149-150). Upper levels get ArrayNodesIterator or CollectionNodesIterator. getNodesOnLevel itself is abstract (HnswGraph.java:101): the lucene90 back-compat graphs throw UnsupportedOperationException, and a custom HnswGraph picks its own iterator.

The bug

#
  1. DenseNodesIterator.consume(dest) (HnswGraph.java:241-251) computes numToCopy = Math.min(size - cur, dest.length), writes dest[i] = cur + i and returns numToCopy. It never runs cur += numToCopy.
  2. So cur is where it was: the next consume copies the same block, hasNext() stays true, and nextInt() returns an id consume already handed out.
  3. The siblings move their cursor: ArrayNodesIterator.consume has the same body plus cur += numToCopy; (:212), and CollectionNodesIterator.consume fills dest through nextInt() (:277-289). Upper levels are therefore correct.
  4. Lucene never notices: its only production consume() call, Lucene99HnswVectorsWriter.writeMeta (:629-637), runs only if (level > 0), makes one call with a buffer of size() and drops the iterator. Every in-tree reader of level 0 uses hasNext() / nextInt().

The numbers

#
  • new DenseNodesIterator(4) consumed twice into an int[2]: [0, 1] and [0, 1] (expected [0, 1], [2, 3]).
  • Stored graph of a 2,000-vector default-codec index, level 0 read with consume(int[7]) in a while (hasNext()) loop: every call returns 0-6; the test's bound stops it after 286 calls and 2,002 ids (expected 2,000 distinct ids, then hasNext() false). Level 1 of the same graph returns every node once.
  • 1,000-document index, buffer 64: hasNext() is still true after 16 calls that returned 1,024 ids.
  • consume(new int[3]) returns 0, 1, 2; the next nextInt() returns 0 instead of 3.
Exposure and likelihood378 words
  • Who is hit. Code outside Lucene that reads level 0 of an HNSW graph with consume() in more than one call, or mixes consume() with nextInt() / hasNext(). The iterator is public API in the exported package org.apache.lucene.util.hnsw (module-info.java:50): the stored graph through HnswGraphProvider#getGraph (@lucene.experimental, in the exported package org.apache.lucene.codecs.hnsw, :76), a completed OnHeapHnswGraph from HnswGraphBuilder (which a custom KnnVectorsWriter holds during flush and merge; while it is still being built, getNodesOnLevel throws IllegalStateException), getSortedNodes(0) on any graph, or new HnswGraph.DenseNodesIterator(n).
  • What happens. A while (hasNext()) consume(buf) loop never ends on any non-empty level with any non-empty buffer; if it collects the ids, memory grows until the heap runs out. A loop that stops when the counts add up to size() ends, but when the buffer is smaller than the level it returns the first block repeatedly and misses the rest (by reading the code; with a buffer of at least size() such a loop is correct). consume() then nextInt() returns duplicates. One consume() into a size() buffer returns the right ids but leaves hasNext() true. A custom vectors writer that wrote level 0 from such a loop would hang on flush or write wrong graph data (by reading the code); Lucene's own writer does not do this.
  • Lucene is not affected. Its only production consume() call reads upper levels in one full-size call; every in-tree reader of level 0 uses nextInt(); the query-time searcher does not use these iterators. Stored graphs are correct: a public-API test reads level 1 of a stored graph in chunks and gets every node once. This covers Lucene's own code; a custom HnswGraph implementation chooses its own level-0 iterator.
  • The downstream code that was read is safe (a handful of repositories read during the prior-report search, not a survey). An Elasticsearch GPU HNSW writer, a cuVS helper and lucene-knn-oxide call consume only on upper levels with one full-size call; OpenSearch k-NN and cuVS have their own iterators that advance (read, not executed).
  • How likely. Rare: no report since 9.5.0 (2023), and the callers found use the one-shot pattern. A caller that drains level 0 with while (hasNext()) consume(buf) hits it on any non-empty graph; how many such callers exist is not known.

Why it looks unintended

#
  • NodesIterator is a PrimitiveIterator.OfInt; consume is documented to "consume integers from the iterator" and return how many it wrote. Nothing limits it to one call.
  • Both sibling classes advance; in #11860 only the dense branch of the original method skipped cur += numToCopy.
  • No test, comment or CHANGES entry describes a non-advancing consume.
The full argument307 words
  • Contract. NodesIterator implements PrimitiveIterator.OfInt (HnswGraph.java:166); consume: "Consume integers from the iterator and place them into the dest array. @return The number of integers written to dest" (:179-185). Consuming from an iterator removes what was consumed; a method that leaves the cursor in place would be a peek or a copy, and nothing documents it that way.
  • The code expects chunks. The array and dense versions compute Math.min(size - cur, dest.length) and copy from cur, not from 0; the collection version fills until dest is full; all return the count written. A partial fill points to callers that call again.
  • History. #11860 (d0be9ab57c9, 2022-12-07) added consume as one method with two branches: the array branch ran cur += numToCopy, the dense branch (nodes == null) returned before it. The review on HnswGraph.java went in three steps: jpountz objected that "It's awkward to have a method that returns the entire set of data on an iterator" (2022-12-02); benwtrent first asked whether a one-shot copy from index 0 would do ("Would you prefer: public void consume(int[] dest) { System.arraycopy(nodes, 0, dest, 0, dest.length); } Or something?", the same day); then wrote "I added a "consume" method to this iterator. Seems to fit nicer to the iterator model." (2022-12-05). The merged method copies from cur, not from 0, returns how many it wrote and advances in its array branch. #12050 and #15425 moved the dense branch unchanged; git log -G'cur \+= numToCopy' shows no commit ever added the advance there.
  • Tests and docs. #11860 added no test that calls consume; no upstream test calls consume on a level-0 iterator today; no comment, CHANGES.txt or MIGRATE.md entry describes a non-advancing consume.
  • Independent implementations advance. cuVS, OpenSearch k-NN and a Go port implement consume with an advance (read).
The devil's-advocate check378 words

The case for intended (the strongest version, from the intended-behaviour verifier and the cross-model reviews):

  • (a) "Internal": the #15425 CHANGES entry (lucene/CHANGES.txt:1399, 10.4.0) says "Refactoring internal HnswGraph.NodesIterator", and the org.apache.lucene.util package-info says "APIs in this package are primarily internal and may change between releases" (util/package-info.java:35).
  • (b) The consume javadoc never literally says "advances".
  • (c) Every known caller does one full-size consume() on levels above 0, where the result is right, so consume is a one-shot bulk copy in practice.
  • (d) In the #11860 review, benwtrent's first proposal was exactly such a one-shot copy from index 0, with no cursor: public void consume(int[] dest) { System.arraycopy(nodes, 0, dest, 0, dest.length); } (2022-12-02).
  • (e) The stored graph is handed out through HnswGraphProvider#getGraph, and HnswGraphProvider is @lucene.experimental; stock Lucene is not affected at all.

Why it fails:

  • (a) "Internal" in CHANGES is prose, not an API tag. The package-info sentence covers org.apache.lucene.util, a different Java package; the org.apache.lucene.util.hnsw package-info says nothing about internal use. HnswGraph, NodesIterator, DenseNodesIterator and its constructor are public, have no @lucene.internal or @lucene.experimental tag, and sit in an exported package.
  • (b, c) The count, the copy from cur and the two advancing siblings strongly indicate cursor semantics. The one-shot callers explain why the bug stayed latent, not what was intended: the array branch written in the same commit advances.
  • (d) That was a question in review ("Would you prefer: ... Or something?"). What was merged copies from cur, returns how many it wrote and advances in its array branch, and its author described it as fitting "the iterator model", so the design moved from a one-shot copy to iterator semantics.
  • (e) @lucene.experimental says the API may change, not that it may return repeated ids. This point does make a "won't fix, internal" reply plausible.

How strong the case is: the adjudication records that all verifiers judged it weak, and the cross-model reviews rated it weak. A later cross-model fact check of the brief (OpenAI GPT-5.6) rated it moderate, because the contract is implied rather than written, HnswGraphProvider is experimental, the #15425 entry says "internal" and stock Lucene is unaffected; it still called it a narrow, latent correctness bug. It lowers the impact (minor, latent), not the validity.

Suggested fix

#

Recommended A. Advance the cursor in DenseNodesIterator.consume

Add cur += numToCopy; before the return in DenseNodesIterator.consume, as ArrayNodesIterator already does. One line; the repro then passes with assertions on and off, and 16 core HNSW test classes (321 tests) and the back-compat HNSW format tests (578 tests) pass.

       for (int i = 0; i < numToCopy; i++) {
         dest[i] = cur + i;
       }
+      cur += numToCopy;
       return numToCopy;
     }

A. Advance the cursor in DenseNodesIterator.consume (validated by the checks) (recommended)

#

       for (int i = 0; i < numToCopy; i++) {
         dest[i] = cur + i;
       }

  • No cost: one addition per call.

B. Fix A plus one javadoc sentence on NodesIterator#consume (validated by the checks)

C. Document consume as a one-shot copy instead

#

Trade-offs

Not recommended, not tested: it contradicts the two advancing implementations and PrimitiveIterator.OfInt, and keeps the chunked-loop trap.

Downstream note

#

Code outside Lucene that reads level 0 of an HNSW graph should walk it with hasNext() / nextInt(), or make one consume() into a size() buffer and then drop the iterator, until a fix ships.

How it was found

#

Non-formal: code reading. While writing a small model of the HNSW node-iterator API (each iterator as a cursor over a finite list), the finder checked nextInt and consume against all three implementations and saw that only the dense one never moves its cursor. A JUnit on the stock jars confirmed it; independent reproducers and reviewers then checked it.

The method in full155 words

Method: non-formal (code reading during modelling). The hunt unit on the HNSW graph format modelled HnswGraph.NodesIterator as a cursor over a finite sequence: nextInt() returns the element at the cursor and advances it, and consume(dest) copies up to dest.length elements from the cursor and advances it by the returned count. Checking that model against the three implementations showed that ArrayNodesIterator and CollectionNodesIterator follow it and DenseNodesIterator, the level-0 iterator of Lucene's in-memory and stored graphs, does not.

The finder wrote a JUnit on the stock main jars (a drain loop, a consume-then-nextInt check and an ArrayNodesIterator control): 2 of 3 failed with assertions on and off. It was then reviewed by a reviewer from another model family (OpenAI GPT-5.6), reproduced by independent verifiers (one through the stored graph of real indexes, from a package outside Lucene), judged, traced through every release since 9.5.0, and cut to the one-test repro on 645d4fe14a20.

LFV-159, snapshot of 2026-11-08

Registry title
HnswGraph.DenseNodesIterator.consume() (the level-0 node iterator of every HNSW graph) does not advance its cursor, so draining level 0 in chunks with consume() returns the first chunk forever and a nextInt() after consume() starts again at node 0 (latent: Lucene itself never calls consume() on level 0)
Area
util / HNSW graph node iterators (HnswGraph.NodesIterator, DenseNodesIterator)
Priority
Low, rank 1217: DenseNodesIterator.consume() never advances on HNSW level 0, which no Lucene code reads that way.
Impact class
minor
Impact note
Latent: only code outside Lucene that reads level 0 of an HNSW graph (HnswGraph.getNodesOnLevel(0) or getSortedNodes(0), on an OnHeapHnswGraph or on the stored graph from HnswGraphProvider#getGraph, default codec) with consume() in more than one call, or mixed with nextInt()/hasNext(), is hit: a 'while (hasNext()) consume(buf)' loop never ends and mixed use returns duplicate node ids, while one full-size consume() returns the right ids but leaves hasNext() true; Lucene's only consume() caller (Lucene99HnswVectorsWriter.writeMeta) reads upper levels only, no known downstream caller consumes level 0, any graph size triggers it, and every release since 9.5.0 is affected.
Summary
You take the level-0 node iterator of an HNSW graph (getNodesOnLevel(0), a DenseNodesIterator over the node ids [0, size)) and read it in chunks with consume(buf), expecting each call to hand out the next block of ids, as the javadoc ('Consume integers from the iterator') and the two sibling iterator classes do. Instead DenseNodesIterator.consume copies the block but never moves its cursor, so every call returns the same first block, hasNext() stays true and the loop never ends; a nextInt() after consume() also starts again at 0. Lucene's own code never calls consume() on level 0, so indexes and search results are not affected.
