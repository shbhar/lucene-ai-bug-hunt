BPIndexReorderer's javadoc usage example calls setForkJoinPool and a 2-argument reorder, both removed

The "Typical usage" example in the BPIndexReorderer javadoc (lucene-misc) still calls reorderer.setForkJoinPool(pool) and the 2-argument reorder(reader, targetDir). Both went away when the thread pool became a third argument of reorder, so the copied example fails to compile on every release since 9.12.0.

The finding in 30 seconds

#

The example is a <pre> block in the class javadoc. Javadoc does not compile such blocks, so when the API changed nothing failed, and Lucene's own tests already use the new 3-argument call.

  1. You want BP doc-id reordering and copy the class javadoc's "Typical usage": build a ForkJoinPool, call reorderer.setForkJoinPool(pool), then reorderer.reorder(SlowCodecReaderWrapper.wrap(reader), targetDir).
  2. You expect the two calls to compile and the reordering to run on your pool, as they did on 9.8.0 to 9.11.1.
  3. Instead javac reports 2 errors on 10.0.0 to 10.6.0 and main: there is no method setForkJoinPool, and reorder needs 3 arguments (CodecReader, Directory, Executor), not 2. On 9.12.x only the reorder error appears, because the setter still exists there, deprecated.
  4. Why: in 2024 (#13289) the pool moved from the setter to the new third Executor argument of reorder; Lucene's tests were updated, this example was not. Delete the setter line and pass pool as the third argument, and both calls compile.

Who is affected

#

Developers adopting the opt-in BP reordering tool of lucene-misc who start from its class javadoc: the copied calls fail to compile every time, on every release since 9.12.0. Documentation only: nothing runs differently, and the method javadoc of reorder shows the right signature.

Mechanism, terms and numbers386 words

BPIndexReorderer (lucene-misc) renumbers documents with recursive graph bisection so that similar documents sit together, which shrinks postings and can speed up queries. Its class javadoc, after describing the algorithm, says "Typical usage would look like this:" (line 73) and gives a 14-line example. Two of its lines name API that no longer exists: reorderer.setForkJoinPool(pool); (removed in 10.0.0) and reorderer.reorder(SlowCodecReaderWrapper.wrap(reader), targetDir) (the 2-argument form, removed in 9.12.0). The only public reorder is now reorder(CodecReader reader, Directory tempDir, Executor executor). Copied into a project, the two calls give cannot find symbol: method setForkJoinPool(java.util.concurrent.ForkJoinPool) and method reorder ... required: CodecReader,Directory,Executor; found: CodecReader,Directory on 10.0.0 to 10.6.0 and main, and the reorder error alone on 9.12.x. #13289 (2024-09-12) made both API changes and updated TestBPIndexReorderer to reorder(codecReader, dir, pool), but left the example. Passing the example's own pool as the third argument and deleting the setter line makes both calls compile; Lucene's 8 TestBPIndexReorderer tests pass with that javadoc change. Nothing in Lucene behaves wrongly; only the example is stale.

The real API

#

public CodecReader reorder(CodecReader reader, Directory tempDir, Executor executor) (line 838): "The provided Executor can be used to perform reordering concurrently. A value of null indicates that reordering should be performed in the current thread." and "The provided Executor must not reject tasks." A ForkJoinPool is an Executor, so the example's own pool fits the third argument unchanged. setForkJoinPool occurs nowhere under lucene/ except the javadoc line 83.

Why nothing caught it

#

Javadoc does not compile <pre> code and no test reads the example. TestBPIndexReorderer calls reorder(codecReader, dir, pool) (lines 122, 184) and reorder(codecReader, dir, null) (line 307).

Not claimed

#

That the block as a whole "does not compile": reader is never initialised, targetPath is undeclared and targetDir is declared twice; those are placeholders. The claim is about the two API calls.

Exposure and likelihood106 words
  • Who. Readers of the BPIndexReorderer class javadoc who copy its example, its only class-level usage guide. No query, document or index file reaches it.
  • Default vs opt-in. Opt-in: an expert, offline tool the application calls itself. No configuration or input changes the outcome: the copied calls always fail.
  • Scale. 1 error on 9.12.0 to 9.12.3, 2 errors on 10.0.0 to 10.6.0 and main.
  • Effect. A compile error, not wrong behaviour. The 9.12.x deprecation note on setForkJoinPool pointed to the 3-argument reorder; it went with the method in 10.0.0.
  • Priority. Low; the same kind of defect as the other stale javadoc examples of the same sweep.

Why it looks unintended

#
  • The block is introduced as "Typical usage would look like this:", and its two calls compiled verbatim on 9.8.0 to 9.11.1.
  • #13289 gave reorder an Executor argument and updated Lucene's tests to reorder(codecReader, dir, pool), but not this example; no CHANGES or MIGRATE entry mentions it.
  • Lucene has fixed stale javadoc examples before as ordinary doc fixes (LUCENE-9046, #12693).
The full argument178 words
  • Offered as working code. "Typical usage would look like this:" (line 73), with no pseudo-code marker.
  • Maintained as real code. #12568 (36432fa6724, 2023-09-19) replaced setForkJoinPool(ForkJoinPool.commonPool()) with the custom-factory pool, and 1d0edd76a5e ("Fix compilation under Java 11.", the same day) escaped the lambda's -> in it as -&gt; (the Java 11 problem of that day's dev@ thread) and replaced a test-only random().nextBoolean() with false.
  • The API change forgot it. #13289 (ff8b81afc59, Adrien Grand, 2024-09-12) removed setForkJoinPool on main (deprecated it on branch_9x: "Pass an executor to reorder(CodecReader, Directory, Executor) instead") and gave reorder the Executor argument. It updated TestBPIndexReorderer from setForkJoinPool(pool) + reorder(codecReader, dir) to reorder(codecReader, dir, pool); none of its hunks touches the class javadoc, and its discussion never mentions it.
  • Public API. The class is public, in an exported package, with no @lucene.experimental or @lucene.internal tag.
  • Precedent. LUCENE-9046 "Fix wrong example in Javadoc of TermInSetQuery"; #12693 "chore: update the Javadoc example in Analyzer" (2023-10-18); LUCENE-7763 removed an outdated javadoc comment (LUCENE-9046 and LUCENE-7763 were found by the cross-model reviewer, OpenAI GPT-5.6).
The devil's-advocate check120 words

Strongest case for "not a bug": the block is illustrative pseudo-code. It never compiled as written (reader uninitialised, targetPath undeclared, targetDir declared twice), Lucene does not compile javadoc snippets, lucene-misc changes freely, the error is loud and the method javadoc is right.

Why it fails: it explains the placeholders, not two exact method calls. A reader supplies reader and targetPath; no context makes a removed method compile. The calls were edited as real code, compiled verbatim until 9.11.1, and broke only because #13289 changed the API without touching the example. The verifiers and the adjudication called it real (the refute lens could not run anything; its "not real" is procedural); the adjudication rated it a Low documentation defect.

Trade-offs

None for users: documentation only. It keeps the pool as written (the devil's-advocate verifier's point); its custom thread factory came from #12568 ("Fix issues with BP tests and the security manager."), and whether the example still needs it is a separate question. reorder needs an Executor that does not reject tasks (line 834), which a live ForkJoinPool satisfies; the example never shuts the pool down (the devil's-advocate verifier's run did), and a pool.shutdown() after use would be optional polish (not run).
