kNN queries without a filter size each segment's heap from k: on 3 documents in one segment, k = Integer.MAX_VALUE throws and k = 2^28 runs out of memory

Since 9.10.0, unfiltered KnnFloatVectorQuery and KnnByteVectorQuery size each segment's heap from k before looking at the segment. On a 3-document, one-segment index, k = Integer.MAX_VALUE throws IllegalArgumentException and k = 2^28 exhausts a 2 GiB heap; with a non-match-all filter the same k returns all 3 (main).

The bug in 30 seconds

#

A kNN query asks every segment for its k nearest vectors. Since 9.10.0 the unfiltered query builds each segment's collector first, with a heap of k + 1 longs allocated up front, and only then looks at how many vectors the segment holds. Nothing caps k at the segment's size.

  1. Index 3 documents with a float vector (one segment, default codec) and search new KnnFloatVectorQuery("v", target, k) with no filter, on a plain IndexSearcher.
  2. k = 1000 returns all 3 documents, as the javadoc ("the number of documents to find") and the upstream testFindAll promise. You expect the same for k = Integer.MAX_VALUE, the usual "all" value; 9.9.2 gives exactly that for the unfiltered query.
  3. Instead the query builds the segment's collector first, with a heap of k + 1 longs, and only then reads the segment's vector count. k = Integer.MAX_VALUE throws IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: 2147483647.
  4. Smaller huge k values allocate instead: k = 2^24 reserves 128 MiB to return 3 hits, and k = 2^28 throws OutOfMemoryError with a 2 GiB heap. Four segments cost about 9 times one.
  5. With a filter that matches every document, the same k = Integer.MAX_VALUE returns the 3 hits: that path caps its queue at min(k, matches) (since 9.11.0). Lucene capped k at the segment's vector count until 9.9.2; #12962 dropped the cap. The join DiversifyingChildren*KnnVectorQuery has the same flaw since 9.8.0, and SeededKnnVectorQuery also sizes its seed collector by k.

Who is affected

#

Anyone on 9.10.0 to 10.5.2 or main who runs KnnFloatVectorQuery or KnnByteVectorQuery (also seeded or patience variants) without a filter with a very large k, such as Integer.MAX_VALUE for "all" or a client's k forwarded unchecked; the join DiversifyingChildren*KnnVectorQuery since 9.8.0. Default codec and searcher. Ordinary k (thousands) wastes only kilobytes; no wrong hits were seen.

Mechanism, terms and numbers858 words

KnnFloatVectorQuery accepts any k >= 1 ("the number of documents to find"), and a k larger than the index returns every vector: k = 1000 over a 3-document index gives 3 hits. Since 9.10.0 the unfiltered (approximate) path builds each segment's collector with a heap sized from k (k + 1 longs on a single segment) before it looks at how many vectors the segment has. So on a single-segment index k = Integer.MAX_VALUE throws IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: 2147483647 from an internal heap (with several segments it runs out of memory instead), k = 2^28 over the same 3 documents throws OutOfMemoryError with a 2 GiB heap, and k = 2^24 allocates about 128 MiB to return 3 hits. On main the same k works on that index with a filter that is not match-all (the exact path caps its queue at Math.min(k, cost), since 9.11.0) and through LeafReader#searchNearestVectors(..., int k, ...), which still caps k at the vector count. Up to 9.9.2 the query went through that method, and the readers before it carried the comment "bound k by total number of vectors to prevent oversizing data structures"; #12962 (9.10.0) made the query build its own collector and the cap was lost. The join DiversifyingChildren{Float,Byte}KnnVectorQuery has the same shape and has been unbounded since it was added in 9.8.0, and SeededKnnVectorQuery also sizes its seed collector by k. No wrong hits were seen: every search either returned the expected hits or threw.

Terms

#
  • Segment collector: for each segment, the kNN query creates a KnnCollector through a KnnCollectorManager. The default one, TopKnnCollector, keeps the best hits in a NeighborQueue, which is a TernaryLongHeap.
  • Approximate vs exact path: without a filter, every segment takes the approximate path (approximateSearch). With a filter, a segment whose matching documents are no more than its share of k takes the exact path (exactSearch), which scores the matches directly.

The bug

#
  1. The constructor rejects only k < 1 (AbstractKnnVectorQuery.java:67-68). Without a filter (or with one that rewrites to MatchAllDocsQuery, which is dropped, :87-103), getLeafResults calls approximateSearch (:252-254).
  2. KnnFloatVectorQuery.approximateSearch calls knnCollectorManager.newCollector(...) first (KnnFloatVectorQuery.java:107-108), then reads the vector values (:110) and checks Math.min(knnCollector.k(), floatVectorValues.size()) == 0 (:115): the remnant of the old cap, after the allocation. KnnByteVectorQuery is the same (:106-107, :114).
  3. OptimisticKnnCollectorManager turns k into perLeafTopK from the segment's share of the index (AbstractKnnVectorQuery.java:319-347); for one segment that is k itself (computed in float, so a k above 2^24 is rounded to the nearest float). TopKnnCollectorManager passes it on unchanged: new TopKnnCollector(k, visitedLimit, searchStrategy) (knn/TopKnnCollectorManager.java:46, :52).
  4. TopKnnCollector builds new NeighborQueue(k, false) (TopKnnCollector.java:45), and TernaryLongHeap(k) throws IllegalArgumentException for k >= ArrayUtil.MAX_ARRAY_LENGTH ("Throw exception to prevent confusing OOME") or allocates new long[k + 1] at once (util/TernaryLongHeap.java:56-69).
  5. With several segments, the optimistic re-entry pass builds two more full-k collectors per re-entered segment (ReentrantKnnCollectorManager, AbstractKnnVectorQuery.java:128-130, :433-476).
  6. Join: DiversifyingNearestChildrenKnnCollectorManager builds new DiversifyingNearestChildrenKnnCollector(k, ...) (:65-66, :77-78), whose NodeIdCachingHeap(k) allocates three arrays of k + 1 entries and a k-sized hash map (DiversifyingNearestChildrenKnnCollector.java:61, :140-153).
  7. Seeded: SeededKnnVectorQuery first builds a seed collector, new TopScoreDocCollectorManager(k, null, Integer.MAX_VALUE).newCollector() (SeededKnnVectorQuery.java:315-316), with the query's full k on every segment; its TopScoreDocCollector allocates new TernaryLongHeap(numHits, ...) at once (TopScoreDocCollector.java:44).

Where Lucene does cap the same request: the exact path, Math.min(k, Math.toIntExact(acceptIterator.cost())) (AbstractKnnVectorQuery.java:373, #13184, from 9.11.0); LeafReader#searchNearestVectors(..., int k, ...), k = Math.min(k, ...size()) (index/LeafReader.java:288, :332, :376); regular top-N search, IndexSearcher#searchAfter caps numHits at max(1, maxDoc) (IndexSearcher.java:587-597).

Exposure and likelihood268 words
  • Who is hit. Unfiltered KnnFloatVectorQuery / KnnByteVectorQuery (or with a filter that rewrites to MatchAllDocsQuery) on 9.10.0 through 10.5.2 and main; DiversifyingChildrenFloatKnnVectorQuery / DiversifyingChildrenByteKnnVectorQuery on 9.8.0 and later. Default codec, default IndexSearcher, no setting. SeededKnnVectorQuery and PatienceKnnVectorQuery (since 10.2.0) and KnnFloat16VectorQuery (main only) fail the same way on main (executed on main only).
  • Trigger. k = Integer.MAX_VALUE to mean "all" (an idiom IndexSearcher supports: TestIndexSearcher.testHugeN), a k derived from the index size, or a server that forwards a client's k unchecked.
  • Effect. On a single-segment index, k at or above ArrayUtil.MAX_ARRAY_LENGTH always throws IllegalArgumentException on the first search; with several segments the first pass sizes each heap by the segment's share of k, so it runs out of memory instead (4 segments, 2 GiB heap). Below that, a single-segment search reserves about 8 bytes per unit of k before it collects anything: 128 MiB for k = 2^24, a 512 MiB heap exhausted at k = 2^26, a 2 GiB heap at k = 2^28. More segments (about 9x for 4: first-pass heaps by each segment's share, plus two full-k collectors per re-entered segment) and concurrent searches add up. After a caught OutOfMemoryError a follow-up search on the same searcher worked; with -XX:+CrashOnOutOfMemoryError the JVM aborted.
  • Not affected. No wrong hits were seen; on the 3-document index a filter that is not match-all takes the bounded exact path; ordinary k values cost kilobytes.
  • Scale. None: 3 documents in one segment.
  • How likely. Rare: only a very large k fails, and the Integer.MAX_VALUE case is loud on the first search; nothing was reported since 9.10.0 (2024-02).

Why it is a bug, not intended

#
  • The javadoc accepts any k >= 1 ("the number of documents to find"), and testFindAll expects a k above the document count to return every document.
  • Until 9.9.2 Lucene capped k at the segment's vector count "to prevent oversizing data structures"; #12962 dropped it, and no review comment mentions it.
  • Since 9.11.0 a non-match-all filter makes the same k work.
The full argument297 words
  • Contract. KnnFloatVectorQuery: "@param k the number of documents to find", "@throws IllegalArgumentException if <code>k</code> is less than 1" (KnnFloatVectorQuery.java:60-61, :73-75; KnnByteVectorQuery.java:59-60, :72-74). These constructors are not @lucene.experimental. The heap's "initialCapacity must be > 0 and < 2147483630" for an accepted k is not the documented failure.
  • Upstream test. BaseKnnVectorQueryTestCase.testFindAll: "Tests that a AbstractKnnVectorQuery whose topK &gt;= numDocs returns all the documents in score order" (k = 10 over 3 documents, :178-194).
  • A deliberate cap, lost silently. 9.0-9.7 readers: "// bound k by total number of vectors to prevent oversizing data structures" / k = Math.min(k, fieldEntry.size()); (9.7.0 Lucene95HnswVectorsReader.java:288-289, from LUCENE-9614 / #413). 9.8-9.9: the cap lived in LeafReader#searchNearestVectors(..., int k, ...) (9.9.2 LeafReader.java:253), which the query called (9.9.2 KnnFloatVectorQuery.java:82); main still has it (LeafReader.java:288). #12962 (9.10.0) made the query build its own collector; reviewers asked to keep the int-k LeafReader method unchanged, and none of the 22 conversation or 40 review comments discusses the cap.
  • Siblings are capped. #13184 (9.11.0) capped the exact path of the same class (AbstractKnnVectorQuery.java:373) because "the number of candidates is actually lower than k". Until then that path failed for a huge k too (9.9.2, 9.10.0), so the project has bounded this kind of k-sized preallocation before. LUCENE-4938 extended IndexSearcher's min(maxDoc, n) cap to the sorted searches and added TestIndexSearcher.testHugeN ("should not throw exception"), which runs search(query, Integer.MAX_VALUE).
  • Inconsistent (from 9.11.0). On one index, k = Integer.MAX_VALUE and 2^28 return all hits with a filter matching every document and through LeafReader#searchNearestVectors(int k), but throw without the filter (this doc's test; a verifier's contrast probe).
  • The manager API speaks of per-leaf sizing. KnnCollectorManager#newOptimisticCollector: "generally with a specific k value, scaled per leaf statistics".
The devil's-advocate check209 words

The strongest case for "intended": top-k naturally needs O(k) storage; TopKnnCollector is @lucene.experimental; the heap's IllegalArgumentException is deliberate ("to prevent confusing OOME"); maintainers have said Lucene targets "some reasonable value of k" (#9588), that k = Integer.MAX_VALUE "will not only run in O(maxDoc) time but also use O(maxDoc) memory" (#12679), and, on dev@ (2022-11), of a very large k, "something that I would like to be documented as not recommended"; downstream engines bound k; SECURITY.md leaves bounding resource-consuming input to the application.

Why it fails: here the storage does not grow with the index at all, because it is reserved per segment before the segment's size is known; 3 documents need 2 GiB. Lucene capped exactly this on purpose until 9.9.2 and still caps it on the filtered path and in LeafReader, and the remarks above were made while the cap existed, so they assume O(maxDoc). The heap's guard only turns an OOME into an exception; it does not make k = Integer.MAX_VALUE a documented failure of the query. Every reviewer rejected the intended-behaviour argument; the latest cross-model fact check rated it moderate, mainly as an argument about which fix to choose (a documented high upper bound would not contradict testFindAll, which uses k = 10).

Suggested fix

#

Recommended Cap the per-segment k at the segment's maxDoc in both collector managers and the seeded query's seed collector

Cap each segment's collector at min(k, maxDoc) in TopKnnCollectorManager, in the join DiversifyingNearestChildrenKnnCollectorManager and in SeededKnnVectorQuery's seed collector (+22/-5 lines in three files). Validated with gradle on main: the repro tests and 8 large-k variant tests pass with assertions on and off, the 13 closest kNN suites (323 tests) pass, and format and lint pass.

All options and trade-offs4 options · 875 words

One fix was built and validated, first in two files and then completed with the seeded query; the alternatives are untested.

Cap the per-segment k at the segment's maxDoc in both collector managers and the seeded query's seed collector (validated by the checks) (recommended)

#

A segment cannot return more hits than it has documents. TopKnnCollectorManager.newCollector and newOptimisticCollector pass perLeafK(k, context) instead of k, DiversifyingNearestChildrenKnnCollectorManager does the same in both methods, and SeededKnnVectorQuery's collector manager sizes its seed collector the same way (an unpublished file = fix.diff + seeded-cap.diff). The TopKnnCollectorManager change covers KnnFloatVectorQuery, KnnByteVectorQuery, KnnFloat16VectorQuery, the optimistic re-entry pass and PatienceKnnVectorQuery; SeededKnnVectorQuery builds its seed collector from the full k on every segment, so it needs the third change (executed).

// TopKnnCollectorManager: newCollector and newOptimisticCollector
return new TopKnnCollector(perLeafK(k, context), visitedLimit, searchStrategy);

/** A leaf cannot return more than {@code maxDoc} hits, so do not size its collector by a larger k. */
private static int perLeafK(int k, LeafReaderContext context) {
  return Math.max(1, Math.min(k, context.reader().maxDoc()));
}

// DiversifyingNearestChildrenKnnCollectorManager: the same helper, in both methods
return new DiversifyingNearestChildrenKnnCollector(
    perLeafK(k, context), visitedLimit, searchStrategy, parentBitSet);

// SeededKnnVectorQuery.SeededCollectorManager.newCollector: the seed collector
// a leaf cannot return more than maxDoc seeds, so do not size the collector by a larger k
int seedK = Math.max(1, Math.min(k, ctx.reader().maxDoc()));
TopScoreDocCollector seedCollector =
    new TopScoreDocCollectorManager(seedK, null, Integer.MAX_VALUE).newCollector();

Trade-offs

  • Same hits. A segment has at most maxDoc vectors, so min(k, maxDoc) slots hold every hit. The reader's choice between graph search and an exhaustive scan (knnCollector.k() < numVectors, Lucene99HnswVectorsReader.java:373) does not change: if k >= numVectors, then min(k, maxDoc) >= numVectors too. A segment cannot hold more than maxDoc seed hits either. Math.max(1, ...) keeps k >= 1 for an empty segment.
  • Bound is maxDoc, not the vector count as before 9.10.0 (the managers do not know the field), so a large segment can still reserve 8 bytes per document for a huge k: O(maxDoc), the cost maintainers described in #12679.
  • Custom KnnCollectorManager implementations are not covered. No benchmark was run; the change adds one Math.min per segment. Add a CHANGES entry under Bug Fixes.
  • Backports (read): branch_10x and branch_10_6 have the same manager code as main. Older lines also allocate a global BlockingFloatHeap(k) per multi-segment query (TopKnnCollectorManager from 9.10.0, the join manager in 9.12.3, both up to 10.2.2), which a backport must bound too; 9.8.x and 9.9.x build the join collector directly in the query; SeededKnnVectorQuery exists from 10.2.0.

Cap at the field's vector count, as before 9.10.0 (untested)

#

In approximateSearch, read the vector values first and size the collector by min(k, values.size()), in the core and the join queries.

Trade-offs

The pre-9.10 behaviour of the core queries (the join queries were unbounded before 9.10 too) and the tightest bound, but KnnCollectorManager#newCollector has no k parameter, so it needs an API change (or routing a bounded k through newOptimisticCollector).

Grow the heap lazily up to k (untested)

#

Start NeighborQueue / TernaryLongHeap small and grow it as hits arrive, up to k.

Trade-offs

Also helps large segments with a huge k, but the heap's capacity is its overflow bound today (TernaryLongHeap.java:93-103), so it needs a separate maximum, and it touches the hot path of every kNN search; needs benchmarks. The heap's growth has its own limit (TernaryLongHeap stops growing at 715,827,883 elements, registry LFV-069).

Reject or document a maximum k (not recommended)

#

Validate k against an upper bound in the constructor, or document one.

Trade-offs

The query does not know the index when it is built, and a bound would not fit the filtered path, LeafReader's int-k method and IndexSearcher (testHugeN), which all accept any k (testFindAll uses only k = 10, so a high documented bound would not contradict it). Until a fix ships, applications can cap k themselves, for example at reader.maxDoc() (read, not executed); that caps by the whole index, so on several segments each segment's collectors can still be sized by the index's maxDoc.

Downstream note

#

Downstream: Elasticsearch and OpenSearch cap k at 10,000, while Solr's kNN parser reads topK with no upper bound (source reading only), so an application that forwards a client's k should cap it, for example at the index size.

How it was found

#

A hunt for accepted-parameter boundaries scanned the argument checks of Lucene's public APIs and probed the ranges they accept: the kNN query constructors reject only k < 1. End-to-end runs with very large k then hit the failure, and a JUnit test reproduced it on the stock jars.

The method in full152 words

Method: a static and dynamic boundary scan (the finder's label: semi-formal; no model checker, solver or prover found it).

  • A static guard inventory of the real jars: a JDK ClassFile API pass over 27 core and non-sandbox module jars listed 1,231 public entry points whose bytecode reaches an IllegalArgumentException, with each guard's parameters and constants.
  • The kNN query constructors reject only k < 1 (AbstractKnnVectorQuery.java:67-68), so every k up to Integer.MAX_VALUE is accepted.
  • A scratch driver (its output was not saved) then ran KnnFloatVectorQuery, KnnByteVectorQuery and the two DiversifyingChildren* queries end to end on the stock jars with k in {5, 1000, 2^20, 2^27, 2^28, Integer.MAX_VALUE - 9, Integer.MAX_VALUE}, and a public-API JUnit test witnessed the failure (2026-10-26).
  • The same scan found the pattern at LatLonPoint.nearest(..., n = Integer.MAX_VALUE) and RescoreTopNQuery(..., n = Integer.MAX_VALUE) (an IllegalArgumentException from PriorityQueue); those are separate sites and were not filed.

Bug record

LFV-454, snapshot of 2026-10-29

Registry title
kNN vector queries size each segment's result heap from the requested k, not from what the segment can return, so k = Integer.MAX_VALUE throws IllegalArgumentException and k = 2^28 runs out of a 2 GiB heap on a 3-document index (core KnnFloat/KnnByteVectorQuery without a filter: regression in 9.10.0; join DiversifyingChildren*KnnVectorQuery: since 9.8.0)
Area
search / kNN vector queries (per-segment collector sizing: AbstractKnnVectorQuery, TopKnnCollectorManager, TopKnnCollector; join DiversifyingNearestChildrenKnnCollectorManager)
Priority
Low, rank 325: Core default kNN queries throw for the k=Integer.MAX_VALUE 'all' idiom and allocate memory in proportion to k, a loud MAX_VALUE-idiom core failure that is more reachable than LFV-394, so it heads that group.
Impact class
crash
Impact note
Applications on 9.10.0 through 10.5.2 or main that run a KnnFloatVectorQuery or KnnByteVectorQuery without a filter (default codec, IndexSearcher and query, no setting needed), or on 9.8.0 and later a DiversifyingChildrenFloat/ByteKnnVectorQuery, with a very large k get an IllegalArgumentException from an internal heap for k = Integer.MAX_VALUE (the usual Java 'all' value), and each search reserves heap in proportion to k before any segment's size is consulted (about 8 bytes per unit of k on a single-segment index; four segments cost about 9 times as much), so one k = 2^24 search over 3 vectors allocates 128 MiB and k = 2^28 runs out of a 2 GiB heap; ordinary k values (up to the thousands) waste only kilobytes, results are never wrong, no index size is needed, Elasticsearch and OpenSearch cap k at 10,000, and Solr's kNN parser does not bound topK (read in source only, not run).
Summary
You run a KnnFloatVectorQuery with a k larger than the index, for example k = Integer.MAX_VALUE to mean 'all vectors', and expect every vector back, as k = 1000 over 3 vectors gives, and as 9.9.2 gives for any k. Instead each segment's collector is built with a heap sized from k (k + 1 longs on a single-segment index) before the segment's vector count is looked at: k = Integer.MAX_VALUE throws IllegalArgumentException('initialCapacity must be > 0 and < 2147483630; got: 2147483647') from TernaryLongHeap, and k = 2^28 over a 3-document index throws OutOfMemoryError with a 2 GiB heap. Lucene used to cap k at the segment's vector count ('bound k by total number of vectors to prevent oversizing data structures'); a search speed-up change dropped that cap in 9.10.0, and the join DiversifyingChildren*KnnVectorQuery never had it.
