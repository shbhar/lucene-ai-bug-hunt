The collation package overview's Danish Sorting example calls Sort.setSort, removed in 9.0.0, so it does not compile

The Danish Sorting example on the collation package overview still builds its sort with new Sort() plus sort.setSort(...), a method Lucene removed in 9.0.0, so copied code fails with cannot find symbol: method setSort(SortField). On main it is the page's only remaining error; the fix is one line.

The finding in 30 seconds

#

The page's three "Example Usages" are plain code blocks in the package's javadoc. Lucene's javadoc build renders them as text without compiling them, so when Sort lost its setters in 9.0.0 the build did not notice.

Two things to know first

#
  1. The collation package turns each value into a binary collation key from a java.text.Collator, so a plain sort on that field gives the language's order. CollationDocValuesField stores the key for sorting.
  2. Sort describes how hits are ordered. Since 9.0.0 it is immutable: you pass the SortFields to its constructor, and there is no setter.

The finding, step by step

#
  1. You copy the Danish Sorting example from the collation package overview (analysis-common). It indexes HAT, HUT, HÅT, HØT and HOT with tracers A to E and sorts all hits on a collated field.
  2. You expect it to compile, like the page's Farsi and Turkish examples, and to return the tracers in Danish order A, E, B, D, C (Danish puts Ø before Å; code-point order would give A, E, B, C, D).
  3. Instead javac stops at one line, sort.setSort(new SortField("contents", SortField.Type.STRING)), with cannot find symbol: method setSort(SortField): Sort became immutable in 9.0.0 and lost both setSort methods.
  4. Written as Sort sort = new Sort(new SortField("contents", SortField.Type.STRING));, the example compiles, runs and returns A, E, B, D, C.
  5. Every release page from 9.0.0 to 10.6.0 has the call too. #16904 updated the page's other stale API uses on main on 2026-11-02 and kept this one.

Who is affected

#

Developers who adopt the opt-in collation package and copy its Danish Sorting example: it fails to compile every time, on every release from 9.0.0 to 10.6.0 and on main. Documentation only: the error is loud, names the missing method, and MIGRATE.md names the replacement.

Mechanism, terms and numbers421 words

The analysis-common collation package overview shows three "Example Usages". Its Danish Sorting example indexes five words with CollationKeyAnalyzer and CollationDocValuesField and sorts the hits in Danish order. It builds the sort with new Sort() and then sort.setSort(new SortField("contents", SortField.Type.STRING)) (package-info.java:90-91). Sort became final and immutable in 9.0.0 (LUCENE-9325, 9e9c3bd249e), which removed both setSort methods without deprecating them first, so the copied example fails to compile with cannot find symbol: method setSort(SortField). #16904 (merged 2026-11-02, main only) brought the page's examples up to current APIs and edited this very line, but kept setSort; on main it is the only error left on the page, and on the 9.0.0 to 10.6.0 release pages it is one of several stale API uses. Written as new Sort(new SortField("contents", SortField.Type.STRING)), the example compiles, runs and returns the documented order A, E, B, D, C. The defect does not change how Lucene runs; only the page is stale.

The page

#

lucene/analysis/common/src/java/org/apache/lucene/collation/package-info.java heads the section "Example Usages" (:37). The Danish Sorting block (:67 heading, :69-:98) is a plain <pre><code class="language-java"> block. Lines :90-:91:

Sort sort = new Sort();
sort.setSort(new SortField("contents", SortField.Type.STRING));

The API

#

Sort.java:34 declares public final class Sort. Its constructors are Sort() (:54, the relevance sort, this(SortField.FIELD_SCORE)) and Sort(SortField...) (:63). Its other public members (getSort() :75, rewrite(...) :88, needsScores() :129, the static getPrimarySortField(...) :145, the RELEVANCE and INDEXORDER constants :41, :44, and the Object overrides) include no setter: there is no setSort.

Why the build did not notice

#

The example is HTML text inside a javadoc comment. Lucene's renderJavadoc task runs the javadoc tool (build-tools/build-infra/.../RenderJavadocPlugin.java:91-98), which renders a <pre> block as text and does not compile the Java in it.

The removal

#

9e9c3bd249e "LUCENE-9325: Make Sort final (#338)" (Alan Woodward, 2021-10-06) removed setSort(SortField) and setSort(SortField...), which carried no @Deprecated before. It touched CHANGES.txt, MIGRATE.md, Sort.java, TopFieldCollector.java and two tests, not this page. CHANGES.txt:4822 (9.0.0): "Sort is now final, and the setSort() method has been removed". MIGRATE.md:1638-1641, "Sort is immutable": "Rather than using setSort() to change sort values, you should instead create a new Sort instance with the new values."

The last edit

#

#16904 (e1faeba08bd, by Deepcodr, merged by vsop-479 on 2026-11-02, main only) rewrote the page for current APIs. Following vsop-479's review it changed this line's SortField.STRING to SortField.Type.STRING and added the CollationDocValuesField the sort needs, but kept setSort.

Why it looks unintended

#
  • The section is titled "Example Usages", with no note that the code is pseudocode or targets an old release.
  • #16904 (merged 2026-11-02) set out to "update collation package examples to current APIs" and edited this very line, but never mentions setSort.
  • MIGRATE.md ("Sort is immutable") tells users to create a new Sort; the page's Farsi and Turkish examples compile.
The full argument98 words
  • Offered as working code. "Example Usages" (package-info.java:37), no pseudocode or version note.
  • An oversight, not a decision. #16904's review commented on this line ("SortField.STRING is also stale, we should use SortField.Type.STRING", vsop-479). Its body, 8 reviews, 7 line comments and 2 issue comments never mention setSort, and nothing was posted after the merge.
  • The contract says the opposite. MIGRATE.md:1638-1641 tells users to construct a new Sort.
  • Only this line is wrong. In the same compile check the Farsi and Turkish blocks compile on main, and with the one-line fix all three compile and run.
The devil's-advocate check129 words

Strongest case for "not a bug": the blocks are raw <pre> fragments without imports that call JUnit's assertEquals; Lucene never promises they compile (#9534, LUCENE-8488, asking to keep examples in sync with compiled code, is still open); the removal was deliberate and documented in CHANGES and MIGRATE; and the analysis-icu overview has the same call.

Why it fails: imports and the assertion are context any reader supplies, but no context makes setSort compile; the page offers the code as current usage, and a merged PR has just tried to make it so; the analysis-icu page is itself a registered documentation defect (LFV-992), not evidence of design. A reviewer from another model family (OpenAI GPT-5.6) rated the case "weak", and every check rejected it: a documentation defect, minor.

Suggested fix

#

Recommended Construct the Sort with its field (validated)

Javadoc only, one line: replace new Sort(); plus sort.setSort(...) with Sort sort = new Sort(new SortField("contents", SortField.Type.STRING));. The patched page's block then compiles and runs in Danish order, and the collation tests, renderJavadoc and the format check pass.

- *   sort.setSort(new SortField("contents", SortField.Type.STRING));
+ *   Sort sort = new Sort(new SortField("contents", SortField.Type.STRING));
