Shape doc-values box queries stay cacheable after a doc-values update, so the query cache returns the old matches

LatLonShape and XYShape.newSlowDocValuesBoxQuery read shapes from doc values but tell the query cache they are always cacheable. Move a shape out of the box with updateDocValues, reopen, and a cached count or filter still returns 5 hits instead of 4 until a merge or the entry leaves the cache.

The bug in 30 seconds

#

The query cache remembers, per segment, which documents a filter matched. After an in-place doc-values update the segment keeps its cache identity, so every query that reads doc values must tell the cache not to reuse the old answer. The shape doc-values box query never does.

  1. Index 20 documents with a doc-values-only LatLonShape field (createDocValueField): doc i is a small square at (i, i). newSlowDocValuesBoxQuery over latitude and longitude -1 to 4.5 matches docs 0-4: 5 hits, and the query cache stores that answer for the segment.
  2. Move doc 0's square to (60, 60) in place with IndexWriter#updateDocValues and reopen. You expect 4 hits, which is what a searcher without a cache returns.
  3. Instead the cached search returns 5: doc 0 still matches. The same with XYShape, on every release from 9.4.0 to 10.5.2 and on main (assertions off also checked on 9.4.0, 10.0.0, 10.5.2 and main).
  4. Why: the query reads each shape from doc values, but its isCacheable comes from SpatialQuery and is always true. The cache keys its entries on the segment core, which a doc-values update does not change, so it reuses the old answer.
  5. Only uses that do not need scores read the cache (a filter or exclusion clause, ConstantScoreQuery, count()); a relevance-scored search is correct. The stale answer lasts until the segment is merged into a new one, the entry is evicted or the cache is cleared. On 9.4.0-10.5.2 the default IndexSearcher cache is enough (12,000-document segment: 5 instead of 4, run on 9.4.0, 9.12.3, 10.0.0 and 10.5.2); main has no default cache, so it needs an installed one.

Who is affected

#

Applications with a doc-values-only LatLonShape or XYShape field that move shapes with updateDocValues and repeat newSlowDocValuesBoxQuery as a filter, exclusion or count across reopens. On 9.4.0-10.5.2 the default searcher cache is enough for large segments (10,000+ documents and a big share of the index); main needs an installed cache. Indexed shape fields cannot be updated, so they are safe.

Mechanism, terms and numbers596 words

LatLonShape.newSlowDocValuesBoxQuery and XYShape.newSlowDocValuesBoxQuery build subclasses of BaseShapeDocValuesQuery extends SpatialQuery, which read every candidate's shape from BinaryDocValues (BaseShapeDocValuesQuery.java:64). Their weight's isCacheable is SpatialQuery's, which returns queryIsCacheable(ctx) (SpatialQuery.java:221-222), a constant true (:146-148) that no class overrides. SegmentCacheable requires doc-values readers to return DocValues#isCacheable, because "Updated doc values fields are not suitable for caching" (SegmentCacheable.java:30-32), and LRUQueryCache trusts isCacheable and keys entries on the segment's core cache helper (LRUQueryCache.java:816-834), which by design ignores doc-values updates (LeafReader.java:65-70). So after IndexWriter#updateDocValues moves a document's shape in a doc-values-only field and the reader is reopened, a cache entry built before the update keeps being served to every use that does not need scores (filter and exclusion clauses, ConstantScoreQuery, count()): in the repro 5 hits instead of 4, the moved document still matching, until the segment is merged into a new one or the entry is evicted or cleared. Relevance-scored searches skip the cache and are correct. All 29 releases from 9.4.0 to 10.5.2 fail the repro with an installed cache, and on these releases the default IndexSearcher cache is enough (zero configuration run on 9.4.0, 9.12.3, 10.0.0 and 10.5.2); main needs an installed cache (no default since GITHUB#14187). The introducing PR (#1017) had a DocValues.isCacheable check in its first commit, which an in-PR refactor dropped. A one-method override fixes it.

Terms

#
  • Query cache: LRUQueryCache stores, per segment, the documents a filter clause matched (and their count), keyed on the query and the segment's core cache key (LRUQueryCache.java:827-834). The searcher puts it in front of a query only where scores are not needed (IndexSearcher.java:979-981): filter and exclusion clauses, ConstantScoreQuery, count(). Before it looks anything up, it asks the weight whether the segment may be cached: Weight#isCacheable(ctx) (:816, and :903 for count()).
  • Core cache key: identifies a segment's immutable core. "Two readers that have the same data but different sets of deleted documents or doc values updates may be considered equal" (LeafReader.java:65-70). After updateDocValues and a reopen, the segment keeps its key.
  • The rule: "Objects that depend on doc values should return DocValues#isCacheable(LeafReaderContext, String...), which will check to see if the doc values fields have been updated. Updated doc values fields are not suitable for caching" (SegmentCacheable.java:30-32). DocValues.isCacheable returns false once the field has a doc-values update generation (DocValues.java:340-346).
  • Shape doc values: LatLonShape.createDocValueField and XYShape.createDocValueField store a shape as BINARY doc values only, "without creating indexable fields" (LatLonShape.java:89-92; ShapeDocValuesField.java:46-52, @lucene.experimental at :38). IndexWriter#updateDocValues accepts BINARY updates on such a field (IndexWriter.java:2081-2127).

The bug

#
  1. newSlowDocValuesBoxQuery (LatLonShape.java:262-284, XYShape.java:211-217) builds a LatLonShapeDocValuesQuery or XYShapeDocValuesQuery, both final subclasses of BaseShapeDocValuesQuery extends SpatialQuery (BaseShapeDocValuesQuery.java:40).
  2. The scorer reads reader.getBinaryDocValues(field) (:64) and decodes each candidate's shape in matches() (:77-79). The class overrides only getScorerSupplier.
  3. The weight is SpatialQuery's ConstantScoreWeight: isCacheable(ctx) returns queryIsCacheable(ctx) (SpatialQuery.java:221-222), which returns true (:146-148). Nothing in lucene/ overrides it.
  4. After the update and a reopen, isCacheable still says true for the updated segment, the core cache key is unchanged, and LRUQueryCache returns the entry computed from the old shapes: the old doc-id set, or for count() the old count (LRUQueryCache.java:914-924).
  5. Deletions are not affected: live docs are applied on top of a cached set, and count() skips the cache on a segment with deletions (:893-896); a later delete was honoured in a control run.
Exposure and likelihood561 words
  • Who is exposed. Applications that keep shapes in a doc-values-only LatLonShape or XYShape field, move them in place (IndexWriter#updateDocValues or updateBinaryDocValue; for example moving geofences or re-geocoded assets) and repeat the same newSlowDocValuesBoxQuery as a filter, an exclusion clause or a count (any use that does not need scores) across reopens.
  • What it takes. (a) A doc-values-only field: a field name that also has indexed shape triangles cannot be updated in place (verifyOrCreateDvOnlyField, IndexWriter.java:2097; points rejected at FieldInfos.java:619-626), so the "indexed + doc values" pairing is not affected. (b) An in-place update. (c) The same query cached before the update. (d) A query cache that survives the reopen.
  • Default vs opt-in. On 9.4.0-10.5.2 zero configuration is enough: the default IndexSearcher cache is a JVM-wide LRUQueryCache (1,000 queries, at most 32 MB; 10.5.2 IndexSearcher.java:96-99) that caches segments of at least 10,000 documents holding more than half the average segment size (9.6.0 onward; 10.5.2 LRUQueryCache.java:175-198; on 9.4.0-9.5.0 at least 10,000 documents and at least 3% of the index, 9.4.0 LRUQueryCache.java:150, :170-171), and the default policy caches this query after 5 uses (10.5.2 UsageTrackingQueryCachingPolicy.java:122-137). A zero-configuration program with a 12,000-document segment (accepted by both size rules) prints 5 instead of 4 on 9.4.0, 9.12.3, 10.0.0 and 10.5.2; it was not run on the other 25 releases. The unreleased branch_10_6 and branch_10x still have that default cache (read only). On main "Caching is disabled by default" (IndexSearcher.java:82-84, GITHUB#14187, unreleased), so it needs setQueryCache or setDefaultQueryCache. An installed new LRUQueryCache(maxSize, maxRamBytesUsed) applies the same 10,000-document rule (LRUQueryCache.java:252, :277-296) and needs RAM for five dense bit sets over the index (:792-808); only a custom leaf predicate, as in the repro, accepts any segment size.
  • What you see. Silent wrong match decisions for the moved documents of that segment, in both directions: a document moved out of the box still matches, and one moved into it is missed (in a separate executed example, 3 hits instead of 4). Every use of the box query that does not need scores sees it: a FILTER or MUST_NOT clause, ConstantScoreQuery, count() of the query or of a query that contains it, and (by reading the code) a search sorted by a field without scores, including a later request that never ran before. A relevance-scored use (the box as the top-level query of search(q, n), or a scored MUST/SHOULD clause) does not use the cache and is correct: a fact-check probe on main returned [1, 2, 3, 4] for those both ways, while ConstantScoreQuery, FILTER, MUST_NOT and both counts were stale. No error.
  • How long. Until the segment is merged into a new segment (forceMerge cleared it), the LRU evicts the entry, or the application clears the cache (clear(), clearQuery(q)) or replaces it (eviction and clearing read from the code, not run); it survives further reopens. Each updated segment serves only its own old decisions: no document of another segment leaks in, and an update that moves documents in several segments makes each of them stale.
  • How likely. Rare: shape doc values are @lucene.experimental, the query is the slow doc-values variant, and a code search found no Elasticsearch, OpenSearch or Solr code that runs it or updates shape doc values in place.

Why it is a bug, not intended

#
  • SegmentCacheable: "Objects that depend on doc values should return DocValues#isCacheable ... Updated doc values fields are not suitable for caching."
  • Sibling doc-values queries return DocValues.isCacheable(ctx, field), and TestLRUQueryCache asserts that an updated segment is not served from the cache.
  • The introducing PR's first commit had this check; an in-PR refactor dropped it, with no review comment about caching.
The full argument243 words
  • The documented rule. SegmentCacheable.java:30-32 (quoted above). It says "should": strong guidance that the cache relies on, not something it checks. QueryCache.java:27-30: the cached weight "will only be equivalent if scores are not needed"; here it is not equivalent even with scores off.
  • Upstream tests assert the rule for other queries. TestLRUQueryCache#testDocValuesUpdatesDontBreakCache (TestLRUQueryCache.java:2222) shares one cache across reopens and asserts that after updateNumericDocValue the segment is "no longer cached due to DV update"; TestSegmentCacheables#testMultipleDocValuesDelegates builds SegmentCacheable lambdas over DocValues.isCacheable and asserts that, after field3 is updated, every composite that refers to it is uncacheable (TestSegmentCacheables.java:43-92).
  • The siblings follow it. LatLonDocValuesBoxQuery.java:164-165, LatLonDocValuesQuery.java:169-170, XYDocValuesPointInGeometryQuery.java:141-142 and BinaryRangeFieldRangeQuery.java:146-147 return DocValues.isCacheable(ctx, field). So does Elasticsearch's own, independent shape doc-values query.
  • History: the check existed and was lost. In PR #1017's first commit (3554306677, 2022-05-18) the doc-values query class had isCacheable(ctx) { return DocValues.isCacheable(ctx, field); }. Commit 2cf24b47c0b6 ("Major refactor to leveral SpatialQuery" [sic], 2022-07-20) replaced that class with BaseShapeDocValuesQuery extends SpatialQuery, added queryIsCacheable returning true and routed Weight#isCacheable through it, without an override. None of the PR's 10 comments or 30 review comments mentions caching; no javadoc, CHANGES or MIGRATE entry limits updates or caching for shape doc values.
  • The trigger is legal. Public factories, a documented doc-values-only field, and an update path that accepts BINARY updates on doc-values-only fields (IndexWriter.java:2081-2127). The upstream DV query tests (TestLatLonPolygonShapeDVQueries and siblings) index only the doc-values field.
The devil's-advocate check157 words

The intended-behaviour checker built the strongest case: shape doc values and LRUQueryCache are @lucene.experimental, SpatialQuery is @lucene.internal (SpatialQuery.java:58), the shape doc-values field was designed as a companion of the indexed triangles (LUCENE-10654 motivates it with IndexOrDocValuesQuery), and main does not cache by default, so this is an unsupported combination.

Why it fails: @lucene.experimental is about API stability, not permission to return wrong results. The doc-values-only field is documented (LatLonShape.java:89) and is what the upstream DV tests use, and a companion field of the same name cannot be updated at all, so the only updatable case is exactly the doc-values-only one. SpatialQuery being internal does not matter: users reach it through public factories. The missing default cache on main narrows reach but does not change the rule, and 9.4.0-10.5.2 reproduce with zero configuration. The first PR commit had the right check. No verifier or reviewer rated the intended argument better than weak.

Suggested fix

#

Recommended Override queryIsCacheable in BaseShapeDocValuesQuery (validated)

Override queryIsCacheable in BaseShapeDocValuesQuery to return DocValues.isCacheable(ctx, field), as the sibling doc-values queries do (+8 lines, no public API change). The test then passes 3 of 3 with assertions on and off, and 63 suites (547 tests) of the document package and the query-cache tests pass.

@Override
protected boolean queryIsCacheable(LeafReaderContext ctx) {
  // matches are read from doc values, which may be updated in place
  return DocValues.isCacheable(ctx, field);
}

One fix was built and validated. Two alternatives that move the rule into SpatialQuery were not built.

Override queryIsCacheable in BaseShapeDocValuesQuery (validated) (validated by the checks) (recommended)

#

In BaseShapeDocValuesQuery, add the override below and import org.apache.lucene.index.DocValues and org.apache.lucene.index.LeafReaderContext. 1 file, +8 lines. SpatialQuery and BaseShapeDocValuesQuery are package-private, so there is no public API change.

@Override
protected boolean queryIsCacheable(LeafReaderContext ctx) {
  // matches are read from doc values, which may be updated in place
  return DocValues.isCacheable(ctx, field);
}

Trade-offs

Segments whose shape doc values were updated are no longer cached until they are merged, the same behaviour as the four sibling doc-values queries named under Why it is not intended; one FieldInfo lookup per segment. It fixes only this subclass family; a future doc-values subclass of SpatialQuery would have to remember the override. No benchmark was run.

Make SpatialQuery's default check doc-values updates (not built)

#

Change SpatialQuery.queryIsCacheable (SpatialQuery.java:146-148) to return DocValues.isCacheable(ctx, field);.

Trade-offs

Protects any future doc-values subclass. For the BKD-backed subclasses (LatLonShapeQuery, LatLonShapeBoundingBoxQuery, LatLonPointQuery, XYShapeQuery) the answer stays true: a field also indexed with points cannot be updated in place (FieldInfos.java:619-626), so its doc-values generation stays -1 (DocValues.java:343). The cost is that the base class of the point and triangle queries then reasons about doc values, plus a cheap FieldInfo lookup per segment for every spatial query.

Make queryIsCacheable abstract (not built)

#

Remove the default so that every SpatialQuery subclass family states its own rule.

Trade-offs

The most explicit, with a larger diff over all subclasses; still internal API only.

Downstream note

#

If an application uses this query as a region restriction, moved documents keep their old decision in non-scoring uses until the segment is merged or the entry leaves the cache: one moved out of an allowed region is still returned, one moved into an excluded region is still shown; deletes are still honoured.

How it was found

#

A scan of the bytecode of every isCacheable implementation in Lucene flagged SpatialQuery's constant true in a class family that reads binary doc values. A sweep of the real jars that compares cached and uncached results after an in-place update (35 doc-values query cases) returned stale results for both shape queries; a minimal JUnit confirmed it.

The method in full186 words

Method: semi-formal (the hunt's middle tier): a bytecode scan and a differential sweep, with a TLA+ model written right after.

  • The hunt unit checked query-cache correctness: every Weight#isCacheable must be false where the cached answer could differ from a fresh one.
  • A scan with the JDK ClassFile API listed every isCacheable implementation in the main jars (123 classes) and what it returns. It flagged SpatialQuery's weight, which delegates to queryIsCacheable, a constant true never overridden, in a class family whose doc-values subclass reads BinaryDocValues.
  • A differential sweep on the real jars ran 35 doc-values query cases: fill a cache, update doc values in place, reopen with the same segment core, compare the cached with the uncached result. Both shape queries returned STALE (27 ok and 8 STALE cases in all, the STALE ones explained by three separate root causes).
  • A TLA+ model of the LRUQueryCache path (QueryCacheDV.tla) violates its SearchCorrect invariant with a 5-state counterexample for a constant-true isCacheable and holds for the correct shapes.
  • The finder reduced the finding to a 3-test public-API JUnit; the independent checks followed (see Checks).

Versions tested8 rows

Bug record

LFV-308, snapshot of 2026-10-29

Registry title
LatLonShape/XYShape newSlowDocValuesBoxQuery reports Weight#isCacheable() == true although it reads the shape from binary doc values, so after an in-place doc-values update the query cache keeps returning the old matches
Area
core / document: shape doc-values queries (BaseShapeDocValuesQuery via SpatialQuery) and the query cache
Priority
Medium, rank 244: The same stale-cache class as LFV-320 and LFV-336, here for in-place-updated experimental doc-values-only shapes and the slow doc-values box query, gets the same tier and ends that group.
Impact class
silent wrong results
Impact note
Applications that store shapes in doc-values-only LatLonShape or XYShape fields (an experimental API), move them in place with IndexWriter#updateDocValues or updateBinaryDocValue, and filter or count with newSlowDocValuesBoxQuery through a query cache that survives the reopen are hit; on 9.4.0-10.5.2 the default IndexSearcher cache is enough (zero-configuration repro executed on a 12,000-doc segment), on main only an application-installed cache (no default cache since GITHUB#14187); the moved document keeps its old match decision until the segment is merged into a new one or the entry is evicted; ordinary scale.
Summary
You keep a shape in a doc-values-only field (LatLonShape.createDocValueField or XYShape.createDocValueField), run LatLonShape/XYShape.newSlowDocValuesBoxQuery through a query cache, then move one document's shape out of the box with IndexWriter#updateDocValues and reopen the reader. You expect the reopened searcher to stop matching that document, because a query that reads doc values must report itself not cacheable once those doc values have been updated (SegmentCacheable). Instead its Weight#isCacheable stays true (inherited from SpatialQuery#queryIsCacheable, which always returns true), the segment keeps its core cache key, and the cache keeps serving the pre-update result (5 hits instead of 4 in the repro) until the segment is merged away or the entry is evicted.
