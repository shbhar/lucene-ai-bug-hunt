Flexible query parser prints the phrase slop through a float: "a b"~2147483647 comes back as ~2147483648, which it cannot parse

SlopQueryNode stores the phrase slop as an int but prints it through a float, so toQueryString() changes every slop above 16,777,216 that a float cannot hold. The "any distance" query "a b"~2147483647 prints ~2147483648, which the same parser rejects; the query that actually runs is correct.

The finding in 30 seconds

#

Whole numbers in a float

#
  1. A Java float has 24 bits of precision, so it holds every whole number exactly only up to 2^24 = 16,777,216.
  2. Above that, converting an int to float rounds to the nearest float: 16,777,217 becomes 16,777,216, and every int from 2,147,483,584 to 2,147,483,647 becomes 2,147,483,648 (2^31), one more than the largest int.

The finding, step by step

#
  1. Parse f:"a b"~2147483647 with the flexible StandardSyntaxParser, the syntax parser behind StandardQueryParser. 2147483647 is Integer.MAX_VALUE, a historically suggested "any distance" slop. The tree's SlopQueryNode keeps it exactly: getValue() is 2147483647.
  2. Print the tree with toQueryString(new EscapeQuerySyntaxImpl()). You expect the input back: the method is documented to produce "a query string understood by the query parser".
  3. Instead you get f:"a b"~2147483648. The node converts its int slop to a Float before printing it, and a float holds every whole number exactly only up to 2^24 = 16,777,216, so 2147483647 rounds to 2^31.
  4. Parsing that text again throws NumberFormatException: For input string: "2147483648". Smaller slops change silently: ~16777217 prints ~16777216, which parses back as slop 16777216.
  5. Search is unaffected: StandardQueryParser.parse builds a PhraseQuery with slop 2147483647 from the original text. Only code that prints node trees (toQueryString, toString) and reuses the text sees it.

Who is affected

#

Applications that print a flexible-parser syntax tree or a hand-built slop node (toQueryString, toString) and then parse, compare or forward the text, when a phrase slop above 16,777,216 is one a float cannot hold (most likely the "any distance" ~2147483647). Default configuration. Searches built by StandardQueryParser.parse are unaffected.

Mechanism, terms and numbers486 words

The flexible query parser reads the phrase slop of "..."~N with Integer.parseInt into SlopQueryNode, whose value is an int. To print it, toQueryString() and toString() box the int into a Float and print the float's long value. A float is exact only up to 2^24, so 2,071,986,176 of the 2,147,483,648 non-negative slops print a different number: "a b"~16777217 prints ~16777216, and the 64 slops from 2147483584 to 2147483647, including the "any distance" value Integer.MAX_VALUE, print ~2147483648, which the same parser rejects with NumberFormatException. That breaks the documented promise that a node tree prints "a query string that can be parsed back by the original text parser". The Query built from the original text is correct, so searches are unaffected. The printer has not changed since 2.9.0, and the parsed "a b"~2147483647 has printed ~2147483648 in every release. Up to 9.0.0 the grammar rounded the slop itself, so that text still read back as the same slop; since 9.1.0, when the grammar started keeping the exact int, the text is rejected and other parsed slops above 2^24 print a different value. PhraseSlopQueryNode has the same printer. The fix is Integer.toString(this.value) in both classes.

The code

#
  • Parse side, exact int. The grammar builds new SlopQueryNode(q, parseInt(slop)) (StandardSyntaxParser.jj:833), and parseInt is Integer.parseInt(token.image) (:119-121).
  • The node is int-typed: private int value; (SlopQueryNode.java:35), the constructor SlopQueryNode(QueryNode query, int value) (:41) and int getValue() (:57-59).
  • Print side, through a float (SlopQueryNode.java:61-65; PhraseSlopQueryNode.java:53-57 is identical):
private CharSequence getValueString() {
  Float f = Float.valueOf(this.value);   // int -> float: rounds above 2^24
  if (f == f.longValue()) return "" + f.longValue();
  else return "" + f;                    // never taken for an int
}

toQueryString returns the child's text + "~" + getValueString() (:73-76), and toString prints <slop value='...'> with the same helper (:68-70). The body is a copy of BoostQueryNode.getValueString (BoostQueryNode.java:80-84), where the value really is a float (:33).

The numbers

#
  • Exhaustively over every non-negative int: 2,071,986,176 of 2,147,483,648 slops print a different number, exactly the ints in [2^24, 2^31) that are not floats (2^31 - 2^24 - 7 x 2^23). The smallest is 16777217 -> 16777216; the largest error is 64.
  • The 64 slops 2147483584..2147483647 print 2147483648, which Integer.parseInt rejects, so re-parsing throws NumberFormatException: For input string: "2147483648" from StandardSyntaxParser.parseInt.
  • Hand-built nodes: SlopQueryNode(q, 20000001).toString() shows <slop value='20000000'>; PhraseSlopQueryNode(q, 123456789) prints ~123456792.
  • Only non-negative slops are in scope: the grammar's NUMBER token has no sign (StandardSyntaxParser.jj:160) and PhraseQuery rejects a negative slop (PhraseQuery.java:173-174).

What is not affected

#

SlopQueryNodeBuilder copies getValue() into the PhraseQuery (SlopQueryNodeBuilder.java:47), so StandardQueryParser.parse("\"a b\"~2147483647", "f") searches with slop 2147483647. Inside Lucene, toQueryString output only goes into exception messages (for example QueryTreeBuilder.java:161). No processor or builder creates PhraseSlopQueryNode, so that half is reachable only through hand-built trees.

Exposure and likelihood246 words
  • Who. Code that turns node trees back into text to log, display, cache, forward or rewrite a query and then parses or compares it. The usual source is the syntax tree from StandardQueryParser.getSyntaxParser().parse(text, field), plus hand-built SlopQueryNode and PhraseSlopQueryNode trees. No option is needed.
  • Trigger. A phrase slop above 16,777,216 that a float cannot hold. The most likely such value is the "any distance" slop "..."~2147483647, which a 2004 java-user answer recommends ("red fox"~2147483647; a 2010 java-user thread uses the same value as a SpanNear slop in the XML query parser). How often applications use it was not measured.
  • Effect. For slops 2147483584..2147483647 the printed query cannot be parsed again (NumberFormatException). Other slops above 2^24 that a float cannot hold parse into a slightly different query (off by at most 64); whether that changes matching or scoring for a given document was not measured. toString() shows the same wrong value, which can mislead debugging.
  • Not affected. Search results: the query is built from the exact int. In processed trees a SlopQueryNode survives only above a tokenized or multi-phrase child (PhraseSlopQueryNodeProcessor.java:43-50), which prints in internal form ([TP[...]], [MTP[...]], commented as not re-parseable), so for them only the displayed number differs. The bug concerns raw syntax-parser trees and hand-built nodes.
  • Likelihood: rare. It needs both the print-and-reuse pattern and a huge slop; it is deterministic when both are present, and the recorded prior-report searches found no report.

Why it looks unintended

#
  • The javadoc promises "a query string understood by the query parser"; the package doc, one that "can be parsed back by the original text parser".
  • The slop is an int in the grammar, field and getter; the float printer is a copy of the boost node's.
  • Since 9.1.0 the parser accepts "a b"~2147483647 but prints text it rejects.
The full argument144 words
  • The contract: QueryNode.java:26 ("convert to a query string understood by the query parser"); core/nodes/package-info.java:42-43 ("A query node tree can also generate a query string that can be parsed back by the original text parser, at this point only the standard lucene syntax is supported."). Both date from 2.9.0.
  • Upstream enforces it: GITHUB#7865, fixed by #14697 (merged 2025-05-29): "AbstractRangeQueryNode#toQueryString(EscapeQuerySyntax) now returns a string which can be parsed back into the original node" (lucene/CHANGES.txt:296-297, 11.0.0 bug fixes), with TestAbstractRangeQueryNode parsing the printed string back.
  • Int end to end: Integer.parseInt in the grammar, the int field, constructor and getter, StandardQueryParser.setPhraseSlop(int) and PhraseQuery.Builder.setSlop(int). Nothing documents float precision for the slop.
  • Copy-paste artifact: identical to BoostQueryNode.getValueString, whose field is a float; for an int its else branch can never run.
  • Tests: no upstream test prints a slop above 2^24 or asserts the current output.
The devil's-advocate check255 words

The strongest case for "intended": Lucene's standard syntax has always read the slop as a float and truncated it. The classic QueryParser still does on main (QueryParserBase.java:802, (int) Float.parseFloat(...): "a b"~16777217 becomes slop 16777216), and the flexible grammar did the same until 9.0.0, so on 9.0.0 a parsed tree's printed text reads back as the same node and the float printer "matches the parser". toQueryString is also loosely honoured elsewhere (phrases in processed trees print as [TP[...]]), Lucene uses it only for messages, and the open #8667 (LUCENE-7616) calls the contract weak.

Why it fails: since 9.1.0 the flexible grammar reads an exact int, and the node is int-typed; a hand-built SlopQueryNode(q, 16777217) has never printed a value any Lucene parser reads back as 16777217; the documented contract is a re-parsable string, and upstream fixed another node for breaking it; #8667 is about custom parsers getting standard syntax back. Even on 9.0.0 the printer did not match the parser for the headline value: the parser stored 2147483647 (the (int) cast saturates float 2^31) and the printer showed ~2147483648, which read back as 2147483647 only because the cast saturated again; the minimal test fails on 9.0.0 too. The fix is also harmless under the float reading: a slop stored by a float-rounding parser prints the same digits, except the saturated Integer.MAX_VALUE, which then prints 2147483647 instead of 2147483648 and reads back as the same value. Verifiers and the adjudication rejected the intended-behaviour case; a read-only cross-model review rated it weak.

Suggested fix

#

Recommended Print the int as an int (one line per class, validated)

Print the slop as an int: in SlopQueryNode and PhraseSlopQueryNode, getValueString() becomes return Integer.toString(this.value);. Every slop then prints exactly, and nothing changes for slops that already printed correctly. It passes the repro, the finder's tests and the whole queryparser module.

private CharSequence getValueString() {
  return Integer.toString(this.value);
}

Print the int as an int (one line per class, validated) (recommended)

#

Replace the float detour in both getValueString() methods (+2/-6 in SlopQueryNode.java and PhraseSlopQueryNode.java). Covers toQueryString and toString of both nodes.

private CharSequence getValueString() {
  return Integer.toString(this.value);
}

Trade-offs

  • Output is unchanged for every slop that printed correctly before (all of [0, 2^24] and the float-representable values above it); an exhaustive check found 0 mismatches over [0, 2^26) with the fix.
  • Formatting only; not benchmarked.
  • It does not change parsing: the grammar's Integer.parseInt still throws a raw NumberFormatException on a fractional or out-of-range slop, a separate parse-side issue.

How it was found

#

A sweep of rarely discussed public queryparser APIs. While writing the reference for a round-trip check (Integer.toString, the inverse of the grammar's Integer.parseInt), the finder noticed the float conversion, then ran every non-negative int slop through toQueryString: 2,071,986,176 of 2,147,483,648 printed a different number, exactly the ints a float cannot hold.

History

#

The float printer dates from 2.9.0 (2009): hand-built nodes print wrong in every release, and the parsed "a b"~2147483647 has always printed ~2147483648. Up to 9.0.0 the grammar rounded the slop itself, so that text read back as the same slop; since 9.1.0 (LUCENE-10223, exact-int grammar) it is rejected, and other parsed slops above 2^24 can read back changed.

Versions tested7 rows

Printer introduced by 343992fcbb4 "LUCENE-1567: New flexible QueryParser framework." (2009-08-03, the original contribution, GitHub #2641), which added both nodes with an int slop and the float printer copied from the boost node; it has not changed since (835de0b44d4 only swapped new Float for Float.valueOf). Re-parse broken for parsed queries by f725b27e12a on main / ff9ee28c603 on branch_9x, "LUCENE-10223: interval support in standard syntax parser (#429)" (dweiss, 2021-11-11, first released in 9.1.0), which changed the grammar action from (int) Float.parseFloat(slop.image) to parseInt(slop). The PR does not discuss the slop. Before it, the parser rounded the slop at parse time and the (int) cast saturated: on 9.0.0 "a b"~16777217 is stored, printed and read back as 16777216, and "a b"~2147483647 is stored as 2147483647, printed as ~2147483648 and read back as 2147483647. Not a regression of the printer.

Registry title
Flexible query parser: SlopQueryNode and PhraseSlopQueryNode print their int slop through a float, so toQueryString changes every slop above 2^24 (~16777217 prints ~16777216, ~2147483647 prints ~2147483648, which the parser rejects)
Area
queryparser / flexible parser node serialization (SlopQueryNode and PhraseSlopQueryNode toQueryString/toString)
Priority
Low, rank 786: This toQueryString round-trip break needs a slop above 2^24 and only matters to apps that re-parse node text.
Impact class
minor
Impact note
A round-trip (contract) defect in a utility method, with no effect on the Query that StandardQueryParser.parse builds: applications that print flexible-parser node trees with toQueryString or toString (trees from StandardQueryParser.getSyntaxParser(), processed trees, or hand-built SlopQueryNode/PhraseSlopQueryNode) and parse, compare or forward that text get a different slop for every slop above 2^24 (rounded to the nearest float, at most 64 off below 2^31, e.g. 16777217 -> 16777216), and for the 64 slops 2147483584..2147483647, including the 'any distance' value Integer.MAX_VALUE, the string ~2147483648, which the same parser rejects with a NumberFormatException on re-parse (through the parse-side path of LFV-027); inside Lucene the output only feeds exception messages; default parser configuration, any scale; parser-built trees since 9.1.0, hand-built nodes since 2.9.0.
Summary
You parse "a b"~16777217, or the 'any distance' phrase "a b"~2147483647, with the flexible StandardSyntaxParser, print the node tree with toQueryString, and expect the same slop back, since QueryNode#toQueryString is documented as 'convert to a query string understood by the query parser' and the package documentation says the string 'can be parsed back by the original text parser'. Instead SlopQueryNode prints ~16777216, and ~2147483648 for the second query, which the same parser rejects with NumberFormatException, because getValueString boxes the int slop into a Float and prints its long value, so every slop above 2^24 is rounded to the nearest float. PhraseSlopQueryNode has the same helper (123456789 prints ~123456792), and toString() of both nodes uses it too.
Introduced
