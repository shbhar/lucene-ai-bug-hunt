DocIdSetBuilder.build() throws for maxDoc 0 instead of returning the empty set

new DocIdSetBuilder(0).build() throws IllegalArgumentException: maxValue must be non-negative (got: -1) instead of an empty set, so FacetsCollector fails on a leaf with maxDoc 0, such as an empty ParallelLeafReader. A 6.1.0 regression; only in-memory readers have such a leaf, and on 10.x and main IndexSearcher rejects it first (LFV-202).

The finding in 30 seconds

#

DocIdSetBuilder gathers one segment's matching doc ids and build() sorts them. Before sorting, it computes the sort width as PackedInts.bitsRequired(maxDoc - 1). With maxDoc 0 that is bitsRequired(-1), which throws, although the buffer is empty and the sorter would skip it.

Background: how faceting collects matches

#
  1. A reader is a list of leaves (segments). FacetsCollector visits each leaf, records its matching doc ids in a DocIdSetBuilder sized by the leaf's maxDoc, and calls build() when the leaf is done.
  2. A leaf can have maxDoc 0 when the application composes a reader in memory, for example new ParallelLeafReader() with no sub-readers inside a MultiReader. IndexWriter never writes such a segment. A fully deleted segment is different: it has numDocs 0 but maxDoc > 0, and is not affected.

The finding, step by step

#
  1. Create new DocIdSetBuilder(0), add nothing and call build(). FacetsCollector does exactly this for a leaf with maxDoc 0, for example new ParallelLeafReader() with no sub-readers.
  2. You expect the empty set: its iterator's first nextDoc() is NO_MORE_DOCS, as for new DocIdSetBuilder(1) (or 2, 128, 1000), and as Lucene 6.0 returned for 0.
  3. Instead build() throws IllegalArgumentException: maxValue must be non-negative (got: -1), with assertions on and off.
  4. Why: before sorting its buffer, which is empty, build() computes the sort width as PackedInts.bitsRequired(maxDoc - 1). With maxDoc 0 that is bitsRequired(-1), which rejects negative values.
  5. Effect: on 9.12.3 a faceted search over MultiReader(2-document index, new ParallelLeafReader()) throws instead of returning the 2 hits of the other leaf. On 10.x and main IndexSearcher rejects that reader earlier (LFV-202), and fixing that brings this failure back.

Who is affected

#

Applications that facet over a reader they compose in memory with a leaf with maxDoc 0, such as an empty ParallelLeafReader, and direct callers of new DocIdSetBuilder(0). On 9.12.3 a plain faceted search fails; on 10.x and main IndexSearcher rejects the leaf first (LFV-202), and fixing that exposes this. Never a wrong result.

Mechanism, terms and numbers411 words

DocIdSetBuilder collects the matching doc ids of one segment, sized by the segment's maxDoc. With maxDoc 0 and nothing added, build() throws IllegalArgumentException: maxValue must be non-negative (got: -1) instead of returning the empty set, because its sparse branch always computes the radix-sort width as PackedInts.bitsRequired(maxDoc - 1). A public caller, and the demonstrated route, is FacetsCollector, which builds one per leaf, so it fails on a leaf with maxDoc 0 (for example an empty ParallelLeafReader inside a MultiReader) instead of counting the other leaves. A plain faceted search reaches it on 9.12.3; on 10.x and main IndexSearcher rejects such a reader first (LFV-202), so only code that drives FacetsCollector directly does. It is a regression from LUCENE-7261 (6.1.0); 5.3.0 to 6.0.1 returned the empty set. IndexWriter never writes a 0-document segment, so only readers composed in memory are affected, and the failure is loud, never a wrong result.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/DocIdSetBuilder.java)

#
  1. No lower bound. DocIdSetBuilder(int maxDoc): "Create a builder that can contain doc IDs between {@code 0} and {@code maxDoc}." (:148-151), with no check. The class is @lucene.internal (:35).
  2. With maxDoc 0 the sparse path is always empty. threshold = maxDoc >>> 7 is 0 (:187). grow(n) for any n > 0 exceeds it and switches to a FixedBitSet(maxDoc) (:220-232, :296), which builds an empty set fine. With nothing added, or grow(0), the builder stays on the sparse path with an empty buffer.
  3. The fix site. build() (:313), sparse branch: sorter.sort(PackedInts.bitsRequired(maxDoc - 1), concatenated.array, concatenated.length) (:322).
  4. Why an empty buffer still throws. LSBRadixSorter.sort returns early for fewer than 30 values (LSBRadixSorter.java:89-93), but Java evaluates the argument first, and PackedInts.bitsRequired(int) throws "maxValue must be non-negative (got: -1)" for any negative value (PackedInts.java:803-806).
  5. A public caller, and the demonstrated route. FacetsCollector.doSetNextReader creates new DocIdSetBuilder(context.reader().maxDoc()) (FacetsCollector.java:108) and finish() calls build() (:120). An empty ParallelLeafReader sets maxDoc = numDocs = 0 (ParallelLeafReader.java:96-98). FacetsCollector is one of 21 new DocIdSetBuilder( sites in non-test code; the others were not probed.

Why it looks unintended

#
  • The constructor allows "doc IDs between 0 and maxDoc" with no lower bound; the class returns the empty set for maxDoc 0 on its dense path and for every maxDoc of 1 or more.
  • 5.3.0 to 6.0.1 returned the empty set; the throw came with a 2016 sort speed-up (LUCENE-7261).
  • The public FacetsCollector reaches it on an empty ParallelLeafReader.
The full argument225 words
  • Contract. DocIdSetBuilder(int maxDoc): "Create a builder that can contain doc IDs between {@code 0} and {@code maxDoc}." (DocIdSetBuilder.java:148); build(): "Build a {@link DocIdSet} from the accumulated doc IDs." (:312). No javadoc, assert, CHANGES or MIGRATE entry says maxDoc must be at least 1. That is strong evidence, not proof: the class is @lucene.internal, and "between 0 and maxDoc" is loose about the usual exclusive upper bound. With the points below it makes maxDoc 0 a plausible unsupported-boundary defect rather than a documented limit.
  • The class handles the case elsewhere. maxDoc 0 on the dense path (grow(1), then build()) returns an empty BitDocIdSet (cost estimate 1 from the grow(1) reservation, iterator empty).
  • Tests. Upstream TestDocIdSetBuilder.testEmpty asserts that an empty builder builds an empty set, for maxDoc = 1 + random().nextInt(1000) (TestDocIdSetBuilder.java:30-32). That form predates the regression (first in 8f96faf3d33, 2014); it never exercises 0, and no rationale for leaving 0 out is recorded. TestParallelReaderEmptyIndex builds new ParallelLeafReader() on purpose (:50).
  • History. LUCENE-7261 "Speed up LSBRadixSorter" (#8316, 2016) replaced sorter.sort(buffer, 0, bufferSize) with sorter.sort(PackedInts.bitsRequired(maxDoc - 1), buffer, bufferSize) to skip radix passes. Its discussion is about radix-sort speed only; 6.0.x returned the empty set for maxDoc 0.
  • Precedent. LUCENE-5045 (#6109): DrillSideways threw on an empty reader and was fixed as a bug.
The devil's-advocate check169 words

The strongest case for "intended": Lucene never writes 0-document segments, and maintainers have said such segments must not exist (LUCENE-5173 #6237, opened partly over a Solr split-shard error with this very message, and the related LUCENE-5116 #6180, both 2013; later #12872 and #15803). The builder is @lucene.internal, and on 10.x and main IndexSearcher blocks the search route anyway (LFV-202).

Why it mostly fails: those statements concern segments that IndexWriter writes and codecs read, while an empty ParallelLeafReader is public API with an explicit zero-reader branch and an upstream test. @lucene.internal is a compatibility tag, not a precondition, though it does leave maintainers free to define the builder's domain; the failure is reached through the public FacetsCollector. On 9.12.3 a plain faceted search hits it, and LFV-202's recommended fix brings it back on main. Verdict: not intended, a Low robustness defect. A maintainer may still call it too minor to fix, or prefer LFV-202's skip-empty-leaves option or fix C; that is a fair outcome for a Low bug.

Suggested fix

#

Recommended Clamp the bitsRequired argument to 0 (A, recommended, validated)

Clamp the sort width: PackedInts.bitsRequired(Math.max(maxDoc - 1, 0)) at DocIdSetBuilder.java:322. The repro passes with assertions on and off, and 37 tests of the closest core and facet suites pass.

        sorter.sort(
            PackedInts.bitsRequired(Math.max(maxDoc - 1, 0)),
            concatenated.array,
            concatenated.length);

Clamp the bitsRequired argument to 0 (A, recommended, validated)

#

In DocIdSetBuilder.build(), sparse branch (:322), pass Math.max(maxDoc - 1, 0) to PackedInts.bitsRequired, wrapped as google-java-format wants it.

        sorter.sort(
            PackedInts.bitsRequired(Math.max(maxDoc - 1, 0)),
            concatenated.array,
            concatenated.length);

Trade-offs

One Math.max per sparse build(), nothing per document (expected negligible, not benchmarked); every maxDoc of 1 or more sorts exactly as before. Caveat: it also stops most negative maxDoc values (invalid, but the constructor does not reject them) from throwing here, and they would then sort with a 1-bit width; option B is narrower, or reject a negative maxDoc in the constructor. Open PR #12800 rewrites the same line (and keeps bitsRequired(maxDoc - 1)).

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, seed DEADBEEF: the repro fails without the fix (assertions on and off) and passes with it (assertions off).
  • With the fix and assertions on: the repro (1), TestDocIdSetBuilder (9), TestLSBRadixSorter (6), TestIntArrayDocIdSet (7) and, in :lucene:facet, TestDrillSideways (14): 37 tests, 0 failures. checkGoogleJavaFormat flags only the repro's long comment line, not the fix.
  • Earlier the finder, the independent reproducer and the cross-model reviewer each checked the clamp by shadowing the class: their tests passed, and TestDocIdSetBuilder passed 9 of 9 in the finder's and the reviewer's runs.

Skip the sort when the buffer is empty (B, not run)

#

Guard the sorter.sort(...) call with if (concatenated.length > 0).

Trade-offs

Equivalent for this bug, since a maxDoc 0 builder's sparse buffer is always empty; it also skips work for every empty builder, at the cost of one more branch.

Special-case empty leaves in FacetsCollector (C, not run)

#

In FacetsCollector, record DocIdSet.EMPTY for a leaf with maxDoc 0 instead of building one.

Trade-offs

Fixes the faceting route only and leaves the builder's boundary in place for other callers.

Downstream note

#

Downstream products are affected only if they facet over readers they compose with an empty leaf; end-user queries and documents cannot create such a leaf.

How it was found

#

A proof-obligation audit of DocIdSetBuilder's contract: build() must return a set for every documented maxDoc, including the empty domain 0. The sparse branch fails that obligation at bitsRequired(maxDoc - 1); a one-method JUnit test then witnessed the exception.

The method in full121 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked build() against the constructor's domain ("doc IDs between 0 and maxDoc") on both paths, dense and sparse, and found that only the sparse path evaluates an expression that is undefined at maxDoc 0.
  • The finder then wrote a public-API JUnit test, probes for the FacetsCollector and IndexSearcher routes, and the one-line clamp that makes the test pass.
  • An independent reproducer and an executed cross-model review reproduced it with their own tests; a devil's-advocate verifier and an adjudication re-ran the finder's test (the adjudication with a new seed), and the verifier's own faceting test showed it once LFV-202 is fixed ("Prior reports, history and checks").

Summary
