LRUQueryCache.clearQuery and clearCoreCacheKey say "Remove all cache entries", but on main they only mark the entries for cleanUp()

On unreleased Lucene (main and branch_11x), LRUQueryCache.clearQuery and clearCoreCacheKey still document "Remove all cache entries", but since #15558 they only mark the entries: until cleanUp() runs (or LRU eviction or clear() drops them), the cache keeps counting them, keeps their memory and answers searches from them. MIGRATE.md never mentions this duty; search results stay correct.

The finding in 30 seconds

#

Since #15558 the two clear methods only add the query or segment key to a pending set, and only cleanUp() drains those sets. Lookups ignore the pending sets, so a cleared entry is still counted, still uses memory and still answers searches. The class javadoc documents this; the methods' own one-line javadocs still say they remove.

Background: the query cache and its clear methods

#
  1. LRUQueryCache keeps the matching documents of a query per segment, as (segment, query) entries. It is off by default on main; an application turns it on with IndexSearcher.setQueryCache or setDefaultQueryCache.
  2. clearQuery(q) drops the entries of one query, clearCoreCacheKey(key) those of one segment. The cache also calls clearCoreCacheKey itself when a segment is closed.
  3. Up to 10.6.0 both removed the entries before returning. #15558 (11.0) moved the removal to cleanUp(), which runs on a background scheduler if you pass CacheCleanUpParameters, or when you call it.

The finding, step by step

#
  1. On main you enable the query cache, here new LRUQueryCache(100, 1 << 20, context -> true, 1f), and run a TermQuery once on a 1-document index: getCacheSize() is 1.
  2. You call cache.clearQuery(query), whose javadoc says "Remove all cache entries for the given query." You expect the size to go 1 -> 0, as it does on 10.6.0 and earlier releases.
  3. Instead the size stays 1, ramBytesUsed() is unchanged, no eviction callback fires, and the next identical search is a cache hit on the "removed" entry (hit count 0 -> 1, the correct 1 document). clearCoreCacheKey(key) does the same.
  4. The call only put the query into a pending set. Only cleanUp() acts on that mark: called by you, or by a scheduler that only the 6-argument constructor with CacheCleanUpParameters sets up; until then the entry stays unless LRU eviction or clear() removes it first. The class javadoc says so; the two method javadocs and MIGRATE.md do not.

Who is affected

#

Applications on 11.0 and later that enable the query cache and call clearQuery or clearCoreCacheKey, for example behind a clear-cache action, trusting the method javadoc. Until the next cleanUp() they still see the entries in getCacheSize(), ramBytesUsed() and hit counts, the memory is not freed, and eviction callbacks come late. Opt-in: the cache is off by default. Results stay correct.

Mechanism, terms and numbers619 words

LRUQueryCache.clearQuery(query) and clearCoreCacheKey(key) are documented as "Remove all cache entries for the given query" and "... for the given core cache key" (LRUQueryCache.java:450, :442). Up to 10.6.0 they did exactly that before returning. #15558 (2026-04-14, not backported to 10.x) made removal deferred on purpose: both methods now only add the query or segment key to a pending set, and cleanUp() removes the marked entries later, on a background schedule if the cache was built with CacheCleanUpParameters, otherwise only when the application calls it. #15558 described this in the class javadoc ("Stale cache entries (from closed segments or cleared queries) are not removed inline"), but left the two method one-liners as they were.

So on main, after a clear call returns, the entry is still counted by getCacheSize(), still accounted in ramBytesUsed(), still returned by lookups and counted as a hit, and its eviction callback has not fired. MIGRATE.md, whose 11.0 recipe enables the cache with the 2-argument constructor (no automatic cleanup), never mentions cleanUp() or CacheCleanUpParameters. Search results stay correct. The fix is text only: reword the two javadocs and add a MIGRATE.md note.

The code (main 645d4fe14a20)

#
// LRUQueryCache.java:442-455
/** Remove all cache entries for the given core cache key. */
public void clearCoreCacheKey(IndexReader.CacheKey coreKey) {
  this.registeredClosedListeners.remove(coreKey);
  synchronized (keysToClean) {
    keysToClean.add(coreKey);                    // only marks the key
  }
}

/** Remove all cache entries for the given query. */
public void clearQuery(Query query) {
  for (int i = 0; i < numberOfPartitions; i++) {
    this.lruQueryCachePartition[i].clearQuery(query);   // :1250-1257: queriesToClean.add(query)
  }
}
  1. Both methods only mark. Neither removes a cache entry, fires an eviction callback or lowers ramBytesUsed() inside the call; clearCoreCacheKey also drops the segment's closed-listener registration (:443).
  2. Lookups ignore the marks. LRUQueryCachePartition.get (:1060-1083) returns the cached entry and calls onHit (:1077) without looking at keysToClean or queriesToClean.
  3. Only cleanUp() drains the marks (:1392-1413, the only code that drains the two sets); until it runs, a marked entry stays unless LRU eviction (:1214-1246) or clear() (:457-463) removes it first. It runs on a scheduler only when the 6-argument constructor got CacheCleanUpParameters with an executor (:197-207); the 4-argument constructor passes null (:150) and the 2-argument one delegates to it (:252).
  4. Closed segments take the same path. The close listener registered for each cached segment is clearCoreCacheKey itself (:1135).
  5. Results stay correct. Only SegmentCacheable queries are cached, which depend only on segment-immutable structures (SegmentCacheable.java:27-36), so a still-served entry holds the documents the query would compute again. The study's model-based test found 0 cached-vs-uncached mismatches.

The numbers (tie-break probe, main)

#

For both clearQuery and clearCoreCacheKey, on one document: cached size=1; right after the call size=1, ramBytesUsed() unchanged, 0 evictions; next identical search size=1, hits=1, 1 document; after cleanUp() size=0, 1 eviction, ramBytesUsed() 0. With the 2-argument constructor and a 10,000-document segment, closing the reader leaves the entry counted with no eviction until cleanUp(): cached=1 afterReaderClose=1 evictedAfterClose=0 afterCleanUp=0 evicted=1.

Exposure and likelihood319 words
  • Who. Applications on 11.0 (branch_11x) and later (main) that install an LRUQueryCache and call clearQuery or clearCoreCacheKey, and 10.x users who learned that these calls remove at once. The class is @lucene.experimental (LRUQueryCache.java:117).
  • Default vs opt-in. Opt-in: the query cache is off by default on main (IndexSearcher.java:84, DEFAULT_QUERY_CACHE = null, #14187). Among those who turn it on, MIGRATE.md's own recipe builds a cache with no automatic cleanup.
  • What they see. After a clear call: the entries in getCacheSize(), ramBytesUsed(), hit counts and onHit; memory not freed; onCacheEntryEvicted / onDocIdSetEviction only at the next cleanUp(), LRU eviction or clear().
  • Scale. Every call, deterministically. If the application never calls cleanUp(), the study's 1,000-round near-real-time run ended with 996 pending keys and 402 of 434 entries belonging to closed segments (432,704 accounted bytes, against 32 entries and 206,400 bytes with cleanUp() every round), and a Query passed to clearQuery stayed strongly reachable after LRU had evicted its entries. Entry count and accounted memory stay within maxSize and maxRamBytesUsed, and that run's hit and miss counts matched a run with cleanUp() every round, so no hit-rate loss is claimed. The PR author wrote that without cleanup "it will affect cache hit rates pretty badly", about stale segment entries piling up until LRU evicts them (sgup432 on #15558, 2026-04-22); one synthetic run settles neither way, so no hit-rate claim is made either way.
  • Not affected. Search results; the cache's size and memory bounds; every release up to 10.6.0.
  • Migration impact is recognized (evidence that someone relied on the two summaries was not found). On #15558, msokolov warned that cleanups being disabled by default "could bite someone if they are relying on it"; elastic/elasticsearch#163523 (open) lists "Cleanup is now async: a scheduler, or cleanup(). Without either, stale keys sit until LRU evicts them." among its adaptations to Lucene 11.

Why it looks unintended

#
  • The method javadocs say "Remove all cache entries for the given query"; from 5.1.0 to 10.6.0 these words meant removal before return.
  • The class javadoc in the same file says cleared-query entries "are not removed inline": the two texts contradict each other.
  • #15558 rewrote the surrounding javadocs and tests but left the two one-liners; MIGRATE.md says nothing.
The full argument255 words
  • The method text. "Remove all cache entries for the given core cache key." (LRUQueryCache.java:442) and "Remove all cache entries for the given query." (:450). The text dates from LUCENE-6077 (2014) and LUCENE-6303 (2015); in 10.6.0 it sits over bodies that remove under the write lock (10.6.0 LRUQueryCache.java:373-404).
  • The same file disagrees. "Stale cache entries (from closed segments or cleared queries) are not removed inline during cache operations." (:103-104). After the call the entries are not even logically removed: they are still returned and counted as hits.
  • #15558 updated everything around them. The squash commit d50fb36d9af3 wrote the class paragraph, the 6-argument constructor, CacheCleanUpParameters and cleanUp() javadocs; in TestLRUQueryCache it inserted cleanUp() between existing clear calls and their assertions (e.g. :472-473, :762-769) and added a new test, testInvalidation (:2679-2722), whose clear calls are followed by cleanUp(). It left the two one-liners; no comment or review comment discusses them (the one inline review thread on the new clearCoreCacheKey body is about what it removes, not its javadoc).
  • The migration guide is silent. MIGRATE.md's #15558 section (:514-542, added by #16756) shows a clearCoreCacheKey call and no cleanup note. Explaining why #15558 stayed off 10.x ("the query cache re-implementation introduced some breaking changes"), the PR author added: "we also changed the cleanup logic of the cache from sync to async flow" (sgup432, 2026-07-20).
  • What is not claimed. That deferral is wrong (it is the design), that results are wrong, or that the hit rate drops.
The devil's-advocate check192 words

Strongest case for "intended / noise" (the cross-model refute reviewer, OpenAI GPT-5.6, which ran its own failing two-segment test and voted not real with high confidence): the deferral is deliberate and documented four times (class, 6-argument constructor, CacheCleanUpParameters, cleanUp()); a test comment says "clearQuery() populates queriesToClean so that cleanUp() actually scans cache entries" (TestLRUQueryCache.java:272); the later fix #16212 kept the two-stage design; "Remove all" does not say "immediately"; the class is @lucene.experimental; no result is ever wrong.

Why it fails. It defeats a code-bug claim, which nobody makes. It does not make the method text true: on that reading "Remove all cache entries" would also fit a method that removes nothing until another method runs, and the class javadoc in the same file says these entries are "not removed inline". The reader most likely to trust the one-liner is the 10.x user, for whom the same words meant removal before return. The reviewer itself conceded that "MIGRATE.md and the method summaries could more explicitly repeat the cleanup requirement" and called the wording patch "a reasonable documentation enhancement". The objection fits the MIGRATE.md half better than the one-liners.

#

Recommended Reword the two javadocs and add a MIGRATE.md note

Documentation only: reword the two method javadocs to say the entries are marked and removed by the next cleanUp() (scheduled through CacheCleanUpParameters, or called by the application), and add a MIGRATE.md paragraph on deferred removal and the cleanup duty. No behaviour change.

Reword the two javadocs and add a MIGRATE.md note (validated by the checks) (recommended)

#

Both method javadocs: "Marks all cache entries for the given query (core cache key) for removal. Marked entries are removed by the next cleanUp(), which runs either on the background schedule configured through CacheCleanUpParameters or when the caller invokes it, unless LRU eviction or clear() removes them first. Until then they may still be returned by lookups and are counted by getCacheSize() and ramBytesUsed()."

MIGRATE.md, in the #15558 section: "clearQuery, clearCoreCacheKey and the segment close listener no longer remove entries right away: they mark them, and cleanUp() removes them. Either pass CacheCleanUpParameters with a ScheduledThreadPoolExecutor to the 6-argument constructor (and close() the cache when done), or call cleanUp() yourself. The 2- and 4-argument constructors configure no automatic cleanup."

Trade-offs

  • No code or behaviour change, no risk; the deferral and its performance reasons stay.
  • Callers still have to remember cleanUp(); the text only tells them. close() shuts down the executor passed in CacheCleanUpParameters (LRUQueryCache.java:271-275), so a shared executor needs care; the MIGRATE.md note could say so.
  • "The next cleanUp()" strictly means the next one that starts after the call: a cleanUp() already running has taken its copy of the pending sets (LRUQueryCache.java:1393-1394).

Code option: make the two explicit clear methods remove at once again (for upstream to weigh) (validated by the checks)

#

From the hunt: clearQuery removes the query's entries from its one partition under that partition's write lock (routing is by query alone); an explicit clearCoreCacheKey removes the segment's entries from every partition; the segment close listener moves to a private onCoreClosed that keeps the deferred path, so segment close stays cheap. The javadocs then stay true as written.

Trade-offs

  • Reverses part of a deliberate #15558 design; the author moved cleanup off the calling thread on purpose.
  • clearCoreCacheKey scans every partition on the calling thread (linear in the cache size); clearQuery scans one partition under its write lock.
  • clearCoreCacheKey takes the partition locks one at a time, so it is not atomic with concurrent inserts (10.6.0's method held the cache's single write lock); it also replaces the public LRUQueryCachePartition.clearQuery(Query) (LRUQueryCache.java:1250, partitions public through getLruQueryCacheSegments(), :210) with a package-private removeIf. Neither point was stress-tested.
  • With this option the minimal test is the regression test.

What the checks validated

Downstream note

#

Projects that expose a clear-cache operation on top of these methods need to call cleanUp() or configure CacheCleanUpParameters when they move to Lucene 11; Elasticsearch already tracks the new cleanup model in elastic/elasticsearch#163523.

How it was found

#

A probe saw an entry survive clearQuery. The hunt then drove the real cache through every sequence of up to 6 operations on a 2-segment reader against two models, the method javadocs and the class javadoc: on main 165,496 of 299,592 sequences break the first and none the second; on 10.x none break the first.

The method in full156 words
  • Lead. A code-reading probe on main showed the entry still present and served after clearQuery and clearCoreCacheKey; clear() was the control.
  • Intended or not. The hunt unit read #15558's body and comments and the class javadoc and concluded that the deferral is intended, so this is a documentation defect, not a code bug.
  • Model-based test. It drove the real jar through every sequence of up to 6 operations (search q0/q1, clearQuery q0/q1, clearCoreCacheKey s0/s1, clear, cleanUp) on a 2-segment reader and compared it with two reference models, SYNC (the method javadocs and 10.x) and DEFERRED (the class javadoc). Main: 299,592 sequences, 165,496 diverge from SYNC (the first is [search q0, clearQuery q0]) and 0 from DEFERRED. 10.5.2 and 10.6.0: 137,256 sequences each, 0 diverge from SYNC. A result oracle (cached documents equal uncached documents) found 0 mismatches in all three.
  • Reduction. The finding was reduced to a one-test public-API JUnit, then made portable to 10.x.

On main, the javadocs of LRUQueryCache.clearQuery and clearCoreCacheKey still say 'Remove all cache entries', but since #15558 both methods only mark the entries for the next cleanUp(), so the entries stay counted and keep producing cache hits until then; MIGRATE.md does not mention the deferred removal or the new cleanUp() duty (documentation defect, main only)
Area
search / query cache (LRUQueryCache method javadocs and MIGRATE.md)
Priority
Low, rank 1248: This main-only javadoc and MIGRATE.md gap in the core LRUQueryCache affects only cache statistics and memory until cleanUp() runs.
Impact class
minor
Impact note
Documentation only, in an opt-in expert cache on unreleased main (11.0): search results are always correct, but an application that installs an LRUQueryCache, calls clearQuery or clearCoreCacheKey and trusts the method javadoc still sees the entries in getCacheSize(), ramBytesUsed(), hit counts and onHit callbacks until the next cleanUp() (manual, or a background run that is off unless CacheCleanUpParameters is passed; default delay 60 s), and MIGRATE.md's own 11.0 recipe configures no cleanup; 10.6.0 (released 2026-10-29) and every earlier release are unaffected.
Summary
On main you install an LRUQueryCache, run a query so that it is cached, and call clearQuery(query) or clearCoreCacheKey(key), whose javadocs say 'Remove all cache entries for the given query' and '... for the given core cache key'. You expect the entries to be gone when the call returns, as on 10.x; instead #15558 made both methods only add the query or key to a pending set, so getCacheSize() still counts the entry and the next search is a cache hit (with correct documents) until cleanUp() runs. The deferral is deliberate and the class javadoc describes it, but the two method javadocs were left unchanged, and MIGRATE.md, whose 11.0 recipe builds a cache with no cleanup, never mentions the new cleanUp() or CacheCleanUpParameters duty.
