NoNormalization.explain reports 1 instead of tf, so IBSimilarity explains its Distribution at tfn = 1

With IBSimilarity and NoNormalization, explain shows the normalized term frequency as 1 instead of tf and computes the Distribution child from that 1: for a term that occurs 3 times, 0.6931472 under a score of 1.3862944. Scores are right; only the explanation is wrong, in every release since 4.0.

The finding in 30 seconds

#

IndexSearcher.explain prints how a score was computed as a tree of numbers, each child an input of its parent. With IB and no normalization, two children are wrong.

Background: explanations and IB scoring

#
  1. IndexSearcher.explain(query, doc) returns an Explanation: a tree whose nodes each carry a value and say how it was computed from the nodes below them.
  2. IBSimilarity (information-based models) scores a term in a document as distribution.score(tfn, lambda): tfn is the term frequency after length normalization, lambda a corpus statistic.
  3. The normalization is pluggable: NormalizationH1, H2, H3, Z, or NoNormalization, which leaves tf as it is (tfn = tf). Each one also explains its own value, the tfn, in the tree.

The finding, step by step

#
  1. Index one document whose field f is "a a a" (the term occurs 3 times) and score it with IBSimilarity(DistributionLL, LambdaDF, NoNormalization), the documented way to ask IB for no normalization.
  2. Call IndexSearcher.explain for f:a. The IB node is 1.3862944 (ln 4), the real score, and says it is computed as distribution.score(stats, normalization.tfn(...), lambda).
  3. You expect its children to add up: 3 = no normalization, since no normalization means tfn = tf = 3, and 1.3862944 = DistributionLL, as with NormalizationH1, H2, H3 or Z.
  4. Instead you get 1 = no normalization and 0.6931472 = DistributionLL (ln 2): the LL score at tfn = 1, a number the scorer never computed.
  5. Why: NoNormalization.explain returns the value 1 while its tfn returns tf, and IBSimilarity.explain hands that 1 to the distribution as tfn. Under DFRSimilarity only the 1 = no normalization child is wrong.

Who is affected

#

Anyone who calls explain on a field scored by IBSimilarity with NoNormalization, an opt-in, experimental setup, gets a wrong Distribution child on every hit whose frequency is not 1 (a repeated term or a fractional sloppy-phrase frequency); with DFRSimilarity only the normalization child is off. Scores and rankings are correct. Present since 4.0 (2012); no prior report found.

Mechanism, terms and numbers549 words

Normalization.NoNormalization.tfn returns tf, but NoNormalization.explain returns Explanation.match(1, "no normalization"). IBSimilarity.explain passes that explanation's value to distribution.explain as tfn, so under IB with NoNormalization the Distribution child is distribution.score(stats, 1, lambda) while the node it explains is the real score at tfn = tf. On one document "a a a" with DistributionLL and LambdaDF the node is 1.3862944 (ln 4) and the child 0.6931472 (ln 2). All four IB distribution/lambda pairs show it; NormalizationH1/H2/H3/Z do not. Under DFRSimilarity, which computes tfn itself since 8.0.0, only the "no normalization" child shows 1, next to model children computed from "3.0 = tfn". Scores and rankings are correct. The code dates from LUCENE-2959 (2011): every release from 4.0.0-ALPHA to 10.6.0 has it, and all 14 releases run show the same defect, with identical numbers within each probe. A one-line fix, Explanation.match((float) tf, "no normalization"), passes the repro and the 118 similarity tests of lucene/core. Low priority: an opt-in, experimental similarity and explain output only.

Mechanism (Lucene main 645d4fe14a20)

#
  1. Normalization.tfn "Returns the normalized term frequency" and explain "Returns an explanation for the normalized term frequency" (Normalization.java:33-46). The generic explain has the value (float) tfn(stats, tf, len) (:47-56).
  2. NoNormalization overrides both: tfn returns tf (:64-67), explain returns Explanation.match(1, "no normalization") (:69-72).
  3. IBSimilarity.score uses the real tfn: boost * distribution.score(stats, normalization.tfn(stats, freq, docLen), lambda.lambda(stats)) (IBSimilarity.java:114-118).
  4. IBSimilarity.explain adds normExpl = normalization.explain(...) as a child and then calls distribution.explain(stats, normExpl.getValue().floatValue(), lambdaExpl.getValue().floatValue()) (:125-131): it takes the explanation's value as tfn.
  5. Distribution.explain "Returns the name of the model only, since both tfn and lambda are explained elsewhere" and returns score(stats, tfn, lambda) (Distribution.java:35-41). With NoNormalization that is distribution.score(stats, 1, lambda).
  6. The node's own value is score(stats, freq, docLen) (IBSimilarity.java:139-140), so the top value equals the search score.
  7. DFRSimilarity.explain computes tfn = normalization.tfn(...) itself (DFRSimilarity.java:139-140) for its BasicModel and AfterEffect children (:143-144) but still adds normExpl (:142), so only "1 = no normalization" is wrong there.

The numbers

#

DistributionLL.score = -ln(lambda / (tfn + lambda)) (DistributionLL.java:33-35). One document, so LambdaDF = (1 + 1) / (1 + 1) = 1, moved down one ulp to 0.99999994 (LambdaDF.java:31-39). tfn 3 gives ln 4 = 1.3862944, the node and the search score; tfn 1 gives ln 2 = 0.6931472, the child. On the hunt's 5-document index (freq 3) the four pairs show node / child 1.7047480 / 0.9162907 (LL, DF), 1.2729657 / 0.6190392 (LL, TTF), 1.5447564 / 0.7996423 (SPL, DF) and 1.3294159 / 0.6553519 (SPL, TTF); with NormalizationH1 the child equals the node. Documents where the term occurs once look right, because there tfn = 1.

Why no test caught it

#

CheckHits.verifyExplanation takes a "computed as ... from:" node's own value as its combined value instead of recomputing it from the children (CheckHits.java:375, 437-438, 494-496). TestSimilarityBase runs NoNormalization but compares only the top explanation value with the score (:213-231); testLLForIB and testSPLForIB check the score only (:401-414, :468-476). TestDistributionLL and TestDistributionSPL do draw NoNormalization at random for IB (DistributionTestCase.java:97-99), but compare the score with the top explanation value and only rarely run CheckHits.verifyExplanation, which lets such a node through (BaseSimilarityTestCase.java:392-401).

Exposure and likelihood213 words
  • Who. Callers of IndexSearcher.explain on a field scored by IBSimilarity built with Normalization.NoNormalization: every explained hit whose frequency, as passed to the similarity, is not exactly 1 is wrong, with no other data condition: a term that occurs more than once, or a fractional sloppy-phrase frequency (a sloppy phrase with freq 0.5 gives IB nodes of 0.40546513 over 0.6931472 = DistributionLL children). Under DFRSimilarity with NoNormalization only the "no normalization" child shows 1.
  • Default or opt-in. Opt-in: IB and DFR are not the default similarity, and NoNormalization is one of five normalizations; both IB constructors name it as the way to ask for no normalization. Elasticsearch and OpenSearch map the IB/DFR setting normalization: no, and Solr none, to NoNormalization (read in their sources, not run).
  • Effect. A misleading explanation, not wrong results. IndexSearcher.explain is "intended to be used in developing Similarity implementations", which is the audience that reads the children: here the Distribution child is about half the real score (0.6931472 against 1.3862944).
  • Scale. A one-document index is enough. Since 4.0.0-ALPHA (2012); no prior report found.
  • Likelihood: plausible. Anyone using that configuration meets it on the first explained hit whose frequency is not 1, but IB without normalization is a niche choice and explanation children are rarely checked by hand.

Why it looks unintended

#
  • Normalization.explain is documented to explain "the normalized term frequency": for NoNormalization that is tf, not 1.
  • IB uses that value as tfn, so the Distribution child shows a score never computed; with H1, H2, H3 or Z it equals the node.
  • Nothing documents 1 as intended; tests check only the top value, and Lucene fixes explain-only errors as bugs.
The full argument262 words
  • The contract. Normalization.explain "Returns an explanation for the normalized term frequency" (Normalization.java:41); the generic implementation's value is that tfn (:49); NoNormalization.tfn returns tf (:66).
  • IB relies on it. Distribution.explain: tfn and lambda "are explained elsewhere" (Distribution.java:35-38). IBSimilarity.explain passes the normalization explanation's value as tfn (IBSimilarity.java:129-131), and the node text says "computed as boost * distribution.score(stats, normalization.tfn(stats, freq, docLen), lambda.lambda(stats)) from:" (:145-147). With H1, H2, H3 or Z the Distribution child equals the node at boost 1, up to float rounding (the H1 control and the hunt's 16 IB configurations with H1/H2/H3/Z).
  • DFR's own tree contradicts itself: "1 = no normalization" sits next to BasicModelIn, whose own child reads "3.0 = tfn, normalized term frequency". This is the weaker of the two symptoms: under DFR no computation consumes the 1, so it can be read as a display marker; under IB the Distribution child is a value the scorer never computes.
  • Explanations are a supported feature of these models. LUCENE-2959's CHANGES entry: the models "support all of lucene's features (boosts, slops, explanations, etc)" (lucene/CHANGES.txt:16108-16112).
  • Precedent. Lucene files explain-only value errors under Bug Fixes: "GITHUB#13691: Fix incorrect exponent value in explain of SigmoidFunction" (9.12.0, lucene/CHANGES.txt:2705); LUCENE-7065 (6.0.0, :9496).
  • History. The value 1 and the IB hand-off arrived together in cfaf91c7398 (2011); later commits on these lines are mechanical. No javadoc, test, CHANGES or MIGRATE entry or code comment says 1 is intended, nor does any upstream discussion found; the LUCENE-2959 and LUCENE-3220 threads discuss NoNormalization's name only.
The devil's-advocate check167 words

The strongest case for "not a bug" (the intended-behaviour check and the cross-model "intended" review): 1 is a neutral "nothing applied" marker, the convention of the old AfterEffect.NoAfterEffect, which explained itself as 1; Explanation.match documents its value as "the contribution to the score of the document"; the classes are @lucene.experimental; explain is a debugging aid; CheckHits deliberately treats "computed as" nodes as opaque; and nobody complained in 15 years.

Why it fails: normalization is not a multiplier. NoAfterEffect's 1 matched its own score, a factor of 1; NoNormalization's output is tf, and its documented explanation is of the normalized term frequency. Even read as a marker, IB consumes the 1 as tfn, so the Distribution child explains a score that was never computed, which is nobody's "contribution to the score". The experimental tag and the debugging purpose lower the impact (Low priority); they do not make the number right. Survival with tests that check only the top value is missing coverage, not intent.

Suggested fix

#

Recommended NoNormalization.explain returns tf (validated)

Make NoNormalization.explain return tf as its value: Explanation.match((float) tf, "no normalization"), one line. It fixes the IB Distribution child and the normalization child under IB and DFR, and no score changes. The repro, the 118 similarity tests of lucene/core and the core lint checks pass with it.

    @Override
    public Explanation explain(BasicStats stats, double tf, double len) {
-      return Explanation.match(1, "no normalization");
+      return Explanation.match((float) tf, "no normalization");
    }
All options and trade-offs2 options · 355 words

Both options were run through gradle in a scratch worktree of 645d4fe14a20. The first fixes the root cause; the second only stops IB from reading tfn off an explanation. The two were not run together; the first alone is the minimal demonstrated fix.

How it was found

#

A semi-formal check recomputed every "computed as ... from:" node of 3,178 explanations (79 similarity configurations, 14,554 formula nodes) from its own children. The 104 IB nodes with NoNormalization disagreed while every other IB normalization agreed; the finder reduced it to a public-API test.

The method in full175 words

Method: semi-formal (a differential evaluation of explanation trees on the stock jars).

  • Sweep. A public-API test program dumped every explained hit with its index statistics over 79 similarity configurations (DFR, IB, DFI, Axiomatic, LM, BM25, Classic and others) and many query types, with assertions on and off: 3,178 explained hits. An independent evaluator recomputed each "computed as <formula> from:" node from its own children and checked combiners and labelled statistics: 14,554 formula nodes.
  • Finding. The 104 IB score nodes of the four IB configurations with NoNormalization did not match boost * distribution.score(...) on their own children; the 16 IB configurations with H1, H2, H3 or Z did. 10 of 10 injected wrong formulas were caught, so the check is not vacuous.
  • Then the finder reduced it to a JUnit test. An executing cross-model review, an independent reproducer, a second cross-model review, a devil's-advocate check, an adjudication, the registration check, an audit, the version-history runs, a prior-report search and a repro minimization followed. The same sweep found two sibling bugs with their own fix sites (LFV-920, LFV-922).

Summary
You score a field with IBSimilarity(distribution, lambda, new Normalization.NoNormalization()) and call IndexSearcher.explain on a document where the term occurs 3 times. You expect the explanation to add up: the IB node says it is 'computed as boost * distribution.score(stats, normalization.tfn(stats, freq, docLen), lambda.lambda(stats))', NoNormalization.tfn returns tf, and Normalization.explain is documented to return 'an explanation for the normalized term frequency', so the normalization child should show 3 and the Distribution child should equal the node at boost 1. Instead NoNormalization.explain returns the value 1, IBSimilarity feeds that 1 into distribution.explain as tfn, and the Distribution child shows 0.9162907 under a node of 1.7047480 (all four IB distribution/lambda pairs), while the score itself is right.
