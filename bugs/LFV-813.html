RegExp numeric interval accepts a '+' on a bound and counts it as a digit

A + on a numeric-interval bound is neither rejected nor ignored but counted as a digit: RegexpQuery <+1-+9> matches "05" and not "5", the meaning of <01-09>, and <+100-999> loses its fixed width. Unsigned bounds work; every release since 4.0.0-ALPHA does this on Java 7 or later.

The finding in 30 seconds

#

The bound's text goes to Integer.parseInt, which accepts "+1" as 1, and the fixed width is the length of that text, so the + counts as one more digit.

Background: numeric intervals in Lucene regexps

#
  1. Lucene's RegExp syntax, used by RegexpQuery and the query parsers' /.../ syntax, has an optional numeric interval <n-m> that matches the numbers from n to m written as text. It is on by default.
  2. When both bounds have the same number of digits, every match has exactly that many characters: <1-9> matches "1" to "9", <01-09> matches "01" to "09". When they differ, any number of leading zeros is allowed.

The finding, step by step

#
  1. Index the terms "5" and "05" and search with RegexpQuery <1-9> (or type /<1-9>/ into the classic QueryParser): you get "5". Bounds with the same number of digits fix the length, so <01-09> would give "05".
  2. Write the same range with plus signs, <+1-+9>. You expect interval syntax error, which <-1-9>, < 1-9> and <1-9x> give, or the meaning of <1-9>.
  3. You get no error and only "05". Each bound's text goes to Integer.parseInt, which accepts a leading + (since Java 7), and the width is the text length: "+1" is 2 characters, so Lucene builds <01-09>.
  4. With a + on one bound the two lengths differ and the fixed width is dropped: <+100-999> also matches "0500" and "00500", which <100-999> rejects. <+100-+999> means "0100" to "0999".

Who is affected

#

Anyone whose regexp has a + on an interval bound, typed into a query parser or built by an application from signed number text. Interval syntax is on by default. The query silently matches a different set of terms; nothing else breaks, unsigned bounds are exhaustively correct, and nothing new can be expressed. Rare: no report since 2011.

Mechanism, terms and numbers562 words

Lucene's RegExp has an optional numeric-interval syntax <n-m>, on by default in RegexpQuery, the query parsers' /.../ syntax, Intervals.regexp and RegexCompletionQuery. Its javadoc says the bounds are "non-negative decimal integers" and that bounds with the same number of digits fix the length of the matching strings: <1-9> matches "1" to "9", <01-09> matches "01" to "09".

A bound written with a leading + is accepted without error and the + is counted as a digit. The parser passes each bound's text to Integer.parseInt, which accepts a leading + since Java 7, and takes the width from the raw text length. So <+1-+9> is built as <01-09>: a RegexpQuery or a classic QueryParser query /<+1-+9>/ returns the term "05" instead of "5". A + on one bound only makes the lengths differ, which drops the fixed width: <+100-999> also matches "0500". Every other malformed bound tried (-1, spaces, trailing text, hex, overflow) is rejected with interval syntax error. Unsigned bounds are exhaustively correct, and every + form means something an unsigned spelling can also say, so the only effect is a silently different match set for the author's own query. It has been in every release since 4.0.0-ALPHA, observable on Java 7 or later. Requiring ASCII digits before Integer.parseInt fixes it; it passes the repro, the closest suites and :lucene:core:check -x test.

The bug, step by step (main 645d4fe14a20, RegExp.java)

#
  1. The bound texts. For <...> with a - (:1460-1465), a - at the start, at the end or twice is rejected (:1474), then String smin = s.substring(0, i); String smax = s.substring(i + 1); (:1476-1477).
  2. Integer.parseInt accepts a +. int imin = Integer.parseInt(smin); int imax = Integer.parseInt(smax); (:1478-1479). Its javadoc allows "an ASCII plus sign '+' ... to indicate a positive value" (parseInt("+42", 10) returns 42); that is true since Java 7 (JDK-5017980).
  3. The width is the text length. if (smin.length() == smax.length()) digits = smin.length(); else digits = 0; (:1480-1482), so the + is counted.
  4. Built as a fixed-width interval. makeInterval(flags, imin, imax, digits) (:1488) becomes Automata.makeDecimalInterval(min, max, digits) (:728-729), where digits > 0 means a fixed number of digits and 0 means any number of leading zeros (Automata.java:490-501).
  5. Every other bad bound fails. Any NumberFormatException becomes IllegalArgumentException("interval syntax error at position ...") (:1489-1490).

Exposure and likelihood225 words
  • Who is hit. A regular expression with a numeric-interval bound written with a leading +: typed by a user into a query parser, or built by an application such as "<" + lo + "-" + hi + ">" from text that carries a sign (a %+d format or a user field; Integer.toString never adds a +).
  • Default reach. RegexpQuery(Term) ("By default, all regular expression features are enabled"), the classic QueryParser and the flexible StandardQueryParser (RegExp.ALL), Intervals.regexp (default flags) and RegexCompletionQuery(Term, BitsProducer) (RegExp.ALL). The classic QueryParser path was run: /<+1-+9>/ matches "05" and not "5".
  • What goes wrong. No exception, and a different match set: with both bounds signed the intended values are missed and zero-padded ones match; with one bound signed any number of leading zeros is accepted.
  • Limits. Deterministic, any index size, no setting. The study's bounded-exhaustive run (every <n-m> with n, m up to 1100, leading zeros and optional +, 44.4 million parses) found 0 mismatches for unsigned bounds. Every + language equals a documented spelling (<+1-+9> = <01-09>, <+100-999> = <0100-999>; 36,905 checks), and the automaton stays at most 14 states.
  • Likelihood: rare. It needs a + in a bound; then it happens every time. No report since Java 7 made it reachable in 2011. RegExp and RegexpQuery are @lucene.experimental.

Why it looks unintended

#
  • The javadoc fixes the width by "the same number of digits", and + is not a digit: read as 1, "+1" must give <1-9>; read as invalid, it must be rejected.
  • The parser rejects every other malformed bound tried, and upstream tests assert that truncated and empty intervals throw.
  • The 2010 code predates Java 7, whose Integer.parseInt began accepting +.
The full argument262 words
  • The documented contract. "Numerical intervals are specified by non-negative decimal integers and include both end points, and if n and m have the same number of digits, then the conforming strings must have that length (i.e. prefixed by 0's)." (RegExp.java:347-350). Under neither reading of "+1" is <01-09> right.
  • The block validates bounds. It rejects a misplaced - (:1474) and turns every NumberFormatException into interval syntax error (:1489-1490); the constructors document @exception IllegalArgumentException if an error occurred while parsing the regular expression (:510, :521, :533). 14 other malformed spellings are rejected.
  • The sibling syntax is ASCII-digits-only. {n,m} scans peek("0123456789") (:1272-1279); a{+2} fails with integer expected at position 2.
  • Tests. testTruncatedInterval (<1-), testTruncatedInterval2 (<1) and testEmptyInterval (<->) expect IllegalArgumentException (TestRegExpParsing.java:491-513); <1- and <1 fail at the > check (:1463), <-> at the bound check (:1474); no test covers a malformed bound spelling such as <1-9x>, and every interval in the tests is unsigned.
  • Never designed. The parse lines came with the 2010 port of dk.brics.automaton (b679816a7001). On Java 6 Integer.parseInt("+1") threw, so <+1-+9> was an interval syntax error; JDK-5017980 (Java 7, 2011) widened parseInt afterwards (read; no Java 6 run).
  • Precedent. #10410 (LUCENE-9370, type:bug): "The RegExp class is too lenient in parsing user input which can confuse or mislead users", fixed in 9.0 (its CHANGES entry is under Improvements). PR #12277 made a{99,11} throw: "we catch an invalid usage and throw a clean exception in that case".
The devil's-advocate check162 words

The strongest case (reading-only cross-model reviews said not real on it): + is outside the documented <n-m> grammar of an @lucene.experimental class, so what it parses to is unspecified; every documented input is exhaustively correct; garbage in, garbage out.

Why it fails: the parser does not treat out-of-grammar bounds as unspecified; it rejects all the others tried, and its tests assert that truncated and empty intervals throw. The + gets through only because of a later JDK change, and the meaning it gets contradicts the digit-count rule even under the lenient reading. The root-cause reviewer graded its works-as-designed argument "strong", but still wrote: "The case is not conclusive because the interval documentation never formally defines the lexical production for n and m, and counting an accepted plus sign as a digit conflicts with the stated width rule." It is a good reason for low priority, and maintainers may file the fix as an improvement; it does not make <+1-+9> = <01-09> correct.

Suggested fix

#

Recommended Bounds must be ASCII digits (reject everything else)

Require each bound to be ASCII digits 0-9 before Integer.parseInt, else throw the existing interval syntax error. Validated on main: the repro passes with assertions on and off, the automaton, regexp, query parser, intervals and regex-completion tests pass, and :lucene:core:check -x test passes. It also rejects non-ASCII digit bounds; rejecting only a leading + is the narrower alternative.

Trade-offs

  • It also rejects non-ASCII decimal digit bounds, which main reads as ASCII values: <١-٩> (Arabic-Indic) and <１-９> (full-width) are accepted as <1-9> on main and rejected with this fix. That reading is defensible and not claimed as a bug, so it is a behaviour change worth a CHANGES entry; a javadoc tweak ("written with the digits 0-9") would document it.
  • A query that uses a + bound today gets an exception instead of a different match set.

Downstream note

#

Downstream, an application that builds <lo-hi> range filters from signed number text (for example %+d output) would silently filter on a different range; pass digits only.

How it was found

#

A bounded-exhaustive check parsed every interval <n-m> with n and m up to 1100, up to two leading zeros and an optional + on each bound (44.4 million parses), with the real jar and compared each result with a reference written from the javadoc. Unsigned bounds had 0 mismatches; 14,647,338 + parses got another meaning.

The method in full170 words

Method: semi-formal (the finder's label): bounded-exhaustive translation validation of the real main jar against the javadoc, not a proof.

  • The unit's plan predicted the + signal by reading the Integer.parseInt lines; the exhaustive run witnessed and measured it.
  • Harness h297.IntervalTV: every <n-m> text with 0 <= n, m <= 1100, up to two leading zeros and an optional + on each bound, both orders, against a reference built from the javadoc rules; for n, m <= 120 an exact language comparison (product of the determinized Lucene automaton with the reference's minimal DFA).
  • 195.3 million checks in seven legs with 0 in-domain mismatches (documented input); 35 of 35 mutants of the checker were killed, and a RegExp mutant that drops the fixed width gives 99,438 mismatches, so the check can see width errors.
  • An independent reproducer then wrote its own public-API test comparing each signed form with its unsigned form over all 111,111 digit strings of length 0 to 5, and ran RegexpQuery and the classic QueryParser on an index.

Registry title
RegExp numeric interval <n-m> accepts a leading '+' on a bound and counts it as a digit, so <+1-+9> matches 01..09 instead of 1..9 and <+100-999> loses its fixed width
Area
util / automaton
Priority
Low, rank 921: An undocumented '+' on a RegExp interval bound silently changes the matched language, but only with a contrived spelling.
Impact class
minor
Impact note
Hits anyone whose regular expression writes a numeric-interval bound with a leading '+', passed with the default flags to RegexpQuery or the classic QueryParser /.../ syntax [exec] (by reading also the flexible StandardQueryParser, Intervals.regexp and RegexCompletionQuery): the query silently matches a different set of strings (for <+1-+9> the two-character strings 01..09, not 1..9) instead of failing with 'interval syntax error'; documented unsigned ASCII bounds are exhaustively correct, no setting or scale is needed, and it is in every release from 4.0.0-ALPHA to 10.6.0 on Java 7 or later.
Summary
You run a RegexpQuery, or a classic QueryParser query /<+1-+9>/, on a field with the terms 5 and 05. The RegExp javadoc says interval bounds are non-negative decimal integers and that bounds with the same number of digits fix the length of the matching strings, so you expect either an 'interval syntax error' (as for '-1', ' 1' or an overflowing bound) or the meaning of <1-9>, which matches 5. Instead the parser accepts the '+' and counts it as a digit, so <+1-+9> matches only 01 to 09 and returns 05; <+1-9> and <+100-999> lose their fixed width and accept any number of leading zeros, and <+100-+999> means 0100 to 0999.
