CheckIndex skips its seek-by-ord test for later fields when earlier fields hold fully deleted terms

With an ord-capable postings format from lucene/codecs, CheckIndex silently skips its seek-by-ord test for a field once earlier fields hold at least as many fully deleted terms as that field has live terms, so a broken seekExact(ord) passes. Every release since 5.3.0 is affected; the default codec is not.

The finding in 30 seconds

#

While CheckIndex walks a segment's fields in name order, it keeps two running totals: terms that still have a live document, and terms whose documents are all deleted. The on/off switch of its seek-by-ord test subtracts the wrong starting total, so fully deleted terms in earlier fields turn the test off for later fields.

Seek by ord in one minute

#
  1. Some terms dictionaries number a field's terms 0, 1, 2, ... (their ords) and can jump straight to a term by number with TermsEnum.seekExact(long ord); ord() then says where the enum is.
  2. Lucene's default terms dictionary does not support ords. The ord-capable postings formats are in lucene/codecs: BlockTreeOrds, Direct, and BlockTerms with a fixed-gap index (the in-memory MemoryIndex has ords too, but no deleted documents).
  3. For such a field, CheckIndex (level 2 and up) seeks to up to 10000 ords, checks that each seek lands on the ord it asked for, then seeks back to the same terms by value.

The finding, step by step

#
  1. Index one BlockTreeOrdsPostingsFormat segment: document 0 has a:a0 and a:a1, document 1 has b:b0 and b:b1. Delete document 0, so field a's 2 terms have no live document.
  2. Run CheckIndex.testPostings on a reader whose field-b terms enum sends seekExact(0) to ord 1, as a broken terms dictionary could.
  3. You expect the error seek to ord 0 returned ord 1: CheckIndex reports exactly that for the same broken enum when nothing is deleted, and with the one-line fix.
  4. You get no error. CheckIndex runs the test for a field only if status.termCount - termCountStart > 0; for b that is 2 live terms - (2 deleted + 0 live terms counted before b) = 0.
  5. So deletions in one field switch the test off for later fields, and a field whose terms are all deleted is never tested.

Who is affected

#

Users of an ord-capable lucene/codecs postings format, or of their own ord-capable terms dictionary, who run CheckIndex at level 2 or higher, and Lucene's randomized tests, whose random codec picks these formats. An unmerged update-by-id segment can trigger the skip. Nothing in the index or in results is wrong; only a seek bug in such a dictionary would go unreported.

Mechanism, terms and numbers689 words

CheckIndex.checkFields runs a "Test seeking by ord" block for every field whose terms enum supports ord(): up to 10000 seekExact(ord) calls, each followed by an ord() check ("seek to ord N returned ord M"), then seekCeil back to the same terms. The block is gated on hasOrd && status.termCount - termCountStart > 0 (CheckIndex.java:2399 on main). Since LUCENE-4485 (2012), status.termCount counts only terms with a live document, status.delTermCount the others, and termCountStart is their sum taken at the start of the field, so the gate computes (live terms of this field) minus (fully deleted terms of all earlier fields). In the repro, field a's 2 terms are fully deleted and field b has 2 live terms: the gate is 0 for b, and a terms enum whose seekExact(0) lands on ord 1 passes CheckIndex.testPostings with no error; without the deletion the same enum is reported. The other uses of termCountStart (ordExpected, and fieldTermCount, which the unique-term-count check right above uses) subtract it from the live-plus-deleted sum, and gating on fieldTermCount (one line) restores the test. Among Lucene's own postings formats only the ord-capable ones in lucene/codecs can hit it (the default block tree does not support ord()), and only CheckIndex at level 2 or higher, which includes Lucene's own randomized tests. No index, score or search result is wrong. Every release from 5.3.0 through 10.6.0, and main, is affected.

The code (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/index/CheckIndex.java)

/** Number of terms with at least one live doc. */  public long termCount = 0L;     // :315-316
/** Number of terms with zero live docs. */         public long delTermCount = 0L;  // :318-319

for (String field : fields) {                       // :1498, name order (PerFieldPostingsFormat keeps a TreeMap)
  boolean hasOrd = true;                            // :1632
  final long termCountStart = status.delTermCount + status.termCount;   // :1633

Step by step in the repro

#
  1. Field a, first by name: termCountStart = 0 + 0 = 0. Both terms a0 and a1 belong only to the deleted document 0, so delTermCount goes 0 -> 2 and termCount stays 0. Gate for a: 0 - 0 = 0, skipped (a field whose terms are all deleted is never tested).
  2. Field b: termCountStart = 2 + 0 = 2. Both terms are live, so termCount goes 0 -> 2. fieldTermCount = (2 + 2) - 2 = 2, and the unique-term-count check runs. Gate for b: 2 - 2 = 0, skipped.
  3. testPostings returns termCount=2 delTermCount=2 error=null. With the gate on fieldTermCount, the seek loop asks for ord 1 (fine) and then ord 0, lands on ord 1, and reports seek to ord 0 returned ord 1.

Without the deletion, or with the deleted field named c so that it sorts after b, stock main reports the same broken enum (executed with the repro's enum). The skip comes only from fully deleted terms in fields checked earlier.

Partial fallback

#

Earlier in checkFields, CheckIndex reads terms.getMax() (:1560). The default Terms.getMax() seeks by ord to size() - 1 (Terms.java:153-168), so formats that do not override it (Direct, BlockTerms) still get one ord seek; BlockTreeOrds overrides it and returns its stored max term (OrdsFieldReader.java:118-124; only an older index without one falls back to the ord seek), so the repro's index gets none. The repro's broken enum only remaps ord 0, so that fallback cannot see it.

Exposure and likelihood277 words
  • Who is hit. Users of BlockTreeOrds, Direct or BlockTerms with a fixed-gap index (all in lucene/codecs), or of their own ord-capable terms dictionary, who rely on CheckIndex at level 2 or higher (testPostings runs from Level.MIN_LEVEL_FOR_INTEGRITY_CHECKS = 2; the command-line default is 1), or call the public static CheckIndex.testPostings. Also Lucene's own randomized tests: TestUtil.checkIndex and checkReader run testPostings at level 3, and RandomCodec picks Direct, BlockTreeOrds and the fixed-gap BlockTerms format among others.
  • Not hit. The default codec: its block tree throws UnsupportedOperationException from ord(), so the block is never reached. Nor MemoryIndex: it has ords and reaches the test, but it has no deleted documents (getLiveDocs() returns null), so the gate equals the per-field count. Nor the per-document term-vector check, which passes no live docs, so the gate there equals the per-field count.
  • When. Any segment whose earlier fields (by name) hold at least as many fully deleted terms as a later field has live terms. An unmerged update-by-id segment can do this (merges can drop fully deleted terms): in a probe segment of 200 documents, kept unmerged with NoMergePolicy, 100 of which are then re-indexed under new ids with updateDocument, the fields id and title hold 200 fully deleted terms, and the later field zbody (44 live terms) gets 0 seekExact(ord) calls on main and 44 with the fix; the index is clean either way.
  • What they lose. Only the check: a terms dictionary whose seekExact(ord), ord() or seekCeil is wrong on such a field passes CheckIndex. The recorded searches found no shipped format with such a bug. Hence impact minor, likelihood contrived, priority Low.

Why it looks unintended

#
  • LUCENE-4485 (2012) made termCount live-only and moved termCountStart, ordExpected and the sibling gate right above to the live-plus-deleted sum, but not this gate.
  • Whether field b is tested depends on another field's deletions and name order.
  • Counter: coverage only, and no shipped format has such a bug. True, hence Low; still unintended.
The full argument222 words
  • Contract. The block is headed "Test seeking by ord" and seeks over Terms.size() terms, deleted ones included (:2390, :2398-2406). The counters are documented as live-only and deleted-only (:316, :319). The intended-behaviour advocate found no javadoc, CHANGES.txt or MIGRATE.md entry, test or list thread that says the test is skipped because of deletions in other fields.
  • History: the diffs are consistent with a missed edit, twice. The gate was written by a4d0cf02a8a (LUCENE-2682, 2010-10-04) when termCountStart = status.termCount and termCount counted every term, so it meant "this field has terms". cd6c2fe0a2e (LUCENE-4485, "CheckIndex's terms, terms/docs pairs counts don't include deleted docs", 2012-10-16, in 4.1.0) made termCount live-only, added delTermCount, and changed termCountStart, ordExpected and the unique-term-count gate directly above to the live-plus-deleted sum, leaving this gate as it was. 30807709e66 (LUCENE-5879, 2015-04-02, in 5.2.0) rewrote that sibling gate to fieldTermCount > 0 and again left this one.
  • Field-order dependence. With the fully deleted field named c, so that it sorts after b, stock main reports the same broken enum (executed with the repro's enum; an earlier control with an enum that swaps ords 0 and 1 shows the same, reported as seek to ord 1 returned ord 0). A skip that depends on other fields' names and deletions is not a policy.
The devil's-advocate check122 words

The case for "noise": CheckIndex documents no list of sub-tests, this block is a spot check (at most 10000 seeks), and no shipped ord-capable format is known to have a seek-by-ord bug, so nothing a user sees changes.

Why it fails as an intent argument: it is about impact, which is why the bug is Low, not about intent. The gate's value depends on unrelated fields, the same commit moved termCountStart, ordExpected and the sibling gate's condition to the live-plus-deleted sum, and the bugs this block catches do happen (#7455, LUCENE-6395, a MemoryIndex seek-by-ord bug). CheckIndex's public status.error is null for a reader whose terms enum is broken. Verdict: not intended, a defect (Low). The "coverage only" point holds, hence Low.

Downstream note

#

Products that validate indexes built with ord-capable lucene/codecs formats, or with their own ord-capable terms dictionary, through CheckIndex lose seek-by-ord coverage for any field whose earlier fields hold at least as many fully deleted terms as it has live terms, until this is fixed.

How it was found

#

A proof-obligation check of CheckIndex.checkFields (the seek-by-ord test should run for every field of an ord-capable terms dictionary that has terms) found that the gate's arithmetic breaks this once earlier fields hold fully deleted terms. An executable JUnit test then showed the skip.

The method in full125 words

Method: semi-formal (2026-11-03, main 5adff78bb168).

  • The obligation: for every field with hasOrd and at least one term, the "Test seeking by ord" block runs. Its gate is status.termCount - termCountStart > 0 (:2399); with termCountStart = delTermCount + termCount (:1633) and live-only termCount increments (:1902-1906), the gate equals (live terms of this field) - (fully deleted terms of earlier fields), which is 0 or less whenever the earlier fields' fully deleted terms are at least the field's live terms.
  • Witness: a public-API JUnit test with one segment and a terms enum whose seekExact(ord) lands on the wrong ord, reduced to the two-document test here; a probe on an update-by-id index showed the same skip on a realistic segment.

History

#

Introduced by LUCENE-4485 (cd6c2fe0a2e, 2012, in 4.1.0) and hidden by a second "ignoring deletes" pass until LUCENE-6553 removed it. Every release from 5.3.0 (2015) through 10.6.0, and main, is affected; not fixed upstream.

Impact note
Only users of an ord-capable postings format from lucene/codecs (BlockTreeOrds, Direct, or BlockTerms with a fixed-gap terms index; the default block tree throws UnsupportedOperationException from ord(), so default-codec users are not affected) who rely on CheckIndex at level 2 or higher, and Lucene's own randomized tests (RandomCodec picks these formats; TestUtil.checkIndex and checkReader run testPostings), lose the seekExact(ord)/ord()/seekCeil check for every later field of a segment whose earlier fields hold at least as many fully-deleted terms as that field has live terms (an ordinary update-by-id segment is enough); no index, score or search result is wrong, and the lost check matters only if such a terms dictionary has a seek bug; every release from 5.3.0 through 10.6.0 [exec], no scale needed.
Summary
You index one segment with BlockTreeOrdsPostingsFormat and NoMergePolicy (document 0 has terms a0 and a1 in field a, document 1 has terms b0 and b1 in field b), delete document 0 so that both terms of field a have no live document, and run CheckIndex.testPostings over a reader whose field-b terms enum swaps ords 0 and 1 on seekExact(ord), as a broken terms dictionary could. You expect the seek-by-ord test to report it, as it does on stock main when nothing is deleted ('seek to ord 1 returned ord 0'). Instead status.error is null on main (-ea and -da), 10.6.0, 10.5.2 and 9.12.3: for field b the gate computes 2 live terms minus the 2 fully-deleted terms of field a = 0, so the test never runs for field b.
