After a failover, an NRT replica can keep the old primary's same-named file and serve the wrong documents

After a failover, an NRT replica whose copy job from the old primary is still alive can keep a file the job finished if the new primary's file has the same name. It then shows a document the new primary deleted, hides a live one, commits it; CheckIndex is clean.

The bug in 30 seconds

#

In NRT replication a replica copies each new point's files into temp files. If a newer point arrives mid-copy, the new copy job keeps the temp files the old job already finished, matched by file name only. After a failover, the new primary can write a different file under the same name.

  1. You run NRT replication: primary P1, replicas A and B, segments _0 = {a0, b0} and _1 = {a1, b1}. P1 deletes a0 and a1 and publishes a point with two new delete files, _0_1.liv and _1_1.liv. B's copy job finishes P1's _1_1.liv; then P1 goes down (the test closes it without waiting for copies).
  2. A is promoted to primary P2. P2 deletes b0 and b1 and publishes version 9 with its own _0_1.liv and _1_1.liv: the same names, one delete each, other bits.
  3. You expect B, once it is at version 9, to show P2's documents: a0 and a1.
  4. Instead B hears of P2 before its old copy job has failed, and CopyJob.transferAndCancel keeps the finished temp file because the name matches; B copies only P2's _0_1.liv. At version 9, B shows a0 and b1: b1, deleted on P2, is visible, a1 is hidden, and the hit count is still 2.
  5. B commits that state and CheckIndex reports no problems. By reading the code, the stale file stays until that segment gets a newer delete file or is merged away; a restart alone does not remove it. Reproduced on 12 releases from 6.0.0 to 10.5.2 and on main.

Who is affected

#

Only applications on the opt-in, experimental NRT replication classes that fail over. When the new primary's first point reaches a replica, its copy job from the old primary must still be alive and have finished a file the new primary reuses by name. Lucene's own stress test never does that; any index size, default codec.

Mechanism, terms and numbers869 words

In lucene-replicator's NRT segment replication a replica copies a new point's files into temp files. When a newer point arrives while a copy runs, ReplicaNode.newNRTPoint calls CopyJob.transferAndCancel, which keeps every temp file the old job has finished whose name the new job also needs. It compares names only, never the files' FileMetaData, and it does so even when the newer point comes from a new primary. After a failover the new primary can write a different file under the same name, such as the live-docs file _1_1.liv of a segment both primaries share. The replica then reports the new primary's version but searches a mix of both primaries' deletes ([a0, b1] instead of [a0, a1] in the repro: a deleted document visible, a live one hidden, the same hit count), commits it, and CheckIndex reports the index clean. It needs no split brain: the old primary can be gone before the promotion. It was reproduced on 12 releases from 6.0.0 to 10.5.2 and on main (the releases in between have the same code), and it affects only applications that use the opt-in, experimental NRT replication classes and fail over while a replica's copy job from the old primary is still alive.

Terms

#
  • Primary and replicas: PrimaryNode indexes; each ReplicaNode copies the primary's new files and opens them. A failover promotes a replica to primary with a higher primaryGen.
  • NRT point: a searchable state with a version number. For each point, a replica runs a copy job (CopyJob) that copies the files it lacks into temp files and renames them when the job finishes.
  • .liv file: a segment's live-docs (deletes) file, named by segment and delete generation: _1_1.liv is the first delete generation of segment _1. Two primaries that each delete one document of the shared segment _1 both write _1_1.liv, with different bits.

The bug

#
  1. ReplicaNode.newNRTPoint first calls maybeNewPrimary (ReplicaNode.java:545). On a primary change it discards only pre-copied merge files; the comment above says why: "it's still a bit risky to rely solely on checksum/file length to catch the difference, so we defensively discard here and re-copy" (:536-544).
  2. It builds the new job, whose toCopy lists the new point's files that the replica lacks (getFilesToCopy, ReplicaNode.java:834-847); a temp file is not a local file, so both .liv files are listed.
  3. With a job in flight it calls job.transferAndCancel(curNRTCopy) (:613-616), whatever the jobs' primaryGens.
  4. CopyJob._transferAndCancel, unless the old job already failed (CopyJob.java:119-123), keeps every temp file the old job finished whose name the new job wants: prevJob.copiedFiles.get(fileName) != null moves it over and drops the name from toCopy (:133-156). Which of the two files the old job finished, and so which is carried, follows the job's iteration order; here _1_1.liv, in the independent reproducer's run _0_1.liv. The old and new FileMetaData are never compared.
  5. The replica renames the old primary's temp file to _1_1.liv and opens the new primary's version with it.
  6. Nothing notices. CopyOneFile checks checksums only while it copies bytes (CopyOneFile.java:99-126). The carried file is genuine (its footer matches its bytes), its header has the shared segment's id and the same generation, and both primaries deleted one document there, so the reader's header, footer and delete-count checks pass (Lucene90LiveDocsFormat.java:86-92, :98, :123-126).
  7. It stays (by reading, not executed): finishNRTCopy caches the new point's metadata as the replica's own (ReplicaNode.java:475) and readLocalFileMetaData answers from that cache (Node.java:196-205), so later points do not re-copy the stale file until the segment gets a new delete generation or is merged away. A restart alone does not repair it: the commit records primaryGen 2 (ReplicaNode.java:367-373), so a restart with the same primary reopens that commit without a sync (:189, :301-305, :317-318); the restart clears the cache, so the next point with a higher version compares the file on disk and copies it again.

Doc-values update files of a shared segment, including a soft-deletes field, take the same name-only branch (not executed).

Exposure and likelihood479 words
  • Who: applications that use lucene-replicator's NRT segment replication (PrimaryNode, ReplicaNode and their own CopyJob subclass, all @lucene.experimental) and fail over. One open-source downstream user was found, nrtsearch; its replica node and copy jobs inherit this code (read only, not run); whether its failover sequencing and copy timing can open the window was not examined. Elasticsearch, OpenSearch and Solr use their own replication.
  • The window: when the replica gets the new primary's first NRT point, its copy job from the old primary has not failed yet and has finished a file that the new primary reuses by name with other content. Orderings that open it: the old primary is gone before the promotion and the job has not noticed yet (this doc's test, which closes P1 without waiting for copies); a deposed primary that keeps publishing after the promotion (partition or long pause; executed by the finder); a half-open connection; a copy job idle between files; a controller that promotes without draining copies.
  • Narrow with the reference copy job: the module's socket-based test SimpleCopyJob holds its monitor while it reads (SimpleCopyJob.java:184), so against a dead primary the carry-over only wins a race between the failed read and the cancel (verifiers' reading, not run). Applications supply their own CopyJob, so their window depends on it. Every no-split-brain reproduction keeps the old job alive by construction (a no-op launch(), one file copied by hand, then the new point before the job reads again): legal for a CopyJob subclass, but no networked job has reproduced it.
  • Why Lucene's tests miss it: TestStressNRTReplication crashes the primary's process (its socket copy jobs then normally fail on their next read) and waits for in-flight copies before it promotes (SimpleReplicaNode.java:222-234); a TLA+ model finds no violation under that discipline (220 states). Its hit-count oracle would not notice either (2 = 2).
  • Silent condition: the reused file must pass the reader's checks; in every executed run it was a .liv of a shared segment with the same delete count. A different count fails loudly.
  • Damage: the replica reports the new primary's version but serves a mix of both primaries' deletes, commits it, and CheckIndex is clean. By reading: it lasts until the segment gets a new delete generation or is merged away, and if that replica is promoted it becomes the authoritative index.
  • Scale: none; two segments of two documents suffice. Default codec, default IndexWriterConfig apart from NoMergePolicy (set only to keep the two segments), ordinary hard deletes; for silence the same-named file must also pass the reader's checks (above).
  • How likely: rare (a judgement): it needs that failover timing plus a same-named generation file with the same delete count, and no matching public report was found in the documented searches. Not contrived: each step is an ordinary failover event.

Why it is a bug, not intended

#
  • On a primary change, newNRTPoint discards pre-copied data because "it's still a bit risky to rely solely on checksum/file length" (ReplicaNode.java:536-544); the carry-over trusts the bare name.
  • The module's identity rule is name plus header plus footer (FileMetaData javadoc, fileIsIdentical: "Segment name was reused! ... otherwise devastating").
  • No drain or fencing precondition is documented, and it reproduces without split brain.
The full argument307 words
  • Contracts. The newNRTPoint comment (ReplicaNode.java:536-544): on a primary change pre-copied data is discarded because "it's still a bit risky to rely solely on checksum/file length to catch the difference, so we defensively discard here and re-copy". fileIsIdentical (:849-873): a local file stands in for the primary's only if "its header (includes the segment id), length, footer (including checksum)" match, with "Segment name was reused! This is rare but possible and otherwise devastating". FileMetaData javadoc (FileMetaData.java:20-23): "Header and footer of the file must be identical between primary and replica to consider the files equal". newCopyJob javadoc (ReplicaNode.java:502-507): a new job may salvage files "shared with the new copy job". PrimaryNode (PrimaryNode.java:116-119) forces the version forward after a crash, "else versions can be illegally reused but show different results"; here one version shows different results on two nodes.
  • Design. LUCENE-5438 (#6501), by @mikemccand: a file is "the same" across primary and replica if "its file name is the same, its full byte[] index header and footer are identical, and it's in a "known to be fsync'd" state"; after a promotion "file names can be re-used (Lucene is no longer write-once)".
  • Tests. No upstream test targets transferAndCancel across a primaryGen change; the stress test's discipline avoids it (TLA+ model, 220 states). TestStressNRTReplication asserts that "all nodes show the same hit count for the same version, i.e. they really are replicas of one another" (:1118-1119), and its promoteReplica comment notes that "file name reuse can cause a replication to fail" (:393-397).
  • History. The carry-over and the unconditional transferAndCancel came with the package (1ae7291429b, 2016). 9afa560054a (same branch, "fix one stress test failure") added the defensive discard on a primary change, but only for pre-copied merge files. No "won't fix" or "by design" statement was found.
The devil's-advocate check262 words

The strongest case for "intended or misuse" (built by a devil's-advocate verifier; reviews by an independent reviewer from another model family, OpenAI GPT-5.6, rated it moderate): the module is @lucene.experimental; replicas do not fence a deposed primary (maybeNewPrimary only asserts a higher primaryGen); the reference controller kills the old primary and drains copies before promoting; and the transferAndCancel javadoc literally says it "Transfers whatever tmp files were already copied in this previous job" (CopyJob.java:97-100).

Why it fails: no javadoc, package doc, CHANGES or MIGRATE entry states a drain or fencing precondition, and the drain lives in test code with another stated purpose ("to be sure we really pick the most current replica"); newNRTPoint deliberately accepts a higher primaryGen while a job is in flight and right there states a policy of not trusting old-primary files; the module's own identity rule is name plus header plus footer; and split brain is not needed, since the old primary can be gone before the promotion. What the argument does establish, and the issue should say: the reference controller in effect drains (it waits while a replica is copying, SimpleReplicaNode.java:222-238); a default PrimaryNode.close() waits for outstanding copies without limit (PrimaryNode.java:207-216, :339-359), and the test sets that timeout to 0, as Lucene's own TestNRTReplication.testPrimaryCloseWhileCopyingNoWait does; the test's launch() is a no-op; no socket-based job has reproduced it. That narrows the reach; it does not make installing content other than the announced CopyState intended. Verdict: a defect; the argument only narrows the window, which the issue should state plainly.

Suggested fix

#

Recommended Carry a file over only if both jobs mean the same file

In CopyJob._transferAndCancel, carry a finished or partly copied file over only when the old job's FileMetaData for that name equals the new one (length, checksum, header, footer), +17/-2. The repro, the earlier tests, the replicator module's tests including the nightly stress test, and the static checks pass. Never salvaging across a primary change also works.

All options and trade-offs3 options · 843 words

Both fixes were built and checked in a scratch worktree at ea57360912ed. Workaround in every affected release: before promoting, make sure every replica's in-flight copy job has failed or finished (as TestStressNRTReplication does), or override transferAndCancel in your CopyJob subclass to cancel instead of transferring when the previous job's primaryGen differs. To repair an affected replica, re-copy its index from the current primary. A restart alone does not repair it (with the same primary it reopens its own commit without a sync); by reading, the first point with a higher version after a restart re-copies the stale file. The fixes were tested on main only.

Carry a file over only if both jobs mean the same file (validated by the checks) (recommended)

#

Applies the module's own identity rule (name plus length, checksum, header and footer) at the one place that skipped it. Within one primary nothing changes, because a name is written once and the metadata matches; a same-named file with other content is copied again from the new primary. It also guards the in-progress branch, which today fails loudly and cancels the job; with the fix that file is copied afresh in the same job. Diffs: carry-over-same-file-only.diff, fix-with-test.diff (applies cleanly at ea57360912ed).

String prevTmpFileName = prevJob.copiedFiles.get(fileName);
// After a primary change the same file name can hold different content, so only carry a
// file over if the previous job was copying the very same file:
if (prevTmpFileName != null && isSameFile(prevJob.files.get(fileName), ent.getValue())) {
  ...  // unchanged: keep the temp file
} else if (prevJob.current != null
    && prevJob.current.name.equals(fileName)
    && isSameFile(prevJob.current.metaData, ent.getValue())) {
  ...  // unchanged: resume the partly copied file
}

private static boolean isSameFile(FileMetaData a, FileMetaData b) {
  return a != null && b != null && a.length() == b.length() && a.checksum() == b.checksum()
      && Arrays.equals(a.header(), b.header()) && Arrays.equals(a.footer(), b.footer());
}

Trade-offs

  • Identical files are still salvaged across a primary change (for example files the promoted replica had also copied from the old primary); only differing ones are copied again.
  • It relies on CopyJob.files holding the previous job's metadata for every name in its copiedFiles, which holds for jobs built by ReplicaNode.newCopyJob (read); a subclass that breaks this would re-copy (safe).
  • Rejected temp files are cleaned up: a finished one stays in the old job's copiedFiles and is deleted with the others (CopyJob.java:200-202), a partly copied one is closed and force-deleted (:204-210), and the new copy writes its own uniquely named temp file (CopyOneFile.java:51-52) (read).
  • The fix does not repair a replica that already committed the bad state: the upgrade's restart reopens it as it is, and by reading the next point with a higher version then re-copies the stale file; re-copying the index repairs it at once. Worth a CHANGES note.
  • Not reviewed by a committer.

Never salvage a copy job across a primary change (validated by the checks)

#

In ReplicaNode.newNRTPoint, if curNRTCopy.getCopyState().primaryGen() != newPrimaryGen, call curNRTCopy.cancel(...) instead of job.transferAndCancel(curNRTCopy) (option-b.diff, +7/-1). It extends the existing "defensively discard" policy to the in-flight job.

Trade-offs

Throws away identical files too, so the first copy after a failover may re-copy more (a failover is rare). It relies on the CopyJob subclass's cancel being safe to call from newNRTPoint: the module's SimpleCopyJob makes it synchronized, the base method is not.

What the checks validated

This doc's test passes (gradle -ea; harness -ea and -da), and the earlier hunt tests give the same results as the recommended fix. The replicator module with the nightly tests and one test JVM: 17 tests, 0 failures, 1 skipped; TestStressNRTReplication ran 332 s. An earlier two-JVM nightly run under heavy machine load had 2 TestNRTReplication tests time out on a socket read during the primary's own 58 s flush; that class then passed 13 of 13 on its own. The static checks pass.

Document a drain-or-fence precondition

#

State that a controller must drain or cancel every replica's copy jobs and fence the old primary before promoting.

Trade-offs

Leaves the silent state for every application that does not, and the no-split-brain ordering shows how easy that is to miss. Not recommended.

Downstream note

#

Downstream: Lucene's replica code trusts a file name across primaries, so the mix-up happens even with authenticated transport and intact files, and a replica can keep serving a document the current primary deleted. Out of scope of SECURITY.md: no untrusted input is involved, and the module documents no guarantee for untrusted input (lines 28, 50).

How it was found

#

Semi-formal. While writing a TLA+ model of the NRT replication protocol, an AI tool suspected from the code that the carry-over matches by name only. The TLC model checker produced an 11-step counterexample, and a JUnit replayed it on the stock jars. With the fix modelled, TLC finds no violation in the bounded configurations it checked.

The method in full242 words

Method: TLA+ model checking (TLC), a hunt unit (the NRT replication protocol, 2026-10-26). Tier semi-formal: the hypothesis came from code reading and the tool witnessed it.

  • The finder was writing the transferAndCancel step of a TLA+ model of the protocol (NrtReplication.tla) and noticed that the carry-over compares names only.
  • TLC found an 11-step trace violating the invariant NoSilentForeignContent (no replica silently serves another primary's file content): 923 distinct states with assertions off, 788 with them on. With the fix modelled as content-equality carry-over (closest to the recommended fix), TLC finds no violation in the bounded configurations it checked (978 states for the core model, 82,805 for the full one), nor under the stress test's kill-and-drain discipline (220).
  • A JUnit replayed the trace step by step on the stock main jars and failed; it also failed on 10.5.2 and 9.12.3, as did the independent reproducer's test; the devil's advocate's no-split-brain variant failed on main and 10.5.2.
  • Then: a review by an independent reviewer from another model family (OpenAI GPT-5.6, reading only: real, medium) and a refute review by the same (procedural "not real, low": it could not run code and agreed on the root cause); an independent reproducer writing their own test in another package; a four-mode control test; a devil's advocate who found the no-split-brain ordering; an adjudication; a release sweep, a prior-report search, a security screen and a credibility audit; and this doc's own test and fix validation.

Bug record

LFV-241, snapshot of 2026-10-28

Registry title
After a primary change, an NRT replica keeps a file it already copied from the old primary when the new primary's file has the same name, matching by name only, so the replica serves and commits the wrong documents with CheckIndex clean
Area
replicator / NRT segment replication (CopyJob.transferAndCancel, ReplicaNode.newNRTPoint)
Priority
Medium, rank 76: Since 6.0.0 a failover while a replica's copy job from the old primary has finished a file that the new primary reuses by name (such as a shared segment's .liv) makes lucene-replicator NRT replication keep the old file, so the replica serves and commits the wrong deletes with CheckIndex clean and a later promotion makes that authoritative, severe silent corruption but only for opt-in NRT replication users and a rare failover timing that Lucene's own stress test never produces.
Impact class
data corruption
Impact note
Applications that use lucene-replicator's NRT segment replication (PrimaryNode/ReplicaNode/CopyJob subclasses, opt-in and @lucene.experimental; the one downstream user found, nrtsearch, inherits the code, by reading) and fail over, at any index size and in every release since 6.0.0, are hit when a replica learns of the new primary while its copy job from the old primary is still alive and has finished a file that the new primary reuses under the same name with other content (in every executed run a per-segment .liv file of a segment both primaries share, with the same delete count): the replica reports the new primary's NRT version but serves and commits a mix of both primaries' deletes (a document the new primary deleted is visible, a live one is hidden), hit counts can still match, CheckIndex reports the index clean, and if that replica is promoted later the mix becomes the authoritative index (inferred, not executed).
Summary
You run Lucene's NRT segment replication with failover: replica A is promoted to primary (a higher primaryGen) while replica B is still copying an NRT point from the old primary and has already finished one of its files, for example _1_1.liv. You expect B, once it has installed the new primary's NRT point, to search exactly the new primary's documents, because the module discards pre-copied data on a primary change and treats two files as the same only if name, header and footer match. Instead CopyJob._transferAndCancel keeps the old primary's finished temp file because the new primary's file has the same name, so B, at the new primary's version, shows [a0, b1] instead of [a0, a1], commits that state, and CheckIndex reports the index clean.
