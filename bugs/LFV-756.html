The bug in 30 seconds

#

highlightWithoutSearcher passes the caller's text straight to the field highlighter. The only cut to maxLength is in the stored-field loader (LimitedStoredFieldVisitor), which only the searcher entry points use, and the re-analysis code that follows assumes "content is already truncated to maxLength".

Background: maxLength and the two ways to highlight

#
  1. UnifiedHighlighter turns a document's text into a short snippet with the query's matches marked, such as <b>Lucene</b> is here..
  2. maxLength (default 10,000 chars; withMaxLength(n) changes it) bounds how much text it looks at: "Content will be truncated to this size before highlighting." A match after it is not shown; the first passage comes back instead.
  3. There are two ways in. The searcher entry points (highlight, highlightFields) load each hit's stored field. highlightWithoutSearcher, on a highlighter built with builderWithoutSearcher, takes the text as a String and re-analyzes it; no index is needed.

The bug, step by step

#
  1. You build a highlighter without an index, UnifiedHighlighter.builderWithoutSearcher(analyzer).withMaxLength(20).build(), and call highlightWithoutSearcher("body", query, text, 1) for the term lucene on the 48-char text Alpha beta gamma. Delta epsilon. Lucene is here.. Its only match starts at char 33.
  2. You expect the text cut to its first 20 chars before highlighting, as getMaxLength() documents: "Content will be truncated to this size before highlighting". The same text, query and option through an index and a searcher give Alpha beta gamma. , with no match.
  3. Instead you get <b>Lucene</b> is here.: all 48 chars were analyzed and the match past char 20 is highlighted, while getMaxLength() returns 20.
  4. The default is skipped too: on a 10,527-char text whose only match is at char 10,512, the searcher path returns Alpha beta gamma. and highlightWithoutSearcher returns <b>Lucene</b> is here..
  5. Why: the only cut is in the stored-field loader, which only the searcher entry points use. highlightWithoutSearcher hands the caller's String straight to the field highlighter, whose re-analysis code assumes "content is already truncated to maxLength".

Who is affected

#

Applications that call highlightWithoutSearcher with text longer than maxLength: any text over 10,000 chars by default. The snippet can come from past the bound, and the work grows with the whole text (58 ms for 1 million chars in one probe). Hits, counts and the searcher entry points are unaffected; the entry point itself is rarely used.

Mechanism, terms and numbers631 words

UnifiedHighlighter has a maxLength option, 10,000 chars by default, documented as "The maximum content size to process. Content will be truncated to this size before highlighting." With the default stored-field loader, the searcher entry points (highlight, highlightFields) cut the text while they load it. highlightWithoutSearcher, the entry point for a highlighter built with builderWithoutSearcher, takes the text from the caller and never cuts it: the whole text is analyzed, and a match or passage after maxLength can be returned. With withMaxLength(20), the 48-char text Alpha beta gamma. Delta epsilon. Lucene is here. gives <b>Lucene</b> is here. where the searcher path gives Alpha beta gamma. ; with the default, a match at char 10,512 of a 10,527-char text is highlighted. The work grows with the whole text (58 ms at 1 million chars and 217 ms at 4 million in one probe, against about 1 ms when the caller cuts it). Hits, counts and scores are correct, and no recorded run threw an exception. Present since the class was added in 6.3.0 (2016); a 4-line cut, with a javadoc sentence, passes the whole highlighter test suite.

Terms

#
  • maxLength: DEFAULT_MAX_LENGTH = 10000 (UnifiedHighlighter.java:100). getMaxLength(): "The maximum content size to process. Content will be truncated to this size before highlighting. Typically snippets closer to the beginning of the document better summarize its content." (:596-603). Builder.withMaxLength: "The text to be highlight is effectively truncated by this length." (:354). builderWithoutSearcher returns that same Builder (:453-455).
  • Searcher entry points: the public highlight (:747, :766) and highlightFields (:796, :828, :854) overloads, which all reach the protected highlightFieldsAsObjects (:890). It loads each hit's text with loadFieldValues (:958, :1382-1404); a subclass may override that loader.
  • highlightWithoutSearcher(field, query, content, maxPassages) (:1096-1108): "Highlights text passed as a parameter. ... This use-case is more rare. Naturally, the mode of operation will be OffsetSource#ANALYSIS" (:1079-1081), that is, the text is re-analyzed. Its javadoc says nothing about maxLength.

The bug

#
  1. On the searcher path, the default loadFieldValues reads stored fields through new LimitedStoredFieldVisitor(fields, MULTIVAL_SEP_CHAR, getMaxLength()) (:1409-1410), which keeps value.substring(0, Math.min(maxLength, value.length())) (:1446-1447) and caps later values of a multi-valued field by the remaining budget (:1450-1465). The cut text goes to fieldHighlighter.highlightFieldForDoc(leafReader, docId, content.toString()) (:987-988).
  2. highlightWithoutSearcher checks that the searcher is null and that content is not null, then calls highlightFieldForDoc(null, -1, content) with the caller's full String (:1104-1107).
  3. Nothing downstream cuts: FieldHighlighter and the offset strategies never read maxLength; the only getMaxLength() use in the class is the visitor above.
  4. With the default flags, the re-analysis is done by MemoryIndexOffsetStrategy (chosen at :1294-1302), whose getOffsetsEnum says "note: don't need LimitTokenOffsetFilter since content is already truncated to maxLength" (MemoryIndexOffsetStrategy.java:104). With phrases not position sensitive and both passage relevancy and weight matches off, TokenStreamOffsetStrategy re-analyzes the full text the same way (the fact check's probe ran both strategies: the same snippet).
  5. The break iterator, the scorer and the formatter then see the whole text, so the best passage can lie after maxLength, and the analysis work grows with the whole length.

Exposure and likelihood284 words
  • Who is hit. Every caller of highlightWithoutSearcher (a highlighter built with builderWithoutSearcher, or the deprecated constructor with a null searcher) whose text is longer than maxLength. With the default that is any text over 10,000 chars, such as a full article; with a small withMaxLength almost any text. Every such call skips the cut; the snippet differs when the chosen passage depends on text past maxLength.
  • Default vs opt-in. The entry point is opt-in and rare: its javadoc says "This use-case is more rare", the class is @lucene.experimental, and Lucene itself has no non-test caller. Once used, the default bound is skipped with no option set.
  • Effect on the snippet. A match or passage after maxLength can be returned where the searcher path returns the first passage. The snippet is valid text from the caller's own string.
  • Effect on the work. One probe (StandardAnalyzer, one TermQuery, default maxLength; time is the median of 5 calls, allocation the bytes the thread allocated in the last of them) measured 21 ms and 63.5 MiB for 100,000 chars, 58 ms and 635 MiB for 1,000,000 chars, and 217 ms and 2,538 MiB for 4,000,000 chars; about 1 ms and 6.4 MiB when the caller cuts the text to 10,000 first. Only these sizes, one analyzer and one query were measured: a sanity check on one machine, not a benchmark; the allocation is not retained memory.
  • Not affected. Hits, counts and scores; the searcher entry points with the default loader. No recorded run threw an exception or crashed, with assertions on or off.
  • Why nobody noticed. The output is a plausible snippet, and the upstream tests call highlightWithoutSearcher only on short text.

Why it is a bug, not intended

#
  • The option's javadoc has no exception: "Content will be truncated to this size before highlighting" (getMaxLength); withMaxLength says the same on the Builder that builderWithoutSearcher returns.
  • The re-analysis code on this path relies on it ("content is already truncated to maxLength"), written in the same 2016 commit as the method.
  • No test, javadoc or discussion exempts this path.
The full argument197 words
  • The contract is unconditional. getMaxLength (UnifiedHighlighter.java:596-603, wording from the original 2016 commit) and Builder.withMaxLength (:354, added in #412 / LUCENE-10197, 2021) describe the text that is highlighted, with no exception for any entry point. The highlightWithoutSearcher javadoc (:1078-1093) is silent on maxLength.
  • The code relies on it on this exact path. MemoryIndexOffsetStrategy.java:104 ("content is already truncated to maxLength") came in with highlightWithoutSearcher in 722e8271243 (then in AnalysisOffsetStrategy; moved by LUCENE-7526).
  • The 2021 builder review used this combination. In #412 the withMaxLength wording was suggested in review by @dsmiley, and the PR author's example in the same review was builderWithoutSearcher(indexAnalyzer).withMaxLength(100), with no remark that it has no effect.
  • Tests pin maxLength as visible on the searcher path. TestUnifiedHighlighterMTQ.testWithMaxLen (withMaxLength(25): "ask for 2 but we'll only get 1") and TestUnifiedHighlighter.testFormatWithMatchExceedingContentLength (withMaxLength(17)) assert snippets cut by it. The only highlightWithoutSearcher tests (TestUnifiedHighlighterReanalysis, TestLengthGoalBreakIterator, TestUnifiedHighlighterStrictPhrases.testMatchNoDocsQuery) use short text and the default.
  • Precedent. maxLength edge cases of the predecessor PostingsHighlighter were fixed as bugs: LUCENE-5166 (a term spanning the boundary) and LUCENE-5032 (multi-valued fields exceeding it). No CHANGES, MIGRATE or package entry exempts this path.
The devil's-advocate check220 words

The strongest case for "works as designed" (the intended-behaviour checker, and this hunt's own earlier triage, which had left it as a documentation gap): maxLength is a stored-value loading bound. It is enforced only in LimitedStoredFieldVisitor, whose javadoc says it "honors a max length to retrieve"; a subclass that overrides loadFieldValues also gets uncut text (executed: with a searcher and withMaxLength(20), an override returning the full text gives <b>Lucene</b> is here.); highlightWithoutSearcher loads nothing, its caller owns the String, its javadoc is silent, the class is experimental, and the behaviour has not changed in ten years, so a code change alters what existing callers get.

Why we still read it as a bug: the option's own javadoc describes the highlighted text, not loading; the module's code on this exact path assumes the cut (this shows that the documentation and the implementation disagree, not that the authors considered caller-supplied text and chose to cut it); the default 10,000 is skipped with stock settings, while the override case needs a user to replace the loader on purpose; and we found no doc, test or discussion that records the loading-only reading. Our reading: not intended. The reviewers rated the intended-behaviour case weak to moderate, so a maintainer may fairly prefer to document the gap; the fix section offers both.

Suggested fix

#

Recommended Truncate in highlightWithoutSearcher (recommended, validated)

Cut content to getMaxLength() at the start of highlightWithoutSearcher, as the stored-field loader does, and say so in its javadoc (+6/-1). With it the repro passes and so does the whole highlighter test task (725 tests, assertions on and off). Callers who pass longer text today then get only its first maxLength chars highlighted, worth a CHANGES note.

Objects.requireNonNull(content, "content is required");
if (content.length() > getMaxLength()) {
  // like LimitedStoredFieldVisitor on the searcher path; the offset strategies rely on it
  content = content.substring(0, getMaxLength());
}
Set<Term> queryTerms = extractTerms(query);

Trade-offs

  • Behaviour change for callers who pass more than maxLength chars today (10,000 by default) and rely on highlights beyond it; they would need withMaxLength(...).
  • The cut is in UTF-16 units, like the searcher path's, so it can split a supplementary character; that is the separate bug LFV-775 (the same cut on the searcher path). One surrogate-safe helper can serve both sites.
  • getMaxLength() is overridable and is read twice; a local variable would read it once.
  • Not tested at the edges: withMaxLength(0) (allowed), a maxLength near Integer.MAX_VALUE, an overridden getMaxLength(), or a supplementary character at the cut.

How it was found

#

Code reading (non-formal). A hunt unit checked each documented UnifiedHighlighter option on each of its entry points and saw that maxLength is applied only by the stored-field loader, which highlightWithoutSearcher never calls. A JUnit comparing the same text through a searcher and without one confirmed it.

The method in full104 words
  • Unit. An inventory of override hooks and accessors that can bypass documented behaviour. One leg crossed each documented option with the entry points (the public highlight and highlightFields overloads, the protected highlightFieldsAsObjects they reach, and highlightWithoutSearcher).
  • Signal. Code reading: the only getMaxLength() use is newLimitedStoredFieldsVisitor, reached only from loadFieldValues, and highlightWithoutSearcher never calls it.
  • Witness. A differential public-API JUnit (the same text, query and maxLength through a searcher and without one) failed 1 of 1 on main with assertions on and off, and on 10.5.2 and 9.12.3; with the hunt's cut shadowed it passed (2026-10-27).
  • Independent checks followed (see "Independent checks").

Registry title
UnifiedHighlighter.highlightWithoutSearcher ignores maxLength (the default 10,000 included): it analyzes and highlights the whole supplied text, although getMaxLength and Builder.withMaxLength document that content is truncated to maxLength before highlighting
Area
highlighter / UnifiedHighlighter (highlightWithoutSearcher entry point, maxLength option)
Priority
Low, rank 476: HighlightWithoutSearcher ignores the documented maxLength on a rarely used entry point and only produces a plausible snippet from past the bound plus extra work, so this display-only bug closes the UnifiedHighlighter output rows after LFV-599.
Impact class
minor
Impact note
Hits every application that calls the rarely used, @lucene.experimental UnifiedHighlighter.highlightWithoutSearcher (no searcher, re-analysis offsets) with text longer than maxLength, the default of 10,000 chars included: the whole text is analyzed, a match or passage after maxLength can be returned, and the work grows linearly with the full text length (one probe: about 55 ms and 635 MB of transient allocation per million chars, against about 1 ms when the caller truncates), but there are no wrong hits or counts, no crash and no exception, with -ea and -da alike; the searcher entry points truncate correctly [exec: main, 10.5.2, 10.0.0, 9.12.3, 9.1.0, 9.0.0, 8.11.4, 7.7.3, 7.0.0, 6.6.6, 6.4.0, 6.3.0].
Summary
You build a UnifiedHighlighter without a searcher (builderWithoutSearcher, optionally withMaxLength(20)) and call highlightWithoutSearcher on a text longer than maxLength, expecting the text to be cut to its first maxLength chars before highlighting, as getMaxLength ('Content will be truncated to this size before highlighting') and withMaxLength document and as the searcher entry points do. Instead the whole text is analyzed and highlighted: with maxLength 20, the 48-char text 'Alpha beta gamma. Delta epsilon. Lucene is here.' gives '<b>Lucene</b> is here.' (its only match is at offset 33) where the searcher path returns 'Alpha beta gamma. ', and with the default maxLength of 10,000 a match at char 10,541 of a 10,560-char text is highlighted. The only truncation lives in the stored-field loader (LimitedStoredFieldVisitor), which this entry point never calls, although the re-analysis strategy it uses relies on it ('content is already truncated to maxLength').
