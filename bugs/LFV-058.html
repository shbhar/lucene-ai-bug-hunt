SparseFixedBitSet.nextClearBit returns NO_MORE_DOCS in the last 4096-bit block

SparseFixedBitSet.nextClearBit returns NO_MORE_DOCS once its search reaches the last 4,096-bit block of a set over 2,147,479,552 bits: the block's end, 2,147,479,552 + 4,096, overflows int. BitSetIterator.docIDRunEnd then claims docs not in the set; this needs a segment within 3,966 docs of MAX_DOCS; no in-tree query path using it was found.

The finding in 30 seconds

#

nextClearBit searches block by block and caps each block at Math.min(blockBase + 4096, length), in int. For the last block, which starts at 2,147,479,552, the sum is 2^31: it wraps to -2,147,483,648, so the cap is negative, the block is never read, and the answer is NO_MORE_DOCS.

Background: sparse bit sets, clear bits and run ends

#
  1. SparseFixedBitSet stores bits (doc ids) in blocks of 4,096 and keeps only the non-empty 64-bit words, so a huge, mostly empty set is cheap. The default codec uses one for a segment's deleted docs when at most 1% are deleted.
  2. nextClearBit(i) returns the first bit at or after i that is off, or NO_MORE_DOCS (2,147,483,647) when every bit from i to the end is on.
  3. BitSetIterator.docIDRunEnd() uses it to say where a run of consecutive set bits ends, so a scorer can handle the whole run at once.
  4. A Java int holds at most 2,147,483,647 (2^31 - 1). Adding 1 more wraps around to -2,147,483,648.

The finding, step by step

#
  1. Create an empty new SparseFixedBitSet(Integer.MAX_VALUE): 2,147,483,647 bits, all clear. It is cheap, because a sparse set only allocates its block index.
  2. Call nextClearBit(2147483646). You expect 2147483646: that bit is clear.
  3. You get 2147483647, which is NO_MORE_DOCS. The bit sits in the last 4,096-bit block, which starts at 2,147,479,552. The block's end, 2,147,479,552 + 4,096 = 2^31, does not fit in an int and wraps to -2,147,483,648, so the search skips the block without reading it.
  4. Every set longer than 2,147,479,552 bits has this block; shorter sets are fine. BitSetIterator.docIDRunEnd turns the wrong answer into a run that is too long: on a 2,147,482,624-doc segment with two deletes, the deleted-docs iterator says 1,000 consecutive docs are deleted when only 1 is.

Who is affected

#

Only bit sets longer than 2,147,479,552 bits, when a search reaches their last 4,096 bits. In an index: one segment of more than 2,147,479,552 docs (the top 3,967 sizes, up to and including MAX_DOCS). The wrong value is silent and reachable through public reader API (the deleted-docs iterator), but no in-tree query path that consumes it was found.

Mechanism, terms and numbers654 words

SparseFixedBitSet is Lucene's bit set for sparse sets; the default codec uses it for the deleted docs of sparsely deleted segments. It splits its bits into blocks of 4,096. Its nextClearBit, added in 10.5.0 by #16072 to make BitSetIterator#docIDRunEnd fast, caps the search in each block at Math.min(blockBase + 4096, length), computed in int. For the last block an int-indexed set can have, which starts at 2^31 - 4096 = 2,147,479,552, the sum is 2^31 and wraps to Integer.MIN_VALUE: the block is skipped unread and nextClearBit returns NO_MORE_DOCS although clear bits exist.

Every set longer than 2,147,479,552 bits is affected whenever the search reaches its last block: a start inside it, or an earlier start with every bit from there up to the block set. BitSetIterator#docIDRunEnd turns the wrong answer into a run that covers docs not in the set. Through public reader API, the deleted-docs iterator of a sparsely deleted 2,147,482,624-doc segment (built from a synthetic reader for speed) claims 1,000 consecutive deleted docs where only 1 is. No in-tree query path that consumes the wrong value was found, so the practical impact is very low; the fix is two lines.

The code (main 645d4fe14a20, SparseFixedBitSet.java)

#
private int firstClearInBlock(int i4096, int fromGlobal, int upperBound) {
  final int blockBase = i4096 << 12;                        // :435  last block: 524287 << 12 = 2147479552
  final int blockEnd = Math.min(blockBase + 4096, length);  // :436  2147479552 + 4096 wraps to Integer.MIN_VALUE
  int from = Math.max(fromGlobal, blockBase);
  final int blockCap = Math.min(upperBound, blockEnd);      // :438  Integer.MIN_VALUE
  if (from >= blockCap) {                                   // :439  always true
    return DocIdSetIterator.NO_MORE_DOCS;                   // :440  the block is never read
  }
  • Call chain. nextClearBit(int) and nextClearBit(int, int) (:418-428) call nextClearBitInRange (:484-500), which asks firstClearInBlock block by block and returns NO_MORE_DOCS when every block says none.
  • When. Block i4096 = 524287 exists exactly when length > 2147479552. An empty set is enough: the early return fires before the block's bits are looked at. Lengths up to 2,147,479,552 work; 2147479553, 2147483519 (IndexWriter.MAX_DOCS) and 2147483647 fail. FixedBitSet is correct for the same bits. The search also reaches that block from an earlier start when every bit from there up to the block is set (nextClearBitInRange moves on block by block, :488-498): with only bits 2147479542 to 2147479551 set, nextClearBit(2147479542) returns NO_MORE_DOCS instead of 2147479552 (a scratch check, assertions on and off; fix A passes it).
  • A second wrap behind it. pos = wStart + 64 (:475) overflows on the last 64-bit word (start 2^31 - 64) when length > 2^31 - 64. The early return hides it today. A fix of :436 alone exposes it: on a set of Integer.MAX_VALUE bits whose last word has all its bits set, nextClearBit(2147483584) then returns -2147483648. (The same expression at :459 never runs: inside while (pos < blockCap), the return pos just before it always fires.)

Exposure and likelihood296 words
  • Scale. Bit sets are sized to a segment's maxDoc, so in an index this needs one segment with more than 2,147,479,552 docs: the 3,967 largest legal sizes, up to and including IndexWriter.MAX_DOCS = 2,147,483,519, so within 3,966 docs of it. A set built directly can be any length up to Integer.MAX_VALUE (4,095 bad lengths).
  • Default code builds such sets. The default codec reads live docs with at most 1% deletions into a SparseFixedBitSet(maxDoc) of the deleted docs (Lucene90LiveDocsFormat.java:69, :113-116, :141); BitSet.of and AcceptDocs build one for sparse filters.
  • Public reach (executed). LeafReader#getLiveDocsWithDeletedIterator() (@lucene.experimental) returns that LiveDocs, whose deletedDocsIterator() is a BitSetIterator over it; docIDRunEnd() has no internal marker. On a single on-disk segment of 2,147,482,624 docs (default codec, two deletes, committed and reopened; built for speed with IndexWriter#addIndexes from a synthetic, field-less CodecReader whose overridden accessors are @lucene.internal; normal indexing of that many docs was not run for this bug), the iterator on deleted doc 2,147,481,624 returns docIDRunEnd() = 2,147,482,624 instead of 2,147,481,625. The deleted doc outside the last block gives the right answer. Fails on main, 10.6.0 and 10.5.2.
  • No in-tree consumer found (a grep survey, not a proof). No main-source code calls getLiveDocsWithDeletedIterator() or deletedDocsIterator(); the other production nextClearBit callers (HNSW building) get a FixedBitSet; the AcceptDocs iterators feed kNN, which only calls nextDoc() or bits(). Wrong search hits need custom code, such as a query that hands such an iterator to a conjunction.
  • Silent. No exception and no assertion; the same with assertions on and off.
  • Narrower live-docs window today. On 10.4.0 and later, deletions in a segment above 2,147,482,624 docs cannot be committed at all (a separate bug, LFV-147), so the live-docs path is open for maxDoc in (2,147,479,552, 2,147,482,624].

Why it looks unintended

#
  • BitSet#nextClearBit returns NO_MORE_DOCS only "if every bit in [index, length()) is set"; here every bit is clear.
  • The constructor accepts any length from 1 up, MAX_DOCS allows segments this large, and FixedBitSet returns the right answer for the same bits.
  • Maintainers already fixed an assertion overflow at exactly these lengths in this class (#16347), with a test at length 2,147,479,553.
The full argument186 words
  • Contract. BitSet.java:105-111: "Returns the index of the first unset (clear) bit at or after index, or NO_MORE_DOCS if every bit in [index, length()) is set." :113-117: "Returns the first unset bit in [start, upperBound), or NO_MORE_DOCS if none." DocIdSetIterator.java:251: "All docs in range [docID(), docIDRunEnd()) match this iterator."
  • Any length is accepted. SparseFixedBitSet.java:60-67: "Create a SparseFixedBitSet that can contain bits between 0 included and length excluded"; only length < 1 is rejected. IndexWriter.MAX_DOCS = Integer.MAX_VALUE - 128 (IndexWriter.java:208) makes such segment sizes legal.
  • The code means to cap the block. Math.min(blockBase + 4096, length) exists to stop at length; the wrap defeats it.
  • Precedent. #16347 ("Fix integer underflow in assertion in SparseFixedBitSet", romseygeek, merged 2026-07-03, 10.6.0) fixed the blockCount assertion at these lengths and added TestSparseFixedBitSet.testLargeValuesDoNotOverflow (blockCount(2147479553), the smallest length that fails here). Its body: "the error is only in the assertion; the actual calculated block count is correct and there is no production bug". This one is in the returned value.
  • Why tests miss it. #16072's testNextClearBit uses sets of 1 to 40,000 bits.
The devil's-advocate check181 words

Strongest case for "not a bug" (a cross-model reviewer, OpenAI GPT-5.6, refute lens, who reproduced it and agreed on the cause and the fix): BitSet, SparseFixedBitSet and BitSetIterator are all @lucene.internal, so outside callers cannot rely on them, and no non-internal path had been shown. The reviewer rated this "moderate" and wrote that "nothing ... documents the wrong NO_MORE_DOCS result itself as intended" and that a maintainer "may still reasonably fix this".

Why it fails: the tie-break observed the wrong run end through a consumer path that names no internal type: DirectoryReader, LeafReader#getLiveDocsWithDeletedIterator, the @lucene.experimental LiveDocs, and DocIdSetIterator#docIDRunEnd. (To be fair to the objection: that test built its segment with IndexWriter#addIndexes from a synthetic CodecReader whose overridden accessors are @lucene.internal; an application would have to index more than 2,147,479,552 docs into one segment, which was not run for this bug.) @lucene.internal limits API stability, not correctness, and Lucene's own BitSetIterator relies on this contract. Nor is it absurd input failing loudly: the sizes are within the documented MAX_DOCS, and the failure is silent.

Suggested fix

#

Recommended A. MathUtil.unsignedMin for the block end, stop at the first clear bit past the cap

Compute the block end with MathUtil.unsignedMin(blockBase + 4096, length), and return NO_MORE_DOCS as soon as a word's first clear bit is past the cap, so wStart + 64 cannot wrap either. Validated: the test fails before and passes after; 586 tests pass (every util test class plus the dense-conjunction and live-docs-format suites).

// SparseFixedBitSet.firstClearInBlock
-    final int blockEnd = Math.min(blockBase + 4096, length);
+    final int blockEnd = MathUtil.unsignedMin(blockBase + 4096, length);
...
         final int cand = pos + Long.numberOfTrailingZeros(inv);
-        if (cand < blockCap) {
-          return cand;
-        }
+        return cand < blockCap ? cand : DocIdSetIterator.NO_MORE_DOCS;

A. MathUtil.unsignedMin for the block end, stop at the first clear bit past the cap (validated by the checks) (recommended)

#

Two hunks in SparseFixedBitSet.firstClearInBlock. cand is the first clear bit at or after pos in this word. If it is at or past the cap, no clear bit lies in [pos, blockCap), so NO_MORE_DOCS is the right answer for this block, and returning it skips the increment. On every word but the last, the current code reaches the same answer one step later; on the last word, which starts at 2^31 - 64, it would compute wStart + 64, which wraps (with the first hunk only, the scratch check returns -2147483648). That word's top bit, 2^31 - 1, is below no int length, so it is always clear and the loop always returns at that word.

// SparseFixedBitSet.firstClearInBlock
-    final int blockEnd = Math.min(blockBase + 4096, length);
+    final int blockEnd = MathUtil.unsignedMin(blockBase + 4096, length);
...
         final int cand = pos + Long.numberOfTrailingZeros(inv);
-        if (cand < blockCap) {
-          return cand;
-        }
+        return cand < blockCap ? cand : DocIdSetIterator.NO_MORE_DOCS;

Trade-offs

  • Two lines; MathUtil.unsignedMin is the idiom DenseConjunctionBulkScorer already uses against the same kind of wrap (DenseConjunctionBulkScorer.java:198).
  • unsignedMin takes a moment to read: 2^31 read as unsigned is larger than any length.
  • No extra work on the hot path; the early return skips the rest of the word loop.

Downstream note

#

Downstream relevance only: code that uses a sparse bit set or the deleted-docs iterator as a filter on a segment of more than 2,147,479,552 docs, and trusts docIDRunEnd, could treat docs outside the set as inside it.

How it was found

#

Formal. A CodeQL inventory of int window additions listed this line; a Z3 bit-vector query, with Lucene's documented limits as preconditions, found a wrapping length and proved the line exact only up to 2^31 - 4096. JBMC found it independently on the real bytecode, and an independent verifier reproduced it.

The method in full205 words
  • Sweep. The study's overflow-at-scale experiment (main 7cecf79523, 2026-10-22) used CodeQL to list every non-constant int multiplication, left shift and "x + C" window or block addition in the target packages (602 + 63 rows); SparseFixedBitSet.java:436, :459 and :475 were three of them (:459 later turned out to be unreachable).
  • Solver. Each scale-relevant expression was transcribed into Z3 bit-vector logic with Java wraparound and the documented limits as preconditions. For this line: a counterexample (length 2147483135, block 524287); a proof that the line is exact if and only if length <= 2^31 - 4096; a proof that wStart + 64 is safe up to MAX_DOCS, and a counterexample for lengths above 2^31 - 64.
  • Bytecode. JBMC on the real lucene-core jar found its own counterexample (length 2147480574, start 2147480000, result 2147483647), with blockEnd = blockCap = -2147483648 in its trace; replayed on the JVM it gives the same wrong result. A JVM sweep of 556,920 (length, start) pairs in the safe region found no mismatch.
  • Verification. An independent verifier wrote its own 8 tests (threshold sweep, docIDRunEnd, DenseConjunctionBulkScorer, the second-wrap probe) and reproduced it; the hunt then reduced it to the one-assertion test and found the public live-docs path.

#

LFV-058, snapshot of 2026-11-10

Registry title
SparseFixedBitSet.nextClearBit returns NO_MORE_DOCS in the last 4096-bit block
Area
util / bitsets
Priority
Low, rank 1241: SparseFixedBitSet.nextClearBit returns NO_MORE_DOCS in the last 4096-bit block, which needs a segment past 2^31-4096 docs and custom code, with no in-tree path.
Impact class
silent wrong results
Impact note
Only bit sets longer than 2^31-4096 bits; no in-tree query path was found at that scale; released since 10.5.0.
Summary
You call nextClearBit on a SparseFixedBitSet longer than 2^31-4096 bits at a position in its last 4096-bit block. You expect the next clear bit. Instead blockBase + 4096 wraps, it returns NO_MORE_DOCS, and BitSetIterator.docIDRunEnd then claims absent documents (DenseConjunctionBulkScorer collected 3,966 docs instead of 1 in an independent verifier's test).

#16072 (9f33b54a13a) (2026-05-18)
