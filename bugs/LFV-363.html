Taxonomy getTopDims shows another dimension's children under a multi-valued dimension's name

With multi-valued taxonomy dimensions, Facets#getTopDims can return the right dimension name with another dimension's children and childCount (and, with requireDimCount, its value): x with 2 hits comes back as x value=1 [y1 (1)], which are y's numbers. A reused queue entry keeps the old dimension's ordinal; every release since 9.2.0 does this.

The bug in 30 seconds

#

Taxonomy facets can list the top dimensions of a result set with Facets#getTopDims(topNDims, topNChildren); its javadoc says the result equals the first topNDims entries of getAllDims. Dimensions whose documents can carry several values, such as tags or authors, must be declared with FacetsConfig#setMultiValued. The bug hits those.

  1. Declare dimensions x and y multi-valued with requireDimCount (as the getTopDims javadoc advises) and index three documents: x=x1, x=x2, then y=y1. So x is created first.
  2. Run a match-all query and call getTopDims(1, 10) on FastTaxonomyFacetCounts. You expect what getAllDims(10) lists first: x, value 2, children x1 (1) and x2 (1).
  3. You get x with value 1, childCount 1 and the child y1 (1): y's numbers under x's name, and x's own children are gone. No error, with assertions on or off.
  4. Why: dimensions are visited newest first, so y fills the one-slot queue. When x beats it, Lucene reuses the slot and sets its name and value but not its ordinal, and the children are later read from y's ordinal.
  5. The order breaks too: getTopDims(2, 10) over a (3 hits), b (2) and c (1) returns a with value 1 and c's child above b with value 2. Adding the missing bottomDim.dimOrd = dimOrd; fixes it, and the whole facet test suite passes.

Who is affected

#

Applications that call getTopDims on FastTaxonomyFacetCounts or the int and float association facets with multi-valued dimensions, asking for fewer dimensions than the code admits (every dimension with a non-zero value). Deterministic: an older multi-valued dimension that outranks a newer one in the full queue gets the newer one's children. Single-valued dimensions, getAllDims, getTopChildren and SortedSetDocValues facets are correct.

Mechanism, terms and numbers788 words

Facets#getTopDims(topNDims, topNChildren) should return the same as the first topNDims entries of getAllDims. Taxonomy facets compute it with a priority queue of topNDims entries, each holding a dimension's name, ordinal and value. When the queue is full and a dimension beats the bottom entry, TaxonomyFacets#getTopDims reuses that entry and updates its name and value but not its ordinal. A multi-valued dimension's children are computed from that ordinal at the end, so the result carries the pushed-out dimension's children and childCount under the winner's name (with requireDimCount, since 9.3.0, also its value), and the list can fall out of value order. Dimensions are visited newest-created first, so it happens whenever an older multi-valued dimension outranks a newer one already in the queue; with topNDims = 1 a multi-valued winner gets the children of the newest-created dimension with a non-zero value (with requireDimCount, the newest-created one with hits). In the repro, x with 2 hits is returned as x value=1 childCount=1 [y1 (1)]. It needs FacetsConfig#setMultiValued, which multi-valued data requires, and fails with and without requireDimCount. Single-valued dimensions, getAllDims, getTopChildren, hits and SortedSetDocValues facets are correct. Every release from 9.2.0 to 10.5.2 and main is affected; one added line fixes it.

Terms

#
  • Taxonomy facets: each document gets category labels such as x/x1 through FacetField; a side index, the taxonomy, gives each dimension (x) and each label (x/x1) an ordinal, in order of creation. FastTaxonomyFacetCounts counts a query's hits per ordinal; the association facets aggregate a value instead.
  • Multi-valued dimension: FacetsConfig.setMultiValued(dim, true), "Pass true if this dimension may have more than one value per document" (FacetsConfig.java:180-181). Such data needs it: FacetsConfig.build rejects a second value of a single-valued dimension ("is not multiValued, but it appears more than once in this document", FacetsConfig.java:233-241). With setRequireDimCount(dim, true) the dimension's own ordinal is indexed too, so its document count is exact (FacetsConfig.java:190-194, :386-397).
  • getTopDims: "Returns labels for topN dimensions and their topNChildren sorted by the number of hits/aggregated values that dimension matched. Results should be the same as calling getAllDims and then only using the first topNDims" (Facets.java:60-62). Taxonomy facets override it with a priority queue of topNDims entries; each DimValue holds dim, dimOrd and value (TaxonomyFacets.java:46-56, :610-614).

The bug

#
  1. The loop visits dimensions newest-created first: the taxonomy's children array gives "the category that was added last" and each sibling is "the previous youngest child" (TaxonomyIndexArrays.java:253-255, :269; the loop is TaxonomyFacets.java:620-668).
  2. While the queue has room, each dimension with a non-zero value gets a new entry (:652-654). Once it is full, a dimension that beats the bottom entry reuses it: bottomDim.dim = dim; bottomDim.value = dimValue; pq.updateTop(); (:656-662). The entry's dimOrd keeps the ordinal of the dimension that was pushed out.
  3. At the end, a single-valued dimension takes its children from a cache keyed by name (:639-651, :678-680): correct. A multi-valued dimension's children are computed from dimValue.dimOrd (:683), and for multi-valued dimensions with requireDimCount the value comes from that ordinal too (without it, the -1 placeholder; :506-512). createFacetResult(topChildrenForPath, dim) labels the result with the winner's name (:685).
  4. No entry is created after the queue is full, so the ordinals in the queue stay those of the first topNDims dimensions admitted: the newest-created ones with a non-zero value (:652). That includes multi-valued dimensions without requireDimCount, admitted at -1 even without hits (the sibling bug LFV-368). With topNDims = 1 a multi-valued winner therefore gets the children of the newest-created dimension with a non-zero value; with requireDimCount on every dimension, of the newest-created dimension with hits. A single-valued winner keeps its own children, cached by name.

The numbers

#
  • x/y: taxonomy ordinals 1 = x, 4 = y. Visit y: the queue gets {y, 4, 1}. Visit x: 2 > 1, the entry becomes {x, 4, 2}. The result is built from ordinal 4: x value=1 childCount=1 [y1 (1)] instead of x value=2 childCount=2 [x1 (1), x2 (1)].
  • a, b, c with 3, 2 and 1 hits, created in that order, getTopDims(2, 10): [a value=1 childCount=1 [c1 (1)], b value=2 childCount=2 [b1 (1), b2 (1)]], out of value order.
  • Variants the verifiers executed: a name tie between dimensions without dim counts (value -1 each); TaxonomyFacetIntAssociations (dimension a reported with b1 (7)); a multi-valued dimension replacing a single-valued one (value=0 and the loser's child); and, when the pushed-out dimension has no hits (possible only through the sibling bug LFV-368), a null entry with assertions off or an AssertionError at TaxonomyFacets.java:686 with assertions on.
Exposure and likelihood385 words
  • Who is exposed. Applications that call getTopDims on FastTaxonomyFacetCounts, TaxonomyFacetIntAssociations or TaxonomyFacetFloatAssociations (all three executed; the float class with a value source and with indexed associations) with dimensions declared multi-valued, and ask for fewer dimensions than the code admits: every dimension with a non-zero value (TaxonomyFacets.java:652), which includes multi-valued dimensions without requireDimCount even when they have no hits (:637, the sibling LFV-368). The exact trigger is a multi-valued winner replacing the bottom entry of a full queue. The association facets cannot follow the javadoc's requireDimCount advice (FacetsConfig.build rejects it, FacetsConfig.java:305-307), so for them the value stays the -1 placeholder while the children and childCount are wrong. Tags, authors or genres must be multi-valued, because FacetsConfig.build rejects a second value otherwise; the demo's association dimensions are multi-valued (AssociationsFacetsExample.java:59-61), though the demo does not call getTopDims.
  • Default vs opt-in. setMultiValued is opt-in (the default dimension config is single-valued) but required for multi-valued data. requireDimCount, which the javadoc recommends for getTopDims, does not help. The defect is in query-time code that runs after counting, so codec, IndexWriterConfig and searcher should not matter; the test (randomized directory, searcher and codec, plain IndexWriterConfig) failed with every seed tried: the fixed seeds and 10 random iterations, on Linux aarch64.
  • Scale. Deterministic for a fixed taxonomy, counts and query; one document with three dimensions is enough. A multi-valued entry is right only when no older multi-valued dimension had to push a newer one out of the full queue; with topNDims = 1 and requireDimCount on every dimension, only when the top dimension is also the newest-created one with hits.
  • Silent. The wrong entry has the right name and plausible numbers, and nothing is thrown (except in LFV-368's null-entry case). FacetResult#equals compares the value, the childCount and every child label and count but ignores dim and path (FacetResult.java:72-79), so a comparison with equals misses it only when all of those happen to match.
  • Not affected. Single-valued dimensions (looked up by name), getAllDims, getTopChildren, getSpecificValue, hits, drill-down, the index (nothing is written) and SortedSetDocValues facets (looked up by name).
  • Reach. getTopDims exists since 9.2.0. GitHub code search of the Elasticsearch, OpenSearch and Solr default branches found 0 hits each for getTopDims, FastTaxonomyFacetCounts and DirectoryTaxonomyReader.

Why it is a bug, not intended

#
  • The javadoc: getTopDims results "should be the same as calling getAllDims and then only using the first topNDims".
  • It fails with requireDimCount, the setting the javadoc recommends; the SortedSetDocValues version of the same algorithm looks children up by name and is correct.
  • No upstream test runs the replacement branch with a multi-valued dimension; no commit ever set dimOrd there.
The full argument289 words
  • Contract. Facets.java:60-64: "Returns labels for topN dimensions and their topNChildren sorted by the number of hits/aggregated values that dimension matched. Results should be the same as calling getAllDims and then only using the first topNDims. Note that dims should be configured as requiring dim counts if using this functionality to ensure accurate counts are available". FacetResult: dim is the "Dimension that was requested", value the "Total number of documents containing a value for this path", labelValues its "Child counts" (FacetResult.java:24-40). The base method is getAllDims(topNChildren).subList(...) (Facets.java:69-72). Taxonomy facets inherited it only in development history (before #779/#806 on main and #889 on branch_9x); no release shipped that, since 9.1.0 has no getTopDims and 9.2.0 contains #889.
  • Twin. AbstractSortedSetDocValueFacetCounts#getTopDims runs the same queue and the same two-field update (:206-208), but has no ordinal in its entry and looks children up by name (:226, :228): correct.
  • Tests. TestTaxonomyFacetCounts#testCountRoot (getTopDims(1, 10) at :677), testGetFacetResultsTwice (:722) and testSparseFacets (:253), and TestTaxonomyFacetValueSource (:219, :702) use single-valued dimensions; testRandom asks for every dimension (:1062). The multi-valued tests of TestTaxonomyFacetCounts (setMultiValued at :390, :430, :481, :533) do not call getTopDims, and TestTaxonomyFacetAssociations calls getTopDims(10, 10) for its 4 multi-valued dimensions, more slots than dimensions. A grep of the test trees finds no test that runs the replacement branch with a multi-valued dimension. The tests compare with FacetResult#equals (for example :678, :722), which ignores dim.
  • History. Introduced by the LUCENE-10488 optimisation (#779, #806, backport #889). git log -S 'bottomDim.dimOrd' over the full history finds no commit; nobody raised it in the review threads of 12 related PRs.
The devil's-advocate check203 words

The strongest "intended" case: Facets is @lucene.experimental; the javadoc says "should be the same", soft wording, and advises requireDimCount; the finder's first repro needs a three-way tie broken by name; the default single-valued dimensions are fine; and FacetResult#equals ignores the name anyway.

Why it fails: @lucene.experimental is about API stability, not wrong numbers. The recommended requireDimCount setting fails with no tie at all (x/y, a/b/c), and the value and childCount are wrong too, so equals sees it. Multi-valued dimensions are a designed-for input: getTopDims has its own multiValued/requireDimCount branch (TaxonomyFacets.java:629-638), and multi-valued data cannot be indexed any other way. The SortedSetDocValues version of the same algorithm is correct, and the fix costs nothing. Both reviews that rated the intended-behaviour argument called it weak; the devil's advocate rejected it (bug real, high confidence) and the adjudication confirmed the bug with high confidence. Two narrower points stand: without requireDimCount, ranking dimensions by the -1 placeholder and then by name is intended (accurate counts need requireDimCount), so there only the wrong children and childCount are the bug; and the association facets cannot set requireDimCount at all (FacetsConfig.java:305-307), so for them the javadoc's advice cannot be followed.

Suggested fix

#

Recommended Set the ordinal when the bottom entry is reused

Add bottomDim.dimOrd = dimOrd; next to bottomDim.dim = dim; in TaxonomyFacets#getTopDims, so the reused queue entry gets the winner's ordinal. The repro, the other repros and the whole lucene/facet test suite pass with it, assertions on and off. Mention open PR #13287, which edits the same lines.

                DimValue bottomDim = pq.top();
                bottomDim.dim = dim;
+               bottomDim.dimOrd = dimOrd;
                bottomDim.value = dimValue;
                pq.updateTop();
All options and trade-offs4 options · 619 words

The reused entry then describes the winner completely and the result phase computes the winner's own children; no extra work. Until a fix ships, applications can call getAllDims(topNChildren) and take the first topNDims entries, which is what the base Facets#getTopDims does. Only query-time results change, so no reindex is needed. Either way, add a test that compares getTopDims with the getAllDims prefix for multi-valued dimensions with fewer slots than dimensions and an older dimension winning, and that compares the dimension name, since FacetResult#equals ignores it. Open PR #13287 (2024, stale) rewrites the same replacement block for zero-valued dimensions and also sets only dim and value; a fix will conflict with it. The sibling LFV-368 (dimensions without hits admitted with the -1 placeholder) needs its own fix in the admission line.

Downstream note

#

GitHub code search of Elasticsearch, OpenSearch and Solr found no use of getTopDims, FastTaxonomyFacetCounts or DirectoryTaxonomyReader, so the exposure found is in applications that use Lucene's facet module directly.

How it was found

#

An AI finder suspected the stale ordinal while reading TaxonomyFacets#getTopDims to build a bounded-exhaustive check of the facet result API, which compares getTopDims with the getAllDims prefix over every subset of hits of 12 modelled documents. The check then reported wrong taxonomy entries in every stock run, and the finder reduced it to a JUnit test.

The method in full169 words

Method: semi-formal. The hypothesis came from code reading; a bounded-exhaustive translation-validation harness witnessed it, and a public-API JUnit test reproduced it.

  • The harness models 12 documents over taxonomy and SortedSetDocValues facets and checks every one of the 2^12 hit subsets per seed, with and without 1,100 padding documents, several segment layouts and deletions, comparing getTopDims with the getAllDims prefix and with exact counts.
  • On stock main every one of 8 runs reported wrong taxonomy getTopDims results (seed 1: 1,920 mismatching taxonomy getTopDims results without a null entry among 3,504 mismatches in 703,437 checks; the other 1,584 contain a null entry, in taxonomy and SortedSetDocValues facets, the symptom of the sibling bug LFV-368).
  • With this one-line fix and the sibling's fix, 184 of 192 configurations completed with 0 mismatches in 131,356,014 checks; the other 8 stopped at the harness's own setup check (AssertionError: maxDoc) before checking anything.
  • The finder then wrote a one-document JUnit test (three tied dimensions); the independent reproducer added the no-tie x/y case used here.

History

#

Introduced by the 2022 getTopDims optimisation for taxonomy facets (#779, #806; backport #889) and first released in 9.2.0. Every release from 9.2.0 to 10.5.2 and main fails; from 9.3.0 (#915) every multi-valued dimension is affected and the value and childCount are wrong too. Not fixed upstream.

Versions tested7 rows

Introduced by LUCENE-10488 "Optimize Facets#getTopDims" (issue #11524): #779 (57f8cb2fd6b, IntTaxonomyFacets) and #806 (f0ec2261672, FloatTaxonomyFacets) by @Yuti-G, approved by @gsmiller, merged 2022-05-13; branch_9x backport #889 (87655fd015c) the same day. Before it (and before #779/#806 on main), taxonomy facets inherited the correct base getTopDims, but only in development history: no release shipped that, since 9.1.0 has no getTopDims and 9.2.0 contains #889. 9.3.0: LUCENE-10585 (#915, 8db1e41fc07; branch_9x 075f5103e9a) sent every multi-valued dimension down the uncached path and built the value and childCount from the recomputed children; hierarchical single-valued dimensions, affected in 9.2.0, have been cached since. #12966 (9ba4af7b883, first in 10.0.0; 9.11.0 got the backport 42884fab46d, #13358) merged the int and float copies into TaxonomyFacets and #14761 (a7704f5242d) switched to a comparator queue; both kept the omission. LFV-363, snapshot of 2026-10-30

Registry title
Taxonomy Facets#getTopDims returns another dimension's children, childCount and value under a multi-valued dimension's name, because replacing the bottom of the top-dims queue updates dim and value but not dimOrd (released since 9.2.0)
Area
facet / taxonomy facets (TaxonomyFacets#getTopDims, shared by FastTaxonomyFacetCounts and the int and float association facets)
Priority
Medium, rank 154: GetTopDims can silently give one dimension's entry another dimension's children, which is plausible, but it needs multi-valued dims with requireDimCount, a narrower configuration than its sibling LFV-368.
Impact class
silent wrong results
Impact note
Applications that call Facets#getTopDims(topNDims, topNChildren) on taxonomy facets (FastTaxonomyFacetCounts, TaxonomyFacetIntAssociations, TaxonomyFacetFloatAssociations) with dims configured through FacetsConfig#setMultiValued (with requireDimCount, as the getTopDims javadoc advises, or without) and with more dims with hits than topNDims silently get an entry that has the right dim name but another dimension's children, childCount and (since 9.3.0) value whenever a dim visited later outranks the queue bottom (dims are visited newest-created first, so typically when an older dim wins); the winner's own children are missing and the list can be out of value order; default codec, IndexWriterConfig and taxonomy, one document suffices, -ea and -da, every release from 9.2.0 to 10.5.2 and main; flat single-valued dims (the default DimConfig), getAllDims, getTopChildren, hits and drill-down are correct, and nothing is written to the index.
Summary
You mark taxonomy facet dims as multi-valued, run a query and call getTopDims(1, 10), and expect the same as getAllDims(10).subList(0, 1), as the Facets#getTopDims javadoc says. When the winning dim is visited after the dim it pushes out of the internal top-dims queue (dim x with 2 hits, created first, and dim y with 1 hit, both with requireDimCount), Lucene returns 'dim=x value=1 childCount=1 y1 (1)' instead of 'dim=x value=2 childCount=2 x1 (1) x2 (1)', that is y's children and count under x's name. The queue-replacement branch sets bottomDim.dim and bottomDim.value but never bottomDim.dimOrd, and the children of multi-valued dims are then computed from that stale ordinal.
