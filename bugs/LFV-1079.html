Vector similarity value sources: equals() ignores the similarity function that hashCode() includes, so EUCLIDEAN and COSINE sources compare equal

Two FloatVectorSimilarityFunction value sources over the same vectors, one EUCLIDEAN and one COSINE, score the document vector [2, 1] 0.333 and 0.9, yet equals() returns true while their hash codes differ. The shared base class compares only the two vector sources; one added condition fixes it.

The finding in 30 seconds

#

These value sources compute similarityFunction.compare(v1, v2) for each document. Their base class stores three fields, but equals() compares only the two vector sources, while hashCode() and description() include the function. So two sources that differ only in the function are equal, yet their hash codes differ (with equal operands they could only match if the two enum constants' identity hash codes collided).

Background: vector similarity function queries

#
  1. A ValueSource (module lucene/queries) computes one value per document. FunctionQuery scores each document by it, and FunctionRangeQuery matches the documents whose value lies in a range.
  2. FloatVectorSimilarityFunction(function, v1, v2) (also ByteVectorSimilarityFunction and, on main and branch_11x, Float16VectorSimilarityFunction) computes function.compare(v1, v2), for example a document's vector field against a constant query vector, with any of EUCLIDEAN, DOT_PRODUCT, COSINE or MAXIMUM_INNER_PRODUCT.
  3. ValueSource declares equals and hashCode abstract, and the query classes delegate their equality to it. Java requires that objects that are equals return the same hash code.

The finding, step by step

#
  1. Build two value sources over the vector field v and the query vector [1, 2]: new FloatVectorSimilarityFunction(EUCLIDEAN, new FloatKnnVectorFieldSource("v"), new ConstKnnFloatValueSource(new float[] {1, 2})), and the same with COSINE.
  2. They compute different things: for a document with v = [2, 1] the EUCLIDEAN source gives 0.333 and the COSINE source 0.9. You expect equals() to return false; hashCode() and description() already tell them apart.
  3. Instead equals() returns true, with assertions on and off, in every release since 9.7.0, while the hash codes differ (1652613436 vs 613814086 in one run). Java requires equal objects to have equal hash codes.
  4. The queries built on them inherit it: two such FunctionQuery objects are equal, so List.contains says yes while a HashSet says no, and a FunctionRangeQuery over [0.5, 1] that matches 0 documents equals one that matches 1.
  5. Why: VectorSimilarityFunction.equals compares only vector1 and vector2, while hashCode is Objects.hash(similarityFunction, vector1, vector2). A review commit in the PR that added the class (#12253) dropped the function from equals.

Who is affected

#

Only callers that compare two of these sources (or the queries around them) with different functions over the same operands by equals alone: List.contains, equality-based caches or de-duplication, tests. Inside Lucene no search result changes in practice: these value-source weights are never cached, and query de-duplication is hash-based (barring an identity-hash collision of the two enum constants).

Mechanism, terms and numbers484 words

FloatVectorSimilarityFunction, ByteVectorSimilarityFunction and (on main and branch_11x) Float16VectorSimilarityFunction are lucene/queries value sources that score each document by similarityFunction.compare(v1, v2), for example a document's vector field against a constant query vector. Their shared base class valuesource.VectorSimilarityFunction holds three fields, but its equals() compares only the two vector sources, while hashCode() (Objects.hash(similarityFunction, vector1, vector2)) and description() include the function. So a EUCLIDEAN and a COSINE source over the same field and query vector, which score a document [2, 1] 0.333 and 0.9, compare equal with different hash codes, breaking the java.lang.Object contract; FunctionQuery, FunctionRangeQuery and FunctionScoreQuery pass the false equality on. Inside Lucene no search result changes in practice, because these value-source weights are never cached and query de-duplication is hash-based (only a collision of the two enum constants' identity hash codes could defeat that); only callers that compare with equals alone are misled. It has been in every release since the classes were added in 9.7.0 (#12253): an earlier commit of that PR compared the function, and a review commit dropped it. The fix is one added condition.

The mechanism (main e1faeba08bde, valuesource/VectorSimilarityFunction.java)

#
  1. Three fields: similarityFunction, vector1, vector2 (:29-31), set by the public constructor (:33-41).
  2. The function decides the values. Each subclass's func ends in return similarityFunction.compare(v1, v2); (FloatVectorSimilarityFunction.java:46, ByteVectorSimilarityFunction.java:47, Float16VectorSimilarityFunction.java:46). No subclass overrides equals or hashCode.
  3. equals leaves it out (:79-85): after the this == o, null and getClass() checks it returns Objects.equals(vector1, ...vector1) && Objects.equals(vector2, ...vector2).
  4. hashCode and description() include it: Objects.hash(similarityFunction, vector1, vector2) (:89) and similarityFunction.name() + "(" + ... (:94).
  5. The operands compare by value (ConstKnnFloatValueSource with Arrays.equals, FloatKnnVectorFieldSource by field name), so separately built EUCLIDEAN and COSINE sources over "field v, vector [1, 2]" are equal.
  6. The wrappers pass it on. FunctionQuery.equals is sameClassAs(other) && func.equals(...) (FunctionQuery.java:180-182); FunctionRangeQuery compares its bounds and Objects.equals(valueSource, other.valueSource) (FunctionRangeQuery.java:115-125); FunctionScoreQuery compares its source (FunctionScoreQuery.java:144-149), and ValueSource.asDoubleValuesSource() wraps with Objects.equals(in, that.in) (ValueSource.java:249-253). FunctionScoreQuery use became possible in 10.4.0 (#15328).

The numbers (illustration probe, main, not the repro)

#

One document with v = [2, 1] and the query vector [1, 2]: EUCLIDEAN gives 1 / (1 + 2) = 0.333, COSINE (1 + 0.8) / 2 = 0.9. equals is true and the hash codes are 1652613436 and 613814086 (the function's part of the hash is the enum constant's identity hash, so the numbers can change between JVM runs: both runs of this probe printed this pair, the probe behind the diagram printed -1860021253 and -1987185915; they differed in every recorded run). List.of(euclideanQuery).contains(cosineQuery) is true, a HashSet of the same query says false. FunctionRangeQuery(source, 0.5f, 1f, true, true) matches 0 documents with EUCLIDEAN and 1 with COSINE, and the two range queries are equals.

Exposure and likelihood360 words
  • Who is exposed. Callers that compare these value sources or the queries around them with equals alone, for example List.contains, indexOf or remove, an equality-based cache or request de-duplicator, or a test that asserts two queries differ, and that see two functions over the same operands.
  • What does not break inside Lucene. The weights are never cached: isCacheable returns false in FunctionQuery (FunctionQuery.java:82-83), FunctionRangeQuery (FunctionRangeQuery.java:177-178) and the asLongValuesSource and asDoubleValuesSource wrappers (ValueSource.java:150-151, :230-231), so LRUQueryCache never keys on them. FunctionScoreQuery's scoring weight is cacheable only when both its inner weight and its source are (FunctionScoreQuery.java:280-282), so never with these sources; when scores are not needed it returns the inner query's weight itself (:117-120), which may be cached but whose matches do not depend on the function. BooleanQuery keeps its clauses in a Multiset / HashSet (BooleanQuery.java:132-140) and DisjunctionMaxQuery its disjuncts in a Multiset (DisjunctionMaxQuery.java:47); these compare hash codes first, which differ. Executed: a BooleanQuery with SHOULD EUCLIDEAN + SHOULD COSINE keeps both clauses (score 0.333 + 0.9 = 1.2333). No full sweep of in-tree consumers was run. One theoretical exception: with equal operands the two sources' hash codes are equal exactly when the two enum constants' identity hash codes are (Objects.hash multiplies the function's hash by 961, an odd number), and identity hash codes are not unique; in a JVM run where they collided, these sets and BooleanQuery.deduplicateClauses (BooleanQuery.java:714-716) would reach the wrong equals and could merge the two clauses. Never observed; not claimed.
  • Downstream. Solr's vectorSimilarity() builds these classes, and its 4-argument form takes the function from the request. Whether a Solr cache could mix them up was not tested (the devil's-advocate verifier only re-did Solr's key hash arithmetic by hand), so it is not claimed.
  • Default vs opt-in. Opt-in lucene/queries classes, not on the default search path. No index, codec or setting matters; assertions on or off behave the same.
  • How likely. Rare: it needs an equals-only caller that meets two functions over the same operands, and no report of it was found since 9.7.0 (June 2023).

Why it looks unintended

#
  • The function decides the values, and hashCode() includes it: equal objects with different hash codes are wrong under any equality definition.
  • The PR that added the class compared the function in equals; a review change adding getClass() and null checks dropped it, unremarked.
  • LUCENE-7736: equals must "never return true for values sources that could return different values".
The full argument188 words
  • Contract. ValueSource declares equals and hashCode abstract (ValueSource.java:51-55); core Query.java:95-100 asks subclasses to implement equivalence "properly ... so that QueryCache works properly". java.lang.Object#hashCode requires objects that are equal by equals to return the same hash code; here they are equal and their hash codes differ.
  • Maintainer rule. On LUCENE-7736 (#8787) jpountz wrote: "I think it's important for equals to behave correctly and never return true for values sources that could return different values." romseygeek agreed in the next comment ("I'll change things back again").
  • Siblings. Other value sources put every value-deciding parameter in equals, for example LinearFloatFunction compares slope, intercept and source (LinearFloatFunction.java:85-91).
  • Tests. TestKnnVectorSimilarityFunctions has no equals, hashCode or QueryUtils assertions; it passes unchanged with the fix.
  • History. In PR #12253, commit 901febe400 (2023-06-13) compared similarityFunction in equals. uschindler's review asked for a getClass() check and a this == other / null check; commit 7219987d52 ("Addressing review") added them, and the function term disappeared, while hashCode kept the field. No review or conversation comment on the PR mentions leaving it out. The PR was squash-merged as 14c18d86245 (2023-06-14, 9.7.0).
The devil's-advocate check134 words

The strongest "intended" case (built by the devil's-advocate verifier; the cross-model lenses rated it weak): equality identifies only the subclass and its two operands, the function is "implied" by the vector field, and Query.equals' javadoc speaks of "document-filtering properties", which a FunctionQuery (it matches every document) does not change.

Why it fails: it cannot explain why hashCode() and description() include the function, and equal objects with different hash codes are wrong under any equality definition. The function is an independent constructor argument (func never reads the field's own similarity, and Solr's 4-argument form lets a request choose it). For FunctionRangeQuery the function does decide which documents match (0 vs 1 hits in the probe, still equals). And the PR history is consistent with an accidental omission. Verdict: a defect, Low.

#

Recommended Compare the similarity function in equals (fix A)

Compare the function in equals: add similarityFunction == ((VectorSimilarityFunction) o).similarityFunction && before the two operand checks, one line. Compare the similarity function in equals (fix A) (validated by the checks) (recommended)

#

In VectorSimilarityFunction.equals, compare similarityFunction too, so equals uses the same three fields as hashCode. The field is an enum, so == is exact (and null-safe: the constructor does not null-check the function, VectorSimilarityFunction.java:33-41, though a null one already fails in func and description()). Sources with the same function and operands stay equal, and the three subclasses and every wrapper are fixed at once. LFV-1079, snapshot of 2026-11-03

Registry title
Function-query vector similarity value sources (Float/Byte/Float16VectorSimilarityFunction) leave the similarity function out of equals but hash it, so EUCLIDEAN and COSINE sources over the same vectors compare equal with different hash codes
Area
queries / function queries: valuesource.VectorSimilarityFunction equality (base of Float/Byte/Float16VectorSimilarityFunction, and so of the FunctionQuery, FunctionRangeQuery and FunctionScoreQuery that wrap them)
Priority
Low, rank 799: Since 9.7.0, vector similarity value sources with different similarity functions compare equal but have different hash codes. Lucene's own consumers are hash-based or never cache these queries, so in practice no search result changes and only application code that relies on equals alone is affected, which keeps it Low.
Impact class
minor
Impact note
Only code that builds two of these lucene-queries value sources (or the FunctionQuery, FunctionRangeQuery or FunctionScoreQuery that wrap them) over the same two vector sources with different similarity functions, and then compares them with equals alone (List.contains or indexOf, equality-based de-duplication or caching, tests that assert inequality), treats a COSINE source as the same as a EUCLIDEAN one; inside Lucene no search result changes in practice, because these weights are not cacheable (FunctionQuery, FunctionRangeQuery and ValueSource.asDoubleValuesSource return isCacheable false) and in-tree de-duplication (the BooleanQuery and DisjunctionMaxQuery Multiset/HashSet) is hash-based while the hash codes differ; no index or scale is needed, -ea and -da behave the same, and it has been in every release since 9.7.0.
Summary
You build two function-query value sources over the same vector field and the same query vector, one with EUCLIDEAN and one with COSINE (new FloatVectorSimilarityFunction(EUCLIDEAN, field, target) and the same with COSINE), and expect them to be unequal because they compute different scores; the class itself treats the function as part of its identity, since hashCode() and description() include it. Instead equals() compares only the two vector sources and returns true, while hashCode() returns different values, which breaks the java.lang.Object rule that equal objects have equal hash codes. The Byte and Float16 subclasses share this equals, and FunctionQuery and the other wrappers pass the false equality on.
