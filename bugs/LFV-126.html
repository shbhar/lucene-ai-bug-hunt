MMapDirectory puts a slice's read advice on the wrong bytes when the slice starts inside an mmap chunk and reaches or crosses that chunk's end (10.0.0+)

With read advice on, an MMapDirectory slice that starts inside an mmap chunk and reaches or crosses its end is advised from the chunk start: with 1 MiB chunks, slice [512 KiB, 1.5 MiB) gets MADV_RANDOM on [0, 1 MiB). Reads stay correct; only readahead changes.

The finding in 30 seconds

#

Lucene can tell the operating system how a part of a file will be read, so the OS tunes readahead for those pages only. Here the hint is computed from the wrong starting byte.

Background: chunks, slices and read advice

#
  1. MMapDirectory maps each file in chunks of maxChunkSize bytes: 16 GiB by default on 64-bit JVMs, or a smaller chunk size passed to its constructor (rounded down to a power of two).
  2. A slice is a window [offset, offset + length) of an open file. A compound file (.cfs) packs a segment's small files into one, and Lucene reads each inner file through a slice.
  3. With setReadAdvice (for example ADVISE_BY_CONTEXT), a slice opened with an IOContext gets its own madvise hint: RANDOM turns readahead off for its pages, SEQUENTIAL makes it more aggressive. Lucene advises only the part of the slice that lies in its first chunk.

The finding, step by step

#
  1. Open an MMapDirectory with 1 MiB chunks and setReadAdvice(ADVISE_BY_CONTEXT), write a 2 MiB file and open it normally. The file is mapped as two chunks, [0, 1 MiB) and [1 MiB, 2 MiB).
  2. Take slice("inner", 512 KiB, 1 MiB, context with DataAccessHint.RANDOM), the call the compound-file reader makes for each inner file. The slice is bytes [524,288, 1,572,864): it starts halfway into chunk 0 and ends halfway into chunk 1.
  3. You expect MADV_RANDOM only on the slice's own pages. Lucene advises only the part of a slice in its first chunk, by design, so that is [524,288, 1,048,576).
  4. Instead the random-read flag lands on [0, 1,048,576): the 512 KiB before the slice get it. The slice remembers that it starts 512 KiB into chunk 0, and prefetch() adds that offset (fixed in #14109), but the advice call does not.
  5. In a compound file those bytes belong to other inner files: an .fdt hint covered the compound header and 11 other inner files. A short slice that straddles a chunk boundary can get none of its own pages advised. Every byte read stays correct.

Who is affected

#

MMapDirectory users on Linux or macOS with a 64-bit JVM who set a read-advice function (opt-in since 10.3.0; on 10.1-10.2.x the defaults already advise compound files). An inner file of at least a page must start inside a chunk and reach or cross its end: a smaller maxChunkSize, or a compound file over 16 GiB. Performance only; slowdown not measured.

Mechanism, terms and numbers890 words

MMapDirectory maps a file in chunks (16 GiB by default on 64-bit JVMs, smaller when the application passes a maxChunkSize). With a read-advice function set, IndexInput#slice(name, offset, length, IOContext) gives the slice its own madvise hint, and the compound-file reader uses it so that each inner file advises its own pages. A slice that starts inside a chunk and reaches or crosses that chunk's end keeps the whole first chunk and remembers where it starts inside it, in MultiSegmentImpl.offset. slice(..., IOContext) then advises the slice from its offset 0, and advise() never adds that in-chunk start, so the hint starts at the chunk start instead of the slice start. #14109 fixed the same omission for prefetch() only. In the repro (1 MiB chunks) a slice of [512 KiB, 1.5 MiB) with a RANDOM hint puts MADV_RANDOM on [0, 1 MiB). In a compound file those bytes belong to other inner files, and a short slice straddling a chunk boundary can get none of its own pages advised. Every byte read and every query result stays correct: it is a performance defect, needing a non-NORMAL read advice (opt-in on 10.3.0+ and main, the default on 10.1-10.2.x) and a slice of at least one page that starts inside a chunk and reaches or crosses its end. Affected: every 10.x release and main. No slowdown was measured.

Where it happens (main 645d4fe14a20, store/MemorySegmentIndexInput.java)

#
  1. The slice keeps the whole first chunk. buildSlice (:653-700) copies the chunks the slice touches (:663-667), truncates the last one (:670) and keeps only the in-chunk start, offset = offset & chunkSizeMask (:672). A single-chunk slice cuts its segment to exactly the slice (slices[0].asSlice(offset, length), :680); a multi-chunk slice passes offset to new MultiSegmentImpl(...) (:688-698), which stores it (:848, :871).
  2. The slice is advised from its offset 0. slice(String, long, long, IOContext) (:623-650) returns early for NORMAL advice (:627-630) and for slices shorter than a page (:632-640), then calls:
slice.advise(                                   // :642
    0,
    slice.length,
    segment -> {
      nativeAccess.madvise(segment, advice);
      return true;
    });
  1. advise() does not know about the slice offset. It takes segments[(int) (offset >> chunkSizePower)] (:405) and offset &= chunkSizeMask (:406), clamps the length to that segment (:408-413), rounds to pages (:414-427) and advises segment.asSlice(offset, length) (:429-430).
  2. MultiSegmentImpl translates every other data position. It adds offset in seek (:886-889), the positional read* methods (:896-919), segmentSliceOrNull (:921-934), buildSlice (:936-940) and prefetch (:942-946, the #14109 fix), and subtracts it in getFilePointer() (:891-894) and in the positions it reports in errors (:880-883). It has no advise override. A whole multi-chunk file and its clones have offset 0 (:93-105), so only slices that start inside a chunk are affected, together with their clones (which keep the offset, :578) and slices of them (buildSlice adds the parent's offset, :936-940). A slice that ends exactly on a chunk boundary also gets a 0-byte second segment (:665-670), so it is a MultiSegmentImpl too.

Exposure and likelihood494 words
  • Effect. MADV_RANDOM turns readahead off for the pages it covers, so sequential reads of the neighbouring inner files (for example a merge reading .tim or .pos) take more, smaller page faults. ADVISE_BY_CONTEXT returns SEQUENTIAL for MERGE and FLUSH contexts (MMapDirectory.java:159-161), which makes readahead more aggressive on pages the slice does not own. A short slice straddling a chunk boundary can get no hint on its own pages while its readAdvice field still says RANDOM, which isEfficientFor() trusts (MemorySegmentIndexInput.java:381-392) when the compound reader decides whether to reuse a mapping (Lucene90CompoundReader.java:196). None of this was measured.
  • Correctness is unaffected. The hint is NORMAL, RANDOM or SEQUENTIAL on a read-only mapping of the same file. Reads go through the slice's own segments and offset, which the bug does not touch.
  • Platform. madvise is used only on Linux and macOS (NativeAccess.java:41-46) and only on 64-bit JVMs (PosixNativeAccess.java:66-67).
  • Default vs opt-in. On main and 10.3.0-10.6.0 the default read-advice function returns Optional.empty() (MMapDirectory.java:172-173), which maps to Constants.DEFAULT_READADVICE, NORMAL (MMapDirectory.java:326-328, Constants.java:186-189), and NORMAL advises nothing. It takes an explicit setting: in practice setReadAdvice, for example with ADVISE_BY_CONTEXT (MMapDirectory.java:157-170). The other setting, the system property org.apache.lucene.store.defaultReadAdvice (Constants.java:181-189), gives every file and context the same advice, so the whole compound file already carries it and the misplaced hint changes nothing visible (by reading). On 10.1.0-10.2.2 the default settings already advise compound inner files. On 10.0.0 only direct slice(..., ReadAdvice) calls are affected.
  • Callers. The in-tree callers of slice(..., IOContext) are the compound readers: Lucene90CompoundReader (:195, :207, :210) and SimpleText's compound format (SimpleTextCompoundFormat.java:138-139, a debugging codec); applications and custom codecs may call it too.
  • Layout. The slice must start inside a chunk and reach or cross that chunk's end. With the default 16 GiB chunk (MMapDirectory.java:185-186) that needs a compound file above 16 GiB, which the defaults make unusual: by default a merged segment is a compound file only up to 64 MB with byte-size merge policies such as the default TieredMergePolicy, or up to 65,536 documents with LogDocMergePolicy (CompoundFormat.java:38-42, :163-180). Realistic triggers are a smaller maxChunkSize (public constructor MMapDirectory(Path, long); the class javadoc recommends reducing the chunk size when mapping fails, MMapDirectory.java:49-50, though on 64-bit it says the chunk "should always be large (like 16 GiBytes)", :241-242) or raised compound-file thresholds together with segments above 16 GiB (the default TieredMergePolicy keeps merged segments below 5 GB, TieredMergePolicy.java:77, so that also takes a larger maximum segment size or a forceMerge). With 1 MiB chunks the end-to-end tests needed only 400 and 2,000 documents.
  • Size of the misplaced range. At most one chunk (min(length, C)) of the same file. In the compound-reader path it happens once per inner-file open (segment open, merge), not per query; other callers of the public API choose their own frequency.

Why it looks unintended

#
  • The compound reader slices each inner file "so inner files advise their own pages"; slice() even skips sub-page files to spare neighbours' advice.
  • #14109 fixed the same missing offset in prefetch() as a bug (10.2.0); advise() was missed.
  • "Advice is best effort" covers advice that stops at the first chunk or is page-rounded, not advice moved before the slice.
The full argument224 words
  • The API exists to advise one inner file. The IndexInput#slice(String, long, long, IOContext) javadoc: "This is typically used by CompoundFormat implementations to modify the IOContext for specific files within the compound file" (IndexInput.java:126-139).
  • The code says neighbours must not be advised. slice(..., IOContext) skips slices shorter than a page because advising them means "potentially overriding the advice of other files that share the same pages" (MemorySegmentIndexInput.java:633-638). The compound reader opens its extra mapping "without advice, like handle, so inner files advise their own pages" (Lucene90CompoundReader.java:202). In the #16883 review, jimczi wrote that "each inner file advises its own pages through its slice".
  • The same omission was fixed as a bug. #14109, "prefetch may select the wrong memory segment for multi-segment slices", is under Bug Fixes for 10.2.0 (lucene/CHANGES.txt:1998-1999): "When sliced, a multi-segment index input uses an offset into the initial memory segment. This offset should be added to the prefetch offset to determine the absolute offset." uschindler's review there: "it's way too easy to add new methods but forget to look at code of methods ... prefetch just works". That fix overrode prefetch() only.
  • No test pins the current range. TestMMapDirectory#testPrefetchWithMultiSegment "does not verify that the actual segment is prefetched" (TestMMapDirectory.java:468). TestMMapDirectory, TestMultiMMap and TestLucene90CompoundFormat pass on the stock jar and with the fix.
The devil's-advocate check204 words

The strongest case for "intended": read advice is a best-effort hint. The javadoc says "only certain IOContext may be usable here" (IndexInput.java:130-131); advise() deliberately advises only the first chunk ("this case is rare enough that we don't try to optimize it and keep things simple", MemorySegmentIndexInput.java:409-411); the sub-page comment accepts that an inner file can override a neighbour's advice on shared pages; and the #16883 review deferred rounding the advised range inwards (jimczi: "We could, by rounding the advised range inwards so only pages fully inside the inner file get advised ... Could we do it in a follow up?").

Why it fails: each accepted imprecision is advice that does not reach far enough (later chunks) or one shared page at each end of an inner file. This defect moves the window up to a whole chunk before the slice, onto other files, and can miss the slice entirely; rounding inwards would act inside the same wrong window. The same missing offset in advise()'s other caller was treated as a bug. The works-as-designed reviewer (OpenAI GPT-5.6) rated the intended argument "moderate" and still judged the bug real; the devil's-advocate verifier found no argument that survives. Verdict: a defect, low severity.

Suggested fix

#

Recommended Override advise() in MultiSegmentImpl; let prefetch() rely on it

Give MultiSegmentImpl an advise() override that adds the slice's in-chunk offset, as its seek, read* and buildSlice already do, and drop the same addition from its prefetch() override, which goes through advise(). Validated: the repro passes with assertions on and off, and 180 tests of the closest suites and the core lint checks pass.

   @Override
   public boolean prefetch(long offset, long length) throws IOException {
     Objects.checkFromIndexSize(offset, length, this.length);
-    return super.prefetch(this.offset + offset, length);
+    return super.prefetch(offset, length);
+  }
+
+  @Override
+  boolean advise(long offset, long length, IOFunction<MemorySegment, Boolean> advice)
+      throws IOException {
+    // offsets are relative to this slice; segments[0] starts this.offset bytes before it
+    return super.advise(this.offset + offset, length, advice);
   }
All options and trade-offs3 options · 535 words

One option was validated through Gradle in a scratch worktree of 645d4fe14a20; the study had validated the same diff by shadowing the class.

Override advise() in MultiSegmentImpl; let prefetch() rely on it (validated by the checks) (recommended)

#

In MemorySegmentIndexInput.MultiSegmentImpl: advise() adds this.offset, and the prefetch() override keeps its bounds check but passes the slice-relative offset, because the base prefetch() calls advise() (:366), which now adds the offset once. Both callers of advise() then pass slice-relative offsets, the convention of every other MultiSegmentImpl method. +8/-1 lines in one file.

   @Override
   public boolean prefetch(long offset, long length) throws IOException {
     Objects.checkFromIndexSize(offset, length, this.length);
-    return super.prefetch(this.offset + offset, length);
+    return super.prefetch(offset, length);
+  }
+
+  @Override
+  boolean advise(long offset, long length, IOFunction<MemorySegment, Boolean> advice)
+      throws IOException {
+    // offsets are relative to this slice; segments[0] starts this.offset bytes before it
+    return super.advise(this.offset + offset, length, advice);
   }

Trade-offs

  • prefetch() advises the same absolute range as before.
  • Nuance: a multi-chunk slice whose start is not page-aligned now rounds its first page down (with chunks of at least a page, its segments[0] starts on a page boundary), so up to pageSize-1 bytes of the preceding inner file can still get the hint, while a single-chunk slice skips the shared first page (MemorySegmentIndexInput.java:414-427). That is the one-shared-page limitation the #16883 review accepted; the third option would make both consistent.
  • Main only: on 10.x advise() is void advise(long, long, IOConsumer<MemorySegment>) and prefetch() returns void (10.6.0 MemorySegmentIndexInput.java:404, :962), so a backport needs the same change with those signatures.
  • No benchmark was run.

What the checks validated

  • With the fix, the closest suites pass: TestMMapDirectory (70), TestMultiMMap (73), TestLucene90CompoundFormat (36) and the repro: 180 tests, 0 failures, 1 skipped (testLargeCFS, @Nightly).
  • :lucene:core:checkGoogleJavaFormat, ecjLintMain and ecjLintTest pass with the repro test in place.
  • In the study, the same diff alone passed the verifiers' own tests (including an end-to-end compound-file test) and 178 upstream tests with -ea (the refute reviewer's own tests also with -da; the study's -da run of the 178 tests combined it with another fix of the same unit). A probe shows it advises [524288, 1048576) in the repro.

Advise through the parent at the call site

#

In slice(..., IOContext), call advise(offset, length, ...) on the input being sliced instead of slice.advise(0, slice.length, ...).

Trade-offs

One line, but correct only when the parent's offset is 0 (a whole file, as in the compound reader); a slice of a multi-chunk slice would still be advised wrongly, and it leaves the trap the #14109 review described. Not validated.

Follow-up: round a slice's advised range inwards

#

Advise only pages fully inside the inner file, as agreed as a follow-up in the #16883 review.

Trade-offs

The helper is shared with prefetch(), which needs outward rounding (jimczi, #16883), so it needs a parameter or a second helper. It does not fix this bug on its own. Not validated.

How it was found

#

Semi-formal: while writing a Z3 bit-vector model of the MemorySegmentIndexInput chunk arithmetic, the hunting AI tool noticed that MultiSegmentImpl overrides prefetch() but not advise(), and the solver witnessed it (the advised range starts before the slice). A JUnit reading /proc/self/smaps then showed it on the stock jars.

The method in full155 words

Method: semi-formal (a hypothesis formed while modelling, then witnessed by the solver). A hunt unit modelled the chunk arithmetic of MemorySegmentIndexInput (seek, slice, prefetch and advise ranges) in Z3 bit-vector arithmetic, 44 queries.

  • While writing the model the AI tool noted that MultiSegmentImpl overrides prefetch() (the #14109 fix) but not advise(). One query, declared expect="sat" with that reasoning in its comment, was SAT: the range slice(..., IOContext) advises starts at the chunk start, before the slice. All 44 queries matched their declared expectation; it is the only one about advise(), and the prefetch range proofs hold (the other counterexample queries concern different findings of the same unit).
  • Because the hypothesis came before the solver's answer, the finding is classed as semi-formal, not formal.
  • The defect was then executed on the stock jars by reading the per-mapping random-read flag (rr) from /proc/self/smaps, and reproduced by every verifier with its own test.

History

#

Introduced in 10.0.0 by #13467 (cfbf8d93df81, merged 2024-06-21), which added the slice-with-advice API and the slice.advise(0, ...) call; compound files reach it since 10.1.0 (#13907). Every 10.x release and main are affected; not fixed upstream.

Versions tested6 rows

Introduced by apache/lucene#13467, "Honor read advice on compound files." (cfbf8d93df81, jpountz, merged 2024-06-21 before the 10.0 branch was cut; earliest tag 10.0.0). It added IndexInput#slice(String, long, long, ReadAdvice), turned the prefetch() body into the shared advise() helper and added the slice.advise(0, slice.length, ...) call. The defect was born with the API, so the before/after pair is the releases 9.12.0 (no API) and 10.0.0 (fails).

Related: #13337 / #13363 (2024-05, prefetch() and the segment-selection lines advise() reuses); #13907 (e2636c648df, 2024-10-15, "Only call madvise when necessary.": the compound reader slices each inner file with its own advice, from 10.1.0); #14109 (d4f0a3244e5, 2025-01-08, the sibling fix in prefetch() only, 10.2.0); #14482 (bb76f0a2d98, 2025-04-30, slice(..., IOContext) replaces the ReadAdvice overload and keeps the call); #15040 (cefc6c7cfbf, 2025-08-08, default advice NORMAL, so 10.3.0+ needs opt-in). The releases not executed (10.2.0, 10.2.1, 10.3.1-10.5.1) have the same code by source identity.

Registry title
MMapDirectory applies a slice's read advice to the wrong bytes when the slice starts inside an mmap chunk and crosses into the next one (the #14109 prefetch fix missed this caller of advise())
Area
store / MMapDirectory read advice (MemorySegmentIndexInput slices, compound files)
Priority
Low, rank 863: MMapDirectory applies a slice's read advice to the wrong bytes when the slice crosses an mmap chunk boundary, performance only and needing non-default advice plus a non-default chunk size or a compound file over 16 GiB.
Impact class
minor
Impact note
Applications that use MMapDirectory where madvise is available (Linux or macOS, 64-bit JVM, native access) with a non-NORMAL read advice for some files (opt-in on 10.3+ and main through setReadAdvice, for example ADVISE_BY_CONTEXT; the default on 10.1-10.2.x) and that have a compound-file inner file, or a direct IndexInput#slice(..., IOContext) call, that starts inside an mmap chunk and crosses into the next one (a non-default maxChunkSize, or a compound file larger than the 16 GiB default chunk); performance only, deterministic with -ea and -da: up to one chunk of neighbouring bytes of the same file gets the hint and a short slice can get none of its own pages advised, while every byte read and every query result stays correct; the real-world slowdown was not measured; released since 10.0.0.
Summary
You take a slice of an MMapDirectory file with IndexInput#slice(name, offset, length, IOContext) and a context that asks for RANDOM or SEQUENTIAL read advice, as the compound-file reader does for each inner file, and you expect the madvise hint to land on the slice's own pages. When the slice starts inside an mmap chunk and crosses into the next chunk, the hint is applied from the start of that chunk instead: in the repro, a slice of [512 KiB, 1.5 MiB) with 1 MiB chunks puts the RANDOM hint on [0, 1 MiB), so other inner files of a compound file get it, and a short slice that straddles a chunk boundary can get none of its own pages advised. Reads and query results stay correct; only the operating system's readahead and caching behaviour on those pages changes.
