Flexible StandardQueryParser ignores setFuzzyMinSim: a fuzzy term without a number always gets 2 edits

With setFuzzyMinSim(1f), the flexible StandardQueryParser still parses lucene~ to lucene~2: its grammar writes the default 2 edits into every fuzzy term typed without a number, and the configured value only replaces an unset one, which that grammar never produces. The classic QueryParser honours the setting; all 12 releases run, 2.9.0 to 10.6.0, are affected, and so is main.

The finding in 30 seconds

#

setFuzzyMinSim sets how many edits a fuzzy term typed without a number (term~) may have; an explicit term~N always wins. The classic and the flexible query parser both get this setter from one shared interface, CommonQueryParserConfiguration.

  1. Index three one-word documents: lucene, lucena (1 edit away) and lucxna (2 edits away). Create a StandardQueryParser and call setFuzzyMinSim(1f): a fuzzy term without a number should now allow at most 1 edit.
  2. Parse lucene~ and search. You expect f:lucene~1 and 2 hits, which is exactly what the classic QueryParser gives with the same setting.
  3. Instead you get f:lucene~2 and 3 hits, lucxna included. No error, and getFuzzyMinSim() still returns 1.0.
  4. Why: for a ~ with no number the grammar fills in FuzzyQuery.defaultMaxEdits (2). FuzzyQueryNodeProcessor copies the configured value only onto a node whose value is unset (below 0), which the grammar never produces, so the setting never reaches a query.

Who is affected

#

Applications on the flexible StandardQueryParser that call setFuzzyMinSim with a value that does not itself give 2 edits (1f, 0f, or a fraction such as 0.8f), and Luke users who lower "Minimal similarity" (Luke's desktop app uses the Standard parser by default). Every bare term~ silently matches up to 2 edits. Explicit term~N and the default setting are unaffected.

Mechanism, terms and numbers506 words

StandardQueryParser#setFuzzyMinSim stores its value in the parser's FuzzyConfig, and FuzzyQueryNodeProcessor copies that value onto a fuzzy node only when the syntax parser left the node's similarity unset (below 0). The grammar never does: for a ~ without a number it writes FuzzyQuery.defaultMaxEdits (2), and a number after ~ is never negative (the grammar's NUMBER token is unsigned). So with the stock syntax parser a non-default setFuzzyMinSim never reaches a parsed query: with setFuzzyMinSim(1f), lucene~ parses to lucene~2 and also matches words two edits away, while getFuzzyMinSim() returns 1.0 and the classic QueryParser, which implements the same interface method, gives lucene~1. setFuzzyPrefixLength, stored in the same FuzzyConfig, is applied; an explicit term~N and the default setting are unaffected. Present since the flexible parser was first committed (2009, release 2.9.0) through 10.6.0 and main. A one-line grammar change that leaves a bare ~ unset fixes it.

  • StandardQueryParser#setFuzzyMinSim (StandardQueryParser.java:509-519) only stores the value with fuzzyConfig.setMinSimilarity(...), first creating a FuzzyConfig if none is set; getFuzzyMinSim (:463-473) reads it back. With the stock syntax parser, that getter is the setter's only observable effect (only a custom syntax parser installed with setSyntaxParser could leave the value unset and so get it applied).
  • FuzzyQueryNodeBuilder turns the node's value into edits with FuzzyQuery.floatToEdits: a value of 1 or more is truncated to whole edits, at most 2 (1.5 gives 1, 3 gives 2), 0 is exact, a fraction s gives (int) ((1 - s) * termLength), at most 2. For the bare lucene~ the value is 2, so 2 edits.
  • The classic parser does what the setter promises: QueryParserBase#getFuzzyDistance parses the number after ~ and otherwise returns fuzzyMinSim (classic/QueryParserBase.java:776-784).
  • In both eras the grammar's constant equals the config default (a similarity of 0.5 before 4.0, 2 edits since; FuzzyConfig.java:26), so only a non-default value is lost.

Exposure and likelihood208 words
  • Who is hit. Applications that parse with the flexible StandardQueryParser and call setFuzzyMinSim with a value that does not itself give 2 edits: 1f, 0f (exact match), or a legacy fraction such as 0.8f (1 edit for a 6-letter term). PrecedenceQueryParser, which extends StandardQueryParser and keeps its grammar and FuzzyQueryNodeProcessor, is hit the same way: with setFuzzyMinSim(1f) it also gives f:lucene~2 (run in the independent fact check). Luke users too, as soon as they lower "Minimal similarity" (default 2.0): the Luke desktop app selects the StandardQueryParser by default, every search uses the parser options pane's config, and the Standard path passes that value to setFuzzyMinSim.
  • What happens. Every fuzzy term typed without a number, the usual fuzzy syntax, gets 2 edits: more hits than configured (and so possibly a different ranking), no error, and getFuzzyMinSim() reports the configured value.
  • Not affected. An explicit term~N (it overrides the setting in both parsers), the default setting (2), and setFuzzyPrefixLength.
  • Scale. Any index size, assertions on or off. Bounded: 2 edits is Lucene's default and maximum, and term expansion stays capped by maxExpansions (default 50).
  • Age. Every release since 2.9.0 (2009); no public report was found, which fits an opt-in setting whose failure is "more results".

Why it looks unintended

#
  • setFuzzyMinSim is documented on the interface both parsers share, and the classic QueryParser applies it to term~.
  • The processor's javadoc says it takes the "default similarity" from the fuzzy config, but its unset check never fires; the sibling setFuzzyPrefixLength works.
  • In 2009 the contributor reported "support to set the minimum fuzzy similarity was added to the configuration handler".
The full argument313 words
  • The contract. CommonQueryParserConfiguration#setFuzzyMinSim: "Set the minimum similarity for fuzzy queries. Default is defined on {@link FuzzyQuery#defaultMaxEdits}." (CommonQueryParserConfiguration.java:123-127; the same javadoc on StandardQueryParser.java:504-507). The interface is shared with the classic parser (QueryParserBase.java:179-183, "Default is 2f"), which applies the value to a bare ~ (:776-784).
  • The config and the processor say the same. FUZZY_CONFIG is the "Key used to set the {@link FuzzyConfig} used to create fuzzy queries", @see StandardQueryParser#setFuzzyMinSim(float) (StandardQueryConfigHandler.java:139-147). The processor "gets the fuzzy prefix length and default similarity from it and set to the fuzzy node" (FuzzyQueryNodeProcessor.java:30-34). Its < 0 check is an "unset" marker that StandardQueryParser's own grammar never produces, so with the stock syntax parser the branch is dead (only a custom syntax parser, installed with the public setSyntaxParser, could reach it).
  • The sibling works. setFuzzyPrefixLength, stored in the same FuzzyConfig, is applied unconditionally (:66).
  • History. In the contribution thread of the flexible parser (#2641, LUCENE-1567), Adriano Crestani wrote on 2009-03-24 that QueryParser.setFuzzyMinSim(float) and QueryParser.setFuzzyPrefixLength(int) "are kind of hardcoded for now, always using the default values for these configs ... I will try to implement them for the next patch", and on 2009-07-16: "support to set the minimum fuzzy similarity was added to the configuration handler". The first commit has the setter and the processor's < 0 fallback, but the grammar kept its constant (0.5f), which is consistent with wiring that was left incomplete (an inference: no maintainer has said so).
  • Lucene itself uses the setter. Luke passes its "Minimal similarity" option to StandardQueryParser#setFuzzyMinSim.
  • Nothing pins the current behaviour. No javadoc, test, CHANGES or MIGRATE entry says a non-default setFuzzyMinSim is ignored by the flexible parser; with the fix, the whole queryparser module runs with 0 failures (534 tests: 533 pass, the repro included, and 1 is skipped as on stock).
The devil's-advocate check204 words

The case: since LUCENE-2667 a bare ~ means 2 edits. The query syntax docs say "The default that is used if the parameter is not given is 2 edit distances" (classic/package-info.java:212), TestQPHelper asserts term~ -> term~2 (TestQPHelper.java:541, :556-557), and the processor's < 0 fallback is only a hook for custom syntax parsers.

Why it fails: those docs and tests describe the default setting, which the fix keeps (FuzzyConfig defaults to defaultMaxEdits, and TestQPHelper passes with the fix). That sentence is in the classic parser's own syntax documentation, and the classic parser still honours setFuzzyMinSim. And the setter sits on StandardQueryParser itself, whose stock syntax parser always fills in the constant, so under this reading the public setter could never do anything without a custom syntax parser.

Fair residue: the fix narrows bare ~ matches for users who set a non-default value, which is what they asked for, but users who set one and came to rely on a bare ~ meaning 2 edits would see fewer hits; a CHANGES entry should say so. A maintainer may also prefer deprecating the legacy-named setter (LUCENE-5496, #6559, once proposed removing fuzzyMinSim; it was abandoned and nothing was deprecated).

Suggested fix

#

Recommended Leave a bare '~' unset in the grammar (validated)

In the grammar, leave a ~ without a number unset (float fms = -1f; instead of FuzzyQuery.defaultMaxEdits) and regenerate the parser. The processor's existing fallback then applies the configured value, and the default stays 2 edits. The repro passes, the whole queryparser test suite has 0 failures (534 tests, 1 skipped as on stock), and the module's static checks pass.

+    float fms = -1f; // unset: FuzzyQueryNodeProcessor applies the configured FuzzyConfig value

Keep the change to one line: javacc names its lookahead methods after grammar line numbers, so adding a line to the .jj renames dozens of generated methods. Leave a bare '~' unset in the grammar (validated) (recommended)

#

The node then carries the "unset" value the processor already checks for, so FuzzyQueryNodeProcessor applies FuzzyConfig.getMinSimilarity(). StandardQueryConfigHandler always installs a FuzzyConfig whose default is defaultMaxEdits, so the default stays 2 edits; an explicit ~N is unchanged.

# parser/StandardSyntaxParser.jj:718 (the regenerated StandardSyntaxParser.java:1077 gets the same line)
-    float fms = org.apache.lucene.search.FuzzyQuery.defaultMaxEdits;
+    float fms = -1f; // unset: FuzzyQueryNodeProcessor applies the configured FuzzyConfig value

Trade-offs

  • Until the processor runs, the syntax tree's FuzzyQueryNode holds -1: toQueryString of an unprocessed tree prints ~-1.0, and toString similarity='-1.0'. (Executed in the independent fact check.)
  • A custom QueryConfigHandler without FUZZY_CONFIG now reaches the processor's existing IllegalArgumentException("No FUZZY_CONFIG set in the config") for a bare ~, where today it gets 2 edits (executed in the independent fact check). Making that branch fall back to FuzzyQuery.defaultMaxEdits instead removes the difference (not run).
  • A custom pipeline without FuzzyQueryNodeProcessor builds floatToEdits(-1f, n) = min(2n, 2): still 2 edits for a non-empty term.
  • setFuzzyMinSim checks nothing, and with the fix the configured value reaches every bare ~ unchecked: for lucene~, -1f gives 2 edits and 1.5f 1 edit, where the classic parser throws a ParseException for both, and NaN gives 0 edits, as in the classic parser (today the flexible parser gives 2 edits for all three; executed). A check in the setter or the processor could come with the fix (not run).
  • Behaviour change: users with a non-default setFuzzyMinSim get the narrower matches they configured; a CHANGES entry under Bug Fixes fits.

An explicit "unset" state on FuzzyQueryNode (not run)

#

A FuzzyQueryNode constructor or flag for "no similarity given", applied by the processor, with toQueryString printing a plain ~ when unset.

Trade-offs

  • No magic value in the syntax tree and no ~-1.0 when an unprocessed tree is printed.
  • Changes the public FuzzyQueryNode API in flexible/core/nodes: a larger change for the same effect.

Downstream note

#

Products that expose a fuzzy-distance option backed by StandardQueryParser#setFuzzyMinSim silently apply 2 edits to every bare term~, whatever their users configured.

How it was found

#

Semi-formal contract checking: the documented promise of setFuzzyMinSim was written as a proof obligation (it governs every fuzzy term typed without a number) and checked against the code, with the classic QueryParser, the interface's other implementation, as the reference. A public-API probe on main showed the gap; a 650-parse comparison of both parsers mapped it.

The method in full134 words

Method: semi-formal (proof obligations stated from the documented contracts and checked against the code, witnessed by executable tests).

  • Obligation. For CommonQueryParserConfiguration#setFuzzyMinSim: the configured value governs every fuzzy term typed without a number; an explicit term~N overrides it.
  • Check. The classic parser meets it (getFuzzyDistance returns fuzzyMinSim for a bare ~); the flexible grammar writes a positive constant and the processor's fallback needs a negative one, so the obligation fails for every non-default value.
  • Witness. A public-API probe on main 5adff78bb168 (three one-word documents, setFuzzyMinSim(1f) on both parsers, lucene~: classic 2 hits, flexible 3), then a one-test JUnit, and a bounded-exhaustive differential check of both parsers over 650 parses (13 settings x term lengths 1-10 x 5 suffixes): 79 of the 130 bare parses differ, 0 of the 520 explicit ones.

Impact note
Applications that parse with the flexible StandardQueryParser and call setFuzzyMinSim with a value other than the default 2 (for example 1f, 0f or a legacy fraction such as 0.8f), and Luke users who lower 'Minimal similarity' (the Luke desktop app selects the Standard parser by default), get 2 edits for every fuzzy term typed without a number ('term~'): silently broader matches (3 hits instead of 2 in the repro), no error, while getFuzzyMinSim() still reports the configured value; an explicit 'term~N' and the default setting are unaffected; opt-in setting, any index size, -ea and -da; every release from 2.9.0 through 10.6.0, and main [exec].
Summary
You configure the flexible StandardQueryParser with setFuzzyMinSim(1f), which the shared CommonQueryParserConfiguration interface documents as 'Set the minimum similarity for fuzzy queries' and which the classic QueryParser applies to a fuzzy term without a number, then parse 'lucene~' and expect FuzzyQuery lucene~1 (at most one edit). Instead you get lucene~2, which also matches 'lucxna' (two edits), although getFuzzyMinSim() returns 1.0: the grammar (StandardSyntaxParser.jj FuzzyOp) fills in FuzzyQuery.defaultMaxEdits for a bare '~', and FuzzyQueryNodeProcessor copies the configured value onto the node only when its similarity is unset (below 0), which the grammar never produces. So the setter only changes what its getter returns; the sibling setFuzzyPrefixLength, stored in the same FuzzyConfig, is applied.
