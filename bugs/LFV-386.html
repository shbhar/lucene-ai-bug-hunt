A postings stream that ends at the very last byte of the 2 GiB indexing pool reads back with up to 3 wrong bytes (int overflow in ByteSliceReader)

When one document fills its indexing thread's 2 GiB in-RAM postings pool to the exact last byte, an int overflow in ByteSliceReader can commit a term's last 1-3 postings bytes wrong: a payload ending 0x41 0x42 0x43 reads back 0x11 0x11 0x11, and CheckIndex reports the segment clean.

The finding in 30 seconds

#

The reader's test "is the next slice the last one?" adds two ints. For a slice that ends exactly at byte 2^31 of the pool the sum overflows, so the last slice is read as if it pointed onward, and its last 3 bytes are taken as an address.

Background: how Lucene buffers postings in RAM

#
  1. While indexing, each thread keeps its terms' postings (doc numbers, frequencies, positions, payloads) in one in-RAM byte pool of 32 KiB blocks. The pool holds at most 65,536 blocks = 2^31 bytes; asking for one more throws ArithmeticException (since 9.8.0).
  2. Each term's stream is a chain of slices of growing size: 5 bytes, then 14, 20, 30, 40, 40, 80, 80, 120 and 200. A slice that fits exactly at the end of a block is placed there. A slice's last byte is a level marker; when a slice is full, its last 4 bytes become the address of the next slice.
  3. At flush, ByteSliceReader walks the chain: in a slice that is not the last, it stops 4 bytes before the end, reads the address and jumps; in the last slice it reads up to the stream's end.

The finding, step by step

#
  1. Index one document with the default IndexWriterConfig and codec. Its tokens carry payloads: 65,419 tokens a with 32,000-byte payloads (about 1.95 GiB), then a few planned tokens, ending with term b and a 355-byte payload whose last 3 bytes are 0x41 0x42 0x43. Together they fill the indexing thread's in-RAM postings pool, 65,536 blocks of 32 KiB = 2^31 bytes, to its very last byte.
  2. You expect b's payload back exactly, or the loud ArithmeticException Lucene throws when the pool would grow past 2^31 bytes.
  3. At flush the reader walks b's chain of slices and asks of each next slice "is this the last one?" with nextIndex + newSize >= endIndex in int. b's last slice is the 200 bytes ending at byte 2^31, so the sum is exactly 2,147,483,648, which wraps to -2,147,483,648: "not the last".
  4. So the reader takes the slice's last 3 data bytes plus its marker byte as the address of a next slice, and reads the payload's last 3 bytes from there: 0x41 0x42 0x43 come back as 0x11 0x11 0x11.
  5. No error: the commit succeeds and CheckIndex reports the segment clean. With that payload 3 bytes shorter, or with the fixed comparison, everything reads back correctly.

Who is affected

#

Anyone whose single indexing call (one document or one addDocuments block) fills its thread's in-RAM postings pool to exactly 2 GiB with this alignment; the default config and codec suffice. It needs about 2 GB of postings in one call plus exact alignment, so it is contrived; the result is up to 3 wrong committed bytes that CheckIndex accepts.

Mechanism, terms and numbers787 words

During indexing, each thread buffers its postings (doc deltas, frequencies, positions, payloads) in one in-RAM byte pool of 32 KiB blocks, as chains of small "slices"; at flush ByteSliceReader walks each chain and follows the forwarding address at the end of every slice but the last. Its test for "the next slice is the last one", nextIndex + newSize >= endIndex (ByteSliceReader.java:109), is computed in int. The pool deliberately admits its 65,536th block, whose last byte is global offset 2^31 - 1, and the allocator places a slice that fits exactly at the end of a block, so a stream's final slice can end exactly at 2^31. The sum is then 2^31, which wraps negative; the reader treats the final slice as non-final and, if the stream wrote any of the slice's last 3 data bytes, returns those 1-3 bytes from an unrelated place in the pool.

Through IndexWriter with the default config and codec, one document with payloads that fills the pool this way commits normally, a 355-byte payload reads back with its last 3 bytes wrong, and CheckIndex reports the segment clean. A slightly larger input fails loudly with the ArithmeticException that #12392 added for this regime. The expression dates from LUCENE-843 (2007, first released in 2.3.0); comparing lengths (endIndex - nextIndex <= newSize) fixes it. Priority is low: it needs about 2 GB of postings in one indexing call and exact alignment.

The bug, step by step (main 645d4fe14a20)

#
  1. The pool can be exactly 2^31 bytes. ByteBlockPool.nextBuffer advances byteOffset = Math.addExact(byteOffset, BYTE_BLOCK_SIZE) (ByteBlockPool.java:199): the 65,536th block (offset 2^31 - 32,768) is admitted, the next throws. Upstream TestByteBlockPool.testTooManyAllocs asserts this boundary.
  2. A slice can end at the block's last byte. ByteSlicePool.allocKnownSizeSlice opens a new block only if pool.byteUpto > BYTE_BLOCK_SIZE - newSize (ByteSlicePool.java:117-119), so an exact fit stays; the last byte gets the marker 16 | level (:137), and the previous slice's last 4 bytes the forwarding address (:134). newSlice uses the same rule (:79).
  3. The overflow. ByteSliceReader.nextSlice reads the address (ByteSliceReader.java:98) and the next size (:101), then tests if (nextIndex + newSize >= endIndex) (:109). endIndex, the stream's write position, is at most 2^31 - 1, because the slice's last byte is the marker. For the slice [2^31 - newSize, 2^31) the sum is 2^31, which wraps to -2,147,483,648: the test is false, and the reader sets limit = upto + newSize - 4 (:116), as for a slice that points onward. The assert endIndex - nextIndex > 0 (:111) sits on the other branch, so -ea does not catch it.
  4. The misread. If the stream stops before the slice's last 3 data bytes, the reader stops at endIndex first and nothing goes wrong. If it wrote into any of them, the reader reaches limit (readByte :73, readBytes :129), calls nextSlice again, reads those bytes plus the marker as a little-endian address (:98) and returns the stream's last 1-3 bytes from there. (For a few byte values that address lands so close to a block's end that the remaining 2-3 bytes do not fit; then the read runs off the 32 KiB block and throws ArrayIndexOutOfBoundsException instead, as a probe on main showed.)
  5. How IndexWriter gets there. At flush, FreqProxFields reads each term's doc/freq and position/payload streams through TermsHashPerField.initReader (TermsHashPerField.java:94) and this reader (FreqProxFields.java:320, :435-436). Term bytes and postings share one pool (TermsHash.java:50-55). The per-thread RAM hard limit is checked only after a whole document (DocumentsWriter.java:427-434, DocumentsWriterFlushControl.java:239), so one document can fill the pool to its last byte.
  6. The init twin. init has the same pattern, startIndex + firstSize >= endIndex (:58), but TermsHashPerField.initStreamSlices always leaves room after a first slice (TermsHashPerField.java:158-162), so the indexing chain cannot produce that layout. Changing it is for consistency only.

Exposure and likelihood358 words
  • Defaults. Default IndexWriterConfig (16 MB RAM buffer, 1,945 MB per-thread hard limit) and the default codec, executed end to end. The payloads come from the public TokenStream API, not a setting.
  • Scale and alignment. With the 16 MB buffer the thread flushes after any larger document, so one document must bring about 2 GiB of term bytes and postings by itself. One stream's final slice must be the exact-fit slice ending at byte 2^31, with the stream's last write in that slice's last 3 data bytes, and the call must end before anything else allocates from the pool (the next allocation throws the known ArithmeticException). A planned token stream hits it deterministically; ordinary workloads essentially never. Reproducing end to end takes an 8 GiB heap and about 6 s.
  • Large RAM buffers (code reading, not executed): the hard limit is checked only between documents, so with a large non-default buffer earlier documents can pre-fill the pool and the crossing document needs only the rest, about 103 MiB with the default 1,945 MB hard limit and about 1 MiB with the maximum 2,047 MB. Exact alignment is still needed.
  • What goes wrong. Up to 3 wrong bytes at the end of one term's stream are committed with no error, and CheckIndex cannot tell. Executed: the last 3 bytes of a payload. Code reading only: the bytes could also be the last position or offset codes, and a hit in a doc/freq stream could change a doc delta or frequency or make the flush fail.
  • Not tested, not claimed: term vectors (TermVectorsConsumerPerField.java:114-117 uses the same reader), MemoryIndex's similar test on its int pool (MemoryIndex.java:360), and FSDirectory (the wrong bytes come from the in-RAM buffer before the codec writes, so the directory should not matter).
  • Bounds. The bogus address's high byte is the slice's level marker (0x11 to 0x19), so it always points 272-416 MiB into the full pool (code reading; the runs that print it agree). No hang, no memory unsafety. In the rare byte-value case above the read throws ArrayIndexOutOfBoundsException instead; through IndexWriter that would be an exception at flush (not executed).

Minimal repro

#

One JUnit test in org.apache.lucene.index (the classes are package-private, as in upstream TestByteSliceReader). It advances a byte pool to its last block with a memory-saving allocator, writes the 14 bytes 1..14 into two slices whose second ends exactly at byte 2^31, and reads them back. No index, about 1 s, deterministic.

More files, environment, full output278 words

The allocator hands out one shared zeroed 32 KiB array for the first 65,535 blocks (the memory-saving pattern of upstream TestByteBlockPool.testTooManyAllocs) and a fresh array for the last, so the test needs about 64 KiB of block memory. A filler slice of 32,768 - 5 - 14 bytes makes the stream's 5-byte and 14-byte slices tile the rest of the last block. The write loop is upstream TestByteSliceReader's.

The shared array is not what causes the failure: a full-size test with the stock DirectTrackingAllocator, all 65,536 real blocks and the real TermsHashPerField write path fails the same way, and so does the public-API end-to-end program (one document, default config and codec, 8 GiB heap); both are impact evidence, not the repro. As a regression test it is the same test: it fails on stock and passes with the fix, and needs no @Monster annotation.

Why it looks unintended

#
  • ByteSliceReader promises to read each slice to its end, then follow its forwarding address; here it follows an address that was never written.
  • The pool admits its 65,536th block on purpose; for growing past it Lucene chose a loud ArithmeticException (#12392), not silent wrong data.
  • With the two-comparison fix the same full 2 GiB document reads back exactly.
The full argument184 words
  • The reader's contract. "We read the bytes in each slice until we hit the end of that slice at which point we read the forwarding address of the next slice and then jump to it" (ByteSliceReader.java:25-29).
  • The public contract. PostingsEnum.getPayload: "Returns the payload at this position" (PostingsEnum.java:96-100). IndexWriter.addDocument documents no per-document size limit other than MAX_TERM_LENGTH (IndexWriter.java:1480-1481).
  • The state is legal. The pool admits the 65,536th block and only the next throws (ByteBlockPool.java:199, asserted by TestByteBlockPool.testTooManyAllocs); CHANGES.txt: "Each DWPT can address up to 2048 MB memory" (CHANGES.txt:15722-15729). Every offset fits in an int; only the intermediate sum does not.
  • Upstream's answer for this regime is a loud failure. "GITHUB#9660: Throw an ArithmeticException when the offset overflows in a ByteBlockPool", under Bug Fixes (CHANGES.txt:3445, #12392); IndexingChain turns it into an aborting exception (IndexingChain.java:2098-2100). This exact fit slips past that guard.
  • Nothing else is exhausted. With the fix, the same full-pool document indexes and reads back exactly (executed). No javadoc, test, CHANGES entry or discussion accepts the wrapped comparison.
The devil's-advocate check156 words

The strongest case for "unsupported": setRAMPerThreadHardLimitMB calls the hard limit a safety limit against "address space exhaustion due to its internal 32 bit signed integer based memory addressing. The given value must be less that 2GB (2048MB)" (IndexWriterConfig.java:374-378); DocumentsWriterFlushControl.java:240-241 says "we can not address more than 2048 MB per DWPT"; on PR #15330 rmuir wrote "But this is not supported: the limits on IndexWriter are 2GB"; on #10790 mikemccand called the hard limit "best effort" and said a gigantic document "can lead to exceptions like this"; and the classes are package-private.

Why it fails: the failing state is inside the documented 2,048 MB, Lucene itself lets one document reach it, and every statement above accepts an exception there, never silent wrong postings that CheckIndex accepts. It argues for low priority, not for "not a bug". The works-as-designed reviewer from another model family (OpenAI GPT-5.6) rated the argument moderate and still called the bug real.

Suggested fix

#

Recommended Compare lengths instead of int sums

Compare lengths instead of sums in ByteSliceReader: endIndex - nextIndex <= newSize in nextSlice (and endIndex - startIndex <= firstSize in init, for consistency). The differences cannot overflow. The repro passes with assertions on and off, and so do the closest suites (109 tests), the whole core suite (8,898 tests) and check.

-    if (startIndex + firstSize >= endIndex) {
+    if (endIndex - startIndex <= firstSize) { // no int overflow when the slice ends at 2^31
       // There is only this one slice to read
@@
-    if (nextIndex + newSize >= endIndex) {
+    if (endIndex - nextIndex <= newSize) { // no int overflow when the slice ends at 2^31
       // We are advancing to the final slice

Never place a slice at the pool's last byte

Make the allocator open no exact-fit slice at the end of block 65,535.

Trade-offs

A check in doAfterDocument.

Trade-offs

Downstream note

#

Not a Lucene security issue; downstream, a service that indexes untrusted documents without a size cap far below 2 GiB would let a submitter plant up to 3 wrong bytes in their own document's postings.

How it was found

#

Formal: an AI tool modelled the pool's slice arithmetic as Z3 bit-vector constraints. The solver showed that the reader's final-slice test goes wrong only for a slice ending exactly at byte 2^31, and that data is misread exactly when the stream uses one of that slice's last 3 data bytes. Tests on the real code and through IndexWriter confirmed it.

The method in full149 words

Method: formal (an SMT model produced the signal), a hunt unit on Lucene's byte and int pools.

  • A Z3 bit-vector model of ByteSlicePool and ByteSliceReader (query group Q4): Q4c is satisfiable at every slice level with block 65,535 and a slice ending at 2^31; Q4c' (a wrap anywhere else) is unsatisfiable; Q4d / Q4d' show the reader follows a bogus address if and only if one of the slice's last 3 data bytes is used; Q4e' shows TermsHashPerField.initStreamSlices cannot produce the init twin.
  • A bounded-exhaustive round-trip harness below the pool end (3,564,378 write schedules, 6,300,936 read-backs in 5 read modes) found no other defect.
  • The witness was executed as a JUnit through the real TermsHashPerField write path; an independent verifier then wrote a full-size test with the stock allocator and a public-API end-to-end program, using a planner that replays the indexing chain's pool writes to compute the token schedule.

History

#

Born with LUCENE-843 (cff5767e443, 2007-07-04, first released in 2.3.0), which introduced the in-RAM byte slices; unchanged since. Every release from 2.3.0 to 10.6.0 and main is affected: the root cause was executed on 17 releases, end to end through IndexWriter on 7 releases from 8.11.4 to 10.6.0, and main. Not fixed upstream.

Versions tested9 rows

Introduced by cff5767e443 (svn r553236, 2007-07-04), "LUCENE-843: speed up IndexWriter performance", by Michael McCandless (JIRA LUCENE-843, migrated as #1918; no PR). It added DocumentsWriter with a nested ByteSliceReader whose nextIndex + newSize >= endIndex and startIndex+firstSize >= endIndex are today's two lines. e5f9b4e1cb3 (LUCENE-1212, 2008) moved them unchanged to their own file; 2d6ad2fee6d (2020) only reformatted the init line.

Latent, not a regression. #12392 (b88d3e19889, 2023, 9.8.0) added the 2^31 cap; it neither caused nor fixed this: 9.7.0 (no cap) and 9.8.0 (cap) both fail.

Scope of execution. The minimal test needs ByteSlicePool (9.9.0+), so it was ported with the same layout and 14-byte stream to the 2.3.x, 2.4-3.6 and 4.0-9.8 APIs; every port fails, and the one-block-earlier control passes wherever it was run (2.3.0, 2.3.2, 2.4.0, 3.6.2, 4.0.0 and 9.8.0). Before 8.11.4, reachability through IndexWriter rests on identical code only (the end-to-end schedule was built for the 8.x+ layout).

Not fixed upstream (2026-10-31): main 2f424fd428da, branch_11x and branch_10_6 still have both lines; the newest commit on ByteSliceReader.java is a70432c110c (#12795, 2023-11-13).

LFV-386, snapshot of 2026-11-07

Registry title
ByteSliceReader's final-slice test (nextIndex + newSize >= endIndex) overflows int when a postings stream's last slice ends exactly at the 2^31-byte end of the in-RAM byte pool, so IndexWriter silently commits up to 3 wrong postings bytes that CheckIndex accepts
Area
index / in-RAM postings byte slices (ByteSliceReader, TermsHashPerField)
Priority
Low, rank 969: Silent postings corruption that CheckIndex accepts is severe, but it needs a contrived 2 GiB pool filled to its exact last byte with exact slice alignment, so it follows LFV-385.
Impact class
data corruption
Impact note
Anyone whose single indexing call (one document or one addDocuments block) grows the indexing thread's in-RAM postings byte pool to exactly its 2 GiB (65,536-block) cap so that one term's stream ends in the slice occupying the pool's last bytes, with its last write in that slice's last 3 data bytes; default IndexWriterConfig and codec (executed end to end through the public API, -ea and -da), extreme scale (about 2 GB of postings in one call with the default 16 MB RAM buffer, 6-8 GiB of heap) plus exact alignment; the segment commits with up to 3 wrong postings bytes (executed: the last 3 bytes of a payload) and CheckIndex reports it clean, where a slightly larger input fails loudly with the #12392 ArithmeticException; released (executed end to end on 8.11.4 through 10.6.0 and at unit level from 2.3.0; the code dates from 2007).
Summary
You add one very large document whose postings fill the indexing thread's in-RAM byte pool to its very last byte (global offset 2^31), and you expect the flushed segment to hold exactly the positions and payloads you indexed, or a loud failure such as the ArithmeticException Lucene has thrown since 9.8.0 once the pool would grow further. Instead, if one term's postings stream ends in the slice that occupies the pool's last bytes, ByteSliceReader.nextSlice computes nextIndex + newSize = 2^31 in int, which wraps negative, so it treats that final slice as non-final, reads its last 3 data bytes plus the level marker as a forwarding address, and returns the stream's last 1-3 bytes from an unrelated part of the pool. IndexWriter commits with no exception (with -ea and -da) and CheckIndex reports the segment clean; in the executed run the last 3 bytes of a 355-byte payload, 0x41 0x42 0x43, read back as 0x11.
