Relevance-sorted searches never set the minimum competitive score at the 1,000-hit threshold, so they can score every match

search(q, 10, Sort.RELEVANCE) and Sort(FIELD_SCORE, tiebreak) paging should stop scoring hopeless documents after 1,000 hits, as search(q, 10) does; since 8.7.0 they wait for a later hit to beat the 10th. If none does, they score every match: 10,011 hits instead of 1,024, same results.

The bug in 30 seconds

#

Lucene counts the first 1,000 hits of a top-n search exactly (the first n, if n is larger). After that it tells the scorer the n-th best score so far, and the scorer skips documents that cannot beat it. A search sorted by relevance through TopFieldCollector is meant to do the same, and did until 8.6.3.

  1. Index 10,011 documents: docs 0-1,010 contain "a b c" (score 0.887), the rest "a b" (score 0.00005). Search a OR b OR c for the top 10.
  2. search(q, 10) returns docs 0-9. On hit 1,001 it tells the scorer that only scores above 0.887 can still make the top 10; the scorer skips the rest, and the search stops after 1,024 hits.
  3. You expect search(q, 10, Sort.RELEVANCE), or Sort(FIELD_SCORE, id) for paging that stays stable across index changes, to do the same, as Lucene 8.6.3 does: 1,011 hits for both.
  4. Instead it returns the same docs 0-9 but scores all 10,011 matches. On hit 1,001 it first marks the hit count as "at least"; the call that would pass 0.887 to the scorer runs only while the count is still exact, so it never runs.
  5. Skipping then waits for a later hit that beats the 10th. Here none does, so nothing is skipped, and later segments would start with no minimum either. On a 200k-document index sorted by a static rank: 183,669 hits instead of 1,060.

Who is affected

#

Anyone sorting by relevance through TopFieldCollector with default settings: search(q, n, Sort.RELEVANCE), and searchAfter paging with Sort(FIELD_SCORE, tiebreak), which has no unsorted equivalent. The loss is large when no later hit beats the n-th best: best documents first (an index sorted by rank) or n tied top scores; random order with varied scores loses about 1.1-1.3x.

Mechanism, terms and numbers703 words

IndexSearcher#search(query, n) counts hits exactly up to 1,000 (or up to n when n is larger) and then passes the n-th best score to the scorer through Scorable#setMinCompetitiveScore, so the scorer can skip documents that cannot make the top n. A search sorted by relevance through TopFieldCollector (Sort.RELEVANCE, or Sort(SortField.FIELD_SCORE, tiebreak), which deep paging uses for an order that stays stable across index changes) is meant to do the same: LUCENE-8507 added it in 8.0.0, and 8.0.0, 8.5.2, 8.6.0 and 8.6.3 do it. Since 8.7.0 it no longer happens on the hit that crosses the threshold. TopFieldCollector.countHit (TopFieldCollector.java:77-90 on main a9779ef3c193) first sets totalHitsRelation to GREATER_THAN_OR_EQUAL_TO, and the updateMinCompetitiveScore call in thresholdCheck that should follow is guarded by totalHitsRelation == EQUAL_TO (:104-107), so it can never take effect; the searchAfter branch (:276-282) is dead the same way. Skipping starts only when a later hit beats the queue bottom, and later segments start with no minimum either. With the best documents first in doc-id order, or n hits tied at the top score already in the queue at the crossing, the search scores every match: 10,011 hits instead of 1,024 in the repro, 183,669 instead of 1,060 on a 200k-document index sorted by a static rank. Results, their order and the TotalHits lower bound stay correct; no wall-clock time was measured. Introduced by LUCENE-9449 (99220677fe4, apache/lucene-solr#1725). The fix calls updateMinCompetitiveScore right after the flip and removes the two dead branches; it does not help when every score ties, an older gap.

Terms

#
  • Total hits threshold: IndexSearcher counts hits exactly up to TOTAL_HITS_THRESHOLD = 1000 (IndexSearcher.java:100), or up to n when n is larger (both collectors use Math.max(1000, n): TopScoreDocCollectorManager.java:69, TopFieldCollector.java:337); past it the count may become a lower bound (TotalHits.Relation.GREATER_THAN_OR_EQUAL_TO, printed as 1024+ hits).
  • Minimum competitive score: once the threshold is passed and the top-n queue is full, the collector calls Scorable#setMinCompetitiveScore(bottom score); scorers in ScoreMode.TOP_SCORES may then skip documents that score lower (ScoreMode.java:28-32).
  • Relevance-first sort: a Sort whose first field is descending relevance: Sort.RELEVANCE, new Sort(), or Sort(SortField.FIELD_SCORE, tiebreak). TopFieldCollector then uses ScoreMode.TOP_SCORES and may set the minimum score (canSetMinScore, TopFieldCollector.java:342-347). IndexSearcher#search(Query, int, Sort) and searchAfter(..., Sort) build it with the 1,000 threshold (IndexSearcher.java:677-679, :719-735).

The bug

#
  1. Every hit runs countHit(), then thresholdCheck(doc) (true for a non-competitive hit) or collectCompetitiveHit(doc) (TopFieldCollector.java:203-213).
  2. On hit 1,001, countHit sets totalHitsRelation = GREATER_THAN_OR_EQUAL_TO for every non-exhaustive score mode, TOP_SCORES included (:83-89).
  3. thresholdCheck then reaches } else if (totalHitsRelation == TotalHits.Relation.EQUAL_TO) { // we can start setting the min competitive score if the threshold is reached for the first time here. updateMinCompetitiveScore(scorer); } (:104-107). The relation is no longer EQUAL_TO; and before the threshold updateMinCompetitiveScore does nothing, because it needs totalHits > totalHitsThreshold (:381). So this call can never have an effect. The "Already collected on a previous page" branch of PagingFieldCollector has the same guard (:276-282).
  4. Per hit, only collectCompetitiveHit and collectAnyHit still call updateMinCompetitiveScore (:114-132): skipping waits for a hit that strictly beats the queue bottom. (setScorer also calls it, :139, but only without a shared accumulator, and TopFieldCollectorManager.java:90 creates one for every finite threshold.)
  5. Later segments read only the shared MaxScoreAccumulator in setScorer (:135-143; TopFieldCollectorManager.java:90 creates it for every finite threshold). It is filled only by a successful updateMinCompetitiveScore (:388-390), so they start with no minimum too.
  6. TopScoreDocCollector makes the call on that same hit: if (hitCountSoFar == totalHitsThreshold + 1) { ... updateMinCompetitiveScore(scorer); } (TopScoreDocCollector.java:116-120).

The numbers

#

10,011 documents in one segment; docs 0-1,010 "a b c" score 0.8867903, docs 1,011-10,010 "a b" score 4.6311867E-5; a OR b OR c, top 10. TopScoreDocCollector calls setMinCompetitiveScore(0.88679034) at hit 1,001 (doc 1,000) and collects 1,024 hits. The relevance-sorted TopFieldCollector never calls it and collects all 10,011. Same top 10 (docs 0-9). With the fix it calls setMinCompetitiveScore(0.8867903) at hit 1,001 and collects 1,024. Sort(FIELD_SCORE, id) and searchAfter page 2 behave the same, with one segment or six.

Exposure and likelihood337 words
  • Who is exposed. Default settings and stable entry points: IndexSearcher#search(q, n, Sort.RELEVANCE) (or new Sort()), search(q, n, sort, doDocScores), searchAfter(after, q, n, sort) with Sort(FIELD_SCORE, tiebreak), and any TopFieldCollectorManager whose first sort field is descending relevance. A tie-break field after the score keeps a deep-paging order stable across index changes (doc ids break ties only within one reader), and there is no TopScoreDocCollector equivalent for it.
  • Not exposed. search(q, n) / TopScoreDocCollector; sorts whose first field is not descending relevance; exhaustive counts (totalHitsThreshold = Integer.MAX_VALUE).
  • When the loss is large. When no hit after the threshold strictly beats the n-th best. That happens when the best documents come first in doc-id order (for example an index sorted by a static rank with IndexWriterConfig#setIndexSort) or when the top scores tie and the queue already holds n of them at the crossing (short fields, single terms: an equal-score later hit loses the tie on doc id).

  • Effect. Extra scoring work only. Top hits, their order and the TotalHits lower bound stay correct, and the collector keeps only its fixed-size top-n queue (memory was not measured). The worst case is scoring and comparing every match, more than an exhaustive count of the same query, which need not score. All numbers are hits collected; no wall-clock time was measured.
  • How likely. Plausible: every relevance-first sorted search past the threshold runs the dead code, but the big loss needs one of the two data shapes above. No earlier report was found in 236 recorded searches, although the code has been there since 8.7.0 (2020).

Why it is a bug, not intended

#
  • LUCENE-8507 (8.0.0) made a relevance-first TopFieldCollector set the minimum score at the threshold; the dead branch's comment still says so.
  • TopScoreDocCollector still does it, as did the four releases tested from 8.0.0 to 8.6.3; LUCENE-9449 dropped it, by every sign by accident: its threads never mention relevance.
  • Skipping is optional: a performance regression, not a broken contract.
The full argument337 words
  • Documented intent. lucene/CHANGES.txt:6850-6851 (LUCENE-8507, 8.0.0): "TopFieldCollector can now update the minimum competitive score if the primary sort is by relevancy and the total hit count is not required." Its commit 947f82679af put the call on the non-competitive branch, already behind today's totalHitsRelation == EQUAL_TO guard ("we just reached totalHitsThreshold, we can start setting the min competitive score now"; 8.0.0 TopFieldCollector.java:143-146). The guard then meant "minimum score not set yet": in 8.0.0 only updateMinCompetitiveScore (:331) and the index-sort early termination (:138) set GREATER_THAN_OR_EQUAL_TO. LUCENE-8992 (8.4.0, branch_8x commit 1c23a3c14e7; the master commit 93d135e79d7 first shipped in 9.0.0) gave the two PagingFieldCollector branches the same guard. A related promise, from an entry about field comparators that skip documents: CHANGES.txt:4864-4869 (LUCENE-9280), a finite totalHitsThreshold "instructs Lucene to skip non-competitive documents whenever possible".
  • The code says so. The comment on the dead branch: "we can start setting the min competitive score if the threshold is reached for the first time here" (TopFieldCollector.java:105-106).
  • The sibling does it. TopScoreDocCollector.java:116-120 calls updateMinCompetitiveScore on the non-competitive hit with hitCountSoFar == totalHitsThreshold + 1.
  • It stopped, by every sign as a side effect. 8.0.0, 8.5.2, 8.6.0 and 8.6.3 skip; 8.7.0 and later do not. The 8.7.0 source with only the new flip suppressed for relevance-first collectors skips again. LUCENE-9449 changed the flip from filteringLeafComparator != null && ... (never true for a relevance comparator) to scoreMode.isExhaustive() == false && ..., after a review suggestion on #1725 to set GREATER_THAN_OR_EQUAL_TO "every time a TOP_SCORES collection reaches the total hits threshold"; no comment on #1725, #1856 or #10489 mentions relevance sorts. The relation change itself was deliberate; nothing in the record shows that losing the minimum-score start was.
  • Tests. No upstream test asserts the current behaviour. TestTopFieldCollector#testSetMinCompetitiveScore crosses the threshold on a competitive hit; its comment "Make sure we do not call setMinCompetitiveScore for non-competitive hits" (:303) comes from the LUCENE-8507 commit and checks that the setter is not called again. It passes with the fix.
The devil's-advocate check223 words

The strongest case for "works as designed": ScoreMode.TOP_SCORES only "optionally" allows skipping (ScoreMode.java:28-32); TopFieldCollector is @lucene.experimental (TopFieldCollector.java:35); Sort.RELEVANCE "returns the same results as calling IndexSearcher#search() without a sort criteria, only with slightly more overhead" (Sort.java:36-41); and the 8.7.0 CHANGES entry for LUCENE-9449 says "TopFieldCollector sets TotalHits.relation to GREATER_THAN_OR_EQUAL_TO, as soon as the requested total hits threshold is reached, even though in some cases no skipping optimization is applied and all hits are collected" (8.7.0 release lucene/CHANGES.txt:19-23; not in main's CHANGES).

Why it fails: the skipping is a documented feature built for exactly this path and lost as a side effect of LUCENE-9449; the entry point IndexSearcher#search(Query, int, Sort) is stable API; scoring every match (4x-170x the hits of search(q, n) in the probes where it happens) is not "slight", and Sort(FIELD_SCORE, tiebreak) has no alternative. The 8.7.0 note explains why the reported relation can be a lower bound when every hit was collected; it does not announce that relevance-first sorts stop setting the minimum score, and the code comment still says they set it. Verdict: not intended, as far as the record shows (the relation change was deliberate; losing the minimum-score start at the threshold appears to be its side effect); a performance regression with correct results. An issue should answer the 8.7.0 note up front.

Suggested fix

#

Recommended Set the score where the flag is flipped, and drop the dead branches

In countHit, call updateMinCompetitiveScore(scorer) right after the relation flips to GREATER_THAN_OR_EQUAL_TO, and delete the two EQUAL_TO-guarded calls that can no longer fire (+3/-9 in TopFieldCollector.java). The test passes, every relevance-first sort in the repro counts 1,024 hits, and the org.apache.lucene.search tests (2,333) and :lucene:core:check pass. It does not help when every score ties, an older gap.

if (scoreMode.isExhaustive() == false
    && totalHitsRelation == TotalHits.Relation.EQUAL_TO
    && totalHits > totalHitsThreshold) {
  // for the first time hitsThreshold is reached, notify comparator about this
  comparator.setHitsThresholdReached();
  totalHitsRelation = TotalHits.Relation.GREATER_THAN_OR_EQUAL_TO;
  // and start setting the min competitive score (only has an effect when the primary sort is
  // by relevance and the queue is full)
  updateMinCompetitiveScore(scorer);
}

Set the score where the flag is flipped, and drop the dead branches (validated by the checks) (recommended)

#

In countHit, call updateMinCompetitiveScore(scorer) after totalHitsRelation = GREATER_THAN_OR_EQUAL_TO; remove the else if (totalHitsRelation == EQUAL_TO) branch of thresholdCheck (TopFieldCollector.java:104-107) and the EQUAL_TO block in the PagingFieldCollector "Already collected on a previous page" branch (:278-282). 1 file, +3/-9.

if (scoreMode.isExhaustive() == false
    && totalHitsRelation == TotalHits.Relation.EQUAL_TO
    && totalHits > totalHitsThreshold) {
  // for the first time hitsThreshold is reached, notify comparator about this
  comparator.setHitsThresholdReached();
  totalHitsRelation = TotalHits.Relation.GREATER_THAN_OR_EQUAL_TO;
  // and start setting the min competitive score (only has an effect when the primary sort is
  // by relevance and the queue is full)
  updateMinCompetitiveScore(scorer);
}

Trade-offs

  • updateMinCompetitiveScore returns at once unless the sort is relevance-first with a finite threshold, the queue is full and the threshold is passed (TopFieldCollector.java:381), so field sorts are untouched; the flip runs at most once per collector, so this is at most one extra call per collector (none for a collector whose relation the shared accumulator flipped first). The call passes the queue bottom from before the current hit is compared; that loses nothing, because a competitive crossing hit calls updateMinCompetitiveScore again with the new bottom (:119). The removed blocks can never have an effect in any score mode.
  • For searchAfter, if the page's queue is not full at the crossing, the existing call in collectAnyHit (:128-131) sets the score when it fills (but see the deep-page limit below). The score is also accumulated, so later segments start with it.
  • It passes the bottom score itself, as the competitive-hit path does, not Math.nextUp as TopScoreDocCollector does. That is needed when a tie-break follows the score; with Sort.RELEVANCE alone and tied top scores it still scores more than search(q, n) (1,187 vs 1,001 hits in one probe). That gap predates this bug (the 8.6.3 source also passes the bottom score). When every score is equal, A does not help at all (20,000 docs with body "a", TermQuery body:a): search(q, 10) collects 1,001, Sort.RELEVANCE and Sort(FIELD_SCORE, id) 20,000 with or without A (fact-check probe).
  • In a concurrent search, a collector whose relation the shared accumulator already flipped skips countHit's block; its own bottom score then waits for its next competitive hit, and the shared score it has can be low. In a fact-check probe (two segments, one per slice, 40 searches each way) stock Sort.RELEVANCE collected 10,011 every time; with A 1,024-4,096 in 39 of 40 (3,072 in 28) and 10,011 once, when that edge hit; search(q, 10) collected 1,024-2,184. The counts depend on thread timing.
  • A deep page whose queue fills with tied low scores is not helped either: on the repro's index, the page after hit 1,005 collects 10,011 with or without A, against 1,051 for searchAfter(q, 10). The page queue fills at hit 1,015 with the low score that every later doc ties: the same nextUp gap.
  • No wall-clock benchmark was run. Open PR #16857 rewrites the same leaf collector.

Mirror TopScoreDocCollector's guard (not built)

Downstream note

#

Downstream code relies on this skipping for score-plus-tiebreak sorts (Solr's BlockMax WAND support, SOLR-13289, names sort=score desc, id asc); no downstream report of the gap was found.

How it was found

#

Found while testing sorted search: debugging another candidate, the finder saw a relevance-sorted collector count all 100 matches where the unsorted one stopped at 11. Reading countHit, thresholdCheck and the history explained it, and a public-API repro on main and release jars confirmed it. The unit's metamorphic harness compares results only, so it could not flag it.

The method in full122 words

Method: non-formal (code reading and testing, hunt unit on sorted search, score modes and threshold invariance, 2026-10-27, main a9779ef3c193).

  • The unit's primary method was a metamorphic threshold-invariance check on the real jars (about 305M checks): a sorted search with a small totalHitsThreshold must return the same hits and sort values as the exhaustive one. It compares results only, so it cannot see a performance-only defect.
  • While debugging the unit's other candidate (in DrillSidewaysQuery), the finder saw TopFieldCollectorManager(Sort.RELEVANCE, 10, 10) count all 100 matches where TopScoreDocCollectorManager(10, 10) stopped at 11.
  • Reading countHit and thresholdCheck and git log led to LUCENE-9449; a public-API main() repro failed on main, 10.5.2, 9.12.3 and 8.7.0 and passed on 8.6.3 and with a one-line shadowed fix.

History

#

Introduced in 8.7.0 by LUCENE-9449 (99220677fe4, #1725, 2020), which flipped the hit-count relation for every non-exhaustive score mode; the feature it disabled came with LUCENE-8507 in 8.0.0. Executed: 8.0.0, 8.5.2, 8.6.0 and 8.6.3 skip; all 8 releases run from 8.7.0 to 10.5.2, and main, do not.

Bug record

#

LFV-791, snapshot of 2026-10-30

Registry title
A relevance-first TopFieldCollector (Sort.RELEVANCE or Sort(FIELD_SCORE, tiebreak)) never sets the minimum competitive score when totalHitsThreshold is crossed, so skipping starts only if a later hit is competitive, and the search can score every match (performance regression since 8.7.0; results correct)
Area
search / sorting (TopFieldCollector, relevance-first sort: minimum competitive score at the totalHitsThreshold crossing)
Priority
Low, rank 319: Performance-only with correct results, and the large loss needs a rank-ordered index or tied top scores; search(q, n) without a sort is not affected.
Impact class
minor
Impact note
Performance only, with default settings: every relevance-first sorted search with a finite totalHitsThreshold (IndexSearcher#search(q, n, Sort.RELEVANCE), searchAfter paging with Sort(FIELD_SCORE, tiebreak), which has no TopScoreDocCollector alternative, or a TopFieldCollectorManager with FIELD_SCORE first) skips nothing until some hit after the threshold strictly beats the queue bottom, in that segment and in every later one, so when the best documents come first in doc-id order (an index sorted by a static rank) or the top scores tie it scores every match (measured 10,011 vs 1,024, 20,000 vs 1,001 and 183,669 vs 1,060 hits collected against search(q, n)), while with random doc order and varied scores the loss is small (about 1.1-1.3x hits per query); top hits, their order and the TotalHits lower bound stay correct, and no wall-clock time was measured.
Summary
You run IndexSearcher#search(query, 10, Sort.RELEVANCE), or a searchAfter page sorted by Sort(SortField.FIELD_SCORE, tiebreak), on a query with many matches, and expect it to start skipping non-competitive documents once 1,000 hits are counted, as search(query, 10) does and as LUCENE-8507 made relevance-first TopFieldCollector do from 8.0.0 to 8.6.3. Instead TopFieldCollector.countHit flips totalHitsRelation to GREATER_THAN_OR_EQUAL_TO on the hit that crosses the threshold, before thresholdCheck's EQUAL_TO-guarded updateMinCompetitiveScore call runs, so that call can never take effect and the minimum competitive score is set only when a later hit is competitive; with the best documents first, the relevance-sorted search scores all 10,011 matches where search(query, 10) stops at 1,024, with the same top 10. This is a regression from LUCENE-9449 (8.7.0); results are always correct.
