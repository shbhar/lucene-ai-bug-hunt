FSTCompiler.Builder: a second build() shares the first compiler's default output, so the second FST misses its own keys

Calling build() twice on one FSTCompiler.Builder with no dataOutput gives both compilers the same default on-heap buffer. With a -> 1 in the first FST and b -> 2 in the second, the second FST returns null for b and answers a -> 1; 9.9.2 got it right.

The finding in 30 seconds

#

FSTCompiler.Builder.build() keeps the default output it creates in the Builder, so every later build() hands out the same, already used buffer.

Background: building an FST

#
  1. An FST (finite state transducer) maps byte strings to outputs, for example a -> 1. Lucene uses FSTs for synonym maps, suggesters and dictionaries. You build one with an FSTCompiler: add the keys in sorted order, then call compile().
  2. FSTCompiler.Builder holds the settings (label type, outputs, RAM limit), and build() returns a compiler. If you set no dataOutput, the compiler writes the FST's bytes into an on-heap buffer, and FST.fromFSTReader(compile(), getFSTReader()) turns that buffer into a readable FST.
  3. Inside the buffer a node is found by its byte address, and address 0 is reserved, so each compiler writes one padding byte first. compile() records the root node's address and the byte count, then freezes the buffer.

The finding, step by step

#
  1. Create one FSTCompiler.Builder (BYTE1 labels, PositiveIntOutputs, no dataOutput). Call build(), add a -> 1, and make FST 1 with FST.fromFSTReader(compile(), getFSTReader()), the recipe in compile()'s javadoc.
  2. Call build() again on the same Builder, add b -> 2, and make FST 2 the same way. You expect FST 2 to map b to 2, as it does with two Builders and as the same calls did on 9.9.2.
  3. Instead, with assertions off, FST 2 returns null for b and returns 1 for a, a key it never got. With assertions on, the second compile() throws an AssertionError in ReadWriteDataOutput.writeByte.
  4. Why: the first build() stored its default buffer in the Builder, so compiler 2 writes into the same buffer. FST 1 fills bytes 0-3 and its root is at address 3. Compiler 2 appends its bytes at 4-7 but counts addresses from 0, so FST 2's root address is also 3: FST 1's root.

Who is affected

#

Code that keeps one FSTCompiler.Builder, sets no dataOutput, and calls build() more than once, for example one FST per field or batch. It is deterministic: the second FST is wrong whenever the first is non-empty and the second holds other non-empty keys, silently with assertions off. No Lucene module does this, and FSTCompiler is @lucene.experimental. Releases 9.10.0 to 10.6.0.

Mechanism, terms and numbers499 words

FSTCompiler.Builder.build() creates the default on-heap output when the caller set no dataOutput, but it stores it in the Builder's own field (FSTCompiler.java:352-355 at 5adff78bb168). A second build() on the same Builder therefore gives the new compiler the same buffer, which the first compile() already froze. The new compiler appends its bytes after the first FST's bytes but counts its node addresses from the start, so the second FST's root address points into the first FST. With a -> 1 in the first FST and b -> 2 in the second, the second FST returns null for b and 1 for a with assertions off; with assertions on, the second compile() fails on assert frozen == false in ReadWriteDataOutput.writeByte. Up to 9.9.2 each compiler made its own byte store, so the same calls gave two correct FSTs; #12624 (first released in 9.10.0) introduced the stored default. It is latent in Lucene itself: no Lucene module builds twice from one Builder.

The bug, step by step (main 5adff78bb168)

#
  1. First build(). dataOutput is null, so build() creates a ReadWriteDataOutput and assigns it to the Builder's own field: if (dataOutput == null) { dataOutput = getOnHeapReaderWriter(15); } (FSTCompiler.java:352-355). Compiler 1 writes its padding byte and its root node; the buffer holds 4 bytes, 00 01 61 1f. compile() records root address 3 and 4 bytes, and freezes the buffer (finish(), :960-965).
  2. Second build(). The field is no longer null, so compiler 2 gets the same buffer object (a probe prints same output object: true).
  3. Compiler 2 counts from 0. Every compiler starts its byte counter at 1, reserving address 0 for its padding byte (:172-175), whatever the buffer already holds. Its padding byte and root node really land at bytes 4-7: 00 01 61 1f 00 02 62 1f. Writes after freeze() are guarded only by assert frozen == false (ReadWriteDataOutput.java:52, :58): with assertions off they go through; with assertions on, the first one, the padding byte (writePaddingByte, FSTCompiler.java:576), throws inside the second compile().
  4. FST 2 reads FST 1. FST 2's metadata says root address 3 and 4 bytes, the same values as FST 1's. getFSTReader() returns the whole shared buffer (:228-234), so FST 2's root is FST 1's root node: get(b) is null and get(a) is 1.
  5. FST 1's save() grows. FST.save copies the whole buffer (FST.java:524-527, ReadWriteDataOutput.writeTo, :128-130): after the second build it writes 8 data bytes while its metadata still says 4. An independent probe with cat -> 5 and dog -> 7 measured 16 bytes against 8. Anything a caller writes after it in the same stream would be read at the wrong offset on reload (by reading; reload not executed).

Not claimed: a caller-supplied dataOutput shared across builds. That is the caller's choice; only the default, which the caller never chooses or supplies, is shared without their asking.

Exposure and likelihood198 words
  • Who is hit. Code that keeps one configured Builder without a dataOutput and builds several FSTs from it. Default settings, one key per FST and no scale are enough. The second FST is wrong whenever the first FST is non-empty and the second holds other non-empty keys, and a third build() is wrong the same way. Two cases happen to look right with assertions off: building the same keys twice, and an empty first FST (its compile() returns null before writing anything).
  • Silent without assertions. With assertions disabled (the JVM default) there is no error: FST 2 misses its own keys and can answer FST 1's (get(a) is 1 in the probe). Only with assertions on does it fail, on an internal assert.
  • Narrow reach. FSTCompiler is marked @lucene.experimental (FSTCompiler.java:68). All 53 new FSTCompiler.Builder sites in the tree build once; the three that keep a Builder variable (TestUtil, TestFSTs, FSTTester) also call build() once. Lucene's own analyzers, codecs and suggesters are not affected, and the recorded searches found no report since 9.10.0 (2024).
  • Side effect. FST 1's save() afterwards also writes FST 2's bytes, after metadata that counts only its own.

Why it looks unintended

#
  • build() says "Creates a new FSTCompiler"; nothing says or enforces single use, while other Lucene APIs that mean it say so (SegmentInfo.setCodec, PackedLongValues.Builder).
  • Up to 9.9.2 each compiler made its own buffer, so the same calls gave two correct FSTs; #12624's review discussed the allocation, never reuse.
  • build() itself creates the shared buffer; two Builders work.
The full argument265 words
  • Contract. build(): "Creates a new {@link FSTCompiler}." (FSTCompiler.java:350). The Builder is a "Fluent-style constructor for FST" (:237) whose setters return this. Nothing in the Builder, build() or dataOutput(...) javadoc (:301-315), CHANGES.txt or MIGRATE.md says a Builder is single-use, and nothing enforces it. Other Lucene APIs state single use explicitly, for example SegmentInfo.setCodec ("Can only be called once.", checked only by an assert, index/SegmentInfo.java:174-176) and PackedLongValues.Builder, which throws IllegalStateException("Cannot be reused after build()") on add() after build() (util/packed/PackedLongValues.java:237, :248, :267).
  • History. Before #12624 the Builder's only storage setting was bytesPageBits (a page size, not a store), and each compiler made its own store (bytes = new BytesStore(bytesPageBits), FSTCompiler.java:134 at b6999818474^); 9.9.2 passes the same scenario. In #12624's review, an earlier revision created the default in a field initializer, and mikemccand asked "can we avoid even creating this, unless the caller didn't pass a Builder.dataOutput themselves?" (r1415507219, 2023-12-05). The creation moved into build() but still wrote the field. The thread is about the allocation; nobody discusses building twice. One earlier comment may come up: on a BytesStore revision mikemccand asked "Is caller allowed to freeze() more than once?" (r1391064549, 2023-11-13; no reply in the exported thread). It is about the output's freeze(), not Builder reuse, but with assertions off the second compile() here does call freeze() a second time on the same output.
  • Controls. Two Builders, or one Builder given a fresh explicit output for each build, give two correct FSTs (cross-model review's control runs).
The devil's-advocate check151 words

The argument. Builders are single-use by convention: the compiler itself is single-use (a second compile() on it returns null, because the first one cleared the root node, FSTCompiler.java:402, :1002-1005; and finish() refuses a second call with "already finished", :954-956), ReadWriteDataOutput's frozen assert shows one on-heap buffer is meant for exactly one FST, the API is @lucene.experimental, and no Lucene caller reuses a Builder.

Why it fails. The single-use object is the compiler, not the Builder, which holds only configuration. The frozen assert protects a buffer from a second writer, and it is build() that hands the buffer to one. Other Lucene APIs that mean single use say so; nothing says it here. And the same calls worked through 9.9.2.

What survives. A maintainer may prefer to document "one Builder per FST" (option C) rather than change the code; the code fix costs nothing for single use.

Suggested fix

#

Recommended A. Create the default in a local variable (recommended)

Create the default output in a local variable in build(), so every compiler gets its own: DataOutput out = dataOutput != null ? dataOutput : getOnHeapReaderWriter(15); and pass out. A caller-set dataOutput is unchanged. The repro passes with assertions on and off, and 274 FST and suggest tests pass.

All options and trade-offs3 options · 388 words

Option A restores the pre-9.10 behaviour (one buffer per compiler) and allocates exactly what a single build allocates today. Options B and C are policy choices for maintainers who prefer to declare the Builder single-use.

A. Create the default in a local variable (recommended) (validated by the checks)

#

build() keeps the caller's dataOutput if one was set and otherwise creates a fresh on-heap output for this compiler only, without writing the Builder field.

     /** Creates a new {@link FSTCompiler}. */
     public FSTCompiler<T> build() {
-      // create a default DataOutput if not specified
-      if (dataOutput == null) {
-        dataOutput = getOnHeapReaderWriter(15);
-      }
+      // create a default DataOutput if not specified, a fresh one for every compiler
+      DataOutput out = dataOutput != null ? dataOutput : getOnHeapReaderWriter(15);
       return new FSTCompiler<>(
           inputType,
           suffixRAMLimitMB,
           outputs,
           allowFixedLengthArcs,
-          dataOutput,
+          out,
           directAddressingMaxOversizingFactor,
           version);
     }

Trade-offs

None for single use: it allocates the same one output per build() as today. A caller-supplied dataOutput is still passed to every compiler, as before (sharing it stays the caller's choice).

Downstream note

#

Downstream code that reuses one FSTCompiler.Builder for several FSTs would silently get FSTs that miss their own keys and can answer the first FST's entries; no Lucene module does this.

How it was found

#

A proof-obligation audit of FSTCompiler.Builder's contract: since build() "Creates a new FSTCompiler", every compiler from one Builder must build an FST independent of earlier builds. build() writing its default output into the Builder field breaks that obligation on the second call; a one-method JUnit test using public methods then witnessed the wrong lookup.

The method in full88 words

The audit took the documented contract of FSTCompiler.Builder.build() and checked what state each call leaves behind. The default output is assigned to a Builder field rather than a local variable, so the obligation "a new compiler, independent of earlier ones" fails from the second call on.

An executable one-test repro witnessed it on main with assertions on and off. An independent reproducer, an executed cross-model review (OpenAI GPT-5.6, refute lens), a devil's-advocate verifier and an adjudication then confirmed it, and a version sweep placed its start in 9.10.0.
