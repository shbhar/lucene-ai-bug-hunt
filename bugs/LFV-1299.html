PatienceKnnVectorQuery treats saturation thresholds 0.0 and -0.0 as equal but gives them different hash codes

Wrap one kNN query in PatienceKnnVectorQuery twice, with saturation threshold 0.0 and with -0.0: the two queries are equals, but their hash codes differ by exactly 2^31, which breaks Java's equals/hashCode contract. A HashSet holding one then misses the other; hits and scores stay the same.

The finding in 30 seconds

#

equals compares the saturation thresholds with ==, under which 0.0 == -0.0. hashCode puts the threshold through Objects.hash, which hashes the double's bits, and the two zeros differ in the sign bit. The factories accept -0.0 unchecked, so two equal queries get hash codes exactly 2^31 apart.

Background: two zeros, and how hash lookups work

#
  1. Java's double has two zeros, 0.0 and -0.0. 0.0 == -0.0 is true, but their bit patterns differ only in the sign bit, so Double.hashCode gives 0 and 0x80000000 (-2147483648).
  2. A HashMap, a HashSet or a query cache compares hash codes first and calls equals() only when they match. So equal objects must have equal hash codes; otherwise the lookup never reaches equals and misses.
  3. PatienceKnnVectorQuery wraps a kNN query and stops the HNSW graph search early: for each visited candidate it computes a queue-saturation ratio (min(current, previous) / current queue size) and stops once that ratio has met saturationThreshold (default 0.995) on more than patience consecutive candidates (HnswQueueSaturationCollector.java:81-92).

The finding, step by step

#
  1. Build knn = new KnnFloatVectorQuery("v", new float[] {1f}, 10), then a = PatienceKnnVectorQuery.fromFloatQuery(knn, 0.0, 7) and b, the same with -0.0. The factory accepts any double threshold; nothing checks it.
  2. a.equals(b) is true: equals compares the thresholds with ==, and in Java 0.0 == -0.0.
  3. You expect a.hashCode() == b.hashCode(): Java requires it for equal objects, and Query's javadoc asks for it so that query caching works.
  4. Instead hashCode feeds the threshold through Objects.hash, which hashes the double's bits: 0 for 0.0, 0x80000000 for -0.0. The hash codes come out as 1050736867 and -1096746781, exactly 2^31 apart.
  5. So a HashSet holding a does not contain b, and BooleanQuery(FILTER a) is not equal to BooleanQuery(FILTER b). Hits and scores are identical, and Lucene's own query cache never sees these queries (they are rewritten first).

Who is affected

#

Applications that build the same Patience kNN query with threshold 0.0 and with -0.0 (for example a client's "-0" parsed with Double.parseDouble) and keep such queries in their own hash sets, maps or BooleanQuery comparisons. Opt-in, experimental class; every release since 10.2.0. Cost: a hash miss or a duplicate entry; hits and scores never change. Contrived, so priority Low.

Mechanism, terms and numbers507 words

PatienceKnnVectorQuery (experimental) wraps a kNN query and stops the HNSW search early once the queue-saturation ratio it computes for each visited candidate has met saturationThreshold (default 0.995) on more than patience consecutive candidates. Its factories and public constructors accept any double threshold (PatienceKnnVectorQuery.java:56-58, :82-84, :108-110, :139-173) and store it as given (:135). equals compares saturationThreshold == that.saturationThreshold (:229), under which 0.0 == -0.0, so the 0.0 and -0.0 versions of one query are equal. hashCode is Objects.hash(super.hashCode(), saturationThreshold, patience, delegate) (:236), which boxes the double and uses Double.hashCode: 0 for 0.0, 0x80000000 for -0.0. Their hash codes therefore always differ by exactly 2^31 (1050736867 and -1096746781 in the repro). That breaks the Object.hashCode contract, which Query's javadoc requires "so that QueryCache works properly" (Query.java:95-116). Hash-based structures that hold the unrewritten query treat the two as different: HashSet/HashMap lookups miss and can hold both, and a BooleanQuery holding one is not equal to one holding the other. Hits and scores are identical (the threshold's only use is queueSaturation >= saturationThreshold), and Lucene's own LRUQueryCache is not affected, because the kNN query is rewritten into a DocAndScoreQuery first. In every release from 10.2.0 (where the class was added) through 10.6.0 and on main; a one-line Double.compare in equals fixes it.

The code (main 5adff78bb168)

#
// PatienceKnnVectorQuery.java (excerpts)
this.saturationThreshold = saturationThreshold;                  // :135  stored as given, -0.0 included

return saturationThreshold == that.saturationThreshold          // :229  equals: IEEE ==, 0.0 == -0.0
    && patience == that.patience
    && Objects.equals(delegate, that.delegate);

return Objects.hash(super.hashCode(), saturationThreshold, patience, delegate);  // :236  hashCode: Double.hashCode
  • Why exactly 2^31. Double.hashCode(d) is (int) (bits ^ (bits >>> 32)): 0 for 0.0, 0x80000000 for -0.0. Objects.hash is Arrays.hashCode; the threshold is the second of four terms, so its difference is multiplied by 31^2 = 961, an odd number, and stays 0x80000000 modulo 2^32. The test input has no random part, so the values (1050736867 and -1096746781) are the same on every seed and on every version it ran on (10.2.0, 10.3.0, 10.6.0 and main).
  • No input check. No javadoc states a range for the threshold, and neither the factories (fromFloatQuery, fromByteQuery, fromSeededQuery) nor the public constructors validate it. Double.parseDouble("-0") or a computed negative zero gives -0.0.
  • No result change. The threshold's only use is queueSaturation >= saturationThreshold (HnswQueueSaturationCollector.java:85), the same answer for both zeros. toString prints the stored value, so it shows 0.0 and -0.0.
  • Where it shows. Only in structures that hold the unrewritten query: application HashSets and HashMaps keyed by query, and composite queries that keep clauses in hash sets (BooleanQuery's clause sets, BooleanQuery.java:126-140, used by its equals and hashCode). Lucene's LRUQueryCache and BooleanQuery's duplicate removal are not reached: AbstractKnnVectorQuery.rewrite (:75-156) replaces the query with a DocAndScoreQuery or MatchNoDocsQuery first, and BooleanQuery.rewrite rewrites every clause (:299-341) before it removes duplicates (:343-362).
Exposure and likelihood362 words
  • Who is hit. Code that ends up with both zeros for one query and relies on the two being one query in a hash-based structure: a HashSet or HashMap keyed by query, an application-level cache, or equality of parent queries (BooleanQuery keeps FILTER and MUST_NOT clauses in a HashSet and SHOULD/MUST in a multiset, and uses them in equals/hashCode).
  • Default vs opt-in. Opt-in: PatienceKnnVectorQuery is @lucene.experimental, and the default threshold 0.995 is not affected. Only an explicit zero threshold, built with both signs, triggers it. Assertions on or off.
  • Effect. Equality and hashing only. Executed in the verifiers' tests: HashSet.contains misses, QueryUtils.checkEqual fails, BooleanQuery(FILTER a) is not equal to BooleanQuery(FILTER b), and on a 20-document index both thresholds give identical hits and scores. The diagram's probe adds that a HashSet holding a grows to two entries when b is added (a same-sign copy stays one). A BooleanQuery keeps the unrewritten clause queries in its clause sets (BooleanQuery.java:126-140), which is why the parents compare unequal. Not affected, by reading: Lucene's LRUQueryCache and BooleanQuery's rewrite-time duplicate removal, because the kNN query is rewritten into a DocAndScoreQuery before either sees it; no extra kNN search is claimed. An application's own cache pays whatever a miss normally costs it.
  • Scale. None needed: one pair of queries.
  • Downstream context (read, not executed). The recorded review of solr#3644 (read 2026-11-03) indicates that Solr's support for this query (merged 2025-09-23) passes a request's saturationThreshold to fromFloatQuery/fromByteQuery, that a first revision rejected NaN, infinite and <= 0.0 values, and that a reviewer asked for validation to live on the Lucene side. A -0 request value can therefore reach the class; nothing beyond the hash mismatch is claimed for it.
  • Likelihood: contrived. Queries that all use the same zero are consistent with each other; it takes both zeros for one query. A zero threshold is also a degenerate setting: the saturation ratio is never negative, so every visited candidate with a non-NaN ratio meets 0.0 and -0.0 alike, and the collector stops after patience + 1 consecutive such candidates rather than on real saturation (HnswQueueSaturationCollector.java:82-91).

Why it looks unintended

#
  • Java's Object.hashCode contract and Query's javadoc ("required so that QueryCache works properly") demand equal hash codes for equal queries.
  • Lucene's own test oracle QueryUtils.checkEqual fails on these two queries; BoostQuery and the wrapped KnnFloatVectorQuery compare bits.
  • Lucene fixed the same -0.0 mismatch in five geo classes (#13292 / #13301, 2024), a year before this class was added.
The full argument171 words
  • The contract. Object.hashCode: "If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result." Query.java:95-116: "Override and implement query hash code properly in a subclass. This is required so that QueryCache works properly."
  • Lucene's test oracle. QueryUtils.checkEqual asserts assertEquals(q1, q2) and assertEquals(q1.hashCode(), q2.hashCode()) together (QueryUtils.java:104-107); a verifier ran it on the two queries and it fails.
  • The core convention. BoostQuery compares and hashes Float.floatToIntBits (BoostQuery.java:61-71); the wrapped KnnFloatVectorQuery compares its target with Arrays.equals (KnnFloatVectorQuery.java:146-159), bit semantics like Arrays.hashCode. PatienceKnnVectorQuery is the outlier.
  • Upstream precedent. #13292 / #13301 (merged 2024-04-15) fixed the same == versus bit-hash mismatch for -0.0 in Circle, Point, Rectangle2D, XYCircle and XYPoint with Float.compare/Double.compare.
  • History. Both lines come from the commit that created the class (#14094); its review never discusses equals, hashCode or the threshold's range, and no test, CHANGES or MIGRATE entry treats -0.0 specially.
The devil's-advocate check126 words

The strongest case: a -0.0 threshold is meaningless, the two zeros really are the same query (the collector treats them alike), so equals returning true is right; and the class is @lucene.experimental.

Why it fails: that justifies equals being true, not a different hash code. The public factories accept -0.0 with no documented range, so an input the API takes must still obey the equals/hashCode contract, and @lucene.experimental allows API changes, not an exemption from Object's contract. What survives is only a severity argument (no result change, a contrived trigger, and a zero threshold is itself degenerate), which is why it is Low. Every verifier rated it real; an executed review by another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Compare with Double.compare in equals

Compare the thresholds with Double.compare in equals, matching the bit-based hash, as #13301 did for the geo classes: a one-line change. Validated: the repro passes with assertions on and off; with it, 82 tests (the repro and the Patience float/byte query and saturation-collector suites) and :lucene:core:check -x test pass.

One line, the same choice as #13301. The two zero queries become two different queries (they still search the same), consistently. Map -0.0 to +0.0 in the constructor (validated by the checks)

In the constructor every factory reaches: this.saturationThreshold = saturationThreshold == 0 ? 0d : saturationThreshold;.

Trade-offs

Reject -0.0 (or every non-positive or non-finite threshold) (not run)

#

Two different changes. Narrow: throw when Double.compare(saturationThreshold, 0d) < 0 in the constructor; that rejects -0.0 and every negative value but still accepts +0.0, NaN and +Infinity. Broad: also reject NaN, infinite and <= 0.0 thresholds (as Solr's first revision did), which rejects +0.0 too and documents a real domain for the threshold.

Trade-offs

Both are behaviour changes: callers passing -0.0 today (or, with the broad check, 0.0, NaN or an infinite value) would get an IllegalArgumentException.

How it was found

#

A proof-obligation audit of PatienceKnnVectorQuery's contract checked that equals and hashCode agree for every threshold the factories accept. The threshold is compared with == but hashed by its bits, which disagree only for 0.0 and -0.0. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full129 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for all accepted inputs, a.equals(b) implies a.hashCode() == b.hashCode() (Object.hashCode, Query.java:95-116). The proof needs x == y to imply Double.hashCode(x) == Double.hashCode(y) for every threshold the factories accept; that fails only for x = 0.0, y = -0.0 (NaN is never ==, so it cannot break the implication), and nothing rejects -0.0.
  • A one-test JUnit witnessed it on main with assertions on and off. An independent reproducer and an executed review by another model family (OpenAI GPT-5.6) wrote their own tests from the claim (through fromFloatQuery and fromByteQuery); a devil's-advocate verifier added the HashSet, QueryUtils.checkEqual, BooleanQuery and identical-hits checks.

You wrap the same kNN query twice with PatienceKnnVectorQuery.fromFloatQuery, once with saturation threshold 0.0 and once with -0.0. equals() returns true (it compares the thresholds with ==, under which 0.0 == -0.0), so by the Object#hashCode contract, which Query's javadoc asks subclasses to honour so that QueryCache works, the two hash codes must be equal. Instead they differ by exactly 2^31 (1050736867 and -1096746781 in the repro), because hashCode() is Objects.hash(super.hashCode(), saturationThreshold, patience, delegate), which hashes the double's bits, so a HashSet holding one query does not find the other, while search results stay the same.
