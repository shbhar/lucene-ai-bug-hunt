CheckIndex.doCheck(Options) throws NullPointerException instead of returning its exit code when setOut was never called

Build options with CheckIndex.parseOptions(new String[] {path}), skip setOut to get only the exit code, and call doCheck: on a clean index it should return 0, but it checks silently, then throws NullPointerException on the unset output stream. Affects every release since 5.5.0; the command-line tool is fine.

The finding in 30 seconds

#

Options.out starts as null; in Lucene's own code only the command-line main sets it (to System.out). doCheck hands it to setInfoStream, which treats null as "print nothing", so the check itself runs fine. Then doCheck prints its own closing lines through opts.out with no null check, and throws.

CheckIndex from code in one minute

#
  1. CheckIndex verifies an index. From the command line, java org.apache.lucene.index.CheckIndex <path> prints a report and exits with 0 (clean) or 1 (problems).
  2. The same tool is public API: CheckIndex.parseOptions(args) turns those arguments into a CheckIndex.Options, and checker.doCheck(options) runs the check and returns the exit code.
  3. The report goes to Options.out, set with options.setOut(stream). It starts as null, and nothing says you must set it.

The finding, step by step

#
  1. Commit an empty index, then build options the way the command-line tool does: opts = CheckIndex.parseOptions(new String[] {path}). You skip opts.setOut(...) because you only want the exit code.
  2. Call new CheckIndex(dir).doCheck(opts). Its javadoc: "@return 0 iff the index is clean, 1 otherwise".
  3. You expect 0. The unset stream is null, and doCheck hands it to setInfoStream, documented as "If null, no messages are printed", so the check runs quietly.
  4. Instead, after the check, doCheck prints a closing blank line with opts.out.println() (line 4925 of CheckIndex.java) and throws NullPointerException: ... because "opts.out" is null. You never get the 0.
  5. On a corrupt index it throws at the warning line instead of returning 1; with -exorcise it throws before the repair is written. Calling setOut with any stream avoids all of it.

Who is affected

#

Code that runs the check through doCheck(Options), with Options from parseOptions or new CheckIndex.Options(), and never calls setOut, for example to get only the exit code. Every such call whose check completes throws, on any index except one whose commit cannot be read. The command-line tool and checkIndex() are not affected. Loud, with a one-line workaround, so Low.

Mechanism, terms and numbers467 words

CheckIndex.doCheck(Options) is documented to return 0 for a clean index and 1 otherwise. Its Options come from the public CheckIndex.parseOptions(String[]) or new CheckIndex.Options(), and neither sets the output stream Options.out, which starts as null; in Lucene's own code only the private command-line entry point sets it, to System.out. doCheck passes the null stream to setInfoStream, where null means "no messages are printed", so the check runs quietly, and then prints its own closing lines through opts.out without a null check. On a clean index the call throws NullPointerException at its last print (CheckIndex.java:4925 on main) instead of returning 0; on a corrupt index it throws at the warning line instead of returning 1; with -exorcise it throws before the repair is written, so nothing changes on disk. Calling setOut with any stream avoids it, and the command-line tool is not affected. Every release since 5.5.0 (2016) has it.

Step by step in the repro

#
  1. new IndexWriter(dir, new IndexWriterConfig()).close() commits an empty index: no segments, nothing wrong.
  2. CheckIndex.parseOptions(new String[] {path}) returns Options with out == null (it only fills the fields named on the command line).
  3. doCheck calls setInfoStream(null, false). Every print in checkIndex is null-guarded, through the msg(PrintStream, ...) helpers (:557-567) or an explicit if (infoStream != null) (e.g. :735, :809, :1055), so the check completes silently and result.clean is true.
  4. doCheck reaches opts.out.println() at :4925 and throws NullPointerException: Cannot invoke "java.io.PrintStream.println()" because "opts.out" is null. The return at :4927 is never reached.

The corrupt-index paths

#

A probe that flips one byte of a stored-fields file (_0.fdt) shows the other two sites: without -exorcise, doCheck throws at :4904 (the "WARNING: would write new segments file" line) instead of returning 1; with -exorcise it throws at :4909, before exorciseIndex(result) at :4919, and the commit point is segments_2 before and after, so nothing is written. With setOut the same index returns 1.

Exposure and likelihood180 words
  • Who is hit. Callers of the public doCheck(Options) that leave Options.out unset, for example to get the exit code with no console output, the quiet mode setInfoStream documents. Both public ways to build Options leave it null.
  • Not hit. The command-line tool (main and the private doMain set the stream), and callers of checkIndex() / checkIndex(List), which return a Status. No other code in Lucene calls doCheck; the recorded search found one caller outside Lucene, Solr's CheckHdfsIndex (and copies of it), and it calls setOut.
  • What they see. An unchecked NullPointerException after the whole check has run, instead of the 0 or 1, on any index whose commit point can be read (an unreadable one returns 1 first). No data effect: with -exorcise the exception comes before the new segments file is written.
  • How likely. Rare: the API is public but little used, CheckIndex is @lucene.experimental (:110), the failure is loud on the first call, and setOut is a one-line workaround. Hence priority Low. No scale is needed: an empty index triggers it.

Why it looks unintended

#
  • doCheck promises "0 iff the index is clean, 1 otherwise" with no precondition; nothing says setOut is required.
  • doCheck itself hands the null stream to setInfoStream, where null means "no messages are printed".
  • Counter: Options is command-line plumbing, so call setOut. That is documented nowhere, and the API is public.
The full argument188 words
  • Contract. doCheck: "@return 0 iff the index is clean, 1 otherwise" (:4884), no precondition. setOut: "Set the PrintStream to use for reporting results." (:4693), not marked as required. Both public ways to build Options leave out null. No CHANGES.txt or MIGRATE.md entry, and no test, says a null out is unsupported; no test calls doCheck at all.
  • The class's own convention. doCheck passes the null stream to setInfoStream, whose javadoc says "If null, no messages are printed" (:543-546), and every print in checkIndex is null-guarded, through the msg helpers (:557-567) or an explicit if (infoStream != null) (e.g. :735, :809, :1055). That convention dates from LUCENE-1402 (#2476, 2008, commit d8a60238e3f), which made a null CheckIndex stream mean "no messages" in the older static API.
  • History. SOLR-7928 (562d97a69d9, 2015) moved main's System.out.println(...) calls into the new public doCheck as opts.out.println(...) and left out = null as the default. Its review never discusses the null default. Consistent with an oversight of the split; no recorded decision says a null stream is invalid.
The devil's-advocate check147 words

The case for "misuse": Options is "Run-time configuration options for CheckIndex commands" (:4669) and parseOptions "Parse command line args into fields"; doCheck holds an interactive -exorcise countdown ("THIS IS YOUR LAST CHANCE TO CTRL+C!"), which only makes sense with a visible console; every known caller sets the stream; the programmatic API is checkIndex(), which returns a Status; the class is @lucene.experimental; and the failure is loud with a one-line workaround. The cross-model refute review rated this moderate, the cross-model intended-behaviour review gave a maintainer pushback risk of medium.

Why it fails: none of it is documented. parseOptions, Options() and doCheck are public and javadoc'd, doCheck promises an exit code, and doCheck itself accepts the null stream as the quiet mode before tripping over it. Verdict: not intended, a defect (Low). If maintainers prefer failing fast, fix D also closes the gap.

Suggested fix

#

Recommended A: print through the null-safe msg(opts.out, ...) helper in doCheck

Fix A: in doCheck, print through the class's existing null-safe msg(opts.out, ...) helper instead of opts.out.println(...) (one file, +11/-8, no API change). The test passes, and so do TestCheckIndex and the format, forbidden-API and lint checks; a corrupt index then returns 1.

Trade-offs

  • With -exorcise and no stream, the 5-second "last chance" countdown runs silently before the repair is written; a caller who wants to see it sets the stream.
  • With a stream set, the output is the same (println("") and println() print the same line). No API change; one file.

Downstream note

#

Products that run index checks through doCheck with their own Options must call setOut (any stream) to get the exit code; Solr's CheckHdfsIndex already does.

How it was found

#

A proof-obligation check of doCheck's return contract ("0 iff the index is clean, 1 otherwise") for Options from both public factories found that every exit but one dereferences opts.out, which neither factory sets. An executable JUnit test then showed the NullPointerException.

The method in full95 words

Method: semi-formal (2026-11-03, main 5adff78bb168).

  • The obligation: for Options from parseOptions or new Options(), doCheck returns 0 or 1 (:4884). Along every path after checkIndex, except missingSegments (:4898-4900), it dereferences opts.out (:4904, :4909-4921, :4925); neither factory assigns out (:4678, :4781-4878), so the obligation holds only if the caller has called setOut.
  • Witness: a public-API JUnit test on a clean one-document index, later reduced to the empty-index test here. A probe on a corrupt index covered the warning and -exorcise lines.

History

#

Introduced by SOLR-7928 (562d97a69d9, 2015-11-30), which split the command-line main into the public Options, parseOptions and doCheck and left out null by default. Every release from 5.5.0 (2016) through 10.6.0, and main, is affected; not fixed upstream.

Versions tested7 rows

Introduced by SOLR-7928, "Improve CheckIndex to work against HdfsDirectory" (Gregory Chanan; credited to Mike Drob and Gregory Chanan in the 5.5.0 Solr CHANGES; a JIRA patch, no GitHub PR): 562d97a69d9 on trunk and df88bd76611 on branch_5x, 2015-11-30. It added Options with PrintStream out = null; and setOut, the public parseOptions and doCheck(Options), and turned main's System.out.println(...) calls into unguarded opts.out.println(...) calls. Later changes to these lines are formatting (2d6ad2fee6d, LUCENE-9570) and a cleanup that turned the last println("") into println() (64cf54a4bff, #12979); no commit added a null check. All 90 release tags from 5.5.0 to 10.6.0 in the history clone carry the unguarded calls (the clone has no tags for 8.8.2-8.11.4; the jar runs and bracketing cover those); upstream main f72004515ec2 (2026-11-03) is unchanged.

On 8.11.x and 9.0.0 with more than one CPU the same call throws earlier, at a separate null dereference in the concurrent check (LUCENE-9662, fixed by #637 for 9.1.0); the user sees the same exception. With one CPU those releases fail at doCheck's own print.
