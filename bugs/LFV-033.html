The test framework's RAMOnlyPostingsFormat cannot flush a DOCS-only field: NegativeArraySizeException: -1

A test that uses the test framework's RAMOnly postings format crashes on its first flush as soon as a document has a StringField: NegativeArraySizeException: -1, and the IndexWriter closes. The format stores "no frequencies" as freq = -1 and then allocates an array of that length.

The finding in 30 seconds

#

For a field without frequencies, RAMFieldsConsumer.write sets freq = -1 and calls startDoc(docID, freq); startDoc creates new RAMDoc(docID, freq), whose constructor runs positions = new int[freq]. The same array doubles as the frequency: RAMDocsEnum.freq() returns positions.length. The -1 is the documented "frequencies omitted" marker of Lucene's push-style writers; RAMOnly's storage was never taught it.

Background: postings formats and DOCS-only fields

#
  1. A postings format decides how a segment stores, for each term, the documents that contain it, plus frequencies and positions when the field indexes them. The test framework ships a few formats for tests; RAMOnly keeps everything in Java objects in memory.
  2. A field's IndexOptions say what is stored. StringField and KeywordField use DOCS: documents only, no frequencies, no positions. Readers then report freq 1 for every document.
  3. While writing, Lucene's push-style postings writers mark "frequencies omitted" by passing freq = -1 for each document.

The finding, step by step

#
  1. In a test, set the codec to TestUtil.alwaysPostingsFormat(PostingsFormat.forName("RAMOnly")), add one document with new StringField("id", "1", Field.Store.NO) and call IndexWriter.flush().
  2. You expect the flush to succeed, as with every other postings format, and the term 1 to read back with docFreq 1 and freq 1 (a field without frequencies reports freq 1).
  3. Instead flush() throws NegativeArraySizeException: -1 and the writer closes itself, with assertions on or off, on main and on every release since 4.0.0-BETA (132 releases run).
  4. Why: for a field without frequencies, RAMOnly's writer passes the marker freq = -1 to its own per-document record, which allocates its positions array as new int[freq], that is new int[-1].

Who is affected

#

Only tests that choose the RAMOnly test codec: Lucene's suite run with -Dtests.postingsformat=RAMOnly, or downstream tests that name it. The randomized test codec never picks it, and no Lucene test writes a field with it. Once chosen, any StringField or KeywordField crashes the first flush. It fails loudly; no production codec or user data is involved.

Mechanism, terms and numbers401 words

RAMOnlyPostingsFormat, the in-memory postings format of lucene-test-framework (SPI name RAMOnly), cannot write a field indexed with IndexOptions.DOCS, the index option of StringField and KeywordField. Its writer passes the "no frequencies" marker freq = -1 to its own startDoc, the same convention as Lucene's push-style postings writers, but its per-document record RAMDoc sizes its positions array with new int[freq]. So the first flush that contains such a field throws NegativeArraySizeException: -1, an aborting exception that closes the IndexWriter. One document with one StringField is enough, with assertions on or off. The array also serves as the format's frequency (freq() returns its length); the -1 marker arrived in 2012 (LUCENE-4248), after the array was written, and RAMDoc was never adapted to it (LUCENE-5268 later rewrote the writer and kept the -1). Only tests that pick this format are hit: Lucene's randomized codec never picks it, and no Lucene test actually writes a field with it.

Exposure and likelihood129 words
  • Routes: -Dtests.postingsformat=RAMOnly makes the test framework use PostingsFormat.forName("RAMOnly") for every field (SetupAndRestoreStaticEnv.java:147-158), or a test sets it itself (for example with TestUtil.alwaysPostingsFormat). The package is exported and the format registered as a PostingsFormat provider (module-info.java:45, :75; META-INF/services/org.apache.lucene.codecs.PostingsFormat:17), so downstream tests can use it.
  • Not default: RandomCodec never picks it (RandomCodec.java:236-259). Its only user in Lucene's sources, TestExternalCodecs, routes every field except field1, field2 and id to it, but its documents contain only those three fields (TestExternalCodecs.java:44-51, :72-83). No BasePostingsFormatTestCase subclass is for RAMOnly.
  • Scale: one document with one StringField; deterministic; the first flush fails.
  • Effect: a NegativeArraySizeException and a closed writer in a test. No index damage, no wrong results, no production code path.

Why it looks unintended

#
  • Nothing documents a limit on index options; the one real limit, offsets, gets a clear UnsupportedOperationException.
  • A DOCS field must report freq 1, and CheckIndex enforces it; the format's own writer makes the -1 its own storage cannot take.
  • LUCENE-4248 (2012) changed the "no frequencies" marker from 0 to -1 and did not update RAMOnly.
The full argument209 words
  • No documented limitation: the class javadoc says "Stores all postings data in RAM, but writes a small token (header + single int) ... NOTE: this codec sorts terms by reverse-unicode-order!" (RAMOnlyPostingsFormat.java:56-61); the package javadoc says "Codec for testing that never writes to disk." (package-info.java:18).
  • The designed limitation is explicit: throw new UnsupportedOperationException("this codec cannot index offsets") (:211-215). DOCS gets no such check; it fails on an array allocation.
  • The writer handles DOCS on purpose: it computes writeFreqs and branches on it (:228, :234-235, :271-276); the crash is in the storage class it hands the marker to.
  • The read contract: PostingsEnum#freq "Returns term frequency in the current document, or 1 if the field was indexed with IndexOptions#DOCS" (PostingsEnum.java:74-82). CheckIndex enforces it ("When a field didn't index freq, it must consistently 'lie' and pretend that freq was 1", CheckIndex.java:1765-1777) and requires totalTermFreq == docFreq for such fields (:1695-1705, :1935-1937). FieldsConsumer#write puts no restriction on index options (FieldsConsumer.java:47-64).
  • History: LUCENE-4248 (2012) made the indexing chain pass -1 instead of 0 for omitted frequencies and documented it; it did not touch RAMOnly. No commit message, comment, CHANGES or MIGRATE entry mentions a RAMOnly index-options limitation.
The devil's-advocate check176 words

The strongest case for "intended": RAMOnly is a test-only codec (behind the @lucene.experimental PostingsFormat API) that nothing in Lucene's own suite exercises; the only in-tree route is an unusual system property; and the study verifier found other, separate breakages in the class (with compound files on, the default, any field fails because its 17-byte .id file has no index header or footer; positions without payloads are stored as -1; RAMDocsEnum.docID() throws before nextDoc()). So one could call it dead code that simply does not support DOCS. The cross-model refute review (OpenAI GPT-5.6) weighed exactly this status and still judged the bug real with high confidence.

Why it fails: the class is shipped, exported and SPI-registered in lucene-test-framework, so downstream tests can use it; nothing documents a DOCS restriction while the one real restriction, offsets, is enforced explicitly; and the crash comes from the format's own writer feeding its own storage the documented push-API marker. Low use lowers the severity, not the correctness. Fixing or removing the class is upstream's choice; either resolves the bug.

Suggested fix

#

Recommended A. Store freq separately and size positions only when positions are indexed

Give RAMDoc its own freq, size its positions array only when positions are indexed, and write freq 1 (counted into totalTermFreq) for fields without frequencies; freq() returns the stored value. Validated: the test fails before and passes after, assertions on and off; the 643 test-framework tests (33 skipped, 0 failures) and TestExternalCodecs pass.

// RAMDoc
final int freq;
public RAMDoc(int docID, int freq, boolean hasPositions) {
  this.docID = docID;
  this.freq = freq;
  positions = new int[hasPositions ? freq : 0];
}
// RAMFieldsConsumer.write, field without frequencies
freq = 1;
totalTermFreq += freq;
postingsWriter.startDoc(docID, freq, writePositions);
// RAMDocsEnum.freq()
return current.freq;

  • Separates the array's two jobs (frequency and positions storage), returns 1 for DOCS as PostingsEnum#freq and CheckIndex require (CheckIndex.java:1765-1777), and keeps totalTermFreq == docFreq for DOCS terms (:1695-1705, :1935-1937; TermsEnum#totalTermFreq is "the sum of the freq() for each doc").

  • RAMDoc gains one int per posting (test-only memory).
  • The class keeps its other, separate defects (compound files, positions without payloads, docID() before nextDoc()); this fix does not address them.

B. Clamp the array size

#

positions = new int[Math.max(freq, 0)]; in RAMDoc stops the exception with one line. Not run.

Trade-offs

freq() then returns 0 for DOCS documents (CheckIndex requires 1), DOCS terms keep totalTermFreq = 0 (CheckIndex requires docFreq), and DOCS_AND_FREQS still trips the assertion. Not recommended.

C. Reject DOCS explicitly, or remove the class

#

Throw UnsupportedOperationException for fields without frequencies, as for offsets; or delete RAMOnlyPostingsFormat with its SPI and module entries. Not run.

Trade-offs

Rejecting gives a clear message but makes the most basic index option unsupported. Removal fits a class nothing in Lucene's suite exercises, but it is an API removal in the test framework and a maintainers' call.

Downstream note

#

Downstream test suites built on Lucene's test framework can choose RAMOnly by name the same way (a Solr test was run with it in 2015, SOLR-7631, and failed differently), and their DOCS-only fields would then crash at the first flush.

How it was found

#

Non-formal. In the October 2026 study, a differential probe ran the same queries against all 15 registered postings formats; every format agreed except RAMOnly, which crashed at flush on DOCS-only fields. An independent verifier reproduced it with its own tests, and later checks cut it to one test.

The method in full121 words
  • First signal: the study's fuzzing and property-based run (2026-10-22, main 7cecf79523) compared Lucene against independent oracles, including a second implementation inside Lucene: 15 postings formats. A probe that indexes the same documents and runs the same queries through every registered format found that all agreed except RAMOnly, whose flush threw NegativeArraySizeException on a StringField.
  • Verification: the study verifier wrote its own 9-test class, a plain main() run with -ea and -da, a run through -Dtests.postingsformat=RAMOnly, and an experimental patched copy that confirmed the root cause; it reproduced the crash on main and on the 10.5.2 jars.
  • Minimal repro (2026-10-29): one test method, one StringField, public API only; fails on main 645d4fe14a20 with assertions on and off.

History

#

Introduced in 4.0.0-BETA by LUCENE-4248 (2012), which made Lucene pass freq -1 instead of 0 for fields without frequencies; RAMOnly kept new int[freq]. Every release from 4.0.0-BETA to 10.6.0 (132) and main fails; 4.0.0-ALPHA passes; the commit is confirmed by revert and apply runs.

Versions tested7 rows

Introduced by LUCENE-4248 "Producers to the Codec API don't always follow the spec" (Robert Muir, 2012-07-23; migrated to apache/lucene#5318), commit 42bd0e24f87 on branch_4x and its trunk twin e0d137f8e2ad (same patch). Their message says "LUCENE-4828", very likely a typo: LUCENE-4828 is an unrelated 2013 issue, and Robert Muir's LUCENE-4248 comment 11 minutes before the trunk commit describes this patch. The commit made the indexing chain and PostingsConsumer.merge pass -1 instead of 0 for DOCS_ONLY fields and documented "freq will be -1 when term frequencies are omitted for the field"; RAMOnly was not changed.

Current form: LUCENE-5268 (78d52bef1f0f, 2013; first released in 6.0.0, backport 2be4061beea in 5.0.0) rewrote RAMOnly's writer and put freq = -1 into RAMOnly's own write(), the code on main today. The array line is older (blame: fa6500fa6caa, LUCENE-3490, 2011).

Not fixed upstream (a snapshot): no commit touches the file between 645d4fe14a20 and upstream main f815e679bf6c (2026-11-01).
