A wrong-length kNN query on a legacy Lucene99 scalar-quantized field reports the query and field dimensions swapped

On a legacy Lucene99 scalar-quantized field, a wrong-length kNN query is rejected with the two numbers swapped: a 1-number query on a 2-dimension field gives "vector query dimension: 2 differs from field dimension: 1". Where this check runs, only the message is wrong (10.4.0 to 10.6.0 and main); swapping two arguments fixes it.

The finding in 30 seconds

#

Lucene rejects a kNN query vector whose length differs from the field's dimension and names both numbers in the message. The helper takes (query length, field dimension); one scorer, for the legacy Lucene99 scalar-quantized format, passes them the other way round.

  1. Open an index whose vector field f was written with the legacy Lucene99 scalar-quantized HNSW format (int7 from Lucene 9.9, int4 from 9.11, written up to 10.3; read-only since 10.4.0). Here it holds 1 document with the vector {1, 2}, so the field has 2 dimensions.
  2. Search it with a 1-number query: new KnnFloatVectorQuery("f", new float[] {1}, 1).
  3. You expect IllegalArgumentException: vector query dimension: 1 differs from field dimension: 2, the text Lucene's kNN query tests require for this input on the other formats.
  4. You get vector query dimension: 2 differs from field dimension: 1. The format's scorer calls checkDimensions(queryLen, fieldLen) with the field's 2 first and the query's 1 second. The query is still rejected, with the right exception; only the labels trade places.

Who is affected

#

Applications on 10.4.0 or later that still read an index written by Lucene 9.9 to 10.3 with the opt-in int7/int4 HNSW format (int4 from 9.11), and send it a query vector of the wrong length, for example after an embedding-model change. Every such query that reaches this check gets the swapped message. Results and index data are not affected.

Mechanism, terms and numbers367 words

FlatVectorsScorer.checkDimensions(int queryLen, int fieldLen) rejects a query vector whose length differs from the field's dimension with "vector query dimension: <queryLen> differs from field dimension: <fieldLen>". The heap scorer of the legacy Lucene99 scalar-quantized vectors format calls it as checkDimensions(values.dimension(), targetBytes.length), field first. A wrong-length KnnFloatVectorQuery on such a field (an index written by Lucene 9.9 to 10.3 with Lucene99HnswScalarQuantizedVectorsFormat, read by 10.4.0 or later) is therefore rejected with the two numbers under each other's label: "vector query dimension: 2 differs from field dimension: 1" for a 1-number query on a 2-dimension field. On these paths (the default vectorization provider, and the Panama provider on vectors that are not memory-mapped) the exception type, the condition and the rejection are right; only the labels are wrong. With Panama on memory-mapped vectors the check is skipped altogether, a separate bug (LFV-1121). Introduced in 10.4.0; swapping the two arguments fixes it.

The bug, step by step

#
  1. Query in. Lucene99ScalarQuantizedVectorScorer.getRandomVectorScorer(sim, values, float[] target) (Lucene99ScalarQuantizedVectorScorer.java:62-79 at 5adff78bb168) quantizes the query into byte[] targetBytes = new byte[target.length] (:67) and calls fromVectorSimilarity(targetBytes, ..., quantizedByteVectorValues) (:70-75).
  2. Reversed call. fromVectorSimilarity (:101-107) checks FlatVectorsScorer.checkDimensions(values.dimension(), targetBytes.length): the field's dimension lands in queryLen, the query's length in fieldLen.
  3. The helper. checkDimensions(int queryLen, int fieldLen) (FlatVectorsScorer.java:75-80) throws when queryLen != fieldLen, a symmetric test, so exactly the right queries are rejected; the text prints queryLen as "vector query dimension" and fieldLen as "field dimension", so the labels swap.
  4. How a search gets there. The read-only backward-codecs reader Lucene99ScalarQuantizedVectorsReader.getRandomVectorScorer(String, float[]) (:326-343) hands the query to the format's scorer. With the default vectorization provider that is this scorer. With the Panama provider it is Lucene99MemorySegmentScalarQuantizedVectorScorer (java25, :62-73), which delegates to this scorer unless the vectors sit in a memory-mapped slice (DELEGATE at :45-46, the memory-mapped test at :65-66, the delegate call at :72); on a memory-mapped slice it skips the check altogether, a separate bug (LFV-1121) with its own fix site.
  5. The only reversed caller. Lucene104ScalarQuantizedVectorScorer.java:64, :76, :85 and java25 Lucene99MemorySegmentFlatVectorsScorer.java:88, :113 pass the query length first, and DefaultFlatVectorScorer.java:64-69 builds the same text inline with target.length first.
Exposure and likelihood172 words
  • Reach. 10.x and main read such indexes when the backward-codecs module is on the classpath: Version.MIN_SUPPORTED_MAJOR = 9 (Version.java:305), and upstream's own TestInt7HnswBackwardsCompatibility reads int7_hnsw.<version>.zip indexes. Independent checks reached the line through public API only, with the upstream int7_hnsw.9.12.3.zip index and with indexes written by the released 10.3.2 jars.
  • Opt-in, legacy. The format was never the default (10.3.2's Lucene103Codec defaults to Lucene99HnswVectorsFormat), and since 10.4.0 it is read-only in backward-codecs (fieldsWriter throws "Old codecs may only be used for reading").
  • Which setups. The default vectorization provider on any directory, and the Panama provider on directories that are not memory-mapped. Panama on a memory-mapped directory skips the check altogether (LFV-1121).
  • Effect. Deterministic, every wrong-length float query on such a field. Whoever debugs the mismatch is told the query has the field's length and the field the query's, so they may look at the wrong side (for example the wrong embedding model). Both numbers are printed and the exception type is right, so the harm is limited to the diagnostic.

Why it looks unintended

#
  • The helper is checkDimensions(int queryLen, int fieldLen) and labels each number; every other caller passes the query length first.
  • Lucene's kNN query tests require "vector query dimension: 1 differs from field dimension: 2" for this input on the other formats.
  • The call was first written in the right order (#14049), then reversed by a refactor (#15355).
The full argument181 words
  • Contract. checkDimensions(int queryLen, int fieldLen) names its parameters and prints them as "vector query dimension" and "field dimension" (FlatVectorsScorer.java:75-80); the other five calls pass (query length, field dimension).
  • Standardised text, pinned by tests. bc214d4958b "standardize exception text for vector dimension mismatch (in SimpleText codec)" (Michael Sokolov, 2022) put the query first. BaseKnnVectorQueryTestCase.testDimensionMismatch (:274-283) asserts "vector query dimension: 1 differs from field dimension: 2" for a 1-number query on a 2-dimension field; BaseVectorSimilarityQueryTestCase (:365-373) and BaseExplicitVectorSimilarityQueryTestCase (:257) assert the same order. All their subclasses (11 direct, 1 indirect: TestKnnByteVectorQueryMMap extends TestKnnByteVectorQuery) live in lucene/core's tests, which do not use the backward-codecs formats.
  • History. 6b0112cdee2 (#14049, 2024-12-09) added this check on main as checkDimensions(targetBytes.length, values.dimension()). 821c289bd9e (#15355, "Add checkDimension check to Lucene104ScalarQuantizedVectorScorer#getRandomVectorScorer", author date 2025-10-24) moved the helper into FlatVectorsScorer and reversed this one call; its review: "this is just a rote refactor to consolidate 2X duplicated code". Its branch_10x copy #15359 (4633b88bed2) added the reversed call directly. No javadoc, CHANGES or MIGRATE entry, or test accepts the reversed order.
The devil's-advocate check106 words

The strongest case for "intended": exception text is not API, the scorer is @lucene.experimental (Lucene99ScalarQuantizedVectorScorer.java:39), the format is legacy and read-only, and on the 10.x line this format never had a labelled message, so nothing regressed.

Why it fails: nobody asks for a compatibility promise. The message states two facts and both are false; the helper's parameter names and the other callers define the order, and the fix is one line; no documented contract requires the reversed wording. The three test bases set the convention but never run this legacy format. The argument does support Low, and a maintainer could reasonably call it minor.

Suggested fix

#

Recommended A. Swap the two arguments (validated)

Swap the two arguments at the one call: FlatVectorsScorer.checkDimensions(targetBytes.length, values.dimension()). The repro then passes with assertions on and off, and the scorer's own suite and the backward-codecs lucene99 tests pass. The condition is symmetric, so the same queries are rejected.

-    FlatVectorsScorer.checkDimensions(values.dimension(), targetBytes.length);
+    FlatVectorsScorer.checkDimensions(targetBytes.length, values.dimension());
All options and trade-offs2 options · 212 words

B. Make the order hard to get wrong

#

Give the helper the field's values instead of a second int, for example checkDimensions(int queryLen, KnnVectorValues field), and update its six call sites.

Trade-offs

A wider change for a one-line slip; not built or tested. Option A fixes this bug on its own.

How it was found

#

A semi-formal proof-obligation audit of the callers of FlatVectorsScorer.checkDimensions: each call must pass the query length as queryLen and the field dimension as fieldLen. This call passes them reversed. A one-method JUnit test then witnessed the swapped message.

The obligation came from the helper's own parameter names and message, checked against all six call sites at 5adff78bb168; only Lucene99ScalarQuantizedVectorScorer.java:107 fails it. The witness test wrote a field of dimension 4 and ran a 3-number query ("vector query dimension: 4 differs from field dimension: 3"); the repro above is its smallest form.

A KnnFloatVectorQuery of the wrong length on a Lucene99 scalar-quantized (int7/int4) vector field fails with the query and field dimensions swapped in its message ('vector query dimension: 4 differs from field dimension: 3' for a 3-component query on a 4-dimension field), because Lucene99ScalarQuantizedVectorScorer calls FlatVectorsScorer.checkDimensions(queryLen, fieldLen) with its two arguments reversed (introduced in 10.4.0)
