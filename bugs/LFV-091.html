Single-valued SortedSetDocValues: nextOrd() after intoBitSet returns an earlier document's ordinal, so DocValuesRangeIterator.forOrdinalRange can return extra hits

When each document of a segment has at most one value for a SortedSetDocValuesField, nextOrd() after intoBitSet returns an earlier document's ordinal: 0 instead of 1 for documents "a" and "b" (since 10.3.0). Since 10.5.0 this gives custom filters built on DocValuesRangeIterator.forOrdinalRange extra hits; core queries are not affected.

The finding in 30 seconds

#

The view caches the current document's ordinal and refreshes it in nextDoc, advance and advanceExact. Its intoBitSet, added in 10.3.0, only forwards the call to the inner iterator, so the iterator moves while the cached ordinal stays behind.

Background: ordinals, the single-valued view and skip blocks

#
  1. A SortedSetDocValuesField stores each document's values as ordinals, positions in the field's sorted list of distinct values ("a" = 0, "b" = 1). You position on a document with nextDoc() or advanceExact(doc), then call nextOrd() up to docValueCount() times.
  2. When every document of a segment has at most one value, the default codec stores the field as single-valued and hands out a thin multi-valued view over it. Lucene's core queries unwrap it with DocValues.unwrapSingleton; other code, including the sandbox SortedSetDocValuesMultiRangeQuery, may use it as it is.
  3. intoBitSet(upTo, bits, offset) is a bulk shortcut: mark the remaining documents below upTo and stop on the first document at or after upTo, exactly as a nextDoc() loop would.
  4. With a skip index (SortedSetDocValuesField.indexedField), DocValuesRangeIterator sorts skip blocks (by default every block but a segment's last holds at least 4,096 documents with a value) into classes: YES_IF_PRESENT when every value present is in the range (mark the documents that have one, in bulk), MAYBE when each document's ordinal must be tested.

The finding, step by step

#
  1. Index two documents with a SortedSetDocValuesField f: doc 0 = "a" (ordinal 0), doc 1 = "b" (ordinal 1). Each has one value, so the default codec stores f as single-valued and DocValues.getSortedSet hands out a thin view that remembers the current document's ordinal.
  2. Call nextDoc() (doc 0), then intoBitSet(1, bits, 0). Its javadoc says it behaves exactly like a nextDoc() loop: it marks doc 0 and leaves the iterator on doc 1.
  3. You expect nextOrd() to return 1, doc 1's "b". You get 0, doc 0's "a", with no error: the view's intoBitSet moved the inner iterator but did not update the remembered ordinal.
  4. The consequence: forOrdinalRange loads a skip block with intoBitSet, then tests the next block's first document with nextOrd(). On 16,384 skip-indexed documents the range [b, b] also matches doc 8192, whose value is "a": 8,193 hits instead of 8,192 in a count of a FILTER conjunction or a field-sorted filtered search.

Who is affected

#

Only custom code: code that reads nextOrd() after intoBitSet on a single-valued segment, or that hands this view of a skip-indexed field to the experimental forOrdinalRange (or uses the sandbox multi-range query) and evaluates it in bulk: counts, field-sorted or no-scores filters. Core queries unwrap the view first; top-scores searches were correct.

Mechanism, terms and numbers969 words

When every document of a segment has at most one value for a SortedSetDocValuesField, the default codec stores the field as single-valued and hands out SingletonSortedSetDocValues, a multi-valued view that caches the current document's ordinal. nextDoc, advance and advanceExact refresh the cache; the intoBitSet override added by #14618 (first released in 10.3.0) only forwards to the wrapped SortedDocValues, so after it the view reports the new document while nextOrd() still returns an earlier document's ordinal. That breaks the DocIdSetIterator#intoBitSet contract ("should behave exactly as if implemented as" the nextDoc() loop) and nextOrd()'s ("the next ordinal for the current document"). Two documents suffice: after nextDoc() and intoBitSet(1, ...), nextOrd() returns 0 instead of 1, with assertions on and off. Since 10.5.0, DocValuesRangeIterator.forOrdinalRange(SortedSetDocValues, ...) turns this into extra hits: it bulk-loads a YES_IF_PRESENT skip block with intoBitSet, then tests the next MAYBE block's first document with the stale ordinal. Core queries unwrap the view first and are not affected; exposed is code that reads ordinals after intoBitSet, or passes the reader's view of a skip-indexed field to the experimental factory and evaluates it in bulk (counts, field-sorted or no-scores filters), plus the sandbox multi-range query. #16714 fixed the identical omission in the SortedSetSelector wrappers in 2026 and did not touch this class. A 4-line fix (refresh the ordinal after in.intoBitSet) passes the test and the doc-values, range-iterator and codec suites.

The mechanism (main 645d4fe14a20)

#
  1. The view. Lucene90DocValuesProducer#getSortedSet returns DocValues.singleton(getSorted(entry.singleValueEntry)) for a field that is single-valued in the segment (Lucene90DocValuesProducer.java:2282-2286). DocValues.getSortedSet passes the reader's view through, or wraps a SORTED field the same way (DocValues.java:325-336); DocValues.unwrapSingleton returns the inner SortedDocValues (:177-183).
  2. The cache. SingletonSortedSetDocValues has private long ord (SingletonSortedSetDocValues.java:31). nextOrd() returns it (:54-57), docValueCount() is 1 (:59-62), and nextDoc(), advance() and advanceExact() set ord = in.ordValue() on a hit (:64-89).
  3. The override (#14618, :91-94):
   @Override
   public void intoBitSet(int upTo, FixedBitSet bitSet, int offset) throws IOException {
     in.intoBitSet(upTo, bitSet, offset);
   }

docID() is in.docID() (:49-52), so afterwards the view reports the new document while ord keeps the old ordinal.

  1. The contract. DocIdSetIterator#intoBitSet: "This should behave exactly as if implemented as below, which is the default implementation: for (int doc = docID(); doc < upTo; doc = nextDoc()) bitSet.set(doc - offset);" (DocIdSetIterator.java:186-210, @lucene.internal). Through that loop the view's own nextDoc() refreshes ord. SortedSetDocValues#nextOrd: "Returns the next ordinal for the current document" (SortedSetDocValues.java:35-36).
  2. The consumer. forOrdinalRange(SortedSetDocValues, skipper, min, max) builds a predicate on values.nextOrd() and, with a skipper, a BulkOrdinalRangeIterator (DocValuesRangeIterator.java:109-133). Its intoBitSet walks skip blocks (:349-371): a YES_IF_PRESENT block is loaded with disi.intoBitSet(blockEnd, ...) (:357-366), which leaves disi on the next block's first document; the following MAYBE block advances only if disi.docID() < blockStart (it is not) and evaluates the predicate at disi.docID() (:537-548), reading the stale ord. applyMask has the same YES_IF_PRESENT branch (:404-408).
  3. Block classes. All values of a block in range and its documents contiguous gives YES; in range but with gaps gives YES_IF_PRESENT; otherwise MAYBE (SkipBlockRangeIterator.java:90-98). A skip block closes once it holds at least 4,096 documents with a value (the default, Lucene90DocValuesFormat.java:226); it grows past that only while the run stays single-valued, constant and without gaps (Lucene90DocValuesConsumer.java:250-262).

The consequence, block by block

#

16,384 documents with SortedSetDocValuesField.indexedField("f", ...): docs 0-8191 have "b" on even docs only, docs 8192-16383 have "a" on even and "b" on odd docs. Block 0 is docs 0-8190 with 4,096 values, all "b", with gaps: YES_IF_PRESENT for [b, b]. Block 1 starts at doc 8192 ("a"): MAYBE. For block 0 the iterator calls disi.advance(0), which sets ord at doc 0 (DocValuesRangeIterator.java:362-364, SingletonSortedSetDocValues.java:74-80); the following disi.intoBitSet(8191, ...) (:365) never writes ord. So after block 0 the view sits on doc 8192 with the ordinal it cached at doc 0 ("b"), and the predicate accepts doc 8192 (a fact-check probe with doc 0 = "b" and docs 2-8190 = "c" gets ord("b") there, not ord("c")). Expected 8,192 matches, got 8,193 (an independent verifier asserted this block layout through the skipper).

When it happens and when not

#
  • The root cause needs only a single-valued segment and a caller that reads nextOrd() after a valid SortedSetDocValues#intoBitSet call (the iterator positioned and offset <= docID(), as DocIdSetIterator.java:196-197 requires; the repro meets both).
  • The extra hit needs all of: a skip index on the field (without one, forOrdinalRange returns a per-document iterator, DocValuesRangeIterator.java:129-130); the reader's view passed without unwrapping to forOrdinalRange, or to the TermsEnum overload of forOrdinalSet when the matching terms form a contiguous ordinal range (:215-219, :246-247); bulk evaluation through intoBitSet or applyMask, as DenseConjunctionBulkScorer and ConstantScoreBulkScorer do for counts and for field-sorted or no-scores conjunctions (BooleanScorerSupplier.java:440-446); and a YES_IF_PRESENT block directly followed by a MAYBE block whose first valued document is out of range.
  • Not affected: the core SortedSetDocValuesField.newSlowExactQuery in the same search shapes, top-scores searches with the custom filter, per-document matches() over the same iterator, the same layout made multi-valued (the codec's multi-valued iterators reset their state in intoBitSet, Lucene90DocValuesProducer.java:2373-2380 and :2433-2436), all executed; and by code reading a forOrdinalSet call with a non-contiguous set or through the LongBitSet overload, which always passes contiguous=false (DocValuesRangeIterator.java:230-239; per-document iterator, :249-265), and a field that every document of a block carries (such a block is YES or MAYBE, never YES_IF_PRESENT, SkipBlockRangeIterator.java:91-97).
  • Direction: by code reading, the stale ordinal comes from an in-range document of the preceding YES_IF_PRESENT block, so the range path only adds documents, at most one per such block boundary. Not checked exhaustively.
Exposure and likelihood384 words
  • No core query. SortedSetDocValuesRangeQuery unwraps the view before building the iterator (SortedSetDocValuesRangeQuery.java:122-123, :159-164), and so does DocValuesRewriteMethod (DocValuesRewriteMethod.java:165-174); the core newSlowExactQuery counted correctly in the same search shapes.
  • Who is exposed. Code that reads nextOrd() after SortedSetDocValues#intoBitSet on a single-valued segment; code that passes the reader's view of a skip-indexed field to DocValuesRangeIterator.forOrdinalRange (or to the TermsEnum overload of forOrdinalSet when the matching terms form a contiguous ordinal range) and lets it run in bulk (the intended-behaviour check built such a filter from public classes that are not @lucene.internal, its own Query, Weight, ScorerSupplier and Scorer; the independent reproduction's filter uses ConstantScoreWeight and ConstantScoreScorer (public) and Weight.DefaultScorerSupplier (a protected nested class of Weight, usable from a Weight subclass), all three @lucene.internal; both miscount in a FILTER conjunction); and the sandbox SortedSetDocValuesMultiRangeQuery on a skip-indexed field when its ranges collapse to one ordinal range, which miscounts in a FILTER conjunction on main and 10.5.2.
  • Effect. Silent extra hits: IndexSearcher#count of a FILTER conjunction (the custom filter plus a FILTER on another field) 8,193 instead of 8,192 (counted alone, an independent verifier's filter gives the correct 8,192), and a field-sorted MUST+FILTER search or a no-scores collector returns doc 8192, whose value "a" is outside the filter's [b, b] (main with assertions on and off, 10.5.2). A verifier's own layout gave 4,151 instead of 4,150. Top-scores searches were correct in every shape tried.
  • Default vs opt-in. The root cause is on the default codec, for every single-valued segment. The extra hits need the opt-in skip index and the @lucene.experimental factory called without unwrapping.
  • Scale. By code reading, at most one extra document per YES_IF_PRESENT block directly followed by a MAYBE block (every block but a segment's last holds at least 4,096 documents with a value); the total depends on how many such boundaries a segment has, so there is no small fixed bound per segment. The data shape is ordinary: a sparse field (some documents lack it) where a block whose present values are all in range is followed by a mixed block, for example a low-cardinality status field.
  • Not affected. Data on disk, multi-valued segments, and deleted documents (live docs are applied to the window separately, by code reading: DenseConjunctionBulkScorer.java:281-283, ConstantScoreBulkScorer.java:141-142).

Why it looks unintended

#
  • intoBitSet must behave exactly like a nextDoc() loop, which refreshes the view's ordinal; nextOrd() is for the current document.
  • The asserting test wrapper resets its ordinal state after intoBitSet, consistent with allowing nextOrd() there, and the codec's own sorted-set iterators refresh their state there.
  • #16714 fixed the same omission in the SortedSetSelector wrappers; 10.2.2, before this override, is correct.
The full argument436 words
  • Contract. DocIdSetIterator#intoBitSet "should behave exactly as if implemented as" the docID()/nextDoc() loop (DocIdSetIterator.java:187-194); through that loop the view refreshes ord. SortedSetDocValues#nextOrd: "Returns the next ordinal for the current document" (SortedSetDocValues.java:35-36).
  • The test framework expects this call. AssertingSortedSetDocValues#intoBitSet delegates, then sets lastDocID = docID() and ordsRetrieved = 0 (AssertingLeafReader.java:1313-1323), so it resets its per-document ordinal state, consistent with reading the new current document's ordinals after intoBitSet (there is no prose contract saying so). By git blame that code came with #14529, by the author of #14618, two weeks earlier.
  • The codec's own sorted-set iterators refresh their state in intoBitSet: dense multi-valued calls advance(upTo) (Lucene90DocValuesProducer.java:2373-2380), sparse multi-valued sets set = false (:2433-2436).
  • Same omission, fixed in a sibling. #16714 ("Make SimpleCodec return docvalues singletons", by dweiss, merged 2026-09-25, milestone 10.6.0) added setOrd() after in.intoBitSet(...) in all four SortedSetSelector wrappers (SortedSetSelector.java:135-138, :215-218, :299-302, :384-387). The PR body says "it also did find a bug in there so it's piggybacked"; asked in review what the bug was, its author explained that these classes "keep a pointer to the current doc's ordinal (in a private field) [...] But the intoBitSet method just delegated the call and didn't update this ordinal properly." SingletonSortedSetDocValues was not touched. This is a precedent from a sibling class, not a maintainer statement about SingletonSortedSetDocValues.
  • The other wrapper in #14618 is safe because it has no cache. SingletonSortedNumericDocValues delegates intoBitSet the same way (SingletonSortedNumericDocValues.java:67-68) but reads in.longValue() on demand (:90). #14618 had one approval and no review comments.
  • No unwrap precondition. The forOrdinalRange(SortedSetDocValues, ...) javadoc (DocValuesRangeIterator.java:109-116) does not ask callers to unwrap singletons; the sandbox query and the test framework (BaseDocValuesFormatTestCase.java:1193-1226) pass the reader's view. #16172 presents the core unwrap as a speed-up: "Single-valued fields see the largest gain (2.4–3.4x) because the singleton unwrap avoids multi-valued ordinal iteration in YES_IF_PRESENT/MAYBE blocks".
  • Regression. 10.2.2, without the override, returns the right ordinal; swapping only this file between its pre- and post-#14618 versions flips the result both ways.
  • Why tests missed it. The ordinal-range intoBitSet tests in TestDocValuesRangeIteratorIntoBitSet use the SortedDocValues overload (:623-626, :728-732); the test-framework check that does pass the reader's SortedSetDocValues view tests docIDRunEnd(), not intoBitSet (BaseDocValuesFormatTestCase.java:1193-1240); and the test framework's testRandomDenseSortedSetIntoBitSet / testRandomSparseSortedSetIntoBitSet (:997-1016, via doTestRandomIntoBitSet, :1041-1095) add two values per document, so they do not get the single-valued view, and they compare only docID() and the bits, never nextOrd(). Not an exhaustive audit of the tests.
The devil's-advocate check153 words

Strongest case (the intended-lens reviewers and the adjudication): intoBitSet is @lucene.internal and its javadoc talks only about which doc IDs get loaded; DocValuesRangeIterator is @lucene.experimental; both core callers unwrap the singleton first, so the SortedSetDocValues overload could be read as meant for truly multi-valued iterators.

Why it fails: "behave exactly as if implemented as" the loop covers the iterator's state after the loop; the asserting test wrapper resets its ordinal state after intoBitSet, consistent with allowing nextOrd() there; the codec's own sorted-set iterators and, since #16714, the SortedSetSelector wrappers refresh their state; nothing documents an unwrap precondition, and a caller cannot know it got the singleton without checking, because the reader returns it by default. The annotations lower severity, not validity. The cross-model review rated the intended-behaviour argument weak; the intended-behaviour check concluded that it does not survive, and the adjudication rejected it on the same contract, implementation and reach evidence.

Suggested fix

#

Recommended Refresh the cached ordinal in SingletonSortedSetDocValues#intoBitSet

After in.intoBitSet(...), refresh the cached ordinal unless the iterator is exhausted (ord = in.ordValue(), +4 lines in SingletonSortedSetDocValues), as #16714 did for the SortedSetSelector wrappers. With it the test passes, and so do the doc-values, range-iterator and codec suites (262 tests in a re-run, 532 in the first run), assertions on and off.

  @Override
  public void intoBitSet(int upTo, FixedBitSet bitSet, int offset) throws IOException {
    in.intoBitSet(upTo, bitSet, offset);
    // the wrapped iterator moved: refresh the cached ordinal, as nextDoc/advance do
    if (in.docID() != NO_MORE_DOCS) {
      ord = in.ordValue();
    }
  }
All options and trade-offs4 options · 552 words

Two fixes were built and run in scratch worktrees of 645d4fe14a20: refresh the cached ordinal after intoBitSet (recommended, the same shape as #16714) and drop the cache. Two narrower or costlier options are listed for completeness.

Refresh the cached ordinal in SingletonSortedSetDocValues#intoBitSet (validated by the checks) (recommended)

#

After in.intoBitSet(...), set ord = in.ordValue() unless the iterator is exhausted (SingletonSortedSetDocValues.java, +4 lines), like nextDoc and advance already do and like #16714's setOrd() in the SortedSetSelector wrappers.

  @Override
  public void intoBitSet(int upTo, FixedBitSet bitSet, int offset) throws IOException {
    in.intoBitSet(upTo, bitSet, offset);
    // the wrapped iterator moved: refresh the cached ordinal, as nextDoc/advance do
    if (in.docID() != NO_MORE_DOCS) {
      ord = in.ordValue();
    }
  }

Trade-offs

  • Smallest change; keeps #14618's bulk path and the cache's design.
  • Cost: one ordValue() read per intoBitSet call, not per document. No benchmark was run.

Drop the cache: nextOrd() returns in.ordValue() (validated by the checks)

#

Remove the ord field; nextOrd() returns in.ordValue(), and nextDoc, advance and advanceExact just delegate (+5/-18). The view then cannot go stale after any present or future bulk method. The stale open PR #14475 makes the same change as part of a larger refactor.

Trade-offs

The ordinal is decoded when nextOrd() is called instead of on every positioning: bulk loads and counts skip the read, but each nextOrd() call decodes it. nextOrd() now throws IOException, which the abstract method already declares. No benchmark was run.

What the checks validated

  • Stock + this fix instead: the same 14 suites, 532 tests, 43 skipped, 0 failures, with assertions on (not run with assertions off or through check).

Unwrap singletons inside forOrdinalRange(SortedSetDocValues, ...)

#

Call DocValues.unwrapSingleton(values) in the factory and use the SortedDocValues path when it returns non-null, as the core queries already do. Not built.

Trade-offs

Fixes the visible extra hits for every caller and is the path #16172 measured as faster, but leaves the root cause: any other caller that reads nextOrd() after intoBitSet still gets a stale ordinal. Worth doing in addition, not instead.

Remove the intoBitSet override

#

Fall back to the inherited nextDoc() loop, as before #14618. Not built.

Trade-offs

Correct (10.2.2 behaves this way) but gives up #14618's bulk loading for single-valued sorted-set fields, which the range iterator relies on for speed.

Downstream note

#

An application that builds an access-restriction filter on forOrdinalRange over the raw single-valued view could let through at most one document per qualifying skip-block boundary; no core query or known downstream product builds filters that way.

How it was found

#

Reading the iterator state while modelling the bulk range protocol (a YES_IF_PRESENT skip block followed by a MAYBE block) suggested the stale ordinal. A bounded-exhaustive check on the real codec confirmed it: 137 wrong answers with the single-valued view, none once it is unwrapped. It was then reduced to a two-document test.

The method in full133 words

Method: semi-formal (a code-reading hypothesis witnessed by bounded-exhaustive translation validation), a hunt unit, 2026-10-25, on main ea57360912ed. The harness DvRangeExhaustive indexes every assignment of {missing, a, b, c} to 5 documents with a skip interval of 2, runs forOrdinalRange for every ordinal range through the bulk paths (intoBitSet, applyMask) and compares with a brute-force reference: 1,024 configurations, 164,196 checks, 137 mismatches when the single-valued view is passed as is, 0 when it is unwrapped. The first witness, values [a, -, a, b, a] with range [a, a], marks doc 3 ("b").

The finder then wrote the JUnit repro and a cross-model refute review ran before the candidate was filed; verifiers and an adjudication followed. On 2026-10-29 the repro was re-run on main 645d4fe14a20 and minimized to the two-document test.

History

#

Introduced in 10.3.0 by #14618 (cebfb0f415b, merged 2025-05-09), which added the forwarding intoBitSet override. The root cause is in every release since 10.3.0, the latest as of 2026-10-30, 10.6.0, included; the forOrdinalRange extra hits since 10.5.0 (#15989, #16172). 10.2.x is not affected.

#14618 "Impl intoBitset and docIdRunEnd for wrappers" (by gf2121, approved by jpountz with no comments) is cebfb0f415b on main and f2319c52ea9 on branch_10x, merged 2025-05-09, first released in 10.3.0 (CHANGES 10.3.0, Optimizations). Before it the class inherited the default intoBitSet loop, which calls the view's own nextDoc(). Swapping only SingletonSortedSetDocValues.java between its pre- and post-#14618 versions flips the result both ways on 10.2.2, 10.3.0, 10.5.2 and main; no build at the parent commit was made. The visible consequence also needs the forOrdinalRange(SortedSetDocValues, ...) factory (#15989) and the batched sorted-set path that calls disi.intoBitSet on YES_IF_PRESENT blocks (#16172, merged 2026-06-05), both first released in 10.5.0; they rely on the contract #14618 broke and are not themselves the defect.

LFV-091, snapshot of 2026-11-10

Registry title
SingletonSortedSetDocValues.intoBitSet does not refresh its cached ordinal, so nextOrd() returns an earlier document's ordinal and DocValuesRangeIterator.forOrdinalRange can return extra hits on single-valued segments
Area
index / doc values (single-valued SortedSetDocValues view, DocValuesRangeIterator)
Priority
Low, rank 621: Moved down from Medium: SingletonSortedSetDocValues.intoBitSet leaves a stale ordinal so skip-indexed forOrdinalRange filters return a few extra documents, but only custom code on internal or experimental APIs (or a sandbox query) reaches it, because core queries unwrap the singleton.
Impact class
silent wrong results
Impact note
Hits only code that reads ordinals after SortedSetDocValues#intoBitSet (@lucene.internal) on a single-valued segment, or that passes the reader's single-valued SortedSetDocValues view of a skip-indexed field (opt-in SortedSetDocValuesField.indexedField) without unwrapping it to the experimental DocValuesRangeIterator.forOrdinalRange (or a contiguous forOrdinalSet) and evaluates it in bulk (count, sort-by-field or no-scores FILTER conjunctions; top-scores searches were correct), plus the out-of-scope sandbox SortedSetDocValuesMultiRangeQuery when its ranges collapse to one; no core Lucene query is affected because they unwrap the singleton first; default codec, ordinary scale, a few extra hits per segment; the root cause is released since 10.3.0 and the range-iterator consequence since 10.5.0.
Summary
You take the SortedSetDocValues of a segment whose documents have at most one value each (DocValues.getSortedSet and LeafReader#getSortedSetDocValues then return a single-valued wrapper), call intoBitSet(upTo, ...), and read nextOrd() for the document the iterator now sits on; or you pass that view to DocValuesRangeIterator.forOrdinalRange on a skip-indexed field and load the matches in bulk. You expect nextOrd() to describe the current document, as after the nextDoc() loop that the intoBitSet javadoc says it behaves exactly like, and the range iterator to mark only documents whose value is in range. Instead the wrapper's intoBitSet moves the inner iterator without refreshing its cached ordinal, so with two documents a and b nextOrd() on doc 1 returns a's ordinal, and forOrdinalRange for [b, b] also marks doc 8192, whose value is a.
