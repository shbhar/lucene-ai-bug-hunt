HNSW merge reuses a mostly deleted graph as its base: the 40% deletion check overflows `int`

Lucene computes an HNSW graph's deleted share as deleted * 100 / size in int, so from 21,474,837 deleted vectors on it overflows. A segment of 22,000,000 vectors with 97.6% deleted then reads as -97% deleted, passes the 40% limit and is reused as the merge base instead of being rebuilt.

The finding in 30 seconds

#

When segments merge, Lucene may reuse the biggest HNSW graph instead of building a new one, but never a graph more than 40% deleted (counted in whole percent, rounded down). The check that enforces this overflows int for graphs with more than 21,474,836 deleted vectors.

How a merge reuses an HNSW graph

#
  1. Each segment of a vector field has its own HNSW graph: every vector is a node with links to a few nearby vectors.
  2. Building the merged segment's graph from scratch is slow. Since 10.4.0 the merge can start from an existing graph, the base: it drops the deleted nodes and repairs the nodes that lost links.
  3. A graph that lost many nodes repairs badly, so a graph more than 40% deleted (in whole percent) may not be the base. If no graph qualifies, the merge builds a new graph from the live vectors.

The finding, step by step

#
  1. One segment holds 22,000,000 vectors in an HNSW field. A bulk delete removes 21,474,837 of them (97.6%), leaving 525,163, and the segment is merged, for example by forceMergeDeletes() or forceMerge(1).
  2. Before reusing a segment's graph, the merge computes deletePct = ((graphSize - live) * 100) / graphSize in int. Only a graph whose deletePct is at most 40 (DELETE_PCT_THRESHOLD, in whole percent, rounded down) may be the base.
  3. You expect 97% > 40%: no base, so the merge builds a fresh graph from the 525,163 live vectors.
  4. Instead 21,474,837 x 100 = 2,147,483,700 is above Integer.MAX_VALUE (2,147,483,647) and wraps to -2,147,483,596, so deletePct is -97. -97 <= 40 passes, and the merge copies, prunes and repairs the 22M-node graph.
  5. No error. By code reading the merge still drops the deleted documents; the recall and merge-time cost is unmeasured. On 10.x (executed on 10.4.0, 10.5.2 and 10.6.0) the opt-in concurrent merger throws ArrayIndexOutOfBoundsException when such a base has no live vectors.

Who is affected

#

Only an index with one segment holding more than 21,474,836 deleted vectors in one HNSW field: a segment of 21.5M+ vectors, past the default 5 GB merge cap (built by forceMerge(1), a raised cap or addIndexes), merged after a bulk delete. Default codec on main and 10.5.1-10.6.0. Rare; the quality and merge-time cost is unmeasured.

Mechanism, terms and numbers940 words

Since 10.4.0 (#15003) a merge may start its HNSW graph from an existing segment's graph that has deletions: it drops the deleted nodes and repairs the rest. To keep badly connected graphs out, IncrementalHnswGraphMerger.addReader skips a graph whose deleted percentage is above DELETE_PCT_THRESHOLD = 40. It computes that percentage as ((graphSize - candidateVectorCount) * 100) / graphSize in 32-bit int, in whole percent rounded down (so a graph just under 41% deleted still reads 40 and stays eligible, as the upstream test oracle also computes; that is not this bug). Once a graph has more than 21,474,836 deleted vectors (Integer.MAX_VALUE / 100), the product overflows and deletePct is never above 33 for any graph size up to IndexWriter.MAX_DOCS, so deletePct <= 40 always passes: 22,000,000 nodes with 21,474,837 deleted gives -97, 30,000,000 with 25,000,000 deleted gives -59. The heavily deleted graph becomes the base, in either reader order against a cleaner graph with fewer live vectors, and also when it is the only segment in the merge, where the rule says to build a fresh graph from the live vectors. By code reading the merge still drops the deleted nodes and repairs the rest; the repro does not run the merge, and the recall and merge-time cost is unmeasured. On 10.x the opt-in concurrent merger additionally throws ArrayIndexOutOfBoundsException when the chosen base has no live vectors (executed on 10.4.0, 10.5.2 and 10.6.0; the same code is in every 10.4.0-10.6.0 release and branch_10_6); on main that path is gone since #16794 (executed), and branch_11x has the same sources as main. A one-line long widening fixes both. The repro drives the real merger with a stub segment; no index with more than 21.5 million vectors in one segment was built.

The mechanism (main 645d4fe14a20)

#
  1. Every merging segment reaches the check. On a merge, Lucene99HnswVectorsWriter.buildAndWriteGraph calls merger.addReader(...) for every merging segment that has the field, then merger.merge(...) (Lucene99HnswVectorsWriter.java:510-525). createGraphMerger returns IncrementalHnswGraphMerger by default and ConcurrentHnswMerger only with a merge executor, or an intra-merge executor and more than one merge worker (:668-689; DEFAULT_NUM_MERGE_WORKER = 1, Lucene99HnswVectorsFormat.java:120). ConcurrentHnswMerger inherits addReader unchanged. On main the default per-field reader is an HnswGraphProvider (PerFieldKnnVectorsFormat.java:198, :357-369), so default-codec graphs get here.
  2. The rule. DELETE_PCT_THRESHOLD = 40 (IncrementalHnswGraphMerger.java:65), javadoc :57-64: "A value of 40 means that if more than 40% of the graph's original vectors have been deleted, the graph will not be selected as the base." The check works in whole percent, rounded down, so a graph just under 41% deleted reads 40 and stays eligible; the upstream test oracle uses the same expression (TestIncrementalHnswGraphMergerBaseSelection.java:119). That rounding is not this bug.
  3. The overflow. addReader (:110-147) counts live vectors (:128), takes graphSize = graph.size() (:129) and computes int deletePct = ((graphSize - candidateVectorCount) * 100) / graphSize; (:133). The deleted count times 100 exceeds Integer.MAX_VALUE from 21,474,837 deleted vectors on. For 21,474,837 to 42,949,672 deleted vectors the product wraps exactly once to a negative number, so deletePct is 0 or less (it can be 0: a 42,949,672-node graph with every vector deleted gives the product -96 and deletePct 0). With more deleted vectors the product can wrap to a positive number, but deletePct then stays at most 33 for any graph size up to IndexWriter.MAX_DOCS (computed: a positive product after k >= 1 wraps gives deletePct < 50 / (k + 0.5); a check of every deleted count agrees), and an SMT query found passing graphs up to 100% deleted.
  4. The guard passes. if (deletePct <= DELETE_PCT_THRESHOLD && (largestGraphReader == null || candidateVectorCount > largestGraphReader.liveVectorCount)) largestGraphReader = graphReader; (:135-139). Any value the overflow produces (at most 33) satisfies the first half. With two segments, a heavily deleted big graph beats a clean smaller one in either reader order, because it still has more live vectors (the hunt's two-segment tests, executed). Below the overflow the check is exact: one deletion fewer (21,474,836, same live count) is rejected.
  5. What the merge then does (code reading). createBuilder (:157-177) builds from scratch only when largestGraphReader == null (:159-161). Otherwise orderGraphReaders puts the base first, adding it although it has deletions (:187-192), getNewOrdMapping maps its live nodes (:204-250), and MergingHnswGraphBuilder.fromGraphs (MergingHnswGraphBuilder.java:108) calls InitializedHnswGraphBuilder.initGraph (InitializedHnswGraphBuilder.java:187), whose builder runs initializeFromGraph (:303-316): it copies the surviving structure, repairs disconnected nodes and rebalances the levels. The concurrent merger on main does the same through pruneGraph (ConcurrentHnswMerger.java:77-101). getNewOrdMapping sizes its map and ordinal array for the base to the full graph (new IntIntHashMap(graphSize), new int[graphSize], :221, :229), here 22,000,000 entries. The repro never calls merge(), so none of this step ran.
  6. The 10.x crash path. In 10.6.0 and branch_10_6, ConcurrentHnswMerger.getNewOrdMapping returns new int[0] when the base has no live document (ConcurrentHnswMerger.java:161-163 at 10.6.0), and copyAndPruneGraphStructure then reads newOrdMap[oldOrd] (InitializedHnswGraphBuilder.java:352 there): ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 (executed at class level on 10.4.0, 10.5.2 and 10.6.0's release commit). #16794 (CHANGES 11.0.0) replaced that method with the shared one, which allocates a full -1-filled array, so on main the base choice is wrong but the merge completes (executed on 645d4fe14a20); branch_11x has the same sources, so it should behave the same (code reading). The same new int[0] return is in every release from 10.4.0 to 10.6.0 (with the default codec 10.4.0 and 10.5.0 never pick a base, #16400). By code reading, IndexWriter treats the 10.x merge exception as tragic and closes the writer.
Exposure and likelihood396 words
  • Who. Anyone with one segment that has more than 21,474,836 deleted vectors in one HNSW field, merged afterwards. Default codec and default merger on main, branch_11x and 10.5.1-10.6.0; on 10.4.0 and 10.5.0 only with a vectors format that is not wrapped per field, because there the default per-field reader never reached the check (#16400, fixed by #16403 in 10.5.1).
  • How such a segment comes about. Not by default background merges at typical dimensions: TieredMergePolicy caps merged segments at 5 GB (TieredMergePolicy.java:77), and 22M float vectors of 128 dimensions are already about 11 GB of vector data. forceMerge(1) lifts the cap (:789-791), as do a raised maxMergedSegmentMB, a custom merge policy or addIndexes. A later bulk delete (for example by query on a tenant or a time range) can push that segment far over 40% deleted in one step.
  • The trigger is the merge after that (code reading). forceMerge(1) rewrites every segment with deletions (:813); forceMergeDeletes() merges segments over 10% deleted (:81), and a segment bigger than the cap is merged alone; natural merges stop excluding a too-big segment once both its own and the index-wide deleted share exceed deletesPctAllowed, 20% (:82, :383-385). The singleton merge is the simplest case: the rule says rebuild from the live vectors, Lucene reuses the 97.6%-deleted graph instead.
  • What it costs. The merge prunes and repairs exactly the kind of graph the guard was added to exclude. On a pre-merge revision of #15003 at 100k documents, reuse at 90% deletes cut recall from 0.961 to 0.562 (maxConn 16) for a 1.4x faster force merge. On today's repair code it is unmeasured. By code reading, deleted nodes are still dropped and search-time live docs and filters still apply; no run built, merged, reopened or searched such an index, so recall, merge time, memory and the merged index itself were not checked.
  • The 10.x crash needs the opt-in concurrent merger, one 21.5M+-node segment whose vector documents are all deleted while other documents in it stay live (a fully deleted segment is dropped before the merge), and no cleaner graph in the same merge. Contrived, but loud.
  • Scale. Rare: one segment of more than 21.5 million vectors (about 11 GB of vector data at 128 float dimensions); the memory and time to build and merge it were not measured here.

Put the file at lucene/core/src/test/org/apache/lucene/util/hnsw/TestMergeBaseDeletePctOverflow.java. Not covered by the repro (code reading only): building a real 22M-vector segment, a real IndexWriter merge of it, and what the reused graph does to recall. Why it looks unintended

#
  • The javadoc: a graph more than 40% deleted "will not be selected as the base".
  • Upstream tests assert the rule, but only at sizes where int cannot overflow.
  • #15003 added the guard on purpose after reuse at 90% deletes cut recall from 0.961 to 0.562; overflow was never discussed.
The full argument260 words
  • The rule is written down. IncrementalHnswGraphMerger.java:57-64: "A value of 40 means that if more than 40% of the graph's original vectors have been deleted, the graph will not be selected as the base."
  • Tests assert it. TestIncrementalHnswGraphMergerBaseSelection (:94-98): "The base must be a graph within the deletion threshold that has the most live vectors, or none if no graph is within the threshold" (segments of 10-200 docs, :104; its oracle uses the same int expression, :119). TestHnswMergeAbort (:63-67): "Every segment carries more than IncrementalHnswGraphMerger#DELETE_PCT_THRESHOLD deletions, so no source graph is eligible as a base and the merged graph is rebuilt from scratch via HnswGraphBuilder#addVectors." (javadoc; {@code} shown as code).
  • Why the guard exists. In #15003, Pulkitg64 benchmarked reuse at 60-90% deletes on 100k documents: "With higher deletes we are regressing on recall with out any benefits on force merge time. This suggest it is required to add some guardrails" (2025-11-06; at 90% deletes and maxConn 16, recall 0.961 rebuilt vs 0.562 reused, force merge 1.4x faster; across 60-90% the speed-up was 0.96x-2.01x). benwtrent proposed "lets focus on 40% or fewer deleted total docs" (2025-11-07), and the author replied "Keeping this threshold at 40% now." Nobody in the PR's 79 discussion items mentions overflow, long or Integer.MAX_VALUE.
  • Elsewhere Lucene uses floating point. TieredMergePolicy.java:383: double segDelPct = 100 * (double) segSizeDocs.delCount / (double) segSizeDocs.maxDoc;.
  • The input is legal. Segments up to IndexWriter.MAX_DOCS (Integer.MAX_VALUE - 128, IndexWriter.java:208) are allowed; no HNSW format or merger documents a smaller per-segment vector limit.
The devil's-advocate check204 words

The strongest case: IncrementalHnswGraphMerger is @lucene.experimental (:42) and DELETE_PCT_THRESHOLD is a package-private merge heuristic, not public API; the addReader javadoc (:105-108) still says a reader must not "contain any deleted vector", so the documentation is inconsistent anyway; the trigger needs more than 21.5 million deleted vectors in one segment, beyond the default 5 GB merge cap; and the merged graph is still valid and searchable.

Why it fails: every point is about severity, not intent. Nobody designs an int overflow; #15003 deliberately removed the old no-deletions rule and added the 40% guard after measuring recall losses; upstream tests treat the guard as an invariant; and the input is reachable through documented operations (forceMerge(1), a bulk delete, a merge). The severity points do bear on priority, which is why it is rated low. The no-deletions rule in the addReader javadoc is older than #15003; #15003 even reworded that sentence ("deleted docs" -> "deleted vector") but kept the rule its own change made stale (git blame: :106 is 3752dba9c51d, :107 is #15003's ef10476d98ab; a separate doc nit). Every verifier rejected the intended-behaviour reading; the cross-model reviews, the only ones that rate its strength, called it weak.

Suggested fix

#

Recommended Compute the percentage in long

Widen the product to long: long deletePct = ((long) (graphSize - candidateVectorCount) * 100) / graphSize; (one line, IncrementalHnswGraphMerger.java:133; :138 on branch_10_6). The repro then passes with assertions on and off, 19 HNSW and codec suites (352 tests) pass, and the core static checks pass. It also removes the 10.x crash.

Downstream note

#

Engines built on Lucene that let users bulk-delete and force-merge very large vector segments, or that turn on the concurrent HNSW merger on 10.x, inherit this; it changes merge work and possibly graph quality; by code reading it does not expose deleted documents or corrupt data.

How it was found

#

Found while modelling HNSW merge-base selection: encoding the rule for a small-scope checker, the finder noticed the int product, and an SMT query (Z3) over the exact Java expression showed graphs more than 40% deleted passing the check. A JUnit on the real merger confirmed it, and independent verifiers reproduced it with their own tests.

The method in full130 words

A hunt unit on HNSW merge-time graph reuse was building a bounded-exhaustive harness for the base-selection rule ("the base has the most live vectors among graphs at most 40% deleted"). Its small scopes cannot reach the overflow, but writing the invariant down exposed the int product (2026-10-25). A Z3 4.12 query over the exact Java expression, with an explicit 32-bit wrap and IndexWriter.MAX_DOCS as the size bound, found "at least 41% deleted but eligible" satisfiable (up to 100% deleted), the same without wrap-around unsatisfiable, and "at most 40% deleted but rejected" unsatisfiable; the smallest witness has 21,474,837 nodes. A JUnit on the stock jars that drives the real IncrementalHnswGraphMerger.addReader with stub readers then failed on main (-ea, -da), 10.5.2 and 10.4.0, and passed with the one-line fix.

LFV-160, snapshot of 2026-11-08

Registry title
HNSW merge computes a graph's deleted percentage in int, so a graph with more than 21,474,836 deleted vectors (41-100% deleted) passes the 40% DELETE_PCT_THRESHOLD and is reused as the merge base; in 10.4.0-10.6.0 and branch_10x the opt-in concurrent merger then throws ArrayIndexOutOfBoundsException for an all-deleted base (main since #16794, 11.0 only, rebuilds the graph instead)
Area
search / HNSW (merge-time graph reuse: IncrementalHnswGraphMerger base-graph selection)
Priority
Low, rank 1005: The HNSW merge deleted-percentage overflows past 21.47M deleted vectors, so a mostly deleted graph is reused as the merge base (and the opt-in concurrent merger can crash), contrived scale.
Impact class
minor
Impact note
Anyone whose HNSW vector field has one segment with more than 21,474,836 deleted vectors (for example a 30M-vector segment after a bulk delete) and then merges it, with the default codec and merger on main and from 10.5.1: Lucene reuses that 41-100%-deleted graph as the merge base, or reuses it instead of rebuilding when the segment is merged alone, so the merge prunes and repairs exactly the kind of graph the 40% guard was added to exclude (the recall and merge-time cost of that is unmeasured; results stay valid approximate kNN and the index stays readable); with the opt-in concurrent HNSW merger (numMergeWorkers > 1, default 1) an all-deleted base additionally makes the merge throw ArrayIndexOutOfBoundsException (executed at class level; that IndexWriter then closes the writer as a tragic event is from code reading).
Summary
You merge an HNSW vector segment that has had most of its vectors deleted and expect Lucene to rebuild the graph or reuse a cleaner one, because the DELETE_PCT_THRESHOLD javadoc says a graph with more than 40% of its vectors deleted is never selected as the merge base. Once more than 21,474,836 vectors of one graph are deleted, the percentage ((graphSize - live) * 100) / graphSize overflows int and goes negative (-59 for 25M deleted out of 30M), so the guard passes and a graph that is up to 100% deleted becomes the base, in either reader order and also when the segment is merged alone. The default merger still finishes, pruning and repairing the reused graph. In 10.4.0 through 10.6.0 and branch_10x, and on main before #16794 (for example ea57360912ed), the opt-in concurrent merger throws ArrayIndexOutOfBoundsException for an all-deleted base; on main since #16794 (from a9779ef3c193; to be released in 11.0, not in 10.6.0) it rebuilds the graph, and only the wrong choice of merge base remains.
