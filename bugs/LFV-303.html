Multi-valued range facet counts drop values that do not arrive in ascending order

Lucene's range facet counter assumes a document's values arrive smallest first and skips any later value at or below what it already counted. A document whose distances arrive as 3.0 km, then 0.5 km, is missing from "< 1 km" and "< 2 km", though their drill-down queries find it.

The bug in 30 seconds

#

A range facet counts, per range, the documents with at least one value in it. For a multi-valued document, LongRangeCounter.addMultiValued keeps the highest interval it has counted and returns early for any later value at or below it. That is only right when values arrive in ascending order, which nothing guarantees.

  1. You count distance ranges "< 1 km", "< 2 km" and "< 5 km" with DoubleRangeFacetCounts. A document has two locations, so your own MultiDoubleValuesSource returns two distances in storage order: 3.0 km, then 0.5 km.
  2. You expect the document in all three ranges, counts 1, 1, 1: each range's drill-down query (DoubleRange.getQuery) matches it.
  3. You get 0, 0, 1. The counter put 3.0 in the interval [2, 5) and then skips every later value at or below that interval's top, so 0.5 is never placed.
  4. At scale, 1,000 documents with two random distances in 0-10 km give 85, 180, 494 instead of 154, 325, 740. Lucene's own fromDoubleField and the DoubleRangeFacetCounts(String, ...) constructor can do the same for raw-bit doubles with two negative values: -1.0 arrives before -5.0, and -5.0 is skipped.
  5. No error: counts and the total are only ever too low. Every release from 8.10.0 to 10.5.2 is affected; ascending inputs such as long fields are not.

Who is affected

#

Applications that range-facet multi-valued numbers whose values are not ascending: a custom MultiDoubleValuesSource or MultiLongValuesSource, such as distances to a document's several locations; raw-bit doubles or floats with two or more negative values per document; or fromField with a decreasing decoder. Default settings, every release since 8.10.0. Long fields are not affected.

Mechanism, terms and numbers891 words

LongRangeFacetCounts and DoubleRangeFacetCounts count, for each range, the documents that have at least one value in it. For a document with several values, LongRangeCounter.addMultiValued remembers the highest elementary interval it has counted for that document and returns early for any later value at or below that interval's upper end; its field comment states the assumption, "this takes advantage of the fact that values within a given doc are sorted". Nothing guarantees that order: MultiLongValues.nextValue and MultiDoubleValues.nextValue promise none, so a custom source such as the distances from the user to each of a document's locations (the use case both class javadocs name) is counted in delivery order, and Lucene's own fromDoubleField and the DoubleRangeFacetCounts(String, ...) constructor read raw-bit doubles in signed-long order, which reverses negative values: two different negative values in one document reach the counter in descending order. A document with distances 3.0 km and 0.5 km is counted under "< 5 km" but not under "< 1 km" or "< 2 km", although those ranges' drill-down queries find it; across 1,000 such documents the counts are 85, 180, 494 instead of 154, 325, 740. Counts and FacetResult.value are only ever too low, and nothing fails. Every release from 8.10.0 to 10.5.2, and main, is affected.

Terms

#
  • Range facet counts. LongRangeFacetCounts and DoubleRangeFacetCounts count, for each requested range, the documents that have at least one value in it; the result's value (FacetResult.value) is the number of documents that hit any range. Doubles are mapped to sortable longs, so both classes share one counter, LongRangeCounter.
  • Elementary intervals. The counter cuts the number line at the range bounds; boundaries() holds each interval's inclusive upper end, the last one Long.MAX_VALUE (range/LongRangeCounter.java:90-92, :169-170). For "< 1 km", "< 2 km", "< 5 km": E0 below 0, E1 [0, 1), E2 [1, 2), E3 [2, 5), E4 [5, +inf). Non-overlapping ranges use ExclusiveLongRangeCounter, overlapping ones OverlappingLongRangeCounter (:52-58).
  • Multi-valued sources. MultiLongValues.nextValue() and MultiDoubleValues.nextValue(): "Iterates to the next value in the current document", with no ordering (MultiLongValues.java:42-46, MultiDoubleValues.java:42-46). Custom sources are the stated purpose of #543 (9.1.0).
  • Raw-bit doubles. SortedNumericDocValuesField(Double.doubleToRawLongBits(v)), the encoding fromDoubleField decodes (Double::longBitsToDouble, MultiDoubleValuesSource.java:80-83) and the DoubleRangeFacetCounts(String, ...) constructor documents ("assumes that the field was indexed with DoubleDocValuesField", range/DoubleRangeFacetCounts.java:53-56). SortedNumeric returns the longs in signed order, and for negative doubles the raw bits sort in reverse: 0xBFF0000000000000 (-1.0) is below 0xC014000000000000 (-5.0).

The bug

#
  1. For a document with more than one value the callers call startMultiValuedDoc(), addMultiValued(v) for each value, then endMultiValuedDoc() (range/LongRangeFacetCounts.java:200-212, range/DoubleRangeFacetCounts.java:227-239, range/RangeFacetCounts.java:169-181). Only a document for which endMultiValuedDoc() returns true is added to the total (RangeFacetCounts.java:179-181, :213).
  2. addMultiValued (range/LongRangeCounter.java:116-161) keeps multiValuedDocLastSeenElementaryInterval, reset to -1 per document (:66-68). If it is set and v <= boundaries[lastSeen], it returns at once (:125-130); otherwise it binary-searches only the intervals above lastSeen (:139-160). The field comment: "this takes advantage of the fact that values within a given doc are sorted" (:45-49).
  3. Distances 3.0, then 0.5: 3.0 lands in E3 and lastSeen becomes 3; 0.5 is <= boundaries[3] (just below 5.0), so the method returns. E1 is never marked: "< 1 km" and "< 2 km" get 0.
  4. If the first value lies above every range ({500, 5} with [0, 10), [10, 100)), lastSeen is the last interval, every later value is skipped, and the document also drops out of the total.
  5. Raw-bit doubles with the sign bit set come in reverse order through fromDoubleField and through the field constructor, which maps with NumericUtils.sortableDoubleBits (range/DoubleRangeFacetCounts.java:272-275): two different negative values arrive descending, and so do -0.0 and a negative value. An out-of-order value is lost only when it falls in a lower elementary interval than one already counted (raw {-5.0, -6.0} with [-10, -2], [-2, 0], both in one interval, is counted right). Without -0.0 or NaN, a document with at most one negative value arrives ascending and is counted right. One more edge: through fromDoubleField, a NaN with the sign bit set arrives first but maps above every finite value, so the next value is skipped (executed: {NaN, 5.0} in [0, 10] counts 0, total 0).
  6. Both counters lose the skipped values. The exclusive one relies on the shortcut to count each interval at most once per document ("We can do this without fear of double-counting since we know the requested ranges don't overlap", range/ExclusiveLongRangeCounter.java:122-132).
  7. Counts can only go down: a value that is searched always lands in its true interval, and no interval is counted twice for one document.

The numbers

#

One document per test: distances 3.0, 0.5 give [0, 0, 1] instead of [1, 1, 1]; longs {30, 5} with [0, 10), [10, 100) give [0, 1] instead of [1, 1]; {500, 5} gives [0, 0] and total 0 instead of [1, 0] and total 1; raw-bit {-1.0, -5.0} with [-10, -2], [-2, 0] gives [0, 1] instead of [1, 1], through fromDoubleField and through the field constructor. 1,000 documents with two random distances in [0, 10) km: [85, 180, 494], total 494, against drill-down [154, 325, 740]. Two random raw-bit temperatures in [-20, 20): [-20, -10) counts 271, drill-down 390.

Exposure and likelihood362 words
  • Custom sources. Both class javadocs name per-request values such as "distance from the user's location, '< 1 km', '< 2 km', etc." (range/DoubleRangeFacetCounts.java:36-39, range/LongRangeFacetCounts.java:33-37), and #543 says "This change allows users to provide custom multi-valued 'value sources' for numeric faceting". Such a source returns one value per location in whatever order it computes them; nothing asks it to sort them.
  • Raw-bit doubles. The field constructor documents the raw-bit encoding (DoubleDocValuesField encodes "via Double#doubleToRawLongBits"), fromDoubleField decodes it, the MultiLongValuesSource javadoc recommends fromDoubleField(f).toMultiLongValuesSource() for double fields, and upstream's own multi-valued tests index the IEEE bits (doubleToLongBits / doubleToRawLongBits, the same bits for non-NaN values) with values in [0, 1) only. A document with two or more different negative values (western longitudes, sub-zero temperatures) reaches the counter in descending order and loses a later value that falls in a lower elementary interval; -0.0 next to a negative value does the same. fromFloatField over raw float bits behaves the same.
  • Not affected (executed controls): long fields through fromLongField/fromIntField; DoubleField (sortable encoding) read with fromField(f, NumericUtils::sortableLongToDouble); raw-bit documents with at most one negative value and no -0.0 or NaN; single-valued documents; ascending custom sources.
  • Default vs opt-in. Default codec, IndexWriterConfig and searcher; no setting. But each trigger needs a less common API shape: an @lucene.experimental custom source, hand-encoded raw-bit multi-valued doubles, or a decreasing decoder.
  • Effect. Per-range counts and FacetResult.value are silently too low and disagree with the range's drill-down; a document whose first value lies above every range vanishes from all of them. Never too high, no error, nothing written to the index. With 1,000 documents and two random distances each, one third of the documents are missing from "< 5 km" (494 of 740).
  • Likelihood. Plausible: wrong on every affected document, but these paths are uncommon, upstream tests never deliver unordered values, and no public report was found in the recorded searches, although the code has shipped since 8.10.0 (2021).
  • Same assumption elsewhere. LongValueFacetCounts de-duplicates a document's values only against the previous value, so a source that returns 5, 3, 5 counts 5 twice for one document (tracked with this bug; needs its own change).

Why it is a bug, not intended

#
  • MultiLongValues and MultiDoubleValues promise no order; "values within a given doc are sorted" is only a comment in a package-private class.
  • The same range's drill-down query checks every value and finds the document.
  • The shortcut was added in review when every input was sorted; unordered sources came in 9.1.0 without any discussion of order.
The full argument216 words
  • Contract. MultiLongValues.java:22-46 and MultiDoubleValues.java:22-46: "Documents may produce multiple values"; nextValue() "Iterates to the next value in the current document". No ordering, then or now. The precondition lives only in the field comment of the package-private LongRangeCounter (range/LongRangeCounter.java:40, :45-49).
  • What a count means. The upstream random multi-valued tests count a document once per range if any of its values is in it ("ensure each doc can contribute at most 1 count to each range", range/TestRangeFacetCounts.java:1015, :1358) and assert that the facet count and the drill-down count both equal that (:1053, :1072, :1399, :1420).
  • The same API disagrees with itself. DoubleRange/LongRange.getQuery(fastMatchQuery, Multi*ValuesSource), "Create a Query that matches documents in this range", accepts a document if any value is in the range, in any order (range/DoubleRange.java:298-302, range/LongRange.java:285-289).
  • History. #127 (LUCENE-9946, 8.10.0) first searched from interval 0 with a per-document bitset; after a reviewer asked whether it took advantage of "the sortedness of SORTED_NUMERIC", revision 923d35eb0cee added the last-seen-interval search. At the time every multi-valued input was sorted. #543 (LUCENE-10245, 9.1.0) then fed unordered Multi*Values into the unchanged counter; its review, issue and dev@ thread never mention order.
  • Tests. No upstream test builds a custom multi-valued source, and no multi-valued test uses negative doubles.
The devil's-advocate check221 words

Strongest case (built by the devil's advocate; a reviewer from another model family rated it moderate): (a) the counter documents its precondition and the review asked for it; (b) Multi*Values copy the SortedNumericDocValues shape, and every consumer in the module assumes ascending values; (c) SortedNumericDocValuesField says doubles need NumericUtils encoding "with proper sort order", and in #11997 a committer noted that raw-bit multi-valued doubles are not ordered within a document; (d) the classes are @lucene.experimental.

Why it fails: (a) is a package-private invariant that no public API passes on; (b) is unwritten, and Lucene's own fromDoubleField and field constructor break it; (c) does not touch the custom-source trigger, and the facet API documents and decodes raw bits, while with the sortable encoding the field constructor mis-decodes negatives ({-5.0, -6.0} lands in [-2, 0] instead of [-10, -2], executed), so for that constructor neither encoding is reliable for documents with two or more negative values (the sortable encoding mis-decodes every negative value; raw bits drop a lower value that arrives second, as with {-1.0, -5.0}, while raw {-5.0, -6.0}, both in one interval, is counted right); (d) experimental is not unsupported, and custom sources are the purpose of #543. Verdict: a defect. Lead with the custom source; expect "use the sortable encoding" only for the raw-bit trigger.

Suggested fix

#

Recommended Order-independent addMultiValued with the ascending fast path kept (validated)

Make LongRangeCounter.addMultiValued order-independent: keep today's path for ascending values, but search all intervals when a value falls below the last counted one, and count each interval once per document with a small bitset (one file, +43/-25). The new tests, the three independent repros and all 313 facet tests pass, assertions on and off.

Order-independent addMultiValued with the ascending fast path kept (validated) (validated by the checks) (recommended)

#

One file, range/LongRangeCounter.java: a per-document FixedBitSet of counted elementary intervals, allocated once and cleared in startMultiValuedDoc(). A value above the highest counted interval is searched from there, as today; a value inside that interval returns, as today; a value below it is searched over all intervals. Each interval is passed to processMultiValuedHit at most once per document.

final int lastSeen = multiValuedDocLastSeenElementaryInterval;
final int firstCandidateElementaryInterval;
if (lastSeen == -1 || v > boundaries[lastSeen]) {
  firstCandidateElementaryInterval = lastSeen + 1; // ascending: as today
} else if (lastSeen == 0 || v > boundaries[lastSeen - 1]) {
  return; // same interval as the last one counted
} else {
  firstCandidateElementaryInterval = 0; // out of order
}
// ... unchanged binary search from firstCandidateElementaryInterval -> idx
if (multiValuedDocCountedElementaryIntervals.getAndSet(idx) == false) {
  processMultiValuedHit(idx);
}
if (idx > lastSeen) {
  multiValuedDocLastSeenElementaryInterval = idx;
}

Trade-offs

  • Fixes every caller at once: the source paths of both facet classes, the field constructor, and both counters.
  • Cost: ascending input takes the same path as today plus one bitset write per counted interval and a clear per multi-valued document (intervals / 64 words); each out-of-order value pays a full binary search and one bitset write, even when its interval was already counted. Not benchmarked; not reviewed upstream.
  • OverlappingLongRangeCounter already keeps its own per-document interval bitset; a maintainer may prefer to share it.
  • LongRangeCounter.java is unchanged since 2021, so the patch applies to every affected branch. Open PR #16439 also edits this file (its single-valued, exclusive path); expect a small merge.

Sort and de-duplicate each document's values at the callers (the finder's patch, validated) (validated by the checks)

Three files (RangeFacetCounts, LongRangeFacetCounts, DoubleRangeFacetCounts, +34/-24): buffer each multi-valued document's mapped values, sort them, and feed the distinct ones to the unchanged counter.

Trade-offs

Keeps the counter's precondition true, but every multi-valued document pays a buffer copy and an O(k log k) sort even when already sorted (a sortedness check could avoid it), and any new caller must remember to sort.

The simplest code, and essentially what #127 did before its review added the shortcut.

Document an ascending-order contract on Multi*Values.nextValue (a possible API decision; not run, not enough alone)

#

Say that values must arrive in ascending order.

Trade-offs

No counter change, but Lucene's own fromDoubleField, fromFloatField and the field constructor break that contract for raw-bit negatives and would need fixing too, and existing custom sources would stay silently wrong. Paired with those repairs it is a coherent choice a maintainer may prefer: the #127 author relied on sorted input on purpose.

Downstream note

#

A read-only code search of the default branches of Elasticsearch, OpenSearch and Solr found no use of these range-facet classes, so the exposure is mainly applications that embed Lucene's facet module directly.

How it was found

#

Semi-formal: a Z3 model of LongRangeCounter turned its comment "values within a given doc are sorted" into proof obligations. The solver found wrong hits once the order is free, and that raw-bit doubles can arrive unsorted, though never when both are non-negative (why upstream tests in [0, 1) pass). A bounded-exhaustive run of the real counters and JUnit tests followed.

The method in full186 words

Method: SMT solving with Z3 (the semi-formal tier: a hypothesis formed while modelling, then witnessed by the tool), in a hunt unit on facet taxonomy and range counting. The finder tagged it formal; the registry records it as semi-formal because the key obligation was posed as an expected counterexample search from the code comment.

  • Obligations on a model of addMultiValued: with the ascending precondition the per-document hit set equals the true set (unsatisfiable, so it always holds); without it a mismatch exists (satisfiable); raw-bit SortedNumeric order is not ascending in sortable space (satisfiable) but is when both values are non-negative (unsatisfiable), which is why the upstream random tests, all in [0, 1), pass.
  • A bounded-exhaustive run of the real counters: 93,196 range sequences, 0 mismatches with ascending values, 92,376 sequences mis-count when the same documents are fed in descending order; a 24-seed randomized differential against a brute-force oracle classified every mismatch.
  • Then a public-API JUnit on the stock jars, an independent reproducer, read-only reviews by a model from another family (OpenAI GPT-5.6), a devil's advocate, an adjudication, a history sweep and a security scope check.

LFV-303, snapshot of 2026-10-29

Registry title
Multi-valued range facet counts drop matches when a document's values do not arrive in ascending order (custom MultiLongValuesSource/MultiDoubleValuesSource, or raw-bit doubles with two or more negative values): LongRangeCounter.addMultiValued assumes sorted values
Area
facet / range facet counts (LongRangeCounter multi-valued path, exclusive and overlapping counters)
Priority
Medium, rank 140: Multi-valued range facet counts come out silently too low for the javadoc's own distance-source use case, which is more plausible than the fastMatchQuery trigger.
Impact class
silent wrong results
Impact note
Applications that range-facet multi-valued numbers whose values reach the counter out of ascending order get per-range counts (and FacetResult.value) that are silently too low and disagree with the range's own drill-down query: a custom MultiLongValuesSource or MultiDoubleValuesSource such as per-request distances to each of a document's locations (the use case the class javadoc names), MultiDoubleValuesSource.fromDoubleField/fromFloatField or the DoubleRangeFacetCounts(String, ...) constructor over raw-bit SortedNumeric doubles when a document has two or more negative values, or fromField with a decreasing decoder; default codec, IndexWriterConfig and searcher, any scale (one document with two values suffices), released 8.10.0-10.5.2; long fields, fromLongField/fromIntField and sortable-encoded doubles are not affected, and counts are only ever too low, never too high.
Summary
You compute range facet counts over a multi-valued source, for example the distances from the user to each of a document's locations computed by your own MultiDoubleValuesSource, or doubles stored as raw bits in a SortedNumeric field and read with fromDoubleField or the DoubleRangeFacetCounts(String, ...) constructor. You expect each range to count every document that has at least one value in it, which is exactly what the range's own drill-down query finds. Instead, when a document's values arrive in descending order (a custom source in its natural order, or raw-bit doubles whenever the document has two or more negative values), the counter skips every later value that sorts below an interval it already counted for that document, so a document with distances {3.0, 0.5} is missing from '< 1 km' and '< 2 km'.
Introduced
d669ddebc538 (LUCENE-9946, PR #127 'Support multi-value fields in range facet counting', by GitHub gsmiller), released first in 8.10.0 through the lucene-solr branch_8x backport e1ffcb11d9c2 (PR #2507) [read: git log -S 'multiValuedDocLastSeenElementaryInterval' finds only d669ddebc538; git blame -w on LongRangeCounter.java:45-50 and 117-161; read-only GitHub API for the PR revisions and the backport's containment in the 8.10.0 but not the 8.9.0 release commit; exec: 8.9.0 rejects multi-valued range faceting, 8.10.0 fails]. The ascending-order shortcut came in during review (PR revision 923d35eb0cee 'optimize the bsearch for multi-valued cases', after rmuir asked about using the sortedness of SORTED_NUMERIC); the PR's earlier search from interval 0 did not depend on order. Exposure widened by 82703757fe05 (LUCENE-10245, PR #543, 9.1.0), which fed MultiLong/MultiDoubleValues, whose nextValue() promises no order, into the unchanged counter. A shortcut that was valid while SortedNumericDocValues was the only multi-valued input, not a later regression (2021-05-30 (d669ddebc538, -0700; 2021-05-31 UTC); branch_8x backport 2021-06-24; exposure widened 2022-01-10 (82703757fe05))
