SynonymQuery.Builder.addTerm keeps the term it rejects with TooManyClauses, so build() can return a query over the clause limit

SynonymQuery.Builder.addTerm stores a term before it checks the clause limit, so a term it rejects with TooManyClauses stays in the builder, and build() returns a query over the limit that still matches it. Every release since 8.1.0 has it.

The finding in 30 seconds

#

addTerm appends the term to its list first (SynonymQuery.java:95) and checks the limit second (:96-98); build() never checks again. So the exception leaves the rejected term inside the builder. BooleanQuery.Builder.add does it the other way round: check, then store.

SynonymQuery and the clause limit in one minute

#
  1. SynonymQuery matches any of several terms in one field and scores them as if they were one term. QueryBuilder and the query parsers build one for each set of synonyms the analyzer produces.
  2. IndexSearcher.getMaxClauseCount() (1024 by default, set with setMaxClauseCount) caps how many clauses a query may hold. The query builders throw IndexSearcher.TooManyClauses when you try to add one more.
  3. With BooleanQuery.Builder, a rejected add changes nothing, so code can catch the exception and build what it has. MoreLikeThis does exactly that.

The finding, step by step

#
  1. Set the clause limit to 2 with IndexSearcher.setMaxClauseCount(2) (the default 1024 and a 1025th synonym behave the same), and add terms a and b to a SynonymQuery.Builder for field f.
  2. Add a third term, c. addTerm throws IndexSearcher.TooManyClauses, as documented. You catch it and call build(), the way Lucene's own MoreLikeThis caps a BooleanQuery.
  3. You expect Synonym(f:a f:b): 2 terms, within the limit, just as BooleanQuery.Builder keeps nothing of a clause it rejects.
  4. Instead build() returns Synonym(f:a f:b f:c): addTerm appended c before it checked the limit, and build() does not check again.
  5. On an index with one document per term, search(q, 10) returns 3 hits, including the document that has only c, while count(q), a FILTER clause and ConstantScoreQuery(q) throw TooManyClauses.

Who is affected

#

Code that builds a SynonymQuery itself, catches TooManyClauses from addTerm (for example to cap a long synonym list at the limit) and then calls build(). The default limit of 1024 is enough. Lucene's own callers, QueryBuilder and the query parsers, never catch it and keep building, so they are not hit. Contrived, hence Low.

Mechanism, terms and numbers442 words

A SynonymQuery may hold at most IndexSearcher.getMaxClauseCount() terms (1024 by default). SynonymQuery.Builder.addTerm appends the new term to its list first (SynonymQuery.java:95 on main) and only then checks the limit and throws TooManyClauses (:96-98); build() does not check again (:103-106). So the term it rejects stays in the builder. A caller that catches the exception and builds, the catch-and-build pattern Lucene's own MoreLikeThis uses with BooleanQuery.Builder, gets a query over the limit that contains the rejected term: with the limit at 2, Synonym(f:a f:b f:c). A scored search then matches documents of the rejected term, while count(), FILTER and MUST_NOT clauses and ConstantScoreQuery throw TooManyClauses, because the non-scoring path rebuilds the terms as a BooleanQuery. BooleanQuery.Builder.add and BlendedTermQuery.Builder.add check before they store. Every release since 8.1.0 has it; Lucene's own code is not affected: QueryBuilder.newSynonymQuery, which the query parsers use, lets the exception propagate, and the classic QueryParserBase.parse catches it only to rethrow it as a ParseException; no in-tree caller catches it and keeps building.

The code (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/search/SynonymQuery.java)

#
public Builder addTerm(BytesRef term, float boost) {          // :90
  if (Float.isNaN(boost) || ...) throw new IllegalArgumentException(...); // :91-94, rejects before storing
  terms.add(new TermAndBoost(term, boost));                    // :95, stored first
  if (terms.size() > IndexSearcher.getMaxClauseCount()) {      // :96, checked second
    throw new IndexSearcher.TooManyClauses();                  // :97, the term is already in the list
  }
  return this;
}
public SynonymQuery build() {                                  // :103-106, no check
  terms.sort(Comparator.comparing(a -> a.term));
  return new SynonymQuery(terms.toArray(TermAndBoost[]::new), field);
}

Step by step (limit 2)

#
  1. addTerm(a), addTerm(b): the list is [a, b], size 2, not over the limit.
  2. addTerm(c): the list becomes [a, b, c], size 3 > 2, TooManyClauses is thrown. Nothing removes c.
  3. build() returns Synonym(f:a f:b f:c). Each further rejected call adds one more term: a probe that catches two rejected calls (c, d) builds 4 terms.

Why scored search and count disagree

#
  • Scored search runs. IndexSearcher's clause visitor counts a whole SynonymQuery as one clause (consumeTerms, IndexSearcher.java:916-921), so rewrite accepts the query, and the scoring weight (SynonymWeight, :184-185) matches every stored term: on an index with documents f:a, f:b, f:c, search(q, 10) returns 3 hits.
  • Count and filters throw. Without scores, createWeight rebuilds the terms as a BooleanQuery with one SHOULD TermQuery per term (:186-195, bq.add at :190), and BooleanQuery.Builder.add throws at the third clause (BooleanQuery.java:82-83). Stack (abridged): BooleanQuery$Builder.add(BooleanQuery.java:83) <- ... <- SynonymQuery.createWeight(SynonymQuery.java:190) <- ConstantScoreQuery.createWeight <- ... <- IndexSearcher.count(IndexSearcher.java:527). A FILTER or MUST_NOT clause and ConstantScoreQuery(q) take the same path.
Exposure and likelihood149 words
  • Who is hit. Application code that builds a SynonymQuery with SynonymQuery.Builder, catches TooManyClauses from addTerm, and keeps the builder. Default configuration is enough: the default limit of 1024 and a 1025th synonym.
  • What they see. No error from build(). The query holds one extra term per rejected call: scored searches match documents of the rejected synonyms, and the same query later throws TooManyClauses from count(), as a FILTER or MUST_NOT clause, or inside ConstantScoreQuery.
  • Not hit. QueryBuilder.newSynonymQuery (QueryBuilder.java:603-608), the only non-test user of the builder, used by the query parsers, lets the exception propagate, and the classic QueryParserBase.parse catches TooManyClauses only to rethrow it as a ParseException (QueryParserBase.java:140-144). No Lucene code catches it from this builder and keeps building.
  • How likely. Contrived: it needs the catch-and-continue pattern on this builder, and nobody has reported it since 8.1.0. Hence priority Low.

Why it looks unintended

#
  • getMaxClauseCount is "the maximum number of clauses permitted", yet build() returns a query with more.
  • BooleanQuery.Builder.add, BlendedTermQuery.Builder.add and addTerm's own field and boost checks all reject before they store, and MoreLikeThis relies on that.
  • Counter: do not reuse a builder after it threw. Nothing documents that, and the order arrived unremarked with the builder in 8.1.0.
The full argument216 words
  • Contract. getMaxClauseCount: "Return the maximum number of clauses permitted, 1024 by default. Attempts to add more than the permitted number of clauses cause TooManyClauses to be thrown." (IndexSearcher.java:246-247). TooManyClauses: "Thrown when an attempt is made to add more than getMaxClauseCount() clauses" (:1171). build() still returns more than is permitted.
  • The sibling builders. BooleanQuery.Builder.add checks clauses.size() >= IndexSearcher.maxClauseCount before clauses.add (BooleanQuery.java:82-85); its comment calls the check "necessary to prevent run-away 'rewriting' of bad queries from creating BQ objects" (:79-81). BlendedTermQuery.Builder.add does the same (BlendedTermQuery.java:94-100). In addTerm itself, the field check (:80-82) and the boost check (:91-94) also run before the add; only the limit check runs after.
  • Lucene relies on "rejected means not added". MoreLikeThis.createQuery (abridged): try { query.add(tq, SHOULD); } catch (IndexSearcher.TooManyClauses _) { break; } ... return query.build(); (MoreLikeThis.java:609-615). #11009 (LUCENE-9970) describes a builder's TooManyClauses as the builder refusing to let its caller add the clause.
  • History. Before the builder, the SynonymQuery(Term...) constructor threw for terms.length > BooleanQuery.getMaxClauseCount() (8.0.0, SynonymQuery.java:73-74), so no over-limit query could be obtained. LUCENE-8652 (d8cfeba912e, 2019) added the builder with append-then-check; its commit message is about boosts, and the 13 comments on #9698 never discuss the order of the check.
The devil's-advocate check132 words

The case for "intended": addTerm's javadoc promises nothing about the builder after it throws and has no @throws (unlike BooleanQuery.Builder.add, BooleanQuery.java:71); Java mutators are not failure-atomic in general; MultiPhraseQuery.Builder.add sets its field before it validates (MultiPhraseQuery.java:127-134); and no Lucene caller keeps building after the exception. So: do not reuse a builder after it threw. The cross-model reviews rated this argument moderate.

Why it fails: the limit is documented as what is permitted, yet the builder hands out a query over it; the core builders of the same limit treat the exception as "not added", and Lucene's own MoreLikeThis depends on that; and the order came in with the builder without discussion. Verdict: not intended, a defect (Low). The reuse point is answered by BooleanQuery.Builder.add and MoreLikeThis.

Suggested fix

#

Recommended A: check the limit before storing the term

Fix A: check terms.size() >= IndexSearcher.getMaxClauseCount() before terms.add, the order BooleanQuery.Builder.add uses (one file, +2/-2, no API change; exactly maxClauseCount terms are still accepted). The repro, TestSynonymQuery and TestQueryBuilder pass, and so do the format, forbidden-API and lint checks.

public Builder addTerm(BytesRef term, float boost) {
  if (Float.isNaN(boost) || Float.compare(boost, 0f) <= 0 || Float.compare(boost, 1f) > 0) {
    throw new IllegalArgumentException(
        "boost must be a positive float between 0 (exclusive) and 1 (inclusive)");
  }
  if (terms.size() >= IndexSearcher.getMaxClauseCount()) { // was: add first, then '>'
    throw new IndexSearcher.TooManyClauses();
  }
  terms.add(new TermAndBoost(term, boost));
  return this;
}

A: check the limit before storing the term (validated by the checks) (recommended)

#

Move the check above terms.add and compare with >=, as BooleanQuery.Builder.add does (BooleanQuery.java:82-85). Optionally add @throws IndexSearcher.TooManyClauses to the addTerm javadocs, as on BooleanQuery.Builder.add (:71).

public Builder addTerm(BytesRef term, float boost) {
  if (Float.isNaN(boost) || Float.compare(boost, 0f) <= 0 || Float.compare(boost, 1f) > 0) {
    throw new IllegalArgumentException(
        "boost must be a positive float between 0 (exclusive) and 1 (inclusive)");
  }
  if (terms.size() >= IndexSearcher.getMaxClauseCount()) { // was: add first, then '>'
    throw new IndexSearcher.TooManyClauses();
  }
  terms.add(new TermAndBoost(term, boost));
  return this;
}

Trade-offs

  • The limit is unchanged: exactly maxClauseCount terms are still accepted, and the next one throws.
  • After the exception the builder holds the accepted terms only, as with BooleanQuery.Builder. No API change; one file.

What the checks validated

  • gradle, scratch worktree of 5adff78bb168: the repro and TestSynonymQuery pass with assertions on and off (11 tests, 0 failures); TestQueryBuilder passes (26 tests); :lucene:core:checkGoogleJavaFormat, forbiddenApisMain, forbiddenApisTest, ecjLintMain and ecjLintTest pass with the test added.
  • The finder's search-versus-count test and the independent reproducer's test also pass with this change applied.

B: remove the term again before throwing

#

Keep the order and the > comparison, and call terms.removeLast() inside the if before the throw.

Trade-offs

Same behaviour as A, but a less obvious idiom than checking first, and it differs from the sibling builders.

C: A plus a check in build()

#

Also throw TooManyClauses from build() when the list is longer than the current limit.

Trade-offs

Also rejects a builder that was filled under a higher limit before setMaxClauseCount was lowered. That changes when the exception appears for callers who are not affected today, and this bug does not need it.

D: document only

#

Say in the addTerm javadocs that the builder must not be used after it throws TooManyClauses.

Trade-offs

No code change, but build() can still return a query over the limit, and the builder stays inconsistent with BooleanQuery.Builder, whose behaviour MoreLikeThis relies on.

Downstream note

#

Applications that cap synonym lists by catching TooManyClauses from SynonymQuery.Builder.addTerm should stop adding at the limit themselves, or rebuild without the rejected term, until a fix ships.

How it was found

#

A proof-obligation check of SynonymQuery.Builder's contract (a term that addTerm rejects with TooManyClauses must not end up in the built query, as with BooleanQuery.Builder.add) found that the limit check runs after the term is stored. An executable JUnit test then showed the rejected term in build()'s result.

The method in full102 words

Method: semi-formal (2026-11-04, main 5adff78bb168).

  • The obligation: after addTerm throws TooManyClauses, the builder's term list is unchanged, so build() never returns more than getMaxClauseCount() terms (IndexSearcher.java:246-247, :1171). addTerm discharges it for the field and boost checks (:80-82, :91-94) but not for the limit check, which runs after terms.add (:95-98); build() (:103-106) has no check that could restore it.
  • Witness: a public-API JUnit test on a three-document index (scored search versus count()), and a probe showing one extra term per rejected call; later reduced to the no-index getTerms() test here.

#
