A zero-length token makes TokenStreamToAutomaton drop every path through it, so the document suggester, AnalyzingSuggester and FuzzySuggester silently lose the suggestion

With ArabicAnalyzer, "foo ـ bar" (a standalone tatweel) never comes back for "foo": the tatweel becomes an empty token, and TokenStreamToAutomaton adds no arc for a token with no bytes, so every path through it vanishes. The document suggester (since 5.1.0), AnalyzingSuggester and FuzzySuggester (since 4.1.0) lose such values silently.

The bug in 30 seconds

#

Completion suggesters turn each value's tokens into an automaton, one arc per byte. A token with no bytes gets no arc, so every path through it is cut: the value gets no suggestion entry, and a lookup key with such a token matches nothing.

  1. Index two suggestions with the stock ArabicAnalyzer: "foo bar" (weight 1) and "foo ـ bar" (weight 2; the middle character is a standalone tatweel, U+0640). The analyzer turns them into the tokens [foo, bar] and [foo, "", bar].
  2. Ask for the prefix "foo": PrefixCompletionQuery on a SuggestField, or lookup("foo") on AnalyzingSuggester or FuzzySuggester. You expect both suggestions, [foo ـ bar, foo bar].
  3. You get [foo bar]. The suggester turns a value's tokens into an automaton with one arc per byte. The empty token has 0 bytes, so no arc reaches the state after it, and the automaton for "foo ـ bar" accepts no string at all.
  4. So ConcatenateGraphFilter emits 0 tokens for a token graph with exactly one path, the document gets no completion entry, and AnalyzingSuggester counts 1 entry for 2 inputs. The document and its other fields are indexed; only the suggestion entry is missing. Nothing throws, with assertions on or off.
  5. Not only Arabic: a chain that strips punctuation turns "-" into "", so "Spider Man - Homecoming" never comes back for "spider". In a test set of 84 suggestions, all 45 that contain a standalone tatweel got no entry: the 42 that mix it with words should have one (the 3 made only of tatweels get none even with the recommended fix).

Who is affected

#

Applications using SuggestField/CompletionAnalyzer, AnalyzingSuggester, FuzzySuggester or ConcatenateGraphFilter, for values whose analysis has an empty token: a standalone tatweel under the stock Arabic, Persian or Sorani analyzer, or a filter that blanks a token, such as punctuation stripping. Deterministic and silent for every value whose only path runs through the empty token; index size plays no part; other entries are unaffected.

Mechanism, terms and numbers691 words

TokenStreamToAutomaton turns a token graph into an automaton whose labels are each token's bytes, with a separator (POS_SEP) between tokens. For each token it creates the state where the token ends and adds one arc per byte, the last one into that state. A token whose term is empty has no bytes, so no arc is added, the end state is never reached, and every path through the token is lost. Stock analysis emits such tokens on purpose: ArabicAnalyzer, PersianAnalyzer and SoraniAnalyzer turn a standalone tatweel (U+0640) into "", and PatternReplaceFilter can blank a punctuation-only token. Everything built on the class then drops the value without an error (the other suggesters, such as the infix and FST lookups, do not use it): ConcatenateGraphFilter emits no token although it promises "one output token for every path", the document suggester (SuggestField, CompletionAnalyzer) indexes no entry, and AnalyzingSuggester and FuzzySuggester skip the input. With ArabicAnalyzer, the suggestions "foo bar" and "foo ـ bar" and the prefix "foo" give only [foo bar]; a lookup that contains a standalone tatweel returns nothing. A stacked empty token loses only its own path. The loop has had no zero-length case since the class was written in 2012: all 120 release tags from 4.1.0 to 10.5.2 in the history clone have it, the 21 releases executed fail, and so does main.

Terms

#
  • Empty token: a token whose term has zero characters, "". Lucene allows them, and some stock filters produce them on purpose: the Arabic, Persian and Sorani normalizers delete the tatweel (U+0640), a typographic stretching mark, so a tatweel standing alone between spaces becomes ""; PatternReplaceFilter can blank a token such as -.
  • TokenStreamToAutomaton: turns the tokens of one value into an automaton, a graph of states joined by arcs, one arc per byte of each token, with a separator arc (SEP) between tokens and a HOLE arc where a position is missing (a removed stop word). Each path from the start to an accept state spells one way to read the value.
  • Its users: ConcatenateGraphFilter joins every path into one token; the document suggester (SuggestField, CompletionAnalyzer) indexes those joined tokens; AnalyzingSuggester and FuzzySuggester index the automaton's strings directly. The other suggesters (AnalyzingInfixSuggester, BlendedInfixSuggester, FreeTextSuggester, FSTCompletionLookup, WFSTCompletionLookup) do not use it.

The bug

#
  1. For every token, the state where the token ends is created first (TokenStreamToAutomaton.java:178-181).
  2. The token's arcs are added only inside for (int byteIDX = 0; byteIDX < termLen; byteIDX++) (:197-207); the last arc ends in that state.
  3. For an empty token termLen is 0, the loop runs zero times, and nothing joins the state where the token starts to the state where it ends. Everything after it hangs off an unreachable state: for foo, "", bar the automaton accepts no string.
  4. With no strings, ConcatenateGraphFilter emits no token, the completion field gets no entry, and the analyzing suggesters get no input. If the empty token is stacked on a non-empty one at the same position, only its own path is lost.

Exposure and likelihood343 words
  • Entry points. The document suggester (SuggestField, ContextSuggestField, CompletionAnalyzer, PrefixCompletionQuery and its siblings), AnalyzingSuggester, FuzzySuggester, and ConcatenateGraphFilter (or its concatenateGraph factory) in any analysis chain.
  • What it takes. A value, or a lookup key, whose analysis contains a token with an empty term that the paths must cross (an empty token stacked next to a non-empty one loses only its own path). Stock prebuilt analyzers: ArabicAnalyzer, PersianAnalyzer and SoraniAnalyzer on a standalone tatweel. Custom chains: a filter that can blank a token with no LengthFilter after it, for example PatternReplaceFilter stripping punctuation under a whitespace tokenizer (its javadoc warns it "may produce Tokens whose text is the empty string"), or KeywordTokenizer + TrimFilter on blanks.
  • Opt-in. The completion suggesters and ConcatenateGraphFilter are features an application chooses (the document suggester also needs a completion postings format), and TokenStreamToAutomaton, ConcatenateGraphFilter and the suggester classes are marked experimental (the analyzers and PatternReplaceFilter are not). Within such an application the trigger is ordinary text.
  • Deterministic and silent. Every value whose only path runs through an empty token is lost on the first try, with assertions on or off; no exception, no log line. The automaton is built from the value's own tokens, so index size plays no part. In the security probe the document and its other fields were indexed, CheckIndex was clean and other entries were unaffected.
  • Both sides. At index time the value never becomes a suggestion (the document is indexed, its completion entry is not); at lookup time a key with a standalone tatweel ("foo ـ") returns nothing.
  • Not affected. AnalyzingInfixSuggester, BlendedInfixSuggester, FreeTextSuggester, FSTCompletionLookup and WFSTCompletionLookup do not use TokenStreamToAutomaton or ConcatenateGraphFilter.
  • How often. A standalone tatweel is uncommon in titles and names (it normally sits inside words); a punctuation-stripping chain hits ordinary text such as "Spider Man - Homecoming" every time. Nobody has reported it since 4.1.0, so the registry rates it rare (a judgement, not a measurement).
  • Downstream. Search servers build completion features on these classes; that path was not executed.

Why it is a bug, not intended

#
  • ConcatenateGraphFilter promises "one output token for every path"; foo → "" → bar has one path and gets none.
  • The authors' own 2012 comment says two adjacent separators also match an empty-string token; on our reading, its path was meant to survive.
  • Empty tokens are intended: Lucene's Sorani test asserts that a standalone U+0640 normalizes to "".
The full argument317 words
  • ConcatenateGraphFilter javadoc (ConcatenateGraphFilter.java:40-41): "Concatenates/Joins every incoming token with a separator into one output token for every path through the token stream (which is a graph)."
  • TokenStreamToAutomaton javadoc (:31-33): the labels are the token's bytes, and "Between tokens we insert POS_SEP and for holes we insert HOLE." Read literally, a, "", b gives a SEP SEP b, not an empty language; the javadoc does not mention empty tokens, so this is a reading, not an explicit rule.
  • The authors' comment in replaceSep (AnalyzingSuggester.java:295-301, added with the trunk commit of the class, f2f91bae46c; the copy at ConcatenateGraphFilter.java:316-322 came later through CompletionTokenStream, LUCENE-6339, and LUCENE-8332): removing a hole leaves "two SEP tokens next to each other ... Note that it will also match an empty-string token". Our reading, an inference: it assumes the empty token's path is there.
  • preservePositionIncrements javadoc (ConcatenateGraphFilter.java:103-105): "Whether to add an empty token for missing positions. The effect is a consecutive SEP_LABEL."
  • Empty terms are legal: TestSoraniNormalizationFilter asserts checkOneTerm(a, "\u0640", "") (:85); PatternReplaceFilter's javadoc warns it may produce empty tokens; LUCENE-3529 and LUCENE-4880 made IndexWriter and MemoryIndex accept empty terms. Being legal to index does not by itself mean every experimental graph consumer promises to handle them; the case rests on the ConcatenateGraphFilter promise and on the absence of any exclusion.
  • Upstream tests: one randomized test, TestFlattenGraphFilter (:702), asserts that this class's output for its graphs has no dead states (not a stated invariant, but dead states are not expected output); the empty-token automaton has them. TestGraphTokenizers and TestConcatenateGraphFilter cover holes and an empty stream, never a zero-length token, and no test pins today's behaviour.
  • History: the loop never had a zero-length case (LUCENE-3842, 2012); the 66 JIRA comments of that issue discuss holes and separators only, and no won't-fix or by-design discussion was found.
The devil's-advocate check218 words

Strongest case for "intended": the classes that build and consume the automaton are experimental; PatternReplaceFilter warns about empty tokens, so users should add LengthFilter(min=1); some components reject empty tokens; AnalyzingSuggester documents that "Lookups with the empty string return no results", SuggestField rejects an empty value, and an empty stream yields no output by design. And an empty term has no byte for an arc, so encoding it as a HOLE conflates a real token with a missing position; nobody has reported the behaviour.

Why it fails: experimental allows API changes, not silent loss of entries; no javadoc of these classes asks for non-empty tokens, and the authors' comment, on our reading, expects the empty token to survive; the prebuilt Arabic, Persian and Sorani analyzers have no option for an extra filter (wrapping them works, but nothing tells users to); the empty-input rules cover an empty value, stream or lookup, not a non-empty value with one empty token inside; and an upstream test treats dead states as a failure for its graphs. The encoding point is about how to keep the path, not whether to keep it. Every checker concluded "not intended". The exact joined form (a SEP SEP b or a SEP b) is a design choice for the maintainers; the path must not vanish.

Suggested fix

#

Recommended Connect an empty token like a hole, unless every token is empty (recommended of the two tested shapes)

Recommended of the two tested shapes: connect a zero-length token like a hole (one HOLE arc to its end state), only when the stream also has a non-empty token, so an all-empty lookup still matches nothing. +20 lines; the new tests and the core analysis, analysis-common and suggest suites pass. Limit: an all-empty ContextSuggestField value gets an entry.

Connect an empty token like a hole, unless every token is empty (recommended of the two tested shapes) (validated by the checks) (recommended)

#

optionA2-hole-arc-unless-all-empty.diff, TokenStreamToAutomaton.java only, +20 lines (counting an IntArrayList import and two blank lines). Each empty token's start and end states are recorded; after the loop they get the one HOLE arc a hole gets, if the stream had any non-empty token. ConcatenateGraphFilter and AnalyzingSuggester (so also FuzzySuggester) turn HOLE into an epsilon, so a, "", b is joined as a SEP SEP b, the form the replaceSep comment and the preservePositionIncrements javadoc describe; direct callers of toAutomaton, such as the test framework's assertGraphStrings, see the raw HOLE label. A stream of only empty tokens keeps today's automaton (it accepts nothing), so a lookup key made only of empty tokens still matches nothing, like an empty key, and for SuggestField, AnalyzingSuggester and FuzzySuggester a value made only of tatweels still gets no entry. Automaton.Builder accepts transitions in any order.

    // (from, to) state pairs of zero-length tokens, connected at the end:
    final IntArrayList emptyTokens = new IntArrayList();
    boolean sawNonEmptyToken = false;
    while (in.incrementToken()) {
      ...
      if (termLen == 0) {
        emptyTokens.add(state);
        emptyTokens.add(endPosData.arriving);
      } else {
        sawNonEmptyToken = true;
      }
      ...
    }
    in.end();

    if (sawNonEmptyToken) {
      // A zero-length token has no bytes, but it still spans its position(s): connect it like a
      // hole so the paths through it are kept (consumers remove HOLE, leaving two adjacent
      // separators). A stream of only zero-length tokens accepts nothing, like an empty stream.
      for (int i = 0; i < emptyTokens.size(); i += 2) {
        builder.addTransition(emptyTokens.get(i), emptyTokens.get(i + 1), HOLE);
      }
    }

Trade-offs

  • ContextSuggestField: the all-empty exception looks at the whole stream, and ContextSuggestField puts a non-empty context-prefix token in front of the value. So with this fix a ContextSuggestField value made only of tatweels gets an entry with an empty key (stock gets none), and a match-all ContextQuery returns it (executed by the fact check). The guard test checks only the lookup side. Any non-empty token, even one stacked alternative, turns the exception off.
  • An empty token and a removed (hole) token become the same in the automaton when preservePositionIncrements is true; with false a hole collapses to a SEP b while this fix still gives a SEP SEP b. The exact form is the maintainers' choice.
  • A prefix lookup "foo" returns "foo ـ bar", but the exact lookup "foo bar" does not match it, as with a stop-word hole.
  • Edges: a stream whose only position holds a non-empty token and a stacked empty one also accepts the empty string (no stock analyzer was seen producing that); an empty token with positionLength > 1 gets one HOLE arc across its span (untested).
  • Not reviewed by a committer.

Trade-offs

A value or lookup made only of empty tokens becomes the empty string: a lookup for a lone tatweel returns every suggestion (AnalyzingSuggester 2 of 2 instead of 0, PrefixCompletionQuery 1 of 1), against the documented "Lookups with the empty string return no results". With assertions off a ContextQuery returns 2 of 2, including an entry made only of a tatweel; with assertions on that lookup fails with an AssertionError at ContextQuery.java:319.

Join an empty token without its position (a SEP b)

#

Treat a zero-length token like a removed token with preservePositionIncrements=false, so "foo ـ bar" matches the lookup "foo bar".

Trade-offs

More code (merge the token's start and end states, or an epsilon), and an empty token then behaves differently from a hole, against the preservePositionIncrements javadoc. Untested.

Remove empty tokens in each consumer

#

Wrap the stream in ConcatenateGraphFilter and the analyzing suggesters with a filter that drops empty tokens and carries their position increment, as LengthFilter does.

Trade-offs

For an empty token alone at its position it gives the recommended fix's result for those consumers; for a stacked one (position increment 0) the filter removes the alternative, while the recommended fix keeps it as a HOLE path. TokenStreamToAutomaton stays wrong for its other callers (for example the test framework's assertGraphStrings), and three places change instead of one. Untested.

Make an empty token explicit: reject it, or give it its own label

#

Either toAutomaton throws on a zero-length term, so the loss becomes loud, or the empty token gets its own label instead of HOLE, so consumers can tell it from a missing position.

Trade-offs

Rejecting makes values that index silently today fail at index time; a new label needs every consumer of the automaton to handle it. Untested; listed because the cross-model fact check suggested presenting it.

Workaround in every affected release: drop empty tokens before the suggester (validated by the checks)

#

In a CustomAnalyzer, add the length filter with min=1; around a prebuilt analyzer, an AnalyzerWrapper whose wrapComponents appends new LengthFilter(tokenStream, 1, Integer.MAX_VALUE). LengthFilter turns the removed token into a hole, so the value is joined as foo SEP SEP bar, the same form as the recommended fix for an empty token alone at its position (a stacked empty token is simply removed).

Trade-offs

Each application has to know about it; nothing in the suggester documentation says it is needed.

On stock main, ArabicAnalyzer wrapped this way returns [foo ـ bar, foo bar] from both AnalyzingSuggester and SuggestField (2 tests, 0 failures).

How it was found

#

Bounded-exhaustive translation validation: a checker compared the real ConcatenateGraphFilter and TokenStreamToAutomaton with an independent reference of the documented join semantics over every token graph of up to 3 positions (1,041,120 checks). Paths through an empty token went missing; a suggester-level checker and a survey of stock analyzers then found the tatweel trigger.

The method in full240 words

Method: bounded-exhaustive translation validation (a hunt unit, completion suggester indexing, 2026-10-26, main ea57360912ed). No model checker, SMT solver or prover was involved.

  • The finder (an AI tool) wrote an independent reference of the documented join semantics: one output token for every path, separators between tokens, holes for missing positions.
  • Its checker (ConcatGraphTV.java) ran the real classes against it over every token graph of up to 3 positions, each a hole or 1-2 distinct stacked tokens from an 8-token alphabet that includes the empty token (every token with position length 1; graphs made only of holes skipped), with trailing holes on and off, 5 separators and both preservePositionIncrements settings: 1,041,120 checks. The run reported 889,575 mismatches in all, sorted into classes; the class "missing paths through an empty token" (245,958 checks) is this bug, and the other classes (separator escaping, non-ASCII separators, the expansion limit and an unclassified rest) are separate questions, not part of this report.
  • A suggester-level checker (SuggestTV.java), with a token mapped to "", found 7,915 mismatching (query x configuration) checks out of 13,440, each missing one or more results and none returning an extra one; a survey of stock analyzers found that the Arabic, Persian and Sorani analyzers emit an empty token for a standalone tatweel.
  • Then a public-API JUnit, a cross-model review, independent verifiers, an adjudication, a 66-run release sweep, a prior-report search and a security screen (see Independent checks).

Present since the class was written for LUCENE-3842 (2012) and first released in 4.1.0; the loop never changed. Fails on all 21 releases tried from 4.1.0 to 10.5.2 and on main. Silent everywhere except 4.10.x and 5.1-5.2, where unrelated changes made it throw. Not fixed upstream.

Versions tested9 rows

Introduced by LUCENE-3842 "add AnalyzingSuggester" (@mikemccand, issue #4915): written on the feature branch in 9d7873ff5a6 (2012-09-15), committed to trunk as f2f91bae46c and merged to branch_4x as 0c89e05d765 (2012-09-28). The trunk commit added the replaceSep comment (in AnalyzingSuggester) that, on our reading, expects an empty-string token to read as two separators. Later edits to the loop (LUCENE-5030, LUCENE-5752, LUCENE-6653, the LUCENE-9570 reformat) added no zero-length case. Not a regression.

Consumers are affected from their own first release: AnalyzingSuggester and FuzzySuggester 4.1.0, the document suggester 5.1.0 (LUCENE-6339), ConcatenateGraphFilter 7.4.0 (LUCENE-8332). On 4.10.x and 5.1-5.2 the same lost path made an unrelated automaton change throw IllegalStateException: from state (0) already had transitions added; LUCENE-5963 and LUCENE-6365 made it silent again. No issue links that exception to empty tokens. On upstream main the file's last change is the 2020 reformat.

Bug record

LFV-523, snapshot of 2026-10-28

Registry title
A zero-length token makes TokenStreamToAutomaton drop every path through it, so ConcatenateGraphFilter emits nothing and the document suggester, AnalyzingSuggester and FuzzySuggester silently lose that suggestion (stock trigger: a standalone tatweel U+0640 with ArabicAnalyzer, PersianAnalyzer or SoraniAnalyzer)
Area
analysis / TokenStreamToAutomaton (core), reached through ConcatenateGraphFilter (analysis-common) and the completion suggesters (suggest: NRT document suggester, AnalyzingSuggester, FuzzySuggester)
Priority
Medium, rank 53: A zero-length token (for example a standalone tatweel under the stock Arabic analyzers) silently drops the whole suggestion from the completion suggesters, a rare silent suggester loss like LFV-248.
Impact class
silent wrong results
Impact note
Hits applications that use a completion suggester (the NRT document suggester through SuggestField or CompletionAnalyzer, AnalyzingSuggester or FuzzySuggester) or ConcatenateGraphFilter directly, and only for values whose analysis contains a zero-length token, which the stock ArabicAnalyzer, PersianAnalyzer and SoraniAnalyzer emit for a standalone tatweel and custom chains emit when a filter such as PatternReplaceFilter blanks a punctuation-only token: that suggestion is silently never indexed or never returned (a stacked empty token loses only its own alternative path), with -ea and -da, no scale needed and no exception.
Summary
You index the suggestion 'foo ـ bar' (a standalone Arabic tatweel between two words) with ArabicAnalyzer into a SuggestField, or build an AnalyzingSuggester or FuzzySuggester from it, and expect a lookup for 'foo' to return it next to 'foo bar', because ArabicAnalyzer turns the tatweel into an ordinary empty token and ConcatenateGraphFilter promises one output token for every path through the token graph. Instead TokenStreamToAutomaton adds a token's transitions only inside its per-byte loop, which never runs for a zero-length token, so the token's end state is unreachable: ConcatenateGraphFilter emits nothing, the document suggester indexes no entry for the value and the analyzing suggesters skip the input, so the suggestion never comes back. A stacked empty token loses only its own alternative path; nothing throws, with assertions on or off.
