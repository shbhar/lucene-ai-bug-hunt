Intervals.analyzedText drops stacked synonyms when another token of the text spans several positions (e.g. a multi-word synonym)

With the synonym rules wifi => wi fi and dog => canine, Intervals.analyzedText("wifi dog") finds 2 of 4 documents and misses "wifi dog" itself: once one word has a multi-word synonym, each position outside that synonym's span keeps only the first token stacked there. With assertions on it throws AssertionError; since 9.1.0.

The bug in 30 seconds

#

Interval queries built from analyzed text lose stacked synonyms as soon as some other word of the same text has a multi-word synonym.

  1. Give the query analyzer two SynonymGraphFilter rules, wifi => wi fi (two words) and dog => canine (one word), and index 4 documents: "wifi dog", "wifi canine", "wi fi dog", "wi fi canine".
  2. Search with Intervals.analyzedText("wifi dog", analyzer, "f", 0, true), or fn:or("wifi dog") in the flexible query parser. You expect all 4: QueryBuilder with the same analyzer finds 4, and analyzedText("dog") alone keeps or(canine, dog).
  3. You get 2, "wifi canine" and "wi fi canine". The document with exactly the query text is missed: the built query is or(BLOCK(wi,fi,canine), BLOCK(wifi,canine)), and dog is gone.
  4. Why: wifi spans two positions, so the whole text takes the builder's token-graph path. At a position with no multi-word alternative that path takes only the first token stacked there (canine, emitted first) and asserts there is no second one.
  5. With assertions on, building the query throws AssertionError at IntervalBuilder.java:233; with them off (production) matches are silently lost, in every gap and order mode. WordDelimiterGraphFilter with KeywordRepeatFilter and a stemmer does the same with no synonyms at all.

Who is affected

#

Applications that build interval queries with Intervals.analyzedText or the flexible parser's fn: functions, with a query analyzer that mixes a multi-word synonym (or WordDelimiterGraphFilter catenation) with a stacked token elsewhere (a one-word synonym, or KeywordRepeatFilter and a stemmer). Every such query loses the stacked alternatives outside the multi-position token's span, at any index size; the index is fine.

Mechanism, terms and numbers586 words

Intervals.analyzedText turns analyzed text into an interval source. When no token spans more than one position, tokens stacked at one position (a single-word synonym, or a stem next to the original word) are ORed. As soon as one token spans two or more positions (a multi-word synonym, a WordDelimiterGraphFilter catenation), the whole text goes through IntervalBuilder.analyzeGraph, which, at every position without a multi-word alternative, keeps only the first finite string and asserts there is no second one. Stacked tokens of equal length are exactly such a position with several strings, so all but the first emitted token are dropped with assertions off, and AssertionError is thrown with assertions on. With wifi => wi fi and dog => canine, analyzedText("wifi dog") finds 2 of 4 documents and misses "wifi dog"; core QueryBuilder finds all 4. It is reached through both analyzedText overloads and the plain-term and quoted-text operands of the flexible StandardQueryParser fn: functions (not the patterns of fn:wildcard and fn:fuzzyTerm), in every release from 9.1.0 to 10.5.2 and on main. The index is not affected.

Terms

#
  • Stacked token: a token with position increment 0, at the same position as the token before it, for example canine on top of dog. Interval queries should treat stacked tokens as alternatives, or(canine, dog).
  • Token graph: a token stream in which some token spans more than one position (position length > 1), for example wifi spanning the two positions of wi fi. The paths through the graph are its finite strings: wi fi dog, wi fi canine, wifi dog, wifi canine.
  • Side path: GraphTokenStreamFiniteStrings.hasSidePath(state) is true when alternatives of different length start at a state (wifi versus wi fi). Equal-length stacked tokens (dog, canine) are not a side path: they leave the state together and arrive together.

The bug

#
  1. IntervalBuilder.analyzeText notes whether any token has position length > 1 (IntervalBuilder.java:95-98). If so, the whole text goes to analyzeGraph (:109-111) instead of analyzeSynonyms, which would OR the stacked tokens (:172-199).
  2. analyzeGraph (:201-237) walks the graph segment by segment. A segment with a side path becomes an OR of phrases, one per finite string (:215-228). Any other segment runs TokenStream ts = it.next(); once and then assert it.hasNext() == false; (:230-233).
  3. For wifi dog the last segment holds canine and dog: no side path, two finite strings (the diagram probe prints hasSidePath=false finiteStrings(in order)=["canine", "dog"]). Line 231 keeps canine, line 233 throws under -ea, and under -da dog is dropped. The built source is or(BLOCK(wi,fi,canine),BLOCK(wifi,canine)).
  4. Which token survives is the one the analyzer emits first: SynonymGraphFilter emits the synonym canine before the original dog, so the user's own word is the one lost.

Exposure and likelihood317 words
  • Entry points. Both Intervals.analyzedText overloads, and the plain-term and quoted-text operands of the flexible StandardQueryParser fn: functions (the grammar's IntervalText rule, StandardSyntaxParser.jj:681-686, then AnalyzedText.java:38); the patterns of fn:wildcard and fn:fuzzyTerm are not analyzed. Core QueryBuilder and the parsers built on it are not affected.
  • What it takes. In one query text, a token that spans several positions (a multi-word SynonymGraphFilter rule, or WordDelimiterGraphFilter catenation) and a token stacked at another position (a single-word synonym, or KeywordRepeatFilter with a stemmer). Mixed multi-word and single-word synonym lists are an ordinary query-time setup.
  • Opt-in. The intervals package is marked experimental, and both executed triggers need query-time filters configured on purpose (Lucene's ready-made analyzers were not checked one by one); the index side needs nothing special (default writer, codec and searcher).
  • Deterministic. Every such query text loses all but the first stacked token at each position that no multi-position token spans (stacked tokens inside such a span are kept), in every (maxGaps, ordered) mode and at any index size; it does not depend on the documents.
  • Silent in production. With assertions off nothing signals the loss; the lost token can be the word the user typed. With assertions on, building the query throws java.lang.AssertionError (through StandardQueryParser it reaches the caller as that Error, not as a QueryNodeException).
  • Negation flips it. A MUST_NOT clause or the subtrahend of fn:notWithin built this way returns documents it should exclude, including the one with exactly the excluded words (executed). Rated not a security issue: the dropped token is fixed by the query text and the analyzer, so index contents play no part (documents matter only if an application builds its query text from them).
  • Downstream (code reading only, not executed). Solr's {!intervals} parser, merged in 2026 and not yet released, calls Intervals.analyzedText. Elasticsearch and OpenSearch carry their own copies of the same branch; a Lucene fix does not change those copies.

Why it is a bug, not intended

#
  • The code's own assert it.hasNext() == false (IntervalBuilder.java:233) fails on stock filters through public API.
  • Without a multi-word token the same class keeps or(canine,dog), and core QueryBuilder.createPhraseQuery keeps both on the same graph (4 of 4).
  • Core's graph test has asserted since 2017 that such a segment has two finite strings (testGraphWithRegularSynonym).
The full argument222 words
  • Javadoc. analyzedText "Returns intervals that correspond to tokens from a TokenStream returned for text by applying the provided Analyzer" (Intervals.java:601-603). A stacked token is a token of that stream.
  • The class itself. analyzeSynonyms ORs stacked tokens (IntervalBuilder.java:172-199), and the side-path branch ORs every finite string (:215-228). Whether dog is honoured should not depend on an unrelated word having a multi-word synonym.
  • Core parity. Core QueryBuilder keeps stacked tokens on the same graph. The executed control, createPhraseQuery, goes through analyzeGraphPhrase, one phrase per finite string (QueryBuilder.java:340-343, :566-583); by code reading, analyzeGraphBoolean walks the same segments and keeps every stacked term of a segment without a side path through graph.getTerms(start) (:540-556).
  • Core test. TestGraphTokenStreamFiniteStrings#testGraphWithRegularSynonym (fast|speedy wi|wifi fi network) asserts hasSidePath(0) == false and then the two finite strings fast and speedy (:467-473), since LUCENE-7638 (2017): the input the interval builder asserts away.
  • Upstream interval tests stack tokens only inside side paths (TestIntervalBuilder#testGraphSynonyms*, testGraphTerminatesOnGap), which is why it stayed hidden; testSimpleSynonyms* assert the OR on the non-graph path.
  • History. The branch came with the method (LUCENE-10220, #427, 2021) and has not changed since; the introducing issue and PR never discuss graphs or synonyms, and no CHANGES, MIGRATE or javadoc text says stacked tokens are dropped.
The devil's-advocate check140 words

Strongest case for "intended": the intervals package is experimental; the javadoc never spells out synonym semantics; SynonymGraphFilter's javadoc says that fully correct positional queries over multi-token synonyms need a TermAutomatonQuery; the code was ported as-is from another engine that still has it; maybe the assert was valid when written.

Why it fails: the TermAutomatonQuery note is about multi-token replacements, while the token dropped here is a single-position one, often the user's own word; the class and core QueryBuilder keep stacked tokens on every other path; hasSidePath has meant "different length" since 2017, so the assert was never valid; and an AssertionError on stock filters through public API is not a design decision. Every checker concluded "not intended". One honest caveat: the miss with assertions off rests on this implicit contract, while the AssertionError with assertions on is unambiguous.

Suggested fix

#

Recommended OR the terms of every finite string of a segment without a side path

In the graph path's branch for segments without a side path, OR the terms of every finite string instead of taking the first one (+11/-3 in IntervalBuilder.java). It passes the new tests, all 120 interval tests, the whole queries module (515 tests) and the highlighter and parser suites that use analyzedText.

Trade-offs

  • No maxClauseCount check, unlike the side-path branch (IntervalBuilder.java:221); the non-graph path has none either, and the number of alternatives is the number of tokens the analyzer emitted at that position.
  • synonyms.size() == 1 is only a shortcut: Intervals.or of one source returns that source. The OR order does not matter, since disjunction equality is set-based.
  • It relies on each finite string of a no-side-path segment being a single token (the code comment says so and every tested graph agrees, but getFiniteStrings does not document it); if that changed, addAll would turn a phrase into an OR of its words. The PR can assert one term per finite string, or use option B.
  • Not reviewed by a committer.

How it was found

#

While writing an independent reference semantics for query token graphs, the hunting AI tool suspected the no-side-path branch by reading it. A bounded-exhaustive harness then compared analyzedText with that reference over 24.9 million checks on stock main: apart from known repeated-term behaviours, every failure combined a multi-word token with a stacked one, and that class vanishes with the fix.

The method in full190 words

Method: bounded-exhaustive translation validation (a hunt unit, 2026-10-26, main ea57360912ed). No model checker, SMT solver or prover was involved.

  • The finder (an AI tool) wrote an independent reference semantics for query token graphs: segments with alternatives, holes and multi-position side paths, and when a document matches in each (maxGaps, ordered) mode. While writing it, it suspected the defect by reading IntervalBuilder.analyzeGraph.
  • The harness (AtTV.java, public API only) compared every 1- and 2-segment query from a pool of 68 segments against every document of 1 to 4 positions over {a, b, c, d, z} in 6 modes: 24,882,731 checks on stock main with assertions off, plus 315,197,137 in larger runs on separate build machines. The failure category "graph plus stacked token" is this bug; with the fix shadowed it is 0 (208,009,964 checks).
  • Vacuity check: three deliberately broken copies of IntervalBuilder (ignore holes, keep only the first synonym on the non-graph path, unordered side paths) were each caught in their own category.
  • Then a public-API JUnit, a parser reachability probe, independent verifiers, an adjudication, a release sweep, a prior-report search and a security screen (see Independent checks).

Bug record

LFV-457, snapshot of 2026-10-28

Registry title
Intervals.analyzedText keeps only the first of the tokens stacked at a position whenever the analyzed text is a token graph (a multi-word synonym or a WordDelimiterGraphFilter catenation elsewhere in the text), so interval queries silently miss documents, even documents with exactly the query words (AssertionError under -ea)
Area
queries / intervals (Intervals.analyzedText: IntervalBuilder.analyzeGraph; flexible StandardQueryParser fn: interval functions)
Priority
Medium, rank 43: Intervals.analyzedText and the flexible parser's fn: functions have deterministically dropped stacked synonyms on token-graph text since 9.1, but Elasticsearch and OpenSearch use their own copies.
Impact class
silent wrong results
Impact note
Applications that build interval queries from analyzed text, through Intervals.analyzedText (both overloads), through every term or quoted argument of the flexible StandardQueryParser fn: interval functions, or (by code reading only) through Solr's still unreleased {!intervals} match rule, with a query-time analyzer that both builds a token graph (a multi-word SynonymGraphFilter rule, or WordDelimiterGraphFilter catenation) and stacks tokens at another position (a single-word synonym, or KeywordRepeatFilter with a stemmer), silently lose matches: every stacked alternative except the first one emitted is dropped, which can be the query's own word, in every (maxGaps, ordered) mode, at any index size, with the default writer, codec and searcher, with -da in every release from 9.1.0 through 10.5.2 and on main; with -ea building the query throws AssertionError instead; the index is not affected.
Summary
You build an interval query with Intervals.analyzedText("wifi dog", analyzer, "f", 0, true) (or the flexible StandardQueryParser's fn:or("wifi dog")), where the query analyzer's SynonymGraphFilter has the rules wifi => 'wi fi' and dog => canine. You expect it to match 'wifi dog', 'wifi canine', 'wi fi dog' and 'wi fi canine', as QueryBuilder's phrase query with the same analyzer does and as analyzedText("dog") alone does with or(canine,dog). Instead, because 'wifi' has a two-position synonym, the builder keeps only the first token stacked at the 'dog' position, builds or(BLOCK(wi,fi,canine),BLOCK(wifi,canine)) and misses the two 'dog' documents, including the one that holds exactly the query text; with assertions enabled it throws AssertionError.
