The Lucene90NormsFormat javadoc gives a wrong .nvm Entry grammar: two fields written since 8.0 are missing

The javadoc of the default norms format omits two values (an Int16 and a byte) that every .nvm Entry has stored after DocsWithFieldLength since 8.0. A parser that follows it reads NumDocsWithField as 67108863 instead of 3; Lucene itself is unaffected.

The finding in 30 seconds

#

The .nvm grammar in the class javadoc is missing two fields that the writer has stored after DocsWithFieldLength since 8.0, so the documented Entry is 3 bytes short and the first value read wrong is NumDocsWithField.

What you need to know first

#
  1. Norms are one small number per document and field that scoring uses (by default computed from the field's length). Each segment keeps them in two files: .nvd holds the values, and .nvm holds one Entry per field saying which documents have a norm, how many, and where the values are.
  2. When only some documents have a norm, the set of those documents is written with IndexedDISI (already in 7.x). Since 8.0 (LUCENE-8585) that set also carries lookup tables (a jump table and a rank index) for fast access, and reading it back needs two more numbers: the jump-table entry count and the dense rank power.
  3. Each codec format documents its files in its class javadoc as a typed grammar, and the default codec's overview sends readers there for the details.

The finding, step by step

#
  1. You write your own reader for the norms metadata file (.nvm) from the Lucene90NormsFormat javadoc. It says each field's Entry is FieldNumber (Int32), DocsWithFieldAddress (Int64), DocsWithFieldLength (Int64), NumDocsWithField (Int32), BytesPerNorm (byte), NormsAddress (Int64).
  2. You index 3 documents with one text field (default codec) and read the first Entry of _0.nvm: FieldNumber 0, then the two Int64 values. You expect NumDocsWithField = 3, since every document has a norm.
  3. You get 67108863. Right after DocsWithFieldLength the writer stores two values the javadoc does not list: the jump-table entry count (Int16, here -1 = FF FF) and the dense rank power (byte, -1 = FF). Your Int32 reads FF FF FF 03 = 0x03FFFFFF.
  4. Every later value is 3 bytes off, in every Entry of every .nvm file. Lucene's own reader reads the two values and is unaffected: only the javadoc is wrong, since LUCENE-8585 added the fields in 8.0.0 (2019). The grammar line also calls the file .dvm.

Who is affected

#

People who read or re-implement .nvm from the javadoc: ports, index inspection or recovery tools, format write-ups. For them the first Entry of every .nvm file the default codec writes goes wrong (any index with a normed field, such as a TextField). Lucene's own indexing, merging and search are unaffected. Priority Low.

Mechanism, terms and numbers545 words

Lucene90NormsFormat is the norms format of every default codec since 9.0. Its class javadoc documents the norms metadata file (.nvm) as a typed grammar: each field's Entry is FieldNumber (Int32), DocsWithFieldAddress (Int64), DocsWithFieldLength (Int64), NumDocsWithField (Int32), BytesPerNorm (byte), NormsAddress (Int64). Since the jump tables of LUCENE-8585 (8.0.0, 2019) the writer also stores the jump-table entry count (Int16) and the dense rank power (byte) right after DocsWithFieldLength, in every Entry, and the reader reads them there. A parser written from the javadoc therefore reads NumDocsWithField from the wrong bytes (67108863 instead of 3 for a 3-document segment) and every later value 3 bytes off. The grammar line also labels the file .dvm, the doc-values extension, and the notes call BytesPerNorm "BytesPerValue". It is a documentation defect: Lucene's writer and reader agree, so nothing goes wrong at runtime; the fix is javadoc only.

The javadoc on main 645d4fe14a20 (Lucene90NormsFormat.java)

The notes below it (:59-67) give the sentinels (FieldNumber -1 ends the metadata; DocsWithFieldAddress -2 when no document and -1 when every document has a norm) and call the bytes-per-norm element BytesPerValue (:61-62, and :76 in the .nvd grammar). The file extension is nvm (METADATA_EXTENSION, :103); .dvm is the doc-values metadata file.

What the writer writes (Lucene90NormsConsumer.addNormsField)

#
  • :100 meta.writeInt(field.number).
  • In each of the three branches (no document has a norm :102-106, every document has one :107-111, some do :112-121; the first was only read, no run exercised it): writeLong(docsWithFieldOffset), writeLong(docsWithFieldLength), writeShort(jumpTableEntryCount), writeByte(denseRankPower). In the first two branches both are -1 (:105-106, :110-111); in the sparse branch they are the count IndexedDISI.writeBitSet returns and IndexedDISI.DEFAULT_DENSE_RANK_POWER = 9 (:116-120).
  • :123 writeInt(numDocsWithValue), :126 writeByte(numBytesPerValue), :128/:130 the single value or the norms offset. close() writes the -1 end marker and the footer (:70-71).

The reader (Lucene90NormsProducer.readFields, :212-240) reads readLong, readLong, readShort (:223), readByte (:224), readInt (:225), readByte (:226), readLong (:238): the writer's order. Because all three branches write the two values, every Entry is 3 bytes longer than documented.

Exposure and likelihood169 words
  • Who. Only people who decode .nvm themselves from this javadoc. Lucene's own code never consults it.
  • Default codec. Codec.getDefault() is Lucene104 (Codec.java:59), which uses Lucene90NormsFormat (Lucene104Codec.java:76); the codec overview links this class as the norms format (package-info.java:165, :283) and says "Details on each of these are provided in their linked pages" (:188). So the wrong grammar is the documented format of every index written since 9.0.0 that has a field with norms.
  • What they get. A wrong NumDocsWithField in the first Entry, then garbage for every later value. The misread count is usually absurd (67,108,863 for a 3-document segment), so it costs debugging time rather than silently corrupting anything.
  • What nobody gets. Any runtime effect: writer and reader agree, and the upstream TestLucene90NormsFormat round trip passes.
  • Scale and priority. Every release from 8.0.0 (March 2019) to 10.6.0 and main; nobody has reported it in more than seven and a half years, which fits the small audience. Impact minor, priority Low.

Why it looks unintended

#
  • The javadoc is an exact grammar: fixed order, a typed DataOutput link per element, sentinel values; the codec overview sends readers to it for details.
  • The same Entry text matched the Lucene70 writer exactly; LUCENE-8585 (2019) added the two writes and kept the old text.
  • Upstream has fixed such format-doc drift as bugs before (LUCENE-349, LUCENE-713, LUCENE-3072).
The full argument283 words
  • An exact byte grammar. The class lists the elements in order, gives each a fixed type with a link to the DataOutput method that writes it, and gives sentinel values (Lucene90NormsFormat.java:46-67). Nothing marks it as approximate; package-info.java:188 sends readers to it for the details.
  • It used to be exact, and was kept in step with the writer. LUCENE-7475 (9128bdbaf54, 2016) wrote the Lucene70 Entry with five elements; LUCENE-7485 (2fbbcac580f, 2016) added DocsWithFieldLength to the writer and, in the same commit, to the Entry, giving today's text. It matched that writer; the study's probe parses 7.5.0, 7.7.0 and 7.7.3 files exactly with it.
  • An oversight in a copy. LUCENE-8585 (c13645bd4c6, 2019) added the two writes and created Lucene80NormsFormat from the Lucene70 javadoc, changing only the title, the codec names and the .nvd DocsWithFieldData link; it also added prose about jump tables to the lucene80 package doc. LUCENE-9705 (4d7b2aebfe0, 2021) copied the text verbatim into Lucene90NormsFormat. No comment on #9631 or on the PR review (apache/lucene-solr#525) mentions the norms grammar.
  • Upstream wants the current codec documented well. On that PR a reviewer (jpountz) wrote "Only the current codec needs to have a good description if its file formats". Upstream has fixed this kind of drift as bugs: LUCENE-349 (#1427, docs that "leave out several fields that are read from the file"), LUCENE-713 (#1788), LUCENE-3072 (#4145, "fileformats out of date"). The closest precedent is LUCENE-9353: it moved the terms metadata to a new .tmd file without touching the grammar (#1473, 2020), and about ten months later a separate commit under the same issue revised the terms-dictionary format documentation to match (5f5d1949e92, #90, 2021).
The devil's-advocate check153 words

The case for "intended" (rated moderate by reviewers): the codec format classes are @lucene.experimental (Lucene90NormsFormat.java:81); the overview says it "attempts to provide a high-level definition of the Apache Lucene file formats" (package-info.java:54, the LUCENE-2946 policy that moved the docs away from bit-for-bit detail); the supported way to read norms is the codec's own NormsProducer; and the round trip is tested. So nobody should parse .nvm by hand.

Why it fails: this class does not give a high-level description, it gives a typed, ordered grammar, and a precise grammar that is wrong is worse than none. In the LUCENE-2946 thread rmuir said detail is "fine (for now)" for "the simple metadata files", which .nvm is. @lucene.experimental is about API stability, not about whether the docs are true, and the Lucene70 version of this very text was exact. At most the argument makes the fix low priority, which it is.

Suggested fix

#

Recommended Correct the .nvm grammar in the Lucene90NormsFormat javadoc (validated)

Javadoc only, one file (+8/-4): add JumpTableEntryCount (Int16) and DenseRankPower (byte) after DocsWithFieldLength, note that both are -1 when no or all documents have a norm, label the file .nvm, and say BytesPerNorm throughout. Validated with gradle: the corrected grammar parses the file to the footer, the norms format tests pass, and javadoc, format and lint checks pass.

Downstream note

#

Products built on Lucene read norms through the codec and are unaffected; only tools that parse .nvm themselves from this javadoc misread it.

How it was found

#

A semi-formal differential check. Each default-codec file grammar was written down twice, from the class javadoc and from the writer, and one interpreter parsed the bytes of 64 generated indexes with both. The writer grammar parsed every file to the footer; under the javadoc grammar all 112 .nvm files diverged at NumDocsWithField.

The method in full124 words
  • Hunt. The grammars are data in a small grammar language; the interpreter compares every parsed value with Lucene's own reader. 64 index configurations (4 fixed and 60 seeded random), 1,114 file checks, assertions on and off.
  • Controls. The writer grammar parses every file exactly to the footer (0 failures). Each of 14 single-element mutants of the writer grammar is detected, including dropping the .nvm JumpTableEntryCount or DenseRankPower, so the check is not vacuous.
  • Result for .nvm. 112 of 112 files diverge under the javadoc grammar, always first at Entry NumDocsWithField; the same unit found the sibling file-format javadoc defects of .fnm, .si, segments_N, the terms dictionary and the vector formats.
  • Minimized to the one-test repro of the Minimal repro section.

LFV-938, snapshot of 2026-11-09

Registry title
The file-format javadoc of the default norms format (Lucene90NormsFormat) gives a wrong .nvm grammar: each Entry omits the Int16 jump-table entry count and the byte dense rank power that the writer stores right after DocsWithFieldLength, so a parser that follows it misreads NumDocsWithField and every later field; the grammar line is also labelled '.dvm' (documentation defect; the writer and reader agree)
Area
codecs / norms (Lucene90NormsFormat .nvm file-format javadoc vs Lucene90NormsConsumer / Lucene90NormsProducer)
Priority
Low, rank 1332: The default norms .nvm grammar is wrong, a documentation-only defect, and norms exist for most text fields.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so indexing, merging, CheckIndex, scoring and search are unaffected in every configuration; the people misled are those who read, inspect or re-implement the .nvm format from this class javadoc (the default codec's package docs link it as the Norms format), and a parser that follows the text misreads NumDocsWithField in the first entry of every .nvm file the default codec writes and then every later field (executed); the Entry has been wrong in every release since 8.0.0 (2019), and no scale or special setting is needed.
Summary
You decode the norms metadata (.nvm) file of the default codec by following the Lucene90NormsFormat javadoc, which says each Entry is FieldNumber (Int32), DocsWithFieldAddress (Int64), DocsWithFieldLength (Int64), NumDocsWithField (Int32), BytesPerNorm (byte), NormsAddress (Int64). Since the jump tables of Lucene 8.0 the writer stores two more fields right after DocsWithFieldLength, an Int16 jump-table entry count and a byte dense rank power, so a parser built from the text reads NumDocsWithField as 67108863 instead of 3 (the bytes FF FF and FF of the two missing fields plus the first byte of the real count) and every later field is shifted. Lucene's own reader matches the writer, so nothing breaks at runtime; only the documentation is wrong (it also labels the file '.dvm', the doc-values extension).
