The finding in 30 seconds

#

The HNSW vectors formats can merge a segment's vector graph with several threads: you pass a worker count and an ExecutorService to the format's constructor. The constructor checks the other graph settings, but not that the worker count is at least 1.

Background: concurrent HNSW merging

#
  1. Each segment of a kNN vector field holds an HNSW graph. A merge combines segments, so it builds or joins their graphs into one.
  2. By default one thread does that. Lucene99HnswVectorsFormat(maxConn, beamWidth, numMergeWorkers, mergeExec) lets the merge use numMergeWorkers threads from your own ExecutorService (since 9.9.0).
  3. Since 10.4.0, merges too small to need a graph skip it (tinySegmentsThreshold, default 100); the repro sets it to 0 so two vectors suffice.

The finding, step by step

#
  1. Configure concurrent HNSW merging with 0 workers and a thread pool: new Lucene99HnswVectorsFormat(16, 100, 0, executor, 0). The last 0 (tinySegmentsThreshold) makes even a one-vector segment get a graph. The constructor accepts it.
  2. Index two documents with one 2-dimensional vector each, committing after each (two segments), and call forceMerge(1).
  3. You expect an IllegalArgumentException from the constructor, as for maxConn 0 or for 1 worker with a pool, or a working merge, which is what 0 workers without a pool gives on 10.2.0 and later.
  4. You get ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 from the merge, and the writer closes itself, losing its uncommitted changes. -1 workers gives NegativeArraySizeException. With the default 4-argument constructor a merge of two 1000-vector segments fails the same way.
  5. Why: with a pool, the writer always picks the concurrent merger, which makes an array of numMergeWorkers workers and reads worker 0. With 0 workers the array is empty.

Who is affected

#

Only applications that hand-configure concurrent HNSW merging and end up with a count below 1 while passing a thread pool, for example availableProcessors() / 2 on a one-CPU machine. The default codec (1 worker, no pool) is safe. The writer closes at its first graph-building merge and loses uncommitted changes; the last commit stays intact.

Mechanism, terms and numbers572 words

Lucene99HnswVectorsFormat(maxConn, beamWidth, numMergeWorkers, mergeExec) lets an application merge HNSW graphs with several threads from its own ExecutorService. The constructor rejects maxConn and beamWidth outside their range and one worker together with an executor, but stores any numMergeWorkers <= 0. With a non-null executor the writer sends every graph-building merge to ConcurrentHnswMerger without looking at the count, and HnswConcurrentMergeBuilder sizes its worker array by it: for 0 the first read of workers[0] throws ArrayIndexOutOfBoundsException, for -1 the allocation throws NegativeArraySizeException. IndexWriter.merge treats that as a tragic event, so the writer closes and loses its uncommitted changes; every new writer with that setting fails the same way at its first such merge. Lucene104HnswScalarQuantizedVectorsFormat, HnswBitVectorsFormat and, since 10.6.0, the sandbox's DedupHnswVectorsFormat and DedupHnswScalarQuantizedVectorsFormat copy the same partial check. The same 0 without an executor merges serially on 10.2.0 and later. Opt-in and loud: the default codec (1 worker, no executor) is not affected, the last commit stays intact and CheckIndex is clean. Every release from 9.9.0 to 10.6.0 and main.

Terms

#
  • Vectors format: the codec component that writes a field's kNN vectors and its HNSW graph. Lucene99HnswVectorsFormat is the default one; Lucene104HnswScalarQuantizedVectorsFormat (core), HnswBitVectorsFormat (lucene/codecs) and the sandbox's DedupHnswVectorsFormat and DedupHnswScalarQuantizedVectorsFormat (since 10.6.0) take the same merge arguments.
  • numMergeWorkers, mergeExec: "number of workers (threads) that will be used when doing merge" and the ExecutorService they run on (Lucene99HnswVectorsFormat.java:215-219). The default constructor uses 1 worker and no executor (:120, :177-185).
  • Tragic event: an unexpected exception inside IndexWriter that makes it roll back to the last commit and close itself; later calls throw AlreadyClosedException.

The mechanism (main 645d4fe14a20)

#
  1. No lower bound. The constructor rejects maxConn and beamWidth outside their range ("must be positive ...", Lucene99HnswVectorsFormat.java:271-284) and numMergeWorkers == 1 && mergeExec != null (:289-292), then stores the count as is (:293). 0 and -1 pass. Lucene104HnswScalarQuantizedVectorsFormat.java:181, HnswBitVectorsFormat.java:125, DedupHnswVectorsFormat.java:185 and DedupHnswScalarQuantizedVectorsFormat.java:201 have the same check; both Dedup formats fail the same way (executed on main and 10.6.0).
  2. The executor decides the merger, not the count. Lucene99HnswVectorsWriter.createGraphMerger returns a ConcurrentHnswMerger with the format's count whenever mergeExec != null (Lucene99HnswVectorsWriter.java:674-676). Only the other path, the merge scheduler's intra-merge executor, is guarded by > 1 (:678); otherwise the merge is serial (:688).
  3. An array of 0 workers. HnswConcurrentMergeBuilder does workers = new ConcurrentMergeWorker[numWorker] (HnswConcurrentMergeBuilder.java:153). For -1 that throws NegativeArraySizeException; for 0 the array is empty.
  4. Worker 0 is read. Joining the segments' graphs goes through runInBatches, whose first statement reads workers[0].batchSize (:374-375): ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0. Without graphs to join, finish() reads workers[0] (:478) and fails the same way; that is the site on 10.4.0-10.6.0.
  5. The writer closes. IndexWriter.merge catches any Throwable and calls tragicEvent(t, "merge") (IndexWriter.java:5109-5113).

The numbers

#

Two committed segments of one 2-dimensional vector each, tinySegmentsThreshold 0, SerialMergeScheduler, forceMerge(1), on main (the diagram probe and the fact check's probe): (0, executor) throws ArrayIndexOutOfBoundsException, (-1, executor) throws NegativeArraySizeException, and after either the writer is closed (isOpen() == false, the merge exception as its tragic exception); (0, null) and (2, executor) merge fine. With the default 4-argument constructor, two 1000-vector segments fail the same way (the independent reproduction, the diagram probe) and two 20-vector segments build no graph and merge.

Exposure and likelihood302 words
  • Who is exposed. Code that builds one of the five formats with an explicit numMergeWorkers and an ExecutorService, and computes or forwards the count: availableProcessors() / 2 on a one-CPU container gives 0, or a 0 / -1 "auto" default is passed through while an executor is always supplied. On 9.11.0-10.1.x even (0, null) fails, through the merge scheduler's intra-merge executor.
  • Opt-in. The default codec builds new Lucene99HnswVectorsFormat(): 1 worker, no executor (Lucene104Codec.java:123). All five formats are @lucene.experimental.
  • Effect. Loud and immediate: the first graph-building merge throws and the writer closes as a tragic event, losing its uncommitted changes. In the security probe forceMerge(1) threw 31-232 ms after it was called, with 600 committed documents kept and 50 uncommitted ones lost; with ConcurrentMergeScheduler the indexing thread saw the error within 0.6 s of starting to index, as "this writer hit an unrecoverable error" or AlreadyClosedException. Every new writer with that setting fails the same way at its first such merge. The minimal repro commits both documents first, so it shows the crash and the closed writer, not a loss.
  • Not affected. The last commit stays intact and CheckIndex is clean; a valid setting merges the same index afterwards; other writers on the same executor are unaffected; the probe observed no hang, no resource growth and no wrong search results.
  • Scale. None: two one-vector segments with threshold 0, or, with the default constructor (tinySegmentsThreshold 100), any merge large enough to build a graph: a merge of n vectors builds one when n > (int) (100 * ln n), from 648 vectors on (Lucene99HnswVectorsWriter.java:453, :712-722). Two 1000-vector segments fail; a 40-vector merge builds no graph and passes.
  • Likelihood: rare. Nobody sets 0 workers on purpose, and no report was found in the documented searches.

Why it looks unintended

#
  • The javadoc calls it the "number of workers (threads)" for the merge, with no lower bound and no exception.
  • The same constructor rejects maxConn or beamWidth below 1 and 1 worker with a pool; ConcurrentMergeScheduler rejects thread counts below 1.
  • Without a pool the same 0 merges serially (10.2.0+); with one, the writer closes.
The full argument214 words
  • The contract. @param numMergeWorkers number of workers (threads) that will be used when doing merge (Lucene99HnswVectorsFormat.java:215-216, :232-233, :254-255; the same in the other four formats). No range, no @throws; no javadoc, CHANGES or MIGRATE entry gives 0 or a negative count a meaning.
  • Validation is the constructor's style. maxConn and beamWidth "must be positive" (:271-284) and (1, executor) is rejected (:289-292); TestLucene99HnswVectorsFormat.testLimits asserts these (:64-74), and so does the quantized format's (TestLucene104HnswScalarQuantizedVectorsFormat.java:273-295); the bit format's testLimits checks only maxConn and beamWidth (TestHnswBitVectorsFormat.java:117-124).
  • Thread counts below 1 are rejected elsewhere: "maxThreadCount should be at least 1" (ConcurrentMergeScheduler.java:145-146).
  • Inconsistent. (0, null) merges serially on 10.2.0+ (the > 1 guard, Lucene99HnswVectorsWriter.java:678, from #14331); open PR #16871 also reads numMergeWorkers <= 1 as serial.
  • Out of proportion. An accepted constructor argument fails later, at an unrelated merge, as an internal array exception that closes the writer.
  • History. The worker array and the partial check came together in #12660 (9.9.0); no review of #12660, #13124/#13190 or #14331 discusses counts below 1. One upstream test passes 0 with a null executor as a placeholder (backward-codecs TestLucene99HnswQuantizedVectorsFormat.testLimits, five calls that never merge), so do not claim that no test passes 0.
The devil's-advocate check297 words

Strongest case (refute review, the cross-model review, the intended-behaviour check, adjudication): 0 or -1 worker threads is nonsense input to an @lucene.experimental expert API; two committers said the count should not be a user setting at all (benwtrent in a #13124 PR discussion comment, 2024-02-23; mikemccand on luceneutil #507, 2026); and the 5-argument constructor the repro uses is labelled "(This is a Test-Only Constructor)".

Why it fails: the constructors are public, and the 4-argument one, not test-only, fails the same way on a 2000-vector merge; the constructor already validates its neighbouring arguments; the value works without an executor; and the failure closes the writer late instead of raising an argument error at configuration time. If maintainers prefer to remove the knob, that resolves the report too. Verdict: not intended, a small missing-validation defect; no checker before the cross-model fact check rated the intended-behaviour argument better than weak; that check rated it moderate.

No-noise check. The hunt does not claim behaviour that needs absurd parameters and then fails loudly. For noise: 0 or -1 worker threads is nonsensical, and the failure is loud. Why it is still claimed, as a low-priority missing-validation bug only: 0 is an accepted value of this constructor (with a null executor it merges serially on 10.2.0+), so adding an executor turns an accepted value into a crash; a 0 comes from ordinary computed settings such as availableProcessors() / 2 on a one-CPU container; and the failure is late and destructive (at the first graph-building merge, closing the writer and dropping uncommitted documents), not an argument error at configuration time where the neighbouring arguments are checked. The cross-model fact check (OpenAI GPT-5.6) judged it "claim-low, not noise", if filed as a narrow missing-validation hardening bug, not as corruption, security or broad availability impact.

Suggested fix

#

Recommended A: reject a count below 1 when an executor is passed

Reject a count below 1 when an executor is passed, in all five formats' constructors (5 lines each). The repro then passes, and so do the format, HNSW and sandbox Dedup test suites. Alternative: merge serially in createGraphMerger when the count is not above 1 (one line).

if (numMergeWorkers < 1 && mergeExec != null) {
  throw new IllegalArgumentException(
      "numMergeWorkers must be at least 1 when a merge executor is passed; numMergeWorkers="
          + numMergeWorkers);
}
if (numMergeWorkers == 1 && mergeExec != null) { // existing check, unchanged

LFV-589, snapshot of 2026-11-02

Registry title
The HNSW vectors formats (Lucene99HnswVectorsFormat, Lucene104HnswScalarQuantizedVectorsFormat, HnswBitVectorsFormat and, since 10.6.0, the sandbox DedupHnswVectorsFormat and DedupHnswScalarQuantizedVectorsFormat) accept numMergeWorkers <= 0 together with a merge ExecutorService, and then every merge that builds an HNSW graph throws ArrayIndexOutOfBoundsException (0 workers) or NegativeArraySizeException (negative) and closes the IndexWriter as a tragic event (since 9.9.0)
Area
codecs / HNSW vectors formats (constructor parameter validation; concurrent HNSW merge)
Priority
Low, rank 617: The core HNSW formats accept numMergeWorkers <= 0 together with an executor, and every graph merge then closes the writer, which is loud and needs a degenerate computed setting but sits in core formats, so it heads the accepted-setting crash rows ahead of LFV-166 and LFV-226.
Impact class
crash
Impact note
Only applications that build their codec with an HNSW vectors format given numMergeWorkers <= 0 and a non-null merge ExecutorService (the default is 1 worker and no executor; on 9.11.0-10.1.x 0 workers without an executor fails too) are hit: construction, indexing and flushing succeed, but the first merge that builds a graph (from 10.4.0, with the default tinySegmentsThreshold of 100, only a merge of n vectors with n > (int) (100 * ln n), that is from 648 vectors on) throws within milliseconds and the IndexWriter closes as a tragic event, losing its uncommitted changes, and every new writer with that setting fails the same way; -ea and -da, no scale needed; no hang was observed, the last commit stays intact (CheckIndex clean) and a valid setting merges the same index afterwards.
Summary
You build a codec with, for example, new Lucene99HnswVectorsFormat(16, 100, 0, executor), that is zero merge workers plus a merge executor. The constructor already rejects maxConn or beamWidth <= 0 and one worker with an executor, so you expect it to reject 0 as well (or to merge serially, as it does without an executor). Instead it accepts the value, indexing works, and the first merge that builds an HNSW graph throws ArrayIndexOutOfBoundsException (NegativeArraySizeException for -1) inside HnswConcurrentMergeBuilder, whose worker array is sized by that count, and the IndexWriter closes itself with that exception.
