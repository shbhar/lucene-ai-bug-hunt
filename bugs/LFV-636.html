DrillSideways with an ExecutorService wraps failures of its searches in RuntimeException(ExecutionException), unlike the sequential mode

With an ExecutorService, DrillSideways reports any failure inside its searches (the clause limit, a query timeout, the declared IOException) as RuntimeException -> ExecutionException -> the real exception, while the sequential mode throws the real one, so catch blocks for those types are skipped. Opt-in; 6.4.0 to 10.6.0 and main.

The finding in 30 seconds

#

DrillSideways computes facet counts for a drill-down query plus "sideways" counts for each drilled dimension. It runs those searches one after another on your thread, or in parallel on an ExecutorService that you pass to its constructor.

Background: drill sideways and Java futures

#
  1. A drill-down query narrows the hits, say to color = red. Drill sideways also counts the other colors as if red were not selected, so the user can switch: one extra search per drilled dimension.
  2. new DrillSideways(searcher, config, state) runs these searches one after another on your thread. The 5-argument constructor with an ExecutorService runs them as parallel tasks.
  3. In Java, when a task on an executor throws, Future.get() throws an ExecutionException whose cause is the task's exception. Code that collects the results has to unwrap it; IndexSearcher has done so since 9.8.0.

The finding, step by step

#
  1. Your application runs faceted search with DrillSideways and catches IndexSearcher.TooManyClauses to answer "query too large". A user's drill-down query has a base query with 1,026 term clauses; the default limit is 1,024.
  2. Without an executor, search(query, 10) throws IndexSearcher$TooManyClauses: maxClauseCount is set to 1024, and your catch block handles it.
  3. You pass an ExecutorService to the constructor so that the drill-down and drill-sideways searches run in parallel. You expect the same exception: the javadoc presents the two modes as alternatives that differ in speed and duplicate work.
  4. Instead you get RuntimeException: ExecutionException: TooManyClauses, two levels deep, and your catch block is skipped. A fired ExitableDirectoryReader timeout, an IOException and an Error arrive wrapped the same way.
  5. Why: the concurrent path reads each task's Future and turns any task failure into throw new RuntimeException(e) around the ExecutionException. The search still fails and returns nothing; in every tested case only the exception's type differs.

Who is affected

#

Applications that pass an ExecutorService to DrillSideways (opt-in; the default constructors are sequential) and catch TooManyClauses, ExitingReaderException, IOException or Error by type, for example to answer "query too large" or "timed out". No wrong results: the search still fails, with the real exception two causes down.

Mechanism, terms and numbers601 words

DrillSideways runs a drill-down search plus one drill-sideways search per drilled dimension, either one after another on the caller's thread or, when an ExecutorService is passed to its 5-argument constructor, as parallel tasks. In the parallel mode, searchConcurrently collects the tasks with Future.get and turns any task failure into throw new RuntimeException(e) around the ExecutionException. So the caller gets RuntimeException -> ExecutionException -> the original exception, where the sequential mode throws the original itself: the clause limit (IndexSearcher$TooManyClauses), a fired ExitableDirectoryReader timeout, the IOException every search overload declares, or an Error. Handlers that catch those types do not fire. The search still fails and returns nothing, and the original exception with its message stays in the cause chain. IndexSearcher stopped wrapping the same way in 9.8.0 (#12516) to make sequential and concurrent exceptions the same, and the facet module's other concurrent code already rethrows the cause. Opt-in mode of an @lucene.experimental class; every release from 6.4.0 to 10.6.0 and main.

Terms

#
  • Drill down / drill sideways: a DrillDownQuery is a base query plus one filter per drilled dimension. DrillSideways returns its hits and facet counts, and for each drilled dimension the counts computed without that dimension's filter (the "sideways" counts).
  • Sequential and concurrent mode: the 3- and 4-argument constructors pass no executor (DrillSideways.java:89-112); the 5-argument one takes an ExecutorService ("Use this constructor to use the concurrent implementation", :114-125). The class javadoc presents the two as alternatives that differ in speed and duplicate work (:57-64).

The mechanism (main 645d4fe14a20)

#
  1. The executor picks the path. Every search overload is declared throws IOException and ends in if (executor != null) searchConcurrently(...) else searchSequentially(...) (DrillSideways.java:352-355, :424-428).
  2. Sequential. searchSequentially (:441-481) runs one DrillSidewaysQuery with searcher.search(...) on the caller's thread (:467); a failure propagates as thrown.
  3. Concurrent. searchConcurrently (:483-522, no throws clause) wraps each search in a CallableCollector whose call() is searcher.search(query, collectorManager) (:302-310), submits the drill-down task (:506), runs the drill-sideways tasks with invokeAll (:507-508) and reads them with Future.get (:510, :514). Future.get reports a task's exception as an ExecutionException, and the catch wraps that again: catch (ExecutionException e) { throw new RuntimeException(e); } (:519-520).
  4. Result. RuntimeException (message: the ExecutionException's toString()) -> ExecutionException -> the original exception. So an IOException thrown inside a search task never reaches the caller as an IOException in this mode (one thrown afterwards on the caller's thread, for example by buildFacetsResult at :390, still can).

Any exception a task throws is wrapped: from rewrite, weight creation, scoring or collection, including what an executor-backed IndexSearcher rethrows from its own slices. Not affected: argument checks and facet building on the caller's thread, a RejectedExecutionException from the executor (propagates unchanged), and interrupts, which take a separate ThreadInterruptedException path (:517-518).

Exposure and likelihood267 words
  • Who is hit. Code that runs DrillSideways with an executor and handles failures by type: catch (IndexSearcher.TooManyClauses e) for "query too large", catch (ExitingReaderException e) for "timed out", catch (IOException e), which the signature invites, or treating Error as fatal. In the concurrent mode all of them miss, and the failure takes the generic error path instead.
  • Opt-in. Only the 5-argument constructor with a non-null ExecutorService is affected; the 3- and 4-argument constructors are sequential. DrillSideways is @lucene.experimental.
  • Effect. For the tested failures, only the outer exception type differs. The search still aborts and returns nothing, every task has finished before the wrapper is thrown (invokeAll and Future.get wait for them, DrillSideways.java:506-516), and the original exception and message stay in the cause chain. (The separate interrupt path does not wait for the drill-down task; it is not part of this bug.) Handlers that catch RuntimeException (as TooManyClauses and ExitingReaderException are) or unwrap the cause chain are not affected.
  • Scale. None: one document and any failing task.
  • Not tested: identical query semantics. Sequential mode runs one DrillSidewaysQuery, whose visit only calls visitLeaf(this) (DrillSidewaysQuery.java:121-124); concurrent mode runs the DrillDownQuery plus one query per dimension (DrillSideways.java:488-503). Whether a visitor-based check such as the nested clause count can then fail in one mode only was not tested; that would be a separate issue.
  • Likelihood: plausible. The triggers are ordinary for user-facing search (a query over 1,024 clauses, a reader timeout under load, an I/O error), but it only bites type-specific handlers, and the recorded searches found no report of it since 2017.

Why it looks unintended

#
  • The javadoc presents the two modes as alternatives differing in speed and duplicate work; every search overload declares IOException, which a failing task cannot throw as such in that mode.
  • #12516 (9.8.0) removed the same wrapping from IndexSearcher to unify sequential and concurrent exceptions; it touched no facet file.
  • The facet module's other concurrent code already rethrows the task's exception.
The full argument275 words
  • The javadoc (DrillSideways.java:57-64): "There is both a "standard" and "concurrent" implementation for drill sideways. The concurrent approach is enabled by providing an ExecutorService to the ctor. The concurrent implementation may be a little faster but does duplicate work ... The standard approach may be a little slower but avoids duplicate computations and query processing." Nothing about exceptions. (Added by #142, LUCENE-9944; in every release from 9.0.0 on.)
  • The signature. Every search overload declares throws IOException (:188-190, :220, :225-226, :326-328, :406-410); in the concurrent mode an IOException thrown by a search task only ever arrives wrapped in an unchecked RuntimeException.
  • #12516 (Luca Cavanna, 9.8.0, CHANGES.txt:3429-3432, "Changes in runtime behavior": "Unwrap and throw execution exceptions cause when performing concurrent search") made TaskExecutor rethrow the cause (TaskExecutor.java:118-134). Its description: "This unifies the exceptions that get thrown between sequential codepath (when no executor is provided) and concurrent codepath (when an executor is provided)." Besides its CHANGES.txt entry it changed only core files; it touched no facet file and never mentions DrillSideways.
  • The module's convention. ConcurrentSortedSetDocValuesFacetCounts.java:310-313 and :342-345, and DynamicRangeUtil.java:92-93, rethrow the cause with IOUtils.rethrowAlways.
  • Tests. TestParallelDrillSideways extends TestDrillSideways and only swaps in the executor constructors, so the whole suite runs in both modes; no test makes a DrillSideways.search call fail, and no facet test mentions ExecutionException, so neither shape is pinned.
  • Intent at introduction. In LUCENE-7588 (#8639) mikemccand asked to fold the parallel version into DrillSideways: "It's really an implementation/execution detail I think? Similar to how IndexSearcher takes an optional executor." The thread never discusses how task failures reach the caller.
The devil's-advocate check215 words

Strongest case (refute review, the cross-model review, the intended-behaviour check, adjudication): DrillSideways is @lucene.experimental; no javadoc promises the same exception types in both modes, and throws IOException does not forbid unchecked wrappers; the wrapping is as old as the concurrent mode (2017) and matched IndexSearcher until 9.7.0, where TestLRUQueryCache still has the branch "expected: wrapped when executor is in use" (TestLRUQueryCache.java:1500-1504); and upstream filed #12516 under "Changes in runtime behavior", not "Bug Fixes".

Why it fails: the wrapping was never documented or discussed as a choice; it matched the IndexSearcher of its time, whose maintainers later removed the wrapping as the "root cause" (javanna, #12516 review) of mismatched exceptions; the module's other concurrent code unwraps; and the declared IOException, when a search task throws it, cannot arrive as one. The verifiers rated the case moderate as history and weak as a defence. Verdict: not intended; a low-priority consistency fix following #12516.

No-noise check. The call fails loudly either way and the cause is preserved. It is still claimed, as low priority, because the inputs are ordinary (clause limit, timeout, I/O error), the effect is visible to users (type-based handlers take the wrong branch), and Lucene treated the identical pattern in IndexSearcher as worth changing. The hunt's noise audit rated it "claim-low".

Suggested fix

#

Recommended A: rethrow the task's own exception

In searchConcurrently, declare IOException and replace throw new RuntimeException(e) with throw IOUtils.rethrowAlways(cause), as TaskExecutor (#12516) and the facet module's other concurrent code do. The repro then passes, and so does the whole lucene/facet test suite (307 tests).

      final List<? extends CollectorManager<K, R>> drillSidewaysCollectorManagers)
      throws IOException {
  ...
    } catch (ExecutionException e) {
      // Rethrow the task's own exception, as the sequential path and IndexSearcher do
      Throwable cause = e.getCause();
      throw IOUtils.rethrowAlways(cause != null ? cause : e);
    }

A: rethrow the task's own exception (validated by the checks) (recommended)

#

+6/-2 in DrillSideways.java: import org.apache.lucene.util.IOUtils, declare throws IOException on searchConcurrently (both callers already declare it), and rethrow the ExecutionException's cause, null-guarded as in ConcurrentSortedSetDocValuesFacetCounts.java:310-313. IOUtils.rethrowAlways throws an IOException, RuntimeException or Error as itself and wraps anything else in a RuntimeException (IOUtils.java:495-513); a task here can only throw what IndexSearcher.search throws. This is the shape #12516 gave TaskExecutor, where jpountz suggested IOUtils.rethrowAlways in review.

      final List<? extends CollectorManager<K, R>> drillSidewaysCollectorManagers)
      throws IOException {
  ...
    } catch (ExecutionException e) {
      // Rethrow the task's own exception, as the sequential path and IndexSearcher do
      Throwable cause = e.getCause();
      throw IOUtils.rethrowAlways(cause != null ? cause : e);
    }

Trade-offs

  • A behaviour change for callers that today unwrap RuntimeException -> ExecutionException by hand: they now get the exception itself. #12516 shipped the same change under "Changes in runtime behavior", where a CHANGES entry belongs.
  • When several tasks fail, only one exception is thrown, as today (the drill-down task's, else the first failing drill-sideways task's); the others are not added as suppressed.
  • Interrupt handling is unchanged.

How it was found

#

An enumerated differential sweep: 13 calls into Lucene APIs that take an executor, each run under 9 executor behaviours and compared with the same call without an executor. A failing DrillSideways search differed in all 9 cells. The finder, an AI tool, reduced it to a public-API JUnit; no model checker or solver was involved.

The method in full157 words

Method: semi-formal (the hunt's tag; an enumerated differential sweep, borderline with ordinary differential testing).

  • A hunt unit (executor pluggable-behaviour sweep), 2026-10-26, on main a9779ef3c193: 13 API surfaces x 9 executor behaviours (caller-runs, single thread, rejecting at the 1st/2nd/3rd execute, shut down, LIFO pool, pool thread interrupted before task 1 or 2) = 117 cells, each compared with the executor-less call: same result, same exception class and message, returns within 8 s, executor terminates.

History

#

Wrong since the concurrent mode was added by LUCENE-7588 (6.4.0, 2017); every release since has the same catch line. Until 9.7.0 IndexSearcher with an executor wrapped the same way; since #12516 (9.8.0) concurrent DrillSideways is the odd one out. Executed from 6.3.0 (no concurrent mode) to 10.6.0 and main; not fixed upstream.

LFV-636, snapshot of 2026-11-03

Registry title
DrillSideways with an ExecutorService reports every failure of its drill-down and drill-sideways searches as RuntimeException(ExecutionException(cause)), while sequential DrillSideways, and IndexSearcher with an executor since 9.8.0, throw the cause itself (for example IndexSearcher.TooManyClauses, ExitableDirectoryReader.ExitingReaderException or the declared IOException)
Area
facet / DrillSideways concurrent mode (ExecutorService constructor, searchConcurrently)
Priority
Low, rank 781: Opt-in concurrent DrillSideways wraps every task failure in RuntimeException(ExecutionException), but the search still aborts with the cause in the chain.
Impact class
wrong error
Impact note
Applications that pass an ExecutorService to DrillSideways (the opt-in concurrent mode of the @lucene.experimental facet helper; a read-only code search found no use of DrillSideways in Elasticsearch, OpenSearch or Solr) get every failure of a drill-down or drill-sideways task, such as the clause limit (IndexSearcher.TooManyClauses), a fired ExitableDirectoryReader timeout (ExitingReaderException), an IOException that search() declares, or an Error, as an unchecked RuntimeException wrapping an ExecutionException wrapping the original, so handlers that catch those types by class (for example to answer 'query too large' or 'timed out') take their generic error path instead; the search still aborts and returns nothing, and the original exception and its message stay in the cause chain; any index size, default codec, IndexWriterConfig and searcher, every release from 6.4.0 to 10.6.0 and main.
Summary
You construct DrillSideways with an ExecutorService so that its drill-down and drill-sideways searches run concurrently, and one of those searches fails, for example because the base query has more clauses than IndexSearcher's clause limit, an ExitableDirectoryReader timeout fires, or a query or collector throws IOException. You expect the exception the sequential DrillSideways throws for the same search: the class javadoc presents the two modes as alternative implementations that differ in speed and duplicate work, every search overload declares IOException, and IndexSearcher has rethrown task failures as-is since 9.8.0 (GITHUB#12516) precisely so that sequential and concurrent searches throw the same exceptions. Instead DrillSideways.searchConcurrently catches the ExecutionException from Future.get and throws new RuntimeException(e), so the caller receives RuntimeException -> ExecutionException -> the original exception, and catch blocks for TooManyClauses, ExitingReaderException or IOException do not fire.
