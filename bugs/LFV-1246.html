SegmentInfos.readCommit's deletion-count check overflows int, so an inconsistent commit of a 2^30-document segment opens without CorruptIndexException

When Lucene opens a commit it rejects a segment that claims more hard plus soft deletions than documents, but it adds the two counts as int. From 2^30 documents per segment the sum can wrap negative, so such a commit opens without the CorruptIndexException a small segment gets.

The finding in 30 seconds

#

A corruption check in commit parsing goes blind once a segment's two deletion counts add up past the int limit.

Background: deletion counts in a commit

#
  1. A commit (segments_N) lists every segment with its size maxDoc and two counts: delCount, documents deleted outright (hard deletes), and softDelCount, documents hidden by a soft-deletes field and not also hard-deleted.
  2. Together they can never exceed the segment's size: delCount + softDelCount <= maxDoc.
  3. When a commit is opened, SegmentInfos.readCommit checks this and throws CorruptIndexException ("invalid deletion count") if a writer bug or damage broke it.

The finding, step by step

#
  1. Write a commit whose one segment holds 1,073,741,824 documents (2^30) but records 1,073,741,824 hard deletes and 1,073,741,824 soft deletes: 2^31 deletions for 2^30 documents. A correctly working IndexWriter never writes this; a writer bug, a damaged file or a hand-built commit can.
  2. Open it with SegmentInfos.readLatestCommit, the parser DirectoryReader.open and IndexWriter use. You expect CorruptIndexException, as for a small segment: 5 + 5 deletions on 6 documents gives "invalid deletion count: 10 vs maxDoc=6".
  3. You get no exception. The commit opens and reports 1,073,741,824 + 1,073,741,824 deletions for 1,073,741,824 documents.
  4. Why: each count is checked alone (both are at most maxDoc), then softDelCount + delCount > maxDoc adds them as int. 2,147,483,648 is one past Integer.MAX_VALUE, so it wraps to -2,147,483,648, which is never greater than maxDoc.
  5. Every over-count whose sum stays below 2^31 is caught; only the wrapping ones slip through. A (long) cast fixes it, as the same method already does for its document total.

Who is affected

#

Only someone opening a commit that is already inconsistent, from a writer bug, a damaged file whose checksum still matches, or a hand-built commit, on a segment of at least 1,073,741,824 documents. Healthy indexes are never affected; a correctly working IndexWriter never writes such counts. The effect is a missed CorruptIndexException; nothing after it was tested.

Mechanism, terms and numbers484 words

SegmentInfos.readCommit parses segments_N and, for each segment, checks the hard-delete count delCount and the soft-delete count softDelCount against [0, maxDoc] one by one, then rejects the commit when softDelCount + delCount > maxDoc. That sum is int arithmetic. A segment may hold up to IndexWriter.MAX_DOCS (2,147,483,519) documents, so from 2^30 documents on, two counts that are each legal can sum past Integer.MAX_VALUE, wrap negative and pass. A commit that records 2^30 + 2^30 deletions for a 2^30-document segment is then read without the CorruptIndexException the same check gives a small segment. Only an already-inconsistent, checksum-valid commit is affected (a correctly working IndexWriter never writes one), and nothing is shown to go wrong after it is read. The fix is a (long) cast in the comparison and the message; the same method already sums its document total in a long.

The checks (main 5adff78bb168)

#
  • parseSegmentInfos (SegmentInfos.java:379) reads int delCount (:426) and rejects delCount < 0 || delCount > info.maxDoc() (:427-430); then int softDelCount (:433) with the same check (:434-437). Each count may therefore be as large as maxDoc.
  • if (softDelCount + delCount > info.maxDoc()) (:438) adds the two as int. A true sum of 2^31 or more wraps negative and passes. The message (:440) prints the same int sum.

When the sum can wrap

#
  • Both counts are at most maxDoc, so a wrap needs maxDoc >= 2^30 and an over-count (delCount + softDelCount - maxDoc) of at least 2^31 - maxDoc: 2^30 at maxDoc = 2^30, down to 129 when one segment holds MAX_DOCS documents.
  • A segment's size is bounded only by the index total, totalDocs <= IndexWriter.getActualMaxDocs() (:551-557; MAX_DOCS = Integer.MAX_VALUE - 128, IndexWriter.java:208). That total is a long (:401, :424); the deletion-count sum is not.

How such a commit gets written

#

SegmentInfos.write checks each count alone, not their sum (:690-714), and the public SegmentCommitInfo constructor stores the counts as given (SegmentCommitInfo.java:101-122); the package-private setters assert softDelCount + delCount <= info.maxDoc() (:374-392). The segments_N checksum is verified after parsing (SegmentInfos.java:371, in a finally block), so only a checksum-valid commit is returned.

Same shape, not exercised

#

SegmentCommitInfo.getDelCount(true) (:453-454) and the setter asserts use the same int sum. Once the reader rejects bad sums, a commit read from disk has a sum of at most maxDoc, so they cannot overflow for such commits. Not claimed.

Exposure and likelihood167 words
  • Where the check runs. Every commit open: DirectoryReader.open (StandardDirectoryReader.java:95), new IndexWriter (IndexWriter.java:1011, :1085) and SegmentInfos.readLatestCommit/readCommit.
  • Where bad counts come from. The delete-count checks exist to catch Lucene writer bugs (LUCENE-5615). LFV-593, a separate IndexWriter soft-delete counting bug, writes checksum-valid commits that this check rejects at small scale ("invalid deletion count: 3 vs maxDoc=2"); a logically inconsistent file whose checksum still matches (for example one rewritten with a recomputed footer), or code that builds commits with the @lucene.experimental SegmentInfos/SegmentCommitInfo API, are the other sources. A correctly working IndexWriter never writes such counts: the SegmentCommitInfo setters assert the invariant (SegmentCommitInfo.java:379-380, :389-390).
  • Settings. None involved; any codec.
  • Scale. One segment of at least 2^30 documents, half the index-wide limit, and an over-count of at least 2^31 - maxDoc.
  • Effect. The due CorruptIndexException is not thrown, and the commit is returned with impossible counts. What the accepted commit does later was not tested and is not claimed.

Why it looks unintended

#
  • The check rejects every over-count whose sum fits in an int (5 + 5 on 6 documents, 2^30 + 1 on 2^30); only wrapping ones pass: arithmetic, not policy.
  • Lucene validates delete counts on read precisely to catch writer bugs that write bad counts (LUCENE-5615).
  • The same method already sums its document total in a long.
The full argument145 words
  • The check exists for exactly this input. SegmentInfos.java:438-442 rejects delCount + softDelCount > maxDoc, and does so for every over-sum below 2^31.
  • Stated purpose. LUCENE-5615 (#6677, 2014), Mike McCandless: "When reading the segment infos, we already check if the delCount is out of bounds ... and throw CorruptIndexException if so", adding write checks "in case there are Lucene bugs that mess up the delete counts"; lucene/CHANGES.txt:12626-12627: "Validate per-segment delete counts at write time, to help catch bugs that might otherwise cause corruption".
  • Same risk, already handled. long totalDocs (:401) avoids the overflow in the document total.
  • No record of a choice. The sum came as int + int with fe83838ec37 (LUCENE-8341, #9388), whose 11 comments never mention overflow; LUCENE-9482 (#10521, 2020) edited this line only to fix the message and kept the int sum. No upstream test covers counts near 2^30.
The devil's-advocate check232 words

Index files are trusted and "not defensively validated when read" (SECURITY.md:32); readCommit's javadoc promises only "@throws CorruptIndexException if the index is corrupt" (SegmentInfos.java:290); the repro builds an impossible commit through the SegmentInfo constructor, which "is public only to allow access from the codecs package" (SegmentInfo.java:113); and IndexWriter never writes such counts. An independent reviewer from another model family (OpenAI GPT-5.6) rated it not real on these grounds, while reproducing it with its own check, agreeing on the root cause and seeing the long cast fix it.

Why it fails: Lucene already chose to validate these counts on read, so the only question is whether the check works; "IndexWriter never writes this" is the precondition of every corruption check, not a reason for one to miss (and LFV-593 is an IndexWriter bug that does write counts this check rejects). The constructor is only how the test plants the counts: upstream's TestSegmentInfos builds commits the same way (TestSegmentInfos.java:64-97) and tests corruption detection (:321). SECURITY.md:46 welcomes hardening, for example a change that "replaces a low-level failure with a clean CorruptIndexException on a broken index", provided it does not hurt performance; this fix is of that kind (it restores a missed detection rather than replacing a failure) and adds one widening per segment per commit read. Verdict: a real Low bug, a hardening fix.

Downstream note

#

Systems that hold segments of a billion or more documents and rely on Lucene's open-time checks to catch a writer bug's bad deletion counts get no CorruptIndexException for this case until the fix lands.

How it was found

#

A proof-obligation audit of SegmentInfos's commit-parsing contract: the read-side check must reject every segment whose hard plus soft deletion counts exceed maxDoc. Evaluating that obligation at the largest legal counts exposed the int sum, and a one-test JUnit repro witnessed it.

The method in full81 words

The obligation came from the check itself (SegmentInfos.java:438-442) and the invariant the SegmentCommitInfo setters assert (SegmentCommitInfo.java:374-392). Each count is bounded only by maxDoc and maxDoc only by the index total, so the audit asked whether the sum can leave the int range; at maxDoc = 2^30 it can. A probe then showed the over-sums it tried that fit in an int rejected and the wrapping ones accepted, and the repro committed one wrapping pair through public API.
