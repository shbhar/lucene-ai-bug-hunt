The finding in 30 seconds

#

New in 11.0, in no release. On the 11.0 branch (branch_11x daa54f2e0cd3) a Maven project with one JUnit 4 test that extends LuceneTestCase executes 0 of 1 tests, assertions on and off (Maven 3.9.16, Surefire 3.5.4), and its build is green. With 10.6.0 it executes 1 of 1. Introduced by the merged #16027 (commit 227255fdb08).

How Maven decides which tests it can run

#
  1. A library's POM lists its dependencies. They land on the test class path of every project that uses the library.
  2. Maven's test plugin, Surefire, picks a "provider" from that class path when the project configures none. JUnit 4 and nothing newer: the JUnit 4 provider. A JUnit Platform artifact (JUnit 5 or 6): the JUnit Platform provider.
  3. On the JUnit Platform every kind of test needs its own engine. The Jupiter engine runs Jupiter tests. JUnit 3 and 4 tests need the vintage engine.
  4. A run that finds no test is a success unless the project sets failIfNoTests.

The finding, step by step

#
  1. Your Maven project has one test dependency, lucene-test-framework, and one JUnit 4 test that extends LuceneTestCase. With Lucene 10.6.0, mvn test (Maven 3.9.16, which binds Surefire 3.5.4) prints Tests run: 1.
  2. You change the Lucene version to 11.0.0-SNAPSHOT (a build of the unreleased 11.0 branch) and run mvn test again. You expect Tests run: 1: the JUnit section of the 11.0 migration guide names no step for a project that keeps JUnit 4 tests.
  3. You get Tests run: 0 and BUILD SUCCESS, with assertions on and off. The test was never started, and nothing in the output says that a test was left out.
  4. Why: the 11.0 POM of the test framework adds junit-jupiter-engine 6.1.3. Surefire 3.5.4 then switches to its JUnit Platform provider, where JUnit 4 tests need junit-vintage-engine. Lucene's own build adds that engine for itself; the POM does not carry it.
  5. The way out is one dependency: with junit-vintage-engine 6.1.3 in your project the test runs again, 1 of 1. Surefire 3.6.0 and 3.6.1 also run it. No Lucene class is wrong.

Who is affected

#

Maven projects that test with lucene-test-framework and still have JUnit 4 tests, on Surefire 3.5.4 (the default of Maven 3.9.16), without junit-vintage-engine of their own and without a pinned provider. Their JUnit 4 tests are not discovered and not run while the build passes. Shown for Maven only; no release has it; no shipped class misbehaves.

Mechanism, terms and numbers1,251 words

Lucene's test framework is published for other projects too: they add lucene-test-framework as a test dependency and extend LuceneTestCase. For 11.0, #16027 added JUnit Jupiter support, and with it two dependencies of the module: randomizedtesting-jupiter and junit-jupiter-engine. Both are now in the POM that the build generates for the module. Nothing in that POM runs JUnit 4 tests: Lucene's own build adds junit-vintage-engine for its own test tasks in a build plugin, outside the published metadata.

For a Maven project this changes how its tests are run. Surefire picks its provider from what is on the test class path. With the 10.6.0 POM it finds JUnit 4 only and runs the tests with its JUnit 4 provider. With the 11.0 POM it finds the JUnit Platform, picks its JUnit Platform provider, and Surefire 3.5.4 (the version Maven 3.9.16 binds by default) then finds no engine for a JUnit 4 class. It prints Tests run: 0, and because a run without tests is a success by default, BUILD SUCCESS.

The dependency is deliberate and the POM states it truthfully, and the build tool's half is documented by the tool and changed in Surefire 3.6.0. What is missing is on the release side: the JUnit section of the 11.0 migration guide names no step for a project that keeps JUnit 4 tests. That is a release and migration gap of the unreleased 11.0, at Low, and not a bug in LuceneTestCase or any other shipped class. A project ends it with one dependency, junit-vintage-engine 6.1.3, or with Surefire 3.6.0 or 3.6.1.

What Surefire 3.5.4 does with each class path

#

Source: apache/maven-surefire at the tag surefire-3.5.4, AbstractSurefireMojo.java. This half of the mechanism is public since 2021 for other products (Jesse Glick's SUREFIRE-1911, and Slawomir Jaranowski's SUREFIRE-2235, which writes the rule of item 4 out); it is not a discovery of this page.

  1. The list of providers has the JUnit Platform provider before the JUnit 4 one (:1150-1161). The platform provider applies when junit-platform-runner is not among the project's artifacts and either junit-platform-engine is among the Surefire plugin's own dependencies or junit-platform-commons is among the project's artifacts (:3078-3080, :2295-2306). In the repro it applies through the last part: the project has no junit-platform-runner, the plugin has no dependency of its own, and junit-platform-commons 6.1.3 arrives with junit-jupiter-engine. With JUnit 4 and the JUnit Platform both on the class path, the log shows that it is the one selected.
  2. 10.6.0: no JUnit Platform artifact. The log says Using auto detected provider org.apache.maven.surefire.junit4.JUnit4Provider, then Running TestConsumer, Tests run: 1.
  3. 11.0: junit-jupiter-engine brings junit-platform-engine and junit-platform-commons. The log says Using auto detected provider org.apache.maven.surefire.junitplatform.JUnitPlatformProvider.
  4. Under that provider Surefire 3.5.4 first asks whether a junit-platform-engine is among the plugin's own dependencies (:3113-3114); if so it takes those dependencies and derives no engine from the test dependencies. No project with such a plugin dependency was run. The repro has none, so the other branch applies (:3115-3143): Surefire adds a Jupiter engine only when junit-jupiter-api is among the test dependencies and the engine is not, and it adds junit-vintage-engine only together with a Jupiter engine that it has just added. Here the engine is already there, so it adds neither. The local repository of the plain 11.0.0-SNAPSHOT run holds no junit-vintage-engine at all.
  5. The Jupiter engine finds no Jupiter test in a JUnit 4 class: Tests run: 0. failIfNoTests defaults to false (:419): BUILD SUCCESS.

Why it looks unintended

#
  • The dependency is intended. That a project's JUnit 4 tests silently stop running is stated nowhere: the guide's JUnit section names no engine and no step.
  • The overview says the framework "can also be used for testing third-party code".
  • Lucene's own build cannot see it: it adds the vintage engine for itself, outside the POM.
The full argument384 words

Intended: the dependency. LuceneTestCaseJupiter and randomizedtesting-jupiter need the Jupiter engine, and #16027 added it on purpose; the POM states it truthfully. Not stated, and not shown to be wanted: that a Maven project that keeps JUnit 4 tests stops running them without a message.

  • The guide names no step. The JUnit section of MIGRATE.md (its opening is quoted under "The finding in 30 seconds") tells a reader that LuceneTestCase remains the base class for JUnit 4 tests and lists what changes for Jupiter tests. It names no engine, no version of the JUnit artifacts (it speaks of JUnit5/jupiter; the engine the POM brings is 6.1.3) and no build tool.
  • The change list has two lines on the subject, neither for a consumer. lucene/CHANGES.txt:150 on branch_11x (:180 on main): "GITHUB#: Add junit5/jupiter support to the test-framework module. (Dawid Weiss)". :513 (:543 on main): "GITHUB#15949: Use junit5 engine vintage runner to run junit4 tests. (Dawid Weiss)", which is about Lucene's own build.
  • Outside use is a supported use. lucene/test-framework/src/java/overview.html:23-25: "The Lucene Test Framework is used by Lucene as the basis for its tests. The framework can also be used for testing third-party code that uses the Lucene API." The module's description is 'Framework for testing Lucene-based applications' (build.gradle:20).
  • The pull request did not weigh it. The thread of #16027 (merged 2026-05-14; the description and two comments by the author) has no sentence on Maven, a POM, Surefire or the vintage engine. Its "what next?" paragraph expects downstream projects to be affected by a later step: "if we want to move forward and actually convert all the existing tests to junit5 (and eventually drop junit4) this becomes a more problematic issue because it affects all the downstream projects [...]".
  • A precedent. #8010 (LUCENE-6953, "clean up lucene-test-framework dependencies", Robert Muir, closed 2015-12-29, labelled a bug) treated the dependency list of this module's published POM as something to get right: it removed junit4-ant and ant, which only Lucene's own build needs, from the module's dependencies.
  • Nothing in Lucene's tree can show it. Its test tasks take the launcher and the vintage engine from the build plugin (TestsAndRandomizationPlugin.java:582), and the release smoke test checks digests, signatures and POM coordinates of the Maven artifacts (dev-tools/scripts/smokeTestRelease.py:736-939) without building a project against them.
The devil's-advocate check272 words

The strongest case for "intended", in four points. (1) The dependency is deliberate and the POM is truthful. (2) Choosing the provider from the class path, needing the vintage engine for JUnit 4 tests on the JUnit Platform, and passing a build without tests are Surefire's documented behaviour ("If you want to write and execute JUnit 3 or 4 tests via the JUnit Platform add the Vintage Engine to the dependencies [...]"), and Surefire 3.6.0 changed it. (3) No Lucene text promises that the test framework's metadata provides a test engine for other builds; 11.0 is a major release; the javadoc of LuceneTestCase already asks to move to LuceneTestCaseJupiter. (4) JUnit's 6.1.3 guide ("Migrating from JUnit 4") calls the vintage engine deprecated, and LUCENE-6953 removed from this POM what only a test run needs, so a maintainer may well decline a change of the POM.

Why it does not settle the matter: all four defeat a claim that Lucene or Surefire is wrong, and this page makes no such claim. They do not show that an upgrader is told. The trigger is an ordinary project on the default tooling of the newest Maven 3.9, the effect is silent, Lucene's own checks cannot see it, and the one sentence that ends it (add the vintage engine, or use a newer Surefire) stands nowhere in the 11.0 notes. What remains is size, not intent: at least a note, and that is why this is Low. One second opinion that set out to refute the finding ended at "uncertain" for exactly these reasons and left the answer to a maintainer; it contested no run.

Or the vintage engine as a runtime dependency in the generated POM. A project's own way out is one dependency.

B. junit-vintage-engine as a runtime dependency in the generated POM (validated)

#

One dependency line in lucene/test-framework/build.gradle, with group org.hamcrest excluded as the build plugin does for Lucene's own tests, and the regenerated versions.lock: 2 files, 14 added lines (3 and 11). The generated POM gains exactly one dependency, junit-vintage-engine 6.1.3 in runtime scope.

   moduleApi(deps.randomizedtesting.jupiter)
   moduleApi(deps.junitplatform.jupiter)
+  moduleRuntimeOnly(deps.junitplatform.vintage, {
+    exclude group: "org.hamcrest"
+  })

Trade-offs. A build change, and the maintainers may decline it: JUnit's 6.1.3 guide ("Migrating from JUnit 4") says "The JUnit Vintage engine is deprecated and should only be used temporarily while migrating tests to JUnit Jupiter or another testing framework with native JUnit Platform support", and #8010 (LUCENE-6953) removed from this POM what only Lucene's own test run needs. It does not help a project that pins junit-vintage-engine 5.11.4 without the JUnit BOM (that build fails with and without it). It is not a one-line change: the one-line form without the exclusion fails checkLocks, and its regenerated lock file has 163 added lines because hamcrest-core 1.3 arrives with the engine. A released POM cannot be changed afterwards.

What the runs validated.

  • On main 781025d6fe32: checkLocks fails before writeLocks and passes after it; checkLicenses passes (the engine's licence files are already in lucene/licenses).
  • The project executes 1 of 1 against the publication of the changed checkout, assertions on and off.
  • ./gradlew :lucene:test-framework:test: 642 tests, 33 skipped, as on the unchanged commit.
  • The diff passes git apply --check on branch_11x daa54f2e0cd3.
  • An earlier run of the same change through Lucene's own build on the 11.0 branch (at 57f96b20d32b): the one-test project 1 of 1 with assertions on and off, 1 of 1 without a plugin named, the plain JUnit 4 class 2 of 2, the mixed module 5 of 5 with no test run twice (Surefire 3.5.4 and 3.6.1), the integration test under Failsafe 3.5.4 1 of 1, the Jupiter-only project 4 of 4. The project that pins junit-vintage-engine 5.11.4 fails with the change as without it.
  • The binary distribution does not change: it packs the test framework without transitive dependencies (lucene/distribution/build.gradle:108-110).

Not remedies (from the recorded runs). A POM without any Jupiter engine runs the JUnit 4 tests under Maven and breaks a Gradle project that uses useJUnitPlatform() with a vintage engine of its own ("RepeatExecutionTestEngine could not be instantiated"). Dropping only the direct junit-jupiter-engine dependency changes nothing, because randomizedtesting-jupiter names the engine too.

What a project can do itself, each one run: add org.junit.vintage:junit-vintage-engine 6.1.3 in test scope (it also runs 1 of 1 on 10.6.0, so it can go in before the upgrade); or use Surefire 3.6.0 or 3.6.1; or pin the JUnit 4 provider of Surefire 3.5.4 (Maven Central lists no surefire-junit4 newer than 3.5.6, read 2026-11-16). -DfailIfNoTests=true turns the silent build into a failing one.

Downstream note

#

Nothing happens at the run time of an application that embeds Lucene: the effect is limited to the test builds of Maven projects that use the test framework, which can lose their JUnit 4 test runs on the upgrade without a failing build.

How it was found

#

The dependency lists of the 10.6.0 POMs on Maven Central were compared with the POMs the 11.0 branch generates. The test framework's POM had gained junit-jupiter-engine. One small Maven project, built against both versions, showed what that does to JUnit 4 tests.

The method in full191 words

Method: semi-formal (a differential check of the release against the release branch through a build tool, with a small model of the tool's rule; no model checking, constraint solving or proof was involved).

  • Signal. The dependency list of each published 10.6.0 POM was compared with the POM the 11.0 branch generates for the same module. lucene-test-framework had two new compile-scope dependencies.
  • Witness. One consumer build that counts what the build tool executed: 1 of 1 on 10.6.0, 0 of 1 on the 11.0 branch. It was reduced to the two-file project of this page.
  • Model. The rule by which Surefire 3.5.4 adds engines was read from its source and turned into predictions for the unchanged POM, three changed POMs, a project with a vintage engine 5.11.4 of its own, and Surefire 3.6.0 and 3.6.1. Every prediction was confirmed by the runs (102 Maven runs and 11 Gradle runs were made in all), including the two that separate "an engine anywhere among the dependencies" from "the direct dependency". The model makes no prediction for the other Surefire versions that were run; one of them, 2.22.2, fails the build instead of passing it.
