The finding in 30 seconds

#

commit() cuts indexing into before and after. An indexing thread that checked "no commit running" a moment too early flushes an after-the-cut buffer into the commit.

Background

#
  1. Buffers. Each indexing thread writes into its own in-memory buffer (a DWPT). Deletes, including the delete half of updateDocument, go into a shared delete queue.
  2. Full flush. commit() (and an NRT reopen) switches to a new delete queue, the cut, and writes every buffer of the old queue into the commit. Indexing goes on into buffers of the new queue; those must wait until the commit is done.
  3. Helping flush. After each update, the indexing thread looks for a buffer the RAM policy marked for flushing and, if no full flush is running, flushes it itself.

The finding, step by step

#
  1. 16 threads replace documents by key with updateDocument, each on its own 50 keys (800 keys), while the test thread loops commit() and counts every key in each commit point. Default codec, 0.25 MB RAM buffer, JVM pinned to 2 CPUs.
  2. You expect at most one live document per key in every commit: updateDocument's delete and add are atomic for readers, and a commit holds exactly the operations up to the sequence number commit() returns.
  3. Instead commit 106 holds two live documents for key 388 (after 15.6 s, assertions off; 6 of 6 runs fail). With assertions on, it fails too: with the same duplicate, or with an assertion in DocumentsWriter.doFlush that closes the writer.
  4. Why: after an update, an indexing thread asks "is a commit running?" under a lock, releases the lock, then picks a buffer marked for flushing and flushes it. If commit() starts in that gap, the thread flushes a buffer that belongs after the commit inside the commit.
  5. So the commit gets operations newer than its sequence number, and the newer update's delete can miss the older copy. One re-check under the lock fixes it: all 5,000 commits are clean.

Who is affected

#

Applications that call updateDocument from several threads on one IndexWriter while another thread commits (by code reading also softUpdateDocument and NRT reopens, not run), on the default code path. Rare: reliable only when indexing threads outnumber CPUs (16 on 2 or 4); not seen unpinned on 32 cores in 120 s, nor shown at the default 16 MB buffer.

Mechanism, terms and numbers745 words

Several threads replace documents by key with IndexWriter.updateDocument while another thread calls commit(). DocumentsWriterFlushControl.nextPendingFlush checks "is a full flush running?" under its lock, releases the lock, and only then checks out a flush-pending in-memory buffer (DWPT) without checking again. If the commit's full flush starts in that gap, the indexing thread flushes a buffer of the new, post-commit delete queue inside the commit. The commit point then holds operations above the sequence number commit() returned and, when the newer update's delete misses the older document, two live documents for one key; the duplicate stays until the key is updated again, and a crash after that commit would recover it. With assertions on, the same race shows either as the duplicate or as a tripped doFlush assertion that closes the writer. One public-API test reproduces it on main when the indexing threads outnumber the CPUs; the code dates from LUCENE-3090 (2011), and 10.6.0 and 10 of the 14 releases run from 5.3.0 to 10.5.2 fail too. A one-hunk re-check of fullFlush under the lock fixes it.

The code (main 645d4fe14a20, lucene/core/src/java/org/apache/lucene/index/)

#
  1. Indexing threads help flush. After every update DocumentsWriter.postUpdate calls maybeFlush (DocumentsWriter.java:400-410, with the default checkPendingFlushOnUpdate), which calls flushControl.nextPendingFlush() (:493-500).
  2. The stale check. nextPendingFlush (DocumentsWriterFlushControl.java:441-469) copies fullFlush and numPending into locals under the monitor (:450-451) and releases it (:452). Then if (numPending > 0 && fullFlush == false) { // don't check if we are doing a full flush (:453) scans the pool and returns checkOutForFlush(next) for the first flush-pending DWPT it can lock (:454-459).
  3. No second look. checkOutForFlush (:409-424) is synchronized but never reads fullFlush.
  4. The full flush starts in the gap. commit() reaches DocumentsWriter.flushAllThreads (DocumentsWriter.java:667-715), whose markForFullFlush sets fullFlush = true and swaps the delete queue under the monitor (DocumentsWriterFlushControl.java:564, :575), then collects the old queue's DWPTs (:580-606).
  5. A new-queue DWPT can already be pending. Indexing continues during the commit, and the RAM policy marks the largest non-pending DWPT pending, possibly another thread's idle one (FlushByRamOrCountsPolicy.java:83-90).
  6. The sibling path does it right. checkout() reads fullFlush under the monitor and parks such a DWPT in blockedFlushes until finishFullFlush (DocumentsWriterFlushControl.java:253-272, :397-407, :649-664).
  7. Result. The stale thread flushes a new-queue DWPT inside the full flush; flushAllThreads waits for it (DocumentsWriter.java:690) and the commit publishes its segment and its frozen new-queue deletes. DocumentsWriter.java:508-515 asserts that only the full flush's queue flushes during it. That assertion is armed only after markForFullFlush returns (DocumentsWriter.java:680-681), so it catches an out-of-turn flush that starts after the collection but not one that starts during it; with -ea the test shows either the assertion or the duplicate.

Why a delete goes missing

#

In the TLA+ model's counterexample, the out-of-turn flush starts while markForFullFlush is still collecting, so its flush ticket is queued ahead of the old queue's tickets. Its delete packet is then published before old-queue segments that flush after it, and a packet applies only to segments published before it, so the newer update's delete never reaches the older copy (FrozenBufferedUpdates.java:460-462). By code reading this also needs the older version's own delete to have been frozen already, by an old-queue flush whose ticket is ahead of the out-of-turn one: every flush freezes its queue's whole delete buffer (DocumentsWriterPerThread.java:429), and an old-queue packet published after the new segment would delete the newer version instead. The model does not model deletes, so it cannot settle this; the executed duplicates are consistent with it. Neither ordering was instrumented at runtime, and one step of the cited trace (state 23) is not a code schedule: a thread marks another buffer pending while its own is pending, which doAfterDocument does not do (DocumentsWriterFlushControl.java:232-238). Observed directly: an observation-only probe tied every failing commit to a new-queue check-out by nextPendingFlush during that commit's full flush (or the one before), and the -ea stack goes through postUpdate -> maybeFlush -> doFlush.

Exposure and likelihood264 words
  • Trigger. Concurrent updateDocument on one writer while commit() runs (softUpdateDocument takes the same updateDocuments path by code reading, IndexWriter.java:1938-1947; not run); an indexing thread descheduled inside a two-statement window of nextPendingFlush just as the full flush starts; a buffer of the new delete queue already marked pending by the RAM policy. Default flush-by-RAM policy and codec; any Directory by code reading (every run used ByteBuffersDirectory); no opt-in feature or expert API. IndexWriter is documented as "completely thread safe".
  • Effect. Silent wrong results: the commit point holds two live documents for one key until the key is updated again, and a crash after that commit would recover the duplicate (inferred from commit semantics; no crash was simulated); the commit also holds operations above the sequence number commit() returned. With -ea (tests), it can instead show as a tragic AssertionError that closes the writer.
  • How often. With 16 indexing threads pinned to 2 or 4 CPUs every 30 s run failed (10 of 10, 5 of 5); unpinned on 32 cores no run failed in 120 s. The repro lowers the RAM buffer to 0.25 MB and uses NoMergePolicy only to raise the flush and commit rate; an independent test failed with the default merge policy and scheduler at 1 MB. No failure has been shown at the default 16 MB buffer, and no field report is known. CPU-oversubscribed indexing with frequent commits raises the rate.
  • Not exercised. NRT reopen runs the same full flush and softUpdateDocument the same update path by code reading, but only commit(), updateDocument and ByteBuffersDirectory were run.

Why it looks unintended

#
  • updateDocument promises its delete and add are "atomic as seen by a reader"; commit() holds "all sequence numbers <= this value" and no others.
  • The code agrees: "don't check if we are doing a full flush", and doFlush asserts that no such flush happens.
  • Upstream fixed bugs of the same family at other sites (LUCENE-3348, LUCENE-8317, #13627).
The full argument337 words
  • Contracts. "IndexWriter instances are completely thread safe, meaning multiple threads can call any of its methods, concurrently" (IndexWriter.java:167-168). updateDocument: "The delete and then add are atomic as seen by a reader on the same index (flush may happen only after the add)" (:1902-1904). commit(): "All sequence numbers <= this value will be reflected in the commit, and all others will not" (:4208-4210; the same on prepareCommit, :3730-3732).
  • The code's intent. The comment at the check, "don't check if we are doing a full flush" (DocumentsWriterFlushControl.java:453); checkout() parks a pending DWPT during a full flush (:253-272); numBlockedFlushes describes a DWPT that "needs flushing but must not be flushed until the full flush has finished" (:722-726); doFlush asserts that only the full flush's queue flushes during it (DocumentsWriter.java:508-515), and assertTicketQueueModification says "only modifications from the current flushing queue are permitted while doing a full flush" (:654-658). prepareCommitInternal clones the segment infos "so that no partial changes (eg a delete w/o corresponding add from an updateDocument) can sneak into the commit point" (IndexWriter.java:3845-3849). The 4.0 CHANGES entry: flushes that occur while a full flush is running "are queued and will happen after all DWPT involved in the full flush are done flushing" (lucene/CHANGES.txt:15736-15741).
  • Tests. TestIndexingSequenceNumbers.testStressConcurrentCommit (@Nightly) checks the same contract with concurrent updates and commits ("this commit point should reflect all operations <= this seqNo"); TestIndexWriter.testNeverCheckOutOnFullFlush asserts that nothing is checked out once a full flush has started through checkoutLargestNonPendingWriter. No test targets the nextPendingFlush window; concurrent stress tests such as the @Nightly testStressConcurrentCommit can reach it only by chance (nextPendingFlush runs after every update, DocumentsWriter.java:406-407, :493-494).
  • History. Bugs of the same family, from other root causes, were fixed as bugs: LUCENE-3348 (#4421, 2011), LUCENE-3368 (#4441), LUCENE-8317 (#9364, 2018), LUCENE-8639 (#9685), LUCENE-8813 (#9857, 2019; seen as the sibling assertTicketQueueModification assertion) and #13127/#13571 (seen as maxSeqNo assertions), fixed by #13627 (2024).
The devil's-advocate check152 words

The strongest case: DocumentsWriterFlushControl is internal, and the unlocked scan deliberately keeps the flush-control lock off the hot indexing path (contention work such as #12198 and #12958 shows the concern); commit() does not block indexing, so an update racing the cut may land on either side, and the sequence-number finding could be called a linearization question.

Why it fails: the duplicate does not depend on sequence numbers at all, since a reader sees an update's add without its delete, which updateDocument promises cannot happen; the comment, the sibling path, the javadoc and the assertion all say a new-queue DWPT must not flush during a full flush; and the fix keeps the unlocked scan, adding one re-check where the lock is taken anyway (checkOutForFlush is synchronized). An optimisation can justify the unlocked read, not a lost delete. Verdict: not intended, a defect. Cross-model reviewers (OpenAI GPT-5.6) rated the works-as-designed case weak.

Suggested fix

#

Recommended Re-check fullFlush under the lock before the check-out (validated)

In nextPendingFlush, re-check fullFlush under the flush-control lock right before checkOutForFlush, and skip the buffer when a full flush has started; it stays pending and is flushed after the commit (+7/-1 lines). The test then passes all 5,000 commits, and the closest index tests pass.

if (perThreadPool.isRegistered(next)) {
  synchronized (this) {
    // fullFlush was read before the scan: a full flush may have started since, and a
    // pending DWPT of its new delete queue must wait until that full flush is done
    if (this.fullFlush == false) {
      return checkOutForFlush(next);
    }
  }
}

Re-check fullFlush under the lock before the check-out (validated) (recommended)

#

In the pool scan of DocumentsWriterFlushControl.nextPendingFlush, wrap the check-out in synchronized (this) and call checkOutForFlush only while fullFlush is still false. A skipped DWPT stays flush-pending in the pool; once finishFullFlush clears fullFlush, the next nextPendingFlush (or the next commit's markForFullFlush) flushes it.

if (perThreadPool.isRegistered(next)) {
  synchronized (this) {
    // fullFlush was read before the scan: a full flush may have started since, and a
    // pending DWPT of its new delete queue must wait until that full flush is done
    if (this.fullFlush == false) {
      return checkOutForFlush(next);
    }
  }
}

Trade-offs

  • Lock order DWPT -> flush control is the existing one (checkOutForFlush already runs under the DWPT lock and is synchronized); the unlocked scan stays, so indexing threads take the lock no more often than before.
  • A pending new-queue DWPT now waits for the commit to finish before it flushes, which is what the sibling checkout() path and the 4.0 CHANGES entry already describe.
  • The hunt's first version of the comment said fullFlush "was read without the lock held"; it is read under the lock, which is then released. The diff here rewords the comment; the executable change is the same.

Block the buffer like checkout() does (untested)

#

On the re-check, when fullFlush is true, call checkoutAndBlock(next) so the DWPT goes to blockedFlushes, as the sibling checkout() does (DocumentsWriterFlushControl.java:256-259).

Trade-offs

Mirrors the sibling path, but must handle a pending DWPT of the old queue found while markForFullFlush is still collecting: it would leave the pool before markForFullFlush sees it and reaches the flush queue only if pruneBlockedQueue(flushingQueue) (:612) runs after the block. Not built.

Hold the lock across the scan (untested)

#

Run the pool scan of nextPendingFlush inside its synchronized block.

Trade-offs

Simplest to reason about, but puts the flush-control lock on the indexing path whenever buffers are pending, the contention the unlocked scan avoids (#12198, #12958). Not built or benchmarked.

Downstream note

#

Applications that rely on updateDocument to replace or remove content can keep serving the old version from that commit until the key is updated again.

How it was found

#

A TLA+ model of IndexWriter's flush protocol kept nextPendingFlush's check and check-out as two steps; the model checker found a schedule that breaks the commit, and none with the step made atomic. A public-API JUnit then reproduced it on the stock jars, and the one-line re-check made it pass.

The method in full179 words

Method: TLA+ model checking (TLC) of the flush protocol, then an executed public-API test (the hunt classes it as semi-formal: the model gave the schedule, the stock-jar test is the proof).

  • Model (2026-10-27). A code-reading hypothesis, formed while building a TLA+ model of the full flush (FnbFlush.tla), kept nextPendingFlush's fullFlush read and its pool scan as two steps, as in the code. TLC violated NoBad at depth 27 and TicketOrder at depth 30 (the new-queue ticket queued ahead of the old-queue tickets); the same model with the step atomic is exhaustively clean (13,954,054 distinct states). That unit could not reproduce it on the stock jar and judged it proof-only.
  • Execution (2026-10-29). A second unit wrote a public-API JUnit (16 updateDocument threads, a commit() loop, oracles: one live document per key and the commit's sequence-number cut) and ran it on the stock main jars pinned to 2 CPUs: it failed with assertions off and on, and passed with the one-hunk fix in matched runs. The minimal repro above is that test cut down to the duplicate-key oracle.

History

Versions tested7 rows

Introduced by LUCENE-3090 (#4163, 4fd5dceb998, svn r1104026, 2011-05-17; svn/JIRA era, no pull request). Before it, the synchronized tryCheckoutForFlush returned null while fullFlush was set, so the check and the check-out were one step; the change moved the check into nextPendingFlush, outside the monitor. LFV-1045, snapshot of 2026-11-07

Registry title
updateDocument racing commit() can leave two live documents for one key (a lost delete) and operations above the sequence number commit() returned in the commit point, because DocumentsWriterFlushControl.nextPendingFlush flushes a DWPT of the new delete queue during the running full flush
Area
index / IndexWriter full flush (DocumentsWriterFlushControl.nextPendingFlush)
Priority
Medium, rank 13: A silent, durable lost delete and broken commit cut in core updateDocument/softUpdateDocument on the default path of every release since 5.3 puts it high in Medium, but.
Impact class
silent wrong results
Impact note
Applications that call updateDocument (or softUpdateDocument) from several threads on one IndexWriter while another thread calls commit(), on the default code path (flush by RAM, default codec and directory, no opt-in feature) of every release checked from 5.3.0 to 10.6.0 and main, can get a commit point that holds two live documents for one key (the older one stays until the key is updated again, and a crash after that commit recovers it) and operations above the sequence number commit() returned; it is silent with assertions off; it shows within seconds when indexing threads outnumber CPUs, did not show in 120 s unpinned on 32 cores, and has not been shown at the default 16 MB RAM buffer.
Summary
Several threads replace documents by key with updateDocument while another thread calls commit(); you expect every commit point to hold exactly one live document per key and only the operations up to the sequence number commit() returned. Instead, an indexing thread that has just seen 'no full flush running' in nextPendingFlush can, if the commit's full flush starts at that moment, flush a buffer that belongs after the commit inside it, so the commit contains newer operations and, when the delete half of an update misses the older document, two live documents for one key. With assertions enabled it often shows instead as a tragic AssertionError in DocumentsWriter.doFlush that closes the writer.
