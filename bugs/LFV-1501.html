Lucene 11.0 keeps RegexpQuery(Term, int, int), but its third int is now match flags, and the migration notes do not say so (documentation only)

New in 11.0: 10.6.0 does not have it, and 11.0.0 would be the first release with it. A gap in the migration notes, not a bug in RegexpQuery: since #15939 the third int of RegexpQuery(Term, int, int) is match flags, not the determinize work limit, and no note says so.

Summary

The finding in 30 seconds

#

New in 11.0. On the 11.0 branch (branch_11x daa54f2e0cd3) the one test fails 1 of 1, with assertions on and off; on the 10.6.0 release it passes 1 of 1, so 10.6.0 does not have this and 11.0.0 would be the first release with it. Introduced by the merged #15939 (commit 650684e6b44). The test is a 10.x call left unchanged.

  1. Your 10.x code passes a determinize work limit as the third argument: new RegexpQuery(new Term("f", "ab"), RegExp.NONE, 20_000). Over the terms ab, AB and aB it counts 1 on 10.6.0. You rebuild it against 11.0 unchanged.
  2. You expect a compile error, as for the six other constructors that took the limit (CHANGES.txt: these overloads were "Removed"), or a line in MIGRATE.md.
  3. Instead it compiles: in 11.0 the same parameter list is (Term, int syntaxFlags, int matchFlags). 20,000 (0x4E20) has the bit of RegExp.CASE_INSENSITIVE, so the count is 3, with no message. 10,000, the default limit of 10.x, has the removed bit 0x0100 and throws IllegalArgumentException at construction.
  4. RegexpQuery is not at fault: its 11.0 javadoc names the third parameter matchFlags. Missing is one MIGRATE.md sentence saying that this constructor stays with another meaning; removing the overload would also do.

Who is affected

#

Only code that calls this one constructor directly with a work limit and moves to 11.0 without changing the call. Lucene's own code does not, and as read on 2026-11-14 neither do the default branches of Elasticsearch, OpenSearch, Solr and nrtsearch. No release is affected; 11.0.0 would be the first. Rare.

Mechanism, terms and numbers683 words

In Lucene 10.x, RegexpQuery(Term term, int flags, int determinizeWorkLimit) takes the determinize work limit as its third argument. For 11.0, #15939 removed the determinization controls: it deleted that constructor and cut the last parameter off the four-int form, which leaves RegexpQuery(Term term, int syntaxFlags, int matchFlags): the same parameter types with another meaning. Old calls to the six other constructors that took the limit stop compiling.

The notes cover the change itself: CHANGES.txt says the overloads that exposed determinization controls were "Removed", and MIGRATE.md shows how to keep an explicit limit. They do not say that the old three-int call still compiles with another meaning. That is a gap in the migration notes of the unreleased 11.0, not a bug in RegexpQuery: the 11.0 javadoc names the third parameter matchFlags, the class is @lucene.experimental, and 11.0 is a major release.

The old call on 11.0

#

Line numbers are those of main 781025d6fe32; both files are byte-identical on branch_11x.

  1. RegexpQuery.java:77-79: public RegexpQuery(Term term, int syntaxFlags, int matchFlags) forwards to the five-argument form. Its javadoc names the third parameter (:75): "@param matchFlags boolean 'or' of match behavior options such as case insensitivity". (The @param syntaxFlags text above it, :72-74, still ends with a leftover of the work-limit wording, which came onto this constructor with #15939.)
  2. RegexpQuery.java:98: the third int reaches new RegExp(term.text(), syntaxFlags, matchFlags). The two-argument form passes 0 (:64-66); it is the only caller of the three-int form in the tree.
  3. RegExp.java:532-545: a match word from 1 to ALL (0xff, :411) throws "Illegal match flag" (:537-539); a match word with bit 0x0100, the removed ASCII_CASE_INSENSITIVE (:422), throws the removed-flag message (:541-544, added by the merged #16968); everything else is OR-ed into the flags (:545).
  4. 20,000 is 0x4E20: bit 0x0200 (CASE_INSENSITIVE, :469) is set and bit 0x0100 is clear, so the regexp ab matches ab, AB and aB. Its other bits do not change these hits: 0x0400 (CASE_INSENSITIVE_RANGE, :477), 0x0020 (the syntax flag INTERVAL, :408) and two bits no flag uses (0x0800, 0x4000). 10,000 is 0x2710: bit 0x0100 is set, so construction throws.

The same parameter types in 10.6.0

#

public RegexpQuery(Term term, int flags, int determinizeWorkLimit) (RegexpQuery.java:70-82 at the tag releases/lucene/10.6.0), not deprecated; its javadoc recommends Operations#DEFAULT_DETERMINIZE_WORK_LIMIT (10000, Operations.java:63). The constructor determinized up front, so too small a limit threw TooComplexToDeterminizeException at construction.

Exposure and likelihood272 words
  • Who. Application code that calls new RegexpQuery(term, flags, limit) with a determinize work limit, as the 10.x javadoc of this constructor describes, and is rebuilt against 11.0 unchanged. A class compiled against 10.6.0 and run on the 11.0 jar shows the same effect (count 3).
  • What they get. Depending on the bits of the limit: a query that matches case-insensitively without any message (20,000; 100,000; 1,000,000), or an exception at construction (10,000 and every value with bit 0x0100; 1 to 255). The message for 10,000 names a flag the caller never passed, and its advice, "use CASE_INSENSITIVE", would turn a case-sensitive 10.x query into a case-insensitive one.
  • Not hit. Callers of the other limit-taking constructors (a compile error stops them), of the one- and two-argument forms, and anyone who writes against the 11.0 javadoc. With the constructor removed, every module's main and test sources still compile, so Lucene's own code does not make this call. As read on 2026-11-14 (not executed), the default branches of Elasticsearch, OpenSearch, Solr and nrtsearch pass their limits through the longer constructors, which stop compiling.
  • Why Low. The 11.0 javadoc names the third parameter matchFlags, the class is @lucene.experimental, the release is a major one, the notes already say how to keep a limit, the reach is one constructor, and the recommended default fails at once instead of silently.
  • A dependency. Ordinary decimal limits pass quietly because RegExp checks the match word by range, not by bit (RegExp.java:537): a separate, older finding (LFV-1315). With a stricter check most limits would throw "Illegal match flag"; exact flag words such as 512 would still pass.

Why it looks unintended

#
  • The code is intended: the 11.0 javadoc names the third parameter matchFlags. Only the notes are incomplete.
  • CHANGES.txt says the limit-taking overloads were "Removed"; six of seven stop compiling, this one does not.
  • On the merged #16968 the maintainers chose an error plus an exact MIGRATE.md sentence over a silent change for a raw 10.x flag value.
The full argument303 words

The code is intended: the determinization controls were removed on purpose, and the 11.0 javadoc documents matchFlags. The claim is only that the notes do not tell a 10.x caller of this constructor that the old call still compiles with another meaning. They do say what changed and how to keep a limit, so the gap is one sentence.

  • The notes say "Removed". A reader expects the compiler to stop an old call, and it does for six of the seven constructors that took the limit. MIGRATE.md names the removed parameter only for WildcardQuery's constructors.
  • No sign that the parameter types were kept on purpose. The thread of #15939 (description, comments, reviews and inline comments) never mentions the three-int form. The diff shows how it arose: one constructor was deleted and the last parameter was cut off its four-int neighbour.
  • The maintainers' own practice in this release. On #16968 (merged 2026-11-04; the same flag word of RegExp(String, int, int)), the author, cbuescher, raised the caller who passes a raw 10.x flag value: "you would get a different behaviour (silently ignoring the flag completely)". javanna, reviewing, listed silently ignoring it as option 3 and wrote: "I am not a fan of 3). ... Shall we throw a runtime error when 0x0100 is provided in the constructor and clearly document the exact constructor call that needs to be adjusted in the migrate guide?" That was merged: MIGRATE.md:72-79 names the constructor call, and the test added with it carries the comment "rejected instead of silently ignored" (TestRegExp.java:43-49). On #16965, merged the same day, the note got the words "the constructors are not a drop-in rename" (MIGRATE.md:65-70).
  • The trigger is ordinary. A public, documented, non-deprecated 10.x constructor, called as its javadoc says. No upstream test calls the three-int form today.
The devil's-advocate check214 words

The strongest case for "intended", in four points. (1) The 11.0 API is deliberate and documented: @param matchFlags says what the third int is, RegexpQuery is tagged @lucene.experimental, and 11.0 is a major release. (2) The change is announced: read literally, the CHANGES.txt entry is true, because the constructor that took determinizeWorkLimit is gone, and MIGRATE.md already shows how to keep an explicit limit. (3) The recommended default fails loudly on the first query, and Lucene's own tree does not make this call. (4) This int has changed its meaning before without a compile break: a state count through 8.9.0, a work limit from 8.10.0 on (LUCENE-9981), with a CHANGES.txt entry and nothing in the 9.0.0 MIGRATE.md.

Why it does not settle the matter: all of that defeats a claim that RegexpQuery is wrong, and this page makes no such claim. It does not make the notes complete: "Removed" points an upgrader at a compile error that does not come for this one form. For the same kind of caller the project chose an explicit error and an exact MIGRATE.md sentence on the merged #16968. What remains is size, not intent. A maintainer may still answer "works as designed, the notes are sufficient"; the outcome is then at most one sentence in MIGRATE.md.

Suggested fix

#

Recommended One sentence in MIGRATE.md, no code change (validated)

Notes only: one sentence in MIGRATE.md's determinization section saying that RegexpQuery(Term, int, int) stays and that its third argument is now matchFlags: drop the old third argument, or keep a limit with the determinize() and AutomatonQuery form shown there. Alternative: remove the overload, so the old call stops compiling. Both were run.

LFV-1501, snapshot of 2026-11-20

Registry title
Lucene 11.0 keeps RegexpQuery(Term, int, int), but its third int is now match flags instead of the determinize work limit (since #15939), and neither CHANGES.txt nor MIGRATE.md says so: an unchanged 10.x call still compiles and either matches case-insensitively without an error (limit 20,000: 3 hits instead of 1) or throws IllegalArgumentException about a flag the caller never passed (limit 10,000) (documentation defect of the unreleased 11.0; the 11.0 javadoc names the third parameter matchFlags, and the constructor treats it as that)
Area
release notes (lucene/CHANGES.txt 11.0.0, lucene/MIGRATE.md 10.x -> 11.0) x search / RegexpQuery constructors (GITHUB#15939; the flag word is checked in util/automaton RegExp)
Priority
Low, rank 1430: A gap in the release and migration notes of the unreleased 11.0 (branch_11x and main only): RegexpQuery(Term, int, int) keeps its 10.x parameter types but now reads the third int as match flags, so an unchanged 10.x call that passes a determinize work limit still compiles and, depending on the value, matches case-insensitively without an error (20,000), throws an exception about a flag the caller never passed (10,000, the 10.x default) or changes no hit of a plain regexp such as ab (2,000,000), and neither CHANGES.txt nor MIGRATE.md says so. It is Low because the 11.0 javadoc names the third parameter matchFlags and the constructor treats it as that, on an experimental class in a major release, only direct callers of this one overload who pass a limit are hit, and such calls were found only in a few small public projects, none in Lucene's own code or in Elasticsearch, OpenSearch, Solr or nrtsearch.
Impact class
minor
Impact note
Only code that calls the public constructor RegexpQuery(Term, int, int) with a determinize work limit as its third argument, as the 10.x javadoc describes, and is rebuilt against 11.0 unchanged (or runs as 10.x-compiled bytecode on the 11.0 jar) is hit, and only on unreleased branch_11x and main: the call still compiles and the limit is read as match flags, so depending on its bits the query matches case-insensitively without an error (20,000: 3 hits instead of 1) or with optional syntax switched on, construction throws IllegalArgumentException about a flag the caller never passed (10,000, the default the 10.x javadoc recommends, and every value with bit 0x0100 set; 1 to 255 give 'Illegal match flag'), or the hits of a plain regexp such as ab stay as they were (2,000,000) [exec]; the 11.0 javadoc names the third parameter matchFlags and the constructor treats it as that, so what is missing is one sentence in the notes (MIGRATE.md says how to keep a limit, but not that this call still compiles with another meaning); no setting, scale or index data is involved, -ea and -da alike; Lucene's own code and the default branches of Elasticsearch, OpenSearch, Solr and nrtsearch contain no three-argument call (by reading their sources), and no release is affected.
Summary
Your Lucene 10.x code builds a regular-expression query with new RegexpQuery(term, RegExp.NONE, 20_000), where the third argument is the determinize work limit, and you rebuild it against Lucene 11.0 without changes. You expect a compile error, as for the other constructors that took that limit and that the 11.0 change list says were removed, or a sentence in MIGRATE.md. Instead the call still compiles and 11.0 reads the number as match flags, so 20,000 quietly makes the query case-insensitive (3 hits instead of 1 for the terms ab, AB and aB) and 10,000, the default the 10.x javadoc recommends, throws IllegalArgumentException about a removed flag you never passed. The 11.0 javadoc names the third parameter matchFlags, and the constructor treats it as that, so what is missing is one sentence in the migration notes, or the removal of this overload.
