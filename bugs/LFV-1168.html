PackedInts writes wrong bytes when it encodes an int[] at 33 to 64 bits per value

PackedInts' int[] to byte[] encoder writes wrong bytes at 33 to 64 bits per value: it shifts an int, and Java takes int shift counts mod 32, so at 64 bits the value 1 becomes 4,294,967,297. Latent, as no Lucene code encodes int[] this way; since 4.2.0.

The finding in 30 seconds

#

At more than 32 bits per value, the int[] to byte[] encoder cuts each value into bytes with int shifts of 32 or more. Java wraps those counts around (mod 32), so bytes that should be zero get copies of the value's low bits.

Background in three steps

#
  1. PackedInts stores numbers with a fixed number of bits each ("bits per value", 1 to 64), back to back in big-endian blocks. The class is @lucene.internal, but PackedInts.getEncoder(format, version, bitsPerValue) is public.
  2. An encoder reads long[] or int[] values and writes long[] or byte[] blocks. At 64 bits per value one value fills one 8-byte block: the value 1 is 00 00 00 00 00 00 00 01.
  3. In Java, shifting an int uses only the shift count mod 32: 1 >>> 32 is 1, not 0. A long shift uses the count mod 64.

The finding, step by step

#
  1. Get the PACKED encoder for 64 bits per value, PackedInts.getEncoder(Format.PACKED, VERSION_CURRENT, 64), and encode the int[] {1} into its 8-byte block.
  2. You expect 00 00 00 00 00 00 00 01, the 64-bit block of 1: the same encoder writes exactly that for long[] {1L}, and its int[] to long[] method gives the block 1.
  3. You get 00 00 00 01 00 00 00 01, which reads back as 4,294,967,297 (2^32 + 1). No exception, with assertions on or off.
  4. Why: the loop shifts an int right by 56, 48, 40, 32, 24, 16, 8 and 0 bits. Java uses int shift counts mod 32, so they act as 24, 16, 8, 0, 24, 16, 8, 0: the four high bytes repeat the four low ones.
  5. Every width from 33 to 64 bits writes some value wrong; widths 1 to 32 are fine. Lucene's non-test code only encodes long[], so no index is affected.

Who is affected

#

Only code outside Lucene that calls the internal PackedInts.getEncoder itself with 33 to 64 bits per value and encodes an int[] into a byte[]. It silently gets wrong bytes (at 64 bits, for every non-zero value). Lucene's own writers all encode long[], so no index, codec or query is affected.

Mechanism, terms and numbers568 words

PackedInts.getEncoder(Format.PACKED, VERSION_CURRENT, bitsPerValue) accepts any width from 1 to 64, and its encode(int[] values, .., byte[] blocks, ..) writes wrong bytes at every width from 33 to 64: the int[] {1} at 64 bits per value becomes {0, 0, 0, 1, 0, 0, 0, 1} (4294967297) instead of {0, 0, 0, 0, 0, 0, 0, 1}, which the same encoder writes for long[] {1L}. The method keeps the value in an int (BulkOperationPacked.java:249) and cuts it into bytes with v >>> bits (:258, :261); at these widths bits reaches 32 to 63, and Java takes an int shift count mod 32.

PackedInts is @lucene.internal, and every Lucene writer that uses these encoders passes long[], so no index, codec or query is affected: only code that calls the encoder directly with int[] input at such a width. LUCENE-4726 (4.2.0, 2013) introduced the int shift when it replaced a long-based implementation that had no int shift. The fix zero-extends once and then shifts a long, like the loop of the long[] variant. Related row: LFV-1164, a different defect in the sibling int[] to long[] method (BulkOperationPacked.java:209).

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/packed/)

#
  1. getEncoder (PackedInts.java:657-660) returns BulkOperation.of(format, bitsPerValue); for PACKED at 25 to 64 bits that is the generic BulkOperationPacked (BulkOperation.java:50, :58, :89).
  2. encode(int[] values, .., byte[] blocks, ..) (BulkOperationPacked.java:243-269) reads final int v = values[valuesOffset++]; (:249) and flushes it byte by byte: (byte) (nextBlock | (v >>> bits)) (:258), then (byte) (v >>> bits) (:261) while bits counts down by 8. :249 is the fix site.
  3. For an int left operand Java uses only the five low bits of the shift count (JLS 15.19). At 33 to 64 bits per value bits reaches 32 to 63, so v >>> 32 is v, v >>> 40 is v >>> 8, and so on.
  4. At 64 bits the counts 56, 48, 40, 32, 24, 16, 8, 0 act as 24, 16, 8, 0, 24, 16, 8, 0: the high four bytes repeat the low four, so every non-zero int is written wrong. For 1 only the count-32 shift is non-zero, which sets byte 3.
  5. From 33 to 39 bits a count of 32 or more occurs only at some positions of a block ((bitsPerValue - 32) eighths of them; at 33 bits, only for the last of the 8 values in each 33-byte block). From 40 bits up it occurs at every position: a value's first count is bitsPerValue - bitsLeft (:257) with bitsLeft between 1 and 8, so at least 32. Whether a value comes out wrong then depends on its bits. For the value 1 only a count of exactly 32 matters: probes find it written wrong at exactly one position per block, the last, at every width from 33 to 64, and at none from 1 to 32. The value 0 is always right.
  6. The siblings are right for this input: encode(long[] -> byte[]) (:215-241) runs the same loop on a long, and encode(int[] -> long[]) (:192-213) zero-extends with & 0xFFFFFFFFL (its own sign-extension slip at :209 is the related row LFV-1164).
  7. The number of bytes written is right and nothing is written outside the array; only the content is wrong.
Exposure and likelihood149 words
  • Who: application code that calls the public static PackedInts.getEncoder(Format.PACKED, .., bitsPerValue) (the class is @lucene.internal, PackedInts.java:32) with 33 to 64 bits per value, then encode(int[], .., byte[], ..).
  • Not hit: Lucene itself. The non-test in-tree PACKED encoder users all encode long[]: PackedWriter.java:42/:83, AbstractBlockPackedWriter.java:120/:129, Packed64.java:157/:176 and the backward-codecs LegacyDirectWriter.java:65/:102. The only int[] caller is TestPackedInts.testEncodeDecode (TestPackedInts.java:882, :909), and only at 32 bits per value or less (:880, :907).
  • Effect: silently wrong data: no exception, and the method's own assert (:250) passes; whatever reads the bytes back gets a larger number (1 becomes 4294967297).
  • Scale: one value is enough. At 64 bits every non-zero value is wrong; from 33 to 39 bits only some positions of each block can be hit, from 40 bits every position can be.

Why it looks unintended

#
  • Nothing limits the width: getEncoder accepts 1 to 64 bits, the javadoc states no limit, and the method's assert admits any int at 32+ bits.
  • Its siblings, long[] to byte[] and int[] to long[], encode 1 correctly.
  • 4.1.0 was right; a 2013 byte-alignment change introduced the int shift; tests check int[] only up to 32 bits.
The full argument203 words
  • Contract. The Encoder.encode(int[], .., byte[], ..) javadoc (PackedInts.java:339-349): "Read iterations * valueCount() values from values, encode them and write 8 * iterations * blockCount() blocks into blocks", with no width limit. getEncoder (:649-660) takes any width; Format.PACKED is "Compact format, all bits are written contiguously." (:73); the class stores "unsigned long values" (:28).
  • The method's own assert (BulkOperationPacked.java:250), PackedInts.bitsRequired(v & 0xFFFFFFFFL) <= bitsPerValue, admits every int at widths of 32 and more.
  • History. 4.0.0 and 4.1.0 write the correct bytes for the same call. LUCENE-4726 (6e94f431523, 2013-01-29), "Make PackedInts encoding from/to byte byte-aligned", replaced a long-based implementation that had no int shift (it zero-extended each value with & 0xFFFFFFFFL, except in its block-crossing branch, which had the separate sign-extension slip of LFV-1164) with the int loop, and in the same commit removed the bitsPerValue > 32 check from decode(byte[] -> int[]). Nothing in the issue or commit restricts int[] widths.
  • Tests. TestPackedInts.testEncodeDecode (TestPackedInts.java:814) loops over 1 to 64 bits but checks the int[] paths only under if (bpv <= 32) (:864, :880, :896, :907), so the wide case was never tested.
The devil's-advocate check233 words

Strongest case for "intended": int[] input above 32 bits is a pointless internal corner. On #5389 (LUCENE-4322), Adrien Grand wrote on 2012-08-23 "maybe we could first stop specializing encode for int[] values when bitsPerValue > 32. I can't think of a use-case this method could be useful to", and Michael McCandless replied "Still if we have pointless code (int[] values with bpv > 32) we should remove it." decode(long[] -> int[]) throws UnsupportedOperationException above 32 bits (BulkOperationPacked.java:120-126), and no Lucene caller uses an int[] above 32 bits per value. An independent reviewer from another model family (OpenAI GPT-5.6, refute lens; run on the earlier main ea57360912ed, where the three files involved are byte-identical) reproduced the defect, agreed on cause and fix, rated the intended-behaviour argument weak, and still returned "not real" on this scope ground.

Why it fails: those remarks are from August 2012, five months before the defect existed, when the encoder was still correct; they propose removing the path, not accepting wrong output, and nothing was removed or guarded. The long[] -> int[] decoder refuses because an int cannot hold a wider value; writing an int into a wider field has no such problem. The call is legal through the public getEncoder and returns silently wrong data rather than a rejection. Verdict: not intended. The argument is about reach, hence priority Low; a maintainer may prefer fix B.

Suggested fix

#

Recommended A. Zero-extend once and shift a long (validated)

Zero-extend each value once and then shift a long, like the loop of the long[] variant: final long v = values[valuesOffset++] & 0xFFFFFFFFL; plus two casts. The repro passes with assertions on and off, TestPackedInts passes, and the checksum of the regenerated packed sources needs a one-line refresh.

final long v = values[valuesOffset++] & 0xFFFFFFFFL;
assert PackedInts.bitsRequired(v) <= bitsPerValue;
// ...
nextBlock |= (int) (v << (bitsLeft - bitsPerValue));
// ...
nextBlock = (int) ((v & ((1L << bits) - 1)) << bitsLeft);
All options and trade-offs2 options · 385 words

Two options. A was validated with gradle in a scratch worktree of 5adff78bb168; B is by reading. A fixes this site only; LFV-1164's site (BulkOperationPacked.java:209) needs its own fix. B closes the int[] encode path above 32 bits for both rows. BulkOperationPacked.java is checksum-tracked by the regeneratePacked64SingleBlock task, so either patch also refreshes lucene/core/src/generated/checksums/regeneratePacked64SingleBlock.json.

A. Zero-extend once and shift a long (validated) (recommended)

#

In encode(int[] -> byte[]) (BulkOperationPacked.java:249-265):

final long v = values[valuesOffset++] & 0xFFFFFFFFL;
assert PackedInts.bitsRequired(v) <= bitsPerValue;
// ...
nextBlock |= (int) (v << (bitsLeft - bitsPerValue));
// ...
nextBlock = (int) ((v & ((1L << bits) - 1)) << bitsLeft);

Trade-offs

  • The same loop as the long[] sibling; one zero-extension per value.
  • Output at widths 1 to 32 is unchanged: every shift count there is below 32, and the casts keep the same low bits.
  • Leaves encode(int[] -> long[]) (LFV-1164) to its own fix.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: on stock the repro fails with assertions on and off; with A it passes, on and off.
  • With A: TestPackedInts and the repro, 29 tests, 3 skipped, 0 failures.
  • regeneratePacked64SingleBlockChecksumCheck fails on the patch alone ("Checksums mismatch for generated resources"); ./gradlew :lucene:core:regeneratePacked64SingleBlock rewrites only the BulkOperationPacked.java checksum line (the regenerated BulkOperation*.java are unchanged), and the check then passes.
  • checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest for lucene/core pass with the fix and the test file.
  • Not run: the full lucene/core suite.

B. Reject bitsPerValue > 32 for int[] encoding

#

Throw UnsupportedOperationException at the top of both int[] encode overloads of BulkOperationPacked when bitsPerValue > 32, as decode(long[] -> int[]) already does (:123-126); optionally restore the same check in decode(byte[] -> int[]), which LUCENE-4726 removed. The specialized BulkOperationPacked1 to 24 and the single-block operations (at most 32 bits) never see such widths.

Trade-offs

Closes the path for this row and LFV-1164 in one change, follows the 2012 remarks of Adrien Grand and Michael McCandless on #5389, and makes misuse loud. But it changes behaviour for any external caller that encodes int[] at a wide width, and the regression test becomes an expectThrows. TestPackedInts.testEncodeDecode uses the int[] paths only up to 32 bits, so it is unaffected. By reading, not run.

Downstream note

#

Relevant only to downstream code that packs int[] values at more than 32 bits each through the internal PackedInts encoder; no Lucene index, codec or query path does.

How it was found

#

Semi-formal: a proof-obligation audit of PackedInts.Encoder required encode(int[] -> byte[]) to write the bytes encode(long[] -> byte[]) writes for the same non-negative values. The int shift breaks that above 32 bits per value, and a one-test JUnit repro on stock main witnessed it.

The method in full81 words
  • Obligation: for every width getEncoder accepts and every non-negative value, the int[] and long[] byte encoders write the same bytes, as Format.PACKED ("all bits are written contiguously") and the method's assert imply.
  • Finding: the int[] variant holds the value as an int (BulkOperationPacked.java:249) and shifts it by counts up to 63 (:258, :261).
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
