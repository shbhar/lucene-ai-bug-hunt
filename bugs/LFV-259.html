PerFieldSimilarityWrapper does not forward computeQueryTermWeight, so a BM25 or StableTfl k3 setting has no effect behind a per-field similarity

On unreleased main, BM25's opt-in k3 makes a word repeated in a query count less than linearly, but behind a PerFieldSimilarityWrapper, the documented per-field route, it is silently ignored: apple apple gets boost 2.0 instead of 1.78, so one document scores 0.2615 instead of 0.2325.

The finding in 30 seconds

#

BooleanQuery turns a repeated clause into one boosted clause and asks the searcher's similarity for the boost. With k3, BM25Similarity answers 1.78 for a term repeated twice. A PerFieldSimilarityWrapper never passes the question on to the field's similarity, because the hook has no field parameter, so it answers 2.0.

Background

#
  1. k3 (new, unreleased). new BM25Similarity(k1, b, discountOverlaps, k3) with k3 ≥ 0 weighs a term that appears qtf times in a query ((k3 + 1) × qtf) / (k3 + qtf) instead of qtf: with k3 = 7, two repeats weigh 1.78 instead of 2. It is off by default (k3 = -1). StableTflSimilarity has the same parameter.
  2. Where k3 is applied. BooleanQuery.rewrite merges equal unboosted SHOULD or MUST clauses into one clause and gets its boost from searcher.getSimilarity().computeQueryTermWeight(qtf). That hook has no field parameter; its default returns qtf.
  3. Per-field similarities. PerFieldSimilarityWrapper is how Lucene uses a different similarity, or different parameter values, per field: a subclass implements get(field). Search servers built on Lucene install such a subclass as the searcher's similarity.

The finding, step by step

#
  1. Create new BM25Similarity(1.2f, 0.75f, true, 7f) (k3 = 7) and install it through a PerFieldSimilarityWrapper whose get(field) returns it for every field. Index one document body: apple and search apple OR apple (two equal SHOULD clauses).
  2. You expect the score of the bare similarity: with k3 = 7 a term repeated twice weighs (7 + 1) × 2 / (7 + 2) = 16/9 = 1.78, and the document scores 0.2325.
  3. Instead it scores 0.2615: the merged clause got the linear boost 2.0, exactly as with k3 off. No error, with assertions on or off.
  4. Why: BooleanQuery merges the duplicates and asks the searcher's similarity, here the wrapper, for the weight via computeQueryTermWeight(2). That hook has no field parameter, and the wrapper forwards only computeNorm and scorer to get(field), so it answers with the linear default.
  5. Rankings change too: in a five-document index, apple repeated 5 times plus banana puts an apple document on top instead of the banana one. Which documents match never changes.

Who is affected

#

Applications on main or branch_11x (unreleased 11.0.0) that opt into k3 on BM25Similarity or StableTflSimilarity and install it through a PerFieldSimilarityWrapper. Queries that repeat an unboosted term on one field, such as QueryParser text w w w, are scored as if k3 were off. A bare similarity on the searcher is not affected.

Mechanism, terms and numbers495 words

#15818 (unreleased, 11.0.0) added query-side term frequency saturation: BM25Similarity built with k3 >= 0 weighs a term repeated qtf times in a query ((k3 + 1) * qtf) / (k3 + qtf) instead of qtf; #16243 gave StableTflSimilarity the same k3. The weighting is applied in BooleanQuery.rewrite, which merges equal unboosted clauses and takes the merged clause's boost from indexSearcher.getSimilarity().computeQueryTermWeight(qtf).

That hook has no field parameter and defaults to linear. PerFieldSimilarityWrapper forwards only computeNorm and scorer to get(field) and inherits the default. So behind a wrapper, even one that returns the same k3 similarity for every field, k3 does nothing: scores and ranking are exactly those of k3 disabled, with no error or warning. The matching set is unchanged. No release has the bug; main and branch_11x do.

The code (main 645d4fe14a20)

#
  1. Duplicates are merged. BooleanQuery.java:438-447 deduplicates SHOULD clauses when minimumNumberShouldMatch <= 1, :449-455 MUST clauses; both call deduplicateClauses (:714-758).
  2. The searcher's similarity is asked. :734 Similarity similarity = indexSearcher.getSimilarity();. When no occurrence has an explicit boost, the merged clause's boost is similarity.computeQueryTermWeight(Math.toIntExact(Math.round(boostSum))) (:743-746); with explicit boosts it stays the linear sum, by design. This is the hook's only production caller.
  3. The hook. Similarity.java:163-177: computeQueryTermWeight(int queryTermFrequency), no field parameter, @lucene.experimental, default return (float) queryTermFrequency; (:175-177), "Subclasses may override this to apply saturation (e.g. BM25's k3 parameter)".
  4. The overrides. BM25Similarity.java:130-136 and StableTflSimilarity.java:158-164 return ((k3 + 1f) * qtf) / (k3 + qtf) when k3 >= 0, else qtf. k3 is off by default (BM25Similarity.java:79-81 passes -1f; StableTflSimilarity.java:65-66 DEFAULT_K3 = -1f).
  5. The wrapper. PerFieldSimilarityWrapper.java:31-48 overrides only computeNorm (:36-39) and scorer (:41-44), both final delegations to get(field). It does not override computeQueryTermWeight, so step 2 lands on the linear default and never reaches the per-field BM25Similarity.

The numbers of the minimal repro

#

One document, so idf = ln(1 + 0.5 / 1.5) = 0.2877 and the tf part is 1 / (1 + 1.2) = 0.4545: base score 0.13076. Bare k3 similarity: × 16/9 = 0.23247036. Behind the wrapper: × 2 = 0.26152915, a ratio of 1.125.

The same defect elsewhere (executed by the verifiers)

#
  • Duplicate MUST clauses: +(f:w)^2.0 +f:x instead of +(f:w)^1.8 +f:x (k3 = 8).
  • Classic QueryParser text w w w: (f:w)^3.0 instead of (f:w)^2.4545455 (k3 = 8).
  • StableTflSimilarity with k3: (f:w)^2.0 instead of (f:w)^1.7777778.

  • Ranking: documents A apple, B banana and three fillers apple filler (k3 = 7). For apple repeated n times plus banana, the bare similarity and a wrapper that forwards the hook rank B first for n = 2 to 6; the stock wrapper ranks A first for n = 5 and 6.
Exposure and likelihood248 words
  • Who. Users of main or branch_11x who build BM25Similarity or StableTflSimilarity with k3 >= 0 (off by default) and set it through a PerFieldSimilarityWrapper, the documented route for per-field similarities and parameters (Similarity.java:62-66; CHANGES.txt:16128-16130, 4.0.0-ALPHA: "implement PerFieldSimilarityWrapper with your per-field logic").
  • Trigger. A BooleanQuery with a repeated unboosted SHOULD clause (with minimumNumberShouldMatch <= 1) or MUST clause on one field that reaches the duplicate-merging step (earlier rewrite rules can replace the query first; for example a MUST clause that is also MUST_NOT becomes MatchNoDocsQuery): query-parser text that repeats a word, or programmatic queries built from verbose text, the queries k3 is meant for. Any index size; one document is enough.
  • Effect. Silent wrong results: scores, and so ranking, equal the k3-disabled ones. Nothing throws. The matching set does not change, and no score goes above the k3-disabled score, because k3 can only lower a weight. The repeated term is over-weighted by qtf / w(qtf): 1.125 for 2 repeats with k3 = 7, 6.44 for 50 repeats with k3 = 8.
  • Not claimed. A repeated clause that spans several fields (for example a duplicated DisjunctionMaxQuery) has no single correct delegate. MultiSimilarity and the test framework's AssertingSimilarity and RandomSimilarity also inherit the linear default; they are related, but what MultiSimilarity should return is unclear and the others are test-only.
  • How likely: plausible once k3 is on: the wrapper is the standard per-field route, while users who set a bare similarity never hit it.

Why it looks unintended

#
  • The k3 javadoc unconditionally promises the saturated weight for repeated query terms; the wrapper is documented for "field-specific parameter values".
  • Lucene fixed the same trap as a bug before: LUCENE-7395 (6.2) made the wrapper forward the field-less queryNorm and coord.
  • No discussion in #15818 or #16243 and no test chose this; IDFValueSource already unwraps the wrapper per field.
The full argument261 words
  • The k3 contract. BM25Similarity.java:44-46: "When duplicate terms appear in a query, their boost is computed as ((k3 + 1) * qtf) / (k3 + qtf) instead of linear summing." StableTflSimilarity.java:103-105 says the same. No javadoc, CHANGES or MIGRATE text says k3 needs a bare similarity on the searcher.
  • The wrapper's contract. PerFieldSimilarityWrapper.java:24-27: subclasses implement get(String) "to return an appropriate Similarity (for example, using field-specific parameter values) for the field". A wrapper whose get() returns S for every field should behave like S, the argument of LUCENE-4559 (#5625).
  • Precedent. In 6.x the wrapper did not forward the field-less queryNorm and coord; LUCENE-7395 / SOLR-9315 fixed it under 6.2.0 Bug Fixes (CHANGES.txt:9006-9008, "Fix PerFieldSimilarityWrapper to also delegate query norm and coordination factor using a default similarity added as ctor param", Uwe Schindler and Sascha Markus); jpountz called the old default "trappy" on #8448. Those hooks were removed in 7.0; computeQueryTermWeight is the first field-less hook added to Similarity since.
  • In-tree convention. IDFValueSource.asTFIDF (lucene/queries/.../IDFValueSource.java:62-72) loops while (sim instanceof PerFieldSimilarityWrapper pfsw) sim = pfsw.get(field); to reach the field's similarity.
  • No decision, no test. The #15818 thread (9 comments, 13 inline review comments) and #16243 never mention wrappers or per-field configuration. The k3 tests use a bare similarity (TestBooleanRewrites.java:1137-1171). testDefaultSimilarityPreservesLinearDedup (:1192) runs through the test framework's wrapper chain but passes either way, because no RandomSimilarity member enables k3.
  • Context. On #14433 (2025), rmuir wrote in review that a field-less Similarity method is "impossible for someone to implement correctly if they customize just one field" (a different, unmerged method).
The devil's-advocate check160 words

The strongest case: the hook is documented as field-less with a linear default and "Subclasses may override this"; PerFieldSimilarityWrapper only delegates the methods that carry a field; the hook is not final, so a wrapper subclass can forward it itself (that workaround works in the verifiers' controls); and both APIs are @lucene.experimental on unreleased code. A maintainer could answer "document that wrappers must override it".

Why it fails: the k3 promise has no condition and nothing documents the override requirement; the project treated the same non-forwarding of field-less hooks as a bug in LUCENE-7395; a field-less override cannot express the per-field parameters the wrapper exists for, so it only works when every field shares one k3; and no discussion or test shows the gap was considered. The evidence supports raising it as a pre-release bug, but it cannot show what the maintainers intend: they may still decide that a javadoc note or a wrapper override is the intended resolution.

Suggested fix

#

Recommended A field-aware hook that the wrapper forwards

Give the hook a field: add Similarity#computeQueryTermWeight(String field, int qtf) (default: the field-less method), forward it in PerFieldSimilarityWrapper to get(field), and let BooleanQuery pass the field when a clause it weighs targets one field. The repro passes, and so do core's search tests (2,339) and lint.

// PerFieldSimilarityWrapper
@Override
public final float computeQueryTermWeight(String field, int queryTermFrequency) {
  return get(field).computeQueryTermWeight(field, queryTermFrequency);
}

// BooleanQuery.deduplicateClauses: one field -> the field-aware method
return fields.size() == 1
    ? similarity.computeQueryTermWeight(fields.iterator().next(), queryTermFrequency)
    : similarity.computeQueryTermWeight(queryTermFrequency);

A field-aware hook that the wrapper forwards (validated by the checks) (recommended)

#

Similarity gets computeQueryTermWeight(String field, int queryTermFrequency), which by default returns the field-less method, so BM25Similarity and StableTflSimilarity need no change. PerFieldSimilarityWrapper overrides it as a final delegation to get(field), like computeNorm and scorer. BooleanQuery.deduplicateClauses, wherever it calls the hook today, collects that clause's fields with a QueryVisitor and calls the field-aware method when there is exactly one (3 files, +44/-1). As on stock main, once an occur type has any duplicate, every distinct unboosted clause of that type gets its weight from the hook (singletons with qtf = 1 included), so this covers all of them, not only the merged ones.

// PerFieldSimilarityWrapper
@Override
public final float computeQueryTermWeight(String field, int queryTermFrequency) {
  return get(field).computeQueryTermWeight(field, queryTermFrequency);
}

// BooleanQuery.deduplicateClauses: one field -> the field-aware method
return fields.size() == 1
    ? similarity.computeQueryTermWeight(fields.iterator().next(), queryTermFrequency)
    : similarity.computeQueryTermWeight(queryTermFrequency);

Trade-offs

  • Per-field k3. Different fields can use different k3 values, which is what the wrapper is for.
  • API. One new @lucene.experimental method. Since the hook is unreleased, a variant replaces the field-less signature instead of adding an overload; the multi-field case then needs a defined argument. That variant was not run.
  • Multi-field clauses. A merged clause over several fields keeps the field-less path, as today: linear behind the stock wrapper, or whatever a wrapper subclass's own override of computeQueryTermWeight(int) returns.
  • Field detection. The field comes from QueryVisitor: TermQuery reports it, but a query that reports no field (such as MatchAllDocsQuery) or a custom query with incomplete visitor information falls back to the field-less path.
  • Existing overrides. A wrapper subclass that already overrides the field-less hook (the workaround below) is bypassed for single-field clauses, because the new wrapper method is final and goes to get(field); with the usual workaround body the result is the same.
  • Cost. Once an occur type has duplicates, one QueryVisitor walk per distinct unboosted clause of that type, only on the dedup path; no benchmark was run.

Resolve the wrapper in BooleanQuery, no new API (validated by the checks)

#

For each clause whose weight comes from the hook and that targets a single field (found with a QueryVisitor, as in A), BooleanQuery does what IDFValueSource.asTFIDF does, while (similarity instanceof PerFieldSimilarityWrapper perField) similarity = perField.get(field);, before calling computeQueryTermWeight(qtf) (BooleanQuery.java only, +25/-1).

Trade-offs

No public API change and the smallest diff, but BooleanQuery special-cases one Similarity subclass, and a custom delegating similarity that does not extend PerFieldSimilarityWrapper is not resolved. It also unwraps past a wrapper subclass's own override of the field-less hook, so the workaround below is bypassed for single-field clauses (same result with the usual workaround body), and the QueryVisitor fallback of A applies.

A default similarity, as in LUCENE-7395 (not run)

#

Give PerFieldSimilarityWrapper a default similarity (constructor argument) and forward the field-less computeQueryTermWeight(int) to it, as 6.2 did for queryNorm and coord.

Trade-offs

Simple and precedented, but one k3 for all fields, and every subclass must supply the default or keep today's behaviour.

Documentation only, plus the workaround (not a fix)

#

A javadoc note that wrappers must forward the hook. Until a fix lands, users can override it in their wrapper subclass: public float computeQueryTermWeight(int qtf) { return bm25.computeQueryTermWeight(qtf); } (the verifiers' forwarding controls pass).

Trade-offs

Works only when every field shares one k3, and leaves the trap for the next user.

Downstream note

#

Elasticsearch, OpenSearch and Solr each install a PerFieldSimilarityWrapper subclass as the searcher's similarity, so a k3 setting they expose on Lucene 11 would be inert unless the wrapper forwards the hook (read from their source, not tested).

How it was found

#

While modelling how BooleanQuery boosts duplicate clauses, the finder read the #15818 change and saw that the new hook has no field and that PerFieldSimilarityWrapper does not forward it. A differential JUnit, wrapped versus bare similarity on the stock jars, confirmed it.

The method in full109 words

Method: non-formal (code reading plus a differential test). The hunt unit covered the similarities, with the #15818 change as its main target.

  • Reading. The duplicate-clause boost path: deduplicateClauses, its only call of computeQueryTermWeight, and every Similarity subclass that overrides or inherits it.
  • Differential. The same index and query on a searcher with the bare BM25Similarity(k3 = 7) and on one with a PerFieldSimilarityWrapper returning that instance: rewrites ^1.7777778 versus ^2.0, scores 0.5601189 versus 0.63013375 (two documents), failing with assertions on and off, and 10 of 10 iterations with assertions on.
  • Minimal repro. The test above is that test cut down to one document and one assertion.

LFV-259, snapshot of 2026-11-06

Registry title
PerFieldSimilarityWrapper does not forward Similarity#computeQueryTermWeight, so a BM25Similarity or StableTflSimilarity k3 (query-term saturation) setting silently has no effect behind a per-field wrapper
Area
search / similarities (PerFieldSimilarityWrapper, Similarity#computeQueryTermWeight) and BooleanQuery duplicate-clause rewrite
Priority
Low, rank 726: In the unreleased opt-in k3 setting, PerFieldSimilarityWrapper silently drops k3, the same feature family as LFV-103.
Impact class
silent wrong results
Impact note
Only applications on unreleased main (11.0.0) that opt into k3 >= 0 on BM25Similarity or StableTflSimilarity and install it through a PerFieldSimilarityWrapper (the documented way to set per-field similarity parameters; Elasticsearch, OpenSearch and Solr each install a PerFieldSimilarityWrapper subclass as the searcher similarity [read]) are hit, on every BooleanQuery with a repeated unboosted SHOULD or MUST clause (for example classic QueryParser text 'w w w' or two equal TermQuery clauses), at any scale; the repeated term is weighted linearly, exactly as with k3 disabled, so k3 is a silent no-op: scores change (by a factor of 4.8 for a term repeated 50 times), never beyond the k3-disabled score, the set of matching documents does not change, and no verifier showed two documents swapping rank.
Summary
You configure BM25Similarity with its opt-in k3 parameter (new BM25Similarity(1.2f, 0.75f, true, 7f)), whose javadoc promises that a term repeated in a query is weighted ((k3 + 1) * qtf) / (k3 + qtf) instead of linearly, and you install it through a PerFieldSimilarityWrapper, the documented way to use per-field similarities, even one whose get() returns that same instance for every field. You expect the query 'apple apple' to score as it does with the bare BM25Similarity, where BooleanQuery's duplicate-clause rewrite gives (body:apple)^1.7777778. Instead the rewrite asks the wrapper, which does not forward Similarity#computeQueryTermWeight and inherits its linear default, so the query becomes (body:apple)^2.0 and the document scores 0.63013375 instead of 0.5601189; StableTflSimilarity's k3 is ignored the same way.
