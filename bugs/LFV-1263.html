A failed open of the default terms dictionary carries a spurious suppressed NullPointerException

On main, when a segment's terms files fail to open (say openInput throws for the .tip file), the reader's cleanup calls its own close(), which clears a map the constructor has not assigned yet. The right IOException still arrives, but with a suppressed NullPointerException attached; no release is affected.

The finding in 30 seconds

#

close() is safe on a half-built reader except for one line: fieldMap.clear() in its finally, on a field the constructor assigns only after all three files are open and checked. So every failed open throws an NPE inside its own cleanup, and the cleanup attaches it to the real error.

Background in three steps

#
  1. With the default codec, a segment's terms dictionary is three files: .tim (the terms), .tip (their index) and .tmd (metadata). Lucene103BlockTreeTermsReader opens them, in that order, whenever a reader, a merge or CheckIndex opens the segment.
  2. If anything fails during that open, the constructor cleans up by calling its own close(), so the files already open get closed again.
  3. Since #14633 (on main, so also branch_11x), whatever that cleanup throws is attached to the real exception as a suppressed exception, so that real close failures are not lost.

The finding, step by step

#
  1. You index one document (StringField f = "a") with the default codec, compound files off, and call DirectoryReader.open through a FilterDirectory whose openInput throws IOException("simulated") for the .tip file, as a "Too many open files" error would.
  2. You expect DirectoryReader.open to throw that IOException with 0 suppressed exceptions: closing the one file already open, .tim, succeeds.
  3. Instead the IOException carries 1 suppressed exception: NullPointerException: Cannot invoke "IntObjectHashMap.clear()" because "this.fieldMap" is null.
  4. Why: the constructor's cleanup calls close(), which closes the open files and then, in a finally, runs fieldMap.clear(). The constructor assigns fieldMap only near its end, after every file is open and checked, so it is still null.
  5. Only main and branch_11x: since #14633 the cleanup attaches whatever close() throws; every release through 10.6.0 still swallows it. Diagnostics only, no data effect.

Who is affected

#

Anyone on main or branch_11x with the default codec whose reader open, NRT reopen, merge or CheckIndex fails while opening a segment's terms files: too many open files, a missing file, a corrupt terms file. The trace then shows a Lucene NPE next to a disk problem. Upstream CI printed it 15 times (2025-05-31 to 2026-11-04). No release is affected.

Mechanism, terms and numbers470 words

When the default terms dictionary of a segment fails to open (an IOException such as "Too many open files" or a missing file on .tim, .tip or .tmd, or a header, footer or checksum CorruptIndexException), the constructor of Lucene103BlockTreeTermsReader cleans up by passing this to IOUtils.closeWhileSuppressingExceptions. close() closes the inputs (null-tolerant) and then runs fieldMap.clear() in a finally with no null check, but the constructor assigns fieldMap only near its end, after all the file opens and checks. So close() throws a NullPointerException, and the helper attaches it to the real exception as suppressed.

The caller still gets the right exception, and the files are closed, but every such trace ends with Suppressed: java.lang.NullPointerException ... "this.fieldMap" is null, which points at a Lucene bug instead of the disk or the file; and if closing a file also fails in that cleanup, the NPE replaces that close failure. It became visible with #14633 (2025-05-13, on main; in no release); every release keeps the older cleanup, which swallows the NPE. The fix is a one-line null guard.

The bug

#

All in Lucene103BlockTreeTermsReader.java at 5adff78bb168:

  1. private final IntObjectHashMap<FieldReader> fieldMap; (:100), with no initializer.
  2. The constructor's try (:113) opens .tim (:116), checks its header, opens .tip (:128), reads .tmd into a local map (:140) and verifies checksums. Only after all of that does it run this.fieldMap = fieldMap; (:235; only this.fieldList = sortFieldNames(...) at :236 follows).
  3. Any Throwable before :235 lands in catch (Throwable t) { IOUtils.closeWhileSuppressingExceptions(t, this); throw t; } (:237-240).
  4. close() (:271-280) runs IOUtils.close(indexIn, termsIn, postingsReader) (:274, which skips null inputs), then, in a finally, fieldMap.clear() (:278): fieldMap is null, so it throws an NPE.
  5. IOUtils.closeWhileSuppressingExceptions ("Closes all given Closeables, suppressing all thrown Throwables in ex", IOUtils.java:97-103) calls close() (:121) and adds the NPE to the primary exception (:129), which is rethrown at :239.
  6. Because the NPE is thrown from a finally, it also replaces any exception from IOUtils.close at :274 (JLS 14.20.2): a failure while closing .tim in the same cleanup is lost. A side probe showed it: with the .tmd open failing and .tim's close() also throwing, main attaches only the NPE, the null guard attaches the .tim close failure, and 10.6.0 attaches nothing.

The numbers

#

One document, .tip open fails: expected 0 suppressed exceptions, got 1, the NPE from close() at :278, with assertions on and off. The primary IOException ("simulated") and its type are unchanged, and the .tim input is closed. The same happens when the .tim or .tmd open fails (both executed), and by reading for every failure before :235, such as a header or checksum CorruptIndexException.

Why it looks unintended

#
  • close() is meant to run on a half-built reader: it already skips null inputs; only fieldMap is dereferenced unguarded.
  • The cleanup helper attaches close failures; this NPE is not one, and it even replaces a real one.
  • A refactoring leftover: before LUCENE-9045 (2019) the map was initialised at its declaration; sibling readers still do that.
The full argument192 words
  • close() is meant to run on a half-built reader. The constructor's cleanup passes this to the helper, and 10.6.0's version of the same cleanup says so: // this.close() will close in: (10.6.0 source, :241-242). IOUtils.close already skips the unset indexIn and termsIn ("Some of the Closeables may be null; they are ignored", IOUtils.java:65-66).
  • The helper's purpose. "Closes all given Closeables, suppressing all thrown Throwables in ex" (IOUtils.java:97-103): it attaches close failures. An NPE on an unassigned field is not a failure to close any resource.
  • A refactoring leftover. Before LUCENE-9045 (71f1bc33b37, 2019-12-02) the map was private final TreeMap<String,FieldReader> fields = new TreeMap<>();. LUCENE-9045 made it a field assigned in the constructor, and LUCENE-9353 (87a3bef50f8, 2020-06-16) moved the assignment to the end.
  • Siblings. Lucene90PointsReader uses the same closeWhileSuppressingExceptions(t, this) cleanup (:123) but initialises its map at declaration (:39) and clears it in close() (:156).
  • Nothing accepts it. No javadoc, CHANGES.txt or MIGRATE.md entry, test or review comment says a failed open may carry an NPE from close(); #14633's discussion never mentions fieldMap, BlockTree or an NPE.
The devil's-advocate check148 words

The strongest case for "intended" (the cross-model reviews rated it weak as a case for "intended"): DirectoryReader.open promises only "@throws IOException if there is a low-level IO error" and keeps that promise; nothing documents which suppressed exceptions a failed open may carry; the reader is @lucene.experimental; and #14633 deliberately made cleanup throwables visible ("any problems that occur whilst closing/deleting during exception handling will now be added to the top-level rethrown exception, rather than being swallowed and disappearing").

Why it fails: #14633 meant to surface real close failures, and this NPE is not one; it even pushes out the real close failure #14633 wanted to keep. CI has printed it since May 2025 without comment, but that is tolerance, not intent: the one issue about that test failure (#15580, from a local run) pasted only the primary trace. What remains is impact, not intent, so it stays Low.

Suggested fix

#

Recommended A. Null guard in close() (validated)

In close(), guard the clear: if (fieldMap != null) fieldMap.clear();. A failed open then carries only real close failures, and a file's close failure is no longer replaced. Validated: the repro passes with assertions on and off, and 75 tests of the closest suites and lucene/core's format, lint and forbidden-API checks pass.

@Override
public void close() throws IOException {
  try {
    IOUtils.close(indexIn, termsIn, postingsReader);
  } finally {
    // Clear so refs to terms index is GCable even if
    // app hangs onto us (null if the constructor failed):
    if (fieldMap != null) {
      fieldMap.clear();
    }
  }
}

A. Null guard in close() (validated) (recommended)

#

In close() (Lucene103BlockTreeTermsReader.java:278):

@Override
public void close() throws IOException {
  try {
    IOUtils.close(indexIn, termsIn, postingsReader);
  } finally {
    // Clear so refs to terms index is GCable even if
    // app hangs onto us (null if the constructor failed):
    if (fieldMap != null) {
      fieldMap.clear();
    }
  }
}

Trade-offs

  • No change on a successful open or a normal close().
  • Keeps #14633's intent: the primary exception carries real close failures only.
  • Optionally the same guard in backward-codecs Lucene90BlockTreeTermsReader.close() (:309), which has the same shape but no symptom (its cleanup still uses closeWhileHandlingException(this), :269).
  • Open PR #16201 changes this line to fieldMap.release(); whichever lands second must keep the guard.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the guard it passes, on and off.
  • With the guard, the repro plus the closest suites (TestAllFilesCheckIndexHeader, TestAllFilesDetectTruncation, TestAllFilesDetectMismatchedChecksum, TestAllFilesHaveChecksumFooter, TestAllFilesHaveCodecHeader, TestLucene104PostingsFormat, TestTrie, TestDirectoryReaderReopen): 9 classes, 75 tests, 0 failures, 3 skipped as nightly-only.
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the guard and the test.
  • The full Lucene test suite was not run.

B. Close the opened inputs, not this (not run)

#

Keep the inputs in local variables and close those in the constructor's catch instead of this.

Trade-offs

Java does not let the catch read a blank final field that may be unassigned, so this needs locals for the inputs: more churn than A for the same result.

Not recommended: go back to closeWhileHandlingException(this)

#

Restores the release behaviour for this reader.

Trade-offs

Hides the NPE again, but also drops every real close failure, which #14633 set out to stop.

Downstream note

#

Downstream, services that alert on NullPointerException in Lucene traces may see this one next to ordinary I/O or corruption failures on builds from main; the primary exception is the one to act on.

How it was found

#

Semi-formal: a proof-obligation audit of the reader's constructor failure cleanup. The obligation is that the cleanup closes what was opened and adds nothing but close failures to the propagated exception; the path where an open fails before fieldMap is assigned breaks it. A one-test repro on stock main witnessed it.

The method in full113 words
  • Obligation: from the cleanup idiom (catch (Throwable t) { closeWhileSuppressingExceptions(t, this); throw t; }) and the helper's javadoc: on a failed open, the inputs opened so far are closed, the primary exception propagates, and only their close failures are attached.
  • Check: every field close() touches, against the point in the constructor where it is assigned: indexIn and termsIn may be null but IOUtils.close skips them; fieldMap is assigned last and dereferenced unguarded.
  • Witness: a one-test JUnit repro through public API, then the minimal test shown here.
  • Checks: an independent reproduction, reviews by a model from another family (OpenAI GPT-5.6), an intended-behaviour review, an adjudication and a separate re-run (see Independent checks).
