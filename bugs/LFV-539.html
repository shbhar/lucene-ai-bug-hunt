Every release since 9.11.0 does this.

The bug in 30 seconds

#

Taxonomy facets can aggregate a per-document value, such as a price or the score, per category: TaxonomyFacetFloatAssociations with a DoubleValuesSource. Since 9.11.0 each result label also carries count, the number of matching documents under it, as FastTaxonomyFacetCounts reports.

  1. Declare dimension d hierarchical and index two documents: d/a/x with weight 7 and d/a/y with weight 2. Sum the weights per category with TaxonomyFacetFloatAssociations and DoubleValuesSource.fromLongField("w").
  2. You expect category a with value 9.0 (7 + 2) and count 2, the two documents under it. FastTaxonomyFacetCounts reports 2 for the same hits.
  3. You get value 9.0 but count 4, from getTopChildren and getAllChildren. One document at d/a/b/x gives counts 3, 3 and 1 instead of 1, 1 and 1: the deeper the path, the bigger the overcount.
  4. Why: the roll-up first adds up the counts of the whole sub-tree (the super call), then walks the tree again through the same method, so each level adds its children's already rolled-up counts again, and the extra counts compound with depth.
  5. No error, and values, value order, childCount and leaf counts are right (short of an int overflow at extreme depths). A one-line fix makes the second walk roll up values only; the whole facet test suite passes with it.

Who is affected

#

Applications that sum or max a per-document value per category with TaxonomyFacetFloatAssociations and a DoubleValuesSource, over a dimension set with setHierarchical and paths two or more levels deep, and show LabelAndValue.count. Every category with matching documents below it is wrong, on every such request, on 9.11.0 to 10.5.2 and main; the values look right.

Mechanism, terms and numbers708 words

TaxonomyFacetFloatAssociations with a DoubleValuesSource aggregates a per-document value per taxonomy category, and since 9.11.0 each LabelAndValue also carries count, the "Number of occurrences for this label". On a dimension declared hierarchical (and single-valued, the default), every label that has matching documents below it gets a count that is too high: two documents under d/a give a (9.0) with count 4, and one document at d/a/b/x gives 3 at a and at a/b, where FastTaxonomyFacetCounts gives 2 and 1. FloatTaxonomyFacets#updateValueFromRollup calls super, which rolls up the counts of the whole sub-tree, and then its own recursion, which calls the same method, and so super, again for every descendant. This defect leaves values, value order, childCount and leaf counts right, short of an int overflow at extreme depths. Upstream testRollupValues runs this path but compares only toString(), which omits the count. Every release from 9.11.0 to 10.5.2 and main is affected; a one-line change that makes the private recursion roll up values only fixes it, and the whole lucene/facet test suite passes with it.

Terms

#
  • Taxonomy facets: each document gets category paths such as d/a/x (FacetField); a side index, the taxonomy, gives every path prefix an ordinal: d, d/a, d/a/x.
  • Hierarchical dimension: FacetsConfig.setHierarchical("d", true), "Pass true if this dimension is hierarchical (has depth > 1 paths)" (FacetsConfig.java:170). If it is also single-valued (the default), only the leaf ordinal is indexed per document; the counts and values of d/a are computed at search time by a roll-up from the leaves (FacetsConfig.java:380-398; TaxonomyFacets.java:261-285).
  • Value-source association facets: TaxonomyFacetFloatAssociations(taxoReader, config, fc, SUM or MAX, valuesSource) aggregates valuesSource per category. The code says "Hierarchical dimensions are supported when using a value source, so we need to rollup" (TaxonomyFacetFloatAssociations.java:164-165).
  • LabelAndValue.count: "Number of occurrences for this label" (LabelAndValue.java:27-28), added by #13414 for 9.11.0 ("Counts are always available in the result when using taxonomy facets", CHANGES.txt:2784).

The bug

#
  1. Each hit adds its value and count + 1 at its indexed ordinal, the leaf (TaxonomyFacetFloatAssociations.java:149-161, :158). For d/a/x and d/a/y: x = 1, y = 1, a = 0, d = 0.
  2. rollup() calls the virtual updateValueFromRollup(d, a) (TaxonomyFacets.java:281). The float override first calls super.updateValueFromRollup (FloatTaxonomyFacets.java:96), which rolls up the counts of the whole sub-tree in place (TaxonomyFacets.java:242-244, :287-299): a = 2, d = 2. Already right.
  3. The override then calls its own rollup(a) for the values (FloatTaxonomyFacets.java:98, :112-122). That loop calls the virtual updateValueFromRollup(a, firstChild) (:117), so the super count pass runs again under a and adds x + y once more: a = 4. Every node with children repeats this, and each extra pass rewrites the counts below it in place, so the extra counts compound with depth: one document at depth D is counted C(D, k) times at level k. A label whose hits all sit at the label itself keeps its right count, because the extra passes add only zeros.
  4. Values are aggregated once, by the float recursion, and stay right. getTopChildren and getAllChildren put getCount(ord) into each LabelAndValue (TaxonomyFacets.java:325, :333-334, :410-412).

Exposure and likelihood440 words
  • Who is exposed. Applications that aggregate a per-document value per category with TaxonomyFacetFloatAssociations and a DoubleValuesSource (revenue per category, or score-weighted facets with DoubleValuesSource.SCORES), over a dimension declared setHierarchical(dim, true) and not multi-valued, and that read LabelAndValue.count, for example to show "Fiction (2 books, 9.00)". On 9.11.0-9.12.x the deprecated TaxonomyFacetSumValueSource (a subclass; count 4, value 9.0) and the deprecated TaxonomyFacetCounts(OrdinalsReader, ...) (count 4, value 2) are hit too; both were removed in 10.0.0.
  • Default vs opt-in. setHierarchical and the value-source constructor are opt-in, and the class is @lucene.experimental. Single-valued is the default for a dimension. The defect is in the roll-up after collection, which reads only the per-ordinal counts; the tests ran under Lucene's randomized codec, IndexWriterConfig and searcher settings and failed with every seed tried, in both the dense and the sparse (hash-table) counter branches.
  • Scale. A label's count is inflated whenever the request's hits include documents below it; labels whose hits all sit at the label itself, and requests with no hits, are unaffected. Nothing in the roll-up depends on index size. The overcount compounds with depth: with one document at each level of a 20-level path the largest count, 352,716, is at levels 9 and 10, while the deepest labels are near-exact (21 and 1).
  • Silent. No exception and no log line, and the values are right, which makes it easy to miss.
  • Extreme inputs. The same double walk visits each sub-tree once per ancestor, so the roll-up costs about the sum of node depths on every request with a hit: one 4,095-level path (Lucene's 8,191-character limit) takes 86.9 ms per request against 0.81 ms with the fix, and 5 paths of depth 4,000 take 412 ms against 3.2 ms (medians of 5 after 2 warm-ups on one shared host, -da; only the ratios matter). The walk covers the dimension's whole sub-tree in the taxonomy, so deep paths indexed by other documents raise every request's cost. At 33 levels with one document per level some counts wrap past 2^31, and those labels vanish from the results although they have hits, so result membership and childCount are wrong too. The fix removes both.
  • Not affected (short of the int overflow): values and value-based ranking; childCount; leaf counts; the dimension's own value and its internal count (FacetResult carries no count for the dimension itself); FastTaxonomyFacetCounts; indexed FloatAssociationFacetField and IntAssociationFacetField (they cannot be hierarchical); multi-valued hierarchical dimensions (not rolled up); flat dimensions. Nothing is stored wrong, so a fix needs no reindex. "Values are right" means this defect does not change them; a separate all-negative MAX bug in the same roll-up code does.

Why it is a bug, not intended

#
  • LabelAndValue.count is the "Number of occurrences for this label"; since 9.11.0 counts are "always available" for taxonomy facets.
  • The code says hierarchical dimensions "are supported when using a value source"; FastTaxonomyFacetCounts gives 2 for the same hits.
  • Upstream testRollupValues runs this path but checks only toString(), which omits the count; a count assertion fails with 4.
The full argument322 words
  • Contract. LabelAndValue.java:27-28: count is the "Number of occurrences for this label". CHANGES.txt:2784 (9.11.0): "GITHUB#13414: Counts are always available in the result when using taxonomy facets." TaxonomyFacetFloatAssociations.java:42-44: a DoubleValuesSource "can dynamically supply a weight from each doc"; :164: "Hierarchical dimensions are supported when using a value source, so we need to rollup". No reading of "number of occurrences" gives 4 for two documents, or 3 for one.
  • Consistency. FastTaxonomyFacetCounts on the same hits gives 2; so do the same paths on a dimension that is also multi-valued (ancestors indexed, no roll-up), with the same value 9.0. The count should not depend on an indexing detail or on the facet class.
  • Tests. TestTaxonomyFacetValueSource#testRollupValues (:437-485) uses this exact setup (hierarchical dimension, value-source constructor, SUM and MAX) but compares only FacetResult.toString() (:467-469, :479-481); LabelAndValue.toString() prints label and value (LabelAndValue.java:44-47), and equals/hashCode ignore count (:49-60). With a count assertion added, it fails on main: count of 1 (6.0) expected:<2> but was:<4>. TestTaxonomyFacetAssociations#testAggregationCounts (:573-611) asserts counts that mean documents, on a flat dimension only.
  • History. #12966 ("always do counts", 2024-04) introduced three pieces together: the base TaxonomyFacets#updateValueFromRollup (counts of the whole sub-tree), the FloatTaxonomyFacets override that calls super, and a private recursion that calls the overridable method again for every child. Before it, the private float roll-up aggregated values directly, the shape the recommended fix restores. In its 41 comments none notices that the counts are rolled up more than once (the one roll-up thread is about sharing updateValueFromRollup between the Int and Float classes). Until #13414 exposed LabelAndValue.count (2024-05) the counts were only checked for > 0, which inflation cannot change short of the int overflow at extreme depths.
  • Precedent. #14008, wrong association-facet counts from a different cause, was fixed as a bug in 9.12.1 and 10.1.0 (CHANGES.txt:2141, :2510). This bug reproduces after that fix.
The devil's-advocate check174 words

The strongest "intended" case: the classes are @lucene.experimental; LabelAndValue.equals and toString leave count out, so it could look secondary; the base javadoc says "Overrides should probably call this to update the counts" (TaxonomyFacets.java:237-241) and the override does; LUCENE-5536 (#6599, 2014) said association facets should not roll up; and #11282 (counts from association facets) is still open.

Why it fails: the value-source path explicitly supports hierarchical dimensions, and LUCENE-5536 was about indexed association values, before this path and before counts existed. CHANGES promises counts, LabelAndValue itself is not experimental, and @lucene.experimental is about API stability, not wrong numbers. Leaving count out of equals (for backward compatibility, as #13414 says) and of toString explains why tests missed it, not what the number should be. Calling super is exactly what nests the two recursions; nothing documents a depth-dependent count. Verdict: a defect (adjudication: confirmed, high; every verifier rated the intended case weak; the only not_real vote was a read-only review that could not run Java). It lowers the severity: only the count is wrong.

Suggested fix

#

Recommended Roll up only values in the private recursion

In the private roll-up of FloatTaxonomyFacets, and of its twin IntTaxonomyFacets, aggregate the values directly instead of calling updateValueFromRollup again; the super call already rolls the counts up once. The repro, upstream testRollupValues with count assertions and the whole lucene/facet suite (308 tests) pass, assertions on and off.

  private float rollup(int ord) throws IOException {
    ...
    while (ord != TaxonomyReader.INVALID_ORDINAL) {
-      updateValueFromRollup(ord, children.get(ord));
+      // Values only: super.updateValueFromRollup already rolled up the counts of this sub-tree.
+      setValue(ord, aggregationFunction.aggregate(getValue(ord), rollup(children.get(ord))));
       aggregatedValue = aggregationFunction.aggregate(aggregatedValue, getValue(ord));
       ord = siblings.get(ord);
     }
// the same line in IntTaxonomyFacets.rollup(int)
All options and trade-offs3 options · 653 words

Counts are then rolled up once (by the base class) and values once (by the private recursion), each walk visiting every node once, so the roll-up is linear again and the extreme-depth cost and overflow disappear (executed: 0.81 ms instead of 86.9 ms for one 4,095-level path; exact counts at 33 and 40 levels). Values are computed exactly as before. The IntTaxonomyFacets half changes nothing on main, where no class rolls it up, but keeps the two copies the same; a 9.x backport needs it for the deprecated TaxonomyFacetCounts. Add count assertions to testRollupValues either way. Workaround until a fix ships: take the counts from FastTaxonomyFacetCounts over the same FacetsCollector; this avoids the wrong counts, not the roll-up cost, which runs in the association facets' constructor. Only query-time numbers change, so no reindex is needed.

Roll up only values in the private recursion (validated by the checks) (recommended)

#

FloatTaxonomyFacets.java:117 and IntTaxonomyFacets.java:108: replace the call to the virtual updateValueFromRollup(ord, children.get(ord)) with the value aggregation it performed; the super call in updateValueFromRollup keeps rolling up the counts of the sub-tree once, as the base javadoc asks. +2/-1 in each file.

+      // Values only: super.updateValueFromRollup already rolled up the counts of this sub-tree.

Trade-offs

  • The private recursion no longer goes through the overridable hook; only the dimension root does. Both classes are package-private and their in-tree subclasses do not override updateValueFromRollup, so no in-tree code depends on it. The public subclasses are not final and inherit the protected hook: an application subclass that overrides it would see it called only for dimension roots (the classes are @lucene.experimental).
  • The IntTaxonomyFacets change is latent on main; drop it for the smallest diff.

Drop the super call and add the direct children's counts (validated by the checks)

#

The finder's sketch: after rollup(childOrdinal) has finished every child sub-tree, add the children's rolled-up counts to ordinal (+9/-1 in FloatTaxonomyFacets.java).

Trade-offs

Same results for the in-tree classes, also linear; it keeps the per-node calls to the protected hook. It goes against the base javadoc ("Overrides should probably call this to update the counts") and duplicates the count logic in the float class; IntTaxonomyFacets would need the same.

What the checks validated

The new test passes (standalone); the whole :lucene:facet:test, 40 suites and 308 tests, passes with assertions on; the finder's harness count mismatches go from 2,977 to 0 with it; 75 upstream facet tests passed with the unit's four fix sketches applied together. (The gradle log label fixA means this alternative fix.)

Workaround: counts from FastTaxonomyFacetCounts

#

Applications can read counts from FastTaxonomyFacetCounts over the same FacetsCollector and values from the association facets.

Trade-offs

A second facet pass per request; it avoids the wrong counts but not the roll-up cost; not a fix.

Downstream note

#

Products that let users create very deep category paths (folders, breadcrumbs) also pay a roll-up cost that grows with depth squared on every such facet request, 86.9 ms instead of 0.81 ms for one 4,095-level path, until they upgrade or cap path depth.

How it was found

#

An AI finder wrote a plain-language spec of the Facets API and a randomized metamorphic test harness over random facet schemas and tiny indexes. The relation "a label's count equals the matching documents under it" failed for value-source float associations; a bounded-exhaustive check pinned it to labels with children, and the finder reduced it to a JUnit test.

The method in full163 words

Method: randomized model-based metamorphic and differential testing (the hunt's "non-formal" tier; the finder called it semi-formal), a hunt unit (facet API metamorphic relations), 2026-10-26, stock main jars.

  • The finder wrote a Facets API specification and a harness that builds random facet schemas and tiny indexes and checks metamorphic relations. Relation F1d, "LabelAndValue.count equals the number of matching documents under the label, cross-checked with FastTaxonomyFacetCounts", failed on the value-source float association path: 1,490 SUM and 1,487 MAX mismatches in 400 iterations (seed 2, non-negative values), none with the fix.
  • A bounded-exhaustive check then ran every sequence of 1-3 documents over the 14 paths of depth 1-3 of one hierarchical dimension (438,872 checks): count mismatches only at labels with children, ratios such as 2/1, 4/2 and 9/3; 0 with the fix (the remaining mismatches are a separate MAX bug).
  • The finder reduced it to a public-API JUnit test with two documents. Then independent AI tools reproduced, reviewed and judged it (see the checks).

Bug record

LFV-539, snapshot of 2026-10-29

Registry title
TaxonomyFacetFloatAssociations with a DoubleValuesSource reports a too-high LabelAndValue.count for every label that has matching documents below it in a hierarchical dimension, because FloatTaxonomyFacets rolls the counts up again at every ancestor level (values are right; every release since 9.11.0)
Area
facet / taxonomy association facets (TaxonomyFacetFloatAssociations value-source path, FloatTaxonomyFacets#updateValueFromRollup count roll-up)
Priority
Medium, rank 190: Float association facets with a DoubleValuesSource inflate LabelAndValue.count on every hierarchical request, the same inflated-facet-count profile as LFV-151, LFV-433 and LFV-437, so it joins them.
Impact class
silent wrong results
Impact note
Applications that aggregate a per-document value (a price, a weight, a score) per category with TaxonomyFacetFloatAssociations and a DoubleValuesSource over a dimension declared hierarchical in FacetsConfig (a non-default setting; single-valued, the default for such a dim) and read LabelAndValue.count get a count that is too high for every label with matching documents below it (two documents under d/a reported as 4; one document at cat/a/b/x counted 3 times at a and at a/b), on every request, with the default codec, IndexWriterConfig and searcher, tiny indexes, -ea and -da, in every release from 9.11.0 to 10.5.2 and main; values, value ranking, childCount, leaf counts and FastTaxonomyFacetCounts are right, and only with very deep paths (about 33 levels with one document each) do the inflated int counts wrap and drop labels that have hits from the result.
Summary
You index documents with a FacetField in a dimension declared hierarchical (FacetsConfig.setHierarchical("d", true)), for example d/a/x with weight 7 and d/a/y with weight 2, and sum a per-document DoubleValuesSource per label with TaxonomyFacetFloatAssociations; you expect label a under d to report value 9 and count 2, the 'Number of occurrences for this label' that FastTaxonomyFacetCounts reports for the same hits. Instead getTopChildren and getAllChildren report a (9.0) with count 4, because FloatTaxonomyFacets#updateValueFromRollup first calls super.updateValueFromRollup, which rolls up the counts of the whole sub-tree, and then its own rollup(childOrdinal), which calls updateValueFromRollup again for every descendant, so the sub-tree counts are added once more at each ancestor level. Values and leaf counts are right; only LabelAndValue.count of labels with descendants is inflated, and the deeper the tree, the larger the overcount.
Introduced

It added the super call to FloatTaxonomyFacets#updateValueFromRollup, whose own private rollup(int) already recursed through the virtual updateValueFromRollup. The counts became user-visible with #13414 ('Allow users to retrieve counts from taxo association facets', main b3dc9153bb5d, branch_9x 09302078a6eb), which added LabelAndValue.count filled from getCount(ord); before that the counts were used only for count > 0 checks, which the inflation cannot change.
