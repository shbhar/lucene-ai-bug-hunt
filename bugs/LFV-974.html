The finding in 30 seconds

#

The default codec's file-format javadoc for doc values gives the wrong block size for terms dictionaries and leaves out their LZ4 compression.

Background: doc-values terms dictionaries

#
  1. A SORTED or SORTED_SET doc-values field stores, per document, an ordinal (ord) into the sorted list of the field's distinct terms. That list, the terms dictionary, lives in the segment's .dvd file.
  2. To save space, a term is stored as the length of the prefix it shares with the previous term plus the rest, its suffix. Every so many terms, one term is stored in full, so that a lookup can start decoding there instead of at the beginning.

The finding, step by step

#
  1. You read the Lucene90DocValuesFormat javadoc, the doc-values format of the default codec, to learn how a SORTED field's distinct terms are stored in the .dvd file: "written in chunks of 16, with the first value written completely and other values sharing prefixes".
  2. You index 17 documents with the SORTED values term00 to term16 and look in .dvd for each term stored in full (a length byte, then its bytes). You expect ords 0 and 16, the first term of each chunk of 16.
  3. Instead only ord 0 is there. The writer uses blocks of 64: the first term in full, the other 63 as suffixes after a shared prefix (just "6" for term16, which shares term1 with term15), and that part LZ4-compressed. With 1,000 terms the javadoc predicts 63 full terms; the file has 16 (ords 0, 64, 128, ...).
  4. A smaller slip in the same javadoc: a lookup table is said to be used for fewer than 256 unique values, but exactly 256 get it too. 4,096 documents with 256 distinct values give a 4,169-byte .dvd; with 257 values it is 24,651 bytes.
  5. Nothing breaks: Lucene's reader matches its writer. The text has been stale since LUCENE-9843 removed the 16-term mode in 9.0.0 (2021), and the fix is a javadoc edit.

Who is affected

#

Developers who learn the .dvd format from this javadoc to inspect, debug, port or re-implement it. On every release since 9.0.0, with no setting involved, the text omits the LZ4 step for any SORTED or SORTED_SET field with 2 or more terms and gets the block size wrong from 17 terms on. Lucene users see no runtime effect.

Mechanism, terms and numbers602 words

The class javadoc of Lucene90DocValuesFormat, the doc-values format of the default codec, says that terms dictionaries ("Prefix-compressed Binary", used by SORTED and SORTED_SET fields) are "written in chunks of 16, with the first value written completely and other values sharing prefixes" (Lucene90DocValuesFormat.java:101-104 on main 645d4fe14a20). Since 9.0.0 the writer uses blocks of 64 terms: it writes the first term of each block in full, prefix-codes the other 63, and compresses them with LZ4 (Lucene90DocValuesConsumer.addTermsDict, :758-851; TERMS_DICT_BLOCK_LZ4_SHIFT = 6, Lucene90DocValuesFormat.java:217); since 9.2.0 (LUCENE-10536) the first term is the LZ4 dictionary. LUCENE-9843 (a7a02519f0a, 2021) removed the 16-term mode and deleted its constant from this same file, but left the sentence. So only terms 0, 64, 128, ... appear in full in a .dvd file: 17 terms give 1 complete term where the text predicts 2, and 1,000 terms give 16 where it predicts 63. A second, smaller slip: table compression is said to apply for "(< 256)" unique values (:77), but the writer keeps the table up to and including 256 (Lucene90DocValuesConsumer.java:434, size() > 256). Lucene's reader matches its writer, so only the documentation is wrong.

The javadoc (main 645d4fe14a20)

#
  • Lucene90DocValuesFormat.java:101-104 (BINARY section; the SORTED bullet at :110 says terms are "written as Prefix-compressed Binary"): "Prefix-compressed Binary: values are written in chunks of 16, with the first value written completely and other values sharing prefixes. chunk addresses are written as Monotonic-compressed numerics. A reverse lookup index is written from a portion of every 1024th term." No word about LZ4.
  • :77: "Table-compressed: when the number of unique values is very small (< 256), and when there are unused "gaps" in the range of values used ... a lookup table is written instead."

The code

#
  • Lucene90DocValuesFormat.java:217-219: TERMS_DICT_BLOCK_LZ4_SHIFT = 6 (64 terms) is the only block size.
  • Lucene90DocValuesConsumer.addTermsDict (:758-842, called for SORTED at :755 and SORTED_SET at :1061): when (ord & blockMask) == 0 (:785, every 64th term) it records the block address and writes the term in full, data.writeVInt(term.length) and its bytes (:797-798); every other term goes into a buffer as one token byte (shared-prefix and suffix lengths, with extra vints for long ones) plus its suffix (:803-816). Each block's buffer is written as its length and LZ4.compressWithDictionary(termsDictBuffer, 0, dictLength, ...) with the block's first term as the dictionary (:844-851; the dictionary dates from LUCENE-10536 in 9.2.0, while 9.0.0 and 9.1.0 call LZ4.compress without one). A last block that holds only its first term gets no LZ4 data (:823).
  • The reader mirrors it: block mask from TERMS_DICT_BLOCK_LZ4_SHIFT (Lucene90DocValuesProducer.java:1770, :1792) and LZ4.decompress (:1950).
  • Table: the writer drops the unique-value table only when uniqueValues.size() > 256 (Lucene90DocValuesConsumer.java:434) and uses it only for 2 or more unique values whose ordinals need fewer bits than the value range (:485-488); the reader rejects only tableSize > 256 (Lucene90DocValuesProducer.java:392-393).

The numbers

#
  • 17 SORTED terms term00..term16, default codec, one segment: only ord 0 appears in full in .dvd (the javadoc predicts ords 0 and 16).
  • The hunt's check: 100, 300 and 1,000 distinct terms give 2, 5 and 16 complete terms (ords 0, 64, 128, ...); chunks of 16 would give 7, 19 and 63.
  • 4,096 NUMERIC values with a gap (0 to 254 and 2^40, i.e. 256 distinct): .dvd is 4,169 bytes, 8-bit ordinals per document, a table (the table itself goes to .dvm, Lucene90DocValuesConsumer.java:492-494); with 257 distinct values 24,651 bytes, 48 bits per document.
Exposure and likelihood224 words
  • Who is hit. People who study the default codec's file formats: to inspect or recover an index, to write a reader in another language, or to start a custom codec from Lucene90DocValuesFormat. The default codec's overview sends them here: lucene104/package-info.java:172 and :288 link the class as the per-document values format, and :188 says "Details on each of these are provided in their linked pages".
  • Default vs opt-in. Default: Lucene104Codec uses new Lucene90DocValuesFormat() (Lucene104Codec.java:122), and Lucene90 has only the 64-term LZ4 layout; no setting gives 16-term chunks. A dictionary with one term has no LZ4 data, and the text is right for it.
  • What a reader gets wrong. The text puts the block boundaries in the wrong place and does not say that the rest of each block is LZ4-compressed, so it is not enough to read this part of the format. A mental model built from it gets the block size wrong by a factor of 4 and misses the decompression step.
  • Scale. None needed: 2 or more distinct terms give an LZ4 block the text does not mention; 17 or more show the wrong block size (ord 16 is not stored in full).
  • What it does not do. No wrong result, exception or corruption: Lucene reads what it writes. Impact minor, priority Low; no public report found since 9.0.0 (2021).

Why it looks unintended

#
  • "Chunks of 16" was true until 8.x. LUCENE-9843 (9.0.0) removed the 16-term mode and deleted its constant from this same file, but left the sentence.
  • Lucene's own CHANGES (9.2.0) describes the real layout: the first term of each block uncompressed, the other 63 compressed.
  • Tests are built on 64-term blocks and say "<= 256"; the reader accepts a 256-entry table.
The full argument205 words
  • History. The sentence was written for Lucene45DocValuesFormat (c2f37e0de2d, 2013-08-19, "javadocs/cleanups"), when it was true (16-term address interval), and copied into every later format, into Lucene90DocValuesFormat by LUCENE-9705 (4d7b2aebfe0, 2021-02-22). LUCENE-9663 (8.9.0) added 64-term LZ4 blocks for the non-default BEST_COMPRESSION mode; LUCENE-9843 (a7a02519f0a, 2021-05-06, 9.0.0) removed the modes, and its diff of this file deletes TERMS_DICT_BLOCK_SHIFT = 4 but not the sentence. Its issue (#10882, 18 comments) never mentions the javadoc.
  • The real layout is documented elsewhere. CHANGES.txt:4257-4259 (9.2.0, LUCENE-10536): "Doc values terms dictionaries now use the first (uncompressed) term of each block as a dictionary when compressing suffixes of the other 63 terms of the block."
  • Tests. TestLucene90DocValuesFormat builds its terms-dictionary cases from TERMS_DICT_BLOCK_LZ4_SIZE (:1116, :1204); LegacyBaseDocValuesFormatTestCase.java:1359 and :1518: "for numbers of values <= 256, all storage layouts are tested".
  • The text is meant to be exact. It gives numbers (16, 256, 1024; "blocks of 16384 values" at :89 is right), and the codec overview sends readers to it for the details (lucene104/package-info.java:188). Upstream merged javadoc corrections of this kind (#13801 "Correct Point file extensions in Codec javadocs", #12984 "Improve Javadoc for Lucene90StoredFieldsFormat"), and in 2015 replaced outdated doc-values format javadocs (#7921, LUCENE-6863).
The devil's-advocate check192 words

Strongest case for "intended" (built by the cross-model refute and intended reviews, the intended-behaviour verifier and the adjudication): the layout is deliberate (LUCENE-9843, LUCENE-10536); the class is @lucene.experimental (Lucene90DocValuesFormat.java:140); the codec overview calls itself "a high-level definition" (lucene104/package-info.java:54); the bullets are informal prose, not a byte grammar; and "(< 256)" reads like "fits in a byte", a sufficient condition rather than the exact threshold (the bullet also leaves out the bits-saved test).

Why it fails: it defends the code, not the text. "Chunks of 16" is a specific number about the current default format, and Lucene90 has no 16-term path at all. The LZ4 step is not a detail a high-level description may skip, since the bytes after a block's first term cannot be read without decompressing them. @lucene.experimental warns of API changes, not of wrong docs. The constant was deleted from the same file without the sentence, and no discussion decided to keep it. Every verifier and the adjudication rejected the argument for the text; the "(< 256)" half is the weaker one (medium confidence), so it is presented as an imprecision fixed in the same edit.

Suggested fix

#

Recommended A. Describe the 64-term LZ4 blocks and the inclusive 256 bound

Rewrite two javadoc bullets: terms are "written in blocks of 64, with the first value written completely and other values sharing prefixes; the rest of each block is compressed with LZ4, using the first value as a dictionary", and the lookup table is used for up to 256 unique values ("<= 256"). Javadoc only; no code changes.

Trade-offs

  • It states the numbers again (64 and 256), so a future layout change must update the text, as it should have in 9.0; both match the code (TERMS_DICT_BLOCK_LZ4_SIZE, size() > 256).
  • "using the first value as a dictionary" is the LUCENE-10536 wording from CHANGES; "Block addresses" replaces the lower-case "chunk addresses".
  • The table bullet stays as informal as today: besides at most 256 unique values, the writer needs 2 or more of them and ordinals that take fewer bits than the value range (Lucene90DocValuesConsumer.java:485-488), which "unused gaps" only paraphrases. For the exact condition, a wording such as "a lookup table of up to 256 unique values is written instead when their ordinals need fewer bits than the values themselves" would state it (not validated).
  • Like the current text, A stays a high-level description (no token or vint grammar), not a spec to build a parser from.

Downstream note

#

No downstream runtime relevance: Lucene's reader and writer agree, so only an outside .dvd reader written from this javadoc would be affected.

How it was found

#

Semi-formal: a check pulled the numeric claims out of the codec file-format javadocs ("written in chunks of N", "< N") and tested them against the bytes of .dvd files the default codec wrote. Independent reproducers, cross-model reviews and an adjudication confirmed it; runs on releases from 4.4.0 to main dated it.

The method in full174 words
  • The hunt's check (part of a differential file-format check) extracted "written in chunks of 16" and "very small (< 256)" from the javadoc text and checked them on real files: for SORTED fields with 100, 300 and 1,000 distinct terms, which ords appear in clear; for NUMERIC fields of 4,096 documents with 254 to 258 distinct values, the .dvd size. The corrected text matched both checks.
  • An independent reproducer wrote its own test (200 terms dvterm-000000 to dvterm-000199, all sharing the 10-byte prefix dvterm-000, plus controls: complete ords are exactly the multiples of 64; 255 values compact, 257 not); on 8.11.4 the same test sees 16-term chunks, so the method detects them where they exist.
  • A reviewer from another model family (OpenAI GPT-5.6) ran its own test on 9 seeds (5 with assertions on, 4 off) and a corrected-contract variant (4 of 4 pass); a second review, an intended-behaviour devil's advocate and an adjudication agreed it is real.
  • This is a byte-level check of documentation claims, not model checking or a proof.

History

#

The "(< 256)" wording has been off by one since 4.5.0.

LFV-974, snapshot of 2026-11-03

Registry title
The file-format javadoc of the default doc-values format (Lucene90DocValuesFormat) says terms dictionaries are 'written in chunks of 16, with the first value written completely', but since 9.0 they are written in blocks of 64 terms whose other 63 terms are prefix-coded and then LZ4-compressed; it also says table compression is used for fewer than 256 unique values, while exactly 256 are table-compressed (documentation defect; the writer and reader agree)
Area
codecs / doc values (Lucene90DocValuesFormat class javadoc prose vs Lucene90DocValuesConsumer)
Priority
Low, rank 1115: The doc-values javadoc describes 16-term chunks without LZ4 while the writer uses 64-term LZ4 blocks, which misleads .dvd re-implementers for every SORTED and SORTED_SET field.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so indexing, merging, CheckIndex, sorting, faceting and search on doc values are unaffected in every configuration; the people misled are those who read, inspect or re-implement the .dvd format from this class javadoc (the default codec's package docs link it as the Per-Document Values format), who are told that every 16th term is stored in full and nothing about LZ4, while every SORTED and SORTED_SET terms dictionary the default codec writes stores only every 64th term in full and LZ4-compresses the rest (executed for SORTED, SORTED_SET read from the shared writer code); the 'chunks of 16' sentence has been stale since 9.0.0 (2021), the '< 256' wording is a one-value imprecision from 4.5.0 (2013), and no scale or special setting is needed.
Summary
You read the Lucene90DocValuesFormat javadoc to learn how the default codec stores the terms of SORTED and SORTED_SET doc values, and it says they are written in chunks of 16 terms, each starting with one term written in full while the others share prefixes. Since Lucene 9.0 the writer instead uses blocks of 64 terms: only the first term of each block is stored in full, and the other 63 are prefix-coded and then compressed with LZ4, a step the javadoc never mentions, so in the .dvd file only terms 0, 64, 128, ... appear in clear, not 0, 16, 32, .... The same javadoc says a lookup table is used for numeric fields with fewer than 256 unique values, but a field with exactly 256 is also table-compressed; Lucene's own reader matches the writer, so nothing breaks at runtime, only the documentation is wrong.
