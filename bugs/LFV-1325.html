The merged view's getOffHeapByteSize throws NullPointerException when a merged segment has no vectors

A custom OneMerge#reorder that asks the merged view of a merge for a vector field's off-heap size gets NullPointerException as soon as one merged segment has no vectors. The same class skips that missing reader in checkIntegrity and getVectorCount; every release since 10.3.0 has it.

The finding in 30 seconds

#

The merged view keeps one vector sub-reader per segment and stores null for a segment without vectors. close, checkIntegrity and getVectorCount skip that null; getOffHeapByteSize calls every entry and throws.

Background: the merged view a reorder hook sees

#
  1. A merge policy can renumber the documents of a merge by overriding OneMerge#reorder. When index sorting is off and the merge has two or more segments (and not document blocks without a parent field), IndexWriter calls it with one merged CodecReader view over all of them.
  2. KnnVectorsReader.getOffHeapByteSize(field) (since 10.3.0) reports how many bytes of a vector field's files should fit in memory, per file extension, for example {vec=8, vex=0}. The merged view answers by adding up its segments' maps.
  3. A segment in which no document has a vector has no vector reader at all: null.

The finding, step by step

#
  1. Index 2 one-document segments: doc 0 has a 2-dimensional vector field v = {1, 2}; doc 1 is an empty document, so its segment has no vectors at all.
  2. Merge them through a merge policy whose OneMerge#reorder(view, ...) asks the merged view for v's off-heap size: view.getVectorReader().getOffHeapByteSize(view's FieldInfo for v).
  3. You expect segment 0's map, {vec=8, vex=0} (8 bytes of raw vectors in .vec, 0 bytes of graph in .vex), since segment 1 adds nothing; the same view's getVectorCount(v) returns 1.
  4. Instead it throws NullPointerException (because "reader" is null) at SlowCompositeCodecReaderWrapper.java:847, with assertions on and off. On forceMerge(1) the IndexWriter then closes itself with that exception.
  5. Why: the view keeps one vector reader per segment and stores null for segment 1. checkIntegrity and getVectorCount skip the null; getOffHeapByteSize calls every entry.

Who is affected

#

Only applications with their own merge code that size a vector field through the merged view, such as a custom OneMerge#reorder; nothing in Lucene makes that call. The data shape is ordinary (documents without an embedding). Inside a merge the IndexWriter closes; committed data stays intact and no search result is wrong.

Mechanism, terms and numbers349 words

When index sorting is off, and unless the merged segments have document blocks but no parent field, IndexWriter passes each merge of two or more segments to OneMerge#reorder as one merged CodecReader view, SlowCompositeCodecReaderWrapper (IndexWriter.java:5545-5557; also addIndexes(CodecReader...), :3549-3562). The view's vector reader keeps one sub-reader per segment, and that sub-reader is null for a segment in which no document has a vector (SlowCompositeCodecReaderWrapper.java:800-807, SegmentCoreReaders.java:136-140). close, checkIntegrity and getVectorCount handle that null; getOffHeapByteSize (:843-850) calls every entry with the view's FieldInfo and throws NullPointerException at :847.

Nothing in Lucene calls getOffHeapByteSize on this view, so only application code reaches it: a custom OneMerge#reorder that sizes a vector field through the view's getVectorReader(). On the merge path IndexWriter treats the exception as a tragic event (IndexWriter.java:5108-5112) and closes. The fix is the per-segment lookup getVectorCount already does, a few lines below.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/)

#
  1. The view. SlowCompositeCodecReaderWrapper.wrap(readers) returns the reader itself for one input and a new wrapper for two or more (index/SlowCompositeCodecReaderWrapper.java:49-57); the class is "primarily targeted at merging, not searching" (:43-46).
  2. A null sub-reader on purpose. getVectorReader() builds SlowCompositeKnnVectorsReaderWrapper (:789-792), whose constructor stores readers[i] = codecReaders[i].getVectorReader() (:800-807). A segment reader's vector reader is null when the segment has no vector values (index/SegmentCoreReaders.java:136-140; the probe prints seg1 vectorReader=null).
  3. Three methods handle it. close uses IOUtils.close, which ignores null (:809-812); checkIntegrity tests reader != null (:815-822); getVectorCount looks up each segment's own FieldInfo by name and skips segments where it is null or has vector dimension 0 (:852-862).
  4. getOffHeapByteSize does not (the fix site). for (var reader : readers) calls reader.getOffHeapByteSize(fieldInfo) on every entry with the view's FieldInfo (:843-850) and dereferences the null at :847.
  5. A second shape, not executed. For a segment that has vectors but not this field, the view's FieldInfo reaches PerFieldKnnVectorsFormat.FieldsReader.getOffHeapByteSize, which dereferences fields.get(fieldInfo.number) without a check (codecs/perfield/PerFieldKnnVectorsFormat.java:371-375). The recommended fix covers it too.
Exposure and likelihood189 words
  • Who. A OneMerge#reorder override (@lucene.experimental, MergePolicy.java:311-325) that calls view.getVectorReader() (@lucene.internal, CodecReader.java:80-85) and then getOffHeapByteSize (@lucene.experimental, KnnVectorsReader.java:230-260), for example to decide whether a reordering fits in memory. In Lucene's main sources (src/java) only forwarders and the test framework's per-segment check call the method.
  • Default vs opt-in. Opt-in: custom code is required; stock merges never make this call. The data shape is ordinary: a merge of two or more segments where one has no vectors.
  • Effect. A NullPointerException instead of the size map. Inside a merge, IndexWriter.merge rethrows the NPE from mergeMiddle (IndexWriter.java:5084, :5053-5055) and its outer catch (Throwable t) calls tragicEvent(t, "merge") (:5108-5112): an independent reproducer's route test (a FilterMergePolicy whose reorder makes the call, then forceMerge(1)) shows isOpen() false and the NPE as getTragicException(). Like any tragic close, this discards uncommitted changes (read, not executed). The addIndexes(CodecReader...) path was not executed.
  • Scale. Two one-document segments; every seed tried fails.
  • Workaround. None through this method on the view; getVectorCount on the same view works, and each segment's own reader answers getOffHeapByteSize correctly.

Why it looks unintended

#
  • The contract promises a size map, empty by default, with no exception; v is a vector field of the view itself.
  • The class creates the null itself and skips it in close, checkIntegrity and getVectorCount (#16647, right below).
  • #14426 overrode the method here on purpose; the same missing-segment pattern was fixed as a bug before (#12859, #14123).
The full argument228 words
  • Contract. KnnVectorsReader.getOffHeapByteSize: "Returns the desired size of off-heap memory for the given field", "@return a map of the desired off-heap memory requirements by category", "The default implementation returns an empty map"; no @throws (KnnVectorsReader.java:230-260).
  • The class contradicts itself. The null entry is a state the view creates (SlowCompositeCodecReaderWrapper.java:800-807) and handles in close, checkIntegrity and getVectorCount (:809-862). Operations this view does not support throw UnsupportedOperationException instead (:491, :1112-1126).
  • History. #14426 (686a5b8def5, 2025-04-15) added the method and this override, which adds up the segments' maps with mergeOffHeapByteSizeMaps (KnnVectorsReader.java:271-276); its review has no remark on null sub-readers. In that review the API author described the expected use: "the caller would get all the fieldInfos from the reader (LeafReader::getFieldInfos), and then iterate over them checking for vector info" (2025-04-03), which is the repro's call. #16647 (874ba4d39af, 2026-09-08, in 10.6.0) added the guarded getVectorCount right below it.
  • Tests. No test covers the view's getOffHeapByteSize; the only upstream test of this class, TestGetVectorCountCodecWrappers, checks getVectorCount on two segments that both have vectors.
  • Precedent. #12858/#12859 (null PointValues in this same view) and #14123/#14125 (SortingCodecReader threw NPE for a segment without points, vectors and other formats; the fix makes its sub-reader getters return null for a null delegate, 1778377176b) were fixed as bugs.
The devil's-advocate check239 words

The strongest case for "not a bug", made by the cross-model reviewers (OpenAI GPT-5.6; the executed review reproduced the NPE through OneMerge#reorder and agreed on the root cause): the trigger needs the @lucene.internal getVectorReader() inside the @lucene.experimental reorder hook, nothing in Lucene makes the call, and the view is a merge construct while the method sizes memory "for optimal search performance" (KnnVectorsReader.java:231-233); the view's FieldInfos come from FieldInfos.getMergedFieldInfos (SlowCompositeCodecReaderWrapper.java:96), whose javadoc warns that "the returned field numbers will likely not correspond to the actual field numbers in the underlying readers" (FieldInfos.java:190-196), so handing the view's FieldInfo to segment readers is not generally safe; and the lack of a @throws is no promise that this internal view supports sizing. So Lucene promises nothing here.

Why it does not settle it: those tags speak to API stability, not to a documented method throwing NPE on a state the class creates itself; #14426 chose to override the method in this view instead of keeping the empty-map default or throwing UnsupportedOperationException; the caller can neither see nor guard the null sub-reader; and the caller passes the view's own FieldInfo to the view's own reader, so translating it per segment is the view's job, which getVectorCount already does by name. That argues for Low priority, not for intended behaviour. A maintainer may still answer "do not size the merge view", a fair outcome for a Low bug.

Suggested fix

#

Recommended Look up each segment's own FieldInfo and skip segments without the field (fix A)

Mirror getVectorCount: for each segment, look up its own FieldInfo by name and add only the maps of segments that have the field with vectors (+7/-2 lines). With it the repro passes, and 117 tests of the repro and 5 closest suites pass.

      for (int i = 0; i < readers.length; i++) {
        FieldInfo subFieldInfo = codecReaders[i].getFieldInfos().fieldInfo(fieldInfo.name);
        if (subFieldInfo != null && subFieldInfo.getVectorDimension() > 0) {
          map =
              KnnVectorsReader.mergeOffHeapByteSizeMaps(
                  map, readers[i].getOffHeapByteSize(subFieldInfo));
        }
      }

Same shape and cost as the sibling getVectorCount (one FieldInfos lookup per segment per call). It also covers a segment that has vectors but not this field (read, not executed). How it was found

#

A proof-obligation audit of every getOffHeapByteSize forwarder against its sibling getVectorCount: each must cope with a segment that has no vector reader or lacks the field. The merged view's forwarder meets neither obligation; a JUnit test then witnessed the exception.

The method in full102 words

Method: semi-formal (a proof-obligation audit of a method's forwarders, witnessed by an executable repro).

  • The finder took the obligations the newer getVectorCount meets in each wrapper (skip a null sub-reader, skip a segment without the field) and checked every forwarder of getOffHeapByteSize against them; the merged view's loop fails both.
  • A one-test JUnit repro on the public API (plus the package-private wrap) then showed the NPE on main, with assertions on and off.
  • An independent reproducer and an executed cross-model review reproduced it with their own tests; a devil's-advocate verifier and an adjudication re-ran the repro ("Prior reports, history and checks").

Summary
You write a merge policy whose OneMerge#reorder asks the merged view it receives for a vector field's off-heap size, view.getVectorReader().getOffHeapByteSize(view.getFieldInfos().fieldInfo("v")), and merge a segment that has field v with one in which no document has a vector; you expect the field's size map, here the vector segment's own map, because the method returns a map per field (empty when there is nothing to report) and the same view's getVectorCount simply skips the segment without vectors. Instead getOffHeapByteSize throws NullPointerException at SlowCompositeCodecReaderWrapper.java:847: the view keeps a null vector reader for the segment without vectors (:800-807), and this loop (:843-850) calls every entry with the view's FieldInfo, without the null and field-presence checks that checkIntegrity (:815-822) and getVectorCount (:852-862) have. On the forceMerge path the exception becomes IndexWriter's tragic exception and the writer closes.
