Sandbox PhraseWildcardQuery: two queries with different expansion limits compare equal, so Lucene merges them

Two PhraseWildcardQuery objects for "a b*" with expansion limits 100 (2 hits) and 1 (1 hit) compare equal, so BooleanQuery, a query cache and the delete buffer treat them as one query: "limit 100 but not limit 1" finds 0 documents instead of 1. Affects every release since 8.4.0.

The finding in 30 seconds

#

PhraseWildcardQuery's expansion limit decides which documents match, but its equals and hashCode ignore it, and the segment-optimization flag too. Lucene code that relies on query equality then treats two different queries as one.

Background

#
  1. PhraseWildcardQuery (sandbox, @lucene.experimental) is a phrase with wildcard parts, such as "a b*". maxMultiTermExpansions caps how many terms the wildcard parts may expand to, across all of them and all segments; terms past the cap are not searched.
  2. Query equality. Query#equals and hashCode must be implemented properly "so that QueryCache works properly", and equal queries typically filter the same documents: BooleanQuery drops or cancels equal clauses, the query cache finds stored results by query, and IndexWriter buffers delete-by-query calls in a map keyed by query.

The finding, step by step

#
  1. Index two documents, a bx and a by. Build the phrase "a b*" twice with PhraseWildcardQuery.Builder: limit 100 expands b* to bx and by and matches 2 documents; limit 1 expands it to bx only and matches 1.
  2. Search FILTER(limit 100) + MUST_NOT(limit 1): "in the limit-100 hits but not in the limit-1 hits". You expect 1 document, a by.
  3. You get 0, with assertions on and off. equals and hashCode look only at the slop and the phrase terms, so the two queries are equal and BooleanQuery rewrites the pair to MatchNoDocsQuery("FILTER clause also in MUST_NOT").
  4. Query cache: entries are keyed by segment and query, compared with Query#equals, so the two queries share one entry: once the limit-100 query is cached, the limit-1 query reads its 2 hits instead of 1. On 9.x and 10.x a plain IndexSearcher's default cache is enough.
  5. Deletes: deleteDocuments(limit 1) then deleteDocuments(limit 100) before one commit applies only the first, so a by is not deleted.

Who is affected

#

Applications that build the same sandbox PhraseWildcardQuery phrase with two expansion limits (or segment-optimization settings), where the budget really cuts expansions, and combine the two in one BooleanQuery, one query cache or one delete batch. Hits are silently wrong, or a delete is lost; default codec, config and searcher.

Mechanism, terms and numbers609 words

PhraseWildcardQuery (sandbox, @lucene.experimental) builds a phrase with wildcard parts, such as "a b*". Its maxMultiTermExpansions is one budget for all wildcard parts and all segments, so a lower limit can match fewer documents: on a bx and a by, limit 100 matches both, limit 1 only a bx. But equals compares only the slop and the phrase terms, and hashCode is classHash() ^ slop ^ phraseTerms.hashCode(); segmentOptimizationEnabled, which also changes the matches once the budget binds, is left out too. Code that relies on query equality then merges two queries that match different documents: BooleanQuery.rewrite turns FILTER(limit 100) + MUST_NOT(limit 1) into a no-match query (count 0 instead of 1; 7 of the 8 clause pairs tested give a wrong count), LRUQueryCache, which finds stored results by segment and query, serves one query's hits for the other (with the default IndexSearcher cache on 9.x and 10.x), and IndexWriter's delete buffer, a map keyed by query, keeps only the first of two such deletes. This goes against Query#equals, whose javadoc says a proper equals "is required so that QueryCache works properly", and against the class's own claim that it "can be used safely as a key of the query cache". Every release from 8.4.0 to 10.6.0 and main is affected; comparing the two fields in equals/hashCode fixes it and passes the sandbox search tests.

The bug (main f794ff5a505c)

#
  1. Two fields decide the matches. maxMultiTermExpansions and segmentOptimizationEnabled are final fields (PhraseWildcardQuery.java:95-96).
    • The budget: createWeight starts with remainingExpansions = maxMultiTermExpansions and splits it over the multi-terms (:179-206); each multi-term walks the segments, smallest first (:146-153), and a segment that uses up its share stops the walk (:436-458, :498-516). Terms past the budget are never expanded, so documents that only contain them do not match.
    • The flag: with it on, a segment that lacks a phrase term is removed from the walk (:400-403, :454-457), so it no longer uses up budget. On a 2-segment index (budget 2; the smaller segment holds b1 b2 but no x), "x b*" matches doc 0 with the flag on and nothing with it off.
  2. Equality ignores both. equals returns slop == pwq.slop && phraseTerms.equals(pwq.phraseTerms); hashCode returns classHash() ^ slop ^ phraseTerms.hashCode() (:323-334).
  3. Core code trusts equality.
    • BooleanQuery keeps FILTER and MUST_NOT clauses in HashSets (BooleanQuery.java:137-138); rewrite drops duplicates (:343-361) and returns MatchNoDocsQuery("FILTER clause also in MUST_NOT") when a FILTER clause equals a MUST_NOT clause (:363-368; "MUST clause also in MUST_NOT" at :379).
    • LRUQueryCache.get builds QueryCacheKey(readerKey, key, key.hashCode()) (LRUQueryCache.java:420-427), whose equals compares the segment's cache key and Query#equals (:1309-1342).
    • BufferedUpdates.deleteQueries is a HashMap<Query, Integer> (BufferedUpdates.java:64); addQuery calls deleteQueries.put(query, docIDUpto) (:110-111), so an equal later query keeps the first query object as key and only moves its doc-id limit.

Scope, executed on main

#
  • 8 clause pairs of wide (limit 100) and narrow (limit 1), one per BooleanQuery rewrite rule that compares clauses, with SHOULD + SHOULD in both orders: 7 give a wrong count, e.g. MUST(wide) + MUST(narrow) counts 2 instead of 1 and SHOULD(narrow) + SHOULD(wide) 1 instead of 2; only SHOULD(wide) + SHOULD(narrow) is right, by order (also on 10.6.0).
  • Delete-by-query on a bx, a by, c: narrow then wide leaves 2 documents instead of 1; wide then narrow is right (the narrow matches are a subset).
  • The segment flag: two queries that differ only in the flag compare equal with equal hash codes and match [0] and [].
Exposure and likelihood361 words
  • Who is hit. For example an application that tunes the limit per request and runs both forms through one searcher; nothing in the Lucene tree outside the class's own tests builds the class, and no use was found in Elasticsearch, OpenSearch or Solr code.
  • What goes wrong. Wrong hit counts and hit sets with no error; a cached result served for the other query; an acknowledged delete-by-query not applied, so documents the wider delete matches stay in the index.
  • The query cache, plainly. LRUQueryCache stores one entry per (segment, query) and finds it through Query#hashCode and Query#equals. "a b*" with limit 100 and with limit 1 have the same hash and compare equal, so they share one entry: whichever is cached first fills it with its own matches, and the other reads them. The cache never sees the limit.
  • Default cache on released versions. On 9.x and 10.x every IndexSearcher has a default LRUQueryCache (IndexSearcher.java:95-99 on 10.6.0) for segments of at least 10,000 documents that hold more than half the average segment size (LRUQueryCache.java:175-177, :187-197 on 10.6.0), caching this class once a query has been seen 5 times (the threshold for queries the policy does not count as costly; MultiTermQuery, point and TermInSetQuery queries need 2: UsageTrackingQueryCachingPolicy.java:45-53, :122-128 on 10.6.0). The cache serves only searches that need no scores (QueryCache.java:27-30), such as counts and FILTER or MUST_NOT clauses. Executed on 10.6.0 and 9.12.3 with a plain new IndexSearcher(reader): one 12,000-document segment, the limit-100 query counted 10 times, then the limit-1 query counts 2 instead of 1. Main disabled the default cache (IndexSearcher.java:82-84, #14187, 2025-04-02, in no release yet), so there the same program counts 1; with an application-installed cache main shows the collision too.
  • Related, separate bug. The class's Weight reports isCacheable true although its budget depends on the reader's whole segment set. Fixing that would also keep budget-limited queries out of the cache, so either fix removes the cache collision; the BooleanQuery and delete consequences need this fix.
  • Scale. Two documents are enough (the default cache only needs one segment of 10,000 documents). Silent, with assertions on and off.

Why it looks unintended

#
  • A proper Query#equals "is required so that QueryCache works properly", and this class says it "can be used safely as a key of the query cache".
  • The limit decides the matches (2 vs 1 here); core expansions such as FuzzyQuery keep their limits in equals.
  • Upstream fixed the same omission in sandbox CombinedFieldQuery (LUCENE-10026), because rewrites dropped clauses.
The full argument200 words
  • The contract. Query#equals asks subclasses to implement equality properly: "This is required so that QueryCache works properly" (Query.java:96-97). It adds a softer rule of thumb, "Typically a query will be equal to another only if ... its document-filtering properties are identical" (:99-100); the firm part is the cache requirement, and here the cache serves wrong hits. The Builder javadoc says the budget is "across all multi-terms and across all segments" (PhraseWildcardQuery.java:585-592), and jpountz noted on #14168 (2025-01-27) that a low maxMultiTermExpansions may miss matches.
  • The class's own claim. The PhraseTerm javadoc: the query "is immutable and light itself and can be used safely as a key of the query cache" (:677-679).
  • Core precedent. FuzzyQuery.equals compares maxExpansions (FuzzyQuery.java:249), TopTermsRewrite.equals compares size (TopTermsRewrite.java:186), MultiTermIntervalsSource.equals compares maxExpansions (MultiTermIntervalsSource.java:175).
  • History. equals/hashCode are as old as the class (8485b5a939c, LUCENE-8983); the issue and PR discussion (#10026, apache/lucene-solr#889) never mention equality or caching, and no upstream test compares two instances. LUCENE-10026 (#212, b9a70c28b69, 2021-07-16, Julie Tibshirani) fixed sandbox CombinedFieldQuery: "The previous equals and hashCode methods only compared query terms ... rewrites could accidentally drop CombinedFieldQuery clauses."
The devil's-advocate check268 words

Strongest case for "intended": the limit is a resource guard rail, not part of what the phrase means (Michael Froh on java-user@, 2020-02-17: maxMultiTermExpansions "serves as a guard rail, to put a rough bound on memory consumption and query execution time"), so two limits could count as the same phrase cut off at different points; the flag's javadoc says it only "changes the scoring. The result ranking is preserved." (PhraseWildcardQuery.java:606-609), and Query#equals says only that equal queries "typically" have identical document-filtering properties; and the class is @lucene.experimental. There is also a counter-example in lucene/queries: SpanMultiTermQueryWrapper.equals/hashCode ignore its settable rewrite method (SpanMultiTermQueryWrapper.java:86-87, :132-139), which can carry a top-N expansion limit; dsmiley asked in a 2018 review on #7571 (LUCENE-6513, still open): "SpanMultiTermQueryWrapper: shouldn't equals() consider the rewrite method?".

Why it fails: the guard rail decides which documents match (2 vs 1 on two documents), which is exactly what breaks the cache requirement of Query#equals, and core keeps its own guard rails in equals. SpanMultiTermQueryWrapper is an open question, not a decision, and its rewrite method is a mutable setting, while this class's limit and flag are final constructor arguments and the class itself says it is safe as a query-cache key. The flag's "only scoring" sentence is wrong once the budget binds ([0] vs [] on a 2-segment index). "Experimental" allows API changes, not a wrong equals, and upstream fixed a sandbox query for the same reason. An independent reviewer from another model family (OpenAI GPT-5.6) and the intended-behaviour verifier both rated the "intended" case weak.

Suggested fix

#

Recommended (a) Compare both fields in equals and hashCode (recommended, validated)

In PhraseWildcardQuery.equals and hashCode, also compare maxMultiTermExpansions and segmentOptimizationEnabled (+9/-2). The repro passes, as do TestPhraseWildcardQuery (11 tests, assertions on and off) and the whole sandbox search test package (115 tests, the new one included).

return slop == pwq.slop
    && maxMultiTermExpansions == pwq.maxMultiTermExpansions
    && segmentOptimizationEnabled == pwq.segmentOptimizationEnabled
    && phraseTerms.equals(pwq.phraseTerms);

// hashCode
int h = classHash();
h = 31 * h + slop;
h = 31 * h + maxMultiTermExpansions;
h = 31 * h + Boolean.hashCode(segmentOptimizationEnabled);
return 31 * h + phraseTerms.hashCode();

(a) Compare both fields in equals and hashCode (recommended, validated)

#

The change, +9/-2 in PhraseWildcardQuery.java:

return slop == pwq.slop
    && maxMultiTermExpansions == pwq.maxMultiTermExpansions
    && segmentOptimizationEnabled == pwq.segmentOptimizationEnabled
    && phraseTerms.equals(pwq.phraseTerms);

// hashCode
int h = classHash();
h = 31 * h + slop;
h = 31 * h + maxMultiTermExpansions;
h = 31 * h + Boolean.hashCode(segmentOptimizationEnabled);
return 31 * h + phraseTerms.hashCode();

Trade-offs

  • None known: two queries that differ only in limit or flag stop sharing cache entries and clauses, which is the point.
  • The hashCode style is a choice; keeping the ^ form and adding the two fields would also be correct.
  • Optionally correct the flag's javadoc ("The result ranking is preserved.", :606-609), which is not true once the budget binds.

What the checks validated

  • Clean scratch worktree of f794ff5a505c, gradle, OpenJDK 25.0.3, 2026-11-10: the repro fails on stock with assertions on and off and passes with the fix, on and off.
  • With the fix: TestPhraseWildcardQuery 11 of 11, on and off; the org.apache.lucene.sandbox.search package (the 14 upstream classes plus the new test), 115 tests (5 skipped), 0 failures (on); :lucene:sandbox:checkGoogleJavaFormat passes.
  • Other checks of this change alone: the bounded-exhaustive check has 0 equal pairs that match differently (215,776 on stock), and the clause-pair probe passes 8 of 8. Re-run on main (-da) during this page's fact check: the delete-by-query probe leaves 1 document (right; stock leaves 2), and the two segment-flag queries no longer compare equal. (The finder's own delete and flag probe runs used this change together with the fix of the related bug, option (c).)

(b) Compare only the budget, and fix the flag's javadoc

#

Add maxMultiTermExpansions to equals/hashCode and document the flag as scoring-only.

Trade-offs

Smaller, but the flag also changes matches once the budget binds, so two equal queries could still match differently. Not recommended.

(c) Complementary: make the Weight not cacheable once its expansion budget runs out (a related bug)

#

The fix of the related, separate bug described under Exposure and likelihood: the Weight reports itself cacheable although its one expansion budget is spent across the reader's segments.

Trade-offs

Removes the cache collision too, but not the BooleanQuery or delete-by-query consequences; a separate fix for a separate bug.

Downstream note

#

Downstream, a MUST_NOT exclusion or a retention delete built from two such queries can silently fail to apply, but only the application's own code can create the pair.

How it was found

#

Semi-formal: code reading and public-API probes, then a bounded-exhaustive check on the stock jar. It ran every segment of 1-2 documents over a 3-term vocabulary as one- and two-segment readers (8,190), three phrase shapes, limits 1, 2, 3 and 100, flag on and off: of 687,960 equal query pairs, 215,776 match different documents.

The method in full89 words

Method: translation validation, bounded and exhaustive. Each pair of queries that equals calls equal was run on the same small reader and their matching documents compared; an independent exact-phrase reference agreed with the real query at limit 100 and contained every budget-limited result (196,560 checks, 0 mismatches). Vocabulary terms with 1-, 3- and 4-byte UTF-8 characters; shapes a b*, b* a, b* b*.

With the recommended fix the check finds 0 equal pairs that match differently. The finding was reduced to the one-test JUnit shown here.

Summary
You index 'a bx' and 'a by' and build the phrase "a b*" twice with PhraseWildcardQuery.Builder, once with maxMultiTermExpansions 100 (it matches both documents) and once with 1 (it matches one), and you expect FILTER(limit 100) + MUST_NOT(limit 1) to match one document. Instead equals and hashCode compare only slop and the phrase terms, so the two queries are equal and BooleanQuery rewrites the pair to MatchNoDocsQuery("FILTER clause also in MUST_NOT"): count 0. The same equality merges the two queries in a query cache (one limit's hits are returned for the other) and in IndexWriter's delete-by-query buffer (one of two deletes is lost), and segmentOptimizationEnabled is ignored the same way although it also changes the matches once the budget binds.
