OfflineSorter with an ExecutorService can leave temp files behind when sort() fails

With your own ExecutorService, a failed OfflineSorter.sort() (disk error, truncated input, interrupt) deletes only the temp files that exist at that moment and throws, without waiting for the sort jobs it already queued. Those jobs then run and can leave <prefix>_sort_N.tmp files that nothing deletes, in every release since 6.6.0.

The finding in 30 seconds

#

sort() cleans up on failure, but only the temp files that exist when it fails. A job still waiting in your pool writes its file later, and nobody deletes it.

Background: how OfflineSorter sorts

#
  1. OfflineSorter (org.apache.lucene.util) sorts more data than fits in memory: it reads the input in partitions that fill its RAM buffer, sorts each partition into a temp file named <prefix>_sort_N.tmp, and merges those files into one sorted output.
  2. Since 6.6.0 you can pass an ExecutorService to the 8-argument constructor: partition sorts and merges then run as background jobs, at most maxPartitionsInRAM partitions in memory at a time. Without one, every job runs on the calling thread.
  3. If sort() fails, it deletes the temp files it created and rethrows; its code says "So we can remove any partially written temp files on exception".

The finding, step by step

#
  1. Build an OfflineSorter with your own ExecutorService (the 8-argument constructor, maxPartitionsInRAM 2) and a 1 MB buffer, and sort 1,100 records of 1,000 bytes whose last record is cut short. Partition 1, 1,016 records, goes to the pool as a background sort job.
  2. Before that job runs, reading partition 2 reaches the cut-off record and throws EOFException. You expect sort() to throw it and leave only the input file, as it does without an executor.
  3. Instead sort() deletes only the temp files that exist at that moment (none yet) and throws. It neither cancels nor waits for the queued job.
  4. The job then runs and writes foo_sort_1.tmp, 1,016 sorted records (1,018,048 bytes), which nothing ever deletes. With ordinary 1- and 2-thread pools, 32 to 39 of 320 injected I/O failures left files behind this way; without an executor, 0 of 160.

Who is affected

#

Code that passes its own ExecutorService to the 8-argument constructor of this @lucene.internal class and whose sort() fails while a job is still queued or running. No in-tree caller on main does; 9.8.0's BPIndexReorderer did when given a ForkJoinPool. Up to one leftover temp file per unfinished job; no wrong result, and the failed sort() returns at once.

Mechanism, terms and numbers677 words

OfflineSorter.sort() wraps its Directory in a TrackingDirectoryWrapper "So we can remove any partially written temp files on exception". With a non-null ExecutorService (the 8-argument constructor, since 6.6.0), each partition sort and each merge runs as a job on that executor, and a job creates its temp file only when it runs. When sort() fails, its catch blocks delete a snapshot of the files created so far and rethrow, without cancelling or waiting for the jobs already submitted, so jobs that run afterwards can leave files nobody deletes. Without an executor every job runs inside submit(), and the same failure leaves nothing. In the repro a truncated 1.1 MB input leaves foo_sort_1.tmp (1,016 sorted records) behind; with plain 1- and 2-thread pools, 32 to 39 of 320 injected I/O failures leaked files. Successful sorts are unaffected, the failed sort() returns at once and no result is wrong. The class is @lucene.internal and no in-tree caller on main passes an executor, so the reach is small. Waiting for the submitted jobs (after making queued ones no-ops) before the cleanup fixes it.

Terms

#
  • Partition: as many input records as fit in the RAM buffer; reading one takes a partitionsInRAM permit (OfflineSorter.java:430-433).
  • Job: a SortPartitionTask (sorts one partition into a temp file) or a MergePartitionsTask (merges up to maxTempFiles temp files), submitted with exec.submit(...).
  • TrackingDirectoryWrapper: a Directory wrapper that records the name of every file created through it; getCreatedFiles() returns a copy of those names.

The bug

#
  1. sort() starts with // So we can remove any partially written temp files on exception: and wraps the directory in a TrackingDirectoryWrapper (:295-296).
  2. With exec != null the constructor keeps the caller's executor (:240-245); otherwise it uses a SameThreadExecutorService, whose execute just runs the job (:246-248; SameThreadExecutorService.java:34-37).
  3. Each partition becomes a job, Callable<Partition> job = new SortPartitionTask(trackingDir, part); (:309), submitted with segments.add(exec.submit(job)); (:311); merges are submitted the same way (:394-398).
  4. A job creates its temp file only when it runs: dir.createTempOutput(tempFileNamePrefix, "sort", ...) in SortPartitionTask.call (:630-631) and in MergePartitionsTask.call (:698-700).
  5. On failure both catch blocks (:363-369) call IOUtils.deleteFilesSuppressingExceptions(..., trackingDir, trackingDir.getCreatedFiles()) and rethrow. That set is a copy taken at that moment (TrackingDirectoryWrapper.java:70-73), and nothing touches the futures in segments: no cancel, no get.
  6. A job that had not yet created its file does so after the cleanup. Its name lands in the tracking set, but nobody reads the set again, and sort() gives the caller neither the generated names nor a way to wait for the jobs. A partition file stays unless a later merge consumes it (:749-753); a merge whose inputs the cleanup already deleted creates its output (:698-700), fails to open an input and leaves that output empty.

Without an executor every job has run before the failure is caught, so the snapshot is complete. A successful sort is fine too: it waits for the final job (:350, future.get() at :662), which waits for all its inputs.

The numbers

#

Stock main, the repro's input and executor (a small probe, not the repro): partition 1 holds 1,016 records; right after sort() throws EOFException the directory holds only input_tmp_0.tmp and one job is still queued; once it runs, foo_sort_1.tmp is there for good: 1,018,048 bytes, 1,016 records, a valid footer. With exec == null the same input leaves only input_tmp_0.tmp.

Natural timing, no test gating: a harness that injects one IOException per run into the Directory or one of its inputs or outputs (at each of the first 40 such operations of a sort and at 40 randomly chosen later ones, 80 runs per configuration) leaked files in 32 (assertions on) and 39 (off) of 320 failed sorts with 1- and 2-thread FIFO pools, and in 0 of 160 without an executor. Other executed triggers: an injected read error 1,000 entries into partition 2, and an interrupt while sort() waits for a partition permit.

Exposure and likelihood319 words
  • Who is hit. Callers of the 8-argument constructor with a non-null ExecutorService, the documented way to sort concurrently. The default constructors are not affected.
  • Reach. OfflineSorter is tagged @lucene.experimental and @lucene.internal. On main, hunspell SortingStrategy and the suggesters (SortedInputIterator, AnalyzingSuggester, FSTCompletionLookup) use the 2- or 3-argument constructors. In release 9.8.0 BPIndexReorderer (lucene/misc) passed its ForkJoinPool (when one was set) to this constructor; 9.9.0 dropped that use (#12712). A code search of the default branches of Elasticsearch, OpenSearch and Solr found no use of OfflineSorter.
  • What happens. Per failed sort, at most one leftover <prefix>_sort_N.tmp for each job that had not yet created its file: at most maxPartitionsInRAM partition jobs plus any merge jobs already submitted. There can be fewer, because a merge that runs later deletes the partition files it consumes: with maxTempFiles 2, two queued partition jobs and their queued merge left one file, the merge's output. A leftover partition file is a complete sorted copy of the records it held (1,016 in the repro); a merge whose inputs the cleanup had already deleted fails and leaves an empty output file with no footer (both cases executed by the fact check's probes). The orphaned jobs also keep their CPU, I/O and partition buffer until they finish. The documented maxPartitionsInRAM * ramBufferSize bound is per sorter and still holds: a later sort() on the same sorter waits for those permits, and can wait forever if the executor never runs the orphaned jobs (for example after shutdownNow() dropped them; code reading).
  • What does not happen. No wrong or partial result (sort() throws), the failed sort() does not hang, no index file change; a successful sort is unaffected. Assertions on or off make no difference.
  • Likelihood. Rare: a sort must fail (disk error, damaged input, interrupt) while a job is in flight; under natural timing about 1 in 10 injected failures leaked.

Why it looks unintended

#
  • The code states the intent: "So we can remove any partially written temp files on exception" (OfflineSorter.java:295).
  • Without an executor the same failure leaves nothing; the executor was added as an optional speed-up, with no new duties for callers.
  • Leftover temp files were fixed as bugs before (LUCENE-4209); no test sorts with an executor and fails.
The full argument290 words
  • Intent stated in the code. No javadoc promise: sort() says only "Sort input to a new temp file, returning its name" (:286). The code states the goal at :295, again at :353-354 ("We should be explicitly removing all intermediate files ourselves unless there is an exception"), and in the catch blocks (:363-369).
  • The executor is presented as optional. Constructor javadoc: "If you pass a non-null ExecutorService then it will be used to run sorting operations that can be run concurrently" (:226-227); CHANGES: "OfflineSorter can now run concurrently if you pass it an optional ExecutorService" (lucene/CHANGES.txt:8312-8313). Nothing tells the caller to drain the executor or to delete files after a failure, and the caller never gets the generated names.
  • History. LUCENE-4209 (CHANGES :15305-15308) fixed temp files left behind in the system temp directory. In LUCENE-6829 (#7887, 2015) Mike McCandless wrote: "I cutover to TrackingDirectory in OfflineSorter to manage deleting temp files on exception". When BKDWriter used this class, TestBKD.testWithExceptions checked "BKDWriter should fully clean up after itself" (7.7.3, TestBKD.java:413). LUCENE-7792 (db92a9efc2ee) moved file creation into jobs and kept the one-shot cleanup; its same-day follow-up 25f1dd2f9b2 "add try/finally to make sure semaphore is released on exceptions" shows the failure paths were meant to be handled. The #8843 thread never discusses a failure with jobs in flight.
  • Tests. testBitFlippedOnInput1/2 use the 2-argument constructor and testBitFlippedOnPartition1/2 pass null (TestOfflineSorter.java:356, :414, :460, :528); randomExecutorServiceOrNull() is used only where the sort succeeds (:96, :120, :145, :551).
  • Legal trigger. Public constructor, a standard executor, BufferSize.megabytes(1); the class detects corrupt input on purpose (compare testBitFlippedOnInput2) and catches the interrupt explicitly (:363).
The devil's-advocate check194 words

The strongest case for "works as designed" (the intended-behaviour verifier and the cross-model reviews): the class is @lucene.experimental and @lucene.internal; the executor belongs to the caller, who can shut it down and delete files by prefix; the cleanup is best effort (deleteFilesSuppressingExceptions); there is no javadoc promise; and TaskExecutor waiting for sibling tasks after a failure (#12523) was labelled an enhancement. A maintainer may call the fix an improvement, or deprecate the executor option, which nobody in-tree has used since 9.9.0.

Why it fails: @lucene.internal is about API stability, not about cleanup being optional. Nothing documents a duty to drain the executor, and sort() gives the caller no completion signal and no list of the generated names: short of shutting down its own, possibly shared, executor or polling the Directory, it cannot tell when the orphaned jobs are done. The class already holds the futures and waits on them when the sort succeeds. "Best effort" covers a delete that fails, not a file created after the cleanup ran. The argument limits priority (low), not validity; this is an inference from the code, its comments and history, not a maintainer ruling.

Suggested fix

#

Recommended A. Abort, then wait for every submitted job before the cleanup

On failure, mark the sort aborted so jobs that have not started do nothing, then wait for every submitted job before deleting the created files (+49/-2 in OfflineSorter.java). The repro then passes with assertions on and off; TestOfflineSorter (incl. nightly), the suggest tests and :lucene:core:check pass. Trade-off: a failing sort() waits for running jobs.

All options and trade-offs4 options · 1,245 words

Option A was run through gradle in a scratch worktree of 645d4fe14a20 and is the suggested option: validated against main's tests, not against every legal executor, so it needs a maintainer's design review. B, C and D are alternatives a maintainer may prefer; none was tried. No open PR touches OfflineSorter.java. The one-test repro passes under any option that leaves no file once the queued job has run.

A. Abort, then wait for every submitted job before the cleanup (validated by the checks) (recommended)

#

sort() records every future it submits (partition and merge jobs) and a fresh aborted flag per call. Both catch blocks first call abortAndAwaitTasks(): set the flag, then get() every submitted future, ignoring the job's own failure, retrying on InterruptedException and restoring the interrupt flag at the end. Each job starts with: if aborted, return the permit (partition jobs) and throw CancellationException, so queued jobs create no file. Only then are trackingDir.getCreatedFiles() deleted.

Trade-offs

  • A failing sort() returns only after the running jobs have finished (bounded: at most maxPartitionsInRAM partition sorts plus running merges) and a worker has picked up each queued job (which returns at once). On a stalled or saturated caller-owned executor, or one shut down with shutdownNow() that drops queued jobs, the wait can be long or never end. The success path already waits on the executor the same way; today's failure path does not. For example, a sort() running on the only worker of its own executor already deadlocks on success (it waits for a job queued behind itself); with A it waits the same way on failure.
  • The wait continues through further interrupts (the flag is restored), so a second interrupt cannot cut a failing sort short.
  • Waiting before the snapshot also removes the unconfirmed getCreatedFiles() copy race.
  • The new fields are set per call but live on the instance, and the jobs read the flag when they run, so A requires one sort() at a time per sorter (sortInfo is shared the same way; testThreadSafety uses one sorter per thread). Passing the call's list and flag to the jobs would drop that requirement. submitted keeps the finished futures until the next call and could be cleared at the end.
  • The diff uses unnamed catch variables (catch (InterruptedException _), Java 22+): fine for main (minimum Java 25); a 10.x backport (minimum Java 21) needs named variables.
  • No API or format change; the success path adds one list append per job.

B. Each job deletes its own output when it sees the abort flag

#

Set the flag in the catch blocks as in A, and let every job check it again after writing its file and delete that file, also when the job fails because the cleanup removed its inputs.

Trade-offs

sort() throws at once, but the files disappear only when the jobs finish, sort() gives the caller no signal when that is, and the getCreatedFiles() copy race stays for a separate TrackingDirectoryWrapper fix (compare #13142). Not tried.

C. Cancel the queued futures and wait only for running jobs

#

Future.cancel(false) on each queued job, then wait for the running ones before the cleanup.

Trade-offs

A cancelled SortPartitionTask never runs its finally, so its permit (taken in readPartition, released only by the job) would be lost and a later sort() on the same sorter could block, unless sort() releases it itself (the same permit accounting as LFV-384). Relies on the executor's futures honouring cancel. Not tried.

D. Deprecate or remove the executor option

#

No in-tree caller has used the 8-argument constructor with an executor since 9.9.0, and the class is @lucene.internal.

Trade-offs

Simplest for main, but it leaves released versions as they are for the callers that use it, and it is an API decision for the maintainers.

Downstream note

#

A leftover partition file holds a sorted copy of records the failed sort had already read, so an application that deletes its sort input for data-retention reasons can keep a copy after such a failure.

How it was found

#

TLA+ model checking (TLC) of a protocol model of sort(): the invariant "after a failed sort, once every job has finished, no temp file remains" fails for every pool size of 1 or more and holds without an executor. A fault-injection harness then showed it on the real jar, and the repro was cut to one deterministic test.

The method in full287 words

Method: formal (TLA+ model checking, the tool's own counterexample). In the hunt's offline-sorter hunt (2026-10-26, main ea57360912ed), the hunting AI tool wrote a protocol model of sort(): the main thread, the partitionsInRAM semaphore, a FIFO executor with W workers, partition and merge jobs, the merge cascade, the final merge and the failure cleanup, with one injected failure (an I/O error, corruption or an interrupt) at any step. Record contents are not modelled.

  • With no failure, TLC found no deadlock, every partition reaches the result exactly once, and only the result file remains.
  • With one failure, the invariant FailureClean ("after a failed sort and once every job has finished, no temp file remains") is violated in all 12 configurations with 1 or 2 workers (shortest trace 9 states: partition 1 queued, the main thread fails, the cleanup deletes nothing, the queued job then creates its file) and holds in all 6 with 0 workers, the same-thread executor.
  • The AI tool wrote the model and chose the invariant, the property the code's own comment states; TLC then found the failing schedule among every fault position and job schedule it explored, so the scenario was not hand-picked.

A fault-injection harness on the stock jar (one IOException per run, injected into the Directory or one of its inputs or outputs at each of the first 40 such operations and at 40 randomly chosen later ones; plain thread pools, no gating) confirmed it: 32 and 39 of 320 failed sorts leaked with 1- or 2-thread pools, 0 of 160 without an executor, 0 of 480 with the fix. The hunt's two-test JUnit followed; on 2026-10-29 it was replaced with the one deterministic test, because the interrupt test was not deterministic.

LFV-357, snapshot of 2026-11-09

Registry title
OfflineSorter.sort with an ExecutorService runs its failure cleanup before the partition-sort and merge tasks it already submitted have finished, so each task still queued or running leaves a temp file (prefix_sort_N.tmp) behind that nothing deletes (released since 6.6.0)
Area
util / OfflineSorter concurrent sort (temp-file cleanup on failure)
Priority
Low, rank 1128: OfflineSorter leaves stray temp files behind, a minor resource leak that happens only after a failed or interrupted run with an opt-in executor, the same exception-path leak profile as LFV-309.
Impact class
minor
Impact note
Only applications that build OfflineSorter (tagged @lucene.experimental and @lucene.internal) with the 8-argument constructor and their own non-null ExecutorService (opt-in since 6.6.0; no in-tree caller on main and none found on the default branches of Elasticsearch, OpenSearch or Solr) and whose sort() fails (an I/O error, a truncated or corrupt input file, or an interrupt of the sorting thread) while a submitted task is still queued or running: each such task writes one temp file after the cleanup has run, which nothing deletes, and keeps using CPU, its partition buffer and I/O after the caller has seen the exception; bounded per failed sort (at most maxPartitionsInRAM partition tasks plus merges already submitted), no wrong result, no hang, no index file touched; ordinary scale, every release 6.6.0 to 10.6.0 and main.
Summary
You give OfflineSorter your own ExecutorService so it sorts partitions in parallel, and when sort() fails (an I/O error, a truncated input file, or an interrupt of the sorting thread) you expect it to delete every temp file it created, as it does without an executor and as its own code comment says ('So we can remove any partially written temp files on exception'). Instead sort() deletes only the temp files that exist at that moment and rethrows, without waiting for or cancelling the partition-sort and merge tasks it already handed to the executor. Those tasks then run and each writes a new prefix_sort_N.tmp file that nothing ever deletes (executed: the directory holds no sorter file right after sort() throws, and foo_sort_1.tmp once the queued task has run; with exec == null the same failure leaves nothing).
