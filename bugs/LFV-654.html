Nori user dictionary: a trailing space or inline comment on a noun's line can change how the next word is analysed

The nori user-dictionary lines 사람 (trailing space) and 사람 # memo define the same noun as 사람, yet with them KoreanAnalyzer indexes 사람이나 ("person or") as [사람][이] instead of [사람]. Nori reads the noun's ending from the end of the line, in every release since 7.4.0.

The bug in 30 seconds

#

Each user noun stores a right context id that says whether its last syllable ends in a consonant, because the reading of the next word depends on it. Nori takes the noun from the line's first whitespace-separated part, but the id from the line's last character.

  1. Give KoreanAnalyzer a user dictionary whose line for 사람 ("person") ends with a space, 사람 , or carries a comment, 사람 # memo. Nori deletes # memo but keeps the space before it.
  2. You expect the result of the plain line 사람: the parser splits lines on whitespace, so all three lines define the same noun. With 사람, 사람이나 ("person or") is indexed as [사람]: the stop filter drops the particle 이나 (tag JX).
  3. Instead the noun's right context id, which says whether its last syllable ends in a consonant, is read from the line's last character. A space is not Hangul, so 사람 gets the generic id 3533 instead of 3535.
  4. That id scores the next word. On main, from 3535 the particle 이나/JX is cheapest (cost -10 vs 321 for 이/VCP 나/EC); from 3533 이/VCP 나/EC wins (184 vs 315), so [사람][이] is indexed. On 9.12.3, 학교가방을 샀다 ("bought a school bag") with the line 학교 loses the term 가방 ("bag").
  5. No error or warning. Every nori release from 7.4.0 to 10.5.2 and main is affected; a comment written with no space (사람# memo) is not.

Who is affected

#

Applications that give nori a user dictionary (opt-in) with a noun line ending in whitespace or in a # comment after a space. With correct context ids only some continuations change (이나, 과, 다, noun + noun compounds); on stock 10.x and main (LFV-658 mixed in) also 가 and 이. Silent, at index and query time, on every occurrence.

Mechanism, terms and numbers694 words

Nori's user dictionary stores, for each custom noun, a right context id that tells the tokenizer whether the noun's last syllable ends in a consonant (a coda), because the reading of the next word depends on it. UserDictionary takes the noun from the line's first whitespace-separated part but the id from the last character of the whole line (UserDictionary.java:94). A line with trailing whitespace, or with an inline # comment after a space (the comment is removed, the space stays), therefore gives the same noun the generic id 3533 instead of 3535 or 3534. The next morpheme can then get another part of speech, and KoreanAnalyzer's default stop filter keeps or drops other terms: 사람이나 ("person or") is [사람] with the line 사람 but [사람][이] with 사람 (9.12.3, 10.5.2 and main), and on 9.12.3 학교가방을 샀다 ("bought a school bag") loses the term 가방 ("bag") with 학교 . Silent and deterministic; opt-in (user dictionaries only); present since nori was added in 7.4.0. Fix: read the character from the noun, with a guard for an empty noun.

Terms

#
  • Nori user dictionary: a text file with one custom noun per line, optionally followed by its parts (세종시 세종 시); # starts a comment. It is loaded with UserDictionary.open(Reader) and passed to KoreanTokenizer, KoreanAnalyzer or the korean factory's userDictionary file.
  • Right context id: a number per dictionary entry that the tokenizer's Viterbi search uses to score the morpheme that follows. User nouns get one of three: 3535 when the last syllable has a final consonant (a coda, as in 사람), 3534 when it has none (학교), 3533 when the last character is not Hangul (UserDictionary.java:40-45). Korean particles depend on the coda: 사람이 but 학교가.
  • Part-of-speech stop filter: KoreanAnalyzer drops tokens whose tag is in KoreanPartOfSpeechStopFilter.DEFAULT_STOP_TAGS (:36-68): endings such as EC and particles such as JX; the copula VCP is kept.

The bug

#
  1. UserDictionary.open removes comments with line.replaceAll("#.*$", "") and keeps the line untrimmed (UserDictionary.java:56-64): 사람 # memo becomes 사람 .
  2. The constructor takes the noun from entry.split("\\s+")[0] (:89-90). Java's split drops trailing empty strings, so 사람, 사람 and 사람\t give the same noun, no segmentation and the same FST key (:125-131).
  3. But it picks the id from char lastChar = entry.charAt(entry.length() - 1);, the last character of the whole line (:94-103). A space or tab is not Hangul, so the noun gets 3533.
  4. Viterbi stores that id on the noun's node and uses it as the left side of the connection cost to the next morpheme (morph/Viterbi.java:469-472, :530-539), so another reading of what follows can win, and the stop filter then keeps or drops other terms. In every executed probe the noun itself is still emitted (the code does not guarantee it: the id enters the cost of every path through the noun).
  5. Secondary trigger, same line: a segmentation shorter than the noun, 세종시 세종, ends in 종 (coda), so 세종시 gets 3535 instead of 3534; only segmentations longer than the noun are rejected (:114-121).

Exposure and likelihood282 words
  • Who is exposed. Applications that load a nori user dictionary: the KoreanTokenizer constructors that take a UserDictionary (KoreanTokenizer.java:104-106, :121-123, :154-159), KoreanAnalyzer(userDict, ...) (KoreanAnalyzer.java:59), or the korean factory's userDictionary file (KoreanTokenizerFactory.java:44-57, :111-123). The classes are @lucene.experimental. Without a user dictionary nothing changes.
  • What it takes. A noun line that ends with whitespace, or with a # comment after a space. Both are easy to produce in a hand-edited file. A comment written right after the noun (사람# memo) is not affected.
  • When it shows. The text must then continue the noun with something whose reading depends on the context. With correct context ids (9.12.3, or main with LFV-658's fix) an independent reproducer saw 0 of 336 well-formed noun + matching-particle sentences change, but continuations such as 이나, 다, 지, 나, 과 and noun + noun compounds such as 학교가방 do: 67 of 1,420 probe sentences on main with LFV-658's fix, 113 of 1,420 on stock main, which mixes in LFV-658. The finder's sweep of 16 nouns x 21 particles (plain line vs # memo) found 34 differences on 9.12.3 and 61 on main (reported by the finder; the raw output was not kept and the sweep was not re-run).
  • Effect. Extra terms ([사람][이]), lost terms (가방 on 9.12.3) or another part of speech for the morpheme after the noun, at index and at query time alike. No exception, with assertions on or off.
  • Scale. No threshold: one dictionary line is enough, and it applies to every occurrence of that noun. A fix changes the terms of fields analysed with an affected line, so those fields need a reindex.

Why it is a bug, not intended

#
  • The constants' comments tie the id to the noun: "NNG right with hangul and a coda on the last char" (UserDictionary.java:42-45).
  • The same method treats trailing whitespace as a separator: 사람 and 사람 get the same noun and FST key; only the id differs.
  • LUCENE-8603 (7.7.0) fixed wrong user-noun right ids as a bug; no test pins the line-based choice.
The full argument266 words
  • The contract. RIGHT_ID_T is the "NNG right with hangul and a coda on the last char", RIGHT_ID_F "... and no coda on the last char" (UserDictionary.java:42-45). The coda belongs to the noun's last syllable, and the noun is token; the class javadoc speaks of "adding custom nouns (세종) or compounds (세종시 세종 시)" (:32-35).
  • The parser's own rules. Whitespace is a separator: split("\\s+") gives the same surface and the same (absent) segmentation for 사람 and 사람 (:89-90), and the FST key is the same (:125-131). The implementation removes # and everything after it anywhere on a line (// Remove comments above replaceAll("#.*$", ""), :57-58), although the line grammar is not documented; the space before # survives only because the line is not trimmed.
  • Tests. userdict.txt and TestKoreanTokenizerFactory.java:72 use only whole-line comments and complete segmentations, and no test pins a user entry's right-id value or checks that it is the same however the line is written (TestKoreanTokenizer.testDuplicate only checks getRightId(3) != 0 to count deduplicated entries, TestKoreanTokenizer.java:563-577). With the fix, all 85 upstream nori tests that ran pass.
  • History. The line is in nori's first commit (LUCENE-8231, e851b89cbeb1); neither #9278 (62 comments) nor any later commit explains reading the line's end. LUCENE-8603 (7.7.0, listed under "Bug fixes": "Fix the inversion of right ids for additional nouns in the Korean user dictionary", lucene/CHANGES.txt:6910-6911) fixed the values of the same three constants.
  • Design evidence only. An independent C++ port of nori strips comments and whitespace and takes the coda from the surface term.
The devil's-advocate check225 words

The strongest case for "not a bug" (the intended-behaviour checker, the cross-model intended lens and the adjudication): Lucene documents no line grammar for the nori user dictionary (open has no javadoc; the factory says only "User dictionary path"); the classes are @lucene.experimental; first-party tests use only whole-line comments; kuromoji accepts # comments only at line start since LUCENE-8596 (CHANGES.txt:4839-4841), so an inline comment may count as unsupported; and kuromoji rejects segmentations that do not add up to the surface (LUCENE-8933, #9976).

Why it fails: it does not cover plain trailing whitespace, which nori's own parser already treats as a separator, and nori strips # comments anywhere on the line (it never adopted LUCENE-8596's line-start rule). The constants' comments tie the id to the noun, and LUCENE-8603 treated wrong user-noun ids as a bug. The case is strong for the shorter-segmentation trigger (세종시 세종): the documented example is a complete segmentation, kuromoji requires the parts to add up to the surface, and the line is plausibly malformed input that nori accepts only because it does not validate it; present it as a separate validation consequence, or leave it out. Verdicts: devil's advocate real (medium-high for whitespace and comments, low for the segmentation); cross-model intended lens real (high), its intended argument "moderate" and failing for bare trailing whitespace; adjudication confirmed (high).

Suggested fix

#

Recommended Read the character from the noun, and reject an empty noun

In UserDictionary's constructor, read the coda from the noun (token) instead of the whole line, after rejecting an empty noun (+7/-1). Validated: the new test passes, as do the 85 upstream nori tests that ran and :lucene:analysis:nori:check. Ship it with the fix for the stale context ids (LFV-658); affected fields need a reindex.

Read the character from the noun, and reject an empty noun (validated by the checks) (recommended)

#

Take lastChar from token, the surface form, instead of the cleaned line (+7/-1 in UserDictionary.java). The guard matters: a line that starts with whitespace ( 학교) gives token = "". Stock main rejects that line later with IllegalArgumentException: ... the segmentation is bigger than the surface form (); without the guard token.charAt(-1) would throw StringIndexOutOfBoundsException first. With the guard it stays an IllegalArgumentException, with a clearer message. Moving the right-id block below the segmentation check instead keeps the old message; that variant is the one the diagram's fix sketch shows, and it was also executed (every 사람 line form gives 3535 and [사람]; 사람 still throws IllegalArgumentException). It also fixes the secondary trigger (세종시 세종 now gets 시's id).

Trade-offs

  • On 10.x and main, until LFV-658 is fixed, lines with trailing whitespace move from the generic id to the stale coda ids, so their analysis changes, and not always for the better: after this fix 학교가 reads as 가/VV with every line form. Ship both fixes together, or at least cross-reference them; with both, the independent reproducer's sweeps show 0 differences.
  • Fields analysed with an affected line need a reindex; worth a CHANGES line.
  • Cost: none to speak of (one charAt at dictionary load; not benchmarked).

Workaround until a fix ships

#

Keep noun lines free of trailing whitespace and put comments on their own line, or right after the noun with no space (사람# memo behaves like 사람, executed). A loader that strips each line removes the trailing-space form but not 사람 # memo unless it also removes comments.

Downstream note

#

Products that pass user-dictionary lines to nori unchanged inherit this, and after a fix, fields indexed with an affected line keep their old terms until they are reindexed.

How it was found

#

Semi-formal. While building an exhaustive minimum-cost reference for the CJK tokenizers' Viterbi lattice, the finder read UserDictionary.java:94, suspected that the id comes from the line, and confirmed it with a differential probe of 336 noun + particle inputs, plain line vs # memo (the finder reports 34 differences on 9.12.3 and 61 on main; not re-run).

The method in full182 words

Method: differential probe of the stock jar (the hunt's "semi-formal" tier), during a hunt unit that checked the CJK tokenizers' Viterbi output against an exhaustive minimum-cost path over the same dictionary data (kuromoji first, then nori), 2026-10-27, main a9779ef3c193.

  • While modelling nori's user-dictionary costs for that reference, the finder read UserDictionary.java:94 and saw that the right id comes from the cleaned line, not from the noun.
  • A differential probe, NoriWsSweep, analysed 16 user nouns x 21 particles = 336 inputs, each with the plain line and with the same line plus # memo: the finder reports 34 differences on 9.12.3 and 61 on main (the raw output was not kept; not re-run).
  • The finder then wrote a public-API JUnit (2 of 2 fail on main, 10.5.2, 9.12.3 and 9.0.0) and the one-line fix (later given an empty-noun guard). No solver or model checker produced the signal.
  • Independent AI tools reproduced and judged it (see the checks). The same unit also found a separate root cause in the same class, the stale context ids (LFV-658), filed as its own bug.

LFV-654, snapshot of 2026-10-29

Registry title
Nori UserDictionary picks a user noun's right context id (last syllable with a final consonant, without one, or not Hangul) from the last character of the whole entry line instead of the noun, so a trailing space or an inline comment ('학교 # memo') changes how the word after the noun is analysed
Area
analysis / nori UserDictionary (right context id of user nouns, used by the Viterbi connection costs)
Priority
Medium, rank 145: In the opt-in nori user dictionary, an easy slip like a trailing space or a spaced inline comment silently changes the analysis and drops terms, but it also needs a context-dependent continuation.
Impact class
silent wrong results
Impact note
Hits applications that give KoreanTokenizer, KoreanAnalyzer or KoreanTokenizerFactory a user dictionary (opt-in) in which a noun line ends with whitespace or carries an inline '#' comment after a space (secondary: a segmentation whose last part ends in another syllable than the noun, such as '세종시 세종'): after every occurrence of that noun the tokenizer scores the next morpheme with the wrong right context, so for some continuations (이, 가, 과, 와, 이나, noun+noun compounds) the next morpheme gets another part of speech and KoreanAnalyzer's default part-of-speech stop filter indexes a spurious term or loses or changes a real one (9.12.3: '학교가방을 샀다' loses the term 가방); ordinary text, no scale, deterministic with -ea and -da, no exception, the user noun itself is still emitted, and with correct context ids well-formed noun+matching-particle sentences were unaffected in the independent reproduction's probes; every release 7.4.0 to 10.5.2 and main.
Summary
You load a nori user dictionary whose line for the noun 학교 ('school') ends with a space, or carries an inline comment as in '학교 # memo' (the parser deletes '#' to the end of the line but keeps the space before it), and expect the same analysis as with the plain line '학교', because the parser splits the line on whitespace and gets the same noun with no segmentation. Instead UserDictionary.java:94 takes the noun's right context id, which tells the tokenizer whether the noun's last syllable ends in a consonant, from the last character of the whole line, here the space, so the noun gets the generic id and the word after it is analysed differently: on 9.12.3 '학교이' gives 이/VCP with '학교' but 이/J with '학교 ', and KoreanAnalyzer turns '학교가방을 샀다' into [학교][가방][사] with '학교' but [학교][방][사] with '학교 ', losing the term 가방 ('bag'). The two line forms disagree in every release from 7.4.0 to 10.5.2 and on main (main: '학교이' gives 이/JKS vs 이/VCP, '사람이나' gives [사람] vs [사람][이]), and a shorter segmentation such as '세종시 세종' takes the id from 종 (final consonant) instead of 시 (none) in the same way.
