Since 10.5.0, IndexWriter accepts a document that omits part of a field built from several field types

Since 10.5.0, IndexWriter accepts a document that omits part of a multi-type field, such as StringField("id") without the field's SortedDocValuesField("id"), which 10.4 rejects; sorts and range queries can then silently miss it. A 10.5.0 cache treats the field's first value type as its whole schema.

The bug in 30 seconds

#

Lucene requires every document that contains a field to give it the same data structures (postings, doc values, points, vectors), and checks each document against the field's established structures.

  1. Add doc 0 with StringField("id", "a") and then SortedDocValuesField("id", "a"). Field id now has two structures: postings and sorted doc values.
  2. Add doc 1 with only StringField("id", "b"). You expect IllegalArgumentException ("doc values type: expected 'SORTED', but it has 'NONE'"), as on 10.4.0; main also rejects it when doc 0 lists the doc-values value first, or after a flush.
  3. On 10.5.0, 10.5.1, 10.5.2 and main, doc 1 is accepted with no error, with assertions on or off. So is doc 1 = StringField + StoredField: it is checked, but against doc 0's leftover state.
  4. Why: after doc 0, Lucene caches the type of the field's first value, StringField's shared frozen type, as "validated", and skips the check for every later document whose first value has that type. But the field's schema came from two types.
  5. Effect: an accepted document lacks a structure, so a search that reads it can miss that document. In one segment of 20,000 documents with NumericDocValuesField + LongPoint, a doc-values-only document holding the top value 1,000,000 is accepted, and a default top-1 descending sort of a term query returns 999,999 (seen with that document at positions 10,000 to 19,999, not at 1,500 or 5,000). No error is raised; CheckIndex reports the index clean.

Who is affected

#

Applications on 10.5.0-10.5.2 and main that build one field from several field classes (StringField + SortedDocValuesField, NumericDocValuesField + LongPoint) and sometimes leave one part out. Lucene used to reject that mistake; now it can accept it if the field's last validated document in the in-memory segment started with the same frozen type. Sorts and queries can then miss it.

Mechanism, terms and numbers748 words

Lucene requires every document that has a field to give that field the same data structures (LUCENE-9334, 9.0). A documented, ordinary way to build a field is from several Field instances under one name, for example a StringField plus a SortedDocValuesField, as StringField's javadoc suggests. Since 10.5.0, a later document that carries only one part is accepted when that part's type was the first value of the field in the most recently validated document of that field in the same in-memory segment; 9.1.0-10.4.0 reject it. The frozen-FieldType cache added by #15886 caches the first value's type after the document was validated and then skips validation for later documents whose first value has that type. Whether Lucene enforces its rule now depends on value order, frozen vs unfrozen types and flushes. The same fast path keeps leftover per-document schema state, so after a rejected addBatch the next valid multi-type document is rejected once. The index stays valid; queries and sorts that use the missing structure can silently miss the document.

Terms

#
  • Field schema / FieldInfo: the data structures a field has in a segment, fixed by the first document that contains it (MIGRATE.md, "Require consistency between data-structures on a per-field basis").
  • Multi-type field: one field name filled by several Field instances of different types in a document, for example StringField (postings) + SortedDocValuesField (doc values). The field's schema is the union of the types.
  • Frozen type: a FieldType after freeze(). Stock classes share static frozen types, for example StringField.TYPE_NOT_STORED, TextField.TYPE_*, StoredField.TYPE, the *DocValuesField.TYPE constants and KeywordField's types; an application can also reuse its own frozen FieldType (for example one from KnnFloatVectorField.createFieldType). LongPoint, IntPoint and the default vector-field constructors build a new type per instance.

What the code does (main ea57360912ed, IndexingChain.java)

#
  1. For each document, processDocument builds a per-document schema for every field from all its values and initAndValidateFields compares it with the FieldInfo (:611-640, :683-697, assertSameSchema :2290-2304). The FieldSchema javadoc (:2154-2161): "If there is inconsistency, we raise an error."
  2. Since 10.5.0 (#15886), PerField.reset runs for the field's first value and records its type. If it is the cached validatedFrozenFieldType, it only updates the doc id (resetJustDocId, :1821-1831, :2272-2274), the field is not validated (:622-624) and the value is not added to the schema (:633-635).
  3. A later value forces validation only if its type differs from the cached one (multiValueForcesDeoptimize, :625-630, :1833-1835), and it is merged into whatever schema state the previous operation left.
  4. After validation, trySetValidatedFrozenFieldType caches the first value's type if it is frozen (:695, :1837-1843), although the FieldInfo was checked against the union of all values.

Walk-through

#
  • doc 0 = [StringField, SortedDocValuesField]: no cache yet, so both values enter the schema; FieldInfo = postings DOCS + doc values SORTED; StringField.TYPE_NOT_STORED is cached.
  • doc 1 = [StringField]: first value has the cached type, so no schema update and no validation. Indexed with postings and no doc value.
  • doc 1 = [StringField, StoredField]: the StoredField deoptimises, but the schema still holds doc 0's DOCS + SORTED, and a stored value adds nothing to it, so the check passes.
  • With doc 0 = [SortedDocValuesField, StringField] the cached type is SortedDocValuesField.TYPE: a StringField-only document is rejected, a SortedDocValuesField-only one is accepted.

The batch face

#

processBatch resets the field's schema and fills it from the batch columns (:756-783) but never clears the cache; a rejected batch throws before the cache is updated (:693, :695). After addDocument([StringField("id")]), an addBatch with a NumericDocValuesField.TYPE column for id is correctly rejected, which leaves the batch's state (index options NONE, doc values NUMERIC) in the schema. The next document [StringField, StoredField] takes the fast path for its StringField, deoptimises on the StoredField, and is compared using the batch's leftovers: index options: expected 'DOCS', but it has 'NONE'. One false rejection per rejected batch; the next document is validated from scratch.

Exposure and likelihood511 words
  • Who is hit. Default IndexWriterConfig and codec, assertions on or off. The cached first value must be a shared frozen type (for example StringField, TextField, StoredField, the *DocValuesField constants, KeywordField, or a frozen FieldType the application reuses), so "point first" does not trigger it. Examples: StringField + SortedDocValuesField (StringField's javadoc: "If you also need to sort on this field, separately add a SortedDocValuesField"), NumericDocValuesField + LongPoint (the numeric sort optimisation), SortedNumericDocValuesField + LongPoint (the IndexOrDocValuesQuery pattern), StoredField + doc values.
  • What it takes. A later document in the same in-memory segment that omits one of the field's structures. That document is the application's own mistake; Lucene documents that it rejects it, and every tested release from 9.1.0 to 10.4.0 does.
  • Sort consequence (executed). One segment of 20,000 documents, each with StringField("k", "x"): 19,999 with NumericDocValuesField + LongPoint on ts (doc-values value first; document 1 holds 999,999) and, as document 15,000, one with only NumericDocValuesField("ts", 1000000), the highest value. It is accepted; a default top-1 descending sort of the term query k:x (search(query, 1, sort)) returns 999,999, while the same search without skipping returns 1,000,000. Default codec, plain main(), main -ea/-da and 10.5.2. MIGRATE.md: the sort optimisation "relies on the assumption that the same data is stored in these points and doc values."
  • Conditions of the sort consequence. Whether the document is missed depends on where it falls: at positions 10,000 to 19,999 (five tried) the default search returns 999,999, at 1,500 and 5,000 it finds it, and MatchAllDocsQuery with the same sort found it at every position tried. The verifier's JUnit shows the miss with seed 5EEDF00D; with 15 other seeds its default search did not skip at all and returned 1,000,000.
  • Query consequence (executed). 5,000 documents with SortedNumericDocValuesField + LongPoint on n, then a doc-values-only document with value 7: IndexOrDocValuesQuery(n in [7, 1500]) alone does not match it (points path), but id:dv-only AND the same query does (doc-values path); the same with 6 test seeds and codecs, while 10.4.0 rejects the document. IndexOrDocValuesQuery requires its two queries to match the same documents, so this is the bypass letting the application's violation through, not a defect of that query.
  • Not corruption. CheckIndex is clean before and after forceMerge(1); each structure holds exactly the documents that carried it (a probe of 350 documents: id postings 350, sorted doc values 300). On this bug's path an accepted document can lack a checked structure, but a value with a conflicting checked schema dimension (index options, norms, term vectors, doc values, points, vectors) is still rejected; stored status and attributes are not part of the check, and the sibling LFV-127 is a separate path.
  • The batch face. With the experimental IndexWriter#addBatch, a schema-rejected batch makes the next valid multi-type document of that field fail once (measured: 1 of 50 per rejected batch, in each of 3 rounds), then it heals.
  • Scale. Two documents are enough.
  • Status. Regression in 10.5.0; still on main and on the unreleased 10.6 branches.

Why it is a bug, not intended

#
  • MIGRATE.md (LUCENE-9334): every later document with the field "must also have" the same structures; the FieldSchema javadoc: "If there is inconsistency, we raise an error."
  • 10.4.0 rejects the document; so does main with the other value order or after a flush, and upstream's TestPerFieldConsistency fails if only its loop order is reversed.
  • #15886 was an optimisation: "this work is redundant".
The full argument404 words

The contract, in its own words (at ea57360912ed):

  • MIGRATE.md:1557-1564: "The per field data-structures are implicitly defined by the first document indexed that contains a certain field. ... if you first index a document where a certain field is indexed with doc values and points, all subsequent documents containing this field must also have this field indexed with only doc values and points." CHANGES (9.0.0): "LUCENE-9334: Require consistency between data-structures on a per-field basis."
  • IndexingChain.FieldSchema javadoc (:2154-2161): "If there is inconsistency, we raise an error. This ensures that a field has the same data structures across all documents."
  • TestPerFieldConsistency#testDocWithMissingSchemaOptionsThrowsError: "the same segment: indexing a doc with a missing field throws error", for each of four structures.

Why upstream's test misses it. It drops the fields first to last. Its first rejected document drops field 0, the frozen postings type, so that document's first value has another type, which clears the cache, and the later documents are fully checked. Reversed, the first rejected document still starts with the cached type and is accepted: the reversed copy fails on main, 10.5.0, 10.5.2 and #15886's own commit, and passes on 10.4.0, 9.12.3, #15886's parent and with the fix.

Intent of #15886 (commit message): "For the common case where a field consistently uses the same frozen FieldType instance, this work is redundant — a frozen type is immutable, so its schema contribution is identical every time." "If a different type is encountered, the cache is invalidated and the full validation path runs." "A deoptimize path handles multi-valued fields where a later value uses a different type than earlier values within the same document." CHANGES lists it under 10.5.0 Optimizations. The PR had one approval and no discussion of fields made of complementary types; its tests and those of #16171 cover multi-valued fields whose types share one schema or conflict inside one document. The author's first PR comment names the motivation: light-indexing workloads where schema validation dominates processDocument; no difference in the luceneutil benchmarks, and a 10% documents-per-second gain in doc-values-oriented macro runs of Elasticsearch, together with another change.

Old behaviour. 9.1.0, 9.12.3, 10.0.0, 10.3.2, 10.4.0 and #15886's parent reject every subset document; #15886 and every later release accept them.

Context. In LUCENE-10125 (2021) a committer wrote that "the schema definition of a field to be splitted across multiple Field instances makes it challenging to improve" the LUCENE-9334 check: the case the cache gets wrong.

The devil's-advocate check253 words

The cache is a deliberate hot-path optimisation keyed by object identity (the PerField comment says it lets IndexingChain "skip schema validation if fields keep using the same frozen field type"); the subset document breaks the documented rule anyway (garbage in); the LUCENE-9334 issue called the check "best-effort"; addBatch is @lucene.experimental.

Why it fails: Lucene documents that it rejects such input, upstream tests assert it, and 9.1.0-10.4.0 did so deterministically. The "best-effort" list in the LUCENE-9334 issue (#10374) names this very case: "it is illegal for a document to only enable points and another document to only enable doc values". "Best-effort" does not cover an outcome that flips with value order, frozen vs unfrozen types and flush timing. #15886 presented the change as removing redundant work, not as relaxing the rule. The comment's premise (the field keeps using one frozen type) is false for a field built from several types. And an experimental API does not license a rejected call making a later valid addDocument fail.

What a maintainer could still raise (the cross-model fact check rated the intended case moderate for the subset document and weak for the other two faces): detection may have been meant as a defence rather than a guarantee, and the triggering document is the application's own mistake; a document that omits the field entirely is always legal, while this one has the field with only part of its structures; and the two faces have separate causes and fix parts, so they could be filed as two issues.

Suggested fix

#

Recommended Cache a type only if it was the field's only type in the document; rebuild before deoptimising

Don't cache a frozen type when the field used several types in the document (a candidateMixed flag), and rebuild the schema from the cached type before deoptimising: +19/-6 lines in IndexingChain. Valid multi-type documents already run the full validation on main, so they cost almost nothing more. The repro, the regression tests and all 8,870 :lucene:core tests pass.

} else {  // a later value of a field already seen in this document
  if (fieldType != pf.candidateFieldType) {
    pf.candidateMixed = true;  // several types: the first one alone does not describe the field
  }
  if (pf.multiValueForcesDeoptimize(fieldType)) {
    pf.schema.reset(docID);   // rebuild from the earlier values, all of the cached type
    updateDocFieldSchema(fieldName, pf.schema, pf.validatedFrozenFieldType);
    pf.validatedFrozenFieldType = null;
    fields[fieldsNeedInitOrValidate++] = pf;
  }
}
// PerField.reset: candidateMixed = false;
// trySetValidatedFrozenFieldType: cache only if candidateMixed == false

Trade-offs

  • Almost no cost for valid documents of a field that always carries the same several types: on main every such document already deoptimises and is fully validated, because its second value's type differs from the cached one (IndexingChain.java:625-630, :1833-1835). On main its first value still takes the fast path; with the fix each such document does one schema.reset and one more updateDocFieldSchema call (a few assignments and comparisons). Not benchmarked.
  • The documents that lose the fast path are single-type documents right after a multi-type document of the same field. When the other type adds a structure, these are the subset documents the bug lets through. When it adds none (StringField + StoredField, or two types with the same schema), the first valid single-type document after a multi-type one is validated instead of skipped, as on 10.4.0; the next one is cached again. Not benchmarked.
  • The rebuild does not depend on every other path (such as processBatch) clearing the cache when it leaves a foreign schema state behind. It uses FieldSchema.reset, which does not clear the skip-index type; that is the separate bug LFV-116, with its own fix.

Remove the cache (revert #15886 and #16171) (validated by the checks)

Never cache a frozen type; every document is fully validated, as in 10.4.0.

Trade-offs

Fixes both faces by construction but gives up the validation skip #15886 added for documents that repeat one frozen type. Its author reported no difference in the luceneutil benchmarks and about 10% more documents per second in doc-values-oriented macro runs of a downstream engine, measured together with another change; nothing was benchmarked here.

Cache the field's whole validated schema instead of one type

#

For example, remember the set of types of the last validated document and take the fast path only for the same set.

Trade-offs

How it was found

#

An AI tool writing an Alloy 6.2 model of IndexingChain's per-field schema checks and their frozen-type cache noticed the problem while reading the code; Alloy then produced 3-document counterexamples against a stateless reference of the per-document rule. A JUnit test on the stock jar and a bounded-exhaustive harness on the real code confirmed it.

The method in full202 words

Method: Alloy 6.2 model plus bounded-exhaustive differential testing (semi-formal: the first signal came from code reading while modelling).

  • The hunting unit modelled the per-segment FieldSchema / PerField state machine of IndexingChain, including the frozen-type cache, addBatch and flushes, with a file:line mapping to the Java code.
  • While writing the cache part, the AI tool saw that the cached type is the first value's type while validation runs on the union. The check RowOnlyStockCacheSound against a stateless reference of the per-document contract was satisfiable with 3-document counterexamples; with the fix, CacheFixLocalCacheSound had no counterexample in a small bounded universe without addBatch (row-only traces; the larger fixed-model checks timed out).
  • A differential harness on the real jar ran every pair of a first document (928 kinds) and a second document that has only field f (133 kinds), with and without a flush in between (246,848 sequences: 352 accepted although invalid), and every document / addBatch / single-field document triple (928 x 133 = 123,424: 292 valid documents rejected); this fix removes both classes, and neither of the two sibling fixes does.
  • The counterexample was minimised to a public-API JUnit test on the stock main jar (4 of 6 fail, -ea and -da).

LFV-118, snapshot of 2026-10-27

Registry title
The frozen-FieldType validation cache (#15886) keys a field on its first value's type, so for a field built from several field types a later document skips the per-field schema check (or is checked against stale state after a rejected addBatch), depending on value order, flushes and earlier operations
Area
index / IndexingChain per-field schema validation (frozen-FieldType cache)
Priority
Medium, rank 12: Released 10.5 regression in the default indexing chain: the frozen-FieldType cache stops rejecting a document that omits part of a multi-type field such as StringField plus SortedDocValuesField, so sorts and IndexOrDocValuesQuery later miss it silently, but it needs the application's own inconsistent document and leaves the index valid, and the cheap fix should land before 10.6 ships the same code.
Impact class
wrong error
Impact note
Applications on 10.5.0 and later (default IndexWriterConfig and codec, -ea or -da, ordinary scale) that give one field name several stock field types in a document with a shared frozen type first (StringField then SortedDocValuesField, the pairing StringField's javadoc recommends; NumericDocValuesField then LongPoint; StoredField plus doc values; KeywordField): a later document in the same in-memory segment that omits one of the field's structures is accepted, where 9.0-10.4 reject it and main still rejects it with the other value order, an unfrozen type or a flush in between, and queries or sort optimisations that use the omitted structure can then miss that document with no error (executed: a wrong top-1 of a default descending numeric sort, and an IndexOrDocValuesQuery that misses a document its own conjunction matches); separately, after an experimental addBatch on such a field is rejected, the next valid multi-type document for that field is rejected once; the triggering subset document is itself the application's mistake, and the index stays valid (CheckIndex clean).
Summary
You index documents whose field id is a StringField plus a SortedDocValuesField, adding the StringField first, and then a document that has only the StringField. You expect IllegalArgumentException, as Lucene's per-field consistency rule (LUCENE-9334, MIGRATE.md) requires, as 9.0-10.4 do, and as main still does when the doc-values value comes first, the type is an unfrozen copy, or a flush comes in between. Instead the document is accepted, because the frozen-FieldType cache added in 10.5.0 (#15886) caches the first value's type after the union of all the document's values was validated and then skips the check for every later document whose first value has that type; on the same fast path the schema state is not rebuilt, so after a rejected addBatch a valid StringField + StoredField document fails with 'index options: expected DOCS, but it has NONE'.
