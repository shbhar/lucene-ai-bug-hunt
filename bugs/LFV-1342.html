FuzzyCompletionQuery accepts maxEdits above 2, then suggest() throws NullPointerException

FuzzyCompletionQuery's 9-argument constructor accepts maxEdits = 3 although Lucene supports only 0 to 2 edits, so a suggest() on a key of 3 or more characters then throws a NullPointerException from deep inside the suggester. Its siblings FuzzySuggester and FuzzyQuery reject 3 up front with an IllegalArgumentException.

The finding in 30 seconds

#

The constructor never checks maxEdits. For a long enough key, toAutomaton(3, prefix) returns null, the weight keeps it, and the FST lookup dereferences it at search time.

Background: fuzzy suggestions in the document suggester

#
  1. The document suggester indexes SuggestField values with a completion postings format; SuggestIndexSearcher.suggest(query, n, skipDuplicates) returns the top completions for what the user has typed.
  2. FuzzyCompletionQuery tolerates typos: it turns the typed key into a Levenshtein automaton that accepts every string within maxEdits edits (with 1 edit "lucene" also matches "lucxne"; with 2, "lxcxne") and intersects it with the suggester's FST.
  3. LevenshteinAutomata supports 0, 1 or 2 edits (MAXIMUM_SUPPORTED_DISTANCE = 2). Keys shorter than minFuzzyLength (default 3) are matched exactly, without a Levenshtein automaton.

The finding, step by step

#
  1. Index one suggestion, "lucene", and build new FuzzyCompletionQuery(analyzer, new Term("suggest", "lucene"), null, 3, true, 1, 3, false, Operations.DEFAULT_DETERMINIZE_WORK_LIMIT): maxEdits 3, every other argument at its default. With maxEdits 2 the same search returns "lucene".
  2. You expect IllegalArgumentException: maxEdits must be between 0 and 2 from the constructor, as FuzzySuggester and FuzzyQuery throw for 3, or a normal search.
  3. Instead the constructor keeps 3, and SuggestIndexSearcher.suggest(query, 1, false) throws a NullPointerException (... because "a" is null) from FSTUtil.intersectPrefixPaths, with assertions on and off.
  4. Why: LevenshteinAutomata has automata for 0, 1 and 2 edits only, and toAutomaton(3, "l") quietly returns null. The query's weight keeps that null until the suggester's FST lookup dereferences it. maxEdits = -1 throws ArrayIndexOutOfBoundsException instead.
  5. Short keys hide it: "lu" (2 characters, below minFuzzyLength 3) is matched exactly, without a Levenshtein automaton, and works with maxEdits 3.

Who is affected

#

Applications that use the opt-in document suggester and pass maxEdits above 2 (say 3, for more fuzziness) or below 0 to the 9-argument constructor. A suggest on a key of 3 or more characters then fails with an exception that names no parameter; short test keys pass. No wrong results; the 2- and 3-argument constructors are safe. Rare.

Mechanism, terms and numbers387 words

FuzzyCompletionQuery (document suggester, @lucene.experimental) stores maxEdits from its 9-argument constructor with no check (FuzzyCompletionQuery.java:138). LevenshteinAutomata can build automata only for 0, 1 or 2 edits (MAXIMUM_SUPPORTED_DISTANCE = 2), and its toAutomaton(n, prefix) returns null for n >= 3 (LevenshteinAutomata.java:156), which its javadoc does not mention. So with maxEdits = 3, createWeight builds a weight around a null automaton, and SuggestIndexSearcher.suggest on a key of 3 or more characters throws a NullPointerException from FSTUtil.intersectPrefixPaths; maxEdits = -1 throws ArrayIndexOutOfBoundsException: Index -1 out of bounds for length 3. Keys shorter than minFuzzyLength (default 3) never build the Levenshtein automaton and work.

FuzzySuggester, whose automaton-building loop this class copied, and FuzzyQuery reject the same values with an IllegalArgumentException at construction (so does the package-private FuzzyAutomatonBuilder behind FuzzyQuery). Loud, no wrong results, opt-in API; in every release since 5.3.0. Fix: the same 4-line check in the constructor.

Exposure and likelihood181 words
  • Who is hit. Code that queries SuggestField data through SuggestIndexSearcher with a FuzzyCompletionQuery built by the 9-argument constructor, with maxEdits 3 or more or below 0.
  • Opt-in twice. The document suggester itself, and a non-default maxEdits in the 9-argument constructor. Assertions on or off make no difference.
  • What goes wrong. Such a suggest call throws an exception that names no parameter, far from the argument that caused it: a NullPointerException from FSTUtil for maxEdits 3 or more (once a segment holds suggestions for the field, as in the repro; with unicodeAware already in createWeight, from UTF32ToUTF8.convert), or an ArrayIndexOutOfBoundsException from LevenshteinAutomata in createWeight for a negative value. No wrong results; the failure is on the read-only query path, so nothing is written to the index (read from the code, not separately tested).
  • Why tests can miss it. Keys shorter than minFuzzyLength (default 3) never reach toAutomaton, so a test with "lu" passes while real input such as "lucene" fails.
  • How likely. Rare. Elasticsearch and OpenSearch completion suggesters validate fuzziness 0..2 themselves, so their users do not reach it.

Why it looks unintended

#
  • The 0..2 limit is real: LevenshteinAutomata builds automata only up to 2 edits, and toAutomaton's javadoc promises a DFA, never null.
  • FuzzySuggester, whose loop this class copied, and FuzzyQuery reject 3 with an IllegalArgumentException; TestFuzzyQuery asserts it.
  • The class was added without the check in 2015 (LUCENE-6459); no comment records a decision, and no test or later commit adds one.
The full argument205 words
  • The class's own contract states no range: @param maxEdits maximum number of acceptable edits (FuzzyCompletionQuery.java:119), no @throws. So 3 breaks no documented precondition, and nothing in the docs says it turns into a null automaton (LevenshteinAutomata.java:138-149).
  • Every public sibling validates up front. FuzzySuggester documents "maxEdits must be >= 0 and <= MAXIMUM_SUPPORTED_DISTANCE" (FuzzySuggester.java:143-144) and throws IllegalArgumentException("maxEdits must be between 0 and 2") (:176-179); FuzzyQuery the same (FuzzyQuery.java:76-77, :95-98), and so does the package-private FuzzyAutomatonBuilder behind FuzzyQuery and FuzzyTermsEnum (FuzzyAutomatonBuilder.java:38-44, with its own message); DirectSpellChecker.setMaxEdits throws UnsupportedOperationException (:115); sandbox FuzzyLikeThisQuery rejects (:182-189); SimpleQueryParser clamps foo~3 to 2 (:412). TestFuzzyQuery asserts the IllegalArgumentException for MAXIMUM_SUPPORTED_DISTANCE + 1 (TestFuzzyQuery.java:541-552). FuzzyCompletionQuery is the only in-tree caller of toAutomaton that skips the check.
  • History records no decision to leave it out. be4d58c7740 (LUCENE-6459, #7518, 2015) created the class with toLevenshteinAutomata copied from FuzzySuggester, down to its TODO comments, but not FuzzySuggester's check (there since 83a1417bd56, LUCENE-3846, 2012). None of the 23 comments on #7518 discusses a range; none of the 12 later commits on the file adds one; TestFuzzyCompletionQuery uses only the 2-argument constructor.
The devil's-advocate check162 words

The strongest case for "intended": the class is @lucene.experimental (FuzzyCompletionQuery.java:53); the 2-edit cap is a Lucene-wide fact documented on FuzzyQuery and FuzzySuggester; the failure is loud and returns no wrong results; and anyone who tries 3 with a normal-length key sees the exception on the first search. So validation would be hardening rather than a bug fix. The cross-model reviewer rated this argument moderate.

Why it fails: the value is not rejected where it is passed; the exception arrives later, from code unrelated to the argument, and names no parameter; whether it arrives at all depends on the length of the user's input; and every other public API that hands an edit distance to LevenshteinAutomata (FuzzySuggester, FuzzyQuery, DirectSpellChecker, SimpleQueryParser by clamping) rejects or clamps it. The check FuzzySuggester and FuzzyQuery already use removes the question. Its one cost: it also rejects invalid values that happen to work today on short keys (see the fix trade-offs).

Suggested fix

#

Recommended A. Reject out-of-range values in the constructor (recommended; validated)

Add FuzzySuggester's check to the 9-argument constructor: throw IllegalArgumentException("maxEdits must be between 0 and 2") for maxEdits < 0 or > MAXIMUM_SUPPORTED_DISTANCE, and state the range in the @param. Validated through gradle: the repro passes, the whole :lucene:suggest suite passes and check -x test is clean.

-   * @param maxEdits maximum number of acceptable edits
+   * @param maxEdits maximum number of acceptable edits, must be &gt;= 0 and &lt;= {@link
+   *     LevenshteinAutomata#MAXIMUM_SUPPORTED_DISTANCE}
@@
     super(analyzer, term, filter);
+    if (maxEdits < 0 || maxEdits > LevenshteinAutomata.MAXIMUM_SUPPORTED_DISTANCE) {
+      throw new IllegalArgumentException(
+          "maxEdits must be between 0 and " + LevenshteinAutomata.MAXIMUM_SUPPORTED_DISTANCE);
+    }
     this.maxEdits = maxEdits;

Trade-offs

  • Fails fast, at the call that passed the value, with a message that names it; matches the project's existing practice.
  • No change for valid values. Invalid values that fail later today now fail at construction. This deliberately changes behaviour for invalid values that happen to work today on short keys ("lu" with 3 or -1, see the probe table): those callers get an exception where they now get results.

What the checks validated

  • Without the fix the repro fails with assertions on and off (gradle, seed DEADBEEF).
  • With the fix the repro passes with assertions off, and the whole :lucene:suggest test suite passes with assertions on: 32 classes, 237 tests, 0 failures, 7 skipped (the repro, TestFuzzyCompletionQuery, TestContextQuery, TestSuggestField, TestFuzzySuggester among them).
  • :lucene:suggest:check -x test (google-java-format, ecj lint, forbidden APIs) passes with the fix and the test in place. One seed, no nightly tests.

B. Clamp to 0..2 (not validated)

#

maxEdits = Math.min(maxEdits, LevenshteinAutomata.MAXIMUM_SUPPORTED_DISTANCE), as SimpleQueryParser does for foo~3 (SimpleQueryParser.java:412).

Trade-offs

No exception at all, but the caller silently gets less fuzziness than asked for, and a negative value still needs its own rule; the siblings FuzzySuggester and FuzzyQuery choose an explicit error.

C. Make LevenshteinAutomata.toAutomaton throw instead of returning null (not validated)

#

Replace return null at LevenshteinAutomata.java:156 with an IllegalArgumentException, and check n < 0.

Trade-offs

Covers any future caller, but changes a public (@lucene.experimental) core class whose other callers already check, and the error would still come at search time rather than at construction. Better as a follow-up than as the fix.

Downstream note

#

Not security-sensitive; downstream, a service that passes a user-supplied fuzziness straight into this constructor would answer those requests with a server error instead of rejecting the value.

How it was found

#

A semi-formal proof-obligation audit of FuzzyCompletionQuery's contract: every edit distance it passes to LevenshteinAutomata.toAutomaton must lie in 0..2, the precondition its siblings enforce. The 9-argument constructor never checks it, and a public-API JUnit test witnessed the failure on stock main.

The method in full68 words

The check compared each argument FuzzyCompletionQuery hands to LevenshteinAutomata with the precondition that FuzzySuggester, FuzzyQuery and the package-private FuzzyAutomatonBuilder check before the same call. maxEdits reaches toAutomaton unchecked, and toAutomaton returns null above 2. An executable JUnit test on the stock main build confirmed the failure, and an independent reproducer, a cross-model review, an intended-behaviour devil's advocate and an adjudication then checked it (see the checks below).
