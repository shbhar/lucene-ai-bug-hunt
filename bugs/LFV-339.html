IndexMergeTool rejects '--' as an unrecognized option because it compares the argument with ==

IndexMergeTool -- -merged src1 src2 stops with "unrecognized option: '--'" and exit code 2 instead of merging into -merged: the parser's end-of-options check uses ==, which misses a command-line --, and it would also forget to skip the --. A small command-line defect since 9.0.0; ./-merged works around it.

The finding in 30 seconds

#

Background: the tool, --, and == on Strings

#
  1. IndexMergeTool (module lucene-misc) merges indexes from the command line: IndexMergeTool [OPTION...] <mergedIndex> <index1> <index2> ..., with the options -merge-policy, -max-segments and -verbose.
  2. By a common command-line convention, -- ends the options: everything after it is a name, even a name that starts with -.
  3. In Java, a == b on two Strings asks whether they are the same object; a.equals(b) compares the text. A string literal in code is one shared (interned) object, while each command-line argument is a new String, so arg == "--" is false even when arg is --.

The finding, step by step

#
  1. You want to merge two indexes, src1 and src2, into a new directory named -merged. IndexMergeTool -merged src1 src2 stops with "unrecognized option: '-merged'": every leading argument that starts with - is read as an option.
  2. So you write IndexMergeTool -- -merged src1 src2, the usual way to say "options end here". The parser even has a branch for --; you expect "Merging...", "Done." and an index in -merged.
  3. Instead you get "unrecognized option: '--'", the usage text and exit code 2, and nothing is written. The branch tests args[index] == "--": == asks whether two Strings are the same object, and a command-line argument arrives as a new String, not the same object as the literal "--" in the code.
  4. The branch is also wrong when it does match, which only Java code passing the interned literal "--" can make happen: it does not skip the --, so -- becomes the target directory and -merged is read as the first source index.

Who is affected

#

Only people who run the misc IndexMergeTool command line (9.0.0 and later) and put -- before the paths: by habit, to name a target that starts with -, or from a wrapper script that adds --. They get a clean error with nothing written; ./-name works around it. No indexing or search API is affected.

Mechanism, terms and numbers518 words

IndexMergeTool, the misc module's command-line program that merges indexes, has an option parser whose branch for the end-of-options marker -- compares the argument with == instead of equals. The launcher passes each command-line argument as a new String, not the interned literal, so for a command-line -- the branch does not fire: -- falls through to the option switch and the tool stops with "unrecognized option: '--'" and exit code 2 before opening any directory. The branch is also missing index++, so if Java code passes the interned literal "--" to the public main(), -- itself becomes the merged-index path. Both defects date from LUCENE-9206 (commit 93b83f635df, 2020-02-05), first released in 9.0.0, and are still on main. Only this tool is affected (its command line and its main()), no indexing or search API; nothing is lost, and ./-name works around it. The fix is two lines: args[index].equals("--") and index++ before the break.

The bug

#

All lines are in lucene/misc/src/java/org/apache/lucene/misc/IndexMergeTool.java at 645d4fe14a20.

  1. Options.parse (:54-94) loops over the arguments and stops at the first one that does not start with - (:58-60); from there on the arguments are the target and the sources (:84-92).
  2. Next comes if (args[index] == "--") { break; } (:61-63), with no comment. == compares object identity, and the launcher gives main() a new String for each command-line argument (on OpenJDK 25 a JVM given -- prints args[0] == "--" false and args[0].equals("--") true), so for a command-line -- this is false.
  3. -- reaches switch (args[index]) (:64), which knows -merge-policy, -max-segments and -verbose; its default throws IllegalArgumentException("unrecognized option: '--'" + USAGE) (:77-79). main() prints the message and calls System.exit(2) (:99-104), before any directory is opened (:107-113).
  4. When the branch does fire (Java code passing the interned literal "--" to main() or to the package-private Options.parse), the break skips the index++ at :81. So mergedIndexPath = args[index] is "--" (:90), and the intended target becomes the first source (:91-92). The target is opened with OpenMode.CREATE (:51).
  5. Lucene's build had no Error Prone when this code landed; it came seven months later with LUCENE-9497 (17a3ba723ae, 2020-09-07), with its ReferenceEquality check off, and that check is still off ("ReferenceEquality:OFF", // noisy, build-tools/build-infra/src/main/java/org/apache/lucene/gradle/plugins/java/ErrorPronePlugin.java:738), so the build does not flag it.

Exposure and likelihood182 words
  • Who is hit. Users of the command-line tool who type -- before the paths, and scripts that add it defensively. No query, document or index file reaches this parser.
  • Default vs opt-in. It is the tool's only parser; no setting is involved, and assertions make no difference.
  • Effect. A clean, immediate refusal with exit code 2 before any directory is opened; a probe found the working tree byte-for-byte unchanged. A target that starts with - cannot be passed with --; ./-name works.
  • Wrong output only from Java. The case where -- becomes the target needs Java code that passes the interned literal "--"; the merge then lands in ./-- (an index already there would be replaced, because the target is opened with OpenMode.CREATE), and the named target is only read: an existing index stays byte-identical, and a target that does not exist is left behind as an empty directory holding write.lock.
  • Reach. In the Lucene tree only the tool, its test, CHANGES.txt and MIGRATE.md mention it; a code search of Solr, Elasticsearch and OpenSearch (2026-10-26) found no use.

Why it looks unintended

#
  • The -- branch can only be meant to end the options, yet with == it does not fire for a command-line argument.
  • When it does fire, it leaves -- as the target path.
  • Nothing chose to reject --: the issue that added the parser never mentions it, and no test or comment covers it.
The full argument162 words
  • The branch. if (args[index] == "--") { break; } (IndexMergeTool.java:61-63) matches only -- and leaves the option loop; every verifier and the adjudication read it as the end-of-options rule.
  • History. LUCENE-9206 (#10246) added the whole parser in 93b83f635df; its discussion covers defaults, merge policy, -max-segments and forbidden-apis and never mentions --, and its patch already had the ==.
  • Tests. The upstream TestIndexMergeTool (7 tests) has no -- case. Its tests pass string literals, which are interned, so a test with the literal "--" would have hit the second defect, not the first.
  • The rest of the parser compares text. The switch on args[index] (:64) uses equals, as do other Lucene command-line parsers, for example "-level".equals(arg) in CheckIndex (lucene/core/src/java/org/apache/lucene/index/CheckIndex.java:4787).
  • Related precedent. #9095 (LUCENE-8047, open since 2017) lists String == comparisons in analysis code, which committers defended because only the same static final constants flow in. That reasoning does not hold for command-line arguments.
The devil's-advocate check247 words

The strongest case (the review and the works-as-designed review, two reading-only runs of the same reviewer from another model family, OpenAI GPT-5.6, with different lenses; the intended-behaviour checker): -- is documented nowhere in the repository (USAGE :36-45 lists only -merge-policy, -max-segments and -verbose; the class javadoc :29-32 names no option; lucene/CHANGES.txt:4866-4868 and lucene/MIGRATE.md:1280-1284 name only -max-segments; no upstream test uses --); the tool fails closed with a clear message; ./-name works; no other Lucene command-line tool supports --; and Lucene turned ReferenceEquality off on purpose.

Why it fails: this shows that -- support is undocumented, not that rejecting it was chosen. The author wrote a branch whose only purpose is to recognise --. Turning ReferenceEquality off was a project-wide call about a noisy check (LUCENE-9497, lucene-solr#1816), not a decision about this line. These points limit impact, not validity. The refute-lens review gave a procedural "not real" (it could not run code) while agreeing on both defects and rating the works-as-designed case weak; the works-as-designed review also rated it weak; the devil's advocate found the bug real with high confidence that it is not intended. A later cross-model fact check (2026-11-01) rated the works-as-designed case moderate, mainly because -- is documented nowhere, while agreeing that a branch written only for --, plus the missing index++, points to an unfinished implementation rather than a chosen rejection. Maintainers may well prefer to delete the branch, a legitimate answer that keeps today's behaviour.

Suggested fix

#

Recommended Compare with equals and skip the --

Compare with equals and skip the --: if (args[index].equals("--")) { index++; break; }. After -- every argument is a path, as the branch intends. Validated with the minimal test, TestIndexMergeTool and the whole misc test suite.

         if (!args[index].startsWith("-")) {
           break;
         }
-        if (args[index] == "--") {
+        if (args[index].equals("--")) {
+          index++;
           break;
         }
