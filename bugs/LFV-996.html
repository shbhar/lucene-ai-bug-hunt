SpellChecker.suggestSimilar computes 10 * numSug in int, so numSug = Integer.MAX_VALUE throws "numHits must be > 0" instead of returning the suggestions

SpellChecker.suggestSimilar(word, numSug) asks its search for 10 * numSug candidates, computed in int, so numSug = Integer.MAX_VALUE ("all suggestions") wraps to -10 and throws IllegalArgumentException: numHits must be > 0. Every count from 214,748,365 that wraps to zero or below fails; some larger ones silently return fewer suggestions.

The finding in 30 seconds

#

The classic n-gram SpellChecker fetches ten times as many candidate words as the suggestions you ask for and computes that budget in a Java int. A huge count wraps the budget negative, and the search underneath rejects it.

Background: the n-gram SpellChecker

#
  1. SpellChecker keeps a separate spell index with one document per dictionary word, split into n-grams.
  2. suggestSimilar(word, numSug) searches that index for words sharing n-grams with word, takes the top 10 * numSug hits (n-gram overlap is only a rough guide), ranks them by edit distance and returns the best numSug.
  3. The search it calls, IndexSearcher.search(query, n), caps n at the index size, so there n = Integer.MAX_VALUE simply means "all hits"; a Lucene test requires that it not throw.

The finding, step by step

#
  1. You build a spell index from a one-word dictionary, lucene, and call suggestSimilar("lucenx", Integer.MAX_VALUE) to get every suggestion.
  2. You expect [lucene]. Counts of 5, 1,000 and 214,748,364 return exactly that on the same index (run with a 3 GiB heap: at 214,748,364 the queue alone is about 0.8 GiB), and the javadoc sets no upper bound on numSug.
  3. You get IllegalArgumentException: numHits must be > 0; please use TotalHitCountCollectorManager if you just need the total hit count, about a parameter you never passed. 214,748,365 fails the same way.
  4. Why: the spell checker asks the search for 10 * numSug hits, computed in int, and 10 x 2,147,483,647 wraps to -10. The search caps its n at the index size, min(n, maxDoc), which keeps -10, and rejects it. Every count whose product wraps to zero or below fails: 1,073,741,824 values in five blocks.
  5. Where the product wraps to a small positive number, the call silently returns fewer: on a 10-word dictionary numSug = 429,496,730 (budget 4) returns 4 of the 9 suggestions, after reserving a 1.6 GiB queue.

Who is affected

#

Applications that call the classic SpellChecker.suggestSimilar (default settings, any dictionary) with a huge count: most naturally Integer.MAX_VALUE for "all suggestions", or a user-chosen count with no upper bound. Ordinary counts, up to 214,748,364, are unaffected. The failure is loud on the first call; the silent short result needs a count above 429 million.

Mechanism, terms and numbers718 words

SpellChecker.suggestSimilar(word, numSug), Lucene's classic n-gram spell checker, fetches ten times as many candidate words from its spell index as the suggestions requested and computes that budget as int maxHits = 10 * numSug. For numSug = Integer.MAX_VALUE ("all suggestions") the product wraps to -10; IndexSearcher.search(query, n) caps n with min(n, max(1, maxDoc)), which keeps the negative value, and TopScoreDocCollectorManager throws IllegalArgumentException: numHits must be > 0; please use TotalHitCountCollectorManager if you just need the total hit count, naming a parameter the caller never passed. The javadoc sets no upper bound on numSug and nothing validates it, while the search below is tested to accept Integer.MAX_VALUE. Every count whose product wraps to zero or below fails (1,073,741,824 values in five blocks, the first at 214,748,365); where it wraps to a small positive number the call silently returns fewer suggestions (numSug = 429,496,730: 4 of 9). A second line sizes the result queue by numSug, so the fix has two lines: compute the budget in long and saturate it, and size the queue by min(numSug, hits.length). Every release from 1.9 to 10.6.0 and main is affected; it is not a regression (Integer.MAX_VALUE never worked, only the exception changed), no index data or search results are affected, and ordinary counts up to 214,748,364 work.

Exposure and likelihood252 words
  • Who is hit. Code that passes a huge numSug to any suggestSimilar overload. No setting is needed, and the dictionary size does not matter: a one-word dictionary fails.
  • What goes wrong. For 1,073,741,824 counts the call throws an exception that names numHits and recommends TotalHitCountCollectorManager, neither of which the caller used. Where the product wraps to a small positive budget, the call can return fewer suggestions with no error; that needs a count of at least 429,496,730 and a queue of about 1.6 GiB first. Below the threshold results are right, but memory follows the count (381.7 MiB at 10^8).
  • Not a regression. Integer.MAX_VALUE has never worked: NegativeArraySizeException in 1.9 to 2.9.1, "nDocs must be > 0" in 2.9.2 to 3.0.3, "numHits must be > 0" since 3.1.
  • Workaround. Cap the count before calling, for example at the number of words in the spell index; any count up to 214,748,364 works, given a heap large enough for the numSug-sized queue (about 0.8 GiB at 214,748,364).
  • How likely. Rare: usual counts (the javadoc asks for "at least 5"; upstream tests use 1 to 10) never come near the threshold, and the recorded searches found no earlier report.
  • Downstream (read, not executed). By default, Solr's index- and file-based spell checkers pass max(spellcheck.count, 5) to suggestSimilar (with a non-zero alternativeTermCount they pass that count instead for a word that is in the index), and Solr reads spellcheck.count with no upper bound; Lucene.NET's port has the same two lines (SpellChecker.cs:364, :369).

Why it looks unintended

#
  • The javadoc calls numSug "the number of suggested words", with no upper bound and no check; the error names numHits, which the caller never passed.
  • The search below fixed this failure as a bug (LUCENE-2119) by capping n at the index size; the int product wraps before that cap.
  • Asking for more can return fewer: 429,496,730 gives 4 of 9.
The full argument321 words
  • The exception is an overflow artifact, not a check. It fires at 214,748,365, the point where 10 * numSug passes Integer.MAX_VALUE; no comment, test, CHANGES entry or commit chooses that threshold. The pre-allocation note sits on the @lucene.internal PriorityQueue (PriorityQueue.java:34-35, :39), which the suggestSimilar javadoc does not reference. Nothing documents Integer.MAX_VALUE as an "all suggestions" value either: it is a request for more suggestions than exist, which the contract does not forbid.
  • LUCENE-2119 (#3195, reported by Michael McCandless, type:bug, fixed in 2.9.3, 3.0.2 and 3.1): "If you pass Integer.MAX_VALUE as 2nd param to search(Query, int) you hit unexpected NegativeArraySizeException"; "This trips users up fairly often because they assume our PQ doesn't statically pre-allocate (a reasonable assumption...)"; "in IndexSearcher, if that n is ever > maxDoc(), set it to maxDoc()". That cap is IndexSearcher.java:597. This is context for the search's own contract, not proof that SpellChecker promises the same.
  • Precedent in this file. LUCENE-10533 (#11569, Kevin Risden, type:bug, fixed in 9.2), a missing bounds check in SpellChecker.formGrams reached from Solr: "There is an argument that the caller should not be invalid, but a simple bounds check would prevent this in Lucene".
  • The sibling spell checkers are no counter-example. WordBreakSpellChecker returns an empty result below 1 and caps its initial queue capacity at 10 (WordBreakSpellChecker.java:81-83, :91). DirectSpellChecker is no evidence that large counts are supported: it returns its full result for Integer.MAX_VALUE only because its own int product numSug * maxInspections (DirectSpellChecker.java:359, default 5 at :67) happens to wrap to the positive 2,147,483,643; with default settings 500,000,000 throws NullPointerException there and 858,993,460 returns 4 of 10 (executed first-signal probe), which is the sibling LFV-986.
  • History. The factor 10 is a recall heuristic (LUCENE-786, Karl Wettin: "I suppose that number (10) was something the original author came up with when testing"); :361 came from the mechanical LUCENE-1856 "Remove Hits" migration. Nothing discusses bounds.
The devil's-advocate check219 words

The strongest case for "works as designed" (built by an intended-behaviour devil's advocate; reading-only reviewers from another model family, OpenAI GPT-5.6, rated it "moderate" and "weak"): a spell checker asked for hundreds of millions of suggestions is an odd request, and the javadoc's only guidance is small ("at least 5"; DirectSpellChecker adds "typically a low value for numSug will work very well"); PriorityQueue documents its up-front allocation, and SuggestWordQueue(int size, ...) takes "the size of the queue", so sizing it by numSug is designed use; in LUCENE-2119 the reporter called n = Integer.MAX_VALUE "a nonsense value to pass in, since our PQ impl allocates the array up front"; Integer.MAX_VALUE has never worked in any SpellChecker release, and a reviewer argued that "a clear validation exception would still be preferable".

Why it fails: LUCENE-2119 was still fixed as a bug, in the very search SpellChecker calls, and testHugeN keeps that contract; the request is feasible (with the fix every count, Integer.MAX_VALUE included, returns the full result at -Xmx512m); today's behaviour is not a clear validation exception but an overflow artifact about another parameter, plus a silent short result in other blocks. The argument does bear on priority (Low) and on the likely reply: a maintainer may prefer a bound check (option B) over saturation, and either resolves the bug.

Suggested fix

#

Recommended Compute the budget in long and saturate it; size the queue by min(numSug, hits.length)

Compute the budget in long and cap it at Integer.MAX_VALUE (the search then caps it at the index size), and size the result queue by min(numSug, hits.length). Both lines are needed. Counts that do not overflow give the same results; silently short positive-wrap counts now get the full result. The test and the suggest module's 237 tests pass.

// saturate: 10 * numSug overflows int for numSug >= 214748365 (e.g. Integer.MAX_VALUE)
int maxHits = (int) Math.min(10L * numSug, Integer.MAX_VALUE); // was: 10 * numSug

ScoreDoc[] hits = indexSearcher.search(query.build(), maxHits).scoreDocs;
// size the queue by what the search can return, not by numSug
SuggestWordQueue sugQueue =
    new SuggestWordQueue(Math.min(numSug, hits.length), comparator); // was: numSug

Trade-offs

  • No change in results for counts that do not overflow. Up to 214,748,364 the product is exact, and the queue size is numSug whenever numSug <= hits.length. When numSug > hits.length, a queue of hits.length slots holds every inspected hit (at most stop <= hits.length inserts, :369), as the larger queue did; the "queue full" accuracy raise (:396-399) cannot fire in either version, because the queue never reaches numSug entries.
  • Positive-wrap counts change on purpose. Today they can return a silently short result (429,496,730: 4 of 9); with the fix they return the full 9.
  • Allocations are bounded by the spell index, not by the count. With the saturated budget IndexSearcher caps n at maxDoc, the path testHugeN covers, and the queue gets hits.length <= maxDoc slots (a large spell index still means large allocations).
  • For numSug <= 0 the fix computes exactly today's maxHits and queue size, so behaviour there does not change.
  • Both lines are needed: with only the first, Integer.MAX_VALUE fails in PriorityQueue ("maxSize must be >= 0 and < 2147483631") and 214,748,365 runs out of memory at -Xmx512m.
  • The minimal test, as the regression test, covers only Integer.MAX_VALUE; the positive-wrap leg was checked only with the tie-breaker's probe, and counts <= 0 are not tested.

Reject counts that overflow, with a clear message

#

For example if (numSug < 1 || numSug > Integer.MAX_VALUE / 10) throw new IllegalArgumentException(...) at the top of the 6-argument suggestSimilar. Not executed.

Trade-offs

Replaces the misleading exception and the silent short result with a clear error and needs no change at :366, but keeps "all suggestions" an error (unlike the search below, which accepts Integer.MAX_VALUE) and keeps the numSug-sized pre-allocation for large legal counts (381.7 MiB at 10^8).

Clamp numSug to the spell index size first

#

The spell index holds one document per indexed word (SpellChecker.java:534-535; indexDictionary skips words shorter than 3 characters and words already in the spell index, :521-530), so at most maxDoc suggestions exist: clamp numSug to it, then compute the budget in long. Not executed.

Trade-offs

Same effect as A in one place, but it changes the numSug that the "queue full" check (:396) compares against, so it needs the same reasoning about unchanged results.

How it was found

#

A planning probe of numeric limits on public API arguments called suggestSimilar with Integer.MAX_VALUE and 214,748,365 on the stock jars and got "numHits must be > 0". A finder wrote the JUnit; a Z3 bit-vector model and an exact enumeration gave the boundaries and predicted the silent short-result leg, which an independent reproducer then ran.

The method in full183 words

Method: executed differential testing, then SMT modelling (the hunt's non-formal tier: the first signal was an executed probe, not a model).

  • First signal. In a round on numeric limits of public API arguments, a planning probe ran SpellChecker.suggestSimilar on a 10-word dictionary with Integer.MAX_VALUE, 214,748,365 and 10^8 on the stock jars of main a9779ef3c193, 10.5.2, 9.12.3 and the 10.6 release candidate (2026-10-28): the first two threw "numHits must be > 0", the third returned after a 381 MiB allocation.
  • Hunt.   • Checks. An independent reproducer executed the modelled silent leg (4 of 7 suggestions); an intended-behaviour devil's advocate, an adjudication, a credibility audit, a current-main re-check and a tie-breaker confirmed it; the single test shown here is the audited reduction.

History

#

No regression: both halves were in the class as first written (2004), so every release from 1.9 to 10.6.0 fails. Only the exception changed: NegativeArraySizeException up to 2.9.1, "nDocs must be > 0" in 2.9.2 to 3.0.3, "numHits must be > 0" since 3.1.

LFV-996, snapshot of 2026-11-07

Registry title
SpellChecker.suggestSimilar computes its hit budget 10 * numSug in int, so numSug = Integer.MAX_VALUE ('all suggestions'), 214748365 and every other count whose product wraps to <= 0 throw IllegalArgumentException 'numHits must be > 0' instead of returning the suggestions, and counts whose product wraps to a small positive value silently return fewer suggestions
Area
suggest / spell checking (SpellChecker.suggestSimilar hit budget 10 * numSug and SuggestWordQueue size)
Priority
Low, rank 659: The legacy SpellChecker throws a misleading IAE for numSug = Integer.MAX_VALUE and only truncates above about 429M, the same loud MAX_VALUE pre-size class as the SearchGroup.merge and MoreLikeThis rows.
Impact class
wrong error
Impact note
Applications on every release from 1.9 to 10.6.0 and main that call the n-gram SpellChecker.suggestSimilar (default settings suffice) with a huge suggestion count, most naturally Integer.MAX_VALUE as 'all suggestions', get IllegalArgumentException 'numHits must be > 0; please use TotalHitCountCollectorManager if you just need the total hit count' (since 3.1; 'nDocs must be > 0' in 2.9.2-3.0.x; NegativeArraySizeException or a silently empty result in 1.9-2.9.1) for every numSug whose 10 * numSug wraps to <= 0 (1,073,741,824 of the positive ints, the first being 214,748,365), at any dictionary size; in the positive-wrap blocks (the first being 429,496,730) the call silently inspects too few hits (4 instead of 7 suggestions on a 10-word dictionary), but only after pre-allocating a numSug-slot queue of at least 1.6 GiB, and every large legal count costs heap in proportion to numSug (about 381 MiB per call for 10^8); counts up to 214,748,364 give the right answer, and no index data or search results are affected.
Summary
You build an n-gram spell index with SpellChecker and call suggestSimilar(word, Integer.MAX_VALUE) to get all suggestions; you expect the same 9 suggestions that numSug 1000 returns on a 10-word dictionary. Instead SpellChecker multiplies numSug by 10 in int to size its search, the product wraps to -10, and the search throws IllegalArgumentException 'numHits must be > 0; please use TotalHitCountCollectorManager ...', naming a parameter the caller never passed; the same happens for half of all counts from 214,748,365 up, and in the blocks between (for example 429,496,730, whose product wraps to 4) the call silently returns fewer suggestions after allocating a queue of numSug slots. The fix is two lines: compute the budget in long and saturate it at Integer.MAX_VALUE, and size the queue by min(numSug, hits.length).
