Operations.determinize throws when an arc ends at Integer.MAX_VALUE: the sweep's point comparator overflows

Determinizing a tiny hand-built automaton with an arc ending at Integer.MAX_VALUE throws AssertionError (assertions on) or ArrayIndexOutOfBoundsException (off): the sweep files the arc's end at 1 + max, which wraps to Integer.MIN_VALUE, then sorts points by subtraction. Affects every release since 4.0.0-alpha; the built-in query parsers cannot reach it.

The finding in 30 seconds

#

Operations.determinize turns an automaton into a DFA by walking label boundaries in sorted order. For one boundary value that order breaks.

Background: how determinize walks label ranges

#
  1. A Lucene Automaton has states joined by arcs. Each arc carries a label range [min, max], stored as int; Automata.makeCharRange(min, max) builds one such arc.
  2. Operations.determinize builds the DFA one set of NFA states at a time. For each set it collects the points where the set's arcs start (min) and end (max + 1), sorts them, and walks them from left to right.
  3. At each point it first emits the range since the previous point, then closes the arcs that end there and opens the arcs that start there. That is only correct when the points come in increasing order: every arc must be opened before it is closed.

The finding, step by step

#
  1. Build hi = label 0 followed by any label from 11 to Integer.MAX_VALUE (2147483647), and lo = label 0 followed by a label from 0 to 10, with makeChar, makeCharRange and concatenate. Their union accepts every two-label word that starts with 0, such as [0, 5].
  2. Call Operations.determinize(union(hi, lo), DEFAULT_DETERMINIZE_WORK_LIMIT). You expect a DFA that accepts [0, 5]. union(lo, hi), the same language, and an upper end of 2147483646 both give exactly that.
  3. Instead it throws, every time: AssertionError in StateSet.decr with assertions on, ArrayIndexOutOfBoundsException: Index -5 out of bounds for length 9 with them off.
  4. Why: determinize walks the labels where arcs start (min) and end (max + 1) in sorted order. 1 + 2147483647 wraps to -2147483648, and the sort compares point - other.point, which overflows again against 0. The points 11, -2147483648, 0 look sorted, so the walk closes [0, 10] at 11 before opening it at 0.

Who is affected

#

Only application code that builds its own automaton with an arc ending at exactly Integer.MAX_VALUE (an open upper end, as Lucene's own tests write it) next to an arc starting at label 0, and determinizes it. One tiny automaton is enough and it fails every time. The in-tree regex, wildcard, prefix and fuzzy query builders do not produce the label.

Mechanism, terms and numbers583 words

Operations.determinize builds each DFA state by sweeping, in sorted order, the labels where the arcs of the current NFA state set start (find(t.min)) and end (find(1 + t.max)), and sorts these points with PointTransitions.compareTo, which returns point - other.point (Operations.java:530, :615, :619-620 at 5adff78bb168).

For an arc ending at Integer.MAX_VALUE the end point wraps to Integer.MIN_VALUE. Against point 0 the subtraction overflows as well (0 - MIN and MIN - 0 are both MIN), so the comparator has no consistent order. For union({0}[11, MAX], {0}[0, 10]) the state set reached on label 0 discovers the points 11, MIN, 0, which already look ascending; the sweep reaches 11, the end of [0, 10], before 0, its start, and decrements a state it never added (StateSet.decr, :772). Result: AssertionError with -ea, ArrayIndexOutOfBoundsException: Index -5 out of bounds for length 9 with -da. The same language with the union's operands swapped, or with Integer.MAX_VALUE - 1 as the upper end, determinizes correctly.

The fix is one line: Integer.compareUnsigned(point, other.point). Only application-built automata carry the label in the code we inspected: the in-tree RegExp, wildcard, prefix, Levenshtein and UTF-8 paths stay at or below 0x10FFFF.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/automaton/)

#
  1. Operations.java:653-661: the union is not deterministic and has more than one state, so the subset construction runs.
  2. :713-721: for the state set reached on label 0 (one NFA state from hi, one from lo, hi first because it comes first in the union), points.add(t) files [11, MAX] under 11 (start) and 1 + MAX (end, :620), then [0, 10] under 0 (start) and 11 (end, already there). 1 + 2147483647 wraps to -2147483648, so the discovered points are 11, MIN, 0.
  3. :530 (the fix site) and :615: compareTo(11, MIN) = 11 - MIN wraps negative (11 first, as wanted); compareTo(MIN, 0) = MIN, negative ("MIN before 0"); compareTo(0, MIN) = 0 - MIN, which wraps to MIN, also negative. So 11 < MIN < 0 < 11: a cycle. ArrayUtil.timSort sees the run 11, MIN, 0 as already ascending and leaves it. Only the pair {0, MIN} is inconsistent; for every point p >= 1 the subtraction happens to put MIN after p.
  4. :735-788: the sweep visits 11 first. No arc is open, so nothing is emitted (:739-764); then it closes the arcs ending at 11, which is [0, 10], and calls statesSet.decr(dest) (:772) for a state it never incremented.
  5. StateSet.java:58-61: assert inner.containsKey(state) fails with -ea; with -da, indexOf returns a negative slot and IntIntHashMap.indexGet reads values[-5] (lucene/core/src/java/org/apache/lucene/internal/hppc/IntIntHashMap.java:330-334).

In the correct order 0, 11, end the sweep opens [0, 10] at 0; at 11 it emits [0, 10], closes it and opens [11, MAX]; at the end point it emits [11, end - 1], and end - 1 wraps back to Integer.MAX_VALUE (:763). So only the sort is wrong.

NFARunAutomaton (@lucene.internal, NFARunAutomaton.java:35) reuses Operations.PointTransitionSet and StateSet.decr (:389, :434). On main its getNumTransitions for the state after label 0 fails the same way (StateSet.decr:59 <- NFARunAutomaton.java:434), while step() on the same input is correct (a later probe). It also has a second signed comparison against the wrapped point (:421); see Suggested fix.

Exposure and likelihood207 words
  • Who. Application code that builds its own automaton with an arc ending at exactly Integer.MAX_VALUE (for example makeCharRange(x, Integer.MAX_VALUE) or addTransition(s, d, x, Integer.MAX_VALUE) as an open upper end) plus an arc starting at label 0 that meet in one determinize step, and then determinizes it, directly or through code that calls Operations.determinize. No configuration, no scale. Whether a shape fails depends only on discovery order: union(hi, lo) throws, union(lo, hi) works.
  • Not affected. RegExp, wildcard, prefix, Levenshtein (with its in-tree callers) and the UTF-8 conversion never emit a label above 0x10FFFF, so the in-tree paths we inspected that build automata from strings cannot reach it. Where the automaton package itself passes Integer.MAX_VALUE to determinize or complement, it is a work limit (ByteRunAutomaton.java:45, CompiledAutomaton.java:260, RegExp.java:680), not a label.
  • Effect. A loud internal exception instead of a DFA, with assertions on or off, on every current release. Before 8.10.0 (the old SortedIntSet, replaced by StateSet in LUCENE-9983, #163) the -da run returned a silently wrong, empty-language DFA instead.
  • Likelihood: rare. No matching public report was found in the searches listed under Prior reports, and no in-tree component we inspected builds the label; but a shape that fails fails every time.

Why it looks unintended

#
  • determinize promises a DFA and documents only TooComplexToDeterminizeException; here it fails with an internal assertion or array index.
  • No upper label bound is checked, Lucene's own tests use Integer.MAX_VALUE as an open upper end, and swapping the union's operands makes it work.
  • Disputed: the package describes a Unicode alphabet, so a maintainer could reasonably call labels above 0x10FFFF out-of-domain input.
The full argument209 words
  • Contract. determinize: "Determinizes the given automaton"; it documents only TooComplexToDeterminizeException (Operations.java:640-652) and its own assert requires a deterministic result (:794).
  • Legal input. makeCharRange(int min, int max) returns the empty automaton only for min > max and checks no upper bound (Automata.java:136-151); addTransition checks the state ids but no label value (Automaton.java:154-160).
  • Lucene's own tests write the value (a test-side idiom). TestRegExpParsing builds the expected automata of [^c] and [^b-d] with makeCharRange('d', Integer.MAX_VALUE) and makeCharRange('e', Integer.MAX_VALUE) (TestRegExpParsing.java:190-194, :240-244). Caveat: those unions are already deterministic, so determinize returns early (:654-657) and they never reach the sweep; they show the idiom, not a test of this path.
  • Order dependence. For one language the outcome depends only on the order of the union's operands, and the tested upper ends below Integer.MAX_VALUE work (MAX - 1, 0x10FFFF, 1000000), as expected since only 1 + MAX wraps. If such labels are inside the contract, that order dependence is not defensible.
  • History. Both lines date from the commit that widened labels from char to int (2010); with char labels 1 + max was at most 0x10000 and could not wrap. No commit, issue or PR found discusses the wrap.
The devil's-advocate check322 words

The strongest case for "intended", and a strong one: the package documents a "DFA/NFA implementation with Unicode alphabet" (package-info.java:33); makeCharRange speaks of a codepoint; makeAnyChar ends at Character.MAX_CODE_POINT (Automata.java:105-107); Automaton.getStartPoints adds an end point only when max < Character.MAX_CODE_POINT (Automaton.java:639); and NFARunAutomaton's default constructor assumes the Unicode code point space (NFARunAutomaton.java:56-62). So an arc ending at Integer.MAX_VALUE can be read as outside the domain, and the same shape ending at Character.MAX_CODE_POINT works. Operations, Automata and Automaton are also @lucene.experimental (Operations.java:56, Automata.java:44, Automaton.java:43), and a maintainer once said a special label must be valid Unicode for UTF32ToUTF8 (#6094, LUCENE-5030). The issue could reasonably be closed as out-of-domain input ("validate or document the bound instead"). The cross-model reviewer (OpenAI GPT-5.6) refuted the bug on these grounds, the Unicode alphabet plus the @lucene.experimental tag, with high confidence, while reproducing it and agreeing with the root cause; its own test passed with fix A, but it left the fix verdict open because it did not run the test suite.

Our answer (a judgement): no javadoc states the precondition and nothing enforces it; @lucene.experimental allows API changes, not undocumented exceptions; the same language works with the operands swapped; and the result is an opaque internal exception rather than a validation error. On #6094 Michael McCandless had first suggested Integer.MAX_VALUE as a special label and withdrew it only because those labels go through UTF32ToUTF8 (after Artem Lukanin noted the conversion fails), so that remark is about UTF32ToUTF8, not determinize. Lucene's tests write the value as an open upper end, but only as a test-side idiom. That is a fair argument for Low priority and for treating the fix as hardening (or for documenting or validating the bound), not evidence that the behaviour is intended. The independent reproducer, the devil's-advocate verifier and the adjudication did not accept it as making the behaviour intended.

Suggested fix

#

Recommended Compare the points unsigned (fix A)

Compare the sweep points unsigned: return Integer.compareUnsigned(point, other.point); in PointTransitions.compareTo. The wrapped end then sorts last, and point - 1 wraps back to Integer.MAX_VALUE. The repro passes with assertions on and off, and core's util.automaton tests run 239 with 0 failures. NFARunAutomaton needs one more unsigned compare (fix B).

    @Override
    public int compareTo(PointTransitions other) {
-      return point - other.point;
+      return Integer.compareUnsigned(point, other.point);
    }

Compare the points unsigned (fix A) (validated by the checks) (recommended)

In Operations.PointTransitions.compareTo (Operations.java:530), return Integer.compareUnsigned(point, other.point) instead of point - other.point.

    @Override
    public int compareTo(PointTransitions other) {
-      return point - other.point;
+      return Integer.compareUnsigned(point, other.point);

Trade-offs

One line, no new branch. Labels are meant to be non-negative (Automaton.next asserts label >= 0, Automaton.java:692; the sweep's lastPoint = -1 sentinel, Operations.java:730 / :740, assumes it), so every point is in [0, 2^31], which fits an unsigned int: the wrapped end MIN reads as 2^31 and sorts last, and the emitted point - 1 (:763) wraps back to Integer.MAX_VALUE. For every point in [0, Integer.MAX_VALUE] the order is the same as before. Caveat: nothing rejects a negative label, and determinize(union({0}[-5, 3], {0}[10, 20])), which works on main today, fails the same way under A (the negative point sorts last; AssertionError at StateSet.decr:59, or Index -5 with -da; a later probe). Fix C keeps today's order for negative labels. Integer.compare alone would not fix it (MIN would sort first). On its own, A leaves NFARunAutomaton's second site (see B).

Downstream note

#

Downstream code that builds its own automata with Integer.MAX_VALUE as an open upper end can hit this exception when it determinizes them; automata built by the in-tree query parsers cannot.

How it was found

#

A proof-obligation audit of Operations.determinize's contract: for every legal input (arcs with 0 <= min <= max) it must return a DFA for the same language, which needs the sweep points in increasing order. That obligation fails for the end point 1 + Integer.MAX_VALUE, which wraps; a public-API JUnit test then witnessed the crash.

The method in full160 words

Method: semi-formal (a proof-obligation audit of a method's contract, witnessed by an executable repro).

  • The audit took determinize's promise (a deterministic automaton for the same language, Operations.java:640-653, :794) over the full input domain the public factories accept, and checked what the sweep relies on: the points must be in increasing order so every arc is opened before it is closed. find(1 + t.max) (:620) can wrap, and point - other.point (:530) is then no consistent order.
  • A public-API JUnit test built from makeChar, makeCharRange, concatenate and union witnessed the failure with assertions on and off, and the compareUnsigned change made it pass.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier and an adjudication then reproduced it: the reproducer and the cross-model reviewer with their own tests, the devil's-advocate verifier with the finder's test and its own probe, the adjudication with the reproducer's test (see Prior reports, history and checks).

History

#

Introduced in 2010 by LUCENE-2265 (5b74a4ec611), which changed automaton labels from char to int and added both the subtraction comparator and the 1 + max end point. First released in 4.0.0-alpha; present through 10.6.0 and main. Not fixed upstream.

Versions tested6 rows

Introduced by 5b74a4ec611 (2010-05-03, svn r940671), commit subject "LUCENE-2265: cutover Fuzzy, Wildcard, Regexp queries to operate on Unicode UTF32 code point not UTF16 code units", for the issue LUCENE-2265 (now #3341, "improve automaton performance by running on byte[]"); committed by Michael McCandless, CHANGES credits Robert Muir and Mike McCandless; no pull request. It rewrote BasicOperations.determinize into the point sweep and added both point - other.point and find(1+t.max); git log -S on both strings finds it as the first commit. With char labels 1 + max was at most 0x10000 and could not wrap. LUCENE-5752 (#6814, 2014, first in 4.10.0) moved the sweep into Operations unchanged and LUCENE-9570 (2020) only reformatted it, which is why plain git blame names those commits.

LUCENE-9983 (#163, 8.10.0) replaced SortedIntSet with StateSet: through 8.9.0 the -da run returns a silently wrong, empty-language DFA; from 8.10.0 on it throws. -ea throws in every version. Upstream main aa366ae209a (2026-11-04) still has both lines.

LFV-1180, snapshot of 2026-11-08

Registry title
Operations.determinize throws (AssertionError with -ea, ArrayIndexOutOfBoundsException with -da) for a valid automaton with an arc ending at Integer.MAX_VALUE, because its sweep sorts points with 'point - other.point' and the arc's end point 1 + max wraps to Integer.MIN_VALUE
Area
util / automaton (Operations.determinize sweep: PointTransitions / PointTransitionSet; also NFARunAutomaton's lazy determinize)
Priority
Low, rank 1157: Operations.determinize throws for a valid hand-built automaton with an arc ending at exactly Integer.MAX_VALUE next to an arc starting at label 0, in every release since 4.0.0-alpha (before 8.10.0, without assertions, it returned a wrong automaton instead). No query string or Lucene builder produces such labels, and current releases fail loudly.
Impact class
minor
Impact note
Only application code that determinizes an automaton it built itself with an arc ending at exactly Integer.MAX_VALUE (for example makeCharRange(x, Integer.MAX_VALUE) as an open upper end, an idiom upstream's own TestRegExpParsing uses) next to an arc starting at label 0 in the same determinize subset is hit: Operations.determinize, and NFARunAutomaton's lazy determinize, throw with -ea and -da on a tiny input with default settings, and whether a given shape fails depends only on the order in which the subset's points are discovered (union(hi, lo) fails, union(lo, hi) of the same language works); RegExp, wildcard, prefix, Levenshtein and UTF-8 paths never emit labels above 0x10FFFF and cannot reach it; every release from 4.0.0-alpha to 10.6.0 and main (before 8.10.0 the -da run returned a silently wrong, empty-language automaton instead of throwing).
Summary
You build the union of {0}[11, Integer.MAX_VALUE] and {0}[0, 10] (a 0 followed by any one label) with Automata.makeChar, makeCharRange, Operations.concatenate and union, and call Operations.determinize; you expect a deterministic automaton for the same language. Instead it throws AssertionError in StateSet.decr with -ea, and ArrayIndexOutOfBoundsException 'Index -5 out of bounds for length 9' with -da. The sweep files the end of the [11, MAX] arc under 1 + MAX, which wraps to Integer.MIN_VALUE, and sorts its points with the subtraction point - other.point, which is no consistent order for MIN and 0, so it closes the [0, 10] arc before opening it and decrements a state it never added.
