Automaton.copy(a) on a itself throws IndexOutOfBoundsException once a has an accept state, and leaves the automaton half-copied

a.copy(a) should append a second copy of automaton a, but once a has an accept state it throws IndexOutOfBoundsException and leaves a half-copied, because copy grows a before it reads the source's size. Only direct users of the experimental Automaton API hit it, in releases 4.10.0 to 10.6.0 and main.

The finding in 30 seconds

#

Background: how an Automaton numbers its states, and what copy does

#
  1. An Automaton has states 0 to n-1 (getNumStates() is n), arcs that leave each state, and a bit set of accept states. setAccept(s, true) sets bit s and rejects any s that is not below n.
  2. a.copy(b) appends b to a: b's state s becomes a's state n + s (n = a's state count before the call), with the same arcs and the same accept bit. Lucene uses it to build unions and optional or repeated automata from parts.

The finding, step by step

#
  1. Build a 2-state automaton a: state 0 has an arc 'a' to state 1, and state 1 accepts, so a matches "a".
  2. Call a.copy(a). copy appends a copy of its argument, so you expect states 2 and 3 with 2 -a-> 3 and state 3 accepting: 4 states, 2 arcs. Copying a separate identical automaton gives exactly that.
  3. Instead it throws IndexOutOfBoundsException: Index 5 out of bounds for length 4, with assertions on and off. If you catch it, a has 4 states but 1 arc: state 2 claims an arc that was never stored.
  4. Why: copy grows a to 4 states before it reads the source's state count (now 4, not 2) and accept bits (now a's own). It marks state 3 accepting, then finds that new bit and asks for state 2 + 3 = 5, which does not exist.

Who is affected

#

Application code that builds automata with the experimental Automaton API and appends an automaton to itself, for example to build L(a)L(a) in place. Every automaton that accepts anything fails; no scale is needed. No Lucene query, regex, analyzer or suggester path does it: Lucene's own callers always copy into a new automaton. Releases 4.10.0 to 10.6.0.

Mechanism, terms and numbers490 words

Automaton.copy(other) documents: "Copies over all states/transitions from other. The states numbers are sequentially assigned (appended)." (Automaton.java:201-204 at 5adff78bb168). It grows the receiver's state array and advances nextState (:209-216) before it reads other.getNumStates() (:217) and scans other.getAcceptStates() (:218-223). When other is the receiver, the count it reads is already doubled and the bit set it scans is the receiver's own live set, so after marking a copied accept state the scan finds that new bit and calls setAccept on a state that does not exist. For 0 -a-> 1 with state 1 accepting, a.copy(a) throws IndexOutOfBoundsException: Index 5 out of bounds for length 4 from setAccept (:108), with assertions on and off. The arcs are copied only after the scan (:225-231), so a caller that catches the exception keeps an automaton with 4 states but 1 arc. Without accept states the same call is correct, and copying from a separate identical automaton gives 4 states and 2 arcs. No Lucene caller copies an automaton into itself; application code that builds automata with the experimental API can, for example to build L(a)L(a) in place. The statement order dates from the LUCENE-5752 rewrite (2014); releases 4.10.0 through 10.6.0 and main are affected (12 releases and main executed). Reading the count before growing and bounding the scan by it fixes it.

The bug

#
  1. copy(other) (Automaton.java:205-236) sets stateOffset = getNumStates() (:208), grows states and appends other's state records (:209-215), and advances nextState += other.nextState (:216).
  2. Only then does it read int otherNumStates = other.getNumStates() (:217, the fix site) and BitSet otherAcceptStates = other.getAcceptStates() (:218). getAcceptStates() returns the automaton's own live set (:139-141).
  3. The scan while (state < otherNumStates && (state = otherAcceptStates.nextSetBit(state)) != -1) { setAccept(stateOffset + state, true); state++; } (:219-223) marks each copied accept state.
  4. With other == this and 2 states: stateOffset is 2, but otherNumStates reads 4 and the scanned set is a's own. The scan finds bit 1 and sets bit 3 (fine, 4 states exist now); then, from state = 2, nextSetBit finds that new bit 3 and the scan calls setAccept(2 + 3). setAccept checks Objects.checkIndex(state, getNumStates()) (:108): 5 is not below 4, so it throws.
  5. The arc copy (:225-231) never runs. State 2's record was already appended and points past the stored arcs, so the automaton is left with 4 states, 1 arc and accept states {1, 3}, and state 2 claims one arc that is not there.

With state 0 accepting instead, the scan sets bit 2, finds it, and fails at index 4. Without accept states a.copy(a) is correct: the rest of copy reads its bounds before changing them, and each System.arraycopy reads the old range and writes the free range right after it (the two do not overlap).

Exposure and likelihood219 words
  • Who. Direct users of the Automaton API (Automaton.java:43: @lucene.experimental) who pass an automaton to its own copy. One natural use: build the concatenation L(a)L(a) in place with a.copy(a), an epsilon from a's accept state to the start of the copy, and clearing the old accept bit. With a separate source those steps give the same language as Operations.concatenate(List.of(a, a)); with a as its own source the first step throws.
  • Effect. A loud IndexOutOfBoundsException in the calling thread, and a corrupt receiver if the caller catches it (4 states, 1 arc, state 2 claiming an arc that was never stored). No silent wrong result and no hang was observed; the observed effect is the immediate exception.
  • Not affected. Every non-test caller of Automaton.copy copies into a freshly created automaton: Operations.optional (Operations.java:176, :188), Operations.repeat(a, min, max) with min == 1 (:301) and Operations.union (:486), so even a union of a list holding the same automaton twice is safe. Operations.repeat (:312, :315) and GraphTokenStreamFiniteStrings (:171) use Automaton.Builder.copy (Automaton.java:936-952), which reads the source's count first and cannot take the Builder itself. No Lucene source or test calls x.copy(x).
  • Likelihood: contrived. No Lucene caller, and no public report was found since 2014.

Why it looks unintended

#
  • The javadoc promises to append other's states and transitions and neither forbids nor explicitly allows other == this; nothing in the class, tests or history excludes it.
  • The rest of copy already handles it: a self-copy without accept states is correct.
  • Two states and one arc are not an absurd input, and the call fails halfway, corrupting the automaton.
The full argument234 words
  • Contract. "Copies over all states/transitions from other. The states numbers are sequentially assigned (appended)." (Automaton.java:201-204). The class javadoc (:33-43), the package docs, the tests, CHANGES.txt and MIGRATE.md state no aliasing rule. Self-copy is not explicitly allowed either: appending other as it was before the call is the reasonable reading of the javadoc, not a stated promise.
  • The method almost handles it. Only the accept scan reads other after the receiver has changed. ArrayUtil.grow keeps the old contents, each System.arraycopy writes a range that does not overlap the one it reads, and the two fix-up loops read other.nextState and other.nextTransition before those change, so a self-copy without accept states is correct. The failure depends on the accept set, not on a design rule.
  • History. copy came with the 2014 Automaton rewrite (LUCENE-5752, #6814). The issue's 29 comments never discuss copying an automaton into itself, and no Lucene source or test does it. The unreleased branch revisions before the shipped text were unsafe in another way: they iterated the receiver's own live HashSet of accept states while adding to it, which threw ConcurrentModificationException with two accept states (with one it passed, because the iterator had already moved past the only element when the new one was added, and a HashSet iterator checks for changes in next(), not in hasNext()). Nothing suggests the case was ever considered, let alone deliberately excluded.
The devil's-advocate check198 words

The strongest case for "intended". Self-aliasing in bulk-append methods is undefined by Java convention: java.util.Collection.addAll says its behaviour is undefined if the argument is modified during the call, which it notes is the case when the argument is this collection and it is nonempty; copy is in effect an addAll of other's states. Automaton is @lucene.experimental, getAcceptStates() is marked @lucene.internal (Automaton.java:131-141) and returns a live view, no Lucene code calls a.copy(a), a self-copy alone does not change the language, and the failure is loud.

Why it fails. The JDK states its aliasing rule explicitly where it applies; Automaton states none. @lucene.experimental marks API instability, not permission to throw on a call the javadoc allows. A self-copy is a meaningful construction step (such as building L(a)L(a) in place), and the method throws halfway through, leaving the receiver corrupt instead of failing fast. That is a fair argument for Low priority and for accepting a documentation-only fix (option C), not evidence that the exception is intended; a maintainer could reasonably close it that way. The independent reproducer, the cross-model review lenses (OpenAI GPT-5.6, "intended argument weak"), the devil's-advocate verifier and the adjudication all rejected it.

Suggested fix

#

Recommended Read the source's count first and bound the scan by it (fix A)

Read other.getNumStates() before copy grows the receiver, and stop the accept scan at that count, checking each nextSetBit result. Nothing changes when other is a different automaton built through the API. The repro passes with assertions on and off, and core's util.automaton and util.graph tests run 254: 252 pass, 2 skipped, 0 failures.

    int stateOffset = getNumStates();
    // read before this grows: other may be this
    int otherNumStates = other.getNumStates();
    states = ArrayUtil.grow(states, nextState + other.nextState);
    // ... unchanged: append other's states and shift their pointers ...
    nextState += other.nextState;
    BitSet otherAcceptStates = other.getAcceptStates();
    for (int state = otherAcceptStates.nextSetBit(0);
        state != -1 && state < otherNumStates;
        state = otherAcceptStates.nextSetBit(state + 1)) {
      setAccept(stateOffset + state, true);
    }
All options and trade-offs3 options · 640 words

Fix A was built and checked through gradle in a scratch worktree at 5adff78bb168; B and C were not run. Both halves of A are needed: the old loop checks its bound before calling nextSetBit, so moving only the count read still lets a just-set bit through (with only state 0 accepting, the scan sets bit 2, nextSetBit(1) returns it and the loop calls setAccept(4)). The repro, whose accept state is 1, would pass under that partial change, so review the loop, not only the test. A maintainer may prefer B (reject the call) or C (a javadoc line); A makes the documented call work in a small change (5 lines added, 4 removed). The same change applies to the 4.10.0 source and makes it pass.

Read the source's count first and bound the scan by it (fix A) (validated by the checks) (recommended)

#

In Automaton.copy (Automaton.java:205-236), move int otherNumStates = other.getNumStates(); above the growth of states, and replace the accept loop with one that checks every nextSetBit result against otherNumStates.

    int stateOffset = getNumStates();
    // read before this grows: other may be this
    int otherNumStates = other.getNumStates();
    states = ArrayUtil.grow(states, nextState + other.nextState);
    // ... unchanged: append other's states and shift their pointers ...
    nextState += other.nextState;
    BitSet otherAcceptStates = other.getAcceptStates();
    for (int state = otherAcceptStates.nextSetBit(0);
        state != -1 && state < otherNumStates;
        state = otherAcceptStates.nextSetBit(state + 1)) {
      setAccept(stateOffset + state, true);
    }

Trade-offs

For other != this the result is unchanged for every automaton whose accept bits all lie below its state count, which is anything built through setAccept (it checks the index): other is not modified during the call, so its count and its accept bits below that count are the same whenever they are read. One behaviour change: getAcceptStates() (@lucene.internal) returns the live bit set, so a caller can set a bit at or above the state count directly; today copy can throw on such a bit, and fix A skips it (for a 2-state source with bits {0, 5}: Index 5 out of bounds for length 2 without the fix, accept {0} with it). For other == this the scan stops at the original states, and the arc copy then runs as for a separate source (4 states, 2 arcs, accept {1, 3}). No extra allocation or pass; one extra comparison per accept state (not measured).

Reject a self-copy (fix B)

#

Add if (other == this) throw new IllegalArgumentException("cannot copy an automaton into itself"); at the top of copy, plus a javadoc line.

Trade-offs

Fails fast and leaves the receiver untouched, but turns a meaningful call (such as building L(a)L(a) in place) into an error, while A makes it work for one extra comparison per accept state (not measured). Not run.

Document that other must not be this (fix C)

#

Add "other must not be this automaton" to the javadoc.

Trade-offs

Cheapest, but keeps the half-copied receiver for anyone who misses the line. Not run.

How it was found

#

A proof-obligation audit of Automaton's contract: copy(other) must append all of other's states and transitions for every argument its javadoc allows, the automaton itself included. The obligation fails because copy reads other's size after growing the receiver; a public-API JUnit test then witnessed the exception.

The method in full114 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked copy against its javadoc for every argument it allows. For other == this the obligation is that every read of other sees other as it was before the call; the state count and the accept bits are read after nextState has grown.
