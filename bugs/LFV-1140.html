Index sort with STRING_LAST: a merge over more than 2^31 distinct values puts the largest values on the wrong side of documents without a value

A STRING_LAST index sort's merge keys documents without a value at Integer.MAX_VALUE (2,147,483,647) and documents with one at their 64-bit global ordinals. When one addIndexes(CodecReader...) call merges more than 2^31 distinct values, the largest values silently land on the wrong side of the documents without a value (after them ascending, before them with reverse=true); since 8.2.0.

The finding in 30 seconds

#

The merge keys mix two widths: a document with a value gets its global ordinal as a long, a document without one gets the int sentinel Integer.MAX_VALUE. Once global ordinals reach 2^31 - 1, the sentinel is no longer the largest key.

Background: how an index-sorted merge orders documents

#
  1. With an index sort, every segment is written in sort order. For a STRING field, a segment keeps each distinct value once in a sorted dictionary and numbers it (its segment ordinal); documents are compared by these numbers.
  2. Segment ordinals mean nothing across segments, so a merge builds an OrdinalMap that numbers the distinct values of all inputs together: the global ordinals, stored as long.
  3. Each document gets a long merge key, its global ordinal, and the merge interleaves the inputs by these keys. For STRING_LAST, a document without a value needs a key above every value.

The finding, step by step

#
  1. Sort an index by a string field with documents without a value last: new SortField("s", SortField.Type.STRING, false, SortField.STRING_LAST). Within one segment this works.
  2. Merge two indexes sorted this way with one addIndexes(CodecReader...) call. The merge numbers every distinct s value of all inputs, counting values that only deleted documents still hold: with 2^30 + 1 values per input, these global ordinals run from 0 to 2,147,483,649.
  3. You expect each document without a value to get a merge key above every value, so it still sorts last.
  4. Instead its key is the int Integer.MAX_VALUE, 2,147,483,647, which is below the key of the document with the largest value, 2,147,483,649. The merged segment puts the document without a value first, at doc 0 (this ascending example; with reverse=true, where STRING_LAST puts documents without a value first, the same keys move the largest values ahead of them).
  5. No error, with assertions on or off; only CheckIndex at level 2 or higher notices. An index's own merges never see that many values: it takes about 2^31 source documents.

Who is affected

#

The route shown to reach it: applications that opt into a STRING_LAST index sort on a STRING field and call addIndexes(CodecReader...) on two or more sorted indexes whose dictionaries, deleted documents' values included, together hold more than 2^31 distinct values while the live total fits under MAX_DOCS. An index's own merges cannot get there; STRING_FIRST is unaffected.

Mechanism, terms and numbers397 words

For an index sort on a STRING field, IndexSorter.StringSorter gives each document a long merge key: its global ordinal from an OrdinalMap over all inputs' dictionaries, or, for a document without a value and STRING_LAST, the int sentinel Integer.MAX_VALUE. Global ordinals are not bounded by the int range, so at 2^31 distinct values in one merge the largest value ties with the sentinel (reader order decides), and with more than 2^31 the largest values get keys above it: the merged segment silently places documents without a value ahead of them (ascending sort; with reverse=true, where STRING_LAST puts documents without a value first, the same keys move the largest values ahead of them), against its declared sort. The in-segment comparator of the same class stays correct, because segment ordinals are ints. The route shown to get there is addIndexes(CodecReader...) over heavily deleted sorted indexes of about 2^31 documents in total; an index's own merges cannot, and STRING_FIRST is not affected. In 7.6.0-8.1.1 the same input threw ArithmeticException (Math.toIntExact, LUCENE-8592); LUCENE-8900 made the keys long in 8.2.0 and dropped that guard. Low priority; the fix is a long sentinel.

The mechanism (main 5adff78bb168, IndexSorter.java)

#
  1. getComparableProviders builds OrdinalMap.build(null, values, PackedInts.DEFAULT) over every input's SortedDocValues, deleted documents' values included (:487); getGlobalOrds returns LongValues (:497).
  2. It sets final int missingOrd = Integer.MAX_VALUE for STRING_LAST, else Integer.MIN_VALUE (:488-493).
  3. A document with a value returns globalOrds.get(readerValues.ordValue()), a long; a document without one returns missingOrd, widened to 2,147,483,647 (:498-506).
  4. The keys are cached per reader and compared with Long.compare (:98-111); MultiSorter orders the merged documents by that comparison (MultiSorter.java:88-97), and MergeState.java:223 takes the merge's doc maps from MultiSorter.sort.
  5. The in-segment getDocComparator (:512-528) fills an int[] with the same sentinel and int segment ordinals, which always stay below Integer.MAX_VALUE, so inside one segment the order is right. Only the merge keys disagree with it.

Exposure and likelihood315 words
  • How the input is legal. addIndexes(CodecReader...) reserves only the sum of live numDocs() (IndexWriter.java:3275-3297); OneMerge(CodecReader...) sets totalMaxDoc to that sum (MergePolicy.java:245-255); the default findMerges(CodecReader...) puts all inputs in one merge (MergePolicy.java:616-619); with an index sort the inputs are not wrapped (IndexWriter.java:3548-3566). The OrdinalMap still counts values that only deleted documents hold, so heavily deleted sources of about 2^30 documents each can pass 2^31 global ordinals while the merged index fits MAX_DOCS. A scale model with the document limit lowered to 10 showed exactly this accounting: addIndexes(Directory...) rejected the inputs, addIndexes(CodecReader...) accepted them, and the largest live key, 11, counted the deleted documents' values.
  • Not reachable otherwise. An index's own merges cannot get there for a single-valued STRING sort (its maxDoc is at most MAX_DOCS < 2^31 - 1). addIndexes(Directory...) (IndexWriter.java:3124-3144), which the bundled IndexMergeTool uses, counts maxDoc and rejects such inputs. The open PR #16847 (long global doc ids) may widen the reach to ordinary merges, depending on its final design.
  • Effect. Live documents without a value sort ahead of the documents with the largest values (ascending sort; with reverse=true, where STRING_LAST puts documents without a value first, the same keys move the largest values ahead of them); either way the merged segment contradicts its declared sort, and document contents are unchanged. CheckIndex at level 2 or higher reports segment has indexSort=<string: "s"> missingValue=SortField.STRING_LAST but docID=0 sorts after docID=1; the default level 1 reports the index clean. Code that relies on the index sort, such as early termination on that sort, could return wrong top hits (by reading, not executed).
  • Default vs opt-in. Opt-in: an index sort, STRING_LAST, and the expert addIndexes(CodecReader...) API. Assertions on or off make no difference.
  • Likelihood: contrived. About 2^31 source documents (an estimate: hundreds of GB) in one call; no public report found since 8.2.0 (2019).

More files, environment, full output349 words

TestStringSorterMissingLast (one method, extends LuceneTestCase, package org.apache.lucene.index of the lucene/core tests, ASF header included). It uses only public API: IndexSorter.StringSorter's constructor with SortField.STRING_LAST and a SortedDocValuesProvider. Segment 1's document has no value; segment 2's document holds the largest of the 2^31 + 2 terms. The cost is the OrdinalMap over 2^31 + 2 terms, so the test needs -Ptests.heapsize=2g (the default 512 MB test heap is too small: a run with a 512 MB heap ran out of memory inside OrdinalMap.build). No smaller input can show the bug: it needs at least 2^31 global ordinals (2^31 gives a tie with the missing key, more than 2^31 a strict inversion; the repro uses 2^31 + 2).

The dictionaries are larger than their one-document segments, which IndexWriter never writes itself; they stand in for huge segments whose values mostly belong to deleted documents. The real trigger, about 2^31 source documents in one addIndexes(CodecReader...) call, was not run. An end-to-end variant that runs the real addIndexes(CodecReader...) merge over two sorted segments (each a deleted document with a value and a live document, dictionaries enlarged to 2^30 + 1 terms by a FilterCodecReader) fails on main, 10.6.0, 10.5.2 and 9.12.3 with STRING_LAST: the document with a value must be doc 0 expected:<0> but was:<1>, and passes with 2^10 + 1 terms; it is supporting evidence, not the repro.

As a regression test the same method fits in TestIndexSorting next to testMissingStringLast. With the fix in place, the file passes checkGoogleJavaFormat; it differs from the first executed copy only by one comment wrapped onto two lines, as the formatter asked, and fails the same way. Why it looks unintended

#
  • STRING_LAST promises "missing string values sort last", and ComparableProvider promises its long keys order documents as the comparator does; neither has a size limit.
  • In 7.6.0-8.1.1 this input threw ArithmeticException (Math.toIntExact, LUCENE-8592); LUCENE-8900 made the keys long and dropped the guard without discussion.
  • The same class's in-segment comparator keeps documents without a value last; only the merge keys disagree.
The full argument183 words
  • Contracts. SortField.java:346: "Pass this as a missingValue constructor parameter to have missing string values sort last." IndexWriterConfig.java:504: setIndexSort, "Set the Sort order to use for all (flushed and merged) segments." IndexSorter.java:57-62: ComparableProvider "Returns a long so that the natural ordering of long values matches the ordering of doc IDs for the given comparator". No javadoc, CHANGES entry or test caps the combined dictionary of a merge.
  • History. LUCENE-8592 (#9638, 9f29ed0757e, 2018) wrapped the global ordinal in Math.toIntExact, so this input threw (executed on 7.6.0 and 8.1.1). LUCENE-8900 (#9943, 17f2f96a5cf, 2019, "Simplify MultiSorter") turned the keys into longs and returned the raw ordinal but kept the int sentinel; its thread mentions neither.
  • Tests. TestIndexSorting.testMissingStringLast (TestIndexSorting.java:479) checks the property on small inputs only; no test covers global ordinals past the int range.
  • Not claimed, not investigated. The SortedSetSortField route through the same code. SortedSetSelector documents "Fields containing Integer.MAX_VALUE or more unique values are unsupported" (SortedSetSelector.java:35); whether that limit, stated for one selector view, also covers the combined dictionary of a merge was not examined.
The devil's-advocate check118 words

Strongest argument: Michael McCandless wrote on #9638 that for single values "it should never happen that the long ord exceeds positive int space"; no Lucene merge or bundled tool reaches 2^31 values; and the repro uses synthetic dictionaries larger than their segments. Why it fails: that sentence is a claim of impossibility, true for an index's own merges, and its consequence was a fail-loud guard that a later refactor removed as a side effect. addIndexes(CodecReader...) legally merges inputs whose dictionaries exceed it, and Lucene itself feeds StringSorter views whose value count exceeds maxDoc (SortedSetSortField.java:184-191, through SortedSetSelector, whose views report the whole multi-valued dictionary, SortedSetSelector.java:156-157). The argument lowers the priority (hence Low), not the intent.

Suggested fix

#

Recommended Use Long.MAX_VALUE / Long.MIN_VALUE as the missing merge key (A, recommended, validated)

Make the missing merge key a long outside the global-ordinal range in StringSorter.getComparableProviders: Long.MAX_VALUE for STRING_LAST, Long.MIN_VALUE for STRING_FIRST. The in-segment int sentinels stay. The repro passes, and so do the 62 TestIndexSorting tests.

      OrdinalMap ordinalMap = OrdinalMap.build(null, values, PackedInts.DEFAULT);
      // global ordinals are longs and may exceed Integer.MAX_VALUE
      final long missingOrd;
      if (missingValue == SortField.STRING_LAST) {
        missingOrd = Long.MAX_VALUE;
      } else {
        missingOrd = Long.MIN_VALUE;
      }

Use Long.MAX_VALUE / Long.MIN_VALUE as the missing merge key (A, recommended, validated)

#

In IndexSorter.StringSorter.getComparableProviders (IndexSorter.java:488-493), declare missingOrd as long and use Long.MAX_VALUE for STRING_LAST, Long.MIN_VALUE otherwise. Global ordinals are >= 0 and below the total value count, so these keys are always outside their range. getDocComparator keeps its int sentinels, which are correct for int segment ordinals.

      OrdinalMap ordinalMap = OrdinalMap.build(null, values, PackedInts.DEFAULT);
      // global ordinals are longs and may exceed Integer.MAX_VALUE
      final long missingOrd;
      if (missingValue == SortField.STRING_LAST) {
        missingOrd = Long.MAX_VALUE;
      } else {
        missingOrd = Long.MIN_VALUE;
      }

Trade-offs

No cost: the key is already a long. The merged order changes only for inputs that hit the bug.

Use the OrdinalMap's value count and -1 as the missing keys (B, equivalent variant)

#

Set the STRING_LAST key to ordinalMap.getValueCount() and the STRING_FIRST key to -1: one past the largest global ordinal and one below the smallest.

Trade-offs

The same order as A with dense keys; A stays closer to the existing code. Not run.

Restore Math.toIntExact on the global ordinal (C, not recommended)

#

Narrow the global ordinal with Math.toIntExact, as LUCENE-8592 did, so such a merge throws ArithmeticException instead of writing a mis-sorted segment.

Trade-offs

Loud instead of silent, but a legal addIndexes(CodecReader...) call is then rejected. 7.6.0 and 8.1.1 behave this way (executed); not run on main.

Downstream note

#

Only an application that itself runs such an addIndexes(CodecReader...) merge can trigger it; a downstream product that relies on early termination over a STRING_LAST index sort could then return wrong top hits from the merged segment (by reading, not executed).

How it was found

#

A proof-obligation audit of IndexSorter.StringSorter's contract: its merge keys must order documents as its in-segment comparator does, for every global ordinal an OrdinalMap can return. The obligation fails once global ordinals reach Integer.MAX_VALUE, and a one-method JUnit test on the stock main jars witnessed it.

The method in full130 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation comes from ComparableProvider (IndexSorter.java:57-62): the long keys must order documents as getDocComparator does. For StringSorter the audit compares the key ranges: global ordinals take any value in [0, valueCount) with a long valueCount, while the missing key is fixed at Integer.MAX_VALUE. The obligation holds only while valueCount <= 2^31 - 1, and nothing on the addIndexes(CodecReader...) path enforces that.
  • A one-method JUnit test with dictionaries just past that bound witnessed the gap, and the long sentinel made it pass.
  • An independent reproducer wrote its own end-to-end addIndexes test, cross-model reviews and a devil's-advocate verifier tried to refute it, and an adjudication re-ran the tests ("Prior reports, history and checks").

History

#

Introduced by LUCENE-8900 "Simplify MultiSorter" (17f2f96a5cf, branch_8x aad4b411cdd, 2019-07-09, #9943), first released in 8.2.0. 7.6.0-8.1.1 throw ArithmeticException on the same input instead (executed on 7.6.0 and 8.1.1; the tags between have the same Math.toIntExact). Every release run from 8.2.0 to 10.6.0, and main, fails; not fixed upstream.

Versions tested11 rows

Before: LUCENE-6766 (2016) introduced the int sentinel; LUCENE-8592 (9f29ed0757e, Jim Ferenczi, 2018, #9638) added Math.toIntExact on the global ordinal, so 7.6.0-8.1.1 fail loudly. 7.0.0-7.5.0 truncate the ordinal with an (int) cast, a different defect (by reading).

Introduced: 17f2f96a5cf on master and aad4b411cdd on branch_8x (Adrien Grand, 2019-07-09; a JIRA patch migrated as #9943). In MultiSorter, return Math.toIntExact(globalOrds.get(readerValues.ordValue())); became return globalOrds.get(readerValues.ordValue()); while missingOrd stayed an int. On the 8.2.0 jars, putting back only the pre-commit MultiSorter.java restores the ArithmeticException, and the commit's file with long sentinels passes. LUCENE-9330 (2020) moved the code unchanged into IndexSorter.StringSorter.

Not fixed upstream: upstream main 1c2072f0284 (2026-11-02) still has the int sentinel; the last commit on IndexSorter.java is e6f12f31d08 (#16202, 2026-06-05). 8.8.2-8.11.3 are inferred, not run.

Hits only applications that opt into an index sort on a STRING field with missing value STRING_LAST and call IndexWriter.addIndexes(CodecReader...) on the leaves of two or more indexes already sorted the same way whose doc-values dictionaries, counting values that only deleted documents still hold, together have at least 2^31 distinct values while the live total fits under MAX_DOCS: the merged segment then silently places live documents without a value ahead of the documents with the largest values, contrary to its declared sort, with -ea and -da; CheckIndex at level 2 or higher reports the violation (the default level 1 does not), and index-sort early termination on that sort could return wrong top hits (by reading, not executed); STRING_FIRST, an index's own merges of a single-valued STRING sort (maxDoc <= MAX_DOCS < 2^31 - 1) and smaller addIndexes calls are not affected, and the full-scale trigger (2^31 or more source documents) was not run (proof-only end to end).
Summary
You configure the index sort new SortField("s", SortField.Type.STRING, false, SortField.STRING_LAST) and merge, with IndexWriter.addIndexes(CodecReader...), sorted source indexes whose 's' dictionaries together hold more than 2^31 - 1 distinct values, expecting documents without a value to come after every document with one, as STRING_LAST and the in-segment comparator promise. At merge, IndexSorter.StringSorter gives a document with a value its long global ordinal (from an OrdinalMap over every input's full dictionary, deleted documents' values included) but gives a document without a value the int key Integer.MAX_VALUE, so every value whose global ordinal is above 2^31 - 1 sorts after the missing documents (a value at exactly 2^31 - 1 gets the same key as they do). The merged segment is written out of its declared sort with no error: in an end-to-end addIndexes(CodecReader...) test over two one-live-document segments whose dictionaries a FilterCodecReader enlarges to 2^30 + 1 terms each, the document without a value ends up at doc 0.
