Bundled commons-codec upgrades changed phonetic filter tokens (RefinedSoundex in 10.2.0; Metaphone, ColognePhonetic and Daitch-Mokotoff on main), and no release note says to re-index

Lucene's phonetic filters get their codes from the bundled commons-codec, whose upgrades changed the codes of ordinary words (on main Metaphone chair is XR, not KR; since 10.2.0 RefinedSoundex codes Köln as K378). No release note says to re-index, so an index kept across the upgrade silently changes sound-alike matches.

The finding in 30 seconds

#

PhoneticFilter passes each word to a commons-codec Encoder and DaitchMokotoffSoundexFilter to commons-codec's DaitchMokotoffSoundex; Lucene has no code tables of its own. So the indexed codes follow the bundled commons-codec: 1.13 up to 10.1.0, 1.17.2 in 10.2.0 to 10.6.0, 1.23.0 on main. Fixes in those releases changed four encoders' codes, and none of the bumps touched phonetic code, phonetic tests or a note about commons-codec.

Background: phonetic fields

#
  1. A phonetic field indexes a sound code for each word, so a query spelled differently but sounding the same still matches: with Metaphone on Lucene 10.x, kair and chair are both KR.
  2. The same analysis runs when you index and when you search, and a query matches only when both produce the same code. Segments written before an upgrade keep the codes the old version computed.
  3. inject=true, the factory default, indexes the code and the original word; inject=false indexes only the code.

The finding, step by step

#
  1. You index chair, kair and share in a field analyzed with PhoneticFilter(new Metaphone(), false) on Lucene 10.5.2 (10.6.0 gives the same codes). The field stores the sound codes KR, KR and XR, so a query for kair finds chair too.
  2. You upgrade to main, the future 11.0, and keep the index; its migration guide says "Simply open the index with the new version". You expect the same codes, or a note telling you to re-index, as Lucene gave in 2014 for a commons-codec upgrade (LUCENE-6058) and gives in 11.0 for Snowball.
  3. Instead, main bundles commons-codec 1.23.0 rather than 1.17.2, and its Metaphone fix codes chair as XR. On the old index the query chair now finds only share; a freshly built index finds chair and share.
  4. Across four encoders, 12 of 72 test queries return different documents than a fresh re-index (0 in same-version controls). With the same inject=false, ColognePhonetic codes quick as 4 instead of 44, so the query quick finds 0 documents instead of 2.
  5. Nothing in CHANGES.txt or MIGRATE.md mentions these upgrades. The new codes are correct upstream fixes; the missing re-index note is the bug.

Who is affected

#

Applications that use PhoneticFilter (Metaphone, ColognePhonetic, RefinedSoundex) or DaitchMokotoffSoundexFilter and keep their index across an upgrade. Released: RefinedSoundex words with letters outside A-Z, from 10.2.0 (19.0% of 2,901 city names). With 11.0: ColognePhonetic changes 11.8-16.7% of distinct words in two test corpora, Metaphone 0.7-2.1%. No error; matches change silently.

Mechanism, terms and numbers627 words

Lucene's phonetic filters compute no codes themselves: PhoneticFilter calls a commons-codec Encoder and DaitchMokotoffSoundexFilter calls commons-codec's DaitchMokotoffSoundex, so the indexed codes are whatever the bundled commons-codec computes. Lucene bundled 1.13 up to 10.1.0, 1.17.2 from 10.2.0 to 10.6.0, and 1.23.0 on main and branch_11x. Bug fixes in those releases changed the codes of ordinary words: RefinedSoundex Köln gets K378 since 10.2.0 (10.1.0 indexed only the word), and on main Metaphone chair is XR instead of KR, ColognePhonetic quick is 4 instead of 44 and Daitch-Mokotoff it's is 040000 instead of 034000. Neither CHANGES.txt nor MIGRATE.md mentions any of these upgrades or asks for re-indexing, although Lucene announced the same kind of change in 2014 (LUCENE-6058, "any index using it will need to be rebuilt"), gives re-index advice for the 11.0 Snowball upgrade, and tells 11.0 users to "Simply open the index with the new version". An index written by the older version and searched by the newer one silently changes its sound-alike matches in that field until it is re-indexed. The new codes are correct; the fix is a migration note.

The code (main 645d4fe14a20)

Line 73 is where commons-codec computes the code; if the encoder throws, lines 75-76 keep only the word.

  • Delegation: PhoneticFilter encodes every token with the configured Encoder (PhoneticFilter.java:73); DaitchMokotoffSoundexFilter calls encoder.soundex(term) on a DaitchMokotoffSoundex (DaitchMokotoffSoundexFilter.java:38, :79).
  • inject: with inject=false the code replaces the word (PhoneticFilter.java:80-84); with inject=true, the factory default (PhoneticFilterFactory.java:52-53, :106), the code is emitted and the word is kept at the same position (:86-96). So with inject=true exact-word matches survive an upgrade and only sound-alike matches change.
  • Why 10.1.0 kept only the word for Köln: commons-codec 1.13's RefinedSoundex throws ArrayIndexOutOfBoundsException for letters outside A-Z (Müller: "Index 155 out of bounds for length 26"), and PhoneticFilter.java:75-76 swallows it. From 1.16.1 (CODEC-311) the encoder skips those letters and codes the rest of the word (Köln -> K378, the code of Kln). With inject=false the code now replaces the word; with inject=true the word stays and the code is added.
  • The pin: gradle/libs.versions.toml:8 is commons-codec = "1.23.0" on main; the release POMs declare 1.17.2 for 10.2.0 to 10.6.0 and 1.13 for 9.0.0 to 10.1.0.

Why CI did not notice

#

Lucene's phonetic tests pin no input that changed: the Metaphone assertions use "aaa bbb ccc easgasg" (TestPhoneticFilter.java:36-44), and TestDaitchMokotoffSoundexFilter uses the same words. None of the bumps touched phonetic code, phonetic tests or a note about commons-codec: the commons-codec part of each changed only the version catalog, the lock file and license checksums, plus one test module-info line (requires org.apache.commons.codec;) in #14129 and #14177, and #14177 also carried the OpenNLP upgrade with its CHANGES line.

Why it looks unintended

#
  • LUCENE-6058 (2014), same module and dependency: a commons-codec upgrade changed an experimental filter, "so any index using it will need to be rebuilt".
  • 11.0's guide asks for re-indexing after the Snowball upgrade, yet says "Simply open the index with the new version".
  • The 10.2.0 bump was hand-written; its OpenNLP sibling got a CHANGES line, commons-codec none.
The full argument239 words
  • Same module, same dependency: CHANGES.txt:11240-11243, LUCENE-6058: "With the upgrade to Apache commons codec 1.10, the experimental BeiderMorseFilter has changed its behavior, so any index using it will need to be rebuilt." On that issue Michael McCandless wrote: "It's marked experimental so it's allowed to change between releases... but I'll updated the CHANGES.txt entry to advertise this." (#7120).
  • Current practice for analysis-output changes: Snowball in 11.0 (MIGRATE.md:196-202: "Existing indexes that used Snowball stemming should be reindexed so search-time analysis matches indexed tokens"), Thai in 10.6 (:757-764: "may therefore stop matching queries analyzed with 10.6 until it is reindexed"), Romanian in 10.0 (:871-873: "you should reindex Romanian documents").
  • The released bump was hand-written: #14129 ("Upgrade commons-codec from 1.13.0 to 1.17.2", msfroh, merged by msokolov) is not a dependabot PR. Its backport #14177 also upgraded OpenNLP, which got a 10.2.0 CHANGES line (GITHUB#14130, CHANGES.txt:2026-2027); commons-codec got none.
  • The new upgrade policy raises the stakes: 11.0 invites in-place upgrades across majors (MIGRATE.md:136-154), exactly where phonetic matches change.
  • Nothing points users to the codec notes: no Lucene documentation (javadoc, the module overview, CHANGES.txt or MIGRATE.md) says which commons-codec version is bundled; only the build files and the published POM do, and the module overview names Apache Commons Codec without a version (lucene/analysis/phonetic/src/java/overview.html:28-31). By contrast the ICU module's overview has a "Backwards Compatibility" section about the Unicode version it tracks (lucene/analysis/icu/src/java/overview.html:343-350).
The devil's-advocate check203 words

The intended-behaviour verifier and the cross-model lenses built the strongest case for "intended": no Lucene document promises stable phonetic codes (the javadoc says only "Create tokens for phonetic matches" and links to Commons Codec), DaitchMokotoffSoundexFilter is @lucene.experimental, dependabot PRs carry the skip-changelog label in every ecosystem, including the gradle bumps (.github/dependabot.yml:53; also :13 GitHub Actions and :35 uv) and 349 of 351 dependabot commits touch no CHANGES.txt, CONTRIBUTING.md says only "You may want to add a CHANGES entry", the bump PR bodies quote the commons-codec release notes, the 10.0 Snowball upgrade got only an API note (MIGRATE.md:867-869), and the main-only part is still unreleased.

Why it fails: LUCENE-6058 is the same module, the same dependency and an experimental filter, and was announced with a rebuild note; #14661 added skip-changelog to the bot labels so the changelog-check workflow skips bot PRs, which is not a decision about migration notes for changed analysis output (that workflow has since been turned off, #16366); the released 10.2.0 change came from a hand-written PR; and no Lucene documentation tells a user which codec notes to read. These arguments are why the bug is minor and documentation-only, not why the omission would be intended.

A. An 11.0 MIGRATE.md section next to the Snowball note (validated by the checks) (recommended)

#

Add to "Migration from Lucene 10.x to Lucene 11.0" on main and branch_11x (a draft):

### Phonetic analysis: commons-codec upgrade changes some phonetic codes

The analysis-phonetic module gets its encoders from the bundled commons-codec, which
Lucene 11 upgrades to 1.23.0 (Lucene 10.2 to 10.6 bundle 1.17.2). Fixes in commons-codec
change the codes of some ordinary words:

- `Metaphone`: "CH" follows the basic Metaphone rules, for example `chair` is `XR`
  instead of `KR` (CODEC-249).
- `ColognePhonetic`: repeated codes are collapsed, for example `quick` is `4` instead
  of `44` (CODEC-317).
- `DaitchMokotoffSoundexFilter`: punctuation is ignored, for example `it's` is `040000`
  instead of `034000` (commons-codec 1.19.0).

Indexes upgraded from Lucene 10.1 or earlier (commons-codec 1.13) also see a
`RefinedSoundex` change from Lucene 10.2: words with letters outside A-Z, such as `Köln`,
now get a code (`K378`) where only the original word was indexed before (CODEC-311).

An existing index whose fields use these encoders may stop matching queries analyzed
with Lucene 11 until it is reindexed. With `inject=true` (the `PhoneticFilterFactory`
default) the original words are indexed too, so exact-word matches still work, but
sound-alike matches change. Reindex such fields.

Trade-offs

  • Docs only; no behaviour change. It reaches users who read the migration guide before upgrading.
  • The example codes are executed facts for these words only; the draft names no Beider-Morse change because none was measured.

Not recommended: revert or pin an older commons-codec

#

Trade-offs

An application that must keep its old codes until it re-indexes can run its own commons-codec version at its own risk (the history proxy runs ran the main jars with 1.17.2 and 1.13); Lucene should not.

Downstream note

#

Search servers that bundle their own commons-codec version follow their own pin rather than Lucene's, so the same re-index advice applies when they upgrade it.

How it was found

#

Non-formal: release-jar differential testing. The finder compared the token streams of 55 analyzers and about 650 filter chains across five Lucene versions and matched every difference to a CHANGES or MIGRATE entry. Only the phonetic differences had none; the release POMs and the commons-codec changelog then showed the cause.

The method in full129 words
  • Method: a harness dumped canonical token streams of 55 analyzers and about 650 SPI filter chains on the stock jars of 9.12.3, 10.0.0, 10.3.2, 10.5.2 and main, each with its own declared dependencies, over five corpora (edge texts, 662 natural texts, 11,288 stemmer-vocabulary texts, 133,872 code points in 4 contexts, CJK with user dictionaries) and 249 generated per-parameter factory configurations.
  • Oracle: the previous release's output plus the release notes; every adjacent-version difference was mapped to a CHANGES or MIGRATE entry. The phonetic differences were the only family with none.
  • Cause: reading the release POMs (commons-codec 1.13, 1.17.2, 1.23.0) and the commons-codec changelog, then a four-encoder JUnit test pinning the previous release's tokens.
  • Tier: non-formal (no model or proof), because the oracle is a previous release, not an exact semantics.

LFV-514, snapshot of 2026-11-07

Registry title
Bundled commons-codec upgrades changed phonetic filter tokens (RefinedSoundex in 10.2.0; Metaphone, ColognePhonetic and Daitch-Mokotoff on main), and neither CHANGES.txt nor MIGRATE.md mentions it or asks for re-indexing (documentation defect)
Area
analysis / phonetic (PhoneticFilter and DaitchMokotoffSoundexFilter output from the bundled commons-codec); release notes (lucene/CHANGES.txt, lucene/MIGRATE.md)
Priority
Low, rank 1248: A documentation-only gap, but released (RefinedSoundex since 10.2) and upgraders who keep their index silently get different phonetic matches.
Impact class
minor
Impact note
Only applications with an analysis-phonetic field (PhoneticFilter with RefinedSoundex, Metaphone or ColognePhonetic, or DaitchMokotoffSoundexFilter; default constructors and ordinary words) that keep their index across a Lucene upgrade without re-indexing are hit: from 10.1 to 10.2 or later, RefinedSoundex words with letters outside A-Z gain a new code, and from 10.x to main (the future 11.0) ordinary words change code under the other three encoders (in the independent reproduction's corpora 11.8-16.7% of distinct words under ColognePhonetic, 0.7-2.1% under Metaphone, 0.6% under Daitch-Mokotoff), so in that field old documents and new queries stop matching each other until it is re-indexed; no scale is needed, there is no exception and no index damage, and the encoder code itself is correct.
Summary
You index a field with a phonetic filter, for example PhoneticFilter with ColognePhonetic, upgrade Lucene and keep searching the same index; you expect the same tokens or a CHANGES/MIGRATE note telling you to re-index, as Lucene gave in 2014 for the Beider-Morse change of the commons-codec 1.10 upgrade (LUCENE-6058) and gives on main for the Snowball upgrade (GITHUB#15505). Instead the bundled commons-codec moved from 1.13 (up to 10.1.0) to 1.17.2 (10.2.0 to 10.6.0) and to 1.23.0 (main) with no note anywhere, and its encoder fixes change the tokens: 'Köln' gets the RefinedSoundex code K378 from 10.2.0 (10.1.0 kept only the word), and on main 'chantaient' becomes XNTN instead of KNTN (Metaphone), 'quick' 4 instead of 44 (ColognePhonetic) and "it's" 040000 instead of 034000 (Daitch-Mokotoff). An index written by the older version and searched by the newer one silently misses or changes matches in that field until it is re-indexed (executed: ColognePhonetic with inject=false, the query 'quick' finds no document in a 10.5.2 index searched by main, against 2 in a fresh index).
