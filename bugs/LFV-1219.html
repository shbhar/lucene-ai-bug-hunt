NotDocIdSet throws NullPointerException instead of matching every document when the wrapped set is empty and its iterator() is null

Negating an empty set with NotDocIdSet should match every document, but when the empty set reports itself with a null iterator(), as an empty RoaringDocIdSet does, the first nextDoc() throws NullPointerException. In every release since 5.0.0; Lucene's own code never builds this combination.

The finding in 30 seconds

#

NotDocIdSet walks the inner set's iterator alongside docs 0 to maxDoc-1 and skips the docs it finds there. It takes the inner iterator as given, so when the inner set says "empty" with a null iterator, its first step forward dereferences null.

Background in three steps

#
  1. A DocIdSet is a set of document ids in one segment. Its iterator() walks them in order with nextDoc() and advance(target).
  2. DocIdSet.iterator() may return null to mean "no docs match". An empty RoaringDocIdSet, the compressed set the query cache stores, does exactly that.
  3. NotDocIdSet(maxDoc, in) is the complement: it iterates every doc in [0, maxDoc) that in does not contain. RoaringDocIdSet uses it internally to store a very dense block as its few missing docs.

The finding, step by step

#
  1. Build an empty set with Lucene's own builder: new RoaringDocIdSet.Builder(10).build(). Its iterator() returns null, which DocIdSet documents as the way to say "no docs match".
  2. Negate it over 10 documents: new NotDocIdSet(10, empty).iterator(). You expect docs 0, 1, ..., 9; negating DocIdSet.EMPTY (a non-null empty iterator) gives exactly that.
  3. iterator() returns normally and cost() says 10: NotDocIdSet stored the inner iterator, null, without checking it.
  4. The first nextDoc() calls advance(0) on that null and throws NullPointerException, with assertions on and off. No wrong result: the failure is loud.

Who is affected

#

Only code that uses the internal NotDocIdSet directly and wraps a set that can be empty and reports empty with a null iterator, such as an empty RoaringDocIdSet from its public builder. It fails exactly when that set is empty, at any size. Lucene's own code never builds this combination.

Mechanism, terms and numbers370 words

NotDocIdSet "encodes the negation of another DocIdSet" (NotDocIdSet.java:25), and DocIdSet.iterator() "can return null if there are no docs that match" (DocIdSet.java:42-46), which is exactly what an empty RoaringDocIdSet returns (RoaringDocIdSet.java:393-394). NotDocIdSet.iterator() stores in.iterator() without a null check (NotDocIdSet.java:51), so the negation of an empty set does not iterate every document: iterator() and cost() succeed, and the first nextDoc() or advance() throws NullPointerException at NotDocIdSet.java:65, with assertions on and off.

Both classes are @lucene.internal, and Lucene's only production NotDocIdSet wraps a set whose iterator is never null, so only code that uses these classes directly is hit. Both halves arrived together in LUCENE-5983 (5.0.0). The fix reads a null inner iterator as DocIdSetIterator.empty(), as LRUQueryCache already does.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/)

#
  1. RoaringDocIdSet.iterator() (util/RoaringDocIdSet.java:392-397) returns null when cardinality == 0, as DocIdSet.iterator() allows (search/DocIdSet.java:42-46: "This implementation can return null if there are no docs that match").
  2. NotDocIdSet.iterator() (util/NotDocIdSet.java:50-94) stores final DocIdSetIterator inIterator = in.iterator(); (:51) with no null check and returns an anonymous iterator. Its cost() returns maxDoc without touching inIterator (:88-92), so creating the iterator and asking its cost both succeed. :51 is the fix site.
  3. The first nextDoc() calls advance(doc + 1) (:57-58). advance sees doc > nextSkippedDoc (0 > -1) and calls inIterator.advance(doc) (:64-65): NullPointerException. The skip loop's inIterator.nextDoc() (:76) is the other dereference.
  4. Controls on main (assertions off): the same empty set given as DocIdSet.EMPTY, whose iterator is a non-null empty one, negates to 0,1,...,9 over 10 docs, and a Roaring set {3} negates to 0,1,2,4,...,9. So the failure depends only on how the inner set represents "empty".
  5. Reach: the only production new NotDocIdSet(...) is in RoaringDocIdSet.Builder (util/RoaringDocIdSet.java:101), for a super-dense block, over a private ShortArrayDocIdSet of at least one excluded doc whose iterator() is never null (:297); a full block uses AllDocIdSet instead (:71-73). LRUQueryCache caches possibly empty RoaringDocIdSets but never negates them and maps the null to DocIdSetIterator.empty() (search/LRUQueryCache.java:859-862). TestNotDocIdSet wraps only a BitDocIdSet (TestNotDocIdSet.java:32), so the null case was never tested.
Exposure and likelihood119 words
  • Who: application code that uses the @lucene.internal NotDocIdSet directly (NotDocIdSet.java:28) over a DocIdSet that represents empty with the documented null: an empty RoaringDocIdSet from its public Builder, or the application's own DocIdSet.
  • Not hit: Lucene itself. No query, collector, query cache or index path builds NotDocIdSet over such a set (see the mechanism, point 5). A code search found no use of NotDocIdSet in Elasticsearch, OpenSearch or Solr.
  • Effect: a NullPointerException in the caller's thread, assertions on and off, at the first nextDoc() or advance(), which can be far from where the set was built. No wrong result, no index damage, no hang.
  • Scale: none needed: one document and an empty inner set fail.

Why it looks unintended

#
  • NotDocIdSet is documented as "the negation of another DocIdSet", any one; DocIdSet.iterator() documents null for "no docs that match". No precondition says otherwise.
  • Core code handles the null elsewhere: LRUQueryCache maps it to an empty iterator ("docIdSet.iterator() is allowed to return null when empty").
  • Lucene fixed the same unchecked-null pattern as a bug before: LUCENE-3816 (FilteredDocIdSet) and LUCENE-3446 (BooleanFilter).
The full argument174 words
  • Contract. The class javadoc says without condition "This DocIdSet encodes the negation of another DocIdSet" (NotDocIdSet.java:25), and the "Sole constructor" takes any DocIdSet (:38-42). DocIdSet.iterator() documents the null (DocIdSet.java:42-46). No javadoc, code comment, test, CHANGES or MIGRATE entry says the inner iterator must be non-null.
  • The null is live in core. LRUQueryCache.java:859-862 handles it ("docIdSet.iterator() is allowed to return null when empty but we want a non-null iterator here"); BaseDocIdSetTestCase.java:134-136 reads a null iterator as the empty set; TestRoaringDocIdSet.java:102 asserts the null for an empty set.
  • History. LUCENE-5983 (bfc1b3deee5, 2014) added both the unchecked in.iterator() and Roaring's null return. That first NotDocIdSet did check the then-documented null of in.bits() (if (inBits == null) return null;), so the iterator case looks like an oversight.
  • Precedent. LUCENE-3816 fixed FilteredDocIdSet "if null was returned from the delegate DocIdSet.iterator(), which is allowed to return null by DocIdSet specification when no documents match" (lucene/CHANGES.txt:16895-16898); LUCENE-3446 (573ecd5d7b6, 2011) fixed "NPE in BooleanFilter when DocIdSet/DocIdSetIterator is null".
The devil's-advocate check224 words

Strongest case for "intended": both classes are @lucene.internal; the util package says its "APIs ... are primarily internal and may change between releases" (util/package-info.java:35); NotDocIdSet exists for one private Roaring encoding whose inner set is never empty; and the project would rather remove null iterators at the source (open #6181, LUCENE-5117, "DISI.iterator() should never return null"). So composing the two classes is unsupported. An independent reviewer from another model family (OpenAI GPT-5.6) reproduced the NPE, agreed on the root cause and the fix, and on this ground still returned "not real" with high confidence.

Why it fails: @lucene.internal is a compatibility disclaimer, not a ban on use (the same package doc says these classes "are generally not intended for direct use by most applications, but may be useful for advanced integrations or extensions", :22-23); the class documents itself as the negation of any DocIdSet, and the null is the current documented contract; the failing input is the most ordinary set there is, built with Lucene's own builder; and #6181 is an open proposal, so until it lands the documented null governs. Verdict: not intended. The argument is about reach, which is why the priority is Low. A maintainer may still take the change only as hardening, prefer fix C, or decline to support direct composition of the two classes.

Suggested fix

#

Recommended A. Read a null inner iterator as empty (validated)

In NotDocIdSet.iterator(), read a null inner iterator as DocIdSetIterator.empty() (1 line becomes 3). The repro passes with assertions on and off; TestNotDocIdSet, TestRoaringDocIdSet, TestLRUQueryCache and the lint checks pass.

// DocIdSet#iterator may return null when no docs match
final DocIdSetIterator it = in.iterator();
final DocIdSetIterator inIterator = it == null ? DocIdSetIterator.empty() : it;
All options and trade-offs3 options · 466 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B and C are by reading. A fixes every producer of the documented null; C fixes only the Roaring producer and is complementary. Open PR #16510 adds an intoBitSet that also calls inIterator.nextDoc(): A covers it, because it fixes the captured variable.

A. Read a null inner iterator as empty (validated) (recommended)

#

In NotDocIdSet.iterator() (NotDocIdSet.java:51):

// DocIdSet#iterator may return null when no docs match
final DocIdSetIterator it = in.iterator();
final DocIdSetIterator inIterator = it == null ? DocIdSetIterator.empty() : it;

Trade-offs

  • One null check per iterator() call, none per document.
  • Fixes every DocIdSet that uses the documented null, not only Roaring. docIDRunEnd() stays correct: min(NO_MORE_DOCS, maxDoc) is maxDoc (:84).
  • Also covers any later use of inIterator, such as the intoBitSet of open PR #16510; if #16510 lands first, the fix applies unchanged.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: on stock the repro fails with assertions on and off; with A it passes, on and off.
  • With A: TestNotDocIdSet 9 of 9, TestRoaringDocIdSet 23 of 23, search.TestLRUQueryCache 37 of 40 (3 skipped) and the repro: 73 tests, 3 skipped, 0 failures.
  • checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest for lucene/core pass with the fix (run without the test file, whose 101-column line needs tidy).
  • Not run: the full lucene/core suite, and the optional editorconfig check eclint, a separate tool from ecjLint that this build has not configured (gradle logs that it skips it).

B. Return an all-docs iterator when the inner one is null

#

if (it == null) return DocIdSetIterator.all(maxDoc); at the top of iterator(). The negation of nothing is every doc; all() is a range iterator over [0, maxDoc) that implements docIDRunEnd (DocIdSetIterator.java:36-41, :102).

Trade-offs

Skips the skip loop for the empty case, but adds a second return path with a different iterator class, and for a negative maxDoc (the constructor does not check it, NotDocIdSet.java:38-42) it throws IllegalArgumentException from all() (DocIdSetIterator.java:37-39) where A gives an empty iterator. Elasticsearch fixed its own, separately written NotDocIdSet this way in 2011 (elastic/elasticsearch#953). By reading, not run.

C. Make RoaringDocIdSet return an empty iterator (complementary)

#

RoaringDocIdSet.iterator() returns DocIdSetIterator.empty() instead of null (RoaringDocIdSet.java:393-394). Alan Woodward (romseygeek) raised changing these null returns on elastic/elasticsearch#143798 ("I wonder if we should change this?"), since "most callsites" do not check them.

Trade-offs

Removes this repro's trigger and that downstream NPE, but not the failure for other DocIdSets that return the documented null; TestRoaringDocIdSet.java:102, which asserts the null, must change, so it also changes Roaring's tested empty representation. Good together with A, not instead of it. By reading, not run.

Downstream note

#

Relevant downstream only to code that negates a possibly empty RoaringDocIdSet, or its own null-iterator DocIdSet, with NotDocIdSet; a code search found no use of NotDocIdSet in Elasticsearch, OpenSearch or Solr.

How it was found

#

Semi-formal: a proof-obligation audit of NotDocIdSet's contract checked its "negation of another DocIdSet" promise against every value DocIdSet.iterator() may return, including the documented null. The null case has no handling, and a one-test JUnit repro on stock main witnessed the NullPointerException.

The method in full99 words
  • Obligation: for every legal inner DocIdSet, the iterator of new NotDocIdSet(maxDoc, in) returns exactly the docs in [0, maxDoc) that in does not contain (NotDocIdSet.java:25), including when in.iterator() returns the documented null (DocIdSet.java:42-46).
  • Finding: iterator() stores the inner iterator unchecked (:51) and dereferences it at :65 and :76; an empty RoaringDocIdSet from the public builder produces the null (RoaringDocIdSet.java:393-394).
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review with a refute and an intended lens, an intended-behaviour review and an adjudication (see Independent checks).
