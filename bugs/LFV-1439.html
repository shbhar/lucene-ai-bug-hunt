CodecUtil's header and footer javadoc gives the wrong byte order: read as documented, the magic number comes back byte-swapped

CodecUtil's javadoc says the codec header and footer integers (Magic, Version, AlgorithmID, Checksum) are written like DataOutput#writeInt / #writeLong, which are little-endian since 9.0, but Lucene writes them big-endian on purpose. Read as documented, the magic 0x3fd76c17 comes back as 0x176cd73f; only the javadoc is wrong.

The finding in 30 seconds

#

The files of Lucene's default codec start with a codec header and end with a codec footer: a few fixed-width integers (a magic number, a version, a checksum) around the data. CodecUtil's javadoc gives their layout, and other file-format docs point to it.

Byte order in 20 seconds

#
  1. A 4-byte integer can be stored high byte first (big-endian) or low byte first (little-endian). The magic number 0x3fd76c17 is 3f d7 6c 17 big-endian and 17 6c d7 3f little-endian.
  2. Read with the wrong order, the same 4 bytes give a different number: 3f d7 6c 17 read low byte first is 0x176cd73f.
  3. Since Lucene 9.0, DataOutput#writeInt and DataInput#readInt are little-endian, while CodecUtil.writeBEInt and readBEInt are big-endian.

The finding, step by step

#
  1. Write a file with CodecUtil.writeHeader(out, "Foo", 1) and CodecUtil.writeFooter(out). It is 28 bytes and starts with the magic bytes 3f d7 6c 17.
  2. Read it back as the javadoc grammar says: Magic and Version are {@link DataOutput#writeInt Uint32}, so readInt(); the footer's Checksum is writeLong, so readLong().
  3. You expect what the javadoc promises: Magic "is always" 1071082519 (0x3fd76c17), then Version 1.
  4. Instead readInt() takes the low byte first, as it has since 9.0: Magic 0x176cd73f, Version 16777216, footer Magic 0xe89328c0, Checksum 0x62233eeb00000000, each byte-swapped. A header written with writeInt as documented is rejected with "codec header mismatch".
  5. Lucene's own writer and reader both use big-endian (writeBEInt / readBEInt), so indexing and search are fine. Only the javadoc is wrong, from 9.0.0 to 10.6.0 and on main.

Who is affected

#

Only developers who read or write codec headers and footers by following this javadoc: a file inspector, a recovery tool, a reimplementation in another language, or a custom format that writes its own header with writeInt. Everyone who goes through CodecUtil, as all of Lucene's codecs do, is unaffected, and the first file shows the mismatch.

Mechanism, terms and numbers585 words

The files of Lucene's default codec start with a codec header (Magic, CodecName, Version) and end with a codec footer (Magic, AlgorithmID, Checksum). CodecUtil's javadoc describes both and types Magic, Version and AlgorithmID as {@link DataOutput#writeInt Uint32} and Checksum as {@link DataOutput#writeLong Uint64}. Since 9.0.0 (LUCENE-9047) those methods write little-endian ("LE byte order"), but CodecUtil has kept writing these four fields big-endian on purpose, through writeBEInt / writeBELong, and its readers read them big-endian. So a reader that follows the javadoc gets every one of these values byte-swapped (the magic 0x3fd76c17 reads as 0x176cd73f, Version 1 as 16777216), and a header written as documented is rejected by checkHeader with CorruptIndexException. Lucene's indexing, search and checksum validation are unaffected. The fix is javadoc only: link #writeBEInt / #writeBELong and say big-endian.

The contract and the code (main f794ff5a505c, CodecUtil.java)

#
  • :57-65, the header grammar: CodecHeader --> Magic,CodecName,Version; :60 "Magic --> {@link DataOutput#writeInt Uint32}. This identifies the start of the header. It is always {@value #CODEC_MAGIC}."; :64 "Version --> {@link DataOutput#writeInt Uint32}".
  • :396-405, the footer grammar: CodecFooter --> Magic,AlgorithmID,Checksum; :399 Magic and :401 AlgorithmID "--> {@link DataOutput#writeInt Uint32}", :403 "Checksum --> {@link DataOutput#writeLong Uint64}".
  • The linked methods: DataOutput.java:68 "Writes an int as four bytes (LE byte order)", :218 "Writes a long as eight bytes (LE byte order)"; their inverses DataInput.java:97 and :141 say the same.
  • The writer: writeHeader calls writeBEInt(out, CODEC_MAGIC) and writeBEInt(out, version) (:84, :86); writeFooter calls writeBEInt(out, FOOTER_MAGIC), writeBEInt(out, 0) and writeCRC (:411-413), which calls writeBELong (:686). writeBEInt writes the high byte first (:690-695).
  • The reader: checkHeader compares readBEInt(in) with CODEC_MAGIC (:186-194, "codec header mismatch"); checkFooter and retrieveChecksum read the footer magic and the algorithm id with readBEInt (through the private validateFooter, :584, :594); readCRC uses readBELong (:667). Writer and reader agree. The Checksum is a CRC-32 zero-extended into those 8 bytes: readCRC and writeCRC reject a value with any of the upper 32 bits set (:666-670, :680-686).
  • The one hint: the helpers' javadocs say "write int value on header / footer with big endian order" (:689, and likewise :697, :703, :711), but neither grammar links them.

The 28 bytes of the example

#

writeHeader(out, "Foo", 1) then writeFooter(out) writes 3f d7 6c 17 | 03 46 6f 6f | 00 00 00 01 (Magic, CodecName as a length byte and "Foo", Version) and c0 28 93 e8 | 00 00 00 00 | 00 00 00 00 eb 3e 23 62 (footer Magic, AlgorithmID 0, the CRC-32 of the 20 bytes before the checksum). Read as documented: Magic 0x176cd73f, Version 16777216 (1 << 24), footer Magic 0xe89328c0, Checksum 0x62233eeb00000000. AlgorithmID 0 and the codec name read correctly.

Reach

#

The IndexHeader grammar defers to CodecHeader (:97-100), and 11 core javadocs link CodecUtil#writeHeader, #writeIndexHeader or #writeFooter, 37 links in all: 34 are the Header and Footer elements of 9 file-format grammars (SegmentInfos, Lucene99SegmentInfoFormat, Lucene94FieldInfosFormat, Lucene90NormsFormat, Lucene90LiveDocsFormat, Lucene90CompoundFormat, Lucene90TermVectorsFormat, Lucene103BlockTreeTermsWriter, Lucene104PostingsFormat), and 3 are prose that requires them (CompoundFormat.java:188-189, OfflineSorter.java:509). Lucene's own tests check that every file of a default-codec test index has a codec header (TestAllFilesHaveCodecHeader) and a checksum footer (TestAllFilesHaveChecksumFooter). So the stale byte order describes the header and footer of the default codec's files.

Exposure and likelihood160 words
  • Who is hit: code that decodes or writes headers and footers from the grammar instead of calling CodecUtil. It reads byte-swapped Magic, Version and Checksum values, so it rejects valid files or misreads the version and the stored checksum; or it writes files that Lucene rejects with CorruptIndexException ("codec header mismatch", "codec footer mismatch").
  • Who is not: every reader and writer that uses CodecUtil (writeHeader, checkHeader, writeFooter, checkFooter, retrieveChecksum), so every application on the default codec. No runtime setting is involved.
  • Scale: documentation only, but it describes the header and footer of every default-codec file, and one file is enough to see it. Every release from 9.0.0 to 10.6.0 and main.
  • Why it is Low: CodecUtil is @lucene.experimental (CodecUtil.java:41); the documented magic value exposes the misreading on the first file; the big-endian helper javadocs on the same class page point to the answer. No report since 9.0.0 surfaced in the searches.

Why it looks unintended

#
  • The grammar says Magic is written by DataOutput#writeInt and "is always" 0x3fd76c17, but writeInt writes the low byte first, which gives 0x176cd73f.
  • The links were right when written (2012, 2014); LUCENE-9047 moved the calls to writeBEInt in 2021 and left the links.
  • Lucene's tests follow the code: they read every file's header magic and footer big-endian.
The full argument245 words
  • The links were right when written and nobody chose to keep them. The header grammar dates from 46085655dc7 (LUCENE-2946, Robert Muir, 2012-04-27), the footer grammar from c189d0fb74d (LUCENE-2446, Robert Muir, 2014-04-01), when DataOutput#writeInt / #writeLong were big-endian and CodecUtil called them directly, so the links gave the right byte order. (The footer's Checksum was first labelled Uint32; d8b4128eb5c, Robert Muir, 2014-04-22, "fix file format typo", made it Uint64.) b84e0c272b6 (LUCENE-9047, PR #107, Ignacio Vera, 2021-05-03) replaced out.writeInt(CODEC_MAGIC) and the other calls with writeBEInt and left the links. No comment on #107 or #10089 mentions the header or footer grammar. The one documentation remark, Adrien Grand's review comment on CodecUtil.java in #107 (2021-04-27, "Maybe say explicitly on these methods that they write in big-endian order?"), was about the new helpers, whose "big endian order" javadocs it led to.
  • Maintainers fix stale byte-order wording when they see it: f3c3b90e352 (Uwe Schindler, 2021-09-19, "LUCENE-9047: fix typo in javadocs (still referred to big endian)") and 321d274b799 (LUCENE-10148, Robert Muir, 2021-10-05) corrected DataOutput's and DataInput's own text; neither touched CodecUtil.
  • Tests: TestAllFilesHaveCodecHeader.java:86 checks every file's header magic with CodecUtil.readBEInt; TestAllFilesHaveChecksumFooter.java:79 checks every footer with CodecUtil.checksumEntireFile, which reads it big-endian (CodecUtil.java:657, :434, :584); TestCodecUtil.java:190-192 hand-writes a footer with writeBEInt / writeBELong. No test asserts the documented order.
  • Migration note: lucene/MIGRATE.md:1278-1282 says only that writeShort(), writeInt() and writeLong() "now encode with little-endian byte order", with no exception for headers and footers.
The devil's-advocate check172 words

Strongest case: the big-endian bytes are deliberate. In PR #107 Ignacio Vera wrote "all headers / footers will be written using BE order", and Robert Muir replied "I think its fine that segments_N and codec headers just stay bigendian" (2021-04-28). CodecUtil is @lucene.experimental; in LUCENE-9893 (#10932) Robert Muir called it "a utility class, either you use it or you dont" and Adrien Grand pointed to CodecReader#checkIntegrity(), which uses CodecUtil "as an implementation detail for the default codec". And the helpers' javadocs on the same page say big-endian. On that reading these grammars describe an experimental implementation API, not a promised, stable specification of the file format.

Why it fails: that defends the bytes, which nobody proposes to change, not the five links. The grammar is the only per-field description of the format, and it names a method whose contract says little-endian. @lucene.experimental lets the format change; it does not excuse a wrong description of the current one. The helper javadocs reduce the harm; they do not make the grammar right.

Suggested fix

#

Recommended Link the big-endian helpers and say big-endian (recommended)

Javadoc only: in the five grammar lines, link CodecUtil#writeBEInt / #writeBELong instead of DataOutput#writeInt / #writeLong, and say big-endian. No code, format or caller changes.

All options and trade-offs3 options · 586 words

Option A is the fix. Option B is listed only in case a reviewer prefers a smaller diff; option C widens the same change to the segments_N grammar. Making the bytes little-endian is not an option: it would change every file's on-disk format, and LUCENE-9047 kept headers and footers big-endian on purpose.

Downstream note

#

Tools outside Lucene that parse or write codec headers and footers (inspectors, recovery tools, reimplementations) should treat these fields as big-endian, as CodecUtil.readBEInt / writeBEInt do, not as the javadoc's DataOutput#writeInt link says.

How it was found

#

A proof-obligation audit of CodecUtil's contract (semi-formal) checked the CodecHeader and CodecFooter javadoc grammars against the bytes writeHeader and writeFooter write. The obligation (decoding with the linked methods returns the written values) fails for Magic, Version and Checksum; a public-API JUnit test on main confirmed it.

The method in full112 words

The audit took each field of the two grammars and the method its link names, and checked that decoding with that method's inverse returns what CodecUtil wrote. For CodecName (writeString) and for AlgorithmID (always 0) it holds; for Magic, Version and Checksum it fails, because the linked DataOutput#writeInt / #writeLong are little-endian (DataOutput.java:68, :218) while writeHeader, writeFooter and writeCRC use writeBEInt / writeBELong (CodecUtil.java:84, :86, :411-412, :686). An executable JUnit test on main f794ff5a505c witnessed it (decoded as documented: Magic 0x176cd73f, Version 16777216, footer Magic 0xe89328c0, Checksum 0x62233eeb00000000), and a control that decodes with readBEInt / readBELong passed.

LFV-1439, snapshot of 2026-11-10

Registry title
CodecUtil's codec header and footer javadoc gives Magic, Version, AlgorithmID and Checksum as the little-endian DataOutput#writeInt/#writeLong, but CodecUtil writes these fields big-endian, so a header or footer read or written as documented comes out byte-swapped or is rejected (documentation defect; the writer and reader agree)
Area
codecs / CodecUtil (codec header and footer javadoc grammar vs the written bytes)
Priority
Low, rank 1370: Documentation only: the CodecUtil header and footer grammar describes little-endian writes, but the code writes big-endian, and every core file format that refers to this grammar inherits the error, in every release since 9.0.0. Lucene's writer and reader agree, and a re-implementer sees the mismatch at once in the first file's magic value.
Impact class
minor
Impact note
Documentation only: Lucene's writer and its checkHeader/checkFooter readers agree, so indexing, search, CheckIndex and checksum validation are unaffected in every configuration; the people misled are those who parse, inspect or hand-write codec headers and footers from CodecUtil's javadoc (CodecUtil is @lucene.experimental; the IndexHeader grammar and 11 core file-format javadocs, among them SegmentInfos, the .si, .fnm, .nvm, .liv, compound, term-vectors, block-tree and postings formats, defer their Header and Footer elements to these grammars [read]), and for them the header and footer of every file CodecUtil writes decode byte-swapped (Magic 0x176cd73f instead of 0x3fd76c17, Version 1 as 16777216) [exec], while a header or footer written as documented is rejected with CorruptIndexException 'codec header mismatch' / 'codec footer mismatch' [exec]; no scale or special setting is needed, and the documented magic value exposes the misreading on the first file.
Summary
You write a file with CodecUtil.writeHeader(out, "Foo", 1) and CodecUtil.writeFooter(out) and decode it as the CodecHeader and CodecFooter grammars in CodecUtil's javadoc say: they link Magic, Version and AlgorithmID to DataOutput#writeInt and Checksum to DataOutput#writeLong, which are little-endian since 9.0, so you read them with readInt/readLong and expect Magic 0x3fd76c17 (the javadoc says 'It is always' CODEC_MAGIC), Version 1, footer Magic 0xc02893e8 and the file's CRC. Instead you get Magic 0x176cd73f, Version 16777216, footer Magic 0xe89328c0 and Checksum 0x62233eeb00000000, each byte-swapped, because CodecUtil writes these fields big-endian (writeBEInt/writeBELong); the other way round, a header or footer written with writeInt/writeLong as documented is rejected by checkHeader/checkFooter with CorruptIndexException. Lucene's own reader matches its writer, so indexing and search are unaffected; only the five javadoc links, left unchanged when LUCENE-9047 made DataOutput little-endian in 9.0.0, are wrong.
Introduced
b84e0c272b6e1beb29e2a22d16d1d8a2bd05a731 'LUCENE-9047: Directory API is now little endian' (apache/lucene#107, issue #10089, author Ignacio Vera (iverase), merged 2021-05-03): it made DataOutput#writeInt/#writeLong and DataInput#readInt/#readLong little-endian and switched CodecUtil's header, footer and CRC calls to the new big-endian helpers writeBEInt/writeBELong/readBEInt/readBELong, but left the five grammar links (CodecUtil.java:60, :64, :399, :401, :403 on main) pointing at DataOutput#writeInt/#writeLong [read: commit diff and author date in the full-history clone; exec: release bracket, 8.8.2 and 8.11.4 pass, 9.0.0 fails]. The grammar text is older and was right when written: the header grammar from 46085655dc7 (LUCENE-2946, Robert Muir, 2012-04-27), the footer grammar from c189d0fb74d (LUCENE-2446, Robert Muir, 2014-04-01), when DataOutput#writeInt/#writeLong were big-endian and CodecUtil called them directly. The follow-ups f3c3b90e352 (Uwe Schindler, 2021-09-19) and 321d274b799 (LUCENE-10148, Robert Muir, 2021-10-05) made the linked DataOutput/DataInput javadoc say little-endian and did not touch CodecUtil. No later commit changed the five lines. The commit-level bracket (b84e0c272b6^ against b84e0c272b6) was not executed (both are 2021 snapshots that need the 2021 toolchain) (2021-05-03 (author date of b84e0c272b6, 2021-05-03T07:49:56+02:00); the grammar lines date from 2012-04-27 (header) and 2014-04-01 (footer), when they were correct)
