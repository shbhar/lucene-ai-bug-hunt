Highlighter returns no fragment for a phrase with a hole and slop Integer.MAX_VALUE

The classic Highlighter rewrites a phrase as a span query with slop + holes as a plain int. For "quick the fox"~2147483647 with the stop word removed, 2147483647 + 1 wraps to -2147483648, the span query matches nothing, and the hit gets no highlight (getBestFragment returns null).

The bug in 30 seconds

#

WeightedSpanTermExtractor rewrites a phrase as new SpanNearQuery(clauses, slop + positionGaps, inorder), a plain int sum (WeightedSpanTermExtractor.java:161-162; MultiPhraseQuery :232). It is exact only while slop is at most Integer.MAX_VALUE minus the holes. Above that it wraps to about Integer.MIN_VALUE, and since a span match must be at most slop wide, none is found.

Background: slop, holes and how the Highlighter finds words

#
  1. A phrase's slop is how far its words may move and still match: "quick fox"~1 matches quick brown fox. Slop Integer.MAX_VALUE is the usual way to say "any distance"; Lucene's own core tests use it.
  2. A hole is a position with no word. An analyzer that removes stop words keeps their positions, so "quick the fox" becomes quick at position 0 and fox at position 2, printed "quick ? fox".
  3. The classic Highlighter with QueryScorer does not ask the search what matched. It rewrites the phrase as a span query, runs it on the text and marks the words of each match, adding one to the slop per hole so the hole fits.

The bug, step by step

#
  1. You index the quick brown fox jumps with an analyzer that removes stop words. A user types "quick the fox"~3000000000; the classic QueryParser makes it "quick ? fox"~2147483647 (the removed "the" leaves a hole, and the parser caps the huge slop at Integer.MAX_VALUE), and the search finds the document.
  2. You highlight the hit with Highlighter and QueryScorer and expect the <B>quick</B> brown <B>fox</B> jumps, which you get with slop 2147483646 or with the same phrase without the hole.
  3. To find the words, the Highlighter rewrites the phrase as a span query with slop + holes = 2147483647 + 1. In int arithmetic that is -2147483648.
  4. A span match may be at most slop positions wide, so with -2147483648 none qualifies: getBestFragment returns null, with no error, assertions on or off. The UnifiedHighlighter with weight matches off returns the quick brown fox jumps with nothing marked.

Who is affected

#

Applications that highlight with the classic Highlighter and QueryScorer, or with the UnifiedHighlighter with weight matches, multi-term or passage-relevancy handling off and strict phrases on, for a phrase with a hole and slop + holes > Integer.MAX_VALUE. Search hits stay correct; ordinary slops and the default UnifiedHighlighter are fine.

Mechanism, terms and numbers624 words

The classic Highlighter with its span-aware QueryScorer finds the words to mark by rewriting each phrase query as a SpanNearQuery and running it on the document's text. A phrase can have holes, positions with no word, most often a stop word that the analyzer removed; the rewrite widens the slop by one per hole, slop + positionGaps, as a plain int sum. When the slop is Integer.MAX_VALUE, the usual way to say "any distance" and what the classic QueryParser makes of any huge typed ~N, one hole is enough: the sum wraps to -2147483648, the span query matches nothing, and the Highlighter returns null for a document the query matched. MultiPhraseQuery has the same sum, and the UnifiedHighlighter reaches it when weight matches are off while strict phrase highlighting stays on (the default). Search hits, counts and scores are correct; only highlighting is lost, silently. Present since 2.4.0 (2008); a two-line saturating fix passes the whole highlighter test suite.

Terms

#
  • Classic Highlighter: org.apache.lucene.search.highlight.Highlighter. With a QueryScorer it "converts appropriate Querys to SpanQuerys and attempts to score only those terms that participated in generating the 'hit'" (QueryScorer.java:33-37). The conversion is WeightedSpanTermExtractor.extract.
  • Position hole (positionGaps): the number of positions between the phrase's first and last term that hold no term: positions[last] - positions[0] - positions.length + 1 for a PhraseQuery (WeightedSpanTermExtractor.java:150-156), the empty positions up to the last one for a MultiPhraseQuery (:215-224).
  • Span slop: a SpanNearQuery accepts a match only if its width is at most the slop: matchWidth <= allowedSlop (ordered, NearSpansOrdered.java:67, :89) or (maxEndPosition - start - totalSpanLength) <= allowedSlop (unordered, NearSpansUnordered.java:84). Its constructor stores any slop (SpanNearQuery.java:119-131).

The bug

#
  1. The PhraseQuery branch builds new SpanNearQuery(clauses, phraseQuery.getSlop() + positionGaps, inorder) (WeightedSpanTermExtractor.java:161-162); the MultiPhraseQuery branch new SpanNearQuery(clauses, slop + positionGaps, inorder) (:232). Both are plain int additions.
  2. For slop >= 0 and positionGaps >= 0 the sum is exact and non-negative when slop <= Integer.MAX_VALUE - positionGaps (proved with Z3, checked with cvc5), and above that it wraps to about Integer.MIN_VALUE (the converse, checked separately with cvc5 and Z3).
  3. A wrap needs a slop of at least 1, so the conversion is not in order and the unordered check decides. For the reproduced phrase the width is 4 - 1 - 2 = 1 (one unmatched position, "brown"), and 1 <= -2147483648 is false, so no span matches, no weighted term is extracted, and getBestFragment returns null, its documented value for "no terms found" (Highlighter.java:71, :92). An independent check captured the converted query: spanNear([body:quick, body:fox], -2147483648, false).
  4. The UnifiedHighlighter's PhraseHelper builds an anonymous subclass of the same extractor ("WSTE will convert to an equivalent SpanQuery", PhraseHelper.java:106-109). It is used when weight matches are not applied and strict phrase highlighting is on (UnifiedHighlighter.java:1219-1236: no PhraseHelper with weight matches, :1221-1223, or with strict phrases off, :1225-1235); it then returns the passage with nothing marked. With withHighlightPhrasesStrictly(false) the passage is marked correctly (executed).

Exposure and likelihood331 words
  • Who is hit. The classic Highlighter with QueryScorer, its span-aware scorer, which LUCENE-1685 made the default in 2.9.0. The UnifiedHighlighter when weight matches are not applied and strict phrase highlighting stays on (the default): withWeightMatches(false), and also withHandleMultiTermQuery(false) or withPassageRelevancyOverSpeed(false), because weight matches are applied only when multi-term handling, strict phrases, passage relevancy and weight matches are all on (UnifiedHighlighter.java:518-528; all on by default, :108-111). All three settings were executed on main; withWeightMatches(false) also on 10.5.2 and 10.0.0. withHighlightPhrasesStrictly(false) uses no PhraseHelper (:1225-1235) and highlights correctly (executed).
  • Which queries. A PhraseQuery or MultiPhraseQuery with at least one hole and a slop above Integer.MAX_VALUE minus the number of holes (slop + holes > Integer.MAX_VALUE). In practice:
    • slop Integer.MAX_VALUE as "any distance": Lucene's core tests use it (TestPhraseQuery.java:339, TestSimpleSearchEquivalence.java:173), a 2004 java-user@ answer recommends "red fox"~2147483647, and QueryParser.setPhraseSlop(Integer.MAX_VALUE) applies it to every phrase (executed);
    • a huge typed ~N: the classic parser reads it with (int) Float.parseFloat (QueryParserBase.java:802), so any typed slop from 2147483584 up becomes Integer.MAX_VALUE.
  • Where holes come from. Analyzers that remove stop words keep their positions (EnglishAnalyzer() uses ENGLISH_STOP_WORDS_SET; the no-argument StandardAnalyzer removes none, StandardAnalyzer.java:51-53), and phrases built with explicit positions.
  • Effect. Silent and deterministic: a hit with no snippet (null) or an unmarked passage. One document is enough; no index size or setting matters. Not affected: hits, counts and scores; ordinary slops, even in the millions, on phrases with ordinary position gaps (a phrase built with very far apart explicit positions has a huge gap count, so a small slop could cross the same bound; not run); the default UnifiedHighlighter.
  • Not assessed. The FastVectorHighlighter, the MatchHighlighter, and UnifiedHighlighter offset sources other than re-analysis of the stored text.
  • Why nobody noticed. For one hole the cliff is one value wide (slop 2147483646 works), and nobody has reported it in the 17 years since it reached the default scorer.

Why it is a bug, not intended

#
  • PhraseQuery and MultiPhraseQuery accept any slop of 0 or more; Lucene's core tests use slop Integer.MAX_VALUE as "any distance", and the classic QueryParser produces it from user text.
  • LUCENE-5503 (5.4.0) fixed the same symptom in this converter as a bug: "a slop that is too low (no highlight)".
  • The cliff is arbitrary: slop 2147483646 is highlighted, 2147483647 is not.
The full argument164 words
  • The inputs are legal. PhraseQuery rejects only slop < 0 (PhraseQuery.java:173-175), MultiPhraseQuery.Builder.setSlop only s < 0 (MultiPhraseQuery.java:95-102). The getSlop javadoc defines slop as "the maximum edit distance for a document to match", with no bound (PhraseQuery.java:268-283); so does QueryParserBase.setPhraseSlop (:205-210).
  • Precedent in this converter. CHANGES.txt, 5.4.0 Bug Fixes: "LUCENE-5503: When Highlighter's WeightedSpanTermExtractor converts a PhraseQuery to an equivalent SpanQuery, it would sometimes use a slop that is too low (no highlight) or determine inOrder wrong." (lucene/CHANGES.txt:10042-10045). That commit (c5b49baa592, #6566) wrote today's getSlop() + positionGaps; its thread never mentions overflow.
  • Tests state the goal. TestHighlighterPhrase.testStopWords ("shows the need to sum the increments in WeightedSpanTermExtractor", :273-274) and testInOrderWithStopWords (:308) assert that a matching phrase with stop-word holes is highlighted.
  • The terms are found. The query matches the document, and the default UnifiedHighlighter marks the same text; only the converted slop is wrong. The classic Highlighter is not deprecated.
The devil's-advocate check230 words

The strongest case for "intended": slop Integer.MAX_VALUE is a degenerate sentinel; huge slops are known to be costly for highlighting, and in LUCENE-5182 (#6246, the FastVectorHighlighter's run time at high slop) @rmuir suggested "maybe just a Math.min and a default of Integer.MAX_VALUE. Sure its still trappy but at least its an improvement"; QueryScorer only "attempts" to score the terms that produced the hit, and getBestFragment documents null for "no terms found".

Why it fails: that thread is about run time in another highlighter; the Math.min there was a suggested user-configurable cap (not adopted: the committed fix terminates phrase searches early once a maximum phrase window is exceeded), it bounds work, and nothing in it makes dropping highlights intended. Accepting a slop through the public API does not by itself promise a fragment from every highlighter path; the case rests on the combination: nothing documents an upper bound on slop, core tests use Integer.MAX_VALUE as "any distance", Lucene's own parser produces the value, the converter's purpose is an equivalent span query, here the terms are found, nothing gets slower, and the answer flips at an arbitrary point (slop 2147483646 works, 2147483647 does not); LUCENE-5503 treated "converted slop too low, no highlight" as a bug. The independent reproducer, the cross-model review (it rated the intended argument's strength "weak"), the devil's advocate, the adjudication and the audit all concluded it is not intended.

Suggested fix

#

Recommended Saturate slop + positionGaps at Integer.MAX_VALUE (two lines)

Saturate both sums: MathUtil.unsignedMin(slop + positionGaps, Integer.MAX_VALUE) in WeightedSpanTermExtractor. Both operands are 0 or more, so a wrapped sum becomes Integer.MAX_VALUE and every other slop stays as it is. The repro then passes, and so does the whole highlighter test task (727 tests), assertions on and off.

// PhraseQuery branch (WeightedSpanTermExtractor.java:161-162)
// both are >= 0: saturate at Integer.MAX_VALUE instead of wrapping to a negative slop
int slop = MathUtil.unsignedMin(phraseQuery.getSlop() + positionGaps, Integer.MAX_VALUE);
SpanNearQuery sp = new SpanNearQuery(clauses, slop, inorder);

// MultiPhraseQuery branch (:232)
SpanNearQuery sp =
    new SpanNearQuery(
        clauses, MathUtil.unsignedMin(slop + positionGaps, Integer.MAX_VALUE), inorder);

Saturate slop + positionGaps at Integer.MAX_VALUE (two lines) (validated by the checks) (recommended)

#

Both operands are >= 0, so a wrapped sum is negative as a signed int and above Integer.MAX_VALUE as an unsigned one; MathUtil.unsignedMin(sum, Integer.MAX_VALUE) (MathUtil.java:196-199) returns the exact sum when it fits and Integer.MAX_VALUE when it wrapped. Core uses the same idiom (MaxScoreBulkScorer.java:424: MathUtil.unsignedMin(Integer.MAX_VALUE, windowMin + minWindowSize); BitSetDocIdStream.java:34). Z3 proves the result is at least the phrase's own slop and never negative.

// PhraseQuery branch (WeightedSpanTermExtractor.java:161-162)
// both are >= 0: saturate at Integer.MAX_VALUE instead of wrapping to a negative slop
int slop = MathUtil.unsignedMin(phraseQuery.getSlop() + positionGaps, Integer.MAX_VALUE);
SpanNearQuery sp = new SpanNearQuery(clauses, slop, inorder);

// MultiPhraseQuery branch (:232)
SpanNearQuery sp =
    new SpanNearQuery(
        clauses, MathUtil.unsignedMin(slop + positionGaps, Integer.MAX_VALUE), inorder);

Trade-offs

  • None found for valid inputs: every sum that fits is unchanged, and a saturated slop means "any distance", which is what such a slop asks for. One unsigned compare per converted phrase.
  • A PR could add the paste-ready test (or a shorter one) next to TestHighlighterPhrase.testStopWords, and apply the same line to sandbox PayloadSpanUtil.java:152, which has the same sum (not run).

  • Scratch worktree at a9779ef3c193, gradle: the paste-ready test fails 3 of 5 on stock main, assertions on and off, and 30 of 50 with 10 random seeds per method; with the patch the whole :lucene:highlighter:test task passes, 35 classes, 727 tests, 0 failures, assertions on and off (counting the 5 paste-ready tests), and 50 of 50 with 10 random seeds per method.
  • ecjLintMain, ecjLintTest and checkGoogleJavaFormat for the module pass.
  • The UnifiedHighlighter settings probe passes 4 of 4 with the patch; the hunt's equivalent patch passed every earlier repro and the highlighter, facet and grouping suites plus two core merge-policy test classes (1,097 tests, with five other fixes).

(int) Math.min((long) slop + positionGaps, Integer.MAX_VALUE) at both sites: the same values, and perhaps easier to read.

Trade-offs

Reject a negative slop in SpanNearQuery (separate hardening)

Trade-offs

Downstream note

#

Search servers that pass user-typed ~N through the classic QueryParser to the classic Highlighter, or that turn off the UnifiedHighlighter's weight matches with strict phrases on, inherit the missing highlights.

How it was found

#

Formal. A scan of the compiled highlighter code for int additions of two variables passed on as a slop flagged the two sums. Z3 then found a wrapping input, proved the exact safe bound and proved that the saturating fix is never stricter than the phrase (cvc5 agrees); a public-API JUnit on the stock jars confirmed it.

The method in full147 words
  • Signal. A hunt unit on int overflow at scale ran a bytecode inventory of int arithmetic (a JDK 25 java.lang.classfile abstract interpreter flagging iadd of two non-constant ints passed as an argument). Its rows for WeightedSpanTermExtractor.extract at lines 162 and 232 were reviewed while triaging highlighter parameters that users set to sentinel values.
  • Proof obligations. Z3 bit-vector checks: WS1 gave a counterexample (the sum wraps negative); WS1s proved the sum is exact and non-negative when slop <= Integer.MAX_VALUE - positionGaps (the converse, that it wraps above, was checked separately with cvc5 and Z3); WS2 proved that MathUtil.unsignedMin(slop + positionGaps, Integer.MAX_VALUE) is never below the phrase's slop and never negative. cvc5 agrees on all three.
  • Witness. A 3-test public-API JUnit (MemoryIndex, explicit positions) failed 2 of 3 on main with assertions on and off, and on 10.5.2 and 9.12.3; the slop Integer.MAX_VALUE - 1 control passed.

Impact note
Applications on any release from 2.4.0 through 10.5.2 or main that highlight with the original Highlighter and the default QueryScorer (or with the UnifiedHighlighter with weight matches turned off, through PhraseHelper) a PhraseQuery or MultiPhraseQuery whose slop is above Integer.MAX_VALUE minus the phrase's number of position holes, in practice slop Integer.MAX_VALUE used as 'any distance' or a huge user-typed ~N that the classic QueryParser saturates to it, on a phrase with a removed stop word or an explicit gap, get no highlight for a document the query matches (getBestFragment returns null; the UnifiedHighlighter path returns the passage unmarked); search hits, counts and scores are correct, there is no exception with -ea or -da, no index size or setting is needed, ordinary slops are safe, and the default UnifiedHighlighter (weight matches on) is not affected.
Summary
You analyse 'the quick brown fox jumps' with a stop-word analyzer, search for the phrase "quick the fox" with slop Integer.MAX_VALUE (for example from the user text "quick the fox"~3000000000, which the classic QueryParser turns into "quick ? fox"~2147483647; the query matches), and highlight the hit with Highlighter and QueryScorer, expecting 'the <B>quick</B> brown <B>fox</B> jumps', which slop Integer.MAX_VALUE - 1 or the same phrase without the hole gives. Instead getBestFragment returns null, with no error: WeightedSpanTermExtractor rewrites the phrase as new SpanNearQuery(clauses, slop + positionGaps, inorder) with a plain int sum, the removed stop word counts as one position gap, the sum wraps to -2147483648, and a span query with that slop accepts no match, so no term is marked. MultiPhraseQuery has the same sum, and the UnifiedHighlighter with weight matches turned off reaches it through PhraseHelper and returns the passage with no highlight.
