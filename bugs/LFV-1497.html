With LogDocMergePolicy, the megabyte limit of setMaxCFSSegmentSizeMB is compared with the merged segment's document count, so a segment larger than the limit is still written as a compound file (file layout only; since 4.0.0)

With LogDocMergePolicy, the megabyte limit of setMaxCFSSegmentSizeMB is compared with a merged segment's document count, not its size in bytes: under a 1 MB limit, a merged segment of 2 documents and 2,098,992 bytes is still a compound file. Only the file layout is affected, not search results.

The finding in 30 seconds

#

The limit is stored in bytes: 1 MB is 1,048,576. When a merge finishes, Lucene compares it with the merge policy's own size of the new segment. LogDocMergePolicy measures a segment in documents, so the check is 2 > 1,048,576, which is false, and the segment is packed into a compound file whatever its size in bytes.

Background: three pieces

#
  1. A segment is a set of files. Lucene can pack them into one compound file (.cfs, plus a small .cfe) to keep the number of files down. Packing copies the segment's files once more, so large segments are often left as separate files.
  2. setMaxCFSSegmentSizeMB(N) on the codec's CompoundFormat says: a merged segment larger than N megabytes stays as separate files. The default is no limit. From 4.4.0 to 10.x the same setter is on MergePolicy; in 4.0.0 to 4.3.1 it is on LogMergePolicy.
  3. Every merge policy has its own measure of a segment's size. The default TieredMergePolicy and LogByteSizeMergePolicy measure bytes. LogDocMergePolicy measures the number of documents.

The finding, step by step

#
  1. Use LogDocMergePolicy and tell Lucene not to pack large merged segments into a compound file: codec.compoundFormat().setMaxCFSSegmentSizeMB(1). Index two documents with 1 MiB of binary doc values each, one segment per document, and call forceMerge(1).
  2. The merged segment has 2 documents and 2,098,992 bytes, about twice the limit. You expect separate files, as the setter's javadoc says and as TieredMergePolicy and LogByteSizeMergePolicy do with the same segment.
  3. Instead it is written as a compound file (_2.cfs, _2.cfe, _2.si): exactly what you get with no limit set.
  4. Why: Lucene stores the limit as 1,048,576 bytes and compares it with the merge policy's size of the segment. For LogDocMergePolicy that size is the document count, so the check is 2 > 1,048,576: false. A limit of N MB acts as a limit of N x 1,048,576 documents.
  5. No search result is wrong and nothing is lost: searches, stored data and the index are fine. The cost is the layout you asked not to have, and one extra copy of the merged segment into its .cfs file at merge time.

Who is affected

#

Only applications that use LogDocMergePolicy, which is not the default, and also set a finite maximum. For them the limit is not applied in bytes: merged segments above it are still packed into a compound file, with one extra copy of the segment at merge time. No result is wrong and nothing is lost. Rare; in every release since 4.0.0.

Mechanism, terms and numbers793 words

CompoundFormat#setMaxCFSSegmentSizeMB (on the 11.0 branch and main; MergePolicy#setMaxCFSSegmentSizeMB from 4.4.0 to 10.x, LogMergePolicy#setMaxCFSSegmentSizeMB in 4.0.0 to 4.3.1) promises that a merged segment larger than the given number of megabytes is left as separate files and not packed into a compound (.cfs) file. The setter stores the limit in bytes (CompoundFormat.java:140 on main 781025d6fe32), and CompoundFormat.useCompoundFile compares it with the size its callers pass (:170), which is the merge policy's own size of the segment. LogDocMergePolicy measures a segment in documents (LogDocMergePolicy.java:40-43), so under that policy a document count is compared with a byte count: a limit of N MB acts as a limit of N x 1,048,576 documents, and this check never looks at the segment's size in bytes. In the repro, a 1 MB limit and a merged segment of 2 documents and 2,098,992 bytes give a compound file, the same files as with no limit at all, while TieredMergePolicy and LogByteSizeMergePolicy leave the same segment as separate files. This is a file-layout effect only: no search result is wrong, nothing is lost and Lucene throws no exception in the repro; the cost is one extra copy of the merged segment into its .cfs file at merge time. It needs LogDocMergePolicy, which is not the default merge policy, and an explicitly set limit; the same comparison is made when LogDocMergePolicy is wrapped in a FilterMergePolicy. The comparison is as old as the setting (LUCENE-4323, 89f9beb7384, first released in 4.0.0 in 2012); #15295 moved it to CompoundFormat for 11.0 unchanged. Every release from 4.0.0 to 10.6.0, the 11.0 branch and main are affected; it is not new in 11.0. Passing the segment's size in bytes to the check (+20/-5 lines) fixes it and was validated with the closest upstream suites and the index and codecs tests of core.

The code (main 781025d6fe32)

#
  1. The limit is stored in bytes. setMaxCFSSegmentSizeMB(double v) (CompoundFormat.java:127-142) does v *= 1024 * 1024; // Convert MB to bytes (:140) and stores the result in maxCFSSegmentSize (:141). The default is Long.MAX_VALUE, no limit (:44-45).
  2. The check. useCompoundFile(long mergedInfoSize, MergePolicy mergePolicy) (:163-180) returns false when compound files are switched off, then does if (mergedInfoSize > maxCFSSegmentSize) return false; (:170), then applies one of two thresholds: for a document-count policy mergedInfoSize <= cfsThresholdDocSize (65,536 documents by default), for the others mergedInfoSize <= cfsThresholdByteSize (64 MB by default) (:175-179). The two thresholds are split by the policy's measure. The maximum is not.
  3. What the callers pass. The only three callers pass the merge policy's own size as the first argument: IndexWriter.java:3619-3629 (addIndexesReaderMerge, the merge behind addIndexes(CodecReader...)), IndexWriter.java:5558-5565 (packageMergedSegment, every merge that writes a segment; the call there reads .useCompoundFile(mergePolicy.size(info, this), mergePolicy), :5564) and MergePolicy.java:898-906 (isMerged).
  4. The policy's size is a document count. LogDocMergePolicy.size returns sizeDocs(info, mergeContext) (LogDocMergePolicy.java:40-43), and getSizeUnit() returns SizeUnit.DOCS (:45-48). The class javadoc: "measures size of a segment as the number of documents" (:21-24). By default that count is the segment's maxDoc less the deleted documents a merge would drop (LogMergePolicy.java:156-164); the repro has no deletions.
  5. With the repro's numbers. mergedInfoSize is 2 (documents) and maxCFSSegmentSize is 1,048,576 (bytes). 2 > 1048576 is false, so the maximum does not object. Then 2 <= 65536 is true: compound. The check never looks at the 2,098,992 bytes.
  6. The byte-size policies compare bytes with bytes. MergePolicy.size is the segment's size in bytes, pro-rated by the deleted documents a merge would drop (MergePolicy.java:864-876). TieredMergePolicy uses it as it is, and LogByteSizeMergePolicy uses it by default (LogMergePolicy.java:166-175). The repro has no deletions, so there it is the plain byte size.

Up to 10.6.0 the same two lines are in MergePolicy.useCompoundFile (10.6.0: MergePolicy.java:743-746, before the noCFSRatio rule), and in 4.0.0 to 4.3.1 in LogMergePolicy.useCompoundFile.

Exposure and likelihood472 words
  • Who. An application that chose LogDocMergePolicy and set a finite maximum compound-file segment size. Both are opt-in: the default merge policy is TieredMergePolicy and the default maximum is no limit.
  • Also when the policy is wrapped. FilterMergePolicy passes size() through to the policy it wraps (FilterMergePolicy.java:78-81), and none of the in-tree wrappers overrides it (OneMergeWrappingMergePolicy, UpgradeIndexMergePolicy, BPReorderingMergePolicy, MergeOnFlushMergePolicy). Run as an evidence probe: the repro's scenario with OneMergeWrappingMergePolicy around LogDocMergePolicy gives the same compound segment of 2,098,992 bytes on main and on the 11.0 branch, and separate files with the fix. A custom policy whose size() counts documents is in the same position (by reading, not run).
  • No scale needed. Two one-document segments are enough.
  • What it costs. Merged segments above the limit are packed into a compound file: the layout the setting was meant to prevent, one extra copy of the segment's files into the .cfs file at merge time, and the disk space for both forms until the separate files are deleted (IndexWriter.java:5567-5617, read). No timing was measured.
  • What it does not cost. No wrong search result and no lost data; Lucene throws no exception in the repro, and both layouts are valid indexes.
  • Reach on 11.0 and main. For a document-count policy the document threshold is checked after the maximum: a merged segment is compound only up to 65,536 documents by default. So the affected segments are merged segments of at most 65,536 documents that are larger than the limit in bytes: documents of more than limit / 65,536 bytes on average (8 KB at the 512 MB of the MIGRATE.md example), and more segments when setCfsThresholdDocSize is raised. With the defaults the maximum can change a decision under this policy only when it is set below 65,536 bytes (0.0625 MB).
  • Reach on 4.4.0 to 10.6.0. The maximum is the only absolute cap for merged segments; the other rule, noCFSRatio, is relative to the index (0.1 by default for this policy). For LogDocMergePolicy the maximum works only as a ceiling of N x 1,048,576 documents (about 537 million at 512 MB), never as a limit in bytes. From 2048 MB on it cannot act at all: a segment holds at most 2,147,483,519 documents (IndexWriter.MAX_DOCS), fewer than 2048 x 1,048,576.
  • Newly flushed segments are not involved on 4.4.0 and later: they follow IndexWriterConfig.setUseCompoundFile (DocumentsWriterPerThread.java:643).
  • Likelihood: rare. The two settings together are uncommon, and whoever has them sees only a .cfs file where separate files were asked for. No report of the effect was found.
  • Ways around it today. If a byte limit is needed, use LogByteSizeMergePolicy or TieredMergePolicy, which honour it. Under LogDocMergePolicy on 11.0 and main, the control that works is the document threshold, setCfsThresholdDocSize, which limits by documents and not by bytes.

Why it looks unintended

#
  • The setter's javadoc: megabytes, and "If a merged segment will be larger than this value, it will be left as a non-compound file". No exception for document-count policies.
  • TieredMergePolicy and LogByteSizeMergePolicy leave the same merged segment as separate files (2,098,445 bytes).
  • The limit was added "in absolute byte size terms" (LUCENE-4323). 1 MB = 1,048,576 documents is documented nowhere.
The full argument385 words
  • The setter's contract. CompoundFormat.java:127-135: "Sets the maximum size limit for compound file segments in megabytes. If a merged segment will be larger than this value, it will be left as a non-compound file even if compound files are enabled." The getter (:117-125): "Segments larger than this size will not use compound files even if otherwise eligible." Neither has an exception for document-count policies, and the setter converts megabytes to bytes itself (:140).
  • The settings beside it name their policy kind. setCfsThresholdDocSize: "the document count threshold for using compound files with LogDocMergePolicy" (:59-67). setCfsThresholdByteSize: "with merge policies other than LogDocMergePolicy" (:69-78). The maximum has one megabyte setter and no such sentence.
  • The migration guide. MIGRATE.md (:401-427) shows cfs.setMaxCFSSegmentSizeMB(512); as the replacement for the merge policy's setter, with no exception, in the section that introduces the 65,536-document threshold for LogDocMergePolicy (:389-399).
  • The original intent. LUCENE-4323 (#5390), which added the limit: "The meaning of "small" here is in absolute byte size terms, not as a percentage of the overall index." Its CHANGES.txt entry: "Added support for an absolute maximum CFS segment size (in MiB) to LogMergePolicy and TieredMergePolicy." LogMergePolicy is the parent of LogDocMergePolicy.
  • The releases say the same. 10.6.0, MergePolicy#setMaxCFSSegmentSizeMB: "If a merged segment will be more than this value, leave the segment as non-compound file even if compound file is enabled."
  • The sibling policies do it. With LogByteSizeMergePolicy or TieredMergePolicy the same segment is left as separate files (the probe).
  • The resulting rule is documented nowhere. N MB = N x 1,048,576 documents is not a meaning anyone would write down. Megabyte setters elsewhere in the merge policies mean bytes, and the document-count policy has its own setter in documents (LogByteSizeMergePolicy.setMinMergeMB and setMaxMergeMB against LogDocMergePolicy.setMinMergeDocs).
  • No test asserts today's behaviour. TestCompoundFormat.testMaxCFSSegmentSize is the only upstream test of a finite maximum and uses TieredMergePolicy only. The 2012 commit's testSetters called the megabyte setter on new LogDocMergePolicy() and checked only that the getter returns the value. The test framework sometimes sets a random finite maximum of 0.2 to 2.2 MB and sometimes picks LogDocMergePolicy, and asserts nothing about the result.
  • No "by design" statement. None in LUCENE-4323 (its description and 14 comments) or in the review of #15295.
The devil's-advocate check188 words

The strongest case for "intended": useCompoundFile documents its size argument in the policy's own measure, "document count for DOCS-based policies, bytes for BYTES-based policies" (CompoundFormat.java:157-158). LogDocMergePolicy measures everything in documents by definition. CompoundFormat and MergePolicy are @lucene.experimental. The behaviour is as old as the setting, and no user report was found.

Why it fails: that @param says what the callers pass; it does not say that a megabyte value turns into a document count. The same javadoc lists "If segment size exceeds the maximum CFS segment size, return false" as a step of its own (:152), before the two thresholds, which are split by policy kind while the maximum is not. On 11.0 the comparison cannot even act as a sensible document limit: with the default threshold it can change a decision only below 0.0625 MB. The setter says megabytes, converts to bytes, and the byte-size policies honour it.

What remains: the reach is small, and a maintainer may prefer to document the behaviour or to decide everything on bytes. That is a choice of repair, not a reason to call it intended.

Suggested fix

#

Recommended Compare the maximum with the segment's size in bytes (validated)

Compare the maximum with the segment's size in bytes: a three-argument useCompoundFile takes the byte size, and Lucene's three callers pass sizeInBytes() (+20/-5 lines). Validated: the test passes, the closest suites and the index and codecs tests of core pass, the module's checks are clean. The direction is from epotyom's review comment on #15295.

public boolean useCompoundFile(long mergedInfoSize, MergePolicy mergePolicy) throws IOException {
  return useCompoundFile(mergedInfoSize, mergedInfoSize, mergePolicy);
}

public boolean useCompoundFile(
    long mergedInfoSize, long mergedInfoSizeInBytes, MergePolicy mergePolicy) throws IOException {
  if (this.shouldUseCompoundFile == false) {
    return false;
  }
  if (mergedInfoSizeInBytes > maxCFSSegmentSize) {
    return false;
  }
  // ... the two thresholds, unchanged
}

Compare the maximum with the segment's size in bytes (validated) (recommended)

#

Add useCompoundFile(mergedInfoSize, mergedInfoSizeInBytes, mergePolicy) to CompoundFormat: it checks the maximum against the byte size and keeps the two thresholds as they are. The three callers (IndexWriter.addIndexesReaderMerge, IndexWriter.packageMergedSegment, MergePolicy.isMerged) pass info.sizeInBytes(). The two-argument method delegates with its one size for both. Three files, +20/-5 lines. The excerpt below leaves out the javadoc and the comments.

The idea of using sizeInBytes() here is epotyom's, from their review comment on #15295 (Prior reports).

public boolean useCompoundFile(long mergedInfoSize, MergePolicy mergePolicy) throws IOException {
  return useCompoundFile(mergedInfoSize, mergedInfoSize, mergePolicy);
}

public boolean useCompoundFile(
    long mergedInfoSize, long mergedInfoSizeInBytes, MergePolicy mergePolicy) throws IOException {
  if (this.shouldUseCompoundFile == false) {
    return false;
  }
  if (mergedInfoSizeInBytes > maxCFSSegmentSize) {
    return false;
  }
  // ... the two thresholds, unchanged
}

Trade-offs

  • The two-argument method still compares what it is given (the probe's direct calls give the same answers with the fix). useCompoundFile is new in 11.0 and not released, so a PR could change its signature or drop the two-argument form instead of adding an overload.
  • An override of the two-argument method is no longer consulted. useCompoundFile(long, MergePolicy) is public and not final. With the overload, Lucene's three callers call the three-argument method, so a CompoundFormat subclass that overrides the two-argument one is bypassed at merge time (run: a subclass that prints from such an override prints three decisions on the stock tree and none with the fix). No in-tree subclass overrides it. This is the reason to change the signature and not to add an overload.
  • Behaviour change for the affected setups. With LogDocMergePolicy and a finite maximum, merged segments above the limit stop being compound. isMerged then reports an existing compound segment above the limit as not merged, so a later forceMerge(1) can rewrite it once. Run with the limit set on the config's default codec (the MIGRATE.md route): the compound segment is rewritten once as separate files, and further forceMerge(1) calls change nothing; on the stock tree nothing is rewritten. With the limit on a private codec instance, as in the repro, an existing segment is not rewritten, with or without the fix, because isMerged asks the codec of the segment and a segment read back from the directory has the shared codec instance.
  • Byte-size policies. The maximum is then compared with the raw sizeInBytes(), not with the policy's size, which is pro-rated by the deleted documents a merge would drop. At the three changed call sites the two are the same: isMerged evaluates the check only for a segment with no deletes to merge (MergePolicy.java:901-905), and a just-merged segment is created with a delete count of 0 (IndexWriter.java:3611-3612, :5413, :5691) (by reading; no suite showed a difference).
  • The cached size. The fix calls SegmentCommitInfo.sizeInBytes() before the compound file is built, and that value is cached (SegmentCommitInfo.java:270-279). So under LogDocMergePolicy the writer's in-memory size of a merged segment that then becomes a compound file is the sum of its separate files. Nothing new: the byte-size policies have this today, and so has LogDocMergePolicy when infoStream is on (by reading).
  • Not run: nightly tests, modules other than core.

Decide everything on bytes

#

The alternative in epotyom's review comment on #15295: always pass sizeInBytes() and stop relying on MergePolicy#size for the compound-file decision.

Trade-offs

It removes the document threshold and the SizeUnit enum that #15295 added, so LogDocMergePolicy's compound-file rule changes for everyone, not only for those who set a maximum. Not built.

Document it

#

Say in the javadoc of the setter and getter and in MIGRATE.md that under a document-count policy the maximum is compared with the document count, or skip the maximum for such policies and say so.

Trade-offs

The smallest change. It leaves a megabyte setter whose value means documents under one policy, or a setting that silently does not apply. Not built.

Workaround for applications today

#

If a byte limit is needed, use LogByteSizeMergePolicy or TieredMergePolicy, which honour it. Under LogDocMergePolicy on 11.0 and main, bound compound segments with the document threshold, setCfsThresholdDocSize.

Trade-offs

Not a fix: it changes the merge policy, or limits by documents and not by bytes.

Downstream note

#

Read, not run: Solr can build a LogDocMergePolicy from its configuration and hands configured properties such as maxCFSSegmentSizeMB to the policy's setters, so such a setup on Lucene 10.x or earlier would have its limit compared with a document count in the same way; no downstream report of it was found.

How it was found

#

Non-formal: by reading the code. A list of every size threshold that changed between 10.6.0 and the 11.0 branch showed that the megabyte maximum is compared with the merge policy's size, which for LogDocMergePolicy is a document count. A test confirmed it. No formal-methods tool was involved.

LFV-1497, snapshot of 2026-11-19

Registry title
With LogDocMergePolicy, the megabyte limit of CompoundFormat#setMaxCFSSegmentSizeMB (MergePolicy#setMaxCFSSegmentSizeMB from 4.4.0 to 10.x, LogMergePolicy#setMaxCFSSegmentSizeMB in 4.0.0 to 4.3.1) is compared with the merged segment's document count, so a merged segment larger than the limit is still written as a compound file (file layout only; in every release since 4.0.0)
Area
codecs / compound-file decision for merged segments (CompoundFormat.useCompoundFile: the maximum segment size under LogDocMergePolicy; MergePolicy.useCompoundFile up to 10.x)
Priority
Low, rank 1096: In every release since 4.0.0, an application that uses LogDocMergePolicy and sets a maximum compound-file segment size in megabytes can still get merged segments above that size written as compound files, because the limit is compared with the segment's document count. It is Low because it needs a non-default merge policy plus an explicit setting, and only the file layout and one extra copy of the segment at merge time are affected: no result is wrong and nothing is lost.
Impact class
minor
Impact note
Hits only applications that combine LogDocMergePolicy (a stock merge policy, not the default) with an explicitly set, finite maximum compound-file segment size (CompoundFormat#setMaxCFSSegmentSizeMB on 11.0 and main, MergePolicy#setMaxCFSSegmentSizeMB from 4.4.0 to 10.6.0, LogMergePolicy#setMaxCFSSegmentSizeMB in 4.0.0 to 4.3.1), with no scale needed (two one-document segments are enough): a merged segment larger than the limit is still written as a compound file, because the limit in bytes is compared with the segment's document count (N MB acts as N * 1,048,576 documents), so the setting is not applied as a limit in bytes under that policy; the cost is the file layout of merged segments and one extra copy of each such segment into its .cfs file at merge time, while search results, stored data and index integrity are unaffected and Lucene throws no exception in the repro; on 11.0 and main only merged segments of at most 65,536 documents (the default document threshold) can be affected, on the releases up to 10.x only those within noCFSRatio of the index (0.1 by default for this policy).
Summary
You use LogDocMergePolicy and tell Lucene not to pack large merged segments into a compound (.cfs) file, for example with setMaxCFSSegmentSizeMB(1). You expect a merged segment larger than 1 MB to be written as separate files, as the setter's javadoc says ('If a merged segment will be larger than this value, it will be left as a non-compound file even if compound files are enabled') and as the byte-size merge policies do. Instead the merged segment is still written as a compound file however large it is, because Lucene compares the limit, converted to bytes, with the segment's number of documents, so a 1 MB limit acts as a limit of 1,048,576 documents; search results are not affected, only the file layout and one extra copy of the segment at merge time.
