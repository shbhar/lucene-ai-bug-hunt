With soft deletes, a merge wrapper that keeps hard-deleted documents makes IndexWriter write a segment with a phantom document

With soft deletes on, a merge policy whose wrapForMerge keeps hard-deleted documents makes IndexWriter write a segment that declares 2 documents but stores 1. With assertions off this is silent, and the phantom document breaks stored-field reads, CheckIndex level 3 and a later merge of that segment.

The finding in 30 seconds

#

IndexWriter removes the hard-deleted documents a merge wrapper kept, but counts only those that have a soft-deletes value. The merged segment is sized from that count, so it declares more documents than it stores.

Background in two steps

#
  1. Soft deletes are opt-in: with IndexWriterConfig.setSoftDeletesField("soft"), a value in the doc-values field soft marks a document as deleted. Hard deletes (deleteDocuments) still work next to them.
  2. Before a merge, a merge policy may wrap each segment's reader (OneMerge#wrapForMerge) and change which documents survive; that is how retention keeps soft-deleted documents. Since LUCENE-8381, IndexWriter then removes any hard-deleted documents the wrapper kept, and it sizes the merged segment from each reader's numDocs().

The finding, step by step

#
  1. Turn on soft deletes (setSoftDeletesField("soft")) and install a merge policy whose OneMerge#wrapForMerge keeps every document: a FilterCodecReader with getLiveDocs() null and numDocs() = maxDoc(). Index 3 documents in one segment: live, hard, softThenHard.
  2. Soft-delete softThenHard, commit, hard-delete hard and softThenHard, and call forceMerge(1). You expect a consistent segment: 1 document if IndexWriter drops the 2 hard-deleted ones, 3 if it keeps them.
  3. IndexWriter re-wraps the reader to drop hard-deleted documents. Its live bits drop both (1 left), but its count subtracts only softThenHard, the one with a soft value: 3 - 1 = 2. The new segment gets maxDoc 2 and 1 stored document.
  4. With assertions off the merge succeeds: numDocs and count(MatchAllDocsQuery) say 2, reading doc 1 throws IndexOutOfBoundsException, CheckIndex passes at level 1 (the command-line default) but fails at level 3, and a later merge of the segment throws. With assertions on the merge fails: numMerged=1 vs mergeState.segmentInfo.maxDoc()=2.

Who is affected

#

Applications that enable soft deletes and install their own merge wrapper that keeps hard-deleted documents, for example a keep-everything FilterCodecReader. The default and the in-tree SoftDeletesRetentionMergePolicy are not affected. Three documents suffice. With assertions off the damage is silent and committed: a later ordinary merge of the segment fails.

Mechanism, terms and numbers525 words

With IndexWriterConfig.setSoftDeletesField set, a merge policy may wrap each segment's reader before a merge (OneMerge#wrapForMerge) and so decide which documents survive. If that wrapper keeps hard-deleted documents live, IndexWriter.mergeMiddle wraps the reader once more to drop them again (added by LUCENE-8381). The new live bits drop every kept hard-deleted document, but the new numDocs subtracts only the kept hard-deleted documents that also carry a soft-deletes value, because countSoftDeletes walks only the documents that have one.

When a segment holds both kinds (one document soft-deleted and later hard-deleted, one only hard-deleted), the merged segment is sized one document too large: in the repro it declares maxDoc 2 and stores 1 document. With assertions off, as in production, the merge succeeds silently: numDocs and IndexSearcher#count(MatchAllDocsQuery) count the phantom document, reading its stored fields throws IndexOutOfBoundsException, CheckIndex passes at level 1 (the command-line default) and fails at level 3, and a later merge of the segment throws, also with the default merge policy and no wrapper. With assertions on, SegmentMerger's assertion fails the merge.

The trigger is opt-in and narrow: soft deletes plus a custom wrapper that keeps hard-deleted documents without a soft value. No in-tree production merge policy does this. A sibling defect in the other branch of the same accounting block (segments without hard deletes) is LFV-730; the two need separate fixes.

The mechanism (main 5adff78bb168)

#
  1. IndexWriter.java:5496: mergeMiddle calls merge.wrapForMerge(reader); in the repro it returns a keep-all reader W (maxDoc 3, numDocs 3, no live bits).
  2. IndexWriter.java:5498-5503: soft deletes are on, W is not the segment reader, and the segment has hard deletes, so hardLiveDocs (only live is set) is not null and the accounting branch runs.
  3. IndexWriter.java:5426-5451 countSoftDeletes iterates only documents that have a value in the soft-deletes field (:5435-5436). Of the documents W keeps, only softThenHard has one, and it is hard-deleted, so hardDeleteCount = 1 (:5444). hard has no soft value and is never visited.
  4. IndexWriter.java:5510-5527: because hardDeleteCount > 0, W is wrapped again with liveDocs = hardLiveDocs (W has no live bits, :5512-5513), which drops both hard and softThenHard, and with numDocs = wrappedReader.numDocs() - hardDeleteCount = 3 - 1 = 2 (:5525-5527). FilterCodecReader.wrapLiveDocs (FilterCodecReader.java:139-160) takes that number as given.
  5. MergeState.java:170-173 sizes the new segment as the sum of the readers' numDocs(): maxDoc 2. The stored-fields merge copies only live documents: 1. SegmentMerger.java:123-128 checks numMerged == maxDoc only with an assert, so with assertions off the segment is written and committed with one phantom document.
  6. If no kept hard-deleted document has a soft value, hardDeleteCount is 0, nothing is wrapped again and W's decision to keep hard stands. Without a soft-deletes field the branch does not run at all. So whether hard survives depends on an unrelated document.

Controls (executed, assertions off)

#
  • No soft-deletes field, same steps: the merge keeps all three documents (maxDoc 3, all readable).
  • Soft-deletes field, but no soft-then-hard document: no second wrap, hard is kept (maxDoc 3, consistent).

The branch for segments without hard deletes (IndexWriter.java:5529-5535) has a different defect, LFV-730.

Exposure and likelihood304 words
  • Who is hit: applications that set a soft-deletes field and install their own merge policy whose wrapForMerge marks hard-deleted documents live without a soft-value filter (a keep-everything wrapper, or a home-grown retention rule). Upstream's own TestIndexWriter#softUpdatesConcurrently installs exactly this keep-all wrapper on a soft-deletes index, but only when mixDeletes == false, so never together with hard deletes.
  • Not the default: SoftDeletesRetentionMergePolicy revives only documents that match FieldExistsQuery(softField), so it never keeps a hard-only deleted document, and no other in-tree production policy keeps hard-deleted documents. None of the merge wrappers read in Elasticsearch, OpenSearch and Solr does either.
  • Hard deletes do occur in soft-deletes indexes: deleteDocuments stays legal ("If soft-deletes are enabled, documents can still be hard-deleted"), and a document that hits a non-aborting exception while being indexed is hard-deleted (LUCENE-8425 commit message).
  • Shape: one segment being merged that holds at least one live document, a document that was soft-deleted and later hard-deleted, and a document that was only hard-deleted, both kept by the wrapper. Three documents suffice; no scale. A bounded-exhaustive sweep of 1884 small cases found it in exactly 18, all of this shape.
  • Effect: with assertions off, counts include the phantom document, its stored-field read throws, CheckIndex at level 1 does not notice, and a later ordinary merge of the segment throws, also with the default merge policy and no wrapper (executed: one later forceMerge(1), in two probes). By code reading, not run: deleting the phantom document by doc ID (IndexWriter.tryDeleteDocument) or deleting all documents (deleteAll) would clear it. With assertions on the merge fails loudly.
  • Likelihood: rare. No matching public report was found, though the code has shipped since 7.5.0 (2018), and Lucene advises against mixing hard and soft deletes. Priority Medium; Low if wrappers that keep hard-deleted documents are ruled out of contract.

Minimal repro

#

One JUnit test: three documents, a keep-all merge wrapper, forceMerge(1), then read every counted document back. It fails with assertions on and off; public API only, one thread, deterministic. It passes whether a fix drops or keeps the hard-deleted documents.

The merged segment stores every document it counts: numDocs 1 (hard-deleted documents dropped) or 3 (kept).
Observed

Why it looks unintended

#
  • wrapForMerge may "add/remove fields or documents"; only reordering doc IDs is illegal (MergePolicy.java:302-305).
  • LUCENE-8381 added this re-wrap so that "IW excludes the hard-deleted documents from a merge reader"; its count walks only soft-valued documents, assuming every kept hard delete has one.
  • SegmentMerger asserts that a merge writes maxDoc documents, and CheckIndex level 3 rejects the segment: Lucene's own invariant breaks.
The full argument192 words
  • The wrapper is in contract. OneMerge#wrapForMerge: "Wrap a reader prior to merging in order to add/remove fields or documents." The only stated restriction: "It is illegal to reorder doc IDs here" (MergePolicy.java:302-305). setSoftDeletesField: "Soft deletes allow to retain documents across merges if the merge policy modifies the live docs of a merge reader" (IndexWriterConfig.java:551-552). No javadoc, CHANGES or MIGRATE entry says a wrapper must not keep a hard-deleted document.
  • IndexWriter took on this job. LUCENE-8381 (0ccd5d580d1): "This change makes sure that IW excludes the hard-deleted documents from a merge reader". In #9428, @dnhatn offered an inline patch ("The calculation now loops over only the soft-deleted docs, not all docs") and one passing hardLiveDocs to the merge policy ("cleaner but requires other custom MP to handle the hard-deletes by itself"); @s1monw: "I think we should go with the inline patch." The optimisation is the assumption this trigger breaks.
  • The wrapper is consistent; IndexWriter's second wrap is not: its bits drop two documents, its count drops one.
  • The outcome depends on an unrelated document: hard is kept unless another kept hard-deleted document has a soft value.
The devil's-advocate check186 words

The strongest case for "not supported": Lucene declined to keep hard deletes across merges. LUCENE-8198 "Add ability to persist deletes across merges" (#9245) was closed as Won't Fix on 2018-03-14 "in favor of" LUCENE-8200 (#9247, which added softUpdateDocument), and retention was built on soft deletes instead. setSoftDeletesField says "Hard-deleted documents won't be considered as soft-deleted even if they have a value in the soft-deletes field" (IndexWriterConfig.java:562-563). Further: no javadoc lets a wrapper revive a hard-deleted document; the in-tree retention policy revives only soft-deleted ones; the LUCENE-8425 commit message says "The recommendation is to not mix those"; upstream's keep-all test wrapper is installed only without hard deletes; and with assertions on the merge fails loudly.

Why it fails: none of this is a documented precondition (the advice is a commit message). Even under this reading, IndexWriter should reject the wrapper or drop the documents consistently; with assertions off it instead commits a segment that a later ordinary merge cannot process. Under this reading the report narrows to "fail loudly or drop consistently" and the priority to Low; under the javadoc reading it is Medium.

Suggested fix

#

Recommended A: count every hard-deleted document the wrapper kept (recommended)

Recommended (validated): in the second wrap, count every hard-deleted document the wrapper kept, not only those with a soft value, so the count matches the live bits. The repro and the 7 nearest suites (8 classes, 200 tests, assertions on and off) pass, as does the whole org.apache.lucene.index package (assertions on). Cost: one bit pass per wrapped segment.

All options and trade-offs4 options · 727 words

The test accepts a fix that drops the hard-deleted documents or one that keeps them; which direction is the maintainers' call. LFV-730 (the branch for segments without hard deletes, IndexWriter.java:5529-5535) needs its own fix: each fix alone leaves the other failing, and the two compose (bounded-exhaustive sweep, below).

A: count every hard-deleted document the wrapper kept (recommended) (validated by the checks)

#

In mergeMiddle's branch for segments with hard deletes (IndexWriter.java:5503-5508), compute hardDeleteCount as the number of documents that the wrapper keeps live and hardLiveDocs marks deleted, instead of taking it from countSoftDeletes, which still supplies the merged segment's soft-delete count. The second wrap's numDocs then matches its bits, and it happens whenever the wrapper keeps any hard-deleted document (the intent of LUCENE-8381).

// index/IndexWriter.java, mergeMiddle, branch for segments with hard deletes
               Bits wrappedLiveDocs = wrappedReader.getLiveDocs();
-              Counter hardDeleteCounter = Counter.newCounter(false);
               countSoftDeletes(
-                  wrappedReader, wrappedLiveDocs, hardLiveDocs, softDeleteCount, hardDeleteCounter);
-              int hardDeleteCount = Math.toIntExact(hardDeleteCounter.get());
+                  wrappedReader,
+                  wrappedLiveDocs,
+                  hardLiveDocs,
+                  softDeleteCount,
+                  Counter.newCounter(false));
+              // The re-wrap below drops every hard-deleted doc that the wrapper kept live,
+              // with or without a soft-deletes value, so count all of them
+              int hardDeleteCount = 0;
+              for (int doc = 0; doc < wrappedReader.maxDoc(); doc++) {
+                if (hardLiveDocs.get(doc) == false
+                    && (wrappedLiveDocs == null || wrappedLiveDocs.get(doc))) {
+                  hardDeleteCount++;
+                }
+              }

Trade-offs

  • Behaviour change: today a kept hard-only deleted document survives the merge when no other kept hard-deleted document has a soft value; with A it is always dropped. Indexes without a soft-deletes field are not touched.
  • Cost: one pass of Bits.get over maxDoc per merged segment that has hard deletes and a wrapper that returns another reader; the merge itself is linear in the documents it copies. Not measured. LUCENE-8381's count walks only the soft-valued documents instead ("The calculation now loops over only the soft-deleted docs, not all docs"); a cheaper exact count is possible when both bit sets are FixedBitSet (word-wise), or, when the wrapper returns no live bits, as the number of clear bits of hardLiveDocs (untested ideas).

B: derive the second wrap's numDocs from its final bits (validated by the checks)

#

Count the set bits of the combined liveDocs instead of subtracting hardDeleteCount.

Trade-offs

Every merged segment becomes consistent, but the rule "wrap again only if a kept hard-deleted document has a soft value" stays, so whether a hard-only deleted document survives still depends on an unrelated document. Same worst-case cost as A (one pass over maxDoc), but only for segments it wraps again.

What the checks validated

Run as a shadow class by the independent reproduction: its test passes with assertions on and off. Not run through gradle or the upstream suites.

C: reject wrappers that keep hard-deleted documents

#

If keeping hard-deleted documents is ruled out of contract, throw an IllegalStateException that names the merge when a wrapper does it, and document the rule on wrapForMerge.

Trade-offs

Loud instead of silent, but it breaks such wrappers in segments that merge fine today (no soft-then-hard document), and it needs the same scan to detect the case. Not run.

Hardening, with any option: make SegmentMerger's document-count check a real check

#

Turn assert numMerged == mergeState.segmentInfo.maxDoc() (SegmentMerger.java:124-128) into a check that fails the merge with assertions off too.

Trade-offs

A future accounting slip would then fail the merge instead of committing a broken segment. It does not fix this bug on its own: the merge would fail. Not run.

Downstream note

#

Products that keep documents across merges with their own wrapper on top of soft deletes should check that it never marks a hard-deleted document without a soft value live; none of the merge wrappers read in Elasticsearch, OpenSearch and Solr does.

How it was found

#

Semi-formal. An invariant check of merges on the real code (each segment's numDocs against its live bits, count(MatchAllDocsQuery) and CheckIndex), run as a seeded fuzz and minimised by delta debugging, flagged it; reading mergeMiddle gave the cause. A bounded-exhaustive sweep of 1884 small cases then gave the exact trigger set: 18 cases.

The method in full170 words
  • Invariant: after any sequence of soft updates, soft and hard deletes and wrapped merges, each segment's numDocs agrees with its live bits and stored documents, count(MatchAllDocsQuery) agrees with numDocs, and CheckIndex passes.
  • Lead: a seeded fuzz run of that check on the real jars failed; delta debugging reduced it, and reading mergeMiddle showed the second wrap's count (IndexWriter.java:5426-5451, :5503-5528).
  • Exact trigger set: a bounded-exhaustive sweep of the real jar: one segment of 1-3 documents, each live, soft-deleted, hard-deleted or soft-then-hard-deleted, times a wrapper that keeps, removes or revives each, plus one live segment, then forceMerge(1), with an oracle that accepts any consistent outcome (1884 cases, assertions on and off). Stock main fails 121: 18 are this bug, exactly the cases that keep a soft-then-hard-deleted and a hard-only-deleted document in a segment that is not fully deleted; 103 are LFV-730. With this fix the 18 pass; with both fixes all 1884 pass.
  • Witness: the one-test repro on stock main, then the checks listed under Independent checks.

LFV-1392, snapshot of 2026-11-09

Registry title
With a soft-deletes field configured, a merge whose OneMerge#wrapForMerge keeps hard-deleted documents live can make IndexWriter write a segment that declares a document it never stored: mergeMiddle's re-wrap drops every kept hard-deleted document but subtracts only those that carry a soft-deletes value, so with -da the merge succeeds silently, the phantom document has no stored fields, CheckIndex level 3 fails and no later merge can process the segment; since 7.5.0 (LUCENE-8381)
Area
index / IndexWriter merge soft-delete accounting (mergeMiddle re-wrap of wrapper-kept hard-deleted documents x OneMerge#wrapForMerge, OneMergeWrappingMergePolicy)
Priority
Medium, rank 173: Since 7.5.0, with assertions off (the production default), a merge can silently write a segment that declares a document it never stored: counts include the phantom document, reading its stored fields throws, CheckIndex level 3 fails and every later merge of that segment throws even without the wrapper, so the damage is permanent. It needs the opt-in soft-deletes field plus a custom merge wrapper that keeps hard-deleted documents live, and one merged segment that holds both a soft-then-hard-deleted and a hard-only-deleted document; no in-tree production policy and no downstream wrapper that was read does this.
Impact class
data corruption
Impact note
Only applications that set a soft-deletes field and install their own merge policy whose OneMerge#wrapForMerge marks hard-deleted documents live without SoftDeletesRetentionMergePolicy's soft-value filter (for example a keep-everything FilterCodecReader, the idiom upstream's own TestIndexWriter#softUpdatesConcurrently installs on a soft-deletes index; no in-tree production policy and none of the downstream wrappers read does this, so default configurations are unaffected) are hit, deterministically and at any index size, whenever one merged segment holds both a document that was soft-deleted and later hard-deleted and a document that was only hard-deleted: with -da (as in production) the merge silently writes a segment whose maxDoc exceeds the documents it stores, the phantom document has no stored fields (IndexOutOfBoundsException when read), numDocs and IndexSearcher#count(MatchAllDocsQuery) count it, CheckIndex passes at the default level and fails at level 3, and every later merge of the segment throws, also with the default merge policy and no wrapper, so the damage is permanent; with -ea the merge itself fails at SegmentMerger's assertion; every release from 7.5.0 to 10.6.0 and main [exec].
Summary
You set IndexWriterConfig#setSoftDeletesField and a merge policy whose OneMerge#wrapForMerge returns a FilterCodecReader that keeps every document (getLiveDocs() null, numDocs() == maxDoc()), index three documents in one segment, give one of them a soft-deletes value, then hard-delete it and one other document, and call forceMerge(1); you expect a consistent merged segment, whether IndexWriter drops the two hard-deleted documents (the intent of LUCENE-8381) or keeps them (as it does without a soft-deletes field). Instead IndexWriter re-wraps the reader with the hard live docs, which drop both hard-deleted documents, but subtracts only the one that has a soft value, so it writes one stored document into a segment with maxDoc 2. With assertions off the merge succeeds, numDocs and count(MatchAllDocsQuery) report 2, reading the second document's stored fields throws IndexOutOfBoundsException, CheckIndex fails at level 3 (the default level passes), and every later merge of that segment fails, even without the wrapper; with -ea the merge fails at SegmentMerger's assertion 'numMerged=1 vs mergeState.segmentInfo.maxDoc()=2'.
