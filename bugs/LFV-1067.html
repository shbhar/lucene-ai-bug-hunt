A failed NRT reader open whose leaf sorter throws never releases its file reference, so the open writer keeps that point in time's segment files on disk

If the IndexWriterConfig leaf sorter throws while DirectoryReader.open(writer) builds an NRT reader, the failed open never gives back the file reference it took on the writer. The still-open writer then never deletes those files: after forceMerge(1) and commit(), all 6 files of the two merged-away segments stay in the directory.

The finding in 30 seconds

#

The open takes a file reference on the writer before it builds the reader, and only that reader's close() gives it back. When the leaf sorter throws inside the constructor, there is no reader to close.

Background: NRT readers, file references and leaf sorters

#
  1. An NRT reader opened from an IndexWriter (DirectoryReader.open(writer), openIfChanged, SearcherManager) sees the writer's current segments, committed or not.
  2. While such a reader is open the writer must not delete its segments' files. So the open adds one reference per file in the writer's file bookkeeping, and closing the reader takes them back. A file is deleted only when no commit and no reader references it.
  3. IndexWriterConfig#setLeafSorter (since 8.9.0) adds a Comparator<LeafReader> that orders the segments inside every NRT reader, for example newest first for time-based data. It runs inside the reader's constructor.

The finding, step by step

#
  1. Give IndexWriterConfig a leaf sorter, a Comparator<LeafReader> that orders the segments of every NRT reader, and commit two one-document segments, _0 and _1.
  2. Call DirectoryReader.open(writer). The open first tells the writer "keep every file of _0 and _1, a reader uses them", then builds the reader, whose constructor runs the sorter. Here it throws, as a sorter bug on a segment without the sort field, or an I/O error it rethrows, would.
  3. You expect only that exception. No reader exists, so once forceMerge(1) merges _0 and _1 into _2 and commit() runs, the writer deletes their files. Without the failed open, only _2's 3 files and segments_3 remain.
  4. Instead all 6 files of _0 and _1 stay. The open's cleanup gave back the segment readers but not the file reference, and the writer, which survives the exception, holds it until it closes.
  5. Every failed retry pins the current files again: 19 failed SearcherManager refreshes with merges in between left 118 files (524,782 bytes) in the directory for an index of 4 files (41,211 bytes). A new IndexWriter on the directory deletes them.

Who is affected

#

NRT applications that set the opt-in IndexWriterConfig#setLeafSorter (since 8.9.0) and refresh through DirectoryReader.open(writer), openIfChanged or a SearcherManager/ReaderManager on the writer. It takes a sorter that throws during a refresh of 2+ segments. Each failure keeps that point in time's segment files, up to the whole index, while the writer stays open; results stay correct.

Mechanism, terms and numbers775 words

IndexWriterConfig#setLeafSorter (LUCENE-9507, since 8.9.0) gives the writer a Comparator<LeafReader> that orders the segments of every NRT reader opened from it. The NRT open StandardDirectoryReader.open(IndexWriter, ...), behind DirectoryReader.open(writer), openIfChanged(reader[, writer]) and SearcherManager/ReaderManager refreshes over a writer, first calls writer.incRefDeleter(segmentInfos), which makes the writer keep every segment file (not segments_N) of the point in time it is about to expose, and then constructs the reader. That constructor sorts the segment readers with the leaf sorter. If the sorter throws, the open's catch (Throwable) gives back only the segment readers; the file reference is released only by the returned reader's close(), and no reader is returned. IndexWriter.getReader treats only an Error as tragic, so the writer stays open and usable while it keeps those files referenced for the rest of its life. With two one-document segments, after the failed open, forceMerge(1) and commit(), the six files of _0 and _1 are still in the directory; 19 failed refreshes with merges in between left 118 files / 524,782 bytes in the directory for an index of 4 files / 41,211 bytes. No wrong results, no index damage, and the next IndexWriter opened on the directory deletes the files. A 9-line guarded decRefDeleter in the same catch fixes it. Every release from 8.9.0 to 10.6.0 and main is affected (8 of those releases and main executed, the rest by reading).

  • Deleter reference: IndexWriter.incRefDeleter(segmentInfos) (IndexWriter.java:6306-6317) adds one reference in the writer's IndexFileDeleter to every file of the segments in a point in time, not to segments_N (it calls deleter.incRef(segmentInfos, false), IndexFileDeleter.java:603-609); decRefDeleter (:6319-6336) takes it back.   • Leaf sorter: the Comparator<LeafReader> from IndexWriterConfig#setLeafSorter (IndexWriterConfig.java:517-527), null by default.

The bug

#
  1. The NRT open gets one segment reader per segment (StandardDirectoryReader.java:136), keeps it or drops a fully deleted one (:137-145), and then calls writer.incRefDeleter(segmentInfos) (:148).
  2. It returns new StandardDirectoryReader(dir, readers.toArray(...), writer, segmentInfos, writer.getConfig().getLeafSorter(), ...) (:150-157). The BaseCompositeReader constructor runs Arrays.sort(subReaders, subReadersSorter) (BaseCompositeReader.java:74-77): the application's comparator.
  3. The comparator throws. The catch (StandardDirectoryReader.java:158-164) runs IOUtils.applyToAll(readers, SegmentReader::decRef) and rethrows. The only decRefDeleter for this reference is in the reader's doClose (:548-568), and no reader was returned.
  4. IndexWriter.getReader's catch (IndexWriter.java:711-721) calls onTragicEvent only for an Error, so after the sorter's RuntimeException the writer stays open and usable, with a count on every segment file of that point in time that nothing will take back.
  5. Later merges and commits drop their own references, but these files never reach zero while the writer lives. They are still there after IndexWriter.close(); the next IndexWriter opened on the directory deletes them as unreferenced.

Without a leaf sorter no application code runs in that constructor; its only other explicit throw is the "Too many documents" check (BaseCompositeReader.java:89-98), which IndexWriter prevents. So before 8.9.0 no realistic input reached this gap (read, not executed); the one contrived way, then and now, is a caller-supplied InfoStream (trusted configuration) whose message throws inside incRefDeleter after deleter.incRef has run (IndexWriter.java:6306-6317), which the fix below does not cover either. By reading only: IndexWriter's merge-on-refresh second open (maybeReopenMergedNRTReader, IndexWriter.java:755, :766) calls the same method and would leak the same way.

Exposure and likelihood350 words
  • Who is hit. NRT applications with IndexWriterConfig#setLeafSorter (for example a newest-first sorter for time-based indices) that refresh through DirectoryReader.open(writer), openIfChanged(reader[, writer]), or a SearcherManager/ReaderManager built on the writer (SearcherManager.java:66, ReaderManager.java:41; refreshIfNeeded at SearcherManager.java:194-205). Executed: DirectoryReader.open(writer) and SearcherManager.maybeRefresh().
  • Default vs opt-in. Opt-in: the leaf sorter is null by default (LiveIndexWriterConfig.java:422-431), and Lucene ships none.
  • What triggers it. The sorter must throw during an NRT open of two or more segments (with one segment the sort makes no comparison): a comparator bug on a segment that lacks the sort field (Lucene's own test sorter handles a null getPointValues, TestIndexWriterReader.java:1212-1222), or an I/O error inside a correct sorter, which Comparator.compare forces it to rethrow unchecked. Elasticsearch's time-series leaf sorter does exactly that (read through the GitHub API by a verifier).
  • How much. One failure pins every segment file of that point in time for the writer's lifetime: after merges, up to the index size at the time of the failure. Each further failure pins the then-current segment files again, which adds up when new segments or merges are written between the attempts (118 files / 524,782 bytes against a 41,211-byte index after 19 failures). Any index size.
  • When it builds up. Only if the application keeps the writer open and retries. A product that closes the writer on a refresh failure does not accumulate (a verifier cites Elasticsearch's failEngine("refresh failed ...")), and ControlledRealTimeReopenThread ends at the first failed refresh (ControlledRealTimeReopenThread.java:212-216 catches only IOException and rethrows it unchecked). A service that catches the exception and retries maybeRefresh() on its own schedule accumulates.
  • What does not happen. No wrong or resurrected results (no reader or commit refers to these files), no index modification, no hang. The refresh fails loudly with the sorter's exception, and the next IndexWriter on the directory deletes the files.
  • Related findings. LFV-1059: the same trigger on the non-NRT reopen factory, which leaks segment reader references; LFV-626: the keep check in this same method, before incRefDeleter, which leaks one segment reader. Each is an independent fix.

Why it looks unintended

#
  • decRefDeleter: "Only call this if you are sure you previously called incRefDeleter". Only the open knows it did, and it returns no reader.
  • The same catch (Throwable) already gives back the open's segment readers (LUCENE-5262, LUCENE-8215).
  • The writer stays usable after the exception, so the reference is kept for the writer's whole life.
The full argument274 words
  • The pair contract. IndexWriter.decRefDeleter (IndexWriter.java:6319-6324): "Record that the files referenced by this {@link SegmentInfos} are no longer in use. Only call this if you are sure you previously called {@link #incRefDeleter}."
  • The same catch. LUCENE-5262 (#6326, 2013, "StandardDirectoryReader should decRef readers on exception, not close them") added the cleanup that gives the segment readers back when the open fails (LUCENE-8215, #9262, 2018, rewrote it as today's catch (Throwable)); the deleter reference added in 2014 (LUCENE-5434, #6497) was never added to it.
  • The writer is meant to stay usable. getReader's catch rethrows a non-Error without a tragic event (IndexWriter.java:711-721; the inner catch says "Uh oh, tidy up then rethrow", :669-676). The class javadoc reserves self-closing for an Error or a failed checkpoint, when "reference counts" may be corrupted (:162-165).
  • Tests. TestIndexWriterReader.testNRTOpenExceptions (:1108-1153): "test that several failed attempts to obtain an NRT reader don't leak file handles"; its injected failure comes before incRefDeleter, so it never reaches this gap. No test at 645d4fe14a20 makes a leaf sorter throw: the only test that sets one, testIndexReaderWriterWithLeafSorter (:1204-1222), does not throw.
  • No precondition on the sorter. setLeafSorter (IndexWriterConfig.java:517-527) and getLeafSorter (LiveIndexWriterConfig.java:422-431) say nothing about exceptions, and Comparator.compare may throw.
  • History. The missing release existed since 2014, but no realistic input reached it: before LUCENE-9507 (48715fe898bf, 2021) the constructor could throw only "Too many documents", which IndexWriter prevents (a throwing caller-supplied InfoStream inside incRefDeleter is the only, contrived, exception). LUCENE-9507 put the application's comparator inside it; none of the review comments on #32, apache/lucene-solr#2256 or #2473 discuss exceptions.
The devil's-advocate check248 words

The strongest case for "intended" (the devil's-advocate verifier and the intended-lens reviewer): Lucene tolerates leftover files, since the doClose comment calls them "harmless" because "the next time IW is opened on the index, it will delete them" (StandardDirectoryReader.java:554-559), LUCENE-5574 (#6636) turned the test framework's unreferenced-files check off by default, and on #12228 rmuir wrote that a new IndexWriter "will delete the unnecessary files" and that IndexWriter should not "try to be a superhero and do dangerous things such as deleting files when handling exceptions"; the sorter is application code and the repro's sorter always throws; DirectoryReader.open(writer) is @lucene.experimental and incRefDeleter/decRefDeleter are @lucene.internal.

Why it fails: the tolerance covers a writer that is already closed or a tragic event, while here the writer stays open after a non-Error exception and keeps the files for its whole life; the fix only gives the count back: in the repro it deletes nothing while handling the exception (the directory listing is unchanged right after the failed open), and by reading the writer itself still references those files at that moment, so it does not do what that comment warns about. An always-throwing comparator is within Comparator's contract, no javadoc asks for a non-throwing sorter, and a correct sorter doing I/O reaches the same path. Experimental is about API stability, not a licence to leak, and the user path is public. Every reviewer rated the intended case weak; it explains the Low priority, not the leak.

Suggested fix

#

Recommended Release the deleter reference in the NRT open's catch, guarded by a flag

In the NRT open's catch (Throwable), call writer.decRefDeleter(segmentInfos) (adding its exception as suppressed) when a flag set right after incRefDeleter says the reference was taken. The flag matters: the catch also runs for failures before incRefDeleter. Validated through gradle: the repro passes with assertions on and off, and the 112 tests of the closest suites pass.

+    boolean deleterIncRefd = false; // declared before the try
       writer.incRefDeleter(segmentInfos);
+      deleterIncRefd = true;
       return new StandardDirectoryReader(...); // runs the leaf sorter
     } catch (Throwable t) {
       // ... decRef the segment readers (unchanged) ...
+      if (deleterIncRefd) {
+        try {
+          writer.decRefDeleter(segmentInfos);
+        } catch (Throwable t1) {
+          t.addSuppressed(t1);
+        }
+      }
       throw t;

Release the deleter reference in the NRT open's catch, guarded by a flag (validated by the checks) (recommended)

#

In StandardDirectoryReader.open(IndexWriter, ...) (StandardDirectoryReader.java:126-165), declare boolean deleterIncRefd = false before the try and set it to true right after writer.incRefDeleter(segmentInfos) (:148); in the catch, after the segment readers are given back, call writer.decRefDeleter(segmentInfos) when the flag is set and add any exception from it as suppressed. +9 lines.

+    boolean deleterIncRefd = false; // declared before the try
       writer.incRefDeleter(segmentInfos);
+      deleterIncRefd = true;
       return new StandardDirectoryReader(...); // runs the leaf sorter
     } catch (Throwable t) {
       // ... decRef the segment readers (unchanged) ...
+      if (deleterIncRefd) {
+        try {
+          writer.decRefDeleter(segmentInfos);
+        } catch (Throwable t1) {
+          t.addSuppressed(t1);
+        }
+      }
       throw t;

Trade-offs

  • Why the flag. The catch also runs when readerFunction.apply or the keep check fails, before incRefDeleter. An unconditional decRefDeleter would then release a reference this open never took, one that belongs to a commit point or another reader: in the TLA+ model the unguarded variant violates NoOverRelease for every failure before incRefDeleter.
  • No deletion during exception handling. It only gives the count back. The open runs under the writer's lock on a clone of the writer's current segments, which the writer itself still references at that moment (by reading; with the fix, the fact check's probe saw the directory listing unchanged right after the failed open), so the files go only at the next merge or commit that drops them.
  • Writer closed meanwhile. decRefDeleter calls ensureOpen(); its AlreadyClosedException would be added as suppressed and the sorter's exception rethrown.
  • Not covered. It does not make incRefDeleter itself transactional: if incRefDeleter throws after deleter.incRef has run (only a throwing caller-supplied InfoStream can do that; trusted configuration, contrived), the flag is still false and those references stay, as they do today.
  • Scope. No change on success. Fixes this leg only; the reopen-factory leak (LFV-1059) and the keep-check leak (LFV-626) are other lines.

One exception-safety patch for the three leaf-sorter leaks of StandardDirectoryReader (validated by the checks)

#

The guarded release above, plus the StandardDirectoryReader constructor sorts a copy (super(directory, readers.clone(), leafSorter), so the initial open's cleanup still sees every reader once), plus LFV-1059's try/catch around the reopen factory's constructor call.

Trade-offs

One patch closes the family, but it is three changes needing three tests; the copy costs one array copy per open.

What the checks validated

By the hunt, not re-run here: it passes this test, LFV-1059's minimal test, the initial-open late-sort test and 99 upstream tests (TestDirectoryReader, TestDirectoryReaderReopen, TestIndexWriterReader, TestIndexFileDeleter, TestNRTReaderWithThreads; standalone JUnit runner, seed 5EED0018).

Call decRefDeleter unconditionally in the catch (not recommended)

#

The same call without the flag.

Trade-offs

Over-releases when the failure comes before incRefDeleter (a failing readerFunction or keep check): it would take back a reference owned by a commit point or another reader. The TLA+ model shows the violation.

Take the deleter reference only after the reader is built (considered, not run)

#

Move incRefDeleter after the constructor.

Trade-offs

The returned reader's doClose always calls decRefDeleter, so a failing incRefDeleter (for example ensureOpen on a writer closed meanwhile) would need its own cleanup that closes the reader without that call: more invasive than the guarded release for the same effect.

Downstream note

#

Services that keep the writer open and retry a failing refresh on a schedule pin the then-current segment files on each attempt, so the retained files grow while new segments or merges are written between attempts, until the writer closes and a new writer cleans up; a service that closes its writer when a refresh fails does not accumulate.

How it was found

#

Semi-formal. While mapping a TLA+ model of reader reference counting to the NRT open, an AI tool saw in the code that the file reference is never released when the constructor throws, and confirmed it with a JUnit test. A second TLA+ model, checked with TLC, reproduced it as an invariant violation and separated it from a sibling leak.

The method in full171 words

Method: semi-formal, a hypothesis formed while modelling, then witnessed by an executed test.

  • A hunt unit (2026-10-26), building a TLA+ model of IndexReader reference counting (ReaderLifecycle.tla), noticed this leg by code reading while mapping the model to StandardDirectoryReader.open(IndexWriter, ...) and witnessed it with a public-API JUnit (testNrtOpenLeaksFileReferences), the second manifestation of its leaf-sorter finding. LFV-1059 covers that finding's reopen leg and leaves this leg out of its claim; a later probe re-ran it.
  • The adjudication (2026-11-01) wrote a TLA+ model of the NRT open's acquire/release protocol (NrtOpen.tla) with a fault at five selected steps (each of two readerFunction.apply calls, the second segment's keep check, incRefDeleter failing before its increment, and the constructor; not every statement that can throw) and checked 35 TLC configurations: only the constructor fault violates NoDeleterLeak (10 distinct states), only the keep-check fault violates NoSegmentReaderLeak (that is LFV-626), each fix alone leaves the other violation, and an unguarded decRefDeleter violates NoOverRelease. It then reduced the witness to the one-test repro.

History

#

Introduced by LUCENE-9507 (48715fe898bf, 2021-03-26; branch_8x backport 1cfd0df4e7bb), which put the leaf sorter inside a constructor that runs after the file reference is taken; the unreleased reference dates from 2014, but no realistic input reached it before. First released in 8.9.0; 8 releases executed from 8.9.0 to 10.6.0 fail. Not fixed upstream.

Versions tested6 rows

Introduced by 48715fe898bf, LUCENE-9507 "Custom order for leaves in IndexReader and IndexWriter (#32)" (#10546; author date 2021-03-26), backported to branch_8x as 1cfd0df4e7bb (apache/lucene-solr#2473, 2021-03-30). It passed the writer's leaf sorter into the StandardDirectoryReader constructor that the NRT open calls right after incRefDeleter, and added the Arrays.sort to BaseCompositeReader.

LFV-1067, snapshot of 2026-11-02

Registry title
A failed NRT reader open (DirectoryReader.open(IndexWriter), openIfChanged over the writer, or a SearcherManager/ReaderManager refresh) whose IndexWriterConfig leaf sorter throws never releases the IndexFileDeleter reference it took, so the still-open writer keeps every segment file of that point in time on disk for the rest of its life
Area
core / NRT reader open from IndexWriter (StandardDirectoryReader.open(IndexWriter, ...) failure path, with an IndexWriterConfig leaf sorter, LUCENE-9507)
Priority
Low, rank 913: In every release since 8.9.0, when an opt-in leaf sorter throws during an NRT open, the still-open writer keeps every file of that point in time on disk. The open fails loudly and the leak only grows if the application keeps the writer and retries, so it is Low.
Impact class
minor
Impact note
NRT applications that set the opt-in IndexWriterConfig#setLeafSorter (since 8.9.0) and refresh through DirectoryReader.open(writer), openIfChanged(reader, writer) or SearcherManager/ReaderManager over the writer: when the sorter throws during an NRT open of two or more segments (a comparator bug on a segment that lacks the sort field, or an I/O error that a sorter reading per-segment data rethrows unchecked), the refresh fails loudly but the writer stays open and keeps a file reference on every segment of that point in time, so merges and commits no longer delete those files until the writer closes and a new IndexWriter opens on the directory (executed: the 6 files of two merged-away segments are left after forceMerge(1) and commit; 19 failed refreshes with indexing and merges in between left 118 files / 524,782 bytes on disk for an index of 4 files / 41,211 bytes, against at most 10 files without the failures); the leak builds up only if the application keeps the writer open and retries; no wrong results, no index damage, any index size.
Summary
You set a leaf sorter on IndexWriterConfig and open an NRT reader from the writer; if the sorter throws while the new reader sorts its leaves, you expect only that exception and a writer left as it was, because the open's own catch releases the segment readers it took and IndexWriter.getReader keeps the writer usable after a non-Error exception. Instead the open has already called writer.incRefDeleter(segmentInfos), which only the returned reader's close undoes, and no reader is returned, so the writer keeps every segment file of that point in time referenced for the rest of its life: after forceMerge(1) and commit, the files of the merged-away segments _0 and _1 are still in the directory.
