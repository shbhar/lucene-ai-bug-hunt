With assertions on, WANDScorer.getChildren() before the first hit throws AssertionError: its self-check scores clauses that are not positioned yet

With JVM assertions on (-ea), calling getChildren() before the first hit on a top-k BooleanQuery scorer with minimumNumberShouldMatch >= 2, as collectors do in setScorer, throws AssertionError: WANDScorer's self-check scores clauses that are not on a document yet. Without assertions the result is correct; 10.1.0 to 10.6.0 and main.

The finding in 30 seconds

#

A collector that looks at the scorer tree before the first hit trips an assertion inside WANDScorer, the scorer Lucene uses for top-k disjunctions with minimumNumberShouldMatch >= 2.

Background

#
  1. Scorable.getChildren() returns a scorer's clause scorers. Collectors call it in LeafCollector.setScorer, before the first hit, to find per-clause scorers; Lucene's own tests do this.
  2. WANDScorer keeps the clauses that match the current document in a "lead" list, with a running sum of their scores, leadScore.
  3. With -ea, WANDScorer re-checks that sum from time to time: it asks every lead for score() and asserts that the total equals leadScore.

The finding, step by step

#
  1. Index one document with StringField f = a, b, c. Query: three SHOULD ConstantScoreQuery(TermQuery) clauses with minimumNumberShouldMatch(2). For top-k (TOP_SCORES) scoring, the scorer Lucene builds for it is a WANDScorer.
  2. Before the first hit, call getChildren() on that scorer: that is the state a collector's setScorer sees. You expect the 3 clause scorers, and that is what you get with assertions off, or on 10.0.0.
  3. With -ea you get AssertionError at WANDScorer.java:238. getChildren() runs a self-check that asks each clause for score(); a constant-score clause answers 1.0 even before it is on a document, so the sum is 3.0.
  4. But WANDScorer adds its clauses to the lead list unscored (addUnpositionedLead) before the first document, so its running lead score is 0.0. The check asserts 3.0 == 0.0 and fails. After the first nextDoc() both are 3.0.

Who is affected

#

Only code running with JVM assertions on (in practice application and downstream test suites) whose top-k collector walks getChildren() before the first hit over a minimumNumberShouldMatch >= 2 query of clauses that score non-zero while unpositioned: ConstantScoreQuery, constant-score PrefixQuery, TermQuery on a StringField. Without assertions, hits and children are correct for the tested query shapes.

Mechanism, terms and numbers566 words

For a top-k (ScoreMode.TOP_SCORES) BooleanQuery with minimumNumberShouldMatch >= 2, the scorer Weight.scorer builds for the SHOULD clauses is a WANDScorer. A search scores with it on main and, since 10.5.0, at any index density; in 10.1-10.4 a dense top-level disjunction is bulk-scored by BooleanScorer instead. Since #14021 (10.1.0) its constructor puts every clause into its "lead" list without scoring it, so the running lead score is 0 before the first document. getChildren() always ends in the -ea consistency check ensureConsistent(), which under TOP_SCORES calls score() on every lead and asserts that the sum equals the lead score.

Before the first document, which is when LeafCollector.setScorer runs, the clause scorers are not positioned. A constant-score clause still answers its constant, so three clauses sum to 3.0 against a lead score of 0.0 and the assertion fails. With assertions disabled, getChildren() returns the three clause scorers and the search is correct. The fix is a two-line change to the assertion code.

Mechanism (Lucene main 5adff78bb168)

#
  1. The constructor adds every clause with addUnpositionedLead(new DisiWrapper(scorer, true)) (WANDScorer.java:198-205, call at :204). addUnpositionedLead (:382-388) links the clause into lead and does freq += 1 but adds no score (unlike addLead, :373-380), so leadScore stays 0 at doc -1.
  2. getChildren() (:269-277) calls advanceAllTail() unconditionally (:272).
  3. advanceAllTail() (:537-550) has nothing to advance at doc -1 (the tail is empty) and ends with assert ensureConsistent(); (:549).
  4. ensureConsistent() (:217-255), in its TOP_SCORES block (:218-244), collects w.scorable.score() for every lead (:226-230, the call at :229) and asserts recomputedLeadScore == leadScore (:238). This is the fix site.
  5. Calling score() on an unpositioned scorer is itself outside the Scorable protocol: with the test framework's asserting sub-scorers the same path fails one step earlier, AssertionError: SHALLOW_ADVANCING from AssertingScorer.score (AssertingScorer.java:127, assert iterating() : state) via WANDScorer.java:229 (executed).

The numbers (executed, assertions off)

#

At doc -1, each of the 3 ConstantScoreScorer children (docID -1) returns score() = 1.0, so the check's sum is 3.0, while WANDScorer.leadScore is 0.0. After the first nextDoc() (doc 0) the lead score is 3.0, as it should be.

How a search gets there

#
  • DefaultBulkScorer.score calls collector.setScorer(scorer) before the first document (Weight.java:251-254).
  • BooleanScorerSupplier.java:314-321 gives TOP_SCORES with minShouldMatch > 1 no bulk scorer, so the search falls back to the per-document scorer tree ("BS2" in the code comment), whose disjunction part is the WANDScorer, at any index density since #16176 (10.5.0). In 10.1-10.4 a dense top-level disjunction was bulk-scored by BooleanScorer instead, so a search reaches WANDScorer.getChildren() there only for sparse clauses (cost < maxDoc/3; executed with 50 filler documents on 10.1.0, 10.2.2, 10.3.2 and 10.4.0) or, by reading, for a nested disjunction with minimumNumberShouldMatch > 1. The minimal test calls Weight.scorer directly, so it reaches WANDScorer on every affected release.

Which clauses trigger it

#

Those whose score() is non-zero while unpositioned. Executed: ConstantScoreQuery, PrefixQuery (default constant-score rewrite) and a plain TermQuery on a docs-only StringField fail; TermQuery and BoostQuery(TermQuery) over a TextField pass. In the tested configuration that is because an unpositioned TermScorer scored 0.0 on the TextField and 0.1798 on the StringField, while ConstantScoreScorer scored 1.0, against a lead score of 0.0 in every case (executed probe); TermScorer.score() depends on the postings and the similarity, so other configurations may differ.

Why it looks unintended

#
  • Lucene's own TestBooleanQueryVisitSubscorers calls getChildren() on a WANDScorer from setScorer and asserts the result (under COMPLETE, which skips the failing check).
  • #6858 (LUCENE-5796) fixed this same call on this query shape as a bug, and #14021 itself keeps clauses unscored before the first document.
  • The failing check calls score() on scorers that are not on a document.
The full argument275 words
  • Lucene's own tests make the same call: TestBooleanQueryVisitSubscorers.testGetChildrenMinShouldMatchSumScorer (:246-266) walks getChildren() from setScorer (:316-319) and asserts the subtree MUST WANDScorer / SHOULD TermScorer x3; MyCollector walks it from setScorer too (:171-174). These pass because they run under COMPLETE, which skips the failing TOP_SCORES block (:307-308; MyCollector through its Integer.MAX_VALUE hit threshold, TopScoreDocCollector.java:58-59), and their clauses are TermQuery over a TextField. TestConjunctions.testScorerGetChildren (TestConjunctions.java:95-124) also asserts 2 children in setScorer (:147-151), on a MUST + FILTER conjunction that never builds a WANDScorer: it shows the call pattern, not this code path.
  • The test framework says collectors walk the tree: AssertingScorer.getChildren() exposes the wrapped scorer so that "collectors ... that need to walk the scorer tree" do not miss it (AssertingScorer.java:136-142).
  • History: LUCENE-6228 (910a0231f6f, 2018) moved getChildren() onto Scorable, the type setScorer receives, and deleted the old note that it "should not be called on Scorers passed to LeafCollector#setScorer" (its stated reason was that these "may be synthetic Scorers produced by BulkScorer which will throw an Exception", not positioning). LUCENE-5796 (#6858, 2014) fixed this very call pattern (three SHOULD clauses, minimumNumberShouldMatch 2) in the since-removed MinShouldMatchSumScorer.
  • The breaking change leaves the leads unscored at doc -1: #14021 introduced addUnpositionedLead, which adds a clause to the lead list without scoring it (its commit message does not discuss doc -1); only the content of the check changed (before, it summed max scores, which holds at doc -1; 10.0.0 passes).
  • Precedent: illegal WANDScorer assertions were fixed as bugs before: #9704 (LUCENE-8658) and #11015 (LUCENE-9976, fixed by #171).
The devil's-advocate check222 words

Scorable.getChildren() is @lucene.experimental and documented as "Returns child sub-scorers positioned on the current document" (Scorable.java:56-63); before the first document there is no current document. The LUCENE-7628 entry still in lucene/CHANGES.txt (:8429-8432) says "AssertingScorer checks that getChildren() is not called on an unpositioned Scorer"; in 2017 a maintainer suggested on #8679 that the docs say the method is only valid when positioned; a maintainer called the API "best effort", no guarantees, on #9006 (LUCENE-7957), and #7291 (open) proposes removing it. So a maintainer could answer "do not call it before the first document".

Why it fails: that AssertingScorer check existed only in the reverted first commit (5bdc492c9ca, reverted by 94e3460305a); the re-commit ac38872a791 did not add it, and today's AssertingScorer.getChildren() has no such check. The javadoc describes the children ("positioned on the current document") but states no precondition on when the method may be called, so it is ambiguous before the first document rather than a ban; the "not from setScorer" note was deleted when the method moved to Scorable, Lucene's own tests rely on the call, and WANDScorer answers it correctly with -da. On #9006 "best effort" was said about which matching clauses the API can expose, not about production code throwing (read 2026-11-05). TestBooleanQueryVisitSubscorers and #6858 answer this objection; it stays Low.

How it was found

#

Semi-formal: a proof-obligation audit of WANDScorer's contract (its -ea consistency check must hold in every state a caller can reach through the public Scorable API) checked the state before the first document, where a collector may call getChildren(). The obligation fails there, at doc -1, and a JUnit test on stock main witnessed the failure.

The method in full86 words
  • Obligation: every assert ensureConsistent() in WANDScorer holds in every state a caller can reach through public API, including a fresh scorer at doc -1, which is what LeafCollector.setScorer receives (Weight.java:251-254).
  • Finding: at doc -1 leadScore is 0 by construction (addUnpositionedLead, WANDScorer.java:382-388), while the check recomputes it from score() on unpositioned leads (:229), which need not be 0.
  • Witness: the one-test JUnit repro, then an independent reproduction, an adversarial cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

History

#

Introduced by #14021 (d9aa525c9ea on main, 3f620dcd34f on branch_10x, 2024-11-26), first released in 10.1.0. Fails on 10.1.0 through 10.6.0 and main with -ea; 10.0.0 and 9.12.3 pass. Reverting only #14021's WANDScorer change on the 10.1.0 jars makes it pass. Not fixed upstream.

Versions tested8 rows

Introduced by #14021 "Make WANDScorer compute scores on the fly." (Adrien Grand), d9aa525c9ea on main and 3f620dcd34f on branch_10x, 2024-11-26. It added addUnpositionedLead and made ensureConsistent() recompute the lead score with score() on every lead; before, the check compared sums of max scores, which holds at doc -1. git tag --contains 3f620dcd34f lists 10.1.0 through 10.6.0; 9.x never got it.

The call path is as old as WANDScorer: since LUCENE-4100 (4fc5a872ded, 2017) getChildren() has called the helper that advances the tail and ends in assert ensureConsistent() (named updateFreq() until LUCENE-8135, 4fb7e3d02c6, 2018, renamed it advanceAllTail()). #16176 (135b348b370 / 4f720f944b8, 10.5.0) routes every top-k minShouldMatch > 1 disjunction to WANDScorer, which widens a real search's reach. Upstream main still has the same three lines (:204, :229, :238); the newest WANDScorer.java commit is 62f29b6c915 (#16220, authored 2026-07-29), the same as at 5adff78bb168 (re-checked 2026-11-05 against upstream main d060c053bd89).

You search a BooleanQuery with three SHOULD clauses and minimumNumberShouldMatch 2 with a collector whose scoreMode is TOP_SCORES and whose setScorer walks the scorer tree with Scorable.getChildren(), a pattern Lucene's own TestBooleanQueryVisitSubscorers uses. You expect getChildren() to return the three clause scorers, as it does with assertions disabled. Instead, with -ea, WANDScorer.getChildren() runs its internal consistency check before any document has been read: the check calls score() on the not-yet-positioned clause scorers and asserts that their sum equals the lead score, which is still 0, so the search fails with AssertionError at WANDScorer.java:238 whenever a clause scores non-zero while unpositioned (for example ConstantScoreQuery clauses).
