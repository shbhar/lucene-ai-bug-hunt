A +Infinity minimum competitive score makes ScorerUtil.minRequiredScore return NaN, so top-k search can drop documents scoring +Infinity

When the k-th best score of a top-k search is Float.MAX_VALUE, the pruning cut-off ScorerUtil.minRequiredScore comes out as NaN, so conjunctions and disjunctions drop every remaining candidate: search(q, 1) returns doc 0 at Float.MAX_VALUE instead of doc 1001 at +Infinity. A rare regression in 10.3.0, still in 10.6.0.

The finding in 30 seconds

#

Pruning keeps a document only if its partial score can still reach the minimum competitive score. For a minimum of +Infinity the cut-off comes out as NaN, and no score is >= NaN.

Background: how top-k pruning works

#
  1. A top-k search keeps the k best hits; ties go to the lower doc id. After counting 1,000 hits, the collector tells the scorer the minimum competitive score: what a later document must reach to get in.
  2. Conjunctions and disjunctions score one clause for a batch of documents first, then drop those whose partial score cannot reach that minimum even if the other clauses add their maximum.
  3. That cut-off is ScorerUtil.minRequiredScore: the minimum competitive score minus the other clauses' maximum, stepped down one float ulp at a time until it is safe.

The finding, step by step

#
  1. Index 1,002 small documents with two FeatureField features and run a plain searcher.search(q, 1) for the conjunction +linear(a, 1.9999999) +linear(b, 1). Doc 0 scores exactly Float.MAX_VALUE (3.4028235E38); on doc 1001 the feature times the weight overflows, so it scores +Infinity. The rest score about 3.
  2. You expect doc 1001, the only +Infinity hit. An exhaustive search and Lucene 10.2.2 return it.
  3. After 1,000 hits the collector starts pruning. Ties go to the lower doc id, so a later document must beat 3.4028235E38: the minimum competitive score becomes nextUp(Float.MAX_VALUE), which is +Infinity.
  4. The bulk scorer turns that into a cut-off for partial scores: +Infinity - ulp(+Infinity) is NaN, and keeping only partial scores >= NaN keeps nothing. Doc 1001 is dropped and you get doc 0, with no error.
  5. Concurrent searches lose +Infinity ties the same way (docs 100, 101, 102 instead of 0, 1, 2). Every release from 10.3.0 to 10.6.0 fails the test; 10.2.2 passes.

Who is affected

#

Top-k conjunctions and disjunctions that reach the block-max filter step, even a plain IndexSearcher#search(q, n) with default settings, over documents whose scores overflow to +Infinity (large FeatureField values, huge finite boosts). Single-threaded it needs the k-th score to be exactly Float.MAX_VALUE; concurrent, k +Infinity hits in a later slice. Rare input; only hits scoring Float.MAX_VALUE or +Infinity are affected.

Mechanism, terms and numbers653 words

Lucene's top-k conjunctions (BlockMaxConjunctionBulkScorer) and disjunctions (MaxScoreBulkScorer) prune candidates with ScorerUtil.filterCompetitiveHits, which keeps a document only if its partial score is at least minRequiredScore(maxRemainingScore, minCompetitiveScore, n). When the minimum competitive score is +Infinity, that helper computes +Inf - R = +Inf, subtracts Math.ulp(+Inf) = +Inf and returns NaN; nothing is >= NaN, so every candidate is dropped, including documents that already score +Infinity.

TopScoreDocCollector asks for +Infinity itself: Math.nextUp(Float.MAX_VALUE) when the k-th best score is Float.MAX_VALUE, and the raw +Infinity from another slice in a concurrent search. So a plain single-threaded search(q, 1) returns doc 0 at Float.MAX_VALUE instead of doc 1001 at +Infinity, and a concurrent search can return the wrong documents among hits tied at +Infinity. No error is raised. It is a regression from a 10.3.0 speed-up (#14827 and a same-day follow-up); 10.2.2 is correct. The trigger is rare: scores must overflow to +Infinity, for example from very large FeatureField values or boosts near Float.MAX_VALUE. Starting the threshold from Float.MAX_VALUE for a +Infinity minimum fixes it.

The bug, step by step (main 645d4fe14a20)

#
  1. The collector asks for +Infinity. TopScoreDocCollector breaks ties by ascending doc id, so once it is pruning, a later document must score strictly more than the k-th best: it calls setMinCompetitiveScore(Math.nextUp(topScore)) (TopScoreDocCollector.java:154-164, nextUp at :160). For a k-th score of Float.MAX_VALUE that is +Infinity. In a concurrent search, a leaf with lower doc ids gets the raw score from another slice, without nextUp, so that its tied documents stay competitive (:137-152, :145); after k hits at +Infinity in that slice, that is +Infinity too.
  2. The bulk scorers turn it into a cut-off. Before adding each further clause, BlockMaxConjunctionBulkScorer.scoreWindowScoreFirst calls ScorerUtil.filterCompetitiveHits(buffer, sumOfOtherClauses[i], minCompetitiveScore, n) (BlockMaxConjunctionBulkScorer.java:182-191); MaxScoreBulkScorer.scoreNonEssentialClauses does the same (MaxScoreBulkScorer.java:452-458). These are the only callers.
  3. The cut-off is NaN. minRequiredScore (ScorerUtil.java:131-142) starts from minCompetitiveScore - maxRemainingScore = +Inf - R = +Inf (:133) and steps by Math.ulp(minCompetitiveScore) = +Inf (:135). The loop test minRequiredScore > 0 && (float) sumUpperBound(minRequiredScore + R, n) >= minCompetitiveScore is true (:136-138), so it computes +Inf - +Inf = NaN (:139); NaN > 0 is false, and NaN is returned (:141).
  4. NaN keeps nothing. filterCompetitiveHits returns early only if (minRequiredScore <= 0) (:158), which is false for NaN, and then VectorUtil.filterByScore keeps a document only if score >= NaN (:162-163; VectorUtil.java:601-620), which is never true. The batch is emptied and none of it is collected (BlockMaxConjunctionBulkScorer.java:194-197).

Exposure and likelihood291 words
  • Who can be hit. Top-k searches (ScoreMode.TOP_SCORES; IndexSearcher#search(Query, int) is enough) that run a top-level conjunction on BlockMaxConjunctionBulkScorer or a top-level disjunction on MaxScoreBulkScorer, over documents whose scores overflow to +Infinity, when the search reaches the filter step (the conjunction scorer skips it before a clause when two consecutive remaining-score bounds are equal, BlockMaxConjunctionBulkScorer.java:184-189). The inputs pass every check: FeatureField accepts any finite positive normal value (FeatureField.java:152-172) and linear weights in (0, 64] (:593-597); BoostQuery rejects only non-finite or negative boosts (BoostQuery.java:38-43), and the classic QueryParser accepts a 38-digit boost.
  • When. Single-threaded: the k-th best score is exactly Float.MAX_VALUE and a later document scores +Infinity. Concurrent: a slice with higher doc ids collects k hits at +Infinity first, so a slice with lower doc ids drops its +Infinity ties. A single-threaded search whose k-th score is already +Infinity shows nothing wrong.
  • Defaults. Default IndexWriterConfig and codec, an IndexSearcher without an executor, 1,002 documents. The rare part is the input.
  • What goes wrong. A silently wrong top-k, with assertions on and off: a +Infinity document loses to a Float.MAX_VALUE one, or the documented doc-id tie-break among +Infinity hits breaks. Hits below Float.MAX_VALUE rank correctly; no extra, deleted or filtered-out document ever appears (22 executed checks). With the stock collector the result is never empty: it raises the minimum to +Infinity only once a queue holds k hits whose k-th best scores Float.MAX_VALUE or more (TopScoreDocCollector.java:137-171). A custom collector that sets a +Infinity minimum before any hit collects nothing (0 of 300 in the first verifier's test).
  • Plausible patterns (API reachability only; no real-world use was observed). Boosts near Float.MAX_VALUE used as a "pin this first" sentinel, or unbounded FeatureField values.

Why it looks unintended

#
  • Scorable#setMinCompetitiveScore lets a scorer skip only documents whose score is less than the minimum. +Infinity is not less than +Infinity.
  • +Infinity is not declared invalid: TopScoreDocCollector lists only NaN and -Infinity as invalid, and it passes +Infinity as the minimum itself.
  • 10.2.2 returns the right hit. The change was a speed-up whose javadoc says a loose threshold "doesn't hurt correctness".
The full argument247 words
  • The contract. A scorer "may safely ignore all documents whose score is less than the given minScore" (Scorable.java:45-52). The minRequiredScore javadoc promises a value with (float) sumUpperBound(minRequiredScore + maxRemainingScore, n) <= minCompetitiveScore and says a non-optimal value "doesn't hurt correctness, it just means that these docs will be filtered out later" (ScorerUtil.java:123-130). NaN is no threshold, and here the documents are lost, not filtered later.
  • +Infinity is not declared invalid. TopScoreDocCollector names only Float.NaN and Float.NEGATIVE_INFINITY as invalid (TopScoreDocCollector.java:30-31); +Infinity was taken off that list in LUCENE-2271 (2010). That is an omission, not an affirmative guarantee, but the collector produces +Infinity itself (next point). The test framework's AssertingScorer never checks for infinity: it asserts not-NaN, >= 0 and <= the max score for scores (AssertingScorer.java:129-131), and not-NaN and non-decreasing from 0 for minimum scores (:63, :92-93). TestWANDScorer covers +Infinity max scores (testRandomWithInfiniteMaxScore, @Nightly, :828-836).
  • Lucene produces the +Infinity minimum itself, at TopScoreDocCollector.java:160 (nextUp) and :145 (the raw score that keeps lower-doc-id ties competitive).
  • A regression from a speed-up. 10.2.2 and 9.12.3 pass the same test. #14827 is listed under Optimizations in CHANGES 10.3.0; its review and the two same-day follow-ups discuss finite rounding only, and no comment, commit message, test or CHANGES entry mentions infinite or NaN scores. Upstream TestScorerUtil.testMinRequiredScore draws the minimum from random().nextFloat(), in [0, 1) (TestScorerUtil.java:100-104), so it never reaches this case.
The devil's-advocate check190 words

The strongest case for "intended": overflowing scores are degenerate. LUCENE-8016 (#9064, open since 2017) calls the infinite scores from boosts near Float.MAX_VALUE "trappy" and proposes bounding boosts; WANDScorer.scaleMinScore asserts Float.isFinite(minScore) (WANDScorer.java:112); FeatureField's linear function is "Expert", with "an expectation that a feature value is encoded in the index in a way that makes sense for scoring" (FeatureField.java:78-81); and the filterCompetitiveHits javadoc speaks of scores that "exceed" the minimum.

Why it fails: none of these is a documented precondition. LUCENE-8016 was never implemented, and BoostQuery and FeatureField accept the trigger inputs. The WANDScorer assert is an internal assumption that TopScoreDocCollector itself breaks (a separate bug, LFV-113). "Exceed" cannot mean that a +Infinity document must be dropped when the collector asks for exactly +Infinity, and 10.2.2 kept it. The study's reviewers rated the argument weak; it is about how rare the input is, which the low priority reflects. A later cross-model fact check of this doc (OpenAI GPT-5.6) rated it moderate: upstream could treat the fix as low-priority hardening, given the extreme inputs and no known production report, though it still judged the behaviour a real defect.

Suggested fix

#

Recommended Start the cut-off from Float.MAX_VALUE for a +Infinity minimum

In minRequiredScore, start from Float.MAX_VALUE when the minimum competitive score is +Infinity. The loop still compares against +Infinity, so it returns a finite cut-off below which no document can reach +Infinity. It passes the repro, the 2,340 tests of the core search package and :lucene:core:check.

-    double minRequiredScore = minCompetitiveScore - maxRemainingScore;
+    // With minCompetitiveScore = +Infinity, starting from it would give +Inf - ulp(+Inf) = NaN.
+    // Start from the largest finite float instead; the loop below still compares against +Inf.
+    float start =
+        minCompetitiveScore == Float.POSITIVE_INFINITY ? Float.MAX_VALUE : minCompetitiveScore;
+    double minRequiredScore = start - maxRemainingScore;
     // note: we want the float ulp in order to converge faster, not the double ulp
-    double subtraction = Math.ulp(minCompetitiveScore);
+    double subtraction = Math.ulp(start);

Start the cut-off from Float.MAX_VALUE for a +Infinity minimum (validated by the checks) (recommended)

#

In ScorerUtil.minRequiredScore (ScorerUtil.java:133-135). Finite minimums are unchanged; for an infinite maximum of the other clauses the start is -Infinity and nothing is filtered, as today when that maximum exceeds the minimum.

-    double minRequiredScore = minCompetitiveScore - maxRemainingScore;
+    // With minCompetitiveScore = +Infinity, starting from it would give +Inf - ulp(+Inf) = NaN.
+    // Start from the largest finite float instead; the loop below still compares against +Inf.
+    float start =
+        minCompetitiveScore == Float.POSITIVE_INFINITY ? Float.MAX_VALUE : minCompetitiveScore;
+    double minRequiredScore = start - maxRemainingScore;
     // note: we want the float ulp in order to converge faster, not the double ulp
-    double subtraction = Math.ulp(minCompetitiveScore);
+    double subtraction = Math.ulp(start);

Trade-offs

  • A top-k saturated at +Infinity now keeps and scores its +Infinity candidates, as the contract requires, so it costs about as much as exhaustive scoring: 13.9-17.3 ms against 12.2-17.8 ms for COMPLETE on 400,000 documents that all score +Infinity, where the buggy path took 3.5-3.8 ms because it discarded them (rough, best of 5 on a shared host).
  • Normal queries are unaffected: the new branch runs only for a +Infinity minimum.
  • The candidate fix used Float.isInfinite(minCompetitiveScore), which is also true for -Infinity; then the loop would step down from Float.MAX_VALUE about 2^24 times. Lucene's collectors never pass -Infinity, but == Float.POSITIVE_INFINITY keeps today's behaviour for it. From 0 to +Infinity the two forms are identical.

Downstream note

#

Not a Lucene security issue; downstream, an application that passes user-typed boosts to the classic QueryParser lets users reach the concurrent form, which only changes which of the hits tied at +Infinity come back.

How it was found

#

Semi-formal: while modelling the proof obligations of block-max pruning, an AI tool saw that the lemma "a partial score below minRequiredScore cannot reach the minimum" assumes a finite minimum. Evaluating the helper by hand at +Infinity gave NaN; a unit test on the stock jar confirmed it, and independent checkers then reproduced it with their own tests.

The method in full134 words

Method: semi-formal (a hypothesis formed while modelling, then witnessed by a tool), a hunt unit on WAND and block-max bounds.

  • While modelling WAND and block-max pruning bounds (SMT lemmas for WANDScorer's scaled-integer test, which assume finite scores), an AI tool reviewed the block-max filter by code reading: a document dropped by filterCompetitiveHits must not be able to reach the minimum competitive score. That obligation, like the earlier study's proof of the two helpers, presumes a finite minimum.
  • Evaluating minRequiredScore at +Infinity by hand gives +Inf - ulp(+Inf) = NaN, and filterByScore(NaN) keeps nothing. The signal came from code reading while modelling.
  • A JUnit on the stock main jar witnessed it (the helper and a forced-order concurrent search); an independent verifier found the simpler single-threaded form that the minimal test is cut down from.

History

#

A regression from the 10.3.0 speed-up #14827 (2025-07-03), widened the same day by the follow-up 3f71b54c47a, which gave today's NaN loop. The minimal test fails on all 8 releases from 10.3.0 to 10.6.0 and on main, and passes on 10.2.2 and 9.12.3. Not fixed upstream.

Versions tested8 rows

Introduced on 2025-07-03 in two steps, both first released in 10.3.0:

  1. #14827 "Pre-calculate minRequiredScore to speedup filterCompetitiveHits" (main 62e02760321, branch_10x 5687ed5e8a0; CHANGES 10.3.0, Optimizations) replaced the per-document test (float) sumUpperBound(score + R, n) >= minCompetitiveScore, which kept these documents, with a precomputed threshold. For a +Infinity minimum it returned +Infinity, so a document whose finite partial score would overflow to +Infinity was already dropped.
  2. The same-day follow-up "Improve test and address more test failures." (main 3f71b54c47a, branch_10x d0a4b104214, no PR) gave today's loop, which returns NaN, so documents already at +Infinity are dropped too. The minimal test fails from here on.

The commit in between, bf848a9a3ab "Fix test failures.", does not change the result for this input; commit-level runs (each commit's ScorerUtil and BlockMaxConjunctionBulkScorer over the 10.3.0 jars) show 13/13 correct before #14827, 7 of 19 wrong at #14827 and bf848a9a3ab, and 16 of 19 wrong from 3f71b54c47a on, as on every release. LFV-104, snapshot of 2026-11-05

Registry title
ScorerUtil.minRequiredScore returns NaN when the minimum competitive score is +Infinity, so block-max conjunctions and MaxScore disjunctions drop documents that score +Infinity
Area
search / top-k dynamic pruning (block-max conjunction and MaxScore bulk scorers)
Priority
Low, rank 951: A +Inf minimum competitive score turns minRequiredScore into NaN so block-max and MaxScore scorers drop +Inf docs, which only Float.MAX-scale pin-first boosts or overflowing FeatureField values produce.
Impact class
silent wrong results
Impact note
Applications whose top-k searches (a plain IndexSearcher#search(Query, int) is enough) run a top-level conjunction on BlockMaxConjunctionBulkScorer or a top-level disjunction on MaxScoreBulkScorer, with at least one clause whose maximum score is finite so that the filter step runs, over documents whose scores overflow to +Infinity (FeatureField linear queries on very large feature values, or very large finite boosts, including ones typed into the classic QueryParser): a single-threaded search goes wrong when the k-th best score is exactly Float.MAX_VALUE, a concurrent search when a slice with higher doc ids collects k +Infinity hits first; default IndexWriterConfig, codec and searcher; ordinary scale (a few thousand documents); rare input shape; released 10.3.0-10.6.0.
Summary
You run an ordinary top-k search, for example IndexSearcher#search(query, 1), with a two-clause conjunction or disjunction whose scores can overflow to +Infinity (two FeatureField linear queries over very large feature values, or two clauses with very large finite boosts). You expect the best documents first, +Infinity before Float.MAX_VALUE and ties by ascending doc id, as Lucene 10.2.2 returns them. Instead, once the minimum competitive score reaches +Infinity, ScorerUtil.minRequiredScore returns NaN and filterCompetitiveHits discards every remaining candidate, so the search silently returns doc 0 scoring Float.MAX_VALUE instead of doc 3000 scoring +Infinity (one thread, one segment), or docs 100, 101, 102 instead of the equally scored docs 0, 1, 2 (a concurrent search in which the slice with the higher doc ids finishes first).
