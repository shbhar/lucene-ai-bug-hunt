The opt-in polygon self-intersection check misses overlapping edges when they are horizontal or vertical

With checkSelfIntersections = true, XYShape and LatLonShape reject a ring that runs twice along the same slanted stretch but accept one that does so along a horizontal or vertical stretch, because a bounding-box shortcut skips the overlap test for them. The invalid ring gets the same triangles as with the check off, in every release since 9.1.0.

The finding in 30 seconds

#

The check compares pairs of ring edges. It first skips a pair when the two bounding boxes are disjoint or only touch (<=, >=), and only then runs the overlap test. A horizontal edge has a box of height 0, so two edges on one horizontal line always only touch, however much they overlap.

Background: what the check does

#
  1. createIndexableFields(name, polygon, true) asks the Tessellator to check the polygon before cutting it into triangles. The two-argument overload, the default, does not run this check.
  2. The check looks at pairs of ring edges. Two edges that cross raise "Polygon self-intersection"; two edges that lie on one line and overlap raise "Polygon ring self-intersection".
  3. To save work, it first skips pairs whose bounding boxes do not overlap, and this shortcut also skips boxes that only touch.

The finding, step by step

#
  1. Build the 6-point ring (x, y) (4,4) (1,1) (4,1) (2,0) (0,1) (2,1) as an XYPolygon and index it with XYShape.createIndexableFields("f", p, true), asking Lucene to check that it is valid.
  2. Two of its edges, (1,1)-(4,1) and (0,1)-(2,1), both lie on the line y = 1 and overlap for x from 1 to 2: the ring runs over that piece twice, so it is not a valid polygon.
  3. You expect IllegalArgumentException: Polygon ring self-intersection. The same ring rotated by 45 degrees gets exactly that: "Polygon ring self-intersection at lat=3.0 lon=1.0".
  4. Instead it is accepted: createIndexableFields returns the same 4 triangle fields as with the check off. Before testing two edges for overlap, the check skips every pair whose bounding boxes only touch, and two edges on one horizontal line have flat boxes (height 0) that always only touch.
  5. Vertical edges are missed the same way, and LatLonShape behaves the same; every release from 9.1.0 to 10.6.0 and main.

Who is affected

#

Only applications that turn on the opt-in check (checkSelfIntersections = true in createIndexableFields or createDocValueField) and index a ring that runs twice along the same horizontal or vertical stretch. The ring gets the same triangle fields as with the check off, and nothing throws. One 6-point ring is enough. Rare input, so priority Low.

Mechanism, terms and numbers605 words

XYShape.createIndexableFields(name, polygon, true) and its LatLonShape twin promise that "the validity of the provided polygon is checked". The check, Tessellator.checkIntersectionPoint, looks at pairs of ring edges: it first returns when the two edges' bounding boxes are disjoint or only touch (<=, >=, Tessellator.java:1016-1020), then rejects a proper crossing and, after that, two collinear overlapping edges ("Polygon ring self-intersection", :1051-1064). A horizontal edge has a box of height 0, so two edges on the same horizontal line always only touch, however much they overlap, and the overlap test never runs; vertical edges hit the same through the x tests. A ring that runs twice along the same horizontal or vertical stretch is therefore accepted and gets the same triangle fields as with the check off, while the same ring rotated by 45 degrees is rejected. It is a missing validation error of an opt-in check: nothing throws. It has been there since the check was added (#428, LUCENE-9538, first released in 9.1.0) and is in every release through 10.6.0 and on main; running the overlap test in the shortcut branch when the edges' x or y ranges overlap by a positive length fixes it.

The worked example

#
  • The repro ring is (4,4) (1,1) (4,1) (2,0) (0,1) (2,1). Its edges (1,1)-(4,1) and (0,1)-(2,1) lie on y = 1; both boxes have height 0, so max(aY) = 1 <= min(bY) = 1 and the method returns at :1020 before the overlap test.
  • Its 45-degree rotation (x, y) -> (x - y, x + y) (which also scales it by √2, keeping whole-number coordinates) makes the two edges slanted. Their boxes now overlap with positive area, the overlap test runs, and the ring is rejected with "Polygon ring self-intersection at lat=3.0 lon=1.0" for XY and lat/lon polygons. With the check off, the rotated ring tessellates without error.
  • The transpose (overlap on the vertical line x = 1) is accepted like the original.
  • The ring overlaps itself rather than crossing itself: no two edges properly cross, but it runs twice, both times in the same direction, along the piece of y = 1 from (1,1) to (2,1), where its two lobes meet: a clockwise lower lobe (0,1) (4,1) (2,0) (area 2) and a counter-clockwise upper lobe (1,1) (2,1) (4,4) (area 1.5). An invalid ring has no defined fill; for illustration, its 4 triangles add up to area 5.0, the two lobes to 3.5.

Why the shortcut has <=

#

GeoUtils.lineOverlapLine (GeoUtils.java:231-244) only checks that all four end points are collinear. The touching-box return is what keeps two collinear edges that merely meet at one point from being flagged. That is right for zero-length contacts, but for horizontal or vertical edges it also swallows overlaps of any length. Polygons with more than 80 points in total (outer ring and holes, :186-192) take the Morton path, which calls the same method (:993-1006).

Exposure and likelihood139 words
  • Who is hit. Applications that pass checkSelfIntersections = true to XYShape or LatLonShape createIndexableFields / createDocValueField (XYShape.java:96-112, LatLonShape.java:98-114) to reject invalid polygons.
  • Default vs opt-in. Opt-in: the two-argument overloads do not check. Assertions on or off make no difference.
  • Effect. A missing validation error. The invalid ring gets the same triangle fields as with the check off, so it is indexed as check = false would index it; the triangles cover area 5.0, more than the 3.5 of the ring's two lobes.
  • Scale. None needed: one 6-point ring.
  • Likelihood: rare. Axis-parallel edges are common (boxes, grid-aligned data), but a ring that overlaps itself is unusual input; no polygon in the eight upstream shape test classes run with the check forced on (two seeds) or in nightly TestTessellator reaches the case (other polygon tests were not run).

Why it looks unintended

#
  • The javadoc: "If checkSelfIntersections is set to true, the validity of the provided polygon is checked"; the Tessellator requires "No self intersections".
  • A dedicated overlap test rejects the same ring rotated by 45 degrees, which tessellates fine without the check.
  • Maintainers call the flag strict validation (#11690); its author wanted invalid polygons that still tessellate to fail.
The full argument156 words
  • The contract. XYShape.java:93-94 and LatLonShape.java:95-96: "If checkSelfIntersections is set to true, the validity of the provided polygon is checked with a small performance penalty." Tessellator.java:43-45: "Requires valid polygons: No self intersections". No best-effort wording.
  • The code and its test. The overlap branch (Tessellator.java:1051-1064) exists to reject collinear overlapping edges; upstream TestTessellator.testInvalidPolygonOverlap (TestTessellator.java:154-176) pins its message for slanted edges.
  • Maintainer statements. On lucene-solr#1907, the first version of this check, iverase wrote that a polygon can be invalid yet still tessellate: "IMHO I think we should fail in this case." On #11690 nknize wrote "we have API guardrails to enable or disable strict validation". On #11767 iverase wrote that with checkSelfIntersections set to true the Tessellator "will fail before getting to this place".
  • History. The shortcut came with the check (#428, which had no review comments) and was never discussed: nothing in the issue, the PR or the tests discusses axis-parallel overlaps.
The devil's-advocate check120 words

The strongest case: the check was added "so it can provide a more meaningful error" (#428) for shapes that cannot be tessellated, and the repro ring tessellates; Tessellator is @lucene.internal; and the lat/lon Polygon javadoc says a polygon "must not be self-crossing, otherwise may result in unexpected behavior" (Polygon.java:34).

Why it fails: the check already rejects the 45-degree rotation, which tessellates without error when the check is off, so it is a validator and not only a better error. The public entry point promises validity, XYPolygon has no self-crossing precondition, and the maintainers' own words call the flag strict validation. Both executed reviews by another model family (OpenAI GPT-5.6) rated the argument moderate and still voted real.

Suggested fix

#

Recommended Test the overlap of axis-parallel edges in the shortcut branch

When the box shortcut is about to skip a pair, still run the overlap test if both are ring edges and their x or y ranges overlap by a positive length (only horizontal or vertical overlaps can make it throw), then return. Validated: the repro passes, and TestTessellator, TestXYShape and TestLatLonShape pass (108 tests).

All options and trade-offs2 options · 523 words

Side effect of the recommended fix: check = true also starts rejecting axis-parallel "keyhole" rings, where a ring enters a hole along a cut and leaves along the same cut. Such a ring is accepted today; its 45-degree rotation is already rejected, so the fix makes the two consistent, but a committer may weigh it. Out of scope: two holes that share an axis-parallel piece of edge are accepted (a probe pair, and upstream testComplexPolygon21), while the probe pair rotated by 45 degrees is rejected. The devil's-advocate verifier traces that to hole elimination, which runs before the check, and the fix does not change it (executed). Holes that share slanted pieces with the outer ring are rejected today (testComplexPolygon17). Two equal axis-parallel holes, rejected today with "Unable to Tessellate shape", get "Polygon ring self-intersection" with the fix.

Trade-offs

Keeps the shortcut for zero-length contacts. Cost, not measured: a projection test for every pair of ring edges that takes the shortcut, and the four-orient lineOverlapLine call for every such pair whose x or y ranges overlap by a positive length, slanted pairs included (for example (0,0)-(2,1) and (1,5)-(3,6)); only a collinear horizontal or vertical overlap can make it throw. Rejects axis-parallel keyhole rings that pass today (see above). A cleaner shape of the same idea, a precise overlap test run before the shortcut, was not run.

How it was found

#

A proof-obligation audit of the Tessellator's contract asked whether the self-intersection check rejects every overlap of two ring edges, whatever their orientation. The box shortcut before the overlap test breaks that for horizontal and vertical edges. A one-test JUnit witnessed it on main; independent checks reproduced it with their own rings.

The method in full124 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for every pair of ring edges that overlap over a positive length, checkIntersectionPoint reaches the overlap test. The proof needs the box shortcut to return only for pairs whose overlap has zero length; that fails when both boxes are flat, which is exactly the horizontal or vertical case.
  • A one-test JUnit witnessed it on main with assertions on and off; a probe contrasted the ring with its transpose and its 45-degree rotation for XY and lat/lon polygons. An independent reproducer and two executed reviews by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier re-ran the repro.
