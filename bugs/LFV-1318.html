LongBitSet.or and LongBitSet.xor accept a longer set in the same 64-bit word and copy its bits past length() into the set

LongBitSet.or and xor compare word counts, not lengths, so a longer set ending in the same 64-bit word gets its bits past length() copied in: an empty 10-bit set ORed with a 64-bit set holding bit 20 reports nextSetBit(0) = 20. No Lucene production code calls them.

The finding in 30 seconds

#

A LongBitSet keeps its bits in 64-bit words. The bits of the last word past length(), its ghost bits, must stay 0, because cardinality, nextSetBit, equals and others read whole words. or/xor combine whole words, never clear those bits, and their only check counts words, not bits.

Background in three steps

#
  1. new LongBitSet(n) allocates ((n - 1) >> 6) + 1 64-bit words: a 10-bit set and a 64-bit set both use exactly one word.
  2. In a 10-bit set, bits 10-63 of that word are "ghost bits". The class keeps them 0, and cardinality, nextSetBit, intersects, equals and hashCode read whole words and trust that they are 0.
  3. a.or(b) and a.xor(b) work word by word: they OR or XOR b's words into a's words, as many as both have.

The finding, step by step

#
  1. Make other = new LongBitSet(64) with only bit 20 set, and an empty a = new LongBitSet(10). Both fit in one 64-bit word.
  2. Call a.or(other) (or a.xor(other)). You expect a to stay empty: other has no bit in 0-9, and a 10-bit set cannot hold bit 20. Refusing the call, as FixedBitSet.or does, would also be fine.
  3. or/xor only check that other has no more words than a (1 <= 1), then combine the whole word. Bit 20 lands in a's unused high bits, which must stay 0.
  4. Now a.nextSetBit(0) returns 20 and a.cardinality() returns 1, with assertions on and off, and a no longer equals an empty 10-bit set. Nothing is thrown.

Who is affected

#

Only application code that calls the @lucene.internal LongBitSet.or or xor itself, with a longer set whose extra bits fall in this set's last word. No Lucene production code calls them (only TestLongBitSet, with sets that are not longer), so no index, query or search result is affected. When hit, the result is silently wrong, assertions on or off.

Mechanism, terms and numbers510 words

A LongBitSet has a fixed length and stores its bits in 64-bit words; the unused high bits of its last word (the "ghost bits") must stay clear, and cardinality, nextSetBit, intersects, scanIsEmpty, equals, hashCode and ensureCapacity rely on that. or(other) and xor(other) combine whole words and check only assert other.numWords <= numWords. A longer other whose length ends in the same word passes that check, even with assertions on, and its bits at or above this set's length() are copied into the ghost bits. ORing a 64-bit set holding only bit 20 into an empty 10-bit set leaves nextSetBit(0) = 20 and cardinality() = 1, with no error. No Lucene production code calls LongBitSet.or or xor (only its unit test TestLongBitSet does, with sets that are not longer), and the class is @lucene.internal, so only application code that uses it directly is hit. Related row: LFV-1317, the same shape in FixedBitSet.xor(FixedBitSet).

The mechanism (main 5adff78bb168)

#
  1. A set of numBits bits uses numWords = bits2words(numBits) = ((numBits - 1) >> 6) + 1 words (LongBitSet.java:63-71, :79-83).
  2. The invariant: the "'extra' or 'ghost' bits must be clear (or they may provoke spurious side-effects)" (:85-88). verifyGhostBitsClear checks the last word above numBits (:105-121, "Some methods rely on this implicit assumption") and is asserted by the adopting constructor (:102), so by clone() (:421-425).
  3. Fix sites. or (:235-243) and xor (:245-253) assert other.numWords <= numWords, then combine words [0, min(numWords, other.numWords)) in whole. For a 10-bit set and a 64-bit set the check is 1 <= 1, word 0 of other (bits 0-63) is ORed in, and nothing masks this set's last word above numBits: other's bit 20 becomes ghost bit 20.
  4. The readers marked "Depends on the ghost bits being clear!" then see it: cardinality (:137-144) returns 1, nextSetBit (:191-209) returns index + numberOfTrailingZeros(bits[0] >> index) = 20, and intersects (:256-263), scanIsEmpty (:290-302), equals (:439-440) and hashCode (:445-453) are wrong too. ensureCapacity (:44-57) carries the words into the grown set, where bit 20 becomes a real member.
  5. Every write stays inside the backing long[]; only the set's contents are wrong.
  6. Not claimed: a longer set with more words (say 128 bits into 10 bits) is caught by the assert under -ea and, under -da, damages the shared last word the same way, like any other assert-only precondition. The claim is the same-word case, which is silent even with -ea.

Also wrong after the call (side probes, not the repro)

#
  • With the repro's input: equals(new LongBitSet(10)) is false; LongBitSet.ensureCapacity(a, 30) returns a set with get(20) true (its length is 320, the size of the grown backing array, not 30); a later clone() throws AssertionError under -ea.
  • With a 5-bit set and a 40-bit set holding bit 33: intersects(other) is true, scanIsEmpty() false, and hashCode differs from an empty 5-bit set's.
Exposure and likelihood200 words
  • Who: code that calls LongBitSet.or or LongBitSet.xor directly. The class is public but @lucene.internal (LongBitSet.java:26) and meant for more than 2.1B bits; the util package says its classes "are generally not intended for direct use by most applications" (package-info.java:21-23).
  • In Lucene: no production caller. The users on main (DocValuesConsumer, CheckIndex, DocValuesRangeIterator, the join module's GlobalOrdinals*, one sandbox query, the test framework) call neither method; the only test that does, TestLongBitSet, combines sets only when b0.length() <= b.length() (TestLongBitSet.java:144).
  • Trigger: other.length() > length() while both lengths end in the same 64-bit word, for example 10 vs 64 bits, or 70 vs 128 bits and sets of more than 2^31 bits (the cross-model reviewer's runs).
  • Effect: silent wrong counts, iteration, equality and hashing, and a real extra member after ensureCapacity. The wrong values come back at once; under -ea no assertion fires inside or/xor, only on a later call such as clone() (the ghost-bit check, LongBitSet.java:102) or an index-checked call like get(20) with the index nextSetBit reported (:147).
  • Since: 4.7.0 (2014); the recorded keyword searches found no report of it (see Prior reports).

Why it looks unintended

#
  • Javadoc: "this = this OR other" on a "BitSet of fixed length"; ghost bits "must be clear".
  • The 2014 author meant to refuse a longer set ("we silently discarded bits!"), but the committed assert counts words, so this input passes even with -ea.
  • FixedBitSet.or(FixedBitSet) throws IndexOutOfBoundsException for the same input.
The full argument208 words
  • Contract. or/xor javadocs say only "this = this OR other" / "this = this XOR other" (LongBitSet.java:235, :245), with no length rule. The class is a "BitSet of fixed length (numBits)" (:22), and the ghost bits "must be clear (or they may provoke spurious side-effects)" (:85-88). A 10-bit set that reports nextSetBit(0) = 20 breaks both.
  • The check was meant to refuse this input. When LUCENE-5440 (#6503) added LongBitSet and these methods, its author wrote (2014-02-11): "I added an assert to FBS.or/xor if the given set.length() was bigger than current – we silently discarded bits!" (FBS is FixedBitSet). The assert committed for both classes (87f987082b5, 2014-02-16) compares word counts instead of lengths, so this input passes it even with -ea, and the extra bits are kept as ghost bits instead of being refused.
  • The sibling refuses it. FixedBitSet.or(FixedBitSet) throws IndexOutOfBoundsException ("Range [0, 0 + 64) out of bounds for length 10") for a longer set, through orRange's Objects.checkFromIndexSize (FixedBitSet.java:477-481, :604-606, since #14134).
  • Under -ea the class's other guards do fire: set(20) on a 10-bit set and or with a two-word set throw AssertionError, while the one-word longer set goes through.
The devil's-advocate check199 words

"LongBitSet is @lucene.internal, the upstream test never passes a longer set, the 2014 author meant 'other must not be longer', and an assert-only class corrupts silently under -da anyway", from two reviews. The cross-model reviewer returned not real with confidence "high", because LongBitSet is an internal-only API, and rated the intended-behaviour argument itself "moderate". Its points: the class is @lucene.internal, the util package says its classes "are generally not intended for direct use by most applications", the upstream test combines sets only when b0.length() <= b.length() (TestLongBitSet.java:144), and the word-count assert is an imperfect enforcement of an assumed "not longer" precondition. The intended-behaviour review added the 2014-intent and assert-only points (set(20) on a 10-bit set under -da also corrupts). This narrows the bug but does not remove it: the precondition is written nowhere a caller can read, the only in-code statement of it, the assert, accepts this input with -ea while it rejects set(20) and a two-word set, and the outcome is the opposite of the recorded intent. @lucene.internal removes the API-stability promise, not correctness; this site lists other Low rows on these bit-set classes reached through public API (LFV-025, LFV-133, LFV-1298).

Suggested fix

#

Recommended A. Refuse a longer set, as FixedBitSet.or does (validated)

Recommended, A: refuse a longer set as FixedBitSet.or does, with Objects.checkFromIndexSize(0, other.numBits, numBits) at the top of or and xor (+13/-6 lines). Validated with gradle: the call throws IndexOutOfBoundsException, the exception form of the test passes with assertions on and off, and TestLongBitSet passes. B, masking the last word, also validated.

/**
 * this = this OR other
 *
 * @throws IndexOutOfBoundsException if {@code other} is longer than this set
 */
public void or(LongBitSet other) {
  Objects.checkFromIndexSize(0, other.numBits, numBits);
  int pos = Math.min(numWords, other.numWords);
  while (--pos >= 0) {
    bits[pos] |= other.bits[pos];
  }
}
// xor: the same javadoc line and check before its loop
All options and trade-offs3 options · 598 words

Three options. A and B were validated with gradle in a scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-05); C is by reading. The related row LFV-1317 (FixedBitSet.xor) needs a decision too, and its doc recommends masking there: FixedBitSet.xor(DocIdSetIterator) already drops bits at or above numBits on its generic path (FixedBitSet.java:620-623), so masking makes its two paths agree. Here the sibling FixedBitSet.or refuses a longer set and LongBitSet has no iterator path, so refusing is the closer match. A fix for both rows can keep that per-class difference, or use one policy for both (B here is the masking option).

A. Refuse a longer set, as FixedBitSet.or does (validated) (recommended)

#

Replace the word-count assert in or (LongBitSet.java:237-238) and xor (:247-248) by a length check, document it, and import java.util.Objects (+13/-6 lines):

/**
 * this = this OR other
 *
 * @throws IndexOutOfBoundsException if {@code other} is longer than this set
 */
public void or(LongBitSet other) {
  Objects.checkFromIndexSize(0, other.numBits, numBits);
  int pos = Math.min(numWords, other.numWords);
  while (--pos >= 0) {
    bits[pos] |= other.bits[pos];
  }
}
// xor: the same javadoc line and check before its loop

Trade-offs

  • Does what the 2014 author said the check was for, holds with assertions off, and matches FixedBitSet.or(FixedBitSet): same exception type and message ("Range [0, 0 + 64) out of bounds for length 10").
  • A behaviour change: a caller that passes a longer set now gets an exception instead of a silent result. No production caller in Lucene; a GitHub code search found no downstream caller (Elasticsearch uses LongBitSet only through set, and and clear), which covers the code that search reaches, not every downstream user. One comparison per call.
  • The regression test becomes the same test asserting the exception: expectThrows(IndexOutOfBoundsException.class, () -> new LongBitSet(10).or(other)), and the same for xor.

What the checks validated

  • Stock: the repro fails with assertions on and off. With A, the unchanged repro stops at the first call with IndexOutOfBoundsException at LongBitSet.or, and the exception form of the test passes, on and off.
  • TestLongBitSet plus the test with -Ptests.iters=5: 60 runs, 0 failures, 5 skipped (testHugeCapacity is @Monster).
  • :lucene:core:checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain, forbiddenApisTest: pass. Not run: the full lucene/core suite (no other test calls these methods).

B. Clear the ghost bits after the whole-word OR/XOR (validated)

#

After each loop, when other.numWords >= numWords && numWords > 0, run bits[numWords - 1] &= -1L >>> -numBits (a private helper, +9 lines).

private void clearGhostBitsOfLastWord(LongBitSet other) {
  if (other.numWords >= numWords && numWords > 0) {
    bits[numWords - 1] &= -1L >>> -numBits;
  }
}

Trade-offs

  • Keeps the methods lenient: bits at or above length() are dropped, the "silently discarded bits" the 2014 author wanted to avoid. Keeps the word-count assert for longer sets with more words.
  • The repro passes unchanged and is the regression test. One masked word per call.

What the checks validated

  • The repro passes with assertions on and off; TestLongBitSet plus the test with -Ptests.iters=5: 60 runs, 0 failures, 5 skipped; the same five lint and format checks pass.

C. Remove the two methods

#

No Lucene production code calls LongBitSet.or or xor; the unit test TestLongBitSet calls both (TestLongBitSet.java:160, :162). In LUCENE-6427 (#7486) a committer noted that FixedBitSet.xor was unused and said they would "have a look at removing unused stuff later".

Trade-offs

An API removal, even if on an @lucene.internal class; outside callers would have to write the loop themselves, and TestLongBitSet would need rewriting. By reading, not run.

Downstream note

#

Downstream code that combines LongBitSets of different lengths itself gets silently wrong sets; no query, document or index input reaches these methods through Lucene.

How it was found

#

Semi-formal: a proof-obligation audit of LongBitSet's contract. The ghost-bit invariant must hold after every mutating method, here or/xor with any set their check accepts. A longer set that ends in the same word passes the check and breaks the invariant; a JUnit test on stock main witnessed it.

The method in full92 words
  • Obligation: after or(other) or xor(other) with any other the methods accept, the bits of this set's last word at or above numBits are still 0 (LongBitSet.java:85-88, :105-121).
  • Finding: the only guard is assert other.numWords <= numWords (:237, :247), and the loops combine whole words with no mask, so any other with length() > length() in the same number of words breaks the obligation.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

core / util: LongBitSet (or, xor)

Impact note

Summary
You make a 10-bit LongBitSet and a 64-bit LongBitSet other with only bit 20 set, and call or(other) (or xor(other)) on the 10-bit set. You expect the 10-bit set to stay empty, because other has no bit in [0, 10) and the class keeps the bits past length() (its 'ghost bits') clear, which cardinality, nextSetBit, intersects, equals and hashCode rely on. Instead or/xor combine whole 64-bit words and check only that other has no more words (both have one, and the check is an assert), so bit 20 lands in the set's word: cardinality() returns 1 and nextSetBit(0) returns 20 for a set of length 10, with no error.
