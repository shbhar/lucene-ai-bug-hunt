A reused IntsRefFSTEnum returns a wrong seekCeil/seekFloor after a term with label Integer.MAX_VALUE

A reused IntsRefFSTEnum on [3, Integer.MAX_VALUE] answers seekCeil([3]) with [3, MAX] and seekFloor([3]) with null, although [3] is in the FST: it compares labels by subtraction, and MAX - (-1) overflows. With in-range seek targets, only expert-API users who store that label are hit; every release since 3.3.

The finding in 30 seconds

#

Background: FST enumerators and seeking

#
  1. An FST maps sorted keys to outputs. With input type BYTE4 a key is a sequence of int labels, each any value >= 0. Lucene's own BYTE4 FSTs (synonyms, stemmer overrides, hunspell) store Unicode code points.
  2. IntsRefFSTEnum walks the keys in order, like a SortedMap iterator. seekCeil(t) moves to the smallest key >= t; seekFloor(t) to the largest key <= t.
  3. The same enum can seek again, forward or backward. To save work it first keeps the labels its current key shares with the new target, then searches only the rest. Where the target has no more labels, the enum uses the marker label -1 (END_LABEL).

The finding, step by step

#
  1. Build a BYTE4 FST with two keys: [3] -> 1 and [3, 2147483647] -> 2. 2147483647 is Integer.MAX_VALUE, a legal BYTE4 label.
  2. On one IntsRefFSTEnum, call seekCeil([3, MAX]): it correctly lands on [3, MAX]. Then call seekCeil([3]) on the same enum.
  3. You expect [3] with output 1: it exists, so it is its own ceiling, and a fresh enum returns exactly that.
  4. Instead you get [3, MAX] with output 2, and seekFloor([3]) returns null. No error, with assertions on or off.
  5. Why: to reuse its position, the enum compares its current label with the target's label by subtracting them. The target [3] has run out, which the enum marks as label -1, and 2147483647 - (-1) wraps to -2147483648. So the enum thinks the target lies ahead and keeps the MAX arc.

Who is affected

#

With in-range seek targets, only application code that puts the label Integer.MAX_VALUE into its own BYTE4 FST and reuses one IntsRefFSTEnum to seek back to a prefix of its current key; also a reused enum given a target with a huge negative label. No Lucene component does either. Every release from 3.3 to 10.6.0.

Mechanism, terms and numbers613 words

IntsRefFSTEnum.seekCeil and seekFloor begin with FSTEnum.rewindPrefix(), which keeps the part of the current term that the new target shares and decides, label by label, whether to seek forward or reset to the node's first arc. It decides with final int cmp = getCurrentLabel() - getTargetLabel(); (FSTEnum.java:79 at 5adff78bb168). Once the target is used up, getTargetLabel() returns FST.END_LABEL, -1 (IntsRefFSTEnum.java:91-97). If the current label there is Integer.MAX_VALUE, a legal BYTE4 label, 2147483647 - (-1) wraps to Integer.MIN_VALUE, the code takes the "seek forward" branch and keeps the MAX arc. In the BYTE4 FST {[3] -> 1, [3, MAX] -> 2}, an enum positioned on [3, MAX] answers seekCeil([3]) with [3, MAX] and seekFloor([3]) with null; a fresh enum answers both correctly. The line dates from 2011 (LUCENE-2843) and is in every release from 3.3 to 10.6.0. No Lucene component builds a BYTE4 FST with that label; the fix is one Integer.compare.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/fst/)

#
  1. IntsRefFSTEnum.seekCeil (IntsRefFSTEnum.java:60-65) stores the target and calls doSeekCeil, which first calls rewindPrefix() (FSTEnum.java:136) "to match the shared prefix between current term and target term" (:66).
  2. rewindPrefix (FSTEnum.java:67-94) walks positions upto = 1, 2, ... of the current term and at :79 (the fix site) computes cmp = getCurrentLabel() - getTargetLabel(). cmp < 0 ("seek forward") breaks and keeps the current arc (:80-83); cmp > 0 ("seek backwards") resets this position to the node's first arc (:84-89).
  3. Current term [3, MAX], target [3]. Position 1: 3 - 3 = 0, go on. Position 2: the target is used up, so getTargetLabel() returns FST.END_LABEL = -1 (IntsRefFSTEnum.java:93-94; FST.java:139). The right answer is MAX > -1, reset. But 2147483647 - (-1) = 2147483648 does not fit in an int and wraps to -2147483648, so cmp < 0 and the MAX arc is kept.
  4. doSeekCeil's scan (FSTEnum.java:139-161) continues from the kept arc with target label -1. On this list-encoded node doSeekCeilList sees label MAX > -1 and calls pushFirst() (:286-288), which completes [3, MAX]. After a reset, the node's first arc would be the final (END_LABEL) arc, which matches -1 and gives [3].
  5. doSeekFloor calls the same rewindPrefix (:328): seekFloor([3]) returns null (executed). doSeekExact also calls it (:653) but then finds the arc with findTargetArc, so seekExact is correct (executed). Positioning on [3, MAX] with two next() calls instead of seekCeil triggers it too (executed).

Why only this one value (with in-range targets)

#

The labels an FST stores are >= 0 (asserted in FSTCompiler.java:581 and :1109; Java asserts only, so nothing checks it with assertions off), and a target made of such labels adds only END_LABEL = -1 as a negative value, so the subtraction can overflow only for Integer.MAX_VALUE - (-1). With label 0x7ffffffe the same reused-enum sequence is correct: reusedCeil=[3]/1 reusedFloor=[3]/1; with 0x7fffffff: reusedCeil=[3 7fffffff]/2 reusedFloor=null. BytesRefFSTEnum labels are 0-255 and cannot overflow.

Out-of-range targets. seekCeil/seekFloor do not check the target: getTargetLabel() returns the caller's own ints (IntsRefFSTEnum.java:96), and no javadoc states a label range for seek targets. A target label at least 2^31 below the current label wraps the same line. On the BYTE4 FST {[1] -> 1, [3] -> 2} (no MAX label), an enum first positioned by seekCeil([3]) answers seekCeil([Integer.MIN_VALUE]) and seekCeil([-2147483645]) with [3]/2, while a fresh enum gives [1]/1; -2147483644 (no wrap) is correct; the Integer.compare line fixes both (executed). A side remark, not a second repro.

Exposure and likelihood218 words
  • Who. Application code that builds its own BYTE4 FST containing the label Integer.MAX_VALUE and reuses one IntsRefFSTEnum to seekCeil or seekFloor to a proper prefix of its current term whose next label is that MAX label. Two keys suffice; no scale, default settings. Outside the label range, also code that seeks a reused IntsRefFSTEnum with a target holding a huge negative label (seekCeil, executed).
  • Effect. A silent wrong lookup: seekCeil returns a term (and its output) that is not the ceiling; seekFloor returns null for a target that exists. Same with assertions on and off.
  • Not affected. Lucene's BYTE4 FSTs hold code points <= 0x10FFFF (SynonymMap.java:244, StemmerOverrideFilter.java:214, hunspell Dictionary.java:648 in lucene/analysis/common). The only non-test IntsRefFSTEnum user, hunspell WordFormGenerator.java:68-71, calls next() only. The codecs' term readers use BytesRefFSTEnum (byte labels). A fresh enum and seekExact are correct.
  • Opt-in part. FST, FSTCompiler and IntsRefFSTEnum are @lucene.experimental (FST.java:62, FSTCompiler.java:68, IntsRefFSTEnum.java:26).
  • Likelihood: rare. No caller found does it and no public report of it was found since 2011. It is deterministic, though: whoever uses MAX as a label, reuses the enum and then seeks to a proper prefix whose next current label is MAX gets the wrong answer every time; other in-range seeks after a MAX term compare without overflow.

Why it looks unintended

#
  • seekCeil promises the "smallest term that's >= target" and seekFloor the "biggest term that's <= target", with no fresh-enum rule; a fresh enum is correct.
  • INPUT_TYPE documents the "allowed range of each int input label"; BYTE4 accepts any label >= 0.
  • Backward seeks are designed: rewindPrefix has a seek-backwards branch, and Lucene's FST tests reuse one enum for random-order seeks.
The full argument238 words
  • Contract. IntsRefFSTEnum.java:59: "Seeks to smallest term that's >= target"; :67: "Seeks to biggest term that's <= target". The package doc says the enumerators "behave like SortedMap iterators" (package-info.java:30-32) and "Like TermsEnum, this also supports seeking (advance)" (:73).
  • Legal label. FST.java:68: INPUT_TYPE "Specifies allowed range of each int input label for this FST". FSTCompiler.writeLabel asserts BYTE1 <= 255 and BYTE2 <= 65535 but for BYTE4 only v >= 0, written as a vInt (FSTCompiler.java:580-590; Java asserts, not run-time checks). Input order is IntsRef.compareTo, a signed Arrays.compare (IntsRef.java:106-107), so MAX is just the largest label. Michael McCandless described the input type the same way on LUCENE-3695 (#4769): "The "INPUT_TYPE" really describes the allowed range of the input int labels", and "FST is just like a SortedMap".
  • Backward seeks. rewindPrefix exists to reuse the current position and has a "seek backwards -- reset this arc to the first arc" branch (FSTEnum.java:84-89). FSTTester in the test framework reuses one IntsRefFSTEnum for seekCeil, seekFloor and seekExact on random targets in random order (FSTTester.java:420-520), only with byte and code-point labels, so it never reaches the overflow.
  • History. Before LUCENE-2843 the forward-only advance(target) (never released) said "NOTE: target must be >= where we are already positioned"; LUCENE-2843 replaced it with seekCeil/seekFloor without such a note. No commit, issue or PR since calls the subtraction deliberate.
The devil's-advocate check143 words

The strongest case for "intended": the Builder javadoc says strings are represented as BYTE4 "full unicode codepoints" (FSTCompiler.java:253-255), every in-tree BYTE4 FST stays <= 0x10FFFF, the API is @lucene.experimental, and IntsRef itself is @lucene.internal (IntsRef.java:25); so labels near 2^31 are off-label.

Why it fails: the same javadoc says the input type "Can be anything from INPUT_TYPE enumeration"; the code-points sentence is an example of use, and no narrower BYTE4 range is documented or enforced. @lucene.experimental allows API changes, not wrong answers; IntsRefFSTEnum's public seek methods take an IntsRef, so every caller of them builds one; and the failure is silent rather than a clear rejection. The cross-model reviewer rated this case moderate and rejected it, as did the independent reproducer, the devil's-advocate verifier and the adjudication. A maintainer who prefers to restrict labels has fix B.

Suggested fix

#

Recommended Compare, do not subtract (fix A)

Compare the labels with Integer.compare(getCurrentLabel(), getTargetLabel()) instead of subtracting them: one line in FSTEnum.rewindPrefix. The repro passes with assertions on and off, and the selected FST and FST-based postings-format suites show 0 failures (188 tests, 43 skipped). Open PR #14477 rewrites the same loop.

-      final int cmp = getCurrentLabel() - getTargetLabel();
+      final int cmp = Integer.compare(getCurrentLabel(), getTargetLabel());
All options and trade-offs2 options · 491 words

Fix A was built and checked through gradle on 5adff78bb168; B was not run. Open PR #14477 ("Use Arrays#mismatch in FSTEnum#rewindPrefix", a performance change) keeps getCurrentLabel() - getTargetLabel() for the first mismatching label, so the same change belongs there if it lands first. Open PR #12688 copies the compare into a new PrimitiveLongFSTEnum that only sees byte labels and cannot overflow, so a change there would only be for consistency. Scope: fix A covers the in-range case (MAX against END_LABEL) and the executed out-of-range negative-target case (a list-encoded root node). On array-encoded nodes the seek code does more label arithmetic on the target (FSTEnum.java:166, :196, :362, :393, :507, :529; FST.java:1047, :1068, :1085; Util.java:917), which was not tested with such targets; whether seek targets must hold labels >= 0 is for the maintainers to state, as nothing documents or checks it today.

Compare, do not subtract (fix A) (validated by the checks) (recommended)

#

In FSTEnum.rewindPrefix (FSTEnum.java:79), replace the subtraction with Integer.compare.

-      final int cmp = getCurrentLabel() - getTargetLabel();
+      final int cmp = Integer.compare(getCurrentLabel(), getTargetLabel());

Trade-offs

No functional change for any pair of labels that does not overflow: the sign is the same as before. Not benchmarked; the JMH FSTEnumSeekBenchmark of open PR #16095 could measure it.

Restrict BYTE4 labels (fix B, not recommended) (not run)

Downstream note

#

Downstream code that uses Integer.MAX_VALUE as a label in its own BYTE4 FST and reuses an IntsRefFSTEnum would silently get wrong ceiling and floor lookups, as would code that passes a seek target with a huge negative label to a reused enum; no Lucene component builds such an FST or seeks an IntsRefFSTEnum.

How it was found

#

A proof-obligation audit of FSTEnum's seek contract: for every label >= 0, a seek on a reused enum must match a fresh enum. It fails where an int subtraction stands in for a comparison, at one in-range pair, MAX against the end marker -1; a JUnit test witnessed it. A later fact check: huge negative target labels wrap too.

The method in full161 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked rewindPrefix against the obligation that seekCeil/seekFloor on a reused enum equal the fresh-enum answer for every label BYTE4 accepts (any v >= 0) and found that cmp = getCurrentLabel() - getTargetLabel() changes sign for Integer.MAX_VALUE - (-1).
  • The finder then wrote a JUnit test and the one-line Integer.compare fix that makes it pass; the repro was later cut to a single method with two keys.
  • An independent reproducer, an executed cross-model review and a devil's-advocate verifier reproduced it with their own tests, and an adjudication re-ran the finder's and the reproducer's tests ("Prior reports, history and checks").
  • The audit took target labels to be >= 0 as well. The doc's fact check later ran a reused enum with a huge negative target label (Integer.MIN_VALUE) and showed that it wraps the same line; the same fix covers that run.

LFV-1147, snapshot of 2026-11-08

Registry title
A reused IntsRefFSTEnum gives wrong seekCeil/seekFloor results after visiting a term with label Integer.MAX_VALUE, because FSTEnum.rewindPrefix compares labels by subtraction and it overflows
Area
util / FST (FSTEnum.rewindPrefix label compare; IntsRefFSTEnum seekCeil/seekFloor)
Priority
Low, rank 944: A reused IntsRefFSTEnum returns a wrong seekCeil or seekFloor result after a term with the label Integer.MAX_VALUE, in every release since 3.3. It needs that exact label in an application-built BYTE4 FST of the expert FST API, which no Lucene caller uses, so its reach is very narrow.
Impact class
minor
Impact note
Only application code that uses the expert, @lucene.experimental FST API directly is hit: in a BYTE4 FST that holds the label Integer.MAX_VALUE, an IntsRefFSTEnum reused to seek to a proper prefix of its current term whose next label is that MAX label silently gets a term above the ceiling from seekCeil, or null from seekFloor although the target exists, with -ea and -da; tiny input, no scale needed, default settings otherwise; no in-tree caller can reach it (in-tree BYTE4 FSTs hold code points, BytesRefFSTEnum labels are <= 255, seekExact is not affected); every release since 3.3 and main.
Summary
You build a BYTE4 FST with [3] -> 1 and [3, Integer.MAX_VALUE] -> 2, move one IntsRefFSTEnum to [3, MAX] with seekCeil, then call seekCeil([3]) on the same enum; you expect [3], the smallest term >= [3], as a fresh enum returns. Instead it returns [3, MAX] (and seekFloor([3]) returns null), with or without assertions.
