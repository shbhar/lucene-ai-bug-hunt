Similarity-threshold vector queries with traversalSimilarity == resultSimilarity skip documents that score exactly the threshold

With traversalSimilarity equal to resultSimilarity (what the short constructors do), FloatVectorSimilarityQuery and ByteVectorSimilarityQuery can skip documents that score exactly the threshold once they have found a document at or above it: in the runs, looking up exact copies of a vector returned 1 of 2, or 1 of 6 on an HNSW graph. Affects 9.10.0-10.4.0, 10.5.2 and main.

The bug in 30 seconds

#

A similarity-threshold query should return every document whose similarity to the target is at least resultSimilarity. The collector counts a score equal to the threshold as a hit, but then reports that same value as the bound at or below which nothing is worth looking at, and the search code skips scores equal to the bound.

  1. Index 65 vectors with the default codec. Docs 0 and 64 are exact copies of the query vector [1, 2], so their EUCLIDEAN similarity is 1.0, the highest possible; the other 63 vectors are far away.
  2. Ask for every document with similarity >= 1.0: new FloatVectorSimilarityQuery.Explicit("v", target, 1.0f), which sets traversalSimilarity = resultSimilarity = 1.0. You expect docs 0 and 64.
  3. You get only doc 0, and count() is 1, although explain(query, 64) says "Score above threshold". On a 3,000-vector segment with an HNSW graph and 6 exact copies you get 1 of the 6.
  4. Why: after doc 0 the collector reports 1.0 as its minimum competitive score, and the search treats a score equal to that bound as not worth collecting. Doc 64 sits alone in the second batch of 64 scored vectors, whose best score is not > 1.0, so it is skipped; the graph search likewise accepts only scores above 1.0.
  5. The same query with traversalSimilarity one step lower (Math.nextDown(1f)) returns every copy, and on this segment every vector is scored, so this is not a graph-approximation miss. The fix is one line in the collector.

Who is affected

#

Callers that set traversalSimilarity equal to resultSimilarity: the short constructors in 9.10.0-10.4.0, the deprecated Explicit classes in 10.5.2 and main. It needs an exact score tie, which is routine for exact-duplicate lookups (EUCLIDEAN 1.0), byte vectors, or a threshold copied from a document's score. Default codec, no error; from 10.4.0 a segment needs at least 65 vectors.

Mechanism, terms and numbers846 words

A similarity-threshold vector query (FloatVectorSimilarityQuery, ByteVectorSimilarityQuery) returns every document whose similarity to the target is at least resultSimilarity; traversalSimilarity controls how far the search explores. The constructors without a traversal argument, (field, target, resultSimilarity[, filter]), set the two equal: the plain constructors in 9.10.0-10.4.0, the deprecated Explicit classes in 10.5.2 and main (the full forms behave the same when given equal values). Then, once the collector has seen a hit at exactly the threshold t, its minCompetitiveSimilarity() = min(traversalSimilarity, maxSimilarity) equals t, and every consumer treats a score equal to that bound as not competitive: the exhaustive scan of a segment without a graph collects a 64-vector batch only if its best score is > the bound, and the HNSW graph search accepts only scores >= nextUp(bound). So later documents at exactly t can be silently dropped (without a graph, those in a later batch that holds no better score; on a graph, those met after the first hit), although the query's own collect(), explain() and exact fallback all count them. On 65 vectors with exact copies of the target at docs 0 and 64 (EUCLIDEAN, t = 1.0) the query returns [0]; on a 3,000-vector HNSW segment with 6 copies, 1 of 6; with traversal one ulp lower, all of them. It needs an exact score tie, which is routine for exact-duplicate lookups, byte vectors and thresholds copied from a document's score. The fix is one line: Math.min(Math.nextDown(traversalSimilarity), maxSimilarity).

Terms

#
  • Similarity-threshold query: FloatVectorSimilarityQuery / ByteVectorSimilarityQuery (@lucene.experimental, "Search for all (approximate) float vectors above a similarity threshold"). resultSimilarity is the score a document must reach to be returned; traversalSimilarity (<= resultSimilarity) controls how far the HNSW graph is explored. The constructors without a traversal argument, (field, target, resultSimilarity[, filter]), pass resultSimilarity for both; the full forms (field, target, traversalSimilarity, resultSimilarity[, filter]) take both values. On 10.5.2 and main these are the deprecated Explicit classes ("Equivalent to the FloatVectorSimilarityQuery constructors in Lucene 10.4 and earlier"), next to the Adaptive classes, which are not affected. In 10.5.0 and 10.5.1 the plain constructors are adaptive (#15784); the nested Adaptive and Explicit classes first appear in 10.5.2 (#16654/#16671).
  • EUCLIDEAN similarity: 1 / (1 + squared distance), so 1.0 means "identical to the target" and nothing scores higher.
  • minCompetitiveSimilarity(): the KnnCollector method that the vector readers and the HNSW searcher ask for the score below which candidates are not worth visiting. Its javadoc says only "When full, the minimum score should be returned"; every consumer treats a score equal to it as not competitive, which is right for top-k collectors.

The bug

#
  1. The short constructors set traversalSimilarity = resultSimilarity = t (FloatVectorSimilarityQuery.java:182-183, :194-195; ByteVectorSimilarityQuery.java:181-182, :193-194). Only traversal > result is rejected.
  2. ExplicitVectorSimilarityCollector.collect() keeps similarity >= resultSimilarity (:59) and tracks the best score seen (:58); minCompetitiveSimilarity() returns Math.min(traversalSimilarity, maxSimilarity) (:66-67). After the first hit at exactly t, that is t.
  3. Segments without a graph (with the default format, fewer than 648 vectors; from 10.4.0): Lucene99HnswVectorsReader scores vectors in batches of 64 and collects a batch only if bulkScore(...) > minCompetitiveSimilarity() (:396, :408). A later batch whose best score is exactly t is skipped. Ties inside a collected batch are kept, so on this path it takes at least 65 vectors (a segment with a graph can lose a tie with a few vectors: 3 in a run with a forced graph). The scalar-quantized reader has the same gate (Lucene104ScalarQuantizedVectorsReader.java:390, :402).
  4. Segments with a graph (every affected release): HnswGraphSearcher accepts a neighbour only if score >= Math.nextUp(minCompetitiveSimilarity()) (:304, :347, :352) and skips a scored batch unless its best is > the bound (:341-343). Every node at exactly t met after the first hit is neither collected nor explored. A filter does not change this: the query pins KnnSearchStrategy.Hnsw(0) (AbstractVectorSimilarityQuery.java:48), so FilteredHnswGraphSearcher is never chosen (HnswGraphSearcher.java:139-145, KnnSearchStrategy.java:80-82) and the same searcher runs with acceptOrds.
  5. The query's other paths count the dropped document: explain() says "Score above threshold" for score >= resultSimilarity (AbstractVectorSimilarityQuery.java:175-176), and the exact fallback keeps score >= threshold (:363).

Exposure and likelihood487 words
  • Who is exposed. Code that builds a similarity-threshold query with traversalSimilarity equal to resultSimilarity: the plain constructors without a traversal argument in 9.10.0-10.4.0 (the short, non-deprecated forms (field, target, resultSimilarity[, filter])), [Float|Byte]VectorSimilarityQuery.Explicit with those arguments in 10.5.2 and main (deprecated), or a full form (field, target, traversalSimilarity, resultSimilarity[, filter]) with equal values. Not 10.5.0 or 10.5.1 (adaptive collector, no Explicit), not the Adaptive queries, not Float16VectorSimilarityQuery, and not any call with traversal strictly below result.
  • What it takes. A document scoring exactly the threshold after another vector at or above it was collected in the same segment (without a graph, only in a later 64-vector batch that holds no better score). Exact-duplicate lookup at EUCLIDEAN 1.0 always qualifies (nothing scores above 1.0, so every further copy is a tie); byte vectors give many equal scores; so does a threshold copied from a known document's score. For float embeddings with an arbitrary threshold an exact tie is very unlikely.
  • How much is lost. On a segment with a graph, every tie met after the first hit: 1 of 6 and 1 of 12 copies in the runs. On a segment without a graph (fewer than 648 vectors with the default format, from 10.4.0), a tie in a later 64-vector batch that holds no better vector. Rarely an above-threshold document reachable only through tied graph nodes goes too: in a 120-query check, 11 of 6,699 missing documents were above the threshold, and the fix recovered all 11 (attributed to tied nodes, inferred).
  • Silent and inconsistent. No error; count() matches the short hit list, while explain() says the missing documents match. The answer changes with document order, with an all-matching filter (no-graph segments in which every document has a vector, 10.4.0 on) and with a one-ulp change of traversalSimilarity. As a MUST_NOT clause, a tied document is not excluded (64 hits instead of 63).
  • Settings and size. Default codec, directory and IndexSearcher. From 10.4.0 a segment needs at least 65 vectors: below 648 it has no graph and is scanned in 64-vector batches, and ties in the first collected batch are kept. Smaller segments are hit only when they have a graph: with a format whose tiny-segment threshold is 0 (executed with 3 vectors), or on 9.10.0-10.3.2, which had no tiny-segment threshold (read; not run below 65 vectors). The scalar-quantized formats have the same gate; a random hunt hit them, but no dedicated test targets them.
  • Downstream. Solr's vector-similarity parser defaults minTraverse to -Infinity (not affected), but a request may set minTraverse equal to minReturn, and an open Solr issue (SOLR-17713) shows a user doing that. The OpenSearch k-NN plugin uses the Adaptive query or 0.95 x threshold (not affected); no Elasticsearch use was found.
  • How likely. Rare: it needs both the equal-thresholds setting and an exact tie, and no public report was found in the two and a half years since 9.10.0 (released 2024-02-20).

Why it is a bug, not intended

#
  • The query's own code counts a tie as a match: collect() and the exact fallback use >=, and explain() says "Score above threshold".
  • Every vector of the 65-vector segment is scored, and a traversal one step lower returns every copy: not a graph-recall miss.
  • The strict tie rule was made for top-k (#12770) while this query (#12679) was in review.
The full argument376 words
  • Contract text. Collector javadoc (ExplicitVectorSimilarityCollector.java:35-37): "The graph is traversed till better scoring nodes are available, or the best candidate is below {@link #traversalSimilarity}. All traversed nodes above {@link #resultSimilarity} are collected." A tie is not "below". collect() (:59) uses >=; explain() (AbstractVectorSimilarityQuery.java:175-176) returns "Score above threshold" for score >= resultSimilarity; the exact fallback (:363) uses score >= threshold.
  • Release notes. The 9.10.0 CHANGES entry for #12679: "find all vectors scoring above a resultSimilarity while traversing the HNSW graph till better-scoring nodes are available, or the best candidate is below a score of traversalSimilarity in the lowest level."
  • Upstream tests. TestVectorSimilarityCollector.testExplicitResultCollection (:53-85) expects node 4 (score 0.5) at resultSimilarity 0.5 under "All nodes above resultSimilarity appear in order of collection" (:76-78). BaseExplicitVectorSimilarityQueryTestCase.testVectorsAboveSimilarity builds the expected set with score >= resultSimilarity (:404) and asserts all are returned (:427-428), but with traversal = -Infinity (:414), which hides the tie. Three upstream tests do run traversal == result (testFallbackToExact and testApproximate at the exact score of an indexed document, testExtremes at -Infinity and +Infinity), but none checks that tied documents are returned: testFallbackToExact asserts only the fallback to exact search (:452), testApproximate only an upper bound (:489).
  • The PR's own definition. In #12679 the author describes the baseline as "any vector with a score >= resultSimilarity".
  • History. #12770 (merged 2023-11-07, 9.9.0) made the graph searcher's neighbour test strict because the search over-explored the graph on equal scores (its commit message names lower dimensionality and quantization); for top-k an equal score does not raise the cutoff. #12679 was in review then; the traversal = result default was proposed on 2023-11-30, and the PR merged on 2023-12-11 without adapting the collector. #14215 (10.2.0) kept the strict form; in its review jimczi noted that this contract "does place the responsibility on the various implementers". #15021 (10.4.0) added the exhaustive batch gate, and #16654 (10.5.2) restored the 10.4 collector's body, renamed and deprecated, behind Explicit.
  • Counterfactuals. On 9.10.0, the pre-#12770 >= in the graph searcher makes the repro pass; on 10.4.0, an inclusive batch gate makes it pass; on main, the one-line collector fix makes it pass.
The devil's-advocate check364 words

The strongest "works as designed" case (built on purpose by a devil's-advocate verifier and by a cross-model refute review, which rated it strong): (1) the queries are documented as "(approximate)" and @lucene.experimental, and no upstream traversal == result test checks that tied documents are returned (testApproximate asserts an upper bound); (2) the strict tie rule in the searchers is deliberate (#12770, #14215), and TestFilteredHnswGraphSearcher.testAllTiedScoresBoundedVisitation bounds equal-score exploration on purpose; (3) completeness is promised only for traversal = -Infinity: #15836 (10.5.0) made that case exact "to guarantee completeness"; (4) "above" can be read as strictly above, and testExplicitResultCollection pins the bound to min(traversal, best); (5) Explicit is a deprecated shim that #16654 proposed to remove.

Why it fails: (1, 3) approximation and #15836 cover documents the search never reaches (#15836 fixed a disconnected graph, where the missed document scored 0.1033 against 0.0979, not a tie); here the tie is reached: on a segment without a graph it is scored and then thrown away at a batch boundary, and on a graph a traversal one ulp lower finds every copy on the same graph; (2) the strict rule and the bounded tie test serve top-k collectors, which still pass with the fix, while this collector defines its results with >=; (4) collect(), explain(), the exact fallback and the upstream unit test all mean >=, the pinned bound uses delta 1e-3 with traversal 0.3 below result 0.5, and under either reading one document at exactly 1.0 is returned and another is not, depending only on document order; (5) deprecation is a won't-fix risk, not intent: 9.10.0-10.4.0 hit it through the primary constructors, and Explicit still ships on main and branch_10_6. Verdict: a defect. The devil's advocate rated the intended argument weak, cross-model reviews moderate, the refute review strong (it could not run code); the reproducer and the adjudication say real. The cross-model fact check of the brief rated the case moderate for the no-graph path and strong for the graph path, where the query is approximate and equal-score exploration was bounded on purpose, so expect maintainers to weigh the graph case that way and lead with the no-graph case.

Suggested fix

#

Recommended A: report a bound one ulp below traversalSimilarity

One line in ExplicitVectorSimilarityCollector.minCompetitiveSimilarity(): return Math.min(Math.nextDown(traversalSimilarity), maxSimilarity), so a score equal to the threshold stays competitive. The strict search gates and top-k collectors are untouched. With it the repro passes, and 90 similarity-query tests and 891 vector, kNN and HNSW tests pass.

@Override
public float minCompetitiveSimilarity() {
  // Searchers treat a score equal to minCompetitiveSimilarity() as not competitive, but a score
  // equal to traversalSimilarity must still be traversed (and, when traversalSimilarity ==
  // resultSimilarity, collected).
  return Math.min(Math.nextDown(traversalSimilarity), maxSimilarity);
}
All options and trade-offs5 options · 698 words

The cause is one inclusive threshold handed to exclusive gates, and the gates are right for top-k collectors, so the fix belongs in the collector. Option A was built and validated in a scratch worktree at ea57360912ed (removed afterwards); the others were not built. Option A is this doc's recommendation: it also covers the full constructors, but whether equality should include ties is the maintainers' call, and its cost on tie-heavy data was not benchmarked. Users can work around it today with a full constructor (field, target, traversalSimilarity, resultSimilarity[, filter]) and traversalSimilarity = Math.nextDown(resultSimilarity), or with the Adaptive query on 10.5.2 and later (in 10.5.0 and 10.5.1 the plain constructors are already adaptive).

A: report a bound one ulp below traversalSimilarity (validated by the checks) (recommended)

#

In ExplicitVectorSimilarityCollector (and VectorSimilarityCollector in 9.10.0-10.4.0: 10.4.0 :65, 9.10.0 :64), return Math.min(Math.nextDown(traversalSimilarity), maxSimilarity). The bound is then below resultSimilarity, so any batch holding a score >= resultSimilarity passes the exhaustive gate, and the graph searcher's acceptance bound nextUp(bound) is at most traversalSimilarity (for finite thresholds; with traversalSimilarity -Infinity nothing changes, and the fix does not change how a NaN traversalSimilarity, which the constructor check lets through, is handled).

@Override
public float minCompetitiveSimilarity() {
  // Searchers treat a score equal to minCompetitiveSimilarity() as not competitive, but a score
  // equal to traversalSimilarity must still be traversed (and, when traversalSimilarity ==
  // resultSimilarity, collected).
  return Math.min(Math.nextDown(traversalSimilarity), maxSimilarity);
}

Trade-offs

  • Extra work. With many exact ties at the threshold the graph search now explores all of them; they are all results, so the work is proportional to the output. With traversal < result, nodes scoring exactly traversalSimilarity are now explored, as the javadoc ("below traversalSimilarity") describes. The worst case is a large plateau of equal scores at a traversalSimilarity below resultSimilarity: the graph search now explores it in full and returns none of it. No benchmark was run, and the upstream bounded-tie test uses a top-k collector, so it does not cover this collector.
  • Scope. The strict gates in the readers and searchers, and every top-k collector, are unchanged. The upstream testExplicitResultCollection pins minCompetitiveSimilarity with delta 1e-3 and still passes.
  • Backports. Not run on releases before main; the same line exists in 9.10.0-10.4.0 under the old class name.

How it was found

#

While building a metamorphic test harness for the kNN and similarity queries, the finder read the exhaustive-scan batch gate and wrote a probe: the same query returned one copy without a filter and both with an all-matching filter. Random small indexes checked against an exact brute-force reference then hit it 473 times, always with traversal equal to result.

The method in full172 words

Method: code reading, then random differential (metamorphic) testing (the registry's non-formal tier; the finder tagged it semi-formal). A hunt unit built a harness of random small indexes (0-300 documents, 1-4 segments, deletions, small-integer vectors so every similarity is computed exactly, several vector formats) and checked every kNN and similarity query against an exact brute-force reference.

  • Reading the exhaustive-scan gate bulkScore(...) > minCompetitiveSimilarity() next to the collector's >=, the finder wrote a public-API probe: Explicit(field, target, 1.0f) returned [0], the same query with a MatchAllDocsQuery filter [0, 64].
  • The random hunt's relation "similarity query == documents with exact score >= t" then failed 473 times in 55,970 traversal == result checks over 1,496 indexes (default codec and both scalar-quantized formats), with 0 failures for traversal -Infinity, traversal t - 0.25 and the Adaptive query, 0 when no segment exceeded 60 vectors, and 0 with the fix.
  • The finder minimised it to the 65-vector JUnit; an independent reproducer, a root-cause verifier, a devil's advocate and an adjudication followed (see the checks).

Bug record

LFV-467, snapshot of 2026-10-29

Registry title
FloatVectorSimilarityQuery and ByteVectorSimilarityQuery with traversalSimilarity == resultSimilarity (the 3- and 4-argument constructors: the plain ones in 9.10.0-10.4.0, the deprecated Explicit classes in 10.5.2 and main) silently drop documents whose similarity is exactly resultSimilarity, because the collector's minCompetitiveSimilarity() rises to the inclusive threshold and every searcher treats an equal score as not competitive
Area
search / vector similarity-threshold queries (ExplicitVectorSimilarityCollector with the exhaustive scan and the HNSW graph search)
Priority
Low, rank 241: Needs an exact score tie at the threshold, and on 10.5.2 and main only the deprecated Explicit similarity-query classes are affected.
Impact class
silent wrong results
Impact note
Applications that run a similarity-threshold vector query with traversalSimilarity equal to resultSimilarity on the default codec, directory and IndexSearcher (in 9.10.0-10.4.0 the plain, non-deprecated FloatVectorSimilarityQuery/ByteVectorSimilarityQuery(field, target, resultSimilarity[, filter]) constructors; in 10.5.2 and main only the deprecated Explicit classes; 10.5.0 and 10.5.1 are not affected) silently miss documents whose score is exactly the threshold once another vector at or above it was seen earlier in the same segment: deterministically on the graph path for every tie met after the first hit (1 of 6 and 1 of 12 exact copies returned on 3,000- and 4,000-vector graphs), and on segments below about 650 vectors, which have no graph, whenever the tie sits in a later 64-vector scoring batch with no better vector; rarely an above-threshold document reachable only through tied graph nodes is lost too; no index size is needed, only an exact score tie, which is natural for exact-duplicate lookups (EUCLIDEAN threshold 1.0), byte vectors (integer arithmetic) and thresholds copied from a known document's score.
Summary
You index vectors with the default codec and run FloatVectorSimilarityQuery.Explicit(field, target, 1.0f) on main or 10.5.2 (the plain FloatVectorSimilarityQuery(field, target, 1.0f) on 9.10.0-10.4.0), which sets traversalSimilarity = resultSimilarity, to find every exact copy of target under EUCLIDEAN, and you expect every document with similarity >= 1.0, as collect() ('similarity >= resultSimilarity'), explain() ('Score above threshold') and the query's own exact fallback all count them. Instead only the first copy comes back: a 65-vector segment with copies at doc 0 and doc 64 returns [0] and count() 1, the same query with a MatchAllDocsQuery filter returns [0, 64], a 4,000-vector HNSW segment returns 1 of its 12 copies, and a traversalSimilarity one ulp lower returns all of them (byte vectors at an exact 0.5 behave the same). Once a hit at the threshold is collected, ExplicitVectorSimilarityCollector.minCompetitiveSimilarity() = min(traversalSimilarity, maxSimilarity) equals the inclusive result threshold, and both the exhaustive scan (a 64-vector batch is collected only if its best score > minCompetitiveSimilarity()) and the graph search (score >= nextUp(minCompetitiveSimilarity())) treat an equal score as not competitive; the one-line fix returns min(nextDown(traversalSimilarity), maxSimilarity).
Introduced
cd195980ecbcb45e19ce9465854fed0b6be79ea7 on main (GITHUB#12679 'Add support for similarity-based vector searches' by kaivalnp, merged 2023-12-11) and its branch_9x backport 8089b8c9d3374dc4d451a4280daae85e0b139b84, first released in 9.10.0 [read: git blame, git log -L and git show of the merge parent in the full-history clone; exec: 9.9.0 and 9.9.2 lack the API, 9.10.0 fails]: the new collector kept similarity >= resultSimilarity but reported min(traversalSimilarity, maxSimilarity) as minCompetitiveSimilarity, and the 3/4-argument constructors passed resultSimilarity as traversalSimilarity (a default the author proposed in the PR on 2023-11-30), while #12770 (e1ce1d692ca4, merged 2023-11-07 during that review, released in 9.9.0) had already made HnswGraphSearcher's level-0 neighbour test strict ('>'), so the code was defective the day it merged. Not adapted when #15021 (0421a8de771e, 10.4.0) added the exhaustive-scan batch gate 'max > minCompetitiveSimilarity()', and #14963 (4a7c9c2780b, 10.4.0) stopped building graphs for small segments, so that gate became the normal path for them. Gone in 10.5.0 (#15784, be2af1e7b43: the plain constructors use the adaptive collector) and restored verbatim in 10.5.2 by #16654 (bc9adc96cc58 on main, 2026-09-13; backport #16671 5caef2a1fda9) as the deprecated ExplicitVectorSimilarityCollector behind [Byte|Float]VectorSimilarityQuery.Explicit [read + exec] (2023-12-11 (main cd195980ecbc, #12679); reintroduced 2026-09-13 (main bc9adc96cc58, #16654; backport #16671, released in 10.5.2))
