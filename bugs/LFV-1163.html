IntsRefFSTEnum.seekCeil returns a term below the target when a negative int follows a term prefix

On a BYTE4 FST with keys [5] and [5, 3], seekCeil([5, Integer.MIN_VALUE]) returns [5], a key below the target, instead of [5, 3]: the seek compares the negative int with the FST's hidden end-of-key marker, -1. Only application-built seek targets reach it; every release since 3.3.

The finding in 30 seconds

#

Background: FST enumerators and the end-of-key arc

#
  1. An FST maps sorted keys to outputs. With input type BYTE4 a key is a sequence of int labels, each of which must be >= 0 (FSTCompiler asserts it). Lucene's own BYTE4 FSTs store Unicode code points.
  2. IntsRefFSTEnum walks the keys in order, like a SortedMap iterator. seekCeil(t) moves to the smallest key >= t, seekFloor(t) to the largest key <= t, and seekExact(t) to t or returns null. The target t does not have to be a key.
  3. When a key is also a prefix of longer keys, like [5] of [5, 3], the FST reader shows the node after it with an extra first arc labelled -1 (FST.END_LABEL), meaning "a key ends here". The real arcs (here 3) come after it.

The finding, step by step

#
  1. Build a BYTE4 FST with two keys, [5] -> 1 and [5, 3] -> 2, with the default FSTCompiler settings. [5] is a key and also a prefix of [5, 3].
  2. On a fresh IntsRefFSTEnum, call seekCeil([5, Integer.MIN_VALUE]). In IntsRef's signed order, [5] < [5, -2147483648] < [5, 3].
  3. You expect [5, 3] with output 2, the smallest key >= the target; seekCeil([5, 0]) returns exactly that.
  4. Instead you get [5] with output 1, a key below the target. No error, with assertions on and off. On the same FST seekFloor([5, -7]) returns null instead of [5], and with assertions off seekExact([5, -1, 9]) finds [5].
  5. Why: because [5] is a key, the FST reader starts the node after it with a hidden arc labelled -1 (FST.END_LABEL, "a key ends here"), before the real arc 3. The seek compares the target's next int with that -1 as if it were a normal label; every negative int is <= -1, so the seek stops at [5].

Who is affected

#

Only application code that builds its own FST and seeks an IntsRefFSTEnum with a target holding a negative int right after a prefix that is itself a key, such as Integer.MIN_VALUE as the smallest next label or a -1 sentinel. Two keys, default settings. No Lucene code path seeks this enum, and BytesRefFSTEnum cannot hit it.

Mechanism, terms and numbers637 words

IntsRefFSTEnum.seekCeil promises the "smallest term that's >= target" (IntsRefFSTEnum.java:59 at 5adff78bb168), and IntsRef order is signed (IntsRef.java:104-114), so in a BYTE4 FST {[5] -> 1, [5, 3] -> 2} the ceiling of [5, Integer.MIN_VALUE] is [5, 3]. A fresh enum returns [5], a key below the target, with no exception and with assertions on or off. Inside the FST, the node after a key that is also a prefix of longer keys starts with a "fake" arc labelled FST.END_LABEL = -1 (FST.java:697-712). getTargetLabel hands the seek scan the target's raw int (IntsRefFSTEnum.java:91-98), and the scan compares it with that arc as if it were a normal label (FSTEnum.java:274-288): -1 is equal, any lower int is smaller, and either way the seek stops at the prefix. seekFloor and seekExact go wrong the same way. On a fresh enum, no target without a negative int was answered wrongly in the checks run (the separate LFV-1147 overflow on a reused enum aside). The code dates from 2011 (LUCENE-2843) and is in every release from 3.3 to 10.6.0. No Lucene code path seeks an IntsRefFSTEnum, and FST labels must be >= 0 (asserted when the FST is built), so only application-built seek targets reach it.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/fst/)

#
  1. seekCeil stores the target and calls doSeekCeil (IntsRefFSTEnum.java:60-65); nothing checks the target's ints. getTargetLabel returns FST.END_LABEL once the target is used up and otherwise the raw int (IntsRefFSTEnum.java:91-98).
  2. After matching label 5, the scan reads the next node with readFirstTargetArc (FSTEnum.java:285). Because [5] is a key, the arc is final, and readFirstTargetArc inserts a "fake" first arc with label END_LABEL = -1 (FST.java:697-712; FST.java:138-139: "If arc has this label then that arc is final/accepted"). The real arc 3 follows it.
  3. The scan loop sends this end arc to the list scan (FSTEnum.java:147 and :159). doSeekCeilList (FSTEnum.java:274-288) compares the end arc's label -1 with the target int. For MIN_VALUE, -1 > MIN_VALUE takes the "ceiling found" branch (:286-288) and calls pushFirst(), which stops at once on an END_LABEL arc (:714-716): the enum is left on [5]. A target int of exactly -1 matches the arc (:277-282) and also ends on [5].
  4. seekFloor: the walk-back in doSeekFloorList (FSTEnum.java:600-624) looks for an arc with a label below the target int and never finds the end arc below an int < -1, so it backs up past [5] (null here, or a smaller key). seekExact: findTargetArc(-1, ...) (FSTEnum.java:663) matches the end arc, and :674 reports success. With assertions on, assert upto == 1 + target.length (IntsRefFSTEnum.java:84) fires instead.
  5. The same -1 shows outside the enum (context; fix A does not change it): Util.get passes each int to FST.findTargetArc (Util.java:47-67), which treats END_LABEL as a request for the end-of-key arc (FST.java:1013-1029), so Util.get(fst, [5, -1, 3]) returns 2, the output of [5, 3], instead of null, with assertions on and off.

Exactly when it goes wrong

#

A bounded-exhaustive check against a TreeMap oracle (8,191 BYTE4 FSTs over labels {0, 1, 2}, every target over {MIN, -2, -1, 0, 1, 2, 3, MAX} up to length 3, all three seeks, plus list, continuous, direct-addressing and binary-search node encodings; a fresh enum per seek; 14,376,393 checks): 0 mismatches for targets without a negative int, including positive ints outside the alphabet; mismatches exactly when the first negative int follows a prefix that is a key: seekCeil for every negative int, seekFloor for ints below -1, seekExact for -1; 0 mismatches when that prefix is not a key; the same for all four encodings. With fix A: 0 mismatches.

Exposure and likelihood228 words
  • Who. Application code that builds its own FST and seeks an IntsRefFSTEnum with a target that holds a negative int right after a prefix that is itself a key: for example Integer.MIN_VALUE as "the smallest possible next label" in a ceil-based prefix scan, or a -1 "unknown" sentinel. Two keys suffice; default FSTCompiler settings; no scale.
  • Effect. A silent wrong lookup: a ceiling below its target, a floor that skips an existing key, an exact match for a key that is not there (assertions off). Ceiling and floor are wrong with assertions on too.
  • Not affected. No Lucene code path: the only non-test IntsRefFSTEnum user, hunspell WordFormGenerator, calls only next() (WordFormGenerator.java:68-71 in lucene/analysis/common). BytesRefFSTEnum cannot hit it: its target labels are bytes & 0xFF (BytesRefFSTEnum.java:96). In the checks (a fresh enum per seek), targets without a negative int, and a negative int after a prefix that is not a key, were answered correctly; the separate LFV-1147 overflow on a reused enum aside.
  • Opt-in part. IntsRefFSTEnum, FSTEnum and FST are @lucene.experimental (IntsRefFSTEnum.java:26, FSTEnum.java:28, FST.java:62).
  • Likelihood: contrived. No valid key contains a negative int, no caller found builds such a target, and no public report of it was found since 2011. It is deterministic, though: whoever builds such a target after a key prefix gets the wrong answer every time.

Why it looks unintended

#
  • seekCeil promises the "smallest term that's >= target", with no rule on the target's ints, and IntsRef order is signed.
  • Positive off-alphabet ints were answered correctly in every check (fresh enum); only negative ones failed.
  • Labels >= 0 is only a build-time assert, and ints below -1 fail too. Contested: negative targets may be judged out of domain.
The full argument223 words
  • Contract. IntsRefFSTEnum.java:59: "Seeks to smallest term that's >= target"; :67: "Seeks to biggest term that's <= target"; :76: "Seeks to exactly this term, returning null if the term doesn't exist". None states a precondition on the target's ints. The package doc says the enumerators "behave like SortedMap iterators" (package-info.java:30-32), and IntsRef.compareTo is "Signed int order comparison" (IntsRef.java:104), so the expected answers are well defined for every IntsRef.
  • Other off-alphabet targets work. BYTE1 seekCeil([5, 300]), BYTE4 Integer.MAX_VALUE and every positive out-of-alphabet target of the exhaustive check were answered correctly. No mismatch was found for them in that corpus or those probes, which fits the mechanism: the -1 marker sits below every int >= 0 and at or above every negative int.
  • Tests. FSTTester (test framework) checks IntsRefFSTEnum seeks against the sorted key list (FSTTester.java:420-484), but only with in-alphabet targets, so it never reaches this case.
  • History. The marker, the fake end arc and the raw-int getTargetLabel all arrived together in 1cab313a2b8 (LUCENE-2843, 2011); its issue (#3917) does not discuss negative seek targets. Dawid Weiss remarked in 2011 that END_LABEL "makes having -1 label on a transition impossible" (commit 931c8294064) and that marker values from the domain range made them nervous (#4370): a design concern about labels, not a decision about seek targets.
The devil's-advocate check216 words

The strongest case for "intended" (made by the cross-model reviewer): INPUT_TYPE "Specifies allowed range of each int input label for this FST" (FST.java:68); BYTE4 represents strings as "full unicode codepoints" (FSTCompiler.java:253-255); FSTCompiler asserts v >= 0 and label >= 0 (FSTCompiler.java:581, :1109); END_LABEL = -1 is public, and findTargetArc treats it as the end-of-key marker on purpose (FST.java:1013-1029); the class is experimental with no in-tree seek caller. So a negative target int is garbage in.

Our answer, a judgement call the code does not settle: those lines describe the labels an FST is built from and how arcs are marked, not seek targets, and a ceiling or floor target is normally not a key. The label rule is a build-time Java assert and is never checked on the seek path. Ints below -1 are not END_LABEL and fail too. And "unsupported input" would justify an IllegalArgumentException, not a ceiling below its target. The independent reproducer, the devil's-advocate verifier and the tie-breaker rejected the case; the adjudication called the bug disputed only on this question, and the cross-model reviewer was not persuaded. Whether negative targets are in contract is the maintainer's call; if they are not, this is a hardening request, and fixes B and C fit.

Suggested fix

#

Recommended Normalise negative target ints at the IntsRefFSTEnum boundary (fix A)

Normalise negative target ints in IntsRefFSTEnum (fix A): valid keys hold only labels >= 0, so seekCeil(p ++ [x<0] ++ rest) can seek p ++ [0], seekFloor can seek p, and seekExact can return null. The repro passes, assertions on and off, and all core FST tests pass. Alternatives: reject such targets, or document the rule.

Trade-offs

Preserves the tested behaviour for FSTs that satisfy the non-negative-label invariant, and changes nothing for targets without a negative int. It adds an extra O(target length) scan per seek, which the seek itself may not need: a seek stops at the first label where the target leaves the FST (FSTEnum.java:286-306), and seekExact short-circuits (:664-670), as its javadoc says (IntsRefFSTEnum.java:76-78); not benchmarked. It allocates once only when a negative int is present. A seekExact rejected this way leaves the enum at its previous position; the javadoc does not specify the position after a miss either way. No negative target int reaches FSTEnum's label comparisons any more; the internal END_LABEL (-1) that getTargetLabel returns at the end of the target still does (IntsRefFSTEnum.java:93-94). Caveat: the label rule is only a Java assert (FSTCompiler.java:581, :1109). With assertions off, FSTCompiler accepts a negative label (a BYTE4 key [-2] was built and found by Util.get and next(); with assertions on the build fails). On such an FST, outside the documented label range, main's seekExact([-2]) matches the -2 arc (by FST.findTargetArc), while fix A returns null (fix B would throw). The repro's FST has only labels 5 and 3, so its assertions-off runs build a valid FST and only the seek differs. Fix A is sound for FSTs built within the label range; a maintainer may prefer B, or a build-time check that does not rely on asserts.

Reject negative target ints (fix B)

#

Throw IllegalArgumentException from seekCeil, seekFloor and seekExact when a target int is negative.

Trade-offs

The same scan cost as A; a loud failure instead of a silent wrong answer; changes behaviour for any caller that passes such ints today (none in tree). Not run.

Document the restriction (fix C)

#

Add a javadoc line to the three seek methods (or the class) saying that target ints must be >= 0.

Trade-offs

No code change; the silent wrong answer stays for callers who miss the line. A documentation-only resolution is a possible maintainer answer. Not run.

Downstream note

#

Downstream code that seeks an IntsRefFSTEnum with sentinel-style negative ints in its targets would silently get wrong ceiling, floor or exact lookups; no Lucene component does this.

How it was found

#

A proof-obligation audit of IntsRefFSTEnum's seek contract: for every IntsRef target, the three seeks must give the SortedMap answers in signed order. The obligation fails where the target's raw int meets the hidden end-of-key arc labelled -1; a JUnit test witnessed it, and a later exhaustive check of 14.4 million seeks mapped exactly when.

The method in full121 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked IntsRefFSTEnum's seeks against the obligation that, for every IntsRef target, seekCeil, seekFloor and seekExact return the SortedMap answers in signed IntsRef order, and found that getTargetLabel's raw int is compared with the end-of-key arc's label -1.
  • The finder wrote a JUnit test (target [5, -1]) and the boundary fix; the adjudication replaced -1 with Integer.MIN_VALUE so the target does not contain END_LABEL, and a final repro check kept that single method.
  • An independent reproducer, an executed cross-model review and a devil's-advocate verifier reproduced it with their own tests; the tie-breaker added the bounded-exhaustive check ("Prior reports, history and checks").

History

#

Present since LUCENE-2843 added the -1 end marker and the generic seeks (1cab313a2b8, 2011), first released in 3.3 through the branch_3x copy; its parent commit answers correctly and 3.2.0 has no FST package. Every release run since, through 10.6.0 and main, fails. Not fixed upstream.

Versions tested5 rows

LFV-1163, snapshot of 2026-11-05

Registry title
IntsRefFSTEnum.seekCeil returns a term below the target (and seekFloor and seekExact answer wrongly) when a negative target int follows a prefix that is itself a term, because the seek compares it with the virtual end-of-term arc whose label is FST.END_LABEL = -1
Area
util / FST (IntsRefFSTEnum seek targets vs. FSTEnum's virtual END_LABEL arc)
Priority
Low, rank 925: IntsRefFSTEnum seekCeil, seekFloor and seekExact silently give wrong answers when an application-built target holds a negative int right after a prefix that is itself a term, in every release since 3.3. It needs that sentinel-style target on the expert, experimental enum, which no FST key and no Lucene caller has, so it is contrived.
Impact class
minor
Impact note
Only application code that seeks the expert, @lucene.experimental IntsRefFSTEnum with a target it builds itself is hit, and only when a negative int (for example Integer.MIN_VALUE as the smallest next label, or a -1 sentinel) follows a prefix that is itself a term: seekCeil then silently returns that prefix, a term below the target, for every negative int; seekFloor returns null or a smaller term for every int below -1; seekExact reports the prefix as found for -1 under -da (an internal assert fires under -ea); ceil and floor are wrong under -ea too; tiny input, default FSTCompiler settings, no scale needed; no Lucene code path seeks an IntsRefFSTEnum and BytesRefFSTEnum cannot hit it; every release since 3.3 and main.
Summary
You build a BYTE4 FST with [5] -> 1 and [5, 3] -> 2 and call seekCeil([5, Integer.MIN_VALUE]) on a fresh IntsRefFSTEnum; you expect [5, 3], the smallest term >= the target in IntsRef's signed order ([5] < [5, MIN_VALUE] < [5, 3]). Instead it returns [5], a term below the target, with or without assertions. IntsRefFSTEnum hands the raw target int to FSTEnum's arc scan, and the node after the final arc [5] starts with a virtual end-of-term arc labelled END_LABEL = -1, so a negative int either equals that label (-1) or sorts below it and the scan stops at [5]; seekFloor and seekExact go wrong the same way.
