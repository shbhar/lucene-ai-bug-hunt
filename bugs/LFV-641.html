Hunspell rejects and cannot stem twofold-suffix words when a suffix class has cross product N

When a Hunspell dictionary chains two suffixes and either class says cross product N, Lucene rejects the word and finds no stem, although that flag only governs prefix + suffix. In Luxembourgish that is at least 47,840 correct forms on main, like räichsten; the bug affects every release since 3.5.0.

The bug in 30 seconds

#

Hunspell affix files allow "twofold suffixes": a suffix whose continuation class allows a second suffix. Lucene follows such a chain only if both suffix classes say cross product Y, a field the format reserves for prefix + suffix combinations.

  1. You load a dictionary where the suffix st (class S) allows the endings en and e (class E) through its continuation class /E, and E's header says cross product N: SFX S Y 1, SFX S 0 st/E ., SFX E N 2 (en, e), entry raich/SE. Real Luxembourgish has this shape: räich + st + en = räichsten, "richest".
  2. You expect raichsten and raichste to be correct with root raich: hunspell(5) defines cross product as the "permission to combine prefixes and suffixes", there is no prefix here, and native Hunspell (1.3.2 and 1.7.2) accepts both with N or Y.
  3. Instead spell("raichsten") is false and getRoots returns []. Lucene strips en, then never looks for st, because class E is N (Stemmer.java:621); with S = N a second check rejects st (:564). Only S = Y with E = Y works.
  4. No error is raised: HunspellStemFilter leaves raichsten unstemmed, so a document containing it gets 0 hits for the term raich (1 with E = Y), and getAllWordForms("raich") returns 4 forms instead of 6.
  5. On the real Luxembourgish dictionary, at least 47,840 word forms of 13,526 distinct roots that native Hunspell 1.3.2 accepts are rejected by Lucene main, such as räichsten, verstümmeltem and Hälsercher. A small fix at three sites makes Lucene accept them.

Who is affected

#

Applications using Lucene's opt-in Hunspell module (spell-checking, HunspellStemFilter, getAllWordForms) with a dictionary whose twofold-suffix chains contain an N class. Real Luxembourgish is hit on ordinary words: correct words are flagged and stay unstemmed, so searches for the root miss them. Silent and deterministic; Elasticsearch's and OpenSearch's hunspell token filters wrap the same filter.

Mechanism, terms and numbers689 words

In a Hunspell .aff file a suffix can carry a continuation class that allows a second suffix after it ("twofold suffix stripping"). Each affix class header also has a cross-product field, Y or N, which hunspell(5) defines as the "permission to combine prefixes and suffixes". Lucene also requires it for suffix + suffix: if either suffix class of a chain says N, Hunspell.spell rejects the word, getRoots, analyzeSimpleWord and Stemmer return no stem, HunspellStemFilter leaves the token unstemmed, and getAllWordForms leaves the form out. Native Hunspell (1.3.2 and 1.7.2, in every Y/N variant tested) accepts these words. Three code sites carry the assumption (Stemmer.java:621, Stemmer.java:564, WordFormGenerator.java:251 on main a9779ef3c193). On the real Luxembourgish dictionary, from the collection Lucene's package docs point to, at least 47,840 word forms of 13,526 distinct roots that native Hunspell 1.3.2 accepts are rejected by Lucene main. All 18 releases tested from 3.5.0 to 10.5.2 fail, and the same gates are in every release since 3.5.0; nothing throws.

Terms

#
  • Affix class: a group of PFX or SFX rules under one flag. Its header line is SFX <flag> <cross product> <count>, for example SFX E N 2.
  • Cross product (Y or N): hunspell(5) field (2), "Cross product (permission to combine prefixes and suffixes)" (Hunspell 1.7.2 man/hunspell.5:522).
  • Continuation class: flags after a slash on a rule, SFX S 0 st/E .: a word that got st may take a suffix of class E next. hunspell(5) calls this "Twofold suffix stripping" (:921); its example is drink/X with SFX X 0 able/Y . and SFX Y 0 s ., giving drink, drinkable, drinkables.
  • Outer / inner suffix (Lucene's naming): the outer suffix is the last one applied and the first one stripped (en in raich + st + en), the inner suffix the first one applied (st).

The bug

#
  1. Dictionary.java:685 parses the field per class (crossProduct = args[2].equals("Y")), :791 stores it with every rule and isCrossProduct(affix) reads it back (:812-814).
  2. Outer suffix N: no search for the inner suffix. Stemmer.applyAffix strips an affix, checks the stem, then decides whether to strip one more. The decision is gated on the affix just stripped: if (dictionary.isCrossProduct(affix) && recursionDepth <= 1) (Stemmer.java:621); for a suffix it then looks for "another suffix" (:630-634). With E = N, after en is stripped from raichsten, the search for st never starts.
  3. Inner suffix N: the continuation check is never reached. Stemmer.isAffixCompatible accepts an inner suffix only inside if (dictionary.isCrossProduct(affix)) { ... return dictionary.hasFlag(append, prevFlag); } (:564-571) and otherwise returns false (:573). With S = N: after en is stripped, the intermediate raichst is looked up (:262) and is not an entry; then this check refuses to strip st as the inner suffix, so the root raich is never reached, although st/E carries the continuation flag.
  4. The generator copies the rule. WordFormGenerator.expand recurses for a further affix only if (dictionary.isCrossProduct(affix.id)) (WordFormGenerator.java:251-253), so getAllWordForms omits the same forms.
  5. Native Hunspell checks cross product only when a prefix is combined: SfxEntry::check_twosfx skips an entry only if ((optflags & aeXPRODUCT) != 0 && (opts & aeXPRODUCT) == 0) (Hunspell 1.7.2 affentry.cxx:712, "if this suffix is being cross checked with a prefix"), and without a prefix it checks the inner suffix with optflags 0 (:753-755). nuspell, an independent C++ implementation, does the same.

The numbers

#

With the hunspell(5) example, only X = Y, Y = Y accepts drinkables; the other three Y/N combinations give spell = false, roots = [] and getAllWordForms("drink") = [drink, drinkable], while drinkable stays accepted and drinks rejected in all four. Native Hunspell 1.3.2 accepts drinkables and stems it to drink in all four. For prefix + suffix words Lucene already agrees with native Hunspell 1.3.2 on every Y/N combination of a 4-dictionary matrix with a prefix class (S and E each Y or N, the prefix class tied to S); only the suffix chains differ.

Exposure and likelihood299 words
  • Who. Users of Hunspell.spell, suggest, getRoots, analyzeSimpleWord, HunspellStemFilter / HunspellStemFilterFactory and getAllWordForms whose dictionary gives cross product N to a class in a twofold-suffix chain. No setting beyond the dictionary; deterministic; assertions on or off.
  • What goes wrong. No exception. Spell-checking flags correct words, and suggest may offer a different word (suggest("raichsten") = [raichen] in the hunt's probe). Stemming returns nothing, so the stem filter indexes and queries the surface form: in an 8-document probe index a query for raich found 4 of 6 forms, and a query for raichsten only itself. Every hit set was a subset of the correct one. getAllWordForms omits the forms.
  • Scale on a real dictionary (Luxembourgish lb from wooorm/dictionaries at 8cfea406b505, the commit Lucene's regression build pins). generateAllSimpleWords over every entry gives 293,583 distinct forms on stock and 341,573 with the fix, none lost. Of the letters-only added forms, 47,840 of 13,526 distinct roots are accepted by native Hunspell 1.3.2 (the observed hunspell -l result), rejected by stock Lucene and accepted with the fix: 36,137 lowercase (for example superlatives and participles with adjective endings: räichsten, verstümmeltem, standardiséierten) and 11,703 capitalised (for example diminutive and feminine plurals: Hälsercher, Steenemerinne). Native -m output on the named forms shows two suffixes, for example verstümmeltem st:verstümmelen po:verb is:adjective is:papa is:em; morphology was not run on all 47,840.
  • Other dictionaries. A static survey of 191 public .aff files found such chains in 8, among them lb, hu_HU, ta_IN, is and fa; only lb was executed. Lucene documents Hungarian as unsupported.
  • Downstream. The hunspell token filters of Elasticsearch and OpenSearch return Lucene's HunspellStemFilter (source read, not executed).
  • Since. Every release with Lucene's Hunspell code: stemming since 3.5.0, Hunspell.spell since 8.9.0, getAllWordForms since 9.5.0.

Why it is a bug, not intended

#
  • hunspell(5) defines the field as "permission to combine prefixes and suffixes"; native Hunspell and nuspell check it only when a prefix is involved.
  • Lucene claims native behaviour: Hunspell "can be used in place of native Hunspell"; LUCENE-5483 says recursion is "driven correctly by continuation classes".
  • No test or comment found says N blocks suffix chains; all twofold fixtures use Y.
The full argument288 words
  • The format's contract. hunspell(5) (Hunspell 1.7.2 man/hunspell.5:522): "(2) Cross product (permission to combine prefixes and suffixes). Possible values: Y (yes) or N (no)". Its "Twofold suffix stripping" section (:921-962) ties the second suffix to the continuation class only. A native maintainer restated the rule on hunspell/hunspell#177 (2026): "A prefix and a suffix are only combined on the same word when both the prefix rule and the suffix rule are marked with the cross-product flag Y."
  • Lucene claims that behaviour. Hunspell javadoc: "can be used in place of native Hunspell for many languages" (Hunspell.java:34-37; the listed exceptions are Hungarian, non-BMP characters and PHONE). Stemmer javadoc: "conforms to the algorithm in the original hunspell algorithm, including recursive suffix stripping" (Stemmer.java:28-32). CHANGES for LUCENE-5483 (4.8.0): "Multi-stage affix-stripping, prefix-suffix dependencies, and COMPLEXPREFIXES now work correctly according to the hunspell algorithm ... rules for recursive affix application are driven correctly by continuation classes in the affix file" (lucene/CHANGES.txt:12545-12549); its issue #6546 "greatly refined this algorithm to match correct hunspell behavior".
  • No source we found documents the rule. The searches found no test, comment, CHANGES entry, issue or commit message saying N blocks suffix chains; no commit message in the full history contains "cross product" or "twofold".
  • Why tests never caught it. 12 of Lucene's 97 test .aff files chain two suffixes (twofold.aff, the manual's example in TestTwoFold, and dependencies.aff, compress.aff, needaffix5.aff and others), all with Y on both classes; no Lucene fixture and no Hunspell 1.7.2 test fixture puts an N class in a continuation chain.
  • Asymmetry. For prefix + suffix words Lucene already applies the cross-product rule exactly as native Hunspell does; only suffix + suffix uses it.
The devil's-advocate check229 words

The strongest case for "intended": the gate is deliberate code from the very first Lucene Hunspell port (2011), LUCENE-5483 (2014) added the inner check, LUCENE-10626 (2022) copied it into the generator, every manual example uses Y, the Hunspell javadoc says not all languages are supported, and in 2012 the original author wrote on LUCENE-4311 (#5379) that "our implementation of Hunspell is not a port of the C/C++ app per se". So it could be read as a conservative supported subset.

Why it fails: no source gives a reason for the gate; the later, explicit intent (LUCENE-5483's issue and CHANGES entry, the Hunspell and Stemmer javadocs, LUCENE-9687 "on a par with the native C++ Hunspell") is native compatibility; the unsupported-language list is about language-specific logic, while this is generic affix semantics shown by a six-line dictionary; and keeping drinkable but dropping drinkables only because an unrelated flag says N is not a coherent subset. The cross-model reviewer rated the argument moderate in a lens and weak in the other; the independent reproducer and the devil's-advocate check rated it weak, and the adjudication found that none of the intended-behaviour arguments holds. Verdict: a defect. WordFormGenerator is the same misreading in a second place, not a separate defect; its javadoc promises "all word forms for all dictionary entries with the given root word" (WordFormGenerator.java:117), which the omission also contradicts.

Suggested fix

#

Recommended Use cross product only when a prefix is combined (suffix chains need only the continuation class)

Check cross product only when a prefix is combined: keep the Stemmer.applyAffix gate for prefixes only, accept an inner suffix in isAffixCompatible by its continuation flag (plus cross product after a prefix), and let WordFormGenerator recurse after affixes with continuation flags. Validated: the repro passes; analysis-common: 1,911 tests, 0 failures, 18 skipped. Analysis output changes, so affected indexes need reindexing.

Trade-offs

  • Bounded extra work: suffix recursion still stops at two suffixes, and the generator at two affixes of a kind (WordFormGenerator.java:376).
  • It leaves the mirror case unchanged: under COMPLEXPREFIXES, two prefixes whose classes say N (reunfoo) are accepted by native Hunspell and rejected by Lucene with or without this fix. That path is entangled with a separate prefix-recursion bug (option B) and is better fixed on its own.
  • Compatibility: the fix changes analysis output. HunspellStemFilter now stems the affected words, so an index built before the fix keeps their surface forms and needs reindexing to match the fixed query-time analysis. A Lucene-only dictionary that relied on N to block a suffix chain (nonportable: native Hunspell ignores it there) would accept more words, and getAllWordForms returns more forms (on Luxembourgish 341,573 instead of 293,583); no benchmark was run.

  • With the fix shadowed onto the stock jars: the finder's test, the independent reproducer's spell/stem and generator tests (4 of 4 each), the cross-model review's 4-dictionary prefix/suffix matrix (prefix + suffix results unchanged, now equal to native everywhere), the cross-model reviewers' tests (6 of 6, 2 of 2), and the hunt's security probe (no query loses hits; its COMPLEXPREFIXES N dictionary still does not overflow, as on stock, while its Y dictionary still overflows for bx and bbx, as on stock: that is the separate LFV-375).

  • Not run: the full Lucene suite, the external-dictionary suites, a benchmark.

Drop the cross-product gate for prefixes too (the finder's sketch; not alone)

#

Also lets a second prefix under COMPLEXPREFIXES combine without cross product, which fixes the mirror case (reunfoo accepted). It passes the repro and, by the finder's run, the 146 hunspell tests of the time.

Trade-offs

Alone it lets a separate known bug, the COMPLEXPREFIXES third-prefix recursion that ends in StackOverflowError (registry LFV-375), reach dictionaries whose chained prefix classes say N, which today are immune: in the hunt's security probe the COMPLEXPREFIXES dictionary with N overflows for bx with B, and not with A or on stock. In the finder's differential, words Lucene accepts and native rejects went from 49 to 96, all new ones under COMPLEXPREFIXES. Only safe together with or after the LFV-375 fix (doPrefix = false at Stemmer.java:640) and the sibling second-prefix continuation fix.

Document the restriction instead

#

State in the Hunspell javadoc that suffix chains need cross product Y.

Trade-offs

Contradicts hunspell(5) and the class's "in place of native Hunspell" claim, and leaves real dictionaries such as Luxembourgish broken.

Downstream note

#

Elasticsearch and OpenSearch build their hunspell token filter on Lucene's HunspellStemFilter (source read, not executed), so their users of dictionaries with this shape get the same missed stems; the effect is lower recall only.

How it was found

#

Differential testing of Lucene's Hunspell code against native Hunspell 1.7.2 on 4,000 generated micro-dictionaries and 1,069 fixture cases; with the finder's fix (option B) alone, the words native accepts and Lucene rejects fell from 202 to 24. A public-API JUnit then reproduced it on the stock jar.

The method in full190 words

Method: cross-implementation differential testing (the hunt's non-formal tier), in a hunt unit comparing Lucene's word-form generator, spell and analyzeSimpleWord with native Hunspell 1.7.2 (libhunspell spell and stem) and the hunspell-tools unmunch/munch.

  • Inputs: 4,000 seeded, grammar-built micro-dictionaries (per dictionary every candidate word reachable by at most 3 affix rules) and 1,069 per-root cases from the Hunspell 1.7.2 and Lucene test fixtures.
  • Root causes were separated with switchable shadow fixes: with the finder's fix for this bug (option B) alone, words native accepts and Lucene rejects fell from 202 to 24 (the rest are other causes or native deviations from hunspell(5)).
  • The finder then wrote a public-API JUnit (raich/SE) that fails on the stock jar, found the real Luxembourgish case and checked native Hunspell on it.
  • Found 2026-10-27 on main a9779ef3c193; then checked by an independent reproducer, an intended-behaviour devil's advocate, two executed reviews by a model from another family (OpenAI GPT-5.6), a re-run of the intended lens, an adjudication, a history and prior-report follow-up, a security screen and a credibility audit. This doc added the gradle runs, the fix validation and the Luxembourgish count.

Bug record

#

LFV-641, snapshot of 2026-10-29

Registry title
Hunspell rejects, cannot stem and does not generate twofold-suffix words (a second suffix allowed by the first suffix's continuation class) when either suffix class has cross product N, although cross product only governs prefix+suffix combinations: with 'SFX S 0 st/E', 'SFX E N 2' (en, e) and raich/SE, spell("raichsten") is false; the real Luxembourgish dictionary rejects räichsten
Area
analysis / hunspell (Stemmer affix stripping: Hunspell.spell, getRoots, analyzeSimpleWord, Stemmer.stem, HunspellStemFilter; WordFormGenerator.getAllWordForms)
Priority
Medium, rank 315: Since 3.5, Hunspell spell and stemming silently fail on ordinary twofold-suffix words in a real public dictionary (Luxembourgish), which changes index-time stemming and recall, but only a few dictionaries have this shape, so it ends the narrow silent-result Medium rows after LFV-479.
Impact class
silent wrong results
Impact note
Only applications that use the opt-in Hunspell analysis (Hunspell.spell, getRoots and analyzeSimpleWord, Stemmer.stem and HunspellStemFilter, and the getAllWordForms tooling) with a dictionary in which a suffix class of a twofold-suffix chain has cross product N are hit: valid twofold-suffix words are reported as misspelled, get no stems (HunspellStemFilter passes them through unstemmed, so a search for the root misses them) and are missing from getAllWordForms, with no error [exec]; no scale is needed; the real Luxembourgish dictionary (lb, from the dictionary collection at the commit Lucene's regression build pins) triggers it on ordinary superlatives such as räichsten, räichste, räichstem and räichster [exec, the independent reproduction and the intended-behaviour check]; the finder's static survey of 191 public .aff files found such chains in 8 files (among them lb, hu_HU, ta_IN, is and fa; only lb was executed, and Lucene documents Hungarian as unsupported); every release with Lucene's Hunspell code, 3.5.0 to 10.5.2, has it [exec].
Summary
You load a Hunspell dictionary with a twofold suffix, where the first suffix's continuation class allows a second suffix (for example 'SFX S Y 1 / SFX S 0 st/E .', 'SFX E N 2 / SFX E 0 en . / SFX E 0 e .' and the entry raich/SE), and spell-check or stem raichsten. You expect it to be accepted and stemmed to raich: hunspell(5) defines the cross-product field only as the 'permission to combine prefixes and suffixes', no prefix is involved, and C Hunspell accepts the word with N as with Y. Instead Lucene rejects raichsten and raichste, returns no stems and leaves them out of getAllWordForms("raich"), because Stemmer.applyAffix (Stemmer.java:621), Stemmer.isAffixCompatible (:564) and WordFormGenerator.expand (:251) follow a suffix+suffix chain only when the suffix classes are cross product Y; the real Luxembourgish dictionary shows the same for räichsten, räichste, räichstem and räichster.
