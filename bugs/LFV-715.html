ComplexPhraseQueryParser skips its same-field check for prefix and regexp clauses inside a phrase

ComplexPhraseQueryParser rejects "jo* id:2?" at parse time because id is not the phrase's field, but it accepts "jo* id:2*", and the search then throws IllegalArgumentException; name:"id:2*" even searches field id. The class checks the field of term, wildcard, fuzzy and range clauses, but never of prefix or regexp clauses.

The finding in 30 seconds

#

ComplexPhraseQueryParser in three steps

#
  1. It is the classic query parser plus wildcards, fuzzy words and ranges inside quotes: "jo* smith" becomes a span query that finds "john smith".
  2. It parses twice. Pass 1 treats each quoted phrase as one unit; pass 2 parses the text inside the quotes again, with the phrase's field as the default field.
  3. A span query can only combine clauses of one field, so pass 2 must reject any clause that names another field. The class javadoc says it does, and a test checks that "jo* id:1 smith" is rejected.

The finding, step by step

#
  1. Parse with ComplexPhraseQueryParser on default field name, over 2 documents: (name "john smith", id 1) and (name "jane doe", id 2). "jo* smith" finds john smith.
  2. Put a clause for another field inside the quotes. "jo* id:2?" is rejected by parse(): Cannot have clause for field "id" nested in phrase for field "name". So are id:2~1, id:[1 TO 2] and id:2 (for id:2 the message comes as the cause of a RuntimeException), so you expect the prefix "jo* id:2*" to be rejected too.
  3. Instead parse() accepts "jo* id:2*" and "jo* id:/2/", and search() throws IllegalArgumentException: Clauses must have same field. "jo* id:9*", whose prefix matches no term, returns 0 hits and no error.
  4. With one clause there is no error at all: the phrase name:"id:2*" runs as id:2 and returns jane doe; name:"id:/[12]/" returns both documents.
  5. Why: the second pass runs the field check only in newTermQuery, getWildcardQuery, getRangeQuery and getFuzzyQuery. The classic parser sends x* and /re/ words to getPrefixQuery and getRegexpQuery, which this class never overrides.

Who is affected

#

Applications that run end-user query text through the opt-in ComplexPhraseQueryParser (Solr's {!complexphrase} builds on it), default settings, when a user field-qualifies a prefix or regexp word inside quotes. They get an unchecked exception from search instead of a ParseException, silently 0 hits, or a search on the other field. Nothing is corrupted. Rare.

Mechanism, terms and numbers541 words

ComplexPhraseQueryParser parses the text inside quotes a second time and, as its javadoc says, checks that every clause in it is for the phrase's own field. The check runs for term, wildcard, fuzzy and range clauses but not for prefix (id:2*) or regular-expression (id:/2/) clauses, because the class never overrides getPrefixQuery or getRegexpQuery. So "jo* id:2*" parses and the search then throws IllegalArgumentException: Clauses must have same field., "jo* id:9*" silently matches nothing, and the one-clause phrase name:"id:2*" searches field id. The prefix gap is as old as the class (2.9.0, 2009), the regexp gap dates from 4.0.0-alpha, and both are still on main; two small overrides fix it.

The check and where it is missing

#
  • The class javadoc: the second pass parses phrase content "checking all embedded clauses are referring to the same field and therefore can be rewritten as Span queries" (ComplexPhraseQueryParser.java:51-53).
  • checkPhraseClauseIsForSameField (:153-164) throws ParseException("Cannot have clause for field ... nested in phrase for field ..."). It is called only from newTermQuery (:141-151, wrapped in a RuntimeException because that method cannot throw a checked exception), getWildcardQuery (:166-172), getRangeQuery (:174-182) and getFuzzyQuery (:198-205).
  • The classic parser's handleBareTokenQuery sends x* words to getPrefixQuery and /re/ words to getRegexpQuery (QueryParserBase.java:747-754). Both build their query directly (:709-715, :679-686), and ComplexPhraseQueryParser overrides neither, so their field is never checked. No commit ever added or removed such an override (git log -S).

What happens at search time (ComplexPhraseQuery.rewrite)

#
  • One clause: a lone TermQuery, MultiTermQuery or SynonymQuery is returned unchanged (:261-265). id:2* is a MultiTermQuery, so name:"id:2*" runs as id:2* on field id.
  • Several clauses: each clause is rewritten (:285). A foreign prefix or regexp that matches terms becomes a span clause on field id: a span term when it matches one term (id:2* rewrites to id:2, :317-318), a span OR when it matches several (:294-300, :371-414). Then new SpanNearQuery(...) (:333) throws IllegalArgumentException("Clauses must have same field.") (SpanNearQuery.java:119-126).
  • A foreign clause that matches nothing is replaced by a placeholder term on the phrase's field (:299-315, "Dummy clause because no terms found - must match nothing"): 0 hits, no error.

Same-root sibling

#

With a synonym analyzer, a plain word for another field becomes a SynonymQuery through QueryBuilder.newSynonymQuery instead of newTermQuery, so "smith id:dogs" (with dogs -> dogs|dog) also parses and fails at search, while "smith id:cats" is rejected. The two overrides do not cover it; fix B below does.

Exposure and likelihood170 words
  • Who is hit: code that parses user queries with ComplexPhraseQueryParser, default parser settings, documented classic syntax, public API. The trigger is a field qualifier on a prefix or regexp word inside a quoted phrase, for example title:"jo* author:sm*". No index size, setting or concurrency is involved.
  • Several clauses, the foreign clause matches a term: the rejection moves from parse() (a checked ParseException) to IndexSearcher.search (an unchecked IllegalArgumentException). Code that catches ParseException to report a bad query does not see it.
  • Several clauses, the foreign clause matches nothing: no error and 0 hits.
  • One clause: no error; name:"id:2*" searches field id. That field is one the user typed, and the classic syntax lets them search it at top level anyway (id:2*), so nothing new is reachable.
  • Assertions: -ea and -da behave the same.
  • Likelihood: rare. A malformed query shape in an opt-in parser; no report was found in the 17 years since 2.9.0. An open proposal (#16820) would deprecate this parser for Lucene 11.

Why it looks unintended

#
  • The class javadoc says pass 2 checks that "all embedded clauses are referring to the same field"; the original test expects parse() to reject "jo* id:1 smith".
  • Term, wildcard, fuzzy and range clauses are checked: "jo* id:2?" is rejected, "jo* id:2*" is not.
  • The same missing getRegexpQuery override in MultiFieldQueryParser was fixed as a bug (#5943).
The full argument251 words
  • The class promises the check. ComplexPhraseQueryParser.java:51-53 (quoted above); the pass-1 comment says pass 2 runs "with different set of syntax restrictions (i.e. all fields must be same)" (:119-121).
  • The original test pins it at parse time. TestComplexPhraseQuery.java:87: checkBadQuery("\"jo* id:1 smith\""); // mixing fields in a phrase is bad; checkBadQuery (:127-135) expects qp.parse(...) itself to throw. It dates from the class's creation (LUCENE-1486).
  • Every other clause kind is checked. QueryParserBase.java:688-693 calls getPrefixQuery "similar to getWildcardQuery" and a prefix "a special case of generic wildcard term"; :706-707 documents "throw in overridden method to disallow" as the way to reject input.
  • Later changes kept the rule. LUCENE-5530 (#6593, 4.8.0) made author:"fred* smith" work and kept the rejection of other-field clauses. LUCENE-7614 (#8665, 6.4.0) added the one-clause fast path but did not lift the check: name:"id:2?" and name:"id:2" are still rejected (probe).
  • Precedent. In #5943 (LUCENE-4878) the issue body quotes Simon Willnauer: "This is in-fact a bug in the MultiFieldQueryParser [...] MultifieldQueryParser should override getRegexpQuery but it doesn't"; it was fixed with the missing override in 4.2.1.
  • The recorded searches found nothing that says otherwise. No javadoc, test, CHANGES or MIGRATE entry, and no issue, PR or list thread among the recorded searches, presents prefix or regexp clauses as exempt. The adjudication, the verifiers and the cross-model reviews rated the intended-behaviour argument weak; a cross-model fact check agreed for intent but rated it moderate as a "not worth changing" compatibility argument, so a behaviour-changing fix is something to discuss.
The devil's-advocate check181 words

Strongest case for "intended": (1) the classic parser's docs say wildcard searches work "within single terms (not within phrase queries)" (classic/package-info.java:162-163); (2) the input is malformed, and the multi-clause form still fails, only later; (3) the parser always validated loosely: in #2560 (LUCENE-1486) its author, Mark Harwood, introduced the list of supported in-phrase operators with "these are not necessarily definitive answers or guarantees of correctly implemented support", and "john -percival" is a known non-working case commented out in TestComplexPhraseQuery.java:81-82; (4) LUCENE-7614's CHANGES entry says the parser "ignores double quotes around single token prefix, wildcard, range queries", so name:"id:2*" could be read as id:2*; (5) #16820 proposes deprecating the parser.

Why it fails: (1) is the generic limitation that ComplexPhraseQueryParser exists to lift, and its own javadoc states the same-field rule. (2), (3) and (5) are about severity and priority, not intent; (3) is about operators, while the field rule has a dedicated check and a test. (4) proves too much: the same entry names wildcard and range queries, yet name:"id:2?" and name:"id:[1 TO 2]" are still rejected.

Suggested fix

#

Recommended A: run the existing check in getPrefixQuery and getRegexpQuery (validated)

Override getPrefixQuery and getRegexpQuery in ComplexPhraseQueryParser to run the existing checkPhraseClauseIsForSameField in the second pass, then call super (16 lines). Validated on main: the repro passes with assertions on and off, as do the complexPhrase tests (two seeds) and the whole queryparser test module. A third override (fix B) also closes the synonym path.

All options and trade-offs3 options · 613 words

Fix A is the finder's patch; an independent verifier wrote the same two overrides without reading it. Fix B adds one more override for the same-root synonym path. Both were validated with gradle in a scratch worktree of 645d4fe14a20. Both change behaviour (queries that parse today are rejected), so they are a choice: the narrow fix A, which leaves the synonym path open, or the complete fix B, which also turns the other-field term-clause error from a wrapped RuntimeException into a plain ParseException.

A: run the existing check in getPrefixQuery and getRegexpQuery (validated) (recommended)

#

Two overrides next to the four existing checks, 1 file, +16 lines.

  @Override
  protected Query getPrefixQuery(String field, String termStr) throws ParseException {
    if (isPass2ResolvingPhrases) {
      checkPhraseClauseIsForSameField(field);
    }
    return super.getPrefixQuery(field, termStr);
  }

  @Override
  protected Query getRegexpQuery(String field, String termStr) throws ParseException {
    if (isPass2ResolvingPhrases) {
      checkPhraseClauseIsForSameField(field);
    }
    return super.getRegexpQuery(field, termStr);
  }

Trade-offs

  • The smallest change, in the style of the existing checks. A query that used to parse and then fail (or return nothing, or search the other field) now fails in parse(); anyone relying on name:"id:2*" searching field id would get a ParseException (worth a CHANGES line).
  • Same-field prefixes and regexps ("jo* smi*", "jo* name:smi*", "jo* /smi.h/") keep working.
  • Leaves the synonym sibling ("smith id:dogs" with a synonym analyzer) open; fix B closes it.
  • Solr's {!complexphrase} would get the check: on apache/solr main its getPrefixQuery override calls super and getRegexpQuery is inherited (read, not run).

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20, OpenJDK 25.0.3: the repro fails on stock with assertions on and off and passes with the fix, on and off.
  • org.apache.lucene.queryparser.complexPhrase.* (12 tests: the repro 1, upstream TestComplexPhraseQuery 11) passes with seeds DEADBEEF and CAFEBABE; the whole :lucene:queryparser:test passes with seed DEADBEEF (31 test classes, 534 tests, 1 skipped, 0 failures).
  • An independent verifier's 9-test probe: 8 of 9 pass; only the synonym case ("smith id:dogs") still fails, as expected.
  • A probe of 13 queries with the fix: every other-field prefix and regexp clause, including "jo* id:9*" and name:"id:2*", is rejected by parse() with the usual ParseException; the same-field controls still find john smith.
  • Earlier, with the fix shadowed: the finder's, the independent reproduction's and separate tests and upstream TestComplexPhraseQuery all pass.

B: A plus a check in getFieldQuery(String, String, boolean), which also covers synonyms (validated)

#

Fix A plus one more override, +9 lines; every plain word passes through it before QueryBuilder builds a term, synonym, boolean or phrase query.

  @Override
  protected Query getFieldQuery(String field, String queryText, boolean quoted)
      throws ParseException {
    if (isPass2ResolvingPhrases) {
      checkPhraseClauseIsForSameField(field);
    }
    return super.getFieldQuery(field, queryText, quoted);
  }

Trade-offs

  • Also rejects "smith id:dogs" with a synonym analyzer at parse time.
  • Side effect: a term clause for another field ("jo* id:2") is then rejected with a plain ParseException instead of a RuntimeException wrapping one; the newTermQuery check becomes redundant on that path but is harmless.
  • A broader change than the bug strictly needs; the synonym path's history was not traced.

Trade-offs

Downstream note

#

Solr's {!complexphrase} parser subclasses this class and adds no field check of its own: on apache/solr main (read 2026-11-01) its getPrefixQuery override calls super and getRegexpQuery is inherited; older Solr (8.8.1) inherits both. So by reading the source it has the same gap and would pick up the upstream fix (not run).

How it was found

#

Found by reading the parser's second-pass overrides while working out its same-field rule: four factory methods run the check, and the prefix and regexp factories are not overridden. Probes and a public-API JUnit then confirmed it on main, 10.5.2 and 9.12.3.

Finding record

LFV-715, snapshot of 2026-11-09

Registry title
ComplexPhraseQueryParser skips its same-field check for prefix and regular-expression clauses: "jo* id:2*" parses and then fails at search time with IllegalArgumentException, and name:"id:2*" searches field id
Area
queryparser / complexPhrase: ComplexPhraseQueryParser (pass-2 same-field check for clauses nested in a phrase)
Priority
Low, rank 1090: An unusual field-qualified prefix or regexp clause inside a complex phrase fails loudly at search time instead of at parse time in the opt-in parser.
Impact class
wrong error
Impact note
Hits applications that use the opt-in ComplexPhraseQueryParser (default parser settings, documented classic syntax) only when a user writes a prefix or regular-expression clause that names another field inside a quoted phrase: in a multi-clause phrase ("jo* id:2*", "jo* id:/2/") parse() accepts what it rejects for term, wildcard, fuzzy and range clauses, and the search then throws an unchecked IllegalArgumentException 'Clauses must have same field.' (or silently matches nothing when the foreign clause matches no term: "jo* id:9*" returns 0 hits and no error [exec: main 645d4fe14a20, -ea and -da, 2026-11-01]), while a one-clause phrase (name:"id:2*", name:"id:/[23]/") raises no error and searches field id; -ea and -da behave the same, no scale is needed, and nothing is corrupted.
Summary
You parse a quoted phrase such as "jo* id:2*" or "jo* id:/2/" with ComplexPhraseQueryParser on the default field name; its class javadoc says the second pass checks that all embedded clauses refer to the same field, and it rejects "jo* id:2", "jo* id:2?", "jo* id:2~1" and "jo* id:[1 TO 2]" at parse time, so you expect a parse error. Instead parse() succeeds, because the check is wired into newTermQuery, getWildcardQuery, getRangeQuery and getFuzzyQuery but the class never overrides getPrefixQuery or getRegexpQuery, and the search then throws IllegalArgumentException 'Clauses must have same field.'. A one-clause phrase such as name:"id:2*" also parses, and because rewrite returns a lone multi-term query unchanged, it searches field id and returns the document whose id is 2.
Introduced
f7fa57997191 (LUCENE-1486, GitHub #2560, the initial commit of ComplexPhraseQueryParser, 2009-07-06; Subversion era, no pull request) for the prefix forms: it applied checkPhraseClauseIsForSameField in newTermQuery, getWildcardQuery, getRangeQuery and getFuzzyQuery but never overrode getPrefixQuery, although the classic grammar already sent prefix tokens there (QueryParser.jj at f7fa5799719). The regexp forms come from 838e19beae1f (LUCENE-2604, #3678, 2010-08-30), which added regexp syntax and QueryParser.getRegexpQuery without an override in this class. The one-clause search on the other field comes from LUCENE-7614 (#8665; 52f2a77b78fc on master, backport ac85a41cbefa on branch_6x, 2017-01-05), whose rewrite fast path returns a lone MultiTermQuery unchanged; before it, the one-clause form threw 'Unknown query type' at search. Not a regression: the gap is as old as the class [read: git log -S getPrefixQuery and -S getRegexpQuery over every path of the file return no commit; executed: shadowing only this class, the 2.9.0 and 4.0.0 sources with the missing overrides pass while the unmodified sources fail, and the 6.3.0 class on 6.4.0 jars restores the 6.3.0 one-clause behaviour] (2009-07-06 (prefix forms, LUCENE-1486); 2010-08-30 (regexp forms, LUCENE-2604); 2017-01-05 (one-clause search on the other field, LUCENE-7614))
