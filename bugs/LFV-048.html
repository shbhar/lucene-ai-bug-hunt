BooleanScorer loops forever on the last 4,096-doc window of a segment of about 2^31 documents, and a query timeout cannot stop it

On a segment of more than 2,147,479,552 documents (Lucene allows 2,147,483,519), a pure SHOULD disjunction run as a count, sort or other exhaustive search never returns once it matches a doc ID at or above 2,147,479,552: the window end windowBase + 4096 overflows int. A query timeout cannot stop it.

The finding in 30 seconds

#

BooleanScorer.scoreWindow computes the window end as Math.min(max, windowBase + 4096) in int. In the last window below 2^31 the sum is exactly 2^31 and wraps to Integer.MIN_VALUE, so the window is empty, nothing advances and score() asks for the same window again, forever.

How BooleanScorer walks a segment

#
  1. A BooleanQuery of only SHOULD clauses, run by a collector that needs every match (a count, a sort, facets), is scored by BooleanScorer. The default relevance top-k search uses a different scorer.
  2. BooleanScorer works in windows of 4,096 doc IDs. It finds the window of the next match, windowBase = doc & ~4095, and ends it at windowMax = min(max, windowBase + 4096).
  3. It collects every clause's matches below windowMax, then moves to the window of the next match, until no clause has a match left.

The finding, step by step

#
  1. Index IndexWriter.MAX_DOCS = 2,147,483,519 documents with the default config into one segment: a plain addDocument loop of empty documents and commit gave one 30 MB segment that CheckIndex reports clean. Doc 2,147,483,319 has f:a, doc 2,147,483,419 has f:b.
  2. Run searcher.count(f:a OR f:b), two SHOULD term clauses. You expect 2 at once; the relevance search search(q, 10) on the same index returns both docs in 0.015 s.
  3. Instead count never returns (still running after 20 s, one core busy), and neither does search(q, 10, Sort.INDEXORDER). With a 1 s QueryTimeout set, the count is still running after 20 s. With a one-line fix, count returns 2 in 0.006 s.
  4. Why: these searches use BooleanScorer, which works in windows of 4,096 doc IDs. The window of doc 2,147,483,419 starts at 2,147,479,552, so its end is 2^31 = 2,147,483,648, one more than an int holds: it wraps to -2,147,483,648. No doc is below a negative end, so nothing is collected, no iterator moves, and the scorer re-enters the same window forever.

Who is affected

#

Only indexes with one segment of more than 2,147,479,552 documents, at most 3,966 below Lucene's hard limit. There, every pure SHOULD disjunction run as a count, sort, facet or other exhaustive collection that matches a document at doc ID 2,147,479,552 or above hangs a search thread. Default relevance top-k and single-term queries are safe.

Mechanism, terms and numbers925 words

BooleanScorer, the bulk scorer for pure disjunctions in every score mode except TOP_SCORES (with minShouldMatch > 1 only for dense clauses), scores a segment in windows of 4,096 doc IDs. For the window of the next match it computes windowMax = Math.min(max, windowBase + SIZE) in int. For a match at doc ID 2,147,479,552 (2^31 - 4096) or above, the sum is 2^31 and wraps to Integer.MIN_VALUE, so the window is empty: nothing is collected, no iterator advances, and score() gets the same window back forever. IndexWriter.MAX_DOCS is 2,147,483,519, so 3,967 legal doc IDs sit in that window, and a segment with maxDoc of at least 2,147,479,553 and a match there is enough. On a real, CheckIndex-clean segment of MAX_DOCS documents written with nothing but addDocument and commit, IndexSearcher.count(f:a OR f:b), an index-order sort and a count under a 1 s QueryTimeout were all still running after 20 s, while search(q, 10) returned in 0.015 s; the timeout cannot help because TimeLimitingBulkScorer checks it only between calls. The one-line fix Math.min -> MathUtil.unsignedMin, the helper the other windowed bulk scorers in core's search package use, makes all three return correct results. The unguarded sum is as old as BooleanScorer; every published release jar loops on the same layout.

The window arithmetic

#

BooleanScorer.java on main 645d4fe14a20: SIZE = 1 << 12 = 4,096 and MASK = SIZE - 1 (:33-35); in scoreWindow (:270-272):

final int windowBase = top.doc & ~MASK; // find the window that the next match belongs to
final int windowMin = Math.max(min, windowBase);
final int windowMax = Math.min(max, windowBase + SIZE);

For any doc in the last window, windowBase is 2,147,479,552 and windowBase + SIZE is 2,147,479,552 + 4,096 = 2^31, which as an int is Integer.MIN_VALUE.

One round of the loop (two clauses on doc 2,147,483,419, max = NO_MORE_DOCS)

#
  1. score() (:295-303) advances the clauses to the doc and loops while (top.doc < max) top = scoreWindow(...).
  2. windowMax is Integer.MIN_VALUE, so head.top().doc < windowMax is never true (:277): one lead only.
  3. With minShouldMatch == 1 that takes the single-scorer path (:281-286). There end = Math.max(windowMax, Math.min(max, nextWindowBase)) is 2,147,479,552, the other clause's window base (:247-248), which is not above the doc: the collect loop runs zero times and the clause stays put (:256-261). It goes back into the queue.
  4. score() gets the same top back and calls scoreWindow again. The only work per round is two setScorer calls and a priority-queue pop and insert.
  5. With minShouldMatch > 1 the multiple-scorer path tests candidate.doc < windowMax (:211), which is never true either; nothing is scored (run in the study's direct tests). Needing scores does not change the path: with minShouldMatch == 1 the single-scorer path of step 3 is taken with or without scores, because maxFreq is always 1 in this window.

Why nothing outside stops it

#
  • TimeLimitingBulkScorer checks queryTimeout.shouldExit() before each call to the wrapped score (TimeLimitingBulkScorer.java:70-86); the call that enters the last window never returns (run). Its smaller per-call max (:73) does not help: Math.min of any positive max and Integer.MIN_VALUE is still Integer.MIN_VALUE.
  • ExitableDirectoryReader checks when doc values iterators move (ExitableDirectoryReader.java:110-331, check at :486-497), when vectors are searched or iterated (:333-479, :499-703), when points are visited (:705-942) and when terms are enumerated (:944-1018); the loop reads nothing from the index (by reading).
  • The loop does no I/O and checks no interrupt flag, so Thread.interrupt() does not stop it (by reading).

Which searches take it

#

BooleanScorer is built in one place, BooleanScorerSupplier.optionalBulkScorer (:337), used when the query has no MUST or FILTER clause (:210-232): always with minShouldMatch <= 1 (cost threshold -1), with minShouldMatch > 1 only for dense clauses (cost >= maxDoc / 3). TOP_SCORES goes to MaxScoreBulkScorer instead (with minShouldMatch > 1 to the fallback scorer; :315-328). Every other mode builds BooleanScorer: TotalHitCountCollector (COMPLETE_NO_SCORES), TopFieldCollector for a non-relevance sort (TOP_DOCS or COMPLETE...), FacetsCollector (COMPLETE or COMPLETE_NO_SCORES), and relevance top-k with exact hit counting (COMPLETE; by reading). With MUST_NOT clauses, ReqExclBulkScorer wraps it when the positive cost is above 0.3% of maxDoc (by reading, not run).

IndexSearcher.count first tries a two-term shortcut (IndexSearcher.java:506-520): with no deletions and two TermQuery clauses, if one count is 0 or below 10% of the other, it counts without BooleanScorer. Otherwise, and for 3+ clauses, non-term clauses or a reader with deletions, it collects with a TotalHitCountCollector (:525-528), which asks Weight.count for each leaf (TotalHitCountCollector.java:48). That is -1 for two clauses that each match some but not all docs, so the leaf is collected with BooleanScorer. In every run here both terms match one doc. Sorts and facets have no shortcut.

The other windowed bulk scorers in core's search package guard the same sum with MathUtil.unsignedMin (ConstantScoreBulkScorer, DisjunctionMaxBulkScorer, MaxScoreBulkScorer, DenseConjunctionBulkScorer, BlockMaxConjunctionBulkScorer, TimeLimitingBulkScorer, and BitSetDocIdStream, which BooleanScorer itself uses for its window) or a long cast (ReqExclBulkScorer). Outside core, DrillSidewaysScorer in the facet module has the same unguarded window sum (a separate bug, LFV-383).

Exposure and likelihood268 words
  • Who. Applications with one segment of more than 2,147,479,552 documents. The whole index is capped at IndexWriter.MAX_DOCS = 2,147,483,519, so that means an index at most 3,966 documents below the hard limit with almost all of it in one segment. A plain addDocument loop of empty documents under the default config produced one (a single flushed segment; with real documents the writer would flush many segments, an inference); forceMerge(1), the general route, does too, because TieredMergePolicy drops its segment-size cap for a single-segment forced merge, and so does addIndexes (the study's segment).
  • Settings. Default codec, IndexWriterConfig and IndexSearcher. Only the size is unusual.
  • Queries. Pure SHOULD disjunctions of 2 or more clauses with a match in the last window, run as a count, an index-order or field sort, a facet collection or any other exhaustive collection. Not affected: default relevance top-k (search(q, n), TOP_SCORES, with the default hit-count threshold), single-term queries, and FILTER + SHOULD queries (another scorer).
  • Effect. The call never returns and keeps one core busy. Hits before the last window are collected first, then the loop starts. No exception was thrown in any run, the loop logs nothing (by reading), and IndexSearcher#setTimeout does not help (run). Every such request takes a search thread for good (an inference, not run). The index is not touched.
  • Likelihood: contrived. Almost no deployment holds 2.1 billion documents in one segment; one that does hits it on every such query, deterministically.
  • Mitigation until fixed (by reading, not run): keep segments at or below 2,147,479,552 documents, for example do not forceMerge(1) an index near the limit.

Why it looks unintended

#
  • IndexWriter.MAX_DOCS (2,147,483,519) is the only documented document limit, and Lucene's own @Monster test builds and searches a segment of exactly that size.
  • BulkScorer.score must collect the matches in [min, max) and return; this call never returns.
  • Core's other windowed bulk scorers guard the same window sum with MathUtil.unsignedMin or a long cast; BooleanScorer never had a guard.
The full argument229 words
  • The only documented limit is MAX_DOCS. "Hard limit on the maximum number of documents that may be added to the index" (IndexWriter.java:201-208). LUCENE-5843 added it so that adding more throws "instead of silently creating an unusable index" (CHANGES.txt). IndexReader.maxDoc() is "one greater than the largest possible document number", so doc ID 2,147,483,518 is legal. No search-side limit is documented.
  • Lucene's own test builds this state. TestIndexWriterMaxDocs.testExactlyAtTrueLimit (@Monster) adds exactly MAX_DOCS documents, searches them before and after forceMerge(1), and asserts that doc MAX_DOCS - 1 comes first in a reverse doc-ID sort. It uses a single TermQuery, which never reaches BooleanScorer.
  • The BulkScorer contract. score "Collects matching documents in a range and return[s] an estimation of the next matching document which is on or after max"; the return value "must be >= max".
  • The project treats this overflow as a defect. #14750 (2025) added MathUtil#unsignedMin because dividing the doc ID space into windows "is prone to integer overflows if the size of the window is greater than Integer.MAX_VALUE - windowStart". The scorers it touched already had long casts that it replaced; BooleanScorer never had a guard and was not in it.
  • Nothing describes the hang. No comment, test, CHANGES or MIGRATE entry; no commit message on the file mentions overflow; the LUCENE-6184 discussion does not discuss it.
The devil's-advocate check136 words

The strongest case for "not a bug": the scale is absurd (one segment of 2.1 billion documents), BooleanScorer is package-private and the minimal test builds it directly, and the cross-model refute review (OpenAI GPT-5.6) returned "not real".

Why it fails: the size is legal by Lucene's own documentation and its own @Monster test; the hang shows through IndexSearcher.count, Sort.INDEXORDER and a timed count on a real index written with plain addDocument, and the one-line fix makes all three return. The cross-model verdict was procedural: it could not open any file or run anything and saw only the claim's text, and it gave low confidence; its one substantive point, that "only its package-private direct test is visible in the supplied text", is answered by the real-index run. Scale argues for low priority, not for intent.

Suggested fix

#

Recommended Compute the window end with MathUtil.unsignedMin

In BooleanScorer.scoreWindow, compute the window end with MathUtil.unsignedMin(max, windowBase + SIZE) instead of Math.min, the helper the other windowed bulk scorers in core's search package use. The wrapped sum then counts as larger than any max, so the last window ends at max. With it the repro and all 2,340 core search tests pass, with assertions on and off.

import org.apache.lucene.util.MathUtil;
...
// BooleanScorer.scoreWindow, instead of: Math.min(max, windowBase + SIZE)
final int windowMax = MathUtil.unsignedMin(max, windowBase + SIZE);

Compute the window end with MathUtil.unsignedMin (validated by the checks) (recommended)

#

BooleanScorer.java:272 plus one import, +2/-1 lines.

import org.apache.lucene.util.MathUtil;
...
// BooleanScorer.scoreWindow, instead of: Math.min(max, windowBase + SIZE)

Trade-offs

  • Integer.MIN_VALUE is 2^31 as an unsigned value, above any legal max (at most NO_MORE_DOCS = 2^31 - 1), so the last window ends at max; every other window is unchanged. Exhausted clauses sit at NO_MORE_DOCS, which is not below that end.
  • Cost: one unsigned compare per 4,096-doc window.
  • The same helper and pattern as ConstantScoreBulkScorer, DisjunctionMaxBulkScorer and MaxScoreBulkScorer.

What the checks validated

  • Scratch worktree of 645d4fe14a20, gradle --offline, OpenJDK 25.0.3, seed DEADBEEF. Stock: the repro fails with assertions on and off.
  • With the fix: the 9 core TestBoolean* suites, the repro included, run 140 tests with 0 failures; all core org.apache.lucene.search.* tests (215 suites, 2,340 tests, including TestTimeLimitingBulkScorer and TestTotalHitCountCollector) pass; both with assertions on and off. Core's checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest pass. Other modules and the full core suite were not run.
  • On the real 2,147,483,519-document segment the same line makes count return 2 in 0.006 s, the index-order sort both docs in 0.009 s and the timed count 2 in 0.001 s.

Downstream note

#

A service that relies on IndexSearcher#setTimeout to bound slow requests is not protected here: the stuck call never reaches a timeout check, so each such request keeps a search thread busy.

How it was found

#

A study of integer overflows near Lucene's size limits used CodeQL to list every unguarded int window sum in the search code, and flagged windowBase + SIZE in BooleanScorer. A Z3 bit-vector query found the wrap in 0.011 s and proved the window correct below 2^31 - 4,096; a test and a run on a real segment confirmed the hang.

The method in full210 words

Method: formal (a static inventory, then SMT queries, then dynamic checks).

  • Inventory. A CodeQL query listed every int sum "x + C" (C >= 64) in the search, util, codecs and index code that is not wrapped in unsignedMin or a long cast: 63 rows. One was windowBase + SIZE in BooleanScorer.scoreWindow.
  • SMT. A Z3 bit-vector query with the documented limit maxDoc <= IndexWriter.MAX_DOCS as the precondition found a counterexample in 0.011 s (topDoc = 2147480836); a second query proved windowMax > topDoc for every topDoc < 2^31 - 4096, and a third that in the overflow case the single-scorer path collects nothing. cvc5 agreed.
  • Confirmation. A direct JUnit failed on main; an independent study verifier wrote 16 tests (12 through IndexSearcher with a FilterLeafReader reporting maxDoc = MAX_DOCS and 4 direct BooleanScorer tests; 10 bug tests and 6 controls in all) and built a real 2,147,483,519-document segment with addIndexes, on which count and the index-order sort hung and the fix returned at once.
  • Then a main refresh, a current-main reproducer, a cross-model review (OpenAI GPT-5.6, which could not run), a tie-breaker who built a segment with plain addDocument, a history sweep over every release jar, a prior-report search and a repro-minimization step followed.

History

#

As old as BooleanScorer: the window end has been an unguarded int sum since the 2001 import (release 1.0.1); LUCENE-6184 (5.1.0, 2015) wrote today's line. A direct probe loops on all 164 published release jars from 1.2 to 10.6.0 and on main. Not fixed upstream.

Versions tested7 rows

Introduced by bd3948c539ec "Initial revision" (2001-09-18, svn r149570), the import of the Lucene sources into the Apache repository: the window end was already an unguarded int sum. Later rewrites kept it, among them 6f8347c6fef (2004, end += BucketTable.SIZE), 10a852570a1 (LUCENE-6179, 5.0.0), cb3ec682d41 / branch_5x 5c9b5e7ea4e (LUCENE-6184, 2015-01-19, today's windowMax = Math.min(max, windowBase + SIZE), first released in 5.1.0), and #13931 (10.1.0, same line). #13605 (2024; 8d4f7a6e99d on main, backport 24de36cc28c in 9.12.0) raised the window from 2,048 to 4,096 IDs, which moved the trigger from the last 1,919 legal IDs to the last 3,967.

Reach through IndexSearcher differs by era (by reading): 8.0.0 on, every score mode except TOP_SCORES; 5.0.0-7.7.3, every score mode; 1.9-2.4.1, opt-in only. Whether old IndexWriters could build such a segment was not checked.

LFV-048, snapshot of 2026-11-02

Registry title
BooleanScorer loops forever on the last 4096-doc window of a segment of about 2^31 documents, and a query timeout cannot stop it
Area
search / scoring
Priority
Low, rank 818: BooleanScorer loops forever, and timeouts cannot stop it, on the last window of a segment holding about 2^31 docs, severe, but at an extreme scale that almost no deployment reaches.
Impact class
hang
Impact note
Holders of one segment filled to within 3,967 docs of IndexWriter.MAX_DOCS (for example a read-only shard force-merged to one segment) that run count, index-order or field-sorted, facet or other exhaustive disjunction queries; default configuration otherwise; deterministic once such a segment exists; every release from 1.0.1 (1.2 the oldest executed) to 10.6.0 and main.
Summary
You run a pure disjunction of two or more SHOULD clauses as a count, an index-order or field sort, or a facet collection (any score mode other than TOP_SCORES) on a segment with maxDoc >= 2,147,479,553 and a match in its last 3,967 doc ids. You expect the search to return. Instead windowMax = Math.min(max, windowBase + 4096) wraps to Integer.MIN_VALUE, no iterator advances and the thread spins at 100% CPU forever: on a real, CheckIndex-clean segment of 2,147,483,519 docs, count(f:a OR f:b) and an index-order sort hung while search(q, 10) returned at once.
