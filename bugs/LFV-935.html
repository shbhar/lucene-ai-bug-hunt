QualityStats.average(...).getPrecisionAt(n) extrapolates an already averaged precision: mean P@10 0.4 instead of 0.6

Average a query with 10 relevant hits (P@10 = 1.0) and one with only 2 (P@10 = 0.2), and QualityStats.average(stats).getPrecisionAt(10) returns 0.4, not the mean 0.6. Above the mean result count, the average drops the mean it stored and extrapolates again; the printed SUMMARY hides those cutoffs.

The finding in 30 seconds

#

QualityStats.average() stores the right mean P@n for every cutoff, but it also sets the result count to the mean result count, and getPrecisionAt(n) then extrapolates once more for every n above it.

Background: precision at n in Lucene's benchmark module

#
  1. QualityBenchmark.execute(...) runs each judged query and returns one QualityStats per query. getPrecisionAt(n) is the share of relevant hits among the top n results, for n = 1 to 20.
  2. If a query returned fewer than n results, the missing ranks count as non-relevant: 2 relevant hits out of 2 results give P@10 = 2/10 = 0.2. trec_eval's P_10 is defined the same way.
  3. QualityStats.average(stats) combines the queries into one object; its MAP, recall, MRR and P@n are meant to be the means over the judged queries (those with at least one relevant document).

The finding, step by step

#
  1. You score a run with the benchmark module's QualityBenchmark and setMaxResults(10). Query "apple" returns 10 hits, all relevant: P@10 = 1.0. Query "banana" has only 2 hits, both relevant: P@10 = 2/10 = 0.2, because missing ranks count as non-relevant, as in trec_eval.
  2. You call QualityStats.average(stats).getPrecisionAt(10) and expect the mean, (1.0 + 0.2) / 2 = 0.6. average() does compute 0.6 and stores it.
  3. Instead you get 0.4. average() also sets the result count to the mean, (10 + 2) / 2 = 6, and for n above 6 getPrecisionAt(n) treats the average like one short query: it ignores the stored 0.6 and returns 6 x P@6 / 10 = 6 x 0.667 / 10.
  4. No error. Here P@7 to P@20 are all wrong (P@20 0.2 instead of 0.3). Other inputs give too-high values (P@6 0.458 instead of 0.417) or 0 at every cutoff when the mean result count is below 1. MAP, recall and MRR are right.
  5. The SUMMARY that log() prints shows only P@1 to P@5 here, the cutoffs below the mean result count, so it never shows a wrong number. Only code that reads the averaged P@n gets one.

Who is affected

#

Code that reads QualityStats.average(stats).getPrecisionAt(n) in the opt-in benchmark module, when the judged queries return different numbers of results and n (at most 20) is above their mean: for example setMaxResults below 20, a small collection, or queries with few or no hits. The printed SUMMARY is not affected.

Mechanism, terms and numbers793 words

Lucene's benchmark module can score a search run the way TREC does. QualityBenchmark returns one QualityStats per judged query, and QualityStats.average(stats) combines them into one object whose getters are the means over the judged queries (those with at least one relevant document). For precision at n, average() computes and stores the correct mean for every cutoff 1 to 20, but it also sets the object's result count to the mean result count. getPrecisionAt(n) then treats the average like a single query that returned fewer than n hits: for every n above the mean result count it ignores the stored mean and extrapolates a second time. Two queries with 10 and 2 relevant hits give an averaged P@10 of 0.4 instead of 0.6. The value is silently wrong (too low, too high, or 0 when the mean result count is below 1); per-query values, MAP, recall and MRR are right, and the SUMMARY that log() prints never shows an affected cutoff. Only code that reads the averaged P@n through the API sees it, in the opt-in benchmark module. The code has been this way since the package was added (LUCENE-836, first released in 2.3.0).

The contract

#
  • Class javadoc: "Results of quality benchmark run for a single query or for a set of queries" (QualityStats.java:24).
  • average(): "Create a QualityStats object that is the average of the input QualityStats objects" (:189-194).
  • getPrecisionAt(n): "Return the precision at rank n", for any n from 1 to MAX_POINTS = 20 (:104-109), with no restriction to n <= getNumPoints().
  • getMRR(): "the Mean reciprocal rank over the queries or RR for a single query" (:267-268): the getters of an averaged object are means over the queries.

The mechanism

#
  1. One query. addResult(n, ...) sets numPoints = n and stores the precision at n in pAt[n] for n <= 20 (:92-99); pAt[0] is "unused" (:72). When the query returned fewer than n results, getPrecisionAt(n) returns (numPoints * pAt[(int) numPoints]) / n (:115-116), which is relevant hits found / n. Correct.
  2. The average. For each query with judgements (:206), average() adds stat.getPrecisionAt(j) to avg.pAt[j] for every j = 1..20 (:214-216), with that extrapolation already included, and adds stat.numPoints to avg.numPoints (:209). Then avg.numPoints /= m (:224) and avg.pAt[j] /= m (:228-230). Now avg.pAt[j] is the correct mean P@j for every j, and avg.numPoints is the mean result count M.
  3. The second extrapolation. avg.getPrecisionAt(n) with n > M takes the one-query branch and returns M * avg.pAt[floor(M)] / n (:115-116), discarding the stored mean avg.pAt[n].
  4. Not affected. log() prints P@i only for i < (int) numPoints (:162), so the SUMMARY shows only cutoffs below M, where the branch does not run. MAP, recall and MRR are averaged directly.

When the value is wrong

#

With f = floor(M) and R_i(k) the relevant hits of query i in its top min(k, length) results, the returned value is (M / f) x mean R_i(f) / n and the correct one is mean R_i(n) / n. They agree when every query returned the same number of results. With a whole-number M they agree exactly when no query has a relevant hit at ranks f + 1 to n; with a fractional M they differ except in special cases where the two sides happen to be equal (lists [relevant, relevant] and [relevant] give M = 1.5 and every cutoff right; [relevant, not relevant] and [relevant] give P@2 0.75 instead of 0.5 with no relevant hit after rank 1). The error goes both ways. When M < 1, f = 0 and the branch reads the never-filled avg.pAt[0], so every P@n is 0. (Earlier records said the value is right unless a query has a relevant hit between rank f + 1 and n; that holds only for a whole-number M or M < 1: with 4 and 7 results, M = 5.5, neither query has a relevant hit at rank 6 and P@6 is still 0.458 instead of 0.417.)

Exposure and likelihood239 words
  • Opt-in tool. lucene/benchmark's search-quality package is a developer evaluation tool; nothing in indexing or search uses it.
  • Only programmatic reads. QueryDriver (trec/QueryDriver.java:101-102) and the package's documented sample (package-info.java:68-69) call only average() and log(), and log() prints only the cutoffs below the mean result count, so the printed SUMMARY never shows an affected cutoff. A program that reads avg.getPrecisionAt(n) (as upstream TestQualityRun does for n = 1..20) gets the wrong value silently.
  • When. The judged queries return different numbers of results and n is above their mean. The default maxResults is 1000 (QualityBenchmark.java:64; QueryDriver and the sample also use 1000), which keeps the mean above 20 whenever the judged queries return more than 20 hits on average (broad queries on a larger collection; in upstream TestQualityRun it is 247.6), but not with setMaxResults below 20, a small collection, very selective queries, or queries with no hits.
  • Size of the error. 0.4 instead of 0.6 (P@10, the example), 0.4125 instead of 0.5625 (P@8, an end-to-end run with setMaxResults(8)), 0.458 instead of 0.417 (P@6), and 0 at every cutoff when the mean result count is below 1. Per-query values, MAP, recall and MRR are right.
  • How likely: rare. A maintainer who runs relevance experiments, Robert Muir (@rmuir), has said they use the module's QueryDriver to run the queries and send its output to trec_eval (#9048, 2017; also #3263, 2010), which bypasses this path.

Why it looks unintended

#
  • average() is documented as "the average of the input QualityStats objects" and stores the correct mean P@n for every cutoff; the extra extrapolation discards it.
  • For a fractional result count the formula is no query's precision; below 1 it returns 0.
  • Upstream TestQualityRun reads the averaged P@n at all 20 cutoffs (with 1000 results, so the branch never runs).
The full argument190 words
  • Contract. The class holds results "for a single query or for a set of queries" (QualityStats.java:24); average() creates "a QualityStats object that is the average of the input QualityStats objects" (:189-194); getPrecisionAt(n) accepts any 1 <= n <= 20 (:104-109); getMRR() is "the Mean reciprocal rank over the queries" (:267-268).
  • average() computes the right answer. It fills avg.pAt[j] with the mean P@j for every j = 1..20 (:214-216, :228-230); the stored means above the mean result count are never returned, and nothing documents why they should be discarded.
  • trec_eval. Its P_n counts missing ranks as non-relevant per query and reports the mean over queries; the per-query getPrecisionAt follows it, and the exhaustive check found 0 per-query mismatches.
  • Upstream test. TestQualityRun asserts 1.0 > avg.getPrecisionAt(j) for j = 1..20 (TestQualityRun.java:149-153), with maxResults = 1000 (:54, :85), so the branch never runs there and the assertion holds either way.
  • History. The branch and average() came together in LUCENE-836 (98fa2d898d1, 2007); no javadoc, CHANGES entry, test or comment on LUCENE-836 (#1911) describes extrapolating an average.
The devil's-advocate check135 words

The strongest case (the cross-model review, the intended-behaviour check and the refute-lens cross-model review): the averaged object is a synthetic query whose length is the mean result count, so cutoffs above it are extrapolated like a short query's, and log() agrees by printing only cutoffs below numPoints. The reading is coherent but undocumented and weak.

Why it fails: average() computes and stores the true mean for every cutoff, which would be pointless under that reading; a fractional length is not a query, and for a mean below 1 the formula returns 0 at every cutoff; the javadoc calls the object an average of the inputs; nothing documents synthetic-query semantics. log() hiding the cutoffs explains why nobody noticed, not that it is intended. The cross-model reviews rated the argument moderate, and every reviewer rejected it.

Suggested fix

#

Recommended Do not extrapolate the averaged object

Mark the object that average() returns and skip the one-query extrapolation for it, since its pAt[] already holds the mean for every cutoff (1 file, +4/-1). With it the repro and the quality tests pass with assertions on and off, and the whole benchmark module passes; the SUMMARY output is unchanged.

@@ average(QualityStats[] stats)

Trade-offs

  • Smallest change; per-query objects behave exactly as before.
  • getNumPoints() of the average still returns the mean result count, and log() is unchanged, so the SUMMARY output is identical.
  • Edge cases unchanged: with no input stats every P@n stays 0; with no judged query (possible only with assertions off) the values stay NaN.

Downstream note

#

The Lucene.NET port of the benchmark module has the same code in QualityStats.cs, so its averaged P@n has the same error.

How it was found

#

A bounded-exhaustive differential check ran the stock QualityStats against an independent implementation of trec_eval's P@n, average precision, recall and reciprocal rank over every small set of relevance lists. Per-query values all matched; 341,559 of 1,181,520 averaged P@n values did not, all at cutoffs above the mean result count.

The method in full143 words
  • Method (semi-formal). Translation validation of the stock jar: every ordered pair of relevance lists of length 0..5 (15,840 sets), every ordered triple of length 0..3 (3,375) and 39,861 random sets of 1-8 queries with 0-30 results (59,076 sets with a judged query in all), each compared at all 20 cutoffs with a reference written from trec_eval's definitions. Per query: 0 mismatches in 2,950,908 checks. Averaged: 341,559 of 1,181,520 P@n values (59,076 sets x 20 cutoffs) wrong, none when n <= the mean result count or when all lists have the same length; MAP, recall and MRR 0 mismatches; with the fix, 0 wrong. A mutant reference was detected (vacuity check).
  • First signal. A planning probe of the benchmark quality metrics against trec_eval found 6 of 20 averaged cutoffs wrong; the hunt unit re-ran and characterised it, then reduced it to a public-API JUnit.
