In no release: 10.6.0 does not have it; 11.0.0 would be the first release with it. On the 11.0 branch (branch_11x daa54f2e0cd3) the one test fails 1 of 1, assertions on and off; 10.6.0 passes 1 of 1. Background: how the tokenizer knows a top-level domain

#
  1. UAX29URLEmailTokenizer splits text into words like StandardTokenizer, but keeps URLs and e-mail addresses whole, as tokens of type <URL> and <EMAIL>.
  2. It gives an e-mail address at a domain name the type <EMAIL>, and a host name without a scheme the type <URL>, only when the name ends in a known top-level domain. The known domains are a table generated from IANA's public list and compiled into the tokenizer's scanner.
  3. The table is a dated copy of a list that changes. A build task regenerates it from the live list; by the build code it runs only when it is forced or when its saved checksums no longer match. Each line of development is regenerated on its own.

The finding, step by step

#
  1. You analyze text with UAX29URLEmailTokenizer (or UAX29URLEmailAnalyzer, or the uax29UrlEmail tokenizer factory). On 10.6.0 the address user@example.web is one token of type <EMAIL>. You move to a build of the 11.0 branch.
  2. You expect the same token. web is a top-level domain in the IANA list that the tokenizer's domain table is generated from (delegated 2026-07-23), and the 10.6.0 table has it.
  3. Instead, on the 11.0 branch (branch_11x) and on main you get two word tokens, user and example.web, both <ALPHANUM>. Nothing is thrown.
  4. Why: the table is generated data. The 10.x line regenerated it from the list of 2026-09-03 (1,438 domains). Main and branch_11x still carry the list of 2026-06-19 (1,437 domains). The two files differ by the date line and one entry, web.
  5. What it costs: an analyzed query for the address no longer matches the token that 10.6.0 indexed. In a test index of three documents written by 10.6.0 it finds 1 document on 10.6.0 and 0 on the 11.0 branch. In general the query becomes the two words; with the classic query parser's default operator (OR) it can still match a document that holds either word.

Who is affected

#

Only applications that use UAX29URLEmailTokenizer, UAX29URLEmailAnalyzer or the uax29UrlEmail factory, and only for one domain, web. StandardAnalyzer and StandardTokenizer do not use the table. An http or https URL is one token on every build. Only text that 10.6.0 itself analyzed can lose a match: every older release splits the address as branch_11x does. No release is affected. Rare.

Mechanism, terms and numbers1,217 words

UAX29URLEmailTokenizer splits text into words like StandardTokenizer and, in addition, keeps URLs and e-mail addresses whole, as tokens of type <URL> and <EMAIL>. It accepts an address at a domain name, or a host name without a scheme, as such a token only when the name ends in a known top-level domain. The known domains are a table, ASCIITLD.jflex, that a build task generates from IANA's public list and that is compiled into the scanner.

That table is a dated copy. On main and on the 11.0 release branch (branch_11x), both unreleased, it is the list of 2026-06-19 (1,437 domains), from the merged #16274. In the 10.6.0 release it is the list of 2026-09-03 (1,438 domains), from the merged #16592, which went to the 10.x line only. The two files differ by the date line and one entry, web, which IANA delegated on 2026-07-23, between the two dates. So 11.0.0 would know one current domain fewer than the release before it.

Nothing is wrong with the tokenizer's logic and no stated guarantee is broken: every build does what its table says, and main's table was current on the day it was generated. The repair is the project's routine regeneration of the table and the scanner. Its scanner step was run for this finding on 2026-11-15, outside the build and with the table of the 10.6.0 tag, and the repro test passes on the regenerated scanner; the gradle task itself, which takes IANA's list of the day, was not run then. Update 2026-11-17: it has been run since, in a scratch checkout of pull request #17035 (merged on 2026-11-19; it left the table as it was), and the repro test passes on the scanner that run generated (see the fix). Where the table decides

#

Line numbers are those of main 781025d6fe32.

  1. UAX29URLEmailTokenizerImpl.jflex:124: %include ASCIITLD.jflex, the only include of the table in the tree. StandardTokenizer has no such table.
  2. :128: DomainNameStrict = {DomainLabelSequence} ({ASCIITLD} | {ASCIITLDprefix_1CharSuffix} | {ASCIITLDprefix_2CharSuffix}). A strict domain name must end in a listed domain.
  3. :198: EMAIL = {EMAILlocalPart} "@" ({DomainNameStrict} | {EMAILbracketedHost}), and :297 returns the type <EMAIL> for it. Without the entry the rule cannot match user@example.web, and the word rules give user and example.web.
  4. A host name without a scheme is a URL only with a listed domain: :157 (URIhostStrict uses DomainNameStrict), :173 (HTTPurlNoScheme: the host followed by a port, a path, a query or a fragment), :276 and :283-290 (the bare host rules).
  5. Only three kinds of URL with a scheme do not use the table: an http or https URL (:166-167; HTTPurlFull takes any host name, :161 and :133), an ftp URL with a path (:179-180) and a file URL with a path (:182-183). :185 is URL = {HTTPurl} | {FTPurl} | {FILEurl}. The grammar has no URL rule for any other scheme: the scheme becomes a word, and the host after it goes through the rules of item 4.
  6. UAX29URLEmailTokenizerImpl.java is the scanner that JFlex generates from this grammar with the table included. A newer table reaches users only through a regenerated scanner.

How the two lines came apart

#
  • 2026-06-19: the merged #16274 regenerates the table on main from that day's IANA list (1,437 domains). The list was current: web did not exist yet.
  • 2026-07-23: IANA delegates web.
  • 2026-09-03: the table is regenerated on the 10.x line inside the merged #16592 (merged 2026-09-05; 1,438 domains, with web). Main's table is not regenerated afterwards.
  • 2026-10-28: branch_11x leaves main with the June table. 2026-10-29: 10.6.0 is released with the September table.

The task (regenerateTlds, lucene/core/build.gradle:134-182) downloads the live list; nothing pins a version. By the build code (RegenerateTasksSupportPlugin.java:249-268) and the project's help file (help/regeneration.md:116-131) a regenerate task runs when gradle is started with --rerun-tasks or when its saved checksums no longer match, and the only declared input of regenerateTlds is the constant URL (build.gradle:143). The release scripts name no regeneration step. This paragraph is read from the code, not observed in a run.

Why it looks unintended

The full argument389 words

This is a generated data table that fell behind on main, not a logic error. No stated guarantee is broken. The claim is only that an 11.0 table older than the 10.6.0 table is decided or defended nowhere in the sources and threads that were read.

  • The table says what it is. ASCIITLD.jflex:17: "Generated from IANA TLD Database". web has been in that list since 2026-07-23, and the 10.6.0 table has it.
  • Upstream's own test encodes the rule. TestUAX29URLEmailTokenizer.testExampleURLs (:867-888) requires that example.<domain> is one <URL> token for every line of TLDs.txt, the list the same task writes. On main that list has no web, so the test passes and cannot see the gap (90 tests of the three suites of this tokenizer, 1 skipped, none failed). With only the table and the test list regenerated in a scratch checkout of main, and the scanner unchanged, it fails: type 0 term=example.web expected:<<[URL]>> but was:<<[ALPHANUM]>>.
  • The stated aim of the last refresh on main. The merged #16274 (Dawid Weiss, milestone 11.0.0), whole description: "This refreshes all resources that are generated from sources on the web (tlds are changing)."
  • History. At the 34 release tags from 9.0.0 to 10.6.0 the table's stamp never goes back from one release to the next. 11.0.0 would be the first release since 9.0.0 with an older table than its predecessor.
  • The order of two routine runs, not a decision. Main was regenerated on 2026-06-19. IANA delegated web on 2026-07-23. The 10.x line was regenerated on 2026-09-03 inside the merged #16592 (Dawid Weiss: "All tests pass. I also ran regenerate --rerun-tasks so some generated files have changed."). Main's table was not regenerated after that. Neither thread says anything about the domain table, or about a regeneration, of the other line.
  • One earlier case. #6815 (LUCENE-5753, "Refresh UAX29URLEmailTokenizer's TLD list", opened in 2014 as a bug, fixed in 7.1.0) is the one time an out-of-date list was typed as a bug upstream. It is a weak precedent: the project's CHANGES file lists that refresh under "Other" of 7.1.0, and it took the table from 342 to 1,543 domains (Steven Rowe's comment on the issue), where this is one entry. Other refreshes are typed as tasks or enhancements, so this may be treated as a task. The outcome is the same run.
The devil's-advocate check343 words

The strongest case for "intended", in seven points. (1) The table is a dated copy by design. As Steven Rowe wrote on #5402 (LUCENE-4335, 2012), "generation based on external content we don't control, e.g. rules matching TLDs generated for UAX29URLEmailTokenizer, shouldn't be a regular part of the build". (2) No javadoc promises a current list, and no document says that a release knows every domain its predecessor knew: the class javadoc says only that "URLs and email addresses are also tokenized according to the relevant RFCs", and an address under a suffix that is in no table is split on every build. (3) Lucene's stated policy (CHANGES.txt 9.0.0, LUCENE-9669): "semantic changes like analysis or certain encoding on top of the file format are only supported on a best effort basis"; and the note on the 9.0.0 refresh of this table (LUCENE-9904) says it "may change the token sequence compared to previous Lucene versions". (4) 11.0 already changes this tokenizer's output on purpose, with a CHANGES entry (GITHUB#12561): foo,bar@yahoo.com is one <EMAIL> token on 10.6.0 and foo plus bar@yahoo.com on branch_11x and main. (5) The 10.6.0 refresh itself changed fourteen domains against 10.5.2 (two added, twelve removed) without a CHANGES entry. (6) No release step regenerates the table. (7) The routine repair does not make 11.0 equal to 10.6.0 either: on IANA's list of 2026-11-15 it adds web and drops helsinki and juniper, which 10.6.0 still has. Any dated copy falls behind again when the list changes.

Why it does not settle the matter: all seven bound the weight, and the finding is Low because of them. Points 1 to 3 explain why a table may lag the live list, not why a release branch should lag the last release. Point 4 is an announced grammar fix. Points 5 to 7 describe how refreshes happen and what they change. None says that 11.0 should know one current domain fewer than 10.6.0. A maintainer may still answer "a routine task, not a bug"; the outcome is then the same single run of the task.

How it was found

#

A comparison of the generated files of the 10.6.0 release and the 11.0 branch showed one table that is newer in the release: the top-level-domain table. One test on both builds showed the effect. A sweep of every domain of the tables (1,450 domains, 8 input shapes) found 7 differing lines, all for web.

The method in full193 words

Method: non-formal (a comparison of generated data between the last release and the release branch, then execution on the real jars; no model checking, constraint solving or proof was involved).

  • Signal. The question was which generated tables are newer in the 10.6.0 release than on the 11.0 branch. The date stamps and entries of the generated files of the two source trees were compared; the top-level-domain table was the one that is newer in the release.
  • Witness. One test, the same source on every build: it passes on 10.6.0 and fails on the 11.0 branch and on main. It was reduced to the one-method test of this page.
  • Bound. The table was parsed at six revisions (1,448 entries at 10.5.2, 1,438 at the 10.6.0 tag, 1,437 on branch_11x and main). Every domain of the three tables (1,450) was run in eight input shapes through new UAX29URLEmailTokenizer() on 10.6.0, branch_11x, main and 10.5.2: 11,600 inputs per build. The sweep bounded the finding; it did not find it.
