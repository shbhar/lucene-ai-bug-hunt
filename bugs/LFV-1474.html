LatLonShape.newSlowDocValuesBoxQuery accepts CONTAINS for a dateline-crossing box instead of rejecting it

The doc-values shape box query rejects CONTAINS as unsupported for every box except one that crosses the dateline: there newSlowDocValuesBoxQuery(f, CONTAINS, -1, 1, 175, -175) returns a points-index query, so a doc-values-only field gets 0 hits and no error. No hit is lost; the rejection is missing.

The finding in 30 seconds

#

One factory, two answers to the same request: CONTAINS is rejected for a normal box, but for a box that crosses the dateline it is silently accepted and answered from the points index, which a doc-values-only field does not have.

Background: two ways to store and query a shape

#
  1. LatLonShape stores a shape in the points index (createIndexableFields, queried by newBoxQuery) or as doc values (createDocValueField, queried by newSlowDocValuesBoxQuery). A query on one structure finds nothing in a field that has only the other.
  2. A box whose minLongitude is greater than its maxLongitude crosses the dateline. Rectangle handles that itself; for CONTAINS, newBoxQuery splits such a box at 180 into two halves that must both be contained.
  3. The doc-values shape queries support INTERSECTS, WITHIN and DISJOINT; their constructor throws for CONTAINS.

The finding, step by step

#
  1. Store one polygon, lat -4..4 x lon 170..178, as doc values only (LatLonShape.createDocValueField). newSlowDocValuesBoxQuery(field, INTERSECTS, -1, 1, 175, -175), a box that crosses the dateline (minLongitude 175 > maxLongitude -175), finds it through doc values: 1 hit.
  2. Doc-values shape queries do not support CONTAINS: the box lon 171..179 with CONTAINS throws IllegalArgumentException: ShapeDocValuesBoundingBoxQuery does not yet support CONTAINS queries, and XYShape's doc-values factory throws for every CONTAINS box. You expect the crossing box lon 175..-175 to be rejected the same way.
  3. Instead it is accepted. The factory starts with a copy of newBoxQuery's CONTAINS dateline split, whose two halves (lon 175..180 and lon -180..-175) are points-index LatLonShapeBoundingBoxQuerys. They never read doc values, so the count is 0, with no error.
  4. No hit is lost: the points-index CONTAINS query for a crossing box also counts 0 for shapes built through LatLonShape, because polygons cannot cross the 180th meridian. The bug is the missing rejection, present since 9.4.0.

Who is affected

#

Applications that keep shapes in doc-values-only fields (an experimental feature) and send CONTAINS with a dateline-crossing box to newSlowDocValuesBoxQuery, for example by passing a user's box and relation through. They get an empty success instead of an error. Default settings, no scale, every release since 9.4.0. Rare, and no hit is lost.

Mechanism, terms and numbers442 words

LatLonShape.newSlowDocValuesBoxQuery is documented as "create a docvalue query" (LatLonShape.java:262 on main f794ff5a505c), and shape doc-values queries do not support CONTAINS: their constructor throws IllegalArgumentException "ShapeDocValuesBoundingBoxQuery does not yet support CONTAINS queries" (BaseShapeDocValuesQuery.java:42-52). The factory, however, starts with a verbatim copy of newBoxQuery's CONTAINS dateline split (LatLonShape.java:270-281), whose two halves are built by newBoxQuery, the points-index factory. So for CONTAINS with a box that crosses the dateline (minLongitude > maxLongitude, a legal Rectangle) the call succeeds and returns two points-index LatLonShapeBoundingBoxQuery clauses that never read doc values: a doc-values-only field gets 0 hits and no error, while every non-crossing CONTAINS box, and every XYShape CONTAINS box, is rejected. No hit is lost: the points-index CONTAINS answer for a crossing box is also 0 for shapes built through LatLonShape's factories (by code reading, and in every document tested); the defect is the missing rejection. Present since the factory was added (LUCENE-10654, #1017, 9.4.0). Deleting the copied block fixes it (validated).

Terms

#
  • Shape doc values: LatLonShape.createDocValueField stores a shape's triangles in one binary doc-values field (LatLonShapeDocValuesField, @lucene.experimental, LatLonShapeDocValuesField.java:52). newSlowDocValuesBoxQuery reads them per document; newBoxQuery reads the points index that createIndexableFields writes.
  • Dateline-crossing box: a Rectangle "can cross the dateline, in which case minLon > maxLon" and "handles dateline crossing automatically" (Rectangle.java:38-39, :44).
  • CONTAINS split: for CONTAINS with a crossing box, newBoxQuery returns a BooleanQuery of two MUST halves, lon minLongitude..180 and lon -180..maxLongitude (LatLonShape.java:246-257). On the points index that is the right construction.

The bug

#
  1. newSlowDocValuesBoxQuery (LatLonShape.java:263-284) starts with the same if (queryRelation == QueryRelation.CONTAINS && minLongitude > maxLongitude) block (:270-281), copied verbatim; its halves call newBoxQuery (:273, :277), which builds a points-index LatLonShapeBoundingBoxQuery (:259).
  2. Only the fall-through builds LatLonShapeDocValuesQuery (:282-283). Its superclass constructor calls validateRelation, which throws IllegalArgumentException("ShapeDocValuesBoundingBoxQuery does not yet support CONTAINS queries") (BaseShapeDocValuesQuery.java:42-52).
  3. So CONTAINS with minLongitude > maxLongitude never reaches the rejection, and the returned query never reads doc values. XYShape.newSlowDocValuesBoxQuery has no such block and rejects CONTAINS for every box (XYShape.java:214-217).

The numbers

#

One polygon lat -4..4 x lon 170..178, stored as doc values only, and boxes lat -1..1: CONTAINS lon 171..179 throws; CONTAINS lon 175..-175 returns a BooleanQuery of two MUST LatLonShapeBoundingBoxQuery clauses, lon 175..180 and lon -180..-175, equal to newBoxQuery's query, and counts 0; INTERSECTS lon 175..-175 builds a LatLonShapeDocValuesQuery and counts 1. Over a lattice of 2,268 boxes, all 1,008 crossing CONTAINS boxes are accepted and all 1,260 non-crossing CONTAINS boxes are rejected, with assertions on and off.

Exposure and likelihood312 words
  • Who. Callers of LatLonShape.newSlowDocValuesBoxQuery with QueryRelation.CONTAINS and a box with minLongitude > maxLongitude, on fields written with LatLonShape.createDocValueField (the shape doc-values classes are @lucene.experimental). Default codec, IndexWriterConfig and searcher; no scale.
  • What they see. An empty successful result instead of an IllegalArgumentException, so they are not told that CONTAINS is unsupported on doc values. On a field that also has points, they get the points-index CONTAINS answer.
  • No lost hits. For a crossing box the points-index CONTAINS answer is also 0 for shapes built through LatLonShape's factories. By code reading: polygons cannot cross the 180th meridian (Polygon.java:36), so a polygon that covers a half box reaching lon 180 or -180 has an edge of its own on that meridian, and the CONTAINS check gives NOTWITHIN when an edge of the original shape touches the box (SpatialQuery.java:947-998); upstream asserts 0 for a crossing CONTAINS box (TestLatLonShape.java:349-350) and notes "Not supported due to encoding" (:388). By execution: 0 on both structures for all 15 documents of the bounded check and for a document that is the full-width band lat -20..20 x lon -180..180. That is strong evidence, not a proof over every possible document: hand-encoded triangles can match the points-index query (two did in a probe, with score 2 x boost).
  • IndexOrDocValuesQuery. With the fix, new IndexOrDocValuesQuery(newBoxQuery(...), newSlowDocValuesBoxQuery(...)) for a crossing CONTAINS box throws while its doc-values argument is evaluated, before the IndexOrDocValuesQuery constructor runs (it only stores its two queries, IndexOrDocValuesQuery.java:68-71), as it already does for every non-crossing CONTAINS box; today the pair holds the points-index query twice and returns 0 for shapes built through LatLonShape.
  • Likelihood: rare. No Elasticsearch, OpenSearch or Solr code calls the factory (code search), and no Lucene test uses CONTAINS with it (BaseLatLonShapeDocValueTestCase.java:28-35).
  • Versions. Every release from 9.4.0 to 10.6.0, and main.

Why it looks unintended

#
  • The factory rejects CONTAINS for every other box, and XYShape's twin factory rejects it for every box.
  • Its javadoc promises "a docvalue query"; for this input the query never reads doc values.
  • In the introducing PR the CONTAINS rejection came first; the split was copied in later from newBoxQuery, with its points-index halves, and nothing documents a fallback.
The full argument174 words
  • The rule depends on the relation, not the box. Every non-crossing CONTAINS box is rejected; only minLongitude > maxLongitude slips through (all 1,008 crossing CONTAINS boxes of the lattice accepted, all 1,260 others rejected).
  • The twin factory has no such case. XYShape.newSlowDocValuesBoxQuery (XYShape.java:214-217) builds the doc-values query directly and rejects CONTAINS for every box.
  • The javadoc promises a doc-values query (LatLonShape.java:262); the returned query equals newBoxQuery's and never reads doc values.
  • Upstream's doc-values tests declare CONTAINS unsupported: getSupportedQueryRelations returns INTERSECTS, WITHIN and DISJOINT (BaseLatLonShapeDocValueTestCase.java:28-35).
  • History. In the first commit of #1017 (3554306677, 2022-05-18) the CONTAINS rejection already existed, in BaseShapeDocValuesBoundingBoxQuery.validateRelation with today's message, and the doc-values factory (then newDocValuesBoxQuery) had no split. The PR commit "Major refactor to leveral SpatialQuery" (2cf24b47c0b, author date 2022-07-20) replaced that class with BaseShapeDocValuesQuery, which keeps the rejection, and copied the split from newBoxQuery, with its points-index halves, into the factory. No commit message, review comment, test or CHANGES entry describes a points-index fallback.
The devil's-advocate check135 words

The case for "intended or harmless": no javadoc promises the exception; the rejection lives in a package-private @lucene.experimental class; the shape doc-values feature is experimental; and the returned query equals newBoxQuery's, whose answer for a crossing CONTAINS box is 0 anyway.

Why it fails: the factory itself is public and not marked experimental, and it does reject the same relation for every other box, on LatLonShape and XYShape alike; the fallback is documented nowhere; and on a doc-values-only field the 0 is not a computed answer but the result of querying a structure the field does not have (INTERSECTS with the same box finds the shape). It stays Low because no hit is lost; a maintainer may still weigh the change from a silent 0 to an exception as a cost for existing callers.

Suggested fix

#

Recommended Delete the copied split from newSlowDocValuesBoxQuery

Delete the copied CONTAINS dateline split from newSlowDocValuesBoxQuery (12 lines). Rectangle already accepts a crossing box and the doc-values query already rejects CONTAINS, so the factory then behaves like XYShape's. Validated: the test passes, and the 27 upstream suites matched by *Shape* and check -x test pass.

  public static Query newSlowDocValuesBoxQuery(
      String field,
      QueryRelation queryRelation,
      double minLatitude,
      double maxLatitude,
      double minLongitude,
      double maxLongitude) {
    // CONTAINS is rejected by the doc-values query for every box, including one that crosses the
    // dateline
    return new LatLonShapeDocValuesQuery(
        field, queryRelation, new Rectangle(minLatitude, maxLatitude, minLongitude, maxLongitude));
  }

How it was found

#

A bounded-exhaustive check of the three shape box-query factories it drives on the main jar, 2,268 LatLon boxes x 4 relations over 15 documents: exactly the 1,008 crossing CONTAINS boxes were accepted by the doc-values factory. A z3 query over the factory's branches showed that this is the only region where it departs from its rejection rule.

The method in full229 words

Method: semi-formal, a bounded-exhaustive decision-table check on the real main jar plus an SMT query.

  • The check drove three shape box-query factories (LatLonShape.newBoxQuery and LatLonShape.newSlowDocValuesBoxQuery, and XYShape.newSlowDocValuesBoxQuery as a control) over a lattice of 7 latitudes x 9 longitudes, 2,268 LatLon boxes x 4 relations, against 15 single-geometry documents indexed both in the points index and as doc values, plus an XY control lattice (225 boxes per relation).
  • Its contract: a doc-values factory either rejects the relation or returns a doc-values query. Exactly the 1,008 crossing CONTAINS boxes broke it, each returning two LatLonShapeBoundingBoxQuery clauses and 0 hits on the doc-values-only field; all 1,260 non-crossing CONTAINS boxes were rejected, and XY rejected every CONTAINS box.
  • Parity of doc values against points for INTERSECTS, WITHIN and DISJOINT: 0 mismatches over 6,804 box queries x 15 documents (38,872 hits on each side); a deliberately wrong points side gave 68,040 parity mismatches (every box and document of the two swapped relations), so the comparison is not vacuous.
  • A z3 query over the factory's transcribed branches: the region where the outcome departs from the rejection rule is exactly CONTAINS with minLongitude > maxLongitude, and there the outcome is always a points-index query; with the fix the region is empty (UNSAT).
  • Then an independent reproducer and executing reviews by another model family (OpenAI GPT-5.6) each reproduced it with their own tests.
