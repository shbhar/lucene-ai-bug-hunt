IndriAndQuery hides its clauses from every QueryVisitor

IndriQuery.visit reports the whole query as a leaf, so tools that walk an IndriAndQuery with a QueryVisitor never see its clauses: term extraction returns nothing, term-extraction highlighting marks nothing, and the cumulative clause limit counts it as one clause. Search hits are right; since 8.9.0.

The bug in 30 seconds

#

Tools that need to know what a query contains walk it with a QueryVisitor. Every query that holds other queries must pass the visitor on to them; IndriAndQuery does not.

  1. Build an IndriAndQuery of two term clauses, body:president and body:washington, and search a one-document index ("president washington was the first leader"): 1 hit, the same as the BooleanQuery over the same clauses.
  2. Ask which terms it may match with QueryVisitor.termCollector. You expect {body:president, body:washington}, as for the BooleanQuery. You get []. The UnifiedHighlighter in term-extraction mode uses the same collector and returns the passage with no <b> marks.
  3. Set maxClauseCount to 4: a DisjunctionMaxQuery and a nested BooleanQuery over 6 term clauses throw TooManyClauses. An IndriAndQuery of the same 6 clauses runs (1 hit), and so does a BooleanQuery of two 3-clause IndriAndQuerys. With a limit of 16, a 2,000-clause IndriAndQuery runs too.
  4. Why: IndriQuery.visit is visitor.visitLeaf(this), so the visitor is told "leaf" and never sees the clauses, although Query#visit must "recurse through the query tree, visiting any child queries". The same root makes RamUsageEstimator.sizeOf return 1,024 bytes for 1 clause and for 1,000 (BooleanQuery: 1,169,024).

Who is affected

#

Applications that build an IndriAndQuery (no Lucene parser produces one) and inspect it with a visitor-based tool: their own term extraction, the UnifiedHighlighter outside weight-matches mode, IndexSearcher's cumulative clause limit, or the query RAM estimate. Default codec and settings, any index size. Search hits stay right, so it goes unnoticed.

Mechanism, terms and numbers687 words

Tools that need to know what a query contains (term extraction, highlighting, IndexSearcher's cumulative clause limit, the query RAM estimate) walk the query tree with a QueryVisitor, and every query that holds other queries is supposed to pass the visitor on to them. IndriAndQuery holds a list of clauses, but IndriQuery.visit only calls visitor.visitLeaf(this). So for an IndriAndQuery of body:president and body:washington, QueryVisitor.termCollector returns [] instead of both terms, the UnifiedHighlighter in term-extraction mode highlights nothing, a 6-clause IndriAndQuery runs at maxClauseCount=4 while a DisjunctionMaxQuery over the same clauses is refused, and RamUsageEstimator.sizeOf gives 1,024 bytes for 1 clause and for 1,000 (on main the query cache sizes cached keys this way). Search hits are right (matching and scoring never call visit), and no error is raised. It has been there since the Indri classes were added (LUCENE-9537, first released in 8.9.0). A one-method fix that visits every clause through a SHOULD sub-visitor makes all repros pass, and the search-package and highlighter test suites pass with it.

Terms

#
  • QueryVisitor: Lucene's query-introspection API. Query#visit is documented to "Recurse through the query tree, visiting any child queries". A query with children pulls a sub-visitor with getSubVisitor(occur, this) and visits each child with it; a query that matches on terms calls consumeTerms; visitLeaf is for "leaf queries that do not match on terms".
  • Who walks queries this way: QueryVisitor.termCollector ("collects all terms that may match a query"), the UnifiedHighlighter's term extraction, IndexSearcher's cumulative clause check (run by IndexSearcher.rewrite), RamUsageEstimator.sizeOf(Query), and on main the LRUQueryCache key accounting that uses it.
  • IndriAndQuery: a core query (since 8.9.0, LUCENE-9537) built from a List<BooleanClause>; its base class IndriQuery keeps the list, and IndriAndWeight builds a Weight for every clause and, per segment, a scorer for each clause that has one.

The bug

#

IndriQuery.visit (IndriQuery.java:71-74 at a9779ef3c193) is one line, visitor.visitLeaf(this). The visitor is told the whole query is a leaf that does not match on terms, and the clauses are never handed to it. Each consumer then sees an empty box:

  1. termCollector collects only from consumeTerms, and visitLeaf is a no-op: it returns [].
  2. The UnifiedHighlighter's extractTerms is query.visit(QueryVisitor.termCollector(...)); it is used whenever the highlighter is not in weight-matches mode (withWeightMatches(false), or any of multi-term, strict-phrase or passage-relevancy handling turned off). No terms, so no highlights.
  3. IndexSearcher.rewrite runs a clause-counting visitor that adds one per visitLeaf, consumeTerms or consumeTermsMatching call, so a whole IndriAndQuery counts as one clause. Neither Indri class overrides rewrite, and the IndriAndQuery constructor has no size check (BooleanQuery.Builder.add refuses more than maxClauseCount clauses at build time).
  4. RamUsageEstimator.sizeOf(Query) starts at the default size for the root and adds nothing for a root that calls visitLeaf, so it is 1,024 bytes whatever the clauses hold.

Matching and scoring do not use visit (only the clause check before a search does): IndriAndWeight iterates the clause list itself, so the hits are right (the security probe found the same hit sets as the SHOULD BooleanQuery for 1, 2, 10 and 50 clauses; it did not compare scores).

Exposure and likelihood218 words
  • Who is exposed. Only application code builds an IndriAndQuery: in the whole lucene/ tree no parser or builder produces one (only IndriAndQuery.java itself, IndriAndWeight.java and TestIndriAndQuery.java mention it). Every such query is affected, every time, for every visitor-based consumer.
  • Term extraction and highlighting. Custom code that calls termCollector (for example to log, cache or route on query terms) gets nothing. The UnifiedHighlighter uses it whenever it is not in weight-matches mode. Two clauses and one document are enough.
  • Clause limit. The cumulative check counts the whole IndriAndQuery as one clause, at any nesting depth, so it only matters once counting the clauses would trip the limit: more than maxClauseCount + 1 calls (default 1,025), since the counter checks before it increments. A QueryTimeout still stops a large query.
  • RAM estimate. RamUsageEstimator.sizeOf ignores the clauses in every release since 8.9.0; on main (unreleased, #15124) LRUQueryCache sizes cached query keys with it, which needs an application-installed cache (caching is off by default) and a non-scoring use, and grows with the clauses, about 184 bytes per term clause (a cached 16-clause IndriAndQuery: 192 bytes against 3,136 with the fix; 500 clauses: 192 against 92,192; independent reproducer).
  • How likely. IndriAndQuery is a rarely used API, and the visible symptoms are in tools that inspect the query, not in search results.

Why it is a bug, not intended

#
  • Query#visit must "recurse through the query tree, visiting any child queries"; IndriAndQuery holds clauses but reports itself as a leaf.
  • The clause limit counts "total clauses cumulatively in all of its children", for "all queries, rather than only booleans" (LUCENE-8811).
  • visitLeaf(this) was never discussed or tested; the same omission in other classes was fixed as a bug (LUCENE-8849, LUCENE-9050).
The full argument247 words
  • Javadoc. Query#visit: "Recurse through the query tree, visiting any child queries." QueryVisitor#visitLeaf: "Called by leaf queries that do not match on terms". termCollector: "collects all terms that may match a query". TooManyNestedClauses: "Thrown when a client attempts to execute a Query that has more than getMaxClauseCount() total clauses cumulatively in all of its children."
  • CHANGES. LUCENE-3041 (the visitor API): queries should "either pass the visitor down to any child queries, or call a visitX() or consumeX() method on it". LUCENE-8811 (9.0.0): the clause checks "are now implemented using a QueryVisitor and apply to all queries, rather than only booleans".
  • The API designer's rule (review of the visitor API, apache/lucene-solr#581, 2019-02-26, @romseygeek): "Yes, all compound queries should pull a sub visitor and call visit on each of their sub queries with it. And visitLeaf is for queries that don't match on terms."
  • Tests. TestQueryVisitor.testExtractTermsEquivalent asserts that termCollector reaches terms inside nested BooleanQuery and BoostQuery composites; TestMaxClauseLimit.testLargeDisjunctionMaxQuery asserts that a non-Boolean composite with 1,050 children throws TooManyNestedClauses. TestIndriAndQuery checks hit counts only.
  • History. visitLeaf(this) is in the first commit of the introducing PR (apache/lucene-solr#2097, 2020-11-24) and unchanged since on the main line (on branch_8x, which shipped 8.9.0, Query#visit then still defaulted to the same visitLeaf(this)); no review comment, issue comment (#10577, #11194, #463) or commit message mentions it.
  • Precedent. LUCENE-8849 ("DocValuesRewriteMethod.visit wasn't visiting its embedded query", 8.6.0) and LUCENE-9050 ("MultiTermIntervalsSource.visit() was not calling back to its visitor", 8.3.1) were fixed as bugs.
The devil's-advocate check280 words

The strongest case for "intended": the visitor API lets a composite be opaque, and several are on purpose (ToParentBlockJoinQuery, ToChildBlockJoinQuery, DrillDownQuery, MoreLikeThisQuery and CompositeVerifyQuery call visitLeaf(this); block-join highlighting was dropped by design). ToParentBlockJoinQuery gets past the cumulative limit the same way. RamUsageEstimator.sizeOf is documented as an estimate. And maintainers see Indri as marginal (#11194 proposes moving it to the sandbox).

Why it is weaker than the contract: most precedents have a reason that does not apply here. The block-join children match other documents. DrillDownQuery and MoreLikeThisQuery rewrite to a BooleanQuery, which the clause check (run after rewriting) sees; a visitor applied to the query as given, such as the UnifiedHighlighter's term extraction, does not, so for those consumers they are as opaque as IndriAndQuery. The closest case, CompositeVerifyQuery (spatial-extras), holds one same-document child and calls visitLeaf(this), but it is @lucene.experimental, its child is an approximation that "matches more than needed", and a shape predicate decides the final match, so its child's terms only approximate what it matches. IndriAndQuery is in core, not experimental, has no rewrite, and its clauses are the match: a plain disjunction over the same document. The estimate argument only explains why 1,024 follows from the leaf, which is why the RAM effect is a consequence, not the headline. "Marginal" bears on priority, not on whether it is a bug: the classes are public, not experimental, and shipped since 8.9.0. Verdict: most likely not intended (a defect), or at least a contradiction with the documented visit contract; maintainers could still choose to keep Indri opaque and document it. The issue should answer the opaque-composite comparison up front.

Suggested fix

#

Recommended Visit every clause through a SHOULD sub-visitor (validated)

Make IndriQuery.visit pass a SHOULD sub-visitor to every clause (+6/-1 in IndriQuery.java), since the Indri scorers match the union of the clauses. All repro tests pass, and so do 2,353 tests (the search package plus TestRamUsageEstimator) and 723 highlighter tests, with assertions on and off. Oversized Indri queries then hit the clause limit, as other composites do.

@Override
public void visit(QueryVisitor visitor) {
  // The Indri scorers match the union of all clauses, whatever their Occur, so every clause is
  // visited as a SHOULD clause.
  QueryVisitor v = visitor.getSubVisitor(BooleanClause.Occur.SHOULD, this);
  for (BooleanClause c : clauses) {
    c.query().visit(v);
  }
}

Visit every clause through a SHOULD sub-visitor (validated) (validated by the checks) (recommended)

#

IndriQuery.visit pulls visitor.getSubVisitor(Occur.SHOULD, this) and visits each clause's query with it. SHOULD describes what the clauses do today: IndriAndQuery matches the union of its clauses whatever their Occur (a separate finding), so a MUST_NOT clause, which still matches, keeps its terms visible. Fixed in the base class, so a future IndriOrQuery (open PR #463) inherits it.

@Override
public void visit(QueryVisitor visitor) {
  // The Indri scorers match the union of all clauses, whatever their Occur, so every clause is
  // visited as a SHOULD clause.
  QueryVisitor v = visitor.getSubVisitor(BooleanClause.Occur.SHOULD, this);
  for (BooleanClause c : clauses) {
    c.query().visit(v);
  }
}

Trade-offs

  • Behaviour change: an IndriAndQuery whose clauses take the cumulative count over the limit now throws TooManyNestedClauses, like other composites. The counter checks before it increments, so at the default 1,024 an IndriAndQuery of 1,025 term clauses still runs and one of 1,026 throws (read; the executed check used 6 clauses at a limit of 4). Queries under the limit keep their hits; oversized ones that ran before now fail. Mention it in CHANGES.
  • RamUsageEstimator.sizeOf and, on main, the query cache now account for the clauses (a cached 16-clause IndriAndQuery: 3,136 bytes, equal to the BooleanQuery; 500 clauses: 92,192).
  • Visitors now also receive callbacks from clauses that need rewriting (for example a PrefixQuery). Searching such a query already fails at createWeight, because IndriAndQuery does not rewrite its clauses (a related finding), but visitor-only consumers (term extraction, highlighting, sizeOf, custom visitors) never call createWeight, so for them these callbacks are new. Cross-reference the two issues.
  • Does not fix the blank highlights in the default weight-matches mode, which needs Weight#matches in IndriAndWeight.
  • Not benchmarked (a visit walks the clause list once).

Visit each clause with its own Occur (validated on a narrow set) (validated by the checks)

#

Mirrors BooleanQuery.visit: c.query().visit(visitor.getSubVisitor(c.occur(), this)) for every clause.

for (BooleanClause c : clauses) {
  c.query().visit(visitor.getSubVisitor(c.occur(), this));
}

Trade-offs

Right once IndriAndQuery honours (or rejects) MUST, FILTER and MUST_NOT. Today it hides a MUST_NOT clause's terms from termCollector (the default sub-visitor for MUST_NOT is empty) although that clause still produces matches. The clause count includes MUST_NOT clauses either way.

Workaround without a Lucene change

#

Count getClauses() before searching or set a QueryTimeout; walk getClauses() yourself for term extraction; or wrap the query in your own Query whose visit descends. Such a wrapper must also delegate createWeight, equals, hashCode and toString, and its rewrite must keep the wrapper rather than return the bare IndriAndQuery. Not run.

Every application has to know about it.

Downstream note

#

An application that relies on maxClauseCount alone to bound user-built IndriAndQuery clause lists is not protected: it should count the clauses itself or set a QueryTimeout.

How it was found

#

An automated bytecode scan of every concrete Query class flagged that IndriAndQuery never hands its clauses to a visitor. A later hunt compared it with the equivalent BooleanQuery on all 1,884 small clause lists against a Z3 model: term collection differed in 1,845, the clause count in 1,860. A public-API JUnit test then reproduced it.

The method in full182 words

Method: semi-formal (an automated scan, then bounded-exhaustive translation validation of the real core jar against a Z3 model).

  • First signal (2026-10-26). An earlier unit scanned the bytecode of every concrete Query class in the stock main jars (JDK ClassFile API) for contract checks; its rows VISIT-MISS and VISIT-NOSUB flagged that IndriAndQuery's clauses are never handed to a visitor. That unit registered the related rewrite bug and recorded this visit root as separate.
  • Hunt (2026-10-28). An outside-reviewer probe pack re-raised it (termCollector returns []). The finder built a bounded-exhaustive harness: every clause list over 3 terms and 4 Occur values (1,884 queries), run through the real jar and compared with the same clauses in a BooleanQuery and with a Z3 model of the expected visitor results. termCollector differed in 1,845 lists and the clause-count visitor in 1,860, with 0 mismatches against the model's prediction for the leaf-only visit.
  • The finder then wrote a public-API JUnit test (term collection, clause limit, RAM estimate) and a highlighter test, and found the RAM-estimate and query-cache consumers by searching for callers of Query.visit.

Bug record

LFV-872, snapshot of 2026-10-28

Registry title
IndriQuery.visit reports the whole query as a leaf and never visits its clauses, so QueryVisitor.termCollector, UnifiedHighlighter term extraction, IndexSearcher's cumulative clause limit and RamUsageEstimator.sizeOf all ignore an IndriAndQuery's clauses
Area
search / IndriQuery (QueryVisitor traversal of Indri composite queries; consumers: QueryVisitor.termCollector, IndexSearcher's cumulative clause limit, RamUsageEstimator.sizeOf(Query), UnifiedHighlighter)
Priority
Medium, rank 258: Every IndriAndQuery silently breaks QueryVisitor-based tools (term extraction and highlighting return nothing, clause limit and RAM estimate skip its clauses) while hits stay correct in a niche core API, so it ends the highlighting and visitor wrong-result rows after LFV-516 and below the hit-changing Indri row LFV-874.
Impact class
silent wrong results
Impact note
Applications that build an IndriAndQuery (a rarely used core API that no Lucene query parser produces) get wrong answers, with no error, from every QueryVisitor-based tool on every such query: QueryVisitor.termCollector returns no terms, the UnifiedHighlighter in term-extraction mode (withWeightMatches(false)) highlights nothing, IndexSearcher's cumulative maxClauseCount check (since 9.0.0) counts the whole IndriAndQuery as one clause whatever it holds, and RamUsageEstimator.sizeOf returns the 1024-byte default (on main only, LRUQueryCache's key accounting inherits this, a few KB per cached entry); search hits and scores are unchanged; default codec, IndexWriterConfig and searcher, ordinary scale; every release since 8.9.0.
Summary
You build an IndriAndQuery of ordinary TermQuery clauses, for example f:a and f:b, and inspect it with a QueryVisitor, as term extraction, highlighting, IndexSearcher's clause-count check and the query RAM estimate do. You expect the visitor to reach both clauses, as it does for a BooleanQuery over the same clauses, because Query#visit is documented to 'recurse through the query tree, visiting any child queries'. Instead IndriQuery.visit only calls visitor.visitLeaf(this), so termCollector returns [], with maxClauseCount=4 a 51-clause IndriAndQuery and BooleanQuery(IndriAndQuery(3), IndriAndQuery(3)) both run while the same nesting of BooleanQuery clauses throws TooManyClauses, and RamUsageEstimator.sizeOf gives 1,024 bytes for 1,000 clauses against 1,169,024 for the BooleanQuery.
