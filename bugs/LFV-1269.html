CodecUtil.checkFooter throws "Self-suppression not permitted" instead of CorruptIndexException when the footer read rethrows the prior exception

If your IndexInput rethrows the same CorruptIndexException object on every failed read, opening an index whose .si read (or a segments_N read after its header) fails throws an unchecked IllegalArgumentException: Self-suppression not permitted instead of a CorruptIndexException. CodecUtil.checkFooter asks that exception to suppress itself; every release since 8.6.0 is affected.

The finding in 30 seconds

#

One exception object e plays two roles: the first read failure (the prior) and the footer check's corruption. checkFooter makes the corruption the main exception and attaches the prior to it, which here means attaching e to itself. Java refuses, and that refusal escapes instead of e.

Background: how Lucene reads a metadata file

#
  1. Every metadata file (segments_N, .si, .fnm, ...) ends with a 16-byte footer that holds a checksum of the file.
  2. A reader reads the file inside try, keeps any failure as priorE, and in finally calls CodecUtil.checkFooter(input, priorE), which checks the footer and rethrows.
  3. Since 8.6.0, if the footer check fails too, its CorruptIndexException becomes the main exception and priorE is attached to it with addSuppressed, so callers see a corruption error.

The finding, step by step

#
  1. Wrap a Directory so the input for _0.si fails half way with a CorruptIndexException and then rethrows that same object on every later read (a fail-fast wrapper). Call DirectoryReader.open.
  2. The .si reader keeps the failure as priorE and calls CodecUtil.checkFooter(input, priorE) to verify the 16-byte checksum footer. Reading the footer fails with the same object.
  3. You expect a corruption error: CorruptSegmentInfoException: segment info file: _0.si cannot be read, which is exactly what you get when the wrapper throws a fresh exception per failure.
  4. Instead checkFooter calls e.addSuppressed(e). Java refuses, and DirectoryReader.open throws IllegalArgumentException: Self-suppression not permitted, with the corruption only as its cause, so catch (IOException) and catch (CorruptIndexException) handlers miss it.

Who is affected

#

Only applications whose own IndexInput, ChecksumIndexInput or Directory wrapper rethrows one cached CorruptIndexException; Lucene's inputs never do. Then a failing footer-checked file surfaces as an unchecked IllegalArgumentException that skips catch (IOException) handlers, the CorruptSegmentInfoException mapping and the retry in FindSegmentsFile. The open fails either way; nothing is written or lost.

Mechanism, terms and numbers450 words

Lucene's metadata readers (segments_N, .si, .fnm, codec metadata) read a file inside try, keep any failure as priorE, and call CodecUtil.checkFooter(input, priorE) in finally; it verifies the checksum footer and rethrows. Since LUCENE-7822 (8.6.0), when the footer check fails with a CorruptIndexException, that exception becomes the main one and the prior is attached to it: corruptException.addSuppressed(priorException); throw corruptException; (CodecUtil.java:507-509). There is no identity check. If the input reports failures by rethrowing one cached CorruptIndexException, the footer read throws the very object that is the prior, and Throwable.addSuppressed rejects self-suppression with IllegalArgumentException("Self-suppression not permitted", e). Thrown inside a catch block, it skips the sibling catch (Throwable) and leaves a method declared throws IOException. Through DirectoryReader.open it bypasses SegmentInfos' mapping to CorruptSegmentInfoException and FindSegmentsFile's retry on IOException. The trigger needs a custom input (no Lucene input and no JVM mechanism reuses one CorruptIndexException); the failure is loud, the corruption is kept as the cause, and nothing is written or lost. Before 8.6.0 the same input produced the CorruptIndexException.

Exposure and likelihood176 words
  • Who is hit. A custom input that throws a CorruptIndexException and rethrows that same object on later reads of the same input: a fail-fast ("sticky") wrapper, a block-verifying or a decrypting input that remembers its first failure. The read must fail in a footer-checked file (segments_N, .si, .fnm, codec metadata).
  • Default vs opt-in. Opt-in in practice: no Lucene input does this and the JVM never reuses CorruptIndexException objects. No public report of it was found since 8.6.0.
  • Scale. None: one input, one failed read.
  • What breaks. The exception type callers key on. LUCENE-7822 made the corruption the main exception for exactly this downstream use: "knowing that the problem is a corruption is also more useful as in some cases you can re-create the shard from another copy that isn't corrupt automatically" (jpountz on #8873). Here the corruption is only the cause of an IllegalArgumentException.
  • Not affected. Stock Lucene inputs, any input that creates a fresh exception per failure (then the intended CorruptIndexException or CorruptSegmentInfoException comes out), the index on disk, search.

Why it looks unintended

#
  • The code comment and the 8.6.0 CHANGES entry say that when the footer check finds corruption, that CorruptIndexException becomes the main exception; here an IllegalArgumentException replaces it.
  • A regression: before 8.6.0 the same input produced the CorruptIndexException (8.5.2 passes the test, 8.6.0 fails it).
  • The JDK's own FilterOutputStream.close() guards exactly this pattern with an identity check.
The full argument256 words
  • Corruption first. Javadoc: "When a priorException is provided, this method will add a suppressed exception indicating whether the checksum for the stream passes, fails, or cannot be computed, and rethrow it" (CodecUtil.java:452-454). Comment: "If we have evidence of corruption then we return the corruption as the main exception and the prior exception gets suppressed" (:477-479). CHANGES 8.6.0, API Changes: "CodecUtil#checkFooter(IndexInput, Throwable) now throws a CorruptIndexException if checksums mismatch or if checksums can't be verified" (lucene/CHANGES.txt:5757-5759). These indicate the corruption comes out as the main exception. They do not promise that the method never throws an unchecked exception: an unchecked prior is rethrown as is (IOUtils.rethrowAlways), as the stock TestCodecUtil.java:143-153 expects for a RuntimeException prior. The defect is narrower: the footer's corruption is replaced by an IllegalArgumentException that neither the input nor the caller threw.
  • Regression. Before LUCENE-7822 the footer's CorruptIndexException was added to the prior inside the outer try; for the same object the IAE fell into catch (Throwable) and the prior, the CorruptIndexException, was rethrown (git show 583499243a2).
  • Never considered. #8873 (16 comments) is about which of two distinct exceptions should be primary, and the review comments on apache/lucene-solr#1482 are about message wording and tests; neither considers one object in both roles, and the commit's tests use distinct objects only. No Lucene test asserts the current behaviour, and no javadoc requires a fresh exception object per failure.
  • Platform precedent. FilterOutputStream.close(): if (flushException != closeException) { closeException.addSuppressed(flushException); } throw closeException; (JDK FilterOutputStream.java:194-198).
The devil's-advocate check205 words

The strongest case, from the intended-behaviour check and an executed cross-model review (an independent reviewer from another model family, OpenAI GPT-5.6): only a contrived custom input triggers it; CodecUtil is @lucene.experimental (CodecUtil.java:41); throws IOException does not forbid unchecked exceptions (an unchecked prior is rethrown as is); the Throwable javadoc says that where an exception object is "repeatedly caught and rethrown", immutable throwable objects "would be appropriate" (JDK Throwable.java:366-371); and plain try-with-resources raises the same IAE when close() rethrows the in-flight object.

Why it fails: the JDK advice cannot help, because addSuppressed checks self-suppression before it checks whether suppression is enabled (Throwable.java:1100-1105), and CorruptIndexException has no constructor that disables suppression (CorruptIndexException.java:31-58). The case does not rest on throws IOException: the comment and the CHANGES entry indicate that a footer corruption comes out as the main exception, the pre-8.6 code delivered it for this input, and @lucene.experimental is about API stability. Reachability is a severity point (hence Low), not intent. Both executed cross-model reviews rated the intended-behaviour argument weak and the bug real; a later cross-model fact check rated it moderate (the trigger needs a custom input, and throws IOException is no guarantee) and still found the bug real.

Suggested fix

#

Recommended A. Identity guard at the fix site (recommended; validated)

At CodecUtil.java:508, call corruptException.addSuppressed(priorException) only when corruptException != priorException, then throw as before. The same object is both the corruption and the prior, so nothing is lost, and distinct objects behave as today. Validated through gradle: the repro passes with assertions on and off, and the closest suites pass.

       } catch (CorruptIndexException corruptException) {
-        corruptException.addSuppressed(priorException);
+        // the input may rethrow the prior exception itself: a Throwable cannot suppress itself
+        if (corruptException != priorException) {
+          corruptException.addSuppressed(priorException);
+        }
         throw corruptException;

Downstream note

#

Products with their own Directory or IndexInput layer (encrypting, caching, remote storage) that rethrow a remembered failure should know that recovery keyed on CorruptIndexException, such as rebuilding a corrupt shard from another copy, does not run for this exception.

How it was found

#

A semi-formal proof-obligation audit of CodecUtil.checkFooter(in, priorException)'s contract: with a prior exception it must end by throwing either the footer's corruption, with the prior suppressed, or the prior itself with a checksum note. Checking each exit path found one where the JDK throws instead, and a one-test JUnit repro witnessed it.

The method in full74 words

The obligation follows every exit of the method's try: the normal path (the prior with a "checksum passed" note), a corruption from the footer (catch (CorruptIndexException)), and any other failure (catch (Throwable)). The corruption arm calls a JDK method that can itself throw; it throws when the corruption and the prior are one object, and nothing catches it. The repro then built an input that rethrows one exception object.
