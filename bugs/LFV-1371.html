QueryBuilder.analyzeGraphBoolean and analyzeGraphPhrase reset the source stream twice, so a fresh analyzer TokenStream throws IllegalStateException

A QueryBuilder subclass that passes a fresh analyzer stream to the protected analyzeGraphBoolean or analyzeGraphPhrase gets IllegalStateException: ... reset() called multiple times instead of the graph query: the hook resets the stream, then GraphTokenStreamFiniteStrings resets it again. The public create*Query methods and shipped parsers are unaffected; since 6.4.0.

The finding in 30 seconds

#

Each graph hook resets the stream and then hands it to GraphTokenStreamFiniteStrings, whose constructor resets it again. A cache that was already read survives two resets; a stream fresh from the analyzer does not.

Background: how a token stream is consumed

#
  1. A consumer calls reset() once, then incrementToken() until it returns false, then end() and close(). A Tokenizer enforces the "once": after a second reset() it reads from a placeholder reader whose first read throws.
  2. QueryBuilder.createFieldQuery wraps the analyzer's stream in a CachingTokenFilter, reads it once to count tokens and spot tokens that span several positions, and then hands the cache to a hook such as analyzeGraphBoolean. Resetting a filled cache only rewinds it.
  3. The analyze* hooks are protected methods, so a custom query parser that subclasses QueryBuilder can call or override them.

The finding, step by step

#
  1. Your analyzer turns "guinea pig" into a token graph: "guinea" and "pig" at two positions, plus a synonym "cavy" that spans both. createBooleanQuery("field", "guinea pig", SHOULD) builds ((+field:guinea +field:pig) field:cavy).
  2. Your QueryBuilder subclass calls the protected hook that builds this query itself: analyzeGraphBoolean("field", analyzer.tokenStream("field", "guinea pig"), SHOULD). You expect the same query.
  3. Instead it throws IllegalStateException: TokenStream contract violation: ... reset() called multiple times ..., with assertions on and off. analyzeGraphPhrase fails the same way.
  4. Why: the hook calls source.reset() and then new GraphTokenStreamFiniteStrings(source), which calls reset() again before reading. A tokenizer reset twice reads from a placeholder reader that throws. createFieldQuery never shows it: it passes a cache it has already read, and resetting a filled cache only rewinds it.

Who is affected

#

Only a custom query parser that calls the protected analyzeGraphBoolean or analyzeGraphPhrase itself with an unread stream, typically straight from Analyzer.tokenStream. Every such call fails, whatever the text (a parser would use them for token graphs, e.g. multi-word synonyms). createBooleanQuery, createPhraseQuery, createFieldQuery and the shipped parsers pass a read cache and are unaffected. Loud and immediate, never a wrong result.

Mechanism, terms and numbers491 words

QueryBuilder.analyzeGraphBoolean and analyzeGraphPhrase call source.reset() and then new GraphTokenStreamFiniteStrings(source), whose constructor resets the stream again before reading it. A Tokenizer treats the second reset() as a contract violation, so a QueryBuilder subclass that passes a stream straight from Analyzer.tokenStream to either protected hook gets IllegalStateException: TokenStream contract violation: ... reset() called multiple times ... instead of the graph query, whether or not the text forms a token graph (createFieldQuery uses these hooks only for token graphs, such as multi-word synonyms). createBooleanQuery, createPhraseQuery, createFieldQuery and the shipped query parsers are not affected: they pass a CachingTokenFilter they have already read, where a reset only rewinds. Loud and immediate, never a wrong result; in every release run from 6.4.0 through 10.6.0 and on main, never fixed.

Exposure and likelihood222 words
  • Who is hit. A QueryBuilder subclass (a custom query parser) that calls analyzeGraphBoolean or analyzeGraphPhrase with a stream that has not been read. Every such call fails, whatever the text. A parser would use these hooks for text whose analysis has a token spanning more than one position (the test createFieldQuery uses to pick a graph hook, QueryBuilder.java:326-329), as multi-word synonyms do, but the failure does not depend on it (a probe shows it for non-graph and empty text too). Seen with the test framework's MockSynonymFilter and, in an independent check, with the production SynonymGraphFilter.
  • Not hit. Everyone using createBooleanQuery, createPhraseQuery, createMinShouldMatchQuery, createFieldQuery or a shipped parser (classic QueryParser, SimpleQueryParser): all reach the hooks through createFieldQuery's filled cache. Graph queries are on by default (QueryBuilder.java:62), but only the direct-call path breaks.
  • Scale. Deterministic, with assertions on or off; an exception on the first such call, no index involved, no wrong result.
  • How likely. Rare: it needs a subclass that calls these hooks directly, it shows in the developer's first test, and no public report of it was found, though it has been there since 6.4.0 (2017).
  • Workaround. Wrap the stream in a CachingTokenFilter and read it once before the call, or call the protected createFieldQuery(TokenStream, ...) (QueryBuilder.java:289), which does that.

Why it looks unintended

#
  • The TokenStream workflow has the consumer call reset() once, and Tokenizer's own message calls "reset() called multiple times" a contract violation.
  • Neither hook's javadoc asks for a cached, already-read stream, and upstream's TestQueryBuilder calls both hooks directly with fresh streams.
  • The extra reset is redundant on every path: GraphTokenStreamFiniteStrings resets its input itself.
The full argument193 words
  • The contract. "The consumer calls TokenStream#reset()", then incrementToken() "until it returns false" (TokenStream.java:49-61). Tokenizer names "reset() called multiple times" a contract violation (Tokenizer.java:115-118); the test framework's MockTokenizer fails with "double reset()" (MockTokenizer.java:332).
  • No precondition. "Creates a boolean query from a graph token stream" (QueryBuilder.java:499-503) and "Creates graph phrase query from the tokenstream contents" (:565): no word about a cache, and neither is @lucene.internal. The class "can also be used as a subclass for query parsers" (:55-57).
  • Upstream calls them with fresh streams. TestQueryBuilder.testMaxBooleanClause (TestQueryBuilder.java:535-547, added in 2018 by LUCENE-8479).
  • The siblings accept a fresh stream. The five other analyze* hooks reset once and work on a fresh stream (QueryBuilder.java:371-475).
  • Redundant. GraphTokenStreamFiniteStrings "Consumes a TokenStream" and resets it itself (GraphTokenStreamFiniteStrings.java:42-46, :197).
  • Precedent. LUCENE-6121 (#7183) treated an earlier QueryBuilder double reset as a defect: 72d3f294606 (David Smiley, 2014) "add test to ensure no double-reset" (TestQueryBuilder.testNoTermAttribute, :491).
  • Nothing endorses it. The threads that added and split the hooks (#8654, #8689) do not discuss the reset (it appears only inside quoted diff excerpts).
The devil's-advocate check164 words

Strongest case for "intended": the analyze* methods are template steps of createFieldQuery, which always calls them after its first pass has filled a CachingTokenFilter, so every later reset() is a rewind; the five sibling hooks say they work "from the cached tokenstream contents" (QueryBuilder.java:371, :384, :413, :436, :463); and a parser with a raw stream can call the protected createFieldQuery(TokenStream, ...). A maintainer could answer "call createFieldQuery instead".

Why it fails: the graph hooks do not say "cached"; even a CachingTokenFilter not yet read fails, so of the analyzer (Tokenizer-backed) streams tried, only an already-read cache works, an undocumented precondition (a stream whose reset() can be repeated, such as upstream's CannedBinaryTokenStream, also works); upstream's own test passes fresh streams; the siblings work on fresh streams despite their wording; and the line is redundant even on the intended path. It does justify the Low priority (the cross-model review rated the "intended" case moderate).

Trade-offs

  • No behaviour change seen in the tests run, apart from the fix itself. A stream whose reset() cannot be repeated (any Tokenizer) now sees one reset instead of two; a stream whose reset() can be repeated (a filled cache, the default no-op) behaves as before, because the constructor still resets it once.
  • Empty text: on a fresh stream with no tokens, analyzeGraphBoolean now gets past the reset and then fails the way it already fails on main for a read, empty cache (AssertionError in Automaton.initTransition with assertions on, ArrayIndexOutOfBoundsException with them off). createFieldQuery never calls a hook for zero tokens (QueryBuilder.java:335-336), so this is outside the bug and not claimed.
  • Optionally drop the same redundant line in the private IntervalBuilder.analyzeGraph (IntervalBuilder.java:202) for consistency; it is not reachable with a fresh stream and was not tested.
  • Open PR #14262 would remove the analyzeGraphBoolean half as a side effect of its multi-field change, not the analyzeGraphPhrase half.

What the checks validated

  • Without the fix the repro fails with assertions on and off (gradle, seed DEADBEEF).
  • With the fix: the repro passes with assertions on and off; :lucene:core:test --tests org.apache.lucene.util.TestQueryBuilder --tests 'org.apache.lucene.util.graph.*' passes, 41 tests (TestQueryBuilder 26, TestGraphTokenStreamFiniteStrings 15); :lucene:queryparser:test passes, 533 tests, 1 skipped (it includes classic-parser tests of multi-word-synonym graph queries, e.g. TestQueryParser.java:557-626; not a proof that every parser path was covered); checkGoogleJavaFormat for core passes.
  • The probe returns the expected queries from both hooks on fresh streams and on unread and read caches.
  • One seed; the full suite and nightly tests were not run. The same change made the other checks' own tests pass.

B. Document a precondition instead

#

Say in both hooks' javadoc that source must be a CachingTokenFilter that has already been read.

Trade-offs

No behaviour change, but it writes down a rule that the sibling hooks and upstream's own test do not follow, and it keeps Lucene's own double reset. Not validated (documentation only).

Downstream note

#

A downstream parser that subclasses QueryBuilder and calls these hooks directly can work around it today by passing a CachingTokenFilter it has read once, or by calling the protected createFieldQuery(TokenStream, ...) instead.

How it was found

#

A semi-formal proof-obligation audit of QueryBuilder's graph hooks against the TokenStream consumer workflow (reset once, then read): each hook resets its stream and then hands it to a consumer that resets it again. A one-test JUnit on stock main witnessed the violation.

The method in full83 words

The audit took the obligation that every consumer of a TokenStream calls reset() exactly once before reading it (TokenStream.java:49-61, enforced by Tokenizer) and checked each QueryBuilder hook against it. In the two graph hooks the stream is reset by the hook and again by GraphTokenStreamFiniteStrings.build. A one-test JUnit on the stock main jars witnessed the exception with assertions on and off; a probe showed which inputs survive (of the analyzer streams tried, only a cache that was already read).
