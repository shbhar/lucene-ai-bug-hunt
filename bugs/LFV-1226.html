BinaryPoint.newRangeQuery accepts bounds with different numbers of dimensions when their byte totals match

BinaryPoint.newRangeQuery documents an IllegalArgumentException when the two bounds have different numbers of dimensions, but checks only their byte totals. A 2 × 2-byte lower bound and a 1 × 4-byte upper bound are accepted, and the upper bound is cut into two 2-byte dimensions; since 6.0.0.

The finding in 30 seconds

#

The constructor compares the two bounds' packed byte lengths, not their numbers of dimensions, so a shape mistake that keeps the byte total gets through.

Background: how a BinaryPoint range is built

#
  1. A BinaryPoint field stores points of N dimensions, each dimension a fixed number of bytes; both numbers are fixed when the field is indexed.
  2. newRangeQuery(field, lower, upper) takes each corner of the box as a byte[][], one byte[] per dimension, so lower.length is the number of dimensions.
  3. Inside, the query keeps each corner as one flat byte[] (its dimensions concatenated) plus a dimension count, and cuts the flat bytes back into dimensions of bytes / count bytes.

The finding, step by step

#
  1. On a BinaryPoint field with 2 dimensions of 2 bytes each, build a range but get the upper bound's shape wrong: newRangeQuery("f", {{0,0},{0,0}}, {{1,1,1,1}}). The lower bound has 2 dimensions × 2 bytes, the upper bound 1 dimension × 4 bytes; both are 4 bytes in total.
  2. You expect IllegalArgumentException: the javadoc promises it whenever lowerValue.length != upperValue.length, here 2 != 1.
  3. Instead you get a query, f:[binary(0 0) TO binary(1 1)],[binary(0 0) TO binary(1 1)]. Each bound is flattened to bytes on its own (4 and 4), only those lengths are compared, and the upper bound's 4 bytes are read as two 2-byte dimensions.
  4. On a field indexed as 2 × 2 bytes the query then runs with no error; on a 1 × 4-byte field the search fails later, with a message about the field. With unequal byte totals (2 × 2 against 1 × 3 bytes) the call is rejected, as documented.

Who is affected

#

Only applications that call the multi-dimensional BinaryPoint.newRangeQuery with a mis-shaped bound whose byte total still matches. The mistake is not reported where the javadoc promises: the query runs silently if the lower bound matches the field's layout; on a field with another layout, search fails later with an error about the field. Well-formed queries and fixed-width point types are unaffected.

Mechanism, terms and numbers608 words

The n-dimensional BinaryPoint.newRangeQuery(String, byte[][], byte[][]) documents @throws IllegalArgumentException ... if lowerValue.length != upperValue.length, that is, when the two bounds have different numbers of dimensions. It packs each bound into one flat byte[] on its own and passes only the lower bound's dimension count to PointRangeQuery, whose constructor compares just the two packed lengths. A dimension-count mismatch is therefore caught only when it also changes the byte total: 2 × 2 bytes against 1 × 4 bytes is accepted, and the upper bound's bytes are read in the lower bound's layout. The caller's shape error then goes unreported: the query runs silently when the lower bound's layout matches the indexed field and, on a segment whose field has a different layout, fails at search time with an IllegalArgumentException about the field. Well-formed queries, mismatches with different byte totals and the fixed-width point types are unaffected. It has been there since the 2016 refactor to packed bounds (LUCENE-7117/7118), in every release from 6.0.0 through 10.6.0 and on main. Low priority; the fix is a single dimension-count check before packing.

The mechanism (main 5adff78bb168)

#
  1. The factory. BinaryPoint.newRangeQuery(String, byte[][], byte[][]) (BinaryPoint.java:192-194) returns new PointRangeQuery(field, pack(lowerValue).bytes, pack(upperValue).bytes, lowerValue.length) {...}: each bound is packed separately, and only the lower bound's dimension count is passed on.
  2. pack (BinaryPoint.java:86-119) rejects a null bound and zero dimensions (:87-92) and returns a one-dimension bound as is (:93-95); only for two or more dimensions does it also reject null or empty values and dimensions of unequal byte length within one bound (:96-113), then concatenate them (:114-118). It never sees the other bound.
  3. The constructor (PointRangeQuery.java:72-98) checks numDims > 0 (:75), that lowerPoint.length is a multiple of numDims (:81) and that the two packed lengths are equal (:84-90), then sets bytesPerDim = lowerPoint.length / numDims (:92). With 4 and 4 bytes and numDims = 2, every check passes and bytesPerDim = 2.
  4. Why only BinaryPoint. IntPoint, LongPoint, FloatPoint and DoublePoint carry the same @throws sentence (IntPoint.java:212, LongPoint.java:231, FloatPoint.java:241, DoublePoint.java:241), but their bytes per dimension are fixed, so a different dimension count always changes the byte total and :84 rejects it. The same holds for the sandbox types BigIntegerPoint (16 bytes, BigIntegerPoint.java:51, :217) and HalfFloatPoint (2 bytes, HalfFloatPoint.java:61, :369). The one-dimension overload newRangeQuery(String, byte[], byte[]) wraps each bound in a one-element array (BinaryPoint.java:177-179) and is unaffected.

At search time

#

One document with a 2 × 2-byte field and a 1 × 4-byte field: the 2 × 2 / 1 × 4 query on the 2 × 2 field counts 1 hit with no error and equals() the well-formed query from {{0,0},{0,0}} to {{1,1},{1,1}}; on the 1 × 4 field the search throws field="p1x4" was indexed with numIndexDimensions=1 but this query has numDims=2. The 1 × 4 / 2 × 2 query behaves the same way the other way round.

Exposure and likelihood229 words
  • Who. Applications that build multi-dimensional BinaryPoint ranges from bounds they assemble themselves and get one bound's shape wrong while keeping the same byte total. Lucene's query parsers do not build BinaryPoint ranges: outside tests, BinaryPoint appears in main only in BinaryPoint.java, in javadoc (PointValues, SortedDocValuesField, SortedSetDocValuesField) and in the test framework.
  • Effect. The documented IllegalArgumentException at construction is missing. When the lower bound's layout matches the indexed field, the query runs over the upper bound's bytes in that layout and nothing ever reports the mistake; on a segment whose field has a different layout the search fails with an IllegalArgumentException about the field's dimension count or bytes per dimension (PointRangeQuery.java:627-644), which points away from the bounds; a segment without points for the field gives no hits and no error (:622-625), as for any query.
  • Default vs opt-in. BinaryPoint is an opt-in field type; no setting is involved, and assertions on or off make no difference.
  • Scale. One call; nothing is written to the index; no persistent effect and no resource amplification was found.
  • Likelihood: contrived. One plausible slip, passing one bound as a single already-packed byte[], either re-splits into the intended bound (the query equals() the well-formed one) or fails at search time on a segment that has the field. No public report of it was found since 2016.

Why it looks unintended

#
  • The javadoc names this input: @throws IllegalArgumentException ... if lowerValue.length != upperValue.length, on byte[][] bounds, so dimension counts.
  • The check worked when the clause was written; the 2016 move to packed bounds dropped it without discussion.
  • No test or CHANGES entry relaxes it; the fixed-width point types still enforce it.
The full argument177 words
  • Contract. BinaryPoint.java:188-189: @throws IllegalArgumentException if {@code field} is null, if {@code lowerValue} is null, if {@code upperValue} is null, or if {@code lowerValue.length != upperValue.length}. Nothing narrows it.
  • History. The clause comes from 099e0311398 (LUCENE-7045, 2016-02-23), when PointRangeQuery still took byte[][] bounds and threw lowerPoint has length=... but upperPoint has different length=... on a dimension-count mismatch. e1a1dbfabcc (LUCENE-7117/7118, 2016-03-20) moved to packed bounds and kept the javadoc; its new check first compared upperPoint.length with itself, and 54e662b6dab (later the same day) made it today's packed-length comparison. The review thread (#8173) discusses only that self-comparison.
  • Tests. No test passes bounds of different dimension counts to BinaryPoint. TestPointQueries.testInvalidPointLength (:2381-2394) asserts the packed-length error on the expert constructor (4 against 8 bytes); testWrongNumDims (:1147) and testWrongNumBytes (:1176) cover a query whose shape disagrees with the indexed field.
  • Executed bisect. With the parent commit's BinaryPoint.java and PointRangeQuery.java compiled over the 6.0.0 jars the repro passes (lowerPoint has length=2 but upperPoint has different length=1); with the introducing commit's files it fails.
The devil's-advocate check102 words

Strongest argument: this is malformed caller input; the accepted query has a consistent byte-level meaning (it equals() the well-formed query on the same packed bytes), and a layout that does not match the field fails at search time anyway. Why it fails: the javadoc promises to reject exactly this input at construction, the promise was true when it was written and was lost as a side effect of a refactor, and in the silent case nothing ever reports the mistake. The argument lowers the impact (hence Low), not the intent. A committer may still prefer to narrow the javadoc instead (option B).

Suggested fix

#

Recommended Reject differing dimension counts in newRangeQuery before packing (A, recommended, validated)

Check the dimension counts before packing: in newRangeQuery(String, byte[][], byte[][]), throw IllegalArgumentException when lowerValue.length != upperValue.length. The repro passes, and so do the 54 TestPointQueries tests.

  public static Query newRangeQuery(String field, byte[][] lowerValue, byte[][] upperValue) {
    if (lowerValue != null && upperValue != null && lowerValue.length != upperValue.length) {
      throw new IllegalArgumentException(
          "lowerValue has "
              + lowerValue.length
              + " dimensions but upperValue has "
              + upperValue.length);
    }
    return new PointRangeQuery(
        field, pack(lowerValue).bytes, pack(upperValue).bytes, lowerValue.length) {

Reject differing dimension counts in newRangeQuery before packing (A, recommended, validated)

#

In BinaryPoint.newRangeQuery(String, byte[][], byte[][]) (BinaryPoint.java:192), throw IllegalArgumentException when both arrays are non-null and lowerValue.length != upperValue.length. Null arguments keep pack's existing IllegalArgumentException. With equal dimension counts and equal packed lengths, pack's per-bound check already forces equal bytes per dimension, so nothing else is needed.

Trade-offs

One comparison per query construction. Code that relies on the silent re-split today (for example an upper bound passed as one packed byte[] against a multi-dimension lower bound) gets the exception the javadoc already documents. One message changes: for a null field together with two non-null bounds of different dimension counts, the new dimension-count message now comes before PointRangeQuery.checkArgs' field must not be null (PointRangeQuery.java:73, :107-108); both are IllegalArgumentException. Starting the fix with PointRangeQuery.checkArgs(field, lowerValue, upperValue), as IntPoint.newRangeQuery does (IntPoint.java:216), would keep the null-field message first (not run).

Narrow the @throws clause to the packed byte lengths (B, documentation only)

#

Change the @throws text of newRangeQuery(String, byte[][], byte[][]) to say what is enforced: the two bounds' total byte lengths must be equal. The expert PointRangeQuery constructor's javadoc (PointRangeQuery.java:69-70) also still says lowerValue.length != upperValue.length, names that constructor does not have; that stale clause can be fixed with either option.

Trade-offs

No behaviour change, so nothing can break, but the caller's shape mistake stays silent whenever the byte totals agree; the fixed-width point types do not need the change. Not run.

Downstream note

#

Lucene's query parsers never build BinaryPoint ranges, so only a downstream product that turns its own input into multi-dimensional BinaryPoint bounds can reach this, and checking that both bounds have the same number of dimensions there avoids it.

How it was found

#

A proof-obligation audit of BinaryPoint.newRangeQuery's documented @throws contract: every input the javadoc says it rejects must be rejected. The obligation fails for bounds with different dimension counts but equal byte totals, and a one-method JUnit test witnessed it on main and on the release jars.

The method in full126 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The audit takes each @throws condition of newRangeQuery(String, byte[][], byte[][]) as an obligation and traces which check discharges it: the null conditions are discharged by pack (BinaryPoint.java:87-89) and PointRangeQuery.checkArgs (PointRangeQuery.java:106-116); lowerValue.length != upperValue.length by nothing, because only the packed lengths reach PointRangeQuery.java:84.
  • A shape probe then mapped which mismatches get through (equal byte totals) and which do not (unequal totals), and a one-method JUnit test plus the one-check fix that makes it pass witnessed the gap.
  • An independent reproducer, an executed cross-model refute review and a devil's-advocate verifier reproduced it with their own tests or re-runs, and an adjudication re-ran the test ("Prior reports, history and checks").
