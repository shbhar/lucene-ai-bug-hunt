IndexWriter.tryUpdateDocValue never checks the RAM buffer, so pending updates grow the heap until the next refresh

Every successful IndexWriter.tryUpdateDocValue call parks about 334 bytes of pending updates per updated numeric field in the writer, and no RAM check ever writes them out: with a 1 MB buffer, 10,000 calls leave 3,340,000 bytes pending. Without a refresh, flush() or commit the heap keeps growing until OutOfMemoryError.

The finding in 30 seconds

#

Background: where doc-values updates wait before they reach disk

#
  1. An update by term, such as updateNumericDocValue(new Term("id", "7"), "counter", 5), is first buffered, then resolved to document ids in a batch (a packet). The resolved per-document values wait in the writer's per-segment state, the reader pool, until they are written to disk.
  2. After every packet the writer checks the reader pool: if it holds more than half the RAM buffer (16 MB by default), it writes the largest segments' pending updates. A refresh, flush() or commit writes them too.
  3. tryUpdateDocValue (Expert) skips the batch: it takes a document id from an NRT reader and adds its resolved update to the reader pool directly.

The finding, step by step

#
  1. Open a writer with a 1 MB RAM buffer, add and commit one document with a numeric doc-values field counter, and open an NRT reader on the writer.
  2. Call writer.tryUpdateDocValue(reader, 0, new NumericDocValuesField("counter", i)) 10,000 times. Every call succeeds.
  3. You expect the writer to write the pending updates to disk once they pass half the buffer (524,288 bytes, after 1,570 calls), as it does for the same updates made through updateNumericDocValue(Term, ...).
  4. Instead 3,340,000 bytes stay pending: 10,000 separate update objects of 334 bytes, none written, and IndexWriter.ramBytesUsed() does not count them.
  5. Keep going with the default 16 MB buffer and no refresh: 73, 138 and 202 MiB of heap after 187,500, 375,000 and 562,500 calls, then OutOfMemoryError in a 256 MB heap. The term-based path stays at 13 to 24 MiB for 1.5 million calls.

Who is affected

#

Applications that call the Expert tryUpdateDocValue (counters, soft-deletes, un-deletes) many times between NRT refreshes, flush() or commit, with default settings otherwise. Each call keeps about 334 bytes per numeric field (about 530 for an 8-byte binary value); a soft-delete pass over a 200,000-document segment leaves 66.8 MB pending. Any refresh, flush() or commit bounds it again.

Mechanism, terms and numbers710 words

IndexWriter.tryUpdateDocValue (Expert) updates a doc value of a document found through an NRT reader. Each successful call builds a new per-field update object and adds it straight to the segment's pending updates in the writer's reader pool. The writer's rule for those pending updates, "If the reader pool is > 50% of our IW buffer, then write the updates", runs only after a packet of buffered deletes or updates has been applied, which the try path never creates. So nothing ever compares the try-updates with the RAM buffer: they stay on the heap, about 334 bytes per numeric field update and about 530 per binary one (8-byte values), until an NRT refresh, flush(), commit, a merge of the segment or an unrelated term-based update writes them. With a 1 MB buffer, 10,000 calls on one document leave 3,340,000 bytes pending; with the default 16 MB buffer and a reader that is never refreshed, the heap grows linearly to OutOfMemoryError. IndexWriter.ramBytesUsed() does not count this memory. The same updates through updateNumericDocValue(Term, ...) stay bounded. Every release since the method arrived in 7.4.0 is affected; calling the existing rule after a successful try-update fixes it.

Terms

#
  • Reader pool / pending updates: the writer keeps one ReadersAndUpdates per segment. Resolved doc-values updates wait there as DocValuesFieldUpdates objects, one list per field, until they are written as a new doc-values generation of the segment. ReadersAndUpdates.addDVUpdate documents the plan: "We buffer these in RAM and write to disk when too much RAM is used or when a merge needs to kick off, or a commit/refresh" (ReadersAndUpdates.java:148-151).
  • The rule: IndexWriter.writeSomeDocValuesUpdates sums the reader pool and, "If the reader pool is > 50% of our IW buffer", writes the largest segments' pending updates (IndexWriter.java:807-884, test at :816; skipped when RAM flushing is disabled, :812). Its only call site runs after a frozen packet is applied: "Since we just resolved some more deletes/updates, now is a good time to write them" (:6599-6600).

The bug (main e1faeba08bde)

#
  1. public synchronized long tryUpdateDocValue(IndexReader readerIn, int docID, Field... fields) (IndexWriter.java:1721) builds the updates (:1724) and calls tryModifyDocument (:1725, defined at :1791-1829), which finds the segment's ReadersAndUpdates and runs the closure.
  2. The closure takes a fresh generation (:1729), creates a new NumericDocValuesFieldUpdates or BinaryDocValuesFieldUpdates per field (:1740, :1743), adds the one document, then updates.finish(); rld.addDVUpdate(updates); (:1773-1776) and changed() (:1782). Nothing runs after it.
  3. addDVUpdate appends the object (ReadersAndUpdates.java:163) and adds its size to the segment's counter (:161). It compares nothing.
  4. A try-update creates no packet, so it never reaches the rule. Pending try-updates are written only by an NRT refresh, flush(), commit, a merge of the segment, or the packet apply of an unrelated term-based delete or update. An automatic RAM-triggered segment flush from adding documents, with no buffered term-based deletes or updates, does not write them (a flush that also publishes such a packet runs the rule through that packet's apply).
  5. IndexWriter.ramBytesUsed() returns docWriter.ramBytesUsed() only (IndexWriter.java:795-799), so it reports 0 for all of this memory. It leaves out the reader pool on every path, so this is context, not a second bug.

Exposure and likelihood253 words
  • Who is hit. Applications that call tryUpdateDocValue on a numeric, binary or soft-deletes field many times between NRT refreshes, flush() or commit, with no term-based delete or update in between: for example one try soft-delete or un-delete per document over a large segment (the javadoc names un-deleting a soft-deleted document as a use), or a stream of per-document counter updates while refresh is paused. Inside Lucene only two tests call it; a code search found no call in Elasticsearch, OpenSearch or Solr (2026-11-02).
  • Default vs opt-in. The API is Expert and opt-in; everything else is the default IndexWriterConfig (16 MB buffer). The bug needs RAM-based flushing, which is the default: with RAM flushing disabled (DISABLE_AUTO_FLUSH, flushing by document count instead) the rule skips its check (IndexWriter.java:812), so no path has it and the try path no longer differs.
  • Scale. Growth is per call, not per document. Between 562,500 and 750,000 numeric calls fill a 256 MB heap when the reader is never refreshed. One long bulk pass over a single reader, the natural way to resolve the doc ids, is enough.
  • What bounds it. Any NRT refresh, flush(), commit, a merge of the segment, or an unrelated term-based delete or update. NRT applications that refresh every few seconds will rarely notice.
  • What does not happen. No wrong search results, no index damage, no data loss. With assertions enabled each call also gets slower (an assertion scans the growing list); that is test-only and not part of the claim.

Why it looks unintended

#
  • ReadersAndUpdates.addDVUpdate, called on this path, says these updates are written "when too much RAM is used"; the writer's rule is "If the reader pool is > 50% of our IW buffer, then write the updates".
  • The same updates through updateNumericDocValue(Term, ...) are bounded by that rule.
  • The rule (2017) predates the try method (2018), which never added the check.
The full argument344 words
  • Contract and design statements. ReadersAndUpdates.addDVUpdate: "Adds a new resolved (meaning it maps docIDs to new values) doc values packet. We buffer these in RAM and write to disk when too much RAM is used or when a merge needs to kick off, or a commit/refresh." (ReadersAndUpdates.java:148-151). writeSomeDocValuesUpdates: "If the reader pool is > 50% of our IW buffer, then write the updates" (IndexWriter.java:811). setRAMBufferSizeMB: "Determines the amount of RAM that may be used for buffering added documents and deletions before they are flushed to the Directory." (LiveIndexWriterConfig.java:158-159). The IndexWriter class javadoc: "These changes are buffered in memory and periodically flushed to the Directory" (IndexWriter.java:123-124). The tryUpdateDocValue javadoc (:1707-1720) says nothing about memory and does not ask callers to refresh for it.
  • The sibling paths are bounded. Term-based updates are held first by the buffered-updates RAM trigger and, once a packet apply resolves them into the pool, by the rule: 200,000 term updates with a 1 MB buffer leave 371,596 bytes in the pool, below half the buffer. tryDeleteDocument creates no doc-values updates; it writes into a fixed-size live-docs bitset. A merge also adds resolved updates to the merged segment (IndexWriter.java:4526-4542), but only the ones that resolved on its source segments while it ran, remapped once per merge, so it adds no growth of its own. Upstream TestNumericDocValuesUpdates.testUpdatesAreFlushed sets a tiny RAM buffer and asserts that getFlushDeletesCount() goes up after each term-based update; it does not look at the reader pool or the 50% rule. No upstream test covers memory on the try path or relies on the unbounded behaviour.
  • History: no record of a decision to exempt this path. LUCENE-7868 (58105a203a1, 2017-06-21, 7.0.0) added the rule. LUCENE-8297 (b0b32931b28, 2018-05-05, 7.4.0) added tryUpdateDocValue on tryModifyDocument, shared with tryDeleteDocument, and added no check; #9344 never mentions RAM.
  • Precedent. LUCENE-5248 (#6312, 2013, fixed in 4.6) fixed the same symptom on the then term-based path, where resolved updates would "just keep accumulating there, until RAM is exhausted".
The devil's-advocate check230 words

The strongest case for "works as designed" (built by the devil's-advocate verifier; the cross-model reviews and the adjudication rated it moderate): the RAM buffer names only "added documents and deletions", "is just an indicator when to flush" (LiveIndexWriterConfig.java:166-172) and may release only part of the buffer, depending on the FlushPolicy (:179-181); ReadersAndUpdates is package-private, so its javadoc states design intent, not a public contract; the API is Expert and tied to an NRT reader the caller is expected to refresh, and the same javadoc already tells delete-by-Query users to "compensate by either calling commit() or refresh() periodically yourself" (:174-177).

Why it fails: the "indicator" and FlushPolicy caveats allow overshoot from flushes that run while other threads keep adding documents (:169-171) and partial flushes (:179-181), not memory that grows with every call and is never checked; the refresh-yourself advice is scoped to delete-by-Query, whose RAM "Lucene currently has no way to measure", while these bytes are measured (ReadersAndUpdates.java:161) and then never compared; the same resolved updates through the term path are bounded by exactly this rule; and the commit and issue records show no decision to exempt this path. What stays true: no public javadoc promises in so many words that tryUpdateDocValue honours the RAM buffer, so it is Low and a maintainer may call the fix an improvement.

Suggested fix

#

Recommended A. Run the existing RAM rule after a successful try-update (validated)

Call the writer's existing RAM rule, writeSomeDocValuesUpdates(), after a successful try-update (+8/-1 in IndexWriter.java). The test passes (assertions on and off) and 104 tests of the seven closest suites pass (assertions on). Open question for maintainers: this writes doc-values files while holding the writer's monitor; option B makes the same call outside it and passes the same tests.

A. Run the existing RAM rule after a successful try-update (validated) (recommended)

#

The hunt's diff, unchanged: keep tryModifyDocument's sequence number and, when it is not -1, call writeSomeDocValuesUpdates(), so each successful call attempts the same best-effort 50% rule that runs after a packet apply (the attempt is skipped while another thread holds writeDocValuesLock and is itself writing, IndexWriter.java:808). No API change.

Trade-offs

  • Writes under the monitor. tryUpdateDocValue is synchronized, so doc-values files are written while the IndexWriter monitor is held. writeSomeDocValuesUpdates was designed to take that monitor once per segment write ("Only acquire IW lock on each write, since this is a time-consuming operation. This way other threads get a chance to run in between our writes", IndexWriter.java:842-843), and LUCENE-7868 first asserted that it runs without the monitor (the assert was removed in LUCENE-8260, 8975692953). Other threads that need the writer's monitor (for example other try-updates and tryDeleteDocument, both synchronized) wait while these files are written. No new lock-order edge that can block: the only edge A adds is the writer's monitor -> writeDocValuesLock, which is taken only with tryLock() (:808) and never waits; the monitors the method then takes (ReaderPool, the synchronized ReadersAndUpdates.writeFieldUpdates) are already taken under the writer's monitor on the packet path (synchronized (this), :844-860). No run deadlocked, but no concurrent stress test was run.
  • Per-call cost. Each successful call also sums the reader pool (ReaderPool.ramBytesUsed(), synchronized, one pass over the pooled segments).
  • More files. Heavy try-update streams write new doc-values generations more often instead of holding memory.
  • Untested corner (a cross-model review note): the write covers only generations up to the completed delete generation (:857), so while older packets are still being applied the call may write nothing until those packets' own apply runs the rule.
  • Error semantics. The update is already in the pool when writeSomeDocValuesUpdates runs, so if that write throws an IOException the caller gets an exception for an update that took effect, and a retry adds another update.

B. The same call, outside the monitor (validated)

#

Drop synchronized from tryUpdateDocValue and make the same call after tryModifyDocument returns. tryModifyDocument stays private synchronized and runs the closure under the monitor, so the update itself is serialized as before; building the update objects then runs unsynchronized, as it already does in updateDocValues(Term, ...). This matches the packet-apply call site, which also runs outside the monitor ("don't hold IW monitor lock here", IndexWriter.java:6590).

Trade-offs

Changes the locking of a public method: callers no longer hold the writer's monitor for the whole call. Otherwise as A (per-call sum, more files, the same untested corner, the same error semantics).

What the checks validated

The same gradle runs as A: the minimal test passes with B, assertions on and off, and the same 104 tests pass with assertions on. Only this doc and the fact check ran B, and it was not format-checked; the hunt's exhaustive check, its 86 upstream tests and the reviewers covered A only.

C. Merge per-call updates (not run)

#

Keep one update object per segment and field and add to it, so memory grows with documents, not calls.

Trade-offs

Each call has its own delete generation, which orders it against buffered term-based updates; merging generations touches the ordering that LFV-009 (a try-update overwritten by an earlier buffered update) is about. A larger change.

D. Count the reader pool in flush decisions or in IndexWriter.ramBytesUsed() (not run)

#

Let the existing flush control see the pending updates.

Trade-offs

Broader: changes accounting for every path, not only this one.

E. Documentation only

#

Say in the tryUpdateDocValue javadoc that its pending updates are held until the next refresh, flush() or commit.

Trade-offs

Cheapest; leaves memory that is measured but never checked.

Downstream note

#

An application that lets its users trigger unlimited try-updates (for example per-document counters or soft-deletes) without refreshing can exhaust its own heap, so such applications should refresh, flush or commit on a schedule until a fix ships.

How it was found

#

Non-formal: a sweep that compared the retained heap of 11 IndexWriter workloads with the RAM buffer flagged try-updates on a never-refreshed reader, and their soft-delete variant, as growing without bound. The hunt reduced it to one JUnit test and checked it with a bounded exhaustive run over all 11,110 short sequences of writer operations.

The method in full165 words

Method: non-formal (the first signal was a heap probe).

  • The hunt swept 11 single-threaded IndexWriter workloads with the default config in a 256 MB heap and compared the heap retained after garbage collection with the 16 MB RAM buffer and IndexWriter.ramBytesUsed(). tryUpdateDocValue with a reader that is never refreshed, and its soft-delete variant, grew without bound to OutOfMemoryError; the same workload with a refresh every 10,000 calls, tryDeleteDocument and the term-based update workloads stayed bounded.
  • A hunt unit reduced the lead to the one-test repro and ran a bounded exhaustive model-based check on the real jar: all 11,110 sequences of 1 to 4 operations over 10 writer operations (try numeric, binary and soft-delete bursts, term updates, tryDeleteDocument, addDocument, an automatic flush, flush(), refresh, commit), comparing the pooled segment's pending bytes after every operation with the documented rule. 4,922 sequences break it on main and 0 with the fix; an abstract model of the code predicts all 33,570 byte values exactly.

LFV-1075, snapshot of 2026-11-02

Registry title
IndexWriter.tryUpdateDocValue never checks the RAM buffer for the doc-values updates it adds, so they pile up on the heap without bound until the next refresh, flush() or commit
Area
index / IndexWriter tryUpdateDocValue (reader-pool doc-values update RAM)
Priority
Low, rank 841: In every release since 7.4.0, bulk use of the Expert tryUpdateDocValue without a refresh, flush or commit piles up updates on the heap that the RAM buffer never counts, until OutOfMemoryError. Periodic refreshes bound it and no major search server calls the API, so it is Low.
Impact class
minor
Impact note
Hits applications that call the Expert IndexWriter.tryUpdateDocValue (numeric, binary or soft-deletes field) many times between NRT refreshes, flush() or commit, with default settings: every call keeps about 334 bytes (numeric) to 530 bytes (binary) of resolved updates on the heap that no RAM-buffer check ever writes out and that IndexWriter.ramBytesUsed() reports as 0, so one try soft-delete per document over a 200,000-doc segment leaves 66.8 MB pending (about 4x the default 16 MB buffer) and a run with a reader that is never refreshed grows linearly to OutOfMemoryError (256 MB heap, between 562,500 and 750,000 calls); any refresh, flush(), commit, merge of the segment or unrelated term-based delete or update bounds it again, and an automatic RAM-triggered segment flush does not.
Summary
You open an NRT reader from an IndexWriter and call tryUpdateDocValue on its documents many times, for example 10,000 counter updates or one soft-delete per document, and expect the writer to keep these pending updates within its RAM buffer and write them out once they use too much RAM, as it does for the same updates made through updateNumericDocValue. Instead every call adds one more pending-update object to the writer's per-segment state and nothing ever compares their size with the buffer: with a 1 MB buffer, 10,000 calls leave 3,340,000 bytes pending, and without a refresh, flush() or commit the heap keeps growing until OutOfMemoryError. IndexWriter.ramBytesUsed() reports 0 for all of it.
Introduced
b0b32931b28da83d47f0561f4da734d6b9ee6e16 (master, 'LUCENE-8297: Add IW#tryUpdateDocValues(Reader, int, Fields...)', by Simon Willnauer (s1monw); JIRA LUCENE-8297 = apache/lucene#9344, a patch, no pull request; the code the 8.0+ releases ship) and its same-day branch_7x commit 48a2138e899bca0b8a8485fb7e490a9dc943d997 (the code the 7.x releases ship): tryUpdateDocValue was built on tryModifyDocument, shared with tryDeleteDocument, and adds each call's resolved updates straight to the pooled ReadersAndUpdates (rld.addDVUpdate), so it never reaches writeSomeDocValuesUpdates, the 'reader pool > 50% of our IW buffer' rule from LUCENE-7868 (58105a203a1, 2017-06-21, first in 7.0.0), whose only call site is after a frozen-packet apply; no RAM check was added [read: git blame on 7cecf795236c, whose IndexWriter.java is byte-identical to 645d4fe14a20; the later edits a3c86373e47 (LUCENE-8298), 2d6ad2fee6d (reformat), 79fcd99f4cf, 169cbffd12f (#16581) and 7540c29ee84 (javadoc) do not touch RAM].
