The bug in 30 seconds

#

The completion filter adds romaji tokens to each Japanese word, read from the bundled table romaji_map.txt, so a suggester can match Latin-letter input. The row for ッヘ has a look-alike hiragana character in its key, so it never matches.

  1. You index the names ヨッハン and ヨッヘン as suggestions with JapaneseCompletionAnalyzer and type their romaji into a completion query.
  2. You expect yohhen to suggest ヨッヘン, as yohhan suggests ヨッハン: Hepburn, Kunrei and Nihon all spell ッヘ hhe, and the table has a row for it, ッへ,hhe.
  3. Instead yohhen suggests nothing, with no error. Typing through an input method, the state よっh (query term yohh) finds ヨッハン but not ヨッヘン.
  4. Why: in that row the へ is hiragana (U+3078), not katakana ヘ (U+30D8). Inside the analyzer the romanizer only ever sees katakana or a-z, so the row never matches: ッヘ becomes ッ xtu + ヘ he, and ヨッヘン is indexed as [ヨッヘン, yoxtuhen, yoxtuhenn].
  5. Kana typed in full (よっへ, ヨッヘ) still find it, because both sides share the wrong spelling. The rows ッスォ (suxo) and ッドゥ (ddoxi) carry other rows' spellings; no user impact is claimed for them.

Who is affected

#

Applications using the opt-in JapaneseCompletionAnalyzer or JapaneseCompletionFilter, with default settings, in every release since 9.0.0. Only words with katakana ッヘ, mostly transliterated names such as ヨッヘン, typed as raw romaji or caught in the input-method state よっh; kana typed in full still match. Rare and silent.

Mechanism, terms and numbers605 words

Kuromoji's completion analyzer (JapaneseCompletionAnalyzer, JapaneseCompletionFilter) indexes each Japanese word together with its romaji spellings, read from the bundled table romaji_map.txt, so an autocomplete can match Latin-letter input. Row 219 of that table, meant for katakana ッヘ, is written ッへ,hhe with the look-alike HIRAGANA LETTER HE (U+3078). Inside the analyzer romanize() only ever receives katakana or a-z, so the row can never match: ッヘ is spelled ッ → xtu plus ヘ → he, ヨッヘン is indexed as yoxtuhen, and typing yohhen (the Hepburn, Kunrei and Nihon spelling) or the input-method state よっh suggests nothing, while kana typed in full still match. Two more rows carry other rows' spellings (ッスォ suxo, ッドゥ ddoxi). All three are typos from the table's creation, in every release from 9.0.0 to 10.5.2 and on main; the fix is three characters of data.

Terms

#
  • Sokuon ッ: the small tsu doubles the next consonant. In romaji it is written by doubling: ッハ is hha, ッヘ is hhe in Hepburn, Kunrei and Nihon alike; input methods also accept xtu for a lone small tsu.
  • JapaneseCompletionFilter: for each word it emits the word itself and every romaji spelling of its katakana reading at the same position (generateOutputs, JapaneseCompletionFilter.java:217-233). The spellings come from romaji_map.txt; KatakanaRomanizer loads it (KatakanaRomanizer.java:44-84), splits a reading by longest key match and combines the matched rows' spellings (:103-169).
  • Completion query: PrefixCompletionQuery suggests a word when the typed text, after the QUERY-mode analyzer, is a prefix of one of the word's indexed forms. While an input method is still composing, the pending letters are appended to the reading (よっh → ヨッh → yohh, via the partial-input row ッh,hh, romaji_map.txt:332).

The bug

#

romanize() asserts that its input is katakana or a-z (KatakanaRomanizer.java:104), and its only production caller, JapaneseCompletionFilter.generateOutputs (JapaneseCompletionFilter.java:228), converts kana surfaces to katakana (:125-128) and skips every other reading (:221-226). A key with a hiragana character can therefore never be matched on the analyzer path. (KatakanaRomanizer is public; the only other calls in the tree are the module's own tests, with katakana and a-z input. Called directly with the hiragana key and assertions off, romanize returns [hhe]; with assertions on it fails.)

The numbers

#

On main: romanize(ッヘ) = [xtuhe] (control ッハ → [hha]); romanize(ッスォ) = [sswo, suxo]; romanize(ッドゥ) = [ddwu, ddoxi]. ヨッヘン is indexed as [ヨッヘン, yoxtuhen, yoxtuhenn], ヨッハン as [ヨッハン, yohhan, yohhann]. Typed yohhen and yohhe: no suggestion; よっh: ヨッハン only; よっへ, よっへん, ヨッヘ: ヨッヘン, because the query side makes the same mistake (よっへ and ヨッヘ → yoxtuhe, よっへん → yoxtuhen; ヨッヘ is also a prefix of the surface form).

The code follows the table: romanize() matched a separately coded longest-match model of the same table on all 1,830,854 inputs of length up to 3 and on 57,289,761 inputs of length 4 (0 mismatches; a shortest-match mutant was caught). The defects are in the data rows.

Why it is a bug, not intended

#
  • The row states its own mapping, ッへ,hhe, between ッヒ,hhi and ッホ,hho; its key differs from katakana ッヘ only by a look-alike character.
  • romanize() documents and asserts katakana input (KatakanaRomanizer.java:100-104), so the row can only match input that breaks that precondition.
  • suxo and ddoxi are verbatim spellings of other rows (スォ, ッドィ); nothing tests or discusses them.
The full argument224 words
  • The row states its own mapping. ッへ,hhe sits between ッヒ,hhi and ッホ,hho and differs from the katakana key only by a look-alike character. Every other key in the file is katakana, or ッ plus a letter a-z (the partial-input rows, :326-338).
  • The key is outside the asserted input domain. romanize() "Translates a sequence of katakana to romaji" (:100) and asserts it (:104); the filter enforces it (JapaneseCompletionFilter.java:125-128, :221-226).
  • The contract's three systems agree. The javadoc lists "(modified) Hepburn-shiki, Kunrei-shiki (Nihon-shiki) and Wāpuro shiki" (JapaneseCompletionFilter.java:41-42); all spell ッヘ hhe, with the same doubling as the sibling rows and the partial-input rows (ッh,hh; the upstream test asserts サッｋ → sakk, TestJapaneseCompletionFilter.java:213-219).
  • suxo and ddoxi are other rows' spellings. suxo is スォ's (:135), ddoxi is ッドィ's (:288); an input method composes them to すぉ and っどぃ (the open-source Mozc romaji table).
  • Nothing pins the current behaviour. No test asserts hhe, suxo, ssuxo or ddoxi; no CHANGES or MIGRATE entry or review comment mentions these rows; the only later commit on the file (#12047) fixed comment typos.
  • Precedent. In the #297 review a missing jji spelling was added on request; #12885, a romanization gap in the module's other romanizer, is listed under "Bug Fixes" in 9.10.0.
The devil's-advocate check128 words

The strongest case (the intended-behaviour checker and the cross-model review): the javadoc and the table header say the table "does not strictly comply with the romanization systems listed above, but tries to cover possible keystroke supported by various Input Methods", so coverage is best effort; KatakanaRomanizer is public, and with assertions off a caller passing mixed-script ッへ does get hhe; kana queries still work; the words are rare.

Why it fails: the caveat excuses deviations from the romanization systems (its example is the long-vowel mark), not a row that cannot deliver the mapping it states; mixed-script input breaks romanize()'s documented and asserted precondition; the partial-input design needs the doubled spelling; and suxo and ddoxi are verbatim spellings of other rows. The rest only limits the impact.

How it was found

#

A self-check script over every table row flagged a key with a hiragana character and two rows with other rows' spellings. Checks of the table's own rules confirmed them, and a bounded-exhaustive check showed KatakanaRomanizer implements the table as written (0 mismatches on 59 million inputs), so the defects are in the data.

The method in full204 words
  • First signal. A planning probe's self-check of romaji_map.txt (a script over every row) reported HIRAGANA-IN-KEY for line 219 (ッへ, U+3078) and GEMINATION-MISMATCH and SAME-SPELLING-FOR-DIFFERENT-KANA for lines 281 and 289.
  • Table laws. A checker of the table's own rules: L1 (every key lies in romanize()'s katakana/a-z input domain) flags only line 219; L2s (each spelling of a small-tsu row doubles a spelling of its base) flags lines 281 and 289, among its four hits (the other two, line 249 ッイ yyi and line 263 ッウ wwu, are not part of this bug); L3 (input-method round trip against the open-source Mozc romaji table) shows suxo composes to すぉ and ddoxi to っどぃ.
  • Translation validation (bounded-exhaustive). Part A: romanize() equals an independent longest-match model of the table on all 1,830,854 inputs of length up to 3 and 57,289,761 inputs of length 4 (0 mismatches; a shortest-match mutant: 33,518 mismatches). Part B: the standard spelling hhe of ッヘ is missing in Hepburn, Kunrei and Nihon alike.
  • Reduction. A public-API JUnit with the document suggester on the stock main jars, then this doc's kuromoji-only test.
  • Tier. Semi-formal: the first signal came from a script and a custom checker, not from a formal tool's own output.

Bug record

#

LFV-848, snapshot of 2026-10-28

Registry title
Kuromoji's completion table romaji_map.txt has three typo rows: the ッヘ row uses a hiragana へ (U+3078) in its key, so katakana ッヘ is romanized 'xtuhe' instead of 'hhe' and a word like ヨッヘン is not suggested for 'yohhen', and the ッスォ and ッドゥ rows carry the copied spellings 'suxo' and 'ddoxi'
Area
analysis / kuromoji (JapaneseCompletionFilter and JapaneseCompletionAnalyzer romanization table romaji_map.txt, read by KatakanaRomanizer)
Priority
Low, rank 418: The typo in the ッヘ key and the two rows for words that almost never occur only affect rare names like ヨッヘン typed in raw romaji, which is narrower than its sibling table-gap row LFV-850.
Impact class
silent wrong results
Impact note
Only applications that use the opt-in kuromoji JapaneseCompletionAnalyzer or JapaneseCompletionFilter (default constructors, INDEX and QUERY mode) are hit, and only for words that contain katakana ッヘ (for example the name ヨッヘン, indexed as 'yoxtuhen'): a raw-romaji query 'yohhen' (the Hepburn, Kunrei/Nihon and IME spelling) suggests nothing and the mid-composition query 'よっh' finds ヨッハン but not ヨッヘン, while queries typed fully in kana ('よっへ', 'ヨッヘ') still match because index and query side share the same wrong romanization; the ッスォ and ッドゥ rows are data typos with practically no reachable words, each keeping a working first spelling; no scale is needed, and every release from 9.0.0 to 10.5.2, branch_10_6 and main are affected.
Summary
You index the katakana name ヨッヘン with JapaneseCompletionAnalyzer and type its romaji 'yohhen' into a suggester, and expect the name to be suggested, just as ヨッハン is suggested for 'yohhan'. Instead nothing is suggested: the table row meant for ッヘ, 'ッへ,hhe' (romaji_map.txt line 219), has the look-alike HIRAGANA LETTER HE (U+3078) in its key, and romanize() only ever receives katakana or a-z, so the row can never match and ッヘ falls back to 'ッ'->'xtu' plus 'ヘ'->'he' (indexed as 'yoxtuhen'). The same table gives ッスォ the undoubled spelling 'suxo' (line 281, the spelling of スォ) and ッドゥ the spelling 'ddoxi' (line 289, copied from ッドィ) instead of 'ssuxo' and 'ddoxu'; a three-character table edit fixes all three.
