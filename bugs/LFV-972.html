The default codec's file-extension table is stale: seven extensions it writes are missing, and the vector row lists .veq instead of .vemf

The "Summary of File Extensions" table in the File Formats overview leaves out 7 of the 21 extensions that one ordinary document produces with the default codec, and its vector row lists .veq, which the default vector format never writes. Lucene handles every file correctly; only the documentation is wrong.

The finding in 30 seconds

#

The table that maps file extensions to formats in the File Formats overview has not kept up with the default codec since 8.5.0.

Background: index files and the extension table

#
  1. A Lucene segment is a set of files that share a name and differ by extension; each format of the codec writes its own files, for example .tim for the terms dictionary. Small segments are packed into one compound .cfs file; by default, merged segments above 64 MB stay separate files.
  2. The default codec's package documentation, the File Formats overview, has a "Summary of File Extensions" table: one row per kind of file, its extensions, a short description and a link to the format page with the details.

The finding, step by step

#
  1. You index one document with a stored field with term vectors, a numeric doc-values field and a 2-dimensional vector, with the default codec and no compound file. The directory gets 21 segment files with 21 different extensions.
  2. You look each extension up in the File Formats overview's "Summary of File Extensions" table, which "summarizes the names and extensions of the files". It lists 25 extensions, including the metadata files .nvm, .dvm, .kdm and .vem, so you expect all 21 there.
  3. 7 are missing: .fdm, .tvm, .tmd and .psm (stored-fields, term-vectors, terms and postings metadata), .dvs and .dvp (doc-values skip index and presence data) and .vemf (vector metadata).
  4. The vector row says .vec, .vem, .veq, vex; the default vector format wrote .vec, .vem, .vemf and .vex. .veq comes only from the optional quantized formats, and vex lacks its dot. The postings format's own file list also omits .tmd and .psm.
  5. Why: since 8.5.0 (2020), six format changes each added a file and documented it at most on its own format page, never in this table.

Who is affected

#

People and tools that learn a segment's files from the overview: someone sizing an index by file type, a backup or copy tool that picks files by extension, a format port. Default codec, ordinary documents; the files show for non-compound segments (by default, merged segments above 64 MB). Lucene and its searches are unaffected.

Mechanism, terms and numbers582 words

The default codec's package documentation (codecs/lucene104/package-info.java, the File Formats overview) says it "defines the index file formats used in this version of Lucene" (:50), and its "Summary of File Extensions" table "summarizes the names and extensions of the files in Lucene" (:211, table :213-319). The table lists the metadata files of norms, doc values, points and vectors (.nvm, .dvm, .kdm, .vem) but not seven extensions the default codec writes for ordinary documents: .fdm, .tvm, .tmd, .psm, .dvs, .dvp and .vemf.

Its vector row (:312-318) links the default Lucene99HnswVectorsFormat and reads .vec, .vem, .veq, vex: that format writes .vec, .vemf, .vem and .vex, .veq comes only from the optional scalar-quantized formats, and vex has no dot. The default postings format's "Files and detailed format" list (Lucene104PostingsFormat.java:81-89) names .tim, .tip, .doc, .pos and .pay but not the .tmd and .psm files the same format writes.

Lucene writes, reads, merges and checks all these files correctly; nothing reads the table at runtime. The table matched the codec through 8.4.1. None of the six format changes since 8.5.0 (2020) that added the missing files put them in the table: five touched no package-info.java, and #13585 copied the whole table into its new lucene912 package without a .psm row. The vector row's current text was written by #12582 (9.9.0), when the HNSW format could still write .veq; from 9.0.0 through 9.8.0 the row read .vec, .vem and lacked .vex. Documentation only; the fix is javadoc text.

The vector row (package-info.java:312-318)

#

It links Lucene99HnswVectorsFormat, the default (Lucene104Codec.java:123), with the cell .vec, .vem, .veq, vex and the text ".vem the vector metadata, .veq the quantized vector data, and .vex the hnsw graph data". In lucene/core, .veq (with .vemq) is defined only by the optional Lucene104ScalarQuantizedVectorsFormat (:107-108); the read-only backward-codecs Lucene99ScalarQuantizedVectorsFormat (:53-54) defines the same two for old indexes. The default format writes .vec and .vemf through its flat format and .vem and .vex itself (:89-90).

The postings list (Lucene104PostingsFormat.java:81-89)

#

"Files and detailed format:" .tim, .tip, .doc, .pos, .pay. The format also writes .psm and, through its terms dictionary (:410-413), .tmd; .tim and .tip, also terms-dictionary files, are listed.

Exposure and likelihood274 words
  • Who is hit. Anyone who looks an index file up in the File Formats overview, or builds on it: sizing an index by file type, a backup, copy or inspection tool that selects files by extension, a port of the format. Lucene users who only call its APIs are unaffected, and Lucene's own file lists (SegmentInfo.files(), the commit's file names) are correct.
  • Default vs opt-in. The default codec and ordinary documents: .fdm, .tmd and .psm are written for nearly every segment (stored fields and postings), .dvs and .dvp for every segment with doc values, .vemf for every segment with vectors, .tvm with term vectors.
  • When the files are visible. Flushed segments are compound by default (IndexWriterConfig.java:99, DocumentsWriterPerThread.java:643), but a merge writes any segment above 64 MB as separate files (CompoundFormat.java:42, :163-179; the default TieredMergePolicy measures bytes, MergePolicy.java:598-600). So any default index with a merged segment above 64 MB shows them in its directory.
  • Scale. None needed: one document shows 7 of 21 extensions unlisted.
  • What it does not do. No wrong results, no index change, no runtime path. Every missing file except .psm is documented on its own format page, though not every such page is reachable from the table: .tmd's page (Lucene103BlockTreeTermsWriter) is one link away from the table's postings link, and .vemf's page (Lucene99FlatVectorsFormat) cannot be reached from the vector row's link, whose page links only the abstract FlatVectorsFormat (Lucene99HnswVectorsFormat.java:41). The searches found no report of it although it dates from 8.5.0 (2020), which suggests the audience is small. Impact class minor, priority low.

Why it looks unintended

#
  • The page "defines the index file formats used in this version"; its table lists norms, doc-values, points and vector metadata files, not these.
  • The vector row is wrong, not short: it credits .veq to a format that never writes it, omits .vemf and writes vex undotted.
  • Upstream fixed the same staleness in this table before (#13801, points row).
The full argument246 words
  • Contract text. package-info.java:50: "This document defines the index file formats used in this version of Lucene"; :211: "The following table summarizes the names and extensions of the files in Lucene". The table was added (LUCENE-1841, #2916, 2009) so readers can look files up by extension.
  • No rule explains the omissions. The table lists the metadata files of norms, doc values, points and vectors (.nvm, .dvm, .kdm, .vem), but not those of stored fields, term vectors, terms, postings and flat vectors.
  • History shows omissions, not decisions. None of the six changes that added the missing files put them in the table: five touched no package-info.java, and #13585, which copied the whole table into its new lucene912 package, gave .psm no row and documented it only in the constant's javadoc. The PR discussions the follow-up read do not mention the table. A history search (git log -G over every package-info.java) found no version of the table that ever had a cell with any of the seven extensions. vex was dotted in 10.2.x and came back undotted from an older copy in 10.3.0.
  • Precedent. #13801 (romseygeek, merged 2024-09-18, "Correct Point file extensions in Codec javadocs") replaced the stale points cell .dii, .dim with .kdd, .kdi, .kdm. Other file-format doc fixes: LUCENE-7532 (#8583), #15625.
  • Tests. No test or build check was found that compares the overview with the files written (searched lucene/*/src/test, build-tools and gradle at 645d4fe14a20).
The devil's-advocate check179 words

Strongest case for "intended" (the refute reviewer, the intended-lens cross-model reviewer and the devil's-advocate verifier; all rated it moderate): the page "attempts to provide a high-level definition" (:54), the table only "summarizes", the details are "provided in their linked pages" (:188), and those pages document the missing files (all but .psm); .veq is a real extension of this version (the optional scalar-quantized formats); and the codec is @lucene.experimental (Lucene104Codec.java:53).

Why it fails: a summary may be short, but not wrong: the vector row states something false about the format it links, vex is a typo, and listing some formats' metadata files but not others is inconsistency, not brevity. @lucene.experimental allows the format to change, not the current one to be described wrongly. The linked pages do not close the gap either: .vemf's page cannot be reached from the vector row's link, .tmd's is one link further on, and .psm has no page. Upstream treated exactly this as a defect in #13801. Every verifier and the adjudication rejected the "intended" reading.

Suggested fix

#

Recommended A. Update the table and the postings list to the files the default codec writes

Add rows for .fdm, .tvm, .tmd and .psm; add .dvs, .dvp to the doc-values row; make the vector row .vec, .vemf, .vem, .vex, noting that optional quantized formats add .veq and .vemq; list .tmd and .psm in the postings format's files. Javadoc only. Validated: a check that parses the fixed text finds no gap; tests and static checks pass.

Downstream note

#

Downstream relevance only for tools that select or copy index files by the table's extensions instead of Lucene's own file lists; Lucene, and products that read indexes through Lucene, are unaffected.

How it was found

#

Semi-formal: a differential check extracted the table's extension cells and the postings "Files" list from the javadoc source and compared them both ways with the files of 91 generated default-codec indexes. Seven written extensions were never listed and the listed .veq was never written by the default format; on the fixed text a 41-configuration sweep finds nothing.

The method in full206 words
  • Hunt unit, 2026-10-28: the table's extension cells and Lucene104PostingsFormat's "Files and detailed format" list were extracted mechanically from the javadoc source. The extensions written were collected from the real files (top level and inside compound files) of 91 generated indexes: 11 fixed configurations (two of them with a scalar-quantized vectors format) and 80 seeded random feature mixes (stored fields, term vectors, postings with positions, offsets and payloads, norms, all five doc-values types dense and sparse with and without a skip index, points, float, byte and float16 vectors, deletions, soft deletes, doc-values updates, compound files, a file-system directory). The two sets were compared both ways, with assertions on and off.
  • Result: written but not in the table [.dvp, .dvs, .fdm, .psm, .tmd, .tvm, .vemf]; in the table but never written by the default format [.veq]; postings list misses [.psm, .tmd]. On the fixed text the same extraction, run as a separate 41-configuration sweep (the 11 fixed and 30 seeded random), finds nothing missing, extra or undotted (positive control; a sweep, not a proof).
  • Starting lead: a follow-up of an earlier unit that collected the set of extensions the default codec writes. This is a differential check, not model checking or a proof.

LFV-972, snapshot of 2026-11-09

Registry title
The default codec's 'Summary of File Extensions' table (codecs/lucene104 package documentation) is stale: it omits .fdm, .tvm, .tmd, .psm, .dvs, .dvp and .vemf, which the default codec writes, credits .veq to the default HNSW vectors format (which does not write it) and gives 'vex' without its dot; Lucene104PostingsFormat's 'Files and detailed format' list also omits .tmd and .psm (documentation defect; the code is correct)
Area
codecs / default codec file-format overview (codecs/lucene104 package-info 'Summary of File Extensions' table and the Lucene104PostingsFormat 'Files and detailed format' list vs the files the default codec writes)
Priority
Low, rank 1325: The stale extension table in the default codec overview leaves out common files, but the per-format javadocs list nearly all of them and it is a missing-name list, not a wrong byte grammar.
Impact class
minor
Impact note
Documentation only: Lucene's writers and readers are unaffected in every configuration; the people misled are readers of the published File Formats overview and of the Lucene104PostingsFormat file list (people who inspect, size or copy index directories by extension, or write format tools from the overview), who find .fdm, .tmd and .psm (written for almost every default-codec index) and .tvm, .dvs, .dvp and .vemf unlisted and a .veq that the default vectors format never writes; the linked per-format javadocs already document every missing file except .psm; the drift began in 8.5.0 (2020) and needs no scale or special setting.
Summary
You index ordinary documents with the default codec and look up the files in the index directory in the 'Summary of File Extensions' table of the codec's package documentation, which says it 'summarizes the names and extensions of the files' of this format version. Seven extensions the default codec writes are missing (.fdm, .tvm, .tmd, .psm, .dvs, .dvp, .vemf); the vector row lists '.vec, .vem, .veq, vex', but the default Lucene99HnswVectorsFormat it links writes .vec, .vemf, .vem and .vex (.veq comes only from the optional scalar-quantized formats) and 'vex' lacks its dot; and Lucene104PostingsFormat's own 'Files and detailed format' list leaves out .tmd and .psm. Lucene itself reads and writes all these files correctly; each format change since 8.5.0 that added a file updated at most its own class javadoc, never this overview.
