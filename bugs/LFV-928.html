Hunspell Dictionary cannot load SET ISO8859-10, and loads ISO8859-14 only when spelled exactly so

An affix file that says SET ISO8859-10, an encoding the Hunspell manual lists, makes Lucene's Dictionary constructor throw UnsupportedCharsetException, so the dictionary never loads; ISO8859-14 loads only in that exact spelling. Every release since 3.5.0 (2011) has it.

The finding in 30 seconds

#

Lucene picks the decoder in getDecoder: its own ISO-8859-14 table for the exact string ISO8859-14, two exact aliases, then Charset.forName. The JDK has no ISO-8859-10 or ISO-8859-14 charset, so every other spelling of those two throws. C Hunspell lower-cases the name, keeps letters and digits, and has both tables.

Background: how a Hunspell dictionary names its encoding

#
  1. A Hunspell dictionary is two files: an affix file (.aff) with the rules and a word list (.dic). Many older dictionaries store words in an 8-bit encoding, one byte per letter.
  2. The affix file's SET line names that encoding, for example SET ISO8859-2. The same byte means different letters in different encodings: 0xBF is ŋ in ISO-8859-10 but ¿ in Latin-1.
  3. Lucene reads the SET line first and turns the name into a Java decoder for both files. Without a decoder the dictionary cannot be read at all.

The finding, step by step

#
  1. Write a two-line Hunspell dictionary: the affix file says SET ISO8859-10 (Latin-6, Nordic) and the word list holds one word, the bytes x, 0xBF, y. In ISO-8859-10, byte 0xBF is the letter ŋ.
  2. Load it with new Dictionary(dir, "d", aff, dic). You expect it to load and spell("xŋy") to be true: the Hunspell manual lists ISO8859-1 to ISO8859-10, and C Hunspell reads such a file.
  3. Instead the constructor throws UnsupportedCharsetException: ISO8859-10. Lucene uses its own table only for the exact name ISO8859-14 and hands every other name to the JDK, which has no ISO-8859-10 or ISO-8859-14 charset at all.
  4. So ISO-8859-14 and iso8859-14 fail too. Of 32 spellings each, ISO8859-10 loads in 0 and ISO8859-14 in 1, while ISO8859-2 and the other listed parts load in 8 to 10.
  5. It fails loudly at load time, so nothing is misread. Matching the name as C Hunspell does (lower case, letters and digits only) plus a 96-entry ISO-8859-10 table makes all 64 spellings load and decode correctly.

Who is affected

#

Users of the opt-in Hunspell module whose affix file says SET ISO8859-10, or writes ISO-8859-14 other than exactly ISO8859-14. The dictionary never loads, so the stem filter and spell-checker never get one; nothing is misread or stored. No surveyed public dictionary uses these values. Workaround: convert the dictionary to UTF-8.

Mechanism, terms and numbers518 words

A Hunspell affix file names its character encoding on a SET line; the Hunspell manual lists "UTF-8, ISO8859-1 - ISO8859-10, ISO8859-13 - ISO8859-15, KOI8-R, KOI8-U, cp1251, ISCII-DEVANAGARI". Lucene turns the value into a decoder in Dictionary.getDecoder (Dictionary.java:899-908 on main 645d4fe14a20): its own ISO8859_14Decoder for the exact string ISO8859-14, two exact aliases, otherwise Charset.forName(value). The JDK has no ISO-8859-10 or ISO-8859-14 charset under any of its 963 names and aliases, so SET ISO8859-10 (every spelling tested), SET ISO-8859-14 and SET iso8859-14 make the public constructor throw java.nio.charset.UnsupportedCharsetException, and the dictionary does not load. C Hunspell lower-cases the value, keeps only letters and digits, and has tables for both. The failure is loud and at load time; only the opt-in Hunspell module is involved, and no surveyed public dictionary uses these values. Every release with Hunspell, 3.5.0 to 10.6.0, and main is affected; since 4.8.0 the exact ISO8859-14 loads.

The code (main 645d4fe14a20, lucene/analysis/common/.../hunspell/Dictionary.java)

#
  1. The public constructors (:189, :206, :226) end in the last one, which reads the affix prologue and calls readConfig(...) (:260).
  2. readConfig (:837) passes the SET argument on: decoder = getDecoder(singleArgument(reader, line)); (:849). The second pass repeats the lookup in its consistency check (:465-470).
  3. CHARSET_ALIASES (:889-890) has two exact keys: microsoft-cp1251 -> windows-1251 and TIS620-2533 -> TIS-620.
  4. getDecoder (:899-908): if ("ISO8859-14".equals(encoding)) return new ISO8859_14Decoder(); (exact, case-sensitive), then the alias map, then replacingDecoder(Charset.forName(encoding)) (:907). Its javadoc (:893-894): "Note, This isn't perfect as I think ISCII-DEVANAGARI and MICROSOFT-CP1251 etc are allowed...".
  5. ISO8859_14Decoder.java:25: "many hunspell dictionaries use this encoding, yet java does not have it?!?!". There is no ISO-8859-10 counterpart.
  6. Charset.forName resolves ISO-8859-2, ISO8859-2 and iso8859-2 through JDK aliases. JDK 25.0.3 has 173 charsets with 963 names and aliases, and none normalises to iso885910 or iso885914; Charset.isSupported is false for ISO8859-10, ISO-8859-10, ISO8859-14 and ISO-8859-14.

Exposure and likelihood201 words
  • Who is hit. Applications whose affix file says SET ISO8859-10 (Latin-6, Nordic) in any tested spelling, or writes ISO-8859-14 (Latin-8, Celtic) as anything but exactly ISO8859-14. The exception comes where the affix file is read: new Dictionary(...) or HunspellStemFilterFactory.inform. HunspellStemFilter and the Hunspell spell-checker take a built Dictionary, so they simply never get one. No default analyzer uses Hunspell.
  • What happens. The constructor throws java.nio.charset.UnsupportedCharsetException naming the SET value. No wrong results, no index damage, nothing persisted, no scale needed. The constructor javadoc names only IOException and ParseException; through HunspellStemFilterFactory the exception arrives unwrapped. The hunt's impact class "crash" means exactly this, an unchecked exception on input the API accepts, here at load time; the JVM keeps running.
  • How likely. Rare. The finder's survey of the two dictionary collections the package javadoc recommends found 0 of 191 dictionaries using these values (recorded only as the finder's summary; not re-checked). Hunspell's own test data writes a hyphenated SET ISO-8859-15 (1.7.2 tests/encoding.aff), which loads in Lucene only because the JDK has that name (the canonical name of its ISO-8859-15 charset).
  • Workaround. Convert the dictionary to UTF-8 and write SET UTF-8, or, for ISO-8859-14, write exactly ISO8859-14.

Why it looks unintended

#
  • The Hunspell manual lists ISO8859-10 as a SET value and C Hunspell has its table; nothing in Lucene limits SET names.
  • Lucene ships its own ISO-8859-14 table but reaches it through one spelling, while other ISO-8859 parts also load as ISO-8859-n and iso8859-n.
  • Precedent: the same exception for SET TIS620-2533 (SOLR-2934) was fixed in 2014 with a table entry.
The full argument166 words
  • Contract. The constructors read "hunspell affix and dictionary files" and document only IOException and ParseException (Dictionary.java:178-188, :195-205, :216-225). The package is "A Java implementation of Hunspell stemming and spell-checking algorithms" (package-info.java:19-20, link markup dropped). No javadoc, test or CHANGES entry limits SET to JDK charset names.
  • The manual. hunspell(5) lists ISO8859-10 among the possible SET values (1.3.4 and 1.7.2), and C Hunspell resolves it to its own table after normalising the name.
  • Lucene adds missing tables on purpose. ISO8859_14Decoder exists because "many hunspell dictionaries use this encoding, yet java does not have it", but only one exact spelling reaches it.
  • Precedent. SOLR-2934 (a 2012 comment) reported the same UnsupportedCharsetException for SET TIS620-2533 through the same lookup; LUCENE-5468 (#6531, 2014) fixed that value with the CHARSET_ALIASES entry.
  • Tests. No upstream test exercises ISO8859_14Decoder or asserts that a SET name is rejected; the one test aimed at parsing the SET value (TestDictionary.testSetWithCrazyWhitespaceAndBOMs) checks whitespace and BOM handling for UTF-8.
The devil's-advocate check246 words

The strongest case for "works as designed" (rated moderate for ISO8859-10, moderate to strong for the ISO8859-14 spellings): the getDecoder javadoc has admitted since 2011 that SET support "isn't perfect"; the supported set is JDK charsets plus a small table built from real dictionaries (LUCENE-5468's CHANGES entry: the filter "loads all known openoffice dictionaries without error"); the manual writes part 14 only as ISO8859-n, which works; LUCENE-9687 scopes C parity to some languages; failing loudly is safer than C's silent ISO-8859-1 fallback; and in SOLR-2934 the maintainer (Robert Muir) replied the same day that there was "no point in worrying about adding aliases/matching up charset naming for Thai", because the filter would be a no-op with that word-list-only dictionary (the alias came two years later).

Why it fails: the javadoc is hedged ("I think ... etc") and names ISCII-DEVANAGARI and MICROSOFT-CP1251, not these values; ISO8859-10 is a documented value that the public constructor accepts; nothing limits SET names; and the one-spelling special case was already narrower than C Hunspell's normalisation when it was written. Concede that the compatibility contract is implied (by the manual and by constructors that read "hunspell affix and dictionary files"), not written down. Honest caveat: C Hunspell's own ISO-8859-10 table has no case data for the high bytes (for 0xBF it stores {0x00, 0xbf, 0xbf}), so C loads such a dictionary but does not case-map its non-ASCII letters. Verdict: a long-standing compatibility gap with a small fix, not a regression.

Suggested fix

#

Recommended Normalise the special-case names like C Hunspell and add an ISO8859_10Decoder

Match the SET name as C Hunspell does (lower case, letters and digits only): iso885914 gets the existing ISO-8859-14 decoder, iso885910 a new 96-entry ISO-8859-10 one, and the two alias keys match the same way (then 12 failing spellings of those two load); other names reach Charset.forName unchanged. Validated: the repro and the hunspell test package (159 tests) pass.

// C Hunspell matches SET values lower-cased and without non-alphanumerics
// (csutil.cxx get_current_cs)
String normalized = encoding.toLowerCase(Locale.ROOT).replaceAll("[^a-z0-9]", "");
if ("iso885914".equals(normalized)) {
  return new ISO8859_14Decoder();
}
if ("iso885910".equals(normalized)) {
  return new ISO8859_10Decoder();
}
All options and trade-offs3 options · 559 words

Three options. The first was validated with gradle in a fresh scratch worktree at 645d4fe14a20; the other two were not executed. C Hunspell's behaviour for unknown names (fall back to ISO-8859-1) is not an option: it would load the file but misread the 46 of the 96 bytes from 0xA0 up where ISO-8859-10 and Latin-1 differ (0xBF would read as ¿, not ŋ).

Normalise the special-case names like C Hunspell and add an ISO8859_10Decoder (validated by the checks) (recommended)

#

In Dictionary.getDecoder, compute encoding.toLowerCase(Locale.ROOT).replaceAll("[^a-z0-9]", ""); map iso885914 to ISO8859_14Decoder and iso885910 to a new ISO8859_10Decoder (bytes 0xA0-0xFF from the unicode.org 8859-10 mapping, built like ISO8859_14Decoder). The sketch also maps normalised microsoftcp1251 and tis6202533 onto the two existing alias keys, so 12 spellings of those two that fail today (7 for windows-1251, 5 for TIS-620) load too; drop those lines for the narrowest change. Everything else keeps going to the alias map and Charset.forName unchanged. Dictionary.java +13/-1, new ISO8859_10Decoder.java (59 lines).

// C Hunspell matches SET values lower-cased and without non-alphanumerics
// (csutil.cxx get_current_cs)
String normalized = encoding.toLowerCase(Locale.ROOT).replaceAll("[^a-z0-9]", "");
if ("iso885914".equals(normalized)) {
  return new ISO8859_14Decoder();
}
if ("iso885910".equals(normalized)) {
  return new ISO8859_10Decoder();
}

Trade-offs

  • One more hand-written table to maintain; its 96 entries match an independent ISO-8859-10 codec (96 of 96).
  • Like ISO8859_14Decoder, the new decoder reports ISO-8859-1 as its charset(), so it inherits LFV-932 (FLAG UTF-8 with an 8-bit SET merges flags); that bug has its own fix site.
  • Over 1,457 names (all JDK names and aliases plus generated spellings), every name that loads today still loads with the same charset and decoder class, and 75 names that fail today load.
  • Open PR #16422 moves the SET call sites into a switch but leaves getDecoder alone; the two should not conflict. The 2011 "isn't perfect" javadoc could be updated in the same change.

Narrow variant: an exact ISO8859-10 case and a case-insensitive ISO8859-14 test

#

Add if ("ISO8859-10".equals(encoding)) return new ISO8859_10Decoder(); and compare ISO8859-14 case-insensitively. Not executed.

Trade-offs

Fixes the lead case with fewer lines, but ISO-8859-14 and ISO-8859-10 still fail, and the special cases stay inconsistent with the JDK-alias behaviour of the other ISO-8859 parts.

Clearer error only

#

Catch the charset exception in getDecoder and throw a ParseException that names the SET value. Not executed.

Trade-offs

Gives the documented exception type and a clearer message, but the dictionary still does not load: a complement to the first option, not a fix.

Downstream note

#

Services that accept user-supplied Hunspell dictionaries get a raw UnsupportedCharsetException from HunspellStemFilterFactory at analyzer setup, not its "Unable to load hunspell data!" IOException, so a handler that catches only IOException misses it.

How it was found

#

A probe loaded a dictionary through the stock jar for every SET value the Hunspell manual lists, plus spelling variants, and flagged ISO8859-10 and two ISO8859-14 spellings as rejected. A model of C Hunspell's name lookup against Lucene's then mapped the gap over 536 spellings, with 0 disagreements against the real jar.

The method in full178 words

Method: a differential model checked on the real jar (the hunt's "semi-formal" tier; the first signal was the probe, the model came after it).

  • First signal. A planning probe loaded a one-word-per-letter-byte dictionary through the stock main jar for every SET value hunspell(5) lists plus 8 spelling variants, and checked every letter byte against the standard mapping tables. It reported ISO8859-10, ISO-8859-10, ISO-8859-14 and iso8859-14 as rejected (and the javadoc-acknowledged ISCII-DEVANAGARI and MICROSOFT-CP1251, which this bug leaves out); every other listed value loaded with 0 misdecoded letters.
  • Model. The finder wrote a model of SET-name acceptance: C Hunspell 1.7.2's name normalisation and encoding table against Lucene's getDecoder, over the JDK 25 charset registry's 927 case-insensitively distinct names and aliases (963 counted raw). ISO-8859-10 and ISO-8859-14 have no JDK spelling at all.
  • Check on the jar. 536 spellings through the public constructor: 113 load, 0 disagreements with the model, 10,374 decode checks with 0 mismatches against the unicode.org tables. The finder reduced it to a public-API JUnit; the hunt later minimised that to the one-test repro.

LFV-928, snapshot of 2026-11-09

Registry title
Hunspell Dictionary cannot load SET ISO8859-10, or ISO8859-14 spelled any way except exactly "ISO8859-14" (UnsupportedCharsetException at load)
Area
analysis / hunspell (Dictionary SET encoding lookup)
Priority
Low, rank 628: A loud load-time UnsupportedCharsetException in the opt-in Hunspell module for SET ISO8859-10 or non-exact ISO8859-14 spellings, which no surveyed public dictionary uses and which corrupts nothing.
Impact class
crash
Impact note
Only applications that use the opt-in Hunspell module (a Dictionary built directly, through HunspellStemFilterFactory, or for the Hunspell spell-checker) with an affix file that says SET ISO8859-10 (any spelling) or ISO8859-14 in any spelling except the exact "ISO8859-14" are hit: the Dictionary constructor throws UnsupportedCharsetException and the dictionary does not load, loudly and at load time, with no wrong results, nothing persisted and no scale needed; the finder's survey found no public dictionary that uses these values (0 of 191, not re-checked), and every release from 3.5.0 to 10.6.0 has it (in 3.5.0-4.7.2 even the exact "ISO8859-14" fails).
Summary
You load a Hunspell dictionary whose affix file says SET ISO8859-10 (Latin-6, Nordic), a value the hunspell(5) man page lists among the possible SET values, or says ISO8859-14 (Latin-8, Celtic) spelled ISO-8859-14 or iso8859-14, and expect it to load: C Hunspell lower-cases the SET value and drops non-alphanumerics before its table lookup, and in Lucene every other listed ISO-8859 part loads in its hyphenated and lower-case spellings (ISO-8859-2, iso8859-2, ...). Instead the Dictionary constructor throws java.nio.charset.UnsupportedCharsetException, because Dictionary.getDecoder uses Lucene's own ISO8859_14Decoder only for the exact string "ISO8859-14" and otherwise calls Charset.forName, and the JDK has no ISO-8859-10 or ISO-8859-14 charset under any name. Spellings that do load decode every letter byte correctly, so nothing is silently wrong; the dictionary is refused.
