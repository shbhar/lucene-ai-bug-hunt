XY distance sort as a later sort key drops closer tied hits, because its comparator keeps a too-small bounding box when the queue bottom gets farther away

Sort by a category, then by XYDocValuesField.newDistanceSort, and the top hit can be a tied document with no location instead of one at distance 3. The distance comparator keeps a pre-filter box built for an earlier, closer bottom; every release that was run, from 8.5.0 on, has it.

The finding in 30 seconds

#

When the queue's weakest hit changes, the XY distance comparator rebuilds its pre-filter box only if the new bottom is below Float.MAX_VALUE and sampling does not skip the call (after 1024 calls it skips 63 of 64). As a later sort key the bottom can grow; the old box is then too small and drops closer tied hits.

Background: how a sorted top-n search skips documents

#
  1. A search for the top n hits by a Sort keeps a queue of the best n so far. The worst of them is the bottom. Each new hit is compared with the bottom (compareBottom); if it does not sort before it, it is dropped.
  2. With several SortFields the first one decides. A later SortField is asked only when all earlier ones tie, so it only breaks ties. Its bottom is the bottom of the whole sort, which need not be its own worst value.
  3. The XY distance comparator speeds up compareBottom with a box: a point outside the square of half-width d around the origin is farther than d, so when d is the bottom's distance the point can be rejected without computing its distance. setBottom rebuilds the box when the bottom changes.

The finding, step by step

#
  1. Index 3 documents: doc 0 (category b, point (1, 0)), doc 1 (category a, no point) and doc 2 (category a, point (3, 0)). Sort by category, then by XY distance from (0, 0), and ask for the top 1.
  2. You expect doc 2: docs 1 and 2 tie on category a, and distance 3 beats doc 1's missing location, which counts as +Infinity and sorts last.
  3. Doc 0 fills the queue, so the distance comparator builds a box of half-width 1 around (0, 0). Doc 1 replaces doc 0 on category; its distance +Infinity is not below Float.MAX_VALUE, so setBottom keeps the old box.
  4. Doc 2 ties on category. Its x = 3 lies outside the old box, so compareBottom answers "not competitive" without computing the distance. You get doc 1, with no error.
  5. The same stale box appears after 1024 bottom updates, when only every 64th update rebuilds it: 1,100 leading documents, then a tie at distance 100 and at 50, and 100 wins.

Who is affected

#

Applications that sort by another key first and then by XYDocValuesField.newDistanceSort, ask for fewer hits than match, and have documents without a location (or more than 1024 bottom updates). Default config, any index size. Only ties on the earlier keys are broken wrongly; a nearest-first sort is not affected by this bug. Rare: the XY distance sort is little used.

Mechanism, terms and numbers909 words

XYDocValuesField.newDistanceSort sorts by ascending distance, and a document without the field counts as +Infinity and sorts last. To skip far documents cheaply, XYPointDistanceComparator keeps a box around the origin sized to the distance of the queue's weakest hit (the bottom) and rejects any point outside it without computing its distance. setBottom records every new bottom but rebuilds the box only when the bottom is below Float.MAX_VALUE, and, after 1024 calls, only on every 64th call. That is safe while the bottom only gets closer, which holds when the distance is the first SortField. As a later SortField it only breaks ties, the bottom slot changes whenever an earlier key improves, and its distance can grow: the old box is then too small, and a tied document closer than the bottom but outside the old box is silently dropped. With Sort(cat, distance), three documents and top 1, you get the document without a location instead of the one at distance 3. Wrong in every release that was run (8.5.0 to 10.6.0) and on main; a 13-line change in the comparator (+13/-2) fixes it.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/...)

#
  1. The contract. newDistanceSort "orders documents by ascending distance from the location", and a document missing the field "is treated as having Double#POSITIVE_INFINITY distance (missing values sort last)" (document/XYDocValuesField.java:136, :139-140). Sort: if the first SortField "produces a tie, then the second SortField is used to break the tie" (search/Sort.java:58-61). LeafFieldComparator: the bottom slot "may not hold the weakest value according to your comparator, in cases where your comparator is not the primary one (ie, is only used to break ties from the comparators before it)" (search/LeafFieldComparator.java:28-31), and compareBottom "should return the same result as FieldComparator#compare(int,int) as if bottom were slot1 and the new document were slot 2" (:55-57).
  2. The box. On setBottom the comparator recomputes "a bounding box representing competitive distance to the top-N" so that compareBottom can "quickly reject hits based on bounding box alone" (document/XYPointDistanceComparator.java:35-37). It starts as the full encoded range (:55-58); setBottomCounter counts calls ("adversary protection", :60-61).
  3. setBottom (:82-99), the fix site. bottom = values[slot] on every call (:83), but the box is rebuilt only if (bottom < Float.MAX_VALUE && (setBottomCounter < 1024 || (setBottomCounter & 0x3F) == 0x3F)) (:87-88), from XYRectangle.fromPointDistance (:90), which throws for a non-finite radius (geo/XYRectangle.java:76-78) and pads the radius by one float ulp (:81). Otherwise the box of an earlier bottom stays.
  4. compareBottom (:122-161). A point outside the box is skipped (:139-146); only a point inside gets its distance compared (:149-154). It starts at cmp = -1 (:134) and returns -1, "not competitive", when no point is inside (:160).
  5. The callers. MultiLeafFieldComparator.setBottom gives the slot to every comparator (search/MultiLeafFieldComparator.java:45-49), and its compareBottom asks a later comparator only on a tie of the earlier ones (:52-63). TopFieldCollector drops a hit when compareBottom <= 0 (search/TopFieldCollector.java:79-80) and calls setBottom when the queue first fills (:107-109) and after each competitive hit (:94-98).

The worked example (the repro)

#
  • Doc 0 (b, (1, 0)) fills the 1-slot queue: bottom = 1 on call 0, so the box is rebuilt with radius Math.nextUp(1f) = 1.0000001: x and y in [-1.0000001, 1.0000001].
  • Doc 1 (a, no location): "a" beats "b", so the category comparator decides and doc 1 replaces doc 0. Its distance is +Infinity (sortKey, :190-208). setBottom: bottom = +Infinity; +Infinity < Float.MAX_VALUE is false, so the radius-1 box stays.
  • Doc 2 (a, (3, 0)): category ties, so the distance comparator decides. x = 3 is outside the box, no point is inside, and compareBottom returns -1, although compare(+Infinity, 3) is positive. The collector drops doc 2. Top-1 = doc 1; with n = 3 the same search returns [2, 1, 0].

The second trigger: sampling

#

From call 1024 on, only calls with (counter & 63) == 63 rebuild the box (1087, 1151, ...). The finder's case: 1,100 documents at (1, 0), each with a smaller category than the one before (so each becomes the new bottom), then A (category "0", (100, 0)) and B (category "0", (50, 0)). The last rebuild is at call 1087 with bottom 1. A's call is number 1100 (1100 & 63 = 12): the bottom becomes 100 but the box keeps radius 1, so B at x = 50 is dropped and top-1 is A. With 1,000 leading documents (A's call below 1024) or 1,087 (A's call is a 64th call) B is found.

A third, extreme path

#

The guard bottom < Float.MAX_VALUE also skips the rebuild for a finite bottom of at least Float.MAX_VALUE, which needs extreme coordinates. The fact check ran the repro's 3 documents with doc 1 at (-Float.MAX_VALUE, 0) instead of without a location: the same wrong top-1 on main, the right one with fix A.

Why a nearest-first sort is safe from this bug

#

With the distance as the first SortField, the bottom is the farthest hit in the queue and only gets closer. A box built for an earlier, larger bottom is then too large, which costs speed but no hits. The guard and the 1024/64 rule are correct under that assumption, and only under it.

Exposure and likelihood331 words
  • Who is hit. Applications that use XYDocValuesField.newDistanceSort (cartesian x/y points, lucene-core, public and not @lucene.experimental) as a later SortField, for example category first and distance second, or after any key that has ties, and ask for fewer hits than match. Default IndexWriterConfig, codec and IndexSearcher, any index size.
  • When. (1) Some documents have no XY location (documented as +Infinity, sorting last): whenever one of them becomes the bottom after a finite bottom, the box stays stale until a finite bottom arrives on a rebuilding call. (2) More than 1024 setBottom calls in one search's comparator, and the bottom grows on a call that does not rebuild. (3) Rarely in practice: points so far from the origin that the bottom's distance reaches Float.MAX_VALUE.
  • Size of the error. Only the tie-breaking among documents that tie with the bottom on all earlier keys is wrong: a dropped document is closer than the bottom it should have replaced. Documents that win on an earlier key are unaffected, and which documents match is unchanged. In the finder's 6-document case with n = 2 the result is [4, 2] instead of [5, 4].
  • Silent. No exception and no assertion, with assertions on and off.
  • Not affected by this bug. The distance as the first or only SortField (the case upstream tests cover), and n at least the number of hits (the queue is full only after the last hit, if at all, so compareBottom is never called). This is no claim about other box issues, for example the separate, already known rounding of XYRectangle.fromPointDistance for large centre coordinates (LFV-767), which was not assessed here. The LatLon distance sort does not have the missing-value trigger but has the sampling trigger (LFV-1136, a separate fix site).
  • Likelihood: rare. The XY distance sort is little used (the hunt's GitHub code search found no production caller in Elasticsearch, OpenSearch or Solr), distance sorts are usually nearest-first, and no report was found since 8.5.0 (2020).

Why it looks unintended

#
  • LeafFieldComparator names this case (a comparator that only breaks ties) and requires compareBottom to equal compare(bottom, doc); here it says -1 for 3 against +Infinity.
  • The Float.MAX_VALUE guard apparently only keeps an infinite radius from the box helper; before it, an infinite bottom built the full box.
  • The LatLon twin gets the same 3 documents right.
The full argument330 words
  • Contract. newDistanceSort promises ascending distance with missing values last (XYDocValuesField.java:136-140); neither its javadoc (:133-151) nor the class javadoc limits it to the first SortField, and Sort defines later SortFields as tie-breakers (Sort.java:58-61). LeafFieldComparator names the non-primary comparator (LeafFieldComparator.java:28-31) and requires compareBottom to agree with compare(bottom, doc) (:55-57). The class javadoc says the box represents "competitive distance to the top-N" (XYPointDistanceComparator.java:35-36); a box smaller than the bottom's distance does not.
  • Tests. TestXYPointDistanceSort uses the distance only as the first SortField (TestXYPointDistanceSort.java:69, :108, :239-240), where the bottom never grows, so no test sees it. Upstream does use a distance sort as a later key elsewhere: new Sort(SortField.FIELD_SCORE, LatLonDocValuesField.newDistanceSort("foo", lat, lon)) (TestLatLonPointDistanceFeatureQuery.java:471).
  • History. LUCENE-9243 (c653c04bb17, 2020-03-02, #10283, "Add fudge factor when creating a bounding box of a xycircle") switched to XYRectangle.fromPointDistance, which throws for a non-finite radius, and added bottom < Float.MAX_VALUE && in front of the rebuild. Before it, a +Infinity bottom built the full box (Math.max(-Float.MAX_VALUE, x - bottom) and so on). The issue and its PR discuss only the fudge factor. An executed counterfactual: 8.5.0 with the comparator from before the guard returns the right top-1.
  • The LatLon precedent. In LUCENE-7102 (#8157, 2016), Robert Muir wrote that for a +Infinity bottom "we can just bound Integer.MIN_VALUE .. Integer.MAX_VALUE for each dimension", because "+Inf means we've filled the priority queue with only missing values, so any possible value competes"; for -Infinity, "only missing values can possibly compete anymore (and only if you have another comparator)". So the use of a distance sort next to another comparator was considered. LatLonPointDistanceComparator.setBottom has no Float.MAX_VALUE guard (LatLonPointDistanceComparator.java:88-113), and the same 3-document sort with LatLonDocValuesField returns doc 2.
  • The sampling is framed as protection of speed: "don't make gobs of bounding boxes if comparator hits a worst case order (e.g. backwards distance order)" (XYPointDistanceComparator.java:84-86). Nothing documents approximate results.
The devil's-advocate check169 words

The strongest "intended" case (the cross-model reviews, OpenAI GPT-5.6, rated it moderate): the box and its sampling were designed for the shrinking bottom of a nearest-first sort; the comparator is package-private and LeafFieldComparator is @lucene.experimental (LeafFieldComparator.java:41); upstream XY tests use the distance only as the first key.

Why it fails: newDistanceSort is public, not experimental and not limited to the first position, and Sort makes every later SortField a tie-breaker; LeafFieldComparator's own javadoc names the non-primary comparator, and compareBottom's contract is exact; the guard apparently exists to keep a non-finite radius away from the box helper (an inference from the code; its commit and tests do not document a kept box as intended), and before it, as in the LatLon twin, a +Infinity bottom means the full box. The argument explains how the bug arose (an assumption that held for the first key), not why dropped hits would be acceptable. Verdict: not intended, a defect (finder, reproducer, the cross-model reviews, the devil's-advocate verifier, adjudication, audit).

Suggested fix

#

Recommended Rebuild the box whenever the bottom grows; full box for a bottom not below Float.MAX_VALUE (fix A)

In XYPointDistanceComparator.setBottom, remember the bottom the box was built for: reset to the full box when the bottom is not below Float.MAX_VALUE, and always rebuild when the bottom grows; the 1024/64 sampling stays for a shrinking bottom (+13/-2). The repro, the finder's trigger matrix, 699 tests in document.*, TestXY* and TestSort*, and :lucene:core:check -x test pass.

    if ((bottom < Float.MAX_VALUE) == false) {
      // the bottom is not below Float.MAX_VALUE (+Infinity: no location): use the full box
      this.minX = Integer.MIN_VALUE;
      this.maxX = Integer.MAX_VALUE;
      this.minY = Integer.MIN_VALUE;
      this.maxY = Integer.MAX_VALUE;
      boxBottom = Double.POSITIVE_INFINITY;
    } else if (bottom > boxBottom || setBottomCounter < 1024 || (setBottomCounter & 0x3F) == 0x3F) {
      // a box built for a smaller bottom is too small, so always rebuild when the bottom grows
      boxBottom = bottom;
      XYRectangle rectangle = XYRectangle.fromPointDistance((float) x, (float) y, (float) bottom);
      // ... unchanged: encode minX, maxX, minY, maxY from the rectangle
    }

Rebuild the box whenever the bottom grows; full box for a bottom not below Float.MAX_VALUE (fix A) (validated by the checks) (recommended)

#

A new field boxBottom remembers the bottom the current box was built for. A bottom that is not below Float.MAX_VALUE (+Infinity, or a finite distance that large) resets the full box, as the code did before LUCENE-9243 for +Infinity and as the LatLon twin does; it also catches NaN and -Infinity, which valid points and a finite origin cannot produce, so that part is only defensive. A bottom larger than boxBottom always rebuilds. A bottom that shrinks keeps the 1024/64 sampling. It is the finder's patch with the else if condition on one line, as google-java-format wants, and one comment reworded after the fact check (it used to say "no finite box covers this bottom", which is wrong for a finite bottom of at least Float.MAX_VALUE).

    if ((bottom < Float.MAX_VALUE) == false) {
      // the bottom is not below Float.MAX_VALUE (+Infinity: no location): use the full box
      this.minX = Integer.MIN_VALUE;
      this.maxX = Integer.MAX_VALUE;
      this.minY = Integer.MIN_VALUE;
      this.maxY = Integer.MAX_VALUE;
      boxBottom = Double.POSITIVE_INFINITY;
    } else if (bottom > boxBottom || setBottomCounter < 1024 || (setBottomCounter & 0x3F) == 0x3F) {
      // a box built for a smaller bottom is too small, so always rebuild when the bottom grows
      boxBottom = bottom;
      XYRectangle rectangle = XYRectangle.fromPointDistance((float) x, (float) y, (float) bottom);
      // ... unchanged: encode minX, maxX, minY, maxY from the rectangle
    }

Trade-offs

  • A nearest-first sort behaves exactly as today: its bottom never grows, so bottom > boxBottom is never true after the first box.
  • A later-key distance sort pays one box rebuild (one XYRectangle and four encodes, the same work as each of the first 1024 calls) each time its bottom grows, so for growth the 1024/64 throttle no longer applies: an order in which the bottom grows on almost every update rebuilds on almost every call. No benchmark was run.
  • One double field per comparator; no index, format or API change.

Downstream note

#

No caller of the XY distance sort was found in Elasticsearch, OpenSearch or Solr, so mainly applications that call Lucene directly are affected.

How it was found

#

A proof-obligation audit of XYPointDistanceComparator's contract: compareBottom must agree with compare(bottom, doc), so the box must cover every point closer than the bottom. The audit found two setBottom paths that keep a smaller box; a public-API JUnit witnessed the first, and a trigger matrix checked against an independent sort model witnessed both.

The method in full194 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read XYPointDistanceComparator against the contracts it implements (newDistanceSort's ordering, LeafFieldComparator.setBottom and compareBottom) and asked what each method must guarantee. For compareBottom to agree with compare(bottom, doc), the box must contain every point closer than the bottom; setBottom keeps that only if it rebuilds whenever the bottom grows. Two paths do not: a bottom that is not below Float.MAX_VALUE, and an unsampled call after 1024. Both matter only when the bottom can grow, which needs the distance as a later SortField.
  • The finder wrote the one-test JUnit (3 documents, top 1) on the public API and ran it on main with assertions on and off, 10.6.0 and 9.12.3; and an 8-test trigger matrix (both triggers and 5 controls), each case checked against an independent sort model and against the same search with n = maxDoc; and a fix sketch that passes all of it and upstream TestXYPointDistanceSort.
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication then reproduced it with their own tests (section "Prior reports, history and checks").

LFV-1132, snapshot of 2026-11-10

Registry title
XY distance sort used as a later Sort key drops closer tied hits, because XYPointDistanceComparator.setBottom keeps an old, too-small bounding box when the bottom grows (a missing-value bottom of +Infinity, or growth after 1024 bottom updates)
Area
core / document: XY distance sort (XYDocValuesField.newDistanceSort, XYPointDistanceComparator)
Priority
Medium, rank 211: The XY distance sort used as a later sort key silently drops closer tied hits from the top-N, with default settings in every release since 8.5.0. This happens every time a document without a location becomes the queue bottom, and can also happen after more than 1024 bottom updates. It sits low in Medium because the cartesian XY sort is little used and only its use as a later sort key is affected, not the usual nearest-first sort.
Impact class
silent wrong results
Impact note
Applications that sort with XYDocValuesField.newDistanceSort as a later SortField (for example Sort(category, distance)) and ask for fewer hits than match get a silently wrong top-N, with the default IndexWriterConfig, codec and searcher, at any index size and with -ea or -da: a document that ties on the earlier keys and is closer than the queue bottom is dropped whenever the bottom's distance has grown since the comparator last built its bounding box, which happens deterministically when a document without a location (distance +Infinity) becomes the bottom after a finite bottom (3 documents and n=1 suffice), and also after 1024 bottom updates when the bottom grows on one of the 63 of 64 updates that skip the rebuild; which documents match is unchanged, only which of them make the returned top n; a nearest-first (primary) distance sort is not affected because its bottom only shrinks; released since 8.5.0.
Summary
You sort three documents, (cat b, distance 1), (cat a, no location) and (cat a, distance 3), with Sort(new SortField("cat", STRING), XYDocValuesField.newDistanceSort("loc", 0, 0)) and ask for the top 1; you expect the (a, 3) document, because ties on cat are broken by ascending distance and a missing location counts as +Infinity and sorts last. Instead you get the (a, no location) document: when it becomes the queue bottom, setBottom skips rebuilding the comparator's bounding box because +Infinity is not below Float.MAX_VALUE, so the box built for the earlier bottom at distance 1 stays, and compareBottom rejects the (a, 3) document as outside it. The same stale box arises after 1024 bottom updates, when only every 64th update rebuilds it and the bottom grows on another one; a nearest-first distance sort is not affected because its bottom only shrinks.
