Grouping by if() or def() puts documents without a value into the 0.0 group, not the null group

Grouping by if() or def() silently counts a document without a value in the real 0.0 group, not the null group: two documents (x = 0, and no x) grouped by if(1, x, x) give 1 group instead of 2. Affected since 4.0.0 (def()) and 5.0.0 (if()).

The finding in 30 seconds

#

Grouping by a function decides each document's group from a reusable value object that the function fills: a number plus a flag saying whether the document has a value at all. Documents whose flag is false form the null group.

  1. You index two documents: one with the numeric doc-values field x = 0, one without x. You group all documents with GroupingSearch by the function if(1, x, x), which is just x.
  2. You expect what grouping by x itself gives: 2 groups, value 0 (1 document) and the null group (1 document). The function agrees that the second document has no value: its exists(doc) is false.
  3. You get 1 group, value 0.0, holding both documents, and no null group. No error, with assertions on or off.
  4. Why: grouping reads each document's value through the function's value filler. if() and def() use the default filler, which copies the number (0 for the missing document) but never the "has a value" flag, so the flag stays at its initial true.
  5. def(x, y) on a document with neither field fails the same way; def(x, 0), the usual default-value idiom, always has a value and is unaffected.

Who is affected

#

Applications that group with GroupingSearch(ValueSource, Map) by if() or def() (or by a vector similarity function or the fromDoubleValuesSource bridge, executed on main) over a field some documents lack. Their 0.0 group's count and members are wrong and the null group is missing or too small. Grouping by a plain field, def(x, constant), matching, hits and scores are unaffected.

Mechanism, terms and numbers462 words

Grouping by a function (GroupingSearch(ValueSource, Map), ValueSourceGroupSelector) is meant to put a document for which the function has no value into the null group, as grouping by the plain field does. IfFunction and DefFunction report "no value" correctly through exists(doc), but they inherit the default FunctionValues.getValueFiller(), which writes floatVal(doc) into a MutableValueFloat and never sets its exists flag. The flag keeps its initial true, so the document is counted in the real 0.0 group, together with documents whose value really is 0. Every typed filler sets the flag; only the default filler, written before exists() existed, does not. A small change in the default filler (+2/-1) fixes it.

Terms

#
  • Grouping by a function: new GroupingSearch(valueSource, context) groups the matching documents by the value of a ValueSource (a function such as if(cond, a, b) or def(a, b, ...)), through ValueSourceGroupSelector.
  • Value filler: FunctionValues.getValueFiller() returns an object that fills a reusable MutableValue for each document. A MutableValue carries the value and a public exists flag; grouping uses the filled value itself as the group key.
  • Null group: the group of documents whose filled value has exists() == false, i.e. no value.

The bug (file:line at 5adff78bb168)

#
  1. ValueSourceGroupSelector.setNextReader takes the function's filler (ValueSourceGroupSelector.java:53-57); advanceTo fills the document and decides the null group only from the filled value: if (value.exists() == false) (:63-68).
  2. The default filler (FunctionValues.java:155-169) does only mval.value = floatVal(doc); (:166). It never writes mval.exists, which starts as true (MutableValue.java:25).
  3. IfFunction.exists follows the chosen branch (IfFunction.java:102-105) and DefFunction.exists is "any source exists" (DefFunction.java:110-119), but both return super.getValueFiller() under TODOs about the value type: "for now, use float" (IfFunction.java:107-112) and "need ValueSource.type() to determine correct type" (DefFunction.java:121-125, likewise MultiFunction.java:141-145).
  4. Every typed filler sets the flag, e.g. mval.value = longVal(doc); mval.exists = exists(doc); (LongDocValues.java:138-142, and the Int, Float, Double, Bool and Str fillers). Only the default filler omits it.
  5. For the document without x, exists(doc) is false and floatVal(doc) is 0, so the filled value reads 0.0 with exists == true, equal to the real x = 0 document's value: one group.

Also affected (executed on main): the float, byte and float16 vector similarity functions and the ValueSource.fromDoubleValuesSource bridge put a document without a value into a 0.0 group (the float and byte functions exist since 9.7.0, the float16 one is not in a release yet, the bridge since 7.0.0). setIgnoreDocsWithoutGroupField(true) does not drop such documents either (FirstPassGroupingCollector.java:220-226 relies on the same check): with it, grouping by x drops the document without x, while if(1, x, x) keeps it in the 0.0 group (executed in this doc's fact check).

Exposure and likelihood119 words
  • Opt-in and rare: function grouping is a rarely used path, and GroupingSearch and getValueFiller are both @lucene.experimental; it needs if() whose chosen branch, or def() whose every source, is a field the document lacks.
  • No scale needed: two documents, assertions on or off; it fails with the test framework's randomized index configuration for every seed tried (11 of 11) and with a plain default IndexWriterConfig (the diagram's probe).
  • Silent: no exception; documents with a real 0 and documents without a value are merged, so counts per group are wrong.
  • Downstream (read in Solr's main branch, not run): Solr's group.func builds Lucene's IfFunction and DefFunction and groups them with Lucene's ValueSourceGroupSelector, a plausible path to the same miscount.

Why it looks unintended

#
  • FunctionValues.exists: "Returns true if there is a value for this document". if() returns false here, as upstream TestValueSources.testIf asserts.
  • Grouping by the plain field puts the same document into the null group.
  • Every typed filler sets mval.exists = exists(doc); only the default filler, older than exists(), does not.
The full argument166 words
  • Contract: FunctionValues.exists: "Returns true if there is a value for this document" (FunctionValues.java:105). IfFunction returns "the value of the trueSource or falseSource function" (IfFunction.java:27-29), so if(1, x, x) should group like x. The grouping javadoc describes documents without a group value being put "in a null group" (FirstPassGroupingCollector.java:87-88). MutableValueFloat: "any instance where exists is set to false must also value set to 0.0F" (MutableValueFloat.java:20-22).
  • Tests: TestValueSources.testIf asserts assertNoneExist for an if() whose chosen branch has no value (TestValueSources.java:315-321). No test groups by if() or def() over a missing field.
  • History: the default filler came with grouping in 2010 (0269c89b07f, SOLR-1682), before exists(). When exists() and the typed fillers' exists line were added (0742b30b724, 2011-04-15), the default filler was not updated. DefFunction and IfFunction (1da4ffee6ee, SOLR-2136, 2011-06-03) inherited it. LUCENE-5961 (#7023, 2014) made IfFunction.exists() follow the chosen branch as a listed bug fix and left the filler alone.
The devil's-advocate check178 words

The strongest case for "intended": the TODOs mark the filler as a known float-only stopgap, and the ValueFiller javadoc only encourages FunctionValues whose value is not a float to define their own filler (FunctionValues.java:137-140); LUCENE-5961's MIGRATE note tells users who want the old behaviour to wrap their sources in def(..., 0.0); GroupingSearch and getValueFiller are @lucene.experimental and MutableValue is @lucene.internal; and an open proposal (#10409, LUCENE-9369) would deprecate grouping by ValueSource.

Why it fails: the TODOs and the javadoc are about the value type, not existence (these functions' values are floats, which is what the default filler is for), and the TODOs were written when IfFunction.exists() was hard-coded true; the MIGRATE note names def(x, 0.0) as the way to opt into missing = 0, which implies missing is otherwise not 0 (and that opt-in still works with the fix); @lucene.experimental allows API change, not wrong results; a deprecation proposal argues priority, not intent. Three independent reviews, two of them by a model from another family (OpenAI GPT-5.6), rated the intended case weak.

Suggested fix

#

Recommended Set the flag in the default FunctionValues filler

Make the default filler copy the flag and zero the value when it is missing, as MutableValueFloat requires: mval.exists = exists(doc); mval.value = mval.exists ? floatVal(doc) : 0f;. Validated: the repro passes, and the grouping module and the queries function tests pass.

@Override
public void fillValue(int doc) throws IOException {
  mval.exists = exists(doc);
  mval.value = mval.exists ? floatVal(doc) : 0f;
}
All options and trade-offs3 options · 367 words

One option was validated with gradle in a scratch worktree; the other two are by reading.

Set the flag in the default FunctionValues filler (validated by the checks) (recommended)

#

In FunctionValues.getValueFiller() (FunctionValues.java:165-167), +2/-1. One place fixes every in-tree inheritor: IfFunction, DefFunction, MultiFunction.Values, the vector similarity functions and the fromDoubleValuesSource bridge (executed on main: they move the document without a value into the null group).

@Override
public void fillValue(int doc) throws IOException {
  mval.exists = exists(doc);
  mval.value = mval.exists ? floatVal(doc) : 0f;
}

Trade-offs

  • The : 0f keeps MutableValueFloat's rule that a missing value is 0.0F (MutableValueFloat.java:20-22), which its equalsSameType, compareSameType and hashCode assert; without it, a function whose floatVal is nonzero for a missing document would form one null group per value (by reading).
  • Cost: one exists(doc) call per filled document, on the grouping path only.
  • def(x, 0) still gives the 0.0 group, so LUCENE-5961's documented opt-in keeps working.
  • Compatibility: FunctionValues is extensible, so a third-party implementation that inherits the default filler would now have its own exists(doc) called on this path, and floatVal(doc) only when that returns true; one whose exists is wrong would change behaviour. Only the in-tree inheritors were run.

What the checks validated

  • Scratch worktree of 5adff78bb168, gradle, OpenJDK 25.0.3: the repro fails stock (assertions on and off, seed DEADBEEF, and 10 of 10 random seeds) and passes with the fix (on and off).
  • With the fix: :lucene:grouping:test (the whole module, with the repro) and :lucene:queries:test --tests 'org.apache.lucene.queries.function.*' pass, seed DEADBEEF.
  • checkGoogleJavaFormat, ecjLint and forbiddenApis pass for the changed files.

Override getValueFiller in IfFunction, DefFunction and MultiFunction.Values

#

Give each composite its own filler that sets the flag.

Trade-offs

Same effect for those three, more code, and it leaves the other inheritors (the vector similarity functions, the bridge) wrong. Not run.

Fix only the consumer (ValueSourceGroupSelector asks exists(doc))

#

Let the selector consult FunctionValues.exists(doc) instead of the filled value's flag.

Trade-offs

The filled value is the group key, so the selector would still have to set its flag (a missing document's 0.0 key equals the real 0.0 group): the first option done in the wrong place, leaving other filler users wrong. Not run.

Downstream note

#

Downstream, Solr's group.func builds these same if() and def() functions and groups them with this selector (read in Solr's code, not run), so its function-grouping counts can be off the same way.

How it was found

#

Semi-formal: a metamorphic identity check. Grouping by if(1, x, x) or def(x, ...) must give the same groups as grouping by x, checked through the public GroupingSearch API, plus code reading of the default value filler. A bounded-exhaustive run (all 39 indexes of 1-3 documents, 1,092 comparisons) found 700 mismatches, exactly where a document lacks x.

The method in full151 words
  • Origin: a metamorphic identity check of grouping by function through the public GroupingSearch API, plus code reading of the default value filler, both proposed by a model from another family (OpenAI GPT-5.6) in a review of public classes the hunt had rarely examined; an executed probe showed if(1, x, x) grouping a document without x into the 0.0 group on main 5adff78bb168 (2026-11-04).
  • Relation: for identity shapes F of if() and def() (if(1,x,x), if(0,x,x), if(1,x,absent), def(x), def(x,x), def(x,absent), def(absent,x)), group(F) must equal group(x).
  • Bounded-exhaustive run: every index of 1-3 documents with x absent, 0 or 1 (39 indexes), Int/Long/Float/Double field sources, 7 shapes: 700 of 1,092 comparisons differ, exactly on the 25 indexes that contain a document without x; 0 with the fix, assertions on and off.
  • Reduction: one public-API JUnit test (the repro), then independent reproduction and adversarial reviews (see Independent checks).
