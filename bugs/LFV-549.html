A failed SpellChecker.indexDictionary leaves the spell index write-locked until the JVM restarts

If SpellChecker.indexDictionary fails partway on its input, say a word list that is not valid UTF-8, it never closes or rolls back its IndexWriter, which keeps the spell index's write lock. Every later rebuild or clearIndex() in that JVM then fails with LockObtainFailedException until a restart, in releases from 2.4.0 (2008) to 10.6.0.

The finding in 30 seconds

#

One failed build, then a retry. The first indexDictionary throws (a bad encoding, an I/O error or a line over 32766 bytes); after the input is fixed, the retry should rebuild the spell index. It gets LockObtainFailedException, because the failed call's writer still holds write.lock.

Background: how SpellChecker builds its index

#
  1. SpellChecker (lucene-suggest) keeps its own small Lucene index of dictionary words, split into n-grams. indexDictionary(dict, config, fullMerge) adds the words of a Dictionary (a word-list file, the terms of an index field, ...) to it, and clearIndex() empties it.
  2. Each call opens an IndexWriter on that spell index. Only one writer may be open per index: it takes the index's write.lock when it opens and gives it back only when it is closed or rolled back.
  3. With the default FSDirectory, NativeFSLockFactory also records each held lock path in a static set shared by the whole JVM, and refuses a second lock on the same path with "Lock held by this virtual machine".

The finding, step by step

#
  1. Build a spell index with the defaults: new SpellChecker(FSDirectory.open(path)), then indexDictionary(new PlainTextDictionary(words), new IndexWriterConfig(), false). The word list holds alpha, bravo, café, delta, saved as ISO-8859-1, so reading café throws CharacterCodingException, an IOException.
  2. Re-save the file as UTF-8 and call indexDictionary again (or clearIndex()). You expect it to work: the failed call threw its documented exception and nothing else changed.
  3. Instead you get LockObtainFailedException: Lock held by this virtual machine: .../write.lock, and so does every later write to that spell index, even after SpellChecker.close(), Directory.close() and System.gc(), until the JVM restarts.
  4. Why: indexDictionary opens a local IndexWriter (line 496) and closes it only when the build succeeds (line 544); its only finally releases the searcher. The caller has no handle on that writer, and the default lock factory keeps the lock path in a JVM-wide set until the lock is closed.
  5. Reads keep working: suggestions keep coming from the last good build, and words the failed build added before it threw never become visible (0 of 20 in a probe). Nothing is corrupted; only writes are blocked.

Who is affected

#

Applications that use the classic n-gram SpellChecker with default settings and rebuild or clear its index in a long-running JVM after one build failed. No scale is needed: one badly encoded or over-long line is enough. Writes stay blocked until restart; reads keep serving the last good build. Rare: no diagnosed field report since 2008.

Mechanism, terms and numbers632 words

SpellChecker.indexDictionary (lucene-suggest) opens an IndexWriter on the spell index and closes it only when the build succeeds. When the build throws, from an I/O error while the dictionary is read, a word list that is not valid UTF-8, or a line over 32766 UTF-8 bytes, the writer is neither closed nor rolled back. It keeps the index's write.lock, the caller cannot reach it, and SpellChecker.close() does not close it. With the default FSDirectory, every later indexDictionary, clearIndex() or new IndexWriter on that path in the same JVM throws LockObtainFailedException: Lock held by this virtual machine until the JVM restarts. Suggestions keep coming from the last good build; nothing is corrupted. Every release from 2.4.0 (2008) to 10.6.0 and main is affected; rolling the writer back on failure fixes it.

Mechanism (Lucene main 645d4fe14a20)

#
// SpellChecker.indexDictionary, condensed
final IndexWriter writer = new IndexWriter(dir, config);       // :496  takes write.lock
IndexSearcher indexSearcher = obtainSearcher();                 // :497
...                                                             // :498-510
try {                                                           // :512
  BytesRefIterator iter = dict.getEntryIterator();              // :513  may throw IOException
  while ((currentTerm = iter.next()) != null) {                 // :517  may throw IOException
    ...
    writer.addDocument(doc);                                    // :535  may throw IllegalArgumentException
  }
} finally {
  releaseSearcher(indexSearcher);                               // :537-539  the only cleanup
}
if (fullMerge) writer.forceMerge(1);                            // :540-542
writer.close();                                                 // :544  success path only
  1. Line 496 opens the writer. With FSDirectory, NativeFSLockFactory puts the lock path into its static LOCK_HELD set (NativeFSLockFactory.java:68, :108) and holds an OS file lock.
  2. An exception from the dictionary at line 513 or 517, or the immense-term IllegalArgumentException at line 535, runs the finally, which releases the searcher only, and leaves the method: writer.close() at line 544 is skipped, and nothing rolls the writer back. IndexWriter does not treat these exceptions as tragic, so it does not roll itself back either. The writer is a local variable, so it becomes unreachable with the lock still held.
  3. SpellChecker.close() (SpellChecker.java:639-647) closes only the searcher's reader; there is no API to reach the writer.
  4. The next new IndexWriter on that path (line 496 in a retry, line 456 in clearIndex(), or the application's own) finds the path in LOCK_HELD and throws LockObtainFailedException("Lock held by this virtual machine: ...") (NativeFSLockFactory.java:119). Once the lock is held, only closing it removes the path (NativeFSLock.close(), :212 -> :145-146), and nothing closes it; GC does not remove the path either.

The three executed triggers (public API, default settings)

#
  • A word list that is not valid UTF-8. PlainTextDictionary(Path) decodes strictly as UTF-8 ("NOTE: content is treated as UTF-8", PlainTextDictionary.java:47-50): alpha, bravo, café, delta saved as ISO-8859-1 throws CharacterCodingException at café.
  • An I/O error while the dictionary is read. Dictionary.getEntryIterator() and BytesRefIterator.next() both declare IOException; the minimal repro uses this one.
  • A line over IndexWriter.MAX_TERM_LENGTH = 32766 UTF-8 bytes (IndexWriter.java:258). addDocument throws IllegalArgumentException "Document contains at least one immense term", as documented at IndexWriter.java:1480-1481 (from 4.8.0 on).

After any of them, a retry with good input, clearIndex(), and a plain new IndexWriter on a freshly opened FSDirectory after SpellChecker.close(), Directory.close() and five System.gc() calls all throw LockObtainFailedException (executed on main with assertions on and off, 10.5.2 and 9.12.3).

Not every failure leaks. When the writer itself hits an unrecoverable error, IndexWriter treats it as tragic and rolls itself back, so the retry works (executed in the fact check): an I/O error on the spell index while addDocument writes a segment (DocumentsWriterPerThread.java:585-603, IndexWriter.java:1629-1641, 6090-6104; the immediate retry succeeds), and a failed merge inside forceMerge (IndexWriter.java:5108-5113; a retry 3 s later succeeds, an immediate one can still race the merge thread's rollback). The leak needs an exception the writer does not treat as tragic, as in the three triggers above.

Exposure and likelihood273 words
  • Who. Users of the classic n-gram SpellChecker of lucene-suggest (not DirectSpellChecker, which has no spell index) that rebuild or clear the spell index without restarting the JVM. Defaults suffice: new SpellChecker(dir), new IndexWriterConfig(), FSDirectory.open with its default NativeFSLockFactory.
  • When. One build fails once: an I/O error while the dictionary is read, a word list that is not valid UTF-8, a line over 32766 UTF-8 bytes, or a custom Dictionary that throws. Index-based dictionaries (LuceneDictionary, HighFrequencyDictionary) over text the index accepted cannot produce the over-long word (executed with 32766-byte terms).
  • What goes wrong. After the input is fixed, the spell index cannot be rebuilt or cleared again in that JVM: every write throws LockObtainFailedException until restart. If the application called clearIndex() just before the failed build, that spellchecker returns no suggestions until the restart (by reading).
  • What it does not do (executed on main with assertions on and off, 10.5.2 and 9.12.3): no corruption and no data loss; the last good build keeps being served; none of the 20 words the failed build added is visible, even to a fresh DirectoryReader (numDocs=3, the last commit); another spell index in the same JVM works; the source index is never written; the leak is bounded in the probe (5 to 10 file descriptors after the failed build, 0 more over 200 retries; the heap the leaked writer keeps was not measured).
  • How likely. Rare: it needs a failed build followed by an in-process rebuild, and no diagnosed field report exists since 2.4.0 (2008). One undiagnosed 2012 solr-user mail shows the same symptom from clearIndex (see Prior reports).

Why it looks unintended

#
  • indexDictionary documents @throws IOException, so failure is expected; nothing says the index stays locked afterwards, and the caller has no handle to release the writer.
  • AnalyzingInfixSuggester.build, in the same module, rolls back its writer on any Throwable.
  • Up to 2.3.2 a retry worked (a force-unlock); LUCENE-1152 removed it in 2008 without discussing failed builds.
The full argument186 words
  • The contract. indexDictionary: "@throws IOException If there is a low-level I/O error" (SpellChecker.java:489). Nothing documents that the spell index stays locked afterwards, and the writer is a local variable, so only the method can release it.
  • The module's own idiom. AnalyzingInfixSuggester.build: catch (Throwable t) { if (writer != null) { writer.rollback(); writer = null; } throw t; } (AnalyzingInfixSuggester.java:362-368); PlainTextDictionary.FileIterator.next closes its reader on any Throwable (PlainTextDictionary.java:92-95).
  • History. Up to 2.3.2 every indexDictionary force-unlocked the index first, so a retry after a failed build worked (executed: 1.9.1 to 2.3.2 pass). LUCENE-1138 (#2215) objected that SpellChecker "shouldn't be calling unlock unless it has reason to think there is a 'stale lock'" (hossman), and LUCENE-1152 (#2229) removed the unlock in a clean-up; neither thread discusses a failed build. The later try/finally (LUCENE-2391, #3466, 2011) covered only the searcher.
  • Upstream precedent. LUCENE-2476 (#3550, "Constructor of IndexWriter let's runtime exceptions pop up, while keeping the writeLock obtained") was a type:bug, Blocker, fixed in 2.9.3, 3.0.2, 3.1 and 4.0.
  • Tests. TestSpellChecker never makes a build fail; no test asserts the current behaviour.
The devil's-advocate check154 words

The strongest "intended or not worth it" case (the devil's-advocate verifier and the intended-lens review): the javadoc promises only @throws IOException and says nothing about the state afterwards; PlainTextDictionary says "content is treated as UTF-8", so a Latin-1 file is misuse, and a 32766-byte "word" is bad input; SpellChecker is an old class with DirectSpellChecker as the newer alternative; a restart fixes it.

Why it fails: the caller has no handle on the writer, so no correct usage can release the lock on that path (the application can only move the SpellChecker to another directory with setSpellIndex, or restart); even where the input is misuse, the documented result is the exception, not a lock that outlives the fixed input; the I/O-error trigger involves no misuse at all; the class is not deprecated, experimental or internal; and the same module rolls back in the identical situation. The cross-model lenses rated the intended argument weak.

Suggested fix

#

Recommended A. Roll the writer back on any failure and rethrow the original exception

Wrap everything between new IndexWriter(...) and writer.close() in try { ... } catch (Throwable t) { IOUtils.closeWhileSuppressingExceptions(t, writer::rollback); throw t; }, the pattern AnalyzingInfixSuggester.build already uses. Rollback releases the lock and keeps the last good build. Validated: the repro passes with assertions on and off, and the suggest module's tests pass.

       final IndexWriter writer = new IndexWriter(dir, config);
+      try {
         IndexSearcher indexSearcher = obtainSearcher();
         ... (body unchanged, indented two more spaces) ...
         if (fullMerge) {
           writer.forceMerge(1);
         }
+      } catch (Throwable t) {
+        // the build failed: roll back so the write lock is released and the last good build stays
+        IOUtils.closeWhileSuppressingExceptions(t, writer::rollback);
+        throw t;
+      }
       // close writer
       writer.close();

A. Roll the writer back on any failure and rethrow the original exception (validated by the checks) (recommended)

#

In SpellChecker.indexDictionary (SpellChecker.java:496-544), plus import org.apache.lucene.util.IOUtils;: 41 lines added and 34 removed, almost all re-indentation; ignoring whitespace, the change is the try { line, the five-line catch and the import.

       final IndexWriter writer = new IndexWriter(dir, config);
+      try {
         IndexSearcher indexSearcher = obtainSearcher();
         ... (body unchanged, indented two more spaces) ...
         if (fullMerge) {
           writer.forceMerge(1);
         }
+      } catch (Throwable t) {
+        // the build failed: roll back so the write lock is released and the last good build stays
+        IOUtils.closeWhileSuppressingExceptions(t, writer::rollback);
+        throw t;
+      }
       // close writer
       writer.close();

Trade-offs

  • IndexWriter.rollback() closes the writer without committing (IndexWriter.java:2566-2576): the lock is released and the spell index stays at its last commit, which is what readers already see today, so nothing partial becomes visible.
  • The original exception is rethrown, with a rollback failure attached as suppressed (IOUtils.java:104-137). By that helper's design, if the build threw something other than an Error and the rollback throws an Error, that Error is thrown instead, with the original attached as suppressed. AnalyzingInfixSuggester.build calls writer.rollback() directly, which would lose the original exception if the rollback also threw.
  • The try starts right after the writer opens, so it also covers obtainSearcher(), the terms() setup and forceMerge (by reading). If the terms() setup throws, the writer is rolled back but, as today, the searcher is not released, because the inner finally starts only at line 512; moving that setup inside the inner try would cover it too. writer.close() stays outside: when close() fails, IndexWriter already rolls back itself (with the default commitOnClose through shutdown(), IndexWriter.java:1307-1338; with commitOnClose=false close() just calls rollback(), :1363-1369).
  • Backports: IOUtils.closeWhileSuppressingExceptions(Throwable, ...) exists from 10.4.0 on; on older branches use IOUtils.closeWhileHandlingException(writer::rollback) or the AnalyzingInfixSuggester shape.

B. Close (commit) the writer in a finally instead

#

Not run. Releases the lock too.

Trade-offs

  • close() commits by default, so the words added before the failure would become visible as a half-built spell index, unlike today, where readers keep the last good build.

C. Restore the old force-unlock before opening the writer (rejected)

#

The JVM-wide lock record and the OS file lock belong to the leaked writer, and there is no public API to drop them; force-unlocking is also what LUCENE-1138 objected to (SpellChecker "shouldn't be calling unlock unless it has reason to think there is a 'stale lock'"), and by our reading it could break a lock that another writer legitimately holds.

Downstream note

#

By reading only (nothing run downstream), Solr's IndexBasedSpellChecker and FileBasedSpellChecker call clearIndex() and then indexDictionary(), so there one failed rebuild would leave that spellchecker with no suggestions and unable to rebuild until the restart.

The finder confirmed it by reading and with a public-API JUnit test.

History

#

The lock-out came with LUCENE-1152 (a379a678759, 2008-05-22), which removed the force-unlock that let a retry work; first released in 2.4.0. 2.3.2 and earlier pass, 2.4.0 fails, and the commit itself is pinned; 22 releases from 2.4.0 to 10.5.2, 10.6.0 and main fail.

Versions tested7 rows

Introduced by a379a6787596 "LUCENE-1152 Fix for calling indexDictionary after clearIndex call" (svn r659013, 2008-05-22, committed by Otis Gospodnetic; CHANGES.txt credits Naveen Belkale). It removed the IndexReader.unlock(spellIndex) that indexDictionary and clearIndex ran before opening their writers. The missing close or rollback on the failure path is older: indexDictionary has reached writer.close() only on success since the spellchecker's first commit, 57cd0765650 (David Spencer, 2004-11-02); later rewrites (LUCENE-2108, LUCENE-2391, LUCENE-3557) kept that.

Recovery by GC changed over time: in 2.4.x IndexWriter.finalize still released the lock; from 2.9.0 (LUCENE-1715 removed the finalizer) the lock survives GC; 4.8.0 is the one exception on JDK 25 (LUCENE-5612 had dropped the JVM-wide set, LUCENE-5738 restored it in 4.9.0). The immediate retry fails in every affected version. The over-long-word trigger exists only from 4.8.0 (LUCENE-5472).

LFV-549, snapshot of 2026-11-07

Registry title
SpellChecker.indexDictionary never closes or rolls back its IndexWriter when the build throws, so the spell index stays write-locked and every later indexDictionary, clearIndex or IndexWriter on it in the same JVM fails with LockObtainFailedException until the JVM restarts
Area
suggest / spell: SpellChecker.indexDictionary (n-gram spell index build, failure cleanup)
Priority
Low, rank 1084: A failed SpellChecker.indexDictionary leaves the write lock held until JVM restart and can be triggered by an ordinary badly encoded word list.
Impact class
crash
Impact note
Applications of the classic n-gram SpellChecker of lucene-suggest (default constructor, default IndexWriterConfig and FSDirectory with its default NativeFSLockFactory suffice) whose indexDictionary build throws once, from an I/O error while the dictionary is read, a PlainTextDictionary word list that is not valid UTF-8 (CharacterCodingException) or a word-list line over 32766 UTF-8 bytes (IllegalArgumentException 'immense term', from 4.8.0 on), and that then rebuild or clear that spell index in the same JVM get LockObtainFailedException 'Lock held by this virtual machine' on every write to it (indexDictionary, clearIndex, a new IndexWriter on the path, even after SpellChecker.close(), Directory.close() and System.gc()) until the JVM restarts; suggestions keep coming from the last good build (none if clearIndex had already emptied the index in that cycle, code reading), nothing is lost or corrupted, other indexes are unaffected, 200 retries leak nothing more [exec], LuceneDictionary and HighFrequencyDictionary cannot produce the over-long term, and no scale is needed.
Summary
You build a spell index with SpellChecker.indexDictionary and the build throws, for example because the word-list file is not valid UTF-8, has a line longer than 32766 bytes, or its reader hits an I/O error; you fix the input and call indexDictionary or clearIndex again. You expect the retry to work, because the failed call should close or roll back the IndexWriter it opened. Instead indexDictionary closes its writer only on the success path, so the writer, which the caller cannot reach, keeps the spell index's write lock, and every later write to that index in the same JVM throws LockObtainFailedException 'Lock held by this virtual machine' until the JVM restarts.
