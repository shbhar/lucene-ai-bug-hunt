The default SortedSetDocValues terms enum casts the ordinal to int in seekExact(long): a seek to an ordinal of 2^31 or more throws or silently lands on the wrong term

Sorted-set ordinals are long, but the default SortedSetDocValues terms enum stores (int) ord in seekExact(long): on a view with more than 2^31 distinct values a seek to an ordinal from 2^31 to 2^32 - 1 throws, and seekExact(4294967301) (2^32 + 5) silently lands on ordinal 5. No Lucene code seeks such a view with an ordinal that large.

The finding in 30 seconds

#

One cast: SortedSetDocValuesTermsEnum.seekExact(long) stores currentOrd = (int) ord, which keeps only the low 32 bits of the 64-bit ordinal, then looks up that truncated ordinal.

Background: sorted-set ordinals and the default terms enum

#
  1. Sorted-set doc values store each distinct value once, in sorted order, and number them 0, 1, 2, ...: the ordinal. Ordinals are long (lookupOrd(long), long getValueCount()), so a view may hold more than 2^31 values.
  2. SortedSetDocValues#termsEnum() walks those values as a TermsEnum. You can jump to a value by ordinal with seekExact(long), or save a position with termState() and come back with seekExact(term, state).
  3. Per-segment doc values of the default codec bring their own enum. Views without one get the default, SortedSetDocValuesTermsEnum: the top-level MultiDocValues view over several segments, SortingCodecReader (meant for merging), SimpleText's multi-valued fields, or your own subclass.

The finding, step by step

#
  1. Take a sorted-set doc-values view with 4,294,967,302 (2^32 + 6) distinct values that keeps the default termsEnum(): for example MultiDocValues.getSortedSetValues over a huge multi-segment index, or your own SortedSetDocValues subclass.
  2. Call te = values.termsEnum() and te.seekExact(4294967301L). Ordinals are long and termsEnum() is documented to support seekExact(long), so you expect te.ord() to be 4,294,967,301.
  3. Instead seekExact stores currentOrd = (int) ord, which keeps only the low 32 bits: 2^32 + 5 becomes 5. ord() returns 5 and term() the value of ordinal 5, with no error, assertions on or off.
  4. Between 2^31 and 2^32 - 1 the cast turns negative: seekExact(2147483655) (2^31 + 7) looks up ordinal -2,147,483,641 and throws. Seeking back with a saved termState() goes through the same line and fails the same way.
  5. Everything else in the enum (seekCeil, seekExact(BytesRef), next(), ord()) uses the long and is right. Dropping the cast fixes it.

Who is affected

#

Only code that seeks by ordinal (seekExact(long) or seekExact(term, TermState)) on the default enum of a sorted-set view with more than 2^31 distinct values: the top-level MultiDocValues view, SortingCodecReader, SimpleText or your own subclass. No Lucene code does this with an ordinal of 2^31 or more, and per-segment default-codec doc values have their own correct enum.

Mechanism, terms and numbers722 words

SortedSetDocValues#termsEnum() returns, by default, a SortedSetDocValuesTermsEnum and documents that "The enum supports TermsEnum#ord() and TermsEnum#seekExact(long)". Sorted-set ordinals are long, and the enum keeps its position in a long field, but seekExact(long ord) stores currentOrd = (int) ord; before looking the value up. The cast keeps the low 32 bits as a signed int, and the assert one line above checks the un-narrowed long, so assertions do not catch it.

On a view with more than 2^31 distinct values a seek to an ordinal from 2^31 to 2^32 - 1 makes the enum look up a negative ordinal, which Lucene's views reject with an exception; from 2^32 to 2^32 + 2^31 - 1 it silently lands on ord mod 2^32: seekExact(4294967301) leaves the enum on ordinal 5 with the term of ordinal 5. Higher up the two behaviours alternate in bands of 2^31. seekExact(term, TermState) delegates to the same method. Only views that keep the default enum are affected: the top-level MultiDocValues view over several segments, SortingCodecReader's sorted-set view (documented for merging only), SimpleText's multi-valued fields, the test framework's asserting wrapper and application subclasses; per-segment values of the default codec have their own correct enum, and no Lucene code seeks these views with an ordinal of 2^31 or more. The line dates from 2013 (4.2.0) and is unchanged on main; currentOrd = ord; fixes it.

The code (main 645d4fe14a20)

#
// SortedSetDocValuesTermsEnum (abridged)
private long currentOrd = -1;                                 // :26

public void seekExact(long ord) throws IOException {          // :67
  assert ord >= 0 && ord < values.getValueCount();            // :68, checks the long
  currentOrd = (int) ord;                                     // :69, keeps the low 32 bits
  scratch.copyBytes(values.lookupOrd(currentOrd));            // :70
}

public void seekExact(BytesRef term, TermState state) throws IOException {  // :114
  this.seekExact(((OrdTermState) state).ord);                 // :116, same cast
}

What the cast does

#
ordinalhex (64-bit)(int) ordresult
2^31 - 1 = 2,147,483,6470x00000000_7FFFFFFF2,147,483,647correct
2^31 + 7 = 2,147,483,6550x00000000_80000007-2,147,483,641lookup of a negative ordinal throws
2^32 - 1 = 4,294,967,2950x00000000_FFFFFFFF-1throws
2^32 + 5 = 4,294,967,3010x00000001_000000055silently on ordinal 5; next() then goes to 6

In general an ordinal whose low 32 bits read as a negative int (2^31 to 2^32 - 1, 3 x 2^31 to 2^33 - 1, ...) makes the enum look up a negative ordinal. Lucene's own views reject that with an exception (by code reading; the type depends on the view: IndexOutOfBoundsException from the default codec's bounds check, IllegalArgumentException from the finder's synthetic values), and an application subclass's lookupOrd decides for itself. Any other ordinal of 2^32 or more (2^32 to 2^32 + 2^31 - 1, 2^33 to 2^33 + 2^31 - 1, ...) lands on ord mod 2^32. After a bad seek, ord(), term(), termState() and next() all continue from the wrong position.

Why the cast is there

#

The class was created in 2013 as a copy of SortedDocValuesTermsEnum, which has private int currentOrd and the same line; there it is correct, because SortedDocValues ordinals are ints. The copy widened the field to long and kept the line. That it is a copy leftover is an inference: no comment, test or commit message explains it.

Which views use this enum

#
  • MultiDocValues.MultiSortedSetDocValues (@lucene.internal), returned by MultiDocValues.getSortedSetValues for a reader with more than one segment when at least one segment has the field (otherwise it returns null); its ordinals are global ordinals from an OrdinalMap, so the bound is on distinct values across all segments. Executed by an independent check over a real OrdinalMap with two synthetic segments: fails, passes with the fix.
  • SortedSetDocValuesWriter.SortingSortedSetDocValues, returned by SortingCodecReader's sorted-set producer. SortingCodecReader's javadoc says it "should only be used for merging", and merging walks these values with next().
  • SimpleText's multi-valued sorted-set values (a debugging codec; single-valued SimpleText fields come back as a singleton and use the sorted enum), the test framework's AssertingLeafReader.AssertingSortedSetDocValues wrapper, the unused debugging helper GenericTermsCollector.verbose in join, and any application or downstream SortedSetDocValues subclass that does not override termsEnum(). FilterSortedSetDocValues and SingletonSortedSetDocValues delegate to the wrapped values.
  • Not affected: per-segment sorted-set values of the default codec, which return their own terms dictionary enum; its seekExact(long) works on the long. The merged view built for sorted-set merges also brings its own enum (MergedTermsEnum).
Exposure and likelihood274 words
  • Not Lucene's own code. Merges only iterate these enums with next(); the cited facet and join classes reject more than Integer.MAX_VALUE values up front; grouping's term facets seek SortedSetDocValues#termsEnum() by ordinal, but narrow the value count to int and seek with int ordinals, so they cannot reach 2^31. So no Lucene query, filter, facet, join, grouping or merge returns a wrong result from this (code reading; tests seek these enums only with small ordinals).
  • Default, not opt-in. No setting is involved: the enum is the default of the public base class. Assertions on and off behave the same.
  • Scale. 2^31 = 2,147,483,648 distinct values in one view, 2^32 = 4,294,967,296 for the silent case. The format allows it (the default codec writes the value count as a variable-length long), and a maintainer stated on #11636 / LUCENE-10600 that SORTED_SET fields can exceed Integer.MAX_VALUE unique values. For a multi-segment view the bound is on distinct values across all segments.
  • Effect. Ordinals 2^31 to 2^32 - 1, and every later band whose low 32 bits read as a negative int: the enum asks lookupOrd for a negative ordinal, which Lucene's own views reject with an exception (code reading; every executed view threw); an application subclass decides for itself. Ordinals 2^32 to 2^32 + 2^31 - 1, and every later band whose low 32 bits are non-negative: the enum silently reports ordinal ord mod 2^32 and its term, and next() continues from there. No memory unsafety (Java bounds checks).
  • Likelihood: contrived. It needs billions of distinct values in one view plus an ordinal seek on the default enum; nobody has reported it in 13 years.

More files, environment, full output267 words

Why it looks unintended

#
  • SortedSetDocValues#termsEnum() promises ord() and seekExact(long); ordinals are long, and even an ordinal that ord() reported lands on the wrong term.
  • Every other method of the enum uses its long field; the cast is left over from copying the int-ordinal sibling in 2013.
  • Maintainers removed the same kind of "bogus cast" in OrdinalMap in 2014 (LUCENE-5767).
The full argument202 words
  • Contract. SortedSetDocValues#termsEnum(): "Returns a TermsEnum over the values. The enum supports TermsEnum#ord() and TermsEnum#seekExact(long)." Ordinals and getValueCount() are long ("one plus the maximum ordinal"). TermsEnum#seekExact(long): "Seeks to the specified term by ordinal (position) as previously returned by ord(). The target ord may be before or after the current ord, and must be within bounds." seekExact(BytesRef, TermState) is legal with a state from the same enum instance.
  • The class is long-ordinal everywhere else. seekCeil, seekExact(BytesRef), next(), ord() and termState() use the long field, and OrdTermState.ord is a long. The cast is the only narrowing.
  • Upstream tests exercise this method. LegacyBaseDocValuesFormatTestCase.testSortedSetTermsEnum and testSortedSetEnumAdvanceIndependently (through its helper) seek by ordinal on multi-valued documents, and they run through TestSimpleTextDocValuesFormat, whose multi-valued sorted-set view uses this enum. Ordinal seeking is supported, just never tested above 2^31.
  • Precedent. rmuir's commit 7ab10178c38 (LUCENE-5767, 2014): "remove bogus cast (in this case can exceed Integer.MAX_VALUE, and the underlying delta reader takes long anyway)", changing (int) ord to ord in the global-ordinals code of MultiDocValues.
  • No documented limit. No javadoc, test, comment or CHANGES entry limits sorted-set views to 2^31 values; the facet and join guards are module-local caps for their own int arrays.
The devil's-advocate check270 words

The strongest case for "works as designed" (built by the intended-behaviour checker): (a) the enum is a package-private, generic fallback that LUCENE-4819 put behind termsEnum(), which codecs can override, and the default codec does; (b) the views that keep it are niche: MultiDocValues is @lucene.internal and @lucene.experimental ("This is very costly"), SortingCodecReader is documented as "should only be used for merging", and SimpleText is a debugging codec ("FOR RECREATIONAL USE ONLY"); (c) no Lucene code seeks them with an ordinal of 2^31 or more: the sorted-set merge view brings its own enum, grouping uses int ordinals, and the cited facet and join classes reject that many values; (d) seekExact(long) takes ordinals "as previously returned by ord()", which the minimal test's bare seekExact(2^32 + 5) is not; (e) no real index with more than 2^31 distinct values was built: the failing view is synthetic.

Why it fails: the public method SortedSetDocValues#termsEnum() promises seekExact(long) and every subclass that does not override it gets this enum; @lucene.internal and @lucene.experimental allow API changes, not a long-ordinal API that narrows to int, and niche, merge-only or debugging views limit reach, not correctness. The strict reading is answered by the round trips: seekCeil returns FOUND with ord() 4,294,967,301, and seeking back with that ord() or with that enum's termState() lands on 5. A synthetic view is the practical way to reach 2^31 values in a test; it uses only public classes, and an independent check reached the same line through a real OrdinalMap and MultiSortedSetDocValues over synthetic segments. "Nobody calls it at this scale" limits severity, not validity. Verdict: not intended, a defect; low priority.

Suggested fix

#

Recommended Drop the cast

Drop the cast: currentOrd = ord; in SortedSetDocValuesTermsEnum.seekExact(long). One token; it also fixes seekExact(term, TermState), which delegates there. The test passes with assertions on and off, and the closest core suites, the SimpleText doc-values suite and :lucene:core:check -x test pass.

Make the limit explicit with Math.toIntExact(ord)

#

Throw instead of narrowing.

Trade-offs

Turns the silent wrong position into an exception, but invents a 2^31 limit the long-ordinal API does not have and still rejects valid seeks. Not recommended; not validated.

Override termsEnum() in the affected in-tree views

#

Give MultiSortedSetDocValues and SortingSortedSetDocValues their own enums.

Trade-offs

Leaves every application or downstream subclass that relies on the default enum broken, and is far more code than one token. Not recommended; not validated.

Downstream note

#

Downstream, by code reading only: Elasticsearch's composite aggregation (since 8.7.0) seeks this default enum by a global ordinal taken from the request, so on a shard with more than 2^31 distinct values of one keyword field such a request could fail, or past 2^32 walk about 2^32 extra terms before answering correctly.

How it was found

#

Code reading. While writing a reference model of the doc-values terms-enum views for a small bounded-exhaustive test harness, an AI tool noticed that one method narrows the long ordinal to int; the harness itself (at most 4 values) cannot reach 2^31. A public-API JUnit test over a synthetic view with billions of values then reproduced it.

The method in full141 words
  • The hunt unit checked that terms and postings cursors stay coherent after every move. It modelled the doc-values terms-enum views for a bounded-exhaustive translation-validation harness, with at most 4 values per view, so no tool could reach 2^31; the signal came from reading the types while writing the model.
  • The finder then wrote a public-API JUnit over a synthetic SortedSetDocValues with 5 x 2^30 values that keeps the default termsEnum(): 3 tests (a seek to 2^31 + 7, a seek to 2^32 + 5, a same-instance TermState round trip), all failing on main, 10.5.2 and 9.12.3 with assertions on and off, all passing with the cast removed.
  • An independent reviewer from another model family (OpenAI GPT-5.6) pointed out that from 2^32 the cast wraps to a non-negative wrong ordinal; that became the silent-case test, and later the one-method minimal repro.

Only code that seeks by ordinal (seekExact(long), or seekExact(term, TermState) with the enum's own state) on the default terms enum of a sorted-set doc-values view holding more than 2^31 distinct values is hit: Lucene's MultiDocValues.getSortedSetValues over a composite reader, SortingCodecReader's sorted-set view, SimpleText, or an application or downstream SortedSetDocValues subclass; no in-tree caller makes that call (per-segment default-codec doc values use their own long-capable enum), so it is latent for Lucene's own code; ordinals from 2^31 to 2^32-1 make the seek throw, and ordinals such as 2^32+5 silently land on a much smaller ordinal (5) with no error; default codec and settings, extreme scale, every release since 4.2.0.
Summary
You take the terms enum of a sorted-set doc-values view with more than 2^31 distinct values (for example MultiDocValues.getSortedSetValues over a very large multi-segment index), position it on a term with seekCeil, keep ord() or termState(), and later return with seekExact(ord) or seekExact(term, state); you expect to land on that term again, because sorted-set ordinals are longs and termsEnum() is documented to support ord() and seekExact(long). Instead seekExact(long) stores '(int) ord' (SortedSetDocValuesTermsEnum.java:69), so for ordinals from 2^31 to 2^32-1 it asks the values for a negative ordinal and throws, and for 2^32+5 it silently positions on ordinal 5 and returns that term, with -ea and -da. seekCeil, seekExact(BytesRef), next() and ord() use long arithmetic and are correct; the fix is to drop the cast.
