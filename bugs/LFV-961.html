The grouping package overview says groupOffset 3 with topNGroups 10 returns 7 groups, but the collector managers it names return 10

The grouping package overview says groupOffset 3 with topNGroups 10 gives 7 groups, but the collector managers it names since 10.6.0 return 10, because for them topNGroups is the page size after the offset. The code is right; paging written from that sentence gets oversized, overlapping pages.

The finding in 30 seconds

#

Both managers give each collector a pool of groupOffset + topNGroups groups, then merge, skip groupOffset groups and return up to topNGroups. So topNGroups is the page size. The inputs list describes the plain collectors, whose topNGroups includes the offset; since 10.6.0 the page names the managers and no plain collector, and their own @param texts do not correct it.

Background: paging grouped results

#
  1. A grouped search ranks groups, for example all books by one author, by groupSort. To show page 2 at 5 groups per page you skip 5 groups (groupOffset) and ask for the next 5.
  2. The plain first-pass collector FirstPassGroupingCollector(selector, sort, topNGroups) keeps topNGroups groups in total, and getTopGroups(groupOffset) drops the first groupOffset of them: offset 3 of 10 leaves 7.
  3. Since 10.5.0 the module also has collector managers for concurrent search, FirstPassGroupingCollectorManager(selector, sort, groupOffset, topNGroups) and BlockGroupingCollectorManager(sort, groupOffset, topNGroups, ...). Since 10.6.0 the package overview names these and no plain collector.

The finding, step by step

#
  1. You page grouped results with the first-pass class the grouping overview names, FirstPassGroupingCollectorManager. Its inputs list says topNGroups is "how many top groups to keep" and that groupOffset 3 "means you'll get 7 groups back (assuming topNGroups is 10)".
  2. On an index with 13 groups you pass groupOffset 3 and topNGroups 10, and you expect 7 groups: ranks 4 to 10.
  3. You get 10 groups: ranks 4 to 13. BlockGroupingCollectorManager and GroupingSearch.search(searcher, query, 3, 10) also return 10; only the plain collectors return 7: FirstPassGroupingCollector with getTopGroups(3), and BlockGroupingCollector with topNGroups 10 and groupOffset 3.
  4. Paging written from the sentence, 5 groups per page (groupOffset 5p, topNGroups 5p+5), over 15 groups g00 to g14: page 1 returns g05 to g14 (10 groups) and page 2 repeats g10 to g14.
  5. Why: each manager keeps groupOffset + topNGroups groups per collector, then skips groupOffset and returns up to topNGroups, as GroupingSearch documents. The sentence describes the plain collectors, which the page stopped naming in 10.6.0 (#16385).

Who is affected

#

Developers who page grouped results with FirstPassGroupingCollectorManager or BlockGroupingCollectorManager (experimental, since 10.5.0) and take topNGroups from the package overview, its most explicit definition (the managers' @param texts read the same way). Their pages are larger than the page size and repeat groups of the next page; every group still matches the query. GroupingSearch users are not affected.

Mechanism, terms and numbers566 words

The lucene-grouping package overview defines the two paging inputs of a grouped search: topNGroups is "how many top groups to keep. For example, 10 means the top 10 groups are computed", and groupOffset 3 "means you'll get 7 groups back (assuming topNGroups is 10). This is useful for paging, where you might show 5 groups per page". Since #16385 (10.6.0) the same page names FirstPassGroupingCollectorManager as the first pass and builds BlockGroupingCollectorManager(groupSort, groupOffset, topNGroups, ...). Both managers, like GroupingSearch, treat topNGroups as the number of groups to return after the offset, so (3, 10) returns 10 groups, ranks 4 to 13. The "7 groups" rule holds only for the plain FirstPassGroupingCollector and BlockGroupingCollector, whose topNGroups includes the offset, and the 10.6 page names neither. The code is correct and intended; the text needs fixing. The bullet has also disagreed with the page's own example code since 3.2.

Exposure and likelihood205 words
  • Who: code written against the two collector managers from the overview's inputs list. Users of GroupingSearch, and anyone who passes the page size as topNGroups (the meaning GroupingSearch documents for its groupLimit), get the intended page size.
  • Default, not a special setting: no index size, codec or flag is involved. The minimal repro uses 13 one-document groups, and 11 already show the mismatch: with (3, 10) the first-pass manager returns 6, 7, 8, 9 and 10 groups for 9, 10, 11, 12 and 13 groups, so from 11 groups on it returns more than the sentence's 7. Since 10.6.0 the page names the managers and no plain collector, so the overview now leads its readers to them.
  • Effect: silent. No exception; pages look plausible. Nothing excluded or deleted appears: every group comes from the same query, filters and reader. The first pass also does somewhat more work than meant (each collector keeps about 2 x groupOffset + pageSize groups instead of groupOffset + pageSize).
  • Likelihood: plausible but limited. The managers are new (10.5.0) and @lucene.experimental, most users go through GroupingSearch, and no one has reported the mismatch in the roughly 15 years the bullet has disagreed with the page's examples.

Why it looks unintended

#
  • The page contradicts itself: its own examples always passed groupOffset + topNGroups to the plain collectors, which returns 10 groups, not 7.
  • The managers' meaning was chosen in the #15936 review to match GroupingSearch, and TestGrouping checks it.
  • #16385 renamed the classes on the page but kept the inputs list; nothing endorses it for the managers.
The full argument158 words
  • Self-contradiction since 2011: LUCENE-1421's two-pass example passed groupOffset+topNGroups to FirstPassGroupingCollector, and LUCENE-3129's Block example new BlockGroupingCollector(groupSort, groupOffset+topNGroups, ...) with getTopGroups(withinGroupSort, groupOffset, ...). Run with topNGroups 10 and groupOffset 3, that example returns 10 groups on 9.12.3, 10.4.0, 10.5.2, 10.6.0 and main.
  • The code is intended: in the #15936 review a reviewer asked whether the Block manager should "also use groupOffset", and the author changed it to groupOffset+topNGroups to match GroupingSearch. TestGrouping's oracle computes limit = Math.min(groupOffset + topNGroups, groups.size()) and returns limit - groupOffset groups (TestGrouping.java:676, :680), and passes groupOffset, topNGroups straight to both managers (:1110-1112, :1300-1309).
  • Nothing endorses the bullet for the managers: #16385 rewrote the class names and the example at a reviewer's request and left the inputs list; no review comment discusses it, no test uses (3, 10) or asserts the bullet's 7 groups (the assertEquals(7, ...) calls in TestGrouping.java:173-174 and TestGroupingSearch.java:125-126 check hit counts).
The devil's-advocate check139 words

Strongest case (a separate intended-behaviour verifier and a cross-model reviewer, OpenAI GPT-5.6, works-as-designed lens): the inputs list is a 2011 conceptual description of the low-level collectors; "how many top groups to keep" is their @param word for word, and for them "7 groups" is exactly right; the managers' meaning was decided in review and is tested; GroupingSearch documents it; the looseness is 15 years old and unreported.

Why it fails: all of that shows the code is right, which is the claim. The 10.6 page names no plain collector; it names the managers and shows a manager example, and for every paging API it names (both managers and GroupingSearch) its example "3 means you'll get 7 groups back" is false. The managers' own @param texts read like the bullet, so a manager user has nothing that corrects it.

Suggested fix

#

Recommended A. Rewrite the topNGroups and groupOffset bullets, naming both plain collectors (recommended)

Rewrite the two bullets in the package overview: topNGroups is how many groups to return counted from groupOffset, so 3 with 10 returns the groups ranked 4 to 13, as for GroupingSearch and the managers; add that the plain FirstPassGroupingCollector and BlockGroupingCollector take a count that includes the offset. Text only; the javadoc build and grouping tests pass.

 *   <li><code>topNGroups</code>: how many groups to return, counted from <code>groupOffset</code>.
 *       For example, 10 means up to 10 groups are returned.
 *   <li><code>groupOffset</code>: which "slice" of top groups you want to retrieve. For example, 3
