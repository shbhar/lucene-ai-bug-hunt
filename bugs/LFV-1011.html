A failed IndexRearranger.execute() closes its input reader under tasks that are still running

When a task of IndexRearranger.execute() fails while a task listed after it still runs, execute() stops waiting and closes the shared input reader, then the IndexWriter, under that task, whose selector code can then fail with AlreadyClosedException. Every release since 8.9.0 is affected.

The finding in 30 seconds

#

When one task fails, execute() stops waiting at once (it waits in list order), and leaving its try-with-resources closes the reader and the writer that tasks listed after it are still using.

Background: what IndexRearranger does

#
  1. IndexRearranger (module lucene/misc, @lucene.experimental) copies an index into a chosen segment layout, mainly to build comparable indexes for benchmarks. You give it an input and an output Directory and a list of DocumentSelectors; each selector picks the documents of one output segment.
  2. execute() opens one IndexWriter on the output and one reader on the input, and runs one task per selector in a pool of min(processors, selectors) threads. Each task calls its selector on the input's segments and then writer.addIndexes(...).
  3. It then waits for the tasks with future.get(), one after the other in list order, inside a try-with-resources that closes the reader and the writer when the block ends.

The finding, step by step

#
  1. Run IndexRearranger.execute() with two segment selectors on a machine with 2 or more processors. Both selectors run at the same time in a 2-thread pool, on one shared input reader, and each task then calls addIndexes on one shared IndexWriter.
  2. Selector 1 throws an IOException (its signature allows that) while selector 2 is still running. You expect execute() to throw that error once selector 2 has finished, and only then to close the reader and the writer.
  3. Instead execute() stops waiting at the first failed Future.get(), and its try-with-resources closes the reader, then the writer, under selector 2. The one-test repro sees the reader close under the running selector in every run: 20 of 20 with assertions off, and with assertions on too.
  4. Under normal timing: selector 2 scans the doc values of a 200,000-document segment (about 80 ms). The reader was closed 4.6 ms into the scan, and the scan failed with AlreadyClosedException. Since 9.4.0 an addIndexes merge still running also dies on a merge thread with an uncaught MergeException.
  5. execute() still throws the same first error, the input index is not changed and a successful run is unaffected: the damage is work left running on closed resources after a failure. It does not need two processors: with a one-thread pool the next queued task can start while the reader is being closed (9 of 10 check runs).

Who is affected

#

Callers of the experimental lucene/misc IndexRearranger with two or more selectors whose run fails (a selector throws, or addIndexes hits an I/O error) while a later-listed task still runs. That task can then fail with AlreadyClosedException; since 9.4.0 each in-flight merge adds an uncaught MergeException. The input index is not changed; successful runs are unaffected.

Mechanism, terms and numbers985 words

IndexRearranger.execute() opens the output IndexWriter and the input reader in one try-with-resources and runs one task per segment selector in a pool of min(processors, selectors) threads; each task calls its DocumentSelector on the input's segments and then writer.addIndexes(...). It waits with for (future : futures) future.get() in list order, so the first failed task makes it leave the block at once, without waiting for or stopping the tasks listed after it, and leaving the block closes the reader and then the writer while those tasks still use them. The delete phase (10.0.0+) has the same loop. In the one-test repro the reader is closed under a running selector in 20 of 20 runs; under natural timing a selector scanning a 200,000-document segment saw the reader closed 4.6 ms into its scan and failed with AlreadyClosedException, and since 9.4.0 an in-flight addIndexes merge also reports an uncaught MergeException on a merge thread. A one-thread pool is no protection: its thread can start the next queued task while the caller closes the reader (9 of 10 check runs). execute() still throws the same first exception as before, the input is only read and successful runs are unaffected, so the impact is minor. Waiting for every task before rethrowing fixes it; it is as old as the class (8.9.0) and not fixed upstream.

Terms

#
  • Segment selector (IndexRearranger.DocumentSelector): user code, BitSet getFilteredDocs(CodecReader reader) throws IOException, called once per input segment; the selected documents form one output segment.
  • Task: one per selector, submitted to the pool; it wraps each input segment in a filtered reader (whose constructor calls the selector) and passes them to writer.addIndexes(...).
  • try-with-resources: Java closes the resources in reverse order when the block ends, also when an exception leaves it; here the reader first, then the writer.

The bug (main 645d4fe14a20, IndexRearranger.java)

#
  1. execute() (:113-137) creates Executors.newFixedThreadPool(Math.min(availableProcessors, segmentSelectors.size()), ...) (:114-117) and opens try (IndexWriter writer = new IndexWriter(output, ...); IndexReader reader = DirectoryReader.open(input)) (:126-129).
  2. createRearrangedIndex (:180-200) submits one task per selector (:188-195). Each runs addOneSegment (:202-210): a DocSelectorFilteredCodecReader per leaf, whose constructor calls selector.getFilteredDocs(in) (:256), then writer.addIndexes(readers) (:209).
  3. It waits with for (Future<Void> future : futures) { future.get(); } (:197-199), in list order, so every task listed before the failed one has already finished. The first failed get() throws ExecutionException (the first failure in list order, not necessarily the first in time); the later futures are neither waited for nor cancelled. A check of both orders on main: [failing, running] closed the reader under the running selector in 5 of 5 runs, [running, failing] in 0 of 5.
  4. The exception leaves the try-with-resources, which closes the reader (its segment readers' closed listeners fire) and then the writer while the later tasks are still inside their selector or addIndexes. Only then does execute() throw.
  5. A running selector's next read fails with AlreadyClosedException: this IndexReader is closed; since 9.4.0 an addIndexes merge reading the input fails on its merge thread with MergePolicy$MergeException: AlreadyClosedException: Already closed: MemorySegmentIndexInput(.../_0.cfs) [slice=_0.fdx].
  6. In the selector phase, a task that starts only after the close fails at once in reader.leaves() (:204-205; CompositeReader.getContext() calls ensureOpen()), in a future nobody reads, so it never reaches its selector. The delete phase differs (code reading, not run): each task gets its segment reader before it is submitted (:221-227) and calls the deletes selector directly (:237), so a delete task that starts late does run the user's deletes selector.
  7. applyDeletes (:212-233, since 10.0.0) has the same loop (:230-232) inside the second try-with-resources (:132-135), whose reader is an NRT reader of that writer. It is a separate failure point, reached only when the selector phase succeeded, with one task per output segment (normally one per selector).

The one-test repro needs a pool of two threads, so that its signals can run both selectors at once. The bug does not: with one thread the tasks run one after the other, but FutureTask records the failure and wakes the caller before the pool thread takes the next queued task, which can then start while the caller is closing the reader. A check with the JVM limited to one processor (on a 32-processor host): the reader was closed under the next selector's scan in 9 of 10 runs on main, in 0 of 10 with the fix; a machine with a single core was not tried. Separately, executor.shutdown() (:136) runs only when both phases succeed, so a failed run also leaves its pool threads idle; that needs its own change.

The numbers

#
  • The one-test repro (one document, two selectors): the reader is closed under the running second selector in 20 of 20 runs on main with assertions off, and fails on the 10.5.2 and 10.6.0 release jars too; with the fix it passes 20 of 20.
  • A natural-timing probe (verification only, no ordering signals): one selector throws at once, the other scans a NumericDocValues field of a 200,000-document segment 100 times (57-93 ms when both succeed, 21 runs). On stock main the reader was closed 4.6 ms into the scan and the scan failed with AlreadyClosedException: Already closed: MemorySegmentIndexInput(.../_0.cfs) [slice=_0_Lucene90_0.dvd]. Over 10 iterations all 10 failure runs went wrong: 4 hit that exception mid-scan, and in 6 the scan never started within the probe's 60 s wait (from the code, the task met the already closed reader first). With the fix 20 of 20 pass, and the scan always finished 33-97 ms before the reader was closed.
  • A one-thread-pool check (the same selectors, -XX:ActiveProcessorCount=1, assertions off, 10 iterations): on main the reader was closed under the running scan in 9 of 10 runs (in the 10th the scan never started); with the fix in 0 of 10.
Exposure and likelihood323 words
  • Who is hit. Callers of IndexRearranger (@lucene.experimental, IndexRearranger.java:66) with two or more selectors whose run fails while a task listed after the failed one is still running (the await loop waits in list order). Two or more processors, the normal shape, make that the usual case; with a one-thread pool it is a race, which still happened in 9 of 10 check runs.
  • Triggers are ordinary. DocumentSelector.getFilteredDocs is declared throws IOException; addIndexes can fail on I/O. The shipped BinaryDocValueSelector.getFilteredDocs dereferences reader.getBinaryDocValues(field) without a null check, so a segment without that field throws NullPointerException (code reading). #1019 (2022) fixed a race after its author hit a rare TestIndexRearranger task failure, and a Jenkins build in November 2022 shows another task failure.
  • Default vs opt-in. The tool itself is opt-in (a misc module). Inside it no setting is needed: every multi-selector run on a multi-core machine waits with the early-leaving loop.
  • Per failed run. The tasks listed after the failed one that are running when the reader closes (at most one per pool thread) can each fail with AlreadyClosedException on their next read of the closed input, while execute() unwinds or after it has already thrown; since 9.4.0 each addIndexes merge still running also reports one uncaught MergePolicy.MergeException on a merge thread. In the selector phase, tasks that start after the close fail in futures nobody reads. The user's selector code can still run after execute() has thrown.
  • What does not happen. The input index is not changed (it is only read); execute() throws the same first exception as before (the first failure in list order); successful runs are unaffected; assertions on or off make no difference. The output of a failed run should not be relied on (not part of this claim).
  • Reach. Its main known consumer is benchmark tooling (luceneutil discussed using it for its nightly benchmark). No public report since 8.9.0 (2021) was found; likelihood rare, priority low.

Minimal repro

#

The test shows that a failed IndexRearranger.execute() rethrows the first selector's failure at once and closes its input reader while a second selector of the same call is still running on it.

Expected vs actual
How: the second selector keeps running until the caller either closes the reader under it (the bug) or stops running to wait for it (the fix). It starts this check once the caller holds the first failure: Future.get() builds new ExecutionException(cause), which calls the failure's toString(). No sleeps or timeouts. Needs at least 2 processors (pool = min(processors, selectors)), otherwise it is skipped.

Why it looks unintended

#
  • IndexReader.close(): "No other methods should be called after this has been called". IndexRearranger opens the reader for its own tasks, then closes it while they still call it.
  • Lucene fixed this pattern in its own TaskExecutor: wait for all tasks before rethrowing (#12523), cancel the rest (#12689).
  • Nothing documents the current behaviour, and selectors may throw IOException by signature.
The full argument240 words
  • Reader contract. IndexReader.close(): "Closes files associated with this index. Also saves any new deletions to disk. No other methods should be called after this has been called." (IndexReader.java:345-346). addIndexes(CodecReader...): "The provided IndexReaders are not closed." (IndexWriter.java:3257), so the caller keeps them open for the call. IndexRearranger opens the reader itself and hands it to its own tasks, so it is that caller.
  • Precedent. Issue #12278 (opened by javanna) asked: "Is it a reasonable expectation that once IndexSearcher#search(Query, CollectorManager) returns, that specific search has completed and has left no threads behind still working on it? I would expect this to be true". 9.9.0 then shipped "GITHUB#12523: TaskExecutor waits for all tasks to complete before returning when Exceptions are thrown during concurrent operations" and "GITHUB#12689: TaskExecutor to cancel all tasks on exception to avoid needless computation." (lucene/CHANGES.txt:3168, :3198); the code says "We rather want to make sure that invokeAll does not leave any running tasks behind when it returns." (TaskExecutor.java:186). StandardDirectoryReader keeps processing the remaining futures after one fails (:208-216), and CheckIndex shuts down and awaits its pool in a finally (:599-614).
  • Not documented. execute() has no javadoc; the class javadoc says nothing about failures; the CHANGES entries are features; TestIndexRearranger has 3 tests, all on successful runs, with no expectThrows.
  • Legal trigger. DocumentSelector.getFilteredDocs is declared throws IOException (IndexRearranger.java:283), and addIndexes(CodecReader...) declares IOException.
The devil's-advocate check235 words

The strongest case for "works as designed" (the intended-behaviour verifier, the cross-model review and the adjudication): IndexRearranger is an @lucene.experimental offline tool whose javadoc promises nothing on failure, fail-fast Future.get() loops are a common idiom, and IndexWriter is built to tolerate close() racing addIndexes: LUCENE-1335's TestAddIndexes.testAddIndexesWithClose, testAddIndexesWithCloseNoWait and testAddIndexesWithRollback close or roll back the writer while other threads add indexes, and since LUCENE-10216 (9.4.0) addIndexes(CodecReader...) merges are aborted on close (IndexWriter.java:3298-3302). So the IndexWriter.close() NOTE, "You must ensure no other threads are still making changes at the same time that this method is invoked." (:1359-1360), is weak support for the writer half.

Why it fails: it does not cover the reader half, where both observed failures come from (the selector's read, and the merge's read of the input _0.cfs, because the reader is closed before the writer). IndexRearranger owns the reader and the tasks and closes the reader while its own tasks still call it, and Lucene rejected fail-fast for its own concurrent code (#12278, #12523, #12689). @lucene.experimental is about API stability, not about leaving work running. The argument limits priority (low), not validity; this is an inference from the code, its contracts and precedent, not a maintainer ruling. Conceded: IndexReader.close() is a usage rule, not a concurrency or lifetime protocol, and a maintainer could reasonably see this as low-value clean-up of a run that has already failed.

Suggested fix

#

Recommended A. Wait for every task before rethrowing

Wait for every task before rethrowing: both await loops call get() on every future, keep the first ExecutionException and add later failures as suppressed (+23/-4 in IndexRearranger.java). The repro then passes with assertions on and off, and the misc module's tests and :lucene:misc:check pass. Trade-off: queued tasks still run to completion on a failing run.

Trade-offs

  • A failing execute() returns only after every submitted task has finished, including queued ones, which still do their full addIndexes work for a run that is reported as failed (bounded: one task per selector). B avoids that.
  • Only ExecutionException is collected. An InterruptedException in get() still leaves the loop at once, so an interrupt of the calling thread can still close the reader under running tasks; a fuller fix keeps waiting and restores the interrupt flag, or uses C. (A CancellationException cannot occur: nothing cancels these futures.)
  • A task that hangs now also keeps a failing execute() waiting, indefinitely, as it already does for a successful one.
  • It does not shut the pool down on failure (:136); the study's combined change adds a finally that does (+35/-13). With both, the regression test needs no thread-leak filter (executed).
  • Future.cancel(false) alone would not do: a running FutureTask keeps running after cancel, and get() then throws CancellationException at once, which is why TaskExecutor overrides cancel.
  • Error path only; no API or format change.

B. Cancel the tasks that have not started, then wait for the running ones

#

As TaskExecutor does since #12689: wrap each task so that it records when it starts; on the first failure cancel every task that has not started and wait for the started ones before rethrowing.

Trade-offs

Saves the wasted work of A on a failing run. More code: plain Future.cancel(false) returns true for a queued and for a running task alike, so it cannot tell them apart; it needs an atomic started flag as in TaskExecutor. Not tried.

C. Drain the pool before the reader and writer close

#

Use a pool per phase and declare it as the last resource of each try-with-resources, so that its close() runs first: ExecutorService.close() (JDK 19+) shuts down and waits for all tasks, and on interrupt calls shutdownNow() and keeps waiting for the running ones. This also fixes the pool leak.

Trade-offs

Queued tasks still run unless also cancelled. Interrupts are cooperative, so a selector that ignores them keeps close() waiting. Lucene 10.x and main (Java 21+) have close(); a 9.x backport (Java 11) needs an explicit shutdown() and awaitTermination() in a finally. Not tried.

How it was found

#

Semi-formal: while building a failure-point model of execute() (no task may outlive it, and the reader and writer must not close under a task), the hunting AI tool found the early-leaving future.get() loop by reading the code. The model's bounded runs never hit it with 6-document inputs; deterministic JUnit tests on the stock jars then showed it.

The method in full167 words

Method: semi-formal (the hunt's unit on failed-run cleanup in IndexRearranger and PKIndexSplitter, 2026-10-29, main 645d4fe14a20). The hunting AI tool built a failure-point model of execute() with obligation I4: no task of the call outlives execute(), and the writer and reader are not closed while a task uses them. Reading the modelled resource lifecycle against the reader and writer contracts, it saw that the await loop leaves on the first failure inside the try-with-resources.

  • The model's bounded-exhaustive single-fault model-based test (4,147 IndexRearranger runs, each at 1 and at 4 processors; vacuity mutants killed) never fired I4 with its 6-document inputs, so the model did not find it by itself.
  • Two deterministic, latch-ordered public-API JUnit tests on the stock jars showed it (a selector still running after execute() threw, and an addIndexes merge dying on a merge thread).
  • On 2026-10-29 the repro was cut to one test with no sleeps or timeouts; on 2026-11-01 a current-main re-verification and a tie-break re-ran it and added a natural-timing probe.

LFV-1011, snapshot of 2026-11-05

Registry title
A failed IndexRearranger.execute() throws without waiting for its other tasks, and closes the input reader and the IndexWriter while those tasks still use them
Area
misc / index tools (IndexRearranger.execute failure path: the await loops of createRearrangedIndex and applyDeletes inside the try-with-resources)
Priority
Low, rank 1103: Same pattern as LFV-357 (cleanup runs before the submitted tasks finish) in the experimental IndexRearranger, failing loudly with nothing corrupted.
Impact class
minor
Impact note
Hits only callers of the experimental lucene/misc IndexRearranger (8.9.0 through 10.6.0 and main) whose execute() is already failing, because one task's DocumentSelector throws or addIndexes hits an I/O error, while another task of the same call still runs (needs a pool of at least two threads, that is two or more selectors and processors, the normal shape): execute() still throws the correct first exception, but the other tasks' selector code and addIndexes merges keep running after it on a reader and a writer it has closed and then fail with AlreadyClosedException, and since 9.4.0 each in-flight merge also reports one extra uncaught MergePolicy.MergeException on a merge thread; nothing is corrupted, the input index is only read, and a successful execute() is unaffected [exec, -ea and -da].
Summary
You run IndexRearranger.execute() with several segment selectors and one of the tasks fails (its selector throws an IOException, or addIndexes hits an I/O error). You expect execute() to throw that error only after the tasks it started have stopped using its input reader and output IndexWriter. Instead execute() rethrows the first failed Future.get() at once and its try-with-resources closes the reader and the writer while the other tasks still run, so their selector code keeps running after execute() has thrown and fails with AlreadyClosedException 'this IndexReader is closed', and an addIndexes merge that is still running dies on a merge thread with an uncaught MergeException.
