XYDocValuesField.newDistanceSort accepts a NaN or infinite origin instead of throwing

XYDocValuesField.newDistanceSort promises an IllegalArgumentException for invalid coordinates but accepts a NaN or infinite origin, because its sort field never checks x and y. The sort then runs in a meaningless order: with a NaN origin, documents without a location come first instead of last (every release since 8.5.0 and main).

The finding in 30 seconds

#

newDistanceSort passes x and y to a sort field whose constructor checks only the field name. Every computed distance then contains the bad coordinate: NaN for a NaN origin, Infinity for an infinite one, while documents without a location keep their fixed distance, Infinity.

Background: sorting by x/y distance

#
  1. XYDocValuesField stores a point on a flat x/y plane per document. XYDocValuesField.newDistanceSort(field, x, y) returns a SortField that orders hits by straight-line distance from the origin (x, y), nearest first.
  2. A document without the field gets distance Infinity, so it sorts after every document that has a location ("missing values sort last").
  3. For XY, only finite floats are valid coordinates: a NaN or Infinity in an indexed point, an XYPoint, an XYCircle or a distance query throws IllegalArgumentException.

The finding, step by step

#
  1. Index three documents: A at (1, 1), B with no location, C at (2, 2). Sorting with XYDocValuesField.newDistanceSort("p", 0, 0) gives A (1.41), C (2.83), then B (Infinity): missing values sort last, as documented.
  2. Now the origin is (NaN, 0), for example a centroid computed as 0/0 or a request value "NaN" read with Float.parseFloat. You expect IllegalArgumentException: the javadoc promises it for invalid coordinates, and new XYDocValuesField("p", NaN, 0), XYPointField.newDistanceQuery and the lat/lon twin all throw it.
  3. You get no error: the sort field's constructor only checks that the field name is not null. Every located document's distance becomes NaN, and Double.compare puts NaN after Infinity.
  4. So the order is B, A, C: the document with no location comes first, and A and C report distance NaN. An infinite origin makes every distance Infinity and returns A, B, C in doc-id order.
  5. Only requests that use this sort are affected: in the probe the matching documents, hit count and paging were unchanged, and the bad sort does not change the index.

Who is affected

#

Applications that sort by x/y distance and let a NaN or infinite origin through, such as a computed 0/0 or "NaN" or "Infinity" parsed with Float.parseFloat. They get no error and a meaningless order for those requests. Rare: a GitHub code search found no caller in Elasticsearch, OpenSearch or Solr, and no public report since 2020.

Mechanism, terms and numbers596 words

XYDocValuesField.newDistanceSort(field, x, y) documents "@throws IllegalArgumentException if {@code field} is null or location has invalid coordinates", word for word like its lat/lon twin. It returns new XYPointSortField(field, x, y), whose constructor checks only field != null, so a NaN or infinite x or y is accepted. The XY APIs around it that take coordinates (the XYDocValuesField constructor, XYPointField.newDistanceQuery, and the XYPoint, XYCircle, XYRectangle, XYLine and XYPolygon constructors) reject exactly these values through XYEncodingUtils.checkVal, and the lat/lon sort field validates its origin.

The search then runs. A document without the field has distance +Infinity; a located one has sqrt((x - docX)^2 + (y - docY)^2), which is NaN for a NaN origin and +Infinity for an infinite one. Double.compare orders NaN after +Infinity, so with a NaN origin documents without a location come first, against the documented "missing values sort last"; with an infinite origin everything ties and comes back in doc-id order. Only requests that use this sort are affected. It came with the XY sort in 8.5.0 (LUCENE-9238, a port of the lat/lon code that kept the @throws line but not the check) and is in every release through 10.6.0 and on main. Two XYEncodingUtils.encode calls in the constructor fix it; the fix passes the repro, the closest XY suites and check.

The bug, step by step (main 645d4fe14a20, under lucene/core/src/java/org/apache/lucene/)

#
  1. No check. XYDocValuesField.newDistanceSort is return new XYPointSortField(field, x, y); (document/XYDocValuesField.java:151-152). The constructor calls super(field, Type.CUSTOM, false, Double.POSITIVE_INFINITY) (the missing value), throws only when field == null, and stores x and y as given (document/XYPointSortField.java:28-35). The twin LatLonPointSortField calls GeoUtils.checkLatitude(latitude); GeoUtils.checkLongitude(longitude); at the same place (document/LatLonPointSortField.java:34-35), and checkLatitude rejects NaN explicitly (geo/GeoUtils.java:85-86).
  2. The sort key. XYPointDistanceComparator.sortKey starts from Double.POSITIVE_INFINITY, which a document without the field keeps, and takes Math.min over Math.sqrt(diffX * diffX + diffY * diffY) with diffX = x - docX (document/XYPointDistanceComparator.java:190-209). For a NaN origin the distance is NaN and Math.min(Infinity, NaN) is NaN. For an infinite origin every distance is +Infinity, equal to the missing value.
  3. The order. Slots are compared with Double.compare (:77-79), which orders NaN after +Infinity; a missing document is compared as +Infinity in compareBottom (:126-128). Ascending order therefore puts missing documents first under a NaN origin and ties everything under an infinite origin (ties go by doc id).
  4. No crash, no hang. setBottom builds its pruning box only when bottom < Float.MAX_VALUE (:87-97), which is false for NaN and +Infinity, so nothing throws at search time and nothing loops. The box keeps its initial full range (:55-58), so compareBottom never skips a value by the box and computes the distance of every value it sees (:122-160): possibly more work than with a finite origin. The probe saw no timing blow-up; memory was not measured.

Exposure and likelihood278 words
  • Who is hit. Applications that sort with XYDocValuesField.newDistanceSort and let a non-finite origin through: a reference point computed as 0/0 (for example the centroid of an empty set), or a request parameter "NaN" or "Infinity" parsed with Float.parseFloat and passed on unchecked. Default IndexWriterConfig, codec and searcher; the missing check is in the sort field's constructor, so it does not depend on the index; query-time only.
  • What goes wrong. No exception, and the results come back in a meaningless order: documents without a location first (NaN origin) or plain doc-id order (infinite origin), with NaN or Infinity as the reported distances. An application that relies on the documented IllegalArgumentException to reject bad input never sees it.
  • Limits. The sort field belongs to the request that builds it, so only requests that use it are affected. In the study's probe (20,000 documents, 8 segments, 7 origins; main with assertions on and off, 10.5.2 with assertions on) the matched set and hit count equalled a filter's count, searchAfter paging returned every match exactly once, a sliced concurrent search returned the same top 50 hits as the sequential one, and search time did not blow up. These are the tested workloads, not a proof for every index. The bad sort runs only at query time and does not change the index; index-time XY fields still reject non-finite values.
  • Reach. A GitHub code search found no caller in Elasticsearch, OpenSearch or Solr (default branches, 2026-10-26), only copies of Lucene's own test elsewhere. That bounds the search; it does not prove there are no callers.
  • Likelihood: rare. Normal code passes finite coordinates; the recorded searches found no public report since 8.5.0 (2020).

Why it looks unintended

#
  • The javadoc promises IllegalArgumentException when the location has invalid coordinates, and says missing values sort last.
  • For XY, invalid means non-finite: the same class's constructor, XYPoint, XYCircle and XYPointField.newDistanceQuery all reject NaN and Infinity.
  • The lat/lon twin, from which the XY code was ported, validates its origin; the port kept the @throws line but not the check.
The full argument306 words
  • The method's own contract. "@throws IllegalArgumentException if {@code field} is null or location has invalid coordinates." (XYDocValuesField.java:149) and "missing values sort last" (:139-140).
  • What "invalid" means for XY. The same class's constructor and setLocationValue: "@throws IllegalArgumentException if ... x or y are infinite or NaN" (:79, :91), enforced through XYEncodingUtils.encode (:94-95), which calls checkVal, "validates value is a number and finite" (XYEncodingUtils.java:34-41). XYPoint and XYCircle call checkVal too.
  • The sibling query enforces the identical wording, and a test checks it. XYPointField.newDistanceQuery: "@throws IllegalArgumentException if {@code field} is null, location has invalid coordinates, or radius is invalid" (XYPointField.java:174-175), enforced by new XYCircle (:178). Upstream BaseXYPointTestCase.testDistanceIllegal, "distance query should not accept invalid x/y as origin", passes a NaN origin. No upstream test passes a non-finite origin to the XY sort.
  • The twins validate. LatLonPointSortField has checked its origin since its first commit (LUCENE-7099, 2016), and the Geo3D distance sort goes through Geo3DUtil.fromDistance, which calls GeoUtils.checkLatitude/checkLongitude.
  • A port that lost the check. LUCENE-9238 (PR apache/lucene-solr#1272, whose description reads "Adaptation of LatLonPoint to generic cartesian space.") copied the @throws line word for word but not the check. That the check was lost in the port is an inference from the identical javadoc and the validating twin, not a stated intent; the PR has no discussion of validation.
  • The finite-only rule predates the sort. XYEncodingUtils.checkVal has rejected NaN and values beyond +/-Float.MAX_VALUE (so both infinities) since it was added with XYEncodingUtils in LUCENE-8632 (0c09481374c, 2019-07-08). One week before the sort, LUCENE-9218 (apache/lucene-solr#1252, merged 2020-02-14) rewrote it for floats as Float.isFinite(x) == false, "validates value is a number and finite"; in that PR the author had written Float.isNaN(x) || Float.isInfinite(x) and a reviewer suggested the single test.
The devil's-advocate check174 words

The strongest case: the XY javadoc is lat/lon boilerplate (it still says the sort value is a "distance in meters", XYDocValuesField.java:137, although x/y coordinates have no unit), XYPointSortField is package-private, NaN in means garbage out, and Double.compare is a total order, so the result is at least deterministic. Finiteness is an XY-family rule, not a Lucene-wide one: the generic FloatPoint deliberately accepts NaN and the infinities (TestPointQueries.testCrazyFloats), and a caller could be using a NaN origin as a sentinel today. The cross-model reviews rated this case weak.

Why it fails: the @throws clause is exactly what the siblings enforce (the lat/lon and Geo3D sorts, the XY field, point, circle and distance-query APIs, the same class's constructor). The fix rejects only non-finite origins; the finite origins probed are unchanged (an origin at -Float.MAX_VALUE still sorts with missing last, with and without the fix). A caller that relies on a non-finite origin would now get the exception, a compatibility change. It is a good reason for low priority, not for keeping the gap.

Suggested fix

#

Recommended Validate x and y in the XYPointSortField constructor (+4 lines)

Validate the origin in the XYPointSortField constructor with the XY family's finite check: XYEncodingUtils.encode(x); XYEncodingUtils.encode(y); plus an import. Validated on main: the repro passes with assertions on and off, the closest XY suites (90 tests) pass, and check passes.

Trade-offs

  • A caller that passes a non-finite origin now gets the documented exception instead of a meaningless order: a visible behaviour change worth a CHANGES entry, and a break for any caller that used a NaN or infinite origin on purpose (say, as a sentinel). The finite origins probed give the same results: an origin at -Float.MAX_VALUE still sorts, missing last. Constructor-time cost only.
  • Calling encode for its side effect reads slightly odd; the alternatives below avoid that.
  • Open PR #14775 ("Add the ability to inverse a Sort") also edits XYPointSortField.java, outside the constructor, so a fix PR conflicts at most trivially.

What the checks validated

  • Stock 645d4fe14a20: the repro fails (1 of 1) with assertions on and off, through gradle and the standalone runner; also on the 10.6.0 jars.
  • With the fix: the repro passes with assertions on and off; the 5 closest XY suites pass (90 tests, 5 skipped, 0 failures); :lucene:core:check -x test (google-java-format, ecj lint main and test, forbidden APIs, dependency license check) passes with the repro test in place. These are targeted runs, not the full Lucene test suite.
  • Probe with the fixed file shadowed: (NaN, 0), (0, NaN), (Infinity, 0) and (0, -Infinity) are rejected; (0, 0) and (-Float.MAX_VALUE, 0) give the same order and distances as stock.
  • The diff shown (reworded comment) applies to 645d4fe14a20 with git apply --check, is google-java-format clean, and passes the minimal repro with assertions on and off (stock still fails both).

Trade-offs

Reads as "the origin must be a valid point", at the cost of one small allocation per sort field.

An explicit finite check with its own message (not run)

Trade-offs

Clearest intent, but a new message unlike the rest of the XY family.

Map NaN distances to Infinity in the comparator

Would keep missing documents last for a NaN origin.

Trade-offs

Not enough: it hides the bad input instead of rejecting it, and the javadoc promises an exception.

Downstream note

#

A GitHub code search found no caller of this API in Elasticsearch, OpenSearch or Solr; an application that forwards a user-supplied origin unchecked lets that user scramble only the order of their own results.

How it was found

#

A normalised static diff of sibling classes compared LatLonPointSortField with its x/y port XYPointSortField: the lat/lon origin checks have no counterpart in the XY class. A public-API JUnit with NaN and Infinity then showed that newDistanceSort accepts them.

The method in full128 words

Method: non-formal (the diff is an automated code-reading aid, not a model, a proof or a bounded-exhaustive check).

  • The unit's twin-diff tool normalised the lat/lon and x/y sibling classes of the geo family and listed every member that differs beyond the expected type and name changes. In LatLonPointSortField vs XYPointSortField, the GeoUtils.checkLatitude/checkLongitude lines exist only in the lat/lon twin.
  • The finder then ran a targeted public-API JUnit on the stock jar with the non-finite values (NaN, +Infinity, -Infinity): newDistanceSort accepted all of them, and a NaN origin put the document without a location first. An independent reproducer wrote its own test (all six non-finite origins accepted, controls passing), a devil's advocate and an adjudication confirmed it, and the repro was later cut to the one-line test above.

History

#

Born with the feature: LUCENE-9238 (88dd1c3f3d4, 2020-02-21) ported the lat/lon distance sort to x/y without its origin check; first released in 8.5.0. It fails the same way on all 52 releases 8.5.0 to 10.5.2, on 10.6.0 and on main; never fixed.

Versions tested8 rows

Introduced by 88dd1c3f3d4 (master, now main) and the branch_8x backport 53cb6acf912, both "LUCENE-9238: Add new XYPointField, queries and sorting capabilities (#1272)" (Ignacio Vera, 2020-02-21; PR apache/lucene-solr#1272, issue now #10278), which created XYDocValuesField, XYPointSortField and XYPointDistanceComparator. The constructor has checked only field != null ever since; later edits (LUCENE-9570, LUCENE-10377, #12405, #15483, #15486) never touched validation. Not a regression, so there is no commit-level A/B: the parents do not have the classes.

Before 8.5.0 the API does not exist (8.4.1: the study's JUnit does not compile, failing only at the uses of XYDocValuesField). The constructor is unchanged on 10.6.0, branch_10_6 and upstream main 2f424fd428d (2026-10-30).

XYDocValuesField.newDistanceSort accepts a NaN or infinite origin although its javadoc promises IllegalArgumentException for invalid coordinates (the LatLon twin and every other XY entry point reject such values); with a NaN origin, documents without a location sort first instead of last

core / document: XY distance sort (XYDocValuesField.newDistanceSort, XYPointSortField, XYPointDistanceComparator)
Priority
Low, rank 969: XYDocValuesField.newDistanceSort accepts a NaN or infinite origin instead of rejecting it, with a minor missing-last sort side effect, the same accepts-NaN-parameter profile as LFV-304.
Impact class
wrong error
Impact note
Applications that sort by cartesian distance with XYDocValuesField.newDistanceSort and let a NaN or +/-Infinity origin coordinate through (for example a value computed as 0/0, or request text parsed with Float.parseFloat, which accepts 'NaN' and 'Infinity') get no IllegalArgumentException, and the search runs with a meaningless order: with a NaN origin every distance is NaN and documents without the field (distance +Infinity) come first, against the documented 'missing values sort last'; with an infinite origin every distance is +Infinity and the hits come back in doc-id order; default IndexWriterConfig, codec and searcher, any index size; query-time only, so the match set, the hit count, other requests and the index are unaffected; released since 8.5.0.
Summary
You build a distance sort with XYDocValuesField.newDistanceSort("p", Float.NaN, 0f), or with an infinite x or y, and expect the IllegalArgumentException that its javadoc promises when the 'location has invalid coordinates', as LatLonDocValuesField.newDistanceSort throws for NaN and as the XYDocValuesField constructor, XYPointField.newDistanceQuery and XYCircle throw for the same values. Instead the sort is built and the search runs, because the XYPointSortField constructor checks only that the field name is not null. With a NaN origin every distance is NaN, which Double.compare orders after +Infinity, so a document without a location (distance +Infinity, documented as 'missing values sort last') is returned before the documents that have one; with an infinite origin all distances tie at +Infinity.
