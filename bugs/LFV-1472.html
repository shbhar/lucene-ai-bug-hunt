Sandbox HistogramCollectorManager throws ArithmeticException when a segment has a skip-indexed field but no value for it

The sandbox HistogramCollectorManager fails the whole search with ArithmeticException once one segment lists a skip-indexed field but has no value for it (for example, its valued documents were deleted and merged away), because it reads that segment's empty range as a small bucket span. Affects 10.2.0 to 10.6.0 and main.

The finding in 30 seconds

#

The dense-array shortcut reads an empty segment's inverted range as a small, negative bucket span and sizes its counter array from it.

What the collector reads from the skip index

#
  1. A doc-values skip index (DocValuesSkipper) keeps, per segment, the minimum and maximum value of a field and how many documents have a value (docCount()).
  2. When a segment lists the field but no document has a value, the skipper is empty: docCount() 0, minValue() Long.MAX_VALUE, maxValue() Long.MIN_VALUE, an inverted "nothing here" range.
  3. HistogramCollectorManager(field, w) counts values per bucket of width w. When the segment's lowest and highest bucket indices differ by at most 1,024 (up to 1,025 buckets), it counts in a dense int[] sized from the skipper's range; otherwise it uses a hash map.

The finding, step by step

#
  1. You index two documents with the default codec: one without field f, and one with NumericDocValuesField.indexedField("f", 50) (doc values plus a skip index; no index sort). You delete the second one and run forceMerge(1).
  2. The merged segment still lists f, but no document has a value. Its skip index is empty: docCount() 0, minValue() Long.MAX_VALUE, maxValue() Long.MIN_VALUE, a state core writes on purpose and CheckIndex accepts.
  3. You run search(MatchAllDocsQuery.INSTANCE, new HistogramCollectorManager("f", 10)) and expect an empty histogram, which is what the same index gives without a skip index.
  4. Instead the bucket span is floorDiv(Long.MIN_VALUE, 10) - floorDiv(Long.MAX_VALUE, 10) = -1,844,674,407,370,955,161. It passes the <= 1024 test for the dense counter array, and new int[Math.toIntExact(span + 1)] throws ArithmeticException: integer overflow, with assertions on and off.
  5. One such segment fails the whole search: with a second segment holding f = 7 you still get the exception instead of {0: 1}, until a merge folds the empty segment into one with values.

Who is affected

#

Users of the sandbox HistogramCollectorManager on a single-valued numeric field with a doc-values skip index (opt-in), default codec. Any segment left with the field but no value (deletes plus a merge, addIndexes, soft deletes, a rejected document) fails every histogram search on that field until a later merge. Loud; no wrong counts.

Mechanism, terms and numbers554 words

HistogramCollector.getLeafCollector (sandbox) counts with a dense int[] when the bucket indices of the segment's DocValuesSkipper bounds differ by at most 1,024: floorDiv(maxValue, w) - floorDiv(minValue, w) <= 1024 (HistogramCollector.java:107-116). It never looks at docCount(). A segment that lists the field but in which no document has a value has an empty skipper, with the inverted bounds minValue() Long.MAX_VALUE and maxValue() Long.MIN_VALUE; core writes this state on purpose, CheckIndex accepts it and a core format test builds it. The span is then hugely negative, passes the one-sided check, and the dense collector's new int[Math.toIntExact(span + 1)] (:274) throws.

Ordinary operations leave such a segment behind: deleting every valued document of a segment and merging it (forceMerge, or the default merge policy at commit; also on an index sorted on the field), addIndexes, soft deletes whose retention keeps nothing, or a document IndexWriter rejected. From then on every histogram search on that field throws, and the other segments' counts are lost too, until a merge folds the empty segment into one with values. It is loud and writes nothing wrong. The code dates from the class's introduction (#14204); every release from 10.2.0 to 10.6.0 and main is affected.

Mechanism (main f794ff5a505c)

#
  1. getLeafCollector (HistogramCollector.java:69-74): a segment without the field in its FieldInfos throws CollectionTerminatedException ("The segment has no values, nothing to do."). The merged segment has the field, so it goes on.
  2. :86-100: the point-tree bulk path, only for a match-all or point-range query on a segment with point values for the field; not taken here (with a field that also indexes points, the empty segment's getPointValues is null too, and the same exception follows). :102-105: a multi-valued field takes the naive collector; this field is single-valued.
  3. :107-116: the skipper is not null, so leafMinBucket = floorDiv(skipper.minValue(), w) and leafMaxBucket = floorDiv(skipper.maxValue(), w), and if (leafMaxBucket - leafMinBucket <= 1024) returns the dense HistogramLeafCollector. There is no docCount() test, and the check is one-sided, so any negative span passes.
  4. The constructor (:272-274) runs counts = new int[Math.toIntExact(leafMaxBucket - leafMinBucket + 1)]. With width 10: -922,337,203,685,477,581 - 922,337,203,685,477,580 + 1 = -1,844,674,407,370,955,160, so toIntExact throws ArithmeticException: integer overflow. For widths of 8,589,934,585 or more the length fits in an int but is negative, and the allocation throws NegativeArraySizeException (-2,147,483,648 at that width).
  5. The exception leaves IndexSearcher.search, so the counts of every other segment are lost as well.

Why the skipper is empty

#

Lucene90DocValuesConsumer starts the global bounds at Long.MIN_VALUE/Long.MAX_VALUE and asserts globalDocCount == 0 || globalMaxValue >= globalMinValue (Lucene90DocValuesConsumer.java:340), so a field with no values is written with the inverted pair. DocValuesSkipper.minValue()/maxValue() only promise bounds (DocValuesSkipper.java:83-97), and docCount() is "the global number of documents with a value for the field" (:99-100). The inverted pair is what the default codec writes and CheckIndex accepts, not a documented API value; docCount() == 0 is the reliable signal.

An SMT model (z3, exact Math.floorDiv semantics) proves the dense path safe for every non-empty skipper and every width >= 2 (1 to 1,025 counters, no long wrap), and broken for every legal width on the empty skipper, with the exception boundary above; both faces were checked on the stock jar.

Exposure and likelihood306 words
  • Who: applications that run the sandbox HistogramCollectorManager on a single-valued NUMERIC or SORTED_NUMERIC field with a skip index (NumericDocValuesField.indexedField, SortedNumericDocValuesField.indexedField or FieldType.setDocValuesSkipIndexType). The javadoc says the implementation "is optimized for the case when field is part of the index sort and has a skip index" (HistogramCollectorManager.java:39-40); the repro uses the skip index alone, without an index sort. Default codec and IndexWriterConfig. Without a skip index the naive collector runs and the bug does not occur.
  • What creates the state (each run on main, assertions off): deleting every valued document of a segment that keeps other documents, then forceMerge, or only a commit under the default TieredMergePolicy; addIndexes(CodecReader...) of a reader with such deletions; a soft update of the valued document under a SoftDeletesRetentionMergePolicy whose retention query keeps nothing, plus a merge; and, without an explicit delete or merge, a document IndexWriter rejected for an immense term in a field added before f (the rejected document stays in the segment as a deleted document). The delete-and-merge route also fails on an index sorted on the field. A single-valued SORTED_NUMERIC field fails the same way.
  • Effect: every histogram search on the field throws, match-all or not (a TermQuery fails too, and for a field that also indexes points, a point-range query), and the other segments' counts are lost, until a merge folds the empty segment into one with values. No wrong count is returned, nothing is written wrong, and CheckIndex reports the index clean.
  • Scale and likelihood: two documents are enough, but it needs both the sandbox collector on a skip-indexed field and a segment left with no value of it, typically when only some documents carry the field and all of those in one segment are deleted before it is merged. Rare; no report found (see the prior-report section).

Why it looks unintended

#
  • The manager computes "a histogram of the distribution of the values of a field"; a segment without the field is already "nothing to do".
  • Core writes, validates and tests this empty skip index on purpose.
  • In the #14204 review the <= 1024 check was accepted as the fallback that keeps the array size safe; a negative span passes it.
The full argument319 words
  • Contract. HistogramCollectorManager is a "CollectorManager that computes a histogram of the distribution of the values of a field" (HistogramCollectorManager.java:31). Besides a null check on field (:74), its only argument checks are bucketWidth >= 2 and maxBuckets >= 1 (:75-81). The sentence "optimized for the case when field is part of the index sort and has a skip index" (:39-40) describes an optimization, not a precondition. The repro has the skip index without an index sort; with an index sorted on the field it fails the same way.
  • Same collector. A segment without the field "has no values, nothing to do" (HistogramCollector.java:71-73); the same index without a skip index returns the empty histogram.
  • Core designs, validates and tests the empty skipper. The writer's assert (Lucene90DocValuesConsumer.java:340, from #13563); CheckIndex rejects minValue() > maxValue() only when docCount() > 0 (CheckIndex.java:3694); maxValueCount() "returns 0 if docCount() is 0" (DocValuesSkipper.java:107-111); globalMinValue/globalMaxValue start from Long.MAX_VALUE/Long.MIN_VALUE and fold with min/max (:145-184); and BaseDocValuesFormatTestCase#testNumberMergeAwayAllValuesWithSkipper (:151-183, added in #13487 on 2024-06-17, before the collector existed) builds this exact index, reads a non-null skipper and asserts its docCount() is 0.
  • History. In the #14204 review (2025-02-18) epotyom asked on this constructor: "Maybe fallback to HistogramNaiveLeafCollector instead of throwing ArithmeticException when array size overflows an int, to avoid this hidden limitation?", then: "Ah never mind, you already have it." So the reviewer accepted the span check as the fallback that keeps the array size from overflowing an int; the code comment on the check (HistogramCollector.java:112-114) gives its purpose as counting a few buckets in a dense array instead of a hash table. Neither covers a negative span.
  • Tests. TestHistogramCollectorManager never builds a segment that lists the field without values; its expectThrows cover only IllegalStateException (too many buckets, missing doc values).
The devil's-advocate check138 words

The strongest case: it is sandbox code with no stability promise; the javadoc says the collector is optimized for a field that is part of the index sort and has a skip index, so the dense path may assume every segment with a skipper has values; and DocValuesSkipper does not say what minValue()/maxValue() return when empty (open #15996 calls the class under-documented).

Why it fails: the code ships in every lucene-sandbox release from 10.2.0 to 10.6.0 and nothing says a search may fail on a valid index; the javadoc sentence sets no precondition, and the index-sorted case fails the same way; and core makes the empty skipper a deliberate, validated and tested state that docCount() identifies. A maintainer may prefer non-inverted bounds in core instead; that moves the fix, it does not make the exception intended.

#

Recommended A. Treat an empty skipper like a segment without the field (validated)

In HistogramCollector.getLeafCollector, throw CollectionTerminatedException when skipper.docCount() == 0, before the span is computed, as already done for a segment without the field. Validated: the repro passes with assertions on and off, the histograms package tests pass (8 tests), and :lucene:sandbox:check -x test passes.

A. Treat an empty skipper like a segment without the field (validated) (recommended)

#

Four lines in HistogramCollector.getLeafCollector, before the span is computed.

DocValuesSkipper skipper = context.reader().getDocValuesSkipper(field);
if (skipper != null) {
  if (skipper.docCount() == 0) {
    // The segment has the field, but no document has a value: nothing to do.
    throw new CollectionTerminatedException();
  }
  long leafMinBucket = Math.floorDiv(skipper.minValue(), bucketWidth);
  ...

Trade-offs

  • No API change and no cost on segments with values; it mirrors the existing "no values, nothing to do" exit (HistogramCollector.java:71-73) and keys on docCount() as CheckIndex does.
  • Leaves core's empty-skipper encoding as it is.

What the checks validated

  • Stock f794ff5a505c: the minimal test fails with assertions on and off.
  • With the fix: it passes with assertions on and off; the histograms package tests (TestHistogramCollectorManager, 7 tests, plus the new test) pass, 8 tests, 0 failures; ./gradlew :lucene:sandbox:check -x test (format, ecj lint, forbidden APIs) passes with the test in place.
  • Earlier, the same guard made eight further executed cases pass (five more ways to reach the state, both width faces and a TermQuery), and a two-segment index then returns {0: 1}.

B. Make the span check two-sided

#

if (leafMaxBucket >= leafMinBucket && leafMaxBucket - leafMinBucket <= 1024): an inverted range falls back to the naive single-valued collector, which finds no values.

Trade-offs

Also guards any other inverted bounds, but visits every matching document of a segment that has no values. Not run.

C. Report non-inverted bounds for an empty skipper in core

#

Change what minValue()/maxValue() return when docCount() is 0.

Trade-offs

Not recommended: the writer's assert, CheckIndex and globalMinValue/globalMaxValue rely on the inverted pair as the neutral element, so it is a wider change, and other consumers would still need to check docCount(). Not run.

Downstream note

#

A service that offers histograms on such a field fails those requests while the empty segment exists; it is a clean exception with no wrong result, and no request input causes or prevents it.

How it was found

#

Semi-formal: a model-based check ran every sequence of up to 4 index operations, plus seeded random sequences of 12, against a brute-force histogram; a random sequence hit the exception. Reduced to one JUnit test; an SMT solver proved the dense path safe for every non-empty skip index and broken for every bucket width on the empty one.

The method in full222 words

Method: model-based checking (bounded-exhaustive plus seeded random sequences), then SMT. A model-based check drove the stock jar through every sequence of up to 4 operations (adding one of five document shapes, deleting a document, an in-place doc-values update, reopening the reader, forceMerge(1)) in two writer configurations (no merges; an index sorted on the skip-indexed field), plus seeded random sequences of length 12, and after every step compared each histogram with a brute-force count over the live documents. The exhaustive part cannot reach this state (it takes at least five operations: two adds, a delete, a merge and a reopen of the checked reader); seeded random sequences hit it in both configurations, the first after 9 operations: the sandbox histogram collector threw ArithmeticException where the oracle expected an empty histogram.

The case was then reduced to one public-API JUnit test, and the bucket arithmetic was encoded in z3 with exact Math.floorDiv semantics: the dense path is safe for every non-empty skipper and width >= 2, and gives a negative array length for every legal width on the empty skipper, with ArithmeticException below width 8,589,934,585 and NegativeArraySizeException from it on (both checked on the stock jar). Eight further cases were then executed (five more ways to reach the empty segment, both width faces and a non-match-all query): all fail, none with the fix.
