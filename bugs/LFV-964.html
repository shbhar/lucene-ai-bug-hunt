GroupingSearch throws for groupLimit or groupDocsLimit = Integer.MAX_VALUE instead of returning all groups

Ask GroupingSearch for all groups with Integer.MAX_VALUE, which IndexSearcher.search accepts, and it throws NegativeArraySizeException: -2147483648 or an exception naming that number, even on a 1-document index. It never caps the limits at maxDoc, and it adds offset + limit in int; every release tested since 4.0.0 fails.

The finding in 30 seconds

#

The "give me everything" value that IndexSearcher.search accepts makes GroupingSearch throw. One document is enough:

Two things to know first

#
  1. GroupingSearch groups the hits of a query by a field value. search(searcher, query, groupOffset, groupLimit) returns one page of groups; setGroupDocsLimit(n) sets how many documents each group returns (default 1).
  2. Top-N collectors allocate their arrays for N up front. IndexSearcher.search(query, n) therefore caps n at maxDoc first, so Integer.MAX_VALUE ("all") is safe there; that cap fixed the same NegativeArraySizeException in 2009 (LUCENE-2119).

The finding, step by step

#
  1. You index 1 document whose group field g is a. IndexSearcher.search(q, Integer.MAX_VALUE) returns its 1 hit, and new GroupingSearch("g").search(searcher, q, 0, 1) returns 1 group.
  2. To get every group you pass Integer.MAX_VALUE as the limit: search(searcher, q, 0, Integer.MAX_VALUE). You expect the same 1 group; the javadoc calls the limit "the number of groups to return", with no upper bound.
  3. You get NegativeArraySizeException: -2147483648, with assertions on or off. The next page (offset 1) throws topNGroups must be >= 1 (got -2147483648), a number you never passed; setGroupDocsLimit(Integer.MAX_VALUE) fails too.
  4. Why: GroupingSearch hands the limit on unchanged, and the collector sizes an array by limit + 1 in int: 2147483647 + 1 wraps to -2147483648. IndexSearcher caps the count at maxDoc (here 1) before sizing anything; GroupingSearch never does.
  5. Below the wrap, the same missing cap costs memory: one search with groupDocsLimit = 10,000,000 allocated about 600 MB on a 20-document index.

Who is affected

#

Applications that group with GroupingSearch (the opt-in grouping module) and pass Integer.MAX_VALUE for all groups or all documents per group, or forward an uncapped page size. Every grouping mode; a 1-document index is enough. The search fails loudly; no wrong result observed. Workaround: for a valid offset and limit, cap both at maxDoc before the call, with the fix's rule.

Mechanism, terms and numbers591 words

GroupingSearch, the grouping module's convenience class, throws when the caller passes Integer.MAX_VALUE ("all") as groupLimit or as groupDocsLimit, although the same search with the limit set to reader.maxDoc() works and IndexSearcher.search(query, Integer.MAX_VALUE) works. With offset 0 the search throws NegativeArraySizeException: -2147483648, OutOfMemoryError: Requested array size exceeds VM limit or a queue-size IllegalArgumentException; with offset 1 it throws IllegalArgumentExceptions that name a value the caller never passed: "topNGroups must be >= 1 (got -2147483648)", "numHits must be > 0" or "maxDocsPerGroup must be >= 1 (got -2147483648)". Every grouping mode fails (term, function, term with caching enabled, the Supplier constructor, doc block), with assertions on and off; a large finite limit such as 10,000,000 does not throw but allocates memory in proportion to the limit. The cause is one missing cap: GroupingSearch hands the caller's offsets and limits unchanged to collector managers that add offset + limit in int and pre-size their queues and comparators by the limit, while IndexSearcher caps the count at maxDoc since LUCENE-2119 (2009). No silently wrong result was observed in 21,040 differential searches. Every release tested since 4.0.0 (2012) fails, as does main; capping the limits at maxDoc in GroupingSearch fixes it, and the grouping module's tests pass with that change.

Exposure and likelihood316 words
  • Who is exposed. Applications that use GroupingSearch and pass Integer.MAX_VALUE as groupLimit or groupDocsLimit to mean "all", or forward an uncapped user-chosen page size or offset. Term, function, cached and doc-block grouping all fail; the default groupDocsLimit is 1, so the per-group path needs an explicit setGroupDocsLimit.
  • What happens. That search throws an unchecked exception instead of returning the groups; with offset 1 or more the message names a value the caller never passed. No silent wrong result was observed in 21,040 differential searches, and the index does not change.
  • Scale. None for Integer.MAX_VALUE: a 1-document index is enough. Large finite limits cost memory in proportion to the limit (about 600 MB for groupDocsLimit = 10,000,000 on a 20-document index).
  • Versions. Every release tested from 4.0.0 (2012) to 10.6.0 fails, and main; releases not run are inferred affected (the same int sums in every tag read, no capping commit).
  • How likely. Rare: it fails on the first call, so developers who try this value switch to a finite value; Lucene's own DatasetSplitter passes setGroupDocsLimit(originalIndex.maxDoc()), and no public report was found.
  • Workaround. For a valid offset and limit (offset >= 0, limit >= 1), cap both before the call, with the rule of the fix: maxDoc = Math.max(1, reader.maxDoc()), offset = Math.min(offset, maxDoc), limit = Math.max(1, Math.min(limit, maxDoc - offset)), for the group page and for setGroupDocsOffset / setGroupDocsLimit. Leave other values as they are (or validate them first), as the fix does; applied to limit 0 or a negative limit, the formula would turn it into 1 instead of letting the API reject it. Capping only the limit (Math.min(limit, reader.maxDoc())) is not enough: a large offset still wraps offset + limit (e.g. offset Integer.MAX_VALUE - 1 with limit 20), and an empty index gives limit 0, which the API rejects ("topNGroups must be >= 1 (got 0)").

Why it looks unintended

#
  • The javadoc calls groupLimit "The number of groups to return from the specified group offset", with no bound, and every failing value passes the API's own checks.
  • "topNGroups must be >= 1 (got -2147483648)" blames the caller for a number Lucene computed by overflowing int.
  • Core fixed the same symptom as a bug: LUCENE-2119 caps IndexSearcher.search at maxDoc.
The full argument208 words
  • No documented bound. groupLimit: "The number of groups to return from the specified group offset" (GroupingSearch.java:123); groupDocsLimit: "The number of documents to return inside a group" (:321). No javadoc, package doc, CHANGES or MIGRATE entry limits them, and every failing value passes the API's own checks (FirstPassGroupingCollectorManager.java:92-97, BlockGroupingCollectorManager.java:112-128).
  • The wrapped values have no rationale. "topNGroups must be >= 1 (got -2147483648)" and "maxDocsPerGroup must be >= 1 (got -2147483648)" report sums that Lucene computed (FirstPassGroupingCollectorManager.java:110, BlockGroupingCollectorManager.java:143, GroupingSearch.java:235).
  • Core precedent. lucene/CHANGES.txt, Bug fixes of 2.9.3 / 3.0.2: "LUCENE-2119: Don't throw NegativeArraySizeException if you pass Integer.MAX_VALUE as nDocs to IndexSearcher search methods." The fix is the cap at IndexSearcher.java:588/:597; FacetsCollectorManager and DrillSideways cap the same way.
  • Integer.MAX_VALUE per group was made to work elsewhere. In LUCENE-4832 (#5897, 4.3.0), Michael McCandless asked in review "Could we just fix it so passing in Integer.MAX_VALUE for maxDocsPerGroup works?" for the join module's ToParentBlockJoinCollector, and the committed fix capped it with the group size.
  • The module's grouped-facet test (the grouped-facet API, not GroupingSearch) passes Integer.MAX_VALUE as a limit and guards the offset + limit sum itself (TestTermGroupFacetCollectorManager.java:106-118); no upstream test asserts the exception.
The devil's-advocate check161 words

The strongest case for "intended": the LUCENE-2119 issue text (#3195) calls Integer.MAX_VALUE "a nonsense value to pass in, since our PQ impl allocates the array up front"; core documents that TopScoreDocCollectorManager instances "pre-allocate a full array of length numHits"; no Lucene doc says that Integer.MAX_VALUE means "all" for these limits, and no index can hold that many documents (IndexWriter.MAX_DOCS is smaller); GroupingSearch is @lucene.experimental; the defaults are safe; Solr caps in its own layer; and the doc-block offset-0 case already gives an honest queue-size message.

Why it fails: LUCENE-2119 itself was resolved as a bug by capping in the convenience layer, and GroupingSearch is the convenience layer for grouping, which sizes the collectors on the caller's behalf; the pre-allocation note is on the core collector managers, not on GroupingSearch's limits; and no design reading explains an exception that names -2147483648. The defence fits the memory cost of large finite limits best, so present that part as secondary.

Suggested fix

#

Recommended A. Cap the offsets and limits at maxDoc in GroupingSearch (validated)

Cap the offsets and limits at maxDoc inside GroupingSearch, as IndexSearcher.search does: offset' = min(offset, maxDoc), limit' = max(1, min(limit, maxDoc - offset')), for groups and for documents per group. Validated: the repro passes with assertions on and off, all 57 grouping-module tests pass, and all 21,040 differential searches match an exact reference.

All options and trade-offs3 options · 930 words

Option A fixes every GroupingSearch caller. Code that builds the collector managers directly still gets the wrapped sums; option B covers it and can be added to A. No CHANGES entry is drafted.

A. Cap the offsets and limits at maxDoc in GroupingSearch (validated) (recommended)

#

In GroupingSearch.search, cap groupOffset and groupLimit; for the documents per group, pass capped groupDocsOffset and groupDocsLimit to TopGroupsCollectorManager and BlockGroupingCollectorManager. Invalid values (negative offset, limit < 1) pass through unchanged, so they behave exactly as today: the group-page checks reject them, and invalid per-group values give the same result with and without the patch. +29/-4 lines in GroupingSearch.java. B. Checked or saturating sums in the collector managers (not run)

#

Make the offset + limit sums in FirstPassGroupingCollectorManager.newCollector, TopGroupsCollectorManager.newCollector, BlockGroupingCollectorManager.newCollector and GroupingSearch.groupByDocBlock overflow-safe: reject offset > Integer.MAX_VALUE - limit in the constructors with a clear message, or saturate the sum.

Trade-offs

Removes the misleading -2147483648 messages for every caller, but on its own does not make "all" work: the first-pass collector still computes topNGroups + 1, and the queues are still pre-sized by the limit. Best as a complement to A.

C. Document and validate an upper bound (not run)

#

State in the javadoc of search and setGroupDocsLimit that the limits pre-allocate and must not exceed maxDoc, and reject larger values with a clear message.

Trade-offs

Honest, but callers still need their own cap, and it differs from IndexSearcher.search, which accepts Integer.MAX_VALUE.

Downstream note

#

A service that forwards a user-chosen group page size or offset to GroupingSearch without capping it fails that request (or allocates in proportion to the size); Solr caps these sums in its own grouping layer.

How it was found

#

Code reading left the grouping module's int offset + limit sums as a lead, and a probe on main showed the -2147483648 exceptions. A public-API JUnit, a differential check of 21,040 grouped searches against an exact reference (0 silent mismatches) and a z3 model of the eight int size sites followed.

The method in full194 words
  • First signal (non-formal). Code reading of the PriorityQueue / TopDocs.merge area (2026-10-26) noted the grouping module's int offset + limit sums as a lead without running them; a planning probe on 2026-10-28 ran them on main, 10.5.2 and branch_10_6 and showed NegativeArraySizeException: -2147483648 and "topNGroups must be >= 1 (got -2147483648)".
  • Then (semi-formal). A public-API JUnit (term and doc-block grouping x groupLimit or groupDocsLimit = Integer.MAX_VALUE x offset 0 or 1, each compared with the same search at limit maxDoc): 8 of 8 fail. A bounded-exhaustive differential harness against an exact long-arithmetic reference: 6 seeded indexes of 2-15 documents in 1-3 segments, 5 grouping modes, field and relevance sorts, sequential and executor searchers, a boundary grid of offsets and limits: 21,040 searches, 7,872 agree, 13,168 throw, 0 silent mismatches; 21,040 of 21,040 agree with the cap. A z3 bit-vector model of the 8 int size sites: a wrap witness at every site, the wrap region is exactly offset + limit >= 2^31, and, in an abstract model of the group window, the cap is proved result-preserving and overflow-free; two fix mutants refuted.
  • The repro was later minimized to the one test above.

LFV-964, snapshot of 2026-11-09

Registry title
GroupingSearch with groupLimit or groupDocsLimit = Integer.MAX_VALUE ('all remaining groups/documents') throws NegativeArraySizeException, OutOfMemoryError or an IllegalArgumentException naming -2147483648, because it does not cap the limits at maxDoc as IndexSearcher.search does and its collectors add offset + limit in int (every release since 4.0.0)
Area
grouping / GroupingSearch (term, function, cached two-pass and doc-block grouping) x the first-pass, TopGroups and block collector managers
Priority
Low, rank 654: GroupingSearch fails loudly on the usual Integer.MAX_VALUE 'all' idiom in a module and never returns wrong groups, like its UnifiedHighlighter MAX_VALUE sibling LFV-438.
Impact class
wrong error
Impact note
Hits applications on every release from 4.0.0 to 10.6.0 and on main that pass a 'no limit' value such as Integer.MAX_VALUE as GroupingSearch's groupLimit (search) or groupDocsLimit (setGroupDocsLimit), with default settings in every grouping mode and with -ea or -da: the search throws instead of returning the groups, and with an offset of 1 or more the exception names a value the caller never passed (-2147483648); large finite limits allocate memory in proportion to the limit, not to the index (about 600 MB for groupDocsLimit = 10,000,000 on a 20-document index); the failure is loud on the first such search, no result is ever silently wrong, and capping the limit at reader.maxDoc() avoids it.
Summary
You call GroupingSearch.search(searcher, query, 0, Integer.MAX_VALUE) or setGroupDocsLimit(Integer.MAX_VALUE) to get every group, or every document of each group, and expect the same TopGroups as with a limit of maxDoc, the way IndexSearcher.search(query, Integer.MAX_VALUE) returns every hit. Instead the search throws: with offset 0 a NegativeArraySizeException -2147483648, an OutOfMemoryError 'Requested array size exceeds VM limit' or a queue-size IllegalArgumentException, and with offset 1 an IllegalArgumentException such as 'topNGroups must be >= 1 (got -2147483648)' or 'numHits must be > 0'. GroupingSearch hands the limits on uncapped to collectors that add offset + limit in int and pre-size their queues by the limit; nothing is ever returned wrong.
