The merge-time postings view reuses a PostingsEnum from an earlier merge and numbers documents with that merge's doc maps

A custom postings format that passes a PostingsEnum kept from an earlier merge back as the reuse hint gets it back still numbering documents the earlier merge's way: [0, 1, 1] instead of [0, 1, 2], or an ArrayIndexOutOfBoundsException. Lucene's own formats never do this, so only custom codec code is hit, in every release since 5.0.0.

The finding in 30 seconds

#

The merged view reuses an enum when the field name matches, but the enum's doc maps (here simply where each old segment starts in the new one) were fixed when it was built, for the merge it was built in. Handed in from another merge, it renumbers the new merge's documents with the old maps.

Background in three steps

#
  1. A merge copies several segments into one new segment and renumbers their documents: each old segment gets a doc map, here simply a start offset (segments of 2 and 1 documents start at 0 and 2).
  2. A postings format writes postings in FieldsConsumer.write(Fields, ...). At a merge, the default FieldsConsumer.merge passes MappedMultiFields, a view over the old segments that applies those doc maps.
  3. TermsEnum.postings(reuse, flags) may recycle a PostingsEnum you pass as reuse instead of allocating a new one. It is only a hint: the result must be the same as with reuse = null.

The finding, step by step

#
  1. A custom postings format wraps the default one. During each merge its write() reads term f:t from the merged view and keeps the PostingsEnum in an instance variable, to pass back as reuse in the next merge.
  2. Merge 1 joins two 1-document segments; in the new segment their documents start at 0 and 1. Merge 2 joins a 2-document and a 1-document segment, which start at 0 and 2.
  3. You expect merge 2's postings to be [0, 1, 2], the same as with reuse = null: reuse is only a hint.
  4. You get [0, 1, 1]. The view accepts the old enum because the field name matches and resets it onto merge 2's segments, but the enum still uses merge 1's starts (0 and 1). If merge 2 has more segments than merge 1, it throws ArrayIndexOutOfBoundsException instead and the merge fails.

Who is affected

#

Only a custom postings format that keeps the default merge, reads postings from the merged view in write(), and passes an enum kept from an earlier merge as reuse for the same field. Three documents suffice. Lucene's own formats keep their reuse enum for one write, so stock codecs and indexes are unaffected.

Mechanism, terms and numbers507 words

When segments merge, the default FieldsConsumer.merge hands the postings format's write() a MappedMultiFields view that renumbers every document into the new segment. Its postings(reuse, flags) recycles any MappingMultiPostingsEnum whose field name matches, but that enum's per-segment doc maps were fixed, in its constructor, for the merge it was built in. A postings format that keeps an enum from one merge and passes it back as the reuse hint in a later merge gets the same object back, reset onto the new merge's segments but still numbering them with the old merge's doc maps: wrong doc ids with no error ([0, 1, 1] instead of [0, 1, 2] in the repro; ids can also go backwards or past maxDoc), or an ArrayIndexOutOfBoundsException when the new merge has more segments.

Lucene's own postings writers keep their reuse enum for one segment write only, so stock codecs and indexes are unaffected. The defect dates from LUCENE-5123 (first release 5.0.0). The fix is a reference compare: remember the MergeState in the enum and reuse it only for the same one.

The mechanism (main 5adff78bb168)

#
  1. FieldsConsumer.merge (codecs/FieldsConsumer.java:72-96) builds new MappedMultiFields(mergeState, new MultiFields(...)) and calls write(mergedFields, norms) (:91-95). Every FieldsConsumer that keeps the default merge() gets this view; PerFieldPostingsFormat creates one consumer per format per merge (codecs/perfield/PerFieldPostingsFormat.java:189-191).
  2. MappingMultiPostingsEnum's constructor (index/MappingMultiPostingsEnum.java:56-63) fixes, for that merge, allSubs, one sub per old segment holding mergeState.docMaps[i] (:58-61), and a DocIDMerger sized and typed for it (:62). It does not keep the MergeState.
  3. MappedMultiTermsEnum.postings(reuse, flags) (index/MappedMultiFields.java:117-134) reuses the enum when reuse instanceof MappingMultiPostingsEnum postings and postings.field.equals(this.field) (:119-121). Nothing compares the merge. Fix site.
  4. The inner MultiTermsEnum reuses only its own enum (canReuse(this), an identity check, index/MultiTermsEnum.java:319-324, index/MultiPostingsEnum.java:54-56), so the new merge's segment postings are right. reset(...) (MappedMultiFields.java:132; MappingMultiPostingsEnum.java:65-77) then picks allSubs[subsArray[i].slice.readerIndex()] (:71) with the new merge's segment indexes: each new segment is renumbered with the old merge's doc map for that index, and an index past the old allSubs throws.

The numbers

#

Merge 1 joins two 1-document segments: doc bases 0 and 1. Merge 2 joins the 2-document result and a new 1-document segment: doc bases 0 and 2. The reused enum maps merge 2's second segment with base 1, so f:t lists [0, 1, 1] instead of [0, 1, 2]. Other sizes, in the independent tests, give ids that go backwards ([0, 1, 2, 3, 1] for [0, 1, 2, 3, 4], merge 1 over 1+3 documents, then 4+1) or past maxDoc ([0, 3, 4, 5] in a 4-document segment); a merge 2 with 3 segments after a merge 1 with 2 throws ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 2 at MappingMultiPostingsEnum.reset (:71). The default writer underneath pulls its own enums, so the segment it writes is correct (the diagram's probe read the merged segment back: [0, 1, 2]); only the custom code's own read is wrong.

Exposure and likelihood268 words
  • Who is hit: a custom PostingsFormat (public, @lucene.experimental extension API) whose FieldsConsumer keeps the default merge(), pulls postings from the merged Fields in write(), and keeps an enum beyond one segment write (for example in an instance variable of the format) to pass back as reuse. No scale or special document content is needed; the wrong ids need a segment position whose doc map differs between the two merges (the normal case), and the repro fixes merge order and scheduling only to make that deterministic.
  • Not hit: stock codecs. Every non-sandbox Lucene FieldsConsumer keeps its reuse enum in a local or a per-instance field, i.e. for one segment write (for example codecs/PushPostingsWriterBase.java:42, :125); the reviews checked SimpleText, Bloom, Completion and the test-framework Asserting and RAMOnly formats the same way. Downstream codecs were not surveyed.
  • Effect: in the merge that receives the stale enum, that custom code sees wrong doc ids with no error, or the merge fails with ArrayIndexOutOfBoundsException. Whether wrong postings reach a written segment depends on what the custom code does with them.
  • How likely: contrived. Such a cache is unusual. A naive one that write() also fills at flush time is replaced by a flush-time enum, which fails the instanceof check (read from the code), but back-to-back or cascading merges have no flush in between. Under the default ConcurrentMergeScheduler a shared cache needs synchronization or a per-thread copy, and either can still carry an enum from one merge to the next. No public report was found in the searches listed under Prior reports (the code dates from 5.0.0, 2015).

Why it looks unintended

#
  • TermsEnum.postings documents reuse only as a hint ("pass a prior PostingsEnum for possible reuse"), with no rule on where the enum came from.
  • In the same call the inner MultiTermsEnum reuses only its own enum; this check compares the field but not the merge.
  • Before 5.0 the merge code rebound its cached enum to each new merge (setMergeState).
The full argument246 words
  • Contract. @param reuse pass a prior PostingsEnum for possible reuse (index/TermsEnum.java:151, :166). FieldsConsumer.write lists the limits of the Fields it is given (no statistics/counts, no non-null live docs, codecs/FieldsConsumer.java:59-61); reuse is not among them. An intended-behaviour review found no javadoc, MIGRATE.md or CHANGES.txt entry and no test that restricts where a reuse enum may come from.
  • Siblings check the source. MultiTermsEnum.postings reuses only an enum "previously created w/ this MultiTermsEnum" (index/MultiTermsEnum.java:319-324); FreqProxFields, the flush-time Fields handed to the same write(), reuses only when postingsArray is identical (index/FreqProxFields.java:242-246, :262-266).
  • The check is half there. LUCENE-6382 (82b3106f6c3, 5.2.0, "enforce max allowed indexed position") gave the enum a field name for its position-limit errors and, with it, a field-name comparison before reuse. So the method already refuses one kind of foreign enum (another field's); no commit ever compared the other thing the enum is bound to, the merge.
  • History. On 4.x the merge code called setMergeState(mergeState) on its cached mapping enum at the start of every merge (codecs/TermsConsumer.java:99, :127, :154, :181 at 4.10.4). LUCENE-5123 moved the binding into the constructor; no commit message or issue discussion says cross-merge reuse was given up. The removed Terms.iterator(TermsEnum reuse) javadoc put the decision on the implementation: "If you have a previous TermsEnum, for example from a different field, you can pass it for possible reuse if the implementation can do so" (index/Terms.java:39-42 at 5.1.0).
The devil's-advocate check207 words

The strongest case for "intended" or misuse: MappedMultiFields is @lucene.internal and FieldsConsumer @lucene.experimental; Lucene creates one consumer per merge, so within Lucene only the field can differ, which is what the check covers; the carried enum belongs to a merge whose readers are closed; "a prior PostingsEnum" could be read as "one this enum returned". A maintainer may fairly answer "don't keep enums across write() calls". An independent cross-model reviewer rated this case moderate.

Why it fails: nothing found documents that restriction; the method already refuses another field's enum; the inner layer of the very same call already rejects this enum; and reset() points every sub it uses at the new merge's postings, so from the next nextDoc() on, the enum reads the new merge's postings through the old merge's doc maps, the state the check forgets. (reset() also leaves the last positioned sub, current, in place until that nextDoc(), within one merge too; that is LFV-1303, not this bug.) What survives is a likelihood argument, which is why it is Low.

This is hardening: MappedMultiFields is @lucene.internal and the enum class package-private, so this is defensive behaviour at an internal boundary that the public codec API reaches, not a broken public promise.

Suggested fix

#

Recommended A: reuse only an enum built for the same MergeState (recommended)

Keep the MergeState in MappingMultiPostingsEnum and reuse the enum only when it was built for the same one: postings.field.equals(this.field) && postings.mergeState == this.mergeState. +3/-1 lines; reuse with the same MergeState object, i.e. every reuse inside one default merge() call, is unchanged. Validated with the repro and the closest merge and postings suites.

// MappingMultiPostingsEnum
final MergeState mergeState;
// constructor:
this.mergeState = mergeState;

// MappedMultiFields.MappedMultiTermsEnum.postings(reuse, flags)
if (postings.field.equals(this.field) && postings.mergeState == this.mergeState) {

A: reuse only an enum built for the same MergeState (recommended) (validated by the checks)

#

In MappingMultiPostingsEnum add final MergeState mergeState; and set it in the constructor; in MappedMultiTermsEnum.postings(reuse, flags) require postings.mergeState == this.mergeState next to the field check. An enum from another merge is then replaced by a new one, as MultiTermsEnum already does for its inner enum.

// MappingMultiPostingsEnum
final MergeState mergeState;
// constructor:
this.mergeState = mergeState;

// MappedMultiFields.MappedMultiTermsEnum.postings(reuse, flags)
if (postings.field.equals(this.field) && postings.mergeState == this.mergeState) {

Trade-offs

  • One reference compare per postings() call; no benchmark was run.
  • A custom format that carries enums across merges loses the reuse (it gets a new enum), which is the correct outcome.
  • Reuse with the same MergeState object is unchanged; each default merge() call builds one MappedMultiFields over one MergeState (codecs/FieldsConsumer.java:91-95), so every reuse inside it is kept.
  • The enum then keeps the whole MergeState reachable for as long as a caller keeps the enum; today it keeps that merge's doc maps and per-segment postings enums through allSubs (MappingMultiPostingsEnum.java:35, :58-61, :72). Keeping and comparing only mergeState.docMaps would avoid the extra reference (not run).

B: rebind the enum on reuse

#

Give reset() the MergeState and rebuild allSubs and the DocIDMerger when it differs, as the 4.x code did with setMergeState.

Trade-offs

Keeps reuse across merges, but more code and the final fields become mutable, for a case Lucene itself never exercises. Not run.

C: document the limit only

#

Say in FieldsConsumer.write's javadoc that enums pulled from the given Fields must not be passed as reuse after write() returns.

Trade-offs

No code change, but the wrong ids stay silent and the check stays weaker than its siblings. Not recommended.

Downstream note

#

Relevant downstream only to custom postings formats: keep any PostingsEnum pulled from the merged view for that one write() call, as Lucene's own formats do.

How it was found

#

Semi-formal: a proof-obligation check of MappedMultiTermsEnum.postings(reuse, flags) against the reuse contract, that a reused enum gives the same postings as a new one. The obligation fails when the reuse enum was built for another merge; a one-test JUnit repro on stock main witnessed it.

The method in full78 words
  • Obligation: for any reuse the method accepts, the returned enum lists the same documents as postings(null, flags) (TermsEnum.java:151, :166).
  • Finding: the accept condition (MappedMultiFields.java:119-121) depends only on the field, while the accepted enum's doc maps depend on the merge (MappingMultiPostingsEnum.java:56-63); reset() does not rebind them (:65-77).
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

LFV-1305, snapshot of 2026-11-08

Registry title
The merge-time postings view (MappedMultiFields) accepts a PostingsEnum built for an earlier merge as the reuse hint, because MappedMultiTermsEnum.postings(reuse, flags) compares only the field name and not the MergeState; the reused MappingMultiPostingsEnum keeps the earlier merge's per-segment doc maps, so a postings format that passes such an enum back gets wrong doc ids ([0, 1, 2, 3, 1] instead of [0, 1, 2, 3, 4]) or an ArrayIndexOutOfBoundsException (every release since 5.0.0)
Area
core / index: merge-time postings view (MappedMultiFields, MappingMultiPostingsEnum) that FieldsConsumer.merge hands to FieldsConsumer.write
Priority
Low, rank 1218: The merge-time postings view accepts a PostingsEnum from an earlier merge as a reuse hint and keeps that merge's doc maps, so the consumer sees wrong doc ids or an ArrayIndexOutOfBoundsException, in every release since 5.0.0. Only a custom postings format that keeps an enum across segment writes and passes it back can hit it, which no Lucene codec does, so it is contrived.
Impact class
minor
Impact note
Hits only applications with a custom postings format whose FieldsConsumer.write pulls postings from the merged Fields and passes a PostingsEnum kept from an earlier segment write back as the reuse hint: in that merge the consumer sees wrong doc ids with no error, out of order or beyond maxDoc [exec], or an ArrayIndexOutOfBoundsException that fails the merge when the new merge has more segments than the earlier one [exec]; whether wrong postings reach the written segment depends on that custom code; every non-sandbox Lucene FieldsConsumer keeps its reuse enum for one segment write only [read], so stock codecs, indexes and search results are unaffected; any index size, single thread.
Summary
You write a postings format whose FieldsConsumer.write pulls postings from the Fields that a merge hands it, keep the PostingsEnum it returned, and pass that enum back as the reuse hint in a later merge. You expect the result to list the same documents as a fresh enum, since TermsEnum.postings documents reuse only as a hint ('pass a prior PostingsEnum for possible reuse'). Instead MappedMultiFields accepts the old enum because only the field name matches, resets it against the earlier merge's per-segment doc maps and returns wrong doc ids ([0, 1, 2, 3, 1] instead of [0, 1, 2, 3, 4] in the repro), or throws ArrayIndexOutOfBoundsException when the new merge has more segments; no Lucene codec passes an enum from one merge into another, so only such custom codec code is affected.
