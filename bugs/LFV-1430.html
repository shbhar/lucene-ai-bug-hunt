addIndexes(CodecReader...) output is kept in heap by NRTCachingDirectory, whatever its size

IndexWriter.addIndexes(CodecReader...) opens its merged segment's files with merge size -1 ("unknown"), which NRTCachingDirectory reads as tiny: the merged segment stays in heap until the next commit, ignoring maxMergeSizeMB. With a 1 MB limit a 2.1 MB addIndexes caches all 2.1 MB; past the free heap, OutOfMemoryError closes the writer.

The finding in 30 seconds

#

IndexWriter tells the directory how big each new file's segment will be; for addIndexes(CodecReader...) it says -1, and NRTCachingDirectory takes -1 as "tiny".

NRTCachingDirectory in two steps

#
  1. NRTCachingDirectory wraps a disk directory and keeps small new files in a heap cache, so near-real-time readers can open fresh segments without disk I/O. commit() writes the cached files to disk and frees the heap.
  2. When IndexWriter creates a file, it passes an IOContext that says whether the file belongs to a flush or a merge and how large that segment is expected to be. The cache uses that size to decide: up to maxMergeSizeMB goes to heap, anything bigger to disk.

The finding, step by step

#
  1. Wrap a disk directory in new NRTCachingDirectory(fsDir, 1.0, 60.0): new files of flushes and merges whose estimated size is up to 1 MB are kept in heap while the cache holds at most 60 MB, bigger ones are written to disk (both checked when a file is created).
  2. Call writer.addIndexes(codecReader) with a small index: one document with a 2 MiB stored field. The merged segment is about 2.1 MB.
  3. You expect it on disk: 2.1 MB is above the 1 MB limit, and flushes, forceMerge(1) and addIndexes(Directory...) of large segments do go to disk (0 bytes cached in the probes).
  4. Instead ramBytesUsed() is 2,107,555 bytes, all of it, until the next commit: IndexWriter opened every file with merge size -1, and NRTCachingDirectory checks -1 <= 1 MB, which is always true.
  5. Nothing bounds it: about 100 MB added with the javadoc's own (5.0, 60.0) caches 105 MB, and 120 MB added on a 64 MB heap throws OutOfMemoryError in the merge and closes the writer; a plain FSDirectory adds the same 120 MB fine.

Who is affected

#

Applications that wrap their directory in the opt-in NRTCachingDirectory and call addIndexes(CodecReader...) to import, merge or split indexes, with default settings. The merge's outputs stay in heap until the next commit (in the executed runs, all or nearly all of the segment); past the free heap the merge throws OutOfMemoryError and the writer closes. Other writes are not affected.

Mechanism, terms and numbers546 words

NRTCachingDirectory keeps a newly created file in a heap cache only if it is a flush or a merge whose estimated size is at most maxMergeSizeMB, and only while the cache holds at most maxCachedMB; it reads the estimate from the IOContext the writer opens the file with. IndexWriter.addIndexes(CodecReader...) opens every output of its merge with IOContext.merge(new MergeInfo(numDocs, -1, false, ...)) (IndexWriter.java:3520-3522), where -1 stands for "size not known". doCacheWrite takes -1 as a size and -1 <= maxMergeSizeBytes holds for any non-negative limit (NRTCachingDirectory.java:235-244), so every output of that merge created while the cache is within maxCachedMB goes into the heap cache (in the test, the whole merged segment) and stays there until the next commit or close().

With (1.0, 60.0) a 2 MiB document's segment caches 2.1 MB; with the class javadoc's (5.0, 60.0) about 100 MB added caches 105 MB; 120 MB added on a 64 MB heap throws OutOfMemoryError in the merge and the writer closes as tragic (by reading, a tragic close rolls back its uncommitted changes), while a plain FSDirectory succeeds. Flushes, normal merges and addIndexes(Directory...) pass real size estimates, so the size rule applies to them. LUCENE-9115 (8.5.0) made NRTCachingDirectory refuse files of unknown size, but only when the context carries no size information at all; since 10.6.0 IOContext.merge() with a null MergeInfo is the documented "unknown size", which IndexWriter does not use here. All 20 executed releases from 3.2.0 to 10.6.0 and main are affected (before 5.0.0 through addIndexes(IndexReader...); the releases in between by reading).

Exposure and likelihood275 words
  • Who is hit. Any application that combines the two public APIs: NRTCachingDirectory (opt-in, @lucene.experimental) and IndexWriter.addIndexes(CodecReader...). Default IndexWriterConfig and codec, no special data. By reading only (not executed): Solr's default directory factory is NRTCachingDirectoryFactory (maxMergeSizeMB 4, maxCachedMB 48), and its shard split and merge-indexes paths call addIndexes(CodecReader...).
  • What goes wrong. Every output of that merge created while the cache is within maxCachedMB stays in heap until the next commit, whatever its size. With more data than free heap, the merge throws OutOfMemoryError and IndexWriter closes as tragic (probe: 120 MB added with a 64 MB heap gives the error, getTragicException() set and isOpen() false; a plain FSDirectory with the same heap succeeds). By reading, a tragic close rolls the writer back (IndexWriter.java:6095-6103), so its uncommitted changes are lost; the probe did not inspect the index afterwards.
  • Scale. The heap held is the outputs of the merge created while the cache was within maxCachedMB: in the three executed sizes the whole merged segment (2.1 MB and 8.2 MB) or all but its small files (105 MB in _0.fdm, _0.fdt and _0.fdx; .fnm and .si went to disk), with no bound from either limit.
  • Not affected. addIndexes(Directory...), flushes, normal and forced merges (they pass real size estimates, so the size rule applies; the flush, forceMerge(1) and addIndexes(Directory...) controls cached nothing), and applications without NRTCachingDirectory.
  • How likely. Plausible: every call hits it, nothing unusual is needed. Several Solr reports of heap exhaustion inside IndexWriter.addIndexes during shard split and merge-indexes (SOLR-5214, SOLR-5808, solr-user threads 2013-2018) fit the symptom, but none was diagnosed, so they are probable sightings, not proof.

Minimal repro

#

One JUnit test method in org.apache.lucene.store: one document with a 2 MiB random stored field (Random(0)), addIndexes of its CodecReader into a writer on NRTCachingDirectory(FSDirectory, 1.0, 60.0), then a check that at most 1 MiB is cached. Deterministic; no threads of its own (the merge runs on the merge scheduler's thread). Fails on main with assertions on and off.

Expected
At most 1 MiB cached: the 2.1 MB merged segment is above maxMergeSizeMB 1.0 and goes to disk.
Observed
AssertionError: cached 2107555 bytes: the whole segment is in the heap cache (assertions on and off; 10.6.0 and 9.12.3 too).

All files of this repro: repro/LFV-1430/

More files, environment, full output218 words

Default IndexWriterConfig on both writers, public API only; the only test-framework use is LuceneTestCase and createTempDir(). The project's applyGoogleJavaFormat leaves the file unchanged. The same file fails unchanged on the 10.6.0 and 9.12.3 jars (2,107,260 and 2,107,259 bytes cached). Why it looks unintended

#
  • The javadoc caches a merge only if "the estimated size of the merged segment is <= maxMergeSizeMB" (NRTCachingDirectory.java:92-95); -1 is not a size.
  • LUCENE-9115 (8.5.0): "NRTCachingDirectory no longer caches files of unknown size"; 10.6.0 documents a null MergeInfo as the unknown size.
  • LUCENE-5724 fixed the same symptom as a bug: compound files cached "when it shouldn't, then causing OOMEs".
The full argument261 words
  • Contract. Constructor javadoc: "We will cache a newly created output if 1) it's a flush or a merge and the estimated size of the merged segment is <= maxMergeSizeMB, and 2) the total cached bytes is <= maxCachedMB" (NRTCachingDirectory.java:92-95). Class javadoc: it caches "all merges whose expected segment size is <= 5 MB, unless the net cached bytes exceed 60 MB" (:59-61).
  • Stated intent for unknown sizes. LUCENE-9115 (#10156, commit 7ad33c3a98a "NRTCachingDirectory shouldn't cache files of unknown size."; lucene/CHANGES.txt:6091), with TestNRTCachingDirectory.testUnknownFileSize asserting that a context without size is not cached. Since 10.6.0 (#16749) IOContext.merge() is the merge context "when the caller does not know how large the merge is", with mergeInfo() null (IOContext.java:83-89, :160-163), which doCacheWrite refuses. MergeInfo documents no sentinel ("These values are only estimates", MergeInfo.java:19-26).
  • Precedent. The same symptom (a file cached that the size rule should have kept on disk) was fixed as a bug three times: 4.0.0 ("NRTCachingDirectory was always caching a newly flushed segment in RAM, instead of checking the estimated size of the segment", CHANGES.txt:15196-15198), LUCENE-5724 (4.9.0, CHANGES.txt:12387-12390) and LUCENE-9115.
  • No test or doc allows it. No upstream test adds indexes through NRTCachingDirectory with a size check; the addIndexes javadoc speaks of temporary disk space, not heap. (The test framework's newDirectory() now and then wraps its directory in NRTCachingDirectory with random limits below 1 MB, LuceneTestCaseParent.java:2150-2151, :2269-2273, and TestAddIndexes uses newDirectory() on 63 lines, so upstream tests have probably run this path at times, without checking what was cached.)
The devil's-advocate check248 words

The strongest case for "intended": when IOContext was designed (LUCENE-2793, #3867, 2011), s1monw proposed exactly this best-effort context for addIndexes, new MergeInfo(numDocs, -1, true, false), and wrote that "nobody should rely on these number they are just best effort"; read literally, -1 is <= maxMergeSizeMB; maxCachedMB was never a hard cap (it is checked only when a file is created); and addIndexes output has been cached since 2011 without a report.

Why it fails: NRTCachingDirectory's own documented contract relies on these estimates, and nothing found in that thread or since tied the -1 to the cache decision; maintainers fixed "cached although the size rule says no" as a bug three times and wrote the rule "shouldn't cache files of unknown size"; and 10.6.0 now documents a null MergeInfo as the unknown-size form. An independent reviewer from another model family (OpenAI GPT-5.6), asked in two separate reviews to refute the bug and to argue it is intended, rated the defence weak both times. A later cross-model fact check of this page (OpenAI GPT-5.6) rated the intended-behaviour case moderate rather than weak: MergeInfo calls its values "only estimates", the -1 was a deliberate best-effort choice, the class is @lucene.experimental and opt-in, addIndexes(CodecReader...) is an advanced API, the behaviour is old, and a maintainer may read it as a leftover of #14993/#15120; it still called the rebuttal strong (but incomplete) and the bug real. Qualification: the maxCachedMB overshoot alone is defensible, so the claim rests on maxMergeSizeMB.

Recommended A: doCacheWrite refuses a negative estimate (recommended)

Fix A (recommended, 4 lines): NRTCachingDirectory.doCacheWrite returns false when the estimate is negative, as LUCENE-9115 does when it is missing. A: doCacheWrite refuses a negative estimate (recommended) (validated by the checks)

#

In NRTCachingDirectory.doCacheWrite, after the size is read from the merge or flush info, return false when it is negative: a negative estimate means the size is unknown, and since LUCENE-9115 files of unknown size are not cached.

--- a/lucene/core/src/java/org/apache/lucene/store/NRTCachingDirectory.java
+++ b/lucene/core/src/java/org/apache/lucene/store/NRTCachingDirectory.java
@@ -240,6 +240,10 @@
     } else {
       return false;
     }
+    if (bytes < 0) {
+      // unknown size (e.g. IndexWriter#addIndexes(CodecReader...) merges): do not cache
+      return false;
+    }
 
     return (bytes <= maxMergeSizeBytes) && (bytes + cacheSize.get()) <= maxCachedBytes;
   }

Trade-offs

Small addIndexes outputs are no longer cached either (they go straight to disk, as files of unknown size do since 8.5.0). It also guards against any other caller or custom MergePolicy passing a negative estimate. It leaves the DirectIODirectory face as it is. The same guard fits 10.x and 9.x (doCacheWrite has the same structure in 10.5.2 and 9.12.3).

What the checks validated

Earlier checks: the larger test passes with it and the upstream TestNRTCachingDirectory stays at 58 of 58. The whole :lucene:core:test was not run.

B: addIndexesReaderMerge says "unknown" the documented way, IOContext.merge() (validated by the checks)

#

Replace IOContext.merge(new MergeInfo(Math.toIntExact(numDocs), -1, false, UNBOUNDED_MAX_MERGE_SEGMENTS)) (IndexWriter.java:3520-3522) with IOContext.merge(), whose mergeInfo() is null (10.6.0+), and drop the then-unused MergeInfo import (3 insertions, 4 deletions).

Trade-offs

Fixes both consumers: NRTCachingDirectory refuses a null MergeInfo, and DirectIODirectory treats null as unknown and uses direct I/O for these outputs, small ones included (by reading). Custom directories lose totalMaxDoc and isExternal for these merges and must handle a null mergeInfo() (documented since 10.6.0). The Math.toIntExact overflow check goes; testReserveDocs(numDocs) just above already rejects more than MAX_DOCS. Before 10.6.0 a merge context must carry a MergeInfo (9.12.3 asserts it, 10.5.2 requires it), so older branches need A. Passing merge.getStoreMergeInfo() instead is no fix: reader merges have no segments, so it gives estimate 0, which is cached just the same.

What the checks validated

Same worktree and seed: the test passes with assertions on and off; TestNRTCachingDirectory, TestAddIndexes and TestIndexWriterOnDiskFull pass (103 tests, 0 failures, 2 skipped); lucene/misc TestDirectIODirectory and TestDirectIODirectoryCopyFrom pass (70 tests, 0 failures, 2 skipped); checkGoogleJavaFormat passes. That these outputs now use direct I/O was not measured.

C: pass a real estimate (not built)

#

Estimate the merged size from the added readers (for example the segment sizes of SegmentReaders minus deletes, as addEstimatedBytesToMerge does for normal merges), with A or B as the fallback when no size can be known.

Trade-offs

Best behaviour: small addIndexes stay cached and large ones use direct I/O; it would also give the merge scheduler the estimate #14993 asked for, which reader merges still lack after #15120 (estimate 0). More code; not validated.

Downstream note

#

Servers that run index merges or shard splits through addIndexes(CodecReader...) on an NRTCachingDirectory (by reading, Solr's default directory factory) hold the whole added segment in heap until the next commit and can run out of memory on large inputs.

How it was found

#

Model-based testing of the IOContext each index file is opened with: a trace harness ran 256 writer and directory configurations (MMapDirectory, NIOFSDirectory, DirectIODirectory) on the real code against exact context oracles. One unexplained kind of merge-context read in its addIndexes step, not served with direct I/O, led by code reading to the -1 and to NRTCachingDirectory; a one-test JUnit followed.

The method in full92 words

The harness tagged every input and output with the context it was opened with and compared the tags with an exact model of what each writer step should use. Its addIndexes step showed a merge-context read of a vector file that DirectIODirectory did not serve with direct I/O. Reading IndexWriter.addIndexesReaderMerge showed the -1 merge size behind it, and searching for the value's other consumers found NRTCachingDirectory.doCacheWrite, where the effect is heap use rather than speed. A one-test JUnit on stock main then confirmed it, followed by scale, control and OutOfMemoryError probes.

History

#

Present since NRTCachingDirectory was added in 3.2.0 (LUCENE-3092, 2011); the current -1 mechanism since 4.0.0 (LUCENE-2793, IOContext). Kept through LUCENE-6165 (5.0.0), LUCENE-9115 (8.5.0), LUCENE-10216 (9.4.0) and #15120 (10.3.0). Executed: 20 releases from 3.2.0 to 10.6.0 and main fail. Not fixed upstream.

Versions tested6 rows
  • 3.2.0 (LUCENE-3092, #4165; branch_3x 8035a5ecf0f, trunk 3525ba940fa, Michael McCandless, 2011-05-17): NRTCachingDirectory added. In 3.2.0-3.6.2 its check was thread-based, and addIndexes merged in the caller's thread, which the class never saw as a merge.

LFV-1430, snapshot of 2026-11-10

Registry title
IndexWriter.addIndexes(CodecReader...) opens its merged segment with an estimated merge size of -1 ('unknown'), which NRTCachingDirectory reads as a tiny merge, so the whole merged segment is cached in heap past maxMergeSizeMB until the next commit, and a large addIndexes can end in OutOfMemoryError with a tragic writer close (every release since 3.2.0; before 5.0.0 through addIndexes(IndexReader...))
Area
store / NRTCachingDirectory cache decision for IndexWriter.addIndexes(CodecReader...) outputs (IOContext MergeInfo estimatedMergeBytes -1)
Priority
Medium, rank 121: In every release since 3.2.0, a reader-based IndexWriter.addIndexes through NRTCachingDirectory keeps the merged segment's files in heap until the next commit whatever their size, ignoring maxMergeSizeMB, so adding, splitting or merging large indexes on a modest heap can end in OutOfMemoryError and a tragic writer close that loses uncommitted changes. It is Medium because the trigger is ordinary use of two public APIs that a major downstream server combines by default (by code reading), and not higher because NRTCachingDirectory is opt-in in Lucene, the failure is loud and nothing on disk is corrupted.
Impact class
crash
Impact note
Hits applications that wrap their index directory in the opt-in NRTCachingDirectory (by reading, Solr's default directory factory does) and call IndexWriter.addIndexes(CodecReader...), for example to add, split or merge whole indexes: every output file of that merge created while the cache holds at most maxCachedMB stays in heap until the next commit whatever its size, ignoring maxMergeSizeMB [exec: 8.2 MB cached with maxMergeSizeMB 1.0; with the class javadoc's own (5.0, 60.0) about 72 MB and 100 MB additions cache 74 MB and 105 MB], and when the added data exceeds the free heap the merge throws OutOfMemoryError and IndexWriter closes tragically, losing uncommitted changes [exec by the finder only: 64 MB heap, 120 MB added; plain FSDirectory succeeds]; default IndexWriterConfig and codec, no special data; addIndexes(Directory...), flushes and normal merges are not affected.
Summary
You wrap your directory in NRTCachingDirectory with maxMergeSizeMB 1.0 and call IndexWriter.addIndexes(CodecReader...) with the segments of an index of about 2 MB. You expect the merged segment to be written to the wrapped directory, because NRTCachingDirectory caches only flushes and merges whose estimated size is at most maxMergeSizeMB and, since LUCENE-9115, no files of unknown size. Instead IndexWriter opens every output of that merge with a merge size of -1, NRTCachingDirectory compares -1 with its limits and admits it, so all 2.1 MB stay in the heap cache until the next commit; with more data than free heap the merge fails with OutOfMemoryError and the writer closes.
Introduced
8035a5ecf0f (branch_3x) / 3525ba940fa (trunk), LUCENE-3092 (apache/lucene#4165, migrated JIRA issue, no pull request; by mikemccand, 2011-05-17): NRTCachingDirectory was added, and addIndexes output was never bounded by its maxMergeSizeMB. In 3.2.0 to 3.6.2 the reason was its thread-based check, which never saw addIndexes as a merge. The present mechanism came with LUCENE-2793 (apache/lucene#3867, by s1monw): branch commits 92b07b725e6 (2011-06-20, doCacheWrite reads the IOContext's estimatedMergeBytes) and e9937378c92 (2011-06-30, the addIndexes context becomes new MergeInfo(numDocs, -1, true, false)), merged to trunk as c49d2d5d84b (2011-07-08), first released in 4.0.0. Later changes kept it: the 4.0.0 rewrite of the check (bytes <= maxMergeSizeBytes && bytes + cached <= maxCachedBytes), LUCENE-6165 (1a394ff3950, 5.0.0, the addIndexes(CodecReader...) overload on the same path), LUCENE-9115 (#10156, 8.5.0, refuses only contexts with neither merge nor flush info), LUCENE-10216 (#11253, 9.4.0, reader merges through the merge scheduler, -1 kept) and #15120 (fix of #14993, 10.3.0, sets OneMerge.estimatedMergeBytes, not the IOContext) [read from history; release onset exec] (2011-05-17 (LUCENE-3092, author date of 8035a5ecf0f and 3525ba940fa; first release 3.2.0); the -1 mechanism 2011-06-20 and 2011-06-30 (LUCENE-2793 branch commits), merged to trunk 2011-07-08, first release 4.0.0)
