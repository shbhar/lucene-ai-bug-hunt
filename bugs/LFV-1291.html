VerifyingLockFactory.obtainLock keeps the inner lock when the handshake with the lock verify server fails

When the handshake with the lock verify server fails, VerifyingLockFactory.obtainLock throws but never releases the inner lock it already took, and returns nothing you could close, so the lock name stays taken (every release since 5.3.0).

The finding in 30 seconds

#

obtainLock is return new CheckedLock(lf.obtainLock(dir, lockName)). The inner lock is taken first; the CheckedLock constructor then sends "acquired" and reads the echo. If the write or the read fails, the stream ends or the reply is wrong, the constructor throws and nothing closes the inner lock. CheckedLock.close does release it when the "released" handshake fails.

Background in three steps

#
  1. LockStressTest checks a lock implementation: client JVMs take and release the same lock in a loop and report every acquire and release to one LockVerifyServer, which fails if two clients ever hold the lock at once.
  2. Each client wraps its real (inner) lock factory in VerifyingLockFactory. After taking the inner lock it sends "acquired" (byte 1) and waits for the server to echo it; before releasing it sends "released" (byte 0).
  3. After its first locking error the server closes each client's connection at that client's next message, so that client's next handshake reads end-of-stream.

The finding, step by step

#
  1. Wrap a SingleInstanceLockFactory in VerifyingLockFactory, the wrapper LockStressTest uses to check a lock implementation against a LockVerifyServer. Give it a server connection that is already closed: an empty input stream.
  2. Call obtainLock(dir, "test.lock"). It takes the inner lock, sends "acquired" (byte 1), reads end-of-stream instead of the echo and throws IllegalStateException: Lock server died because of locking error.
  3. You expect the lock to be free again: obtainLock either returns a Lock you can close, or throws and leaves the lock free.
  4. Instead the next obtain of test.lock fails with lock instance already obtained: nothing closed the inner lock, and you got no handle to close it. With NativeFSLockFactory the name stays "held by this virtual machine"; with SimpleFSLockFactory test.lock stays on disk.

Who is affected

#

Only code that wraps a lock factory in VerifyingLockFactory, the lock-testing wrapper, when the server handshake fails during an acquire: in practice after a stress run has already failed. The name stays taken until the factory goes away or the JVM exits, or a SimpleFS lock file must be deleted by hand. Fails closed; IndexWriter locking is unaffected.

Mechanism, terms and numbers457 words

VerifyingLockFactory is the wrapper LockStressTest uses to check a lock implementation against a LockVerifyServer. Its obtainLock first obtains the real (inner) lock and then, in the CheckedLock constructor, tells the server "acquired" and waits for the echo. If that handshake fails (the server has closed the connection, answers with a wrong byte, or the write or the read fails), obtainLock throws, but nothing closes the inner lock, and the caller gets no Lock it could close.

The lock name then stays taken: SingleInstanceLockFactory reports "lock instance already obtained", NativeFSLockFactory "Lock held by this virtual machine" (with its FileChannel left open), and a SimpleFSLockFactory lock file stays on disk. The release side of the same class already handles this case; the acquire side does not. It fails closed (never two holders), affects no index or search result, and default IndexWriter locking never goes through this class. The fix is a few lines in obtainLock.

The bug

#
  1. obtainLock is one line, return new CheckedLock(lf.obtainLock(dir, lockName)); (VerifyingLockFactory.java:86-89): the inner lock is obtained first and passed straight into the constructor.
  2. The constructor runs the handshake: this.lock = lock; verify((byte) MSG_LOCK_ACQUIRED); (:44-47).
  3. verify writes and flushes the byte, then reads the echo (:62-72): a failed write, flush or read throws; end-of-stream throws IllegalStateException("Lock server died because of locking error.") (:66-67); a wrong byte throws IOException("Protocol violation.") (:69-70).
  4. When the constructor throws there is no CheckedLock, so the caller has nothing to close, and obtainLock has no try that closes the inner lock. It stays held: in SingleInstanceLockFactory's locks set (SingleInstanceLockFactory.java:34-43), in NativeFSLockFactory's JVM-wide held set with its channel open (NativeFSLockFactory.java:108-119), or as a SimpleFSLockFactory lock file.

The other side of the same class

#

CheckedLock.close wraps the "released" handshake in try (Lock l = lock) (:54-60), so the inner lock is released even when that handshake fails. Both sides were written in the same commit (LUCENE-6508); only the acquire side lacks the cleanup.

When it happens for real

#

After its first locking error LockVerifyServer sets lockedID[0] = -2 (LockVerifyServer.java:92, :105); every other server thread then returns at its client's next message and closes that socket (:83-87, :126-128). A client whose next message is "acquired" has just obtained the inner lock and reads end-of-stream, which the repro's empty stream stands in for. So does the client whose "acquired" caused that first error: its server thread throws, and the finally closes its socket (:92, :126-128). A killed server or a dropped connection gives either the same end-of-stream or an IOException from the read (for example a connection reset); the inner lock stays held either way.

Exposure and likelihood179 words
  • Who: only code that wraps a LockFactory in VerifyingLockFactory, which LockFactory's javadoc suggests for testing a lock implementation with LockVerifyServer and LockStressTest (LockFactory.java:34-36). Default IndexWriter locking never goes through this class.
  • When: only when the handshake fails during an acquire, which in practice happens when a stress run has already hit a locking error and the server is closing connections, or the server dies.
  • Effect: the lock name stays taken for the life of the inner factory (SingleInstance), until the JVM exits (NativeFS, plus an open FileChannel), or until someone deletes the lock file by hand (SimpleFS). The lock is never held twice; no index or search result is affected.
  • Bound: LockStressTest, the only in-tree caller, catches only LockObtainFailedException (LockStressTest.java:120-135), so the exception already ends the run and the client JVM, which frees in-JVM and native locks. What stays in practice is a SimpleFSLockFactory lock file, or a blocked name in a long-lived JVM that drives the wrapper itself.
  • Likelihood: rare; no public report of it was found since 5.3.0 (2015).

Why it looks unintended

#
  • LockFactory.obtainLock returns "a new obtained Lock instance" or throws; LUCENE-6508's CHANGES entry: a Lock "that can be released (or fails with exception)".
  • The same class releases the inner lock when the "released" handshake fails (CheckedLock.close); only the acquire side lacks it.
  • The trigger is what a real LockVerifyServer does after its first error: it closes each client's connection.
The full argument152 words
  • The contract: LockFactory.obtainLock: "Return a new obtained Lock instance identified by lockName", and throws if the lock could not be obtained (LockFactory.java:44-52). The LUCENE-6508 CHANGES entry that created today's API: "there is now just Directory.obtainLock() which returns a Lock that can be released (or fails with exception)" (lucene/CHANGES.txt:10412-10415). Lock's javadoc idiom try (final Lock lock = directory.obtainLock("my.lock")) (Lock.java:25-31) can only release a lock that was returned.
  • The same class, other side: CheckedLock.close releases the inner lock even when the "released" handshake fails (VerifyingLockFactory.java:54-60), written in the same commit.
  • The sibling: NativeFSLockFactory undoes what it took when a later step fails (NativeFSLockFactory.java:108-118, :129-143).
  • Nothing allows it: no javadoc, test, CHANGES or MIGRATE entry says a failed acquire may keep the lock. Uwe Schindler on #7566 (LUCENE-6507, 2015): "you just get a Lock instance if you have actually locked the directory".
The devil's-advocate check165 words

The strongest case for "intended": the class is a single-purpose diagnostic. A failed handshake is terminal by LockVerifyServer's design, the wrapper's streams are unusable afterwards, and LockStressTest runs one client per JVM and exits on the exception, so nothing observes the held lock except a SimpleFSLockFactory lock file, which SimpleFSLockFactory's javadoc already says can be left after an abnormal JVM exit (SimpleFSLockFactory.java:30-36). Mike McCandless also wrote on PR #12535 (2023) that they doubt users often run these tools.

Why it fails: that is an argument about impact, and it is why this is Low, not an argument about intent. obtainLock still breaks the return-or-throw shape its javadoc and the CHANGES entry describe, the class already releases the inner lock on the release side, and the trigger is what a real LockVerifyServer produces after its first error. It is a small exception-safety fix that mirrors CheckedLock.close; it matters only after a failed lock-verification run, and IndexWriter locking is not at risk.

Suggested fix

#

Recommended A. Close the inner lock when the handshake throws (validated)

Keep the inner lock in a local and, if the CheckedLock constructor throws, close it (attaching any exception from that close as suppressed) and rethrow: +9/-1 in VerifyingLockFactory.java, with the import. The repro passes with assertions on and off; the six lock-factory test classes (36 tests) and the format and lint checks pass.

Lock lock = lf.obtainLock(dir, lockName);
try {
  return new CheckedLock(lock);
} catch (Throwable t) {
  // the handshake failed and the caller gets no Lock to close: release the inner lock
  IOUtils.closeWhileSuppressingExceptions(t, lock);
  throw t;
}
All options and trade-offs3 options · 442 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B was run with the patched class shadowed on the classpath; C is by reading.

A. Close the inner lock when the handshake throws (validated) (recommended)

#

In VerifyingLockFactory.obtainLock (VerifyingLockFactory.java:86-89), plus import org.apache.lucene.util.IOUtils;:

Lock lock = lf.obtainLock(dir, lockName);
try {
  return new CheckedLock(lock);
} catch (Throwable t) {
  // the handshake failed and the caller gets no Lock to close: release the inner lock
  IOUtils.closeWhileSuppressingExceptions(t, lock);
  throw t;
}

Trade-offs

  • The handshake error stays the thrown exception; an exception while closing the inner lock is attached as suppressed, the idiom NativeFSLockFactory.tryLock uses in the same package (NativeFSLockFactory.java:139-142). Only an Error from that close is thrown instead, with the handshake error attached to it (IOUtils.java:114-136).
  • Nothing changes on success.
  • The inner lock is released without a "released" message to the server. With LockVerifyServer a failed handshake means the server has stopped checking or the connection is gone (it echoes every message it accepts, LockVerifyServer.java:118), and today LockStressTest ends on the error without sending one either; a different peer that recorded the "acquired" and then sent a wrong reply would still count the lock as held.
  • CHANGES: a Bug Fixes entry under the next release.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: TestLockFactory, TestSingleInstanceLockFactory, TestSimpleFSLockFactory, TestNativeFSLockFactory, TestSleepingLockWrapper, TestStressLockFactories (which drives VerifyingLockFactory through LockStressTest and a LockVerifyServer on 127.0.0.1) and the repro: 7 classes, 37 tests, 0 failures, 0 skipped.
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test.
  • The full lucene/core suite was not run.

B. The same with a success flag and closeWhileHandlingException in a finally

#

boolean success = false; try { CheckedLock checked = new CheckedLock(lock); success = true; return checked; } finally { if (success == false) IOUtils.closeWhileHandlingException(lock); }

Trade-offs

Same behaviour, but an exception while closing the inner lock is dropped instead of attached to the handshake error. An Error from that close is thrown in both forms; here without the handshake error attached (IOUtils.java:155-177). The repro passed with this form shadowed on the classpath, assertions on and off; not run with gradle.

C. Document that a failed obtain may leave the inner lock held

#

Say in the javadoc that the inner lock may stay held after a failed handshake.

Trade-offs

Contradicts LockFactory.obtainLock's contract and the class's own release side. Not recommended.

Downstream note

#

Downstream, only tools that drive VerifyingLockFactory inside a long-lived JVM, or over SimpleFSLockFactory, see a lock name or lock file left behind after a failed verification run; normal IndexWriter locking never goes through this class.

How it was found

#

Semi-formal: a proof-obligation audit of VerifyingLockFactory's contract, that an obtainLock that throws leaves the lock free. The exception path out of the CheckedLock constructor fails the obligation, and a JUnit test on stock main witnessed it.

The method in full95 words
  • Obligation: an obtainLock that throws leaves the lock free, as the return-or-throw shape of LockFactory.obtainLock's javadoc and the LUCENE-6508 CHANGES entry implies (a releasable Lock, or an exception).
  • Finding: the normal path discharges it (the returned CheckedLock releases the inner lock in close(), also when the "released" handshake fails); on the exception path out of the constructor the inner lock is in no object the caller can reach.
  • Witness: a JUnit test with an empty server stream, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Registry title

Impact class
minor
Impact note
Hits only code that wraps a LockFactory in VerifyingLockFactory, the diagnostic wrapper that LockFactory's javadoc suggests for testing a lock implementation with LockVerifyServer and LockStressTest, and only when the acquire handshake with the verify server fails (the server exits or closes the connection, which LockVerifyServer does to each client at its next message after the first locking error; or a wrong reply or a failed write); the inner lock then stays held: for SingleInstanceLockFactory for the life of that factory, for NativeFSLockFactory in the JVM-wide held set with its FileChannel open until the JVM exits [exec], and for SimpleFSLockFactory as a lock file on disk that must be deleted by hand [exec]; in LockStressTest the error already ends the run and the process, so in practice only a SimpleFS lock file is left; default IndexWriter locking never goes through this class, the lock is never held twice, and no index or result is affected.
Summary
You wrap a lock factory in VerifyingLockFactory (the wrapper LockStressTest uses to check a lock implementation against a LockVerifyServer) and call obtainLock while the connection to the verify server is broken, for example because the server has closed it or answers with an unexpected byte. You expect obtainLock either to return a Lock you can close or to throw and leave the lock free, as LockFactory.obtainLock's contract and the LUCENE-6508 CHANGES entry ('returns a Lock that can be released (or fails with exception)') say. Instead it obtains the inner lock, then throws from the handshake in the CheckedLock constructor without closing that lock and without returning anything to close, so the same name can no longer be obtained: SingleInstanceLockFactory says 'lock instance already obtained', NativeFSLockFactory says 'Lock held by this virtual machine', and a SimpleFS lock file is left on disk.
