Monitor HighlightsMatch drops a hit that has the same positions as another hit but different offsets (shingles, multi-word synonyms), because Hit.compareTo ignores offsets (since 8.2.0)

A Monitor query that matches two tokens stacked at one position, such as wi and the shingle wi fi, gets only one of its two hits from HighlightsMatch.MATCHER: getHitCount() is 1, not 2, with no error. Hit.compareTo ignores offsets and the hits sit in a TreeSet; affected since 8.2.0.

The bug in 30 seconds

#

A Monitor matches incoming documents against stored queries; HighlightsMatch.MATCHER also returns where each query matched, as hits with positions and character offsets. Some analyzers stack two tokens of different lengths at one position, and then two different hits share their positions.

  1. You build a Monitor whose analyzer adds two-word shingles (ShingleFilter(2, 2), unigrams kept). The text wi fi then has the tokens wi (characters 0-2) and wi fi (characters 0-5) at the same position, 0.
  2. You register wi OR "wi fi" and match the document wi fi with HighlightsMatch.MATCHER. You expect the two hits that Weight#matches reports, 0(0)->0(2) and 0(0)->0(5) (startPosition(startOffset)->endPosition(endOffset)), and getHitCount() = 2.
  3. Instead getHits("f") is [0(0)->0(2)] and getHitCount() is 1, silently. A multi-word synonym does the same: with guinea pig => cavy, the query guinea OR cavy keeps cavy (characters 0-10) and loses guinea (0-6).
  4. The cause: the hits are kept in a TreeSet, which treats two elements as the same when compareTo returns 0, and Hit.compareTo compares positions only. Hit.equals (a record over all four numbers) says the two hits differ.
  5. The same comparator makes getHits("f").contains(new Hit(0, 2, 0, 4)) true for a set holding only 0(0)->0(2), and makes two matches with different hits equals while their hash codes (4564, 6480) differ. Which queries match is unaffected.

Who is affected

#

lucene-monitor applications that match with HighlightsMatch.MATCHER and analyse with stacked tokens of different lengths: ShingleFilter with unigrams, multi-word SynonymGraphFilter rules with FlattenGraphFilter, CJKBigramFilter with unigrams. Each time a query matches two such tokens, one highlight span is lost and getHitCount() is one too low. One document suffices; matching itself is unaffected.

Mechanism, terms and numbers649 words

HighlightsMatch.MATCHER reports, for every stored query that matches a document, the hits that Weight#matches finds, as Hit(startPosition, startOffset, endPosition, endOffset) records per field. It keeps them in a TreeSet, and Hit.compareTo compares the start and end positions only, although Hit is a record whose equals and hashCode use all four fields. Analyzers that stack tokens of different lengths at one position (ShingleFilter with unigrams, multi-word synonyms through SynonymGraphFilter and FlattenGraphFilter, CJKBigramFilter with unigrams) produce two different hits with equal positions, because the index stores no position length; when a query matches both, the set keeps one. For wi fi with shingles and the query wi OR "wi fi", Weight#matches reports [0(0)->0(2), 0(0)->0(5)] and HighlightsMatch returns [0(0)->0(2)], getHitCount() 1, with no error. Which hit survives depends on clause order. The same comparator makes getHits(field).contains(...) ignore offsets and lets two matches with different hits be equals while their hash codes differ. Which queries match is not affected. The fix is a tie-break on offsets in compareTo; with it alone, one upstream batch test fails because a batch reports offsets -1 for TextField, so the test must index offsets (or the batch path must change).

Terms

#
  • Monitor: Lucene's reverse search module (lucene-monitor). You register queries, then monitor.match(doc, matcher) tells you which of them match a document. The matcher decides what you get back; HighlightsMatch.MATCHER returns a HighlightsMatch per matching query with its hits per field.
  • Hit: HighlightsMatch.Hit(startPosition, startOffset, endPosition, endOffset), a public record (HighlightsMatch.java:189). It prints as startPosition(startOffset)->endPosition(endOffset): 0(0)->0(5) is position 0 to 0, characters 0 to 5. The hits come from Weight#matches (HighlightsMatch.java:49-95).
  • Stacked tokens: tokens at the same position. ShingleFilter(2, 2) keeps unigrams by default, so wi fi gives wi [0,2), wi fi [0,5) and fi [3,5); wi and wi fi are both at position 0. A multi-word synonym guinea pig => cavy (original kept, flattened for indexing) puts cavy [0,10) on guinea [0,6). The index stores no position length, so both hits of a pair span position 0 to 0; only the offsets tell them apart.

The bug

#
  1. addHit puts every hit into a TreeSet per field: hits.computeIfAbsent(field, _ -> new TreeSet<>()).add(new Hit(...)) (HighlightsMatch.java:176-179).
  2. Hit.compareTo compares startPosition, then endPosition, and stops (HighlightsMatch.java:199-203). For 0(0)->0(2) and 0(0)->0(5) it returns 0.
  3. A TreeSet decides that an element is already present when compareTo returns 0 (its javadoc: "two elements that are deemed equal by this method are, from the standpoint of the set, equal"), so the second hit is dropped, although equals says the two differ.
  4. The default query decomposer splits wi OR "wi fi" into two queries; when both match, CandidateMatcher.addMatch merges their matches through HighlightsMatch.merge (CandidateMatcher.java:75-85, HighlightsMatch.java:65-67, :142-151), which copies the hits into a new TreeSet and drops the same hit. Without decomposition, the one Weight#matches call loses it in addHit.
  5. getHits(field) returns a read-only view of that TreeSet (:125-129), so contains answers through compareTo and ignores offsets; HighlightsMatch.equals compares the hit maps (:159) and ignores offsets too, while hashCode (:164-169) includes them.

Which hit survives depends on clause order (SHOULD(shingle, unigram) keeps 0(0)->0(2), SHOULD(unigram, shingle) keeps 0(0)->0(5)) and, in decomposed queries, on hash iteration order; the loss happened for every seed tried.

Exposure and likelihood255 words
  • Who is exposed. Applications that use the monitor with HighlightsMatch.MATCHER, for example to show which words of an incoming document matched a stored query, and whose analyzer stacks tokens of different lengths at one position. Every time a stored query matches two such stacked tokens in one document (a word and its multi-word synonym, a prefix query that matches a unigram and a shingle, a disjunction of both), one hit is silently dropped and getHitCount() is one too low.
  • Opt-in on both sides. The caller picks the matcher on every Monitor.match call (Monitor.java:218, :240; the other standard matchers are QueryMatch.SIMPLE_MATCHER, ScoringMatch.DEFAULT_MATCHER and ExplainingMatch.MATCHER), and the analysis chain is the application's. HighlightsMatch.MATCHER is one of the module's documented standard matchers, not an expert API.
  • No scale needed. One document, one query, one stacked pair. Single documents, batches whose fields index offsets (a batch of plain TextField documents reports offsets -1, so its stacked hits are identical), and both the plain and the decomposed query paths are affected.
  • Not affected. Which queries match a document; the simple, scoring and explaining matchers; hits whose offsets are not recorded (-1), which are truly identical.
  • Contract fallout. getHits(field).contains(...) cannot detect wrong offsets (upstream's own offset assertions are affected), and HighlightsMatch objects that are equals can have different hash codes, which breaks hash-based collections.
  • How likely. Rare: it needs the matcher, a stacking analyzer and a query that matches two stacked tokens. Nobody has reported it since the TreeSet was introduced in 2015. Priority Low.

Why it is a bug, not intended

#
  • Hit is a record whose equals uses all four numbers, and getHitCount() promises "the total number of hits for the query".
  • The deliberate dedup was tested only on fully identical hits, which the fix still merges; the survivor depends on clause order.
  • Upstream tests check hits via getHits(...).contains(new Hit(...)) 16 times; none of them can catch a wrong offset today.
The full argument347 words
  • Contract text. Hit is a public record over (startPosition, startOffset, endPosition, endOffset) (HighlightsMatch.java:181-189). getHits(): "a map of hits per field" (:105-110); getHitCount(): "the total number of hits for the query" (:131-140). The package doc says HighlightsMatch#MATCHER returns "the matching queries along with the matching terms for each query" (package-info.java:46-47); the dropped hit is a different matched term covering different text. No javadoc explicitly promises that every distinct Weight#matches hit is kept: the expectation rests on the record's equals, this wording and the JDK contracts, a strong reading rather than a quoted guarantee.
  • JDK contracts. Comparable strongly recommends a natural ordering consistent with equals because sorted sets "behave 'strangely'" otherwise; the TreeSet javadoc says a set with an inconsistent ordering "fails to obey the general contract of the Set interface"; Set.contains and Object.hashCode are specified through equals.
  • Tests. TestHighlightingMatcher asserts exact hits with getHits(...).contains(new HighlightsMatch.Hit(...)) 16 times (14 on FIELD, 2 on "field1"/"field2" at lines 108-109; for example line 63, Hit(3, 10, 3, 14)). The tests treat offsets as part of a hit, but these assertions cannot catch a wrong offset today: they fail when no hit has the expected positions, never when only the offsets differ; the batch assertion at line 541 does not even hold (a batch returns offsets -1 for TextField), and nobody could notice. testIdenticalMatches (lines 182-198) is the deliberate dedup: the same term as MUST and SHOULD, hits identical in positions and offsets, getHitCount() 1; it passes with the fix.
  • History. In Luwak, the library the module was imported from, compareTo was already position-only while hits lived in lists; commit 95e9eaf5b6 (2015, "Decompose DisjunctionQueries, and ensure highlights are only reported once") switched to TreeSets with only the identical-hit test. Hit.equals was hand-written over all four fields, and flaxsearch/luwak#87 (2016) added a hashCode "compatible with the existing equals()". The donation (LUCENE-8766) and the record conversion (#13328, 10.0.0) kept all of it. No CHANGES, MIGRATE or javadoc text says that hits with equal positions are merged.
The devil's-advocate check198 words

The intended-behaviour checker built the strongest case for "dedup by position is the design": the class javadoc says it "contains the hit positions of a matching Query" (HighlightsMatch.java:36); the position-keyed TreeSet was added on purpose; Comparable only recommends consistency with equals; core's DisjunctionMatchesIterator also orders by position (DisjunctionMatchesIterator.java:197-206); and the index has no position length anyway.

Why the evidence weighs against it: the dedup commit targeted hits reported twice by decomposed clauses, which are identical in positions and offsets and stay merged with the fix (its test is no longer decomposed today, because QueryDecomposer keeps a MUST plus SHOULD query whole, QueryDecomposer.java:93-95, but it still checks that identical hits merge); the author made offsets part of a hit's identity (equals, then hashCode); the survivor depends on clause order, which no dedup policy (such as "keep the widest span") would do; and the result breaks the Set and equals/hashCode contracts and blinds the module's own offset assertions. No document promises distinct same-position hits, so this is a judgement on the evidence. The checker rated the argument weak, a cross-model reviewer moderate; the adjudication confirmed the bug with high confidence.

Suggested fix

#

Recommended A1. Tie-break on offsets in Hit.compareTo, and make testHighlightBatches index offsets

Break position ties in Hit.compareTo by startOffset, then endOffset (+6/-1), so the TreeSets keep hits that differ in offsets and still merge identical ones. Pair it with a small test change: testHighlightBatches must index offsets, because a batch reports -1 offsets for TextField. Validated: the new test passes, and all 185 monitor tests pass.

     public int compareTo(Hit other) {
       if (this.startPosition != other.startPosition)
         return Integer.compare(this.startPosition, other.startPosition);
-      return Integer.compare(this.endPosition, other.endPosition);
+      if (this.endPosition != other.endPosition)
+        return Integer.compare(this.endPosition, other.endPosition);
+      // consistent with equals: the hit TreeSets must not drop a hit that differs in offsets only
+      if (this.startOffset != other.startOffset)
+        return Integer.compare(this.startOffset, other.startOffset);
+      return Integer.compare(this.endOffset, other.endOffset);
     }

A1. Tie-break on offsets in Hit.compareTo, and make testHighlightBatches index offsets (validated by the checks) (recommended)

#

Hit.compareTo keeps comparing start and end positions, then compares startOffset and endOffset (+6/-1 in HighlightsMatch.java). With this alone, TestHighlightingMatcher.testHighlightBatches fails at line 541, assertTrue(m1.getHits(FIELD).contains(new HighlightsMatch.Hit(1, 4, 2, 16))): a TextField document matched in a batch of two or more documents is indexed with its own field type and gets offsets -1, while a single document goes through a MemoryIndex that records offsets. Today the assertion passes only because contains ignores offsets. The test change gives the test's three batch documents a field type that indexes offsets, so the asserted hits are what the batch really returns (all three: a batch must have one schema).

+      // a batch is indexed with the documents' own field types, so index offsets to get them back
+      FieldType withOffsets = new FieldType(TextField.TYPE_NOT_STORED);
+      withOffsets.setIndexOptions(IndexOptions.DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS);
       Document doc1 = new Document();
-      doc1.add(newTextField(FIELD, "the cell biology count", Field.Store.NO)); // matches
+      doc1.add(new Field(FIELD, "the cell biology count", withOffsets)); // matches
       Document doc2 = new Document();
-      doc2.add(newTextField(FIELD, "nope", Field.Store.NO));
+      doc2.add(new Field(FIELD, "nope", withOffsets));
       Document doc3 = new Document();
-      doc3.add(newTextField(FIELD, "biology text", Field.Store.NO));
+      doc3.add(new Field(FIELD, "biology text", withOffsets));

(plus the imports of FieldType, TextField and IndexOptions.)

Trade-offs

  • Hit is public and Comparable: its natural ordering gains a tie-break, but only among hits with equal positions, which cannot coexist in a HighlightsMatch today.
  • getHitCount() and getHits(field) report one more hit at each stacked position: the point of the fix, but visible; a CHANGES entry under bug fixes fits.
  • Hits without recorded offsets (-1) stay identical and are still merged, so fields without offsets keep today's counts.
  • The test change leaves the batch question open: whether a batch should record offsets for TextField is a separate, disputed behaviour.

  • Tie-break + test change: all of :lucene:monitor:test with assertions on, 33 classes, 185 tests (181 existing, 4 new), 1 skipped, 0 failures; the new test and TestHighlightingMatcher with assertions off, 24 tests, 0 failures; :lucene:monitor:check -x test (google-java-format, ecjLint, forbiddenApis) passes. Downstream note

Applications that render monitor highlights show one span too few at such positions; the open Solr integration of the monitor (apache/solr#2382) uses HighlightsMatch.

How it was found

#

A hunt comparing the monitor's batch matching with single-document matching noticed, by reading the upstream batch test, that its offset assertion could never fail, and traced that to Hit.compareTo. The finder reduced it to a public-API test with Weight#matches as the reference; independent checkers then reproduced it with their own tests.

The method in full157 words

Method: code reading (the registry's "non-formal" tier). A hunt unit compared Monitor.match(Document[]) with Monitor.match(Document). While reading TestHighlightingMatcher.testHighlightBatches, the finder saw that its assertion on offsets (line 541) could never fail, and traced that to Hit.compareTo and the TreeSet.

  • The finder wrote a public-API JUnit with Weight#matches on a MemoryIndex as the reference (shingles, wi OR "wi fi"), which fails on main with and without assertions, on branch_10_6 and 10.5.2, and passes with the tie-break.
  • It replayed the upstream monitor suite with the tie-break in its own harness: 179 of 180 pass, the one failure being testHighlightBatches (the batch-offsets behaviour); 180 of 180 together with the batch change. (The 185 tests in the fix section come from a separate gradle run of the whole module, 181 existing tests plus the 4 new ones; the two counts are not comparable.)
  • Independent checks followed (see "Independent checks"), then a version sweep and this doc's gradle validation.

Bug record

LFV-915, snapshot of 2026-10-29

Registry title
Monitor HighlightsMatch drops a hit when another hit has the same positions but different offsets (for example shingles or multi-word synonyms), because HighlightsMatch.Hit.compareTo ignores offsets
Area
monitor / HighlightsMatch hit set (Hit.compareTo used as TreeSet identity)
Priority
Low, rank 407: Opt-in Monitor HighlightsMatch drops a highlight span at each stacked-token position while matching.
Impact class
silent wrong results
Impact note
Hits lucene-monitor applications that match with HighlightsMatch.MATCHER and analyse with stacked tokens of different lengths at one position (ShingleFilter with unigrams, multi-word synonyms through SynonymGraphFilter plus FlattenGraphFilter, CJKBigramFilter with unigrams): whenever two such tokens both match, getHits(field) and getHitCount() silently lose one of the two distinct hits that Weight#matches reports, for single documents and batches and on both the addHit and the decomposer merge path, with no error and no scale needed; which queries match is not affected, and the SIMPLE and scoring matchers are not involved.
Summary
You register a query such as wi OR "wi fi" (or the prefix query wi*, or guinea OR cavy with a 'guinea pig => cavy' synonym rule) in a Monitor whose analyzer stacks tokens at one position, match a document with HighlightsMatch.MATCHER, and expect both hits that Weight#matches reports: for 'wi fi' with ShingleFilter(2,2) and unigrams these are 0(0)->0(2) for 'wi' and 0(0)->0(5) for 'wi fi'. Instead HighlightsMatch keeps only one of them and getHitCount() is 1, because Hit.compareTo compares start and end positions only and the hits are kept in TreeSets, which treat compareTo == 0 as a duplicate, although Hit's own equals (a record over all four fields) says the two hits differ. Which hit survives depends on clause order, and the same root cause makes getHits(field).contains(...) ignore offsets and lets HighlightsMatch.equals return true for two objects whose hashCodes differ.
