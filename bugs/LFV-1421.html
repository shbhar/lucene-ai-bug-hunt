BinaryRangeDocValues javadoc says to pass twice the value size; following it throws on the first document

The public BinaryRangeDocValues constructor's javadoc says numBytesPerDimension is "2 * encoded value size" (16 for a long range), but the class already doubles it and needs the value size itself (8). Code that follows the javadoc throws ArrayIndexOutOfBoundsException on the first document of a field whose ranges all have the same dimensions; Lucene's own callers pass 8 and are fine.

The finding in 30 seconds

#

A range doc-values field stores one min and one max per dimension: for a one-dimension long range, 8 + 8 = 16 bytes. BinaryRangeDocValues copies these bytes out per document, and its constructor asks how wide one value is.

  1. Index one document with LongRangeDocValuesField("r", {1}, {2}). Lucene stores it as 16 bytes: an 8-byte min and an 8-byte max.
  2. Read it back with new BinaryRangeDocValues(values, 1, 2 * Long.BYTES), that is 16, because the javadoc says numBytesPerDimension is the "size of each dimension (2 * encoded value size)".
  3. You expect nextDoc() to return doc 0 with its 16-byte range.
  4. Instead the class multiplies by 2 again and copies 2 × 1 × 16 = 32 bytes out of the 16-byte value: ArrayIndexOutOfBoundsException: arraycopy: last source index 32 out of bounds for byte[16].
  5. Passing Long.BYTES (8), what Lucene's slow range queries and range facets pass, works. Only the javadoc is wrong.

Who is affected

#

Only application code that builds BinaryRangeDocValues itself (say, in a custom collector over a LongRangeDocValuesField) and follows the javadoc. Lucene's slow range doc-values queries and range-on-range facets pass the right value. If every range in the field has the same dimensions, it throws on the first document, in every release from 9.5.0 to 10.6.0 and on main.

Mechanism, terms and numbers368 words

BinaryRangeDocValues is a public core class that wraps the BinaryDocValues of a range doc-values field (LongRangeDocValuesField, IntRangeDocValuesField, DoubleRangeDocValuesField, FloatRangeDocValuesField) and exposes each document's packed range. Its constructor's javadoc says numBytesPerDimension is the "size of each dimension (2 * encoded value size)", so 16 for a long range. The class already applies the factor 2 itself (one min and one max per dimension) and needs the size of one encoded value, 8 for a long, which is what Lucene's own callers pass. A caller who passes 16 as documented gets ArrayIndexOutOfBoundsException: arraycopy: last source index 32 out of bounds for byte[16] from the first nextDoc(), with assertions on or off and no codec or other setting needed. It has been so in every release from 9.5.0 to 10.6.0 and on main. The fix is one @param in the javadoc.

The contract and the code (main f794ff5a505c, BinaryRangeDocValues.java)

#
  • :37, the @param: numBytesPerDimension size of each dimension (2 * encoded value size).
  • :44, the constructor: this.packedValue = new byte[2 * numDims * numBytesPerDimension];
  • :52 (nextDoc), :72 (advance), :82 (advanceExact): each calls decodeRanges() when the wrapped iterator is on a document.
  • :108-109, decodeRanges: System.arraycopy(bytesRef.bytes, bytesRef.offset, packedValue, 0, 2 * numDims * numBytesPerDimension);

So the class applies the factor 2 (min and max) itself. With the documented 16 the copy length is 2 × 1 × 16 = 32, but the stored value is 16 bytes (LongRange.java:124, new byte[BYTES * 2 * min.length]), and System.arraycopy throws on the first document.

The class never checks the value's length against that copy length; its comment at :105-107 assumes every value in the field has the same length.

What Lucene's own callers pass

#
  • BinaryRangeFieldRangeQuery.java:104-105 passes its numBytesPerDimension, which the four slow range queries set to one value's width (LongRangeSlowRangeQuery.java:34 passes LongRange.BYTES; the Int, Double and Float versions likewise). The same value is the width of its per-value comparator (:55).
  • RangeOnRangeFacetCounts.java:83 computes dims = encodedRanges[0].length / (2 * numEncodedValueBytes) and :92-93 passes numEncodedValueBytes, which is Long.BYTES or Double.BYTES (LongRangeOnRangeFacetCounts.java:50, DoubleRangeOnRangeFacetCounts.java:53).
  • The fields use the name the same way: LongRangeDocValuesField.java:33 passes LongRange.BYTES as numBytesPerDimension.
Exposure and likelihood286 words
  • Who is hit: code that constructs BinaryRangeDocValues directly and passes numBytesPerDimension as documented (16 for a long range, 8 for an int range). A GitHub code search for "new BinaryRangeDocValues(" language:Java found 42 hits, all Lucene's own two callers or copies of Lucene's source.
  • Who is not: *RangeDocValuesField.newSlowIntersectsQuery (through BinaryRangeFieldRangeQuery) and the facet module's LongRangeOnRangeFacetCounts / DoubleRangeOnRangeFacetCounts.
  • Config: no codec or other setting is needed. The test sets no codec, so under seed DEADBEEF the test framework draws Asserting(Lucene104); with -Dtests.codec=Lucene104 (the plain default codec), 6 other seeds and a plain main() outside the test framework (codec Lucene104) it fails the same way. The opt-in part is direct use of the class.
  • Symptom: one document is enough. For a field whose ranges all have the same number of dimensions, every read fails: the default codec's doc-values reader returns each value in a buffer of exactly its length when all values have one length (Lucene90DocValuesProducer.java:1332, :1432), so the copy throws ArrayIndexOutOfBoundsException on the first nextDoc, advance or advanceExact, with assertions on and off.
  • Not always an exception: in a field that mixes 1- and 2-dimension long ranges, the values differ in length and the reader reuses one buffer of the longest value's size (:1373, :1452). The 32-byte copy of a 16-byte value then succeeds and silently picks up 16 stale bytes left from the value read before it (a plain main() probe, assertions on and off). Such a field is outside the class's assumption: with the correct value 8 its 2-dimension values are misread too.
  • How likely: rare. No report since 9.5.0 surfaced in the recorded searches, and the message points straight at the size.

Why it looks unintended

#
  • The class applies the factor 2 itself: it allocates and copies 2 * numDims * numBytesPerDimension bytes.
  • Every caller passes one value's width, including the facet caller added in the same commit as the javadoc (Long.BYTES).
  • The class is public with no @lucene.internal or @lucene.experimental tag, and the @param is the only guidance.
The full argument116 words
  • No reading of the @param gives the value the class needs. "Size of each dimension" and "2 * encoded value size" both give 16 for a long range and 8 for an int range, twice what the class reads.
  • The javadoc's own commit contradicts it. cbfed77fd33 (#11901) wrote the @param and, in the same commit, added RangeOnRangeFacetCounts, which passes numEncodedValueBytes (Long.BYTES).
  • The name means one value's width everywhere else in org.apache.lucene.document: BinaryRangeFieldRangeQuery builds a per-value comparator from it (:55), and the range fields pass LongRange.BYTES under that name (LongRangeDocValuesField.java:33).
  • No test pins the documented value. No Lucene test constructs BinaryRangeDocValues directly; it is exercised only through its two callers.
The devil's-advocate check106 words

Strongest case: the class is plumbing. When it was added in LUCENE-8362 (#9409, 2019) a reviewer asked "BinaryRangeDocValues doesn't need to be public?", and it became public in 9.5.0 only so the facet module could use it; the parenthetical could be read as a remark about the min+max footprint of a dimension.

Why it fails: since 9.5.0 the class and constructor are public in an exported core package with no @lucene.internal or @lucene.experimental tag, the @param assigns the doubled number to the argument itself, and nothing else in the class says what to pass. The history lowers the priority; it does not make the @param right.

Downstream note

#

Downstream code that builds BinaryRangeDocValues itself should pass the encoded value size (for example LongRange.BYTES), not twice it; a GitHub code search of Java files found no such caller outside copies of Lucene's own two.

How it was found

#

A proof-obligation audit of the constructor's contract (semi-formal) asked whether the copy in decodeRanges stays inside the stored value when a caller passes the documented numBytesPerDimension. It does not; a one-document JUnit test on main confirmed it.

The method in full91 words

The audit took each public parameter's documented meaning and checked it against the code it drives. Here the obligation is the bound of System.arraycopy in decodeRanges (BinaryRangeDocValues.java:108-109): the copy length 2 * numDims * numBytesPerDimension must not exceed the stored value's length 2 * numDims * valueSize. That holds only when numBytesPerDimension equals the value size, and the @param says twice the value size, so the obligation fails for every input. An executable JUnit test through the public constructor on main f794ff5a505c witnessed it, and passing Long.BYTES instead made the test pass.
