RunAutomaton.toString prints the last character class one past its end: U+110000 instead of U+10FFFF

A CharacterRunAutomaton for any single character, Automata.makeAnyChar(), prints its range as \\U00000000-\\U00110000, but the last code point is U+10FFFF. Since 6.5.0, toString() prints the last character class up to the alphabet's exclusive size; only this debug text is wrong, matching is correct.

The finding in 30 seconds

#

Inner classes print their inclusive end, points[j + 1] - 1; the last class prints alphabetSize, the exclusive size of the alphabet. Any class that reaches U+10FFFF is the last one, so it prints one past its end.

Background: how a run automaton prints itself

#
  1. A CharacterRunAutomaton is the table form of a deterministic automaton over Unicode code points, U+0000 to U+10FFFF (Character.MAX_CODE_POINT).
  2. It splits that alphabet into character classes, ranges of code points every state treats alike. The class boundaries are the automaton's start points.
  3. toString() prints, for each state, one line per class that has a transition: min-max -> dest with both ends included, or just min when the class is one code point.

The finding, step by step

#
  1. Build a run automaton that accepts any one code point, U+0000 to U+10FFFF: new CharacterRunAutomaton(Automata.makeAnyChar()), and print it.
  2. toString() prints one line per character class, min-max -> dest, both ends included. You expect \\U00000000-\\U0010ffff -> 1, as Automaton.toDot() prints the same arc and as 6.4.2 printed it.
  3. You get \\U00000000-\\U00110000 -> 1: the end is 0x110000 = 1,114,112, one past Character.MAX_CODE_POINT (1,114,111) and not a code point. A class holding only U+10FFFF prints as the two-value range \\U0010ffff-\\U00110000.
  4. Why: an inner class prints the next class's start minus one, but the last class prints alphabetSize, which is the exclusive size MAX_CODE_POINT + 1. LUCENE-7465 (6.5.0) made that field exclusive and kept the line. Matching, step() and run() are unaffected, and ByteRunAutomaton does not show it for byte-based input.

Who is affected

#

Anyone who prints a CharacterRunAutomaton, while debugging or in a test log, whose last class reaches U+10FFFF: ., .*, makeAnyChar(), makeAnyString(), negated classes like [^a]. Default settings, assertions on and off. It is one wrong value in debug text; a source search found no Lucene code that parses or asserts it, so the impact is cosmetic and probably rare.

Mechanism, terms and numbers633 words

RunAutomaton.toString() lists each state's transitions as one line per character class, min-max -> dest, with both ends included: an inner class ends at the next class's start minus one, and a class of one code point prints as a single value. For the last class it prints alphabetSize, which is the exclusive size of the alphabet (Character.MAX_CODE_POINT + 1 for a CharacterRunAutomaton). So any class that reaches U+10FFFF is printed as ending at \\U00110000, which is not a code point, and a last class holding only U+10FFFF is printed as a range of two values.

new CharacterRunAutomaton(Automata.makeAnyChar()).toString() prints \\U00000000-\\U00110000 -> 1, where Automaton.toDot() prints the same arc as \\U00000000-\\U0010ffff. The line came in with LUCENE-7465 (93fa72f77bd, first released in 6.5.0), when the inclusive field maxInterval became the exclusive alphabetSize; it is in every release since, through 10.6.0 and main. Only the debug string is wrong: matching, step() and run() are correct, a source search found no Lucene code that parses or asserts the text, and ByteRunAutomaton does not show it for byte-based input. The one-line fix alphabetSize - 1 was validated with gradle.

toString writes a code point outside ! to ~, and also \ and ", as two backslash characters, U and 8 hex digits, so the real output reads \\U00110000; the text here quotes it exactly as printed.

The code (main 5adff78bb168)

#
// RunAutomaton.toString, RunAutomaton.java:109-122, for each state i and class j
int k = transitions[i * points.length + j];
if (k != -1) {
  int min = points[j];
  int max;
  if (j + 1 < points.length) max = (points[j + 1] - 1);   // :113 inner class: inclusive end
  else max = alphabetSize;                                 // :114 last class: the exclusive size
  b.append(" ");
  Automaton.appendCharString(min, b);
  if (min != max) {                                       // :117 a range, else a single value
    b.append("-");
    Automaton.appendCharString(max, b);
  }
  b.append(" -> ").append(k).append("\n");
}
  1. Classes. The constructor takes points = a.getStartPoints() (RunAutomaton.java:67). Automaton.getStartPoints adds each arc's min, and max + 1 only when max < Character.MAX_CODE_POINT (Automaton.java:626-648, :639). An arc that reaches U+10FFFF gets no start point after it, so it always lies in the last class.
  2. The bound is exclusive. CharacterRunAutomaton passes Character.MAX_CODE_POINT + 1 = 0x110000 (CharacterRunAutomaton.java:27); step() asserts c < alphabetSize (RunAutomaton.java:173); the fast lookup table is new int[Math.min(256, alphabetSize)] (:89). The last class really ends at alphabetSize - 1.
  3. Result. The last class prints one past its end. A last class holding only U+10FFFF has min 0x10FFFF and max 0x110000, so min != max prints it as a range of two values.
  4. Why bytes are spared. ByteRunAutomaton uses 256 (ByteRunAutomaton.java:37). For byte-based input (the one-argument constructor converts to UTF-8; the expert ByteRunAutomaton(a, true) requires it, :32) its arcs end at 255 or below, so getStartPoints always adds max + 1; its last class carries no transition and is never printed. Given a non-byte automaton anyway, the expert constructor prints the same way: makeAnyChar() with isBinary = true shows \\U00000000-\\U00000100 -> 1 (executed). The sandbox TermAutomatonScorer.TermRunAutomaton passes the term count (TermAutomatonScorer.java:367-370) and its arcs end at termCount - 1 at most (TermAutomatonQuery.java:174-197), so it is spared too.

Exposure and likelihood139 words
  • Default: ordinary public API and default classes; no special input or setting. Assertions on or off make no difference.
  • Effect: someone reading the output to check which code points an automaton covers sees an end value that is not a code point, and a class of the one code point U+10FFFF shown as two values.
  • Seen in the wild: two automated 2018 dev@ CI failure mails contain a TestRandomChains log that prints a MockTokenizer's run automaton with !-\\U00110000 -> 1; nobody remarked on it.
  • Not affected: matching, step(), run(), and ByteRunAutomaton with byte-based input. A source search found no Lucene code that parses the string and no test that asserts it.
  • Likelihood: probably rare (not measured): printing a run automaton is an uncommon debugging step, and the recorded searches found no report since 6.5.0 (2017).

Why it looks unintended

#
  • The same method prints every other class with its inclusive end, and a one-code-point class as one value; toDot() prints the same arcs inclusively.
  • alphabetSize is exclusive everywhere else: step() asserts c < alphabetSize; NFARunAutomaton ends its last arc at alphabetSize - 1.
  • 6.4.2 printed \\U0010ffff; LUCENE-7465 made the inclusive maxInterval the exclusive alphabetSize and kept the line.
The full argument191 words
  • Contract: no grammar is documented (the javadoc is "Returns a string representation of this automaton.", RunAutomaton.java:99), so the obligation comes from the method itself: inclusive inner ends (:113) and the single-value rule (:117). Automata.makeAnyChar() is documented to accept "any single codepoint" (Automata.java:104), and 0x110000 is not one.
  • The package agrees: Automaton.toDot() prints arcs with their inclusive max (Automaton.java:612-616); NFARunAutomaton sets the last arc's t.max = alphabetSize - 1 (NFARunAutomaton.java:228). The merged PR #559 (2021) made NFARunAutomaton's default alphabet size MAX_CODE_POINT + 1 because a MAX_CODE_POINT size tripped the c < alphabetSize assert. The open PRs #13072 and #16564 test transition.max == alphabetSize - 1 as the inclusive top.
  • History: before LUCENE-7465 the field was maxInterval, inclusive (CharacterRunAutomaton passed Character.MAX_CODE_POINT), and else max = maxInterval; was right; 5.5.5 and 6.4.2 print the correct text. ByteRunAutomaton already passed 256 and kept it. 93fa72f77bd (Mike McCandless, 2017-02-13) changed the argument to Character.MAX_CODE_POINT+1 and the line to else max = alphabetSize;. The issue, #8517, is about a new tokenizer and a fast lookup table; it never mentions toString.
The devil's-advocate check128 words

The strongest case for "intended": the format is undocumented, RunAutomaton is @lucene.experimental (RunAutomaton.java:40), no test asserts the text and nothing reads it; the last bound could be read as half-open, "up to the alphabet size"; and with assertions off step() maps any c past the last start point into the last class.

Why it fails: a half-open last line contradicts the inclusive inner lines of the same output, and the single-value rule turns a lone U+10FFFF into the two-value range \\U0010ffff-\\U00110000, which no reading makes right. "Experimental" is about API stability, not a licence for wrong text, and a c of alphabetSize or more is what step()'s assert forbids. It stays Low; a maintainer may still call it trivial, which is a fair outcome.

How it was found

#

Semi-formal: an audit of the proof obligation of RunAutomaton.toString (each printed min-max -> dest line covers exactly its class's code points, both ends included) flagged the last-class line, and a public-API JUnit test witnessed it on main with assertions on and off.

The method in full94 words
  • First signal: the obligation holds for every inner class (points[j + 1] - 1) and fails for the last one, which prints the alphabet's exclusive size.
  • Witness: the one-test JUnit above failed on main with assertions on and off and on the 10.6.0 and 9.1.0 jars; a probe showed the same for [^a] and the single code point U+10FFFF, and correct output for toDot() and ByteRunAutomaton.
