SimpleRateLimiter.pause sleeps 24.86 days for any pause between 2.49 and 24.86 days

SimpleRateLimiter.pause sleeps the full 24.86 days for any single pause between 2.49 and 24.86 days, up to 10 times too long, because its int-overflow guard compares with 100000L * Integer.MAX_VALUE ns where 1000000L is meant. Only direct users with a single pause over 2.49 days are hit, since 4.10.3.

The finding in 30 seconds

#

One constant in an overflow guard is 10 times too small.

Background: how SimpleRateLimiter pauses

#
  1. SimpleRateLimiter throttles IO to a rate in MB/s (1 MB = 2^20 bytes). The caller reports bytes with pause(bytes), and the limiter sleeps until those bytes fit the rate.
  2. It sleeps with Thread.sleep(ms, ns), keeping the milliseconds in an int, in a loop that repeats until the target time, because one sleep may wake early.
  3. An int holds at most Integer.MAX_VALUE = 2,147,483,647 ms, about 24.86 days. A guard clamps longer sleeps to that, and the loop sleeps the rest.

The finding, step by step

#
  1. You throttle IO with new RateLimiter.SimpleRateLimiter(1.0) (1 MB/s) and one pause call reports 3 days' worth of bytes: 271,790,899,200 bytes, about 253 GiB. At 1 byte/s, 259,200 bytes need the same 3-day pause.
  2. You expect pause to sleep about 3 days, as a 2-day pause sleeps 2 days; Lucene 4.10.2 asked for about 3 days.
  3. Instead pause asks Thread.sleep for Integer.MAX_VALUE ms: 24.86 days, 8.3 times the pause. Only an interrupt ends it early.
  4. Why: pause keeps the milliseconds in an int (int sleepMS, RateLimiter.java:140; cast at :146) before calling Thread.sleep(long, int). An int holds at most Integer.MAX_VALUE ms (24.86 days), so a guard clamps longer sleeps. It should fire above 1000000L * Integer.MAX_VALUE ns (24.86 days, the "25 days" its comment names) but compares with 100000L * Integer.MAX_VALUE ns, 2.49 days: one zero is missing.
  5. So every remaining pause between 2.49 and 24.86 days sleeps 24.86 days, up to 10 times too long. No exception; the limiter changes no data or search result.

Who is affected

#

Only code that calls SimpleRateLimiter directly with one pause longer than 2.49 days: a near-zero rate (259,200 bytes at 1 byte/s) or about 210 GiB in one call at 1 MB/s. Lucene builds it only in tests; merges use MergeRateLimiter (sleeps capped at 250 ms). An already multi-day stall becomes 24.86 days; the limiter changes nothing else.

Mechanism, terms and numbers468 words

RateLimiter.SimpleRateLimiter.pause splits the remaining pause into milliseconds and nanoseconds held in ints (int sleepMS, RateLimiter.java:140; the cast at :146) before calling Thread.sleep(long, int). To keep that cast from overflowing, LUCENE-6075 (2014) added a guard that sleeps Integer.MAX_VALUE ms instead, with the comment "Not really practical (sleeping for 25 days) but we shouldn't overflow int". The cast only overflows above 1000000L * Integer.MAX_VALUE ns (24.86 days), but the guard compares with 100000L * Integer.MAX_VALUE ns (2.49 days). So every remaining pause between 2.49 and 24.86 days sleeps the full 24.86 days, up to 10 times too long: a 3-day pause asks Thread.sleep for 2,147,483,647,000,000 ns, 8.3 times the pause. Up to 4.10.2 the same pause asked for about 3 days. Only code that calls SimpleRateLimiter directly with one remaining pause over 2.49 days is hit; Lucene's merges use MergeRateLimiter, and the limiter changes no data or search result. The fix is the missing zero.

The code (RateLimiter.java at 5adff78bb168)

#
  1. :103, :113, :125: secondsToPause = (bytes / 1024. / 1024.) / mbPerSec, targetNS = lastNS + (long) (1000000000 * secondsToPause), lastNS = targetNS.
  2. :130-157: "While loop because Thread.sleep doesn't always sleep enough": each pass sleeps pauseNS = targetNS - curNS; the loop ends once curNS >= targetNS.
  3. :141-144: if (pauseNS > 100000L * Integer.MAX_VALUE) { // Not really practical (sleeping for 25 days) but we shouldn't overflow int: sleepMS = Integer.MAX_VALUE; sleepNS = 0; }. The bound is 214,748,364,700,000 ns = 2.4855 days.
  4. :139-140, :145-147: sleepMS and sleepNS are ints; the else branch, sleepMS = (int) (pauseNS / 1000000); sleepNS = (int) (pauseNS % 1000000);, is exact for every pauseNS up to 1000000L * Integer.MAX_VALUE = 2,147,483,647,000,000 ns = Integer.MAX_VALUE ms = 24.855 days, the "25 days" of the comment.
  5. For a remaining pause in (2.49 d, 24.86 d], :149 sleeps Integer.MAX_VALUE ms, longer than the pause; the loop then finds curNS >= targetNS and returns curNS - startNS (:159), the elapsed time, at least 24.86 days (by reading: every repro interrupts the first sleep). Only an interrupt ends it early (ThreadInterruptedException, :150-151).

Exposure and likelihood184 words
  • Who is hit: code that uses the public RateLimiter.SimpleRateLimiter constructor and pause(long) and makes one remaining pause longer than 2.49 days: a near-zero rate (259,200 bytes at 1 byte/s; a 512 KiB call at 1 byte/s needs about 6 days), about 210 GiB or more in one call at 1 MB/s, or a lastNS backlog of over 2.49 days from threads sharing one limiter. The constructor and setMBPerSec (RateLimiter.java:66-77) put no lower bound on the rate.
  • Lucene itself is not: in-tree, SimpleRateLimiter is constructed only in tests (TestRateLimiter.java:41, :54; the replicator test node SimpleReplicaNode.java:86). Merges use MergeRateLimiter, which caps each sleep at 250 ms (MergeRateLimiter.java:37, :156-157).
  • Effect: a thread already stalled for days stalls up to 10 times longer (at most 24.86 days for pauses in the window). No exception; the limiter changes no data, index or search result (what a long stall does downstream, such as timeouts, was not tested). Assertions on and off behave the same.
  • Priority Low: the trigger is a multi-day single pause, and no public report of the oversleep was found.

Why it looks unintended

#
  • The guard's comment says it only stops an int overflow ("we shouldn't overflow int") at "25 days": that is Integer.MAX_VALUE ms, where the cast really overflows.
  • The loop sleeps until the target time; a clamp longer than the remaining pause defeats it.
  • The commit's own test is sized at 1.5 x Integer.MAX_VALUE ms, and 4.10.2 asked for the right sleep.
The full argument176 words
  • Purpose: RateLimiter.java:142 says the guard exists so "we shouldn't overflow int" and names the size it clamps, "25 days" = Integer.MAX_VALUE ms. The expression N * Integer.MAX_VALUE mirrors the overflow condition pauseNS / 1000000 > Integer.MAX_VALUE; 100000 is one zero short of the 1,000,000 ns per ms the else branch divides by.
  • Loop design: :130-131 "While loop because Thread.sleep doesn't always sleep enough": the method sleeps until targetNS. Clamp-then-loop only works if a clamped sleep is never longer than what remains.
  • Test: TestRateLimiter.testOverflowInt (TestRateLimiter.java:31-49, "LUCENE-6075") pauses 1.5 * Integer.MAX_VALUE ms, sized against the real int limit. Its only check is an expectThrows(ThreadInterruptedException) in a child thread that the test interrupts after 10 ms (the parent neither joins nor asserts), and its pause lies above both bounds, so no test covers the 2.49-24.86 day window.
  • History: before LUCENE-6075 the code was Thread.sleep((int) (pauseNS/1000000), (int) (pauseNS % 1000000)), exact up to 24.86 days; on 4.10.2 a 3-day pause asked for about 3 days.
  • Precedent: over-throttling by SimpleRateLimiter was fixed as a bug before (LUCENE-5641, #6703).
The devil's-advocate check191 words

The case for intended: the javadoc only promises "to keep the instantaneous IO rate at or below the target" (RateLimiter.java:41, :91), which an oversleep still meets. The comment calls such sleeps "Not really practical", and in LUCENE-6075 (#7137) the reporter, Boaz Leskes, wondered whether a "sanity check" upper bound on long sleeps makes sense, and Michael McCandless answered "25 days is clearly rather silly ... but I'm not sure we should add such checks at this low level. Where would you draw the line?". A maintainer may see a 10x error on impractical sleeps as not worth an issue.

Why it still holds: that exchange is about an extra cap (the reporter then agreed to leave it as is); it does not choose this bound. Nothing in the commit, its patch, the CHANGES entry or the issue names a 2.5-day rule, and both the comment's "25 days" and the commit's own test point at the int limit. That intended bound is an inference from the code, the comment and the test; no source states it. The argument is about impact, not intent, which is why this is Low.

Compare with 1000000L * Integer.MAX_VALUE (validated) (recommended)

#

The guard then fires only above Integer.MAX_VALUE ms (24.86 days): pauses up to that are slept as asked, and longer ones in Integer.MAX_VALUE ms steps, the loop sleeping the rest, so no step is longer than what remains. Strictly, the cast still fits for the first 999,999 ns above the bound; there this fix sleeps Integer.MAX_VALUE ms and the loop sleeps the sub-millisecond rest. The exact predicate would be pauseNS / 1000000 > Integer.MAX_VALUE (not run).

Trade-offs

  • One character; 1000000L * Integer.MAX_VALUE (2.1e15) is far from long overflow.
  • No hot-path cost: the comparison already runs once per sleep.

Drop the guard: a long sleepMS or Thread.sleep(Duration) (not run)

#

Thread.sleep takes long milliseconds, so declaring long sleepMS = pauseNS / 1000000, or sleeping Thread.sleep(Duration.ofNanos(pauseNS)) (JDK 19+), needs no guard at all.

Trade-offs

  • Removes the guard entirely; a larger diff than the missing zero.
  • Sub-millisecond behaviour does not change on the JDK main requires (25, gradle/libs.versions.toml:41): in OpenJDK 25.0.3 Thread.sleep(long, int) and Thread.sleep(Duration) both pass the total nanoseconds to the same sleepNanos (Thread.java:565-578, :596-602); the round-up the NOTE at RateLimiter.java:136-138 describes is not in this JDK's Thread.sleep(long, int).

Downstream note

#

Applications that let users set a SimpleRateLimiter rate should reject near-zero rates until this is fixed: with them, pauses over 2.49 days become 24.86-day sleeps.

How it was found

#

A semi-formal proof-obligation audit of SimpleRateLimiter.pause: its overflow guard must clamp only sleeps whose int cast would overflow. The guard's bound is 10 times below that point, and an executable test on main showed the oversleep. Independent reviewers re-ran it, scanned the boundary and argued the case for intended behaviour.

The method in full85 words
  • Method: the guard's obligation ("clamp only when (int) (pauseNS / 1000000) would overflow") was checked against its constant at RateLimiter.java:141. The bound 100000L * Integer.MAX_VALUE ns lies a factor of 10 below the overflow point, so pauses in between are clamped although the cast is exact; an executable JUnit test confirmed it on main 5adff78bb168 (2026-11-03).
  • Reviews: an independent reproduction with a boundary scan, an adversarial review by a model from another family (OpenAI GPT-5.6), an intended-behaviour review and a final review; see Independent checks.

History

#

Introduced in 4.10.3 and 5.0.0 by LUCENE-6075 (ebb9a5d971b5, 2014), the fix for an int overflow on pauses above 24.86 days. 4.10.2 asked for about 3 days for a 3-day pause; every release since, through 10.6.0 and main, sleeps 24.86 days.

Versions tested6 rows

LUCENE-6075 "don't overflow int in SimpleRateLimiter" (Michael McCandless; issue #7137, reported by Boaz Leskes; svn commit, no PR) is ebb9a5d971b5 on trunk and 13ed8b5697ca on branch_5x (both 2014-11-25), and cd08ecbb00ce on lucene_solr_4_10 (2014-12-01). It replaced Thread.sleep((int) (pauseNS/1000000), (int) (pauseNS % 1000000)), which could make Thread.sleep throw for pauses above 24.86 days, with the guard and its 10x-too-low bound. First released in 4.10.3 (2014-12-20) and 5.0.0. The constant is in every release tag from 4.10.3 to 10.6.0 (101 tags) and in none up to 4.10.2; lines 139-149 are unchanged since, apart from a whitespace-only reformat of line 146 (2d6ad2fee6df, LUCENE-9570, 2020-12-23); git log -S on main's history finds no other commit touching the constant. Upstream main f72004515ec (2026-11-03) still has it, as does aa366ae209a (re-checked 2026-11-04); the last commit to the file is 4b5917029f6 (#13001, 2024-02-05). The old releases were run with a main() probe making the same check, because the test needs a newer test framework. Caveat: the probe first calls pause(1), because up to 4.10.2 the constructor left lastNS at 0 (LUCENE-5948 made it start at System.nanoTime() in 4.10.3), so a first 3-day pause would be counted from time 0 of System.nanoTime; on later releases that call asks for at most about 1 microsecond.
