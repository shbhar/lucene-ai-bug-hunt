Sequential DrillSideways lets a top-N hit collector prune the shared base query, so sideways facet counts silently miss documents

In the sequential DrillSideways, a top-N hit collector with a finite threshold, like TopScoreDocCollectorManager(10, 10), also stops the base-query iteration that feeds the sideways facet counts: 150 shoes drilled into color=red show red 11, blue 10 instead of 75 and 75. Top hits match an exhaustive run; affected since 8.10.0.

The finding in 30 seconds

#

Drill sideways keeps a facet useful after the user picks a value: after a click on red, the color facet still lists blue 75, so the user can switch.

Two things to know first

#
  1. Drill sideways: for each drilled-down dimension, DrillSideways counts facets as if that dimension's own filter were not applied. Without an executor it does this in one pass: one iteration over the base query feeds the hit collector and every sideways counter.
  2. A top-N collector with a total-hits threshold t counts hits exactly up to t. After that it may call setMinCompetitiveScore on the scorer it was given, which tells that scorer it may skip documents that cannot enter the top N. A constant-score filter can then skip everything left.

The finding, step by step

#
  1. Index 4,000 products, half red and half blue; 150 of them are shoes, 75 red and 75 blue. Filter on shoes, drill down on color=red, and run the sequential DrillSideways (no executor) with TopScoreDocCollectorManager(10, 10): top 10 hits, hit count exact up to 10.
  2. You expect the color facet to ignore its own drill-down and count every shoe: red 75, blue 75. An unlimited threshold, or the concurrent DrillSideways, gives exactly that.
  3. Instead you get red 11, blue 10. At the 11th hit, one past its threshold, the hit collector raises its minimum competitive score. DrillSideways handed it the base query's own scorer, so the filter's iterator stops after doc 20 for everyone, and the facet counters never see shoes 21-149.
  4. Nothing fails, and the top 10 hits are the same as with an exhaustive collector. With IndexSearcher's default threshold, 1000, the drilled value stops at 1001: 1001 instead of 2250 on 48,000 documents.

Who is affected

#

The sequential DrillSideways with a caller's finite-threshold top-N manager (1000 included), via the 3-arg search or a null drill-down facets hook: TopScoreDocCollectorManager(n, t) on a filter-style or minShouldMatch > 1 base, a relevance-sorted TopFieldCollectorManager only on the latter; a narrow base and more than t drill-down hits. The default 2-arg search is safe since 9.12.0.

Mechanism, terms and numbers568 words

DrillSidewaysQuery.createWeight builds the base query's weight with the hit collector's score mode (DrillSidewaysQuery.java:129 on main 5adff78bb168), which is TOP_SCORES for a TopScoreDocCollectorManager or relevance-sorted TopFieldCollectorManager with a finite total-hits threshold. In the query-first strategy (DrillSidewaysScorer.java:130), doQueryFirstScoring hands the base Scorer itself to the hit collector and the sideways collectors (:199-200). Once more documents than its threshold have matched every dimension, the hit collector's setMinCompetitiveScore reaches the shared base scorer: with TopScoreDocCollectorManager a constant-score base empties its iterator and a minShouldMatch > 1 disjunction skips documents; a relevance-sorted TopFieldCollectorManager asks only for the bottom score itself, which prunes the minShouldMatch > 1 case only. The sideways FacetsCollectors never see the rest, so drill-sideways counts are silently too low (red 11, blue 10 instead of 75 and 75 in the repro; 1001 instead of 2250 at threshold 1000), while the top hits matched an exhaustive run in every executed case. The other two scoring strategies and the concurrent DrillSideways are exact. Introduced by LUCENE-10030 (8.10.0 / 9.0.0); affected through 10.6.0 and main. The fix hands the collectors a FilterScorable, as core's MultiCollector does; building the base weight with an exhaustive score mode is an optional extra.

The code (main 5adff78bb168)

#
  1. The base weight gets the hit collector's score mode. searchSequentially runs searcher.search(dsq, drillDownCollectorManager) (DrillSideways.java:467), and DrillSidewaysQuery.createWeight passes that score mode on: baseQuery.createWeight(searcher, scoreMode, boost) (DrillSidewaysQuery.java:129). The drill-down weights always use COMPLETE_NO_SCORES (:133-134). TopScoreDocCollector.scoreMode() is TOP_SCORES unless the threshold is Integer.MAX_VALUE (TopScoreDocCollector.java:58-60); IndexSearcher.search(Query, int) uses 1000 (IndexSearcher.java:100, :599).
  2. Query-first scoring shares the base scorer. When scoreSubDocsAtOnce() is set or the base cost is below a tenth of the drill-down cost (DrillSidewaysScorer.java:130; in the repro 150 vs 2,000), doQueryFirstScoring runs collector = ScoreCachingWrappingScorer.wrap(collector); setScorer(collector, baseScorer); (:199-200), and setScorer gives the same scorable to every sideways leaf collector (:746-751). ScoreCachingWrappingScorer forwards setMinCompetitiveScore (ScoreCachingWrappingScorer.java:93-96).
  3. The hit collector prunes. After more than t hits (only documents that match every dimension reach it, DrillSidewaysScorer.java:714-719), TopScoreDocCollector calls scorer.setMinCompetitiveScore(nextUp(topScore)) (TopScoreDocCollector.java:155-162). A constant-score base has the same score for every document, so ConstantScoreScorer replaces its iterator with an empty one (ConstantScoreScorer.java:149-153); a WANDScorer (minShouldMatch > 1) raises its bound and skips (WANDScorer.java:258-267). A relevance-sorted TopFieldCollector passes the bottom entry's own score instead (TopFieldCollector.java:337-343), which ConstantScoreScorer ignores (it needs minScore > score, :150), so with it only a minShouldMatch > 1 base is pruned.
  4. The sideways counters starve. The same iteration drives collectHit and collectNearMiss for the sideways collectors (DrillSidewaysScorer.java:697-735), so they stop receiving documents too. In the repro the iteration ends right after the 11th red shoe, doc 20: 11 red and 10 blue documents were counted.
  5. The other paths are exact. The drill-down-advance and union strategies give every collector a private Score scorable (DrillSidewaysScorer.java:336, :548, class at :753-764) that keeps Scorable's no-op setMinCompetitiveScore (Scorable.java:45-52); the concurrent DrillSideways runs separate searches. So the same query can be exact or wrong depending on an internal cost heuristic: an independent test got 1500 with the union strategy and 11 with scoreSubDocsAtOnce() for the same base and collector.

Counts can only be too low: every document still collected passes the base query, its filters, the live docs and the other drill-down dimensions.

Exposure and likelihood521 words
  • Who is hit. The sequential DrillSideways (no executor) plus a caller-supplied top-N hit collector manager with a finite t (1000 included): TopScoreDocCollectorManager(n, t), or, with a minShouldMatch > 1 base only, TopFieldCollectorManager(Sort.RELEVANCE, n, t). Routes on main: the 3-arg search(DrillDownQuery, CollectorManager, List), documented as usable "with any CollectorManagers" (DrillSideways.java:399-400), and the 2-arg search when createDrillDownFacetsCollectorManager() returns null, documented as valid (:133-135; the hit manager is then used alone, :338).
  • Which queries. Base scorers that react to the hit collector's minimum competitive score: with TopScoreDocCollectorManager, filter-only booleans, ConstantScoreQuery, point or term ranges and minShouldMatch > 1 disjunctions; with a relevance-sorted TopFieldCollectorManager, only minShouldMatch > 1 disjunctions (it passes the bottom score itself, which a constant-score scorer ignores; with it the filter and ConstantScoreQuery bases gave 75/75). On main a plain scoring TermQuery or plain SHOULD disjunction is not affected (verifier controls). The base must cost less than a tenth of the drilled value (the common "filter, then pick a broad facet value" case), or scoreSubDocsAtOnce() is overridden.
  • Scale. Pruning starts once more than t documents match every drill-down dimension, since only those reach the hit collector (DrillSidewaysScorer.java:714-719; near misses go to the sideways collector only, :730-735): with the repro's 150 shoes, 75 of them red, t = 74 gives 75/74 and t = 75, 100 or 149 give 75/75. With a constant-score base the loss is deterministic, and in one segment the drilled value ends at t + 1: 11 for t = 10; 1001 instead of 2250 (48,000 docs) and 1001 instead of 2000 (60,000 docs) at t = 1000. With about 12 segments and an IntPoint range base: 1171 instead of 3000. With a minShouldMatch > 1 base the loss depends on the data and the release: the history test's minShouldMatch=2 case is exact on 9.12.x and 10.0.0, gives 50/50 instead of 75/75 on 10.1.0-10.3.0 and 21/19 from 10.4.0.
  • Silent. No exception or log line; the counts look plausible and the top hits matched the exhaustive run in every executed case, with assertions on or off.
  • Default vs opt-in. Default codec and IndexWriterConfig and the default (sequential) DrillSideways mode; the test turns the query cache off, which is main's default (IndexSearcher.java:84; 10.6.0 and 9.12.3 default to an LRUQueryCache, which the test also turns off). The trigger is the caller's finite-threshold collector on the 3-arg path or the null hook. In 8.10.0-9.11.x the plain default search(DrillDownQuery, Collector) and the 2-arg manager search with default hooks were affected too, and drill-down counts were low as well. Since 9.12.0 the default 2-arg path wraps hits and facets in MultiCollectorManager, which forces a COMPLETE mode.
  • Workarounds. An Integer.MAX_VALUE threshold; the concurrent DrillSideways; or, as the 3-arg search's javadoc Note suggests (DrillSideways.java:402-404), a MultiCollectorManager holding the hit manager together with a FacetsCollectorManager, which then uses a COMPLETE mode (MultiCollector.java:104-121) and was exact in a verifier's control. A MultiCollectorManager around the hit manager alone is still affected.
  • Likelihood: plausible. No public report of this mechanism since 8.10.0 (2021).

Why it looks unintended

#
  • Sideways collectors are documented to see every hit matching the other dimensions, and the 3-arg search "can be used with any CollectorManagers".
  • A threshold only affects the hit count; core's MultiCollector ignores setMinCompetitiveScore so that "the other collector still sees all hits".
  • The same search is exact in the concurrent mode and in the other two scoring strategies.
The full argument257 words
  • The sideways contract. "Drill sideways counts include alternative values/aggregates for the drill-down dimensions so that a dimension does not disappear after the user drills down into it" (DrillSideways.java:50-52). Each sideways collector "exposes the hits that match on all DrillDownQuery dimensions, but treating their corresponding sideways dimension as optional" (:272-274).
  • Any collector manager is allowed. "This method can be used with any CollectorManagers" (:399-400); for the drill-down facets hook, "Returning null is valid if no drill down facet collection is needed" (:133-135).
  • The modes differ in speed, not results. The concurrent implementation "may be a little faster but does duplicate work"; the standard one "may be a little slower but avoids duplicate computations and query processing" (:57-62).
  • A threshold only affects the hit count. "If the query matches more than totalHitsThreshold hits then its hit count will be a lower bound" (TopScoreDocCollectorManager.java:50-54).
  • Core decided the same question. MultiCollector ignores setMinCompetitiveScore "so that if we wrap two collectors and one of them wants to skip low-scoring hits, then the other collector still sees all hits" (MultiCollector.java:195-202, LUCENE-8382, #9429), and uses a COMPLETE mode when its collectors' modes differ (:104-121).
  • History. LUCENE-10030 (#11069, PR #217) exposed the base scorer so that scores are computed lazily; its issue thread, PR description and CHANGES entry discuss only the cost of score(). Before it, every strategy gave collectors a private scorable that ignored the call. No facet test passes a TOP_SCORES hit collector to DrillSideways.
The devil's-advocate check241 words

The strongest case for "works as designed": TOP_SCORES explicitly permits skipping ("its iterator may safely ignore all documents whose score is less than the given minScore", Scorable.java:45-51); DrillSideways is @lucene.experimental (DrillSideways.java:69); its own top-N helpers use Integer.MAX_VALUE thresholds (:200-201, :232-233); and upstream knowingly lets an explicit CollectionTerminatedException from the hit collector cut sideways collection short (the TODO at DrillSidewaysScorer.java:149-151, TestDrillSideways.testCollectionTerminated), while #15220 asks for incomplete counts as an opt-in; and the 3-arg search's own javadoc Note recommends MultiCollectorManager for collecting hits and facets (DrillSideways.java:402-404), which makes the search exact.

Why it fails: the permission belongs to the collector that asked for TOP_SCORES; the sideways collectors (by default FacetsCollector, COMPLETE_NO_SCORES) never asked to skip, and core's MultiCollector blocks exactly this cross-collector pruning. Raising a minimum score is not a termination request; in #15220 a maintainer (gsmiller) described the design as "each wrapped collector can independently terminate, but those terminations don't impact the ability for other sibling collectors to continue". The result also depends on an internal cost heuristic and on the executor setting, and no javadoc, test or commit requires an exhaustive hit collector; the javadoc Note is advice on collecting facets for the whole query, and a MultiCollectorManager around the hit manager alone is still affected. Maintainers could still choose to document "the hit collector must be exhaustive" instead; that would contradict the 3-arg search's javadoc as written.

Suggested fix

#

Recommended FilterScorable for the collectors (the minimal fix)

In doQueryFirstScoring, hand the collectors new FilterScorable(baseScorer), which ignores setMinCompetitiveScore as MultiCollector does. Validated with gradle: the repro passes with assertions on and off, and 42 DrillSideways tests pass. Building the base weight with COMPLETE (or COMPLETE_NO_SCORES) on top is optional; with it all 307 facet tests and :lucene:facet:check -x test pass.

All options and trade-offs3 options · 802 words

Both code options were validated on 2026-11-03 with OpenJDK 25.0.3, seed DEADBEEF, in a clean scratch worktree of 5adff78bb168, and, for the finder's two-test repro, with the patched classes compiled over the main jars (a filter base with TopScoreDocCollectorManager(10, 10) and a minShouldMatch=2 base with TopFieldCollectorManager(Sort.RELEVANCE, 10, 10)).

The score-mode change alone is not a fix: ConstantScoreScorer then ignores the call, but WANDScorer still receives it, so the minShouldMatch=2 test fails with "minCompetitiveScore can only be set for ScoreMode.TOP_SCORES, but got: COMPLETE" under -ea and counts 12 instead of 100 under -da.

The open proposals #11128 (competitive iterators in DrillSidewaysScorer) and #11076 (one scoring path through doQueryFirstScoring) would widen the exposure if implemented without this guard.

Documentation only: require an exhaustive hit collector

#

State on the 3-arg search and on the null drill-down facets hook that the hit collector must not prune (threshold Integer.MAX_VALUE).

Trade-offs

Cheapest, but it contradicts "can be used with any CollectorManagers", keeps a silent failure mode for existing callers, and leaves the answer dependent on the cost heuristic. Not validated (no code change).

Downstream note

#

A product that shows drill-sideways counts while collecting hits with a finite-threshold top-N manager shows counts that are too low; every counted document still matches the user's query and filters, so nothing hidden is revealed.

How it was found

#

Code reading: an inventory of every place where a non-exhaustive score mode reaches a scorer whose matches feed more than one collector found that the sequential DrillSideways hands the base scorer to the hit collector. A differential JUnit test, the same search with an exhaustive collector and with the concurrent mode, confirmed it.

The method in full126 words

Method: non-formal (code reading, then an executable differential check), on main a9779ef3c193, 2026-10-27.

  • The inventory listed every site that passes a non-exhaustive ScoreMode to a weight whose matches feed more than one consumer. DrillSidewaysQuery.createWeight passes the hit collector's mode to the base weight, and doQueryFirstScoring hands that scorer to the hit collector and the sideways collectors.
  • A public-API JUnit test compared the sideways counts of the sequential DrillSideways with a TOP_SCORES hit collector against the same search with an exhaustive hit collector and against the concurrent DrillSideways; only the first was low.
  • Independent verifiers wrote their own tests from the claim, an adjudication re-ran them, a history sweep bisected the change to LUCENE-10030, and this doc's one-test repro was re-run on main 5adff78bb168.

Related items, each about a different defect:

  • #15220 (open, tflobbe, 2025-09), "DrillSideways and early termination": since the default path wraps the hit collector in MultiCollector, a hit collector that throws CollectionTerminatedException no longer stops facet collection; the reporter asks for stopping as an opt-in feature. Its 8.10 symptom, incomplete counts, is the same kind of result this bug gives (the 8.10.0-9.11.x default path was exposed to it), and the issue does not name the collector, but it attributes the counts to explicit termination and wants them: a related design question with a different, explicit mechanism, while this bug needs no exception at all. The maintainer reply (gsmiller) says sibling collectors continue by design and points to the 3-arg search with a custom MultiCollectorManager that "terminates all collection as soon as one collector terminates".
  • Draft PR #15221 (a failing test for that request) and #11040 (LUCENE-10001, make MultiCollector's termination handling configurable): the same opt-in termination request.
  • #12640: added the TODO in DrillSidewaysScorer.score about CollectionTerminatedException; with testCollectionTerminated it covers the explicit-exception case only.
  • #9429 (LUCENE-8382, fixed 2018): the precedent; MultiCollector stopped forwarding setMinCompetitiveScore so one collector cannot hide hits from another.
  • #11069 / PR #217 (LUCENE-10030): the introducing change; its discussion covers only the cost of score().
  • #12211 / #12212 ("DrillSideways may miss documents", fixed in 9.6.0): a two-phase matches() called twice. #11098 (LUCENE-10060): query caching bypassed DrillSidewaysScorer. Both different mechanisms.

LFV-789, snapshot of 2026-11-08

Registry title
Sequential DrillSideways lets a TOP_SCORES hit collector prune the shared base query, so drill-sideways facet counts silently miss matching documents
Area
facet / DrillSideways (sequential query-first scoring: score mode of the base weight and the scorable handed to the hit collector)
Priority
Medium, rank 38: Sequential DrillSideways silently undercounts sideways facets like LFV-358 but needs a caller-supplied finite-threshold top-N collector.
Impact class
silent wrong results
Impact note
Applications that run DrillSideways without an executor (the default sequential mode) and collect hits with a relevance-ranked top-N collector manager that has a finite total-hits threshold (TopScoreDocCollectorManager(n, t), including t = 1000, the threshold IndexSearcher#search(Query, int) uses, or TopFieldCollectorManager(Sort.RELEVANCE, n, t)), passed through the 3-arg search(DrillDownQuery, CollectorManager, List) or through the 2-arg search with createDrillDownFacetsCollectorManager() returning null (documented as valid), get drill-sideways facet counts that are silently too low (11 instead of 75; 1001 instead of 2250 at threshold 1000) whenever the base query's scorer can skip (filter-only or constant-score bases, minShouldMatch > 1 disjunctions) and the query-first strategy runs (base cost below a tenth of the drill-down cost, or scoreSubDocsAtOnce()); default codec, IndexWriterConfig and searcher, ordinary scale, -ea and -da alike; top hits stay correct, the concurrent DrillSideways and, since 9.12.0, the default 2-arg path are correct, while in 8.10.0-9.11.x the default search(DrillDownQuery, Collector) and the 2-arg manager search with default hooks undercounted both sideways and drill-down facets.
Summary
You run a sequential DrillSideways search (no executor) with a filter-style base query drilled down to color=red, and pass a TopScoreDocCollectorManager with a finite total-hits threshold (10 in the repro, or IndexSearcher's default 1000) as the hit collector through search(DrillDownQuery, CollectorManager, List). You expect the drill-sideways counts for color to include every document that matches the base query (75 in the repro), as the same search does with an exhaustive hit collector or with the concurrent DrillSideways. Instead the counts are silently too low (11, or 1001 instead of 2250 at threshold 1000): the base query is scored with the hit collector's TOP_SCORES mode and its scorer is handed to the hit collector, whose min-competitive-score updates make the shared base iteration skip documents that the sideways collectors then never see; the top hits are correct.
