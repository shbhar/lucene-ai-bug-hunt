The doc-values update iterator's intoBitSet also writes docs whose value the update removed, so a bit set that holds every returned doc can overflow

After a doc-values update removes a value, the iterator IndexWriter hands the codec still bulk-loads the removed doc in intoBitSet, so writing into a bit set that holds every returned doc throws and the commit fails. Only custom codecs hit it (Lucene's own passes a full window), in every release since 10.3.0.

The finding in 30 seconds

#

When an update removes a doc value, the iterator IndexWriter gives the codec skips that doc, but its intoBitSet first copies every doc with a value on disk, the removed one included, into a scratch bit set as long as the destination. A removed doc past the destination's end throws.

Background in three steps

#
  1. updateDocValues changes or removes doc values without reindexing. At commit, IndexWriter writes the column again. When it rewrites the whole column (on main, for example, whenever the batch removes a value), the codec's DocValuesConsumer gets an iterator that merges the on-disk values with the pending updates and skips docs whose value was removed.
  2. intoBitSet(upTo, bitSet, offset) sets bit doc - offset for each doc the iterator returns below upTo. Its javadoc defines it by that per-doc loop, so only the returned docs must fit: a shorter bit set is legal (#14142).
  3. Lucene's own doc-values writer calls it with a 65536-bit buffer for a window of at most 65536 docs, so every doc of the window always fits.

The finding, step by step

#
  1. A custom doc-values codec wraps the default one. In each write it counts the docs the column's iterator returns, allocates a FixedBitSet just big enough for them, calls intoBitSet(NO_MORE_DOCS, bits, 0) and then delegates the write.
  2. Index 65 documents with a numeric doc value on docs 0 and 64, and commit. Then updateDocValues(id:64, new NumericDocValuesField("n", (Long) null)), which removes doc 64's value, and commit again.
  3. In that update write the iterator returns only doc 0, so the codec allocates a 1-bit set. You expect bit 0 set and the commit to succeed: by its javadoc, intoBitSet should act like setting the returned docs one at a time.
  4. Instead it throws AssertionError: index=64, numBits=1 (with assertions off ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1): it first copies every doc that has a value on disk, removed doc 64 included, into a scratch the size of the 1-bit set, and only then applies the update.
  5. commit() throws. With assertions off the update stays buffered and the commit inside close() fails the same way; with them on the AssertionError is a tragic event, so the writer is rolled back and closed. No wrong bit reaches the destination and nothing wrong is written to the index.

Who is affected

#

Only a custom doc-values codec whose consumer, during an update write, calls intoBitSet (tagged @lucene.internal) with a bit set sized for the docs it gets back, in a batch that removes a value past that bit set. Lucene's own codec always passes a 65536-doc window. The commit fails loudly; nothing wrong is written.

Mechanism, terms and numbers741 words

When IndexWriter rewrites a whole doc-values column at commit after updateDocValues (on main, for example, any update batch that removes a value; on 10.3.0 through 10.6.0, with the default configuration, every update write), it hands the codec's DocValuesConsumer an iterator (ReadersAndUpdates.MergedDocValues) that merges the on-disk values with the pending updates and skips docs whose value was removed. Its intoBitSet override, added by #14552 in 10.3.0, first bulk-loads every on-disk doc in [docID(), upTo) into a scratch bit set as long as the destination, the removed docs included, and only then applies the updates.

Its javadoc says DocIdSetIterator#intoBitSet should behave exactly like the per-doc loop, which writes only the returned docs, so a destination that holds every returned doc is legal even when it ends before upTo; upstream said so in #14142 and fixed the same call shape in BitSetIterator (#14142) and IndexedDISI (#14922). Here a removed doc past the end of the destination makes the write throw (FixedBitSet.set in the repro), and IndexWriter.commit() fails. Lucene's own consumer always passes a full 65536-doc window, so only a custom codec hits it; nothing wrong is written. The fix is a clamp, as in BitSetIterator.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/)

#
  1. The dense rewrite. An update batch with a removal sets anyRemoval, so sparseDelta is false (index/ReadersAndUpdates.java:351-363), and handleDVUpdates passes the codec a NumericDocValues built on MergedDocValues (:494, :510); its intoBitSet delegates to MergedDocValues.intoBitSet (:832-834). The binary (:480-482) and sorted-numeric (:539, :580-582) update writes delegate to the same method (read only). A sorted-numeric update cannot remove a value through the stock field class (SortedNumericDocValuesField takes only a long, document/SortedNumericDocValuesField.java:77), so in practice numeric and binary updates trigger it.
  2. nextDoc() skips removed docs (:711-740): it loops until the current doc has a value, so doc 64 is never returned.
  3. intoBitSet (:742-794) sizes scratch to bitSet.length() (:749-755), calls onDiskDocValues.intoBitSet(upTo, scratch, offset) (:757), which writes every on-disk doc in [docID, upTo), then applies the update entries with set or clear, also up to upTo (:760-766), and ORs bitSet.length() bits into the destination (:768). Nothing limits the bulk load or the update loop to offset + bitSet.length(). Fix site: :757 and :760.
  4. In the repro (a sparse on-disk block), FixedBitSet.set(64) on the 1-bit scratch fails its assert (util/FixedBitSet.java:296) or, with assertions off, the array store (:299): the scratch has one 64-bit word.
  5. Exact trigger: the field has on-disk values (otherwise the method takes the default loop, :743-747), and a consumer calls intoBitSet on this iterator with offset + bitSet.length() < upTo, in an update batch that resets (passes null for) a doc in [offset + bitSet.length(), upTo). If that doc has an on-disk value, the bulk load (:757) fails on it, as below; if it has none, the update loop's scratch.clear (:764) still touches it and fails in FixedBitSet.clear (util/FixedBitSet.java:336). Without a reset every on-disk doc and every update entry is a returned doc, so a destination that covers the returned docs covers them all. How the bulk load fails depends on how the on-disk column is encoded. A sparse block (as in the repro) or a column where every doc has a value (as in the independent reproduction) fails in FixedBitSet.set, and with assertions off only once the doc lies past the scratch's last 64-bit word; inside it the stray bit stays in the scratch and is never copied out (orRange copies only bitSet.length() bits, :768). A dense block (more than 4095 docs with a value in a 65536-doc window, codecs/lucene90/IndexedDISI.java:111, :120) clamps its copy to the destination (:724) and then throws IllegalStateException: There are bits set in the source bitset that are not accounted for (:742-751), with assertions on or off, even when the doc lies inside the scratch's last word. No wrong bit reaches the destination in any case (executed: one probe test, five cases, sparse and dense, each inside and past the last word, and a reset without a value past it, assertions on and off; with fix A every case passes).
  6. Lucene's own caller cannot hit it: IndexedDISI.writeBitSet passes a 65536-bit buffer for a window of at most 65536 docs (codecs/lucene90/IndexedDISI.java:206-213).
Exposure and likelihood226 words
  • Who is hit: only a custom DocValuesFormat (a public codec extension point, @lucene.experimental) whose consumer calls intoBitSet (public, @lucene.internal) on the iterator it gets during an update write, with a bit set sized for the docs it returns rather than for the window, in a batch that resets (removes the value of) a doc past that bit set.
  • Default vs opt-in: a custom codec is required. Given such a consumer, nothing unusual is needed on the writer side: on main any update batch with a removal takes this path with the default IndexWriterConfig (default maxDocValuesOverlays 8, IndexWriterConfig.java:115); on 10.3.0 through 10.6.0 every doc-values update write does. Numeric, binary and sorted-numeric update writes share the method; a sorted-numeric update cannot remove a value through SortedNumericDocValuesField, so in practice numeric and binary updates trigger it.
  • Effect: For a consumer that makes this call, the update write fails and IndexWriter.commit() throws. An AssertionError (assertions on) is a tragic event, so the writer is rolled back and closed; any other exception (assertions off, or, by reading, a dense block's IllegalStateException) leaves the update buffered, and close() fails the same way. Loud: no wrong value reaches the destination and nothing wrong is written to the index.
  • Scale and likelihood: any index size (the repro has 65 docs); contrived. No report found since 10.3.0 (see Prior reports).

Why it looks unintended

#
  • The javadoc says intoBitSet "should behave exactly as" the per-doc loop, which writes only the docs the iterator returns.
  • Upstream calls a shorter destination legal when no returned doc lies past it: #14142, the BitSetIterator comment and the test-framework case "This call is legal".
  • Before #14552 this iterator used that loop: the same test passes on 10.2.2.
The full argument230 words
  • Contract. DocIdSetIterator#intoBitSet (search/DocIdSetIterator.java:186-210): "This should behave exactly as if implemented as below, which is the default implementation: for (int doc = docID(); doc < upTo; doc = nextDoc()) { bitSet.set(doc - offset); }". Its only preconditions are offset <= docID() and a positioned iterator; the repro meets both.
  • Upstream's own reading. #14142 (jpountz, merged 2025-01-16): having upTo - offset exceed the length of the destination is legal "as long as no bits are set beyond offset + bitSet.length()" (as jpountz put it there). It left the comment "The destination bit set may be shorter than this bit set. This is only legal if all bits beyond offset + bitSet.length() are clear." (util/BitSetIterator.java:126-128) and the test-framework case "This call is legal, since all "set" bits are in the range" (BaseDocIdSetTestCase.java:230-245). #14922 fixed IndexedDISI's dense block for the same shape.
  • The rest is documented use. DocValuesConsumer "is free to iterate over the values multiple times" (codecs/DocValuesConsumer.java:62-64), and a null NumericDocValuesField value means "the existing fields value should be removed on update" (document/NumericDocValuesField.java:77-78).
  • History. Before #14552 MergedDocValues used the default loop, and the same test passes on 10.2.2. In the #14552 review, jpountz asked to size the scratch by bitSet.length() rather than upTo - offset because callers pass upTo = NO_MORE_DOCS; nobody discussed a destination shorter than the window.
The devil's-advocate check142 words

The strongest case for "intended": intoBitSet is @lucene.internal, DocValuesConsumer is @lucene.experimental, Lucene's only caller passes a full window, and MergedDocValues already throws UnsupportedOperationException from advance/advanceExact (ReadersAndUpdates.java:695-703), so it is not a general-purpose iterator. An independent reviewer from another model family (OpenAI GPT-5.6) rated it not real on that scope ground alone, while reproducing it and agreeing on the root cause and the fix.

Why it fails: the tags warn about API stability; they do not narrow the javadoc's contract. advance fails by design with an explicit UnsupportedOperationException; intoBitSet is overridden on purpose for this very call path and overflows by accident. Upstream declared this call shape legal and fixed it as a bug in two sibling classes. Scope is why it is Low, not why it is intended; a maintainer may still call it hardening.

Suggested fix

#

Recommended A: bulk-load only what fits, then finish with the default loop (recommended)

Bulk-load only the docs that fit in the destination, then let the default per-doc loop finish the window, as BitSetIterator does since #14142: limit = min(upTo, offset + bitSet.length()) for the bulk load and the update loop, then super.intoBitSet(upTo, bitSet, offset) if docs remain. +8/-2 lines; validated.

// Only bulk-load the docs that fit in the destination; any doc left before upTo is handled by
// the default loop below, which only writes the docs this iterator returns.
final int limit = (int) Math.min(upTo, (long) offset + bitSet.length());
onDiskDocValues.intoBitSet(limit, scratch, offset);
docIDOnDisk = onDiskDocValues.docID();
for (int doc = updateDocValues.docID(); doc < limit; doc = updateDocValues.nextDoc()) {
  // set or clear doc - offset, unchanged
}
// ... orRange and the current-doc update, unchanged; then at the end of the method:
if (docIDOut < upTo) {
  super.intoBitSet(upTo, bitSet, offset);
}

A: bulk-load only what fits, then finish with the default loop (recommended) (validated by the checks)

#

In ReadersAndUpdates.MergedDocValues#intoBitSet, limit the on-disk bulk load and the update loop to min(upTo, offset + bitSet.length()) and, after the current doc is updated, hand any rest of the window to super.intoBitSet. This is the pattern BitSetIterator has used since #14142. +8/-2 lines.

// Only bulk-load the docs that fit in the destination; any doc left before upTo is handled by
// the default loop below, which only writes the docs this iterator returns.
final int limit = (int) Math.min(upTo, (long) offset + bitSet.length());
onDiskDocValues.intoBitSet(limit, scratch, offset);
docIDOnDisk = onDiskDocValues.docID();
for (int doc = updateDocValues.docID(); doc < limit; doc = updateDocValues.nextDoc()) {
  // set or clear doc - offset, unchanged
}
// ... orRange and the current-doc update, unchanged; then at the end of the method:
if (docIDOut < upTo) {
  super.intoBitSet(upTo, bitSet, offset);
}

Trade-offs

  • When the destination covers the window (Lucene's own caller), limit == upTo and the tail never runs, so nothing changes. A short destination keeps the bulk path up to its end.
  • If a returned doc does lie past the destination (an illegal call), the tail behaves like the reference loop.
  • Sizing the scratch to the window instead is not an option: callers pass upTo = NO_MORE_DOCS (the #14552 review). No benchmark was run.

B: fall back to the default loop for a short destination (validated by the checks)

#

One condition at the top of the method: when the destination ends before upTo, use the per-doc loop, exactly as 10.2.2 did for every call.

if (onDiskDocValues == null || (long) offset + bitSet.length() < upTo) {
  super.intoBitSet(upTo, bitSet, offset);
  return;
}

Trade-offs

Simplest, but gives up the bulk path for every short destination, including ones where only the last few docs fall outside. No Lucene caller passes a short destination today.

What the checks validated

Same worktree and seed: the repro passes with assertions on and off; the same 10 suites pass (142 tests, 2 skipped, 0 failures); checkGoogleJavaFormat, ecjLintMain and forbiddenApisMain pass.

C: document a full-window precondition

#

State that this iterator needs upTo - offset <= bitSet.length().

Trade-offs

No code change, but it contradicts #14142, testIntoBitSetBoundChecks and the clamps in BitSetIterator and IndexedDISI. Not recommended.

Downstream note

#

Relevant downstream only to custom doc-values codecs that call intoBitSet on the update-time iterator with a bit set shorter than the window: until a fix lands, clamp upTo to offset + bitSet.length() or size the bit set to maxDoc - offset (a maxDoc-sized bit set passed in two independent controls).

How it was found

#

Semi-formal: a proof-obligation audit of MergedDocValues.intoBitSet against the DocIdSetIterator#intoBitSet contract. The obligation, that only returned docs are written, fails for docs whose value a pending update removed; a one-test JUnit repro on stock main witnessed it.

The method in full125 words
  • Obligation: for every legal call (offset <= docID(), a positioned iterator), the bits set and the final docID() equal those of the per-doc loop for (doc = docID(); doc < upTo; doc = nextDoc()) bitSet.set(doc - offset) (DocIdSetIterator.java:186-210); the loop only needs the returned docs to fit.
  • Finding: nextDoc() skips docs whose value an update removed (ReadersAndUpdates.java:711-740), but the bulk path loads every on-disk doc below upTo into a scratch sized to the destination before the update entries clear them (:749-766), so it also needs the removed docs to fit.
  • Witness: a JUnit test on the stock main jars, then an independent reproduction, cross-model reviews, an intended-behaviour review, an adjudication and a separate re-run (see Independent checks).

Registry title
During a doc-values update rewrite, the iterator IndexWriter hands to a DocValuesConsumer (ReadersAndUpdates.MergedDocValues) throws from intoBitSet when the destination bit set covers every returned doc but ends before upTo, because it bulk-loads on-disk docs whose values the update removed, contrary to the DocIdSetIterator#intoBitSet contract (latent: Lucene's own consumer always passes a full 65536-doc window; since 10.3.0, #14552)
Area
index / doc-values update write path (ReadersAndUpdates.MergedDocValues.intoBitSet, the iterator handed to a DocValuesConsumer)
Priority
Low, rank 1215: Latent: the iterator IndexWriter hands to a doc-values codec during an update rewrite throws from intoBitSet when the destination ends before upTo and the update removed a value past it, so commit() fails (with assertions off the update stays buffered and close() fails too; with them on the writer is rolled back and closed), in releases 10.3.0 through 10.6.0. Lucene's own consumer always passes a full window and nothing is written wrongly, so only contrived custom codec code reaches it.
Impact class
minor
Impact note
Latent: hits only a custom DocValuesFormat consumer (public codec extension point, @lucene.experimental) that, while IndexWriter rewrites a doc-values column after an update, calls the @lucene.internal DocIdSetIterator#intoBitSet on the iterator it is given with a destination sized for the docs that iterator returns rather than for the whole window, in an update batch that removes a value past the end of that destination; the update write then throws and IndexWriter.commit() fails, at any scale: with -da (ArrayIndexOutOfBoundsException) the update stays buffered and close() fails the same way, with -ea the AssertionError is a tragic event that rolls the writer back and closes it; Lucene's own consumer always passes a full 65536-doc window, no wrong value reaches the destination and nothing is written to the index wrongly [exec + read].
Summary
A custom doc-values codec, while IndexWriter rewrites a numeric column after a doc-values update, positions the iterator it is given on its first doc and calls intoBitSet(NO_MORE_DOCS, bits, 0) with a bit set just large enough for the docs that iterator returns; in the repro a 65-doc segment has values in docs 0 and 64 and the update removes doc 64's value, so the iterator returns only doc 0 and a 1-bit destination should get bit 0, because the javadoc says intoBitSet must behave exactly like the loop 'for (doc = docID(); doc < upTo; doc = nextDoc()) bitSet.set(doc - offset)'. Instead ReadersAndUpdates.MergedDocValues.intoBitSet first bulk-loads every on-disk doc below upTo, including the removed doc 64, into a scratch bit set of the destination's size, so FixedBitSet.set(64) fails (AssertionError 'index=64, numBits=1' with -ea, ArrayIndexOutOfBoundsException 'Index 1 out of bounds for length 1' with -da) and IndexWriter.commit() throws. Upstream declared this call shape legal when it fixed the same failure in BitSetIterator (#14142) and IndexedDISI (#14922); Lucene's own consumer always passes a full window, so only custom codecs hit it.
