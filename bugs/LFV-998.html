BlendedInfixSuggester: num x numFactor overflows an int, so asking for all suggestions throws and some large num values return fewer

BlendedInfixSuggester.lookup("luc", false, Integer.MAX_VALUE) throws IllegalArgumentException: numHits must be > 0, even with one entry: the suggester fetches num x numFactor (10) hits, computed in an int, and 2,147,483,647 x 10 wraps to -10. Other large values wrap to small counts: with 8 matches, num = 429,496,731 silently returns 1 suggestion.

The finding in 30 seconds

#

To re-rank by where the typed word sits, BlendedInfixSuggester asks its parent for num x numFactor hits and later divides that count by numFactor to get num back. The product is an int: above Integer.MAX_VALUE it wraps, to a negative count, which the collector rejects, or to a small one, which keeps too few results.

Background: how BlendedInfixSuggester picks its suggestions

#
  1. AnalyzingInfixSuggester finds the entries with a word that starts with what the user typed and returns the num with the highest weight.
  2. BlendedInfixSuggester extends it and favours entries whose matched word comes early, which can change the order. So it over-fetches: it asks the parent for num x numFactor hits by weight (numFactor 10 by default).
  3. It lowers each hit's weight by the matched word's position and keeps the best count / numFactor, where count is the number it asked the parent for: normally exactly num.

The finding, step by step

#
  1. Build a BlendedInfixSuggester with the default constructor from one entry, lucene, and ask for every completion of luc: lookup("luc", false, Integer.MAX_VALUE). num is documented only as the "maximum number of results to return".
  2. You expect [lucene], the same as num = 1000 returns.
  3. Instead it throws IllegalArgumentException: numHits must be > 0; please use TotalHitCountCollector if you just need the total hit count. To re-rank by word position the suggester first fetches num x numFactor hits (numFactor is 10 by default), computed in an int: 2,147,483,647 x 10 = 21,474,836,470, which wraps to -10.
  4. Other large values wrap to a small positive count, which the suggester divides by numFactor to get back "the num initially requested". With 8 matching entries, num = 429,496,731 wraps to 14, and 14 / 10 = 1: one of the 8 suggestions, no error. num = 429,496,730 wraps to 4; with 4 / 10 = 0 it throws NoSuchElementException.
  5. Every num above Integer.MAX_VALUE / numFactor wraps: from 214,748,365 with the default factor, from 2,147,484 with numFactor 1000. It is as old as the class (4.7.0, 2014) and is in 10.6.0 and main.

Who is affected

#

Applications that call BlendedInfixSuggester.lookup with a num above Integer.MAX_VALUE / numFactor (214,748,364 for the default 10), for example Integer.MAX_VALUE for "all suggestions" or a count passed through from a request. Default constructor, any built suggester (executed with one entry). Ordinary counts are unaffected; rare.

Mechanism, terms and numbers788 words

BlendedInfixSuggester over-fetches: to return num suggestions it asks its parent AnalyzingInfixSuggester for num * numFactor hits (numFactor is 10 by default), re-scores them by the position of the matched word, and divides the count back ("we reduce the num to the one initially requested", int actualNum = num / numFactor). The multiplication is a plain int product (BlendedInfixSuggester.java:199 on main 645d4fe14a20), so for num > Integer.MAX_VALUE / numFactor (214,748,364 for the default factor) it wraps. lookup("luc", false, Integer.MAX_VALUE), a natural way to ask for every suggestion, then fails on any built suggester (executed with one entry) with IllegalArgumentException: numHits must be > 0, a message about an argument the caller never passed. At other values the wrapped count is small and positive and the lookup silently returns too few results: with 8 matching entries, num = 429,496,731 returns 1, while num = 1000 returns all 8; num = 429,496,730 throws NoSuchElementException. On stock code the same huge values that do not wrap fail with OutOfMemoryError in the parent's collector pre-size (the sibling bug LFV-1004), so the short list is the correctness impact (at Integer.MAX_VALUE stock code fails either way) and returning every match needs both fixes: a saturating long product here and a collector cap at maxDoc there, validated together. The defect is as old as the class (LUCENE-5354, 4.7.0, 2014) and is in every release up to 10.6.0 and main.

The bug (main 645d4fe14a20)

#
  1. Contract. Lookup.lookup(key, onlyMorePopular, num): "@param num maximum number of results to return" (Lookup.java:190; also :206, :219). No bound and no check. The class is @lucene.experimental (BlendedInfixSuggester.java:54); its javadoc says "it increases the number of elements searched and applies the ponderation after" (:49-52). DEFAULT_NUM_FACTOR = 10 (:64, set at :90); the two longer constructors take numFactor unchecked (:114, :152).
  2. The product, once, in int. Three lookup overloads pass num on unchanged ("Don't * numFactor here since we do it down below, once, in the call chain", :162, :174, :186). The last one multiplies: "We need to do num * numFactor here only because it is the last call in the lookup chain" and return super.lookup(key, contextQuery, num * numFactor, allTermsRequired, doHighlight); (:198-199). Java int arithmetic wraps modulo 2^32: 2,147,483,647 x 10 = 21,474,836,470 is -10; 429,496,731 x 10 = 4,294,967,310 = 2^32 + 14 is 14.
  3. Negative count. The parent builds new TopFieldCollectorManager(SORT, num, null, 1) with the wrapped value (AnalyzingInfixSuggester.java:739), which throws for numHits <= 0 (TopFieldCollectorManager.java:62-65).
  4. Small positive count. The search runs and the parent hands the same wrapped value to createResults (AnalyzingInfixSuggester.java:745). The override divides it back: "we reduce the num to the one initially requested", int actualNum = num / numFactor; (BlendedInfixSuggester.java:226-227), which restores the caller's num only when the product did not wrap. boundedTreeAdd keeps at most actualNum results (:281, :294-306); with actualNum = 0 the check results.size() >= num is true on the empty set and results.first() (:297-298) throws NoSuchElementException.
  5. Never more, never outside the filter. A wrapped product is always below the true one, so the list can only get shorter. The context filter is part of the query (AnalyzingInfixSuggester.java:692-715), independent of num.

Tied to LFV-1004

#

On stock code the parent pre-sizes its collector by the fetch count (LFV-1004, suggester-lookup-presizes-by-num), so huge values that do not wrap fail too: with a 2 GB heap, num = 214,748,364 (product 2,147,483,640) throws OutOfMemoryError: Java heap space in the parent and in the blended class alike. The wrap turns that loud failure into a misleading exception or a short list. Each fix alone leaves Integer.MAX_VALUE failing; together they return every match.

Exposure and likelihood257 words
  • Who is hit. Callers of lookup on a BlendedInfixSuggester with num above Integer.MAX_VALUE / numFactor: 214,748,364 for the default factor, 2,147,483 for numFactor 1000, 3,579,139 for numFactor 600. For example Integer.MAX_VALUE as "all suggestions" (the module's own TestFSTCompletion uses it that way on the separate FSTCompletion API, TestFSTCompletion.java:157, :165), or a count forwarded from a request without a bound.
  • Default or opt-in. The default constructor and default numFactor; the class itself is an opt-in, @lucene.experimental suggester. Counts in the tens to thousands are not affected.
  • Effect. At Integer.MAX_VALUE every lookup on a built suggester fails (the collector is created before the search, AnalyzingInfixSuggester.java:739; executed with one entry), with an IllegalArgumentException that blames numHits and suggests TotalHitCountCollector, neither of which the caller used. At specific values in the hundreds of millions (millions with a large numFactor) the lookup silently returns fewer suggestions than exist, and a larger num can return fewer than a smaller one. That short list is the correctness impact: on stock code Integer.MAX_VALUE fails anyway (LFV-1004), so there the wrap swaps one error for another.
  • Workaround. Pass a finite count no larger than Integer.MAX_VALUE / numFactor; with LFV-1004 also present, small enough for the collector the parent pre-allocates (in practice the number of entries, getCount()).
  • How likely: rare (registry likelihood rare, priority low). The natural trigger fails loudly on the first call, so developers meet it in testing and pick a finite count; the silent values are narrow windows; the recorded searches found no public report since 4.7.0.

Why it looks unintended

#
  • num is the "maximum number of results to return" (Lookup.java:190); nothing bounds it.
  • The code says the division restores "the num initially requested"; after a wrap it does not, so a larger num can return fewer: 1,000 gives 8, 429,496,731 gives 1.
  • SOLR-7865 already fixed a count that did not match num in this very expression.
The full argument234 words
  • Contract. num is a maximum (Lookup.java:190); the BooleanQuery overload says "@param num number of items to return" (AnalyzingInfixSuggester.java:617). Nothing bounds it or says the subclass multiplies it.
  • The code's own intent. "we reduce the num to the one initially requested" (BlendedInfixSuggester.java:226) holds only without overflow.
  • A positive num must not produce these errors. The IllegalArgumentException message is false for the caller's input, the NoSuchElementException is undocumented, and a larger num can return fewer results (1,000 gives 8, 429,496,731 gives 1), with the count jumping between nearby values (429,496,730 throws, 429,496,732 gives 2); a top-N lookup should not shrink when N grows.
  • History: a count that does not match num was a bug here. SOLR-7865 ("BlendedInfixSuggester was returning more results than requested", Arcadius Ahouansou's patch, committed by Michael McCandless as 602a1f50e72, 2015) fixed the opposite symptom, num * numFactor applied several times along the call chain, and left one multiplication, still in int: today's line 199.
  • History: overflow in this class's arithmetic was a bug. On LUCENE-8343 (#9390) Adrien Grand asked of the score arithmetic "It might even introduce overflows?", and Alessandro Benedetti fixed it (e0232f10450, 2018, "weight long overflow fix + test"). Reviewing LUCENE-6339 (#7400), Michael McCandless asked of a suggester's queue-size product whether it "could possibly overflow int? Maybe use long".
  • Tests. TestBlendedInfixSuggester uses num up to 10 only; no test accepts the wrap.
The devil's-advocate check194 words

The strongest "works as designed" case (first raised by the finder's refute-lens reviewer from another model family, OpenAI GPT-5.6, then argued by the intended-lens reviewer and the devil's advocate): num is only a maximum; a num in the hundreds of millions is unreasonable for a suggester; the class is @lucene.experimental and warns that it "might be costly"; the small-num design is explicit in LUCENE-5354 (Remi Melisson: "If I want 10 suggestions, then I search against the current ordered index for the 100 first results"); and on stock code the parent already throws OutOfMemoryError at these values.

Why it fails: that bears on likelihood and priority, not on correctness. No doc bounds num or numFactor; a design for small num does not make a false error message or a wrong count acceptable for a large one; @lucene.experimental is about API stability; and once the parent's pre-size is fixed (LFV-1004), the wrap is the only thing that still fails. The adjudication (confirmed, high confidence, priority low), the independent reproduction, the cross-model review and the intended-behaviour check treat it as a real defect; the refute-lens review's "not real" (low) was procedural, as it could not run Java.

Suggested fix

#

Recommended Multiply in long and saturate at Integer.MAX_VALUE, plus LFV-1004's collector cap

Compute num x numFactor in long and saturate it at Integer.MAX_VALUE (+3/-1 in BlendedInfixSuggester.lookup), together with LFV-1004's collector cap at maxDoc (+3/-1): each alone still fails at Integer.MAX_VALUE. Validated with gradle: the repro passes, and the whole suggest module (237 tests) and check pass, with assertions on and off.

// BlendedInfixSuggester.lookup(key, contextQuery, num, ...), line 199:
// Multiply in long and saturate: in int, num * numFactor wraps once num > MAX_VALUE / numFactor
int fetch = (int) Math.min((long) num * numFactor, Integer.MAX_VALUE);
return super.lookup(key, contextQuery, fetch, allTermsRequired, doHighlight);

// AnalyzingInfixSuggester.lookup, line 739 (LFV-1004's fix):
int numHits = Math.min(num, Math.max(1, searcher.getIndexReader().maxDoc()));
TopFieldCollectorManager c = new TopFieldCollectorManager(SORT, numHits, null, 1);

Multiply in long and saturate at Integer.MAX_VALUE, plus LFV-1004's collector cap (validated by the checks) (recommended)

#

Past the threshold the fetch count becomes Integer.MAX_VALUE, so createResults keeps Integer.MAX_VALUE / numFactor results (214,748,364 for the default) instead of a wrapped count, and every larger num behaves like num = 214,748,364. Below the threshold nothing changes. The parent still hands the uncapped count to createResults (AnalyzingInfixSuggester.java:745); only the collector is capped. It is the end state of the neighbouring queue-size product in NRTSuggester (#11923 made that product long; its Math.min saturation was already there), and the fix recommended for LFV-999.

// BlendedInfixSuggester.lookup(key, contextQuery, num, ...), line 199:
// Multiply in long and saturate: in int, num * numFactor wraps once num > MAX_VALUE / numFactor
int fetch = (int) Math.min((long) num * numFactor, Integer.MAX_VALUE);
return super.lookup(key, contextQuery, fetch, allTermsRequired, doHighlight);

// AnalyzingInfixSuggester.lookup, line 739 (LFV-1004's fix):
int numHits = Math.min(num, Math.max(1, searcher.getIndexReader().maxDoc()));
TopFieldCollectorManager c = new TopFieldCollectorManager(SORT, numHits, null, 1);

Trade-offs

  • Both parts are needed for Integer.MAX_VALUE. Saturation alone sends 2,147,483,647 to the parent, which pre-sizes its collector and throws OutOfMemoryError: Requested array size exceeds VM limit (executed, standalone, 512 MB heap). The cap alone gives min(-10, maxDoc) = -10 and the same IllegalArgumentException (executed). So this fix goes with LFV-1004's fix, in the same change or after it.
  • Cap only the collector. If the count handed to createResults were capped too, the division would give maxDoc / numFactor and truncate again (code reading).
  • Ceiling. A lookup returns at most Integer.MAX_VALUE / numFactor results, far above any realistic suggester. The fix removes the false errors; it does not make billions of results cheap (memory and time still bound them).
  • Equivalent to the finder's sketch, which saturates at the largest multiple of numFactor that fits an int: both give createResults the same Integer.MAX_VALUE / numFactor.
  • numFactor <= 0, not addressed. The constructors do not check numFactor (a remark of the intended-lens reviewer). The fix changes a result only where the true product exceeds Integer.MAX_VALUE; with a negative numFactor that takes a negative num (-2,147,483,647 x -2: -2 today, Integer.MAX_VALUE with the fix), and a negative product can still wrap (Integer.MAX_VALUE x -10 gives 10 before and after). A patch could validate numFactor > 0 in the constructors; not part of this report.

Downstream note

#

Solr passes the request parameter suggest.count unchanged to lookup as num, so a Solr deployment with a BlendedInfixSuggester has to bound suggest.count itself.

How it was found

#

A differential probe ran every suggester with growing num and flagged this class: IllegalArgumentException at Integer.MAX_VALUE where num = 1000 returns all 8 matching entries. A 32-bit SMT bit-vector model then proved the wrap-free bound and found the silent short-list values, and each was executed on the stock jars.

The method in full143 words

Method: non-formal first signal, then a small formal model (the hunt's hunt unit for suggester num sizes, 2026-10-28, main a9779ef3c193).

  • First signal. A numeric-limits probe ran 9 Lookup configurations (8 classes) at growing num on the stock main jars (8 entries, 1 GB heap): BlendedInfixSuggester threw IllegalArgumentException at Integer.MAX_VALUE and 214,748,365 and NoSuchElementException at 429,496,730, where num = 1000 returns 8.
  • Model. A Z3 32-bit bit-vector model of the num arithmetic proved the wrap-free region num <= Integer.MAX_VALUE / numFactor, showed the bound tight, and produced the silent-truncation witnesses the probe had not shown (429,496,731 gives 1 of 8; 4,294,969 with numFactor 1000). An exhaustive evaluation of every positive int counted the outcomes, and a differential sweep covered 11 Lookup configurations.
  • Execution. Each witness ran on the stock jars, then became a JUnit; the minimal-repro step reduced it to one method.

History

#

Introduced with the class by LUCENE-5354 (fb5fd910780, 2014-01-09; first release 4.7.0). SOLR-7865 (602a1f50e72, 2015) cut the call chain to today's single int product, which moved the threshold to 214,748,365. Executed on 21 releases from 4.7.0 to 10.5.2, 10.6.0 and main; unchanged on main.

Versions tested7 rows

Introduced: fb5fd910780 (trunk) / 89a9302d5a7 (branch_4x), 2014-01-09, LUCENE-5354 "add new BlendedInfixSuggester" (#6418; Remi Melisson's patch, committed by Michael McCandless). The class arrived with both halves: lookup overrides that pass num * numFactor down as an int, and int actualNum = num / numFactor (line 227 still blames to fb5fd910780).

Later changes: LUCENE-6050 (127eed36dd5, 5.0.0) and LUCENE-6464 (213cdf67930, 5.2.0) added overloads that multiplied again; SOLR-7865 (602a1f50e72, 2015; in 5.3.2, 5.4.1, 5.5.0 and later) kept only the last multiplication, still in int: line 199 today (blame 213cdf67930). So the default-factor threshold was 21,474,837 in 4.7.0-4.10.4 (num x 100), 2,147,484 in 5.0.0-5.3.1 and 5.4.0 (num x 1000) and 214,748,365 since. In 4.7.x a negative product threw NegativeArraySizeException instead. Old releases ran on JDK 25.

Finding record

LFV-998, snapshot of 2026-11-07

Registry title
BlendedInfixSuggester.lookup computes num * numFactor in int, so a large num wraps: num = Integer.MAX_VALUE throws IllegalArgumentException 'numHits must be > 0', some values throw NoSuchElementException, and specific values silently return fewer suggestions than exist
Area
suggest / analyzing: BlendedInfixSuggester lookup over-fetch (num * numFactor)
Priority
Low, rank 656: BlendedInfixSuggester's int num * numFactor wrap is the same class as the SpellChecker 10 * numSug row LFV-996 (mostly a misleading IllegalArgumentException at Integer.MAX_VALUE, silent truncation only at specific huge num values) in the opt-in suggest module.
Impact class
wrong error
Impact note
Applications that use BlendedInfixSuggester (any constructor, including the default numFactor 10) and pass a num above Integer.MAX_VALUE / numFactor (214,748,364 for the default factor, 2,147,483 for numFactor 1000, 3,579,139 for 600), most naturally Integer.MAX_VALUE as 'all suggestions', get a misleading IllegalArgumentException 'numHits must be > 0', or for some values a NoSuchElementException or a silently short list such as 1 of 8, on every such lookup at any index size; ordinary num values are not affected, and on stock code the same num range would otherwise fail with OutOfMemoryError in the parent class's collector pre-size (LFV-1004, a separate finding), so returning every match needs both fixes.
Summary
You build a BlendedInfixSuggester with its defaults (numFactor 10) from 8 entries that match 'luc' and call lookup("luc", false, Integer.MAX_VALUE) to get all suggestions; num is documented as the 'maximum number of results to return', so you expect the same 8 suggestions that num = 1000 returns. Instead the over-fetch count num * numFactor is computed in int (BlendedInfixSuggester.java:199) and wraps: a negative product throws IllegalArgumentException 'numHits must be > 0; please use TotalHitCountCollector ...' (num = Integer.MAX_VALUE or 214748365), a product below numFactor leaves room for 0 results and throws NoSuchElementException (num = 429496730), and a small positive product silently cuts the list (num = 429496731 returns only [lucas]; with numFactor 1000 already num = 4294969 does). So the number of suggestions can go down as num goes up.
