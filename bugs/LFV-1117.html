GraphTokenStreamFiniteStrings.getFiniteStrings: a TokenStream read after the iterator fetches another path replays wrong tokens

The TokenStreams of one GraphTokenStreamFiniteStrings.getFiniteStrings() iterator read its one reused buffer of token ids, so a stream left unread when the iterator fetches another path replays wrong tokens. For tokens new, ny, york in that order, collecting both streams first gives [ny, york] and [ny]; Lucene's query builders are unaffected.

The finding in 30 seconds

#

Background: token graphs and their paths

#
  1. A synonym filter can put several tokens at one place. For "new york" with the synonym ny, the token graph has new (position 0), ny (also position 0, position length 2, so it spans both words) and york (position 1). The tokens form a graph, not a line. Each token gets an id in the order it arrives: the repro feeds new, ny, york, while Lucene's SynonymGraphFilter emits ny first.
  2. GraphTokenStreamFiniteStrings turns that graph into an automaton. getFiniteStrings() returns an Iterator<TokenStream> with one plain, linear TokenStream per path: here [new, york] and [ny]. Lucene's query builders use it to build one clause per path.

The finding, step by step

#
  1. Feed GraphTokenStreamFiniteStrings three tokens in this order, as the repro's CannedTokenStream does: new (position 0), ny (also position 0, position length 2, so it spans both words) and york (position 1). This is the graph of "new york" with the synonym ny; it has two paths, [new, york] and [ny].
  2. Build new GraphTokenStreamFiniteStrings(stream), collect every path's TokenStream with getFiniteStrings().forEachRemaining(list::add), then read each stream.
  3. You expect [new, york] and [ny], which is what you get when you read each stream before asking the iterator for the next one.
  4. Instead you get [ny, york] and [ny], with no error; [ny, york] is no path of the graph. With the token order of Lucene's SynonymGraphFilter, which emits ny first, the same pattern gives [new] and [new, york] instead: the ny path is lost.
  5. Why: both streams read the same buffer of token ids, numbered in arrival order (new 0, ny 1, york 2). Stream 1 was made for 2 ids, [new, york]; fetching path 2 wrote ny into slot 0, and stream 1 still reads 2 slots: ny plus the left-over york.

Who is affected

#

Only code that calls getFiniteStrings() itself and keeps a returned stream unread while the iterator fetches another path: it collects the streams first, calls next() twice, or peeks with hasNext(). Lucene's QueryBuilder and IntervalBuilder read each stream at once, so their queries are right. Every release from 6.5.0 to 10.6.0.

Mechanism, terms and numbers547 words

GraphTokenStreamFiniteStrings.getFiniteStrings() returns an Iterator<TokenStream> with one stream per path of a token graph. Each next() creates a new stream, but all streams of one iterator wrap the same IntsRef: for every non-empty path, FiniteStringsIterator.next() returns its builder's one reused IntsRef ("just valid until the next call of this method", FiniteStringsIterator.java:97 at 5adff78bb168), and the wrapper passes it on without a copy (GraphTokenStreamFiniteStrings.java:154). The stream reads its token ids from that buffer only when it is read (:72), so a later hasNext() or next() that fetches another path overwrites (part of) the ids of a stream that has not been read yet. For the tokens new, ny (spanning both positions), york, fed in that order, collecting both streams and then reading them gives [ny, york] and [ny] instead of [new, york] and [ny], silently, with assertions on and off; with the token order of Lucene's SynonymGraphFilter (ny first) the same pattern loses the ny path. LUCENE-7638 introduced this in 6.5.0 (2017), when it replaced the 6.4 API, which copied each path, with the lazy iterator; every release run since then has it. Lucene's own callers (QueryBuilder, IntervalBuilder) read each stream before they advance, so only application code that calls the helper itself and holds a stream is hit. A one-line copy fixes it. Priority Low.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/)

#
  1. The iterator pre-fetches into a reused buffer. getFiniteStrings(start, end) wraps a FiniteStringsIterator (util/graph/GraphTokenStreamFiniteStrings.java:132-158). hasNext() fetches the next path, current = it.next() (:139-147). FiniteStringsIterator.next() returns string.get() (util/automaton/FiniteStringsIterator.java:132, :144), the same IntsRef object of its one builder for every non-empty path (only the empty string gets a static EMPTY, :102-105), and documents that "The return value is just valid until the next call of this method!" (:97).
  2. No copy (the fix site). next() returns new FiniteStringsTokenStream(current) (GraphTokenStreamFiniteStrings.java:154).
  3. The stream reads late. FiniteStringsTokenStream keeps that object (this.ids = ids, :63), fixes end = offset + length once (:65) and reads ids.ints[offset] on every incrementToken() (:72).
  4. The numbers (the repro's token order). Token ids: new = 0, ny = 1, york = 2. The first path is [0, 2], length 2, so stream 1 gets end = 2. The next hasNext() writes 1 into slot 0 and sets the length to 1; slot 1 still holds 2. The third hasNext() finds no more paths and only sets the length to 0, which no stream reads. Read now, stream 1 emits slots 0 and 1, [ny, york]; stream 2 emits [ny].
  5. Always in bounds. The builder's array only grows, and every id is a label of the graph's automaton, so the stream never throws: the result is a silently wrong token sequence.

Exposure and likelihood318 words
  • Who. Application code that calls the public getFiniteStrings() or getFiniteStrings(start, end) itself and holds a returned stream unread while the iterator fetches another path (the next hasNext() or next() does, unless the iteration has ended), for example to count or cap the paths before building clauses.
  • Not affected (by reading). QueryBuilder.analyzeGraphBoolean builds each side-path query inside its lazy Iterator<Query>.next() (util/QueryBuilder.java:520-538; the default newGraphSynonymQuery takes them one at a time, :618-622); QueryBuilder.analyzeGraphPhrase reads each stream before the next hasNext() (:575-581); IntervalBuilder.analyzeGraph does the same (lucene/queries, IntervalBuilder.java:216-234). So these in-tree callers, and query parsers that use these QueryBuilder methods unchanged, get the right paths; a subclass that overrides them was not checked. The two downstream match-query parsers that were read also consume each stream at once.
  • Effect. The held stream silently replays a later path's tokens, or a mix of two paths that is no path of the graph. Which wrong tokens depends on the token order, because token ids follow the order the tokens arrive in. For the repro's order (new, ny, york), a caller that builds clauses from the collected streams would search for ny york and never for new york. Lucene's SynonymGraphFilter emits the synonym first (it adds the original tokens last, SynonymGraphFilter.java:504-519): for "new york" with the synonym ny it emits ny, new, york, and the same collect-then-read pattern gives [new] and [new, york], so such a caller would search for new and new york and never for ny (read at once: [ny] and [new, york]; executed on main, assertions on and off).
  • Scale. Token graphs with two or more paths can trigger it; three tokens in the repro. No configuration involved.
  • Likelihood: rare. No public report since 6.5.0 (2017), and every in-tree caller (and the two downstream parsers that were read) consumes each stream at once.

Why it looks unintended

#
  • No javadoc says a returned stream expires; each is a new TokenStream with its own attributes. Comparable iterators document reuse (FiniteStringsIterator.next(), BytesRefIterator.next()).
  • The 6.4 API copied every path; the 6.5 rewrite to a lazy iterator dropped the copy without discussion.
  • In the repro the wrong [ny, york] is no path of the graph, and a bare hasNext() triggers it.
The full argument203 words
  • Contract. The class javadoc (GraphTokenStreamFiniteStrings.java:42-47), both methods (:126 "Get all finite strings from the automaton.", :131) and util/graph/package-info.java state no lifetime rule. The class is public, exported (module-info.java:49) and has no @lucene.internal or @lucene.experimental tag. Each element is a fresh TokenStream with its own cloned attributes (:61). Comparable Lucene iterator APIs document their reuse: FiniteStringsIterator.next() (:97) and BytesRefIterator.next() ("The returned BytesRef may be re-used across calls to next", BytesRefIterator.java:26).
  • Tests. Lucene's own test of FiniteStringsIterator honours that warning and deep-copies every result before keeping it (TestFiniteStringsIterator.java:181-185). The class's original tests (LUCENE-7603) collected all streams into a List and then read get(0), get(1). No test asserts the sharing; today's TestGraphTokenStreamFiniteStrings always reads each stream at once.
  • History. LUCENE-7603 (0a5300af6cf on branch_6x, released in 6.4.0; a81ebce8049 on the main line, first released in 7.0.0) added the class with a static getTokenStreams(TokenStream) that built each stream from IntsRef.deepCopyOf(ids). LUCENE-7638 (#8689; 5386116e9a3, released in 6.5.0, and e764d3e0590 on the main line) replaced it with the lazy iterator, whose next() passes current without the copy. Neither the LUCENE-7638 discussion nor its CHANGES entry mentions the copy or a lifetime rule.
The devil's-advocate check136 words

The strongest case for "intended": java.util.Iterator promises no snapshots, the class is a query-parsing helper, and every caller reads each stream before advancing, so the rule is "consume before you advance".

Why it fails: that rule is written nowhere; a bare hasNext(), which callers do not expect to change anything, already corrupts the stream handed out before; the held stream then shows neither its own path nor the iterator's current one (in the repro, [ny, york] is no path of the graph); and the API this replaced copied each path. The devil's-advocate verifier rated the case weak to moderate and rejected it; the cross-model reviewer rated it moderate and judged it outweighed. A maintainer may still read the result as an undocumented cursor-backed view and prefer a javadoc note to the copy (fix option C).

Suggested fix

#

Recommended Copy the path in next() (fix A)

Copy the path when the iterator hands out a stream: new FiniteStringsTokenStream(IntsRef.deepCopyOf(current)) (one line). It restores the 6.4 per-path copy for one small int[] per path. The repro passes with assertions on and off, and 69 tests of the closest suites pass.

        TokenStream next = new FiniteStringsTokenStream(IntsRef.deepCopyOf(current));

Document the lifetime instead (not run)

State on both getFiniteStrings methods that each returned TokenStream is valid only until the next hasNext() or next() call.

Trade-offs

No cost, but it keeps the trap, makes even a bare hasNext() a documented hazard (unusual for an Iterator), and keeps the impossible mixed path as the failure mode. The alternative a maintainer may prefer, not the main proposal.

Downstream note

#

For the repro's token order, a downstream query parser that collected the paths before building its clauses would search for ny york instead of new york; with SynonymGraphFilter's order (ny first), for new instead of ny. Either way it would silently miss matches. The downstream match-query parsers that were checked read each stream at once.

How it was found

#

A proof-obligation audit of GraphTokenStreamFiniteStrings' contract: every stream that getFiniteStrings() returns must replay its own path however the iterator is driven. That obligation fails against FiniteStringsIterator.next()'s documented buffer reuse, which the wrapper passes on without a copy; a public-API JUnit test then witnessed the wrong tokens.

The method in full109 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked getFiniteStrings against the obligation that each returned element replays its own path whatever the caller does with the iterator, and found that next() (:154) wraps the IntsRef that FiniteStringsIterator.next() documents as valid only until its next call.
  • The finder then wrote a public-API JUnit test (paths [A, C] and [B]; the first stream gives [B, C]) and the one-line copy that makes it pass.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

Summary
You build a GraphTokenStreamFiniteStrings over the tokens new, ny (a synonym spanning both positions) and york, whose paths are [new, york] and [ny], collect both TokenStreams from getFiniteStrings() into a list, and then read them. You expect each stream to replay its own path, as the original 6.4 API (which copied each path) did. You get [ny, york] and [ny], with no error: every stream reads the iterator's one reused IntsRef, which hasNext() overwrites with the next path, so the first stream mixes the second path's first token with its own leftover second token.
