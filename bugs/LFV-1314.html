LevenshteinAutomata.toAutomaton(0) rejects its own word when a high and a low surrogate are separate symbols

For the word {0xD83D, 0xDE00} (the emoji U+1F600 as UTF-16 code units) with alphaMax 0xFFFF, toAutomaton(0) rejects the word and accepts [0x1F600], while toAutomaton(1) accepts it. The zero-edit shortcut round-trips the word through a Java String, which joins the two surrogates; only direct callers are hit, since 4.10.0.

The finding in 30 seconds

#

For zero edits, LevenshteinAutomata does not build the automaton from the word's symbols: it writes them into a Java String and reads the String back by code point. That read joins a high surrogate followed by a low surrogate into one code point, so a word that holds the two as separate symbols no longer matches itself.

Background: Levenshtein automata, symbols and surrogates

#
  1. LevenshteinAutomata turns a word into a DFA that accepts every string within n edits of it (n = 0, 1 or 2). FuzzyQuery uses it for each edit distance up to its maxEdits.
  2. The word is an array of int symbols. The String constructor fills it with Unicode code points; the expert constructor takes any symbols up to a maximum alphaMax, for example 255 for bytes or 0xFFFF for UTF-16 code units.
  3. In UTF-16, a character above U+FFFF is two code units: a high surrogate (0xD800-0xDBFF) followed by a low one (0xDC00-0xDFFF). Reading a Java String by code point joins such a pair into one value: 0xD83D, 0xDE00 becomes 0x1F600.

The finding, step by step

#
  1. Build new LevenshteinAutomata(new int[] {0xD83D, 0xDE00}, 0xFFFF, false): an alphabet of UTF-16 code units (alphaMax 0xFFFF) and a two-symbol word, the emoji U+1F600 written as its two code units.
  2. Call toAutomaton(0) and run the word through it. You expect it to be accepted: the word is 0 edits from itself, and toAutomaton(1) on the same object accepts it.
  3. Instead it is rejected, silently, with assertions on and off. For n = 0 the class writes the symbols into a Java String and reads the String back by code point, and that read joins 0xD83D followed by 0xDE00 into the single code point 0x1F600.
  4. The result has 2 states and one transition, labelled 0x1F600: it accepts [0x1F600], a symbol above alphaMax and two edits from the word. toAutomaton(1) (8 states) keeps the two symbols apart.
  5. FuzzyQuery and the fuzzy suggesters pass code points or bytes and are not affected. Releases 4.1 to 4.9 built n = 0 symbol by symbol; the String shortcut came in 4.10.0.

Who is affected

#

Only code that calls the experimental LevenshteinAutomata itself, asks for zero edits, and has a high and a low surrogate as adjacent symbols: UTF-16 code units as the alphabet, other integers in that range, or a String prefix and word cut inside a surrogate pair. It silently gets a wrong automaton; FuzzyQuery and the fuzzy suggesters never build such input.

Mechanism, terms and numbers492 words

LevenshteinAutomata builds a DFA that accepts every string within n edits of a word. Its expert constructor takes the word as int symbols up to a chosen alphaMax. For n >= 1, toAutomaton(n, prefix) adds the prefix code point by code point and the word symbol by symbol. For n == 0 it takes a shortcut, Automata.makeString(prefix + UnicodeUtil.newString(word, 0, word.length)): newString writes each symbol below 0x10000, a surrogate included, as one char, and makeString(String) reads the String back with codePointAt, which joins a high surrogate followed by a low one into one supplementary code point.

So for the word {0xD83D, 0xDE00} with alphaMax 0xFFFF (UTF-16 code units as the alphabet), toAutomaton(0) has a single transition labelled 0x1F600: it rejects the word itself and accepts [0x1F600], a symbol outside the alphabet and two edits away, while toAutomaton(1) accepts the word. Nothing throws, with assertions on or off. No Lucene caller builds such input, so only direct callers of the experimental class are hit. Releases 4.1 to 4.9 built n == 0 from the word symbol by symbol; the fix builds it symbol by symbol again, as n >= 1 does.

Other forms of the same line (verification probes, not the repro)

#
  • Default alphaMax (Character.MAX_CODE_POINT) and the word {0xD800, 0xDC00}: toAutomaton(0) rejects the word and accepts [0x10000]; toAutomaton(1) accepts the word and rejects [0x10000].
  • The String API, word "\uDC00" with prefix "\uD800": toAutomaton(1, prefix) accepts [0xD800, 0xDC00]; toAutomaton(0, prefix) does not and accepts [0x10000].
  • An alphaMax above U+10FFFF with the word {0x110000}: toAutomaton(0) throws an IllegalArgumentException with no message from UnicodeUtil.newString; toAutomaton(1) accepts the word.
  • Controls that work: the well-formed String word "\uD800\uDC00" (U+10000) through the String constructor (both n accept [0x10000]), and a byte alphabet (alphaMax 255) with a prefix.

The round trip is lossless for a word of Unicode scalar values, which is why FuzzyQuery and the suggesters never see it.

Exposure and likelihood223 words
  • Who is hit. Code that calls LevenshteinAutomata directly and asks for n = 0, with the expert int[] constructor and an alphabet in which a value from 0xD800-0xDBFF can be followed by one from 0xDC00-0xDFFF (UTF-16 code units with alphaMax 0xFFFF, or other integer symbols in that range), or an alphaMax above 0x10FFFF with a symbol above it (then n = 0 throws while n >= 1 works); or the String overload toAutomaton(0, prefix) with a prefix that ends in a high surrogate before a word that starts with a low one. It gets a wrong automaton and no error: the word itself does not match, a different word does.
  • Default vs opt-in. Opt-in: an @lucene.experimental class (LevenshteinAutomata.java:29) and its "Expert" constructor (:61-64), or an ill-formed String split. Assertions on or off make no difference.
  • Lucene itself is not affected. FuzzyQuery builds its automata in FuzzyAutomatonBuilder, which decodes the term into code points once and splits prefix and suffix by code point (FuzzyAutomatonBuilder.java:50-56); FuzzySuggester and FuzzyCompletionQuery pass bytes (alphaMax 255) or code points decoded from analyzed UTF-8 (FuzzySuggester.java:255-260, FuzzyCompletionQuery.java:182-187). None of them can produce a high surrogate symbol directly followed by a low one.
  • Scale. None needed: a two-symbol word.
  • Likelihood. Contrived: no public report found in the twelve years since 4.10.0.

Why it looks unintended

#
  • toAutomaton(n) is documented to accept "all strings within an edit distance of n"; the word is at distance 0.
  • The expert constructor rejects only symbols above alphaMax; no doc excludes surrogates.
  • n >= 1 keeps the symbols apart, so L(0) is not inside L(1), a relation Lucene's own test asserts; 4.1 to 4.9 built n = 0 symbol by symbol.
The full argument198 words
  • The contract. toAutomaton(n): "Compute a DFA that accepts all strings within an edit distance of n" (LevenshteinAutomata.java:124); toAutomaton(n, prefix): the same, "matching the specified exact prefix" (:139-140).
  • The input is legal. The expert constructor ("Expert: specify a custom maximum possible symbol (alphaMax)", :62-63) rejects only symbols above alphaMax (:73-74). No javadoc, package doc, CHANGES.txt or MIGRATE.md entry says the symbols must be Unicode scalar values or that alphaMax must stay at or below 0x10FFFF.
  • The class contradicts itself. n >= 1 keeps the symbols apart, n == 0 merges them, so L(0) is not a subset of L(1). Upstream TestLevenshteinAutomata asserts that relation for its well-formed words: "check that the dfa for n-1 accepts a subset of the dfa for n" (TestLevenshteinAutomata.java:79-97). With alphaMax 0xFFFF the n == 0 automaton even carries a label above alphaMax.
  • History says accident. 4.1.0 to 4.9.1 built n == 0 with BasicAutomata.makeString(word, 0, word.length) (4.9.0 LevenshteinAutomata.java:129). 5927445bb60 (LUCENE-5752, 2014, "move prefix handling into LevA") added the prefix overload and replaced that line with the String concatenation; the issue thread (#6814) never mentions surrogates or the n == 0 branch.
The devil's-advocate check216 words

The strongest case for "intended": surrogate code points are not Unicode scalar values, Lucene's automata are meant to carry code points (the package doc speaks of a "Unicode alphabet", package-info.java:33, and Automaton.step calls its label a "codepoint", Automaton.java:654, though neither states a precondition), a prefix and word cut inside a surrogate pair is a caller error for which the merged U+10000 is arguably the useful answer, no Lucene caller passes such symbols, and the class is @lucene.experimental. The cross-model reviewer rated this argument moderate; the devil's advocate called it a fair point for the default-alphaMax form; both found that it does not hold.

Why it fails. No documented precondition excludes these symbols and the constructor accepts them. In the int[] form there is no String at all, so "a UTF-16 caller error" does not apply; the alphaMax 0xFFFF case needs no ill-formed Unicode (the word is a well-formed emoji in code units), yet n == 0 gets a label outside the alphabet; above 0x10FFFF n == 0 throws where n == 1 works; and nothing explains why n == 0 and n == 1 disagree on the same object. @lucene.experimental allows API changes, not silent wrong answers. A maintainer may still prefer to document "symbols are code points" (options B and C).

Suggested fix

#

Recommended A. Build n == 0 symbol by symbol, as n >= 1 does (recommended; validated)

Build the zero-edit automaton as the n >= 1 path does (4.1 to 4.9 built the word this way too): the prefix's code points, then the word's symbols as given, through Automata.makeString(int[], int, int). Well-formed input gets the same automaton as today. Validated through gradle: repro, core automaton, fuzzy and fuzzy-suggester tests pass; checkGoogleJavaFormat and forbiddenApisMain on core clean.

Trade-offs

n == 0 now splits the prefix exactly as n >= 1 does (String.codePoints() and the codePointAt loop at :170-175 treat a lone surrogate the same way) and takes the word's symbols as given, so L(0) is inside L(1) again. For a word of Unicode scalar values and a well-formed prefix, which is everything FuzzyQuery and the suggesters pass, the automaton is the same chain of states and labels as today. The one visible change for String callers: a prefix that ends in a high surrogate before a word that starts with a low one is no longer merged, as in n >= 1; an alphaMax above 0x10FFFF no longer throws for n == 0. Arrays.copyOf would be shorter but is on Lucene's forbidden-API list.

B. Document and reject (not validated)

#

State in the class and constructor javadoc that symbols are Unicode code points that are not surrogates and that alphaMax is at most 0x10FFFF, and throw from the constructor otherwise.

Trade-offs

The silent wrong answer becomes a loud error, but inputs that n >= 1 handles correctly today (alphabets of UTF-16 code units, larger integer alphabets) stop working, and the String prefix split still merges silently unless it is checked too. More code and a behaviour change, for no gain over A.

C. Javadoc only (not validated; the smallest change)

#

Say on toAutomaton that for n == 0 the prefix and the word are joined as UTF-16 text, so a high and a low surrogate symbol merge and symbols above 0x10FFFF are rejected.

Trade-offs

No code change, but the trap stays silent.

Downstream note

#

Until a fix ships, code that builds zero-edit automata over such an alphabet can use Automata.makeString(word, 0, word.length) directly, which takes the symbols as given.

How it was found

#

A semi-formal proof-obligation check of toAutomaton's contract: the zero-edit automaton must accept exactly the prefix followed by the word, and its language must lie inside the one-edit language. The n = 0 shortcut breaks that obligation for adjacent surrogate symbols; a public-API JUnit test witnessed it on stock main.

The method in full108 words

The obligations come from toAutomaton's javadoc (all strings within edit distance n, matching the exact prefix) and the subset relation upstream TestLevenshteinAutomata asserts between n - 1 and n. The check compared how the two branches of toAutomaton(int, String) turn the prefix and the word into labels: n >= 1 adds them one symbol at a time, n == 0 round-trips them through a String, and only the second can join two symbols into one. An executable JUnit test on the stock main build confirmed it, and an independent reproducer, a cross-model review, an intended-behaviour devil's advocate and an adjudication then checked it (see the checks below).
