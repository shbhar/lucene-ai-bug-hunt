The finding in 30 seconds

#

The limits first. Silent: another term, no error. Narrow, for the title's face: the text must be decomposed (e + U+0308 for ë) with that diaeresis inside the part of the token that a cwords.txt entry matches. How often real Albanian text has the shape was not measured. The code is on branch_11x and main and in no release.

Background: three pieces

#
  1. Albanian has two letters outside ASCII, ë and ç. Both are often typed as plain e and c, so the normalizer folds ë to e, and ç and c to q: the spellings are meant to index to the same term.
  2. Some words really have a c (cili, kec). They are listed in cwords.txt, as whole words or as prefixes such as kepuc*, and keep it.
  3. A letter such as ë can be stored as one code point (U+00EB, precomposed) or as e followed by the combining diaeresis U+0308 (decomposed). Both look the same on screen.

The finding, step by step

#
  1. You analyze Albanian text with the new AlbanianAnalyzer or AlbanianNormalizationFilter (on branch_11x and main since 2026-11-20, in no release). The normalizer folds ë to e, and ç and c to q. Words that really have a c are listed in cwords.txt and keep it: këpucë, under the entry kepuc*, becomes kepuce.
  2. The same word arrives in decomposed form, each ë as e + U+0308: k, e, U+0308, p, u, c, e, U+0308. The class javadoc says the folding holds "whether precomposed or written as a base letter followed by a combining diaeresis / cedilla (text copied from PDFs and some web pages comes in that decomposed form)". You expect kepuce again.
  3. You get kepuqe: no error, assertions on and off. Through new AlbanianAnalyzer() the two spellings give kepuc and kepuk, and in the runs a term query made from one spelling found no document indexed in the other.
  4. Why: normalize decides first, on the token as it arrives, whether the token keeps its c. The lookup key still holds U+0308 behind the first e, so kepuc* does not match and the c becomes q. The combining marks are deleted afterwards, in the loop that folds the letters.
  5. The limits: with only the last ë decomposed (the mark behind the listed part), for a word that is not on the list (çfarë) and for a word without c (mëshirë) both spellings gave equal terms. A second face needs no decomposed text: t'cilat leaves the token qil, though cilat alone is a stop word.

Who is affected

#

Applications that analyze Albanian text with the new analyzer, filter or factory, built from branch_11x or main; no setting is involved. It takes decomposed text with a listed word whose diaeresis stands inside the listed part, and the other side of the match in another spelling: a search can miss, silently. How often was not measured. No release is affected.

The limits first. The defect is silent (another term, no error, the same with assertions on and off) and narrow. For the face that the title names, the text must be in decomposed form (e + U+0308 for ë), and the combining diaeresis must stand inside the part of the token that an entry of cwords.txt matches (run with këpucë, entry kepuc*, and kërcej, entry kerc*). The code is new on branch_11x and main and in no release; 11.0.0 would be the first release with it if branch_11x is released with the code as it was on 2026-11-20.

You analyze Albanian text with the new AlbanianAnalyzer or AlbanianNormalizationFilter (code that is on main and on branch_11x since 2026-11-20 and in no release). The normalizer's class javadoc says ë is folded to e, and ç and c to q, "whether precomposed or written as a base letter followed by a combining diaeresis / cedilla (text copied from PDFs and some web pages comes in that decomposed form)", and that words that really have a c keep it because they are listed in cwords.txt. So you expect a listed word such as këpucë (entry kepuc*) to get one term however its ë is encoded. Instead the normalizer decides whether the token keeps its c before it handles the combining marks: këpucë written with e + U+0308 becomes kepuqe, while the precomposed spelling and the spelling typed without marks become kepuce (through the analyzer kepuk against kepuc). In the runs a term query in one spelling found no document indexed in the other, with no error.

A second face, on the record since 2026-11-21, needs no decomposed text. The same decision is taken before the normalizer drops a one-letter elided clitic, so new AlbanianAnalyzer() gives the token qil for t'cilat and no token for cilat alone, a line of the stop list. In the run with the six one-letter clitics that the package names and the three apostrophes the normalizer handles, 14 of the 350 lines of the stop list left a token and the other 336 left none. How often Albanian text holds that shape was not measured either.

The path (lines at main b5a4546a5964, lucene/analysis/common/src/java/org/apache/lucene/analysis/sq/)

#
  1. normalize takes the keep-c decision as its first statement, on the buffer as it came in: boolean keepC = keepsC(s, len); (AlbanianNormalizer.java:141).
  2. keepsC (:106-131) looks for the first raw c or C (:107-116) and builds its key: the token in lower case, with only the one-character ë (U+00EB) read as e (:117-121). A U+0308 in the token stays in the key.
  3. It tests the whole key against the whole-word entries (:122-124) and each prefix of the key that ends at or behind the first c against the prefix entries (:125-129).
  4. For k, e, U+0308, p, u, c, e, U+0308 the key holds U+0308 behind the first e. Its three prefixes that end at or behind the c are not on the list, so keepC is false. The entry is kepuc* (cwords.txt:80).
  5. The loop folds: case 'c' writes q unless keepC (:159-164; C at :168-172). The four combining marks U+0308, U+0327, U+0302 and U+0301 are deleted in the same loop, after the decision (:205-211). The result is kepuqe.
  6. The precomposed spelling: the key is kepuce, its prefix kepuc is on the list, keepC is true and the c stays: kepuce. The spelling typed without marks has the same key.
  7. The callers: AlbanianNormalizationFilter.java:50 applies the normalizer to the term buffer; the factory's name is albanianNormalization (AlbanianNormalizationFilterFactory.java:41); AlbanianAnalyzer puts the filter behind StandardTokenizer and LowerCaseFilter (AlbanianAnalyzer.java:141-143) and into Analyzer.normalize (:153-157). The stock analyzer has no step that composes the text first.

Why it looks unintended

#
  • The class javadoc's first rule: the folding holds "whether precomposed or written as a base letter followed by a combining diaeresis / cedilla".
  • The javadoc of the package's own test: such letters "fold the same way as the precomposed letters".
  • No one sentence states the keep-c rule for decomposed spellings: the texts are combined. No text asks for composed input.
The full argument399 words

The four texts, each quoted by itself (lines at main b5a4546a5964):

  • Class javadoc, first rule (AlbanianNormalizer.java:37-39): ë to e, and ç and c to q, "whether precomposed or written as a base letter followed by a combining diaeresis / cedilla (text copied from PDFs and some web pages comes in that decomposed form)".
  • Class javadoc on listed words (:58-61): "Words that really have a c ... keep it: they are listed, as whole words or stem prefixes" in cwords.txt.
  • Header of cwords.txt (:3-6): "A token that starts with an entry here, read on its lowercased, ë-folded form, keeps its c".
  • Javadoc of the package's test of combining marks (TestAlbanianNormalizer.java:37-40): ë and ç "written as a base letter plus a combining mark, as text copied from PDFs often is, fold the same way as the precomposed letters".
  • None of the package's 61 tests fails, and none feeds a listed word in a decomposed spelling. The four combining marks occur in the package's tests in the three inputs of testCombiningMarks (:42-44) and nowhere else, and these three hold no listed entry. The 61 tests pass on the unchanged sources of main b5a4546a5964 in Lucene's own build.
  • History. Inside the pull request the keep-c list and the decision came with its second source commit (dc27985c1016, 2026-11-01). With the two classes of its first source commit (243046735ca7, 2026-10-31: no list, no decision) the test passes; with those of the second and of the third it fails (runs of 2026-11-20).
  • Not a matter of linguistic quality. That the word keeps its c is the list's choice: the entry is there. The claim is that one listed word in two canonically equivalent encodings gets two terms through a class that says it handles both. Which term is better Albanian is not assessed.
  • The second face has the weaker written rule. "so the remaining word can be matched against the stop list" (:43-45) is a clause of purpose with three examples, not an explicit rule for each clitic and each line. The header of cwords.txt puts the keep-c rule on the token, and t'cilat does not start with an entry. The javadoc of the package's test of clitics says the clitic is dropped "so that the word it was attached to can still be recognized" (TestAlbanianNormalizer.java:110-113).
The devil's-advocate check219 words

The strongest case for "intended": the javadoc of the package-private keepsC says "lowercased and with ë read as e" (AlbanianNormalizer.java:102-105), and that sentence and the list's header can be read for the one-character ë only. The answer would then be "compose the text first" (NFC, for example with an ICU normalization filter in front).

The answer, in four points: the first rule of the public class javadoc puts base letter + combining mark into what the class folds and says where such text comes from; the class deletes the four marks itself (:205-211); the stock AlbanianAnalyzer has no composing step (AlbanianAnalyzer.java:141-143); and no text of the package, lucene/CHANGES.txt or lucene/MIGRATE.md asks for composed input.

What stays open: a maintainer could still answer "compose the text first", most likely in this form: the first rule is met to the letter (the mark is deleted and ë gives e); what differs is the list decision, and the two texts that describe the lookup, the javadoc of keepsC and the header of cwords.txt, name the letter ë. No text that was read says that input must be composed. And what bounds the finding is true and is said first on this page: the shape is narrow and its frequency in real text was not measured.

Suggested fix

#

No patch is proposed. A shape that was tried: before the decision, read e + U+0308 and c + U+0327 as the precomposed letters and drop the one-letter clitic (17 added lines at one place). With it both tests pass, assertions on and off, and the analysis-common suite shows no failure. The maintainers choose the form.

What was tried, not a patch to apply and not a recommendation. Which form a fix takes is the maintainers' choice. The root is one order of steps: the decision is taken on the token as it arrives. The shape that was tried: decide after the marks and the clitic are handled

#

In front of the statement at AlbanianNormalizer.java:141, two small steps: read e + U+0308 and c + U+0327 as the precomposed letters, then drop a one-letter elided clitic. 17 added lines at one place, nothing removed. The decision then reads the token in the form the list is written for.

public int normalize(char[] s, int len) {
  // read e + U+0308 and c + U+0327 as the precomposed letters before the keep-c decision
  for (int i = 0; i + 1 < len; i++) {
    char composed = 0;
    if (s[i + 1] == '\u0308') {
      composed = s[i] == 'e' ? '\u00EB' : s[i] == 'E' ? '\u00CB' : 0;
    } else if (s[i + 1] == '\u0327') {
      composed = s[i] == 'c' ? '\u00E7' : s[i] == 'C' ? '\u00C7' : 0;
    }
    if (composed != 0) {
      s[i] = composed;
      len = StemmerUtil.delete(s, i + 1, len);
    }
  }
  // drop a one-letter elided clitic before the keep-c decision
  if (len > 2 && (s[1] == '\'' || s[1] == '\u2019' || s[1] == '\u02BC')) {
    len = StemmerUtil.deleteN(s, 0, len, 2);
  }
  boolean keepC = keepsC(s, len);   // unchanged from here on

Registry title
AlbanianNormalizer decides whether a token keeps its c before it handles combining marks, so a word under a cwords.txt entry written with e + combining diaeresis inside the matched part can fold its c to q: the token k, e, U+0308, p, u, c, e, U+0308 gives 'kepuqe', the precomposed spelling of the same word gives 'kepuce' (new code on main and branch_11x, both unreleased; in no release)
Area
analysis-common / Albanian normalizer (AlbanianNormalizer.normalize and keepsC; AlbanianNormalizationFilter, the 'albanianNormalization' factory and AlbanianAnalyzer); new on main and branch_11x, both unreleased
Priority
Low, rank 565: On main and branch_11x, both unreleased, a word under a cwords.txt entry whose ë is written as e + combining diaeresis inside the matched part gets another term than its precomposed spelling ('kepuqe' against 'kepuce'), with no error. It is Low because, for this face, the text must be in decomposed form and the combining diaeresis must stand inside the part of the token that a cwords.txt entry matches; with the diaeresis behind the matched part, for an unlisted word and for a word without c the runs gave equal terms. Summary
You analyze Albanian text with the new AlbanianAnalyzer or AlbanianNormalizationFilter (code that is on main and on branch_11x since 2026-11-20 and in no release). The normalizer's class javadoc says ë is folded to e, and ç and c to q, 'whether precomposed or written as a base letter followed by a combining diaeresis / cedilla (text copied from PDFs and some web pages comes in that decomposed form)', and that words that really have a c keep it because they are listed in cwords.txt, so you expect a listed word such as këpucë (entry kepuc*) to get one term however its ë is encoded. Instead the normalizer decides whether the token keeps its c before it handles the combining marks, so këpucë written with e + U+0308 becomes 'kepuqe' while the precomposed spelling and the spelling typed without marks become 'kepuce' (through the analyzer 'kepuk' against 'kepuc'), and in the runs a term query in one spelling found no document indexed in the other, with no error.
