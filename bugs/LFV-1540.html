The finding in 30 seconds

#

The order shown below is as run with the weights 30, 20, 10, not a rule: with 30, 20, 5 the weight-20 suggestion comes first, and with twelve suggestions and num 1 the tenth by weight is returned. A fetched suggestion that starts with the raw key gets the coefficient 1 instead (run: the hobbit, weight 20, came first).

Background: three pieces

#
  1. An infix suggester is a small Lucene index of its own. Each suggestion is one document with a weight. A lookup analyzes the key into tokens, searches for suggestions that match them and returns the heaviest.
  2. A context is a label on a suggestion. A lookup can pass a set of contexts; then a suggestion must carry one of them to be returned.
  3. BlendedInfixSuggester fetches more hits than asked for (ten times as many by default) and multiplies each weight by a coefficient that falls with the position of the first matching word (1 - 0.10 × position by default). A hit whose text starts with the key gets the coefficient 1.

The finding, step by step

#
  1. Build a BlendedInfixSuggester with its two-argument constructor over the stock EnglishAnalyzer. Add three suggestions to one context, books: dune with weight 30, emma with 20, ulysses with 10.
  2. Call lookup("the", books, false, 1). the is a stop word, so the key has no token; with all terms required (the default) the search is then the context alone, and all three suggestions are hits. The parent class AnalyzingInfixSuggester returns dune/30 for the same call, so by that comparison the test expects dune/30. No javadoc states what such a key should return.
  3. You get ulysses/-2147483637, the lowest weight, and no error. With num 3 you get ulysses/-2147483637, emma/-4294967274, dune/-6442450911.
  4. Why: to blend a weight with the position of the matching word, createCoefficient searches for the closest matching term, starting at Integer.MAX_VALUE. A key without a token matches no term, so the start value is scored as a position: 1 - 0.10 × 2147483647 = -214748363.7, times the weight. Negative values alone are not the defect: the documented formula gives them for a word matched past position 10.
  5. Second symptom, same method: with to be as the only suggestion of the context (two stop words, so its text has no token, and it does not start with the key), the same lookup throws NullPointerException. Such a suggestion has no term vector, and the method reads it without a null check.

Who is affected

#

Applications that use this opt-in, experimental class with a context filter, at a key that names nothing: the stop word the under EnglishAnalyzer, or a space, ? or - under StandardAnalyzer without stop words (those three run on 10.6.0, branch_11x and main only). The returned suggestions were those of the requested context in each run. Nothing is stored wrongly.

Mechanism, terms and numbers1,839 words

Small and narrow. BlendedInfixSuggester is an opt-in class of the suggest module, marked experimental. It extends AnalyzingInfixSuggester and multiplies each hit's weight by a coefficient that depends on the position of the first matching word. For a hit that matched no word of the key, createCoefficient passes the start value of its search, Integer.MAX_VALUE, to the formula as if it were a position (BlendedInfixSuggester.java:325, :347; lines at main f6e694652c3d). For a hit without a term vector it throws NullPointerException (:322-323). The same with assertions on and off.

The shape that was run: a lookup that passes contexts with a positive clause, with all terms required (the default), for a non-empty key that the query analyzer turns into no token (run: the stop word the under the stock EnglishAnalyzer; a space, ? or - under StandardAnalyzer without stop words, those three on 10.6.0, branch_11x and main only). The query is then the context clause alone, and every suggestion that it matches is a hit. With the key the and three suggestions with the weights 30, 20, 10, the lookup returns the weight-10 suggestion first with the value -2147483637, where the parent class returns the weight-30 one. That order is as run, not a rule for any weights. A fetched suggestion whose text starts with the raw key is not scored this way: it gets the coefficient 1 (run: the hobbit with weight 20 came back first, as the hobbit/20). The exception needs a fetched suggestion whose own text has no token and that does not start with the raw key (run: to be). In each run the returned suggestions were those of the requested context, and nothing is stored wrongly.

On the older releases one shape of each symptom was run: the wrong order (the example above) on 4.10.4 and on every release from 5.0.0 to 10.6.0 (109), the exception (a context whose one suggestion is To Be or Not to Be) on every release from 4.8.0 to 10.6.0 (117). Both were run on builds of branch_11x and main; the two lines came with the class in 2014. What such a key should return is not stated by any javadoc. The expected order on this page is by comparison with the parent class, and returning nothing would be defensible as well. Neither reading scores the start value as a position or allows the exception. Two repair shapes were run; which one is right is for the maintainers to decide.

Why it looks unintended

#
  • The scored value is a search's start value, not a position; calculateCoefficient documents its argument as the "position of the first matching word in text".
  • An earlier NullPointerException of this method was fixed as a bug (LUCENE-6093).
  • Open, not claimed: what such a key should return. No javadoc says; the expected order is by comparison with the parent class.
The full argument453 words

No javadoc says what a non-empty key without a token returns in a lookup with contexts. What follows is what the code and its documentation say about the two lines.

  • The class's own description. It "transforms the weight after search to take into account the position of the searched term into the indexed text" (BlendedInfixSuggester.java:49-50). Here no searched term is in the text, so there is no position.
  • The method's contract. "Calculate the weight coefficient based on the position of the first matching word. Subclass should override it to adapt it to particular needs", with the parameter "position of the first matching word in text" (:351-354). BlenderType.CUSTOM is documented as "Application dependent; override {@link #calculateCoefficient} to compute it." (:74). A subclass written to that javadoc receives 2147483647 (run).
  • A start value by the code's own comment. "find the closest token position" (:327).
  • Taken as unreachable in a public comment. In a comment of 2018-06-07 on #9390 (LUCENE-8343), in a discussion of overflow with small weights, Alessandro Benedetti lists the linear coefficient for "input position is Integer.MAX_VALUE" as an edge case "which is not going to be achievable as Strings full length are maxed by that value". The comment speaks of a real position, not of the loop's start value; that the value was not meant to be scored is this page's reading.
  • Null is a documented return value. TermVectors.get(doc, field) returns the term vector "or null if term vectors were not indexed" (TermVectors.java:56). The javadoc does not spell out this case (term vectors on, a text without a token); by the run such a suggestion has none.
  • The inputs are legal. By reading, no javadoc of Lookup, AnalyzingInfixSuggester or BlendedInfixSuggester puts a precondition on the key or on a suggestion's text (the key is "the lookup key", Lookup.java:217; "the keyword being looked for", AnalyzingInfixSuggester.java:614).
  • History. An exception from this same method for a key without a prefix token was fixed as a bug: LUCENE-6093 (#7155), listed under the bug fixes of 5.0.0 and 4.10.4, with the regression test testNullPrefixToken (TestBlendedInfixSuggester.java:262-276).
  • Tests. TestBlendedInfixSuggester has no lookup with contexts: each of its calls that has a contexts argument passes null (:368-389).

What is open. The test expects the highest weight by comparison with the parent class, which returns the context by weight for the same call, and with this class's own answer for the empty key. Returning nothing for such a key would be defensible as well: that is what the same key returns without contexts and with allTermsRequired = false. Under that reading the repair belongs in AnalyzingInfixSuggester.lookup and the test's expected values become empty lists.

The devil's-advocate check279 words

The strongest case for "works as designed": a non-empty key without a token asks for nothing, so the whole context is not a meaningful answer and its order is nobody's contract.

  • Three javadoc sentences call the contexts a filter of the key lookup: "contexts to filter the lookup by" (Lookup.java:203), "A query for further filtering the result of the key lookup" (Lookup.java:218), "to be used to filter the result of the suggester" (AnalyzingInfixSuggester.java:611-612).
  • The same key returns nothing without contexts and with allTermsRequired = false (run).
  • #8556 (LUCENE-7505, 2016) fixed as a bug that suggestions "did match solely the context filter" when allTermsRequired is false and the key has terms.
  • On the java-user list in January 2017 ("Strange results returned from suggester") a user who got all entries of a context from AnalyzingInfixSuggester for the stop word will was told to use SuggestStopFilter at query time.
  • The class is experimental, negative values are within the documented linear formula, and no report came since 2015.

What speaks against it: this is an argument about what the parent class should match, and it leads to "return nothing", not to "score the start value". With SuggestStopFilter at query time the key the followed by a space still shows the wrong order, and an analyzer without stop words shows it for a space, ? and - (run). Under either reading a weight of 10 does not come back as -2147483637, and a public lookup does not throw NullPointerException on a suggestion made of stop words. A maintainer may still answer that such a key should return nothing; the second repair shape on this page is that answer.

Suggested fix

#

Recommended A hit without a matching term, or without a term vector, gets the coefficient 1

Summary
You build a BlendedInfixSuggester with its two-argument constructor over the stock EnglishAnalyzer, add three suggestions to one context (dune 30, emma 20, ulysses 10) and call lookup("the", contexts, false, 1). 'the' is a stop word, so the key has no token and the lookup matches every suggestion of the context; AnalyzingInfixSuggester returns dune, the highest weight, for the same call, and BlendedInfixSuggester returns dune for the empty key, so you expect dune. Instead you get ulysses, the lowest weight, with the value -2147483637 (with num 3: ulysses, emma, dune with -2147483637, -4294967274, -6442450911), and no error: createCoefficient starts its search for the closest matching term with position = Integer.MAX_VALUE, no term of a hit matches a key without tokens, and the start value goes into the linear formula 1 - 0.10 * position. If a suggestion of the context is among the fetched hits and its text has no token and does not start with the raw key ('To Be or Not to Be' under EnglishAnalyzer), the same lookup throws NullPointerException, because the method reads the hit's term vector without a null check.
