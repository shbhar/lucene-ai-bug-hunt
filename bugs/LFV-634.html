Hunspell getAllWordForms never generates a suffix that only a prefix allows

If a Hunspell prefix rule allows a suffix that the entry itself lacks (PFX U 0 kilo/S with ampere/U), Lucene's spell() accepts amperes and kiloamperes, but getAllWordForms("ampere") yields only the words ampere and kiloampere. generateAllSimpleWords and compress are wrong the same way, in every release since 9.5.0.

The bug in 30 seconds

#

A Hunspell affix rule can carry a continuation class: PFX U 0 kilo/S means "after kilo-, the suffix S is allowed too". Lucene's spell-checker honours this; its word-form generator does not, so a prefix plus a suffix that only the prefix allows is silently left out.

  1. You load a dictionary with two prefix rules, PFX U 0 0/S . and PFX U 0 kilo/S ., the plural rule SFX S 0 s . and the entry ampere/U. The /S on a prefix rule means: after this prefix, the plural is allowed too. The entry itself has no S.
  2. You expect getAllWordForms("ampere") = [ampere, amperes, kiloampere, kiloamperes]: Lucene's spell() accepts all four, analyzeSimpleWord() analyses each as a form of ampere/U, and C Hunspell 1.7.2 agrees.
  3. Instead you get only the words ampere and kiloampere (the raw list is [ampere, ampere, kiloampere]; the empty prefix rebuilds ampere). After a prefix the generator recurses with the prefix's S, but WordFormGenerator.java:378 rejects every suffix once a prefix is applied, so that S is never used; only a suffix flag on the entry itself can combine with a prefix (suffix first).
  4. No error. generateAllSimpleWords misses the same words, and for work/P with PFX P 0 re/S compress([work, rework, reworks]) proposes work/PS, an edit that also adds works, a word the dictionary rejects.
  5. Real dictionary: in the current French dictionary getAllWordForms("ampère") returns 29 singular forms and none of the 25 plurals spell() accepts. Over the whole dictionary a fix adds 833 forms, all accepted by spell(), and removes none.

Who is affected

#

Only callers of the opt-in Hunspell dictionary-tooling API (getAllWordForms, generateAllSimpleWords, compress, NGramFragmentChecker.fromAllSimpleWords) with a dictionary whose prefix rules enable suffixes, such as the French unit prefixes. Word lists come back incomplete and compress suggests needless edits. Spell-checking, stemming and search are not affected.

Mechanism, terms and numbers715 words

Hunspell lets a prefix rule enable a suffix through its continuation class: with PFX U 0 kilo/S ., SFX S 0 s . and the entry ampere/U, the dictionary defines ampere, amperes, kiloampere and kiloamperes, although the entry has no S. Lucene's spell-checker has accepted this since LUCENE-9688 (2021), and C Hunspell 1.7.2 accepts all four words. Lucene's word-form generator (Hunspell.getAllWordForms, WordFormGenerator.getAllWordForms, generateAllSimpleWords, compress, and through them NGramFragmentChecker.fromAllSimpleWords) never produces these forms: getAllWordForms("ampere") yields only the words ampere and kiloampere. After a prefix it recurses with the prefix's continuation flags, but the guard if (!isPrefix && !stem.getPrefixes().isEmpty()) return false; (WordFormGenerator.java:378 on main a9779ef3c193) rejects every suffix once a prefix is applied, so a prefix-plus-suffix form is built only suffix first, from a suffix flag the entry itself carries. No error is raised, and compress proposes needless edits that over-generate. In the current French dictionary getAllWordForms("ampère") returns 29 singular forms and none of the 25 plurals; over the whole dictionary a fix adds 833 forms, all accepted by spell(). Every release from 9.5.0 through 10.5.2 and main is affected. Spell-checking, stemming, HunspellStemFilter, indexing and search do not use this code.

Terms

#
  • Entry: a line of the .dic file. ampere/U has the stem ampere and the flag U.
  • Affix rule: SFX S 0 s . says that entries with flag S take the suffix s (amperes); PFX U 0 kilo . adds the prefix kilo.
  • Continuation class: the flags an affix gives to the word it creates. PFX U 0 kilo/S . gives S to kiloampere, so kiloamperes is a word even though ampere/U has no S. hunspell(5): "affix (optionally with flags of continuation classes, separated by a slash)".

The bug

#
  1. expand (WordFormGenerator.java:233-259) walks the entry's flags. For each affix it checks isCompatibleWithPreviousAffixes (:240), applies it, keeps the word if stemming it reaches a stem with the entry's stem text and no forbidden word (canStemToOriginal, :184-217; it compares the stem string only, not the entry's flags), and recurses with updateFlags(flags, flag, append) (:251-252): the applied flag removed, the affix's continuation flags added.
  2. isCompatibleWithPreviousAffixes (:372-383), line 378: if (!isPrefix && !stem.getPrefixes().isEmpty()) return false;. No suffix after a prefix, which fixes the order: suffixes first, prefixes second.
  3. For ampere/U the flags are [U]. Applying kilo gives kiloampere and recurses with [S], the prefix's continuation. S is a suffix, a prefix is present, and line 378 rejects it: kiloamperes is never built. The empty prefix (PFX U 0 0/S) loses amperes the same way.
  4. The other cases work. If the entry has S (work/PS), S is applied first and P second, and the guard only prevents building reworks twice. In the mirror case, a suffix whose continuation allows a prefix (SFX S 0 s/P, work/S), a prefix after a suffix is allowed, so reworks is generated.
  5. The spell-checker accepts this exact path on purpose: Stemmer.java:269-270, dictionary.hasFlag(entryId, flag) || dictionary.isFlagAppendedByAffix(prefixId, flag) (LUCENE-9688).

Exposure and likelihood263 words
  • Who is hit. Callers of Hunspell.getAllWordForms and compress, both WordFormGenerator.getAllWordForms overloads, generateAllSimpleWords and compress, and NGramFragmentChecker.fromAllSimpleWords. The API exists "to aid dictionary editing" (LUCENE-10626): listing a dictionary's words, minimising entries, building fragment checkers. No setting is involved; which forms go missing depends only on the dictionary, deterministically.
  • The trigger. A valid dictionary with a PFX rule whose continuation class carries an SFX flag the entry lacks. Lucene's own dependencies.aff has it (PFX p 0 0/s .). The current French dictionary has it on 35 unit entries: 833 missing forms, 25 of them for ampère. The finder's static survey reports the shape in 16 of 191 public .aff files (French, Danish, de_*_frami, Armenian, Bengali, Kinyarwanda); their 3,000-root samples changed only French, not da_DK, de_DE_frami, lb, nb_NO or sv_SE (not re-checked).
  • What goes wrong. Incomplete getAllWordForms and generateAllSimpleWords output, with no error. compress proposes edits the dictionary does not need (ampere/SU for words ampere/U already covers; work/PS for work/P), and the work/PS edit adds works, which it lists in getExtraGeneratedWords(). A fragment checker from fromAllSimpleWords lacks n-grams that only the missing forms have: in the hunt's probe it flagged amperes and kiloamperes as containing an impossible fragment. That checker is opt-in (Suggester.withFragmentChecker; Hunspell.suggest does not use one), and no changed suggestion was seen in the probe's 8 misspellings.
  • Not affected. spell(), analyzeSimpleWord(), the Stemmer, HunspellStemFilter, indexing and search: they do not call the generator, and the hunt's probe found the same stems and hits with and without a fix.

Why it is a bug, not intended

#
  • The javadoc promises "all word forms", and Lucene's test oracle checkGoodSugWordsAreGenerated requires every accepted word to be generated.
  • The Stemmer accepts these words on purpose since LUCENE-9688 (2021), and so does C Hunspell 1.7.2.
  • The mirror case (a suffix that allows a prefix) is generated; the prefix-first path is not, and nothing excludes it.
The full argument275 words
  • The contract. getAllWordForms: "Generate all word forms for all dictionary entries with the given root word" (WordFormGenerator.java:117-119, Hunspell.java:334-336). generateAllSimpleWords (:294-298) names only compounds and case variants as excluded. NGramFragmentChecker.fromAllSimpleWords derives "all word forms (using WordFormGenerator) ... to get all words acceptable by the spellchecker" and names only compounds as a limitation (NGramFragmentChecker.java:76-81).
  • Lucene's test oracle. TestSpellChecking.checkGoodSugWordsAreGenerated (TestSpellChecking.java:357-376, called at :324-327) asserts, for every fixture whose .dic it can expand whole and whose dictionary needs no input cleaning, that every lowercase .good/.sug word that analyzeSimpleWord accepts is generated; amperes and reworks would meet those conditions if such a fixture listed them. No fixture it runs on has a PFX rule whose continuation carries an SFX flag; dependencies.aff (:24-25), which does, is used only by TestDependencies. The same check runs in TestHunspellRepositoryTestCases on the C Hunspell test fixtures (when configured), and none of the 131 C Hunspell 1.7.2 test .aff files has the shape either.
  • Deliberate support elsewhere. LUCENE-9688 (#10727, PR apache/lucene-solr#2229, 0a1a3f4c409, 2021-01-22; backported to 8.x and first released in 8.9.0), "Hunspell: consider prefix's continuation flags when applying suffix", made the Stemmer accept exactly this pattern; TestDependencies.java:42-43 asserts that calories stems to calorie.
  • The reference implementation. C Hunspell checks a "conditional suffix (enabled by prefix)" (affentry.cxx:673, 1.7.2) and accepts amperes, kiloamperes, reworks and books, and rejects kilo and works.
  • History. The guard came with the generator in #975, without a comment; the PR's 3 conversation and 19 inline review comments and #11904, which moved the line unchanged, never mention prefix continuation classes.
The devil's-advocate check236 words

The case for "intended": the javadoc says getAllWordForms "is equivalent to "unmunch" from the "hunspell-tools" package", and C unmunch does not produce amperes either; line 378 looks like a deliberate canonical order (suffix first, prefix second) that avoids building each prefix+suffix form twice; and the same author wrote LUCENE-9688, so they knew the pattern. Read that way, the generator is a bounded enumerator in one canonical order, not a complete one.

Why it fails: C unmunch 1.7.2 has no continuation-class support at all; on this dictionary it prints ampere, 0/S|ampere and kilo/S|ampere, pasting the raw rule text onto the root. Lucene's generator already goes beyond it (kiloampere, twofold suffixes, suffix-enabled prefixes), so "equivalent" names the tool's purpose, not its limits. The canonical-order argument holds only when the entry carries the suffix flag; without it there is no suffix-first path, so the form is not deduplicated but lost. When the guard was written (d537013e708), the generator also collected forms in a LinkedHashSet<AffixedWord>, so a second copy would not have reached the output then; #11904 switched to lists for speed. The "bounded enumerator" reading conflicts with the method contracts ("all word forms"). Two executed reviews by a model from another family rated the intended-behaviour argument weak, as did the cross-model fact check of this doc, and an intended-behaviour devil's advocate and the adjudication rejected it. The argument does support low impact.

Suggested fix

#

Recommended Allow a suffix after the prefix when only the prefix's continuation class carries it (validated)

Let a suffix follow the prefix when the prefix's continuation class carries its flag and the entry does not (for the tested rules, the entry's own suffixes are already combined suffix-first): +17/-6 in WordFormGenerator.java. Validated: the repro passes; hunspell package 162 tests and analysis-common 1,913 tests, 0 failures; French gains 833 forms, all accepted by spell().

if (!isPrefix && !stem.getPrefixes().isEmpty()) {
  // Suffixes are applied before prefixes, so a suffix that the root allows has already been
  // combined with this prefix. Only a suffix that the prefix's continuation class allows
  // (and the root does not) still needs to be applied here.
  return size == 0
      && stem.getPrefixes().size() == 1
      && !FlagEnumerator.hasFlagInSortedArray(flag, rootFlags, 0, rootFlags.length)
      && dictionary.isFlagAppendedByAffix(stem.getPrefixes().get(0).affixId, flag);
}

One option was built and validated in a scratch worktree of a9779ef3c193; the others are alternatives.

Allow a suffix after the prefix when only the prefix's continuation class carries it (validated) (validated by the checks) (recommended)

#

Pass the entry's own sorted flags down expand and replace line 378 of isCompatibleWithPreviousAffixes. The new path applies a suffix only when the single prefix's continuation class carries its flag and the entry does not, the condition under which the Stemmer accepts such a word (Stemmer.java:269-270). The new forms still pass canStemToOriginal, but that is no guarantee: it compares stem text only, not flags (with work/P it is true for works, which spell() rejects), and NGramFragmentChecker.processNGrams overrides it to return true. The evidence is the runs: every added form is accepted by spell() (French: all 833; the repro dictionaries). The rootFlags check avoids a second copy when the entry has the flag: for the tested rules (cross-product, no conditions) the suffix-first path has already built the word, so work/PS still gives 4 forms, not 5.

if (!isPrefix && !stem.getPrefixes().isEmpty()) {
  // Suffixes are applied before prefixes, so a suffix that the root allows has already been
  // combined with this prefix. Only a suffix that the prefix's continuation class allows
  // (and the root does not) still needs to be applied here.
  return size == 0
      && stem.getPrefixes().size() == 1
      && !FlagEnumerator.hasFlagInSortedArray(flag, rootFlags, 0, rootFlags.length)
      && dictionary.isFlagAppendedByAffix(stem.getPrefixes().get(0).affixId, flag);
}

Trade-offs

  • Scope. One prefix and no suffix yet. A second prefix under COMPLEXPREFIXES, or a prefix-enabled suffix on top of an entry suffix, stays as today; whether C Hunspell accepts those was not checked. Not tested: affix conditions or strips that let a rule apply in one order only, and the fragment-checker path, where canStemToOriginal is bypassed. With a non-cross-product suffix or prefix (SFX S N, PFX P N), spell("reworks") is false and stock, fix A and patch B generate exactly the accepted forms (executed).
  • Cost. One short scan of the entry's flags per suffix flag after a prefix. French generateAllSimpleWords: 24.2 and 23.2 s on main, 27.3 and 22.8 s with the fix (four single runs on a loaded host, not a benchmark): no measurable difference.
  • Compatibility. More forms from the dictionary-tooling API and fewer needless compress edits; no index, analysis, stemming or spell-checking change. A fragment checker from NGramFragmentChecker.fromAllSimpleWords gains the n-grams of the added forms, so a Suggester configured with withFragmentChecker may suggest differently (no change in the hunt probe's 8 misspellings). Only private signatures change.

Downstream note

#

No use of these APIs was found in Elasticsearch, OpenSearch or Solr, so downstream the effect is limited to tools that build word lists, dictionary edits or n-gram fragment checkers with Lucene's generator.

How it was found

#

Differential testing of Lucene's word-form generator, spell() and analyzeSimpleWord() against C Hunspell 1.7.2 on 4,000 generated micro-dictionaries and 1,069 fixture cases, where Lucene's own dependencies fixture showed the gap. A public-API JUnit then reproduced it on the stock jar.

The method in full119 words

Method: cross-implementation differential testing (non-formal tier). A hunt unit compared Lucene getAllWordForms, spell and analyzeSimpleWord with C Hunspell 1.7.2 (spell, stem) and the unmunch tool.

  • Inputs: 4,000 grammar-built micro-dictionaries (per dictionary, every candidate word reachable by at most 3 affix rules) and 1,069 per-root cases from the Hunspell 1.7.2 and Lucene test fixtures; Lucene's dependencies.aff showed the difference.
  • Root causes were separated with switchable shadow fixes: this fix alone adds 21 generated forms that spell() accepts and attributes to the root.
  • The finder then wrote a one-test public-API JUnit that fails on the stock jar. Independent checkers and two executed reviews by a model from another family (OpenAI GPT-5.6) reproduced it with their own tests.

LFV-634, snapshot of 2026-10-29

Registry title
Hunspell getAllWordForms, generateAllSimpleWords and compress never generate a suffix that only a prefix's continuation class allows: with ampere/U and 'PFX U 0 kilo/S', spell() accepts amperes and kiloamperes, but getAllWordForms("ampere") returns only [ampere, kiloampere]
Area
analysis / hunspell (WordFormGenerator: getAllWordForms, generateAllSimpleWords, compress)
Priority
Low, rank 389: Silent incomplete word-form lists in the rarely used opt-in Hunspell tooling API that never affect spell-checking, stemming or search, so it closes the silent Hunspell rows after LFV-376.
Impact class
silent wrong results
Impact note
Only applications that call Lucene's opt-in Hunspell dictionary-tooling API (Hunspell.getAllWordForms and compress, WordFormGenerator.getAllWordForms, generateAllSimpleWords and compress, and indirectly NGramFragmentChecker.fromAllSimpleWords) with a dictionary that has a PFX rule whose continuation class carries an SFX flag that the entry itself lacks are hit: the word-form list is incomplete with no error, and compress() proposes an unneeded flag whose edit can add a word the caller did not ask for (it is listed in getExtraGeneratedWords) [exec]; spell-checking, stemming, HunspellStemFilter, indexing and search are not affected [exec, security probe]; no scale is needed; every release from 9.5.0 through 10.5.2 and main [exec]; Lucene's own dependencies.aff test fixture has the pattern, and the finder reports it in the LibreOffice French dictionary (fr.aff 'PFX Um' unit prefixes: 2 of 3,000 sampled roots, 48 missing forms), which the verifiers did not re-check.
Summary
You load a Hunspell dictionary in which a prefix rule's continuation class allows a suffix, for example 'PFX U 0 kilo/S' and 'SFX S 0 s' with the entry ampere/U, and ask Hunspell.getAllWordForms("ampere") for all forms of that entry. You expect ampere, amperes, kiloampere and kiloamperes: Lucene's own spell() accepts all four and analyzeSimpleWord() analyses each one as a form of ampere/U, as C Hunspell 1.7.2 also does. Instead you get only [ampere, kiloampere], because WordFormGenerator applies suffixes only from the entry's own flags and then forbids any suffix once a prefix has been applied (WordFormGenerator.java:378); generateAllSimpleWords misses the same words, and compress() suggests an unneeded flag (for work/P with 'PFX P 0 re/S', compress([work, rework, reworks]) proposes work/PS, which also adds the unrequested word works).

Not a regression: the guard is as old as the generator. The spell-checker side has accepted this affix pattern since LUCENE-9688 (#10727, commit 0a1a3f4c409, 2021-01-22, first released in 9.0.0), 17 months before the generator existed.
