ICUTokenizerFactory keeps the UTF-8 byte order mark of a custom rule file as rule text

An ICUTokenizerFactory rule file saved with a UTF-8 byte order mark has the invisible mark glued to its first rule: with a BOM, Lucene's KeywordTokenizer.rbbi silently loses its Cyrillic and Thai tokens (4 of 6 left). Files starting with a !! directive fail with a misleading syntax error.

The bug in 30 seconds

#

A custom ICU rule file saved with a UTF-8 byte order mark: the mark ends up inside the first rule.

  1. You tailor one script with your own rule file: rulefiles="Latn:keyword.rbbi", where the file holds the single rule .+ {200}; (all Latin text is one token). Your editor saves it as UTF-8 with a byte order mark (BOM): 3 invisible bytes, EF BB BF, at the start. ICU's own rule-file compiler, genbrk, accepts and recommends that.
  2. You expect the same tokens as from the file without the BOM: ab cd gives one token, [ab cd].
  3. You get 0 tokens and no error. Lucene decodes the BOM to the character U+FEFF and hands it to ICU as the first character of the first rule, so that rule only matches text that starts with U+FEFF. The tokenizer drops every piece of text with rule status 0, which is what text that no rule matched gets.
  4. Lucene's own test file KeywordTokenizer.rbbi (comment lines, then .+ {200};) with a BOM loses the Cyrillic and Thai tokens of its upstream test: 4 tokens instead of 6. With a second rule after the first, only the first rule's tokens vanish: ab 12 cd gives [12] instead of [ab] [12] [cd].
  5. A file that starts with a !! directive fails instead: Lucene's Latin-break-only-on-whitespace.rbbi with a BOM throws IllegalArgumentException: Error 66052 at line 20 column 1, an ICU syntax error that points at line 20, while the cause sits invisibly on line 1.

Who is affected

#

Only applications that set rulefiles (custom per-script ICU rules) and save a rule file as UTF-8 with a BOM, as editors such as Windows Notepad often do. The default configuration is unaffected. A file that starts with a rule silently loses that rule's tokens; one that starts with a directive fails at setup. Rare: no report found since 4.1.0.

Mechanism, terms and numbers745 words

ICUTokenizerFactory's rulefiles argument replaces the break rules of one script with a rule file of your own. parseRules reads that file as UTF-8, blanks the lines that start with # and passes the text to ICU's new RuleBasedBreakIterator(String), but it never removes a leading byte order mark. ICU's string API treats U+FEFF as an ordinary literal character, so the BOM becomes part of the file's first statement. If that statement is a rule, it compiles but can no longer match: the one-rule file .+ {200}; gives no token for ab cd, and Lucene's own test file KeywordTokenizer.rbbi with a BOM drops the Cyrillic and Thai tokens (4 tokens instead of 6), with no error. If it is a !! directive, ICU throws Error 66052 at line 20 column 1 (a rule syntax error) for Lucene's Latin-break-only-on-whitespace.rbbi, pointing away from the invisible cause on line 1. ICU's own compiler for this file format, genbrk, strips a BOM and its man page recommends one; Lucene's word-list and hunspell readers skip it too. Present since rulefiles arrived in 4.1.0 (SOLR-4123, 2012). Skipping a U+FEFF at the start of the first line fixes it; the whole ICU module passes with that change.

Terms

#
  • rulefiles: an argument of ICUTokenizerFactory (ICU analysis module) that replaces the break rules of one script with your own ICU rule file, for example rulefiles="Latn:my.Latin.rules.rbbi".
  • Rule status: each ICU rule ends with a number such as {200}; text a rule matches gets that status. ICUTokenizer emits only pieces with a non-zero status and skips status-0 pieces (ICUTokenizer.java:209-213).
  • Byte order mark (BOM): the 3 bytes EF BB BF that many editors write at the start of a UTF-8 file. Decoded, it is the character U+FEFF.

The bug

#
  1. inform calls parseRules once per script entry of the rulefiles map (ICUTokenizerFactory.java:108-135, the call at :119; a repeated script overwrites the earlier pair, :86-95).
  2. parseRules reads the file with IOUtils.getDecodingReader(stream, UTF_8) (:141). Java's UTF-8 decoder keeps a leading BOM as U+FEFF.
  3. line.startsWith("#") is false for U+FEFF# ..., so the negated test if (!line.startsWith("#")) (:144) is true and the first line is kept instead of blanked. Lines are joined with \n, so line numbers stay as in the file (:147).
  4. new RuleBasedBreakIterator(rules.toString()) (:150). ICU's rule scanner skips only Pattern_White_Space; U+FEFF is not in that set, so it is a literal character. ICU still reads the rest of a # line as a comment, so U+FEFF joins the first statement, after any comment lines.
  5. First statement is a rule (.+ {200};): it compiles as "U+FEFF, then .+". Ordinary text has no U+FEFF, so the rule does not match it and ICU falls back to breaking after each character with status 0. Directly in ICU4J: .+ {200}; on ab cd gives its first boundary at 5 with status 200; with U+FEFF in front, at 1 with status 0. The tokenizer skips all of it. No error.
  6. First statement is a directive or a variable definition: U+FEFF !!forward; is ICU error 66052 (U_BRK_RULE_SYNTAX), reported at the start of the directive (Lucene's two files: line 20 or 44, column 1, after their comment lines); U+FEFF $Var = ...; reads as a use of an undefined variable, error 66058, reported just past the variable name (the independent reproduction's $Ws file: line 1, column 5; with $Whitespace, column 13). Neither message names the invisible character at line 1, column 1.

Exposure and likelihood274 words
  • Who is exposed. Applications that opt in to custom per-script rules: ICUTokenizerFactory with rulefiles, directly, through the icu SPI name, or through a search server schema built on it (the factory javadoc shows such a schema).
  • What it takes. One custom rule file saved as UTF-8 with a BOM. Editors such as Windows Notepad often write one (the SOLR-1865 change note says so), and ICU's genbrk(1) man page recommends one.
  • Silent case. The first statement is a rule, the shape of Lucene's KeywordTokenizer.rbbi: no error; text that only the first rule covers gets no tokens. With a one-rule file that is all text of the script, which is then not indexed and cannot be found; an index built that way needs reindexing after the fix.
  • Loud case. The first statement is a !! directive or a variable definition, the shape of two of Lucene's three test rule files: the analyzer fails to build with an ICU syntax error whose position points at that statement (a directive's line, or just past a variable's name), not at the invisible BOM at line 1, column 1. ICU's own rule guide calls stray literals "surprisingly hard to recognize and debug".
  • Scale. Deterministic: the rules are compiled once, when the analyzer is built, whatever the index size. Which tokens are lost depends on the text and on which rules cover it.
  • How likely. Rare (registry: rare, priority low): opt-in, needs the BOM, a file that starts with a directive or a variable fails loudly (two of Lucene's three test files have that shape), and no report was found in the searched public sources since 4.1.0 (January 2013).

Why it is a bug, not intended

#
  • ICU's own rule-file compiler, genbrk, strips a leading BOM; its man page recommends saving rule files "in UTF-8 with the BOM".
  • Lucene's word-list and hunspell readers skip a leading BOM; this reader never did, and no document or test covers its behaviour.
  • Lucene's own KeywordTokenizer.rbbi with a BOM loses the Cyrillic and Thai tokens its upstream test asserts.
The full argument277 words
  • The factory owns the file reading. It turns bytes into a String and already pre-processes the file (blanking # lines) before handing a String to ICU (ICUTokenizerFactory.java:137-151). ICU maintainers place the encoding signature in the file reader, not the string API (ICU-21907, open: genbrk "detects and honors a BOM"; "the rbbi API for building from rules takes a UnicodeString. The code page stuff is in the genbrk tool").
  • ICU's reader for this file format strips the BOM. genbrk.cpp calls ucnv_detectUnicodeSignature and skips the signature (ruleSourceC += signatureLength); its man page (CAVEATS) says "it is recommended that you write this file in UTF-8 with the BOM". (The man page's sentence that a BOM-less file is read in the operating system's codepage is stale: the code assumes UTF-8.)
  • Lucene's other resource readers skip it. WordlistLoader.getLines ("skip initial bom marker", WordlistLoader.java:302-304, SOLR-1865, 2010) and the hunspell Dictionary (Dictionary.java:246, :351-352; LUCENE-5505, listed under "Bug fixes" in 4.8.0). parseRules (2012, more than two years later) never adopted it.
  • Nothing documents or tests the current behaviour. The javadoc says only that rule files "are compiled by the ICU RuleBasedBreakIterator" and links ICU's syntax page (ICUTokenizerFactory.java:49-52), which says nothing about encodings. SOLR-4123's 21 JIRA comments never discuss encoding, no later commit on the file mentions a BOM, and all five checked-in .rbbi files are BOM-free.
  • Classification is open. No Lucene document promises BOM handling for rule files, so upstream may call the fix an improvement: SOLR-1865 was typed Improvement. Frame the report as "rule files saved with a UTF-8 BOM, which ICU's genbrk strips and recommends, are mis-parsed", not as a broken documented contract.
The devil's-advocate check268 words

An independent reviewer from another model family (OpenAI GPT-5.6), refute lens, executed, without network access: "not real, high", although it reproduced the silent no-token outcome. (a) The javadoc delegates the format to ICU, and RuleBasedBreakIterator(String) treats U+FEFF as a literal by design; Java's UTF-8 decoder keeps it on purpose. (b) Lucene's build-time RBBIRuleCompiler.getRules keeps a BOM the same way. (c) BOM skipping in WordlistLoader and hunspell is component-specific, and Lucene bans BOMs in its own source tree (SOLR-9295, #12937). (d) In 2010 a committer answered "No." to "should we consider that a bug?" about BOMs in Solr's resource files.

Why it fails: (a) the factory reads a file, and ICU's own file reader for this format strips the BOM; the reviewer did not have ICU's genbrk source or man page, and the same reviewer family, given the genbrk man page's CAVEATS section, rated the case real (high), intended-behaviour argument moderate. (b) RBBIRuleCompiler compiles only Lucene's own BOM-free files at build time. (c) The source-tree ban is repository hygiene, not a rule for users' files. (d) That remark predates rule files by more than two years, and the same reply went on: "we can ignore them for the first line of the file to be more user-friendly. I'll open an issue" (SOLR-1865); in 2014 the same slip in hunspell went under "Bug fixes". Two points stand: rule files are trusted configuration, and ICU-2003 (2002, Won't Fix) declined to make ICU's own rule parsers ignore such characters; both fit fixing it in Lucene's file reader (ICU-21907) but keep the classification open. What survives is the bug-or-improvement classification, not the defect.

Suggested fix

#

Recommended Skip a BOM at the start of the first line (recommended, validated)

In ICUTokenizerFactory.parseRules, drop a U+FEFF at the start of the first line before the # comment check, the idiom WordlistLoader.getLines already uses (+6 lines). The 3 new tests pass, and so do the ICU module's 161 tests and its static checks.

    String line = null;
    boolean firstLine = true;
    while ((line = reader.readLine()) != null) {
      // skip initial bom marker
      if (firstLine && line.length() > 0 && line.charAt(0) == '\uFEFF') {
        line = line.substring(1);
      }
      firstLine = false;
      if (!line.startsWith("#")) {
        rules.append(line);
      }

Skip a BOM at the start of the first line (recommended, validated) (validated by the checks) (recommended)

#

Before the # test, remove a U+FEFF at position 0 of the first line. The first comment line is then blanked as intended, and every other line, and so every line number in ICU's error messages, stays as in the file. Same idiom as WordlistLoader.getLines:302-304, with braces; the hunt's sketch is the same change on one line.

    String line = null;
    boolean firstLine = true;
    while ((line = reader.readLine()) != null) {
      // skip initial bom marker
      if (firstLine && line.length() > 0 && line.charAt(0) == '\uFEFF') {
        line = line.substring(1);
      }
      firstLine = false;
      if (!line.startsWith("#")) {
        rules.append(line);
      }

Trade-offs

Only a U+FEFF at the very start of the file is removed; one later in the file, a legitimate literal, is untouched. A file that deliberately began its first rule with a literal U+FEFF would change meaning; ICU's own genbrk strips that character too. Scope: a UTF-8 BOM only (the factory decodes strictly as UTF-8, so UTF-16 files stay unsupported); a file that holds only a BOM was not tested. No CHANGES entry is drafted.

Strip a leading U+FEFF from the assembled rule text (not run)

#

if (rules.length() > 0 && rules.charAt(0) == '\uFEFF') rules.deleteCharAt(0); before compiling.

Trade-offs

One line. Lucene would no longer blank the first line, but ICU reads # ... as a comment anyway, so the result should be the same; not executed.

Reject a BOM with a clear message (not run)

#

Throw an IllegalArgumentException naming the file and the byte order mark.

Trade-offs

Nothing is lost silently and the message is precise, but it refuses a file that ICU's own tool accepts and recommends.

Downstream note

Two downstream search servers' ICU plugins have their own copy of this rule-file reader with the same pattern, so a Lucene fix would not reach them.

How it was found

#

A bounded enumeration ran the same rule through the tokenizer in 9 file layouts (line ends, comments, blank lines, a leading BOM) and 8 spellings of the rulefiles argument, each compared with the plain file, plus a default-configuration control: 18 checks, 2 mismatches, both with a BOM. The idea came from a sibling BOM bug in a word-list loader.

The method in full158 words

Method (semi-formal): bounded enumeration in a hunt unit on analysis-factory resource file formats, on the stock main jar.

  • The harness tried 8 spellings of the rulefiles argument and 9 layouts of the same rule file: with and without a final newline, LF and CRLF line ends, comment lines, indented and trailing comments, blank lines, and a leading BOM. Each was checked through the tokenizer against the tokens of the plain BOM-less file, plus one default-configuration control: 18 checks, 2 mismatches, both BOM files (.+ {200};, alone and after a # line).
  • The hypothesis came from extending the unit's earlier finding, a BOM kept by the snowball word-set loader (LFV-718), to the other resource readers that do not go through WordlistLoader.getLines.
  • The finder reduced it to a public-API JUnit test; no model checker, solver or proof was involved. Writing this doc, a probe added the two-rule case, which shows that only the first rule is broken.

History

#

Introduced with the rulefiles feature (SOLR-4123, 2012-12-03), first released in 4.1.0, unchanged since and not fixed on main. Every executed release from 4.1.0 to 10.5.2 is affected; 4.0.0 has no such feature.

Versions tested6 rows

Introduced by SOLR-4123 "ICUTokenizerFactory - per-script RBBI customization" (JIRA, Improvement; Subversion era, no PR): trunk 6024e1465e0 and the branch_4x merge 9a23a0799e5, both 2012-12-03, committed by Steve Rowe; the 4.1.0 change note credits Shawn Heisey, Robert Muir and Steve Rowe. It added rulefiles and parseRules with no BOM handling. Later commits only changed the charset constant (LUCENE-5560, 2014) and the formatting (LUCENE-9570, 2021).

Not a regression and not tied to an ICU4J version (the bundled 49.1, 53.1, 54.1, 56.1, 62.1, 68.2, 74.2, 77.1 and 78.3 behave the same). In the history clone's release tags the whitespace-normalized parseRules body has three forms, none of which changes behaviour: 4.1.0 to 4.7.2, 4.8.0 to 8.8.1 (charset constant) and 9.0.0 to 10.5.2 (reformat). The clone has no tags for 8.8.2 to 8.11.4; 8.11.4 was executed, and the releases not executed are inferred to be affected from the unchanged code. Upstream main c5ab3e57b9b (2026-10-28) has the same ICU module as a9779ef3c193, with no BOM handling.

LFV-719, snapshot of 2026-10-29

Registry title
ICUTokenizerFactory keeps the UTF-8 byte order mark at the start of a custom per-script rule file (rulefiles) as rule text, so the file either fails with a misleading ICU syntax error or loads without error and the tokenizer then emits no tokens for that script (every release since 4.1.0)
Area
analysis / ICU (ICUTokenizerFactory per-script rule files: rulefiles, parseRules)
Priority
Low, rank 416: This is the same kept-BOM slip in ICUTokenizerFactory's opt-in custom rule files, where most such files fail loudly and only a file that starts with a rule silently loses tokens.
Impact class
silent wrong results
Impact note
Only applications that opt in to custom per-script ICU rule files (the rulefiles argument of ICUTokenizerFactory, analysis-icu module) and save such a file as UTF-8 with a byte order mark are hit, at analyzer setup: a file whose first statement is a rule (for example '.+ {200};', alone or after '#' comment lines, the shape of Lucene's own test file KeywordTokenizer.rbbi) compiles without error and every token of that script is then silently dropped, while a file that starts with a '!!' directive or a variable definition is rejected with an IllegalArgumentException whose position does not point at the BOM; the default configuration (no rulefiles) is not affected, no scale is needed, and it is the same with -ea and -da in every release from 4.1.0 to 10.5.2 [exec].
Summary
You configure ICUTokenizerFactory with rulefiles="Latn:latin.rbbi" and a rule file saved as UTF-8 with a byte order mark (BOM), as editors such as Windows Notepad often write and as ICU's own rule-file compiler genbrk accepts (it strips the BOM, and its man page recommends one), and expect the same tokens as with the same file without the BOM. Instead ICUTokenizerFactory.parseRules decodes the BOM to U+FEFF and passes it to ICU's RuleBasedBreakIterator(String) as rule text: a file that starts with the rule '.+ {200};' (alone or after '#' comment lines) compiles with U+FEFF as a literal prefix of that rule, so 'ab cd' gives no tokens at all instead of ['ab cd'], and a file that starts with a comment and '!!forward;' (the shape of Lucene's Latin-break-only-on-whitespace.rbbi) fails with 'IllegalArgumentException: Error 66052 at line 2 column 1'. Nothing on disk is corrupted, but in the silent case all text of the tailored script disappears from the analyzed output with no error.
Introduced
6024e1465e02 (svn trunk r1416617, 2012-12-03, by sarowe), SOLR-4123 'Add per-script customizability to ICUTokenizerFactory via rule files in the ICU RuleBasedBreakIterator format' (Subversion and JIRA era, no PR; none of the 21 JIRA comments mentions a BOM or the file encoding); merged to branch_4x the same day as 9a23a0799e5e (r1416629), the commit that shipped in 4.1.0. It added the rulefiles argument and parseRules, which reads the file through a UTF-8 decoding reader, drops '#' lines and never removes a leading U+FEFF [read: git log -S parseRules, git blame -w -M -C -C, git log -L in the full-history clone] [exec: 4.0.0 ignores rulefiles, 4.1.0 fails]. Later commits on parseRules changed no behaviour (2f8192f3c5a, LUCENE-5560, 2014, charset constant; 7f8b7ffbcad, LUCENE-9570, 2021, reformatting), and git log --all -G 'FEFF|bom' on the file finds no commit. Not a regression and not tied to an ICU4J version (2012-12-03)
