ConfusionMatrixGenerator never stops a classification that exceeds its 5 s limit, so the documents after it time out too

ConfusionMatrixGenerator waits at most 5 s per classification but never stops a slower one, which keeps its only worker thread, so the next documents time out in the queue behind it. With 3 documents, one 12 s classification drops an instant one; a hung one drops both.

The finding in 30 seconds

#

What ConfusionMatrixGenerator does

#
  1. getConfusionMatrix measures a classifier: for every document that has a class label it asks the classifier for a class from the document's text and counts the pair (true class, assigned class).
  2. Each classification runs on the generator's own single worker thread, and the generator waits at most 5 s for it; a slower one is counted as a timeout and skipped.
  3. getNumberOfEvaluatedDocs() and getAvgClassificationTime() report how many documents were counted and how long a classification took on average.

The finding, step by step

#
  1. You evaluate a classifier with getConfusionMatrix(reader, classifier, "class", "text", -1) (no overall time budget) on 3 labelled documents: the first takes 12 s to classify, the other two are classified instantly and correctly.
  2. The generator runs each classification on its single worker thread and waits at most 5 s ("fail if classification takes more than 5s"); on a timeout it adds 5,000 ms and moves on. You expect only the slow document to be skipped: 2 documents evaluated.
  3. But the slow classification is never stopped and keeps the worker. The second document's task waits in the queue behind it, its 5 s run out before it even starts, and it is counted as a timeout too.
  4. You get 1 of the 2 instant documents counted and an average classification time of 11,999 ms. If the first classification hangs: 0 of 2, an empty matrix and an average of Infinity, after 15 s. No error; only a lower getNumberOfEvaluatedDocs() hints at it.

Who is affected

#

Code that calls this opt-in evaluation utility of the classification module (in Lucene only tests do; no use found in Solr, Elasticsearch or OpenSearch) with no overall budget or one above 5 s, and a classifier that takes more than about 10 s on some document or hangs. Indexes, searches and the classifier's own answers are not affected.

Mechanism, terms and numbers746 words

ConfusionMatrixGenerator.getConfusionMatrix evaluates a Classifier by classifying every labelled document of an index on a one-thread executor, waiting at most 5 s for each ("fail if classification takes more than 5s"). On a timeout it adds 5,000 ms to the running time and moves on, but it never cancels or abandons the timed-out task. That task keeps the only worker, so the next documents queue behind it, use up their own 5 s in the queue and are counted as timeouts too, although their own classification takes no time. On main 645d4fe14a20, 3 documents with a 12 s first classification give 1 of 2 instant documents counted and an average classification time of 11,999 ms; a hung first classification gives 0 of 2, an empty matrix and an average of Infinity. There is no error; only a lower getNumberOfEvaluatedDocs() hints at the loss, and when the stuck classification outlives the call, it and the documents queued behind it are still classified afterwards, with the results thrown away. Every release with the class, 6.0.0 to 10.6.0, and main is affected. It is a low-priority robustness and accounting bug in an opt-in evaluation utility: no index, search or classifier answer is affected.

The bug (main 645d4fe14a20)

#
  1. One worker. getConfusionMatrix creates Executors.newFixedThreadPool(1, new NamedThreadFactory("confusion-matrix-gen-")) (ConfusionMatrixGenerator.java:71-72); the thread is non-daemon (NamedThreadFactory.java:73).
  2. A 5 s wait per document, the Future dropped. For every labelled document: // fail if classification takes more than 5s, then executorService.submit(() -> classifier.assignClass(text)).get(5, TimeUnit.SECONDS), and time += end - start (:100-107).
  3. Timeout = skip and continue, on the same executor. catch (TimeoutException _) { time += 5000; } (:140-142). Nothing cancels the task or replaces the executor.
  4. So the next task queues. The timed-out task still holds the only worker; the next document's task is queued behind it, and its get(5, SECONDS) counts queue time. If the stuck task needs about 5 s more, that document times out without ever starting, and so on.
  5. The overall budget acts only when positive. if (timeoutMilliseconds > 0 && time >= timeoutMilliseconds) break; (:87-89). With no budget every document is visited; with a budget of at most 5,000 ms the loop stops after the first timeout anyway.
  6. Result and afterwards. new ConfusionMatrix(counts, time / counter, counter) (:149), so the average is Infinity when timeouts were charged but nothing was counted (NaN if nothing added time at all) and includes queue waits otherwise. finally shutdown() (:150-151) does not wait, so when the stuck classification outlives the call, it and the tasks still queued run afterwards, and their results go nowhere.

In the 12 s case b queues at 5 s and times out at 10 s; c is queued at 10 s; at 12 s the slow task ends, b runs (its result is discarded) and c returns inside its own 5 s, so only c is counted, and the running time of about 12,000 ms is divided by 1.

Reach rule (from the code, with no overall budget): while the slow classification runs, each later labelled document with text is submitted when the previous wait times out, so the k-th is submitted about 5k s after the slow one started and times out if the slow one is still running 5 s later. A classification of d seconds therefore loses about floor(d/5) - 1 later documents when d > 10 s and none when d < 10 s (near an exact multiple of 5 s, scheduling decides); verifiers ran it at 7 s (none lost) and 12 s (one lost). One that never returns loses every later labelled document with text.

Exposure and likelihood268 words
  • Who calls it. ConfusionMatrixGenerator is the classification module's evaluation utility ("Utilities for evaluation, data preparation, etc."). In Lucene only 8 test classes call it; a read-only code search found no use in Solr, Elasticsearch or OpenSearch.
  • What it takes. One classification slower than about 10 s, or one that hangs (a slow custom or remote classifier, a blocked lock), and no overall budget (timeoutMilliseconds <= 0, as 13 of the module's 15 test calls use) or one above 5 s. The only timings on record are dev@ CI failure mails of 2017-2018 for a classifier performance test that #9270 later relaxed: on slow CI machines the whole evaluation of a 100-document test index took 61-153 s, about 0.6-1.5 s per document. That is weak evidence about classifiers in general, but nothing near 10 s per document. Likelihood: rare.
  • What goes wrong. A smaller evaluation sample, biased by hit order (the documents right after a slow one drop out), with no error; an average classification time that includes queue waits or is Infinity; classification work already counted as timed out keeps running after the call returns.
  • What does not. Nothing is written (the index is only read), the counted cells are correct, getNumberOfEvaluatedDocs() reports the lower count (since 6.1.0), and the overall budget still stops the loop when set, as before (it is checked before each document, so a call can run up to one 5 s wait past it, bug or not). With a budget of at most 5,000 ms there is no extra loss.
  • Priority. Low: a robustness and accounting bug in an evaluation helper.

Why it looks unintended

#
  • The code says a timeout costs one document: "fail if classification takes more than 5s", then it charges 5,000 ms and moves on.
  • The dropped documents are not slow; they only waited behind another one. A legal 12 s classification is enough.
  • Work already counted as timed out still runs after the call returns, and its result is thrown away.
The full argument202 words
  • Code intent. The comment // fail if classification takes more than 5s (ConfusionMatrixGenerator.java:100) and the catch branch that adds 5,000 ms and continues with the next document (:140-142) only make sense if a timeout costs that one document.
  • The dropped documents take no time. They time out only because they waited behind another document's task; no broken classifier is needed (12 s and then a normal return is enough).
  • The skipped work still runs. In the hung case the calls after release are [slow, b, c]: b and c, already counted as timed out, are classified after the call returned, and the results are discarded.
  • Nothing endorses it. No test covers a timed-out classification (the module's tests use fast classifiers and no budget), there is no CHANGES or MIGRATE entry, and the issue that added the timeout (#7538) has only commit notices and one thank-you comment. This shows only that nothing documents the behaviour as intended, not what the author meant.
  • Code intent, not contract: the per-document 5 s limit is in the code only; the javadoc documents only the overall timeoutMilliseconds and the number of evaluated documents. The 12 s case shows the effect most clearly.
The devil's-advocate check168 words

The strongest case for "intended" (a devil's-advocate verifier and the cross-model review lenses): an experimental, best-effort evaluation utility whose javadoc promises only the overall budget (@param timeoutMilliseconds timeout to wait before stopping creating the confusion matrix) and "the no. of documents evaluated", so a partial matrix is a visible, allowed outcome; Future.get(timeout) only bounds the wait; the single worker serialises calls into a classifier with no thread-safety contract (an effect of the code; nothing records it as a goal); Lucene's NIOFSDirectory and MMapDirectory javadocs warn that Thread#interrupt() or Future#cancel(boolean) during I/O can close the channel, so interrupting the stuck task is risky; and a classifier that hangs is arguably broken.

Why it fails: "fail if classification takes more than 5s" cannot mean that documents taking no time fail; a finite 12 s classification triggers it; and the interrupt concern limits how to fix it, not whether it is a bug (the recommended fix does not interrupt). All verifiers returned "real"; the adjudication confirmed with high confidence.

Suggested fix

#

Recommended After a timeout, leave the stuck task alone and continue on a fresh worker

After a timeout, leave the stuck classification running (no interrupt) and continue on a fresh single-thread executor, so later documents no longer queue behind it (+10/-2 lines). Validated: the repro, the module's tests (43, one @Monster skipped) and lint pass; the 3-document check counts 2 of 2 in 5 s. Trade-off: calls may overlap, and classifiers have no thread-safety contract.

After a timeout, leave the stuck task alone and continue on a fresh worker (validated by the checks) (recommended)

#

In the TimeoutException branch, shutdown() the executor whose worker is stuck (it accepts no more work and its thread ends when the stuck classification returns; nothing is interrupted) and continue with a new single-thread executor. Calls without a timeout are unchanged. This stops the executor queue from turning one timeout into several; a classifier that serialises internally (for example, behind a lock the stuck call holds) would still lose the next documents.

Trade-offs

  • Overlap. The stuck classification can now run at the same time as the next ones on the same Classifier instance; today the single worker serialises all calls. This is an open API-contract question: the Classifier interface says nothing about thread safety. The reader is safe to share (IndexReader instances "are completely thread safe", IndexReader.java:58-61), but a classifier's own state may not be. LUCENE-6045 (#7107) refactored the classifiers to be shared across threads, but some keep per-call mutable state: KNearestNeighborClassifier sets the boost settings of its shared MoreLikeThis inside each call (KNearestNeighborClassifier.java:160-172; read, no overlap failure was run). A javadoc note or a cap may be wanted.
  • Threads. One non-daemon thread per timed-out classification lives until that classification returns; one that never returns keeps its thread, as today; from the code (not run), such a non-daemon thread can keep the JVM from exiting normally, today and with the fix. A cap (stop after a few timeouts) would bound them.
  • Accounting unchanged. The 5,000 ms charge is still divided by the evaluated count (average 2,500 ms in the fixed 3-document runs), and the average is still Infinity when timeouts were charged but nothing was evaluated.

cancel(true) the timed-out task and replace the executor (not recommended)

#

A verifier's root-cause sketch: future.cancel(true), shutdownNow() and a new executor on a timeout, shutdownNow() in finally. It also makes the repro pass (6.4 s) and counts 2 documents in 5,080 ms when the first hangs.

Trade-offs

It interrupts a thread that is usually reading the caller's index; the NIOFSDirectory and MMapDirectory javadocs warn that this can close the channel for good (ClosedChannelException afterwards). The verifiers and the adjudication advise against proposing it.

Start each document's 5 s when its task starts running (not built)

#

Keep one worker, and measure the 5 s from the moment the task starts (or wait for the busy worker before submitting the next document).

Trade-offs

No overlap and no interrupt, but with no overall budget a classification that never returns would make the whole call wait forever (today it returns after 5 s per document); it needs a bound such as the overall budget.

Stop at the first timeout whose task is still running (not built)

#

break (or fail) instead of submitting more work to a busy worker.

Trade-offs

No overlap and no interrupt, and the call returns sooner, but no later document is evaluated, so the repro's expected count is not met; it makes the cut-off explicit only if documented.

Complement: document the 5 s limit and define the empty average (not built)

#

Javadoc the hard-coded 5 s per-document limit, and return a defined, documented value from getAvgClassificationTime() when no document was evaluated (today Infinity after timeouts, NaN when nothing added time).

Trade-offs

Accounting only; it does not stop the collateral timeouts.

Downstream note

#

No downstream caller was found: a read-only code search on 2026-10-27 found no use of ConfusionMatrixGenerator in Solr, Elasticsearch or OpenSearch, so only applications that evaluate their own classifiers with it are affected.

How it was found

#

Reading code while sweeping Lucene APIs that run work on executors: the generator creates its own one-thread executor, and its timeout branch never stops the timed-out task. A deterministic JUnit with a latch-blocked classification confirmed it on the stock jar.

The method in full123 words

Method: non-formal (code reading, then a public-API JUnit).

  • A hunt unit swept Lucene APIs that accept or create executors against differently behaving executors and tasks. ConfusionMatrixGenerator creates its own executor, so it was not one of the sweep's surfaces; reading its timeout path showed that a timed-out task is never cancelled and keeps the only worker.
  • A JUnit with one latch-blocked and two instant documents failed on the stock main jar with assertions on and off, and on 10.5.2 and 9.12.3.
  • Then an independent reproducer, a devil's-advocate verifier, cross-model reviews (OpenAI GPT-5.6, executed mode), an adjudication and a credibility audit checked it; a follow-up ran the version history, a prior-report search and a security screen; the repro was minimized to one 2-document test.

History

#

Introduced by LUCENE-6479 (8b2e0d937d5, 2015-09-02), which added the one-thread executor, the 5 s wait and the skip-without-cancel; first released in 6.0.0. Every release from 6.0.0 to 10.6.0 and main is affected; never fixed.

Versions tested8 rows

Introduced by 8b2e0d937d5 "LUCENE-6479 - improved cm testing, added stats, minor fixes" (Tommaso Teofili, @tteofili, 2015-09-02, svn r1700914; SVN era, no pull request; issue #7538). It added the one-thread pool, the comment, submit(...).get(5, SECONDS) with the Future dropped, time += 5000 without a cancel and finally shutdown() in one commit. Before it (2011dbedabd) classifications ran on the caller's thread with no timeout, so a hung one hung the call; the commit bounded the wait but did not isolate the stuck task. 9e340d3e82f (2015-09-03) only added the thread factory.

LFV-633, snapshot of 2026-11-09

Registry title
ConfusionMatrixGenerator never cancels a classification that exceeded its 5 s limit, so later documents queue behind it on the single worker thread and are also counted as timed out
Area
classification / ConfusionMatrixGenerator (classifier evaluation utility)
Priority
Low, rank 835: In the opt-in classification evaluation utility, a stuck or slow classification blocks the single worker and skews the confusion matrix, which fits the executor stuck-task rows after the OfflineSorter hang LFV-384.
Impact class
minor
Impact note
Applications or tests that evaluate a Classifier with ConfusionMatrixGenerator.getConfusionMatrix (an opt-in evaluation utility in lucene/classification; in-tree only tests call it and no downstream caller was found) with timeoutMilliseconds <= 0 or above 5000 get a smaller, hit-order-biased confusion matrix with no error once one classification runs longer than about 10 s or never returns: documents whose own classification is instant and correct are counted as timed out because they waited behind it (finite 12 s classification: 1 of 2 later documents lost; hung classification: all later documents lost, getAvgClassificationTime Infinity), the shortfall shows only in getNumberOfEvaluatedDocs, and the stuck and queued classifications keep running on the generator's worker thread after the call returns; no index, search or stored data is touched; every release since 6.0.0 [exec].
Summary
You evaluate a classifier with ConfusionMatrixGenerator.getConfusionMatrix and one document's classification is slow (more than about 10 s) or hangs. You expect, as the code's own comment ('fail if classification takes more than 5s') and its skip-and-continue timeout branch intend, that only that document counts as a timeout and the other documents are still classified and counted. Instead the timed-out classification is never cancelled and keeps the generator's only worker thread, so the next documents wait behind it, their own 5 s waits expire while they are still queued, and they are dropped too: with a hung first document 0 of 2 instantly classifiable documents are counted (empty matrix, average time Infinity), with a 12 s one 1 of 2.
