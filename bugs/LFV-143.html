Byte DOT_PRODUCT scores are mirrored at 65,536 to 131,071 dimensions: the divisor len * (1 << 15) overflows int, so the closest vector scores lowest

Lucene computes the byte DOT_PRODUCT score's divisor, dimensions x 32,768, in int: for 65,536 to 131,071 dimensions it is negative, so the least similar vectors rank first; at 131,072 it is 0. Stock formats stop at 1,024 dimensions, so only direct scoring calls and formats raising that limit are hit.

The finding in 30 seconds

#

The byte DOT_PRODUCT score is 0.5 + dot / (dimensions x 32,768). The divisor is multiplied in 32-bit int before it becomes a float, so it is right up to 65,535 dimensions, negative from 65,536 to 131,071 and zero at 131,072.

Background: how a byte DOT_PRODUCT score is made

#
  1. A byte vector stores each dimension as a signed byte, -128 to 127, so the dot product of two byte vectors is a whole number.
  2. Lucene maps it into [0, 1]: divide by the largest possible magnitude, dimensions x 2^15 (2^15 = 2 x 128 x 128), and add 0.5. Higher scores mean closer vectors, and kNN keeps the highest.
  3. Three places compute this: VectorUtil.dotProductScore (behind VectorSimilarityFunction.DOT_PRODUCT and the default scorers) and, with the Panama vector code on memory-mapped files, a query-time and a graph-build scorer.

The finding, step by step

#
  1. Take byte vectors of 65,536 dimensions: the query and document A are all +1, document B is all -1. Both documents have the same norm, as byte DOT_PRODUCT requires.
  2. Score them with VectorSimilarityFunction.DOT_PRODUCT.compare, or index them through a vectors format that raises the 1,024-dimension limit and run a KnnByteVectorQuery.
  3. You expect 0.5 + dot / (65,536 x 32,768): A = 0.5000305 and B = 0.49996948, so A, a copy of the query, ranks first.
  4. Instead 65,536 x 32,768 = 2,147,483,648 does not fit in an int and wraps to -2,147,483,648: A = 0.49996948, B = 0.5000305, so B outranks A (a six-document kNN test came back in exactly reverse order). Nothing throws.
  5. Up to 65,535 dimensions all is correct. Higher up it gets worse: at 131,071 dimensions A and B score -3.4999695 and 4.4999695, and at 131,072 the divisor wraps to 0, so scores are Infinity, -Infinity or NaN.

Who is affected

#

Only byte DOT_PRODUCT vectors of 65,536 or more dimensions. Stock vectors formats accept at most 1,024, so ordinary indexes are safe. Hit: code calling the scoring API on such arrays, and fields indexed through a format that raises getMaxDimensions, the delegation pattern committers recommend for higher limits. No such deployment is known.

Mechanism, terms and numbers655 words

The byte DOT_PRODUCT score is documented as "scaled to be in [0, 1]" and computed as 0.5 + dot / (len * 2^15). Three places write the divisor as (float) (len * (1 << 15)): VectorUtil.dotProductScore, which VectorSimilarityFunction.DOT_PRODUCT.compare(byte[], byte[]) and the default scorers use, and the two Panama MemorySegment byte scorers (query time and graph build). The product is taken in int and only then cast, so it is exact up to 65,535 dimensions, wraps to -2^31 at 65,536 and to 0 at 131,072.

From 65,536 to 131,071 dimensions every score is mirrored around 0.5: a vector scores its own copy 0.49996948 and its opposite 0.5000305, so any two candidates compare the wrong way round (a six-document kNN test came back in exactly reverse order). In that band scores can also leave [0, 1] and go negative; at 131,072 they are infinite or NaN. Nothing throws. No stock vectors format accepts more than 1,024 dimensions, so ordinary indexes are safe; it is reached through the public scoring API on long arrays and through a format that raises getMaxDimensions, the delegation pattern committers recommend for higher limits. No deployment with byte vectors that large is known, so the priority is low. Casting to float before multiplying, at all three sites, fixes it and leaves every score below 65,536 dimensions bit-identical.

The bug, step by step (main 645d4fe14a20)

#
  1. The expression. VectorUtil.dotProductScore (VectorUtil.java:427-438): javadoc "Dot product score computed over signed bytes, scaled to be in [0, 1]", comment "divide by 2 * 2^14 (maximum absolute value of product of 2 signed bytes) * len", then float denom = (float) (a.length * (1 << 15)); and return 0.5f + dotProduct(a, b) / denom;. VectorSimilarityFunction.DOT_PRODUCT.compare(byte[], byte[]) returns it (VectorSimilarityFunction.java:65-68), and DefaultFlatVectorScorer scores through compare.
  2. The copies. With the Panama provider on MMapDirectory, the query-time Lucene99MemorySegmentByteVectorScorer.DotProductScorer returns 0.5f + raw / (float) (query.length * (1 << 15)) (:127) and the graph-build scorer 0.5f + raw / (float) (values.dimension() * (1 << 15)) (Lucene99MemorySegmentByteVectorScorerSupplier.java:169). "On MMapDirectory" is shorthand: these scorers are used only when the vector values have a non-null index slice that is a MemorySegmentAccessInput; otherwise, for example for the in-memory vectors at flush, scoring falls back to DefaultFlatVectorScorer and VectorUtil. The native dot-product option uses the same two classes and keeps the divisor.
  3. The wrap. Java multiplies two ints in int and drops the high bits; the cast to float comes after. len x 2^15 fits only while len <= 65,535 (65,535 x 32,768 = 2,147,450,880).
  4. Only the normalization is wrong. The signed dot product itself fits in an int below 131,072 dimensions (|dot| <= len x 2^14). Float DOT_PRODUCT and byte COSINE are correct at 65,536 dimensions (a checker ran them); byte EUCLIDEAN and MAXIMUM_INNER_PRODUCT do not divide by the length. Only raw byte DOT_PRODUCT scores are affected: the short[] overload normalizes differently, and the scalar-quantized scorers use their own formulas.

For 65,536-131,071 dimensions the divisor is len x 2^15 - 2^32, negative, so every score is mirrored around 0.5. Scores leave [0, 1] once |dot| > (2^32 - len x 2^15) / 2 (from 65,537 dimensions with saturated components, from 131,065 with unit components). At 131,072 the divisor is 0 (NaN when the dot product is 0 too). The divisor's pattern repeats every 131,072 dimensions (positive but far too small for 131,073-196,607: order right, scores can leave [0, 1]); from 131,072 dimensions the dot product's own int accumulator can also overflow with saturated components, a separate limitation (LFV-138). Default and Panama providers print the same values.

Exposure and likelihood302 words
  • Reachable through direct calls to VectorUtil.dotProductScore, VectorSimilarityFunction.DOT_PRODUCT.compare(byte[], byte[]) or the flat byte scorers on arrays of 65,536+ bytes, and through a KnnVectorsFormat that raises getMaxDimensions, for example a thin delegating wrapper over the stock HNSW format. Committers recommend that pattern: #13150 was closed "Won't Do" with "Lucene prefers the delegation pattern", and #12436 (which made the limit codec-defined in 9.8.0) and a 2023 java-user thread say the same. Apache Solr ships such a wrapper with no upper bound (read from Solr's source, not run).
  • Not reachable with stock formats and no wrapper: every one declares 1,024, checked at index time (IndexingChain.java:1386-1391), the only dimension check: KnnByteVectorField's "dimension > 1024" javadoc is not enforced. Elasticsearch caps vector fields at 4,096 dimensions although it keeps its own copy of the expression.
  • Once such a field exists, every query on it is affected, for every user: for 65,536-131,071 dimensions every score comparison is reversed whatever the data. A delegating-format kNN test returned its 6 same-norm documents as [5, 4, 3, 2, 1, 0], the query's own vector last; recall and ranking on larger graphs were not measured. At 131,071 dimensions its kNN scores ran from about 250 down to -372.5 (the adjudication's re-run; random vectors, so the values depend on the seed), and MIGRATE.md (LUCENE-7996) says scorers may not return negative scores; at 131,072 scores are infinite or NaN. The HNSW graph is built from the same inverted similarities with either provider (effect on graph quality not measured).
  • Silent: no exception on main or 10.1.0 and later, with assertions on or off. On 9.x and 10.0.0 with assertions on, a negative score trips TopScoreDocCollector's assert score >= 0 (executed on 9.12.3, read for 10.0.0), a test-time assertion removed in 10.1.0 (#13939). No crash, hang or index damage.

Why it looks unintended

#
  • The API promises scores "scaled to be in [0, 1]", higher for closer vectors, with no length limit.
  • In #913 (2022) msokolov showed that the byte dot product's int accumulator is safe up to 2^17 dimensions; this divisor breaks at 2^16.
  • Float DOT_PRODUCT, byte COSINE and the Panama query scorer before 10.3.0 (a long product) are correct at these sizes.
The full argument267 words
  • The contract. VectorUtil.dotProductScore: "scaled to be in [0, 1]" (VectorUtil.java:428), with the intended divisor in the comment (:435). VectorSimilarityFunction.compare(byte[], byte[]): "Higher similarity scores correspond to closer vectors" (VectorSimilarityFunction.java:132-133), no length limit. msokolov on #12256: "the only requirement is that they sort the same as the dot-product score". uschindler on #12342: byte scores "can't get <0" thanks to dotProductScore. The ordering statements fail from 65,536 dimensions; the [0, 1] range and non-negativity from 65,537 with saturated components, from 131,065 with unit components, and for every input at 131,072.
  • The authors' own bound. In the #913 review (2022), rmuir asked about overflow of the byte dot product's int accumulator, and msokolov answered that the limit is "2^31/2^14 = 2^17 and I don't think we would ever have a 2^17-dimensional vector". The remark is about the accumulator, not this divisor, and is not an API contract; it shows the authors assumed int arithmetic safe up to 2^17 dimensions, while the score's divisor overflows at half that.
  • The siblings are right. Float DOT_PRODUCT and byte COSINE are correct at 65,536 dimensions. The Panama query scorer's divisor was correct from 9.11.0 to 10.2.2 because it multiplied query.byteSize(), a long; #14874 replaced it with query.length without discussing the type.
  • No source found makes it intended. No reviewed javadoc, test, CHANGES/MIGRATE entry, commit or searched discussion declares the behaviour at 65,536+ dimensions intended (the searches have gaps). TestVectorUtil checks dotProductScore only on 2- and 3-element vectors (with a reference that has the same int product), and the byte-kernel tests stop at 4,098 dimensions.
The devil's-advocate check138 words

The strongest case for "intended or unsupported": every stock format caps at 1,024; KnnByteVectorField's javadoc says a dimension above 1,024 throws; the util package says its APIs are "primarily internal"; LUCENE-10471 called 16K dimensions "well beyond any stated use case"; and in #913 the author did not expect vectors this large. A checker rated this argument moderate.

Why it fails: the limit has been codec-defined since 9.8.0 and committers recommend raising it by delegation, so the KnnByteVectorField sentence is stale, not a contract; VectorSimilarityFunction lives in org.apache.lucene.index and documents no limit; the authors' own accumulator bound (2^17) is twice the size where this breaks; and the defect is operator order in one expression, fixed by moving one cast per site. The scale explains the low priority, not the behaviour. All checkers and the adjudication rejected the argument.

Suggested fix

#

Recommended Cast to float before multiplying, at all three sites

Cast to float before multiplying, at all three sites: float denom = (float) a.length * (1 << 15); and the same in the two Panama scorers. Every score below 65,536 dimensions stays bit-identical. Validated with both vectorization providers; fixing only VectorUtil leaves the Panama scorers inverted.

-    float denom = (float) (a.length * (1 << 15));
+    float denom = (float) a.length * (1 << 15);

-      return 0.5f + raw / (float) (query.length * (1 << 15));
+      return 0.5f + raw / ((float) query.length * (1 << 15));

-          return 0.5f + raw / (float) (values.dimension() * (1 << 15));
+          return 0.5f + raw / ((float) values.dimension() * (1 << 15));

Trade-offs

  • One cast moves per site; no behaviour change below 65,536 dimensions (performance not benchmarked). Empty arrays passed directly still give NaN (0 / 0), as before (executed).
  • All three sites are needed: with only the VectorUtil change, the Panama scorers still invert the scores (executed).

Downstream note

#

A product that passes a schema-defined dimension straight to a delegating vectors format with no upper bound (Solr's wrapper does, read from its source, not run) would serve inverted rankings on byte DOT_PRODUCT fields of 65,536+ dimensions. Only configuration creates such a field; document authors could then use the inversion for rank placement.

How it was found

#

Non-formal: while modelling the integer ranges of the byte-vector kernels, an AI tool read the score's divisor and saw that len * (1 << 15) is multiplied in int and reaches 2^31 at 65,536 dimensions. A JUnit test on the stock jars confirmed it, and independent checkers reproduced it with their own tests.

The method in full125 words

Method: non-formal (code reading plus an executed test; no model checker or solver produced the signal), a hunt unit on VectorUtil and the vectorization providers.

  • The finder was bounding the int ranges of the byte kernels; a small arithmetic script for the sibling candidate (LFV-138) also prints the divisor's threshold, a.length = 2^16, by plain integer arithmetic.
  • A JUnit test on the stock jars confirmed it with assertions on and off and with the Panama and default providers; the fix was first checked by shadowing the patched classes onto the jars.
  • A cross-model reviewer (OpenAI GPT-5.6) then corrected the first claim's expected scores (0.5 +/- 2^-15, not 1.0 and 0.0) and had the kNN test reframed, since it raises the stock format's declared limit.

History

#

Introduced in 9.4.0 by #1054 (a693fe819b0, 2022-08-10, LUCENE-10577); copied into the Panama graph-build scorer in 9.11.0 (#13339) and the query-time scorer in 10.3.0 (#14874, which replaced a correct long). Fails on releases from 9.4.0 to 10.6.0 and on main; 9.3.0 has no such API. Not fixed upstream.

Versions tested7 rows

Introduced by a693fe819b0, LUCENE-10577 / #1054 "enable quantization of HNSW vectors to 8 bits" (msokolov, 2022-08-10; branch_9x 87a8f7d48f3), which added byte vectors with the divisor (float) (a.length * (1 << 15)); #1073 (798c02dd70d, 2022-08-20) fixed an offset in the same formula and kept the int product. The 1,024-dimension limit was then a global constant; since #12436 (9.8.0) it is the codec's getMaxDimensions.

Copies: #13339 (05f04aa08a4, 2024-05-21, first release 9.11.0) added the Panama graph-build scorer with values.dimension() * (1 << 15) in int, and the query-time scorer with query.byteSize() * (1 << 15), a long, which is correct. #14874 (b3f4011292c, 2025-07-29; backport #15010, first release 10.3.0) changed the latter to query.length. So with Panama on MMapDirectory, kNN query-time scores were right in 9.11.0-10.2.2 (read at every tag; executed with Panama forced on 9.12.3 and 10.2.2, since 9.11.0 cannot enable Panama on JDK 25) and wrong from 10.3.0, while the graph was still built from int-product scores; with the default provider they are wrong from 9.4.0.

Not fixed upstream (2026-10-31): main 2f424fd428da, branch_11x, branch_10_6 and the 10.6.0 tag still have all three expressions.

LFV-143, snapshot of 2026-11-08

Registry title
Byte DOT_PRODUCT scores (VectorUtil.dotProductScore and the two Panama byte scorers) compute len * 2^15 in int, so from 65,536 dimensions every score is mirrored around 0.5 (closer vectors score lower) and at 131,072 dimensions scores become +/-Infinity or NaN
Area
util / VectorUtil byte DOT_PRODUCT score x internal/vectorization / Panama MemorySegment byte scorers
Priority
Low, rank 1002: From 65,536 dimensions byte DOT_PRODUCT scores are mirrored, which inverts every ranking on such a field, but no stock format accepts more than 1024 dimensions and no deployment with byte vectors that large is known.
Impact class
silent wrong results
Impact note
Only byte (int8) DOT_PRODUCT vectors of 65,536 or more dimensions are affected, which no stock KnnVectorsFormat accepts (all declare getMaxDimensions 1024): code that calls VectorUtil.dotProductScore, VectorSimilarityFunction.DOT_PRODUCT.compare(byte[], byte[]) or the flat byte scorers on such arrays, and fields indexed through a delegating KnnVectorsFormat that raises getMaxDimensions (the pattern committers recommend for raising the limit, and what Solr ships with no upper bound, read from its source, not run); there every byte DOT_PRODUCT score is mirrored around 0.5 for 65,536-131,071 dims so kNN returns the least similar documents first, scores leave [0, 1] (including negative kNN scores) near the top of that band, and at 131,072 dims they are +/-Infinity or NaN; -ea and -da, ordinary data, no deployment with such dimensions is known.
Summary
You score two byte vectors of 65,536 dimensions with VectorSimilarityFunction.DOT_PRODUCT (or VectorUtil.dotProductScore, or run a KnnByteVectorQuery on a byte DOT_PRODUCT field indexed through a format that raises getMaxDimensions) and expect the documented score 0.5 + dot / (len * 2^15): within [0, 1] and higher for more similar vectors. Instead the divisor len * (1 << 15) is multiplied in int before the cast to float, so from 65,536 dimensions it wraps to a negative number and every score is mirrored around 0.5: a vector identical to an all-ones query scores 0.49996948 and its opposite 0.5000305, and kNN returns the documents in exactly reverse order. At 131,072 dimensions the divisor wraps to 0 and the scores are +Infinity, -Infinity or NaN.
