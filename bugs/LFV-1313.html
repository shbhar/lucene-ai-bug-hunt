Automaton.copy while the current state is still open silently corrupts the automaton once that state is finished

Calling copy on a hand-built Automaton while a state is still open corrupts it once that state is finished: the state's arcs merge in place and the next arc overwrites a copied one. A 4-state automaton that should accept "acx" accepts nothing, silently; affected since 4.10.0.

The finding in 30 seconds

#

A state's arcs are kept as one block in a shared array, and finishing a state may shrink its block, which is only safe while it is the last block. copy appends a whole automaton after the still-open block, so when that block shrinks, the next arcs are written over copied ones.

Background: how a hand-built Automaton stores its arcs

#
  1. You build an Automaton state by state: createState(), then addTransition(source, dest, label) for one state's arcs, then the next state's. Each state's arcs must be added at once.
  2. All arcs live in one int[], 3 ints per arc (dest, min, max), one contiguous block per state; nextTransition is where the next int is written.
  3. When you move on to another state (or call finishState()), the open state is finished: its arcs are sorted and merged in place (arcs a and b to the same state become one arc [a-b]), and nextTransition moves back by the ints saved.

The finding, step by step

#
  1. Build state 0 by hand: addTransition(0, 1, 'a') and addTransition(0, 1, 'b'). State 0 is still the open state; its 2 arcs fill ints 0-5 of the transition array (3 ints per arc).
  2. While state 0 is open, append Automata.makeChar('x') with a.copy(...). It becomes states 2 and 3, and its arc 2 -x-> 3 goes to ints 6-8, right after state 0's arcs. The write position is now 9.
  3. Add addTransition(1, 2, 'c') and call finishState(). You expect 0 -[a-b]-> 1 -c-> 2 -x-> 3, which accepts "acx"; that is what you get with finishState() before copy.
  4. Instead, adding state 1's arc first finishes state 0: a and b merge into one arc [a-b], and the write position drops from 9 to 6, inside the copied arc. State 1's c is written over state 2's x: state 2 now reads 2 -c-> 2, accept state 3 is unreachable, and run("acx") is false, with no exception or assertion.

Who is affected

#

Only application code that builds an automaton by hand with the experimental Automaton class and calls copy while the state it is adding arcs to is open, with arcs that merge on finish (like the single characters of [ab]). It then matches the wrong strings, silently. No Lucene parser, query or Operations method does this.

Mechanism, terms and numbers508 words

Automaton stores every transition in one int[] as (dest, min, max) triples, one contiguous block per state, and the state still receiving arcs is meant to be the last block. copy(other) never looks at that open state: it appends other's triples after the open block (Automaton.java:205-236). When the open state is finished later, by finishState() or by adding arcs to another state as the class javadoc documents, finishCurrentState merges its arcs in place and lowers the write position by the ints it saved (:294), which is right only for the last block.

After copy the write position lands inside the copied block, and the next state's arcs overwrite a copied arc. The result is a wrong automaton with no exception or assertion, with assertions on and off. No Lucene parser, query or Operations method makes this call. The one-line fix calls finishState() at the start of copy.

A state dump on main (a probe, not the repro): right after copy, state 0 holds [a-a]->1 [b-b]->1 and state 2 holds [x-x]->3; at the end, state 0 holds [a-b]->1, state 1 [c-c]->2 and state 2 [c-c]->2. State 3, the only accept state, is unreachable, so the automaton accepts no string at all.

A second effect, not part of the repro: with no further arcs after copy and finishState(), the receiver still reads the copied arcs, but copying the receiver into another automaton copies only [0, nextTransition) and loses them: the copy reads them as [0-0]->0, or, when its transition array is exactly full (a default new Automaton()), reading copied state 2 throws ArrayIndexOutOfBoundsException (Automaton.java:495).

Exposure and likelihood170 words
  • Who is hit. Application code that gives a state its arcs and then appends a sub-automaton with copy before moving on (a natural "build a prefix, then append a piece" order), where the open state's arcs merge when it is finished: adjacent labels or duplicates to one destination. Any matcher or query built on the result can give wrong answers (the repro's automaton accepts no string at all).
  • Default vs opt-in. Public @lucene.experimental API (Automaton.java:43); no setting; assertions on or off.
  • Lucene itself. Every non-test caller of Automaton.copy copies into an automaton with no open state (Operations.java:176, :188 in optional, :301 in repeat, :486 in union: states are created, copied, then wired), and Operations.repeat (:312, :315) and GraphTokenStreamFiniteStrings.java:171 use Automaton.Builder.copy, which is safe. So RegExp, wildcard, fuzzy, prefix and range queries and the query parsers cannot produce it.
  • Scale. None needed: 4 states, 3 addTransition calls and 1 copied arc.
  • Likelihood. Rare: no public report since 4.10.0 (2014).

Why it looks unintended

#
  • copy's javadoc promises to copy all states and transitions, appended, with no condition on the receiver.
  • The class javadoc says a state is finished once you add arcs to another state, exactly what the repro does.
  • copy's first body (June 2014, never released) added arcs one by one, finishing the open state first; with it, 4.10.0 passes the bug's test.
The full argument221 words
  • The contracts. copy: "Copies over all states/transitions from other. The states numbers are sequentially assigned (appended)." (Automaton.java:201-204). The class javadoc: "Each state must have all of its transitions added at once" and "Once a state is finished, either because you've starting adding transitions to another state or you call finishState, then that states transitions are sorted ... and reduced" (:36-41). The repro adds state 0's arcs at once, then adds arcs to another state.
  • Silent where the API is otherwise loud. The misuse the class detects, adding arcs to a state that was already finished, throws IllegalStateException "already had transitions added" (:169-172). Here the result is just wrong.
  • History. On the LUCENE-5752 branch, copy first added each arc with addTransition, whose first call finished the receiver's open state. 5927445bb60 (2014-06-14) replaced it with the bulk System.arraycopy body; its message does not mention copy. The stock 4.10.0 jars fail an earlier form of the same test (the same automaton, with x built by hand); with only copy shadowed by the earlier body they pass.
  • No test or document endorses it. No upstream test copies into an automaton with an open state (the closest, TestOperations.naiveOptional, copies into a fresh one, TestOperations.java:602-612), and CHANGES.txt and MIGRATE.md do not mention copy or finishState.
The devil's-advocate check169 words

The strongest case for "intended": finishState's javadoc says "call this once you are done adding transitions for a state" (Automaton.java:321-325), and the caller is done with state 0 when it calls copy without calling it. The class is @lucene.experimental, its javadoc points to Automaton.Builder "if this is too restrictive" (:36-37), no Lucene code copies into an open state, and nobody reported it in twelve years.

Why it fails: the same javadoc continues "This is automatically called if you start adding transitions to a new source state, but for the last state you add you need to [call] this method yourself", so the explicit duty is for the last state only, and the repro meets it. The class javadoc's own definition of finishing covers the repro's order, copy states no precondition, and @lucene.experimental is about API stability, not silent corruption. The intended-behaviour devil's advocate and the adjudication rated the argument weak; the cross-model reviewer rated it moderate and found that it does not hold.

Suggested fix

#

Recommended A. Finish the open state at the start of copy (recommended; validated)

Call finishState() at the start of copy, so the open state is finished while its block is still the last one. It does nothing when no state is open. Validated through gradle: the repro passes with assertions on and off, the core util.automaton tests pass, and the formatter check is clean.

Trade-offs

finishState() is a no-op when no state is open (Automaton.java:326-331), so every in-tree caller is unchanged. Besides the bug, it changes what happens when more arcs are added to the old open state after copy: that then throws the existing IllegalStateException "already had transitions added" (:169-172), which enforces the class javadoc's "all of its transitions added at once" rule. Today that sequence silently corrupts the automaton when other has transitions; when other has none (e.g. Automata.makeEmptyString()) it is correct today and would then throw.

Trade-offs

Not validated. Makes the precondition explicit and loud, but breaks callers that copy while a state with non-merging arcs is open, which get a correct automaton today.

C. Document the precondition on copy

A javadoc note: call finishState() before copy.

Trade-offs

Not recommended: it leaves a silent corruption that a one-line change removes.

Downstream note

#

Downstream code that builds automata by hand can avoid it until a fix ships by calling finishState() before every copy, or by building with Automaton.Builder.

How it was found

#

A semi-formal proof-obligation audit of Automaton's build protocol: the state still receiving arcs must stay the last block of the transition array. copy breaks that obligation, and a public-API JUnit test witnessed the wrong automaton on stock main.

The method in full69 words

The obligation comes from finishCurrentState, whose nextTransition decrement is correct only when the open block is the last block. The audit checked copy against that obligation: it appends after the open block without finishing it. An executable JUnit test on the stock main build confirmed the overwrite, and an independent reproducer, a cross-model review, an intended-behaviour devil's advocate and an adjudication then checked it (see the checks below).

Impact class
minor
Impact note
Only application code that builds an automaton by hand with the @lucene.experimental Automaton class and calls copy while the state it is adding arcs to is still open, with arcs that merge when that state is finished (adjacent labels or duplicates to the same destination, like the single-character arcs of a class [ab]), is hit: once the open state is finished the automaton silently accepts the wrong language (a copied state's arc is overwritten and part of the copied automaton becomes unreachable), with -ea and -da, no exception and no scale needed; no Lucene parser, query, analyzer or Operations method makes this call (they copy into a receiver with no open state, and Automaton.Builder is not affected), and every release from 4.10.0 through 10.6.0 is affected.
Summary
You build an Automaton by hand: state 0 gets arcs 'a' and 'b' to state 1; while state 0 is still the state being built you append a small automaton x (0 -x-> 1, accepting) with copy, which becomes states 2 and 3, and then add state 1's arc 'c' to state 2, which by the class javadoc finishes state 0. You expect 0 -[a-b]-> 1 -c-> 2 -x-> 3, which accepts "acx", exactly what you get if you call finishState() before copy. Instead the automaton silently rejects "acx": finishing state 0 merges its two arcs into one in place and moves the transition write position back into the copied block, so state 1's new arc overwrites copied state 2's arc (state 2 now reads 2 -c-> 2 and state 3 is unreachable).
