CharsRefBuilder.append(CharSequence, int, int) does not throw IndexOutOfBoundsException when start > end

CharsRefBuilder is a java.lang.Appendable, so append("abc", 2, 1) (start 2 after end 1) must throw IndexOutOfBoundsException, as StringBuilder does. On a builder that already holds text it returns normally and appends nothing, so a caller's backwards range goes unnoticed.

The finding in 30 seconds

#

append(csq, start, end) goes straight from the null check to grow(length + end - start) and the copy loop for (i = start; i < end; i++). With start > end, grow asks for less than the builder holds (a no-op) and the loop never runs, so nothing rejects the range.

Background in three steps

#
  1. CharsRefBuilder is Lucene's growable char[] buffer that builds a CharsRef, much like a StringBuilder. It is a public class marked @lucene.internal.
  2. It implements java.lang.Appendable, so any code that writes to an Appendable can write into it.
  3. Appendable.append(csq, start, end) appends the characters csq[start, end) and must throw IndexOutOfBoundsException when start or end is negative, start > end, or end > csq.length().

The finding, step by step

#
  1. Put "abc" into a CharsRefBuilder (length 3), then call append("abc", 2, 1): a range whose start, 2, is after its end, 1, for example from an off-by-one in your own code.
  2. You expect IndexOutOfBoundsException: the class implements java.lang.Appendable, whose append(csq, start, end) must throw when start > end. StringBuilder and Lucene's CharTermAttributeImpl do.
  3. Instead the call returns normally. The builder still holds "abc", length 3, with assertions on and off.
  4. Why: the method never checks the range. grow(3 + 1 - 2) = grow(2) changes nothing, and the copy loop for (i = 2; i < 1; i++) runs zero times. On an empty builder, grow(-1) trips an assertion, but only under -ea.

Who is affected

#

Only code that calls this three-argument overload, directly or through a java.lang.Appendable reference, with a backwards range from its own bug. It gets a silent no-op instead of an exception, so text goes missing without an error. No non-test Lucene code calls this overload with an explicit range, and the text already in the builder never changes.

Mechanism, terms and numbers452 words

CharsRefBuilder implements java.lang.Appendable, and its append(CharSequence csq, int start, int end) has no javadoc of its own, so it inherits Appendable's contract: throw IndexOutOfBoundsException if start or end is negative, start > end, or end > csq.length(). StringBuilder and the other Appendable in lucene-core, CharTermAttributeImpl, do.

CharsRefBuilder does not check the range at all. On a builder that already holds text, append("abc", 2, 1) returns normally and appends nothing, with assertions on and off, so a caller whose own code computed the range backwards never finds out. The text already in the builder does not change. On an empty builder the same call trips assert minSize >= 0 in ArrayUtil.grow under -ea only. Present since the method was added in 4.10.0 (LUCENE-5892, 2014). The fix is one line, Objects.checkFromToIndex(start, end, csq.length()), as CharTermAttributeImpl has.

The code (CharsRefBuilder.java:73-83)

#
@Override
public CharsRefBuilder append(CharSequence csq, int start, int end) {
  if (csq == null) {
    return append(NULL_STRING);
  }
  grow(ref.length + end - start);          // :78
  for (int i = start; i < end; ++i) {       // :79-81
    setCharAt(ref.length++, csq.charAt(i));
  }
  return this;
}

The bug, step by step

#
  1. There is no range check between the null branch (:75-77) and the copy.
  2. With "abc" in the builder, append("abc", 2, 1) calls grow(3 + 1 - 2) = grow(2) (:78). The array already holds at least 3 chars, so ArrayUtil.grow returns it unchanged (CharsRefBuilder.java:98-100; ArrayUtil.java:481-486).
  3. The loop for (i = 2; i < 1; ++i) (:79-81) runs zero times, and the method returns this.
  4. On an empty builder, step 2 is grow(0 + 1 - 2) = grow(-1), which trips assert minSize >= 0 (ArrayUtil.java:482) when assertions are on. With assertions off it is the same silent no-op.

An empty range outside the sequence, such as (5, 5) or (-1, -1) on "abc", is accepted the same way; Appendable requires an exception there too.

Not part of this bug

#
  • With a non-empty range, an end past csq.length() or a negative start does throw IndexOutOfBoundsException, from csq.charAt, after length() was already bumped. The JDK 25 Appendable javadoc allows that: the contents are "unspecified if ... an exception is thrown when accessing the CharSequence".
  • append(null, 1, 3) appends all of "null", where Appendable (and StringBuilder, CharTermAttributeImpl) would append "ul"; TestCharsRefBuilder.testAppendNull pins this (TestCharsRefBuilder.java:46-47), so leave it alone. The recommended fix keeps it: it fixes backwards ranges and is not full Appendable conformance.
  • analysis-common OpenStringBuilder.append(CharSequence, int, int) is just as lenient, and facet's package-private CharBlockArray.append(CharSequence, int, int) reads its third argument as a length (CharBlockArray.java:90-96); those are different classes.
Exposure and likelihood180 words
  • Who: code that writes into a CharsRefBuilder through append(CharSequence, int, int), directly or through a java.lang.Appendable reference, and passes a backwards range by its own mistake (for example an end computed from an indexOf that returned -1).
  • Not hit: no non-test Lucene code calls this overload with an explicit range; only TestCharsRefBuilder does, with valid ranges and the null case (TestCharsRefBuilder.java:36, :46). append(CharSequence) passes 0 and csq.length() (CharsRefBuilder.java:70), and the other in-tree three-argument calls on a CharsRefBuilder use the char[] overload (:121-126), e.g. KatakanaRomanizer.java:136, :150, :165 and TokenStreamFromTermVector.java:146.
  • Effect: a silent no-op instead of a fail-fast exception; the caller's bug shows only later as missing text. Nothing already in the builder changes and nothing is written out of bounds.
  • Default vs opt-in: not a configuration matter; only callers of this public method of an @lucene.internal class.
  • Scale and likelihood: one call; no in-tree production path reaches it, so the only effect shown is text missing from the builder. Rare: no public report of it was found since 4.10.0 (2014).

Why it looks unintended

#
  • The class implements Appendable and the method has no javadoc of its own, so it inherits "@throws IndexOutOfBoundsException If ... start is greater than end".
  • lucene-core's other Appendable, CharTermAttributeImpl, checks first with Objects.checkFromToIndex(start, end, csq.length()); CharsRef range-checks "to meet the specs of CharSequence".
  • Every JDK Appendable tried throws for append("abc", 2, 1); no Lucene text or test chooses leniency.
The full argument241 words
  • The contract: public class CharsRefBuilder implements Appendable (CharsRefBuilder.java:24); the method is an @Override with no javadoc (:73-74), so it inherits Appendable's "@throws IndexOutOfBoundsException If start or end are negative, start is greater than end, or end is greater than csq.length()" and "behaves in exactly the same way as the invocation out.append(csq.subSequence(start, end))" (JDK 25). "abc".subSequence(2, 1) throws.
  • lucene-core's other Appendable checks first: CharTermAttributeImpl.append(CharSequence, int, int) calls Objects.checkFromToIndex(start, end, csq.length()) before changing anything (CharTermAttributeImpl.java:124-129); LUCENE-2401 (#3476) made it "fully implement Appendable".
  • The same package range-checks CharSequence: CharsRef.charAt and subSequence: "NOTE: must do a real check here to meet the specs of CharSequence" (CharsRef.java:140-141, :147-148). The builder's own char[] append fails loudly on a bad range: System.arraycopy throws (CharsRefBuilder.java:121-126; on an empty builder a negative length trips the grow assertion first, under -ea).
  • The class takes Appendable's special rules into account: append(CharSequence) appends "null" for a null sequence (CharsRefBuilder.java:67-69), added on review in LUCENE-5892 (#6954).
  • Every JDK Appendable tried throws for this input: the seven tried, StringBuilder, StringBuffer, StringWriter, CharArrayWriter, PrintWriter, PrintStream and CharBuffer (and CharTermAttributeImpl) all throw for append("abc", 2, 1).
  • Nothing allows it: no javadoc, test, CHANGES or MIGRATE entry chooses leniency; TestCharsRefBuilder.testAppend uses only valid ranges (TestCharsRefBuilder.java:24-41); the LUCENE-5892 thread discussed the null rule, return types, IOException and code sharing with CharTermAttributeImpl, never ranges.
The devil's-advocate check296 words

The strongest case for "intended": CharsRefBuilder is @lucene.internal; Appendable's class javadoc says "Since this interface may be implemented by existing classes with different styles of error handling there is no guarantee that errors will be propagated to the invoker"; the trigger is the caller's own error and the outcome is a harmless no-op. An independent reviewer from another model family (OpenAI GPT-5.6) rated it not a bug on these grounds, while reproducing it and agreeing on the root cause and the fix. A maintainer may add: the org.apache.lucene.util package javadoc says its classes "are generally not intended for direct use by most applications" (util/package-info.java:22-23); analysis-common's OpenStringBuilder.append(CharSequence, int, int) is just as lenient (OpenStringBuilder.java:68-74); and this very method already departs from Appendable for a null sequence with a sub-range, pinned by testAppendNull.

Why it fails: @lucene.internal renders as "NOTE: This API is for internal purposes only and might change in incompatible ways in the next release" (RenderJavadocPlugin.java:506), and the package javadoc speaks of audience and stability ("APIs in this package are primarily internal and may change between releases", :35): neither waives the @throws clause of a JDK interface the class chose to implement. Our reading of the class-level sentence (the JDK does not say which classes it means): it excuses "existing classes" with their own error style, not a class made an Appendable in 2014 whose lucene-core sibling CharTermAttributeImpl checks the range. OpenStringBuilder has the same gap (a different class), and the null handling was asked for on review (#6954) and is pinned by a test, while nothing chooses leniency for ranges. What remains is an impact argument, and it is why this is Low: it is an Appendable range-check fix, not a bug users are hitting.

A. Objects.checkFromToIndex after the null branch (validated) (recommended)

#

In CharsRefBuilder.append(CharSequence, int, int) (CharsRefBuilder.java:73-83), plus import java.util.Objects;:

if (csq == null) {
  return append(NULL_STRING);
}
Objects.checkFromToIndex(start, end, csq.length());
grow(ref.length + end - start);

Trade-offs

  • The same call CharTermAttributeImpl uses; a few integer comparisons per call (no benchmark was run). append(CharSequence) passes 0 and csq.length(), so it does not trip the check (for a sequence whose length does not change during the call).
  • Leaves the null sub-range rule that testAppendNull pins unchanged, so it fixes backwards ranges but is not full Appendable conformance.
  • Side effect: an end past csq.length() or a negative start now throws before anything is written.
  • A caller that passes a backwards range today gets an exception instead of a no-op; that is the point, but say so in CHANGES.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: the 66 top-level org.apache.lucene.util test classes of lucene/core (TestCharsRefBuilder 2 of 2 incl. testAppendNull, TestCharsRef 5 of 5, ...) and the repro: 67 classes, 561 tests, 0 failures, 10 skipped (an incremental gradle run: the compile tasks were up to date from the fix runs just before it; the test task ran).
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test.
  • The full lucene/core suite was not run.

B. An explicit if-and-throw

#

if (start < 0 || start > end || end > csq.length()) throw new IndexOutOfBoundsException(...) at the same place.

Trade-offs

Same behaviour with a custom message; more code than A and unlike the sibling class.

C. Delegate to append(csq.subSequence(start, end))

#

Let the CharSequence check the range.

Trade-offs

May allocate a subsequence per call (String.subSequence copies) and depends on every CharSequence checking its range. Not recommended.

D. Document that the range is not checked

#

Add javadoc saying invalid ranges are ignored.

Trade-offs

Contradicts the inherited @throws clause of Appendable. Not recommended.

Downstream note

#

Downstream code that writes into a CharsRefBuilder as an Appendable and counts on the exception to catch bad offsets will not get it; nothing else changes.

How it was found

#

Semi-formal: a proof-obligation audit of CharsRefBuilder against the java.lang.Appendable contract it implements, which requires an IndexOutOfBoundsException for start > end. The method has no range check that could discharge the obligation, and a JUnit test on stock main witnessed it.

The method in full107 words
  • Obligation: append(csq, start, end) throws IndexOutOfBoundsException when start or end is negative, start > end, or end > csq.length() (the JDK Appendable javadoc, inherited because the override has no javadoc of its own).
  • Finding: CharsRefBuilder.append(CharSequence, int, int) checks only for null; with start > end, grow and the copy loop both do nothing, so the call returns normally.
  • Witness: a one-test JUnit repro on main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks). The claim was narrowed to start > end: the out-of-range charAt case throws the right exception, and the JDK allows the contents to be unspecified there.
