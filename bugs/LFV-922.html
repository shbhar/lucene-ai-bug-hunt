The finding in 30 seconds

#

A term found 6 times in 3 documents: the explanation says its inputs are those counts + 1, but prints 6 and 3.

Background: explain and the DFR after effect

#
  1. IndexSearcher.explain(query, doc) returns a tree: each node is a number, a description of how it was computed, and its inputs as children.
  2. DFRSimilarity (divergence from randomness) scores a term as basic model x after effect, from tfn, the term's count in the document adjusted for document length. Lucene ships two after effects, B and L.
  3. After effect B uses F = the term's total count in the index + 1 and n = the number of documents that contain it + 1. Its value is (F + 1) / (n x (tfn + 1)).

The finding, step by step

#
  1. Score with new DFRSimilarity(new BasicModelIn(), new AfterEffectB(), new NormalizationH2()) and index five short documents in which the term a occurs 6 times in 3 documents (totalTermFreq 6, docFreq 3). Call IndexSearcher.explain for f:a on document 0, a b c a a.
  2. The after-effect node reads 0.61625993 = AfterEffectB, computed as (F + 1) / (n * (tfn + 1)) from:, with inputs labelled F, ... + 1 and n, ... + 1. You expect 6 + 1 = 7 and 3 + 1 = 4: (7 + 1) / (4 x (2.245 + 1)) = 0.616, the value shown (tfn = 2.245 is the term's count, 3, adjusted for document length).
  3. Instead the inputs print as 6 = F, ... + 1 and 3 = n, ... + 1, and tfn is listed twice. Redo the printed formula with the printed numbers and you get (6 + 1) / (3 x 3.245) = 0.719, not 0.616.
  4. The node's 0.616 and the score, 1.0760068, are right: scoring adds the 1s, but explain prints the raw counts under labels that promise the + 1. Every explained hit with after effect B shows this, since 8.0.0.

Who is affected

#

Users who choose DFRSimilarity with AfterEffectB (any basic model and normalization; not Lucene's default) and read explain output. Every explained hit shows F and n one too low and tfn twice, so recomputing the node from its printed inputs gives a wrong number. Scores, ranking and matching are unaffected.

Mechanism, terms and numbers515 words

AfterEffectB scores with F = totalTermFreq + 1 and n = docFreq + 1, and its explanation node says so: "AfterEffectB, computed as (F + 1) / (n * (tfn + 1)) from:", with children labelled "F, total number of occurrences of term across all documents + 1" and "n, number of documents containing term + 1". But the children are the raw stats.getTotalTermFreq() and stats.getDocFreq(), and tfn is listed twice. For a term with totalTermFreq 6 and docFreq 3 the children show 6 and 3 where the labels promise 7 and 4, and the formula on the printed children gives 0.71897 while the node correctly shows 0.61626 (DFR I(n)B2). Scores, ranking and the node value are correct. It came in with LUCENE-8011 (8.0.0), which added the formula text and the "+ 1" labels but kept the raw values; 7.7.3 printed accurate raw labels. A fix that changes three lines (+2/-3) prints the + 1 and drops the duplicate child.

Mechanism (Lucene main 645d4fe14a20, AfterEffectB.java)

#
  • scoreTimes1pTfn (:32-36): long F = stats.getTotalTermFreq() + 1; long n = stats.getDocFreq() + 1; return (F + 1.0) / n;
  • explain(BasicStats stats, double tfn) (:39-49):
    • node value scoreTimes1pTfn(stats) / (1 + tfn) (:41): right;
    • description "AfterEffectB, computed as (F + 1) / (n * (tfn + 1)) from:" (:42);
    • child tfn (:43);
    • child stats.getTotalTermFreq() labelled "F, total number of occurrences of term across all documents + 1" (:44-46): the raw value;
    • child stats.getDocFreq() labelled "n, number of documents containing term + 1" (:47): the raw value;
    • child tfn again (:48).
  • DFRSimilarity.explain (DFRSimilarity.java:134-145) adds this node (:144) to every explanation of a DFRSimilarity built with AfterEffectB, whatever the basic model and normalization. Scoring (:127-131) uses only scoreTimes1pTfn, so the score is not involved.

The example, step by step

#

Five documents a b c a a, a d e, f g h, a a b, x y z; term a: docFreq 3, totalTermFreq 6. Document 0 has a 3 times in 5 terms; NormalizationH2 gives tfn = 3 x log2(1 + 3.4 / 5) = 2.2453837.

  1. Node: (6 + 1 + 1) / ((3 + 1) x (2.2453837 + 1)) = 8 / 12.98 = 0.61626, printed 0.61625993: right.
  2. Printed children: 6 = F, ... + 1, 3 = n, ... + 1.
  3. The printed formula on the printed children: (6 + 1) / (3 x 3.2453837) = 7 / 9.74 = 0.71897.
  4. Score: 1.7460274 (BasicModelIn) x 0.61625993 = 1.0760068: right, the same on 7.7.3, 8.0.0, main and main with the fix.

Why no test caught it

#

CheckHits.verifyExplanation accepts a node whose description matches .*, computed as .* from: (CheckHits.java:375, :437-438) by setting combined = value (:494-496), so it never checks such a node against its children. The test framework's RandomSimilarity does use AfterEffectB (RandomSimilarity.java:96, :131), so Lucene's tests explain with it, but nothing compares the children with their labels.

Exposure and likelihood156 words
  • Who. Users of DFRSimilarity built with AfterEffectB (public constructors, @lucene.experimental, not the default similarity) who read IndexSearcher.explain output, for example to tune or debug relevance. Lucene ships two after effects, B and L; L's explanation is consistent.
  • What they see. On every explained hit, F and n one lower than their labels say, and tfn twice. Recomputing the node from its printed inputs gives 0.719 instead of the 0.616 shown in the example, which can make a reader suspect the score.
  • Not affected. Scores, ranking, matching, the node's own value and the top explanation value; nothing throws; assertions on and off behave the same.
  • Downstream (by reading, not run): Elasticsearch and OpenSearch expose a DFR similarity with after effect b and an explain API, so their explain output would show the same numbers.
  • Likelihood: plausible. Every explained hit is affected, but only a reader who checks children against labels notices; no report since 8.0.0 (2019).

Why it looks unintended

#
  • The node states its formula and its labels promise the + 1, as the scoring code and Lucene's testIFB compute.
  • BasicModelG prints F = totalTermFreq + 1 under the same label; 7.7.3 printed raw counts under raw labels.
  • LUCENE-8011 added the "+ 1" labels and a second tfn but kept the raw values; GITHUB#13691 fixed a similar explain-only error.
The full argument241 words
  • The node defines its operands. "computed as (F + 1) / (n * (tfn + 1)) from:" and the "+ 1" labels (AfterEffectB.java:42-47) match the scoring code (:33-34); only the printed values differ.
  • What a description means. Explanation.match: "@param description how {@code value} was computed", "@param details sub explanations that contributed to this explanation" (Explanation.java:42-47).
  • Lucene's own test writes the + 1. TestSimilarityBase.testIFB (:449-453) computes the after effect as B = (TOTAL_TERM_FREQ + 1 + 1) / ((DOC_FREQ + 1) * (FREQ + 1)). On LUCENE-8020 (#9068), rmuir described the code as using (F + 1 + 1) / ((n + 1) * (tfn + 1)).
  • Same family. BasicModelG.explain computes F = stats.getTotalTermFreq() + 1 (BasicModelG.java:55) and prints it under "F, total number of occurrences of term across all docs + 1" (:62-63). BasicModelIn prints the raw docFreq under "n, number of documents containing term", without "+ 1".
  • History. Before LUCENE-8011 the node read "AfterEffectB, computed from:" with 6.0 = totalTermFreq and 3.0 = docFreq: accurate (7.7.3, executed). LUCENE-8011 (8.0.0 CHANGES "Improved similarity explanations", CHANGES.txt:6825) added the formula, the "+ 1" labels and a second tfn, and kept the raw values. Its issue (#9059) and review (apache/lucene-solr#280) do not discuss the values.
  • Precedent. 9.12.0 Bug Fixes: "GITHUB#13691: Fix incorrect exponent value in explain of SigmoidFunction." (CHANGES.txt:2705), a wrong explain value with a correct score.
The devil's-advocate check192 words

The strongest case for "not a bug": IndexSearcher.explain "is intended to be used in developing Similarity implementations" (IndexSearcher.java:934-940); AfterEffectB, AfterEffect and DFRSimilarity are @lucene.experimental; no javadoc promises that a "computed as" node can be rebuilt from its children, and CheckHits treats such nodes as opaque; the strings have stood for about nine years without a complaint; and the open LUCENE-8023 (#9071) proposes dropping the "+ 1" terms from the scores, so one could call the raw counts the real F and n.

Why it fails: under any reading, a child whose label says "+ 1" and whose value has no + 1 contradicts itself. If the raw counts were meant, the label and the formula would say so, as 7.7.3's did and as BasicModelIn's n child does today. The duplicated tfn child reads as a copy slip. The rest (expert API, experimental class, no complaints) argues for Low priority, which is how it is classed, not for intent. LUCENE-8023 would change scores; it does not make today's explanation right. The independent verifier, the devil's-advocate check and the cross-model reviews (OpenAI GPT-5.6) all rated the works-as-designed case weak.

Downstream note

#

Elasticsearch and OpenSearch expose a DFR similarity with after effect b and an explain API, so their explain output would show the same off-by-one inputs (by reading, not run); scores there are unaffected too.

How it was found

#

A semi-formal check explained 3,178 hits under 79 similarity configurations and recomputed every "computed as" formula from the inputs its node lists. All 1,000 AfterEffectB nodes disagreed with their own formula while the other DFR nodes agreed, and the check caught 10 of 10 injected errors. The finding was then reduced to a public-API test.

The method in full171 words

Method: semi-formal (a differential evaluation of explain trees against their own formula strings).

  • Sweep. A test program ran IndexSearcher.explain over 79 similarity configurations x TermQuery, PhraseQuery, SynonymQuery and a 2-clause BooleanQuery x boosts 1 and 2.5, plus other scoring queries: 3,178 explained hits, 14,574 "computed as <formula> from:" nodes (14,554 evaluated on their own labelled children) and 3,806 labelled statistics checked against the index, with assertions on and off.
  • Result. All 1,000 AfterEffectB formula nodes over the 20 DFR configurations that use after effect B disagreed with their formula, and 200 + 200 "F, ... + 1" / "n, ... + 1" children were 1 below the index statistic + 1; every other DFR node agreed.
  • Oracle check. 10 of 10 injected mutants were detected, so the check is not vacuous.
  • Then a public-API JUnit, a cross-model refute review (OpenAI GPT-5.6, with execution), an independent reproducer, a cross-model intended-behaviour review, a devil's-advocate check, an adjudication, the registration check, an audit, a repro minimization, the version-history runs and a prior-report search followed.

Anyone who calls IndexSearcher.explain on a search that uses a DFRSimilarity built with AfterEffectB (any basic model and normalization; public constructors, @lucene.experimental, not the default similarity; default IndexWriterConfig, codec and searcher, -ea and -da, a plain TermQuery) sees F and n each 1 lower than their labels promise, plus a duplicated tfn child, on every explained hit; scores, ranking, matching, the AfterEffectB node value and the top explanation value are all correct and nothing throws; every release from 8.0.0 to 10.6.0; by the finder's reading (not executed) Elasticsearch and OpenSearch expose a DFR similarity with after effect 'b' and an explain API, so their explain output would show the same.
Summary
You search with DFRSimilarity(basic model, new AfterEffectB(), normalization) and call IndexSearcher.explain on a hit. The AfterEffectB node says 'computed as (F + 1) / (n * (tfn + 1)) from:' and labels its children 'F, total number of occurrences of term across all documents + 1' and 'n, number of documents containing term + 1', so for a term with totalTermFreq 6 and docFreq 3 you expect F = 7 and n = 4. Instead the children show 6 and 3 (the raw statistics) and tfn is listed twice, so the formula on the listed children gives 0.71897 while the node correctly shows 0.61626 (I(n)B2); the score is right and only the explanation's operands are wrong.
