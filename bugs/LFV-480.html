Inputs from BufferedIndexInput.wrap and the default BufferedIndexInput.slice accept seek and skipBytes past the end instead of throwing EOFException

An input from BufferedIndexInput.wrap, or from the default slice() of a BufferedIndexInput subclass, accepts seek past its end: on a 20-byte input seek(21) succeeds and getFilePointer() returns 21, though IndexInput#seek promises EOFException. The error comes one read later; no default Directory produces such an input.

The finding in 30 seconds

#

A wrapped or default-sliced input checks its length when it reads, not when it seeks.

Background: seeking an IndexInput, and BufferedIndexInput.wrap

#
  1. An IndexInput reads a file. seek(pos) moves the read position and getFilePointer() reports it. Since 5.5.0 its javadoc says a position beyond the end throws EOFException at once.
  2. BufferedIndexInput is the public base class for inputs that read through a buffer (1,024 bytes by default). A subclass implements two hooks: readInternal fills the buffer, seekInternal moves the underlying position.
  3. BufferedIndexInput.wrap(desc, in, offset, length) returns a view of length bytes of another input. The default slice() of a BufferedIndexInput subclass returns the same kind of view.

The finding, step by step

#
  1. Write a 30-byte file to a ByteBuffersDirectory, open it and take its first 20 bytes with BufferedIndexInput.wrap("w", in, 0, 20). The wrapped input's length() is 20.
  2. Call seek(21), one byte past the end. You expect EOFException: IndexInput#seek says "If this is beyond the end of the file then this will throw EOFException", and the stock input and its own 20-byte slice both throw it.
  3. Instead seek(21) returns normally and getFilePointer() reports 21 on a 20-byte input; skipBytes(21) does the same. Only the next readByte() throws EOFException ("read past EOF").
  4. Why: BufferedIndexInput.seek hands every target outside its buffer to the subclass hook seekInternal(pos) (BufferedIndexInput.java:326-334), and the wrapper's seekInternal is empty (:423). Nothing compares the target with length() until refill() runs at the next read (:290-295).
  5. The same class backs the default slice() of any BufferedIndexInput subclass that does not override it, and, in 9.0 to 10.1.x, the slices of the opt-in DirectIODirectory. Every release from 5.5.0 to 10.6.0 is affected.

Who is affected

#

Only code that seeks or skips past the end of a BufferedIndexInput.wrap input (Apache Solr's block-cache input calls wrap() in its slice()), of a default slice() of a BufferedIndexInput subclass outside Lucene, or, in 9.0 to 10.1.x, of an opt-in DirectIODirectory slice. No default Directory is affected on main. The error comes one read late, and that read returns no data.

Mechanism, terms and numbers668 words

IndexInput#seek promises: "If this is beyond the end of the file then this will throw EOFException and then the stream is in an undetermined state", and skipBytes is "functionally equivalent" to that seek (IndexInput.java:69-91). The public static BufferedIndexInput.wrap(desc, in, offset, length) and the default BufferedIndexInput.slice(), which returns wrap(...), both return the private SlicedIndexInput. BufferedIndexInput.seek hands every target outside its buffer to seekInternal(pos), and SlicedIndexInput.seekInternal is empty, so seek(21) on a 20-byte input returns normally, getFilePointer() reports 21, and the error only comes at the next read. In normal use the core Directories' own inputs and slices (ByteBuffersDirectory, NIOFSDirectory, MMapDirectory) throw at the seek (an MMapDirectory input after a read has hit EOF is a separate bug, LFV-130), and NIOFSDirectory and RAFDirectory do it with exactly the check SlicedIndexInput lacks.

The empty method came with wrap() and the default slice() in LUCENE-4371 (4.9.0, 2014). It became a contract violation in 5.5.0, when LUCENE-6932 wrote the seek sentence and fixed four other inputs but not this one. Every release from 5.5.0 to 10.6.0 is affected. The reach is narrow: no default Directory on main produces this class; it is reached through direct wrap() calls, slices of BufferedIndexInput subclasses outside Lucene that keep the default slice(), and, in 9.0 to 10.1.x, slices of the opt-in DirectIODirectory. The first read after the accepted seek never returned data. A three-line check in SlicedIndexInput.seekInternal fixes it.

Terms

#
  • IndexInput: Lucene's read handle on a file. seek(pos) moves the read position, getFilePointer() reports it, length() is the size, and skipBytes(n) is seek(getFilePointer() + n) (IndexInput.java:86-91).
  • BufferedIndexInput (core, public, abstract, BufferedIndexInput.java:25): the base class for inputs that read through a buffer. Subclasses implement readInternal (fill the buffer from the current position) and seekInternal ("Sets current position in this file, where the next readInternal will occur", :336-342). The NIOFSDirectory and misc RAFDirectory inputs are subclasses.
  • BufferedIndexInput.wrap(desc, in, offset, length) (public static, :371-379, javadoc: "in most cases ineffective, because it may double buffer!"): a buffered view of length bytes of another input, starting at offset. Its class is the private SlicedIndexInput (:382). The default slice() returns the same view (:354-357); the in-tree subclasses override it.

The bug

#
  1. seek(pos) outside the buffer sets bufferStart = pos, empties the buffer and calls seekInternal(pos) (:326-334). It never compares pos with length(); that is left to the hook.
  2. SlicedIndexInput.seekInternal is empty: protected void seekInternal(long pos) {} (:422-423). Any target is accepted, and getFilePointer(), which is bufferStart + buffer.position() (:321-322), returns it.
  3. The first length check runs at the next read: refill() finds no bytes left and throws EOFException (:290-295); SlicedIndexInput.readInternal has a second check (:413-416). For some targets more than 2^31 bytes past the end, the int cast at :294 gives a value above the 1,024-byte buffer and the read fails with an unchecked IllegalArgumentException from buffer.limit (:303) instead (executed at 2^31+1 bytes past the end; at 2^32-10 or 2^32 bytes past the end the read still throws EOFException, at :415 or :295).
  4. skipBytes goes through seek, and clones, slices and nested wraps of a wrapped input are SlicedIndexInputs too, so all of them accept the same targets.
  5. The in-tree subclasses that conform put exactly this check in their own seekInternal (NIOFSDirectory.java:203-208, misc RAFDirectory.java:191-196: if (pos > length()) throw new EOFException(...)) and override slice().

Exposure and likelihood444 words
  • Who is hit. Code that calls the public static BufferedIndexInput.wrap(...) directly, and clones and slices of such inputs. Downstream example: Apache Solr's block-cache input CustomBufferedIndexInput, which extends IndexInput (not BufferedIndexInput), returns BufferedIndexInput.wrap(...) from its own slice() (source read, not run). Slices of any BufferedIndexInput subclass outside Lucene that keeps the default slice(): they accept seeks past their end even when the subclass's own seek rejects them (executed: a strict subclass's own seek(101) throws, its 10-byte default slice accepts seek(11)).
  • Also hit in 9.0.0 to 10.1.x: slices of the opt-in misc DirectIODirectory, whose slice() returned wrap(...) (executed on 9.1.0, 9.12.3, 10.0.0 and 10.1.0; the slice class is BufferedIndexInput$SlicedIndexInput). 10.2.0 gave them their own class (#14103).
  • Not hit: every default setup on main. No in-tree Directory produces a SlicedIndexInput, and nothing in-tree calls wrap() (grep). Fresh MMapDirectory, NIOFSDirectory and ByteBuffersDirectory inputs and slices throw at the seek (differential harness and controls, on fresh inputs; LFV-130 is a separate MMapDirectory exception after a read has hit EOF).
  • What happens. The illegal seek or skip succeeds and getFilePointer() reports a position beyond length(); the next read throws EOFException, or, for some targets more than 2^31 bytes past the end, IllegalArgumentException. Code that checks getFilePointer() after a seek, or relies on the seek to reject a bad offset, sees the error one call later, or never if it does not read.
  • What does not happen. The first read after the accepted seek never returned a byte: a probe of 56,550 accepted past-end seeks or skips and 82,650 reads per run (main with assertions on and off, 10.5.2), and 42,252 reads on DirectIODirectory slices of 9.12.3 and 10.1.0, found no byte from outside the input. Caveat from the same probe: a caller that catches that failure and reads again can, for some targets more than 2^31 bytes past the end, get zeros or bytes this input buffered earlier, never bytes from outside it; that stale-byte half is a separate, already tracked refill() defect (LFV-492), and fix A removes this route to it. No Lucene code path was found that reads the same input again after this exception; CodecUtil.checkFooter(in, priorException) does keep using an input after an earlier exception, but for a position past the end it throws CorruptIndexException before it reads (CodecUtil.java:482).
  • Default vs opt-in, scale. Opt-in: an expert API (wrap(), or a custom BufferedIndexInput subclass), or the opt-in DirectIODirectory in 9.0 to 10.1.x. One byte past the end is enough; data size plays no part. Valid indexes never produce such a target. Likelihood: rare; no matching public report was found in the sources searched.

Why it looks unintended

#
  • IndexInput#seek: "If this is beyond the end of the file then this will throw EOFException".
  • LUCENE-6932 (5.5.0) wrote that on purpose, for all implementations, and fixed four inputs; this one was missed.
  • In normal use the core Directories' inputs and slices throw at the seek; BaseDirectoryTestCase: "Seeking past EOF should always throw EOFException".
The full argument269 words
  • Contract, this exact call. IndexInput#seek: "Sets current position in this file, where the next read will occur. If this is beyond the end of the file then this will throw EOFException and then the stream is in an undetermined state." (IndexInput.java:69-71). skipBytes: "Behavior is functionally equivalent to seeking to getFilePointer() + numBytes" (:80). Neither wrap() nor slice() documents an exception.
  • Written on purpose, for all implementations. LUCENE-6932 (#7990, ddc65d977f92, 2016-01-21, 5.5.0) added that sentence and the API-change entry "IndexInput.seek implementations now throw EOFException if you seek beyond the end of the file" (lucene/CHANGES.txt:9726-9727). Its discussion chose to "throw EOFException immediately if you try to seek beyond the end of the file, rather than delaying it until the next read" (patch comment, 2016-01-21). It fixed the RAM, NIOFS, SimpleFS and RAF inputs; its 30 comments never mention SlicedIndexInput or wrap.
  • Tests. BaseDirectoryTestCase#testSeekPastEOF ("Seeking past EOF should always throw EOFException", :731) and #testSeekBeyondEndOfFile run against Directories; no in-tree Directory produces this class and no upstream test calls wrap(), so it was never exercised.
  • Consistency. In normal use the core Directories' inputs and slices (ByteBuffersDirectory, NIOFSDirectory, MMapDirectory) throw at the seek in the same differential harness, and the two in-tree BufferedIndexInput subclasses implement the check in their seekInternal. (Two separate, state- or class-specific exceptions are tracked on their own: an MMapDirectory input after a read hit EOF, LFV-130, and the DirectIOIndexInput slice slack pinned by #16619.) Executed 5.4.1 against 5.5.0: the wrap results are identical, only the stock controls switch from accepting to throwing.
The devil's-advocate check328 words

The strongest case for "not a bug" (verifiers and the adjudication built it): lazy EOF on the next read is how BufferedIndexInput always worked, and seekInternal's javadoc does not ask for a check; wrap() is discouraged ("in most cases ineffective, because it may double buffer!"; LUCENE-5681: "It is almost always a better idea to implement slicing on your own!") and a 2014 Won't Fix (#6890, LUCENE-5828) said "The slice wrapper is not used in any core directories, so maybe we should leave it as it is"; #16619 (2026-09) tolerates an analogous slack in DirectIOIndexInput, and one of its tests deliberately keeps a seek beyond a slice's length working there; and nothing in-tree reaches it on main.

Why it fails: LUCENE-6932 replaced the lazy model on purpose, two years after #6890, and listed it under API changes for all implementations. The warnings about wrap() concern double buffering and per-byte bounds-check cost, not seek semantics, and the fix adds nothing per byte (seekInternal runs only for seeks outside the buffer). #16619 is partly a fair point: it made the first fill of a DirectIOIndexInput slice lazy and pinned the old behaviour in two tests, one called "a characterization test, not an endorsement" (TestDirectIODirectory.java:380-386), the other (testSeekBeyondSliceLengthMatchesEagerBehaviour, :448-483) keeping a seek beyond a slice's length working, with the next read returning the byte past the slice's end while the target stays inside the buffered window. It is a different class with a different fix site, and the tests keep old behaviour through a refactor rather than define the contract, but they show maintainers keeping a similar quirk for compatibility. "Not reached in-tree" limits impact, not validity: wrap() is public static and BufferedIndexInput is a public, non-final base class whose default slice() returns it. This is a real contract violation; maintainers may still accept it as long-standing, low-value compatibility behaviour, which is a choice of priority, compatibility or fix site, not "works as designed".

Suggested fix

#

Recommended A. EOF check in SlicedIndexInput.seekInternal

Give SlicedIndexInput.seekInternal the check NIOFSDirectory and RAFDirectory already have: throw EOFException when pos > length. With it the repro passes with assertions on and off, every core store test passes (29 classes, 777 tests), and so do core's static checks.

All options and trade-offs3 options · 741 words

Fix A is the recommended, validated fix. Fix B, the alternative site the adjudication named, was validated too. Option C is listed for completeness. All gradle runs were in scratch worktrees of 645d4fe14a20, removed afterwards.

A. EOF check in SlicedIndexInput.seekInternal (validated by the checks) (recommended)

#

Throw EOFException from SlicedIndexInput.seekInternal when pos > length, with the same check and message as NIOFSDirectory and RAFDirectory. seek(length) stays legal.

--- a/lucene/core/src/java/org/apache/lucene/store/BufferedIndexInput.java
+++ b/lucene/core/src/java/org/apache/lucene/store/BufferedIndexInput.java
@@ -420,7 +420,11 @@
     }
 
     @Override
-    protected void seekInternal(long pos) {}
+    protected void seekInternal(long pos) throws EOFException {
+      if (pos > length) {
+        throw new EOFException("read past EOF: pos=" + pos + " vs length=" + length + ": " + this);
+      }
+    }
 
     @Override
     public void close() throws IOException {

Trade-offs

  • Covers wrap(), the default slice(), clones and nested wraps (all SlicedIndexInput), skipBytes (through seek) and positional RandomAccessInput reads, which call seekInternal directly (BufferedIndexInput.java:239); far targets then get EOFException instead of IllegalArgumentException too (executed in a probe with this check shadowed: 0 accepted).
  • Cost: one comparison per seek outside the buffer, nothing per byte (the concern of #6890).
  • Does not help third-party subclasses whose own seekInternal is empty.
  • It throws from seekInternal, which BufferedIndexInput.seek calls after it has set bufferStart = pos and emptied the buffer (:330-332), so after the exception getFilePointer() reports the rejected target. IndexInput#seek allows that ("then the stream is in an undetermined state"), but callers must not keep using the input after catching it; fix B rejects before any state change.

B. EOF check in BufferedIndexInput.seek itself (validated by the checks)

#

Reject pos > length() in the out-of-buffer branch of BufferedIndexInput.seek, before any state changes.

--- a/lucene/core/src/java/org/apache/lucene/store/BufferedIndexInput.java
+++ b/lucene/core/src/java/org/apache/lucene/store/BufferedIndexInput.java
@@ -327,6 +327,10 @@
     if (pos >= bufferStart && pos < (bufferStart + buffer.limit()))
       buffer.position((int) (pos - bufferStart)); // seek within buffer
     else {
+      if (pos > length()) {
+        throw new EOFException(
+            "seek past EOF: pos=" + pos + " vs length=" + length() + ": " + this);
+      }
       bufferStart = pos;
       buffer.limit(0); // trigger refill() on read
       seekInternal(pos);

Trade-offs

  • Enforces the contract for every BufferedIndexInput subclass, including outside ones whose seekInternal is a no-op (the in-tree test helper FaultyIndexInput in TestFieldsReader has one; it overrides slice(), so it is not this class).
  • A behaviour change for all subclasses, not just this class; one virtual length() call per out-of-buffer seek; duplicates the checks NIOFSDirectory and RAFDirectory already make.
  • Positional reads call seekInternal without seek (:239) and keep today's behaviour: EOFException from refill(), but IllegalArgumentException for some targets more than 2^31 bytes past the end (code reading). A and B can be combined.

What the checks validated

  • Gradle, same worktree setup, seed DEADBEEF: the repro passes with assertions on and off.
  • Every core store test plus TestFieldsReader: 30 classes, 779 tests, 0 failures, 17 skipped; every misc store test (TestRAFDirectory, TestDirectIODirectory and three more): 5 classes, 244 tests, 0 failures, 6 skipped.
  • ./gradlew :lucene:core:check -x test with the fix and the repro: passes.

C. Keep the code, document the exception (not recommended)

#

State in the wrap() and default slice() javadoc that a seek past the end is detected only on the next read.

Trade-offs

  • No behaviour change, but it leaves IndexInputs that break their own interface's contract, which LUCENE-6932 removed elsewhere; the regression test would pin the lenient behaviour instead.

How it was found

#

Semi-formal: a differential harness ran every 1- and 2-operation sequence (144,211 sequences on files of 0, 7 and 65 bytes) on wrap() inputs against an independent reference model and the stock Directory inputs, comparing values, file pointers and exception classes. Every seek or skip past the end was accepted; code reading then found the empty seekInternal.

The method in full150 words
  • Method: bounded-exhaustive differential checking of the real jar against exact semantics (the hunt's semi-formal tier), in the hunt unit on store implementations. The harness ran every 1- and 2-operation sequence on BufferedIndexInput.wrap over a ByteBuffersDirectory input, on the top-level wrapper, its clones and its slices (144,211 sequences, 301,319 checks), against an independent reference model and the stock Directory inputs, comparing returned values, file pointers and exception classes.

History

#

The empty seekInternal came with wrap() and the default slice() in LUCENE-4371 (4.9.0, 2014). It became a contract violation in 5.5.0, when LUCENE-6932 promised EOFException on seek and fixed the other inputs. Executed on 17 releases from 5.5.0 to 10.6.0 and on main: all affected.

Versions tested9 rows

Code introduced by LUCENE-4371, "Replace IndexInputSlicer with IndexInput.slice" (Robert Muir; trunk 7aeac4f07b35, 2014-05-17; branch_4x backport 3c8d05ca0629, shipped in 4.9.0; issue #5437, no PR). It added wrap() and the default slice() and moved the empty seekInternal over from Directory.SlicedIndexInput (4.0.0 to 4.8.1). Became a contract violation with LUCENE-6932 (ddc65d977f92, 2016-01-21, #7990), first released in 5.5.0: 4.9.0 to 5.4.1 behave the same but had no contract (a stock RAMDirectory input also accepted the seek there). The skipBytes variant starts in 9.0.0, when LUCENE-9480 made skipBytes call seek. LFV-480, snapshot of 2026-11-08

Registry title
Inputs from BufferedIndexInput.wrap and the default BufferedIndexInput.slice accept seek and skipBytes past the end instead of throwing EOFException
Area
store / BufferedIndexInput.SlicedIndexInput (BufferedIndexInput.wrap and the default slice())
Priority
Low, rank 1171: A late EOFException on a seek past the end, with no in-tree producer on main and no wrong bytes ever returned; it is rare rather than contrived.
Impact class
minor
Impact note
Only code that seeks or skips past the end of an input made by the public static BufferedIndexInput.wrap (Apache Solr's blockcache CustomBufferedIndexInput, an IndexInput, calls it in its own slice(); read only), by the default slice() of a BufferedIndexInput subclass that does not override it (third-party subclasses), or, in releases 9.0 to 10.1.x, by an opt-in DirectIODirectory slice is affected, with no scale needed; on main no in-tree Directory produces such an input, the illegal seek succeeds and getFilePointer() then reports a position beyond length(), and the first read after it still fails (EOFException, or an unchecked IllegalArgumentException for some targets more than 2^31 bytes past the end), so the effect is a late error and no byte from outside the input was ever returned (executed).
Summary
You take 20 bytes of a file with BufferedIndexInput.wrap("w", in, 10, 20), or a slice of a BufferedIndexInput subclass that keeps the default slice(), call seek(21) or skipBytes(21), and expect the EOFException that IndexInput#seek promises for a position beyond the end and that the stock Directories' inputs and slices throw in normal use. Instead the call succeeds and getFilePointer() returns 21; only the next read throws EOFException. The cause is the empty SlicedIndexInput.seekInternal: BufferedIndexInput.seek hands every target outside its buffer to seekInternal, and only readInternal checks the slice's length.
Introduced
7aeac4f07b35d663009f946e07fb7bd3c90757a3 (trunk, svn r1595480) and its branch_4x backport 3c8d05ca062944b1a95b25a517a37d29f5ee21e9 (svn r1599274), which 4.9.0 shipped: LUCENE-4371 'Replace IndexInputSlicer with IndexInput.slice' (rmuir; JIRA and svn era, no PR; the issue is now apache/lucene#5437). It added the public static BufferedIndexInput.wrap and the default BufferedIndexInput.slice(), both returning the private SlicedIndexInput, whose empty 'protected void seekInternal(long pos) {}' it moved from Directory.SlicedIndexInput [read: git blame on main attributes the empty seekInternal and the slice() override to it; git log -S finds no other commit; exec: 4.8.1 cannot compile the probe because wrap() and IndexInput.slice do not exist, 4.9.0 accepts the seek]. The behaviour became a contract violation with ddc65d977f920013c5fca16c8ac75ae2c6895f9d (svn r1726039; branch_5x aa1a0cf3be8a), LUCENE-6932 (apache/lucene#7990), which wrote the IndexInput#seek EOFException sentence and fixed the RAM, NIOFS, SimpleFS and RAF inputs but not SlicedIndexInput [exec: the wrap and default-slice results are identical on 5.4.1 and 5.5.0; only the stock-directory controls change, from accepting the seek to throwing]. The deferred check itself is older: Directory.SlicedIndexInput (LUCENE-3218, 28f59a2e056, 4.0.0-4.8.1, executed on 4.8.1) and CompoundFileReader.CSIndexInput (1.4-3.0.0 tags) [read] (2014-05-17 (LUCENE-4371 on trunk; branch_4x backport 2014-06-02); 2016-01-21 (LUCENE-6932 wrote the contract it violates))
