Surround query parser keeps the escaping backslashes inside a quoted term, so "a\"b" searches for a\"b instead of a"b

In the surround query parser, the quoted term "a\"b" should mean a"b, but the parser keeps the escaping backslash and searches for a\"b. The document that holds a"b gets 0 hits, or a document that literally holds a\"b matches instead, with no error, in every release checked since 1.9.

The bug in 30 seconds

#

The surround parser (lucene/queryparser) treats "..." as one literal term. Its lexer allows two escapes inside the quotes, \" and \\, but the parser passes the text between the quotes to the term query without removing them.

  1. You index one untokenized value per document in field k: doc quote holds a"b, and doc raw-quote holds a\"b, the same text with a backslash in it.
  2. You search the surround query "a\"b". Inside quotes the parser accepts a backslash only as \" (a quote) or \\ (a backslash); its grammar says "escape quoted quote or backslash by backslash".
  3. You expect the term a"b: 1 hit, doc quote. The classic QueryParser decodes the same text to a"b.
  4. Instead the parser cuts off only the outer quotes, so it searches a\"b: doc raw-quote matches, doc quote does not, and without doc raw-quote you get 0 hits. Likewise "c:\\temp dir" searches c:\\temp dir, not the path c:\temp dir.
  5. No error, and no other surround spelling matches a"b exactly: a quote cannot appear in an unquoted term.

Who is affected

#

Applications that pass query text to the surround parser, including Solr's surround plugin, and need an exact term with a double quote, or a quoted term with a backslash (a value with a space or :, such as a Windows path). No setting is involved; it happens every time, at any index size. Rare: the parser is niche.

Mechanism, terms and numbers568 words

In the surround query language a term in double quotes is one literal term. Inside the quotes the lexer accepts a backslash only as \" or \\ and rejects a lone backslash, and the grammar comment on the token says "escape quoted quote or backslash by backslash". But the parser action for the token only removes the outer quotes, so SrndTermQuery searches the text with the escaping backslashes still in it: "a\"b" searches a\"b and "c:\\temp dir" searches c:\\temp dir. The intended term gets 0 hits, or a term that literally contains the backslashes matches instead; nothing throws. Since a quote cannot appear in an unquoted term and a lone backslash cannot appear inside quotes, no surround syntax matches such terms exactly. The classic and flexible parsers use a similar, broader quoted-token idiom and do remove the escapes. The token and its action date from the 2005 contribution and are semantically unchanged; every release checked from 1.9 to 10.5.2, and main, is affected. Unescaping in the parser and re-escaping in SrndTermQuery.toString fixes it and keeps parse(toString()) round-tripping.

How it happens

#
  1. Lexer (QueryParser.jj:223-228): the comment "Literal non empty term between single quotes, escape quoted quote or backslash by backslash." sits above the token <QUOTED: "\"" ( (~["\"", "\\"]) | ("\\" ["\\", "\""]))+ "\"">. Inside the quotes a character is anything except " and \, or a backslash followed by \ or ". A lone backslash, as in "p\q", is a ParseException.
  2. Parser action (QueryParser.jj:429-430, generated QueryParser.java:479-487): getTermQuery(term.image.substring(1, term.image.length()-1), true /* quoted */). Only the outer quotes are cut off; nothing removes the backslash of \" or \\.
  3. Query (SrndTermQuery.java:40-41, :50-61): getTermQuery builds new SrndTermQuery(text, true), which seeks exactly that text (seekCeil, :57). When the text is not in the index the query rewrites to MatchNoDocsQuery (SimpleTermRewriteQuery.java:48).

No other spelling

#
  • An unquoted term cannot contain " (_TERM_CHAR, QueryParser.jj:194-196), so a"b is a lexical error.
  • Unquoted, c:\temp dir is two terms and c: is the field operator: c:\temp parses as field c, term \temp.
  • The truncated form "c:\temp dir"* (TRUNCQUOTED, :227, no escapes) keeps backslashes as typed, but it is a prefix query and also matches longer terms. It cannot contain a quote ("a\"b"* is a lexical error), so for a term with a quote only a prefix that stops before the quote is left: "say "* matches say "hi", and every other term that starts with say .
  • ? can stand in for an inner quote (abc?def), but it also matches any other character, and it needs at least 3 other characters: a?b is rejected ("Too unrestrictive truncation").
  • An unquoted term with a backslash already works: a\b matches a\b.
Exposure and likelihood224 words

  • Which terms. An exact value that contains a double quote (12" pipe, say "hi", or a whitespace token that keeps its quotes), or a value with a backslash that also needs quotes because of a space, : or an operator character (c:\temp dir). Users are pointed to exactly this syntax: the one answer to Stack Overflow question 16935363 (2013, Solr 4.0) recommends "sec\"ond".

No setting is involved: a probe with a plain new IndexWriterConfig(), the default codec, a plain IndexSearcher and BasicQueryFactory (its 1024-clause limit still applies) gives the same wrong match; the compact repro runs under the test framework's randomized configuration. Only the parser is opt-in.
  • Always, silently. The term text is wrong before the index is touched, so it happens every time, with assertions on and off, at any scale: 0 hits, or hits on a different term that literally contains the backslashes. No exception.
  • Likelihood: rare. Such terms are unusual in fields searched with surround, and the only public trace the searches found in 21 years is the 2013 question.

Why it is a bug, not intended

#
  • The grammar says "escape quoted quote or backslash by backslash", and the lexer rejects a lone backslash: strong evidence that the escape is meant to be removed.
  • The classic and flexible parsers accept these escapes too and remove them; LUCENE-573 and LUCENE-1189 fixed quoted-escape bugs there.
  • No surround test puts an escape inside quotes; all 67 pass with the fix.
The full argument289 words
  • Grammar. QueryParser.jj:223-225: "Literal non empty term between single quotes, escape quoted quote or backslash by backslash. Evt. truncated." (it says single quotes, but the token uses double quotes). The token admits a backslash only as such an escape. With raw semantics "p\q" would be unambiguous, yet it is rejected, and requiring \\ would make every quoted single-backslash term impossible.
  • Docs and intent. The class javadoc lists "quoting (with ")" (QueryParser.java:27). The parser's author wrote on java-user on 2004-06-09 ("Syntax for query parsers"): "double quotes can be used to search for any single term". A term with a quote that is not preceded by a backslash, such as a"b, cannot be searched exactly today.
  • Sibling parsers. Classic QueryParser.jj:188, 207 define QUOTED with a similar, broader idiom (a backslash may escape any character, :182, and the body may be empty), and QueryParserBase.handleQuotedTerm calls discardEscapeChar on the inner text (QueryParserBase.java:809), documented as "Returns a String where the escape char has been removed, or kept only once if there was a double escape" (:834-840). The flexible StandardSyntaxParser.jj:831 does the same. Surround has the lexical half, restricted to \" and \\, without the decoding.
  • Precedent. LUCENE-573 ("Escaped quotes inside a phrase cause a ParseException", 2006) and LUCENE-1189 ("QueryParser does not correctly handle escaped characters within quoted strings", 2008) were fixed as bugs in the classic parser.
  • Tests and history. Test01Exceptions, Test02Boolean, Test03Distance and TestSrndQuery never put an escape inside quotes; with the fix all 67 pass. The token and its action are semantically unchanged since the 2005 contribution. No CHANGES or MIGRATE entry says the backslashes are meant to stay, and the searches found no issue or list thread that does.
The devil's-advocate check236 words

The cross-model reviews (refute and intended lens) built the strongest case for "intended" and rated it moderate; the devil's advocate built the same case and concluded that none of it survives. The case: surround can be read as raw, the text between the quotes being the term, with the backslash rule only keeping the token from ending early. Unquoted terms and the truncated form "..."* also keep backslashes as typed. Keeping the raw text makes parse(q).toString() round-trip exactly, which matters because surround query equality is toString() equality (LUCENE-2945). No complaint was found in 21 years, a fix changes what existing queries with \\ mean, and the protected getTermQuery(String, boolean) hook lets an application decode itself.

Why it fails: under the raw reading ordinary terms cannot be written exactly (a term with a quote that is not preceded by a backslash, such as a"b; a quoted term with one backslash, such as c:\temp dir), the lexer's rejection of a lone backslash would serve no evident purpose, and the grammar's "escape" comment would describe nothing. That is strong evidence, not proof. The round trip is kept by re-escaping in toString (the validated fix). Age without reports reflects how niche the parser is; the hook is a workaround, and the javadoc says parse() is the only method clients should need. Verdict: a defect. Upstream may still prefer to document raw semantics, but the impossible terms would remain.

Suggested fix

#

Recommended Unescape in the QUOTED action and re-escape in SrndTermQuery.toString

Remove the backslash of each \" and \\ in the parser's QUOTED action (a small unescapeQuoted helper in QueryParser.jj, then regenerate), and re-escape \ and " in SrndTermQuery.toStringUnquoted() for quoted terms, so parsed queries print and compare exactly as before. The repro and the whole lucene/queryparser suite pass.

   | term=<QUOTED>
-    {return getTermQuery(term.image.substring(1, term.image.length()-1), true /* quoted */);}
+    {return getTermQuery(unescapeQuoted(term.image.substring(1, term.image.length()-1)), true /* quoted */);}

   // SrndTermQuery.toStringUnquoted()
+    if (isQuoted()) {
+      return getTermText().replace("\\", "\\\\").replace("\"", "\\\"");
+    }
     return getTermText();

Unescape in the QUOTED action and re-escape in SrndTermQuery.toString (validated by the checks) (recommended)

#

In QueryParser.jj, a static unescapeQuoted(String) drops the backslash of each \" and \\ (the lexer guarantees that a backslash inside QUOTED is followed by one of the two), and the QUOTED action calls it; QueryParser.java and its checksum file are regenerated with ./gradlew :lucene:queryparser:regenerateSurroundQueryParser. In SrndTermQuery.toStringUnquoted(), a quoted term writes \ as \\ and " as \", so parse(q).toString() is unchanged and still parses back to an equal query.

   | term=<QUOTED>
-    {return getTermQuery(term.image.substring(1, term.image.length()-1), true /* quoted */);}
+    {return getTermQuery(unescapeQuoted(term.image.substring(1, term.image.length()-1)), true /* quoted */);}

   // SrndTermQuery.toStringUnquoted()
+    if (isQuoted()) {
+      return getTermText().replace("\\", "\\\\").replace("\"", "\\\"");
+    }
     return getTermText();

Trade-offs

  • Meaning change. "a\\b" then searches a\b instead of a\\b, and "a\"b" searches a"b. Worth a CHANGES line.
  • Hook input. Subclasses that override the protected getTermQuery(String, boolean) now receive the decoded text for quoted terms.
  • Direct construction. A SrndTermQuery built by hand with quoted=true and a backslash or quote in its text now prints with escapes, so its toString, equals and hashCode change: it equals a parsed query only when its text is the decoded form. What it matches does not change.
  • Truncated form left as is. TRUNCQUOTED ("..."*) has no escapes and keeps a lone backslash, so "a\\b" would mean a\b while "a\\b"* still means the prefix a\\b. Upstream can decide whether to give it the same escapes; that would turn today's "x\y z"* into a lexical error.
  • Tests to add upstream. By inspection, unescapeQuoted and the re-escaping are inverses on every body the QUOTED token accepts, but the round-trip guard runs only three strings: add adjacent and repeated escape pairs and directly constructed queries.

What the checks validated

  • Stock main a9779ef3c193, gradle in a clean worktree: the repro fails 2 of 4 with assertions on and with assertions off.
  • With the fix: the whole lucene/queryparser suite passes (31 classes, 537 tests, 0 failures, 1 skipped by an existing @Ignore), including the repro 4 of 4 and the four surround suites (67 tests); the repro also passes 4 of 4 with assertions off.
  • With the fix: checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain, forbiddenApisTest and regenerateSurroundQueryParserChecksumCheck pass; QueryParser.java was regenerated from the grammar by the project's own task.
  • Fix shadowed onto the stock jars: the finder's test 3 of 3 and the independent reproducer's 7 of 7 pass; the devil's advocate's 4 bug tests and its round-trip check pass, and only its info test that records today's behaviour flips, as expected.
  • Not run: a benchmark (the helper returns its input unchanged when it has no backslash).

Unescape in the QUOTED action only (the hunt's sketch)

#

One replaceAll on the text between the quotes. Fixes matching: the finder's, the reproducer's, both reviewers' and the devil's advocate's bug tests pass, and the 67 surround tests pass.

Trade-offs

Breaks the toString round trip, so query equality changes: the parsed query "a\"b" then prints as "a"b", which does not parse back (this repro's guard fails: expected:<"a[\]"b"> but was:<"a[]"b">). Not recommended alone.

Document raw semantics instead

#

Change the grammar comment and the javadoc to say that backslashes inside quotes are kept.

Trade-offs

No compatibility change, but a term with a quote that is not preceded by a backslash (a"b), or a quoted term with a single backslash (c:\temp dir), stays impossible to search exactly. Not explored: also accepting a lone backslash inside quotes (fixes "c:\temp dir", not a"b), or changing nothing and leaving it to the deprecation discussed in #16820.

Downstream note

#

Solr's surround query parser plugin hands user query text to this parser, so Solr users who quote a term with \" or \\ get the same wrong term (read in the Solr source, not executed).

How it was found

#

Code reading, not a formal tool. While writing the quoted-term renderer for a bounded-exhaustive differential harness of the surround parser, the finder noticed that the QUOTED token accepts escapes that the parser never removes; the harness itself passed for quoted terms without escapes. A probe on the stock jar and a public-API JUnit confirmed it.

The method in full132 words
  • Method: non-formal code reading. The hunt unit checked surround query parsing against a reference semantics with a bounded-exhaustive translation-validation harness. Its check passed for quoted terms without escapes, so the harness did not give the signal.
  • While writing the harness's renderer for quoted leaves, the finder read the lexer's QUOTED token, saw that it admits \" and \\, and found no code that removes them.
  • A probe on the stock main jar showed "a\"b", "a\\b" and "c:\\temp" rewriting to MatchNoDocsQuery (0 hits), while unquoted a\b matched and the classic parser decoded the same quoted escapes. A public-API JUnit followed (2026-10-27).
  • An independent reproducer, reviewers from another model family (OpenAI GPT-5.6) and an intended-behaviour devil's advocate then reproduced it with their own tests, and an adjudication confirmed it with new seeds.

LFV-687, snapshot of 2026-10-28

Registry title
Surround query parser keeps the escaping backslashes inside a quoted term, so "a\"b" searches for a\"b instead of a"b and "c:\\temp dir" searches for c:\\temp dir instead of c:\temp dir
Area
queryparser / surround (QueryParser.jj QUOTED token and SimpleTerm production, SrndTermQuery)
Priority
Medium, rank 308: It silently changes matches every time since 1.9 but needs the niche surround parser plus a quoted term with an escaped quote or backslash, so it joins the narrow deterministic silent rows after LFV-409 and above the ranking-only suggester row LFV-479.
Impact class
silent wrong results
Impact note
Hits applications that pass query text to the surround QueryParser (an opt-in, niche parser of the queryparser module; open issue #16820 proposes deprecating it) when a quoted term uses one of the two escapes the lexer accepts inside quotes, \" or \\: with the default IndexWriterConfig, codec and searcher, at any scale and with -ea or -da, the term is searched with its backslashes still in it, so the intended term (one that contains a double quote, or a quoted term that contains a backslash because it also needs quotes for a space, ':' or an operator character) gets 0 hits, or a document whose field holds the backslash-escaped text matches instead; nothing throws and the index is not touched.
Summary
You parse a surround query with a quoted term that escapes a double quote or a backslash, such as "a\"b" or "c:\\temp dir", and run it on a field that holds the untokenized value a"b or c:\temp dir. You expect a match, because the grammar comment on the QUOTED token says 'escape quoted quote or backslash by backslash' and the lexer accepts a backslash inside quotes only as such an escape. Instead the parser strips only the outer quotes, so SrndTermQuery searches for a\"b and c:\\temp dir with the backslashes kept: 0 hits, or a silent match on a different document that holds that escaped text, and no surround syntax matches those terms exactly.
