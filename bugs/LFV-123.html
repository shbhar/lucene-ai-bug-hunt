A kNN query's mergeLeafResults may return its hits in any order, but Lucene reads the first hit as the max score and the last as the lowest (k-th) score

The finding in 30 seconds

#

Lucene reads two scores from fixed positions of the merged hit list: the first hit as the maximum and the last as the lowest, the k-th best when k hits were collected. That is right only while the list is sorted by score, which the hook's javadoc does not require.

How a kNN query is rewritten

#
  1. A KnnFloatVectorQuery searches each segment's vector graph first. mergeLeafResults then merges the per-segment hits into the index-level top k. The default uses TopDocs.merge, which returns them sorted by descending score; subclasses may override it.
  2. The merged hits become a fixed query (DocAndScoreQuery) that returns each hit with its score and reports a maximum score, getMaxScore. That is an upper bound: top-score pruning, for example in a BooleanQuery disjunction, skips a clause whose bound cannot make a document competitive.
  3. Since 10.3.0 the search is optimistic: each segment first collects a share of k (38 of k = 50 for 10 equal segments), and a segment is searched again if its lowest hit reaches the merged list's lowest (k-th) score.

The finding, step by step

#
  1. You subclass KnnFloatVectorQuery and override mergeLeafResults to return the default merged hits sorted by doc id: same documents, same scores. Its javadoc says the result has "no constraint on their ordering".
  2. You index doc 0 at (0, 0) and doc 1 at (1, 0) and search (1, 0) with k = 2. The hits are doc 1 (score 1.0, the exact match) and doc 0 (score 0.5).
  3. You expect the rewritten query's scorer to report a maximum score (getMaxScore) of at least 1.0, the best score it returns.
  4. You get 0.5: Lucene takes the maximum from the first hit, now doc 0. Pruning trusts such bounds: over 200,001 documents the reordered kNN clause's bound is its first hit's score, doc 0's 0.0099, so the top-1 of kNN OR 0.5 x term is doc 0 (0.51) instead of the exact match, doc 200000 (1.0).
  5. From 10.3.0 Lucene also reads the last hit as the lowest (k-th best) score when it decides which segments to search again. On 10 segments with k = 50 it searches none again, and the 50 nearest include a far document, doc 16000. No error is raised.

Who is affected

#

Only applications that override the protected, experimental mergeLeafResults of KnnFloatVectorQuery or KnnByteVectorQuery and return hits not sorted by descending score, for example re-weighted without re-sorting. Stock queries are fine, and the five downstream overrides read all return sorted hits. Any index size; no error.

Mechanism, terms and numbers649 words

AbstractKnnVectorQuery#mergeLeafResults is a protected, @lucene.experimental hook on the public KnnFloatVectorQuery and KnnByteVectorQuery. Its javadoc says it returns "index-level kNN results (no constraint on their ordering)" and is "useful for reading and / or modifying the final results as needed". rewrite() passes its output unchanged to three readers that assume descending score order: DocAndScoreQuery.createDocAndScoreQuery takes the max score from the first hit, the optimistic re-entry pass (10.3.0 and later) and the no-match explainer take the lowest (k-th) score from the last. An override that returns exactly the default hits in another order therefore gets a rewritten query whose getMaxScore is below scores it returns (0.5 against 1.0 with 2 documents), so top-score pruning in a disjunction can skip the best kNN hit, and on a multi-segment index the second search pass is skipped and farther neighbours come back. Stock queries are not affected. Affected: 9.12.3 and 10.0.0 through 10.6.0, and main; sorting a copy of the hook's output in runSearchTasks fixes it.

The bug (main 645d4fe14a20)

#
  1. The hook promises freedom of order. mergeLeafResults says "@return index-level kNN results (no constraint on their ordering)" and "This method is useful for reading and / or modifying the final results as needed" (AbstractKnnVectorQuery.java:416-430). It is protected and @lucene.experimental, inherited by the public, non-final KnnFloatVectorQuery (KnnFloatVectorQuery.java:48), KnnByteVectorQuery (KnnByteVectorQuery.java:47) and, on main, KnnFloat16VectorQuery.
  2. rewrite() uses its output as is. runSearchTasks returns mergeLeafResults(...) unchanged (:227), for the first pass (:118) and the re-entry pass (:150).
  3. Max score from the first hit. DocAndScoreQuery.createDocAndScoreQuery does float maxScore = topK.scoreDocs[0].score; (DocAndScoreQuery.java:125) before sorting by doc id (:126), and the scorer's getMaxScore returns it (:238-241), while score() returns each hit's own score (:243-246). Scorer#getMaxScore must bound the scores of the documents in range (Scorer.java:75-79).
  4. Lowest (k-th) score from the last hit. The re-entry pass takes minTopKScore = topK.scoreDocs[topK.scoreDocs.length - 1].score (AbstractKnnVectorQuery.java:126) and searches a segment again only if its lowest hit reaches it (:136-137). The no-match explainer repeats the read, with the comment "topK is score-descending" (:160-166). A probe on the 10-segment shape below executed both: the stock query re-enters 1 segment and the override 0, and explain for doc 0 cites a minimum top-K score of 1.0 with the override against 4.1631973E-4 for the stock query.
  5. Pruning trusts the bound. Under TOP_SCORES a disjunction is scored by MaxScoreBulkScorer, which treats a clause as non-essential once the minimum competitive score exceeds its bound; the kNN-only best hit is then never scored.

The numbers

#
  • Minimal repro: 2 documents, doc 0 at (0, 0) and doc 1 at (1, 0), query (1, 0), k = 2, an override that returns the default hits sorted by doc id: getMaxScore 0.5, then score() 1.0 for doc 1.
  • Pruned disjunction: 200,001 documents, top-1 of SHOULD(kNN, k = 5) + SHOULD(0.5-boosted constant-score term), where doc 200000 is the query vector and has no term. In doc-id order the kNN clause's bound is doc 0's score, 1/101 = 0.0099 (the term clause's is 0.5), and the result is doc 0 (0.51) instead of doc 200000 (1.0). With a BM25 term clause over 20,000 documents and the default IndexSearcher#search(Query, int): doc 0 (0.32496786) instead of doc 19999 (1.0).
  • Re-entry (10.3.0 and later): 10 segments of 2,000 documents, k = 50, the nearest neighbours at the end of the last segment. The stock query returns exactly docs 19950-19999. In doc-id order the last hit is the exact match (score 1.0), so no segment is searched again (the stock query re-enters 1), and the result contains doc 16000 from segment 8 (distance 4000). An independent shape (10 x 150 documents, k = 50): 12 of the 50 hits come from other segments.

Every test ran the stock KnnFloatVectorQuery as a control, and it was correct.

Exposure and likelihood326 words
  • What goes wrong. Silent, lower-quality results, the same with assertions on and off. (1) The rewritten query breaks the Scorer#getMaxScore upper bound, so top-score pruning over it (a scored disjunction under TOP_SCORES, as the default IndexSearcher#search(Query, int) runs it) can skip the kNN clause's best hits. (2) From 10.3.0 a kNN query on its own, on a multi-segment index, can return farther neighbours because the second pass is skipped; whether it shows depends on where the neighbours sit. (3) On 10.6.0 and main, explanations of documents that were not collected cite a wrong minimum score (executed on main by a probe).
  • What the safety probe never saw. 10 runs, 9 random indexes with deletions, vectorless documents, kNN filters, FILTER and MUST_NOT clauses, and five overrides (four pure reorderings and one that re-weights the hits without re-sorting): no deleted, filtered, excluded or vectorless document was returned; for the pure reorderings no score was paired with the wrong document and no rewrite re-entered more segments than the stock query, which also follows from the code (the last entry of a reordering is never below the true minimum). An override that also lowers scores can re-enter more segments; that comes from the score change, not from the order.
  • Who is exposed. Subclasses of KnnFloatVectorQuery or KnnByteVectorQuery (also when wrapped in SeededKnnVectorQuery or PatienceKnnVectorQuery, which delegate the hook) whose mergeLeafResults returns hits not sorted by descending score: re-weighted or rescored without re-sorting (an override that multiplies each score by 1 + 3 x doc/N gave score 2.0 above getMaxScore 1.0), in doc-id order, or concatenated per segment (as an early revision of #12679 did).
  • Configuration and scale. Default codec, IndexWriterConfig and IndexSearcher. The bound break shows with 2 documents; the executed top-1 losses used 20,000 and 200,001 documents, enough for pruning to engage.
  • How likely. Rare. No in-tree query triggers it, and the five downstream overrides read (Elasticsearch, Solr, OpenSearch k-NN, mongot, nrtsearch) return sorted TopDocs.merge output.

Why it looks unintended

#
  • The hook's javadoc says it returns "index-level kNN results (no constraint on their ordering)" and invites "modifying the final results".
  • A pure reordering of the default hits (same documents, same scores) breaks Scorer#getMaxScore, an upper bound on returned scores.
  • The order-dependent reads predate the hook (#12146) or came later (#14226, #16271); no review discussed ordering.
The full argument194 words
  • The contract for overriders says the opposite (AbstractKnnVectorQuery.java:416-427). No javadoc, MIGRATE.md or CHANGES.txt entry asks overrides to sort.
  • The precondition that exists is for another caller. "The entries of topK are expected in descending score order" is on createDocAndScoreQuery (DocAndScoreQuery.java:109-111, #16686). Lucene makes that call with the override's output; the overrider never calls it, and the order-dependent reads inside rewrite() are undocumented implementation details.
  • Bound breaks are treated as bugs. #14857 "AbstractKnnVectorQuery breaks shallowAdvance contract, causing chaos" (fixed by #14858) and #16697 "Fix block-max support of DoubleValuesSource" (merged 2026-10-09: getMaxScore covered too little of the range).
  • History. The first-entry read (#12146, 2023-02) was correct when written, because the merge could not be overridden. #12590 (2023-10) made it overridable and documented the order as free without touching that read. The last-entry reads came later (#14226, #16271). No review comment on #12590, #12679, #14226, #16271, #16324 or #16686 discusses the hook's ordering.
  • The planned use was unordered. In the first revision of #12679 the hook's author overrode it to concatenate per-segment results: "Results of HNSW searches need not be sorted".
  • No test covers it. No upstream test overrides mergeLeafResults with unsorted output.
The devil's-advocate check203 words

The strongest case for "intended" (a devil's-advocate verifier, cross-model reviews and the adjudication built it): the hook is @lucene.experimental and custom queries are "an expert level task, so tread carefully" (package-info.java:388-390); in #12590 a reviewer (benwtrent) warned that "It would be very easy to do the wrong thing by allowing sub-classes to override this method for yet another avenue of customization"; every later change (#14226, #16271, #16686) treats the merged result as score-descending, so the 2023 sentence may be a stale doc; the default delegates to TopDocs.merge, whose javadoc says it returns the top hits "sorting by score" and requires sorted input (TopDocs.java:197-198), so score order is the default's convention; and no known deployment is affected.

Why it fails: experimental status allows incompatible API changes, not code that contradicts the API's own javadoc; the default's score order is a convention, but the hook's contract does not ask overrides to keep it and says the opposite; the warning was general and ordering was never raised; the later code never revisited the hook. It does make a javadoc change that requires descending order an acceptable resolution (option C), not "not a bug": today the documented contract and the code disagree.

Suggested fix

#

Recommended Sort a copy of the hook's output in runSearchTasks (recommended, validated)

Sort a copy of the hits mergeLeafResults returns by descending score (then doc id) in AbstractKnnVectorQuery.runSearchTasks, so all three readers see the order they assume (+10/-1, one file). Validated: the repro passes with assertions on and off, and so do 372 core and 39 join kNN tests and the lint checks.

TopDocs merged = mergeLeafResults(perLeafResults.values().toArray(TopDocs[]::new));
// mergeLeafResults may return its hits in any order, but the re-entry pass in rewrite(), the
// no-match explainer and DocAndScoreQuery (max score) read them as score-descending
ScoreDoc[] hits = merged.scoreDocs.clone();
Arrays.sort(
    hits,
    (a, b) ->
        a.score != b.score ? Float.compare(b.score, a.score) : Integer.compare(a.doc, b.doc));
return new TopDocs(merged.totalHits, hits);

Sort a copy of the hook's output in runSearchTasks (recommended, validated)

#

Where rewrite() receives the hook's output, sort a copy by descending score, then ascending doc id. The override's hits and scores are kept; only their order changes, and createDocAndScoreQuery re-sorts by doc id anyway.

TopDocs merged = mergeLeafResults(perLeafResults.values().toArray(TopDocs[]::new));
// mergeLeafResults may return its hits in any order, but the re-entry pass in rewrite(), the
// no-match explainer and DocAndScoreQuery (max score) read them as score-descending
ScoreDoc[] hits = merged.scoreDocs.clone();
Arrays.sort(
    hits,
    (a, b) ->
        a.score != b.score ? Float.compare(b.score, a.score) : Integer.compare(a.doc, b.doc));
return new TopDocs(merged.totalHits, hits);

Trade-offs

  • Coverage. Fixes the max-score, re-entry and explainer reads, and any later reader in rewrite(), at the one place where the order became free.
  • Cost. One copy of the ScoreDoc[] and an O(k log k) sort of the merged hits per pass (not benchmarked); the default output is already sorted, so an O(k) check could skip the copy.
  • Stock results unchanged. TopDocs.merge orders by descending score, then shard index (-1 for these hits), then doc id (TopDocs.java:44-45), the same order as the sort (read).
  • Aliasing. Today createDocAndScoreQuery sorts the override's own array by doc id in place; with the fix it sorts the copy, so an override that keeps a reference to the array it returned no longer sees it reordered.
  • Scope. It does not harden the public createDocAndScoreQuery for other callers that pass unsorted hits (see the scan option).
  • Score-changing overrides. The min and max reads become consistent, but the re-entry pass then compares the override's lowest score with raw per-segment scores; the sort does not make such overrides fully consistent.

Scan for the min and max instead of reading positions (validated)

#

A private minScore(TopDocs) scan for the re-entry pass (AbstractKnnVectorQuery.java:126) and the explainer (:163), and a max scan in createDocAndScoreQuery (DocAndScoreQuery.java:125), whose javadoc then says the entries "may be in any order" (+19/-7, two files).

float maxScore = Float.NEGATIVE_INFINITY; // DocAndScoreQuery.createDocAndScoreQuery
for (ScoreDoc scoreDoc : topK.scoreDocs) {
  maxScore = Math.max(maxScore, scoreDoc.score);
}

Trade-offs

No reordering, and it also relaxes the public createDocAndScoreQuery precondition, so any caller may pass hits in any order (that also covers RescoreTopNQuery, a separate case found earlier that reaches the same line with heap-ordered hits). It touches three sites, and a future reader in rewrite() must remember to scan. Same score-changing caveat as the sort.

What the checks validated

Gradle on 645d4fe14a20: the same core and join test selection, 372 + 39 tests, 0 failures; checkGoogleJavaFormat and ecjLintMain pass; the finder's two end-to-end tests pass with it on the main jars.

Document that overrides must return descending score order (not built)

#

Change the @return line of mergeLeafResults to require hits sorted by descending score, in line with #16686 and the explainer comment; optionally assert the order in runSearchTasks.

Trade-offs

No runtime change and consistent with the later code, but it changes the contract under existing overrides that followed the current javadoc, an assertion fires only with assertions on, and an override that misses the note still gets silently wrong results. Reasonable as a companion to a code fix, weaker alone.

Downstream note

#

Downstream products that subclass a kNN query to re-rank or re-weight the merged hits must, until this is fixed, return them sorted by descending score or silently lose top hits; the overrides read in Elasticsearch, OpenSearch k-NN, Solr, mongot and nrtsearch already do.

How it was found

#

Code reading. While writing the merge step of a TLA+ model of the kNN rewrite, which treats the merged hits as a set and so could not show this, the finder compared rewrite() with the mergeLeafResults javadoc, saw the first- and last-hit reads, and confirmed the effect with a public-API JUnit on the stock jars.

The method in full137 words

Method: non-formal (code reading, then public-API JUnit tests).

  • A hunt unit on the kNN query layer was modelling AbstractKnnVectorQuery.rewrite in TLA+ (KnnRewrite.tla). Its merge step is a set (the top k of the union), so the model cannot see an ordering defect.

LFV-123, snapshot of 2026-11-09

Registry title
AbstractKnnVectorQuery#mergeLeafResults is documented to return hits in any order, but rewrite() reads the k-th score from the last entry and DocAndScoreQuery the max score from the first, so an override that only reorders the hits changes the results
Area
search / kNN query rewrite (AbstractKnnVectorQuery#mergeLeafResults extension point, optimistic re-entry pass) and DocAndScoreQuery max score
Priority
Low, rank 897: A mergeLeafResults override that returns unsorted hits, which the javadoc allows, silently breaks max-score and re-entry results, but no in-tree code or known downstream override does that.
Impact class
silent wrong results
Impact note
Only applications that subclass KnnFloatVectorQuery or KnnByteVectorQuery (directly, or wrapped in SeededKnnVectorQuery or PatienceKnnVectorQuery, which delegate the hook) and override the protected, @lucene.experimental mergeLeafResults so that it returns hits not sorted by descending score, for example by re-weighting the merged hits without re-sorting them, which its javadoc permits: the rewritten query's getMaxScore then under-reports its own scores (a Scorer contract break), so a top-k disjunction pruned under TOP_SCORES drops the true best kNN hit (since 9.12.3 and 10.0.0), and from 10.3.0 the optimistic multi-segment re-entry reads the wrong k-th score, so even a stand-alone kNN query on a multi-segment index returns farther neighbours; no in-tree query triggers it, and the five downstream overrides read (Elasticsearch, Solr, OpenSearch k-NN, mongot, nrtsearch) all return sorted output; ordinary scale, default codec and searcher, no error, the same under -ea and -da.
Summary
You subclass KnnFloatVectorQuery and override mergeLeafResults, whose javadoc says it returns 'index-level kNN results (no constraint on their ordering)' and is 'useful for reading and / or modifying the final results', so that it returns exactly the default merge's hits in another order (same documents, same scores). You expect the same search results as the stock query. Instead rewrite() takes the k-th score from the last entry and DocAndScoreQuery the max score from the first, so with doc-id order a top-1 search for the kNN query OR a 0.5-boosted term returns doc 0 (score 0.51) instead of the exact match, doc 200000 (score 1.0), and on a 10-segment index the k = 50 query re-enters no segment and returns farther documents (first differing doc 16000 instead of 19950).
