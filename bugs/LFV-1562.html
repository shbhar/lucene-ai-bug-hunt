The finding in 30 seconds

#

In the one real read fault that was run (staged: a file truncated by the program during the scan), the default MMapDirectory closed the writer with no loss; NIOFSDirectory gave the outcome. A Lucene maintainer wrote on #9738 in 2019 that going on after a failed reopen can end in inconsistency or data loss: a statement about that practice, not a report of this defect.

Background: three pieces

#
  1. With IndexWriterConfig.setSoftDeletesField("soft"), a document counts as deleted once it has a value in the doc-values field soft. A commit stores two numbers per segment: delCount (hard-deleted documents) and softDelCount (soft-deleted ones).
  2. IndexWriter can keep one pooled reader per segment. When it first opens that reader it scans the soft-deletes field and clears the bit of each soft-deleted document in its own live-docs bit set.
  3. A hard delete (deleteDocuments, or the delete half of updateDocument) of a document that is already soft-deleted, and not yet hard-deleted, must not raise the segment's total: the writer adds one hard delete and, because the bit is already clear, takes one soft delete away.

The finding, step by step

#
  1. Turn soft deletes on: new IndexWriterConfig().setSoftDeletesField("soft") (opt-in; the default is off). Index document 1 and document 2 with softUpdateDocument, soft-delete document 1 with updateDocValues, close. The commit has one segment with 2 documents, 1 of them soft-deleted (softDelCount 1, delCount 0).
  2. Open a new writer (the test sets NoMergePolicy) and call DirectoryReader.open(writer). In the test a wrapping Directory makes a read fail with an IOException while the writer scans the segment's soft deletes. The open throws; getTragicException() is null and the writer stays open.
  3. Go on with the same writer: deleteDocuments(new Term("id", "1")), then commit(). Document 1 was already soft-deleted, so you expect the commit to hold document 2: 1 document.
  4. With assertions off, both calls return and the commit has 0 documents. The scan was left undone and the reader kept, so the delete of document 1 is counted on top of its soft delete: 1 + 1 = 2, the segment's 2 documents, and the writer drops the segment, document 2 with it. With assertions on, commit() instead throws Lucene's own AssertionError: softDeleteCount doesn't match 1 != 0, the writer closes and the previous commit stays: no loss.
  5. rollback() after the failed open, then a new writer: the same delete and commit keep document 2 (run). In another run (2 documents, both deleted by id after the failed open, assertions off) commit() returns and the new commit cannot be read back: CorruptIndexException: invalid deletion count: 3 vs maxDoc=2.

Who is affected

#

In the runs the double count took: soft deletes over a Directory whose reads can throw an exception and then work again; such a failure inside this scan (staged in each run), in the test's index at an open with no delete or update buffered; a writer kept in use; a delete or update by id of a document already soft-deleted in that segment, with no successful near-real-time open, flush or commit in between.

Mechanism, terms and numbers2,194 words

The limits first. Soft deletes are opt-in (IndexWriterConfig.setSoftDeletesField). The read error was injected in each run, at one point: inside the writer's first soft-deletes scan of a segment, which the test reaches through a near-real-time open (DirectoryReader.open(writer)). It has to be transient: in the runs it was gone again before the delete call, and where it stayed on through the delete and the commit, commit() threw it and the writer closed with the last commit intact. In the one real read fault that was run (a file truncated by the program during the scan), the default MMapDirectory closed the writer with no loss and NIOFSDirectory gave the outcome. In runs of 2026-11-20 in the test's index the writer stayed open after the failed open when nothing was buffered in it at that open, or only a document added with addDocument; with a delete by term or by query, a soft delete, a doc-values update of another field (in the same index with one more doc-values field), or an updateDocument or softUpdateDocument call buffered, the same read failed while the writer was applying the buffered deletes and updates inside the open, and the writer recorded the exception as tragic and closed with the last commit unchanged (branch_11x 3221dd4cf3a1, main 7b8418faa2ff and the 10.6.0 release jars, assertions on and off). In the runs with a delete counted twice the application went on using the writer after the call that failed (the open, in the test) and then deleted or updated by id a document that is already soft-deleted in that segment, with no successful near-real-time open, flush() or commit() in between (in the three controls with one in between the commit was right); rollback() after the failed open restores the last commit. With assertions on, Lucene's own assert stops the commit and closes the writer with the previous commit intact. With assertions off the commit drops the segment only when the double count reaches the segment's maxDoc, as it does in the test (2 documents in one segment, NoMergePolicy), where the delete, the commit and the close of the writer then return normally. In the test's shape the loss also needs the read to fail before the scan has cleared the bit of the document that is deleted later: of the scan's 18 single-byte reads, a failure of one of the first 12 gives the loss and a failure of one of the last 6 the right commit (a run on main f2b061406c4b, assertions off).

You use soft deletes. A near-real-time open, DirectoryReader.open(writer), called with no delete or update buffered in the writer, throws an IOException from a read; the writer stays open and reports no tragic exception, so you go on: you delete by id a document that is already soft-deleted in that segment (or has an older, soft-deleted version there), and commit. You expect the commit to lose only that document. Instead the deletion can be counted twice, because the read failed while the writer was scanning the segment's soft deletes and the writer kept the segment reader with the scan undone: ReadersAndUpdates.getReader stores the new reader (ReadersAndUpdates.java:191, lines at main f2b061406c4b) before pendingDeletes.onNewReader returns (:192), and nothing undoes that when the call throws. In the test (2 documents in one segment, NoMergePolicy, assertions off) the writer takes the segment for fully deleted and drops it, so the other document, which no call deleted, is missing from the commit, and no later call threw: deleteDocuments, commit() and close() returned. With assertions on, commit() stops at Lucene's own assert (softDeleteCount doesn't match 1 != 0), the writer closes and the previous commit stays.

The other outcomes that were run. With 2 documents and both deleted by id after the failed open (assertions off), commit() returns and the new commit cannot be read back (CorruptIndexException: invalid deletion count: 3 vs maxDoc=2). With 3 documents and one delete the count stays below maxDoc: no document is lost, but the commit stores the deletion twice. With no delete at all (runs of 2026-11-20 on branch_11x 3221dd4cf3a1, main 7b8418faa2ff and the 10.6.0 release jars): when a merge policy that selects merges without asking the writer for a segment's delete count merged the segment, with no flush(), commit() or successful open after the failed open, the merged segment was wrong. With assertions off the merge and the next commit returned normally: in the one test of it the commit had two documents and no recorded deletion, and a reader that filters soft deletes saw one document where two are live. With assertions on Lucene's assert stopped the merge, and the writer closed with the previous commit unchanged. The wrong segment was written under TemporalMergePolicy and under LogByteSizeMergePolicy and LogDocMergePolicy with setCalibrateSizeByDeletes(false); under TieredMergePolicy (the default policy, here with two segments per tier) the merged segment was right. The wrong merges are in the impact note of the finding record.

That going on with a writer after a failed reopen can end in inconsistency or data loss was said by Simon Willnauer on #9738 in 2019 ("if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss"): a statement about that practice, without this mechanism, and not a report of this defect. The sequence fails on the releases 7.4.0 to 10.6.0 that were run (9: the test of this page on three of them, a second test or a copy for the older API on the others) and on the builds of branch_11x and main that were run. One change was validated through Lucene's own build: keep the reader only when the scan returned.

Why it looks unintended

#
  • The javadoc of DirectoryReader.open(IndexWriter) (tagged experimental) mentions no rollback after an IOException, and the writer reports no tragic exception.
  • Lucene's own assert rejects the count, and a sibling method guards the same call.
  • A maintainer's 2019 statement on #9738 (going on after a failed reopen can end in inconsistency or data loss) names no mechanism; nothing was decided there.
The full argument537 words
  • Contract. IndexWriterConfig.setSoftDeletesField: "If soft-deletes are enabled, documents can still be hard-deleted. Hard-deleted documents won't be considered as soft-deleted even if they have a value in the soft-deletes field." (IndexWriterConfig.java:561-563). deleteDocuments(Term...): "Deletes the document(s) containing any of the terms." (IndexWriter.java:1855-1857). The class javadoc of IndexWriter: "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself. This is a defensive measure in case any internal state (buffered documents, deletions, reference counts) were corrupted." (:164-167).
  • None of the three javadocs asks for a rollback here. About exceptions, the javadoc of DirectoryReader.open(IndexWriter) has two lines, "@throws CorruptIndexException if the index is corrupt" and "@throws IOException if there is a low-level IO error" (DirectoryReader.java:112-121), and that of IndexWriter.getReader has one, "@throws IOException If there is a low-level I/O error" (IndexWriter.java:476-516). Neither says what state the writer is in afterwards, and neither they nor the javadoc of rollback() (:2566-2574) tie a rollback to a failed near-real-time open.
  • The API is tagged experimental. Both javadocs carry @lucene.experimental (DirectoryReader.java:120, IndexWriter.java:512; the text of getReader says "As this is a new and experimental feature", :490). The devil's-advocate check289 words

The strongest case for "intended": on the open #9738 (LUCENE-8692; its subject is which exceptions getTragicException() reflects), Simon Willnauer, who wrote the two statements of getReader, said on 2019-03-06 that getReader() and six other IndexWriter methods "might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback() to go back the the last known safe-point / previous commit", and on 2019-03-11: "if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss. I can't think of a reason why you would want to do it." Read as a design statement: these failures were left non-tragic on purpose, and after a failed reopen the application is expected to roll back.

What speaks against reading this outcome as intended: the same comment of 2019-03-06 says "I am all for making it even more strict"; nothing was decided there (the issue is open with the label type:bug, its last comment is of 2019-03-12, and no javadoc states the obligation); the comments name no mechanism, no soft deletes and no reader-pool state; and here the lost document is not the failed call's own work but a committed document that a later, successful call on another document removes. What stays true: the class of weakness and the rollback remedy are theirs, said in public in 2019, and rollback() does restore the last commit here (run). Whether this instance is intended is the maintainers' call. A maintainer may answer "roll back after a failed reopen", which leaves the code as it is (at most a javadoc sentence, the third option under Suggested fix), or "make this failure tragic", the second option there.

How it was found

Reading the code for ways to break it led to the reader kept after its soft-deletes scan threw. A public-API program showed it; it was reduced to one test.

Method: semi-formal (a proof-obligation audit witnessed by an executable test; by a strict reading that counts code reading plus a test as testing, it would be non-formal). No model-checking, SMT or proof tool was involved.

Area
index / IndexWriter reader pool and soft-deletes accounting (ReadersAndUpdates.getReader, PendingSoftDeletes)
Priority
Low, rank 353: With a soft-deletes field, an IOException from a read inside the writer's first soft-deletes scan of a segment (injected during a near-real-time open with no delete or update buffered) leaves IndexWriter open, and a later delete by id of an already soft-deleted document can be counted twice, so the next commit can drop a segment with a live document or store counts that cannot be read back, with no exception when assertions are off (run on nine releases from 7.4.0 to 10.6.0 and on builds of main and branch_11x, both unreleased). Summary
You use soft deletes (IndexWriterConfig.setSoftDeletesField). A near-real-time open, DirectoryReader.open(writer), called with no delete or update buffered in the writer, throws an IOException from a read; the writer stays open and reports no tragic exception, so you go on: you delete by id a document that is already soft-deleted in that segment (or has an older, soft-deleted version there), and commit. You expect the commit to lose only that document. Instead the deletion can be counted twice, because the read failed while the writer was scanning the segment's soft deletes and the writer kept the segment reader with the scan undone: in the test (2 documents in one segment, NoMergePolicy, assertions off) the writer takes the segment for fully deleted and drops it, so the other document, which no call deleted, is missing from the commit and no later call threw; with assertions on, commit() stops at Lucene's own assert ('softDeleteCount doesn't match 1 != 0'), the writer closes and the previous commit stays. rollback() after the failed open avoids it. That going on with a writer after a failed reopen can end in inconsistency or data loss was said by Simon Willnauer on #9738 in 2019, without this mechanism.
