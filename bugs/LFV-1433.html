SingleTermsEnum's constructor javadoc says the new enum already points to the term; it is unpositioned until next()

SingleTermsEnum's constructor javadoc says the new enum "is already pointing to the term", but like every TermsEnum it is unpositioned until the first next(). Read at once over a fresh terms.iterator(), it gives an empty term and, with assertions off, docFreq() 0 and no postings for a term that exists; only the sentence is wrong.

The finding in 30 seconds

#

The constructor only stores the term to seek. FilteredTermsEnum moves the wrapped enum on the first next(), so until then term(), docFreq() and postings() show the wrapped enum's unpositioned state, or the term it was on before. The constructor's javadoc promises the opposite.

Background: where a TermsEnum starts

#
  1. A TermsEnum walks a field's terms in sorted order. It starts unpositioned: you call next() (or a seek method) before reading term(), docFreq() or postings().
  2. FilteredTermsEnum wraps another TermsEnum and lets only some terms through. It cannot seek, so next() is the only way to move it.
  3. SingleTermsEnum is the filter for exactly one term. FuzzyQuery with maxEdits 0 and single-term automata use it.

The finding, step by step

#
  1. You index one document whose field f holds the term b, then build new SingleTermsEnum(terms.iterator(), new BytesRef("b")), for example inside a custom MultiTermQuery.
  2. The constructor javadoc says: "After calling the constructor the enumeration is already pointing to the term, if it exists." So you call term() at once and expect b.
  3. You get an empty term: expected:<[62]> but was:<[]>, with assertions on and off. In a 3-document index where b is in 2 documents, docFreq() is 0 and the postings are empty (assertions off), so the term looks absent.
  4. Why: the constructor only remembers b; the enum seeks to it inside the first next(), which then returns b with docFreq() 2. That lazy start is the intended TermsEnum design; the sentence is a leftover from a pre-4.0 class that did position itself in its constructor.

Who is affected

#

Only code that builds SingleTermsEnum itself and reads it before next(), as the javadoc invites (for example a custom MultiTermQuery). No Lucene code path does, and no use was found in Elasticsearch, OpenSearch or Solr. Default codec, any index that holds the term, every release since 4.0.0-alpha; silent with assertions off.

Mechanism, terms and numbers549 words

SingleTermsEnum is a public FilteredTermsEnum that enumerates exactly one term, for MultiTermQuerys that need only one. Its constructor javadoc says: "After calling the constructor the enumeration is already pointing to the term, if it exists." (SingleTermsEnum.java:34).

The constructor only calls setInitialSeekTerm(termText) (:36-40). FilteredTermsEnum seeks the wrapped enum inside the first next() (FilteredTermsEnum.java:223-241), and term(), docFreq() and postings() simply return the wrapped enum's values (:135-137, :140-142, :195-197). So right after the constructor over a fresh terms.iterator() (default codec), term() is an empty BytesRef; with assertions off docFreq() is 0 and the postings are empty; with assertions on those two trip an internal assertion of the terms dictionary. If the wrapped enum was already on another term, the new enum reports that term. The first next() returns the term and the second null, so iteration is correct. These values are off-contract (TermsEnum.java:118, :128-131, :140-170: do not call these methods while the enum is unpositioned), so another codec may give different ones.

The lazy start is the documented design (TermsEnum.java:34-35: "The TermsEnum is unpositioned when you first obtain it"; LUCENE-2110, #3186). The sentence was written for the pre-4.0 SingleTermEnum, whose constructor did position itself, and was kept when the class became lazy. The fix is one javadoc sentence; no code changes.

What a caller sees (executed probe, not the repro)

#

Index with terms a (1 document) and b (2 documents), default codec, new SingleTermsEnum(terms.iterator(), new BytesRef("b")):

  • before next(): term() = ''; assertions off: docFreq() = 0, postings().nextDoc() = NO_MORE_DOCS; assertions on: both throw an internal AssertionError;

The repro pins the default codec. With the codec left random, the test framework's asserting terms enum reports "term() called on unpositioned TermsEnum" instead for some seeds (when field f gets the asserting postings format, assertions on); for most seeds the failure is the same empty term: 2 of 40 seeds run on main with assertions on gave the asserting message, the other 38 expected:<[62]> but was:<[]>. Why it looks unintended

#
  • The constructor javadoc says it outright: "already pointing to the term, if it exists" (SingleTermsEnum.java:34).
  • The sentence was true for the pre-4.0 SingleTermEnum, which positioned itself in its constructor; LUCENE-2110 (#3186) made the enum lazy on purpose and kept the sentence.
  • So the fix is javadoc only: the lazy start is the documented TermsEnum contract (TermsEnum.java:34-35).
The full argument110 words
  • Contract. The sentence is the most specific statement about the state after this constructor, and it is unconditional.
  • History. Written 2009-10-08 (b98e0976b0e, LUCENE-1951) for the eager SingleTermEnum, when it was true. LUCENE-2110 (#3186, flex branch, 2009-12-06) made FilteredTermsEnum unpositioned until next() ("should instead work like an uninitialized TermsEnum") and changed this constructor to setInitialSeekTerm, keeping the sentence. It reached main with the flex merge (b679816a700, 2010-04-06); later commits moved the file and reformatted it (2d6ad2fee6d, 2020), none changed the sentence.
  • What the code intends (and the fix keeps): TermsEnum.java:34-35, FilteredTermsEnum.java:93-111, and #3858 (LUCENE-2784: "TermsEnum must be unpositioned initially before next()").
The devil's-advocate check105 words

The case: TermsEnum's class javadoc says every enum starts unpositioned; the accessors say "do not call this when the enum is unpositioned"; codec and test-framework assertions enforce it; every caller calls next() first; and no report of the sentence since 4.0 was found, so it is a trivial nit.

Why it fails: all of that defends the code, which stays as it is, not the sentence. A constructor javadoc that explicitly says the opposite of the general rule reads as a documented exception, and a reader who trusts it gets silent wrong results with assertions off. Every reviewer agreed: real, with a javadoc-only fix.

A: say what the code does (validated) (recommended)

#

Javadoc only, lucene/core/src/java/org/apache/lucene/index/SingleTermsEnum.java:34.

    * Creates a new <code>SingleTermsEnum</code>.
    *
-   * <p>After calling the constructor the enumeration is already pointing to the term, if it exists.
+   * <p>Like any {@link TermsEnum}, the new enumeration is unpositioned: call {@link #next()} to
+   * position it on the term, if it exists; {@link #next()} returns {@code null} otherwise.

Trade-offs

None for users; no behaviour changes. The new sentence is true: accept returns YES only for the exact term and END otherwise (SingleTermsEnum.java:42-45), so next() returns the term or null. That holds for a wrapped enum that can seek, such as terms.iterator() or a doc-values termsEnum(), which every in-tree construction passes; if the wrapped enum cannot seek (for example another FilteredTermsEnum, FilteredTermsEnum.java:175-177), the first next() throws UnsupportedOperationException from tenum.seekCeil(t) (:236), as for every FilteredTermsEnum that starts with a seek. To say so, begin the sentence with "When wrapping a seekable enum such as Terms.iterator()" (not validated separately). {@link #next()} renders as FilteredTermsEnum.next() because the method is inherited; {@link #next() next()} would print just next().

Remove SingleTermsEnum.java:34; the constructor then inherits TermsEnum's class contract silently.

Trade-offs

Smallest change and removes the false promise, but gives a reader of this constructor no hint about next(). Not run separately (a subset of A).

C (rejected): make the constructor position the enum

Trade-offs

Contradicts TermsEnum.java:34-35 and the deliberate LUCENE-2110 design; FilteredTermsEnum would have to make its first next() return the current term, and every in-tree caller already calls next() first. The behaviour is right; the documentation is not.
