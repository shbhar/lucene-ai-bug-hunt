BlendedTermQuery's dis-max rewrite, the LatLon distance feature query and the XY distance sort treat 0.0 and -0.0 as equal but give them different hash codes

Three core objects (a BlendedTermQuery with DisjunctionMaxRewrite, LatLonPoint.newDistanceFeatureQuery and XYDocValuesField.newDistanceSort) say that one built with 0.0 equals one built with -0.0, yet hash the two differently. A HashSet or HashMap then treats one object as two; hits, scores and sort order stay the same.

The finding in 30 seconds

#

Each class compares a float or double parameter with == in equals (0.0 == -0.0 is true) but hashes its bit pattern in hashCode (0x00000000 versus 0x80000000). This row covers three sites in core: the DisjunctionMaxRewrite tie-breaker, the distance feature query's origin latitude and longitude, and the XY distance sort's x and y.

Background: two zeros, and how hash lookups work

#
  1. Java's float and double have two zeros, 0.0 and -0.0. 0.0 == -0.0 is true, but their bit patterns differ in the sign bit: 0x00000000 and 0x80000000.
  2. A HashSet or HashMap first compares hash codes and calls equals() only when they match. So equal objects must have equal hash codes; otherwise the lookup never reaches equals and misses.

The finding, step by step

#
  1. Build a distance boost twice: a = LatLonPoint.newDistanceFeatureQuery("p", 1f, 0.0, 0.0, 1000.0) and b, the same with origin latitude -0.0 (rounding -0.001 to two decimals gives -0.0). Both are accepted: -0.0 is a valid latitude.
  2. a.equals(b) is true: equals compares the latitudes with ==, and in Java 0.0 == -0.0.
  3. You expect equal hash codes: Java requires them for equal objects, and Query's javadoc asks for them so that the query cache works.
  4. Instead hashCode hashes the double's bits, which differ in the sign bit: 280779518 versus -1866704130, exactly 2^31 apart. A HashSet holding a does not find b, and a BooleanQuery around a is not equal to the same one around b.
  5. The same happens with the DisjunctionMaxRewrite tie-breaker (0f vs -0f) and with the XY distance sort's x or y. The two zeros give identical hits, scores and order; only hash-based lookups go wrong.

Who is affected

#

Applications that build one of these objects with 0.0 and again with -0.0 (a rounded or negated zero, a parsed "-0") and rely on hashing: their own hash sets, maps or caches, BooleanQuery equality, or Sort hashes. Default configuration, any size, every release since 5.3.0. The cost is a hash miss or a duplicate entry; contrived, so Low.

Mechanism, terms and numbers541 words

Three classes in lucene/core compare a float or double parameter with == in equals but hash its bit pattern in hashCode: BlendedTermQuery.DisjunctionMaxRewrite (the tie-breaker; BlendedTermQuery.java:180 versus :185, and BlendedTermQuery.equals/hashCode delegate to it), LatLonPointDistanceFeatureQuery, built by LatLonPoint.newDistanceFeatureQuery (origin latitude and longitude; LatLonPointDistanceFeatureQuery.java:78-79 versus :87-88), and XYPointSortField, built by XYDocValuesField.newDistanceSort (x and y; XYPointSortField.java:65 versus :52, :54).

In Java 0.0 == -0.0 is true, but the bits differ in the sign bit (0x00000000 versus 0x80000000). So an object built with 0.0 and one built with -0.0 are equal but have different hash codes, which breaks the Object.hashCode contract, which Query's javadoc also asks of the two queries "so that QueryCache works properly" (Query.java:95-116). Every public entry point accepts -0.0. Hash sets and maps miss and can hold both, a BooleanQuery holding one is not equal to one holding the other, and two Sorts over the two sort fields are equal but hash differently. No hit, count, score or sort-order change was shown, and none of these objects becomes a key of Lucene's own query cache.

Each site has been wrong since the commit that created it: every release since 5.3.0 (the LatLon site since 8.0.0, the XY site since 8.5.0), through 10.6.0 and main 5adff78bb168. A one-test JUnit reproduces all three sites; comparing with Float.compare / Double.compare in equals, as #13301 did for five geo classes, fixes it.

Related rows (same defect shape, other fix sites, not duplicates): LFV-1335 (queries module value sources and CommonTermsQuery), LFV-1341 (spatial3d), LFV-1236 (DisjunctionMaxQuery), LFV-1299 (PatienceKnnVectorQuery) and LFV-1165 (FloatArrayList).

Exposure and likelihood198 words
  • Who is hit: code that builds the same logical object with both zeros and then hashes it, compares a parent query that holds it (BooleanQuery keeps clauses in hash-based sets) or hashes a Sort. A -0.0 comes from a computed zero, for example rounding a coordinate to a grid (Math.rint(-0.001 * 100) / 100 is -0.0, executed), negating a zero, or parsing "-0". No Lucene query parser builds these objects.
  • Default vs opt-in: default configuration, assertions on or off. LatLonPoint.newDistanceFeatureQuery and XYDocValuesField.newDistanceSort are ordinary public API; BlendedTermQuery is @lucene.experimental (BlendedTermQuery.java:45).
  • Effect: hash misses and duplicate entries only. No hit, count, score or sort-order change was shown; by reading, the two zeros give the same dis-max, haversine and euclidean arithmetic.
  • Lucene's query cache: none of the three objects becomes one of its keys. The distance feature query's weight is not cacheable (LatLonPointDistanceFeatureQuery.java:112-115); BlendedTermQuery is always rewritten before caching (BlendedTermQuery.java:271-301) into a DisjunctionMaxQuery, whose own identical tie-breaker mismatch is the related row LFV-1236; the XY sort field is not a query.
  • Scale: none needed; one pair of objects. Likelihood: contrived: objects that all use the same zero are consistent.

Why it looks unintended

#
  • Java's Object.hashCode contract and Query's javadoc ("so that QueryCache works properly") require equal hash codes for equal objects; Lucene's QueryUtils.checkEqual asserts both.
  • LatLonPointSortField, the LatLon counterpart of XYPointSortField (apache/lucene-solr#1272), compares the bits in equals, consistent with its hash.
  • Lucene fixed this same == versus bit-hash pattern in five geo value classes (#13292 / #13301).
The full argument168 words
  • The contract. java.lang.Object#hashCode: "If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result." Query.java:95-116: implement equals and hashCode properly "so that QueryCache works properly". This covers the two queries; the XY sort field is not a Query, so the Object rule alone applies to it.
  • Lucene's test oracle. QueryUtils.checkEqual asserts assertEquals(q1, q2) and assertEquals(q1.hashCode(), q2.hashCode()) together (QueryUtils.java:104-107).
  • The LatLon counterpart. The PR that added the XY classes describes them as an "Adaptation of LatLonPoint to generic cartesian space" (apache/lucene-solr#1272), and LatLonPointSortField compares Double.doubleToLongBits in equals (LatLonPointSortField.java:68-70) and hashes the same bits (:55, :57).
  • History. The introducing issues (#7753, #9528, #10278) and apache/lucene-solr#1272 never discuss equals, hashCode or signed zero; no javadoc, test, CHANGES or MIGRATE entry treats -0.0 specially. #13292 / #13301 (2024) treated the same pattern as a bug in Circle, Point, Rectangle2D, XYCircle and XYPoint.
The devil's-advocate check100 words

Argument: the two zeros are the same coordinate and the same tie-breaker (identical arithmetic), so equals returning true is right, and -0.0 is an odd input that BoostQuery even rejects for boosts.

Why it fails: that argues only for which side to repair, not for unequal hash codes. None of these entry points rejects -0.0, and -0.0 is a valid latitude, longitude and XY coordinate, so the contract must hold for it. Every verifier rated the bug real; two executed reviews by another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak, and noted that @lucene.experimental covers BlendedTermQuery only.

Trade-offs

Three small edits, matching #13301 and LatLonPointSortField. The two zero variants become two distinct objects (they still score and sort the same). Side effect: objects with the same NaN parameter become equal (today a NaN tie-breaker or NaN pivot query is not even equal to itself, and two separately built NaN-origin XY sort fields are unequal). NaN is accepted today at all three sites; the separate rows LFV-304 (the pivot, and the related DisjunctionMaxQuery tie-breaker) and LFV-426 (the XY origin) cover that.

Reject -0f for the DisjunctionMaxRewrite tie-breaker

#

Throw IllegalArgumentException for -0f, as BoostQuery does for boosts.

Trade-offs

Covers only the tie-breaker; for the coordinates -0.0 is a legal value. A behaviour change for callers passing -0f. Not run.

Downstream note

#

Services that key their own caches or de-duplication sets by these queries or sort fields can store one logical boost or sort more than once (up to four times for one XY origin, whose four sign combinations all hash apart; twice at the other two sites) when a coordinate or tie-breaker arrives as -0; results do not change.

How it was found

#

A static screen of equals/hashCode pairs looked for float and double fields compared with == but hashed by their bits, the shape of earlier rows such as LFV-1236. An executed public-API probe witnessed each site. A bytecode scan of core, queries and spatial3d then grouped the flagged classes into three rows by module.

The method in full139 words

Semi-formal. A javaparser-based static equality screen over core and 18 other modules flagged equals methods that compare float or double fields with primitive == while the matching hashCode hashes their bits; it carried over the shape of LFV-1236, LFV-1299 and LFV-1165. A public-API probe executed every flagged site on main (assertions on and off) and on 10.6.0. A bytecode scan of equals versus hashCode over the core, queries and spatial3d jars of main (25 classes flagged) split the family by module: these three core sites here, the queries module in LFV-1335, spatial3d in LFV-1341. Sites whose constructors reject -0.0 (the pivot distance, the FeatureField functions) were excluded.

Then: one minimal JUnit test, an independent reproducer, two executed reviews by another model family (OpenAI GPT-5.6), a devil's-advocate verifier, an adjudication, a history step (executed release boundaries) and a prior-report search.

Only applications that build one of these objects twice, once with 0.0 and once with -0.0 for the same parameter (the DisjunctionMaxRewrite tie-breaker, the distance feature query's origin latitude or longitude, or the XY distance sort's x or y; every public entry point accepts -0.0), and then rely on the two being one object in a hash-based structure are hit, in the default configuration, with -ea and -da, at any size, in every release since 5.3.0 (the LatLon site since 8.0.0, the XY site since 8.5.0): HashSet and HashMap lookups miss and can hold both, a BooleanQuery holding one is not equal to an otherwise identical BooleanQuery holding the other, and two Sort objects over the two sort fields are equal but hash differently; no change to hits, counts, scores or sort order was shown (the two zeros give the same arithmetic), and Lucene's own query cache is not involved (the distance feature query's weight is not cacheable, and BlendedTermQuery is rewritten into a DisjunctionMaxQuery before caching).
Summary
You build the same object twice, once with 0.0 and once with -0.0 for one parameter: a BlendedTermQuery with new DisjunctionMaxRewrite(0f) versus (-0f), LatLonPoint.newDistanceFeatureQuery with origin latitude (or longitude) 0.0 versus -0.0, or XYDocValuesField.newDistanceSort with x 0f versus -0f. equals() says the two are equal, because it compares the parameter with ==, under which 0.0 == -0.0, so by the Object#hashCode contract, which Query's javadoc asks subclasses to honour so that QueryCache works, their hash codes must be equal. Instead they differ, because hashCode() hashes the raw bits (Float.floatToIntBits or Double.hashCode), which differ in the sign bit, so a HashSet holding one object does not find the other, while hits and scores stay the same.
