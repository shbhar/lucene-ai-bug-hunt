The per-field merge view of FieldInfos reports hasVectorValues() for the whole segment

At a merge, a per-field postings or doc-values delegate gets a FieldInfos view of only its own fields, yet the view's hasVectorValues() still answers for the whole segment. Lucene's own formats never ask, so only custom delegate formats that read it are hit, in every release since 9.0.0.

The finding in 30 seconds

#

FilterFieldInfos copies every field of the segment into its base FieldInfos (to keep field numbers), which computes all flags segment-wide. It then recomputes and overrides nine flags, the iterator, size() and the lookups for its own fields, but has no hasVectorValues() override, so that one flag leaks the segment's value.

Background in three steps

#
  1. A codec can pick a postings or doc-values format per field: Lucene104Codec asks getPostingsFormatForField and getDocValuesFormatForField, and PerFieldPostingsFormat / PerFieldDocValuesFormat route each field to its format.
  2. FieldInfos describes a segment's fields and caches "does any field have X?" flags such as hasPostings(), hasPointValues() and hasVectorValues().
  3. At a merge, each per-field delegate gets a MergeState whose FieldInfos is a filtered view, PerFieldMergeState.FilterFieldInfos, that shows only the fields this delegate writes.

The finding, step by step

#
  1. A custom postings format wraps the default one and is installed per field through Lucene104Codec.getPostingsFormatForField. Index two documents, each with a keyword field id and a 2-dimension vector field v, one commit each, and run forceMerge(1).
  2. The merge hands the postings format a MergeState whose mergeFieldInfos is restricted to its own fields: size() is 1, iteration sees only id, and looking up v throws.
  3. You expect hasVectorValues() to be false: it is documented as "true if any fields have vector values", and the view's nine other "any field has X" flags are recomputed for id alone.
  4. You get true, with assertions on and off. The view passes all of the segment's fields to the FieldInfos constructor to keep field numbers, which computes the flag over v too, and it overrides every flag except this one, added in 9.0.0 after the view was written.

Who is affected

#

Only a custom PostingsFormat or DocValuesFormat that runs as a per-field delegate and reads hasVectorValues() on its merge view: it gets true at every merge of segments that hold a vector field, from two documents up. Lucene's own readers of the flag see unrestricted FieldInfos, so stock codecs and indexes are unaffected.

Mechanism, terms and numbers388 words

At merge time, PerFieldPostingsFormat and PerFieldDocValuesFormat give each delegate format a MergeState whose FieldInfos (mergeFieldInfos and every per-reader fieldInfos[i]) is a PerFieldMergeState.FilterFieldInfos restricted to that delegate's fields. The view restricts size(), iteration and both fieldInfo(..) lookups and recomputes nine "any field has X" flags over its own fields, but not hasVectorValues(), which FieldInfos gained in 9.0.0 (LUCENE-9322), four years after the view was written (LUCENE-7456). Because the view passes every field of its source FieldInfos to the base constructor to keep field numbers consistent, hasVectorValues() reports that whole source: mergeFieldInfos says true whenever the merged segment has a vector field, and each fieldInfos[i] whenever its input segment has one, even when the delegate's only field is a keyword field.

No Lucene format reads the flag on this view, so stock codecs and indexes are unaffected; only a custom delegate format that reads it gets the wrong answer. Every release from 9.0.0 through 10.6.0 and main is affected. The fix is one override, like the nine siblings.

The mechanism (main 5adff78bb168)

#
  1. The only callers of PerFieldMergeState.restrictFields are PerFieldPostingsFormat.java:191 and PerFieldDocValuesFormat.java:151; each passes the restricted MergeState to a delegate's merge.
  2. restrictFields (codecs/perfield/PerFieldMergeState.java:44-75) wraps every per-reader fieldInfos[i] (:45-48) and mergeFieldInfos (:56) in a FilterFieldInfos.
  3. Its constructor calls super(toArray(src)) with every field of the segment (:95; comment at :94: "the field numbering must be kept consistent"), so the base constructor computes hasVectorValues |= (info.getVectorDimension() != 0) over all of them (index/FieldInfos.java:123).
  4. It then recomputes nine flags over the filtered fields (:97-133) and overrides them (:150-194: hasFreq, hasPostings, hasProx, hasPayloads, hasOffsets, hasTermVectors, hasNorms, hasDocValues, hasPointValues), plus iterator() (:146), size() (:196) and fieldInfo(String) / fieldInfo(int) (:201-227, which throw IllegalArgumentException for a field outside the view). There is no hasVectorValues() override, so FieldInfos.hasVectorValues() (index/FieldInfos.java:297-299) returns the whole segment's value.
  5. The view contradicts itself: hasVectorValues() says yes, iteration finds no vector field, and fieldInfo("v") throws "The field named 'v' is not accessible in the current merge context" (:204-209; executed in a separate re-run). The lookup throws for any name outside the view, bug or not; what is wrong is the flag that invites it.
Exposure and likelihood229 words
  • Who is hit: a custom PostingsFormat or DocValuesFormat (public, @lucene.experimental extension points) that runs as a per-field delegate, for example through the codec's getPostingsFormatForField / getDocValuesFormatForField hooks, and whose merge reads hasVectorValues() on mergeState.mergeFieldInfos or on a per-reader mergeState.fieldInfos[i]. It gets true from mergeFieldInfos on every merge whose merged segment holds a vector field, and from fieldInfos[i] for every input segment that holds one (the repro observes mergeFieldInfos; a probe of the same two-segment merge shows fieldInfos[0] and fieldInfos[1] say true too). Two documents suffice; apart from installing the custom delegate, no scale or unusual index setting is needed.
  • Not hit: Lucene itself. The in-tree readers of FieldInfos.hasVectorValues() (SegmentMerger.java:161, KnnVectorsWriter.java:126 and :332, CheckIndex.java:2853 and :2937, SegmentCoreReaders.java:136) never receive the restricted view, and no in-tree postings or doc-values format reads the flag.
  • Effect: a wrong boolean. A delegate that acts on it may take a needless vector-related path, or get the view's IllegalArgumentException when it then looks up the vector field. For example, the public helper KnnVectorsWriter.MergedVectorValues.hasVectorValues(fieldInfos, "v") (KnnVectorsWriter.java:331-337), which checks the flag before the lookup, throws that exception when given the repro's postings view, and returns false with fix A (executed in a separate re-run).
  • How likely: rare. Doc-values and postings formats have little reason to ask about vectors, and no public report of it was found since 9.0.0 (2021).

Why it looks unintended

#
  • hasVectorValues() is documented as "true if any fields have vector values"; the view holds no such field.
  • The view filters its nine other "any field has X" flags; the 2016 review that created it warned that wrong flags "can result in sneaky future bugs".
  • hasPostings() (2022) got its filtered override in the same commit; hasVectorValues() (2020) never did.
The full argument204 words
  • Contract. FieldInfos.hasVectorValues(): "Returns true if any fields have vector values" (index/FieldInfos.java:296). The view's own size(), iterator() and lookups say there is no such field.
  • Siblings. The same view recomputes and overrides every other "any field has X" flag, including hasPointValues(), which matters to a postings or doc-values delegate no more than vectors do. An independent test reads, on one doc-values delegate's view, size() 1, hasPointValues() false and hasVectorValues() true.
  • Recorded intent. On LUCENE-7456 (#8508), which created the class, Michael McCandless reviewed the first patch (2016-09-23): "Methods like FilterFieldInfos.hasProx, etc., are also wrong, which can result in sneaky future bugs for codecs that rely on this." The revised patch, the one committed (796ed508f39), "now correctly computes and exposes the hasXXX properties" (Julien Massenet, 2016-09-27): all eight flags FieldInfos had then.
  • Maintenance precedent. LUCENE-9322 (c02f07f2d5d) added hasVectorValues without touching PerFieldMergeState.java; the next flag, hasPostings (LUCENE-10291, #539, 8fa7412dec4, 2022), got its filtered override in the same commit.
  • No sign of a decision. Nothing in the LUCENE-9322 discussion, javadoc, CHANGES or tests says vectors should stay unfiltered; the two upstream tests that read the restricted view (TestPerFieldDocValuesFormat.java:280, TestPerFieldPostingsFormat2.java:403) check only its field names.
The devil's-advocate check224 words

The strongest case for "intended": PerFieldMergeState is a package-private helper and MergeState and FieldInfos are @lucene.experimental; mergeFieldInfos is documented as "FieldInfos of the newly merged segment" (MergeState.java:52), and that segment does have a vector field; knnVectorsReaders are passed unrestricted next to the view (PerFieldMergeState.java:69); the view is not a full FieldInfos anyway (a lookup of a field outside the view throws IllegalArgumentException where a plain FieldInfos returns null; getSoftDeletesField() and getParentField() are not overridden); and no Lucene code reads the flag.

Why it fails: the same argument would justify an unfiltered hasPointValues() (the points readers are passed unrestricted too, :68) and an unrestricted size() and iterator, yet all of those are filtered. The recorded intent (the 2016 review) and the later hasPostings precedent strongly support filtering every aggregate has* flag on this view, and "nothing in Lucene reads it" is why this is Low, not why it is intended. getSoftDeletesField() and getParentField() name one designated segment-wide field rather than an "any field has X" aggregate, and are not part of this report. The cross-model reviews and the intended-behaviour review rated the "intended" case weak; the independent reproduction added a caveat: the restriction is an undocumented internal design, so the rule for this view is implied by its treatment of the sibling flags rather than stated for the view.

Suggested fix

#

Recommended A: add the missing hasVectorValues() override (recommended)

Add the missing override, like the nine siblings: compute hasVectorValues |= fi.hasVectorValues() over the filtered fields and return it from hasVectorValues() (+9 lines in PerFieldMergeState.java). Validated: the repro passes, and the per-field and segment-merger suites and the core lint checks pass.

private final boolean filteredHasVectorValues;
// constructor, before the loop:
boolean hasVectorValues = false;
// in the filtered loop:
hasVectorValues |= fi.hasVectorValues();
// after the loop:
this.filteredHasVectorValues = hasVectorValues;

@Override
public boolean hasVectorValues() {
  return filteredHasVectorValues;
}

How it was found

#

Semi-formal: a proof-obligation audit of FilterFieldInfos, checking that each has* flag of the restricted view equals "some field of the view has it", as the FieldInfos javadoc says and the class does for nine flags. hasVectorValues() fails the obligation; a one-test JUnit repro on stock main witnessed it.

The method in full92 words
  • Obligation: for every has* flag of FieldInfos, the restricted view must return "some field of the view has it" (FieldInfos.java:251-299 javadocs), the rule the class follows for nine flags (PerFieldMergeState.java:97-133, :150-194).
  • Finding: hasVectorValues() is the one public has* method of FieldInfos that the view does not override; its value comes from the base constructor over every field of the segment (PerFieldMergeState.java:95, FieldInfos.java:123).
  • Witness: a JUnit test on stock main, then an independent reproduction, cross-model reviews, an intended-behaviour review and an adjudication (see Independent checks).
