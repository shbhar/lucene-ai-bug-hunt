BM25 k3 query-term saturation is skipped for repeated SHOULD clauses when 2 <= minimumNumberShouldMatch < number of SHOULD clauses

With BM25's opt-in k3 setting (unreleased main), a word repeated in a minimum-should-match query counts in full instead of saturated when 2 <= minimumNumberShouldMatch < number of SHOULD clauses. Document "a b", SHOULD a, a, b: score 0.3661 at minimumNumberShouldMatch 1, 0.3923 at 2.

The finding in 30 seconds

#

BooleanQuery.rewrite applies k3 only when it merges duplicate clauses into one boosted clause. It merges duplicate SHOULD clauses only when minimumNumberShouldMatch is at most 1, because merging changes how many clauses a document matches. In between, the duplicates stay separate clauses with weight 1 and add up linearly.

Background

#
  1. k3. Opt-in since #15818 (unreleased 11.0.0): new BM25Similarity(k1, b, discountOverlaps, k3), and StableTflSimilarity with k3, weight a term repeated n times in a query ((k3 + 1) * n) / (k3 + n). With k3 = 8 that is 1.8 for n = 2 and 2.45 for n = 3. The default constructor keeps k3 off.
  2. Where it is applied. BooleanQuery.rewrite merges equal clauses into one clause boosted by Similarity#computeQueryTermWeight(n): SHOULD a, a becomes a^1.8. That merge is the only place the weight is applied.
  3. minimumNumberShouldMatch (msm). A document must match at least msm of the SHOULD clauses, and duplicates count separately: a document with only a matches (a a b)~2. Merging the two a clauses would change that, so the SHOULD merge is skipped when msm is 2 or more (LUCENE-7925, 2017).
  4. msm = number of SHOULD clauses. Then every SHOULD clause becomes a MUST clause, and MUST duplicates are always merged.

The finding, step by step

#
  1. Turn on BM25's opt-in k3: new BM25Similarity(1.2f, 0.75f, true, 8f). Its javadoc promises that a word repeated n times in a query counts ((k3 + 1) * n) / (k3 + n) times instead of n times: 1.8 instead of 2 for a word typed twice.
  2. Index one document, "a b", and search SHOULD a, SHOULD a, SHOULD b with minimumNumberShouldMatch 1: score 0.3661 = 1.8 × 0.13076 + 0.13076. The rewrite merged the two a clauses into a^1.8.
  3. Run the same query with minimumNumberShouldMatch 2. The document still matches all three clauses, so you expect 0.3661 again.
  4. Instead you get 0.3923 = 3 × 0.13076, 7% higher: the repeated a counts twice. With all three clauses required (minimumNumberShouldMatch 3) it is 0.3661 again.
  5. Why: the rewrite applies k3 only when it merges duplicates, and it may merge duplicate SHOULD clauses only when minimumNumberShouldMatch is at most 1, since merging changes how many clauses a document matches. In between, nothing applies the weight.

Who is affected

#

Applications on main or branch_11x (unreleased 11.0.0) that opt into k3 with BM25Similarity or StableTflSimilarity as the searcher's similarity and run minimum-should-match queries whose text repeats a word, for example through QueryBuilder.createMinShouldMatchQuery. Only scores change: about 5-10% in small examples, 4.8 times for a word repeated 50 times; which documents match never changes.

Mechanism, terms and numbers616 words

#15818 (unreleased, 11.0.0) added an opt-in k3 to BM25Similarity, and #16243 to StableTflSimilarity: a term repeated n times in a query is weighted ((k3 + 1) * n) / (k3 + n) "instead of linear summing". The weight is applied in exactly one place, when BooleanQuery.rewrite merges duplicate clauses into one boosted clause. Duplicate SHOULD clauses are merged only when minimumNumberShouldMatch <= 1, a correct guard from LUCENE-7925 (2017), because merging changes how many clauses a document matches. So for 2 <= minimumNumberShouldMatch < number of SHOULD clauses the duplicates stay separate and add up linearly, while msm 0, 1 and msm = number of SHOULD clauses are saturated. One document "a b", SHOULD a, a, b, k3 = 8: 0.3661408 at msm 1 and 3, 0.39229372 at msm 2. Only scores change; the matching documents do not, and nothing throws. Main and branch_11x only; no release has k3. A small BooleanWeight change that leaves the rewrite alone fixes it.

The code (main 645d4fe14a20)

#
  1. The promise. BM25Similarity.java:44-46, @param k3: "Controls query-side term frequency saturation. When duplicate terms appear in a query, their boost is computed as ((k3 + 1) * qtf) / (k3 + qtf) instead of linear summing. A negative value disables saturation (linear behavior)." StableTflSimilarity.java:103-105 has the same words, and its class javadoc lists "query-side saturation for repeated query terms" (:50). The formula: BM25Similarity.java:125-136, StableTflSimilarity.java:153-164; the default constructor sets k3 = -1 (BM25Similarity.java:121-123).
  2. The hook. Similarity#computeQueryTermWeight (Similarity.java:164-177, @lucene.experimental) "is used during query rewriting to compute the boost for duplicate query terms"; the default is linear.
  3. Its only caller. deduplicateClauses (BooleanQuery.java:714-758) groups equal clauses of one occur and boosts the merged clause by similarity.computeQueryTermWeight(n) (:746); with explicit boosts it sums them linearly (:740-742). No other production code calls the hook.
  4. The guard. The SHOULD dedup runs only when minimumNumberShouldMatch <= 1 (BooleanQuery.java:438-447, condition at :442). Merging a a into a^w would make a document with only a stop matching (a a b)~2, so the guard is right; the hunt's Z3 model shows that a guard of msm <= 2 breaks matching (counterexample: msm = 2, two equal SHOULD clauses).
  5. The MUST path. MUST duplicates are merged unconditionally (BooleanQuery.java:449-455); when the number of SHOULD clauses equals msm, every SHOULD becomes MUST (:570-587). That is why msm = number of SHOULD clauses saturates again.
  6. Result. For 2 <= msm < number of SHOULD clauses the rewrite leaves the duplicate SHOULD clauses apart (for the repro's query it returns the query unchanged; duplicate MUST clauses in the same query would still be merged), BooleanWeight creates one weight per clause with the same boost (BooleanWeight.java:49-62), and the duplicates add up linearly.
  7. Before k3 the guard changed no score: merged (a^2) and unmerged (a a) duplicates both add up linearly. k3-free controls on 9.12.3, 10.5.2, the parent of #15818 and main give one score for msm 1, 2 and 3.

Exposure and likelihood409 words
  • Who. Users of main or branch_11x (unreleased 11.0.0) that set BM25Similarity(k1, b, discountOverlaps, k3) or StableTflSimilarity(k1, c, k3) with k3 >= 0 as the searcher's similarity, and run a BooleanQuery with a repeated unboosted SHOULD clause and 2 <= msm < number of SHOULD clauses. The typical producer is a "minimum should match" option over user text with a repeated word: QueryBuilder.createMinShouldMatchQuery("body", "alpha alpha bravo", f) scores one document 0.8479051 at f = 0.5 (msm 1), 0.90846974 at f = 0.7 (msm 2) and 0.8479051 at f = 1.0. Query text with a repeated word is the case k3 is for (#15768: "duplicate terms in query strings see their scores boosted by their number of occurrences").
  • Reach limit. The rewrite takes the weight from IndexSearcher#getSimilarity() (BooleanQuery.java:734, :746), so k3 has an effect only if that similarity applies it. BM25Similarity and StableTflSimilarity do. The stock PerFieldSimilarityWrapper does not override computeQueryTermWeight, so behind it the rewrite gives (body:a)^2.0, not ^1.8 (executed); a custom wrapper could override the hook and delegate (Similarity.java:175, public and not final). That gap may be a separate issue; it was not judged.
  • Effect. Wrong scores, silently: the repeated term contributes n * s instead of w(n) * s, about 5-10% of the total in the small examples and a factor of 4.84 for a term repeated 50 times next to two other terms (2.1188598 at msm 1, 10.250274 at msm 2). Inside the window the repeated SHOULD term contributes exactly its k3-disabled amount. When those are the query's only duplicates (the repro and every example here), the whole score equals the k3-disabled score; duplicates that the rewrite still merges (MUST ones) stay saturated. k3 only ever lowers scores (w(n) <= n), so no score goes above Lucene's default. Which documents match does not change and nothing throws. No check showed two documents swapping rank: scores change, and with them possibly the ranking.
  • Consistency. For one document and one query text the score is not monotone in msm: higher at msm 2 than at msm 1 or at msm 3.
  • Sibling, not part of this claim. Duplicates split across occurs (+a a) are never merged: linear at msm 0, saturated at msm 1, because a single SHOULD clause with msm 1 becomes MUST and is merged. The recommended fix does not change that case.
  • No release has k3, so a fix before 11.0.0 means no release ever ships the bug.

Why it looks unintended

#
  • The k3 javadoc is unconditional: duplicate query terms get ((k3 + 1) * qtf) / (k3 + qtf) "instead of linear summing" (#15818).
  • The only documented exception is explicit boosts; no k3 javadoc, test or review comment mentions minimumNumberShouldMatch.
  • An upstream regression test expects msm to keep a matching document's score; with k3 on, 6 of 2,000 queries fail.
The full argument269 words
  • The contract. The k3 @param on BM25Similarity (:44-46) and StableTflSimilarity (:103-105) has no msm condition. The #15818 description: "Saturation is applied in BooleanQuery.rewrite() through a new Similarity.computeQueryTermWeight(int qtf) method, which BM25Similarity overrides. This works transparently regardless of which query parser or programmatic API produced the query."
  • The one documented exception is different. Explicit boosts are summed linearly: a code comment (BooleanQuery.java:740-742) and TestBooleanRewrites#testDeduplicateWithExplicitBoostsFallsBackToLinearSum (:1173). The upstream k3 tests use msm 0 only (:1137, :1153), and none of the #15818 review comments mentions minimumNumberShouldMatch.
  • An existing upstream test expects the same. TestBooleanMinShouldMatch#testRandomQueries (:312-360), a randomized regression test (not API documentation), checks that adding a minimumNumberShouldMatch to a random query leaves the score of a document that still matches unchanged (assertSubsetOfSameScores, :363); its comment cites "(field:v field:v field:v) gets rewritten into field:v^3" (:398-399). As configured it cannot see k3: its searcher uses the framework's AssertingSimilarity(RandomSimilarity) (newSearcher, LuceneTestCaseParent.java:2638; SetupAndRestoreStaticEnv.java:230), and neither wrapper overrides computeQueryTermWeight (RandomSimilarity is a PerFieldSimilarityWrapper, RandomSimilarity.java:68), so the rewrite always uses the linear default; its BM25 entry also has k3 off (:123). Adding a k3 BM25 to RandomSimilarity would not exercise this bug. With BM25 k3 = 8 set on the searcher the same check finds 6 violations in 2,000 queries (0 with k3 off): 2 are this bug, 4 the +a a sibling.
  • Precedent. #5368 / LUCENE-4300 ("BooleanQuery inconsistently applies coord() if it rewrites itself"): a score that depended on the rewrite shape, caught by the same invariant test, was fixed.
The devil's-advocate check205 words

The strongest case for "intended": k3 is defined by its mechanism. The hook's javadoc says it is "used during query rewriting", the PR says "Saturation is applied in BooleanQuery.rewrite()", and the SHOULD merge carries a deliberate, tested guard: TestBooleanRewrites#testDeduplicateShouldClauses (:610) asserts that (foo:bar foo:bar foo:quux)~2 rewrites to itself (:634-642). In the #15818 review rmuir called the boost handling "a bit odd and difficult to understand" and said that processing qtf separately from the boost "would create a much more invasive change", and added "This approach could use some fresh eyes and thoughts before committing to it"; the merged implementation kept the rewrite-based design. The hook is experimental, and Lucene does not promise comparable scores across different queries.

Why it fails: the guard explains why the clauses cannot be merged, not why the weight is dropped. The user-facing @param and the PR promise saturation regardless of how the query was built. For one document and one query text the score is not monotone in msm, which no review comment mentions. And a way to apply the weight without changing matching exists (the recommended fix); testDeduplicateShouldClauses stays green with it. Upstream may still reasonably prefer a javadoc caveat; that is the maintainers' call.

Suggested fix

#

Recommended Apply the weight in BooleanWeight when the rewrite could not merge (validated)

In BooleanWeight, when scores are needed and minimumNumberShouldMatch > 1, create each of the n unboosted occurrences of a duplicate SHOULD clause with computeQueryTermWeight(n) / n of the boost. Matching and the rewrite stay unchanged, so count() still converges. The repro, 147 tests of the closest suites and the 2,339 tests of the search package pass.

float clauseBoost = boost;
if (c.occur() == Occur.SHOULD) {
  // computeQueryTermWeight(n) / n for an unboosted query that occurs n >= 2 times, msm > 1
  clauseBoost *= duplicateShouldWeights.getOrDefault(c.query(), 1f);
}
Weight w = searcher.createWeight(
    c.query(), c.isScoring() ? scoreMode : ScoreMode.COMPLETE_NO_SCORES, clauseBoost);

Apply the weight in BooleanWeight when the rewrite could not merge (validated) (recommended)

#

In the BooleanWeight constructor (BooleanWeight.java:49-62), when scores are needed and minimumNumberShouldMatch > 1, count the unboosted SHOULD occurrences of each query; a query that occurs n >= 2 times, and never with an explicit boost, gets each clause weight created with boost * computeQueryTermWeight(n) / n (+47/-1 lines, BooleanWeight.java only).

float clauseBoost = boost;
if (c.occur() == Occur.SHOULD) {
  // computeQueryTermWeight(n) / n for an unboosted query that occurs n >= 2 times, msm > 1
  clauseBoost *= duplicateShouldWeights.getOrDefault(c.query(), 1f);
}
Weight w = searcher.createWeight(
    c.query(), c.isScoring() ? scoreMode : ScoreMode.COMPLETE_NO_SCORES, clauseBoost);

Trade-offs

  • Matching unchanged. The clauses and msm stay as they are, so exactly the same documents match. Equal clauses match the same documents, so a document matches all n occurrences or none, and the n split weights add up to the merged weight (up to float rounding).
  • Rewrite unchanged. The rewrite is not touched, so count(), ConstantScoreQuery and FILTER rewrites converge exactly as on stock main; that is where option B fails.
  • Same rules as the merge. Explicitly boosted duplicates stay linear, as in BooleanQuery.java:740-742; with k3 off the factor is 1; with msm <= 1 nothing changes, since the rewrite already merged.
  • Scope. It does not change the +a a sibling (see option D).
  • Cost. A few small hash collections per scoring BooleanWeight with msm > 1; no benchmark was run.

Per-occurrence boosts in BooleanQuery.rewrite (rejected: non-scoring rewrites never converge)

#

The hunt's first fix wraps each duplicate SHOULD clause in BoostQuery(q, computeQueryTermWeight(n) / n) during the rewrite when msm > 1. It fixes the scores and passed 99 upstream tests.

Trade-offs

BooleanQuery.rewriteNoScoring strips the boosts again (BooleanQuery.java:228-231, reached from ConstantScoreQuery.rewrite, ConstantScoreQuery.java:44-62), the scoring rewrite adds them back, and IndexSearcher.rewrite loops until it gets the same object back (IndexSearcher.java:871-878). With this patch IndexSearcher.count on an ordinary (a a b)~2 query never returns (20 s timeout; stock main returns). Any rewrite-time fix must keep non-scoring rewrites convergent.

Document the limitation

#

Say in the k3 @param of both similarities and in Similarity#computeQueryTermWeight that saturation applies only where BooleanQuery merges duplicates (duplicate SHOULD clauses only when minimumNumberShouldMatch <= 1).

Trade-offs

No code risk, but the scores keep depending on msm, and the score expectation of TestBooleanMinShouldMatch stays false with k3 on the searcher. A maintainer could reasonably choose it. Not run.

One rule for all scoring duplicates (wider, not built)

#

Do option A's counting across SHOULD and MUST occurrences of the same query, which would also cover +a a.

Trade-offs

It has to interact with the MUST merge, which already turns +a +a into +a^1.8, and with explicit boosts, so it needs its own design and tests.

Downstream note

#

An application that relies on k3 to damp repeated words in user queries does not get that damping for minimum-should-match queries; the worst case is Lucene's default k3-off weighting, and which documents match never changes.

How it was found

#

A Z3 model of BooleanQuery's rewrite rules proved that duplicate SHOULD clauses may be merged only when minimumNumberShouldMatch is at most 1; while writing it, the finder noticed that the new k3 weight is applied only where they are merged. A second Z3 model checked the score consequence, and a public-API JUnit confirmed it.

The method in full176 words

Method: semi-formal (the hunt's tier for a hypothesis formed during modelling and confirmed by execution). The hunt unit covered BooleanQuery rewrite and dispatch.

  • Rewrite model. A Z3 model of 47 rewrite obligations; obligation R9 ("SHOULD dedup when msm <= 1" preserves matching) is proved, and its mutant R9m ("when msm <= 2") has the counterexample msm = 2 with two equal SHOULD clauses. While writing R9 the finder saw that the k3 weight is applied only inside this dedup.
  • Score model. A second Z3 model: the msm 1 and msm 3 paths equal the documented k3 score (UNSAT for a difference), the msm 2 path differs (SAT), and with k3 disabled there is no difference.
  • JUnit. A public-API test on the stock jar failed for BM25 and StableTfl with assertions on and off and did not compile on 10.5.2. The minimal repro above is that test cut to one document, one query shape and one assertion.

The solver's own output was not the first signal: the hypothesis came from reading the code while writing the obligation.

LFV-103, snapshot of 2026-11-08

Registry title
BM25Similarity/StableTflSimilarity k3 query-term saturation is skipped for duplicate SHOULD clauses when 2 <= minimumNumberShouldMatch < number of SHOULD clauses
Area
search / BooleanQuery rewrite and similarities
Priority
Low, rank 735: Moved down from Medium: opting into the new BM25/StableTfl k3 parameter skips query-term saturation for duplicate SHOULD clauses under minimum-should-match, changing scores with no demonstrated rank change, in unreleased main only, so a cheap fix before 11.0.
Impact class
silent wrong results
Impact note
Only applications on unreleased main (11.0.0) that opt into k3 >= 0 on BM25Similarity or StableTflSimilarity used as the searcher's own similarity (PerFieldSimilarityWrapper does not pass computeQueryTermWeight through), and that run a BooleanQuery with a repeated unboosted SHOULD term and 2 <= minimumNumberShouldMatch < number of SHOULD clauses, for example QueryBuilder.createMinShouldMatchQuery on text with a repeated token; any scale; only scores change (about 5-10% of the total in the small examples, a factor of 4.8 for a term repeated 50 times), never above the k3-disabled score; the set of matching documents does not change, and no verifier showed two documents swapping rank.
Summary
You turn on BM25's opt-in k3 parameter (new BM25Similarity(1.2f, 0.75f, true, 8f), or StableTflSimilarity with k3), whose javadoc promises that a term repeated in a query is weighted ((k3 + 1) * qtf) / (k3 + qtf) instead of linearly, and you search with a BooleanQuery that repeats a SHOULD term, for example QueryBuilder.createMinShouldMatchQuery('body', 'a a b', fraction). You expect a document that matches every clause to get the same saturated score whatever minimumNumberShouldMatch is. Instead, when 2 <= minimumNumberShouldMatch < the number of SHOULD clauses, the repeated term is summed linearly: with k3=8 the document 'a b' scores 1.0150898 at msm=2 but 0.9568421 at msm=1 and at msm=3 (all clauses required).
