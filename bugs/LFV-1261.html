LRUQueryCache registers another close listener each time an open segment is cleared with clearCoreCacheKey and cached again

Calling LRUQueryCache.clearCoreCacheKey on a still-open segment and then caching it again adds a second close listener to it: at close the listener runs 2 times instead of 1, and each further cycle adds one. It is in every release since 5.0.0 (on 10.x also after clear()); results are unaffected.

The finding in 30 seconds

#

When a segment core closes, it calls back every close listener registered on it. LRUQueryCache registers one per core the first time it caches something for that core, so it can drop the core's cached entries when the segment goes away.

  1. Index 1 document and search it with an LRUQueryCache that caches every query. The search for ConstantScoreQuery(f:a) caches its inner f:a, and the cache adds 1 close listener to the segment's core, so it can drop the entries when the segment closes.
  2. Call cache.clearCoreCacheKey(coreKey) and cleanUp() while the reader stays open, then run the same search: the query is cached again.
  3. You expect closing the reader to notify the cache once: the cache keeps a map, registeredClosedListeners, so that it registers only once per segment core.
  4. Instead the listener runs 2 times. clearCoreCacheKey also removed the core from that map, so the second caching added a second listener, and a core never drops a listener before it closes. Each further clear-and-recache cycle adds one more: N cycles leave N+1 listeners.
  5. On 10.x and earlier releases clear() does the same. On main clear() keeps 1.

Who is affected

#

Applications that clear cached entries for segments that stay open and keep searching them: clearCoreCacheKey on main and in every release since 5.0.0, also clear() on 10.x and earlier, as a per-index clear-cache operation does. Each cycle adds one small object per re-cached segment, freed when the segment closes. Results are never wrong; rare, so priority Low.

Mechanism, terms and numbers604 words

LRUQueryCache registers a close listener on a segment core the first time it caches something for that core, and on main keeps a map, registeredClosedListeners, so that it registers only once per core (LRUQueryCache.java:129-130, :1133-1136). The public clearCoreCacheKey removes the core from that map (:444), also when the core is still open, so the next caching for the same core registers again. A core keeps its listeners in an add-only set until it closes (SegmentCoreReaders.java:71-72, :192-194, :201-204), and at close each duplicate re-runs clearCoreCacheKey. One clear-and-recache cycle makes the cache's listener run 2 times instead of 1, and N cycles leave N+1 listeners. On 10.x and every release back to 5.0.0 (LUCENE-6077; the class was LRUFilterCache in 5.0.0) a listener is added whenever a per-core LeafCache is created, and both clearCoreCacheKey and clear() drop it. Search results are never affected; the cost is one small object per cycle per re-cached segment, held until the segment closes. Fix on main: only the real close removes the map entry.

The code (main 5adff78bb168)

#
  • The once-per-core guard. registeredClosedListeners (LRUQueryCache.java:129-130) has one entry per core key. LRUQueryCachePartition.putIfAbsent adds the listener only when registeredClosedListeners.putIfAbsent(cacheKey, TRUE) == null (:1133-1135, comment "we just created a new leaf cache, need to register a close listener").
  • The removal. The public clearCoreCacheKey (:442-447, "Remove all cache entries for the given core cache key.") first removes the core from the map (:444), then queues it for cleanUp(). It is also the method the close listener calls, so the same removal makes the map forget closed cores; we found no stated reason for removing the entry of a core that stays open. On an open core it re-arms the guard. The cached entries go only at the next cleanUp() (:1392-1410, called by the application or an optional background scheduler), so the second listener comes with the next new entry for that core: in the repro, the same query cached again after cleanUp(). Without cleanUp() the second search would be served from the old entry and add nothing.
  • No way back. SegmentCoreReaders keeps listeners in Collections.synchronizedSet(new LinkedHashSet<>()) (SegmentCoreReaders.java:71-72), only adds (:192-194) and runs them all at close (:201-204). IndexReader.CacheHelper has only getKey() and addClosedListener (IndexReader.java:112-126). In the Java 25 runtime used, the two evaluations of the capturing method reference LRUQueryCache.this::clearCoreCacheKey gave two distinct, unequal objects (Java does not promise this either way), so the set keeps both.
  • clear() on main (:457-463) does not touch the map and keeps one listener.

The 10.x form

#

10.6.0 has no map: putIfAbsent adds a listener whenever it creates a per-core LeafCache (10.6.0 LRUQueryCache.java:331-337). clearCoreCacheKey(Object) removes the LeafCache (:374-377) and clear() removes all of them (:415-418), so both re-arm it. Ordinary LRU eviction only removes queries from each LeafCache (:406-411), so, without a clear or a close, query traffic never adds a second listener for a core.

The numbers

#

One clear-and-recache cycle (cache, clear, cache again): 2 calls instead of 1 (main and 10.6.0). N such cycles leave N+1 listeners: a probe on the stock main jar counted 1, 2 and 4 runs after 0, 1 and 3 cycles. The older tests, three rounds of cache-then-clear (two clear-and-recache cycles), give 3 (5.0.0 through 10.6.0 and main). Four rounds of cache-then-clear with a pass-through CacheHelper: 4 addClosedListener calls for one open core. Controls: no clear gives 1; clear() on main gives 1; on 10.6.0 three rounds of cache-then-clear() give 3.

Exposure and likelihood305 words
  • Who is hit. Code that clears the cache for live segments and keeps searching them. Example by reading (not run): Elasticsearch's per-index clear-cache operation, IndicesQueryCache.clearIndex, calls cache.clearCoreCacheKey(coreKey) for every core key it tracks for the index, then cache.clear() if the cache is empty (the 10.x API; read through the GitHub API on 2026-11-03 at the file's latest commit there, 3c2e355030f, 2026-08-20).
  • Effect. One listener object plus one set node per clear-and-recache cycle per re-cached segment core, held until the core closes; at close every duplicate re-runs the idempotent clearCoreCacheKey. Growth is linear in (number of clears) x (number of long-lived segments cached again). Arithmetic only, not measured: one clear per minute for a week adds about 10,000 listeners to a segment that lives that long.
  • Not hit. Search results, and applications that never clear a live segment.
  • What it takes. An explicit clear of a core that stays open, by the application, and then a new cache entry for that core. Caching needs a segment the leaf predicate accepts and a query the policy caches: with the two-argument constructor the predicate (MinSegmentSizePredicate(10000), LRUQueryCache.java:251-253, :278-296) accepts only segments of at least 10,000 documents that are also more than half the average segment size, and the default UsageTrackingQueryCachingPolicy caches a query only after repeated use. The repro removes both barriers on purpose, so a 1-document segment is enough.
  • Default vs opt-in. From 5.4.0 through 10.x, IndexSearcher's default query cache is an LRUQueryCache built with that two-argument constructor (10.6.0 IndexSearcher.java:95-100); 5.0.0 had no query cache in IndexSearcher, and 5.1.0 to 5.3.x set the default to null. On main the query cache is off by default (#14187, IndexSearcher.java:82-84), so the application installs the cache itself.
  • Likelihood: rare. No matching public report found since 5.0.0 (released February 2015).

Why it looks unintended

#
  • #15558 added registeredClosedListeners to register once per core; clearCoreCacheKey also removes a core that stays open, and we found no stated reason for that.
  • clearCoreCacheKey is public with no closed-core precondition; the migration guide shows it as user code on a live reader.
  • On main, clear() already keeps one listener; only clearCoreCacheKey adds one per cycle.
The full argument113 words
  • Purpose of the map. #15558 (d50fb36d9af, sgup432, merged 2026-04-14) added registeredClosedListeners; its only uses are the putIfAbsent guard (LRUQueryCache.java:1133) and the removal (:444). The comment at :1134 ties registration to the first caching of a core.
  • Legal call. clearCoreCacheKey is documented as "Remove all cache entries for the given core cache key." (:442). MIGRATE.md:543-554 shows cache.clearCoreCacheKey(reader.getCoreCacheHelper().getKey()); as user code. TestLRUQueryCache.java:767-769 and :2713 call it on open cores, and so does the JMH benchmark (LRUQueryCacheBenchmark.java:280).
  • History. #15558's review never discusses the listener; LUCENE-6077, which introduced the per-LeafCache registration, says nothing about clearing a live core. No test or comment relies on re-registration.
The devil's-advocate check141 words

The strongest case: LRUQueryCache, CacheHelper and ClosedListener are @lucene.experimental; no javadoc promises one listener per core; Lucene's own CacheHelper javadoc example adds a listener on every call (IndexReader.java:96, cacheHelper.addClosedListener(counts::remove)); the duplicates are idempotent, cheap and freed at close; and no public report was found in nearly 12 years.

Our reading, a judgment rather than a fact: these points bear mostly on severity. The cache already de-duplicates per core on purpose, and the removal at :444 also runs on cores that stay open, where we found no stated reason for it. Every verifier, including an executed review by another model family (OpenAI GPT-5.6), rated the bug real; that review still rated the intended-behaviour case moderate, so a maintainer could reasonably treat listener multiplicity as an implementation detail and close it as won't-fix, or rank it low priority.

Suggested fix

#

Recommended Main: only the real close removes the core from registeredClosedListeners

Let only the real core close forget the core: the close listener removes its registeredClosedListeners entry itself, and clearCoreCacheKey no longer does. Validated with gradle: the repro passes with assertions on and off, TestLRUQueryCache passes (40 tests, 0 failures, 3 skipped) and :lucene:core:check -x test passes.

Downstream note

#

Downstream products see it only if they clear the query cache for segments that stay open, for example through an administrative clear-cache call; queries and documents alone never add a second listener for a core.

How it was found

#

A proof-obligation audit of LRUQueryCache's contract checked that each cache registers one close listener per segment core, the de-duplication registeredClosedListeners encodes. The public clearCoreCacheKey undoes it on an open core. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full112 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: one close listener per (cache, segment core), as the putIfAbsent guard on registeredClosedListeners intends. Every path that removes a core from the map was checked against whether the core can still be open; the public clearCoreCacheKey can be called on an open core.
  • A JUnit test witnessed it on main with assertions on and off; probes checked clear() on main and 10.6.0. An independent reproducer and an executed review by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier and an adjudication re-ran the repro.

LFV-1261, snapshot of 2026-11-07

Registry title
LRUQueryCache registers another core-closed listener each time a still-open segment core is cleared with clearCoreCacheKey and then cached again (on 10.x also after clear()), so a long-lived segment core collects one duplicate listener per clear-and-recache cycle
Area
core / search (LRUQueryCache: core-closed listener registration)
Priority
Low, rank 1114: Each time an application clears a still-open segment from LRUQueryCache (through clearCoreCacheKey, and on 10.x and earlier also through clear()) and that segment is cached again, the cache adds one more close listener, in every release since 5.0.0. Search results do not change and each duplicate is a small object freed when the segment closes, so only long-lived segments that are cleared very often see the growth.
Impact class
minor
Impact note
Only applications that clear a still-open segment core from an LRUQueryCache and then let it be cached again are hit: on main through the public clearCoreCacheKey (a downstream engine's per-index clear-cache operation calls it for every live core [read]), on 10.x and earlier releases also through clear(); each such cycle adds one more listener object to the core's add-only close-listener set, which is freed only when the core closes, where every duplicate re-runs the idempotent clearCoreCacheKey; search results are never affected and the growth is one small object per cycle per re-cached core (not measured), so it matters only for long-lived segments that are cleared very often; default cache, reader and settings, every release from 5.0.0 through 10.6.0 and main [exec].
Summary
You cache a query for a segment, call LRUQueryCache.clearCoreCacheKey with that segment's core key while the reader stays open (then cleanUp()), and search again so the query is cached for the same core once more. You expect the cache to keep its single close listener on that core, because the code registers one listener per core (the registeredClosedListeners map that #15558 added), so closing the reader should notify the cache once. Instead clearCoreCacheKey also forgets that the listener was registered, the next caching registers a second one, and closing the reader runs the cache's listener twice; every further clear-and-recache cycle adds one more, and on 10.x the same happens after clear().
