SpanTermQuery equality ignores its TermStates, so BooleanQuery merges two same-term span clauses with different statistics and scores only one of them

Two SpanTermQuery clauses on one term built with different statistics (the expert TermStates constructor) compare equal, so BooleanQuery merges them into one clause counted twice: a document scores 0.630 instead of 0.398. Affected since 7.1.0; TermQuery had the same bug, fixed on main by #12354.

The finding in 30 seconds

#

SpanTermQuery scores with the statistics you give it, but its equals and hashCode ignore them, so BooleanQuery's duplicate-clause merge treats two different span clauses as one.

Background: term statistics and duplicate clauses

#
  1. A term's score depends on its statistics, mainly docFreq, the number of documents that contain it: the rarer the term, the higher its score. TermStates holds these statistics.
  2. The expert constructors TermQuery(Term, TermStates) and SpanTermQuery(Term, TermStates) take the statistics from the caller. Core BlendedTermQuery uses this to give several terms adjusted, blended statistics.
  3. Since 7.1.0, BooleanQuery.rewrite merges equal SHOULD or MUST clauses into one clause with weight 2 (a a becomes a^2). That is right only if equal queries score the same.

The finding, step by step

#
  1. You index two one-word documents, "a" and "b", and build two span queries for f:a with the expert constructor SpanTermQuery(Term, TermStates): q1 with the reader's real statistics (docFreq 1), q2 with adjusted statistics (docFreq 2), the way BlendedTermQuery adjusts statistics for TermQuery. Alone, document "a" scores 0.315 for q1 and 0.083 for q2.
  2. You search q1 SHOULD q2 and expect document "a" to score the sum, 0.398, as two different clauses do and as TermQuery does on main.
  3. Instead it scores 0.630, twice q1. SpanTermQuery.equals and hashCode look only at the term, so BooleanQuery's rewrite sees one clause repeated, keeps the first and gives it weight 2.0: (f:a)^2.0. The statistics of q2 are dropped. q1 MUST q2 also scores 0.630.
  4. No error, with assertions on and off; the same document matches and hit counts are unchanged. Only that term's share of the score is off; with BM25, the default, by the same factor (1.58 here) for every matching document.

Who is affected

#

Only code that passes its own statistics to the expert SpanTermQuery(Term, TermStates) and puts two clauses on one term into a BooleanQuery, such as a span version of statistic blending. Lucene's own span rewrites pass real statistics, so their scores do not change; no caller was found in Elasticsearch, OpenSearch or Solr.

Mechanism, terms and numbers493 words

SpanTermQuery(Term, TermStates) scores with the statistics it is given (when they were built for the searcher's top-level reader context), but its equals and hashCode compare only the term. BooleanQuery.rewrite merges equal SHOULD and MUST clauses into one clause with weight Similarity#computeQueryTermWeight(2) (2.0 with the default BM25), so two span clauses on the same term that carry different statistics become one clause counted twice, and the second clause's statistics are silently dropped. In the repro (documents "a" and "b") the clauses alone score 0.31506687 and 0.082873434; their disjunction should score the sum, 0.3979403, but scores 0.63013375. TermQuery had the same defect (#10309), fixed on main by #12354; SpanTermQuery was not touched. Only callers that build their own statistics are hit ("minor" is a reachability call: the scores are silently wrong); matching and hit counts stay correct.

The code (main 5adff78bb168)

#
  1. SpanTermQuery.java:52-59: the expert constructor ("Construct a SpanTermQuery matching the named term's spans, using the provided TermStates") stores the caller's TermStates.
  2. SpanTermQuery.java:81-95, createWeight: when the stored TermStates wasBuiltFor(topContext), it is used as is. SpanWeight.java:101-120, buildSimWeight, takes ts.docFreq() and ts.totalTermFreq() from it (:109-111). So a standalone SpanTermQuery scores with the caller's statistics.
  3. SpanTermQuery.java:204-206: hashCode is classHash() ^ term.hashCode(); :209-211: equals is sameClassAs(other) && term.equals(other.term). The statistics are in neither. This is the fix site.
  4. BooleanQuery.java:134-140: the constructor already counts the SHOULD and MUST clause queries in a Multiset, a HashMap from query to count (Multiset.java:33, :80-82), so two equal queries share one key, the first-added, with count 2. BooleanQuery.java:438-455: rewrite then deduplicates SHOULD clauses (when minimumNumberShouldMatch <= 1) and MUST clauses with deduplicateClauses (:714-758), which sums the boosts per query (boosts.merge, :726, 1 + 1 = 2) and gives the surviving query weight similarity.computeQueryTermWeight(2) (:746). BM25Similarity.computeQueryTermWeight returns the count when k3 < 0, the default (BM25Similarity.java:131-136), hence ^2.0.
  5. Result: 2 × score(q1) instead of score(q1) + score(q2). Both clauses are the same term, so they match the same documents; with BM25 (the default) every matching document gets the same factor on that term's contribution, 2·idf1 / (idf1 + idf2), here 0.63013375 / 0.3979403 = 1.58. Other similarities may not scale by a constant.

Exposure and likelihood218 words
  • Who. Code that calls SpanTermQuery(Term, TermStates) with statistics it built itself (new TermStates or TermStates.build, then register / accumulateStatistics) and puts two clauses on the same term with different statistics into one BooleanQuery, as SHOULD or MUST clauses: for example a span version of BlendedTermQuery's statistic blending whose expansions share a term.
  • Default vs opt-in. Opt-in expert API (TermStates is @lucene.experimental). Everything else is default: codec, IndexWriterConfig, IndexSearcher and BM25. Any index size.
  • What goes wrong. That term's share of every matching document's score is silently wrong, by one constant factor with BM25 (the default); matching documents and hit counts are unchanged, and nothing is thrown.
  • Not affected. Lucene's own producers of the two-argument constructor, the SpanMultiTermQueryWrapper rewrites (SpanMultiTermQueryWrapper.java:180, :226, :321), pass the reader's real statistics, so merging their clauses does not change scores. No query parser builds it (the XML query parser builders use SpanTermQuery(Term)). Code search found no two-argument caller in Elasticsearch, OpenSearch or Solr.
  • Likelihood. Rare: the prior-report searches found no report, though the code has been affected since 7.1.0 (2017).
  • TermQuery on released versions. #12354 is on main and branch_11x only, so on 7.1.0 to 10.6.0 TermQuery merges the same way; the two classes behave differently only on main and branch_11x.

Why it looks unintended

#
  • Lucene fixed the same defect in TermQuery as a wrong-scores bug: #12354 (for #10309) added its TermStates to equals and hashCode.
  • A maintainer on #10309: "Queries shouldn't be considered equal if they might return different scores."
  • SpanTermQuery really scores with the given statistics, and nothing documents that a BooleanQuery may drop them.
The full argument182 words
  • Lucene already called the same defect a bug, for TermQuery. #10309 (LUCENE-9269, "Blended queries with boolean rewrite can result in inconsistent scores", 2020) was fixed by #12354 (3e077fdc076, Rafał Harabień, 2026-01-24): TermQuery.equals and hashCode include perReaderTermState (TermQuery.java:337-349), listed under 11.0.0 Bug Fixes as "Do not merge term queries with different docFreq. Fixes wrong scores" (lucene/CHANGES.txt:360-361). Neither the issue nor the PR mentions spans, and the PR did not touch SpanTermQuery.java.
  • The maintainer's rule. Adrien Grand on #10309 (2020-03-10): "Queries shouldn't be considered equal if they might return different scores."
  • Same pattern fixed before. LUCENE-10026 (#11065, PR #212): CombinedFieldQuery.equals ignored its field weights and was fixed as a bug.
  • The constructor is meant to drive scoring. LUCENE-6466 (#7525), which added it, says "SpanTermQuery can take an optional TermContext in its constructor, similar to TermQuery"; createWeight uses it for scoring; the spans package doc says "Span queries may be freely intermixed with other Lucene queries" (package-info.java:77). No upstream test asserts term-only equality for a SpanTermQuery with TermStates (TestSpanTermQuery.testHashcodeEquals uses only the one-argument constructor).
The devil's-advocate check233 words

The strongest case for "intended", raised as moderate by an independent reviewer from another model family (OpenAI GPT-5.6) and weighed by an intended-behaviour check: the Query#equals javadoc says "Typically a query will be equal to another only if it's an instance of the same class and its document-filtering properties are identical to those of the other instance" (Query.java:95-107), and statistics never change which documents match. Also, TermQuery's expert javadoc says it "will use the provided docFreq" (TermQuery.java:277-280), while SpanTermQuery's says only "using the provided TermStates", so it might be meant as a lookup cache.

Why we think it does not hold: "typically" is not a rule, and BooleanQuery's documented merge ("merging repeated queries into a single clause with a combined boost", BooleanQuery.java:706-713) is only correct if equal queries score the same; the same javadoc argument applied to TermQuery, which the project fixed as a wrong-scores bug. The code does score with the given statistics, and accumulateStatistics is public expert API that core uses for exactly this (BlendedTermQuery). What holds is reachability (no in-tree producer of differing statistics, none found downstream): that makes it Low. The span contract itself is inferred from the TermQuery precedent, not documented for spans, so a maintainer could still say that caller-made span statistics were never a supported scoring contract; fix C (document it) is the fallback then.

Suggested fix

#

Recommended A. Include the TermStates in equals and hashCode (recommended, validated)

Recommended (A): include the TermStates in SpanTermQuery.equals and hashCode, mirroring what #12354 did for TermQuery (+4/-2 lines). The repro passes with assertions on and off, and the whole lucene/queries test task runs with 0 failures.

   @Override
   public int hashCode() {
-    return classHash() ^ term.hashCode();
+    return classHash() ^ term.hashCode() ^ Objects.hashCode(termStates);
   }
 
   @Override
   public boolean equals(Object other) {
-    return sameClassAs(other) && term.equals(((SpanTermQuery) other).term);
+    return sameClassAs(other)
+        && term.equals(((SpanTermQuery) other).term)
+        && Objects.equals(termStates, ((SpanTermQuery) other).termStates);
   }

A. Include the TermStates in equals and hashCode (recommended, validated)

#

SpanTermQuery.java:204-211, +4/-2 lines; java.util.Objects is already imported. It mirrors the change #12354 made to TermQuery.

   @Override
   public int hashCode() {
-    return classHash() ^ term.hashCode();
+    return classHash() ^ term.hashCode() ^ Objects.hashCode(termStates);
   }
 
   @Override
   public boolean equals(Object other) {
-    return sameClassAs(other) && term.equals(((SpanTermQuery) other).term);
+    return sameClassAs(other)
+        && term.equals(((SpanTermQuery) other).term)
+        && Objects.equals(termStates, ((SpanTermQuery) other).termStates);
   }

Trade-offs

  • It inherits TermStates#equals, which compares only docFreq (TermStates.java:264-272, tracked separately as LFV-435): two clauses that differ only in totalTermFreq still merge, as with TermQuery today.
  • SpanTermQuery(term) and SpanTermQuery(term, states) stop being equal, as for TermQuery since #12354.
  • SpanMultiTermQueryWrapper's default scoring rewrite attaches a TermStates to every expanded SpanTermQuery, so the equality and hash of such rewritten queries now follow docFreq, and a cache key built from them can change across reopens. For TermQuery, Adrien Grand judged this acceptable on #10309 ("boolean rewrites are generally used for scoring queries, which are not cached"); maintainers may weigh it differently for spans.
  • Equality then depends on a mutable object: TermStates.register and accumulateStatistics (TermStates.java:139-164) change docFreq, so a query's hash changes if the caller keeps changing its TermStates after building the query, as for TermQuery since #12354.

What the checks validated

  • The repro fails before the change and passes after it, with assertions on and off.
  • The whole :lucene:queries:test task: 514 tests (the repro and the scratch check included), 5 skipped, 0 failures (one seed; not the full Lucene suite and no downstream compatibility check).
  • A scratch check prints q1.equals(q2)=false, rewrites f:a f:a and +f:a +f:a, and 0.3979403 for both the SHOULD and the MUST query.
  • :lucene:queries:checkGoogleJavaFormat passes.

Trade-offs

Also catches a totalTermFreq-only difference, but diverges from how TermQuery does it; fixing TermStates#equals itself (LFV-435) would give A the same coverage.

The method in full79 words

Semi-formal. The obligation checked comes from #10309: a BooleanQuery of two clauses that may score differently must score their sum, so queries that may score differently must not be equal. The proposal was turned into a public-API probe (two same-term clauses with different TermStates, one BooleanQuery, score against the sum), run on main with assertions on and off and on 10.6.0, then reduced to the one JUnit test of the repro and checked independently (see Independent checks).
