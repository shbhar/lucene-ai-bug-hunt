SimpleTextCodec only: the stored-fields, term-vectors and doc-values/norms readers leave their file open when opening a segment fails while the file is read

This affects SimpleTextCodec only, Lucene's plain-text codec for reading and debugging an index, not for production. When DirectoryReader.open fails while a segment's stored-fields, term-vectors, doc-values or norms file is being read, the open throws, as it should, but that file is never closed: one open file per failed open.

The finding in 30 seconds

#

SimpleTextCodec reads part of each of these files while a segment is opened. The stored-fields and term-vectors readers scan the whole file and check its checksum. The doc-values reader, also used for norms, scans the field headers. Each opens its file first. If the scan then fails, no code path closes the file.

Background: three pieces

#
  1. SimpleTextCodec writes every index file as readable text. It exists for reading and debugging an index. Its javadoc says "FOR RECREATIONAL USE ONLY"; production indexes use the default codec.
  2. Opening an index opens each segment, and each segment asks the codec for one reader per kind of file. A reader's constructor opens its file and keeps it open for later searches.
  3. If a reader's constructor fails, the whole open fails and Lucene closes the readers it already holds. A reader that fails inside its own constructor must close its own file, because nobody else has a reference to it yet.

The finding, step by step

#
  1. You write one empty document with SimpleTextCodec, the plain-text codec meant for reading and debugging an index, with compound files switched off so that each file of the segment is on its own. Its stored-fields file _0.fld is 40 bytes of text: doc 0, END and a checksum line.
  2. The file gets damaged. In the test it is replaced by an empty file. You call DirectoryReader.open and expect a CorruptIndexException and no file left open. That is what happens when the segment's postings or field-infos file is damaged the same way.
  3. The exception comes, but _0.fld stays open. Closing the test directory fails with cannot close: there are still 1 open files: {_0.fld=1}. Three failed opens leave three open files.
  4. Why: the reader's constructor opens the file inside a block that closes the reader on failure, and then reads the whole file after that block. A failure during the read is outside the block. The half-built reader was never handed to anyone, so nothing closes its file.
  5. The term-vectors reader (.tvc) has the same shape. The doc-values reader, which also reads norms (.dat, .len), has no such block. An I/O error on a read has the same effect as a damaged file. Search results and stored data are never wrong. The codec's compound-file reader (.scf) has the same defect in a fourth place; this page's test and fix do not cover it.

Who is affected

#

Applications reading a SimpleTextCodec index, when a segment open fails while one of these four files is read on its own (no compound file, or a doc-values update): an I/O error or a damaged file. The codec is opt-in. Each failed open leaves one input unclosed; only a process that keeps retrying accumulates them. Results are never wrong.

Mechanism, terms and numbers2,263 words

SimpleTextCodec only: the plain-text codec whose javadoc says "FOR RECREATIONAL USE ONLY", meant for reading and debugging an index, not for production. The default codec is not affected. When opening a segment fails while the stored-fields file (.fld) is being read, because of a read I/O error or a damaged or cut file, DirectoryReader.open throws, as it should, but the .fld input is never closed. SimpleTextStoredFieldsReader's constructor opens the input inside a block that closes the reader on failure (SimpleTextStoredFieldsReader.java:73-82 on main 781025d6fe32) and calls readIndex, which reads the whole file and checks its footer, after that block (:83). The block therefore guards only openInput, where there is nothing to close yet, and SegmentCoreReaders never receives the reader, so its own failure handling cannot close it. SimpleTextTermVectorsReader has the same shape for .tvc (:83-91). SimpleTextDocValuesReader, which also serves norms, opens its input and scans the field headers with no failure handling at all (:101-205), for .dat and .len.

With the same failure, the codec's postings, points, field-infos and segment-info files and the 24 files of the probe's default-codec index are closed. The effect is one unclosed input per failed open. On a real file system, three failed opens left three file descriptors with NIOFSDirectory, which were gone after garbage collections, and nine mappings with MMapDirectory (three each of .fld, .pst and .len, because the unclosed input keeps the segment's shared arena), which stayed. No search result or stored data is wrong. The stored-fields, term-vectors and norms files and a segment's first doc-values file exist on their own only in a segment that is not a compound file; the test switches compound files off. A doc-values update, which a soft delete is too, writes a new doc-values file next to the segment even when the segment is a compound file, and a failed open leaves that file open in the same way.

This is not the full account for the codec: its compound-file reader (SimpleTextCompoundFormat.getCompoundReader, .scf) has the same defect and is not covered by the test or the fix of this page.

The shape is as old as the classes (2011; 4.0.0 for stored fields and term vectors, 4.2.0 for doc values and norms) and is in every release up to 10.6.0, on branch_11x and on main. A validated three-file fix reads the file inside a block that closes the reader on failure.

The bug

#
  1. SimpleTextStoredFieldsReader's constructor (SimpleTextStoredFieldsReader.java:70-84) opens the input in try { in = directory.openInput(...); } (:73-78), closes the reader in catch (Throwable t) (:79-82) and then calls readIndex(si.maxDoc()) (:83), after the block.
  2. readIndex (:96-109) reads the whole file to record where each document starts (the comment at :93-95: "we read the stored fields file in entirety up-front and save the offsets"). It reads line by line up to END (:100-106) and then checks the checksum footer (:107, SimpleTextUtil.java:82-102).
  3. So the block guards only openInput. If that call throws, in is still null and close() (:194-201) has nothing to release. Every step that can fail with the input open runs at :83, where nothing closes it: a read error, a failed footer check, offsets[upto] out of bounds when the file has more doc lines than the segment has documents (:103) and, with assertions on, the count check (:108).
  4. Nobody else can close it: the constructor never returns, so SegmentCoreReaders never receives the reader, and its decRef() closes only the readers it holds.
  5. In the test the empty _0.fld makes the first line read hit the end of the file (EOFException), which SegmentCoreReaders reports as CorruptIndexException (:141-142). The exception is right. The input opened at SimpleTextStoredFieldsReader.java:75 stays open.
  6. SimpleTextTermVectorsReader has the same shape: try at :83-86, catch at :87-90, readIndex(si.maxDoc()) at :91, the scan and footer check at :103-116.
  7. SimpleTextDocValuesReader opens its input at :104-107 and scans the field headers at :109-200 with no failure handling. It reads .dat and, through SimpleTextNormsProducer (SimpleTextNormsFormat.java:60-64), the norms file .len.
  8. The siblings that do it right: SimpleTextFieldsReader reads its field list inside a block that closes the reader (SimpleTextFieldsReader.java:80-90), and so does SimpleTextPointsReader (SimpleTextPointsReader.java:92-100).

Which exception the caller gets

#

The open fails in every case of the table above, and the exception depends on the file and on the kind of failure: the IOException of the read for a read error, CorruptIndexException for an empty .fld, .tvc or .len, a bare EOFException for an empty .dat. A second probe on the same index changed one byte (xor 0xFF) at each offset in turn, with assertions off:

  • _0.fld (98 bytes) and _0.tvc (205 bytes): CorruptIndexException at every offset.
  • _0.dat (260 bytes): the open succeeds at 199 offsets and fails at 61, with NumberFormatException (36), StringIndexOutOfBoundsException (14), IllegalArgumentException (9) and EOFException (2), never with CorruptIndexException.
  • _0.len (260 bytes): the open succeeds at 199 offsets and fails at 61, with the same three unchecked exceptions (59) and CorruptIndexException (2).

The file stays open in every one of these failing cases.

  • Why .dat and .len differ. Norms are opened inside the block of SegmentCoreReaders that reports an EOFException as CorruptIndexException (SegmentCoreReaders.java:141-142). Doc values are opened by SegmentReader (SegmentReader.java:111), whose handler closes what it holds and rethrows (:113-121).
  • What it means. The caller gets the exception one would expect for a read error, for a damaged or empty .fld or .tvc and for an empty .len. A damaged .dat or .len mostly fails the open with an unchecked exception from parsing a header line. That is a separate property of this codec (the sweep that found the bug shows the same for its field-infos, points and segment-info files) and is not part of this finding.
  • With assertions on, part of these cases end in AssertionError: 8 of the 98 and 8 of the 205 offsets of .fld and .tvc, and 196 of the 224 offsets at which the open then fails for .dat and for .len.
  • Other versions. branch_11x prints the same lines. On the 10.6.0 jars .dat and .len are one byte shorter and the failing counts are the same.

Three failed opens on a real file system

#

Three failed opens of the same broken segment leave three unclosed inputs. On Linux, with the .fld cut by 20 bytes:

  • NIOFSDirectory. Three file descriptors on _0.fld right after the opens, none after five System.gc() calls. That release depends on garbage collection, which has no fixed time.
  • MMapDirectory. Nine mappings right after the opens: three each of _0.fld, _0.pst and _0.len. The postings and norms inputs were opened before the stored-fields reader and were closed when the open failed, but MMapDirectory keeps a segment's inputs in one shared arena that is released only when the last of them is closed (MMapDirectory.java:192, :402-428; RefCountedSharedArena.java:111-124), and the unclosed .fld input keeps it. The nine mappings were still there after five System.gc() calls and after the directory was closed.
  • The default codec, the same steps on its stored-fields file: no descriptor and no mapping at any point.

The counts are the same on branch_11x and on the 10.6.0 jars. They were measured for a cut .fld only.

Reach: where the four files exist on their own

#

The stored-fields, term-vectors and norms files and a segment's first doc-values file exist on their own only in a segment that is not a compound file. A doc-values update adds a doc-values file next to any segment, compound or not.

  • Flushed segments. With the default IndexWriterConfig, a flushed one-document segment is _0.scf, _0.si and segments_1 (main, branch_11x, 10.6.0, 9.12.3). With setUseCompoundFile(false), as in the test, the files are separate.
  • Merged segments. With the default config, forceMerge(1) of three one-document segments wrote separate files on 10.6.0 and 9.12.3, and a compound file on main and branch_11x, where setUseCompoundFile(false) did not change that. On main the codec's compound format decides this for merged segments, by size (IndexWriter.java:5560-5564; CompoundFormat.java:38-57, :163-180).
  • Inside a compound segment. For the files inside it, the three readers read slices of _0.scf. A slice holds no file of its own, and the compound reader, which Lucene holds by then, is closed when the open fails. Executed: with every read inside the sub-files failing, the open fails and nothing stays open.
  • After a doc-values update. An update is always written next to the segment, not into the compound file (ReadersAndUpdates.java:411-415; SegmentDocValues.java:40-45: "gen'd files are written outside CFS"), and the same constructor reads it when the segment is opened. With the default IndexWriterConfig, one updateNumericDocValue on a flushed segment leaves _0.scf, _0.si, _0_1.dat, _0_1.inf and segments_2. Then a read error on _0_1.dat fails the open with IOException, an empty _0_1.dat fails it with EOFException, and both leave _0_1.dat open. A soft delete is a doc-values update (IndexWriter.java:1940-1949): softUpdateDocument on a 20-document segment put _0_1.dat next to _0.scf, with the same two results. The same on main with assertions on, on branch_11x and on the 10.6.0 and 9.12.3 jars. The default codec, same steps: nothing stays open. With the fix, _0_1.dat is closed.

So a compound segment is exposed through its compound reader (next section) and, once it has had a doc-values update or a soft delete, through the doc-values reader.

The same defect in the compound reader (.scf)

#

This page's test and fix are about the three readers. The codec's compound-file reader has the same defect in a fourth place.

  1. SimpleTextCompoundFormat.getCompoundReader opens the compound file (SimpleTextCompoundFormat.java:58), reads the table of its sub-files (:62-104: seeks, line reads, number parsing) with nothing that closes the input on failure (its one try, :70-75, only turns a ParseException of the trailer into CorruptIndexException), and hands the input to the CompoundDirectory it returns only at :106. Why it looks unintended

#
  • The cleanup block exists, but it guards only openInput, where there is nothing to close yet. It can never release anything.
  • The same codec's postings and points readers close their file on this failure. Maintainers added that cleanup in 2013 and 2016.
  • With the same damage, the probe's six other SimpleText files and its 24 default-codec files are closed.
The full argument370 words

No javadoc sentence says what a failed open closes, so this is not a broken documented contract. The intent is in the code and its history.

  • A cleanup block that cannot work. SimpleTextStoredFieldsReader.java:79-82 and SimpleTextTermVectorsReader.java:87-90 close the reader on failure, but they guard only openInput. If that call fails there is no input to close. A block that can never release anything is a misplaced line, not a design.
  • The codec's postings and points readers close on this failure. SimpleTextFieldsReader.java:85-90 and SimpleTextPointsReader.java:93-100 (its compound reader does not; see the full explanation). Maintainers added exactly this: 176aca3a1ee (LUCENE-4653, Michael McCandless, 2013) put the postings reader's up-front scan inside the guarded block, and ff49bd5922f (Michael McCandless, 2016) is titled "make SimpleTextPointReader heroic about exceptions too".
  • Core closes what a failed open had opened. SegmentReader.java:113-121: "we want to explicitly close any subset of things that were opened so that we don't have to wait for a GC to do so." SegmentCoreReaders.java:146-149 does the same for the core readers.
  • Lucene's tests treat an unclosed input as a failure. MockDirectoryWrapper.close() throws "cannot close: there are still N open files" (MockDirectoryWrapper.java:873-888). The format test base that the SimpleText format tests inherit says its exception test "just ensures the codec does not corrupt the index or leak file handles" (BaseIndexFileFormatTestCase.java:621-625).
  • Controls. With the same steps, the codec's postings, points, field-infos and segment-info files and the 24 files of the probe's default-codec index leave nothing open (probe).
  • Why no test saw it. The test directory injects failures when a file is opened, created, written, synced, renamed, deleted or closed (MockDirectoryWrapper.java:203-270, :587-632), not on a read of an open input (MockIndexInputWrapper.java:208-226; its only injection point is close(), :82). Robert Muir pointed this out on LUCENE-4438 (#5504, 2012): "we never throw random exceptions from MockIndexInputWrapper.java when random exceptions are enabled. So any such bugs currently wont be found." The damaged-file suites pin the default codec (TestAllFilesDetectTruncation.java:62 and its four siblings).
  • History. readIndex() has been after the block since the first version of the class (2011). Two later edits of the block, LUCENE-4456 (2012) and #14995 (2025), kept the call where it was; neither discussion mentions it.
The devil's-advocate check246 words

The strongest case for "intended": the codec says "FOR RECREATIONAL USE ONLY" and @lucene.experimental. It is knowingly weaker about damaged files: TestSimpleTextCompoundFormat switches off three inherited damage checks with the comment "SimpleText does not catch broken sub-files in CFS!". No javadoc promises cleanup after a failed open. The shape is from 2011 and survived two edits of the block. The codec's compound reader has the same gap, so these are not the codec's only readers without cleanup. The trigger is an I/O error or a damaged index file, and the failure is already loud.

Why it fails: the javadoc's labels ("plain text index format", "FOR RECREATIONAL USE ONLY", @lucene.experimental) lower what a user can expect of support, speed and stability; that is a reading of them, and none of them says that leaving a file open is intended. The accepted weakness is about detecting damage; in the cases of this page the open already fails (in the test with CorruptIndexException), and what is missing is the cleanup after it. The guarded block shows that cleanup was meant and sits one statement too early. The codec's postings and points readers got this same cleanup from maintainers. A fourth place with the same gap is a reason not to call these the only readers, not a sign of intent. What survives of the argument is "low value": this is a small failure-path cleanup in a debugging codec, and it is rated Low for that reason.

How it was found

#

A fault-injection sweep opened small indexes of 13 codec configurations while breaking one file at a time: one byte flipped per case (261,361 cases), or one read, seek, slice or clone failing (23,194 cases). Its rule: after a failed open no file stays open. In the SimpleText codec these four files broke it. Its SimpleText indexes had no compound file.

The method in full248 words

Method: semi-formal (fault injection and bounded-exhaustive file damage on the real jars).

  • The sweep. For each codec configuration and each index file: the open of the file fails, one header byte is flipped or the file is cut by 20 bytes; byte offsets are flipped one at a time (every offset of a file of up to 20,000 bytes, a fixed stride for larger files; 261,361 cases); the n-th read, seek, slice or clone on the file fails (23,194 cases on main). After every failed open it checks that no input is still open.
  • The signal. On main and on the 10.6.0 jars, with assertions off, every failing read of .fld (78 of 78 tried positions) and of .tvc (83 of 83) left the file open, and so did most failing reads of .dat (75 of 81) and .len (70 of 75). SimpleText's postings, points, field-infos, live-docs and vectors readers and the other formats of the codecs module left nothing open. In the default codec the sweep flagged one site, which is the separate bug LFV-1231. The sweep wrote a compound-file variant only for the default codec, so the SimpleText compound reader was not exercised; its case was found later, when this page was fact-checked.
  • Reduction. The three constructors were read and the signal was reduced to one public-API test that injects a read error. A later minimality check replaced it with the smaller test of the repro, which damages the file and uses only Lucene's test framework.

Summary
You open an index that was written with SimpleTextCodec (Lucene's plain-text codec, which its javadoc labels 'FOR RECREATIONAL USE ONLY'), and reading the stored-fields file (.fld) fails, for example with an I/O error from the disk. You expect DirectoryReader.open to fail with that error and to close every file it had opened, as it does when the same error hits the segment's postings, points or field-infos file. Instead the open fails with the error, as it should, and leaves the .fld file open: the reader's constructor closes its input only when opening the file fails, and reads the whole file after that block, where nothing can close it; the term-vectors reader (.tvc) has the same shape, and the doc-values reader, which also reads norms (.dat, .len), has no such block at all.
