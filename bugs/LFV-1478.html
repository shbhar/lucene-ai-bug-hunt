LatLonShape/XYShape WITHIN over several query geometries tests each one alone, so a shape inside their union is missed

A WITHIN shape query over several geometries checks each stored segment or triangle against each geometry alone, not against their union. A line from lon 0.5 to 3.5 is WITHIN the box lon 0..4 (1 hit) but not WITHIN the overlapping boxes lon 0..3 and lon 1..4 (0 hits).

Summary

Priority

The trigger is rare because it needs edge-sharing or overlapping query parts, which are not a valid OGC MultiPolygon but come naturally when neighbouring regions are queried together, and point documents are not affected.

The finding in 30 seconds

#

Several query geometries are combined into one tree, ComponentTree. For WITHIN, Lucene asks that tree whether it contains each stored piece of a document, and the tree says yes only if one of its geometries contains the whole piece.

Background: three pieces

#
  1. LatLonShape and XYShape store a line as its segments and a polygon as triangles. A WITHIN query keeps a document only if every stored segment and triangle lies inside the query shape.
  2. newGeometryQuery and newPolygonQuery take several geometries. With more than one, they become one ComponentTree, and the query shape is the area they cover together, as it is for INTERSECTS and DISJOINT.
  3. For a point, "inside one of the geometries" and "inside their union" are the same. For a segment or a triangle they are not: it can lie in the union while crossing from one geometry into the next.

The finding, step by step

#
  1. Index one document in a LatLonShape field: the line from (lat 1.5, lon 0.5) to (lat 1.5, lon 3.5). newBoxQuery(field, WITHIN, 0, 3, 0, 4) (lat 0..3, lon 0..4) counts 1.
  2. Ask for the same area as two overlapping boxes: newGeometryQuery(field, WITHIN, new Rectangle(0, 3, 0, 3), new Rectangle(0, 3, 1, 4)). Together they cover lat 0..3, lon 0..4, and the line is inside with half a degree to spare, so you expect 1.
  3. Instead the count is 0. WITHIN keeps a document only if every stored segment passes ComponentTree.containsLine, and that asks each box alone: box 1 ends at lon 3, box 2 starts at lon 1, so both say no and the document is dropped.
  4. The answer even depends on how the line is stored: with one extra vertex at lon 2, each half fits one box and the count is 1. INTERSECTS (1) and DISJOINT (0) over the same boxes answer for their union. Polygon documents, XYShape and two polygons that only share an edge miss the same way; point documents do not.

Who is affected

#

Applications that run a LatLonShape or XYShape WITHIN query over geometries that overlap or share an edge (several drawn search areas, neighbouring regions sent together, a box plus a polygon) against lines or polygons that cross between them. Default settings, silent, every release since 7.5.0. Rare: points, separated geometries and the documented dateline split are unaffected.

Mechanism, terms and numbers624 words

LatLonShape.newGeometryQuery, newPolygonQuery and the XYShape equivalents accept several query geometries. With more than one, the query builds one ComponentTree over them (LatLonShape.java:325-342, ComponentTree.java:360-371 on main f794ff5a505c) and, for WITHIN, checks every stored segment with containsLine and every stored triangle with containsTriangle (LatLonShapeQuery.java:127-162, XYShapeQuery.java:109-144). ComponentTree.containsLine and containsTriangle (ComponentTree.java:198-281) return true only when one geometry contains the whole piece (:221, :266); nothing tests the union. So a line or polygon that lies inside the area the geometries cover, but crosses from one geometry into another, is silently left out: a line from lon 0.5 to 3.5 counts 1 WITHIN the box lon 0..4 and 0 WITHIN the overlapping boxes lon 0..3 and lon 1..4. INTERSECTS and DISJOINT over the same boxes answer for the union, and the same line with one extra vertex at lon 2 is found, so the result depends on how the document is cut into segments. Polygon documents, XYShape and edge-sharing polygons miss the same way; point documents, separated geometries and the documented dateline split do not. Present since WITHIN was added (LUCENE-8447, cbaedb470c8, 7.5.0 in sandbox; core since 8.5.0). A validated fix keeps the per-geometry test as the fast path and falls back to a union test for polygon and rectangle parts; documenting per-geometry WITHIN is the smaller alternative.

Terms

#
  • Stored pieces: LatLonShape.createIndexableFields turns a line into one field per segment and a polygon into one field per triangle; a point is one field. The WITHIN leaf predicate decodes each piece and calls component2D.contains (point), containsLine (segment) or containsTriangle (triangle) (LatLonShapeQuery.java:127-162; XYShapeQuery.java:109-144).
  • All pieces must pass: SpatialQuery adds a document whose piece passes (SpatialQuery.java:452-456) and, for documents with several pieces, excludes it at the first piece that fails (:561-569, then result.andNot(excluded) at :354-356).
  • ComponentTree: the "2D multi-component geometry" built when a query has more than one geometry (ComponentTree.java:24; LatLonGeometry.java:37-44, ComponentTree.java:360-371). A single Rectangle goes to newBoxQuery instead (LatLonShape.java:327-331); CONTAINS over several geometries is split into a MUST of one CONTAINS per geometry (:336-337, :354-370).

The bug

#
  1. ComponentTree.containsLine (ComponentTree.java:210-236) returns true when this node's geometry contains the segment (:221) or a subtree does (:224-233), else false (:235). containsTriangle (:253-281) is the same (:266).
  2. No step asks whether the geometries together cover the piece. The same "any geometry" rule is exact for a point (contains, :87-109) but not for a segment or a triangle.
  3. So a segment that runs from one geometry into another, inside their union, fails, and WITHIN drops the document. The BKD cell around it spans both geometries, so it is not pruned early: relate returns CELL_CROSSES_QUERY (:337-357) and the segment reaches the leaf predicate.

The numbers

#

Stored segment after encoding: lat 1.4999999944, lon 0.4999999702 .. 3.4999999590. Query boxes after quantization (Rectangle2D.java:299-320): A lon 0.0 .. 2.9999999888, B lon 1.0000000242 .. 3.9999999292, both lat 0.0 .. 2.9999999888. Rectangle2D.containsLine is a bounding-box test (Rectangle2D.java:124-134): A fails (3.4999 > 2.9999), B fails (0.4999 < 1.0000), so the tree says false; the single box lon 0 .. 3.9999999292 contains the segment.

Probe on main (one document each): WITHIN the single box 1; WITHIN the two boxes 0; the same line with a vertex at lon 2, 1; INTERSECTS 1, DISJOINT 0; a polygon document lat 1..2, lon 0.5..3.5: single box 1, two boxes 0; a line lon 1.5..2.5 over two polygons sharing the edge lon 2: 0 (one polygon: 1); a point at lon 3.5: 1; XYShape with two overlapping XYRectangles: 0 (one box: 1).

Exposure and likelihood421 words
  • Who. Any WITHIN query with two or more geometries that overlap or share an edge, over line or polygon documents that cross from one into another. Natural sources: several search areas drawn on a map; neighbouring regions sent together, for example a GeoJSON MultiPolygon read with Polygon.fromGeoJSON, which returns the Polygon[] that newPolygonQuery takes (Polygon.java:248-256); a Rectangle plus a Polygon; several circles (newDistanceQuery(field, WITHIN, c1, c2)).
  • Default configuration, silent. Default codec, IndexWriterConfig and searcher (the probe, a main() outside the test framework), one segment, no scale, assertions on and off. No error: the matching document is simply absent.
  • Executed faces. Overlapping boxes with a line document (0) and with a polygon document (0, the containsTriangle path); two polygons that only share the edge lon 2 (0); XYShape with two overlapping boxes (0); each single-geometry control 1. Earlier checks found a Rectangle plus a Polygon, overlapping polygons, a polygon split along its diagonal and two overlapping circles missing the same way.
  • Not affected. Point documents (1); query geometries that are apart; the dateline split the Polygon javadoc recommends (Polygon.java:36), because no stored segment crosses the dateline.
  • Not claimed (boundary contact). A valid OGC MultiPolygon whose parts touch only at a vertex, with a line through that vertex. Usually the encoded line passes just beside the vertex and leaves the union, so 0 is right there. When the vertex is on the encoding grid, the line stays in the closed union and touches its boundary only at the vertex: two polygons lat -50..0 x lon -50..0 and lat 0..50 x lon 0..50 touch at (0,0), and the line (-45,-45)-(45,45) still counts 0 (1 with the suggested fix, 1 for the single box -50..50). Whether such a boundary touch counts as WITHIN is a boundary-semantics question, so this case is not claimed.
  • Likelihood: rare. It needs overlapping or edge-sharing query geometries plus data that crosses their joins; the recorded searches found no public report of it since WITHIN was added in 2018 (Prior reports). Where such queries are used (roads or parcels crossing a district border, several drawn areas), the miss is systematic: every document with a stored segment or triangle that no single geometry contains is dropped.
  • Downstream (read, not executed). Elasticsearch's geo_shape field mapper passes all geometries of a query shape to one LatLonShape.newGeometryQuery, so a WITHIN geo_shape query whose parts overlap or share an edge may reach this code; it may also run a doc-values query instead, which was not checked.

Why it looks unintended

#
  • CONTAINS over several geometries means "contains their union"; INTERSECTS and DISJOINT answer for the union too.
  • The result depends on how the document is stored: the same line plus a vertex at lon 2 matches.
  • LUCENE-8669 tells users to split a region into two edge-sharing polygons; its test expects WITHIN over the pair to act like the region.
The full argument488 words
  • The other relations answer for the union. CONTAINS over several geometries is built on purpose as a MUST of one CONTAINS per geometry (LatLonShape.java:354-370, XYShape.java:263-270): the document must contain them all, that is their union, where a "one member" reading would be a SHOULD. INTERSECTS (1) and DISJOINT (0) over the same two boxes also answer for the union (the probe), but for these two relations "any member" and "the union" give the same answer, so they do not separate the two readings; CONTAINS, the vertex dependence and multi-part documents (next point) do.
  • Representation dependence. The same straight line stored with one extra vertex at lon 2 (segments lon 0.5..2 and 2..3.5, each inside one box) is found: 1 instead of 0 (the probe). A document whose parts each lie in a different query geometry also matches (testWithinDateLine, below). So today's answer is not a consistent "within one member" rule either.
  • Lucene's expectation for a split region. The Polygon javadoc: "Polygons cannot cross the 180th meridian. Instead, use two polygons: one on each side." (Polygon.java:36). LUCENE-8669 (#9715, Nicholas Knize, 2019): "It is therefore up to the calling application / user to split dateline crossing polygons into a MultiPolygon query with two search polygons that share the dateline"; it fixed WITHIN for that pair. Its regression test testLUCENE8669 (edb05314b31; now TestLatLonShape.java:472-525) asserts WITHIN over the two polygons = 1 (:506-507). The later testWithinDateLine (:293-353, added with LUCENE-8620, 2ef2ddd77c5, Ignacio Vera, 2019) asserts the same for the pair (:328-329), and both tests today also expect 1 for the one crossing box (:340-341; :515-516 in testLUCENE8669, added by LUCENE-8736, 55c241d87f4). That split cannot show this bug (no stored segment crosses the dateline); it only states the expectation.
  • Contract. No public javadoc defines WITHIN over several geometries: QueryRelation.WITHIN says "used for WITHIN Queries" (ShapeField.java:122-123); newPolygonQuery "a provided polygon (or array of polygons)" (LatLonShape.java:294-297); newGeometryQuery "a provided geometry (or array of geometries)" (:321-324); XYShape.newGeometryQuery "a provided geometry collection" (XYShape.java:257-259). The GeoJSON parser behind Polygon.fromGeoJSON describes its input as "type: MultiPolygon (union of polygons) is also accepted." (SimpleGeoJSONPolygonParser.java:44, a block comment, not javadoc). The internal Component2D methods promise "return true if this component2D contains the provided line" / "triangle" (Component2D.java:73, :84). So this is undocumented behaviour that contradicts the other relations and LUCENE-8669, not a javadoc violation.
  • Why tests never saw it. Random query polygons are single polygons (BaseSpatialTestCase.java:190-192), and the random tests compute their expected answer with the same Component2D methods (:747-797).
  • History. LUCENE-8447 (#9493) added WITHIN on LUCENE-8435's per-polygon tree walk; LUCENE-9273 (#10313), which added the per-component containsLine/containsTriangle (later commits, the LUCENE-9570 reformat and the #14476 refactor, edited those lines but kept the rule), is a speed-up; neither discusses containment across geometries.
The devil's-advocate check182 words

The strongest case for "intended": WITHIN over an array could mean "within at least one member". LUCENE-9595 (#10635) deliberately chose a component-wise, non-union rule for CONTAINS against indexed geometry collections; Elasticsearch 7.4-7.6 built WITHIN over a geometry collection as a SHOULD of per-member WITHIN queries (7.6.0's code comment: "at least one shape must intersect / contain the indexed shape"), replaced in 7.7 by one newGeometryQuery call for efficiency; edge-sharing or overlapping parts are not a valid OGC MultiPolygon; and Ignacio Vera remarked on the Elastic forum (2020, an INTERSECTS question) that overlapping polygons in a multi-polygon are a bad idea.

Why it fails: the code does not implement "within one member" either (the extra-vertex line and multi-part documents match), so the result depends on vertex placement; the minimal repro is a plain collection of two Rectangles, which no OGC validity rule covers, and polygons that only share an edge miss the same way; every other relation over the same array answers for the union; nothing documents per-member WITHIN. A reviewer may still prefer to document per-geometry WITHIN (Suggested fix, option B).

Suggested fix

#

Recommended Union containment for WITHIN in ComponentTree (validated)

Keep the per-geometry check; when it fails and every query geometry is a polygon or box, split the piece at their edges and test the pieces against the union. Validated: the test passes, 44 geo suites show no new failures, check is clean. It also changes some multi-hole polygon queries. About 215 lines; documenting per-geometry WITHIN is smaller.

@Override
public boolean containsLine(
    double minX, double maxX, double minY, double maxY,
    double aX, double aY, double bX, double bY) {
  if (containsLine(minX, maxX, minY, maxY, aX, aY, bX, bY, ROOT_SPLITX)) {
    return true;
  }
  // no single component contains the segment: it may still lie in their union
  return edges != null
      && Component2D.within(minX, maxX, minY, maxY, this.minX, this.maxX, this.minY, this.maxY)
      && unionContainsSegment(aX, aY, bX, bY);
}
All options and trade-offs3 options · 1,011 words

One fix was built and validated; a documentation-only option and an application-side workaround were not built.

Union containment for WITHIN in ComponentTree (validated) (recommended)

#

Keep today's per-geometry test. Only when it fails, and only if every query geometry is a polygon (holes included), a rectangle or a nested tree, decide by the union:

  • segment: split it at every point where it meets a boundary edge of any geometry; between two split points it is inside or outside each geometry as a whole, so it is in the union exactly when its endpoints and the midpoint of every piece are (the existing union point test ComponentTree.contains);
  • triangle: its three edges must be in the union, and every cell of the triangle cut by the boundary lines that cross it (at most 1024 cells, else the old answer) must have its centroid in the union, which also rejects a triangle that covers a hole of the union;
  • the boundary edges are collected once, on the root, in ComponentTree.create; with circles, lines or points as query parts the list is null and the old answer stays.

One file, ComponentTree.java, +216/-2. The excerpt below joins the method's parameters onto two lines.

@Override
public boolean containsLine(
    double minX, double maxX, double minY, double maxY,
    double aX, double aY, double bX, double bY) {
  if (containsLine(minX, maxX, minY, maxY, aX, aY, bX, bY, ROOT_SPLITX)) {
    return true;
  }
  // no single component contains the segment: it may still lie in their union
  return edges != null
      && Component2D.within(minX, maxX, minY, maxY, this.minX, this.maxX, this.minY, this.maxY)
      && unionContainsSegment(aX, aY, bX, bY);
}

Trade-offs

  • Not small: about 200 lines of new geometry code; a reviewer will want a robustness review of the floating-point splitting (split parameters and centroids in double; slivers between near-coincident crossings could be misjudged, not seen in any run) and of the 1024-cell cutoff.
  • Cost: extra work for pieces that no single component of a ComponentTree with polygon or rectangle parts contains. Such trees are built for multi-geometry queries, but also for the holes of a query polygon with two or more holes (Polygon2D.java:371-375, :381-385) and for a dateline-crossing box (two Rectangle2Ds, Rectangle2D.java:312-317). O(edges near the piece) per such segment over a flat edge list (a real patch would walk each Polygon2D's edge tree). No benchmark was run.
  • Coverage: polygons and rectangles only, so it is a partial remedy: two overlapping circles (newDistanceQuery) still miss with it.
  • Effect outside WITHIN: Polygon2D.intersectsLine and intersectsTriangle ask the hole tree (holes.containsLine / holes.containsTriangle, Polygon2D.java:171, :198). With the fix, a piece covered by two holes together, but by neither alone, no longer intersects the polygon, so INTERSECTS and DISJOINT can change for polygons with two or more holes; by reading, that needs holes that reach or leave the shell's boundary. Executed (fact check): holes that stick out of the shell (shell lat 0..10 x lon 0..10, holes lat 2..8 x lon 8..12 and lon 11..14, a line at lat 5 from lon 9 to 13) give INTERSECTS 1 -> 0 and DISJOINT 0 -> 1, the geometrically right answer but a change outside WITHIN; two overlapping holes inside the shell give the same answer with and without the fix. The dateline box gets the extra work but, by reading, no new answer. For WITHIN the fix only turns "not within" into "within"; cell relations are unchanged. Collecting edges only for the query-level tree would keep hole trees as they are.

Document per-geometry WITHIN

#

State in the javadoc of newPolygonQuery/newGeometryQuery (LatLonShape and XYShape) and of QueryRelation.WITHIN that WITHIN with several geometries tests each stored segment and triangle against each geometry separately, so a shape that crosses from one geometry into another does not match, and that touching or overlapping polygons should be merged first.

Trade-offs

Small and safe, but it keeps the inconsistency with the other relations and the dependence on vertex placement, and puts polygon merging on every application. Not built.

Workaround: merge the query geometries first

#

Applications can merge overlapping or edge-sharing query polygons into one polygon with a geometry library (or send one box when the boxes form a box) before calling Lucene.

Trade-offs

Not a fix: Lucene core has no polygon union operation to do it internally, and it does not help with circles. Not built.

Downstream note

#

An application that uses a multi-geometry WITHIN query as a region or geofence filter silently loses line and polygon documents that cross the inner borders; it never gains extra ones, because a piece that one geometry contains also lies in their union.

How it was found

#

Semi-formal: a differential harness compared Lucene's WITHIN answers with an exact planar reference (the union of the query parts, computed on the decoded coordinates) over millions of random cases, and reported misses for touching, overlapping and split query arrays. The finder traced them to ComponentTree and reduced them to one public-API test.

The method in full168 words

Method: semi-formal.

  • Differential harness. Random query arrays (polygons sharing an edge, overlapping polygons, a polygon split along its diagonal, a rectangle plus a triangle) and random documents were run through LatLonShape and XYShape queries and compared with an exact planar reference: JTS RelateNG on the decoded, encoding-grid-exact coordinates against the union of the query parts, 4.5 to 9.4 million checks per family. It reported WITHIN false negatives for the four array families.
  • Attribution. The finder re-ran the harness in four arms (stock, with the fixes of other registered geo bugs, with this fix, with both): exactly these four signatures disappear with this fix and with no other. An exact rational decode of the repro's coordinates shows the stored line strictly inside the union and inside neither part.
  • Reduction. First to a public-API JUnit test with two edge-sharing polygons; a later minimality check replaced it with the two overlapping boxes of the repro, which have no geometry-validity excuse. Independent reproducers, cross-model reviews and an adjudication checked it (Independent checks).

History

#

Introduced in 7.5.0 (sandbox) by LUCENE-8447 (cbaedb470c8, 2018), which added WITHIN on a per-polygon tree walk; the per-component methods are from LUCENE-9273 (f914e08b364, 8.6.0). In core since 8.5.0. Every executed release from 7.5.0 to 10.6.0, and main, misses the shape.

Versions tested6 rows

Introduced by cbaedb470c8 on master, "LUCENE-8447: Add DISJOINT and WITHIN support to LatLonShape queries" (Nicholas Knize; authored 2018-08-06, committed 2018-08-08; branch_7x 3102c21e004; JIRA patch, migrated as #9493), in 7.5.0 (lucene-sandbox). It defined WITHIN as "every stored triangle is inside" on top of LUCENE-8435's tree walk (18c2300fd61, #9481), which answered for the first polygon that was not outside.

The per-component methods were added by LUCENE-9273 (f914e08b364, branch_8x a001f135f22; Ignacio Vera, 2020-04-20; PR lucene-solr#1341; 8.6.0): containsLine/containsTriangle true if one component contains the whole piece, the same per-geometry rule. ComponentTree itself dates from LUCENE-8746 (68a3886b977, 2019); git blame on today's lines also shows the LUCENE-9570 reformat (2d6ad2fee6d) and the #14476 refactor (6e5b2acc2a6, 2025), which kept the rule. LatLonShape and XYShape moved to lucene-core in 8.5.0 (LUCENE-8621); XYShape has the bug since its first release, 8.2.0 (sandbox). 7.4.0 has no shape API. Not a regression; not new in 10.6.

The repro test needs the 9.1+ test framework; for older releases an earlier edge-sharing version (a line lon 1.5..2.5 over polygons lon 0..2 and lon 2..4) ran its two assertions as a main(). In every failing run the single-geometry control returned 1. "Affected 7.5.0 to 10.6.0" is inferred from the source history; the releases above are the ones executed.

LFV-1478, snapshot of 2026-11-10

Registry title
LatLonShape/XYShape WITHIN over several query geometries misses a line or polygon that lies inside their union but crosses from one part into another, because ComponentTree.containsLine/containsTriangle test each part alone (since 7.5.0 in sandbox; every core release since 8.5.0)
Area
core / geo: LatLonShape and XYShape WITHIN queries over an array of query geometries (ComponentTree.containsLine/containsTriangle, the WITHIN leaf predicates of LatLonShapeQuery and XYShapeQuery)
Priority
Medium, rank 45: Core LatLonShape and XYShape WITHIN queries over two or more query geometries that share an edge or overlap silently miss lines and polygons that lie inside their union but cross from one part into another, with default settings in every core release since 8.5.0 (earlier in sandbox). The trigger is rare because it needs edge-sharing or overlapping query parts, which are not a valid OGC MultiPolygon but come naturally when neighbouring regions are queried together, and point documents are not affected.
Impact class
silent wrong results
Impact note
Hits applications that run a LatLonShape or XYShape WITHIN query over two or more geometries whose parts share an edge or overlap (neighbouring regions passed together as a polygon array or GeoJSON MultiPolygon, a Rectangle plus a Polygon, overlapping polygons or circles) against line or polygon documents that cross from one part into another: with the default codec, IndexWriterConfig and searcher, -ea or -da and no scale, such a document is silently left out although it lies inside the query region; point documents, query parts that are apart, the dateline split that the Polygon javadoc recommends, and a valid MultiPolygon whose parts touch only at a point are not affected.
Summary
You index the line (lat 1.5, lon 1.5)-(lat 1.5, lon 2.5) in a LatLonShape field and run WITHIN over two boxes that share the edge lon 2 (lat 0..3 x lon 0..2 and lat 0..3 x lon 2..4), expecting 1 hit, the answer WITHIN over the single box lat 0..3 x lon 0..4 gives. Instead the count is 0: ComponentTree.containsLine asks each query polygon alone whether it contains the whole segment, neither does, and WITHIN drops the document, while INTERSECTS, DISJOINT and CONTAINS over the same array answer for the union. XYShape, polygon documents (containsTriangle) and overlapping parts fail the same way.
Introduced
cbaedb470c8 (master; branch_7x backport 3102c21e004) [read: history clone; release boundary executed: 7.4.0 has no LatLonShape, 7.5.0 fails] LUCENE-8447 'Add DISJOINT and WITHIN support to LatLonShape queries' (migrated issue apache/lucene#9493; JIRA patch, no GitHub PR; by Nicholas Knize (nknize)): WITHIN = poly2D.relateTriangle(...) == CELL_INSIDE_QUERY for every indexed triangle, on top of the LUCENE-8435 tree walk (18c2300fd61 / d85defbedc5, apache/lucene#9481) that returns the first component's non-OUTSIDE answer, so a segment crossing from one polygon into another was never inside. The current lines come from LUCENE-9273 (f914e08b364 / a001f135f22, 8.6.0, apache/lucene#10313, PR lucene-solr#1341, by Ignacio Vera (iverase)): ComponentTree.containsLine and containsTriangle return true only if one component contains the whole segment or triangle, the same per-part rule. Not a regression: there is no earlier working version. (2018-08-06 (author date of cbaedb470c8; committed 2018-08-08); current code 2020-04-20 (f914e08b364))
