LatLonDocValuesField.newSlowGeometryQuery keeps the caller's array, so queries built from one refilled array compare equal and BooleanQuery merges them

Two doc-values geometry queries built from one array that you refill in between still match their own regions but compare equal, so BooleanQuery keeps only one: an OR of two squares finds 1 document instead of 2. Affected: 8.8.0 through 10.6.0, and main.

The finding in 30 seconds

#

LatLonDocValuesField.newSlowGeometryQuery matches points stored as doc values against shapes such as rectangles. Its javadoc calls it slow and suggests pairing it with LatLonPoint.newGeometryQuery. Lucene merges queries that are equals(), so an equal pair must match the same documents.

  1. Index two points with LatLonDocValuesField: doc 0 at (0, 0) and doc 1 at (0, 10). Put a 2x2-degree square around doc 0 into LatLonGeometry[] buf and build q0 = LatLonDocValuesField.newSlowGeometryQuery("loc", WITHIN, buf).
  2. Write a square around doc 1 into the same slot, buf[0], and build q1 the same way. Each query alone finds 1 document.
  3. Search q0 OR q1 (two SHOULD clauses). You expect 2 documents; you get 1, with no error. Built from two fresh arrays, the same OR finds 2.
  4. Why: the query builds its matching shape once, in its constructor, but keeps your array without a copy, and equals, hashCode and toString read the array as it is now. So q0.equals(q1) is true and BooleanQuery drops the "duplicate". The points query and the XY doc-values query copy their array.

Who is affected

#

Applications that pass an explicit array to newSlowGeometryQuery (or newSlowPolygonQuery) and refill it to build further queries on the same field, for example a loop over regions through one scratch array. For INTERSECTS, WITHIN and DISJOINT only the slow query used on its own is hit; the IndexOrDocValuesQuery pairing stays correct. Plain varargs calls are safe.

Mechanism, terms and numbers546 words

LatLonDocValuesField.newSlowGeometryQuery(field, relation, LatLonGeometry...) passes the caller's array straight to LatLonDocValuesQuery, whose constructor stores it without a copy and builds the matching shape (component2D) from it once. INTERSECTS, WITHIN and DISJOINT match on that snapshot, but equals, hashCode and toString read the array as it is now, and CONTAINS (Points only) rebuilds its shapes from it for every segment. So when an application refills one array between two calls, the first query keeps matching the first region but compares equal to, hashes like and prints as the second. BooleanQuery de-duplicates equal clauses: an OR of two squares finds 1 document instead of 2, and a FILTER pair of two DISJOINT squares returns more documents than it should. That goes against what Query#equals asks for (typically, equal queries have identical document-filtering properties). The points query and the XY doc-values query already copy their array; the same one-line geometries.clone() fixes it. Affected: every release from 8.8.0 through 10.6.0, and main. The trigger is narrow: explicit reuse of one array with the slow doc-values factory and, except for CONTAINS, the slow query used on its own.

Exposure and likelihood268 words
  • Who is hit. Code that passes an explicit LatLonGeometry[] and then writes new geometries into the same array to build another query on the same field. A Polygon[] passed to newSlowPolygonQuery (LatLonDocValuesField.java:228-230) goes the same way, but Polygon itself is marked @lucene.experimental (Polygon.java:41); the repro uses Rectangle.
  • Only on its own, except CONTAINS. For INTERSECTS, WITHIN and DISJOINT the merge needs the slow query used on its own, for example on a field indexed only with doc values. In the javadoc-recommended IndexOrDocValuesQuery pairing with LatLonPoint.newGeometryQuery, the points half copies its array, so two wrappers stay unequal: the OR finds 2 of 2. CONTAINS reaches the pairing: a CONTAINS(0, 0) pair whose array was later refilled to (0, 10), under a selective lead clause that lets the doc-values half run, counts 1 instead of 0.
  • Not affected: plain varargs calls such as newSlowGeometryQuery("loc", WITHIN, rect), whose array the compiler creates per call; one Rectangle with INTERSECTS, which becomes a box query; the LatLonPoint queries and the XY doc-values query, which copy.
  • What happens. Silent wrong hits: missing documents for an OR, extra documents for a FILTER pair. No special setup: outside the test framework, a plain main() with new IndexWriterConfig() (so the default codec) and new IndexSearcher(reader) also counts 1; the JUnit runs use the framework's randomized codec. No query cache needed; assertions on or off.
  • Scale. The cause is query equality, which never reads the index, so index size should not matter (by reading); executed on a two-document index.
  • How likely. Rare: ordinary call sites build a fresh array per call.

Why it looks unintended

#
  • Query#equals asks that equal queries have identical document-filtering properties; these two match doc 0 and doc 1.
  • The query disagrees with itself: it matches on a shape built in the constructor but compares the live array: they diverge once it is refilled.
  • Its siblings, the points query and the XY doc-values query, copy the same argument with geometries.clone().
The full argument260 words
  • The contract. Query#equals: "Override and implement query instance equivalence properly in a subclass. This is required so that {@link QueryCache} works properly. Typically a query will be equal to another only if it's an instance of the same class and its document-filtering properties are identical to those of the other instance." (Query.java:95-101).
  • Self-inconsistent. The constructor snapshots the array for matching (LatLonDocValuesQuery.java:87) but equals, hashCode and toString read the live array (:98, :110, :118), so the two diverge as soon as the caller writes to the array.
  • The siblings copy. SpatialQuery.java:83 and XYDocValuesPointInGeometryQuery.java:60 (since LUCENE-9238). The points query has copied its array since LUCENE-7153 (81c83b44318, 2016); LUCENE-9552 (8bfbed8d4cd, 2020) generalised both lat/lon queries to geometry arrays and kept the copy only in the points one; LUCENE-9641 (14009f4424d) carried the uncopied array into LatLonDocValuesQuery.
  • Project direction. In 2015 LUCENE-6321 (#7382, make Term more defensive) and LUCENE-6369 (#7429, make queries more defensive and clone deeply) were both closed Won't Fix in favour of immutable queries, which LUCENE-6590 (#7648, fixed in 5.4) delivered; Adrien Grand closed #7429 with "Superseded by #7648: queries should now be immutable." A query whose equals reads a caller-owned array is not immutable (our reasoning). #12158 (2023) made KeywordField#newSetQuery clone its argument because a query sorted it in place.
  • Nothing pins the current behaviour. The factory's javadoc says only "array of LatLonGeometries. must not be null or empty" (LatLonDocValuesField.java:243); the introducing PR and its JIRA issue do not discuss the copy.
The devil's-advocate check191 words

The case: no javadoc promises a copy, and reusing an argument array after handing it to a library is caller misuse. In LUCENE-6321 a maintainer called changing term bytes after building a query "an abuse case", and IndexSearcher.setQueryCache says "When using a query cache, queries should not be modified after they have been passed to IndexSearcher." (IndexSearcher.java:268-269).

Why it is weak here: no Query object is modified; the array is refilled before either query reaches a searcher; the repro runs with the query cache off. In the same LUCENE-6321 comment that says "abuse case", Robert Muir adds: “But maybe its a good idea to do a little "extra" clone work to make these core queries defensive.” And once the caller writes to the array, the query's matching and its equals describe different regions. The defect does need that write after the call. The verifying reviewers rated this case weak; a later cross-model check of the brief rated it moderate, because the trigger is narrow and the recommended pairing avoids it. A maintainer may still answer "do not reuse the array"; the one-line copy is cheap and matches the siblings.

Downstream note

#

Products that build several region filters for one doc-values-only geo field through one reused array can silently return too few (OR) or too many (FILTER) hits.

How it was found

#

Semi-formal: a proof-obligation check asked whether LatLonDocValuesQuery's equals and hashCode cover the same state its matching uses. They do not: matching uses a shape built once, equality the caller's uncopied array. A JUnit test on main turned that into a wrong count.

The method in full126 words

Method: semi-formal (a proof-obligation check of the Query#equals/hashCode contract against the state the query's matching reads, witnessed by an executable repro).

  • Obligation. Equal queries must filter the same documents (Query.java:95-104), so every field matching reads must be covered by equals, and that state must not change after construction.
  • Finding. Matching reads component2D, built once in the constructor; equals/hashCode read geometries, the caller's array, kept without a copy. The obligation fails as soon as the caller refills the array.
  • Witness. A one-test JUnit on the stock main jars: the OR of two queries built from one refilled array finds 1 document instead of 2, with assertions on and off. A probe added the FILTER, hash/toString and CONTAINS effects.

History

Introduced by LUCENE-9641 (14009f4424d, 2021-01-08), which built the matching shape once in the constructor but kept the uncopied array for equality; first release 8.8.0. Every release run from 8.8.0 to 10.6.0 fails, and so does main; 8.7.0 lacks the API.

Versions tested8 rows

Read, not run: the source of all 36 local release tags in the range (8.8.0, 8.8.1, and every 9.x and 10.x tag through 10.6.0) has the same four lines: the uncopied assignment, the once-built component2D, and the array-based equals and hashCode. Applications that call LatLonDocValuesField.newSlowGeometryQuery (or newSlowPolygonQuery, which delegates to it) with an explicit array and then write new geometries into that same array to build another query on the same field, for example a loop that ORs or excludes several regions through one scratch array; default IndexWriterConfig, codec and searcher, no query cache, with -ea and -da; BooleanQuery then silently merges the clauses that compare equal (an OR of two regions finds only the first region's points; a FILTER pair of two DISJOINT rectangles returns docs [1, 2] instead of [2]); for INTERSECTS, WITHIN and DISJOINT this needs the slow query used on its own (for example on a field indexed only with doc values), because in the javadoc-recommended IndexOrDocValuesQuery pairing the points half copies its array and keeps the pair unequal, while a CONTAINS query reaches that pairing through its doc-values half; single-Rectangle INTERSECTS queries are not affected (they become box queries); ordinary scale; every release from 8.8.0 through 10.6.0.
Summary
You build several lat/lon doc-values geometry queries in a loop by writing each region into one scratch LatLonGeometry[] and calling LatLonDocValuesField.newSlowGeometryQuery(field, relation, scratch), then OR them in a BooleanQuery. You expect each query to stay the region it was built from, as LatLonPoint.newGeometryQuery and XYDocValuesField.newSlowGeometryQuery do, since both copy the array. Instead LatLonDocValuesQuery keeps a reference to your array: it matches on a shape it captured when it was built, but equals, hashCode and toString read the array's current contents, so both queries compare equal, BooleanQuery de-duplicates them, and an OR of WITHIN(square around doc 0) and WITHIN(square around doc 1) counts 1 document instead of 2.
