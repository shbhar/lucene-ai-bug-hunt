spatial3d points, planes and Geo3DPoint queries are equal for 0.0 and -0.0 but have different hash codes

Geo3DPoint.newDistanceQuery at latitude 0.0 and at -0.0 gives two queries that are equals but whose hash codes differ by 2^31: spatial3d's Vector, behind every GeoPoint, compares coordinates with == but hashes their bits. So the query cache and hash sets see two queries; the tested hits stayed the same.

The finding in 30 seconds

#

This row covers spatial3d's own classes (the related rows LFV-1335 and LFV-1337 cover the queries module and core). Vector.equals compares x, y, z with ==; Vector.hashCode hashes Double.doubleToLongBits of each. GeoPoint inherits both, and so does every shape and query built from points. Plane and four slice and degenerate shapes repeat the pair on their own fields.

Background: two zeros, and how hash lookups work

#
  1. Java's double has two zeros. 0.0 == -0.0 is true, but their bit patterns differ: Double.doubleToLongBits gives 0x0000000000000000 and 0x8000000000000000.
  2. A HashMap, a HashSet or Lucene's query cache compares hash codes first and calls equals() only when they match. So equal objects must have equal hash codes, or the lookup misses.

The finding, step by step

#
  1. You build a = Geo3DPoint.newDistanceQuery("g", PlanetModel.WGS84, 0.0, 10.0, 1000.0) and b, the same call with latitude -0.0 (a computed zero such as -1 * 0.0, or a parsed "-0"). The latitude check accepts -0.0.
  2. Both queries wrap a circle around the same centre point: x = 0.985909609096169 and y = 0.17384246462339042 in both, z = 0.0 in a and -0.0 in b. a.equals(b) is true, because the point's equals compares coordinates with ==, and 0.0 == -0.0.
  3. You expect a.hashCode() == b.hashCode(): Java requires it for equal objects, and Query's javadoc asks for it so that the query cache works.
  4. Instead the point's hashCode hashes the coordinates' bits, 0x0000000000000000 for 0.0 and 0x8000000000000000 for -0.0: the hash codes come out as 209447998 and -1938035650, exactly 2^31 apart.
  5. So hash lookups miss. On a 5-document index with a cache-everything policy, counting a and then a fresh copy of a gives 1 cache entry and 1 hit; counting a and then b gives 2 entries and 0 hits, and a HashSet keeps both. Both queries match the same 5 documents with the same scores.

Who is affected

#

Applications using the spatial3d module (@lucene.experimental entry points) that build the same query or shape with both 0.0 and -0.0 (a negated zero, a parsed "-0") and rely on the query cache or their own hash maps. Every release since 5.2.0, assertions on or off. Only cache misses and duplicate entries; executed examples kept the same hits and scores.

Mechanism, terms and numbers670 words

In the spatial3d module, Vector.equals compares other.x == x && other.y == y && other.z == z (Vector.java:579), under which 0.0 == -0.0, while Vector.hashCode hashes Double.doubleToLongBits of the same fields (:582-593), which differ for the two zeros. GeoPoint extends Vector without overriding either method, shapes compare and hash their points, and PointInGeo3DShapeQuery hands both methods to its shape. So Geo3DPoint.newDistanceQuery at latitude 0.0 and at -0.0 (a legal input: it passes GeoUtils.checkLatitude and keeps its sign through the degrees-to-radians conversion) gives two equal queries whose hash codes are exactly 2^31 apart. That breaks the Object.hashCode contract, which Query's javadoc requires "so that QueryCache works properly" (Query.java:95-116). Plane (D), GeoLongitudeSlice and GeoWideLongitudeSlice (leftLon, rightLon), GeoDegenerateLatitudeZone (latitude) and GeoDegenerateLongitudeSlice (longitude) repeat the same pair on their own fields, so box queries and the shape factories show it too. The query cache keeps a second entry with no hit and hash sets hold both; in every executed example hits, counts and scores were unchanged. It has been there since the first geo3d commit (2015) and is in every release from 5.2.0 through 10.6.0 and on main. Comparing with Double.compare in equals, as #13301 did for the core geo classes in 2024, fixes it.

The code

#
// geom/Vector.java (GeoPoint extends Vector and overrides neither method)
public boolean equals(Object o) {
  if (!(o instanceof Vector other)) {
    return false;
  }
  return (other.x == x && other.y == y && other.z == z);   // :579  0.0 == -0.0
}

public int hashCode() {
  int result;
  long temp;
  temp = Double.doubleToLongBits(x);                        // :586
  result = (int) (temp ^ (temp >>> 32));
  temp = Double.doubleToLongBits(y);
  result = 31 * result + (int) (temp ^ (temp >>> 32));
  temp = Double.doubleToLongBits(z);                        // 0x0 vs 0x8000000000000000
  result = 31 * result + (int) (temp ^ (temp >>> 32));      // adds 0 vs 0x80000000
  return result;
}

How the distance query reaches it

#
  1. Geo3DPoint.newDistanceQuery (Geo3DPoint.java:122-130) calls Geo3DUtil.fromDistance (Geo3DUtil.java:152-162), which checks the latitude with GeoUtils.checkLatitude (GeoUtils.java:85-86: NaN or a value outside [-90, 90] throws; -0.0 passes), converts it with degrees * RADIANS_PER_DEGREE (Geo3DUtil.java:61-63, which keeps the sign) and builds a GeoStandardCircle (GeoCircleFactory.java:38-47).
  2. The circle's centre is new GeoPoint(planetModel, lat, lon) (GeoStandardCircle.java:65). Its z comes from sin(lat), so it is 0.0 or -0.0; x and y come from cos(lat) and are identical.
  3. GeoStandardCircle.equals compares the centres (:233) and hashCode adds center.hashCode() (:239); PointInGeo3DShapeQuery hands equals and hashCode to its shape (:129-142).
  4. Why exactly 2^31. z's folded bits are 0 or 0x80000000; every later step multiplies by 31, an odd number, and adds the same other terms, so the difference stays 0x80000000 modulo 2^32. The values themselves are deterministic: they use only the class name, the field name and the doubles.

Exposure and likelihood330 words
  • Who is hit. Code that ends up with both zeros for one coordinate. -0.0 comes from arithmetic (-1 * 0.0, Math.rint(-0.4)) or from Double.parseDouble("-0"). Queries that all use the same zero are consistent with each other.
  • Default vs opt-in. The separate spatial3d module. Its entry points Geo3DPoint and PointInGeo3DShapeQuery and the value classes Vector, GeoPoint and Plane are @lucene.experimental (Geo3DPoint.java:42, PointInGeo3DShapeQuery.java:42, Vector.java:22, GeoPoint.java:26, Plane.java:24); the four slice and zone classes carry no such tag. No configuration is needed beyond that.
  • Effect. Equality and caching only. In a probe on a 5-document index with a cache-everything policy, a then b left 2 cache entries and 0 hits, where a then an equal copy of a left 1 entry and 1 hit; a HashSet and a HashMap keyed by a miss b. Both queries returned the same 5 documents with the same scores; a miss only means the cache computes the query again. A different query is never served a cached result: the bug only makes equal objects look different.
  • Inside Lucene. spatial3d calls these equals methods explicitly only from other equals methods. Its own hash-based structures are the polygon-edge sets and maps of GeoPolygonFactory and GeoComplexPolygon, whose edges use identity (GeoPolygonFactory.java:1724-1745, GeoComplexPolygon.java:912), and the SidedPlane-keyed prevBrotherMap / nextBrotherMap of GeoConvexPolygon and GeoConcavePolygon, whose keys compare and hash through Plane and Vector (SidedPlane.java:338-359). Those maps are filled and read only with the polygon's own edge planes (GeoConvexPolygon.java:292-293, :504-506; GeoConcavePolygon.java:300-301, :520-526), so signed zeros, and either fix, can change a lookup there only for two edges of one polygon that lie on exactly the same sided plane and differ just in the signs of zeros (or, under fix A, hold NaN). No internal effect was found, and the whole spatial3d test suite passes with either fix.
  • Scale. None needed: one pair of queries. Likelihood: contrived, hence priority Low.

Why it looks unintended

#
  • Java's Object.hashCode contract and Query's javadoc ("required so that QueryCache works properly") demand equal hash codes for equal queries; Lucene's QueryUtils.checkEqual asserts both together.
  • The core counterpart, LatLonPointDistanceQuery, compares its doubles by their bits, consistent with its hash.
  • Lucene fixed the same -0.0 mismatch in five core geo classes (#13292 / #13301) and did not touch spatial3d.
The full argument173 words
  • The contract. Object.hashCode: "If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result" (JDK 25 Object.java:81-84). Query.java:95-116: "Override and implement query hash code properly in a subclass. This is required so that QueryCache works properly."
  • Lucene's test oracle. QueryUtils.checkEqual asserts assertEquals(q1, q2) and assertEquals(q1.hashCode(), q2.hashCode()) together (QueryUtils.java:104-107).
  • The core convention. LatLonPointDistanceQuery.equalsTo compares latitude, longitude and radius by Double.doubleToLongBits (LatLonPointDistanceQuery.java:362-367).
  • In-module precedent. SidedPlane.equals, in the same package, already compares its sigNum with Double.compare (SidedPlane.java:349).
  • Upstream precedent. #13292 / #13301 (1c3c0942270, 2024): "when using == to compare the floats -0.0 and 0.0 they will be considered equal but their hashcode is different", fixed with Float.compare/Double.compare in Point, Circle, Rectangle2D, XYPoint and XYCircle.
  • History. The == lines come from the first geo3d commit and were never discussed; later edits kept them. No javadoc, test, CHANGES or MIGRATE entry treats -0.0 specially.
The devil's-advocate check98 words

The strongest case: latitude 0.0 and -0.0 are the same place, so equals returning true is geometrically right; the entry points and value classes are @lucene.experimental; and the only cost is a duplicate cache entry.

Why it fails: that justifies equals being true, not a different hash code. @lucene.experimental relaxes API stability, not the Object contract, and -0.0 is a legal input that passes the coordinate checks. The small effect limits the priority (Low), not the verdict. Every verifier rated the bug real; two executed reviews by another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Compare with Double.compare in equals (six classes)

Compare with Double.compare(a, b) == 0 in equals of Vector, Plane and the four slice and zone shapes, matching their bit-based hashCode, as #13301 did for core geo. Validated with gradle: the repro passes with assertions on and off; the whole spatial3d suite (182 tests) and :lucene:spatial3d:check -x test pass.

Compare with Double.compare in equals (six classes) (validated by the checks) (recommended)

#

In equals, replace each a == b on a double field with Double.compare(a, b) == 0, which agrees with doubleToLongBits in hashCode: Vector (x, y, z), Plane (D), GeoLongitudeSlice and GeoWideLongitudeSlice (leftLon, rightLon), GeoDegenerateLatitudeZone (latitude), GeoDegenerateLongitudeSlice (longitude). hashCode is unchanged. Trade-offs

A choice of meaning, not only a contract repair: a point at latitude -0.0 is no longer equal to one at 0.0, so the two queries can occupy separate cache entries, now consistently with equals. NaN coordinates, which the raw Vector and Plane constructors accept unchecked (Vector.java:60-64, Plane.java:53-56), become equal to each other, as with Double.equals. Inside spatial3d it can change a lookup only in the brother-map case under Inside Lucene. SidedPlane.equals already compares sigNum this way (SidedPlane.java:349).

Hash -0.0 like 0.0 (six classes) (validated by the checks)

#

Add a package-private helper static long hashBits(double v) { return Double.doubleToLongBits(v == 0.0 ? 0.0 : v); } to Vector and use it for the same fields in the six hashCode methods; equals is unchanged.

Trade-offs

Keeps today's "the two zeros are one point" meaning, so equal queries can reuse one cache entry. A slightly larger diff (a helper plus six call sites); hash codes change only for -0.0. Inside spatial3d it can change a lookup only in the brother-map case under Inside Lucene.

What the checks validated

Gradle, the same worktree: the repro passes with assertions on and off; the whole spatial3d suite, 182 tests, 0 failures, 3 skipped; :lucene:spatial3d:check -x test passes; the sweep shows 0 violations, all 14 pairs equal with equal hash codes.

Downstream note

#

A service that builds these queries from client coordinates gets at most one extra, bounded cache entry for such a query; results do not change.

How it was found

#

A pattern-transfer review looked for the equals/hashCode mismatch on signed zero that #13301 fixed in core geo, at other sites. A bytecode scan of the spatial3d jar flagged equals methods that compare doubles with == while hashCode hashes their bits; an executed sweep of the public factories and a one-test JUnit confirmed it.

The method in full138 words

Method: semi-formal (a known defect shape transferred to other code, then a static scan and executed checks), on main 5adff78bb168, 2026-11-04.

  • The pattern: equals compares a float/double field with == while hashCode hashes its bits, which disagree only for 0.0 and -0.0. #13301 fixed it in core geo in 2024.
  • A bytecode scan of the spatial3d jar listed every equals with such a comparison whose hashCode hashes the same field; inputs that only take positive values (a circle's cutoff angle, a radius) were set aside. An executed sweep of the public factories then found 14 violating pairs, and the distance-query pair became the one-test repro.
  • An independent reproducer and two executed reviews by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier and an adjudication re-ran the repro.

LFV-1341, snapshot of 2026-11-07

Registry title
spatial3d Vector (and so GeoPoint and the Geo3DPoint distance and box queries), Plane and the longitude-slice and degenerate latitude/longitude shapes compare doubles with == in equals() but hash Double.doubleToLongBits, so objects built with 0.0 and -0.0 are equal yet have different hash codes (since 5.2.0)
Area
spatial3d / geom value classes and Geo3DPoint queries (equals and hashCode contract)
Priority
Low, rank 1029: Spatial3d points, planes, shapes and the Geo3DPoint distance and box queries treat 0.0 and -0.0 as equal but hash them differently, so the query cache and hash structures keep two entries, in every release since 5.2.0. Hits and scores stay identical and it needs a computed negative-zero coordinate in the spatial3d module, so it is contrived.
Impact class
minor
Impact note
Only applications that build the same spatial3d query or shape twice, once with a 0.0 and once with a -0.0 latitude or longitude (Geo3DPoint.newDistanceQuery, Geo3DPoint.newBoxQuery and the public geom factories accept -0.0: it passes GeoUtils.checkLatitude/checkLongitude and survives the degrees-to-radians conversion), and then rely on the two being one object in a hash-based structure are hit, with -ea and -da, at any size, in every release from 5.2.0 through 10.6.0 and on main: the two equal queries take two entries in an LRUQueryCache with no hit (a probe with an always-cache policy: cacheSize=2, hitCount=0), and hash sets and maps keyed by these queries, points or shapes miss and can hold both; hits, counts and scores do not change (5 = 5 in the same probe), and an unequal query is never served a cached result.
Summary
You build Geo3DPoint.newDistanceQuery("g", PlanetModel.WGS84, 0.0, 10.0, 1000.0) and the same query with latitude -0.0: equals() says they are equal, because the circle's centre GeoPoint is compared by Vector.equals, which uses ==, and under == the two centres (whose z is +0.0 and -0.0) are equal. By the Object#hashCode contract, which Query's javadoc asks subclasses to honour so that the query cache works, their hash codes must then be equal, but they differ by exactly 2^31, because Vector.hashCode hashes Double.doubleToLongBits(z), and those bits differ for the two zeros. Plane (its D) and the longitude-slice and degenerate latitude/longitude shapes have the same == versus doubleToLongBits pair, so box queries and the geom factories show it too, while hits and scores stay the same.
