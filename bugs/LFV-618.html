MultiPassIndexSplitter cannot split an index that has a soft-deletes field or a parent field

MultiPassIndexSplitter opens every part's writer with a bare IndexWriterConfig and takes no config, so addIndexes rejects any index whose field infos mark a soft-deletes field (since 7.4.0) or a parent field (since 9.10.0): the split throws IllegalArgumentException before any part gets a document. Two documents and one soft update are enough.

The finding in 30 seconds

#

Each part's writer gets new IndexWriterConfig(null): no soft-deletes field, no parent field, and split() has no way to pass one. addIndexes checks the input's fields first and refuses the marked field, so the split stops before copying anything.

Background

#
  1. The tool. MultiPassIndexSplitter cuts one index into N parts. For each part it hides the other parts' documents and copies the rest into a new writer with IndexWriter.addIndexes.
  2. Soft deletes. With IndexWriterConfig#setSoftDeletesField("soft"), softUpdateDocument marks the old copy deleted through a doc-values field instead of deleting it. The index's field infos record that soft is the soft-deletes field.
  3. The check. Since 7.4.0 a writer refuses to take in a field marked as soft-deletes field unless its own config names the same field. Since 9.10.0 the same holds for the parent field set with setParentField.

The finding, step by step

#
  1. You index a and b with setSoftDeletesField("soft"), then replace b with softUpdateDocument. The index now has 2 live documents.
  2. You split it into 2 parts with new MultiPassIndexSplitter().split(reader, parts, true) and expect a in one part and b in the other: split() says the source "can have deletions".
  3. Instead it throws IllegalArgumentException: this index has [soft] as soft-deletes already but soft-deletes field is not configured in IWC, with assertions on and off, and nothing is split.
  4. Why: each part's writer gets new IndexWriterConfig(null), which names no soft-deletes field, and you cannot pass one. Since 7.4.0 addIndexes refuses a soft-deletes field the writer does not name, since 9.10.0 also a parent field: a 12-document index with one block under setParentField fails the same way.
  5. The source is only read and no part gets a document. Giving each part the input's two field names fixes it.

Who is affected

#

Users of the misc MultiPassIndexSplitter, by command line or split(), on an index whose segments carry a soft-deletes field (7.4.0+) or has a parent field (9.10.0+; required since 10.0 for index sorting with blocks). Every split fails at once, at any size. Nothing is damaged; PKIndexSplitter with configs is the workaround.

Mechanism, terms and numbers666 words

MultiPassIndexSplitter (lucene/misc) splits an index into N parts by copying the input's segments, with the other parts' documents hidden, into one new IndexWriter per part. Every part's writer is opened with new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE), and split(IndexReader, Directory[], boolean), the only API, takes no config. Since LUCENE-8335 (7.4.0) IndexWriter.addIndexes rejects an incoming field marked as the soft-deletes field unless the writer's config names the same field, and since #12829 (9.10.0) the same holds for the parent field. So the splitter throws IllegalArgumentException on every index whose segments still mark a soft-deletes field (in practice any index with a soft update or soft delete in a surviving segment; the mark survives merges), and on every index written with setParentField, in both split modes and from its command line. It fails before any part gets a document; the source is only read. No release has been able to split an index whose segments carry the soft-deletes mark: 7.4.0 shipped soft deletes and the check together. Configuring each part with the input's two field names fixes it.

The code (main 645d4fe14a20)

#
  1. The split. split() (MultiPassIndexSplitter.java:70) wraps the input in a private FakeDeleteIndexReader (:81), and for each part marks every document outside the part as deleted (:84-107), opens the part's writer with new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE) (:108-109) and copies the leaves with w.addIndexes(...) (:113). The command line main() opens a plain DirectoryReader (:157) and calls split() (:182); run on such an index it throws the same exception and exits with code 1 (executed).
  2. The writer's field roles. The writer builds its field-number map from its config: new FieldNumbers(config.getSoftDeletesField(), config.getParentField()) (IndexWriter.java:1267-1269), so here both are null.
  3. The check. addIndexes(CodecReader...) runs "Best effort up front validations" over every incoming field (IndexWriter.java:3288-3295, verifyFieldInfo at :3292). verifySoftDeletedFieldName throws "this index has [soft] as soft-deletes already but soft-deletes field is not configured in IWC" (FieldInfos.java:459-465); verifyParentFieldName throws "can't add field [_parent] as parent document field; this IndexWriter has no parent document field configured" (FieldInfos.java:484-490).
  4. What carries the mark. A segment's field infos mark the soft-deletes field once a soft update or soft delete wrote it. In the minimal test the writer has already merged the soft-deleted old b away when it closes: the index is one segment from a merge with 2 documents, both live, and none has a value in soft, yet the mark alone is rejected. The mark is per segment: once every segment that carried it has been dropped as fully deleted, the index has no soft field info and splits (executed). A configured but never-written soft-deletes field splits fine. A parent field is added to every index written with setParentField.
  5. No supported way around it. The config is built inline and the reader wrapper is private; the command line has no option for these settings.
  6. Side effect. The exception leaves the first part's writer open with its write lock (a separate registry row, LFV-554).

Exposure and likelihood210 words
  • Who. Users of MultiPassIndexSplitter (its command line or split()) on an index whose segments carry a soft-deletes field (7.4.0 and later; at least one soft update or soft delete in a surviving segment, whose mark survives merges) or has a parent field (9.10.0 and later). Both settings are opt-in, but MIGRATE.md requires the parent field since 10.0 for index sorting combined with document blocks. A default index is not affected.
  • Effect. Every split of such an index fails at once, in both split modes, with assertions on and off, at any size and with no timing condition. No release has been able to split an index whose segments carry the soft-deletes mark, because 7.4.0 shipped soft deletes and the check together.
  • Workarounds. None supported through this API. PKIndexSplitter with its config constructors, or addIndexes into writers configured with the same field, do work.
  • Not affected. The source index (only read). The parts get no document and no commit; on a file-system directory the first part keeps only its write.lock (LFV-554). It is not data loss or corruption.
  • How likely: plausible. Deterministic for anyone who runs the tool on such an index, but the tool is little used, and no report was found in the searched sources (see Prior reports).

Why it looks unintended

#
  • split() accepts a source that "can have deletions", and a soft-deleted document "is treated as if it has been hard-deleted". Its only documented limit is breaking up document blocks.
  • Core tests copy such an index into a writer configured with the same field; the splitter cannot.
  • The split worked just before the 2018 check (LUCENE-8335) and broke with it.
The full argument221 words
  • Contract. "This tool splits input index into multiple equal parts" (MultiPassIndexSplitter.java:43); @param in "source index, can have deletions, can have multiple segments (or multiple readers)" (:63); the only stated limitation is that it "can easily break up" document blocks (:53-55). setSoftDeletesField: a soft-deleted document "is treated as if it has been hard-deleted through the IndexWriter API" (IndexWriterConfig.java:541-545).
  • Tests. TestMultiPassIndexSplitter builds plain indexes only. No test splits a soft-deletes or parent-field index or asserts the rejection for this tool. The core tests that assert the two messages are about a writer whose config disagrees with its index (TestIndexWriter.testPreventChangingSoftDeletesField, testIndexWithParentFieldIsCongruent), and TestAddIndexes.testAddIndicesWithSoftDeletes and testIllegalParentDocChange copy such an index into a destination configured with the same field.
  • History. The splitter's fixed config is older than both checks (LUCENE-2294, 2010; LUCENE-5871, 2014). The checks came from core changes that did not touch lucene/misc and mention no tool: LUCENE-8335 (#9382, 2018) and #12829 (2024). At the branch_7x parent of LUCENE-8335, which already had soft deletes, the split worked; at that commit it throws (executed).
  • Normal indexes. Lucene's own RandomIndexWriter turns soft deletes on at random in ordinary tests, and PKIndexSplitter and IndexUpgrader accept a config (IndexRearranger's constructors take one too, but since 10.0 it keeps only the analyzer, a separate row, LFV-695).
The devil's-advocate check158 words

The strongest case: an old command-line tool that never took a config; in LUCENE-3296 (#4369, 2011, an enhancement) committers gave PKIndexSplitter config constructors and left this class without one; soft deletes are an expert feature; and for the parent field the class already warns that it breaks blocks, so rejecting such an index may even be the safer outcome.

Why it fails for soft deletes: the 2011 decision was about defaults, seven years before soft deletes existed; no javadoc, test, CHANGES or MIGRATE entry excludes such indexes; "can have deletions" covers them; and core shows the supported copy path. For the parent field the argument is partly right (see the fix's trade-off), which is why that half is secondary. Three reviews rated the works-as-designed case moderate and found it does not hold for the soft-deletes half (verifier and the refute-lens review, both OpenAI GPT-5.6, and the devil's-advocate verifier): a classification risk (bug or improvement), not evidence of intent.

Suggested fix

#

Recommended Give each part the input's soft-deletes and parent field names (validated)

Read the input's soft-deletes and parent field names once with FieldInfos.getMergedFieldInfos(in) and set them on each part's config (+10/-1). The repro, the hunt's longer tests and the misc module pass. Caveat: a split that cuts a document block then succeeds but breaks it under a declared parent field, so for that half it is a policy choice.

// before the loop:
// each part must name the input's soft-deletes and parent fields (null if none), or
// IndexWriter#addIndexes rejects the input's field infos
FieldInfos inputFieldInfos = FieldInfos.getMergedFieldInfos(in);
// in the loop, instead of new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE):
IndexWriter w =
    new IndexWriter(
        outputs[i],
        new IndexWriterConfig(null)
            .setOpenMode(OpenMode.CREATE)
            .setSoftDeletesField(inputFieldInfos.getSoftDeletesField())
            .setParentField(inputFieldInfos.getParentField()));

Give each part the input's soft-deletes and parent field names (validated) (recommended)

#

In split() (MultiPassIndexSplitter.java:83-109), read the input's merged field infos once before the loop and set both names on each part's config (null, the default, when the input has none). The hunt's fix sketch did the same inside the loop with fully qualified names.

            .setParentField(inputFieldInfos.getParentField()));

Trade-offs

  • Parent field. With the fix a split that cuts a block succeeds but leaves a part whose segment ends in child documents with no parent after them, under a declared parent field. A round-robin split always cuts blocks (executed by the intended-behaviour verifier); a sequential split does when a part boundary falls inside a block (executed by the fact check on an index-sorted block index). That is the documented "can easily break up such document groups" behaviour, now in an index that declares blocks, and the precondition of a separate registry row (LFV-417: BP reordering merges then throw). So for the parent field this option is a policy choice for the maintainers, not a finished fix: keep rejecting parent-field input with a clearer message, or make the split block-aware.
  • Soft deletes. The markers are copied with the documents into parts configured with the same field, so soft-deleted documents stay deleted (an independent check read the input with a plain reader, as main() does). Never strip the mark instead: that would bring soft-deleted documents back.
  • Mixed inputs. One config cannot name two fields: getMergedFieldInfos throws if the input's leaves (for example a MultiReader over two indexes) disagree on the parent field or use different soft-deletes field names (read from the code). Such an input is rejected today anyway.
  • Other settings. Only the two field names are carried over; other settings of the input, such as an index sort, are still not set on the parts (the config-supplier option would let the caller choose them).

API change: let the caller supply the parts' configs

#

A split(..., Supplier<IndexWriterConfig>) overload or constructor, as PKIndexSplitter has (LUCENE-3296).

Trade-offs

Fully explicit, and it also lets a caller choose codec or index sort and covers the previous-major-version rejection noted in LFV-554. But callers must know to set the fields, the command line still needs option A or new options, and it adds public API. Not run.

Document that such indexes cannot be split

#

Javadoc change only.

Trade-offs

Leaves the tool unusable for soft-deletes and parent-field indexes, while the core already supports copying them.

Downstream note

#

No use of MultiPassIndexSplitter was found in Solr, Elasticsearch or OpenSearch (code search of their default branches).

How it was found

#

A randomized round-trip test built random indexes and ran them through Lucene's index tools. Of 597 sources with a soft-deletes or parent field, MultiPassIndexSplitter threw on 525 while PKIndexSplitter with matching configs reproduced all 597. The finder then cut it down to a public-API JUnit.

The method in full151 words

Method: randomized metamorphic round-trip differential testing of the index tools (the hunt classes it as non-formal).

  • A harness built random source indexes, some with a soft-deletes field, a parent field or both, split or merged them with each tool, and compared the parts' live documents with the source's.
  • In one batch of 10 JVMs (5 with assertions on, 5 off), MultiPassIndexSplitter threw IllegalArgumentException on 525 of 597 such sources (412 parent-field and 113 soft-deletes messages; the other 72 split), while PKIndexSplitter with matching configs reproduced all 597 exactly.
  • The finder minimised it to a two-test public-API JUnit (soft deletes, parent field) on the stock jars; the minimal repro above is its soft-deletes test cut down to two documents and one soft update.
  • The same harness saw IndexMergeTool, which has the same bare config, reject such sources too; no verifier traced or ran that, so it is only a sibling here.

LFV-618, snapshot of 2026-11-04

Registry title
MultiPassIndexSplitter builds every output part with a bare IndexWriterConfig and accepts no config, so it cannot split any index that uses soft deletes (7.4.0+) or has a parent field (9.10.0+): split() and its command line throw IllegalArgumentException before any part gets a document
Area
misc / index tools (MultiPassIndexSplitter.split, output IndexWriterConfig); IndexWriter.addIndexes field-role checks
Priority
Low, rank 644: A little-used misc tool fails loudly every time on soft-deletes or parent-field indexes without damaging anything.
Impact class
minor
Impact note
Only users of the lucene/misc MultiPassIndexSplitter (its command line, or split(IndexReader, Directory[], boolean)) are hit, and only on an index that uses soft deletes, meaning at least one soft update or soft delete was written under IndexWriterConfig#setSoftDeletesField (7.4.0 and later; a configured but never written field does not trigger it), or that has a parent field set with IndexWriterConfig#setParentField (9.10.0 and later; from 10.0 every index that combines index sorting with document blocks needs one). Every split of such an index then fails at once with IllegalArgumentException, in both split modes, with -ea and -da, and with no scale or timing condition; the tool's API offers no way to pass a config, so the only workarounds are PKIndexSplitter with its config constructors or addIndexes into writers configured with the same fields. Nothing is written or damaged: the source index stays byte-identical, no part receives a document, and the only side effect is the first part's writer left open with its write lock (LFV-554).
Summary
You split an index with MultiPassIndexSplitter, for example one written with IndexWriterConfig#setSoftDeletesField("soft") and a single softUpdateDocument call, or one written with IndexWriterConfig#setParentField("_parent"), and expect it to split like any other index: the split() javadoc says the source 'can have deletions, can have multiple segments (or multiple readers)', and the only documented limitation is that document blocks may be broken up. Instead split() opens every part's IndexWriter with new IndexWriterConfig(null), which names no soft-deletes or parent field and cannot be replaced by the caller, so IndexWriter.addIndexes rejects the input's field infos with IllegalArgumentException ('this index has [soft] as soft-deletes already but soft-deletes field is not configured in IWC', or 'can't add field [_parent] as parent document field; this IndexWriter has no parent document field configured') and nothing is split.
Introduced
Two halves, each introduced by a core change that began checking a field role against the writer's config; neither touched lucene/misc, and the splitter's fixed output config was not adapted. (1) Soft deletes: LUCENE-8335 'Enforce soft-deletes field up-front' (apache/lucene#9382, 'Do not allow changing soft-deletes field'), e7a0a12926c399758a4021715a7419e22e59dab6 on master and 67b6593e7adbce76532e285cef42118e6cc3448f on branch_7x, both 2018-06-04 (a first landing a2d92766741 on 2018-06-02 was reverted the same day by 3dc4fa199c1) [exec at commit level: the branch_7x parent 6f6b7f57edd splits a soft-deletes index, 67b6593e7ad rejects it; plain-index controls pass on both]. (2) Parent field: apache/lucene#12829 'Add support for index sorting with document blocks', df6bd25ce44ead0b38cffca6ef9bc3a9ce63dbea on main and 0aa88910ca9a1032d288996d14203eac4953f2de on branch_9x, both 2024-01-11; it added IndexWriterConfig#setParentField and the rejection together [read; bounded by execution: 9.9.2 lacks the API, 9.10.0 rejects]. The splitter's own config is older and unchanged: a default IndexWriterConfig since LUCENE-2294 (2010) and 'new IndexWriterConfig(null).setOpenMode(CREATE)' since LUCENE-5871 (2014), only reformatted since [read: git blame and git log -S on MultiPassIndexSplitter.java:108-109] (2018-06-04 (soft-deletes half, LUCENE-8335); 2024-01-11 (parent-field half, #12829))
First affected version
7.4.0 (tagged 2018-06-22) for soft deletes [exec, -ea and -da]: it is the first release with soft deletes at all, so no released version ever split a soft-deletes index (the two-month window in which the split worked, executed at 6f6b7f57edd, was never released); 9.10.0 (tagged 2024-02-20) for the parent field [exec], the first release with IndexWriterConfig#setParentField. 7.3.1 and 9.9.2 lack the respective APIs (compile errors) [exec]
