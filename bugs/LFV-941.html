The Lucene99 vector format javadocs give a wrong .vemf/.vem/.vex grammar: the vector encoding int32 is missing, and .vex neighbour deltas are group-varint, not vints

The default vector formats' javadocs omit the int32 vector encoding that every .vemf and .vem entry stores after the field number, so a parser following them reads a COSINE field's similarity as 1 (DOT_PRODUCT), not 2. Since 10.3 they also call the group-varint .vex neighbour deltas vints; Lucene is unaffected.

The finding in 30 seconds

#

Both javadocs list a field's metadata entry as field number, then similarity; both writers store an int32 vector encoding in between. Since 10.3 the .vex list also calls the neighbour deltas vints, though they are group-varint.

What you need to know first

#
  1. Each vector field of a segment has a metadata entry in two small files of the default codec: .vemf (the raw vectors, Lucene99FlatVectorsFormat) and .vem (the HNSW graph, Lucene99HnswVectorsFormat). The entry says which field it is, how its values are stored (the encoding: BYTE or FLOAT32 in the releases; main also has FLOAT16), which similarity it uses, and where its data lives.
  2. The graph itself is in .vex: for each node, a neighbour count and the sorted neighbour ordinals stored as differences (deltas).
  3. Each codec format documents its files in its class javadoc as a typed list ([int32], [vlong], [vint]), and the default codec's overview sends readers there for the details.

The finding, step by step

#
  1. You write your own reader for the vector metadata files from the javadocs of Lucene99FlatVectorsFormat (.vemf) and Lucene99HnswVectorsFormat (.vem). Both say each field's entry is [int32] field number, [int32] vector similarity function ordinal, [vlong] offset, [vlong] length, [vint] dimension, [int] count, ...
  2. You index 1 document with a 2-dimensional COSINE KnnFloatVectorField (default codec), read field number 0, then the similarity. You expect 2: COSINE in the format's list EUCLIDEAN 0, DOT_PRODUCT 1, COSINE 2, MAXIMUM_INNER_PRODUCT 3.
  3. You get 1 in both files, which means DOT_PRODUCT: a valid value, so reading it raises no error. It is the vector encoding (FLOAT32 = 1), an int32 both writers store between the two. The real similarity comes next, and from there on the parser is out of step (the documented offset starts on the real similarity, 4 bytes early), so every later value is misread: the dimension reads 0 instead of 2.
  4. Since 10.3.0 the .vex graph file is off too: the javadoc says the neighbour deltas are vints, but they are group-varint, with a flag byte before every 4 deltas. In a bigger index (the finder's test: 1000 random 4-dimensional vectors), node 0's neighbours 1, 2, 5, 9, ... read back as 0, 1, 2, 5, 9, ... Lucene's own readers match the writers: only the javadoc is wrong.

Who is affected

#

People who read or re-implement the vector files from these javadocs: ports, index inspection or recovery tools, format write-ups. For them every vector field the default codec writes goes wrong at the second value, and nothing flags it there, since the wrong similarity is a valid one. Lucene's own indexing, merging and kNN search are unaffected. Priority Low.

Mechanism, terms and numbers796 words

Lucene99HnswVectorsFormat is the vectors format of the default codec, and it stores the raw vectors with Lucene99FlatVectorsFormat. Their class javadocs document each field's metadata entry in .vemf and .vem as a typed list that goes from [int32] field number straight to [int32] vector similarity function ordinal. Since LUCENE-10577 (9.4.0, 2022) the writers store one more int32 between the two, the vector encoding ordinal, and the readers read it there; the list was copied without it into both Lucene99 classes when they were created in 9.9.0. A parser written from the javadoc therefore reads the encoding as the similarity (every FLOAT32 field comes out as DOT_PRODUCT, every BYTE field as EUCLIDEAN, valid values, so nothing flags the first misread), and from there on it is out of step (the documented offset starts on the real similarity, 4 bytes early), so every later value of the entry is misread. Separately, since #14932 (10.3.0, 2025) the .vex neighbour deltas are written with group-varint, while the .vex list still says array[vint], so a vint reader decodes wrong neighbours from the first list of 4 or more neighbours on. It is a documentation defect: Lucene's writers and readers agree, so nothing goes wrong at runtime; the fix is javadoc only.

What the writers write, and the readers read

#
  • Lucene99FlatVectorsWriter.writeMeta (:342-351): writeInt(field.number), writeInt(field.getVectorEncoding().ordinal()), writeInt(similarity ordinal), writeVLong(offset), writeVLong(length), writeVInt(dimension), writeInt(count). Lucene99HnswVectorsWriter.writeMeta (:615-621) writes the same first seven values.
  • Lucene99FlatVectorsReader (:482-487) and Lucene99HnswVectorsReader (:249-250) read readVectorEncoding before readSimilarityFunction. Ordinals: VectorEncoding BYTE 0, FLOAT32 1 (VectorEncoding.java:29, :32); similarities EUCLIDEAN 0, DOT_PRODUCT 1, COSINE 2, MAXIMUM_INNER_PRODUCT 3 (Lucene99HnswVectorsReader.java:224-229).
  • .vex: Lucene99HnswVectorsWriter writes writeVInt(count) and then writeGroupVInts(deltas, count) when version >= VERSION_GROUPVARINT (writeGraph :591-597, used by the unsorted flush and by merges; reconstructAndWriteNeighbours :422-428, on the index-sorted flush path); VERSION_CURRENT = VERSION_GROUPVARINT = 1 (Lucene99HnswVectorsFormat.java:92-94); the reader mirrors it (Lucene99HnswVectorsReader.java:605-619). A package-private constructor's javadoc in the same file already says "VarInt=0, GroupVarInt=1" (:261).

The documented offset starts on the real similarity int32, 4 bytes early, and the documented offset, length and dimension read its first three bytes, so the documented dimension reads 0 for every field (the similarity ordinal is at most 3); the finder's 4-dimensional field reads 0 too. The shift is not constant: in .vemf the real offset is a 2-byte vlong, so the later values start 5 bytes early; in .vem (a 1-byte offset here) 4 bytes early.

Worked example: a .vex neighbour list (finder's test, 1000 random 4-dimensional vectors)

#

Node 0 has 19 neighbours 1, 2, 5, 9, 10, 17, ..., so the deltas are 1, 1, 3, 4 | 1, 7, 3, 8 | 3, 32, 10, 12 | 2, 117, 108, 112 | 137, 176, 7. Group-varint (GroupVIntUtil.java:144-173) writes each group of 4 as one flag byte with the four byte lengths, then the values in 1-4 little-endian bytes, and a tail of fewer than 4 as vints: 00 01 01 03 04 | 00 01 07 03 08 | .... A vint reader of 19 deltas reads 0, 1, 1, 3, 4, 0, 1, 7, ... (each flag byte is a delta of 0), so the running sums are 0, 1, 2, 5, 9, 9, 10, 17, ..., and it stops 6 bytes before the end of the 25-byte list. Lists of 1 to 3 neighbours look the same in both encodings; every list of 4 or more is misread, because the vint reader takes each flag byte for a delta.

On main VectorEncoding also has FLOAT16 (ordinal 2, #16383, in no release yet), whose documented similarity would read as COSINE (read in code, not run).

Exposure and likelihood282 words
  • Who. Only people who decode .vemf, .vem or .vex themselves from these javadocs. Lucene's own code never consults the text. Outside ports exist: one closely transcribes the stale text, two others document the real layout, traced from the writer; none reported the javadoc.
  • Default codec, every vector field. Codec.getDefault() is Lucene104 (Codec.java:59), whose default vectors format is Lucene99HnswVectorsFormat (Lucene104Codec.java:123), which stores raw vectors with Lucene99FlatVectorsFormat (Lucene99HnswVectorsFormat.java:155-156). The codec overview links Lucene99HnswVectorsFormat as "Vector values" (package-info.java:183, :313) and says "Details on each of these are provided in their linked pages" (:188). So every KnnFloatVectorField or KnnByteVectorField written with the default codec has the extra int32 (in .vem since 9.4.0, in .vemf since 9.9.0, when that file was created), and every field whose segment gets a graph has group-varint .vex lists (tiny segments skip the graph).
  • What they get. A similarity that is wrong but plausible (DOT_PRODUCT for every float field, EUCLIDEAN for every byte field), then wrong offsets, lengths, dimensions and counts; and wrong neighbour ordinals from the first list of 4 or more neighbours on. A parser that checks later fields may notice the zero dimension, an implausible count or a missed footer; nothing flags the similarity itself.
  • What nobody gets. Any runtime effect: writers and readers agree, and the six upstream codecs.lucene99 test classes, the vector format round-trip suites among them, pass with the fix applied (212 tests, 9 skipped).
  • Scale and priority. Every release from 9.4.0 (2022) for the metadata part and from 10.3.0 (2025) for .vex, through 10.6.0 and main; nobody has reported it in four years, which fits the small audience. Impact minor, priority Low.

Minimal repro

#

One JUnit class, one test, no randomness. It indexes 1 document with a 2-dimensional COSINE float vector (default codec, no compound file) and reads, in .vemf and .vem, the field number and then the int32 the javadoc calls the similarity. Put it in lucene/core's tests and run it with gradle.

Observed
It is 1 in both (expected:<[2, 2]> but was:<[1, 1]>): the FLOAT32 encoding, which reads as DOT_PRODUCT; with assertions on and off.

Why it looks unintended

#
  • Both javadocs give exact typed lists, the codec overview sends readers to them, and the sibling Lucene104ScalarQuantizedVectorsFormat documents this "vector encoding ordinal".
  • The lines were right when written; the 9.4.0 and 10.3.0 writer changes left them; a constructor comment in the file says "VarInt=0, GroupVarInt=1".
  • #13548 refreshed these lists in 2024; upstream fixes format-doc drift as bugs (LUCENE-713, LUCENE-7532).
The full argument273 words
  • Typed, ordered lists that read as an exact grammar. Both classes list the elements in order with a type per element ([int32], [vlong], [vint], array[vint]). Nothing marks them as approximate, and package-info.java:188 sends readers to them for the details. The sibling Lucene104ScalarQuantizedVectorsFormat documents "int the field number / int the vector encoding ordinal / int the vector similarity ordinal" (:84-86).
  • They used to be exact. [int32] field number comes from LUCENE-9844 (5b36af3cd79, 2021), the similarity line from 6d4b5eaba35 (2021), the .vex vint lines from #11860 (d0be9ab57c9, 2022), each correct when written; the study's lineage probe reads the documented prefix of a 9.3.0 .vem correctly and fails from 9.4.0.
  • Oversights, not decisions. LUCENE-10577 (#1054) added the encoding write to the then-default HNSW writer and edited other lines of that javadoc, but not these; #12582 and #12729 created the two Lucene99 classes with the stale list; #14932 documented group-varint in the @param of a package-private constructor and in its 10.3.0 CHANGES.txt entry, not in the class list. No comment in the saved #1054, #12729 and #14932 threads mentions the class lists (the #12582 thread was not saved).
  • Maintained as exact layouts. #13548 (2024) refreshed exactly these lists ("Javadoc for Lucene99HnswVectorsFormat is a bit outdated") and kept the omission; on #870 a reviewer asked for the lists to be kept "in order ... more precise". Upstream has fixed format-doc drift as bugs (LUCENE-713, LUCENE-7532).
  • Tests. No test that compares a format javadoc with the bytes was found in the lucene99 codec test sources reviewed; the format suites check writer/reader agreement, which is not in question.
The devil's-advocate check147 words

The case for "intended" (rated moderate by reviewers): the format classes are @lucene.experimental (Lucene99FlatVectorsFormat.java:74, Lucene99HnswVectorsFormat.java:83); the overview "attempts to provide a high-level definition of the Apache Lucene file formats" (package-info.java:54, the LUCENE-2946 policy); version 0 .vex files really do store vints; and the supported way to read vectors is the codec's own reader, whose round trip is tested.

Why it fails: these pages do not give a high-level description, they give typed, ordered lists, and a precise list that is wrong is worse than none. The LUCENE-2946 thread kept detailed docs for simple metadata files, which these are. @lucene.experimental allows the format to change, not the description of the current format to be wrong; the default writer always writes the group-varint version and the .vex list carries no version note. At most the argument makes the fix low priority, which it is.

How it was found

#

A semi-formal differential check. Each default-codec file grammar was written down twice, from the class javadoc and from the writer, and one interpreter parsed the bytes of 64 generated indexes with both. The writer grammar parsed every file; under the javadoc grammar all 106 .vemf and 106 .vem files diverged, and so did every .vex with a graph.

The method in full137 words
  • Hunt. The grammars are data in a small grammar language; the interpreter compares every parsed value with Lucene's own reader. 64 index configurations (4 fixed and 60 seeded random), 1,114 file checks, assertions on and off.
  • Controls. The writer grammar parses every file exactly to the footer (0 failures). Each of 14 single-element mutants of the writer grammar is detected, including dropping the .vemf or .vem vector encoding, so the check is not vacuous.
  • Result. 106 of 106 .vemf and 106 of 106 .vem files diverge under the javadoc grammar; the 6 .vex files that hold a graph diverge under vint reading and parse under group-varint. The same unit found the sibling file-format javadoc defects of .fnm, .si, segments_N, .nvm and the terms dictionary.
  • Minimized to the one-test repro of the Minimal repro section.

LFV-941, snapshot of 2026-11-05

Registry title
The file-format javadocs of the default vector formats (Lucene99FlatVectorsFormat and Lucene99HnswVectorsFormat) give a wrong .vemf/.vem/.vex grammar: both metadata lists leave out the int32 vector encoding that is written right after the field number, so every later element is misread, and since 10.3 the .vex list still calls the HNSW neighbour deltas vints although they are group-varint encoded (documentation defect; the writers and readers agree)
Area
codecs / vectors (Lucene99FlatVectorsFormat .vemf and Lucene99HnswVectorsFormat .vem and .vex file-format javadoc vs their writers and readers)
Priority
Low, rank 1233: The vector-format grammars, wrong since 9.4 for the metadata and 10.3 for .vex, touch only indexes with vector fields.
Impact class
minor
Impact note
Documentation only: Lucene's writers and readers agree, so indexing, merging, CheckIndex and kNN search are unaffected in every configuration; the people misled are those who read, inspect or re-implement the vector files from these class javadocs (the default codec's package docs link Lucene99HnswVectorsFormat as the Vector values format), and a parser that follows the text takes the encoding ordinal for the similarity (every float32 field reads as DOT_PRODUCT, every byte field as EUCLIDEAN, valid values, so nothing flags the similarity itself), misreads every later metadata field, and since 10.3 decodes wrong HNSW neighbours from the first list of 4 or more neighbours on (executed); the metadata part has been wrong in every release since 9.4.0 (2022) and the .vex part since 10.3.0 (2025), and no scale or special setting is needed.
Summary
You decode the vector metadata (.vemf, .vem) or the HNSW graph (.vex) files of the default codec by following the Lucene99FlatVectorsFormat and Lucene99HnswVectorsFormat javadocs, which list each field as '[int32] field number, [int32] vector similarity function ordinal, [vlong] offset, ...' and each neighbour list as '[vint] count, array[vint] delta-encoded ordinals'. Both writers instead store an extra int32, the vector encoding (BYTE or FLOAT32), between the field number and the similarity, and since 10.3 they write the neighbour deltas with group-varint, so a parser built from the text reads the encoding as the similarity (a COSINE float field comes out as DOT_PRODUCT), gets the offset, length, dimension and count wrong, and decodes wrong neighbours from the first list of 4 or more neighbours on. Lucene's own readers match the writers, so nothing breaks at runtime; only the documentation is wrong, the metadata part since 9.4.0 and the .vex part since 10.3.0.
