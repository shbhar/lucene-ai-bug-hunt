All bugs · Lucene bug · LFV-105 · invertterm-counts-each-value-twice

Lucene's single-term (InvertableType.BINARY) indexing path counts each value twice in the field length, so untokenized DOCS_AND_FREQS fields with norms store a doubled length in their norms and get lower BM25 scores

Lucene's single-term indexing path (InvertableType.BINARY, used by custom fields and addBatch columns) adds 2 to the field length per value instead of 1. An untokenized field with term frequencies and norms then gets norm 2 instead of 1 for one value and, in the repro, a 29% lower BM25 score, silently; StringField and KeywordField are unaffected.

The bug in 30 seconds

#

Lucene inverts an indexed field either through a TokenStream or, since 9.6.0, through a fast single-term path for untokenized values (InvertableType.BINARY). The fast path updates the field length twice per value, and the norm, which BM25 uses as the document length, is computed from that length.

  1. You give an untokenized field tag term frequencies and norms (DOCS_AND_FREQS, norms on by default) and index "red" twice in one index: doc 0 through a plain Field, doc 1 through a Field subclass whose invertableType() returns BINARY, the fast path StringField uses. addBatch columns take the same path.
  2. You expect a field length of 1 for both: FieldInvertState#getLength is the "total number of terms in this field", and a BINARY value is "a single value" with term frequency one. So both documents should get norm 1 and the same BM25 score for tag:red.
  3. Instead the fast path, IndexingChain.invertTerm, adds 1 to the length twice per value: invertState.length++; and, two lines later, invertState.length = Math.addExact(invertState.length, 1);. Doc 1 gets norm 2; with two values, 4 instead of 2.
  4. BM25 then treats doc 1 as twice as long: tag:red scores 0.0829 for doc 0 and 0.0588 for doc 1, 29% lower, with no error. The postings still say freq 1, and which documents match does not change.
  5. Through addBatch it is the same: a BinaryColumn and a DictionaryColumn both get norm 2 next to norm 1 for the same value added with addDocument (BM25 0.0607 vs 0.0431).

Who is affected

#

Applications that index an untokenized field with DOCS_AND_FREQS and norms through the single-term path: a custom field returning InvertableType.BINARY (released since 9.6.0) or an untokenized BinaryColumn or DictionaryColumn in the experimental addBatch (10.5.0 and later). Every such document gets twice its length, deterministically. StringField, KeywordField and DOCS-only fields are not affected.

Mechanism, terms and numbers644 words

Since 9.6.0 an untokenized value can be indexed through a single-term path that skips the TokenStream (InvertableType.BINARY, IndexingChain.invertTerm). StringField and KeywordField use it, and so does IndexWriter#addBatch for untokenized BinaryColumn and DictionaryColumn columns. The path updates the field length twice for every value (invertState.length++; and invertState.length = Math.addExact(invertState.length, 1);), although FieldInvertState#getLength is the "total number of terms in this field" and a BINARY value is "a single value" with term frequency one. For an untokenized field with DOCS_AND_FREQS and norms, Similarity#computeNorm uses that length, so the norm encodes a length of 2k instead of k for k values and BM25 scores the document lower than the identical document indexed through a TokenStream (0.058813408 vs 0.082873434 in the repro). Postings, matching and CheckIndex are unaffected; StringField and KeywordField are DOCS-only with norms omitted. Both increments came in with the path itself in #12139; deleting the plain invertState.length++; fixes it.

Terms

#
  • Field length and norm: while a field is inverted, FieldInvertState counts its terms (getLength(), "total number of terms in this field"). At the end of the document Similarity#computeNorm turns that count into the norm, which BM25 reads back as the document length dl.
  • Two inversion paths: IndexableField#invertableType() chooses how a field is inverted. TOKEN_STREAM (a plain Field) runs the analyzer or a one-token stream; BINARY indexes binaryValue() as one term without a TokenStream. StringField and KeywordField return BINARY, and addBatch uses it for untokenized BinaryColumn and DictionaryColumn columns.

The bug

#
  1. PerField.invert calls invertTerm for BINARY and invertTokenStream for TOKEN_STREAM (IndexingChain.java:1950-1968 on main a9779ef3c193). The addBatch row pass (processRowColumns, :847) wraps a BinaryColumn or DictionaryColumn in a BinaryColumnAdapter (ColumnFieldAdapter.java:51-62) whose invertableType() is BINARY for indexed untokenized columns (:244-250), and reaches the same invert through invertAndStore (IndexingChain.java:1477-1487).
  2. invertTerm (IndexingChain.java:2127-2170) rejects tokenized fields and anything with positions or term-vector positions, offsets or payloads (:2136-2144), then runs invertState.position++; (:2147), invertState.length++; (:2148), termsHashPerField.start(field, first); (:2149) and invertState.length = Math.addExact(invertState.length, 1); (:2150). It adds the term once (:2152), so the postings get freq 1, but the length grows by 2.
  3. invertTokenStream adds 1 per token (or the custom term frequency) in a single Math.addExact (IndexingChain.java:2053-2064).
  4. PerField.finish stores similarity.computeNorm(invertState) (IndexingChain.java:1926-1944). Similarity#computeNorm uses getLength() for every index option except DOCS, which uses the unique-term count (Similarity.java:151-161). The length is encoded with SmallFloat.intToByte4 (Similarity.java:160), so a DOCS_AND_FREQS field gets the norm of length 2k instead of k for k values; a DOCS field is unaffected under the stock similarities. The norm byte equals the length up to 40 and is lossy above (SmallFloat.java:139-165): one value gives norm 2 instead of 1, 21 values the code 41 (decoded length 42) instead of 21.
  5. BM25's average length is sumTotalTermFreq / docCount (BM25Similarity.java:143-146), which is right; only each document's own length is doubled, so every BINARY document's dl/avgdl is twice its correct value (2 instead of 1 in the repro, where each document's true length equals the average).

The numbers

#

One index, default IndexWriterConfig (BM25), field type untokenized DOCS_AND_FREQS with norms. Two values per document: norms [2, 4], the same scores. addBatch, doc 0 with addDocument and docs 1 and 2 as a BinaryColumn and a DictionaryColumn: norms [1, 2, 2], scores [0.06069608, 0.043074638, 0.043074638]. The same with IndexOptions.DOCS: norms [1, 1], equal scores. With values a, b, a in one document the BINARY path writes norm 6 while sumTotalTermFreq is 3; the TokenStream path and MemoryIndex give 3.

Exposure and likelihood495 words
  • Who. Applications with an untokenized indexed field whose FieldType has DOCS_AND_FREQS and norms enabled (omitNorms defaults to false, FieldType.java:41) that goes through the BINARY path: addDocument with a custom IndexableField or Field subclass whose invertableType() returns BINARY (public API, 9.6.0 on; IndexableField#invertableType() has no default, so every implementation that does not extend Field picks one), or the @lucene.experimental IndexWriter#addBatch with an indexed untokenized BinaryColumn or DictionaryColumn (10.5.0 on), where no override is needed.
  • What goes wrong. Norms and BM25 scores only, silently: no exception, CheckIndex clean. Matching, deletions and FieldExistsQuery are unchanged (executed through addDocument: 40 random documents, 2 deleted, once with a plain Field and once with a BINARY field, assertions on and off; addBatch reaches the same invertTerm by code reading).
  • Size of the effect. BM25's term-frequency factor is tf = freq / (freq + k1 * (1 - b + b * dl / avgdl)) (BM25Similarity.java:219, :272-273, :307-328), so doubling dl/avgdl lowers each score by a fraction that depends on the document's frequency and length: 29% for freq 1 at dl = avgdl, as in the repro. The scores do not drop uniformly, and ranking can flip even inside one field where every document takes the BINARY path (executed by the fact check, public API, seed DEADBEEF, main with assertions on and off and 9.6.0): docs A = [x], B = [x, x, y] and a third with 8 distinct values (avgdl 4), query tag:x. All through a plain Field: A 0.3081991 < B 0.3159688; all as BINARY: A 0.26857352 > B 0.25753623 (A loses 12.9%, B 18.5%), so the order flips; with the fix the BINARY scores equal the plain-Field ones. The doubling also shifts the field's weight against other fields and against documents of the same field indexed through a TokenStream, for example addDocument with a plain Field next to addBatch columns.
  • Default vs opt-in. Default IndexWriterConfig, codec and similarity; the opt-in part is the field type, which no stock Lucene field uses.
  • Not affected. StringField and KeywordField (DOCS, norms omitted); DOCS-only fields with norms under the stock computeNorm, which counts unique terms. For DOCS fields getLength() is doubled too (executed: the independent reproducer's recording BM25Similarity and the diagram probe print getLength() [1, 2] with norms [1, 1]), so a custom Similarity that reads it there would see the doubling (read).
  • Scale. Deterministic for every value that takes the path, independent of the index size, up to the overflow limit below.
  • Side effect (read, not executed). The Math.addExact overflow check fires after about 2^30 values in one field of one document instead of about 2^31: today the 2^30th value makes Math.addExact (IndexingChain.java:2150) throw a raw ArithmeticException; with the fix the limit moves to the 2^31st value, still a raw ArithmeticException, while the TokenStream path wraps the same overflow in IllegalArgumentException (:2061-2064).

Why it is a bug, not intended

#
  • FieldInvertState#getLength is the "total number of terms in this field"; a BINARY value is "a single value" with term frequency one.
  • The TokenStream path and MemoryIndex's single-term path count 1 per value; the writer's own sumTotalTermFreq says 1.
  • Lucene's own BINARY test accepts this field type but never checks norms; both increments came in a speed-only change.
The full argument244 words
  • The contract. FieldInvertState.java:124-131: getLength(): "Get total number of terms in this field." InvertableType.java:25-32: BINARY: "The field should be treated as a single value whose binary content is returned by IndexableField#binaryValue(). The term frequency is assumed to be one. [...] If the same value is provided multiple times, the term frequency will be equal to the number of times that this value occurred in the same document."
  • Every sibling counts 1 per value (executed): the same field type through the TokenStream path, and MemoryIndex's single-term path added in the same commit (storeTerm, info.numTokens++ once per value, MemoryIndex.java:968-969). The same writer's sumTotalTermFreq (1 per value) disagrees with its own norm (2 per value).
  • Lucene's own test accepts the trigger. TestDocumentWriter#testIndexBinaryValueWithoutTokenStream (TestDocumentWriter.java:435), added in #12139, indexes a BINARY field with six legal field types, including untokenized DOCS_AND_FREQS with setOmitNorms(false) (:502-509). It checks postings and term vectors, never norms (:543-592). The upstream column tests set omitNorms(true) on their untokenized types.
  • History. invertState.length++; is the form the TokenStream path used before LUCENE-7854 (2017) replaced it with the Math.addExact form; invertTerm has both, already in the first commit of #12139, unchanged since. The PR is about attribute overhead; its 12 comments discuss API shape and naming and never mention length, norms or scores. CHANGES lists it under 9.6.0 as "GITHUB#12139: Faster indexing of string fields." No javadoc, CHANGES or MIGRATE entry restricts norms on BINARY fields.
The devil's-advocate check232 words

The strongest works-as-designed case, built by the intended-behaviour verifier, a review by a model from another family (OpenAI GPT-5.6) and the adjudication: BINARY is a performance fast path whose only stock users omit norms, so norms on a BINARY field are an unsupported combination; addBatch is @lucene.experimental and its javadoc does not promise the same index as addDocument; and the addDocument trigger needs a custom invertableType() override.

Why it fails: #12139 promised only speed and no document restricts norms on this path; the PR's own test lists the trigger field type as legal; overriding invertableType() is public API that StringField and KeywordField use themselves; two adjacent increments of the same counter serve no performance or semantic purpose; and @lucene.experimental covers API stability, not wrong index data, while the released trigger is addDocument. For DOCS fields under a custom Similarity that reads getLength() (not the stock case) the argument is narrow reach, not correctness: getLength() still promises the total number of terms and reports twice that. Every verifier and the cross-model reviews rated the intended argument weak; the cross-model fact check of this doc rated it weak for addDocument and moderate for the experimental addBatch path and the custom-Similarity DOCS case, and found no plausible purpose for the duplicate increment. For the issue, cite getLength, the BINARY javadoc and the TokenStream/MemoryIndex agreement rather than an addBatch equivalence promise.

Suggested fix

#

Recommended Delete invertState.length++ and keep the Math.addExact update

Delete the extra invertState.length++; in IndexingChain.invertTerm and keep the overflow-checked Math.addExact update, one line. The repro passes with assertions on and off, 18 nearby core test classes (20 with the two repro classes, 258 tests) and lucene/memory pass, and a norms check added to TestDocumentWriter's BINARY test fails on stock main and passes with the fix.

How it was found

#

Translation validation of the experimental addBatch against row-by-row addDocument on the real jar: 29,408 bounded-exhaustive scenarios gave 1,242 norm mismatches, all from the one untokenized DOCS_AND_FREQS column with norms, and none with the one-line fix. Reading invertTerm then gave the root cause and the second trigger, a BINARY field in addDocument.

The method in full203 words

Method: bounded-exhaustive translation validation on the stock jar (semi-formal tier), in a hunt unit on the column-batch addBatch API.

  • The harness indexes every one of 26 single-column specs (Long, Binary, Dictionary, Vector and TokenStream columns with different field types) through addBatch and, as the reference, the same documents row by row through addDocument, then compares the two indexes: dense and every sparse pattern for 0 to 3 documents, a document before and/or after the batch, and 4 IndexWriterConfigs, with assertions on and off (29,408 scenarios).
  • It reported 1,242 norm mismatches, all from the one DictionaryColumn spec that is untokenized with DOCS_AND_FREQS and norms: batch norm 2, row norm 1. With the one-line fix shadowed onto the jar the mismatches went to 0.
  • The root cause was then located by reading invertTerm, which showed that the path is shared with addDocument; the finder added the addDocument trigger (a Field subclass returning BINARY), which reaches back to 9.6.0.
  • Found 2026-10-25 on main ea57360912ed; then checked by an independent reproducer, an intended-behaviour devil's advocate, two executed reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history and prior-report follow-up and a credibility audit.

History

#

Born with the single-term path in #12139 (cce33b07e4f5, 2023-02-21; first release 9.6.0); addBatch added a second trigger in 10.5.0 (#15990). Executed: 9.6.0, 9.12.3, 10.0.0, 10.4.0, 10.5.0, 10.5.2 and main fail, the introducing commit fails and passes with the deletion; 9.5.0 has no InvertableType. Not fixed upstream.

Versions tested8 rows

Introduced by cce33b07e4f5 on main, "Skip the TokenStream overhead when indexing simple keywords. (#12139)" (@jpountz, merged 2023-02-21), backported to the 9.x line the same day as 668246439ddf. It created InvertableType, the abstract IndexableField#invertableType(), invertTerm with both increments (already in the PR's first commit) and switched StringField and KeywordField to BINARY. IndexWriter#addBatch came with #15990 (3d895681557, merged 2026-05-14; 3ec3bff01b1 in 10.5.0), and its BinaryColumnAdapter returns BINARY for untokenized indexed columns. Later edits of invertTerm, #15826 (2026-03, ArrayUtil.copyOfSubArray in the immense-term prefix copy) and #15584 (2026-04, the index-options guard), leave the increments alone. On 2026-10-26 main, branch_10x, branch_10_6, branch_10_5 and branch_9_12 still had both lines (read only; the plain increment re-read on all five on 2026-10-27 by the fact check).

Bug record

#

LFV-105, snapshot of 2026-10-29

Registry title
IndexingChain.invertTerm adds 2 to the field length for each single-term (InvertableType.BINARY) value, so untokenized DOCS_AND_FREQS fields with norms get double the norm and a lower BM25 score
Area
index / indexing chain (single-term BINARY inversion, norms)
Priority
Medium, rank 289: Single-term BINARY inversion adds 2 to the field length per value, silently doubling norms and lowering BM25 for untokenized DOCS_AND_FREQS fields with norms since 9.6, deterministic once used but a combination no stock field uses.
Impact class
silent wrong results
Impact note
Applications that index an untokenized field whose FieldType has DOCS_AND_FREQS and norms enabled through the single-term BINARY inversion path, either with addDocument and a custom IndexableField whose invertableType() returns BINARY (released since 9.6.0) or with the experimental IndexWriter#addBatch and an indexed untokenized BinaryColumn or DictionaryColumn (10.5.0 and later), get norm 2k instead of k for k values and wrong BM25 scores with no error, at any scale and with the default codec, IndexWriterConfig and similarity; stock StringField and KeywordField (DOCS-only, norms omitted) are not affected, and matching is unchanged.
Summary
You index one value in an untokenized field whose FieldType has DOCS_AND_FREQS and norms enabled, once through a plain Field (TokenStream inversion) and once through the single-term path (a Field subclass whose invertableType() returns BINARY, or an IndexWriter#addBatch BinaryColumn or DictionaryColumn). You expect the same field length and norm, 1 per value, because FieldInvertState#getLength is the 'total number of terms in this field' and a BINARY value is documented as a single value with term frequency one. Instead IndexingChain.invertTerm adds 2 to the length for every value, so the norm is 2 (2k for k values) and the BM25 score of the identical document drops (0.082873434 to 0.058813408 in the repro), while the postings still record freq 1 per value.
Introduced
