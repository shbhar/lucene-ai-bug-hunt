DirectoryTaxonomyWriter keeps a closed ReaderManager when closing it fails at the end of the cache fill, so later addCategory calls on the still-open writer throw AlreadyClosedException

If the one internal reader close at the end of DirectoryTaxonomyWriter's cache fill throws an IOException, the writer stays open but keeps the closed ReaderManager. From then on addCategory throws AlreadyClosedException each time the cache evicts entries, until the writer is closed and reopened.

The finding in 30 seconds

#

Once its cache holds every category, the writer closes its internal reader and forgets it. The forgetting is two statements after the close, with no try/finally. If the close throws, they are skipped: the open writer keeps a ReaderManager that is already closed, and nothing ever replaces it.

Background: three pieces

#
  1. DirectoryTaxonomyWriter gives every facet category a number, its ordinal, and stores the mapping in a small Lucene index. An in-memory cache answers most lookups. The default is an LRU cache of 4,000 entries.
  2. For lookups the cache cannot answer, the writer keeps an internal reader on that index, managed by a ReaderManager. On a reopened taxonomy, the 11th cache miss (by default) makes the writer copy every category its reader sees into the cache. If they all fit, the cache is "complete" and the writer closes the reader to save resources.
  3. When the cache overflows it drops about a third of its entries, the least recently used ones, and is no longer complete. The writer then needs its reader again. It creates a new one on demand, unless a flag says it still has one.

The finding, step by step

#
  1. You reopen an existing taxonomy with a DirectoryTaxonomyWriter (the test gives it a 12-entry LRU cache) and add c1 to c10, committing after each. The default merge policy merges the small segments along the way, so the writer's internal reader becomes the last user of the old segment file _0.cfs.
  2. You add c11. It is the writer's 11th cache miss, so the writer fills its cache from its internal reader. The cache now holds every category, so the writer closes that reader. The close releases _0.cfs, and the directory throws an IOException from this one file close (injected by the test). addCategory(c11) throws it.
  3. You expect the writer, which is still open, to have dropped the reader manager it closed, as it does when the close succeeds. A second addCategory(c11) does return 11.
  4. Instead addCategory(c12) throws AlreadyClosedException: this ReferenceManager is closed. c12 is the 13th entry of the 12-entry cache, so the cache evicts, and the writer refreshes the manager it still holds, which is closed. c12 was already indexed: getSize() went from 12 to 13.
  5. It repeats at every later eviction: 4 of the next 20 new categories throw (c17, c22, c27, c32). With the default 4,000-entry cache the first exception comes at the 3,990th new category. commit() and close() still work, and a reopened writer is healthy. Two other calls, replaceTaxonomy and reindexWithNewOrdinalData, also run into the closed manager, without an eviction.

Who is affected

#

Applications that keep using a taxonomy writer after addCategory or FacetsConfig.build threw an IOException from this internal close. That needs a taxonomy opened for append that fits the cache, a merge, and a Directory whose file close can throw; the default MMapDirectory cannot. The failure is loud. Reopening the writer recovers; after a failed replaceTaxonomy or reindexWithNewOrdinalData, only rollback() does.

Mechanism, terms and numbers1,569 words

DirectoryTaxonomyWriter keeps an internal near-real-time reader, managed by a ReaderManager, for category lookups its cache cannot answer. When an existing taxonomy is reopened, the 11th cache miss (the default threshold) makes the writer put every category its internal reader sees into the cache (perhapsFillCache, DirectoryTaxonomyWriter.java:604-663 on main 781025d6fe32). If they all fit, the cache is complete and the writer drops the manager: readerManager.close(); readerManager = null; initializedReaderManager = false; (:658-660), with no try/finally. ReferenceManager.close() marks the manager closed before it releases the reader (ReferenceManager.java:53-58, :134-142). So when the release throws an IOException (in the test: the close of a file of a segment that a merge has already retired), the manager is closed but stays in the field, and the flag still says it is initialized. The addCategory call that ran the fill throws the IOException; the writer is not closed. From then on every addCategory whose cache insertion evicts entries calls maybeRefresh() on the closed manager (:504-505) and throws AlreadyClosedException: this ReferenceManager is closed, after it has already indexed its category document. With the test's 12-entry cache that is the second call after the failure; with the default 4,000-entry cache it is the 3,990th new category. After such a failed addCategory, close() or rollback() and a reopen recover fully. Two other calls, replaceTaxonomy and reindexWithNewOrdinalData, use the closed manager without an eviction, after they have already changed the index: they throw the same exception half-way, and a close() after them stores the half-done taxonomy, while rollback() returns to the last commit.

The trigger is narrow, and every run injected it: the default MMapDirectory has no path that throws an IOException from that file close, and FSDirectory records a failed delete as pending (a missing file aside), so it takes NIOFSDirectory with a failing descriptor close, a custom, filter or remote Directory, or an application's segment-closed listener that throws. No javadoc promises that the writer stays usable after an IOException; the claim is the invariant that an open writer must not keep a closed manager installed. That makes this a Low priority bug. It is present since 4.0.0 (LUCENE-4061, 2012), with the writer's default cache since 9.5.0, in 10.6.0, on branch_11x and on main. A validated try/finally around the close fixes it (7 insertions, 3 deletions).

Terms

#
  • Writer cache. A TaxonomyWriterCache maps category paths to ordinals in memory. The default is LruTaxonomyWriterCache with 4,000 entries (DirectoryTaxonomyWriter.java:89, :274-276). Its put returns true when the cache held more than its maximum and dropped its least recently used entries, down to two thirds of that maximum (LruTaxonomyWriterCache.java:104-118, NameIntCacheLRU.java:81-93, :110-126).
  • Complete cache. "We call the cache 'complete' if we know that every category in our taxonomy is in the cache" (DirectoryTaxonomyWriter.java:110-118). A writer opened on an existing taxonomy starts with an incomplete cache (:186-194).
  • Cache fill. Each cache miss is counted (:331). At miss number cacheMissesUntilFill (11 by default, :101; setCacheMissesUntilFill changes it, :596-599), perhapsFillCache (:604-663) puts every category its internal reader sees into the cache (:618-650). The reader is not refreshed first. In the repro it was opened at the first miss and still sees only the root; c1 to c10 are in the cache from their own additions. The fill runs once (:609-613; replacing the taxonomy arms it again, :886, :914) and aborts when the cache is full (:626, :637-641).
  • Internal reader. A ReaderManager on the writer's own IndexWriter, created lazily by initReaderManager, and only while initializedReaderManager is false (:104-108, :246-258).

The bug

#
  1. After the fill, cacheIsComplete = !aborted (:652). If the cache is complete, the writer drops the manager, under the comment "everything is in the cache, so no need to keep readerManager open" (:655): readerManager.close(); readerManager = null; initializedReaderManager = false; (:658-660).
  2. ReferenceManager.close() calls swapReference(null) (ReferenceManager.java:134-142), which sets current = newReference (:56) before release(oldReference) (:57). Releasing the reader's last reference closes it; a segment whose last user it is closes its files (StandardDirectoryReader.java:548-568, SegmentCoreReaders.java:167-180).
  3. If one of those closes throws, the exception leaves close() with current == null: the manager is closed. In the writer, :659 and :660 are skipped, so the field still holds the closed manager and the flag is still true. Everything else is as after a successful fill: cacheIsComplete is true, the fill will not run again, and the files of the retired segment are gone from the directory (probe output after the failed call).
  4. Later, an addCategory of a new category adds its document and takes its ordinal (:468-469), then puts it into the cache (:479, :485). When that put evicts, refreshReaderManager (:491) calls readerManager.maybeRefresh() because the flag is true (:504-505). maybeRefresh starts with ensureOpen() and throws AlreadyClosedException (ReferenceManager.java:207, :47-51).
  5. Two more public calls refresh the manager, without an eviction: replaceTaxonomy (:872-891) and ReindexingEnrichedDirectoryTaxonomyWriter.reindexWithNewOrdinalData, through deleteAll (ReindexingEnrichedDirectoryTaxonomyWriter.java:87-104, DirectoryTaxonomyWriter.java:902-919). Both change the index first (:874-875, :903) and then call refreshReaderManager (:876-878, :904-906). On the closed manager that throws before the writer resets its ordinal counter, its parent arrays and its cache (:879-890, :907-918).
  6. Nothing replaces the manager, because initReaderManager only looks at the flag. closeResources closes it again, which is a no-op (DirectoryTaxonomyWriter.java:308-313, ReferenceManager.java:135), so close() and rollback() work.

Why a file is closed at all

#

The internal reader is opened at the writer's first cache miss. In the test the index then has one segment, _0. The first nine addCategory + commit calls each add a small segment. With _0 that makes ten, and the writer's merge policy (LogByteSizeMergePolicy, DirectoryTaxonomyWriter.java:240-242; merge factor 10) merges them into _a; the tenth call adds _b. Afterwards the latest commit holds the segments _a and _b, and _0.cfs is still in the directory only because the internal reader uses it. Closing that reader therefore closes _0.cfs, and that is the close the test makes fail (the probe's output names _0.cfs, under ReferenceManager.close:139 called from perhapsFillCache:658). Without a merge the reader is not the last user of any file, and its close touches no file (an earlier control).

Exposure and likelihood750 words
  • Who. An application that keeps a DirectoryTaxonomyWriter in use after one addCategory call (or FacetsConfig.build, which calls it) threw an IOException, when that exception came from the one reader close at the end of the cache fill.
  • What it takes. All of the following:
    • a taxonomy opened for append that fits the writer cache when it is filled (at most 4,000 categories by default). A larger one aborts the fill and the reader is not closed there (an earlier control);
    • a merge that retires the segments the internal reader was opened on, between the writer's first cache miss and the fill (misses 1 to 11 by default). Without it the close touches no file and nothing fails (an earlier control);
    • an exception from that close;
    • continued use of the writer, and then a call that uses the internal reader manager: an addCategory whose cache insertion evicts (growth past the cache size), replaceTaxonomy or reindexWithNewOrdinalData.
  • Triggers executed, all injected. No run used a real I/O error. An IOException from closing a file handle of the retired segment (the test). In earlier runs also: an IOException from Directory.deleteFile during the same close, and an application's segment-closed listener that throws, on a stock MMapDirectory.
  • Not with the default directory. The default MMapDirectory's input close unmaps the file and has no path that throws an IOException (MemorySegmentIndexInput.java:703-726; FSDirectory.open returns MMapDirectory on 64-bit JVMs, FSDirectory.java:155-161). FSDirectory records a failed delete as a pending delete, except for a missing file, which it rethrows (:337-367). NIOFSDirectory closes a FileChannel there (NIOFSDirectory.java:122-126); a custom, filter or remote Directory may throw.
  • Default writer settings. The default cache evicts since 9.5.0 (LruTaxonomyWriterCache(4000)). Earlier releases reach the eviction path only with an explicitly chosen LruTaxonomyWriterCache. The two other calls below need no eviction; they were run with the default cache on main, branch_11x and 10.6.0.
  • What the user sees from addCategory. Only calls whose cache insertion evicts throw. With the default cache: the 3,990th new category after the failure, then the 5,325th (one per 1,335). Each failing call has already indexed its category, and calling it again returns the ordinal from the cache.
  • Two other calls throw without an eviction. replaceTaxonomy and ReindexingEnrichedDirectoryTaxonomyWriter.reindexWithNewOrdinalData refresh the manager after they have already changed the index (DirectoryTaxonomyWriter.java:872-891, :902-919), so on a writer in this state they throw AlreadyClosedException half-way, with any cache. Executed: after the failed replaceTaxonomy the writer still reports the old size and hands out ordinals from its old counter and cache (11, 1 and 12 where a working call gives 1, 3 and 4), and commit() and close() then store a taxonomy with one label at two ordinals and another one missing. After the failed reindexWithNewOrdinalData, close() stores an empty taxonomy. rollback() instead of close() returns to the last commit in both cases. With the fix both calls work. That half-done state is the subject of two other entries, LFV-978 and LFV-977 (neither call is failure-atomic); the closed manager is one more way to get an exception in the middle.
  • What still works. In the repro's state: getSize, getParent (the parent arrays are already built), commit and lookups of cached categories; the internal IndexWriter stays open with no tragic exception (earlier controls). After a failed addCategory, close() or rollback() and a reopen recover fully: the reopened taxonomy is consistent.
  • Likelihood: contrived (an estimate, not usage data). No report of it since 2012 was found.
  • Not claimed.
    • A documented guarantee that the writer recovers after an IOException. There is none.
    • "Every later call fails." Only calls that use the internal reader manager throw: an addCategory whose cache insertion evicts, replaceTaxonomy, reindexWithNewOrdinalData, and the second path below.
    • Second ordinals. On stock main the same failure can also end with an existing category getting a second ordinal, because the refresh that throws sits before cacheIsComplete = false (DirectoryTaxonomyWriter.java:491-492). That statement order is the root of another entry, LFV-521, and is not counted here. The probe never re-adds a label that the cache has evicted, so it shows no second ordinal.

Why it looks unintended

#
  • The code's own comment says the manager is dropped here: "no need to keep readerManager open". The statements have no failure path.
  • The writer ends up neither closed nor usable: commit and cached lookups work, calls that need the reader throw.
  • Nothing documents or tests that state. No javadoc promises recovery after an IOException either: the claim is the invariant.
The full argument417 words
  • The code states the intent. The comment at DirectoryTaxonomyWriter.java:655 says the manager is no longer needed and is dropped; on the success path it is. The statements at :658-660 have no failure path.
  • The state is neither closed nor usable. After the failure getSize(), commit() and cached lookups work, the IndexWriter is open, and the calls that use the reader manager throw: an addCategory whose cache insertion evicts, after indexing its document, and replaceTaxonomy and reindexWithNewOrdinalData, after changing the index. AlreadyClosedException came to this writer for the case that it "has been closed/rollback" (#4653, LUCENE-3579, Shai Erera). ensureOpen documents it that way: "Verifies that this instance wasn't closed, or throws AlreadyClosedException if it is" (:431-438). Upstream tests expect it only after close() or rollback() (TestDirectoryTaxonomyWriter.java:165-180, :193-206).
  • ReferenceManager documents a closed manager as unusable. "Applications should not acquire new references from this manager once this method has been called" (ReferenceManager.java:127-129); maybeRefresh throws AlreadyClosedException "if the reference manager has been closed" (:204). The writer keeps calling it.
  • The design needs a reader again once the cache has evicted. On LUCENE-4061 (#5133) Shai Erera explained why the reader is closed: "The TaxoWriterCache can be 'complete' ... In that case, it is a waste to keep the reader open and we close it", and for the LRU cache: "it can be 'complete' until it evicts the first entry, in which case it will never be complete, and we'll need to keep the reader open". When the close succeeded, the writer opens a new reader at its next on-disk lookup after an eviction (the control run ends with one). Here the eviction itself already throws.
  • No test or discussion covers a failing close. No test under lucene/facet/src/test injects an I/O failure. The commits that wrote the lines (LUCENE-4061, LUCENE-4565) and their threads (#5133, #5631) never mention a close that throws.
  • The trigger is legal. IndexInput.close() and Directory.deleteFile declare IOException. The injected failure happens once and releases the file first, so the directory behaves like a stock one afterwards.
  • Upstream has fixed comparable exception-cleanup gaps as bugs. LUCENE-8244 in this module ("Do not leak open file descriptors in SearcherTaxonomyManager's refresh on exception"), LUCENE-5553 ("IndexReader#ReaderClosedListener is not always called on IndexReader#close()") and LUCENE-4246 ("fix IW.close to just close, even on exception").
  • What is not claimed. That the writer is documented to stay usable after addCategory threw an IOException. The request is that an open writer never keeps a closed manager installed.
The devil's-advocate check242 words

The strongest case for "intended", or at least "outside the contract": nothing promises that the writer stays usable after addCategory threw an IOException, and both TaxonomyWriter and DirectoryTaxonomyWriter are marked experimental. IndexWriter's javadoc says that after an Error, or when "disaster strikes during a checkpoint", "IndexWriter will close itself ... Any subsequent calls will throw an AlreadyClosedException" (IndexWriter.java:164-167), and in an earlier control run a file-close failure inside one of its own merges did close it. The one comparable maintainer statement of this autumn, by Uwe Schindler on #16937 and #16951 about IndexInput, is that after an IOException the object's state is undetermined and "it is recommended to close it"; since 2026-11-15 the IndexInput javadoc says so (#17026, merged to main and branch_11x). The documented exits work here: close or roll back, then reopen. And the trigger is remote.

Why it does not make the behaviour intended: the writer does not close itself. It stays half usable, and whether a call throws depends on whether the cache happens to evict. IndexWriter's self-close is documented and consistent; this state is neither. The author's design remark says that a reader is needed again after an eviction. The fix is small (four new lines, three re-indented) and changes nothing on the success path. What does survive is the question of worth: a maintainer may answer "after an IOException, close the writer". That is why this is rated Low.

Suggested fix

#

Recommended try/finally around the close: 7 insertions, 3 deletions (validated)

Wrap the close in try/finally so the field and the flag are always cleared: 7 insertions and 3 deletions in perhapsFillCache (four new lines). The injected IOException is still thrown once; later calls create a new manager when they need one. Validated: the test passes, and so do the 18 upstream taxonomy test classes, the facet module and check.

-        readerManager.close();
-        readerManager = null;
-        initializedReaderManager = false;
+        try {
+          readerManager.close();
+        } finally {
+          // never keep a closed manager installed, even if close() throws
+          readerManager = null;
+          initializedReaderManager = false;
+        }

try/finally around the close: 7 insertions, 3 deletions (validated) (recommended)

#

In perhapsFillCache, put readerManager.close() into a try and the two clearing statements into its finally (DirectoryTaxonomyWriter.java:658-660). The exception of the failed close still propagates from the same addCategory call. Afterwards the writer holds no manager, and the next call that needs one creates a new one through initReaderManager.

-        readerManager.close();
-        readerManager = null;
-        initializedReaderManager = false;
+        try {
+          readerManager.close();
+        } finally {
+          // never keep a closed manager installed, even if close() throws
+          readerManager = null;
+          initializedReaderManager = false;

Trade-offs

  • Success path unchanged. The same three statements run in the same order when the close does not throw.
  • The failure stays visible. The IOException is still thrown once; nothing is swallowed.
  • Scope. closeResources has the same three statements (:308-313). There the writer is already marked closed, so it is not part of this bug and the patch leaves it alone.
  • The retired segment's files are released. In the probe they are gone from the directory after the failed call, with and without the fix.

Uninstall the manager first, then close it (validated by the checks)

#

Copy the field to a local variable, clear the field and the flag, then close the local. Same effect without a try block. The idea comes from the independent reproduction of this bug.

-        readerManager.close();
+        // uninstall the manager first, then close it
+        ReaderManager toClose = readerManager;
         readerManager = null;
         initializedReaderManager = false;
+        toClose.close();

Trade-offs

Two lines shorter than the try/finally (3 insertions, 1 deletion). It changes the statement order on the success path, which is harmless inside the synchronized block.

What the checks validated

Standalone runner with the changed class ahead of the main jars: the test passes, assertions on and off, and the second probe prints the same lines as with the try/finally. Not run through gradle.

Make the failure final (not built)

#

Treat an exception from this close like a tragic event: mark the writer closed, so that every later call throws AlreadyClosedException consistently, as IndexWriter does after a tragic exception.

Trade-offs

Consistent, but it turns a failed close of a reader the writer no longer needs into the loss of the writer, and it is a behaviour change. Not built.

Workaround: reopen the writer after an IOException

#

After addCategory throws an IOException, call close() or rollback() and open a new writer.

Trade-offs

Not a fix. Executed: after the failure commit() and close() work, the reopened taxonomy is consistent and a new writer adds the next category (the probe); earlier controls did the same with close() and with rollback() right after the failed call. After a failed replaceTaxonomy or reindexWithNewOrdinalData only rollback() returns to the last commit (second probe); close() stores the half-done taxonomy.

Downstream note

#

A long-lived service on a custom or remote Directory that retries addCategory after an IOException without reopening its taxonomy writer can see later indexing calls fail with AlreadyClosedException.

How it was found

#

A fault-injection study ran the real taxonomy classes with one I/O failure at a time. Its standard runs never reach this line, because their taxonomies never merge. The unguarded statement order was noticed while reading the code. A targeted check that fails each of the 6 directory calls of the cache-filling addCategory flagged the two file closes.

The method in full206 words

Method: bounded single-fault enumeration on the real classes, then a targeted check (the study's "semi-formal" tier: a hypothesis formed while modelling and then shown by a tool).

  • The model. Small taxonomy workloads run on the stock jars with one injected IOException per run, at each counted directory call in turn. After the failure the writer is kept in use and its results are checked.
  • Why the standard runs miss it. Their taxonomies never merge, so the writer's internal reader is never the last user of a file, and closing it touches nothing that can fail.
  • The lead. The close-then-clear order at the end of perhapsFillCache was noted while reading the code for the model, and an independent critique of the model's blind spots named the same lines.
  • The targeted check. A new fault site, "close of a top-level file handle", on a taxonomy that merges, with every writer default: of the 6 counted directory calls of the cache-filling addCategory (four reads, two closes), the two closes leave a writer that is open and later throws AlreadyClosedException (after 3,955 more categories in that run).
  • Reduction. First to a same-package test with a forced merge, then to a public-API test, then to the one-method test of the repro.

LFV-1480, snapshot of 2026-11-18

Registry title
DirectoryTaxonomyWriter keeps a closed ReaderManager installed when closing it fails at the end of the cache fill, so addCategory on the still-open writer throws AlreadyClosedException whenever it next needs its internal reader, at every later cache eviction (since 4.0.0)
Area
facet / taxonomy writer (DirectoryTaxonomyWriter cache fill, perhapsFillCache, and the lifecycle of its internal near-real-time ReaderManager after a failed close)
Priority
Low, rank 1176: After one failed internal reader close at the end of its cache fill, a DirectoryTaxonomyWriter that stays in use throws AlreadyClosedException from addCategory at every later cache eviction until it is closed or rolled back and reopened, in every release since 4.0.0 (with the default writer cache since 9.5.0). It is Low because the default MMapDirectory cannot produce that close failure, the taxonomy must also be opened for append, fit the writer cache and have had a merge retire the segments its internal reader holds, the failure is loud, and reopening the writer recovers (after a failed replaceTaxonomy or reindexWithNewOrdinalData, which run into the closed manager too, only rollback() does).
Impact class
minor
Impact note
Applications that index taxonomy facets and keep a DirectoryTaxonomyWriter in use after one addCategory (or FacetsConfig.build) call threw an IOException are hit only when that IOException came from the one internal reader close at the end of the writer's cache fill: the taxonomy was opened for append and fits the writer cache (at most 4,000 categories by default), a merge had retired the segments the internal reader was opened on, and closing or deleting one of their files (or an application's segment-closed listener) threw, which the default MMapDirectory's input close cannot do and an FSDirectory delete does only for a missing file (any other failed delete is recorded as pending), so it takes NIOFSDirectory with a failing descriptor close or a custom, filter or remote Directory; from then on every addCategory whose cache insertion evicts entries throws AlreadyClosedException after it has already indexed its category document (with the default 4,000-entry cache the first one about 3,990 new categories later, then about one per 1,330), until the writer is closed or rolled back and reopened, which works; default writer settings from 9.5.0 (earlier releases need an explicitly chosen LruTaxonomyWriterCache), -ea and -da, no scale needed.
Summary
You reopen an existing taxonomy with a DirectoryTaxonomyWriter and add categories, committing as you go; at its 11th cache miss the writer has read every category into its cache and closes its internal near-real-time reader, and that close fails once with an IOException (here the close of a file of a segment that a merge has already retired), so that addCategory call throws. You expect a writer that is still open (it was never closed or rolled back, and its IndexWriter is open) not to keep a reader manager that is already closed: it should drop it, as it does when the close succeeds, so that later addCategory calls do not fail because of it. Instead the closed ReaderManager stays installed for the rest of the writer's life, and every later addCategory whose cache insertion evicts entries throws AlreadyClosedException ('this ReferenceManager is closed') after it has already indexed the category's document (the second call after the failure in the shipped test, which uses a 12-entry cache), until the writer is closed or rolled back and reopened.
