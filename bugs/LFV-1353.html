Multi-threaded CheckIndex loses an interrupt that arrives at the end of the check

An interrupt sent to the thread running a multi-threaded CheckIndex.checkIndex() (the default whenever the JVM reports more than one processor) just as the check ends, for example by Future.cancel(true), is silently lost: the call returns its correct Status with the flag cleared. setThreadCount(1) keeps it; every release since 8.11.0.

The finding in 30 seconds

#

With threadCount > 1, checkIndex() runs the segment checks on its own thread pool. On the way out, a finally block shuts the pool down and waits for it. If the calling thread was interrupted by then, that wait throws, and the catch only logs the error: it neither rethrows nor restores the interrupt.

Interrupts in Java, in two lines

#
  1. Thread.interrupt() sets a flag on a thread: the standard way to ask it to stop, used for example by Future.cancel(true) and ExecutorService.shutdownNow().
  2. A blocking call that sees the flag throws InterruptedException and clears it. Code that catches the exception must rethrow it or set the flag again, or the request to stop is lost.

The finding, step by step

#
  1. Index one empty document. Run checkIndex() with setThreadCount(2) (the default thread count takes the same path whenever the JVM reports more than one processor) and interrupt the checking thread when the check prints its last line, "Took ... sec total.", as a Future.cancel(true) at that moment would.
  2. You expect the interrupt to survive: a ThreadInterruptedException, Lucene's usual way to report one, or the flag still set when checkIndex() returns, as it is with setThreadCount(1) (20 of 20 runs).
  3. Instead checkIndex() returns its clean Status normally and Thread.interrupted() is false: 196 of 200 runs with assertions on, 195 of 200 with them off, 20 of 20 through gradle (assertions on).
  4. Why: on the way out, CheckIndex shuts down its internal thread pool and waits up to 5 s for it. That wait sees the pending interrupt, throws InterruptedException and clears the flag, and the catch only logs "ERROR: Interrupted exception occurred when shutting down executor service".
  5. Code after the call never learns it was cancelled: in a probe, a Thread.sleep(2000) after a cancelled checkIndex() ran the full 2 s. One added line, Thread.currentThread().interrupt(); in that catch, fixes it (200 of 200 runs pass).

Who is affected

#

Applications that run CheckIndex with more than one thread (the default whenever the JVM reports more than one processor) and cancel it by interrupting its thread, for example Future.cancel(true). Only an interrupt in the short tail after the last segment result is lost; the Status is correct and the index untouched. Rare.

Mechanism, terms and numbers500 words

CheckIndex.checkIndex() checks segments on a private thread pool whenever threadCount > 1, and threadCount defaults to Runtime.getRuntime().availableProcessors() (CheckIndex.java:541, pool at :593-596). When the check is done, the finally block of checkIndex(List) calls shutdown() and awaitTermination(5, TimeUnit.SECONDS) (:603-605). If the calling thread has been interrupted after its last wait for a segment result and the pool has not terminated yet (the usual case right after shutdown()), awaitTermination throws InterruptedException and clears the flag, and the catch (:606-610) only writes "ERROR: Interrupted exception occurred when shutting down executor service" and a stack trace to the info stream: no rethrow, no restored flag. So checkIndex() returns its correct Status normally and the caller's cancellation is lost; with setThreadCount(1) there is no pool and the same interrupt stays set. The repro races with the pool's termination (about 98% of runs fail). The block came with concurrent CheckIndex (LUCENE-9662, #128, 2021), so every release from 8.11.0 to 10.6.0 and main are affected. One line, Thread.currentThread().interrupt(); in that catch, fixes it; it is the line the JDK's shutdownAndAwaitTermination idiom has and this block lacks.

The path (file:line at 5adff78bb168, lucene/core/src/java/org/apache/lucene/index/CheckIndex.java)

#
  1. Which path. checkIndex() calls checkIndex(null) (:577-579). With threadCount > 1 (default availableProcessors(), :541) it creates Executors.newFixedThreadPool(threadCount, new NamedThreadFactory("async-check-index")) (:593-596) and returns checkIndex(onlySegments, executorService) (:600).
  2. The check. The caller collects each segment's result in order with futures[i].get() (:909), then finishes on its own thread, prints "Took %.3f sec total." (:961-963) and returns the Status (:965).
  3. The bug. The finally (:601-615) calls shutdown() (:603) and awaitTermination(5, TimeUnit.SECONDS) (:605). Its catch (InterruptedException e) (:606-610) writes the ERROR line and the stack trace to the info stream when one is set, and nothing else; shutdownNow() follows (:612). The return value of :600 stands.
  4. Why it nearly always fires. JDK 25 ThreadPoolExecutor.awaitTermination (ThreadPoolExecutor.java:1412-1427) returns at once only if the pool is already terminated; otherwise it waits on a condition, which throws at once for an interrupted thread. Right after shutdown() the idle workers have usually not exited yet. When they have, the wait is skipped and the flag survives; by this code reading, that explains the 4 to 5 passing runs in 200.
  5. The window. Any interrupt that reaches the caller after its last wait on an unfinished segment result: CompletableFuture.get() returns a finished result without looking at the flag, so an interrupt after the first of two segments, when the second is already done, is lost too (5 of 5 runs). An interrupt while the caller still waits in futures[i].get() goes to the other catch (:910-918), a different bug (LFV-631, a NullPointerException).
  6. Sequential path. With threadCount == 1 the executor is null, the finally does nothing, and the flag is kept. The public checkIndex(List, ExecutorService) overload (:618-626) uses the caller's executor and never runs this finally.
Exposure and likelihood230 words
  • Who is hit. Code that runs CheckIndex in a cancellable task (a maintenance job, an admin request, a shutdown) and cancels it by interrupting the thread: Future.cancel(true), shutdownNow(). Elasticsearch #18839 is an example of the pattern: it cancelled a shard's check index by interrupting it (written before concurrent CheckIndex; it shows the call pattern and does not report this bug).
  • Default vs opt-in. The default threadCount takes the pool path whenever the JVM reports more than one available processor, and so does setThreadCount(n > 1); the command-line tool uses the same default unless -threadCount is given. Interrupting is the opt-in part.
  • Effect. Silent: no exception, a correct Status, but the interrupt is gone, so interruptible work the thread does next is not cancelled (in a probe with Future.cancel(true), a following 2 s sleep ran in full; with setThreadCount(1) it was interrupted). The Future itself is still cancelled; what is lost is the signal to the code that keeps running inside the task.
  • Scale. Any index size; the repro has one empty document.
  • Likelihood: rare. The interrupt must land between the caller's last wait for a segment result and the pool's termination. By reasoning, not measured, a randomly timed cancellation of a long check is more likely to arrive while the caller still waits in futures[i].get(), which is LFV-631's path. CheckIndex is @lucene.experimental.

Why it looks unintended

#
  • The handler itself calls the case an "ERROR", and the same call with setThreadCount(1) keeps the interrupt.
  • Lucene's convention (LUCENE-1573, LUCENE-2053, the IndexWriter javadoc) is to throw ThreadInterruptedException; 21 of 23 interrupt catches in lucene-core throw or restore; the other two are in CheckIndex.
  • The block copies the JDK's shutdownAndAwaitTermination idiom minus its "Preserve interrupt status" line.
The full argument223 words
  • The handler's own message: "ERROR: Interrupted exception occurred when shutting down executor service" (CheckIndex.java:609).
  • The sequential path keeps the flag: same call and index with setThreadCount(1), the interrupt is still set afterwards (20 of 20 and 50 of 50 runs in two probes). Whether a caller's cancellation survives should not depend on the thread count.
  • Project convention. CHANGES LUCENE-1573 (2.9.0): "Do not ignore InterruptedException (caused by Thread.interrupt()) nor enter deadlock/spin loop. Now, an interrupt will cause a RuntimeException to be thrown." LUCENE-2053 (3.0.0): "you'll get an oal.util.ThreadInterruptedException". The IndexWriter class javadoc says the same (IndexWriter.java:172-175). Where Lucene must ignore an interrupt, it restores it in a finally ("finally, restore interrupt status", ConcurrentMergeScheduler.java:497-510).
  • The rest of lucene-core. Of the 23 catch (... InterruptedException ...) sites in lucene/core/src/java at 5adff78bb168, 21 throw, wrap and throw, or restore the flag; the only two that do neither are CheckIndex.java:606 (this bug) and :910 (LFV-631).
  • The JDK idiom. The ExecutorService javadoc's shutdownAndAwaitTermination (JDK 25 ExecutorService.java:121-137) is shutdown(), awaitTermination, and in the catch shutdownNow() plus "// Preserve interrupt status" Thread.currentThread().interrupt();.
  • History. The block came with LUCENE-9662 (#128); in review dweiss asked "Add await; shutdown is non-blocking.", which added the awaitTermination. No review comment, test, CHANGES or MIGRATE entry discusses interrupts or pins the cleared flag.
The devil's-advocate check131 words

The case: CheckIndex is experimental and documents no interrupt policy; the check has already finished and its Status is right; and Lucene maintainers have said Lucene will not support Thread.interrupt as a cancellation mechanism (#12023, #11805). Every reviewer made this case; the cross-model reviewer rated it moderate.

Why it fails: those statements reject adding interrupt checks to searches; none says Lucene may consume and drop an interrupt its caller received. The open LUCENE-4649 (#5714) proposes the same restore-status idiom, Thread.currentThread().interrupt(); // restore status, in another catch (InterruptedException) (its example is an fsync catch that then throws), and says "the guy doing the catch (InterruptedException) should do the right thing". The fix asks for no new cancellation support, only for not clearing the flag. The case does keep the bug Low.

Suggested fix

#

Recommended A: restore the interrupt flag in the catch

Add Thread.currentThread().interrupt(); to the catch around awaitTermination (CheckIndex.java:606-610): one line, the JDK idiom's missing step. Validated: the repro passes through gradle with assertions on and off, TestCheckIndex* and TestIndexWriter pass, and the formatter and forbidden-API checks are clean.

A: restore the interrupt flag in the catch (validated by the checks) (recommended)

#

One line in CheckIndex.java:606-610, after the log and the stack trace.

} catch (InterruptedException e) {
  msg(
      infoStream,
      "ERROR: Interrupted exception occurred when shutting down executor service");

Trade-offs

The smallest change, and the same outcome as the sequential path: checkIndex() still returns its Status (or the exception already in flight), and shutdownNow() runs as before. It does not touch LFV-631's catch (:910-918), which needs its own fix.

B: restore the flag and throw ThreadInterruptedException (not run)

#

IndexWriter's convention: report the interrupt as an exception.

Trade-offs

Loud, but the throw would come from a finally block: it discards the Status the check just computed and replaces any exception already propagating (a fail-fast CheckIndexException, or LFV-631's exception). The minimal repro would then end in an error, so it needs a different test.

C: use ExecutorService.close() (not run)

#

JDK 19+ close() waits for the tasks and re-asserts the interrupt if it was interrupted.

Trade-offs

It waits for running checks without the 5 s bound, a behaviour change on the fail-fast path, and it is not available on Java 11, which the 9.x line targets.

Downstream note

#

Services that cancel a running index check by interrupting its thread (a cancellable admin or maintenance task) can miss a cancellation that lands at the end of a multi-threaded check; the check result itself is unaffected.

How it was found

#

A semi-formal proof-obligation audit of CheckIndex.checkIndex's interrupt handling: for each place that catches InterruptedException, does the interrupt still reach the caller? This catch neither rethrows nor restores it. A JUnit repro on main witnessed the lost flag.

The method in full125 words

Method: semi-formal, a proof-obligation audit witnessed by an executable repro. The audit went through CheckIndex.checkIndex's interrupt handling on main 5adff78bb168 and asked of each InterruptedException catch whether the interrupt is rethrown (as ThreadInterruptedException) or the flag restored. The catch around awaitTermination in the pool shutdown does neither. A one-test JUnit repro with public API only (an info stream that interrupts the checking thread at the last line of the check) then showed the flag lost with threadCount 2 and kept with threadCount 1.

Independent checks followed: a separate reproducer with its own test, a reviewer from another model family (OpenAI GPT-5.6) asked to refute it, an intended-behaviour devil's advocate, an adjudication, registry re-runs and a credibility audit; all confirmed it, at Low priority.

Summary
You run CheckIndex.checkIndex() with more than one thread (the default on a multi-core machine) and your application interrupts that thread near the end of the check, for example with Future.cancel(true) to stop the job. You expect the interrupt to be reported (Lucene's convention is to throw ThreadInterruptedException) or at least left set, as it is when the same check runs with setThreadCount(1). Instead the finally block that shuts down CheckIndex's internal thread pool catches the InterruptedException from awaitTermination, only writes 'ERROR: Interrupted exception occurred when shutting down executor service' to the info stream, and returns the Status normally, so Thread.interrupted() is false and the cancellation is lost.
