Re-sorting with SortingCodecReader and addIndexes throws when a segment lacks a quantized vector field

Re-sorting an index the way the SortingCodecReader javadoc describes fails (NullPointerException, or AssertionError with assertions on) when a segment that has other vectors lacks a quantized float vector field: 2 segments of 3 documents, 0 of 6 added. Affects 10.2.0 to 10.5.2 and main; the default format is fine.

The bug in 30 seconds

#

Quantized vector formats store each vector relative to a centroid, the average vector of the segment. A merge recomputes the centroid from every source segment, and the code assumes that a segment without the field answers null. SortingCodecReader, the documented way to re-sort an index, does not.

  1. Your codec stores field vec with Lucene104HnswScalarQuantizedVectorsFormat. Segment 1 has 3 documents with a float vector vec and a byte vector other; segment 2 has 3 documents with only other.
  2. You re-sort as the SortingCodecReader javadoc says: wrap both segments with SortingCodecReader.wrap(reader, sort) and pass them in one addIndexes call to a fresh writer with setIndexSort(sort). You expect 6 documents, 3 with a vec vector, as the default Lucene99HnswVectorsFormat gives on the same index.
  3. Instead the quantized writer recomputes the centroid of vec by asking every segment for its vec vectors, without checking whether that segment has the field. A plain segment answers null and is skipped; SortingCodecReader wraps the null instead.
  4. addIndexes throws NullPointerException (AssertionError with -ea) and adds 0 of 6 documents. The source index is unchanged; one addIndexes call per segment works.

Who is affected

#

Applications that re-sort an index with SortingCodecReader and one addIndexes call over several segments, using a quantized vector format on a float field that a reordered segment lacks while it has another vector field. The default format, ordinary flushes, merges and queries are not affected; one addIndexes call per segment avoids it.

Mechanism, terms and numbers926 words

SortingCodecReader's javadoc describes how to re-sort an existing index: wrap all its readers and add them to a fresh IndexWriter with addIndexes(CodecReader...). With a quantized vector format (Lucene104[Hnsw]ScalarQuantizedVectorsFormat on 10.4+ and main, the Lucene102 BBQ formats on 10.2-10.3) this fails when one segment has vectors for some other field but none for a float32 or fp16 field that uses the quantized format (byte fields skip the centroid code). To recompute the merged centroid, Lucene104ScalarQuantizedVectorsWriter asks every source reader for the field and skips a source only when the answer is null; it never checks that source's FieldInfos, although KnnVectorsReader#getFloatVectorValues is undefined for such a field and "never null". The per-field reader of a plain segment happens to answer null, so ordinary merges pass, but SortingCodecReader wraps the null and fails: NullPointerException at SortingCodecReader.java:252 with assertions off, AssertionError at :318 with assertions on (fp16 fields: the NullPointerException either way). addIndexes throws and adds nothing; the source index is unchanged. It is a new instance of the bug class #13641 fixed for the other vector writers in 9.12.0. Introduced in 10.2.0 by #14078; affects 10.2.0 to 10.5.2 and main.

Terms

#
  • Centroid: the quantized formats (Lucene104ScalarQuantizedVectorsFormat, Lucene104HnswScalarQuantizedVectorsFormat; on 10.2-10.3 the Lucene102 BBQ formats) quantize each vector relative to the segment's average vector. When segments merge, the writer computes the merged segment's centroid from the source segments.
  • Re-sort recipe: SortingCodecReader's javadoc: "This can be used to re-sort and index after it's been created by wrapping all readers of the index with this reader and adding it to a fresh IndexWriter via IndexWriter#addIndexes(CodecReader...)". addIndexes merges all the readers into one segment by default.
  • FieldInfos: each segment's list of fields. A segment where no document has vec has no vec entry.
  • The reader contract: KnnVectorsReader#getFloatVectorValues: "The behavior is undefined if the given field doesn't have KNN vectors enabled on its FieldInfo. The return value is never null." So a merge must check the source's FieldInfos first; the generic merge and the Lucene99 writers do (MergedVectorValues.hasVectorValues, added by #13641).

The bug

#
  1. Lucene104ScalarQuantizedVectorsWriter.mergeOneFlatVectorField calls mergeAndRecalculateCentroids for a float32 or fp16 field (Lucene104ScalarQuantizedVectorsWriter.java:351-360).
  2. Its first loop asks every source through floatingPointVectorValues and skips a source only when the reader or its answer is null (:597-605). A SortingCodecReader-wrapped source has no stored centroid (:569-575), so the loop stops and recalculates (:614-617, :625): calculateCentroid skips only a null reader (:642-646), accumulateCentroid only a null answer (:663-666). Neither loop looks at mergeState.fieldInfos[i]; the helper's javadoc states the assumption, it returns "null when the field is absent from this reader" (:577-591).
  3. A plain segment's reader is PerFieldKnnVectorsFormat.FieldsReader, which returns null for a field not in its FieldInfos (PerFieldKnnVectorsFormat.java:280-287, fp16 :311-318). That is why ordinary flushes and merges pass.
  4. SortingCodecReader's vectors reader wraps the answer unconditionally: new SortingFloatVectorValues(delegate.getFloatVectorValues(field), docMap) (SortingCodecReader.java:631; byte :636, fp16 :641). The constructor asserts delegate != null (:318), then iteratorSupplier calls values.iterator() (:252). SortingFloat16VectorValues has no assertion (:402-406), so fp16 fields get the NullPointerException even with -ea. For points the same class passes a null through (:602-607).
  5. When the lacking segment comes first, the first loop fails (:602); otherwise calculateCentroid does (:646). Both were executed.

When it happens

#
  • a quantized format on a float32 or fp16 field that some segment lacks (quantized only on a field every segment has passes; a byte field skips the centroid code, Lucene104ScalarQuantizedVectorsWriter.java:356-358);
  • the lacking segment goes into one addIndexes call as a SortingCodecReader, with at least one other segment that has the field. In the javadoc recipe every segment is wrapped, so that means two or more wrapped segments; strictly only the lacking one must be wrapped, and the destination needs no index sort (executed: wrapping only the lacking segment fails, wrapping only the other passes);
  • the lacking segment has some other vector field (executed: byte, float32, or float32 in the non-quantized format all fail; other encodings by reading), so it has a vectors reader; a segment with no vector field at all has none and is skipped;
  • the sort reorders that segment; an already sorted segment (for example a one-document segment) is wrapped in a plain FilterCodecReader (SortingCodecReader.java:458-460), which answers null.

IndexWriter's own reorder paths (one SortingCodecReader over a single SlowCompositeCodecReaderWrapper, IndexWriter.java:3561-3564, :5557-5576) and BpVectorReorderer.reorderIndexDirectory (one addIndexes per segment) are not affected by code reading; they were not executed.

Exposure and likelihood348 words
  • Who. Applications that re-sort an existing index with the documented recipe (for example to add or change an index sort, or to reorder documents) and use a quantized vector format for a field that some segment lacks while that segment has another vector field. Realistic shapes: a second embedding field added later, so old segments have only the first; or an optional embedding that a whole segment happens to lack.
  • Default vs opt-in. The default codec uses the non-quantized Lucene99HnswVectorsFormat, which is not affected; the quantized formats are opt-in. From 10.4.0 the older int8 formats, which have the check, are read-only legacy, so every writable quantized format in core is affected. SortingCodecReader and the Lucene104 quantized formats are @lucene.experimental.
  • Scale. No size threshold: 3 documents per segment are enough, as long as the sort reorders the lacking segment. The failure is deterministic (10 of 10 runs; the compact test also fails the same 4 tests in each of 5 iterations with another seed).
  • Effect. A loud failure: addIndexes throws, nothing is added, nothing is corrupted, and the source index is unchanged. With assertions off the writer stays open, and each failed attempt leaves its partly written files in the target directory until the writer is closed (measured: 25 failed attempts, up to 326 files and 281,850 bytes, removed at close). With assertions on, a float32 field's AssertionError closes the writer as a tragic event; an fp16 field's NullPointerException leaves it open in both modes.
  • One way to lose data. An in-place re-sort (OpenMode.CREATE on the source directory, all segments in one call) that closes the writer after the failure with the default commitOnClose commits an empty index over the original (measured: 40 to 0 documents). That is documented close() behaviour applied to any failure in that pattern, not something Lucene commits wrongly.
  • Workaround. One addIndexes call per segment (measured: the in-place per-segment re-sort keeps all 40 documents, as 2 segments rather than one merged segment). Writing into a separate directory does not avoid the exception; it only protects the source from the in-place outcome above.

Why it is a bug, not intended

#
  • The getter's contract: "undefined" for a field missing from the segment's FieldInfo, and "never null". The caller that breaks it is Lucene's own writer.
  • #13641 made the check a merge rule ("we must verify that a given field has vectors and exists"); the other vector writers follow it.
  • The trigger is the documented re-sort recipe.
The full argument239 words
  • Contract. KnnVectorsReader#getFloatVectorValues: "The behavior is undefined if the given field doesn't have KNN vectors enabled on its FieldInfo. The return value is never null" (KnnVectorsReader.java:64-69; the byte and fp16 getters say the same, :82-87, :89-94). The application never calls the getter; the writer does.
  • The stated rule. #13641 (74e3c44063a, 2024-09-11): "During segment merge we must verify that a given field has vectors and exists. The typical knn format checks assume the per-field format is used and thus only check for null. But we should check for field existence in the field info and verify it has dense vectors". CHANGES 9.12.0: "Unify how KnnFormats handle missing fields and correctly handle missing vector fields when merging segments". It added KnnVectorsWriter.MergedVectorValues.hasVectorValues, used by the generic merge (KnnVectorsWriter.java:350), Lucene99HnswVectorsWriter (:520) and the int8 writer.
  • Documented use. SortingCodecReader's javadoc prescribes exactly this re-sort (SortingCodecReader.java:47-51); nothing requires every segment to carry every vector field.
  • History. #14078 (10.2.0) wrote the BBQ centroid loops six months after #13641, with the null-only check; #15169 (10.4.0) copied them byte for byte; #16473 (main) routed fp16 through them. None of the reviews discusses absent fields or SortingCodecReader.
  • Tests. TestSortingCodecReader uses a single vector field. BaseKnnVectorsFormatTestCase.testMergingWithDifferentKnnFields asserts that such merges work, but passes for these formats because their own readers answer null. No CHANGES or MIGRATE entry, documentation or discussion accepts the crash.
The devil's-advocate check209 words

The intended-behaviour verifier, a review by a model from another family and the cross-model fact check of this doc built the strongest case for "works as designed": the contract makes the lookup undefined, so SortingCodecReader's assertion is allowed; SortingCodecReader and the formats are @lucene.experimental; the format is opt-in, the path uncommon and the failure loud with the source unchanged; and the writer documents its own assumption ("null when the field is absent from this reader"), which holds for the per-field reader and the raw Lucene104 reader.

Why it still is a bug: the undefined-behaviour clause binds the caller, and the caller is the writer, not the application, which follows the documented recipe. @lucene.experimental lowers severity, not validity. The helper's javadoc contradicts the abstract contract and #13641's rule; it explains how the bug arose, not that the crash is intended. Which class owns the fix is genuinely open: the writer breaks the caller precondition #13641 made a merge rule, while SortingCodecReader turns the null its delegate actually gives into an exception, unlike its own points path. Both fixes are validated. Verdict: a defect (the earlier verifiers and reviews rated the intended-behaviour argument weak; the cross-model fact check rated it moderate, mainly over which class should own the fix).

Suggested fix

#

Recommended A: skip a source whose FieldInfos lack the field, in both centroid loops

Skip a source segment whose FieldInfos have no vectors for the field, in both centroid loops of Lucene104ScalarQuantizedVectorsWriter, with the hasVectorValues check #13641 added elsewhere (+7/-2). All 15 repro tests and 257 tests of the 9 closest suites pass with assertions on and off; guarding only one loop is not enough.

A: skip a source whose FieldInfos lack the field, in both centroid loops (validated by the checks) (recommended)

#

In Lucene104ScalarQuantizedVectorsWriter.mergeAndRecalculateCentroids and calculateCentroid, skip a source when KnnVectorsWriter.MergedVectorValues.hasVectorValues(mergeState.fieldInfos[i], fieldInfo.name) is false, as #13641 did for the generic merge and the Lucene99 writers. One file, +7/-2.

import static org.apache.lucene.codecs.KnnVectorsWriter.MergedVectorValues.hasVectorValues;
...
// in mergeAndRecalculateCentroids and in calculateCentroid
KnnVectorsReader knnVectorsReader = mergeState.knnVectorsReaders[i];
if (knnVectorsReader == null
    || hasVectorValues(mergeState.fieldInfos[i], fieldInfo.name) == false) {
  continue;
}

Trade-offs

  • Matches #13641 and the sibling writers; up to two FieldInfos lookups per source and field per merge (one in each centroid loop).
  • It does not change what SortingCodecReader returns, so any other caller that asks it for an absent field would still fail (none known in Lucene).
  • The 10.2/10.3 line needs the same two lines in Lucene102BinaryQuantizedVectorsWriter (the release shadow runs show the guard fixes 10.2.0 and 10.3.2); on main the Lucene102 formats in backward-codecs are read-only, and their test-only writer copy has the same null-only checks. Open PR #16839 (ready for review since 2026-10-26) and draft PR #16819, which rewrite this code, would need it too.
  • Not done: the full core suite, check, a CHANGES entry.

FloatVectorValues values = delegate.getFloatVectorValues(field);

How it was found

#

A randomized differential test, not a formal method. It indexed the same documents three ways (index-time sort, re-sort through SortingCodecReader and addIndexes, pre-sorted insertion) with random vector formats and compared them; the re-sort path hit an AssertionError in SortingCodecReader. The stack trace led to the centroid code, then to a minimal JUnit.

The method in full133 words

Method: randomized differential testing (non-formal tier), in a hunt unit on index sorting.

  • The harness builds the same documents with IndexWriterConfig.setIndexSort, through SortingCodecReader.wrap plus addIndexes, and in pre-sorted order, with randomized vector formats, and compares the three per stored id.
  • Its assertions-on hunt hit an AssertionError at SortingCodecReader.java:318 via Lucene104ScalarQuantizedVectorsWriter.floatingPointVectorValues.
  • The finder read the failing frames, found the missing FieldInfos check, minimised it to a 3-test JUnit on the stock jar, ran it on main and released versions, and wrote a fix sketch.
  • Found 2026-10-25 on main ea57360912ed; then checked by an independent reproducer, a devil's-advocate verifier, reviews by a model from another family (OpenAI GPT-5.6) that ran their own tests, an adjudication, a follow-up (history, prior reports, security), the registration check and a re-run on main a9779ef3c193.

LFV-100, snapshot of 2026-10-29

Registry title
Quantized vector merge asks every source reader for a field's vectors without checking that reader's FieldInfos, so re-sorting with SortingCodecReader and addIndexes fails with NullPointerException (AssertionError with -ea) when one segment lacks one of several vector fields
Area
codecs / quantized vector formats merge (Lucene104 OSQ, Lucene102 BBQ) with index / SortingCodecReader
Priority
Medium, rank 317: Bottom of Medium: the documented SortingCodecReader plus addIndexes re-sort recipe fails with NPE on quantized vector formats when one segment lacks one of several vector fields, but it is loud, nothing is corrupted and per-leaf addIndexes avoids it.
Impact class
crash
Impact note
Hits only applications that re-sort an index with the documented SortingCodecReader recipe (IndexWriter.addIndexes with two or more SortingCodecReader-wrapped leaves) when a field that uses a non-default quantized vector format (Lucene104 scalar or HNSW-scalar OSQ on 10.4+ and main, Lucene102 BBQ on 10.2-10.3) is missing from a source segment that has some other vector field and the sort reorders that segment; addIndexes then throws and adds nothing (with -da the writer stays open, with -ea the AssertionError closes it as a tragic event), ordinary flushes and merges are unaffected, any scale, released since 10.2.0, and one addIndexes call per leaf avoids it.
Summary
You re-sort an index the way the SortingCodecReader javadoc describes: wrap every segment with SortingCodecReader.wrap(reader, sort) and pass them all to IndexWriter.addIndexes on a fresh index-sorted writer, with a codec that uses a quantized vector format (for example Lucene104HnswScalarQuantizedVectorsFormat), where one segment has vectors for field b but none for field a. You expect the re-sort to succeed, as it does with the default non-quantized HNSW format and as an ordinary merge of the same segments does. Instead the quantized writer's centroid code asks every source reader for field a without checking that reader's FieldInfos, SortingCodecReader wraps the missing (null) values, and addIndexes fails with a NullPointerException at SortingCodecReader.java:252 (an AssertionError at :318 with -ea), so nothing is added.
