CheckIndex and IndexUpgrader -dir-impl document a Path constructor but need (Path, LockFactory)

CheckIndex and IndexUpgrader -dir-impl (through CommandLineUtil.newFSDirectory) document that your directory class needs a Path constructor, but since 5.0 they require a public (Path, LockFactory) one and otherwise report "constructor with Path as parameter not found". The lookup is intended; only the text is stale.

The finding in 30 seconds

#

All four newFSDirectory overloads end in clazz.getConstructor(Path.class, LockFactory.class) (CommandLineUtil.java:141). A class with only a public Path constructor gets NoSuchMethodException, which the -dir-impl path turns into "constructor with Path as parameter not found" (:64). The @throws text (:113-114, :131-132) and the comment (:140) still describe a (Path) lookup.

Background in two steps

#
  1. CheckIndex and IndexUpgrader open the index with FSDirectory.open by default. The -dir-impl X option lets you pick an FSDirectory class instead, for example your own subclass; the tool creates it by reflection through CommandLineUtil.newFSDirectory.
  2. Since 5.0 every FSDirectory gets its LockFactory (the write lock) through its constructor. The built-ins, NIOFSDirectory and MMapDirectory, have both a (Path) and a (Path, LockFactory) constructor.

The finding, step by step

#
  1. You write demo.PathOnlyFSDirectory extends NIOFSDirectory with one public constructor, (Path path) { super(path); }. The javadoc throws NoSuchMethodException "If the Directory does not have a constructor that takes Path", a condition your class does not meet. Then you run CheckIndex <index> -dir-impl demo.PathOnlyFSDirectory.
  2. You expect CheckIndex to create your directory class and check the index.
  3. Instead it prints ERROR: could not open directory and IllegalArgumentException: demo.PathOnlyFSDirectory constructor with Path as parameter not found, exit 1, although the class has exactly that constructor. Only the Caused by: line names the one really needed: <init>(java.nio.file.Path,org.apache.lucene.store.LockFactory).
  4. Why: since 5.0 (LUCENE-5953) the lookup is getConstructor(Path.class, LockFactory.class) (CommandLineUtil.java:141), on purpose. The @throws text (:113-114, :131-132), the comment (:140) and the message (:64) still describe the old (Path) lookup.

Who is affected

#

Only someone who writes their own FSDirectory subclass with a public Path constructor but no (Path, LockFactory) one, and loads it through -dir-impl or CommandLineUtil. The default (no -dir-impl) and the built-in directories are not affected. The tool stops at once with a misleading message; nothing is opened or changed. Every release since 5.0.0.

Mechanism, terms and numbers381 words

CheckIndex and IndexUpgrader let you pick your own FSDirectory class with -dir-impl. The helper behind the option, CommandLineUtil.newFSDirectory, documents @throws NoSuchMethodException If the Directory does not have a constructor that takes Path, but since 5.0 (LUCENE-5953, #7015) it looks up a public (Path, LockFactory) constructor.

So a directory class whose only public constructor takes Path is rejected, although the documented condition is false for it, and through -dir-impl the top-level error reads <class> constructor with Path as parameter not found, for a class that has exactly that constructor; only the Caused by: line names the constructor that is really needed. The lookup is intended (the lock factory became a constructor argument in 5.0); the text was not updated with it. Nothing is opened or changed, and every built-in directory has both constructors. The fix is text only: both @throws, the comment and the message.

The mechanism

#
  1. CheckIndex.java:4721 and IndexUpgrader.java:124 pass the -dir-impl value to CommandLineUtil.newFSDirectory(String, Path), which adds FSLockFactory.getDefault() (CommandLineUtil.java:40-41) and, through newFSDirectory(String, Path, LockFactory) (:52-55), reaches newFSDirectory(Class, Path, LockFactory). The two-argument Class overload delegates the same way (:119-121), so all four newFSDirectory overloads end in one lookup (the public loadDirectoryClass and loadFSDirectoryClass, :78, :90, only load the class).
  2. The lookup: // Assuming every FSDirectory has a ctor(Path): (:140) above clazz.getConstructor(Path.class, LockFactory.class) (:141).
  3. The String overload turns the NoSuchMethodException into IllegalArgumentException(clazzName + " constructor with " + Path.class.getSimpleName() + " as parameter not found", e) (:62-65).
  4. Both Class overloads document @throws NoSuchMethodException If the Directory does not have a constructor that takes <code>Path</code>. (:113-114, :131-132).
  5. No user-facing text states the real rule. CheckIndex's usage says "-dir-impl X: use a specific FSDirectory implementation." (CheckIndex.java:4847-4852); IndexUpgrader's says "Specify a FSDirectory implementation through the -dir-impl option to force its use." (IndexUpgrader.java:72-76). Both add only the default package; neither names a constructor.
  6. Built-ins pass: FSDirectory's only constructor is protected FSDirectory(Path, LockFactory) (FSDirectory.java:118); NIOFSDirectory (:58, :69), MMapDirectory (:206, :217) and misc RAFDirectory (RAFDirectory.java:56, :68), the only FSDirectory subclasses in Lucene's main sources, have both forms.

Fix sites: CommandLineUtil.java:64, :113-114, :131-132, :140.

Exposure and likelihood117 words
  • Who: a user-written FSDirectory subclass with a public Path constructor but no public (Path, LockFactory) constructor (so the documented @throws condition is false for it), loaded through -dir-impl of CheckIndex or IndexUpgrader, or through CommandLineUtil.newFSDirectory directly.
  • Not hit: the default (no -dir-impl: FSDirectory.open), the built-in names (NIOFSDirectory, MMapDirectory), and any class that has the two-argument constructor.
  • Effect: the tool stops at once with a top-level message that contradicts the user's class; nothing is opened, written or changed. The Caused by: line names the real signature, so a careful reader can recover.
  • Scale: deterministic, first call, assertions on and off. Every release since 5.0.0 (2015); no public report found in those 11 years.

Why it looks unintended

#
  • The lookup is intended: 5.0 (LUCENE-5953) made the lock factory a constructor argument.
  • The text is stale: that commit changed getConstructor(Path.class) to (Path.class, LockFactory.class) under the unchanged ctor(Path) comment and copied the "takes Path" @throws onto the new overload.
  • No usage text, CHANGES or MIGRATE entry states the real rule.
The full argument181 words

The claim is only that the text is wrong; nobody proposes to change the lookup.

  • The lock factory became a constructor argument on purpose. The 5.0 MIGRATE.txt: "Locking is now under the responsibility of the Directory implementation. LockFactory is only used by subclasses of BaseDirectory to delegate locking to an impl class." A Path-only fallback in the three-argument overload would silently drop the caller's LockFactory.
  • The text was left unchanged when the lookup changed. c429f437f08 changed the lookup in the same hunk where // Assuming every FSDirectory has a ctor(Path): stays, copied the "takes Path" @throws onto the new overload and left the message. Every sign points to an oversight, though a diff cannot prove intent. The text comes from LUCENE-5945 (3eb66fb19ca, 2014-09-13), when the lookup really was (Path). In 4.x the lookup was (File) and the text said File: consistent, and a File-only subclass is accepted on 4.10.4.
  • Nothing else states the rule: the -dir-impl usage texts, CHANGES and MIGRATE do not mention it, and no upstream test names CommandLineUtil.
The devil's-advocate check169 words

The failure is loud and immediate, the Caused by: line names the exact signature, every built-in directory has both constructors, main's org.apache.lucene.util package-info calls the package "primarily internal" (#15719, not in 10.6.0), and no report of it in 11 years was found: a cosmetic nit.

Why it still counts, as a small cleanup: that defends the lookup, which nobody proposes to change. It does not defend a public, untagged method's @throws and the top-level message of a documented command-line option that state the wrong requirement and tell a user whose class has the Path constructor that it is missing. (A literal reader may say a (Path, LockFactory) constructor also "takes Path"; the point stands either way: for a class with a public Path constructor the documented condition is false, yet the exception is thrown.) What remains is impact, which is small: that is why this is Low. It is a stale-text defect, not a valid directory being rejected, and it does not call for a Path-only fallback.

How it was found

#

The method in full106 words
  • Obligation: each documented @throws condition holds exactly when the exception is thrown, and each error message describes the actual cause; here, NoSuchMethodException only for a class without a constructor that takes Path.
  • Finding: all four newFSDirectory overloads end in getConstructor(Path.class, LockFactory.class), so a class with a public Path constructor, for which the documented condition is false, still gets the exception, and the -dir-impl message names the wrong missing constructor.
  • Witness: a one-test JUnit on stock main, then an independent reproduction, an executed review by a model from another family (OpenAI GPT-5.6, under a refute and an intended lens), an intended-behaviour review and an adjudication.
