XYShape accepts a WITHIN query with a line geometry, which LatLonShape rejects, and silently returns only the points lying on the line

XYShape.newLineQuery(field, WITHIN, line) should throw, as LatLonShape does and as XYShape did up to 8.4.1, but since 8.5.0 it is accepted and silently returns only indexed points lying on the line. Of the line (0,0)-(10,0), a segment on it and the point (5,0), only the point matches.

The bug in 30 seconds

#

XYShape indexes a line as segments and a point as a point. A WITHIN query asks each indexed piece whether it lies within the query shape. For a query line Lucene can only answer that for points, so LatLonShape rejects WITHIN with a line, and XYShape did up to 8.4.1. Since 8.5.0 XYShape accepts it and answers partially.

  1. You index three cartesian shapes with XYShape: the line (0,0)-(10,0), the segment (2,0)-(4,0) that lies on it, and the point (5,0).
  2. You ask which shapes lie WITHIN that line: XYShape.newLineQuery("shape", QueryRelation.WITHIN, line (0,0)-(10,0)).
  3. You expect an IllegalArgumentException: LatLonShape rejects the same query ("does not support WITHIN queries with line geometries"), and XYShape itself did up to 8.4.1.
  4. You get no error and 1 hit of 3: the point (5,0). The identical line and the segment on it never match. A geometry array such as [polygon, line] is accepted too.
  5. Why: the XYShapeQuery constructor has no WITHIN + line check; the check was lost in 8.5.0 when the old XY line query was folded into it. Once accepted, a point is tested with a point-on-line test, a line segment with Line2D.containsLine, which always returns false.

Who is affected

#

Applications that index cartesian shapes with XYShape and build a WITHIN query with an XYLine, alone or in a geometry array, directly or through a query layer that passes any relation through. Default configuration, any index size, no error: on-line points come back, lines never. Query-time only; LatLonShape is not affected. Rare: no public report found since 2020.

Mechanism, terms and numbers709 words

LatLonShape.newLineQuery(field, QueryRelation.WITHIN, line) throws IllegalArgumentException ("LatLonShapeQuery does not support WITHIN queries with line geometries"), and so do LatLonPoint and LatLonDocValuesField; XYShape threw too, up to 8.4.1 ("XYShapeLineQuery does not support WITHIN queries"). Since 8.5.0, XYShape.newLineQuery(field, WITHIN, xyLine) and XYShape.newGeometryQuery(field, WITHIN, ...) with an XYLine anywhere in the array are accepted: LUCENE-9194 deleted XYShapeLineQuery and routed line queries to the generic XYShapeQuery, whose constructor adds no check of its own on the relation and the geometries. The accepted query then answers by shape type: an indexed point lying on the line matches (a point-on-line test), an indexed line segment never does, because Line2D.containsLine always returns false. For the line (0,0)-(10,0), the segment (2,0)-(4,0) on it and the point (5,0), the WITHIN query returns only the point. No error, any index size, the default configuration; 8.5.0 to 10.5.2 and main (six releases and main executed, the other 46 releases by a jar scan). The fix restores the rejection with the same validateGeometries check that LatLonShapeQuery has.

Terms

#
  • XYShape: Lucene's field for cartesian (unitless x, y) shapes. XYShape.createIndexableFields indexes a polygon as triangles, a line as one segment per pair of consecutive vertices, and a point as a point. Its twin LatLonShape does the same for latitude/longitude.
  • WITHIN: a document matches when every indexed piece of its shape lies within the query geometry. With a query line, only points and collinear segments can lie within it.
  • Line2D: the query-side component built for a query line, shared by both twins.

Step 1: the query is built without a check

#

XYShape.newLineQuery (XYShape.java:219-225 at a9779ef3c193) calls newGeometryQuery (:261-272), which returns new XYShapeQuery(field, queryRelation, xyGeometries) for every relation (only CONTAINS with several geometries is split first). The constructor (XYShapeQuery.java:41-44) is just super(field, queryRelation, geometries);; the superclass (SpatialQuery.java:74-85) and XYGeometry.create (XYGeometry.java:24-44) reject only a null field or relation and null or empty geometry arrays, nothing looks at the combination of relation and geometry type. Its twin LatLonShapeQuery wraps the geometries in validateGeometries (LatLonShapeQuery.java:43-61), which throws for WITHIN with any Line in the array (excerpt; the message spans :54-56 in the source):

if (geometries != null && queryRelation == QueryRelation.WITHIN) {
  for (LatLonGeometry geometry : geometries) {
    if (geometry instanceof Line) {
      // TODO: line queries do not support within relations
      throw new IllegalArgumentException(
          "LatLonShapeQuery does not support " + QueryRelation.WITHIN + " queries with line geometries");

LatLonPointQuery.java:52-63 and LatLonDocValuesQuery.java:63-73 have the same rule and TODO, and LatLonPoint.newGeometryQuery documents it: "Line geometries are not supported for WITHIN relationship" (LatLonPoint.java:314-316).

Step 2: what the accepted query computes

#

The WITHIN leaf test (XYShapeQuery.java:108-144) checks each indexed piece against Line2D:

point (5,0)contains(x, y) (:119) -> Line2D.java:84-90, point-on-line test (orient(...) == 0, no tolerance; EdgeTree.java:146-168)true: matches

triangle of a polygoncontainsTriangle (:137) -> Line2D.java:156-169: return false;false

For a query made only of lines, Line2D.relate (Line2D.java:92-104) never returns CELL_INSIDE_QUERY, so no index cell is accepted in bulk. The answer is essentially the point and multi-point documents whose points all lie on the query line (an indexed line whose vertices all coincide is decoded as a point and would match too): a subset of any reasonable WITHIN answer. In a mixed array such as [polygon, line] the polygon component answers as usual (ComponentTree.java), and only what lies on the line is under-matched.

The numbers

#

Line (0,0)-(10,0), segment (2,0)-(4,0) and point (5,0) indexed; XYShape.newLineQuery("shape", WITHIN, line (0,0)-(10,0)) matches 1 of 3: [point (5,0)]. XYShape.newGeometryQuery("shape", WITHIN, polygon, line) is accepted too; with a far-away polygon it returns only the point on the line. For an L-shaped query polyline (0,0)-(0,10)-(10,10), the independent reproducer's WITHIN query returns only the three indexed points on it and misses the identical polyline and the segments (0,2)-(0,8) and (3,10)-(7,10), while INTERSECTS on the same index returns exactly the 7 expected documents. LatLonShape, LatLonPoint and LatLonDocValuesField throw for the same input.

Exposure and likelihood226 words
  • Who. Applications that index cartesian shapes with XYShape (floor plans, CAD drawings, game maps, projected coordinates) and build a WITHIN query with an XYLine, alone or inside a geometry array such as [polygon, line], directly or through a downstream query layer. Two downstream engines' cartesian shape queries call XYShape.newGeometryQuery with the user's relation and geometry and no WITHIN + line check of their own (source reading, not executed); one of them rejects the same input on its geographic path with the comment "Line geometries and WITHIN relation is not supported by Lucene".
  • Default configuration. Public, non-experimental API, no special setting. The check is missing at query construction, so codec and index layout do not matter: the finder's test uses a plain new IndexWriterConfig(), this doc's repro Lucene's randomized test configuration.
  • Silent. No exception and no assertion, the same with assertions off, and the answer looks plausible because on-line points do come back.
  • Blast radius. Query-time only: that query's result. The index and other queries are unaffected. Any index size.
  • Not affected. LatLonShape, LatLonPoint and LatLonDocValuesField (they reject), and XYShape WITHIN queries whose geometries contain no XYLine (they never meet Line2D).
  • Rare in practice. "Which shapes lie within this line" is an unusual question; no public report was found since 8.5.0 (2020). The registry rates the likelihood "rare" and the priority low.

Why it is a bug, not intended

#
  • LatLonShape, LatLonPoint and LatLonDocValuesField reject WITHIN with a line ("TODO: line queries do not support within relations").
  • XYShape rejected it too up to 8.4.1; the 8.5.0 refactoring that dropped the check announced only an API simplification.
  • The accepted query contradicts itself: a point on the line is "within" it, the identical line is not.
The full argument228 words
  • The twin rejects it, with a TODO saying so. LatLonShapeQuery, LatLonPointQuery and LatLonDocValuesQuery all throw for WITHIN with a line, each with // TODO: line queries do not support within relations; LatLonPoint.newGeometryQuery documents "Line geometries are not supported for WITHIN relationship".
  • XY itself rejected it until 8.5.0. XYShapeLineQuery (LUCENE-8632, 2019) documented "QueryRelation.WITHIN queries are not yet supported" and threw "XYShapeLineQuery does not support WITHIN queries"; 8.2.0 and 8.4.1 throw when run.
  • The change that dropped it announced no behaviour change. LUCENE-9194's CHANGES entry: "Simplify XYShapeXQuery API by adding a new abstract class called XYGeometry. Queries are executed with input objects that extend such interface." Its PR has one approval and no word on WITHIN or lines. Eight days earlier LUCENE-9141, by the same author, folded the LatLon queries into LatLonShapeQuery and kept the check; LUCENE-9641 (2021, the same author) added the rejection to the new LatLonPointQuery and LatLonDocValuesQuery and rewrote XYShapeQuery in the same commit without adding it there. That the XY check was lost by accident is an inference from this record.
  • Inconsistent with itself. A point on the line counts as within it, the identical line does not.
  • Why tests never caught it. The shared random line-query test draws only from POINT_LINE_RELATIONS = {INTERSECTS, DISJOINT, CONTAINS}, so WITHIN with a line is never run; no upstream test asserts the LatLon rejection either.
The devil's-advocate check278 words

The strongest case for "works as designed": WITHIN with a query line is knowingly unsupported. Line2D.containsLine is a deliberate false ("can be improved?"), the random tests exclude WITHIN for line queries, the newLineQuery javadoc speaks of shapes that "intersect" a linestring, and XYShapeQuery is @lucene.internal. Line containment is conservative elsewhere too: CONTAINS with a line query never matches an indexed line on either twin, not even the identical one (executed: XY CONTAINS (0,0)-(10,0) returns only an enclosing square; LatLon CONTAINS on the identical indexed line counts 0, INTERSECTS 1).

Why it fails: all of that explains why the operation is unsupported, which argues for rejecting it, as LatLon does and XY did, not for accepting it silently. The "intersect" wording decides nothing: LatLonShape.newLineQuery has the same sentence and rejects WITHIN, and XYShape.newPolygonQuery has it and supports WITHIN; the XYShape class javadoc says newLineQuery matches shapes "that have some QueryRelation with a linestring". @lucene.internal covers the query class, not the public factories that build it. No record shows that accepting the query was deliberate, and no author has said either way: an accident is the likely reading of the history, not a proven one. Verdict: not intended, framed as the missing rejection; do not claim WITHIN must return the identical line. The executing checks (the independent reproducer, the devil's advocate, the adjudication) rated it real. The cross-model intended-lens reviewer rated the intended argument moderate and concluded that it "justifies rejection rather than the current accepted-but-incomplete behavior". The cross-model refute-lens reviewer recorded a formal "not real" with low confidence because it could not run any code (its notes call that procedural), and agrees on the root cause.

Suggested fix

#

Recommended Restore the rejection in XYShapeQuery, mirroring LatLonShapeQuery (one file)

Restore the rejection: give XYShapeQuery the same validateGeometries check as LatLonShapeQuery, throwing IllegalArgumentException for WITHIN with any XYLine. One file, +18/-1 lines; with it every geo and shape suite of lucene/core passes (587 tests including the repro, 0 failures). Queries accepted today, including [polygon, line] arrays, would start throwing, as on LatLon.

Restore the rejection in XYShapeQuery, mirroring LatLonShapeQuery (one file) (validated by the checks) (recommended)

#

In the XYShapeQuery constructor, pass the geometries through a validateGeometries method that throws IllegalArgumentException for WITHIN with any XYLine in the array, as LatLonShapeQuery does (+18/-1 lines including the XYLine import; the code below is the changed part of an unpublished file). Worth adding "Line geometries are not supported for WITHIN" to the XYShape.newLineQuery and newGeometryQuery javadoc, as LatLonPoint.newGeometryQuery has; that is not part of the validated diff.

  /** Creates a query that matches all indexed shapes to the provided polygons */
  XYShapeQuery(String field, QueryRelation queryRelation, XYGeometry... geometries) {
    super(field, queryRelation, validateGeometries(queryRelation, geometries));
  }

  private static XYGeometry[] validateGeometries(
      QueryRelation queryRelation, XYGeometry... geometries) {
    if (geometries != null && queryRelation == QueryRelation.WITHIN) {
      for (XYGeometry geometry : geometries) {
        if (geometry instanceof XYLine) {
          // line queries do not support within relations (same as LatLonShapeQuery)
          throw new IllegalArgumentException(
              "XYShapeQuery does not support "
                  + QueryRelation.WITHIN
                  + " queries with line geometries");
        }
      }
    }
    return geometries;
  }

Trade-offs

  • Behaviour change. Queries accepted today start throwing: XYShape.newLineQuery(f, WITHIN, ...) and newGeometryQuery(f, WITHIN, ...) with any XYLine in the array, including mixed arrays such as [polygon, line] whose polygon part answers correctly today. That is exactly LatLon's behaviour; it needs a CHANGES entry, and whether it also needs a MIGRATE note or goes to main only is the maintainers' call. Downstream engines that pass the relation through would get an IllegalArgumentException for cartesian WITHIN with a linestring, as for geo shapes.
  • Cost: one loop over the query geometries at construction; nothing at search time.
  • Scope: the check sits in XYShapeQuery only. XYShapeDocValuesQuery extends BaseShapeDocValuesQuery directly and would not get it, but no public API builds it with a line today: XYShape.newSlowDocValuesBoxQuery passes only an XYRectangle (XYShape.java:214-217) and ShapeDocValuesField.newGeometryQuery always throws (ShapeDocValuesField.java:89-95).

Implement line containment in Line2D (not run)

#

Make Line2D.containsLine return true when the indexed segment lies on the query polyline, so that XY WITHIN with a line becomes a supported query.

Trade-offs

Larger and riskier: a segment can span several collinear pieces of the query polyline or of a multi-line query; Line2D is shared with LatLon, whose quantized coordinates may no longer lie exactly on the original line, so LatLon would likely keep rejecting and the twins would diverge on purpose; CONTAINS semantics for lines (conservative today) would deserve the same look; and it needs new random-test coverage.

Document only (keeps today's behaviour)

#

State in the XYShape javadoc that WITHIN with lines is unsupported.

Trade-offs

Compatibility-preserving, and a valid choice if the maintainers prefer to declare the combination unsupported without a behaviour change. It keeps the silent partial answer for every caller who does not read the javadoc, though, and does not restore the 8.4.1 rejection or parity with LatLon.

Downstream note

#

Downstream engines whose cartesian shape queries pass the relation and geometry through to XYShape inherit the silent partial answer; with the fix they get an IllegalArgumentException instead, as for geo shapes.

How it was found

#

A static diff of Lucene's lat/lon and x/y sibling classes showed that LatLonShapeQuery validates its geometries and XYShapeQuery does not. The git history showed that the XY check existed until LUCENE-9194, and a public-API test confirmed that the query is accepted and answers partially.

The method in full159 words

Method: non-formal static comparison of sibling implementations, in a hunt unit on twin families (2026-10-26, main ea57360912ed).

  • A token-level diff of 96 sibling class pairs (Float/Double, Int/Long, vector Float/Byte, LatLon/XY and others), normalised per family, listed members present in only one twin. History

#

Introduced in 8.5.0 by LUCENE-9194 (73dbf6d0610, 2020-02-07), which deleted XYShapeLineQuery and its WITHIN check. Executed: 8.2.0 and 8.4.1 reject the query; 8.5.0, 8.11.4, 9.0.0, 9.12.3, 10.0.0, 10.5.2 and main accept it; the other releases by a jar scan. Unchanged on upstream main.

LFV-434, snapshot of 2026-10-28

Registry title
XYShape.newLineQuery / newGeometryQuery accept QueryRelation.WITHIN with an XYLine, which LatLonShape (and XYShape itself up to 8.4.1) rejects with IllegalArgumentException; the accepted query silently returns only indexed points lying on the line and never an indexed line, not even one identical to the query line (the check was lost in LUCENE-9194, 8.5.0)
Area
core / document: XYShape queries (XYShape.newLineQuery and newGeometryQuery, XYShapeQuery, Line2D)
Priority
Low, rank 349: XYShape accepts WITHIN with a line query and silently returns only on-line points, but asking which shapes lie WITHIN a line is unusual.
Impact class
wrong error
Impact note
Applications that build a cartesian shape query with XYShape.newLineQuery or newGeometryQuery, relation WITHIN and an XYLine (alone or inside a geometry array such as [polygon, line]), directly or through a downstream engine that passes the relation and geometry through, get no IllegalArgumentException, unlike LatLonShape and XYShape before 8.5.0, and instead a silently partial answer: indexed points and multi-points lying on the line match, indexed lines never do, not even the identical line; default IndexWriterConfig, codec and searcher, any index size; query-time only, so other queries and the index are unaffected; LatLonShape is not affected; released since 8.5.0.
Summary
You build XYShape.newLineQuery(field, QueryRelation.WITHIN, line) with a valid XYLine and expect the IllegalArgumentException that LatLonShape.newLineQuery throws for the same relation ('does not support WITHIN queries with line geometries'), and that XYShape itself threw up to 8.4.1 ('XYShapeLineQuery does not support WITHIN queries'). Instead the query is accepted, because the XYShapeQuery constructor has validated nothing since LUCENE-9194 (8.5.0) folded the old XY line query into it. The search then returns indexed points that lie on the line but no indexed line, not even one identical to the query line, because Line2D.containsLine and containsTriangle always return false.
Introduced
73dbf6d06108e9f18423521e339230bda37f8524 (master, now main), backported to branch_8x as 5c1f2ca22a756b16f0e35aa5dde221578fe1ce76; both 'LUCENE-9194: Simplify XYShapeXQuery API by adding a new abstract class called XYGeometry' (the commit subject reads 'UCENE-9194') by iverase, PR apache/lucene-solr#1224 (one approval by nknize, no line comments; issue now apache/lucene#10234) [read: git log, blame and git log -G in the full-history clone; the commit deletes XYShapeLineQuery, whose constructor threw 'XYShapeLineQuery does not support WITHIN queries', and routes XYShape.newLineQuery through newGeometryQuery to XYShapeQuery, whose constructor checks neither relation nor geometry; no later commit re-adds a check; the current constructor body dates from d7fd48c9502 (LUCENE-10654, 2022), a refactor that left XY unchanged].
