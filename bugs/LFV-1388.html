TeluguAnalyzer never strips the locative ending -లో (-lō): నగరంలో (nagaramlō, "in the city") is indexed as నగరంల (nagaramla), not నగరం (nagaram, "city")

TeluguAnalyzer shortens the vowel sign ో (ō) to ొ (o) before stemming, so its stemmer's locative rule -లో (-lō, "in") never fires. నగరంలో (nagaramlō, "in the city") is indexed as నగరంల (nagaramla), not నగరం (nagaram, "city"), and a search for the noun silently misses it.

The finding in 30 seconds

#

TeluguAnalyzer runs TeluguNormalizationFilter before TeluguStemFilter. The normalizer always turns ో (ō) into ొ (o), but the stemmer's locative rule is spelled with ో and has no ొ twin, so inside the analyzer that rule can never fire and only the final vowel sign is cut.

Background: Telugu vowel signs and case endings

#
  1. Telugu writes a vowel after a consonant as a vowel sign: ల (la) with the long-o sign ో is లో (lō); with the short-o sign ొ it is లొ (lo). They are two different characters, U+0C4B and U+0C4A.
  2. Nouns take case endings in the same word: నగరం (nagaram, "city") + -లో (-lō, "in") = నగరంలో (nagaramlō, "in the city").
  3. A stemmer cuts such endings so that both forms index as one term, here నగరం. TeluguStemmer does it with a fixed list of suffixes.

The finding, step by step

#
  1. You index Telugu text with the stock new TeluguAnalyzer(). A document says నగరంలో (nagaramlō, "in the city"); a user searches for నగరం (nagaram, "city").
  2. You expect both to become the term నగరం: the analyzer's last filter, TeluguStemFilter, has a rule that cuts the locative ending -లో (-lō, "in"), and that filter on its own turns నగరంలో into నగరం.
  3. But an earlier filter, TeluguNormalizationFilter, always rewrites the long vowel sign ో (ō) as the short ొ (o). The stemmer sees నగరంలొ (nagaramlo), its -లో rule cannot match, and a 1-letter rule drops only the vowel sign.
  4. The document is indexed as నగరంల (nagaramla), and the query నగరం finds 0 of 1 documents (a document that says నగరం: 1 of 1). గ్రామంలో (grāmamlō, "in the village") becomes గ్రామంల (grāmamla) the same way.
  5. No error, with assertions on or off, in every release since 8.10.0. TeluguStemFilter used on its own is not affected.

Who is affected

#

Anyone who indexes or searches Telugu text with the stock TeluguAnalyzer (any constructor), or a custom chain with teluguNormalization before teluguStem, since 8.10.0. A query for a bare noun misses documents that have only its -లో (-lō, "in") form. The exact form typed still matches; TeluguStemFilter alone is not affected.

Mechanism, terms and numbers606 words

TeluguAnalyzer runs IndicNormalizationFilter, TeluguNormalizationFilter, StopFilter and then TeluguStemFilter. TeluguStemmer's 2-letter rule group strips the locative ending "లో" (-lō, "in"), and TeluguStemFilter on its own turns నగరంలో (nagaramlō, "in the city") into నగరం (nagaram, "city"). But TeluguNormalizer always rewrites the long vowel sign ో (U+0C4B) as the short ొ (U+0C4A), and nothing writes ో again, so no token that reaches the stemmer inside the analyzer can end in "లో" (a token marked as a keyword by a stem-exclusion set skips both TeluguNormalizationFilter and the stemmer), and that rule is dead code. The token falls through to the 1-letter rule "ొ", which removes only the vowel sign: నగరంలో is indexed as నగరంల (nagaramla), while నగరం stays నగరం. A search for the bare noun misses a document that has only the locative form, with no error. It has been so since the analyzer was added (8.10.0) and is still so on main; a one-line fix adds the normalized twin "లొ" (lo) next to "లో".

TeluguStemmer cites no algorithm, so the intended behaviour comes from its own rule table and from the suffix list its first commit pointed to; both strip -లో. No native-speaker check was done, of the examples or of the fix.

The chain and the rule

#
  1. TeluguAnalyzer.createComponents (TeluguAnalyzer.java:114-125): StandardTokenizer -> DecimalDigitFilter -> (SetKeywordMarkerFilter if a stem exclusion set is given) -> IndicNormalizationFilter (:120) -> TeluguNormalizationFilter (:121) -> StopFilter (:122) -> TeluguStemFilter (:123). All three public constructors (:84-101) use this chain.
  2. TeluguNormalizer.normalize folds long vowel signs to short ones under the comment "long -> short vowels matras" (TeluguNormalizer.java:76-88). For ో the case is unconditional: case '\u0C4B': s[i] = '\u0C4A'; (:86-88). No case writes U+0C4B, so a token the stemmer works on never contains ో (a keyword-marked token skips both TeluguNormalizationFilter and the stemmer: TeluguNormalizationFilter.java:49, TeluguStemFilter.java:42).
  3. TeluguStemmer.stem tries a 4-letter group, then the 2-letter group (TeluguStemmer.java:32-48, len > 3, returns len - 2), then the 1-letter group (:50-60, len > 2, returns len - 1). The 2-letter group has endsWith(buffer, len, "లో") (:42) and no "లొ" twin: the fix site.
  4. In the analyzer, నగరంలో reaches the stemmer as నగరంలొ (nagaramlo, 6 chars). No 2-letter literal matches; the 1-letter literal "ొ" (:58) does, and only the vowel sign goes: నగరంల (nagaramla, 5 chars). The bare noun నగరం matches no rule and stays నగరం.
  5. Index and query use the same chain, so the exact form typed still matches itself; what is lost is the conflation of the locative form with the bare noun, which is what the rule is for.

Proof that the rule is dead

#

An inductive invariant over TeluguNormalizer.normalize shows that no token that TeluguStemFilter stems inside TeluguAnalyzer contains ో or ే (keyword-marked tokens are not stemmed). A bounded-exhaustive run on the real filters confirmed it for all 2,214,030 strings of length 1 to 3 over the Telugu block plus ZWNJ and ZWJ: 0 outputs contain either sign, while a control with only the Indic normalizer produces 50,571 outputs with ో and 50,830 with ే.

Exposure and likelihood148 words
  • Who: every application that indexes or searches Telugu text with TeluguAnalyzer (all three constructors share the chain), and any custom chain that puts teluguNormalization before teluguStem. TeluguStemFilter used alone, as in its factory's javadoc example (TeluguStemFilterFactory.java:26-32), is not affected.
  • What: missed matches only. A query for the bare noun does not find documents that contain only its locative form, and the reverse. -లో ("in") is the locative noun ending; its frequency in real text and the effect on a corpus were not measured.
  • Conditions: default classes, no setting, ordinary words, no scale; deterministic; assertions on and off.
  • Downstream reach: Elasticsearch and OpenSearch document no built-in Telugu analyzer; a Solr schema can still name the Telugu factories; IR toolkits use the stock TeluguAnalyzer for published Telugu BM25 baselines.
  • Cost of a fix: it changes indexed terms, so fields analyzed with TeluguAnalyzer need a reindex after it.

Why it looks unintended

#
  • The stemmer's own table strips -లో (-lō) (TeluguStemmer.java:42), and TeluguStemFilter, the analyzer's last filter, does so when used alone.
  • Its 1-letter rules list the long and the short form of each folded vowel sign; only this 2-letter rule lacks the short twin.
  • TeluguStemmer cites no algorithm: the intended behaviour comes from its own table. No native-speaker check was done.
The full argument482 words
  • The rule exists and the public filter applies it. TeluguStemFilter is "A TokenFilter that applies TeluguStemmer to stem Telugu words" (TeluguStemFilter.java:26), and the analyzer's javadoc says its stream is "filtered with ... TeluguStemFilter" (TeluguAnalyzer.java:103-112; it lists the filters in a different order from the code, and the code at :114-123 is what runs). Inside the analyzer, one of the table's own rules can never fire, for any input.
  • The 1-letter group already allows for the normalizer. It lists ి/ీ, ు/ూ, ె/ే and ొ/ో (TeluguStemmer.java:52-59), the short and long form of every sign the normalizer folds. This is consistent with a table meant to work after the normalizer; it does not prove it.
  • Another Lucene word list read after a normalizer carries the normalized forms. The Hindi stop list "also contains forms normalized by HindiNormalizer ... When adding additional entries to this list, please add the normalized form as well" (hi/stopwords.txt:4-7). A commutation sweep of the Bengali and Sorani stemmers found no suffix rule lost to their normalizers (0 of 312 and 0 of 69 root + suffix pairs differ; Telugu, as a control, 9 of 75), and reading the Persian and Arabic analyzers found none either. Of the analyzers checked, only Hindi (related row LFV-1387) and Telugu lose rules.
  • The suffix table the first commit pointed to strips -లో. The stemmer's first commit in PR #275 (c143ef618e, 2021-08-13) said "The algorithm is based on the report in: Natural Language Processing in an Indian Language (Telugu)-I: Verb Phrase Analysis P Sengupta and B B Chaudhuri" (the title is in <i> tags in the javadoc; the report itself was not read, so what it says about -లో is not known) and had a TODO linking an outside Python stemmer (nirupampratap/lda_te, tepy.py) whose 2-letter list also strips "లో". Both references were removed in 300d9937ea ("added few mote terms", 2021-08-31) before the merge; the rule stayed.
  • Nothing we found says otherwise. No javadoc, CHANGES or MIGRATE entry turns the rule off in the analyzer; upstream tests never pin a -లో result (TestTeluguStemmer tests the filter alone on plurals and verbs); PR #275 had one approval ("LGTM"), one general comment pointing to a Telugu test collection, and no discussion of the suffix rules.
  • The result is neither form: నగరంల (nagaramla) is neither the bare noun నగరం (nagaram) nor the written form నగరంలో (nagaramlō).

Scope. Only the -లో rule is claimed. The instrumental -చే (-cē, "by") rule (TeluguStemmer.java:40) is dead the same way, but a "చె" (ce) twin would over-stem the -ించే / -చ్చే (-incē / -ccē) verb forms the analyzer conflates today (ఉపయోగించే, upayōgincē, would become ఉపయొగిం, upayogim, while ఉపయోగించి, upayōginci, stays ఉపయొగించ, upayoginca), so that leg is a defensible trade-off. The వు (vu) difference comes from IndicNormalizer's వు -> మ (vu -> ma) mapping, upstream #14659 / PR #14699.

The devil's-advocate check216 words

The strongest case (from the cross-model refute review): TeluguStemmer is package-private since LUCENE-10561 (#883), so its table is no public promise; the analyzer javadoc lists the filters but promises no stem; the factory javadoc shows TeluguStemFilter used alone; the rule, the fold and the chain arrived together in one commit (544dbbea468) and no complaint was found since 2021; light stemmers are heuristics, and a fix changes indexed terms, so it wants native-speaker or corpus evidence.

Why it fails: the same table is the documented behaviour of the public TeluguStemFilter, which strips -లో; the dead rule is not a trade-off but code that no input can reach in the stock TeluguAnalyzer or in any chain that normalizes before stemming (TeluguStemFilter alone, as in its factory's example, does apply it); the 1-letter group already allows for the normalizer; "shipped together" shows no decision, since the PR had no review discussion of the rules. What remains is an impact argument (implied contract, recall only, a reindex), which is why the bug is Low. The same review reproduced the bug and agreed on the root cause and the fix, but on the contract question alone it still judged the report not a bug, with high confidence; the reviewer's other lens called the contract a judgement call.

Suggested fix

#

Recommended A. Add the normalized twin "లొ" (lo) to the 2-letter group

Add the normalized twin "లొ" (lo) next to "లో" (lō) in TeluguStemmer's 2-letter group: one line. The test passes, and the Telugu and Indic test classes pass with it (19 tests). Fields analyzed with TeluguAnalyzer need a reindex after the fix.

             || endsWith(buffer, len, "లో")
+            || endsWith(buffer, len, "లొ")
             || endsWith(buffer, len, "డు")

A. Add the normalized twin "లొ" (lo) to the 2-letter group (validated by the checks) (recommended)

#

One line in TeluguStemmer.java, after :42. Inside the analyzer, a token longer than three characters whose normalized form ends in లొ then loses that two-character ending: నగరంలో (nagaramlō) -> నగరం (nagaram), and దేశంలో (dēśamlō) -> దెశం (deśam), the normalized spelling of the stem TeluguStemFilter alone gives (దేశం, dēśam). The tested -ించే / -చ్చే verb examples do not change. Same idea as the Hindi stop list: list the normalized form too.

             || endsWith(buffer, len, "లో")
+            || endsWith(buffer, len, "లొ")
             || endsWith(buffer, len, "డు")

Trade-offs

A word written with a short -లొ (lo) in the source text is cut the same way, two letters instead of one: the string కాలొ (kālo) gives కాల (kāla) today and కా (kā) with the fix (executed on main). No native speaker checked which real words that affects. It changes indexed terms: the CHANGES entry should tell users of TeluguAnalyzer to reindex. An inline comment such as // "లో" after TeluguNormalizer is optional.

What the checks validated

Gradle, seed DEADBEEF: the test fails stock and passes with the fix, assertions on and off; with the fix, --tests 'org.apache.lucene.analysis.te.*' --tests 'org.apache.lucene.analysis.in.*' runs 6 classes, 19 tests, 0 failures; checkGoogleJavaFormat, ecjLint and forbiddenApis of lucene/analysis/common pass (executed in an independent run in a fresh scratch worktree). A separate re-run repeated the stock and fixed runs with the same results. The full module suite was not run.

B. Add both twins, "లొ" (lo) and "చె" (ce)

#

Also revives the instrumental -చే (-cē, "by") rule.

Trade-offs

Over-stems the -ించే / -చ్చే (-incē / -ccē) verb forms the analyzer conflates today: ఉపయోగించే (upayōgincē) -> ఉపయొగిం (upayogim) instead of ఉపయొగించ (upayoginca), వచ్చే (vaccē) -> వచ్ (vac) instead of వచ్చ (vacca). Not recommended without a native-speaker check.

C. Normalize the whole suffix table (or match both spellings)

#

Run every literal through the normalizer once, or compare against both forms.

Trade-offs

General, but it does more than the bug needs. Through the analyzer's normalizers three literals change to a spelling that is not already in the table: "చే", "లో" and "వు" (వు becomes మ, vu -> ma, through IndicNormalizer, the separate #14659 / PR #14699 question). So C also revives "చే", with B's verb side effect, and touches the "వు" rule. Replacing the literals, rather than adding the normalized ones, would also stop TeluguStemFilter used alone from matching the long-vowel spellings. Not recommended.

D. Stem before normalizing

#

Swap TeluguNormalizationFilter and TeluguStemFilter in createComponents.

Trade-offs

Changes the documented chain order and far more terms than the bug needs, since the stemmer would then see every spelling variant. Not run; not recommended.

E. Document that locatives keep the -ల (-la) ending

#

Javadoc only.

Trade-offs

Leaves a dead rule and a stem that is neither the noun nor the written form. Not recommended.

Downstream note

#

Solr schemas that chain the Telugu normalization and stem factories in this order, and IR toolkits that use the stock TeluguAnalyzer for Telugu baselines, inherit the missed matches; since a fix changes indexed terms, their Telugu fields need a reindex after it.

How it was found

#

A bounded check put root + suffix through TeluguAnalyzer and through TeluguStemFilter alone for each of the stemmer's 25 suffixes (75 pairs); only -వు (-vu), -చే (-cē) and -లో (-lō) differed. An inductive invariant then proved the normalizer never lets ో reach the stemmer, confirmed on all 2,214,030 strings of up to 3 characters.

The method in full156 words

Method: semi-formal. A bounded metamorphic check asked whether stemming commutes with the analyzer's normalizers: for every suffix literal parsed from TeluguStemmer.java and three roots, it compared the public TeluguAnalyzer with TeluguStemFilter alone. Of 25 literals, only "వు", "చే" and "లో" differ. A fixed-point check of each literal under the normalizers gives the same three.

An inductive invariant over TeluguNormalizer.normalize then proved that no token that TeluguStemFilter stems inside TeluguAnalyzer contains ో or ే (keyword-marked tokens are not stemmed), so "లో" and "చే" are the only 2-letter rules that can never fire. A bounded-exhaustive run on the real filters checked all 2,214,030 strings of length 1 to 3 over the Telugu block plus ZWNJ and ZWJ (0 outputs with either sign), with a control that does produce them. The finding was reduced to the one-test public-API JUnit above. "వు" is left to upstream #14659 / PR #14699, and "చే" is not claimed (a twin would over-stem verbs).

LFV-1388, snapshot of 2026-11-09

Registry title
TeluguAnalyzer folds the long vowel sign ో (ō) to ొ (o) before TeluguStemFilter runs, so TeluguStemmer's locative '-లో' (-lō) rule can never fire, and 'నగరంలో' (nagaramlō, 'in the city') is indexed as 'నగరంల' (nagaramla) instead of 'నగరం' (nagaram)
Area
analysis-common / Telugu analyzer (TeluguAnalyzer filter chain; TeluguStemmer suffix table versus TeluguNormalizer)
Priority
Low, rank 304: In every release since 8.10.0 the stock TeluguAnalyzer gives every noun in the everyday locative -లో (-lō) form a stem of its own, so a search for the bare noun silently misses those documents. It stays Low because the analyzer-level contract is implied rather than written, the exact form typed still matches, and the fix changes indexed terms and has had no native-speaker check.
Impact class
minor
Impact note
Missed matches only, with no error: every application that indexes or queries Telugu text through the stock TeluguAnalyzer (all three constructors share the chain), on every release from 8.10.0 through 10.6.0 and on main, gets a stem of their own for nouns in the locative case -లో (-lō, 'in'), which keeps the suffix consonant (నగరంలో nagaramlō -> నగరంల nagaramla, గ్రామంలో grāmamlō -> గ్రామంల grāmamla, దేశంలో dēśamlō -> దెశంల deśamla), while the bare noun gets the plain stem (నగరం nagaram, గ్రామం grāmam, దెశం deśam), so a search for the bare noun misses documents that hold only the locative form; TeluguStemFilter used on its own is not affected, no scale or setting is needed, -ea and -da behave the same, and because a fix changes indexed terms, affected fields need reindexing after it.
Summary
You index Telugu text with the stock TeluguAnalyzer; a document says 'నగరంలో' (nagaramlō, 'in the city') and a query says 'నగరం' (nagaram, 'city'). You expect both to get the term 'నగరం', because the analyzer's last filter, TeluguStemFilter, applies TeluguStemmer, whose rule table strips the locative suffix '-లో' (-lō), and the filter on its own does turn నగరంలో into నగరం. Instead TeluguNormalizationFilter, which runs earlier in the chain, always rewrites the long vowel sign ో (ō) to the short ొ (o), so the stemmer's 'లో' (lō) rule can never match: only the final vowel sign is removed, 'నగరంలో' is indexed as 'నగరంల' (nagaramla), and the query finds nothing, with no error.
