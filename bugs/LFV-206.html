WITHIN shape queries with a non-convex polygon match lines and polygons that leave it between boundary vertices

For a 4x4 square notched down to (2,1), a WITHIN query returns the road (0,4)-(4,4) across the notch and the notch triangle itself: 2 hits instead of 0. Lucene treats "every corner on or inside the polygon, no edge crossed" as contained, which holds only for convex polygons.

The finding in 30 seconds

#

For each indexed segment or triangle, WITHIN asks the polygon whether it contains it. Polygon2D says yes when every corner is inside or on the boundary and no polygon edge crosses the shape strictly. On a dented polygon, corners on the boundary plus edges that only touch are not enough: the shape can pass outside between the corners.

Background: how a WITHIN shape query decides

#
  1. XYShape and LatLonShape index every shape as triangles; a line becomes one degenerate triangle per segment.
  2. A WITHIN query matches a document only if every one of its triangles lies inside the query polygon.
  3. For a polygon query that per-triangle test is Polygon2D.containsLine (segments) or Polygon2D.containsTriangle.

The finding, step by step

#
  1. Take the query polygon (0,0) (4,0) (4,4) (2,1) (0,4): a 4x4 square with a V-shaped notch cut from its top edge down to (2,1). Index two XYShape documents: the segment (0,4)-(4,4), a road between the two top corners, and the triangle (0,4) (4,4) (2,1), the notch itself.
  2. Both touch the polygon, so INTERSECTS returns 2. You expect WITHIN to return 0: the segment's midpoint (2,4) and the triangle's centre (2,3) lie in the notch, outside the polygon.
  3. Instead WITHIN returns 2, with no error, with assertions on and off: on main and on the 9.1.0, 9.12.3 and 10.6.0 releases. Earlier runs found it in every release since 8.5.0.
  4. Why: for each indexed segment or triangle, Lucene answers "contained" when every corner is inside or on the boundary and no polygon edge crosses it strictly. Here every corner is a polygon corner and the polygon's edges only touch the shapes there or run along their sides, so both checks pass. That shortcut is exact only for convex polygons.
  5. XYShape hits it whenever data and query polygons share exact corners (parcels, districts and roads from one map); LatLonShape only when the shared coordinates lie on its encoding grid.

Who is affected

#

Applications running XYShape or LatLonShape WITHIN queries with non-convex polygons, whose indexed lines or polygons have every vertex exactly on the polygon's boundary: shared corners in planar data, or on-grid coordinates for lat/lon. No special codec or settings; no error, and the wrong region is a whole area, not a precision sliver. Rare. Priority Low.

Mechanism, terms and numbers575 words

XYShape and LatLonShape WITHIN queries test each indexed triangle with Polygon2D.containsLine (a segment) or Polygon2D.containsTriangle. Both return true when every vertex is contains()-ed, where a point on the polygon's boundary counts as inside, and no polygon edge crosses the shape strictly, where an edge that only ends on the shape or runs along it does not count. That implies containment only for convex polygons: on a non-convex polygon a segment or triangle can meet the boundary only at its own vertices and still pass outside between them. For the polygon (0,0) (4,0) (4,4) (2,1) (0,4), WITHIN returns the segment (0,4)-(4,4) and the triangle (0,4) (4,4) (2,1), although (2,4) and (2,3) are outside the polygon. No error is raised; the wrong region has positive area, so it is not a precision effect. XYShape hits it with exactly shared float coordinates, LatLonShape only with coordinates on its encoding grid. The current form dates from LUCENE-8736 (8.1.0, polygons) and LUCENE-9152 (8.5.0, lines), a narrower one from 7.7.0; it is on main and in 10.6.0 and is not fixed upstream.

The bug, on the repro

#
  1. XYShapeQuery.within() calls containsLine for a LINE triangle and containsTriangle for a TRIANGLE (XYShapeQuery.java:109, :127, :137; LatLonShapeQuery.java:127, :145, :155). A document matches only if every triangle passes (SpatialQuery.java:296-300, :354-356, :560-569).
  2. Segment (0,4)-(4,4). Both ends are polygon vertices, so contains returns true (on an edge). Each of the four polygon edges that reach the segment ends exactly on it: every orientation product is 0, so lineCrossesLine is false for all of them and crossesLine(..., false) is false. containsLine returns true; contains(2,4) is false.
  3. Triangle (0,4) (4,4) (2,1). All three vertices are polygon vertices; two of its edges lie on polygon edges (collinear, orientation 0) and the third is the segment above. crossesTriangle(..., false) is false, so containsTriangle returns true; its centroid (2,3) is outside.
  4. With includeBoundary == true both crossing tests would return true. That is why the shortcut was safe in 7.5.0-7.6.0, while a touch still counted as a crossing; LUCENE-8669 (7.7.0, 8.0.0) first made the test strict, and LUCENE-8736 (8.1.0, triangles) and LUCENE-9152 (8.5.0, segments) gave it today's strict form (history below).
  5. For a convex polygon the shortcut is exact: a segment or triangle whose vertices are in the closed polygon is inside it. The reflex vertex (2,1) is what lets the shape leave.

Executed on main 5adff78bb168 (diagram probe, assertions on and off identical): contains(2,4) false, contains(2,3) false, containsLine((0,4),(4,4)) true, containsTriangle((0,4),(2,1),(4,4)) true, the control containsTriangle((0,0),(4,0),(2,1)) true. Shape vertices on edge interiors trigger it too: containsLine((1,2.5),(3,2.5)) is true while contains(2,2.5) is false.

Exposure and likelihood287 words
  • Who is hit. XYShape/LatLonShape polygon queries with QueryRelation.WITHIN against a non-convex polygon, with indexed shapes whose vertices lie exactly on that polygon's boundary, at its vertices or on its edges.
  • Planar data. Likely when query polygons and indexed shapes come from one dataset and share corners. In an L-shaped zone (0,0) (10,0) (10,4) (4,4) (4,10) (0,10), the road (10,4)-(4,10) across the inner corner and a neighbouring parcel (10,4) (4,4) (4,10) that fills the corner (two of its edges lie on the zone's boundary, its interior is outside the zone) both match WITHIN; a road that stays inside is the control (main and 10.5.2, assertions on and off).
  • Lat/lon data. Only when the shared coordinates sit on the encoding grid, for example a query polygon built from decoded index data: placed 300 times at random positions and scales, the configuration reproduces 300 of 300 times on-grid and 0 of 300 times with arbitrary doubles, because quantization moves the indexed vertices off the query vertices.
  • No special settings. No codec or setting chosen by hand: the plain-program probe used the real default codec and IndexWriterConfig, the gradle runs the test framework's seed-chosen codec; assertions on and off. Multi-polygon queries delegate to each polygon (ComponentTree.java:198-277) and inherit it (read, not run). Box queries use the convex Rectangle2D and are not affected (read).
  • Silent, not a precision effect. No exception. The wrongly accepted region has positive area (the whole notch, 6 of the square's 16) and grows with the input; XY float coordinates are stored exactly.
  • How likely. Rare: a non-convex query polygon, every shape vertex exactly on its boundary and a path that leaves it are needed together; no user report was found since 2019.

Why it looks unintended

#
  • The javadoc promises to "return true if this component2D contains the provided line"; the polygon's own contains() says (2,4) and (2,3) are outside.
  • Boundary points count as inside on purpose (LUCENE-8736); here a whole region of each shape lies outside.
  • The hand-written shared-boundary tests use only convex polygons and expect "not contained" once a triangle leaves the polygon.
The full argument231 words
  • The contract. Component2D.java:73: "return true if this component2D contains the provided line"; :84: "... the provided triangle". No approximation is documented. The public QueryRelation.WITHIN says only "used for WITHIN Queries" (ShapeField.java:122), so what the user sees promised is the plain meaning of WITHIN, which these internal methods implement.
  • The tests. The hand-written shared-boundary tests use convex polygons: TestLatLonShape.testTriangleTouchingEdges (TestLatLonShape.java:560) checks shared points on the unit square and asserts containsTriangle == false for "1 shared point but out" (:602-614); testLUCENE8736 (:656) queries a 4x7 rectangle and testTriangleCrossingPolygonVertices (:701) a convex pentagon; TestPolygon2D.testIntersectsSameEdge (TestPolygon2D.java:333) asserts that a corner-to-corner diagonal of a convex square is contained (:339). No targeted test exercises containsLine/containsTriangle on a non-convex query polygon with every shape vertex on its boundary. Random tests do use non-convex polygons (GeoTestUtil.nextPolygon returns surpriseMePolygon() half the time, GeoTestUtil.java:453-479), but cannot see it: testIndexAndQuerySamePolygon (TestLatLonShape.java:769-812) queries a polygon WITHIN itself, which checks only the positive direction, and the random spatial tests' oracle calls the same containsLine/containsTriangle (BaseSpatialTestCase.java:769, :781).
  • The history. LUCENE-8736 (CHANGES.txt:6535-6538, "Point in Polygon now correctly includes boundary points") is about boundary points. LUCENE-9152 (#10192) states the line rule "If all points are inside the polygon, then do not consider the boundary". Neither discusses non-convex polygons.
The devil's-advocate check120 words

The strongest case for "intended": boundary inclusion is deliberate (LUCENE-8736), Component2D is @lucene.internal, XYShape warns that vertices are indexed "with some loss of precision" (XYShape.java:71), and #9782 is an open umbrella for wrong WITHIN results with shared boundaries, where boundary cases were treated as best effort.

Why it fails: inclusion covers boundary points, not shape interiors that lie outside the polygon; the failure goes through the public WITHIN query with valid simple polygons; the coordinates are exact and the wrong area is a whole region; and #9782 is open as a bug about the opposite direction (false negatives), with no statement accepting false positives. Every reviewer, including the one asked to argue for "intended", rated it real.

Suggested fix

#

Recommended A: refine the shortcut when the cheap checks pass (validated sketch)

After the existing checks pass, also check between the corners: split each segment and triangle edge at polygon vertices on it and require every piece's midpoint inside; reject a triangle with a polygon vertex strictly inside. Validated as a sketch: the repro passes with assertions on and off, and 390 geo and shape tests pass.

// containsLine: after the existing checks
    && tree.crossesLine(minX, maxX, minY, maxY, aX, aY, bX, bY, false) == false
    && segmentPiecesInside(aX, aY, bX, bY)
// containsTriangle: after the existing checks
    && segmentPiecesInside(aX, aY, bX, bY)
    && segmentPiecesInside(bX, bY, cX, cY)
    && segmentPiecesInside(cX, cY, aX, aY)
    && vertexStrictlyInside(aX, aY, bX, bY, cX, cY) == false
// segmentPiecesInside: split the segment at every polygon vertex on it
//   and require the midpoint of each piece to be contains()-ed.
// vertexStrictlyInside: true if a polygon vertex has the same nonzero
//   orientation against all three triangle edges.

A: refine the shortcut when the cheap checks pass (validated sketch) (recommended)

#

fix.diff, +60/-2 in Polygon2D.java only. Only when the existing checks already say "contained": containsLine splits the segment at every polygon vertex lying on it and requires the midpoint of each piece to be contains()-ed; containsTriangle does the same for its three edges and also requires that no polygon vertex lies strictly inside the triangle.

    && segmentPiecesInside(bX, bY, cX, cY)
    && segmentPiecesInside(cX, cY, aX, aY)
    && vertexStrictlyInside(aX, aY, bX, bY, cX, cY) == false
// segmentPiecesInside: split the segment at every polygon vertex on it
//   and require the midpoint of each piece to be contains()-ed.
// vertexStrictlyInside: true if a polygon vertex has the same nonzero

Trade-offs

Shows the root cause, but scans every polygon vertex on each call that passes the cheap checks (O(polygon vertices) per candidate triangle) and uses a boxed list: it may be too costly for WITHIN queries with large polygons (no benchmark was run). Holes keep their existing check.

B: the same refinement through the EdgeTree (not implemented)

#

Find "a polygon vertex on the segment" and "a polygon vertex strictly inside the triangle" with a bounding-box walk of the existing edge tree (every polygon vertex is an edge end point).

Trade-offs

The extra cost is bounded by the edges near the shape, not by the polygon size; more code than A. The shape an upstream patch should take.

C: keep the plain shortcut for convex polygons (complement to A or B, not implemented)

#

Compute once at construction whether the polygon is convex; for a convex polygon without holes the current shortcut is exact.

Trade-offs

Keeps today's cost for convex query polygons; adds a flag and a construction-time pass.

D: count touching as crossing again (rejected)

#

Call the crossing tests with includeBoundary == true in these two methods.

Trade-offs

Removes the false positives but, by reading, brings back the false negatives LUCENE-8736 and LUCENE-9152 fixed: shapes that share a boundary with a convex query would stop matching WITHIN (testTriangleTouchingEdges, testIntersectsSameEdge). Not run.

Downstream note

#

An application that uses a WITHIN polygon query as an allow filter (a geofence or a region scope) lets such shapes through; a deny rule built with MUST_NOT WITHIN hides them instead.

How it was found

#

A bounded-exhaustive consistency check compared Lucene's geometry predicates with an exact integer oracle over every small grid polygon, box and triangle. relate, contains and intersectsTriangle agreed everywhere; containsLine and containsTriangle said "contained" for shapes holding a point strictly outside the polygon. The cause was then read from Polygon2D.

The method in full139 words

Method: semi-formal (a bounded-exhaustive consistency check on the stock main jar).

  • The oracle: exact integer geometry with sample points on a 1/4 grid, over every simple polygon with 3-5 vertices on 3x3 and 4x4 grids (with triangular holes for 3-4 vertices), every half-grid box and every grid triangle, degenerate ones included.
  • relate() against contains(), and intersectsTriangle and contains() against the oracle: 0 violations.
  • containsTriangle/containsLine returned true while a point strictly outside the polygon lay in the shape in 104 cases (3x3 grid, 3-4 vertices and holes), 868 (3x3, 3-5 vertices and holes), 4,908 (4x4, 3-4 vertices and holes) and 58,792 (4x4, 5 vertices).
  • The root cause was then read from Polygon2D and EdgeTree, and a JUnit on the public XYShape/LatLonShape API reproduced it on main, 10.5.2 and 9.12.3 with assertions on and off.

History

#

Current form since LUCENE-8736 (55c241d87f42, 2019, first in 8.1.0) for polygons and LUCENE-9152 (c98229948a0b, 2020, 8.5.0) for lines; a narrower form since LUCENE-8669 (7.7.0). 7.5.0 and 7.6.0 are clean. Not fixed upstream.

Versions tested9 rows

How it evolved. The triangle shortcut ("all vertices contained and no crossing") exists since 7.5.0 and was safe while a touch counted as a crossing. edb05314b315 (LUCENE-8669, #9715, nknize, 2019-01-31; 7.7.0, 8.0.0) stopped counting touches, which made it unsafe in a narrow form; LUCENE-8712 undid that on main and branch_8x, first released in 8.1.0; 7.7.x and 8.0.0 kept it. 55c241d87f42 (LUCENE-8736, #9782, nknize, 2019-04-11; branch_8x b518bed8b3ba, 8.1.0) made Polygon2D.contains boundary-inclusive and lineCrossesLine strict: the wide form for triangles. c98229948a0b (LUCENE-9152, #10192, iverase, 2020-01-29; 29542c7f59ee, 8.5.0) moved lines with both endpoints contained to crossesLine(..., false). f914e08b3647 (LUCENE-9273; branch_8x a001f135f22, 8.6.0) split the code into today's methods without changing behaviour.

Every maintained line has the 8.1.0 form (LUCENE-8736); both dates are executed. Upstream main last changed Polygon2D.java and EdgeTree.java in de3b294be44c (2023-10-11, formatting); 10.6.0 has the same code as main.

LFV-206, snapshot of 2026-11-09

Registry title
Polygon2D.containsLine/containsTriangle accept a segment or triangle whose vertices lie on the boundary of a non-convex polygon even when it passes outside between them, so LatLonShape/XYShape WITHIN queries return false positives
Area
geo / shape queries (Polygon2D containsLine/containsTriangle, LatLonShape and XYShape WITHIN)
Priority
Low, rank 415: Polygon2D's convexity shortcut makes WITHIN queries with a non-convex polygon return shapes whose vertices lie on its boundary but which leave it, again exact shared coordinates (common for planar XYShape, on-grid only for LatLonShape); #9782 is related but about a different defect (false negatives on a convex query).
Impact class
silent wrong results
Impact note
Applications that run LatLonShape or XYShape polygon queries with QueryRelation.WITHIN (default codec, IndexWriterConfig and searcher, any index size) against a non-convex query polygon get, with no error, indexed lines and polygons whose vertices all lie exactly on that polygon's boundary (at its vertices or on its edges) but which leave it between those vertices, for example a road between two corners of a district that cuts across a dent, or a neighbouring parcel that fills a notch and whose interior lies outside (two of its edges are on the boundary); XYShape hits it with any exactly shared float coordinates, LatLonShape only when the shared coordinates are on the encoding grid (for example taken from decoded index data), and the wrong region has positive area that scales with the input, so it is not a precision effect.
Summary
You index a line or polygon whose corner points lie exactly on the boundary of a non-convex (dented) query polygon, for example a road between two corners of a district, and search for shapes WITHIN that polygon; you expect only shapes that lie inside it. Polygon2D.containsLine/containsTriangle accept a segment or triangle when every vertex is contained, with boundary points counting as inside, and no polygon edge crosses it strictly; that shortcut is only valid for convex polygons, so a segment that cuts across a dent between two boundary points, or a triangle that fills the dent and whose interior lies outside, is reported as contained. The WITHIN query returns those documents with no error (repro: for the polygon (0,0),(4,0),(4,4),(2,1),(0,4), WITHIN returns the indexed segment (0,4)-(4,4) and the indexed notch triangle (0,4),(4,4),(2,1) although (2,4) and (2,3) are outside the polygon).
