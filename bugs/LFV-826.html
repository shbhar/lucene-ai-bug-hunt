The bug in 30 seconds

#

Under a phrase, Lucene splits an or into one phrase per alternative, so that a longer alternative is not lost. The split does not reach an or that sits inside a wrapper which is itself one alternative of another or.

  1. Index one document, x b c d (positions 0 to 3), with default settings. Take W = maxwidth(5, or(phrase(b, c), b)): an or with a two-word alternative b c and a one-word alternative b inside it.
  2. Search phrase(x, W, d): 1 hit. Lucene rewrites an or under a phrase into one phrase per alternative, so x [b c] d is found.
  3. Now search phrase(x, or(W, y), d), where the word y is in no document. You expect the same 1 hit, since y adds nothing. You get 0 hits, with assertions on or off, and no error.
  4. Why: the rewrite asks the outer or for its alternatives only one level deep, gets [W, y], and never splits the or inside W. That inner or keeps only minimal intervals: it drops b c [1,2] for the b [1,1] inside it, so the phrase looks for x b d.
  5. Analyzed text can supply the wrapped or: with the query-time synonym york => "new york", phrase(in, or(A, boston)) misses in new york city, where A is analyzedText("york city") (ordered, no gap limit) and phrase(in, A) finds it.

Who is affected

#

Anyone whose interval query puts an or with alternatives of different lengths inside maxwidth, fixField, extend, ordered or unordered and uses that as one alternative of another or under phrase, maxgaps or containedBy: Java factories, analyzedText with multi-word synonyms, or fn: query strings. Default settings, any index size, 8.1.0 to 10.5.2 (every minor line run) and main. Rare, but silent.

Mechanism, terms and numbers733 words

Intervals.or promises to rewrite itself under a gap-sensitive parent (phrase, maxgaps, the big side of containedBy and containing) into one parent per alternative, because a disjunction drops any of its intervals that contains another one and a longer alternative would otherwise vanish (LUCENE-8477, 8.1.0). The rewrite asks an or for its alternatives only one level deep (Disjunctions.splitDisjunctions), so an or that sits inside maxwidth, fixField, extend, ordered or unordered, where that wrapper is itself one alternative of another or, is never split. With W = maxwidth(5, or("b c", b)), phrase(x, W, d) finds x b c d but phrase(x, or(W, y), d), with y in no document, finds nothing; the same holds for fixField, extend, ordered(or(a, "b a"), c), under maxgaps(0, ordered(...)), containedBy and containing, for the query string fn:phrase(x fn:or(fn:maxwidth(5 fn:or("b c" b)) y) d), and for analyzed text with a multi-word synonym. A plain nested or(or(...), y) is flattened and works. It reproduces on 8.1.0, 8.1.1 and the latest patch of every minor line through 10.5.2, and it is not fixed upstream. Expanding nested alternatives recursively in splitDisjunctions, with a guard against sources that list themselves, fixes every shape run and passes the queries, queryparser and highlighter test suites.

Terms

#
  • Minimal intervals: an interval query returns position ranges per document. A disjunction returns only the intervals of its alternatives that contain no other of its intervals. In x b c d, or("b c", b) returns b [1,1] and drops b c [1,2], which contains it.
  • The rewrite (LUCENE-8477, 8.1.0): a gap-sensitive parent (phrase, maxgaps, the big side of containedBy and containing) splits an or among its arguments into one parent per alternative. phrase(x, or("b c", b), d) becomes or(phrase(x, "b c", d), phrase(x, b, d)) and finds x b c d. The class javadoc promises this; or(false, ...) is the documented, lossy opt-out.
  • Wrappers: maxwidth, fixField, extend, ordered and unordered do not split at construction. They hand their alternatives up when a parent asks (pullUpDisjunctions()).

The bug

#
  1. phrase(...) asks Disjunctions.splitDisjunctions for the alternatives of each argument (BlockIntervalsSource.java:34, Disjunctions.java:39).
  2. splitDisjunctions takes source.pullUpDisjunctions() once (Disjunctions.java:82). For or(W, y) that is [W, y] (DisjunctionIntervalsSource.java:146-152); W's own alternatives are never asked for, although MaxWidth.pullUpDisjunctions() would split them (FilteredIntervalsSource.java:72-74; likewise ExtendedIntervalsSource.java:134-143, FixedFieldIntervalsSource.java:59-68, OrderedIntervalsSource.java:78-80).
  3. Two paths. (a) W has minExtent 1 (its alternative b), so it is grouped with y into one or (Disjunctions.java:83-92), against the comment's assumption that "all combinatorial sources have a minExtent > 1" (:78). (b) An alternative with minExtent 2, such as ordered(or(a, "b a"), c), gets its own branch but is still not split.
  4. The query is built as BLOCK(x,or(MAXWIDTH/5(or(BLOCK(b,c),b)),y),d). At search time the inner or yields only b [1,1], the phrase needs d to start at position 2, but d is at 3, so it returns nothing.
  5. A plain nested or(or("b c", b), y) works: DisjunctionIntervalsSource.simplify flattens a direct or child (DisjunctionIntervalsSource.java:58-68). Any non-or wrapper in between stops it, and so does an inner or(false, ...), which lists only itself, as the documented opt-out intends.

Why it is a bug, not intended

#
  • Intervals.or "Automatically rewrites if wrapped by an interval source that is sensitive to internal gaps"; or(false, ...) is documented to "miss valid hits".
  • Upstream testNestedMaxWidth asserts the rewrite through maxwidth; its query plus one never-matching alternative loses the hit.
  • or(W, y) has the same intervals as W when y occurs nowhere, so adding y must not remove a hit.
The full argument232 words
  • Contract. The Intervals class javadoc (Intervals.java:47-54): gap-sensitive sources "will rewrite their sub-sources so that disjunctions of different lengths are pulled up to the top of the interval tree", with or(boolean, ...) for those who "care more about speed than about accuracy". Intervals.or (:121): "Automatically rewrites if wrapped by an interval source that is sensitive to internal gaps". or(false, ...) (:130-131): "can miss valid hits due to minimization". CHANGES 8.1.0, LUCENE-8477: "Interval disjunctions could miss valid hits if some of the clauses of the disjunction are minimized away. We now rewrite intervals ...".
  • Tests. TestDisjunctionRewrites#testNestedMaxWidth (:138-154) and #testNestedFixField (:156-166) assert the rewrite through maxwidth and fixField; no upstream test puts such a wrapper inside another or. The repro's testNestedMaxWidthInsideOr is testNestedMaxWidth's query plus one outer alternative, and it loses its hit.
  • Consistency. The nested query with the default rewrite behaves like the documented-lossy or(false, W, y): both 0 hits, while phrase(x, W, d) finds 1.
  • Maintainers. On LUCENE-8477 (#9523), romseygeek gave the reason to rewrite inside the library: "disjunctions can end up being wrapped multiple times". On LUCENE-9204 (#10244): "Intervals automatically rewrite disjunctions (and have done since LUCENE-8477) so that queries behave as your or I would expect them to" (romseygeek) and "it's the key for correctness ... If it's not correct, it's a bug, not a feature" (jimczi).
The devil's-advocate check184 words

The strongest case for "intended": the comment above splitDisjunctions (Disjunctions.java:75-78) describes a one-level split; before the LUCENE-8477 PR jimczi suggested documenting "other pathological cases due to minimum interval semantics" instead of rewriting; with minimal-interval semantics W alone only ever yields one-position intervals; the Expert hook pullUpDisjunctions() promises nothing about depth (IntervalsSource.java:66-71); and the package is marked experimental.

Why it fails: the comment states an assumption ("all combinatorial sources have a minExtent > 1") that these wrappers break, and path (b), with minExtent 2, fails without any grouping, so it does not describe a deliberate limit. The project chose to rewrite by default and to document or(false, ...) as the lossy option; nothing documents a depth limit, users rely on the Intervals javadoc rather than the Expert hook, and the built-in wrappers already answer correctly when asked (whether to recurse into custom hooks is a maintainer decision). Minimization is exactly what the rewrite exists to work around, and the direct form is rewritten for that reason. "Experimental" is an API-stability label, not permission for wrong results. Verdict: not intended, a defect.

Suggested fix

#

Recommended Expand nested alternatives recursively in splitDisjunctions, with a guard

In Disjunctions.splitDisjunctions, expand an alternative that has disjunctions of its own, recursively, and skip a source that lists itself (one private method in Disjunctions.java). The repro and the queries, queryparser and highlighter suites pass. Without the guard, the candidate fix of the sibling bug LFV-809 makes the recursion overflow the stack.

Expand nested alternatives recursively in splitDisjunctions, with a guard (validated by the checks) (recommended)

#

an unpublished file (+29/-1 in Disjunctions.java, one private method). Before the existing minExtent grouping, an alternative whose own pullUpDisjunctions() returns more than one source is replaced by those sources, recursively. A source already being expanded (one that lists itself or an ancestor among its disjuncts) is kept whole. The nested form then builds the direct form's branches, with y added to the one-position branch. Sources that return one disjunct (terms, phrases, or(false, ...), atLeast) are untouched, so the opt-out stays lossy.

List<IntervalsSource> disjuncts = new ArrayList<>();
expandDisjunctions(source, source.pullUpDisjunctions(), new HashSet<>(), disjuncts);
for (IntervalsSource disj : disjuncts) { ... }   // the existing minExtent grouping

private static void expandDisjunctions(IntervalsSource source,
    Collection<IntervalsSource> disjuncts, Set<IntervalsSource> expanding,
    List<IntervalsSource> out) {
  expanding.add(source);
  for (IntervalsSource disj : disjuncts) {
    Collection<IntervalsSource> inner =
        expanding.contains(disj) ? Collections.emptyList() : disj.pullUpDisjunctions();
    if (inner.size() > 1) {
      expandDisjunctions(disj, inner, expanding, out);
    } else {
      out.add(disj);
    }
  }
  expanding.remove(source);
}

Trade-offs

  • Why the guard. pullUpDisjunctions() is a public Expert hook. LFV-809's candidate fix returns this plus the alternative sequences for a whole unordered(X, X). With that fix and the unguarded option B, phrase(z, unordered(X, X)) throws StackOverflowError; with option A it finds its hit, and LFV-809's own tests pass with both (so they would not catch it). The guard compares with equals; a custom source that invents new unequal sources forever would still recurse. The hook's javadoc says nothing about depth, so recursing into custom implementations at all is a question for maintainers.
  • Cost. More branches only for the affected nested shapes. Where the split runs in the list overload of Disjunctions.pullUp (phrase, overlapping, ordered/unordered when asked), the clause guard (Disjunctions.java:43-45) checks the product and nested alternatives now count toward it, so a query near the limit can now throw "Too many disjunctions to expand". The single-source overload (:66-73: maxwidth, the big side of containedBy/containing, notContainedBy/notContaining) has no clause guard, today or with the fix (read, not run). No benchmark was run.

Flatten wrapped alternatives when the or is built (not tested)

#

DisjunctionIntervalsSource.simplify (:58-68) could replace any sub-source whose pullUpDisjunctions() has more than one entry, as it already does for nested ors.

Trade-offs

Changes every rewriting or tree, also outside gap-sensitive parents (toString, equals, cache keys, matches and highlighting), needs the same guard, and reverses the wrappers' "do not pull up at construction time" design.

Workaround until a fix ships

#

Distribute by hand so that each wrapper sits directly under the gap-sensitive parent: or(phrase(x, W, d), phrase(x, y, d)) instead of phrase(x, or(W, y), d); or use a plain nested or without the wrapper where the wrapper is not needed.

Trade-offs

The application must know which alternatives contain an or; analyzed text hides it.

How it was found

#

An automated check of Lucene's query code against algebraic laws that need no reference implementation (for example, each interval comes back from exactly one of a relation and its negation; or is commutative), over 30,000 random query pairs on 363 short documents. One mismatch class that no known bug explained was reduced by hand to this case.

The method in full161 words

Method: reference-free translation validation of the real jar against algebraic laws (the hunt's "semi-formal" tier).

  • A hunt unit on interval relations wrote a harness (ComplementLawsTV) that runs real interval sources on an index of 363 short documents and checks laws that need no reference semantics: each minimal interval of X is returned by exactly one of a relation and its negation, containedBy is a subset of overlapping, and or is commutative and idempotent. Every known interval fix was shadowed in, so that known bugs would not show up.
  • A run of 30,000 random depth-3 pairs (24,510 checked) left one class it could not attribute (within0:neither:OTHER, 142 rows). The finder reduced it by hand to containedBy over or(fixField(g, or(BLOCK(a, a), z)), a), generalised it with a probe to phrase, maxwidth and extend, and wrote a one-document public-API JUnit on the stock jar.
  • Independent AI tools then reproduced, reviewed and judged it (see the checks).

Bug record

LFV-826, snapshot of 2026-10-28

Registry title
The intervals disjunction rewrite looks only one level into an or(), so an or() inside a maxwidth, fixField or extend wrapper (or inside an ordered()) that is itself one alternative of another or() is never split, and phrase, maxgaps or containedBy miss hits: phrase(x, or(maxwidth(5, or("b c", b)), y), d) misses 'x b c d', which phrase(x, maxwidth(5, or("b c", b)), d) matches
Area
queries / intervals (gap-sensitive disjunction rewrite of LUCENE-8477: Disjunctions.splitDisjunctions and Disjunctions.pullUp vs an alternative of an or() that has disjunctions of its own: maxwidth, extend, fixField, ordered)
Priority
Medium, rank 232: Since 8.1.0 the query silently misses hits on ordinary text, but only for an unusual doubly nested or() shape inside maxwidth, fixField, extend or ordered under phrase, maxgaps or containedBy, so it joins the rare-shape interval missed-match rows after LFV-805 and above the partly known LFV-810.
Impact class
silent wrong results
Impact note
Anyone whose interval query puts an or() with alternatives of different lengths inside maxwidth, fixField or extend (or inside an ordered()) and uses that as one alternative of another or() under a gap-sensitive parent (phrase, maxgaps, or containedBy over it as the reference), through the Java Intervals factories or StandardQueryParser fn: strings, with default writer, codec, analyzer and searcher settings, at any index size, with -ea and -da, in every release from 8.1.0 to 10.5.2 and on main and branch_10_6, silently misses documents that the same query without the outer or() matches; a plain nested or(or(...), y) and the directly wrapped form are not affected, and nothing is written to the index.
Summary
You build phrase(x, or(W, y), d) with W = maxwidth(5, or(phrase(b, c), b)) and expect the hit on 'x b c d' that phrase(x, W, d) finds, because Intervals.or 'Automatically rewrites if wrapped by an interval source that is sensitive to internal gaps' and adding an alternative y that occurs in no document cannot remove a match. Instead the rewrite (Disjunctions.splitDisjunctions) asks the outer or() for its alternatives only one level deep, so W reaches the phrase whole (here grouped with y into one minimizing or(), because W's shortest match is one position), the inner or() drops the interval 'b c' in favour of the 'b' it contains, and the query returns no hits. The same happens with fixField(g, or(...)) or extend(or(...), 0, 0) in place of maxwidth, with containedBy or maxgaps as the parent, and with an ordered() alternative whose own or() has alternatives of different lengths.
Introduced
f1782d0dd1195c823c79aab87529ebd7e8217b95 (master, released from 9.0.0) and its branch_8x backport 2571bf355f82e193d50ec2509f83ba698b262562 (the first released form, in 8.1.0), both 2019-03-27: 'LUCENE-8477: Automatically rewrite disjunctions when internal gaps matter' (apache/lucene-solr#620 by romseygeek; the JIRA issue is now apache/lucene#9523). It added the gap-sensitive rewrite with the one-level Disjunctions.splitDisjunctions, its minExtent-1 grouping and the wrapper pull-ups [read: git blame on main; every line of splitDisjunctions and the 'return subSources' line of DisjunctionIntervalsSource.pullUpDisjunctions come from f1782d0dd11, later touches are formatting or refactoring only] [exec: the intervals package at the backport's parent b08566cacc7, shadowed on the 8.1.0 jars, has no rewrite at all (direct and nested forms both miss); the package at 2571bf355f8 shows the bug signature 4 of 4]. An incomplete fix, not a regression: before it no form was rewritten (2019-03-27 (f1782d0dd11 and the branch_8x backport 2571bf355f8))
