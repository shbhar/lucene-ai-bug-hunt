A deletes/updates packet whose RAM estimate is exactly 2^31 bytes leaves IndexWriter reporting pending changes for the rest of its life

If one frozen deletes/updates packet has a RAM estimate of exactly 2^31 bytes, IndexWriter's pending-bytes total ends at -2^32 instead of 0: after commit(), hasUncommittedChanges() and hasDeletions() stay true and NRT readers are never current until the writer closes. Byte-exact, contrived trigger; only redundant work.

The finding in 30 seconds

#

IndexWriter keeps a running byte total of the deletes/updates packets not yet applied, and "not 0" means "changes pending". Each packet stores its size as an int, added on push and subtracted on finish by negating the int. For a size of exactly 2^31 that negation changes nothing, so the total is left at -2^32 instead of 0.

Buffered deletes and updates in one minute

#
  1. deleteDocuments(term) and updateNumericDocValue(term, field, value) are buffered in RAM. When they are applied (at flush or commit, or when the buffer is full), the buffer is frozen into a packet that carries a RAM estimate.
  2. Each writer has one BufferedUpdatesStream. It adds a packet's estimate to a total when the packet is pushed and subtracts it when the packet is finished. A total that is not 0 means "something is pending".
  3. hasUncommittedChanges(), hasDeletions() and isCurrent() on an NRT reader all ask the stream that question.

The finding, step by step

#
  1. Disable RAM-based flushing, commit one document, then send 20 numeric doc-values updates: one by its key, 19 keyed by a term whose field name is 56,511,839 chars (about 57 MB of heap). Lucene charges that name again for each update, so the packet's estimate is exactly 2,147,483,648 bytes (2^31).
  2. The packet stores its estimate as an int, so 2^31 becomes -2,147,483,648. Pushing the packet adds that to the writer's pending-bytes total, a long: -2^31.
  3. Finishing the packet should subtract it again, but the code negates the int, and -Integer.MIN_VALUE is Integer.MIN_VALUE. The total becomes -4,294,967,296, not 0, and nothing resets it.
  4. After commit() you expect hasUncommittedChanges() to be false, and it is when the field name is one char longer (estimate 2^31 + 38). Instead it is true, hasDeletions() is true, and an NRT reader says isCurrent() false while openIfChanged returns null, for the writer's life.
  5. Nothing else is wrong: hits, counts, files and commits are right. Each refresh or commit check just does redundant work, and a new writer starts clean.

Who is affected

#

Only a writer that freezes one packet whose estimate is exactly 2^31 bytes (mod 2^32). On 10.6.0 and earlier that needs a RAM buffer of 2 GB or more, or RAM-based flushing off; on main, one operation of about 103 MB crossing the 1945 MB limit. It lasts until the writer closes but costs only redundant work.

Mechanism, terms and numbers667 words

IndexWriter keeps a running byte total of the frozen deletes/doc-values-updates packets that are not yet applied (BufferedUpdatesStream.bytesUsed, an AtomicLong) and treats "total != 0" as "changes pending". Each packet stores its estimate as an int: FrozenBufferedUpdates computes a long and casts it with (int). The total adds the packet's int on push and adds -packet.bytesUsed on finish, a negation in int arithmetic. For every value but one the two cancel, even when the cast made the value negative. For Integer.MIN_VALUE, which is what an estimate of exactly 2^31 (mod 2^32) becomes, the negation is a no-op: the total goes 0, -2^31, -2^32: a residual that no later push/finish pair removes and nothing resets while the writer is open. From then on, whenever no packet is pending, the total reads -2^32, so hasUncommittedChanges() and hasDeletions() return true even right after commit(), and every NRT reader reports isCurrent() == false while openIfChanged returns null. No hit, count, file or commit is wrong (the total is read only by those answers and one InfoStream message); the cost is redundant refresh, flush and commit work, and a new writer starts clean. The code dates from LUCENE-2897 (2011); it reproduces on every release tested from 4.6.0 through 10.6.0 except 7.6.0 (7.0.0-7.6.0 lack the cheap trigger).

Step by step in the repro

#
  1. The first update, keyed by primary_key, sets the buffer's first field. FieldUpdatesBuffer.java:147-148 charges sizeOfString(field) for every later update whose field is a different one ("that's an easy win of not accounting if there is an outlier"), so each of the 19 updates keyed by the 56,511,839-char field adds about 108 MB of estimate (2 bytes per char) while the field name exists once in memory.
  2. On main the 19th update crosses the 1945 MB delete-buffer limit (DocumentsWriterFlushControl.java:45-49, #16867) and the buffer is applied as one packet. Its estimate is exactly 2,147,483,648; the cast stores -2,147,483,648 (InfoStream: "compressed 2147483632 to -2147483648 bytes").
  3. Push: the total becomes -2,147,483,648. Finish: -packet.bytesUsed is computed as an int, and -Integer.MIN_VALUE == Integer.MIN_VALUE, so the total becomes -4,294,967,296.
  4. commit() applies and commits everything, but any() is still true. hasUncommittedChanges() returns true (the test's assertion), and stays true.

Only one value drifts

#

For any other estimate x, (long) (int) x + (long) (-(int) x) is 0, even when (int) x is negative. The same 20 updates with a field one char longer give an estimate of 2^31 + 38, narrowed to -2,147,483,610: push and finish cancel and the writer is clean after commit. Only Integer.MIN_VALUE is its own negation.

What it does and does not touch

#
  • Wrong, for the writer's life: isCurrent() is false on every NRT reader, and openIfChanged goes through the writer's full-flush path and returns null; hasUncommittedChanges() and hasDeletions() are true. With assertions on, the next packet push fails checkDeleteStats (BufferedUpdatesStream.java:296-303): bytesUsed2=0 vs -4294967296.
  • Not affected: hits, counts, files and commits. Outside any() the total is read only by BufferedUpdatesStream.ramBytesUsed(), which IndexWriter prints in one InfoStream message (IndexWriter.java:4446); flush control and IndexWriter.ramBytesUsed() do not read it. A commit with no real changes writes no new commit point (IndexWriter.java:5933-5935). Real later changes still become visible after reopen (numDocs=2 in a probe). A new writer starts at 0.
Exposure and likelihood257 words
  • What it takes. One frozen packet whose estimate is exactly 2^31 (mod 2^32) to the byte; every other size cancels out.
    • 10.6.0 and earlier: a RAM buffer of 2 GB or more, or RAM-based flushing disabled, with that much buffered deletes or updates. The default 16 MB buffer applies deletes far below that.
    • main: #16867 applies the buffer once it reaches 1945 MB, so the operation that crosses must bring it from below 1945 MB to 2048 MB or more: about 103 MB of estimate in one operation. The repro uses a 56,511,839-char selector-term field name, re-charged per update.
    • A natural packet that large would also have to land on that one byte value; the reviewers put the odds at one in 10^8 or less (an estimate, not measured). Hence likelihood contrived.
  • What the application sees, until the writer is closed. Every openIfChanged on an NRT reader, which SearcherManager.maybeRefresh calls on each refresh (refreshIfNeeded, SearcherManager.java:194-206), loses its cheap early return (StandardDirectoryReader.java:462-464): it goes through IndexWriter.getReader's full-flush path and then returns null because nothing changed (:466-472). Code that polls isCurrent() before reopening does the same on every poll. Code that commits when hasUncommittedChanges() is true keeps calling commit() (nothing new is written); hasDeletions() is true on an index without deletions. With assertions on (tests), the next packet push throws an AssertionError.
  • What it does not do. No hit, count, file or commit is wrong; RAM and flush accounting are unaffected; a new writer starts clean. Not new in 10.6.

Minimal repro

#

One JUnit test in lucene/core (org.apache.lucene.index) that uses only public IndexWriter API to trigger it: commit one document, send one doc-values update by its key and 19 keyed by a term with a 56,511,839-char field name, commit, and assert hasUncommittedChanges() is false. It fails on main with assertions on and off, and on the 10.6.0 and 9.12.3 jars.

Expected
hasUncommittedChanges() is false after commit(): every update was applied and committed.
Observed
hasUncommittedChanges() is true (AssertionError at TestTwoGiBUpdatePacket.java:54), with assertions on and off, and it stays true for the writer's life.

All files of this repro: repro/LFV-1287/

More files, environment, full output286 words

One test method, single thread. The test uses the test framework (LuceneTestCase, TestUtil.getDefaultCodec()) and reads two RamUsageEstimator constants (an @lucene.internal class) in its assumeTrue; the writer config, directory, codec and payload are fixed, while the framework still randomizes environment settings such as locale and timezone. It sits in org.apache.lucene.index by convention only. The assumeTrue guards the exact byte arithmetic: the 56,511,839-char length is calibrated for compressed oops and 12-byte object headers (the defaults for heaps below 32 GB), so on another layout the test is skipped. It needs about 60 MB of heap (the default 512 MB gradle test heap is enough); the test itself runs in about 1.4 s. The file passes :lucene:core:checkGoogleJavaFormat.

The control is the same test with the field name one char longer (estimate 2^31 + 38): it passes, so the unmatched update terms are not the cause; only the exact value is. The test's sizes hit 2^31 on 8.5.0 and later; 7.7.0-8.4.x charge 8 bytes less and need a key field 4 chars longer.

Regression test: this same test. It passes with fix A through gradle, with assertions on and off.

Why it looks unintended

#
  • isCurrent(): if it returns false, "you should call openIfChanged to get a new reader that sees the changes". Here openIfChanged returns null, forever.
  • The class asserts its total equals the sum of pending packets; upstream tests expect hasUncommittedChanges() false after commit.
  • Counter: the javadoc allows a spurious true, but for transient state; one more char gives false.
The full argument190 words
  • Contract. DirectoryReader.isCurrent() (DirectoryReader.java:625-642): for an NRT reader it "checks if either a new commit has occurred, or any new uncommitted changes have taken place via the writer", and "if this returns false, you should call openIfChanged to get a new reader that sees the changes". Here nothing changed and openIfChanged returns null, for the writer's life.
  • The class's own invariant. checkDeleteStats (BufferedUpdatesStream.java:296-303) asserts that the total equals the sum of the pending packets' bytesUsed; any() relies on it meaning "a packet is pending".
  • Tests. TestIndexWriter.testHasUncommittedChanges (TestIndexWriter.java:2385; :2418-2422: delete, commit, assertFalse(writer.hasUncommittedChanges())) and TestIndexWriterDelete.testNRTIsCurrentAfterDelete (:1333; :1351-1353: an NRT reader opened after the delete was applied is current).
  • History. The int field and the int negation came with LUCENE-2897 (62b692e9a3b, 2011-01-31), which replaced a packet byte count that was an AtomicLong negated as a long; the explicit (int) cast of a long estimate followed in LUCENE-3342 (963bce23d16, 2011-07-29). #11923 (1b9d98d6ec0, 2022, error-prone NarrowCalculation) widened the multiplication inside this expression and kept the outer (int) cast without discussing it. Nothing documents or accepts the drift.
The devil's-advocate check233 words

The intended-behaviour advocate's strongest case: (1) the int field matches a design bound, packets stay below 2 GB, and on main #16867 applies the buffer once it reaches 1945 MB (an application threshold checked after each change, FlushByRamOrCountsPolicy.java:34-39, not a cap: the repro's buffer overshoots it to 2,147,483,632 bytes), so the repro needs an absurd 56-million-char field name; (2) only one byte value in 2^32 drifts; (3) the effect is conservative: hasUncommittedChanges()'s javadoc (IndexWriter.java:4218-4223) allows true "when there are no actual \"real\" changes to the index", for example unmatched deletes or a merge right after commit, and hasDeletions()'s (:1444-1448) allows true for unmatched buffered deletes.

Why it fails: those leniencies are about transient pending state; here everything was applied and committed, and the same unmatched updates with a field one char longer give false. isCurrent()'s only stated exception is merging, where openIfChanged does return a new reader (the independent reproducer's reading); here it returns null. The class asserts the opposite invariant, no documented limit on a selector term's field-name length is exceeded, and the cast was kept mechanically. The advocate itself found that no intended, documented or misuse argument holds; what survives is strong: reach and a benign effect, so a maintainer could reasonably call it too contrived to be worth a change. That is why the bug is Low. Verdict: not intended, a defect.

Suggested fix

#

Recommended A: keep the packet estimate as a long

Fix A: store the packet estimate as a long in FrozenBufferedUpdates and drop the (int) cast (one file, +4/-4, no API change). The repro passes with assertions on and off, and so do 8 nearby suites (243 tests) and the format, forbidden-API and lint checks.

Downstream note

#

Applications that refresh NRT readers (for example through SearcherManager.maybeRefresh) or commit when hasUncommittedChanges() is true would, once a writer is in this state, go through the writer's full-flush path on every refresh and commit on every check until that writer is reopened; no data is wrong.

How it was found

#

A proof-obligation check of BufferedUpdatesStream's byte count (it must equal the sum of the pending packets' sizes, so it is 0 when none is pending) found the int field and the int negation that break it for one value, Integer.MIN_VALUE. A public-API JUnit test then reached that value and showed the stuck writer state.

The method in full123 words

Method: semi-formal (2026-11-03, main 5adff78bb168).

  • The obligation: after every push/finish pair the total returns to the sum of the still-pending packets (checkDeleteStats, BufferedUpdatesStream.java:296-303), so any() is false once all packets are finished. Push adds (long) x and finish adds (long) (-x) for the packet's int x (:80, :164); the pair cancels for every int except Integer.MIN_VALUE, and the estimate is narrowed from a long (FrozenBufferedUpdates.java:109-112), so the obligation fails for an estimate of exactly 2^31 (mod 2^32).
  • Witness: a public-API JUnit test that reaches that estimate cheaply through the per-update field-name charge (FieldUpdatesBuffer.java:147-148), calibrated with InfoStream, with a one-char-longer control that passes. It was later reduced to the test shown here.

History

#

Introduced by LUCENE-2897 (62b692e9a3b, 2011-01-31), which stored the packet size as an int and negated it as an int. The code is in every release since 3.2; it reproduces on 4.6.0-6.6.6, 7.7.0-10.6.0 and main. Not fixed upstream.

Versions tested6 rows

Introduced by LUCENE-2897, "apply delete-by-term on flushed segment while we flush" (Michael McCandless, GitHub mikemccand; 62b692e9a3b, 2011-01-31; archived issue #3971, svn r1065855, no PR; branch_3x aea84d391f3, 2011-05-05). Before it, the packet byte count was an AtomicLong negated as a long (LUCENE-1076, two days earlier, never released). The explicit (int) cast of a long estimate followed in LUCENE-3342 (963bce23d16, Robert Muir, 2011-07-29). A mechanical check of all 129 final release tags from 3.2 through 10.6.0 in the history clone finds the int field, the int negation and any() = bytesUsed.get() != 0 in every one; the clone has no 8.x tags after 8.8.1, and of those releases 8.11.4 was run from its release jars.

Whether a release reproduces depends on how it computes the estimate: 4.6.0 (the first release with doc-values updates) through 6.6.6 sum each update's size including the field name; 7.0.0-7.6.0 count real serialized bytes (LUCENE-7868), so this cheap input does not reach 2^31; LUCENE-8590 (7.7.0) brought back the per-update field-name charge. 3.2-4.5.1 have deletes only, and whether exactly 2^31 is reachable there was not determined. On main, #16867 (2813efa40a3, 2026-10-30) applies the buffer once it reaches 1945 MB, which narrows the trigger but does not fix it.

Registry title
FrozenBufferedUpdates narrows its packet RAM estimate to int and BufferedUpdatesStream subtracts it with an int negation, so a deletes/updates packet whose estimate is exactly 2^31 bytes (mod 2^32) leaves the stream's byte count at -2^32: for the rest of the writer's life NRT readers are never current while openIfChanged returns null, and hasUncommittedChanges() and hasDeletions() stay true
Area
index / IndexWriter buffered deletes and doc-values updates (BufferedUpdatesStream byte accounting)
Priority
Low, rank 789: Contrived: in every release since 4.6.0, a deletes/updates packet whose RAM estimate is exactly 2^31 bytes leaves IndexWriter reporting pending changes and NRT readers not current for the writer's whole life, but only a byte-exact estimate gets there (in releases it also takes a RAM buffer of 2 GB or more, or RAM-based flushing turned off). The cost is redundant refresh, flush and commit work; no hit, count, file or commit is wrong.
Impact class
minor
Impact note
Only a writer that freezes one deletes/doc-values-updates packet whose RAM estimate lands exactly on 2^31 bytes (mod 2^32) is hit: on 10.6.0 and earlier that needs a RAM buffer of 2 GB or more, or RAM-based flushing disabled, with that much buffered; on main (#16867) one operation of about 103 MB of estimate or more that crosses the 1945 MB delete-buffer limit; the effect lasts until the writer is closed but is only redundant refresh, flush and commit work (no hit, count, file or commit is wrong); 4.6.0 to 6.6.6 and 7.7.0 to 10.6.0 [exec on 4.6.0, 6.6.6, 7.7.0, 8.0.0, 8.4.1, 8.5.0, 8.11.4, 9.0.0, 9.1.0, 9.12.3, 10.5.2 and 10.6.0], while 7.0.0 to 7.6.0 count real serialized bytes, so this cheap input does not reach 2^31 there [exec: 7.6.0 passes].
Summary
You buffer numeric doc-values updates in one IndexWriter (RAM-based flushing disabled, NoMergePolicy) so that the frozen packet's RAM estimate is exactly 2^31 bytes; the test gets there with 19 updates keyed by a term whose field name is 56,511,839 chars (about 60 MB of real heap), and the 19th update crosses main's 1945 MB delete-buffer limit, so the packet is frozen and applied. After commit() you expect a newly opened NRT reader to be current and hasUncommittedChanges() and hasDeletions() to be false. Instead isCurrent() is false while openIfChanged returns null, and both writer methods return true, for the writer's lifetime, because the packet is added to the stream's long counter as Integer.MIN_VALUE and subtracted as -Integer.MIN_VALUE, which in int arithmetic is Integer.MIN_VALUE again (main -ea and -da, 10.6.0, 10.5.2, 9.12.3).
Introduced
62b692e9a3b0b4f86dfaeac43b5c7d7743d2185d, 'LUCENE-2897: apply delete-by-term on flushed segment while we flush' by Michael McCandless (GitHub mikemccand); JIRA LUCENE-2897 = apache/lucene#3971, svn trunk r1065855, patch on JIRA, no pull request; merged to branch_3x as aea84d391f3bdd1bf909a01146daf7ff6b756628 (r1099830, 2011-05-05). The new FrozenBufferedDeletes stored the packet byte count as 'final int bytesUsed' and BufferedDeletesStream subtracted it as 'bytesUsed.addAndGet(-packet.bytesUsed)', an int negation; before, the count was an AtomicLong negated as a long (LUCENE-1076, 295c8f84c73, two days earlier, never released), and any() = 'bytesUsed.get() != 0' already fed nrtIsCurrent and hasDeletions [read: git log -S over the full history clone]. The cheap trigger arrived later with the per-update field-name charge (4.6.0, LUCENE-5189 doc-values updates; again from 7.7.0, LUCENE-8590 FieldUpdatesBuffer, eaf840867fa / b0e6a92ede3). First affected version
