SortRescorer can give kept hits other hits' scores when topN is smaller than the number of hits

SortRescorer (and Expression#getRescorer) asked to keep fewer hits than it was given returns the right documents in the right order, but typically with other hits' scores: keeping 3 of 6, docs 3, 5, 1 get the scores of docs 1, 2, 0. Affects every release since 8.0.0.

The bug in 30 seconds

#

SortRescorer.rescore(searcher, hits, topN) re-sorts first-pass hits by a Sort and keeps the best topN. Which hits are kept, their order and their sort values are computed from each hit's own score. Only the last step, which writes ScoreDoc.score back, pairs hits by position instead of by document.

  1. Search body:lucene over six documents: BM25 ranks doc 5 first (0.0618) and doc 1 last (0.0337). Re-sort the 6 hits by popularity and keep 3: new SortRescorer(sort).rescore(searcher, hits, 3), as the search package docs suggest for "the best 1,000 hits" and "the final top-100".
  2. You expect the 3 most popular, docs 3, 5, 1 (popularity 60, 50, 40), each with its own first-pass score: 0.0463, 0.0618, 0.0337.
  3. You get docs 3, 5, 1 in that order with the right sort values, but with scores 0.0337, 0.0598, 0.0529: those of docs 1, 2 and 0. No error; with assertions on, an AssertionError at SortRescorer.java:86 instead.
  4. Why: to put scores back, rescore sorts the 3 kept hits by doc id (1, 3, 5) and copies, position by position, the scores of all 6 hits sorted by doc id (0, 1, 2, ...). A kept hit gets its own score only if no hit with a smaller doc id was dropped; here docs 0, 2 and 4 were dropped, so none does.
  5. In a probe of the documented pipeline (1,000 hits re-sorted to a top 100) 99 of 100 kept hits had a wrong score. Rescoring with topN equal to the number of hits is correct. Fix: pair the scores by doc id.

Who is affected

#

Anyone who calls SortRescorer or Expression#getRescorer with topN below the number of first-pass hits, the use the search docs describe, and then reads ScoreDoc.score: to show scores, apply a threshold or combine with another pass. Documents and order stay right. Default codec and settings, any index size, every release since 8.0.0.

Mechanism, terms and numbers828 words

SortRescorer.rescore(searcher, firstPassTopDocs, topN) re-sorts first-pass hits by a Sort and keeps the best topN; the search package docs give exactly this use: "the best 1,000 hits by BM25 score may be sorted by descending popularity in order to compute the final top-100 hits". Since 8.0.0 the method puts the first-pass scores back on the kept hits by position: it sorts the kept hits by doc id and gives the i-th of them the score of the i-th first-pass hit by doc id. That is sure to pair each hit with itself only when no hit was dropped, which is what the assert just before the copy assumes; otherwise a kept hit keeps its own score only if no hit with a smaller doc id was dropped. With topN smaller than the number of hits, the documents, their order and their FieldDoc sort values are right, but kept hits typically carry other hits' scores (how many depends on the sort; none with a FIELD_DOC sort): keeping 3 of 6 hits, docs 3, 5, 1 come back with the scores of docs 1, 2, 0, and in a probe of the documented 1,000 -> 100 pipeline 99 of 100 kept hits had a wrong score. With assertions enabled every call with topN < hits throws AssertionError at SortRescorer.java:86. Expression#getRescorer returns an ExpressionRescorer, which extends SortRescorer without overriding rescore, and behaves the same. 4.8.0 to 7.7.3 returned each hit's own score; the copy and the assert came with LUCENE-8412 (55bfadbce115, released in 8.0.0). The fix pairs the scores by doc id instead of by position.

Terms

#
  • Rescorer: takes the top hits of a cheap first search and re-orders them with something more expensive. Rescorer.rescore(searcher, firstPassTopDocs, topN) returns "How many re-scored hits to return" (Rescorer.java:40).
  • SortRescorer(sort): a rescorer that re-sorts the first-pass hits by a Sort (a field such as popularity, the score itself, or an expression). Expression#getRescorer(bindings) returns an ExpressionRescorer, a SortRescorer subclass that only adds a more detailed explain.
  • Doc id: a document's number in the index. The first-pass hits come best first; SortRescorer works on them in doc-id order.

The bug

#
  1. rescore clones the first-pass hits and sorts the clone by doc id (SortRescorer.java:41-44).
  2. It creates a field-sorted collector that keeps the best min(topN, hits) entries (TopFieldCollectorManager(sort, topN, null, Integer.MAX_VALUE), :48-49) and feeds it every hit, in doc-id order, with that hit's own score (:57-82, the score at :77). So the kept set, its order and the sort values (also FIELD_SCORE and expressions over _score) are right.
  3. The collector's topDocs() (:84) carries no scores (NaN): a field-sorted collector does not track them since LUCENE-8412 (executed: [doc 3 fields[0]=60 score=NaN] ...).
  4. To put scores back (:85-91, comment "set scores from the original score docs") it sorts the kept hits by doc id and runs rescoredDocsClone[i].score = hits[i].score (:90), where hits holds all first-pass hits by doc id. The k-th smallest kept doc id gets the score of the k-th smallest first-pass doc id: the same document exactly when no hit with a smaller doc id than that kept hit was dropped, which topN >= hits guarantees. The assert just before, hits.length == rescoredDocs.scoreDocs.length (:86), states that assumption.
  5. With -ea the assert throws on every call with topN < hits. With -da (production) the copy runs silently. The clone shares its ScoreDoc objects with the returned array, so the returned hits get the wrong values.
  6. ExpressionRescorer (ExpressionRescorer.java:37-47) never overrode rescore, so Expression#getRescorer (Expression.java:112-114) has the same defect.
  7. Not triggered with topN >= hits. A FIELD_DOC sort keeps the smallest doc ids, so the positions line up by accident under -da (-ea still throws).

Exposure and likelihood385 words
  • Who is exposed. Callers of new SortRescorer(sort).rescore(searcher, hits, topN) or expression.getRescorer(bindings).rescore(...) with topN < hits.scoreDocs.length: the use the search package docs give (1,000 hits re-sorted to a top 100, package-info.java:371-373) and the typical use the Rescorer javadoc describes ("collecting the top few hundred hits perhaps").
  • What goes wrong. Only ScoreDoc.score. Each kept hit gets the first-pass score of another hit from the same result, sometimes of a hit that was not kept. Code that displays scores, applies a minimum score, merges result lists by score or feeds the score into a later pass gets those values. With a FIELD_SCORE sort the same FieldDoc holds its own score in fields[0] and another hit's in .score.
  • Not affected. Which documents are returned, their order and their sort values. Calls with topN >= hits.
  • How often. With assertions on, every call with topN < hits throws. With assertions off, the number of kept hits with a wrong score ranges from 0 to topN and depends on how the sort reorders doc ids: 3 of 3 in the 6-document example, 99 of 100 in one probe corpus of the documented pipeline, 0 with a FIELD_DOC sort. A randomized check on 30 random indexes confirmed the doc-id-rank pairing in all 2,072 cases it checked; in 1,737 of the 1,832 cases with topN < hits at least one kept hit had a wrong score, and in the other 95 the pairing happened to give every kept hit its own score.
  • With assertions enabled (-ea, as in Lucene's own test runs) the call throws AssertionError, so an application test that covers this path with assertions on fails.
  • Settings. Opt-in API, nothing else non-default: new IndexWriterConfig() (so BM25) and a plain IndexSearcher; the diagram and security probes also ran Lucene's default codec, the JUnit tests the test framework's randomized default codec, which does not change BM25 scores; 2 hits and topN = 1 suffice. Rescorer and ExpressionRescorer are @lucene.experimental; SortRescorer itself carries no experimental tag.
  • Downstream (code search of default branches): Solr and OpenSearch do not reference SortRescorer or ExpressionRescorer; Elasticsearch has no SortRescorer and wraps Expression#getRescorer in its expression module, with only a unit test found calling it. A 2021 java-user thread recommends SortRescorer for re-sorting results. Private code is not visible.

Why it is a bug, not intended

#
  • The search package docs give this exact use: re-sort "the best 1,000 hits" into "the final top-100 hits".
  • The code means to keep scores ("set scores from the original score docs") and does when topN >= hits; 7.7.3 and earlier did for every topN.
  • The assert at :86 encodes the broken assumption; no doc restricts topN.
The full argument268 words
  • The contracts. Search package docs (package-info.java:371-373): "SortRescorer, to rescore using a Sort. For instance, the best 1,000 hits by BM25 score may be sorted by descending popularity in order to compute the final top-100 hits." Rescorer (Rescorer.java:21-25, :40): "collecting the top few hundred hits perhaps, and then use this class to mix in a more costly second pass scoring"; "@param topN How many re-scored hits to return". The code's comment (SortRescorer.java:85): "set scores from the original score docs". ScoreDoc.score (ScoreDoc.java:25): "The score of this document for the query." ExpressionRescorer (ExpressionRescorer.java:30-33): "Functionally this is the same as SortRescorer ... except for the explain method".
  • History. 4.8.0 (LUCENE-5545) to 7.7.3 created the collector with trackDocScores=true, so every kept hit recorded its own score; all 14 releases 7.0.0-7.7.3 pass (7.4.1 and 7.5.1 have CHANGES sections but were never released). LUCENE-8412 (55bfadbce115, 8.0.0) removed that option and added the comment, the assert and the positional copy. Its CHANGES entry says scores "need to be set on top hits via TopFieldCollector#populateScores instead" and its MIGRATE entry explains an efficiency change; neither says rescored scores became undefined, and the issue discussion (#9459) never mentions SortRescorer or topN.
  • Untested case. TestSortRescorer calls rescore with topN 10 for 3 hits (TestSortRescorer.java:96, :134) or topN == hits (testRandom, :179-186); TestExpressionRescorer with topN 10 for 3 hits (:106). None asserts a score after rescoring.
  • No 'by design' record. No issue, PR, review comment, list thread or JIRA entry calls the current behaviour intended.
The devil's-advocate check235 words

The strongest case for "intended" (built by a devil's-advocate verifier and by an OpenAI GPT-5.6 reviewer): the class javadoc promises only that it "re-sorts according to a provided Sort"; since LUCENE-8412 a field-sorted collector computes no scores, so scores of re-sorted hits are unspecified; the assert at :86 states a precondition, topN >= hits; Rescorer is @lucene.experimental; and for ExpressionRescorer the javadoc says it assigns "second pass scores", so the first-pass score is not the obvious expected value.

Why it fails: the code sets the scores on purpose (the comment at :85) and returns each hit's own score whenever topN >= hits; without the copy the scores would be NaN, and what it returns is neither NaN nor "unspecified" but another document's plausible score. The assert encodes an internal assumption that the documented use contradicts, not a documented precondition: no javadoc, CHANGES or MIGRATE text restricts topN, and the package docs give topN < hits as the example. LUCENE-8412 was an efficiency refactor that announced no SortRescorer change, and 4.8.0-7.7.3 returned own scores. @lucene.experimental allows API changes, not wrong values. For ExpressionRescorer, another hit's first-pass score is wrong under every reading. That few callers read scores after a re-sort argues for low impact, not for intended behaviour. The independent reproducer, the devil's advocate and the adjudication rejected the intended-behaviour argument, and the cross-model review records rate it weak. Verdict: a defect.

Suggested fix

#

Recommended A: copy each kept hit's own score by a doc-id merge walk

Pair the scores by document, not by position: walk the kept hits and all first-pass hits together in doc-id order and copy each kept hit's own score (+9/-4 lines, SortRescorer.java only, same order of cost). The tests, every core rescorer suite and the whole expressions module pass with it, with assertions on and off.

assert rescoredDocs.scoreDocs.length == Math.min(topN, hits.length);
ScoreDoc[] rescoredDocsClone = rescoredDocs.scoreDocs.clone();
Arrays.sort(rescoredDocsClone, docIdComparator);
int h = 0;
for (ScoreDoc rescored : rescoredDocsClone) {
  while (hits[h].doc != rescored.doc) {
    h++;
  }
  rescored.score = hits[h].score;
}
All options and trade-offs4 options · 529 words

The kept hits are a subset of the first-pass hits and both arrays are already sorted by doc id, so a merge walk restores each hit's own score. One option was built and validated in a scratch worktree at ea57360912ed (removed afterwards); the others are not built.

A: copy each kept hit's own score by a doc-id merge walk (validated by the checks) (recommended)

#

Replace the positional loop at SortRescorer.java:89-91 by a walk over both doc-id-sorted arrays, and change the assert to what is actually true: rescoredDocs.scoreDocs.length == Math.min(topN, hits.length). +9/-4 lines in SortRescorer.java; ExpressionRescorer inherits the fix.

assert rescoredDocs.scoreDocs.length == Math.min(topN, hits.length);
ScoreDoc[] rescoredDocsClone = rescoredDocs.scoreDocs.clone();
Arrays.sort(rescoredDocsClone, docIdComparator);
int h = 0;
for (ScoreDoc rescored : rescoredDocsClone) {
  while (hits[h].doc != rescored.doc) {
    h++;
  }
  rescored.score = hits[h].score;
}

Trade-offs

  • Cost. The positional loop becomes a walk of at most hits.length steps (O(hits + topN)), next to the existing O(hits log hits) doc-id sort; no new allocation.
  • Safety. Every kept doc is a first-pass hit, so the walk cannot run past the end. This relies on the documented input contract that the first-pass hits come from the same searcher (Rescorer.java:38-39); caller-built TopDocs that break it were not examined.
  • Rebase. Open draft #16847 (long doc ids) changes the doc-id types in this file but not these lines.

B: look up each kept doc's score (not built)

#

Arrays.binarySearch(hits, rescored, docIdComparator) for each kept hit, or a doc-to-score map built before collection.

Trade-offs

Same result and does not depend on walking in step, but O(N log M) or an extra map; option A is simpler and cheaper.

C: application workaround, no Lucene change

#

Call rescore(searcher, hits, hits.scoreDocs.length) and keep the first topN entries; then the positional copy lines up.

Trade-offs

Executed in the verifier's 1,000 -> 100 probe: the same 100 documents in the same order (compared with assertions off), each with its own score. Costs a collector queue the size of the first pass (1,000 instead of 100).

D: require or document topN >= hits (not recommended)

#

Throw IllegalArgumentException when topN < hits, or document the restriction.

Trade-offs

Contradicts the search package docs' own example and the typical use the Rescorer javadoc describes.

How it was found

#

Code reading, then checking. The hunt plan pointed at the positional copy; an AI tool then compared the stock jar with an independent reference on every index of up to 5 documents (41 million checks): every wrong score has topN < hits, none has topN >= hits. Independent verifiers and an adjudication confirmed it.

The method in full233 words

Method: code reading, bounded by bounded-exhaustive translation validation, then a public-API JUnit.

  • A hunt unit (2026-10-26) swept the siblings of earlier rescorer findings. Its plan named the lead from code reading: with topN < hits, the copy at SortRescorer.java:90 pairs the i-th smallest doc id of all hits with the i-th smallest doc id of the top N.
  • The finder, an AI tool, compared the stock jar with an independent reference (the first min(topN, hits) hits in sort order, each with its own score and sort values) on every index of up to 5 documents in every segment layout, plus zero-leaf and empty readers, every value assignment, every first-pass hit subset, topN 1 to hits + 1 and 11 sorts (including FIELD_SCORE, FIELD_DOC, a values-source sort field and 3 expressions): 41,261,000 checks with assertions off and 32,369,216 with them on, of which 20,630,500 in each mode check scores, the doc set, order and sort values (the rest check totalHits, a separate observation).
  • Every wrong score and every AssertionError had topN < hits; there were none with topN >= hits, and 0 doc-set, order or sort-value mismatches. Two injected mutants of SortRescorer (the collector size, the collected score) were detected, so the check is not vacuous.
  • A public-API JUnit on the stock jars followed; then the cross-model reviews, verifiers, an adjudication, the release sweep, the prior-report search and the security screen.

History

#

Introduced in 8.0.0 by LUCENE-8412 (55bfadbce115, 2018), which stopped the collector from tracking scores and added the positional copy and the assert. All 60 releases 8.0.0-10.5.2 and main fail; all 14 releases 7.0.0-7.7.3 pass. Not fixed upstream.

Versions tested7 rows

Introduced by 55bfadbce115, LUCENE-8412 "TopFieldCollector no longer takes a trackDocScores option" (jpountz, 2018-07-23, master only; JIRA patch workflow, no GitHub PR; the issue is now #9459). It replaced TopFieldCollector.create(sort, topN, true, true), which tracked each kept hit's own score, and added the comment, the assert and the positional copy; git blame and git log -L84,92 attribute these lines only to it (besides cbd8cacc50c, which created the class). No commit-level bisect (it would need the 2018 build); the release bracket confirms it. SortRescorer and Expression#getRescorer exist since 4.8.0 (LUCENE-5545), so this is a regression. Upstream main (a9779ef3c193), branch_10x and branch_10_6 (the unreleased 10.6.0) still have the assert and the copy (read 2026-10-26); the lines are unchanged since 2018.

Bug record

LFV-424, snapshot of 2026-10-27

Registry title
SortRescorer and ExpressionRescorer give returned hits another hit's first-pass score when topN is smaller than the number of first-pass hits (AssertionError with -ea)
Area
search / rescoring (SortRescorer; expressions ExpressionRescorer inherits rescore())
Priority
Medium, rank 51: Documented, plausible SortRescorer or ExpressionRescorer use with topN below the hit count silently gives nearly every hit a wrong score while order and documents stay correct.
Impact class
silent wrong results
Impact note
Applications that call SortRescorer.rescore or Expression#getRescorer(bindings).rescore with topN smaller than the number of first-pass hits (the use the search package docs describe: the best 1,000 BM25 hits re-sorted by popularity into the final top 100) get, with the default codec, IndexWriterConfig and searcher, at any scale and in every release since 8.0.0, another first-pass hit's score in ScoreDoc.score on nearly every returned hit (99 of 100 in that documented pipeline), while the documents, their order and the FieldDoc sort values are correct, so only callers that read the scores (display, score thresholds, combining with a later pass) are misled; with -ea the same call throws AssertionError at SortRescorer.java:86 instead.
Summary
You run a search, take its top hits and call new SortRescorer(sort).rescore(searcher, hits, topN), or Expression#getRescorer(bindings).rescore, with topN smaller than the number of hits, for example to re-sort the best 1,000 hits by popularity and keep the top 100 as the search package docs suggest. You expect the top N hits in sort order, each with its own first-pass score, which is what every release up to 7.7.3 returned and what you still get when topN is at least the number of hits. Instead the documents and their order are right, but the k-th smallest doc id among the returned hits gets the score of the k-th smallest doc id among all first-pass hits, so nearly every returned hit carries another hit's score (with 2 hits and topN=1, doc 1 comes back with doc 0's score), and with assertions enabled rescore throws AssertionError at SortRescorer.java:86.
