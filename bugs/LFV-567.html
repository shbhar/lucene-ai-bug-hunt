scale() writes to the context map that all slices of an executor search share: NullPointerException or silently different scores

On an IndexSearcher with an executor, a function query with scale() and about 20 query() sources can silently return different scores or throw NullPointerException: all slices share one context map, and scale()'s write during the search makes it grow while others read it. The repro fails 20 of 20 runs.

The finding in 30 seconds

#

A function query's Weight keeps one small map, the context, for the whole search, and all slices of an executor search use it. scale() fills in its min/max entry lazily, during the search, from whichever slice thread gets there first.

Function queries and their context map in one minute

#
  1. FunctionQuery (module lucene/queries) scores every document with a function built from ValueSources, for example sum(scale(num, 0, 1), query(body:w0)). scale(num, 0, 1) maps a field's values onto the range 0..1 using the min and max over the whole index; query() uses another query's score.
  2. When the search starts, createWeight makes one context map (an IdentityHashMap) and each source may store per-search data in it: query() stores its Weight, and the map always holds "searcher". For each segment, getValues then reads that data.
  3. new IndexSearcher(reader, executor) groups the segments into slices that run on different threads. They all use the same Weight, so the same map.

The finding, step by step

#
  1. Index 1,600 small documents in 32 segments. Search FunctionQuery(sum(scale(num, 0, 1), query(body:w0), ..., query(body:w19))) for the top 10 with BM25Similarity(1.8, 0.3) on new IndexSearcher(reader, executor): 8 threads, 7 slices.
  2. You expect what the same search gives without an executor, every time: doc 612 first with score 4.680546. IndexSearcher is documented as completely thread safe.
  3. Instead, within the first 70 of 1,000 searches, one returns other scores and another order, with no error. In the gradle run doc 1271 is first with 5.1422386 and doc 612 has 5.1421137: exactly what the default BM25Similarity() gives, so the configured Similarity was silently dropped.
  4. Why: the query's Weight has one context map for all slices. After createWeight it holds 21 entries ("searcher" and 20 query() weights). scale() adds the 22nd from a slice thread during the search; the 22nd entry makes the map copy itself into a bigger table, and meanwhile other slices find "searcher" and their weights missing. A query() that misses both its weight and "searcher" then rebuilds its weight on a new searcher with the default Similarity.
  5. Functions that also use maxdoc(), idf(), docfreq(), norm() or tf() can crash instead: NullPointerException ("searcher" is null; seen in earlier tests). With 10 query() sources the map never grows, and all 5 control runs were right. Every release since 4.0.0-ALPHA (2012) is affected.

Who is affected

#

Applications that search with an executor (opt-in) and use FunctionQuery, FunctionRangeQuery or a ValueSource sort whose function has scale() plus about 20 query(), totaltermfreq() or sumtotaltermfreq() sources, so that scale()'s entry is the map's 22nd or 43rd (or a later growth point). Searchers without an executor are unaffected, and a 10-source function passed every control run. Every release since 4.0.0-ALPHA.

Mechanism, terms and numbers694 words

FunctionQuery, FunctionRangeQuery and ValueSource sort fields create one context map per search (ValueSource.newContext, an IdentityHashMap documented as "non-threadsafe") and hand it to every slice of an executor search. ScaleFloatFunction stores nothing in createWeight; it computes the whole-index min/max on first use in getValues and puts it into that shared map from a slice thread. When that put makes the map grow (the 22nd, 43rd or a later growth point), the other slices can briefly find entries missing: a query() that misses both its weight and "searcher" rebuilds it with the default Similarity, so a searcher whose Similarity scores differently silently gets different scores and top hits, and sources that need "searcher" (maxdoc(), idf(), ...) throw NullPointerException. In the repro (1,600 documents, 7 slices, sum(scale(num), 20 x query()), BM25Similarity(1.8, 0.3)), 20 of 20 runs return a different top 10 within the first 70 searches. Every release since 4.0.0-ALPHA is affected; the fix computes the scale in createWeight.

  • FunctionRangeQuery shares its map the same way (FunctionRangeQuery.java:148-149, :154, :170), and so does a sort by ValueSource.getSortField (ValueSource.java:379-382, :434).
  • After createWeight the map in the repro holds 21 entries: "searcher" and the 20 query() weights. The JDK's IdentityHashMap grows its table when an entry would make 3 * size exceed the table length, so at the 22nd entry for the default capacity 32 (table length 64), then at the 43rd, the 86th and so on, as the table doubles (JDK 25 IdentityHashMap.java:160, :456).
  • resize copies the entries one by one into a new array, nulling each old slot as it goes (:489-501), and only then publishes the new table (:502). A get on the old table that meets a nulled slot returns null (:337-349). By reading the code, two slices that resize at the same time could also drop entries for the rest of the search (not observed directly).
  • A missing "searcher" makes MaxDocValueSource throw (MaxDocValueSource.java:49-50; the same read in DocFreqValueSource.java:60, IDFValueSource.java:51, NormValueSource.java:66, TFValueSource.java:54). A query() that misses both its weight and "searcher" rebuilds its weight with the default Similarity and puts it back into the shared map (QueryValueSource.java:125, then :85), where later leaves of the same search find it; a weight lost again on the way throws NullPointerException: ... because "this.weight" is null (QueryValueSource.java:150).
  • ScaleFloatFunction is the only built-in ValueSource that writes the context outside createWeight (the query() fallback above calls createWeight during a search only after an entry went missing). asDoubleValuesSource is not affected: it makes a new context per leaf (ValueSource.java:200).

Exposure and likelihood276 words
  • Who is exposed. Applications that use IndexSearcher(IndexReader, Executor) and run a FunctionQuery, FunctionRangeQuery or ValueSource sort whose function contains scale() and enough context-storing sources (query(), totaltermfreq(), sumtotaltermfreq(); "searcher" counts once) that scale()'s entry is the 22nd or 43rd (or a later growth point) of the map: about 20 such sources with one scale(), or 41.
  • Nearby sizes. With several scale() calls the window widens. With 19 query() sources (the put is then the 21st entry, below the growth point) one of five runs also failed, at search 597 of 1,000; that failure was not instrumented and its cause is open.
  • What they see. With a Similarity that scores differently from the default BM25Similarity(), silently different scores and top hits (no exception; this doc's test, 20 of 20 runs). With maxdoc(), idf(), docfreq(), norm() or tf() in the function, a failed search (earlier tests): NullPointerException: Cannot invoke "org.apache.lucene.search.IndexSearcher.getIndexReader()" because "searcher" is null. With the default Similarity, no run showed different scores (5 runs of this function), but one threw.
  • Contained. Only the triggering search is affected; other searches on the same searcher and executor were unaffected (0 of about 17,000 in a probe), nothing is cached and the index is not touched.
  • Not affected. Searchers without an executor; in the controls, a 10-source function (5 of 5 runs pass all 1,000 searches); asDoubleValuesSource.
  • How likely. Narrow: it takes an executor and a function sized to a growth point, and the searches found no report of it since 4.0.0-ALPHA (2012). But a deployment whose ranking function sits at a growth point fails in most runs.

Why it looks unintended

#
  • IndexSearcher instances "are completely thread safe" (IndexSearcher.java:71-75); nothing says function queries need a searcher without an executor.
  • ValueSource's convention: sources store weight info in createWeight, and getValues retrieves it (ValueSource.java:66-68); scale() writes in getValues.
  • Lucene's own Weight code shares the map, not the user, and the wrong scores are exactly the default Similarity's.
The full argument177 words
  • Contract. IndexSearcher instances "are completely thread safe, meaning multiple threads can call any of its methods, concurrently" (IndexSearcher.java:71-75); the executor constructor "Runs searches for each segment separately, using the provided Executor" (:194). Nothing says function queries need a searcher without an executor.
  • ValueSource's convention. "Implementations should propagate createWeight to sub-ValueSources which can optionally store weight info in the context. The context object will be passed to getValues() where this info can be retrieved." (ValueSource.java:66-68). ScaleFloatFunction stores nothing in createWeight (:148-151) and writes in getValues (:98, :106-109).
  • Who shares the map. FunctionWeight, FunctionRangeWeight and ValueSourceSortField hand the one map to every slice; the user never sees it.
  • Tests. TestValueSources searches through newSearcher(reader) (TestValueSources.java:201), which randomly adds an executor (LuceneTestCaseParent.java:2563-2583, :2641-2675); its testScale (:593) passes because its functions are small.
  • Effect. The configured Similarity is silently replaced by the default one for some or all of the terms of a search; that is not a documented trade-off of concurrent search.
The devil's-advocate check118 words

Strongest case for "intended": newContext is documented "Returns a new non-threadsafe context map" (ValueSource.java:73); FunctionQuery (FunctionQuery.java:38) and the executor constructor (IndexSearcher.java:199) are @lucene.experimental; and 20 query() sources is an unusual function.

Why it fails: that javadoc warns whoever shares the map, and the sharing is Lucene's own Weight code; experimental status does not make silently different scores acceptable; no limit on function size is documented, and the failures appear at or next to the map's growth points (21 or 42 entries before scale()), not at some size where things degrade. The intended-behaviour verifier and reviews by another model family (OpenAI GPT-5.6, reading-only) rejected this argument. Verdict: not intended, a defect.

Suggested fix

#

Recommended A: compute the scale in createWeight

Compute the scale in ScaleFloatFunction.createWeight, so getValues only reads the shared map (one import, one parameter type, five lines). Validated: the repro passes with assertions on and off, the 112 function-query tests and the whole lucene/queries suite (513 tests) pass, and :lucene:queries:check -x test passes.

private ScaleInfo createScaleInfo(Map<Object, Object> context, IndexReaderContext readerContext)
    throws IOException { /* unchanged body */ }

@Override
public void createWeight(Map<Object, Object> context, IndexSearcher searcher) throws IOException {
  source.createWeight(context, searcher);
  // The slices of a concurrent search share this context, so compute the scale now: getValues
  // must only read the context, never write to it.
  if (context.get(ScaleFloatFunction.this) == null) {
    createScaleInfo(context, searcher.getTopReaderContext());
  }
}

Fix A was validated with gradle in a scratch worktree of 5adff78bb168; B was checked earlier with the changed class compiled over the jars in standalone runs; C was not run. A fixes scale(); B also covers custom ValueSources that write the context from getValues. They combine well.

A: compute the scale in createWeight (validated by the checks) (recommended)

#

ScaleFloatFunction.createWeight computes the min/max right after source.createWeight, on the thread that creates the Weight, and stores it in the context; getValues then only reads it. createScaleInfo takes an IndexReaderContext instead of a LeafReaderContext, so it can be called with searcher.getTopReaderContext(); ReaderUtil.getTopLevelContext walks to the same root as the stock lazy path, so the min/max is unchanged. The lazy path stays for callers that never call createWeight (asDoubleValuesSource, one context per leaf).

private ScaleInfo createScaleInfo(Map<Object, Object> context, IndexReaderContext readerContext)
    throws IOException { /* unchanged body */ }

@Override
public void createWeight(Map<Object, Object> context, IndexSearcher searcher) throws IOException {
  source.createWeight(context, searcher);
  // The slices of a concurrent search share this context, so compute the scale now: getValues
  // must only read the context, never write to it.
  if (context.get(ScaleFloatFunction.this) == null) {
    createScaleInfo(context, searcher.getTopReaderContext());
  }
}

Trade-offs

  • Fixes scale() only: a custom ValueSource that writes the context in getValues stays unsafe (see B).
  • The whole-index scan moves into createWeight: it runs once, on the calling thread, before the slices start (today each slice that misses the entry may scan in parallel), and it also runs when no scorer is ever pulled. TotalTermFreqValueSource.createWeight already loops over all leaves (TotalTermFreqValueSource.java:65-71), an in-tree precedent for the eager scan.
  • No targeted test yet covers a nested scale() or the FunctionRangeQuery and sort-field entry points; the runs cover this test and the existing suites only.

What the checks validated

  • The repro passes with assertions on and off; with the fixed class compiled over the jars in standalone runs, 10 of 10 runs pass (5 on, 5 off).
  • All 15 classes under org.apache.lucene.queries.function, 112 tests including TestValueSources.testScale and the repro, pass; the whole :lucene:queries:test, 513 tests, 5 skipped, passes.
  • :lucene:queries:check -x test passes (google-java-format, ecj lint, forbidden APIs) with the fix and the new test.

B: make the shared context map thread-safe (validated by the checks)

#

ValueSource.newContext returns Collections.synchronizedMap(new IdentityHashMap<>()). This covers every writer, custom sources included.

Map<Object, Object> context = Collections.synchronizedMap(new IdentityHashMap<>());

Trade-offs

  • A lock on each context access (per leaf and source, not per document).
  • Slices may still compute the scale twice (harmless, same value).
  • A caller-supplied map, for example in GroupingSearch(ValueSource, Map), is not covered.

What the checks validated

Checked earlier with a replaced ValueSource on main ea57360912ed: the independent reproducer's four tests pass with assertions on and off, 0 of 20 + 0 of 20 runs fail on a 64-vCPU host, and the same replacement passes on 4.0.0. Not run through gradle.

C: give each slice its own copy of the map (not run)

#

Copy the context per slice or leaf after createWeight. Not recommended alone: with the lazy scale() each copy would rescan the whole index. Only useful together with A.

Trade-offs

One small map copy per leaf; needs A to avoid repeated scans.

Downstream note

#

For downstream servers that turn client function syntax into these classes and search with an executor: a client can only break its own search (an error or a wrong ranking); other searches were unaffected.

How it was found

#

Semi-formal: a bytecode scan of Lucene's search-time classes found that scale() is the only built-in function source that writes to the per-search context outside createWeight. A bounded-exhaustive model of the JDK's IdentityHashMap growth rule then predicted which function sizes make that write grow the map, and directed runs failed at or next to those sizes.

The method in full182 words

Method: semi-formal (2026-10-26, main ea57360912ed).

  • A bytecode scan (an abstract interpretation of the class files with a per-basic-block symbolic operand stack that resolves the receiver of every field write and collection mutation) covered 689 subtypes of Weight, Query, ValueSource, Similarity and other search-time types in 17 jars. It flagged ScaleFloatFunction.createScaleInfo as the only built-in ValueSource method that puts into the per-search context map outside createWeight. Code reading showed that FunctionWeight hands that map to every slice.
  • A differential test of executor and sequential searches passed for small functions, so a bounded-exhaustive model of the real JDK growth rule enumerated every pair of entries before the search (up to 120) and puts during the search (up to 8): 968 cases, 108 of them grow the map during the search.
  • Directed experiments and sweeps on a 64-vCPU host then failed at the predicted growth points (20 and 41 padding sources: 5 of 5 runs each; none at 18, 19, 21, 22 and 42 in the independent reproducer's sweep; one throw in five runs at 40, next to the second).

History

#

In Lucene since the function queries moved into the queries module (a993ae90323, LUCENE-3249, 2011); first released in 4.0.0-ALPHA; the code pattern has not changed since. Executed on 14 releases from 4.0.0-ALPHA to 10.6.0 and on main: affected each time. 3.6.x has no such API.

Versions tested7 rows

Introduced into Lucene by a993ae90323 (2011-06-28, LUCENE-3249 = #4322 "Moved FunctionQuery impls to new Queries module", Christopher John Male), with b3f0ae9b7a0 the day before (LUCENE-3240 = #4313: FunctionQuery, ValueSource and newContext). The search-time put came with that move from Solr code, where 8b241d92303 (2011-01-08, LUCENE-2831 = #3905, Yonik Seeley) made scale() cache its min/max in the shared context from getValues; the executor search with one shared Weight is from 87274d00ac1 (2011-01-05, LUCENE-2837 = #3911). svn era, no PR. FunctionRangeQuery shares its map the same way since it was added (13f8ab93a97, LUCENE-6720, 5.4.0). SOLR-5524 (4.7.0) changed only the context key. The bug's code pattern (one context per Weight shared by the slices, "searcher" in the map, the lazy put from getValues, nothing stored in createWeight) is present at all 123 release tags from 4.0.0-ALPHA to 10.5.2 in the history clone, although the code itself changed over time (for example the context key in 4.7.0); the five affected files are identical in 10.6.0 and main 5adff78bb168; upstream main f72004515ec2 (2026-11-03) has no later commit on them.

LFV-567, snapshot of 2026-11-09

Registry title
FunctionQuery, FunctionRangeQuery and ValueSource sort fields share one non-thread-safe context map across the slices of an executor search, and scale() (ScaleFloatFunction) writes to it during the search, so when that write grows the map the search throws NullPointerException or silently returns different scores
Area
queries / function queries (ValueSource context map under concurrent search)
Priority
Low, rank 723: With an executor search a FunctionQuery whose scale() grows the shared context map throws a NullPointerException or, with a non-default Similarity, silently gives different scores; the trigger is contrived, so it goes with the concurrent-search crash row LFV-125.
Impact class
silent wrong results
Impact note
Applications that search through an IndexSearcher with an executor (opt-in; in Solr, for example, a node executor plus multiThreaded=true [read]) with a FunctionQuery, FunctionRangeQuery or ValueSource sort whose function contains scale() and enough context-storing sources (query(), totaltermfreq(), sumtotaltermfreq(); about 20 with one scale()) that a search-time scale() put is the 22nd or 43rd entry of the shared IdentityHashMap (or close to it, through concurrent duplicate puts) are hit: the search fails with NullPointerException ('"searcher" is null') or, on a searcher with a non-default Similarity, silently returns different scores and top hits (20 of 20 runs of the one-test repro, 2026-11-04); in the controls a 10-source function passed 5 of 5 runs and a 19-source one failed once in 5, searchers without an executor and the asDoubleValuesSource adapter [read] are not affected, and no scale is needed.
Summary
You search with a FunctionQuery (or FunctionRangeQuery, or a sort by ValueSource.getSortField) whose function uses scale() together with about twenty context-storing sources such as query(), on an IndexSearcher built with an executor, and expect the same hits and scores as on a searcher without one, because IndexSearcher is documented as completely thread safe. Instead all slices share the Weight's one IdentityHashMap context (documented 'non-threadsafe'), ScaleFloatFunction.getValues puts its min/max entry into it from the slice threads, and when that put resizes the map other slices miss entries such as "searcher". The search then throws NullPointerException, or, on a searcher with a non-default Similarity, QueryValueSource silently rebuilds its weight with the default Similarity and the scores and top hits change.
