RescoreTopNQuery and LatLonPoint.nearest size their queue from n, not from the index, so n = Integer.MAX_VALUE throws even on a one-document index

Asking RescoreTopNQuery or LatLonPoint.nearest for every hit with n = Integer.MAX_VALUE throws IllegalArgumentException, even on a one-document index, because both allocate a queue of n + 1 slots before collecting any hit. IndexSearcher.search caps the same n at the document count and returns the hit.

The finding in 30 seconds

#

Both APIs size their result queue by the n you pass, not by how many hits the index can have, and Lucene's priority queue allocates all n + 1 slots at once.

Background: top-n queues in Lucene

#
  1. Lucene keeps the best n hits in a priority queue that holds at most n entries. Its PriorityQueue allocates the whole array, n + 1 slots, when it is created, and refuses 2,147,483,631 slots or more.
  2. IndexSearcher.search(query, n) first caps n at the number of documents (maxDoc), so passing Integer.MAX_VALUE is a common way to ask for every hit; a core test checks that it works.
  3. RescoreTopNQuery re-scores another query's matches and keeps the top n (it was added to re-rank a kNN query with full-precision vectors). LatLonPoint.nearest returns the n indexed points closest to a location.

The finding, step by step

#
  1. Index one document with one point, new LatLonPoint("loc", 0, 0), and ask for every hit: searcher.count(new RescoreTopNQuery(new MatchAllDocsQuery(), DoubleValuesSource.constant(1), Integer.MAX_VALUE)), or LatLonPoint.nearest(searcher, "loc", 0, 0, Integer.MAX_VALUE).
  2. You expect 1 hit, as searcher.search(new MatchAllDocsQuery(), Integer.MAX_VALUE) gives: IndexSearcher caps n at maxDoc, and nearest documents itself as equivalent to that search sorted by distance.
  3. You get IllegalArgumentException: maxSize must be >= 0 and < 2147483631; got: 2147483647 from both, with assertions on and off.
  4. Why: both build a priority queue of n + 1 slots first (RescoreTopNQuery.java:73, NearestNeighbor.java:254). Lucene's PriorityQueue allocates every slot up front and refuses 2,147,483,631 or more.
  5. Below that limit the calls work but pay for n: 400,002,296 bytes per call at n = 10^8 for 1 hit (the IndexSearcher control: 1,160 bytes), and OutOfMemoryError at n = 3*10^8 under a 1 GiB heap.

Who is affected

#

Code that passes Integer.MAX_VALUE ("all") or any n from 2,147,483,631 to either API: every call throws, on any index. Large n below that cost 4 bytes per slot per call (compressed references; 400 MB at 10^8) or run out of heap. Default settings; both APIs are opt-in and niche, and results are never wrong.

Mechanism, terms and numbers560 words

RescoreTopNQuery(query, source, n) and LatLonPoint.nearest(searcher, field, lat, lon, n) return the top n hits and accept any n >= 1. Before they collect a single hit, each builds a Lucene PriorityQueue of n + 1 slots (RescoreTopNQuery.java:73, NearestNeighbor.java:254), which allocates every slot up front and refuses 2,147,483,631 or more. So n = Integer.MAX_VALUE, the usual way to ask for every hit, throws IllegalArgumentException on an index with a single document, and a large n below the limit costs 4 bytes per slot per call (compressed object references, as in the tested 1 GiB heap; 400 MB at n = 10^8 for 1 hit) or ends in OutOfMemoryError. IndexSearcher.search has capped the same request at maxDoc since LUCENE-2119 (Michael McCandless, 2009), still asserted by TestIndexSearcher.testHugeN, and nearest documents that it is "functionally equivalent" to that search sorted by distance. The fix caps each queue at what the index can return: maxDoc for RescoreTopNQuery, the number of indexed points for nearest (not maxDoc, because nearest returns a multi-valued document once per point). Default settings, any index; nearest is affected from 10.0.0, RescoreTopNQuery from 10.3.0, through 10.6.0 and main. Results are never wrong; the failure is loud.

The bug

#
  1. RescoreTopNQuery documents "@param n the number of documents to find" and an IllegalArgumentException only "if n is less than 1" (RescoreTopNQuery.java:55-56), and the constructor checks only that (:58-61). The work happens in rewrite (:67-91), which IndexSearcher.rewrite calls: before any candidate is visited it builds HitQueue queue = new HitQueue(n, false); (:73), although the reader is in hand (:70). The class is @lucene.experimental (:34).
  2. LatLonPoint.nearest "Finds the n nearest indexed points", is "functionally equivalent to running MatchAllDocsQuery with a LatLonDocValuesField#newDistanceSort", and does not de-duplicate multi-valued fields, so a document can appear once per point (LatLonPoint.java:380-387). It rejects only n < 1 (:409-411), collects each leaf's PointValues (:418-430) and passes n on unchanged (:432-433). The package-private NearestNeighbor builds new NearestHitQueue(n) (NearestNeighbor.java:254).
  3. The queue. HitQueue and NearestHitQueue pass the size to PriorityQueue (HitQueue.java:62-64, NearestNeighbor.java:80-83). PriorityQueue throws for maxSize >= ArrayUtil.MAX_ARRAY_LENGTH ("Throw exception to prevent confusing OOME", PriorityQueue.java:121-125), otherwise allocates new Object[maxSize + 1] (:129, :134). MAX_ARRAY_LENGTH is Integer.MAX_VALUE minus the array header (ArrayUtil.java:33-34), 2,147,483,631 here.
  4. The sibling that caps. IndexSearcher.searchAfter caps numHits at Math.max(1, reader.maxDoc()) (IndexSearcher.java:588, :597), and the sorted variant does too (:721, :729). TestIndexSearcher.testHugeN ("should not throw exception", TestIndexSearcher.java:78-117) calls them with Integer.MAX_VALUE, with and without a Sort.

Exposure and likelihood212 words
  • Who is hit. Callers of new RescoreTopNQuery(..., n) or LatLonPoint.nearest(..., n) with Integer.MAX_VALUE or any n from 2,147,483,631 up: every call throws, on any index, even one with a single document. Also code that derives n from something large (an index-size estimate, a client's size parameter): about 400 MB per call at n = 10^8, and OutOfMemoryError above what the heap holds (the executed runs show the calling operation failing; effects on other work in the same JVM were not tested).
  • Default vs opt-in. No setting is needed: default codec, IndexWriterConfig and IndexSearcher. Both APIs are opt-in: RescoreTopNQuery (10.3.0 on, @lucene.experimental) was added to re-rank a kNN query with full-precision vectors (#14009); LatLonPoint.nearest (core since 10.0.0) is a geo top-n helper.
  • Scale. Only n matters, not the index size. Ordinary n (tens to thousands) costs kilobytes.
  • Who is not. IndexSearcher.search and searchAfter callers (capped), and any n the heap can hold, which returns correct results.
  • Severity. Loud: an exception for that call; no wrong results, nothing written to the index.
  • How likely. Rare: the throw shows on the first call, so "all" is met in testing; default-branch code search found no use of either API in Solr, Elasticsearch or OpenSearch code, and the documented searches found no prior public report.

Why it looks unintended

#
  • Neither API documents an upper bound on n; nearest calls itself "functionally equivalent" to a sorted MatchAllDocsQuery search, which accepts Integer.MAX_VALUE.
  • IndexSearcher has capped n at maxDoc since LUCENE-2119 (Michael McCandless; a 2.9.3 / 3.0.2 bug fix); testHugeN still asserts it.
  • Not a designed limit: nearest threw OutOfMemoryError at Integer.MAX_VALUE up to 10.4.0 and throws the queue's IllegalArgumentException from 10.5.0.
The full argument306 words
  • Contract. RescoreTopNQuery: "n the number of documents to find", IAE only "if n is less than 1" (RescoreTopNQuery.java:55-56). nearest: "Finds the n nearest indexed points" and "functionally equivalent to running MatchAllDocsQuery with a LatLonDocValuesField#newDistanceSort" (LatLonPoint.java:380-384). That sorted search accepts Integer.MAX_VALUE and returns every document (IndexSearcher.java:721-733; executed on the repro's document with a LatLonDocValuesField added: 1 hit). The javadoc already excludes multi-valued de-duplication, so for single-valued documents the two differ exactly where the queue is sized.
  • Tests. TestIndexSearcher.testHugeN asserts that the core top-n entry points accept Integer.MAX_VALUE; using it as the governing precedent was first pointed out by the cross-model reviewer (an independent reviewer from another model family, OpenAI GPT-5.6). Upstream TestRescoreTopNQuery uses small n only, and TestNearest never asks for more than the number of indexed points.
  • History. LUCENE-2119 (#3195, ae72952fa41, 2009, "behave better if you pass Integer.MAX_VALUE as nDcos [sic] to search methods"; CHANGES.txt lists it under the 2.9.3 / 3.0.2 bug fixes, first released June 2010) added the cap to IndexSearcher; Michael McCandless wrote there: "This trips users up fairly often because they assume our PQ doesn't statically pre-allocate (a reasonable assumption...)". The same pattern was fixed at other sites: LUCENE-9614 (#413, Julie Tibshirani: "bound k by total number of vectors to prevent oversizing data structures") and #13184 (bugmakerrrrrr: kNN exact search caps its HitQueue at the candidate count). The threads that added these two APIs (#14009, #14860, LUCENE-7069 / #8125, LUCENE-10266 / #897) contain no identified discussion of a large n.
  • Not a designed bound. For nearest, n = Integer.MAX_VALUE gave OutOfMemoryError: Requested array size exceeds VM limit up to 10.4.0 and gives the PriorityQueue IAE from 10.5.0, a side effect of #16154 ("Use Lucene's PriorityQueue in NearestNeighbor to replace poll/offer with updateTop"). The message names an internal maxSize, not n.
The devil's-advocate check280 words

The strongest case for "works as designed" (built by an intended-behaviour devil's advocate and the adjudication): the LUCENE-2119 issue body itself calls Integer.MAX_VALUE "a nonsense value to pass in, since our PQ impl allocates the array up front"; Uwe Schindler wrote on java-user in 2009 "If you want to have all results, you do something wrong", and Simon Willnauer defended fixed-size top-k queues there in 2011; pre-allocation is documented on PriorityQueue, HitQueue and the collector managers, which take numHits literally; nearest's javadoc says it throws IllegalArgumentException if n is "out-of-bounds"; SOLR-5661 added the PriorityQueue guard on purpose and Shalin Shekhar Mangar accepted an error for a huge rows value there; RescoreTopNQuery is @lucene.experimental.

Why it fails: the same LUCENE-2119 then fixed the case as a bug, and testHugeN still asserts it. These two are convenience entry points like IndexSearcher.search, not collectors whose caller sizes the queue, and their javadocs mention no pre-allocation (PriorityQueue is @lucene.internal). "Out-of-bounds" came with the n >= 1 check in 2016 (ad86feca097), and no upper bound was ever defined. The guard only turns n >= 2,147,483,631 into an IAE; the OutOfMemoryError range below it has no guard. Willnauer defended fixed-size top-k queues and did not address capacity beyond what the index can return; the cap keeps the queue fixed-size. Honest weak spot: a maintainer may accept the IAE at Integer.MAX_VALUE as documented; the per-call allocation and the OOM on a one-document index do not depend on that reading. Verdict: not intended, a low-severity robustness defect. The claim is that the queue is not bounded by what the index can return, not that memory must follow the number of results.

Suggested fix

#

Recommended A: cap RescoreTopNQuery at maxDoc and nearest at the indexed point count (validated)

Cap each queue at what the index can return: Math.min(n, Math.max(1, reader.maxDoc())) in RescoreTopNQuery.rewrite, and the summed PointValues.size() in LatLonPoint.nearest (not maxDoc: nearest returns a multi-valued document once per point). With it the repro and 2,839 tests of the core search and document packages pass.

// RescoreTopNQuery.rewrite (line 73)
HitQueue queue = new HitQueue(Math.min(n, Math.max(1, reader.maxDoc())), false);

// LatLonPoint.nearest: count the points in the existing leaf loop ...
long totalPoints = 0;
// ... totalPoints += points.size();   (next to totalHits += points.getDocCount();)
// ... and pass the capped n:
NearestNeighbor.nearest(latitude, longitude, readers, liveDocs, docBases,
    (int) Math.min(n, Math.max(1, totalPoints)));
All options and trade-offs5 options · 773 words

Option A was applied in a private scratch worktree of 645d4fe14a20 and run with gradle (worktree removed after the runs); the hunt's checks validated the same diff on a9779ef3c193. Options B to D were not built.

A: cap RescoreTopNQuery at maxDoc and nearest at the indexed point count (validated) (recommended)

#

Two small edits: RescoreTopNQuery.java:73, and LatLonPoint.java:418-433 (sum PointValues.size() in the loop that already visits every leaf, then pass the capped n). The maxDoc cap is the one Michael McCandless gave IndexSearcher on LUCENE-2119 (IndexSearcher.java:588).

// RescoreTopNQuery.rewrite (line 73)
HitQueue queue = new HitQueue(Math.min(n, Math.max(1, reader.maxDoc())), false);

// LatLonPoint.nearest: count the points in the existing leaf loop ...
long totalPoints = 0;
// ... totalPoints += points.size();   (next to totalHits += points.getDocCount();)
// ... and pass the capped n:
NearestNeighbor.nearest(latitude, longitude, readers, liveDocs, docBases,
    (int) Math.min(n, Math.max(1, totalPoints)));

Trade-offs

  • Results are unchanged for every n that works today; only the queue gets smaller. maxDoc is at most IndexWriter.MAX_DOCS (Integer.MAX_VALUE - 128), below the queue limit, so the capped size always fits.
  • nearest is capped at the point count, not maxDoc, because it returns a multi-valued document once per point: on one document with two points, nearest(..., 100) returns 2 hits (the finder's SMT obligation and a harness mutant found the same; the cross-model reviewers agreed). Points of deleted documents are counted, so it is an upper bound. NearestVisitor uses the same n to tell when the queue is full (NearestNeighbor.java:181); with the cap that happens only after every point was collected, so results do not change.
  • Still loose for RescoreTopNQuery when the inner query matches few of many documents (see C).
  • Residual at extreme scale, not part of this bug: n = Integer.MAX_VALUE over 2,147,483,631 or more points would still hit the guard; and under the draft long-doc-id change (#16847) maxDoc could exceed the array limit, so the cap would also need a clamp to ArrayUtil.MAX_ARRAY_LENGTH - 1.

  • The hunt's checks of the same diff: the finder's 4 tests pass (-ea, -da), upstream TestRescoreTopNQuery, TestRescoreTopNQueryPrefetch and TestNearest run 10 tests with 0 failures, an independent reproducer's 6 tests pass, and the bounded-exhaustive harness gives 3,081 checks with 0 failures.

B: cap inside NearestNeighbor.nearest (not built)

#

Sum size() over the readers list that NearestNeighbor.nearest receives and cap there, next to the queue.

Trade-offs

Same effect as A for nearest: the class is package-private and LatLonPoint.nearest is its only caller.

C: size RescoreTopNQuery's queue by the inner query's real candidate count (not built)

#

Count or buffer the inner query's matches first and size the queue by that count.

Trade-offs

Tighter than A when a small candidate set sits in a big index (for example a kNN query with k = 100 over 10^7 documents still gets a 10^7-slot queue for Integer.MAX_VALUE under A), but needs a counting pass or a buffer; more code than the bug needs.

D: grow the queue lazily up to n (not built)

#

Start small and grow only as hits arrive, instead of allocating n + 1 slots up front.

Trade-offs

Would help every top-n path, but core PriorityQueue has a fixed capacity, so it needs a different structure on a hot path; larger than the bug needs.

Not recommended: cap nearest at maxDoc, or reject large n

#

A maxDoc cap for nearest drops hits for multi-valued fields. A documented upper bound on n turns the "all" idiom that IndexSearcher.search supports into an error, and helps the OutOfMemoryError range only if the bound is low.

Trade-offs

Both change results or the contract instead of only the queue size.

How it was found

#

AI tools' boundary probes passed Integer.MAX_VALUE to many top-n APIs: these two threw, while IndexSearcher.search returned every hit. A later hunt built a differential harness over 39 small index layouts and SMT obligations, which added the out-of-memory range and showed that nearest must be capped at the point count. One minimal test reproduces it.

The method in full162 words

Method: semi-formal (the finder's label): executed boundary probes gave the first signal, then a bounded-exhaustive differential harness and SMT obligations on the stock jars.

  • An accepted-parameter boundary probe (2026-10-26) saw both IllegalArgumentExceptions at n = Integer.MAX_VALUE and noted them next to a kNN row, not filed separately. A planning probe for top-n APIs reproduced both on the stock main jars with controls passing.
  • The hunting AI tool wrote a differential harness (39 layouts of 1-3 segments, 1-2 points per document, 11 values of n; oracles: the API's own full result, the exact number of candidates or points, and an allocation bound) and 11 SMT bit-vector obligations. Every layout failed at n = 2,147,483,630 and 2,147,483,647 for both APIs; the obligations proved the maxDoc cap (RescoreTopNQuery) and the point-count cap (nearest) sound and gave the counterexample against a maxDoc cap for nearest, which a harness mutant confirmed.
  • It reduced the case to public-API JUnits with controls, and later to the one-class repro.

LFV-995, snapshot of 2026-11-07

Registry title
RescoreTopNQuery and LatLonPoint.nearest size their priority queue from the caller's n, not from what the index can return, so n = Integer.MAX_VALUE ('all') throws IllegalArgumentException and a large n throws OutOfMemoryError, even on an index of a few documents
Area
search / top-n rescoring and geo nearest search (queue sizing: RescoreTopNQuery.rewrite; LatLonPoint.nearest -> NearestNeighbor)
Priority
Low, rank 646: RescoreTopNQuery and LatLonPoint.nearest throw IAE or OOM for a huge n but return correct results otherwise, core code with niche APIs affected only since 10.0 and 10.3, so it closes the MAX_VALUE facet group after LFV-983 and above LFV-265.
Impact class
crash
Impact note
Applications on 10.0.0 (LatLonPoint.nearest) or 10.3.0 (RescoreTopNQuery) through 10.6.0 and main that pass n = Integer.MAX_VALUE to mean 'all', or forward a large caller-chosen size, get an IllegalArgumentException (n >= 2147483631) or an OutOfMemoryError (n = 3*10^8 under a 1 GB heap) from inside the search instead of every candidate, on any index (even a few documents) and with default settings; an n far above maxDoc still allocates n queue slots per call (38 MiB at n = 10^7 in the finder's harness), results are never wrong, and both APIs are niche (RescoreTopNQuery is @lucene.experimental).
Summary
You search with new RescoreTopNQuery(query, source, Integer.MAX_VALUE), or call LatLonPoint.nearest(searcher, field, lat, lon, Integer.MAX_VALUE), to get every candidate, and expect them all back, as n = 1000 (or 100) gives on a 9-document index and as nearest's documented equivalent, a MatchAllDocsQuery search sorted by distance, gives for Integer.MAX_VALUE. Instead both build a priority queue of n + 1 slots before looking at the index: Integer.MAX_VALUE throws IllegalArgumentException('maxSize must be >= 0 and < 2147483631') from inside the search, and a large n below that throws OutOfMemoryError (n = 3*10^8 under a 1 GB heap). IndexSearcher.search has capped the same request at maxDoc since LUCENE-2119, as Michael McCandless proposed there; the analogous fix caps RescoreTopNQuery's queue at maxDoc and nearest's at the number of indexed points (not maxDoc, because nearest returns a multi-valued document once per point).
