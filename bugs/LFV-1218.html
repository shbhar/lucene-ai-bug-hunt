Cloning the merged view's TermVectorsReader throws NullPointerException when a merged segment has no term vectors

A custom OneMerge#reorder receives a merged view of the segments being merged; cloning that view's term-vectors reader throws NullPointerException as soon as one of those segments has no term vectors. The class handles that missing reader everywhere except in clone(); every release since 9.9.0 has it.

The finding in 30 seconds

#

The merged view keeps one term-vectors sub-reader per segment and stores null for a segment without term vectors. Four of its methods skip that null; clone() calls clone() on every entry and throws.

Background: the merged view a reorder hook sees

#
  1. A merge policy can renumber the documents of a merge (as BPReorderingMergePolicy does) by overriding OneMerge#reorder. When index sorting is off and the merge has two or more segments, IndexWriter calls it with one merged CodecReader view over all of them (for a single segment it passes the plain reader).
  2. The view reads each segment through that segment's own readers. A segment in which no document stored term vectors has no term-vectors reader at all: null.

The finding, step by step

#
  1. Index 2 one-document segments: doc 0 has field f = "a" with term vectors stored; doc 1 is an empty document, so its segment has no term vectors.
  2. Merge them (addIndexes or forceMerge(1)) with a merge policy whose OneMerge#reorder(view, ...) calls view.getTermVectorsReader().clone(), for example to give each worker its own reader.
  3. You expect a clone that returns doc 0's term vectors and null for doc 1, as the uncloned reader does.
  4. Instead clone() throws NullPointerException at SlowCompositeCodecReaderWrapper.java:233, with assertions on and off. On forceMerge the IndexWriter then closes itself, drops uncommitted documents, and fails the same way after a reopen.
  5. Why: the view keeps one sub-reader per segment and stores null for segment 1. get, prefetch, checkIntegrity and close skip the null; clone() calls clone() on every entry.

Who is affected

#

Only applications with their own merge code: a custom OneMerge#reorder that clones the view's term-vectors reader, or a custom codec that clones its merge inputs during a reordering merge. Nothing in Lucene does either. The data is ordinary (any segment without term vectors); on the merge path the writer closes and uncommitted changes are lost.

Mechanism, terms and numbers357 words

When index sorting is off, IndexWriter passes every merge of two or more segments, including an addIndexes(CodecReader...) merge of two or more readers, to OneMerge#reorder as one merged CodecReader view, SlowCompositeCodecReaderWrapper (IndexWriter.java:3561-3562, :5556-5557); not when the segments have blocks but the index has no parent field (:3551-3556, :5547-5552). The view's getTermVectorsReader() keeps one sub-reader per segment, and the sub-reader is null for a segment without term vectors (SlowCompositeCodecReaderWrapper.java:206-213, SegmentReader.java:246-253). get, prefetch, checkIntegrity and close handle that null; clone() maps TermVectorsReader::clone over the array and throws NullPointerException at :233.

Nothing in Lucene clones this reader (merges use getMergeInstance(), MergeState.java:150-152), so only application code reaches it: a custom OneMerge#reorder, or a custom codec that clones MergeState.termVectorsReaders during a reordering merge. On the merge path IndexWriter treats the exception as a tragic event (IndexWriter.java:5111). The fix is a one-line null guard in clone().

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/index/)

#
  1. The view. SlowCompositeCodecReaderWrapper.wrap(readers) returns the single reader itself for one input and a new wrapper for two or more (SlowCompositeCodecReaderWrapper.java:48-57); the class is "primarily targeted at merging, not searching" (:43-45).
  2. A null sub-reader on purpose. getTermVectorsReader() maps CodecReader::getTermVectorsReader over the inputs (:206-213); SegmentReader.getTermVectorsReader() returns null when the segment has no term vectors, else a fresh clone (SegmentReader.java:246-253).
  3. Four methods handle it. close uses IOUtils.close, which skips null (:225-228); checkIntegrity (:237-244), prefetch (:246-253) and get (:255-264) test the entry first.
  4. clone() does not (the fix site). Arrays.stream(readers).map(TermVectorsReader::clone) (:230-235) dereferences the null entry at :233. SortingCodecReader's term-vectors clone() delegates (SortingCodecReader.java:831-834), so a sorting view over the merged view fails too.

Also executed: the reversed order (no term vectors first) and SortingCodecReader.wrap(view, ...) fail the same way; two segments that both have term vectors clone fine; a merge of segments of which none has term vectors also fails, because the view then returns a non-null reader whose entries are all null, so a caller's own null check does not help.

Exposure and likelihood272 words
  • Who. A OneMerge#reorder override (@lucene.experimental, MergePolicy.java:311-328) that clones view.getTermVectorsReader(), for example one reader per task of the executor the hook receives "to parallelize the reordering logic" (:321-322). Or a custom codec whose TermVectorsWriter.merge clones the public MergeState.termVectorsReaders entries during a merge that reorders (a reorder that returns a non-null DocMap, so the merge reads through SortingCodecReader.wrap(view, ...), IndexWriter.java:5574-5575); this trigger needs no @lucene.internal getter and was executed on main.
  • Default vs opt-in. Opt-in: custom code is required. The data shape is common: any merge of two or more segments where at least one has no term vectors, including an index with no term vectors at all.
  • Effect. A NullPointerException. In addIndexes(CodecReader...) it reaches the caller and the writer stays open: with the repro's SerialMergeScheduler it propagates straight out of mergeScheduler.merge (IndexWriter.java:3312); with a concurrent scheduler it is recorded and rethrown at :3380-3382; only an Error is tragic there (:3390-3392). In a merge, IndexWriter.merge sends any non-abort Throwable to tragicEvent(t, "merge") (:5064-5112, :5111). An impact probe on forceMerge(1) showed: the writer is closed, its tragic exception is the NPE, an uncommitted third document is gone after reopening (2 docs left), and a reopened writer fails and closes the same way. That close is IndexWriter's generic handling of an exception that escapes the application's own reorder or codec code; stock merges without such code do not fail. Committed data stays intact; no wrong results.
  • Scale. Two one-document segments.
  • Workaround. Call getTermVectorsReader() (or termVectors()) again instead of clone(): each call builds fresh per-segment readers.

Why it looks unintended

#
  • TermVectorsReader.clone() promises "a clone that one caller at a time may use to read term vectors", with no precondition.
  • The class stores the null itself and skips it in get, prefetch, checkIntegrity and close; clone(), from the same commit, is the outlier.
  • For unsupported operations this class throws UnsupportedOperationException; upstream fixed the same pattern for points in this wrapper (#12859).
The full argument185 words
  • Contract. TermVectorsReader.clone(): "Create a clone that one caller at a time may use to read term vectors" (TermVectorsReader.java:45-47); no precondition, no exception documented.
  • The class contradicts itself. The null entry is a state the view creates (SlowCompositeCodecReaderWrapper.java:206-213) and handles in four methods (:225-264). Unsupported operations in this class throw UnsupportedOperationException (:366, :371, :491).
  • History. getTermVectorsReader(), clone(), the null-checked get and checkIntegrity and the null-skipping close all arrived in f7cab164501 (#12622, 2023-11-23); prefetch came later with its own guard (#13758, 10.0.0). Nothing has touched clone() since. No javadoc, CHANGES or MIGRATE entry says clone() is unsupported on this view.
  • Tests and precedent. Upstream TestSortingCodecReader clones the term-vectors reader of a wrapper view (SortingCodecReader over SlowCodecReaderWrapper) and asserts on the clone (TestSortingCodecReader.java:229-237), so cloning a merge-oriented wrapper's term-vectors reader is exercised; that view wraps a single segment with no null sub-reader, so the test does not cover this case. Maintainers fixed the same pattern elsewhere: #12858/#12859 (null PointValues in this wrapper, 9.9.0) and #14123/#14125 (null vectors reader in SortingCodecReader).
The devil's-advocate check122 words

The strongest case for "not a bug", made by the cross-model reviewer (OpenAI GPT-5.6), which reproduced the NPE and agreed on the root cause: the trigger calls CodecReader#getTermVectorsReader(), which is @lucene.internal (CodecReader.java:44-50), inside an @lucene.experimental hook, and normal merges call getMergeInstance(), not clone().

Why it does not settle it: the codec trigger uses no internal getter, only the codec API and the public MergeState.termVectorsReaders; @lucene.internal and @lucene.experimental speak to API stability, not to a documented method throwing NPE on a state the class creates itself; and a caller that checks for null first still gets the NPE. A maintainer may still call it out of scope or too minor, a fair outcome for a Low bug.

Suggested fix

#

Recommended Null guard in clone() (fix A)

Map a null sub-reader to null in clone(): .map(r -> r == null ? null : r.clone()). With it the repro passes with assertions on and off, and 61 tests of the closest suites pass.

          Arrays.stream(readers)
              .map(r -> r == null ? null : r.clone())
              .toArray(TermVectorsReader[]::new),
All options and trade-offs2 options · 285 words

Fix A was built and checked through gradle on 5adff78bb168; B was not run. The same missing-sub-reader pattern in this wrapper's vector copy() is registered as LFV-269 (a different method, trigger and version range); the two are related hardening in the same class and could be considered together.

Null guard in clone() (fix A) (validated by the checks) (recommended)

#

In SlowCompositeTermVectorsReaderWrapper.clone() (SlowCompositeCodecReaderWrapper.java:230-235), clone only the non-null sub-readers and keep null for the others, as get, prefetch, checkIntegrity and close already assume.

          Arrays.stream(readers)
              .map(r -> r == null ? null : r.clone())
              .toArray(TermVectorsReader[]::new),

Trade-offs

None found: the clone then returns null for documents of a segment without term vectors, exactly like the original reader. The change is confined to clone().

Fill missing sub-readers with an empty reader (not run)

#

When the view is built, put an empty TermVectorsReader (whose get returns null) where a segment has none.

Trade-offs

Removes the null checks everywhere, but is a larger change to a class that already handles null consistently in four methods. Not recommended.

How it was found

#

A proof-obligation audit of SlowCompositeCodecReaderWrapper's term-vectors reader against the TermVectorsReader.clone contract: every method must cope with the null sub-reader the view stores for a segment without term vectors. clone() does not; a public-API JUnit test then witnessed the exception.

The method in full98 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder listed the states the view can be in (a null entry for each segment without term vectors) and checked each method of the term-vectors wrapper against them; only clone() fails the obligation.
  • The finder then wrote a public-API JUnit test and the one-line null guard that makes it pass.
  • An independent reproducer, an executed cross-model review and a devil's-advocate verifier reproduced it with their own tests, and an adjudication re-ran the reproducer's test with a fresh seed ("Prior reports, history and checks").
