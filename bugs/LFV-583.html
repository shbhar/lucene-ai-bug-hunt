The bug in 30 seconds

#

A stop filter removes words but keeps their positions as holes, so one of the best is one, two holes, best. At the end of the input those holes are reported in the final position increment. SuggestStopFilter drops them there, and the suggester's query then has too few holes.

  1. You build an AnalyzingSuggester over two entries, one direction (weight 10) and one of the best (weight 5). The index analyzer removes the stop words to a the of with StopFilter, the query analyzer with SuggestStopFilter, as the class javadoc recommends.
  2. The user types one of the with a space after the, so both stop words are finished. Both filters keep only one, and each removed word should leave a hole: StopFilter reports 2 removed positions at the end of the input (final position increment 2). SuggestStopFilter reports 0.
  3. You expect [one of the best], which the same suggester returns with a StopFilter query analyzer: the query means one, then two skipped words, then whatever comes next.
  4. Instead you get [one direction, one of the best], with no error. With 0 removed positions the suggester sees only one and a space, so every entry that starts with one matches. go to a the reports 0 instead of 3 the same way.
  5. With one finished stop word (one the ) the AnalyzingSuggester adds one hole by itself, because the final offset lies past the end of the last kept word (finalOffsetGapAsHole), which happens to be right; the document suggester (PrefixCompletionQuery) does not, so there one the already matches like one.

Who is affected

#

Applications with SuggestStopFilter in a suggester's query analyzer (directly or as the suggestStop factory), as its javadoc recommends. Lookups ending in finished stop words can get extra suggestions: with two or more such words in AnalyzingSuggester and FuzzySuggester, with one in the document suggester and FreeTextSuggester. No error; it clears once a non-stop word is typed.

Mechanism, terms and numbers905 words

SuggestStopFilter is the query-side stop filter for autocomplete. Its javadoc defines it as "Like StopFilter except it will not remove the last token if that token was not followed by some token separator" and recommends StopFilter in the index analyzer with this class in the query analyzer of the analyzing suggesters. When the typed text ends in stop words followed by a separator, such as one of the , it removes them like StopFilter, but its end() reports the input's own final position increment, 0, instead of adding the positions it removed; StopFilter reports 2. Terms, position increments, offsets and the final offset are identical. The suggesters turn that final increment into trailing holes of the lookup automaton, so with too few holes the lookup matches more entries: AnalyzingSuggester.lookup("one of the ") returns [one direction, one of the best] where a StopFilter query analyzer returns [one of the best]. AnalyzingSuggester and FuzzySuggester show it with two or more removed trailing stop words, the document suggester and FreeTextSuggester with one. In a bounded probe the result was always the result for the same text without its trailing stop words; in exactFirst mode (AnalyzingSuggester, FuzzySuggester) one entry whose text equals the typed text is dropped (with assertions on, the lookup throws an AssertionError). The end value has been wrong since 4.5.0 (LUCENE-3849); it has changed FreeTextSuggester results since that suggester's first release, 4.6.0, and the other suggesters' since 6.5.0 (LUCENE-7619). With a small fix (+6/-2 lines in SuggestStopFilter) the whole suggest test task has 0 failures.

Terms

#
  • Position increment: each token says how many positions it moved on from the previous one. A removed stop word leaves a hole: in go to school, school has increment 2.
  • Final position increment: after the last token, TokenStream#end() reports the positions skipped at the end of the input: "any skipped positions (such as those removed by a stopfilter) can be applied to the position increment" (TokenStream.java:152-154). StopFilter does this (FilteringTokenFilter.java:72-75): go to a the ends with final increment 3.
  • SuggestStopFilter: "Like StopFilter except it will not remove the last token if that token was not followed by some token separator" (SuggestStopFilter.java:29-37). It keeps an unfinished last word (find the), so that a query a can still suggest apple (LUCENE-5165 CHANGES entry).
  • Lookup automaton: AnalyzingSuggester turns the analyzed query into an automaton and matches it as a prefix of the analyzed entries. Each hole becomes an extra separator (AnalyzingSuggester.java:268-307); trailing holes come from the final position increment (TokenStreamToAutomaton.java:212-241).

  2. The final offset is past the end of the (10), so the was finished and is removed. The filter returns false without adding skippedPositions (1) or the's own increment (1). end() restores the captured state: final increment 0. StopFilter gives 2.

  4. The document suggester builds its automaton without that setting (ConcatenateGraphFilter.java:233-244), so there one removed word already matters.

Exposure and likelihood546 words
  • Who. Users of SuggestStopFilter in the query analyzer of AnalyzingSuggester, FuzzySuggester, the document suggester (PrefixCompletionQuery, FuzzyCompletionQuery) or FreeTextSuggester, directly or through SuggestStopFilterFactory (SPI name suggestStop). It is opt-in: no Lucene analyzer uses the class by default. The suggester defaults (exactFirst, preserved separators and position increments) are the configuration shown. preservePositionIncrements=false does not hide it but reverses it: the buggy lookup then misses single-token entries that a StopFilter query analyzer matches (AnalyzingSuggester with entries one direction, one of the best, oneplus: [one direction, one of the best] instead of [one direction, one of the best, oneplus]). AnalyzingInfixSuggester is not affected.
  • Trigger. Ordinary typing: text that ends in removed stop words followed by a space, such as one of the . AnalyzingSuggester and FuzzySuggester need two or more such words (with one, their own trailing-space hole happens to be right); the document suggester needs one (one the matches like one), and so does FreeTextSuggester, which reads the end increment itself (FreeTextSuggester.java:474-541): one of returns the next-word predictions after one where a StopFilter query analyzer returns none.
  • Effect. Extra suggestions. In a bounded probe (6 words, 3 of them stop words, texts of 1 to 4 words: 1,434 entries, 3,108 queries, 777 ending in removed stop words) the result with the bug always equals the result for the same text without its trailing stop words, 0 mismatches. Not every such query changes: 270 of the 777 differ from the fixed filter in AnalyzingSuggester and in FuzzySuggester, 528 (prefix) and 513 (fuzzy) in the document suggester; in FreeTextSuggester 657 of 2,868 queries differ. Contexts and document filters still apply to every hit.
  • One entry can be lost. In exactFirst mode, an entry whose text equals the typed text, trailing space included (entry one of the , query one of the ), is dropped with assertions off: the probe's AnalyzingSuggester returns [one of the best, one direction, one the end], where StopFilter and the fix return [one of the , one of the best, one the end]. With assertions on the lookup throws an AssertionError at AnalyzingSuggester.java:808. FuzzySuggester, which inherits that code, does the same.
  • Index time (not the documented setup). In an index analyzer the lost increment moves the next value of a multi-valued field one position earlier: foo the | bar with gap 0 puts bar at position 1 instead of 2, so the phrase "foo bar" matches.
  • How likely. Plausible: in that setup such a lookup can be broadened, and the extra entries are the suggestions for the shorter text; they go away once a word that is not a stop word is typed. No report was found in the searches performed. No scale is needed.
  • Workaround. None that keeps the class's purpose: preservePositionIncrements=false does not help (above) and ignores every hole; a StopFilter query analyzer is right for one of the but removes an unfinished last word (find the), the case SuggestStopFilter exists for. A filter after it cannot repair the value (the count of removed trailing words stays inside incrementToken()), and the class is final (SuggestStopFilter.java:38); an application would need its own copy of the class with the fix.

Why it is a bug, not intended

#
  • Documented as StopFilter with one exception, an unfinished last word; StopFilter reports the removed trailing positions in end(), and a test asserts it.
  • LUCENE-3849 made end() carry trailing holes; its commit added the skipped positions there for StopFilter and for the plain TokenFilter MockTokenFilter, not here.
  • No test, CHANGES entry or recorded decision was found for the current value.
The full argument241 words
  • One documented exception. "Like StopFilter except it will not remove the last token if that token was not followed by some token separator" (SuggestStopFilter.java:29-34). The LUCENE-5165 CHANGES entry says the same: a stop word "at the very end of the lookup query, and without any trailing token characters, will be preserved" (CHANGES.txt:13275-13280).
  • StopFilter reports the positions, and a test pins it. FilteringTokenFilter.end() adds skippedPositions (:72-75); TestStopFilter.testEndStopword asserts final increment 1 for test of (TestStopFilter.java:172-189).
  • end() is the channel. TokenStream#end: skipped positions "can be applied to the position increment" (TokenStream.java:152-154). LUCENE-3849: "TokenStreams now set the position increment in end(), so we can handle trailing holes" (CHANGES.txt:13337-13340). Its issue text (#4922) says "subclasses of FilteringTokenFilter (e.g. stopfilter) should do: super.end(); posIncAtt += skippedPositions;"; this class is a plain TokenFilter, but the commit made the same change in the test framework's MockTokenFilter, also a plain TokenFilter. Before the commit the committer wrote "I agree this bug is bad. It can also affects suggesters".
  • The class already does it mid-stream (SuggestStopFilter.java:92, :114; testMultipleStopWords asserts +4), and the suggesters read the end increment: FreeTextSuggester since its first release, 4.6.0 (FreeTextSuggester.java:474-541), the analyzing suggesters since LUCENE-7619 (6.5.0).
  • No test covers it. testEndIsStopWord (go to ) and testMultipleStopWordsEnd2 (go to a the ) use the assertTokenStreamContents overload that passes finalPosInc = null (TestSuggestStopFilter.java:47-64, 123-140).
The devil's-advocate check256 words

Strongest case (an intended-behaviour checker and a reviewer from another model family, OpenAI GPT-5.6; rated moderate): TokenStream#end says skipped positions "can" be applied, not "must". The author of the class rewrote SuggestStopFilter.end() in the LUCENE-3849 commit itself, six days after adding the class, and did not add them. The upstream trailing-stop tests leave the final increment unchecked, and TestAnalyzingSuggester strips trailing holes from its oracle because "TokenStream.end() does not tell us any trailing holes, yet ... there is an issue open for this" (TestAnalyzingSuggester.java:900-902).

Why it fails: the class's only documented difference from StopFilter does not apply to text that ends in a separator. LUCENE-3849's issue text asks FilteringTokenFilter subclasses such as StopFilter to add skippedPositions in end(), and the same commit did so for FilteringTokenFilter and for the test framework's MockTokenFilter, a plain TokenFilter like this class. When it landed, no suggester read the end increment yet: FreeTextSuggester, which does, was added six weeks later (4.6.0), and TokenStreamToAutomaton looked only at the final offset until LUCENE-7619 (6.5.0). The indexer reads it too, but an index analyzer is not where the class is documented to go. No record of a decision about the value was found. The TestAnalyzingSuggester comment dates from 2012, before LUCENE-3849, and concerns that test's own filter: it names a known gap, not a design. When filing, base the expected value on the documented StopFilter equivalence and LUCENE-3849, not on an explicit "must", and present the change as a behaviour-changing bug fix: suggestion lists for such text change.

Suggested fix

#

Recommended A. Add the removed positions before capturing the end state (recommended)

On the branch that removes a finished last stop word, add skippedPositions + posInc to the final position increment before capturing the end state (+6/-2 in SuggestStopFilter.java). With two finalPosInc asserts added to TestSuggestStopFilter, the whole :lucene:suggest test task (240 tests, 7 upstream skips) has 0 failures, the repro tests included, with assertions on and off.

Trade-offs

  • Smallest change: the stored end state itself is right, so any consumer that calls end() sees StopFilter's value.
  • Changes suggestions only for text that ends in removed stop words and a separator; those now match StopFilter. FreeTextSuggester results for such text change the same way (one of gives [] instead of the bigrams after one).
  • With preservePositionIncrements=false the change goes the other way: such a lookup then matches like a StopFilter query analyzer, which also includes single-token entries that start with the kept word (oneplus for one of the ).
  • For very long runs of trailing stop words the lookup automaton grows like StopFilter's (40,004 states for 20,000 stop words instead of 6; single runs, not a benchmark); bounding query length is the application's job (SECURITY.md line 38).

Downstream note

#

By code reading only, Elasticsearch and OpenSearch build a SuggestStopFilter for their stop token filter with remove_trailing: false, and Solr documents SuggestStopFilterFactory for suggester query analyzers; nothing was run downstream and no downstream report was found.

How it was found

#

Semi-formal: a bounded-exhaustive sweep compared the end() positions and offsets of 434 selected token-filter configurations with a reference built from their input plus the positions they removed (6.78 million analyses), and flagged SuggestStopFilter. A differential test against StopFilter over 11,718 inputs isolated the final position increment; it was reduced to a public-API JUnit.

The method in full190 words
  • Sweep (bounded-exhaustive translation validation of the stock jars). 434 selected component configurations (the token filters registered through SPI with their defaults, except 27 that need parameters or resources, plus parameter grids for the buffering and token-removing filters), behind 3 upstream chains, on 5,208 texts each (6.78 million analyses). The reference for each run is the end() state of the same chain without the component, plus the positions the component removed; it compares terms, position increments and lengths, offsets, and the final position increment and offset, not every attribute. Every suggestStop configuration with a matching stop word list showed final-position mismatches.
  • Differential against the documented equivalence. Every sequence of 0-5 words over go to a the school with 3 endings (11,718 inputs) through StopFilter and SuggestStopFilter: 4,686 mismatches, all of one shape (only the final position increment differs; terms, position increments, offsets and the final offset equal; other attributes not compared); 0 with the fix (non-vacuous).
  • Reduction. Code reading found the separator branch in incrementToken; the finder wrote the public-API JUnit with the AnalyzingSuggester lookup and ran it on main, 10.5.2 and 9.12.3, and a main() probe on 8.11.4.

Bug record

LFV-583, snapshot of 2026-10-29

Registry title
SuggestStopFilter.end() leaves out the positions of the stop words it removes at the end of the input (StopFilter counts them), so a suggester with SuggestStopFilter in its query analyzer returns extra suggestions for text that ends in removed stop words and a space (two or more stop words for AnalyzingSuggester and FuzzySuggester, one for the document suggester; wrong end() since 4.5.0, visible in suggesters since 6.5.0)
Area
suggest / SuggestStopFilter (query analysis of the analyzing and document suggesters)
Priority
Low, rank 365: SuggestStopFilter's wrong end() broadens as-you-type suggestions in its recommended setup on everyday input, but it affects suggestion quality only and clears at the next typed word, so it joins the suggestion-quality rows right after LFV-240.
Impact class
silent wrong results
Impact note
Applications that put SuggestStopFilter in a suggester's query analyzer (directly, through the suggestStop factory, or, by code reading, through a downstream stop filter with remove_trailing=false), which is the setup its javadoc recommends next to a StopFilter index analyzer, get a broader suggestion list whenever the typed text ends in removed stop words followed by a separator: two or more stop words for AnalyzingSuggester and FuzzySuggester (one is hidden by finalOffsetGapAsHole), one for the document suggester (PrefixCompletionQuery and FuzzyCompletionQuery); the extra entries are exactly the suggestions for the text without those stop words, except that in exactFirst mode an entry whose text equals the typed text, trailing space included, is dropped (or, with -ea, the lookup throws an AssertionError); AnalyzingInfixSuggester is not affected, preservePositionIncrements=false masks it, and no scale is needed. Low severity: suggestion quality only.
Summary
You build an AnalyzingSuggester over 'one direction' and 'one of the best' with a StopFilter index analyzer and a SuggestStopFilter query analyzer, as the SuggestStopFilter javadoc recommends, and look up 'one of the ' (the user has typed 'the' and a space). You expect what a StopFilter query analyzer gives, [one of the best], because the class is documented as 'Like StopFilter' except that it keeps an unterminated last stop word, and StopFilter adds the positions of removed trailing stop words to the final position increment in end(). Instead SuggestStopFilter.end() reports the input's own final increment (0 instead of 2), so the lookup automaton has too few trailing holes and the lookup also returns 'one direction'; the tokens and the final offset are correct.
Introduced
e005a580e9f856e1cdebc3bf3230768911c7105c (branch_4x, svn r1515909, LUCENE-3849 'position increments should be implemented by TokenStream.end()', apache/lucene#4922, committed by mikemccand; the commit that shipped in 4.5.0) and its trunk twin 2a5421ca685b7341bbead24975cd218cbcaf34f7 (svn r1515887, first released in 6.0.0; git blame on main credits it with the SuggestStopFilter lines). Both capture endState right after input.end() and restore it in end() without adding skippedPositions or the removed last stop word's increment, while the same commit made FilteringTokenFilter.end() (StopFilter) add skippedPositions [exec: 4.4.0 jars plus SuggestStopFilter at d5e99b1b959 (just before) agree with StopFilter; 4.4.0 jars plus the four files at e005a580e9f differ like 4.5.0]. The suggester-visible symptom starts with LUCENE-7619 (branch_6x 4e4ec082caa, trunk 637915b890d), which made TokenStreamToAutomaton turn the end() position increment into trailing holes [exec: 6.4.2 gives the same suggestions as a StopFilter query analyzer, 6.5.0 differs] (2013-08-20 (wrong end() increment, LUCENE-3849); 2017-01-17 (visible in suggesters, LUCENE-7619))
