LatLonPoint.newDistanceFeatureQuery can skip a closer document under top-k pruning: its radius search stops up to 1 m short and the box adds only 7 cm

The finding in 30 seconds

#

Distance-feature scoring ranks documents by how close their point is to an origin. Under top-k pruning the scorer may skip documents that cannot make the top k, and it does that with a box around the origin.

Background: how distance-feature pruning works

#
  1. LatLonPoint.newDistanceFeatureQuery(field, weight, lat, lon, pivot) scores each document weight * pivot / (pivot + distance): closer means higher, and a document at the pivot distance scores weight / 2.
  2. In a top-k search, once 1,000 hits are counted, the collector tells the scorer the lowest score that can still enter the top k (setMinCompetitiveScore). The scorer may then skip documents that score below it, and only those.
  3. This scorer converts the score into a radius by binary search, and from then on visits only the documents inside a lat/lon box around the circle of that radius (Rectangle.fromPointDistance, which adds a 7 cm margin).

The finding, step by step

#
  1. You index 2,002 points around the origin (0, 0): doc 0 is 999.999 m due north, 2,000 fillers are thousands of km away, and doc 2001 is 999.803 m due north. You run searcher.search(LatLonPoint.newDistanceFeatureQuery("loc", 1, 0, 0, 1000), 1), which scores 1000 / (1000 + distance).
  2. You expect doc 2001, the closest: it scores 0.5000492, doc 0 scores 0.50000024.
  3. You get doc 0. After 1,000 counted hits the collector tells the scorer it may skip documents scoring below 0.5000003; doc 2001 scores above that and is skipped anyway.
  4. Why: the scorer binary-searches for the largest distance that still scores 0.5000003, stops once the interval [999.729 m, 1000.325 m] is under 1 m wide and keeps the lower end; the true cut-off is 999.999 m. It then visits only a box of 999.729 m + 7 cm = 999.799 m, and doc 2001 is 4.5 mm outside it.
  5. The effect is small but silent: the skipped document lies less than 1 m beyond the box edge (under about 0.53 m on a scorer's first threshold update), near due north, south, east or west of the origin, where the box touches the circle. Every checked release since 8.0.0 has it.

Who is affected

#

Top-k searches ranked by LatLonPoint.newDistanceFeatureQuery alone (top level, boosted, or next to filters), with default settings, since 8.0.0. Not when it is a SHOULD boost on another scoring query. The skipped document lies less than 1 m beyond the box edge, near a cardinal bearing; on uniform random data 0 of 2,300 single-segment and 3 of 1,300 ten-segment queries.

Mechanism, terms and numbers1,013 words

When a top-k search scored by LatLonPoint.newDistanceFeatureQuery has counted enough hits (1,000 for IndexSearcher#search(query, k)), the collector passes the lowest score that can still enter the top k to the query's scorer, which may then skip only documents scoring below it. The scorer turns that score into a radius with a binary search (computeMaxDistance) that stops once the interval is at most 1 m wide and returns its lower end, although distances up to the upper end may still compete. It then visits only the documents inside a lat/lon box built from that radius with Rectangle.fromPointDistance, which pads it by 7 cm. A competitive document between the box edge and the true cut-off is never visited, and a farther one is returned in its place. Because the box circumscribes the circle, this only happens near due north, south, east or west of the origin, and the skipped document lies in a thin band just beyond the box edge: less than about 0.53 m beyond it on a scorer's first threshold update and 0.93 m on later updates. The javadoc's own example use, a SHOULD boost next to another scoring query, is by code reading not affected. In the repro, search(newDistanceFeatureQuery("loc", 1, 0, 0, 1000), 1) returns a document 999.999 m north of the origin (score 0.50000024) instead of one 999.803 m north (score 0.5000492). Every release from 8.0.0 to 10.6.0 and main is affected (8.8.2 to 8.11.3 by inference); the fix is one line.

The code (main 645d4fe14a20, lucene/core/src/java/org/apache/lucene/)

#
  • The threshold. IndexSearcher#search(query, n) uses TopScoreDocCollectorManager(n, after, 1000) (search/IndexSearcher.java:100, :597-599). Once more than 1,000 hits are counted, TopScoreDocCollector calls scorer.setMinCompetitiveScore(Math.nextUp(topScore)) (search/TopScoreDocCollector.java:116-119, :154-164); in a later segment setScorer passes on the threshold already reached (:84-91).
  • The radius. DistanceScorer#computeMaxDistance (document/LatLonPointDistanceFeatureQuery.java:283-308): javadoc "... so we binary search the maximum distance. The limit is set to 1 meter." (:284-285); invariant score(min) >= minScore && score(max) < minScore (:295); while (max - min > 1) (:296); assert min == Double.MAX_VALUE || score(min + 1) < minScore; (:306); return min; (:307). The first search starts from EARTH_MEAN_RADIUS_METERS * Math.PI (:256), so after 25 halvings the interval is 0.5965 m wide; later searches start from the previous radius and can end up to 1 m wide.
  • The box. setMinCompetitiveScore (:353-472) builds Rectangle.fromPointDistance(originLat, originLon, maxDistance) (:375), which uses (radiusMeters + 7E-2) / EARTH_MEAN_RADIUS_METERS (geo/Rectangle.java:149-150, comment // LUCENE-7143). When fewer than min(leadCost, it.cost()) / 8 points are estimated in the box (:462-469), it replaces the iterator with the documents inside the box after the current one (:382-460, :470-471).
  • Sampling. After the first 256 calls, setMinCompetitiveScore recomputes the radius and the box only on every 32nd call (:360-364); in between, the previous radius and box stay in place. The repro needs a single call; the sampling affects how often later updates happen, not the size of the gap.
  • The repro's numbers (public Lucene classes on the main jar): threshold nextUp(0.50000024) = 0.5000003 after the 1,001st hit; bisection from 20,015 km in 25 steps to [999.7288 m, 1000.3253 m], returning 999.7288 m; box north edge 999.7988 m (encoded latitude 214543); doc 2001 at 999.8033 m (encoded latitude 214544) is outside; the true cut-off is 999.9989 m. A box built from 1000.3253 m (fix A) or from 999.7288 + 1 m (fix B) contains it.
  • Only near the axes. The box is the circle's circumscribed lat/lon rectangle, so it touches the circle only due N/S/E/W. For r = 1000 m, a document 0.1 / 0.3 / 0.6 m beyond r is outside the box only within +-0.44 / +-1.23 / +-1.86 degrees of a cardinal bearing (outside the north edge when (r + d) cos(bearing) > r + 0.07 m).
  • Scoring is unchanged. score() recomputes the distance from doc values (:311-316, :235-245; the distance is SloppyMath.haversinMeters, not an exact geodesic), so pruned and exhaustive search give every document the same float score; only the visited set differs.
  • Size of the gap. Over every float threshold in [0.5, 1) for pivots 1 m to 1,000 km (58,720,256 values), on a scorer's first update the true radius exceeds the returned one by 0.24-0.30 m on average and at most 0.5965 m, and 80-87% of thresholds leave a competitive distance beyond the 7 cm pad; on later updates the gap can reach 0.9994 m. The first-update bound holds for every threshold: the first search always starts from 20,015,114 m, so its final interval is always 0.5965 m wide; later intervals are at most 1 m wide by the loop condition (:296).
  • Three sizes; keep them apart. (1) How far the returned radius falls short of the true cut-off: under 0.5965 m on a first update, under 1 m later. (2) How far a skipped document lies beyond the box edge: (1) minus the 7 cm pad, so under about 0.53 m and 0.93 m. (3) How much farther the returned k-th hit is than the skipped one: (2) plus up to one float step of the score, because the returned hit scores just below the threshold (nextUp(topScore), search/TopScoreDocCollector.java:160) and the score is a float (:279-281), so its distance can lie anywhere in one float step, about (pivot + distance) x 6e-8 to 1.2e-7 m. By calculation with the scorer's formula and loop (first update, pivots 1 m to 1,000 km), the bound on (3) is under 0.60 m up to 100 km, 0.62-0.76 m at 1,000 km, 0.78-1.00 m at 3,000 km, 1.13-1.46 m at 8,000 km and 1.59-2.43 m at 15,000 km; computed, not a search that was run. In the repro (3) is 0.196 m.
  • The integer sibling is exact. LongDistanceFeatureQuery#computeMaxDistance (document/LongDistanceFeatureQuery.java:273-294) has the same loop and return min on long distances, where max - min <= 1 leaves nothing unresolved (0 mismatches in the same exhaustive check). The double copy inherited it.
Exposure and likelihood449 words
  • Who is hit. Applications that rank top-k results by LatLonPoint.newDistanceFeatureQuery where the distance query alone sets the score: the top-level query, with or without a weight (BoostQuery), or the SHOULD clause next to FILTER clauses (ReqOptSumScorer.java:282-295 forwards the threshold when the required side scores 0), and later segments, which inherit the threshold. By code reading also the only scoring clause of a conjunction (ConjunctionScorer.java:88-92) and DisjunctionMaxQuery with tieBreaker 0 (DisjunctionMaxScorer.java:116-120). By the finder's reading not when another scoring clause is combined with it, which is the javadoc's example use (a SHOULD boost next to a scoring query).
  • Default vs opt-in. Default codec, IndexWriterConfig and IndexSearcher#search(query, k), which prunes after 1,000 counted hits. Using the query is an explicit choice of a public core API.
  • What goes wrong. Silently, a document that scores higher than the k-th returned hit is missing from the top k and a farther one is returned. Returned documents are real matches with the same scores as in an exhaustive search.
  • Size. The skipped document lies less than about 0.53 m (first threshold update) to 0.93 m (later updates) beyond the box edge, near due N/S/E/W of the origin. The hit returned in its place is farther by at most that band plus one float step of the score: by calculation under about 0.6 m up to 100 km from the origin, more at continental distances (about 1.1 to 2.4 m at 8,000 to 15,000 km); 0.196 m in the repro.
  • Scale. No minimum index size beyond the pruning start (the repro has 2,002 documents), but the box must hold fewer than one eighth of the candidates; when it would hold more, for example with dense data around the origin, the scorer keeps its old iterator and nothing is skipped.
  • How often on natural data. Uniform random points (200,000 in a 20 km square or 1,000,000 in a 5 km square at latitude 45, pivot 1 km, k = 10 or 1): one segment 0 of 1,000, 0 of 300 and 0 of 1,000 queries; ten segments 1 of 1,000 and 2 of 300 (0.67%); 0 with the fix. The finder's explanation: a later segment's scorer receives the converged threshold once and bisects from 20,015 km, while within one segment the threshold usually keeps rising past the gap. With one planted near-threshold document at a near-cardinal bearing, 46 of 300 random configurations returned the wrong top-1 (0 with the fix, and 0 for the distance sort and the long sibling).
  • Workaround. A distance sort (LatLonDocValuesField.newDistanceSort), which the randomized check found correct, or no pruning (new TopScoreDocCollectorManager(k, Integer.MAX_VALUE)), at the cost of scoring every match.

Why it looks unintended

#
  • Scorable#setMinCompetitiveScore allows skipping only documents that score below the threshold; the skipped one scores 0.5000492 against 0.5000003.
  • Lucene's own test runs CheckHits.checkTopScores on this query: pruned and exhaustive top-k must agree.
  • The method's own assert, score(min + 1) < minScore, puts the cut-off up to 1 m above the returned radius; the box allows 7 cm.
The full argument210 words
  • Contract. Scorable#setMinCompetitiveScore: "Tell the scorer that its iterator may safely ignore all documents whose score is less than the given minScore" (search/Scorable.java:45-52). The skipped document scores about 800 float ulps above the threshold.
  • Test. TestLatLonPointDistanceFeatureQuery#testRandom runs CheckHits.checkTopScores(random(), q, searcher) (:396-437, :431), which requires TOP_SCORES and COMPLETE top-k to agree and asserts s1.score() < minScore for every skipped document (CheckHits.java:690-697, :748). Its random points are spread over the whole globe, so they are unlikely to land in the sub-metre band.
  • Public javadoc. LatLonPoint#newDistanceFeatureQuery gives the exact score formula and mentions no approximation (document/LatLonPoint.java:357-368).
  • The original review allowed over-inclusion only. In LUCENE-8482 (#9528), Adrien Grand (jpountz) wrote that when updating the iterator "it's fine if some documents still have a score that is less than the minimum competitive score" and that with a box "we will only fail to exclude documents that are within the bounding box of the circle but not in the circle itself" (comment of 2018-09-07).
  • History. The loop was copied from LongDistanceFeatureQuery (LUCENE-8340, a9acdfdb544, 2018-09-04), where it is exact; the 7 cm pad in Rectangle.fromPointDistance is older (045659533cd, LUCENE-7147, 2016-03-29) and was sized for tiny-radius boxes (LUCENE-7143, #8198), not for a search tolerance.
The devil's-advocate check174 words

The case (built by the intended-behaviour devil's advocate; every reviewer rated it weak): the method's javadoc says "The limit is set to 1 meter", so a 1 m pruning tolerance is documented; in #9528 the author, Ignacio Vera, and the reviewer both called a rounding effect "expected"; SloppyMath.haversinMeters is documented as off by up to 40 cm (util/SloppyMath.java:38), so a misranking inside a sub-metre band is within the score's precision; and the effect is small and rare.

Why it fails: the javadoc is on a private method and says when the search stops, not that pruning may drop competitive documents, and the next assert shows the author knew the cut-off lies above min. The "expected" in #9528 is about two very close points whose float scores tie in a boost-vs-sort test; here the skipped score is strictly higher. Both scoring modes compute the same score from the same encoded values, so distance accuracy cannot explain a disagreement between them. Small and rare is a question of priority (Low), not of intent.

Suggested fix

#

Recommended Return max, the upper end of the final interval (computeMaxDistance)

Return the upper end of the final 1 m interval from computeMaxDistance (return max;): its score is below the threshold, so every competitive document is closer and inside the box. The minimal test, the upstream test (160 of 160 over 20 iterations) and the whole org.apache.lucene.document package (499 tests) pass.

      assert score(min) >= minScore;
-      assert min == Double.MAX_VALUE || score(min + 1) < minScore;
-      return min;
+      assert score(max) < minScore;
+      return max;
All options and trade-offs2 options · 653 words

Two one-line options, both validated with gradle in a fresh scratch worktree at 645d4fe14a20 (JDK 25.0.3, seed DEADBEEF, 2026-10-30): the minimal test fails without a fix and passes with either one, with assertions on and off. Not recommended: a larger pad in Rectangle.fromPointDistance, which LatLonPointDistanceQuery, the distance sort comparator, NearestNeighbor, GeoEncodingUtils and Circle2D share; it would widen all their boxes and would not name the cause.

Return max, the upper end of the final interval (computeMaxDistance) (validated by the checks) (recommended)

Trade-offs

  • The early return at :289 (score(previousMaxDistance) >= minScore) can no longer fire after a scorer's first bisection, because the returned max always scores below its threshold, so every sampled call re-runs the bisection (at most 25 score evaluations). By code reading the box is still rebuilt only when the result changes (:368-371). Not benchmarked.
  • The box radius is now up to 0.6-1 m above the true cut-off instead of up to 1 m below it: a few more candidates at the edge, none skipped.

Downstream note

#

By code reading only, Elasticsearch and OpenSearch build this query for distance_feature on geo_point fields; whether their query shapes pass a top-k threshold to this scorer was not established, and nothing was tested there.

How it was found

#

Code reading in the hunt plan flagged the mismatch: a 1 m radius search next to a 7 cm box margin. An SMT solver (cvc5, floating-point theory) then produced concrete thresholds where a competitive distance falls outside the box, an exhaustive check of 58.7 million float thresholds measured the gap, and a public-API test confirmed it on the stock jar.

The method in full187 words

Method: semi-formal (a hypothesis from code reading, witnessed by a tool). The hunt plan for the distance-feature pruning area pointed at the 1 m bisection that keeps the lower end while the box pads only 7 cm.

  • Solver. With cvc5 1.4.2 (QF_FP), query q1, a proof attempt that the loop invariant and the exit test imply score(r + 0.075) < minScore, came back SAT in 20 s; q2, the real bisection unrolled 11 steps from a reachable previous radius of 2,048 m (pivot 1000, boost 1, a symbolic float threshold), came back SAT in about 3 minutes. Both models were replayed on the JVM.
  • Exhaustive check. A JVM transcription of the search over every float threshold in [0.5, 1) for 7 pivots (58,720,256 thresholds) measured the gap (0.24-0.30 m on average, at most 0.5965 m on a first update) and found 0 mismatches for the integer sibling.
  • Tests. A public-API JUnit on the stock main jar failed; randomized and natural-data probes measured how often it happens. The adjudication's credibility audit and the registration check re-ran it; it was later reduced to the single test shown here.

LFV-379, snapshot of 2026-11-03

Registry title
LatLonPoint.newDistanceFeatureQuery can skip a competitive document under top-k pruning: computeMaxDistance returns the lower end of its 1 m binary search, and the pruning box built from that radius adds only a 7 cm pad
Area
core / document: LatLonPoint distance feature query (dynamic pruning through setMinCompetitiveScore)
Priority
Low, rank 678: A top-k pruning gap in the core, released default searcher silently misranks distance-feature hits, but the error is under a metre and shows in under 1% of queries, so it heads the score-bound pruning rows above the unreleased LFV-203.
Impact class
silent wrong results
Impact note
Top-k searches scored by LatLonPoint.newDistanceFeatureQuery with pruning on (the default IndexSearcher#search(query, k), default codec, IndexWriterConfig and searcher, any index size) can silently return a farther document instead of a closer, higher-scoring one whenever the minimum competitive score reaches the distance scorer (executed: the top-level query with or without a weight, the SHOULD clause next to a FILTER clause, a later segment; by code reading also the only scoring clause among FILTERs and DisjunctionMaxQuery with tieBreaker 0; not when another scoring clause is combined with it), in every release since 8.0.0; the missed document is at most about 0.6 m (first threshold update) to 1 m (later updates) closer than the returned k-th hit and lies near due north, south, east or west of the origin, and on dense uniform random data it showed up in 0 to 0.7% of queries, only on 10-segment indexes.
Summary
You index points with LatLonPoint plus LatLonDocValuesField and run searcher.search(LatLonPoint.newDistanceFeatureQuery("loc", 1, 0, 0, 1000), 1), expecting the closest document, because Scorable#setMinCompetitiveScore lets a scorer skip only documents that score below the threshold and Lucene's own TestLatLonPointDistanceFeatureQuery asserts that pruned (TOP_SCORES) and unpruned (COMPLETE) top-k agree for this query. Instead, once a document 999.999 m due north (score 0.50000024) fills the queue, a document 999.803 m due north (score 0.5000492) is never visited and the farther one is returned. The scorer turns the threshold into a radius with a binary search that stops when the interval is 1 m wide and keeps the lower end (999.729 m, although every distance up to 999.999 m still competes), and the box it then searches adds only 7 cm to that radius, so competitive documents just beyond the box edge are dropped.
