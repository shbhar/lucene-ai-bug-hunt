JoinUtil's global-ordinals join with ScoreMode.None and a min or max filter scores every hit 0 instead of 1 since #16805 (main only), so a boost on the join has no effect

On Lucene main, a JoinUtil.createJoinQuery global-ordinals join with ScoreMode.None and a min or max filter scores every hit 0.0 instead of 1.0, the score of the same join without the filter. The same documents match, but a boost on the join multiplies 0, so it has no effect.

The finding in 30 seconds

#

createJoinQuery has two paths. ScoreMode.None without a min/max window returns a constant-score query: 1 times the boost. With a window it uses the score-collecting query, which since #16805 asks the collector manager for each hit's score. The manager has no case for None and returns the unset value of an empty score array: 0.

Background: the global-ordinals join

#
  1. JoinUtil.createJoinQuery(joinField, fromQuery, toQuery, searcher, scoreMode, ordinalMap, min, max) is a query-time join. It runs fromQuery, notes the join values of the matching "from" documents, and returns a query that matches the "to" documents with those join values.
  2. scoreMode says how the scores of the "from" documents become the score of a "to" document: Total, Avg, Min, Max, or None ("Do no scoring.").
  3. min and max are a filter: a "to" document matches only if at least min and at most max "from" documents matched for its join value. min = 0 with max = Integer.MAX_VALUE turns the filter off.

The finding, step by step

#
  1. Index one "to" document and two "from" documents that share a join value. JoinUtil.createJoinQuery("join", fromQuery, toQuery, searcher, ScoreMode.None, null, 0, Integer.MAX_VALUE) matches the "to" document with score 1.0.
  2. Add a filter: the same call with min = 2 ("at least two from documents"). The document has two, so it still matches. min and max are documented only as a filter on which documents match, so you expect the same score, 1.0, as on 10.6.0 and on branch_11x.
  3. On main the hit scores 0.0. Since #16805 the query asks the collector manager for the score. For ScoreMode.None the manager reads a score array that was created empty and gets its unset value, 0. The old answer, return 1f;, is still in the file, but nothing calls it.
  4. The scorer multiplies that 0 by the boost: BoostQuery(join, 5) scores 0.0 instead of 5.0, and explain() says 0.0. Next to another clause, SHOULD(to^0.5) SHOULD(join), the joined parent ties with an unjoined one at 0.5 instead of ranking first with 1.5.
  5. Hits and counts stay right (default searcher, one thread), and a join used alone or as a filter returns the same documents in the same order. Only main has this: no release does, and branch_11x does not.

Who is affected

#

Code built on unreleased main that calls this overload with ScoreMode.None and a real min/max window, and then boosts the join, combines it with other scoring clauses or reads explain(). Default configuration, one thread, no error. Rare and minor: hits and counts are right, a join used alone ranks the same, and no release has it.

Mechanism, terms and numbers604 words

JoinUtil.createJoinQuery(joinField, fromQuery, toQuery, searcher, ScoreMode.None, ordinalMap, min, max) has two paths. Without a min/max window it returns a GlobalOrdinalsQuery, a constant-score query: every hit scores 1 times the boost. With a window (min > 1 or max < Integer.MAX_VALUE) it returns a GlobalOrdinalsWithScoreQuery, and until #16805 that query asked its one collector for the score; for ScoreMode.None the collector was NoScore, whose score() is return 1f;. #16805 (e0a3a951e7ef, merged to main 2026-11-09) replaced the collector by a collector manager shared by several collectors, and the query now calls collectorManager.score(ord). That method has a case for Avg and otherwise reads the shared score array; for None the array is created empty and returns its unset value, 0. So every hit of a None join with a window scores 0 on main: a boost multiplies 0, explain() reports 0, and a join clause next to other scoring clauses no longer lifts the joined documents. Which documents match is unchanged. Main only: no release has it, and branch_11x does not contain the change (the test passes there). A 4-line fix restores the constant 1 and was validated with the join module's tests.

The code (main 781025d6fe32)

#
  1. Two paths in one method. createJoinQuery returns a GlobalOrdinalsQuery when scoreMode == ScoreMode.None && min <= 1 && max == Integer.MAX_VALUE (JoinUtil.java:569-579). Its weight is a ConstantScoreWeight (GlobalOrdinalsQuery.java:137-143): 1 times the boost. Every other case builds a GlobalOrdinalsWithScoreCollectorManager, runs the from-query into it and returns a GlobalOrdinalsWithScoreQuery (JoinUtil.java:580-593).
  2. Who the query asks. explain and both scorers call collectorManager.score(ord) (GlobalOrdinalsWithScoreQuery.java:203, :278, :315). The scorer returns score * boost (BaseGlobalOrdinalScorer.java:41-43).
  3. The manager's answer. score() has a case for Avg and otherwise returns (float) scores.getScore(globalOrdinal) (GlobalOrdinalsWithScoreCollectorManager.java:114-119). There is no case for None.
  4. The empty score array. For None the constructor creates new Scores(0, unset()) (:69-73); unset() is 0 for None (:296-302); getScore returns unset when there are no blocks (:346-354). The NoScore collector only notes which join values were seen and how often (:239-280), so nothing is ever written to the array.
  5. The old answer, unreachable. NoScore still has public float score(int globalOrdinal) { return 1f; } (:285-288). It overrides the collector's score(int) (:124-126), which only forwards to the manager, and no code calls a collector's score any more.
  6. Result. Base score 0, so 0 times the boost for every hit, and explain reports 0. Which documents match is decided by collectorManager.match(ord) (:102-112), which #16805 did not change, so with the default searcher (one thread) hits and counts stay right.

Before #16805 (its parent commit b00bfc373570, and branch_11x at daa54f2e0cd3) the query held one collector and called collector.score(ord). For None with a window that collector was NoScore, whose score() returned 1f, and the score array was null and never read.

  • The visible effect. In the probe, SHOULD(to^0.5) SHOULD(join) ties the joined parent (0.5) with a parent that has no "from" document (0.5); branch_11x and 10.6.0 rank the joined parent first (1.5 against 0.5). BoostQuery(join, 5) scores 0.0 instead of 5.0.

  • Likelihood: rare. An uncommon input shape (the min/max overload of the optional join module together with ScoreMode.None) on code that no release contains. This is an assessment, not usage data.

Why it looks unintended

#
  • min and max are documented only as a filter on matches; the same call without them scores 1 times the boost.
  • The 2015 return 1f; is still in the file, uncalled; the PR repaired the same slip for Avg only.
  • No CHANGES entry or PR comment mentions a score change; upstream's test reference says case None: return 1f;.
The full argument433 words

The contract is implied, not written. No javadoc names the number 1; ScoreMode.None is documented as "Do no scoring." (ScoreMode.java:22-23). The argument is consistency and history:

  • min and max are a hit filter. JoinUtil.java:526-531: "Optionally the minimum number of "from" documents that are required to match for a "to" document to be a match. The min is inclusive. Setting min to 0 and max to Integer.MAX_VALUE disables the min and max "from" documents filtering". Nothing says they change a score.
  • One method, two scores. Without a window the same call returns a constant-score query, 1 times the boost (JoinUtil.java:569-579, GlobalOrdinalsQuery.java:137-143). With a window it now scores 0. min = 1 was moved from the scored path to the constant-score path in 2020 as a cost saving (LUCENE-9023, 36f6359fe4b: "GlobalOrdinalsWithScore should not compute occurrences when the provided min is 1"), which was behaviour-neutral only because both paths scored 1.
  • The 1 is explicit in the code and is still there. return 1f; in NoScore.score() comes from the commit that added min/max (LUCENE-6472, 3111aeab0e3, 2015, first released in 5.2.0). It is still in the file (GlobalOrdinalsWithScoreCollectorManager.java:285-288), without a caller.
  • The same slip was repaired for Avg inside the PR, not for None. On the PR branch the first conversion commit, b1cc58bd254 (2026-10-09), made the query ask the manager, whose score() was then only return (float) scores.getScore(globalOrdinal);. That left the per-mode overrides of both Avg and NoScore unreachable. The branch commit 6ea689ec7c1 (2026-10-11) moved the Avg case into the manager. No commit added a None case.
  • Nothing announces a score change. CHANGES.txt has no entry for #16805. Its MIGRATE.md entry (MIGRATE.md:854-856) is only about the removed IndexSearcher.search(Query, Collector). The PR discussion is about concurrency, performance and the migration note; it never mentions ScoreMode.None, a score of 0 or 1, or min/max. The PR author (msokolov) describes the change there as done "with the smallest change to code".
  • Upstream's test reference says 1, and its tests cannot see the change. TestJoinUtil.java:2071-2074: case None: return 1f;. But assertTopDocs returns before it compares scores when the mode is None (:1642-1644), and checkBoost (:1102-1111, called after the min/max join at :728) asserts score * 10 == boosted score, which 0 == 10 * 0 satisfies. TestJoinUtil passes 17 of 17 on stock main.
  • A boost is meant to act on a JoinUtil query. CHANGES.txt:3550 (9.8.0, Bug Fixes): "GITHUB#12388: JoinUtil queries were ignoring boosts. (Alan Woodward)". On this path a boost again has no effect, now because it multiplies 0.
The devil's-advocate check305 words

The strongest case for "intended": ScoreMode.None means "Do no scoring", so a caller has no documented claim to any value, and the package doc says None "will disable scoring" (package-info.java:77-80). In the same package and with the same enum, ToParentBlockJoinQuery scores a None parent 0 (ToParentBlockJoinQuery.java:313), and an upstream test asserts it (TestBlockJoin.java:1784-1786: case None: expectedScore = 0f;). A downstream manual says its has_child query with score mode none assigns parent documents a score of 0. A caller who wants a constant can ask for one: new ConstantScoreQuery(join) scores 1.0 on main, and 5.0 under a boost of 5 (run). And the uncalled return 1f; can be read the other way: as obsolete code that the refactoring should have removed.

Why it does not explain this change: nothing in the code, the PR or the change log shows that 0 was chosen. The explicit return 1f; is left as dead code, the Avg half of the same slip was repaired and the None half was not, and nothing announces a new score. This is circumstantial; it does not prove what the author meant. The result is one public method that scores 1 times the boost or 0 depending on arguments documented only as a hit filter. The block join is another query class with its own long-standing, tested convention, while every ScoreMode.None path of JoinUtil has been constant-score since 5.2.0. And the downstream project whose manual says 0 asserts 1 for this very call in its own integration test (read, not run).

What remains: a maintainer may still decide that the score of a None join is unspecified, or that 0 is the better value, and close this as working as designed. Then it is a decision to document (Suggested fix, option C), not a silent side effect.

Suggested fix

#

Recommended A None case in the manager's score() (validated)

In GlobalOrdinalsWithScoreCollectorManager.score(), return 1f for ScoreMode.None before reading the score array, and delete the unreachable NoScore.score() override: one file, +4/-5 lines. Validated: the test passes, the join module's tests pass (106 tests counting the new one, 0 failures, 3 skipped), both with assertions on and off, and the module's checks pass.

  public float score(int globalOrdinal) {
    if (scoreMode == ScoreMode.None) {
      // no scores were collected: every hit gets the constant score 1, like GlobalOrdinalsQuery
      return 1f;
    }
    if (scoreMode == ScoreMode.Avg) {
      return (float) (scores.getScore(globalOrdinal) / occurrences.getOccurrence(globalOrdinal));
    }
    return (float) scores.getScore(globalOrdinal);
  }

A None case in the manager's score() (validated) (recommended)

#

score() is the one place the scorers and explain ask, so one case there restores the constant 1 for every caller. The unreachable NoScore.score() override (return 1f;) is removed. One file, +4/-5 lines.

  public float score(int globalOrdinal) {
    if (scoreMode == ScoreMode.None) {
      // no scores were collected: every hit gets the constant score 1, like GlobalOrdinalsQuery
      return 1f;
    }
    if (scoreMode == ScoreMode.Avg) {
      return (float) (scores.getScore(globalOrdinal) / occurrences.getOccurrence(globalOrdinal));
    }
    return (float) scores.getScore(globalOrdinal);
  }

Trade-offs

No regression was found in the tests listed below; nightly tests and benchmarks were not run. It restores the value every release has and touches no collect path; Total, Avg, Min and Max print the same before and after. Whether a None join should score 1 or 0 is itself a choice for the maintainers: ToParentBlockJoinQuery uses 0 (see "Keep 0 and say so"). Optional tidy-up, not in the validated diff: the collector-level score(int) (GlobalOrdinalsWithScoreCollectorManager.java:124-126) has no caller either.

Decide in the query

#

GlobalOrdinalsWithScoreQuery knows the score mode. It could use 1 for None at its three call sites (GlobalOrdinalsWithScoreQuery.java:203, :278, :315) instead of asking the manager.

Trade-offs

Same behaviour, but three places must stay in sync, and the manager's score() would still return 0 for None to any other caller. Not built.

Keep 0 and say so

#

If maintainers prefer that a None join with a window scores 0, as ToParentBlockJoinQuery does: state it in the javadoc of createJoinQuery and in CHANGES.txt or MIGRATE.md, delete the dead return 1f;, and change the test reference case None: return 1f;.

Trade-offs

One method would still score 1 times the boost without a window and 0 with one, unless GlobalOrdinalsQuery changes too; a boost would have no effect on this path; and the downstream tests that assert 1 for this call (read, not run) would need to change. Not built.

Downstream note

#

Downstream (read, not run): Elasticsearch and OpenSearch pass has_child's min_children and max_children to this overload with score mode none as the default, and their integration tests assert a score of 1 for it; neither builds against a Lucene with the change yet.

How it was found

#

Non-formal. A before/after differential test ran the same joins on main before and after its 13 newest commits and compared the scores: a ScoreMode.None join with min = 2 scored 1.0 before and 0.0 after. A bounded-exhaustive check of 4160 small joins against a reference then showed that only None joins with a min/max filter differ.

The method in full198 words

Method: non-formal (a targeted before/after comparison gave the first signal).

  • Before/after differential. After upstream main moved from f794ff5a505c to 781025d6fe32 (13 commits, among them #16805), a small witness for the changed join code (one parent with two children, ScoreMode.None, min = 2) printed score 1.0 on the earlier main and 0.0 on the new one. A seeded differential over 8 join kinds x 5 score modes x 4 searcher kinds against a brute-force join showed the same on its "None with a filter" lines.
  • Bounded-exhaustive check. 4160 joins (2 segment layouts x 16 child layouts x 5 score modes x 13 min/max windows x 2 boosts) were run on the real classes and compared with reference semantics written from the javadoc and the unfiltered sibling query: hit set, score and explain value of every hit. On main only the 452 "None with a filter" joins that have a hit differ; 0 differ on the earlier main, on 10.6.0 and on main with the fix.
  • Reduction. The case was reduced to one public-API test, and then to the one-assertion form of the repro, which compares the filtered with the unfiltered join instead of asserting a bare number.

History

#

Introduced on main by #16805 (e0a3a951e7ef, merged 2026-11-09): a regression of a path that scored 1 since 5.2.0. No release has it, and branch_11x does not have it (checked 2026-11-16): the test passes on branch_11x and on 10.6.0.

Versions tested8 rows

Introduced by e0a3a951e7ef, "Collector manager join" (apache/lucene#16805, by Michael Sokolov (msokolov); opened 2026-10-09, merged to main 2026-11-09 as one squashed commit of 12 branch commits; 10 files; no CHANGES.txt entry). LFV-1481, snapshot of 2026-11-27

Registry title
JoinUtil's global-ordinals join with ScoreMode.None and a min or max filter scores every hit 0 instead of 1 since #16805 (main only), so a boost on the join has no effect
Area
join / JoinUtil global-ordinals join: the score of a ScoreMode.None join that has a min/max filter (GlobalOrdinalsWithScoreQuery, GlobalOrdinalsWithScoreCollectorManager)
Priority
Low, rank 813: Only on unreleased main (since #16805, not on branch_11x), a JoinUtil global-ordinals join with ScoreMode.None and a min or max filter scores every hit 0 instead of 1, so a boost on the join has no effect and the join no longer lifts joined documents next to other scoring clauses. It is Low because the hits and counts stay right, a join used alone or as a filter ranks the same, no javadoc promises the 1, the trigger is rare and no release has it.
Impact class
minor
Impact note
Hits only unreleased code (upstream main since #16805; not on branch_11x, in no release): an application that calls the public overload JoinUtil.createJoinQuery(joinField, fromQuery, toQuery, searcher, ScoreMode.None, ordinalMap, min, max) with min above 1 or max below Integer.MAX_VALUE (default IndexWriterConfig and IndexSearcher, one thread, one segment or several, -ea or -da, no scale needed) still gets the right hits and counts, but every hit scores 0 instead of 1, so a boost on the join multiplies 0 and a join clause next to other scoring clauses no longer lifts the joined documents; a join used alone or as a filter returns the same documents in the same order, and Total, Avg, Min and Max are not affected.
Summary
You build a global-ordinals join with JoinUtil.createJoinQuery and ScoreMode.None and ask for at least two "from" documents (min = 2); one "to" document has two, so it matches, and you expect the hit to score what the same join scores it without the min/max filter: the constant 1 (times any boost), as on 10.6.0 and every earlier release. Instead, on main since #16805, the hit scores 0.0: the query now asks the collector manager for the score, and for ScoreMode.None the manager reads an empty score array and returns its unset value 0, while the old 'return 1f;' is still in the file with no caller. The hits and counts stay right, but a boost on the join has no effect (0 times the boost), explain() reports 0, and a join clause next to other scoring clauses no longer ranks the joined documents higher.
