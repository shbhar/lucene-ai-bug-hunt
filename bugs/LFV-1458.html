JapaneseTokenizer keeps the dots of a user-dictionary entry although discardPunctuation=true

A Kuromoji user-dictionary entry that splits レオナルド・ダ・ヴィンチ at its dots makes JapaneseTokenizer emit the dots ・ as terms despite discardPunctuation=true. Each dot takes a position, so the phrase "ダ・ヴィンチ" finds the document without the entry (1 hit) but not with it (0 hits); every release since 3.6.0.

The finding in 30 seconds

#

The code that turns a user entry into its segments adds every segment without the punctuation test that every other token path applies.

Kuromoji, punctuation and user dictionaries, in one minute

#
  1. JapaneseTokenizer (Kuromoji) splits Japanese text into words with a dictionary. With discardPunctuation=true (the factory default, and what JapaneseAnalyzer uses) it drops punctuation such as the middle dot ・ that separates the parts of foreign names: レオナルド・ダ・ヴィンチ (Leonardo da Vinci) becomes レオナルド, ダ, ヴィンチ.
  2. Dropped punctuation leaves no position gap: レオナルド, ダ, ヴィンチ sit at consecutive positions, which is what lets the phrase "ダ ヴィンチ" match.
  3. A user dictionary adds an application's own words, one CSV line each: surface, segmentation (space-separated), readings, part of speech. The segments joined together must equal the surface, so a dot in the surface has to go into some segment: on its own, or glued to a neighbour.

The finding, step by step

#
  1. Give JapaneseTokenizer the user-dictionary entry レオナルド・ダ・ヴィンチ,レオナルド ・ ダ ・ ヴィンチ,レオナルド ・ ダ ・ ヴィンチ,カスタム名詞 and keep discardPunctuation=true. The segments joined together must equal the surface, so the dots cannot be left out; this entry gives each dot a segment of its own.
  2. Index レオナルド・ダ・ヴィンチの絵. Without the entry the tokens are レオナルド, ダ, ヴィンチ, の, 絵: 5 tokens, the dots dropped.
  3. You expect the same 5 tokens with the entry. Instead you get 7: レオナルド, ・, ダ, ・, ヴィンチ, の, 絵, exactly what discardPunctuation=false gives.
  4. Each dot takes a position. With the same analyzer at query time, the phrases "ダ・ヴィンチ", "ダ ヴィンチ" and "レオナルド ダ ヴィンチ" find the document without the entry (1 hit each) and miss it with the entry (0 hits). Only the full dotted name still matches; no error.

Who is affected

#

Applications that give Kuromoji a user dictionary (opt-in) with an entry that gives punctuation its own segment, such as a name split at its middle dots. Texts with that entry get the dots as terms, so phrase and proximity queries on part of the name silently miss. JapaneseAnalyzer has no option to turn the flag off.

Mechanism, terms and numbers706 words

With discardPunctuation=true (the factory default; JapaneseAnalyzer always passes true) JapaneseTokenizer drops punctuation. A user-dictionary entry that segments a dotted name at its dots makes it emit the dots anyway: with the entry レオナルド・ダ・ヴィンチ,レオナルド ・ ダ ・ ヴィンチ,レオナルド ・ ダ ・ ヴィンチ,カスタム名詞, the text レオナルド・ダ・ヴィンチの絵 gives [レオナルド, ・, ダ, ・, ヴィンチ, の, 絵] instead of [レオナルド, ダ, ヴィンチ, の, 絵], which is exactly the output for discardPunctuation=false.

The code that expands a user entry into its segments (ViterbiNBest.backtrace, and registerNode for n-best output) never checks a segment for punctuation (registerNode tests only the first character of the whole entry), while every other token path checks its token. The kept dots take positions, so phrase and proximity queries for parts of the name miss: with the same analyzer at index and query time, "ダ・ヴィンチ", "ダ ヴィンチ" and "レオナルド ダ ヴィンチ" find a one-document index without the entry and miss it with the entry. It needs an opt-in user dictionary with such an entry; every release since Kuromoji shipped (3.6.0) is affected.

The code (main f794ff5a505c)

#
  1. Every mode goes through ViterbiNBest (JapaneseTokenizer.java:250). For a token that came from the user dictionary, the backtrace takes the USER branch (ViterbiNBest.java:400-433): it looks up the entry's segment lengths (lookupSegmentation(backID), :404), adds one token per segment to pending (:407-425), then reverses them and adds their count to backCount (:430-433). discardPunctuation is never read there.
  2. The other branches check it. EXTENDED-mode unigrams: if (!discardPunctuation || !isPunctuation(...)) (:448). KNOWN and UNKNOWN tokens: else if (!discardPunctuation || length == 0 || !isPunctuation(fragment[offset])) (:465), otherwise "skip punctuation token". isPunctuation includes OTHER_PUNCTUATION, the class of ・ (:705-727).
  3. n-best output (registerNode, :635-689) tests the flag only on the first character of the whole user node (:639), adds the compound, then adds every shorter segment unchecked (:659-675). Its comment says "The code below are based on backtrace()".
  4. The entry cannot leave the dots out. The loader rejects an entry whose segments do not join to the surface ("does not match the surface form", UserDictionary.java:114-124). On its own a dot becomes a ・ term. Glued to a neighbour (segmentation レオナルド・ ダ・ ヴィンチ, accepted) it becomes part of that term, [レオナルド・, ダ・, ヴィンチ, の, 絵], and the three phrases for part of the name still get 0 hits (the full name 1); fix A leaves that output unchanged. The part of speech is one value per entry (:100), so JapanesePartOfSpeechStopFilter cannot drop only the dots (a stop tag for カスタム名詞 would drop the whole entry); the stock JapaneseAnalyzer keeps the ・ terms.

Exposure and likelihood202 words
  • Who is hit. Users of JapaneseTokenizer, JapaneseAnalyzer or JapaneseTokenizerFactory with a user dictionary that has an entry whose surface contains punctuation that its segmentation puts into a segment of its own: a katakana foreign name split at its middle dots (レオナルド・ダ・ヴィンチ), a product or company name (アイワ・コーポ), a pair such as 東京・大阪 (the cross-model reviewer's own test entry).
  • Defaults otherwise. discardPunctuation defaults to true in the factory (JapaneseTokenizerFactory.java:127); the JapaneseTokenizer constructors take it as a required argument. JapaneseAnalyzer hard-codes true (JapaneseAnalyzer.java:110) and has no constructor option for it, so switching it off needs a custom analyzer chain.
  • Effect. Every document and query containing the entry's surface gets ・ terms. Each takes a position, so phrase and proximity queries for parts of the name miss (0 hits instead of 1 in the probe). The full dotted name still matches. No exception, no index damage.
  • How likely. Narrow. Without an entry this name is already split at ・ and the dot dropped, so such an entry is added for other reasons, for example its readings or its part of speech; how common such entries are was not measured. No public report was found since 2012.

Why it looks unintended

#
  • The flag's javadoc has no exception: "true if punctuation tokens should be dropped from the output" (JapaneseTokenizer.java:109); with the entry, true and false give the same tokens.
  • The pre-2012 code dropped these segments; n-best registerNode reads the flag for user nodes (ViterbiNBest.java:639), the backtrace never.
  • The entry cannot leave the dot out (UserDictionary.java:114-124); glued to a neighbour, phrases still miss.
The full argument330 words
  • Contract. @param discardPunctuation true if punctuation tokens should be dropped from the output. (JapaneseTokenizer.java:109, repeated at :122, :145, :169, :202). No javadoc, the factory doc, CHANGES.txt or MIGRATE.md exempts user-dictionary tokens. UserDictionary says only "This class allows for custom segmentation of phrases." (UserDictionary.java:32): segmentation, not what is emitted.
  • History. Before LUCENE-3767 (430365f7cce, 2012-03-04) each user segment was its own lattice node, and Segmenter.doTokenize skipped every node that starts with punctuation. Source builds: the parent gives [レオナルド, ダ, ヴィンチ] with the entry applied, 430365f7cce gives [レオナルド, ・, ダ, ・, ヴィンチ]. The 30 comments of #4840 (LUCENE-3767) do not discuss punctuation in user entries.
  • The code disagrees with itself. n-best registerNode reads the flag for user nodes, on the node's first character (ViterbiNBest.java:639); the backtrace USER branch never reads it. The output does not show that test: a single-segment user entry （株） is still emitted with n-best on and discardPunctuation=true.
  • No way around it in the entry. Since LUCENE-8933 (first released in 9.0.0) the loader rejects an entry whose segments do not join to the surface (UserDictionary.java:114-124), so the dot cannot be left out; before that, the tokens were cut from the input by the segment lengths, so leaving it out gave no dot-free tokens either. Glued to a neighbour, the dot becomes part of that term ([レオナルド・, ダ・, ヴィンチ, …], accepted), and the phrases for part of the name still get 0 hits. The part of speech is one value per entry (:100), so a part-of-speech filter cannot pick out the dots.
  • No test asserts today's behaviour. The test dictionary's # entries (test#テスト,test # テスト,... and テスト#,テスト #,..., LUCENE-8596, userdict.txt:12-14) are checked only through lookup() (TestUserDictionary.java:100-108). The testUserDict* tests (TestJapaneseTokenizer.java:467-492) load that shared dictionary but tokenize only inputs without punctuation, with discardPunctuation=false (:89); no test tokenizes the # entries with discardPunctuation=true.
The devil's-advocate check332 words

The case for "intended". A user's segmentation is authoritative and emitted verbatim; a token filter should drop the dots. A user entry that is a single punctuation segment (・) or that starts with punctuation (（株）) is also kept today, and in elastic/elasticsearch#57614 (2020) a Lucene committer, jimczi, suggested "a custom user dictionary that overrides the tokenization for （株）" as a workaround for the #10430 drop, which relies on user tokens skipping the test. The test dictionary also has a # segment. The strongest maintainer voice is on #10430 itself (LUCENE-9390, 2020): Tomoko Uchida (mocobeta) wrote that dropping punctuation-only tokens "is a token filter's job rather than a tokenizer", and Jun Ohtani (johtani) proposed removing the flag so that "the part of speech token filter" removes such tokens; in their latest comment there (2020-06-19) Jun Ohtani agreed that a char or token filter can handle it and noted that "removing this option is a big breaking change".

Why it fails. None of these is a documented exemption, and none covers a punctuation-only segment of a multi-segment entry. In the same comment jimczi describes the design: "the expectation in the code is that punctuations are separated from other tokens which is why the check is done only on the first character". A separate ・ segment is exactly such a separated punctuation token. The 2012 code dropped it, and the entry cannot leave the dot out (glued to a neighbour, it still breaks the phrases). Fix A keeps both the （株） workaround (not punctuation-only) and a single-segment ・ entry. The #10430 view is about the flag's design, not an exemption for user entries: while the flag exists its javadoc promises the drop; "use a filter" needs discardPunctuation=false for the whole field, which JapaneseAnalyzer has no option for (a custom chain is needed); and a part-of-speech filter cannot pick out these dots, because they carry the entry's one part of speech. A maintainer may still prefer "verbatim" as a design call.

Suggested fix

#

Recommended Drop punctuation-only segments of a multi-segment entry in backtrace (validated)

In the backtrace USER branch, skip a segment that is all punctuation when discardPunctuation is set and the entry has two or more segments, and count only the emitted tokens (+20/-3 in ViterbiNBest.java). The repro and the kuromoji module's tests pass, and phrases match again. n-best output needs a second change (option B).

In ViterbiNBest.backtrace's USER branch, when discardPunctuation is set and the entry has two or more segments (wordIDAndLength.length > 2), skip a segment whose characters are all punctuation. Count the tokens actually added and use that count for Collections.reverse and backCount, as the KNOWN branch counts only what it emits.

Trade-offs

  • Indexed terms change. Affected documents lose their ・ terms; phrase queries on parts of the name match only after reindexing. The old output was never documented; how to note the change (for example a CHANGES entry) is the maintainers' call.
  • Single-segment entries keep today's behaviour. A user entry that is only ・ (which today makes 東京・大阪 tokenize as [東京, ・, 大阪]) or （株） is emitted as before; option C would change that.
  • n-best is not covered. With nBestCost > 0 the dots still appear (phrase probe with fix A, n-best line); see option B.

Downstream note

#

Products that build the tokenizer from configuration (the factory's userDictionary option, discardPunctuation left at its default) inherit this whenever a configured entry splits at punctuation.

How it was found

#

A semi-formal sweep ran the Japanese and Korean tokenizers with user dictionaries through many analysis chains and checked that discardPunctuation=true emits no punctuation-only token. It flagged a ・ token on a user entry for アイワ・コーポ; a phrase-query probe measured the effect and a one-test JUnit on main confirmed it.

The method in full140 words

Method: semi-formal, property checking of analysis chains, on main f794ff5a505c, 2026-11-09.

  • Sweep. The kuromoji and nori tokenizer variants, including user-dictionary variants, were run inside generated analysis chains against token-stream properties that must hold for any correct chain. One of them: with discardPunctuation=true, no token consists only of punctuation.
  • Signal. The property failed on the user-dictionary variants, for example on the text アイワ・コーポ東京支店 with the entry アイワ・コーポ,アイワ ・ コーポ,.... Tagging the failures example by example separated these ・ cases from a different, already registered punctuation issue (supplementary-plane characters, LFV-749).
  • Confirmation. A probe indexed one document and ran phrase queries with the same analyzer (1 hit without the entry, 0 with it); a one-method JUnit on public API reproduced it on main with assertions on and off, and code reading found the missing test in the USER branch.

LFV-1458, snapshot of 2026-11-10

Registry title
JapaneseTokenizer with discardPunctuation=true (the default, and the only setting JapaneseAnalyzer uses) still emits the punctuation-only segments of a user-dictionary entry, so an entry that segments a dotted name (レオナルド・ダ・ヴィンチ as レオナルド ・ ダ ・ ヴィンチ) indexes '・' terms that take positions, and phrase queries for parts of the name such as "ダ・ヴィンチ" stop matching (since 3.6.0)
Area
analysis-kuromoji / JapaneseTokenizer user-dictionary output (ViterbiNBest backtrace USER branch and the n-best registerNode copy) vs discardPunctuation
Priority
Medium, rank 146: In every release since 3.6.0, a well-formed Kuromoji user-dictionary entry (an opt-in) that splits a dotted name at its dots makes JapaneseTokenizer index and query the dots as terms that take positions despite the default discardPunctuation=true, so phrase and proximity queries for parts of the name, such as "ダ・ヴィンチ", silently miss. It is Medium but low in the tier because that entry shape is rare and the exact full name still matches.
Impact class
silent wrong results
Impact note
Applications that give JapaneseTokenizer, JapaneseAnalyzer or JapaneseTokenizerFactory a user dictionary (an opt-in) with an entry whose surface contains punctuation that its segmentation puts into a segment of its own (a dotted katakana name or product name split at its dots; since LUCENE-8933 in 9.0.0 the loader requires the segments to spell the surface, so the dots cannot be left out) get the punctuation as indexed and query terms on every text that matches the entry, in NORMAL, SEARCH and EXTENDED mode and with n-best output, with -ea and -da, no scale needed: phrase and proximity queries for parts of the name ('ダ・ヴィンチ', 'ダ ヴィンチ', 'レオナルド ダ ヴィンチ') miss the document while the exact dotted full name still matches; every release from 3.6.0 to 10.6.0 and main.
Summary
You give JapaneseTokenizer (or the stock JapaneseAnalyzer) a user dictionary with the well-formed entry 'レオナルド・ダ・ヴィンチ,レオナルド ・ ダ ・ ヴィンチ,レオナルド ・ ダ ・ ヴィンチ,カスタム名詞' and keep discardPunctuation=true, whose javadoc says 'true if punctuation tokens should be dropped from the output'; you expect [レオナルド, ダ, ヴィンチ], which is what the tokenizer gives for the same text without the entry. Instead it emits [レオナルド, ・, ダ, ・, ヴィンチ], exactly as with discardPunctuation=false, because the code that expands a user entry into its segments (ViterbiNBest.backtrace, and registerNode for n-best output) never checks for punctuation, while the other token paths do. The kept dots take positions, so for a one-document index 'レオナルド・ダ・ヴィンチの絵' the phrase queries "ダ・ヴィンチ", "ダ ヴィンチ" and "レオナルド ダ ヴィンチ" find the document without the entry and miss it with the entry, with no error.
