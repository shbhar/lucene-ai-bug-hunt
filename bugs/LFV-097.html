IndexWriter#addBatch: a throwing dense LongColumn cursor gives later documents another document's doc value

If a dense LongColumn's cursor throws part-way through IndexWriter#addBatch, the batch is rejected but values from pages it already filled stay buffered with no document. Later documents of that field in the segment then get another document's doc value (42 reads back as -1), persisted, with CheckIndex clean.

The bug in 30 seconds

#

Lucene buffers a field's doc values in pages of 256 and registers a dense batch's documents only after the whole bulk copy returns. A cursor that throws after a page was filled leaves that page's values counted but registers no documents for them, and flush pairs documents with values by position.

  1. Add 255 documents with a NUMERIC doc value v = 0 to 254 (default IndexWriterConfig and codec). Doc values are buffered in pages of 256 values, so the current page has one free slot.
  2. Call addBatch with 2 documents: a dense LongColumn "v" whose LongValuesCursor returns -1, then throws on its 2nd value. The exception propagates and the 2 batch documents are deleted, as expected.
  3. Add a document with v = 42. You expect it to read back 42, as Lucene's own recovery test asserts for documents indexed after a throwing cursor.
  4. Instead it reads -1. The -1 filled the page's last slot and stayed buffered with no document, so each later document gets the value one position earlier: 42, 43, 44 read back as -1, 42, 43.
  5. No error: CheckIndex is clean and the wrong values survive commit, forceMerge(1) and reopen. Reproduced on 10.5.0, 10.5.1, 10.5.2 and main; turning assertions off changes nothing.

Who is affected

#

Applications that use the experimental IndexWriter#addBatch (10.5.0 and later) with a dense LongColumn feeding NUMERIC or SORTED_NUMERIC doc values, whose own cursor throws mid-batch, and that keep indexing into the same writer. Default configuration and codec. Lucene's own code never throws there, so it is rare; the one known downstream user has its batch path off by default.

Mechanism, terms and numbers637 words

IndexWriter#addBatch (experimental, since 10.5.0) copies a dense LongColumn into the field's NUMERIC or SORTED_NUMERIC doc-values buffer in bulk, one 256-value page at a time, and registers the batch's documents only after the whole copy has returned. If the application's LongValuesCursor throws after at least one page was filled during the call, the batch is rejected correctly (the exception propagates, the writer stays open, the batch's documents are deleted), but the values of the filled pages stay buffered with no document. At flush the k-th document with the field is paired with the k-th buffered value, so every later document of that field in the same in-memory segment is stored with the value of a document that many positions earlier (for a SORTED_NUMERIC field with an earlier multi-valued document: the counts stay right, the values come from other documents). Nothing throws, CheckIndex is clean, and the values survive commit, reopen and forceMerge(1). Default configuration and codec; it needs an application cursor that throws, so it is rare. The sibling dense SORTED path and the stock flat writer of the new dense vector path (#16734) keep documents and values aligned; the fix is a few lines of bookkeeping.

Terms

#
  • Columnar addBatch. IndexWriter#addBatch(ColumnBatch) (experimental, 10.5.0) indexes a batch column by column. A DENSE LongColumn has a value for every document and hands it over through a LongValuesCursor that the application writes (LongColumn.values(), document/column/LongColumn.java:79-88).
  • The doc-values buffer. NumericDocValuesWriter and SortedNumericDocValuesWriter keep the values of the in-memory segment in a PackedLongValues.Builder (pages of 256 values, PackedLongValues.java:34, :66) and the documents that have the field in a docsWithField set.
  • Non-aborting exception. An exception that rejects the current documents but keeps the writer and the in-memory segment for later documents.

The bug, step by step (main a9779ef3c193)

#
  1. IndexingChain.processDenseLongColumn runs the doc-values pass first and calls addDenseValues on the field's writer (IndexingChain.java:1076-1093).
  2. addDenseValues calls pending.add(cursor) and only after it returns registers the batch's documents: docsWithField.addRange, lastDocID / currentDoc, and pendingCounts for SORTED_NUMERIC (NumericDocValuesWriter.java:81-94, SortedNumericDocValuesWriter.java:73-102).
  3. PackedLongValues.Builder.add(LongValuesCursor) packs a full page, asks the cursor for at most the rest of the current page with fillDocValues, then advances pendingOff and size (PackedLongValues.java:265-279). When a later fillDocValues call throws, the values of the earlier calls stay counted.
  4. DocumentsWriterPerThread.updateBatch treats the exception as non-aborting: it deletes the batch's documents and keeps the segment (DocumentsWriterPerThread.java:349-354, :399-409).
  5. The NRT reader, the flush and the index sorter read the buffer through BufferedNumericDocValues, which takes the next document of docsWithField and the next buffered value (NumericDocValuesWriter.java:192-198; single-valued SORTED_NUMERIC uses it too, SortedNumericDocValuesWriter.java:192-199). With k left-over values every later document gets the value k positions earlier (up to the first k get the rejected batch's values); the last k values are never read, so nothing throws. Once an earlier document of a SORTED_NUMERIC field was multi-valued, the per-document counts stay right but the values are read from the same shifted stream (SortedNumericDocValuesWriter.java:192-199, :279-289).

The numbers

#

Writer state from an executed probe: after documents 0-254, 255 values and 255 documents. The 2-document batch: fill call 1 (offset 255, length 1) returns -1, the page is packed, fill call 2 (offset 0, length 1) throws: 256 values, still 255 documents. Documents 257-259 (42, 43, 44) are then paired with -1, 42 and 43; the good document's 44, the last buffered value, is never read. Other executed cases: a 257-document SORTED_NUMERIC batch failing on its last value leaves 256 values (the next document reads -1 instead of 42); a 600-document batch failing at value 520 leaves 512 (42, 43, 44 read -1, -2, -3). Not affected: a throw inside the first fill call, the sparse (tuple) long path, the dictionary SORTED dense path, and a flush right after the failure.

Exposure and likelihood338 words
  • Who is hit. Users of the experimental addBatch / updateBatch with a DENSE LongColumn for NUMERIC or SORTED_NUMERIC doc values (including a LongField-style schema with points plus SORTED_NUMERIC; the doc-values pass runs first), whose LongValuesCursor throws a RuntimeException after the batch crossed a 256-value page boundary of the field's buffer, and who keep adding documents with that field before the segment flushes. updateBatch keeps the writer and the in-memory segment for that, and Lucene's own recovery test indexes more documents afterwards (after a commit()); the public addBatch contract says nothing about unchecked exceptions.
  • Default or opt-in. Default IndexWriterConfig and codec, no assertions needed; reproduced with NoMergePolicy, the default TieredMergePolicy and the randomized test configuration. The opt-in part is the experimental API and a cursor that throws: Lucene ships no LongValuesCursor outside tests, so the cursor is application code, for example one that decodes or validates its source lazily and fails on a bad row.
  • Scale. 255 earlier documents and a 2-document batch are enough. The shift equals the number of values in the completed fill calls: 1, 256 and 512 in the executed cases.
  • The damage. Documents whose own add calls succeeded carry another document's value: sorting, doc-values queries, facets and aggregations on that field, and an index sort (probe: the good document reads -1 with the sort on the field itself or on another field). Points stay correct, so points and doc values of one field disagree; LongField.newExactQuery can return wrong hits when IndexOrDocValuesQuery runs on doc values. CheckIndex is clean; the values survive commit, reopen and forceMerge(1). Repair means finding and reindexing the affected documents; for a doc-values-only field that is not an index-sort field, updateNumericDocValue / updateSortedNumericDocValue can also rewrite them (IndexWriter.java:1962, :2037), but not for a LongField-style field with points.
  • Exposure today. The API shipped in 10.5.0 (June 2026). The only downstream user found, Elasticsearch's batch-indexing path, is unreleased, behind a feature flag and a setting that defaults to off, with no known throw site here.

Why it is a bug, not intended

#
  • Lucene's design note: a non-aborting exception may partially update the index, but "These updates are consistent".
  • Lucene's own recovery test throws from a dense cursor and asserts exact later values; its 6-value batch never fills a page, and it commits right after the failure.
  • The dense SORTED path and the stock flat vector writer (#16734) keep documents and values aligned.
The full argument410 words
  • Design note (DocumentsWriter.java:76-79): "All other exceptions ("non-aborting exceptions") can still partially update the index structures. These updates are consistent, but, they represent only a part of the document seen up until the exception was hit. When this happens, we immediately mark the document as deleted so that the document is always atomically ("all or none") added to the index." updateBatch follows it (DocumentsWriterPerThread.java:349-354). addDocument: "if an Exception is hit ... then the index will be consistent" (IndexWriter.java:1465). The addBatch javadoc (:1528-1536), the column javadocs, CHANGES and MIGRATE never ask for a flush after a failed batch.
  • Lucene's tests deliberately throw from a dense cursor and check the writer afterwards. ColumnBatchTestUtil has throwing-cursor helpers "so tests can exercise the failure-cleanup path in DocumentsWriterPerThread#updateBatch" (:589-591), including ThrowingDenseLongColumn (:638-642). TestColumnBatchIndexing#testLongValuesCursorThrowMidBatchRecovers (:740-792) asserts 777, 111 and 222 for the documents indexed afterwards. That shows intent to keep the writer usable, not a written contract for same-segment recovery. It misses the bug because its 6 values throw inside the first fill call and because it commits right after the failure (:760-762, "so the cleanup-induced fully-deleted segment is pruned"). With a 300-value batch failing at 280 the test passes with that commit() and fails without it: expected:<777> but was:<1>.
  • Two sibling paths do it right. SortedDocValuesWriter.addDenseOrdinalValues (:156-182, #16101) registers exactly the processed documents in a finally; a Z3 model that counts values and documents found no batch of up to 4096 values where the counts differ after a throw. The dense vector path merged in #16734 writes the rule down: "The cursor may throw while it is being consumed ... the writer must remain in a consistent state: every doc ID it has recorded must have its vector ... record doc IDs and vectors only after fill has returned" (KnnFieldVectorsWriter.java:46-50), and its new test keeps the failed and the recovery batch in one segment on purpose (TestColumnBatchIndexing.java:886-922). That holds for the stock flat writer; LFV-579, a separate defect, shows HNSW and scalar-quantized wrappers over a custom flat writer that fall out of step.
  • History. #16270 made batch exception handling match updateDocuments. #16553, backported to 10.5.2, is a precedent: a non-aborting exception left indexing-chain state inconsistent (a stored-fields frame left open), so that a later flush failed; reviewers called it a corruption issue and pulled it into the 10.5.2 release candidate.
The devil's-advocate check208 words

The strongest case for "works as designed" (independent checkers, both still concluding "real"): the API, LongColumn and LongValuesCursor are experimental; the cursor "produces exactly size() values" (LongValuesCursor.java:22-23), so a cursor that throws within range is a broken producer; PackedLongValues.Builder promises no atomicity; addBatch declares only IOException; and the upstream test flushes before indexing again, as if only post-flush recovery were intended.

Why it fails: the documents that end up wrong are later ones whose own add calls succeeded, and no contract lets a successful add store another document's value. The same javadoc requires implementations to throw on overrun (:25-26, :57-58), so exceptions belong to the cursor protocol (that javadoc covers overrun, not an in-range failure, so the contract stays ambiguous), and Lucene's own helper throws in range on purpose. updateBatch keeps the segment and nothing says to flush; the test's commit() is there, by its comment, to prune the deleted segment. A stale comment in testDenseColumnCountMismatchThrows ("avoid the partially-written DV entries", TestColumnBatchIndexing.java:291-292) dates from a PR revision that wrote values and documents together, so it is about values on deleted documents, not misalignment. Verdict: a defect (a correctness bug of an experimental API; a maintainer may still label it an enhancement).

Suggested fix

#

Recommended Register exactly the values that reached the buffer (validated)

Remember pending.size() before the bulk add and, in a finally, register that many of the batch's own (already deleted) documents and pendingCounts entries, as the dense SORTED path does. With it the 3 tests pass, and so do the 20 other closest test classes, all 8,892 core-module tests and :lucene:core:check -x test.

final long sizeBefore = pending.size();
try {
  pending.add(cursor);
} finally {
  // Register a doc for every value that reached the buffer, even if the cursor threw part-way,
  // so that values stay aligned with docsWithField.
  final int added = Math.toIntExact(pending.size() - sizeBefore);
  if (added > 0) {
    docsWithField.addRange(firstDocID, firstDocID + added);
    lastDocID = firstDocID + added - 1;
  }
  updateBytesUsed();
}

Register exactly the values that reached the buffer (validated) (validated by the checks) (recommended)

#

In both addDenseValues methods, remember pending.size() before the bulk add and, in a finally, register as many documents (and, for SORTED_NUMERIC, pendingCounts entries) as values were added, like SortedDocValuesWriter.addDenseOrdinalValues. The registered doc ids are the batch's own documents, which updateBatch deletes right after, so no live document gains a value. +34/-23 lines in two files; the snippet is the NumericDocValuesWriter half.

final long sizeBefore = pending.size();
try {
  pending.add(cursor);
} finally {
  // Register a doc for every value that reached the buffer, even if the cursor threw part-way,
  // so that values stay aligned with docsWithField.
  final int added = Math.toIntExact(pending.size() - sizeBefore);
  if (added > 0) {
    docsWithField.addRange(firstDocID, firstDocID + added);
    lastDocID = firstDocID + added - 1;
  }
  updateBytesUsed();
}

Trade-offs

  • The rejected batch's deleted documents keep values until a merge drops them, as with the per-document path; nothing reads them through live docs.
  • Cost: constant bookkeeping per non-empty dense batch (two size() reads, a subtraction, a Math.toIntExact and a branch); no added work per value on the success path and no extra copy.
  • It relies on Builder.size() counting exactly the completed fill calls, which add(LongValuesCursor) does by construction (PackedLongValues.java:274-276).
  • The finally also runs updateBytesUsed() after a failure; the stock code skips it, so the in-memory segment's RAM accounting misses the kept values until the writer's next successful update.

Make PackedLongValues.Builder.add(LongValuesCursor) atomic

#

On a throw, restore size, pendingOff and the packed pages.

Trade-offs

Not built. Harder than it looks: the loop may already have packed a page that also holds earlier documents' values, so a rollback has to undo a pack or keep a copy.

Fill into a scratch array first, then add

#

Copy the whole batch out of the cursor before touching the buffer.

Trade-offs

Not built. Atomic and simple, but every value is copied once more, which gives up the point of the bulk path.

Treat a cursor exception as aborting

#

Discard the in-memory segment.

Trade-offs

Not recommended: it drops every document since the last flush, against updateBatch's non-aborting handling (#16270) and the recovery Lucene's own test checks.

Downstream note

#

Not a security issue, since only the application's own cursor can throw there, but a multi-tenant service that builds such a cursor from request data could see doc-values filters and sorts apply rejected values to whichever documents are indexed next.

How it was found

#

Semi-formal. A hunt AI tool modelling the columnar dense writers suspected the page loop. A bounded Z3 model found the smallest failing case (255 values in the page, a 2-document batch failing on its 2nd value) and none for batches fitting the page's free slots. A failure-injection sweep on the real jar and a JUnit repro confirmed it.

The method in full208 words

Method: SMT (Z3) model of the dense doc-values page loop, then failure injection on the real jar.

  • The hunt unit covered the columnar addBatch path. Reading the dense writers while modelling them raised the hypothesis; the model (dense_commit.py) encodes PackedLongValues.Builder.add(LongValuesCursor) and the writers' bookkeeping. Property W1, "dense long DV page loop failure-atomic", is violated (sat) with the smallest witness 255 values already in the page and a 2-document batch failing on its 2nd value (1 value kept, 0 documents); no violation for batches that fit in the current page's free slots (unsat). Property W3 found no violation for the dictionary SORTED dense path (batches up to 4096 values). The model is bounded (W1: up to 4 pages, 1,024 values) and counts values and documents only, not buffer contents or RAM accounting.
  • A failure-injection sweep on the stock jar then threw from the cursor at every point of a grid: 301 of 605 points violated for dense NUMERIC and for dense SORTED_NUMERIC, with assertions on and off; 0 of 605 for the sparse long paths.
  • The finder wrote the 2-test JUnit repro and a fix; verifiers then reproduced it with their own tests, and an adjudication re-ran their tests and the finder's with new seeds (Independent checks).

LFV-097, snapshot of 2026-10-30

Registry title

Area
index / columnar addBatch doc values (dense NUMERIC and SORTED_NUMERIC writers)
Priority
Medium, rank 129: Moved down with the addBatch cluster: a throwing dense LongColumn cursor leaves values buffered so every later document of that field in the segment is silently stored with another document's value, surviving merges with CheckIndex clean, but it is an error path of an experimental API whose one known downstream user keeps it off.
Impact class

Impact note
Hits applications that use the experimental IndexWriter#addBatch (10.5.0 and later) with a dense LongColumn feeding NUMERIC or SORTED_NUMERIC doc values (LongField's schema included) whose own values cursor throws a RuntimeException after the field's buffer has completed a 256-value page during the call, and that keep indexing into the same writer before the next flush, the non-aborting recovery path that Lucene's own recovery test exercises; default IndexWriterConfig and codec, ordinary scale (255 earlier documents plus a 2-document batch suffice); every later document of that field in the in-memory segment is then persisted with a wrong value, CheckIndex stays clean, and only reindexing the affected documents repairs it.
Summary
You index a dense LongColumn as NUMERIC or SORTED_NUMERIC doc values with IndexWriter#addBatch, its values cursor throws part-way (for example after 255 earlier documents, a 2-document batch whose cursor fails on its 2nd value), and you keep adding documents to the same writer. You expect what Lucene's own recovery test asserts: the exception propagates, the batch's documents are deleted, and a document added afterwards with value 42 reads back 42. Instead the values the cursor delivered before the throw stay in the doc-values buffer with no document attached, so the good document reads back -1 (a value of the rejected batch) and every later document of that field in the segment is shifted by the same number of values, which survives commit, reopen and forceMerge(1) while CheckIndex finds nothing wrong.
