Numeric sort reads a later segment's points before it knows the query's cost (main and branch_11x since #16857)

Since #16857 (unreleased: main and branch_11x), a numeric-sorted search reads the points of each segment that starts after the 1,000-hit threshold was crossed, even where the query matches one document or none: 1,001 point doc IDs instead of 0 in the repro, roughly 1.5-1.9x slower on a selective 1M-doc segment. Hits stay correct.

The finding in 30 seconds

#

Each segment decides from the query's cost whether reading the sort field's points is worth it. Since #16857 a later segment makes that decision before the cost is known, using the placeholder -1, so it always reads.

Background: how a numeric sort skips documents

#
  1. search(query, n, sort) counts hits exactly up to a threshold, 1,000 by default. Past it, Lucene may skip documents that cannot enter the top n.
  2. For a numeric sort field that is also indexed as points, NumericComparator can ask the points index for the documents whose value still beats the current n-th hit, and then visit only those (a "competitive iterator").
  3. Reading points costs work, so it does that only when the result is at least 8x smaller than what the query itself matches. The query's match count (its cost) arrives with setScorer(); until then the comparator stores -1, meaning "not known yet".

The finding, step by step

#
  1. Index two segments with a LongPoint + NumericDocValuesField field v. Segment 0: 1,001 docs with f:a (v = 1,000 to 2,000). Segment 1: 1,000 docs with f:b (v = 0 to 999) and one f:a doc with v = 1,000,000.
  2. Search f:a, top 10, sorted by v. Segment 0 crosses the default threshold of 1,000 hits, so from now on Lucene may skip documents that cannot beat the 10th value, v = 1,009.
  3. You expect segment 1 to read none of its points: the query matches 1 doc there, and the comparator reads points only when that cuts the documents to check at least 8x. 10.6.0, 10.5.2, 9.12.3 and main before #16857 read 0.
  4. Instead segment 1 reads all 1,001 of its points and builds a set of its 1,000 f:b docs, which the query does not even match. The top 10 is still right; the work is wasted (1,000,001 doc IDs per search for a later segment of 1,000,001 docs).
  5. Why: #16857 tells the comparator "threshold reached" when the segment's collector is created, before setScorer(). The query's cost is still the placeholder -1, so the 8x limit cost >>> 3 becomes 2^61 - 1 and never says no.

Who is affected

#

Users of main or branch_11x (the future 11.0.0) who sort by a numeric points field (a price, a timestamp) with search(query, n, sort) or searchAfter over several segments, default settings. Each later segment pays a points pass over its competitive range, wasted where the query is selective there. Results are correct; no release has it.

Mechanism, terms and numbers844 words

Since #16857 ("Consolidate Sort pruning logic", merged 2026-10-29, on main and branch_11x, in no release), TopFieldLeafCollector's constructor calls comparator.setHitsThresholdReached() when the hits threshold was already crossed in an earlier segment (TopFieldCollector.java:56-59 at 716d6f216f5). The constructor runs before setScorer(). For a numeric sort field indexed as points, that call runs the segment's first competitive-iterator update at once (NumericComparator.java:154-158), while the points builder's iteratorCost is still -1, its "no scorer yet" placeholder (:315). The 8x selectivity threshold iteratorCost >>> 3 (:426) becomes 2^61 - 1, so the "not selective enough to be worth materializing" check (:430-431) never rejects, and the segment intersects its points over the whole competitive range (:441). iteratorCost then holds the new iterator's cost estimate (1,001 here), so setScorer() skips the normal first update with the query's real cost (:346-355).

In the one-method repro, a later segment where the query matches 1 document hands all 1,001 of its points to the visitor; main before #16857, 10.6.0, 10.5.2 and 9.12.3 read 0. It also happens in a segment where the query matches nothing, because IndexSearcher.searchLeaf creates the leaf collector before it asks for a scorer. The top hits are identical in every executed shape. Rough timings on a shared host: 1.5-1.9x on a selective query with a 1M-doc later segment, about +10% for a 2% filter over 10 x 100,000 docs; a 3-line guard restores both.

Terms

#
  • Hits threshold: IndexSearcher#search(query, n, sort) counts hits exactly up to TOTAL_HITS_THRESHOLD = 1,000 (IndexSearcher.java:100). The 1,001st hit switches the collector's totalHitsRelation to GREATER_THAN_OR_EQUAL_TO and calls comparator.setHitsThresholdReached() from countHit() (TopFieldCollector.java:64-77).
  • Competitive iterator: once the threshold is reached and the queue is full, NumericComparator's PointsCompetitiveDISIBuilder intersects the field's points with the range of values that can still enter the top n and hands the collector a doc-ID iterator over the result (NumericComparator.java:363-446).
  • The 8x rule: before intersecting, it estimates the number of points in that range and gives up when the estimate is at least iteratorCost >>> 3: "the new range is not selective enough to be worth materializing, it doesn't reduce number of docs at least 8x" (:426-439). iteratorCost starts as the query's cost, taken in setScorer(): "starting iterator cost is the scorer's cost" (:346-355).
  • The placeholder: private long iteratorCost = -1; (:315) means "not set from the scorer yet" (LUCENE-10555, #864, 2022).

What #16857 changed

#

It added to the TopFieldLeafCollector constructor (TopFieldCollector.java:56-59):

if (totalHitsRelation == TotalHits.Relation.GREATER_THAN_OR_EQUAL_TO) {
  // we only get told when the threshold is crossed, which may have been in a previous segment
  comparator.setHitsThresholdReached();
}

The constructor runs inside getLeafCollector, which IndexSearcher.searchLeaf calls before weight.scorerSupplier (IndexSearcher.java:836, :842), so it runs before setScorer() and even for a segment where the query has no scorer. NumericLeafComparator.setHitsThresholdReached() calls competitiveDISIBuilder.updateCompetitiveIterator() (NumericComparator.java:154-158). The flags it checks, hitsThresholdReached and queueFull, are shared by all segments of the collector (:59-60) and, in the repro, already true, so doUpdateCompetitiveIterator() runs with iteratorCost == -1: the threshold is (-1) >>> 3 = 2^61 - 1, the estimate can never reach it, pointValues.intersect reads the whole competitive range (:441), and iteratorCost becomes the new iterator's cost estimate (:444; 1,001 here). When setScorer() arrives, iteratorCost != -1, so the update with the real cost is skipped (:347).

The call itself is needed. #16857's new IndexSortedLeafFieldComparator keeps its own per-segment hitsThresholdReached flag (IndexSortedLeafFieldComparator.java:35, :91-97). And when the segment that crossed the threshold was index-sorted by the sort field and the search does not page, its comparator is that class (FieldValueHitQueue.java:190-191), which does not pass setHitsThresholdReached() on to its delegate (:91-97), while countHit() makes the call only once per collector (TopFieldCollector.java:70-72): the shared NumericComparator flag stays false, and the constructor call is what turns points skipping on in the next, unsorted segment. An independent check executed that shape: the second segment reads 512 point doc IDs on main, with either fix and on 645d4fe14a20, but 0 with the call deleted (no skipping: 5101+ hits counted instead of 1101+). So the defect is not the call but that, for the points builder, it runs the first update while the cost is still -1. When the earlier segment was not index-sorted, as in the repro, the flag is already set and that early update is the call's only effect on NumericComparator. Before #16857, setHitsThresholdReached() was called only from countHit(), during collect(), after setScorer() (645d4fe14a20 TopFieldCollector.java:87).

In the repro, segment 1's competitive range is v <= 1,008 (the 10th value is 1,009; with a single sort field ties are pruned too, FieldValueHitQueue.java:150). It holds the 1,000 f:b documents, so the intersect visits every one of segment 1's 1,001 points. With the real cost, 1 for f:a there, the threshold is 1 >>> 3 = 0 and nothing is read.

Exposure and likelihood444 words
  • Who. Anyone on main or branch_11x code (so 11.0.0 unless fixed, and downstream projects that build on Lucene snapshots) who calls IndexSearcher#search(query, n, sort) or searchAfter sorted on a numeric field indexed with points plus doc values, over an index with more than one segment. It needs the points builder: the field is the first sort field with pruning on (the default; later sort fields get Pruning.NONE, FieldValueHitQueue.java:146-151) and has points (otherwise the doc-values-skipper builder is used), NumericComparator.java:98-111.

Why it looks unintended

#
  • The comparator reads points only when that cuts the documents to check 8x versus the query's cost; otherwise the range is "not selective enough".
  • -1 is the "no scorer cost yet" placeholder; (-1) >>> 3 = 2^61 - 1 disables the rule by accident.
  • The call serves #16857's index-sort comparator; that PR calls needless iterators from points "redundant work".
The full argument354 words
  • The rule. NumericComparator.java:430-431 (main 716d6f216f5): "the new range is not selective enough to be worth materializing, it doesn't reduce number of docs at least 8x", with threshold = iteratorCost >>> 3 (:426) and the starting cost set in setScorer(): "starting iterator cost is the scorer's cost" (:349). It is an implementation heuristic in a source comment, not a public contract; the report is the measured regression against it.
  • The placeholder. LUCENE-10555 (#11591 "avoid repeated NumericLeafComparator setScorer calls", PRs #864 and #878, 2022) introduced iteratorCost == -1 to mean "not set from the scorer yet". It was never meant to reach the threshold computation.
  • The order is new. On 645d4fe14a20 the production callers of setHitsThresholdReached() are TopFieldCollector.countHit() (:87) and the MultiLeafFieldComparator delegation, both after setScorer(). The only other caller, the unit test TestTermOrdValComparatorAdaptiveSkipping (:145, :192), calls it on a string-sort leaf comparator that never gets a scorer; it does not reach the numeric points builder. #15757 (2026-02) describes the first per-segment update as running from the builder's setScorer(), "by analogy with the points-based version".
  • Purpose of the call. Its comment, "we only get told when the threshold is crossed, which may have been in a previous segment", fits IndexSortedLeafFieldComparator's per-segment flag (IndexSortedLeafFieldComparator.java:35, :91-97) and, after an index-sorted segment, the shared NumericComparator flag; neither needs the points update before the scorer cost is known. That class's comment (:31-33) says that when collection terminates anyway, "the delegate's skipping, e.g. building iterators from points, is redundant work: it measurably slows down index-sorted searches."
  • The PR record. #16857's body, its CHANGES entry ("Sort pruning decisions are now entirely made through the Pruning enum", 11.0.0 API Changes, CHANGES.txt:39-47), MIGRATE.md and all 4 reviews and 4 inline comments say nothing about reading points before the scorer is known. Its one benchmark comment ("no significant difference") ran non-selective tasks.
  • Precedent. #13498, "Avoid performance regression by constructing lazily the PointTree in NumericComparator", is listed under Bug Fixes in 9.11.1 and 10.0.0: avoidable points work in this very comparator was treated as a bug.
The devil's-advocate check211 words

The strongest case for "intended" (built by an intended-behaviour checker and by a reviewer from another model family): no public contract covers this cost. LeafFieldComparator#setHitsThresholdReached says only that it "is called from a collector when hits threshold is reached" (LeafFieldComparator.java:109-113) and orders nothing against setScorer; these APIs are @lucene.experimental; the constructor call is deliberate and commented; and an eagerly built iterator prunes more hits, so it could in principle be faster.

Why it fails: no public contract covers this cost, and an eager iterator can prune more (2005+ instead of 19774+ hits counted in one timed shape). But the call is deliberate for the threshold flag, and no PR record we found discusses whether it should run the points update before a scorer cost is known; fix A keeps the call and drops only that update. The value that reaches the rule is the placeholder, not an estimate. In a segment where the query matches 0 or 1 documents nothing can be gained by building an iterator over 1,000 or 1,000,000 competitive documents. The measured wall-clock is worse with the early read (1.5x to 1.9x, about +10%), and in those runs the 3-line guard restored the old numbers. Being unreleased lowers the priority, not the verdict.

Suggested fix

#

Recommended A: skip the points update until the scorer cost is known

Return early from the points builder's update while its cost is still -1: if (iteratorCost == -1) return; at the top of PointsCompetitiveDISIBuilder.doUpdateCompetitiveIterator() (3 lines). setScorer() then makes the first decision with the query's real cost, as before #16857. With it the test and 11 sort and comparator suites pass (12 classes, 112 tests).

    @Override
    protected void doUpdateCompetitiveIterator() throws IOException {
      if (iteratorCost == -1) {
        return; // no scorer cost yet: setScorer() performs the first update
      }

A: skip the points update until the scorer cost is known (validated by the checks) (recommended)

#

comparators/NumericComparator.java, top of PointsCompetitiveDISIBuilder.doUpdateCompetitiveIterator() (:363), +3 lines:

    @Override
    protected void doUpdateCompetitiveIterator() throws IOException {
      if (iteratorCost == -1) {
        return; // no scorer cost yet: setScorer() performs the first update
      }

Trade-offs

  • setScorer() performs the segment's first update with the real cost (:346-355), as before #16857, while IndexSortedLeafFieldComparator still learns about the threshold from the constructor. A segment with no scorer does no points work.
  • It keeps the constructor call's purposes: setHitsThresholdReached() sets the flag before the update returns (:155), so after an index-sorted segment the next segment still skips (512 point doc IDs read, as on main and 645d4fe14a20).
  • Local to the points builder; the collector protocol is unchanged. The skipped call still increments updateCounter (:235) before it returns, so in each later segment the count runs one ahead of the pre-#16857 code and the sampling that starts after 256 updates (:237-240, :456) shifts by one update. Not measured; for the maintainers to judge.

B: move the constructor's call into setScorer() (validated by the checks)

#

In TopFieldLeafCollector, delete TopFieldCollector.java:56-59 and add the same if (totalHitsRelation == TotalHits.Relation.GREATER_THAN_OR_EQUAL_TO) comparator.setHitsThresholdReached(); right after comparator.setScorer(scorer) (:117).

Trade-offs

  • Restores the "scorer first" order for every comparator and still tells the leaf comparator before its first collect.
  • setScorer() can run more than once per segment: a bulk scorer calls it on every score() call (Weight.java:254), for example once per interval under a query timeout (TimeLimitingBulkScorer), so the call repeats. A segment with no scorer never hears about the threshold, which is harmless because it collects nothing.

Downstream note

#

Downstream services that build on Lucene snapshots and sort by numeric fields pay this extra CPU on selective sorted queries until it is fixed; the hits are unaffected.

How it was found

#

Reading the newly merged #16857 diff for changed call orders, the constructor-time setHitsThresholdReached() call stood out. A probe that counts the points a sorted search reads, run before and after #16857, showed 0 vs 80,000 doc IDs with the same top 10. It was reduced to one test, and the per-segment protocol was modelled in TLA+.

The method in full170 words

Method: non-formal (the first signal came from code reading; the formal model came later).

  • Lead. A lens on newly merged upstream code read the #16857 diff and flagged the constructor call that runs before setScorer().
  • Probe. A differential count with a PointTree wrapper on the public FilterLeafReader API, on the code before #16857 and on upstream main: 0 vs 80,000 point doc IDs read in later segments (5 x 20,000 docs, threshold 10), identical top 10. A skeptic re-run confirmed it.
  • Reduction. The hunt reduced it to one JUnit test (later the one-method test above) and ran it on main code, the commit bracket and three releases, with assertions on and off.
  • Model. A TLA+ model of the per-segment collector and comparator protocol (TLC): the property NoBlindUpdate (no points are read before the scorer cost is known) is violated by upstream main, the shortest trace being a second segment with no scorer; it holds for the code before #16857 and for both fixes, and the vacuity probes are reachable.

LFV-1057, snapshot of 2026-11-06

Registry title
Since #16857 (upstream main and branch_11x, unreleased), a numeric field-sorted search reads a later segment's whole competitive points range before the scorer is set: TopFieldLeafCollector's constructor calls setHitsThresholdReached() while NumericComparator's iteratorCost is still its -1 'no scorer yet' value, so the 8x selectivity check never rejects (1,001 point doc IDs read where releases read 0; performance regression, results correct)
Area
search / field sorting: TopFieldCollector + NumericComparator points-based sort pruning (competitive iterator)
Priority
Low, rank 363: A performance-only regression with correct results on the default numeric-sorted search path, but only in unreleased main/branch_11x code and with measured slowdowns of about 10% to 1.9x, so it is Low.
Impact class
minor
Impact note
Performance regression only, on upstream main and branch_11x since #16857 (no release has it; fixable before 11.0.0), with the default codec, IndexWriterConfig and IndexSearcher: every IndexSearcher#search(query, n, sort) (also searchAfter) sorted on a numeric field indexed with points, over a multi-segment index, runs one points intersect over the competitive range of each segment that starts after the default 1,000-hit threshold was crossed, even where the query matches few or no documents and the 8x rule would have skipped it; the waste per segment is bounded by that segment's points in the range (1,001 doc IDs in the repro, 1,000,001 plus a 1M-bit set for a 1M-doc segment), rough timings on a shared host showed about 1.9x on a selective 1M-doc later segment and about 10% on a 2%-filter 10 x 100k shape (both restored by the one-line fix), and the top hits are identical in every executed shape.
Summary
You run searcher.search(new TermQuery(new Term("brand", "lux")), 10, new Sort(new SortField("price", SortField.Type.LONG))) over two segments: the first has 1,001 hits, so the default 1,000-hit threshold is crossed there, and in the second the query matches one document that cannot compete. You expect the second segment not to read its points, because the comparator builds its competitive iterator from points only when that cuts the query's own cost at least 8x; 645d4fe, 10.6.0, 10.5.2 and 9.12.3 read 0 point doc IDs there. Instead, since #16857 the new leaf collector tells the comparator about the threshold before setScorer(), while its cost is still the -1 'no scorer yet' value (so the 8x limit becomes 2^61-1), and it intersects the whole competitive range, 1,001 doc IDs; the top 10 is still right, only the work is wasted.
