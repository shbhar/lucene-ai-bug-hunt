The finding in 30 seconds

#

Test infrastructure only. In the 10.6.0 sources ./gradlew :lucene:distribution.tests:test -Ptests.gui=true reports 9 tests, 1 skipped: the Luke launch test stays off although the option is on. On main 01deb8e63e0b and branch_11x daa54f2e0cd3 a one-method test that expects the option in the test JVM fails 1 of 1, assertions on and off.

  1. You have the 10.6.0 sources and want Lucene's check that the binary distribution's bin/luke script starts. It is the one test of the group @RequiresGUI, which is off by default. You switch the group on with its build option: ./gradlew :lucene:distribution.tests:test -Ptests.gui=true.
  2. You expect the module's 9 tests to run. The option's description is "Enables or disables @RequiresGUI tests.", and from 9.3.0 to 10.5.2 the option did that.
  3. You get 9 tests, 1 skipped and BUILD SUCCESSFUL. The skipped test is TestScripts.testLukeCanBeLaunched: "'requiresgui' test group is not enabled". The same with -Dtests.gui=true and on a CI build, where the option is on by default. The build's own option listing still prints tests.gui = true.
  4. Why: the build resolves the option and then drops it. It passes to the test JVM only the options named in one set. tests.nightly, tests.monster and tests.awaitsfix are in the set; tests.gui is not. The test group looks for the system property tests.gui inside the test JVM, finds none and stays off.
  5. Main and branch_11x miss the same line: a one-method test that expects the property in the test JVM fails 1 of 1 there, assertions on and off. With one added line it passes, and the 10.6.0 run reports 9 tests, none skipped. On main and branch_11x the Luke test also lacks its @Test (LFV-389, a separate finding) and needs both repairs.

Who is affected

#

Only those who run Lucene's own build with the option on: a developer, CI builds (on by default there) and the Gradle command of the release smoke test, which sets it. No user of Lucene's jars. The skipped test passed in every run made here, so nothing is known to be broken; one intended check does not run.

Mechanism, terms and numbers1,099 words

Lucene's Gradle build has an option, tests.gui, whose description is "Enables or disables @RequiresGUI tests.". One test is in that group: TestScripts.testLukeCanBeLaunched, which starts the Luke launch script of the binary distribution and checks that Luke comes up. The option is off for a developer by default, on by default on CI builds, and the Gradle command of the release smoke test sets it.

Since the build moved from scripts to convention plugins, the option is still declared and resolved, but it is no longer passed to the JVM that runs the tests. The test group reads a system property of that JVM, so switching the option on has no effect on the test. In the 10.6.0 sources the test is reported as skipped while the build succeeds and prints the option as true. Main and branch_11x (both unreleased) miss the same line; there the test method also lacks its @Test since #16028 (LFV-389, a separate finding), so the stock tree does not find the test at all.

This is not a defect of a Lucene class, and not of Luke or its launch script: the test passed in every run made here (one Linux host, no display), so nothing is known to be broken behind it. No jar, API or index format is involved, and no user of Lucene's jars can meet it. What was lost is one check that CI builds and the release smoke test's Gradle command were meant to run. From 9.3.0, the first release with the option, to 10.5.2 it worked. It is not new in 11.0: the 10.6.0 source release has it, and the 11.0 branch has it too. The repair is one added line in the build plugin.

More files, environment, full output703 words

The test names the constant that the @RequiresGUI group reads (AbstractLuceneDistributionTest.SYSPROP_REQUIRES_GUI), so it belongs into the module's test sources and runs with the module's test task. No index, no process, no randomness, one thread. The build option always has a value (false by default, true on CI builds), so a build that passes it gives the test JVM the property in every run: the test checks that the option is delivered, not which value it has. A regression test for the repair is this same test; like the module's other tests it passes only under Lucene's Gradle build, which sets the properties they read.

A JUnit launcher outside the build cannot show this defect: it starts the test JVM itself, where the property is absent on every tree, repaired or not. So "assertions on and off" are the build's -Ptests.asserts=true and false.

The runs for this page added --no-daemon --max-workers 4 --offline -Ptests.jvms=1 -Ptests.seed=D0C1522A, which limit resources, keep Gradle offline and without a daemon, and fix the seed (the test does not use it), and removed CI from the environment. None of them changes the result.

Why it looks unintended

#
  • Still declared: "Enables or disables @RequiresGUI tests.", default true on CI builds. The build shows its value and passes it nowhere.
  • 9.3.0 to 10.5.2 passed it to the test JVM. Neither #14764 nor its backport #16592 lists the change.
  • The same refactoring lost tests.seed the same way; that was repaired as a regression with one line (#14876).
The full argument392 words
  • The option's own text and default. TestsAndRandomizationPlugin.java:292-295: "Enables or disables @RequiresGUI tests.", default true on CI builds. The build shows the option (its option listing, the "Reproduce with" line of a failed test) and nothing acts on its value. A declared option with a description, a CI default and no effect on any test reads as an omission.
  • The pull request that added it states the behaviour. #893 (LUCENE-10531, Tomoko Uchida, merged 2022-05-18), description: "On CI build, tests.gui sysprop is forced to set true to run GUI tests." It shows both runs: with -Dtests.gui=false, "8 test(s), 1 skipped // TestScripts is skipped."; with -Dtests.gui=true, "8 test(s)". Their closing comment of 2022-05-17: "we disabled the GUI test in the mandatory test runs, instead, we enabled it on nightly CI runs (Jenkins, GH Actions) and the smoke tester."
  • The smoke test's line is still there. smokeTestRelease.py:1176-1177: "# We also enable GUI tests in smoke tests (LUCENE-10531)", testArgs = "-Dtests.gui=true %s" % testArgs.
  • It worked before. At the 10.5.2 tag gradle/testing/randomization.gradle:95-99 lists tests.gui as a test option, and :178 passes every resolved option to the test JVM: systemProperties testOptionsResolved. (The script marks three other options buildOnly and not this one. The mark carries little: nothing in that tree reads it, and the marked options were passed too.) Earlier runs of the tags 9.3.0, 9.12.3 and 10.5.2 through their own build: the option reaches the test JVM and the Luke test runs.
  • Neither introducing change lists it. #14764's section "Tweaks to properties and options" names two changes (runtime.java.home; tests.neverUpToDate renamed to tests.rerun). Its description says "most of the code remains identical as in main, it is just moved, reshuffled or slightly modernized" and "I am looking for regressions". Neither description has the words gui or luke.
  • Precedents from the same refactoring. Dawid Weiss's #14876, "Test tasks are not populated with tests.seed (regression)" ("A regression after #14764"), was closed by commit cbb1c479252, whose whole change is one line: optionsInheritedAsProperties += [ "tests.seed" ]. Also their #14944, "Enable tests.haltonfailure (regression on main)".
  • The design discussion wanted the test to keep running somewhere. Dawid Weiss on #11564 (LUCENE-10528, 2022-04-21): "But we want to run this test occasionally, don't we? If we disable it completely then it will stop testing if Luke can be actually launched (and nothing fails)."
The devil's-advocate check356 words

The strongest case for "intended": the new plugin passes an explicit set of options where the old script passed all of them, and the old script carried the comment "TODO: we could remove some options that are only relevant to the build environment and not the test JVM itself" (randomization.gradle:176-177 at 10.5.2). Leaving an option out is what such a set is for. The documented test-group filter (-Ptests.filter=@RequiresGUI) still runs the test. The test has a record of trouble: it opened a window on developers' desktops (#11564) and timed out at times on Windows CI runners (#893's thread, #917), so not running it automatically may be welcome to some. The refactoring's author repaired three other regressions of the same refactoring in 2025 and not this one. And no user of Lucene is affected.

What answers it. (1) tests.gui is not an option of the build environment: nothing in the build acts on its value, so leaving it out of the set does not move its effect into the build, it removes the effect. (2) A decision to retire the option would have removed its declaration, its CI default and the smoke test's line; all three are still in the tree, and no change or thread says the option was retired. (3) The CI default and the smoke test's Gradle command set the option, not the filter, so the runs that the 2022 design named for this test (CI builds, the smoke test) no longer start it through the option. (4) The refactoring's author repaired the same kind of omission as a regression for tests.seed. The record does not settle two points of the case: whether the test's history of trouble makes the skip welcome to some, and why this omission stayed while three siblings were repaired (the build stays green, so nothing drew attention to it). They make the case for "intended" more than a weak one; the declaration, the description, the CI default and the smoke test's line still read as an unintended regression. The last point of the case is about weight, not intent: it is why this is Low.

  • CI builds start bin/luke again in the distribution tests, because the default there is true. That is the state before the refactoring.   • Not run: Lucene's whole gradlew check, a host with a display or with xvfb-run, x86, Windows, macOS, the release smoke test script itself, a real CI job.

How it was found

#

A run of the Luke launch test with the option on reported it as skipped. A scan of the build plugin then listed every declared test option against the set that is passed to the test JVM: tests.gui is the only declared option whose whole effect was that system property. Runs of the build on three trees confirmed it.

The method in full244 words

Method: non-formal (a static scan confirmed by executed runs of the build; no model checking, constraint solving or proof applies to a missing line of build configuration).

  • Signal. While the Luke launch test was checked for another finding (LFV-389), a Gradle run with the option on and one with CI=true both skipped the test, although its @Test had been put back for those runs. It was noted as a separate matter and taken up later.
  • Scan. The declared options of the build plugin were listed against the names in optionsInheritedAsProperties: on branch_11x and main 39 declared options, 26 passed to the test JVM, 13 not. Of the 13, tests.gui is the only one whose whole effect was the system property of the test JVM. Eleven of the other twelve are read by the build itself; the twelfth, tests.file.encoding, is read by nothing and had no reader in any earlier release tag that was checked (an older matter, not claimed here). Of the five test groups that have a system property, the build declares four and passes three.
  • Witness. One test, the same source on every tree: the test JVM has the property tests.gui. It fails on the 10.6.0 tag, branch_11x and main and passes with one added line.
  • Since when. git log -S for the option and for systemProperties testOptionsResolved, then runs of both introducing commits and their parents and of the release tags 9.3.0, 9.12.3 and 10.5.2.
