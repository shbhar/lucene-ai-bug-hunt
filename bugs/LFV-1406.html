An NRT reader opened with applyAllDeletes=false starts a merge that drops a tryUpdateDocValue un-delete while another thread's older delete is still being applied

tryUpdateDocValue un-deletes a soft-deleted document and returns success. If another thread is still applying an older delete, the next NRT open with applyAllDeletes=false runs a merge that still sees the document as deleted and drops it: the commit has 0 hits for it (8.7.0 to main).

The finding in 30 seconds

#

IndexWriter numbers every delete or update packet with a delete generation and tracks the highest one up to which all packets have finished. An NRT open with applyAllDeletes=false writes pending doc-values updates only up to that number, and its merge-on-refresh merge reads the segments right then. An un-delete made while an older packet is still open is not written yet.

Background: soft deletes, delete generations and merge-on-refresh

#
  1. With setSoftDeletesField("soft"), a document with a value in the soft doc-values field counts as deleted but stays in its segment until a merge leaves it out. tryUpdateDocValue(reader, docID, soft = null) removes the value: the documented un-delete.
  2. Every delete or update gets a delete generation (delGen) and is applied as a packet, often by another indexing thread. The writer tracks completedDelGen, the highest delGen up to which every packet has finished, and writes doc-values updates to disk only up to it.
  3. DirectoryReader.open(writer, applyAllDeletes, ...): with true the open first waits for every packet; with false it does not. Either way, since 8.7.0 the open can also run small "merge-on-refresh" merges (on by default since 9.3.0), whose readers are pulled during the open.

The finding, step by step

#
  1. Turn on soft deletes, index a and b into one segment, soft-delete a and open an NRT reader: 1 of 2 documents is live. Another thread runs deleteDocuments(id:nothing) and is still applying that delete (packet 3).
  2. Un-delete a with tryUpdateDocValue(reader, 0, soft = null): it returns 9. Its update is generation 5, but the writer writes updates to disk only up to generation 2, the last one with no unfinished packet before it.
  3. Open DirectoryReader.open(w, false, false). You expect a reader that may still hide a, while the writer keeps the change: with false, "the deletes are not applied but remain buffered (in IndexWriter) so that they will be applied in the future", and the open skips doc-values updates under the same flag.
  4. Instead the open's merge-on-refresh merge pulls readers that still see a as deleted. The merged segment keeps only b, and the writer's own maxDoc drops from 3 to 2.
  5. A fresh NRT reader and the commit (sequence number 11) have 0 hits for a. No error. With the default open (applyAllDeletes=true) the same steps keep a.

Who is affected

#

Applications that turn on soft deletes (off by default), restore documents with the Expert tryUpdateDocValue null reset and refresh NRT readers with the Expert applyAllDeletes=false, while other threads delete or update. Merge-on-refresh is on by default since 9.3.0. The loss is silent and survives commit. Rare: at the paths inspected, Elasticsearch, OpenSearch and Solr open with applyAllDeletes=true.

Mechanism, terms and numbers827 words

With a soft-deletes field, IndexWriter#tryUpdateDocValue(reader, docID, <soft-deletes field = null>) un-deletes a soft-deleted document and returns a sequence number > 0. If another indexing thread is at that moment still applying an older global packet (a delete by term or query, a doc-values update, softUpdateDocument), the un-delete is finished out of order and stays above the writer's completed delete generation. An NRT open with applyAllDeletes=false does not wait for that packet, so it writes doc-values updates only up to the completed generation and the un-delete stays in memory. Since 8.7.0 that open also starts the full-flush (merge-on-refresh) merges, and those merges pull their readers at once: the readers see the document as deleted, the merge leaves it out, and the merged segment replaces the source segment in the writer itself. A fresh NRT reader and the next commit have 0 hits for the document, and nothing throws.

In the repro the call returns 9, the writer's maxDoc drops from 3 to 2 at the open, and the commit (sequence number 11) has 0 hits for the document; with the default open the same steps keep it. It needs the opt-in soft-deletes field, the Expert un-delete, the Expert applyAllDeletes=false open and concurrent indexing, so it is rare, but it is silent loss of an acknowledged write on every release run from 8.7.0 (merge-on-refresh turned on) and 9.3.0 (default merge settings) through 10.6.0, and on main. It is a second path to the loss of LFV-1399: same ingredients, a different place where the merge readers are pulled, and each minimal fix leaves the other's test failing. Running the point-in-time merge-on-refresh merges only when applyAllDeletes is true fixes the repro and keeps 15 nearby core suites green.

The bug, step by step (main 5adff78bb168; numbers from a diagnostic copy of the repro, which adds one default NRT open before the commit)

#
  1. The un-delete is finished out of order. tryUpdateDocValue takes a new delGen (bufferedUpdatesStream.getNextGen(), IndexWriter.java:1729), records the reset (:1770), adds it to the segment's pending updates (rld.addDVUpdate, :1775) and marks that delGen finished at once (finishedSegment(nextGen), :1778). It returns sequence number 9.
  2. The completed generation only moves over a gap-free run. finishedSegment advances completedDelGen while completedDelGen + 1 is finished (BufferedUpdatesStream.java:340-350). The other thread's delete packet, delGen 3, has been applied but not finished, so the log says "finished packet delGen=5 now completedDelGen=2".
  3. The no-apply open neither waits nor writes it. getReader calls applyAllDeletesAndUpdates() only if applyAllDeletes (IndexWriter.java:595-597), then writeReaderPool(writeAllDeletes) (:608), and ReaderPool.writeAllDocValuesUpdates writes only updates up to completedDelGen (ReaderPool.java:244-258). 5 > 2, so the reset stays in memory.
  4. The open still starts point-in-time merges. if (maxFullFlushMergeWaitMillis > 0) (IndexWriter.java:619; 500 ms by default since 9.3.0, IndexWriterConfig.java:108) calls preparePointInTimeMerge(..., MergeTrigger.GET_READER, ...) (:633-648) without looking at applyAllDeletes.
  5. Its merge readers are pulled at once. preparePointInTimeMerge calls merge.initMergeReaders with rld.getReaderForMerge (IndexWriter.java:4077-4088) under the writer lock, before the merge's mergeInit; the wrapper pulls them only once (:4047-4056). getReaderForMerge uses the live docs of pendingDeletes (ReadersAndUpdates.java:1093-1107), which reflect a soft-delete value only once it is written: a is deleted for the merge.
  6. mergeInit comes too late. When the merge runs, mergeInit logs "waitApplyForMerge: 0 packets". LFV-1399's fix makes mergeInit wait for the older packet, but the readers were already pulled, so the loss stays: the independent reproducer's trace with that fix logs "waitApplyForMerge: 1 packets" and still loses a. This test with that fix fails too, but only after its 60 s latch timeout, because the merge now waits for the parked thread.
  7. The writer loses a. The merged segment (maxDoc 1, only b) replaces the source segment in the writer, not only in the returned reader: the writer's doc stats drop from maxDoc 3 to 2. The reset cannot be carried over because a maps to -1. A fresh default NRT reader and the commit (sequence number 12 in the diagnostic copy, which opens that extra reader first; 11 in the repro) have 0 hits for a; a plain DirectoryReader.open(dir) on the commit has no a either.

Control. With open(w, true, false) the open waits ("waitApply: 1 packets"), completedDelGen reaches 5, the reset is written before the readers are pulled, the merge keeps 2 documents and the commit has 1 hit for a.

Why the eager pull is safe elsewhere. Merge-on-commit (8.6.0) pulls its readers the same way, but commit always applies all deletes and updates first. LUCENE-8962 reused the pull for getReader, where deletes are applied only when applyAllDeletes is true.

Only the un-delete was lost in the probe. In the intended-behaviour probe, the four other operations tried in the same window (a tryDeleteDocument, a soft delete and a value update through tryUpdateDocValue, a buffered delete) survived: the merge kept or dropped those documents as their latest state says.

Exposure and likelihood415 words
  • Opt-in, three times. Soft deletes are off by default (IndexWriterConfig.java:561); tryUpdateDocValue is Expert (IndexWriter.java:1708); the applyAllDeletes=false open is Expert and @lucene.experimental (DirectoryReader.java:126-139). It is reached through DirectoryReader.open(w, false, false) or openIfChanged(reader, w, false) (which loses the document too), and, by reading (not run), through a SearcherManager/ReaderManager built with applyAllDeletes=false: both open with DirectoryReader.open(writer, applyAllDeletes, writeAllDeletes) (SearcherManager.java:127, ReaderManager.java:62) and refresh with the same flags.
  • Default merge settings since 9.3.0. LUCENE-10078 set the full-flush merge wait to 500 ms and gave TieredMergePolicy and LogMergePolicy a findFullFlushMerges. A test with a default IndexWriterConfig (plus the soft-deletes field) and no InfoStream, where another thread runs a delete-by-query whose test query sleeps 300 ms on its first segment and matches nothing, lost the document 10 of 10 times with applyAllDeletes=false and kept it 10 of 10 times with the default open (main; also main with assertions off and 10.6.0). It is timing-based and uses an artificially slow query, so it shows the loss is reachable without the hook; it does not measure how often it happens, and it is not the repro. From 8.7.0 to 9.2.x it needs setMaxFullFlushMergeWaitMillis > 0 and a policy with full-flush merges.
  • What it takes. The un-delete and the open both inside the time another thread of the same writer is still applying an older global packet (a delete by term or query, a doc-values update, softUpdateDocument), and the open's merge selects the document's segment. A slow delete-by-query widens the window.
  • Not a test artefact. ConcurrentMergeScheduler loses the document too: the point-in-time readers are pulled on the opening thread. 3 documents suffice.
  • Silent and durable. The call reports success, the open returns normally, and after the commit no copy of the document is in the current commit point. Getting it back needs a copy from outside that commit (an older retained commit, a backup, or the application's own source), if the application notices.
  • How likely. Rated rare. At the paths inspected, Elasticsearch, OpenSearch and Solr open NRT readers with applyAllDeletes=true, and the recorded code searches found none of them calling tryUpdateDocValue. Searches cannot prove absence.
  • Workarounds. Open NRT readers with applyAllDeletes=true; or setMaxFullFlushMergeWaitMillis(0) (the probe with wait 0 keeps the document on 8.7.0 and 9.2.0); or a SoftDeletesRetentionMergePolicy that keeps every document the application may un-delete (a retain-all control keeps it). The first two avoid only this path, not LFV-1399's (an explicit merge in the same window).

Minimal repro

Fails on main, passes with the fix.

More files, environment, full output446 words

Two threads, because concurrency is the bug; latches, no sleeps. The second thread is parked on the writer's own InfoStream message "done inner apply del packet" (printed after its packet is applied and before it is finished) and released after the no-apply open. InfoStream is @lucene.internal and its message text is not an API contract; the default-config slow delete-by-query test (see the checks) reaches the same loss with no hook. NoMergePolicy wrapped to merge the first segment on GET_READER, and SerialMergeScheduler, only make the merge deterministic: ConcurrentMergeScheduler loses the document too.

The final count reads the commit through SoftDeletesDirectoryReaderWrapper, so a document that is present but still soft-deleted cannot pass; keep that wrapper if the test is changed. It failed with every seed tried: DEADBEEF (assertions on and off), 10 random seeds, and fresh seeds in each re-check. As the regression test: this same method, unchanged; it passes checkGoogleJavaFormat. With a fix that makes the open wait for the in-flight packet instead (option B), the test would wait for its 60 s latch timeout and then pass (by reading); release the thread on a non-zero waitApply: message for that variant. LFV-1399's fix makes the merge wait the same way; with it the test fails after the timeout (61.7 s).

Why it looks unintended

#
  • Javadoc: if the segment "has not been merged away" the call succeeds (> 0), "else, it returns -1". No merge existed; it returned 9.
  • applyAllDeletes=false: deletes "remain buffered (in IndexWriter) so that they will be applied in the future" (updates likewise). Here the writer discards one.
  • The default open keeps the document; only the skipped wait loses it.
The full argument267 words
  • Contract. tryUpdateDocValue (IndexWriter.java:1707-1715): "If the provided reader is an NRT reader obtained from this writer, and its segment has not been merged away, then the update succeeds and this method returns a valid (> 0) sequence number; else, it returns -1 ... This can be used to un-delete a soft-deleted document".
  • The open's contract. DirectoryReader.java:131-135: "If false, the deletes are not applied but remain buffered (in IndexWriter) so that they will be applied in the future." It allows a stale reader, not a writer that throws the change away.
  • The feature's limit. CHANGES 7.4, LUCENE-8298 (lucene/CHANGES.txt:7460-7463): "This allows to undelete a soft-deleted document unless it's been claimed by a merge." Nothing had claimed a when the call returned.
  • Sequence numbers. commit(): "All sequence numbers <= this value will be reflected in the commit" (IndexWriter.java:4207-4209); the repro's commit is 11 (12 in the diagnostic copy), the un-delete 9.
  • The point-in-time merge's own javadoc (IndexWriter.java:3937-3947) leaves out only updates "made to documents in the merged segment while it was merging", and only from the point-in-time reader. The un-delete came before the open, and the loss reaches the writer.
  • Upstream's own use. TestSoftDeletesRetentionMergePolicy#testUndeleteDocument (:595-625) un-deletes with the null reset under a plain LogDocMergePolicy. No test, CHANGES entry or javadoc says an applyAllDeletes=false open may discard an acknowledged update.
  • History. Full reads of the LUCENE-8962 threads that added merge-on-getReader (#10005, apache/lucene-solr#1623 with its review comments) found no mention of applyAllDeletes=false or un-deletes, and its getReader comment lists "apply all deletes & updates" as a step (IndexWriter.java:567-581).
The devil's-advocate check193 words

The strongest case for "intended": IndexWriterConfig#setSoftDeletesField still says "Currently there is no API support to un-delete a soft-deleted document. In order to un-delete a document, it must be re-indexed using softUpdateDocument" (IndexWriterConfig.java:557-559); applyAllDeletes=false is Expert and trades the returned reader's accuracy for speed; and the repro opens the window through the @lucene.internal InfoStream.

Why it fails: the IndexWriterConfig sentence came with LUCENE-8233 (main ecc17f90233, 2018-04-04), a month before LUCENE-8298 (main a3c86373e47, 2018-05-07) added the un-delete and the contradicting tryUpdateDocValue sentence, so it predates the un-delete and now conflicts with the method's own javadoc (worth clarifying with the bug). The applyAllDeletes=false trade-off is about what the returned reader shows ("if your app can tolerate deleted documents being returned"), and its javadoc promises the changes are applied later; here they never are. The InfoStream hook only parks the other thread inside its normal in-flight interval (after its apply, before its finish, IndexWriter.java:6612); a slow delete-by-query reaches the same loss with no hook.

What a maintainer could still say: "do not combine un-deletes with applyAllDeletes=false". Nothing documents that, the call returned success, and the default open keeps the document.

Suggested fix

#

Recommended A: no point-in-time merge for an applyAllDeletes=false open (validated)

Run the point-in-time merge-on-refresh merges only when the open applies all deletes: if (maxFullFlushMergeWaitMillis > 0 && applyAllDeletes) in IndexWriter.getReader (+4/-1 with a comment). The repro passes; 15 nearby suites and the core index package (1,398 tests) stay green. Trade-off: no point-in-time merges for applyAllDeletes=false opens; LFV-1399 needs its own fix.

// IndexWriter.getReader
// Point-in-time merges pull their readers right away, before mergeInit. Without
// applyAllDeletesAndUpdates, a finished but unwritten doc-values update (e.g. a
// tryUpdateDocValue un-delete) is invisible to them and the merge drops its document.
if (maxFullFlushMergeWaitMillis > 0 && applyAllDeletes) {

Four options. A was validated by running the repro and the nearest suites in a scratch worktree of 5adff78bb168; D ran only as an experiment; B and C were not run. A: no point-in-time merge for an applyAllDeletes=false open (validated) (recommended)

#

One condition in getReader (IndexWriter.java:619): start the merge-on-refresh merges only when the open has waited for and written every packet (applyAllDeletes). Then no merge reader is pulled while a finished un-delete is still unwritten; the merge happens later, through mergeInit, or at the next default open.

// IndexWriter.getReader
// Point-in-time merges pull their readers right away, before mergeInit. Without
// applyAllDeletesAndUpdates, a finished but unwritten doc-values update (e.g. a
// tryUpdateDocValue un-delete) is invisible to them and the merge drops its document.
if (maxFullFlushMergeWaitMillis > 0 && applyAllDeletes) {

Trade-offs

  • Fewer merges on refresh. It turns off the point-in-time GET_READER merges for every applyAllDeletes=false open, also when nothing is in flight, so such readers may see more small segments. The ordinary FULL_FLUSH merge check at the end of getReader (IndexWriter.java:704-706) still runs. Performance impact not measured.
  • Scope. It does not fix LFV-1399 (an explicit merge in the same window): LFV-1399's test still fails with it, and LFV-1399's fix leaves this test failing (after the test's 60 s latch timeout, since that fix makes the merge wait for the parked thread).

B: wait for older packets before pulling point-in-time readers (not run)

#

Before preparePointInTimeMerge, wait (outside the IndexWriter lock) for in-flight packets older than any finished but unwritten doc-values update of the selected segments, then write those updates. Keeps merge-on-refresh for no-apply opens.

Trade-offs

Adds waiting to the applyAllDeletes=false open, which its users chose to avoid; the open runs under the full-flush lock, so the waiting point needs care.

C: leave such segments out of the point-in-time merge (not run)

#

When building the point-in-time merge spec, skip segments that have finished but unwritten doc-values updates above completedDelGen. Narrow and cheap; those segments merge later.

Trade-offs

Needs a new query on the reader pool under the writer lock; the merge policy's choice is silently narrowed.

D: a commit-time guard shared with LFV-1399 (experiment only)

#

Make commitMerge abort a merge that dropped a document which is live in its source's latest state. In the enumeration probe it fixes this path and LFV-1399's together. The only option here that covers both paths.

Trade-offs

Wasted merge work and retries; a scan at merge commit when soft deletes are on; not run against the test suites.

Downstream note

#

Products that let users restore soft-deleted records through tryUpdateDocValue and refresh with applyAllDeletes=false can lose a restore their own API already confirmed, with no error to report.

How it was found

#

A semi-formal differential enumeration on the real IndexWriter held another thread's update packet in flight and ran each consumer of a pending un-delete (merges, commit, NRT opens and reopens with and without applying deletes, flush, close) with an every-step state trace. Only the applyAllDeletes=false cases lost the document beyond LFV-1399's paths; it was minimised to one JUnit test.

The method in full163 words
  • Method (semi-formal). A differential enumeration on the real IndexWriter that extends LFV-1399's held-packet set-up to a set of consumers of the pending un-delete: an explicit merge, merge-on-commit, NRT opens and reopens with and without applying deletes, a RAM-pressure flush, close, and retention merge policies that keep or do not keep the document, with no-hold controls and an IndexWriter state trace after every step. The applyAllDeletes=false cases were added from code reading (getReader skips the apply step when applyAllDeletes is false, and the point-in-time merge pulls its readers before mergeInit). The default opens and reopens kept the document; the no-apply open and reopen lost it.
  • Minimisation. Minimised to a latch-driven JUnit test (two threads, no sleeps), then cut to one method with a soft-deletes-aware final count.
  • Checks. An independent reproducer wrote its own test from the claim; a per-step trace confirmed the delete-generation numbers and the writer's maxDoc drop at the open; each minimal fix was run against both this test and LFV-1399's.

History

#

Introduced in 8.7.0 by LUCENE-8962 "Merge segments on getReader" (main 8294e1ae206, branch_8x 2f2146aad46, 2020), which starts point-in-time merges in every open with a non-zero wait, also with applyAllDeletes=false. LUCENE-10078 made that the default in 9.3.0. Lost on every release run from 8.7.0 (opt-in before 9.3.0) through 10.6.0 and on main; 8.6.3 keeps the document.

Versions tested5 rows

It made getReader call preparePointInTimeMerge(GET_READER) whenever the full-flush merge wait is above 0, also when applyAllDeletes is false, and that call pulls the merge readers before mergeInit.   • Older pieces: the skip of applyAllDeletesAndUpdates for applyAllDeletes=false (LUCENE-7868, 58105a203a19, 2017); the eager reader pull of merge-on-commit (LUCENE-8962 #1617; main 7f352a96659, branch_8x 9b1c92809e7, first released in 8.6.0), safe there because commit applies everything first; the un-delete (LUCENE-8298; main a3c86373e47, 7.4.0 carries 0c65af048b3).
  • Default exposure: LUCENE-10078 (#921; main b5795db0cf5, branch_9x 7d9de759f24, 2022-06-07, first released in 9.3.0) turned merge-on-refresh on by default with a 500 ms wait. It changed who reaches the defect, not the defect.

LFV-1406, snapshot of 2026-11-09

Registry title
An NRT reader opened with applyAllDeletes=false starts a merge-on-getReader merge whose readers miss a tryUpdateDocValue un-delete that returned > 0 but is not yet written (another thread's older update packet is still being applied), so the merge drops the document and the next commit persists the loss (since 8.7.0; with the default merge settings since 9.3.0)
Area
index / soft deletes (tryUpdateDocValue un-delete vs. merge-on-getReader of an NRT open with applyAllDeletes=false: IndexWriter.getReader, IndexWriter.preparePointInTimeMerge, ReaderPool.writeAllDocValuesUpdates, ReadersAndUpdates.getReaderForMerge)
Priority
Low, rank 268: In every release since 9.3.0 with the default merge settings, and since 8.7.0 with merge-on-getReader turned on, a tryUpdateDocValue un-delete that returned success can be silently dropped by the merge that an NRT open with applyAllDeletes=false starts, and the next commit makes the loss permanent. It is Low because it needs the opt-in soft-deletes field, two Expert calls used together (the un-delete and the applyAllDeletes=false open, neither found in Elasticsearch, OpenSearch or Solr) and another indexing thread still applying an older delete or update at both moments.
Impact class
data corruption
Impact note
Hits applications that enable the opt-in soft-deletes field, restore soft-deleted documents with the Expert IndexWriter#tryUpdateDocValue (soft-deletes value null, the documented un-delete) without a retention query (SoftDeletesRetentionMergePolicy) that keeps them, and open or refresh NRT readers with applyAllDeletes=false (DirectoryReader.open(writer, false, false), openIfChanged(reader, writer, false), or a SearcherManager/ReaderManager built that way), when another of their indexing threads is still applying an older global update packet (a delete by term or query, a doc-values update, softUpdateDocument) at both the un-delete and the open, and that open's merge-on-getReader merge selects the document's segment: no error, the writer itself drops the document and the next commit persists the loss, with -ea and -da, at ordinary scale, with the default IndexWriterConfig merge settings since 9.3.0 and with merge-on-getReader turned on since 8.7.0 [exec].
Summary
With a soft-deletes field, you restore a soft-deleted document a with tryUpdateDocValue(reader, docID, <soft-deletes field = null>), which returns a sequence number > 0 while another thread is still applying an older delete, and then open an NRT reader with DirectoryReader.open(writer, false, false). You expect what the javadocs promise: that reader may not show the restore yet, but unapplied changes 'remain buffered (in IndexWriter) so that they will be applied in the future', so a is in the next commit. Instead the open's merge-on-getReader merge reads a as still deleted and drops it from the writer, so the next commit, a fresh NRT reader and a re-open all have count(id:a) = 0, and nothing reports an error.
Introduced
8294e1ae206 on main and its branch_8x change 2f2146aad46 (first released in 8.7.0): LUCENE-8962 'Merge segments on getReader' (apache/lucene-solr#1623, merged 2020-08-24; s1monw, co-authored by mikemccand; JIRA migrated as apache/lucene#10005) [read: diff, blame and git log -S/-L in the full-history clone; no commit-level build] [exec at release level: 8.6.3 keeps the document because getReader runs no point-in-time merge there; 8.7.0 loses it]. It made getReader call preparePointInTimeMerge(GET_READER) whenever maxFullFlushMergeWaitMillis > 0, also when applyAllDeletes is false, and that call pulls the merge readers at once, before the merge's mergeInit; with applyAllDeletes=false getReader skips applyAllDeletesAndUpdates (code from LUCENE-7868, 58105a203a19, 2017) and writes doc-values updates only up to completedDelGen, so a finished un-delete above completedDelGen is missing from those readers. The eager reader pull itself is older (merge-on-commit, LUCENE-8962 #1617, main 7f352a96659 and branch_8x 9b1c92809e7, first released in 8.6.0) but safe there, because commit always applies all deletes and updates first. Required ancestor: the null reset that makes the un-delete possible, LUCENE-8298 (main a3c86373e47; 7.4.0 carries 0c65af048b3). Default exposure: LUCENE-10078 (b5795db0cf5 on main, 7d9de759f24 on branch_9x, apache/lucene#921, first released in 9.3.0) set the default full-flush merge wait to 500 ms and gave TieredMergePolicy and LogMergePolicy a findFullFlushMerges; it changed who reaches the defect, not the defect.
