Monitor.purgeCache after a failed register drops a query that the next commit still stores

After a Monitor.register fails on an I/O error late in its commit, a cache purge (default: every 5 minutes) and a successful update of another query leave a query that getQueryIds() lists but match() never reports, until a reopen or re-register. Since 8.2.0; needs a query-index Directory that can fail.

The finding in 30 seconds

#

The purge rebuilds the query cache from what the searcher shows. After a failed commit the searcher lags behind the IndexWriter, so the purge drops a query the IndexWriter still holds; the next commit stores it with no cache entry, and match() skips a query without one.

Background: how a Monitor stores its queries

#
  1. A Monitor (module lucene/monitor) stores queries and, for each incoming document, reports which stored queries match it.
  2. Each query is kept twice: as a document in a small query index (an IndexWriter, searched through a SearcherManager that shows the writer's contents as of its last refresh), and as a parsed entry in an in-memory cache keyed by query id and clause number (q1_0).
  3. A match searches the query index for candidates and runs each candidate's cached entry against the document; a candidate with no cache entry is skipped.
  4. purgeCache() rebuilds the cache from the query index to free entries of replaced or deleted queries. The Monitor runs it in the background every 5 minutes by default.

The finding, step by step

#
  1. On a Monitor whose query index is on a Directory that can fail (in practice on disk), register(q1 = f:apple) throws because one Directory.sync fails. The IndexWriter keeps q1's document and will write it with its next commit; the searcher still shows the index without q1.
  2. A cache purge runs: an explicit purgeCache(), or the background purge (every 5 minutes by default). It rebuilds the query cache from that stale searcher, which has no q1, so q1's entry is dropped: 1 cached query becomes 0.
  3. register(q2 = f:banana) succeeds, and its commit writes q1 too. Now getQueryIds() is [q1, q2] and getQuery("q1") returns apple. You expect matching a document apple to report q1.
  4. Instead match() reports no query: it finds q1's index entry, finds no cache entry for it and skips it without an error. Later purges never add it back; only reopening the Monitor or registering q1 again makes it match.
  5. The same happens when the commit succeeds and the searcher refresh right after it fails, and when the purge runs in the background or the later update is a deleteById of another query.

Who is affected

#

Applications of the optional monitor module whose query index is on a Directory that can fail, in practice a persistent one. It takes a late storage error in one register() (which throws), no retry, and a purge before the next update; the default 5-minute background purge supplies that. The queries of the failed commit are missed.

Mechanism, terms and numbers807 words

A writable Monitor keeps every registered query twice: as documents in its query index (an IndexWriter with an NRT SearcherManager) and as parsed entries in an in-memory cache. register() puts the cache entries and adds the documents, then commits and refreshes (WritableQueryIndex.java:121-128 on main f794ff5a505c). If the commit fails with a non-aborting IOException (a failed Directory.sync), or the refresh after a durable commit fails, register() throws, but the IndexWriter keeps the documents and its next commit writes them; the searcher stays behind. A cache purge in that window (explicit, or the background purge every 5 minutes by default) rebuilds the cache by scanning that stale searcher without refreshing it (:268-315) and drops the query's entry. From the next successful register() or deleteById() of another query on, getQueryIds() and getQuery() report the query but match() silently skips it, through every later purge, until the Monitor is reopened or the query is registered again. Only Monitors whose query index is on a Directory that can fail are hit, in practice a persistent one. In every lucene-monitor release from 8.2.0 through 10.6.0 and on main, with assertions on and off.

The code (main f794ff5a505c, WritableQueryIndex.java)

#
  1. commitWithoutNotify (:107-133), under commitLock and the purge read lock: deletes the ids (:117-119), then for each clause puts the cache entry into the live cache (:121) and adds its document (:122), then writer.commit() (:127) and manager.maybeRefresh() (:128). There is no catch: on an exception the finally only unlocks (:129-131). The searcher is an NRT SearcherManager over the writer (:79), so it changes only on a refresh.
  2. A sync failure inside the commit is not fatal to the IndexWriter: startCommit rolls back the pending commit and rethrows (IndexWriter.java:5990-5995; only an Error is a tragic event, :6029), and the next commit writes the buffered documents (TestIndexWriterExceptions.testExceptionDuringSync, LUCENE-1044, asserts all 23 documents after repeated failed commits). After the failed register(q1) the writer holds q1 (getDisjunctCount() = 1, :328-330) and the cache has q1_0, but the searcher is the old one.
  3. purgeCache() (:248-258) calls purgeCache(CachePopulator) (:268-315): under commitLock it sets up the side map for concurrent commits (:294-301), then scans the current searcher (:303), keeping an entry only for a document the scan returns and only if the entry is already cached (if (query != null) newCache.put(...), :254), then swaps the new map in (:305-314). No refresh comes first, so q1_0 is dropped.
  4. register(q2) commits and refreshes, and q1's document becomes visible too: getQueryIds() scans the searcher (Monitor.java:276-280) and returns [q1, q2].
  5. match(): the presearcher finds q1's document; MonitorQueryCollector.collect gets null from queries.get("q1_0") (:384), and StandardQueryCollector.matchQuery returns at if (query == null) return; (Monitor.java:296). No error, nothing in getErrors().
  6. Later purges keep only entries already cached (step 3), so q1_0 never comes back. Reopening rebuilds the cache by deserializing every stored query (:83, :137-181); re-registering q1 puts the entry back.
  7. For contrast only: ReadonlyQueryIndex.purgeCache() refreshes its searcher (ReadonlyQueryIndex.java:107-111), but the read-only index has no query cache to rebuild (:113-116). The writable purge has no refresh and relies on every commit having refreshed.

The numbers

#

Observation probe on main, assertions off: after the failed register 1 cached entry and 1 document in the writer; after purgeCache() 0 cached; after register(q2) getQueryIds() = [q1, q2], getQuery("q1") = apple, 1 cached entry, match(apple) = []; after a second purge the same; after close and reopen 2 cached and match(apple) = [q1]. Without the purge, match(apple) = [q1] after register(q2).

Second trigger, same root cause

#

The commit succeeds (q1 is durable) and the refresh at :128 throws: in the runs, an injected IOException from opening the new segment's compound file (too many open files would be one real cause; none was reproduced). The searcher stays stale in the same way and a purge drops q1_0 (executed on main). A bounded single-fault enumeration on main (every directory operation of six Monitor updates, three kinds of register, deleteById, clear and purge, faulted once, each followed by three follow-up scripts; 1,473 runs per assertion mode) found this bug's signature only in the follow-up with a purge, at 29 of 147 fault positions, for a new query and for a multi-clause one: late in the commit (once the segment's files are written: the clean-up, the sync, the segments_N write and rename) and at the refresh's openInput. An earlier fault, while the segment is being flushed, is an aborting error instead: the IndexWriter drops the document and closes itself (DocumentsWriterPerThread.java:585-603), so the next register() or deleteById() fails loudly with AlreadyClosedException.

Exposure and likelihood225 words
  • Who. Users of the optional lucene/monitor module whose query index is on a Directory that can fail: in practice an on-disk one (MonitorConfiguration.setIndexPath, or setDirectoryProvider with an on-disk Directory). The repro's in-memory directory fails on purpose; what matters is a directory that can throw.
  • Default vs opt-in. Opt-in in practice: the default new Monitor(analyzer) uses a ByteBuffersDirectory (MonitorConfiguration.java:41), whose sync cannot fail (ByteBuffersDirectory.java:195-197). The purge that makes it last is the default: every 5 minutes (MonitorConfiguration.java:36-37, scheduled at WritableQueryIndex.java:85-98).
  • Scale. Every query of the failed commit, with every clause of a multi-clause query. A large register(Iterable) commits in batches of about 5,000 queries (Monitor.java:152-162, MonitorConfiguration.setQueryUpdateBufferSize), so only the batch whose commit failed is exposed. Nothing is lost from the index; the miss lasts until a reopen or a re-register.
  • Silent. The failing register() throws, so the application is told; if it does not retry, it later sees a Monitor that lists the query and never matches it, with no error.
  • How likely. Rare: it needs a storage error late in a commit or in the refresh after it (a failing fsync, a full disk while writing segments_N, too many open files), an application that keeps going without retrying, and a purge before the next successful update. No public report was found.

Why it looks unintended

#
  • The purge is documented to remove "unused" and "deleted" queries; this query is neither, and the next commit stores it.
  • The Monitor contradicts itself: getQueryIds(), "the queries stored in this Monitor", lists it, but no purge ever makes it match again.
  • The read-only index's purgeCache() refreshes (it has no cache, so only a weak contrast); the writable one does not.
The full argument245 words
  • The purge's contract. Monitor.purgeCache: "Remove unused queries from the query cache." (Monitor.java:129); MonitorUpdateListener.onPurge: "Called after the Monitor's query cache has been purged of deleted queries" (MonitorUpdateListener.java:34); setPurgeFrequency: the "querycache will be garbage-collected" (MonitorConfiguration.java:124). The implementation note says the purge creates "a new query cache populated for each query in the index" (WritableQueryIndex.java:272-273).
  • The Monitor's own state. getQueryIds(): "the set of query ids of the queries stored in this Monitor" (Monitor.java:273). It lists q1; match() never reports it.
  • Upstream tests expect cache and index to converge. TestCachePurging.testBackgroundPurges: "It can sometimes take a couple of purge runs to get everything in sync" (TestCachePurging.java:153), then 99 stored and 99 cached queries (:164-165). Here no number of purges brings them back in sync. No monitor test injects I/O failures.
  • IndexWriter survives the failed commit by design and writes the documents at its next commit (LUCENE-1044's test); the Monitor keeps accepting calls, so it inherits that later publication.
  • A weak contrast: the read-only index's purgeCache() does refresh (ReadonlyQueryIndex.java:107-111, added by #679), though that index has no query cache to rebuild (:113-116).
  • History. The purge design (the predecessor library, LUCENE-8766, #12801) is about memory and lock latency; no javadoc, test, issue or commit message says the purge may run on a stale searcher, or that the Monitor must be retried or reopened after an IOException from register.
The devil's-advocate check139 words

The strongest case for "intended". Monitor.register declares IOException with no failure-atomicity promise ("@throws IOException on IO errors", Monitor.java:172), so after an I/O error the Monitor's state is undefined and the caller should retry or reopen.

Why it fails. The test asks for no atomicity, only that the Monitor agree with itself after later calls have succeeded (a design that left q1 unstored would pass too); nothing documents a retry-or-reopen duty; the Monitor neither closes nor rejects later calls, and its own getQueryIds() reports q1. The reviewers who argued this case rated it weak; the cross-model fact check of this page rated it moderate, because register() gives no post-failure guarantee at all. A maintainer may prefer to document the duty instead (fix option C). So it is an inconsistency left after a storage error, not a broken atomicity promise.

Suggested fix

#

Recommended A. Refresh before the purge scan (recommended, validated)

Recommended: refresh the searcher before the purge scans it, manager.maybeRefreshBlocking() at the start of the first synchronized (commitLock) block of WritableQueryIndex.purgeCache(CachePopulator). It covers both triggers and opens no new reader when nothing changed. Validated: the repro passes, all 182 lucene/monitor tests pass (1 skipped) and the formatter check is clean.

     synchronized (commitLock) {
+      // A commit or refresh that failed can leave the searcher behind the IndexWriter, whose
+      // documents the next commit publishes: scan what the writer holds, not a stale searcher.
+      manager.maybeRefreshBlocking();
       purgeLock.writeLock().lock();

A. Refresh before the purge scan (recommended, validated)

#

WritableQueryIndex.purgeCache(CachePopulator), inside the first synchronized (commitLock) block (:294), before the side map is created.

     synchronized (commitLock) {
+      // A commit or refresh that failed can leave the searcher behind the IndexWriter, whose
+      // documents the next commit publishes: scan what the writer holds, not a stale searcher.
+      manager.maybeRefreshBlocking();
       purgeLock.writeLock().lock();
       try {
         purgeCache = new ConcurrentHashMap<>();

Trade-offs

The scan then sees every document the IndexWriter holds (the searcher is NRT over the writer), so it covers both the failed commit and the failed refresh. Cost: a blocking refresh check per purge (the refresh lock, then openIfChanged, which opens no new reader when the IndexWriter has no changes). It runs under commitLock, as each commit's own refresh already does (:109-128), and before the purge's write lock, so matches do not wait for it (the #12801 concern). If the refresh itself throws, the purge fails before it changes anything and the background purge reports it to onPurgeError (:90-94). It does not make register() failure-atomic: until the next commit the transient state remains (that part overlaps LFV-499). One visible change: a purge right after the failed register(q1) now makes q1 listed and matchable through the NRT searcher before any commit has made it durable (executed with the diagram probe and the fix: after the purge getQueryIds() = [q1], match(apple) = [q1]). That is what the next commit publishes anyway, but a maintainer may object that a query whose register() threw becomes visible.

What the checks validated

Gradle, scratch worktree of f794ff5a505c: repro fails before, passes after (assertions on and off); :lucene:monitor:test 182 tests, 1 skipped, 0 failures; checkGoogleJavaFormat clean. Earlier: the refresh-failure test and the 180 upstream monitor tests pass with it.

B. Refresh when the commit throws (narrower)

#

In commitWithoutNotify, call manager.maybeRefresh() when writer.commit() throws, then rethrow (LFV-499's optional add-on).

Trade-offs

Fixes the failed-sync trigger (an independent check ran it: the failed-sync test passes). By the code it cannot fix the refresh-failure trigger: there the commit succeeds and the refresh throws outside the add-on's catch around writer.commit(). (The executed run of the refresh-failure test with the add-on failed earlier, at its expectThrows: that shadowed class also carried LFV-499's own fix, and the injected fault did not fire, so the run does not decide this point.)

C. Document a retry-or-reopen duty (not a fix)

#

State in Monitor.register that after an IOException the caller must retry the call or reopen the Monitor.

Trade-offs

Keeps the code and turns the bug into a documented duty; a missed retry is still made permanent by the background purge. Not run.

Downstream note

#

Downstream, an alerting or filtering service built on a persistent Monitor can silently stop alerting on a query after one storage error, until it reopens the Monitor or registers the query again.

How it was found

#

A single-fault model-based test of the Monitor (one injected IOException at each directory operation, with a self-consistency check after every step) flagged it. A bounded-exhaustive enumeration of every single fault (1,473 runs per assertion mode) located the trigger, and the finding was reduced to one public-API JUnit test.

The method in full158 words

Method: semi-formal. A model-based test ran Monitor operations with one IOException injected at a single directory operation and, after every step, checked the Monitor against itself (a query it lists as stored must match a document it matches). It produced the first failing run.

A bounded-exhaustive single-fault enumeration on the stock main jar then faulted every directory operation of six Monitor updates once (three kinds of register, deleteById, clear and purge; each followed by 3 follow-up scripts; 1,473 runs per mode, assertions on and off): a new and a multi-clause register violate self-consistency only in the follow-up with a purge, at 29 of 147 fault positions each, late in the commit and at the refresh's openInput. With the fix shadowed in, both signatures disappear. The finding was then reduced to one public-API JUnit test and checked by an independent reproducer, two executed cross-model reviews, an intended-behaviour devil's advocate and an adjudication ("Prior reports, history and checks").

LFV-1477, snapshot of 2026-11-10

Registry title
Monitor.purgeCache after a register whose commit or post-commit refresh failed with an I/O error rebuilds the query cache from the stale searcher and drops that query, although IndexWriter still publishes it at the next commit: getQueryIds()/getQuery() then list the query but match() never reports it until the Monitor is reopened (since 8.2.0)
Area
monitor / WritableQueryIndex query cache purge vs. commit and searcher refresh (failure atomicity)
Priority
Low, rank 501: In the optional monitor module with a persistent query index, one non-aborting I/O failure in a register's commit or post-commit refresh, followed by any purge (the default background purge included), leaves the query listed as stored but silently never matched until the Monitor is reopened, in every release since 8.2.0. It is Low because it needs an uncommon storage failure, the failing register throws, and registering the query again heals it.
Impact class
minor
Impact note
Applications of the optional lucene/monitor module with a persistent query index (MonitorConfiguration.setDirectoryProvider, or setIndexPath) are hit when one register() fails with a non-aborting I/O error inside the query index's commit (a Directory.sync failure) or inside the searcher refresh right after a durable commit (openInput of the new segment), and a purge (an explicit purgeCache() or the default background purge, every 5 minutes) runs before the next successful register or deleteById: from then on the query is listed by getQueryIds()/getQuery() but match() silently never reports it, through every later purge, until the Monitor is closed and reopened or the query is registered again; the failing register() does throw IOException, a retry heals it, no scale is needed, -ea and -da.
Summary
You register q1 = f:apple on a Monitor with a persistent query index and the index's commit fails once with an IOException (here a single Directory.sync failure), so register() throws; then purgeCache() runs (explicitly, or as the default background purge) and a later register(q2) succeeds. You expect the Monitor to agree with itself: IndexWriter kept q1's document and publishes it with q2's commit, so a query that getQueryIds() and getQuery("q1") report as stored should match a document containing 'apple'. Instead match() never reports q1, because purgeCache rebuilt the query cache by scanning the searcher that the failed commit left stale, dropped q1's cache entry and never adds it back; only closing and reopening the Monitor, or registering q1 again, makes it match.
