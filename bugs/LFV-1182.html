Automaton.finishState leaves overlapping arcs unmerged after a range ending at Integer.MAX_VALUE, so determinize returns a non-deterministic automaton

Finishing an automaton state should merge overlapping arcs to the same destination, but its test tMin <= max + 1 overflows when max is Integer.MAX_VALUE. So ([0, Integer.MAX_VALUE] | [5, 10])* keeps two self-loops, determinize returns it unchanged and CharacterRunAutomaton throws "Automaton must be deterministic" (10.0.0 to 10.6.0, main).

The finding in 30 seconds

#

A finished automaton state should merge arcs to the same destination whose label ranges touch or overlap. For one boundary value the merge test overflows.

Background: how a finished state is reduced

#
  1. A Lucene Automaton has states joined by arcs. Each arc carries a label range [min, max], stored as int; Automata.makeCharRange(min, max) builds one such arc.
  2. When a state is finished (finishState, or by starting to add arcs to the next state), its arcs are sorted and reduced: arcs to the same destination whose ranges touch or overlap become one arc, so [0, 100] and [5, 10] become [0, 100].
  3. An automaton is deterministic when no two arcs of one state overlap. CharacterRunAutomaton accepts only deterministic automata, and Operations.determinize treats an automaton with at most one state as already deterministic.

The finding, step by step

#
  1. Build repeat(union(makeCharRange(0, Integer.MAX_VALUE), makeCharRange(5, 10))). Since [5, 10] lies inside [0, 2147483647], this is just "any word". Integer.MAX_VALUE stands for an open upper end, an idiom Lucene's own TestRegExpParsing also uses (its language check stops at 0x10FFFF).
  2. Call Operations.determinize on it and wrap the result in new CharacterRunAutomaton(...). You expect one state with one self-loop [0, 2147483647] that accepts "abc". With the upper end 2147483646 that is exactly what you get.
  3. Instead the constructor throws IllegalArgumentException: Automaton must be deterministic, with assertions on and off. The state kept both loops, [0, 2147483647] and [5, 10], and isDeterministic() is false.
  4. Why: a finished state merges the next range to the same destination while tMin <= max + 1. 2147483647 + 1 wraps to -2147483648, so 5 <= -2147483648 is false and [5, 10] stays a second, overlapping arc. determinize treats a one-state automaton as already deterministic and hands it back.

Who is affected

#

Only application code that builds its own automaton with a range ending at exactly Integer.MAX_VALUE and an overlapping range to the same destination in the same state, then runs the one-state result. One state with two arcs is enough and it fails every time. Regex, wildcard, prefix and fuzzy queries cannot produce the label.

Mechanism, terms and numbers576 words

Automaton.finishCurrentState sorts a state's arcs and merges arcs to the same destination whose label ranges touch or overlap, as the class javadoc promises ("reduced (transitions with adjacent labels going to the same dest are combined)", Automaton.java:33-41 at 5adff78bb168). The merge test is if (tMin <= max + 1) in int (:259). When the running max is Integer.MAX_VALUE, max + 1 wraps to Integer.MIN_VALUE, so every later arc to that destination stays separate, even one inside [x, MAX], and the overlap clears the deterministic flag (:300-310).

For repeat(union(makeCharRange(0, Integer.MAX_VALUE), makeCharRange(5, 10))) the result is one state with the self-loops [0, 2147483647] and [5, 10]. Operations.determinize returns any automaton with at most one state unchanged (Operations.java:658-661), and new CharacterRunAutomaton(...) then throws IllegalArgumentException: Automaton must be deterministic (RunAutomaton.java:63-64), with assertions on and off. The accepted language never changes; the upper end Integer.MAX_VALUE - 1 merges correctly.

The fix is one character: tMin <= max + 1L. Only application-built automata can carry the label; RegExp, wildcard, prefix and fuzzy queries stay at or below 0x10FFFF.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/automaton/)

#
  1. Operations.union (Operations.java:478) gives state 0 the arcs [0, MAX] -> 1 and [5, 10] -> 1; state 1 accepts and has no arcs. Operations.repeat (:201-265) folds that accept state into the new start state 0 (:222-224), copies the old start state's arcs onto state 0 with their destination mapped to 0 (:243-248) and drops the now unreachable copy of the old start state (removeDeadStates, :264), so the result is one accepting state with the self-loops [0, MAX] -> 0 and [5, 10] -> 0.
  2. Automaton.java:245: finishCurrentState sorts the arcs by dest, min, max: [0, MAX], then [5, 10].
  3. :259 (the fix site): for [5, 10] the test is 5 <= max + 1 with max = 2147483647. max + 1 wraps to -2147483648, so the test is false: [0, MAX] is written out and [5, 10] starts a new arc.
  4. :298-310: after the min/max sort, the second arc's min (5) is <= lastMax (2147483647), so deterministic is cleared (:305).
  5. Operations.java:654-661: determinize returns its input when it is deterministic or has at most one state ("Already determinized", :658-661). That shortcut is only safe if same-destination arcs were merged; here it hands back the non-deterministic one-state automaton.
  6. RunAutomaton.java:63-64: the constructor rejects it, so new CharacterRunAutomaton(...) (CharacterRunAutomaton.java:27) throws.

The structure probe prints, for upper end 2147483647: union: s0: [0,2147483647]->1 [5,10]->1 | isDeterministic=false, repeat: states=1 | s0*: [0,2147483647]->0 [5,10]->0, and determinize: same object=true; for 2147483646 one arc [0,2147483646], deterministic, and run("abc")=true (assertions on and off).

Other ways in

#
  • Automata.makeCharClass(new int[] {'a', 'x'}, new int[] {Integer.MAX_VALUE, 'z'}), documented as "a new minimal automaton" (Automata.java:158-159), returns the same kind of unreduced state, and new CharacterRunAutomaton on it throws with no determinize call (10.2.0 and later).
  • A state built by hand with addTransition(s, s, 0, Integer.MAX_VALUE) and addTransition(s, s, 'a', 'z') keeps 2 arcs after finishState().
  • With two or more states determinize rebuilds a correct DFA when assertions are off; with them on, two identical unmerged arcs can trip assert transitionSorted(t) in getNextTransition (Automaton.java:493).

With char labels (before 2010) max was at most 0xFFFF and max + 1 could not wrap.

Exposure and likelihood208 words
  • Who. Application code that builds its own automaton (by hand with addTransition, through makeCharClass, or through union / repeat that end in one state) with a range ending at exactly Integer.MAX_VALUE and an overlapping range to the same destination after it, and then runs it with CharacterRunAutomaton. No configuration and no scale.
  • Not affected. RegExp, wildcard, prefix and fuzzy queries: their labels come from code points and stop at Character.MAX_CODE_POINT (RegExp.java:1217-1222, :1379, :1399, :1423). Ranges ending at 0x10FFFF or Integer.MAX_VALUE - 1 merge correctly.
  • Effect. A loud IllegalArgumentException whose message blames non-determinism on the output of the determinize call just made; makeCharClass returns a "minimal automaton" that is not even deterministic. The accepted language is right: no silent wrong result.
  • API status. Automaton, Automata and Operations are tagged @lucene.experimental.
  • Versions. The unreduced state since 4.0.0-alpha, the false deterministic flag since 4.10.0, the exception since 10.0.0 (9.x RunAutomaton determinized its input itself).
  • Likelihood: rare. No in-tree query or parser construction we found produces this shape (core's term-id automata in GraphTokenStreamFiniteStrings use labels that are not code points, but were not shown to produce it), and no public report of it was found since 2010; the shape fails deterministically.

Why it looks unintended

#
  • The Automaton javadoc promises "reduced" finished states (same-destination arcs with adjacent labels combined); makeCharClass promises "a new minimal automaton".
  • No numeric label bound is documented or checked, and Integer.MAX_VALUE - 1 merges: an int overflow, not a limit.
  • Disputed: the javadocs call labels code points, so labels above 0x10FFFF may be out of contract, making the fix hardening.
The full argument342 words
  • Contract. Automaton.java:33-41 ("reduced (transitions with adjacent labels going to the same dest are combined)"); isDeterministic: "for ever state there is only one transition for each label" (:313-316); determinize: "Determinizes the given automaton" (Operations.java:641); makeCharClass: "Returns a new minimal automaton" (Automata.java:158). On #13706 (2024) Robert Muir restated it: ranges added to one state "will be collapsed into one single range when you finishState".
  • No numeric bound is documented or checked. The javadocs call labels code points (makeCharRange: "accepts a single codepoint whose value is in the given interval", Automata.java:137-138; makeCharClass: "any of the codepoint ranges", :158; step / next: "codepoint to look up", Automaton.java:654, :672, :685), but none gives a numeric limit or says larger labels are illegal; addTransition says nothing about code points (Automaton.java:153-154); and nothing checks labels (makeCharRange handles only min > max, Automata.java:141; makeCharClass and addTransition take any int). TestRegExpParsing.testNegatedChar and testNegatedCharRange write makeCharRange('d', Integer.MAX_VALUE) and makeCharRange('e', Integer.MAX_VALUE) as an open upper end (lucene/core/src/test/org/apache/lucene/util/automaton/TestRegExpParsing.java:193, :243; there the MAX-ended arc is the last one to its destination, so the wrap never meets a later arc), but their language check stops at Character.MAX_CODE_POINT (TestRegExpParsing.java:832-835, AutomatonTestUtil.java:681-684): an idiom, not labels above 0x10FFFF in use. Core does use labels that are not code points (term ids, GraphTokenStreamFiniteStrings.java:231), and LevenshteinAutomata has a public expert constructor that takes any alphaMax (LevenshteinAutomata.java:61-65; not tested against this bug).
  • Only the one value fails. Integer.MAX_VALUE - 1 merges, so it is a plain overflow, not a designed limit. Lucene relies on the merge: RegExp turns [a-zx-z] into one arc, and in the #14193 review Michael McCandless expected finishState to dedup repeated code points, and Robert Muir replied that he had a test for duplicates.
  • History. The test was written for char labels, where it could not wrap, and kept unchanged when labels became int in 2010. No commit, issue or PR found discusses the wrap.
The devil's-advocate check286 words

The strongest case for "intended": the package documents a "DFA/NFA implementation with Unicode alphabet" (package-info.java:33); makeCharRange, makeCharClass, step and next call labels code points; CharacterRunAutomaton runs an alphabet of Character.MAX_CODE_POINT + 1 labels, and a Java String cannot contain Integer.MAX_VALUE as a code point; TestRegExpParsing's Integer.MAX_VALUE upper end is compared only up to 0x10FFFF (AutomatonTestUtil.java:681-684); and on LUCENE-5030 (#6094, 2013) Michael McCandless said a special label "must be a valid unicode char since we will send it through UTF32toUTF8". With the upper end 0x10FFFF the same shape merges and runs, assertions on and off. So Integer.MAX_VALUE can be called out of domain and the exception a fair rejection. The cross-model reviewer (OpenAI GPT-5.6) returned not real (medium) on these grounds (the Unicode alphabet, RegExp's code-point cap, the comparator cap), and the devil's-advocate verifier weighed the "codepoint" @param wording; both reproduced the failure with their own tests, and those tests pass with the fix.

Why it fails (a judgement): the code-point wording says what labels mean, but no javadoc gives a numeric bound or calls larger labels illegal, addTransition says nothing about code points, nothing checks labels, and core itself builds automata whose labels are not code points; the failure is int arithmetic inside the reduce step, not a code-point consumer; and if the label were out of domain the right error would name the label, not call determinize's own output non-deterministic. A maintainer could reasonably close it as out of domain, or take the fix only as cheap hardening. It argues for Low priority and for treating the fix as hardening, not for intended behaviour. The independent reproducer, the devil's-advocate verifier and the adjudication rated it real.

How it was found

#

A proof-obligation audit of Automaton's contract: for every arc the API accepts (0 <= min <= max), a finished state must be reduced, so overlapping ranges to the same destination must merge. The obligation fails for a range ending at Integer.MAX_VALUE, because max + 1 wraps; a public-API JUnit test then witnessed the exception.

The method in full92 words

Method: semi-formal, a proof-obligation audit of Automaton's contract (finished states are reduced), witnessed by an executable repro. The audit took the class javadoc's promise as the obligation for finishCurrentState and checked the merge test tMin <= max + 1 against the full int label range; the only value where it fails is max = Integer.MAX_VALUE. A public-API JUnit test (repeat(union(...)), then determinize and CharacterRunAutomaton) turned the failed obligation into an executable failure on main, and a probe confirmed the two unmerged arcs and the false flag (2026-11-03).

History

#

Introduced in 2010 by LUCENE-2265 (5b74a4ec611), which changed labels from char to int and kept the max + 1 merge test. The unreduced state is in every release since 4.0.0-alpha; the exception since 10.0.0 (#485, #13714). Not fixed upstream.

Versions tested6 rows

Introduced by 5b74a4ec611 (2010-05-03, svn r940671), commit message "LUCENE-2265: cutover Fuzzy, Wildcard, Regexp queries to operate on Unicode UTF32 code point not UTF16 code units" (LUCENE-2265 is now #3341, "improve automaton performance by running on byte[]"; committed by Michael McCandless, the int cutover by Robert Muir; no pull request). It widened Transition.min/max to int, moved the merge loop into State.reduce() and kept if (t.min <= max + 1) from the char-label code, where max <= 0xFFFF. Its char-label parent a3da4421208 merges the arcs.

LUCENE-5752 (#6814; landed on trunk as ec2eaaafad8, 2014-06-19, and on branch_4x as 46132142cc2, 2014-06-20, first in 4.10.0) moved the loop unchanged into finishCurrentState, made it compute the deterministic flag and made determinize return a one-state input unchanged (on the issue branch the flag came in 5927445bb60 and the one-state shortcut in ce2f7e9c8cd). The exception in this repro needs two changes first released in 10.0.0: #485 (LUCENE-10010, b2e866b7036, 2021: RunAutomaton stops determinizing and rejects non-deterministic input) and #13714 (11d7566229c, 2024: repeat builds the one-state automaton here); each was checked against its parent. #485 alone is enough when an unreduced automaton reaches CharacterRunAutomaton another way (a hand-built one-state automaton, or makeCharClass with no determinize). Upstream main aa366ae209a (2026-11-04) still has the line.

Registry title

util / automaton (Automaton.finishCurrentState reduce and determinism flag; Operations.determinize, RunAutomaton)

Only application code that builds its own automaton with a label range ending at exactly Integer.MAX_VALUE (an open upper end, an idiom upstream's own TestRegExpParsing uses) and a second, overlapping range to the same destination later in the same state (by hand, through Automata.makeCharClass, or through union/repeat that collapse to one state) is hit: the state is not reduced and isDeterministic() is false, and for a one-state automaton Operations.determinize returns it unchanged, so new CharacterRunAutomaton(...) on determinize's output throws IllegalArgumentException 'Automaton must be deterministic' with -ea and -da and no scale; the accepted language never changes, ranges ending at 0x10FFFF or Integer.MAX_VALUE - 1 merge correctly, RegExp and the query parsers never emit labels above 0x10FFFF, and the exception shows in every release from 10.0.0 to 10.6.0 and on main (4.0.0-alpha to 9.12.3 keep the unreduced state without an error).
Summary
You build the automaton ([0, Integer.MAX_VALUE] | [5, 10])* with Automata.makeCharRange, Operations.union and Operations.repeat, determinize it and run it with CharacterRunAutomaton; you expect it to accept "abc", because a finished state merges same-destination ranges that touch or overlap into one arc, as the Automaton javadoc promises. Instead the CharacterRunAutomaton constructor throws IllegalArgumentException 'Automaton must be deterministic': finishState merges a range only while min <= max + 1, and once max is Integer.MAX_VALUE that sum wraps to Integer.MIN_VALUE, so [5, 10] stays a second, overlapping arc, the state is flagged non-deterministic, and determinize returns the one-state automaton unchanged. The accepted language is right; only the reduced form and the determinism flag are wrong.
