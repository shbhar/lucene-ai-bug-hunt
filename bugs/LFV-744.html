IndriDirichletSimilarity(2000f) scores differently from IndriDirichletSimilarity(): the mu constructor silently uses another collection model

new IndriDirichletSimilarity(2000f) and new IndriDirichletSimilarity() print the same name but score differently: the one-argument constructor gets LMSimilarity's collection model, (cf + 1) / (|C| + 1), instead of Indri's cf / |C|. On a 25-token index the word "president" scores -1.871553 instead of -2.119101.

The bug in 30 seconds

#

Same class, same mu, two constructors, two answers to "how common is this word in the index?": IndriDirichletSimilarity() uses Indri's cf / |C|; IndriDirichletSimilarity(float mu) sets only mu (IndriDirichletSimilarity.java:54-56) and silently inherits LMSimilarity's default, (cf + 1) / (|C| + 1) (LMSimilarity.java:56-58).

  1. You index 4 short documents, 25 tokens in all; the word "president" occurs 3 times. You score them with new IndriDirichletSimilarity(2000f) because you want Indri's Dirichlet smoothing with mu = 2000.
  2. You expect exactly what new IndriDirichletSimilarity() gives, which is documented as using "the default mu value of 2000". Both print LM IndriDirichlet(2000.000000). Doc 0 should score log((1 + 2000 x 3/25) / (6 + 2000)) = -2.119101.
  3. You get -1.871553. The one-argument constructor passes no collection model, so the parent class's default applies: "president" counts as 4/26 = 0.154 of the collection instead of 3/25 = 0.12. explain() shows 0.15384616 as "collection probability".
  4. Every positive mu does this (at mu = 0 the model drops out of the formula). With mu = 3 the document with "george" (one occurrence) scores -1.8718022, while Indri's formula gives -1.9661129; for a word that occurs once the collection probability nearly doubles, 2/26 instead of 1/25.
  5. No error and nothing in the name tells you. The shift is about mu / |C|, so it is large on small indexes and tiny on big ones: 0.02% of the score at 1.3 million tokens; in a synthetic audit of 1,984 queries no top hit changed. Every release since 8.9.0 has it.

Who is affected

#

Applications that pick IndriDirichletSimilarity (opt-in, not the default) and set mu through the one-argument constructor, on every release since 8.9.0. For any mu > 0 every score and explain() is shifted. The shift is about mu / |C|: large on small indexes, tiny on big ones; in a synthetic audit no top hit and no top-10 set changed.

Mechanism, terms and numbers586 words

IndriDirichletSimilarity implements "Bayesian smoothing using Dirichlet priors as implemented in the Indri Search engine": a document's score for a term is log((tf + mu * p(w|C)) / (|D| + mu)), where the collection probability p(w|C) comes from a CollectionModel. The class ships its own IndriCollectionModel, cf / |C|, and the no-argument constructor, documented as "the default mu value of 2000", uses it. The one-argument constructor IndriDirichletSimilarity(float mu) only assigns mu, so Java inserts super(), and LMSimilarity() installs DefaultCollectionModel, (cf + 1) / (|C| + 1). So new IndriDirichletSimilarity(2000f) and new IndriDirichletSimilarity() have the same mu and print the same LM IndriDirichlet(2000.000000), but score differently: on a 4-document index of 25 tokens, "president" (cf 3) gets p(w|C) = 4/26 instead of 3/25, and doc 0 scores -1.871553 instead of -2.119101. Any positive mu is affected (at mu = 0 the model drops out of the formula): every score and explain() is shifted, and close documents can swap places; on large indexes the shift is a fraction of a percent. Nothing throws and nothing is written to the index. Every release since 8.9.0, the first with the class, is affected.

Terms

#
  • Dirichlet smoothing (Indri): a document's score for a term is log((tf + mu * p(w|C)) / (|D| + mu)), where tf is the term's count in the document, |D| the document length, mu the smoothing strength and p(w|C) the collection probability: how common the term is in the whole field.
  • Collection model: the strategy object of LMSimilarity that computes p(w|C). Two exist here: IndriCollectionModel, cf / |C| (Indri's estimate: occurrences of the term divided by all tokens of the field), and LMSimilarity.DefaultCollectionModel, (cf + 1) / (|C| + 1).

The bug

#
  1. IndriDirichletSimilarity has five constructors (IndriDirichletSimilarity.java:40-66). The three that take a CollectionModel pass it on. IndriDirichletSimilarity() is this(new IndriCollectionModel(), 2000) (:64-66). IndriDirichletSimilarity(float mu) is { this.mu = mu; } (:54-56): no this(...) or super(...), so the compiler inserts super().
  2. LMSimilarity() is this(new DefaultCollectionModel()), "Creates a new instance with the default collection language model" (LMSimilarity.java:55-58). DefaultCollectionModel returns (totalTermFreq + 1) / (numberOfFieldTokens + 1) (:150-152); IndriCollectionModel returns totalTermFreq / numberOfFieldTokens (IndriDirichletSimilarity.java:111-113).
  3. LMSimilarity.fillBasicStats stores the model's value once per term (LMSimilarity.java:68-73) and score() uses it for every document (IndriDirichletSimilarity.java:69-72); explain() prints it as "collection probability" (LMSimilarity.java:75-80).
  4. Both models return getName() = null and getName() of the similarity prints only mu (IndriDirichletSimilarity.java:96-99), so both constructors give toString() = LM IndriDirichlet(2000.000000).

How big the shift is

#

(cf + 1)/(|C| + 1) - cf/|C| = (|C| - cf) / (|C| (|C| + 1)), about 1/|C|. So the numerator tf + mu * p(w|C) grows by about mu / |C|: from 241 to 308.7 in the 25-token example (mu 2000), but only by 0.0015 at 1.3 million tokens. The relative change of p(w|C) is about 1/cf, so rare terms move most when the shift matters at all. The shift vanishes at mu = 0, where the term mu * p(w|C) is 0 under both models (one of the upstream test's cases), and when cf = |C|, where both models give 1.

Three related javadoc slips: IndriCollectionModel's javadoc says "divided by the total number of tokens + 1" but the code adds nothing (IndriDirichletSimilarity.java:101-104); LMSimilarity's class javadoc describes DefaultCollectionModel without its +1 (LMSimilarity.java:33-35); and DefaultCollectionModel's own javadoc names only the +1 in the denominator (LMSimilarity.java:140-143).

Exposure and likelihood342 words
  • Who is hit. Users of IndriDirichletSimilarity(float mu), the natural way to tune mu, installed with IndexSearcher#setSimilarity. Any positive mu, assertions on and off. The upstream TestIndriDirichletSimilarity itself only uses this constructor.
  • Effect. For mu > 0, scores and explain() differ from Indri's cf / |C| estimate, which the class description implies, and from IndriDirichletSimilarity() with the same mu (except in the degenerate case cf = |C|). The set of matching documents does not change.
  • How likely a ranking change is. A credibility audit ran 1,984 random 2- and 3-term BooleanQuery queries over 5 synthetic corpora (1,458 to 1,309,450 tokens, mu 2000): no top hit changed, no top-10 set changed, one top-10 order changed. The largest relative score change was 0.019% at 1.3 million tokens and 0.5% to 6.8% on the small corpora. The audit sorted its top-10 lists from Weight#scorer scores, not from IndexSearcher#search, and synthetic corpora say nothing about real workloads. The ranking flips the checkers built are on tiny constructed corpora: in 26 of 146 swept 4-document indexes (130 to 3,030 tokens) two close documents, ranks 3 and 4 of 4, swapped places (scores read through Weight#scorer, the count printed, not asserted); in one 3-document index of 35 tokens the top hit of IndexSearcher#search changed. They show that flips can happen, not how often.
  • Where it shows on each release. Since 10.3.0 a plain top-k TermQuery search under this similarity returns no hits at all, a separate bug (LFV-190, negative scores dropped by BatchScoreBulkScorer). So on 10.3.0 to 10.5.2 and main the wrong values show in explain(), Scorer-level use and multi-clause BooleanQuery search; on 8.9.0 to 10.2.x also in plain search (on 10.2.2, search(TermQuery("president"), 10) returns doc 0 at -2.119101 with the no-argument constructor and -1.871553 with (2000f)). This bug survives a fix of LFV-190 and of open PR #463.
  • Not reached. The case where the shift would be large, the smoothing score of an absent term in IndriAndQuery, is not reached for TermQuery clauses on main (the audit, by reading).

Why it is a bug, not intended

#
  • Class javadoc: "as implemented in the Indri Search engine" (implying cf / |C|); the no-argument constructor is documented only as "the default mu value of 2000".
  • Nothing in code, tests, CHANGES or reviews says a chosen mu should switch the model; the upstream test asserts no scores.
  • The sibling LMDirichletSimilarity() is this(2000): one model for both.
The full argument385 words
  • Contract (implied, not word for word). Class javadoc: "Bayesian smoothing using Dirichlet priors as implemented in the Indri Search engine" (IndriDirichletSimilarity.java:23-25); CHANGES for LUCENE-9537: "the IndriDirichletSimilarity from the academic Indri search engine" (lucene/CHANGES.txt:5346-5347). The class javadoc writes the formula with an unspecified P(t|C) (:27-30), so cf / |C| is implied, not stated. Indri computes cf / |C| for a term that occurs in the collection (a checker read it in the Indri source, and the fact check re-read it), which is what IndriCollectionModel does; for a term that never occurs Indri uses 1 / (2|C|), which Lucene's TermStats never allows, and Indri's own default mu is 2500. The no-argument constructor is documented only as "the default mu value of 2000" (:63).
  • The sibling keeps one model. LMDirichletSimilarity, whose constructor signatures this class mirrors, has LMDirichletSimilarity() { this(2000); } (LMDirichletSimilarity.java:71-73). Only IndriDirichletSimilarity switched its no-argument constructor to another model.
  • No intent for the difference. The PR that added the class (apache/lucene-solr#2097, 10 conversation and 28 inline review comments) and LUCENE-9537 (#10577, 20 comments) never mention the collection model or the constructors. #13845 added the discountOverlaps constructor and discussed only that flag, not Indri. None of them says that choosing a mu should also switch the collection model.
  • The upstream test does not pin it. TestIndriDirichletSimilarity builds only new IndriDirichletSimilarity(mu) with a random mu (:48), asserts generic properties, no values, and passes with the fix.
  • The +1's original reason does not apply. LUCENE-3430 (2011) added the +1 in the numerator because SpanQueries sometimes scored terms with ttf = 0 (the +1 in the denominator dates from the first LMSimilarity, LUCENE-2959). On main TermStats and FieldStats reject zero counts (TermStats.java:77-80, FieldStats.java:102-104), and the no-argument constructor already uses cf / |C| on every input. That removes the zero-count reason; it does not rule out that a maintainer sees the +1 as deliberate smoothing.
  • Before the port (a checker's reading of third-party code): in the class author's own projects, Lucindri (release 1.1, 2020) and IndriLuceneImpl, the same constructor bodies sat on a base class whose default model is cf / |C|, so both constructors gave Indri's estimate. Rebasing the class on LMSimilarity changed the mu constructor's meaning silently. Nobody upstream has said so.
The devil's-advocate check192 words

The strongest case for "works as written" (built by the devil's advocate; the cross-model reviews rated it moderate): by Java's rules the mu-only constructor inherits LMSimilarity's documented default model, its javadoc promises only mu, the constructor signatures mirror LMDirichletSimilarity's, the (cf + 1)/(|C| + 1) default is a deliberate Lucene choice, LMSimilarity is @lucene.experimental (IndriDirichletSimilarity itself carries no marker), and the upstream test has always run the mu constructor.

Why it fails: it explains the mechanism but not why new IndriDirichletSimilarity() and new IndriDirichletSimilarity(2000f) should differ. The LMDirichletSimilarity precedent points the other way (all its model-less constructors share one model, and it claims no Indri fidelity), the +1's reason does not apply on main, the test asserts no values, and the author's original code gave cf / |C| on both paths. Verdict: not intended, but the contract is implied, so present it as a constructor inconsistency; a maintainer may answer with a javadoc note or another API change (deprecating the mu-only overload, naming the model in toString()) because a code fix changes scores for current users; the fix below is one reasonable resolution, not the only one.

The mu constructor uses IndriCollectionModel (validated) (validated by the checks) (recommended)

IndriDirichletSimilarity(float mu) becomes this(new IndriCollectionModel(), mu), like the no-argument constructor. Trade-offs

Scores of current IndriDirichletSimilarity(float) users with mu > 0 change, toward Indri's formula and toward IndriDirichletSimilarity(). Indexes need no change: the model is applied at search time. No material cost change is expected (one model object per similarity, the same arithmetic per score); not benchmarked. A maintainer may want it on main only. Open PR #463 edits score() a few lines away, so the two may conflict textually.

Downstream note

#

Solr and OpenSearch have no Indri code and Elasticsearch documents no Indri similarity, so the exposure is applications that build Lucene's IndriDirichletSimilarity themselves; the Lucindri project ships its own copy of the class.

How it was found

#

Semi-formal: a bounded-exhaustive check scored every 1- to 4-token document over a 3-letter alphabet (120 documents) with TermQuery and compared each score with the Indri formula. IndriDirichletSimilarity(3f) missed it in all 1,080 checks while the no-argument version matched for unboosted queries, which led to the constructor.

The method in full146 words

Method: bounded-exhaustive translation validation of scoring components against their documented formulas (hunt unit "scoring components vs documented formulas", harness part B1, 2026-10-27, main a9779ef3c193).

  • The harness indexed every document of 1 to 4 tokens over a 3-letter alphabet (120 documents, including a 4-byte and a 3-byte letter), scored each TermQuery hit through Weight#scorer, and compared it with log((tf + mu * cf/|C|) / (|D| + mu)).
  • IndriDirichletSimilarity() matched for unboosted queries (its remaining mismatches are boosted queries, whose boost score() ignores, which open PR #463 also changes). IndriDirichletSimilarity(3f) mismatched in all 1,080 of its formula checks.
  • Reading the code traced that to the constructor. The finder then wrote the public-API JUnit, checked it on 10.5.2 and 9.12.3, and validated the one-line fix with the upstream Indri tests.
  • Tier: semi-formal (a bounded-exhaustive check of the real jar against exact semantics); it proves nothing beyond its bounds.

Bug record

LFV-744, snapshot of 2026-10-29

Registry title
IndriDirichletSimilarity(float mu) uses LMSimilarity's default (cf+1)/(|C|+1) collection model instead of IndriCollectionModel (cf/|C|), so new IndriDirichletSimilarity(2000f) scores differently from new IndriDirichletSimilarity() although both print the same name
Area
search / similarities (IndriDirichletSimilarity constructors and the LMSimilarity collection model)
Priority
Medium, rank 64: Every query scored with the released opt-in core IndriDirichletSimilarity built through its mu constructor gets silently wrong scores, but hits stay the same and rankings only flip between closely scored documents.
Impact class
silent wrong results
Impact note
Applications that score with IndriDirichletSimilarity built through its mu-only constructor (a non-default similarity; any mu, any index size, -ea and -da, default codec and IndexWriterConfig) get every score computed with collection probability (cf+1)/(|C|+1) instead of Indri's cf/|C|, so scores and explain() differ from the Indri formula and from IndriDirichletSimilarity() with the same mu (most for rare terms: 2/(|C|+1) instead of 1/|C| at cf = 1) and multi-clause rankings can flip between close documents (constructed probes the cross-model review, the intended-behaviour check); on 10.3.0 and later a plain top-k TermQuery search under this similarity already returns no hits (LFV-190), so there the wrong values show in explain(), Scorer-level use and multi-clause BooleanQuery search, and in 8.9.0 to 10.2.x also through plain search; nothing is written to the index.
Summary
You install new IndriDirichletSimilarity(2000f) and expect the same similarity as new IndriDirichletSimilarity(), which is documented as using 'the default mu value of 2000', and Indri's Dirichlet smoothing log((tf + mu*cf/|C|)/(|D| + mu)) for any mu. Instead the mu-only constructor passes no collection model, so its implicit super() installs LMSimilarity's DefaultCollectionModel, (cf+1)/(|C|+1), while only the no-argument constructor installs the class's own IndriCollectionModel, cf/|C|. On a 25-token index the term 'president' (cf 3) scores -1.871553 instead of -2.119101 in the same document, although both instances print 'LM IndriDirichlet(2000.000000)'.
