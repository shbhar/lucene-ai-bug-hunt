Intervals.range and Intervals.prefix throw ArrayIndexOutOfBoundsException for a bound that is not valid UTF-8 and ends in a cut-off multi-byte sequence, because they decode it only to build a description string

Intervals.range and Intervals.prefix throw ArrayIndexOutOfBoundsException while the query is built when a bound is not valid UTF-8 and ends in a cut-off multi-byte sequence, for example the two bytes 01 F4. TermRangeQuery and PrefixQuery accept the same bound; the factories decode it only to build a description string.

The finding in 30 seconds

#

Both factories build a byte automaton for matching and compile it as binary. Then they turn the bound into text with utf8ToString() for one purpose: the description that toString and the too-many-terms message show. That decoder does not validate, so a multi-byte lead byte at the end of the array makes it read past the end.

Background: three pieces

#
  1. Intervals.range and Intervals.prefix return an IntervalsSource that matches the positions of every term in a range or with a prefix. You wrap it in an IntervalQuery, alone or inside combinators such as Intervals.ordered.
  2. A Lucene term is a byte sequence, a BytesRef. Most terms are UTF-8 text. Some are not: binary terms, collation keys, and the sentinel UnicodeUtil.BIG_TERM (ten FF bytes).
  3. Lucene's UTF-8 decoder takes the length of a character from its first byte: below C0 one byte, C0 to DF two, E0 to EF three, F0 and above four. It does not check that those bytes exist.

The finding, step by step

#
  1. You build an interval source over a range of terms: Intervals.range(term, term, true, true), where term is the two bytes 01 F4, a binary term that is not valid UTF-8.
  2. You expect a source. The byte-based sibling accepts the same bound: new TermRangeQuery("f", term, term, true, true) builds, prints f:[[1 f4] TO [1 f4]] and counts 1 on an index whose field holds that term.
  3. Instead the factory throws ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 2 before any search runs, with assertions on and off.
  4. Why: the factory first builds the byte automaton that does the matching. Then it calls utf8ToString() on each bound, only to make the description string for toString and one error message. F4 is the lead byte of a 4-byte character, so the unchecked decoder reads three more bytes, past the end of the 2-byte array.
  5. Intervals.prefix(term) fails the same way. So do a text prefix cut inside a multi-byte character (the single byte C3) and UnicodeUtil.BIG_TERM as an upper bound. Bounds that are valid UTF-8 are never affected, and a source that builds never gives wrong hits.

Who is affected

#

Applications that pass a non-UTF-8 BytesRef bound to Intervals.range or Intervals.prefix: a binary term in an untokenized field indexed with positions, a text prefix cut by bytes inside a multi-byte character, or UnicodeUtil.BIG_TERM as an upper bound. Default settings, no scale. Rare and loud: ordinary text bounds are never affected, and hits are never wrong.

Mechanism, terms and numbers927 words

Intervals.range and Intervals.prefix build an IntervalsSource over all terms in a range or with a prefix. Both take BytesRef bounds, build a byte automaton with TermRangeQuery.toAutomaton or PrefixQuery.toAutomaton and compile it as binary (Intervals.java:176-180, :279-296 on main 781025d6fe32). Then they call utf8ToString() on the bound (:179, :291, :293) for one purpose: the description string that MultiTermIntervalsSource shows in toString and in the too-many-terms message and uses as one member of equals/hashCode. UnicodeUtil.UTF8toUTF16 does not validate its input and reads whole characters even past the given length, so a bound that ends in a cut-off multi-byte sequence at the end of its array makes the factory throw ArrayIndexOutOfBoundsException before a source exists: the two bytes 01 F4, a text prefix cut inside a multi-byte character (C3), or UnicodeUtil.BIG_TERM as an upper bound. TermRangeQuery and PrefixQuery accept the same bounds, match with them and print them with Term.toString. Bounds that are valid UTF-8 are never affected, a source that builds never gives wrong hits, and the failure is loud at query construction, so this is a Low priority bug. It is as old as the two factories: 8.2.0 (prefix) and 9.12.0 (range), every release up to 10.6.0, branch_11x and main. A validated three-line fix builds the description with Term.toString(BytesRef), the technique Robert Muir proposed in #4016 and used in #7850.

Terms

#
  • Description string. MultiTermIntervalsSource keeps a String pattern (MultiTermIntervalsSource.java:41, :54). It is used in the too-many-terms message (:152), in equals/hashCode (:177, :182) and in toString (:187). Matching uses the automaton. The expert factory Intervals.multiterm documents the parameter as "string representation of the given automaton, mostly used in exception messages" (Intervals.java:348, :365).
  • Byte-safe renderer. Term.toString(BytesRef) prints valid UTF-8 as text and anything else as hex bytes (Term.java:104-121). TermRangeQuery.toString uses it for both bounds (TermRangeQuery.java:171, :176), and PrefixQuery.toString uses it through Term.text() (PrefixQuery.java:73, Term.java:100-102).

The bug

#
  1. Intervals.range (Intervals.java:279-296) builds its automaton with TermRangeQuery.toAutomaton (:285-286) and compiles it with isBinary = true (:287). Intervals.prefix (:176-180) does the same with PrefixQuery.toAutomaton (:177-178). This half works on bytes.
  2. Then the description: lowerTerm.utf8ToString() (:291), upperTerm.utf8ToString() (:293), prefix.utf8ToString() + "*" (:179).
  3. BytesRef.utf8ToString (BytesRef.java:137-141) allocates length chars and calls UnicodeUtil.UTF8toUTF16, whose javadoc says: "Full characters are read, even if this reads past the length passed (and can result in an ArrayOutOfBoundsException if invalid UTF-8 is passed). Explicit checks for valid UTF-8 are not performed." (UnicodeUtil.java:635-637).
  4. The exception leaves the factory, so new MultiTermIntervalsSource(...) (:295) is never reached and no source is returned.

The numbers

The array has indexes 0 and 1, hence Index 2 out of bounds for length 2. F4 is below F8, so the assertion at :655 passes and the result is the same with assertions on and off.

The two 01 E5 rows show that the exception is not an input check: whether the factory throws depends on bytes outside the BytesRef.

The last two rows are a second way to the same exception, on the output side. utf8ToString allocates length chars (BytesRef.java:138). When the last byte of the bound is a 4-byte lead and the array continues, the decoder reads the three bytes behind the bound and, for a code point above U+FFFF, writes two chars for that one byte (UnicodeUtil.java:665-667). In both rows the second char lands past the end of the buffer, so the repro's two bytes 01 F4 throw as a slice too.

Exposure and likelihood663 words
  • Who. Code that calls one of the two factories with a bound that is not valid UTF-8 and ends in a cut-off multi-byte sequence. Three ways to such a bound were executed: a binary term in an untokenized field indexed with positions (Field(String, BytesRef, IndexableFieldType) refuses offsets and tokenized types, not positions: Field.java:199-215; its javadoc still says it throws when the type is indexed, Field.java:196-197, but the code does not, and StringField(String, BytesRef, Store) uses it with an indexed type; on such an index TermRangeQuery and PrefixQuery count 1 and both factories throw); a text prefix cut by bytes inside a multi-byte character (Intervals.prefix of the single byte C3); and UnicodeUtil.BIG_TERM as an upper bound. On 9.12.x and 10.0.0 the range factory has no open-ended form (null bounds came with #13859, first released in 10.1.0), so there a sentinel is the only way to an open upper end through Intervals.range; Intervals.multiterm with an open-ended automaton builds on 9.12.0 and 10.0.0.
  • Which bounds throw. The decoder has to run off an array. Either the bound ends in a cut-off multi-byte sequence and the array ends before that sequence is complete (the read side, as in the repro), or the last byte of the bound is a 4-byte lead, the array continues, and the two chars written for that one byte do not fit the output buffer (the write side: the slice F4 of the array F4 8F BF BF). With assertions off, every other bound that is not valid UTF-8 builds, with a garbled description.
  • Default configuration, loud. Default IndexWriterConfig, codec and searcher. The factory call alone throws, no index is needed, and nothing is searched. Assertions on and off.
  • Not affected. Bounds that are valid UTF-8, the normal case for analyzed text. In an exhaustive check of all byte strings of length 1 to 3 against the real decoder, no valid UTF-8 string throws; of the 14,174,464 strings that are not valid UTF-8, 5,525,568 (39%) throw as exactly sized arrays with assertions off. Collation keys did not throw with assertions off in any probe (138, 6,708 and 18 keys): they build and match like the sibling query, and those that are not valid UTF-8 only get a garbled description. With assertions on, as in Lucene's own test runs, many of them fail with AssertionError, because the decoder asserts on lead bytes 80 to BF (UnicodeUtil.java:646) and F8 to FF (:655): 83 of the 138 keys, 216 to 520 of each group of 559 among the 6,708, and 8 of the 18. Failures that need assertions are not claimed.
  • A source that builds never gives wrong hits. Matching reads only the byte automaton. In a sweep of 2,954 terms of 1 to 3 bytes from a 14-byte alphabet, each as an exactly sized array and as a slice (11,816 bound pairs against TermRangeQuery and PrefixQuery), 4,508 pairs throw at construction and each of the 7,308 that build gives the sibling's hit count (assertions off). Per factory, 2,099 of the 2,881 non-UTF-8 terms throw as exactly sized arrays and 155 as slices (the rates belong to that alphabet).
  • Likelihood: rare (an estimate, not usage data). Interval sources are positional queries over analyzed text, where bounds are UTF-8. No non-test code in the Lucene tree calls either factory.
  • Workaround. Intervals.multiterm(CompiledAutomaton, String) with a description you supply: counts 1 on stock main, branch_11x and 10.6.0.
  • Not claimed. Intervals.wildcard and Intervals.regexp have the same decode line (Intervals.java:208, :241) but take text patterns. Intervals.term(BytesRef) builds and searches a binary term correctly; only its toString decodes. Faces that show only with assertions on. And a second face of the same root: a non-UTF-8 bound that does build gets a garbled description that can include bytes from behind the bound, and since the description is part of equals/hashCode, two sources over equal prefix bytes can be unequal when those bytes differ.

Why it looks unintended

#
  • The factories take BytesRef, state no UTF-8 precondition, validate nothing and compile their automaton as binary.
  • The javadoc's "term text" wording is TermRangeQuery's own; that class accepts the same bound and prints it with Term.toString.
  • The decode serves only a description. It is no input check: 01 E5 builds when the array has two more bytes behind it.
The full argument317 words
  • No stated precondition. Both factories take BytesRef, validate nothing and document one exception, TooManyClauses (Intervals.java:154-159, :164-175, :244-256, :262-278). Their matching half is byte-based on purpose: the automaton comes from TermRangeQuery.toAutomaton or PrefixQuery.toAutomaton and is compiled as binary (:177-178, :285-287).
  • "Term text" is the sibling's wording. The range javadoc says "The term text at the lower end of the range" (Intervals.java:248, :269). TermRangeQuery's constructor has the same sentence (TermRangeQuery.java:52-53), and upstream's collation tests pass collation keys to it, binary keys of which many are not valid UTF-8 (TestCollationKeyAnalyzer.java:45-52, CollationTestBase.java:80-119).
  • The sibling prints such bounds safely. TermRangeQuery.toString renders both bounds with Term.toString, under the comment "it might not be UTF-8!" (TermRangeQuery.java:168-177). Term.toString(BytesRef): "If the term is not unicode, the raw bytes will be printed instead." (Term.java:104-107).
  • The decode serves only a description. Matching never reads it; Intervals.multiterm calls it a "string representation of the given automaton, mostly used in exception messages" (Intervals.java:348, :365).
  • It is not an input check. The same two bound bytes 01 E5 throw as an exactly sized array and build as a slice of 01 E5 41 42. The outcome depends on bytes outside the BytesRef.
  • Tests and history. No upstream test passes a non-UTF-8 bound to an interval factory (TestIntervals.java:963, :1112, :1148, :1167 use text). The introducing changes (LUCENE-8893, #13562) and #13859 do not discuss non-UTF-8 bounds or the description string.
  • Upstream's recorded position on this pattern. #4016 (LUCENE-2942, Robert Muir, open) calls utf8ToString() in toString methods wrong and proposes printing valid UTF-8 as text and anything else as bytes. #7850 (LUCENE-6792, fixed in 5.4) fixed one such site, TermsQuery.toString, with Term.toString.
  • What is not claimed. That binary bounds are documented as supported. The request is a byte-safe description.
The devil's-advocate check195 words

The strongest case for "intended": interval bounds are "term text"; the BytesRef class note says "Unless otherwise noted, Lucene uses this class to represent terms that are encoded as UTF8 bytes in the index" (BytesRef.java:25-29); utf8ToString documents that it "May throw an AssertionError or a RuntimeException if the data is not well-formed UTF-8" (BytesRef.java:133-136); a review comment on PR #12320 (merged 2023) accepts any exception from the decoders on invalid UTF-8; the package calls its classes experimental (package-info.java:21); the failure is loud, happens at query construction and has a workaround.

Why it fails: the "term text" sentence is TermRangeQuery's own, and that class accepts and prints binary bounds. The decoder's precondition binds its caller, here the factory, which treats the same bytes as binary one line earlier and decodes them only for a display string. The package description's word "experimental" states no UTF-8 precondition and documents no exception. Loudness and the workaround set the priority (Low); they do not make the exception a contract. A maintainer may still read bounds as text only; then what remains is a missing argument check or doc line (Suggested fix, option C).

Trade-offs

  • Text bounds unchanged. The probe's text controls print the same descriptions with and without the fix (MultiTerm({a,c}), MultiTerm(café*)); an earlier check compared 200,000 random Unicode strings and found no difference.
  • Descriptions of non-UTF-8 bounds change. A bound that used to build with a garbled description (a collation key, a slice with bytes behind it) now prints as hex, so its toString text and hash code change. Equal bound bytes now always give equal descriptions.
  • Cost. Term.toString creates a decoder per call, once per bound at construction time.

Downstream note

#

A service that passes byte-truncated text to these factories, for example a prefix cut by bytes instead of by characters, gets an unchecked exception at query construction, so it should catch it or check the bound first.

How it was found

#

A substitution probe ran four calls that consume term bytes once with a text key and once with the binary key 01 F4. Both interval factories threw for the binary key while the text key found its document. A comparison with TermRangeQuery and PrefixQuery over 11,816 bound pairs and an exact model of the decoder then mapped which bounds fail.

The method in full185 words

Method: a substitution probe, then bounded checks (the study's "non-formal" tier: the first signal came from a test, not from a model).

  • Substitution probe. Four calls that consume term bytes on the stock main jars, each run once with a text key and once with the binary key 01 F4. Intervals.range and Intervals.prefix threw for the binary key.
  • Call-site inventory. The 324 source lines that name the three UTF-8 decoders (BytesRef.utf8ToString, UnicodeUtil.UTF8toUTF16, copyUTF8Bytes) in the main sources, comments and the decoders' own definitions included, were listed and classified.
  • Comparison with the byte-based siblings. 2,954 terms of 1 to 3 bytes from a 14-byte alphabet, each as an exactly sized array and as a slice, through both factories and through TermRangeQuery and PrefixQuery: 11,816 pairs per run.
  • Exact model of the decoder. A model of the unvalidated decode equals the real BytesRef.utf8ToString on 17,040,384 inputs with assertions on and off; a deliberately wrong variant of the model is caught.
  • Reduction. First to a test that indexes one document and counts it with TermRangeQuery, then to the factory call alone.

LFV-1483, snapshot of 2026-11-19

Registry title
Intervals.range and Intervals.prefix throw ArrayIndexOutOfBoundsException while the source is built when a bound is not valid UTF-8 and ends in a cut-off multi-byte sequence (a bound that TermRangeQuery and PrefixQuery accept), because the factories decode the bound with utf8ToString() only to build the source's description string (prefix since 8.2.0, range since 9.12.0)
Area
queries / intervals (the multi-term source factories Intervals.range and Intervals.prefix; the description string of MultiTermIntervalsSource)
Priority
Low, rank 682: Intervals.range and Intervals.prefix throw ArrayIndexOutOfBoundsException while the query is built when a bound is not valid UTF-8 and ends in a cut-off multi-byte sequence, in every release since 8.2.0 (prefix) and 9.12.0 (range). It is Low because ordinary text bounds are never affected, a binary or truncated bound on a positional interval query is rare, the failure is loud and happens before any search, and Intervals.multiterm works around it.
Impact class
crash
Impact note
Applications that build an interval query with Intervals.range or Intervals.prefix from a BytesRef bound that is not valid UTF-8 and ends in a cut-off multi-byte sequence at the end of its array (a binary term in an untokenized field with positions, a text prefix cut inside a multi-byte character, or the byte sentinel UnicodeUtil.BIG_TERM as an upper bound) get an ArrayIndexOutOfBoundsException from the factory before any search runs, in every release from 8.2.0 (prefix) and 9.12.0 (range) to 10.6.0, on branch_11x and on main, with -ea and -da, the default IndexWriterConfig, codec and searcher, and no scale; bounds that are valid UTF-8 are never affected, the collation keys tried did not throw with assertions off (they only get a garbled description), hits are never wrong, and Intervals.multiterm with a description supplied by the caller works around it.
Summary
You build an interval source over a range or a prefix of terms with Intervals.range or Intervals.prefix and pass a bound that is not valid UTF-8, for example the two-byte binary term {01 F4}, a text prefix cut in the middle of a multi-byte character, or UnicodeUtil.BIG_TERM. You expect the source to be built, as TermRangeQuery and PrefixQuery are with the same bound (they accept it and find a document that holds the term). Instead the factory throws ArrayIndexOutOfBoundsException before any search runs, because it decodes the bound as UTF-8 text only to build the description string that the source shows in toString and in error messages; bounds that are ordinary text are never affected.
