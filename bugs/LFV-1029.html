ContextSuggestField's javadoc example does not compile: its arguments are not in constructor order

The only code example in the ContextSuggestField javadoc passes the contexts as a List before the weight, but the only constructor takes the weight third and the contexts last, so the example has not compiled on any release since 5.3.0. Documentation only: in constructor order it compiles and works.

The finding in 30 seconds

#

A javadoc example that shows how to add a suggestion with contexts calls the constructor with its arguments in the wrong order.

Background: context suggestions

#
  1. ContextSuggestField indexes a suggestion (a string and an integer weight) together with one or more context strings, for the document suggester in lucene-suggest.
  2. At query time a ContextQuery wraps a completion query such as a PrefixCompletionQuery and keeps (or boosts) only suggestions with the given contexts; hits are scored by weight.

The finding, step by step

#
  1. You want suggestions filtered by context, so you copy the example from the ContextSuggestField class javadoc: document.add(new ContextSuggestField(name, "suggestion", Arrays.asList("context1", "context2"), 4));, the suggestion "suggestion" with weight 4 and two contexts.
  2. You expect it to compile and, with a second document ("suggestive", weight 2, context3) in the index, a ContextQuery for prefix "sugg" on context1 to return 1 hit: "suggestion" with score 4.
  3. Instead javac stops with 1 error, on every release from 5.3.0 to 10.6.0 and on main: "incompatible types: no instance(s) of type variable(s) T exist so that List<T> conforms to int".
  4. Why: the only constructor is ContextSuggestField(String name, String value, int weight, CharSequence... contexts). The example puts the List where the int weight goes. No constructor ever took that order: the example was already wrong when it was added in 2015, and a cleanup five days later moved to varargs without updating it.
  5. Fix: write new ContextSuggestField(name, "suggestion", 4, "context1", "context2"). It compiles, and the context1 query returns "suggestion" with score 4.

Who is affected

#

Developers who add context-aware suggestions with the lucene-suggest document suggester (an @lucene.experimental API) and copy the class's only example, on any release from 5.3.0 or main. Nothing wrong ever runs: javac refuses the line, and the constructor javadoc just below has the right order. Low impact, but plainly wrong.

Mechanism, terms and numbers386 words

The class javadoc of org.apache.lucene.search.suggest.document.ContextSuggestField has one example, "Example usage of adding a suggestion with contexts is as follows:" (ContextSuggestField.java:32-37 on main 645d4fe14a20): document.add(new ContextSuggestField(name, "suggestion", Arrays.asList("context1", "context2"), 4));. Copied into code, that call does not compile on any release (5.3.0 to 10.6.0) or on main. The only constructor is ContextSuggestField(String name, String value, int weight, CharSequence... contexts) (:65), so javac tries to pass the List as the int weight and reports "incompatible types: no instance(s) of type variable(s) T exist so that List<T> conforms to int". No constructor has ever accepted the example's (name, value, List, weight) order: LUCENE-6459 (2015-05-28) wrote it against a (name, Collection, value, weight) constructor, and LUCENE-6515 (2015-06-02) changed the constructor to the varargs form on purpose without touching the example; both first shipped in 5.3.0. In constructor order, new ContextSuggestField(name, "suggestion", 4, "context1", "context2"), it compiles, and a ContextQuery on context1 returns suggestion with weight 4. No runtime code is wrong.

The example (main 645d4fe14a20, ContextSuggestField.java:32-38)

#
// Example usage of adding a suggestion with contexts is as follows:
document.add(
  new ContextSuggestField(name, "suggestion", Arrays.asList("context1", "context2"),  4));

The mismatch

#
  • ContextSuggestField.java:65: the only constructor is public ContextSuggestField(String name, String value, int weight, CharSequence... contexts). Its own javadoc (:55-64) lists @param name, value, weight, contexts in that order.
  • The example's arguments are (String, String, List<String>, int). With the varargs, four arguments fit (name, value, weight, one context), so javac tries to pass Arrays.asList("context1", "context2") as the int weight and reports incompatible types: no instance(s) of type variable(s) T exist so that List<T> conforms to int. The default message names int, not the argument order; only with -Xdiags:verbose does javac list required: String,String,int,CharSequence[] against found: String,String,List<String>,int.
  • No build ever had a constructor in the example's order: a class-file scan of 158 builds (1.9.1 to main; no suggest jar was cached for the 26 builds up to 3.6.2, long before the class existed) finds only (String, String, int, CharSequence[]) from 5.3.0 on.

Why the build does not catch it

#

No current build task compiles ordinary <pre> code blocks in javadoc: renderJavadoc, ECJ lint and the missing-javadoc check run, but none compiles this block. The open issue #9534 (LUCENE-8488) asks for compile-checked javadoc examples in general.

Exposure and likelihood110 words
  • Who is hit. Anyone who copies the only code example in the ContextSuggestField class javadoc to index a suggestion with contexts. The class is @lucene.experimental (ContextSuggestField.java:44).
  • Default vs opt-in. Not a configuration matter: every copy fails, on every release that has the class (5.3.0 to 10.6.0, 104 releases) and on main.
  • Scale. One line, one compile error. The constructor javadoc a few lines below lists the right order, but javac's message ("List<T> conforms to int") does not say the order is the problem.
  • What it does not do. No wrong results, no runtime path, no index change. The constructor, its javadoc and context indexing and querying are right.

Why it looks unintended

#
  • It calls a constructor that never existed: (name, value, List, weight). The constructor was (name, Collection, value, weight) in 2015 and is (name, value, weight, contexts...) since 5.3.0.
  • Its constructor javadoc, the parent SuggestField example and all 75 test calls use (name, value, weight, ...).
  • Varargs was a deliberate change a reviewer asked for; the already-wrong example was not updated.
The full argument202 words

ContextSuggestField.java:32-33: "Example usage of adding a suggestion with contexts is as follows:", in a block marked <code class="language-java"> since #15573 (2026-01-15); nothing calls it pseudo-code. :58-61: @param name, value, weight, contexts. The parent class's example, document.add(new SuggestField(name, "suggestion", 4)); (SuggestField.java:42), matches SuggestField(String name, String value, int weight) (:78).

The devil's-advocate check141 words

Strongest case for "intended" (built by the intended-behaviour checks and the refute review): javadoc code blocks are uncompiled fragments that also leave document and name undeclared; Lucene does not compile-check them (#9534 is open), and in #15225 a maintainer (rmuir) said code examples need to be kept extremely minimal because their maintenance cost is high and they have little validation; the class is @lucene.experimental; and the constructor javadoc just below is right, so a user recovers quickly.

Why it fails: a reader can supply missing declarations, but not a different argument order and type. @lucene.experimental warns that the API may change incompatibly, not that its current docs may be wrong. "Recovers quickly" means low impact, not intended. Every verifier and the adjudication rejected the "intended" reading; it stays at Low because it is a wrong call shape, not a typo.
