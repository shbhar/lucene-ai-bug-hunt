FSTCompletionLookup.build leaves an open, empty temp file behind when its second temp file cannot be created, because it opens the first one before the try block that holds its only cleanup

A small cleanup miss on a failure path: when an FSTCompletionLookup build cannot create its second temp file, it fails as it should but leaves the first one, suggest_RefSorterRaw_0.tmp, behind, empty and still open. build() opens that file before the try block that holds its only cleanup.

The finding in 30 seconds

#

build() opens two temp files before its try block: the first inside the constructor of its ExternalRefSorter, the second directly. The finally of that try is the only code that closes the sorter and deletes the temp files. If the second creation throws, the try is never entered and the first file is orphaned.

Background: three pieces

#
  1. FSTCompletionLookup is one of the suggesters in lucene/suggest. build(InputIterator) reads all entries, sorts them on disk and builds the FST that answers lookup().
  2. For the on-disk sort you pass a Directory and a file-name prefix to the constructor. build() creates its scratch files there with Directory.createTempOutput, which creates a new, empty file and returns an open IndexOutput on it.
  3. A temp file is gone only when its output is closed and the file is deleted. ExternalRefSorter, the helper that buffers the entries for the FST builder, opens its temp file in its constructor and removes it in close().

The finding, step by step

#
  1. You build a suggester: new FSTCompletionLookup(tempDir, "suggest").build(entries). The build creates temp files in tempDir: first suggest_RefSorterRaw_0.tmp, then suggest_input_1.tmp, then its sort files (two for a small build, so four files in all). A successful build deletes them all.
  2. Now tempDir can create only one more file, for example because the process has exactly one file descriptor left. The first creation succeeds and the second throws IOException: Too many open files.
  3. You expect the build to fail with that exception and to leave nothing behind. That is what happens when any other creation fails (the 1st, 3rd or 4th of a small build): tempDir.listAll() is empty.
  4. Instead tempDir.listAll() returns [suggest_RefSorterRaw_0.tmp]: 0 bytes, output never closed. On a file-system directory, 20 such failed builds left 20 empty files and 20 open file descriptors. A forced garbage collection released the descriptors. The files stayed.
  5. Why: build() creates its ExternalRefSorter, whose constructor opens the first temp file, then asks for the second file, and only then enters the try whose finally closes the sorter and deletes the temp files. The sorter is a local variable, so no caller can close it. The empty file stays until someone deletes it by name.

Who is affected

#

Applications that build an FSTCompletionLookup when the temp directory can create exactly one more file: one file descriptor free, an inode limit reached between the two creations, or a Directory whose creations can fail one at a time. Rare. The build fails loudly either way. What stays is one empty file per failed build, until someone deletes it.

Mechanism, terms and numbers924 words

FSTCompletionLookup.build(InputIterator) sorts its input on disk, in the Directory passed to the constructor. It first creates an ExternalRefSorter, whose constructor opens the temp output <prefix>_RefSorterRaw_N.tmp (ExternalRefSorter.java:45-52 on main 781025d6fe32), and then calls tempDir.createTempOutput(prefix, "input", ...), both before the try that starts at FSTCompletionLookup.java:176 (:165-168). The method's only cleanup is the finally of that try (:247-250). When the second creation throws, for example because the process has exactly one file descriptor left, build() is left before the try. The sorter is a local variable, so no caller can close it. The file is in the caller's own directory and stays until someone deletes it by name. The build fails with the IOException it would throw anyway, nothing is lost, a successful build is unaffected and a lookup built earlier keeps answering. What stays per failed build is one zero-length temp file, until someone deletes it, and its output, which is never closed: on a file-system directory its file descriptor stayed open until a forced garbage collection. A failure of any other temp-file creation that was tried leaves nothing: the 1st, 3rd and 4th of a small build, and the other seven of a build that created eight. The order dates from LUCENE-6829 (c855dd5a33f, 2015, first released in 6.0.0), which moved the sorter in front of the try; LUCENE-4209 (2012) had fixed this class "to close its sorter, so that it won't leave temp files behind" in the system temp directory. Every release from 6.0.0 to 10.6.0, branch_11x and main have it. It is a Low priority bug, the smallest kind this list keeps. A validated two-line fix creates the sorter inside the try, where it was until 2015.

Terms

#
  • Temp output. Directory.createTempOutput(prefix, suffix, context) "Creates a new, empty, temporary file in the directory and returns an IndexOutput instance for appending data to this file" (Directory.java:94-102). The name is <prefix>_<suffix>_<counter>.tmp.
  • The sorter. ExternalRefSorter (@lucene.experimental, @lucene.internal, ExternalRefSorter.java:35-36) buffers byte sequences in a temp file and sorts them with an OfflineSorter. Its constructor opens the temp output with the suffix RefSorterRaw (:45-52, the call at :47-50). Its close() is documented "Close the writer and remove any temporary files." (:99-108).
  • The only cleanup of build(). finally { IOUtils.closeWhileHandlingException(reader, writer, externalSorter); IOUtils.deleteFilesIgnoringExceptions(tempDir, tempInput.getName(), tempSortedFileName); } (FSTCompletionLookup.java:247-250).

The bug

#
  1. build() creates an OfflineSorter (FSTCompletionLookup.java:165; this opens nothing) and then new ExternalRefSorter(sorter) (:166). The constructor opens temp file 1, suggest_RefSorterRaw_0.tmp.
  2. build() then creates temp file 2: tempDir.createTempOutput(tempFileNamePrefix, "input", IOContext.DEFAULT) (:167-168).
  3. Only then does the try start (:176).
  4. When step 2 throws, the method is left before the try, so the finally never runs. externalSorter is a local variable and the caller gets only the exception: no caller can close the sorter. A caller can still delete the leftover file by name through its own Directory (listAll(), then deleteFile). A check did that on the in-memory directory and on FSDirectory on Linux, where the descriptor then stayed open on the deleted file until a garbage collection (not run on Windows).
  5. The entries play no part. The failure comes before the first entry is read, so an empty input is enough. The lookup's own state is assigned only at the end of a successful build (:242-245), so a lookup built earlier keeps answering.

Exposure and likelihood391 words
  • Who. Applications that build an FSTCompletionLookup (module lucene/suggest, marked @lucene.experimental) when the temp Directory creates the first temp file of a build and then fails to create the second. Three ways there:
    • exactly one file descriptor free in the process. An earlier check reached this with stock classes in one probe (Linux, a descriptor limit of 200, a plain FSDirectory, a build of one entry after one warm-up build): with one descriptor free it gave FileSystemException: ... Too many open files and left the zero-length suggest_RefSorterRaw_N.tmp. In the same probe nothing was left with no descriptor free, and the build succeeded with two free;
    • an inode limit or a file-count quota reached between the two creations (by reasoning; not executed);
    • a Directory implementation whose creations can fail one at a time (the test's directory).
  • Not a full disk. Creating an empty file on a full disk normally succeeds.
  • What a failed build leaves. One zero-length <prefix>_RefSorterRaw_N.tmp, until someone deletes it; the caller can, by name. Its output is never closed. On a file-system directory (FSDirectory, Linux, OpenJDK 25.0.3) 20 failed builds left 20 empty files and 20 open descriptors, and after forced garbage collection (System.gc()) 20 files and 0 descriptors. It is the JDK that closes the unreachable channel, not Lucene, and this was observed on that platform only. The output of an in-memory ByteBuffersDirectory holds no file descriptor.
  • What does not happen. The build fails with the IOException it would throw anyway. A successful build is unaffected. A lookup built earlier keeps answering after a failed rebuild. No data is lost and no suggestion is wrong.
  • Default configuration. The suggester is opt-in; once you use it, no setting and no scale is needed. An empty input is enough.
  • Likelihood: rare (an estimate, not usage data). The window is one temp-file creation wide, and no report of it was found since 6.0.0 (2016).
  • Not claimed. A denial of service or descriptor exhaustion; any data loss; that 5.x was clean (under the analogous fault an earlier probe on 5.5.5 found one closed, empty temp file left).
  • Related entry. LFV-1495 is a second, separate cleanup gap in the same helper: ExternalRefSorter.close() skips closing its output when the footer write fails. It has another fix site, and its fix does not make this test pass.

Why it looks unintended

#
  • LUCENE-4209 (2012) fixed this class "to close its sorter, so that it won't leave temp files behind".
  • The method's own finally cleans up after every later failure: a failed 3rd or 4th creation leaves nothing.
  • The sorter was inside the try until the 2015 refactoring LUCENE-6829 moved it; its thread speaks of deleting temp files on exception.
The full argument522 words
  • The project treated leftover temp files of this class and this sorter as a bug before. lucene/CHANGES.txt:15406-15409: "LUCENE-4209: Fix FSTCompletionLookup to close its sorter, so that it won't leave temp files behind" (the sentence goes on to name the system temp directory). Its commit 524fa2d4f6c (Robert Muir, 2012) kept a reference to the sorter, which was created inside the try, and added it to the close list of the success path and of the failure path. On the issue (#5281, JIRA type bug) Robert Muir named "not calling Sorter.close() in FSTCompletionLookup" as the first cause, and Uwe Schindler wrote of the follow-up patch: "Patch that enforces cleanup of all temporarily generated files on success or failure ... We should do the same for the other places like BytesRefSorter.", answered "+1" by Robert Muir. That defect was wider than this one: the sorter was not closed on any path, success included. What carries over is the intent, and the shape of the fix.
  • The method's own cleanup covers every later failure. The finally at FSTCompletionLookup.java:247-250 closes the sorter and deletes the temp files. A failed 1st, 3rd or 4th creation of a small build leaves nothing (the probe), and so does each of the other seven creations of a build that created eight temp files (a check with a larger input).
  • The order came in with a refactoring, not a decision. c855dd5a33f (LUCENE-6829, 2015) rewrote the head of build() for the Directory API and moved the sorter in front of the try. On its issue (#7887) Michael McCandless described the patch as "I cutover to TrackingDirectory in OfflineSorter to manage "deleting temp files on exception"". In the same review, about the hunspell temp directory, Dawid Weiss's "we always attempt to remove the temp. stuff ... Otherwise you'd have temp files piling up without any visible reason?" was answered "Exactly!". Nothing in the thread says a failed build may leave a file; the statement order in FSTCompletionLookup is not discussed.
  • Lucene's own rule for Directory users. TestBKD.testWithExceptions, for BKDWriter, another class that creates its temp files with Directory.createTempOutput (OfflinePointWriter.java:49): "Make sure we close open files, delete temp files, etc., on exception" (TestBKD.java:287). After the injected IOException the test asserts that the directory lists no file (TestBKD.java:331-335). The test framework's directory refuses to close with an unclosed output ("MockDirectoryWrapper: cannot close: there are still ... open files", MockDirectoryWrapper.java:883). No test under lucene/suggest/src/test injects a failing Directory, which is why no test saw this.
  • The sibling suggester leaves nothing. AnalyzingSuggester.build under the same fault leaves no file and no open output (the probe). It opens only one output before its try (AnalyzingSuggester.java:396-412), so it has no second creation in front of the try and no window of this kind. This is weak consistency evidence, not an explicit guard.
  • What the javadoc says. Nothing either way. Lookup.build: "Builds up a new internal Lookup representation based on the given InputIterator. The implementation might re-sort the data internally." (Lookup.java:178-182). The expectation rests on the points above, not on a javadoc promise.
The devil's-advocate check219 words

The strongest case for "intended": no javadoc promises that a failed build cleans up. The class is @lucene.experimental and ExternalRefSorter is @lucene.internal. build() has acquired resources before its try since 2011 (SOLR-2888: its own two temp files), and the 2012 fix left that window alone. The build fails loudly, a process that is out of file descriptors has bigger problems, and all that lasts is one zero-length file, in a directory the caller owns and can clean. The tested JDK released the descriptor at a garbage collection, and no public report was found in about ten years. A maintainer could reasonably close a stand-alone issue as too minor.

Why it fails: nobody chose this. The sorter was inside the try until the 2015 refactoring moved it, and that refactoring's own thread speaks of deleting temp files on exception. The written intent (LUCENE-4209) names this class and this object, and its fix closed the sorter on failure as well as on success. The method's own finally cleans up for every later failure. The trigger is an IOException that Directory.createTempOutput and Lookup.build declare, reached with a stock FSDirectory and a real "Too many open files". "Experimental" is about API stability. What the argument does establish is the size: this is the smallest kind of Low. The fix is two lines.

Create the sorter inside the try, where it is first used; two lines (validated) (recommended)

#

Declare externalSorter as null in front of the try and create it inside, right before the FSTCompletionBuilder that uses it (after FSTCompletionLookup.java:200). That is where the sorter was created until LUCENE-6829, so the finally that LUCENE-4209 extended covers it again: IOUtils.closeWhileHandlingException skips a null.

Then only one temp output is open before the try, as in AnalyzingSuggester. If creating it fails, nothing else is open.

     OfflineSorter sorter = new OfflineSorter(tempDir, tempFileNamePrefix);
-    ExternalRefSorter externalSorter = new ExternalRefSorter(sorter);
+    ExternalRefSorter externalSorter = null;
     IndexOutput tempInput =
         tempDir.createTempOutput(tempFileNamePrefix, "input", IOContext.DEFAULT);
...
       tempDir.deleteFile(tempInput.getName());
 
+      externalSorter = new ExternalRefSorter(sorter);
       FSTCompletionBuilder builder =
           new FSTCompletionBuilder(buckets, externalSorter, sharedTailLength);

Trade-offs

  • Order of the temp files. They are created as input, sort, RefSorterRaw, sort in place of RefSorterRaw, input, sort, sort, so the counters in their names change. The names are not API.
  • Fewer files open at once. The sorter's temp file is no longer open while the input is read and sorted.
  • No other behaviour change. A successful small build still creates four temp files and deletes them all; the probe's lookup answers the same.

  • Scratch worktree of 781025d6fe32, gradle: the test fails on the stock tree and passes with the fix, assertions on and off.
  • The closest suites, --tests 'org.apache.lucene.search.suggest.fst.*': 25 tests in 4 classes (24 upstream tests in TestBytesRefSorters, TestFSTCompletion and TestWFSTCompletion, plus the new test), 0 failures, 1 skipped by the framework, assertions on and off (seed DEADBEEF).
  • The whole module, :lucene:suggest:test: 237 tests in 32 classes, 0 failures, 7 skipped by the framework (assertions on).
  • :lucene:suggest:check -x test passes (licenses, format, ecjLint, forbiddenApis) with the fix and the test.
  • Standalone runner with the fixed class ahead of the jars: the test passes (assertions on and off). The probe: every failed creation of the four-file build leaves nothing, and 20 failed builds on a file-system directory leave 0 files. The build with eight temp files: every failed creation leaves nothing.

Keep the order and guard the second creation; eight lines (validated)

#

Wrap tempDir.createTempOutput(tempFileNamePrefix, "input", IOContext.DEFAULT) in a try and, when it throws, close the sorter with IOUtils.closeWhileSuppressingExceptions(t, externalSorter) before rethrowing. This is the fix sketch the finding was first checked with.

     ExternalRefSorter externalSorter = new ExternalRefSorter(sorter);
-    IndexOutput tempInput =
-        tempDir.createTempOutput(tempFileNamePrefix, "input", IOContext.DEFAULT);
+    // the sorter above already holds an open temp output: close it if this creation fails
+    IndexOutput tempInput;
+    try {
+      tempInput = tempDir.createTempOutput(tempFileNamePrefix, "input", IOContext.DEFAULT);
+    } catch (Throwable t) {
+      IOUtils.closeWhileSuppressingExceptions(t, externalSorter);
+      throw t;
+    }

Trade-offs

  • Eight lines and a second try in front of the main one. The creation order and the file names stay as they are. The next resource opened before the try would need the same guard.
  • It leans on ExternalRefSorter.close(). The guard cleans up through close(), which writes a footer to the sorter's file before it closes the output (ExternalRefSorter.java:91-97, :101-108). If that write fails as well, the file is deleted but its output is not closed, which is the related entry LFV-1495. A check ran this: with the input creation failing and every write to the sorter's file failing, this variant leaves no file and one output not closed. The recommended fix creates nothing and leaves nothing in that case, because nothing is open yet when the input creation fails.

What the checks validated

Scratch worktree, gradle: the test passes (assertions on and off), the suggest.fst test package passes (25 tests, assertions on and off) and :lucene:suggest:check -x test passes. Standalone: the test passes, and nothing is left for any failed creation of the probe's four-file build and of the build with eight temp files. The whole module was not run with this variant.

A larger cleanup: OfflineSorter owns its temp files (not run)

#

Dawid Weiss's open design wish #8529 (LUCENE-7477) proposes that OfflineSorter create, own and clean up its temp files. If that were done, this window might disappear as a side effect.

Trade-offs

A redesign of the sorter API, far larger than this defect needs.

Downstream note

#

Solr's FSTLookupFactory builds this lookup on one shared directory over the system temp directory (java.io.tmpdir), so there each such failed build leaves its empty file in the system temp directory.

How it was found

#

A fault-injection matrix ran seven users of temp files in a Directory on the real jars and failed one temp-file operation at a time: 359 cases per build, checked against the rule that a failed build leaves no temp file and no open output. Failing the second creation in FSTCompletionLookup.build left one file and one open output.

The method in full188 words

Method: fault injection against a written rule (the study's "semi-formal" tier: exhaustive over a small fault space on the real jars; a reading that counts fault injection as testing would call it non-formal).

  • The matrix. Seven users of temp files in a Directory (OfflineSorter.sort, five suggester builds, BKDWriter past maxPointsSortInHeap) on the main and 10.6.0 jars. One fault per case: the k-th temp output fails on create, on its first write, on its 40th write or on close, or the n-th read fails. 359 cases per build.
  • The rule. After a failed offline sort or suggester build, no temp file is left and no output or input is open.
  • The line. For FSTCompletionLookup.build, failing creation k=1 (the second) reported one file left and one open output on both builds; failing creations 0, 2 and 3 left nothing.
  • Recall. The same matrix flagged the known leftover of SortedInputIterator (LFV-790) unprompted.
  • Reduction. Reading build() gave the statement order. The case was reduced to one public-API JUnit test, and then to the one-method test of the repro.
  • No model checking, SMT solving or theorem proving was involved.

History

#

Introduced by LUCENE-6829 (c855dd5a33f, 2015), first released in 6.0.0: it moved the sorter in front of the try and made its constructor open a temp output through the Directory. Every executed release from 6.0.0 to 10.6.0, branch_11x and main fail. Not fixed upstream.

Versions tested7 rows

Introduced by c855dd5a33f on trunk, "LUCENE-6829: OfflineSorter now uses Directory API; add Directory.createTempOutput and IndexOutput.getName" (Michael McCandless, 2015-10-15; a pre-GitHub commit, the issue is #7887 in the migrated archive). It replaced the two Files.createTempFile calls at the head of build() by new ExternalRefSorter(sorter), whose constructor from this commit on opens its temp output through the Directory, followed by tempDir.createTempOutput(...), both before the try. Before it the sorter was created inside the try and closed by the finally (LUCENE-4209, 524fa2d4f6c, 2012). The later reformatting commit 2cbf261032d (LUCENE-9570, 2021) only re-wrapped the createTempOutput line. First release 6.0.0.

Not a regression from a clean state. Before 6.0, build() created its own two temp files before the try (since SOLR-2888, 2011). A probe on the 5.5.5 jars found that a failing second creation there left one closed, empty temp file. That older shape is not claimed here. What 6.0.0 added is the open output held by a sorter that no caller can reach.

The coming release. branch_11x (daa54f2e0cd3, 11.0.0-SNAPSHOT) has the same two files byte for byte, and the test fails there with assertions on and off, so 11.0 would ship it. It is not new in 11.0: 10.6.0 has it too.

Not fixed upstream as of 2026-11-14: main is still 781025d6fe32, and the last commit on FSTCompletionLookup.java is #14228 (2025-02-24), a lint change.

The minimal test needs the test framework of 9.1 and later. For older releases an earlier check ran a main() form of it with no test framework: the same fault, and the same observations (the file is left, its output not closed). "Affected 6.0.0 to 10.6.0" rests on the source and on the releases executed below. By the source, all 93 releases have the three statements in this order: at the 84 release tags of the local history clone, and at the nine tags it lacks (8.8.2 to 8.11.4), read from the upstream repository.

LFV-1493, snapshot of 2026-11-22

Registry title
FSTCompletionLookup.build leaves an open, empty temp file behind when its second temp file cannot be created: it creates its ExternalRefSorter, whose constructor opens a temp output, before the try block that holds its only cleanup (every release since 6.0.0)
Area
suggest / FSTCompletionLookup build (temp outputs of its offline sort)
Priority
Low, rank 1235: In every release since 6.0.0, an FSTCompletionLookup build whose second temp file cannot be created leaves one empty temp file in the temp directory and never closes its output (on FSDirectory on Linux its file descriptor stayed open until a forced garbage collection). It is Low because the suggester is opt-in, the trigger is a single temp-file creation that fails right after one that succeeded (for example exactly one file descriptor free), the build already fails loudly and nothing is lost.
Impact class
minor
Impact note
Hits applications that build an FSTCompletionLookup (lucene/suggest, marked @lucene.experimental; Solr's FSTLookupFactory builds one on a shared directory over the system temp directory [read]) and only when the temp Directory creates the first temp file of a build and then fails to create the second, which on a file system means exactly one file descriptor free, an inode limit or a file-count quota reached between the two creations (by reasoning, not executed), or a Directory implementation whose creations can fail one at a time: each such failed build leaves one zero-length <prefix>_RefSorterRaw_N.tmp in the temp directory until someone deletes it and never closes its output (on FSDirectory on Linux its file descriptor stayed open until a forced garbage collection), while the build fails loudly with the IOException it would throw anyway, a successful build is unaffected, a lookup built earlier keeps answering and no data is lost; default settings and no scale are needed; the releases from 6.0.0 to 10.6.0 and main [exec on 17 of the releases and on main, see Affected versions; the others by reading the source], the same with -ea and -da.
Summary
You build an FSTCompletionLookup suggester with a temp Directory, and the directory cannot create the second of the temp files the build asks for, for example because the process has exactly one file descriptor left. You expect the failed build to close and delete the temp file it had already created, as its finally block does when a later step of the build fails (with one gap of its own, LFV-1495) and as the 2012 fix LUCENE-4209 set out to do ('close its sorter, so that it won't leave temp files behind' in the system temp directory). Instead build() throws the IOException before it reaches the try block that holds its only cleanup, so the sorter's temp file <prefix>_RefSorterRaw_N.tmp stays in the directory, empty and with its output still open (until garbage collection on a file-system directory), and no caller can close it; the file stays until someone deletes it by name.
