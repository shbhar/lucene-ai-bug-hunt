JapaneseNumberFilter and KoreanNumberFilter merge a keyword-protected word into the number before it

A keyword marker protects a word like the name 京一 from JapaneseNumberFilter only when the word starts a number: 社員の三京一 still becomes the single token 30000000000000001 instead of 3, 京一, so a search for 京一 misses it. KoreanNumberFilter has the same code; both since they were added (6.0.0, 8.2.0).

The bug in 30 seconds

#

The number filters join consecutive numeral tokens into one number. A keyword marker should keep a token out of that, but the filters look at the flag only on the token that starts the number, never on the tokens they append to it.

  1. Build the analyzer of the upstream testName test: JapaneseTokenizer, then SetKeywordMarkerFilter protecting 京一 (a name that can also be read as the number 10000000000000001), then JapaneseNumberFilter. 田中京一 gives 田中, 京一: the name is kept.
  2. Analyze 社員の三京一. The tokenizer gives 社員, の, 三, 京一. You expect 社員, の, 3, 京一: 三 becomes 3 and the protected 京一 stays as it is.
  3. You get 社員, の, 30000000000000001 (offsets 3-6). The filter checked the keyword flag on 三, which starts the number, then appended 京一 because it is made of numeral characters, and read 三京一 as 3 × 10^16 + 1.
  4. Korean, same chain with 경일 protected: the name 오경일 (tokens 오, 경일) gives 50000000000000001 instead of 5, 경일; 이 구조는 튼튼하다 ("this structure is sturdy") with 구조 protected gives 29000000000000, 는, ...
  5. No error. A TermQuery for 京一 misses the document and delete-by-term leaves it live, while a TermQuery for 30000000000000001 finds it: the terms and offsets are the same as with no keyword marker at all (the number even carries 京一's keyword flag).

Who is affected

#

Applications that add JapaneseNumberFilter or KoreanNumberFilter (opt-in; the stock analyzers do not use them) and protect a numeral-looking word with a keyword marker, as the javadoc suggests. When that word comes inside a number (typically right after a numeral), it is lost from the terms and a made-up number is indexed instead; ordinary Korean text does that (오경일, 이 구조는).

Mechanism, terms and numbers538 words

JapaneseNumberFilter and KoreanNumberFilter turn numbers written in kanji or hangul into digits by joining consecutive numeral tokens into one number. Their javadoc warns that they may also normalize words that only look like numbers, such as the name 京一, and says the filter "respects the KeywordAttribute, which can be used to prevent specific normalizations from happening". It checks the flag only on the token that starts a number: a protected word met while a number is being composed (typically right after a numeral token) is appended to the number. With 京一 protected, 社員の三京一 gives 30000000000000001 instead of 3, 京一; with 경일 protected, the Korean name 오경일 gives 50000000000000001. The terms and offsets are the same as without the marker, no error is raised, a term query or delete-by-term on the protected word misses the document, and a term query for the made-up number finds it. Both filters are opt-in; both have had the defect since they were added (Japanese 6.0.0, Korean 8.2.0), through 10.5.2 and main. The recommended fix: a keyword token ends the number, and the number keeps the attributes of its own tokens (which also fixes the known #10130).

Terms

#
  • Number filter: JapaneseNumberFilter (kuromoji) and KoreanNumberFilter (nori) rewrite numbers written with kanji or hangul numerals into Arabic digits: 三千2百２十三 gives 3223 (a javadoc example). A number may span several tokens; the filter reads ahead and joins them. They do not use context or part of speech, so words made of numeral characters are also rewritten: the name 京一 (京 = 10^16, 一 = 1) becomes 10000000000000001, the noun 구조 ("structure"; 구 = 9, 조 = 10^12) becomes 9000000000000.
  • Keyword marker: SetKeywordMarkerFilter (or another filter that sets KeywordAttribute) flags chosen words so that later keyword-aware filters leave them alone. Both number filters declare themselves keyword-aware for exactly the case above.

The mechanism (main a9779ef3c193)

#

For the tokens 三, 京一 with 京一 protected:

  1. JapaneseNumberFilter.java:159-161: if (keywordAttr.isKeyword()) { return true; } runs once, on 三, the token that would start a number. It is not a keyword, so a number starts (:177-179: numeralTerm = isNumeral(term)).
  2. The loop (:181) reads the next token, 京一, which carries keyword=true (:189), and appends 三 to the buffer (:203).
  3. :205-207 decide whether 京一 continues the number: numeralTerm = isNumeral(term) || isNumeralPunctuation(term);. 京一 is all numeral characters (isNumeral, :458-475), so it is appended too; a decimal point or thousands separator would continue the number the same way. The keyword flag is not read.
  4. :211-225: 三京一 is normalized to 30000000000000001 and emitted with the offsets of both tokens; 京一 is gone.

KoreanNumberFilter has the same code here: keyword check :148-150, predicate :196. The number is emitted with the attributes left by the last read, and only the term and offsets are overwritten (:220-222 / :209-211): the look-ahead token's when another token follows, the last token's at the end of the stream. In 社員の三京一 the stream ends at 京一, so stock emits 30000000000000001 with 京一's keyword=true; in 이 구조는 튼튼하다 the look-ahead is 는, so the number has no flag and 는's part of speech.

Exposure and likelihood317 words
  • Who is exposed. Chains that use either number filter (SPI names japaneseNumber, koreanNumber) with a keyword marker in front of it. JapaneseAnalyzer and KoreanAnalyzer do not use the number filters.
  • What it takes. A protected word met while a number is being composed: right after a numeral token, or after a decimal point or thousands separator inside a number (a keyword-marked separator is absorbed the same way). Executed examples: the name 오경일 (surname 오, given name 경일, split by the tokenizer without a user dictionary), 이 구조는 튼튼하다 and 社員の三京一 (a constructed phrase). The spaced Korean example needs the space token removed (by the SP stop filter of the upstream test chain, or by discardPunctuation=true); with punctuation kept and no stop filter the space ends the number. The marker matches whole tokens: protecting 千万 does nothing where the tokenizer emits 千 and 万. Protected words in other positions are unaffected.
  • What the user sees. Nothing fails: the index and the queries get the terms the filter produces with no marker. TermQuery(body:京一) misses a document whose body is 社員の三京一 and finds one with 田中京一; deleteDocuments(body:京一) leaves the first one live; TermQuery(body:30000000000000001) finds it, although with the protection applied it would hold 3 and 京一. A search for the numeral (3) misses it too: the index holds no 3. An analyzed query goes through the same chain, so query text with the same numeral before the word still matches (inference). Other fields, other values and other documents are unaffected; CheckIndex is clean.
  • How likely. Rare: it needs two opt-in pieces and a protected all-numeral word right after a numeral; nobody has reported it since 2015. Within that configuration it is deterministic and one document reproduces it.
  • Downstream (read, not run). A downstream search server's documentation recommends the same nori chain as the upstream tests, and its keyword-marker filter can precede it.

Why it is a bug, not intended

#
  • Both javadocs: the filter "respects the KeywordAttribute, which can be used to prevent specific normalizations from happening", with this very example (京一 / 경일).
  • Lucene's analysis docs: keyword-aware filters "skip modification" of keyword tokens.
  • Read per token, as the analysis docs describe keyword handling, stock is inconsistent: a protected 천만 survives in 천만 원 but not in 삼천만 명.
The full argument220 words
  • Class javadoc (JapaneseNumberFilter.java:69-72, KoreanNumberFilter.java:69-72): "This filter may in some cases normalize tokens that are not numbers in their context. For example, is 田中京一 is a name and means Tanaka Kyōichi, but 京一 (Kyōichi) out of context can strictly speaking also represent the number 10000000000000001. This filter respects the KeywordAttribute, which can be used to prevent specific normalizations from happening."
  • Core analysis docs (lucene/core/.../analysis/package-info.java:487-490): "Keyword-aware TokenStreams/-Filters skip modification of tokens that return true from this attribute's isKeyword() method."
  • The documented limits do not include it. The javadoc lists 15,7 becomes 157 (be aware of this weakness) (:60), the punctuation requirement (:40-47), stacked tokens left untouched (:63-64) and attributes taken from the last composing token (:74-82), but not "keyword protection only for the first token of a number".
  • Tests and history. testName (TestJapaneseNumberFilter.java:161-195, TestKoreanNumberFilter.java:178-219) protects 京一 / 경일 only after a non-numeral word. The keyword check and the predicate are unchanged since each filter's first commit (LUCENE-3922, LUCENE-8812); neither issue, no CHANGES entry and no comment limits the protection to the first token.
  • Inconsistent stock behaviour, read per token. With 천만 protected, 천만 원 keeps 천만, while 삼천만 명 gives 30000000. (Read per run of numeral tokens, the devil's-advocate reading below, this is consistent.)
The devil's-advocate check225 words

The strongest "intended" reading, built by the intended-behaviour checker and rated moderate by the cross-model reviewers: KeywordAttribute only says keyword-aware streams "can decide to modify a token based on the return value of isKeyword()" (KeywordAttribute.java:22-27); the filter composes logical numbers, so the whole run started by an unprotected token could be read as the unit of normalization, and keeping a standalone protected 천만 while composing 삼 + 천만 is then consistent first-token behaviour; and the literal reading costs something: with 천만 protected, stock turns 삼천만 명 into the right amount 30000000, the fix into 3, 천만.

Why it fails: once the filter declares that it respects the attribute, the package contract says keyword-aware filters skip modification of keyword tokens, which is a per-token rule; the "numeric context" or run reading is in no javadoc, comment, test, commit or issue, and the filter "does not use any part-of-speech information" (JapaneseNumberFilter.java:66-67); read per token, stock keeps the same protected word in one position and drops it in another; and the 천만 cost is about the fix direction, not evidence of intent. What the case gets right: a fix changes long-standing output for some real numbers, so documenting the limit is a fair alternative to offer; and it does not settle which attributes the split-off number should carry (see Suggested fix).

Suggested fix

#

Recommended A keyword token ends the number, and the number keeps its own tokens' attributes (A+C)

A keyword token ends the number (!keywordAttr.isKeyword() && in the continuation check), and the number keeps the attributes of its own tokens: restore the last numeral token's state and the first one's position increment before emitting it (the #10130 fix). The new tests and every non-skipped kuromoji and nori test pass. Cost: with 천만 protected, 삼천만 now gives 3, 천만.

    State lastNumeralState = null;
    final int firstPositionIncrement = posIncrAttr.getPositionIncrement();
    ...
      lastNumeralState = captureState();
      moreTokens = input.incrementToken();
    ...
        numeralTerm = !keywordAttr.isKeyword() && (isNumeral(term) || isNumeralPunctuation(term));
    ...
      restoreState(lastNumeralState);
      posIncrAttr.setPositionIncrement(firstPositionIncrement);
    ...
      keywordAttr.setKeyword(false); // from fix A; redundant once the state is restored

Trade-offs

  • Intended change: as for A: a protected word right after a numeral stays a word, and the numeral before it is normalized alone; the 천만 cost below applies too.
  • C's own change: every composed number that is followed by another token now carries the part of speech, reading and other attributes of its own last token, and its first token's position increment, instead of the next token's. A keyword token ends the number, and the number does not take its flag (A, smaller) (validated by the checks)

fixA.diff, +4/-1 in each filter (two code lines and two comments). The first line stops the composition at a keyword token, which is then emitted unchanged on the next call (it is already the captured look-ahead token). The second line is safe because a number starts only at a non-keyword token (:159), and with the first line every continuation token is non-keyword too, so a composed number is never a keyword.

        term = termAttr.toString();

        numeralTerm = !keywordAttr.isKeyword() && (isNumeral(term) || isNumeralPunctuation(term));

    ...
      offsetAttr.setOffset(startOffset, endOffset);

Trade-offs

  • Not fixed by A: the split-off number keeps the protected token's other attributes (the #10130 mechanism; A overwrites only term, offsets and the flag), among them its position increment, part of speech and reading: 이 구조는 튼튼하다 gives 2 with position increment 2 instead of 1 (increments 2, 2 instead of 1, 2, so the positions after it shift by one), and 社員の三京一 gives 3 with 京一's part of speech and reading キョウイチ. The doc's tests pass with A because they do not assert these attributes.
  • Intended change: a protected word right after a numeral stays a word, and the numeral before it is normalized alone (오경일 gives 5, 경일; 이 구조는 gives 2, 구조, ...).
  • Cost: a protected word that is also a real part of a number splits that number: with 천만 protected, 삼천만 명 gives 3, 천만 instead of 30000000, and 일천만 원 gives 1, 천만. The user asked for 천만 not to be normalized, and stock already keeps it in 천만 원.
  • Index-time output changes, so existing indexes keep the old terms until reindexed.
  • One extra boolean check per continuation token.

Downstream note

#

Downstream, a rule that term-matches a protected word on such a field (an exclusion, an alert, a delete-by-term) silently skips documents where the word follows a numeral, and a term match on the made-up number hits them.

How it was found

#

Bounded-exhaustive model checking on the real classes: all 531,440 abstract token streams of length 1 to 6 over 9 symbols (none starting with a stacked synonym) went through both stock filters against six invariants. "A keyword-marked token is emitted with its own term and offsets" failed on 103,089 per filter; the shortest is a numeral, then a keyword-marked numeral.

The method in full265 words

Method: bounded-exhaustive model checking of the real classes (a hunt unit, CJK number filters, 2026-10-26, main ea57360912ed; the hunt's "semi-formal" tier: exhaustive checking of the real jar against an exact oracle, no model checker or prover).

  • The finder, an AI tool, wrote a checker (TokenStreamModelCheck.java) that builds every token stream of length 1 to 6 over 9 abstract token kinds (a digit, an exponent, a decimal point, a word, a stacked synonym, a keyword-marked numeral, a numeral after a removed token, and two decompounded forms) that does not start with the stacked synonym (531,440 streams), and runs it as a canned stream through the stock JapaneseNumberFilter and KoreanNumberFilter.
  • Six invariants, each tied in the unit's model notes to a javadoc statement: no input token vanishes, a number holds no text from outside its span, its attributes come from inside its span, positions, position length 1, and KW: a keyword-marked token is emitted with its own term and offsets (from the class javadoc's keyword sentence). KW failed on 103,089 of 531,440 streams per filter, shortest dk (a digit, then a keyword-marked numeral); with the one-line predicate change, KW fails on 0.
  • The other invariant failures belong to two already reported defects found in the same unit (#10130; #11398 / #11397 / #11395); each of the three fixes clears exactly its own invariants, and all three together satisfy all six.
  • The finder reduced the KW counterexample to the upstream testName analyzer and wrote the JUnit pair; the reproducer later found the natural Korean name 오경일, and the devil's advocate 이 구조는 튼튼하다.

Bug record

#

LFV-360, snapshot of 2026-10-29

Registry title
JapaneseNumberFilter and KoreanNumberFilter honour KeywordAttribute only on the token that starts a number, so a keyword-protected numeral word directly after a numeral token is merged into the number and normalized (三 + protected 京一 gives 30000000000000001, the name 오경일 with 경일 protected gives 50000000000000001) (released since 6.0.0 / 8.2.0)
Area
analysis / kuromoji and nori number filters (JapaneseNumberFilter, KoreanNumberFilter: KeywordAttribute inside a number composition)
Priority
Low, rank 258: Needs the opt-in Japanese or Korean number filter with a keyword marker that protects a numeral word.
Impact class
silent wrong results
Impact note
Applications that add JapaneseNumberFilter or KoreanNumberFilter (opt-in: neither JapaneseAnalyzer nor KoreanAnalyzer uses them) and, as the class javadoc suggests, a keyword marker in front of it to protect numeral-looking words (names such as 京一 or 경일, words such as 구조): whenever a protected word directly follows a numeral token (三京一, the name 오경일, or 이 구조 in the documented nori chain that removes the space), it is silently folded into the number, so the index and query terms are what the filter gives with no marker at all, and term queries or delete-by-term on the protected word miss that document (executed); protected words in other positions are unaffected; deterministic, ordinary scale, every release of each filter (ja 6.0.0, ko 8.2.0, through 10.5.2) and main.
Summary
You put SetKeywordMarkerFilter in front of JapaneseNumberFilter (or KoreanNumberFilter) to protect a word made of numeral characters, as the class javadoc suggests for the name 京一, and expect that word to come out unchanged wherever it occurs. That works when the word starts a number (田中京一 gives 田中, 京一, the upstream testName), but the filter checks the keyword flag only on the first token of a number and accepts every following numeral token without looking at it, so a protected word right after a numeral is appended to the number: 社員の三京一 gives the single token 30000000000000001 (offsets 3-6) instead of 3 and 京一, and the Korean name 오경일 (tokens 오 / 경일, 경일 protected) gives 50000000000000001. No error is raised; a TermQuery for the protected word then misses the document (executed).
