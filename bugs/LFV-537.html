JaroWinklerDistance.setThreshold javadoc says a negative value gives the Jaro distance, but it gives Jaro-Winkler

The setThreshold javadoc says a negative value gives the Jaro distance, but a negative threshold adds the Winkler prefix bonus exactly as 0 does: martha/marhta scores 0.9611, not its Jaro score 0.9444. Only a threshold of 1 or more gives plain Jaro, so the javadoc is the side to fix.

The finding in 30 seconds

#

getDistance computes the Jaro score j (JaroWinklerDistance.java:103) and adds the bonus unless j < threshold (:104). j is never below 0 and the bonus vanishes at j = 1, so 0 or less always adds it and 1 or more always returns plain Jaro (Lucene's unboosted value). The javadoc (:109-110) promises plain Jaro for a negative value.

Background: Jaro and Jaro-Winkler in Lucene

#
  1. JaroWinklerDistance is one of the StringDistance classes that Lucene's spell checkers (and applications) use to score how similar two words are, from 0 (nothing in common) to 1 (identical).
  2. The Jaro score counts matching letters and swapped pairs: for martha/marhta, 6 matches and one swapped pair give (6/6 + 6/6 + 5/6) / 3 = 0.9444.
  3. Jaro-Winkler adds a bonus for a shared prefix: here 0.1 x 3 x (1 - 0.9444) = 0.0167, so 0.9611. Lucene skips it when the Jaro score is below a threshold, 0.7 by default.

The finding, step by step

#
  1. You want plain Jaro similarity from JaroWinklerDistance, so you do what its javadoc says ("Set to a negative value to get the Jaro distance") and call setThreshold(-1).
  2. For "martha" and "marhta" the Jaro score is (6/6 + 6/6 + 5/6) / 3 = 0.9444 (6 matching letters, one swapped pair), so you expect getDistance to return 0.9444.
  3. Instead you get 0.9611, the Jaro-Winkler score: the shared prefix "mar" adds a bonus of 0.1 x 3 x (1 - 0.9444) = 0.0167.
  4. Why: getDistance leaves the bonus out only when the Jaro score is below the threshold, and a Jaro score is never below 0. So any negative threshold adds the bonus, exactly like 0 (pairs with no matching character return 0 before the bonus step); only 1 or more gives plain Jaro, Lucene's unboosted value.
  5. Nothing fails or warns, and scores only go up: abcdef/abxyzw gets 0.6444 instead of its Jaro score 0.5556, while the default threshold 0.7 leaves it at 0.5556.

Who is affected

#

Only applications that use JaroWinklerDistance directly and call setThreshold with a negative value to get plain Jaro, as the javadoc says. They silently get Jaro-Winkler scores (never lower, still in [0, 1]), so a spell checker's accuracy cut-off or their own cut-off can let more pairs through. The default 0.7 is unaffected, and no Lucene code calls the setter.

Mechanism, terms and numbers634 words

JaroWinklerDistance (suggest module) adds a Winkler bonus for a shared prefix to the Jaro score j, but skips it when j is below a threshold, 0.7 by default. The setThreshold javadoc says "Set to a negative value to get the Jaro distance." That is false: getDistance skips the bonus only when j < threshold, and j is never negative, so a negative threshold adds the bonus to every pair that has a matching character (pairs with none return 0 first), exactly as 0 does. setThreshold(-1) then getDistance("martha", "marhta") returns 0.96111107 (Jaro-Winkler) instead of 0.9444444 (Jaro). Only a threshold of 1 or more gives plain Jaro, meaning Lucene's own unboosted value.

The sentence and the condition were written in the same 2008 commit (LUCENE-1297), so the sentence was never true; every release from 2.4.0 to 10.6.0 and main carries it. The threshold condition follows the usual Winkler boost-threshold rule and the rest of the class's documentation agrees with it, so this is a documentation defect: the proposed fix is the javadoc, with a code change only as an option. Not security-sensitive.

The code (main 645d4fe14a20)

#
  • JaroWinklerDistance.java:29: private float threshold = 0.7f;
  • :103: float j = ((m / s1.length() + m / s2.length() + (m - mtp[1]) / m)) / 3; Each term is in [0, 1], so j is in [0, 1]; pairs with no match return 0 earlier (:100-102).
  • :104: float jw = j < getThreshold() ? j : j + Math.min(0.1f, 1f / mtp[3]) * mtp[2] * (1 - j); where mtp[2] is the common prefix length and mtp[3] the longer length (:85-93).
    • threshold 0 or less: j < threshold is never true, so the bonus is always added (it is 0 for a pair with no common prefix). NaN acts the same way, because j < NaN is false. Pairs with no matching character never reach this line: they return 0 at :100-102 for every threshold.
    • threshold 1 or more: either j < threshold (plain j), or j == 1 and the bonus is multiplied by 1 - j = 0. So the result is always plain Jaro, in the sense below.
  • What "plain Jaro" means here: Lucene's own unboosted value, j from :103, or 0 for a pair with no matching character (:100-102). It is not textbook Jaro in every detail: Lucene compares UTF-16 chars and halves the transposition count with integer division (:93), so aaaabc/aaabca gives 0.9444444 at threshold 1, where textbook Jaro (1.5 transpositions) gives 0.9166667; and ("", "") returns 0 at every threshold, where textbook Jaro gives 1 (the separate #3901). The bonus is not textbook Jaro-Winkler either: the prefix is not capped at 4 and the scale is min(0.1, 1 / longer length) (:85-93, :104), so abcdefgh/abcdefgx gives 0.975 at the default, where textbook Jaro-Winkler gives 0.95. None of this changes the bug: in this class, "the Jaro distance" can only mean the unboosted value.
  • :108-113, the false sentence: "Sets the threshold used to determine when Winkler bonus should be used. Set to a negative value to get the Jaro distance."
  • :118-123, the getter, which matches the code: "Returns the current value of the threshold used for adding the Winkler bonus. The default value is 0.7."

Exposure and likelihood188 words

A spot check of three servers, not a survey of applications.
  • Effect. Pairs with a shared prefix score higher, never lower, so a spell checker's accuracy cut-off (the score read in SpellChecker and DirectSpellChecker) can let a few more candidates through and their order can change; an application's own similarity cut-off can accept more pairs. Silent, deterministic, on every call.
  • Scale. Every release since 2.4.0 (2008); no public report was found in 18 years, which fits the small, easy-to-miss effect. Impact minor, priority Low.

Why it looks unintended

#
  • The javadoc promises plain Jaro for a negative value (JaroWinklerDistance.java:109-110); the code adds the bonus instead, as threshold 0 does.
  • The getter's javadoc matches the code ("threshold used for adding the Winkler bonus"); no test, CHANGES entry or issue covers negative values.
  • The threshold condition is the usual Winkler boost-threshold rule and 18 years old: fix the javadoc.
The full argument170 words
  • A direct promise, inverted. The sentence says a negative value gives the Jaro distance; a negative value gives the bonus to every pair that has a matching character.
  • The other documentation agrees with the code: the first sentence of the same javadoc ("the threshold used to determine when Winkler bonus should be used"), the getter ("threshold used for adding the Winkler bonus") and the constructor ("the default threshold for the Jaro Winkler bonus (0.7)").
  • No coverage: no test, CHANGES or MIGRATE entry, or package doc mentions negative thresholds; the upstream tests use only the default.
  • History: one 2008 commit (LUCENE-1297, #2374) added the class, the sentence and the condition. In #2374 a reviewer asked for a configurable threshold and the contributor replied the same day "Added getter/setter for JaroWinker threshold and javadoc"; none of the 16 comments on #2374 (17 on LUCENE-1297 in JIRA, the last being the 2022 migration notice) discusses negative values. Earlier patch versions are not in the repository, so whether one honoured the sentence is unknown.
The devil's-advocate check95 words

The strongest case: the runtime rule is coherent (its threshold condition is the usual Winkler boost-threshold rule) and 18 years old, and users who pass a negative value today get the always-bonus mode and may rely on it; perhaps the author meant "a negative value always applies the bonus" and wrote "Jaro" by mistake.

Why it fails as a defence of the docs: under either reading the sentence is false, since it says "Jaro" and the result is Jaro-Winkler. The argument only shows which side to fix, the javadoc, which is what this doc proposes.

Suggested fix

#

Recommended A. Correct the javadoc

Fix the javadoc: say the bonus is skipped when the Jaro distance is below the threshold and added otherwise, that 1 or more gives the Jaro distance, and that 0 or less always applies the bonus. No behaviour change. Validated with gradle: the format check and javadoc render pass, and all 31 spell tests pass.

A. Correct the javadoc (validated by the checks) (recommended)

#

Replace the false sentence with what the code does.

   /**
-   * Sets the threshold used to determine when Winkler bonus should be used. Set to a negative value
-   * to get the Jaro distance.
+   * Sets the threshold used to determine when Winkler bonus should be used: the bonus is skipped
+   * when the Jaro distance is below the threshold and added otherwise. Set to 1 or more to get the
+   * Jaro distance; a value of 0 or less always applies the Winkler bonus.
    *
    * @param threshold the new value of the threshold
    */

Trade-offs

  • No behaviour change, so no existing score moves; it uses the wording of the first sentence and of the getter ("threshold used for adding the Winkler bonus").
  • Callers who already pass a negative value to get Jaro keep getting Jaro-Winkler; they can use 1 instead.
  • "1 or more", not "above 1": at exactly 1 the bonus is multiplied by 1 - j = 0 when j = 1, so 1 also gives plain Jaro.
  • The wording "skipped when below the threshold, added otherwise" is exactly the j < getThreshold() test, so it is also right for NaN, where the bonus is added (j < NaN is false). An earlier draft said "added when the Jaro distance is at least the threshold", which is wrong for NaN.
  • It keeps the class's historical word "distance"; StringDistance values are similarities (1 means identical, StringDistance.java:22-31), so "Jaro similarity" is a fine alternative. "The Jaro distance" means Lucene's unboosted value; the empty-string result is the separate #3901.

What the checks validated

  • Gradle, a second scratch worktree of 645d4fe14a20 (after the fact check corrected the wording), seed DEADBEEF: :lucene:suggest:checkGoogleJavaFormat and :lucene:suggest:renderJavadoc pass, and the rendered JaroWinklerDistance.html shows the new text in the method detail (the method summary shows its first sentence). The first wording passed the same steps in the first worktree.
  • The spell tests (org.apache.lucene.search.spell.*: the 31 upstream tests of the 8 spell test classes plus the minimal test pinned to the corrected sentence, setThreshold(1)) pass, 32 tests, with assertions on; the pinned test passes with assertions off too.
  • The minimal test as written was not re-run with it: the fix changes only a comment, so it keeps failing as on stock main.

B. Make a negative threshold mean plain Jaro (an option only) (validated by the checks)

#

In getDistance, never add the bonus when the threshold is negative, which makes the current sentence true.

     float j = ((m / s1.length() + m / s2.length() + (m - mtp[1]) / m)) / 3;
-    float jw = j < getThreshold() ? j : j + Math.min(0.1f, 1f / mtp[3]) * mtp[2] * (1 - j);
+    float jw =
+        (getThreshold() < 0 || j < getThreshold())
+            ? j
+            : j + Math.min(0.1f, 1f / mtp[3]) * mtp[2] * (1 - j);
     return jw;

Trade-offs

  • Changes scores for every caller that passes a negative value today (Jaro-Winkler becomes Jaro); it would likely warrant a CHANGES entry as a behaviour change.
  • Makes the threshold non-monotonic: 0 and -0.0 (for which getThreshold() < 0 is false) and NaN still always add the bonus, while -0.5 never does (the study's threshold table, run with this fix). That contradicts the first sentence of the same javadoc.

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20, seed DEADBEEF: the minimal test as written passes with assertions on (inside the 32-test spell run) and off, the 31 upstream spell tests pass, and :lucene:suggest:checkGoogleJavaFormat passes.
  • The study's bounded-exhaustive model, run with this fix, left only the empty pair ('', ''), which is the separate #3901.

Downstream note

#

Products that expose this threshold to their own users would inherit the misleading sentence; in a spot check, Elasticsearch, OpenSearch and Solr use the no-argument constructor and do not call setThreshold.

How it was found

#

Semi-formal. A hunt unit compared Lucene's string distances with a separate model over all 14,641 ordered pairs of strings of up to 4 code points over a 3-code-point alphabet, at thresholds 0.7, -1, 0 and 2. At -1, JaroWinklerDistance differed from Jaro on 4,680 pairs (plus the empty pair, the known #3901); at 2 it matched.

The method in full139 words

Method: bounded-exhaustive translation validation of the StringDistance implementations on the stock jar (hunt unit on spell-checker dictionaries and word break, 2026-10-26, main ea57360912ed).

  • Inputs: every ordered pair of the 121 strings of at most 4 code points over {a, b, U+1F600}, 14,641 pairs; JaroWinklerDistance at thresholds 0.7, -1, 0 and 2.
  • Oracle: a separate Jaro / Jaro-Winkler model that follows Lucene's matching arithmetic (UTF-16 chars, integer-halved transpositions; Jaro of ('', '') is 1), and the setThreshold sentence. Threshold -1 differed from that Jaro on 4,681 pairs: 4,680 plus ('', ''), which is the separate known #3901 (getDistance("", "") returns 0). Threshold 2 matched Jaro except on ('', '').
  • The finder then wrote a public-API JUnit test with controls, which failed on main, 10.5.2 and 9.12.3; a code-variant fix made it pass and kept the upstream TestJaroWinklerDistance green.

Only applications that use the suggest module's JaroWinklerDistance and follow the setThreshold javadoc to get plain Jaro (a negative threshold) are hit: they get Jaro-Winkler scores instead, equal to or higher than Jaro, still in [0, 1] and identical to threshold 0, so pairs with a shared prefix score higher and a spell-check accuracy cut-off or the caller's own match cut-off can let more pairs through; the default threshold 0.7 is unaffected, no Lucene code calls setThreshold, nothing throws and nothing is written, and every release from 2.4.0 (2008) is affected.
Summary
You want the plain Jaro similarity from JaroWinklerDistance, so, as the setThreshold javadoc says ('Set to a negative value to get the Jaro distance'), you call setThreshold(-1) and expect getDistance("martha", "marhta") to return the Jaro value 0.9444. Instead it returns 0.9611, the Jaro-Winkler value: getDistance skips the Winkler bonus only when the Jaro value is below the threshold, which never happens for a negative threshold, so every pair gets the bonus, exactly as with threshold 0. Only a threshold of 1 or more gives plain Jaro; the sentence has been false since the class was added in 2008, so the javadoc is the side to fix by default.
