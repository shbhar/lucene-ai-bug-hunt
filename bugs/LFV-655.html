TermVectorLeafReader.getMetaData() always throws IllegalArgumentException, so a sorted search on the reader fails

TermVectorLeafReader, the public helper that turns one document's term vectors into a one-document reader, builds metadata that LeafMetaData's constructor rejects, so getMetaData() throws on every call. Any search with a Sort, ParallelLeafReader or addIndexes on it fails, in every release since 7.0.0.

The finding in 30 seconds

#

Every LeafReader describes itself through getMetaData(): the Lucene version that created it, the oldest version that wrote to it, and its index sort. TermVectorLeafReader reports "created by 11, oldest writer unknown". LeafMetaData forbids an unknown oldest writer for anything created by 7 or later, so the method throws instead of returning.

Background: three pieces

#
  1. TermVectorLeafReader is a public highlighter class that "Wraps a Terms with a LeafReader, typically from term vectors": it turns one document's term vectors into a tiny searchable reader with maxDoc() = 1.
  2. LeafMetaData is what LeafReader.getMetaData() returns: the major version that created the index, the minimum version that wrote to it, the index sort and a block flag. Its constructor checks these values and throws IllegalArgumentException on an invalid combination.
  3. Some APIs read every leaf's metadata before they start: a search with a Sort (to see whether it can stop early), the ParallelLeafReader constructor, and IndexWriter.addIndexes (to check versions and sort).

The finding, step by step

#
  1. Index one document whose text field body = "foo" stores term vectors, and wrap them in new TermVectorLeafReader("body", terms): a reader with exactly 1 document.
  2. Search it sorted by doc id: searcher.search(new MatchAllDocsQuery(), 1, new Sort(SortField.FIELD_DOC)). You expect 1 hit, doc 0; the same search without a Sort returns it.
  3. Instead it throws IllegalArgumentException: minVersion must be set when createdVersionMajor is >= 7. A sorted search asks each reader for its metadata, and this reader answers "created by version 11, oldest writer unknown", a pair LeafMetaData rejects for anything created by 7 or later.
  4. The arguments are constants, so the call fails every time, for any document, with assertions on or off. new ParallelLeafReader(reader) and addIndexes(SlowCodecReaderWrapper.wrap(reader)) fail the same way; MemoryIndex's reader passes Version.LATEST and works.

Who is affected

#

Only applications that build a TermVectorLeafReader themselves and hand it to an API that reads leaf metadata: a search with any Sort, ParallelLeafReader or addIndexes. Lucene's own highlighters are not affected. The failure is a clean exception and nothing from the reader is written. Every release since 7.0.0; rare: no public report found in nine years.

Mechanism, terms and numbers450 words

TermVectorLeafReader (highlighter module, public, @lucene.experimental) wraps one document's term vectors as a one-document LeafReader. Its getMetaData() returns new LeafMetaData(Version.LATEST.major, null, null, false) (TermVectorLeafReader.java:237-240 on main 645d4fe14a20), and the LeafMetaData constructor throws IllegalArgumentException("minVersion must be set when createdVersionMajor is >= 7") for exactly that pair (LeafMetaData.java:58-60). The arguments are constants, so the method can never return. Every API that reads leaf metadata fails on the reader: a search with any Sort, Sort.RELEVANCE included (TopFieldCollector.java:58), new ParallelLeafReader(reader) (ParallelLeafReader.java:131) and IndexWriter.addIndexes(SlowCodecReaderWrapper.wrap(reader)) (IndexWriter.java:3229). Lucene's own highlighters do not ask for the reader's metadata (code reading of both in-tree call sites; their 21 term-vector tests pass), so the code that is hit is code that uses the class directly, and it gets a clean exception. The commit that added the check (LUCENE-7756, first released in 7.0.0) gave MemoryIndex's reader the valid Version.LATEST; passing the same here fixes it, and with that one-line change the repro and the whole highlighter test suite pass.

The bug (main 645d4fe14a20)

#
  1. The reader. TermVectorLeafReader.java:237-240: return new LeafMetaData(Version.LATEST.major, null, null, false);. Version.LATEST is LUCENE_11_0_0 on main (Version.java:259), so this is created major 11 with a null minVersion.
  2. The invariant. LeafMetaData is a record (LeafMetaData.java:45-46) whose compact constructor, "Expert: Sole constructor. Public for use by custom LeafReader impls." (:48-49), rejects a created major in the future (:50-53) or below 6 (:54-57), and then createdVersionMajor >= 7 && minVersion == null (:58-60). The third check always fires for this reader, whatever its document.
  3. The consumers. TopFieldLeafCollector's constructor reads context.reader().getMetaData().sort() for every leaf (TopFieldCollector.java:53-59), and every IndexSearcher.search(query, n, sort) goes through it, with Sort.RELEVANCE and Sort.INDEXORDER too. ParallelLeafReader's constructor reads every sub-reader's metadata (ParallelLeafReader.java:130-131). SlowCodecReaderWrapper forwards getMetaData() (SlowCodecReaderWrapper.java:140-143), and addIndexes(CodecReader...) reads it in its up-front validateMergeReader (IndexWriter.java:3228-3229, :3288-3290).
  4. The sibling that works. MemoryIndex's reader returns new LeafMetaData(Version.LATEST.major, Version.LATEST, null, false) (MemoryIndex.java:2291-2294), as does the test framework's fake reader (QueryUtils.java:312). Of the seven new LeafMetaData( calls in the non-test sources, this is the only one that passes a literal null.

Exposure and likelihood283 words
  • Who is hit. Code that constructs the reader itself (public class, public constructor) and passes it, or a FilterLeafReader that delegates metadata to it, to a metadata-reading API: a search with any Sort, new ParallelLeafReader(...), addIndexes through SlowCodecReaderWrapper, and other getMetaData() callers such as Sort.getPrimarySortField and CheckIndex (listed from code, not run). Default codec and settings; one document and one term are enough.
  • Not hit: Lucene's own highlighters. The unified highlighter builds the reader and wraps it in OverlaySingleDocTermsLeafReader, a FilterLeafReader over the real segment reader whose metadata it returns (TermVectorOffsetStrategy.java:48-50, FilterLeafReader.java:477-481). The classic highlighter builds it only for term vectors with positions and offsets (WeightedSpanTermExtractor.java:393-401) and only rewrites queries and builds span weights on it. The 21 tests of TestTokenSources, TestHighlighterPhrase and TestUnifiedHighlighterTermVec pass on unfixed main; since the method throws on every call, a reached call would fail them. This rests on code reading of the two in-tree call sites plus these tests; it is not a proof for every query type or extension.
  • Downstream. A code search found no use of the class in Solr, Elasticsearch or OpenSearch (not exhaustive).
  • Effect. An immediate IllegalArgumentException at the call. Nothing from the reader is written: addIndexes first flushes the writer's own buffered documents, as it always does (IndexWriter.java:3286), and then its up-front validation throws before anything from the reader is added (:3288-3290). Only an Error is treated as tragic there (:3390-3392), so the writer stays open. No wrong results, no hang.
  • How likely: rare. The class is a highlighter helper few applications build directly, and the documented searches found no public report since 7.0.0 (September 2017).

Why it looks unintended

#
  • LeafReader.getMetaData() is an abstract method, "Return metadata about this leaf", with no throws clause; the class and its constructor are public.
  • The method can never succeed: its arguments are constants that the LeafMetaData constructor rejects.
  • The 2017 commit that added the check gave the sibling MemoryIndex reader valid metadata (Version.LATEST); this reader got null.
The full argument188 words
  • Contract. LeafReader.java:526-531: public abstract LeafMetaData getMetaData(), "Return metadata about this leaf", @lucene.experimental, no throws clause. TermVectorLeafReader is a public class with a public constructor, whose javadoc reads "Wraps a Terms with a LeafReader, typically from term vectors" (TermVectorLeafReader.java:52-61), so a sorted search on it is ordinary LeafReader use. The expected behaviour follows from the abstract method and the LeafMetaData invariant; it is not stated word for word.
  • History. LUCENE-7756 (23b002a0fdf, 2017) added LeafMetaData with the check, wrote this null call, and gave MemoryIndex the valid Version.LATEST in the same commit. The strict check was asked for in review (migrated issue #8807: throw "if minVersion is null but major version is >= 7"); the thread never mentions TermVectorLeafReader. That this caller was overlooked is an inference.
  • No test. No test in the repository uses TermVectorLeafReader directly or expects "minVersion must be set", so no test calls this method directly.
  • Context only. The LeafMetaData javadoc says minVersion may be null "if this information is not available" (LeafMetaData.java:30-31), but the constructor allows that only with created major 6 ("unknown", :27-29).
The devil's-advocate check241 words

The intended-behaviour checker and the cross-model reviews built the strongest case: the class and the method are @lucene.experimental; the class is a minimal highlighter helper with stub methods (getNormValues returns null with the comment "Is this needed?", null cache helpers, empty stored fields); Lucene's own callers avoid its metadata; and DocValuesLeafReader also throws from getMetaData() (DocValuesLeafReader.java:93-95).

Why it fails: the other stubs return values their contracts allow, and none throws; DocValuesLeafReader is package-private (:25), used only inside the indexing chain and throws UnsupportedOperationException by design, whereas this is a public reader whose one metadata method trips a constructor invariant on every call; @lucene.experimental allows API change, not a method that can never succeed; and the same commit gave MemoryIndex valid metadata. The cross-model reviews rated the argument weak, and the intended-behaviour check rejected it. What it does establish is narrow reach, hence low priority.

A dissenting rating: the cross-model fact check of this doc (OpenAI GPT-5.6, read-only) rated the case moderate, not weak. Its reasons: an experimental, minimal helper; term-vector Terms that are meant to be consumed only on the thread that acquired them (TermVectors.java:26-27); little practical value in sorting a one-document reader; and DocValuesLeafReader as a reader that throws by design. It still judged the bug a real, low-priority claim, not noise, and agreed with an ordinary public issue or small PR that leads with the direct call and the sorted search.

Suggested fix

#

Recommended Pass Version.LATEST as minVersion, as MemoryIndex does

Pass Version.LATEST as the minimum version, as MemoryIndex does: a one-line change in TermVectorLeafReader.getMetaData(). That is the convention Lucene's other synthetic readers already follow. Validated: the repro passes with assertions on and off, and so do all 723 tests of the highlighter module.

   @Override
   public LeafMetaData getMetaData() {
-    return new LeafMetaData(Version.LATEST.major, null, null, false);
+    return new LeafMetaData(Version.LATEST.major, Version.LATEST, null, false);
   }

Pass Version.LATEST as minVersion, as MemoryIndex does (validated by the checks) (recommended)

#

One line in TermVectorLeafReader.getMetaData() (TermVectorLeafReader.java:239, 1 file, +1/-1). The reader then reports "created by and only written by this version" and no index sort, like MemoryIndex's reader (MemoryIndex.java:2293). Sorted searches and ParallelLeafReader accept it, and addIndexes gets past its metadata check (see the trade-offs).

   @Override
   public LeafMetaData getMetaData() {
-    return new LeafMetaData(Version.LATEST.major, null, null, false);
+    return new LeafMetaData(Version.LATEST.major, Version.LATEST, null, false);
   }

Trade-offs

  • Version.LATEST is a convention, not recorded provenance. The constructor gets only a field name and a Terms (TermVectorLeafReader.java:61), so the reader has no version input of its own, and its term vectors may come from a segment an older version wrote. It is the convention MemoryIndex and the test framework's QueryUtils reader already use, and the created major is already Version.LATEST.major. No other trade-off is known.
  • With it, addIndexes gets past validateMergeReader, which checks the created major against the index's and requires a non-null minVersion for major >= 7 (IndexWriter.java:3228-3243). The document was copied in the earlier verifiers' test, which uses SerialMergeScheduler, and in the diagram probe, a plain main() with the default IndexWriterConfig. Term-vector Terms are meant to be consumed only on the thread that acquired them (TermVectors.java:26-27), so addIndexes is a secondary path, not a general promise.
  • An upstream test of the addIndexes path (not part of the repro) should use SerialMergeScheduler: with the fix, the test framework's AssertingTerms rejected the Terms being consumed on a ConcurrentMergeScheduler thread in the first fixed run of the cross-model reviews.

What the checks validated

  • Scratch worktree of 645d4fe14a20, gradle --no-daemon, OpenJDK 25.0.3, seed DEADBEEF: the repro test fails on the stock tree with assertions on and off, and passes with the fix with assertions on and off.
  • With the fix, :lucene:highlighter:test with assertions on: 35 suites (the repro included), 723 tests, 0 failures, 0 errors.
  • :lucene:highlighter:checkGoogleJavaFormat passes with the fix and the test in the tree.
  • Earlier, on main a9779ef3c193: the finder's, the independent reproduction's, the cross-model review's and the intended-behaviour check's own tests all pass with the same change shadowed (the independent reproduction 6 of 6 covering the direct call, ParallelLeafReader, INDEXORDER-sorted search and addIndexes).

Report created major 6 ("unknown") with a null minVersion

#

The LeafMetaData javadoc treats created major 6 as "unknown" (LeafMetaData.java:27-29), and the constructor accepts it with a null minVersion. Not built.

Trade-offs

addIndexes would then reject the reader: validateMergeReader throws when the index's created major differs from the reader's (IndexWriter.java:3230-3236). So it trades one exception for another on that path.

Relax the LeafMetaData check

#

Allow a null minVersion for created major >= 7, as the javadoc wording "or null if this information is not available" suggests (LeafMetaData.java:30-31). Not built.

Trade-offs

Broader and against the review that asked for the strict check; IndexWriter.java:3238-3242 separately rejects a null minVersion for created major >= 7 ("hides it"), so addIndexes would still fail.

Downstream note

#

No use of TermVectorLeafReader was found in Solr, Elasticsearch or OpenSearch; an application that builds one gets a clean exception from its own call, which no document or query can cause.

How it was found

#

A hunt checking that ParallelLeafReader behaves as if its sub-readers were one index wrapped each public LeafReader type in the source tree in turn. Seven of eight types worked; TermVectorLeafReader failed as soon as the parallel reader was built. The failure was then reduced to a public-API JUnit test.

The method in full112 words

Method: non-formal (code reading plus execution; the hunt's hunt unit for ParallelLeafReader "as if one index" metamorphic checks, 2026-10-27, main a9779ef3c193).

  • Reader sweep. One leg of the plan wrapped each public LeafReader type as a ParallelLeafReader sub-reader: SegmentReader, the soft-deletes and exitable leaves, SlowCodecReaderWrapper, SortingCodecReader, FieldFilterLeafReader, MemoryIndex's reader and TermVectorLeafReader, each with construct, identity-dump and addIndexes-copy checks, with assertions on and off. Only TermVectorLeafReader failed, at construction, with the minVersion exception.
  • Reduction. The lead from the plan's code reading was reduced to a public-API JUnit (direct getMetaData(), then ParallelLeafReader and a sorted search), and later minimized to the one-method sorted-search test shown above.

History

#

Introduced in 7.0.0 by LUCENE-7756 (23b002a0fdf, 2017), the commit that added LeafMetaData with the check and wrote this null call; sorted search became a trigger in 7.2.0 (LUCENE-8059). Unchanged since, apart from an appended hasBlocks=false in 9.9.0. 6.x is not affected: the method did not exist.

Versions tested6 rows

Area
highlighter / TermVectorLeafReader (LeafReader over one document's term vectors; LeafMetaData invariant)
Priority
Low, rank 636: TermVectorLeafReader.getMetaData always throws a clear IllegalArgumentException, but only when this rarely used helper is passed to sorted search, ParallelLeafReader or addIndexes.
Impact class
crash
Impact note
Hits only applications that construct a TermVectorLeafReader themselves (public class and constructor, @lucene.experimental; a code search finds no use in Solr, Elasticsearch or OpenSearch) and pass it to an API that reads leaf metadata: IndexSearcher.search(query, n, sort) with any Sort, Sort.RELEVANCE and Sort.INDEXORDER included (since 7.2.0), new ParallelLeafReader(...), or IndexWriter.addIndexes(SlowCodecReaderWrapper.wrap(...)); every such call throws IllegalArgumentException, deterministically with -ea and -da and whatever the document; the exception is clean (nothing is persisted, addIndexes leaves the writer open), relevance search without a Sort works, and Lucene's own highlighters never reach the method.
Summary
You build a TermVectorLeafReader over one document's term vectors (new TermVectorLeafReader(field, terms), the public helper that 'wraps a Terms with a LeafReader') and use it like any other LeafReader, expecting getMetaData() to return metadata with no index sort, as MemoryIndex's in-memory reader does. Instead getMetaData() throws IllegalArgumentException('minVersion must be set when createdVersionMajor is >= 7') on every call, because it passes minVersion=null together with createdVersionMajor=Version.LATEST.major, a combination the LeafMetaData constructor rejects. So a field-sorted search (even with Sort.RELEVANCE), new ParallelLeafReader(reader) and addIndexes(SlowCodecReaderWrapper.wrap(reader)) all fail; a plain relevance search without a Sort works.
