RescoreTopNQuery passes negative values through as negative scores, so a top-k BooleanQuery that ORs it with another clause returns no hits

OR a RescoreTopNQuery whose values are negative with another clause, and a top-k search can return nothing: one document with v = -2 gives 0 hits while count(q) is 1. The query passes -2 through as a score; top-k pruning assumes scores are never below 0.

The finding in 30 seconds

#

A rescoring clause whose values are negative makes a top-k OR query skip documents that match its other clauses.

Background: rescoring and top-k pruning

#
  1. RescoreTopNQuery(query, valuesSource, n) runs query, gives each match the value of valuesSource (a doc-values field, an expression, a vector similarity) and keeps the n best. The result acts like a query that matches exactly those n documents, each with its value as the score.
  2. A BooleanQuery with SHOULD clauses matches a document if any clause matches it; its score is the sum of the matching clauses' scores. Combining a rescored result with other queries this way is the hybrid use named by the #14009 author and in the javadoc of RescoreTopNQuery.createLateInteractionQuery.
  3. A top-k search skips work: each clause reports the highest score it can give, and documents whose best possible score cannot reach the minimum competitive score are skipped unscored. That threshold starts at 0, because Lucene scores are never negative.

The finding, step by step

#
  1. Index one document with NumericDocValuesField("v", -2). Query: RescoreTopNQuery(MatchAllDocsQuery, DoubleValuesSource.fromLongField("v"), 1) as one SHOULD clause of a BooleanQuery, MatchAllDocsQuery as the other.
  2. You expect searcher.search(q, 10) to return the document: it matches the MatchAllDocsQuery clause, and count(q) is 1.
  3. You get 0 hits and totalHits 0, with no error, assertions on or off. With 10 documents (v = -2 to -11) it is 0 of 10.
  4. RescoreTopNQuery copies the value -2 into the score, so its clause reports a best possible score of -2. Lucene requires scores to be at least 0; FunctionScoreQuery would have turned -2 into 0.
  5. The top-k scorer adds up the clauses' best scores, -2 + 1 = -1, and compares the sum with its starting threshold 0. Below it, no document can compete, so it skips the window; the best scores are the same in every window, so it skips them all.

Who is affected

#

Applications that use the experimental RescoreTopNQuery with a values source that can be negative (a signed numeric field, an expression such as -age or ln(x) for x < 1, a negative constant) next to other scoring clauses, on 10.3.0 to 10.6.0 and main. One document is enough. Vector-similarity sources are never negative and are safe.

Mechanism, terms and numbers593 words

RescoreTopNQuery (experimental, new in 10.3.0) rescores another query's matches with a DoubleValuesSource and keeps the top n. It stores each value as the score as it is, so a negative value becomes a negative score and a negative max score, although Lucene requires non-negative scores (LUCENE-7996) and FunctionScoreQuery maps negative values to 0. When the query is a SHOULD clause of a top-k BooleanQuery, MaxScoreBulkScorer starts with a minimum competitive score of 0; if the clauses' max scores add up to less than 0, it treats every clause as non-essential and skips the window, and here every window of the segment. One document with v = -2, OR MatchAllDocsQuery: search(q, 10) returns 0 hits while count(q) is 1, with no error, default configuration, assertions on or off, in every release from 10.3.0 to 10.6.0 and on main.

The bug

#
  1. RescoreTopNQuery.rewrite fills a HitQueue of size n through rescoreInto and returns DocAndScoreQuery.createDocAndScoreQuery(reader, topDocs, 0) (RescoreTopNQuery.java:68-91).
  2. rescoreInto inserts new ScoreDoc(docBase + docId, (float) values.doubleValue()) with no clamp; only a missing value becomes 0 (:224-231). The value -2 becomes the score -2.
  3. DocAndScoreQuery takes maxScore = topK.scoreDocs[0].score (DocAndScoreQuery.java:125) and reports it from getMaxScore (:239-240): -2.
  4. search(q, 10) collects with ScoreMode.TOP_SCORES, and for two SHOULD clauses BooleanScorerSupplier builds a MaxScoreBulkScorer (BooleanScorerSupplier.java:315-328), whose minimum competitive score starts at 0 (SimpleScorable.java:24).
  5. partitionScorers marks clauses non-essential while their running max-score sum stays below that threshold (MaxScoreBulkScorer.java:494-511): -2 < 0, then -2 + 1 = -1 < 0. Every clause is non-essential, it returns false (:515-516), and the window is skipped as "No matches in this window" (:133-137). The max score is the same for every window, so the whole segment is skipped.

The numbers

#
  • One document, v = -2: count(q) = 1, search(q, 10) = 0 hits, totalHits 0. Collected exhaustively (TopScoreDocCollectorManager(10, Integer.MAX_VALUE)), the same query returns the document with score -1.0.
  • 10 documents, v = -2 to -11: 0 of 10 hits, while exhaustive collection returns all 10 (nine at +1.0).
  • A hybrid query, TermQuery OR RescoreTopNQuery(same TermQuery, fromLongField("v"), 1), 3 matching documents with v = -2, -3, -4: 0 of 3 hits.
  • Expressions as the source: -age and ln(age / 100000) give 0 of 10 hits.
  • Two segments, {-2, -3} and {-5, -6}, n = 1: 2 of 4 hits. Only the segment that holds the kept document loses its hits; a segment without one has no scorer for the rescored clause (DocAndScoreQuery.java:198-200).
  • n > 1 with mixed signs, OR MatchAllDocsQuery: values {5, -2} with n = 2 give 0 of 2 hits, {5, 3, -2} with n = 3 give 0 of 3; with n = 2 the -2 is not kept and all 3 are returned. The clause's max score is the first entry of the kept set in heap order, its lowest value.

Not claimed here (same unclamped value, other symptoms)

#
  • If the max-score sum is still at or above 0 (for example a constant -1 OR MatchAllDocsQuery), the search reaches ScorerUtil.minRequiredScore at a threshold of 0 and, with assertions off, never returns; with assertions on it throws AssertionError "All clauses are essential if minCompetitiveScore is equal to zero". That loop is a separate bug with its own fix site (LFV-1016).
  • With minimumNumberShouldMatch 2 over three SHOULD clauses, WANDScorer throws IllegalArgumentException "Scores must be positive or null" (WANDScorer.java:69-71).
  • The query alone, or as a MUST or FILTER clause, returns the right hits, with negative scores.
Exposure and likelihood300 words
  • Who is hit. Callers of RescoreTopNQuery with a non-vector values source that can be negative, used as a SHOULD clause of a top-k BooleanQuery. With n = 1 the kept value has to be negative; with n > 1 one negative value among the n kept documents is enough, because the clause's max score is scoreDocs[0].score (DocAndScoreQuery.java:125) and rewrite fills scoreDocs in heap order (RescoreTopNQuery.java:83-87), so it is the lowest kept value: values {5, -2} with n = 2 give 0 of 2 hits. That is the use the class was built for: the #14009 author described "a hybrid search where KnnFloatVectorQuery and TermQuery (amongst others) are combined into a single BooleanQuery", and the late-interaction factory's javadoc says it is "typically useful in combining a query's results with other queries for hybrid search" (RescoreTopNQuery.java:313-315).
  • Who is not. The built-in vector-similarity sources (full precision, float16, late interaction) are non-negative by construction. The query alone, or as a MUST or FILTER clause, returns the right hits.
  • Default vs opt-in. Default IndexWriterConfig, codec and IndexSearcher; the trigger is the opt-in, @lucene.experimental query (RescoreTopNQuery.java:34) with a non-vector source.
  • Scale. In a single-segment index every matching document disappears; in the tested two-segment index the segment that holds the kept document loses both its hits, and totalHits is wrong too. In general a window is skipped when its clauses' max scores add up to less than the minimum competitive score; at 0 or more, the separate LFV-1016 loop applies instead. No exception or warning, assertions on or off.
  • How likely. Rare: every public user of the query that was found uses vector similarities. The failure does not depend on chance: the same index and query give 0 hits every time (10 of 10 derived seeds).

Why it looks unintended

#
  • Lucene requires non-negative scores since LUCENE-7996: "Queries are now required to produce positive scores."
  • FunctionScoreQuery, which the class javadoc compares this query to, maps negative values to 0, and a test checks it on a similar input (one document, v = -2).
  • Nothing documents or checks a value range, and the same query collected exhaustively returns the hit.
The full argument274 words
  • The rule. lucene/CHANGES.txt:6636: "LUCENE-7996: Queries are now required to produce positive scores." lucene/MIGRATE.md:1368-1375: "Scorers are no longer allowed to produce negative scores" and "FunctionScoreQuery maps negative values to 0." The test framework asserts it (AssertingScorer.java:131): with AssertingIndexSearcher and -ea, the rescored clause alone fails with AssertionError: -2.0.
  • Lucene clamps caller-supplied values itself. FunctionScoreQuery maps a negative value or NaN to 0 (FunctionScoreQuery.java:243-251), and TestFunctionScoreQuery.testTruncateNegativeScores (:236-253) checks it on one document with NumericDocValuesField("foo", -2) and fromLongField. In the LUCENE-7996 thread (#9044) romseygeek asked "could we just set the score to 0?", and jpountz answered with a patch: "New patch that maps negative scores to 0. The explanation says when this happens so that this change is not too trappy." In the same disjunction, FunctionScoreQuery over the same source returns the hit.
  • The class invites this use. Its javadoc says it re-scores "with a DoubleValuesSource function", "can work with any type of Query" and compares it with FunctionScoreQuery (RescoreTopNQuery.java:26-32); the constructor checks only n >= 1 (:58-61); CHANGES calls the source "generic" (CHANGES.txt:1595-1596); hybrid use is advertised (:313-315).
  • Two collections disagree. Exhaustive collection returns the document, top-k returns nothing; CheckHits.doCheckTopScores requires them to be equal (CheckHits.java:700-709).
  • History. Earlier built-in negative-score paths were fixed as bugs: #11184, #12342 / #12727, #13356, #16139. The upstream RescoreTopNQuery tests use constant(0), SCORES over a kNN query's scores and vector similarities, so no test value is negative, and they never put the query in a BooleanQuery; no comment on #14009 or #16926 discusses value ranges.
The devil's-advocate check166 words

The strongest case for "works as designed": the class is experimental and was built to rescore vector shortlists, whose similarities are non-negative; MIGRATE.md tells authors of custom queries to keep "their score formula" non-negative, so a negative values source is the caller's mistake; and negative values carry ranking information (for example -distance), so passing them through is a choice.

Why it fails: RescoreTopNQuery is Lucene's own query, and the caller only passes a values source through a public constructor; for that exact shape LUCENE-7996 chose to clamp inside Lucene; the query is advertised for generic sources and hybrid use, where sorting by the function instead is not an option; nothing documents or checks the precondition; and the failure is silent and far from its cause. Even if negative values are declared illegal, the silent 0-hit result needs a check or a clamp. The ranking point is real, which is why the recommended fix keeps the selection on the raw values. Verdict: not intended, a defect.

Suggested fix

#

Recommended B: keep the top n by raw value, clamp only the emitted scores (validated)

Keep picking the top n by the raw value, then report negative values (and NaN) as score 0, as FunctionScoreQuery does: 5 lines in RescoreTopNQuery.rewrite. With it the repro and the 56 tests of five upstream RescoreTopNQuery, prefetch and kNN test classes pass (0 failures; the nightly tests too).

for (ScoreDoc topDoc : queue) {
  // The top n are chosen by raw value, but scores must not be negative (LUCENE-7996): like
  // FunctionScoreQuery, report negative values and NaN as 0
  if ((topDoc.score > 0) == false) {
    topDoc.score = 0;
  }
  scoreDocs[i++] = topDoc;
}

B: keep the top n by raw value, clamp only the emitted scores (validated) (recommended)

#

+5 lines in RescoreTopNQuery.rewrite, in the loop that copies the queue into scoreDocs (RescoreTopNQuery.java:83-87): a kept document whose value is not above 0 gets score 0.

for (ScoreDoc topDoc : queue) {
  // The top n are chosen by raw value, but scores must not be negative (LUCENE-7996): like
  // FunctionScoreQuery, report negative values and NaN as 0
  if ((topDoc.score > 0) == false) {
    topDoc.score = 0;
  }
  scoreDocs[i++] = topDoc;
}

Trade-offs

  • Keeps the documented meaning (the top n of the values source) and meets the non-negative rule; the max score handed to DocAndScoreQuery can no longer be negative. > 0 also maps -0.0 and NaN to +0.
  • Kept documents with negative values all score 0, so their relative order no longer shows in the combined score (as with FunctionScoreQuery). NaN values, which Float.compare orders above every number in the HitQueue, are still kept first, then reported as 0.
  • Cost: one branch per kept document, outside the per-candidate loop. No benchmark was run.

What the checks validated

  • Gradle, stock 645d4fe14a20: the repro fails with assertions on and off.
  • Gradle with the fix (seed DEADBEEF): the repro, the selection probe below and TestRescoreTopNQuery, TestRescoreTopNQueryPrefetch, TestRescoreTopNQueryFloat16Prefetch, TestFilterReadersForwardVectorPrefetch and TestKnnFloatVectorQuery: 7 classes, 58 tests (56 of them upstream), 0 failures, 2 @Nightly skipped. With assertions off, the repro and the TestRescoreTopNQuery* suites: 10 tests, 0 failures. TestRescoreTopNQuery with -Ptests.nightly=true: 7 of 7 pass. checkGoogleJavaFormat passes.
  • Shadowed into the stock main jars: the two-segment probe returns 4 of 4 hits, and a 7-case control probe (including the hybrid TermQuery case) passes 7 of 7.
  • A selection probe (v = -4, -3, -2, n = 1) keeps doc 2, the best value, with score 0.0.
  • n > 1 with mixed signs (values {5, -2}, n = 2; {5, 3, -2}, n = 3), shadowed: every document is returned.

A: clamp before the queue insert, as FunctionScoreQuery does (validated, changes the selection)

#

In rescoreInto (RescoreTopNQuery.java:224-231): value >= 0 ? (float) value : 0f.

if (values.advanceExact(docId)) {
  double value = values.doubleValue();
  // Scores must not be negative (LUCENE-7996): like FunctionScoreQuery, map negative values and
  // NaN to 0
  queue.insertWithOverflow(new ScoreDoc(docBase + docId, value >= 0 ? (float) value : 0f));
} else {
  queue.insertWithOverflow(new ScoreDoc(docBase + docId, 0f));
}

Trade-offs

  • Mirrors FunctionScoreQuery line for line, and also fixes the repro.
  • All negative values tie at 0 before the top n are chosen, so the HitQueue keeps the lowest doc ids instead of the best values: with v = -4, -3, -2 and n = 1 it keeps doc 0 (the worst value) where stock and option B keep doc 2. A -distance rescore would keep arbitrary documents. -0.0 passes through.

What the checks validated

Gradle: the repro, the selection probe and the TestRescoreTopNQuery* suites, 11 tests, 0 failures, 2 @Nightly skipped. The hunt's earlier checks validated it too (with the upstream TestRescoreTopNQuery* tests, 7 run, 0 failed).

C: reject negative values with IllegalArgumentException (not built)

#

Throw during rewrite when a value is below 0 (or NaN), and document the range on the constructor.

Trade-offs

Loud and explicit, but breaks callers whose sources are legitimately negative (log-probabilities, -distance) and who only need the selection. A maintainer may still prefer it for an experimental API.

D: clamp or reject in DocAndScoreQuery.createDocAndScoreQuery (not built)

#

The factory has been public on main and branch_11x since #16686 (DocAndScoreQuery.java:121-125; package-private on branch_10_6); a check there covers every producer at once.

Trade-offs

Changes a public factory's contract and does not apply to 10.x as it is; the kNN producers already emit non-negative scores.

Downstream note

#

Results only lose hits, never gain any; if an application rescores by values its users can set (a signed field they fill, a boost expression), every search that rescores by those values can come back empty.

How it was found

#

After an upstream fix for empty inner results in RescoreTopNQuery (#16926), AI tools tried its other unchecked inputs; negative values gave 0 hits in an executed public-API probe. A differential harness (1,560 query and value combinations) bounded the effect, and the case was reduced to a one-document JUnit.

The method in full173 words

Method: non-formal (sibling analysis of an upstream fix plus executed probes; the finder tagged it semi-formal; this page classes it by the first signal).

  • Hunt planners read upstream fix #16926 (empty inner results, 2026-10-28) and listed the other inputs RescoreTopNQuery never checks. For negative values an executed public-API probe on main 645d4fe14a20 showed both 0 hits and a hang.
  • An AI finder reduced it to a JUnit and ran a differential harness on the stock jars: 39 value producers x 10 BooleanQuery shapes x 2 indexes x k in {1, 10}, 1,560 cases, with termination, hit count and the exhaustive top k as the oracle. Result: 94 hangs, 128 zero-hit results, 56 IllegalArgumentExceptions and 392 cases with negative scores only; all 520 non-negative controls pass, and with the clamp all 1,440 RescoreTopNQuery cases pass. An SMT check (Z3 and cvc5) covered the sibling minRequiredScore loop.
  • The 0-hit disjunction was then reduced to the one-document test. So this is a find from targeted probing, confirmed by execution, not a blind discovery by a tool.

History

#

Introduced with the class by #14009 (merged 2025-06-28) and its backport #14860, first released in 10.3.0. Every release from 10.3.0 to 10.6.0 and main fails; the rescore loop never clamped. 10.2.2 and older have no RescoreTopNQuery.

Versions tested7 rows

#14009 "Add Query for reranking KnnFloatVectorQuery with full-precision vectors" (dungba88, commit 3404496b3d77, merged 2025-06-28) added RescoreTopNQuery with the unclamped insert; the branch_10x backport #14860 (4fcb6d6d50de, 2025-06-29) shipped it in 10.3.0 (tagged 2025-09-13). Not a regression: the parents of both commits have no RescoreTopNQuery.java.

The release rows ran the repro (on 10.3.x its port with new MatchAllDocsQuery(), as MatchAllDocsQuery.INSTANCE first appears in 10.4.0); the commits built from source ran a public-API main() twin of it with a v = 2 control that passes; all on OpenJDK 25.0.3, Linux aarch64; release jars were SHA-1 checked.

LFV-1015, snapshot of 2026-11-04

Registry title
RescoreTopNQuery passes negative DoubleValuesSource values through as negative scores, so a top-k BooleanQuery that ORs it with another clause silently returns no hits
Area
search / rescoring (RescoreTopNQuery scores, consumed by MaxScoreBulkScorer dynamic pruning)
Priority
Medium, rank 54: In released 10.3+ the experimental RescoreTopNQuery with a negative-valued non-vector source silently returns 0 hits when ORed with another clause, which is severe but a rarer pairing than its siblings LFV-087 and LFV-315, so it closes that RescoreTopNQuery group ahead of LFV-424 and the related negative-score row LFV-190.
Impact class
silent wrong results
Impact note
Applications that use the experimental RescoreTopNQuery with a values source whose best values are negative (a signed numeric field, an expression such as -age or ln(x) for x < 1, a negative constant; the built-in vector-similarity sources are non-negative and safe) as a SHOULD clause of a top-k BooleanQuery, the hybrid use its javadoc names, get 0 hits and totalHits 0 from the default search(q, n) whenever the clauses' max scores sum below 0, while count() matches every document; default IndexWriterConfig, codec and searcher, 10 documents suffice, -ea and -da, released 10.3.0 to 10.6.0; with smaller negative values the same search instead never returns (-da) or throws an AssertionError (-ea), a loop owned by the sibling ScorerUtil candidate.
Summary
You index 10 documents with a numeric doc-values field v = -2..-11 and run BooleanQuery(SHOULD RescoreTopNQuery(MatchAllDocsQuery, DoubleValuesSource.fromLongField("v"), 1), SHOULD MatchAllDocsQuery) with searcher.search(q, 10), expecting all 10 documents, since each one matches the MatchAllDocsQuery clause and count(q) is 10. Instead it returns 0 hits and totalHits 0. RescoreTopNQuery copies the raw value -2 into the score, although Lucene requires non-negative scores (LUCENE-7996) and FunctionScoreQuery maps negative values to 0, so the clause reports a max score of -2, the two clauses' max scores sum to -1, below the initial minimum competitive score of 0, and MaxScoreBulkScorer skips the whole window as if no document could compete.
