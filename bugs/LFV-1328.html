TieredMergePolicy stores a floor below one byte as 0 bytes, and commit() can then loop forever in findMerges

TieredMergePolicy.setFloorSegmentMB accepts any floor above 0 but stores it in whole bytes, so 1e-9 MB or Double.MIN_VALUE becomes 0. If a segment's size after deletes also rounds down to 0 bytes, the next commit() spins forever at full CPU while holding the IndexWriter lock (every release tried from 4.1.0 on).

The finding in 30 seconds

#

Two roundings to whole bytes meet: the stored floor and a segment's size after deletes both become 0, and the tier loop that starts from them never ends.

Background: the merge floor and segment sizes

#
  1. TieredMergePolicy, the default merge policy, treats segments smaller than its floor (setFloorSegmentMB, default 16 MB) as if they were floor-sized, so tiny segments get merged sooner. It keeps the floor in whole bytes.
  2. For merging, a segment's size is its bytes on disk times its share of live documents, cut down to whole bytes (MergePolicy.size()).
  3. To decide how many segments the index may keep, findMerges walks tiers: it starts at a level size (the larger of the floor and the smallest segment size), counts a tier's worth of segments of that size, and multiplies the level size by the merge factor until the remaining bytes fit in one tier.

The finding, step by step

#
  1. Give an otherwise-default IndexWriterConfig new TieredMergePolicy().setFloorSegmentMB(1e-9), a way to switch the floor off since 0 is rejected. The setter accepts it but stores (long) (1e-9 * 2^20) = 0 bytes: getFloorSegmentMB() reads back 0.0.
  2. Add 10,000 one-keyword documents, delete all but one by term, and call commit(). The flushed segment has 3,716 bytes and 1 live document out of 10,000, so its size after deletes is (long) 0.37 = 0 bytes.
  3. You expect commit() to return, as it does on the same steps with a 1-byte floor (1e-6 MB, in about 90-150 ms) or with the default 16 MB floor.
  4. Instead findMerges starts its tier loop at level size max(0, 0) = 0. Dividing by 0 gives NaN or infinity, so neither exit test is ever true, and the level size and the bytes left never change. commit() spins forever inside the synchronized IndexWriter.updatePendingMerges, and Thread.interrupt() does not stop it.

Who is affected

#

Applications that set the default merge policy's floor below one byte, for example Double.MIN_VALUE to switch the floor off (Lucene's own testPartialMerge did so in 2025), and that get a segment whose size after deletes rounds to 0 bytes: tiny documents, nearly all deleted. No scale is needed. The commit then spins until the JVM is stopped.

Mechanism, terms and numbers617 words

TieredMergePolicy.setFloorSegmentMB(double) rejects only v <= 0.0 and stores the floor in whole bytes, (long) (v * 2^20). Every floor below one byte (below 2^-20 MB), such as 1e-9 or Double.MIN_VALUE, is therefore stored as 0 bytes, and getFloorSegmentMB() reads back 0.0, a value the setter itself rejects. A segment's merge size is its byte size prorated by its live documents and truncated to whole bytes, so it is also 0 for a small segment with nearly all documents deleted. When both are 0, findMerges starts its allowed-segment-count loop at a level size of 0, where the loop can never exit and its level size and remaining bytes never change. The caller is the synchronized IndexWriter.updatePendingMerges, so commit() (and, by reading, an NRT reopen) spins at full CPU while holding the writer's monitor; Thread.interrupt() does not end it, and by reading nothing short of stopping the JVM does. No index data is corrupted: by reading, the last commit point stays intact. The default 16 MB floor, and any floor of 1 byte or more, are safe. The fix is one line: store at least 1 byte.

The code (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/index/)

#
  1. The floor is stored as 0. setFloorSegmentMB: if (v <= 0.0) throw new IllegalArgumentException("floorSegmentMB must be > 0.0 ...") (TieredMergePolicy.java:169-171), v *= 1024 * 1024 (:172), floorSegmentBytes = v > Long.MAX_VALUE ? Long.MAX_VALUE : (long) v (:173). For v = 1e-9, v * 2^20 = 0.00105, and the cast gives 0. getFloorSegmentMB() returns floorSegmentBytes / 2^20 (:182-184), i.e. 0.0.
  2. A segment's size can be 0 too. MergePolicy.size() returns (long) (byteSize * (1.0 - delRatio)) (MergePolicy.java:709-716). findMerges computes that size once per segment and sorts by it (TieredMergePolicy.java:297, :300-308) and keeps the smallest as minSegmentBytes (:358).
  3. The loop has a fixed point at 0. levelSize = Math.max(minSegmentBytes, floorSegmentBytes) = 0 (:402). In while (true) (:404-413), segCountLevel = bytesLeft / (double) levelSize (:405) is NaN (0/0, as in the repro) or +Infinity; both make segCountLevel < segsPerTier false, and levelSize == maxMergedSegmentBytes (5 GB by default, :77) is false too (:406). Then bytesLeft -= segsPerTier * 0 (:411) and levelSize = Math.min(maxMergedSegmentBytes, 0 * mergeFactor) (:412) change nothing. Only allowedSegCount grows (:410), and no exit test reads it, so bytesLeft and levelSize, the values that decide termination, stay 0 on every pass. The loop has no blocking call and no interrupt check.
  4. It runs under the writer lock. commit() -> commitInternal -> prepareCommitInternal -> preparePointInTimeMerge (taken because getMaxFullFlushMergeWaitMillis(), 500 ms by default, is > 0: IndexWriter.java:3799, :3858-3864) -> updatePendingMerges (with the configured policy wrapped in a OneMergeWrappingMergePolicy, :3959-3961), which is private synchronized (:2454) and calls findFullFlushMerges for COMMIT and GET_READER (:2494-2496), which calls findMerges first (MergePolicy.java:682).

The numbers

#

Floor 1e-9 MB: stored 0 bytes, read back 0.0 (Double.MIN_VALUE the same; 1e-6 MB is stored as 1 byte and reads back 9.54e-7). 10,000 one-StringField documents, all but one deleted by term, one commit(): the flushed segment has maxDoc 10,000, 9,999 deletes and 3,716 bytes, so its size is (long) (3716 / 10000) = 0, and bytesLeft (the total of the sizes) is 0 too. After 10 s the committing thread is still at TieredMergePolicy.findMerges(TieredMergePolicy.java:413), the closing brace of the loop, with assertions on and off. The full stack on main, from a probe of the repro's steps: TieredMergePolicy.findMerges:413 <- MergePolicy.findFullFlushMerges:682 <- OneMergeWrappingMergePolicy.findFullFlushMerges:72 <- IndexWriter.updatePendingMerges:2496 <- preparePointInTimeMerge:3959 <- prepareCommitInternal:3863 <- commitInternal:4252 <- commit:4214. Releases 4.x-8.x reach the same loop through maybeMerge.

Exposure and likelihood303 words
  • Who. Users of the default TieredMergePolicy who set a floor below 2^-20 MB (one byte). That is a natural way to switch the floor off, because 0 is rejected: TestTieredMergePolicy#testPartialMerge called tmp.setFloorSegmentMB(Double.MIN_VALUE) from #14165 (2025-02-01) until #14259 (2025-02-20); on #14232 Adrien Grand suggested the same call for another test, commented "Disable merges below the floor size", and on #11610 they simulated "TieredMergePolicy with floor segment size = Double.MIN_VALUE". None of these hung, because no segment there had a 0-byte size.
  • The second condition. A segment whose prorated size truncates to 0 bytes. Once a segment has deletes, its live-docs file alone is about maxDoc / 8 bytes, so this needs at most about 7 live documents among many tiny ones; by reading, a fully deleted segment kept by a keepFullyDeletedSegment policy also qualifies.
  • Default vs opt-in. The default 16 MB floor, and any floor of 1 byte or more, are safe. No scale is needed: 10,000 one-keyword documents suffice.
  • Effect. commit() never returns and burns a core. Other writer calls that need the writer's monitor block behind it (IndexWriter.hasPendingMerges() on another thread was BLOCKED after 2 s). Thread.interrupt() does not end the spin (2 s after interrupt() the committer was still RUNNABLE, with 2,000 ms of CPU used). By reading, an NRT reopen takes the same path when maxFullFlushMergeWaitMillis is above 0, as it is by default (IndexWriter.java:619-638); the spin starts before a new segments_N is written, so the last commit point stays intact (a probe of the repro's steps found no segments_N file); and no writer call can stop the loop, so the practical way out is to stop the JVM (not tried). No data is corrupted or exposed.
  • How likely. Two independent unusual conditions must meet, and no public report of it was found since 4.1.0: priority Low.

Why it looks unintended

#
  • The setter rejects only v <= 0.0 ("floorSegmentMB must be > 0.0"), so 1e-9 is legal, yet it stores a value the setter rejects: getFloorSegmentMB() returns 0.0.
  • A 1-byte floor commits the same index in about 90-150 ms; only the stored 0 hangs.
  • Lucene's own TestTieredMergePolicy#testPartialMerge used setFloorSegmentMB(Double.MIN_VALUE) as the no-floor setting in 2025.
The full argument164 words
  • The setter's own rule makes the value legal. Only v <= 0.0 is rejected, with "floorSegmentMB must be > 0.0" (TieredMergePolicy.java:169-170; LUCENE-7005, #8062, changed it from ">= 0.0" to "> 0.0"). The javadoc describes the floor only as the size smaller segments are "rounded up" to, "Default is 16MB", with no other minimum (:156-167).
  • The stored state is one the setter rejects. After setFloorSegmentMB(1e-9), getFloorSegmentMB() returns 0.0.
  • A tiny floor should behave like no floor, as a 1-byte floor does on the same index (it commits in about 90-150 ms and merges the segment away).
  • The failure is silent and permanent: no error, an uninterruptible spin under the writer lock.
  • No test covers it. testSetters checks floors 2.0, +Infinity, Long.MAX_VALUE / 2^20 and -2.0 (TestTieredMergePolicy.java:779-792); the smallest floor in the tree today is 0.00001 MB, about 10 bytes (:800); the randomized test policies use 0.2 MB or more (LuceneTestCaseParent.java:1856, :1979).
The devil's-advocate check146 words

The strongest case, built by an intended-behaviour checker and also tried by an independent reviewer from another model family (OpenAI GPT-5.6): a floor below one byte is physically meaningless, a size in MB has to be quantized to bytes somewhere, TieredMergePolicy is @lucene.experimental (:67), and a segment with a sub-byte prorated size is a narrow shape.

Why it fails: quantizing is fine, but quantizing an accepted value to a value the setter itself forbids is not; the setter's own check and message make every v > 0 legal; Lucene's own test used exactly this value as the no-floor setting; and the outcome is an uninterruptible hang under the writer lock, not an error. The reviewer rated its own not-intended argument weak; the checker and the adjudication found it an argument about likelihood (why this is Low), not about intent. Verdict: a real Low bug.

Suggested fix

#

Recommended A. Store at least one byte (validated)

Store at least one byte in setFloorSegmentMB: Math.max(1L, (long) v). A floor below one byte then acts as a 1-byte floor. The repro passes with assertions on and off; TestTieredMergePolicy (including testSetters) and TestIndexWriterMerging pass, and the formatter check is clean.

     v *= 1024 * 1024;
-    floorSegmentBytes = v > Long.MAX_VALUE ? Long.MAX_VALUE : (long) v;
+    // never store a floor of 0 bytes: findMerges' tier loop needs a level size of at least 1 byte
+    floorSegmentBytes = v > Long.MAX_VALUE ? Long.MAX_VALUE : Math.max(1L, (long) v);
All options and trade-offs3 options · 369 words

Applied in a scratch worktree at 5adff78bb168 and run through gradle. Related, separate: LFV-447, where setSegmentsPerTier(Double.NaN) hangs the same loop through mergeFactor = (int) NaN = 0. Its trigger (NaN, on any index) and its minimal fix (Double.isNaN checks in the double setters) differ; with that fix applied this repro still hangs, and by reading option C would not cure LFV-447. The two fit naturally into one "validate TieredMergePolicy's setters" change, each with its own test.

A. Store at least one byte (validated) (recommended)

#

TieredMergePolicy.java:173, one line. Floors of 1 byte or more are unchanged. A NaN floor, which v <= 0.0 also lets through and which is stored as 0 today, becomes 1 byte as a side effect.

     v *= 1024 * 1024;
-    floorSegmentBytes = v > Long.MAX_VALUE ? Long.MAX_VALUE : (long) v;
+    // never store a floor of 0 bytes: findMerges' tier loop needs a level size of at least 1 byte
+    floorSegmentBytes = v > Long.MAX_VALUE ? Long.MAX_VALUE : Math.max(1L, (long) v);

Trade-offs

getFloorSegmentMB() then returns 9.54e-7 (1 byte) instead of the value given, but it already does not round-trip sub-byte values (today it returns 0.0). No cost at merge time.

B. Reject floors that map to 0 bytes

#

Throw IllegalArgumentException in the setter when (long) (v * 2^20) is 0.

Trade-offs

Loud and simple, but it would reject Double.MIN_VALUE, which a Lucene test and maintainer comments used to switch the floor off, so it carries some compatibility risk for callers that copied that idiom. Not run.

C. Guard the loop

#

Start the loop with levelSize = Math.max(1, Math.max(minSegmentBytes, floorSegmentBytes)) (TieredMergePolicy.java:402).

Trade-offs

Protects the loop against any 0 level size, but leaves the setter storing a value it rejects and the getter reading 0.0. Not run.

Downstream note

#

Applications that expose the merge floor as a setting and pass it straight to setFloorSegmentMB inherit the hang unless they require at least 1 byte (about 1e-6 MB).

How it was found

#

A semi-formal proof-obligation audit of TieredMergePolicy's contract: findMerges' allowed-segment-count loop must terminate for every floor setFloorSegmentMB accepts. Floors the setter accepts but stores as 0 bytes break that obligation once a segment's size is also 0, and a one-test JUnit repro witnessed the hang.

The method in full103 words

The obligation asks, for each value the setter accepts, whether the loop at TieredMergePolicy.java:404-413 reaches one of its two exits. With levelSize >= 1 it does (the level size grows by the merge factor until it reaches the maximum or the remaining bytes fit). With levelSize = 0 neither exit is reachable and the level size and the remaining bytes never change, and levelSize = 0 needs both a stored floor of 0 (any accepted 0 < v < 2^-20 MB) and a segment whose truncated size is 0. The repro builds a small such index (10,000 one-keyword documents; about 3,000 already suffice).

History

#

Code from LUCENE-1076 (f10d92398bc, 2011, in 3.2.0); first hangs in 4.1.0, whose compact default codec lets a segment hold fewer bytes than documents. Hangs on every release tried from 4.1.0 to 10.6.0 and on main; 3.2.0-4.0.0 return. Not fixed upstream as of 2026-11-03.

Versions tested6 rows

LUCENE-1076 (archived issue #2153, "Allow MergePolicy to select non-contiguous merges"; commit message "new TieredMergePolicy"; Michael McCandless; before GitHub, no PR): f10d92398bc on trunk (2011-04-02) and its branch_3x copy ec542dd385e (2011-05-05), first released in 3.2.0, added both the v <= 0.0 check with the truncating store and the loop for which a level size of 0 is a fixed point. Up to 4.0.0 the default stored-fields index wrote 8 bytes per document, so a segment with a live document could not round to 0 bytes; the 4.1 default codec (LUCENE-4446 block postings be27db62e63, LUCENE-4509 compressed stored fields 0f8ee42a944, 2012) stores the 20,000-document test segment in 1,798 bytes, and 4.1.0 hangs. By reading only (not tried): in 3.2 a fully deleted segment that a running merge has already registered stays in the segment list with size 0, so a race might reach the loop there. Later changes kept the fixed point: LUCENE-4323 (89f9beb7384, a clamp at the top end only), LUCENE-7005 (fce97a6ca6e, #8062, message only), the 7.5.0 loop rewrite (LUCENE-8385/8392/8393; its added exit levelSize == maxMergedSegmentBytes cannot fire at 0), #13430 (22ca695ef5c, target search concurrency: changed what is fed into the loop and the clamp after it) and #14165 (d2c69c1472c, merge factor only); neither touched the loop body or its exit test. The call path moved (4.x-8.x via maybeMerge, 9.x on via findFullFlushMerges), but the spinning frame is always the closing brace of the same loop. Before 9.x the runs used a main() form of the scenario adapted to each release's API (20,000 documents, commit, delete all but one, commit again), with assertions off; the one-test repro itself ran unchanged on 9.12.3, 10.5.2, 10.6.0 and main. Upstream main f72004515ec and branch_10_6 have no commit to TieredMergePolicy.java after 5adff78bb168 (2026-11-03). Not new in 10.6.

Applications that give the default TieredMergePolicy a floor below one byte (any 0 < floorSegmentMB < 2^-20, such as 1e-9 or Double.MIN_VALUE, a natural way to try to switch the floor off because 0 is rejected) and that then have a segment whose deletes-adjusted size truncates to 0 bytes (a compact segment of tiny documents with all but a handful deleted, or, by reading, a fully deleted segment that a keepFullyDeletedSegment policy keeps) get a commit() that never returns [exec]: the committing thread spins at full CPU in findMerges inside the synchronized IndexWriter.updatePendingMerges, so other writer calls that need the writer monitor block behind it (hasPendingMerges [exec]), and by reading flushes, NRT reopens and close() that consult the policy hang the same way and Thread.interrupt() cannot end the spin; only a JVM restart recovers; no scale is needed (20,000 one-keyword documents suffice), -ea and -da alike, every release from 4.1.0 through 10.6.0 and main; no index data is corrupted or exposed (by reading the spin starts before a new segments_N is written, so the last commit point stays intact).
Summary
You give the default TieredMergePolicy setFloorSegmentMB(1e-9) (the setter rejects only values <= 0), index 10,000 one-keyword documents into one small segment, delete all but one of them and call commit(), expecting it to return, as it does on the same steps, in about 90-150 ms, with a 1-byte (1e-6 MB) or the default 16 MB floor. Instead the setter stored the floor as (long) (1e-9 * 2^20) = 0 bytes (getFloorSegmentMB() reads back 0.0, a value the setter itself rejects) and the segment's deletes-adjusted size truncates to 0 bytes too, so findMerges starts its allowed-segment-count loop with levelSize = 0, where neither exit test can become true and no variable changes. That commit() spins forever at full CPU while holding the IndexWriter lock.
Introduced
f10d92398bc688b40498d9a4c765728ed446e050 (trunk, 'LUCENE-1076: new TieredMergePolicy', Michael McCandless; Subversion era, no pull request; the issue was migrated as apache/lucene#2153, whose discussion never mentions the low end of the floor) added both pieces: setFloorSegmentMB with only the 'v <= 0.0' check and the (long) (v*1024*1024) store, which is 0 for every 0 < v < 2^-20 MB, and findMerges' allowed-segment-count loop, for which levelSize = 0 is a fixed point [read: git blame at main 5adff78bb168 still attributes the check and the minSegmentBytes update to it]; it shipped in 3.2.0 through the branch_3x backport ec542dd385e ('LUCENE-1076: new TieredMergePolicy (merged from trunk)'), latent there. The hang became reachable in 4.1.0 through the compact default codec, with which a segment can hold fewer bytes than documents: be27db62e63 (LUCENE-4446, #5512, block postings, Robert Muir, 2012-10-14) and 0f8ee42a944 (LUCENE-4509, #5575, compressed stored fields by default, Adrien Grand, 2012-11-13; branch_4x) [exec: 3.2.0, 3.6.2 and 4.0.0 return on the same scenario, 4.1.0 hangs]. Later changes kept the fixed point: 89f9beb7384 (LUCENE-4323, the Long.MAX_VALUE clamp at the top end only), fce97a6ca6e (LUCENE-7005, #8062, message '>= 0.0' to '> 0.0' only), the 7.5.0 loop rewrite (41ddac5b446 LUCENE-8385, 9433ab79e22 LUCENE-8392, 8e0d9849bd4 LUCENE-8393, whose added exit 'levelSize == maxMergedSegmentBytes' cannot fire at levelSize 0) and #13430 and #14165 (mergeFactor only). Not a regression: no commit ever rejected sub-byte floors or guarded levelSize >= 1 (2011-04-02 (trunk f10d92398bc, author date); 2011-05-05 (branch_3x backport ec542dd385e, in 3.2.0); reachable since 2012-10-14 / 2012-11-13 (be27db62e63, 0f8ee42a944; first released in 4.1.0))
