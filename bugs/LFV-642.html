Hunspell COMPLEXPREFIXES accepts a second prefix that the inner prefix rule does not allow

With COMPLEXPREFIXES, Lucene's Hunspell accepts a second prefix when any rule in the dictionary allows it, not only the rule it actually follows: with re, un and dis/A, the non-word reunfoo passes spell() and is stemmed to foo. A regression since 9.5.0; native Hunspell and Lucene 9.4.2 reject it.

The bug in 30 seconds

#

Under COMPLEXPREFIXES a word may carry two prefixes. As with two suffixes, the outer prefix is allowed only if the inner prefix's own rule lists its flag after the slash. Lucene now only checks that some rule in the dictionary lists it.

  1. You load a Hunspell dictionary with COMPLEXPREFIXES (a word may carry two prefixes) and three prefix rules: re (flag A), and in class C un and dis/A. The /A on dis says re may come in front of dis. The root is foo/C.
  2. You expect unfoo, disfoo and redisfoo to be words and reunfoo not, because only dis, not un, allows re. Native Hunspell 1.3.2 and 1.7.2 and Lucene 9.4.2 agree.
  3. Instead, on 9.5.0 to 10.5.2 and main, spell("reunfoo") is true and getRoots("reunfoo") is [foo]. HunspellStemFilter indexes reunfoo as foo, so in a 3-document index (foo, reunfoo, bar) a query for foo matches 2 documents instead of 1. No error is raised.
  4. Why: after stripping re, Stemmer.isAffixCompatible accepts a cross-product second prefix without reading that prefix's continuation class (return true, Stemmer.java:566); the only chain check left is whether some prefix rule anywhere carries A. A 2022 refactor (#975) dropped the per-rule check that 9.4.2 had; two suffixes are still checked rule by rule.

Who is affected

#

Only applications that load a custom Hunspell dictionary with COMPLEXPREFIXES and continuation classes on prefix rules (spell-checking, getRoots, analyzeSimpleWord, HunspellStemFilter). Misspellings pass and non-words are indexed and searched as their root, silently. None of 191 surveyed public dictionaries has this shape. Affected: 9.5.0 to 10.5.2 and main.

Mechanism, terms and numbers745 words

Hunspell's COMPLEXPREFIXES option allows two prefixes on one word. As with two suffixes, the outer affix may only follow an inner affix rule that lists the outer affix's flag in its continuation class (the flags after the slash). With PFX A 0 re, PFX C 0 un, PFX C 0 dis/A and the root foo/C, redisfoo is a word and reunfoo is not. Since 9.5.0 Lucene no longer checks the inner rule: after stripping re, Stemmer.isAffixCompatible accepts an inner prefix of a cross-product class (one that passes the compound checks) without reading its continuation class (Stemmer.java:541, 566 on main a9779ef3c193), and what is left of the chain check is dictionary-wide: whether some prefix rule carries A. So Hunspell.spell("reunfoo") is true, getRoots returns [foo] and HunspellStemFilter indexes the token as foo, silently. Native Hunspell 1.3.2 and 1.7.2 reject reunfoo, and so does Lucene from 4.8.0 to 9.4.2 (11 of those releases run, the rest inferred from the unchanged check). The check was lost in the 2022 refactor #975 (LUCENE-10626), which reached 9.x in 9.5.0 and kept the per-rule check for twofold suffixes. Every release from 9.5.0 to 10.5.2 and main is affected; reach is narrow, because it needs a custom dictionary with COMPLEXPREFIXES and continuation classes on prefix rules.

Terms

#
  • Continuation class: flags after a slash on an affix rule. PFX C 0 dis/A . means: a word that got the prefix dis may take a prefix of class A next. hunspell(4)/(5) calls the suffix version "twofold suffix stripping": "A second s' suffix (affix class Y) will be the continuation class of the suffix able'", and adds that Hunspell "can strip another one yet (or a plus prefix in COMPLEXPREFIXES mode)".
  • COMPLEXPREFIXES: "Set twofold prefix stripping (but single suffix stripping) eg. for morphologically complex languages with right-to-left writing system".
  • Outer / inner prefix (Lucene's naming): the outer prefix is written first and stripped first (re in re+un+foo); the inner prefix is next to the root (un).

Mechanism (main a9779ef3c193)

#
  1. Dictionary collects every flag that appears in the continuation class of any PFX rule (Dictionary.java:738-740, :482). Its javadoc describes it as a pre-filter: "If an outer affix's flag isn't here, there's no need to do 2-level affix stripping with it" (Dictionary.java:138-141). dis/A puts A in it.
  2. Stemmer.applyAffix strips re and, under COMPLEXPREFIXES, looks for a second prefix because isSecondStagePrefix(A) is true (Stemmer.java:626).
  3. For the candidate un, isAffixCompatible is called with outerPrefix = re (:424):
boolean previousWasPrefix = outerSuffix < 0 && outerPrefix >= 0;      // Stemmer.java:541
...
if (dictionary.isCrossProduct(affix)) {                              // :564
  if (previousWasPrefix) return true;                                // :566, also taken for a 2nd prefix
  if (outerSuffix >= 0) {
    char prevFlag = dictionary.affixData(outerSuffix, Dictionary.AFFIX_FLAG);
    return dictionary.hasFlag(append, prevFlag);                     // :567-569, suffixes only
  }
}

previousWasPrefix is meant for "a suffix after a prefix", which needs no continuation requirement, but it is also true when the affix being checked is itself a prefix, so for a cross-product inner prefix (class C is Y) un's continuation flags are never read.

  1. The candidate foo carries un's flag C (:269-270). The root-level check of the outer prefix's flag runs only when there is no inner prefix (:271-276), so nothing rejects reunfoo.
  2. Before #975 the prefix loop passed false for the previousWasPrefix parameter and the method ended in return previousWasPrefix || dictionary.hasFlag(append, prevFlag);, so a second prefix had to carry the outer flag (the 9.4.2 code). #975 derived previousWasPrefix from affix ids instead.
  3. Native Hunspell stores prefix rules as internal suffixes under COMPLEXPREFIXES, so a twofold prefix gets the same per-rule continuation check as a twofold suffix (Hunspell 1.7.2 affixmgr.cxx, SfxEntry::checkword).

The trigger is wider than one class: un may sit in a class of its own, and a root that itself carries A (foo/AC) does not make reunfoo valid in native Hunspell while Lucene accepts it. It is enough that some prefix rule anywhere carries the outer flag.

Exposure and likelihood234 words
  • Who. Users of Hunspell.spell, getRoots, analyzeSimpleWord and HunspellStemFilter / HunspellStemFilterFactory (@lucene.experimental) with a dictionary that sets COMPLEXPREFIXES and gives some prefix rules continuation classes, where an inner prefix rule lacks a flag that another prefix rule carries (both prefix classes cross-product). Nothing else to configure; deterministic; assertions on or off.
  • What goes wrong. No exception. The spell checker accepts misspellings such as reunfoo; stemming returns a root for a non-word, so the stem filter indexes and queries it as the root. In a probe index with the documents foo, reunfoo and bar, the query foo matched 2 documents on main and 1 on 9.4.2, and the query string reunfoo parsed to f:foo.
  • Reach. Narrow. Of 191 surveyed public .aff files (99 LibreOffice, 92 wooorm/dictionaries) only one (Central Kurdish, ckb) sets COMPLEXPREFIXES, and none of its 1,812 prefix rules has a continuation class, so the second-prefix stage is never entered (the finder's survey; the ckb structure was re-checked; the 92 wooorm files were not kept, so the full survey cannot be re-run). Custom dictionaries for languages with complex prefixing are the likely users.
  • In the hunt's differential over 4,000 generated micro-dictionaries, words Lucene accepts and native Hunspell 1.7.2 rejects fell from 49 to 16 with only this fix (finder's run).
  • Since when. 9.5.0 (January 2023) on 9.x and 10.0.0 on 10.x, through 10.5.2 and main.

Why it is a bug, not intended

#
  • The format licenses the second affix through the first affix's rule; native Hunspell 1.3.2 and 1.7.2 reject reunfoo.
  • Lucene 4.8.0 to 9.4.2 checked the inner rule; #975, a feature PR, dropped the check with no CHANGES note, test or review comment about it.
  • Lucene still checks two suffixes rule by rule (fooxs rejected), and its own getAllWordForms("foo") omits reunfoo.
The full argument346 words
  • The format's contract. hunspell(4) as shipped with Hunspell 1.3.2 (hunspell(5) later): COMPLEXPREFIXES "Set twofold prefix stripping (but single suffix stripping)"; "Twofold suffix stripping": "Hunspell can strip another one yet (or a plus prefix in COMPLEXPREFIXES mode)" and "A second s' suffix (affix class Y) will be the continuation class of the suffix able'". Native Hunspell 1.3.2 (run for this doc) and 1.7.2 accept unfoo, disfoo, redisfoo and reject refoo and reunfoo.
  • Lucene's own design record. CHANGES for LUCENE-5483 (4.8.0): "Multi-stage affix-stripping, prefix-suffix dependencies, and COMPLEXPREFIXES now work correctly according to the hunspell algorithm. ... rules for recursive affix application are driven correctly by continuation classes in the affix file." A committer on LUCENE-5484 (#6547): "You should never recurse, unless the affix actually allows for it with a continuation class". The javadoc #975 deleted: "if we are removing a suffix, and it has no continuation requirements, it's ok. but two prefixes (COMPLEXPREFIXES) or two suffixes must have continuation requirements to recurse."
  • Lucene claims native behaviour. Hunspell "can be used in place of native Hunspell for many languages" (its listed exceptions are Hungarian, non-BMP characters and PHONE); Stemmer "conforms to the algorithm in the original hunspell algorithm".
  • Lucene disagrees with itself. The twofold-suffix path keeps the per-rule check (fooxs is rejected for SFX C 0 x, SFX C 0 y/A, SFX A 0 s), and getAllWordForms, documented as "equivalent to \"unmunch\"", returns [disfoo, foo, redisfoo, unfoo] while spell("reunfoo") is true.
  • The change was not meant to change behaviour. #975 ("add tools to aid dictionary editing") has no CHANGES or MIGRATE note about stemming; its test changes add tests and fixtures, none about prefix chains or continuation classes (its one rewritten assertion, in TestDictionary, keeps its value); none of its 3 comments, 12 reviews and 19 inline comments mentions Stemmer, prefixes or continuation classes. 9.4.2 is correct.
  • Why tests never caught it. TestComplexPrefix has one rule per prefix class, so it cannot tell "this rule allows it" from "some rule allows it"; no other Lucene fixture sets COMPLEXPREFIXES.
The devil's-advocate check146 words

The strongest case for "intended" (the devil's-advocate verifier and the cross-model reviewer's intended lens): the Hunspell javadoc concedes incomplete language support, the class-wide second-stage flag set (LUCENE-9799/9803, #10838/#10842) is deliberate, and over-accepting is low-harm for stemming, so the dictionary-wide check could be a permissive approximation.

Why it fails: Dictionary documents that set as a pre-filter ("no need to do 2-level affix stripping"), and LUCENE-9799/9803 introduced it as pruning while the per-rule check in isAffixCompatible stayed; the per-rule check then survived until a refactor that never mentions it; the twofold-suffix twin keeps it; Lucene's own generator disagrees with its spell checker; and the unsupported-language list is about language-specific logic, while this is generic affix semantics shown by a seven-line dictionary. Every check rejected the argument; the ones that rated its strength (the cross-model reviews and the adjudication) rated it weak. Verdict: a defect, a regression since 9.5.0.

Suggested fix

#

Recommended Restore the per-rule check for a second prefix

Restore the per-rule check in Stemmer.isAffixCompatible: when the affix being checked is a second prefix, return hasFlag(append, flag of outerPrefix) instead of true (+7/-1, the 9.4.2 rule). Validated: the repro and an extended TestComplexPrefix pass; hunspell tests: 160 run, 0 failures, 13 skipped. LFV-375 needs its own one-liner; one PR can carry both.

Trade-offs

  • Speed: not measured (no benchmark run); on the second-prefix path only, an affixData read and a hasFlag lookup replace the immediate return true.
  • Behaviour change: dictionaries that relied on the 9.5-10.5 over-acceptance lose those words, which native Hunspell never accepted. HunspellStemFilter stops stemming them, so an index built with an affected version keeps such words as the root term and needs reindexing for exact agreement.
  • Leaves LFV-375 in place: with A alone, LFV-375's repro still fails 3 of 4 with StackOverflowError; with only LFV-375's fix, this repro still fails 2 of 2. Also unchanged: a second prefix whose class has cross product N is still rejected (native accepts it; noted with LFV-641's fix).

Downstream note

#

On its own it only over-accepts words; together with the sibling third-prefix recursion bug LFV-375 (same commit, in every affected release) it lets more COMPLEXPREFIXES dictionaries reach that bug's StackOverflowError and exponential-time shapes (one 57-character token took 11 s).

How it was found

#

Differential testing of Lucene's Hunspell code against native Hunspell 1.7.2 on 4,000 generated micro-dictionaries and 1,069 fixture cases; a switchable fix separated this cause from the others, and a public-API JUnit reproduced it on the stock jar. A verifier of LFV-375 had noticed the same wrong chain a day earlier as a side probe.

The method in full147 words

Method: cross-implementation differential testing (the hunt's non-formal tier): Lucene's getAllWordForms, spell and analyzeSimpleWord against native Hunspell 1.7.2 (libhunspell spell and stem) and the hunspell-tools unmunch/munch.

  • Inputs: 4,000 seeded, grammar-built micro-dictionaries (per dictionary every candidate word reachable by at most 3 affix rules) and 1,069 per-root cases from the Hunspell 1.7.2 and Lucene test fixtures.
  • Root causes were separated with switchable shadow fixes: with only this fix, words Lucene accepts and native rejects fell from 49 to 16.
  • First observation: on 2026-10-26 the intended-behaviour verifier of LFV-375 read the #975 change and ran a targeted probe (spell("cax") true on main, 10.5.2 and 9.5.0, false on 9.4.0 and in native Hunspell); it was kept as an unregistered sibling note until this hunt found it independently.
  • Native oracle: use native spell(), not stem(), which returns nothing for prefixed words under COMPLEXPREFIXES.

Bug record

LFV-642, snapshot of 2026-10-29

Registry title
Hunspell COMPLEXPREFIXES accepts a second prefix after an inner prefix rule whose continuation class does not allow it: with 'PFX A 0 re', 'PFX C 0 un', 'PFX C 0 dis/A' and foo/C, spell("reunfoo") is true and HunspellStemFilter stems reunfoo to foo, although only dis, not un, allows re (a regression since 9.5.0)
Area
analysis / hunspell (Stemmer affix compatibility: COMPLEXPREFIXES twofold prefixes)
Priority
Low, rank 385: This 9.5 regression makes spell and stem over-accept twofold prefixes only with a custom COMPLEXPREFIXES dictionary, the same profile as its affix sibling LFV-374, so it follows that row.
Impact class
silent wrong results
Impact note
Only applications that load a hunspell dictionary combining COMPLEXPREFIXES with continuation classes on prefix rules are hit: Hunspell.spell() then accepts, and getRoots(), analyzeSimpleWord() and HunspellStemFilter stem, words whose outer prefix the stripped inner prefix rule does not allow (it is enough that some prefix rule anywhere in the .aff carries the outer flag), so misspellings pass the spell checker and non-words are indexed and searched as their root, with no error [exec]; no scale is needed; every release from 9.5.0 through 10.5.2 and main [exec at 9.5.0, 9.12.3, 10.0.0, 10.5.2 and main]; no surveyed public dictionary has this shape (the only public COMPLEXPREFIXES dictionary of 191, ckb, has no prefix continuation classes).
Summary
You load a hunspell dictionary that sets COMPLEXPREFIXES (twofold prefix stripping) with the outer prefix 'PFX A 0 re', an inner prefix class C with two rules, 'un' without a continuation class and 'dis/A', and the root foo/C, and expect what hunspell(5), C Hunspell 1.3.2 and 1.7.2 and Lucene up to 9.4.2 do: re may only precede dis, so redisfoo is a word and reunfoo is not, just as Lucene still checks the mirror-image twofold suffixes rule by rule. Instead spell("reunfoo") is true, getRoots("reunfoo") is [foo] and HunspellStemFilter turns the token reunfoo into foo, because since 9.5.0 Stemmer.isAffixCompatible returns true for any prefix stripped after another prefix (Stemmer.java:541, 566) and the only remaining gate is the dictionary-wide check that some prefix rule carries the flag A (Dictionary.isSecondStagePrefix).
