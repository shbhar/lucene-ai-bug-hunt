The finding in 30 seconds

#
  • Known upstream, not a new bug. Another person reported it with the same case and the same cause: #16887 (salvatorecampagna, 2026-10-21). Upstream fixed it on main and branch_11x with #16947 (Alan Woodward, merged 2026-10-30). A review remark on #16857 (kkewwei, 2026-10-27) asks for the guard that #16947 then added, and names #16893 as its case.
  • Released lines only. Each of the 20 releases from 9.10.0 to 10.6.0 fails the test's case, a search over all documents sorted by the whole index sort (the releases before 10.4.0 with the test in the API spelling of their line). Main and branch_11x return the right page since upstream's fix.
  • It takes three things together, each an opt-in or a choice of the application. Document blocks kept under an index sort: IndexWriterConfig#setIndexSort together with #setParentField, both unset in a new IndexWriterConfig, and blocks added with IndexWriter#addDocuments, whose javadoc at the 10.6.0 tag carries the mark @lucene.experimental (the other calls that add a block, updateDocuments and softUpdateDocuments, carry it too). A top-n search sorted by the index sort or by a prefix of it, which means sort fields equal to the first fields of the index sort, missing value included. A query whose hits include child documents.
  • Searches that match only parents were right in the controls that were run. So were, in each shape that was run: a search sorted by another field, n equal to the number of matching documents, children that carry their parent's value, children that sort before both parents, and the same blocks with neither an index sort nor a parent field.
  • What happens. A full page with no error, while a matching document that sorts before a returned hit is left out. In the test and in the twelve shapes (3 to 9 matching documents) the reported hit count was the number of matching documents; in a run with 1,200 matching documents, more than the total-hits threshold of IndexSearcher.search (1000), it was a lower bound ("1001+ hits"). No rate was measured: the cases are chosen small cases.

Background: three pieces

#
  1. An index sort (IndexWriterConfig#setIndexSort) stores the documents of a segment in the order of a sort. A search sorted the same way, or by the first fields of that sort, can then stop early in a segment: once its top n are full, the first document that does not beat the weakest of them means no later one will.
  2. A document block is a group of documents added in one IndexWriter#addDocuments call, for example children followed by their parent. With a parent field (IndexWriterConfig#setParentField) the index sort keeps each block together and orders the blocks by their parent.
  3. So in such a segment the blocks are in sort order, and the documents inside a block need not be.

The finding, step by step

#
  1. You set an index sort on the field ts together with a parent field (IndexWriterConfig#setIndexSort and #setParentField). You add two blocks with IndexWriter#addDocuments: a child without a value and its parent with ts 1, then a child without a value and its parent with ts 2.
  2. You ask for the top 2 of all four documents sorted by ts, missing values last. You expect the two parents: 1 and 2.
  3. On Lucene 10.6.0 you get the parent with 1 and a child without a value. Nothing throws, and the search reports all 4 documents as hits.
  4. Why: the segment holds the documents as none, 1, none, 2, because the blocks are ordered by their parent. The first two fill the collector's queue of 2. The third does not beat the weakest of them, and because the search is sorted by the index sort the collector takes it as the end of the segment's competitive documents. The parent with 2 is counted and never compared.
  5. On main 1640b5c394de and on branch_11x 8a72db074350 (runs of 2026-11-25) you get 1 and 2. Upstream's fix #16947 turns this early termination off for segments with document blocks.

Who is affected

#

Applications on Lucene 9.10.0 to 10.6.0 that keep document blocks under an index sort (an index sort with a parent field, both opt-ins), run a top-n search sorted by that sort or a prefix of it, and whose query matches child documents. Searches that match only parents were right in the controls that were run. No rate was measured.

Mechanism, terms and numbers1,100 words

You set an index sort on a field together with a parent field (IndexWriterConfig#setIndexSort and #setParentField), add two blocks of one child and one parent, the parents with the values 1 and 2 in the sort field and the children without a value, and ask for the top 2 of all four documents sorted by that field with missing values last. You expect the two parents, 1 and 2. On the 10.6.0 release the search returns the parent with 1 and a child without a value, with no error and with all 4 documents counted as hits.

In such a segment the blocks are ordered by their parent's value and the documents inside a block need not be in sort order. In a search sorted by the index sort or by a prefix of it, once the collector's queue holds n hits, it takes the first match of a segment that does not beat the weakest of them as the end of that segment's competitive documents and admits no later match of that segment.

Each of the 20 releases from 9.10.0 to 10.6.0 fails this case, the releases before 10.4.0 with the test in the API spelling of their line. Main and branch_11x return 1 and 2: both have upstream's fix #16947 and neither has a release.

This is known upstream. Another person reported the defect with the same case and the same cause in #16887 (salvatorecampagna, 2026-10-21), and upstream fixed it with #16947 (Alan Woodward, merged 2026-10-30). The case, the cause and the idea of the fix on this page are theirs.

The cause is the one the reporter gave on #16887. The lines below were read for this page and checked by the runs that are named with them.

At the 10.6.0 tag (where the code is)

#

TopFieldCollector.java, SortField.java and IndexSearcher.java are in lucene/core/src/java/org/apache/lucene/search/, IndexingChain.java, MultiSorter.java, Sorter.java, LiveIndexWriterConfig.java and IndexWriter.java in lucene/core/src/java/org/apache/lucene/index/.

  1. The index sort orders the blocks, by their parent. With a parent field the sorter that runs when a segment is flushed compares two documents by the sort values of the parents of their blocks: in.compare(parents.nextSetBit(docID1), parents.nextSetBit(docID2)) (IndexingChain.java:258-271). Two documents of one block tie, and a tie is broken by the document id (Sorter.java:235). A merge uses the parent's values as well (MultiSorter.java:161-171). So the blocks are ordered by their parent's value, and the documents inside a block need not be in sort order. In the test the segment holds, in document order: none, 1, none, 2 (printed by a run; a run that merged two flushed segments into one printed the same order).
  2. The collector decides per segment that it may end early. The leaf collector's constructor: final Sort indexSort = context.reader().getMetaData().sort(); searchSortPartOfIndexSort = canEarlyTerminate(sort, indexSort); (TopFieldCollector.java:58-59). canEarlyTerminate (:151-172) is true when the search sort starts with _doc or is a prefix of the index sort. A prefix means that the search's sort fields are equal to the first fields of the index sort (:168), and two sort fields are equal when field, type, direction, comparator source and missing value are (SortField.java:485-494). The word hasBlocks does not occur in the file at the tag.
  3. Once the queue is full, the first match that does not beat its weakest hit ends the segment's admission. thresholdCheck (:92-103): if (collectedAllCompetitiveHits || reverseMul * comparator.compareBottom(doc) <= 0), with the comment "since docs are visited in doc Id order, if compare is 0, it means this document is larger than anything else in the queue, and therefore not competitive" (:94-96). When the flag of step 2 is set: above the total-hits threshold the method throws CollectionTerminatedException (:100), which ends the collection of the segment; otherwise it sets collectedAllCompetitiveHits = true (:102). From then on each later match of the segment is counted (collect, :203-213) and not compared, until the hit count passes the threshold and the same check ends the segment.

Checked by runs on 10.6.0

#

With the test's own four documents, assertions on and off. With a query that matches only the parents the page is 1 and 2. The same blocks with neither an index sort nor a parent field give 1 and 2. The same search with the document id as a second sort field, which is no prefix of the index sort, gives 1 and 2 (the issue #16887 reports that form too). So does the same search with another missing value in its sort field. With the sort descending the page is wrong again: 2 and a child without a value. It is also wrong, 1 and a child without a value, when the two blocks are added with updateDocuments(Term, docs) in place of addDocuments, and when they are flushed as two segments and merged into one.

What the fix changed (main 1640b5c394de)

#

#16947 disables the sort-based early termination for segments with document blocks. FieldValueHitQueue.canEarlyTerminate(SortField[], LeafReader) begins there with if (reader.getMetaData().hasBlocks()) and the comment "index sorting only orders parent documents, so child documents break the index sort order", and then allows early termination only for a _doc sort (lucene/core/src/java/org/apache/lucene/search/FieldValueHitQueue.java:203-206; javadoc :196-201: "Segments with document blocks only terminate early for {@code _doc}"). The merged change's own text: "This commit disables sort-based early termination for indexes marked this way. Field-based pruning via competitive iterators continues to work as normal." The same lines are on branch_11x at 8a72db074350.

In a scratch checkout of main 1640b5c394de the test passes as it is, and fails with the released lines' message when those four lines are taken out (assertions on and off).

Why it looks unintended

#
  • IndexSearcher.search(Query, int, Sort) javadoc at the 10.6.0 tag: "@param n Return only the top n results". The returned page is not the top 2.
  • Upstream treated it as a defect: on #16887 a maintainer wrote "it should still be fixed" (2026-10-22), and #16947 fixed it.
  • No javadoc read at the tag asks for queries that match only parents.
The full argument196 words
  • The contract. IndexSearcher.search(Query, int, Sort): "Search implementation with arbitrary sorting.", "@param n Return only the top n results", "@return The top docs, sorted according to the supplied {@link org.apache.lucene.search.Sort} instance" (IndexSearcher.java:673-683 at the 10.6.0 tag). The test's page holds a child without a value while the parent with 2 matches.
  • Upstream's own reading. A maintainer on the issue: "it should still be fixed" (2026-10-22). The fix was merged, and its change note reads: "GITHUB#16947: Disable index-sort early termination for indexes with parent-child docs. Index sorts only apply to parent documents so naive early termination checks can read the sort value from a child document as meaning no later documents would be competitive, and incorrectly miss parent documents." (lucene/CHANGES.txt:502-505 on main 1640b5c394de, under Lucene 11.0.0, Bug Fixes).
  • No javadoc asks for it. Read at the 10.6.0 tag: IndexWriterConfig#setParentField (IndexWriterConfig.java:580-589), #setIndexSort (:505), IndexWriter#addDocuments (IndexWriter.java:1504-1530) and LeafMetaData (LeafMetaData.java:24-44). None of the four asks for sort values on child documents or for queries that match only parents.
  • The lines that have the fix give the expected answer on the same input. On main and branch_11x the test passes.
The devil's-advocate check144 words

The strongest case for "not a defect": it is an odd set-up. A search over mixed parent and child documents is not what blocks are for, and the calls involved are marked experimental. On the upstream issue a maintainer called a match-all query over mixed parent and child documents "kind of an odd setup" and wrote "it should still be fixed" (2026-10-22). The case fails for three reasons. Upstream fixed it. The query need not match all documents: a query that matches only children gave a wrong top 1 on 10.6.0, and so did the join module's own query for child documents, ToChildBlockJoinQuery, in the one shape that was run. And @lucene.experimental (on IndexWriter#addDocuments, and on TopFieldCollector at TopFieldCollector.java:35) allows the API to change between releases; it does not make a page that is not the top n the documented result.

Upstream's fix #16947: no index-sort early termination on segments with document blocks (validated by the checks) (recommended)

#

FieldValueHitQueue.canEarlyTerminate(SortField[], LeafReader) returns early for a segment with document blocks: such a segment ends early only for a _doc sort (FieldValueHitQueue.java:203-206 on main 1640b5c394de, the same lines on branch_11x 8a72db074350). The merged change (Alan Woodward, f6e64aa0db37 on main, e5c8f72f00f5 on branch_11x, both of 2026-10-30) also added two tests to TestTopFieldCollectorEarlyTermination. Its lines:

   static boolean canEarlyTerminate(SortField[] searchSort, LeafReader reader) {
+    if (reader.getMetaData().hasBlocks()) {
+      // index sorting only orders parent documents, so child documents break the index sort order
+      return SortField.FIELD_DOC.equals(unwrap(searchSort[0]));
+    }

Trade-offs

  • A segment with document blocks no longer ends early on an index-sort prefix, also for a search that matches only parents. The reporter named this cost on the issue: "This also turns early termination off for queries that only match parents, which may cost performance (not measured)". It was not measured here either.
  • The merged change's text says that pruning through competitive iterators stays: "Field-based pruning via competitive iterators continues to work as normal."

What the checks validated

  • In a scratch checkout of main 1640b5c394de (2026-11-25, Gradle): the test passes 1 of 1 with assertions on and off, and TestTopFieldCollectorEarlyTermination (12 tests) and TestTopFieldCollector (13 tests) pass (the two suites were run with assertions on).
  • With the four guard lines taken out of that checkout: the test fails 1 of 1 with assertions on and off, with the message of the released lines, and the two tests that #16947 added fail (testNoIndexSortEarlyTerminationWithBlocks, testCompetitiveIteratorWithBlocks). TestTopFieldCollector still passes (the two suites with assertions on).
  • On builds of main 1640b5c394de and branch_11x 8a72db074350: the test, the five controls and the twelve shapes are right, and the four probes return 1 and 2.

LFV-1569, snapshot of 2026-11-27

Registry title
On Lucene 9.10.0 to 10.6.0, a search sorted by the index sort (or a prefix of it) on a segment with document blocks can miss a hit that sorts before one it returns, when the query matches child documents (on the released 9.x and 10.x lines only since #16947 fixed it on main and branch_11x, both unreleased; known upstream as #16887)
Area
search / sorted top-n collection: index-sort early termination (TopFieldCollector) on segments with document blocks (IndexWriterConfig#setParentField)
Priority
Low, rank 302: On Lucene 9.10.0 to 10.6.0 (each of the 20 releases fails the case of a search over all documents sorted by the whole index sort), a top-n search sorted by the index sort (or a prefix of it) over an index that keeps document blocks under that sort can return a page that lacks a matching document sorting before a returned hit, with no error, when the query matches child documents. It is Low because another person already reported it upstream and upstream fixed it on main and branch_11x, which passed the runs here, because the configuration is an opt-in (an index sort with a parent field), and because the searches that match only parents were right in the controls that were run. What remains is the affected code in the releases 9.10.0 to 10.6.0; for a search that is affected the result is a wrong page with no error.
Impact class
silent wrong results
Impact note
An application on Lucene 9.10.0 to 10.6.0 can get a wrong top-n page when it keeps document blocks under an index sort (IndexWriterConfig#setIndexSort together with #setParentField, both unset in a new IndexWriterConfig, and blocks added with IndexWriter#addDocuments; the same blocks with neither an index sort nor a parent field gave the right page), runs a top-n search sorted by the index sort or by a prefix of it, and its query matches child documents: the search can then return a full page with no error while a matching document that sorts before a returned hit is left out, with and without assertions; no scale is needed (the test has four documents) [exec]. Twelve shapes were run on 10.6.0 and 9.10.0 with small indexes (two or three blocks of one or two children, n from 1 to 4; in each of the twelve the reported hit count was the number of matching documents, and in a further run on 10.6.0 with a total-hits threshold of 1 it was '3+ hits' for four matches, with the same wrong page): the page was wrong for a query over all documents whose children have a larger value than their parent (in the test itself they have no value), for a query that matches only children, for a descending sort, across two segments of one block each and for a search sorted by the first field of a two-field index sort; it was right for a query that matches only parents, for a search sorted by another field, when n was the number of matching documents, when each child carried its parent's value and when both children carried a value below both parents [exec]. On branch_11x 75eea467ac52 and main f2b061406c4b the test passed and the twelve shapes were right, with -ea and -da, when run on 2026-11-20; the test also passed on branch_11x 55ef56a69344 and main 8506598d7a98 when run on 2026-11-25 [exec]. With the index sort set and no parent field, 10.6.0 and branch_11x reject the block at addDocuments, while 9.10.0 accepts it and stores the documents sorted one by one (no block is kept, and the search was then right) [exec]. IndexWriter#addDocuments, the call the test indexes its blocks with, is marked @lucene.experimental, and so are the other calls that index a block (updateDocuments, softUpdateDocuments).
Summary
You set an index sort on a field together with a parent field (IndexWriterConfig#setIndexSort and #setParentField), add two blocks of one child and one parent, the parents with the values 1 and 2 in the sort field and the children without a value, and ask for the top 2 of all four documents sorted by that field with missing values last. You expect the two parents, 1 and 2. Instead, on the 10.6.0 release the search returns the parent with 1 and a child without a value, with no error and with all 4 documents counted as hits (each of the 20 releases from 9.10.0 to 10.6.0 fails this case, the releases before 10.4.0 with the test in the API spelling of their line). In such a segment the blocks are ordered by their parent's value and the documents inside a block need not be in sort order, but once the collector's queue holds n hits it takes the first match of a segment that does not beat the weakest of them as the end of that segment's competitive documents and admits no later match of that segment. branch_11x and main (both unreleased; fixed there by #16947) returned 1 and 2 in the runs of 2026-11-20 and 2026-11-25.
