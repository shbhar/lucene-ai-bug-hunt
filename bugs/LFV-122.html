SortedNumericSortField's javadoc on main suggests STRING_FIRST / STRING_LAST for missing values, but a numeric sort cannot use them

On main, SortedNumericSortField's javadoc says missing values sort first or last via SortField.STRING_FIRST / STRING_LAST, but a numeric sort cannot use these string markers: it accepts them, then the first search or setIndexSort throws ClassCastException. Only the sentence is wrong; a numeric sort takes a number such as Long.MAX_VALUE.

The finding in 30 seconds

#

The 5-argument constructor stores any Object as the missing value (SortedNumericSortField.java:99-114): SortField checks the missing value only for Type.STRING, and this class passes Type.CUSTOM. The first search or index sort then casts it to Integer, Long, Float or Double (:316, :383 for LONG), and a marker is a plain Object.

Background: missing values in Lucene sorts

#
  1. A sort's missing value says where documents without a value in the sort field go.
  2. String sorts (SortField with Type.STRING, SortedSetSortField) take one of two markers: SortField.STRING_FIRST or SortField.STRING_LAST.
  3. Numeric sorts take a number of the sort's type that such documents sort as: Long.MIN_VALUE puts them first and Long.MAX_VALUE last (the other way round in reverse order); without one they sort as 0.
  4. On main, SortField.setMissingValue is gone (#15486): the missing value is a constructor argument of type Object.

The finding, step by step

#
  1. One document has no value in the LONG field f, and you want such documents to sort last. The class javadoc says: "this also supports sorting missing values as first or last, via SortField#STRING_FIRST or SortField#STRING_LAST".
  2. So you build new SortedNumericSortField("f", SortField.Type.LONG, false, SortedNumericSelector.Type.MIN, SortField.STRING_LAST). The constructor accepts it.
  3. You expect searcher.search(MatchAllDocsQuery.INSTANCE, 1, new Sort(sortField)) to return the document, sorted last, or the constructor to reject the marker.
  4. Instead the search throws ClassCastException: class org.apache.lucene.search.SortField$2 cannot be cast to class java.lang.Long, because the LONG comparator casts the missing value to Long. IndexWriterConfig.setIndexSort with the same sort fails the same way, and so do all 4 numeric types with both markers.
  5. What works is a number of the sort's type: Long.MAX_VALUE puts missing documents last, Long.MIN_VALUE first, as the migration guide and the upstream tests do. Releases through 10.6.0 are unaffected: their javadoc points to setMissingValue(Object).

Who is affected

#

Only users of unreleased main (11.0.0-SNAPSHOT) who follow this sentence for a numeric SortedNumericSortField (INT, LONG, FLOAT or DOUBLE), at search time or as an index sort. With otherwise default settings, at any index size, they get an immediate ClassCastException, before any hit is collected, so no wrongly ordered result comes back.

Mechanism, terms and numbers543 words

On main, the class javadoc of SortedNumericSortField says: "Like sorting by string, this also supports sorting missing values as first or last, via {@link SortField#STRING_FIRST} or {@link SortField#STRING_LAST}." Those two constants are markers for string sorts. A numeric SortedNumericSortField (INT, LONG, FLOAT or DOUBLE) accepts them without complaint, because its 5-argument constructor stores any Object as the missing value, and then the first search or index-sort setup casts the value to Integer, Long, Float or Double and throws ClassCastException.

The code is correct and intended: a numeric sort takes a number of its own type as the missing value (Long.MIN_VALUE / Long.MAX_VALUE to sort missing documents first / last), as the migration guide and the upstream tests show. The sentence came in with #15486, which removed setMissingValue and replaced the old pointer "via setMissingValue(Object)" with the two string markers in both SortedNumericSortField and SortedSetSortField; that is correct only for SortedSetSortField. Main only: no release has the sentence. The proposal is a javadoc fix, optionally with a constructor type check that fails fast.

The mechanism (main 645d4fe14a20)

#
  1. The javadoc names the string markers. SortedNumericSortField.java:44-45: "Like sorting by string, this also supports sorting missing values as first or last, via {@link SortField#STRING_FIRST} or {@link SortField#STRING_LAST}." The constructor's @param missingValue says only "the sort value to use for documents with no value in the field" (:97).
  2. No type check on the way in. The 5-argument constructor calls super(field, SortField.Type.CUSTOM, reverse, missingValue) and stores the object (:99-114). SortField.validateField checks the missing value only for Type.STRING (SortField.java:337-349, the check at :343-348).
  3. The markers are plain objects. SortField.java:309-325: STRING_FIRST and STRING_LAST are anonymous Object instances (hence SortField$1 / SortField$2 in the message), documented as "Pass this as a missingValue constructor parameter to have missing string values sort first/last".
  4. First use casts to the numeric type. getComparator passes (Integer) missingValue, (Float), (Long) or (Double) to the comparator (:272, :294, :316, :338); getIndexSorter does the same (:380, :383, :386, :389); IndexWriterConfig.setIndexSort calls getIndexSorter() on every sort field (IndexWriterConfig.java:505-510). So the index sort fails at configuration time, before any document is indexed.
  5. What a numeric missing value means. The comparators substitute it for absent values and use 0 when it is null (comparators/LongComparator.java:37, likewise for Int, Float and Double), so Long.MIN_VALUE / Long.MAX_VALUE sort missing documents first / last and reverse flips that (upstream TestIndexSorting.testMissingMultiValuedLongFirst runs both directions).
  6. Why the same sentence is right in SortedSetSortField. That class reads the missing value only as one of the two markers (SortedSetSortField.java:128-130, :176, :191).
  7. Type-safe entry points exist. LongField.newSortField(field, reverse, selector, long missingValue) (document/LongField.java:186-189) and its Int, Float and Double counterparts take a primitive, so they cannot get the wrong type.

What is not claimed

#

The late ClassCastException for a wrong-typed missing value is old and general: it was executed on 9.12.3 and 10.3.2 (through setMissingValue(STRING_LAST)) and on 10.4.0 and 10.5.2 (through the 5-argument constructor), and plain new SortField(f, SortField.Type.LONG, false, SortField.STRING_LAST) behaves the same on main and 10.5.2. On those releases the javadoc did not suggest the markers. Only the sentence is new.

Exposure and likelihood183 words
  • Who. Users of main who read this class javadoc to sort missing values first or last on a numeric SortedNumericSortField.
  • Default vs opt-in. The input shape is opt-in (a string marker as the missing value of a numeric sort) and only this sentence suggests it; everything else is default: IndexWriterConfig, codec and IndexSearcher, assertions on or off. The cast fails before any doc values are read, so no codec or setting avoids it.
  • What goes wrong. An immediate ClassCastException on each search with that sort, or from IndexWriterConfig.setIndexSort before an IndexWriter exists. Nothing hangs and nothing is written; the exception comes before any hit is collected, so no wrongly ordered result is returned.
  • Scale. Any index size; one document is enough.
  • Why fix it before 11.0. setMissingValue is gone on main, so a SortedNumericSortField gets its missing value only at construction: through this 5-argument constructor, whose class javadoc is where users look for how, or through typed helpers such as LongField.newSortField(field, reverse, selector, long missingValue), which cannot take a marker. 11.0.0 would be the first release with the sentence.

Why it looks unintended

#
  • The class's own javadoc prescribes the markers, through its public constructor and constants.
  • An accidental edit: #15486 replaced "via setMissingValue(Object)" with the string markers in both SortedSetSortField (correct there) and this class; nobody discussed it.
  • Everything else says numeric: the markers' javadoc ("missing string values"), the migration guide (0L), the upstream tests (Integer.MIN_VALUE / MAX_VALUE).
The full argument173 words
  • Contract. SortedNumericSortField.java:44-45 (quoted above). A user who follows it violates no precondition stated on the class.
  • History. The sentence dates from LUCENE-5748 (2014) with "via {@link #setMissingValue(Object)}": 398af4596bd on trunk (first released in 6.0.0) and its branch_4x counterpart d1522d5fe78 (first released in 4.9.0). #15486 (f4f6d70c0c4, 2025-12-09) changed that one javadoc line and removed the setMissingValue override in this class; the constructor, getComparator, getIndexSorter and the serialization were not touched. The javadoc was not discussed in #15480, #15483, #15486 or #15720.
  • Every other source says numeric. SortField.java:309, :318 (the markers are for "missing string values"); lucene/MIGRATE.md:258-278, which shows new SortedNumericSortField("price", SortField.Type.LONG, false, SortedNumericSelector.Type.MIN, 0L) (:273-274) and STRING_LAST only for SortedSetSortField (:276-277); TestSortedNumericSortField.testMissingFirst / testMissingLast with Integer.MIN_VALUE / Integer.MAX_VALUE (TestSortedNumericSortField.java:158, :194); no upstream test pairs the markers with SortedNumericSortField.
  • A sibling class states the rule. ToParentBlockJoinSortField (join module): "For numeric types use the corresponding boxed type (e.g. {@link Integer} for Type.INT)" (ToParentBlockJoinSortField.java:139-142), and it validates that (:166-198, #15727).
The devil's-advocate check113 words

The strongest case for "intended": numeric sorts take a number, the markers are documented for strings, a wrong-typed Object missing value has always failed late (executed on 9.12.3, 10.3.2, 10.4.0 and 10.5.2), and plain SortField behaves the same, so this is user error.

Why it fails: it defends the code, not the sentence. The javadoc of the very class being called tells users to pass the markers, so following the documentation produces the exception. That is why this is a javadoc defect, and why a constructor type check is an optional usability improvement, not a regression fix. (Such a check would be new here: this class's own setMissingValue override never validated the value.)

Suggested fix

#

Recommended A. Correct the class javadoc (recommended)

Correct the class javadoc: a numeric sort takes a missing value of its own boxed type, for example Long.MIN_VALUE / Long.MAX_VALUE to sort missing documents first / last, and the string markers cannot be used here. No behaviour change. Validated: the format check and the javadoc render pass, and the new text links resolve.

- * <p>Like sorting by string, this also supports sorting missing values as first or last, via {@link
- * SortField#STRING_FIRST} or {@link SortField#STRING_LAST}.
+ * <p>Documents without a value sort as the {@code missingValue} passed to the constructor, or as 0
+ * when it is null. It must match {@code type}: an {@link Integer} for {@code Type.INT}, a {@link
+ * Long} for {@code Type.LONG}, a {@link Float} for {@code Type.FLOAT} or a {@link Double} for
+ * {@code Type.DOUBLE}. To sort them first or last, pass a value that sorts before or after every
+ * value in the field, for example {@link Long#MIN_VALUE} or {@link Long#MAX_VALUE} (the other way
+ * round when {@code reverse} is true). {@link SortField#STRING_FIRST} and {@link
+ * SortField#STRING_LAST} cannot be used here.

A. Correct the class javadoc (recommended) (validated by the checks)

#

Replace the sentence (SortedNumericSortField.java:44-45) with the numeric rule, naming the four supported types. Optionally extend the constructor's @param missingValue (:97) the same way (not run).

- * <p>Like sorting by string, this also supports sorting missing values as first or last, via {@link
- * SortField#STRING_FIRST} or {@link SortField#STRING_LAST}.
+ * <p>Documents without a value sort as the {@code missingValue} passed to the constructor, or as 0
+ * when it is null. It must match {@code type}: an {@link Integer} for {@code Type.INT}, a {@link
+ * Long} for {@code Type.LONG}, a {@link Float} for {@code Type.FLOAT} or a {@link Double} for
+ * {@code Type.DOUBLE}. To sort them first or last, pass a value that sorts before or after every
+ * value in the field, for example {@link Long#MIN_VALUE} or {@link Long#MAX_VALUE} (the other way
+ * round when {@code reverse} is true). {@link SortField#STRING_FIRST} and {@link
+ * SortField#STRING_LAST} cannot be used here.

Trade-offs

  • No behaviour change; it states what the code, the migration guide and the upstream tests already do, close to the wording ToParentBlockJoinSortField uses for its numeric missing values. It does not catch a wrong-typed value early: a marker still fails at first use, now against clear documentation.
  • It names only the four types the class supports (any other type throws AssertionError in getComparator / getIndexSorter, :361-362, :396-397), and it does not call the markers "for string sorts only": BinarySortField takes them too (BinarySortField.java:31-40, :95-97), as does SortField with Type.STRING_VAL.
  • A document whose value equals the chosen value sorts together with the missing documents (ties fall back to the next sort field, then the doc id). For FLOAT and DOUBLE the comparators use Float.compare / Double.compare, which order NaN after positive infinity, so POSITIVE_INFINITY does not sort missing documents after NaN values.

B. A plus a constructor type check (optional extra) (validated by the checks)

#

In the 5-argument constructor, for the four numeric types, reject a non-null missing value whose class does not match the type, with IllegalArgumentException, as ToParentBlockJoinSortField does for its child missing value (#15727).

     if (type == null) {
       throw new NullPointerException();
     }
+    if (missingValue != null) {
+      Class<?> expected =
+          switch (type) {
+            case INT -> Integer.class;
+            case LONG -> Long.class;
+            case FLOAT -> Float.class;
+            case DOUBLE -> Double.class;
+            // $CASES-OMITTED$
+            default -> null;
+          };
+      if (expected != null && expected.isInstance(missingValue) == false) {
+        throw new IllegalArgumentException(
+            "Missing value for Type."
+                + type
+                + " must be a "
+                + expected.getName()
+                + ", got "
+                + missingValue);
+      }
+    }
     this.selector = selector;
     this.type = type;
   }

Trade-offs

  • For INT, LONG, FLOAT and DOUBLE, moves the failure of a wrong-typed missing value from the first search or setIndexSort to construction, with a clear message. It checks only those four: for any other type the default branch yields null, no check runs, and the sort still fails at first use with the AssertionError of getComparator / getIndexSorter. A wrong-typed value always failed at first use already, so only a sort that is built but never used would newly fail; still worth a CHANGES entry.
  • Every in-tree caller passes the matching type (LongField.newSortField and its siblings, the MultiValued*FieldSource classes, the tests), and the core and queries tests below pass.
  • Plain new SortField(f, SortField.Type.LONG, false, SortField.STRING_LAST) has the same late failure and is not covered; a general check would belong in SortField.validateField (a wider change, not run).

C. Make the markers work for numeric sorts (not recommended)

#

Translate STRING_FIRST / STRING_LAST in the constructor into the type's extreme value, taking reverse into account, so that the current sentence becomes true.

Trade-offs

  • A new feature rather than a fix: getMissingValue, equals, toString and serialization would see the translated number, floats and doubles need a choice (infinities), and real extreme values tie with missing documents.
  • Overlaps the typed newSortField helpers on IntField / LongField / FloatField / DoubleField. Not built or run.

Downstream note

#

Products that offer a "missing first / last" option on numeric fields should map it to a typed number such as Long.MAX_VALUE, not to the string markers; the Solr migration to Lucene 11 already passes numeric values.

LFV-122, snapshot of 2026-11-09

Registry title
SortedNumericSortField's class javadoc on main says missing values sort first or last via SortField.STRING_FIRST / STRING_LAST, but a numeric sort cannot use these string sentinels: the constructor accepts them, then every search or index sort with them throws ClassCastException
Area
search / sorting (SortedNumericSortField missing values; javadoc)
Priority
Low, rank 1313: SortedNumericSortField's main-branch javadoc suggests STRING_FIRST/STRING_LAST, which throws ClassCastException on first use, a loud doc error in unreleased code.
Impact class
minor
Impact note
Only users of unreleased main (11.0.0-SNAPSHOT) who follow this one javadoc sentence and pass SortField.STRING_FIRST or STRING_LAST as the missing value of a numeric SortedNumericSortField (INT, LONG, FLOAT or DOUBLE), with the default IndexWriterConfig, codec and searcher, -ea or -da, at any index size: they get an immediate ClassCastException on the first search with that sort (getComparator) or when they set it as an index sort (IndexWriterConfig.setIndexSort, before any document is indexed); results are never wrong, and the code behaves as designed, only the documentation is wrong.
Summary
You follow the SortedNumericSortField class javadoc on main ('Like sorting by string, this also supports sorting missing values as first or last, via SortField#STRING_FIRST or SortField#STRING_LAST') and build new SortedNumericSortField("f", SortField.Type.LONG, false, SortedNumericSelector.Type.MIN, SortField.STRING_LAST). You expect documents without a value to sort last, or, if the sentinels are not supported, the constructor to reject them. Instead the constructor accepts the sentinel, and IndexSearcher.search with that sort, or IndexWriterConfig.setIndexSort with it, throws ClassCastException 'SortField$2 cannot be cast to class java.lang.Long', because a numeric sort needs a missing value of its own numeric type (for example Long.MAX_VALUE to sort missing documents last), as MIGRATE.md and the upstream tests show.
