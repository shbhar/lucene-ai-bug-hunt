ByteBuffersDataInput reads a positioned last buffer from index 0 and returns the wrong bytes

ByteBuffersDataInput never checks that its last buffer starts at position 0: the windows wrap(data, 0, 2) and wrap(data, 2, 1) over {1, 2, 3} read back as [1, 2, 1], with no error. Every release since 7.5.0 has it; Lucene's own code never builds such a list.

The finding in 30 seconds

#

ByteBuffersDataInput reads a list of buffers as one stream of equal-size blocks. Its constructor checks the list, but the check that buffers after the first start at position 0 never looks at the last buffer, and the reads assume it.

Background

#
  1. A ByteBuffer window has a position(), where its data starts, and remaining() bytes. ByteBuffer.wrap(data, 2, 1) is a window over the whole array that starts at index 2 and holds 1 byte.
  2. ByteBuffersDataInput treats its buffers as blocks: the first buffer's position() + remaining(), a power of two, is the block size, and stream byte p is block p / size, offset p % size.
  3. Only the first buffer may start at a non-zero position (it shifts the whole stream). The constructor throws "All buffers except for the first one must have position() == 0" for every middle buffer that breaks this rule.

The finding, step by step

#
  1. Split data = {1, 2, 3} into two buffers, ByteBuffer.wrap(data, 0, 2) and ByteBuffer.wrap(data, 2, 1), and pass them to new ByteBuffersDataInput(List). The second buffer holds one byte, 3, at position() 2.
  2. You expect the bytes [1, 2, 3], or an IllegalArgumentException: the constructor throws "All buffers except for the first one must have position() == 0" for the same buffer in any middle slot.
  3. You get an input with length() 3 whose readBytes returns [1, 2, 1]. A readByte() at position 3 returns 2 instead of throwing EOFException. Nothing fails, with assertions on or off.
  4. Why: the validation loop covers buffers 1 to last - 1 only, so the last buffer is never checked, and the reads address each buffer after the first from index 0. Stream byte 2 is index 0 of the second buffer, which is data[0] = 1.

Who is affected

#

Only code outside Lucene that builds its own buffer list for this public constructor with a positioned last buffer, such as exactly two ByteBuffer.wrap(array, offset, length) windows over one array (three or more already throw). It silently reads wrong bytes. Lucene's own code never builds such a list, so indexing and search are unaffected.

Mechanism, terms and numbers512 words

new ByteBuffersDataInput(List<ByteBuffer>) reads a list of buffers as one stream. Its validation rejects a middle buffer whose position() is not 0, but the loop stops before the last buffer. A positioned last buffer is accepted: length() counts its remaining() bytes, while the reads address those bytes from index 0. With data = {1, 2, 3} split into wrap(data, 0, 2) and wrap(data, 2, 1), the input reads back [1, 2, 1] and returns a byte at length() instead of EOFException. Only hand-built lists reach it; the fix is a one-character loop bound.

The bug (main f794ff5a505c)

#
  1. The check skips the last buffer. ByteBuffersDataInput.ensureAssumptions (:465-477):
// Any block from 2..last-1 should have the same page size.
for (int i = 1, last = buffers.size() - 1; i < last; i++) {
  ByteBuffer buffer = buffers.get(i);
  if (buffer.position() != 0) {
    throw new IllegalArgumentException(
        "All buffers except for the first one must have position() == 0: " + buffer);
  }
  if (i != last && buffer.remaining() != blockPage) { ... }
}

With two buffers last = 1, so the body never runs. Inside i < last the guard i != last is always true, which strongly suggests the loop was meant to reach the last buffer and skip just its size check (the comment above the loop speaks only of the size rule for blocks 2..last-1).

  1. Only the first buffer's position is honoured. The constructor keeps read-only views with each buffer's own position and limit (:58-61), sums remaining() into length() (:74-78: 2 + 1 = 3) and stores only blocks[0].position() as the stream offset (:80-82).
  2. Reads address blocks from index 0. Stream position p maps to block p >> blockBits, offset p & blockMask (:432-438), and readByte() (:94-98), readBytes(byte[], int, int) (:142-148) and readByte(long) (:211-214) use that offset as an absolute index into the block. Stream byte 2 is block 1, offset 0: index 0 of wrap(data, 2, 1), which is data[0] = 1, not data[2] = 3.
  3. No EOF at length(). Position 3 is block 1, offset 1 = data[1] = 2. Index 1 is inside that buffer's limit (3), so the read succeeds and the EOFException path is never taken.

In general, for a last buffer with position() p and remaining() r, the stream bytes it should supply are read from indices 0 to r - 1 instead of p to p + r - 1 (and a read at length() can still land inside the buffer, step 4). Every read goes through bounds-checked java.nio accessors on read-only views, so nothing outside the caller's own buffer is read.

Exposure and likelihood164 words
  • Who is hit. Application or library code that passes its own List<ByteBuffer> to new ByteBuffersDataInput(...) with middle buffers at position 0 and a positioned last buffer. The class is public final, its package is exported (module-info.java:44), and it carries no @lucene.experimental or @lucene.internal tag. Natural shapes: exactly two windows over one array made with ByteBuffer.wrap(array, offset, length) (with three or more, a middle window is positioned and the constructor throws), or a last buffer whose position an earlier read advanced.
  • Silent. length() is right, the bytes are wrong, and nothing throws; a read at length() returns a byte.
  • Default vs opt-in. No configuration is involved, and assertions do not matter. Lucene's own producers never build the shape: ByteBuffersDataOutput.toBufferList() flips every block (ByteBuffersDataOutput.java:241-244), slice positions only the first buffer and limits the last (ByteBuffersDataInput.java:519-520), and ByteBuffersDirectory, PrefixCodedTerms, Lucene90CompressingTermVectorsReader and ReplicaNode pass one buffer or such lists.
  • Scale. Three bytes are enough. No downstream trigger is known.

Why it looks unintended

#
  • The class's own rule, "All buffers except for the first one must have position() == 0", is enforced for middle buffers only.
  • The javadoc constrains only remaining(), which this list meets; length() counts those bytes, the reads return others.
  • i != last is always true inside i < last, which suggests the loop was meant to reach the last buffer.
The full argument158 words
  • The javadoc accepts the list. ByteBuffersDataInput.java:50-54: "Read data from a set of contiguous buffers. All data buffers except for the last one must have an identical remaining number of bytes in the buffer (that is a power of two). The last buffer can be of an arbitrary remaining length." Nothing about position().
  • The class's own rule. The message at :470 is thrown for every positioned middle buffer; the same buffer in the last slot is accepted. Rejecting the list or reading its remaining() bytes would both be consistent; returning other bytes with no error fits neither.
  • The dead guard. i != last (:472) can never be false inside i < last (:466). Both lines are unchanged since the class was created in 2018.
  • Tests. None of the four ensureAssumptions messages appears in any Lucene test, and TestByteBuffersDataInput has no IllegalArgumentException check; its testSlicingLargeBuffers positions only the first buffer and limits the last.
The devil's-advocate check178 words

The argument. The class was designed for ByteBuffersDataOutput pages. A design note by Dawid Weiss on LUCENE-8438 (#9484, comment of 2018-08-06) says "for N buffers, the capacity of buffers 1..N-1 is constant and power-of-two (which is what ByteBuffersDataOutput emits) ... The initial buffer can also have the initial read position shifted from 0 (for easy slicing)". So a positioned last buffer is a caller error, and garbage in gives garbage out.

Why it fails. That note supports rejecting the list (the recommended fix), not silently mis-reading it. It is not in the javadoc users read, the class enforces the rule for middle buffers, and the same thread argued for keeping these classes public so that others can build their own directory or buffer wrappers (Dawid Weiss, #9484, comment of 2018-08-10).

What a maintainer may still say. The exception text and the design note state the rule even though the javadoc does not, so this can also be read as hardening an unwritten precondition (which is what the recommended fix does) rather than as a change of public semantics.

Downstream note

#

Libraries that pass their own buffer lists to this constructor can avoid the bug today by passing every buffer after the first as buffer.slice(), which starts at position 0 (checked on the repro's input).

How it was found

#

A proof-obligation audit (semi-formal) of ByteBuffersDataInput's contract: it listed what every read relies on about the buffer list, here that buffers after the first start at position 0, and asked whether the constructor guarantees it. It found the loop that stops before the last buffer, and a one-test JUnit repro on main witnessed it.

The method in full108 words

Semi-formal method: the audit matched the constructor's validation (ensureAssumptions) against the layout the reads assume (only the first buffer's position is honoured; every other block is addressed from index 0). The obligation "every non-first buffer has position() == 0" is checked for buffers 1 to last - 1 only. A one-test JUnit on main witnessed the gap with assertions on and off; a scratch probe checked sequential, positional and slice reads and the read at length().

An independent reproducer, executed cross-model reviews (OpenAI GPT-5.6) and an intended-behaviour verifier then checked it, most of them with their own tests, and an adjudication re-ran and confirmed it.

Impact class
minor
Impact note
Minor: silent wrong bytes, but only for a hand-built buffer list of an unusual shape that Lucene's own producers never build. Hits only code that builds its own List<ByteBuffer> for the public new ByteBuffersDataInput(List<ByteBuffer>) constructor with a last buffer whose position() > 0 (the natural shape is two windows over one array made with ByteBuffer.wrap(array, offset, length)): the input then silently returns the bytes that lie before that buffer's position() instead of its own bytes, with -ea and -da, in every release from 7.5.0 through 10.6.0 and on main; Lucene's own producers (ByteBuffersDataOutput, slices, ByteBuffersDirectory, PrefixCodedTerms) always build position-0 non-first buffers, so default indexing and search never reach it, and no scale is needed (12 bytes).
Summary
You split a 12-byte array into two pages with ByteBuffer.wrap(data, 0, 8) and ByteBuffer.wrap(data, 8, 4) and pass them to new ByteBuffersDataInput(List<ByteBuffer>); the constructor accepts the list and length() is 12. You expect to read bytes 0..11, or an IllegalArgumentException, which the constructor throws for the same buffer in any middle slot ('All buffers except for the first one must have position() == 0'). Instead bytes 8..11 read back as 0, 1, 2, 3 and a read at length() returns a byte instead of EOFException, because the validation loop stops before the last buffer and every read addresses that buffer from index 0 instead of from its position(); no exception or assertion fires.
