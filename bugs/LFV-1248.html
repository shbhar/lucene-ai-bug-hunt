OfflineSorter loses the original read failure when re-opening the file for its checksum check fails

When OfflineSorter cannot read an entry, it re-opens the file to check its checksum and attach the result to the error. If that re-open fails, sort() throws only the open error and the read failure (here an EOFException from a truncated entry) is lost, in every release since 6.0.0.

The finding in 30 seconds

#

After a failed read, OfflineSorter checks the file's checksum to tell you whether the file is damaged. When that check cannot even open the file, it throws away the error it was meant to explain.

OfflineSorter's checksum check in one minute

#
  1. OfflineSorter sorts a file of entries (a 2-byte length, then that many bytes) that may not fit in RAM: it reads chunks, sorts each into a temp file and merges them. Every file ends with a 16-byte CodecUtil checksum footer.
  2. When reading an entry fails, the sorter calls verifyChecksum(error, reader). It re-opens that file, reads it to the end and checks the footer. The error then comes back with "checksum passed" attached, or, if the checksum is wrong, a "checksum failed" error comes back carrying it.

The finding, step by step

#
  1. You sort a file with OfflineSorter, directly or through a suggester build or hunspell's offline dictionary loading. In the repro the file is 18 bytes: an entry length of 100 with no bytes behind it, then the 16-byte checksum footer.
  2. Reading that entry fails with EOFException. The sorter then re-opens the file to check its checksum. Here the Directory refuses that second open (IOException: re-open failed), as it might on file-handle exhaustion or a deleted file.
  3. You expect sort() to throw the EOFException, with the outcome of the check attached. That is what you get when the re-open works: EOFException with a suppressed checksum passed (3e241443).
  4. Instead sort() throws only IOException: re-open failed, with no cause and no suppressed exception, with assertions on and off. The re-open sits in a try-with-resources header (OfflineSorter.java:378), so CodecUtil.checkFooter(in, priorException), the helper that would keep the EOFException, never runs.

Who is affected

#

Anyone whose sort hits a read failure (a truncated or damaged file, a read I/O error) and then cannot re-open the same file, on default settings, directly or through suggester builds and hunspell. Diagnostics only: the sort still fails and returns nothing, but the real cause is lost. A rare double failure: priority Low.

Mechanism, terms and numbers658 words

When OfflineSorter fails to read an entry of its input or of a temp partition, it calls verifyChecksum(t, reader), whose javadoc says it checks the file's checksum "and add[s] that information (checksum matched or didn't) as a suppressed exception" (OfflineSorter.java:372-375). The method re-opens the file in its try-with-resources header (:378) and only inside calls CodecUtil.checkFooter(in, priorException) (:379), the helper that keeps the prior exception on every path. When that re-open throws (file-handle exhaustion, a deleted file, a failing device or Directory), checkFooter never runs, nothing refers to the read failure again, and sort() runs its temp-file clean-up and rethrows only the open failure, with no cause and no suppressed exception (:366-368). The sort still fails and returns no output, so only diagnostics suffer, and it takes two failures in one sort: priority Low. It reaches the in-tree suggester builds and hunspell's offline sorting with default settings, has been there since verifyChecksum was added (LUCENE-7113, first released in 6.0.0) and is on main; opening the file outside the resource header and attaching an open failure to the read failure fixes it.

Step by step

#
  1. ByteSequencesReader.next() reads a 2-byte length, then that many bytes (:595-598), and stops at end = length - footerLength() (:578, :591). In the repro end is 18 - 16 = 2: the length says 100 and only the 16 footer bytes remain, so readBytes throws EOFException (:598).
  2. The catch at :462-463 passes it to verifyChecksum. All four read sites do this: readPartition (:444-448, :459-464) and MergePartitionsTask for the first and the next entry of each run (:709-714, :725-730), so input files and temp partitions are both covered.
  3. CodecUtil.checkFooter(in, priorException) is built to keep the prior exception. It adds "checksum passed" as a suppressed exception (CodecUtil.java:499-504), makes only evidence of corruption the primary exception, with the prior suppressed (:507-509; in general a read that already ran into the footer counts, :482-488, not this repro's case: the re-opened file starts at 0), and when the check hits an unexpected error it adds "checksum status indeterminate: unexpected exception" and rethrows the prior (:510-516). Its javadoc: it "will add a suppressed exception indicating whether the checksum for the stream passes, fails, or cannot be computed, and rethrow it" (:452-454).
  4. But the open sits in the resource header at :378, before checkFooter is reached. When openChecksumInput (which calls openInput, Directory.java:155-156) throws, that exception leaves verifyChecksum alone, and sort() runs its temp-file clean-up and rethrows it (:366-368).

Exposure and likelihood227 words
  • Who is hit. Anyone whose sort hits a read failure on its input or a temp partition and then cannot re-open that same file (file-handle exhaustion, the file deleted meanwhile, a failing device or Directory). Directly through OfflineSorter.sort, or through the in-tree callers with default settings: FSTCompletionLookup.build, SortedInputIterator (suggester builds), AnalyzingSuggester, and hunspell's Dictionary(Directory tempDir, ...) constructors, which sort offline.   • Default vs opt-in. Default: nothing has to be configured. Assertions on or off make no difference.
  • Effect. Diagnostics only. sort() still fails with an IOException and still runs its temp-file clean-up (:367), and no sorted output is returned.   • Scale. None needed: one entry.
  • Likelihood: rare. It takes two failures in one sort, each uncommon. They can be correlated (a failing device, a vanished file); the lost information matters most when they are independent, for example a damaged file plus file-handle exhaustion. Why it looks unintended

#
  • verifyChecksum's javadoc: it adds the checksum outcome to the failure it is given "as a suppressed exception".
  • Its helper, CodecUtil.checkFooter(in, priorException), keeps that failure on every path, even when the checksum "cannot be computed".
  • Robert Muir (LUCENE-7822, 2017): "just deliver original exceptions to the user"; since 8.6.0 checkFooter keeps the original, on top or suppressed.
The full argument296 words
  • The method's own purpose. verifyChecksum is "Called on exception, to check whether the checksum is also corrupt in this source, and add that information (checksum matched or didn't) as a suppressed exception" (OfflineSorter.java:372-375). Dropping the exception it was called with is the opposite.
  • The contract of the helper it calls. CodecUtil.checkFooter(in, priorException) keeps the prior exception on every path, including "cannot be computed" (CodecUtil.java:452-454, :485, :510-516). The re-open is the first step of that same check.
  • The design, in a committer's words, and how it settled. On LUCENE-7822 (#8873) Robert Muir wrote in 2017 that Lucene should "just deliver original exceptions to the user when things are wrong. Otherwise debugging becomes too hard." The issue was settled differently in 2020: Adrien Grand's #1482 (first released in 8.6.0) made checkFooter throw a CorruptIndexException on top when the checksum fails or cannot be verified, with the original as a suppressed exception; otherwise the original stays on top (lucene/CHANGES.txt:5757-5759, CodecUtil.java:482-488, :507-516). Either way the original is kept.
  • The change that added it. Mike McCandless's patch comment on LUCENE-7113 (#8168, 2016-03-18): "I also validate if we hit an unexpected exception, adding the corruption as a suppressed exception, like we do for index files". Its tests cover corrupt files, not a failing re-open.
  • The same class elsewhere. Since #14913 (2025) sort()'s failure path attaches clean-up failures to the primary exception (IOUtils.deleteFilesSuppressingExceptions(t, ...), :367). The sibling BKDWriter.verifyChecksum has avoided one cause of a doomed re-open since 2019 (a getCreatedFiles() check, BKDWriter.java:1556).
  • No decision to the contrary found. No javadoc, test, CHANGES or MIGRATE entry, issue or list thread accepts the loss. The existing TestOfflineSorter.testBitFlippedOnInput1/2 and testBitFlippedOnPartition1/2 check that checksum corruption is reported; none covers a failing re-open.
The devil's-advocate check177 words

The argument: OfflineSorter is @lucene.experimental and @lucene.internal (OfflineSorter.java:49-50); verifyChecksum is private, so its javadoc is an implementation comment; sort() and the suggester entry points promise only an IOException, and one is thrown; LUCENE-7113 calls the check "best-effort"; and the open failure is a real I/O error that may even be the root cause (a vanished file).

Why it fails: "best-effort" in LUCENE-7113 is about coverage ("the BKDWriter corruption checks are only best effort", because BKD does not always fully consume its temp files); the same comment says OfflineSorter "fully validates checksums for its input source, and all of its temporary sorted partitions". It is not about replacing the original failure. The helper's public contract keeps the original on every path (on top or suppressed), and the fix keeps the open failure too, attached to the read failure, so nothing is hidden either way. Two executed reviews by another model family (OpenAI GPT-5.6) rated this counter "moderate" and not holding; a devil's-advocate verifier judged it weak, and the adjudication found it does not hold up.

Suggested fix

#

Recommended A: open outside the resource header, keep the read failure, attach the open failure

Open the file outside the try-with-resources header. If the open throws, add it to the read failure as a suppressed exception and rethrow the read failure; otherwise try (in) { checkFooter(in, priorException) }. Validated: the repro passes with assertions on and off; TestOfflineSorter, all 236 suggest-module tests and :lucene:core:check -x test pass.

private void verifyChecksum(Throwable priorException, ByteSequencesReader reader)
    throws IOException {
  final ChecksumIndexInput in;
  try {
    in = dir.openChecksumInput(reader.name);
  } catch (Throwable t) {
    // keep the original failure; the re-open failure is extra information
    priorException.addSuppressed(t);
    throw IOUtils.rethrowAlways(priorException);
  }
  try (in) {
    CodecUtil.checkFooter(in, priorException);
  }
}

Downstream note

#

When the re-open fails too, products that log or classify the exception from a suggester build or a hunspell dictionary load see only the open error, not the read failure behind it.

How it was found

#

A proof-obligation audit of OfflineSorter's contract took verifyChecksum's documented job, keep the read failure and attach the checksum outcome, as an obligation on every path out of the method. The path where the re-open throws does not meet it. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full140 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: every exit from verifyChecksum(priorException, reader) rethrows priorException, or an exception that carries it, with the checksum outcome attached, as its javadoc and CodecUtil.checkFooter(in, priorException) promise. The exit through the resource acquisition at OfflineSorter.java:378 does not.
  • A one-test JUnit witnessed it on main with assertions on and off, and a probe printed the exception with and without the failing re-open. An independent reproducer, two executed reviews by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier each wrote their own test (a read I/O error instead of a truncated entry, a public suggester build, a NoSuchFileException on the re-open, from a package outside org.apache.lucene); an adjudication re-ran two of the tests, and the finder's test with the fix.

LFV-1248, snapshot of 2026-11-08

Registry title
OfflineSorter.verifyChecksum re-opens the file in its try-with-resources header, so when that re-open fails, the read failure it was called to annotate (an EOFException from a truncated entry, a read I/O error) is dropped and sort() throws only the unrelated open failure, with no cause and no suppressed exception (since 6.0.0)
Area
util / OfflineSorter (checksum check after a read failure; used by the suggesters and hunspell)
Priority
Low, rank 852: When an OfflineSorter sort (also used by suggester builds and hunspell dictionary loading) hits a read failure and then cannot re-open the file for its checksum check, the real cause is replaced by the unrelated open error, on default settings in every release since 6.0.0. The sort fails loudly either way and nothing wrong is written, so only diagnostics suffer, and the double failure is rare.
Impact class
minor
Impact note
Anyone whose OfflineSorter.sort hits a read failure on its input file or a temp partition (a truncated or damaged file, a read I/O error) and then cannot re-open that same file for the follow-up checksum check (file-handle exhaustion, the file deleted meanwhile, a failing device or Directory) is hit, directly or through the in-tree callers with default settings (suggester builds through FSTCompletionLookup, SortedInputIterator and AnalyzingSuggester; hunspell Dictionary constructors that take a temp Directory), with -ea and -da, in every release from 6.0.0 through 10.6.0 and on main. Diagnostics only: sort() still fails with an IOException and still deletes its temp files, and no wrong data is written or returned, but the exception it reports is the unrelated open failure, so the real cause is lost. No scale is needed; the double failure is rare.
Summary
You sort a file with OfflineSorter (directly, or through a suggester build or hunspell offline sorting), reading one of its entries fails (here a truncated entry gives EOFException), and the sorter's follow-up checksum check cannot re-open the same file (here the Directory's second openInput of that name throws IOException). You expect sort() to throw the read failure with the outcome of the checksum check attached, as verifyChecksum's own javadoc says and as CodecUtil.checkFooter(in, priorException) does on every path, even when the checksum cannot be computed. Instead sort() throws only the re-open IOException, with no cause and no suppressed exception, because the re-open sits in the try-with-resources header, before checkFooter ever receives the prior exception.
