FunctionScoreQuery and FunctionQuery score a function value of -0.0 as -0.0, so the top-1 hit is not the head of the top-2

FunctionScoreQuery and FunctionQuery should score a negative function value as 0, but their check value >= 0 lets -0.0 through. Since 10.2.0 the collector then ranks the two zeros inconsistently: with values -0.0 and 0.0, search(q, 1) returns doc 0 but search(q, 2) puts doc 1 first.

The finding in 30 seconds

#

Two zeros in Java

#
  1. Java floats and doubles have two zeros, +0.0 and -0.0. Ordinary comparisons treat them as equal: -0.0 == 0.0 and -0.0 >= 0 are true, -0.0 < 0 is false.
  2. Sign-aware comparisons do not: Float.compare(-0f, 0f) is -1, and the sortable bits that Lucene's hit heap stores put -0.0 just below +0.0.
  3. -0.0 comes from ordinary arithmetic and input: -1f * 0f, negating a stored 0, or Float.parseFloat("-0").

The finding, step by step

#
  1. Index two documents: doc 0 with FloatDocValuesField("f", -0f), doc 1 with FloatDocValuesField("f", 0f). Search new FunctionScoreQuery(MatchAllDocsQuery, DoubleValuesSource.fromFloatField("f")) with a plain IndexSearcher.
  2. You expect both to score 0, because a negative function value scores 0 (LUCENE-7996), and to tie in doc-id order: search(q, 1) = [doc 0] and search(q, 2) = [doc 0, doc 1].
  3. Instead doc 0 scores -0.0. The clamp tests factor >= 0 (in FunctionQuery: val >= 0 == false), and in Java -0.0 >= 0 is true. A value of -1.0 is clamped to +0.0 as intended.
  4. So search(q, 1) = [doc 0] but search(q, 2) = [doc 1 (0.0), doc 0 (-0.0)], assertions on or off. The collector's score <= topScore test sees two equal zeros and keeps doc 0, while its heap sorts -0.0 below 0.0. Paging can repeat or skip such hits.
  5. Lucene's own test framework rejects the score (AssertionError: -0.0 under newSearcher with assertions on, since 10.3.0). Only zero-scored hits move; matches, counts and positive scores are unchanged.

Who is affected

#

Applications that score with FunctionScoreQuery (including boostByValue) or FunctionQuery where a function value is exactly -0.0 and the score reaches the collector without being summed, e.g. at top level, under BoostQuery, next to MUST_NOT, or as a MUST clause where no SHOULD clause matches. Only zero-scored hits move. Tests on Lucene's test framework can fail with assertions on.

Mechanism, terms and numbers695 words

LUCENE-7996 (8.0.0) forbids negative scores and made FunctionScoreQuery and FunctionQuery score 0 when the function value is negative. Both clamps are ordinary comparisons (factor >= 0, val >= 0 == false; explain uses < 0), and in Java -0.0 >= 0 is true, so a function value of exactly -0.0 is returned as a score of -0.0f. Lucene's test framework rejects that score (Float.compare(score, 0f) >= 0), and since 10.2.0 the hit collector disagrees with itself about it: its competitiveness test score <= topScore treats -0.0 and +0.0 as equal while its heap orders -0.0 below +0.0. With doc 0 = -0.0 and doc 1 = +0.0, search(q, 1) returns doc 0 but search(q, 2) returns doc 1 first, and searchAfter or offset paging can skip or repeat zero-scored hits. With Sort.RELEVANCE the order is consistent, but from 8.0.0 on a -0.0 hit sorts after the +0.0 hits it should tie with. In every executed check only hits whose correct score is 0 are affected; match sets, counts and positive-scored hits are unchanged. Every release from 8.0.0 to 10.6.0 has the -0.0 score; a four-line fix makes the clamps sign-aware.

The clamps

#

LUCENE-7996: "Queries are now required to produce positive scores." and "FunctionQuery and FunctionScoreQuery now return a score of 0 when the function produces a negative value." (lucene/CHANGES.txt:6636, :6732-6733); MIGRATE: "FunctionScoreQuery maps negative values to 0." (lucene/MIGRATE.md:1368-1375).

  • FunctionScoreQuery.score (FunctionScoreQuery.java:244-251): if (factor >= 0) { return (float) (factor * boost); }, otherwise // default: missing value, negative value or NaN return 0;.
  • FunctionQuery.score (FunctionQuery.java:131-136): if (val >= 0 == false) { return 0; } else { return boost * val; }.
  • explain truncates only value < 0 (FunctionScoreQuery.java:191, FunctionQuery.java:146), so it reports -0.0 too.

A value of -0.0 passes each test, and -0.0 times a finite non-negative boost is -0.0. The sign survives whenever the function score reaches the collector without being summed: for example at top level, under BoostQuery, as the only clause of a BooleanQuery, next to MUST_NOT clauses only, as the MUST clause next to SHOULD clauses for documents that no SHOULD clause matches (ReqOptSumScorer.java:245 starts from the required score and adds the optional one only on a match, :254-256), or inside an outer FunctionScoreQuery that multiplies by the inner score (DoubleValuesSource.SCORES, boostByValue). Conjunction scorers and pure disjunctions sum into a double that starts at +0.0 (ConjunctionScorer.java:57-61, DisjunctionSumScorer.java:41-44), and 0.0 + -0.0 is +0.0, so a MUST + FILTER query or a SHOULD-only query loses the sign.

The collector

#

TopScoreDocCollector rejects a hit when score <= topScore (TopScoreDocCollector.java:113), reasoning that "a document with equal score to pqTop.score cannot compete since HitQueue favors documents with lower doc Ids" (:122-124); 0.0f <= -0.0f is true. Its heap (a TernaryLongHeap on main) stores NumericUtils.floatToSortableInt(score) (DocScoreEncoder.java:31-33), the order of Float.compare; HitQueue, the collector's heap in 10.2.x, orders with Float.compare too (HitQueue.java:76-82).

  • k = 1: doc 0 (-0.0) takes the single slot, topScore becomes -0.0, and doc 1 (0.0) is rejected by 0.0 <= -0.0. Result [doc 0].
  • k = 2: both documents get a slot, and the heap sorts doc 1 (0.0) above doc 0 (-0.0). Result [doc 1, doc 0].

searchAfter has the same split (score > afterScore || (score == afterScore && doc <= afterDoc), TopScoreDocCollector.java:103): with page size 2, values [-0.0, +0.0] page as [doc 1, doc 0], then [doc 1] again, and values [-0.0, +0.0, 0.5] page as [doc 2, doc 1] and never show doc 0. Paging with Sort.RELEVANCE is unaffected (RelevanceComparator uses Float.compare), but its order is not the intended one either: there a -0.0 hit sorts after every +0.0 hit in every release from 8.0.0, so on the repro's index search(q, 2, Sort.RELEVANCE) = [doc 1, doc 0] instead of [doc 0, doc 1].

Lucene's test framework asserts Float.compare(score, 0f) >= 0 (AssertingScorer.java:131), so searches through newSearcher that collect such a score throw AssertionError: -0.0 with assertions on (since 10.3.0).

Exposure and likelihood308 words
  • Trigger. A function value of exactly -0.0 that reaches the collector unchanged: a float or double field holding -0.0 (Float.parseFloat("-0") returns it), a negated zero, or zero times a negative factor (-1f * 0f), including boostByValue with a -0.0 factor. Default codec, IndexWriterConfig and searcher; the function query itself is an explicit choice from the queries module.
  • Effect. Only among hits whose correct score is 0. With Sort.RELEVANCE (every release from 8.0.0) a -0.0 hit consistently sorts after every +0.0 hit instead of tying with it in doc-id order. With score-sorted search (since 10.2.0) the result also depends on k: search(q, k) lists depend on k, searchAfter can skip a -0.0 hit for good while repeating +0.0 hits, and offset paging can show a -0.0 hit twice while never showing another zero-scored hit.
  • Scale (randomized probe, 300 small multi-segment indexes with deletions, three searcher kinds, top-level shape): 18,268 of 44,204 top-k comparisons returned a different set of hits (6,564 of them from its Sort.RELEVANCE searches) and 11,590 more a different order; every lost place was lost by a -0.0 document; 2,588 of 4,080 searchAfter runs and 1,500 of 4,080 offset-paging runs repeated or dropped a hit. The probe's value mix (3 of 11 values are -0.0) is not a real-world frequency.
  • Not affected: match sets, count(), totalHits, filters, deny rules, deleted documents, and every positive-scored hit.
  • Test suites that use newSearcher can get AssertionError: -0.0 with assertions on, since 10.3.0, in tests that collect such a score.
  • Downstream (read, not tested): in Apache Solr, edismax's boost parameter and {!boost} wrap the query in boostByValue, and {!func} builds a FunctionQuery.
  • How likely: rare. It needs an exact -0.0 that survives to the collector, and then a ranking or paging that depends on the order of zero-scored hits; the symptom is easy to miss.

Why it looks unintended

#
  • LUCENE-7996 says these queries "return a score of 0 when the function produces a negative value".
  • The same commit made the rule sign-aware elsewhere: AssertingScorer asserts Float.compare(score, 0f) >= 0, and new BoostQuery(q, -0f) must throw.
  • #16139 (10.6.0) mapped another -0.0 score to +0.0. And search(q, 1) disagreeing with search(q, 2) is wrong whatever -0.0 means.
The full argument206 words
  • The rule is documented: lucene/CHANGES.txt:6636 and :6732-6733, lucene/MIGRATE.md:1368-1375 ("Scorers are no longer allowed to produce negative scores ... FunctionScoreQuery maps negative values to 0."). The clamp's comment: "default: missing value, negative value or NaN" (FunctionScoreQuery.java:250).
  • Same commit, sign-aware: a8a63464e7d (LUCENE-7996) added the clamps, AssertingScorer's assert Float.compare(score, 0f) >= 0 (AssertingScorer.java:131) and BoostQuery's Float.compare(boost, 0f) < 0 (BoostQuery.java:40), with a test that requires new BoostQuery(q, -0f) to throw (TestBoostQuery.java:35-36).
  • Precedent: #16137 (open) reports a score from IBSimilarity/DistributionSPL that trips the test framework; the issue calls it negative, and a commenter (iprithv) found that it is -0.0; its fix #16139 (merged 2026-09-10, CHANGES under 10.6.0) uses Math.max(0.0, ...), which maps -0.0 to +0.0. The PR body says a negative score "breaks the contract that Lucene scores must be non-negative"; the approving review says it "is generally going to round -0.0 to 0.0".
  • The upstream test with -0.0: TestFunctionScoreQuery#testTruncateNegativeScores indexes -2 and passes; a verifier's copy with -0.0 fails at AssertingScorer.java:131 on main and 10.5.2 and passes with the fix.
  • The ranking is wrong under any reading: a top-1 hit that the top-2 ranks second contradicts the collector's own comment at TopScoreDocCollector.java:122-124.
The devil's-advocate check136 words

The strongest case for "intended": -0.0 is numerically zero and not < 0; the Scorable#score and FunctionScoreQuery javadocs state no sign rule; FunctionQuery is @lucene.experimental; AssertingScorable and the #16139 test assert only score >= 0, which -0.0 passes; and the 19 comments of LUCENE-7996 (#9044) never mention signed zero.

Why it fails: the author of the clamps wrote the rule sign-aware in the same commit (AssertingScorer, the BoostQuery(-0f) test), upstream treated a -0.0 score as a contract break in #16137/#16139, and the top-k and paging results are inconsistent whatever -0.0 means. Verifiers and the adjudication rejected the intended-behaviour case, and the cross-model reviews rated it weak. Expect the semantic question anyway: in #16137 romseygeek asked for discussion before clamping; here the clamp already exists and the fix only makes it sign-aware.

Suggested fix

#

Recommended Make the two clamps sign-aware (four lines, validated)

Make both clamps sign-aware: factor > 0 in FunctionScoreQuery.score, val > 0 == false in FunctionQuery.score, and Double.compare/Float.compare(..., 0) < 0 in the two explain methods (four lines). -0.0 then scores +0.0; NaN still maps to 0. It passes the repro, the finder's tests and the whole queries module.

// FunctionScoreQuery.score()
if (factor > 0) { // also maps -0.0 to +0.0
// FunctionScoreQuery.explain()
if (Double.compare(value, 0) < 0) { // negative values and -0.0 (NaN compares greater)
// FunctionQuery.score()
if (val > 0 == false) { // covers NaN, negative values and -0.0 (returned as +0.0)
// FunctionQuery.explain()
if (Float.compare(expl.getValue().floatValue(), 0f) < 0) { // negative values and -0.0

Make the two clamps sign-aware (four lines, validated) (recommended)

#

The change is +4/-4 lines in FunctionScoreQuery.java and FunctionQuery.java. A function value of -0.0 now takes the existing return 0 path, and explain its existing "truncated score" branch; Double.compare/Float.compare order NaN above 0, so NaN keeps its own branches. Every other value is unchanged.

if (factor > 0) { // also maps -0.0 to +0.0
// FunctionScoreQuery.explain()
if (Double.compare(value, 0) < 0) { // negative values and -0.0 (NaN compares greater)
// FunctionQuery.score()
if (val > 0 == false) { // covers NaN, negative values and -0.0 (returned as +0.0)
// FunctionQuery.explain()
if (Float.compare(expl.getValue().floatValue(), 0f) < 0) { // negative values and -0.0

Trade-offs

  • Same number of comparisons per document; no benchmark was run.
  • Covers FunctionScoreQuery with any DoubleValuesSource (including boostByValue) and FunctionQuery; not other -0.0 producers (a similarity, the PayloadScoreQuery sibling, custom scorers).

One signed-zero order in the collector (alternative or addition, not run)

#

Make TopScoreDocCollector's competitiveness test (:113) and searchAfter test (:103) use the heap's order (Float.compare or the encoded long), and TopDocs.merge's score comparison (TopDocs.java:114-120) likewise. Suggested by the adjudication, a verifier and the security screen.

Trade-offs

  • Covers every -0.0 producer for top-k and paging consistency.
  • Does not remove the -0.0 score, the -0.0 explanation or the test-framework failure.
  • Touches the collector's hot path, and the minimum-competitive-score step cannot tell the zeros apart (Math.nextUp(-0f) equals Math.nextUp(0f)), so with pruning active a +0.0 hit could still be skipped.

The same idiom in PayloadScoreQuery (complement, not verified)

#

PayloadScoreQuery.getPayloadScore clamps with if (score >= 0 == false) (PayloadScoreQuery.java:260, added for LUCENE-7996). A custom float PayloadDecoder returning -0.0 gives a -0.0 score there (one executed check; not verified as a separate bug). score > 0 == false would match the recommended fix.

Downstream note

#

Where end users can set a scored float field or a boost factor, a -0.0 value only demotes its own document among zero-scored hits and, with offset paging, can push another zero-scored hit off every page; matches, filters and counts are unaffected.

How it was found

#

A hunt on PriorityQueue and TopDocs.merge ran an exhaustive differential that showed -0.0 and 0.0 ordered differently by different code. The finder then asked whether a legal query can produce -0.0, found the >= 0 clamps by reading the LUCENE-7996 code, and confirmed them with a public-API JUnit on the stock build.

The method in full112 words

Method: non-formal (code reading guided by a differential test, confirmed by execution).

  • Signal. The unit's bounded-exhaustive TopDocs.merge differential had a signed-zero probe: merge and the collectors order -0.0f and 0.0f differently. Since -0.0 is outside the score contract, that is not a bug by itself.
  • Question. Can a legal query produce -0.0? Reading the LUCENE-7996 clamps found factor >= 0 and val >= 0 == false.
  • Confirmation. A public-API JUnit (two documents) failed 3/3 on main with assertions on and off; then an independent reproducer, a devil's-advocate verifier, cross-model reviews (OpenAI GPT-5.6) and an adjudication checked it, and a follow-up ran the version history, a prior-report search and a security probe.

LFV-273, snapshot of 2026-11-02

Registry title
FunctionScoreQuery and FunctionQuery score a function value of -0.0 as -0.0f instead of 0, because their LUCENE-7996 negative-value clamps test value >= 0; since 10.2.0 the top-1 hit can then differ from the first of the top-2 hits
Area
queries / function scoring (FunctionScoreQuery and FunctionQuery negative-value clamps, LUCENE-7996; visible through core TopScoreDocCollector tie handling)
Priority
Low, rank 671: A -0.0 function value gives k-dependent ranking and paging skips, the same tie-order problem as LFV-272, but it needs an exact -0.0 to reach the collector, so it is rarer and follows it.
Impact class
minor
Impact note
Applications that score with FunctionScoreQuery (including boostByValue) or FunctionQuery where a document's function value is exactly -0.0 (a float or double doc value of -0.0, a negated zero, zero times a negative factor) get a score of -0.0f for that hit instead of 0; only hits whose correct score is 0 are affected: since 10.2.0 their order depends on k (search(q, 1) is not the head of search(q, 2)), searchAfter paging can skip such a hit on every page and offset paging can show it twice while never showing another zero-scored hit (follow-up security probe), and test suites built on Lucene's test framework fail with 'AssertionError: -0.0' under -ea; match sets, counts, positive-scored hits and the index are unaffected; default IndexWriterConfig, codec and searcher, two documents, -ea or -da; released since 8.0.0.
Summary
You index doc 0 with FloatDocValuesField("f", -0f) and doc 1 with FloatDocValuesField("f", 0f) and search new FunctionScoreQuery(new TermQuery(k:x), DoubleValuesSource.fromFloatField("f")) or new FunctionQuery(new FloatFieldSource("f")), expecting doc 0 to score 0 like any negative function value since LUCENE-7996 ('Scorers are no longer allowed to produce negative scores'; the test framework's AssertingScorer checks Float.compare(score, 0f) >= 0) and the two zero-scored hits to tie in doc-id order. Instead doc 0 scores -0.0f, because the clamps test 'factor >= 0' (FunctionScoreQuery) and 'val >= 0 == false' (FunctionQuery) and -0.0 >= 0 is true in Java; explain() does not truncate it either. Since 10.2.0, search(q, 1) returns doc 0 while search(q, 2) returns [doc 1, doc 0], because TopScoreDocCollector's 'score <= topScore' test treats the two zeros as equal while its heap and HitQueue order -0.0 below 0.0.
