FloatVectorSimilarityQuery returns at most one hit per segment written by Lucene 9.0.0

On a segment written by Lucene 9.0.0, FloatVectorSimilarityQuery returns at most one document however many pass the threshold: 1 instead of 2 in the repro, 1 of 51 on a 20,000-document segment. It affects 9.10.0 through 10.6.0 and main.

The finding in 30 seconds

#

The 9.0 reader asks the collector how many results it wants, gets 1, and hands over a single vector.

Threshold queries and old segments, in one minute

#
  1. FloatVectorSimilarityQuery finds all (approximate) vectors above a similarity threshold. It walks the HNSW graph with a VectorSimilarityCollector, which keeps every visited vector above the threshold and tells the reader how far to keep searching through minCompetitiveSimilarity().
  2. That collector is not a top-k collector. Its k() is 1, and its javadoc says k() "does NOT provide a good estimate of the number of collected results".
  3. Current Lucene opens indexes created with 9.x. A segment written by Lucene 9.0.0 is read by the backward-codecs Lucene90HnswVectorsReader, which has its own older graph search with a fixed-size result queue.

The finding, step by step

#
  1. With the Lucene 9.0.0 jars, index three documents with EUCLIDEAN vectors [1, 0], [1, 0.1] and [0, 1]. Open the index on current Lucene, which still supports 9.x indexes.
  2. Count FloatVectorSimilarityQuery.Adaptive("v", [1, 0], 0.5): every document whose vector has similarity 0.5 or more to [1, 0] (default decay 0.5, no filter).
  3. You expect 2: the similarities are 1.0, 0.990 and 0.333. The same documents written by 9.1.0 count 2, and so does decay 1, which searches exactly.
  4. Instead the count is 1. The query's collector reports k() = 1 because it is not a top-k collector. The 9.0 reader sizes its own graph search by k(), returns one vector, and the query takes that as the whole answer.
  5. No error, and raising decay does not help (decay 0 to 0.999 all give 1 on the repro). On a 20,000-document 9.0.0 segment the query found 1 of 51 matches for each of 4 query vectors.

Who is affected

#

Indexes that still hold an unmerged segment written by Lucene 9.0.0, searched with an unfiltered FloatVectorSimilarityQuery: at decay below 1 (the default 0.5) from 10.5.0, and every such query on 9.10.0-10.4.0, which have no decay. Each query keeps at most one hit per such segment, silently. Rare: a maintainer thought there are probably none in the wild.

Mechanism, terms and numbers569 words

Current Lucene still reads segments written by Lucene 9.0.0 through the backward-codecs Lucene90HnswVectorsReader. On such a segment, an unfiltered FloatVectorSimilarityQuery with decay below 1 (the default is 0.5) returns at most one document, however many vectors are above the threshold (on 9.10.0-10.4.0, which have no decay, every unfiltered query does). The query collects with VectorSimilarityCollector, whose k() is 1 because it is not a top-k collector: newer readers keep walking the graph while candidates beat its minCompetitiveSimilarity(). The 9.0 reader instead runs its own fixed-size graph search sized by k(), returns one vector, and the query takes that vector as the complete result. There is no error, and raising decay does not help: on the repro decay 0 to 0.999 all return one hit, and by code a decay below 1 only moves minCompetitiveSimilarity(), which the 9.0 reader never reads. Decay 1 (the exact path), plain KnnFloatVectorQuery and segments written by 9.1.0 or later are not affected. It is in all 20 releases from 9.10.0 to 10.6.0 and on main, and needs an unmerged 9.0.0 vector segment, which a maintainer called probably rare.

The code (main f794ff5a505c)

The numbers

#

EUCLIDEAN similarity is 1 / (1 + squared distance). For the query [1, 0] the three documents score 1.0, 0.990099 and 0.333333, so two are at or above 0.5. On the 9.0.0-written index the count is 1; the same documents written by 9.1.0 count 2. On a 20,000-document 9.0.0 segment the query returned 1 of the 51 documents above its threshold, for each of 4 query vectors; segments written by 9.1.0, 9.2.0, 9.4.2 and 9.12.3 returned 51 of 51. On upstream's own fixture index.9.0.0-cfs.zip (5 segments) a threshold at the 10th-best exact similarity returns 2 hits instead of 10; index.9.1.0-cfs.zip and index.9.2.0-cfs.zip return 10 of 10.

Same lines, second symptom (side remark)

#

A parent-join kNN query (DiversifyingChildrenFloatKnnVectorQuery) with k = 2 parents returns 1 parent on a 9.0.0-written index when the 2 nearest children share a parent, from 9.8.0 on; a 9.1.0-written control returns 2. It is weaker on its own (kNN may return fewer than k), so it is not a separate claim.

Exposure and likelihood264 words
  • Who is hit. Applications whose index still holds an unmerged segment written by Lucene 9.0.0 (the only 9.0.x release, 2021-12) with KNN vectors, and that run FloatVectorSimilarityQuery without a filter: on 10.5.0 and later at decay below 1 (the constructors without a decay argument use 0.5; the deprecated Explicit form of 10.5.2 and 10.6.0 uses decay 0 and is hit too, executed on 10.6.0), and on 9.10.0-10.4.0, which have no decay, every unfiltered query (executed on 9.10.0 and 10.4.0). Each such query keeps at most one hit from each such segment, whatever the query vector or threshold, with assertions on and off.
  • Silent. No exception and no flag. The decay knob, documented as giving "better recall using more graph exploration" at higher values, does not help on these segments: on the repro decay 0, 0.5, 0.9, 0.99 and 0.999 all return 1 of 2, and only decay 1 (the exact path, which never calls the reader) returns 2. By code, a decay below 1 only moves minCompetitiveSimilarity(), which the 9.0 reader never reads.
  • Not affected. Segments written by 9.1.0 or later; decay 1; plain KnnFloatVectorQuery. Byte vectors did not exist in 9.0, so ByteVectorSimilarityQuery cannot reach this reader. The filtered path may be affected by code reading (when the approximate search finishes within its visit limit); it was not executed and is not claimed.
  • How likely. Rare. In #13910 (2024), about another defect in this same method, msokolov wrote: "Probably there are none in the wild, and this was never noticed?" The searches (see Prior reports) found no report of this one.

Why it looks unintended

#
  • Javadoc: "Search for all (approximate) float vectors above a similarity threshold"; the introducing commit says such queries are "not limited by topK".
  • The collector's javadoc: k() "does NOT provide a good estimate of the number of collected results"; the 9.0 reader uses it as one.
  • 9.x indexes are fully supported, and #13910 fixed another wrong-results bug in this method.
The full argument180 words
  • Contract. FloatVectorSimilarityQuery: "Search for all (approximate) float vectors above a similarity threshold." (FloatVectorSimilarityQuery.java:31-35). The 9.10.0 CHANGES entry for #12679 says the collector finds "all vectors scoring above a resultSimilarity". The introducing commit lists as its first advantage: "Queries that have a high number of "relevant" results will get all of those (not limited by topK)".
  • The collector says k() is not a result count (VectorSimilarityCollector.java:34-39, wording added by #15784, released in 10.5.0).
  • 9.x indexes are fully supported. Version.MIN_SUPPORTED_MAJOR = 9 (Version.java:305); MIGRATE.md: indexes created with 9.x "remain fully supported (open and write)" and "all the built-in codecs provide full support" (lucene/MIGRATE.md:242, :244). TestBasicBackwardsCompatibility runs KnnFloatVectorQuery on the 9.0.0 fixtures.
  • Precedent. #13910 fixed another wrong-results defect in this same method (vector ordinals returned as doc ids) as a back-compat bug, although its author thought such indexes rare.
  • No test or document asserts the one-hit result, and no upstream test runs a similarity query on a 9.0 segment. The newer readers returned every expected hit for the same documents.
The devil's-advocate check176 words

"The reader honours its contract." KnnVectorsReader.search is documented as "Return the k nearest neighbor documents" (KnnVectorsReader.java:97) and KnnCollector.k() as "the expected number of collected results" (KnnCollector.java:57). The threshold collector reports k = 1, says it deviates from KnnCollector, and should be used only by queries "aware of the differences"; the query and the collector are @lucene.experimental, and 9.0 indexes are rare.

Why it fails: the deviation and the reliance on it are both inside Lucene. A user who calls the public Adaptive(field, target, resultSimilarity) constructor on a supported index chooses neither the collector nor the reader. The newer readers returned every expected hit on the same documents and on the other fixtures, and none of them caps the result at one; the 9.0 reader's ceiling of one is structural (a queue of k() = 1), not a recall trade-off that decay could tune. Which side is at fault only decides where the fix goes. Both executed reviews by another model family (OpenAI GPT-5.6) rated this defence moderate and rejected it.

Suggested fix

#

Recommended A: repeat the 9.0 search at twice the size while the collector still wants worse results

Fix A, in Lucene90HnswVectorsReader.search: keep the k-sized search, and while the collector still accepts results worse than the worst one returned, search again at twice the size, collecting each node once. Validated: the repro fails stock and passes with the fix, assertions on and off; the lucene90 and back-compat tests and :lucene:backward-codecs:check pass.

A: repeat the 9.0 search at twice the size while the collector still wants worse results (validated by the checks) (recommended)

#

In Lucene90HnswVectorsReader.search, after collecting, stop if the search was incomplete, the collector terminated early, the search already covered the whole field, or the worst returned score is at or below knnCollector.minCompetitiveSimilarity(); otherwise double topK and search again, skipping nodes already collected (a FixedBitSet). +40/-19 lines, one file, google-java-format clean.

FixedBitSet collected = new FixedBitSet(fieldEntry.size());
int topK = knnCollector.k();
while (true) {
  final SplittableRandom random = new SplittableRandom(checksumSeed);
  NeighborQueue results = Lucene90OnHeapHnswGraph.search(target, topK, topK, vectorValues,
      fieldEntry.similarityFunction, getGraphValues(fieldEntry),
      getAcceptOrds(acceptDocs.bits(), fieldEntry),
      knnCollector.visitLimit() - knnCollector.visitedCount(), random);
  knnCollector.incVisitedCount(results.visitedCount());
  float worst = results.size() > 0 ? results.topScore() : Float.POSITIVE_INFINITY;
  boolean incomplete = results.incomplete();
  while (results.size() > 0) {
    int node = results.topNode();
    float minSimilarity = results.topScore();
    results.pop();
    if (collected.getAndSet(node) == false) {
      knnCollector.collect(vectorValues.ordToDoc(node), minSimilarity);
    }
  }
  if (incomplete || knnCollector.earlyTerminated() || topK >= fieldEntry.size()
      || worst <= knnCollector.minCompetitiveSimilarity()) {
    return;
  }
  topK = (int) Math.min(fieldEntry.size(), 2L * topK);
}

Trade-offs

  • A full top-k collector stops after the first round (its bound is the k-th score, which is the worst returned), so plain kNN is unchanged, except when fewer than k accepted vectors are found (for example under a tight filter), where the search now widens.
  • The threshold collector's bound starts at the lowest float, and each below-threshold vector moves it toward that vector's score. From that start it stays below -1, so below every EUCLIDEAN similarity, until about 128 below-threshold vectors have been collected at decay 0.5 (about 840 at 0.9, about 8,800 at 0.99; computed with the collector's float update). Until then the bound cannot end the rounds, so on segments with fewer vectors than that they run until the whole field is covered.
  • Each round repeats the traversal with a doubled queue; the cost was not measured. The visit budget is passed down as what remains of it. A maintainer should review the cost and the visit accounting.
  • It also fixes the parent-join side remark (the parent-join probe returns 2 parents with it).

B: score the rest exactly when the collector still wants more

#

After the k-sized search, if the worst returned score is above minCompetitiveSimilarity(), score every remaining accepted vector of the field and collect it.

Trade-offs

Simpler to reason about and exact. Costs one pass over the field per query on each 9.0 segment (like the decay-1 path), and also changes filtered top-k on 9.0 segments when fewer than k are found. Not run.

C: a guard in AbstractVectorSimilarityQuery (not recommended)

#

Make the query fall back to exact search on such segments.

Trade-offs

The query cannot see which reader serves a segment, so it would need a format check; the defect is in the reader. A one-line probe that sizes the 9.0 search as max(k, field size) also turns the repro green, but makes every query on a 9.0 segment, plain kNN included, traverse with a queue as large as the field; it is a root-cause check only.

Downstream note

#

A product that relies on similarity-threshold completeness, for example near-duplicate matching, misses matches on segments written by 9.0.0.

How it was found

#

A semi-formal writer oracle. Segments of 20,000 documents were written by the 9.0.0, 9.1.0, 9.2.0, 9.4.2 and 9.12.3 release jars, read on main, and checked against a side file of the vectors the writer stored. The threshold-completeness check returned 1 of 51 matches, only on the 9.0.0 segment; code reading found the cause, and a patched reader confirmed it.

The method in full124 words

Method: semi-formal (a writer oracle over old-format segments), on main f794ff5a505c, 2026-11-09.

  • Oracle. Each fixture is one 20,000-document segment written by a release jar, plus a side file with every vector the writer stored. On main, a FloatVectorSimilarityQuery.Adaptive whose threshold is the 51st-best exact similarity must return the 51 documents at or above it.
  • Signal. The 9.0.0 segment returned 1 of 51 for each of 4 query vectors; the 9.1.0, 9.2.0, 9.4.2 and 9.12.3 segments returned 51 of 51. Every other check on the 9.0.0 segment, kNN with k = 1, 10, 100 and filtered kNN included, was clean.
  • Cause and confirmation. Reading Lucene90HnswVectorsReader.search showed the k()-sized search; a patched reader (fix A) made the check and the minimal test pass.

LFV-1432, snapshot of 2026-11-10

Registry title
On segments written by Lucene 9.0.0, FloatVectorSimilarityQuery returns at most one hit per segment: Lucene90HnswVectorsReader.search sizes its graph search by knnCollector.k(), which is 1 for the similarity-threshold collector (VectorSimilarityCollector); since 9.10.0
Area
backward-codecs / Lucene90 HNSW vectors reader x search / vector similarity-threshold queries
Priority
Low, rank 389: In every release from 9.10.0 through 10.6.0 and on main, an unfiltered similarity-threshold vector query at decay below 1 (the default included) silently returns at most one hit from each segment written by Lucene 9.0.0, whatever the query or threshold. It is Low because it needs an unmerged segment from that single 2021 release, which a maintainer guessed may no longer exist in the wild, together with the experimental similarity-threshold query.
Impact class
minor
Impact note
Applications on Lucene 9.10.0 or later (through 10.6.0 and main) whose index still holds an unmerged segment written by Lucene 9.0.0 (the Lucene90 vector format; 9.1.0 and later write newer formats) silently get at most one hit from each such segment for every unfiltered FloatVectorSimilarityQuery at decay below 1 (the default 0.5 included), whatever the query vector or threshold, with -ea and -da [exec]; decay 1 (the exact path), plain KnnFloatVectorQuery and segments written by 9.1.0 or later are not affected [exec]; a maintainer remarked in #13910 that such 9.0 indexes are probably rare in the wild.
Summary
You open, on current Lucene, an index whose segment was written by Lucene 9.0.0 (three documents with EUCLIDEAN vectors [1, 0], [1, 0.1] and [0, 1]) and count FloatVectorSimilarityQuery.Adaptive("v", [1, 0], 0.5). You expect 2, the two documents with similarity 1.0 and 0.990099, which the same query returns on segments written by 9.1.0 or later and with decay 1 (the exact path). Instead the count is 1: the 9.0 reader runs its own graph search sized by the collector's k(), which is 1 for the similarity-threshold collector, so it hands over a single vector, and the query takes that as the complete result.
