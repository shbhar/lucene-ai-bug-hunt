Automaton.Builder.addEpsilon(s, s) never returns and exhausts the heap once state s has a transition

Read as documented, Automaton.Builder.addEpsilon(s, s) should change nothing, but once state s has an arc it never returns: each copy it appends is again an arc leaving s, which the loop copies too, until OutOfMemoryError. Only code that builds automata with the experimental Builder hits it, in releases 4.10.3 to 10.6.0 and main.

The finding in 30 seconds

#

Background: how Automaton.Builder records arcs, and what addEpsilon does

#
  1. Automaton.Builder lets you add arcs in any order; finish() sorts them into an Automaton. It stores each arc as four ints, (source, dest, min label, max label), in one growing int[]; nextTransition marks the end of the used part, and addTransition writes four ints there and moves it by 4.
  2. An epsilon arc from source to dest means "from source you may also do whatever dest does next". Builder.addEpsilon(source, dest) builds it without a real epsilon: it scans the array and, for every arc that leaves dest, appends a copy that leaves source.

The finding, step by step

#
  1. Build a one-state automaton with Automaton.Builder: state 0 accepts and has one arc 0 -a-> 0, so it accepts "", "a", "aa" and so on.
  2. Call addEpsilon(0, 0). It copies every arc that leaves state 0 onto state 0, so you expect it to return at once (at most adding a duplicate arc) and finish() to still accept "aaa". The sibling Automaton.addEpsilon(0, 0) does return on the state being built.
  3. Instead it never returns. With a 512 MB heap the test dies with OutOfMemoryError: Java heap space after about 1 s; a probe that counts copies stopped it at 1,000,000 copies, with 4,000,004 ints of arcs recorded.
  4. Why: the loop runs while upto < nextTransition and re-reads that bound on every pass. Copying arc 1 appends arc 2, which also leaves state 0; copying arc 2 appends arc 3, and so on, so the scan never reaches the end. With two different states the copies never match, which is why Lucene's own callers are fine.

Who is affected

#

Application code that builds automata with the experimental Automaton.Builder and calls addEpsilon(s, s) after s has an arc, for example a hand-written Kleene star addEpsilon(f, start) for every accept state f when the start state also accepts. No Lucene query, regex, analyzer or suggester path passes the same state twice. All releases from 4.10.3 to 10.6.0.

Mechanism, terms and numbers552 words

Automaton.Builder.addEpsilon(source, dest) documents: "Add a [virtual] epsilon transition between source and dest. Dest state must already have all transitions added because this method simply copies those same transitions over to source." (Automaton.java:805-808 at 5adff78bb168). It scans the builder's transition list and appends a copy of every transition that leaves dest (:809-815), but its loop bound upto < nextTransition (:810) is re-read on every pass while each append advances nextTransition (:795-803). With source == dest every appended copy again leaves dest, the scan reaches it and appends another, and the loop never ends: a one-state builder with the arc s -a-> s and a call addEpsilon(s, s) ends in OutOfMemoryError: Java heap space with a 512 MB heap, assertions on and off. Read as documented, an epsilon from a state to itself changes nothing, and the sibling Automaton.addEpsilon, whose javadoc is word for word the same, returns on the same call on the state being built because it reads its count once (:185-199). No Lucene caller passes source == dest; application code that builds its own automata with the experimental Builder does, for example a hand-written Kleene star when the start state accepts. The loop has been there since the method was added in 2014 (LUCENE-5963); releases 4.10.3 through 10.6.0 and main are affected (every inspected release tag from 4.10.3 on carries the loop line, and 12 releases were executed). Reading the bound once fixes it.

The bug

#
  1. addEpsilon(source, dest) loops for (int upto = 0; upto < nextTransition; upto += 4) (Automaton.java:810, the fix site). For each record with transitions[upto] == dest (:811) it calls addTransition(source, dest', min, max) (:812-813), which grows the array if needed (ArrayUtil.grow, :796-797), writes the record and advances nextTransition by 4 (:799-802).
  2. The bound is read again on every pass. With source == dest, each appended record starts at dest again, so the scan reaches it and appends another one.
  3. With one record (0, 0, 'a', 'a'): at upto = 0 the record matches and a copy goes to index 4 (nextTransition 4 -> 8); at upto = 4 the copy matches and another goes to index 8 (8 -> 12); and so on. The scan stays one record behind the end forever. The first growth of the default 64-int array happens at the 16th copy (64 -> 76 ints); after 1,000,000 copies nextTransition is 4,000,004 and the array has grown 91 times.
  4. ArrayUtil.grow keeps enlarging the array until OutOfMemoryError: Java heap space (ArrayUtil.java:319). By reading, only a heap that holds an int[] of ArrayUtil.MAX_ARRAY_LENGTH (about 8 GiB) and, during that last copy, the previous array too (about 15 GiB or more in total) would get as far as ArrayUtil.oversize's IllegalArgumentException (ArrayUtil.java:145-151); that was not run.

The arc does not have to be a self-loop: any arc that leaves s does it (an independent test with s0 -x-> s1 and addEpsilon(s0, s0) fails the same way). A state without arcs is fine: addEpsilon(s, s) then makes no copy and returns. With source != dest the copies start at source, never match dest, and the loop ends at the old end of the list.

Exposure and likelihood235 words
  • Who. Direct users of Automaton.Builder; the Automaton class is @lucene.experimental (Automaton.java:43). One natural way to get there: a Kleene star written as "copy a, then addEpsilon(f, start) for every accept state f". When a's start state also accepts, one of those calls is addEpsilon(start, start). A counting probe shows it: the star of "b" returns after 1 copy; the star of "b?", whose start state accepts, hits the 1,000,000-copy cap.
  • Effect. The call never returns and allocates until the JVM throws OutOfMemoryError: Java heap space, which can also hit other threads of the same JVM. No wrong automaton is ever returned. No scale is needed: one state and one arc.
  • Not affected. The only non-test callers of Builder.addEpsilon never pass source == dest: Operations.repeat(a, min, max) links earlier accept states to the start of a freshly copied a (Operations.java:313-319), and AnalyzingSuggester.replaceSep walks an acyclic token automaton in topological order (AnalyzingSuggester.java:271-302). ConcatenateGraphFilter and the other Operations and Automata sites use the non-Builder Automaton.addEpsilon. Lucene's own Kleene star, Operations.repeat(a), avoids the shape: it returns early when state 0 is the only accept state (Operations.java:207-209) and skips states merged into the start (if (stateMap[s] != 0), :255).
  • Likelihood: rare. No matching public report was found in the recorded searches, but whoever makes the call hangs every time.

Why it looks unintended

#
  • The only documented precondition, that dest already has all its arcs, holds when source == dest; nothing excludes the case.
  • The sibling Automaton.addEpsilon, with the same javadoc word for word, reads its count once and returns.
  • A self epsilon changes nothing; one state with one arc is not an absurd input.
The full argument244 words
  • Contract. Builder.addEpsilon: "Add a [virtual] epsilon transition between source and dest. Dest state must already have all transitions added because this method simply copies those same transitions over to source." (Automaton.java:805-808). The precondition holds for source == dest. Nothing in the javadoc, package docs, tests, CHANGES.txt, MIGRATE.md or the commit history excludes the case. Nor does anything promise that a self call is supported: the case rests on the natural reading of the documented copy, which is well defined and finite for source == dest.
  • The class is meant for this kind of construction. The Builder javadoc: "Use this when you cannot create the Automaton directly because it's too restrictive to have to add all transitions leaving each state at once." (:761-765).
  • The sibling handles it. Automaton.addEpsilon (:185-199) has the same javadoc but reads its count once (int count = initTransition(dest, t);, :191). A self call there returns on the state being built, or throws a clean IllegalStateException ("from state (0) already had transitions added") once the state is finished.
  • History. The method came with LUCENE-5963 (#7025, 2014), written for one caller, AnalyzingSuggester.replaceSep, where source and dest always differ. The only later change is the 2020 reformat. The issue thread never discusses a self epsilon or the loop bound, and no upstream test calls Builder.addEpsilon at all (the test callers, TestOperations.java:608 and the test framework's AutomatonTestUtil.java:391, use Automaton.addEpsilon).
The devil's-advocate check230 words

The strongest case for "intended". Automaton is @lucene.experimental; Builder.addEpsilon is a minimal helper added for one caller; an epsilon from a state to itself is pointless; a copy into itself is the classic aliasing case other APIs leave undefined (java.util.List.addAll leaves the behaviour undefined if the argument is modified during the call, which it notes happens when the argument is this list and it is nonempty); "Dest state must already have all transitions added" can be read as "no arcs are added to dest afterwards", which the self call itself breaks; and the failure is loud.

Why it fails. @lucene.experimental marks API instability, not permission to hang. Unlike List.addAll, this javadoc states no aliasing exclusion, and its documented effect (copy dest's arcs to source) is well defined and finite for source == dest. The precondition is about dest's arcs before the copy, and they are all there. The sibling with the same contract handles the call. And the call arises in ordinary NFA code, such as a Kleene star whose start state accepts, with one state and one arc. That is a fair argument for Low priority and for accepting a documentation-only fix (option C), not evidence that the hang is intended. The independent reproducer, the cross-model review lenses (OpenAI GPT-5.6, "intended argument weak"), the devil's-advocate verifier and the adjudication all rejected it.

Suggested fix

#

Recommended Read the loop bound once (fix A)

Read the loop bound once (final int end = nextTransition;, then loop to end), as the sibling Automaton.addEpsilon does. Nothing changes when source and dest differ; for a self epsilon finish() merges the duplicates (one per arc of the state). The repro passes with assertions on and off, and core's util.automaton tests (239) and suggest's analyzing tests (89) pass.

    public void addEpsilon(int source, int dest) {
      // read the bound once: with source == dest the copies appended below also leave dest
      final int end = nextTransition;
      for (int upto = 0; upto < end; upto += 4) {
        if (transitions[upto] == dest) {
          addTransition(
              source, transitions[upto + 1], transitions[upto + 2], transitions[upto + 3]);
        }
      }
      if (isAccept(dest)) {
        setAccept(source, true);
      }
    }
All options and trade-offs3 options · 600 words

Fix A was built and checked through gradle in a scratch worktree at 5adff78bb168; B and C were not run. A maintainer may prefer B (an exact early return, no duplicate arc) or C (a javadoc line); A matches the sibling method and is a small change (one local for the bound, and the loop condition). The fix applies to the 10.x source unchanged: the loop line is identical in all 101 release tags of the history clone from 4.10.3 on.

Read the loop bound once (fix A) (validated by the checks) (recommended)

#

In Automaton.Builder.addEpsilon (Automaton.java:809-819), snapshot nextTransition before the loop and loop to the snapshot.

    public void addEpsilon(int source, int dest) {
      // read the bound once: with source == dest the copies appended below also leave dest
      final int end = nextTransition;
      for (int upto = 0; upto < end; upto += 4) {
        if (transitions[upto] == dest) {
          addTransition(
              source, transitions[upto + 1], transitions[upto + 2], transitions[upto + 3]);
        }
      }
      if (isAccept(dest)) {
        setAccept(source, true);
      }

Trade-offs

A changed loop condition plus one local (and a comment). For source != dest the old loop already stopped at the same place, since records appended there never match dest. For source == dest it appends one duplicate of each arc of dest; finish() merges it, because finishCurrentState combines transitions with the same dest and overlapping labels (Automaton.java:247-295); with the fix the probe's finished state has 1 transition and accepts "aaa". So A is not a pure no-op inside the builder: until finish(), a self call on a state with k arcs holds k extra records, which finish() sorts and merges.

Return early when source == dest (fix B)

#

Add if (source == dest) return; at the top of Builder.addEpsilon.

Trade-offs

Exact for the resulting automaton: an epsilon from a state to itself changes neither the arcs nor the accept bit, and no duplicate arc is added. It covers only the self case, which is the only case the re-read bound can break, and leaves the loop as it is. One observable difference: Builder is not final and addTransition is public (Automaton.java:766, :795), so a subclass that overrides addTransition sees no call for a self epsilon under B, while A keeps one call per original arc, as documented. Not run.

Document that source and dest must differ (fix C)

#

Add "source and dest must be different states" to the javadoc, optionally with an IllegalArgumentException.

Trade-offs

Cheapest, but keeps a hang (or turns it into an exception) for a call whose documented effect is well defined and which the sibling method handles. Not run.

Downstream note

#

Downstream products that build their own epsilon-NFAs with Automaton.Builder inside a shared server JVM would see one such call exhaust the heap of that JVM; query, regex, analysis and index input cannot reach it.

How it was found

#

A proof-obligation audit of Automaton.Builder's contract: addEpsilon must copy dest's arcs to source and return for every pair of states that meets its one precondition. The obligation fails for source == dest, because the loop bound grows with the copies; a public-API JUnit test then witnessed the hang.

The method in full106 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked Builder.addEpsilon against its javadoc for every pair of states that meets its one precondition. Termination needs the loop bound to be fixed, but addTransition advances it, and for source == dest every appended record matches again.
  • The finder then wrote a public-API JUnit test, a probe that counts addTransition calls, and the bound-once fix that makes both pass.
  • An independent reproducer, an executed cross-model review with a refute and an intended-behaviour lens, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

Summary
You build an automaton with Automaton.Builder, give a state s one accepting self-loop arc (s -a-> s), and call addEpsilon(s, s). You expect it to return at once: its javadoc says it copies dest's arcs over to source, an epsilon from a state to itself adds nothing, and the sibling Automaton.addEpsilon returns on the same call. Instead the call never returns: its loop re-reads the growing transition count, every copy it appends again leaves s and is copied again, and it runs until OutOfMemoryError: Java heap space.
