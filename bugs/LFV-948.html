The Lucene 10.6.0 release notes say StableTflSimilarity also supports k3, but 10.6.0 has no k3

The 10.6.0 release notes say the new StableTflSimilarity "also supports k3 query-term frequency saturation", but the 10.6.0 class has no k3: new StableTflSimilarity(1.2f, 0.917f, 7f) does not compile. The 10.6 backport had left k3 out and dropped this sentence on purpose; a later, unrelated backport put the sentence back.

The finding in 30 seconds

#

One sentence in the 10.6.0 release notes describes code that is only on main.

Background: k3 and the release notes

#
  1. k3 is a BM25-style knob for queries that repeat a word: with k3 set, a term that appears n times in the query weighs ((k3 + 1) * n) / (k3 + n) instead of n. With k3 = 7 and n = 2 that is 16/9 = 1.78 instead of 2. On main, BooleanQuery applies this weight only when it merges unboosted duplicate SHOULD clauses (with minimumShouldMatch <= 1) or MUST clauses, as for the query a a; boosted duplicates keep their linear sum (BooleanQuery.java:438-454, 740-746).
  2. lucene/CHANGES.txt has one section per release. Main keeps a copy of each stable release's section, and the two copies are meant to match each other and what was actually backported to that release.

The finding, step by step

#
  1. You read the Lucene 10.6.0 release notes. The entry for the new StableTflSimilarity (GITHUB#16243) ends: "It also supports k3 query-term frequency saturation." k3 caps how much a word repeated in a query counts.
  2. You write new StableTflSimilarity(1.2f, 0.917f, 7f) (the default k1 and c, plus k3 = 7) against lucene-core 10.6.0. You expect it to compile, as it does on main, and a query term typed twice (two unboosted SHOULD clauses, the query a a) to count 16/9 (about 1.78x) instead of 2x.
  3. Instead javac stops: "no suitable constructor found for StableTflSimilarity(float,float,float)", and there is no getK3(). The 10.6.0 class has only the (k1, c) and () constructors; a term typed twice counts 2.0x.
  4. Why: k3 exists only on main (the future 11.0). The 10.6 backport (#16322) left it out and, on the feature author's review request, removed this sentence. A week later a test-only backport rewrote the entry back to main's wording, and 10.6.0 shipped with it.

Who is affected

#

Developers adopting the new, opt-in, experimental StableTflSimilarity on 10.6 who read the release notes: the advertised k3 constructor and getK3() fail to compile, and 10.6 has no built-in saturation of repeated query terms. No wrong results and no runtime or index effect. Unfixed, every later CHANGES file (10.6.1, 11.0) repeats the sentence.

Mechanism, terms and numbers538 words

The 10.6.0 New Features entry for GITHUB#16243 reads: "Add StableTflSimilarity, a similarity that estimates term rarity from term length and document length instead of corpus statistics such as document frequency. It also supports k3 query-term frequency saturation. (Tianxiao Wei)". The second sentence describes main (the future 11.0), not 10.6.0. The 10.6.0 class has only the (k1, c) and () constructors and no getK3(), and 10.6.0's Similarity lacks the computeQueryTermWeight hook that k3 needs. The 10.x backport #16322 left k3 out on purpose ("remove k3 which isn't in 10") and, at the feature author's request in review, dropped the sentence as well. A week later 3a75616c943, the 10.x backport of a test-only change (#16300), rewrote the entry back to main's wording in one of its CHANGES hunks. branch_10_6 inherited the sentence, 10.6.0 shipped with it (CHANGES.txt and the published Changes page), and main's copy of the 10.6.0 section has the same sentence. It is a documentation defect: nothing runs differently, and code written from the notes fails loudly at compile time. The fix is to delete the sentence from the 10.6.0 entry on main and branch_10_6.

The claim

#
  • On main 645d4fe14a20, CHANGES.txt:456 is the Lucene 10.6.0 heading and CHANGES.txt:506-508 is the GITHUB#16243 entry ending "It also supports k3 query-term frequency saturation." The release 10.6.0 has the same text at CHANGES.txt:56-58, and the published 10.6.0 Changes page shows it.

What 10.6.0 has

#
  • StableTflSimilarity.java at the 10.6.0 tag: the class javadoc lists only k1 and c (lines 45-49), @lucene.experimental (line 54), and the constructors (float k1, float c) (line 96) and () (line 117). There is no k3 field, constructor or getter.
  • 10.6.0's Similarity has no computeQueryTermWeight, so no 10.6 similarity can apply k3.

What main has

#
  • StableTflSimilarity.java on main: the javadoc bullet "k3 - query-side saturation for repeated query terms (disabled by default)" (line 50), DEFAULT_K3 = -1f (line 66), the (float k1, float c, float k3) constructor (line 110), computeQueryTermWeight with ((k3 + 1) * qtf) / (k3 + qtf) (lines 159-163) and getK3() (line 362).
  • It overrides the main-only hook Similarity.computeQueryTermWeight (Similarity.java:175), which came with GITHUB#15818, listed in main's 11.0.0 section (CHANGES.txt:172, "Add BM25 k3 query-term frequency saturation to BM25Similarity").

How the sentence got into 10.6.0

#
  1. 2026-07-01, main, e3a7a733c8a (#16243, txwei): the entry is written under main's 10.6.0 heading with the k3 sentence. True of main's class.
  2. 2026-07-01, the #16322 review (the 10.x backport): on lucene/CHANGES.txt txwei asked to "remove the last part of supporting k3" and mccullocht replied "Done"; txwei also wrote "This major difference between the 10x backport and main is k3 is not supported on 10x".
  3. 2026-07-01, branch_10x, 8e40c912555 (#16322): "remove k3 which isn't in 10". The entry ends "...such as document frequency. (Tianxiao Wei)". Correct.
  4. 2026-07-08, branch_10x, 3a75616c943 (dweiss, "Backport changes to TestTermInSetQuery. #16300", pushed directly): its CHANGES diff adds the #16300 entry and, in a separate hunk, rewrites the #16243 entry's second line to main's wording, which brings the k3 sentence back. The message does not mention it.
  5. 2026-10-14: branch_10_6 is cut from branch_10x and inherits it. The sentence survives the release manager's changelog clean-ups of 2026-10-20/21 (f79709fd57e, 7cecf795236), which do not touch this entry. 2026-10-26: RC1 4ae946e5a9b, released as 10.6.0.
Exposure and likelihood155 words
  • Who reads it: everyone who reads the 10.6.0 notes: CHANGES.txt in the source release, changes/Changes.html in the release folder, and the website's 10.6.0 Changes page.
  • Who is hit: developers who adopt StableTflSimilarity on 10.6 and want k3. It is new in 10.6.0, not the default similarity, and @lucene.experimental.
  • What they get: a compile error as soon as they try the advertised constructor or getK3(); someone who reads only the notes may plan for a feature that arrives in 11.0.
  • What does not happen: no wrong results, no exception at run time, no index effect. Without k3 a repeated query term keeps its linear weight, which is normal 10.x behaviour.
  • Scale: one sentence in one release line (10.6.x). On main the sentence is text only, since main's class has k3. The released 10.6.0 files stay as released; the fix corrects the 10.6.0 section that 10.6.1 and 11.0 will carry.

Minimal repro

#

One JUnit test, one method, no index, nothing random: it asks whether StableTflSimilarity has a public constructor with 3 parameters, a stand-in for the (k1, c, k3) constructor the 10.6.0 notes advertise. It fails on 10.6.0 and passes on main, which has k3.

Expected
The test passes: the 10.6.0 notes say StableTflSimilarity supports k3, so a 3-parameter (k1, c, k3) constructor should exist, as it does on main.
Observed
AssertionError: expected StableTflSimilarity(k1, c, k3); actual: only StableTflSimilarity(float,float) and StableTflSimilarity().

All files of this repro: repro/LFV-948/

More files, environment, full output335 words

The test counts parameters only: on main the only 3-parameter constructor is (float k1, float c, float k3) (StableTflSimilarity.java:110), and 10.6.0 has none. Because it does not check the parameter types, the javac error, which names the exact (float,float,float) constructor and getK3(), is the stronger evidence. Reflection is used only so the same file compiles on both lines (10.6 and main); the user-facing symptom is the javac error of new StableTflSimilarity(1.2f, 0.917f, 7f), shown in the full output below. The result does not depend on the seed or on assertions.

No regression test applies. The fix is a CHANGES.txt edit. After it, this test still fails on branch_10_6 (the class correctly has no k3) and passes on main either way, so it is evidence, not a regression test.

Why it looks unintended

#
  • The 10.6 backport removed k3 on purpose, and its review asked to drop this very sentence ("remove the last part of supporting k3" / "Done").
  • A test-only backport (#16300) put it back; its message does not mention this entry.
  • Lucene's own tooling asks release entries to match "what changes were actually backported".
The full argument176 words
  • Removed on purpose. 8e40c912555 (#16322): "non-trivial integrations: symbol renames and remove k3 which isn't in 10". Review on lucene/CHANGES.txt: txwei, "remove the last part of supporting k3"; mccullocht, "Done". txwei, in a PR comment that says the changes LGTM: "This major difference between the 10x backport and main is k3 is not supported on 10x".
  • Re-added, most likely by accident. 3a75616c943 (dweiss) backports a TestTermInSetQuery change (#16300) and has no PR of its own; besides adding the #16300 entry, one hunk of its CHANGES diff rewrites the #16243 entry's second line to main's wording, and its message does not mention #16243. Why is not recorded, so "by accident" is an inference.
  • Release sections describe the release. dev-tools/scripts/diff_lucene_changes.py:24-29: keep main's and the stable branch's entries "identical and 2) matching what changes were actually backported to be honest to users". The 10.6 class javadoc itself lists only k1 and c.
  • Precedent. Main's 10.6.0 section listed GITHUB#16794, which is not in 10.6.0; #16912 (mayya-sharipova, merged 2026-10-26, "Move CHANGES entry for GITHUB#16794 from 10.6.0 to 11.0.0") moved it.
The devil's-advocate check157 words

Strongest case for leaving it: CHANGES is an informal summary; the authoritative 10.6 javadoc is correct; the sentence is literally true of main, where its author wrote it; the class is experimental; and the failure is a loud compile error that hurts no one, so it is a cosmetic nit.

Why it fails: it is not a wording slip but a false feature claim under the 10.6.0 heading, the exact claim the maintainers chose to drop for 10.x. Experimental status lets the API change between releases; it does not make the notes describe an API the release lacks. And the sentence is now on the published 10.6.0 Changes page and would be copied into every later CHANGES file. An independent reviewer from another model family (OpenAI GPT-5.6, reading only) rated the 'intended' argument weak; the earlier refute review's "not real" was procedural (it could not execute) and it called the evidence a genuine documentation discrepancy.

How it was found

#

Semi-formal. A probe checked the class and method names cited in the 10.6.0 release notes against the 10.6.0 jars and flagged k3; a finder then wrote a differential checker of the CHANGES entry against the release jar's class files, with a fixed-text control, and traced the sentence through git history.

The method in full161 words
  • Probe: a name-level check of all 39 Class#method and 129 class references in the RC's 10.6.0 section against the RC jars found no other missing API; javap of the RC core jar showed StableTflSimilarity with only (float,float) and (), and a probe calling new StableTflSimilarity(1.2f, 0.917f, 7f) ran on main and was a compile error on the RC.
  • Finder (a hunt unit): a claim checker that reads a CHANGES file's 10.6.0 GITHUB#16243 entry and scans the release jar's class files (MISMATCH for the RC text and for main's 10.6.0 text against the RC jar; CONSISTENT for the fixed text and for main's text against main's jar), the git provenance (git log -S, blame), and a public-API JUnit test.
  • Verification: an independent reproducer, an independent reviewer from another model family (OpenAI GPT-5.6) and an intended-behaviour devil's advocate all called it real; an adjudication confirmed it (high). The repro was then reduced to one test with one assertion.

Documentation only, in the notes of 10.6.0 (released 2026-10-29): every reader of the 10.6.0 CHANGES.txt or Changes page is told that the new, @lucene.experimental, opt-in StableTflSimilarity supports k3, but the 10.6.0 class has only the (k1, c) and () constructors, so code written from the notes (new StableTflSimilarity(k1, c, k3), getK3()) fails to compile and a repeated query term keeps its linear weight; no wrong results, no runtime or index effect, and no earlier release is affected.
Summary
You read the Lucene 10.6.0 release notes, whose GITHUB#16243 entry says StableTflSimilarity 'also supports k3 query-term frequency saturation', and write new StableTflSimilarity(1.2f, 0.917f, 7f) against the 10.6.0 jar. You expect it to compile, as it does on main; instead javac finds no (float, float, float) constructor and no getK3(), because the 10.x backport (#16322) deliberately left k3 out ('remove k3 which isn't in 10') and, on the feature author's review request, also dropped the k3 sentence, which a later, unrelated backport commit (3a75616c943, the #16300 backport) put back. The sentence ships in the RC1 source release's CHANGES.txt and Changes.html and is also in main's copy of the 10.6.0 section.
