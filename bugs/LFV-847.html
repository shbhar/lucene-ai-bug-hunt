Classic and flexible query parsers: the docs never say which characters separate clauses, so AND next to an EM space or no-break space becomes a search word and a '-' is lost

Lucene's classic and flexible query parsers split clauses only at a space, tab, LF, CR or U+3000, and no doc says so. Typed with EM spaces, title:foo AND -bar becomes title:foo title:and title:bar: AND is a search word and 2 documents match instead of 1.

The finding in 30 seconds

#

The query grammars skip only five characters between clauses: space, tab, LF, CR and U+3000. Every other Unicode space is a term character, so a run like foo<EM>AND<EM>-bar is one term; the analyzer then splits it under the first clause's field. No syntax doc lists the five.

  1. Index two documents, {title: foo, body: bar} and {title: foo, body: baz}. Parse title:foo AND -bar with QueryParser or StandardQueryParser and StandardAnalyzer: +title:foo -body:bar, 1 hit.
  2. Paste the same query from a formatted document, where the two spaces are EM SPACEs (U+2003). The syntax docs never say which spaces count, and Java's Character.isWhitespace calls this one whitespace, so you expect the same query and 1 hit.
  3. You get title:foo title:and title:bar and 2 hits: AND became the word "and", the - exclusion is gone and title: now covers all three words. Both parsers, default settings.
  4. Why: both grammars separate clauses at only five characters (space, tab, LF, CR, U+3000). Any other Unicode space is part of a term, so foo<EM>AND<EM>-bar is one term that the analyzer splits under the first field. The five-character set is likely intended; it is just undocumented.

Who is affected

#

Applications that pass human-entered query text to the classic QueryParser (or a parser built on it) or to StandardQueryParser, with default settings, when the text has an operator, +/- or a field prefix and its spaces are not plain spaces, typically text pasted from a web page or word processor. The query silently changes meaning, or throws.

Mechanism, terms and numbers652 words

The classic QueryParser and the flexible StandardQueryParser skip exactly five characters between tokens: space (U+0020), tab, LF, CR and the ideographic space U+3000 (QueryParser.jj:187, StandardSyntaxParser.jj:135). The same five are the only spaces excluded from term characters (QueryParser.jj:183-185, StandardSyntaxParser.jj:131-133), so every other Unicode space, including the EN, EM and THIN spaces, U+205F and the no-break space, is part of a term.

No query syntax doc says this. The classic syntax page says only "A query is broken up into terms and operators" (classic/package-info.java:106), the StandardQueryParser syntax section is silent (StandardQueryParser.java:67-68), and setSplitOnWhitespace speaks of "whitespace" without defining it (QueryParser.jj:152). So a query pasted with EM spaces silently loses its operators: title:foo AND -bar becomes title:foo title:and title:bar. The separator set is very likely intended, so this is a documentation defect; listing the five characters in the two syntax docs fixes it.

The mechanism (main 5adff78bb168)

#
// QueryParser.jj:183-187 (StandardSyntaxParser.jj:131-135 lists the same five)
| <#_TERM_START_CHAR: ( ~[ " ", "\t", "\n", "\r", "\u3000", "+", "-", "!", "(", ")", ":", "^",
                           "[", "]", "\"", "{", "}", "~", "*", "?", "\\", "/" ]
                        | <_ESCAPED_CHAR> ) >
| <#_TERM_CHAR:       ( <_TERM_START_CHAR> | "-" | "+" ) >
| <#_WHITESPACE:      ( " " | "\t" | "\n" | "\r" | "\u3000") >
  1. _WHITESPACE is skipped between tokens (QueryParser.jj:191-193; StandardSyntaxParser.jj:139-141). It has five members.
  2. A term starts with any character outside the exclusion list and continues with term characters, which add - and + (QueryParser.jj:183-186). An EM space is not excluded, so it is a term character, and so is the - after it.
  3. title:foo<EM>AND<EM>-bar is therefore the field title and one TERM. StandardAnalyzer splits it into foo, and, bar; with the default splitOnWhitespace=false (QueryParser.jj:112) these become title:foo title:and title:bar.
  4. If the next clause has its own field (title:foo<EM>AND<EM>-body:bar), the term ends at : and both parsers throw ParseException (independent check, executed).
  5. Plain word queries parse the same under the default (new<EM>york gives body:new body:york), but a field prefix spreads (title:new<EM>york gives title:new title:york) (independent check, executed).
  6. What is lost and what still works next to an EM space or a no-break space, both parsers (own probe, executed): the word operators AND, OR, NOT and &&, || on either side of one are absorbed, and so are a +, a - or a field name right after one (foo<EM>title:bar gets the field name foo<EM>title). Syntax characters still work: (, ), ! and " are recognized, and a - or + written before the space is kept (foo -<EM>bar gives body:foo -body:bar).

The 24 characters that do not separate clauses (both parsers, executed)

#

U+000B, U+000C, U+001C-U+001F, U+0085, U+00A0, U+1680, U+2000-U+200A, U+2028, U+2029, U+202F, U+205F. With StandardAnalyzer, U+202F stays inside a word, so the query has another shape, but AND and the - are still lost.

The exact wrong query depends on the analyzer: with WhitespaceAnalyzer the EM form gives title:foo title:AND title:-bar, and the no-break space form stays one term, title:foo<NBSP>AND<NBSP>-bar (executed).

What the docs say

#
  • classic/package-info.java:106: "A query is broken up into terms and operators." Nothing defines what separates them.
  • StandardQueryParser.java:67-68: "A query consists of clauses, field specifications, grouping and Boolean operators and interval functions." Nothing on separators.
  • QueryParser.jj:152 (setSplitOnWhitespace): "Whether query text should be split on whitespace prior to analysis." The word is not defined.
  • simple/SimpleQueryParser.java:41, :129: SimpleQueryParser does list its own separators, ' ' '\n' '\r' and '\t'.
  • flexible/standard/parser/EscapeQuerySyntaxImpl.java:38: the flexible escaper's own list, escapableWhiteChars, is the five plus form feed (\f) and backspace (\b). It only decides what escape() puts a backslash in front of; the grammar does not separate on FF, and backspace is not whitespace at all.
Exposure and likelihood142 words
  • Who is exposed: callers of QueryParser and its subclasses (MultiFieldQueryParser and others) or of StandardQueryParser, default configuration, with query syntax in the text.
  • How the characters arrive: copy-paste from formatted text. One public example of a no-break space arriving in a search box is Kibana #87176 (Safari turned typed spaces into U+00A0 and broke a NOT); that is a different grammar, cited only to show the input occurs.
  • Effect: an operator becomes a search word, an exclusion is lost, a field prefix spreads, so the hits change (2 instead of 1 in the repro's index); or ParseException when the next clause has its own field. Nothing tells the user why.
  • Limits: plain word queries parse the same under the default splitOnWhitespace=false; no scale is needed; no user report of the operator loss was found. Hence minor, priority Low.

Why it looks unintended

#
  • No doc, CHANGES or MIGRATE entry says which characters separate clauses; the classic syntax page says only "broken up into terms and operators".
  • Java's Character.isWhitespace calls the EM space whitespace, and SimpleQueryParser, in the same module, lists its separators.
  • Lucene fixed the same symptom for newlines as a bug (LUCENE-93, 2004).
The full argument151 words
  • No contract either way. The separator set appears only in the grammars. The syntax docs (classic/package-info.java, StandardQueryParser's class javadoc) and setSplitOnWhitespace's javadoc never list it, so a user cannot learn that an EM space is a term character.
  • Java's own definition disagrees. Character.isWhitespace is true for U+2002, U+2003, U+2009 and U+205F (executed), the four spaces the original test used.
  • Precedent. LUCENE-93 (#1171, "Parser bug when dealing with new lines", 9ada9671259, 2004): a newline next to && (with a space on either side) made the query act like || or match nothing; it was fixed as a bug by adding LF and CR to the set.
  • Old, unaddressed request. LUCENE-1122 (#2199, 2008) asked how whitespace escaping works and for documentation; it was closed in the 2013 bulk cleanup, not on its merits.
  • The module documents separators elsewhere. SimpleQueryParser.java:41, :129 list ' ' '\n' '\r' '\t'.
The devil's-advocate check200 words

The strongest case for "intended": the set is explicit, and tests check that the five are separators (testCJK, QueryParserTestBase.java:250-254 and TestQPHelper.java:324-328; testTabNewlineCarriageReturn, QueryParserTestBase.java:896 and TestQPHelper.java:937), though no test checks that other spaces are not. LUCENE-1528 (#2602, 2.9) added U+3000 alone, on purpose and as an enhancement, although its reference listed every Unicode space. In LUCENE-2465 (#3539, about mid-word quotes) Shai Erera described the syntax as a declared set of characters ("The QP itself does not follow any Unicode standard right?"), while Robert Muir argued in the same thread that "the only solution is to follow unicode". In LUCENE-6874 (#7932) Dawid Weiss and Uwe Schindler defended NBSP as a way to keep words together. The package docs say the parser is for human-entered text and program-generated clauses belong in the query API (package-info.java:82-95), so cleaning input is the application's job, and widening the set would change existing parses.

Why it does not decide the matter: it defeats a code-bug claim, which this doc does not make. None of it is in the user-facing docs, and the searches found no record that explains leaving the other spaces out. The fix asked for is the documentation.

Suggested fix

#

Recommended A: document the five separators

Document the five separators: one paragraph in the classic syntax page's Terms section and one in StandardQueryParser's syntax section, saying that only space, tab, LF, CR and U+3000 count as whitespace between terms and operators, and that operators next to any other Unicode space are joined to the term. Docs only; javadoc renders and all 533 queryparser tests pass.

 * <p>Between terms and operators, only five characters count as whitespace: the space (U+0020),
 * tab, line feed, carriage return and the ideographic space (U+3000). Other whitespace characters,
 * such as the no-break space (U+00A0) or the em space (U+2003), do not separate terms: they become
 * part of the term around them. An operator ({@code AND}, {@code OR}, {@code NOT}, {@code &&} or
 * {@code ||}) next to one of them, or a {@code +}, {@code -} or field name right after one, is then
 * joined to that term and not recognized. Replace these characters with a plain space before
 * parsing if the query text may contain them.

C: normalize the input before parsing (workaround, no Lucene change) (not run)

#

Replace Unicode spaces with U+0020 before calling parse. NFKC normalization maps the space separators U+00A0, U+2002, U+2003, U+2009, U+205F and U+3000 to U+0020 but leaves U+000B, U+000C, U+2028 and U+0085 unchanged (independent check, executed). NFKC is not a space-only mapping: it also rewrites other characters, for example the full-width letter U+FF21 to A and the ligature U+FB01 to fi (executed), so a targeted replacement of the space characters is the safer advice.

Trade-offs

  • Every application has to know to do it, which is what option A tells them.

Downstream note

#

Search applications and servers that hand user-typed query strings to these parsers inherit the behaviour; replacing Unicode spaces with a plain space before parsing avoids it.

How it was found

#

Semi-formal: a parse sweep over the 25 Unicode White_Space code points showed AND becoming a term for 20 of them. A program then compared the grammars' separator and term-character classes with Unicode White_Space and Java's definitions; a bounded-exhaustive lexer check and a query-shape sweep confirmed it, and a public-API JUnit test witnessed it.

The method in full146 words

Method: a parse sweep, a static comparison of the grammars' character classes, then bounded-exhaustive checking of the generated token managers (the study's "semi-formal" tier).

  • Parse sweep: title:foo<c>AND<c>-bar parsed on the stock main jars for each of the 25 Unicode White_Space code points <c>; AND became a term for 20 of them.
  • Set comparison: the classes extracted from QueryParser.jj and StandardSyntaxParser.jj against Unicode White_Space, Character.isWhitespace and Character.isSpaceChar. The obligation "every White_Space code point is grammar whitespace" fails for 20 code points.
  • Bounded-exhaustive lexer check: the real generated token managers on 111,150 inputs of length up to 4 per lexer and lexical state; unlisted spaces end up inside term tokens.
  • Parser-level sweep: 14,610 checks of query shapes (AND, OR, NOT, &&, ||, +/-, field prefixes) against the plain-space form, 10,860 differences.
  • Witness: a public-API JUnit test on the stock main jars, then the independent checks below.

History

#

There since the parser's first revision (2001); the syntax page added in 1.2 (2002) never defined the separators. LF and CR came in 2004, U+3000 alone in 2.9.0. Every release from 1.2 to 10.6.0 and main behave this way; not fixed upstream.

Versions tested5 rows

Introduced: bd3948c539e (svn r149570, "Initial revision", 2001-09-18; the 1.0.1 tag, 4db24b67693, is a cvs2svn commit made from it without 33 build, library and documentation files, with the same QueryParser.jj) with a closed list, " " | "\t". 584d2b394b0 (2001-11-01, 1.2-rc3) made characters above U+00FF term characters, so the EN/EM/THIN spaces stopped throwing and became part of terms. The syntax page, c092af6cfa3 (2002-05-15, 1.2), never defined the separators.

Shaping commits: 9ada9671259 (2004, LUCENE-93: LF, CR), 1ebfc379fd8 (2004: - and + inside terms, so the - of -bar is absorbed too), 13d5245314e (2009, LUCENE-1528: U+3000 alone), 343992fcbb4 (2009, LUCENE-1567: the flexible parser with the same five).

Only the shape of the wrong query changed over time (U+2003, classic): title:foo -body:bar in 1.2-1.3, title:"foo bar" in 1.4.1-2.9.4, title:"foo ? bar" in 3.0.x, title:foo title:bar in 3.1.0-7.7.3, title:foo title:and title:bar from 8.0.0. The plain-space query is +title:foo -body:bar in every version.

LFV-847, snapshot of 2026-11-07

Registry title
Classic QueryParser and flexible StandardQueryParser: the query syntax docs never say that only space, TAB, LF, CR and U+3000 separate clauses, so AND, OR or '-' written next to any other Unicode space (EN, EM or THIN space, U+205F, NBSP, ...) silently becomes part of a search term and a field prefix spreads to the following words: 'title:foo<EM SPACE>AND<EM SPACE>-bar' parses as 'title:foo title:and title:bar'
Area
queryparser / classic and flexible standard grammars (_WHITESPACE, _TERM_START_CHAR) and the query syntax documentation
Priority
Low, rank 1247: The behaviour is very likely intended and the defect is that the query syntax docs never list the clause separators, but pasted queries silently change meaning in the default classic and flexible parsers in every release, so it is Low, like its sibling LFV-845.
Impact class
minor
Impact note
Hits applications that pass human-entered query text to the classic QueryParser (and the parsers built on it) or to the flexible StandardQueryParser in their default configuration (splitOnWhitespace false or true) when the text uses an operator, a '+'/'-' or a field prefix and separates its words with a Unicode space outside the five listed separators, typically text pasted from a web page or a word processor: the query silently changes meaning (more or different hits), or throws ParseException when the next clause has its own field prefix; plain word queries parse the same under the default splitOnWhitespace=false; no scale is needed and every release since 1.0.1 is affected [exec]; classed minor because the five-character set is very likely intended and the defect is that no query syntax doc states it.
Summary
You parse 'title:foo AND -bar' with the classic or the flexible query parser, but the spaces are EM SPACEs (U+2003), as in text pasted from a formatted document; nothing in the query syntax docs says which characters separate clauses, so you expect the same query as with ordinary spaces, '+title:foo -body:bar'. Instead both grammars separate clauses only on space, TAB, LF, CR and U+3000, so 'foo<EM>AND<EM>-bar' is one term that the analyzer splits under the first field: the result is 'title:foo title:and title:bar', AND became the search word 'and', the '-' exclusion is gone and a document whose body contains bar now matches (2 hits instead of 1). The closed separator set is very likely intended, so the defect is the missing documentation; when the next clause has its own field prefix ('-body:bar') both parsers throw ParseException instead.
Introduced

The silent absorption of the four breakable spaces above U+00FF (U+2002, U+2003, U+2009, U+205F) into a term began with 584d2b394b0 (2001-11-01, 'Fix query parser so it accepts queries with unicode characters', CHANGES 1.2 RC3 item 3); before it they made parse() throw a lexical error, while U+00A0 and U+0085 were already silently part of the term [exec, same method]. Documentation side: the query syntax page added by c092af6cfa3 (2002-05-15, 1.2) says 'A query is broken up into terms and operators' and never defines the separators; the same sentence is in classic/package-info.java today [read].
