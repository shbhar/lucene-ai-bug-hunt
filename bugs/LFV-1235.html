A reused LZ4.FastCompressionHashTable throws ArrayIndexOutOfBoundsException when a slice offset plus a position left by a longer earlier call exceeds Integer.MAX_VALUE (needs an array above about 1.07 GB)

Reuse one LZ4.FastCompressionHashTable, as documented, on a 1.1 GB array and then on its last 1 MiB: the second compress throws ArrayIndexOutOfBoundsException, because the slice start plus a position left from the first call overflows int. Only direct LZ4 callers with arrays above about 1.07 GB are hit.

The finding in 30 seconds

#

The fast LZ4 compressor keeps a 16 KB table that remembers where it last saw each 4-byte pattern, relative to the start of the current call. To stay fast on many small inputs it does not clear the table between calls; get() should drop leftovers by checking that a candidate lies before the current position and within 64 KB.

  1. Fill a byte[1_100_000_000] with zeros and put 1,048,576 random bytes at its end, offset 1,098,951,424. With one new LZ4.FastCompressionHashTable(), compress the whole array from offset 0: that works.
  2. Compress just the last 1 MiB (offset 1,098,951,424) with the same table. You expect it to work: the table "can safely be reused", and with a fresh table this slice compresses to 1,052,688 bytes that decompress back.
  3. Instead the second call throws ArrayIndexOutOfBoundsException: Index -2096017425 out of bounds for length 1099999997, with assertions on and off.
  4. Why: the table still holds the first call's positions, such as 1,099,998,447, and get() adds the new start: 1,098,951,424 + 1,099,998,447 = 2,198,949,871, above Integer.MAX_VALUE (2,147,483,647). It wraps to -2,096,017,425, which passes the "earlier position, within 64 KB" checks, and reading there throws.

Who is affected

#

Only applications that call org.apache.lucene.util.compress.LZ4 directly, reuse one fast table, and start a call at an offset that, plus a position left by an earlier, longer call, exceeds Integer.MAX_VALUE (this needs an array above about 1.07 GB). Lucene's own writers always start at offset 0. The failure is a loud exception; no completed output or index data is wrong.

Mechanism, terms and numbers673 words

LZ4.FastCompressionHashTable remembers, for each hash of 4 bytes, where it last saw them, stored relative to the start (base) of the current call. reset() keeps old entries between calls on purpose and relies on get() to reject stale ones ("get() checks that references are less than the current offset", LZ4.java:344-346 at 5adff78bb168). get() rebuilds a candidate as base + stored in int (:369). After a first call over 1.1e9 bytes, a stored value is about 1.1e9; when the next call on the same table starts at 1,098,951,424, the sum passes Integer.MAX_VALUE and wraps negative, the negative position passes both checks at :372, and readInt throws ArrayIndexOutOfBoundsException. compress and compressWithDictionary both say the table "can safely be reused" (:513-515, :527), and a fresh table compresses the same slice. In general it needs direct calls to the utility where a call's start plus a position left by an earlier, longer call passes Integer.MAX_VALUE, which takes an array above about 1.07 GB; the slice itself may start much lower or lie in a separate, smaller array. Lucene's own writers compress from offset 0, and the failure is always a loud exception, never a completed wrong output. In every release from 8.5.0 to 10.6.0 and on main.

The bug, step by step

#
  1. Stored relative to the call's start. get(off) hashes the 4 bytes at off, stores off - base in that slot and gets back the slot's previous value: final int ref = base + hashTable.getAndSet(h, off - base); (LZ4.java:369 at 5adff78bb168).
  2. Old entries are kept on purpose. reset() (:320-349) builds a new table only when the old one is too small or too narrow (:333-335); otherwise: "Avoid calling hashTable.clear(), this makes it costly to compress many short sequences otherwise. Instead, get() checks that references are less than the current offset." (:344-346). A call of at least 65,541 bytes uses a 32-bit table (:326-330), so the second call (2^20 bytes) keeps the 32-bit table the first call filled.
  3. The check. if (ref < off && off - ref < MAX_DISTANCE && readInt(bytes, ref) == v) (:372), with MAX_DISTANCE = 65,536 (:54).
  4. The numbers. The first call has base 0, so the table holds absolute positions, here 1,099,998,447 (inside the random tail). The second call has base 1,098,951,424: ref = 1,098,951,424 + 1,099,998,447 = 2,198,949,871 > 2,147,483,647, which wraps to 2,198,949,871 - 2^32 = -2,096,017,425, the index in the exception. Without the overflow, ref would lie past off and ref < off would reject it.
  5. Why both checks pass. A wrapped ref is negative, so ref < off holds; off - ref wraps too and equals (off - base) - stored, a negative number, so it is < MAX_DISTANCE. readInt (:70-73) reads through BitUtil.VH_NATIVE_INT, a bounds-checked byte-array view (BitUtil.java:109), so it throws before reading anything. The reported length 1,099,999,997 is the array length minus 3, the view's bound for a 4-byte read.

When it can happen

#

base is below the length of the current call's array and stored below the length of the earlier call, so base + stored > 2^31 - 1 needs at least one array of more than 2^30 bytes (about 1.07 GB). The slice itself can start much lower, or lie in a separate, smaller array: after compressing a whole byte[2_000_000_000] with the table, a 1 MiB slice at offset 150,000,000 of the same array, or of a separate 200,000,000-byte array, throws Index -2144975224 (the first case passes with the fix). For compressWithDictionary the call's start is dictOff (:548). Both terms are in [0, 2^31), so a wrapped sum is always negative and readInt always throws: the failure is loud, never a wrong match. The 16-bit table (calls shorter than 65,541 bytes) has the same sum: two short slices of a 2,147,483,631-byte array (60,000 bytes at offset 0, then 1,000 bytes at its end) throw Index -2147442954.

Exposure and likelihood245 words
  • Who is exposed. The package is exported (module-info.java:47) and its package-info.java says only "Compression utilities.", with no @lucene.internal. Code that reuses one FastCompressionHashTable can hit it when a call's start plus a position left by an earlier, longer call passes Integer.MAX_VALUE. That needs some array above about 1.07 GB, but the slice can start well below 1 GB (150,000,000 after a 2,000,000,000-byte call) or lie in a separate, smaller array.
  • Not reached by Lucene. Every production caller found compresses from offset 0, so base is 0 and ref = stored cannot overflow: CompressionMode.java:163 (fast table) and :185 (high-compression table), LZ4WithPresetDictCompressionMode.java:167, Lucene90DocValuesConsumer.java:849, Lucene103BlockTreeTermsWriter.java:902-903 (high-compression table), and backward-codecs' Lucene80DocValuesConsumer.java:479-480 and :851-852. backward-codecs' legacy CompressionMode (:159) forwards its caller's offset, but only a test calls it. Tests use small non-zero offsets on small arrays.
  • The other table is fine. HighCompressionHashTable stores absolute positions and passes the same scenario (an executed cross-model control).
  • Effect. Deterministic for a given input; the call throws, nothing outside the array is read or written, and no index data is involved. Output already written to the DataOutput before the exception is incomplete and must be discarded. Workaround: a fresh table after compressing an array above 1 GB.
  • Likelihood. Contrived: a reused table, an array above 1 GB and a later call whose start plus a leftover position passes Integer.MAX_VALUE; no report was found in the recorded searches since the API appeared in 8.5.0 (2020).

Why it looks unintended

#
  • compress and compressWithDictionary both say the table "can safely be reused", with no offset or size limit.
  • reset() keeps old entries because "get() checks that references are less than the current offset"; the overflow defeats that check.
  • A fresh table compresses the same slice; before 8.5.0 each call got a new or cleared table.
The full argument194 words
  • Contract. compress: "{@code ht} shouldn't be shared across threads but can safely be reused." (LZ4.java:513-515); compressWithDictionary says the same (:527). The arguments pass Objects.checkFromIndexSize (:321, :532-533).
  • Design intent. The reset() comment (:344-346) states the invariant: stale entries stay because get() rejects them by ref < off. The wrap makes a stale entry pass.
  • History. Before LUCENE-4702 the package-private predecessor's reset either allocated a new table or cleared the old one (hashTable.clear()) on every call (codecs/compressing/LZ4.java:185-192 at b283b8df628^); LUCENE-4702 made the class public and dropped clear() as a speed-up for many short inputs. Its review never discusses large offsets. 8.4.1's predecessor passes the same sizes, offset and calls (with a Random(42) tail).
  • Tests. LZ4TestCase tests reuse ("Compress once again with the same hash table to test reuse", :139, :194) on small arrays only; no test, CHANGES or MIGRATE entry mentions a size or offset limit.
  • Reference implementation. Among its reset conditions, the reference LZ4 C library's LZ4_prepareTable (lib/lz4.c:937-976 at lz4/lz4 943cc479c35b) clears a reused 32-bit table once its running offset passes 1 GB (:945-956).
The devil's-advocate check148 words

Strongest case for "intended": LZ4 is a low-level helper written for Lucene's codecs, which always compress from offset 0; reusing one table at non-zero offsets after an array above 1 GB is outside what it was built for, and the failure is loud. The parent package's package-info.java adds that its classes "are generally not intended for direct use by most applications" and that "APIs in this package are primarily internal and may change between releases" (org/apache/lucene/util/package-info.java:22-23, :35). Why it fails: that note is about API stability, not correctness; the compress subpackage is exported with its own unconditional reuse promise, the arguments are legal, a fresh table compresses the same slice, and reset()'s comment shows that get() was meant to reject stale entries. A size limit, if intended, would be documented or checked. The argument is about severity, which is why the priority is Low.

Suggested fix

#

Recommended A. Compare in differences in get() (validated)

In FastCompressionHashTable.get, compare in differences: distance = off - base - stored cannot overflow; accept only 0 < distance < MAX_DISTANCE, then ref = off - distance. The repro passes and all 31 org.apache.lucene.util.compress tests pass, assertions on and off. Alternative: clear the table in reset() for large inputs, as the reference LZ4 C library does.

final int stored = hashTable.getAndSet(h, off - base);
lastOff = off;
// off - base and stored are both in [0, 2^31): this difference cannot overflow
final int distance = off - base - stored;
if (distance > 0 && distance < MAX_DISTANCE) {
  final int ref = off - distance;
  if (readInt(bytes, ref) == v) {
    return ref;
  }
}
return -1;

A. Compare in differences in get() (validated) (recommended)

#

Replace LZ4.java:369-376 so that the stale-entry test works on distance = off - base - stored. Both terms are in [0, 2^31), so the difference cannot wrap; distance > 0 is ref < off and distance < MAX_DISTANCE is the window check. A stale entry gives distance <= 0 and is rejected.

final int stored = hashTable.getAndSet(h, off - base);
lastOff = off;
// off - base and stored are both in [0, 2^31): this difference cannot overflow
final int distance = off - base - stored;
if (distance > 0 && distance < MAX_DISTANCE) {
  final int ref = off - distance;
  if (readInt(bytes, ref) == v) {
    return ref;
  }
}
return -1;

Trade-offs

About as many integer operations on the hot path as before (off - base - stored and two compares, plus off - distance only for an accepted candidate; not benchmarked); keeps the no-clear speed-up for short inputs; covers both table widths, including the 16-bit case (two short slices of a 2,147,483,631-byte array also pass with it).

What the checks validated

  • The repro fails without the fix and passes with it, with assertions on and off (gradle, seed DEADBEEF, 2 GB test heap).
  • With the fix, org.apache.lucene.util.compress.* passes: 5 classes, 31 tests, 0 failures (TestFastLZ4 9, TestHighLZ4 9, TestDecompressLZ4 3, TestLowercaseAsciiCompression 9 and the repro), with assertions on and, in a separate run, off.
  • :lucene:core:checkGoogleJavaFormat passes with the fix and the test file.
  • The 16-bit-table check passes with the fix, with -ea and -da.

B. Clear the table in reset() when it is kept for a large input

#

Clear the kept table in reset() (:343-347) when it serves a call of 64 KB or more, as the reference LZ4 C library clears a reused 32-bit table once its offset passes 1 GB. LZ4.Table has no clear method today: it declares only set, getAndSet, getBitsPerValue and size (:224-233), and the hashTable.clear() named in reset()'s comment is left over from the older packed-ints table. So this needs a new Table method (for example an Arrays.fill of the backing array) or a fresh table.

Trade-offs

A 16 KB clear per call is small next to compressing 64 KB or more. But clearing only the 32-bit table leaves the 16-bit case in place, and clearing on every call gives up the speed-up for many short inputs that LUCENE-4702 introduced. Not built or tested.

Downstream note

#

Downstream code that calls LZ4.compress directly and reuses one table after compressing an array above 1 GB can hit this; a fresh table after such an array avoids it.

How it was found

#

A proof-obligation audit of LZ4.FastCompressionHashTable's contract: the "can safely be reused" promise and reset()'s stale-entry comment were checked against get()'s int arithmetic, which showed that base + stored can wrap for a reused table. A one-method JUnit test on the public API then witnessed it.

The method in full102 words

The obligation: for every legal call sequence on one table, get() must return either -1 or an earlier position within 64 KB. reset() keeps entries from earlier calls, so stored is bounded only by the earlier call's length, and base + stored is bounded by the sum of the two calls' array lengths, which can exceed Integer.MAX_VALUE once an array holds more than 2^30 bytes. The witness test (an earlier variant of the repro above, with the same sizes, offset and calls and a different random tail) fails on main with assertions on and off and on the 10.6.0 and 9.12.3 jars.

Impact class

Impact note
Only applications that call the public org.apache.lucene.util.compress.LZ4 utility directly are hit, when they reuse one FastCompressionHashTable (as both compress methods' javadoc allows) first on a long input and then on a slice whose start offset plus an offset left in the table by that earlier call exceeds Integer.MAX_VALUE, which needs a byte[] of more than about 1.07 GB (executed: a 1.1e9-byte input from offset 0, then its last 2^20 bytes at offset 1,098,951,424): the second call throws ArrayIndexOutOfBoundsException with -ea and -da instead of compressing a slice that a fresh table compresses and round-trips; no Lucene indexing, merge or search path reaches it, because every in-tree LZ4 compress caller starts at offset 0, and the failure is always loud, with no wrong output and no index data touched; in every release from 8.5.0 to 10.6.0 and on main.
Summary
You compress a byte array of 1.1e9 bytes with LZ4.compress, reusing one LZ4.FastCompressionHashTable as the javadoc allows ('can safely be reused'): first the whole array from offset 0, then its last 2^20 bytes (offset 1,098,951,424). You expect the second call to compress the slice, as it does with a fresh table.
