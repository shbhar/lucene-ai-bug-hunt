DatasetSplitter.split with no fieldNames throws at the first document that has a stored binary field

DatasetSplitter.split with fieldNames left out ("all should be used") throws an IOException at the first document that stores a binary value, such as new StoredField("payload", new byte[] {1, 2, 3}): it copies every field as indexed, tokenized text, which cannot hold bytes. Every release since 4.2.0 (2013) has it.

The finding in 30 seconds

#

DatasetSplitter (module lucene/classification) copies the documents of an index into a training, a test and a cross-validation index. With fieldNames left out it copies every stored field, and it rebuilds each copy with one field type: a stored, indexed, tokenized TextField. Lucene does not allow bytes in a tokenized field.

  1. Index one document: a class label cls = "a" as sorted doc values, and a stored binary field payload = {1, 2, 3}.
  2. Split it with new DatasetSplitter(0.5, 0).split(reader, train, test, cv, analyzer, false, "cls"), leaving fieldNames out; the javadoc says all fields "should be used" then.
  3. You expect the split to succeed: with a test ratio of 0.5 the document goes to the test index, payload and all.
  4. Instead split() throws IOException: IllegalArgumentException: cannot set a BytesRef value on a tokenized field, with assertions on and off; in this one-document example no document reaches any output. Only binary values fail: with stored strings and numbers the split runs without error.
  5. Why: every copy gets one field type, an indexed, tokenized TextField.TYPE_STORED, and new Field(name, bytes, thatType) is illegal in core. Copying the bytes as a stored-only StoredField fixes it.

Who is affected

#

Users of the opt-in lucene/classification module who split an index with fieldNames left out, when any document stores a binary value (a payload, an id kept as bytes). No setting or scale is needed: one document shows it. It fails at once and loudly, the source index is unchanged, and naming only the non-binary fields avoids it.

Mechanism, terms and numbers692 words

DatasetSplitter.split copies the documents of an index into a training, a test and a cross-validation index for classifier work. Its fieldNames parameter lists the "names of fields that need to be put in the new indexes or null if all should be used". In the all-fields mode it copies every stored value, and it rebuilds each copy with one field type, new FieldType(TextField.TYPE_STORED): indexed, tokenized and stored. For a binary stored value it calls new Field(name, bytes, ft), which core Field rejects with "cannot set a BytesRef value on a tokenized field". split() wraps that in an IOException at the first copied document that stores a binary value, such as new StoredField("payload", new byte[] {1, 2, 3}), so in that mode such an index cannot be split. The branch was written for binary values in the very first version (2012) and has never worked: every release from 4.2.0 to 10.6.0 and main fails, only the message changed. It is loud and deterministic, needs the opt-in classification module, leaves the source index alone, and naming only the non-binary fields avoids it. Copying the bytes as a stored-only StoredField fixes it.

Terms

#
  • Split: new DatasetSplitter(testRatio, crossValidationRatio).split(reader, training, test, cv, analyzer, termVectors, classFieldName, fieldNames...) groups the source documents by class and sends each one to the test, cross-validation or training index (DatasetSplitter.java:80-180).
  • fieldNames: "names of fields that need to be put in the new indexes or null if all should be used" (:76-77). Leaving it out (or passing null or an empty array) is the all-fields mode.
  • Stored binary field: new StoredField(name, byte[]) or new StoredField(name, BytesRef), "a stored-only field with the given binary value" (StoredField.java:65-77, :95-107). Reading the document back gives a field whose binaryValue() is the bytes.
  • Tokenized field: a field whose value goes through the analyzer into terms. TextField.TYPE_STORED is indexed (DOCS_AND_FREQS_AND_POSITIONS), tokenized and stored (TextField.java:40-43). Bytes cannot be analyzed, so core forbids a BytesRef value on such a type.

The bug

#
  1. split builds one type for every copied field: FieldType ft = new FieldType(TextField.TYPE_STORED), plus term vectors with positions and offsets if termVectors is true (DatasetSplitter.java:128-134).
  2. For each source document it calls createNewDoc (:150). With no names (:187) it loops over every stored field (:195) and picks by value kind: reader (:196-197), binary (:198-199), string (:200-201), numeric as text (:202-203).
  3. The binary branch adds new Field(field.name(), field.binaryValue(), ft) (:199). The constructor throws "cannot set a BytesRef value on a tokenized field" for an indexed, tokenized type (Field.java:213-214). Its javadoc states a broader rule, "@throws IllegalArgumentException if ... the field's type is indexed()" (:196-197); the code accepts an indexed type that is not tokenized, as in StringField(String, BytesRef, Store). ft is tokenized, so it is rejected either way.
  4. split catches it and throws new IOException(e) (DatasetSplitter.java:174-175), at the first document with a stored binary value.
  5. Same cause, other messages: with termVectors = true the offsets check fires first, "It doesn't make sense to index offsets on binary fields" (Field.java:209-211, executed); naming the binary field in fieldNames gives "value must not be null", because stringValue() is null for bytes (DatasetSplitter.java:191, Field.java:244-245, executed).

Exposure and likelihood264 words
  • Who is exposed. Callers of DatasetSplitter.split in its all-fields mode (fieldNames omitted, null or empty) on an index where any document has a stored binary field. No production code in Lucene calls the class; only TestDataSplitter and Test20NewsgroupsClassification do.
  • Default vs opt-in. The all-fields mode is the documented "all should be used" case and is tested upstream (testSplitOnAllFields). No index setting or scale is needed. On main the exception is thrown while the copy is built, before it reaches a writer, so neither the codec nor the analyzer plays a part; the test uses a plain IndexWriterConfig with the test framework's MockAnalyzer and randomized codec.
  • What breaks. In that mode the call throws at the first document it copies that stores a binary value, deterministically, with assertions on and off, so the split never completes. Documents copied before that one stay in the outputs, because the writers are closed, and so committed, in finally (DatasetSplitter.java:178): a fact-check probe found the training index holding 1 document after the failure when a stored-string document came first. In the one-document repro no document reaches any output.
  • Not affected. The source index (only read; split() does close the reader it is given), stored text, string and numeric values, and named mode that leaves the binary fields out (the cross-model reviewer ran it: passes).
  • How likely. Certain once a stored binary field meets the all-fields mode, but the utility has few users, text-classification corpora mostly store text, the failure is loud with an obvious workaround, and no public report was found in 13 years.

Why it looks unintended

#
  • The javadoc: fieldNames is "null if all should be used"; the only precondition is sorted doc values on the class field.
  • createNewDoc has a branch for binary values (DatasetSplitter.java:198-199), which strongly suggests they were meant to be copied; it never worked.
  • StoredField(name, byte[]) is ordinary public API; the searches found no test, javadoc, CHANGES or MIGRATE entry expecting the exception.
The full argument238 words
  • Contract. "@param fieldNames names of fields that need to be put in the new indexes or null if all should be used" (DatasetSplitter.java:76-77). The only stated precondition concerns the class field: "this must be indexed with sorted doc values" (:74-75). Nothing limits the kinds of stored fields in the source.
  • The code's own intent. :198-199 is a branch for binary values, which strongly suggests they were meant to be copied, not refused (the branch alone cannot prove the author's intent).
  • Core is right, the caller is not. Field documents the rejection (Field.java:196-197). The splitter makes that illegal call itself, for legal input.
  • Not a write failure. split() declares "@throws IOException if any writing operation fails on any of the indexes" (DatasetSplitter.java:78); here nothing failed to write, the copy built an illegal field.
  • Tests. TestDataSplitter indexes text fields and sorted doc values only; Test20NewsgroupsClassification stores StringField and TextField values. These are the only current tests that use the class, so no current upstream test stores a binary field for it, and none expects the exception; with the fix the whole module suite stays green.
  • History. The branch is in the very first DatasetSplitter (3459b28334e, LUCENE-4345, 2012), when the constructor already refused an indexed BytesRef ("Fields with BytesRef values cannot be indexed"). LUCENE-4345 never discusses binary values; the recorded searches found no CHANGES or MIGRATE entry that records a limit.
The devil's-advocate check153 words

The strongest "intended" case (the devil's-advocate verifier built it and rejected it; the cross-model reviewer rated it weak): the splitter is a text-classification helper, not a general index copier. It rebuilds every value as a stored TextField and turns numbers into text (DatasetSplitter.java:202-203), so binary values are out of scope; core documents the exception; split() declares IOException; and naming only the text fields works.

Why it fails: no documented limit was found, and the code's own binary branch points the other way. Core documenting the rejection puts the defect in the splitter, which builds the illegal field. The workaround does not make the documented "all" mode work: that mode can never succeed once a document it copies stores a binary field. The recorded searches found no test, issue, CHANGES or MIGRATE entry that treats the exception as expected. Every reviewer rated the bug real, and the adjudication confirmed it (Low).

Suggested fix

#

Recommended Copy a binary value as a stored-only StoredField (fix A)

Copy a binary value as a stored-only field: in createNewDoc's all-fields branch, add new StoredField(field.name(), field.binaryValue()) instead of new Field(..., ft) (one line plus an import). The repro then passes, and TestDataSplitter, the whole lucene/classification suite (assertions on and off) and check -x test pass with it.

Trade-offs

  • The copy is stored, not indexed. The Document that StoredFields.document() returns carries no indexing metadata (keeping it would need a separate lookup of the reader's field infos), and bytes cannot be tokenized anyway. Core does allow an indexed, non-tokenized binary term (StringField(String, BytesRef, Store)), so a maintainer may prefer an explicit policy for binary values.
  • StoredField has its own type, so the fix also works with termVectors = true (executed side probe: stock throws "It doesn't make sense to index offsets on binary fields", the fix passes). The binary copy then gets no term vectors (it is stored only), while the parameter says "true if term vectors should be kept".
  • Named mode is left as it is: naming a binary field still throws "value must not be null" (DatasetSplitter.java:191), the line LFV-681's fix changes, so fix A covers the all-fields mode only (the 12-case check gives 11 of 12 with it). The two diffs touch different lines and apply cleanly with git apply in either order (executed).

Skip binary values in the all-fields copy (not validated)

#

Drop the binary branch, so binary stored fields are not copied.

Trade-offs

The split succeeds, but the bytes the caller asked for ("all should be used") are silently left out; the repro's last assertion would become "the document arrives".

Document the limit (not recommended)

Say in the fieldNames javadoc that stored binary fields must be left out by naming the other fields.

Trade-offs

No behaviour change; the dead branch and the crash stay.

Anyone who runs DatasetSplitter.split (lucene/classification, an offline helper that builds training, test and cross-validation indexes) in its documented all-fields mode on a source index where some document has a stored binary field, such as a StoredField(name, byte[]) payload, gets an IOException at the first such document, in every release since 4.2.0, with the default IndexWriterConfig, codec and analyzer, -ea and -da alike and at any size; the failure is loud and deterministic, the source index is not changed, and naming only the non-binary fields in fieldNames avoids it.
Summary
You split an index into training, test and cross-validation indexes with DatasetSplitter.split and leave fieldNames out, which the javadoc documents as 'all [fields] should be used', and a document of the source index has a stored binary field such as new StoredField("payload", new byte[] {1, 2, 3}). You expect the split to succeed and keep the bytes; createNewDoc even has a branch written for binary values. Instead split() throws an IOException wrapping IllegalArgumentException 'cannot set a BytesRef value on a tokenized field', because every copied field gets the indexed, tokenized type TextField.TYPE_STORED and the core Field constructor refuses a BytesRef value on such a type, so no split of such an index is possible in that mode.
