FieldExistsQuery#count undercounts documents whose norms-free text field analyzes to no tokens but still has a doc value

When a text field has norms turned off and a doc-values field of the same name, IndexSearcher#count(new FieldExistsQuery(f)) skips documents whose text produces no tokens: 2 hits count as 1. Released since 9.1.0; the hits themselves are correct.

The finding in 30 seconds

#

FieldExistsQuery finds the documents that have a value for a field. Its count() shortcut is exact for keyword fields, but not for a norms-free text field whose value produces no tokens.

Background in three steps

#
  1. One field name can carry several structures: indexed terms (for search), norms (per-document length, optional) and doc values (a per-document column for sorting and faceting).
  2. FieldExistsQuery(f) matches the documents that have a value for f: it reads the norms if the field has them, else the vectors, else the doc values.
  3. Weight#count lets IndexSearcher#count answer from index statistics without visiting documents. It must return the exact number of matching live documents, or -1 for "unknown, scan".

The finding, step by step

#
  1. Index two documents with a text field title whose norms are turned off, plus a SortedDocValuesField also named title: one with title "" (no tokens), one with "hello". Default config, one segment, no deletions.
  2. searcher.search(new FieldExistsQuery("title"), 10) returns both documents: without norms the query matches every document that has a doc value.
  3. You expect searcher.count(query) to be 2 as well.
  4. It is 1. On a segment without deletions count() takes a shortcut and returns Terms#getDocCount, the number of documents with at least one term, and the empty title has a doc value but no term. If no document of the segment has a term, the count is 0.
  5. Only counts are wrong: IndexSearcher#count, TotalHitCountCollector and Boolean counts built from the clause (under MUST_NOT they come out too high). Hits, top-k totalHits and CheckIndex are fine.

Who is affected

#

Applications that index a tokenized field with norms omitted plus a same-name doc-values field without a skip index, where some values analyze to no tokens (empty, punctuation-only, stop-words-only). Otherwise default config. Counts on segments without deletions come out too low (0 when no document has a term); hits stay correct.

Mechanism, terms and numbers569 words

FieldExistsQuery's Weight#count uses the number of documents with at least one indexed term as the number of documents with a doc value. For a tokenized field with norms omitted that shares its name with a doc-values field, a value that analyzes to no tokens (an empty, punctuation-only or stop-words-only text) gives a document that matches the query but is not counted. IndexSearcher#count then reports 1 for 2 hits, or 0 for 1 hit when no document of the segment has a term. Released since 9.1.0; not fixed upstream.

The mechanism (main 5adff78bb168)

#
  1. What the query matches. For a field without norms or vectors, scorerSupplier iterates the field's doc values (FieldExistsQuery.java:170-219, the doc-values switch at :188-209), so every document with a doc value is a hit. The class javadoc says the query matches documents that contain "a field that indexes norms or doc values" (:38-41).
  2. What count() returns. count (:222-274) checks norms first and uses only the safe shortcut there (getDocCount(field) == maxDoc, :231-237). For a doc-values field without a skip index on a leaf without deletions (:247), the code says "No deletions: we can use points or terms doc count as a proxy for doc values" (:248) and an indexed field takes count = (terms == null ? 0 : terms.getDocCount()) (:252-255). Then count == 0 returns 0, count == maxDoc returns numDocs, and any other count of 0 or more is returned as exact ("The computed count can be trusted", :261-270).
  3. Why the shortcut is wrong here. Terms#getDocCount is "the number of documents that have at least one term for this field" (Terms.java:117-121). A tokenized value that produces no tokens adds no term, but the document's doc value of the same name is there; the indexing chain handles a field that "exists in this document, but it did not have any indexed tokens" on purpose (IndexingChain.java:1930-1931). When no document of the leaf has a term, Terms is null and the result is 0.
  4. Where the wrong number goes. IndexSearcher#count runs a TotalHitCountCollectorManager (IndexSearcher.java:491-529), whose leaf collector takes weight.count(context) whenever it is not -1 (TotalHitCountCollector.java:48). BooleanWeight#count composes clause counts: a FILTER clause's 0 makes the conjunction 0 (BooleanWeight.java:206-231), and under MUST_NOT the result numDocs - prohibitedCount comes out too high (:196).
  5. What is sound. The points shortcut (every point field instance indexes a point), the skip-index branch (:244-246, an exact DocValuesSkipper#docCount), and the rewrite to MatchAllDocsQuery (:140-154, only when, on every leaf, the terms, points or skip-index doc count equals maxDoc). An untokenized value (StringField) always yields exactly one term, so the shortcut is exact for keyword fields, the shape it was written for.

The numbers

#

Two documents, title = "" and title = "hello", each with a SortedDocValuesField("title", ...), norms omitted: 2 hits, count 1. When the only titled document of the segment is blank: 1 hit, count 0. The unbounded range SortedDocValuesField.newSlowRangeQuery("title", null, null, true, true) rewrites to the exists query: 2 hits, count 1. Stop-words-only values over 3 segments: 6 hits, count 3. #exists #id:1 on a segment where no document has a term: 1 hit, count 0. +*:* -exists over "", "hello" and a document without a title: 1 hit, count 2.

Exposure and likelihood254 words
  • Who is hit. A tokenized indexed field with omitNorms(true) and a doc-values field of the same name (SortedDocValuesField, SortedSetDocValuesField, NumericDocValuesField, ...) without a skip index, for example to sort or facet on the same name. Values that analyze to no tokens are ordinary data: empty strings, whitespace or punctuation only, stop words only with a stop filter. Default IndexWriterConfig, codec and IndexSearcher. The field shape is an opt-in choice.
  • What is wrong. Counts only: IndexSearcher#count, TotalHitCountCollector(Manager), BooleanQuery counts built from the clause (too low under FILTER, too high under MUST_NOT), and unbounded doc-values range queries that rewrite to FieldExistsQuery. Hit lists, top-k totalHits and CheckIndex are fine.
  • Scale. Per segment without deletions the count misses every zero-token document; a segment whose titled documents are all empty counts 0. Segments with deletions scan and are right.
  • Not affected. Fields with norms (from 9.2.0), keyword fields such as StringField, point fields, and doc values with a skip index from 10.5.0.
  • Workarounds today. Keep norms on the text field; or give the doc-values field a skip index (10.5.0 and later; that branch runs first and is exact); or use different names for the text field and the doc-values field (a doc-values-only field has no terms shortcut and is scanned; from the code, not run).
  • Elsewhere. Elasticsearch hit the same mechanism in its own count shortcut (elastic/elasticsearch#89760: 3 total hits for 4 hits on an exists query with an empty string) and fixed it there in #90341.

Why it looks unintended

#
  • Weight#count must return "the number of live documents that match"; here the same query scores 2 documents and counts 1.
  • Lucene dropped the same shortcut from the norms branch in #477 because empty-token documents "don't show up in Reader.getDocCount(field)".
  • Nothing limits the count to untokenized fields, and the index passes CheckIndex.
The full argument297 words
  • Contract. Weight#count: "Counts the number of live documents that match a given Weight#parentQuery in a leaf"; overrides should "provide other accurate sub-linear implementations (that actually return the count)" (Weight.java:181-198). IndexSearcher#count: "Count how many documents match the given query" (IndexSearcher.java:491-494). Terms#getDocCount: "the number of documents that have at least one term for this field" (Terms.java:117-121).
  • The query disagrees with itself. The match set is the query's own doc-values iterator (FieldExistsQuery.java:188-209), not an outside idea of what "exists" means.
  • The twin was treated as a bug. In #477 (LUCENE-10263, 2021, eleven days after #445) jpountz pointed out that zero-token values get a norm "while they wouldn't count as part of Terms#getDocCount which only includes documents that have at least one term", and the norms shortcut was limited to docCount == maxDoc. The upstream test still says "docs that have a text field that analyzes to an empty token stream still have a recorded norm value but don't show up in Reader.getDocCount(field), so we can't use the shortcut for these fields" (TestFieldExistsQuery.java:577-580) and asserts -1 there. The doc-values branch from #445 was not revisited.
  • History. #445's issue based the shortcut on per-field schema consistency (#10374, LUCENE-9334); the review suggested it "for keyword fields"; its test covers the terms shortcut only with StringField + SortedDocValuesField (and the points shortcut with LongPoint + NumericDocValuesField). Nothing in #445 discusses tokenized fields or values without tokens. In #16111 (2026) the author raised the empty-token caveat ("docs can have norms without postings when analyzer produces empty token stream") and concluded "the unified logic works for vectors/docValues/points/terms, but norms still only use the maxDoc shortcut".
  • Legal input. IndexWriter accepts the field shape and the values, and the index passes CheckIndex.
The devil's-advocate check158 words

The strongest case for "intended": the shortcut was a reviewed optimization for keyword fields; LUCENE-9334 makes a field use the same data structures in every document; in #477 a maintainer argued that zero-token values are an analysis-chain problem ("If you want tokens, index your data correctly"); and testDocValuesQueryMatchesCount (TestFieldExistsQuery.java:347) pins the O(1) count, so maintainers could document a limit instead. The works-as-designed reviewer rated this "moderate".

Why it fails: LUCENE-9334 checks which data structures a field uses per document, not that each document produces a term, and the indexing chain handles the zero-token case on purpose; no javadoc, CHANGES or MIGRATE entry limits the count to untokenized fields; the same argument did not keep the norms shortcut in #477; and in 2019 jpountz wrote that this optimization is unsafe unless the indexed and the doc-valued documents are the same (elastic/elasticsearch#37475). What is left is a fix trade-off, not an intent argument. Verdict: not intended, a defect.

Suggested fix

#

Recommended A. Trust the terms doc count only when it equals maxDoc (validated)

Use the terms doc count only when it equals maxDoc (every document has a term), like the norms branch, and scan otherwise: 6 lines in FieldExistsQuery.java. The repro then passes, and so does org.apache.lucene.search (2,351 tests) after one testDocValuesQueryMatchesCount assertion is relaxed. Trade-off: keyword fields that only some documents have lose the O(1) count.

Four options. A was built and validated on main 5adff78bb168; B was run only as a cause check; C and D were not built.

A. Trust the terms doc count only when it equals maxDoc (validated) (recommended)

#

In the doc-values branch, use Terms#getDocCount only to show that every document of the leaf has the field, the rule the norms branch already follows since #477. Otherwise count stays -1 and IndexSearcher#count collects the hits. The points and skip-index branches are unchanged.

} else if (fieldInfo.getIndexOptions() != IndexOptions.NONE) {
  // Terms#getDocCount only counts documents that have at least one term, but a document
  // can have a doc value and no term (a tokenized value that produced no tokens). So it
  // can only show that every document has the field, like the norms shortcut above.
  Terms terms = reader.terms(field);
  if (terms != null && terms.getDocCount() == reader.maxDoc()) {
    count = reader.maxDoc();
  }
}

Trade-offs

  • On deletion-free segments where only some documents have a keyword field (StringField + same-name doc values), the count becomes a scan of the doc-values iterator instead of O(1). Segments where every document has the field keep O(1); users can get O(1) back with a doc-values skip index (10.5.0 on). No benchmark was run.
  • One assertion of an upstream test changes, so this is the maintainers' call.

B. Remove the terms shortcut entirely

#

Delete the three-line branch. As a cause check this made all four tests of the original repro pass on main and on 9.1.0.

Trade-offs

Also drops the safe == maxDoc case: strictly more de-optimization than A.

C. Keep O(1) for keyword fields with an index-time signal

#

FieldInfo does not record whether a field is tokenized, so a read-time fix cannot tell StringField from a norms-free TextField. Recording per segment that every document with the field produced a term, or the number of documents with a doc value, would keep the shortcut exactly where it is sound.

Trade-offs

Needs a format or API change; not built.

D. Keep the shortcut only for IndexOptions.DOCS

#

Would keep StringField (indexed with DOCS) on the O(1) path.

Trade-offs

Not sound: a tokenized field can also be indexed with DOCS and produce no tokens (from the code, not run).

Downstream note

#

From reading Solr's code (not run): SortableTextField indexes analyzed text plus same-name sorted doc values and Solr maps field:* to FieldExistsQuery for doc-values fields, so a SortableTextField with omitNorms may report counts that are too low.

How it was found

#

Code reading while modelling FieldExistsQuery#count's shortcuts in Alloy 6.2 (semi-formal). The model's soundness check has a counterexample at 4 documents only for a tokenized, norms-free field with doc values, and none up to 5 documents once that shape is excluded. An end-to-end JUnit test confirmed it; a differential count-versus-hits check on random indexes finds it too.

The method in full100 words

Method: semi-formal. The hypothesis came from reading FieldExistsQuery#count while building an Alloy 6.2 model of its shortcuts against the query's match set (the scorer's iterator).

  • check countSound (4 documents, 5-bit integers) is satisfiable: the counterexample's field is indexed, tokenized, has doc values and no norms.
  • check countSoundWithoutTokenizedNoNorms (5 documents) is unsatisfiable: with that shape excluded, every shortcut is exact in scope.
  • Vacuity runs show all three exact branches (terms, points, norms) are reachable.
  • An end-to-end JUnit test on the real jars then reproduced it, and a differential check that compares IndexSearcher#count with the collected hits on random indexes rediscovers it.

You expect the count to equal the number of documents the query returns, because the query matches every document that has a doc value.
