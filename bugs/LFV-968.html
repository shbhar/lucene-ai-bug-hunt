QueryParserHelper.setQueryNodeProcessor(null) throws NullPointerException although its javadoc allows null

setQueryNodeProcessor(null) is documented to switch the flexible query parser's processing step off, but on a StandardQueryParser, a PrecedenceQueryParser or any QueryParserHelper it always throws NullPointerException: it stores the null and then calls a method on it. Every release since 2.9.0 (2009) has it.

The finding in 30 seconds

#

The setter stores its argument and then calls a method on it without checking for null; every other place in the class that touches the processor checks first.

Background: the flexible query parser's three phases

#
  1. StandardQueryParser is built on QueryParserHelper, which parses a query string in three phases: a syntax parser turns the text into a tree of query nodes, a processor rewrites the tree, and a builder turns the tree into a Query.
  2. The middle phase is optional. For StandardQueryParser it is a pipeline of 21 processors, among them the analyzer (Foo becomes foo) and the default operator.
  3. setQueryNodeProcessor replaces that processor. Its javadoc says null means no processing, and parse then skips the phase.

The finding, step by step

#
  1. Create new StandardQueryParser(new StandardAnalyzer()): parse("Foo", "f") gives f:foo, because the default processing step runs the analyzer.
  2. Call setQueryNodeProcessor(null). Its javadoc says "The argument can be null, which means that no processor will be used", so you expect parse("Foo", "f") to skip processing and give the raw f:Foo, as a parser built with a null processor in the constructor does.
  3. Instead the call throws NullPointerException ("this.processor" is null) at QueryParserHelper.java:102, with assertions on and off.
  4. Why: line 101 stores the null, and line 102 calls this.processor.setQueryConfigHandler(...) on it. The constructor, setQueryConfigHandler and parse all check for null first; this setter does not.
  5. No query comes out wrong: the field is already null when it throws, so only the exception is wrong. Workaround: build a QueryParserHelper with a null processor in its constructor (StandardQueryParser has no constructor that takes one), or catch the NPE.

Who is affected

#

Code that turns query processing off on an existing parser through this public setter, for example a custom QueryParserHelper that wants raw syntax trees. Every such call fails in the setter itself. Opt-in and rare: the stock parsers never pass null. No query comes out wrong, and code that builds a QueryParserHelper itself can pass null to its constructor.

Mechanism, terms and numbers453 words

The flexible query parser runs three phases: a syntax parser builds a tree of query nodes, an optional processor rewrites it, and a builder turns it into a Query. QueryParserHelper.setQueryNodeProcessor documents that its argument "can be null, which means that no processor will be used to process the query node tree" (QueryParserHelper.java:92-96 at 645d4fe14a20). The body stores the argument (:101) and then calls this.processor.setQueryConfigHandler(getQueryConfigHandler()) without a null check (:102), so the documented call always throws NullPointerException. The constructor (:71), setQueryConfigHandler (:189) and parse (:218) all skip a null processor. StandardQueryParser and PrecedenceQueryParser inherit the setter. The defect dates from the commit that created the class (LUCENE-1567, 2009) and is in every release from 2.9.0 to 10.6.0 and on main. No query comes out wrong: the field is already null when it throws, and code that builds a QueryParserHelper itself can pass null to its constructor instead.

The mechanism (main 645d4fe14a20, QueryParserHelper.java)

#
  1. Three phases, one optional. parse runs the syntax parser (:214), then the processor only if (processor != null) (:216-220), then the builder (:222). The package doc: "at least 2 phases, text parsing and query building, and one optional phase called query processing" (package-info.java:25-26).
  2. Every other entry point handles "no processor". The constructor calls processor.setQueryConfigHandler(queryConfigHandler) only if (processor != null) (:61-74, guard :71); setQueryConfigHandler does the same (:185-192, guard :189); the getter documents a null result "if no processor is used" (:76-87).
  3. The setter forgets the guard (:100-103), right under the javadoc that allows null (:89-99):
public void setQueryNodeProcessor(QueryNodeProcessor processor) {
  this.processor = processor;                                   // :101
  this.processor.setQueryConfigHandler(getQueryConfigHandler()); // :102  NPE when processor == null
}
  1. The state is already right when it throws. Line 101 runs first, so afterwards getQueryNodeProcessor() is null and parse("Foo", "f") gives f:Foo, exactly the documented no-processor parser. Only the exception is wrong.
  2. Who inherits it. StandardQueryParser extends QueryParserHelper (StandardQueryParser.java:231) and PrecedenceQueryParser extends StandardQueryParser (PrecedenceQueryParser.java:35); neither overrides the setter. The only callers in the Lucene tree are the two PrecedenceQueryParser constructors, which pass a new non-null pipeline (:41, :50); no test calls the setter (tests do assume the default pipeline: TestQPHelper.java:165 casts getQueryNodeProcessor() to QueryNodeProcessorPipeline).

Exposure and likelihood251 words
  • Who is hit. Applications that switch the processing phase off on an existing parser through setQueryNodeProcessor(null): a custom QueryParserHelper that builds the raw syntax tree, or code that swaps processors and clears one. It fails every time, deterministically, in the setter itself, whether or not the parser has parsed queries before.
  • Default vs opt-in. Opt-in and rare. StandardQueryParser and PrecedenceQueryParser never pass null. For StandardQueryParser, turning processing off switches off all 21 processors of its pipeline: analysis and the default operator, and also wildcard, regexp, fuzzy, range, point, multi-field, phrase-slop, boost, rewrite-method and interval handling and the tree clean-ups; StandardQueryTreeBuilder says it "should be used" on a tree processed by that pipeline (StandardQueryTreeBuilder.java:45-48). So it is an unusual setup, not a general raw-parser mode, and the runs here cover only the single-term query Foo. GitHub searches of Elasticsearch, OpenSearch and Solr found no use of setQueryNodeProcessor.
  • Effect. A loud NullPointerException: no wrong query, no index or data effect, constant cost. The harm is a documented call that cannot be used, and a confusing NPE for the user who followed the javadoc.
  • Workaround. Code that builds a QueryParserHelper itself (or a subclass that calls super(...)) can pass null as the processor to its four-argument constructor. StandardQueryParser and PrecedenceQueryParser have no constructor that takes a processor, so their users build new QueryParserHelper(new StandardQueryConfigHandler(), new StandardSyntaxParser(), null, new StandardQueryTreeBuilder()) instead (executed: parse("Foo", "f") = f:Foo). Or catch the NPE (the field is already set).

Why it looks unintended

#
  • The setter's javadoc and @param both say null is allowed and means no processing; the getter documents null as "no processor is used".
  • The constructor, setQueryConfigHandler and parse all skip a null processor; the package doc calls processing optional.
  • Where the class refuses null (setSyntaxParser, setQueryBuilder), it says "cannot be null" and throws IllegalArgumentException, not an NPE.
The full argument246 words
  • The contract allows null twice and says what it means: "The argument can be null, which means that no processor will be used to process the query node tree" (QueryParserHelper.java:92-93) and "@param processor ... this argument can be null" (:95-96). The getter: "it returns null if no processor is used" (:77-78).
  • The package design makes processing optional: "one optional phase called query processing" (package-info.java:25-26); "Second (optional) Phase: Query Processing" (:36); "This phase is optional" (:41).
  • The class handles null everywhere else: constructor (:71), setQueryConfigHandler (:189), parse (:218).
  • Null handling was chosen setter by setter: setSyntaxParser and setQueryBuilder document "cannot be null" (:106-107, :123-124) and throw IllegalArgumentException (:115-117, :132-134); setQueryConfigHandler documents "It can be null" (:177-178) and accepts it.
  • Tests and history: no test passes null to the setter or asserts the NPE, and no CHANGES or MIGRATE entry names it. The javadoc, the unguarded call and the guarded constructor were written in the same commit, 343992fcbb4 (LUCENE-1567, 2009); later commits never changed the setter's code or the wording of its javadoc: one renamed getTextParser to getSyntaxParser (565a6d22b5f, LUCENE-1792, 2009-08-19, before 2.9.0); the others moved the file, edited its license header and javadoc HTML, or reformatted it (last: LUCENE-9570, 2cbf261032d, 2021, which only reflowed the setter). No discussion (#2641, #2856, #14168) accepts the NPE.
The devil's-advocate check127 words

Strongest case (from the intended-behaviour checker): the javadoc is stale on an expert hook; no caller or test has passed null in 17 years and nobody reported it; Lucene often treats null arguments as caller errors; the constructor is a workaround (for code that builds the helper itself); so the docs, not the code, should change.

Why it fails: the permission is repeated in the @param, matched by the getter's documented state and the package's "optional phase", and implemented by the class's three other code paths. Where the authors wanted to refuse null, they said so and threw IllegalArgumentException. A doc-only change would leave the constructor, the getter, parse and the package doc saying the opposite. The cross-model reviewer rated the intended argument weak.

Suggested fix

#

Recommended Guard the call, as the constructor does

Add the null check the constructor already has: if (processor != null) processor.setQueryConfigHandler(getQueryConfigHandler()); (+3/-1 lines, one file). With it the minimal test passes with assertions on and off, and the whole lucene/queryparser suite runs clean (534 tests, 0 failures).

public void setQueryNodeProcessor(QueryNodeProcessor processor) {
  this.processor = processor;
  if (processor != null) {
    processor.setQueryConfigHandler(getQueryConfigHandler());
  }
}

Guard the call, as the constructor does (validated by the checks) (recommended)

#

In setQueryNodeProcessor (QueryParserHelper.java:100-103), call setQueryConfigHandler only when the new processor is not null.

public void setQueryNodeProcessor(QueryNodeProcessor processor) {
  this.processor = processor;
  if (processor != null) {
    processor.setQueryConfigHandler(getQueryConfigHandler());
  }
}

Trade-offs

None found. The setter then does what its javadoc says and matches the constructor (:71-73) and setQueryConfigHandler (:189-191); a non-null argument is configured as before in single-threaded use (the fix calls the method on the parameter, which line 101 has just stored in the field; the class has no synchronisation either way).
