Multi-threaded CheckIndex can throw "Comparison method violates its general contract!" instead of reporting a segment with a missing file

When one segment has lost a file, multi-threaded CheckIndex (the default on multi-core machines) can throw IllegalArgumentException "Comparison method violates its general contract!" instead of reporting that segment. Its size sort calls the unreadable segment equal to every other one, which Java's sort may reject from 32 segments on.

The finding in 30 seconds

#

Before checking segments in parallel, CheckIndex sorts them by size, so that small segments print first. A segment with a missing file has no readable size, and the sort's comparator then calls it equal to every segment. That is not a consistent order, and Java's sort may throw instead of sorting.

  1. Commit 32 small segments holding 1, 2, ..., 16, then again 1, 2, ..., 16 documents (769 to 930 bytes each). Delete one file: _k.fdt, the stored-fields data of segment _k (5 documents).
  2. Run CheckIndex with 2 threads (setThreadCount(2), or the default on any machine with 2 or more CPUs). You expect a Status with numBadSegments = 1 naming _k: with one thread you get exactly that, NoSuchFileException: _k.fdt, 5 documents to lose.
  3. Before checking in parallel, CheckIndex sorts the segments by size. _k's size cannot be read, so the comparator answers "equal" for _k against every segment: _0 (769 bytes) equals _k, _k equals _f (930 bytes), yet _0 is smaller than _f.
  4. Java's sort notices the contradiction while merging and throws IllegalArgumentException: Comparison method violates its general contract!. It escapes checkIndex() before any segment is checked: no Status, and -exorcise cannot run.
  5. Below 32 segments the sort never throws; at 32 to 200 it throws for about 1-30% of the size orders simulated, so a given index may pass. The failure is loud, and -threadCount 1 gives the correct report.

Who is affected

#

Anyone who checks an already damaged index with more than one thread: the default checkIndex() and the command-line tool on any machine with 2 or more CPUs. It needs 32 or more segments and a size order the sort detects. Loud, nothing written, and -threadCount 1 gives the correct report. Every release since 8.11.0; rare, so priority Low.

Mechanism, terms and numbers552 words

With more than one thread (threadCount > 1, the default availableProcessors(), CheckIndex.java:541), CheckIndex.checkIndex first sorts a copy of the commit's segments by SegmentCommitInfo.sizeInBytes() (:856-869). When one segment refers to a file that is missing, sizeInBytes() throws on every call (it caches only on success, SegmentCommitInfo.java:270-280, and CheckIndex reads the commit fresh), and the comparator catches the IOException, logs it and returns 0. The broken segment then compares equal to every other segment, which breaks the Comparator contract, and with 32 or more segments List.sort can throw IllegalArgumentException: Comparison method violates its general contract! (:858). The exception leaves checkIndex() before any segment is checked, so there is no Status and the command line's -exorcise cannot run; the same index checked with one thread reports one bad segment. It needs an already damaged index, 32 or more segments and a size order the sort detects (about 1-30% of simulated orders), it is loud and writes nothing, and -threadCount 1 is a full workaround, so it is Low. It has been there since the multi-threaded check was added (LUCENE-9662, first released in 8.11.0 and 9.0.0) and is on main. Reading each size once and sorting on that fixed key fixes it.

Terms

#
  • CheckIndex reads every segment of a commit and returns a Status: which segments are broken, why, and how many documents -exorcise would drop to repair the index. With threadCount > 1 it checks segments in parallel; the default is the number of CPUs (CheckIndex.java:541), and setThreadCount(1) / -threadCount 1 checks them one by one.
  • SegmentCommitInfo.sizeInBytes() adds up the length of every file of a segment and caches the sum only when every length could be read (SegmentCommitInfo.java:270-280). If one file is missing, it throws NoSuchFileException on every call: CheckIndex reads the commit fresh (CheckIndex.java:680, :720), so no size is cached yet.
  • The Comparator contract requires that compare(x, y) == 0 implies signum(compare(x, z)) == signum(compare(y, z)) for all z (JDK Comparator javadoc). List.sort may throw IllegalArgumentException when it finds a comparator that breaks it.

The bug

#
// CheckIndex.java, main 5adff78bb168, concurrent branch
segmentCommitInfos.sort(                                                          // :858
    (info1, info2) -> {
      try {
        return Long.compare(info1.sizeInBytes(), info2.sizeInBytes());            // :861
      } catch (IOException e) {
        msg(infoStream, "ERROR: IOException occurred when comparing SegmentCommitInfo file sizes");
        if (infoStream != null) e.printStackTrace(infoStream);
        return 0;                                                                 // :867
      }
    });
  1. checkIndex() takes this branch whenever threadCount > 1 (:588-600); so does the command-line tool (:4896) and checkIndex(onlySegments, executor).
  2. For the segment _k whose .fdt is missing, every call to sizeInBytes() throws, and the comparator answers 0. With _0 = 769 bytes and _f = 930 bytes it says _0 == _k and _k == _f, but _0 < _f.
  3. The JDK's TimSort sorts fewer than 32 elements by binary insertion without merges and never notices. From 32 elements on it merges runs, and for some size orders the merge finds the contradiction and throws IllegalArgumentException: Comparison method violates its general contract!.
  4. The sort runs before any segment is checked and outside testSegment's catch (Throwable) (:1200-1211), so the exception leaves checkIndex(). The one-thread branch never sorts: it reads the size inside testSegment's try (:1033) and records the segment as broken.
Exposure and likelihood206 words
  • Who is hit. Anyone who checks an index that is already damaged (a segment file lost through a bad copy, restore or external deletion) with more than one thread: the default checkIndex() and the command-line tool on any host with 2 or more CPUs, setThreadCount(n > 1), or checkIndex(onlySegments, executor).
  • Default vs opt-in. Default settings; the class is tagged @lucene.experimental (CheckIndex.java:110).
  • Effect. A wrong error instead of the report: no Status, so no list of broken segments and no document count, and -exorcise cannot run. With an infoStream the NoSuchFileException naming the file is still printed (13 to 27 times on 32 segments), the command line exits 1, and the index is not changed.
  • Scale. 32 or more segments, plausible for a production index, especially during heavy indexing or with a custom merge policy; below 32 it never shows.
  • Likelihood: rare. It needs prior damage and a size order the sort detects: in sort-only simulations of the comparator, none below 32 elements, 9.8-30.2% of random orders and 1.4-20.9% of two synthetic, mostly descending layouts at 32 to 200 (no real merge policy was run). No matching report was found in the recorded searches, although the code has shipped since 8.11.0 (2021).

Why it looks unintended

#
  • Every checkIndex overload "Returns a Status instance detailing the state of the index"; the class exists to find "problematic segments".
  • The one-thread check reports this exact damage as 1 bad segment; Lucene's test framework checks with one thread and with 2-5.
  • The comparator's own catch logs the error and carries on: the authors meant to survive an unreadable size.
The full argument266 words
  • The contract. "Basic tool and API to check the health of an index and write a new segments file that removes reference to problematic segments" (CheckIndex.java:104-105); "Returns a Status instance detailing the state of the index" (:570, :582, :619); the executor overload exists to "speed up the check" (:621), not to change the answer.
  • The intent in the code. The comparator's catch logs the IOException and continues (:862-867), and the ExecutionException handler asserts failFast (:922): with failFast off, the concurrent path is meant to return a Status.
  • Tests exercise both modes. Lucene's test framework checks with a random 2-5 threads in TestUtil.checkIndex(dir) (TestUtil.java:302-331) and with one thread in MockDirectoryWrapper's check on close (MockDirectoryWrapper.java:913-917, to avoid a deadlock), and fails the test on any problem either reports (TestUtil.java:334-337); no test compares the two modes on a damaged index. TestCheckIndex deletes a segment file (_0.si) and expects a not-clean Status (TestCheckIndex.java:295-300).
  • History. The sort and its return 0 came with LUCENE-9662 (#128). The review comments on the sort itself are about the order (which segments to start first, by size or by document count); no review comment addresses the comparator's IOException fallback or what it does to the sort. rmuir wrote there, about the output of the parallel check, "If checkindex fails it is really important that we can read this output", and asked for the change to be "done in a more cautious/defensive way" (2021-05-07). The CHANGES entries list the change without caveat.
The devil's-advocate check127 words

The strongest case: the input is a damaged index, and SECURITY.md says "Modifying, corrupting, or crafting index files can cause undefined behavior such as ... other runtime exceptions ... This is by design"; CheckIndex is experimental, and checkIndex declares IOException anyway.

Why it fails: that sentence is about read paths that skip validation for speed. CheckIndex is the component whose job is to examine damaged indexes, its one-thread mode reports this exact damage, and the comparator's catch shows the authors meant to survive it. SECURITY.md itself welcomes changes that replace "a low-level failure with a clean CorruptIndexException on a broken index", and the fix costs one size read per segment, once per check. An executed review by another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Read each segment's size once, then sort on that fixed key

Read each segment's size once (0 when it cannot be read), then sort on that fixed key: a consistent order, so the sort cannot throw, and the segment's own check still reports the damage. Validated: the repro and the 214 org.apache.lucene.index test classes of :lucene:core pass with assertions on and off, as does :lucene:core:check -x test.

Map<SegmentCommitInfo, Long> sizes = new HashMap<>();
for (SegmentCommitInfo sci : segmentCommitInfos) {
  long size;
  try {
    size = sci.sizeInBytes();
  } catch (IOException e) {
    msg(infoStream, "ERROR: IOException occurred when reading SegmentCommitInfo file sizes");
    if (infoStream != null) e.printStackTrace(infoStream);
    size = 0;
  }
  sizes.put(sci, size);
}
segmentCommitInfos.sort((info1, info2) -> Long.compare(sizes.get(info1), sizes.get(info2)));
All options and trade-offs3 options · 558 words

Validated with gradle in a clean scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-03): the repro fails stock with assertions on and off, and passes with the first option, on and off. The second option was run with the repro and TestCheckIndex only.

Both options make the sort key a fixed value per segment, so the order is consistent (what the Comparator javadoc calls a total ordering; equal keys simply compare equal) and the sort cannot throw; the broken segment is still checked and reported by testSegment. A separate bug in the same sort (with more than one thread, -exorcise writes the surviving segments in size order, LFV-640) needs its own change in the result loop.

Read each segment's size once, then sort on that fixed key (validated by the checks) (recommended)

#

Before the sort, read sizeInBytes() once per segment into a map (log the IOException and use 0 when it throws), then sort with Long.compare on the map's values.

Map<SegmentCommitInfo, Long> sizes = new HashMap<>();
for (SegmentCommitInfo sci : segmentCommitInfos) {
  long size;
  try {
    size = sci.sizeInBytes();
  } catch (IOException e) {
    msg(infoStream, "ERROR: IOException occurred when reading SegmentCommitInfo file sizes");
    if (infoStream != null) e.printStackTrace(infoStream);
    size = 0;
  }
  sizes.put(sci, size);
}
segmentCommitInfos.sort((info1, info2) -> Long.compare(sizes.get(info1), sizes.get(info2)));

Trade-offs

Keeps the intended size order, and logs an unreadable size once per segment instead of once per comparison (today 13 to 27 times on 32 segments). A broken segment sorts as the smallest, so it is started last and printed first.

Sort by maxDoc(), which cannot throw (validated by the checks)

#

segmentCommitInfos.sort(Comparator.comparingInt(info -> info.info.maxDoc())); (CheckIndex.java then also needs java.util.Comparator). mikemccand suggested a document-count order in the #128 review (2021-05-31: "We should maybe sort the segments by descending docCount").

segmentCommitInfos.sort(Comparator.comparingInt(info -> info.info.maxDoc()));

Trade-offs

The smallest diff and no file I/O in the sort. Document count is only a proxy for size (a segment with few large documents is scheduled as small), and the sort no longer logs the unreadable size (the segment's own check still prints it).

What the checks validated

With gradle in the same scratch worktree: the repro and TestCheckIndex pass (10 tests, 0 failures), assertions on; a fact-check re-run with assertions off: the same.

Variant of the first option, not run: a fixed key inside the comparator

#

Keep the comparator, but map an unreadable size to a fixed value (for example 0) instead of returning 0 for the comparison.

Trade-offs

Also consistent, but every comparison that involves the unreadable segment reads its file lengths and logs the error again (healthy segments use their cached size).

Downstream note

#

A downstream check or repair command that calls checkIndex() with more than one thread gets this exception instead of the bad-segment report on such an index; setThreadCount(1) avoids it.

How it was found

#

A proof-obligation audit of CheckIndex's contract took "the multi-threaded check returns the same Status as the one-threaded check" as an obligation. The size sort's comparator returns 0 when a size cannot be read, which breaks the sort's consistency requirement. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full152 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for the same index, checkIndex() with threadCount > 1 returns the Status the one-thread check returns (CheckIndex.java:570, :621); for a segment with a missing .fdt, that is one bad segment.
  • The concurrent branch adds one step the sequential branch does not have, the size sort (:856-869), outside the per-segment catch. Its comparator must be consistent for List.sort; returning 0 for an unreadable size makes the broken segment equal to every segment, which is not.
  • A one-test JUnit witnessed it on main with assertions on and off, and a one-thread control showed the expected answer. An independent reproducer and an executed review by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier and an adjudication re-ran the repro.

Summary
You run CheckIndex on an index of 32 segments in which one segment's stored-fields data file (.fdt) has gone missing, with the default thread count on a multi-core machine (or setThreadCount(2)). You expect a Status that reports that one segment as broken (numBadSegments = 1, with the NoSuchFileException as its error), as the same check with one thread returns, so that you can then exorcise it. Instead checkIndex() throws java.lang.IllegalArgumentException 'Comparison method violates its general contract!' from the sort that orders the segments by size before the concurrent check: its comparator calls sizeInBytes(), which throws for the damaged segment on every call, and then answers 'equal', so that segment is equal to every other segment, the order is not consistent, and the exception escapes checkIndex().
