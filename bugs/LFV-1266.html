AbstractAnalysisFactory.splitAt throws PatternSyntaxException for the separators '^' and '[' instead of splitting the list

A custom analysis factory that calls the inherited helper splitAt('^', "a^b") gets PatternSyntaxException: Unclosed character class instead of [a, b], because splitAt pastes the separator unquoted into a regex [...] class. Only '^', '[' and backslash fail, and no Lucene factory uses them.

The finding in 30 seconds

#

Analysis factories get their settings as strings. A setting that holds a list is split with a helper of the base class AbstractAnalysisFactory: splitAt(separator, list), where a backslash escapes the separator. The helper turns the separator into a regular expression, and for three chars that expression is invalid.

List settings in one minute

#
  1. A factory gets its settings as a Map<String, String>, for example {words=stop1.txt,stop2.txt}, from CustomAnalyzer or TokenFilterFactory.forName(name, args).
  2. To split a list setting, the factory calls a protected helper of AbstractAnalysisFactory: splitFileNames(list) for commas, or splitAt(separator, list) for any other char.
  3. A backslash keeps a separator inside an item: the list a,b\,c split at ',' gives [a, b,c].

The finding, step by step

#
  1. You write a custom TokenFilterFactory whose constructor splits a list setting with the protected helper it inherits from AbstractAnalysisFactory: splitAt('^', "a^b").
  2. You expect [a, b], the result you get with ',', '.', '|', '*', '$' or ']' as the separator.
  3. Instead it throws PatternSyntaxException: Unclosed character class near index 9. splitAt builds the regex "(?<!\\\\)[" + separator + "]", here (?<!\\)[^]: [^ starts a negated class, the ] right after it counts as a literal, and the class never closes.
  4. It throws for every non-null list, even "ab". In a sweep of all 65,536 char separators (two inputs each) exactly 3 fail, '^', '[' and backslash, and none mis-splits. Lucene's own factories pass only ',' and '.'; every release since 7.4.0 (2018) is affected.

Who is affected

#

Only custom or third-party factories whose own code calls the protected splitAt with '^' or '[' (or backslash). No Lucene factory does: the in-tree callers pass only ',' and '.'. Such a factory throws on its first splitAt call with a non-null list (in its constructor, inform() or create()), with a message that shows an internal regex; nothing mis-splits silently.

Mechanism, terms and numbers416 words

AbstractAnalysisFactory, the base class of every TokenizerFactory, TokenFilterFactory and CharFilterFactory, has a protected helper splitAt(char separator, String list) that splits a factory setting into items, with a backslash escaping the separator. It builds its regex by pasting the separator, unquoted, into a character class: list.split("(?<!\\\\)[" + separator + "]") (AbstractAnalysisFactory.java:353). For '^' the pattern is (?<!\\)[^], which does not compile, so splitAt('^', "a^b") throws java.util.regex.PatternSyntaxException: Unclosed character class near index 9 instead of returning [a, b]. '[' and backslash fail the same way; on both sweep inputs the other 65,533 chars split correctly and none mis-splits. No Lucene factory is affected (the in-tree callers pass only ',' and '.'); only custom factories that pick one of these separators are, and they fail loudly on the first call. Present since splitAt was added in LUCENE-8273 (first released in 7.4.0, 2018). Fix: quote the separator with Pattern.quote.

The code

#
// AbstractAnalysisFactory.java, main 5adff78bb168
protected final List<String> splitAt(char separator, String list) {                  // :349
  if (list == null) return Collections.emptyList();
  List<String> result = new ArrayList<>();
  for (String item : list.split("(?<!\\\\)[" + separator + "]")) {                    // :353
    result.add(item.replaceAll("\\\\(?=[" + separator + "])", ""));                   // :354
  }
  return result;
}

Why three chars break it

#
  1. The split regex means "the separator, when not preceded by a backslash": a negative lookbehind (?<!\\) and a one-char class [c]. Inside [...] most regex metacharacters are literal (., |, *, $, even a leading ]), which is why 65,533 separators work.
  2. Three chars are still special inside a class. '^' gives [^]: [^ opens a negated class and the ] right after it is a literal, so the class never closes. '[' gives [[]: the inner [ opens a nested class. Backslash gives [\]: \] is an escaped ].
  3. All three throw PatternSyntaxException: Unclosed character class near index 9 when String.split compiles the pattern at :353, before it looks at the input, so even a list without the separator ("ab") throws. The unescape regex at :354 splices the char the same way; the split throws first.

Why it looks unintended

#
  • splitAt(char separator, String list) accepts any char; its javadoc excludes none and never mentions regular expressions.
  • Wrapping the char in [...] makes it literal for ., |, *, $, ] and 65,528 more chars; only the three that are special inside a class fail.
  • No test, CHANGES entry or comment on the introducing issue #9320 excludes a separator.
The full argument194 words
  • The contract excludes no separator. The signature takes any char; the javadoc (AbstractAnalysisFactory.java:341-348) says "Splits a list separated by zero or more given separator characters. List items can contain comma characters escaped by backslash" and never mentions regular expressions. (The wording is stale, a leftover of splitFileNames: the code splits on one separator and unescapes that separator, not commas. Fix it in the same change.)
  • The code strongly suggests that any char was meant to work. LUCENE-8273 (d91273ddf0b, Steve Rowe, 2018) turned splitFileNames' fixed comma regexes (?<!\\), and \\(?=,) into splitAt(char, ..) and wrapped the char in [...]. That makes every regex metacharacter literal except the three that are special inside a class.
  • No text says otherwise. No javadoc, test, CHANGES or MIGRATE entry, or comment on #9320 (all 87 comments fetched and searched, the relevant ones read in full) records an excluded separator or discusses quoting; no upstream test calls splitAt.
  • AbstractAnalysisFactory is the documented extension base. It is a public abstract class with no @lucene.internal or @lucene.experimental tag, and splitAt is protected so that subclasses can call it (:41-54, :349).
The devil's-advocate check154 words

The case for "not a bug": the factory author's own code chooses the separator, splitAt is a protected helper whose javadoc still speaks of commas, no Lucene factory is affected, no third-party caller was found, the failure is loud on first use, and it has been quiet for more than eight years. Backslash is a defensible exclusion, because it is also splitAt's escape char, so what its escaped form should return is ambiguous.

Why it fails: these points bound the impact (that is why the bug is Low), but none shows intent. Nothing documents a restriction, and '^' is an ordinary separator, not an absurd parameter. The backslash point covers backslash only, so the claim rests on '^' and '['. An executed review by another model family (OpenAI GPT-5.6) rated the intended-behaviour case "weak"; a later fact check by the same model family rated it "moderate", for the protected-helper and no-shipped-caller points.

Suggested fix

#

Recommended A: quote the separator with Pattern.quote (and fix the javadoc)

Quote the separator instead of putting it inside [...]: String quoted = Pattern.quote(String.valueOf(separator)); then split on "(?<!\\\\)" + quoted and unescape with "\\\\(?=" + quoted + ")", and correct the stale javadoc. Validated: the repro passes with assertions on and off, core's analysis tests and all analysis-common tests pass, and :lucene:core:check -x test is clean.

+    String quoted = Pattern.quote(String.valueOf(separator));
+    for (String item : list.split("(?<!\\\\)" + quoted)) {
+      result.add(item.replaceAll("\\\\(?=" + quoted + ")", ""));

A: quote the separator with Pattern.quote (and fix the javadoc) (validated by the checks) (recommended)

#

Build both regexes around Pattern.quote(String.valueOf(separator)) instead of "[" + separator + "]"; java.util.regex.Pattern is already imported. In the same change, the javadoc says "Splits a list at the given separator character. List items can contain the separator character escaped by backslash" and documents @param separator (+6/-5 in AbstractAnalysisFactory.java with the javadoc, two code lines changed and one added).

     List<String> result = new ArrayList<>();
-    for (String item : list.split("(?<!\\\\)[" + separator + "]")) {
-      result.add(item.replaceAll("\\\\(?=[" + separator + "])", ""));
+    String quoted = Pattern.quote(String.valueOf(separator));
+    for (String item : list.split("(?<!\\\\)" + quoted)) {
+      result.add(item.replaceAll("\\\\(?=" + quoted + ")", ""));
     }

Trade-offs

The smallest change, with the same regex structure. On the all-chars sweep, every separator that works today gives the same correct result, and '^' and '[' now split. Backslash then splits a plain list (p\q gives [p, q]), but its escaped form stays ambiguous (p\\q gives [p, \q]), because backslash is also the escape char; a maintainer may prefer to reject it explicitly. The fix only replaces the one-char class [c] with the quoted literal c, which match the same single char for every separator that works today; so it keeps today's handling of empty items, trailing empty items (dropped by String.split) and runs of backslashes, which the javadoc does not define and the sweep did not test.

B: split with a small char loop (not run)

#

Walk the string once, cut at each separator not preceded by a backslash, and drop a backslash that precedes a separator.

Trade-offs

No regex at all, so no pattern compilation on every call, but more code, and the loop must reproduce today's escape rules exactly (a backslash is removed only before a separator; other backslashes stay).

Not recommended: document that '^', '[' and backslash are not allowed

#

Add the restriction to the javadoc and leave the code.

Trade-offs

Keeps a trap that the two-line fix removes, and the exception would still show an internal regex instead of naming the setting.

Downstream note

#

Downstream projects that ship custom factories built on splitAt should avoid '^', '[' and backslash as separators on affected versions; the list text itself never becomes part of the regex.

How it was found

#

A proof-obligation audit of AbstractAnalysisFactory's contract: splitAt must split a list on any given char separator and unescape a backslash-escaped separator. The regex it builds fails that obligation for three chars. A one-test JUnit witnessed it on main, a sweep over all 65,536 chars bounded it, and independent checks reproduced it with their own tests.

The method in full160 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro, supported by a bounded comparison over every char separator), on main 5adff78bb168, 2026-11-03.

  • The obligation: for every char separator c, splitAt(c, x + c + y) returns [x, y], and splitAt(c, x + "\\" + c + y) returns [x + c + y]. The code discharges it only if "[" + c + "]" is a one-char class that matches exactly c, which fails for ^, [ and backslash.
  • A one-test JUnit witnessed it on main with assertions on and off, and on the 10.6.0 and 9.12.3 jars. The sweep checked all 65,536 separators: 65,533 correct, 3 throw, 0 mis-split.
  • An independent reproducer and an executed review by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier reproduced it with its own probe, and an adjudication re-ran the repro with a new seed.
