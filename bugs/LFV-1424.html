The Matches of a disjunction turn a sub-iterator's offset IOException into IllegalArgumentException

When Lucene merges two or more match iterators without positions (MatchesUtils.disjunction, or the Matches of a BooleanQuery or DisjunctionMaxQuery) and an offset read fails, it throws IllegalArgumentException("Failed to retrieve term offset") instead of the declared IOException. Only custom extension code triggers it; 9.11.1 to 10.6.0 and main are affected.

The finding in 30 seconds

#

DisjunctionMatchesIterator merges the matches of several clauses in a priority queue ordered by position. Since 9.11.1, when two matches have no positions, the queue's comparator orders them by character offset. Reading an offset may throw IOException; the queue's LessThan comparator cannot throw it, so it rethrows it as IllegalArgumentException, both while the iterator is built and in next().

Background: the Matches API

#
  1. Weight.matches(leaf, doc) tells you where a query matched inside one document, field by field; highlighters use it. getMatches(field) returns a MatchesIterator that walks the matches, each with a position range and a character-offset range.
  2. A match may have no positions: startPosition() then returns -1 ("positions are not available"). Offsets may be read lazily (as romseygeek explained on #13315), so startOffset() and endOffset() declare IOException.

The finding, step by step

#
  1. You have match iterators that report no positions (startPosition() == -1) and read offsets lazily, say a custom MatchesIterator or a reader wrapper, and merge 2 of them: MatchesUtils.disjunction(List.of(a, b)), or Weight.matches(leaf, doc).getMatches("f") of a 2-clause BooleanQuery.
  2. To return the matches in order, Lucene puts the 2 iterators in a priority queue. Without positions, its comparator compares startOffset() and endOffset() instead. The offset read fails with IOException("offset read failed").
  3. You expect that IOException: startOffset(), MatchesUtils.disjunction, Matches.getMatches and Weight.matches all declare it; in 9.11.0 it reached the caller when the caller read the offset.
  4. Instead you get java.lang.IllegalArgumentException: Failed to retrieve term offset. The comparator is a lambda, which cannot throw a checked exception, so it wraps it; a catch (IOException e) misses it, and the type reads as a caller error.

Who is affected

#

Only applications or plugins whose own match iterators, or reader or codec wrappers, report no positions and do I/O in the offset getters, used under a disjunction, and that catch IOException by type. No Lucene reader throws there. The call still fails, with the IOException as the cause, and returns no result. Priority Low.

Mechanism, terms and numbers568 words

DisjunctionMatchesIterator merges the match iterators of several clauses in a PriorityQueue. Since 9.11.1, when two iterators both report no positions (startPosition() == -1), its comparator orders them by startOffset()/endOffset(). Those getters declare IOException; the comparator is a lambda, so it catches the exception and throws new IllegalArgumentException("Failed to retrieve term offset", e) (DisjunctionMatchesIterator.java:202 on main). The comparator runs while the iterator is built and in next(), both of which declare IOException, as do MatchesUtils.disjunction, Matches.getMatches and Weight.matches. So MatchesUtils.disjunction and the Matches of a multi-clause BooleanQuery or a DisjunctionMaxQuery throw an unchecked IllegalArgumentException with the IOException as its cause, and code that catches IOException misses it. With a single iterator, or with positions, the same failure arrives as IOException. Stock queries can reach the offset comparison, but no Lucene reader does I/O in these offset getters, so only custom extension code makes it fail (a custom match iterator, or a reader or codec wrapper); the call fails rather than returning a result. The wrap came with #13315 (9.11.1); in 9.11.0 the comparator compared positions only, and the IOException reached the caller when it read the offset. The fix carries the IOException out of the comparator in a private wrapper and rethrows it.

Terms

#
  • MatchesIterator (MatchesIterator.java:38-73, @lucene.experimental): next(), startOffset() and endOffset() declare IOException; startPosition()/endPosition() return -1 "if positions are not available".
  • DisjunctionMatchesIterator: the iterator that merges two or more sub-iterators in order. MatchesUtils.disjunction builds it (MatchesUtils.java:144-147), and so does the Matches that MatchesUtils.fromSubMatches returns (MatchesUtils.java:77-86) for BooleanWeight.matches (every required and every matching SHOULD clause, BooleanWeight.java:134-163) and for DisjunctionMaxQuery's weight (DisjunctionMaxQuery.java:122-131). Multi-term and synonym matches over several terms of one document use it too (DisjunctionMatchesIterator.java:124-139).

The bug

#
// DisjunctionMatchesIterator.java:192-213, the constructor (declares IOException)
queue =
    PriorityQueue.usingLessThan(
        matches.size(),
        (a, b) -> {
          if (a.startPosition() == -1 && b.startPosition() == -1) {     // :197 no positions
            try {
              return a.startOffset() < b.startOffset()
                  || (a.startOffset() == b.startOffset() && a.endOffset() <= b.endOffset());
            } catch (IOException e) {
              throw new IllegalArgumentException("Failed to retrieve term offset", e);  // :202
            }
          }
          return a.startPosition() < b.startPosition() || ...;
        });
for (MatchesIterator mi : matches) {
  if (mi.next()) {
    queue.add(mi);                                                      // :210 runs the comparator
  }
}

next() (:216-229, declares IOException) runs the same comparator through queue.pop() and queue.updateTop(). With one sub-iterator no queue is built (fromSubIterators returns it as is, :184); with positions the comparator never reads offsets.

Controls and reach (executed)

#
  • A single offset-only iterator, and two iterators that have positions, pass on main: the same offset failure reaches the caller as IOException when it calls startOffset() (the cross-model reviewer's controls).
  • A stock BooleanQuery of two SHOULD TermQuery clauses on a DOCS_AND_FREQS field, over a FilterDirectoryReader whose postings' offset getters throw IOException, makes Weight.matches(leaf, 0).getMatches("f") throw the same IllegalArgumentException (an independent reproducer's supplementary check, assertions on and off). TermMatchesIterator reports nextPosition(), which is -1 without positions, and delegates startOffset() to the postings (TermMatchesIterator.java:41, :58-60). On such a field stock postings store no offsets and return -1; the wrapper's throw is the trigger, so this shows the public query path, not a failure reading stored offsets.
  • Not claimed: the queue's state after the exception, since seeing it means using the iterator after it threw.
Exposure and likelihood160 words
  • Who is hit: code that supplies match iterators without positions whose offset reads can fail (a custom MatchesIterator, or a reader or codec wrapper whose PostingsEnum.startOffset() reads data), merged by MatchesUtils.disjunction, the Matches of a multi-clause BooleanQuery or a DisjunctionMaxQuery, or a highlighter built on the Matches API, and that handles I/O failures by catching IOException.
  • Default vs opt-in: default codec, searcher and stock queries; the trigger is the custom code, a legal implementation of a public interface.
  • Scale: none: two iterators with one match each.
  • In stock Lucene: no MatchesIterator, postings or term-vectors reader does I/O in startOffset()/endOffset() for matches without positions (postings without positions have no offsets; the default term-vectors reader returns offsets it already decoded), so the comparator's offset branch runs but never throws.
  • Likelihood: contrived. No report of it was found since 9.11.1 (2024). Same pattern and priority as LFV-1222 (a sort comparator that wraps getMaxScore's IOException).

Why it looks unintended

#
  • MatchesIterator allows positions of -1 and declares IOException on startOffset()/endOffset(); MatchesUtils.disjunction, getMatches, Weight.matches and next() declare it too.
  • With one iterator, or positions, the same failure arrives as IOException; only comparing two live position-less iterators wraps it.
  • In 9.11.0 the caller's offset read got the IOException. #13315 added the wrap; its review expected offset I/O; nothing documents the IllegalArgumentException.
The full argument131 words
  • The declared contract. MatchesIterator.java:45, :66, :73; MatchesUtils.java:145; Matches.java:39; Weight.java:78. Nothing documents an IllegalArgumentException, which conventionally signals a caller error; here the caller passed legal arguments to a public method.
  • History. #13315 (d453832bb8d, a fix for unordered matches, #12431) added the offset ordering and the wrap. In its review mikemccand found it "weird that start/endOffset can throw IOException but start/endPosition do not ... Nothing to fix in this PR", and romseygeek answered that offsets are loaded only when asked, "so IO may be involved when calling those methods" (2024-05-21). Nobody discussed the IllegalArgumentException. No javadoc, CHANGES or MIGRATE entry or test mentions it; the message occurs only at :202. #14817 later moved the comparator into a lambda and kept the wrap.
The devil's-advocate check172 words

Strongest argument for "intended": the queue's comparator (PriorityQueue.LessThan, PriorityQueue.java:45-47) cannot throw a checked exception, so some unchecked wrap was forced; the wrap was reviewed on #13315 and kept by #14817; the API is @lucene.experimental; throws IOException does not forbid unchecked exceptions; the cause is kept and the failure is loud; #12516, a similar exception-type change, went under "Changes in runtime behavior".

Why it fails: the review itself expected offset reads to fail with I/O errors, yet nobody chose IllegalArgumentException as the type callers should see, and the enclosing constructor and next() already declare IOException, so the wrapper can be undone before it leaves the class (see Suggested fix). The argument bounds the value of the fix, not the intent. The cross-model reviewer (OpenAI GPT-5.6) rated it moderate; every checker agreed it limits priority only. "Not intended" is still an inference: mikemccand's "Nothing to fix in this PR" was about the offset/position asymmetry, not the exception type, and no maintainer has said either way about the IllegalArgumentException.

Suggested fix

#

Recommended Private comparator-only wrapper, unwrapped in the constructor and next()

Throw a private, comparator-only unchecked wrapper from the comparator, and rethrow its IOException around the queue operations in the constructor and in next(). Callers get the original IOException; nothing else can throw the private type. Validated: the repro passes with assertions on and off; TestMatchesIterator (27 tests), TestUnifiedHighlighterTermVec (6) and :lucene:core:check -x test pass.

} catch (IOException e) {
  throw new OffsetReadException(e);          // was: new IllegalArgumentException(...)
}
...
try {
  for (MatchesIterator mi : matches) {
    if (mi.next()) {
      queue.add(mi);
    }
  }
} catch (OffsetReadException e) {
  throw e.ioe;
}
// next(): the same try/catch around top().next(), pop() and updateTop()
All options and trade-offs2 options · 408 words

Both fixes keep the comparator and the order it produces; they change only the type that leaves the class. Coordinate with open PR #16851, which rewrites the same constructor loop (it already unwraps an UncheckedIOException from a sub-iterator's next() there) and keeps the wrap; with it applied the finder's earlier repro still fails.

Considered, not validated: store each sub-iterator's offsets right after its next() and compare stored values. That moves the offset read out of the comparator but reads offsets eagerly for every match without positions, which the #13315 review says are otherwise loaded only when asked.

Downstream note

#

Downstream products are affected only if their own extension code does I/O in these offset getters; an application that maps IllegalArgumentException to a client error could then report a server-side read failure as a bad request.

How it was found

#

A proof-obligation audit of DisjunctionMatchesIterator's contract asked whether every IOException its comparator can meet reaches the caller as declared, and found the offset branch does not. A public-API JUnit test then witnessed it on main; independent checks reproduced it, two of them with their own tests.

The method in full136 words

The audit walked the exception paths of DisjunctionMatchesIterator (its constructor, next() and the comparator they share) against the throws IOException of MatchesIterator, MatchesUtils.disjunction, Matches.getMatches and Weight.matches. The comparator's offset branch catches the IOException and throws IllegalArgumentException, which breaks that obligation.

The finder's witness was a one-test JUnit class over two hand-written match iterators without positions that builds the disjunction, then iterates and reads offsets; it ran on main with assertions on and off, on the 10.6.0, 9.11.1 and 9.11.0 jars, and with the proposed fix. The shipped test is its minimal form, which only builds the disjunction. An independent reproducer wrote its own test (both iterators failing; build, iterate and read offsets) and a supplementary stock BooleanQuery check; a cross-model reviewer (OpenAI GPT-5.6) wrote and ran its own 5-test class with controls.
