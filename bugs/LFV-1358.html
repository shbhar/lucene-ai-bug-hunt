FlatBitVectorsScorer: scorers of a scorer supplier's copy() still read the original vectors, so HnswBitVectorsFormat's merge workers share one reader

With HnswBitVectorsFormat merging on several threads, each worker gets a copy() of the bit-vector scorer supplier, but its scorers still read the original vectors: the workers share one file position and buffer, so graph-build scores can be wrong. Since 10.2.0; the fix is one line.

The finding in 30 seconds

#

The supplier makes a private copy of the vectors and then never uses it, so the scorers of every copy still read the original.

Background: how a concurrent HNSW merge reads vectors

#
  1. When segments merge, Lucene rebuilds the HNSW graph of a vector field. To pick each node's neighbours it scores pairs of vectors with scorers from a RandomVectorScorerSupplier.
  2. Vectors read from disk carry state: a file position, the last ordinal read and one reused buffer. One such reader must not be used by two threads at once (IndexInput "may only be used from one thread").
  3. With several merge workers (numMergeWorkers > 1), each worker thread gets supplier.copy(), which must copy the vector values so each thread has its own reader.

The finding, step by step

#
  1. You index bit vectors with new HnswBitVectorsFormat(16, 100, 2, executor), so merges build the HNSW graph on 2 threads. Each worker gets its own scorerSupplier.copy(), documented to "copy the underlying vectorValues so the copy is safe to be used in other threads".
  2. You expect each worker to read vectors through its own copy. The repro checks exactly that: a scorer taken from copy(), after setScoringOrdinal(0) and score(1), should have made 0 reads on the original values.
  3. Instead it made 2. The supplier does make a copy, targetVectors = vectorValues.copy(), but never reads it: scorer() uses the original vectorValues, and copy() hands that same instance on.
  4. In a merge the workers then share one reader. In a direct probe, two threads, each on its own copy over a real segment, got 351 of 800,000 scores wrong (0 with the default scorer); a 2-worker merge of 6,000 vectors (one fixed workload) showed no recall loss and no exception.
  5. The default single-thread merge never calls copy() and is not affected. Introduced in 10.2.0 by #14181; up to 10.1.0 copy() copied the values.

Who is affected

#

Only applications that index bit vectors with the codecs module's experimental HnswBitVectorsFormat and turn on multi-threaded merges (numMergeWorkers > 1 with an executor). Every merge of such a field then runs its workers on one shared reader, so build-time scores can be wrong and the graph may differ between runs. Default merges, flush and search are unaffected.

Mechanism, terms and numbers487 words

RandomVectorScorerSupplier.copy() is documented to "copy the underlying vectorValues so the copy is safe to be used in other threads", and the concurrent HNSW merge relies on it: every merge worker gets its own scorerSupplier.copy(). The bit-vector supplier in the codecs module, FlatBitVectorsScorer.BitRandomVectorScorerSupplier, makes that copy in its constructor (targetVectors) and never reads it: scorer() builds on the original vectorValues, and copy() passes the same original on. So when HnswBitVectorsFormat is configured with more than one merge worker, all workers of a merge read through one OffHeapByteVectorValues, with one IndexInput position, one cached ordinal and one reused buffer, so similarity scores used to build the merged graph can come out wrong (a direct two-thread probe on two copies showed it; no merge was caught doing it). The default single-worker merge, flush and search never call copy(). A one-test repro shows the mechanism: a scorer from supplier.copy() makes 2 reads on the original values instead of 0. Introduced by #14181 in 10.2.0, present through 10.6.0 and on main; the fix is one line, scorer() builds on targetVectors, as DefaultFlatVectorScorer already does.

The code (main 5adff78bb168)

#
  1. RandomVectorScorerSupplier.java:32-36: copy() "will copy the underlying vectorValues so the copy is safe to be used in other threads."
  2. HnswConcurrentMergeBuilder.java:155-165: one worker per thread, each created with scorerSupplier.copy() (:158).
  3. FlatBitVectorsScorer.java:111-130 (BitRandomVectorScorerSupplier): the constructor sets vectorValues to its argument and targetVectors = vectorValues.copy() (:115-118); scorer() returns new BitRandomVectorScorer(vectorValues, query) (:123); copy() returns new BitRandomVectorScorerSupplier(vectorValues) (:128). Nothing reads targetVectors.
  4. BitRandomVectorScorer.score (:80-83) and setScoringOrdinal (:91-93) read every vector with vectorValues.vectorValue(node), so all copies read the one original instance.
  5. On disk that instance is an OffHeapByteVectorValues: vectorValue keeps lastOrd and returns one reused buffer (OffHeapByteVectorValues.java:76-82), and readValue seeks and reads one IndexInput slice (:99-102). Two workers can interleave: one seeks, the other seeks elsewhere, the first reads the other's bytes; or one overwrites the buffer while the other scores it. Each can give a wrong score. A real copy would be safe: copy() clones the slice (:154-157).

Exposure and likelihood213 words
  • Who is hit: HnswBitVectorsFormat(maxConn, beamWidth, numMergeWorkers, mergeExec) with numMergeWorkers > 1 and a merge ExecutorService, or with the merge scheduler's intra-merge executor: Lucene99HnswVectorsWriter.createGraphMerger then picks the concurrent merger (Lucene99HnswVectorsWriter.java:668-688). The format is @lucene.experimental (HnswBitVectorsFormat.java:56). Code that calls FlatBitVectorsScorer directly and uses a supplier's copies on several threads is hit the same way.
  • Limits on the trigger: the constructor javadoc says a non-null mergeExec must be passed when numMergeWorkers > 1 (HnswBitVectorsFormat.java:101-102; not enforced). With a null mergeExec the writer falls back to the merge's intra-merge executor (Lucene99HnswVectorsWriter.java:678-687), which ConcurrentMergeScheduler hands out only for merges of at least 50 MB (ConcurrentMergeScheduler.java:276-282).
  • Not hit: the default HnswBitVectorsFormat() (one worker, no executor), flush and search never call copy(). Other vector formats use other scorers; DefaultFlatVectorScorer reads its own copy (DefaultFlatVectorScorer.java:110-142).
  • Effect: possibly wrong similarity scores while neighbours are chosen, so the merged graph may differ between runs and may be slightly worse than intended (inferred from the code path and the probes, not measured). A 2-worker merge of 6,000 vectors showed no recall loss; nothing larger was measured.
  • Not claimed: an exception, recall loss or a read past the end of the slice (none observed).
  • Released: every release from 10.2.0 to 10.6.0.

Why it looks unintended

#
  • RandomVectorScorerSupplier.copy() "will copy the underlying vectorValues so the copy is safe to be used in other threads"; this copy reads the same instance.
  • The supplier makes the copy (targetVectors) but never reads it; DefaultFlatVectorScorer, rewritten in the same commit, reads its targetVectors.
  • Up to 10.1.0 copy() copied the values; #14181 says it "refactors the usage to keep it threadsafe".
The full argument179 words
  • Contract: RandomVectorScorerSupplier.java:32-36, quoted above. KnnVectorValues.copy() exists "to avoid overwriting the underlying vector returned" (KnnVectorValues.java:95-99), ByteVectorValues.vectorValue's array "may be shared across calls" (ByteVectorValues.java:35-41), and IndexInput "may only be used from one thread" (IndexInput.java:28-30).
  • Same commit, other supplier: DefaultFlatVectorScorer.ByteScoringSupplier sets targetVectors = vectors.copy() (:118) and reads it in setScoringOrdinal and score (:129, :134).
  • Review of #14181: msokolov suggested renaming the second values copy to targetVectors (on DefaultFlatVectorScorer), and benwtrent replied "I can happily rename everywhere. We use the same pattern many times." (2025-01-30). The rename landed in FlatBitVectorsScorer, but scorer() stayed on vectorValues. The only review comment on this file is about the query buffer.
  • Tests: TestVectorScorer.testCopiesAcrossThreads ("Tests that copies in threads do not interfere with each other", TestVectorScorer.java:248-249) states the contract for the core scorers. Nothing tests the bit scorer's copy() or a concurrent merge with this format: TestHnswBitVectorsFormat uses only the no-argument and two-argument constructors (plus invalid two-argument values inside expectThrows in testLimits), never the four-argument one or numMergeWorkers > 1.
The devil's-advocate check149 words

The case for intended: the format and FlatVectorsScorer are @lucene.experimental and UpdateableRandomVectorScorer is @lucene.internal; DefaultFlatVectorScorer.ByteScoringSupplier.copy() also passes the same vectors instance on; the default configuration never calls copy(); and no recall loss was measured.

Why it fails: the tags cover API and format stability, not breaking a documented interface contract, and RandomVectorScorerSupplier, whose javadoc states the contract, is not tagged. In ByteScoringSupplier every vectorValue() read goes through its own targetVectors; only dimension, size, ordToDoc and getAcceptOrds touch the shared instance, while the bit supplier routes the stateful reads through it. Reach and severity are limited, but numMergeWorkers > 1 is the documented way to merge on several threads, the shared IndexInput follows from the code, and a direct probe showed wrong scores from two copies used at once. Independent reviewers, including one from another model family (OpenAI GPT-5.6), rated the intended-behaviour case weak.

Suggested fix

#

Recommended scorer() builds on targetVectors (validated)

In BitRandomVectorScorerSupplier.scorer(), build the scorer on targetVectors instead of vectorValues. The copy the constructor already makes is then what the scorers read, and every copy() gets its own, as in DefaultFlatVectorScorer. With it the repro and TestHnswBitVectorsFormat pass (9 tests), as do the format, ECJ and forbidden-apis checks.

     @Override
     public UpdateableRandomVectorScorer scorer() throws IOException {
       byte[] query = new byte[vectorValues.dimension()];
-      return new BitRandomVectorScorer(vectorValues, query);
+      return new BitRandomVectorScorer(targetVectors, query);
     }

scorer() builds on targetVectors (validated) (recommended)

#

One line in FlatBitVectorsScorer.java:123. Each supplier, including each copy(), then scores through its own targetVectors = vectorValues.copy(), i.e. its own IndexInput clone; this is the shape of DefaultFlatVectorScorer.ByteScoringSupplier.

     @Override
     public UpdateableRandomVectorScorer scorer() throws IOException {
       byte[] query = new byte[vectorValues.dimension()];
-      return new BitRandomVectorScorer(vectorValues, query);
+      return new BitRandomVectorScorer(targetVectors, query);
     }

Trade-offs

  • No hot-path cost; uses the copy the constructor already makes.
  • Scorers of one supplier still share its targetVectors, as in DefaultFlatVectorScorer; a merge worker uses its scorers on its own thread.
  • One visible change: values() of a scorer from the original supplier then returns targetVectors, not the caller's instance (FlatBitVectorsScorer.java:105-108); no in-tree code checks for HasKnnVectorValues on these scorers.

Downstream note

#

Downstream, OpenSearch k-NN carries its own version of this scorer, whose copy() always copied the values; its #3504 (2026-08) also made its build-time scorer read the copy, the same shape as the fix suggested here.

How it was found

#

Found semi-formally: each documented contract of FlatBitVectorsScorer was written down as a proof obligation and checked against the code. The obligation "the scorers of a copy() read only copied vector values" failed, and a JUnit test on the stock main jars confirmed it. Independent reviewers then re-ran it and argued the case for intended behaviour.

  • Method: a proof-obligation check of the documented contracts of the codecs module's FlatBitVectorsScorer. For RandomVectorScorerSupplier.copy() the obligation was that a copy's scorers read only copied values; the code shows they read the original, and a test with a ByteVectorValues that records which instance serves each read witnessed it on the stock main jars (5adff78bb168, 2026-11-04).
  • Reduction: the witness was reduced to the one test shown under Minimal repro.
