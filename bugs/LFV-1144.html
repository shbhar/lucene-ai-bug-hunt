IndriAndScorer always reports a max score of 0, so top-k search can skip an IndriAndQuery's best hit

A multi-clause IndriAndQuery reports a constant maximum score of 0, and top-k search believes it: in the repro, search(q, 1) returns doc 0 (score 1.0) instead of doc 9999 (score 101.0), silently. It affects 10.1.0 to 10.6.0 and main when an application's own IndriScorer clauses score above 0.

The finding in 30 seconds

#

IndriAndScorer averages its IndriScorer clauses' scores but reports a maximum score of 0, a constant inherited from IndriDisjunctionScorer. Top-k search uses that bound to skip work, so it can skip the documents this clause scores highest.

Max-score pruning in one minute

#
  1. Every Scorer reports getMaxScore(upTo): an upper bound for the scores it can give documents up to upTo.
  2. IndexSearcher.search(q, n) keeps the n best hits so far; once it has counted 1,000 hits, only documents that score above the n-th best can still get in.
  3. For a disjunction, MaxScoreBulkScorer adds up its clauses' bounds. Clauses whose bounds together cannot lift a document over that threshold become non-essential: a candidate whose score plus their bounds cannot reach the threshold is dropped without asking them for a score. If every clause is non-essential, the whole window is skipped.

The finding, step by step

#
  1. Index 10,000 empty documents. Build an IndriAndQuery of two clauses whose own IndriScorer scores 100 on doc 9999 and 0 elsewhere (and honestly reports a max score of 100). The IndriAndQuery scores (100 + 100) / 2 = 100 on doc 9999.
  2. Make it a SHOULD clause of a BooleanQuery next to SHOULD MatchAllDocsQuery (score 1.0) and call IndexSearcher.search(q, 1). You expect doc 9999 with score 101.0, which an exhaustive search returns.
  3. Instead you get doc 0 with score 1.0, and no error. The IndriAndScorer scores 100 on doc 9999 but reports getMaxScore = 0, a constant it inherits from IndriDisjunctionScorer.
  4. Why: after 1,000 hits the search only wants scores above 1.0. When the first 4,096-document window ends, MaxScoreBulkScorer re-partitions its clauses: their bounds add up to 0 + 1.0, below the new threshold, so it decides that no document can win and skips the rest of the segment unscored, doc 9999 included.
  5. Lucene's own clauses all score 0 inside IndriAndQuery today, so the 0 happens to hold for them; open PR #463 would let plain term clauses score there and hit this.

Who is affected

#

Applications that write their own IndriScorer scoring above 0, put two or more such clauses in an IndriAndQuery, and nest it in a pruning top-k search, such as a BooleanQuery with another scoring clause. Lucene's own clauses all score 0 there today; open PR #463 would change that.

Mechanism, terms and numbers596 words

IndriAndScorer scores a document as the boost-weighted mean of its IndriScorer clauses' score() or smoothingScore(), but the getMaxScore it inherits from IndriDisjunctionScorer is a constant 0. Scorer.getMaxScore must bound every score, and top-k search relies on it: when an IndriAndQuery whose clauses score above 0 sits in a BooleanQuery next to another scoring clause, MaxScoreBulkScorer skips the rest of a window unscored once the minimum competitive score is above the sum of the clause bounds (0 + 1.0 in the repro). In the repro (10,000 empty documents, two one-document Indri clauses scoring 100 on doc 9999, ORed with MatchAllDocsQuery), IndexSearcher.search(q, 1) returns doc 0 (score 1.0) where the exhaustive ranking returns doc 9999 (score 101.0), with assertions on and off. The bound has been wrong since 8.9.0; the wrong hit shows from 10.1.0 on, after #13800 made the bulk scorer re-partition its clauses as the threshold rises. With Lucene's own clauses every IndriAndScorer score is 0 today (#10577), so only application-written IndriScorer subclasses trigger it; open PR #463 would extend it to term clauses.

Step by step in the repro

#
  1. IndriAndWeight.getScorer builds an IndriAndScorer because there are two clause scorers (IndriAndWeight.java:60-63; one clause would be returned as is). On doc 9999 it scores (100 + 100) / 2 = 100; everywhere else 0. getMaxScore is 0 throughout (probe: score()=100.0 getMaxScore(9999)=0.0).
  2. search(q, 1) scores with TOP_SCORES, so the BooleanQuery of two SHOULD clauses gets a MaxScoreBulkScorer (BooleanScorerSupplier.java:315-328).
  3. At first the minimum competitive score is 0 and both clauses are scored. Doc 0 becomes the top hit with 0 + 1.0 = 1.0. After 1,000 hits (IndexSearcher.java:100) the collector raises the minimum competitive score to Math.nextUp(1.0) (TopScoreDocCollector.java:154-162): later documents must beat 1.0.
  4. When the first inner window (at most 4,096 documents, MaxScoreBulkScorer.java:28) ends, the bulk scorer sees the higher threshold and re-partitions (:166, added by #13800). It reads each clause's getMaxScore (:439): Indri 0, match-all 1.0. In order of bound / cost it makes clauses non-essential while their summed bounds stay below the threshold (:502): 0 < 1.0000001, then 0 + 1.0 < 1.0000001 (MathUtil.sumUpperBound returns the sum unchanged for two values). Both clauses are non-essential.
  5. With no essential clause, partitionScorers returns false (:515-517) and the rest of the window is skipped unscored ("No matches in this window", :134-137); here that is the rest of the segment. The clause scorers run on docs 0-4095 only (probe). Doc 9999, really worth 101.0, is never scored. The result: doc 0, score 1.0, total hits "4096+".

In the repro a best hit inside the first inner window is scored before the re-partition: a hit at doc 4095 is kept, one at doc 4096 is lost (a separate probe), and a 2,000-document variant passed. Inner windows can end before 4,096 documents, so in other shapes the point can differ. A top-level IndriAndQuery is scored through DefaultScorerSupplier (IndriAndWeight.java:108-115), whose bulk scorer never reads getMaxScore; it keeps the hit (a separate probe).

Exposure and likelihood261 words

Applications that subclass IndriScorer (public abstract, protected constructor: IndriScorer.java:25-43) with scores above 0, combine two or more such clauses in an IndriAndQuery, and run it under a top-k search that prunes on max scores, for example as a SHOULD clause of a BooleanQuery next to another scoring clause, through the default IndexSearcher.search(q, n). No special codec, writer or searcher settings; at runtime only public extension APIs are involved (Query, Weight, ScorerSupplier, IndriScorer).
  • What they see. A lower-scoring top hit than the exhaustive ranking; no exception, with assertions on and off. In the repro the best hit lies past the first 4,096-document inner window; inner windows can end earlier, so other shapes can differ.
  • Built-in clauses. With Lucene's own clauses every IndriAndScorer score is 0 (only IndriScorer sub-scorers count, #10577; no built-in leaf scorer such as TermScorer is one, and the only built-in IndriScorer, IndriAndScorer, then scores 0 too), so the 0 bound happens to hold. Open PR #463 removes that filter and keeps return 0: if it landed, ordinary term clauses (positive under BM25) would hit this (by reading, not run).
  • Second shape. As a MUST clause next to MUST f:t, the same query loses the top hit on 10.3.1, 10.3.2, 10.4.0, 10.5.0, 10.5.2, 10.6.0 and main (history probe; 10.5.1 not run).
  • Scale. IndriAndQuery is a rarely used core query that no Lucene parser builds; the one public downstream IndriScorer subclass found (Lucindri) scores at most 0 and is not affected (by reading). Hence Low priority.

Why it looks unintended

#
  • Scorer.getMaxScore must bound every score up to upTo (Scorer.java:75-79); AssertingScorer asserts it (:130).
  • Lucene forbids negative scores (LUCENE-7996), so for a conforming scorer 0 bounds only an always-0 score; Indri's log-probability similarity is exempt only in tests.
  • The introducing PR's reviewer accepted no block-max support "as long as it is not kicking in incorrectly here" (r542492206).
The full argument159 words
  • Contract. Scorer.getMaxScore: "Return the maximum score that documents between the last target that this iterator was shallow-advanced to included and upTo included" (Scorer.java:75-79). AssertingScorer.score() checks score <= getMaxScore(docID()) and score >= 0 (lucene/test-framework/.../AssertingScorer.java:130-131).
  • No negative scores. MIGRATE.md:1397-1401 (LUCENE-7996, a8a63464e7d, 2017-12-06): "Scorers are no longer allowed to produce negative scores." For a scorer that follows this rule, 0 is a correct bound only if it always returns 0.
  • No rationale anywhere. return 0 is unchanged since the introducing commit 9cc5c9b7983 (git log -L); no javadoc mentions it; TestIndriAndQuery has two tests that check hit counts only (TestIndriAndQuery.java:111-143).
  • Review history. mikemccand asked on the introducing PR whether Indri uses block-max WAND and was fine deferring it "as long as it is not kicking in incorrectly here" (r542492206, 2020-12-14); the author answered that IndriQuery does not use it (r555482275). The pruning here comes from the enclosing BooleanQuery, not from Indri itself.
The devil's-advocate check217 words

Strongest case for "intended": Indri scores are log-probabilities, at most 0, so 0 is a sound bound. That design is real: the in-tree IndriDirichletSimilarity.score returns Math.log(...), at most 0 (IndriDirichletSimilarity.java:69-72); the introducing commit 9cc5c9b7983 exempted it from BaseSimilarityTestCase's non-negative-score checks (still at :388-389, :417-418, :443-444, :485-486); open PR #463 also skips TopScoreDocCollector's assert score >= 0 for IndriDisjunctionScorer. Besides, Lucene's own clauses all score 0 inside IndriAndQuery, and a custom IndriScorer is unusual.

Why it still fails: the exemptions are test-only and cover one similarity. No Indri javadoc allows negative scores or limits scores to at most 0, while MIGRATE.md forbids negative scores for every Scorer, and the Scorer.getMaxScore contract has no exception. IndriScorer is a public, untagged extension point with a protected constructor, so an IndriScorer that follows Lucene's rule scores at least 0, and the constant 0 is wrong as soon as it scores above 0. The all-zero in-tree scores are a separate defect (#10577) that narrows reach without making the bound right. A reviewer from another model family (OpenAI GPT-5.6) rated this defence "moderate" and rejected it after running its own test with clause scores 0.9 and 0.1 (score 0.5 above a max of 0.0). A maintainer may still raise the exemption.

Suggested fix

#

Recommended A: report no bound (Float.POSITIVE_INFINITY)

Make IndriDisjunctionScorer.getMaxScore return Float.POSITIVE_INFINITY (no bound), as other scorers without a cheap bound do. Validated: the repro passes with assertions on and off, and 63 tests in the Indri, MaxScore, Boolean and WAND suites pass. Cost: the Indri clause is never skipped by max-score pruning.

@Override
public float getMaxScore(int upTo) throws IOException {
  // Subclasses combine the sub-scorers' score() or smoothingScore() values, and nothing bounds
  // smoothingScore(), so no finite bound is known. 0 is wrong once a sub-scorer scores above 0.
  return Float.POSITIVE_INFINITY;
}

A: report no bound (Float.POSITIVE_INFINITY) (validated by the checks) (recommended)

#

One line in IndriDisjunctionScorer.getMaxScore (IndriDisjunctionScorer.java:49-52). The same convention is used by SpanScorer.java:142, FunctionQuery.java:141 and ValueSourceScorer.java:96 (lucene/queries) and by DoubleValues.java:60; WANDScorer.scalingFactor handles infinity (WANDScorer.java:74).

@Override
public float getMaxScore(int upTo) throws IOException {
  // Subclasses combine the sub-scorers' score() or smoothingScore() values, and nothing bounds
  // smoothingScore(), so no finite bound is known. 0 is wrong once a sub-scorer scores above 0.
  return Float.POSITIVE_INFINITY;
}

Trade-offs

Simple and safe. Queries that are pruned correctly today (built-in clauses, all scores 0) lose that skipping and may get slower; their results do not change.

A': keep 0 only when it is true (not run)

#

The boost-weighted mean of a per-clause bound that covers both the clause's getMaxScore(upTo) and its smoothing scores, with advanceShallow passed on to the clauses.

Trade-offs

Keeps pruning, but nothing bounds smoothingScore today, so it needs a new IndriScorer method: a larger change for a feature #11194 proposes to move or narrow.

Downstream note

#

For a downstream product that offers IndriAndQuery with its own positive-scoring clauses, the effect is a wrong ranking only: no documents outside the match set, no crash or hang.

How it was found

#

A proof-obligation check of the Scorer contract in IndriDisjunctionScorer (does getMaxScore bound every score the scorer can return?) flagged the constant 0. An executable JUnit test then showed top-k search returning a different top hit from the exhaustive ranking.

The method in full102 words

Method: semi-formal (2026-11-02, main 5adff78bb168).

  • The obligation: for every scorer, score() <= getMaxScore(upTo) for each document up to upTo (Scorer.java:75-79, enforced by AssertingScorer.java:130). IndriDisjunctionScorer.getMaxScore discharges it only if every subclass always scores 0; IndriAndScorer does not (its boost-weighted mean of IndriScorer clause scores exceeds 0 when a clause with a positive boost scores above 0).
  • Witness: a public-API JUnit test with a user IndriScorer (the class's extension point) under a BooleanQuery, comparing search(q, 1) with an exhaustive search; a probe printed score() 50.0 against getMaxScore 0.0. The repro was then reduced to the 10,000-document test shown here.

Impact note
Only applications that build an IndriAndQuery (a rarely used core query that no Lucene query parser produces) from two or more clauses whose scorers are their own IndriScorer subclasses scoring above 0, and run it under a top-k search that prunes on max scores, for example as a SHOULD clause of a BooleanQuery next to another scoring clause, are hit: IndexSearcher.search(q, n) then silently returns a different top hit from an exhaustive search, with -ea and -da [exec], once the minimum competitive score has risen and the best hit lies past MaxScoreBulkScorer's first 4,096-doc window (10,000 documents in the one-test repro and 20,000 one-term documents in the earlier one; 2,000 did not reproduce); with built-in clauses every IndriAndScorer score is 0 today (a separate defect, reported as #10577), so the 0 bound happens to hold, and a top-level IndriAndQuery is scored without pruning [read]; default codec, IndexWriterConfig and searcher; releases 10.1.0 to 10.6.0 and main (the earlier 20,000-document repro passed on 10.3.0, the one-test repro fails there too); open PR #463, which lets term clauses contribute, would expose ordinary term clauses to it [read].
Summary
You put an IndriAndQuery whose two clauses are your own IndriScorer-based queries (each scores 100 on the last of 10,000 documents and 0 elsewhere, and reports a max score of 100) into a BooleanQuery as a SHOULD clause next to MatchAllDocsQuery, and ask IndexSearcher.search(q, 1) for the best hit; you expect the last document, which an exhaustive search ranks first with score 101.0, because Scorer.getMaxScore must bound every score. Instead top-k search returns doc 0 (score 1.0), with no error, under -ea and -da. IndriDisjunctionScorer.getMaxScore, which IndriAndScorer inherits, always returns 0 while IndriAndScorer scores the boost-weighted mean of its IndriScorer clauses (100 here), so once the minimum competitive score is above the summed max-score bounds of the two BooleanQuery clauses (0 + 1.0), MaxScoreBulkScorer skips the rest of the segment unscored, the last document included. An earlier 20,000-document repro (one clause scoring 100 on the last document, the other 0, next to the term query f:t) fails the same way: doc 0 (score 1.1e-5) instead of the last document (score 50.00001).
