AnalyzingInfixSuggester and BlendedInfixSuggester can return no suggestion for a key whose last word the query analyzer turns into a zero-length token (4.4.0 to 10.6.0, branch_11x and main; BlendedInfixSuggester from 4.7.0, its first release)

Rare and small: the opt-in, experimental AnalyzingInfixSuggester and BlendedInfixSuggester can silently return no suggestion for a key whose last word the query analyzer turns into a zero-length token, when nothing follows it. With default settings and stock ArabicAnalyzer, the key foo ـ (a standalone tatweel, U+0640) misses foo ـ bar.

The finding in 30 seconds

#

The claimed case, a lookup without a context filter, needs all of: nothing typed behind the last word, another word before it, minPrefixChars of 1 or more (default 4) and all terms required (the default). A tatweel normally sits inside a word. Four stemming analyzers remove single words whole; how common those are as a last word was not checked.

Background: three pieces

#
  1. The infix suggester is a small Lucene index of its own. Each suggestion is one document, analyzed into tokens. A lookup analyzes the key the same way and searches that index: every word of the key but the last must match a whole token.
  2. The last word counts as unfinished when no character follows it, and is matched as a prefix. To make short prefixes fast, the first 1 to minPrefixChars characters of every token are also indexed, in a second field named textgrams, and a short last word is looked up there as an exact term.
  3. A token can have length 0: an analyzer may remove every character of a word. The stock ArabicAnalyzer does that to a tatweel (U+0640), a stretching character, when it stands alone as a word.

The finding, step by step

#
  1. Build an AnalyzingInfixSuggester with its default settings over the stock ArabicAnalyzer and add one suggestion, foo ـ bar. The middle word is a standalone tatweel (U+0640). The analyzer removes that character, so the word becomes a token of length 0.
  2. Look up the key foo ـ with lookup(key, 10, true, false). The key is the beginning of the only suggestion, so the test expects 1 suggestion.
  3. You get 0 suggestions and no error. The shorter key foo returns the suggestion, and so does the same key followed by a space.
  4. Why: the last word of a key, when nothing follows it, is matched as a prefix. A prefix shorter than minPrefixChars (default 4) is looked up as an exact term in a helper field that holds the first 1 to 4 characters of every word. No entry there has length 0, and the clause is required, so nothing matches.
  5. The same suggester built with minPrefixChars = 0 returns the suggestion. With allTermsRequired = false the key still returns the suggestions of its other word. BlendedInfixSuggester inherits the lookup and returns the same.

Who is affected

#

Applications that use one of the two infix suggesters, which are opt-in and marked experimental, with a query analyzer that can emit a zero-length token. One lookup returns nothing where the key's other word matches suggestions. Nothing throws and nothing is stored wrongly. The same key followed by a space returns the suggestion.

Mechanism, terms and numbers1,432 words

Small and rare. AnalyzingInfixSuggester and its subclass BlendedInfixSuggester are opt-in classes of the suggest module, both marked experimental. A lookup analyzes the key; the last token, when no character follows it, is matched as a prefix. For a last token shorter than minPrefixChars (default 4), getLastTokenQuery builds no prefix query: it looks the token up as an exact term of the field textgrams, which holds the first 1 to minPrefixChars characters of every token (AnalyzingInfixSuggester.java:543-550, :406-410, lines at main 596ef11ddf96). A token of length 0 is shorter than every minPrefixChars of 1 or more, and no gram has length 0. With allTermsRequired = true (the default) the clause is required, so the lookup returns an empty list, with no error, the same with assertions on and off.

The claimed case is a lookup without a context filter. It takes an analyzer that turns the last word of the key into a zero-length token, with nothing typed behind that word and another word before it. In the run the stock ArabicAnalyzer does this to a standalone tatweel (U+0640): the suggestion foo ـ bar is not returned for the key foo ـ, while foo and the same key followed by a space both return it, and the same suggester built with minPrefixChars = 0 returns it. A tatweel normally sits inside a word. Other producers that were run: the same character under PersianAnalyzer and SoraniAnalyzer, one word each that the stemmers of four analyzers remove whole (how common those words are as the last word typed was not checked), and a filter chain that blanks a punctuation-only token. What is lost is every suggestion that the key's other word matches: on three suggestions the key also loses foo baz, which does not contain the tatweel. Nothing is stored wrongly: the lookup only reads, and the next lookups on the same suggester return their suggestions.

Every release from 4.4.0 to 10.6.0 does it, and so do the builds of branch_11x 89e68e0f3a50 and main 596ef11ddf96 that were run: the condition came with the class (LUCENE-4845, 2013) and was never changed. That the result is not intended is an argued reading, not a documented rule: no javadoc says what an empty last token matches. Two small repair shapes were run; which one is right is for the maintainers to decide.

Why it looks unintended

#
  • The class suggests "prefix matches to any tokens in the indexed text", and its comments call the n-gram lookup the equivalent of the prefix query.
  • minPrefixChars is documented as index size against lookup speed, yet 4 and 1 return nothing where 0 returns the suggestion.
  • This is an argued reading: no javadoc says what an empty last token matches.
The full argument591 words

No javadoc says what an empty last token matches, or that results do not depend on minPrefixChars. What follows is the argument, with the reading that the code implements stated beside it.

  • The class's own description. "Analyzes the input text and then suggests matches based on prefix matches to any tokens in the indexed text." (AnalyzingInfixSuggester.java:86-87). An unfinished last token is a prefix to be matched against tokens, and the empty string is a prefix of every token.
  • The setting is documented as size against speed. "@param minPrefixChars Minimum number of leading characters before PrefixQuery is used (default 4). Prefixes shorter than this are indexed as character ngrams (increasing index size but making lookups faster)." (:189-191). The result here depends on it. The text names index size and lookup speed only; it does not say in so many words that results are the same under every value.
  • The code calls the n-gram lookup the equivalent of the prefix query. "Use PrefixQuery (or the ngram equivalent)" (:671); "The leading ngram was directly indexed" (:545), which is not true for a token of length 0.
  • Lucene's own tests treat the setting as result-neutral. testRandomMinPrefixLength draws the setting from 0 to 9 and asserts one set of results (TestAnalyzingInfixSuggester.java:334-409, the draw at :343). testRandomNRT draws it from 0 to 6 (:637), and its reference model matches the last query term with startsWith (:777), which is true for an empty term. Neither test has a zero-length token.
  • A zero-length token is legal analyzer output. PatternReplaceFilter's javadoc: "this TokenFilter may produce Tokens whose text is the empty string" (PatternReplaceFilter.java:31-32). TestSoraniNormalizationFilter.testRemove asserts the empty output for U+0640 (TestSoraniNormalizationFilter.java:84-85).
  • Where the term is, and where the lookup asks. The suggester indexes the empty term in text and requires it there like any other term when it is not the unfinished last token: the key followed by a space returns only foo ـ bar, and so do the keys ـ foo and ـ fo (run). For the unfinished last token it asks textgrams, which cannot hold a term of length 0.
  • Four readings of an empty last token. Three return the suggestion of the test: a prefix of everything (what minPrefixChars = 0 does), nothing typed yet (no clause), the exact empty term (what the key followed by a space does). The fourth is the one the code composes, and it is coherent: the empty token is a term like any other; an unfinished term shorter than minPrefixChars is looked up among the grams of 1 to minPrefixChars characters; a term of length 0 has no gram, so nothing matches. What speaks against the fourth as the intended one: the comments and the author's sentence below present the gram lookup as a stand-in for the prefix query, and a prefix query for the empty prefix matches; and the result then differs between minPrefixChars 0 and 1 or more. A maintainer may still take the fourth reading as the design.
  • History. The condition came with the class (LUCENE-4845, 2013) and was never changed; the n-gram field came with it and has had a shortest gram of one character ever since. The body and the 33 comments of that issue do not contain the words "empty", "zero" or "minPrefix". Its author's sentence on the field: "I index leading ngrams up to a limit (default 4 characters) and use those instead of PrefixQuery when the last term is short."
The devil's-advocate check300 words

The strongest case for "works as designed": in #6229 (LUCENE-5165, 2013) the author of the class, Michael McCandless, wrote "Really our analysis APIs aren't quite designed to handle a "partial" tokens that suggesters need to work with." That case, a stop word as the unfinished last word, was repaired in the query analyzer with SuggestStopFilter, whose javadoc says "Normally you'd use the ordinary StopFilter in your indexAnalyzer and then this class in your queryAnalyzer" (SuggestStopFilter.java:35-36). By analogy, what the query analyzer does to the last word is the application's business: give the suggester a query analyzer that emits no empty token. That way out exists and works (run): with a length filter behind the query analyzer, added through an AnalyzerWrapper, the key foo ـ returns its suggestions (the filter changes the neighbouring keys too: the key followed by a space, and the key continued with b, then return 2 suggestions instead of 1). The classes are experimental, and no report came in thirteen years.

What speaks against it: in #6229 the analyzer removed the token before the suggester saw it. Here the suggester receives the token, its own text field holds the same term, and the miss comes from its own shortcut, whose comment is false for this length. No javadoc of the class restricts the analyzer or asks for a length filter. The outcome follows a setting documented as index size against lookup speed. "Experimental" allows the API to change; it does not document this result. No test pins it: Lucene's two infix suggester suites pass unchanged with either repair. None of this proves intent: the fourth reading above is what the code does, and nothing written rules it out. A maintainer may answer first that the query analyzer should not emit empty tokens.

Suggested fix

#

Recommended Add no clause for an empty last token

Two small changes were run, and both make the test and the suggest module's tests pass. Shown here: an empty last token adds no clause. The other sends it to the prefix query, as minPrefixChars = 0 does today. They differ for a key that is only the empty token and with allTermsRequired = false. The choice is the maintainers'.

Two repair shapes were run, plus a placement variant of the first. The lists of what each shape changes are for lookups without a context filter and count results. Three things are true of every shape, the placement variant included (run on main with the patched class in front):

  • A context filter. With all terms required, a key that is only the zero-length token changes from no suggestion to every suggestion of the context.
  • Highlighting. The empty prefix is still passed to the highlighter (AnalyzingInfixSuggester.java:676-677, :868-870), and highlighting is on in the generic lookup by default (:160, :512-517). The suggestions that then come back for foo ـ carry empty marks: <b>foo</b> <b></b>ـ <b></b>bar and <b>foo</b> <b></b>baz.
  • The order of BlendedInfixSuggester results. With an empty prefix every word of a suggestion counts as a match (BlendedInfixSuggester.java:328-347), so every result keeps its full weight. With bar baz foo (weight 100) and foo bar baz (weight 95) the key foo returns foo bar baz first (95 against 80); the key foo ـ then returns bar baz foo first (100 against 95).

The marks and the order are what minPrefixChars = 0 gives today, and they concern results that are not returned at all today.

Application side: a query analyzer that emits no zero-length token, or minPrefixChars = 0 (validated by the checks)

#

No Lucene change. Put LengthFilter(1, Integer.MAX_VALUE) at the end of a custom query chain, or around a stock analyzer through an AnalyzerWrapper. Or build the suggester with minPrefixChars = 0.

Trade-offs

  • A way out for one application, not a repair: the default configuration keeps the miss.
  • minPrefixChars = 0 gives up the n-gram field, which the javadoc describes as making lookups of short prefixes faster.
  • The length filter changes the neighbouring keys too (run): the key followed by a space, and the key continued with b, return 2 suggestions instead of 1, because the query no longer carries the empty term.

How it was found

#

Semi-formal: a differential sweep. Every prefix of eight texts was looked up through the suggesters, once with a stock analyzer that turns one word into a zero-length token and once with that word in the analyzer's stop list. Keys that lost their suggestions only under the zero-length token led to getLastTokenQuery, and the case was reduced to one test.

The method in full203 words

Method: semi-formal (a differential over generated keys on the stock jars, then located by reading). No model-checking, SMT or proof tool was involved.

  • Signal. The consumers of zero-length tokens were being swept: the same texts through each consumer, with an analyzer that emits the zero-length token and with a reference analyzer that drops the word. The infix suggesters lost suggestions at keys that end behind that word, and at no other key that the reference analyzer keeps.
  • Reading. The cause was read in getLastTokenQuery: the n-gram shortcut is taken for a token of length 0, for which no gram exists.
  • Reduction. One suggestion, one key, one assertion, with the stock ArabicAnalyzer.
  • A second detector. The suggestions of each key under minPrefixChars 1, 2 and 4 were compared with those under 0 (240 comparisons). That relation is a detector, not the contract for every case: of its 30 differing comparisons, 12 are the case this page claims; the others are the two neighbouring cases named under the suggested fix.
  • A related finding. LFV-523 covers zero-length tokens in TokenStreamToAutomaton, with the same producers of such a token and another fix site; the test of this page still fails with that finding's fix.
