SegmentInfos.commit checks hard and soft deletion counts against maxDoc one at a time but not their sum, so it publishes a commit that cannot be opened

SegmentInfos.commit refuses a segment whose hard or soft deletion count alone exceeds maxDoc, but not one whose two counts together do, although reading a commit rejects exactly that as corruption. So the commit succeeds and the index's newest commit cannot be opened (since 7.4.0).

The finding in 30 seconds

#

Writing a commit and reading it back check the deletion counts differently: the writer checks each count alone, the reader also checks their sum.

Background: deletion counts in a commit

#
  1. A commit (segments_N) lists the index's segments. For each segment it stores maxDoc (its number of documents), delCount (hard-deleted documents) and, since 7.4.0, softDelCount (documents that are only soft-deleted).
  2. A document is live, hard-deleted, or only soft-deleted, never two of these, so delCount + softDelCount can never exceed maxDoc.
  3. SegmentInfos.commit writes a commit. SegmentInfos.readCommit reads one; DirectoryReader.open and IndexWriter open the index through it.

The finding, step by step

#
  1. Index 2 documents and delete one: the only segment has maxDoc 2 and delCount 1. Rebuild its SegmentCommitInfo with softDelCount 2 and call SegmentInfos.commit. Each count is at most 2, but together they claim 3 deleted documents out of 2.
  2. You expect commit to throw IllegalStateException: cannot write segment, as it does when either count alone is above 2.
  3. Instead commit succeeds and writes segments_3. SegmentInfos.readLatestCommit, DirectoryReader.open and new IndexWriter then throw CorruptIndexException: invalid deletion count: 3 vs maxDoc=2.
  4. Why: on write, SegmentInfos checks delCount <= maxDoc and softDelCount <= maxDoc one at a time; on read it also checks delCount + softDelCount <= maxDoc. The sum check was never added to the write side.

Who is affected

#

Code that builds or edits commits through the expert SegmentInfos/SegmentCommitInfo API, and writer bugs that miscount deletes (LFV-593, assertions off); a correctly working IndexWriter never writes such counts. The error is loud. After a direct commit the previous commit stays readable by name; after a bad IndexWriter commit the default deletion policy has deleted it, so no commit opens.

Mechanism, terms and numbers436 words

Each segment in a commit (segments_N) records two deletion counts: delCount (hard deletes) and softDelCount (documents that are only soft-deleted). They count different documents, so their sum can never exceed the segment's maxDoc. SegmentInfos.readCommit, which DirectoryReader.open and IndexWriter use, checks each count and the sum, and rejects a bad sum with CorruptIndexException("invalid deletion count"). SegmentInfos.write checks each count and refuses one out of range with IllegalStateException("cannot write segment"), but never checks the sum. So commit publishes a commit that every opener then refuses, instead of refusing to write it. A correctly working IndexWriter never writes such counts: it takes commit metadata built through the expert @lucene.experimental API, or a separate writer bug that miscounts deletes. The failure is loud. After a direct SegmentInfos.commit, as in the repro, the previous commit stays readable by name; after a bad IndexWriter commit, the realistic path, the default deletion policy has already deleted it, so no commit in the directory opens. The fix is one more check in write, with the same exception as its two neighbours.

The code (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/index/)

#
  • Write side, SegmentInfos.write(IndexOutput), per segment: if (delCount < 0 || delCount > si.maxDoc()) throws IllegalStateException("cannot write segment: invalid maxDoc segment=... delCount=...") (SegmentInfos.java:692-700); if (softDelCount < 0 || softDelCount > si.maxDoc()) throws the same with softDelCount= (:705-713). Nothing compares the sum with maxDoc before writeBEInt(out, softDelCount) (:714).
  • Read side, parseSegmentInfos: the same two range checks (:427, :434) and if (softDelCount + delCount > info.maxDoc()) → CorruptIndexException("invalid deletion count: " + (softDelCount + delCount) + " vs maxDoc=" + info.maxDoc()) (:438-442).
  • No other guard on the write path. The public SegmentCommitInfo constructor stores both counts unchecked (SegmentCommitInfo.java:101-122). The package-private setters range-check each count and only assert the sum (:374-392, asserts at :379, :389), so with assertions off nothing enforces it.
  • Result. commit is prepareCommit + finishCommit (SegmentInfos.java:1031-1034): write succeeds, the pending file is renamed to segments_N, and the newest commit is one that DirectoryReader.open (StandardDirectoryReader.java:95) and IndexWriter (IndexWriter.java:1085 for APPEND, :1011 for CREATE over an existing index) reject.

The numbers

#

2 documents, one deleted by term: maxDoc 2, delCount 1 with its live-docs file. Rebuilt with a fresh id and a hand-set softDelCount 2 (no document is soft-deleted), so each count fits but the sum does not (1 + 2 = 3 > 2). commit returns; readLatestCommit throws CorruptIndexException: invalid deletion count: 3 vs maxDoc=2 from SegmentInfos.java:440, with assertions on and off.

Exposure and likelihood307 words
  • Who. Code that publishes deletion counts that are each in range but sum above maxDoc: tools that build or edit commits through the @lucene.experimental SegmentInfos / SegmentCommitInfo API (SegmentInfos.java:119, SegmentCommitInfo.java:33), for example index upgrade or repair tools; or a separate IndexWriter bug that miscounts deletes.
  • A real producer. LFV-593: an IndexWriter opened from a near-real-time reader's IndexCommit with a soft-deletes field counts the reader's deletions again. With assertions off it publishes exactly such a commit (invalid deletion count: 3 vs maxDoc=2); with this fix the same steps fail at commit with IllegalStateException: cannot write segment: invalid maxDoc segment=_0 maxDoc=2 delCount=1 softDelCount=2.
  • Default vs opt-in. A correctly working IndexWriter never writes such counts; it takes the expert API or another bug. Soft deletes themselves are opt-in (IndexWriterConfig.setSoftDeletesField).
  • Scale. None: 2 documents are enough.
  • Effect. Loud in every case; how bad depends on who wrote the commit. *A direct SegmentInfos.commit (the repro):* the newest commit cannot be opened through DirectoryReader.open, DirectoryReader.listCommits or IndexWriter, but the previous segments_N is still readable by name with SegmentInfos.readCommit(dir, name), and deleting the newest segments_N by hand restores the index. *An IndexWriter commit (the LFV-593 path):* right after finishCommit (IndexWriter.java:4294) the writer calls deleter.checkpoint(pendingCommit, true) (:4306), and the default KeepOnlyLastCommitDeletionPolicy (LiveIndexWriterConfig.java:132) deletes every older commit (KeepOnlyLastCommitDeletionPolicy.java:40-45). A probe of that path (2 documents, 1 soft-deleted, assertions off) ends with segments_3 as the only commit file, and readCommit, readLatestCommit and DirectoryReader.open all reject it: no commit in the directory opens. With the fix the commit is refused in both cases: in the writer probe close() throws IllegalStateException: cannot write segment: ..., segments_2 stays the only commit and DirectoryReader.open reads it. Whether such a writer is still usable after the miscount was not checked.

Why it looks unintended

#
  • LUCENE-5615 made the writer repeat the reader's delete-count check "in case there are Lucene bugs that mess up the delete counts".
  • LUCENE-8341 (7.4.0) added the read-side sum check but no write-side one; nothing calls that deliberate.
  • getSoftDelCount() counts "only soft-deleted docs", and the setters assert the sum is at most maxDoc.
The full argument219 words
  • LUCENE-5615 made the writer repeat the reader's delete-count check. LUCENE-5615 (#6677, Michael McCandless, 2014): "When reading the segment infos, we already check if the delCount is out of bounds for a segment (<0 or > docCount) and throw CorruptIndexException if so. I think we should catch this when writing as well, in case there are Lucene bugs that mess up the delete counts. We have just an assert today..." CHANGES 4.8.0: "Validate per-segment delete counts at write time, to help catch bugs that might otherwise cause corruption". Up to 7.3.1 write and read accepted the same counts (a 7.3.1 control refuses delCount 3 for maxDoc 2 at commit). LUCENE-5615 predates softDelCount and says nothing about the sum; the claim is only that leaving the sum out is inconsistent with that write-time validation.
  • The gap came with the second count. LUCENE-8341 (fe83838ec37, #9388, 7.4.0) added softDelCount, its read-side range check, the read-side sum check and the write-side range check in one commit, but no write-side sum check. Its 11 comments never discuss leaving it out.
  • The invariant is stated in code. getSoftDelCount(): "Returns the number of only soft-deleted docs" (SegmentCommitInfo.java:369); setDelCount/setSoftDelCount assert softDelCount + delCount <= info.maxDoc() (:379, :389); the reader treats a violation as corruption (SegmentInfos.java:438).
The devil's-advocate check227 words

The strongest case, made by an independent reviewer from another model family (OpenAI GPT-5.6), who reproduced the failure with its own test and confirmed the write/read mismatch, but not that it is a defect: hard and soft deletion counts are disjoint by definition, so a sum above maxDoc is impossible metadata handed to an @lucene.experimental API; no contract says commit validates fabricated metadata; and the read side's CorruptIndexException is the correct, loud answer. The intended-behaviour check added that commit is indeed no general validator: it also accepts a commit into a directory without the segment files, or a delCount with delGen -1.

Why it fails: the claim is not that commit should validate everything, only that the delete counts, exactly where LUCENE-5615 made the writer repeat the reader's checks "in case there are Lucene bugs that mess up the delete counts", are checked on one side and not the other. The writer already refuses each count alone; an in-tree writer bug (LFV-593) reaches the gap with assertions off; and the fix turns an index whose newest commit no opener accepts into a refused commit. The same reviewer called the guard reasonable defence in depth and saw the fix make its test pass. Verdict: a real Low bug, a one-check hardening for defensive symmetry with the read side, not a demand that commit validate metadata in general.

Suggested fix

#

Recommended A. Add the sum check to SegmentInfos.write (validated)

In SegmentInfos.write, after the softDelCount range check, throw the same IllegalStateException when (long) delCount + softDelCount > si.maxDoc(). The repro passes with assertions on and off; all 1,398 tests of lucene/core's org.apache.lucene.index package pass and the formatter check is clean.

Trade-offs

C. Check the sum in the public SegmentCommitInfo constructor

#

Reject bad counts when the object is built (SegmentCommitInfo.java:101-122).

Trade-offs

Readers build SegmentCommitInfos through the same constructor, so it changes a public constructor's contract and duplicates the read check. Not run.

Downstream note

#

Downstream tools that build or rewrite commits through the expert API (upgrade, repair or replication tools) learn of a bad deletion count only when the index fails to open, not when they commit.

How it was found

#

A semi-formal proof-obligation audit of SegmentInfos's contract: every commit that write() publishes must be one that readCommit accepts. Comparing the checks on the two sides found a read-side sum check with no write-side counterpart, and a one-test JUnit repro witnessed it.

The method in full73 words

The obligation pairs each read-side check in parseSegmentInfos (SegmentInfos.java:424-442) with a write-side check in write (:690-714). The two range checks have counterparts (:692, :705); the sum check (:438) has none, and the public SegmentCommitInfo constructor and the setters (asserts only) do not enforce it either. The repro then committed counts that are each in range but sum above maxDoc and read the commit back.
