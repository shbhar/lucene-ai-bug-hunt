setRAMBufferSizeMB accepts NaN, and the writer then flushes one segment per document

IndexWriterConfig.setRAMBufferSizeMB(Double.NaN) is accepted although the method rejects enabled sizes not above 0.0, so the default flush policy flushes after every added document (20 documents give 20 segments instead of 1, merging off) and the size-based early write-back of doc-values updates never triggers. Data stays correct; the check is unchanged since 2.3.0.

The finding in 30 seconds

#

One setter check is written so that NaN slips through it.

Background: the RAM buffer

#
  1. IndexWriter keeps added documents in memory and writes them out as a new segment (a flush) when they use ramBufferSizeMB of RAM; the default is 16 MB.
  2. IndexWriterConfig.DISABLE_AUTO_FLUSH (-1) turns flushing by RAM off. Every other value is an enabled buffer and must be above 0.0.
  3. In Java every ordered comparison with NaN (<, <=, >, >=) is false, so a check like x <= 0.0 lets NaN pass.

The finding, step by step

#
  1. You size the writer's RAM buffer from a formula or a settings string, and it comes out NaN, for example 0.0 / 0.0 or Double.parseDouble("NaN"). You pass it to IndexWriterConfig.setRAMBufferSizeMB, or live to IndexWriter.getConfig().setRAMBufferSizeMB.
  2. You expect IllegalArgumentException: ramBufferSize should be > 0.0 MB when enabled, the error that 0.0, -0.0 and -Infinity get.
  3. Instead the check is ramBufferSizeMB <= 0.0, and every comparison with NaN is false, so NaN is stored without a word.
  4. The default flush policy's limit becomes (long) (NaN * 1024 * 1024) = 0 bytes, so every added document is flushed: with one indexing thread, 20 documents and a commit give 20 segments, where the default 16 MB gives 1 (merging off in the measurement).
  5. ramBytesUsed > 0.5 * NaN * ... is never true either, so buffered doc-values updates are never written back early because of their size; they wait for the next NRT reader, commit, flush() or merge. The document count and the updated values stay correct.

Who is affected

#

Only applications that pass NaN, typically a computed or parsed size (a 0 / 0 in a heap-fraction formula, or a settings string read with Double.parseDouble, which accepts "NaN"). The default 16 MB and plain constants are safe. They get no error, a tiny segment per document, and no size-based early write-back of doc-values updates; data stays correct.

Mechanism, terms and numbers634 words

LiveIndexWriterConfig.setRAMBufferSizeMB documents an IllegalArgumentException for an enabled RAM buffer that is not positive, and its message says "ramBufferSize should be > 0.0 MB when enabled". It rejects 0.0, -0.0 and -Infinity, but the check is written ramBufferSizeMB <= 0.0, which is false for NaN, so NaN is stored, on a new IndexWriterConfig and live on an open writer. The default flush policy then computes a 0-byte limit and flushes after every added document (one indexing thread: 20 documents and a commit give 20 segments with merging off; the default 16 MB gives 1), and IndexWriter's size-based early write-back of buffered doc-values updates can never trigger, however many are pending, so they wait for the next NRT reader, commit, flush() or merge. A small legal buffer also flushes per document; what only NaN does is pair that with a size-based write-back that never runs. No exception is thrown, and the document count and updated values stay correct. The check has admitted NaN since the setter was added for 2.3.0 (2007); writing it as (ramBufferSizeMB > 0.0) == false fixes it.

The check

#
  1. The javadoc (LiveIndexWriterConfig.java:162-164) reserves one value, DISABLE_AUTO_FLUSH (-1, IndexWriterConfig.java:72), to turn RAM flushing off, and promises "@throws IllegalArgumentException if ramBufferSize is enabled but non-positive" (:188-189).
  2. The check at :192 is ramBufferSizeMB != IndexWriterConfig.DISABLE_AUTO_FLUSH && ramBufferSizeMB <= 0.0. For NaN the first half is true and the second false, so the throw at :193 is skipped and :200 stores NaN. IndexWriterConfig.setRAMBufferSizeMB (IndexWriterConfig.java:463-466) only delegates, and IndexWriter.getConfig() (IndexWriter.java:1284) returns the same live object.

What the stored NaN does

#
  1. FlushByRamOrCountsPolicy.flushOnRAM() (FlushByRamOrCountsPolicy.java:109-111) is true because NaN != -1. The limit at :46 is (long) (NaN * 1024 * 1024), which Java converts to 0. The test at :49 (deletesRam >= limit && activeRam >= limit && perThread != null) then holds for every added document, so :50 requests applying all buffered deletes and :51 (flushActiveBytes → markLargestWriterPending, :84) marks the largest non-pending per-thread writer for flushing; with one indexing thread that is its own writer, so each document is flushed alone. DocumentsWriterFlushControl.ramBufferGranularity() (DocumentsWriterFlushControl.java:202-213) is 0 too, so doAfterDocument (:219-220) never skips the accounting that calls the policy.
  2. IndexWriter.writeSomeDocValuesUpdates() passes its != DISABLE_AUTO_FLUSH test (IndexWriter.java:812), but ramBytesUsed > 0.5 * ramBufferSizeMB * 1024 * 1024 (:816) is always false for NaN, so this size-based write-back never runs, however large the buffered updates grow. They are written only on the writer's other paths: opening an NRT reader (:608), commit (:3827), flush() (:4423), a merge of their segment (:5309), or releasing a reader when reader pooling is off (ReaderPool.java:205-224; pooling is on by default, IndexWriterConfig.java:90).

Exposure and likelihood201 words
  • Who is hit: applications that set the RAM buffer from a computed or parsed value that can be NaN. The default (IndexWriterConfig.java:83, 16 MB) and any constant never trigger it. The value can arrive at construction or live through IndexWriter.getConfig(); FreeTextSuggester.build(InputIterator, double) passes its argument straight to this setter.
  • What they see: no error at configuration time. The writer then flushes after every added document, so each document becomes its own tiny segment for the merge policy to merge, and buffered doc-values updates are never written back early because of their size; they wait for the next NRT reader, commit, flush() or merge. The document count and the updated values stay correct, which makes the cause hard to trace back to the setting.
  • Scale: any index size; assertions on and off behave the same. Both effects were run on main; the NaN acceptance itself on 14 releases from 2.3.0 to 10.6.0 (13 in the history probe, 10.5.2 in the independent reproduction).
  • Not claimed: with assertions on, an internal assertion's running maximum in DocumentsWriterFlushControl becomes NaN (assertion state only). The cost in indexing time was not measured.
  • Priority Low: it needs a caller-side NaN and gives no wrong result.

Why it looks unintended

#
  • The method's own message names the valid range: "ramBufferSize should be > 0.0 MB when enabled". NaN is not > 0.0.
  • Only DISABLE_AUTO_FLUSH (-1) turns the buffer off, so NaN is an enabled value, and the javadoc promises an exception for those.
  • No test, javadoc or issue thread accepts NaN on purpose; the check was written <= 0.0 in 2007.
The full argument186 words
  • Contract: LiveIndexWriterConfig.java:162-164 reserves DISABLE_AUTO_FLUSH as the only disabling value; :188-189 promises the exception; :193 gives the range as "> 0.0 MB when enabled".
  • Tests: no Lucene test passes NaN to this setter. TestIndexWriterConfig.testInvalidValues checks only the both-triggers-disabled case of this setter (TestIndexWriterConfig.java:236-251).
  • History: the setter came with LUCENE-843 (cff5767e443, 2007-07-04) and the @throws line and "when enabled" message with LUCENE-1007 (54729a50b67, 2007-10-02, #2083). It was copied unchanged into IndexWriterConfig (LUCENE-2294, 53c19d660aa, 2010) and LiveIndexWriterConfig (LUCENE-4132, a11013a9901, 2012). None of the issue threads #1918, #2083, #3370 or #5204 mentions NaN.
  • Precedent: LUCENE-6982 (fb0aa2dc49c, 2016) made BM25Similarity reject NaN for both parameters (Float.isNaN(b), Float.isFinite(k1) == false) and added NaN tests for both. The LRUQueryCache constructor writes its check in accepting form, skipCacheFactor >= 1 == false // NaN >= 1 evaluates false (LRUQueryCache.java:178), and in #14412 (2025) a maintainer asked to keep rejecting skipCacheFactor = NaN there. The JDK reads "nonpositive" as including NaN: HashMap(int, float) documents an exception when "the load factor is nonpositive" and checks loadFactor <= 0 || Float.isNaN(loadFactor).
The devil's-advocate check162 words

The case for intended: "non-positive" literally means <= 0, and NaN is unordered, so the code does what the @throws clause says. Only a caller bug produces NaN, the flush effect is the same as with a small legal buffer (any size up to 0.05 MB flushes per document on the probe's workload), no result is wrong, and other Lucene setters admit NaN too (TieredMergePolicy's double setters; LRUQueryCache.setSkipCacheFactor has no check at all). A maintainer could reasonably see this as a robustness fix rather than a bug.

Why it still holds: the message states the range as "> 0.0", which NaN fails, and the JDK uses the same word to include NaN. A validation check exists to catch caller errors at configuration time. And where Lucene writes such a check in accepting form it rejects NaN on purpose (BM25Similarity, the LRUQueryCache constructor, #14412). The argument is about impact, not intent, and is why the bug is Low.

Suggested fix

#

Recommended Write the check as (ramBufferSizeMB > 0.0) == false (validated)

Write the check in accepting form: ramBufferSizeMB != DISABLE_AUTO_FLUSH && (ramBufferSizeMB > 0.0) == false (+2/-1 lines). It rejects NaN and keeps every other result. With it the repro and TestIndexWriterConfig pass, assertions on and off, and so do the core format, ECJ and forbidden-apis checks.

public synchronized LiveIndexWriterConfig setRAMBufferSizeMB(double ramBufferSizeMB) {
  if (ramBufferSizeMB != IndexWriterConfig.DISABLE_AUTO_FLUSH
      && (ramBufferSizeMB > 0.0) == false) {
    throw new IllegalArgumentException("ramBufferSize should be > 0.0 MB when enabled");
  }
  // rest unchanged

Write the check as (ramBufferSizeMB > 0.0) == false (validated) (recommended)

#

State the range the message already gives, in Lucene's == false style. NaN, 0.0, -0.0 and -Infinity are rejected; +Infinity is still accepted, and -1 (DISABLE_AUTO_FLUSH) is left to the unchanged second check (accepted only while maxBufferedDocs is enabled, LiveIndexWriterConfig.java:195-199).

public synchronized LiveIndexWriterConfig setRAMBufferSizeMB(double ramBufferSizeMB) {
  if (ramBufferSizeMB != IndexWriterConfig.DISABLE_AUTO_FLUSH
      && (ramBufferSizeMB > 0.0) == false) {
    throw new IllegalArgumentException("ramBufferSize should be > 0.0 MB when enabled");
  }
  // rest unchanged

Trade-offs

  • The only behaviour change: NaN, which the method already documents as invalid, now fails at configuration time with the existing message.
  • No hot-path cost: the check runs once per setter call.
  • The one-line form is 102 characters wide and fails google-java-format; the two-line form is the ./gradlew tidy output.

Downstream note

#

A server that lets users set the writer's RAM buffer and parses it with Double.parseDouble should reject NaN itself until Lucene does.

How it was found

#

A semi-formal proof-obligation check of LiveIndexWriterConfig's documented contract: every value the javadoc rules out must be rejected. NaN was the counterexample for setRAMBufferSizeMB, witnessed by the one-line test on main. Independent reviewers re-ran it, measured the flush effects and tested the case for intended behaviour.

The method in full95 words
  • Method: each setter's documented rejection rule was written as an obligation ("an enabled value that is not > 0.0 throws") and checked against the code path. The ordered-only comparison at LiveIndexWriterConfig.java:192 leaves NaN outside the rejected set; an executable JUnit test confirmed it on main 5adff78bb168 (2026-11-04).
  • Effects: a separate probe, not the repro, measured what the stored NaN does to flushing and doc-values write-back ("The finding in 30 seconds").
  • Reviews: an independent reproduction, an adversarial review by a model from another family (OpenAI GPT-5.6), an intended-behaviour review and a final review; see Independent checks.
