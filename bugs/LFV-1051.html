Sorting on a multi-valued SORTED_NUMERIC field returns the wrong top hits after updateSortedNumericDocValue (doc-values overlays)

On main, with doc-values overlays on by default, one updateSortedNumericDocValue on a multi-valued field breaks SortedNumericSortField: documents {50, 60}, {10, 90}, {30, 40} with doc 2 set to 70 sort doc 2 first, not doc 1. The overlay view does not restart a document's values when sorting reads it twice.

The finding in 30 seconds

#

After the update, the segment reads m through OverlaySortedNumericDocValues: the update layer over the multi-valued base column. Its advanceExact moves only layers that are behind the target, so a second advanceExact on the current document leaves the base column's value cursor where the first read stopped.

Background: doc-values overlays and how a sort reads a value

#
  1. A SORTED_NUMERIC field stores a sorted list of numbers per document. You read it with advanceExact(doc), then nextValue() up to docValueCount() times. Calling advanceExact again on the same document is allowed, and Lucene's own sorting relies on it starting the values over.
  2. With overlays on (main's default), a doc-values update is not a rewrite of the column: it is a small layer holding only the updated documents, merged with the old column at read time until the segment is merged (or the updates are folded into one full column).
  3. SortedNumericSortField keys each document by its minimum (or maximum). Once the top-n queue is full, TopFieldCollector reads every competitive document twice, compareBottom(doc) then copy(slot, doc), and each read starts with advanceExact(doc).

The finding, step by step

#
  1. Index three documents with a multi-valued SortedNumericDocValuesField m: doc 0 = {50, 60}, doc 1 = {10, 90}, doc 2 = {30, 40}. Then call updateSortedNumericDocValue(new Term("id", "2"), "m", 70) with the default IndexWriterConfig on main: the update is stored as a small overlay layer on top of the old column.
  2. Search all documents for the top 1 by new SortedNumericSortField("m", LONG), which sorts by each document's minimum. You expect doc 1: 10 is smaller than 50 and 70. With overlays off, that is what you get.
  3. The collector reads a competitive document twice: compareBottom reads doc 1 as 10, then copy calls advanceExact(1) again. The overlay view does not touch a layer that already sits on doc 1, so the old column's value cursor is not reset and the second read returns 90.
  4. Doc 1 is stored with sort key 90, doc 2 (70) beats it, and you get doc 2, with no error. With a MAX sort the stale cursor can also run past the end of the column and throw.

Who is affected

#

Applications on main (default) or on 10.6.0 with setMaxDocValuesOverlays(n > 0) that call updateSortedNumericDocValue on a field with multi-valued documents and sort on it. Such sorts can be wrong until the segment is merged, and the documents you did not update get the wrong keys. Single-valued fields and NUMERIC/BINARY updates are unaffected; data on disk is correct.

Mechanism, terms and numbers814 words

With doc-values overlays (IndexWriterConfig#setMaxDocValuesOverlays, @lucene.experimental; on by default on main with 8 overlays, opt-in in 10.6.0), a set-only doc-values update is written as a sparse layer and merged with the old column at read time. After IndexWriter#updateSortedNumericDocValue (new in 10.6.0, #16581) on a segment whose SORTED_NUMERIC field is multi-valued in some document, the segment reads the field through OverlaySortedNumericDocValues. Its advanceExact delegates to DocValuesOverlayMerger#advanceExact, which moves only layers whose docID() < target; on advanceExact(docID()) nothing moves, so nextValue() continues on the base column where the previous read stopped instead of restarting the document's values. DocValuesIterator#advanceExact allows target == docID() on purpose (LUCENE-7462: comparators read a value more than once), and TopFieldCollector does exactly that for every competitive hit (compareBottom, then copy). So SortedNumericSortField sorts can return wrong top hits and wrong sort values, silently and the same way every time for the same index and search, until a merge (or a fold to one dense column) rewrites the segment; a MAX sort can instead throw IndexOutOfBoundsException or RuntimeException(EOFException). Three documents and one update suffice: the top hit by minimum is doc 2 instead of doc 1. The documents that go wrong are the ones that were not updated; data on disk is correct. Fields that are single-valued everywhere and NUMERIC/BINARY overlays are not affected. A one-method fix in OverlaySortedNumericDocValues#advanceExact (re-position the winning layer when the target is the current document) passes the test and the doc-values-update, overlay and sort suites.

The mechanism (main 645d4fe14a20)

#
  1. The view. SegmentDocValuesProducer#getSortedNumeric returns the base iterator when a field has one producer, else OverlaySortedNumericDocValues.from(...) (SegmentDocValuesProducer.java:218-224). from takes the singleton OverlayNumericDocValues path only when every layer is single-valued (OverlaySortedNumericDocValues.java:79-89), else builds OverlaySortedNumericDocValues (:91), which "works whether the base column is single- or multi-valued" (:23-28).
  2. Delegation. nextValue() and docValueCount() read layers[merger.valueLayer()] (:41-49); advanceExact(target) is merger.advanceExact(target) (:51-54).
  3. The merger (DocValuesOverlayMerger.java:72-80):
   while (layers[heap[1]].docID() < target) {
     layers[heap[1]].advance(target);
     siftDown();
   }
   docID = target;
   winner = layers[heap[1]].docID() == target ? heap[1] : -1;

A layer already on target is not touched. The class javadoc says layers "are advanced with advance only (never advanceExact) so iteration and random access can be interleaved" (:28-29); it says nothing about re-reading the current document.

  1. The base column's cursor. In the default codec's dense multi-valued iterator, advanceExact sets start/end from the address table and nextValue() is values.get(start++) with no end check (Lucene90DocValuesProducer.java:2061-2072). Not re-positioned, a second read continues with the document's next value, then the next document's values (a neighbour's, or the pre-update values of an updated document), or runs past the end of the column.
  2. The consumer. LongLeafComparator#getValueForDoc calls advanceExact(doc) (LongComparator.java:79-85) for compareBottom, compareTop and copy (:93-107), through SortedNumericSelector.MinValue (SortedNumericSelector.java:135-142: one nextValue()) or MaxValue (:169-174, :194-201: docValueCount() values). Once the queue is full, TopFieldCollector calls compareBottom(doc) (TopFieldCollector.java:93) and, for a competitive hit, copy(bottom.slot, doc) (:116). The first n documents only get copy (:122-126), one read.

The repro, read by read

#

A traced run of the three documents (main, assertions off): copy(doc 0) reads 50, the bottom is 50. compareBottom(doc 1) reads 10: competitive. copy(doc 1) calls advanceExact(1) again; the base layer stays on doc 1 with its cursor after 10, so nextValue() is 90 and doc 1 is stored with key 90. compareBottom(doc 2) reads 70 from the update layer; 70 < 90, so doc 2 replaces doc 1. Top hit: doc 2, key 70. With setMaxDocValuesOverlays(0): doc 1, key 10.

Variants (same mechanism)

#
  • Direct re-read: advanceExact(1), nextValue() = 10, advanceExact(1), nextValue() = 90.
  • A MAX sort (reverse) on the same three documents returns doc 2 (70) instead of doc 1 (90).
  • Two documents {5} (updated to 1) and {10, 90}, MAX descending, top 1: IndexOutOfBoundsException on a ByteBuffersDirectory, RuntimeException(EOFException: read past EOF) on an FSDirectory. Correct with overlays off.
  • Wrong sort keys: with doc 0 updated to 70 instead, the MIN top hit is doc 2 with key 40 (its true minimum is 30); with doc 0 updated to 1, a MAX sort returns the right hit, doc 1, but with key 40, doc 2's value.
  • searchAfter: page 2 after (doc 1, key 10) returns doc 1 again, already on page 1, with key 30 (doc 2's pre-update value); with overlays off it returns doc 0, key 50.
  • Updated documents read correctly: their winning layer is the single-valued update, whose nextValue() returns the same value every time. The wrong keys go to documents that were not updated.
  • Not affected: NUMERIC and BINARY overlays (they have no per-document value cursor) and SORTED_NUMERIC fields that are single-valued in every document of the segment (singleton path): 12,846 re-read checks over 200 random indexes, 0 mismatches.
Exposure and likelihood439 words
  • Who is exposed. Users of the new IndexWriter#updateSortedNumericDocValue (or updateDocValues with a SortedNumericDocValuesField) on a field that is multi-valued in at least one document of the segment; the javadoc and CHANGES both allow a multi-valued field ("The field itself may be single- or multi-valued"). On main this is the default configuration; in 10.6.0 it needs the experimental setMaxDocValuesOverlays(n > 0).
  • Effect. Silent wrong top hits and wrong sort values (FieldDoc.fields) for SortedNumericSortField with MIN or MAX. It shows when the collector re-reads a competitive document that was not updated, so that its values come from the multi-valued base column; that needs more matches than the requested top n (or searchAfter); whether the hits or keys then come out wrong depends on the values, and the same index and search give the same wrong result every time. Sometimes loud: with MAX the stale cursor can run past the column and fail the query (IndexOutOfBoundsException or RuntimeException(EOFException)).
  • How long. Until the segment is merged, or until a fold rewrites the field as one dense column, for readers opened after that (a reader that is already open keeps its view). A fold happens while writing the next set-only update once the field already has maxDocValuesOverlays delta generations; it is a dense rewrite, one producer that reads correctly, when the prior deltas' summed docs-with-value counts reach half the segment's maxDoc. Otherwise a sparse fold keeps the base plus one folded generation, still read through the overlay view.
  • Scale. Three documents and one update suffice. In a random probe with 300 documents of 1 to 3 values each (2 to 11 segments) and 400 single-valued updates (6 seeds, overlay limits 1, 2 and 8), a second read was wrong for 71 to 227 of the 300 documents in each run, while single reads were right in all 73,200 checks and CheckIndex was clean.
  • Not affected. Fields that are single-valued in every document of the segment (the motivating case of #16580), NUMERIC and BINARY overlays, overlays off, and persisted data: in the same probe every single read was right, after the updates and after reopening the writer with overlays off. Merges ran in only 3 of its 18 runs, so for merges the evidence is mainly upstream tests such as TestSortedNumericDocValuesUpdates#testUpdateKeepsOtherDocsMultiValuedAcrossMerge, which pass with the fix.
  • Also executed. searchAfter paging, which reads each hit with compareTop and then copy (with compareBottom first once its queue is full): page 2 can return a hit from page 1 again. Application code that calls advanceExact twice on a document to read its values again gets the direct re-read above.

Why it looks unintended

#
  • advanceExact allows target == docID() on purpose: LUCENE-7462 chose >= so comparators can read a value more than once, and TopFieldCollector does.
  • The default codec, the asserting test wrapper and MemoryIndex (fixed for this in LUCENE-7890) restart the values; with overlays off the index sorts correctly.
  • The update API allows multi-valued fields, and overlays are only a storage choice.
The full argument308 words
  • Contract. DocValuesIterator#advanceExact: "target must be greater than or equal to the current doc ID" (DocValuesIterator.java:24-28). Adrien Grand on LUCENE-7462 (#8514, 2016-10-20): "Initially I wanted to require that the target is strictly greater than the current doc id but this caused issues with comparators that may need to get the value multiple times [...] So the current patch only requires that the target is greater than or equal to the current document."
  • The documented way to re-read. In the 2018 java-user thread "Read DocValue twice", the same maintainer answered: "If you want to read the values again, you need to call setDocument (Lucene < 7.0) or advanceExact (Lucene >= 7.0) before calling nextValue()".
  • Same defect class, fixed before. LUCENE-7890 (#8941, 2017): "The SortedSetDocValues and SortedNumericDocValues instances returned by the MemoryIndex should support subsequent advanceExact(0) invocations"; its test TestMemoryIndex#testDocValues_resetIterator is still on main and calls advanceExact(0) three times, expecting all five values each time (TestMemoryIndex.java:327-366). LUCENE-8117 (#9165, 2018) fixed advanceExact returning invalid SORTED_NUMERIC values in the Lucene54 producer.
  • The other implementations checked restart. The default codec recomputes start on each advanceExact, in the dense (Lucene90DocValuesProducer.java:2061-2067) and the sparse multi-valued iterator (:2184-2198, :2263-2271); MemoryIndex does since LUCENE-7890; AssertingSortedNumericDocValues#advanceExact accepts target >= in.docID() and resets its value budget, valueUpto = 0 (AssertingLeafReader.java:1176-1187). No implementation that continues the cursor was found besides the overlay view (not an exhaustive audit).
  • Overlays are a storage choice. setMaxDocValuesOverlays trades read cost for write amplification (IndexWriterConfig.java:335-342); #16581's description says supporting a multi-valued base is intended ("really it's not hard to support multi-valued SortedNumericDocValues"). With overlays off the same data sorts correctly.
  • Why tests missed it. TestSortedNumericDocValuesUpdates never calls advanceExact and uses SortedNumericSortField only to check that an index-sort field is rejected; the overlay and update tests read each document once.
The devil's-advocate check145 words

Strongest case (the intended-lens reviewers and the adjudication): the merger documents an advance-only design; the SortedNumericDocValues javadoc only says "Do not call this more than docValueCount times for the document" and never says that a repeated advanceExact restarts the values; overlays are @lucene.experimental. So continuing the cursor could be called allowed.

Why it fails: the advance-only rule is about moving layers ("so iteration and random access can be interleaved"), not about re-reading a document; the >= contract exists for comparators that read a value more than once, and core TopFieldCollector is that caller, so the view breaks Lucene's own sorting, not an outside misuse; @lucene.experimental marks API instability, and the feature is on by default on main. A maintainer could also document the restart explicitly, but documentation alone would not repair TopFieldCollector on overlays: a code change is still needed, preferably the overlay-local one.

Suggested fix

#

Recommended Restart the winning layer in OverlaySortedNumericDocValues#advanceExact

In OverlaySortedNumericDocValues.advanceExact, when the target is the current document, call advanceExact(target) on the winning layer so its values start over (+8/-1, one file; the layer already sits on the target, so nothing moves). The test and 10 doc-values-update, overlay and sort suites (138 tests) pass, with assertions on and off.

  @Override
  public boolean advanceExact(int target) throws IOException {
    final boolean sameDoc = target == merger.docID();
    final boolean found = merger.advanceExact(target);
    if (found && sameDoc) {
      // advanceExact(docID()) must restart the document's values, but the merger does not move a
      // layer that already sits on target: re-position the winning layer (target == its docID()).
      layers[merger.valueLayer()].advanceExact(target);
    }
    return found;
  }
All options and trade-offs4 options · 510 words

Two forms of the same restart were built and run in a scratch worktree of 645d4fe14a20: in the view (recommended) and in the shared merger. A value-buffering design and a documentation-only change are listed for completeness.

Restart the winning layer in OverlaySortedNumericDocValues#advanceExact (validated by the checks) (recommended)

#

When the target is the current document and a layer has it, call advanceExact(target) on the winning layer, so its values start over (OverlaySortedNumericDocValues.java, +8/-1). The idea is the first finder's.

  @Override
  public boolean advanceExact(int target) throws IOException {
    final boolean sameDoc = target == merger.docID();
    final boolean found = merger.advanceExact(target);
    if (found && sameDoc) {
      // advanceExact(docID()) must restart the document's values, but the merger does not move a
      // layer that already sits on target: re-position the winning layer (target == its docID()).
      layers[merger.valueLayer()].advanceExact(target);
    }
    return found;
  }

Trade-offs

  • Safe by construction: the winning layer sits on target with a value, so advanceExact(target) is legal, returns true and leaves it there; the merger's heap and its advance-only rule for moving layers are unchanged. NUMERIC and BINARY overlays are untouched.
  • Cost: one extra advanceExact on one layer, only when the same document is positioned again. No benchmark was run.

The same restart inside DocValuesOverlayMerger#advanceExact (validated by the checks)

#

When target == docID and a layer wins, call layers[winner].advanceExact(target); reword the class javadoc, which says "never advanceExact" (+10/-2).

Trade-offs

Covers any future multi-valued overlay built on the merger. Adds the extra call to NUMERIC and BINARY re-reads, which do not need it, and changes a class shared by all overlay types; a committer may still prefer it as the single place that owns positioning.

What the checks validated

  • + this fix instead: the same 10 suites, 138 tests, 2 skipped, 0 failures, with assertions on (not run with assertions off or through check).

Buffer the current document's values in the view (not built)

#

Copy the winning layer's docValueCount() values into an array on every positioning and serve nextValue() from it.

Trade-offs

Independent of how layers behave, but adds a copy for every document positioned, whether it is read once or twice.

Document that advanceExact(docID()) does not restart the values (not recommended)

Trade-offs

Downstream note

#

A returned sort value can come from a neighbouring document of the same field and segment, which matters only to an application that shows sort values to users and hides that neighbour through its own authorization.

How it was found

#

A code-reading hypothesis about the overlay merger's value cursor, confirmed by a bounded-exhaustive check: every short sequence of moves on tiny segments, run on the real merger and view, disagreed with an independent reference exactly when advanceExact was repeated on the current document. An Alloy model found it independently; both led to a public-API JUnit.

The method in full154 words

Method: semi-formal (a code-reading hypothesis witnessed by bounded-exhaustive translation validation), a hunt unit, 2026-10-25. The harness drives the real DocValuesOverlayMerger and OverlaySortedNumericDocValues through every legal move sequence (nextDoc, advance, advanceExact) over up to 3 layers and 5 documents, compares every read with an independently written union reference, and repeats with advanceExact(docID()) allowed and forbidden. Re-run on 645d4fe14a20: 38,874 layer assignments, 386,132 reachable merger states; SORTED_NUMERIC counterexamples only when the repeated advanceExact is allowed, NUMERIC 0 in both modes, 0 everywhere with the fix.

Independently, a hunt unit built an Alloy 6 model of the overlay read protocol, got a 4-step counterexample and confirmed it with a differential test on the real jar. Later units (a hunt unit, a hunt unit with the MAX-sort exception, and round-17 probes) saw it again; the adjudication collapsed all of them into this row and the no-noise gate reduced the repro to one test.

LFV-1051, snapshot of 2026-11-07

Registry title
With doc-values overlays (on by default on main), a second advanceExact on the same document does not restart a multi-valued SORTED_NUMERIC column's values, so SortedNumericSortField sorts return the wrong top hits (or throw)
Area
index / doc-values overlays (OverlaySortedNumericDocValues over DocValuesOverlayMerger), seen through search / field sorting (SortedNumericSelector, LongComparator, TopFieldCollector)
Priority
Medium, rank 96: Deterministic silent wrong top hits for SortedNumericSortField, on by default only on unreleased main and opt-in behind the experimental overlay in 10.6.0, and only after a single-valued update on a field that is really multi-valued and only until a merge.
Impact class
silent wrong results
Impact note
Applications that call updateSortedNumericDocValue (or updateDocValues with a SortedNumericDocValuesField) on a SORTED_NUMERIC field whose segment holds at least one multi-valued document, and then sort on that field with SortedNumericSortField (MIN or MAX) or read a document twice through advanceExact, get wrong top hits and wrong sort keys with no error (with MAX sometimes an IndexOutOfBoundsException or EOFException instead) until a merge rewrites the segment; this is the default configuration on main (11.0.0-SNAPSHOT, overlays on by default) and needs the @lucene.experimental setMaxDocValuesOverlays(n > 0) in the released 10.6.0; three documents and one update suffice, while all-single-valued SORTED_NUMERIC fields (the motivating case of #16580) and NUMERIC/BINARY overlays are not affected.
Summary
You index three documents with a multi-valued SortedNumericDocValuesField m = {50,60}, {10,90}, {30,40}, set doc 2 to the single value 70 with IndexWriter.updateSortedNumericDocValue (default IndexWriterConfig on main), and sort all documents by new SortedNumericSortField("m", LONG), which keys each document by its minimum value. You expect doc 1 first (minimum 10), which is what you get with overlays disabled. You get doc 2: the overlay view ignores a second advanceExact on the document it already sits on, so when the collector reads doc 1 again its value cursor continues at 90 instead of restarting at 10, and with a MAX sort the cursor can run past the end of the column and throw.
Introduced
