IndexWriter deadlocks when another thread's merge fails while commit() waits for SerialMergeScheduler

With SerialMergeScheduler, if a merge on one thread fails (say, on a full disk) while another thread's commit() is starting its merge-on-commit merges, the two threads wait for each other's locks forever and the writer can never be closed. Default settings since 9.3.0 suffice.

The finding in 30 seconds

#

Two locks taken in opposite order. commit() holds the writer's commit lock and waits for SerialMergeScheduler's monitor; the failing merge holds that monitor, and the writer's emergency close on that thread waits for the commit lock.

Background

#
  1. SerialMergeScheduler runs merges on the indexing thread that triggered them, one at a time: its merge() is synchronized, so a second thread that wants to merge waits at the door until the first one is done.
  2. Merge-on-commit (on by default since 9.3.0): commit() asks the merge policy for merges of small segments, hands them to the merge scheduler and waits up to 500 ms for them, all while it holds the writer's commit lock.
  3. Tragic events. When a merge fails, for example on a full disk, IndexWriter closes itself right there, on the merging thread. That close first takes the commit lock, so that it never runs in the middle of a commit.

The finding, step by step

#
  1. Open an IndexWriter with SerialMergeScheduler and otherwise defaults, so commit() waits up to 500 ms for merges of small segments. The index has 3 one-document segments; LogDocMergePolicy merges every 2.
  2. Thread A calls maybeMerge(): SerialMergeScheduler runs a 2-segment merge on thread A, inside its synchronized merge(). The test adds 1 document, then thread B calls commit(): it takes the writer's commit lock, picks a commit merge and waits to enter SerialMergeScheduler.merge.
  3. Thread A's merge now fails with IOException("simulated disk full"). You expect the writer to close itself, both threads to finish and commit() to throw, as with ConcurrentMergeScheduler or with merge-on-commit off.
  4. Instead A's emergency close needs the commit lock that B holds, while B waits for the scheduler that A holds. After 10 s the JVM deadlock detector lists both threads. close() hangs and the write lock stays held until the process restarts.

Who is affected

#

Applications that set SerialMergeScheduler (not the default) and commit while other threads index: 9.3.0 and later with defaults, 8.6.0-9.2.x only with merge-on-commit opted in. One merge failure (full disk, I/O error) during the commit's wait is enough; no scale needed. The writer then hangs for good and keeps its write lock until restart.

Mechanism, terms and numbers662 words

With merge-on-commit (maxFullFlushMergeWaitMillis > 0, 500 ms by default since 9.3.0), commit() holds IndexWriter's commitLock while it calls mergeScheduler.merge(mergeSource, MergeTrigger.COMMIT). SerialMergeScheduler.merge is synchronized and runs merges on the calling thread, so if another application thread is already inside it running a merge, commit() waits at the monitor, still holding commitLock. If that merge fails (a full disk, any I/O error), IndexWriter treats the failure as tragic and closes itself on the merging thread; the close (rollbackInternal) needs commitLock while that thread still holds the scheduler's monitor. The two threads deadlock: the JVM deadlock detector lists both, Thread.interrupt() does not free them, close() and rollback() from other threads hang, and the write lock stays held until the process restarts; the last commit stays intact. The same failure closes the writer cleanly with ConcurrentMergeScheduler or with merge-on-commit off. The commit-time merge call came with LUCENE-8962 in 8.6.0 (opt-in); LUCENE-10078 made merge-on-commit the default in 9.3.0. A small change in SerialMergeScheduler (a timed lock that checks the writer for a tragedy while it waits, as ConcurrentMergeScheduler already does) makes commit() throw instead; with it the repro passes, and 184 tests in the 14 closest suites and 1,395 tests of the whole org.apache.lucene.index package pass.

The code (main 645d4fe14a20)

#
  1. Commit holds commitLock across its commit merges. commitInternal takes synchronized (commitLock) (IndexWriter.java:4242) and calls prepareCommitInternal (:4253), which takes it again (:3775), flushes and selects point-in-time merges (preparePointInTimeMerge(toCommit, ..., MergeTrigger.COMMIT, ...), :3863-3864). Then, still under commitLock: eventListener.beginMergeOnFullFlush (:3891), mergeScheduler.merge(mergeSource, MergeTrigger.COMMIT) (:3893), pointInTimeMerges.await(maxCommitMergeWaitMillis, ...) (:3894).
  2. SerialMergeScheduler serializes merges on its own monitor. public synchronized void merge(...) (SerialMergeScheduler.java:32) loops getNextMerge() / mergeSource.merge(merge) on the calling thread (:33-39). Its javadoc says the method is "synchronized" "so that even if the application is using multiple threads, only one merge may run at a time" (:27-29).
  3. A merge failure is tragic and closes the writer on the merging thread. IndexWriter.merge catches any Throwable and calls tragicEvent(t, "merge") (IndexWriter.java:5109-5113), then maybeCloseOnTragicEvent (:6090-6106), then rollbackInternal, which takes synchronized (commitLock) (:2586-2590: "Make sure no commit is running, else e.g. we can close while another thread is still fsync'ing"). The thread is still inside SerialMergeScheduler.merge, holding its monitor.
  4. The cycle. The committer holds commitLock and waits for the scheduler's monitor; the merger holds the monitor and waits for commitLock. Both are blocked on monitor entry, which Thread.interrupt() cannot break.
  5. Why ConcurrentMergeScheduler escapes. LUCENE-10078 made getNextMerge() and hasPendingMerges() throw once the writer has a tragedy (IndexWriter.java:2538-2542, :2558-2562). A committer stalled in ConcurrentMergeScheduler waits in wait(250) and re-checks hasPendingMerges() (ConcurrentMergeScheduler.java:609-636, :647-655), so it throws and releases commitLock. With SerialMergeScheduler the committer never gets past monitor entry.
  6. Lucene avoids this cycle elsewhere. commit() and prepareCommit() run their post-commit maybeMerge outside commitLock: "we must do this outside of the commitLock else we can deadlock" (IndexWriter.java:3738, :4264, LUCENE-7570). getReader waits for its merge-on-refresh merges outside fullFlushLock "since the merge might hit a tragic event and that must not be reported while holding that lock" (:626-632, :738). The merge-on-commit call at :3893 is the one merge call still made under commitLock.

What happens after the deadlock

#

From the verifiers' probes on main and 10.5.2: Thread.interrupt() leaves both threads BLOCKED; rollback() or close() from a third thread hangs in shouldClose / doWait; a new IndexWriter or CheckIndex on the same path fails with LockObtainFailedException; other threads' addDocument, commit and NRT reopen throw AlreadyClosedException at once; a copy of the last commit opens and passes CheckIndex (the live directory stays locked). With merge-on-commit off, the same failure makes addDocument throw the IOException and commit() throw "this writer hit an unrecoverable error; cannot complete commit". With ConcurrentMergeScheduler, commit() throws "this writer hit an unrecoverable error" and both threads finish.

Exposure and likelihood295 words
  • Who. Applications that configure SerialMergeScheduler and call commit() while another thread's indexing call (addDocument, flush, maybeMerge, forceMerge) runs a merge inside it. Merge-on-commit is on by default since 9.3.0 (500 ms; the stock TieredMergePolicy and LogMergePolicy select small-segment merges at commit). In 8.6.0-9.2.x it needs an explicit nonzero wait and a policy that implements findFullFlushMerges. ConcurrentMergeScheduler, the default, is not affected.
  • Trigger. Any merge failure at that moment: a full disk, another I/O error, or an exception from inside a merge. The window: the other thread's merge must fail while a commit waits at its commit-merge call (IndexWriter.java:3893), after the commit has selected commit merges and before that merge ends.
  • Effect. A permanent hang instead of a clean tragic close: two threads stuck, close() and rollback() hang, the write lock stays held, so the index cannot be written again until the process restarts. Documents added since the last commit are lost, as with the clean close.
  • Not affected. The last commit stays intact: a copy of it opens and passes CheckIndex (the live directory stays locked). No corruption and no wrong search results were seen.
  • How likely. Rare: SerialMergeScheduler with concurrent commits is uncommon and merge failures are rare events. It was first seen unforced in a randomized stress run. Lucene's own randomized tests pick SerialMergeScheduler rarely and always with a merge-on-commit wait of at least 200 ms.
  • Workaround. With SerialMergeScheduler, setMaxFullFlushMergeWaitMillis(0); or ConcurrentMergeScheduler (setMaxMergesAndThreads(1, 1) for one merge at a time, as mikemccand suggested in #6727). Executed: the verifiers' wait-0 and default-ConcurrentMergeScheduler controls, and a setMaxMergesAndThreads(1, 1) run (commit() throws, the writer closes, no deadlock).
  • Not shown. prepareCommit() and close() with commitOnClose reach the same prepareCommitInternal (by reading, not executed).

Why it looks unintended

#
  • IndexWriter's own rule: "we must do this outside of the commitLock else we can deadlock" (LUCENE-7570 fixed this lock pair elsewhere).
  • testDeadlockStalledFullFlushMerges requires commit() to throw, not hang, when a merge fails during merge-on-commit; it tests only ConcurrentMergeScheduler.
  • The javadoc's note that commit will "wait for the merge to finish" covers a wait that ends; this one never can.
The full argument179 words
  • The contract. "IndexWriter instances are completely thread safe, meaning multiple threads can call any of its methods, concurrently" (IndexWriter.java:167-170). getTragicException: "If this IndexWriter was closed as a side-effect of a tragic exception, e.g. disk full while flushing a new segment, this returns the root cause exception" (:6108-6111). A disk-full merge is meant to close the writer, not hang it.
  • IndexWriter's own rule. "we must do this outside of the commitLock else we can deadlock" (IndexWriter.java:3738, :4264), from LUCENE-7570 (#8621, 2b073a2f296, 2016: "don't run merges while holding the commitLock to prevent deadlock when merges are stalled and a tragic merge exception strikes"). Merge-on-commit (2020) added a new merge call under commitLock.
  • The test. TestTragicIndexWriterDeadlock.testDeadlockStalledFullFlushMerges (TestTragicIndexWriterDeadlock.java:106-172, LUCENE-10078) asserts that commit() throws "this writer hit an unrecoverable error" when a merge fails during merge-on-commit. It uses ConcurrentMergeScheduler only.
  • A supported combination. SerialMergeScheduler is public and not deprecated, its javadoc names multi-threaded applications (SerialMergeScheduler.java:27-29), IndexWriterConfig.java:495-497 documents it with merge-on-commit, and LuceneTestCase combines the two (LuceneTestCaseParent.java:1710-1711, :1788).
The devil's-advocate check311 words

The strongest case: the setMaxFullFlushMergeWaitMillis javadoc says "If SerialMergeScheduler is used and a non-zero timeout is configured, full-flush merges will always wait for the merge to finish without honoring the configured timeout" (IndexWriterConfig.java:495-497). In the 2020 review of this exact call (apache/lucene-solr#1552), s1monw asked "what if we has a MergeScheduler configured that blocks on this call like SerialMergeScheduler? ... I think we should make sure that this is not trappy", and then concluded "its rather a rare combination ... I think we are fine as it is"; LUCENE-10078 (#921) added the javadoc note. "This blocking in SMS is by design" (mikemccand, #6374, answering s1monw's proposal there to "use a tryLock operation instead of syncing the entire method"), mikemccand also proposed removing SerialMergeScheduler (#6727), and merge scheduling is an expert API.

Why it fails: the note and the review accept a wait for a merge to finish. Here the merge has already failed, and its thread can never leave SerialMergeScheduler.merge, because the tragic close it runs needs the lock the waiting commit holds; nobody in #1552 or #921 discussed a failing merge, the tragic rollback or commitLock. Blocking by design is a wait that ends when the merge ends; the recommended fix keeps that blocking (its tryLock only stops waiting once the writer has a tragedy), so it is not the #6374 change. #6727 is still open (rmuir objected), and the class is public and not deprecated. Lucene fixed this lock pair as a bug at the post-commit merge call (LUCENE-7570), and LUCENE-10078, which turned full-flush merges on by default, added the tragedy checks and a test that make the ConcurrentMergeScheduler variant throw instead of hang. Verdict: not intended. (s1monw flagged this call for SerialMergeScheduler in that review, as a wait, not a deadlock, and proposed a tryLock in #6374; credit them where the issue cites either.)

Suggested fix

#

Recommended SerialMergeScheduler: timed lock that checks for a tragedy while it waits

In SerialMergeScheduler, replace the synchronized monitor with a ReentrantLock taken by tryLock(250 ms) in a loop that calls mergeSource.hasPendingMerges(), which throws once the writer has a tragedy (as in ConcurrentMergeScheduler's stall loop). commit() then throws "this writer hit an unrecoverable error" and frees the commit lock. Validated: the repro passes, so do 1,395 tests of the org.apache.lucene.index package.

All options and trade-offs5 options · 862 words

One fix was validated in a scratch worktree of 645d4fe14a20; the others are directions, not attempted. The cycle can be broken on either side: the committer must not wait uninterruptibly for the scheduler while it holds commitLock, or the tragic close of a merging thread must not wait for commitLock while it holds the scheduler.

SerialMergeScheduler: timed lock that checks for a tragedy while it waits (validated by the checks) (recommended)

#

One file, +27/-8 in SerialMergeScheduler.java. Merges stay serial (one ReentrantLock, reentrant like the monitor). A waiting thread retries tryLock(250, MILLISECONDS) and calls mergeSource.hasPendingMerges() in between, which throws IllegalStateException ("this writer hit an unrecoverable error; cannot merge") once the writer has a tragedy (IndexWriter.java:2558-2562): the same check that lets ConcurrentMergeScheduler's stalled committer escape. Without a tragedy the behaviour is unchanged: the committer waits for the other thread's merges, then runs its commit merges. Excerpt below (the new field and merge()).

  private final ReentrantLock mergeLock = new ReentrantLock();

  @Override
  public void merge(MergeSource mergeSource, MergeTrigger trigger) throws IOException {
    // Do not block forever while another thread merges: IndexWriter calls this for merge-on-commit
    // while it holds its commit lock, and if the other thread's merge hits a tragic event, its
    // rollback waits for that commit lock. hasPendingMerges() throws once the writer hit a tragedy.
    try {
      while (mergeLock.tryLock(250, TimeUnit.MILLISECONDS) == false) {
        mergeSource.hasPendingMerges();
      }
    } catch (InterruptedException ie) {
      throw new ThreadInterruptedException(ie);
    }
    try {
      while (true) {
        MergePolicy.OneMerge merge = mergeSource.getNextMerge();
        if (merge == null) {
          break;
        }
        mergeSource.merge(merge);
      }
    } finally {
      mergeLock.unlock();
    }
  }

Trade-offs

  • A subclass whose merge override is itself synchronized keeps the deadlock: it locks the same scheduler object before super.merge reaches the new lock. Lucene's tests have three overrides that call super.merge, two synchronized (TestIndexWriterMergePolicy.java:568, BaseMergePolicyTestCase.java:83) and one not (:631); they pass with the fix, but the two would need synchronized dropped to be covered.
  • Compatibility: SerialMergeScheduler no longer synchronizes on itself, so code that locked the scheduler object to keep merges out would no longer do so (worth a CHANGES note).
  • A waiting thread wakes every 250 ms (the period ConcurrentMergeScheduler.doStall uses).
  • After a tragedy a waiting thread throws at its next check, at most 250 ms later (in the outcome check the committing thread ended 262 ms after it started), instead of after the failing thread's rollback; it is the exception getNextMerge() would throw to it anyway.
  • Interrupting a waiting thread now throws ThreadInterruptedException, as the IndexWriter javadoc describes for waits; the monitor ignored interrupts.
  • It fixes the SerialMergeScheduler case only: a custom MergeScheduler that blocks the same way under commitLock keeps the hazard. The escape relies on hasPendingMerges() throwing after a tragedy, which IndexWriter's own MergeSource does (a method synchronized on the writer).

SerialMergeScheduler: do not run COMMIT-triggered merges

#

Return at once for MergeTrigger.COMMIT (one of the options s1monw listed in the apache/lucene-solr#1552 review). The commit then waits at most maxFullFlushMergeWaitMillis and the pending merges run at the next merge call.

Trade-offs

Turns merge-on-commit off for SerialMergeScheduler users and changes behaviour that IndexWriterConfig.java:495-497 documents. Not attempted.

IndexWriter: no commit-time merge call under commitLock

#

Run the commit's point-in-time merges without holding commitLock, as LUCENE-7570 did for the post-commit merge.

Trade-offs

Fixes every scheduler, but commitLock protects the commit point from prepare to finish (prepareCommit/commit pairing, rollback exclusion); a larger change in a delicate path. Not attempted.

IndexWriter: a tragic close that starts inside a merge does not wait for commitLock

#

Record the tragedy, leave the scheduler, and close afterwards (or let the commit thread close the writer).

Trade-offs

Changes when the writer closes on a tragedy for every scheduler; LUCENE-6790 added the commitLock wait on purpose ("block commit while rollback runs"). Not attempted.

Workaround for users today

#

With SerialMergeScheduler, setMaxFullFlushMergeWaitMillis(0); or use ConcurrentMergeScheduler (setMaxMergesAndThreads(1, 1) for one merge at a time, as mikemccand suggested in #6727).

Trade-offs

Executed: the verifiers' wait-0 and default-ConcurrentMergeScheduler controls, and a setMaxMergesAndThreads(1, 1) run; the same failure then closes the writer cleanly.

Downstream note

#

Downstream: the indexing engines of Elasticsearch and OpenSearch use their own concurrent schedulers, and Solr uses SerialMergeScheduler only if solrconfig.xml selects it (code read, nothing run downstream).

How it was found

#

A randomized stress test of IndexWriter with injected merge I/O faults and a sequence-number replay oracle hung with SerialMergeScheduler and merge-on-commit; its thread dump showed the lock cycle. The finder reduced it to a latch-driven JUnit; independent AI tools reproduced it and wrote stock-policy versions.

The method in full108 words

Method: non-formal baseline (a randomized stress harness, not a model checker).

  • The harness (stage 3: merge on full flush with SerialMergeScheduler, injected merge I/O faults) hung in round 29 of a local run; its JVM thread dump showed commit() BLOCKED at SerialMergeScheduler.merge from prepareCommitInternal and an indexing thread BLOCKED in rollbackInternal from tragicEvent.
  • The finder reduced it to a deterministic JUnit with a scripted merge policy; an independent reproducer wrote its own main(), and a devil's-advocate verifier wrote a stock-policy JUnit (default wait, LogDocMergePolicy, a simulated "No space left on device"). The minimal test here is that stock-policy test cut down to one method.

History

#

Introduced by LUCENE-8962 (apache/lucene-solr#1617, 7f352a96659, merged 2020-06-27), which added the commit-merge call under commitLock; first released in 8.6.0 (opt-in). On by default since 9.3.0 (LUCENE-10078). Every release from 8.6.0 through 10.6.0 is affected; not fixed upstream as of 2026-10-31.

Versions tested6 rows

Introduced by 7f352a96659 (main) and 9b1c92809e7 (branch_8x), LUCENE-8962 "Merge small segments on commit" (s1monw, with msfroh, msokolov and mikemccand). The other edges are older: SerialMergeScheduler.merge is synchronized since 2.3 (299d6357dd2), a merge failure is tragic since 5.3.0 (LUCENE-6579, 926397824e9), the tragic rollback takes commitLock since 5.4.0 (LUCENE-6790, 690f6d6578b). LUCENE-10078 (#921, b5795db0cf5, 9.3.0) set the default wait to 500 ms and made the stock policies return full-flush merges; from 9.9.0 (#12549) a commit with nothing buffered also runs commit merges.

Finding record

LFV-581, snapshot of 2026-11-07

Registry title
With SerialMergeScheduler, a merge that fails while another thread's commit() waits to run its merge-on-commit merges deadlocks both threads forever (commit() holds commitLock and waits for the scheduler's monitor; the failing merge holds that monitor and its tragic rollback waits for commitLock), and the writer can no longer be closed (since 8.6.0; with default merge-on-commit settings since 9.3.0)
Area
index / IndexWriter commit (merge-on-commit under commitLock, SerialMergeScheduler, tragic-event rollback)
Priority
Low, rank 799: A permanent deadlock keeps the write lock held until restart, but it needs the non-default SerialMergeScheduler, concurrent commit and indexing, and a merge failure such as a full disk, so it follows the deterministic NoMergeScheduler hang.
Impact class
hang
Impact note
Hits applications that configure SerialMergeScheduler (not the default; the default ConcurrentMergeScheduler is unaffected, executed control) and call commit() (executed) or prepareCommit() (same code path, by reading) while other threads index, when a merge on an indexing thread fails (a full disk or another I/O error, or a document that makes merges fail through another bug) during the commit's merge-on-commit wait, which is on by default since 9.3.0 (500 ms wait, stock Log/Tiered policies; opt-in in 8.6.0-9.2.x); no scale is needed and it happens with -ea and -da; the commit thread and the merging thread then block forever on each other's monitors (Thread.interrupt does not free them), close() and rollback() from other threads hang, and the write lock stays held until the process restarts, while the last commit stays intact (it opens and passes CheckIndex).
Summary
You configure IndexWriter with SerialMergeScheduler and keep merge-on-commit on (the default since 9.3); one thread calls commit() while another thread's addDocument runs a merge, and that merge fails, for example because the disk is full. You expect IndexWriter to close itself on the tragic merge failure and both calls to return with an exception, as they do with ConcurrentMergeScheduler or with merge-on-commit off. Instead commit() holds IndexWriter's commit lock while it waits to enter SerialMergeScheduler's synchronized merge method, and the failing merge thread, still inside that method, waits for the commit lock in the tragic rollback, so both threads hang forever and the writer cannot be closed.
