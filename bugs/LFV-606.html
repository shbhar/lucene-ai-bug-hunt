MatchRegionRetriever.highlightDocument throws NullPointerException when a FieldValueProvider returns the null its javadoc allows

FieldValueProvider.getValues may return null "if the field is not loaded or does not exist", but when a custom provider does so for a matched field, MatchRegionRetriever.highlightDocument throws NullPointerException instead of returning no highlights. Every release from 10.0.0 to 10.6.0 and main have it; returning an empty list works.

The finding in 30 seconds

#

The default offset strategies use the list getValues returns without checking for null. In-tree callers are safe only because the built-in provider never returns null.

Background: how matchhighlight finds hit regions

#
  1. MatchRegionRetriever computes, for a document the query matched, the character ranges ("hit regions") to highlight in each matched field.
  2. When the index has no offsets for a field, or a match does not report them, it re-analyzes the field's text to turn match positions into character offsets. It gets that text from a FieldValueProvider.
  3. highlightDocuments(...) uses a built-in provider over the stored fields; the low-level highlightDocument(...) takes your own provider.

The finding, step by step

#
  1. Index one document whose field body = "foo bar" is indexed with positions but not stored (TextField, Field.Store.NO). The query body:foo matches it.
  2. Call the low-level highlightDocument(...) with your own FieldValueProvider. body is not in the stored document, so getValues("body") returns null, as its javadoc allows: "null if the field is not loaded or does not exist".
  3. You expect no hit regions (an empty result map). On main, that is what the same call returns when the provider gives an empty list, and what the built-in highlightDocuments(...) path returns for this index.
  4. Instead it throws NullPointerException ("values" is null) at OffsetsFromPositions.java:70, with assertions on and off: the default offset strategies call values.isEmpty() or values.size() on it without a null check.
  5. Only callers with their own provider are hit: MatchHighlighter and highlightDocuments(...) use a built-in provider that returns an empty list. Workaround: return List.of().

Who is affected

#

Applications that call the low-level highlightDocument(...) with their own FieldValueProvider and return null for a matched field whose offsets must be recomputed from its text: a field indexed without offsets, or one indexed with offsets when a match carries none (for example Intervals.extend). An opt-in expert API: MatchHighlighter and highlightDocuments(...) are not affected. One clean exception per call.

Mechanism, terms and numbers678 words

MatchRegionRetriever.highlightDocument is a public low-level method that "can be used with custom document FieldValueProvider" (MatchRegionRetriever.java:390-393 at 645d4fe14a20). FieldValueProvider#getValues documents that it returns the field's values "or null if the field is not loaded or does not exist for the field" (:100-104). When a custom provider returns that null for a field the query matched, the default offset strategies use it without a check: values.isEmpty() at OffsetsFromPositions.java:70 for a positions field, values.size() at OffsetsFromTokens.java:74 for a DOCS or DOCS_AND_FREQS field, and, for a field indexed with offsets, the OffsetsFromMatchIterator.java:66 fallback whenever a match carries no offsets (for example an Intervals.extend query). The public, non-default OffsetsFromValues loops over it at OffsetsFromValues.java:51. The call throws NullPointerException instead of returning no hit regions; on main, no hit regions is what an empty list gives on the same index and what the built-in highlightDocuments(...) path gives, because its private provider maps a missing field to List.of() (:535-538). The null clause came with #12881, so every release from 10.0.0 to 10.6.0 and main are affected. In the cases run: no wrong results, no corruption, no hang, one clean exception for that call.

The mechanism (main 645d4fe14a20, lucene/highlighter/.../search/matchhighlight/)

#
  1. The contract. FieldValueProvider is a public interface: "@return Return a list of values for the provided field name or {@code null} if the field is not loaded or does not exist for the field." (MatchRegionRetriever.java:99-105).
  2. The entry point. highlightDocument(LeafReaderContext, int, FieldValueProvider doc, ToIntFunction<String>, Map<String, List<OffsetRange>>) is public, documented as usable with a custom provider, and states no non-null precondition (:390-400). For each query-affected highlighted field with matches (:410-418) it calls offsetStrategy.get(matchesIterator, doc) (:434) and stores non-empty ranges (:435-437).
  3. The default strategy per field (:488-505): positions without offsets use OffsetsFromPositions (:492-493); positions with offsets use OffsetsFromMatchIterator with an OffsetsFromPositions fallback (:489-490); DOCS, DOCS_AND_FREQS and DOCS_AND_CUSTOM_FREQS use OffsetsFromTokens (:495-505).
  4. No strategy checks for null:
    • OffsetsFromPositions.java:59 passes doc.getValues(field) on, and :69-72 does
// If values are not stored, there is nothing to highlight...
if (values.isEmpty()) {        // :70  NullPointerException when values == null
  return List.of();
}
  • OffsetsFromTokens.java:54 reads the list and :74 calls values.size().
  • OffsetsFromValues.java:47 reads it and :51 loops over it (a public strategy a caller may choose; never a default).
  • OffsetsFromMatchIterator.java:64-66 falls back to OffsetsFromPositions with doc.getValues(field) as soon as one match reports a negative offset (:52-57). That happens on a field indexed with offsets too: matches of Intervals.extend always report offset -1 (ExtendedIntervalsSource.java:89-101 in lucene/queries), and Lucene's own testDegenerateIntervalsWithOffsets (TestMatchRegionRetriever.java:393-415) uses this fallback with the built-in provider.
  1. Why in-tree callers never see it. The only in-tree provider, the private StoredFieldsVisitor.getValues (:535-538), returns values == null ? List.of() : values, and the only in-tree call of highlightDocument (:372) passes it. No Lucene test implements FieldValueProvider or calls highlightDocument directly.

Exposure and likelihood229 words
  • Who is hit. Callers of the public highlightDocument(...) with a hand-written FieldValueProvider that returns null for a highlighted field the query matched, when the field's offsets have to be recomputed from its text: a field indexed without offsets (positions-only, DOCS, DOCS_AND_FREQS), a field indexed with offsets when a match carries no offsets (for example an Intervals.extend query, whose matches report offset -1), or the opt-in OffsetsFromValues. In every such case run, the call throws.
  • Default vs opt-in. Default strategies and settings, no special codec, no scale; opt-in on the API side. MatchHighlighter and highlightDocuments(...) use the built-in provider and are not affected. On a field indexed with offsets, a query whose matches carry offsets (a term query, for example) never reads the values. The recorded GitHub code searches (default branches) found no use of MatchRegionRetriever in Solr, Elasticsearch or OpenSearch.
  • Effect. An unchecked NullPointerException for that document's highlight call. In the cases run: no wrong regions, no corruption, no hang; 1,000 failing calls left no state behind in the retriever or the shared analyzer. When several fields are highlighted, the caller's output map may already hold the (correct) ranges of fields handled before the failing one, so discard it after a failure. Whether it costs one snippet or a whole result page depends on the application's own error handling.
  • Workaround. Return List.of() instead of null.

Minimal repro

#

One JUnit test in lucene/highlighter, public API only: one document with an unstored TextField, the query body:foo, and a provider whose getValues returns null. Deterministic, single thread. It fails on main with assertions on and off, and on the 10.0.0 and 10.6.0 release jars.

highlightDocument returns normally and the output map stays empty: no hit regions for a field with no values.

NullPointerException ("values" is null) at OffsetsFromPositions.java:70 on main (:96 on 10.0.0 to 10.6.0), with assertions on and off.

The only randomness is the test framework's per-seed default codec, locale and time zone (seed DEADBEEF ran with codec=Asserting(Lucene104), locale=brx, timezone=Asia/Tokyo); the result was the same for every seed tried (DEADBEEF, 5EED1234 three times, 7EB4A001, 7EB4A002).

Why it looks unintended

#
  • getValues documents null "if the field is not loaded or does not exist"; highlightDocument is documented for custom providers, with no precondition.
  • Main treats missing values as "nothing to highlight" (#15577); an empty list on the same index gives no highlights.
  • #12881 added the null clause without a null check in the strategies; its review never discussed null.
The full argument231 words
  • The javadoc allows null and names the case: "or {@code null} if the field is not loaded or does not exist for the field" (MatchRegionRetriever.java:101-102). An indexed but unstored field is the natural reading of the "does not exist" case (the javadoc does not define it further).
  • The entry point invites custom providers: "Low-level method for retrieving hit ranges for a single document. This method can be used with custom document FieldValueProvider." (:390-393). No precondition, and nothing in the package is marked @lucene.experimental or @lucene.internal.
  • Main defines missing values as "nothing to highlight": #15577 (548ae997d12, 2026-01-15) added "If values are not stored, there is nothing to highlight..." and an early return for an empty list (OffsetsFromPositions.java:69-72). The test expects the same for null.
  • History: #12881 (755de5aae33, 2023-12-07) replaced the 9.x interface List<CharSequence> getValues(String field) throws IOException, which had no null clause and whose default provider never returned null. In the same commit it added the null clause, wrote the new provider to return List.of() for a missing field, and changed the strategies only from List<CharSequence> to List<String>. Its body, reviews and comments never discuss null; MIGRATE.md calls it "Minor API changes", and neither it nor CHANGES.txt mentions null.
  • Tests: no upstream test returns null from a provider or expects an exception for it.
The devil's-advocate check190 words

Strongest case (from the intended-behaviour checker, the cross-model reviewer and the adjudication): a custom provider is expected to supply every query-affected highlighted field, as the constructors' field-loading guidance describes (MatchRegionRetriever.java:118-128 and :153-163), and the FieldValueProvider javadoc itself sends readers to that guidance "on which fields are available through this interface" (:93-98); the null clause is a javadoc slip (its wording, "does not exist for the field", is garbled); the strategies date from 9.x, where null was impossible; and the method is labelled low-level. So the javadoc, not the code, should change.

Why it fails, in part: the cross-reference makes the argument stronger than it first looks, but the guidance only says which fields the predicates load; it does not require non-null values or say what null means, while the getValues javadoc explicitly allows null. And "does not exist" is not a loading question: a provider that loads every stored field and returns null only for a field the document does not store still throws, while the empty-list and built-in controls on the same index give no regions. A javadoc-only fix is still a fair outcome.

Suggested fix

#

Recommended Treat a null values list as empty in the three strategies

Treat a null list as empty, "nothing to highlight", in OffsetsFromPositions.convertPositionsToOffsets (which also covers the OffsetsFromMatchIterator fallback), OffsetsFromTokens.get and OffsetsFromValues.get (+10/-2 lines in three files). With it the minimal test passes with assertions on and off, and the whole lucene/highlighter suite passes (35 classes, 723 tests, 0 failures).

// OffsetsFromPositions.convertPositionsToOffsets
// If values are not stored (or not loaded), there is nothing to highlight...
if (values == null || values.isEmpty()) {
  return List.of();
}

// OffsetsFromTokens.get and OffsetsFromValues.get
List<String> values = doc.getValues(field);
if (values == null) {
  return List.of();
}

Treat a null values list as empty in the three strategies (validated by the checks) (recommended)

#

In OffsetsFromPositions.convertPositionsToOffsets change the early return to if (values == null || values.isEmpty()) return List.of();; in OffsetsFromTokens.get and OffsetsFromValues.get return List.of() right after doc.getValues(field) when it is null.

// OffsetsFromPositions.convertPositionsToOffsets
// If values are not stored (or not loaded), there is nothing to highlight...
if (values == null || values.isEmpty()) {
  return List.of();
}

// OffsetsFromTokens.get and OffsetsFromValues.get
List<String> values = doc.getValues(field);
if (values == null) {
  return List.of();
}

Trade-offs

  • Matches the javadoc and the existing "nothing to highlight" early return; non-null lists behave exactly as before, and the check is one comparison per highlighted field.
  • Covers custom callers of the public strategy classes too. A custom OffsetsRetrievalStrategy that calls getValues still has to handle null itself.
  • A 10.x backport needs the same checks; there a positions field also throws for an empty list (fixed on main by #15577), so the backport may want #15577's early return as well.
  • Open PR #16 (2021) adds one more getValues loop in OffsetsFromMatchIterator; it would need the same check if it is ever merged.

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20 with the repro test added, seed DEADBEEF: the repro test passes with -Ptests.asserts=true and false.
  • The whole :lucene:highlighter:test with the fix, assertions on: 35 classes, 723 tests, 0 failures. The same suite without the fix: 723 tests, 1 failure, the repro.
  • :lucene:highlighter:checkGoogleJavaFormat passes with the fix.
  • Earlier hunt runs: with the fix shadowed, the minimal test (main, -ea and -da), the independent reproduction's 7-test class (7 of 7) and the intended-behaviour check's unstored-field test (5 of 5) pass; the 48 matchhighlight tests passed with it on a9779ef3c193.

Change the contract: getValues must return an empty list (not run)

#

Rewrite the getValues javadoc to say that a field with no values (not loaded or absent) returns an empty list, never null.

Trade-offs

No code change and no cost, and it matches what the built-in provider already does. But existing custom providers that followed the current javadoc keep failing with an NPE, and nothing tells them why; a clear exception or the null check would still help them.

How it was found

#

Code reading: while writing a model of the matchhighlight passages path, the finder read the FieldValueProvider contract and saw that the strategies never check the null it allows. The model drives only the built-in path, so no tool produced the signal; a public-API JUnit then showed the NPE.

The method in full89 words

Method: non-formal (code reading, then a directed JUnit), 2026-10-26, main a9779ef3c193. The hunt unit built an end-to-end model of the matchhighlight passages path; that model drives only highlightDocuments(...), whose provider never returns null. Reading the interface it relies on showed the documented null return and the unguarded strategies. The finder's JUnit (a provider that returns null for every field: positions field, DOCS_AND_FREQS field, offsets control) failed 2 of 3 with -ea and -da. A later minimisation step replaced it with the one-method test shown here.

#

Impact note
Hits only applications that call the public low-level MatchRegionRetriever.highlightDocument(...) with their own FieldValueProvider and return null, as its javadoc allows, for a highlighted field that the query matched and whose offsets must be recomputed from the field's text (a positions-only field through the default OffsetsFromPositions, a DOCS or DOCS_AND_FREQS field through the default OffsetsFromTokens, the OffsetsFromMatchIterator fallback, or OffsetsFromValues): that call throws an unchecked NullPointerException instead of returning no hit regions, deterministically, with default codec and settings, with -ea and -da, and with no scale needed; there are no wrong results, no corruption and no hang, a field indexed with offsets is affected only when a match carries no offsets (for example Intervals.extend), and MatchHighlighter and highlightDocuments(...) are not affected because the built-in provider returns an empty list; workaround: return an empty list instead of null.
Summary
You call MatchRegionRetriever.highlightDocument with your own FieldValueProvider, for example one backed by a Map built from the document's stored fields, and for a field that is indexed but not stored it returns null, exactly as FieldValueProvider#getValues documents ('null if the field is not loaded or does not exist'). You expect no hit regions for that field, which is what the same provider gives when it returns an empty list and what the in-tree highlightDocuments path gives on the same index. Instead the default offset strategy uses the null list and the call throws NullPointerException (OffsetsFromPositions.java:70 for a positions-only field, OffsetsFromTokens.java:74 for a DOCS or DOCS_AND_FREQS field; the opt-in OffsetsFromValues fails at OffsetsFromValues.java:51).
Introduced
755de5aae331301acf4c1acd3af6d7329998ee48 (#12881 'Performance improvements to MatchHighlighter and MatchRegionRetriever', author dweiss, merged into main only and never backported to 9.x). It rewrote FieldValueProvider (List<String>, extends Iterable<String>) and added the javadoc '@return ... or {@code null} if the field is not loaded or does not exist for the field'; in the same commit the only in-tree provider (StoredFieldsVisitor.getValues) maps a missing field to List.of(), and none of the strategies got a null check [read: git log -S on the javadoc text and git blame find only this commit; no review comment on #12881 discusses null]. The unguarded dereferences themselves date from LUCENE-9463 (150a8dacb59, lucene-solr#1750, 2020-08-14, first released in 9.0.0), when the 9.x interface had no null clause and its in-tree provider never returned null, so the defect is the contract change, not a code change at the crash sites (2023-12-07 (#12881 merged into main))
