The TSTLookup suggester throws StringIndexOutOfBoundsException on an empty key instead of returning null or a list

Ask the TSTLookup suggester about an empty key, for example the text of a cleared autocomplete box, and it throws StringIndexOutOfBoundsException: get("") should return null and lookup("", false, 5) a list. It fails on main and on all 14 releases run from 3.3.0 (2011) to 10.6.0.

The finding in 30 seconds

#

TSTLookup.lookup and get hand the key straight to TSTAutocomplete.prefixCompletion. Its search loop starts at the tree's root node, which always exists, and its first statement reads key.charAt(0); the only length check comes after that read. A key with no characters therefore throws on the first step, whatever the dictionary holds.

Two things to know first

#
  1. A suggester (Lookup) returns completions for what the user has typed so far: lookup("ca", false, 5) asks for up to 5 entries that start with ca. TSTLookup is one implementation that an application picks explicitly; get(key) returns the weight stored for exactly that key.
  2. TSTLookup keeps its entries in a ternary search tree: each node holds one character and links to a lower, an equal and a higher node. A lookup walks the tree one key character per step, starting from a root node that always exists, even when the dictionary is empty.

The finding, step by step

#
  1. You build a TSTLookup from three entries, car/3, cat/5 and dog/2, behind an as-you-type box. Typing ca works: lookup("ca", false, 5) returns [cat/5, car/3].
  2. The user clears the box and your code calls lookup("", false, 5), or it calls get(""). You expect a list, possibly empty, and null: get's javadoc says "or null if the key does not exist", and an empty key is never stored.
  3. You get StringIndexOutOfBoundsException: Index 0 out of bounds for length 0, for any dictionary (also an empty or never-built one), with assertions on or off. lookup("ca", false, 5) still returns [cat/5, car/3] afterwards.
  4. Why: the search starts at the tree's root node, which always exists, and its first step reads character 0 of the key before any length check. A 4-line guard makes lookup("") return [] and get("") return null.

Who is affected

#

Applications that use the opt-in TSTLookup suggester and pass it an empty key, typically the text of a cleared autocomplete box, or call get(""). Every lookup is affected, with no scale needed. The call fails at once with an unchecked exception; nothing is changed and no wrong result is returned. Workaround: check for an empty key first.

Mechanism, terms and numbers519 words

TSTLookup, the ternary-search-tree implementation of Lucene's Lookup suggester API, throws java.lang.StringIndexOutOfBoundsException: Index 0 out of bounds for length 0 when it is asked about an empty key. Both public entry points fail: get(""), whose javadoc promises null for a key that does not exist, and lookup("", onlyMorePopular, num) for both onlyMorePopular values. Every TSTLookup is affected (built, restored with load(), never built, or built from an empty dictionary), with assertions on and off; non-empty keys work normally. The cause is one missing length check in TSTAutocomplete.prefixCompletion: its loop always runs, because the tree's root node always exists, and its first statement reads s.charAt(0). The code dates from SOLR-1316 (2010); all 14 Lucene releases run from 3.3.0 to 10.6.0, and main, fail, and every release tag checked has the same loop. Returning the empty list before the loop when there is no character to read fixes it; the suggest module's tests pass with that change.

  :102   while (p != null) {
  :103     if (s.charAt(x) < p.splitchar) {          <- s = "", x = 0: StringIndexOutOfBoundsException
  :105     } else if (s.charAt(x) == p.splitchar) {
  :106       if (x == s.length() - 1) { break; }     <- the only length check, after charAt
  • The root is created as an empty node, so its character is the default '\u0000' (TernaryTreeNode.java:27-28). For keys that do not start with '\u0000' it is only the starting point and the entries hang below it; a key that starts with '\u0000' matches the root's character. Because the root is never null, the loop body runs at least once for every dictionary, including an empty or never-built one.
  • A non-empty key is safe: x only grows while x < s.length() - 1, so charAt(x) stays in range. Only the empty key has no character 0.
  • The empty key can never be stored: insert returns before it creates a node when s.length() <= x (TSTAutocomplete.java:58-59), and both build (through balancedTree, TSTAutocomplete.java:43) and add go through it (load restores whatever the stream holds; a stream that store wrote from such a tree holds no empty key). So get("") should be null.
  • Nothing else checks the key: lookup checks only contexts, get nothing. TSTAutocomplete's constructor is package-private, so TSTLookup is the only public way in.

Every form tried fails

#

The recorded runs cover lookup("", false, 5), lookup("", true, 5), get("") and an empty StringBuilder key, and lookups built with TSTLookup(Directory, String), restored with load(), never built (new TSTLookup()) and built from an empty dictionary, with assertions on and off. Not every combination of form and state was run; in every state the root exists, so every form reaches the same unchecked charAt at TSTAutocomplete.java:103. Non-empty keys on the same lookup answer normally, before and after the failing calls.

Exposure and likelihood251 words
  • Who is exposed. Applications that use TSTLookup and pass it an empty key: typically an as-you-type box that forwards its text after the user clears it, or a get(""). TSTLookup is one of several Lookup implementations an application chooses explicitly; Lucene has no default suggester. FSTCompletionLookup's javadoc points users to it for fine-grained weights.
  • What happens. An unchecked exception from an API that declares only IOException; if the caller does not catch it, that request fails. Nothing else: after 3,000 failing calls on a 20,000-entry dictionary, the stored bytes and 66 sampled non-empty answers (8 prefixes with both onlyMorePopular values, and 50 get calls) were unchanged, and a 4-thread run had 0 mismatches. Each failing call took about 8-9 microseconds (single runs on one host: an order of magnitude, not a benchmark).
  • Scale. None: deterministic, every dictionary, on the first loop step.
  • Versions. Lucene 3.3.0 (2011) to 10.6.0, and main: all 14 releases run in that range fail, and all 131 release tags of the history clone that contain the code have the same loop. Not every release was run; the clone has no 8.x tags after 8.8.1, so the later 8.x releases before 8.11.4 are covered by neither check. All runs used OpenJDK 25.
  • How likely. Plausible, not common: it needs an application that forwards an empty key without a check. No public report was found in the searches below, although the code dates from 2010.
  • Workaround. Check key.length() == 0 before calling lookup or get.

Why it looks unintended

#
  • get's own javadoc: "Returns the value for the specified key, or null if the key does not exist." The empty key is never stored.
  • Lookup.lookup accepts any CharSequence and declares only IOException; no test asserts or tolerates the exception.
  • FSTCompletion and AnalyzingSuggester handle "" explicitly; TSTLookup fails on an unguarded charAt.
The full argument284 words
  • get contradicts its own javadoc. "Returns the value for the specified key, or null if the key does not exist." (TSTLookup.java:155). The empty key cannot exist in a tree made by build or add (or restored from what store wrote), because insert drops it (TSTAutocomplete.java:58-59).
  • lookup has no precondition. Lookup.lookup takes "lookup key. Depending on the implementation this may be a prefix, misspelling, or even infix", returns "a list of possible completions" and declares only IOException (Lookup.java:185-194, :209-211).
  • Public API, though experimental. The package is exported by the suggest module and neither class is deprecated or tagged internal, but TSTLookup's base class Lookup is marked @lucene.experimental (Lookup.java:38); TSTAutocomplete has no such base class. That allows API changes between releases and is a point for low priority; it does not document an index exception.
  • No test covers it. Upstream, TSTLookup appears only in TestPersistence (full keys) and the ignored TestLookupBenchmark, which looks up non-empty prefixes: the first 2-4, 6-9 or 100-200 characters of each dictionary key, or the whole key when shorter; none of its dictionary keys is empty.
  • Siblings handle the empty key explicitly. FSTCompletion.lookup returns an empty result for key.isEmpty() (FSTCompletion.java:198, :221); AnalyzingSuggester lists among its limitations "Lookups with the empty string return no results instead of all results" (AnalyzingSuggester.java:95); LUCENE-8287 (2018) made empty regex completion queries return no results.
  • History. The loop is unchanged since SOLR-1316 (2010). Its first caller, Solr's spellcheck-based Suggester, passed the text of each query token, which is normally non-empty, and it has no empty-token check, so the case was probably never considered. No commit, CHANGES or MIGRATE entry mentions it.
The devil's-advocate check173 words

The strongest case for "intended": the empty-key result is deliberately not uniform across the module. For lookup("", false, 5) (the only form run on them), WFSTCompletionLookup returns every entry, FSTCompletionLookup, AnalyzingSuggester, FuzzySuggester, AnalyzingInfixSuggester and BlendedInfixSuggester return [], and FreeTextSuggester throws IllegalArgumentException on purpose, which TestFreeTextSuggester.testEmptyString asserts. So an exception for "" is accepted in this module, Lookup is marked experimental, and a caller can guard trivially.

Why it does not change the verdict: FreeTextSuggester's exception is a deliberate check with a message ("no tokens produced by analyzer, or the only tokens were empty strings", FreeTextSuggester.java:476-479); TSTLookup's is an incidental charAt range check that nothing documents, and get("") breaks a promise in its own javadoc. The argument bears on which answer to return ([], every entry, or a documented exception), not on whether an index exception is intended. Later cross-model reviews of this doc's brief (rounds 1 and 2) each rated the case for "intended" moderate and still judged the bug real, with low priority.

Suggested fix

#

Recommended A. Return the empty list before the loop when there is no character to read

Return the empty list at the top of TSTAutocomplete.prefixCompletion when the key has no character left to read (4 added lines). Then lookup("") returns [] and get("") returns null, and non-empty keys are untouched. Validated: the repro passes with assertions on and off, and the suggest module's whole test run passes (237 tests, 7 skipped, 0 failures).

     TernaryTreeNode p = root;
     ArrayList<TernaryTreeNode> suggest = new ArrayList<>();
+    if (x >= s.length()) {
+      // empty (remaining) key: the loop below reads s.charAt(x)
+      return suggest;
+    }
 
     while (p != null) {
       if (s.charAt(x) < p.splitchar) {
All options and trade-offs4 options · 537 words

Option A answers "no completions", like most sibling suggesters and like get's javadoc. If maintainers prefer every entry (option C) or a documented exception (option D), the repro's expectation changes accordingly. No CHANGES entry is drafted.

A. Return the empty list before the loop when there is no character to read (validated by the checks) (recommended)

#

In TSTAutocomplete.prefixCompletion, before while (p != null), return the (empty) result list when x >= s.length(). One check covers both entry points, lookup and get; non-empty keys never reach it.

     TernaryTreeNode p = root;
     ArrayList<TernaryTreeNode> suggest = new ArrayList<>();
+    if (x >= s.length()) {
+      // empty (remaining) key: the loop below reads s.charAt(x)
+      return suggest;
+    }
 
     while (p != null) {
       if (s.charAt(x) < p.splitchar) {

Trade-offs

It settles the answer as "no completions". The guard sits in the shared helper, so a later caller is covered too. A null key still throws NullPointerException, now from s.length() in the guard instead of s.charAt(x) (read, not run); neither lookup nor get documents null keys.

B. Guard in TSTLookup.lookup and TSTLookup.get (not run)

#

Return a new empty list from lookup (its res list is declared only after the prefixCompletion call) and null from get when key.length() == 0, before they call prefixCompletion.

Trade-offs

Same visible behaviour as A, but two guards instead of one, and prefixCompletion keeps its hidden precondition.

C. Return every entry for an empty prefix (not run)

#

What WFSTCompletionLookup does ([cat/5, car/3, dog/2] on the example dictionary): every key starts with the empty prefix.

Trade-offs

For "", prefixCompletion would walk the whole tree and collect a reference to every entry's node before lookup trims the result to num (with onlyMorePopular true, lookup also creates a LookupResult per match); no entries or strings are copied, and a very short prefix that matches most entries costs the same today. It also differs from five sibling suggesters and from AnalyzingSuggester's documented choice. get("") must still return null.

D. Reject the empty key with a documented IllegalArgumentException (not run)

#

Like FreeTextSuggester: a check with a clear message, documented in the javadoc.

Trade-offs

Better than an index exception, but callers still need their own guard, and get's javadoc, which promises null, would have to change.

Downstream note

#

Downstream, from reading Solr's source only (not run): Solr's suggest component passes suggest.q to Lookup.lookup after only a null check, so a Solr suggester explicitly configured with TSTLookupFactory appears to fail on an empty suggest.q (Solr's default lookup is FST).

How it was found

#

A bounded-exhaustive check compared WFSTCompletionLookup and TSTLookup with an exact reference on every dictionary of 1 to 3 entries drawn from 7 short strings (the empty string among them) and 4 weights, and every key of up to 3 characters, the empty key included: 6,146,280 checks. One exception class appeared, in 136,584 checks: the empty key, on every dictionary.

The method in full179 words
  • Method (semi-formal): bounded-exhaustive translation validation of two suggesters against an exact reference, on the real main jars: WFSTCompletionLookup (exactFirst on and off, onlyMorePopular false) and TSTLookup (onlyMorePopular true); FSTCompletionLookup was not in the model. Dictionaries: every sequence of 1 to 3 (string, weight) entries, duplicates allowed, with strings from "", a, b, aa, ab, ba, bb and weights 0, 1, 2 and Integer.MAX_VALUE (28 + 28^2 + 28^3 = 22,764 dictionaries; the empty dictionary is not in this scope, the independent JUnit and the probes cover it). Keys: every key of length at most 3 over a and b, including "" (15 keys); num 1 to 6: 6,146,280 checks.
  • Signal. One exception class, StringIndexOutOfBoundsException, in 136,584 checks: every dictionary and every num for the empty key. The only other TSTLookup class was a duplicate-input weight difference (19,512 checks; no documented rule; not this bug). WFSTCompletionLookup had 0 mismatches.
  • The class was reduced by hand to a public-API JUnit, and the repro was later minimized to the one test above.

Registry title
TSTLookup.get('') and TSTLookup.lookup('') throw StringIndexOutOfBoundsException instead of returning null or an empty list: TSTAutocomplete.prefixCompletion reads key.charAt(0) before it checks the key length (every release since 3.3.0)
Area
suggest / ternary search tree suggester (TSTLookup.lookup and get, TSTAutocomplete.prefixCompletion)
Priority
Low, rank 620: The opt-in TSTLookup throws StringIndexOutOfBoundsException on an empty key, such as a cleared autocomplete box, which is loud and immediate, so it follows LFV-329.
Impact class
crash
Impact note
Hits applications that use the opt-in TSTLookup suggester and pass it an empty key, for example the text of a cleared autocomplete box: lookup('') with onlyMorePopular false or true, and get(''), throw an unchecked StringIndexOutOfBoundsException on every TSTLookup (built with TSTLookup(Directory, String), restored with load(), never built, or built from an empty dictionary), with -ea and -da, in every release since 3.3.0, instead of returning an empty list and null; the call fails at once, changes no state and returns no wrong result, no scale is needed, and callers can avoid it by checking for an empty key first.
Summary
You build a TSTLookup suggester and call get('') or lookup('', false, 5), for example because a user cleared the search box. You expect null from get(''), whose javadoc says it returns null if the key does not exist (the empty key is never stored), and a list, possibly empty, from lookup(''). Instead both throw StringIndexOutOfBoundsException 'Index 0 out of bounds for length 0', because TSTAutocomplete.prefixCompletion reads key.charAt(0) on its first loop step before it checks the key length, and the tree's root node is never null; non-empty keys work normally on the same lookup.
