CheckIndex's index-sort check calls nextDoc() on an exhausted parent-field iterator when a sorted block segment has no parent document, so with SimpleTextCodec it reports the segment as broken

With SimpleTextCodec (a codec for reading and debugging, not for production), CheckIndex reports a segment as broken that the default codec reports clean. The cause is in CheckIndex: when an index-sorted segment with document blocks holds no parent document, its sort check calls nextDoc() again after NO_MORE_DOCS.

The finding in 30 seconds

#

CheckIndex checks a sorted segment by comparing neighbouring documents. In a segment with document blocks it compares the parents only. Its loop takes the first parent, then asks for the next one without checking that there was a first one. With no parent in the segment, that second call goes to an exhausted iterator.

Background: three pieces

#
  1. With IndexWriter.addDocuments you add a block: the children first, their parent last. To combine blocks with an index sort you set a parent field (IndexWriterConfig.setParentField). Lucene then marks every parent in that field and keeps each block together when it sorts.
  2. CheckIndex is the tool that tells you whether an index is healthy. From level 2 on it runs logical checks on every segment, one of them the index-sort check. An exception in any of these checks counts the segment as broken.
  3. A DocIdSetIterator hands out document numbers with nextDoc() and returns NO_MORE_DOCS at the end. Its javadoc says that nextDoc() should not be called again after that.

The finding, step by step

#
  1. You write an index with SimpleTextCodec (a text codec for debugging, not for production), an index sort and a parent field. You add one block of 2 documents with addDocuments: a child and its parent.
  2. You delete by a term that only the parent carries and call forceMerge(1). The merged segment holds 1 document, the child, and no parent.
  3. You run CheckIndex at level 2 (integrity checks) and expect a clean report with test: index sort..........OK. That is what the same steps give with the default codec.
  4. Instead it prints test: index sort..........ERROR [Index -2 out of bounds for length 1] and counts 1 broken segment. Every other segment test prints OK.
  5. Why: the sort check walks the parent documents. Its first nextDoc() already returns NO_MORE_DOCS, yet its loop calls nextDoc() again, which the iterator's javadoc tells callers not to do. The default codec answers NO_MORE_DOCS again. SimpleText computes NO_MORE_DOCS + 1, a negative number, seeks to a negative file position, and the read fails.

Who is affected

#

With assertions off, only an index written with SimpleTextCodec that has an index sort, a parent field and document blocks, after a merge leaves a segment without any parent, and when CheckIndex runs at level 2 or higher. In practice: test suites and debugging sessions. With the default codec nothing is visible. No search result or stored data changes.

Mechanism, terms and numbers819 words

SimpleTextCodec is a plain-text codec for reading and debugging an index ("FOR RECREATIONAL USE ONLY"), and it is the only codec in the tree that shows this defect with assertions off (with assertions on, the test framework's asserting codec shows it too). The defect itself is in CheckIndex.testSort (CheckIndex.java:1254-1262 on main 781025d6fe32). For an index-sorted segment with document blocks, the check compares the parent documents only, walking the parent field's numeric doc values. It takes int prevDoc = iter.nextDoc() and then calls iter.nextDoc() again in the loop condition without looking at the first result. A segment can hold no parent at all, for example after a delete that matches a block's parent and not its children, followed by a merge. Then the first call returns NO_MORE_DOCS and the second is a call the DocIdSetIterator.nextDoc javadoc tells callers not to make. The default codec's empty iterator returns NO_MORE_DOCS again and the check prints OK. SimpleText's iterator computes advance(docID() + 1), which overflows to Integer.MIN_VALUE, seeks to a negative file position and throws. CheckIndex catches the exception, prints test: index sort..........ERROR [Index -2 out of bounds for length 1] and counts the segment as broken. So the verdict for the same IndexWriter calls depends on the codec. The defect changes no stored data and no search result, and with the default codec nothing is visible. The loop dates from #12829 (df6bd25ce44, first released in 9.10.0); every release up to 10.6.0, branch_11x and main have it. A one-line guard in the loop fixes it.

Terms

#
  • Parent field. IndexWriterConfig.setParentField makes IndexWriter add an internal numeric doc-values field to the last document of every block, the parent (IndexWriterConfig.java:579-589). It is required when blocks are used together with an index sort (#12829).
  • Index-sort check. CheckIndex.testSort (CheckIndex.java:1218-1301) runs for every segment of an index with an index sort once the level is 2 or higher (:1114, :1146-1149; the default level is 1, :4747). It compares each document with the one before it and throws if they are out of order.
  • SimpleTextCodec. A codec that writes the index as readable text, documented "FOR RECREATIONAL USE ONLY" (SimpleTextCodec.java:35). It is meant for reading and debugging, not for production.

The bug

#
  1. For a segment with blocks and a parent field, the iterator of the check is the parent field's numeric doc values, so only parents are compared. For any other segment it is every document, DocIdSetIterator.all(maxDoc) (CheckIndex.java:1254-1259).
  2. int prevDoc = iter.nextDoc(); (:1260). The result is not checked. Then while ((nextDoc = iter.nextDoc()) != NO_MORE_DOCS) (:1262).
  3. In a segment where no document is a parent, the first call returns NO_MORE_DOCS. The loop condition then calls nextDoc() on an exhausted iterator. The javadoc: "after the iterator has exhausted you should not call this method, as it may result in unpredicted behavior." (DocIdSetIterator.java:126-131). The merged segment still takes the parent-field branch: it keeps the parent field and still counts as a segment with blocks (a merge carries hasBlocks over from its inputs, IndexWriter.java:5382-5388), so the iterator exists and is empty.
  4. Default codec. A field without values is DocValues.emptyNumeric() (Lucene90DocValuesProducer.java:888-890), whose nextDoc() returns NO_MORE_DOCS on every call (DocValues.java:89-92). The loop ends and the check prints OK.
  5. SimpleText. nextDoc() is return advance(docID() + 1); (SimpleTextDocValuesReader.java:336-339). docID() is NO_MORE_DOCS, which is Integer.MAX_VALUE (DocIdSetIterator.java:111), so the target overflows to Integer.MIN_VALUE. advance starts its loop at that target and seeks to dataStartFilePointer + (1 + pattern.length() + 2) * (long) i (:352-355), a negative position. The read throws.
  6. testSort catches every Throwable, prints ERROR [message] and stores it (CheckIndex.java:1288-1297). testSegment turns that into CheckIndexException("Index Sort test failed") (:1188-1191), the segment is counted as broken (:1200-1211, :975-981) and Status.clean stays false (:933-943).
  7. Only the parent-field branch can start exhausted. A segment has at least one document, so DocIdSetIterator.all(maxDoc) always returns document 0 first.

Exposure and likelihood590 words
  • Who. Someone who writes an index with SimpleTextCodec, with an index sort, a parent field and document blocks, gets a segment without any parent, and then runs CheckIndex with integrity checks. That is a test suite or a debugging session, not a production index.
  • Lucene's own tests are the most concrete case. A test directory from newDirectory() runs CheckIndex at the slow-checks level when it is closed, if it holds an index and the test has not switched the check off (BaseDirectoryWrapper.java:33, :44-45, :55-58). With the default random codec setting, the test codec is SimpleText on rare seeds and the asserting codec for one value in eleven (SetupAndRestoreStaticEnv.java:144, :185-190, :198-200). A test in upstream idiom that builds this state, for example a regression test for a fix of LFV-011 (deleting only a block's parent makes later merges fail), would fail on those seeds: on SimpleText with assertions on and off, on the asserting codec with assertions on.
  • All of it is opt-in. The codec, the index sort with a parent field, and the level. On 10.x, 11.x and main the sort check runs only from level 2; the default level is 1. On 9.10 to 9.12 CheckIndex has no level setting and runs the check with its default options.
  • A segment must hold no parent at all. An orphaned child beside a surviving parent passes, and so does a whole-block delete.
  • How a segment gets no parent. A delete by a term or query that matches a block's parent and not its children, followed by a merge. The merge need not be a forced one: with the default merge policy the writer merges the half-deleted segment by itself when it closes. Until a merge runs, the deleted parent stays in its segment and the check passes. An update by such a term removes the same parent, but its replacement document is itself a parent, so the merged segment has no parent only when the replacement ends up in another segment (not run; updateDocument followed by forceMerge(1), and updateDocument after a commit followed by forceMergeDeletes(), both end with a clean report). Two more ways were seen in a randomized model run on main and not re-run for this doc: a soft-deletes retention policy that keeps a child without its parent, and one output of a partitioned merge (#16571) that holds only such children. The partitioned merge is on main and on branch_11x, and in no release.
  • Consequence where it shows (SimpleText only). CheckIndex.exorciseIndex on that report, or -exorcise on the command line, drops the segment: 1 live document before, 0 after. That method is documented as destructive (CheckIndex.java:4597-4604) and is a second, explicit action by the operator.
  • What this doc does not say. The segment is not called healthy: it holds an orphaned child, which is a broken block (the join module's CheckJoinIndex rejects a segment without a parent, CheckJoinIndex.java:43-48), and when such a child carries sort values the next merge fails (LFV-011). The claim is that CheckIndex gives different answers for the same IndexWriter calls depending on the codec, through an exception of its own making.
  • Likelihood: rare (a judgement, not usage data). No report of it was found in the searches listed under Prior reports; the loop has been in releases since 9.10.0 (2024). Third-party codecs were not examined; a codec whose empty doc-values iterator does not tolerate a call after exhaustion would show the same, which is a possibility and not an observed case.

Why it looks unintended

#
  • The iterator's javadoc: "after the iterator has exhausted you should not call this method". CheckIndex is the caller that does.
  • The verdict depends on the codec, not on the index: the default codec reports the same steps clean.
  • The loop was written to check that parents are in order (#12829). With no parent there is nothing to compare.
The full argument602 words
  • The iterator's javadoc tells callers not to make this call, and CheckIndex makes it. DocIdSetIterator.nextDoc: "after the iterator has exhausted you should not call this method, as it may result in unpredicted behavior." (DocIdSetIterator.java:126-131). The wording is "should not", not "must not". By it, SimpleText's nextDoc() may do anything after exhaustion; CheckIndex.testSort is the caller that does not follow it.
  • The verdict depends on the codec, not on the index. The same IndexWriter calls give OK with the default codec at levels 2 and 3 and ERROR with SimpleText. In the failing report every other segment test is OK.
  • The error says nothing about the sort order. It is CheckIndex's own exception from its own extra call, printed as Index -2 out of bounds for length 1.
  • The loop it replaced could not do this. Before #12829 the check was for (int docID = 1; docID < maxDoc; docID++).
  • The loop's stated purpose. Mike McCandless, in a review comment on #12829 (2023-12-05), first asked "Hmm can we fix CheckIndex to confirm the blocks are also intact?" and then wrote, in an edit of the same comment, that the change had "fixed CheckIndex so that when it validates the sort it checks only that the parent docs are in the right order". So the loop is there to compare parents, and with no parent there is nothing to compare. Their opening question speaks for a check of the blocks themselves (Suggested fix, last option). No mention of an empty parent iterator was found in the pull request's conversation and review comments.
  • Lucene's test framework treats the call as a violation. AssertingNumericDocValues.nextDoc asserts docID > lastDocID (AssertingLeafReader.java:779-787, the assertion at :782). With the asserting codec and assertions on, the same check reports ERROR for this index; with the fix it reports OK. This is evidence of intent from the test framework, not part of the claim.
  • IndexWriter accepts the delete and the merge. The addDocuments javadoc anticipates deleted marker documents and limits the consequence to search features: "Most search features (like result grouping and block joining) require you to mark documents; when these documents are deleted these search features will not work as expected." (IndexWriter.java:1501-1506). setParentField states no rule about deletes (IndexWriterConfig.java:579-589).
  • A call after exhaustion was fixed as a bug before, in the caller. LUCENE-9618 (f24b497c724, Patrick Zhai, 2020, with a CHANGES entry): "Do not call IntervalIterator.nextInterval after NO_MORE_DOCS is returned". Two later fixes are related, and neither is the same mistake. #16250 / #16252 (cd87d56dd43, 2026, a CHANGES entry under Bug Fixes) made RoaringDocIdSet's iterator handle intoBitSet when it is already exhausted. That call is allowed on an exhausted iterator (the default implementation then does nothing, DocIdSetIterator.java:186-210), and the fix is in the iterator, not in the caller, so it is a precedent for making SimpleText's iterator tolerant as much as for the guard. #15974 (2026) is a test failure that came from an off-by-one in SimpleText's doc-values skipper, fixed with one line in the codec (db3222d4915). It shows that a failure seen only with SimpleText gets fixed; it is not a call after exhaustion.
  • Tests. No upstream test that builds a sorted block segment without a parent was found (the test methods that set a parent field and an index sort were read; not an exhaustive proof). The closest one, TestIndexSorting.testMixRandomDocumentsWithBlocks, deletes by an id term that every document of a block carries, so only whole blocks go (TestIndexSorting.java:3370-3383 the delete, :3389-3419 the id field of every document).
The devil's-advocate check284 words

The strongest case for "intended": the state itself is a broken block structure, so "not clean" is arguably the truth. The join module's CheckJoinIndex rejects it: "Every segment should have at least one parent" (CheckJoinIndex.java:43-48). On #8725 (LUCENE-7674, 2017) Adrien Grand wrote, about Solr's block-join support, that the rules "should be enforced at index time" and that it "could reject update/delete operations that would break the block structure". Simon Willnauer named the parent-only delete as a weak spot of the delete API in a review comment on #12829 (2023-12-12). On top of that, SimpleText is "FOR RECREATIONAL USE ONLY", and CheckIndex is marked experimental and turns any exception into a broken segment by design.

What it does not explain: none of this explains the codec-dependent failure as a choice. If CheckIndex were meant to reject a block segment without a parent, it would do so for every codec and with a message that says so. With the default codec it reports the index from the same calls clean at levels 2 and 3, and core CheckIndex has no such rule; CheckJoinIndex is a separate, opt-in validator for block joins. What SimpleText shows is a bounds exception from a call the iterator's javadoc tells callers not to make. "Recreational" sets the priority (Low); it does not make the extra call right, and the test framework's asserting wrapper flags the same call. The argument does carry weight on another point: a maintainer can reasonably decide that CheckIndex should flag such segments, or that this is not worth a change of its own. The first is a separate, explicit check (Suggested fix, last option), and with it the call after exhaustion still has to go.

Suggested fix

#

Recommended Guard the loop in CheckIndex.testSort, one line (validated)

Guard the loop in CheckIndex.testSort: stop when the first nextDoc() already returned NO_MORE_DOCS. One line. Validated: the test passes, and so do TestCheckIndex, TestIndexSorting and the SimpleText codec's tests. Making SimpleText's iterator tolerant as well is optional and does not replace the guard.

         int prevDoc = iter.nextDoc();
         int nextDoc;
-        while ((nextDoc = iter.nextDoc()) != NO_MORE_DOCS) {
+        // an iterator must not be stepped again once it is exhausted (a segment may hold no parent)
+        while (prevDoc != NO_MORE_DOCS && (nextDoc = iter.nextDoc()) != NO_MORE_DOCS) {

Guard the loop in CheckIndex.testSort, one line (validated) (recommended)

#

Do not enter the loop when the first nextDoc() already returned NO_MORE_DOCS (CheckIndex.java:1262). A block segment without a parent has nothing to compare. With the guard the loop makes no call after exhaustion, so the result no longer depends on what a codec's iterator does then, and the check prints OK, as it does today for the default codec.

         int prevDoc = iter.nextDoc();
         int nextDoc;
-        while ((nextDoc = iter.nextDoc()) != NO_MORE_DOCS) {
+        // an iterator must not be stepped again once it is exhausted (a segment may hold no parent)
+        while (prevDoc != NO_MORE_DOCS && (nextDoc = iter.nextDoc()) != NO_MORE_DOCS) {

Trade-offs

  • Segments with a parent are unchanged. The loop body is the same; the extra comparison is one int test per parent.
  • It keeps today's default-codec answer. A block segment without a parent is then reported clean with SimpleText and with the asserting codec too (both run; third-party codecs were not run). A maintainer who wants such segments flagged needs the explicit rule (last option) on top.

How it was found

#

A seeded model-based test runs random IndexWriter operations and merges on the real code and checks a written model after every step. Run with CheckIndex at level 2 in place of the default level 1, it reported a broken segment in 3 of 20,000 cases, all with SimpleText, document blocks and a parent-only delete. Reading testSort gave the cause.

The method in full235 words

Method: a seeded model-based test, then code reading and reduction (tagged semi-formal; the first signal came from a test, not from a proof or a model-checking tool).

  • The test. Every seeded case runs a sequence of adds, updates, deletes, flushes and merges on the real IndexWriter, once with a partitioned merge and once with the ordinary one-output merge, and checks ten properties of a written model after every operation. One property is that CheckIndex reports the index clean.
  • The signal. With CheckIndex at level 2 in place of the default level 1, 3 of 20,000 cases reported a broken segment. All three used the SimpleText codec, document blocks and a delete of a parent without its children, and one merge output held only orphaned children. At level 3, 60,000 cases gave the same signature in 8 runs (6 partitioned, 2 one-output; 7 after a parent-only delete, 1 after a soft delete under a retention policy that keeps a child without its parent) and no other new signature. At the default level 1 the sort check does not run, so earlier runs of 540,000 cases could not show it.
  • The cause. The SimpleText doc-values file of a reported segment was dumped and is well formed. Reading CheckIndex.testSort then showed the second nextDoc() call.
  • Reduction. To one public-API test that needs no partitioned merge (an ordinary forceMerge), and then to the smaller test shown here.

LFV-1488, snapshot of 2026-11-17

Registry title
CheckIndex's index-sort check calls nextDoc() on the parent-field iterator again after it returned NO_MORE_DOCS when an index-sorted segment with document blocks holds no parent document, so with SimpleTextCodec it reports a segment that the default codec reports clean as broken ('Index Sort test failed'); with the default codec nothing is visible (every release since 9.10.0)
Area
index / CheckIndex (testSort, the index-sort check of segments with document blocks); witness codec: codecs / SimpleText doc values
Priority
Low, rank 1278: In every release since 9.10.0, CheckIndex's index-sort check (level 2 or higher on 10.x and main, the default options on 9.10 to 9.12) steps the parent-field iterator after it is exhausted when an index-sorted segment with document blocks holds no parent document, and with the debug-only SimpleTextCodec that becomes a 'broken segment' report, with assertions on or off, for a segment the default codec reports clean. The default codec shows nothing, the defect changes no search result or stored data, and such a segment arises only when a merge keeps children whose parents were all removed without them (for example after a delete that matches only a block's parent), so the realistic hits are test suites that run SimpleText, no report of one since 2024 was found, and it is Low.
Impact class
minor
Impact note
Hits only an index written with SimpleTextCodec (a text codec documented 'FOR RECREATIONAL USE ONLY'; with assertions on the test framework's asserting codec shows it too, and third-party codecs were not examined) that also uses an index sort with a parent field and document blocks, once a merge leaves a segment with no parent document at all (for example after a delete by a term that only a block's parent carries), and only when CheckIndex runs its index-sort check (level 2 or higher on 10.x and main, the default options on 9.10 to 9.12): CheckIndex then reports that segment as broken, because its check catches an ordinary bounds-checked Java exception from the codec's read, and an exorciseIndex run on that report drops the segment's remaining documents [exec, SimpleText only]; with the default codec the index from the same steps is reported clean and nothing is visible, the defect changes no search result or stored data, and no scale is needed; every release from 9.10.0 to 10.6.0 and main [exec], with -ea and -da.
Summary
You write an index with SimpleTextCodec, an index sort and a parent field, add one block (a child and its parent), delete the parent by a term that only the parent carries, force-merge and run CheckIndex with integrity checks (level 2). You expect the index to be reported clean, as CheckIndex reports it when the same steps run with the default codec. Instead CheckIndex prints 'test: index sort..........ERROR [Index -2 out of bounds for length 1]' and counts one broken segment: the merged segment holds no parent document, so the check's first nextDoc() on the parent field already returns NO_MORE_DOCS, its loop calls nextDoc() once more, which the iterator's javadoc tells callers not to do, and SimpleText's iterator answers that call with a read at a negative file position.
