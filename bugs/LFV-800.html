WordBreakSpellChecker.suggestWordBreaks ignores setMaxChanges(0) and still returns one-break suggestions

After setMaxChanges(0), WordBreakSpellChecker.suggestWordCombinations correctly suggests nothing, but suggestWordBreaks("sunflower") still returns [sun, flower] with score 1: one break where the maximum is 0. The break search always makes the first split and reads the limit only before a second one; every release since 4.0 behaves this way.

The bug in 30 seconds

#

WordBreakSpellChecker suggests by splitting one term into indexed words or joining several terms into one. setMaxChanges(n) caps the number of splits or joins. The join method applies the cap from 0 up; the split method applies it only from the second split on.

  1. Index the words sun, flower, seed and flowerseed. With the default maxChanges of 1, suggestWordBreaks("sunflower") returns [sun, flower] (one break, score 1.0) and suggestWordCombinations([flower, seed]) returns flowerseed (one combination).
  2. Call setMaxChanges(0) on the same instance. Its javadoc calls both word breaks and combinations "changes", so you expect no suggestion from either method.
  3. suggestWordCombinations returns none, as expected. suggestWordBreaks("sunflower") still returns [sun, flower] with score 1.0. setMaxChanges(-1) gives the same. No error.
  4. Why: suggestWordBreaks always starts at one break and offers the one-break splits first. It reads maxChanges only to decide whether to try a second break, so any value below 1 acts like 1.

Who is affected

#

Direct users of WordBreakSpellChecker who set maxChanges to 0 or below, say to mean "no changes", and still call suggestWordBreaks. The default and every value of 1 or more are not affected by this defect, and stock Solr never passes a value below 1. The only effect is extra suggestions built from words already in the index.

Mechanism, terms and numbers473 words

WordBreakSpellChecker (lucene-suggest) suggests corrections by breaking one term into indexed words (sunflower -> sun flower) or combining several terms into one. setMaxChanges documents "The maximum numbers of changes (word breaks or combinations) to make on the original term(s). Default=1" and accepts any int. With a maximum of 0, suggestWordCombinations returns nothing, but suggestWordBreaks still returns the one-break suggestions that a maximum of 1 would give, scored 1 (one break): with sun, flower, seed and flowerseed indexed, suggestWordBreaks("sunflower") returns [sun, flower]; a negative value behaves the same. The reason is that suggestWordBreaks always starts its search at one break and reads maxChanges only before trying a second one. The default and every value of 1 or more are not affected by this defect, Solr's stock integration never passes a value below 1, and the only effect is extra suggestions. It dates from the class's first commit (LUCENE-3523, 2012), reproduces on 17 releases from 4.0.0-ALPHA to 10.5.2 and on main, and a one-line early return, like the existing one for maxSuggestions < 1, fixes it.

Terms

#
  • WordBreakSpellChecker (lucene-suggest, org.apache.lucene.search.spell) offers two kinds of suggestions: suggestWordBreaks(term, ...) splits one term into words that exist in the index, and suggestWordCombinations(terms, ...) joins adjacent terms into one indexed word.
  • maxChanges (default 1): "The maximum numbers of changes (word breaks or combinations) to make on the original term(s)". A suggestion's score is its number of changes: for breaks the javadoc says "The scores returned are equal to the number of word breaks needed".

The bug

#
  1. suggestWordBreaks calls generateBreakUpSuggestions(term, ir, 1, ...): the break count starts at 1 whatever maxChanges is (WordBreakSpellChecker.java:109-118).
  2. Phase 1 of that method tries every split position and offers each pair of indexed words to the result queue (:268-290). maxChanges is not read here.
  3. Only then does it compute newNumberBreaks = numberBreaks + 1 and return if newNumberBreaks > maxChanges (:298-303). That check only stops a second break.
  4. suggestWordCombinations instead bounds its loop with j - i <= maxChanges (:186): with 0 the loop never runs, so no combination.

Exposure and likelihood239 words
  • Who. Direct Lucene API users of WordBreakSpellChecker who set maxChanges to 0 or a negative value and still call suggestWordBreaks: for example an application that maps a "no changes" setting onto one instance used for both methods, or that computes the value and can reach 0. The setter accepts it silently.
  • Not affected by this defect. The default (1) and every value of 1 or more; upstream tests use only values of 1 or more. Solr's word-break spell checker calls setMaxChanges only for values above 0 and turns breaks off with a separate breakWords option, so it cannot be triggered through the stock Solr setting (from reading Solr's source); custom code that calls Lucene directly can.
  • Effect. Extra spelling suggestions: the one-break suggestions that maxChanges 1 would give, each scored 1. The index is unchanged; what the extra suggestions do downstream depends on the caller (for example an application that rewrites queries from them). No exception or hang occurred in any run, and the work is the same as with the default of 1, because phase 1 is bounded by the term length and maxEvaluations.
  • Scale. Deterministic at any index size: a call that returns one-break suggestions at maxChanges 1 returns the same ones at 0 or below (the usual mode, frequency, length and result-count limits still apply).
  • How likely. Rare: it needs a deliberate value below 1, and no matching public report since 2012 was found.

Why it is a bug, not intended

#
  • The setter's javadoc: "The maximum numbers of changes (word breaks or combinations) to make on the original term(s)", with no minimum.
  • Lucene scores the returned split 1.0, defined as "the number of word breaks needed": one break above a maximum of 0.
  • Combinations honour 0, and an upstream test asserts that too low a maxChanges leaves no suggestion.
The full argument227 words
  • Contract. setMaxChanges: "The maximum numbers of changes (word breaks or combinations) to make on the original term(s). Default=1" (WordBreakSpellChecker.java:441-443); getMaxChanges: "Returns the maximum number of changes to perform on the input" (:395-396). No minimum, no exception for breaks, no validation (:447-449).
  • Lucene's own score. "The scores returned are equal to the number of word breaks needed" (:65-67); at maxChanges 0 the returned words have score 1.0.
  • Sibling method. suggestWordCombinations treats the same field as a true upper bound including 0 (:186), unchanged since 2012.
  • Same method, other limits. maxSuggestions below 1 returns nothing (:81-83), and maxEvaluations 0 returns before the first split (:269).
  • Upstream test. TestWordBreakSpellChecker.java:294-316: "onethousandonehundredeleven" needs 4 breaks; at setMaxChanges(3) the test asserts 0 suggestions, at 4 one. So maxChanges is meant to be able to leave nothing.
  • Explicit floors look different. minBreakWordLength 0 is floored on purpose with Math.max(minBreakWordLength, 1) (:254; in 2012, if (useMinBreakWordLength < 1)). Nothing floors maxChanges; its "floor" is only where the check happens to sit.
  • History. The 2012 original already checked if (newNumberBreaks <= maxChanges) only around the recursive call, after offering the split; LUCENE-4587, #12077 ("now correctly respects maxEvaluations") and the #12100 rewrite kept that shape. No issue, PR, CHANGES or MIGRATE entry discusses values below 1.
The devil's-advocate check201 words

The strongest works-as-designed case (the cross-model lenses and the devil's advocate rated it moderate): since 2012 maxChanges has acted as a depth limit after a first split that always happens; the class's author also wrote the Solr integration, which never passes a value of 0 or less and has a separate breakWords switch; the class silently floors another knob; and a 2014 solr-user@ mail by the author describes maxChanges loosely as "the maximum number of words it can break 1 word into ... reasonable to set this to 1 or 2". On that reading, values below 1 are unsupported, and a caller who wants no breaks should not call suggestWordBreaks.

Why it fails: no javadoc, test, CHANGES or MIGRATE entry states a minimum; the setter counts word breaks as changes; Lucene scores the returned suggestion as one break; the same field is a true bound at 0 in the sibling method; and the one floor the class has is explicit code. The case does bear on the resolution: documenting and validating maxChanges >= 1 is a reasonable maintainer choice, which is why the bug ranks low. Verdict: not intended; an unvalidated boundary value that one of the two methods ignores.

Suggested fix

#

Recommended A: suggestWordBreaks returns nothing when maxChanges < 1

In suggestWordBreaks, return no suggestion when maxChanges < 1, in the existing maxSuggestions < 1 early return, and add one javadoc sentence. With it the whole suggest module passes, repro tests included, with assertions on and off. Alternative: reject values below 1 in the setter, which also turns today's working 0 for combinations into an exception.

Trade-offs

  • Values of 1 or more never reach the new condition, so their results are unchanged; values below 1 now do less work than today.
  • A caller that relied on 0 still giving one-break suggestions would get none. Nothing upstream or in Solr does.
  • For values below 1 it also returns before the suggestMode and sortMethod defaults and before ir.docFreq(term), so the reader is not touched: a closed or failing reader that used to raise an I/O error there would not. The existing maxSuggestions < 1 return already behaves this way.

B: reject values below 1 in setMaxChanges

#

setMaxChanges throws IllegalArgumentException("maxChanges must be at least 1, got " + maxChanges) and its javadoc says "Must be at least 1". A related precedent in the same package: DirectSpellChecker.setMaxEdits documents "This value can be 1 or 2" and range-checks its argument, throwing UnsupportedOperationException("Invalid maxEdits") below 1 or above 2 (DirectSpellChecker.java:107-118). Fix B uses IllegalArgumentException, so it does not copy that exception type.

What was run (not a full validation). Gradle, same worktree and seed, assertions on only: all 31 upstream suggest test classes (236 tests) pass, so no upstream test sets a value below 1. The run as a whole failed (240 tests, 3 failures): in the unchanged primary repro the 3 tests that set 0 or -1, the combinations control included, now get the exception. No test that asserts the new exception was written, and B was not run with assertions off. :lucene:suggest:check -x test passes.

public void setMaxChanges(int maxChanges) {
  if (maxChanges < 1) {
    throw new IllegalArgumentException("maxChanges must be at least 1, got " + maxChanges);
  }
  this.maxChanges = maxChanges;
}

Trade-offs

Also changes suggestWordCombinations: setMaxChanges(0) works there today as "no combinations", and such callers would start to fail. That needs a CHANGES entry and suits a major release better than a bug-fix release. Solr is unaffected (it never passes values of 0 or less).

C: document the current behaviour

#

Say in the javadoc that suggestWordBreaks always considers one break and that maxChanges limits only further breaks.

Trade-offs

Keeps the two methods inconsistent under one setting. Not run (no code change).
