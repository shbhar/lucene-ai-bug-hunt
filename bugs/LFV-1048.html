A limited ParentsChildrenBlockJoinQuery returns children beyond childLimitPerParent when a filter, a sort or explain() advances it

With a finite childLimitPerParent, ParentsChildrenBlockJoinQuery's advance() starts counting children at the target document, so filters, sorted searches and explain() can get children beyond the limit: the join alone matches a and c, yet +join #id:b returns b. Silent, in 10.4.0 through 10.6.0 and main.

The finding in 30 seconds

#

ParentsChildrenBlockJoinQuery returns, for each parent matching parentQuery, at most childLimitPerParent of its children matching childQuery. nextDoc() counts them from the start of each block; advance(target) starts counting at target, so it can return a child that nextDoc() never returns.

Background

#
  1. Block join. Each parent is indexed right after its children, in one addDocuments block; a parent filter (BitSetProducer) marks which documents are parents.
  2. ParentsChildrenBlockJoinQuery (10.4.0, experimental) returns child documents: the children matching childQuery whose parent matches parentQuery, at most childLimitPerParent per parent (default Integer.MAX_VALUE). Upstream's randomized test expects the first N matching children of each parent, in doc order.
  3. Iterators. A query's DocIdSetIterator has nextDoc() (the next match) and advance(target) (the first match at or after target), which must give the same matches as calling nextDoc() until target. Conjunctions, sort skipping and explain() use advance().

The finding, step by step

#
  1. Index two blocks with addDocuments: children a (doc 0) and b (doc 1) under parent p1 (doc 2), then child c (doc 3) under parent p2 (doc 4). Build ParentsChildrenBlockJoinQuery(parents, type:parent, type:child, childLimitPerParent = 1).
  2. On its own the join matches a and c, the first matching child of each parent: count(join) = 2. So you expect +join #id:b (join AND id:b) to return 0 hits, and explain(join, 1) to say "Not a match".
  3. Instead count(+join #id:b) = 1 (doc b) and explain(join, 1) reports a match, with assertions on or off, on 10.4.0 through 10.6.0 and main.
  4. Why: id:b is the cheaper clause, so it leads and asks the join to advance(1). advance() jumps straight to doc 1 and counts it as p1's first child; nextDoc() would have counted a first and moved on to p2.
  5. The answer depends on how the query is driven: with only the first block indexed, the same query returns 0 hits; a plain sorted search over 5,000 blocks puts an over-limit child first once top-N skipping starts.

Who is affected

#

Users of the experimental ParentsChildrenBlockJoinQuery (10.4.0 and later) who set a finite childLimitPerParent, the parameter it was added for, and combine the join with a cheaper required or filter clause, sort its results, or call explain(). Default codec and searcher. The default limit and the join alone with unsorted search() or count() are fine.

Mechanism, terms and numbers643 words

ParentsChildrenBlockJoinQuery (new in 10.4.0, @lucene.experimental) returns, for each parent that matches parentQuery, its children that match childQuery, at most childLimitPerParent of them. Its iterator's nextDoc() counts a block's matching children from the block's first child, so the hits are the first N matching children of each parent in doc order, as the upstream randomized test defines them. advance(target) instead jumps to the first matching child at or after target and starts counting there, so the matching children of the block before target are never counted and advance() can return a child that nextDoc() never returns, which breaks the DocIdSetIterator#advance contract. A caller whose advance() enters a block past matching children the iterator has not counted can get the extra children, for example a cheaper MUST or FILTER clause that leads a conjunction (+join #id:b returns b in a 5-document repro), a sorted top-N search once competitive skipping starts, and explain(), which tests advance(doc) == doc. Silent, with assertions on or off, default codec and searcher; the default limit (Integer.MAX_VALUE) is not affected. Present since the class was added by #14728, so every release with it (10.4.0 to 10.6.0) and main.

The code (main 645d4fe14a20, ParentsChildrenBlockJoinQuery.java)

#
  1. nextDoc() (:313-347) advances the child iterator only while childDocCount < childLimitPerParent (:315-317). Once the limit is reached, or the child passed the parent, it resets the count and moves to the next matching parent (:322-330), and alignParentAndChildIterator() moves the child iterator to the first child of that parent's block, parentBits.prevSetBit(parentDoc - 1) + 1 (:386, :390-392). So within each block it returns the first N matching children.
  2. advance(target) (:349-382) calls childIt.advance(target) (:355). If the count is used up or the child is past the current parent (:356), it resets childDocCount = 0 (:358) and moves the parent iterator to the child's block, or on to the next parent when the count is used up inside the current block (:359-367); then childDocCount++ (:380). The block's matching children between its first child and target are skipped and never counted. Inside the current block it adds 1 only for the child it returns, so with a limit of 2 or more it undercounts there too.
  3. Weight#explain (:170-188) tests scorer.iterator().advance(doc) == doc on a fresh scorer (:173).
  4. Who advances the join. Lucene's conjunctions sort their clauses by cost and let the cheapest lead (ConjunctionDISI.java:132, :161; ConjunctionBulkScorer.java:54), using each iterator's cost(); the join iterator's cost is min(childCost, parentCost * childLimitPerParent) (:407-416, formula at :414; the scorer supplier's cost() at :229 is the same formula).

Why the join alone is right

#

Unsorted search() and count() drive the join with nextDoc() only, so they return the first N matching children of each parent; explain() of a real hit lands on that hit. Only paths that call advance() past uncounted children go wrong.

Exposure and likelihood493 words
  • Who is hit. Applications using ParentsChildrenBlockJoinQuery (10.4.0 and later) with a finite childLimitPerParent, the parameter the class was added for (#14565). The default Integer.MAX_VALUE is not affected: 0 of 420,758 checks in the bounded-exhaustive model. No use of the class was found in Elasticsearch, OpenSearch or Solr.
  • Triggers (public API; default codec, IndexWriterConfig and IndexSearcher; a CheckJoinIndex-valid index):
    • a conjunction where a cheaper MUST or FILTER clause leads, for example a child-attribute filter, the composition the feature request describes (the repro);
    • a plain sorted search search(join, 10, sort) with no other clause, once the sort's competitive iterator starts skipping: 5,000 blocks [c0, c1, parent], limit 1, a long sort field with points and doc values, c1 tiny in five blocks; the top hit is c1-3000, an over-limit child (totalHits = 1002+), on main with assertions on and off and on 10.5.2. With the recommended fix the top 10 are c0-0 to c0-9 and the total stays a lower bound (1001+ of 5,000 matches), consistent with skipping still working (the probe does not instrument skipping);
    • IndexSearcher.explain on a non-hit, which reports a match.
  • Same root, notes only. As a MUST_NOT clause the join can exclude documents it does not match (run on 10.5.2 and main only). On 10.5.2 the bounded model finds such cases (up to 6 documents); on main it finds none up to 7 documents, but a separate 15,000-document probe, where the required clause skips past a 4,096-document window into a block, reproduces one (+id:12000 -join returns 0 hits instead of 1). With an explicit LRUQueryCache that caches the join, the conjunction becomes correct (1 hit without the cache, 0 with it), so the answer can also change with caching; not shown with the default caching policy.
  • Effect. Silent wrong results: more children per parent than the limit, and an explain() that disagrees with search() for the query alone. Every extra hit still matches childQuery, has a parent that matches parentQuery and satisfies every other required clause.
  • Scale. A differential check against a reference join written from the javadoc, over every block layout up to 7 documents and every match pattern: 11,180 mismatches in 1,683,032 checks on main (limit 1: 6,562; limit 2: 3,827; limit 3: 791; MAX: 0). With limit 1, 1,772 of 72,818 single-document FILTER conjunctions and 1,973 of 72,818 explain checks are wrong; 0 mismatches with either fix. The model covers one segment, no deletions, blocks that end in a parent, disjoint parent and child queries and limits 1, 2, 3 and Integer.MAX_VALUE; it says nothing about multi-segment indexes, deletions or other query shapes.
  • Not affected: the join alone with unsorted search() and count(), explain() of real hits, the default limit. Intra-segment concurrency is rejected on purpose (ParentsChildrenBlockJoinQuery.java:191-197), so it is not a trigger.
  • Likelihood: plausible. A rarely used, experimental class, but deterministic for its users once a filter, a sort or explain() is involved.

Why it looks unintended

#
  • DocIdSetIterator#advance must behave like a nextDoc() loop to the target; nextDoc() never returns b, advance(1) does.
  • Upstream's randomized test expects the first N matching children per parent, and the feature request expects a limited join in a BooleanQuery to intersect.
  • The result changes with clause costs: with only the first block, the same query returns 0 hits.
The full argument393 words
  • The core contract. DocIdSetIterator#advance: "When target > current it behaves as if written: while ((doc = nextDoc()) < target) {} return doc;" (DocIdSetIterator.java:144-152). With limit 1, nextDoc() never returns doc 1, but advance(1) does.
  • The query's composition. Occur.MUST: clauses that "must appear in the matching documents"; Occur.FILTER: "Like MUST except that these clauses do not participate in scoring" (BooleanClause.java:27, :35). So +join #id:b is the intersection of {a, c} and {b}: empty.
  • Upstream's definition of the hits. testWithRandomizedIndex adds a child to the expected set only while matchingChildrenCount <= childLimitPerParent, walking each block in doc order (TestParentsChildrenBlockJoinQuery.java:119-129).
  • The feature request assumes limit-then-intersect. #14565 (Jinny-Wang, the class's author): with a limit of 1, a join over [child1, child2, child3, Parent1] [child4, child5, Parent2] "will return child1 and child4", so combined with title:milk (child3, child5) "the boolean query will return no match"; it proposes putting a childQuery inside the join for that reason.
  • The authors guard against counting mid-block. The #14728 commit message: "this query type will not work with intrasegment concurrency, as it may split a block, leading to overcollection of child documents". The query throws for intra-segment partitions (ParentsChildrenBlockJoinQuery.java:191-197), and three places in the test class say "Do not use Concurrency.INTRA_SEGMENT as that would break childLimitPerParent counting" (TestParentsChildrenBlockJoinQuery.java:185 in testAdvance, :246 in the shared helper test(...), :369 in testExplain). advance() into the middle of a block is an unguarded path to the same over-collection.
  • No test advances into a block where the limit binds. testAdvance advances only to a block's first child or past the end (TestParentsChildrenBlockJoinQuery.java:212-219); testExplain's explain(query, 4) (:399) advances a fresh scorer to the middle of block [3, 4, 5], past matching child 3, but its limit 2 never binds in that index (:336-386); and the class's tests do not run QueryUtils.check, whose checkFirstSkipTo advances a fresh scorer to every document between hits (QueryUtils.java:408-447).
  • Explain disagreeing with search is treated as a bug. On #15041 benwtrent called an explain match for a non-hit in this class's test "troublesome as that indicates we are matching on a filtered out document now, or that explain is broken" (that failure had another cause, merge-ordered doc ids, and was fixed in the test).
The devil's-advocate check166 words

The strongest case for "intended" (built by the devil's-advocate verifier and the adjudication): the javadoc promises only a maximum, and each pass of the iterator does return at most N children per parent; it never says which N. #14565 motivates the limit as a diversification budget ("to ensure that docs from more parents are considered"), so "limit after the outer filter" could look useful. The class is @lucene.experimental, and explain() is a development aid that is normally called on hits.

Why it fails: one query on one index gives different answers depending on things that must be transparent: clause costs (one block: 0 hits; two blocks: b), query caching (the join cached: 0 hits) and sort skipping (a plain sorted search puts c1-3000 first). No documentation could describe that. "Limit after the filter" holds only when the filter happens to lead. The advance() contract is not optional, @lucene.experimental is about API stability, and explain() is wrong for the query alone. Verdict: not intended.

Suggested fix

#

Recommended Count from the target's block start, keep skipping whole blocks (validated)

For a finite limit, advance(target) first jumps to the first matching child of the target's block (parentBits.prevSetBit(target - 1) + 1), counts from there and steps with nextDoc() to the target, so whole blocks are still skipped (+38 lines). The repro, all 105 lucene/join tests and :lucene:join:check pass with it.

if (childLimitPerParent != DEFAULT_CHILD_LIMIT_PER_PARENT) {
  int blockStart = target >= parentBits.length() ? target
      : target == 0 ? 0 : parentBits.prevSetBit(target - 1) + 1;
  if (blockStart > childDoc) {
    childDoc = childIt.advance(blockStart);   // skip whole blocks
    childDocCount = 0;
    // ... align parent and child, scores, childDocCount++
    if (childDoc >= target) return childDoc;
  }
  int doc;
  while ((doc = nextDoc()) < target) {}    // count inside the block
  return doc;
}
All options and trade-offs3 options · 608 words

Two fixes were built and run; both make advance() return exactly what a nextDoc() loop returns for a finite limit and leave the default limit's code path unchanged.

Count from the target's block start, keep skipping whole blocks (validated) (recommended)

#

For a finite limit, advance(target) computes the first document of the target's block, parentBits.prevSetBit(target - 1) + 1. If that lies after the current child, it moves the child iterator there with one advance, aligns the parent, resets the count and counts the child it lands on as the block's first; then it steps with nextDoc() until it reaches target (+38 lines in ParentsChildrenBlockJoinQuery.java).

if (childLimitPerParent != DEFAULT_CHILD_LIMIT_PER_PARENT) {
  int blockStart = target >= parentBits.length() ? target
      : target == 0 ? 0 : parentBits.prevSetBit(target - 1) + 1;
  if (blockStart > childDoc) {
    childDoc = childIt.advance(blockStart);   // skip whole blocks
    childDocCount = 0;
    // ... align parent and child, scores, childDocCount++
    if (childDoc >= target) return childDoc;
  }
  int doc;
  while ((doc = nextDoc()) < target) {}    // count inside the block
  return doc;
}

Trade-offs

  • Inside the target's block it steps child by child, at most childLimitPerParent counted children before it moves on to the next parent; blocks before the target's block are still skipped with one advance.
  • 38 lines instead of 7. A reviewer may want the original's childDoc <= parentDoc ? parentIt.nextDoc() : parentIt.advance(childDoc) guard (:359-363) mirrored where the fix calls parentIt.advance(childDoc); it only matters if the child query matched a parent document.
  • No benchmark was run.

Step with nextDoc() for a finite limit (validated)

#

For a finite limit, advance(target) runs the DocIdSetIterator#advance reference loop (+7 lines; the sketch of the two hunt units that found the bug).

if (childLimitPerParent != DEFAULT_CHILD_LIMIT_PER_PARENT) {
  // The limit counts the matching children of a block from its first child, so the
  // children between the current doc and the target must be counted, not skipped.
  int doc;
  while ((doc = nextDoc()) < target) {}
  return doc;
}

Trade-offs

Obviously correct, but a finite limit then never skips: a sparse filter leading the conjunction makes the join walk all its matches up to each target (bounded by the join's own cost, matching parents x limit).

Document that the limit depends on how the query is driven (not recommended)

#

Leave the code and say in the javadoc which N children are returned depends on the caller.

Trade-offs

The answer would depend on clause costs, caching and sort skipping, and explain() would stay wrong for the query alone; no check supports it.

Downstream note

#

Not a security issue: every extra hit still matches the child query, belongs to a parent that matches the parent query and passes every other required clause, so no filter is bypassed; only the per-parent limit is exceeded. An application that uses the limit itself as an exposure cap would show more children than intended; that depends on downstream use.

How it was found

#

An automated bounded-exhaustive check compared explain() with the actual hits on every small block-join index and flagged a non-hit explained as a match; reading advance() showed why. An adjudication's differential check against a reference join written from the javadoc then found 11,180 mismatches in 1,683,032 checks, none for the default limit.

The method in full173 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier), on the stock main jar.

  • First signal (2026-10-26). A hunt unit's explain-vs-hit check over block-join indexes (oracle: explain(doc).isMatch() equals "doc is a hit") reported a non-hit child explained as a match; reading advance() found the cause and a probe confirmed the conjunction effect. A second unit found the same root cause the same day, by reading the iterator and with its own advance-vs-nextDoc and FILTER-conjunction checks; its candidate was withdrawn as a duplicate.
  • Widened by the adjudication unit (2026-10-29). LFV-1048, snapshot of 2026-11-06

Registry title
ParentsChildrenBlockJoinQuery: advance() does not count the matching children it skips, so conjunctions, sorted searches and explain return children beyond childLimitPerParent
Area
join / block join iterator (ParentsChildrenBlockJoinQuery advance() and Weight#explain; reached through ConjunctionDISI, sorted-search competitive iterators and IndexSearcher.explain)
Priority
Medium, rank 57: For users of the experimental ParentsChildrenBlockJoinQuery (released 10.4+, no known downstream user) with a finite childLimitPerParent, ordinary conjunctions, sorted searches and explain silently return children over the limit, the same rarely-used experimental wrong-hits profile as the RescoreTopNQuery group, so it closes that group above the score-only LFV-424 and well above its score-only sibling LFV-218.
Impact class
silent wrong results
Impact note
Applications on 10.4.0 through 10.6.0 or main that use the experimental ParentsChildrenBlockJoinQuery with a finite childLimitPerParent (the default Integer.MAX_VALUE is not affected) get children beyond the limit, with no error, whenever something other than the join's own nextDoc() drives its iterator: a cheaper child-level MUST/FILTER clause leading a conjunction, a sorted top-N search once competitive-iterator skipping starts (about 1000+ hits in the intended-behaviour check's probe), or IndexSearcher.explain on a non-hit, which is reported as a match; default codec, IndexWriterConfig and IndexSearcher, -ea or -da, five documents suffice; the join alone with unsorted search() and count() is correct.
Summary
You index the blocks [a, b, p1] and [c, p2] and build a ParentsChildrenBlockJoinQuery with childLimitPerParent 1, which on its own matches a and c, the first matching child of each parent. You expect the BooleanQuery +join #id:b to match nothing and explain(join, b) to say it is not a match. Instead the conjunction returns b and explain reports b as a match: advance(target) starts counting the limit at the target instead of at the block's first child, so it returns a child that nextDoc() never returns, which breaks the DocIdSetIterator#advance contract.
