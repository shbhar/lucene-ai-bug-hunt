After one failed doc-values close, a reopened reader is handed the closed producer

When closing a reader fails on a doc-values file, the segment's shared doc-values cache keeps the closed producer. A reader reopened later onto a commit that needs it opens normally, but reads from the closed files throw AlreadyClosedException; every release since 4.6.0 is affected, and the fix swaps two statements.

The finding in 30 seconds

#

All readers of one segment share a cache of open doc-values producers, one per update generation. When the last reader of a generation closes, the producer is closed first and removed from the cache second, so a close that throws leaves the closed producer cached for the next reader.

  1. Keep old commits (NoDeletionPolicy). Index two docs with n = 0 and 1 and commit; update doc 0 to n = 10 and commit again. The update lives in doc-values generation 1.
  2. Open r1 on commit 1, then r2 = openIfChanged(r1, commit 0). r2 shares r1's segment and its doc-values cache, but does not use generation 1.
  3. Close r1 while one input close() throws an IOException. Lucene closes the generation-1 producer, but the throw skips removing it from the cache, and its reference count is put back to 1.
  4. Reopen: r3 = openIfChanged(r2, commit 1). You expect doc 0 to read n = 10, as a fresh DirectoryReader.open(commit 1) does.
  5. Instead r3 is handed the cached, closed producer: getNumericDocValues("n") throws AlreadyClosedException: Already closed., and keeps throwing until every reader of the segment is closed.

Who is affected

#

Applications that keep older commits (NoDeletionPolicy, SnapshotDeletionPolicy) and move readers between them with openIfChanged(reader, commit), on a Directory whose input close can throw after closing its file (the stock MMapDirectory input close never does). The failure is loud and contained: no data changes, and a fresh open works. Contrived, so priority Low.

Mechanism, terms and numbers584 words

All readers of one segment core share one SegmentDocValues, a cache with one reference-counted doc-values producer per doc-values update generation. When the last reader of a generation lets go, release() closes the producer and only then removes the generation from the cache (SegmentDocValues.java:54-59 on main). If the close throws, the removal is skipped and RefCount.decRef puts the count back to 1 ("Put reference back on failure", RefCount.java:51-54). Nobody owns that count: the closing reader is already marked closed (IndexReader.java:224), so the release is never retried. The next reader of the same core that needs the generation, for example one returned by openIfChanged(reader, commit) onto a kept commit, gets the closed producer, and its doc-values reads that touch the closed files throw AlreadyClosedException (in the repro, the first read). A fresh DirectoryReader.open of the same commit reads correct values. It needs an input close that throws after closing its file, which the stock MMapDirectory input close never does, plus commit-point navigation with kept commits; it fails loudly and changes no data. The order dates from LUCENE-5189 (2013): every release from 4.6.0 to 10.6.0 and main are affected. The fix removes the cache entry before closing.

Terms

#
  • Doc-values generation: each commit that carries doc-values updates for a segment writes them as a new generation of doc-values files (for example _0_1_Lucene90_0.dvd, the file whose close failed in the independent reproducer's diagnostic run). A reader of that commit reads each field from the generations that hold its values: with main's default doc-values overlays (8, IndexWriterConfig.java:115), n is read from generation 1 (the sparse update) layered over generation -1, the segment's original doc values (SegmentDocValuesProducer.java:77-81, :182-186); with overlays off, as in 10.6.0, only from the generation that last rewrote it.
  • SegmentDocValues: one per segment core, shared by every SegmentReader of that core (SegmentReader.java:153, this.segDocValues = sr.segDocValues;). It maps each generation to a RefCount<DocValuesProducer> (SegmentDocValues.java:35-36).
  • Reopen across a doc-values-only change: openIfChanged(reader, commit) builds the new segment reader from the old one (StandardDirectoryReader.java:328-337), so both draw from the same cache.

The bug

#
// SegmentDocValues.java:51-60
return new RefCount<>(dvFormat.fieldsProducer(srs)) {
  protected void release() throws IOException {
    object.close();                       // :55  throws here...
    synchronized (SegmentDocValues.this) {
      genDVProducers.remove(gen);         // :57  ...so this never runs
    }
  }
};

// RefCount.java:46-55 (condensed)
if (refCount.decrementAndGet() == 0) {
  try { release(); }
  catch (Throwable t) { refCount.incrementAndGet(); throw t; }   // "Put reference back on failure"
}

// SegmentDocValues.java:64-75: a cached entry is incRef'd and returned without any check
  1. r1.close() reaches SegmentReader.doClose (SegmentReader.java:214-225), which decRefs generation 1 once. The count hits 0, release() runs, and Lucene90DocValuesProducer.close (:510-512, IOUtils.close(data, ...)) throws from the data input, which the repro's wrapper has already closed (IOUtils.close still tries the other inputs).
  2. The removal at :57 is skipped and RefCount.decRef restores the count to 1. IndexReader.decRef set closed = true before doClose (IndexReader.java:222-227), so r1 can never retry: the count has no owner.
  3. openIfChanged(r2, commit 1) asks the shared cache for generation 1, finds the entry, incRefs it to 2 and returns the closed producer. The reader opens normally; its first doc-values read touches the closed data input and throws (a dense constant column would still read: it is served from metadata, Lucene90DocValuesProducer.java:895-902).

With the repro's plain directory the read fails in ByteBuffersIndexInput.ensureOpen with AlreadyClosedException: Already closed.; under the test framework's MockDirectoryWrapper the same bug shows as its use-after-close check, "Abusing closed IndexInput!".

Exposure and likelihood245 words
  • Who is hit. After one failed close, every later reader of that segment core that needs the released generation is handed the closed producer, and its doc-values reads that touch the closed files fail (in the repro, the first read), until all readers of the core are closed.
  • What triggers the failed close. A doc-values input close() that throws while a reader closes, after it has really closed its file (the repro's wrapper closes its delegate, then throws). The stock MMapDirectory input close propagates no exception (MemorySegmentIndexInput.java:707-730 retries until the arena closes); FSDirectory.open returns MMapDirectory on 64-bit JREs and NIOFSDirectory otherwise (FSDirectory.java:155-161). NIOFSDirectory (FileChannel.close, NIOFSDirectory.java:122-126) or a custom or filter Directory can throw there. A close that throws before closing its file may leave the producer usable or only partly closed (not tested).
  • Default vs opt-in. Every call is public, documented API; the deletion policy that keeps older commits and the commit navigation are the application's choice. No scale is needed: 2 documents and 1 update.
  • Loud, contained. A clean AlreadyClosedException, no data changed, no wrong results; a fresh DirectoryReader.open of the same commit reads correct values. Before 6.6.0 the failed close() itself returned normally, so the first sign was the later read failure.
  • Not claimed. Wrong results, corruption, and the NRT (IndexWriter reader pool) path were not tested.
  • Likelihood: contrived. Two rare events in one process; no public report of it was found since 4.6.0 (2013).

Why it looks unintended

#
  • openIfChanged(reader, commit) promises to "open and return a new reader"; a fresh open reads n = 10.
  • The cache is meant to drop a generation once no reader uses it; release() does so only when the close succeeds.
  • A failed close still really closes (LUCENE-5553); earlier close failures here were fixed as bugs (LUCENE-7775, #13436).
The full argument238 words
  • The contract. openIfChanged(DirectoryReader, IndexCommit): "If the IndexCommit differs from what the provided reader is searching, open and return a new reader" (DirectoryReader.java:276-287); resources are shared "when possible" (:233-234). Nothing documents that sibling readers break after a failed close; IndexReader.close only says no other methods should be called on the closed reader (IndexReader.java:345-346), and the repro never touches r1 again.
  • The cache's design. A design comment in the LUCENE-5189 discussion (#6253) plans for SegmentDocValues to drop a generation once no reader uses it: "If it also removes a gen from the map when it's no longer referenced by any SR, we don't need to take care of clearing the genDVP map when all SRs were closed"; release() does so, but only when the close succeeds.
  • Lucene's close policy. LUCENE-5553 (#6615, 4.7.1) made a failing reader close still close everything and dropped the reference put-back from IndexReader.decRef, with maintainers agreeing on "close really closes and throws first exc" behaviour. RefCount kept the same put-back one level down.
  • Precedents and tests. LUCENE-7775 (#8826: decRef dropped every close exception because of an inverted null check; fixed to throw the first one) and #13436 (later producers were not closed after a failing one) fixed other close failures in SegmentDocValues.decRef as bugs. TestDirectoryReaderReopen.testOverDecRefDuringReopen asserts that the old reader keeps working after its reopen fails on an I/O error (an open failure there, not a close failure).
The devil's-advocate check135 words

The strongest case (the devil's-advocate verifier's steelman): RefCount.decRef puts the reference back on purpose ("Put reference back on failure"), which reads as retry-later semantics, so keeping the entry after a failed release is by design. TaxonomyReader.decRef (lucene/facet) still has the same put-back.

Why it fails: nothing can retry here. The idiom mirrors the IndexReader.decRef of 2013, and LUCENE-5553 removed it there on purpose; the closing reader is marked closed before doClose, so it can never retry (TaxonomyReader.decRef sets closed only after doClose succeeds, so a retry is possible there); SegmentDocValues is the only Lucene user of this RefCount; and no javadoc or test documents the put-back (RefCount.java:22-45). The cross-model review (OpenAI GPT-5.6) rated the intended-behaviour case weak. What survives is a severity argument (rare trigger, loud failure), hence priority Low.

Suggested fix

#

Recommended Remove the cache entry, then close (two lines moved)

Remove the generation from the cache before closing the producer: swap the two statements in SegmentDocValues.release(). A failed close then leaves no cached entry, and the next reader opens a fresh producer. Validated: the repro passes with assertions on and off; 11 related index suites (226 tests) and :lucene:core:check -x test pass.

       protected void release() throws IOException {
-        object.close();
+        // drop the cache entry first, so that a failed close cannot leave a closed producer cached
         synchronized (SegmentDocValues.this) {
           genDVProducers.remove(gen);
         }
+        object.close();
       }

Workaround until fixed: after a reader close fails, open the commits you need with DirectoryReader.open(commit) instead of openIfChanged from a reader of the same segment core, or close all readers of that core first.

A failed close leaves no entry behind, so the next request for the generation opens a fresh producer. This matches the LUCENE-5189 intent that a generation leaves the map once no reader references it.

Trade-offs

The success path is unchanged: release() runs only from SegmentDocValues.decRef, which holds the same lock as getDocValuesProducer (SegmentDocValues.java:64, :78), so no thread sees the in-between state. The half-closed producer is dropped rather than retried, which is no worse than today: nothing retries it now either. Its RefCount keeps the restored count of 1 but is no longer in the cache. Not explored: partly closed inputs, repeated close failures, file handles a failed close leaves open.

Downstream note

#

Downstream products are exposed only if they keep older commits and reopen readers onto them with openIfChanged(reader, commit) over a Directory whose input close can throw; no query or document can trigger it.

How it was found

#

A proof-obligation audit of SegmentDocValues's reference counting asked what a release that throws leaves in the shared cache, and found the closed producer stays cached with no owner. A public-API JUnit test then witnessed it on main; independent checks reproduced it with their own tests.

The method in full126 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: a producer whose release fails must not stay in the per-generation cache that the other readers of the segment core draw from. release() closes before it removes (SegmentDocValues.java:55-57), and RefCount.decRef restores the count on failure (RefCount.java:51-54), so the obligation is not met.
  • A JUnit test using a test-framework fault at the generation-1 input close witnessed it on main (assertions on and off, three seeds) and on 10.6.0 and 9.12.3. An independent reproducer, an executed review by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier wrote their own tests from the claim alone; the one-test plain-directory repro was cut from the independent reproducer's test on 2026-11-03.

Finding record

LFV-1217, snapshot of 2026-11-09

Registry title
After one failed close of a doc-values producer, SegmentDocValues keeps the closed producer in its per-generation cache, so a reader later reopened onto a commit that uses that doc-values generation is handed the closed producer and every doc-values read on it throws AlreadyClosedException
Area
index / SegmentDocValues (per-generation doc-values producer cache shared by the SegmentReaders of one segment core; reopen with openIfChanged(reader, commit))
Priority
Low, rank 626: After one failed doc-values input close, a reader reopened onto a kept commit is handed a closed producer and every doc-values read on it throws AlreadyClosedException, in every release since 4.6.0. It needs that close failure, which stock MMapDirectory never produces, plus commit-point navigation with retained commits, and it fails loudly with no data changed, so it is contrived.
Impact class
minor
Impact note
Hits only applications that keep older commits (NoDeletionPolicy, SnapshotDeletionPolicy or a custom deletion policy) and move readers between commits with DirectoryReader.openIfChanged(reader, commit), and only after closing one reader failed with an exception from a doc-values input close (stock MMapDirectory input closes do not throw; a channel-based, custom or filter Directory whose close can fail, or any Throwable from the producer close, is needed): every later reader of the same segment core that needs the released doc-values generation is handed the closed producer and every doc-values read on it throws AlreadyClosedException until all readers of that core are closed; a fresh DirectoryReader.open of the same commit reads correct values, no index data changes, no scale is needed, and every release since 4.6.0 is affected.
Summary
You keep older commits, open a reader r1 on a commit whose segment has doc-values updates, reopen it onto an older commit as r2 (r2 shares r1's segment core but not the updated doc-values generation), and closing r1 fails with an I/O error from that generation's doc-values input. You expect r2, and any reader later opened from it, to keep working: openIfChanged(r2, newer commit) should return a usable reader of that commit, just as a fresh open of the commit does. Instead SegmentDocValues closed the producer before removing it from its cache and RefCount put the reference back when the close threw, so the reopened reader is handed the closed producer and its first doc-values read throws AlreadyClosedException ('Already closed.').
Introduced
