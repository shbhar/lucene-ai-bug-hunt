Sorani normalizer: an invisible direction mark after a word-final HEH (ه) keeps it from becoming AE (ە)

SoraniAnalyzer folds a word-final HEH ه into AE ە and deletes invisible direction marks, but checks for the word's end before deleting a mark after the HEH. So خانه ("house") plus a right-to-left mark keeps its HEH: a search for خانە finds 2 of 3 spellings, silently, since 4.7.0.

The bug in 30 seconds

#

Sorani's vowel e is AE ە, and the normalizer also folds a word-final HEH ه to it. It deletes invisible formatting characters such as direction marks too, but only after it has already looked at the HEH.

  1. Index three documents with new SoraniAnalyzer() that spell "house" three ways: خانە (AE), خانه (HEH) and خانه followed by an invisible right-to-left mark (RLM, U+200F), each followed by گەورەیە ("is big").
  2. The normalizer's own rules say a word-final HEH becomes AE and direction marks are removed, so all three should be indexed as خانە, and a search for خانە should find 3 of 3 documents.
  3. It finds 2 of 3. The normalizer walks the word once, left to right. At the HEH it asks "is this the last character?", and the answer is no, because the RLM is still behind it. One step later it deletes the RLM, but it never looks at the HEH again.
  4. So the marked word is indexed as خانه (U+0647 at the end), and a query copied with the mark finds only that document, 1 of 3. The same happens with LRM and ALM, at query time (Analyzer.normalize) and after stemming. No error is raised.
  5. It has been like this since the Sorani analyzer was added in 4.7.0 (2014). Treating the HEH as final when only invisible formatting characters (other than ZWNJ and ZWJ) follow it fixes it, and all 30 upstream Sorani tests still pass.

Who is affected

#

Anyone indexing Sorani Kurdish with SoraniAnalyzer (default constructor included), SoraniNormalizationFilter or the soraniNormalization factory. It needs a word whose final e is typed as HEH with an invisible RLM, LRM or ALM right after it: rare, but silent, at index and query time, and the two spellings then never match.

Mechanism, terms and numbers739 words

Lucene's Sorani normalizer (SoraniNormalizer, used by SoraniNormalizationFilter, SoraniAnalyzer and the soraniNormalization factory) documents two rules that meet here: a word-final HEH (U+0647) is converted to AE (U+06D5), and "formatting characters such as directional controls are removed". It applies them in one left-to-right pass and tests i == len - 1 when it reaches the HEH, while a trailing RLM, LRM or ALM is still in the buffer; the mark is deleted one step later and the HEH, now last, is never converted. StandardTokenizer keeps such a mark inside the token, so the stock analyzer indexes خانه + RLM as خانه and خانه as خانە: the two look the same and do not match each other, at index and query time, with no error. Every release from 4.7.0 (2014) to 10.5.2 and main is affected. A 15-line fix that looks past trailing formatting characters the class deletes (any Character.FORMAT character except ZWNJ and ZWJ) passes the new test and all 30 upstream Sorani tests.

Terms

#
  • Sorani normalization: SoraniNormalizationFilter, and SoraniAnalyzer which uses it, runs SoraniNormalizer.normalize on every token. The class javadoc lists its rules, among them "Alternate forms of vowel 'e' (0647+200C, word-final 0647, 0629) are converted to 06D5 (AE)" and "Harakat, tatweel, and formatting characters such as directional controls are removed." (SoraniNormalizer.java:29, :33).
  • HEH and AE: AE ە (U+06D5) is Sorani's letter for the vowel e. At the end of a word the normalizer treats HEH ه (U+0647) as the same vowel; the upstream test gives the reason: "always (and in final form by def), so frequently omitted" (TestSoraniNormalizationFilter.java:70-73).
  • Direction marks: invisible characters such as RLM (U+200F), LRM (U+200E) and ALM (U+061C) that steer the display of mixed left-to-right and right-to-left text. Java classifies them as Character.FORMAT. They do not change how the HEH joins (Unicode joining type Transparent), so خانه + RLM looks exactly like خانه.

The bug

#
  1. normalize walks the buffer once, left to right, with one switch per character (SoraniNormalizer.java:72-128).
  2. case HEH converts the HEH only if (i == len - 1): if it is the last character of the buffer at that moment (:89-93).
  3. A trailing mark is still in the buffer then. The default branch deletes it later, like every Character.FORMAT character (:120-124).
  4. For خانه + RLM (len = 5): at i = 3 the test is 3 == 4, false, so the HEH stays; at i = 4 the RLM is deleted (len = 4); the result خانه ends in an unconverted HEH.
  5. The class's other position rule is safe: a leading mark is deleted before the REH is visited, so a word-initial REH still becomes RREH (:100-104). The ZWNJ rule rewrites the HEH before it itself (:82-88).
  6. SoraniAnalyzer tokenizes with StandardTokenizer, which keeps a trailing format character inside the token (UAX#29 rule WB4, StandardTokenizerImpl.jflex:83-85), and its normalize (the query side) applies the same filter (SoraniAnalyzer.java:113-130).

Exposure and likelihood592 words
  • Who is exposed. Applications that index Sorani Kurdish text with new SoraniAnalyzer() or any other constructor (no option avoids it), with SoraniNormalizationFilter in a custom chain, or with the SPI factory soraniNormalization (the factory javadoc shows the Solr form solr.SoraniNormalizationFilterFactory). Downstream servers that ship a built-in Sorani analyzer on this filter, such as Elasticsearch's sorani analyzer with its sorani_normalization filter, inherit it (read in their documentation; not executed).
  • Default or opt-in. You opt in by choosing the Sorani analyzer or filter for a field; inside it, this is the default behaviour.
  • What triggers it. A word whose final vowel is typed as HEH and whose final HEH is followed only by one or more invisible formatting characters that the class deletes, such as RLM, LRM, ALM, PDF, RLO, PDI or the soft hyphen, with no ZWNJ or ZWJ among them (HEH + RLM + ZWNJ already becomes AE through the ZWNJ rule). Deterministic: every such input, every time; no size or scale is needed.
  • Effect. The marked word is indexed and queried as ..0647, the unmarked one as ..06D5, so they do not match each other in either direction (a search finds 2 of 3 spellings, a query copied with the mark 1 of 3). The stemmer then sees a different word, so the stemmed terms differ too (کوردییه: [..06CC 06CC] without the mark, [..06CC 06CC 0647] with it). The marked term is one that HEH + TATWEEL or HEH + FATHA already produce, so a query typed with the mark also matches a document whose word ends in HEH + TATWEEL (executed in the follow-up's probe).
  • Not affected. Words spelled with AE, words without a trailing mark, marks anywhere but directly after a final HEH. No exception, no hang, no extra cost; offsets and positions are consistent and CheckIndex is clean (the follow-up's probe: 3,000 trigger-dense strings, checkRandomData(200), CheckIndex after forceMerge(1)).
  • How likely. Rare. The upstream Sorani vocabulary test file (8,272 rows of frequent corpus words) has 11 words with a trailing direction control (U+202E), none of them after a HEH, and the prior-report searches found no report in the 12 years since 4.7.0.
  • Existing indexes and rollout. A fix changes indexed terms of affected words, so those fields need a reindex, and index-time and query-time analysis must change together: with the fixed analyzer at query time only, a query typed with the mark no longer finds the old marked documents, so neither spelling finds them (reasoning).
  • Workaround. Until a fix ships, a patternReplace char filter that deletes the direction marks in front of the tokenizer gives ..06D5 and 3 of 3 hits (executed with SPI names through CustomAnalyzer); it must be in both the index-time and the query-time analyzer. Its pattern leaves out the soft hyphen and the other format characters the fix covers, and the executed CustomAnalyzer has no stop filter or keyword marker, so it is not the same as SoraniAnalyzer; to keep SoraniAnalyzer (a final class), wrap it in an AnalyzerWrapper that adds the char filter in wrapReader and wrapReaderForNormalization (not executed).
  • Unicode versions and older JDKs. JDK 25's Character data is Unicode 16.0, StandardTokenizer's tables are Unicode 12.1, and the joining types here come from ICU (Unicode 17). ALM (U+061C) and the isolates LRI, RLI, FSI and PDI (U+2066-U+2069) were added in Unicode 6.3, after Java 8's Unicode 6.2, so on Java 8 they are not format characters and would stay in the term (not executed); RLM and LRM behave the same on every supported JDK.

Why it is a bug, not intended

#
  • The class javadoc: "word-final 0647" is converted to AE, and "directional controls are removed" (SoraniNormalizer.java:29, :33).
  • Its word-initial rule ignores a removed mark: a leading RLM before REH still gives RREH. Only the trailing case breaks.
  • No test keeps HEH before a mark; the upstream vocabulary treats its 11 words with a trailing mark as if it were absent.
The full argument356 words
  • The contract. The class javadoc (SoraniNormalizer.java:21-35): "Alternate forms of vowel 'e' (0647+200C, word-final 0647, 0629) are converted to 06D5 (AE)" (:29) and "Harakat, tatweel, and formatting characters such as directional controls are removed." (:33). The public SoraniNormalizationFilter is "A TokenFilter that applies SoraniNormalizer to normalize the orthography" (SoraniNormalizationFilter.java:24). SoraniNormalizer was a public class, with this rule list in its published javadoc, from 4.7.0 to 9.12.x (javap of the 4.7.0 and 9.12.3 jars; Lucene renders javadoc with -protected); it is package-private only since 10.0.0 (LUCENE-10561). The javadoc states no order of operations and no general "removed characters never change the result" rule, so the claim is that this order leaves two documented rules in tension, not that a stated invariant is broken.
  • The rule's reason. testFinalH: "always (and in final form by def), so frequently omitted" (TestSoraniNormalizationFilter.java:70-73). The rule is about the final letter form; RLM, LRM, ALM, PDF and RLO have Unicode joining type Transparent (PDI: Non_Joining), so a HEH before them is still drawn in final form.
  • The class's own symmetry. A leading RLM, LRM, ALM, RLE or TATWEEL before REH still gives word-initial RREH, and the ZWNJ rule looks past a mark (HEH + RLM + ZWNJ gives AE). Only the trailing check runs before the deletion.
  • Upstream data. The vocabulary of TestSoraniStemFilter.testVocabulary (8,272 rows) has 11 words ending in U+202E whose expected output drops the mark and normalizes and stems as if it were absent (none of them ends in a HEH). Of its words ending in a HEH before characters the class removes, 320 end in HEH + ZWNJ (made AE by the ZWNJ rule) and one is HEH + TATWEEL -> HEH, which is not claimed (TATWEEL forces a joining form) and which the fix keeps; none has a HEH before a direction mark.
  • History. Both rules came in the first commit, in today's order (LUCENE-5379, 2014); the four later commits on the file change only the license header, formatting, array syntax and visibility (package-private from 10.0.0). No test, comment, commit message, CHANGES or MIGRATE entry mentions trailing marks.
The devil's-advocate check296 words

The intended-behaviour checker and the cross-model intended lens (which rated it moderate) built the strongest case: the javadoc is an unordered list of independent rules, and "word-final" can be read literally as "the last character of the token as given"; the upstream vocabulary pins HEH + TATWEEL -> HEH, so a trailing removable character can block the rule on purpose; the class is package-private, so its javadoc is no published contract; the behaviour has been stable for 12 years; and a fix forces a reindex.

The answer: the same class treats removed characters as absent for its word-initial rule and its ZWNJ rule; the stated reason is the final letter form, which the marks do not change, while TATWEEL and ZWJ do, so the pinned row agrees with the narrow claim and the narrow fix keeps it; the class promises to remove direction controls itself and the stock tokenizer hands them over inside the token; the project's own vocabulary expects trailing marks to be ignored; no record supports the literal reading. The package-private point does not hold for most of the bug's life: the class was public, with this list in its published javadoc, from 4.7.0 to 9.12.x; and a reindex is the usual cost of an analyzer fix.

Limits of the answer: the javadoc states no order of operations; the leading-mark case shows what the loop order allows, not what the authors meant for trailing marks; the 11 vocabulary words with a trailing mark do not end in a HEH; no Sorani reference is cited. Verdict: a real, narrow order-of-operations defect, best presented as an inconsistency between two documented rules that appears unintended, with the compatibility cost acknowledged. Do not argue idempotence: it is not documented, and HEH + TATWEEL stays non-idempotent with the fix.

Suggested fix

#

Recommended Treat the HEH as word-final when only formatting characters other than ZWNJ and ZWJ follow it

In SoraniNormalizer, count the HEH as word-final when only formatting characters that the class deletes follow it (any Character.FORMAT character except ZWNJ and ZWJ; +15/-1). Validated with gradle: the new test and all 30 upstream Sorani tests pass, assertions on and off, plus format and lint checks. Affected fields need a reindex.

static final char ZWJ = '\u200D';                      // new constant
case HEH:
  if (isWordFinal(s, i, len)) {                       // was: if (i == len - 1)
    s[i] = AE;
  }
  break;
private static boolean isWordFinal(char[] s, int pos, int len) {
  for (int i = pos + 1; i < len; i++) {
    if (s[i] == ZWNJ || s[i] == ZWJ || Character.getType(s[i]) != Character.FORMAT) {
      return false;
    }
  }
  return true;
}

Trade-offs

  • Existing indexes keep the old term for affected words until reindexed; worth a CHANGES line.
  • Cost: a forward scan from a HEH that stops at the first other character. The extra scan reads each character at most once per token, so the fix adds only linear work. (normalize() itself is not linear today: every deletion shifts the rest of the buffer, StemmerUtil.delete.)
  • Breadth: it admits every format character the class deletes, not only the direction marks. If maintainers want only the direction marks and the soft hyphen, the helper can test an explicit list instead (not built or tested).
  • Index-time and query-time analysis must change together during the rollout.
  • Unchanged by design: HEH + TATWEEL, ZWJ or a vowel mark stays HEH; HEH + ZWNJ was already AE.
  • Only main was built and tested with gradle; normalize() is the same, ignoring whitespace, from 4.7.0 on, so a backport should need at most context changes.

How it was found

The method in full153 words

Method: bounded-exhaustive translation validation of the script normalizers against their documented rules (the hunt's "semi-formal" tier), 2026-10-27.

  • The harness (NormalizerTV.java) ran the stock SoraniNormalizationFilter on every string of length up to 4 over a 29-character alphabet (letters including ZWNJ and TATWEEL, the harakat and 6 format characters), 732,541 inputs, and compared it with oracles derived from the class javadoc.

LFV-668, snapshot of 2026-10-28

Registry title
SoraniNormalizer checks for a word-final HEH before it removes trailing directional marks, so a word ending in HEH followed by RLM, LRM or ALM keeps HEH (U+0647) instead of becoming AE (U+06D5) as the class javadoc says
Area
analysis-common / Sorani normalizer (SoraniNormalizer.normalize; SoraniNormalizationFilter, SoraniAnalyzer and the 'soraniNormalization' factory)
Priority
Medium, rank 153: The stock SoraniAnalyzer silently indexes a different term for a word ending in HEH plus an invisible RLM, LRM or ALM, but only that rare input shape in one niche language triggers it.
Impact class
silent wrong results
Impact note
Search quality only, with no error: applications that analyze Sorani Kurdish text with SoraniAnalyzer (default constructor included), SoraniNormalizationFilter or the 'soraniNormalization' factory, on every release from 4.7.0 through 10.5.2 and on main, index and query a word whose final vowel is typed as HEH and that carries an invisible trailing RLM, LRM or ALM (StandardTokenizer keeps it inside the token) as a different term from the same word without the mark ([..U+0647] vs [..U+06D5]; the stemmed term can differ too), so the two visually identical spellings do not match each other; no scale is needed, -ea and -da behave the same, the mark must sit directly after the final HEH, and because a fix changes indexed terms, affected fields need reindexing after it.
Summary
You analyze Sorani Kurdish text with the stock SoraniAnalyzer or SoraniNormalizationFilter. The normalizer's javadoc says a word-final HEH (U+0647) is converted to AE (U+06D5) and that formatting characters such as directional controls are removed, so خانه ('house') followed by an invisible right-to-left mark should normalize like خانه itself, to خانە. Instead the HEH rule asks 'is this the last character?' while the trailing mark is still in the buffer, and the mark is deleted only later in the same pass, so خانه+RLM (and +LRM, +ALM) becomes خانه with a plain HEH and no longer matches خانە, with no error.
