SearcherTaxonomyManager refresh throws "Self-suppression not permitted" and loses the taxonomy error when closing the new reader also fails

If one SearcherTaxonomyManager refresh fails twice, first reopening the taxonomy and then closing the index reader it just reopened, maybeRefresh() throws IllegalArgumentException: Self-suppression not permitted and the taxonomy's IOException is lost. The cleanup calls t2.addSuppressed(t2) where t1.addSuppressed(t2) was meant; every release since 7.4.0 has it.

The finding in 30 seconds

#

One refresh, two failures: the taxonomy reopen throws IndexNotFoundException, then closing the new index reader throws an IOException. The caller should get the IndexNotFoundException; it gets IllegalArgumentException: Self-suppression not permitted.

Background: how SearcherTaxonomyManager refreshes

#
  1. SearcherTaxonomyManager keeps an IndexSearcher and a TaxonomyReader, the facet module's dictionary of category labels, at matching points in time. maybeRefresh() moves both to newer commits; its javadoc says it throws IOException when refreshing fails.
  2. A refresh reopens the index reader first, then the taxonomy reader. If the taxonomy reopen fails, the code closes the index reader it just opened (so its files do not leak) and rethrows the taxonomy error.
  3. Java's a.addSuppressed(b) attaches a secondary failure b to the primary failure a. A throwable cannot suppress itself: b.addSuppressed(b) always throws IllegalArgumentException("Self-suppression not permitted").

The finding, step by step

#
  1. Keep a searcher and its facet taxonomy in step with SearcherTaxonomyManager and call maybeRefreshBlocking() after new commits. Each refresh reopens the index reader first, then the taxonomy reader.
  2. One refresh fails twice. The taxonomy reopen throws IndexNotFoundException (in the repro its newest commit file is deleted, as in the upstream test testExceptionDuringRefresh). Then closing the index reader just reopened fails: every file close inside it throws an injected IOException (two in the test run), and Lucene's IOUtils.close keeps the first and suppresses the rest, so the manager sees one close failure.
  3. You expect the documented IOException: the taxonomy's IndexNotFoundException, with the close failure attached to it as a suppressed exception.
  4. Instead you get an unchecked IllegalArgumentException: Self-suppression not permitted, caused by the close failure. The IndexNotFoundException is in neither the cause nor the suppressed list: the cleanup calls t2.addSuppressed(t2), which Java always rejects, so throw t1 never runs.
  5. Nothing leaks and, once the faults are gone, the next refresh works; but catch (IOException e) misses it: a refresh task scheduled every 5 ms that catches only IOException is cancelled after this 1 refresh, and its searcher then stays stale; with only the taxonomy failure it catches the IOException and keeps running (93 runs in the test).

Who is affected

#

Applications that use taxonomy facets through SearcherTaxonomyManager (the opt-in facet module), 7.4.0 to 10.6.0 and main, when one refresh suffers two failures at once, in practice two I/O errors. The root cause is lost, and code catching the documented IOException misses the unchecked exception. Nothing leaks and the index is not damaged.

Mechanism, terms and numbers421 words

SearcherTaxonomyManager refreshes an IndexSearcher and its facet TaxonomyReader together: it reopens the index reader, then the taxonomy reader. If the taxonomy reopen throws, it closes the index reader it just opened and rethrows the taxonomy error, a cleanup added in 7.4.0 by LUCENE-8244 to stop a file-handle leak. When that close also throws, the cleanup calls t2.addSuppressed(t2) (SearcherTaxonomyManager.java:209) where t1.addSuppressed(t2) was meant. Java rejects self-suppression with IllegalArgumentException("Self-suppression not permitted"), so maybeRefresh() and maybeRefreshBlocking() throw that unchecked exception, caused by the close failure, instead of the documented IOException, and the taxonomy failure is lost from the whole chain. Nothing leaks, the index is not damaged and, once the faults are gone, the next refresh works; but code that catches only IOException misses it, and a scheduled refresh task that does so is cancelled, leaving its searcher stale. 7.3.1 passes, 7.4.0 fails and 7.4.0 with the one-token fix passes; every release executed (7.4.0, 7.6.0, 7.7.3, 8.0.0, 8.11.4, 9.0.0, 9.12.3, 10.0.0, 10.5.2) fails, and 10.6.0 and main have the same line. Low priority: it needs two failures in one refresh.

Mechanism (Lucene main 645d4fe14a20)

#
// SearcherTaxonomyManager.refreshIfNeeded, condensed
IndexReader newReader = DirectoryReader.openIfChanged(dr, refreshCommit);   // :195  index first
...
try {
  tr = TaxonomyReader.openIfChanged(ref.taxonomyReader);                     // :204  taxonomy: throws t1
} catch (Throwable t1) {
  try {
    IOUtils.close(newReader);                                                // :207  close: throws t2
  } catch (Throwable t2) {
    t2.addSuppressed(t2);                                                    // :209  always throws
  }
  throw t1;                                                                  // :211  skipped
}
  1. ReferenceManager.doMaybeRefresh calls refreshIfNeeded (ReferenceManager.java:167). Line 195 reopens the index reader; line 204 reopens the taxonomy reader, which throws t1.
  2. Line 207 closes the new index reader. When that throws t2, line 209 calls t2.addSuppressed(t2).
  3. Throwable.addSuppressed starts with if (exception == this) throw new IllegalArgumentException(SELF_SUPPRESSION_MESSAGE, exception); (JDK Throwable.java:1099-1101; javadoc: "a throwable cannot suppress itself", since Java 7). So line 209 always throws, with t2 as the cause.
  4. That exception leaves the inner catch, so throw t1 is skipped and t1 is dropped. It is unchecked, so it passes refreshIfNeeded's throws IOException and comes out of maybeRefresh / maybeRefreshBlocking.
  5. doMaybeRefresh's finally blocks release the current reference, notify listeners and unlock (ReferenceManager.java:180-187): the manager is unchanged and usable.

Exposure and likelihood333 words
  • Who. Applications that use taxonomy facets through SearcherTaxonomyManager, with any of its constructors, on 7.4.0 through 10.6.0 and main.
  • When. Only when one refresh suffers two failures at once: the taxonomy reopen throws (an I/O error, an unreadable taxonomy commit, or any other Throwable) and closing the index segment files opened moments earlier also throws. Each is an ordinary environmental fault, but the second is uncommon on its own, so the pair is rare; the recorded searches found no report of it.
  • What goes wrong. An unchecked IllegalArgumentException instead of the documented IOException, and the root cause, the taxonomy failure, is lost from logs and diagnostics; the message points at the JDK, not at the taxonomy.
  • Code that catches IOException misses it (executed on main with assertions on and off, 10.5.2 and 9.12.3): a ScheduledExecutorService task that calls maybeRefresh() every 5 ms and catches only IOException is cancelled by the JDK after the double-failure refresh (1 tick); in that setup, where nothing inspects the task's ScheduledFuture, nothing is logged, and a document deleted in the new commit is still returned until the application refreshes by hand. With only the taxonomy failure, the task catches one IOException and keeps running (93 ticks); with the fix it keeps running too (77 ticks).
  • Lucene's own ControlledRealTimeReopenThread ends on any refresh IOException (it wraps it in a RuntimeException), so for it only the exception type and message change.
  • By reading only: if the taxonomy failure is an Error, such as an OutOfMemoryError, and the close also fails, the caller gets the IllegalArgumentException instead of the Error.
  • What it does not do: no leak (the new reader's files are closed) and no index damage. The failed refresh keeps the previous searcher, as any failed refresh does, and once the faults are gone a later refresh succeeds (executed with transient faults). Results go stale only while nothing refreshes, for example after the application's refresh task died on the unchecked exception (above).

Why it looks unintended

#
  • x.addSuppressed(x) can never succeed, and the block ends with throw t1: the intent is to rethrow the taxonomy error with the close failure attached.
  • maybeRefresh and maybeRefreshBlocking document @throws IOException; the upstream test added with this code asserts the taxonomy's IndexNotFoundException for the single-failure case.
  • The sibling DirectoryTaxonomyReader.doOpenIfChanged does the same cleanup with IOUtils.closeWhileSuppressingExceptions(t, r2), which keeps the primary failure.
The full argument194 words
  • The code states its intent. The block closes the new reader and then throw t1 (SearcherTaxonomyManager.java:211). t2.addSuppressed(t2) can never succeed (the JDK rejects it by contract), so no design calls it; the evident intent is t1.addSuppressed(t2).
  • The contract. maybeRefresh and maybeRefreshBlocking: "@throws IOException if refreshing the resource causes an IOException" (ReferenceManager.java:203, :231); refreshIfNeeded: "@throws IOException if the refresh operation failed" (:72). Nothing documents an IllegalArgumentException.
  • The test that came with this code. TestSearcherTaxonomyManager.testExceptionDuringRefresh (:343-366), added by the same LUCENE-8244 commit, deletes the taxonomy's newest segments_N and asserts expectThrows(IndexNotFoundException.class, mgr::maybeRefreshBlocking). Its close succeeds, and no upstream test makes that close fail.
  • The codebase idiom. DirectoryTaxonomyReader.doOpenIfChanged handles the same situation with catch (Throwable t) { IOUtils.closeWhileSuppressingExceptions(t, r2); throw t; } (DirectoryTaxonomyReader.java:221-223).
  • History. The line came in the LUCENE-8244 patch ("Do not leak open file descriptors in SearcherTaxonomyManager's refresh on exception", 7.4.0 Bug Fixes); its issue (#9291) holds only the patch note and two commit notices (the JIRA record adds the 2022 migration notice), so nobody discussed this line there. Before that fix the taxonomy failure propagated (and the reader leaked).
The devil's-advocate check248 words

The strongest "works as intended or not worth it" case (the refute and intended-lens reviews and the devil's-advocate verifier): it needs two simultaneous failures; nothing leaks and the IllegalArgumentException still carries the close failure as its cause; the classes involved are @lucene.experimental: ReferenceManager (ReferenceManager.java:35), whose maybeRefresh javadoc is the contract quoted above, TaxonomyReader (TaxonomyReader.java:57) and DirectoryTaxonomyReader (DirectoryTaxonomyReader.java:61), while SearcherTaxonomyManager itself has no such tag; Java throws clauses are not exhaustive and no exception priority is documented for two failures at once; and the repro deletes an index file, while Lucene's SECURITY.md treats index files as trusted.

Why it fails: @lucene.experimental says the API may change between releases, not that a call which can never succeed is designed behaviour; none of this makes x.addSuppressed(x) meaningful, the block itself says throw t1, and the test that came with it asserts the taxonomy's exception. The deleted segments_N is the upstream test's own way to make the taxonomy reopen fail, and there Lucene asserts a clean IndexNotFoundException; an independent reproducer gets the same result with a plain injected IOException during DirectoryTaxonomyReader.doOpenIfChanged and no file deleted. Rarity and the unharmed state argue for Low priority, which is how it is classed, not for intent. The cross-model lenses rated the intended-behaviour argument weak; a later cross-model fact check rated it moderate, citing the stale searcher left by a dead refresh task, the experimental tags and fix B's Error handling, all three covered in this doc.

Suggested fix

#

Recommended B. Use IOUtils.closeWhileSuppressingExceptions(t1, newReader), the module's idiom

Replace the hand-written cleanup with IOUtils.closeWhileSuppressingExceptions(t1, newReader); throw t1;, the idiom DirectoryTaxonomyReader.doOpenIfChanged already uses: the taxonomy error is rethrown with the close failure attached. The repro passes with assertions on and off, and the facet module's 307 tests run with 0 failures (7 skipped). The one-token t1.addSuppressed(t2) also works and suits backports.

How it was found

#

Code reading of the refresh exception paths of Lucene's near-real-time reference managers, while writing a TLA+ model of ReferenceManager and SearcherManager. The model does not cover SearcherTaxonomyManager and no model-checker trace showed this, so it is a code-reading find; a JUnit test then confirmed it.

The method in full142 words

Method: code reading (the study's non-formal tier). A hunting AI tool working on the near-real-time reference managers wrote a TLA+ model of ReferenceManager and SearcherManager with refresh and reader-close failures, and read the refresh exception paths of the subclasses while doing so. It noticed t2.addSuppressed(t2) in SearcherTaxonomyManager.refreshIfNeeded.

  • The model covers ReferenceManager and SearcherManager, not SearcherTaxonomyManager, and no TLC trace produced this signal; so the find is credited to code reading, not to the model.
  • The finder confirmed it with a JUnit test that uses two protected extension points (a DirectoryTaxonomyReader subclass whose doOpenIfChanged throws, and a FilterDirectoryReader whose reopened instances fail in doClose).
  • Independent checks then reproduced it without subclassing any reader: one with plain injected I/O errors on the public API, one with the upstream testExceptionDuringRefresh scenario plus injected close errors; that scenario became the minimal repro.

Applications on Lucene 7.4.0 through 10.6.0 (10.6.0 by reading) or main that use SearcherTaxonomyManager (taxonomy facets with NRT, an opt-in module) are hit only when one refresh suffers two failures at once, the taxonomy reopen fails and closing the just-reopened index reader also fails (in practice two I/O errors), and then maybeRefresh() or maybeRefreshBlocking() throws an unchecked IllegalArgumentException whose cause is the secondary close failure instead of the documented IOException carrying the taxonomy failure, which is missing from the whole exception chain; nothing leaks, no data is wrong and the manager stays usable, but a caller that catches only IOException is bypassed (executed: a periodic ScheduledExecutorService refresh task that catches IOException is silently cancelled after that one refresh, so the searcher stays at its old point in time until the application refreshes again).
Summary
You use SearcherTaxonomyManager, and one refresh hits two I/O failures at once: reopening the taxonomy fails, and closing the index reader that was just reopened also fails. You expect maybeRefresh() to throw the taxonomy failure as an IOException, its documented contract, with the close failure attached as a suppressed exception. Instead it throws IllegalArgumentException('Self-suppression not permitted'), because the cleanup code calls t2.addSuppressed(t2) where t1.addSuppressed(t2) was meant, so the taxonomy failure is lost entirely and callers that catch IOException do not see it.
