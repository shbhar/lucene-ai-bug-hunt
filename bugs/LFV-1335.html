Function value sources and CommonTermsQuery treat 0.0 and -0.0 parameters as equal but give them different hash codes

new ConstValueSource(0f) and new ConstValueSource(-0f) are equals, yet their hash codes are 0 and -2147483648, which breaks Java's equals/hashCode contract. Five more value sources and CommonTermsQuery's minimum-should-match setting do the same, so hash sets, maps and composite queries treat equal objects as different; the mismatch changes no query's hits or scores.

The finding in 30 seconds

#

This row covers seven equals methods in lucene/queries: each compares a float or double parameter with == (so 0.0 == -0.0), but hashCode hashes its bits, which differ for the two zeros. FunctionQuery and FunctionRangeQuery inherit it. Related rows, not duplicates: LFV-1337 (core) and LFV-1341 (spatial3d), the same shape at other sites.

Background: two zeros, and how hash lookups work

#
  1. Java's float and double have two zeros, 0.0 and -0.0. 0.0f == -0.0f is true, but their bit patterns differ: Float.floatToIntBits gives 0x00000000 and 0x80000000.
  2. A HashMap or HashSet first compares hash codes and calls equals() only when they match. So equal objects must have equal hash codes; otherwise the lookup never reaches equals and misses.

The finding, step by step

#
  1. Build a = new ConstValueSource(0f) and b = new ConstValueSource(-0f). The constructor takes -0f as is; nothing checks the sign.
  2. a.equals(b) is true: equals compares the constants with ==, and in Java 0.0f == -0.0f.
  3. You expect a.hashCode() == b.hashCode(): Java requires equal hash codes for equal objects, and ValueSource declares both methods abstract so that every source implements them.
  4. Instead hashCode hashes the float's bits, 0x00000000 for 0f and 0x80000000 for -0f, so the hash codes are 0 and -2147483648.
  5. So a HashSet keeps both FunctionQuery(a) and FunctionQuery(b) (size 2, not 1), and a BooleanQuery over one is not equal to a BooleanQuery over the other. DoubleConstValueSource, LinearFloatFunction, ScaleFloatFunction, RangeMapFloatFunction, ReciprocalFloatFunction and CommonTermsQuery break the same way.

Who is affected

#

Applications that build one of these objects once with 0.0 and once with -0.0 (a computed or parsed negative zero) and rely on the two being one object in a hash set, map or composite query. Default configuration, since 4.0.0. The mismatch changes no query's hits or scores, and Lucene's query cache is not involved. Contrived, so priority Low.

Mechanism, terms and numbers631 words

Six function value sources in lucene/queries (ConstValueSource, DoubleConstValueSource, LinearFloatFunction, ScaleFloatFunction, RangeMapFloatFunction, ReciprocalFloatFunction) and CommonTermsQuery's two minimum-should-match fields compare a float or double parameter with == in equals but hash its bits in hashCode. Under ==, 0.0 equals -0.0; their bits differ only in the sign bit. So an object built with 0.0 and the same object built with -0.0 are equal but have different hash codes: for ConstValueSource, 0 and -2147483648. That breaks the Object.hashCode contract, which ValueSource re-declares as abstract (ValueSource.java:51-55) and Query's javadoc asks every query to honour (Query.java:95-116). FunctionQuery and FunctionRangeQuery pass equals/hashCode through to their source and inherit the mismatch. Measured effect: a HashSet keeps both of two equal FunctionQuery objects, and a BooleanQuery over one is not equal to a BooleanQuery over the other. The mismatch changes no query's hits, counts or scores, and Lucene's query cache is not involved. The value sources have had it since 4.0.0 (the code came from Solr in 2011), CommonTermsQuery since 4.2.0 (2013); the comparisons are unchanged in the files' history through 10.6.0 and main. Comparing in equals the same bits hashCode hashes fixes all seven sites.

This row covers the queries module only. LFV-1337 (core: BlendedTermQuery, LatLonPoint, XYDocValuesField) and LFV-1341 (spatial3d) are related rows with the same shape at other sites, each with its own fix.

What it changes

#
  • A HashSet holding FunctionQuery(new ConstValueSource(0f)) and FunctionQuery(new ConstValueSource(-0f)) has size 2; a lookup of one through the other misses.
  • A BooleanQuery whose only clause is FunctionQuery(ConstValueSource(0f)) is not equal to one whose only clause is (-0f), although the clauses are equal: BooleanQuery keeps clauses in hash-based sets.
  • Not changed by the mismatch: any one query's hits, counts and scores, and Lucene's LRUQueryCache. FunctionQuery and FunctionRangeQuery are not cacheable (FunctionQuery.java:82-84, FunctionRangeQuery.java:177-179); CommonTermsQuery is rewritten before caching, and minNrShouldMatch turns both zeros into the int 0 (CommonTermsQuery.java:138-143).
  • The two zeros are not interchangeable, though: FunctionQuery(ReciprocalFloatFunction(const(5), m, 1, b)) with m = b = 0 and with m = b = -0 are equal today and match the same document, but score Infinity and 0, because the scorer returns 0 for a negative value (FunctionQuery.java:130-137). That argues against today's equals; it is not an effect of the hash.
Exposure and likelihood134 words
  • Who is hit. Code that ends up with both zeros for one parameter: -0.0 comes from arithmetic (a negated or rounded zero) or from parsing "-0". Lucene's own query parsers never build these objects; the application chooses the parameters.
  • Default vs opt-in. Default configuration, public API, assertions on or off. CommonTermsQuery is an ordinary public query; the six classes are the function-query value sources.
  • Effect. Equality and hashing only: missed lookups and duplicate entries in hash-based containers keyed by these objects, and composite queries (such as a BooleanQuery) that compare unequal although their parts are equal. The mismatch changes no hit, count or score.
  • Scale. None needed: one pair of objects.
  • Likelihood: contrived. Objects that all use the same zero are consistent with each other; it takes both zeros for one parameter.

Why it looks unintended

#
  • Java's Object.hashCode contract; ValueSource declares equals and hashCode abstract, and Query's javadoc asks for both to be implemented properly.
  • CommonTermsQuery.equalsTo already compares its other three floats by their bits; only the two minimum-should-match fields use ==.
  • Lucene fixed the same -0.0 mismatch in five geo classes (#13292 / #13301).
The full argument198 words
  • The contract. Object.hashCode: "If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result." ValueSource.java:51-55 makes both methods abstract; Query.java:95-116: "Override and implement query hash code properly in a subclass. This is required so that QueryCache works properly."
  • Lucene's test oracle. QueryUtils.checkEqual asserts equal queries and equal hash codes together (QueryUtils.java:104-107).
  • An inconsistency inside one method. CommonTermsQuery.equalsTo compares highFreqBoost, lowFreqBoost and maxTermFrequency with Float.floatToIntBits (:367-371) and only the two minimum-should-match fields with == (:372-373). The field was an int (compared with !=) until LUCENE-4727 (2013) made it a float and changed only hashCode.
  • The module's own convention. FunctionScoreQuery's boost source compares with Float.compare in equals and hashes the boxed float (FunctionScoreQuery.java:403, :408).
  • Upstream precedent. #13292 / #13301 (2024) fixed the same == versus bit-hash mismatch for -0.0 in Point, XYPoint, Circle, XYCircle and Rectangle2D.
  • History. No javadoc, test, commit message or issue treats -0.0 specially at these sites; later rewrites (LUCENE-7277, 2016; the LUCENE-9570 reformat, 2020; #15889, 2026) kept == without discussing it.
The devil's-advocate check126 words

The strongest case: 0.0 and -0.0 are the same number, so equals returning true is right, and -0.0 is an odd parameter.

Why it fails: that would justify equals, not a different hash code; the API accepts -0.0 without validation, so it must still obey the contract. For the value sources the two zeros are not even interchangeable: ConstValueSource prints const(0.0) and const(-0.0), and ReciprocalFloatFunction (a/(m*x+b), a = 1) with m = b = 0 computes +Infinity at x = 5, with m = b = -0 -Infinity; as FunctionQuerys the two equal queries score Infinity and 0. Every verifier rated the bug real; two executed reviews by another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Compare the hashed bits in equals

In each equals, compare the same bits hashCode already hashes: Float.compare(x, y) == 0 for the float value sources, raw-bit equality for DoubleConstValueSource, and Float.floatToIntBits for CommonTermsQuery's two fields, as its other floats do. Validated: the repro passes with assertions on and off, and the whole queries module's tests pass (513 tests, 0 failures, 5 skipped).

All options and trade-offs3 options · 578 words

Validated with gradle in a clean scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-04): the repro fails stock with assertions on and off and passes with the fix, on and off.

All three options restore the contract. A suits the value sources, whose two zeros compute different values; for CommonTermsQuery, whose matching treats -0f as 0, a maintainer may prefer B. A mixed change (A for the value sources, B for CommonTermsQuery) is also reasonable.

The one-test repro checks the contract, so it passes under A and B alike.

Trade-offs

A choice of meaning, not only a contract repair: an object built with -0.0 becomes a different object from the 0.0 one. That matches the value sources, where the two are observably different (const(0.0) versus const(-0.0); ReciprocalFloatFunction +Infinity versus -Infinity). Two CommonTermsQuery objects that match the same documents become unequal. Side effect: at every changed site a NaN parameter compares equal to NaN (for DoubleConstValueSource, NaNs with the same raw bits); today two ConstValueSource(NaN) objects, or two CommonTermsQuery with a NaN minimum-should-match, are unequal because NaN == NaN is false.

Downstream note

#

Downstream products that map client input onto these parameters (for example a -0 from a request) see only a missed lookup or a duplicate entry in their own hash containers; the mismatch does not change query results.

How it was found

#

After the same == versus bit-hash mismatch had turned up in other Lucene classes, a semi-formal audit checked, site by site, that equals and hashCode agree for every value the public API accepts. A bytecode scan of the queries jar flagged the float fields compared with ==; executable 0.0 / -0.0 pairs confirmed each site on main.

The method in full138 words

Method: semi-formal (an equals/hashCode contract audit of sibling sites), 2026-11-04.

  • The obligation: for every accepted input, a.equals(b) implies a.hashCode() == b.hashCode() (Object.hashCode, ValueSource.java:51-55, Query.java:95-116). It needs x == y to imply equal hashed bits for every float or double parameter; that fails only for 0.0 versus -0.0, and no constructor or setter excludes -0.0.
  • A bytecode scan of the queries jar listed the equals methods that compare floating-point fields with primitive comparisons; CommonTermsQuery stood out as mixed (three fields compared by bits, two with ==). Public-API 0.0 / -0.0 pairs, first on the 10.6.0 jars and then on main, witnessed every site.
  • An independent reproducer and two executed reviews by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier and an adjudication re-ran the repro.

queries / function value sources and CommonTermsQuery (equals and hashCode contract)
Priority
Low, rank 1027: Six function value sources and CommonTermsQuery's minimum-should-match setters treat 0.0 and -0.0 as equal but hash them differently, so application hash sets, maps and composite queries can keep both, in every release since 4.0.0 (4.2.0 for CommonTermsQuery). Hits and scores stay identical, Lucene's own query cache is not involved, and only a computed negative zero reaches it, so it is contrived.
Impact class
minor
Impact note
Only applications that build one of these objects twice, once with 0.0 and once with -0.0 for the same parameter (the six value-source constructors and CommonTermsQuery's setLowFreqMinimumNumberShouldMatch / setHighFreqMinimumNumberShouldMatch accept -0.0 without validation), and then rely on the two being one object in a hash-based structure are hit, in the default configuration, with -ea and -da, at any size, in every release since 4.0.0 (CommonTermsQuery since 4.2.0): HashSet and HashMap lookups miss and can hold both, the FunctionQuery and FunctionRangeQuery wrappers inherit the mismatch, and a BooleanQuery holding FunctionQuery(ConstValueSource(0f)) is not equal to one holding FunctionQuery(ConstValueSource(-0f)) although its only clauses are equal; hits, counts and scores do not change, and Lucene's own query cache is not involved (FunctionQuery and FunctionRangeQuery are not cacheable, and CommonTermsQuery is rewritten before caching into a BooleanQuery whose int minimum-should-match is 0 for both zeros).
Summary
You build new ConstValueSource(0f) and new ConstValueSource(-0f), or two CommonTermsQuery objects that differ only in setLowFreqMinimumNumberShouldMatch(0f) versus (-0f): equals() says they are equal, because it compares the parameter with ==, under which 0.0 == -0.0. By the Object#hashCode contract, which ValueSource re-declares as abstract and Query's javadoc asks subclasses to implement properly, their hash codes must then be equal, but they differ, because hashCode() hashes Float.floatToIntBits (Double.doubleToRawLongBits for DoubleConstValueSource), and those bits differ for the two zeros. The same holds for DoubleConstValueSource, LinearFloatFunction, ScaleFloatFunction, RangeMapFloatFunction and ReciprocalFloatFunction and for the FunctionQuery and FunctionRangeQuery wrappers that hold them, so hash-based structures treat equal objects as different, while hits and scores stay the same.
