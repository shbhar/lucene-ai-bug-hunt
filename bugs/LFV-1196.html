The postings enum's intoBitSet throws on a dense block when the destination bit set is shorter than the window

On a dense term, the default postings enum's intoBitSet(upTo, bitSet, offset) throws IndexOutOfBoundsException when the bit set ends before upTo, although every matching doc fits, as the contract allows. No Lucene query passes such a window, so only direct callers are hit, in every release since 10.2.0.

The finding in 30 seconds

#

intoBitSet copies a term's matching docs into a bit set. Its contract only asks that the matching docs fit, but for dense postings blocks the reader copies the whole block slice up to upTo at once, and the whole range of that copy is checked against the destination length, set bits or not.

Background in three steps

#
  1. A PostingsEnum walks one term's matching docs. intoBitSet(upTo, bitSet, offset) sets bit doc - offset for each match from docID() up to, not including, upTo, and leaves the enum on the first match at or after upTo.
  2. Its javadoc defines it by that per-doc loop, so only the matches must fit: a bit set shorter than upTo - offset is legal when no match lies past its end (#14142).
  3. The default postings format writes docs in blocks of 256 (128 before 10.4.0). A dense full block is stored as a bit set, and the reader can OR it straight into the destination with FixedBitSet.orRange.

The finding, step by step

#
  1. Index 512 documents with a StringField term t in every other one (docs 0, 2, ..., 510). The default codec stores this full block of 256 docs as a bit set: 512 bits, less than the 768 bits of packing the deltas at one bit more than the 2 they need, which is the writer's test.
  2. Position t's PostingsEnum on doc 0 and call intoBitSet(2, new FixedBitSet(1), 0): copy the matching docs below 2 into a 1-bit set.
  3. You expect bit 0 set and docID() = 2. Only doc 0 is below 2, and intoBitSet must act like setting the docs one at a time, so a short bit set is fine when no match falls past its end.
  4. Instead it throws IndexOutOfBoundsException: Range [1, 1 + 1) out of bounds for length 1, with assertions on and off. The bit-set path copies the block's bits [1, 2) with one FixedBitSet.orRange, which checks the whole range against the 1-bit destination, set bits or not.
  5. Same with a bigger window: intoBitSet(400, new FixedBitSet(399), 0), where all 200 matching docs below 400 fit in 399 bits, throws Range [1, 1 + 399) out of bounds for length 399.

Who is affected

#

Only code that calls intoBitSet itself (public, tagged @lucene.internal) on a default-codec postings enum, with a bit set shorter than the window and upTo inside a dense block. No Lucene query, scorer or collector passes such a window. The call fails loudly; nothing is written to the index and no wrong result is returned.

Mechanism, terms and numbers537 words

DocIdSetIterator#intoBitSet(upTo, bitSet, offset) must behave exactly like the loop for (doc = docID(); doc < upTo; doc = nextDoc()) bitSet.set(doc - offset), so a destination shorter than upTo - offset is fine as long as no matching doc lies past its end. Upstream said so in #14142 and fixed the same failure in BitSetIterator (#14142) and IndexedDISI (#14922).

Since #14133 (10.2.0) the default postings format stores dense full blocks as bit sets, and BlockPostingsEnum#intoBitSet copies the block slice up to upTo with one FixedBitSet.orRange. orRange bound-checks the whole length against the destination whether the bits are set or not, so the call throws although every matching doc would fit. No Lucene query or scorer passes such a window, so only code that calls intoBitSet itself is hit; nothing is written to the index and no wrong result is returned. The read-only Lucene101 and Lucene103 readers in backward-codecs have the same code. The fix is a clamp, as in the sibling classes.

The mechanism (main 5adff78bb168)

#
  1. Writer. A full block is written as a bit set when that is smaller than packing the deltas at one bit more than they need, or as byte 0 for 256 consecutive docs (codecs/lucene104/Lucene104PostingsWriter.java:425-461). In the repro the deltas need 2 bits, packing at 3 bits takes 768 bits, and the 511-doc range takes 8 longs = 512 bits: bit set.
  2. Reader. refillFullBlock selects DeltaEncoding.UNARY for a non-positive bits-per-value byte and sets docBitSetBase = prevDocID + 1 (Lucene104PostingsReader.java:591-624).
  3. BlockPostingsEnum#intoBitSet (:968-1032) first sets the current doc's bit (bitSet.set(doc - offset), :975), then in the UNARY branch (:1001-1029) takes sourceFrom = 0 on a freshly loaded block and doc - docBitSetBase + 1 otherwise (:1003-1010; the repro takes the second case), computes destFrom = docBitSetBase - offset + sourceFrom (:1012) and sourceTo = Math.min(upTo, level0LastDocID + 1) - docBitSetBase (:1015), and calls FixedBitSet.orRange(docBitSet, sourceFrom, bitSet, destFrom, sourceTo - sourceFrom) (:1018). Nothing limits sourceTo to offset + bitSet.length(). Fix site.
  4. FixedBitSet.orRange (util/FixedBitSet.java:477-481) checks the source range (:480), then the destination range with Objects.checkFromIndexSize(destFrom, length, dest.length()) (:481), so it throws before writing anything, set bits or not. In the repro: orRange(docBitSet, 1, bitSet, 1, 1) into a 1-bit set fails at :481.
  5. Not affected: the PACKED branch (:984-1000) sets docs one at a time (bufferIntoBitSet, :1090-1097).
  6. Exact trigger, narrower than in the sibling classes: upTo falls inside a bit-set block (upTo <= level0LastDocID), the destination ends before upTo (offset + bitSet.length() < upTo), and no matching doc lies between the two. A bit-set block always ends on a matching doc, so callers that pass NO_MORE_DOCS (FixedBitSet.or, DocIdSetBuilder) cannot hit it.
  7. Several blocks: when the window spans several bit-set blocks, the earlier blocks' bits are already in the destination when a later orRange throws. With the 128-doc blocks of 10.2.x and 10.3.x, the 399-bit example throws Range [255, 255 + 145) on the second block (executed); the partial result is read from the code.
  8. Same code, read-only formats: Lucene101PostingsReader.java:1010 and Lucene103PostingsReader.java:1010 in lucene/backward-codecs.
Exposure and likelihood210 words
  • Who is hit: code that calls intoBitSet itself on a default-codec postings enum with a destination shorter than upTo - offset and upTo inside a dense block, for example a custom bulk scorer or collector.
  • Not hit: Lucene's own callers. BooleanScorer, DenseConjunctionBulkScorer, ConstantScoreBulkScorer, ReqExclBulkScorer and MaxScoreBulkScorer size the window to the destination, ConjunctionDISI clamps it (search/ConjunctionDISI.java:281-285), and the NO_MORE_DOCS callers cannot hit it (a read audit of the callers at 5adff78bb168).
  • Default vs opt-in: default codec and IndexWriterConfig; the term only has to be dense enough for a full block to be stored as a bit set (every other doc in the repro). Any index size with at least one full block of the term (256 matching docs since 10.4.0, 128 before): the repro has 512 docs.
  • Effect: an IndexOutOfBoundsException with assertions on and off; the search or iteration that made the call fails. Nothing is written to the index and no wrong result is returned, but the destination already holds the current doc's bit (set at :975 before the copy; even the one-block repro leaves bit 0 set) and, when the window spans several blocks, the earlier blocks' bits.
  • How likely: contrived. No report found since 10.2.0 (April 2025; see Prior reports).

Why it looks unintended

#
  • The javadoc says intoBitSet "should behave exactly as" the per-doc loop; its only preconditions are offset <= docID() and a positioned iterator.
  • Upstream calls this call shape legal: #14142 and the test testIntoBitSetBoundChecks ("This call is legal").
  • BitSetIterator, DocBaseBitSetIterator, IndexedDISI (#14922) and ConjunctionDISI clamp the copy to the destination; the postings reader does not.
The full argument246 words
  • Contract. DocIdSetIterator#intoBitSet (search/DocIdSetIterator.java:186-210): "This should behave exactly as if implemented as below, which is the default implementation: for (int doc = docID(); doc < upTo; doc = nextDoc()) { bitSet.set(doc - offset); }". Its only preconditions are offset <= docID() and a positioned iterator; the repro meets both.
  • Upstream's own reading. #14142 (16da44a1bb7, 2025-01-16, by the author of #14133, two days later): "DocIdSetIterator#intoBitSet only requires matching docs to be set into the bit set, so having upTo - offset exceed the length of the dest bit set is legal as long as no bits are set beyond offset + bitSet.length()." Its test BaseDocIdSetTestCase.testIntoBitSetBoundChecks says "This call is legal, since all "set" bits are in the range". On #14922 (IndexedDISI), Adrien Grand (jpountz) described this very mechanism: orRange "OR's all the bits, whether they are set or not. So it's a bug when the source range of bits to OR is greater than the destination range" (PR conversation, 2025-07-12).
  • Siblings clamp. BitSetIterator.java:129, DocBaseBitSetIterator.java:95, IndexedDISI.java:724 and ConjunctionDISI.java:282 all limit the copy to offset + bitSet.length().
  • Why tests miss it. RandomPostingsTester's INTO_BIT_SET option draws upTo = offset + random.nextInt(set1.length()) (RandomPostingsTester.java:1396-1398), so postings tests never pass a window longer than the destination.
  • History. #14069 (2024-12) added intoBitSet; its postings override set docs one at a time. #14133 added the bit-set branch; #14142 fixed BitSetIterator two days later but did not touch the postings reader.
The devil's-advocate check170 words

The strongest case for "intended": intoBitSet is @lucene.internal, every Lucene caller sizes or clamps its window, postings tests only use short windows, and the failure is loud. An independent reviewer from another model family (OpenAI GPT-5.6) rated it not real (high confidence) because it treats calls into @lucene.internal APIs as out of contract and no audited Lucene caller passes such a window. It reproduced the failure, agreed on the root cause and the fix, and noted that "semantically it violates the internal intoBitSet reference-loop contract" and that "if Lucene maintainers choose to enforce correctness of internal contracts independently of public reachability, this remains a reasonable low-impact fix."

Why it fails: the tag warns about API stability; it does not narrow the javadoc's contract, which defines the behaviour by the per-doc loop. Upstream declared this exact call shape legal and fixed it as a bug in two sibling classes. Scope is why it is Low, not why it is intended; a maintainer may still find it too minor to prioritize.

Suggested fix

#

Recommended A: clamp the copy to the destination, then finish doc by doc (recommended)

Clamp the bulk copy to the destination, then finish doc by doc, as BitSetIterator does: OR only the bits that fit and set the remaining matches below upTo one at a time, so a match past the destination behaves exactly as in the per-doc loop (see the trade-offs). +14 lines in each of the three readers; validated.

long destEnd = (long) offset + bitSet.length() - docBitSetBase;
if (destEnd < sourceTo) {
  int fitTo = (int) Math.max(destEnd, sourceFrom);
  if (fitTo > sourceFrom) {
    FixedBitSet.orRange(docBitSet, sourceFrom, bitSet, destFrom, fitTo - sourceFrom);
  }
  for (advance(docBitSetBase + fitTo); doc < upTo; nextDoc()) {
    bitSet.set(doc - offset);
  }
  return;
}

A: clamp the copy to the destination, then finish doc by doc (recommended) (validated by the checks)

#

In the UNARY branch of BlockPostingsEnum#intoBitSet, right after sourceTo is computed, in Lucene104PostingsReader and the same branch of the backward-codecs Lucene101PostingsReader and Lucene103PostingsReader. This is the pattern of BitSetIterator and DocBaseBitSetIterator, and what Adrien Grand (jpountz) proposed on #14922 for IndexedDISI: adjust the range of bits to copy to the destination, then make sure no match lies between the last copied bit and upTo.

long destEnd = (long) offset + bitSet.length() - docBitSetBase;
if (destEnd < sourceTo) {
  int fitTo = (int) Math.max(destEnd, sourceFrom);
  if (fitTo > sourceFrom) {
    FixedBitSet.orRange(docBitSet, sourceFrom, bitSet, destFrom, fitTo - sourceFrom);
  }
  for (advance(docBitSetBase + fitTo); doc < upTo; nextDoc()) {
    bitSet.set(doc - offset);
  }
  return;
}

Trade-offs

  • The single orRange is unchanged whenever the destination covers the window, as for every Lucene caller today; only a short destination takes the per-doc tail. One extra comparison per bit-set block; no benchmark was run.
  • If a matching doc does lie past the destination (an illegal call), the tail behaves exactly like the reference loop: an AssertionError with assertions on; with them off FixedBitSet.set has no bounds check of its own (FixedBitSet.java:295-300), so a doc past length() but inside the last word is set silently and one past it throws ArrayIndexOutOfBoundsException, where stock main throws IndexOutOfBoundsException from orRange (executed probe: intoBitSet(3, new FixedBitSet(1), 0) with doc 2 matching).
  • The repro exercises only the Lucene104 reader; the two backward-codecs hunks are the same change, covered by their postings-format suites only.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, seed DEADBEEF (2026-11-05): the repro fails on stock main with assertions on and off, and passes with the fix, on and off.
  • With the fix, in core: TestLucene104PostingsFormat, TestPostingsUtil, TestDenseConjunctionBulkScorer, TestConjunctionDISI, TestBooleanScorer, TestConstantScoreBulkScorer, TestReqExclBulkScorer, TestMaxScoreBulkScorer, TestTermQuery, TestDocIdSetBuilder and TestFixedBitSet pass (167 tests plus the repro, 2 skipped, 0 failures).
  • In backward-codecs: TestLucene101PostingsFormat, TestLucene101PostingsFormatV0 and TestLucene103PostingsFormat pass (98 tests, 6 skipped, 0 failures). checkGoogleJavaFormat, ecjLintMain and forbiddenApisMain of both modules pass. The suites ran with assertions on (the default); only the repro also ran with them off.
  • Earlier (2026-11-03), the core hunk alone passed independent reviewers' own tests and TestLucene104PostingsFormat.

B: use the per-doc loop for the whole call when the destination is short

#

At the top of intoBitSet: if ((long) offset + bitSet.length() < upTo) { super.intoBitSet(upTo, bitSet, offset); return; }.

Trade-offs

Simplest, but gives up the bulk copy for every such call, including dense blocks that fit. Not run.

C: document a stricter precondition for postings

#

Require upTo - offset <= bitSet.length() for postings enums.

Trade-offs

No code change, but it contradicts #14142, testIntoBitSetBoundChecks and the clamps in the sibling classes. Not recommended.

Downstream note

#

Relevant downstream only to custom bulk scorers or collectors that call intoBitSet on postings with a bit set shorter than the window: clamp upTo to offset + bitSet.length() as ConjunctionDISI does, or size the bit set to the window.

How it was found

#

Semi-formal: a proof-obligation audit of BlockPostingsEnum#intoBitSet against the DocIdSetIterator#intoBitSet contract, branch by branch. The bit-set branch's single orRange does not meet the obligation when the destination is shorter than the window; a one-test JUnit repro on stock main witnessed it.

The method in full112 words
  • Obligation: for every legal call (offset <= docID(), a positioned iterator), the bits set and the final docID() equal those of the per-doc loop for (doc = docID(); doc < upTo; doc = nextDoc()) bitSet.set(doc - offset) (DocIdSetIterator.java:186-210); the loop only needs the matching docs to fit.
  • Finding: the PACKED branch sets docs one at a time and meets it; the UNARY branch ORs [sourceFrom, min(upTo, level0LastDocID + 1)) in one orRange (Lucene104PostingsReader.java:1015-1018), which also needs the unset bits of that range to fit.
  • Witness: a JUnit test on stock main, then an independent reproduction, cross-model reviews, an intended-behaviour review and an adjudication (see Independent checks).

Hits only code that calls the @lucene.internal DocIdSetIterator#intoBitSet itself on a default-codec postings enum with upTo inside a dense, bit-set-encoded postings block and a destination that ends before upTo with no matching doc in between, a window the javadoc and upstream's own test framework call legal; the call then throws IndexOutOfBoundsException with -ea and -da (with 128-doc blocks in 10.2.x and 10.3.x after an earlier block's bits were already ORed in), at any scale and with the default IndexWriterConfig and codec, while no Lucene query, bulk scorer or NO_MORE_DOCS caller passes such a window at 5adff78bb168, nothing is written to the index and no wrong result is returned [exec + read].
Summary
You index 512 documents with a StringField term t in every other one (docs 0, 2, ..., 510), so its first full postings block is stored as a bit set, position t's PostingsEnum on doc 0 and call intoBitSet(400, new FixedBitSet(399), 0); every matching doc below 400 (0, 2, ..., 398) fits in 399 bits, and the javadoc says the call must behave exactly like the loop 'for (doc = docID(); doc < upTo; doc = nextDoc()) bitSet.set(doc - offset)', so you expect bits 0, 2, ..., 398 and docID() 400. Instead it throws IndexOutOfBoundsException 'Range [1, 1 + 399) out of bounds for length 399' from FixedBitSet.orRange, with -ea and -da: the bit-set branch copies the whole slice [current doc + 1, min(upTo, last doc of the block + 1)) with one orRange, which bound-checks the full length against the destination whether the bits are set or not. Upstream declared this call shape legal when it fixed the same failure in BitSetIterator (#14142) and IndexedDISI (#14922), but the postings reader was never changed; no Lucene caller passes such a window, so only direct callers hit it.
