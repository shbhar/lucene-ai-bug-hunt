One I/O error in PrimaryNode.flushAndRefresh leaves replicas on the old NRT point, and the retry reports no changes

In NRT replication, one transient IOException while flushAndRefresh() reads the new files leaves the primary searching the new point but offering replicas the old one, and the retry returns false ("no changes"). In the repro: searching version 3, offered version 1, until the index changes again.

The finding in 30 seconds

#

setCurrentInfos switches the primary to the new point and releases the old point's files first, then does the work that can fail (opening every new file to read its header), and sets the point it hands to replicas last. One exception in between leaves the two out of step, and the retry's "anything new?" check looks at the wrong one.

Background: how a primary publishes an NRT point

#
  1. In lucene-replicator's NRT segment replication (opt-in, experimental) a PrimaryNode owns the IndexWriter. Each flushAndRefresh() opens a new searcher and, if anything changed, publishes it as an NRT point with a version number and returns true.
  2. Publishing builds a CopyState: the point's files with their headers and checksums. Replicas ask for it with getCopyState() and copy the files they lack; getCopyStateVersion() says which version that is.
  3. The primary holds a reference on the published point's files, so the writer does not delete them while replicas copy them. Callers typically notify replicas only when flushAndRefresh() returned true.

The finding, step by step

#
  1. A PrimaryNode on a new index publishes the empty point, version 1. You add 1 document and call flushAndRefresh().
  2. While it opens the new segment's first file (_0.cfe) to read its header, storage throws one transient IOException (think "too many open files"). flushAndRefresh() throws it.
  3. The error is gone and you retry. You expect the retry to publish version 3 to replicas and return true.
  4. Instead it returns false ("no changes"): the primary searches version 3 but getCopyStateVersion() is still 1, so replicas are never told. Asking for the point now throws AssertionError with assertions on, or hands out the old point, whose files may already be deleted (those the new point no longer uses).
  5. Only the next index change plus another flushAndRefresh() heals it (one more document: versions 5 and 5). On a quiet index the last changes can stay off the replicas indefinitely.

Who is affected

#

Users of the opt-in, experimental NRT segment replication, in every release since 6.0.0, with the default config. It takes one transient I/O error other than not-found, EOF or corruption while the new files are read. A busy index heals at its next change and refresh; on a quiet index the last changes stay off the replicas indefinitely.

Mechanism, terms and numbers658 words

In lucene-replicator's NRT segment replication, PrimaryNode.flushAndRefresh() publishes each new NRT point through setCurrentInfos. That method first switches curInfos to the new SegmentInfos, increfs its files and decrefs the previous point's files, and only then serializes the infos (in memory) and opens every new file to read its header, footer and checksum, which can throw. copyState, the point handed to replicas, is assigned last. One IOException in between (any type except EOF, corrupt-index and not-found, which the metadata read turns into null) leaves curInfos at the new point and copyState at the old one, whose own reference was already released. The retry compares the writer's version with curInfos, sees no change and returns false, so replicas are not offered the new point until the index changes and flushAndRefresh() runs again. In that window getCopyState() throws AssertionError with assertions on, or offers the old point, whose files may already be deleted if the new point no longer uses them, so a copy fails with NoSuchFileException. Nothing wrong is served and the primary's index is intact. The order dates from the feature's first commit (LUCENE-5438) and ships in every release from 6.0.0 to 10.6.0; doing the fallible work first and then switching everything together fixes the repro and passes the module's nightly suites.

Step by step, on the repro

#
  1. Publish the empty point. The constructor's setCurrentInfos publishes version 1 (no files).
  2. Add 1 document, refresh. flushAndRefresh() refreshes the searcher to version 3 (PrimaryNode.java:165) and calls setCurrentInfos. It sets curInfos to version 3 and releases version 1 (:290-295).
  3. One read fails. readLocalFileMetaData opens _0.cfe to read its header (Node.java:213). It returns null only for EOFException | CorruptIndexException (:219) and FileNotFoundException | NoSuchFileException (:232); this plain IOException propagates out of flushAndRefresh(). There is no catch or finally between the switch and copyState, so copyState stays at version 1.
  4. The retry. flushAndRefresh() finds nothing new to refresh, and the version check against curInfos (:280) sees 3 == 3 and returns false. getCopyStateVersion() is still 1 (:183-185).
  5. Asking for the point. getCopyState() asserts curInfos == copyState.infos() (:236): with assertions on it throws; with them off it increfs and returns version 1 (no files here; in general, files only the old point used may already be deleted).
  6. Healing. One more addDocument changes the writer's version; the next flushAndRefresh() passes the check and runs a full publish (versions 5 and 5). Nothing else publishes: the private setCurrentInfos is called only by the constructor (:126) and flushAndRefresh() (:166).

When the new point drops the old point's segment the window is worse: in the reproducer's probe (publish 1 document, delete it, add another, fail the read of _1.cfs, retry) the retry returns false with searching 7 and copy state 3; with assertions off getCopyState() offers _0.cfe, _0.si and _0.cfs, all already deleted, and releaseCopyState throws NoSuchFileException: _0.cfe. When the old segment stays in the new point its files keep a reference: a check probe (publish 1 document, add a second, fail the read of _1.cfs, retry, assertions off) gets false with searching 5 and copy state 3, but the offered _0.cfe, _0.si and _0.cfs all still exist and releaseCopyState succeeds.

Exposure and likelihood420 words
  • Who is hit. Applications that use lucene-replicator's NRT segment replication (a PrimaryNode subclass; the package is @lucene.experimental). Every release since 6.0.0, default IndexWriterConfig, codec and merge policy. Reproduced on small indexes; the order does not depend on the index size once the new point has files to read.
  • What it takes. One transient IOException other than EOF / corrupt / not-found while flushAndRefresh() opens or reads the new point's files, for example a FileSystemException "Too many open files" or an EIO. The hunt's single-fault sweep (a NoMergePolicy script) injected one IOException at one representative event of each (operation, file) class inside setCurrentInfos, 72 classes covering 632 events: 57 of the 72 leave the stale state, with assertions on and off; the other 15 hit the constructor's first publish, which throws; with fix A none leaves the stale state. Likelihood: rare; nothing has been reported since 2016. All of it is injected faults on one platform: it shows the behaviour, not how often it happens in the field.
  • What goes wrong. The caller's retry gets a false "no changes". A primary that pushes points only when flushAndRefresh() returns true, as Lucene's own reference test primary does (SimplePrimaryNode.java:344), never tells replicas about the point. A busy index heals at the next change and refresh; for a quiet index (the end of a bulk load, an idle shard) the last changes stay off the replicas indefinitely.
  • In the window. A replica that asks for the current point (a new or restarted replica) is offered the old point. With assertions off, files only the old point used may already be deleted (when the new point dropped its segment), so the copy fails with NoSuchFileException and releaseCopyState throws; that failing release leaks the copy count, which can make close() wait forever under the default remoteCloseTimeoutMs = -1 (a separate bug with its own fix site, publicly reported as #11674). With assertions on every getCopyState() throws AssertionError until the next change and refresh. When the old segments are still in the new point, the stale point is offered with intact files.
  • What does not go wrong. No wrong bytes are served: Lucene file names are write-once, so a deleted name makes the copy fail loudly. The primary's own index, searcher and commits are intact.
  • Impact class: silent wrong results (the wrong result is the false "no changes" and the stale getCopyStateVersion(), not wrong bytes); priority low (opt-in experimental module, rare trigger, heals at the next change and refresh).

Why it looks unintended

#
  • copyState is documented as the "IncRef'd state of the last published NRT point" handed to replicas, and getCopyState() asserts curInfos == copyState.infos(); both break.
  • flushAndRefresh() "Returns true if there were changes"; the retry returns false.
  • Nothing says to discard a primary after an exception, and the core ReferenceManager refresh swaps only after its fallible work succeeded.
The full argument289 words
  • The module defines copyState as the published point. PrimaryNode.java:59-61: "IncRef'd state of the last published NRT point; when a replica comes asking, we give it this as the current NRT point". CopyState.java:26: "Holds incRef'd file level details for one point-in-time segment infos on the primary node". After the failure the copy state holds no reference of its own: the primary's reference for that point was released at :294, so files only it used are deleted.
  • The code asserts the invariant. getCopyState(): assert curInfos == copyState.infos(); (:236).
  • The API promises a change signal. flushAndRefresh() (:155-158): "Flush all index operations to disk and opens a new near-real-time reader. new NRT point, to make the changes visible to searching. Returns true if there were changes."
  • No discard rule. No javadoc, package doc, CHANGES.txt or MIGRATE.md entry says a PrimaryNode must be thrown away after flushAndRefresh() throws; the node stays open and the IndexWriter has no tragic event.
  • The core refresh is failure-atomic. ReferenceManager.doMaybeRefresh swaps only after refreshIfNeeded succeeded and releases the new reference on failure (ReferenceManager.java:167-178). The replica orders part of its cut-over the same way: ReplicaNode.finishNRTCopy reads the new infos (readCommit, ReplicaNode.java:433-434) before its cut-over call (:440) and increfs the new files before it decrefs the old ones ("Must first incRef new NRT files, then decRef old ones", :442-454). The replica's cut-over itself is not failure-atomic: SegmentInfosSearcherManager.setCurrentInfos sets currentInfos (:99) before the fallible reader open (:100, :116).
  • History. The order dates from the class's first commit (2016) and was never discussed; no upstream test injects I/O errors during point publication. Maintainers have accepted robustness fixes in this module (#11822, LUCENE-9967).
The devil's-advocate check191 words

Strongest case for "intended" (the devil's-advocate verifier): NRT replication follows a crash-and-promote failure model. The module's tests crash nodes and flip bits but never inject I/O errors, and the reference test server fails on any unexpected exception, so a primary whose flushAndRefresh() threw is never used again. readLocalFileMetaData's javadoc says it "returns null ... if there are any problems" (Node.java:193-194), and PrimaryNode.java:312 asserts the file exists, so the author assumed this step cannot fail. The module is @lucene.experimental.

Why it fails:

  1. Nothing documents a discard rule, and instead of failing loudly the node answers the retry with a silent false.
  2. The module's own invariants (the copyState comment, the getCopyState assert, the CopyState javadoc) break.
  3. The method declares IOException, and the metadata read does propagate other IOExceptions despite its javadoc; a real filesystem raises them.
  4. The reference server failing on exceptions is a test-failure mechanism, not a recovery contract; a downstream server rethrows such an exception rather than discarding the primary (read, not run).
  5. Experimental lowers the reach, not the correctness bar. The cross-model reviews, the devil's advocate and the adjudication rejected the "intended" reading.

Suggested fix

#

Recommended A. Read everything first, then publish atomically

In setCurrentInfos, do the fallible work first: incref the new point, serialize it and read every file's metadata into a local map (on failure decref it and rethrow). Only then switch curInfos and copyState together and decref the old point. The repro passes, and so does the module's nightly TestNRTReplication (13 tests).

Trade-offs

  • The previous point's files are held until the new metadata was read, which is the point of the fix (the cost was not measured).
  • An exception from the final decRefDeleter(oldInfos) (a failed file delete, or AlreadyClosedException after a tragic event) now propagates after the new point is published: state stays consistent, but the caller sees an exception instead of true. Today that call runs before the metadata read and leaves the stale state, so A is not worse; a maintainer may prefer to catch and log it there (not run).
  • The failure path's catch (Throwable t) drops a secondary exception; addSuppressed would be more idiomatic (cosmetic, not run).

B. Compare the retry against copyState instead of curInfos

#

Change the version check at PrimaryNode.java:280 to copyState.version(), so the retry re-runs the publish and the new point does reach replicas.

Trade-offs

Between the failure and the retry copyState still points at a point whose reference was released (files only it used deleted, yet offered; or AssertionError). Smaller diff, weaker fix. Not run; not recommended.

C. Treat a failed publish as fatal

#

Close or mark the PrimaryNode failed when setCurrentInfos throws, like IndexWriter's tragic event, so callers cannot continue with a silent false.

Trade-offs

Matches the crash-and-promote model, but turns one transient IOException (for example a momentary file-handle shortage) into a primary failover. Not run; not recommended.

Downstream note

#

Downstream, the open-source nrtsearch server uses this API the same way: it notifies replicas only when flushAndRefresh() returns true, and its reference manager rethrows a refresh exception rather than discarding the primary (read, not run; its outer caller was not checked).

How it was found

#

A review of failure paths asked what one exception in setCurrentInfos leaves behind, and a probe on the stock jars showed it. A single-fault sweep then injected one IOException per file-event class inside the method: 57 of its 72 classes leave the stale state (15 hit the constructor), none with the fix. An independent reproducer's test became the repro.

The method in full196 words
  • Method (non-formal first signal). A failure-path review read PrimaryNode.setCurrentInfos with a failure-atomicity question and ran a probe on the stock main jars: one injected read error on a new .liv file, then searching version 6 against copy state version 3 and a getCopyState listing an already deleted file.
  • Mapping (semi-formal). The finder reduced it to a JUnit and ran a bounded-exhaustive single-fault enumeration on the real jar: one IOException at every Directory/IndexInput event inside setCurrentInfos, one representative per (kind, file) class, five checks (copy state version equals searching version, offered files exist, release does not throw, close returns, no leaked files). With a NoMergePolicy script all 72 classes (covering 632 events) fail a check with assertions on and off: 57 leave the stale state, and the 15 that hit the constructor's first publish only leave unreferenced files; with the fix 0 fail the first four checks (the 15 leftover-file cases remain).
  • Masking. With TieredMergePolicy in tiny test indexes a delete-reclaiming merge often gives the retry a new version and hides the defect; the repro adds one document and deletes nothing.
  • Reduction. The independent reproducer's one-test JUnit, trimmed to the minimum, is the repro.

Finding record

LFV-1024, snapshot of 2026-11-10

Registry title
NRT PrimaryNode: one I/O error during flushAndRefresh leaves the new point unpublished to replicas, and the retry reports no changes
Area
replicator / NRT segment replication (PrimaryNode.flushAndRefresh, setCurrentInfos: NRT point publication)
Priority
Low, rank 987: After one transient I/O error in flushAndRefresh, experimental NRT replication stops offering the new point to every replica until the index changes again, which matches the failure-then-stale profile of LFV-312.
Impact class
silent wrong results
Impact note
Applications that use lucene-replicator's NRT segment replication (a PrimaryNode subclass; opt-in and @lucene.experimental), in every release since 6.0.0, with the default IndexWriterConfig and at any index size, are hit when one transient I/O error other than file-not-found, EOF or corruption (for example too many open files) occurs while flushAndRefresh opens the new point's files to read their headers: the retry returns false ('no changes') and replicas are not offered the new point until the next indexing change or completed merge, which for a quiet index can be indefinitely; in that window a replica that asks for the current point is offered the previous one, whose files the primary may already have deleted (with -da the copy then fails with NoSuchFileException; with -ea getCopyState throws AssertionError).
Summary
You run Lucene's NRT segment replication, index a document and call PrimaryNode.flushAndRefresh; it throws because opening one of the new files hits a transient I/O error, and once the error is gone you call flushAndRefresh again. You expect the retry to publish the new point to replicas, or the failed call to have left the previous point fully in place. Instead the failed call had already switched the primary's current point and released the previous point's files, but not the copy state that replicas are given, so the retry returns false ('no changes'), getCopyStateVersion() stays behind getCurrentSearchingVersion(), and replicas are not offered the new point until the index changes again.
