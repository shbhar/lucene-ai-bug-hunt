A point range that covers every indexed point also matches documents without points on a MultiReader (10.3.0 and later)

Since 10.3.0, a point range covering every indexed point is rewritten to "has the field". On a MultiReader where one index stores the field without points, that also matches its documents: 2 hits instead of 1 in the repro, 0 instead of 1 under a NOT clause.

The finding in 30 seconds

#

A shortcut added in 10.3.0 assumes that a field is stored the same way everywhere in the reader. That holds inside one healthy index created by Lucene 9 or later, but not across a MultiReader of separately built indexes.

Background: points, doc values and MultiReader

#
  1. A numeric field can be stored as points (a BKD tree, which range queries use) and as doc values (per-document values for sorting and faceting). LongField writes both.
  2. Inside one index created by Lucene 9 or later, Lucene requires every document to use the same structures for a field (LUCENE-9334). So in one index, "has a doc value for p" means "has a point for p".
  3. A MultiReader searches several separately built indexes as one. Nothing makes their schemas agree.

The finding, step by step

#
  1. Build two indexes with default settings. Index 1: one document with only a doc value p = 5000, no point. Index 2: one document with LongField p = 100 (a point plus a doc value).
  2. Open both in one MultiReader and count LongPoint.newRangeQuery("p", 0, 1000). You expect 1: only index 2's document has a point, and 100 is in range. Each index alone gives 0 + 1, and 10.2.2 gives 1.
  3. Since 10.3.0 the query first looks at the reader-wide point range. That range skips index 1 (no points), so it is [100, 100], inside [0, 1000]. The query is rewritten to FieldExistsQuery("p"): any document with norms, a vector or doc values for p.
  4. The safety check asks each index only whether p has doc values, norms or vectors, never whether it has points. Index 1 has a doc value, so its document matches: the count is 2, although 5000 is outside the range.
  5. Under a NOT clause it flips: +*:* -p:[0 TO 1000] returns 0 instead of 1. No error; every point range factory tried is affected.

Who is affected

#

Applications on 10.3.0-10.6.0 or main that search one MultiReader over separately built indexes where a field has points plus doc values, norms or a vector in one index (as LongField writes) and only doc values, text, a keyword or a vector in another, with a range covering every indexed point. Default settings; every point range factory tried. A single index created by Lucene 9 or later reaches it only through another defect that lets in documents with and without the field's points (such as a deleteAll() that overlaps addIndexes); an index first created by Lucene 8 can, when Lucene 9 wrote its documents with and without points for the field into separate segments (run on main).

Mechanism, terms and numbers579 words

Since 10.3.0 (#14609), PointRangeQuery.rewrite checks whether the query range contains every indexed point of the whole reader and, if not every document has a point, replaces the query with FieldExistsQuery(field) (PointRangeQuery.java:544-572 at e1faeba08bde). The reader-wide bounds skip leaves without points (PointValues.java:150-151), and the check that should keep the rewrite safe, canRewriteToFieldExistsQuery (:578-592), refuses a leaf only when the field has no doc values, no norms and no vectors there; it never asks whether the leaf has points. On a MultiReader over separately built indexes, where one index stores the field without points (doc values only, text, a keyword or a vector), the rewritten query therefore matches every document of that index that has norms, a vector or doc values for the field, whatever its value, and under MUST_NOT it drops them. The repro counts 2 instead of 1; 10.2.2 returns 1. A single index created by Lucene 9 or later reaches it only through another defect that lets in documents with and without the field's points, such as a deleteAll() that overlaps addIndexes.

Terms

#
  • Points and doc values: two ways to store a numeric field. Range queries such as LongPoint.newRangeQuery read points; FieldExistsQuery reads norms, vectors or doc values. LongField writes a point and a SORTED_NUMERIC doc value.
  • LUCENE-9334: "A field across all documents within an index must be indexed with the same index options and data-structures" (lucene/CHANGES.txt:4771-4775). IndexWriter enforces it per index.
  • MultiReader: "A CompositeReader which reads multiple indexes, appending their content" (MultiReader.java:22-25). Each sub-index becomes one or more leaves; there is no schema check across them.

The bug (e1faeba08bde, lucene/core/src/java/org/apache/lucene/)

#
  1. PointRangeQuery.rewrite takes the reader-wide bounds, PointValues.getMinPackedValue(reader, getField()) and getMaxPackedValue (search/PointRangeQuery.java:552-553). Their javadoc: "Leaves that do not have points for the given field are ignored." (index/PointValues.java:150-151, :185-186). In the repro: [100, 100].
  2. relate gives CELL_INSIDE_QUERY (:560). canRewriteToMatchAllQuery compares reader.maxDoc() with the point doc count (:574-576): 2 vs 1, no.
  3. canRewriteToFieldExistsQuery (:578-592) returns false for a leaf only when info.getDocValuesType() == DocValuesType.NONE && !info.hasNorms() && info.getVectorDimension() == 0 (:582-588). Index 1's leaf has NUMERIC doc values, so it passes; getPointDimensionCount() is never read. The query becomes new FieldExistsQuery(field) (:563-564).
  4. FieldExistsQuery matches documents with a vector field "or a field that indexes norms or doc values" (search/FieldExistsQuery.java:38-41), per leaf through norms, else vectors, else doc values (:170-219). Index 1's document has a doc value, so it matches.
  5. The premise, in FieldExistsQuery's own rewrite: "This optimization is possible due to LUCENE-9334 enforcing a field to always use the same data structures (all or nothing)." (search/FieldExistsQuery.java:143-144). True per index, not across separately built indexes.

Variants (executed reach probe)

#
  • When every document of every leaf has the field (FieldExistsQuery.java:116-163; for example the probe's one-document index 1 with a same-named KeywordField), FieldExistsQuery rewrites further to MatchAllDocsQuery; under MUST_NOT the clause becomes MatchNoDocsQuery.
  • A range that only partly overlaps the indexed points is not rewritten (CELL_CROSSES_QUERY), and one that excludes them all becomes MatchNoDocsQuery (CELL_OUTSIDE_QUERY, PointRangeQuery.java:569-570); both stay correct.
  • If the point-bearing index has points only (LongPoint without doc values, norms or vectors), the check refuses that leaf and the result is correct.
  • Before #14609, PointRangeQuery did not override rewrite(); every leaf was matched through its own points, so a leaf without points matched nothing.

Why it looks unintended

#
  • LongPoint.newRangeQuery returns "a query matching documents within this range"; MultiReader reads multiple indexes with no schema precondition; 10.2.2 is correct.
  • The shortcut's premise, LUCENE-9334, is a per-index rule ("within an index"), and #14609 scoped the rewrite to "all docs in index".
  • Maintainers fixed the same kind of per-index assumption leaking across MultiReader leaves as incorrect results (#14399, fixed in 10.6.0).
The full argument292 words
  • Contracts. LongPoint.newRangeQuery: "@return a query matching documents within this range." (LongPoint.java:212). PointRangeQuery: "Abstract class for range queries against single or multidimensional points" (PointRangeQuery.java:41). MultiReader: "A CompositeReader which reads multiple indexes, appending their content. It can be used to create a view on several sub-readers (like DirectoryReader) and execute searches on it." (MultiReader.java:22-25), no schema precondition.
  • A rewrite must not change results. The un-rewritten query is correct on every leaf; 10.2.2 and 9.12.3 return the right count on the same MultiReader.
  • Scoped to one index by its authors. PR #14609: "handle cases where the query either fully contains or fully excludes all documents within the shard". CHANGES 10.3.0: "rewriting to MatchAllDocsQuery/FieldExistsQuery/MatchNoDocsQuery if all docs in index are contained or excluded" (CHANGES.txt:1681-1682). The review's code comments were about reusing relate(), an early return when a dimension is neither inside nor outside, and null min/max, plus the javadoc tag order and a request for a CHANGES entry; none of them mentions composite readers.
  • Tests. TestPointQueries.testRangeQueryOptimizesRewrites (TestPointQueries.java:2473) uses one consistent index; no upstream test builds a MultiReader with a point-less leaf.
  • Precedent. #14399 (jpountz): "While IndexWriter enforces that the whole index has the same index sort, it is possible to create a MultiReader across several indexes which have different index sorts, so this cache is incorrect." Fixed by #16434: "This fixes incorrect results when searching a MultiReader that combines indexes with different index sorts" (CHANGES.txt:763-765). In the #15083 review jpountz wrote "MultiReader allows mixing segments that have a skip index on the field and segments that don't", and DocValuesSkipper.globalMinValue returns Long.MIN_VALUE when a leaf has the field but no skipper (DocValuesSkipper.java:145-160): the guard this check lacks.
The devil's-advocate check177 words

The strongest case for "intended" (built by an intended-behaviour checker): the rewrite builds on LUCENE-9334, which Lucene relies on for several optimizations; the two indexes conflict on field p, and FieldInfos.getMergedFieldInfos throws on this exact reader ("cannot change field \"p\" from doc values type=NUMERIC to inconsistent doc values type=SORTED_NUMERIC"); PointRangeQuery is @lucene.experimental (PointRangeQuery.java:52); so a mixed-schema MultiReader could be called unsupported.

Why it fails: LUCENE-9334 is documented per index. #14609 combines a reader-wide statistic (point bounds that skip point-less leaves) with a per-leaf FieldExistsQuery that also matches point-less leaves, which stretches the per-index rule across index boundaries. MultiReader documents no schema precondition and getMergedFieldInfos documents no exception (its throw is a separate bug). @lucene.experimental marks an unstable API, not wrong results, and the factories that return the query are not experimental. The extra document's value, 5000, matches [0, 1000] under no reading; with index 1 written as SortedNumericDocValuesField the indexes differ only in the missing points and it still fails. Maintainers fixed the same kind of cross-leaf assumption as incorrect results (#14399 / #16434).

Suggested fix

#

Recommended Also refuse a leaf that has the field without points (validated)

In canRewriteToFieldExistsQuery, also refuse a leaf whose field has no points (info.getPointDimensionCount() == 0). A mixed reader then runs the normal point query; consistent indexes keep the shortcut. Validated with gradle: the repro passes, and so do 275 search and document test classes.

       if (info != null
-          && info.getDocValuesType() == DocValuesType.NONE
-          && !info.hasNorms()
-          && info.getVectorDimension() == 0) {
+          && (info.getPointDimensionCount() == 0
+              || (info.getDocValuesType() == DocValuesType.NONE
+                  && !info.hasNorms()
+                  && info.getVectorDimension() == 0))) {
         // Can't use a FieldExistsQuery on this segment, so return false
         return false;
       }

Two options; the first was built and validated, the second is simpler but gives up more of the optimization. The choice is the maintainers'.

Also refuse a leaf that has the field without points (validated) (recommended)

One condition in canRewriteToFieldExistsQuery (PointRangeQuery.java:582-585). A leaf with the field but no points makes rewrite fall back to super.rewrite(searcher), the normal per-leaf point query; a leaf without the field (info == null) still allows the rewrite.

Trade-offs

  • Keeps the optimization on every consistent layout tested: a rewrite differential over consistent layouts (points only, points plus doc values or norms, sparse, multi-valued, 2-D, absent-field segments, deletions) ran 1,250,932 checks with 0 failures and the same rewrite-kind histogram as stock (FieldExistsQuery 4,696, MatchAllDocsQuery 2,370).
  • On a mixed composite the shortcut is lost for that query, which then runs as before #14609.
  • It does not cover a single 8.x-created segment whose documents are not all-or-nothing; that is a different root and needs its own fix. With such documents in separate segments the fix does apply (count 2 -> 1).

  • Earlier checks: the composite decomposition harnesses go from 600 of 17,366 and 69 of 2,534 mismatching query/composite checks to 0, the factory reach probe from 54 silently wrong cases to 0 (with the fix its summary reads ok=63 bad=8: all 8 are loud IllegalStateExceptions that 10.2.2 throws too), and a Z3 model of the rewrite decision (3 leaves x 2 documents, 11 queries) finds a counterexample with the shipped condition on MultiReaders and none with the fix or on a single strict index.

Drop only the FieldExistsQuery branch (not validated)

#

Keep the MatchAllDocsQuery and MatchNoDocsQuery rewrites, which use reader-wide counts and are sound on composites, and fall back to super.rewrite(searcher) where the FieldExistsQuery branch is. The weight's per-leaf shortcuts stay (for example count returns a leaf's point doc count when its own bounds are inside the range, PointRangeQuery.java:353-357).

Trade-offs

Simplest to reason about, but it also gives up the FieldExistsQuery rewrite on consistent indexes, which TestPointQueries.testRangeQueryOptimizesRewrites asserts and #14609 wanted ("rewriting at the shard level enables other optimizations downstream").

Downstream note

#

Downstream engines that combine indexes with different schemas for one field and filter visibility with a full-coverage point range would show (or, under an exclusion, hide) every document of the point-less index that has norms, a vector or doc values for the field, whatever its value.

How it was found

#

While reviewing 10.x features, reading the 10.3.0 rewrite (#14609) raised the question whether a point range on a composite reader still matches exactly the documents with an in-range point. An executed probe showed 2 hits instead of 1 on main, 10.6.0 and 10.3.0, with 10.2.2 correct. It was reduced to one test and checked with a Z3 model.

The method in full172 words

Method: non-formal (the first signal came from code reading and an executed probe; the Z3 model came later).

  • Lead. A review of features new in 10.x read the #14609 rewrite with the property "on every composite reader a point range query matches exactly the documents that have a point in range, leaf by leaf".
  • Probe. Public-API probes on the stock main jar: 6 hits instead of 3 in a larger probe and a count of 2 instead of 1 in the minimal one, on main, 10.6.0 and 10.3.0; 10.2.2 correct.
  • Generalisation. A composite-reader count-decomposition oracle (a MultiReader count must equal the sum of the per-index counts) found that every mixed-schema mismatch among the layouts it tried has this root.
  • Reduction and model. One JUnit test; a Z3 model of the rewrite decision (3 leaves x 2 documents, 11 queries) finds a counterexample with the shipped condition on MultiReaders, none with the fix or on a single strict index, and shows that positive ranges can only over-match (lost hits need MUST_NOT).

LFV-1109, snapshot of 2026-11-09

Registry title
PointRangeQuery rewrites a range that covers every indexed point to FieldExistsQuery without checking that each leaf has points, so on a MultiReader whose other index stores the field without points it also matches (or, under MUST_NOT, drops) documents that have no point
Area
core / search: PointRangeQuery.rewrite (GITHUB#14609 full-coverage rewrite to FieldExistsQuery, new in 10.3.0) on composite readers
Priority
Medium, rank 92: In 10.3.0 through 10.6.0 with default settings, the core point range queries silently match (or under MUST_NOT drop) documents that have no point when the range covers every indexed point and a composite reader spans separately built indexes, one of which stores the field without points. That mixed-schema layout is rare, so it is mid-Medium.
Impact class
silent wrong results
Impact note
Applications on 10.3.0 through 10.6.0 or main that search one MultiReader (or another composite reader) over separately built indexes in which a field has points plus doc values, norms or a vector in one index (as LongField writes) but no points in another (only doc values, a same-named KeywordField or TextField, or a vector field), with the default IndexWriterConfig, codec and IndexSearcher and at ordinary scale: every point range query on that field whose range covers all indexed points (LongPoint, IntPoint, FloatPoint, DoublePoint, InetAddressPoint and BinaryPoint.newRangeQuery, LatLonPoint.newBoxQuery (tested with a box that does not cross the dateline), and the Long/Int/Float/DoubleField.newRangeQuery factories through IndexOrDocValuesQuery) silently also matches every document of the point-less index that has norms, a vector or doc values for the field, whatever its value, and silently drops those documents under MUST_NOT; the same range used as the filter of a KnnFloatVectorQuery lets those documents into the kNN hits, used as the child query of a ToParentBlockJoinQuery it returns their parents (with every ScoreMode), and a QueryBitSetProducer over it caches the wrong bitset for the point-less index's segment and returns it again when that segment is later reached through the index's own reader; a single index created by Lucene 9 or later reaches it only when IndexWriter has let in documents that have the field without its points, which its per-field consistency check should prevent, for example since 10.5.0 through LFV-118's skipped schema check, which can accept such a document into the same in-memory segment (executed: LongPoint and LongField.newRangeQuery("f", 0, 100) count 3 instead of 2 on main, 10.5.0 and 10.6.0, while 10.4.0 rejects that document), or through a deleteAll() that overlaps addIndexes (LFV-1074), which lets a later document give a field that addIndexes brought in a schema without points (executed with -da, on main also with -ea: LongPoint.newRangeQuery("f", 0, 100) counts 2 instead of 1 on main, 10.6.0, 10.5.0, 10.4.0 and 10.3.0); an index first created by Lucene 8 can reach it when Lucene 9 wrote its documents with and without points for the field into separate segments (executed on main); nothing throws and no index is changed.
Summary
You open a MultiReader over two separately built indexes, one whose document has field p only as a doc value (5000, no point) and one whose document has LongField p=100, and count LongPoint.newRangeQuery("p", 0, 1000); you expect 1, which is what each index gives on its own (0 + 1) and what 10.2.2 returns. You get 2 with no error: since 10.3.0 (#14609) PointRangeQuery.rewrite sees that the reader-wide point range [100, 100] lies inside the query and, because every leaf has doc values, norms or vectors for p, replaces the query with FieldExistsQuery(p), which also matches the document that has no point. Under a MUST_NOT clause the same rewrite drops that document instead.
