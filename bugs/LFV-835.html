PayloadScoreQuery scores a payload of -0.0 as -0.0, so the top-1 hit is not the head of the top-2

The finding in 30 seconds

#

A payload of -0.0 slips through PayloadScoreQuery's negative-score clamp, and Lucene's hit collector then ranks the two zeros inconsistently.

Payload scores and the two zeros of Java

#
  1. A payload is a few bytes stored with a token. PayloadScoreQuery decodes each matching token's payload to a float with a PayloadDecoder and folds them into one score with a PayloadFunction (Min, Max, Sum, Average or your own).
  2. Java floats have two zeros, +0.0 and -0.0. Ordinary comparisons treat them as equal: -0.0 == 0.0 and -0.0 >= 0 are true, -0.0 < 0 is false.
  3. Sign-aware comparisons do not: Float.compare(-0f, 0f) is -1, and the sortable bits that Lucene's hit heap stores put -0.0 just below +0.0.
  4. A float payload can be -0.0: FloatEncoder stores Float.parseFloat of the token text, and Float.parseFloat("-0.0") is -0.0.

The finding, step by step

#
  1. Index two documents with one token each: doc 0 with the float payload -0.0 (the 4 bytes FloatEncoder writes for the text -0.0), doc 1 with 0.0. Search PayloadScoreQuery(SpanTermQuery, MaxPayloadFunction, a decoder that reads the float, false) with a plain IndexSearcher.
  2. You expect both to score 0, because a negative payload score maps to 0 (LUCENE-7996), and to tie in doc-id order: search(q, 1) = [doc 0] and search(q, 2) = [doc 0, doc 1].
  3. Instead doc 0 scores -0.0. The clamp returns 0 only when score >= 0 is false, and in Java -0.0 >= 0 is true. A payload of -1.0 is clamped to +0.0 as intended; explain reports -0.0 too.
  4. So search(q, 1) = [doc 0] but search(q, 2) = [doc 1 (0.0), doc 0 (-0.0)], assertions on or off. The collector's score <= topScore test sees two equal zeros and keeps doc 0, while its heap sorts -0.0 below 0.0.
  5. It takes a decoder that reads IEEE floats (the stock FLOAT_DECODER cannot) and a payload function that keeps the -0.0: a lone -0.0 payload under MaxPayloadFunction or MinPayloadFunction (Min also next to +0.0 or positive payloads), a custom function, or, in a corner case, AveragePayloadFunction. Only zero-scored hits move; matches, counts and positive scores are unchanged.

Who is affected

#

Applications that score with PayloadScoreQuery, a decoder that reads IEEE floats (such as PayloadHelper.decodeFloat; the stock FLOAT_DECODER cannot) and a payload of exactly -0.0 that the payload function keeps (a lone -0.0 under Max or Min, or a custom function). Only zero-scored hits move. Tests on Lucene's test framework can fail with assertions on.

Mechanism, terms and numbers678 words

LUCENE-7996 (8.0.0) forbids negative scores, and PayloadScoreQuery enforces it itself: getPayloadScore returns 0 unless score >= 0, and explain truncates only value < 0. In Java -0.0 >= 0 is true, so a payload score of exactly -0.0 is returned and explained as -0.0. It arises when the decoder reads IEEE floats, such as PayloadHelper.decodeFloat, the inverse of FloatEncoder, and the payload function keeps a -0.0: a lone -0.0 payload under MaxPayloadFunction or MinPayloadFunction (which take the first payload as is; Min also keeps it next to +0.0 or positive payloads, Max loses it to them), or a custom PayloadFunction. The stock FLOAT_DECODER reads one byte and cannot produce it, and Sum and Average turn a lone -0.0 into +0.0. Lucene's test framework rejects that score (Float.compare(score, 0f) >= 0), and since 10.2.0 the hit collector disagrees with itself about it: its competitiveness test score <= topScore treats -0.0 and +0.0 as equal while its heap orders -0.0 below +0.0. With doc 0 = -0.0 and doc 1 = +0.0, search(q, 1) returns doc 0 but search(q, 2) returns doc 1 first. Only hits whose correct score is 0 are affected. Every release from 8.0.0 to 10.6.0 has it; a two-line fix makes the clamp sign-aware.

The clamp

#

LUCENE-7996: "Queries are now required to produce positive scores." (lucene/CHANGES.txt:6636); MIGRATE: "Scorers are no longer allowed to produce negative scores." (lucene/MIGRATE.md:1368-1372). The follow-up commit "LUCENE-7996: PayloadScoreQuery must produce positive scores." added:

  • getPayloadScore (PayloadScoreQuery.java:258-265): float score = function.docScore(...); if (score >= 0 == false) { return 0; } else { return score; }.
  • getPayloadExplanation (:270): the "truncated score" branch only if (expl.getValue().floatValue() < 0), so explain reports -0.0 too.
  • With includeSpanScore the score is getSpanScore() * getPayloadScore() (:291), and a positive span score times -0.0 is still -0.0.

Where -0.0 comes from

#

Each payload is decoded (:226) and folded into an accumulator that starts at 0 for every document (:218-221, :227-235). MaxPayloadFunction and MinPayloadFunction return the first payload as is and Math.max/Math.min afterwards (MaxPayloadFunction.java:34-37, MinPayloadFunction.java:31-34), so a lone -0.0 survives, and Math.min keeps -0.0 next to +0.0 and positive payloads (Min over [2.0, -0.0, 3.5] gives -0.0); Math.max(-0f, 0f) is +0.0, so under Max a -0.0 survives only if no payload is +0.0 or positive (payloads [-0.0, 0.0]: Min -0.0, Max +0.0). SumPayloadFunction adds (SumPayloadFunction.java:35) and 0 + -0.0 is +0.0, so Sum and Average lose the sign of a lone -0.0; Average divides by the payload count, so in a corner case a tiny negative sum rounds to -0.0 (payloads [-1.4E-45, 0.0]). A custom PayloadFunction can return -0.0 directly.

The decoder must read the IEEE float: PayloadHelper.decodeFloat (PayloadHelper.java:60-61), the inverse of encodeFloat, which FloatEncoder uses (FloatEncoder.java:31-32). The stock PayloadDecoder.FLOAT_DECODER returns the payload's first byte (PayloadDecoder.java:29): for -0.0's bytes 80 00 00 00 that is -128, which the clamp maps to 0.

The collector

#

TopScoreDocCollector rejects a hit when score <= topScore (TopScoreDocCollector.java:113), reasoning that "a document with equal score to pqTop.score cannot compete since HitQueue favors documents with lower doc Ids" (:122-124); 0.0f <= -0.0f is true. Its heap stores NumericUtils.floatToSortableInt(score) (DocScoreEncoder.java:31-33), the order of Float.compare; HitQueue, the heap in 10.2.x, uses Float.compare too (HitQueue.java:76-82).

  • k = 1: doc 0 (-0.0) takes the single slot, topScore becomes -0.0, and doc 1 (0.0) is rejected by 0.0 <= -0.0. Result [doc 0].
  • k = 2: both documents get a slot, and the heap sorts doc 1 (0.0) above doc 0 (-0.0). Result [doc 1, doc 0]. No pruning is involved: the collector sets a minimum competitive score only after more than 1,000 hits (IndexSearcher.java:100, TopScoreDocCollector.java:155), and here there are two.

Lucene's test framework asserts Float.compare(score, 0f) >= 0 (AssertingScorer.java:131), so searches through newSearcher that collect such a score throw AssertionError: -0.0 with assertions on (since 10.3.0).

Exposure and likelihood379 words
  • Trigger. A payload that decodes to exactly -0.0: the token text -0.0 or -0 in a delimited float payload field, a tiny negative weight such as -1e-50 (which Float.parseFloat rounds to -0.0f), or a pipeline that writes a computed 0 * negative weight with Float.toString (-0.0). Then a payload function that keeps it (a lone -0.0 under MaxPayloadFunction or MinPayloadFunction; Min also next to +0.0 or positive payloads, Max not; a custom function; in a corner case AveragePayloadFunction), with includeSpanScore true or false, and a decoder that reads the IEEE float. No special setup: default IndexWriterConfig and a plain IndexSearcher (the tests ran with the test framework's randomized codec and directory); payload scoring itself is an explicit choice (PayloadFunction is @lucene.experimental).
  • Effect. Only among hits whose correct score is 0: their score and explanation carry a minus sign, and since 10.2.0 their order depends on k (search(q, 1) is not the head of search(q, 2)). So offset paging (each page re-runs the search with a larger k and skips the earlier hits) can show the -0.0 hit on several pages while other zero-scored hits are never shown: with page size 1, payloads [-0.0], [0.0], [0.0] give doc 0 on all three pages (executed, assertions off). searchAfter paging returned each hit once in the four small shapes tried; for the FunctionScoreQuery sibling of this bug, random multi-segment indexes also showed it skipping a -0.0 hit, which was not tried here.
  • Not affected: which documents match, count(), totalHits, every positively scored hit, the index. With assertions off Lucene throws nothing.
  • Test suites that use newSearcher can get AssertionError: -0.0 with assertions on, since 10.3.0, in tests that collect such a score.
  • Downstream (read, not run): Apache Solr's {!payload_score} parser offers func=min|max|average|sum and decodes float payload fields with PayloadHelper.decodeFloat, so the decoder this needs ships by default there, and a lone term|-0.0 value with func=max or func=min appears to reach the same -0.0 score; not reproduced in Solr.
  • How likely: rare. It needs an exact -0.0 payload that survives the payload function (with several payloads, Max loses it to any +0.0 or positive payload), and then a ranking that depends on the order of zero-scored hits; the symptom is easy to miss.

Why it looks unintended

#
  • LUCENE-7996 forbids negative scores; this clamp's commit is titled "PayloadScoreQuery must produce positive scores", yet it maps -1.0 to 0 and not -0.0.
  • The same LUCENE-7996 work is sign-aware elsewhere: AssertingScorer asserts Float.compare(score, 0f) >= 0; BoostQuery rejects -0f.
  • #16139 (10.6.0) mapped another -0.0 score to +0.0, and top-1 disagreeing with top-2 is wrong either way.
The full argument189 words
  • The rule is documented: lucene/CHANGES.txt:6636, lucene/MIGRATE.md:1368-1372 ("Scorers are no longer allowed to produce negative scores"). The clamp's commit 187849f9b67 is titled "LUCENE-7996: PayloadScoreQuery must produce positive scores."
  • The class breaks its own rule: a payload of -1.0 scores +0.0, -0.0 scores -0.0, and explain has a "truncated score" branch for negatives that -0.0 skips (PayloadScoreQuery.java:270-273).
  • Same day, sign-aware: a8a63464e7d (LUCENE-7996, same author) added AssertingScorer's assert Float.compare(score, 0f) >= 0 (AssertingScorer.java:131) and BoostQuery's Float.compare(boost, 0f) < 0 (BoostQuery.java:40), with a test that requires new BoostQuery(q, -0f) to throw (TestBoostQuery.java:35-36).
  • Precedent: #16137 (open) reports a score from IBSimilarity/DistributionSPL that trips the test framework; a commenter found that it is -0.0. Its fix #16139 (merged 2026-09-10, CHANGES under 10.6.0) uses Math.max(0.0, ...), which maps -0.0 to +0.0.
  • The ranking is wrong under any reading: a top-1 hit that the top-2 ranks second contradicts the collector's own comment at TopScoreDocCollector.java:122-124.
  • Not misuse: a custom PayloadDecoder is the documented extension point, and encodeFloat/decodeFloat is the documented pair. No upstream payload test uses a negative payload.
The devil's-advocate check175 words

The strongest case for "intended": -0.0 is numerically zero and not < 0; the Scorable#score and PayloadScoreQuery javadocs state no sign rule; PayloadFunction is @lucene.experimental; AssertingScorable and AssertingSimilarity assert only score >= 0, which -0.0 passes; TopScoreDocCollector's javadoc names only NaN and negative infinity as invalid scores; the stock decoder cannot produce it; and the 19 comments of LUCENE-7996 (#9044) never mention signed zero.

How far it goes: for the score itself it has some weight, since MIGRATE.md says only "negative" and reading the rule as "no -0.0" is an inference. The inference is supported by the sign-aware checks the clamp's author added the same day (AssertingScorer, the BoostQuery(-0f) test), by the class clamping -1.0 but not -0.0, and by upstream treating a -0.0 score as a contract break in #16137/#16139; the trigger uses only public extension points. For the ranking it fails outright: the top-k result is inconsistent whatever -0.0 means. Verifiers and the adjudication rejected the intended-behaviour case; the cross-model review and a verifier rated it weak.

Suggested fix

#

Recommended Make the clamp and the explanation sign-aware (two lines, validated)

Make the clamp sign-aware: score > 0 == false in getPayloadScore and Float.compare(value, 0f) < 0 in getPayloadExplanation (two lines). -0.0 then scores +0.0; NaN still maps to 0. It passes the repro, the payload tests and the whole queries module (513 tests).

// PayloadScoreQuery.PayloadSpanScorer.getPayloadScore()
if (score > 0 == false) { // also maps -0.0 (and NaN, negatives) to +0
// PayloadScoreQuery.PayloadSpanScorer.getPayloadExplanation()
if (Float.compare(expl.getValue().floatValue(), 0f) < 0) { // includes -0.0

Make the clamp and the explanation sign-aware (two lines, validated) (recommended)

#

The change is +2/-2 lines in PayloadScoreQuery.java. A payload score of -0.0 now takes the existing return 0 path, and explain its existing "truncated score" branch; Float.compare orders NaN above 0, so NaN keeps its own branches. With includeSpanScore, spanScore * +0.0 is +0.0. Every other value is unchanged.

// PayloadScoreQuery.PayloadSpanScorer.getPayloadScore()
if (score > 0 == false) { // also maps -0.0 (and NaN, negatives) to +0
// PayloadScoreQuery.PayloadSpanScorer.getPayloadExplanation()
if (Float.compare(expl.getValue().floatValue(), 0f) < 0) { // includes -0.0

Trade-offs

  • Constant time per document, as before (explain, not on the scoring path, uses Float.compare instead of <); no benchmark was run.
  • Covers every PayloadFunction, built-in or custom, and every decoder; not other -0.0 producers (the FunctionScoreQuery/FunctionQuery sibling, a similarity, custom scorers).

One signed-zero order in the collector (alternative or addition, not run)

#

Make TopScoreDocCollector's competitiveness test (:113) and searchAfter test (:103) use the heap's order (Float.compare or the encoded long).

Trade-offs

  • Hides the top-k and paging symptom for every -0.0 producer.

Downstream note

#

Where end users can write float payloads scored with max or min (for example Solr's {!payload_score}, read, not run), a -0.0 payload changes only the order of zero-scored hits: in a top-k its document can drop below the others, and offset paging can show it on several pages while other zero-scored hits never appear. Matches, filters and counts are unaffected.

How it was found

#

A hunt on payload and span queries compared PayloadScoreQuery scores, bit for bit, with an independent reference model over small bounded inputs: 679,172 of 76,177,080 checks gave -0.0 where the reference gives 0. The reference maps -0.0 to +0.0 on purpose, after the test framework's sign-aware check; the site had already been flagged, unverified, through the sibling bug.

The method in full182 words

Method: non-formal first flag, then semi-formal (bounded-exhaustive translation validation, confirmed by execution).

  • First flag. While verifying the FunctionScoreQuery sibling (2026-10-26), a probe with a custom float decoder returned -0.0 from PayloadScoreQuery; it was noted as an unverified sibling.
  • Signal. The payload/span hunt wrote an independent reference of payload scoring (Min, Max, Sum and Average folded over the decoded payloads, the final score clamped to a non-negative float with -0.0 mapped to +0.0) and compared it, by float bits, with the stock main jar over a bounded-exhaustive space of small indexes and queries (payloads including -0.0, an IEEE-float decoder): 679,172 of 76,177,080 score checks returned -0.0 where the reference gives +0.0; all other non-nested score checks matched. So the run confirmed a suspected site at scale rather than finding it blind.
  • Confirmation. A public-API JUnit failed 3/3 on main with assertions on and off; then a cross-model review with a shell (OpenAI GPT-5.6), an independent reproducer, a second such review, a devil's-advocate verifier and an adjudication checked it, and a follow-up ran the version history, a prior-report search and a security screen.

LFV-835, snapshot of 2026-11-08

Registry title
PayloadScoreQuery scores a payload value of -0.0 as -0.0 instead of 0 (MinPayloadFunction, MaxPayloadFunction or a custom PayloadFunction with a decoder that reads IEEE floats), because its LUCENE-7996 negative-score clamp tests 'score >= 0 == false' and its explain truncation 'value < 0'; since 10.2.0 the top-1 hit is then not the head of the top-2 hits
Area
queries / payloads (PayloadScoreQuery payload-score clamp, LUCENE-7996; visible through core TopScoreDocCollector tie handling; sibling of LFV-273's function-query clamps)
Priority
Low, rank 776: This is the PayloadScoreQuery version of LFV-273's -0.0 clamp bug, but it also needs a custom IEEE-float payload decoder and an exact -0.0 payload, so it is narrower.
Impact class
minor
Impact note
Applications that score with PayloadScoreQuery (lucene-queries) using a PayloadDecoder that reads IEEE floats (for example PayloadHelper.decodeFloat over FloatEncoder payloads; the stock FLOAT_DECODER reads one byte and cannot produce -0.0) and MinPayloadFunction, MaxPayloadFunction or a custom PayloadFunction get, for a document whose payload score is exactly -0.0, the score -0.0f and an explanation of -0.0 instead of 0, with includeSpanScore false and true; only hits whose correct score is 0 are affected: since 10.2.0 their order depends on k (search(q, 1) is not the head of search(q, 2)), and since 10.3.0 test suites built on Lucene's test framework fail with 'AssertionError: -0.0' under -ea; match sets, counts and every positively scored hit are unchanged; SumPayloadFunction and AveragePayloadFunction turn a lone -0.0 into +0.0; default IndexWriterConfig, codec and searcher, no scale needed, -ea and -da; every release since 8.0.0.
Summary
Index two documents whose float payloads are '-0.0' and '0.0' (WhitespaceTokenizer + DelimitedPayloadTokenFilter with FloatEncoder) and search PayloadScoreQuery(SpanTermQuery, MaxPayloadFunction or MinPayloadFunction, a decoder that calls PayloadHelper.decodeFloat, includeSpanScore false or true). You expect both hits to score 0 and tie in doc-id order, because PayloadScoreQuery maps every negative payload score to 0 (LUCENE-7996: 'Scorers are no longer allowed to produce negative scores'; the test framework's AssertingScorer checks Float.compare(score, 0f) >= 0), as it does for a payload of -1.0. Instead the -0.0 document scores and explains as -0.0, because the clamp 'score >= 0 == false' and the explain test 'value < 0' are both false for -0.0, and since 10.2.0 search(q, 1) returns that document while search(q, 2) ranks it second.
