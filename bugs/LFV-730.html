With soft deletes, a merge wrapper that drops documents breaks the merged segment's soft-delete count

With a soft-deletes field set, a merge policy whose wrapForMerge drops a live document (its javadoc allows it) makes forceMerge(1) throw invalid softDelCount=-1 and close the IndexWriter. Under SoftDeletesRetentionMergePolicy the merge stores 0 soft deletes where 1 is right, so counts say 3 for 2 live documents.

The bug in 30 seconds

#

During a merge, the merge policy may wrap each segment's reader and hide documents. With soft deletes, IndexWriter must also record how many soft-deleted documents the new segment keeps. For a segment without hard deletes it subtracts instead of counting, which is right only if the wrapper never hides a live document.

  1. You set setSoftDeletesField("soft") and a merge policy whose OneMerge#wrapForMerge drops expired documents; its javadoc says a wrapper may "add/remove fields or documents". Segment 1 holds a and b (expired), segment 2 holds c. Nothing is soft-deleted.
  2. You call forceMerge(1) and expect one segment with a and c, which is what the same code gives without a soft-deletes field.
  3. For a segment without hard deletes, IndexWriter works out the soft deletes to keep as softDelCount minus the wrapped reader's numDeletedDocs: 0 - 1 = -1, because the dropped live document b counts as a removed soft delete. The merge throws invalid softDelCount=-1 (maxDoc=2), and as a tragic event it closes the IndexWriter: uncommitted changes are lost and every later call throws AlreadyClosedException.
  4. Put SoftDeletesRetentionMergePolicy on top and keep one soft-deleted document (a, replaced by a2): the sum is 1 - 1 = 0 instead of 1, and with assertions off it is committed. A search finds 2 documents, but numDocs and IndexSearcher#count say 3.
  5. CheckIndex at level 2 reports actual soft deletes: 1 but expected: 0, and once a is no longer retained the next merge throws invalid softDelCount=-1 (maxDoc=3) and closes the writer. A segment with one unrelated hard delete is counted properly and merges fine.

Who is affected

#

Applications that set a soft-deletes field and install their own merge wrapper that hides live documents, for example to expire documents at merge time. No in-tree policy does this, so default configurations are safe. For those applications it is deterministic on every merged segment without hard deletes: the merge fails and closes the IndexWriter, or a too-low count is stored.

Mechanism, terms and numbers1,015 words

OneMerge#wrapForMerge is documented as the place to "add/remove fields or documents" before a merge, for example to drop expired documents. When the index also has a soft-deletes field, the merge must record how many soft-deleted documents the new segment still holds. For a wrapped segment with hard deletes, IndexWriter.mergeMiddle counts them; for one without hard deletes it subtracts, getSoftDelCount() - wrappedReader.numDeletedDocs(), which is right only if the wrapper never hides a live document. With nothing soft-deleted, a wrapper that drops one expired document gives -1 and forceMerge(1) throws invalid softDelCount=-1 (maxDoc=2); the failure is a tragic event that closes the IndexWriter and rolls back its uncommitted changes, and a reopened writer fails the same way. Under SoftDeletesRetentionMergePolicy with one retained soft-deleted document the merge succeeds (assertions off) but records 0 soft deletes instead of 1: numDocs, IndexSearcher#count and getDocStats().numDocs say 3 while 2 documents are live, CheckIndex at level 2 reports actual soft deletes: 1 but expected: 0, and once the document is no longer retained the next merge of that segment throws invalid softDelCount=-1 (maxDoc=3) and closes the writer. Searches through the writer's readers stay right. The same merge works without a soft-deletes field, or when the segment happens to hold one unrelated hard delete. The shortcut came with LUCENE-8569 (2018); releases 7.4.0-7.6.0 counted correctly, every release from 7.7.0 to 10.5.2 and main is affected. It needs the application's own document-dropping merge wrapper, so default configurations are not affected.

Terms

#
  • Soft deletes: with IndexWriterConfig.setSoftDeletesField("soft"), softUpdateDocument (or updateDocValues on that field) hides a document by giving it a doc value in the soft-deletes field instead of marking it deleted. Each segment stores how many such documents it holds (softDelCount); the readers the writer hands out compute numDocs as maxDoc - delCount - softDelCount.
  • Merge wrapper: MergePolicy.OneMerge#wrapForMerge may wrap each segment's reader before the merge "in order to add/remove fields or documents" (MergePolicy.java:301-309); OneMergeWrappingMergePolicy is the stock way to install one. A wrapper that returns fewer live documents drops them from the merged segment.
  • SoftDeletesRetentionMergePolicy: a wrapper that does the opposite, it revives soft-deleted documents that match a retention query so they survive the merge.

The bug

#
  1. IndexWriter.mergeMiddle wraps each reader (IndexWriter.java:5497). With soft deletes and a wrapped reader (:5499-5500) it must compute the soft deletes that survive.
  2. With hard deletes it counts. If the segment has hard deletes (:5504), countSoftDeletes (:5427-5452) walks the soft-deletes doc values and counts the documents still live in the wrapped reader. Right for any wrapper.
  3. Without hard deletes it subtracts (:5530-5535): getSoftDelCount() - wrappedReader.numDeletedDocs(), with the assertions "carry-over soft-deletes must be positive" and a recount check. If the segment has s soft-deleted documents and the wrapper revives r and hides k live ones, numDeletedDocs is s - r + k, so the result is r - k instead of r. Right only when k = 0.
  4. The total is stored with merge.info.setSoftDelCount(...) (:5593). A negative total throws IllegalArgumentException("invalid softDelCount=...") (SegmentCommitInfo.java:384-388); a too-low total is committed. Only the total is checked at run time: with assertions off, one segment's negative carry-over can hide behind another segment's positive count.
  5. A failed merge closes the writer. The exception escapes IndexWriter.merge, whose catch (Throwable t) calls tragicEvent(t, "merge") (IndexWriter.java:5109-5113); maybeCloseOnTragicEvent then runs rollbackInternal (:6098-6105). The writer drops everything since its last commit and closes; every later call throws AlreadyClosedException. Under the default ConcurrentMergeScheduler the merge thread does the same and forceMerge(1) throws IllegalStateException: this writer hit an unrecoverable error; cannot complete forceMerge (:2286-2289).
  6. What reads it. In the writer's readers (DirectoryReader.open(IndexWriter)) and IndexWriter#getDocStats(), numDocs is derived from the stored count (PendingDeletes.java:242-250), and IndexSearcher#count(MatchAllDocsQuery) returns numDocs per leaf (search/MatchAllDocsQuery.java:57-58), while live docs are rebuilt from the doc values, so their searches stay right. A SoftDeletesDirectoryReaderWrapper over a directory reader recounts from the doc values (SoftDeletesDirectoryReaderWrapper.java:142-147) and, with assertions off, reports the right count. CheckIndex compares the stored and the counted value (CheckIndex.java:4941-4947) only at level 2 or higher (:1114); neither the command-line default (level 1) nor an API CheckIndex without setLevel (level 0) runs that check.
  7. The next merge. Once the retention query stops matching, the wrapper hides the soft-deleted document again and the shortcut computes 0 - 1 = -1 from the too-low stored count: that merge throws and closes the writer.

Exposure and likelihood279 words
  • Who. Applications that set a soft-deletes field and install their own merge policy whose OneMerge#wrapForMerge hides live documents, for example dropping expired documents at merge time through OneMergeWrappingMergePolicy (@lucene.experimental), alone or under SoftDeletesRetentionMergePolicy. The production overrides of wrapForMerge in Lucene revive (SoftDeletesRetentionMergePolicy) or delegate (IndexWriter, misc's BPReorderingMergePolicy), so default configurations are not affected.
  • Trigger. Deterministic whenever a merge covers a segment without hard deletes and the wrapper hides at least one live document in it; the introducing commit calls segments without hard deletes "the common case". No scale, concurrency or special data.
  • Effect. Loud form: the merge throws and, as a tragic event, closes the IndexWriter: uncommitted changes are rolled back, every later call throws AlreadyClosedException, and a reopened writer closes again on its next merge of the same segments (also under the default ConcurrentMergeScheduler). Silent form (assertions off, as in production, with a retention policy): the committed segment records too few soft deletes; the writer's document counts over-count by the number of hidden documents, CheckIndex at level 2 or higher reports corruption, and the next merge of that segment throws and closes the writer once the retained documents are no longer retained. Searches through the writer's readers still return only live documents; no committed document is lost or revived. With assertions on, every form fails at IndexWriter's own assertion, which closes the writer too.
  • How rare. A judgement: the combination is uncommon. Apache Solr main has a wrapForMerge that drops documents but does not use soft deletes; GitHub searches of Elasticsearch, OpenSearch and Solr for the symptom strings return nothing; other downstream merge policies were not surveyed.

Why it is a bug, not intended

#
  • wrapForMerge may "add/remove fields or documents"; its only stated restriction is no doc-ID reordering.
  • Same wrapper, same documents: it works without a soft-deletes field, or with one unrelated hard delete in the segment.
  • Releases 7.4.0-7.6.0 counted correctly, and the review of the 2018 shortcut called a negative result "a bug".
The full argument213 words
  • Contracts. OneMerge#wrapForMerge: "Wrap a reader prior to merging in order to add/remove fields or documents"; only reordering doc IDs is illegal (MergePolicy.java:301-309, wording since 9.9.0 via #12622; before: "add/remove information to the merged segment"). setSoftDeletesField: "Soft deletes allow to retain documents across merges if the merge policy modifies the live docs of a merge reader" (IndexWriterConfig.java:551-552). IndexWriter's own comment: "this is also required if any MergePolicy modifies the liveDocs" (IndexWriter.java:4844-4845). CheckIndex treats a mismatching count as corruption.
  • The inconsistency. No soft-deletes field: works. Soft-deletes field plus one unrelated hard delete in the segment: works (the counting path). Soft-deletes field, no hard delete: fails. A deliberate rule would not depend on an unrelated hard delete.
  • History. 7.4.0-7.6.0 counted the surviving soft-deleted documents of every wrapped segment. LUCENE-8569 (#9615, apache/lucene-solr#502, 2018) replaced that with the subtraction as an optimization that gives "accurate counts"; neither the issue nor the PR mentions wrappers that hide live documents. In that review the negative-carry-over check was an IllegalStateException; a reviewer asked "AssertionError instead? This means we have a bug right?", and it became the assert: a negative result was treated as an IndexWriter bug, not as misuse.
  • Tests. No upstream test removes documents in wrapForMerge in a soft-deletes index.
The devil's-advocate check236 words

The intended-behaviour verifier and a cross-model review built the strongest case for "not a bug": the merge-policy hooks are expert API and OneMergeWrappingMergePolicy is @lucene.experimental; every in-tree wrapper only revives; the shortcut's assertions show its author expected revive-only wrappers; and the setSoftDeletesField sentence can be read as "with soft deletes, a merge policy changes live docs only to retain documents".

Why it fails: no document states a revive-only rule and wrapForMerge explicitly allows removing documents; the setSoftDeletesField sentence names retention "for instance" and restricts nothing; the review of the introducing change called a negative carry-over a bug; the outcome flips on an unrelated hard delete; 7.4.0-7.6.0 handled the same wrapper correctly; @lucene.experimental permits API changes, not a merge that stores a wrong count or closes the writer; and IndexWriter treats the outcome as a tragic event, not as a cleanly rejected policy. Indexing every document with softUpdateDocument, as setSoftDeletesField asks, fails the same way, so it is not misuse. Both rated the case weak. Verdict: a defect.

Points a maintainer may still raise (a cross-model fact check found the rebuttal fair but incomplete here): the explicit "add/remove fields or documents" wording came in 9.9.0, five years after the shortcut; the usual way to remove documents is a delete; nobody reported it in eight years; and LUCENE-8569 had a real performance motive. None of them makes a closed writer or a wrong stored count acceptable.

Suggested fix

#

Recommended Count the surviving soft deletes in both branches

Count the soft-deleted documents that stay live in the wrapped reader for every wrapped segment, as segments with hard deletes (and releases before 7.7.0) already do: one change in IndexWriter.mergeMiddle, +9/-14. The repros pass with assertions on and off; the full lucene/core suite (8,899 tests) passes with assertions on.

} else {
  // The wrapper may revive soft-deleted documents and may also remove documents
  // (OneMerge#wrapForMerge), so the carried-over soft deletes cannot be derived from
  // the deletion counts alone: count the soft-deleted documents that stay live.
  countSoftDeletes(
      wrappedReader, wrappedReader.getLiveDocs(), null, softDeleteCount, Counter.newCounter(false));
}
All options and trade-offs4 options · 623 words

One fix was applied in a scratch worktree at a9779ef3c193 and run through gradle (seed DEADBEEF). The other options are sketches, not run. Which one, or another design, is the maintainers' call.

Count the surviving soft deletes in both branches (validated by the checks) (recommended)

#

Replace the subtraction in the no-hard-deletes branch with countSoftDeletes, the counting the hard-deletes branch uses and that 7.4.0-7.6.0 used for every wrapped segment, and delete assertSoftDeletesCount, which becomes unused (the ECJ lint settings make an unused private member an error). Patch: fix-count-soft-deletes.diff, +9/-14 in IndexWriter.java. Equivalent by reading: drop the hardLiveDocs != null split and always call countSoftDeletes with hardLiveDocs, as 7.6.0 did.

} else {
  // The wrapper may revive soft-deleted documents and may also remove documents
  // (OneMerge#wrapForMerge), so the carried-over soft deletes cannot be derived from
  // the deletion counts alone: count the soft-deleted documents that stay live.
  countSoftDeletes(
      wrappedReader, wrappedReader.getLiveDocs(), null, softDeleteCount, Counter.newCounter(false));
}

Trade-offs

  • It gives back the LUCENE-8569 optimization for wrapped segments without hard deletes: one pass over the soft-deletes doc values of each such segment (only documents that carry a soft-delete value, one Bits.get each). Segments that are not wrapped still skip all accounting.
  • For SoftDeletesRetentionMergePolicy, the wrapper of such a segment already runs a query over its soft-deleted documents and copies its live docs (SoftDeletesRetentionMergePolicy.java:97-130), so the extra pass is of the same order (by reading). No benchmark was run.

What the checks validated

  • Stock: the compact test and the finder's test together run 10 tests: 6 failed and 1 skipped with assertions on, 7 failed with assertions off.
  • With the fix: 10 of 10 pass with assertions on and with assertions off.
  • With the fix: the full lucene/core test suite passes (750 classes, 8,899 tests, 322 skipped, 0 failures, assertions on, including both repro classes and the soft-delete test classes); :lucene:core:ecjLint and :lucene:core:checkGoogleJavaFormat pass.
  • Earlier, with the same change shadowed: the 584-case exhaustive run has 0 failures (assertions on and off); TestSoftDeletesRetentionMergePolicy (14 tests) and TestSoftDeletesDirectoryReaderWrapper (5 tests) pass over 3 iterations each; the independent reproducer's 6 tests pass.

Keep the shortcut for wrappers that declare they only revive (not run)

#

No cheap runtime check can tell "revives r, hides k" from "revives r - k, hides nothing": both give the same numDeletedDocs. So the shortcut would need the wrapper to declare that it only revives, for example through a new OneMerge method that SoftDeletesRetentionMergePolicy overrides.

Trade-offs

  • New API surface; a chain such as retention over a user wrapper needs every link to declare it; the saving is small by the trade-off above.
  • A generic runtime test ("the wrapped live docs are a superset of the original ones") is no cheaper: it costs a pass over maxDoc and does not cover a wrapper that changes the soft-deletes field itself, which wrapForMerge also permits.

Document a revive-only rule and fail with a clear message (not run)

#

Turn the assertion into an explicit exception and document that wrappers in soft-deletes indexes must not hide live documents.

Trade-offs

  • Contradicts the wrapForMerge javadoc and rejects merges that work without a soft-deletes field; it still fails inside the merge, so the writer still closes; a too-low but non-negative count can only be detected by counting, which is the first option's cost.

Workaround today: hard-delete expired documents instead of hiding them (not run)

#

Drop expired documents with IndexWriter#deleteDocuments(Query) instead of hiding them in wrapForMerge; a segment with hard deletes takes the counting path. The delete must already be applied when the merge takes its readers: the branch is chosen from the merge reader's hard-live-docs snapshot (ReadersAndUpdates.java:1092-1108).

Trade-offs

  • By reading only; it changes when the documents disappear (at the delete, not at the merge).

Downstream note

#

Apache Solr main ships a merge wrapper that drops documents (AuxIndexJoinMergePolicy, apache/solr#4749) but does not use soft deletes, so it is not affected; other downstream merge policies were not surveyed.

How it was found

#

A bounded-exhaustive test that composes merge-policy wrappers checked its own oracle with a deliberately broken wrapper that drops one live document; in every cell IndexWriter's assertion "carry-over soft-deletes must be positive" fired instead. Reading mergeMiddle found the shortcut, and a 584-case exhaustive run on the real code showed exactly when it fails.

The method in full185 words

Method: a bounded-exhaustive differential and model-based test (semi-formal tier) of merge-policy wrapper compositions: 50 wrapper towers x 5 base policies x 10 triggers x 3 data profiles x 2 seeds, checked against a model oracle.

  • To check that its oracle can fail, the harness runs mutants. The mutant that wraps merges to drop one live document was meant to be caught by the model's live-documents check; instead IndexWriter's own assertion "carry-over soft-deletes must be positive" fired in every cell.
  • Reading IndexWriter.mergeMiddle located the no-hard-deletes subtraction.
  • A second bounded-exhaustive run on the real code (584 combinations, reviving a hard-deleted document excluded: segments of 1-3 documents, each live, soft-deleted or hard-deleted, and a wrapper that keeps, removes or revives each) failed in exactly the 103 cases with no hard deletes and a removed live document, and in 0 of 481 others; with the fix, 0 of 584.
  • Found 2026-10-27 on main a9779ef3c193; then checked by an independent reproducer, a devil's-advocate verifier, reviews by a model from another family (OpenAI GPT-5.6) that ran their own tests, an adjudication, a follow-up (history, prior reports, security) and an audit.

Executed: 7.4.0-7.6.0 pass, every executed release from 7.7.0 to 10.5.2 and main fail, and reverting only that change makes 7.7.0 and 8.0.0 pass. Never fixed.

Bug record

#

LFV-730, snapshot of 2026-10-27

Registry title
With a soft-deletes field configured, IndexWriter's merge assumes OneMerge#wrapForMerge only revives documents: for each merged segment without hard deletes, every live document that a merge wrapper hides (which the javadoc allows) lowers the new segment's soft-delete count by one, so the merge throws 'invalid softDelCount=-1' when nothing is revived, and under SoftDeletesRetentionMergePolicy commits a too-low count (numDocs and IndexSearcher#count over-count, CheckIndex rejects it, later merges of it throw); regression since 7.7.0 (LUCENE-8569)
Area
index / IndexWriter merge soft-delete accounting (mergeMiddle carry-over of soft deletes x OneMerge#wrapForMerge, OneMergeWrappingMergePolicy, SoftDeletesRetentionMergePolicy)
Priority
Medium, rank 164: Since 7.7, core IndexWriter soft-delete accounting.
Impact class
silent wrong results
Impact note
Only applications that set a soft-deletes field and install their own merge policy whose OneMerge#wrapForMerge hides live documents (for example dropping expired documents at merge time through the @lucene.experimental OneMergeWrappingMergePolicy; no in-tree policy does this, so default configurations are unaffected) are hit, deterministically and at any index size, whenever a merge covers a segment that has no hard deletes and the wrapper hides a live document in it: the merged segment's soft-delete count comes out too low by the number of such hidden documents. With -ea the merge fails at IndexWriter's assertion 'carry-over soft-deletes must be positive' as soon as one segment's carry-over is negative; with -da (as in production) the merge throws IllegalArgumentException 'invalid softDelCount=-1' when the total is negative (for example nothing soft-deleted), and because the arithmetic is deterministic a retry of the same merge fails the same way [read]; when soft-deleted documents are retained, as with SoftDeletesRetentionMergePolicy over such a wrapper, the merge instead commits the too-low softDelCount silently, so DirectoryReader#numDocs, IndexSearcher#count(MatchAllDocsQuery) and IndexWriter#getDocStats().numDocs over-count while searches still return only the live documents, CheckIndex at level 2 or higher reports 'actual soft deletes: 1 but expected: 0', and once the retention query stops matching the next merge of that segment throws 'invalid softDelCount=-1 (maxDoc=3)'; every release from 7.7.0 to 10.5.2 and main [exec].
Summary
You set IndexWriterConfig#setSoftDeletesField and a merge policy whose OneMerge#wrapForMerge hides expired documents (its javadoc says a wrapper may 'add/remove fields or documents'), index two segments without hard deletes, and call forceMerge(1); you expect the merge to drop the expired document and succeed, as the same merge does without a soft-deletes field, or with one when the segment happens to hold a hard delete. Instead IndexWriter derives the carried-over soft deletes as getSoftDelCount() - wrappedReader.numDeletedDocs(), which counts each hidden live document as a dropped soft delete, so the count comes out -1 and the merge throws IllegalArgumentException 'invalid softDelCount=-1 (maxDoc=2)'. With SoftDeletesRetentionMergePolicy on top (one retained soft-deleted document) the merge silently commits softDelCount=0, so numDocs and IndexSearcher#count report 3 where 2 documents are live, CheckIndex reports 'actual soft deletes: 1 but expected: 0', and after the retention window the next merge of that segment throws 'invalid softDelCount=-1 (maxDoc=3)'.
