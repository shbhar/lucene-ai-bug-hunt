WordBreakSpellChecker.suggestWordCombinations applies minSuggestionFrequency under SUGGEST_MORE_POPULAR, although its setter says the minimum does not apply there

With setMinSuggestionFrequency(2) and SUGGEST_MORE_POPULAR, suggestWordCombinations([sun, flower]) drops the indexed word sunflower (docFreq 1), although the setter says the minimum is "Not applicable" in that mode and suggestWordBreaks replaces it there. One setting means two things in a checker; a one-line change makes the two methods agree.

The finding in 30 seconds

#

WordBreakSpellChecker suggests joining words typed apart (sun flower -> sunflower) and splitting a word into indexed parts. Its one minSuggestionFrequency setting is documented as not applying in more-popular mode. The split method replaces it there; the join method still checks it after its own more-popular rule.

  1. Index one document with the single word sunflower (docFreq 1); sun and flower are not in the index. Call setMinSuggestionFrequency(2), whose javadoc says the minimum is "Not applicable when used with SUGGEST_MORE_POPULAR".
  2. Call suggestWordCombinations([sun, flower], 5, reader, SUGGEST_MORE_POPULAR). You expect sunflower: it is in the index and at least as frequent (1) as its most popular part (0), the mode's documented rule.
  3. You get no suggestion and no error: after the more-popular rule passes, a second check still requires docFreq >= 2. With the default minimum of 1 the same call returns sunflower.
  4. The sibling method keeps the setter's promise: with sun and flower indexed once each, suggestWordBreaks("sunflower") with the same minimum and mode returns [sun, flower], although each part has docFreq 1 < 2.

Who is affected

#

Users who set a minimum suggestion frequency of 2 or more and ask suggestWordCombinations for more-popular suggestions, directly or through a word-break spell-check component that maps such options onto these calls. The default minimum and the other modes are unaffected. Effect: a valid join suggestion is missing; nothing else.

Mechanism, terms and numbers493 words

WordBreakSpellChecker (lucene-suggest) suggests joining terms a user typed apart (suggestWordCombinations, sun flower -> sunflower) and splitting one term into indexed words (suggestWordBreaks). Its setMinSuggestionFrequency javadoc says the minimum is "Not applicable when used with SUGGEST_MORE_POPULAR". suggestWordBreaks follows that: in that mode it replaces the minimum with the term's own docFreq (at least 1). suggestWordCombinations does not: after its more-popular rule it still requires combinedTermFreq >= minSuggestionFrequency, in every mode. With setMinSuggestionFrequency(2), an index holding only sunflower (docFreq 1) and SUGGEST_MORE_POPULAR, suggestWordCombinations([sun, flower]) returns nothing instead of sunflower, while on an index with sun and flower suggestWordBreaks("sunflower") returns [sun, flower] under the same settings. The default minimum (1) and the other modes are unaffected, nothing throws, and the only effect is a missing suggestion. It dates from the class's first commit (LUCENE-3523, 2012) and reproduces on every version run, 4.0.0-ALPHA to 10.6.0 and main. A one-line change that mirrors suggestWordBreaks fixes it; maintainers may prefer to narrow the javadoc instead.

Terms

#
  • WordBreakSpellChecker (lucene-suggest, org.apache.lucene.search.spell): suggestWordCombinations(terms, ...) joins adjacent query terms into one indexed word; suggestWordBreaks(term, ...) splits one term into indexed words.
  • SuggestMode.SUGGEST_MORE_POPULAR: "Return only suggested words that are as frequent or more frequent than the searched word" (SuggestMode.java:28). For joins the method javadoc says "each suggestion will have the same, or better frequency than the most-popular included term" (WordBreakSpellChecker.java:142-143).
  • minSuggestionFrequency (default 1, one field read by both methods): "The minimum frequency a term must have to be included as part of a suggestion. Default=1 Not applicable when used with SUGGEST_MORE_POPULAR" (:413-416).

The bug

#
  1. suggestWordBreaks keeps the promise: under SUGGEST_MORE_POPULAR, useMinSuggestionFrequency = (origFreq == 0 ? 1 : origFreq) (:104-107), so the configured minimum is not used.
  2. suggestWordCombinations checks the more-popular rule combinedTermFreq >= maxFreq (:206), where maxFreq is the docFreq of the most popular included term, and then combinedTermFreq >= minSuggestionFrequency in every mode (:208).
  3. So in more-popular mode a join that passes the method's other checks (separators, maxChanges, word length, evaluation and result limits) is dropped exactly when maxFreq <= combinedTermFreq < minSuggestionFrequency: the joined word and all its parts are rarer than the minimum. The default minimum (1) and the other two modes behave the same with and without the fix.

Why it looks unintended

#
  • The setter's javadoc says the minimum is "Not applicable when used with SUGGEST_MORE_POPULAR", with no method scope; both methods read the one field.
  • The sibling suggestWordBreaks implements that sentence with dedicated code from the same commit.
  • The join method's own rule ("the same, or better frequency than the most-popular included term") has no minimum; no reviewed test endorses the difference.
The full argument190 words
  • Contract. setMinSuggestionFrequency: "The minimum frequency a term must have to be included as part of a suggestion. Default=1 Not applicable when used with SUGGEST_MORE_POPULAR" (WordBreakSpellChecker.java:413-416). Nothing limits the sentence to one method.
  • Sibling method. suggestWordBreaks replaces the minimum with origFreq == 0 ? 1 : origFreq in that mode (:104-107), written in the same commit by the same author (642b882d5a5). That code can even go below the configured minimum, so "not applicable" was meant literally.
  • The method's own rule. "When suggestMode equals SUGGEST_MORE_POPULAR, each suggestion will have the same, or better frequency than the most-popular included term" (:142-143); SuggestMode says "as frequent or more frequent than the searched word" (SuggestMode.java:28). Neither mentions a minimum.
  • Tests and history. Upstream TestWordBreakSpellChecker never uses SUGGEST_MORE_POPULAR (its suggestWordCombinations calls use SUGGEST_ALWAYS and SUGGEST_WHEN_NOT_IN_INDEX); no CHANGES, MIGRATE or issue entry found in the recorded searches discusses the rule. In SOLR-2993, the Solr integration of this class, its author describes the only-more-popular join rule as "a document frequency that is greater or equal than the highest document frequency between "spell" and "check"", with no minimum.
The devil's-advocate check180 words

The strongest works-as-designed case (the cross-model lenses rated it moderate; the credibility audit leans on it): minSuggestionFrequency is a global quality floor and more-popular an extra relative rule. DirectSpellChecker in the same package keeps its thresholdFrequency floor under SUGGEST_MORE_POPULAR (DirectSpellChecker.java:350-356). The join javadoc gives a necessary condition, not a promise to return every qualifying word. The behaviour is 14 years old with no public complaint found, SuggestMode is experimental, and Solr's reference guide presents the minimum as a plain floor, so a user who sets 2 may expect it to apply.

Why it fails as a defence of the current code: DirectSpellChecker's threshold javadoc makes no "not applicable" promise, while this class's setter does, in so many words; the sibling method of the same checker implements the promise; and nothing found endorses applying the minimum to joins only. What the case does show is that the fix direction (code, javadoc, or the minimum in both methods) is the maintainers' choice, which is why the bug ranks Low. Verdict: not intended; one setting, two meanings in a checker.

Suggested fix

#

Recommended A: use 1 instead of the minimum under SUGGEST_MORE_POPULAR (mirrors suggestWordBreaks)

Under SUGGEST_MORE_POPULAR, compare the joined word's docFreq with 1 instead of minSuggestionFrequency, as suggestWordBreaks does (+7/-1 lines). With it the whole suggest module passes, assertions on and off. Maintainers may instead narrow the setter's javadoc or apply the minimum in both methods.

// minSuggestionFrequency is "not applicable" with SUGGEST_MORE_POPULAR (see its setter), and
// suggestWordBreaks replaces it in that mode. Here, in that mode, a combined term only has to
// exist and be at least as frequent as the most popular included term
int useMinSuggestionFrequency =
    suggestMode == SuggestMode.SUGGEST_MORE_POPULAR ? 1 : minSuggestionFrequency;
...
            if (combinedTermFreq >= useMinSuggestionFrequency) {

Trade-offs

  • No change for the default minimum (1) or for the other two modes.
  • Callers who relied on a minimum of 2 or more for joins in more-popular mode get more suggestions: a behaviour change for them.
  • For a minimum of 0 or below, A also stops suggesting a joined word that is not in the index (docFreq 0) in more-popular mode, as suggestWordBreaks already does (its replacement never goes below 1). Today 0 >= 0 lets such a word through; that face is not claimed as a bug.
  • Open PR #16847 changes docFreq variables in this file (including combinedTermFreq) from int to long; A applies cleanly on top of it and still compiles (the int floor is widened when compared with the long docFreq); a reviewer may prefer long for the new local.

C: apply the minimum in both methods

Downstream note

Solr's word-break spell checker maps its minSuggestionFreq and spellcheck.onlyMorePopular options onto these calls, so in one such request word breaks replace the minimum while word joins apply it; its reference guide documents the minimum as a plain floor (from reading Solr's source and docs, not run).
