FunctionRangeQuery scores raw negative values, so a minimumShouldMatch query can drop a document whose value is -Infinity

FunctionRangeQuery scores each match with its raw value, so negative values give negative scores, although Lucene scores must not be negative since 8.0. A matching document whose value is -Infinity then disappears from minimumShouldMatch top-k results: 2 documents match, search(q, 10) returns 1.

The finding in 30 seconds

#

FunctionRangeQuery scores a match with its raw value, so -Infinity scores -3.4e38. Top-k search of a "match at least 2 of these" query checks each document's score against a threshold that starts at 0, and drops this one.

Background

#
  1. FunctionRangeQuery. It matches the documents whose value (here from the numeric field d) lies in a range, and scores each match with that value. An open range, null to null, matches every document that has a value, -Infinity included.
  2. No negative scores. Since Lucene 8.0 (LUCENE-7996) a query must never produce a negative score. FunctionQuery, which scores every document with the same kind of value, returns 0 for a negative value.
  3. minimumShouldMatch and WANDScorer. For top-k search of a BooleanQuery of optional clauses that needs at least 2 of them, as here, Lucene uses WANDScorer. It skips documents that cannot beat the lowest score still worth collecting, a threshold that starts at 0 and relies on scores never being negative.

The finding, step by step

#
  1. Index two documents: doc 0 with d = -Infinity (a DoubleDocValuesField) and body: a, doc 1 with d = 1.0 and body: b. Search "at least 2 of" FunctionRangeQuery(d, open range), body:a and body:b with IndexSearcher.search(q, 10).
  2. You expect 2 hits: each document matches two of the three clauses, and count(q) says 2. Scores must not be negative since Lucene 8.0; FunctionQuery over the same field scores doc 0 as 0.
  3. Instead you get 1 hit, doc 1 (score 1.315), and totalHits "1 hits", an exact count. No error with assertions off; with assertions on, WANDScorer throws AssertionError.
  4. Why: FunctionRangeQuery scores doc 0 with its raw value, -Infinity, mapped to -3.4e38. For "at least 2 of" top-k, WANDScorer rejects a document whose score is below the lowest score worth collecting, which starts at 0. A value such as -5 rounds to 0 in its scaled arithmetic and survives; -3.4e38 does not.
  5. Clamping the score at 0, as FunctionQuery does, fixes it: 2 hits, doc 0 scores 0.315 (its body:a score). Negative scores exist since 8.0.0; the lost hit since 10.1.0, and this two-document shape since 10.5.0.

Who is affected

#

Applications that rank with FunctionRangeQuery as a scoring clause over values that can be negative get negative scores (since 8.0.0). Hits are lost (10.1.0 on) only with a stored -Infinity or a summed score at or below about -4e31, a range that admits it, and the query as a SHOULD clause of a minimumNumberShouldMatch >= 2 query that reaches WANDScorer.

Mechanism, terms and numbers779 words

FunctionRangeQuery (lucene/queries) matches documents whose function value lies in a range and scores each match with the value itself: ValueSourceScorer.score() returns floatVal(doc) and maps NaN and -Infinity to -Float.MAX_VALUE. LUCENE-7996 (8.0.0) made negative scores illegal and changed FunctionQuery's identical code to return 0, but did not touch ValueSourceScorer, whose comment still says "(same as FunctionQuery, but no qWeight)". So negative values give negative scores in TopDocs and explain. Since 10.1.0 it also loses hits: top-k search of a pure-SHOULD BooleanQuery with minimumNumberShouldMatch >= 2 runs on WANDScorer, which rejects a candidate whose scaled score is below the minimum competitive score of 0. An ordinary negative score rounds to 0 there and survives; -Float.MAX_VALUE does not, so a matching document whose value is -Infinity is missing from search(q, n), whose total (exact here, with fewer than 1,000 matches) is too low while count(q) is right. Two documents and the default IndexWriterConfig, codec and IndexSearcher are enough. A one-line clamp fixes it.

The code (main 645d4fe14a20)

#
  1. The score is the raw value. ValueSourceScorer.java:84-92: float score = values.floatVal(disi.docID()); then return score > Float.NEGATIVE_INFINITY ? score : -Float.MAX_VALUE; with the comments "(same as FunctionQuery, but no qWeight)" and "Current Lucene priority queues can't handle NaN and -Infinity, so map to -Float.MAX_VALUE". getMaxScore returns Float.POSITIVE_INFINITY (:94-97).
  2. FunctionQuery clamps. FunctionQuery.java:130-137: if (val >= 0 == false) { // this covers NaN as well ... returns 0 (:132).
  3. Matching is separate and correct. FunctionRangeQuery.java:168-174 builds the scorer with FunctionValues.getRangeScorer; for a double field that is DoubleDocValues.java:87-147, where an open lower bound becomes Double.NEGATIVE_INFINITY (:95-96) and the match test is docVal >= l && docVal <= u (:116). So -Infinity matches, NaN never does.
  4. Routing. For this pure-SHOULD query under ScoreMode.TOP_SCORES with minShouldMatch > 1, BooleanScorerSupplier.java:315-322 declines the bulk scorers ("Fall back to BS2/WANDScorer") and :589-590 builds a WANDScorer. IndexSearcher.search(q, n) is TOP_SCORES (IndexSearcher.java:100, :599; TopScoreDocCollector.java:58).
  5. Scaling. WANDScorer compares scores as scaled longs. The scale comes from the sum of the clauses' max scores (WANDScorer.java:186-193); the range clause's +Infinity gives scalingFactor(+Infinity) = scalingFactor(MAX_VALUE) - 1 (:66, :74-75), that is 2^-105, and scaled scores are rounded up (:104).
  6. The check. WANDScorer.java:333-344 scales the summed score of the clauses that match the candidate and loops while (scaledLeadScore < minCompetitiveScore || freq < minShouldMatch), returning false once scaledLeadScore + tailMaxScore < minCompetitiveScore; the threshold starts at 0 (:163). With assertions on, scaleMaxScore trips assert maxScore >= 0 (:92) first.

The numbers

#

Doc 0 scores -3.4028235E38 + 0.31506687 (body:a). Scaled by 2^-105 that is about -8.4 million, far below 0, so WANDScorer rejects it. A score of -5 scales to about -1e-31, which rounds up to 0, so it survives with assertions off: the -5.0 control document is returned in every run that completes, 30 of 33 (score -4.837875 in the four-document check on 10.5.0); the three stock runs with assertions on throw at WANDScorer.java:92 first and return nothing. The boundary is a summed (lead) score of about -2^105 (about -4.06e31): a finite value of -1e32 is dropped and -1e31 is kept.

An exhaustive search, TopScoreDocCollectorManager(10, Integer.MAX_VALUE) (COMPLETE, TopScoreDocCollector.java:58-59), returns both documents: doc 1 = 1.3150668, doc 0 = -3.4028235E38. On this two-document index it does not run on WANDScorer: with minShouldMatch > 1 the cost threshold is maxDoc / 3 = 0, which the clauses meet (BooleanScorerSupplier.java:212-230), and optionalBulkScorer() declines only under TOP_SCORES (:315-322), so it returns a BooleanScorer (:331-337), which has no minimum-competitive-score check (an executed probe prints BooleanScorer for COMPLETE and WANDScorer for TOP_SCORES). A COMPLETE search that does reach WANDScorer also skips the check (WANDScorer.java:194-196, :334). explain gives doc 0 (abridged) "-3.4028235E38 = sum of: -3.4028235E38 = frange(double(d)):[* TO *] (-Infinity = double(d)=-Infinity), 0.31506687 = weight(body:a in 0)". FunctionQuery(d) alone scores doc 0 as 0.0.

At scale: 20,000 documents in 8 segments, 574 with value -Infinity; the same query shape returned 11,532 of 11,893 matches, reported as exactly "11532 hits", and searchAfter paging skipped the same 361 documents, all valued -Infinity (main and 10.5.2).

The negative score on its own

#

One document with d = -5.0 and FunctionRangeQuery(d, [-10, 10]): the score is -5.0 in TopDocs and explain, where FunctionQuery(d) scores 0.0. In a disjunction, a document that matches tag:x and the range clause scores -4.9171267, below its tag:x-only score 0.082873434. LuceneTestCase.newSearcher rejects the score (AssertingScorer.java:131), and on 8.0.0 to 10.0.0 a top-k search with assertions on throws in core TopScoreDocCollector.

Exposure and likelihood366 words
  • Who. Users of FunctionRangeQuery (an @lucene.experimental class) as a scoring clause, not in a FILTER clause or a ConstantScoreQuery, over a value source that can be negative. Solr's frange uses its own constant-scoring query; Elasticsearch and OpenSearch do not reference FunctionRangeQuery, getRangeScorer or ValueSourceScorer (read-only code search, 2026-10-26).
  • Negative scores (8.0.0 on). Negative scores in TopDocs and explain; matching the range clause can lower a document's score below that of a document that matches only the other clause; Lucene's own asserting test searcher rejects the score, so downstream test suites that use it can fail; on 8.0.0 to 10.0.0 any top-k search with assertions on throws in core TopScoreDocCollector.
  • Lost hits (10.1.0 on). Silent wrong results: the -Infinity document is missing from top-k and from searchAfter paging, and an exact totalHits is too low while count() is right. No exception with assertions off. On 10.1.0 to 10.4.0 only sparse SHOULD clauses or a query nested in a conjunction reach WANDScorer; since 10.5.0 dense top-level queries such as the two-document repro do too.
  • What it takes. A stored -Infinity (for example the log of 0), or a finite value low enough that the document's summed score is at or below about -2^105 (about -4e31; in the tested shapes a field value of about that size); a range that admits it (an open or -Infinity lower bound; a lower bound such as -10 excludes -Infinity); and the scored query as a SHOULD clause of a minimumNumberShouldMatch >= 2 query that reaches WANDScorer (shown for the pure-SHOULD, sparse and nested shapes). NaN cannot trigger it: it fails every range test.
  • What it does not do. Which documents match never changes: count(), FILTER, MUST_NOT and ConstantScoreQuery uses were correct in all 17 probe shapes, and in the probe every omitted result was a document valued -Infinity; no document with a non-negative score was omitted. A -Infinity document scores about -3.4e38 (near the lowest finite float), so it would have ranked at the end; with the default 1,000-hit counting threshold it shows in short result lists, in an exact total, or when paging to the end.
  • How likely: contrived. Three unusual conditions must hold at once.

Why it looks unintended

#
  • Since Lucene 8.0 "Scorers are no longer allowed to produce negative scores" (MIGRATE.md); the test framework and WANDScorer still assert it.
  • ValueSourceScorer says it scores "same as FunctionQuery"; LUCENE-7996 changed FunctionQuery's identical code to return 0 but did not touch this class.
  • count(q) says 2 and search(q, 10) says exactly 1: nothing documents that top-k may drop a match.
The full argument166 words
  • The contract. MIGRATE.md:1368-1372 ("Scorer must produce positive scores (LUCENE-7996)": "Scorers are no longer allowed to produce negative scores"); CHANGES.txt:6636 (8.0.0, API Changes: "Queries are now required to produce positive scores"); CHANGES.txt:6732-6733 ("FunctionQuery and FunctionScoreQuery now return a score of 0 when the function produces a negative value"). On main the test framework enforces it (AssertingScorer.java:131 assert Float.compare(score, 0f) >= 0, AssertingScorable.java:36).
  • Core relies on it. WANDScorer asserts maxScore >= 0 (WANDScorer.java:92) and throws "Scores must be positive or null" for a negative max score (:70-71).
  • The class says it mirrors FunctionQuery. ValueSourceScorer.java:86 "(same as FunctionQuery, but no qWeight)" and :28 "This is similar to FunctionQuery". a8a63464e7d (LUCENE-7996) replaced FunctionQuery's identical -Float.MAX_VALUE mapping with the 0 clamp; ValueSourceScorer and FunctionRangeQuery are not among its 22 files.
  • Two APIs disagree on the match set. count(q) = 2, search(q, 10) = exactly 1 hit.
  • Precedent. Negative scores in other code were fixed as bugs: #12727, #16139, #12342, #11184.
The devil's-advocate check159 words

The strongest case: FunctionRangeQuery.java:33 says "The score is the float value", and ValueSourceScorer.java:26 and FunctionValues.java:224-227 say the same, all @lucene.experimental. Scorable.score() states no sign, and since #13939 (10.1.0) core TopScoreDocCollector no longer asserts score >= 0. A second argument: Lucene tolerates negative scores from IndriDirichletSimilarity, which its similarity test base exempts.

Why it fails: those javadocs come from LUCENE-6720 (2015), two years before the rule, and LUCENE-7996 changed FunctionQuery's identical raw-value code. #13939 moved the assertion into the test framework (AssertingScorable); it did not drop it. The LUCENE-7996 discussion (#9044, 19 comments) never mentions this class, so it looks missed rather than exempted; that is an inference from silence, nobody said so. Even if a maintainer preferred to document negative scores, WANDScorer would still lose the hit, so a javadoc change alone cannot fix it. The Indri exemption is local to that class and is itself the cause of another hit-loss bug (LFV-190).

Suggested fix

#

Recommended Clamp the score at 0 in ValueSourceScorer (validated)

Clamp the score at 0 in ValueSourceScorer.score(), as FunctionQuery does: return score > 0 ? score : 0f;, and update the javadocs that say the score is the raw value. The repro passes with assertions on and off, and so do the closest suites and the whole queries module (512 tests).

// Scores must not be negative (LUCENE-7996): map negative values, -0.0 and NaN to 0. This
// conditional handles NaN since comparisons with NaN are always false.
return score > 0 ? score : 0f;
All options and trade-offs4 options · 580 words

Option A was built and run through gradle. B (document negative scores) would leave the lost hit, C (clamp only inside FunctionRangeQuery) is a narrower variant of A, and D (make WANDScorer tolerate negative scores) works against the documented rule. Workarounds that need no fix: put a FunctionRangeQuery that only restricts results in a FILTER clause or a ConstantScoreQuery, use a finite lower bound where documents valued -Infinity need not match, or reject non-finite values at index time.

Clamp the score at 0 in ValueSourceScorer (validated) (recommended)

#

ValueSourceScorer.score() (ValueSourceScorer.java:91) returns the value only when it is positive, else 0, the rule FunctionQuery applies. The same change updates the javadocs: "The score is the float value, or 0 if it is negative or NaN" in FunctionRangeQuery, a sentence in the ValueSourceScorer class javadoc, and "or 0 where that is negative or NaN" in FunctionValues.getScorer and getRangeScorer (3 files, +12/-10).

// Scores must not be negative (LUCENE-7996): map negative values, -0.0 and NaN to 0. This
// conditional handles NaN since comparisons with NaN are always false.
return score > 0 ? score : 0f;

Trade-offs

  • Behaviour change. Documents with negative values now tie at 0 instead of being ordered by their negative value; users who need that order should sort by the value. Every ValueSourceScorer that does not override score() changes the same way: the getRangeScorer implementations in FunctionValues, DoubleDocValues, LongDocValues, IntDocValues, DocTermsIndexDocValues and EnumFieldSource, FunctionValues.getScorer, and downstream subclasses. Worth a CHANGES.txt entry.
  • -0.0. It becomes 0 here; FunctionQuery lets -0.0 through, which is the separate LFV-273.
  • Matching unchanged. matches() is separate, so count(), filters and ConstantScoreQuery uses do not change.
  • Cost. One comparison per scored document; no benchmark was run.

Document negative scores instead (not recommended)

#

Change no code; say in the javadocs that FunctionRangeQuery may return negative scores.

Trade-offs

Matches today's "The score is the float value" wording, but breaks the global rule, the test framework keeps rejecting the score, and WANDScorer keeps losing the hit. Not run.

Clamp only in FunctionRangeQuery

#

Wrap the scorer that FunctionRangeWeight.scorerSupplier returns (FunctionRangeQuery.java:168-174) so that it clamps, and leave ValueSourceScorer as it is.

Trade-offs

Narrower: other users of getRangeScorer/getScorer keep raw scores, but a scorer that can return negative scores stays in the API, and it is more code than the first option. Not run.

Make WANDScorer tolerate negative scores (not recommended)

#

For example clamp the scaled lead score at 0 in WANDScorer.matches().

Trade-offs

Hides this symptom on one path only, against the documented rule, in a hot core loop; other scorers and collectors may make the same assumption. Not run.

Downstream note

#

Where end users write the value of a numeric field that an application ranks with a scored FunctionRangeQuery inside a minimumShouldMatch query, a stored -Infinity hides only that user's own document; no other, non-matching, deleted or filtered document is affected.

How it was found

#

A hunt unit ran cross-path checks of FunctionRangeQuery under Lucene's asserting test searcher, which rejected a negative score. Reading the code and history traced it to LUCENE-7996, and a public-API JUnit confirmed it. A later randomized security probe of 17 query shapes found the lost hits in the minimumShouldMatch path.

The method in full135 words

Method: non-formal (the hunt's tier for findings from directed testing and code reading). The hunt unit compared range-bound behaviour across query paths.

  • Assertion. Its cross-path FunctionRangeQuery checks ran under the test framework's asserting searcher, and AssertingScorer rejected a negative score.
  • Trace. Code and history reading led to LUCENE-7996 (a8a63464e7d), which clamped FunctionQuery, BoostedQuery and FunctionScoreQuery but not ValueSourceScorer; a public-API JUnit on the stock jar (one document, d = -5.0) failed with assertions on and off.
  • Hit loss. After the verifier panel, the follow-up's security screen ran a randomized probe (20,000 documents, 17 query shapes, 255 checks) and found the minimumShouldMatch >= 2 hit loss (361 missing documents, all valued -Infinity). Three minimal checks then mapped it across releases, and a 2026-10-29 minimization cut it to the two-document test above.

History

#

Introduced in 8.0.0 by LUCENE-7996 (a8a63464e7d, 2017), which forbade negative scores but did not clamp this scorer. The hit loss arrived with #14021 (10.1.0) and widened to dense top-level queries with #16176 (10.5.0). Unchanged on main, branch_11x and 10.6.0.

Versions tested7 rows

Introduced by a8a63464e7da63b3dbc884634fd0e00b3f0c140b, LUCENE-7996 "Queries are now required to produce positive scores." (Adrien Grand, 2017-12-06; a JIRA patch, now GitHub issue #9044; first release 8.0.0). It made negative scores illegal and clamped FunctionQuery, BoostedQuery and FunctionScoreQuery, but not ValueSourceScorer. score() itself dates from LUCENE-6720 (13f8ab93a97 / 88d137632d3, 2015, release 5.4.0), when negative scores were legal and FunctionQuery scored the same way.

The hit loss needs WANDScorer's per-candidate score check from #14021 "Make WANDScorer compute scores on the fly" (Adrien Grand, 2024-11-26; main d9aa525c9ea, release line 3f620dcd34f, first released in 10.1.0); before it, matches() compared the sum of max scores. #16176 "Restore WANDScorer for TOP_SCORES + minShouldMatch > 1" (Tianxiao Wei, 2026-06-03; main 135b348b370, release line 4f720f944b8, first released in 10.5.0) sent dense top-level queries, which 10.1.0 to 10.4.0 ran on BooleanScorer, to WANDScorer too.

#13939 (10.1.0) moved the score >= 0 assertion from core TopScoreDocCollector into the test framework, so since 10.1.0 a plain search with assertions on no longer throws in the collector on a negative score (WANDScorer still asserts on the scores it scales).

LFV-406, snapshot of 2026-11-08

Registry title
FunctionRangeQuery scores a document with its raw, possibly negative, function value although LUCENE-7996 forbids negative scores and FunctionQuery over the same source clamps them to 0; since 10.1.0 a matching document whose value is -Infinity can then disappear from the top-k results of a minimumShouldMatch >= 2 BooleanQuery
Area
queries / function queries (ValueSourceScorer behind FunctionRangeQuery, LUCENE-7996 non-negative score rule; the hit loss surfaces in core WANDScorer)
Priority
Low, rank 726: FunctionRangeQuery scores with raw negative values despite LUCENE-7996, and it loses a hit only for a stored -Infinity under minimumShouldMatch >= 2, the same negative-score bound profile as LFV-203.
Impact class
silent wrong results
Impact note
Applications that score with lucene/queries FunctionRangeQuery (not wrapped in a FILTER clause or ConstantScoreQuery) over a field that can hold negative values get negative scores in TopDocs and explain, and a document that also matches the function clause can rank below one that matches only the other clause; when the field holds -Infinity (scored -Float.MAX_VALUE; by code reading also finite values at or below about -4e31) and the range admits it, a FunctionRangeQuery SHOULD clause of a minimumShouldMatch >= 2 BooleanQuery makes top-k search silently leave that matching document out and report an exact total hit count that is too low while count() includes it (executed with -da on 10.1.0, 10.4.0, 10.5.2 and main; on 10.1.0 to 10.4.0 only when the query takes the WANDScorer path, i.e. sparse SHOULD clauses or a nested query, and since 10.5.0 also for dense top-level queries), and with -ea that path throws AssertionError in WANDScorer, as plain -ea top-k searches did in core TopScoreDocCollector on 8.0.0 to 10.0.0; match sets of count(), FILTER/MUST_NOT/ConstantScoreQuery uses and every other document are unaffected; default IndexWriterConfig, codec and searcher, four to 100 documents suffice; released since 8.0.0.
Summary
You index a document with DoubleDocValuesField("d", -5.0) and search new FunctionRangeQuery(new DoubleFieldSource("d"), -10.0, 10.0, true, true), expecting a non-negative score, because since LUCENE-7996 (8.0) scorers must not produce negative scores and FunctionQuery over the same source scores that document 0. Instead it scores -5.0 (-Infinity and NaN become -Float.MAX_VALUE), because ValueSourceScorer.score() returns the raw value and LUCENE-7996 clamped FunctionQuery, BoostedQuery and FunctionScoreQuery but not this scorer. Since 10.1.0 this also loses hits: with minimumNumberShouldMatch = 2 over SHOULD clauses FunctionRangeQuery(d, open range), body:a and body:b (sparse term clauses; also dense ones since 10.5.0), a matching document whose value is -Infinity is missing from search(q, 10), whose totalHits says '3 hits' while count(q) is 4, because WANDScorer rejects a candidate whose scaled score is below the initial minimum competitive score of 0.
