ConcatenateGraphFilter's maxGraphExpansions javadoc promises an exception, but extra paths are silently dropped (and CompletionAnalyzer's "no limit" is 10000)

The javadoc says ConcatenateGraphFilter throws TooComplexToDeterminizeException above maxGraphExpansions paths, but the code keeps the first maxGraphExpansions paths and silently drops the rest; CompletionAnalyzer's "no limit" constructors cap at 10000. That truncation is intended, so the javadoc needs fixing, not the code.

The finding in 30 seconds

#

maxGraphExpansions is used twice in the code, and neither use matches the javadoc: it caps how many paths are emitted, and it is the determinize work limit.

Background: token graphs and paths

#
  1. A synonym filter can put two tokens at one position, for example wifi and wireless. The token stream is then a graph with 2 paths.
  2. ConcatenateGraphFilter joins each path into one token: wifi network, wireless network. The document suggester's CompletionAnalyzer uses it to index completions.
  3. Paths multiply: two positions with two choices each give 4 paths, fourteen give 16384. maxGraphExpansions (default 10000) bounds this.

The finding, step by step

#
  1. You wrap a synonym graph (a|b) (c|d), which has 4 paths, in new ConcatenateGraphFilter(graph, true, true, 3). The javadoc says: more than 3 paths, so TooComplexToDeterminizeException.
  2. You get 3 concatenated tokens, a␟c, a␟d and b␟c (␟ is the separator), and no exception. The fourth path, b␟d, is silently dropped (which one is dropped follows an iteration order the API leaves unspecified).
  3. The same 3 is also the work limit for determinizing the graph. So a value with only 2 paths, wifi network adapter for laptops with the synonym wifi -> wireless (32 characters), throws at limit 3. A longer value of the same wifi|wireless shape first throws at 94 characters at limit 10 and at 994 at limit 100.
  4. new CompletionAnalyzer(analyzer) is documented as "no limit on graph expansions". A 14-word value where every word has a synonym has 16384 paths; you get 10000 of them.
  5. Keeping the first N is the suggester's deliberate design (LUCENE-4971), so the fix is to describe it in the javadoc.

Who is affected

#

Users of ConcatenateGraphFilter (or the concatenateGraph factory) and of the document suggester's CompletionAnalyzer who trust the javadoc; both are opt-in and experimental. At the default 10000, truncation needs over 10000 paths in one value. With a small explicit limit, extra paths vanish silently and long values can be rejected. The recorded indexing probe saw no corruption and no hang.

Mechanism, terms and numbers728 words

ConcatenateGraphFilter turns a token graph (for example the output of a synonym filter) into one concatenated token per path; the document suggester's CompletionAnalyzer uses it to index completions. Its 4-argument constructors and ConcatenateGraphFilterFactory document maxGraphExpansions as "If the tokenStream graph has more than this many possible paths through, then we'll throw TooComplexToDeterminizeException". The code never counts the total number of paths in the graph. It reads the paths through LimitedFiniteStringsIterator, which by its own javadoc returns "the first limit strings found", so extra paths are dropped without any signal: a 4-path graph at limit 3 gives 3 tokens. It also passes the same value to Operations.determinize as its work limit (an effort budget of 10 x the value), so a 2-path graph whose alternatives share a prefix throws once the input is long enough (in the probe's wifi|wireless shape, from 94 characters at limit 10 and 994 at limit 100). CompletionAnalyzer(Analyzer) and CompletionAnalyzer(Analyzer, boolean, boolean) say "no limit on graph expansions" but pass DEFAULT_MAX_GRAPH_EXPANSIONS = 10000: a value with 16384 paths gets 10000. Keeping the first N is a deliberate design (LUCENE-4971), so this is a documentation defect: the fix is a javadoc-only change in three files, validated on main. The filter and factory text dates from 7.4.0, the CompletionAnalyzer text has been stale since 5.3.0, and nobody has reported either.

The text (main 645d4fe14a20)

#
  • ConcatenateGraphFilter.java:106-110: @param maxGraphExpansions If the tokenStream graph has more than this many possible paths through, then we'll throw {@link TooComplexToDeterminizeException} to preserve the stability and memory of the machine. and @throws TooComplexToDeterminizeException if the tokenStream graph has more than {@code maxGraphExpansions} expansions. The boolean constructor (:126-143) "Calls" this one.
  • ConcatenateGraphFilterFactory.java:35-37: the same sentence; the factory passes any integer through (:62-63, :77-78).
  • CompletionAnalyzer.java:90-93 and :102-105: "... no limit on graph expansions"; both constructors pass ConcatenateGraphFilter.DEFAULT_MAX_GRAPH_EXPANSIONS (:99, :112), which is Operations.DEFAULT_DETERMINIZE_WORK_LIMIT (ConcatenateGraphFilter.java:61) = 10000 (Operations.java:63). The private field doc says "Defaults to -1 (no limit)" (:62-67).

Use 1: a silent cap on emitted paths

#

incrementToken() builds the automaton and wraps it: finiteStrings = new LimitedFiniteStringsIterator(automaton, maxGraphExpansions); (ConcatenateGraphFilter.java:163-166). LimitedFiniteStringsIterator.next() returns null once count >= limit ("Abort on limit.", LimitedFiniteStringsIterator.java:57-61), as its class javadoc documents: "If more than limit strings are accepted, the first limit strings found are returned" (:21-23). incrementToken() then returns false (ConcatenateGraphFilter.java:172-175). No exception, no flag. The only count is the iterator's count of the strings it has returned (LimitedFiniteStringsIterator.java:36-37, :65); since the automaton is determinized first, these are distinct accepted strings (FiniteStringsIterator.java:33), so strictly the cap is on distinct concatenated strings, which can be fewer than the graph's paths when two paths concatenate to the same bytes. For (a|b) (c|d) at limit 3 the tokens are a␟c, a␟d, b␟c (␟ = the separator byte) on this build; which paths come first is not an API guarantee ("the iteration order is implementation dependent and may change across releases", LimitedFiniteStringsIterator.java:28).

Use 2: the determinize work limit

#

toAutomaton() ends with return Operations.determinize(automaton, maxGraphExpansions); (ConcatenateGraphFilter.java:249-250). determinize returns a deterministic automaton unchanged (Operations.java:654-657); otherwise it adds up "effort" (the size of each state set it visits) against effortLimit = workLimit * 10 (:695) and throws TooComplexToDeterminizeException when it reaches it (:707-709). Its own javadoc calls the argument a "Maximum amount of \"work\"" (:645-651), not a path count.

A 2-path graph whose alternatives start with the same bytes (wifi / wireless) is not deterministic, and its effort grows with the input length. In the intended-behaviour check probe (wifi with the synonym wireless, lengthened with short filler words) the first throw came at 43, 94, 193, 493, 994 and 9994 characters for limits 5, 10, 20, 50, 100 and 1000, roughly 10 x the limit for that shape (a measurement, not a general rule); at 10000 the filter did not throw up to 60,004 bytes (one term that long is over IndexWriter.MAX_TERM_LENGTH, 32766 bytes, anyway). The (a|b) (c|d) graph is already deterministic, so use 2 never fires for it (4 tokens at limits 4 and 100, 3 at limit 3).

No code path counts the total number of paths and throws when it is above maxGraphExpansions.

Exposure and likelihood245 words
  • Who. Users of ConcatenateGraphFilter (directly, or as the concatenateGraph SPI factory) and of the document suggester (CompletionAnalyzer behind SuggestField / ContextSuggestField). Both classes are @lucene.experimental.
  • At the default (10000). Truncation needs more than 10000 paths in one value, for example 14 positions that each carry a synonym (10000 of 16384 kept). The determinize throw needs a very large automaton. A single value did not throw in the filter up to 60,004 bytes, but one term that long could not be indexed anyway (IndexWriter.MAX_TERM_LENGTH is 32766 bytes). The realistic case is many contexts: about 1000 shared-prefix contexts on one ContextSuggestField (about 104 KB of contexts) throw; about 54 KB pass.
  • With a small explicit limit. Paths beyond the limit vanish silently (fewer suggestions than the analyzer produced), and a long enough value with a shared-prefix alternative is rejected although it has fewer paths than the limit (in the intended-behaviour check probe's wifi|wireless shape: from 94 characters at limit 10, from 994 at limit 100).
  • Effect. Silently missing completions, or one document rejected with a non-aborting exception. In the recorded indexing probe only that document fails, the IndexWriter stays open and records no tragic exception, the next document indexes, and the index passes the test framework's CheckIndex on close: no corruption and no hang for that input (not a proof for every input).
  • Scale. Every release since 7.4.0 (filter and factory text) and since 5.3.0 (CompletionAnalyzer text); unreported in that time.

Why it looks unintended

#
  • The @param text defines the value only as a path count and promises an exception above it; the code drops paths.
  • CompletionAnalyzer's "no limit on graph expansions" has been false since 5.3.0 changed the default from -1 to 10000.
  • The text was written for moved code that already truncated; no Lucene test checks a graph over the limit.
The full argument209 words
  • The @param sentence is a definition, not a side remark. It describes the value only as a path count past which the filter throws. Both it and the @throws say "more than N paths, then an exception"; the truncation (4 paths, limit 3, no exception) breaks that under any reading, including reading @throws X if C as a sufficient condition only. The below-the-limit determinize throw is weaker evidence: read as a sufficient condition, the text does not forbid a throw with fewer paths; it counts only because the text never says the value is also a work limit.
  • CompletionAnalyzer. "no limit on graph expansions" was true in 5.1.0 and 5.2.1 (default -1: 16384 of 16384 paths kept). LUCENE-6459 (#7518) changed the default to 10000 in 5.3.0 without touching the javadoc (10000 of 16384 from 5.3.0 on).
  • History. LUCENE-8332 (#9379, 7.4.0) moved the logic of CompletionTokenStream, which already used LimitedFiniteStringsIterator(automaton, maxGraphExpansions) and determinize(automaton, maxGraphExpansions), into the new public ConcatenateGraphFilter and wrote the throw-above-N text for it. The issue's 13 comments and the 18 review comments on lucene-solr#384 never discuss what the parameter means.
  • Tests. TestConcatenateGraphFilter.testValidNumberOfExpansions checks a graph under the limit (256 paths at the default). No test in analysis-common or suggest/document builds a graph over the limit.
The devil's-advocate check168 words

Strongest case that this is intended (the cross-model review, the intended-behaviour check and the adjudication): keeping the first N is a committer decision. On LUCENE-4971 (#6035) Mike McCandless wrote "I'd lean towards returning the first N after the limit is hit; this way at least some expansions are indexed", and Robert Muir answered "+1, the new semantics for the getFiniteStrings seem more useful to me anyway". LimitedFiniteStringsIterator documents the cap; reusing the value for determinize dates from LUCENE-6339; @throws X if C can be read as a sufficient condition only; both classes are @lucene.experimental; the "-1 (no limit)" text sits on a private field.

Why it fails: every point argues that the code is right, which is exactly why the javadoc should change. None makes the public @param text or the public "no limit" constructor docs true. The verifier who built this case concluded that it strengthens the documentation defect instead of refuting it. So this page claims only the javadoc, not a "should throw" behaviour bug.

Separately: decouple the determinize work limit (behaviour change, not run)

#

Determinize with Operations.DEFAULT_DETERMINIZE_WORK_LIMIT (or a separate parameter) instead of maxGraphExpansions, so the value means only "number of paths".

Trade-offs

Inputs rejected today under a small limit would be indexed, and determinize could use more memory under a small limit. The adjudication and the audit kept it separate from the docs fix.

Make the code throw past the limit (not recommended, not run)

#

Iterate with limit + 1 and throw when the extra path appears, matching the current text.

Trade-offs

Reverses the LUCENE-4971 decision ("at least some expansions are indexed"), starts rejecting documents that index today, and needs a migration note.

Regression test (optional)

#

None is needed for a javadoc change. If a reviewer wants the documented behaviour pinned, use the same minimal test with its expectation flipped (same graph, same limit: assert 3 tokens and no exception); it passes on the patched build, whose code is that of main. Lucene has no test today for a graph over the limit.

Trade-offs

Pins behaviour that LUCENE-4971 chose, so a later deliberate change would have to update it.

Downstream note

How it was found

#

A semi-formal check: the stock main jar was compared with the javadoc on every small synonym graph, and 42,440 of 129,060 checks expected the exception but got truncation. A directed probe on longer shared-prefix values found the opposite direction, and a cross-model reviewer pointed to CompletionAnalyzer's "no limit" text.

The method in full109 words
  • Translation validation. Every token graph with at least 2 paths over a 6-letter alphabet and up to 3 slots, with maxGraphExpansions = paths - 1, paths and paths + 1; expected (from the javadoc): throw if and only if paths > limit, else all paths. 129,060 checks; 42,440 in the bucket "expected throw, got truncated to limit".
  • Directed probe. Longer shared-prefix synonym values showed the throw below the limit (the determinize work limit).
  • Review. The cross-model reviewer (OpenAI GPT-5.6) pointed to the CompletionAnalyzer "no limit" javadoc; all three facets were then shown by a public-API JUnit on the stock main jar.
  • Tier. Semi-formal (bounded-exhaustive checking against the documented contract).

LFV-536, snapshot of 2026-11-02

Registry title
ConcatenateGraphFilter, its factory and CompletionAnalyzer misdocument maxGraphExpansions: the javadoc promises a TooComplexToDeterminizeException when the token graph has more than maxGraphExpansions paths (and 'no limit on graph expansions' for CompletionAnalyzer's 1- and 3-argument constructors), but the code silently keeps the first maxGraphExpansions paths (default 10000) and also uses the same value as the determinize work limit, so it can throw for a graph with fewer paths than the limit (documentation defect; the truncation is intended)
Area
analysis-common / ConcatenateGraphFilter and ConcatenateGraphFilterFactory (maxGraphExpansions javadoc); also suggest / CompletionAnalyzer
Priority
Low, rank 968: The maxGraphExpansions javadoc promises an exception where the code silently truncates paths, a documentation defect that misleads only users who rely on it.
Impact class
minor
Impact note
Documentation only; the code behaviour is the suggester's intended design and the fix changes no behaviour. Hit are users of ConcatenateGraphFilter (constructor or the concatenateGraph factory) or of the document suggester's CompletionAnalyzer who rely on the javadoc: where it promises an exception (or no limit), they silently get only the first maxGraphExpansions concatenated tokens, which at the default 10000 needs a value with more than 10000 paths (for example 14 positions that each carry a synonym: 10000 of 16384 kept), and with a small explicit limit a value of about 10 x limit bytes that has a shared-prefix alternative is rejected with a non-aborting, per-document TooComplexToDeterminizeException (limit 10: about 94 chars; limit 100: about 994 chars) although it has fewer paths than the limit; at the default limit that throw needs about 100 KB of automaton (for example 1000 shared-prefix contexts on a ContextSuggestField); no corruption, no hang, the writer stays open; same behaviour in every release since 5.3.0 (CompletionAnalyzer) and 7.4.0 (ConcatenateGraphFilter).
Summary
You set maxGraphExpansions on ConcatenateGraphFilter (or its factory), or use CompletionAnalyzer's 1- or 3-argument constructor, and expect what the javadoc says: a TooComplexToDeterminizeException when the token graph has more than that many paths, and, for CompletionAnalyzer, no limit at all. Instead the filter silently emits only the first maxGraphExpansions paths (a 4-path synonym graph at limit 3 gives 3 tokens and no error; CompletionAnalyzer keeps 10000 of 16384 paths), and because the same number is also passed to determinize as its work limit, a 2-path graph at limit 3 throws. Silent truncation is the suggester's deliberate design (LUCENE-4971), so the fix is to correct the javadoc, not the code.
