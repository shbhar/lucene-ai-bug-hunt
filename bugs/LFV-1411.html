Bulk stored-fields merge checks a copied chunk against the merging format's maxDocsPerChunk

A custom stored-fields format with a lower maxDocsPerChunk (same CompressionMode instance and chunk size) that bulk-merges older segments checks each copied dirty chunk against its own limit: under -ea, a chunk holding that many docs or more makes forceMerge throw AssertionError and closes the IndexWriter. Since 8.9.0; -da merges succeed.

The finding in 30 seconds

#

A merge can copy a segment's compressed stored-fields chunks unchanged. While copying, it asserts that each incomplete chunk holds fewer docs than the merging writer's limit. But the chunk obeys the limit of the writer that made it: limit 2 made a 1-doc dirty chunk; with limit 1 the check is 1 < 1, which fails.

Background

#
  1. Stored fields are compressed in chunks. A chunk is written when it reaches chunkSize bytes or maxDocsPerChunk docs, both parameters of the public Lucene90CompressingStoredFieldsFormat.
  2. At the end of a segment the leftover docs are flushed early; that chunk is marked "dirty" (incomplete), so it has fewer docs than its writer's limit.
  3. A merge copies a segment's chunks without recompressing them ("bulk merge") when, among other checks (none of them about maxDocsPerChunk), the compression mode object and the chunk size match, there are no deletions and the segment is not too dirty.

The finding, step by step

#
  1. Index two documents, one commit each, with a stored-fields format that allows 2 docs per chunk (FastCompressingCodec(16384, 2)). Each segment's only chunk holds 1 doc and is flushed before it is full, so it is marked "dirty" (incomplete).
  2. Reopen the index with the same format but maxDocsPerChunk = 1 (same compression mode and chunk size) and call forceMerge(1). The writer sees a matching segment and copies its chunks unchanged (a bulk copy).
  3. You expect the merge to succeed: the format allows a different limit, and the copy itself is correct (with assertions off every document reads back).
  4. Instead, with -ea, the copy asserts bufferedDocs < maxDocsPerChunk for each dirty chunk, using the new limit: 1 < 1 is false, AssertionError at copyChunks:584.
  5. The IndexWriter treats it as tragic and closes: uncommitted changes are lost, and every later writer with this setup fails the same way on those segments.

Who is affected

#

Applications with a custom stored-fields format on Lucene90CompressingStoredFieldsFormat that lower maxDocsPerChunk but keep the compression mode instance and chunk size, and run with assertions on, so it can affect test suites. The source can be the default codec. No trigger with the stock codecs alone was found; in every executed -da run the merge was correct.

Mechanism, terms and numbers517 words

Lucene90CompressingStoredFieldsWriter.copyChunks bulk-copies a source segment's compressed chunks during a merge and, for every incomplete ("dirty") chunk, asserts bufferedDocs < maxDocsPerChunk (:584). bufferedDocs is the source chunk's doc count, bounded by the limit of the format that wrote it; maxDocsPerChunk is the merging writer's own limit, which getMergeStrategy never compares because it is not stored in the segment. So a format with a lower maxDocsPerChunk (same CompressionMode instance and chunk size) that bulk-merges an older segment trips the assert on every copied dirty chunk holding at least the new limit of docs: two one-doc segments written with limit 2 and merged with limit 1 give AssertionError, and the IndexWriter closes as a tragic event. With -da the same bulk copy is correct. No trigger with the stock codecs alone was found; it can affect the -ea test suites of applications with custom stored-fields formats, in every release since 8.9.0.

The bug (main f794ff5a505c)

#
  1. Dirty chunks. triggerFlush writes a chunk at chunkSize bytes or maxDocsPerChunk docs (Lucene90CompressingStoredFieldsWriter.java:227-231). finish force-flushes the leftover docs (:473-476); a forced flush counts as dirty (:233-238) and sets the dirty flag in the chunk header (value 2: dirtyBit = 2 in (numBufferedDocs << 2) | dirtyBit | slicedBit, :215-218; read back as code & 2, :582). A dirty chunk therefore has fewer docs than the limit of the writer that flushed it; a bulk merge copies it unchanged, so it can end up in a segment whose writer has a lower limit.
  2. BULK is chosen (:681-694) when the source has matching field numbers and is a Lucene90CompressingStoredFieldsReader of the current version (otherwise VISITOR, :681-685), bulk merge is enabled (BULK_MERGE_ENABLED, :688), and the reader has the same CompressionMode object, the same chunk size (stored in the segment, :158), no deletions and is not tooDirty (:660-665: more dirty docs than the target's limit and more than 1% dirty chunks). None of these involves the source's maxDocsPerChunk: it is never written to the segment, so the merge cannot compare it.
  3. The copy (:550-587) reads each source chunk header, bufferedDocs = code >>> 2 (:555), rewrites the header and copies the compressed bytes. For a dirty chunk it asserts bufferedDocs < maxDocsPerChunk (:584) with the target's limit.
  4. The numbers. Source limit 2: each segment has one dirty chunk of 1 doc. Target limit 1: tooDirty is 1 > 1, false, so BULK; the assert is 1 < 1, false.
  5. Tragic close. IndexWriter.merge passes any Throwable from the merge to tragicEvent(t, "merge") (IndexWriter.java:5108-5112): afterwards isOpen() is false and getTragicException() is the AssertionError; uncommitted changes are lost; the last commit stays readable (executed probe).
  6. The copy is right. Reading does not use maxDocsPerChunk. With -da the merged segment holds the bulk-copied dirty chunks, every doc reads back and CheckIndex is clean. Full source chunks larger than the target limit are bulk-copied the same way, with no check (an executed control with -ea passes).
Exposure and likelihood264 words
  • Who can be hit. A custom format (or a FilterCodec around one) that lowers maxDocsPerChunk, for example to make single-document reads cheaper, while keeping the CompressionMode instance and chunk size of the format that wrote existing segments.
  • The source can be the default codec. An executed probe wrote two 512-doc segments with the default codec (BEST_SPEED: 1024 docs per chunk, 80 KB chunks), then merged them with a FilterCodec whose format reuses the public Lucene90StoredFieldsFormat.BEST_SPEED_MODE and 80 KB chunks with 512 docs per chunk, under another format name: -ea fails at copyChunks:584, -da reads all 1024 docs back. (That target codec is anonymous and not registered, so the probe reads back through a near-real-time reader and rolls back instead of committing; an application would register its codec, and getMergeStrategy does not compare names.)
  • Only with -ea, so it can affect test suites. Each writer that merges such a segment fails again: the failed merge leaves the committed segments unchanged.
  • Stock codecs alone: no trigger found. Lucene90StoredFieldsFormat fixes 1024 / 4096 docs per chunk (Lucene90StoredFieldsFormat.java:161, :167, unchanged since 9.0), and its two modes use different CompressionMode objects (:178, :185), so switching modes never bulk-copies.
  • Production (-da): a dirty chunk is copied the same way as a full one and the reader does not use maxDocsPerChunk; in every executed -da run the merge succeeded and all documents read back.
  • Workaround: -Dorg.apache.lucene.codecs.lucene90.compressing.Lucene90CompressingStoredFieldsWriter.enableBulkMerge=false (the escape hatch at :492-506) makes the repro pass with -ea (executed), at the cost of recompressing on every merge.

Why it looks unintended

#
  • The format forbids only same name with different CompressionModes; maxDocsPerChunk is free (>= 1) and not stored in the segment.
  • The writer itself chooses the bulk copy, which is correct; full chunks above the new limit are copied unchecked.
  • The term-vectors sibling has no such assert; #6406 (2013) treated mixing instances as supported.
The full argument298 words
  • The contract. Lucene90CompressingStoredFieldsFormat.java:79-81: "You should never instantiate two Lucene90CompressingStoredFieldsFormats that have the same name but different CompressionModes." maxDocsPerChunk is checked only as >= 1 (:113-115). The repro keeps name and mode; the default-codec probe uses another name.
  • The writer's own choice. getMergeStrategy (Lucene90CompressingStoredFieldsWriter.java:681-694) picks BULK from what the segment records; the assert states an invariant of the format that wrote the chunk, not one the merging writer can rely on.
  • Not a consistent bound check. Full chunks above the target limit are bulk-copied with no check; only dirty chunks are asserted. Lucene90CompressingTermVectorsWriter.java:880-884 does the same dirty-chunk bookkeeping without an assert.
  • Not even equal limits are always safe. An executed two-step probe: a -da bulk merge with limit 1 of two limit-2 segments (201 docs each) leaves two 1-doc dirty chunks; a later -ea merge with the same limit-1 setup fails at :584 and closes the writer.
  • History. The assert came with the per-chunk dirty bit in 9a17d67658b (#134, LUCENE-9935 "Enable bulk merge for stored fields with index sort", 2021-05-12); the review does not discuss it. #6406 (LUCENE-5342, 2013) fixed corrupt segments when bulk-merging instances with different chunk sizes by adding the chunk-size condition, not by forbidding the mix.
  • Tests. No upstream test was found that bulk-merges a segment written with a larger maxDocsPerChunk (read: the core, codecs, backward-codecs and test-framework sources that mention CompressingCodec or maxDocsPerChunk). Only the inherited BaseIndexFileFormatTestCase.testRandomExceptions reopens a writer with a fresh random instance after an aborted writer (:671, :710; TestCompressingStoredFieldsFormat.getCodec() randomizes the limit, :50-57), but it deletes each document right after adding it (:658-660), so its segments carry deletions or are dropped, and a segment with deletions is never bulk-copied (Lucene90CompressingStoredFieldsWriter.java:692). No such upstream failure was found.
The devil's-advocate check161 words

Strongest case for "intended": the javadoc calls maxDocsPerChunk "an upperbound on how many docs may be stored in a single chunk" (Lucene90CompressingStoredFieldsFormat.java:84-86) and "the maximum number of documents in a single chunk" (:95), so a maintainer could say a merged segment must respect the target's bound and the assert caught a real violation.

Why it fails: bulk copies of full chunks already exceed that bound with no check, so the dirty-only assert does not enforce it; the bound's stated purpose is "to bound the cpu costs for highly compressible data" (:85-86), and reading does not depend on it; the merge cannot know the source's limit, because it is not stored. Under either reading, a legal configuration trips an internal assert and closes the writer. The one executed cross-model review that finished rated the intended-behaviour argument weak; a later cross-model review of this page rated it moderate, pointing to the upper-bound wording and the @lucene.experimental status.

Suggested fix

#

Recommended (a) Relax the dirty-chunk assert to bufferedDocs > 0 (recommended, validated)

Relax the assert at Lucene90CompressingStoredFieldsWriter.java:584 to assert bufferedDocs > 0;, with a comment that the chunk was written by the source segment's format. With it the repro passes (assertions on and off) and 7 stored-fields and compressing suites pass (110 tests, 8 skipped, 0 failures).

        if (dirtyChunk) {
          // the chunk was written by the source segment's format, whose maxDocsPerChunk may differ
          assert bufferedDocs > 0;
          ++numDirtyChunks;
          numDirtyDocs += bufferedDocs;

How it was found

#

A semi-formal proof-obligation audit of the stored-fields writer's contract: the dirty-chunk assert in the bulk copy holds only if the source's maxDocsPerChunk is at most the target's, and nothing the merge checks establishes that. A two-writer JUnit on main witnessed it; it was later reduced to two one-doc segments.

The method in full106 words

Semi-formal method: a proof-obligation audit of Lucene90CompressingStoredFieldsWriter's contract, witnessed by an executable repro. The obligation here is the dirty-chunk assert in copyChunks, bufferedDocs < maxDocsPerChunk: it holds only if the source segment's limit is at most the merging writer's, while none of the BULK conditions in getMergeStrategy (reader type and version, matching field numbers, the bulk-merge switch, the CompressionMode object, the chunk size, deletions, dirtiness) involves maxDocsPerChunk. Summary
An application indexes with a stored-fields format built on the public Lucene90CompressingStoredFieldsFormat, later reopens the index with a format that keeps the same CompressionMode and chunk size but a smaller maxDocsPerChunk, and merges. The merge should succeed: the format forbids only varying the CompressionMode under one name, the writer itself picks a raw chunk-by-chunk (bulk) copy for such a segment, and that copy is correct.
