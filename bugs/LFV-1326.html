Util.TopNSearcher reports isComplete = true after its bounded queue dropped a result (int overflow)

Ask Util.TopNSearcher for every result (topN = Integer.MAX_VALUE) with a small queue and an acceptResult that rejects one path, and isComplete says true although the queue dropped an accepted result: rejectCount + topN overflows int. Only this flag is wrong; Lucene's own code reads it only in assertions.

The finding in 30 seconds

#

isComplete should be true only when the bounded queue was big enough to find every result. The check adds the number of rejected paths to topN in int; with topN = Integer.MAX_VALUE and one rejection the sum wraps negative, so the check passes even when the queue lost results.

Background: what TopNSearcher and isComplete do

#
  1. Util.TopNSearcher walks an FST best-first and returns the topN lowest-cost keys; several of Lucene's FST suggesters are built on it.
  2. To bound memory it keeps at most maxQueueDepth candidate paths; once the queue is full, a worse path is dropped.
  3. A subclass can override acceptResult to reject finished paths (for example duplicates). Rejections are counted in rejectCount, and the completeness check budgets one queue slot for each.
  4. TopResults.isComplete says whether the queue was large enough. If it is false, the caller can retry with a bigger queue.

The finding, step by step

#
  1. Build an FST with two keys, a -> 1 and b -> 2. Search it with a TopNSearcher that asks for every result (topN = Integer.MAX_VALUE), keeps a queue of depth 1, and has an acceptResult that rejects a.
  2. The depth-1 queue keeps only the better path, a, and drops b. Then a is rejected (rejectCount = 1), so the result list is empty.
  3. You expect isComplete == false: the queue was too small and lost b, which would have been accepted. With topN = Integer.MAX_VALUE - 1 the same search does say false.
  4. Instead isComplete == true, with assertions on or off: 1 + 2147483647 wraps to -2147483648 in int, and -2147483648 <= 1. A caller that retries with a bigger queue when the flag is false never retries.

Who is affected

#

Only code that calls the experimental Util.TopNSearcher directly, rejects something in acceptResult, asks for topN = Integer.MAX_VALUE with a smaller queue, and trusts isComplete. It gets "complete" for a truncated list and never retries. Lucene's own code reads the flag only in assertions, or not at all.

Mechanism, terms and numbers471 words

Util.TopNSearcher finds the lowest-cost paths of an FST with a queue of at most maxQueueDepth candidates and reports in TopResults.isComplete whether that queue was large enough. search() computes the flag as rejectCount + topN <= maxQueueDepth in int (Util.java:409), where rejectCount counts finished paths that the acceptResult hook rejected.

When a caller asks for every result, topN = Integer.MAX_VALUE, and the hook rejects one path, the sum wraps to Integer.MIN_VALUE and the flag reads true even when the queue dropped an accepted result: in the repro, FST {a -> 1, b -> 2}, depth 1, a rejected, the list is empty and isComplete is true. Nothing throws, assertions on or off, in every release since 4.8.0. Only direct callers of this experimental API are hit; Lucene's own code reads the flag only in assertions, or not at all. The fix computes the sum in long.

Around the repro

#
  • Same FST and hook, a grid of (topN, maxQueueDepth): true only for (MAX, 1) and (MAX, MAX); false for (MAX - 1, 1), (1000, 1), (1000, 2) and (1000, 1000). With the long sum all six are false.

Why it looks unintended

#
  • Javadoc: isComplete is "true iff ... the specified queue size was large enough to find the complete list of results". Here the queue dropped b.
  • TestFSTs.testRejectNoLimits comments read it as plain arithmetic: "rejected(4) + topN(2) > maxQueueSize(5)" means false; so does 1 + 2147483647 > 1.
  • The flag exists for queues smaller than needed (LUCENE-5519); nothing limits topN.
The full argument283 words
  • The contract. TopResults.isComplete: "true iff this is a complete result ie. if the specified queue size was large enough to find the complete list of results. This might be false if the TopNSearcher rejected too many results" (Util.java:434-437). Rejections are documented to push the flag toward false, never toward true.
  • The tested meaning. TestFSTs.testRejectNoLimits: assertTrue(res.isComplete); // rejected(4) + topN(2) <= maxQueueSize(6) and assertFalse(res.isComplete); // rejected(4) + topN(2) > maxQueueSize(5) (TestFSTs.java:1390, :1412).
  • Why the flag exists. LUCENE-5519 (#6582, 4.8.0) replaced an assertion that fired when rejections left the queue too small for topN with this flag, so the queue can be bounded below what is needed. Its CHANGES entry: "The queue can still be bound in order to apply pruning ... The TopNSearcher now returns a struct like class that indicates if the result is complete in the sense of the top N or not" (lucene/CHANGES.txt:12556-12562). In that issue Michael McCandless asked for the name isComplete: "it returns true if no truncation happened". The constructors document topN and maxQueueDepth with no bound or relation (Util.java:185-186).
  • Other callers do this arithmetic with care. FreeTextSuggester sizes its queue for rejections as num + seen.size() "because we may reject up to seen.size() paths in acceptResult()" (FreeTextSuggester.java:604-608; a plain int sum, so rejection budgeting, not an overflow guard); NRTSuggester computes its queue size in long and clamps it (NRTSuggester.java:294, :301).
  • History is consistent with an oversight (an inference; no record states intent): the same int sum was first an internal assert ("maxQueueDepth (...) is too small for topN", LUCENE-4481, 2012); LUCENE-5519 turned it into the public value as is.
The devil's-advocate check160 words

The strongest case for "intended": Util is @lucene.experimental; isComplete is a conservative capacity test, not an exact completeness check (it already says false for (1000, 1000) with nothing dropped); and asking for Integer.MAX_VALUE results with a depth-1 queue is an odd request.

Why it fails: @lucene.experimental allows API changes, not wrong values. A conservative test may say false when the result is in fact complete; it must not say true when an accepted result was dropped, and this error is in the unsafe direction. Integer.MAX_VALUE is an obvious way to ask for all results, and a queue smaller than topN is the very mode the flag exists for. The cross-model review passes and the intended-behaviour check rated the argument weak; a later cross-model fact check of the brief rated it moderate, since the flag already fails a literal "iff" and the long-sum fix adds conservative false answers at the boundary, so a maintainer could close it as won't-fix.

Suggested fix

#

Recommended Compute the sum in long (one token)

Compute the sum in long: (long) rejectCount + topN <= maxQueueDepth (Util.java:409). The repro, the core FST tests and the suggest module pass. Caveat: where the sum wraps with nothing dropped, the flag becomes a conservative false; on its own this trips an AnalyzingSuggester assertion for num = Integer.MAX_VALUE (assertions on), so fix the separate LFV-1003 too.

-      return new TopResults<>(rejectCount + topN <= maxQueueDepth, results);
+      return new TopResults<>((long) rejectCount + topN <= maxQueueDepth, results);

Compute the sum in long (one token) (validated by the checks) (recommended)

#

At Util.java:409, widen the sum so it cannot wrap.

-      return new TopResults<>(rejectCount + topN <= maxQueueDepth, results);
+      return new TopResults<>((long) rejectCount + topN <= maxQueueDepth, results);

Trade-offs

  • Restores the formula's own arithmetic for every input; no API change; inputs that do not wrap give the same answer as today.
  • The formula is conservative, and so is the fix: where the sum wraps although nothing was dropped, today's wrapped true happens to be right and becomes false, the answer the formula already gives for (1000, 1000); for example topN = maxQueueDepth = Integer.MAX_VALUE with one rejection (an independent reviewer pointed this out). It does not make the flag an exact completeness test.
  • This fix alone changes one in-tree assertion. With only the long sum applied to main and the assertions on, AnalyzingSuggester.lookup("nellie", false, Integer.MAX_VALUE) (the analyzer and inputs of the existing TestAnalyzingSuggester.testDupSurfaceFormsMissingResults: two analyzed paths per input, so duplicate surface forms are rejected) goes from passing to an AssertionError at assert completions.isComplete (AnalyzingSuggester.java:824). Its queue depth num * maxAnalyzedPathsForOneInput = 2 * Integer.MAX_VALUE already wraps to -2 today (the separate LFV-1003; a negative depth never fills, so nothing is dropped), and today's wrapped sum is <= -2 and hides that; the long sum is not. With the assertions off, main and the fix both return [hambone/6, nellie/5]. So the fix belongs together with a fix for LFV-1003 [exec: an independent fact check's probe on main, without and with the fix].

Same check without widening: rejectCount <= maxQueueDepth - topN

#

Not run. Equivalent to the long sum when topN and maxQueueDepth are non-negative, since the difference cannot overflow then.

Trade-offs

Same conservative false as the long sum. A negative maxQueueDepth, which the separate LFV-1003 overflow can pass in, makes the difference wrap again, so the long sum is the safer form.

Record whether the queue really dropped a path

#

Not built. Set a flag when addIfCompetitive drops a path (:215-233, :248-249) and when search() stops using the queue for the last path (:340-343), and report isComplete = !pruned || (long) rejectCount + topN <= maxQueueDepth.

Trade-offs

Could match the javadoc's "iff" more closely (no conservative false when nothing was dropped), but it is an unbuilt sketch: a patch must define which drops count (paths that acceptPartialPath filters out at :246, :329, :403 are not capacity drops), it touches the search loop, and it needs its own tests; a bigger change than the bug calls for.

How it was found

#

A semi-formal proof-obligation check of TopNSearcher's contract: isComplete may be true only when the bounded queue was large enough to find every result. Checking that obligation against the int arithmetic of the return statement showed it breaks when the sum wraps, and a one-method public-API test then witnessed it on main.

The method in full113 words

Method: semi-formal proof-obligation check, witnessed by an executable repro (2026-11-04, main 5adff78bb168).

  • The obligation: TopResults.isComplete may be true only if the bounded queue was large enough to find the complete list of results (the javadoc at Util.java:434-437).
  • What the check found: the return statement discharges the obligation with rejectCount + topN <= maxQueueDepth, which holds as intended in mathematical integers but is evaluated in int, where the sum wraps for topN near Integer.MAX_VALUE.
  • The finding was then witnessed by the one-method JUnit test and a small (topN, depth) probe grid, and confirmed by an independent reproducer, an independent cross-model reviewer and an intended-behaviour devil's advocate (see Independent checks).
