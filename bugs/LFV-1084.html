A throw from IndexWriter's InfoStream as a commit's full flush ends leaves the writer in full-flush mode, so it stops flushing

If IndexWriter's InfoStream throws on the "finishFullFlush" log line that ends a commit's full flush (before the commit point is written), the open writer stays in full-flush mode: it stops flushing (with maxBufferedDocs=2, 10 more documents all stay in memory), and with RAM-based flushing a lone indexer later blocks in addDocument until another thread acts. Affected since 4.0.0.

The finding in 30 seconds

#

When the full flush of a commit, flush() or NRT refresh ends (for a commit: before the commit point is written), DocumentsWriter.finishFullFlush writes a log line and only then switches full-flush mode off. If the log call throws, the switch never happens. The writer stays open, but in that mode it parks every buffer that should be written instead of writing it.

Background

#
  1. Buffers and flushes. IndexWriter collects new documents in in-memory buffers, one per indexing thread. When a buffer reaches maxBufferedDocs documents or the RAM budget, it is flushed: written to disk as a new segment.
  2. Full flush. commit(), flush() and opening an NRT reader flush all buffers at once. While such a full flush runs, a buffer that becomes due is parked instead of flushed; the end of the full flush releases the parked buffers.
  3. Stall control. If buffers being flushed or parked take more than twice the RAM budget, indexing threads wait in addDocument until flushing catches up.
  4. InfoStream. An optional debug log (off by default) that IndexWriter calls at many points. An application can plug in its own implementation or pass any PrintStream.

The finding, step by step

#
  1. Turn on an InfoStream (IndexWriter's debug log, off by default) and set maxBufferedDocs=2, so the writer should flush every 2 documents. Add 1 document and call commit(); the log sink throws once, on the log line that ends the commit's full flush, "finishFullFlush success=true" (before the commit point is written).
  2. commit() throws that exception, as expected. The writer stays open and is not marked broken (getTragicException() is null), so you keep indexing.
  3. Add 10 more documents. You expect at most 1 to be left in memory; instead all 10 are (numRamDocs() = 10), with assertions on and off.
  4. Why: the log call runs before the code that ends the commit's full-flush mode. In that mode Lucene parks every buffer that is due for flushing until the full flush ends, and now it does not end until the next full flush.
  5. With the default RAM-based flushing, a lone indexing thread then blocks in addDocument once about twice the RAM buffer is parked (1 MB buffer: after 1,186 documents, no progress for 15 s). Another thread's commit or refresh clears it (in the executed add-only case nothing was lost); a rollback() or close() ends it by closing the writer.

Who is affected

#

Only applications that turn on IndexWriter's InfoStream (off by default) with a sink that can throw an unchecked exception, when it throws on this one line during a commit, flush or NRT refresh, and that keep using the writer afterwards. The writer then silently ignores its flush settings; a lone indexing thread with no other commits or refreshes stalls.

Mechanism, terms and numbers949 words

prepareCommit(), commit() (unless an earlier prepareCommit() is still pending), flush() and an NRT reader open each run a full flush. DocumentsWriter.flushAllThreads() starts it by calling DocumentsWriterFlushControl.markForFullFlush(), which sets fullFlush = true, and it must end in DocumentsWriter.finishFullFlush(boolean). That method first logs "<thread> finishFullFlush success=" + success to the InfoStream; only then does it call flushControl.finishFullFlush() or abortFullFlushes(), the only code that sets fullFlush back to false (the first passes the flushes parked during the full flush on to be flushed, the second aborts them). Its finally only resets a flag and applies deletes.

If the log call throws a RuntimeException, commit() (or the flush or NRT open) rethrows it, and because IndexWriter treats only an Error as tragic, the writer stays open with getTragicException() == null. But fullFlush stays true. From then on every in-memory segment buffer that becomes due for flushing is checked out and blocked instead of flushed, so maxBufferedDocs and the RAM buffer no longer flush anything. With RAM-based flushing the parked bytes count as flushing, the stall control engages at twice the RAM buffer, and an indexing thread waits in addDocument until another thread's full flush releases the parked buffers, or a rollback() or close() closes the writer.

With assertions off, the next full flush from any thread (commit, refresh, flush(), close()) clears the state; in the executed single-thread, add-only cases no document was lost. With assertions on, that next full flush trips the internal assertion "called DWFC#markForFullFlush() while full flush is still running" and the writer closes. By code reading, an Error from the log call is tragic and closes the writer. The trigger is opt-in and contrived, so the bug is Low priority; calling rollback() after the failed commit avoids it, and the fix is to end the full flush before logging.

The code (main e1faeba08bde)

#
  1. The protocol. The comment in IndexWriter.getReader (IndexWriter.java:572-581) says the full flush "informs the FlushControl (#markForFullFlush()) that it should prevent any new DWPTs from flushing until we are ... done (DocumentsWriter#finishFullFlush(boolean))". The entry points end it in a finally or right after: prepareCommitInternal (IndexWriter.java:3872-3877), getReader (:671, :680) and flush (:4410-4412).
  2. Log before release. DocumentsWriter.finishFullFlush (DocumentsWriter.java:727-745): the infoStream.message("DW", ... + " finishFullFlush success=" + success) call, inside an isEnabled("DW") guard (:729-732), is the first thing the try does; flushControl.finishFullFlush() / abortFullFlushes() follow (:733-739); the finally (:740-744) only sets pendingChangesInCurrentFullFlush = false and calls applyAllDeletes().
  3. The only way out of full-flush mode. DocumentsWriterFlushControl.finishFullFlush() (:661-676) and abortFullFlushes() (:685-692) are the only code that sets fullFlush = false (:672, :689). Parked buffers return to the flush queue only through pruneBlockedQueue (:647-659), which runs in finishFullFlush() (:666-670) and in the next markForFullFlush (:624); abortFullFlushes() and a rollback() abort them instead (abortPendingFlushes, :694-724).
  4. Not tragic. The throw comes from prepareCommitInternal's finally (IndexWriter.java:3872-3877); only the outer catch (Error tragedy) (:3879-3881) records a tragedy. So after a RuntimeException the writer is open and getTragicException() is null.
  5. Every later flush is parked. DocumentsWriterFlushControl.checkout (:261-268): while fullFlush is set, a flush-pending buffer goes to checkoutAndBlock (:408-418, into blockedFlushes), and nextPendingFlush (:452-480) hands out only buffers from the (empty) flush queue during a full flush.
  6. The stall. setFlushPending (:376-387) moves a buffer's bytes from activeBytes to flushBytes, where parked buffers keep them. updateStallState stalls when activeBytes + flushBytes exceeds twice the RAM buffer while activeBytes stays below it (:114-119, :326). DocumentsWriter.preUpdate (DocumentsWriter.java:386-397) then loops maybeFlush(); waitIfStalled(); (DocumentsWriterStallControl.java:61-78, up to 1 s per round), and nothing can flush; only another thread's full flush, rollback() or close() ends it (a closed writer never stalls, :326). With only maxBufferedDocs (RAM flushing disabled) the stall limit is Long.MAX_VALUE (:116-118): an add-only workload does not stall, it buffers without bound. Deletes are never applied while fullFlush is set (DocumentsWriter.java:174-176), and on main (since #16867, 2026-10-30) buffered delete bytes at maxDeleteBytes (1945 MB) also stall indexing during a full flush (:327-329), so there a delete-heavy workload can stall too.
  7. Healing. The next full flush runs markForFullFlush again. With assertions off it moves the parked buffers to the flush queue (:624), flushes them and ends normally (a second commit kept all 11 documents). With assertions on, assert fullFlush == false : "called DWFC#markForFullFlush() while full flush is still running" (:573-574) fails, and as an Error it closes the writer.

Exposure and likelihood307 words
  • Who. Applications that set an InfoStream with IndexWriterConfig.setInfoStream (a new config takes InfoStream.getDefault(), LiveIndexWriterConfig.java:142, which is NO_OUTPUT unless replaced process-wide). The sink must throw an unchecked exception on exactly this line: a custom InfoStream, a PrintStream passed to setInfoStream(PrintStream) whose underlying stream throws an unchecked exception (a PrintStream only turns IOException into its error flag), or a logging bridge set to pass appender failures to the caller. The stock PrintStreamInfoStream and JavaLoggingInfoStream do not throw by themselves.
  • When. During commit(), prepareCommit(), flush() or an NRT open or reopen (all end their full flush here), and the application keeps using the writer after that exception instead of calling rollback().
  • What breaks. The writer stops flushing without any sign: memory grows past maxBufferedDocs or the RAM buffer until some thread runs another full flush. With RAM-based flushing (the default) a lone indexing thread with no other thread to commit, refresh, roll back or close the writer stays blocked in addDocument after about twice the RAM buffer (executed with a 1 MB buffer; about 32 MB with the default 16 MB buffer, by reading). An application that refreshes or commits on another thread is released at the next refresh (no document was lost in the executed add-only cases, assertions off).
  • Scale. None needed: one failed commit and a few documents.
  • How likely. Contrived: an opt-in log, a sink that throws on this one line, and continued use of the writer instead of rollback(); the recorded searches found no outside report since 4.0 (2012). Before 8.8.0 indexing crawls (about one document per second) instead of stopping.
  • Remedy. Calling rollback() after the failed commit (the remedy a maintainer gives in #9738) avoids it: it discards the buffered documents and closes the writer. Continuing to use the open writer is the case this bug is about.

Why it looks unintended

#
  • setMaxBufferedDocs promises "the writer will flush every maxBufferedDocs added documents"; this writer stays open and reports no tragedy, yet stops flushing.
  • Lucene's own tests already inject RuntimeExceptions through InfoStream.message; the public setInfoStream(PrintStream) sets no no-throw rule.
  • The code requires every full flush to end; the log line was put first in 2011 and kept there since.
The full argument323 words
  • The flush contract. setMaxBufferedDocs (LiveIndexWriterConfig.java:213): "When this is set, the writer will flush every maxBufferedDocs added documents." The class javadoc (IndexWriter.java:162-165) names when the writer closes itself: "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself". Here it does not close (getTragicException() is null), so its documented flush behaviour still applies.
  • The code's own invariant. The full flush prevents new DWPTs from flushing "until we are ... done (DocumentsWriter#finishFullFlush(boolean))" (IndexWriter.java:572-581). Here "done" does not come until the next full flush.
  • Lucene's tests. TestIndexWriterExceptions.testExceptionDuringRollback (:1980-2052) throws RuntimeException("BOOM!") from InfoStream.message at the ordinary message "rollback: done finish merges" (IndexWriter.java:2626) or at the test point "rollback before checkpoint", and asserts "even though we hit exception: we are closed, no locks or files held, index in good state" (:2042). testOutOfMemoryErrorRollback (:1150-1166) throws an Error at "startFullFlush". None throws at "finishFullFlush". These tests check cleanup and close after a logging failure, not continued use of an open writer after a failed commit: they show that a throwing InfoStream is a case Lucene already exercises, not a documented contract.
  • The public API. IndexWriterConfig.setInfoStream(PrintStream) (IndexWriterConfig.java:440-446) is public and states no no-throw condition; MIGRATE.md:1147-1148 presents JavaLoggingInfoStream for logging IndexWriter events through java.util.logging, with a Log4j adapter.
  • History. LUCENE-3348 (78d186e081f, 2011) added the log line as the method's first action, when the info stream was a plain PrintStream; the pluggable InfoStream (LUCENE-2621, 7877d1ff072, 2011-11, which also converted this line to infoStream.message("DW", ...)) and its rework in LUCENE-3598 (2011-12) kept the order. The recorded searches found no commit or issue that discusses a throw from it.
  • Precedent. #6053 (LUCENE-4989, 2013): an exception in abortPendingFlushes skipped cleanup and threads hung in waitIfStalled; fixed with a finally (via #6066). #10547 (LUCENE-9508, 2020): "we can't let blocked flushes go unless the full flush is over" (s1monw).
The devil's-advocate check201 words

The intended-lens reviewer (OpenAI GPT-5.6) and the intended-behaviour check built the case for "not a bug": InfoStream, PrintStreamInfoStream and JavaLoggingInfoStream are @lucene.internal, and InfoStream is a "Debugging API" (InfoStream.java:23-29). A sink that throws is abnormal application behaviour; Lucene does not wrap every InfoStream call and promises no strong exception safety after an arbitrary callback RuntimeException. A maintainer may add #9738 (LUCENE-8692): non-tragic exceptions from prepareCommitInternal "might cause documents go missing", and rollback() is the remedy. The cross-model reviewers rated this argument moderate.

Why it fails: the trigger is reachable through the public setInfoStream(PrintStream) overload with a stock PrintStream over a failing OutputStream (executed); Lucene's own tests already inject RuntimeExceptions through InfoStream.message (during rollback); the writer reports itself open and healthy while silently breaking a documented setting; and the fix is a reorder with no measured cost (it moves the message after the release; it does not make the other InfoStream call sites safe). #9738 is about a failed commit losing documents, which the caller sees; here the writer keeps accepting documents and quietly stops flushing them. Still, rollback() after the failed commit is the practical remedy, and a maintainer could reasonably call the fix low-priority hardening.

Suggested fix

#

Recommended End the full flush, then log

End the full flush first, then log: move the "finishFullFlush success=" message after flushControl.finishFullFlush() / abortFullFlushes() (one hunk in DocumentsWriter). commit() still reports the logging failure, but the writer keeps flushing. Validated: the repro and 265 tests in 12 closest suites pass, and so do the core format and lint checks.

      assert setFlushingDeleteQueue(null);
      if (success) {
        // Release the flush lock
        flushControl.finishFullFlush();
      } else {
        flushControl.abortFullFlushes();
      }
      // log only once the full flush has ended: a failing InfoStream must not leave the writer in
      // full-flush mode, where every later flush is blocked
      if (infoStream.isEnabled("DW")) {
        infoStream.message(
            "DW", Thread.currentThread().getName() + " finishFullFlush success=" + success);
      }

Trade-offs

Smallest change. Without a throw the behaviour is identical except the log order: "finishFullFlush success=" now comes after the release (and after a "done stalling flushes" line, if the release logs one). No test keys on this message. With a throw, commit() still fails with the logging exception, but the writer is out of full-flush mode.

Keep the log line first, end the full flush in a finally (validated by the checks)

#

DocumentsWriter.java, +14/-10 (fix-finally.diff): wrap the log call in try { ... } finally { assert setFlushingDeleteQueue(null); finishFullFlush() or abortFullFlushes(); }.

Trade-offs

Keeps the log order and ends the full flush whatever the log call throws, at the cost of one more nesting level. If the release itself also throws, its exception replaces the logging one (ordinary finally semantics).

What the checks validated

  • The minimal test passes with assertions on and off (same gradle run).
  • The same 12 closest suites: 265 tests, 0 failures, 13 skipped; checkGoogleJavaFormat and ecjLintMain pass.

Not recommended: swallow logging failures

#

Catch RuntimeException around the message and ignore it.

Trade-offs

Hides the failure from the caller and would have to be repeated at every sibling site. IndexWriter swallows an InfoStream failure only where it already has a primary exception to report (onTragicEvent adds it to the tragedy as suppressed). Not run.

Downstream note

#

Servers that forward IndexWriter's InfoStream into their own logging are the group to check: if that logging can throw and the writer is kept after a failed commit or refresh, indexing buffers without flushing until the next refresh.

How it was found

#

A fault-injection sweep made each InfoStream call of a small indexing script throw once during a commit, flush or NRT refresh and then retried the call (2,502 cases); in 10 cases the retry failed at this log line. Code reading found why, and the effect was cut down to one small JUnit test.

The method in full152 words

Method: bounded-exhaustive single-fault injection, then code reading (the hunt's "semi-formal" tier).

  • A hunt unit studies retrying a commit after a non-tragic exception from a public callback. Its sweep ran the real lucene-core jar and made the k-th call, for every k, of InfoStream.message or isEnabled (and of other public callbacks) throw once during commit, prepareCommit, DirectoryReader.open(writer), openIfChanged, flush or flushNextBuffer, over 6 configurations, then retried the call.
  • Its message pass with assertions on (2,502 cases) reported RETRYFAIL at DocumentsWriter.finishFullFlush:730 in 10 cases over commit, prepareCommit, flush and NRT open and reopen: the retried call hit "called DWFC#markForFullFlush() while full flush is still running".
  • Code reading then showed the assertions-off consequence (blocked flushes, maxBufferedDocs ignored, the stall); probes confirmed it, and the finder reduced it to a small JUnit test. The independent reproducer wrote its own test; the one-method test used here is a trimmed copy of it.

History

#

LFV-1084, snapshot of 2026-11-08

Registry title
If IndexWriter's InfoStream throws on the 'finishFullFlush' log line of a commit, flush or NRT open, the still-open writer never leaves full-flush mode, so it stops flushing in-memory segments (maxBufferedDocs is ignored) and, with RAM-based flushing, a lone indexing thread later blocks forever in addDocument (every release since 4.0.0)
Area
index / IndexWriter full flush (DocumentsWriter.finishFullFlush, DocumentsWriterFlushControl blocked flushes and stall control)
Priority
Low, rank 811: If the opt-in InfoStream throws on the finishFullFlush log line, the still-open writer stays in full-flush mode and stops flushing in every release since 4.0.0, and since 8.8.0 a lone indexing thread with RAM-based flushing can then block forever in addDocument. The trigger is contrived, no document was lost in the executed cases with assertions off and the next full flush heals it, so it is Low.
Impact class
minor
Impact note
Hits only applications that turn on IndexWriter's InfoStream (off by default) with a sink that can throw an unchecked exception (a custom InfoStream, a PrintStream passed to setInfoStream(PrintStream) whose write throws, or a logging bridge set to pass appender failures to the caller), when it throws on this one line during commit(), prepareCommit(), flush() or an NRT open, and that keep using the writer after that non-tragic exception: the writer then buffers documents without flushing until some thread runs another full flush (with assertions off no document was lost in the executed add-only cases), and an indexer that is the only thread and does not commit or refresh again stalls forever once about twice the RAM buffer is buffered (1 MB buffer: after 1,186 and 15,785 documents in two probes); no scale is needed, and every release from 4.0.0-ALPHA to 10.6.0 and main is affected (the full stop since 8.8.0, earlier releases crawl at about one document per second).
Summary
You enable an InfoStream on an IndexWriter, and the logging sink throws a RuntimeException once, on the message DocumentsWriter.finishFullFlush logs at the end of a commit (prepareCommit, flush() and NRT opens take the same path). You expect commit() to fail with that exception and the writer, which stays open and has no tragic exception, to keep honouring its flush settings ('the writer will flush every maxBufferedDocs added documents'). Instead the log call runs before the code that ends the full flush, so the writer stays in full-flush mode: every in-memory segment that should flush is parked as blocked (10 more adds with maxBufferedDocs=2 leave 10 documents buffered), and with the default RAM-based flushing a thread that keeps indexing without another commit or refresh eventually waits forever in addDocument.
