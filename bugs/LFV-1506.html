The finding in 30 seconds

#

New in 11.0. On branch_11x daa54f2e0cd3 the one test fails 1 of 1, with assertions on and off; on the 10.6.0 release it passes 1 of 1. Introduced by the merged #14668 (commit 0a4a76f0a869, 2025-05-29), a refactor that removed boolean success flags. It is on main and branch_11x, both unreleased.

Background: the one block, in 10.6.0 and on branch_11x

#
  1. IndexWriter buffers deletes and resolves them later, for example at commit(). After resolving, a clean-up (finishApply) releases the segment readers it used. With reader pooling off, that release writes the segment's live docs, the list of its deleted documents, to a .liv file, and that write can fail.
  2. 10.6.0 (IndexWriter.java:6731-6739 at the tag releases/lucene/10.6.0): try (Closeable finalizer = () -> finishApply(segStates, success.get(), delFiles)) { ... delCount = updates.apply(segStates); success.set(true); } (... stands for an assert on the finalizer and two comment lines). The clean-up is a try-with-resources finalizer. If the resolve throws and the clean-up throws too, Java throws the first exception and attaches the second to it as suppressed.
  3. branch_11x (IndexWriter.java:7006-7014 at daa54f2e0cd3; main :7004-7012): try { ... delCount = updates.apply(segStates); } catch (Throwable t) { finishApply(segStates, false, delFiles); throw t; } (... stands for two comment lines). The clean-up is a plain call in the catch block. If it throws, its exception leaves the block and throw t is never reached.

The finding, step by step

#
  1. You create an IndexWriter with setReaderPooling(false) (the default is on) and never open a near-real-time reader from it. You add 1 document with StringField("id", "1") and commit.
  2. You buffer two deletes: deleteDocuments(new Term("id", "1")) and deleteDocuments(new PhraseQuery("id", "1", "2")). A phrase query cannot run on a field without positions, but the writer only finds that out when it resolves the deletes, at the next commit().
  3. At that commit() the delete by query throws IllegalStateException: the first failure. The clean-up after it writes the live docs of segment _0 for the term delete, and the directory cannot create _0_1.liv (think of a full disk): IOException, the second failure.
  4. You expect what 10.6.0 does: commit() throws the IllegalStateException, with the IOException attached as suppressed. On main and branch_11x it throws only java.io.IOException: cannot create _0_1.liv, with no cause and nothing suppressed, and getTragicException() returns that same object.
  5. Nothing else differs: every build fails the call and closes the writer, the directory lists the same 4 files and the last commit keeps its 1 document. With the default config, after a near-real-time reader, or without the second failure, all three builds throw the IllegalStateException.

Who is affected

#

In every run that shows it: an application on unreleased main or branch_11x that turned reader pooling off, never opened a near-real-time reader from the writer, and hits two failures in one resolve of buffered deletes. Both versions then fail the call and close the writer, and no document, commit or file differs: only the reason is lost. Rare.

Mechanism, terms and numbers1,649 words

IndexWriter resolves buffered deletes and updates later, for example at commit(): IndexWriter.forceApply calls updates.apply(segStates) and then a clean-up, finishApply, which closes the segment states. With reader pooling off, closing a segment state releases its reader and writes the segment's live docs and then its pending doc-values updates (ReaderPool.java:202-205 and :217-218 on main 781025d6fe32), writes that can fail, for example on a full disk.

In 10.6.0 the clean-up ran as a try-with-resources finalizer (IndexWriter.java:6731-6739 at the release tag): when the resolve failed and the clean-up failed too, the first failure was thrown with the clean-up failure attached as suppressed. The merged #14668 (0a4a76f0a869, 2025-05-29), a refactor that removed boolean success flags, made it catch (Throwable t) { finishApply(segStates, false, delFiles); throw t; } (:7006-7014 on branch_11x daa54f2e0cd3, :7004-7012 on main), so an exception from finishApply leaves the catch block before throw t. commit(), flush() and close() then throw only the clean-up failure, getTragicException() returns it and the writer's info stream names it. The first failure is not thrown, not a cause and not suppressed, also when it is a java.lang.Error.

Every run that shows it has three things at once: IndexWriterConfig.setReaderPooling(false) (the default is on), no near-real-time reader ever opened from the writer (that switches pooling on), and two failures in one resolve: the resolve fails, and the clean-up then cannot write what the segment still holds in memory (the live docs of deletes resolved before the failure, or doc-values updates still pending). In every scenario run, both versions fail the call and close the writer, and no document, commit or file differs: a small regression of error reporting. It is in no release. Main and branch_11x, both unreleased, have it; 10.6.0 does not; 11.0.0 would be the first release with it.

In the review of #14668, Dawid Weiss noted that some of its changes "are not strictly equivalent, even if it's highly theoretical to hit such paths", with another site as the example. This finding is one such path. A validated fix runs the clean-up call inside its own try/catch and adds its exception to the first one.

Why it looks unintended

#
  • Every release run, 7.0.0 to 10.6.0, reports the first failure; from 7.4.0 with the clean-up failure suppressed (LUCENE-8215, a deliberate fix of 2018).
  • The refactor series states the opposite aim: clean-up problems "will now be added to the top-level rethrown exception" (#14633).
  • #14668 has no CHANGES entry, and the same file already suppresses for the same close (openSegmentStates).
The full argument452 words
  • A regression against every release run. The test passes on 10.6.0, 10.5.2, 10.3.0, 10.2.2, 10.2.1, 10.0.0 and 9.12.3 (this page), and a print-only probe shows on each of the seven that the first failure is thrown with the clean-up failure as its one suppressed exception. In earlier runs, copies of an earlier test of the same scenario, changed only in the class names of the older release lines, pass on 7.0.0, 7.3.1, 7.4.0, 8.5.2, 8.6.0 and 8.11.4: the recorded tragic exception is the first failure. A print-only copy shows the detail: 7.0.0 and 7.3.1 throw the first failure and drop the clean-up failure; 7.4.0 and 8.11.4 throw it with the clean-up failure as suppressed. No release that was run reports the clean-up failure in place of the first one.
  • The suppressing form was a deliberate fix. LUCENE-8215 (#9262, Simon Willnauer, 2018, commit 2e35ef2b3da, first release 7.4.0), "Fix several fragile exception handling places in o.a.l.index": "Several places in the index package don't handle exceptions well or ignores them. This change adds some utility methods and cuts over to make use of try/with blocks to simplify exception handling." LUCENE-8212 (#9259), three days earlier, states the rule: "the original exception is rethrown and all other exceptions are added as suppressed."
  • The refactor series states the same aim. #14633, the first of the series (Simon Cooper): "As a side-effect, any problems that occur whilst closing/deleting during exception handling will now be added to the top-level rethrown exception, rather than being swallowed and disappearing." Uwe Schindler answered there: "Code is cleaner and the suppressed exceptions are also much better." On issue #14731 (a user on 7.7.3 who lost a VirtualMachineError behind a rollback failure; closed 2025-07-10) Simon Cooper wrote: "The pattern of using finally blocks to handle cleanup is one which we are slowly removing, and replacing with suppressed exceptions; that case in particular is already modified to correctly handle exceptions during cleanup to maintain the root exception." At this block the change does the opposite.
  • No announcement. #14668 describes itself as "Followon from #14633 - refactor uses of success and success2 booleans". It has no CHANGES entry and no milestone.
  • The same file does it the other way for the same close. openSegmentStates closes the segment states inside try { IOUtils.close(segStates); } catch (Throwable t1) { t.addSuppressed(t1); } throw t; (IndexWriter.java:7206-7213 on main).
  • Support only, not the contract. The javadoc of getTragicException (IndexWriter.java:6523-6527 on main, the same text in 10.6.0): "If this IndexWriter was closed as a side-effect of a tragic exception, e.g. disk full while flushing a new segment, this returns the root cause exception." It does not say which of two failures wins, so the claim does not rest on it.
The devil's-advocate check189 words

The strongest case for "intended or accepted": no text ranks two failures. The IOException that the 11.0 branch reports is tragic by itself: with only the clean-up failure injected, every build throws and records it (probe scenario J). And the review of #14668 allowed for such cases in general terms. Dawid Weiss wrote there: "Some of these changes are not strictly equivalent, even if it's highly theoretical to hit such paths." Two maintainers approved the change.

Why it does not make the behaviour intended: the remark names another site (the tragic-event call throwing), and the answer to it was to change that site so that the first exception is kept. Simon Cooper: "I've modified onTragicEvent to ensure it doesn't throw, and any throwables are suppressed (if possible)." Nobody on the thread names forceApply or finishApply, or says that a lost first exception is acceptable. The stated aim of the series and the fix of 2018 both keep the first exception.

What is left is the ranking, and it stands: this finding is an instance of the remark Dawid Weiss made, a path the review itself called highly theoretical.

Method: semi-formal (a reading of every changed clean-up hunk of a refactor series, then a differential fault-injection probe on the real jars; no model checking, constraint solving or proof was involved).
