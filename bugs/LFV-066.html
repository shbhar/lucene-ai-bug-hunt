RoaringDocIdSet.Builder.add(min, max) throws on the last 2^16-doc block

RoaringDocIdSet.Builder.add(min, max) throws for any range that reaches the last 65,536-doc block below 2^31, because that block's end, 2^31, overflows int. Only segments of more than 2,147,418,112 docs (fewer than 65,407 short of MAX_DOCS) have that block, only a non-default query-cache setup reaches it in search, and it never returns wrong data.

The finding in 30 seconds

#

add(min, max) walks the range one 65,536-doc block at a time and ends each step at Math.min(max, (block + 1) << 16), in int. For the last block, 32,767, the shift gives 2^31, which wraps to -2,147,483,648. The step's end is negative: Lucene's assertion fires, and with assertions off the builder either writes past the last block's bit set or moves on to a nonexistent block 32,768.

Background: roaring doc-id sets, blocks and the query cache

#
  1. RoaringDocIdSet stores a set of doc ids in blocks of 65,536 (2^16): doc d is in block d >>> 16. Each block is kept as a short list of docs, a bit set, the inverse list, a single range, or the shared all-docs set.
  2. Builder.add(int) adds one doc. Builder.add(min, max), new in 10.5.0, adds the range [min, max) at once and is documented as equivalent to adding each doc.
  3. LRUQueryCache uses this builder for cached queries that match fewer than 1% of a segment's docs. Scorers that find whole runs of matching docs report them with collectRange(min, max), which the cache passes to add(min, max).
  4. A Java int holds at most 2,147,483,647 (2^31 - 1). A segment may hold up to IndexWriter.MAX_DOCS = 2,147,483,519 docs, so the last block, 32,767, runs up to 2^31, which does not fit.

The finding, step by step

#
  1. Make a builder for the largest legal segment, new RoaringDocIdSet.Builder(IndexWriter.MAX_DOCS): 2,147,483,519 docs. Doc ids are grouped in blocks of 65,536; the last block, number 32,767, starts at doc 2,147,418,112.
  2. Add the segment's last 10 docs in one call, add(2147483509, 2147483519). You expect what ten add(int) calls give: a set of 10 docs.
  3. The method stops each block at its end, (block + 1) << 16. For block 32,767 that is 2^31 = 2,147,483,648, one more than an int holds, so it wraps to -2,147,483,648 and the block end is negative.
  4. You get an exception: Lucene's own AssertionError with assertions on, NegativeArraySizeException: -2 with them off. Every range that touches this block throws; none returns a wrong set.
  5. In search, only the query cache's sparse path adds ranges. It needs such a segment, a custom leaf predicate, a cache over 1.34 GB per partition and an index-sorted range query, so default setups never get there.

Who is affected

#

Only segments of more than 2,147,418,112 docs, the 65,407 largest legal sizes. In search, only the query cache's sparse path adds ranges, and only with a non-default leaf predicate (the default never caches segments of 2^30+ docs), a cache over 1.34 GB per partition and an index-sorted doc-values range query. It throws; it never returns wrong data.

Mechanism, terms and numbers732 words

RoaringDocIdSet splits doc ids into blocks of 65,536 (2^16). #16081 (10.5.0) added Builder.add(int min, int max) so that LRUQueryCache can cache range-collecting scorers cheaply. It walks the range block by block and caps each step at Math.min(max, (block + 1) << 16), in int. For block 32,767, the last one an int doc id can be in (docs 2,147,418,112 and up), the shift gives 2^31, which wraps to Integer.MIN_VALUE. Lucene's own assertion then fires. With assertions off it throws either a NegativeArraySizeException (the loop moves on to a block 32,768 that does not exist) or an ArrayIndexOutOfBoundsException (a write past the last block's bit set), depending on where the range starts.

So new RoaringDocIdSet.Builder(IndexWriter.MAX_DOCS).add(MAX_DOCS - 10, MAX_DOCS) throws instead of adding 10 docs, although the javadoc calls it equivalent to adding each doc, and add(int) handles the same docs correctly. It only throws; no case returns a wrong set. In an index this needs one segment of more than 2,147,418,112 docs (fewer than 65,407 short of IndexWriter.MAX_DOCS), and in search a non-default LRUQueryCache setup (the default leaf predicate never caches such segments). The fix is one line.

The code (main 645d4fe14a20, RoaringDocIdSet.java)

#
int doc = min;
while (doc < max) {
  final int block = doc >>> 16;                            // 2147483509 >>> 16 = 32767
  final int blockEnd = Math.min(max, (block + 1) << 16);   // :164  32768 << 16 = 2^31 wraps to Integer.MIN_VALUE
  if (block != currentBlock) { flush(); currentBlock = block; firstDocId = doc; }
  appendRangeInCurrentBlock(doc, blockEnd, block);         // :170  toDocExclusive = Integer.MIN_VALUE
  doc = blockEnd;                                          // :171  Integer.MIN_VALUE is still < max
}
  • When. Block 32,767 starts at 32,767 << 16 = 2,147,418,112. Segments with maxDoc in (2,147,418,112, 2,147,483,519] have it, with up to 65,407 docs in it. Any range that touches it fails; ranges below it are exact (Z3 proof A1s in the study).
  • Assertions on. :199 repeats the same wrapped expression and passes; :200, assert fromDoc < toDocExclusive, fires.
  • Assertions off. span = toDocExclusive - fromDoc (:201) wraps back to a positive number, but it is the distance from fromDoc to 2^31, not to max (139 for the repro), and :202 takes the sparse branch when currentBlockCardinality + span <= 4096. So the branch depends on where the range starts, not on its size. Sparse branch (:202-206; for a range that starts the block: it starts within 4,096 doc ids of 2^31, the last 3,967 docs of a MAX_DOCS segment, like the repro): the copy loop d < toDocExclusive runs zero times, and lastDocId becomes Integer.MAX_VALUE. The loop goes round again with block = Integer.MIN_VALUE >>> 16 = 32768; there numBits = Math.min(1 << 16, maxDoc - (32768 << 16)) (:208-211) is -129, and new FixedBitSet(-129) throws NegativeArraySizeException: -2.
  • Dense branch (:207-218): any earlier start in block 32,767, whatever the range's size (10 docs at 2,147,418,112, a range that crosses in from block 32,766, or the entire populated last block). The bit set is sized for the real block (at most 65,407 bits, 1,022 words), and denseBuffer.set(fromDoc - offset, Integer.MIN_VALUE - offset) (:216), that is set(..., 65536), writes past it: Arrays.fill in FixedBitSet.set (FixedBitSet.java:793) throws ArrayIndexOutOfBoundsException: Array index out of range: 1023.
  • Why add(int) is fine. The per-doc path (:114-130, :176-194) never computes (block + 1) << 16; the constructor's block count (maxDoc + (1 << 16) - 1) >>> 16 (:63) is unsigned and correct for every maxDoc >= 0 (Z3 proof A2).

The caller in search (LRUQueryCache.java)

#

cacheIntoRoaringDocIdSet (:656-685) forwards LeafCollector.collectRange(min, max) to builder.add(min, max) (:672); the default cacheImpl takes this path when the scorer's cost is below 1% of maxDoc (:580-592). The shipped range-reporting scorer that fits that density is RangeBulkScorer (RangeBulkScorer.java:79), built by SortedSkipperScorerSupplier for doc-values range queries (SortedNumericDocValuesRangeQuery, SortedSetDocValuesRangeQuery) on the primary index-sort field when that field is dense, has a skip index and the segment has no blocks (SortedNumericDocValuesRangeQuery.java:237-253). The study verifier ran this path end to end: IndexSearcher.count(NumericDocValuesField.newSlowRangeQuery(...)) with an accept-all LRUQueryCache throws from RangeBulkScorer.score -> collectRange -> Builder.add(int, int). Its segment is a real 1-doc index seen through a FilterLeafReader that reports maxDoc = MAX_DOCS; no 2^31-doc index was built.

Exposure and likelihood402 words
  • Direct users of the public, @lucene.internal RoaringDocIdSet.Builder#add(int, int) with maxDoc above 2,147,418,112: every range that touches the last block throws.
  • Through search, all of these must hold (the study verifier checked each, by execution where noted):
    1. Scale. One segment with more than 2,147,418,112 docs, up to MAX_DOCS = 2,147,483,519. No segment this large was built: the search-path test fakes the size with a FilterLeafReader, so it shows the code route, not that such a segment is practical to build, merge and search.
    2. A query cache. Main has none by default since #14187 (IndexSearcher.java:82-84); 10.5.x and 10.6.0 install LRUQueryCache(1000, min(32 MB, heap / 20)) by default.
    3. A non-default leaf predicate. The default MinSegmentSizePredicate computes maxDoc * 2, which overflows for maxDoc >= 2^30, so it never accepts such a segment (a separate bug, LFV-081; executed by the study verifier). The expert constructors accept any Predicate<LeafReaderContext>.
    4. A large cache. The worst-case-size gate (LRUQueryCache.java:792-801, called from shouldCache at :804-808 with the top-level reader's maxDoc) needs maxDoc / 8 * 5 bytes per partition. A reader over such a segment has a top-level maxDoc between 2,147,418,113 and MAX_DOCS (BaseCompositeReader.java:89-106), so that is about 1.34 GB. On main the 4-argument expert constructor uses 16 partitions (about 21.5 GB in total); 10.5.x and 10.6.0 have no partitions. The default 32 MB cache never passes.
    5. A sparse, range-collecting query (cost below 1% of maxDoc, about 21 million docs) whose matching docs reach the last 65,536 docs of the segment, for example a "latest docs" filter on a time-sorted index, and the caching policy deciding to cache it.
  • Effect. The search fails with an unchecked exception while the cache is filled. Nothing is cached, no index data is touched, and no wrong result is returned; only the cache's bookkeeping has run (the lookup counted a miss and the caching policy was told the query was used, LRUQueryCache.java:812-814, :1060-1082). It repeats whenever the policy tries to cache that query on that segment.
  • Never silent. The study verifier's sweep compared add(min, max) with the per-doc reference over 4,512 cases: the 2,943 ranges below block 32,767 were exact, and all 1,569 that touch it threw. With the fix all 4,512 are exact. This is not only a sample: both assertions-off branches end in an exception for every maxDoc up to MAX_DOCS (the verifier's case analysis, confirmed against RoaringDocIdSet.java:201-218 and FixedBitSet.java:773-795).

Why it looks unintended

#
  • The javadoc calls add(min, max) "Equivalent to calling add(int) for each min <= doc < max", with only IllegalArgumentException for bad bounds; the same 10 docs added one by one work.
  • IndexWriter.MAX_DOCS (2,147,483,519) makes such segments legal, and the builder accepts any maxDoc.
  • Lucene's own assertion rejects the wrapped value; its scorers guard the same window-end pattern with MathUtil.unsignedMin.
The full argument216 words
  • Contract. RoaringDocIdSet.java:132-142: "Add a contiguous half-open range [min, max) of doc ids. ... Equivalent to calling add(int) for each min <= doc < max, but uses a more efficient implementation for dense ranges." It documents IllegalArgumentException "if min > max, if min <= lastDocId, or if max exceeds maxDoc" as the only failures; none holds here.
  • Legal sizes. IndexWriter.java:201-208: MAX_DOCS = Integer.MAX_VALUE - 128, the "Hard limit on the maximum number of documents that may be added to the index". Builder(int maxDoc) (:61-67) accepts any size.
  • The code means to stop at the block end. Math.min(max, (block + 1) << 16) exists to cap the step at the block end; the wrap defeats it, and assert fromDoc < toDocExclusive (:200) rejects the result.
  • The same pattern is guarded elsewhere. MathUtil.unsignedMin (MathUtil.java:196-199) caps window ends in the search package, for example DenseConjunctionBulkScorer.java:198 and :214, MaxScoreBulkScorer.java:216, ConstantScoreBulkScorer.java:132, DisjunctionMaxBulkScorer.java:90, TimeLimitingBulkScorer.java:73 and RangeDocIdStream.java:68.
  • Why tests miss it. TestRoaringDocIdSet and its base class BaseDocIdSetTestCase use sets of at most 2^20 (1,048,576) docs.
  • History. The line came with the method in #16081; neither the PR nor its review mentions large doc ids, and later edits to the method (#16084, #16256) did not touch it.
The devil's-advocate check171 words

Strongest case for "not a bug" (a cross-model reviewer, OpenAI GPT-5.6, refute lens, which reproduced it with its own tests and rated this argument "moderate"): RoaringDocIdSet is @lucene.internal and the util package is "primarily internal", so direct callers cannot rely on it; and the default leaf predicate never selects a segment this large, so an ordinary deployment cannot reach it.

Why it fails: Lucene's own LRUQueryCache reaches the method through the public LeafCollector.collectRange contract ("max is guaranteed to be greater than min") and a public expert constructor that accepts any leaf predicate; the reviewer showed that with its own test of the default cacheImpl. @lucene.internal limits API stability, not correctness. Unlikely is not intended: a custom predicate and a large cache are documented expert settings, and the default predicate rejects these segments only through another overflow (LFV-081). The reviewer's verdict: real, high confidence. The failure is loud, but the input is not absurd: the sizes are within MAX_DOCS, and the same docs work one at a time.

Suggested fix

#

Recommended A. MathUtil.unsignedMin for the block end

Compute the block end with MathUtil.unsignedMin(max, (block + 1) << 16): one line, the idiom Lucene's scorers already use for window ends. Validated: the test fails before and passes after, with assertions on and off, and 80 tests of the roaring, query-cache and doc-id-set suites pass.

// RoaringDocIdSet.Builder.add(int, int)
-        final int blockEnd = Math.min(max, (block + 1) << 16);
+        final int blockEnd = MathUtil.unsignedMin(max, (block + 1) << 16);
All options and trade-offs3 options · 461 words

Two options were applied in a scratch worktree of main 645d4fe14a20 and run with gradle; a third is correct by reasoning but was not run. All change only line :164.

A. MathUtil.unsignedMin for the block end (validated by the checks) (recommended)

#

max is a non-negative int, so read as unsigned it is below 2^31. For block 32,767 the wrapped value Integer.MIN_VALUE reads as 2^31 unsigned, and unsignedMin returns max; for every other block both values are non-negative and unsignedMin equals Math.min. MathUtil is in the same package, so no import is needed.

// RoaringDocIdSet.Builder.add(int, int)
-        final int blockEnd = Math.min(max, (block + 1) << 16);
+        final int blockEnd = MathUtil.unsignedMin(max, (block + 1) << 16);

Trade-offs

  • One line, no extra work on the hot path, and the idiom DenseConjunctionBulkScorer, MaxScoreBulkScorer and others already use for window ends.
  • unsignedMin takes a moment to read. The assertion at :199 keeps its wrapped second operand but stays correct, because its first operand is then true for the last block.

Downstream note

#

Downstream servers that keep Lucene's default leaf predicate never cache such segments; one that lets operators cache every segment and holds a near-2^31-doc, index-sorted segment, with a large enough cache and a range filter that reaches the last block, would see failed searches, not wrong results.

How it was found

#

Formal. A CodeQL inventory of int shifts and window additions, triaged with git blame, listed this line; a Z3 bit-vector query with Lucene's documented limits as preconditions found the smallest failing doc, 2,147,418,112, in 0.02 s and proved the line exact below it. An independent verifier reproduced it, end to end through IndexSearcher.

The method in full151 words
  • Sweep. The study's overflow-at-scale experiment (main 7cecf79523, 2026-10-22) used CodeQL to list every non-constant int multiplication, left shift and "x + C" window or block addition in the target packages (602 + 63 rows), then triaged them with git blame; RoaringDocIdSet.java:164 was one of them.
  • Solver. The expression was transcribed into Z3 bit-vector logic with Java wraparound and the documented limits (MAX_DOCS) as preconditions: obligation A1 returned a counterexample (doc 2,147,418,112, max 2,147,470,450, maxDoc 2,147,470,604) in 0.021 s, and A1s proved the expression exact whenever doc < 2^31 - 2^16. JBMC on the real bytecode ran out of memory on this harness.
  • Verification. An independent study verifier wrote its own 16 tests (Builder, LRUQueryCache.cacheImpl, end-to-end IndexSearcher.count, and a 4,512-case sweep), reproduced it, found that it only throws, and found the default leaf-predicate overflow (LFV-081) on the way; the hunt then reduced it to the one-test repro.

RoaringDocIdSet.Builder.add(min, max) throws on the last 2^16-doc block
Area
util / bitsets
Priority
Low, rank 1194: RoaringDocIdSet.Builder.add(min, max) throws on the last 2^16-doc block, which needs a segment within 65k docs of MAX_DOCS and a non-default cache predicate, and it is loud only.
Impact class
crash
Impact note
Only segments with more than 2,147,418,112 docs plus the opt-in query cache with a non-default caching predicate; throw-only, never silent; released 10.5.0 to 10.6.0.
Summary
You add a doc-ID range that falls in the last 65,536-doc block below 2^31 to a RoaringDocIdSet.Builder. You expect the range to be added. Instead (block+1)<<16 wraps and the call throws; it never returns wrong data.
