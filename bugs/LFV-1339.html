A throwing OneMerge.mergeFinished in an addIndexes(CodecReader...) merge leaves the merge "running", so rollback() and close() never return

When a merge policy's OneMerge.mergeFinished throws during addIndexes(CodecReader...), IndexWriter never removes that merge from its set of running merges. The writer stays open, but rollback() and close() wait for that merge forever.

The finding in 30 seconds

#

One failing callback at the end of an addIndexes merge leaves IndexWriter believing the merge is still running, and the writer's two exits, rollback() and close(), wait for it forever.

Background: how addIndexes(CodecReader...) runs merges

#
  1. Since 9.4.0, addIndexes(CodecReader...) asks the merge policy for OneMerge objects (findMerges(CodecReader...)) and hands them to the merge scheduler, like ordinary merges.
  2. IndexWriter keeps every merge that is being executed in a set, runningMerges. rollback() and close() wait until that set is empty.
  3. When a merge ends, IndexWriter calls the policy's OneMerge.mergeFinished callback (public, declared throws IOException) and then crosses the merge off runningMerges.

The finding, step by step

#
  1. Give the writer a merge policy whose findMerges(CodecReader...) returns 1 OneMerge whose mergeFinished throws IOException, use SerialMergeScheduler, and call addIndexes with a 1-document reader.
  2. addIndexes throws that IOException, as it should. The writer stays open: isOpen() is true and there is no tragic exception.
  3. You expect rollback() to close the writer, as documented. It never returns: it waits until no merge is running, but 1 merge stays registered as running forever, and it re-checks once a second.
  4. Why: at the end of the merge, AddIndexesMergeSource.merge runs mergeFinished and only then removes the merge from the running set, with no nested finally, so the throw skips the removal. close() hangs the same way, in every release from 9.4.0 to 10.6.0 and on main.

Who is affected

#

Applications that call addIndexes(CodecReader...) with a merge policy returning its own OneMerge whose mergeFinished can fail (cleanup, side data). No in-tree policy does. Then rollback(), the documented way out after an exception, and close() block forever. With the default scheduler, addIndexes does not even report the failure. No scale needed; by code reading the failed call commits nothing.

Mechanism, terms and numbers458 words

Since 9.4.0, IndexWriter.addIndexes(CodecReader...) runs its merges through the merge policy (findMerges(CodecReader...)) and the merge scheduler. Each merge is checked out into runningMerges and run by AddIndexesMergeSource.merge, whose finally calls merge.close(success, ..) and then onMergeFinished(merge). close runs the policy's public OneMerge.mergeFinished callback, which is declared throws IOException; onMergeFinished removes the merge from runningMerges. There is no nested finally, so when the callback throws, the merge stays in runningMerges for good. With SerialMergeScheduler, addIndexes reports the exception and the writer stays open and not tragic, but rollback() then waits forever in abortMerges and close() in waitForMerges; by code reading nothing removes the stale entry, and interrupting the waiting thread makes the call fail with ThreadInterruptedException. With the default ConcurrentMergeScheduler, addIndexes even returns normally, the exception appears only on the merge thread, and rollback() hangs the same way. A second route goes through deleteAll(), whose abort of a queued addIndexes merge skips clearing the queue when the callback throws. The trigger needs a custom OneMerge with a callback that can fail, which no in-tree merge policy has, and by code reading the failed call commits nothing.

Exposure and likelihood413 words
  • What breaks. A maintainer listed deleteAll() and addIndexes() among the methods whose exceptions "we treated ... not as fatal or tragic events since a user could always call rollback()" (s1monw on #9738, LUCENE-8692). Here rollback() and close() block the calling thread forever and never release the write lock or the writer's files (rollback is stuck in abortMerges, before the cleanup that releases them); an interrupt makes them fail with ThreadInterruptedException.
  • Who is hit. A merge policy whose findMerges(CodecReader...) returns its own OneMerge subclass with a mergeFinished that does work that can fail. The pattern exists: Lucene's own TestDemoParallelLeafReader has a mergeFinished that rethrows a decRef failure (:654-668).
  • Opt-in. The default findMerges(CodecReader...) returns a plain OneMerge (MergePolicy.java:616); OneMergeWrappingMergePolicy does not wrap addIndexes merges (:45-80); the only non-test mergeFinished override (IndexWriter.java:3968) belongs to merge-on-commit/refresh merges.
  • Default scheduler: quieter, not safer. A probe (not the repro) with the default ConcurrentMergeScheduler: addIndexes returns normally, the IOException surfaces only as an uncaught MergePolicy.MergeException on the merge thread, isOpen() is true, there is no tragic exception, and rollback() is still waiting in abortMerges after 5 s. Without the throw, rollback() returns.
  • Scale. None: 1 document, 1 merge, 1 indexing thread; assertions on or off.
  • Not affected. Search; the last commit (by code reading the failed addIndexes call commits nothing and deletes the merged files, IndexWriter.java:3316-3323; no run checked the index afterwards); and the regular merge path when the merge itself succeeds: if mergeFinished throws while commitMerge closes the readers (:5012), the outer finally still runs mergeFinish(merge) (:5086-5093, :5389), because the second close is skipped by hasFinished() (:5396; by code reading).
  • A sibling on the regular path (needs two failures; not part of this report). The regular path's failure branch has the same order as this bug: closeMergeReaders(merge, true, false), then mergeFinish(merge), with no nested finally (IndexWriter.java:5090-5093), and suppressExceptions does not cover the callback (:5396-5418). When a regular merge has already failed before mergeMiddle's own try (:5482), e.g. in a MergeScheduler.wrapForMerge that throws (:5470), and mergeFinished throws too, the merge stays in runningMerges and the writer's own tragic-event rollback waits in abortMerges, the hang that the comment at :5109-5110 warns of. A probe showed it (stopped after 120 s; the control without the throw ends at once). A maintainer may ask to harden that site with the same pattern.

Why it looks unintended

#
  • mergeFinished is public and declared throws IOException; its javadoc sets no limit.
  • IndexWriter treats the failure as recoverable (writer open, not tragic), and rollback() is documented to close it. Here it cannot.
  • On an ordinary merge the regular path removes the merge from the running set despite a throwing callback; the addIndexes path does not, even after a successful merge.
The full argument154 words
  • Contract. mergeFinished (MergePolicy.java:276-282): "Called by IndexWriter after the merge is done and all readers have been closed", declared throws IOException. OneMerge.close wraps it in try/finally to release the merge readers anyway (:292-298).
  • Recoverable by IndexWriter's own handling. addIndexes and deleteAll rethrow the exception without a tragic event (only Error is tragic in deleteAll, IndexWriter.java:2811-2813), and rollback() says "Close the IndexWriter without committing any changes" (:2566-2574).
  • Documented expectation for the deleteAll route. deleteAll's javadoc says concurrent addIndexes(CodecReader[]) callers "may receive MergePolicy.MergeAbortedExceptions" (:2743-2745), not a hang or an IllegalStateException.
  • No sign of intent. The review of #633, which introduced the code, never discusses a throwing mergeFinished or this finally. No javadoc or CHANGES entry mentions it, and no upstream test makes mergeFinished throw in an addIndexes merge (the only test merge policies that override findMerges(CodecReader...), in TestAddIndexes, leave it alone).
The devil's-advocate check113 words

The strongest case, made by an executed cross-model review (OpenAI GPT-5.6): MergePolicy, OneMerge and MergeScheduler are @lucene.experimental extension points (MergePolicy.java:69, :189; MergeScheduler.java:34), so a callback that throws is the application's problem.

Why it fails: @lucene.experimental is about API stability, not a license to hang. The method is declared to throw IOException, IndexWriter reports the exception as non-tragic and keeps the writer open, and rollback() is documented to close it. The reviewer itself rated the argument weak and the bug real. One qualification: no javadoc promises recovery after every exception from a custom callback, so "not intended" is a conclusion from the contracts above, not a stated guarantee.

Suggested fix

#

Recommended A + B: nested try/finally in AddIndexesMergeSource.merge, plus clear the queue in a finally in abortPendingMerges (recommended; validated)

In AddIndexesMergeSource.merge's finally, wrap merge.close(..) in try { .. } finally { onMergeFinished(merge); }, so the merge always leaves the running set; the callback's exception is neither caught nor replaced. Also clear pendingAddIndexesMerges in a finally in abortPendingMerges. Validated through gradle: the repro passes, assertions on and off, and the six closest IndexWriter suites pass (143 tests, 0 failures).

      } finally {
        synchronized (IndexWriter.this) {
          try {
            merge.close(success, false, _ -> {});
          } finally {
            onMergeFinished(merge);
          }
        }
      }

Downstream note

#

Products that run addIndexes(CodecReader...) with their own merge policy and a fallible OneMerge.mergeFinished can end up with a writer that can be neither rolled back nor closed, and with the default ConcurrentMergeScheduler the only sign is an uncaught merge-thread exception.

How it was found

#

A proof-obligation audit of AddIndexesMergeSource.abortPendingMerges: the addIndexes merge queue must be empty after an abort, on every exit path. A throwing callback broke it, and an executable two-thread test witnessed the hang. An intended-behaviour review then showed one thread suffices and moved the fix site to merge()'s finally.

The method in full82 words

The obligation was checked on each exit of abortPendingMerges: on the exceptional exit of IOUtils.applyToAll, pendingAddIndexesMerges.clear() is skipped. A test that keeps an addIndexes merge queued while deleteAll() aborts it, with a mergeFinished that throws on the aborted merge, showed rollback() hanging. The intended-behaviour review found the simpler trigger (no deleteAll, stock SerialMergeScheduler, mergeFinished throwing on a normal merge) and showed that the try/finally in AddIndexesMergeSource.merge fixes both tests, while clearing the queue alone leaves the single-thread hang.

Impact note
Hits applications that call addIndexes(CodecReader...) with a merge policy whose findMerges(CodecReader...) returns its own OneMerge subclass, when that OneMerge's public mergeFinished(boolean, boolean) callback (declared throws IOException) throws, for example because a clean-up or side-data write fails: addIndexes (or, on a second route, a deleteAll() that aborts a queued addIndexes merge) reports the exception and leaves the writer open with no tragic exception, but rollback() then waits forever in abortMerges and close() in waitForMerges, and only a thread interrupt ends the wait; executed with the stock SerialMergeScheduler and, in a probe with assertions off, with the default ConcurrentMergeScheduler (addIndexes then returns normally and the exception shows only on the merge thread), -ea and -da alike, no scale, every release from 9.4.0 through 10.6.0 and main; no in-tree OneMerge used by addIndexes(CodecReader...) throws there, and the index is not damaged.
Summary
You give IndexWriter a merge policy whose findMerges(CodecReader...) returns a OneMerge with a mergeFinished override, call addIndexes(CodecReader...), and that mergeFinished throws an IOException (the method is public and declared to throw it). You expect addIndexes to report the exception, which it does while leaving the writer open and not tragic, and rollback() or close() to then close the writer as documented. Instead AddIndexesMergeSource.merge's finally calls merge.close(..), which runs mergeFinished, before onMergeFinished(merge) with no nested finally, so the merge is never removed from runningMerges and rollback() waits forever in abortMerges (close() in waitForMerges); a deleteAll() that aborts a queued addIndexes merge reaches the same spot through abortPendingMerges, which also skips clearing its queue when the callback throws.
