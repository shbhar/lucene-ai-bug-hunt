JapaneseTokenizer and KoreanTokenizer split an emoji in half at the 1024-char unknown-word cap

Kuromoji's JapaneseTokenizer and nori's KoreanTokenizer stop a long run of unknown text at 1,024 UTF-16 chars even when that cut splits an emoji or rare ideograph into its two halves, which the index stores as two U+FFFD characters. Since 3.6.0 (kuromoji) and 7.4.0 (nori); the default JapaneseAnalyzer is not affected.

The bug in 30 seconds

#

Kuromoji and nori turn a run of characters the dictionary does not know, of one class or script, into one unknown word and stop it at 1,024 UTF-16 chars. Neither checks whether char 1023 is the first half of a surrogate pair. Both halves belong to the run's class, so only the cap ends it.

  1. You analyze 1,200 chars of Thai without spaces with an emoji, U+1F600 (two UTF-16 chars), at char 1023, through JapaneseTokenizer or the japanese tokenizer factory with defaults; or 400 × 👁️ (U+1F441 U+FE0F) through the default KoreanAnalyzer.
  2. Both tokenizers read the run as one unknown word and stop it at 1,024 chars, a safety cap. You expect the cut to fall between whole characters, as it does when the emoji is at char 1022 or 1024.
  3. Instead the cut lands between the emoji's two halves: term [0,1024) ends with U+D83D and term [1024,1200) starts with U+DE00. The index stores U+FFFD in both terms, and no term contains the emoji.
  4. In EXTENDED mode (unknown words as single characters) a TermQuery for the emoji finds 0 of 1 documents, against 1 when it sits at char 1022 or 1024. No error: CheckIndex is clean and the stored text keeps the emoji.

Who is affected

#

Chains on kuromoji's JapaneseTokenizer (any mode, the japanese factory with defaults) and nori's KoreanTokenizer, default KoreanAnalyzer and korean factory. Not the default JapaneseAnalyzer, whose stop tags drop these words. It needs over 1,023 chars with no break, such as space-free Thai or emoji runs: one character per cut, a TermQuery miss only in the unigram modes.

Mechanism, terms and numbers614 words

Kuromoji's JapaneseTokenizer and nori's KoreanTokenizer group a run of characters that their dictionary does not know into one unknown word and stop it at MAX_UNKNOWN_WORD_LENGTH = 1024 UTF-16 chars, a limit commented "For safety". Neither checks whether char 1023 is the first half (high surrogate) of a supplementary character such as an emoji or a CJK Extension B ideograph. When it is, the character is split across two terms: one ends with a lone high surrogate, the next starts with the lone low surrogate, and the index stores both as U+FFFD. In the single-character modes (kuromoji EXTENDED, nori outputUnknownUnigrams=true) a TermQuery for the character then misses the document. It needs a run of more than 1,023 chars that the tokenizer cannot break, such as long space-free Thai through kuromoji or long emoji runs; the default JapaneseAnalyzer drops these words and is not affected, the default KoreanAnalyzer is. Present since kuromoji's first release (3.6.0, 2012) and nori's (7.4.0, 2018); a 5-line guard per tokenizer fixes it.

Terms

#
  • Supplementary character, surrogate pair: Java strings are UTF-16. Characters above U+FFFF, such as most emoji (😀 is U+1F600) and CJK Extension B ideographs (U+20000), take two chars: a high surrogate (U+D800-U+DBFF) followed by a low surrogate (U+DC00-U+DFFF). Either half alone is not a character.
  • Unknown word: when the dictionary has no entry, kuromoji and nori make a word from the run of following chars that share the first char's character class (kuromoji) or Unicode script group (nori).
  • Unigram modes: kuromoji's EXTENDED mode and nori's outputUnknownUnigrams=true emit an unknown word as one token per character; that code keeps a surrogate pair together on purpose.

The bug

#
  1. The cap: // For safety: protected static final int MAX_UNKNOWN_WORD_LENGTH = 1024; in the base class both tokenizers share (morph/Viterbi.java:41-42).
  2. Kuromoji's loop (ja/ViterbiNBest.java:137-149) and nori's (ko/Viterbi.java:92-126, the same header for (int posAhead = pos + 1; unknownWordLength < MAX_UNKNOWN_WORD_LENGTH; posAhead++)) add one UTF-16 char at a time. When the length reaches 1024 they stop, and nothing looks at the last char.
  3. Both surrogate halves are class DEFAULT in both tokenizers, like Thai letters and U+FE0F; nori sees each half as script UNKNOWN and joins it to Common or Inherited characters such as U+FE0F. So a long Thai run (kuromoji) or an emoji run with U+FE0F (nori) continues through the emoji, and only the cap ends it. A pair-aligned run such as 600 × 😀 never splits; it takes an odd number of BMP chars before the cut.
  4. When the emoji's high surrogate is char 1023 (or 2047, 3071, ...), one word ends with it and the next starts with the low surrogate. The unigram code works inside one word and cannot rejoin them.
  5. At indexing, UnicodeUtil.UTF16toUTF8 writes each lone half as U+FFFD (UnicodeUtil.java:172-176), as IndexWriter documents (IndexWriter.java:1483-1485). The index stays well-formed, so nothing fails.

Exposure and likelihood353 words
  • Who is exposed. JapaneseTokenizer in SEARCH (the default), NORMAL and EXTENDED mode, with discardPunctuation true or false, and the japanese tokenizer factory with default parameters, in any chain that keeps these words: the hunt's sweep flagged 15 of the 16 kuromoji-based factory chains it built (with reading, base-form, katakana-stem, number and other filters); the 16th, with the part-of-speech stop filter, emitted no broken term, which fits the default stop tags dropping these words. KoreanTokenizer, new KoreanAnalyzer() and the korean factory with defaults on emoji runs joined by U+FE0F, and nori's unigram mode. Both nori classes are @lucene.experimental.
  • Not exposed: the default JapaneseAnalyzer. Kuromoji tags these words 記号-一般 (symbol, general), and the default stop tags drop that tag; it emits 0 tokens for the probe inputs.
  • What it takes. More than 1,023 UTF-16 chars of one unknown-word class with no break, and a supplementary character whose first half lands exactly on a cut (char 1023, 2047, ...). Ordinary Japanese and Korean prose rarely does this: kanji and kana are other classes, and Korean text has spaces. Realistic cases are long space-free Thai (or other text kuromoji has no class for) in a Japanese chain, and long emoji runs for nori. How often real text hits a cut was not measured.
  • What the user sees. The index stores U+FFFD in place of the character, in two terms, and token offsets point inside the pair. In the unigram modes a search, or a term-based exclusion filter, for that character misses the document. In SEARCH, NORMAL and the default KoreanAnalyzer a TermQuery for the character never matched the 1,024-char run token anyway, so its hit count does not change (prefix, wildcard and query-parser queries were not tested); what remains there is the U+FFFD terms, exact-phrase matches between two long runs that differ only in the character at the cut, and lone surrogates in highlight snippets for a U+FFFD query.
  • Scale. One character per 1,024-char cut in that field value. The executed probes found no exception and no measured extra cost (timings 0.88-1.00× a shifted control on about 262,144 chars), CheckIndex clean, stored value intact.

Why it is a bug, not intended

#
  • Kuromoji's own tests ("ensuring we don't ever split supplementaries") require every term to be valid UTF-16, but use 100-char inputs that never reach the cap.
  • Both tokenizers' single-character modes keep surrogate pairs together on purpose.
  • Lucene fixed the same split as a bug in smartcn (LUCENE-8325) and TruncateTokenFilter (#15899). A length cap justifies ending a word, not splitting a character.
The full argument226 words
  • Kuromoji's tests state the contract. TestJapaneseTokenizer.testSurrogates2 (:414-431) and TestExtendedMode.testSurrogates2 (:58-72), "random test ensuring we don't ever split supplementaries", assert UnicodeUtil.validUTF16String(termAtt) for every term. They came with the original contribution (LUCENE-3305), before the cap existed, and their 100-char random inputs never reach 1,024.
  • The same code keeps pairs together. The unigram paths pair a low surrogate with its high surrogate (ja/ViterbiNBest.java:442, ko/Viterbi.java:218); in kuromoji this predates the cap: it came with the original contribution (LUCENE-3305, 2012) and was kept when the cap was added.
  • Precedents. lucene/CHANGES.txt:7479 (7.4.0): "LUCENE-8325: Fixed the smartcn tokenizer to not split UTF-16 surrogate pairs", where the nori author wrote "the tokenizer should not split surrogate pairs into multiple tokens"; :1198-1200 (10.5.0): TruncateTokenFilter "no longer produce half surrogates" (#15899, #15900). In the LUCENE-3767 discussion that added the cap, one comment names "don't separate a lead surrogate from a trail surrogate" as a general rule.
  • No javadoc we examined allows it. The javadocs of both tokenizers and their factories say nothing about the cap or supplementary characters (grep for 1024, surrogate, supplementary). IndexWriter's U+FFFD note covers malformed input; here the input is well-formed and the tokenizer makes the halves.
  • For nori the contract is weaker: no nori test asserts it; it rests on nori's pair-preserving unigram code, the loop it copied from kuromoji and the statement above.
The devil's-advocate check120 words

The strongest case (the intended-behaviour checker and the cross-model reviewer): the cap is a deliberate safety bound counted in UTF-16 chars ("For safety" above both 1,024 constants; on #4970 the sibling forced-backtrace limit is described as "for safety / prevent adversary"); both tokenizers classify each char separately; nori is @lucene.experimental; the input is unusual; and no javadoc promises well-formed terms.

Why it fails: the cap explains why a word is cut, not why a character is, and backing off by one char keeps the bound (the fix). The per-char design is exactly what the unigram code compensates for, and kuromoji's tests state the property. Experimental status and rare input are about impact, not intent. Verdict: not intended, a defect.

Suggested fix

#

Recommended Back off one char when the cap would split a surrogate pair

After each unknown-word loop (kuromoji ViterbiNBest, nori Viterbi): if the word reached 1,024 chars and ends with a high surrogate, shorten it to 1,023 (5 lines each). The cap still holds and the word is never empty. The repro passes, and so do the whole kuromoji (197 tests) and nori (89 tests) test tasks, assertions on and off.

// after the unknown-word loop, in ja/ViterbiNBest.java and in ko/Viterbi.java:
// do not cut a surrogate pair in half when the word reaches its maximum length
if (unknownWordLength == MAX_UNKNOWN_WORD_LENGTH
    && Character.isHighSurrogate((char) buffer.get(pos + unknownWordLength - 1))) {
  unknownWordLength--;
}

Back off one char when the cap would split a surrogate pair (validated by the checks) (recommended)

#

The word ends at 1,023 chars and the next unknown word starts with the whole emoji: [0,1023) + [1023,1200); EXTENDED emits the emoji as [1023,1025); the indexed term contains the emoji and the EXTENDED-mode TermQuery finds the document.

// after the unknown-word loop, in ja/ViterbiNBest.java and in ko/Viterbi.java:
// do not cut a surrogate pair in half when the word reaches its maximum length
if (unknownWordLength == MAX_UNKNOWN_WORD_LENGTH
    && Character.isHighSurrogate((char) buffer.get(pos + unknownWordLength - 1))) {
  unknownWordLength--;
}

Trade-offs

  • The bound still holds (at most 1,024 chars) and the length becomes 1,023, never 0, so the lattice always moves forward. It fires only when the cap is reached and the last char is a high surrogate; all other text tokenizes as before. No cost change in the security probe (0.98-1.00× with the fix).
  • Documents indexed before the fix keep their U+FFFD terms until they are reindexed.
  • The guard is duplicated in two classes; a PR could put a small protected helper next to the constant in the shared morph/Viterbi.java (not run).
  • In nori the loop may already have updated characterId from the dropped char when the run so far was all Common or Inherited (ko/Viterbi.java:120-125); the halves and U+FE0F are all class DEFAULT, so nothing changes in the probed cases. Reviewed but not run: a run of 1,023 Common or Inherited chars whose next char is the high surrogate, where the shortened word keeps the dropped char's class.
  • A PR could add the tests as methods of TestJapaneseTokenizer / TestExtendedMode and TestKoreanTokenizer / TestKoreanAnalyzer; the default KoreanAnalyzer on an emoji run is the default-configuration path worth covering.

Extend by one char instead of backing off.

Trade-offs

The cap is then no longer a strict 1,024 bound, and nothing checked whether other code relies on it. More risk than the back-off for no gain. Not run.

Downstream note

#

Search servers built on Lucene that expose these tokenizers inherit the behaviour; for a U+FFFD query on the single-character fields, UnifiedHighlighter returned snippets containing a lone surrogate (downstream handling of such snippets was not tested).

How it was found

#

Semi-formal. A bounded-exhaustive sweep of factory-built analysis chains (filler texts × probe characters × buffer-edge positions) checked that no term from well-formed input has an unpaired surrogate. It flagged 15 of the 16 kuromoji-based chains (not the part-of-speech stop chain) at chars 1023, 2047, 4095, 8191 and 16383; a follow-up probe of the same cap found the nori variant.

The method in full196 words
  • Sweep. The hunt unit on analysis chains built through the SPI factories ran a bounded-exhaustive buffer-edge sweep: 13 filler texts × 13 probes × buffer boundaries × positions, with the oracle "no term with an unpaired surrogate from well-formed input". It reported 900 violations: 60 in each of 15 kuromoji-based chain configurations, at the cuts 1023, 2047, 4095, 8191 and 16383 (a few chars earlier for multi-code-point probes); the 16th kuromoji chain, with the part-of-speech stop filter, reported none. The hits came from the Thai, Hangul, emoji and Extension B fillers with the emoji, Extension B, flag and ZWJ-sequence probes, and with a BMP Hangul jamo probe that shifts an emoji or Extension B filler run by an odd number of chars. No nori configuration reported this violation: its Thai and Hangul fillers break at the emoji (script change), and its emoji and Extension B filler runs stay pair-aligned.
  • Follow-up. A probe of the same cap in nori found the emoji + U+FE0F run, which keeps one script group up to the cap.
  • Reduction. The finder reduced both to a public-API JUnit (6 tests). No formal tool (model checker, SMT solver or proof) produced a signal.

Bug record

#

LFV-459, snapshot of 2026-10-29

Registry title
JapaneseTokenizer and KoreanTokenizer cut an unknown word at the 1024-char cap (MAX_UNKNOWN_WORD_LENGTH) even in the middle of a surrogate pair, so a supplementary character (an emoji, a CJK Extension B ideograph) at char 1023 of a long same-class run is emitted as two unpaired surrogate halves and indexed as U+FFFD
Area
analysis / kuromoji and nori Viterbi unknown-word length cap (JapaneseTokenizer and the 'japanese' factory; KoreanTokenizer, KoreanAnalyzer and the 'korean' factory)
Priority
Low, rank 427: Kuromoji and nori split a surrogate pair at the 1024-char unknown-word cap, but it needs a run of more than 1023 chars of one unknown-word class (emoji spam, or Thai without spaces in a Japanese chain), and only the opt-in unigram modes turn it into a TermQuery miss, so it is far narrower than its Medium siblings LFV-233 and LFV-445.
Impact class
silent wrong results
Impact note
Applications that analyze text with kuromoji's JapaneseTokenizer outside the default JapaneseAnalyzer chain (the 'japanese' factory with default parameters, SEARCH, NORMAL or EXTENDED mode; the default JapaneseAnalyzer is not affected because its part-of-speech stop tags drop these unknown words) or with nori's KoreanTokenizer or default KoreanAnalyzer get, for every run of more than 1023 UTF-16 chars of one unknown-word class with no break (Thai or other DEFAULT-class text or an emoji run for kuromoji; an emoji run joined by U+FE0F for nori) whose char 1023 is a high surrogate, a term ending in a lone high surrogate and a next term starting with the lone low surrogate: the index stores U+FFFD halves, token offsets fall inside a surrogate pair, and an exact-text phrase also matches a text that differs only in that character; a TermQuery miss for the character itself appears only in the unigram modes (kuromoji EXTENDED, nori outputUnknownUnigrams=true), because in the default modes the character sits inside a 1024-char run token that a short query never matches, bug or not; nothing throws, CheckIndex is clean and the stored value is intact, with -ea and -da, in every release from 3.6.0 (kuromoji) or 7.4.0 (nori) to 10.5.2.
Summary
You analyze a long run of text that kuromoji or nori treat as one unknown word, for example 1,200 chars of Thai without spaces through the 'japanese' tokenizer, or 400 x (U+1F441 U+FE0F) emoji through the default KoreanAnalyzer, and the run holds an emoji or a rare ideograph such as U+20000; you expect every term to consist of whole characters, as it does when that character sits one position earlier or later. Instead both tokenizers stop the unknown word at exactly 1024 UTF-16 chars without checking for a surrogate pair, so when the character's first half is char 1023, term 0 ends in a lone high surrogate and term 1 starts with the lone low surrogate. The index silently stores both halves as U+FFFD, and in the unigram modes a TermQuery for the character finds 0 documents instead of 1.
