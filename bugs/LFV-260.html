An NRT replica's commit can record in VERSION_KEY a newer version than the segments it holds

If an NRT replica installs a newer point while its commit() fsyncs, the commit labels the older segments it writes (version 3) with the newer version (VERSION_KEY = 5). A primary started on that commit reports getLastCommitVersion() = 5, so a log replay from there skips operations; since 6.0.0.

The finding in 30 seconds

#

ReplicaNode.commit() captures the current segments under the node lock, fsyncs their files holding only its separate commitLock, and only then reads VERSION_KEY from the searcher that is current. A point installed during the fsync therefore labels a commit that does not contain it.

Background: NRT segment replication and the commit version

#
  1. In lucene-replicator's NRT segment replication (opt-in, experimental) a PrimaryNode indexes and publishes NRT points, each with a version number; each ReplicaNode copies the new files and switches its searcher to that point.
  2. Any node can commit(). The commit's user data stores VERSION_KEY, the version of the committed content; a node later started as a primary on that commit returns it from getLastCommitVersion().
  3. An application that keeps an operation log uses that number after a failover or a full restart: it replays the log from the position of that version, as the module's stress test does.

The finding, step by step

#
  1. A replica of an NRT-replicated index searches the primary's point version 3 (1 document). The primary adds a second document and publishes version 5 (2 documents).
  2. You call replica.commit(). It captures the version-3 segments, then fsyncs their files without holding the node lock; meanwhile the replica installs version 5.
  3. You expect the commit's VERSION_KEY to be 3, the version it holds, or at worst lower: PrimaryNode.commit() accepts a lagging value because a replay then only repeats operations.
  4. Instead it is 5: after the fsync, commit() reads the version of whatever searcher is current. The commit holds 1 document but claims version 5.
  5. A primary started on this commit reports getLastCommitVersion() = 5 with only the first document. Replaying the operation log from version 5, as Lucene's own stress test does, skips the second document. No error anywhere.

Who is affected

#

Users of the opt-in, experimental NRT segment replication that commit replicas while the primary keeps refreshing, since 6.0.0. The label is wrong whenever a point is installed between the commit's capture and its version read, mostly the fsync (natural rate not measured); harm needs a primary started on that commit without re-committing and a log replay from getLastCommitVersion().

Mechanism, terms and numbers549 words

In lucene-replicator's NRT segment replication, ReplicaNode.commit() captures the current SegmentInfos under the node monitor, fsyncs their files while holding only its separate commitLock, and only then writes VERSION_KEY into the commit data from getCurrentSearchingVersion(), the version of whatever searcher is current at that moment. Installing a new NRT point takes only the node monitor, so a point that arrives during the fsync becomes the label of an older commit: in the repro the commit holds version 3 (1 document) and says 5 (2 documents). A PrimaryNode started on that commit returns 5 from getLastCommitVersion(), and an application that replays its operation log from that version after a failover or a cold start, as the module's own stress test does, skips the operations in between: adds are lost and deletes and updates undone. The committed index itself is consistent and Lucene never reads the value on a replica. The code dates from the feature's first commit (LUCENE-5438) and ships in every release from 6.0.0 to 10.6.0; the one-line fix VERSION_KEY = infos.getVersion() passes the repro and the module's nightly suites.

Step by step, on the repro

#
  1. Capture. Under the node monitor commit() takes the current SegmentInfos (version 3, 1 document) and increfs its files (ReplicaNode.java:350-354). That object is not changed later: installing a point builds a new SegmentInfos and swaps it in (:433-440; SegmentInfosSearcherManager.java:92-101 updates the new object's generation, not the old one's).
  2. Unlocked fsync. dir.sync(indexFiles) runs holding only commitLock (:365). newNRTPoint is synchronized on the node (:530) and finishNRTCopy installs the new point under the node monitor (:412, setCurrentInfos at :440); neither takes commitLock. launch(CopyJob) is documented as "Runs this job async'd" (:516-517), so the install normally runs on another thread while the commit fsyncs.
  3. Late read. After the fsync, VERSION_KEY comes from getCurrentSearchingVersion() (:369), which returns the current searcher's reader version (Node.java:167-174): 5, the point installed meanwhile.
  4. Write. infos.commit(dir) writes the captured version-3 infos with that user data (:373). The next comment (:375-377) says the current infos "may have changed while we were doing dir.sync above" and handles that for the generation, not for the version.
  5. Read back. A PrimaryNode opened on this commit keeps its VERSION_KEY ("keep current commitData version", PrimaryNode.java:99-114) and getLastCommitVersion() returns it (:187-198): 5, while the index holds 1 document. ReplicaNode itself reads only PRIMARY_GEN_KEY from a commit (:177).

When no point is installed between the capture and the late read, both give the same number, which is why idle commits are right (verifiers' idle-commit controls pass on stock).

Exposure and likelihood435 words
  • Who is hit. Applications that use lucene-replicator's NRT segment replication (PrimaryNode, ReplicaNode and CopyJob subclasses; the package is @lucene.experimental) and commit a replica while the primary keeps publishing points. The code is in every release since 6.0.0; it was reproduced on the releases listed under history with indexes of 1 and 2 documents, and nothing in the code path depends on the index size.
  • How often the label is wrong. Whenever a point is installed between a replica commit's capture, when it releases the node monitor (ReplicaNode.java:354), and its late version read (:369); nearly all of that window is the fsync of the index files (:365). Every repro forces the interleaving (the minimal one from inside Directory.sync, an instrumented schedule); the natural rate was not measured.
  • When it does harm. Only if a primary is later started on that replica commit without a fresh re-commit and the application replays an operation log from getLastCommitVersion(). Lucene's own stress test does that replay: it maps each published version to the log position saved before its flush (TestStressNRTReplication.java:276-294), reads the new primary's commit version (:702), looks up that version's log position (:466-474) and replays from it (:520). It re-commits a replica before a live promotion (:425-434), which normally replaces a skewed commit, but its random commits while replication runs (:322-338) and its cold start after the whole cluster is down (:970-979) do not (read, not executed).
  • What goes wrong then. The operations between the committed version and the stored one are skipped: adds are lost, deletes and updates undone. In an executed probe a delete and an update of a per-document access-control field made inside the window were both undone after promotion and replay from getLastCommitVersion() (7, while the commit held version 3); replaying from version 3 gave the right result. On stock main, 10.5.2 and 9.12.3 the probe's replay test fails and its control passes; with the fix both pass (run on main only). The probe is a custom in-process test.
  • What does not go wrong. The committed index is consistent: its files and SegmentInfos are right, only the label is ahead. No exception; assertions on or off make no difference.
  • Downstream. A public code search (2026-10-26, not exhaustive) found no use of the NRT replicator in Elasticsearch, OpenSearch or Solr, and two open-source ReplicaNode subclasses that never read getLastCommitVersion or VERSION_KEY.
  • Impact class: silent wrong results; priority low (opt-in experimental module, rare harm path, no report since 2016).

Minimal repro

#

One JUnit test in the module's test package: an in-memory primary and replica, empty documents, single thread, deterministic. The replica directory's sync() installs the newer point inside the commit's fsync, the interleaving a copy thread produces. Put it in lucene/replicator/src/test/org/apache/lucene/replicator/nrt/ and run it with gradle.

More files, environment, full output311 words

Only public and protected replicator API: an anonymous PrimaryNode and a small ReplicaNode subclass whose CopyJob copies the missing files with Directory.copyFrom and whose launch() runs the job at once; most of the file is that boilerplate, the scenario is 7 lines. Use this one test as the regression test too.

Why one thread is faithful: during dir.sync the commit holds only commitLock, while newNRTPoint and finishNRTCopy take only the node monitor, so a copy thread can install the point at exactly that moment. Running the install inside the first sync() after commit() starts makes that deterministic without a second thread, latches or sleeps. This is an instrumented, forced schedule: it shows that the locks allow the interleaving, not how often it happens naturally. The hunt's original two-thread test (a committer thread held in sync() by a latch) gives the same numbers and also starts a primary on the commit: getLastCommitVersion() = 5 with documents [d1].

Seeds DEADBEEF and 5EED1234 (3 iterations) fail the same way; the seed only drives the test framework's randomization.

Why it looks unintended

#
  • PrimaryNode.commit() accepts a lagging version because replay then means "replaying more ops than necessary"; a version ahead skips operations.
  • The module's stress test replays from the commit version a node "was guaranteed to already have indexed through".
  • commit()'s own comment says the infos "may have changed while we were doing dir.sync above".
The full argument281 words
  • The accepted error is a lag. PrimaryNode.java:222-224: "TODO (opto): it's a bit wasteful that we put "last refresh" version here, not the actual version we are committing, because it means on xlog replay we are replaying more ops than necessary."
  • The module's controller states the use. TestStressNRTReplication.java:462-465: "Get xlog location that this node was guaranteed to already have indexed through; this may replay some ops already indexed but it's OK because the ops are idempotent". :486-488: "the userData in its latest commit point tells us which version it had indexed up to, so we know where to replay from in the xlog."
  • The method knows the infos can change. ReplicaNode.java:375-377: "Notify current infos (which may have changed while we were doing dir.sync above) what generation we are up to".
  • Concurrent commits are designed for. The separate commitLock (:341) lets the fsync run outside the node monitor, and the stress test commits a random node while replication runs (:322-338). TestNRTReplication commits replicas only after they caught up, and the stress test's related assert (NodeProcess.java:77-78) cannot detect this skew, because the new primary's version is force-advanced past every published refresh.
  • Design intent. On LUCENE-5438 (#6501, 2015-03-02) the author, mikemccand, wrote that the test's transaction log shows how NRT points are "used to replay indexing events on primary crash so no indexed documents are lost".
  • Contract wording. Node.java:56-60: "Key to store the version in the commit data, which increments every time we open a new NRT reader." Thin, but it names the commit's version. The "never ahead" rule itself is inferred from PrimaryNode.java:222-224 and the stress controller; the javadoc does not state it.
The devil's-advocate check135 words

Strongest case for "intended" (the devil's-advocate verifier): the package is @lucene.experimental; the VERSION_KEY javadoc never says the value equals the committed version; the primary's own value is approximate, so the replica's getCurrentSearchingVersion() could be read as a "latest point searched" watermark; and the reference controller re-commits a replica before a live promotion, so a skewed commit is replaced before use.

Why it fails:

  1. The direction of the error: the only documented approximation is a lag, justified by replay repeating operations; a lead has no use and makes replay skip operations.
  2. The controller's own cold start and random commits use a replica commit without re-committing it (read).
  3. Experimental lowers the reach, not the correctness bar; no javadoc, test or issue documents a value ahead of the content. The adjudication found no works-as-designed argument that survives.

Suggested fix

#

Recommended A. Store the version of the captured infos (one line)

Store the version of the captured SegmentInfos: commitData.put(VERSION_KEY, Long.toString(infos.getVersion())) in ReplicaNode.commit(), one line. The repro passes, and so do the module's nightly suites with it: TestNRTReplication (13 tests) and TestStressNRTReplication (one run with a 304 s stress phase). Those suites are compatibility coverage; they do not force the interleaving.

Trade-offs

No adverse effect observed in the recorded tests. A replay from the stored version now repeats nothing and skips nothing. The stress test, which asserts that a new primary's commit version is in its version-to-log map (TestStressNRTReplication.java:475-484), passed with it; like the other suites it does not force the interleaving.

Trade-offs

Equivalent to A. Not run.

C. Hold the node monitor across the fsync

#

Makes commit and point install mutually exclusive, so the late read cannot see a newer point.

Trade-offs

Blocks every NRT install on that replica for the whole fsync of the index files, which the current code avoids by fsyncing outside the node monitor under its own commitLock. Not run; not recommended.

Downstream note

#

Downstream, an application that replays an operation log from getLastCommitVersion() loses the skipped operations, including deletes and access-control updates (an executed probe shows a deleted document searchable again), but no use of that replay pattern was found outside Lucene's own stress test.

How it was found

#

TLA+ model checking (TLC) of the NRT replication protocol, with commit() modelled as its two halves (capture under the lock, write after the unlocked fsync): the invariant "a commit's VERSION_KEY is never ahead of its content" failed in a 6-state trace. A JUnit then drove the same interleaving on the stock jars and was reduced to one test.

The method in full144 words
  • Method (formal): TLA+ model checking with TLC in a hunt unit on the NRT replication protocol. The finder's model splits commit() into two actions as in the Java, CommitCapture under the node lock and CommitWrite after the unlocked fsync, and checks CommitVersionSound == commit.versionKey <= commit.ver.
  • Signal. TLC reported the violation with a 6-state trace (294 distinct states, with assertions modelled off and on), also under the stress controller's discipline (202 states). With the fix modelled the invariant holds (7,836 distinct states for the commit model, 82,805 for the full model).
  • Caveat. The finder's record does not say whether a code-reading hypothesis came before the TLC run.
  • Reduction. A JUnit on the stock jars drove the same interleaving (a committer thread held in Directory.sync by a latch while the replica installed the newer point); it was later minimized to the single-threaded test above.

Impact note
Applications that use lucene-replicator's NRT segment replication (PrimaryNode/ReplicaNode/CopyJob subclasses, opt-in and @lucene.experimental), in every release since 6.0.0 and at any index size, get a replica commit whose VERSION_KEY is ahead of its content whenever a newer NRT point is installed during that commit's fsync of the index files (the window is the whole fsync; the natural hit rate was not measured), and are harmed only if they later start a primary on that commit without re-committing it and replay their operation log from getLastCommitVersion(), as Lucene's own stress-test controller does on a cold start: the operations between the committed version and the stored one are then skipped (adds lost, deletes and updates undone, executed in a probe), while the committed index itself stays consistent and Lucene never reads the value on a replica.
Summary
You run Lucene's NRT segment replication and call commit() on a replica while the primary keeps publishing NRT points, and during the commit's fsync the replica installs a newer point (version 5, documents [d1, d2]). You expect the commit's VERSION_KEY to name the version whose content it holds (version 3, [d1]), or at worst an older one, because the module uses that value as the place to resume replaying operations and PrimaryNode.commit accepts only a lagging value ('replaying more ops than necessary'). Instead commit() writes the SegmentInfos it captured before the fsync (version 3) but reads VERSION_KEY from the searcher that is current after it (5), so a primary started on that commit reports getLastCommitVersion()=5 while it holds only d1, and a replay from version 5 skips d2.
