ThaiRepeatFilter emits a word's Maiyamok repeat before the tokens stacked on that word, so IndexWriter rejects the document

With a filter such as KeywordRepeatFilter stacking a token on each word before ThaiRepeatFilter (new in 10.6.0), a Thai word ending in the repetition mark ๆ makes the stacked token land one position late with a start offset that goes backwards, and IndexWriter rejects the document.

The finding in 30 seconds

#

ThaiRepeatFilter queues a word's repeats and returns them on its next calls, with position increment 1, before it reads the next input token (ThaiRepeatFilter.java:63-71). A token stacked on the same word (position increment 0) is read only after the repeat, so it lands on the repeat's position with the word's earlier start offset.

Token streams and the Maiyamok, in one minute

#
  1. An analyzer turns text into tokens. Each token has a term, character offsets [start,end) into the text, and a position increment: 1 moves to the next position, 0 stacks the token on the previous one, as synonyms and KeywordRepeatFilter's copies do.
  2. Lucene's analysis docs make it a rule that positions never go backward and that tokens starting at the same position have the same start offset. IndexWriter checks, for every indexed text field, that start offsets never decrease, and rejects the document otherwise.
  3. Thai writes a repeated word with the mark ๆ (Maiyamok): เร็วๆ reads as เร็ว เร็ว. ThaiRepeatFilter strips the mark and emits the word a second time at the next position, with the mark's offsets.

The finding, step by step

#
  1. Build the analyzer WhitespaceTokenizer > KeywordRepeatFilter > ThaiRepeatFilter and index one TextField with เร็วๆ ("quickly"): the word เร็ว at offsets [0,4) plus the repetition mark ๆ (Maiyamok) at [4,5), which means "say the word twice".
  2. KeywordRepeatFilter passes on two copies of เร็วๆ [0,5) at the same position: the copy has position increment 0.
  3. You expect เร็ว [0,4) twice at position 0, the repeat เร็ว [4,5) twice at position 1, and the document indexed. That is exactly what you get with the two filters swapped.
  4. Instead ThaiRepeatFilter emits the first copy's repeat before it reads the second copy: positions 0, 1, 1, 2 with start offsets 0, 4, 0, 4. The copy moves to position 1 and its start offset goes backwards, so addDocument throws IllegalArgumentException: ... offsets must not go backwards startOffset=0,endOffset=4,lastStartOffset=4.

Who is affected

#

Custom analyzers on 10.6.0 or main with a token-stacking filter (KeywordRepeatFilter, a synonym, TypeAsSynonymFilter) before ThaiRepeatFilter: every document with a word that still has ๆ attached there is rejected, for any indexed text field. Whitespace and standard tokenizers always keep ๆ attached, ThaiTokenizer on some words (ดีๆ). ThaiAnalyzer and the documented ThaiTokenizer chain have no stacking stage.

Mechanism, terms and numbers393 words

ThaiRepeatFilter, new in 10.6.0, expands the Thai repetition mark ๆ (Maiyamok, U+0E46): for เร็วๆ it emits เร็ว [0,4) and then เร็ว again at the next position with the mark's offsets [4,5). It queues that repeat and returns it on the very next call, before it reads the next input token. A token that an earlier filter stacked on the same word with position increment 0 (a KeywordRepeatFilter copy, a synonym for a word written with ๆ attached, a TypeAsSynonymFilter type token) is therefore read only after the repeat: it lands one position late, and its start offset 0 comes after the repeat's 4. IndexWriter rejects start offsets that go backwards for every indexed field, so addDocument throws IllegalArgumentException and the document is not indexed, with assertions on and off. It needs a custom chain with a stacking filter before thaiRepeat and a word that still has ๆ attached when it gets there: whitespace and standard tokenizers always keep the mark attached, and ThaiTokenizer keeps it on some words (ดีๆ stays one token), so ThaiTokenizer > keywordRepeat > thaiRepeat is affected too. ThaiAnalyzer and the documented ThaiTokenizer > ThaiRepeatFilter chain have no stacking stage and are not affected.

Exposure and likelihood362 words
  • Who. Applications on 10.6.0 or main with a custom analyzer that puts a token-stacking filter before thaiRepeat: keywordRepeat, a synonym rule for a word written with ๆ attached (for example เร็วๆ => เร็วๆ, ด่วน), or typeAsSynonym. The trigger is a word that reaches thaiRepeat with ๆ attached (or a run ๆๆ kept as one token). The whitespace and standard tokenizers always keep the mark attached (verified by an independent reproducer); the classic, UAX29URLEmail and ICU tokenizers and the older synonym filter are in the finder's reach records.
  • ThaiTokenizer too. It splits the mark off some words (เร็วๆ gives เร็ว [0,4) + ๆ [4,5)) but keeps it on others (ดีๆ stays one token [0,3)) and keeps a standalone ๆๆ as one token. So ThaiTokenizer > keywordRepeat > thaiRepeat rejects ดีๆ (startOffset=0,endOffset=2,lastStartOffset=2) and มาก ๆๆ, while เร็วๆ alone passes; the swapped order accepts เร็วๆ นี้ ดีๆ (executed on main and 10.6.0).
  • Effect. Every document that contains such a word is rejected by addDocument with IllegalArgumentException, for any indexed text field (a plain TextField without indexed offsets too), with assertions on and off. The failure is loud. By IndexingChain's design (:1989-1994) the exception is non-aborting: only that document is marked deleted (it still uses a doc id) and the writer stays open (the diagram probe: numDocs() = 0 after commit(), writer open). The minimal repro does not index a second document.
  • Not affected. ThaiAnalyzer and ThaiTokenizer > ThaiRepeatFilter (no stacking stage), thaiRepeat placed before the stacking filter, and keywordRepeat > porterStem > removeDuplicates > thaiRepeat (the identical copy is removed before thaiRepeat).
  • How likely. Rare: the class is new (10.6.0, released 2026-10-29), and the documented chains, which have no stacking stage, are clean. Elasticsearch already exposes the filter as thai_repeat, so its users can build such a chain.
  • Also recorded, not verified further (finder and intended-behaviour verifier; the adjudication did not check these): with removeDuplicates after thaiRepeat the document is accepted but เร็วๆ นี้ is indexed with one position too many, and the same chain used at query time can turn a phrase into one that misses a document.

Why it looks unintended

#
  • The analysis docs require ("must") that tokens at one position share a start offset (package-info.java:401), and IndexWriter rejects start offsets that go backwards.
  • Neither the filter nor its factory restricts its input, and it is not @IgnoreRandomChains, so Lucene's random-chain test expects valid output after any filter.
  • Swapping the filters gives the expected stream; PR #16720 never considered stacked input.
The full argument216 words
  • Contract. PositionIncrementAttribute.java:30: "Set it to zero to put multiple terms in the same position". package-info.java:394-403, "How to not write corrupt token streams": "Positions must not go backward" and "Tokens that have the same start position must have the same start offset"; the output breaks the second at position 1. :341-343: synonyms "should be created at the same position as the original token", so stacked tokens are ordinary input.
  • No input restriction. The class javadoc (ThaiRepeatFilter.java:27-34) and the factory javadoc (ThaiRepeatFilterFactory.java:23-36) say nothing about stacked input, unlike WordDelimiterGraphFilter.java:41 and SynonymGraphFilter.java:74, which document that they cannot consume a graph. TestRandomChains puts a ValidatingTokenFilter ("offsets must not go backwards", ValidatingTokenFilter.java:113-121) after every stage (TestRandomChains.java:856, :909) for every filter not annotated @IgnoreRandomChains; ThaiRepeatFilter is not annotated. This shows the filter is eligible and every stage is checked, not that random testing was likely to hit this chain: TestRandomChains picks 0 to 4 random filters (:850) over random text, and an attached ๆ behind a stacking filter is unlikely.
  • Intent. CHANGES.txt:583-584 (GITHUB#16720) announces the filter "with exact OffsetAttribute and highlighter compatibility". Issue #16719 and PR #16720 never discuss stacked input; the PR's one comment (rmuir) is about term frequency. The upstream tests feed only unstacked streams.
The devil's-advocate check300 words

The case for intended. The documented chains put thaiRepeat after ThaiTokenizer with no stacking stage: the factory javadoc (ThaiRepeatFilterFactory.java:26-32) directly after it, ThaiAnalyzer.java:102-107 after the lowercase, decimal-digit and normalization filters. package-info.java:416-419 says token filters "should not modify offsets" and "should not insert positions", which this filter does by design. Lucene tolerates other position-inserting filters that mishandle stacked input: CJKBigramFilter.java:51 is annotated @IgnoreRandomChains(reason = "LUCENE-8092: doesn't handle graph inputs"). On that precedent issue (#9140, LUCENE-8092, still open) Uwe Schindler wrote (2017-12-16) "But I am not really sure if this is really a problem in real-world scenarios ... I think the above combination is useless in real-world, but maybe others make sense?", and rmuir wrote (2018-03-04) that CJKBigramFilter "isn't really prepared to handle an arbitrary input graph (or maybe even synonyms)" and "Maybe it should throw a clear exception if it encounters posinc=0 or poslen > 1 ?". A correct fix must buffer one position group.

Why it fails. Those are good-practice "should"s, while the "must" rules apply to the output; no input limit is documented and the class is not annotated. On the same issue rmuir also wrote (2018-03-04) "if offsets are broken, the tokenfilter is broken" and "This doesn't fix the fact the filter is buggy, we know that.", and Uwe's comment names reordering the tokens in the second filter as a way out, which is the shape of the fix below. The two executed reviews by another model family (OpenAI GPT-5.6) rated the intended case moderate; the independent reproducer and the intended-behaviour verifier likewise concluded that it does not make the behaviour intended. Uwe's real-world doubt and rmuir's exception idea support a Low tier and the risk that a maintainer documents the limit or makes the filter fail fast instead of changing the code, not "intended".

Suggested fix

#

Recommended Pass the stacked tokens through before the repeats

Make ThaiRepeatFilter read ahead after a word that has repeats: pass the tokens stacked on it (position increment 0) through first, expanding their own ๆ the same way, then emit the repeats position by position. Unstacked input gives exactly the old stream. Validated: the repro passes and all 57 tests of org.apache.lucene.analysis.th.* pass.

All options and trade-offs2 options · 593 words

One code fix was written and validated; the alternative is a documentation answer. A user workaround works on every affected version: put thaiRepeat before the stacking filter (... > thaiRepeat > keywordRepeat), which gives exactly the expected stream.

Pass the stacked tokens through before the repeats (validated by the checks) (recommended)

#

Written by the finder (ThaiRepeatFilter.java only, +134/-64). After a token that has repeats, read ahead: every following token with position increment 0 is stacked on it, so expand its own ๆ the same way and emit it first; then emit the repeats position by position (the first token at each new position with increment 1, the others with 0). The first non-stacked token read ahead is kept (captureState) for the next call, and the input is never read again after it returned false. Excerpt below.

// excerpt of the fix: after expand() found `count` repeats for the current token
State base = captureState();
List<List<State>> repeats = new ArrayList<>();
repeats.add(captureRepeats(count));
while (nextInputToken()) {
  if (posIncAtt.getPositionIncrement() != 0) {
    lookahead = captureState();   // next position: keep it for later
    break;
  }
  int stackedCount = expand();     // a stacked token: expand its own marks
  if (stackedCount < 0) continue;
  pending.add(captureState());     // emit it at the word's position
  repeats.add(captureRepeats(stackedCount));
}
// then queue the repeats position by position (increment 1, then 0) and return base

Trade-offs

  • The change is larger than the bug: it buffers one position group and restructures incrementToken. A reviewer flagged that as the main maintenance cost.
  • With the synonym rule เร็วๆ => เร็วๆ, ด่วน, the fixed stream still ends ด่วน [0,5) and เร็ว [0,4) at the same position, a graph end-offset mismatch that only ValidatingTokenFilter checks and IndexWriter accepts (inherent to splitting a token a synonym spans; a record of the finder, not part of this bug).

  • The finder's checks: a bounded-exhaustive model over all 14,775 streams of 1 to 4 Thai tokens (first token not a bare ๆ) with position increment 0 or 1 finds 9,331 offset-rule violations on stock and 0 with the fix, and unstacked streams are identical to stock (the model runs the real ThaiRepeatFilter class; its log does not record the classpath, but the file has only one version); a random test with a ValidatingTokenFilter after every stage (2 chains x 2,000 random Thai strings, then addDocument) fails on stock (seed DEADBEEF) and passes with the fix on 3 seeds (DEADBEEF, 5EED0001, 5EED0002); with the fix, the diagnostic stream equals the swapped-order control.

Document the limit

#

State in the class and factory javadoc that ThaiRepeatFilter must come before any filter that stacks tokens, and annotate it @IgnoreRandomChains, as for CJKBigramFilter. A variant a maintainer may prefer (rmuir's suggestion for CJKBigramFilter on #9140): throw a clear exception when the filter sees stacked (position increment 0) input, so the user gets a clear message instead of IndexWriter's; the document is still rejected.

Trade-offs

Cheap, but such chains still lose every document with an attached ๆ, and the CHANGES promise of exact offsets would need a caveat. Not run.

How it was found

#

Semi-formal. A sweep of analysis chains built from the SPI factories, checked at every stage against the token-stream rules, gave the lead. Bounded-exhaustive translation validation confirmed it: 9,331 of 14,775 streams of 1 to 4 Thai tokens (first token not a bare ๆ, position increment 0 or 1) broke the offset rule. One public-API JUnit test reproduces it.

The method in full165 words

Method: semi-formal, bounded-exhaustive translation validation, on main f794ff5a505c, 2026-11-09.

LFV-1452, snapshot of 2026-11-10

Registry title
ThaiRepeatFilter (new in 10.6.0) emits the repeats of a word ending in the Thai repetition mark Maiyamok (U+0E46) before the tokens stacked on that word (a KeywordRepeatFilter copy, a synonym, a TypeAsSynonymFilter type token), so the stacked token moves one position later with a start offset that goes backwards and IndexWriter rejects the document
Area
analysis / Thai (ThaiRepeatFilter emission order; a custom chain with a token-stacking filter before thaiRepeat)
Priority
Low, rank 638: ThaiRepeatFilter, new in the 10.6.0 release, makes IndexWriter reject every document that holds a word written with the Maiyamok mark when a token-stacking filter such as KeywordRepeatFilter or a synonym rule runs before it and the mark is still attached to the word there (always behind the whitespace or standard tokenizer, on some words behind ThaiTokenizer). It is Low because that chain is rare, ThaiAnalyzer and the documented ThaiTokenizer chain are not affected, and the failure is loud and loses only that document.
Impact class
crash
Impact note
Only applications on 10.6.0 or main whose custom analyzer puts a filter that stacks position-increment-0 tokens (KeywordRepeatFilter, a synonym rule for a word written with an attached Maiyamok, TypeAsSynonymFilter) before ThaiRepeatFilter, on a word that still has U+0E46 attached when it reaches ThaiRepeatFilter (the whitespace and standard tokenizers keep it attached on every such word, ThaiTokenizer on some words such as ดีๆ, and the classic, UAX29URLEmail and ICU tokenizers on เร็วๆ, the word they were run on): every document that contains such a word is rejected by IndexWriter.addDocument with IllegalArgumentException, for any indexed text field (a plain TextField without offsets too), with -ea and -da [exec: whitespace and standard by the independent reproduction, ThaiTokenizer by the fact check's probe; classic, UAX29URLEmail and ICU in the finder's reach records]; ThaiAnalyzer and the documented ThaiTokenizer > ThaiRepeatFilter chain are not affected, and by IndexingChain's non-aborting design only that document is lost [read].
Summary
You build an analyzer whose chain stacks a second token on each word before ThaiRepeatFilter (for example WhitespaceTokenizer > KeywordRepeatFilter > ThaiRepeatFilter) and index the Thai word 'เร็วๆ' ('quickly': the word เร็ว [0,4) followed by the repetition mark Maiyamok [4,5)) in a plain TextField. You expect both copies of เร็ว [0,4) at position 0, the repeat [4,5) at position 1, and the document to be indexed. Instead ThaiRepeatFilter emits the first copy's queued repeat before it reads the stacked copy, so the stream is pos 0 [0,4), pos 1 [4,5), pos 1 [0,4), pos 2 [4,5): the stacked copy moves one position later, its start offset 0 comes after 4, and IndexWriter.addDocument throws IllegalArgumentException 'offsets must not go backwards startOffset=0,endOffset=4,lastStartOffset=4'.
