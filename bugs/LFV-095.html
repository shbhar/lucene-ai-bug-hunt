IndexWriter accepts doc-values updates of the reserved parent field, which breaks index-sorted document blocks

With index sorting and document blocks, IndexWriter marks the last document of each block in a reserved parent field, yet its doc-values update methods let the application rewrite that mark. One updateNumericDocValue call on a 2-document block is accepted and leaves a segment that fails CheckIndex.

The finding in 30 seconds

#

Background: document blocks in a sorted index

#
  1. Index sorting keeps the documents of every segment in the order of a sort, here a long field sort.
  2. addDocuments indexes a block, children first and the parent last; the block must stay together through sorting and merging.
  3. To find where blocks end, IndexWriter writes an internal mark, the parent field named by IndexWriterConfig#setParentField, on the last document of every block. A block sorts by its parent's value.

The finding, step by step

#
  1. Sort the index on a long field sort and set setParentField("_parent"). Add one block with addDocuments: a child (sort=9) and its parent (sort=1), and commit. IndexWriter marks the parent in _parent; the whole block sorts by its parent's value, 1.
  2. Call updateNumericDocValue(id:child, "_parent", -1) and close the writer. You expect an IllegalArgumentException: a document that contains _parent is rejected as "a reserved field", and an update of the sort field is rejected too.
  3. Instead the call is accepted. The child now carries a parent mark, so the segment reads as two blocks, [child] (sort 9) then [parent] (sort 1), which is out of order: CheckIndex reports segment has indexSort=<long: "sort"> but docID=0 sorts after docID=1.
  4. Removing a parent's mark instead (updateDocValues with a null value) is accepted too. If that block was the last one of its segment and every document there has a sort value, the next forceMerge throws EOFException and closes the writer; once the update has been committed, writers opened later fail the same way, while reads still work. Otherwise the orphaned documents silently join the next block.
  5. It fails with assertions on and off. Affected: every release from 9.10.0 (the first with setParentField) to 10.6.0, and main. Only an application that writes its own configured parent field can trigger it.

Who is affected

#

Applications that combine index sorting, document blocks and setParentField (opt-in; required for blocks with a sort since 10.0) and that send a doc-values update naming their own parent field. Untrusted documents cannot: the document path rejects the field. Unlikely, but silent at the call; it surfaces as a broken segment or a writer that can no longer merge.

Mechanism, terms and numbers835 words

With an index sort and IndexWriterConfig#setParentField, IndexWriter writes a reserved numeric doc-values mark on the last document of every block, and CheckIndex and merges use those marks to find block boundaries. A document that contains the field is rejected as "a reserved field", but IndexWriter's doc-values update methods check only index-sort fields, so an application can overwrite or erase a mark. Giving a child a mark splits its block inside an already sorted segment: one updateNumericDocValue call on a committed 2-document block leaves a segment that CheckIndex rejects (segment has indexSort=<long: "sort"> but docID=0 sorts after docID=1), with no merge. Removing a parent's mark leaves its block unmarked: if that block was the last one of its segment and every document there has a sort value, the next merge throws EOFException and closes the writer, and once the update is committed later writers fail the same way; otherwise the orphans silently join the next block. Every release from 9.10.0 to 10.6.0 and main is affected. Only an application that writes the field it configured as its parent field can trigger it, and cross-model reviews call that out of contract, so it reads best as missing input validation. Low priority; a 16-line check fixes it.

Terms

#
  • Index sort: IndexWriterConfig#setIndexSort. Every segment keeps its documents in that order, and CheckIndex checks it.
  • Document block: documents added together with addDocuments, children first and the parent last. IndexWriter guarantees that sorting and merging never reorder or split a block.
  • Parent field: IndexWriterConfig#setParentField("_parent"). IndexWriter writes _parent = -1 on the last document of every block (IndexingChain.java:166-169, :604-609, :645-651). A block sorts by its parent's value. From 10.0.0 a parent field is required to combine blocks with an index sort (MIGRATE.md:875-881).

The bug

#
  1. A document that names the parent field is rejected: "_parent" is a reserved field and should not be added to any document (IndexingChain.java:616-619, :748-750).
  2. The doc-values update methods have no such check. updateNumericDocValue (IndexWriter.java:1962), updateBinaryDocValue (:1996), updateSortedNumericDocValue (:2037) and buildDocValuesUpdate (:2081, which serves updateDocValues, softUpdateDocument(s) and tryUpdateDocValue) reject only index-sort fields (:1965, :2003, :2041, :2098). Once a block has been indexed, _parent is an existing doc-values-only NUMERIC field, which FieldInfos.verifyOrCreateDvOnlyField (FieldInfos.java:562-647) accepts.
  3. CheckIndex.testSort walks only the documents that carry the parent field and compares each block's parent with the next (CheckIndex.java:1255-1282). Merges build block boundaries from the field's current values and give each document the sort value of the next marked document (MultiSorter.java:52-63, :166).

The numbers (the repro)

#

Before the update the segment is doc 0 = child (sort=9, no mark) and doc 1 = parent (sort=1, _parent=-1): one block, trivially sorted. updateNumericDocValue(id:child, "_parent", -1) gives doc 0 a mark, and closing the writer commits it as a doc-values generation of the same segment. testSort now sees two blocks, compares 9 with 1 and reports segment has indexSort=<long: "sort"> but docID=0 sorts after docID=1. Nothing re-sorts the segment. If the marked child had its parent's sort value, CheckIndex would stay clean.

Removing a mark

#

updateDocValues(term, new NumericDocValuesField("_parent", (Long) null)) on a parent is accepted too. Its block's documents then have no mark of their own, and the next merge gives them the sort value of the next marked document of their segment (MultiSorter.java:166). What follows depends on the layout:

  • The block was the last one of its segment, and every document there has a sort value (the layout of every earlier test that threw): nextSetBit returns NO_MORE_DOCS, and the first forceMerge(1) reads past the end of the sort values and throws RuntimeException(EOFException) (from DirectReader via IndexSorter$LongSorter; a plain ByteBuffersDirectory throws IndexOutOfBoundsException). The writer closes with a tragic exception. If the update was committed before the merge, writers opened later fail their first forceMerge(1) the same way (three tried), while readers still open and search; if the merge ran before any commit, the tragic close drops the update and a new writer merges fine.
  • Another block follows in the same segment, or some documents have no sort value: nothing throws and CheckIndex stays clean, but the orphans silently become members of the next block.

After a mark is added and a merge runs, a block join can attribute a child to another root.

Without an index sort, a verifier's control stayed clean through later merges; merge-time reorderers such as BPIndexReorderer, which also read the mark, were not tested. Changing a parent's mark to another non-null value is harmless. Once a block exists, updateBinaryDocValue and updateSortedNumericDocValue already fail with a type-mismatch message, because the field is NUMERIC. On an index with no documents yet, updateDocValues even creates _parent with the type it is given; after a binary one, the writer's next block fails with cannot change field "_parent" from doc values type=BINARY to inconsistent doc values type=NUMERIC.

Exposure and likelihood291 words
  • Who is exposed. Only applications that (a) use index sorting with document blocks and setParentField, and (b) send a doc-values update (updateNumericDocValue, updateDocValues, softUpdateDocument(s) or tryUpdateDocValue) that names the field they configured as the parent field. The default configuration has no parent field. Untrusted documents cannot trigger it (the document path rejects the field), but an application that passes user-chosen field names to these update methods would pass the trigger on; that was not ruled out.
  • Silent at the call. The update returns a sequence number like any other. The damage shows later: CheckIndex rejects the committed segment, or the next merge fails and closes the writer.
  • Lasting, once committed. In the tested remove-a-mark layouts (the unmarked block last in its segment, a sort value on every document, forceMerge(1)), once the update had been committed each writer opened later failed its first forceMerge and closed, while reads kept working (three reopened writers tried). When the merge ran before a commit, the tragic close dropped the update and a new writer merged fine. A natural merge chosen by the merge policy was not tested.
  • Wrong block membership. After a mark is added and a merge runs, ToParentBlockJoinQuery mapped a child to another block's root; a removed mark that does not make the merge fail silently regroups documents into the next block.
  • Scale. Two documents and one call; deterministic.
  • How likely. Low: no legitimate workflow needs to write the parent field. A code read of Elasticsearch, OpenSearch and Solr found no default-configuration path that sends such an update (Solr only if an administrator declares its internal _is_root_ field as an in-place-updatable docValues-only field; not executed).
  • Not claimed. Wrong top hits from sort-based early termination were never verified.

Why it looks unintended

#
  • Lucene enforces the reservation elsewhere: a document that contains the field is rejected as "a reserved field".
  • Updates of index-sort fields are rejected, a guard added as a bug fix (LUCENE-7581: "would lead to corruption").
  • The mark exists "to maintain the API guarantee that the document order of a block is not altered by the IndexWriter" (setParentField javadoc).
The full argument258 words
  • Reserved, enforced by validation. IndexingChain.java:616-619 throws for a document that names the field; TestIndexSorting.testBlockContainsParentField asserts the message. The update API is a second public write path to the same field without that check.
  • The javadoc states the purpose (IndexWriterConfig.java:579-589): IndexWriter "will add an internal field to every root document", "In order to maintain the API guarantee that the document order of a block is not altered by the IndexWriter a marker for parent documents is required."
  • The same class is guarded, as a bug. LUCENE-7581 (2016) made IndexWriter reject doc-values updates of index-sort fields; its CHANGES entry says "since this would lead to corruption". #16565 (2026-08) added the missing guard to updateBinaryDocValue. TestIndexSorting.testBadDVUpdate asserts all four entry points.
  • The design discussion treats the field as IndexWriter's (#12829 review): its author called it "a field name that IW fully controls it's type and content" and "a purely internal field", and wrote "you can't use the parent field I think that is reserved for the top level"; a reviewer asked "are there any other restrictions on the use of the field? Could we clear up the javadoc to be more explicit?" and another answered "+1 to tighten up the language". Doc-values updates were not discussed. The #15960 commit message says the reserved mechanism existed "to guard the field name from external use".
  • Nothing permits it. No javadoc, MIGRATE entry, CHANGES entry or test covers a doc-values update of the parent field. The update javadoc (IndexWriter.java:1950-1961) asks only for an existing doc-values-only field, which _parent is.
The devil's-advocate check253 words

The cross-model reviews (OpenAI GPT-5.6, refute and works-as-designed lenses) made the strongest case: the parent field is documented as internal (IndexWriterConfig.java:579-589; MIGRATE.md:879, "The internally used parent field"), IndexWriter owns its values, and the application chose the name itself. Writing it through a generic API is mutation of writer-owned metadata, garbage in, garbage out; a missing check makes this hardening, not a correctness bug. Both rated it "not real", medium, while reproducing it and agreeing with the root cause and the fix. The cross-model fact check of this doc rated this case strong: a maintainer could reasonably close it as out of contract while still accepting the check as hardening.

Why it does not settle it: Lucene answers "callers might write the reserved field" with validation, already on the document path, and it fixed the closest analogue (updates of index-sort fields) as a bug; those fields belong to the application, so the precedent shows how Lucene treats updates that break the sort invariant, not that writer-owned fields are in contract. The update methods document their preconditions and _parent meets them; nothing in their javadoc excludes fields named in the writer config, and the other such field, the soft-deletes field, is updated through these very methods (a designed use), so the javadoc gives callers no hint. And the failure is silent at the call. What survives is the scope: it is missing input validation, with low likelihood, and only an application writing its own parent field triggers it. Verdict (adjudication): confirmed, medium.

Suggested fix

#

Recommended A. Reject the parent field in the four update entry points

Reject the configured parent field in IndexWriter's four doc-values update entry points with IllegalArgumentException, as the document path already does (+16 lines in IndexWriter.java). The repro, 12 related suites (383 tests) and the whole core index test package pass, and the change passes the core lint.

private void ensureNotParentField(String field) {
  String parentField = config.getParentField();
  if (parentField != null && parentField.equals(field)) {
    throw new IllegalArgumentException(
        "\"" + field + "\" is a reserved field and its doc values cannot be updated");
  }
}
// called first in updateNumericDocValue, updateBinaryDocValue and
// updateSortedNumericDocValue, and for each field in buildDocValuesUpdate

A. Reject the parent field in the four update entry points (validated by the checks) (recommended)

#

A private ensureNotParentField(field) helper in IndexWriter, called first in updateNumericDocValue, updateBinaryDocValue and updateSortedNumericDocValue, and for every field in buildDocValuesUpdate (which serves updateDocValues, softUpdateDocument(s) and tryUpdateDocValue). The message mirrors the document path's "is a reserved field".

private void ensureNotParentField(String field) {
  String parentField = config.getParentField();
  if (parentField != null && parentField.equals(field)) {
    throw new IllegalArgumentException(
        "\"" + field + "\" is a reserved field and its doc values cannot be updated");
  }
}
// called first in updateNumericDocValue, updateBinaryDocValue and
// updateSortedNumericDocValue, and for each field in buildDocValuesUpdate

Trade-offs

  • Runs before verifyOrCreateDvOnlyField, so the binary and sorted-numeric methods now say "reserved field" instead of the type-mismatch message, and updateDocValues cannot create the field with another type on an index without documents (executed).
  • Changes which error comes first: updateBinaryDocValue(parentField, null) now gets the reserved-field error instead of today's "cannot update a field to a null value" (executed), and an updateDocValues field named after the parent field is rejected before its doc-values type is checked.
  • The null-safe comparison keeps today's behaviour for a writer without a parent field and for a null field name.
  • Rejects whether or not an index sort is set, like the document path. Without a sort a verifier's control stayed clean (merge-time reorderers such as BPIndexReorderer, which also read the mark, were not tested), so a maintainer could limit the check to sorted indexes; rejecting always is simpler, keeps the field writer-owned and also protects code that reads the mark without an index sort.
  • Behaviour change: an application that writes its parent field through these methods now gets an exception; no upstream test or javadoc relies on that call.
  • Open PR #16810 edits the same four guard blocks (it merges the index-sort checks into one helper).
  • Worth adding: one sentence in the setParentField and update javadocs that the parent field cannot be updated (a reviewer asked for more explicit javadoc in #12829).

How it was found

#

While building an Alloy 6.2 model of index sorting with document blocks, the finder read IndexWriter's doc-values update guards and saw that they do not reject the parent field. The Alloy check MergeAfterParentDVUpdate then found a 2-document counterexample, and a JUnit test on the stock jars confirmed it. Semi-formal: the model encoded a hypothesis from code reading.

The method in full150 words

Method: an Alloy 6.2 model plus code reading, then JUnit (the hunt's "semi-formal" tier).

  • A hunt unit (index sorting with document blocks) modelled the flush sort and the merge of blocks in Alloy (SortBlocks.als). While modelling which inputs can change parent marks, the finder read IndexWriter's update guards (IndexWriter.java:1962-2110 at the time) and wrote the predicate goodInputsAfterParentDVUpdate: marks may differ from the block structure after a doc-values update.
  • The check MergeAfterParentDVUpdate (blocks preserved by the merge) was satisfiable: a 2-document counterexample in which a parent mark no longer matches its block.
  • The finder's JUnit tests (add a mark; remove a mark) then failed on the stock jars of main, 10.5.2, 9.12.3 and 9.10.0, with assertions on and off, and passed with a fix sketch.
  • It counts as semi-formal because the model encoded a hypothesis formed while reading the code and the tool then showed its consequence.

LFV-095, snapshot of 2026-11-02

Registry title
IndexWriter accepts doc-values updates of the reserved parent field; with index sorting and document blocks this leaves a segment that fails CheckIndex, or an index whose merges fail
Area
index / IndexWriter doc-values updates
Priority
Low, rank 955: IndexWriter accepts doc-values updates of the reserved parent field, which can damage index-sorted block indexes, but only through out-of-contract misuse, with a cheap reject fix.
Impact class
data corruption
Impact note
Only applications that use opt-in index sorting with IndexWriterConfig#setParentField and document blocks and that themselves send a doc-values update naming the field they configured as the parent field (documented as internal; the cross-model reviews call this out of contract), through updateNumericDocValue or a numeric field in updateDocValues, softUpdateDocument(s) or tryUpdateDocValue; untrusted documents cannot trigger it, no default-configuration path was found in Elasticsearch, OpenSearch or Solr (code reading), ordinary scale, released 9.10.0-10.6.0 and main.
Summary
You use index sorting with a parent field (IndexWriterConfig#setParentField) and document blocks, and call IndexWriter#updateNumericDocValue or #updateDocValues on that parent field, for example to give a child document a parent mark or to set a parent's mark to null. You expect the call to be rejected with IllegalArgumentException, as IndexWriter rejects doc-values updates of index-sort fields and any document that contains the parent field ('is a reserved field'), or else the index to stay valid. Instead the update is accepted: a child given a mark can put the segment out of index-sort order, so CheckIndex fails ('segment has indexSort=<long: "sort"> but docID=1 sorts after docID=2') as soon as the update is committed, and a removed mark makes the next merge throw EOFException in MultiSorter and close the writer when the unmarked block was the last of its segment and every document there has a sort value, and otherwise silently moves the orphaned documents into the next block.
