The bug in 30 seconds

#

The completion filter adds romaji tokens to each Japanese word, read from the bundled table romaji_map.txt, so a suggester can match Latin-letter input.

  1. You index チェック, イェール and ツァー as suggestions with JapaneseCompletionAnalyzer, plus the control シェア, and query with PrefixCompletionQuery.
  2. You expect chekku to suggest チェック, as shea suggests シェア: the javadoc lists modified Hepburn, where チェ is che, イェ ye and ツァ tsa, and the open-source Mozc input-method table accepts the same keystrokes.
  3. Instead chekku, ye and tsa return no suggestion, with no error. So do the input-method keystrokes dhisuku (ディスク), dhuetto (デュエット) and whokka (ウォッカ).
  4. Why: the table has シェ,sye,she and even ッイェ,yye, but no row for チェ or イェ. So チェ is split into チ (ti, chi) plus a small ェ (xe), and チェック becomes [チェック, tixekku, chixekku]; che is a prefix of neither.
  5. Kana typed through an input method (ちぇ, ちぇっk) still match, because both sides use the same split. Input-method users miss it only while a romaji prefix is pending: y, dh, w and wh (two keystrokes before うぉ), or ty/cy if they type ちぇ as tye/cye.

Who is affected

#

Applications using the opt-in JapaneseCompletionAnalyzer or JapaneseCompletionFilter (search servers expose it as kuromoji_completion), with default settings, in every release since 9.0.0. It hits loanwords with チェ, イェ, ツァ-ツォ, ディ, デュ or ウォ, such as チェック or ウォッカ. People typing raw romaji lose the suggestion; input-method users only while a romaji prefix such as y, dh, w/wh or ty/cy is pending.

Mechanism, terms and numbers632 words

Kuromoji's completion analyzer (JapaneseCompletionAnalyzer, JapaneseCompletionFilter) indexes each Japanese word together with its romaji spellings, so an autocomplete can match Latin-letter input. Its bundled table romaji_map.txt has rows for loanword sounds such as シェ (she), ジェ (je), ティ (thi), ウィ (wi) and even the doubled ッイェ (yye), but none for チェ, イェ, ツァ/ツィ/ツェ/ツォ, ディ, デュ or ウォ. Those kana are spelled out as base kana plus a small vowel (チェック → tixekku, chixekku; イェール → ixeーru; ツァー → tuxaー, tsuxaー), so typing the Hepburn spellings chekku, ye or tsa, or the input-method keystrokes dhi, dhu or who, suggests nothing, with no error. Kana typed through an input method still match. It affects every release from 9.0.0 to 10.5.2 and main; the fix is data only.

Terms

#
  • Extended katakana: two-kana units for sounds of loanwords, written with a small vowel: チェ (che, as in チェック "check"), イェ (ye, イェール "Yale"), ツァ (tsa, ツァー "tsar"), ディ (ディスク "disk"), デュ (デュエット "duet"), ウォ (ウォッカ "vodka").
  • Romanizations: modified Hepburn writes チェ, イェ, ツァ/ツィ/ツェ/ツォ as che, ye, tsa/tsi/tse/tso. The open-source Mozc input-method table accepts the same keystrokes and maps dhi, dhu, who to でぃ, でゅ, うぉ; a small vowel alone can be typed with x (xe → ぇ).
  • JapaneseCompletionFilter: for each word it emits the word itself and every romaji spelling of its katakana reading at the same position (generateOutputs, JapaneseCompletionFilter.java:217-233). The spellings come from romaji_map.txt, where each row maps a key to its spellings (for example シェ,sye,she); KatakanaRomanizer matches the reading longest key first and combines the spellings of the matched rows (KatakanaRomanizer.java:103-169). The javadoc lists "(modified) Hepburn-shiki, Kunrei-shiki (Nihon-shiki) and Wāpuro shiki" as supported (:41-42).
  • Completion query: PrefixCompletionQuery suggests a word when the typed text, after the QUERY-mode analyzer, is a prefix of one of the word's indexed forms. Raw romaji such as chekku comes out as the single token chekku.

Index-side tokens on main: チェック → [チェック, tixekku, chixekku], イェール → [イェール, ixeーru], ツァー → [ツァー, tuxaー, tsuxaー], ディスク → [ディスク, dexisuku], デュエット → [デュエット, dexyuetto], ウォッカ → [ウォッカ, uxokka]; compare シェア → [シェア, syea, shea]. The code follows the table: romanize() matched a separately coded longest-match model of the same table, bounded-exhaustively, on all 1,830,854 inputs of length up to 3 and on 57,289,761 inputs of length 4 (0 mismatches; a shortest-match mutant was caught). That shows implementation and model agree over the tested domain; the gap itself is in the data rows.

Exposure and likelihood265 words
  • Who. Applications that build Japanese autocomplete with JapaneseCompletionAnalyzer or JapaneseCompletionFilter (also through the analysis SPI as japaneseCompletion; search servers built on Lucene expose it as a kuromoji_completion token filter). Opt-in; it reproduces with the default constructors, the standard INDEX/QUERY configuration and no user dictionary.
  • What triggers it. Loanwords whose reading has チェ, イェ, ツァ/ツィ/ツェ/ツォ, ディ, デュ or ウォ, typed as raw romaji: チェック chekku, イェール ye..., ツァー tsa..., and with the input-method keystrokes ディスク dhi..., デュエット dhu..., ウォッカ who.... No special input, no scale. How often such words occur was not measured.
  • Two groups of users. People who type romaji directly lose the suggestion for these words; raw romaji is a designed input (the introducing issue wants 桜 suggested for "さ", "サ" or "sa"). Input-method users lose it only while a romaji prefix is pending, before the kana appear: y (before いぇ), dh (before でぃ/でゅ), w and then wh (before うぉ, two keystrokes), and ty/cy if they type ちぇ as tye/cye (the Mozc table maps both).
  • What still works. Kana committed or composed through an input method (ちぇ, ちぇっk, いぇ, つぁ, でぃ, うぉ) and the explicit small-vowel spellings (chixe, ixe, tsuxa, dexi, uxo).
  • Silent. No exception, no log line: the suggestion list is just shorter.
  • After a fix the index-side tokens change, so existing suggest fields must be reindexed. The query side needs no change; QUERY mode loads the same table, so kana queries gain the new spellings too (ちぇ → [ちぇ, tye, che, cye, tixe, chixe]).

Why it is a bug, not intended

#
  • The javadoc lists "(modified) Hepburn-shiki": there チェ, イェ, ツァ are che, ye, tsa, as Lucene's reading-form romanizer also emits.
  • The table has シェ,sye,she, ティ,thi,texi, ウィ,wi, even ッイェ,yye, but no チェ, ディ, ウォ or イェ row.
  • The docs name one deviation (long vowels, as an example) and explain none of these gaps; in review, a missing jji was added on request.
The full argument474 words
  • The contract names modified Hepburn. JapaneseCompletionFilter.java:41-42 and romaji_map.txt:3 list "(modified) Hepburn-shiki" as supported. The module's Hepburn romanizer ToStringUtil maps チェ → che (:481), イェ → ye (:304) and ツァ/ツィ/ツェ/ツォ → tsa/tsi/tse/tso (:489-498), and TestToStringUtil asserts these (:154, :187-191). That romanizer has a different contract: it gives one modified-Hepburn reading per token for JapaneseReadingFormFilter (ToStringUtil.java:240, JapaneseReadingFormFilter.java:84-87), not a list of accepted keystrokes, so it corroborates the spellings but does not bind the completion table.
  • The disclaimer's example does not explain it. JapaneseCompletionFilter.java:44-48: "This does not strictly comply with the romanization systems listed above, but tries to cover possible keystroke supported by various Input Methods. e.g.: Circumflex / Macron representing Chōonpu (長音符) are not supported." Its one example of a deviation is the long-vowel mark; it is introduced with "e.g.", so it need not be the full list. che, ye, tsa, dhi, dhu and who are keystrokes the open-source Mozc romaji table accepts (it maps them to ちぇ, いぇ, つぁ, でぃ, でゅ, うぉ), so the stated aim of covering input-method keystrokes argues for them.
  • The table is inconsistent with itself. ッイェ,yye but no イェ; シェ, ジェ and チャ/チュ/チョ but no チェ; ティ/テュ but no ディ/デュ; ウィ/ウェ but no ウォ. It does have クァ, グァ, トゥ, ドゥ and ヴァ (:121-154), which the 1991 government notice on loanword spelling puts in its second, less common table, while its first table has チェ, ツァ/ツェ/ツォ, ディ and デュ (the intended-behaviour checker's reading of the notice).
  • The author's own reference has the rows. In #11140 the author named a comparison of romaji tables as a reference; its input-method loanword row lists sye she, zye je, tye che, tsa tsi tse tso, thi, thu, dhi, dhu, ye, who. Lucene's table has sye/she, zye/je, thi and thu but none of the others; nothing shows how the author picked entries from it (the intended-behaviour checker's reading of the page).
  • The same kind of gap was fixed on request. In the review of PR #297, a reviewer (GitHub johtani) asked on the ッジ,zzi row "Should we add jji? I usually use jajji for ジャッジ"; the author (GitHub mocobeta) answered "yes, of course" and added it.
  • Nothing pins the current spellings. No completion test covers these kana, no comment, CHANGES or MIGRATE entry mentions them, and an anchored exact-key git log --all -G search finds no commit that ever added or removed such a row.
  • Not proof of intent either way. No javadoc, test, CHANGES entry, commit message, saved PR text or code comment explains the absence of these rows; the points above support an undocumented omission, which maintainers may also label an alias-coverage improvement.
The devil's-advocate check215 words

The strongest case (the cross-model review and the intended-behaviour checker): the header says the table "does not strictly comply" and only "tries to cover" keystrokes, and every extended katakana already has some spelling through the small-vowel rows (chixe, ixe, tsuxa, dexi, uxo all work), so this is missing coverage, an enhancement, not a broken contract. ToStringUtil serves another contract, and every extra alias multiplies the indexed forms (a separate unbounded-expansion issue).

Why it is weaker than it looks: the one deviation the documentation names is the long-vowel mark (as an example, not a full list); the module's own Hepburn romanizer and its test use che, ye and tsa; the table covers the siblings and even the doubled ッイェ while missing イェ, which no coverage policy explains; and in the original review a spelling that a reviewer said they usually type (jji) was added as an omission. The best-effort wording, the separate ToStringUtil contract and the token cost lower the priority and may decide the label (bug or improvement); none of them shows that the gap was intended. Not claimed: Hepburn di, dyu, wo for ディ, デュ, ウォ, which this table already uses for ヂ, ヂュ and ヲ (:55, :60, :118).

Trade-offs

  • Every extra spelling multiplies a word's romaji tokens (the product in KatakanaRomanizer.java:138-156): チェ goes from 2 to 5 spellings, ツァ-ツォ from 2 to 3, the others from 1 to 2, so チェック goes from 2 romaji tokens to 5. That slightly enlarges a separate unbounded-expansion issue (different fix site); the module's random and huge-string tests still pass.
  • The ッ-prefixed forms (ッチェ, ッツァ, ...) still use the fallback; the table has no ッシェ or ッジェ row either, so adding them is a separate consistency step.
  • Existing suggest fields must be reindexed to gain the new tokens. The query side needs no code or configuration change (kana queries gain the new spellings too).

How it was found

#

A probe compared the romanizer with ICU4J's Katakana-Latin output for 132 hand-listed katakana units and flagged 23, among them チェ, イェ, ツァ-ツォ, ディ, デュ and ウォ. A model of the table's sibling rows located the gaps; a bounded-exhaustive check found KatakanaRomanizer matching an independent longest-match model on all 59 million tested inputs.

The method in full249 words
  • First signal. A planning probe compared the stock KatakanaRomanizer with the Latin spelling that ICU4J's Katakana-Latin transliterator gives (Hepburn che for チェ, but ie, uo and tsua for イェ, ウォ and ツァ) for a hand-listed chart of 132 gojūon, yōon and extended-katakana units, and flagged 23 units whose ICU spelling the romanizer does not produce, among them チェ, イェ, ウォ, ディ, デュ and ツァ-ツォ; an end-to-end probe showed chekku, disuku and wo suggesting nothing on the stock main jars.
  • Table laws. A model of the table's own regularities: law L4 (sibling-family closure) finds シェ/ジェ present but チェ absent, ウィ/ウェ but not ウォ, ッイェ but not イェ, no ツ+small-vowel row, and テァ-テョ without voiced デ rows.
  • Translation validation (bounded-exhaustive). Part A: romanize() equals an independent longest-match model of the table on all 1,830,854 inputs of length up to 3 and 57,289,761 inputs of length 4 (0 mismatches; a shortest-match mutant: 33,518 mismatches), so the defect is in the data. Part B: the Hepburn images of these extended katakana are missing (che, ye, tsa, ...; the colliding di, dyu, wo are not claimed). Part C: typing ye through a model input method (the open-source Mozc romaji table) already fails at the state y.
  • Reduction. A public-API JUnit with the document suggester on the stock main jars (2026-10-28), then this doc's kuromoji-only test.
  • Tier. Non-formal first signal: a check against another implementation's output; the table-law model and the bounded-exhaustive checks came after it.

LFV-850, snapshot of 2026-10-29

Registry title
Kuromoji's completion table romaji_map.txt has no rows for チェ, イェ, ツァ/ツィ/ツェ/ツォ, ディ/デュ and ウォ, although it has rows for their siblings (チャ/チュ/チョ, シェ/ジェ, ッイェ, ティ/テュ, ウィ/ウェ), so raw-romaji prefixes such as 'che', 'ye' and 'tsa' suggest nothing for words like チェック, イェール and ツァー
Area
analysis / kuromoji (JapaneseCompletionFilter and JapaneseCompletionAnalyzer romanization data: the bundled table romaji_map.txt that KatakanaRomanizer reads)
Priority
Low, rank 419: The opt-in completion table has no rows for loanword kana such as チェ, イェ, ツァ, ディ and ウォ, so those suggestions are lost silently but only when the loanwords are typed in raw romaji, which puts it with the Kuromoji romanization rare-input rows right after LFV-605.
Impact class
silent wrong results
Impact note
Applications that use the kuromoji JapaneseCompletionAnalyzer or JapaneseCompletionFilter for Japanese auto-completion (an opt-in module analyzer; default constructors, INDEX and QUERY mode) silently get no suggestion when a user types the usual raw-romaji spelling of a loanword with チェ, イェ, ツァ/ツィ/ツェ/ツォ, ディ, デュ or ウォ (chekku for チェック, ye for イェール, tsa for ツァー, and the IME keystrokes dhi, dhu and who), because these kana are indexed only through the small-vowel fallback (tixekku/chixekku, ixe, tuxa/tsuxa, dexi, dexyu, uxo), while queries composed in kana, even partly (ちぇっk), and the small-vowel spellings still match; no scale is needed, nothing fails or throws, and every release from 9.0.0 to 10.5.2, branch_10_6 (10.6.0) and main are affected.
Summary
You index ordinary loanwords such as チェック, イェール, ツァー, ディスク or ウォッカ with JapaneseCompletionAnalyzer and expect a user who types the usual romaji, che(kku), ye or tsa (or the IME keystrokes dhi, dhu, who), to get them as suggestions, because the analyzer lists (modified) Hepburn, Kunrei-shiki and Wapuro romanization as supported and its table already has these spellings for the sibling kana: シェ she, ジェ je, チャ cha, ティ thi, テュ thu, ウィ wi, ウェ we and even the doubled form ッイェ yye. Instead romaji_map.txt has no row for チェ, イェ, ツァ, ツィ, ツェ, ツォ, ディ, デュ or ウォ, so KatakanaRomanizer splits each into its base kana plus a small vowel (チ+ェ -> tixe/chixe, イ+ェ -> ixe, ツ+ァ -> tuxa/tsuxa, デ+ィ -> dexi, ウ+ォ -> uxo) and these raw-romaji queries suggest nothing. Queries typed in kana, including partly composed ones such as ちぇっk, still match, because the index and query sides use the same fallback.
