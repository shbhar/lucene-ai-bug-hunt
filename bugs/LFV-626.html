A failing keepFullyDeletedSegment check during an NRT open leaks the segment's reader

If the merge policy's keep check for a fully deleted segment throws during an NRT open (say, SoftDeletesRetentionMergePolicy's retention query fails once), the segment reader Lucene just opened is never released, and its files stay open after IndexWriter.close(). Every release from 7.4.0 to 10.6.0 has it.

The finding in 30 seconds

#

Lucene opens the segment's reader first, asks the merge policy second, and lists the reader for cleanup third. A throw in step two skips step three, so nothing ever releases that reader.

Background: fully deleted segments and the keep check

#
  1. With soft deletes, an update marks the old document as deleted through a doc-values field instead of removing it. A segment whose documents are all deleted is normally dropped.
  2. SoftDeletesRetentionMergePolicy can keep such a segment: its keepFullyDeletedSegment runs your retention query against the segment and keeps it when the query matches a document.
  3. Every NRT open (DirectoryReader.open(writer), openIfChanged, a SearcherManager refresh) opens one reader per segment and runs this keep check for each fully deleted one.

The finding, step by step

#
  1. Use soft deletes with SoftDeletesRetentionMergePolicy and the retention query MatchAllDocsQuery. Index one document, flush, soft-update it and close the writer: segment _0 now holds 1 document, 0 of them live, and the retention query keeps it (the replacement document goes into a second segment, _1).
  2. Open a new IndexWriter and call DirectoryReader.open(writer) while the retention query supplier throws once. The open fails with that exception, as it should.
  3. You expect the failed open to give back what it opened, so that after writer.close() no file of the index is open.
  4. Instead 4 files of _0 stay open: _0.cfs and _0_1_Lucene90_0.dvd, .dvp and .dvs. Lucene had opened a reader for _0, then asked the merge policy whether to keep it; the check threw before the reader was added to the list that the failure handler releases.

Who is affected

#

Opt-in: applications that use soft deletes with SoftDeletesRetentionMergePolicy (or a merge policy whose keep check can throw) and open NRT readers. Each failure leaks one segment's reader, which close() does not release; 10 failing cold-writer reopens left 40 files open. Results and the index stay correct. The default merge policy never throws here.

Mechanism, terms and numbers684 words

When IndexWriter opens an NRT reader, StandardDirectoryReader.open(IndexWriter, ...) obtains a read-only SegmentReader for each segment and, for a segment with no live documents, asks the merge policy whether to keep it: reader.numDocs() > 0 || mergePolicy.keepFullyDeletedSegment(() -> reader). Only after that is the reader added to the readers list, and the method's failure handler releases only that list. keepFullyDeletedSegment is public and declared throws IOException, and the stock SoftDeletesRetentionMergePolicy runs the application's retention query against the segment there. If the check throws, the open fails as it should, but the reader that was just obtained is neither listed nor returned, so nothing releases it: the segment's core and its files stay open after IndexWriter.close() and rollback. The cleanest trigger is the first NRT open of a freshly opened writer over a commit that holds a retained, fully soft-deleted segment; on a writer that already pools the segment, a persistent failure is thrown earlier, in IndexWriter.writeReaderPool, and leaks nothing. No wrong results and no index damage. The gap came with LUCENE-8233 (ecc17f90233, 2018) and is in every release from 7.4.0 through 10.6.0 and in main; releasing the reader when the keep decision throws fixes it.

Terms

#
  • Read-only clone: the SegmentReader that IndexWriter.getReader hands to the NRT reader, rld.getReadOnlyClone(IOContext.DEFAULT) (IndexWriter.java:554). It holds a reference on the segment's core, which owns the open files; the writer releases only its pool handle (:561).
  • Keep check: MergePolicy.keepFullyDeletedSegment(IOSupplier<CodecReader>), public, non-final and declared throws IOException; the default returns false (MergePolicy.java:760-768).

The bug

#
  1. IndexWriter.getReader calls writeReaderPool (IndexWriter.java:608), then StandardDirectoryReader.open(this, readerFactory, segmentInfos, ...) (:613-615).
  2. The loop in StandardDirectoryReader.open(IndexWriter, ...) (StandardDirectoryReader.java:129-146):
final SegmentReader reader = readerFunction.apply(info);                       // :136 obtained
if (reader.numDocs() > 0
    || writer.getConfig().mergePolicy.keepFullyDeletedSegment(() -> reader)) { // :137-138 may throw
  // Steal the ref:
  readers.add(reader);                                                         // :140 listed
  1. The failure handler releases only the list: catch (Throwable t) { ... IOUtils.applyToAll(readers, SegmentReader::decRef); ... throw t; } (:158-165). A throw at :138 skips :140.
  2. Nothing else can release the reader. getReader's own catch block closes r, still null because the open never returned, and onGetReaderMergeResources (IndexWriter.java:711-721), which is set only after a successful open (:649-666). getReader also records each clone in a local map, openedReadOnlyClones (:556-558, when maxFullFlushMergeWaitMillis > 0, the default), but reads it only after a successful open (:684-694). close() and rollback() release the pool's readers, not this clone.
  3. writer.incRefDeleter(segmentInfos) (StandardDirectoryReader.java:148) has not run yet, so file-deletion bookkeeping stays consistent: the leak is open handles and memory only.
  4. SoftDeletesRetentionMergePolicy.keepFullyDeletedSegment calls retentionQuerySupplier.get() (SoftDeletesRetentionMergePolicy.java:86) and runs the query on the segment (:84-91), so a throwing supplier or a read error there is enough.

When it leaks

#
  • Cold writer (the clean case). writeReaderPool first runs the same check, but only for segments already in the reader pool (IndexWriter.java:4128-4140, readerPool.get(info, false) at :4131). On the first NRT open of a new writer the segment is not pooled yet, so StandardDirectoryReader.open runs the only check and any failure leaks.
  • Warm writer. A persistent failure is thrown in writeReaderPool, before any reader is obtained, and leaks nothing; only a transient failure that hits the second check leaks, re-pinning the existing core with no new handles.
  • Merge-on-refresh. IndexWriter.maybeReopenMergedNRTReader uses the same method and says it "will take care of closing" the readers it is handed (IndexWriter.java:766-771); same window, not executed.

Exposure and likelihood283 words
  • Who is hit. Applications using soft deletes with SoftDeletesRetentionMergePolicy, or any merge policy whose keepFullyDeletedSegment can throw, that open NRT readers from their writer (DirectoryReader.open(writer), openIfChanged, SearcherManager). The default MergePolicy.keepFullyDeletedSegment returns false with no I/O; in core only SoftDeletesRetentionMergePolicy does real work there (NoMergePolicy and FilterMergePolicy delegate). Downstream, Elasticsearch's engine passes a sequence-number retention query to the stock SoftDeletesRetentionMergePolicy (code read only, not run).
  • What it takes. A fully soft-deleted segment that the retention query keeps, and an exception inside the keep check when StandardDirectoryReader.open runs it: an I/O error while the retention query reads that segment, or a throwing retention query supplier. Cleanest on the first NRT open of a freshly opened writer. Exceptions inside this keep check have been reported on another call site (#13353 and elastic/elasticsearch #105122, #105474, #99075; no leak reported there).
  • What happens. One SegmentReader per failure stays open (in the repro the compound file and three doc-values update files); IndexWriter.close() and rollback do not release it. No wrong results: the failed open returns no reader, and under a SearcherManager 20 of 20 failed refreshes kept serving the previous reader with the soft-deleted document hidden.
  • Scale. 10 cold-writer reopens while the check kept failing left 40 inputs open, and under MMapDirectory 40 mappings still listed in /proc/self/maps at the end of the loop (48 after a later successful open and close); 0 with the fix. Warm-writer repeats re-pin the same core and add no handles. Not tested: Windows (open files cannot be deleted), disk space of deleted-but-open files, heap of a large core.
  • Rating. Minor, likelihood rare, priority low: an exceptional event at one specific step, silent outside a leak-checking test framework.

Why it looks unintended

#
  • The method's catch block releases every reader it obtained (LUCENE-5262); this one escapes only because it is not in the list yet.
  • TestIndexWriterReader#testNRTOpenExceptions: failed NRT opens must not "leak file handles".
  • keepFullyDeletedSegment is declared throws IOException, and the stock retention policy runs a query inside it.
The full argument193 words
  • The catch block's purpose. StandardDirectoryReader.java:158-165 decRefs every reader the loop took. It goes back to LUCENE-5262 (#6326, 2013) and was rewritten by LUCENE-8215 (2e35ef2b3da, 2018-03-19), two weeks before the keep hook arrived.
  • Lucene's own test. TestIndexWriterReader#testNRTOpenExceptions (TestIndexWriterReader.java:1108-1110): "LUCENE-5262: test that several failed attempts to obtain an NRT reader don't leak file handles." It ends with the same MockDirectoryWrapper open-files check as the repro (dir.close(), :1152).
  • A declared exception. keepFullyDeletedSegment is public, non-final and declared throws IOException (MergePolicy.java:765-766); SoftDeletesRetentionMergePolicy does query I/O inside it (SoftDeletesRetentionMergePolicy.java:80-94).
  • Ownership is handed over. IndexWriter.java:769-771: "as soon as we remove the reader and return it the StandardDirectoryReader#open will take care of closing it."
  • The other keep-check site that holds readers releases them in a finally block (IndexWriter.closeSegmentStates, IndexWriter.java:6743-6762).
  • An oversight in history. Before LUCENE-8233 (ecc17f90233, 2018-04-04) the condition used writer.getKeepFullyDeletedSegments(), a package-private boolean getter that cannot throw; that commit put the public throwing hook in the same spot. No comment on #9280, no CHANGES or MIGRATE entry, test or issue sanctions the leak, and no upstream test throws from the hook.
The devil's-advocate check126 words

The strongest case for "intended" (the intended-behaviour devil's advocate and the cross-model reviewer's intended lens, which rated it moderate): MergePolicy, SoftDeletesRetentionMergePolicy and DirectoryReader.open(IndexWriter) are @lucene.experimental, no javadoc promises cleanup after a merge-policy callback throws, the finder's trigger was a synthetic call-stack-filtered fault, and on a warm writer a persistent failure is caught earlier with no leak.

Why it does not hold up: @lucene.experimental is about API stability, not resource safety; the hook is declared to throw IOException; the release-on-failure catch block and testNRTOpenExceptions show the intent; the minimal repro uses only stock classes, with no subclass and no call-stack filter; and the warm-writer pre-check narrows how often it happens, not whether it is a leak: on a freshly opened writer any failure leaks.

Suggested fix

#

Recommended A. Release the reader when the keep decision throws

In StandardDirectoryReader.open, wrap the keep decision in try/catch and decRef() the not-yet-listed reader before rethrowing, suppressing a secondary failure (+15/-2 lines). The repro then passes with assertions on and off, and 6 neighbouring index test classes plus the repro (135 tests, testNRTOpenExceptions among them) pass, as do the format and lint checks.

All options and trade-offs2 options · 465 words

One option was run through gradle in a scratch worktree of 645d4fe14a20 and is recommended; the alternative was not run.

A. Release the reader when the keep decision throws (validated by the checks) (recommended)

#

Compute the keep decision inside try; on any Throwable, decRef() the reader that is not in readers yet (adding a secondary failure as suppressed) and rethrow, the same pattern as the method's outer catch block. The original exception still propagates. It covers both callers of the method, getReader and the merge-on-refresh reopen (IndexWriter.java:766); the second was not executed. The snippet is a hunk of the full diff, which applies with git apply at 645d4fe14a20.

         final SegmentReader reader = readerFunction.apply(info);
-        if (reader.numDocs() > 0
-            || writer.getConfig().mergePolicy.keepFullyDeletedSegment(() -> reader)) {
+        final boolean keep;
+        try {
+          keep =
+              reader.numDocs() > 0
+                  || writer.getConfig().mergePolicy.keepFullyDeletedSegment(() -> reader);
+        } catch (Throwable t) {
+          // the reader is not in readers yet, so the catch block below would not release it
+          try {
+            reader.decRef();
+          } catch (Throwable t1) {
+            t.addSuppressed(t1);
+          }
+          throw t;
+        }
+        if (keep) {
           // Steal the ref:
           readers.add(reader);

Trade-offs

  • On the success path nothing extra runs beyond entering the try block (not benchmarked); the default merge policy never throws here.
  • It does not change when the check runs or what it returns, and touches one method.

Earlier, the finder's identical change made every verifier's repro and the security probe pass (every leak count 0), and a cross-model reviewer ran TestSoftDeletesRetentionMergePolicy with it (14 tests, 0 failures).
  • Not run: the full Lucene test suite.

B. Add the reader to the list before the check (not run)

#

Add the reader to readers right after readerFunction.apply(info), so the existing catch block owns it, and when the segment is not kept, remove it from the list again before the decRef() and segmentInfos.remove(infosUpto).

Trade-offs

No new try, but it restructures the loop and needs care that a reader removed from the list is decRef'd exactly once.

Downstream note

#

Elasticsearch's engine configures the stock SoftDeletesRetentionMergePolicy with a sequence-number retention query (code read only, not run), so a keep-check failure on its NRT path would leak the same way.

How it was found

#

Non-formal: a randomized stress test of IndexWriter with a sequence-number replay oracle and one injected fault per round. At the keepFullyDeletedSegment fault site, 40 of 54,400 rounds left files open after IndexWriter.close(). Reading the code gave the root cause, and the case was reduced to a single-thread JUnit test.

The method in full102 words

Method: non-formal baseline (randomized stress with injected faults, then executed tests). An earlier hunt unit's stress harness saw the open-files failure in 6 rounds and recorded the root cause by code reading as a lead. A later unit completed that harness: it saw MockDirectoryWrapper report open files after IndexWriter.close() in 40 of 54,400 unfiltered rounds, all with the injected fault fired at StandardDirectoryReader.open:138, and none with this signature in 48,000 rounds with the fix shadowed in. It then reduced the case to a deterministic single-thread JUnit. Verifiers replaced the finder's call-stack-filtered fault with a stock-classes trigger, which became the minimal repro.

History

#

Introduced by LUCENE-8233 (ecc17f90233, 2018-04-04, soft deletes), which put the throwing hook between opening the reader and listing it. First release 7.4.0; executed leaks on 12 releases from 7.4.0 to 10.6.0 and on main; 7.3.1 lacks the API. Not fixed upstream as of 2026-10-30.

Versions tested8 rows

Introduced by ecc17f9023309ca2c46eaf65fd031e4af0ef5a25 on master, "LUCENE-8233: Add support for soft deletes to IndexWriter" (s1monw, 2018-04-04; JIRA LUCENE-8233, now #9280; patch era, no pull request on the Apache repository), backported to branch_7x as 02fa5a0b059 the same day. In StandardDirectoryReader.open(IndexWriter, ...) it replaced writer.getKeepFullyDeletedSegments() (package-private, cannot throw) with mergePolicy.keepFullyDeletedSegment(reader) (public, throws IOException) between obtaining the reader and listing it. Later commits moved the code but kept the window: d9041124281 (LUCENE-8253, the IOSupplier form, before 7.4.0), 8294e1ae206 (LUCENE-8962, 8.7.0, readerFunction.apply(info)) and 2d6ad2fee6d (LUCENE-9570, reformat).

By reading, all 58 release tags 7.4.0-10.5.2 and the 10.6.0 tag call the check right after obtaining the reader with no guard, and upstream main 2f424fd428d (2026-10-30) still does. There is no earlier good version of this path to bisect. The number of leaked files varies by version (2 on 7.4.0-10.0.0, 3 on 10.5.2, 4 on main and 10.6.0) with how many doc-values update files the codec keeps open; the leaked object is the same.

core / index NRT reader open from IndexWriter (StandardDirectoryReader.open(IndexWriter, ...) keep check for fully deleted segments; SoftDeletesRetentionMergePolicy as the stock trigger)
Priority
Low, rank 1093: A bounded exception-path SegmentReader leak in NRT open that needs a throwing keepFullyDeletedSegment under SoftDeletesRetentionMergePolicy, the same class as the LFV-446 and LFV-495 failure-path leaks.
Impact class
minor
Impact note
Applications that use soft deletes with SoftDeletesRetentionMergePolicy (or any merge policy whose keepFullyDeletedSegment can throw) and open NRT readers from their IndexWriter leak one SegmentReader, holding the segment core and its files (the compound file and the doc-values update files, 4 inputs in the main repro), each time the keep check fails inside StandardDirectoryReader.open; the cleanest case is the first NRT open of a new writer on a commit that holds a fully soft-deleted segment the retention query keeps, because there StandardDirectoryReader.open runs the only check, while on a warm writer a persistent failure surfaces earlier in IndexWriter.writeReaderPool and leaks nothing; neither IndexWriter.close() nor rollback releases the reader, repeated cold-writer reopens while the check keeps failing add one core each (10 cycles left 40 inputs open, and 40 MMapDirectory mappings that were not reclaimed in the security probe), warm-writer repeats re-pin the same core and add no handles, any index size, no wrong results, no index damage, and the writer stays open and usable [exec].
Summary
You use soft deletes with SoftDeletesRetentionMergePolicy, open a new IndexWriter on an index whose last commit holds a fully soft-deleted segment that the retention query keeps, and call DirectoryReader.open(writer); the merge policy's keep check for that segment fails (one read error while the retention query reads the segment, or your retention-query supplier throws), so the open fails with that exception. You expect the failed open to release what it acquired, as StandardDirectoryReader.open's own catch block does for every reader already in its list (LUCENE-5262), so that closing the writer leaves no file open. Instead the SegmentReader obtained just before the keep check is neither in that list nor released, so after IndexWriter.close() the segment stays open (MockDirectoryWrapper: 'there are still 4 open files: {_0.cfs=1, _0_1_Lucene90_0.dvp=1, _0_1_Lucene90_0.dvs=1, _0_1_Lucene90_0.dvd=1}'), while the writer itself stays open and a later NRT open works.
