BinaryPoint's one-dimensional exact and range queries keep the caller's byte[], so refilling it changes queries already built

BinaryPoint.newExactQuery and the one-dimensional newRangeQuery keep your byte[] instead of copying it, so refilling the array changes queries already built: two exact queries from one scratch array, OR-ed, match 1 document instead of 2. Two-dimension queries and newSetQuery keep their values; every release since 6.0.0 is affected.

The bug in 30 seconds

#

BinaryPoint indexes fixed-width binary values as points. Its query factories are newExactQuery "for matching an exact 1D point", newRangeQuery for 1D and n-dimensional ranges, and newSetQuery for a set of 1D values. You pass each value as a byte[]; the javadoc does not say whether the query copies it.

  1. Index three documents with a one-dimensional BinaryPoint field holding the keys 1, 2 and 3 (one byte each).
  2. Write key 1 into a scratch byte[] and build q1 = BinaryPoint.newExactQuery(field, scratch). Write key 2 into the same array and build q2. OR the two. Nothing has been searched yet, and no query cache is involved.
  3. You expect 2 hits, keys 1 and 2, as with newSetQuery, which keeps the value it was given.
  4. You get 1 hit. Both queries hold the scratch array itself, so q1 now means key 2: it prints binary(2) and equals q2. A range built for [1, 2] whose arrays you then overwrite with 9 matches 0 documents instead of 2.
  5. Why: for one dimension BinaryPoint.pack returns your array instead of a copy, and PointRangeQuery stores what it gets; for two or more dimensions it packs a new array. No exception, and the index is untouched.

Who is affected

#

Applications that build one-dimensional BinaryPoint exact or range queries from a byte[] they later refill or reuse, such as fixed-width keys encoded into one scratch buffer in a loop. Default configuration, no query cache needed, any index size. Two-dimension BinaryPoint, newSetQuery and the typed points (IntPoint, ...) are unaffected; Lucene itself never calls these factories.

Mechanism, terms and numbers567 words

BinaryPoint.newExactQuery and the one-dimensional BinaryPoint.newRangeQuery build a PointRangeQuery whose bounds are the caller's own byte[]: BinaryPoint.pack returns new BytesRef(point[0]) for one dimension (BinaryPoint.java:93-95), and PointRangeQuery stores the array it gets (PointRangeQuery.java:94-95). Matching, equals, hashCode and toString then read whatever the array holds now. A caller that encodes keys 1, 2 and 3 into one scratch buffer and ORs one exact query per key gets 1 hit instead of 3, before any search and with the query cache off; a range built for keys [1, 2] whose bound arrays are reused for key 3 matches 1 document instead of 2. The same factory copies the bounds for two or more dimensions, and a one-value newSetQuery keeps its value. Every release that has BinaryPoint (6.0.0 to 10.5.2) and main does this; no in-tree code calls these factories. Cloning the packed bounds for one dimension fixes it, and the point-query and document test suites pass with that change.

Terms

#
  • BinaryPoint: a field that indexes a fixed-width binary value (or one per dimension) as a point. Its static factories build point queries: newExactQuery(field, byte[]), newRangeQuery(field, byte[], byte[]), newRangeQuery(field, byte[][], byte[][]) and newSetQuery(field, byte[]...) (class javadoc, BinaryPoint.java:35-44).
  • pack() (BinaryPoint.java:86-119): turns one value per dimension into one packed BytesRef. The field constructor uses it (:129-131), and so does the n-dimension range factory (:192-194).
  • PointRangeQuery: the query the exact and range factories return. Its constructor takes the packed lower and upper bounds (PointRangeQuery.java:72-98).

The bug

#
  1. For one dimension, pack() returns new BytesRef(point[0]) (BinaryPoint.java:93-95): a wrapper over the caller's array, no copy. For two or more it allocates a new array and copies each dimension in (:114-118).
  2. newExactQuery(field, value) calls newRangeQuery(field, value, value) (:160-162), which wraps both arrays into byte[][] (:177-180) and calls the n-dimension factory, which passes pack(lowerValue).bytes and pack(upperValue).bytes to PointRangeQuery (:192-194). With one dimension these are the caller's arrays.
  3. PointRangeQuery stores them as given (PointRangeQuery.java:94-95) and reads them each time it matches (:134-145, :267-268, :285-286, :600-601), hashes (:479-488), compares (:490-501) or prints (:503-530). Its getters return clones (:471-477), so the bounds cannot be changed through the query, only through the caller's own array.
  4. So the query is consistent with itself but follows the caller's buffer: whatever the array holds when the query runs is what it matches.

The numbers (executed on main, assertions on and off)

#
  • Three documents, keys 1, 2, 3 as 4-byte sortable ints, query cache off. Encode each key into one scratch buffer and OR one newExactQuery per key: 1 hit instead of 3 (the same loop with one-value newSetQuery: 3).
  • Build newRangeQuery for keys [1, 2], then write key 3 into both bound arrays: 1 document instead of 2. The two-dimension overload built from the same arrays: 2.
  • Build newExactQuery for key 1, write key 2 into the array: the query prints key:[binary(80 0 0 2) TO binary(80 0 0 2)] instead of binary(80 0 0 1).
  • With one-byte keys (the diagram's example): two exact queries from one scratch array, OR-ed, count 1 instead of 2, and q1.equals(q2) is true with the same hashCode; a range built for [1, 2] counts 0 after 9 is written into its arrays.
Exposure and likelihood264 words
  • Who is exposed. Applications that build one-dimensional BinaryPoint exact or range queries from a byte[] they later refill or reuse while the query is still in use. Typical shape: fixed-width binary keys (sortable ints, hashes, ids) encoded into one scratch buffer in a loop to OR several exact queries. NumericUtils.intToSortableBytes(value, result, offset) writes into a caller-supplied array, so the loop is an ordinary pattern.
  • Default vs opt-in. No special configuration: a plain new IndexWriterConfig() and new IndexSearcher(reader) (the test framework picks a random codec and directory for each seed, and every seed used failed the same way); no query cache needed (the repro turns it off and builds every query before the first search); no index-size prerequisite (3 documents). The typed point classes (IntPoint, LongPoint, ...) take numbers and build their own arrays; BinaryPoint with two or more dimensions and newSetQuery copy. No file outside the tests calls BinaryPoint.newExactQuery or newRangeQuery.
  • Silent. Wrong matches (an OR loses hits, a range matches another range), no exception, no log line, nothing written to the index. Queries built for different keys become equals with the same hashCode.
  • With a query cache. The hunt's cache probe (LRUQueryCache, 16 and 1 partitions) served 0 wrong hits to a freshly built twin; after a key's hashCode drifts, 32 bytes of accounted query RAM stayed after cleanUp. Not counted as impact.
  • How likely. Rare: it needs the reuse pattern on a less-used API, and the recorded searches found no report since 6.0.0 (2016). Once the pattern is used, the wrong results are deterministic.

Why it is a bug, not intended

#
  • One method, newRangeQuery(String, byte[][], byte[][]), copies the bounds for two or more dimensions and shares them for one; its javadoc mentions neither.
  • A one-value newSetQuery keeps its value after a refill; newExactQuery, which returns "a query matching documents with this exact value", does not.
  • Where Lucene shares a caller's array it says "not copied" (Field); these factories say nothing.
The full argument325 words
  • One method, two answers. newRangeQuery(String, byte[][], byte[][]) owns its bounds for two or more dimensions and shares the caller's array for one (BinaryPoint.java:93-95 vs :114-118, both reached from :192-194). Its javadoc (:182-191) does not mention the dimension count.
  • Same class, same request. The class javadoc lists newExactQuery "for matching an exact 1D point" and newSetQuery "for matching a set of 1D values" (:38-40). A one-value newSetQuery(field, scratch) keeps its value after a refill (PointInSetQuery encodes it into its own storage); newExactQuery(field, scratch) does not. newExactQuery's javadoc: "@return a query matching documents with this exact value" (:158).
  • Where Lucene shares, it says so. Field: "NOTE: the provided byte[] is not copied so be sure not to change it until you're done with this field" (Field.java:156-157); MultiPhraseQuery.Builder: "The array is not copied" (MultiPhraseQuery.java:111, :122). These factories carry no such note.
  • The project's recorded direction. LUCENE-6369 (#7429): "It is very important for the query cache that queries be either immutable or clone deeply so that they cannot change after having been put into the cache", superseded by #7648, "queries should now be immutable". LUCENE-6821 (#7879) made Term copy its BytesRef because building queries from shared bytes "is a bit trappy". LUCENE-7307 (#8361) made these very bounds clone on the way out (PointRangeQuery.java:471-477).
  • Tests. No upstream test asserts the sharing. testPointRangeEquals and testPointExactEquals (TestPointQueries.java:2255-2265, :2324-2332) build the "other" query from ones.clone() instead of changing ones.
  • History: an accident. pack()'s one-dimension shortcut came from LUCENE-6881 (f12cb52a3b8, 2015) for the field constructor. The query path started using pack() in LUCENE-7117/7118 (e1a1dbfabcc9, 2016), whose 14 comments discuss the byte[][] equals/hashCode bugs and never array ownership. Before that commit the factories kept the caller's arrays for every dimension count (unreleased code), so the two-dimension copy is a side effect of packing, not a design.
The devil's-advocate check366 words

The strongest "works as designed" case, built by the refute review, the intended-lens review and the devil's advocate: no javadoc promises a copy; PointRangeQuery's constructor is protected and "Expert" and keeps its arrays; keeping caller values without a note is common in Lucene's query API: in the hunt's differential probe, 13 other query entry points follow a later write into the value they were given (the kNN query targets and the adaptive vector-similarity queries, TermRangeQuery for equals/hashCode, SortedSetDocValuesField.newSlowRangeQuery, SortedDocValuesField.newSlowExactQuery, SynonymQuery.Builder.addTerm(BytesRef, float), Intervals.term(BytesRef), RescoreTopNQuery.createFullPrecisionRescorerQuery, ConstKnnFloatValueSource), while PhraseQuery, TermInSetQuery and TermQuery copy; SortedSetDocValuesField.newSlowExactQuery keeps its bytes too (confirmed by running it); in LUCENE-6321 (#7382) a committer wrote "who is modifying term bytes? This seems like an abuse case"; and IndexSearcher.setQueryCache says "When using a query cache, queries should not be modified after they have been passed to IndexSearcher" (IndexSearcher.java:268-269).

Why it fails: the write goes into the caller's own array, before any query reaches a searcher and with no cache, through a public factory whose behaviour depends on the dimension count, so the IndexSearcher note does not apply. The same factory copies for two or more dimensions, so "the caller owns the array" is not the method's rule either. (A maintainer can still call a write into a retained array a modification of the query; that ownership question is what the issue asks them to settle.) The LUCENE-6321 remark continues "But maybe its a good idea to do a little "extra" clone work to make these core queries defensive", and the project then made Term copy. Users call the factories, not the protected constructor. Verdict: a defect (adjudication: confirmed, medium confidence; every verifier: real). The adjudication's own tier is Low because no in-tree code reuses such an array and the query-cache leg showed no wrong hits; the registry priority, medium, is a separate scale. The contract is implicit, which is why it is filed as an inconsistency and a robustness fix, with a javadoc note as the fallback. Do not cite the newSetQuery comment "Don't unexpectedly change the user's incoming values array" or #12158: both are about not sorting the caller's array, the opposite direction.

Suggested fix

#

Recommended Clone the packed bounds for one dimension in the n-dimension factory

Copy the packed bounds when there is one dimension in BinaryPoint.newRangeQuery(String, byte[][], byte[][]), the method every one-dimensional factory goes through (+11/-2). The field constructor keeps its documented sharing. The repro, TestPointQueries, every document suite plus the point suites (62 suites, 589 tests) and :lucene:core:check -x test pass.

byte[] lower = pack(lowerValue).bytes;
byte[] upper = pack(upperValue).bytes;
// pack() returns the caller's array for one dimension (fine for the field constructor); copy
// it so that the query owns its bounds, as it already does for two or more dimensions
if (lowerValue.length == 1) {
  lower = lower.clone();
}
if (upperValue.length == 1) {
  upper = upper.clone();
}
return new PointRangeQuery(field, lower, upper, lowerValue.length) {
All options and trade-offs4 options · 613 words

One site fixes newExactQuery and both newRangeQuery overloads, because they all route through the n-dimension factory. pack() runs first, so its argument checks are unchanged. Each side is copied by its own dimension count; this also covers a mismatched input the method documents as rejected but does not check ({{1},{2}} against {{3,4}} is accepted on main), which is a separate issue. Workaround until a fix ships: pass a fresh array per query (scratch.clone()), or use newSetQuery for several exact values.

Clone the packed bounds for one dimension in the n-dimension factory (validated by the checks) (recommended)

#

In newRangeQuery(String, byte[][], byte[][]), call pack() for both sides first, then clone() each side that has one dimension, and pass the results to PointRangeQuery. +11/-2 in BinaryPoint.java.

byte[] lower = pack(lowerValue).bytes;
byte[] upper = pack(upperValue).bytes;
// pack() returns the caller's array for one dimension (fine for the field constructor); copy
// it so that the query owns its bounds, as it already does for two or more dimensions
if (lowerValue.length == 1) {
  lower = lower.clone();
}
if (upperValue.length == 1) {
  upper = upper.clone();
}
return new PointRangeQuery(field, lower, upper, lowerValue.length) {

Trade-offs

  • Cost: two small array copies per one-dimensional query; nothing changes on the indexing path.
  • Behaviour change: code that, on purpose or not, retargets an already-built one-dimensional query by writing into its array would stop doing so; that has been observable since 6.0.0. This option limits the change to the BinaryPoint factory.
  • pack() runs before the copy, so null and length errors stay IllegalArgumentException (an earlier draft read lowerValue.length first and turned a null argument into a NullPointerException; the refute review caught it).
  • A one-condition variant (clone both sides when lowerValue.length == 1) behaves the same on valid input and was the version the earlier checks shadowed in.

Copy in PointRangeQuery's constructor

#

this.lowerPoint = lowerPoint.clone(); this.upperPoint = upperPoint.clone(); in the protected constructor.

Trade-offs

Also covers subclasses outside Lucene that pass shared arrays. Every point range query then pays two extra copies, although IntPoint, LongPoint, the two-dimension BinaryPoint path and the other typed factories already pass fresh arrays, and it changes an Expert constructor's behaviour, so the behaviour change of option A reaches every PointRangeQuery subclass. Not run.

Make pack() always copy

#

Drop the one-dimension shortcut in pack().

Trade-offs

Not recommended: it adds one allocation and copy per one-dimensional BinaryPoint field instance on the indexing path (two or more dimensions are already copied), and the field would no longer share the caller's array, a field-side behaviour change, to fix a query-side problem. Field itself would still keep the array it is given. Not run.

Javadoc only

#

Document on newExactQuery and the one-dimensional newRangeQuery that the provided byte[] is not copied, as Field does, and say on newRangeQuery(String, byte[][], byte[][]) that its arrays are kept when there is one dimension and copied when there are more.

Trade-offs

No behaviour change and no cost, but the same method still copies for two or more dimensions, and the encode loop still loses hits. The fallback if maintainers prefer no code change.

Downstream note

#

An application that builds an access filter from a reused key buffer would silently match the wrong keys, but that depends on how it uses the API, so this is an ordinary public bug.

How it was found

#

A bytecode ownership scan flagged that PointRangeQuery keeps the arrays it is given. A differential probe then showed the one-dimensional BinaryPoint factories following the caller's buffer while the two-dimension path did not, and the cause was read in BinaryPoint.pack. Independent AI tools then reproduced, reviewed and judged it.

The method in full155 words

Method: semi-formal (the hunt's tier for tool-guided finds that are not a formal tool's own output), a hunt unit (search-side argument ownership), 2026-10-27, stock main jars.

  • A bytecode ownership scan (an abstract interpretation of operand stack and locals over 17 module jars, with per-method keep summaries iterated to a fixpoint) listed PointRangeQuery's constructor as keeping its byte[] bounds.
  • The unit's plan expected the BinaryPoint factories to pack a copy (a negative control). A differential probe over 20 query entry points (mutate after construction, two queries from one buffer, mutate after a cached search; 21 rows with one Sort row) showed the one-dimension BinaryPoint exact and range factories failing while the two-dimension control passed.
  • The cause was then read in BinaryPoint.pack. The scan alone did not single out BinaryPoint; the signal came from the probe. A public-API JUnit test confirmed it, and independent AI tools reproduced, reviewed and judged it (see the checks).

History

#

In every release since 6.0.0: LUCENE-7117/7118 (2016) routed the n-dimension query factory through pack(), which copies two or more dimensions but not one (a shortcut written for the field constructor); the unreleased factories before it kept the caller's arrays for every dimension count. Every release run from 6.0.0 to 10.5.2, and main, fails the repro; 5.5.5 has no BinaryPoint.

Versions tested6 rows

Current form from e1a1dbfabcc9 (master, 2016-03-20, @rmuir, "LUCENE-7117, LUCENE-7118: Remove multidimensional arrays from PointRangeQuery"; JIRA era, no PR; migrated as #8172 and #8173). It changed the n-dimension newRangeQuery to new PointRangeQuery(field, pack(lowerValue).bytes, pack(upperValue).bytes, lowerValue.length), which gave two or more dimensions a private packed copy and left one dimension sharing. Keeping the caller's arrays is older (precursors below). On branch_6_0 the same change is d8c4e6977b0e, the commit in the 6.0.0 tag (e1a1dbfabcc9 itself is not), and on branch_6x 51b109620be7; the 6.0.0 tag's BinaryPoint.java has the shortcut at line 87 and the call at line 176.

Precursors (unreleased): LUCENE-6881 (f12cb52a3b8, 2015-11-08) added pack()'s one-dimension shortcut for the field constructor; LUCENE-7045 (099e0311398, 2016-02-23) added the factories, which then passed the caller's byte[][] through for every dimension count; LUCENE-7061 (e80ab3926c1) gave them their current signatures. No release ever copied the one-dimension bounds. Since then the lines are unchanged apart from the 2020 reformat (2d6ad2fee6d, LUCENE-9570). No release after 10.5.2 exists yet; branch_10x and branch_10_5 were read, not run.

LFV-751, snapshot of 2026-10-29

Registry title
BinaryPoint.newExactQuery and the one-dimensional newRangeQuery keep the caller's byte[] as the query bounds (BinaryPoint.pack returns the caller's array for one dimension), while the same factory packs a private copy for two or more dimensions, so a caller that refills its buffer silently changes queries it already built
Area
document / point query factories (BinaryPoint, PointRangeQuery)
Priority
Medium, rank 70: Core BinaryPoint one-dimensional exact and range queries silently match the wrong documents when the caller refills its byte[], a rare reuse pattern with transient query-side damage, so it closes the mid-Medium point-query group well below the durable caller-array rows LFV-644 and LFV-643.
Impact class
silent wrong results
Impact note
Hits only applications that build one-dimensional BinaryPoint exact or range queries from a byte[] they later refill or reuse (for example fixed-width keys encoded into one scratch buffer in a loop to OR several exact queries), with the default configuration and no query cache needed, before or after the first search: the queries silently match whatever the buffer holds now (an OR of them loses hits) and their equals, hashCode and toString change with it, with no exception and no index damage, in every release since 6.0.0; BinaryPoint queries with two or more dimensions, BinaryPoint.newSetQuery and the typed point factories (IntPoint, LongPoint, ...) build their own arrays and are unaffected, and no in-tree production code calls these factories.
Summary
You write a one-dimensional binary key into a scratch byte[], build BinaryPoint.newExactQuery(field, scratch), write the next key into the same array, build a second query and OR the two; you expect each query to match the key it was built for, as BinaryPoint's two-dimension range queries and its one-value newSetQuery do. Instead both queries now mean the second key (they compare equal and print the same bounds) and the OR finds 1 document instead of 2; likewise a one-dimensional newRangeQuery whose lo/hi arrays the caller overwrites afterwards matches 0 documents instead of the range it was built for. BinaryPoint.pack returns new BytesRef(point[0]), a wrapper over the caller's array, when there is one dimension, and PointRangeQuery stores that array as its bounds, so matching, equals, hashCode and toString read whatever the caller's array holds at the time.
Introduced
e1a1dbfabcc9 (LUCENE-7117/LUCENE-7118 'Remove multidimensional arrays from PointRangeQuery', Robert Muir (rmuir), migrated as apache/lucene#8172 and #8173; JIRA era, no pull request; committed the same day on branch_6_0 as d8c4e6977b0e, the copy in 6.0.0, and on branch_6x as 51b109620be7) [read: git log, git show and git blame in the history clone]: it made BinaryPoint.newRangeQuery(String, byte[][], byte[][]) pass pack(lowerValue).bytes and pack(upperValue).bytes to PointRangeQuery, so two or more dimensions get a private packed array while one dimension keeps the caller's array through pack()'s shortcut 'if (point.length == 1) return new BytesRef(point[0])', which LUCENE-6881 (f12cb52a3b8, 2015-11-08) had written for the field constructor (Field documents its byte[] values as not copied). In the unreleased code between LUCENE-7045 (099e0311398, 2016-02-23) and this commit the query kept the caller's byte[][] for every dimension count, so no released version ever copied the one-dimension bounds. The lines are unchanged on main apart from the 2020 reformat (2d6ad2fee6d, LUCENE-9570) (2016-03-20)
