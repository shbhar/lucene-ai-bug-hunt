A kNN filter backed by a bit set shorter than maxDoc makes the search throw instead of returning hits

A kNN query whose filter hands Lucene a bit set shorter than the segment (10 bits for 100 documents) throws ArrayIndexOutOfBoundsException instead of returning hits: on a segment with no deletions, AcceptDocs reuses the filter's own set as the accept bits without checking its length (9.3.0 to 10.6.0, main).

The finding in 30 seconds

#

The filter itself is fine. The shortcut that reuses its bit set as the accept bits skips the length check that every other path applies.

Background: how a filtered kNN search uses its filter

#
  1. For each segment, a kNN query with a filter first turns the filter into accept bits: one bit per document id, from 0 to maxDoc - 1, saying whether that document may be returned.
  2. The vector search (a walk over the HNSW graph, or a plain loop over all vectors for small segments and small filters) checks a vector's bit before it collects it.

The finding, step by step

#
  1. You index 100 documents with one-dimensional vectors {0} to {99}: one segment, no deletions. Your own filter query matches docs 0 to 9 through a BitSetIterator over a FixedBitSet of 10 bits, not 100.
  2. You run KnnFloatVectorQuery("v", {50}, k=1, filter) and expect doc 9, the nearest of the 10 allowed documents. The same filter on a 100-bit set returns it.
  3. Before searching, Lucene turns the filter into accept bits for the segment. With no deletions it takes a shortcut and reuses the filter's 10-bit set as is, without checking that it covers all 100 documents.
  4. The vector search asks the accept bits about every vector, 0 to 99. Vector 10 is past the end: AssertionError: index=10, numBits=10 with assertions on. With them off, vectors 10 to 63 still read as not allowed, and vector 64 throws ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1.

Who is affected

#

Applications that give KnnFloatVectorQuery or KnnByteVectorQuery their own filter built on a compact bit set (sized to its last match), on segments with no deletions where every document has the vector. No in-tree query builds such a set. Default codec and settings; the request fails loudly; no wrong hit was seen.

Mechanism, terms and numbers681 words

Before a filtered kNN search, AbstractKnnVectorQuery turns the filter into per-segment accept bits through AcceptDocs.fromIteratorSupplier. When the segment has no deletions and the filter's iterator is a BitSetIterator, AcceptDocs.createBitSet returns that iterator's own BitSet without checking its length (AcceptDocs.java:95-97 at 5adff78bb168). Its two other branches build exactly maxDoc bits, and the class's other factory, fromLiveDocs, rejects bits whose length is not maxDoc. The HNSW reader then reads the accept bits for vector ordinals up to the segment's vector count, so a shorter set is read past its end: AssertionError with assertions on, ArrayIndexOutOfBoundsException with them off once an ordinal passes the set's last 64-bit word. No in-tree query builds such a set; a custom filter does, on a segment with no deletions where every document has the vector. It fails loudly; no wrong hit was seen. A one-line guard (reuse the set only when its length is maxDoc) fixes it.

The mechanism (main 5adff78bb168, under lucene/core/src/java/org/apache/lucene/)

#
  1. The filter's own iterator reaches AcceptDocs. The filter is ANDed with FieldExistsQuery(field) and rewritten (search/AbstractKnnVectorQuery.java:88-97); when every document has the vector, FieldExistsQuery rewrites to match-all and drops out, and the filter scorer's iterator goes unwrapped into AcceptDocs.fromIteratorSupplier(.., liveDocs, reader.maxDoc()) (:257-268).
  2. The shortcut reuses the set unchecked. createBitSet: if (liveDocs == null && iterator instanceof BitSetIterator bitSetIterator) { // If we already have a BitSet and no deletions, reuse the BitSet; return bitSetIterator.getBitSet(); } (search/AcceptDocs.java:95-97). This is the fix site. The other branches build new FixedBitSet(maxDoc) (:102) or BitSet.of(.., maxDoc) (:109-111), and BitsAcceptDocs, behind fromLiveDocs, throws IllegalArgumentException("Bits length = .. != maxDoc = ..") (:124-128). bits() hands the reused set out as is (:187-191).
  3. The reader reads every ordinal. accepted = acceptDocs.bits() (codecs/lucene99/Lucene99HnswVectorsReader.java:370); the exhaustive loop tests acceptedOrds.get(i) for every i < scorer.maxOrd() (:388-389), and the graph branch passes the same bits to HnswGraphSearcher, which tests every visited ordinal (:379-381). Ordinals equal doc ids here because every document has a vector.
  4. The read runs off the set. FixedBitSet.get asserts index < numBits (util/FixedBitSet.java:286). With assertions off it reads word index >> 6 (:287-291): ordinals 10 to 63 read the set's only word and correctly return false; ordinal 64 reads word 1 of a 1-word array and throws.

When it happens

#
  • All of these are needed: a filter whose scorer iterates a BitSetIterator over a set shorter than maxDoc; no deletions in the segment (otherwise the copying branch builds maxDoc bits); every document has the vector field (otherwise the FieldExistsQuery conjunction wraps the iterator); the filter not served from the query cache, whose sets are maxDoc long.
  • No in-tree query builds such a set: point, spatial and join queries, DocIdSetBuilder, LRUQueryCache and QueryBitSetProducer size theirs to maxDoc. Custom code can, with the @lucene.internal BitSetIterator, BitDocIdSet or DocIdSetBuilder, or with the public, untagged DocsWithFieldSet.iterator() (index/DocsWithFieldSet.java:101-104), which returns a BitSetIterator once its documents are not exactly 0 to n-1, over a set that grows with the documents added rather than to maxDoc; a custom filter built on it fails the same way (executed). Both are unusual custom-filter constructions.
  • Sets longer than maxDoc are not read past their end here (by reading; not tested). With assertions off, a short set throws only once the reader reaches an ordinal past its last 64-bit word, and the reads below that are correct, so no wrong hit was seen.
  • In the repro, the 100-vector segment gets no HNSW graph (#14963, 10.4.0: graphs are skipped for tiny segments), so the reader takes the exhaustive loop. On bigger segments, or before 10.4.0, the graph walk reads the bits for the ordinals it visits: with assertions on it fails at the first visited ordinal past the set, with them off only at one past the set's last 64-bit word (on 10.0.0 and 10.3.0 the repro's walk visits ordinal 54, so it fails with assertions on and passes with them off).
Exposure and likelihood123 words
  • Who. Code with its own filter Query whose scorer iterates a BitSetIterator over a set sized to its matches, or built for a smaller doc range, instead of the segment's maxDoc. A downstream vector-search plugin built such shorter-than-maxDoc BitSetIterators in 2022 (LUCENE-10674, #1068).
  • Default vs opt-in. Default codec, IndexWriterConfig and searcher; the trigger is the application's filter code.
  • Effect. Loud: that request throws from IndexSearcher.search and returns nothing. No corruption, and no wrong, extra or leaked hit was seen: by reading, the reads below the failing ordinal return the filter's own answer.
  • Scale. None needed: 100 documents, one segment, single thread, deterministic.
  • Likelihood. Rare: no in-tree query reaches it, and no public report of this crash was found since 9.3.0.

Why it looks unintended

#
  • AcceptDocs rejects accept bits whose length is not maxDoc on its other path, and its other branches build exactly maxDoc bits; only this shortcut skips the check.
  • No document requires a filter's set to cover the segment; BitSetIterator works with any length.
  • Upstream already fixed this same input in another class (LUCENE-10674, 9.4.0).
The full argument184 words
  • The class enforces the length on its other path. fromLiveDocs rejects bits of the wrong length (AcceptDocs.java:124-128), the two copying branches of createBitSet build exactly maxDoc bits (:102, :109-111), and upstream TestAcceptDocs asserts bits().length() == maxDoc for both factories (lucene/core/src/test/org/apache/lucene/search/TestAcceptDocs.java:57-59).
  • No length requirement anywhere. No javadoc, CHANGES or MIGRATE entry says a filter's BitSetIterator must cover the segment. BitSetIterator caches bits.length() and returns NO_MORE_DOCS past it (util/BitSetIterator.java:72, :94-95).
  • Core accepts shorter sets elsewhere. BitSetConjunctionDISI uses the minimum length of its sets (search/ConjunctionDISI.java:244-250). LUCENE-10674 (#1068 / #11709, fixed in 9.4.0) fixed that class for exactly this input, built by a downstream plugin; a maintainer called such sets "not typical" (2022-09-09), and the fix was merged with a test.
  • The same filter works everywhere else. On main, the 10-bit filter gives count 10, a plain search 10 hits, and 10 hits in a conjunction with FieldExistsQuery (independent reproducer's controls).
  • History. Before #951 (9.1.0, 9.2.0) the filter was always collected into a new FixedBitSet(maxDoc); #951's description and review do not discuss the set's length.
The devil's-advocate check148 words

The case for intended: BitSetIterator and FixedBitSet are @lucene.internal, so a short backing set is outside the public input domain (the executed cross-model refute review, which still reproduced the crash and agreed on the root cause and the fix). Also: Bits.get says out-of-range indexes are undefined, "just don't do it!" (util/Bits.java:30-31).

The answer (a judgement call): the tag withholds API-stability guarantees; it does not make a valid DocIdSetIterator an illegal filter, and the public, untagged DocsWithFieldSet.iterator() reaches the same crash. The Bits.get rule binds the caller, and here the caller is Lucene's own reader, fed bits that AcceptDocs built against its own invariant. #1068 shows upstream already treated this input class as a bug. On this reading, these points lower the likelihood rather than the validity, and the devil's-advocate verifier and the adjudication rejected the objection; a maintainer may still weigh the contract objection differently.

Suggested fix

#

Recommended Reuse the set only when it covers the segment (fix A)

In AcceptDocs.createBitSet, reuse the filter's set only when it has exactly maxDoc bits; otherwise the existing copy builds a full-size set (one-line guard). The repro passes with assertions on and off, and it and the 3 closest suites (89 tests) pass.

-    if (liveDocs == null && iterator instanceof BitSetIterator bitSetIterator) {
+    if (liveDocs == null
+        && iterator instanceof BitSetIterator bitSetIterator
+        && bitSetIterator.getBitSet().length() == maxDoc) {

Reuse the set only when it covers the segment (fix A) (validated by the checks) (recommended)

#

Add bitSetIterator.getBitSet().length() == maxDoc to the shortcut's condition in AcceptDocs.createBitSet (AcceptDocs.java:95). A short set falls through to the existing copying branches, which build a maxDoc-sized set.

-    if (liveDocs == null && iterator instanceof BitSetIterator bitSetIterator) {
+    if (liveDocs == null
+        && iterator instanceof BitSetIterator bitSetIterator
+        && bitSetIterator.getBitSet().length() == maxDoc) {

Trade-offs

  • In-tree filters, whose sets are maxDoc long, keep the zero-copy shortcut; the cost is one length comparison per segment, plus a copy for sets of any other length.
  • Matches the class's own invariant (fromLiveDocs, TestAcceptDocs).
  • With ==, a set longer than maxDoc is copied too. That is fine while its set bits are below maxDoc, as a filter's matches must be; a set with a bit at or past maxDoc would throw in the copy (BitSetIterator.intoBitSet, util/BitSetIterator.java:126-128), where today's shortcut never reads it. Not tested.

  • With the fix: the repro (1), TestAcceptDocs (5), TestKnnFloatVectorQuery (43) and TestKnnByteVectorQuery (40): 89 tests, 0 failures. :lucene:core:checkGoogleJavaFormat passes with the fix and the test in the tree. The whole core module was not run.

#

Reuse the set when getBitSet().length() >= maxDoc.

Trade-offs

Also keeps the shortcut for oversized sets, which the readers do not read past their end (by reading), but bits().length() could then differ from maxDoc, unlike every other AcceptDocs. Not built.

Bounds-check in the readers instead

Trade-offs

Downstream note

#

A product that builds its kNN filters from compact per-segment bit sets gets a failed request instead of hits; query text or documents cannot choose a filter set's length through any in-tree query.

How it was found

#

A proof-obligation audit of AcceptDocs' contract: the accept bits of a segment must cover all of its documents, as fromLiveDocs enforces. Of the ways createBitSet builds them, one, the reuse shortcut, never checks; a one-test JUnit then witnessed the crash.

The method in full122 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder stated the obligation for AcceptDocs: bits() of an AcceptDocs for a segment covers [0, maxDoc), as fromLiveDocs enforces and as the HNSW reader assumes. Two branches of createBitSet discharge it by construction; the reuse shortcut discharges it only if the filter's set is maxDoc long, which nothing checks.
  • The finder then wrote a JUnit test that fails on main with assertions on and off and on 10.2.0 to 10.6.0, a larger graph-walk probe for older releases, and the one-line guard.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

History

#

Introduced by #951 (LUCENE-10606, 2022; first release 9.3.0), which reused the filter's own set instead of copying it into a maxDoc-sized one. Every release from 9.3.0 to 10.6.0 and main have it; not fixed upstream. For 9.3.0 to 9.8.0 this rests on the code history and a larger graph-walk probe.

Versions tested9 rows

Introduced by #951 (LUCENE-10606, "For KnnVectorQuery, optimize case where filter is backed by BitSetIterator", Kaival Parikh): 03846b468e5 on main and its branch_9x cherry-pick e055e95d3ef, authored and merged 2022-06-27; first release 9.3.0. It replaced the per-segment collector, which always built a new FixedBitSet(maxDoc), with the reuse shortcut.

Later commits only moved the code (#12004, 9.5.0, into AbstractKnnVectorQuery; #15011, 10.3.0, into AcceptDocs, adding the length check to fromLiveDocs only) or changed which loop reads the bits (#14160, 10.2.0: small filters take the exhaustive loop; #14963, 10.4.0: segments as small as the repro's get no graph). The repro's tiny input passes on some older releases because their search reads few bits: on 10.0.0 and 10.3.0 it passes with assertions off, so the graph walk read no ordinal at or past 64, the end of the set's only word. The repro uses the 10.x Weight API; for 9.x the hunt ran an adapted 200-document variant, which passes on 9.3.0, 9.7.0 and 9.8.0 (9.4 to 9.6 not run) because, by code reading, the walk runs out of its visit budget and falls back to an exact search that never reads the bits (not instrumented). The larger graph-walk probe covers those releases.

You run a KnnFloatVectorQuery with a custom filter whose scorer iterates a BitSetIterator over a FixedBitSet sized to its own matches (10 bits for docs 0..9) on a 100-document segment with no deletions, where every document has a vector. You expect the top k vectors among the filter's matches (here doc 9, with k = 1), as with the same filter backed by a maxDoc-sized set. Instead AcceptDocs.createBitSet hands the filter's 10-bit set unchanged to the HNSW reader as the accept bits (its other branches build maxDoc bits, and its fromLiveDocs entry point rejects bits whose length is not maxDoc), the reader tests it for every vector ordinal, and the search throws ArrayIndexOutOfBoundsException (AssertionError 'index=10, numBits=10' with -ea) from FixedBitSet.get.
