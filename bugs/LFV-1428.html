MutableValue.compareTo is not transitive across value classes on JVMs with negative identity hash codes

On OpenJ9 (default settings), MutableValue.compareTo can say Bool < Double < Int, yet Bool > Int: it subtracts the two classes' hash codes and the int overflows. HotSpot is not affected (its identity hash codes are never negative), no Lucene feature orders mixed value classes, and Integer.compare fixes it.

The finding in 30 seconds

#

compareTo orders values of different MutableValue classes by the difference of their class hash codes. When one hash code is very negative and the other very positive, that difference overflows int and changes sign, so the order stops being transitive.

Background: mutable values and class hash codes

#
  1. A MutableValue holds one reusable value of a fixed type: MutableValueBool, MutableValueInt, MutableValueDouble, MutableValueStr and so on. Function queries (FunctionValues.ValueFiller) and grouping by a function (ValueSourceGroupSelector) hand them out, and the class implements Comparable<MutableValue>.
  2. SomeClass.class.hashCode() is the JVM's identity hash code: an arbitrary int fixed for one JVM run. HotSpot only uses non-negative values (its identity hash field has at most 31 bits); OpenJ9 by default uses negative and positive ones.

The finding, step by step

#
  1. Your application compares or sorts MutableValues of different types that it collected itself, say a MutableValueBool, a MutableValueDouble and a MutableValueInt, on OpenJ9 with default settings.
  2. For two different classes, compareTo returns c1.hashCode() - c2.hashCode() of the two classes. In one OpenJ9 run those hash codes were Bool -1728369406, Double -341526595 and Int 1684571406, so Bool < Double and Double < Int.
  3. You expect Bool < Int too: Comparable requires transitivity. But -1728369406 - 1684571406 = -3412940812 does not fit in an int; it wraps to +882026484, so compareTo says Bool > Int.
  4. The order is a cycle, and sorting such values can throw IllegalArgumentException: Comparison method violates its general contract!. On HotSpot the identity hash field has at most 31 bits, so class hash codes are never negative and the subtraction never overflows there.

Who is affected

#

Only applications on OpenJ9 (default settings) whose own code sorts or orders MutableValues of different classes that they collected. No Lucene code orders mixed classes, and HotSpot does not fail. They get an inconsistent order, or the sort throws. Priority Low.

Mechanism, terms and numbers597 words

MutableValue (@lucene.internal), the reusable value holder behind function values and grouping by a function, implements Comparable<MutableValue>. For two values of different classes, compareTo returns c1.hashCode() - c2.hashCode() of the two Class objects, breaking a tie by class name (MutableValue.java:45-51 on main). Class.hashCode() is the identity hash code, which Object.hashCode does not promise to be non-negative. OpenJ9 hands out negative and positive identity hash codes by default, so the difference can overflow and flip sign: in one OpenJ9 run, Bool (-1728369406) < Double (-341526595) < Int (1684571406), but compareTo(Bool, Int) = -3412940812 wrapped to +882026484. The cross-class order is then a cycle in most OpenJ9 runs (7 to 10 of 10 per sampled version), and sorting mixed-class values can throw IllegalArgumentException: Comparison method violates its general contract!. HotSpot keeps identity hash codes in at most 31 bits, so they are non-negative and it does not fail there. No Lucene code orders MutableValues of different classes; only application code that does so on OpenJ9 is hit. Present since 4.0.0-alpha. Integer.compare(c1.hashCode(), c2.hashCode()) fixes it and changes no order on HotSpot.

The bug

#
// MutableValue.java:24 and :41-53 (main f794ff5a505c)
public abstract class MutableValue implements Comparable<MutableValue> {
  ...
  public int compareTo(MutableValue other) {
    Class<? extends MutableValue> c1 = this.getClass();
    Class<? extends MutableValue> c2 = other.getClass();
    if (c1 != c2) {
      int c = c1.hashCode() - c2.hashCode();                         // :46 overflows
      if (c == 0) {
        c = c1.getCanonicalName().compareTo(c2.getCanonicalName());  // :47-49 tie-break
      }
      return c;
    }
    return compareSameType(other);                                   // :52 same class: not affected
  }
  • Why it wraps: two ints of opposite sign can differ by up to 2^32 - 1, outside the int range, and the result then has the wrong sign. The cross-class order behaves like positions on a clock face: it is consistent only if all class hash codes fall within one half of the 32-bit wrap-around circle. Under a model where the 7 class hash codes are independent and uniform over all 32-bit values (ties ignored), that happens with probability 7/2^6, so about 89% of runs would contain a 3-cycle (the independent reproducer's estimate); the observed OpenJ9 rates, 7 to 10 of 10 per sampled version, are broadly consistent with it.
  • Worked example (one OpenJ9 run): Bool - Double = -1728369406 - (-341526595) = -1386842811 (Bool < Double); Double - Int = -341526595 - 1684571406 = -2026098001 (Double < Int); Bool - Int = -3412940812, which is below -2^31 and wraps by +2^32 to +882026484 (Bool > Int).
  • HotSpot: the identity hash field has at most 31 bits (openjdk/jdk jdk-25+36 src/hotspot/share/oops/markWord.hpp:113, masked at :128), so hash codes are non-negative and the difference of two of them always fits; every HotSpot run passed (also with compact object headers).
  • Same-class comparisons are fine: no compareSameType subtracts. Int and Long (and Date, which inherits Long's) use < and > (MutableValueInt.java:56-62), Double and Float use Double.compare/Float.compare, Bool a boolean test and Str BytesRef.compareTo.
  • Public exposure: ValueSourceGroupSelector (public) extends GroupSelector<MutableValue> (ValueSourceGroupSelector.java:32); GroupingSearch.getAllMatchingGroups documents MutableValue group values (GroupingSearch.java:355-366); FunctionValues.ValueFiller.getValue() (@lucene.experimental) returns one (FunctionValues.java:137-150). The repro uses the public classes and constructors directly.
  • Executed consequence (the devil's-advocate verifier's probe): Collections.sort of 2000 mixed-class values threw IllegalArgumentException in 191 to 200 of 200 sorts in each of 5 OpenJ9 runs (assertions off); a sixth run, with assertions on, recorded the message "Comparison method violates its general contract!" (200 of 200). No sort threw on HotSpot or with -XX:+PositiveIdentityHash. Not claimed: lost TreeMap entries (inserting the seven values in all 5040 orders lost no key).
Exposure and likelihood135 words
  • Who is hit: application code on OpenJ9 that sorts, or keys a sorted collection with, MutableValues of different classes, for example values it gathered from several ValueFillers or groupings over value sources of different types.
  • Lucene's own code: not hit. Of the 12 non-test, non-sandbox files outside util/mutable that name MutableValue (in queries and grouping), none calls compareTo, a Comparator, TreeMap/TreeSet or sort. Grouping uses equals/hashCode, each in-tree value source yields one MutableValue class, and each ValueSourceGroupSelector owns one value source.
  • Default vs opt-in: OpenJ9's default (-XX:-PositiveIdentityHash); not on HotSpot.
  • Scale: none; three values of different classes are enough.
  • Likelihood: rare. It needs both OpenJ9 and application code that orders mixed MutableValue types; no matching public report was found in the recorded searches.

Why it looks unintended

#
  • MutableValue implements Comparable<MutableValue> and deliberately orders different classes; Comparable requires transitivity, and Object.hashCode promises no sign.
  • OpenJ9 documents negative identity hash codes as its default; Lucene runs on any Java 25.
  • No javadoc, test or CHANGES entry restricts the cross-class order; the same-class comparators avoid subtraction.
The full argument170 words
  • The contract. Comparable: "The implementor must also ensure that the relation is transitive: (x.compareTo(y) > 0 && y.compareTo(z) > 0) implies x.compareTo(z) > 0" (JDK 25 java/lang/Comparable.java:117-119, after the sign rule at :111-115). The cross-class branch with its name tie-break (MutableValue.java:45-51) shows the author wanted a total order across classes.
  • The JVM's documentation. OpenJ9, -XX:[+|-]PositiveIdentityHash: "Eclipse OpenJ9 allows both positive and negative identity hashcodes (System.identityHashCode / Object.hashCode). This is problematic for programs that incorrectly assume hashcodes can only be positive. ... this option is not enabled by default."
  • Lucene runs on any Java 25. lucene/SYSTEM_REQUIREMENTS.md:20: "Apache Lucene runs on Java 25 or greater." GITHUB#12058 fixed a test so it works on OpenJ9 (lucene/CHANGES.txt:3943), and LUCENE-8402 (#9449) removed a test's identityHashCode assumption as not required by the spec.
  • Nothing restricts it. The class javadoc is only "Base class for all mutable values. @lucene.internal"; TestMutableValues compares same-class values only; CHANGES.txt names MutableValue only for LUCENE-5790 (:12074, a different compareSameType defect).
The devil's-advocate check161 words

Strongest argument for "intended" or "not a bug": the class is @lucene.internal, no Lucene code orders mixed classes, the cross-class order is arbitrary per JVM run anyway, and HotSpot can never trigger it. An independent reviewer from another model family (OpenAI GPT-5.6) returned "not real" on these grounds and because it had only HotSpot JVMs to run on, while agreeing on the root cause and the fix.

Why it fails, and where it holds: @lucene.internal is a stability note ("might change in incompatible ways in the next release"), not leave to break Comparable; an order that is arbitrary but consistent is what Comparable asks for, and the overflow breaks the consistency. A public class alone does not make ordering mixed classes a supported contract; what does is that MutableValue itself declares Comparable<MutableValue> and has a branch written for different classes. The argument limits priority, not correctness, and a maintainer may still reasonably close it as won't-fix or too small.

Suggested fix

#

Recommended Compare the class hash codes with Integer.compare

Replace the subtraction with Integer.compare(c1.hashCode(), c2.hashCode()). On HotSpot it gives the same sign as today for every pair, so no order changes there. Validated with gradle on OpenJ9: the repro passed in 11 of 11 test JVM runs (13 of 14 failed unfixed); TestMutableValues and :lucene:core:check -x test pass.

int c = Integer.compare(c1.hashCode(), c2.hashCode());
All options and trade-offs2 options · 292 words

Both options keep the class-name tie-break and the same-class path. Option A keeps today's cross-class order wherever it is consistent (always on HotSpot); option B would change it everywhere.

Trade-offs

None worth naming: no order change on HotSpot (two non-negative ints never overflow, so the sign is the same; the returned value can differ); the cross-class order stays arbitrary per JVM run, as now. Not touched by either fix: the tie-break for equal class hash codes calls getCanonicalName() (MutableValue.java:48), which returns null for a local, anonymous or hidden class (JDK 25 java/lang/Class.java:1713-1719), so a hash-code tie that involves such a subclass written outside Lucene would throw NullPointerException; a separate edge, not claimed here.

Downstream note

#

Downstream products are affected only if their own code sorts or orders MutableValues of different types and they run on OpenJ9; the effect is a wrong order or an IllegalArgumentException from the sort.

How it was found

#

A proof-obligation audit of MutableValue's Comparable contract asked whether compareTo stays transitive across classes; the class-hash subtraction can overflow. HotSpot cannot show it, so a public-API JUnit test was run on OpenJ9, where it fails. Independent checks reproduced it with their own tests.

The method in full107 words

The audit checked compareTo against Comparable's sign and transitivity rules. No same-class comparator subtracts (they use </>, Double.compare/Float.compare, a boolean test or BytesRef.compareTo); the cross-class branch subtracts two identity hash codes, which overflows whenever their true difference leaves the int range.

The finder first recorded the lead as not claimed, because its test JVM (HotSpot) cannot trigger it. An independent cross-model challenge (OpenAI GPT-5.6) argued it should be claimed, citing OpenJ9's negative identity hash codes and the public ValueFiller path; the finder then ran the same compiled test and stock jars on OpenJ9, where it failed, and kept it.

Summary
You compare MutableValues of different classes, for example a MutableValueBool, a MutableValueDouble and a MutableValueInt, with the public compareTo that MutableValue takes on by implementing Comparable<MutableValue>. You expect a consistent order: compareTo deliberately orders different classes (by class hash code, with a class-name tie-break), and Comparable requires that a < b and b < c imply a < c. On OpenJ9 with default settings, whose identity hash codes are negative or positive, the order can be cyclic instead (Bool < Double < Int, but Bool > Int), because 'c1.hashCode() - c2.hashCode()' overflows int (-1728369406 - 1684571406 = -3412940812 wraps to +882026484); on HotSpot identity hashes are non-negative 31-bit values, so it never fails there.
