OfflineSorter loses a partition permit when its executor rejects a task; once none are left, sort() on the same sorter waits until interrupted

When the ExecutorService you gave OfflineSorter rejects a partition-sort task, sort() throws but never gives back the in-memory partition permit it took. The permits belong to the sorter, so with maxPartitionsInRAM = 1 the next sort() on it waits until interrupted, even with an idle executor.

The finding in 30 seconds

#

OfflineSorter caps the partitions it holds in memory with a pool of maxPartitionsInRAM permits that belongs to the sorter object. A partition whose sort task the executor rejects keeps its permit forever.

How OfflineSorter limits memory

#
  1. OfflineSorter sorts more data than fits in RAM: it reads the input in partitions of at most the buffer size, sorts each partition into a temp file, then merges the files.
  2. With the 8-argument constructor you can pass your own ExecutorService: partitions are then sorted on its threads, and maxPartitionsInRAM caps how many are held in memory at once.
  3. The cap is a semaphore created once per sorter. Reading a partition takes a permit; the task that sorts it gives the permit back when it finishes, also on error.

The finding, step by step

#
  1. Build an OfflineSorter with your own executor, here a single-thread executor that is already shut down, and maxPartitionsInRAM = 1. Sort a one-record file: sort() throws RejectedExecutionException, as it should.
  2. Call sort() again on the same sorter. You expect the same exception at once (with the fix it does: the test method takes 0.07 s).
  3. But the first call had taken the sorter's only permit for its one partition, and only the sort task gives a permit back, when it finishes. The executor refused that task, so it never ran and the permit never came back.
  4. The second call is still blocked after 10 s, parked waiting for that permit with an idle executor, until something interrupts it. With maxPartitionsInRAM = 2, the first rejection silently halves concurrency and the second makes every later call wait.

Who is affected

#

Code that passes its own executor to the 8-argument constructor, lets it reject work (shut down, or bounded and full with the default AbortPolicy) and then calls sort() again on the same sorter, for example as a retry. The default constructors and every in-tree caller are not affected; the class is internal and experimental. Rare.

Mechanism, terms and numbers496 words

OfflineSorter, Lucene's external sorter in org.apache.lucene.util, can sort partitions concurrently on an ExecutorService you pass in, holding at most maxPartitionsInRAM partitions in memory. It enforces that cap with a semaphore owned by the sorter: readPartition takes a permit for each partition, and only the finally of the task that sorts the partition gives it back. sort() submits that task with no guard, so when the executor rejects it (shut down, or bounded and full), sort() throws RejectedExecutionException and the permit is lost for good. Each rejection lowers the sorter's concurrency by one; once all permits are gone, every later sort() on that instance parks in Semaphore.acquire until interrupted, even with an idle executor, and a shut-down executor's fail-fast exception becomes an indefinite wait. Results are never wrong and nothing is written to the index. The default constructors cannot hit it and no in-tree caller passes an executor. Every release from 6.6.0 to 10.6.0 and main is affected.

The code (main 645d4fe14a20)

#
  • A permit per partition: readPartition starts with partitionsInRAM.acquire() (OfflineSorter.java:430-433) and, on success, returns the partition still holding the permit (:478).
  • Who gives it back. Three places, and only one for a partition with data: the empty last read in sort() (:301-304), readPartition's own failure path (:479-484), and the finally of SortPartitionTask.call (:652-656).
  • The unguarded hand-off (:309-311):
Callable<Partition> job = new SortPartitionTask(trackingDir, part);

segments.add(exec.submit(job));
  • If submit throws, call() never runs, so its finally never runs. The catch (Throwable t) of sort() (:366-369) deletes the temp files and rethrows; it does not touch the semaphore.
  • The loss outlives the call: partitionsInRAM is a private final Semaphore (:76) created once per instance (:250). sort() resets its per-call state (sortInfo = new SortInfo(), :289); there is no close() and no "already used" check. The next call opens its input (:298) and parks in acquire (:432), holding that input open.
  • Not affected: the merge hand-off (:398) holds no permit. The 2- and 3-argument constructors pass null, so the sorter creates its own SameThreadExecutorService with one permit (:246-249); nothing outside the sorter can reach that executor, and it rejects only after shutdown().

The numbers

#
  • maxPartitionsInRAM = 1, one-record input, executor already shut down: the first sort() throws RejectedExecutionException; the second is still blocked after 10 s, in Semaphore.acquire <- OfflineSorter.readPartition(OfflineSorter.java:432) <- OfflineSorter.sort(OfflineSorter.java:300).
  • A bounded pool instead (1 thread, queue of 16, default AbortPolicy, filled by other work): the retry after the pool has drained waits with executor active=0 queued=0.
  • maxPartitionsInRAM = 2: after one rejection the next sort still returns correctly sorted output (one permit left); after a second rejection the next sort waits.
  • An interrupt ends the wait: sort() throws ThreadInterruptedException (:363-365). A new sorter on the same executor fails fast; only the old instance is broken.
Exposure and likelihood270 words
  • Who. Code using the 8-argument constructor with an ExecutorService that can reject: one that has been shut down, or a bounded ThreadPoolExecutor with the default AbortPolicy that other work has filled. It then has to call sort() again on the same OfflineSorter after the RejectedExecutionException.
  • Effect. Each rejected partition task silently removes one of the maxPartitionsInRAM permits. Before the last is gone, sorting is only less concurrent and stays correct. After that, every later sort() on the instance parks without CPU use, holding one thread and one open input file, until interrupted (a probe: 8 parked calls used 0 ms of CPU over 2 s and held 8 open inputs; interrupting them closed all 8 and left no temp files). With a shut-down executor, a call that should fail fast waits instead.
  • Not hit. The 2- and 3-argument constructors (their private same-thread executor is never shut down). No in-tree caller passes an executor: the hunspell SortingStrategy, FSTCompletionLookup, SortedInputIterator and AnalyzingSuggester use the default constructors, and BKDWriter passed null, 0 back in 6.x and 7.x. A read-only, non-exhaustive code search found no downstream use of the executor constructor. One in-tree public API does take a sorter the application built: ExternalRefSorter (lucene/suggest, also @lucene.internal) calls sort() from iterator(), so it can be hit only if the application hands it an executor-backed sorter and reuses that sorter after a rejection.
  • Scale. Any input size: the repro sorts one record. The class is tagged @lucene.experimental and @lucene.internal.
  • Likelihood: rare. It needs a rejecting executor plus reuse of the failed sorter; nobody has reported it since 2017.

Why it looks unintended

#
  • The author's same-day follow-up, "add try/finally to make sure semaphore is released on exceptions", fixed every other exception path; this one was missed.
  • The javadoc calls maxPartitionsInRAM "the maximum concurrent in-memory partitions" and sets no condition on the executor.
  • A shut-down executor turns a fail-fast exception into an indefinite wait; Lucene's TaskExecutor treats rejection as something that "only reduces parallelism".
The full argument266 words
  • Intent, from the history: 25f1dd2f9b2 ("LUCENE-7792: add try/finally to make sure semaphore is released on exceptions", 2017-04-26, about three hours after the feature commit) added the releases now at OfflineSorter.java:301-304 and :479-484 and moved the task's release into finally (it wrote the readPartition release as a success flag checked in finally; #14913 rewrote it as a catch in 2025, with the same behaviour). Within one sort() call nothing acquires after either new release (the loop breaks, or sort() rethrows), so they only matter to later calls on the same instance: keeping the permits balanced across calls, failed ones included, was the intent. The rejected submit is the one exception path it missed.
  • Contract: the constructor javadoc (:225-229): "If you pass a non-null ExecutorService then it will be used to run sorting operations that can be run concurrently, and maxPartitionsInRAM is the maximum concurrent in-memory partitions." The leak lowers that maximum silently, down to 0. ExecutorService.submit throws RejectedExecutionException "if the task cannot be scheduled for execution".
  • Nothing says single use: sort() resets its state per call (:289), there is no close() and no "already used" check, and the sort() javadoc is only "Sort input to a new temp file, returning its name." (:286).
  • Precedent: TaskExecutor catches RejectedExecutionException and runs the task on the caller "to ensure a rejecting executor only reduces parallelism and does not result in failure" (TaskExecutor.java:55-67; #10032 / LUCENE-8989, #13622).
  • Tests: TestOfflineSorter uses only unbounded pools (LinkedBlockingQueue), builds a fresh sorter per test and covers neither a rejection nor reuse after a failure.
The devil's-advocate check156 words

The strongest case for "intended" (rated moderate by the cross-model reviews; the devil's-advocate verifier found that none of its parts holds, the internal tag lowering only the priority): OfflineSorter is @lucene.experimental and @lucene.internal, the caller owns the executor and its capacity, every in-tree use is one-shot, and a maintainer could declare that a sorter must be thrown away after any exception; shutting down the executor you handed in is arguably misuse.

Why it fails: the internal tag speaks to API stability, not to the documented executor mode misbehaving; the 2017 follow-up shows the permits were meant to stay balanced across calls on exceptions; and even if reuse after a failure were declared unsupported, a silent, permanent drop of the documented concurrency limit (with k > 1 there is no exception at all) and a fail-fast exception turning into an indefinite wait are hard to call design. A docs-only resolution is still a plausible upstream outcome.

Suggested fix

#

Recommended Release the permit when submit throws, then rethrow (validated)

Guard the hand-off in sort(): if exec.submit(job) throws, release the partition's permit and rethrow (+11/-1 lines in OfflineSorter.java). The failing call still throws, and the sorter keeps all its permits. It passes the repro and TestOfflineSorter with assertions on and off.

Callable<Partition> job = new SortPartitionTask(trackingDir, part);

Future<Partition> future;
try {
  future = exec.submit(job);
} catch (Throwable t) {
  // the task will never run, so its finally clause cannot release the permit
  if (partitionsInRAM != null) {
    partitionsInRAM.release();
  }
  throw t;
}
segments.add(future);

Release the permit when submit throws, then rethrow (validated) (recommended)

#

Wrap segments.add(exec.submit(job)) (OfflineSorter.java:311): when submit throws, the task will never run, so give its permit back before rethrowing. The merge hand-off (:398) needs no change: it holds no permit.

Callable<Partition> job = new SortPartitionTask(trackingDir, part);

Future<Partition> future;
try {
  future = exec.submit(job);
} catch (Throwable t) {
  // the task will never run, so its finally clause cannot release the permit
  if (partitionsInRAM != null) {
    partitionsInRAM.release();
  }
  throw t;
}
segments.add(future);

Trade-offs

  • Only the path that leaks today changes; the failing call still throws the executor's exception, and the next call behaves like the first.
  • Catching Throwable also covers an OutOfMemoryError thrown by submit (the same leak, by code reading only); catching only RejectedExecutionException would be narrower.
  • An executor that threw from submit after it had already accepted the task would get a double release; the ExecutorService contract says rejection means the task "cannot be scheduled for execution", so this is theoretical.
  • partitionsInRAM is never null (:250); the null check only mirrors the existing release sites.
  • Scope: it covers a submit that throws. A rejection handler that drops the task without throwing (DiscardPolicy, DiscardOldestPolicy, or CallerRunsPolicy once the pool is shut down, as the JDK's ThreadPoolExecutor javadoc documents), or tasks removed by shutdownNow(), leave a future that never completes and a permit that never comes back; the sort() call that submitted the task then waits itself (for the future in getPartition, OfflineSorter.java:660-662, or for the permit in the next readPartition). By code reading, not run. No change at the submit site can see that; it is the documented effect of those handlers, not this bug.

Run a rejected partition task on the calling thread, like TaskExecutor (not run)

#

On RejectedExecutionException, call the SortPartitionTask in sort() and wrap the result in a completed future; its finally then releases the permit. Treat the merge hand-off (:398) the same way for consistency.

Trade-offs

A rejecting executor then only reduces parallelism, as in TaskExecutor (TaskExecutor.java:55-67), and the first sort() succeeds too. But it changes visible behaviour: sort() would succeed on an executor that was shut down, which callers may use to stop work, and the regression test would have to assert success instead of the exception. Not validated.

Document that a sorter must not be reused after an exception (complement only)

#

A javadoc note on sort() or the 8-argument constructor.

Trade-offs

Leaves the silent loss of concurrency for maxPartitionsInRAM > 1 and the indefinite wait in place.

Downstream note

#

Downstream, the risk is one unusable sorter object: a service that kept a sorter across requests on a bounded, rejecting executor would see later sorts wait until interrupted; a read-only, non-exhaustive code search found no downstream use of the executor constructor.

How it was found

#

TLA+ model checking (TLC) of a protocol model of the sorter, with "the executor may reject a task" switched on, found a 4-state trace that ends with a permit missing after sort() failed. A JUnit on the stock jar confirmed it, and independent reproducers, read-only cross-model reviews, an adjudication and an audit checked it.

The method in full160 words

Method: formal (TLA+ model checking, then a public-API JUnit).

  • Model. OfflineSortProto.tla models the main thread, the partitionsInRAM semaphore, a FIFO executor with W workers, the partition-sort and merge tasks, the merge cascade and the failure cleanup. Invariant PermitsBack: once sort() has ended and every task has finished, the permits equal maxPartitionsInRAM.
  • Result. With "submit may be rejected" on, TLC reports a 4-state violation (acquire, submit rejected, cleanup, failed with 0 permits) in all 4 rejection configurations (W in {0, 1}, maxPartitionsInRAM in {1, 2}); without rejection it holds in all 24 configurations with one injected I/O error or interrupt.
  • Confirmation. A JUnit on the stock main jar (a saturated bounded pool, then a retry) failed with assertions on and off and on releases back to 6.6.0. An independent reproducer, a devil's-advocate verifier, read-only cross-model reviews (OpenAI GPT-5.6), an adjudication and a credibility audit checked it; a follow-up ran the version history, a prior-report search and a security screen.

Only applications that build OfflineSorter (tagged @lucene.experimental and @lucene.internal) with the 8-argument constructor and their own ExecutorService that can reject work (a bounded ThreadPoolExecutor with the default AbortPolicy that other work has filled, or an executor that has been shut down), and that call sort() again on the same OfflineSorter instance after the rejection: each rejected partition task permanently removes one of the maxPartitionsInRAM permits, so the first k-1 rejections silently lower sort concurrency and after the k-th every later sort() on that instance parks in Semaphore.acquire until interrupted (no CPU spin, no wrong result, no index file touched; the default constructors cannot hit it and no in-tree caller passes an executor); ordinary scale, every release 6.6.0 to 10.5.2 and main.
Summary
You give OfflineSorter your own bounded thread pool, one sort() fails with RejectedExecutionException because the pool was full (or shut down), and you expect the same sorter to work again once the pool is idle, since every other exception path gives the partition's partitionsInRAM permit back. Instead the permit that readPartition took for the rejected partition is never released (only the task's finally block releases it, and a rejected task never runs; the semaphore belongs to the sorter instance), so with maxPartitionsInRAM = 1 the next sort() on that sorter waits forever in Semaphore.acquire with an idle executor (executed: 'sort() did not return within 20 s; waiting for a partition permit: true; executor active=0 queued=0'). With maxPartitionsInRAM = k each rejection costs one permit and after k rejections every later sort() hangs; with a shut-down executor, a call that should fail fast with RejectedExecutionException waits instead.
