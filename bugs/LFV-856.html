Monitor scores a sub-query that occurs twice in a stored query only once

The Monitor keeps a stored query's parts in a Set, so a sub-query that occurs twice, like apple in (red apple) (green apple), is scored once: ScoringMatch gives 0.39229372, not the query's 0.5230583. Matching is right for these shapes; the low scores occur in all 57 releases since 8.2.0.

The bug in 30 seconds

#

The Monitor splits a stored query into parts so it can pick candidate queries fast, then adds up the scores of the parts that match. The parts are kept in a Set, which holds each query once, so a part that occurs twice is run and counted once.

  1. Register (red apple) (green apple) (classic QueryParser, field body) in a default Monitor, and match the document {body: "red green apple"} with ScoringMatch and BM25.
  2. On this document each word alone scores 0.13076457. The query names apple twice, so you expect 4 x 0.13076457 = 0.5230583, which is what IndexSearcher returns.
  3. You get 0.39229372 = 3 x 0.13076457: apple is counted once. ExplainingMatch shows the same value as a "sum of:" green, apple and red. apple apple and +apple +apple get 0.13076457 instead of 0.26152915. No error.
  4. Why: the default QueryDecomposer splits the query into parts so the presearcher can pick candidates fast, and collects the parts in a Set: {red, apple, green}. The two apples are equal queries, so the Set keeps one, and ScoringMatch adds up the scores of the parts that match.
  5. Controls: (red apple) (green pie), with no repeated part, gets 0.39229372 from both, and a decomposer that keeps the query whole gets 0.5230583. Whether each of these queries matches does not change.

Who is affected

#

Applications that use lucene-monitor and read scores through ScoringMatch (also via ParallelMatcher or PartitionMatcher) or ExplainingMatch, with a stored query that repeats a sub-query: a repeated word, overlapping expansions that share a term, or a repeated required clause that is the only distinct required clause (+apple +apple). Default configuration, any scale; for these shapes matching and highlighting are unaffected.

Mechanism, terms and numbers858 words

The Monitor (lucene-monitor) matches documents against stored queries. To select candidate queries quickly, its default QueryDecomposer splits a registered query into parts and collects them in a Set, which keeps equal queries once. When several parts of one query match a document, ScoringMatch and ExplainingMatch merge them by adding their scores. A BooleanQuery, however, counts a repeated clause at every occurrence. So when an equal sub-query occurs more than once among a registered query's decomposed SHOULD parts, or as a repeated required clause that is the only distinct required clause, with no SHOULD clause beside it, the Monitor reports, on every document on which that part matches, a score that counts the part once: (red apple) (green apple) on "red green apple" gets 0.39229372 instead of 0.5230583, and apple apple and +apple +apple get 0.13076457 instead of 0.26152915. The classic QueryParser builds all three from plain input. For these shapes, which queries match is unchanged. It is in every release since the module was imported (LUCENE-8766, 8.2.0). Keeping such a query whole in the decomposer (+25/-4 lines, one decomposer test added) fixes it, and the whole monitor module passes with that change.

Terms

#
  • Monitor (lucene-monitor, org.apache.lucene.monitor): stores queries and matches incoming documents against them. A matcher chosen per match call decides what is reported: SIMPLE_MATCHER (query ids), ScoringMatch (ids and scores), ExplainingMatch (ids and an Explanation), HighlightsMatch (matching terms).
  • QueryDecomposer: splits a registered query into parts that are indexed and run separately, so the presearcher can select only the parts whose terms occur in the document. Each part keeps the registered query's id. decompose returns a Set<Query>.
  • Repeated part: a sub-query that occurs more than once, compared with Query.equals: apple in (red apple) (green apple), a repeated term apple apple, or a repeated required clause +apple +apple.

The bug

#
  1. QueryDecomposer.decompose returns a Set<Query> (QueryDecomposer.java:42). decomposeBoolean adds the parts of every SHOULD clause to one LinkedHashSet (:80, :89) and the MUST/FILTER clauses to a HashSet (:82, :85-86); the DisjunctionMaxQuery branch adds its disjuncts' parts to a LinkedHashSet (:46-52). Equal parts are kept once.
  2. For +apple +apple the HashSet holds one clause, so the keep-whole rule for more than one required clause (:94-95) does not fire, and the single required clause is decomposed (:99-101).
  3. QueryCacheEntry.decompose stores one entry per Set element under the parent's id (QueryCacheEntry.java:51-59), and the Monitor runs every part the presearcher selects on its own (Monitor.java:299).
  4. CandidateMatcher.addMatch merges two matches of one id with resolve() (CandidateMatcher.java:75-85). ScoringMatch.resolve returns match1.getScore() + match2.getScore() (ScoringMatch.java:42-44); ExplainingMatch.resolve builds a "sum of:" explanation (ExplainingMatch.java:44-52).
  5. BooleanQuery.rewrite merges repeated SHOULD and MUST clauses "into a single clause with a combined boost" (BooleanQuery.java:438-455, :706-713): an unboosted repeat gets similarity.computeQueryTermWeight(count) (:743-746), which is count for default BM25 and the base Similarity. So the query counts the repeat, and with default BM25 the Monitor's score is too low by the score of each extra occurrence of a part that matches (with BM25's optional k3 > 0 the loss is smaller, and with k3 = 0 there is none).

A plain Boolean disjunction whose parts are all distinct is scored right (a DisjunctionMaxQuery with tie below 1 and a FILTER-only required clause are mis-scored even without a repeat: those are two separate sibling bugs), and so is a repeated part that does not match the document (it scores 0 both ways). A repeated required clause next to another required clause or a SHOULD clause is kept whole by line 94 and scored right: +apple +apple +red and +apple +apple green both get 0.39229372 from IndexSearcher and from the Monitor, while nested (+apple +apple) red is mis-scored (0.26152915 instead of 0.39229372). For these shapes matching is unchanged: a collapsed part matches exactly where its copies do. The one exception found is +apple +apple with minimumNumberShouldMatch=1, which the collapse turns into the shape of a separately registered minimumShouldMatch bug, so the Monitor reports a match that IndexSearcher does not.

Exposure and likelihood283 words
  • Who. lucene-monitor users with the default QueryDecomposer (MonitorConfiguration.java:38) who read scores through ScoringMatch (directly or through ParallelMatcher / PartitionMatcher, which report the same values) or ExplainingMatch, and register a query in which an equal sub-query occurs more than once among its decomposed SHOULD parts (a repeated word in user input, apple apple; overlapping expansions that share a term, (red apple) (green apple)), or a repeated required clause that is the only distinct required clause of its BooleanQuery, with no SHOULD clause beside it (+apple +apple, or nested, (+apple +apple) red). +apple +apple +red and +apple +apple green are kept whole and scored right.
  • Default vs opt-in. The Monitor configuration and the decomposer are the defaults; lucene-monitor is an optional module, and the matcher is chosen per match call (no default); ScoringMatch and ExplainingMatch are two of the four documented matchers. The classic QueryParser builds all three shapes from plain strings.
  • Scale. None needed: one query and one document show it, deterministically, with assertions on and off.
  • Effect. Too-low scores, and explanations that omit the repeat, which can mis-rank or mis-threshold stored queries against each other. For these shapes the set of matching queries is right (the one exception found, +apple +apple with minimumNumberShouldMatch=1, is described in the bug section); nothing failed or was corrupted in any run, and the values look plausible.
  • How likely. Rare: it needs the scoring matchers and a stored query with a repeated part, which is uncommon within one query; the one public Monitor integration found (an open Solr pull request) defers the scoring matchers. The lack of reports since 2019 is weak evidence, because the wrong values look reasonable.

Why it is a bug, not intended

#
  • The Monitor javadoc reports "the score that each one records against a Document"; nothing says a repeated part counts once.
  • The port's own test expects the "sum of the scores" of the parts, which equals the whole query's score.
  • Core BooleanQuery counts a repeated clause at every occurrence (LUCENE-7925); the Monitor contradicts it on plain QueryParser input.
The full argument320 words
  • Monitor contract. package-info.java:40-45: ScoringMatch.matchWithSimilarity "returns the set of matching queries, with the score that each one records against a Document"; ExplainingMatch is "similar to ScoringMatch, but include the full Explanation". The natural reading is the query's own score.
  • Core contract. BooleanQuery.deduplicateClauses merges repeated queries "into a single clause with a combined boost" (BooleanQuery.java:706-713); core has counted repeated scoring clauses since LUCENE-7925 (#8974, 2017, "Collapse duplicate SHOULD or MUST clauses by summing up their boosts"), asserted by TestBooleanRewrites.testDeduplicateShouldClauses and testDeduplicateMustClauses. The classic QueryParser's apple apple is explained with "2.0 = boost" and rewritten to (body:apple)^2.0.
  • No distinct-parts semantic is documented. QueryDecomposer's javadoc says only "Split a disjunction query into its constituent parts, so that they can be indexed and run separately"; CandidateMatcher.resolve says "combine them". No CHANGES or MIGRATE entry discusses it.
  • The only test that pins a score value. ConcurrentMatcherTestBase.testMatchesAreDisambiguated says "We need to check that each query ends up with the sum of the scores for the 'test' and 'doc' parts" and asserts 1.4874471; an executed check showed that this is IndexSearcher's score for the whole query. The sum was meant to rebuild the query's own score, which it does for a plain Boolean disjunction whose parts are all distinct (the DisjunctionMaxQuery and FILTER sibling bugs aside). The test does not literally state equality with the whole query's score, and no upstream test has a query with a repeated part.
  • History. The predecessor library (Luwak) kept the parts in Lists and its resolve kept the larger match, so a repeat could not change a score there. The 2019 import (LUCENE-8766) changed the parts to a Set and resolve to a sum in the same commit, and rewrote the shared test from "the score for the 'test' subquery, not the 'doc' subquery" to "the sum of the scores", with no recorded discussion. #14886 / #14885 (2025) discussed the Set only for its iteration order.
The devil's-advocate check186 words

The strongest works-as-designed case (the devil's advocate and the cross-model reviewer): decompose has returned Set<Query> in the public API since 8.2.0, so the parts are defined by uniqueness, and running an equal part twice would be wasted work; nothing literally promises that a Monitor score equals IndexSearcher's; the decomposer already misreports DisjunctionMaxQuery and FILTER scores, and Luwak's max never equalled a disjunction's score either, so Monitor scores could be called a heuristic; and a decomposer that never splits is a supported customization.

Why it fails: nothing documents a distinct-parts semantic, the package javadoc reads as the query's own score, and the port's own test treats the sum of the parts as the query's score. The Set is fine for matching; the defect is that the summing resolve assumes each part occurs once. Core deliberately keeps the weight of a repeat, and the Monitor contradicts it on queries built from plain QueryParser input. The other mis-scorings are separate bugs, and a workaround is not a contract. Verdict: not intended; a defect since the import. At worst upstream answers with a javadoc change; the issue should offer both.

Suggested fix

#

Recommended Keep a query whole when a part or a required clause repeats (QueryDecomposer)

In QueryDecomposer, count the parts with multiplicity and keep a query whole when one of its parts or required clauses repeats (+25/-4 lines, plus one decomposer test). The whole monitor module passes (197 tests), the repros included, with assertions on and off, and its static checks pass.

int shouldParts = 0, mandatoryClauses = 0;
for (BooleanClause clause : q) {
  if (clause.occur() == MUST || clause.occur() == FILTER) {
    mandatory.add(clause.query());
    mandatoryClauses++;
  } else if (clause.occur() == MUST_NOT) exclusions.add(clause.query());
  else {
    Set<Query> decomposed = decompose(clause.query());
    shouldParts += decomposed.size();
    subqueries.addAll(decomposed);
  }
}
if (subqueries.size() < shouldParts || mandatory.size() < mandatoryClauses)
  return Collections.singleton(q);

Keep a query whole when a part or a required clause repeats (QueryDecomposer) (validated by the checks) (recommended)

#

decomposeBoolean counts the SHOULD parts and the required clauses before they go into the Sets, and returns the query as a singleton when a Set is smaller than its count; the DisjunctionMaxQuery branch does the same for its disjuncts' parts. The new TestQueryDecomposer.testRepeatedPartsAreNotDecomposed asserts that hello hello, +hello +hello, (hello world) (goodbye world) and DisMax(f:t1, f:t1) stay whole. +25/-4 lines in QueryDecomposer.java, +12 in the test. Trade-offs

  • A query with a repeated part becomes one presearcher entry instead of one per distinct part, and runs whole whenever it is selected. The cost was not benchmarked. Decomposition happens at register, before any matcher is chosen, so the change applies to every matcher, SIMPLE_MATCHER and highlighting included: for such queries the cache entries, the presearcher's selectivity and getQueriesRun() change too. Matching is unchanged for the three repro shapes (the module's matching and presearcher tests pass, and a match-set probe agrees on every row with the fix). The public counts Monitor.getDisjunctCount() and QueryCacheStats drop for a query that had several distinct parts on stock, such as (red apple) (green apple) (3 entries become 1); apple apple, +apple +apple and DisMax(a, a) keep one entry.
  • Queries whose parts are all distinct decompose exactly as before (the 11 existing decomposer tests pass).
  • The rule is conservative: it also keeps whole some repeats whose score the collapse does not change, such as DisMax(a, a) with tie 0 or any repeat under BM25 with k3 = 0. No such case was compared.
  • Side effect: +apple +apple with minimumNumberShouldMatch=1, where the collapse made the Monitor report a match that IndexSearcher does not, is now kept whole and agrees. The separately registered minimumShouldMatch bug (one distinct required clause) needs its own fix.
  • The DisjunctionMaxQuery sibling's fix edits the same DisjunctionMaxQuery branch, so the two patches conflict textually but combine logically; they were not run together.

Keep the split for the presearcher, run the registered query whole (Monitor, QueryCacheEntry) (validated by the checks)

#

From the DisjunctionMaxQuery sibling's doc: each QueryCacheEntry also keeps its parent MonitorQuery's query, and the Monitor runs that whole query once per query id when the presearcher selects any of its parts. +17/-3 lines in QueryCacheEntry.java and Monitor.java; written as a sketch.

Trade-offs

  • Fixes this bug and both sibling decomposition bugs (DisjunctionMaxQuery summed, FILTER clause scored).
  • It changes every matcher, not only the scoring ones; getQueriesRun() no longer equals the number of queries executed; a large disjunction runs whole when one part is selected; every cache entry keeps a reference to its parent's query. Not benchmarked; a design change for maintainers to weigh.

Return a List (or a multiset) from decompose

#

Keep every occurrence as its own part, so the sum counts each one.

Trade-offs

An API change: decompose, decomposeBoolean and decomposeBoostQuery are public and overridable. It would also change the per-part cache ids that #14885 made stable across JVMs. Not run.

Keep the Set, but boost a repeated part by its count

#

Wrap a part that occurs n times in a BoostQuery of n.

Trade-offs

Exact only for linear similarities: on main an unboosted repeat is weighted by Similarity.computeQueryTermWeight(n), which saturates for BM25 with k3 >= 0, and the decomposer does not know the Similarity, which the matcher chooses per match call. Not run.

Document that Monitor scores count each distinct decomposed part once

#

A note in the package javadoc and on ScoringMatch / ExplainingMatch.

Trade-offs

A legitimate maintainer choice, but queries built from plain QueryParser input stay mis-scored. Not run.

Workaround today: a decomposer that keeps such queries whole

#

A QueryDecomposer subclass whose decompose returns the query as a singleton (for every query, or only when a part repeats), set with new MonitorConfiguration().setQueryDecomposer(...). No Lucene change.

Trade-offs

Gives IndexSearcher's exact score (the independent reproducer's oracle, the devil's-advocate probe and this doc's control test); every application has to know about it.

Downstream note

#

For these shapes only scores change, not which queries match, so products that route or alert on Monitor matches are unaffected (one exception: +apple +apple with minimumNumberShouldMatch=1 gives a false match, in the shape of a separately registered bug); products that rank or threshold on ScoringMatch scores see too-low values for stored queries that repeat a sub-query.

How it was found

#

The finder compared six Monitor matchers with IndexSearcher over every small query and document in a bounded space plus 3,000 random larger queries (6.5 million checks). The first signal was a a on document a: 0.13076457 instead of 0.26152915. Keeping a query whole when its parts collapse removed this mismatch family; a Z3 model confirmed the condition.

The method in full210 words

Method: bounded-exhaustive translation validation against a reference semantics (the hunt's "semi-formal" tier).

  • The finder's harness ran six matchers (simple, scoring, explaining, highlighting, parallel, partition) on the stock decomposer, and three of them on six decomposer variants, against IndexSearcher on a one-document index: every depth-1 query (420) on 55 documents, every depth-2 query (7,685) on 19 documents, and 3,000 random depth-3 queries on 34 documents; 6,506,760 checks with assertions on and the same with them off.
  • First signal (depth 1): body:a body:a on the document "a", 0.13076457 instead of 0.26152915. The unit found it itself; the planning probe for this area had not.
  • Root attribution with public decomposer subclasses: the variant that keeps a query whole when its parts would collapse was the only single change that removed 252, 1,142 and 365 score-mismatch rows in the three tiers, for the scoring and the explaining matcher each; further rows were removed by it together with a sibling variant. The DisjunctionMaxQuery and FILTER variants explain the two sibling bugs and leave this repro failing.
  • A Z3 model of the score algebra over the reals confirmed that a collapsed repeat keeps the score only when the repeated part does not match.
  • The finder then wrote the public-API JUnit test, and independent checkers reproduced it.

Bug record

#

LFV-856, snapshot of 2026-10-29

Registry title
Lucene Monitor's QueryDecomposer collects a query's parts in a Set, so a sub-query that occurs more than once in a registered query (a repeated SHOULD or MUST clause, or a term shared by two nested disjunctions) is scored once by ScoringMatch and ExplainingMatch instead of once per occurrence
Area
monitor / query decomposition and match scoring (QueryDecomposer Set<Query> parts, ScoringMatch/ExplainingMatch resolve)
Priority
Low, rank 394: Monitor matches stay correct, and only the opt-in ScoringMatch and ExplainingMatch give scores and explanations that are too low, and only for stored queries that repeat a sub-query.
Impact class
silent wrong results
Impact note
Applications that use lucene-monitor with its default QueryDecomposer and read match scores through ScoringMatch (directly or through ParallelMatcher/PartitionMatcher) or ExplainingMatch get, for every registered query in which an equal sub-query occurs more than once among its decomposed parts or its required clauses ('apple apple', '+apple +apple', '(red apple) (green apple)': shapes the classic QueryParser builds from plain input), a score that counts the repeated part once (0.13076457 instead of 0.26152915 and 0.39229372 instead of 0.5230583 in the repro); which queries match is unchanged (SIMPLE_MATCHER agrees with IndexSearcher), no scale is needed, and it is in every release since 8.2.0.
Summary
You register a query such as '(red apple) (green apple)' or 'apple apple' in a Monitor and match the document 'red green apple' with ScoringMatch or ExplainingMatch, expecting the score the query itself gives that document, which is what IndexSearcher returns, because BooleanQuery counts a repeated clause at every occurrence (0.5230583 and 0.26152915). Instead the Monitor reports 0.39229372 and 0.13076457: the default QueryDecomposer collects the query's parts in a Set, which keeps equal parts once, and the scoring matchers add up the scores of the distinct parts, so the shared 'apple' is counted once. Which queries match is not affected; only the scores and explanations of such queries are too low.
