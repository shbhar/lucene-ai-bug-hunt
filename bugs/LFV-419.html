SortedDocValues#ordinalRangeIntoBitSet, called right after advanceExact returned false, marks a document that has no value

On a SORTED doc-values field that some documents lack, ordinalRangeIntoBitSet called right after advanceExact(d) returned false marks the value-less document d by a neighbouring document's ordinal, or throws (EOFException; ArrayIndexOutOfBoundsException on a plain ByteBuffersDirectory). The method is new in the unreleased 10.6.0; no Lucene query makes this call.

The bug in 30 seconds

#

ordinalRangeIntoBitSet (new in 10.6.0) fills a bit set with the documents in [fromDoc, toDoc) whose ordinal is in a range. Its default reads the ordinal of the document the iterator is on without checking that the document has one.

Background: how a doc-values iterator moves

#
  1. A SortedDocValues iterates over the documents that have a value; nextDoc() and advance() only stop on such documents. ordValue() returns the current document's ordinal: its value's rank in the field's sorted dictionary ("a" = 0, "b" = 1).
  2. advanceExact(d) moves to exactly d and returns whether d has a value. After false, docID() is d but there is nothing to read: calling ordValue() then is illegal.
  3. ordinalRangeIntoBitSet(fromDoc, toDoc, minOrd, maxOrd, bits, offset) is a bulk call. The default codec overrides it for some encodings, such as a field every document has; a sparse field with two or more values runs the default in SortedDocValues.

The bug, step by step

#
  1. Index three documents with the default codec into a SORTED doc-values field f: doc 0 = "a", doc 1 has no value, doc 2 = "b".
  2. On the segment's SortedDocValues, advanceExact(1) returns false: doc 1 has no value, and the iterator now sits on doc 1. On the same iterator, call ordinalRangeIntoBitSet(1, 3, ord("a"), ord("a"), bits, 0): which documents in [1, 3) have "a"?
  3. You expect none: doc 1 has no value and doc 2 has "b". The per-document advanceExact/ordValue loop that the javadoc describes gives exactly that, and so does the same call on a fresh iterator.
  4. Instead bit 1 is set, with no error. The default starts at the current document and calls ordValue() there, which the API calls illegal after a false advanceExact; the codec's sparse iterator still points at doc 0's value, "a".
  5. If no earlier document has a value (doc 0 empty, advanceExact(0)), the same call throws instead: RuntimeException(EOFException) on most directories, ArrayIndexOutOfBoundsException on a plain ByteBuffersDirectory. In this call pair only the first document of the call can be wrong, and only as an extra match.

Who is affected

#

Only code that calls SortedDocValues#ordinalRangeIntoBitSet itself, on the same iterator, right after advanceExact(d) returned false, on a SORTED field that some documents lack (default codec). Lucene's own queries never do this. Each call gets at most one extra document. Unreleased: main and the 10.6.0 release candidate.

Mechanism, terms and numbers955 words

SortedDocValues#ordinalRangeIntoBitSet(fromDoc, toDoc, minOrd, maxOrd, bitSet, offset), added in 10.6.0 by #16180, fills bitSet with "the doc IDs in [fromDoc, toDoc) whose ordinals are in [minOrd, maxOrd]", and its javadoc says the default "falls back to per-doc evaluation via advanceExact and ordValue". The default instead starts at the current document whenever docID() >= fromDoc and calls ordValue() there (SortedDocValues.java:117-118 on main 645d4fe14a20). After advanceExact(d) returned false the iterator sits on d, which has no value, and ordValue() is documented as illegal in that state. The default codec's sparse SORTED iterator (two or more distinct values, some documents without one) has no override, and its ordValue() reads with the stale index that advanceExact left: in the tested layouts doc d is judged by the previous valued document's ordinal (in a DENSE block the next one's, or the padding after the last ordinal when none follows), or the call throws when no earlier document has a value (RuntimeException(EOFException), or ArrayIndexOutOfBoundsException on a plain ByteBuffersDirectory). Wrappers that inherit the default (FilterSortedDocValues, MultiDocValues) are affected even with one distinct value. With docs {0: "a", 1: none, 2: "b"}, advanceExact(1) then ordinalRangeIntoBitSet(1, 3, ord("a"), ord("a"), bits, 0) sets bit 1 instead of nothing, with assertions on and off. In this call pair only the start document can be wrong. No Lucene query, sort, facet or merge path makes this call order, and the method is unreleased (main and the 10.6.0 release candidate), so the priority is low. Skipping a start document without a value (8 lines) fixes it; the test and 14 doc-values suites pass with the fix.

The mechanism (main 645d4fe14a20)

#
  1. The cursor after a false advanceExact. "After this method returns, docID() returns target" (DocValuesIterator.java:24-28); the note below names only intoBitSet and docIDRunEnd() as illegal after a false return (:30-31).
  2. The default (SortedDocValues.java:117-122):
   for (int doc = docID() >= fromDoc ? docID() : advance(fromDoc); doc < toDoc; doc = nextDoc()) {
     long ord = ordValue();
     if (ord >= minOrd && ord <= maxOrd) {
       bitSet.set(doc - offset);
     }
   }

With docID() == fromDoc it starts on that document and calls ordValue() (:118), which "is illegal to call ... after advanceExact(int) returned false" (:38-39).

  1. Which iterator runs it. For ordinals stored as one packed block with more than one value (Lucene90DocValuesProducer.java:1473-1477), the dense branch overrides the method with random access (:1548-1555) and is correct; the sparse branch (:1557) has no override, and its ordValue() is (int) values.get(disi.index()) (:1569-1571). The generic iterator (one distinct value, or ords not in one block) delegates to the numeric rangeIntoBitSet (:1654-1661) and answers correctly when called directly. FilterSortedDocValues (so also ExitableDirectoryReader's wrapper), MultiDocValues.MultiSortedDocValues and AssertingSortedDocValues do not override the method, so wrapped iterators run the faulty default, over the generic iterator too: there ordValue() reaches ords.longValue(), which for one distinct value is the constant entry.minValue (:1090-1096), so a wrapper marks the value-less document whenever that ordinal is in range (AssertingSortedDocValues with -ea fails assert exists instead).
  2. What the stale index holds (the tested layouts). After a miss in a SPARSE block, IndexedDISI steps the index back to the last valued document before the target, or leaves -1 if there is none (IndexedDISI.java:607-616); in a DENSE block the index is the rank of the next valued document (:712-713), which is one past the last stored ordinal when no valued document follows. Hence doc 0's ordinal in the example, the next document's ordinal in a DENSE block, the padding after the last ordinal (read as 0) when nothing follows, and values.get(-1), an exception, when nothing precedes. These are the executed layouts, not every IndexedDISI state: a target inside a 65,536-document block with no values (advanceBlock, :495-516), for example, was not run.
  3. Only the start document. After it the loop moves with nextDoc(), which lands only on documents with a value, so later bits are right and no later valued document is dropped. Separate, pre-existing behaviour, not this bug: when docID() > fromDoc the default starts at docID() and never evaluates [fromDoc, docID()), valued documents included; the fixes below keep that (a forward-only iterator cannot go back).

Why it is a bug, not intended

#
  • The javadoc promises the documents in [fromDoc, toDoc) with an ordinal in range, by per-doc advanceExact/ordValue evaluation, which is right here.
  • The default itself calls ordValue() where the API forbids it, not the caller.
  • From the same state the dense override, the unwrapped single-value path and the numeric siblings' defaults answer correctly; the sparse SORTED path marks doc 1.
The full argument254 words
  • Contract. SortedDocValues.java:99-105 (the method's javadoc); :38-39 (ordValue()); DocValuesIterator.java:30-31 lists only intoBitSet and docIDRunEnd() as illegal after a false advanceExact. The method has no @lucene.internal or @lucene.experimental tag, while DocIdSetIterator#intoBitSet is @lucene.internal (DocIdSetIterator.java:203).
  • Encoding-dependent answers. An executed consistency probe on one codec: a SORTED field with one distinct value (unwrapped) and a NumericDocValues field give the per-doc answer from the same state; a sparse SORTED field with two values marks the value-less document.
  • The test framework flags it. AssertingSortedDocValues.ordValue asserts exists (AssertingLeafReader.java:1084), so the default trips Lucene's own assertion.
  • History. The first revision of #16180 (f5a83a8d11a) was the per-doc advanceExact loop. A reviewer (jimczi) asked "Why advanceExact per-doc here instead of iterating with advance/nextDoc? This is really just a range scan over the docs that have a value, which is the same pattern as the default DocIdSetIterator.intoBitSet and the old BulkOrdinalRangeIterator." They gave a performance reason (per-doc advanceExact walks every gap document of a sparse field) and proposed today's loop; revision 03ccba9729b adopted it and left the javadoc unchanged. Nobody discussed a start state reached by a false advanceExact.
  • Why tests missed it. Three tests reach the method, all through DocValuesRangeIterator, which moves the iterator with advance() and never leaves it on a false advanceExact. TestDocValuesRangeIteratorIntoBitSet#testOrdinalRangeIntoBitSetMatchesPerDocEvaluation and #testOrdinalIntoBitSetMatchesLinearScan index real documents that all have a value; TestDocValuesOrdinalRangeIterator#testSortedDocValuesIntoBitSetMatchesLinearScan runs the stock default on a mock iterator in which some documents have no value, but never from a false advanceExact.
The devil's-advocate check254 words

Strongest case (the intended-behaviour check, the adjudication, the prior-report search): the default was modelled on DocIdSetIterator#intoBitSet on purpose: jimczi's #16180 review chose the scan over present documents so that sparse fields do not walk every gap document. In #14529 a maintainer (jpountz) wrote "It shouldn't be legal to call intoBitSet after advanceExact returns false", which became the note on advanceExact; that settled the rule for DocIdSetIterator#intoBitSet, not for every bulk method. So this call order could be called misuse, fixed by adding the method to that note; the method is also unreleased, no in-tree caller reaches the state, and the default already skips [fromDoc, docID()) when docID() > fromDoc, an implied precondition (the hunt's credibility audit).

Why it fails: intoBitSet is relative to docID(), while this method takes an explicit absolute fromDoc and its javadoc still describes the per-doc loop; nothing documents a precondition; the answer changes with the encoding; one layout throws a codec exception (EOFException, or ArrayIndexOutOfBoundsException on a plain ByteBuffersDirectory) rather than a clean argument check. Open PR #16835 (kkewwei, approved by sgup432, not merged) accommodates this call order in sibling code: for table-encoded entries it adds exactly this guard to the Lucene90 numeric and sorted-numeric overrides, and its test calls advanceExact(fromDoc) before the bulk call; the PR is framed as a speed-up and does not call the sequence a public API contract. Residual risk: maintainers may prefer to document a precondition; the stale javadoc and the codec exception would still need fixing then.

Suggested fix

#

Recommended Skip a start document that has no value

In the default, when the iterator already sits at or past fromDoc, check the current document with advanceExact(docID()) and skip it with nextDoc() if it has no value (SortedDocValues.java, +8/-1). The test and 14 doc-values suites (728 tests) pass, with assertions on and off.

-    for (int doc = docID() >= fromDoc ? docID() : advance(fromDoc); doc < toDoc; doc = nextDoc()) {
+    int doc = docID();
+    if (doc < fromDoc) {
+      doc = advance(fromDoc);
+    } else if (doc < toDoc && advanceExact(doc) == false) {
+      // positioned by advanceExact() on a doc without a value: skip it
+      doc = nextDoc();
+    }
+    for (; doc < toDoc; doc = nextDoc()) {
       long ord = ordValue();

Trade-offs

  • One advanceExact(docID()) per call when the iterator is already at or past fromDoc (legal: target >= docID()); for the in-tree caller one cheap check per MAYBE block. No benchmark was run.
  • Caveat to state (the adjudication, from the cross-model refute review): flush-time BufferedSortedDocValues and some merge views throw UnsupportedOperationException from advanceExact, but they also throw from advance(), so the stock default already fails on them when docID() < fromDoc; none of them is passed to this method in-tree.

How it was found

#

A bounded-exhaustive check: a harness made every legal sequence of up to three iterator moves on tiny segments, for 26 doc-values and norms views, and compared each step with a fresh nextDoc() enumeration. The mismatch class "advanceExact false, then a bulk range call" led here; it was then reduced to a JUnit on the public API.

The method in full198 words

Method: bounded-exhaustive translation validation (semi-formal), a hunt unit. The harness drives the stock jar through every legal move sequence of depth up to 3 over nextDoc, advance, advanceExact, intoBitSet, docIDRunEnd, intoArray, longValues, rangeIntoBitSet and ordinalRangeIntoBitSet on segments of up to 5 documents (skip index on and off), plus random sequences on 70,000-document segments covering SPARSE, DENSE and ALL blocks and two-cursor interleavings, for 26 doc-values and norms views, and compares each step with a fresh nextDoc() enumeration of the same view: about 990M sequences over two batches. Mismatch class LEAD-B (advanceExact(t) == false, then a bulk range call starting at t) had 1,770 mismatches in a small-scope run: 1,350 on SORTED views (this bug) and 420 on SORTED_NUMERIC views (the numeric sibling LFV-415); 0 with this fix and the sibling's fix shadowed. The SORTED mismatches came from the segment's own iterator, its merge instance, the ParallelLeafReader, FilterSortedDocValues, ExitableDirectoryReader and AssertingLeafReader views (that run recorded wrong bits there, not an assertion failure), and the multi-segment views. The finder then wrote a public-API JUnit on the stock main jars; this doc's test is a one-method version of it.

LFV-419, snapshot of 2026-10-30

Registry title
SortedDocValues#ordinalRangeIntoBitSet's default implementation, called after advanceExact(d) returned false, reads ordValue() for doc d, which has no value, so it marks d using a neighbouring document's ordinal (or throws EOFException)
Area
index / SortedDocValues bulk ordinal range (default implementation; Lucene90 sparse SORTED iterator)
Priority
Low, rank 520: This unreleased bulk-API default gives a wrong bit only for an advanceExact-false-then-bulk call pattern that Lucene never uses, so it joins the expert iterator-cursor rows after LFV-142.
Impact class
silent wrong results
Impact note
Only application code that calls the public, untagged SortedDocValues#ordinalRangeIntoBitSet (new in unreleased 10.6.0) itself, from a document d on which advanceExact(d) just returned false on the same iterator, over a SORTED field that some documents lack, is hit, on the default codec; each such call marks at most one extra document (d, judged by the previous valued document's ordinal in a SPARSE block or the next one's in a DENSE block) or throws RuntimeException(EOFException) when no earlier document in a SPARSE block has a value; no Lucene query, sort, facet or merge path makes this call pair (the only in-tree caller positions the iterator with advance()), ordinary scale, unreleased (main and branch_10_6 only).
Summary
On a default-codec index with docs {0: 'a', 1: no value, 2: 'b'} in a SORTED doc-values field, you call advanceExact(1) on the field's SortedDocValues (it returns false) and then ordinalRangeIntoBitSet(1, 3, ord(a), ord(a), bits, 0) on the same iterator. You expect no bit, because neither doc 1 nor doc 2 has the value 'a', and that is what the per-document advanceExact/ordValue evaluation the javadoc describes returns. Instead the default starts at docID() == 1, calls ordValue() there (which the API calls illegal after a false advanceExact), gets doc 0's ordinal and marks doc 1; with {0: no value, 1: 'a', 2: 'b'} and advanceExact(0), the same call throws RuntimeException(EOFException).
