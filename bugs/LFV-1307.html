The finding in 30 seconds

#

Indexing itself handles a "no limit" buffer; only an assertion-only memory check breaks, because it doubles the buffer in long math.

  1. You want no RAM-based flushing, so you call new IndexWriterConfig().setRAMBufferSizeMB(Double.POSITIVE_INFINITY) (or Double.MAX_VALUE). The setter accepts it: it rejects only sizes of 0 or less.
  2. You add one small document in a JVM with assertions on (test runs usually have them on). The writer accounts 65,720 bytes of RAM for this first document, including the indexing buffers it allocates. You expect it to be indexed, as it is with assertions off.
  3. An internal check, assertMemory, turns the buffer into bytes as a long: Infinity becomes Long.MAX_VALUE, 9,223,372,036,854,775,807. It then doubles that in long math, which wraps around to an upper bound of -2 bytes.
  4. ram <= -2 is false for any document, so addDocument throws AssertionError: ... expected mem: -2 byte. On 10.0.0 and later IndexWriter treats the error as tragic: it rolls back the buffered documents and closes itself. Before 10.0.0 the error escapes, the writer stays open, and close() trips the same check.
  5. Any buffer of 2^42 MB (4 EiB) or more trips it on the first document, and values within about 0.03 MB below that trip at the first commit; 2^42 - 1 MB and Lucene's own "unlimited" idiom, Integer.MAX_VALUE MB, do not. Every release since 4.0.0.

Who is affected

#

Code that runs with assertions on (an application's test suite, Lucene's test framework) and passes a "no limit" sentinel such as Double.MAX_VALUE, Long.MAX_VALUE or +Infinity to setRAMBufferSizeMB: the one-document repro fails deterministically, and on 10.x and main the writer closes. Production (-da), the 16 MB default and the tested values below 2^42 MB are unaffected. Every release since 4.0.0.

Mechanism, terms and numbers446 words

IndexWriterConfig.setRAMBufferSizeMB accepts any positive value, including Double.MAX_VALUE and Double.POSITIVE_INFINITY, which a caller may use as a "no limit" sentinel, and the production flush code handles them. But the assertion-only check DocumentsWriterFlushControl.assertMemory converts the buffer to bytes as a long (saturating at Long.MAX_VALUE) and computes its upper bound as 2 * ramBufferBytes in long arithmetic, which wraps to -2. With assertions on, the first accounted document fails assert ram <= expected. On 10.0.0 and later IndexWriter then rolls back and closes itself as a tragic event; on 4.x to 9.x the error escapes addDocument and close() trips the same check. With assertions off nothing goes wrong. Every release since 4.0.0 fails the check.

Where it goes wrong (main 5adff78bb168)

#
  1. The setter accepts the value. LiveIndexWriterConfig.setRAMBufferSizeMB (LiveIndexWriterConfig.java:191-202) throws only for a non-positive size or when both flush triggers would be off (:188-189). There is no upper bound. On a default config maxBufferedDocs is DISABLE_AUTO_FLUSH (IndexWriterConfig.java:78), so setRAMBufferSizeMB(DISABLE_AUTO_FLUSH) throws: a huge value is how you say "no RAM trigger" without also choosing a document-count trigger.
  2. The document is accounted. doAfterDocument (DocumentsWriterFlushControl.java:215-259) accounts a document once its RAM delta reaches at most 16 KiB (:202-213, :219-223); for the repro's first document the accounted delta (peakDelta) is 65,720 bytes, which includes the indexing buffers that first document allocates. Then it runs assert ... && assertMemory(); (:256).
  3. The bound wraps. In assertMemory (:121-186), :131 computes ramBufferBytes = (long) (maxConfiguredRamBuffer * 1024 * 1024); a double too large for a long converts to Long.MAX_VALUE. :144-147 computes expected = (2 * ramBufferBytes) + ... in long: 2 * Long.MAX_VALUE is -2 (exactly 2^42 MB gives Long.MIN_VALUE). The comment below calls it "an upper bound" (:148-149). The guard at :150 is true, so assert ram <= expected (:160) fails.
  4. What the writer does. On 10.0.0 and later, IndexWriter.updateDocuments (IndexWriter.java:1625-1642) treats the Error as a tragic event: rollback, then close (any Error became tragic with #13277, first released in 10.0.0). The rollback's doOnAbort (DocumentsWriterFlushControl.java:389-398) trips the same assertion again with the RAM now 0; that second error is the one addDocument throws ("actual mem: 0 byte"), and the first is the writer's tragic exception. On 4.x to 9.x updateDocuments catches only VirtualMachineError (or, in 4.x, OutOfMemoryError), so the first trip escapes, the writer stays open, and close() trips the check again in setFlushPending (run on 9.12.3).
  5. Production is fine. stallLimitBytes() (:114-119) doubles in double before the cast, so it saturates at Long.MAX_VALUE; FlushByRamOrCountsPolicy.java:46 casts the double directly. Only the assertion doubles in long.
Exposure and likelihood225 words
  • Who: JVMs with assertions on (the Test tasks of Gradle and Maven Surefire enable them by default; Lucene's own build does for about 75% of seeds) combined with a RAM buffer of 2^42 MB or more. In practice that is a "no limit" sentinel: Double.MAX_VALUE, Long.MAX_VALUE or Double.POSITIVE_INFINITY.
  • Effect: a false AssertionError on the first accounted document (the one-document repro fails deterministically; documents below the 16 KiB granularity are accounted later, and a writer that once ran with the RAM trigger disabled skips the check). On 10.x and main the writer closes itself and rolls back its uncommitted documents; a rollback returns to the last commit, so committed data should be untouched (read from the code, not run). On 4.x to 9.x the writer stays open but close() trips the same check. No wrong results.
  • Not hit: production JVMs (assertions off), the default buffer and the tested values below the threshold (2^42 - 1 MB, 2^42 - 1/8 MB, the Integer.MAX_VALUE MB idiom of Lucene's own tests). A window of about 32 KB just below 2^42 MB also overflows, at the first commit (2^42 - 1/64 MB was run).
  • Reach: a 2021 java-user@ thread shows a user configuring setRAMBufferSizeMB(Double.MAX_VALUE) with setMaxBufferedDocs(Integer.MAX_VALUE) to switch off automatic flushes in a real job (no failure mentioned: evidence of use, not a report).
  • Scale: none: one document.

Why it looks unintended

#
  • The setter documents and enforces no upper bound (LiveIndexWriterConfig.java:188-199), and production code handles the value.
  • The code calls the value "an upper bound" (DocumentsWriterFlushControl.java:148-149); the production limit stallLimitBytes (:114-119) saturates instead of wrapping.
  • Earlier false trips of this same assertion on legal settings were fixed: LUCENE-3190 (#4263), LUCENE-4182 (#5254), LUCENE-4561 (#5627).
The full argument113 words
  • Contract: setRAMBufferSizeMB throws only for non-positive sizes or when both triggers would be off; its "The maximum RAM limit is inherently determined by the JVMs available memory" (LiveIndexWriterConfig.java:167-172) is advice, not a precondition.
  • Tests: Lucene's own tests use setRAMBufferSizeMB(Integer.MAX_VALUE) (about 2 PiB, beyond any heap) as an effectively unlimited buffer (TestIndexWriter.java:3746, :3769; TestIndexWriterExceptions.java:749).
  • History: 3.x capped the buffer at 2048 MB (3.1.0 and 3.6.2 reject +Infinity: "ramBufferSize Infinity is too large; should be comfortably less than 2048"); LUCENE-2573 (#3647) removed that cap on purpose. LUCENE-3190's commit is titled "prevent assert from false fail with very low maxBufferedRam settings"; the 2014 commit 3b13b09f984 fixed another false trip.
The devil's-advocate check199 words

2^42 MB is 4 EiB and can never be allocated. The javadoc ties the maximum to the JVM's memory, and the 4.0.0 CHANGES.txt entry that lifted the 2048 MB cap says "Applications should still use a ramBufferSize significantly lower than the JVMs avaliable heap memory". Each DWPT is still force-flushed at the per-thread hard limit whatever the global setting (IndexWriterConfig.java:373-389). DISABLE_AUTO_FLUSH with a document-count trigger (setMaxBufferedDocs(n)) is a documented way to drop the RAM trigger and passes with assertions on; a huge buffer is only needed to flush purely by hand. The failure needs assertions and is loud. An independent reviewer from another model family (OpenAI GPT-5.6) first leaned "not real" on these points.

Why it fails: the heap sentences are advice that replaced a hard check removed on purpose; the per-thread limit bounds one DWPT, not the global bound the assertion computes; the setter accepts the value and production handles it; DISABLE_AUTO_FLUSH throws on a default config, so "no automatic flush at all" has no other spelling; Lucene's own tests use an equally unattainable Integer.MAX_VALUE MB. The same reviewer settled on "real". What remains is an impact argument, which is why this is Low.

Suggested fix

#

Recommended A. Clamp ramBufferBytes in assertMemory (validated)

Clamp the buffer in the assertion: ramBufferBytes = (long) Math.min(maxConfiguredRamBuffer * 1024 * 1024, Long.MAX_VALUE / 4) at DocumentsWriterFlushControl.java:131. Assertion-only; production is untouched. The test passes, and so do 176 tests of the closest index suites.

-      final long ramBufferBytes = (long) (maxConfiguredRamBuffer * 1024 * 1024);
+      // clamp so that doubling cannot overflow; leaves headroom for the peakDelta terms below
+      final long ramBufferBytes =

A. Clamp ramBufferBytes in assertMemory (validated) (recommended)

#

One statement at DocumentsWriterFlushControl.java:131.

-      final long ramBufferBytes = (long) (maxConfiguredRamBuffer * 1024 * 1024);
+      // clamp so that doubling cannot overflow; leaves headroom for the peakDelta terms below
+      final long ramBufferBytes =
+          (long) Math.min(maxConfiguredRamBuffer * 1024 * 1024, Long.MAX_VALUE / 4);

Trade-offs

Buffers above about 2^41 MB are checked as if they were 2^61 bytes, still far beyond any heap, so nothing real is lost. The clamp fixes the demonstrated overflow and leaves about 2^62 bytes of headroom for the peakDelta terms, but it does not by itself prove every product and sum at :144-147 overflow-free (in practice peakDelta is bounded by the per-thread hard limit and the counts are small). With it, the values just below 2^42 MB that failed at commit also commit.

What the checks validated

Scratch worktree of 5adff78bb168, gradle, seed DEADBEEF: the test passes with assertions on; TestInfiniteRamBuffer, TestFlushByRamOrCountsPolicy, TestDocumentsWriterStallControl, TestIndexWriterConfig, TestIndexWriterExceptions and TestIndexWriter: 176 tests, 0 failures, 4 skipped; checkGoogleJavaFormat passes. Those runs used the diff before its comment was reworded (same code); with the reworded diff the test and checkGoogleJavaFormat pass again. The full lucene/core suite was not run.

B. Saturating arithmetic for the whole bound

#

Compute expected with Math.addExact / Math.multiplyExact and fall back to Long.MAX_VALUE, or sum in double and cast once.

Trade-offs

Exact, but it must cover the whole sum, not only the doubling: the 2011 form doubled in double and still wrapped once a DWPT was pending (executed on 4.0.0 with that form substituted). Not run.

C. Reject huge values in setRAMBufferSizeMB

#

Throw IllegalArgumentException for non-finite values and for 2^42 MB or more.

Trade-offs

Fails fast, but changes public behaviour: code that uses Double.MAX_VALUE or +Infinity as "no limit" and works today with assertions off would start to throw, so it needs a migration note and a documented "no RAM trigger" alternative for default configs. Not run.

Downstream note

#

Downstream, only an application that itself sets such a RAM buffer and runs with assertions on is affected; no query, document or index content can set the value.

How it was found

#

A proof-obligation audit of DocumentsWriterFlushControl.assertMemory: its bound must not overflow for any RAM buffer setRAMBufferSizeMB accepts. The obligation fails for 2^42 MB and up, and an executable test witnessed it on main.

The method in full60 words

Semi-formal method: state the obligation (the bound 2 * ramBufferBytes + ... stays a non-negative long for every value the setter accepts), check it against the arithmetic in assertMemory, and witness the failing case with a JUnit test on main 5adff78bb168. Independent reproductions, an intended-behaviour review, a cross-model review and an adjudication then checked it (see the checks below).
