IOUtils.closeWhileSuppressingExceptions stops closing when a close() rethrows the exception being handled

When Lucene cleans up after a failure, IOUtils.closeWhileSuppressingExceptions(t, a, b) closes a and b and attaches their failures to t. If a.close() throws t itself, as the JVM's shared OutOfMemoryError can, the helper throws IllegalArgumentException: Self-suppression not permitted and never closes b.

The finding in 30 seconds

#

The helper closes each closeable and attaches each close failure to ex with ex.addSuppressed(e). Java does not let a Throwable suppress itself. When a close() throws ex itself, that call throws IllegalArgumentException out of the loop, so the closeables after it are skipped and the caller's own rethrow never runs.

  1. A Lucene operation fails with a Throwable t, say an OutOfMemoryError inside DirectoryReader.open. Its cleanup calls IOUtils.closeWhileSuppressingExceptions(t, first, second) to close what it opened, then rethrows t.
  2. first.close() throws the same object t. Out of heap this is normal: in a 64 MB-heap probe the first 4 OutOfMemoryErrors were distinct objects and every later one was one shared object.
  3. You expect what the javadoc promises: both closeables are closed and the same OutOfMemoryError is rethrown.
  4. Instead the helper calls t.addSuppressed(t) (IOUtils.java:129). Java throws IllegalArgumentException: Self-suppression not permitted, which leaves the loop: second.close() never runs, and the caller gets the IllegalArgumentException, with t only as its cause.
  5. On main the IndexWriter constructor cleans up this way. With two config components that throw one IOException object, new IndexWriter throws the IllegalArgumentException and keeps the write lock: a second new IndexWriter on the same directory fails with LockObtainFailedException.

Who is affected

#

Failure paths that clean up through this helper, with default settings: DirectoryReader.open from 10.4.0, codec readers and writers in 10.5 and 10.6, and 100 call sites on main, including the IndexWriter constructor. It needs one exception object thrown twice, as the JVM does out of heap. The error is loud; the leaked resources are silent. Rare, so priority Low.

Mechanism, terms and numbers445 words

After a failure, Lucene code calls IOUtils.closeWhileSuppressingExceptions(t, closeables...) to close what it had opened and then rethrows t (for example StandardDirectoryReader.java:102-104, and on main the IndexWriter constructor, IndexWriter.java:1206). The helper attaches each close failure e to t with t.addSuppressed(e) (IOUtils.java:129) and never checks that e is a different object. Throwable.addSuppressed rejects its own receiver with IllegalArgumentException("Self-suppression not permitted"), the argument as cause. So when a close() throws the very object being handled, that exception leaves the loop: the closeables after it are never closed, and the caller gets the IllegalArgumentException instead of t. This breaks the method's javadoc, "Even if a Error is thrown all given closeable are closed" (:109-110). The same object is thrown twice when the JVM is out of heap and reuses one OutOfMemoryError, or when an application component rethrows one stored exception. It is in every release with the helper, 10.4.0 to 10.6.0, and main; an identity check before addSuppressed fixes it.

Terms

#
  • IOUtils.closeWhileSuppressingExceptions(ex, closeables...): a cleanup helper (IOUtils is @lucene.internal, IOUtils.java:48) used on failure paths as catch (Throwable t) { IOUtils.closeWhileSuppressingExceptions(t, ...); throw t; }. It closes everything and records each close failure on ex; when ex is an Error, it rethrows that Error itself.
  • Suppressed exceptions: ex.addSuppressed(e) attaches e to ex. The JDK throws IllegalArgumentException("Self-suppression not permitted", e) when e == ex (JDK 25 Throwable.java:1100-1101).

The bug

#
// IOUtils.java:114-137 (condensed)
Error firstError = ex instanceof Error err ? err : null;   // :116  an Error ex is the one to throw
for (Closeable object : objects) {
  try {
    if (object != null) object.close();                   // :121
  } catch (Throwable e) {
    if (firstError == null && e instanceof Error err) {
      firstError = err;
      firstError.addSuppressed(ex);                        // :127
    } else {
      ex.addSuppressed(e);                                 // :129  e == ex: IllegalArgumentException,
    }                                                      //       thrown out of the loop
  }
}
if (firstError != null) throw firstError;                 // :134-135  never reached

The repro, step by step:

stepfirstErrorwhat happens
call with ex = oomoom (:116)
first.close() throws oomoomfirstError is set, so the else branch: oom.addSuppressed(oom) (:129)
Throwable.addSuppressedthrows IllegalArgumentException, cause oom, from inside the catch: it leaves the loop
second.close()never runs
throw firstError, the caller's throw tnever reached: the caller gets the IllegalArgumentException

A non-Error ex (an IOException that close() rethrows) takes the same :129 branch and fails the same way; the method should return normally there. Distinct exception objects behave as documented. The :127 call cannot self-suppress: it runs only when ex is not an Error and e is.

Exposure and likelihood271 words
  • Reach by version. 10.4.0: one in-tree caller, StandardDirectoryReader.open (behind DirectoryReader.open of a directory or commit). 10.5.0 to 10.5.2: five caller files. 10.6.0: six non-sandbox caller files (StandardDirectoryReader, Lucene90DocValuesProducer, Lucene99HnswVectorsWriter, Lucene104ScalarQuantizedVectorsReader and Writer, backward-codecs Lucene102BinaryQuantizedVectorsReader). Main: 72 non-sandbox source files with 100 call sites, including the IndexWriter constructor.
  • Trigger. One exception object thrown both by the failed operation and by a later close(). (a) The JVM's shared OutOfMemoryError: in a JDK 25 probe at -Xmx64m the first 4 heap OutOfMemoryErrors were distinct and every later one was the same object, with no stack trace. (b) An application Directory, IndexOutput, IndexDeletionPolicy or MergeScheduler that rethrows one stored exception: on main, IndexWriter.addDocument + commit() on a FilterDirectory whose postings output throws one IOException object twice surfaced the IllegalArgumentException from Lucene104PostingsWriter.<init>, where 10.6.0 surfaced the IOException.
  • Effect. Loud: an IllegalArgumentException whose cause is the original. Silent: the closeables after the one that threw stay open, such as the remaining segment readers of a failed DirectoryReader.open (file handles), or on main the IndexWriter write lock, so a second IndexWriter on the directory gets LockObtainFailedException: lock instance already obtained in the same process.
  • Caveat (by reasoning, not run). Under real heap exhaustion, allocating the IllegalArgumentException might itself fail, so the shared OutOfMemoryError would escape instead; the remaining closeables are skipped either way. Lucene CI mails have printed this IllegalArgumentException from other sites under heap exhaustion (2020, 2025).
  • Scale and likelihood. No scale: one call, single thread, assertions on or off. Rare: no public report of it was found since the helper shipped in 10.4.0.

Why it looks unintended

#
  • The javadoc: "Even if a Error is thrown all given closeable are closed" (IOUtils.java:109-110). Here the rest are skipped.
  • The closeWhileHandlingException code these paths used before still closed everything when one close() rethrew the handled object; the JDK's FilterOutputStream.close guards this exact case.
  • Plain try-with-resources also replaces the exception here, but it still closes every resource.
The full argument201 words
  • The contract. IOUtils.java:109-110 (the varargs overload, which delegates here, carries only the first sentence, :98). The code deliberately rethrows an Error ex (:116, :135); TestIOUtils.testCloseExposesErrors (TestIOUtils.java:76-110) asserts it is the same instance, but only with close failures that are distinct objects.
  • The replaced code handled the repro's case. Before the conversions (main #14633, 2025-05; StandardDirectoryReader.open in #14913, 2025-07-14; on the 10.x line #15445), these paths used a success flag and closeWhileHandlingException, which collects close failures with useOrSuppress and rethrows the first Error (10.3.2 IOUtils.java:113-135, :449-456). When one close() rethrows the handled object, that code closes everything and rethrows it; the new helper fails on that first rethrow. If two closes throw the same object, the old code also fails, in useOrSuppress (LFV-564's site; run against the 10.3.2 core jar).
  • Stated intent. CHANGES, LUCENE-5654: "Fix various close() methods that could suppress throwables such as OutOfMemoryError, instead returning scary messages that look like index corruption."
  • JDK precedent. FilterOutputStream.close: if (flushException != closeException) closeException.addSuppressed(flushException); (JDK 25 java/io/FilterOutputStream.java:195-196).
  • History. The review of #14633 (17 comments and reviews) never discusses a close() that rethrows ex; no javadoc, test, CHANGES or MIGRATE entry forbids it.
The devil's-advocate check166 words

The strongest case: plain try-with-resources (JLS 14.20.3.1) also calls primary.addSuppressed(closeFailure) without an identity check, so Java itself throws "Self-suppression not permitted" in this situation; IOUtils is @lucene.internal; the trigger is narrow; and the JDK's AutoCloseable.close javadoc advises "if it would cause problems for an exception to be suppressed, the AutoCloseable.close method should not throw it" (JDK 25 java/lang/AutoCloseable.java:82-84).

Why it fails: try-with-resources still closes every resource after that failure, while this helper skips the rest, which its own javadoc rules out. The skipped closes cannot. The AutoCloseable advice is aimed at application components; it cannot apply to the JVM's shared OutOfMemoryError. Being internal does not remove the reach, because the helper sits on default failure paths of public APIs. The executed cross-model review (OpenAI GPT-5.6) rated the intended-behaviour argument weak; a later cross-model fact check rated it moderate (a maintainer could reasonably close the report as won't-fix), though not enough to make it intended. What survives is a severity argument, hence priority Low.

Suggested fix

#

Recommended Skip suppression when close() rethrows an object the helper already holds

Skip addSuppressed when close() throws an object the helper already holds (e == ex || e == firstError), a 3-line change in IOUtils.java. Validated: the repro passes with assertions on and off; with it, TestIOUtils, TestDirectoryReader and TestIndexWriterExceptions pass (87 tests, 0 failures, 3 skipped), and so does :lucene:core:check -x test.

--- a/lucene/core/src/java/org/apache/lucene/util/IOUtils.java
+++ b/lucene/core/src/java/org/apache/lucene/util/IOUtils.java
@@ -121,7 +121,9 @@
           object.close();
         }
       } catch (Throwable e) {
-        if (firstError == null && e instanceof Error err) {
+        if (e == ex || e == firstError) {
+          // the same Throwable was rethrown by close(): nothing to suppress
+        } else if (firstError == null && e instanceof Error err) {
           // don't try and suppress it - this Error should be the thing that is thrown
           firstError = err;
           firstError.addSuppressed(ex);

Skip suppression when close() rethrows an object the helper already holds (validated by the checks) (recommended)

#

In the catch, do nothing when e == ex (for the usual catch/cleanup/rethrow callers no record is needed: the object is already the one the caller will throw) or e == firstError (two closes threw the same Error while ex is not one; stock code then attaches it to ex, which that Error already carries as suppressed, a redundant cyclic record visible through getSuppressed() that the guard deliberately drops; by reading). Everything else is unchanged.

One guarded suppression helper for every IOUtils site

#

A private suppress(Throwable into, Throwable t) that skips t == into, used here, in both deleteFilesSuppressingExceptions overloads and in useOrSuppress (LFV-564's site).

Trade-offs

One consistent rule for LFV-564 and this bug, but a larger diff that touches methods outside this finding; the cycle case (e == firstError) still needs its own check here. Not run.

Keep closing even when suppression fails

#

Catch the exception that addSuppressed throws, hold it, and rethrow it only after every closeable has been closed. A bare try/finally would not do: the exception would still leave the loop.

Trade-offs

Every closeable is closed, but the caller still gets the IllegalArgumentException instead of its own exception; the identity check fixes both halves with less code. Not run.

Downstream note

#

Services that run Lucene close to heap exhaustion may log Self-suppression not permitted instead of the OutOfMemoryError and leak file handles or the write lock inside the process; no query, document or index input selects this path.

How it was found

#

A proof-obligation audit of IOUtils's contract checked each promise of closeWhileSuppressingExceptions (all closeables closed, close failures suppressed in ex, an Error ex rethrown) against the code, and found that no addSuppressed call checks for the same object. A one-test JUnit then witnessed it on main; independent checks reproduced it with their own tests.

The method in full110 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for every closeable, close() is called, whatever earlier closes threw (:109-110). It fails when the catch block itself can throw: ex.addSuppressed(e) (:129) throws for e == ex, a case the JDK specifies.
  • A one-test JUnit witnessed it on main with assertions on and off; a JVM probe showed the shared OutOfMemoryError is real JVM behaviour. An independent reproducer, an executed review by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier wrote their own tests from the claim, including two routes through IndexWriter.

Summary
After a failure, Lucene calls IOUtils.closeWhileSuppressingExceptions(ex, closeables...) to close what it had opened and attach any close failures to ex, for example when opening a DirectoryReader fails. If one close() throws the very object ex (the JVM reuses one OutOfMemoryError object once memory is exhausted), you expect what the method documents: every closeable is closed and, for an Error, that same Error is rethrown. Instead ex.addSuppressed(ex) throws IllegalArgumentException 'Self-suppression not permitted', which escapes the loop, so the remaining closeables are never closed and the caller sees the IllegalArgumentException instead of the original failure (kept only as its cause).
