Flexible query parser: QueryNode#toQueryString prints field names without escaping, so 'my\ field:x' comes back as 'my field:x', a query on other fields

The flexible parser reads my\ field:x as a query on the field my field, but QueryNode#toQueryString prints it as my field:x, which parses as df:my OR field:x (and a\:b:x as a:b:x, which does not parse). Every release since 2.9.0 has it; parsing to a Query is fine.

The finding in 30 seconds

#

Escaped field names and toQueryString

#
  1. In the standard syntax, field:text searches one field. A backslash escapes a special character, also in a field name: my\ field:x searches the field my field, a\:b:x the field a:b.
  2. The flexible parser first builds a tree of query nodes (getSyntaxParser().parse), then a Query. A node can also print itself back as query text with toQueryString, documented as a string "understood by the query parser".
  3. When it prints, a node passes its term text through an EscapeQuerySyntax, which puts the backslashes back.

The finding, step by step

#
  1. Parse my\ field:x with new StandardQueryParser().getSyntaxParser(). The escaped space is allowed on purpose: you get a node on the field my field with the text x.
  2. Print it with toQueryString(new EscapeQuerySyntaxImpl()) and parse the text again. You expect my\ field:x, which gives back the same query, as the javadoc promises.
  3. Instead it prints my field:x, which parses as two clauses, df:my OR field:x, with no error. On an index with the documents {my field: x} and {field: x}, the original finds the first, the printed text the second.
  4. Why: every toQueryString that prints a field (term, phrase, fuzzy, range, point, wildcard, regexp, interval, and two nodes no parser builds) appends the name raw; the field never goes through the escaper.
  5. Scale: of 9,119 one- and two-character printable-ASCII field names (all but *), put in hand-built term nodes, 3,384 fail the round trip; a\:b:x prints a:b:x, a syntax error.

Who is affected

#

Applications that print flexible-parser node trees back to text with toQueryString and parse, store or forward that text, for fields whose names contain a query-syntax character (space, colon, quote, bracket) or are a token by themselves (2024, OR, fn). Default settings; no index is needed to show it. StandardQueryParser.parse is unaffected, and no Lucene code re-parses the output.

Mechanism, terms and numbers649 words

The standard flexible query parser accepts escaped field names on purpose: my\ field:x is a term query on the field my field and a\:b:x one on a:b. QueryNode#toQueryString is documented to return "a query string understood by the query parser", and the node package says a tree "can also generate a query string that can be parsed back by the original text parser". But every toQueryString that prints a field appends the name raw; the field never goes through the EscapeQuerySyntax. So the node of my\ field:x prints my field:x, which parses as df:my OR field:x, and the node of a\:b:x prints a:b:x, a syntax error; phrase, fuzzy, hand-built nodes and, on main, range nodes do the same. Of 9,119 printable-ASCII field names of length 1 or 2 (all but *), 3,384 fail. It has been there since the flexible parser's first release, 2.9.0; StandardQueryParser.parse builds the right Query, and only code that prints node trees back to text is affected. A validated fix escapes the field through one helper at the eight field-printing sites of the nodes the standard parser builds; two more raw prints, in nodes no parser builds and whose output does not parse back anyway, are left as they are.

What the code does

#

FieldQueryNode.toQueryString (FieldQueryNode.java:65-71) returns this.field + ":" + getTermEscaped(escaper) (:69); getTermEscaped (:56-58) runs only the text through escaper.escape(text, Locale.getDefault(), Type.NORMAL). The same raw field print is at the seven other sites of the nodes the standard parser builds: QuotedFieldQueryNode.java:39, FuzzyQueryNode.java:55, AbstractRangeQueryNode.java:166 (sb.append(getField()).append(":")), PointQueryNode.java:89, WildcardQueryNode.java:47, RegexpQueryNode.java:93 and IntervalQueryNode.java:49. Where a node escapes its text at all, only the term text meets the escaper: WildcardQueryNode, RegexpQueryNode and IntervalQueryNode print their text raw. Two more nodes print the field raw, AnyQueryNode.java:121 and ProximityQueryNode.java:186, but no parser code builds them, and their ANY / WITHIN output does not parse back even for a plain field (f:(( a b ) WITHIN 3) parses to (f:a f:b) f:WITHIN f:3, executed).

The parser keeps the escapes: FieldName() "strips escape characters from field names" (StandardSyntaxParser.jj:336-344) and returns an UnescapedCharSequence that records which characters were escaped. They are lost only when printing. EscapeQuerySyntax.Type has only STRING and NORMAL, no field mode.

A field name must lex as one TERM token (StandardSyntaxParser.jj:328). A character outside _TERM_START_CHAR (:131-133) cannot start it, and a space, :, ", (, [, @ and the others also outside _TERM_CHAR (:134) end it (+ and - break a name only in first position), and a whole name that is a number (NUMBER, :160), the interval prefix fn: (:147) or AND/OR/NOT (:144-146) lexes as something else.

Exposure and likelihood143 words
  • Who. Trees from the public getSyntaxParser() (QueryParserHelper.java:172), processed trees (which can also hold post-analysis nodes such as TokenizedPhraseQueryNode, marked not re-parseable), or hand-built nodes; the node package says the nodes "are designed to be used by UI or other text parsers" (core/nodes/package-info.java:28).
  • Trigger. A field name with a syntax character, or one that is a token by itself. Namespaced names like dc:title occur in practice (#1349 / LUCENE-271 reported one in 2004, for the classic API).
  • Effect. The printed text fails to parse or, silently, queries other fields. No index damage; the Query from parse is right.
  • In-tree. The output only feeds exception messages (QueryTreeBuilder.java:161, BooleanQueryNodeBuilder.java:72, MatchAllDocsQueryNodeBuilder.java:42, MatchNoDocsQueryNodeBuilder.java:42, AllowLeadingWildcardProcessor.java:74) and IntervalQueryNode.toString; nothing in Lucene parses it again.
  • Likelihood. Rare: the documented searches found no report in the 17 years since 2.9.0.

Why it looks unintended

#
  • The javadoc promises "a query string understood by the query parser", one that "can be parsed back by the original text parser".
  • Escaped field names are deliberate, tested syntax: TestQPHelper asserts a\:b:c is a query on the field a:b.
  • Lucene fixed the same round trip for range nodes as a bug in 11.0.0 (#7865, PR #14697).
The full argument193 words
  • Contract. QueryNode.java:26: "convert to a query string understood by the query parser". core/nodes/package-info.java:42-43: "A query node tree can also generate a query string that can be parsed back by the original text parser, at this point only the standard lucene syntax is supported." EscapeQuerySyntax.java:22-23: the escaper exists "to allow the QueryNode to escape the queries, when the toQueryString method is called". The colon case does not even parse.
  • Deliberate input. StandardSyntaxParser.jj:337; TestQPHelper.java:817-820 asserts a\-b:c, a\+b:c, a\:b:c and a\\b:c give the fields a-b, a+b, a:b and a\b; LUCENE-161 (#1239) added escaped field names in 2004.
  • Precedent. CHANGES.txt:296-298 (11.0.0 Bug Fixes): "GITHUB#7865 AbstractRangeQueryNode#toQueryString(EscapeQuerySyntax) now returns a string which can be parsed back into the original node." Field escaping never came up in #14697 (its tests use an ordinary field name).
  • No intent found. In the material reviewed (the flexible parser's source, tests and javadoc, CHANGES and MIGRATE, the six commits that added the eight sites, the review threads in the follow-up) nothing says fields are printed raw on purpose. The three core lines are unchanged since 2009; the later sites (2010-2025) copied the pattern without comment.
The devil's-advocate check279 words

The strongest case for "intended": a 2017 java-user reply on range round trips said "There has never been a guarantee that going back and forth between a parsed query and its string representation is idempotent"; open #8667 calls toQueryString a design error; #1349 / LUCENE-271, the same symptom for the classic Query.toString(field) (dc\:title:hugo printed as dc:title:hugo), was closed "Not A Problem" in 2011; inside Lucene the output feeds only error messages and one toString; some nodes say their output is not re-parseable (TokenizedPhraseQueryNode.java:47; MultiPhraseQueryNode prints [MTP[...]]); and the escaper never had a field mode.

Why it fails: Query.toString is documented as user-readable, while QueryNode#toQueryString and its package promise text the parser understands and can parse back. In the same 2017 thread Michael McCandless answered "Why don't we fix this in Lucene?", and #14697 then fixed the range round trip as a bug, its approver noting "we're changing behaviour that is public and has been around a long time, but it's also a bug fix". #8667 is about non-standard syntaxes; this fails with the standard one. The not-re-parseable nodes are post-analysis nodes and are marked as such; the syntax parser's field nodes carry no such mark. Being used only in messages limits impact, not intent. For hand-built nodes the promise can hold only for names the standard syntax can write at all (an empty name cannot be written); the claim is about names it can write, as the parser's own escaped-field tests show. A read-only cross-model refute review returned only a procedural "not real" (it could not run Java), agreed on the root cause and rated this argument weak; the intended-lens review said real.

Suggested fix

#

Recommended Escape the field through one helper at the eight standard-parser sites (validated)

A helper in QueryNodeImpl runs the field through the term's escaper (plus a backslash for names that lex as a number or fn:); the eight field-printing sites of the nodes the parser builds call it (+43/-8 in 9 files). The repro and the queryparser module pass; exhaustive field-name mismatches drop from 3,388 to 101 (a sibling escaper gap, harness artifacts).

protected CharSequence getFieldEscaped(CharSequence fld, EscapeQuerySyntax escaper) {
  CharSequence escaped = escaper.escape(fld, Locale.ROOT, EscapeQuerySyntax.Type.NORMAL);
  // a field name must lex as a term; a bare number or "fn" would lex as a number or as the
  // interval function prefix "fn:", so escape its first character
  if (escaped != null
      && ("fn".contentEquals(escaped) || NUMBER_FIELD.matcher(escaped).matches())) {
    return "\\" + escaped;
  }
  return escaped;
}
All options and trade-offs4 options · 779 words

One fix was written and validated in a scratch worktree of 645d4fe14a20; the alternatives are described, and one partial variant was run by a verifier. The output of toQueryString changes for such names, so maintainers may want it in 11.0 only, as for #14697.

Escape the field through one helper at the eight standard-parser sites (validated) (recommended)

#

+43/-8 in 9 files (tidy-formatted). QueryNodeImpl gets protected getFieldEscaped(CharSequence, EscapeQuerySyntax); FieldQueryNode, QuotedFieldQueryNode, FuzzyQueryNode, AbstractRangeQueryNode, PointQueryNode, WildcardQueryNode, RegexpQueryNode and IntervalQueryNode call it instead of printing the raw field. AnyQueryNode.java:121 and ProximityQueryNode.java:186 stay as they are: no parser builds those nodes, and their ANY / WITHIN text does not parse back even for a plain field, so escaping their field alone would not make them round-trip (with the fix their output is unchanged, executed); a maintainer may still want them to call the helper for consistency. NUMBER_FIELD is Pattern.compile("[0-9]+(\\.[0-9]+)?"), the grammar's NUMBER token.

protected CharSequence getFieldEscaped(CharSequence fld, EscapeQuerySyntax escaper) {
  CharSequence escaped = escaper.escape(fld, Locale.ROOT, EscapeQuerySyntax.Type.NORMAL);
  // a field name must lex as a term; a bare number or "fn" would lex as a number or as the
  // interval function prefix "fn:", so escape its first character
  if (escaped != null
      && ("fn".contentEquals(escaped) || NUMBER_FIELD.matcher(escaped).matches())) {
    return "\\" + escaped;
  }
  return escaped;
}

Trade-offs

  • Output change: names with syntax characters print with backslashes (my\ field:x); names equal (ignoring case) to AND, OR, NOT, TO, WITHIN, SENTENCE, PARAGRAPH or INORDER, number-shaped names (2024, 1.5) and fn get a leading one (\to:x, \2024:x); plain names print as before. Worth a CHANGES entry.
  • Inherits the escaper's own gaps. Sibling LFV-398: @ after the first character and the names && / || still fail until EscapeQuerySyntaxImpl is fixed; in the exhaustive printable-ASCII check those are the only real field-name failures left. Beyond ASCII, escapeIgnoringCase matches on a lower-cased copy and inserts the backslashes at its indexes, so a character whose lower case is longer shifts them: with the fix the field İ:a (U+0130) prints İ:\a:x, which does not parse, and İ a prints İ \a:x, which parses to df:İ a:x (executed; stock fails too). Open outside PR #16853 fixes that escaper bug.
  • Reusing the term escaper is safe for fields: \to parses back to the field to, and * / ? are escaped only when they were escaped in the input.
  • Puts two standard-syntax rules (number, fn:) in the core node base class, which already prints standard syntax (:, ~, [ TO ]).

A field mode in the escaper (not run)

#

Add EscapeQuerySyntax.Type.FIELD and let EscapeQuerySyntaxImpl own the field rules (the term rules plus number, fn, inner @, &&, ||); the nodes call escape(field, locale, Type.FIELD).

Trade-offs

Keeps the syntax rules in the syntax's escaper, but adds a constant to a public enum that custom EscapeQuerySyntax implementations must handle.

Reprint the parser's escapes (not run)

#

When the field is an UnescapedCharSequence (as FieldName() returns), print toStringEscaped().

Trade-offs

Reproduces what the user typed, but does nothing for hand-built nodes or String field names (new FieldQueryNode("my field", ...)), nor for parsed interval queries, whose node gets field.toString() and loses the escape flags (StandardSyntaxParser.jj:379); it is incomplete on its own.

Escape in FieldQueryNode only (not recommended; run by a verifier)

#

Change only FieldQueryNode.toQueryString.

Trade-offs

Fixes the term, colon and hand-built-node cases; phrase, fuzzy and range still fail (3 of 11 tests), because each node prints the field itself.

Downstream note

#

An application that checks or rewrites a node tree and then re-parses or forwards the printed text runs a query on other fields than the tree it checked; an allowlist of field names catches it.

How it was found

#

A bounded-exhaustive round-trip check on the stock jar built a term node for every printable-ASCII field name of length 1 or 2 (9,119, all but *), printed it with toQueryString and parsed the text again; about 3,400 names failed. A public-API JUnit then reproduced it from parsed input, and independent verifiers confirmed it with their own tests.

#

LFV-356, snapshot of 2026-11-05

Registry title
Flexible query parser: QueryNode#toQueryString prints field names without escaping, so nodes for escaped field names such as 'my field' or 'a:b' print strings that parse to a different query or do not parse
Area
queryparser / flexible parser node serialization (QueryNode#toQueryString of FieldQueryNode, QuotedFieldQueryNode, FuzzyQueryNode, AbstractRangeQueryNode and the other field-printing nodes)
Priority
Low, rank 766: The flexible parser's toQueryString round trip breaks only for escaped field names and only in applications that re-parse node text, which no in-tree caller does, so it joins the niche flexible-parser rows.
Impact class
minor
Impact note
A round-trip (contract) defect in a utility method, with no effect on the Query that StandardQueryParser.parse builds: applications that turn flexible-parser node trees back into text with toQueryString (trees from StandardQueryParser.getSyntaxParser(), processed trees, or hand-built nodes) and parse or forward that text get a string that does not parse, or that silently queries other fields, whenever a field name contains a query-syntax character (space, colon, quote, bracket, ...) or is a token by itself ('2024', 'OR', 'fn'); inside Lucene the output only feeds exception messages; default parser configuration, any scale, every release since 2.9.0 (the range variant on unreleased main only).
Summary
The standard flexible-parser grammar accepts escaped field names on purpose ('my\ field:x' is a query on the field 'my field', 'a\:b:x' on 'a:b'), and QueryNode#toQueryString is documented to return 'a query string understood by the query parser' that 'can be parsed back by the original text parser'. Every toQueryString that prints a field appends the name raw (only the term goes through the escaper), so the node of 'my\ field:x' prints 'my field:x', which parses as df:my OR field:x, and the node of 'a\:b:x' prints 'a:b:x', which is a syntax error. The same happens for phrase and fuzzy nodes, for range nodes on main (after the #7865 range fix), and for hand-built nodes such as new FieldQueryNode("my field", "x", 0, 0).
