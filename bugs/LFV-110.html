An IOException late in a doc-values update write leaves IndexWriter open: it then loses the update or deletes files it still references

One IOException while IndexWriter re-opens its cached reader after writing a doc-values update leaves the writer open, with the update forgotten and its new files unregistered. If you keep using it, 10.x silently commits the old value (doc 0 = 0, not 100) and main deletes files it still references.

The finding in 30 seconds

#

Doc-values updates are written lazily, and the write has three steps after the files are on disk. An IOException in the last step leaves the writer open but out of step with itself.

Background in four steps

#
  1. A doc-values update (updateNumericDocValue, updateBinaryDocValue, and every soft delete) changes a column value in place. IndexWriter buffers it and writes it at the next refresh, flush or commit as new per-segment files of a new generation, here _0_1.fnm and _0_1_Lucene90_0.dv*.
  2. IndexWriter keeps a cached ("pooled") reader per segment and re-opens it after each such write so that it sees the new values.
  3. IndexFileDeleter counts the references to every file of the writer's current SegmentInfos and deletes a file whose count drops to 0. New files are registered by a checkpoint.
  4. On main, doc-values overlays (on by default) write a later update as a small delta on top of the previous generation; 10.x rewrites the whole column from the pooled reader.

The finding, step by step

#
  1. Default config. Index 4 documents with a numeric doc-values field n = 0, 1, 2, 3, commit, and open an NRT reader: the writer now caches ("pools") a reader for the segment.
  2. Set doc 0 to n = 100 and refresh. The writer writes the update files, forgets the in-memory update, records the files in the segment's metadata, then re-opens its cached reader. That re-open hits one IOException (say, too many open files), so the refresh throws, but isOpen() stays true.
  3. Keep going: set doc 1 to n = 200, refresh, commit, close and reopen the index. You expect n = 100 200 2 3.
  4. On 10.6.0, 10.5.2 and 9.12.3 nothing fails and the commit holds 0 200 2 3: the next write rebuilt the column from the stale cached reader, so doc 0's update is gone.
  5. On main the new files were never registered with the file deleter, so applying the next update deletes them and the refresh throws FileNotFoundException: _0_1_Lucene90_0.dvm. In a variant with two segments, forceMerge(1) in place of the second update makes main commit doc 0 = 0 silently too.

Who is affected

#

Applications on the default config that use doc-values updates or soft deletes and keep using an IndexWriter after an IOException that left it open (disk full, too many open files). Releases since 7.0.0 lose the update silently; main fails until rollback(), or loses it silently after a merge. Rare: it needs a fault at one of two narrow points.

Mechanism, terms and numbers690 words

When IndexWriter writes pending doc-values updates (on an NRT refresh, a flush or a commit), ReadersAndUpdates.writeFieldUpdates writes the new update files, forgets the in-memory updates, records the new files in the segment's SegmentCommitInfo, and only then re-opens the writer's pooled reader of that segment. Only the write itself has a cleanup handler (the re-open helper only releases its own new reader and rethrows). If the re-open throws a non-tragic IOException, the writer stays open with a stale pooled reader and with new files that IndexFileDeleter does not know about. An application that keeps using the writer then gets, on 10.x and earlier, a later successful commit with the acknowledged update reverted (soft deletes: a deleted document visible again), and on main (overlays on by default) a writer that deletes files its own SegmentInfos still lists, so refreshes and commits fail, or, after a merge, the same silent revert. A second trigger, a failure in another segment's write of the same batch, leaves files unregistered too. It is a regression from LUCENE-7868 (7.0.0) and LUCENE-8232 (7.4.0); 5.5.5, 6.6.0 and 6.6.6 pass. A two-part fix is validated.

The write, step by step (ReadersAndUpdates.writeFieldUpdates, main 5adff78bb168)

#
  1. Write the update files inside a try; its catch (ReadersAndUpdates.java:950-961) advances the generations "so that a 2nd attempt to write will write to a new file" and deletes partial files. This is the only cleanup handler.
  2. Prune the now-written updates from memory (:963-987).
  3. Publish the new files in the segment's SegmentCommitInfo (setFieldInfosFiles :992, setDocValuesUpdatesFiles :1017, setDocValuesOverlay :1023).
  4. Re-open the pooled reader (swapNewReaderWithLatestLiveDocs, :1028-1030; createNewReaderWithLatestLiveDocs, :1067-1086), with no handler at the call site (the helper's own catch, :1078-1083, only releases the new reader it created and rethrows).

What a failure in step 4 leaves behind

#
  • (a) A stale pooled reader. It still has n = 0 for doc 0, while the update is gone from memory (step 2).
  • (b) Unregistered files. The callers checkpoint only after a normal return: writeReaderPool (IndexWriter.java:4119-4124), merge init (:5309-5311) and writeSomeDocValuesUpdates (:854-860). ReaderPool.writeAllDocValuesUpdates loops over all pooled segments with no catch (ReaderPool.java:244-258). The published files stay at reference count 0.
  • Not tragic. getReader makes only an Error tragic (IndexWriter.java:711-714): isOpen() stays true, getTragicException() stays null.

What happens next

#
  • Every release (overlays absent, or off by default in 10.6.0), and main with setMaxDocValuesOverlays(0). The next write of the field rewrites the column from the stale reader: generation 2 holds 0 200 2 3 and replaces generation 1. Nothing is missing, so commit, close and CheckIndex succeed.
  • Main, default config (overlays on, IndexWriterConfig.java:115, "Enabled by default" :342). The next incRef/decRef pair on the segment's files deletes the unregistered ones: applying the next update packet (deleter.incRef(delFiles) with delFiles = info.files(), IndexWriter.java:6553-6555, :6584; deleter.decRef in finishApply, :6717). A trace of the same fault shows now delete 5 files: [_0_1_Lucene90_0.dvm, _0_1_Lucene90_0.dvp, _0_1_Lucene90_0.dvs, _0_1_Lucene90_0.dvd, _0_1.fnm]. The next write is a delta on top of generation 1, so its re-open fails. If a merge reads the segment first, it reads the stale pooled reader and the merged segment carries the old value.
  • Second trigger, defect (b) alone. With two pooled segments that both have pending updates, if the first is written and published and the second's write throws in the same writeAllDocValuesUpdates loop, the first segment's new files are never registered. After a follow-up update, commit() on FSDirectory throws NoSuchFileException at fsync; on ByteBuffersDirectory (no-op sync) the commit succeeds but cannot be opened. The NRT reader is correct in this path. The files are deleted only at a later incRef/decRef pair on them (an applied update or delete packet, or the close of an NRT reader) before the next successful checkpoint: a plain NRT open or commit right after the failure passes. rollback() right after the failure recovers; if the application keeps going until commit() fails on FSDirectory, a later rollback() itself throws NoSuchFileException, though it still closes the writer and keeps the previous commit.
Exposure and likelihood318 words
  • Who is hit. Users of updateNumericDocValue, updateBinaryDocValue, updateDocValues and soft deletes (which are doc-values updates of the soft-deletes field), with NRT refreshes, flushes or commits, who keep the writer after an IOException that left it open. Default IndexWriterConfig, codec and directory, FSDirectory included.
  • 10.x and earlier: silent. A later successful commit persists the update reverted; CheckIndex is clean for a plain numeric field. With soft deletes, the soft-deleted document (or the replaced old version after softUpdateDocument, next to the new one) is live again once the index is reopened from that commit (6 of 6 scenarios on 10.5.2 and 9.12.3). CheckIndex then reports a soft-delete count mismatch, but readers do not run it. With assertions enabled, opening that commit trips an AssertionError (a soft-delete count check) instead of showing the document.
  • Main: usually loud, sometimes silent. With overlays on, later refreshes, commits and close() fail with a missing-file exception until rollback(). If a merge reads the segment first, the merge uses the stale pooled reader: two segments, the same fault, then forceMerge(1), commit() and close() all succeed and the index holds 0 1 2 3 instead of 100 1 2 3 (main 5adff78bb168, assertions on and off). An earlier single-fault sweep found the same silent revert when the fault hits the re-open inside forceMerge's own flush of pending updates.
  • Scale. None: 4 documents, one segment.
  • Likelihood: rare. It needs an IOException at one of two narrow points, and an application that continues instead of rolling back. rollback() right after the failed call recovers cleanly. Overlays raise open-file counts (#16644), which makes file-descriptor exhaustion a realistic trigger on main. An IOException at exactly this re-open does occur in practice: #12059 (9.3.0, an index on a network file share) shows one in createNewReaderWithLatestLiveDocs under writeFieldUpdates and getReader; it was closed as an environment problem and says nothing about what happened next.

Why it looks unintended

#
  • The writer closes itself after a checkpoint disaster in case reference counts were corrupted (IndexWriter.java:162-165); a failure just before the checkpoint leaves them wrong, yet it stays open.
  • commit() includes every earlier operation (IndexWriter.java:4202-4204), yet a later commit drops the update.
  • LUCENE-5263 fixed transient IOExceptions "silently losing deletions"; the commit that introduced this deleted the test guarding doc-values updates.
The full argument286 words
  • Reference counts. Class javadoc: "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself. This is a defensive measure in case any internal state (buffered documents, deletions, reference counts) were corrupted" (IndexWriter.java:162-165). That rule covers an Error or a failure during a checkpoint; here the failure comes just before the skipped checkpoint and leaves the reference counts wrong in the same way, so it is an analogy, not a contract. IndexFileDeleter tracks "an in-memory SegmentInfos that a writer is actively updating" (IndexFileDeleter.java:40-45).
  • Acknowledged operations. commit() returns "the sequence number such that all indexing operations prior to this sequence will be included in the commit point" (IndexWriter.java:4202-4204).
  • Continuing is designed in. The writeFieldUpdates catch advances generations "so that a 2nd attempt to write will write to a new file" (ReadersAndUpdates.java:951-952). The addDocument javadoc: "if an Exception is hit (for example disk full) then the index will be consistent" (IndexWriter.java:1465); TestIndexWriterExceptions2.testBasics keeps using the writer after a fake IOException from an NRT open or a commit (TestIndexWriterExceptions2.java:211-244).
  • Precedent. LUCENE-5263 (#6327, 4.5.1): "Transient IOExceptions, e.g. due to disk full or file descriptor exhaustion, hit at unlucky times inside IndexWriter could lead to silently losing deletions" (lucene/CHANGES.txt:13277-13279). LUCENE-5189 extended its test to doc-values updates and LUCENE-5248 moved it to TestIndexWriterExceptions.testNoLostDeletesOrUpdates ("... so we successfully close IW or open an NRT reader, we don't lose any deletes or updates"). LUCENE-7868 (58105a203a1) deleted that test; #8919 gives no reason.
  • History. 6.x published, checkpointed, then re-opened, and kept the updates in the frozen packets, so the same fault lost nothing (5.5.5, 6.6.0 and 6.6.6 pass). Neither introducing issue discusses exception handling.
The devil's-advocate check240 words

The strongest case for "intended": in open #9738 (LUCENE-8692) a maintainer (s1monw) writes, in two comments, that exceptions from getReader() and other methods "might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback()", and "if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss". Together with a clean rollback() right after the failure, this makes rollback a plausible intended recovery.

Why it does not settle it: these are one maintainer's comments in an unresolved issue that lean towards making such failures tragic, not towards accepting silent loss; no javadoc, CHANGES or MIGRATE entry tells users to roll back after a non-tragic IOException (the rollback() and prepareCommit() javadocs, IndexWriter.java:2566-2574, :3720-3725, do not); LUCENE-5263 and the deleted test treat the same scenario as a bug; released versions commit the reverted value without any error; and a writer that deletes files its own SegmentInfos references has exactly the corrupted reference counts the class javadoc's defensive rule is about. If maintainers prefer that reading, option B (make these failures tragic) is a credible fix: it makes the rollback protocol explicit and still removes the silent part. The verifiers, including an executed review by another model family (OpenAI GPT-5.6), rated the counter weak; a later fact check by the same family rated it moderate, for the rollback reason above.

Suggested fix

#

Recommended A. Register the published files before rethrowing, and drop the stale pooled reader (validated)

Make the write exception-safe after publication: when the pooled reader's re-open fails, drop the stale reader; in writeReaderPool, merge init and writeSomeDocValuesUpdates, checkpoint the already-published files before rethrowing (46 lines added, 15 removed). Both halves are needed. With it the repro passes, and so does the org.apache.lucene.index test package (1,398 tests, 0 failures).

// ReadersAndUpdates.writeFieldUpdates: if the re-open fails, drop the stale pooled reader
try {
  swapNewReaderWithLatestLiveDocs();
} catch (Throwable t) {
  final SegmentReader stale = reader;
  reader = null; // the next getReader() re-opens from the published SegmentCommitInfo
  IOUtils.closeWhileSuppressingExceptions(t, stale::decRef);
  throw t;
}
// IndexWriter.writeReaderPool, merge init, writeSomeDocValuesUpdates: register published files
} catch (Throwable t) {
  IOUtils.closeWhileSuppressingExceptions(t, this::checkpointNoSIS);
  throw t;
}
All options and trade-offs2 options · 445 words

Two options. A was built and validated on main 5adff78bb168; B was not run.

A. Register the published files before rethrowing, and drop the stale pooled reader (validated) (recommended)

#

Two files, IndexWriter.java and ReadersAndUpdates.java. The checkpoint half restores what LUCENE-8232 removed (a checkpoint of the already-published files); the reader half undoes the state LUCENE-7868 created (a pooled reader that no longer matches the pruned updates). A segment whose write failed inside the existing try deletes its partial files and has published nothing (ReadersAndUpdates.java:950-961), so the extra checkpoint references only files that exist.

// ReadersAndUpdates.writeFieldUpdates: if the re-open fails, drop the stale pooled reader
try {
  swapNewReaderWithLatestLiveDocs();
} catch (Throwable t) {
  final SegmentReader stale = reader;
  reader = null; // the next getReader() re-opens from the published SegmentCommitInfo
  IOUtils.closeWhileSuppressingExceptions(t, stale::decRef);
  throw t;
}
// IndexWriter.writeReaderPool, merge init, writeSomeDocValuesUpdates: register published files
} catch (Throwable t) {
  IOUtils.closeWhileSuppressingExceptions(t, this::checkpointNoSIS);
  throw t;
}

Trade-offs

  • Dropping the pooled reader costs one segment-reader open at the next refresh.
  • Not covered (found by reading, not reproduced): with reader pooling disabled, ReaderPool.release calls writeFieldUpdates (ReaderPool.java:217-220) and IndexWriter.release checkpoints only on a normal return (IndexWriter.java:6468-6473).
  • No stress or performance run was made.
  • Open PR #16923 (a different defect: NRT version bumps) edits the normal-return checkpoint in writeSomeDocValuesUpdates and the writeFieldUpdates call in ReaderPool.commit; whichever lands second needs a rebase.

What the checks validated

  • Gradle in a clean scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes on and off.
  • The whole org.apache.lucene.index test package with the repro in it: 215 test classes, 1,398 tests, 0 failures, 56 skipped, including TestIndexWriterExceptions (40), TestIndexWriterExceptions2, TestIndexWriterOnDiskFull, TestReaderPool, TestNumericDocValuesUpdates, TestBinaryDocValuesUpdates, TestMixedDocValuesUpdates, TestIncrementalDocValuesUpdates, TestIndexFileDeleter and TestIndexWriter (119).
  • :lucene:core:check -x test (format, ecj lint, forbidden APIs, licenses) passes.
  • Both halves are needed: with only the reader drop the repro still fails (NoSuchFileException: _0_1_Lucene90_0.dvm); with only the checkpoint the repro passes on main but the forceMerge(1) probe still commits 0 1 2 3.
  • Earlier, on main ea57360912ed, the same change made 21 independent tests, a 12-scenario soft-delete probe and 800 fault-injection iterations pass.

B. Treat a failure after publication as tragic (not run)

#

Call onTragicEvent when the re-open, or a later segment's write in the same batch, fails after files were published, so the writer closes and getTragicException() is set.

Trade-offs

Small and removes the silent loss; matches the direction of #9738. But it turns a transient IOException into a closed writer that the application must reopen, which LUCENE-5263 and the retry comment in writeFieldUpdates avoided.

Downstream note

#

Search servers built on Lucene that delete with soft deletes and keep the writer after a failed refresh or commit can, in released versions, see a deleted document come back after a restart; calling rollback() after such an IOException avoids it.

How it was found

#

A fault-injection model-based test ran random doc-values update sequences with IOExceptions injected at random (at 1-3% of the file operations) inside the update write during NRT opens, and compared the values with a reference model. In a few of 800 iterations a commit referenced a deleted update file; a trace of a deterministic fault gave the mechanism.

The method in full170 words

Method: non-formal (randomized fault-injection model-based testing), on main ea57360912ed.

  • The test generated random sequences of doc-values updates, NRT opens and commits, injected IOExceptions at random (at 1-3% of the file operations) only inside the doc-values update write (ReadersAndUpdates) during NRT opens, checked every value against a last-writer-wins reference, and ran CheckIndex at close. In a few of 800 iterations per run a commit failed with NoSuchFileException for a doc-values update file that a SegmentCommitInfo still listed.
  • An IndexFileDeleter trace of one deterministic fault in swapNewReaderWithLatestLiveDocs gave the mechanism; a one-test JUnit reproduced it, and its full-rewrite variant (setMaxDocValuesOverlays(0)) showed the silent lost update.
  • A TLA+ model of the overlay bookkeeping already stated the violated invariant (every file a SegmentCommitInfo lists exists) but had no exception actions, so TLC did not find it. A later TLA+ fault extension reproduced the file deletion in a 4-state trace (update, failed re-open, garbage collection) and found no violation with the fix semantics (4.8 to 7.1 million distinct states).

LFV-110, snapshot of 2026-11-08

Registry title
An IOException late in a doc-values update write leaves IndexWriter open but inconsistent: published update files are never checkpointed and get deleted while still referenced, and a failed pooled-reader re-open silently drops the update
Area
index / IndexWriter doc-values update write path (ReadersAndUpdates.writeFieldUpdates, the checkpoint after writeReaderPool, IndexFileDeleter reference counts)
Priority
Medium, rank 24: A non-tragic IOException (disk full, too many open files) at two narrow points of a doc-values or soft-delete write leaves the writer open and silently reverts acknowledged updates at the next commit in every release since 7.0, a real durability bug in the default config, but it needs a fault at the wrong moment plus an app that keeps the writer, which a maintainer has said risks inconsistency.
Impact class
data corruption
Impact note
Hits applications on the default IndexWriterConfig, codec and directory (FSDirectory included) that keep using an IndexWriter after a non-tragic IOException, such as file-descriptor exhaustion or a full disk, at one of two narrow points of a doc-values update write during an NRT open, flush or commit (the re-open of the pooled segment reader right after the update files are published, or another segment's update write in the same batch): in every release from 7.0.0 to 10.5.2, in 10.6.0 (released 2026-10-29) and on main with maxDocValuesOverlays=0 a later successful commit persists the acknowledged update reverted (with soft deletes, the deleted document is live again after reopen), while on main's default overlay config and on the partial-batch path (every release since 7.4.0) the writer deletes files its own SegmentInfos still lists and later NRT opens or commits fail with NoSuchFileException until rollback() (except when the affected segment is merged first, for example by forceMerge(1): then main's default config also commits the reverted update silently); tiny scale (a few documents), a rare trigger, and rollback() right after the failed call recovers cleanly.
Summary
You update a doc-values field (updateNumericDocValue, updateBinaryDocValue, or a soft delete) and open an NRT reader, flush or commit, and the doc-values update write throws a non-tragic IOException after the new files were already published into the segment's SegmentCommitInfo (re-opening the writer's pooled segment reader fails, or a second segment's update write in the same batch fails); the writer stays open (isOpen() true, no tragic exception) and you keep using it. You expect the acknowledged update to reach the next NRT reader and commit, and every file the writer's SegmentInfos references to stay on disk, as in 6.x and as the since-deleted test testNoLostDeletesOrUpdates required. Instead the writer skips its IndexFileDeleter checkpoint and keeps a stale pooled reader whose pending update was already pruned: in releases (and on main with maxDocValuesOverlays=0) the next update rewrites the column from that stale reader and a later commit succeeds with the update reverted (doc 0 = 0 instead of 100, no exception), while with overlays (main's default) or on the partial-batch path the writer later deletes the published files and NRT opens or commits fail with NoSuchFileException. On main's default config the silent revert happens too when the next step is a merge of that segment, for example forceMerge(1): the merge reads the stale pooled reader, the published overlay files are no longer referenced, and the following commit succeeds with the old value and a clean CheckIndex.
Introduced

Part B (a partial-batch failure deletes still-referenced files): LUCENE-8232 = #9279 'Separate out PendingDeletes from ReadersAndUpdates' (s1monw), a refactoring that removed writer.checkpointNoSIS() from the end of writeFieldUpdates and left the checkpoint to callers that checkpoint only on normal return: branch_7x d47931c4b8a (parent 2caf52587cd correct for part B) and master acb3c379427 (parent ab092942cf6) [exec]. Patch era, no pull requests. Later changes that kept the outcome: #13017 (47792dfcd3c / fc9d6770a55, moved the re-open after publication; 9.10.0 and 9.11.0 behave identically [exec]) and #16418 (75eddfaff22, overlays on by default on main: part A's default symptom became a deleted, still-referenced file [exec at it and its parent 23c1810e431]) (2017-06-21 (part A, LUCENE-7868); 2018-03-29 (part B, LUCENE-8232))
