The finding in 30 seconds

#

The limits first. Only Matches and highlighting fail; the search, the count and explain of the same query are right. The shape is narrow: one sub-source of an ordered, unordered or atLeast source must report 13 or more sub-matches (on a 64-bit JVM); with 12 the same calls answer. The failure is loud, the same with assertions on and off.

Background: three pieces

#
  1. An interval query matches where its sources line up in a document. Intervals.ordered(a, b) wants a match of a followed by a match of b; Intervals.phrase(...) is itself a source, so sources nest.
  2. Weight#matches tells where in a document a query matched: positions, offsets and, for a match made of several terms, its sub-matches, one per term. The default UnifiedHighlighter reads them to highlight a hit.
  3. An ordered, unordered or atLeast source moves on in its sub-sources while it looks for the smallest interval. So it first copies each sub-source's current sub-matches into a small buffer: four numbers per sub-match (start and end position, start and end offset).

The finding, step by step

#
  1. Index one document with the 14-word text a b c d e f g h i j k l m n (default settings). Ask Weight#matches for ordered(phrase(a ... l), term(m)), a 12-term phrase followed by a term: one match at positions 0 to 12, and the default UnifiedHighlighter highlights the hit.
  2. Now ask for ordered(phrase(a ... m), term(n)), a 13-term phrase followed by a term. The document is a hit: the count is 1 and explain says it matches. You expect one match at positions 0 to 13.
  3. Instead Weight#matches throws ArrayIndexOutOfBoundsException: Index 50 out of bounds for length 50, with assertions on and off. The default UnifiedHighlighter throws the same for this hit, because it reads weight matches by default; built withWeightMatches(false) it highlights the hit.
  4. Why 13: the buffer that copies one sub-source's sub-matches takes four ints each and grows only when count * 4 >= length, a test that is right only while the length is a multiple of 4. The lengths are 16, 24, 32, 40, then 50 (a 64-bit JVM). At the 13th sub-match 48 >= 50 is false, and the write to index 50 fails.
  5. What did not fail: a phrase alone and a flat ordered or unordered source of distinct terms answered at each size run (up to 300 terms), and a document that does not match gets null. One highlight call for two hits can fail as a whole when one of them is such a document.

Who is affected

#

Applications that read Weight#matches or IntervalsSource#matches of an interval query, or highlight its hits with the default UnifiedHighlighter, when one sub-source of an ordered, unordered or atLeast source has 13 or more sub-matches (on a 64-bit JVM). No setting or scale is needed. A highlight call for two hits can fail as a whole when one is such a document.

Why it looks unintended

#
  • The javadoc of Weight#matches promises Matches for a document that matches. This one matches: the count is 1.
  • Nothing documents a limit on terms or sub-matches, and the code calls ArrayUtil.grow: it is written to grow.
  • The experimental marker is about API stability. Earlier failures on this path were fixed as bugs (#10074, #10783, #11177).
The full argument262 words
  • Contract. Weight#matches: "Returns Matches for a specific document, or null if the document does not match the parent query" (lucene/core/src/java/org/apache/lucene/search/Weight.java:67-69). The document matches: the count of the same query is 1 and explain says so. IntervalsSource#matches: "Return a MatchesIterator over the intervals defined by this IntervalsSource for a given document and field" (IntervalsSource.java:47-51). MatchesIterator: "You can retrieve the positions of individual matching terms on the current match by calling getSubMatches()" (lucene/core/src/java/org/apache/lucene/search/MatchesIterator.java:30-31).
  • No documented limit. The javadocs of Intervals.phrase (Intervals.java:94-97), Intervals.ordered (:415-422) and Intervals.unordered (:426-436) state no bound on the number of terms or sub-matches. No line of lucene/CHANGES.txt or lucene/MIGRATE.md names the class or the buffer.
  • The code is written to grow. cache() calls ArrayUtil.grow with (count + 1) * 4 and count + 1 (CachingMatchesIterator.java:49-50). ArrayUtil.oversize promises "an array size >= minTargetSize" (ArrayUtil.java:121); it does not promise a multiple of 4.
  • No test expects it. No test names CachingMatchesIterator (the name occurs in three main source files), and no test under lucene/queries/src/test/org/apache/lucene/queries/intervals expects an ArrayIndexOutOfBoundsException.
  • Earlier failures on this path carry the label type:bug: #10074 (LUCENE-9031, an UnsupportedOperationException while highlighting an interval query; fixed in 8.4), #10783 (LUCENE-9744, a NullPointerException for atLeast; fixed), #11177 (LUCENE-10140, inaccurate sub-match positions; fixed in 9.0); #11113 (LUCENE-10075, a NullPointerException with a wildcard source) is open (states read on 2026-11-22).
  • History. The growth test is as old as the feature (Version history); no commit message of the changes that touched it speaks of a limit.
The devil's-advocate check186 words

The strongest case for "intended" has two parts. (a) The API is experimental: Weight#matches and MatchesIterator carry @lucene.experimental (Weight.java:76, MatchesIterator.java:36), and the package doc says "This package contains experimental classes to search over intervals within fields" (package-info.java:21). (b) A task about these buffers was closed Won't Fix in 2019 (#10078).

Why it fails: the marker is about API stability (on #9468 it was used in 2018 to move helper functions in a point release), not a licence for an index error on a matching document, and the four items above carry the label type:bug under the same marker. #10078 is a task ("Increase doc snippet to attempt to overflow buffers at intervals.CachingMatchesIterator"; its body names a test, TestIntervals.testNestedMaxGaps()), closed the next day by the person who opened it with the one comment "Can't do it reliably."; it names no exception and no failing input, and nothing about behaviour was decided there. What bounds the finding is true and is said first on this page: the failure is loud, only Matches and highlighting fail, and the shape is narrow.

Suggested fix

#

No patch is proposed. A shape that was tried: grow each buffer by its own need, in place of the one test. With it the test passes, assertions on and off, and the queries, highlighter and monitor suites show no failure. Correcting only the test moves the failure to the 17th sub-match. The maintainers choose the form.

Summary
You index the 14-word text 'a b c d e f g h i j k l m n' and ask Weight#matches for the interval query ordered(phrase(a ... m), term(n)), a 13-term phrase followed by a term; the default UnifiedHighlighter asks the same question when it highlights a hit of such a query. The document is a hit (count is 1), so you expect the one match at positions 0 to 13, as ordered(phrase(a ... l), term(m)), a 12-term phrase followed by a term, gives positions 0 to 12 on the same text. Instead the call throws java.lang.ArrayIndexOutOfBoundsException (Index 50 out of bounds for length 50) from CachingMatchesIterator.cache(), with and without assertions: the buffer that copies the sub-matches of each sub-source is grown only when 'count * 4 >= length', a test that is right only while the length is a multiple of 4, and after four growths the length is 50, so the 13th sub-match of one sub-source cannot be stored; the search itself is unaffected.
