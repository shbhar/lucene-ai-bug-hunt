SoftDeletesRetentionMergePolicy ignores the wrapped policy when its retention query's scorer is empty, so a fully soft-deleted segment the wrapped policy keeps is dropped at commit

SoftDeletesRetentionMergePolicy lets the policy it wraps decide whether to keep a fully deleted segment only when its retention query has a null scorer; a scorer with no hits means "drop". So soft-deleted documents an inner retention policy keeps vanish at commit: 2 become 0, since 7.4.0.

The finding in 30 seconds

#

Whether the wrapped policy gets a say depends only on how the outer retention query reports "no match" on the segment.

Background: soft deletes and retention

#
  1. With soft deletes (IndexWriterConfig.setSoftDeletesField), deleting a document only marks it in a doc-values field; it stays in its segment.
  2. SoftDeletesRetentionMergePolicy keeps soft-deleted documents that match a retention query (for example the last N operations) alive through merges. It wraps another merge policy.
  3. When every document of a segment is deleted, IndexWriter drops the whole segment unless the merge policy's keepFullyDeletedSegment returns true.
  4. A query that matches nothing on a segment may return a null scorer or a scorer with no hits: null is an optional shortcut.

The finding, step by step

#
  1. Wrap a SoftDeletesRetentionMergePolicy that keeps every soft-deleted document (MatchAllDocsQuery) in a second one whose retention query is seq:[3 TO 4]. Index 2 documents with seq 1 and 10, soft-delete both, commit.
  2. You expect maxDoc 2: the inner policy alone keeps both documents, and the outer query matches neither, so it should leave the decision to the inner policy.
  3. Instead the commit drops the segment: maxDoc 0, no error. With the outer range seq:[20 TO 30], which also matches nothing, the same setup keeps both (maxDoc 2).
  4. Why: keepFullyDeletedSegment asks the wrapped policy only when the query's scorer is null. seq:[20 TO 30] lies outside 1..10 and is rewritten to match nothing (null scorer); seq:[3 TO 4] lies between 1 and 10, gets a real scorer with no hits, and the method answers "drop".

Who is affected

#

Applications with soft deletes whose SoftDeletesRetentionMergePolicy wraps a policy that keeps fully deleted segments (a second retention policy, or a custom one), when the outer query matches nothing on such a segment without a null scorer: a two-sided range in a value gap, or a conjunction with no joint match. Retained history is lost silently; live documents are unaffected.

Mechanism, terms and numbers500 words

When every document of a segment is deleted, IndexWriter drops the segment at commit unless the merge policy's keepFullyDeletedSegment returns true. SoftDeletesRetentionMergePolicy wraps another policy and answers by running its retention query on the segment: a hit means keep; a null scorer means "ask the wrapped policy"; but a scorer that exists and finds nothing means "drop", and the wrapped policy is never asked. Weight.scorer returns null only as an optional shortcut, so two retention queries that both match nothing can give opposite answers. When the wrapped policy keeps the segment (for example an inner retention policy that retains every soft-deleted document, or a custom policy), the segment and the soft-deleted documents it retains are silently lost at commit. Live documents and searches are not affected. It needs a rare composition and an outer query whose scorer is empty but not null (a two-sided range in a gap of the segment's values, or a conjunction with no joint match); a bare one-sided seq_no >= X range, the common retention query, never triggers it. The fix is one branch: return true on a hit, otherwise ask the wrapped policy.

Null versus empty in the repro

#

PointRangeQuery.rewrite compares the range with the segment's min and max (search/PointRangeQuery.java:544-572). For values 1 and 10, seq:[3 TO 4] crosses [1, 10] and stays a range query (:570), whose scorer finds nothing: the method returns false. seq:[20 TO 30] lies outside [1, 10] and becomes MatchNoDocsQuery (:569), whose scorer is null: the method asks the wrapped policy, which keeps the segment. A direct probe over a custom policy that keeps every fully deleted segment gives false for seq:[3 TO 4] and true for seq:[20 TO 30], MatchNoDocsQuery, an absent term and an absent field (all null scorers).

Exposure and likelihood208 words
  • Who. Applications that use soft deletes with a SoftDeletesRetentionMergePolicy wrapped around a policy that keeps fully deleted segments: a second SoftDeletesRetentionMergePolicy (a natural way to retain the union of two criteria), or a custom policy. Lucene's own TestIndexWriter.testRandomOperations wraps a policy whose keepFullyDeletedSegment returns a random flag (TestIndexWriter.java:4247-4256), so a keeping wrapped policy is a public-API configuration that Lucene's own tests exercise (no javadoc documents nesting either way).
  • When. The outer retention query must have an empty, non-null scorer on the fully deleted segment: a two-sided range in a gap of the segment's values, or a conjunction whose clauses each match but never together (for example seq >= 8 AND type:keep). A bare one-sided seq_no >= X range, the common retention query, never produces it: on a segment it either matches the largest value or is rewritten to match nothing. Inside a conjunction it can, as in that example.
  • Default vs opt-in. Opt-in: soft deletes and the @lucene.experimental policy (SoftDeletesRetentionMergePolicy.java:44). A downstream code search found keepFullyDeletedSegment overrides only in test files.
  • Scale. None: 2 documents.
  • Effect. Silent and permanent: the soft-deleted documents the wrapped policy retains disappear at commit, with assertions on and off. Live documents and searches over them are not affected.

Why it looks unintended

#
  • The method's own fallback asks the wrapped policy on a null scorer; an empty scorer is the same "no match" (Weight.java:119).
  • Two queries that both match nothing give opposite answers: seq:[3 TO 4] drops the segment, seq:[20 TO 30] keeps it.
  • Merges already combine both policies: forceMerge keeps the inner policy's document, the next commit loses it.
The full argument260 words

No javadoc says what a no-hit answer must do; the points below infer it from the code, the tests and the merge path. That makes a strong consistency argument, not a documented guarantee.

  • The fallback. return super.keepFullyDeletedSegment(...) (SoftDeletesRetentionMergePolicy.java:93) is what the method does when the query matches nothing with a null scorer. By Weight.java:119 an empty scorer gives the same answer from the query.
  • The inconsistency. In the controls (main, assertions off) the inner policy alone keeps maxDoc 2; outer seq:[3 TO 4] over it gives 0; outer seq:[20 TO 30] over it gives 2; the swapped nesting gives 2. Neither outer query matches a document.
  • Merges compose as a union. With the same nesting, forceMerge(1) keeps the inner-retained soft-deleted document (maxDoc 3, against 2 with the outer policy alone); once the merged segment is fully soft-deleted, the commit drops it (maxDoc 0), while an outer range outside the values keeps it (maxDoc 3).
  • The hook is meant for this. MergePolicy.keepFullyDeletedSegment: "Returns true if the segment ... should be kept even if it's fully deleted. This is useful for testing of for instance if the merge policy implements retention policies for soft deletes" (MergePolicy.java:749-753).
  • No test pins the current answer. TestSoftDeletesRetentionMergePolicy.testKeepFullyDeletedSegments (from :115) asserts false only through the null-scorer path (an absent field) over NoMergePolicy; it passes with the fix.
  • History. The branch came in this shape with the class (LUCENE-8233, 2018); neither its discussion nor later commits touching the method discuss wrapped policies or null versus empty scorers.
The devil's-advocate check160 words

The strongest case for "intended", made by the intended-behaviour check (which found it does not survive) and by an independent reviewer from another model family (OpenAI GPT-5.6), which rated it moderate: no javadoc says the outer policy must honour the wrapped policy's keep answer; the comment at :83 ("we only need a single hit to keep it") presents the query as the authority; the class is @lucene.experimental; and nesting two retention policies is unusual, since one BooleanQuery with SHOULD clauses gives the union.

Why it fails: under that reading the null branch would also have to return false, yet it asks the wrapped policy; the merge path of the same class is a union; and a user cannot tell from a query whether it will produce a null or an empty scorer on a given segment. A maintainer could still document nesting as unsupported; then the null branch would need to change too. Verdict: a real Low bug.

Suggested fix

#

Recommended A. Return true on a hit, otherwise ask the wrapped policy (validated)

In keepFullyDeletedSegment, return true when the retention query has a hit, and otherwise fall through to super.keepFullyDeletedSegment, so the wrapped policy decides whether the scorer is null or empty. The repro passes with assertions on and off; the org.apache.lucene.index package of lucene/core passes (1,398 tests, 0 failures, 56 skipped) and the formatter check is clean.

Trade-offs

Behaviour changes only when the scorer is empty and the wrapped policy keeps the segment. In Lucene's main sources only SoftDeletesRetentionMergePolicy itself can answer true (FilterMergePolicy forwards, NoMergePolicy returns the default false), so over TieredMergePolicy, LogDocMergePolicy or NoMergePolicy the answer is unchanged. Same cost: at most one nextDoc().

What the checks validated

  • Without the fix the repro fails with assertions on and off (gradle, seed DEADBEEF).
  • With the fix the repro passes with assertions off, and the repro plus all 215 test classes of lucene/core's org.apache.lucene.index package pass with assertions on: 1,398 tests, 0 failures, 56 skipped (among them the 14 TestSoftDeletesRetentionMergePolicy tests, TestPendingSoftDeletes, TestSoftDeletesDirectoryReaderWrapper and TestIndexWriter). One seed, no nightly tests; not the full test matrix.
  • :lucene:core:checkGoogleJavaFormat passes with the fix and the repro test in place.

B. Make the outer query authoritative and document it

#

Return false on a null scorer too, and document that the retention query alone decides.

Trade-offs

Consistent, but it removes behaviour that works today (an out-of-range outer query over a keeping policy keeps the segment), contradicts the union on the merge path, and leaves nesting unusable. Not run.

C. Workaround for users (no Lucene change)

#

Use one SoftDeletesRetentionMergePolicy whose query is a BooleanQuery of SHOULD clauses instead of nesting two. Swapping the nesting helps only when the outer policy never answers from an empty scorer: a retain-all query (the swapped control) or a custom policy that always keeps.

Trade-offs

Avoids the branch, but every user has to know about it. Executed: with A = seq:[3 TO 4] and B = seq:[1 TO 1], segments with seq {1, 10} and {0, 3, 5}, all soft-deleted (each segment has a document that A or B matches, so the union keeps both: maxDoc 5), A over B keeps 3, B over A keeps 2, and one policy with A SHOULD B keeps 5. So swapping two selective policies only moves the loss to another segment.

Downstream note

#

Products that keep soft-deleted documents as operation history (for replicas or recovery) are exposed only if they nest retention policies or wrap a policy that keeps fully deleted segments; a bare one-sided seq_no >= X retention range never triggers it.

How it was found

#

A semi-formal proof-obligation audit of SoftDeletesRetentionMergePolicy's contract: when its own retention query keeps nothing, the wrapped policy should decide. Reading keepFullyDeletedSegment showed that only a null scorer reaches the wrapped policy, and a one-test JUnit repro witnessed the empty-scorer case.

The method in full118 words

The obligation: when the policy's own retention query has nothing to keep on a fully deleted segment, the answer must be the wrapped policy's, however the query reports "no match". A probe on the main jars over one segment with seq 1 and 10 and a wrapped policy that keeps every fully deleted segment tried six retention queries: seq:[3 TO 4] (a non-null scorer, 0 hits) gives false and the segment is dropped; seq:[20 TO 30], MatchNoDocsQuery, an absent term and an absent field (all null scorers) give true; seq:[1 TO 1] (one hit) gives true. A second probe nested two retention policies over the same two documents; the JUnit test uses that setup.
