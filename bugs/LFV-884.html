Grouping by score ranges reads a placeholder score when a pass requests no scores

Grouping hits by score ranges (DoubleRangeGroupSelector over DoubleValuesSource.SCORES) silently reads a placeholder score (0 for term and boolean queries) in any grouping pass that requests no scores: hits scoring 1, 2, 3, 1, 3 come back as one empty group [0, 1) once groups are sorted by a field. Affected since 8.6.0; the defaults are not.

The bug in 30 seconds

#

A range group selector can bucket hits by their score; it reads the score from the collector's scorer. But only each pass's sorts (and the max-score setting) decide whether the query computes scores, so with a field group sort the first pass reads 0.

  1. Index five documents and search a OR b OR c made of constant-score clauses: they score 1, 2, 3, 1, 3. Group them with GroupingSearch and new DoubleRangeGroupSelector(DoubleValuesSource.SCORES, new DoubleRangeFactory(0, 1, 10)).
  2. With the defaults plus setGroupDocsLimit(10) (the default returns one document per group) the ranges are right: [1,2) = docs 0, 3; [2,3) = doc 1; [3,4) = docs 2, 4. Now sort the groups by the id field. You expect the same three groups: a document's score does not depend on how groups are ordered.
  3. You get one group, [0, 1), with no documents: 5 hits, 0 grouped. No error on main, with assertions on or off.
  4. Why: each pass asks the query for scores only when its own sort or max-score setting needs them, and a group selector cannot ask. Pass 1 runs without scores: every hit reads 0 and lands in [0, 1). Pass 2 scores (for the max score), and every real score falls outside [0, 1), so every hit is skipped.
  5. Same cause, other outputs: setIncludeMaxScore(false) with a field sort inside groups gives the three right ranges, all empty; AllGroupsCollectorManager alone reports 1 range instead of 3, and AllGroupHeadsCollectorManager alone with a field sort 1 head instead of 3.

Who is affected

#

Applications that group with DoubleRangeGroupSelector or LongRangeGroupSelector over a source that needs scores, and either sort groups by a field, turn off includeMaxScore with a field sort inside groups, or run AllGroupsCollectorManager (or AllGroupHeadsCollectorManager with a field sort) alone. Opt-in and rare; the GroupingSearch defaults are not affected; any index size; queries that compute scores only when asked (term, boolean).

Mechanism, terms and numbers759 words

DoubleRangeGroupSelector and LongRangeGroupSelector group hits by ranges of a values source, and they hand that source the collector's scorer, so a source that reads the score (DoubleValuesSource.SCORES) can group hits into score bands. But a GroupSelector cannot say that it needs scores, and the four grouping collectors that use one decide whether the query computes scores from their sorts or reducer alone. In a pass where none of them needs scores, the query runs in COMPLETE_NO_SCORES, the selector reads a placeholder (0 for the term and boolean queries of every repro) for every hit, and the groups come out silently wrong: one empty group with a field group sort, the right groups without their documents with includeMaxScore=false, and 1 group or head instead of several from AllGroupsCollectorManager or AllGroupHeadsCollectorManager run alone. It has been there since the selectors were added in 8.6.0; the GroupingSearch defaults (relevance group sort, includeMaxScore=true) are not affected.

Terms

#
  • Group selector (GroupSelector): decides the group of each hit. DoubleRangeGroupSelector and LongRangeGroupSelector read a value per hit from a values source and put the hit into a fixed-width range (DoubleRangeFactory(0, 1, 10): ranges of width 1 from 0 to 10).
  • Score-dependent source: a DoubleValuesSource whose needsScores() is true, such as DoubleValuesSource.SCORES (the hit's score) or its toLongValuesSource(). The range selectors feed it the collector's scorer through DoubleValuesSource.fromScorer (DoubleRangeGroupSelector.java:60-63, LongRangeGroupSelector.java:61-64).
  • Score mode: each collector tells the query whether it needs scores (Collector.scoreMode()). In COMPLETE_NO_SCORES, "scores won't be available" (ScoreMode.java:25-26); a non-scoring term weight, for example, uses a dummy scorer that returns 0 (TermQuery.java:77-91).
  • Two-pass grouping: GroupingSearch runs a first pass (FirstPassGroupingCollector) to find the top groups, then a second pass (TopGroupsCollector, a SecondPassGroupingCollector) to collect each group's documents; AllGroupsCollector and AllGroupHeadsCollector can run alongside or on their own.

The bug

#
  1. GroupSelector has setScorer but no needsScores() (GroupSelector.java:34-72), so a selector cannot ask for scores.
  2. The four collectors that use a group selector take their score mode from their sorts or reducer only, each pass on its own: the first pass from the group sort (FirstPassGroupingCollector.java:105, 124-127), the second pass from the reducer, which needs scores only for the max score or a within-group sort that needs them (SecondPassGroupingCollector.java:76-79, TopGroupsCollector.java:127-128), AllGroupHeadsCollector from its sort (:119-122), and AllGroupsCollector never (:91-94, "the result is unaffected by relevancy").
  3. So with a field group sort the first pass runs without scores. The selector reads 0 for all five hits and keeps one group, [0, 1).
  4. The second pass scores, because includeMaxScore defaults to true, and the selector now reads the real scores 1, 2, 3, 1, 3. None falls into [0, 1), the only group, so advanceTo returns SKIP for every hit (DoubleRangeGroupSelector.java:75, SecondPassGroupingCollector.java:90): one empty group.
  5. With the relevance group sort but includeMaxScore=false and a field within-group sort, the first pass is right and the second pass reads 0: the three right ranges come back empty. AllGroupsCollector and AllGroupHeadsCollector alone read 0 for every hit: 1 range, 1 head.

DoubleValuesSource.SCORES.needsScores() is true (DoubleValuesSource.java:349-368); the information exists, but no grouping collector asks the selector. When a sort happens to need scores, the selector is right by accident.

Not every query is hit. Without scores the value a scorer returns is unspecified (ScoreMode only says scores "won't be available"). Term and boolean queries and ConstantScoreQuery clauses return 0 (TermQuery.java:77-91, ConstantScoreQuery.java:141-146, 202-203), so they are grouped wrongly; queries whose score is a constant boost in every mode, such as MatchAllDocsQuery or a point range query (ConstantScoreWeight), still return their real score and are grouped right (executed).

The numbers

#

Five documents with tags {a}, {a,b}, {a,b,c}, {a}, {a,b,c}; a OR b OR c of ConstantScoreQuery(TermQuery) clauses scores them 1, 2, 3, 1, 3 (a plain search, asserted by the control test). Expected for every configuration (with setGroupDocsLimit(10)): {[1,2)=[0, 3], [2,3)=[1], [3,4)=[2, 4]}. Group sort by id: {DoubleRange(0.0, 1.0)=[]} (totalHitCount 5, totalGroupedHitCount 0; with setAllGroups(true) also totalGroupCount 1). LongRangeGroupSelector over SCORES.toLongValuesSource(): {LongRange(0, 1)=[]}. includeMaxScore=false with a within-group sort by id: {[1,2)=[], [2,3)=[], [3,4)=[]}. AllGroupsCollectorManager alone: [DoubleRange(0.0, 1.0)]. AllGroupHeadsCollectorManager with sort id alone: heads [0] instead of [0, 1, 2]. An independent reproducer with 12 documents whose scores are 10.8 to 16.8 recorded what the selector reads under an id sort: 0.0 for all 12.

Exposure and likelihood337 words
  • Who. Grouping with DoubleRangeGroupSelector or LongRangeGroupSelector over a values source that needs scores: DoubleValuesSource.SCORES, its toLongValuesSource(), or (by reading, not run) an expression that binds _score to it, the pattern the expressions module documents (SimpleBindings.java:35), plus any one of: (a) a group sort that does not need scores; (b) includeMaxScore=false and a within-group sort that does not need scores, even with the default relevance group sort; (c) AllGroupsCollectorManager, or AllGroupHeadsCollectorManager with a sort that does not need scores, run on its own.
  • Where (c) shows. On the 10.6 branch and main. On 8.6.0-10.5.2 those stand-alone collectors did not forward the scorer, and the same search throws a NullPointerException instead (a related bug in the same selectors); #16247 (unreleased) turned that exception into these wrong groups.
  • Default vs opt-in. Grouping by score ranges is opt-in; the GroupingSearch defaults (relevance group sort, includeMaxScore=true) request scores in both passes and are right. Once configured with a trigger, a search is mis-grouped whenever the placeholder falls into a different range from the real scores, as for the repro's boolean query; constant-score queries such as MatchAllDocsQuery are grouped right.
  • Scale. None: five documents in one segment show it, deterministically, with assertions on and off.
  • Effect. Silent wrong groups: one empty group, the right groups without documents, documents missing from their groups, or 1 group or head instead of several. Nothing fails on main with a plain IndexSearcher; totalHitCount stays right while totalGroupedHitCount drops to 0.
  • How likely. Rare: grouping by the score is unusual, the defaults hide it, no use of the range selectors was found in Elasticsearch, OpenSearch or Solr, and no public report was found in the searched sources.
  • Workaround. Add a score tie-break to the group sort, new Sort(new SortField("id", SortField.Type.INT), SortField.FIELD_SCORE) (executed), and keep includeMaxScore=true or a within-group sort that needs scores. For the stand-alone collectors, run them in a MultiCollectorManager next to a collector that needs scores (executed by the fact check: 3 right ranges, heads [0, 1, 2]).

Why it is a bug, not intended

#
  • The selectors take any values source and pass it the collector's scorer on purpose, which only matters for sources that need scores.
  • Lucene's value-source sort passes needsScores() on; a missing pass-through was fixed as a bug (#14654).
  • Group membership changes with the group sort. The "unaffected by relevancy" comment predates score-reading selectors.
The full argument296 words
  • Selector contract. DoubleRangeGroupSelector takes "a DoubleValuesSource to retrieve double values per document" (DoubleRangeGroupSelector.java:46; LongRangeGroupSelector.java:47 the same for longs), with no restriction; the package javadoc lists it as grouping "based on the value of a DoubleValuesSource" (package-info.java:67-70).
  • The bridge serves this case. setScorer binds source.getValues(context, DoubleValuesSource.fromScorer(scorer)). DoubleValuesSource.getValues says callers "may safely pass null" for the scores when needsScores() is false (DoubleValuesSource.java:60-66), so the scorer, which the selectors pass to every source, is needed only by score-dependent sources; the class javadoc documents scores as a value source through fromScorer (:43-46).
  • Score-mode contract. COMPLETE_NO_SCORES: "Produced scorers will allow visiting all matches but scores won't be available" (ScoreMode.java:25-26); Collector.scoreMode(): "Indicates what features are required from the scorer" (Collector.java:55-56).
  • Unrelated settings change membership. setIncludeMaxScore is documented as "Whether to include the score of the most relevant document per group" (GroupingSearch.java:329-338); turning it off empties every group. A group sort by a field merges every hit into [0, 1).
  • Convention and precedent. DoubleValuesSortField.needsScores() returns producer.needsScores() (DoubleValuesSource.java:637-640), which is why a sort by a score-dependent source works in grouping today. #14654 (CHANGES 10.3.0, Bug Fixes) fixed a missing pass-through of the same kind: "would throw errors when used if the DoubleValuesSource needed scores".
  • Tests. No upstream grouping test uses a score-dependent source: TestDoubleRangeGroupSelector and TestLongRangeGroupSelector use field sources, and nothing in lucene/grouping/src/test uses SCORES or fromScorer. The case is untested, not decided.
  • History. LUCENE-6912 (2015) wrote the sort-based score modes and the "unaffected by relevancy" comment, when no selector could read a scorer. LUCENE-7889 (2020) added setScorer and the range selectors with the score bridge and changed no score mode; its PR has no review comments and its discussion never mentions scores.
The devil's-advocate check259 words

The strongest case for "intended" (built by the devil's-advocate checker and the other-family reviews; the reviews rate it moderate, the devil's advocate gives no rating): AllGroupsCollector states "the result is unaffected by relevancy"; GroupSelector never had a way to ask for scores, its javadoc says nothing about score availability (GroupSelector.java:25-33), and ValueSourceGroupSelector.setScorer is empty, so the module may never have meant group keys to depend on scores; the defaults work; a score tie-break is a workaround; the tests use field sources only; the collectors and GroupingSearch are marked @lucene.experimental, which leaves maintainers room to narrow the contract; and LUCENE-7889's commit message gives numeric-valued fields as the motivation.

Why it fails: the comment predates score-reading selectors by 4.5 years and was not revisited when they were added; the fromScorer bridge is needed only by score-dependent sources, so wiring it and never requesting scores looks like an oversight; no javadoc restricts the source, SCORES is public and documented, and the numeric-field motivation says why the feature was added, not what it excludes; and the groups change with unrelated settings, which no contract can intend. Verdict: most likely not intended, a defect born with the feature; a javadoc restriction remains a legitimate maintainer alternative. The fact checks read it the same way. The expected behaviour is inferred from the API's shape and the needsScores convention, not quoted from a grouping javadoc, so a maintainer may prefer to document a restriction; the issue should offer both. Not security: wrong groups through correct use of public APIs, chosen by the application.

Suggested fix

#

Recommended Let a GroupSelector declare that it needs scores

Add GroupSelector#needsScores() (default false), return source.needsScores() from the two range selectors, and OR it into the score modes of the first-pass, second-pass, all-groups and all-group-heads collectors (+26/-4 in 7 files). The whole grouping module passes, the repros included, with assertions on and off, and its static checks pass.

Let a GroupSelector declare that it needs scores (validated by the checks) (recommended)

#

The finder's fix, formatted with gradlew tidy: a non-abstract GroupSelector#needsScores() returning false; DoubleRangeGroupSelector and LongRangeGroupSelector override it with source.needsScores(); FirstPassGroupingCollector, SecondPassGroupingCollector (so also TopGroupsCollector and DistinctValuesCollector), AllGroupsCollector and AllGroupHeadsCollector OR it into their score modes. +26/-4 in 7 files.

// GroupSelector
public boolean needsScores() {
  return false;
}
// DoubleRangeGroupSelector, LongRangeGroupSelector
@Override
public boolean needsScores() {
  return source.needsScores();
}
// FirstPassGroupingCollector
this.needsScores = groupSort.needsScores() || groupSelector.needsScores();
// SecondPassGroupingCollector (AllGroupHeadsCollector: sort.needsScores(); AllGroupsCollector: the selector alone)
return groupReducer.needsScores() || groupSelector.needsScores()
    ? ScoreMode.COMPLETE
    : ScoreMode.COMPLETE_NO_SCORES;

Trade-offs

  • A new public, non-abstract method on a public abstract class: additive and source-compatible. A custom GroupSelector that reads scores must override it; say so in the javadoc and in CHANGES.
  • A score-dependent selector now makes the query compute scores: a cost only for those users, and what they need for a correct result. Score-independent selectors are unchanged.
  • It follows the existing convention (DoubleValuesSortField.needsScores() returns producer.needsScores()).
  • It drops the "the result is unaffected by relevancy" comment, which could stay as "unless the selector reads scores".
  • Out of scope (a related bug in the same selectors): the score-less cache replay (setCaching(n, false)) still cannot serve a score-dependent selector, and DistinctValuesCollector's value selector never gets setScorer.

Document the restriction instead

#

Say in the javadoc of both range selectors that the source must not need scores unless a sort that needs scores is used, and correct the AllGroupsCollector comment. Not run.

Trade-offs

The smallest change and a legitimate maintainer choice, but a documented public input keeps giving a silent wrong answer, and the selectors' fromScorer bridge would then serve only passes whose sort or reducer already requests scores.

Reject score-dependent sources in the selectors' constructors

#

Throw IllegalArgumentException when source.needsScores() is true. Not run.

Trade-offs

Breaks configurations that work today (relevance sorts); not recommended.

Downstream note

#

Only grouping output changes (no exception, nothing extra returned or exposed), so a downstream product is affected only if it offers grouping by score ranges together with a field sort or the stand-alone group collectors.

How it was found

#

A bytecode scan of 20 Lucene jars listed every non-scoring score mode that reaches a consumer and every bridge that feeds scores into a values source (561 rows). The range selectors' bridges sat next to grouping collectors that never ask for scores; reading them gave the lead and a public-API test confirmed it.

The method in full183 words

Method: static bytecode inventory plus code reading, then a public-API test (the hunt's "semi-formal" tier; the lead came from reading rows of a mechanical inventory, which a strict reading could put in the non-formal tier).

  • The hunt unit looked for weights or collectors that run without scores while something reads scores. It scanned the class files of 20 non-test jars with the JDK 25 class-file API: 561 rows, among them every site where COMPLETE_NO_SCORES or a needsScores()-conditional mode reaches a consumer and every DoubleValuesSource.fromScorer bridge. Each non-test row was triaged by reading.
  • The bridge rows DoubleRangeGroupSelector.setScorer and LongRangeGroupSelector.setScorer sat next to grouping collectors whose scoreMode() is COMPLETE_NO_SCORES unless a sort or reducer needs scores. The finder wrote the public-API JUnit test, which failed 3 of 4 with assertions on and off.
  • A secondary dynamic sweep ran 5,696 module compositions under the test framework's asserting searcher; its only new scorer-protocol sites were this bug's first-pass and second-pass collectors, including the second-pass-only trigger. A planted non-scoring collector that reads scores fired as a positive control.
  • Independent checks then reproduced it (see the checks below).

LFV-884, snapshot of 2026-10-29

Registry title
Grouping collectors never ask for scores on behalf of their group selector, so DoubleRangeGroupSelector or LongRangeGroupSelector over a score-dependent source (e.g. DoubleValuesSource.SCORES) groups every hit by the placeholder score of a non-scoring search (0 in every repro) when no sort or reducer needs scores, or when AllGroups/AllGroupHeads runs alone (since 8.6.0)
Area
grouping / GroupSelector score needs (FirstPass, SecondPass/TopGroups, AllGroups, AllGroupHeads collector score modes)
Priority
Low, rank 277: Needs uncommon score-range grouping with a non-scoring sort, and GroupingSearch defaults are unaffected.
Impact class
silent wrong results
Impact note
Applications that group by DoubleRangeGroupSelector or LongRangeGroupSelector over a values source that needs scores (for example DoubleValuesSource.SCORES) get silently wrong groups, with no exception under -ea or -da, at any index size (5 documents suffice), in every release from 8.6.0 to 10.5.2 and on main, whenever (a) the group sort does not need scores, (b) includeMaxScore=false and the within-group sort does not need scores (even with the default relevance group sort), or (c) AllGroupsCollectorManager, or AllGroupHeadsCollectorManager with a sort that does not need scores, runs on its own (on 10.6/main; on 8.6.0-10.5.2 that path throws LFV-414's NullPointerException instead); GroupingSearch's defaults (relevance group sort, includeMaxScore=true) are not affected, and a sort that needs scores (for example a score tie-break) is a workaround.
Summary
You group hits into score ranges, for example with new DoubleRangeGroupSelector(DoubleValuesSource.SCORES, new DoubleRangeFactory(0, 1, 10)), and sort the groups by a field, expecting each hit in the range of its own score, which is what the same search returns with the default relevance group sort (three ranges, [1,2) = {0, 3}, [2,3) = {1}, [3,4) = {2, 4}, in the repro). Instead GroupingSearch returns one empty group [0,1) (LongRangeGroupSelector: LongRange(0, 1)), and AllGroupsCollectorManager on its own reports one range instead of three, because the grouping collectors take their ScoreMode only from their sorts or reducer, so the query runs without scores and the selector, which reads the collector's Scorable through DoubleValuesSource.fromScorer, sees the placeholder score 0 for every hit. GroupSelector has no way to say that it needs scores; a GroupSelector#needsScores() hook (true for the range selectors when their source needs scores), ORed into the four collectors' score modes, fixes it.
Introduced
7c350d22c7070acf362fb4f477e6797f2711c910 (master; branch_8x backport 5e62c42c5f304eee7b5695f97f02a2aea7d00366), LUCENE-7889 'Allow grouping on Double/LongValuesSource' (apache/lucene-solr#1484 by romseygeek, merged 2020-05-11 with no review comments; JIRA mirror apache/lucene#8940) [read: git blame -w and git log -L]: it added the abstract GroupSelector.setScorer and the two range selectors, whose setScorer binds source.getValues(context, DoubleValuesSource.fromScorer(scorer)), but gave GroupSelector no way to request scores and changed no collector's scoreMode(). The score-mode lines are older and were complete when written, because no selector read a scorer before (LUCENE-6912 31b6cd6851c, 2015; LUCENE-4100 4fc5a872ded, 2017; LUCENE-8412 55bfadbce11, 2018). Not a regression: the bug was born with the feature. (2020-05-11 (author date 17:34:01+01:00 for both the master and the branch_8x commit); first released in 8.6.0)
