IndexWriter InfoStream counts a delete batch twice when a merge forces a second pass (8 reported for 4 deleted)

When a merge commits while IndexWriter is applying a batch of deletes, IndexWriter applies the batch again and its BD InfoStream log adds the first pass's count a second time: 8 new deletes/updates for 4 deleted documents. Only this opt-in debug count is wrong; the index is correct.

The finding in 30 seconds

#

apply adds each phase's count to the packet field totalDelCount and returns the field. Its caller forceApply sums the returned values over passes, assuming each is that pass's own count. With two passes that delete 4 and 0, the log shows 4 + (4 + 0) = 8.

Background: how IndexWriter applies a batch of deletes

#
  1. deleteDocuments and updateDocument calls are buffered; at flush they are frozen into a packet that IndexWriter applies to the existing segments.
  2. So that threads can resolve deletes concurrently, IndexWriter.forceApply applies the packet without holding the IndexWriter lock. If a merge commits during that time, it applies the packet once more, only to segments it has not seen yet (the merged one).
  3. With InfoStream on, the BD component logs each pass (done inner apply del packet ... N new deletes/updates) and a final total (done apply del packet ... N new deletes/updates ... K iters due to concurrent merges).

The finding, step by step

#
  1. Turn on IndexWriter's InfoStream, flush two segments {a, a, a, b} and {a, b} (a StringField named key), and start a merge of the two.
  2. Call deleteDocuments(new Term("key", "a")) and flush(). The merge commits while IndexWriter is applying that delete, so IndexWriter applies it a second time, to the merged segment.
  3. You expect the log to report 4: pass 1 deletes 4 documents, and pass 2 finds nothing new (its own line says applyTermDeletes ... 0 new deletions).
  4. You get done apply del packet ... 8 new deletes/updates ... 2 iters due to concurrent merges: pass 2 reported the running total, 4, again, and IndexWriter added it. Same with assertions on and off, on main and 10.6.0.
  5. The index is right: 4 deleted, 2 live documents. Nothing but the two logged counts is wrong.

Who is affected

#

Applications that turn on IndexWriter's InfoStream (off by default) and delete or update documents while merges run. Ordinary timing reaches it: a stock workload with aggressive merging logged 838 wrong totals in 3,877 packets. The logged count is too high by up to the number of passes; nothing acts on it, and the index is correct.

Mechanism, terms and numbers575 words

IndexWriter.forceApply resolves a frozen packet of buffered deletes and updates without holding the IndexWriter lock. If a merge commits meanwhile, it resolves the packet again against the segments it has not seen (the merged one) and adds up each pass's count for two BD InfoStream lines, on the stated assumption that each pass returns only the documents it newly deleted (IndexWriter.java:6591-6604). But FrozenBufferedUpdates.apply, whose javadoc promises "the number of new deleted or updated documents", adds each phase's count to the packet's running field totalDelCount and returns that field (FrozenBufferedUpdates.java:171-175).

So a second pass reports the first pass's deletes again. Deleting 4 documents while a merge commits logs done apply del packet ... 8 new deletes/updates ... 2 iters due to concurrent merges, although the second pass's own phase line says 0 new deletions. The bug dates from LUCENE-7868 (58105a203a1, 2017, released in 7.0.0) and is in every release through 10.6.0 and main. The index, the deletions, search results and every public return value are correct, and the packet field that waitApply logs is unaffected; InfoStream is off by default and is an @lucene.internal debugging API. The fix is to return this call's count from apply.

The code (main 5adff78bb168)

// FrozenBufferedUpdates.java:68-69, a field of the packet

  segStates = openSegmentStates(infos, seenSegments, updates.delGen());  // :6559, unseen segments only

  // It's OK to add this here, even if the while loop retries, because delCount only includes
  // newly deleted documents, on the segments we didn't already do in previous iterations:
  totalDelCount += delCount;                          // :6601-6604

  // :6627-6657  if mergeFinishedGen moved, iter++ and resolve again
}
// :6665-6678  "done apply del packet ... %d new deletes/updates ... iters due to concurrent merges"
  • A merge that commits a non-empty segment increments mergeFinishedGen (IndexWriter.java:4487, in commitMergedDeletesAndUpdates, which commitMerge skips for a 0-document result, :4935-4936). Such a merge committing while a packet is being resolved makes forceApply loop again, unless the packet is segment-private (those never retry, :6618-6625); a later pass that finds no unseen segment stops at packet matches no segments without calling apply (:6561-6566).
  • With passes that newly delete d1, d2, ..., pass i returns d1 + ... + di, and the final line prints the sum of these running totals.
  • The phase lines are right: applyTermDeletes ... %d new deletions prints the phase's own count (FrozenBufferedUpdates.java:497-501).
  • "Documents" is loose for doc-values updates: applyDocValuesUpdates counts applied updates, one per matching document per update term (FrozenBufferedUpdates.java:331, :343), which can exceed the number of distinct documents.
  • The packet field keeps the running total its other reader expects and is unaffected by this bug: BufferedUpdatesStream.waitApply adds packet.totalDelCount (BufferedUpdatesStream.java:237); the fix leaves it unchanged.
  • forceApply is void; the summed value feeds only the two BD lines.
Exposure and likelihood147 words
  • Opt-in: InfoStream is off by default (InfoStream.NO_OUTPUT, LiveIndexWriterConfig.java:142, InfoStream.java:57); the BD component must be enabled.
  • Trigger: ordinary timing, no special input: a merge must commit while a packet is being resolved. A hook-free probe (stock TieredMergePolicy with segmentsPerTier 2, ConcurrentMergeScheduler, two threads calling updateDocument, maxBufferedDocs 50, assertions off) logged 3,877 packets, 899 resolved in more than one pass and 838 with a wrong final total, for example a final 28 new deletes/updates where the phase lines summed to 15 (the probe sums phase lines per thread between final lines; it does not key them by packet). That setup merges aggressively; the rate under default settings was not measured.
  • Effect: someone reading the log to debug deletes or merges over-estimates the work done. The index, deletions, search results, public return values and waitApply's total are unaffected.
  • Versions: every release since 7.0.0.

Minimal repro

#

One JUnit test using public classes (its merge hook, MergePolicy.OneMerge, is @lucene.experimental): two small segments, one merge of both held by OneMerge.wrapForMerge, then deleteDocuments(key:a) and flush(). At pass 1's applyTermDeletes took line the InfoStream callback releases the merge and waits for it, so the merge commits mid-resolution. Latches, no sleeps; it fails with every seed tried.

Expected
The final BD line reports 4 new deletes/updates, the 4 documents the delete removed.
Observed
done apply del packet (...) to 3 segments; 8 new deletes/updates; ...; 2 iters due to concurrent merges, with assertions on and off.

All files of this repro: repro/LFV-1310/

More files, environment, full output464 words

Package org.apache.lucene.index for locality only; every class it uses is public (FilterMergePolicy, NoMergePolicy, MergePolicy.OneMerge, InfoStream, IndexWriter) and it compiles outside that package, but MergePolicy and OneMerge are @lucene.experimental. Data: 6 documents in two segments, ByteBuffersDirectory.

Why the hooks: without them the trigger is a race between a merge commit and a delete resolution. The two latches pin the one interleaving that matters: the merge starts and blocks in wrapForMerge, before it merges anything; pass 1 runs; the merge commits (incrementing mergeFinishedGen); pass 1 then sees the generation moved and forceApply starts pass 2 on the merged segment. The isEnabled("BD") filter and the thread check keep other messages out.

As the regression test: this same method. It fails with seeds DEADBEEF, 1, CAFEBABE and 42 and in gradle's single-CPU test JVM, and passes checkGoogleJavaFormat as is. It checks only the logged count; the independent reproduction also asserts 2 passes, 1 segment, 2 live and 4 deleted documents. Its latch waits have no timeout: bounded waits (await(timeout, unit) plus an assertion) would turn a future regression into a failure, not a hang.

Why it looks unintended

#
  • apply's javadoc promises "the number of new deleted or updated documents"; its only caller sums the values because each "only includes newly deleted documents".
  • The same log contradicts itself: pass 2's phase line prints 0 new deletions, its summary line 4.
  • Upstream has fixed wrong IndexWriter InfoStream numbers as bugs before, most recently #15967 (10.5.0 Bug Fixes).
The full argument168 words
  • Contract: the javadoc of apply (FrozenBufferedUpdates.java:153-154) and the caller's comment (IndexWriter.java:6601-6603) both state the per-call meaning.
  • History: 58105a203a1 (LUCENE-7868, mikemccand, 2017-06-21; archived issue #8919, patch era) added the field, the cumulative return totalDelCount;, the retry loop and the comment together. The loop declared a local long totalDelCount = 0 of the same name as the field, which reads as a naming slip. The #8919 discussion never mentions the counts. Later commits kept the cumulative return and the caller's sum: LUCENE-7887 (c9c0121d939) turned an early return into an assertion, LUCENE-8571 (5f8855ee0bf) restructured the locking and completion, and apache/lucene-solr#1454 (8059eea1608) moved the retry loop into IndexWriter.forceApply.
  • No sign of intent: no test reads these counts or apply's return value; no CHANGES or MIGRATE entry describes them.
  • Precedent: 71d836b713f "fix wrong deleted docs count in IW's infoStream" (2014), LUCENE-9322 (ec9a6598459), LUCENE-10009 (3d833fdb661) and #15967, fixed by #15978 under 10.5.0 Bug Fixes (lucene/CHANGES.txt:1256).
The devil's-advocate check157 words

The strongest case for "not a bug": InfoStream is an @lucene.internal "Debugging API" with no message format contract, FrozenBufferedUpdates and apply are package-private, "new deleted" could mean "newly marked deleted" rather than "in this call", and the minimal test forces the timing through MergePolicy.OneMerge, which is @lucene.experimental. A maintainer could reasonably call it a cosmetic logging inconsistency. An independent reviewer from another model family reproduced the bug and agreed on the cause and the fix, but called it not real on these grounds.

Why it still reads as a slip: the caller's comment states the per-call meaning outright; for a packet that deleted 4 documents the passes deleted 4 and 0 and the packet field ends at 4, so nothing in the code supports 8; the hook only pins a timing that a hook-free stock workload hits on its own; and upstream has fixed wrong InfoStream numbers as bugs. What remains is mostly severity (Low).

Suggested fix

#

Recommended Return this call's count from apply (recommended)

In FrozenBufferedUpdates.apply, sum the three phase counts into a local, add it to the packet's totalDelCount, and return the local (+5/-4 lines). The javadoc and the caller's comment then hold, and waitApply still reads the running total. How it was found

#
