The default codec's .fnm file-format javadoc gives a wrong field grammar: it leaves out the IndexOptions byte and later elements, and its tables miss codes Lucene writes

The javadoc that defines the default codec's field infos file (.fnm) lists each field's bytes without the IndexOptions byte written since 5.0.0 and five elements added later, and its tables miss codes Lucene writes. Lucene reads its own files fine; anyone decoding .fnm from this javadoc misreads the first field.

The finding in 30 seconds

#

The javadoc that documents the default .fnm format lists a field record's bytes in an order the writer has not used since 5.0.0.

Background: the .fnm file and its javadoc grammar

#
  1. Every Lucene segment has one .fnm file. For each field it records the name and number and what is indexed for it: postings options, doc values, points, vectors.
  2. Each codec format class documents its file as a grammar in its class javadoc: an ordered list of named elements, each with a type (Byte, VInt, String, ...). The default codec's file-format overview links these pages "for details".

The finding, step by step

#
  1. You index one document with one text field, f = "a", with the default codec, and decode its .fnm file in the order the Lucene94FieldInfosFormat javadoc gives: FieldName, FieldNumber, FieldBits, DocValuesBits, DocValuesGen, ...
  2. You expect FieldName "f", FieldNumber 0 and FieldBits 0, then DocValuesBits 0, because the field has no doc values.
  3. The first three match, but the next byte is 3, which the javadoc's table reads as "SortedDocValues". From there every value is off: DocValuesGen reads -65536 instead of -1, the attribute count 49151 instead of 2, and the parse runs off the end of the file.
  4. Why: since 5.0.0 the writer puts an IndexOptions byte right after FieldBits (3 = DOCS_AND_FREQS_AND_POSITIONS). The javadoc lists its type but never placed it in the sequence. Later releases added a skip-index byte, PointIndexDimensionCount and three vector elements, also never placed.
  5. The tables are stale too: doc-values codes 4 and 5, FieldBits 0x8 and 0x10, IndexOptions 5 and VectorEncoding 2 are written but not listed. Lucene's reader matches its writer, so only the text is wrong.

Who is affected

#

People who read or re-implement the .fnm format from Lucene's documentation: ports to other languages, index inspectors, recovery tools. For them it fails on the first field of every default-codec .fnm that has at least one field. Lucene users who only call its APIs are not affected; nothing wrong happens at runtime.

Mechanism, terms and numbers674 words

The class javadoc of Lucene94FieldInfosFormat, the field infos format of the default codec (Lucene104Codec.java:72), gives the .fnm file as Header, FieldsCount, <FieldName, FieldNumber, FieldBits, DocValuesBits, DocValuesGen, Attributes, DimensionCount, DimensionNumBytes>^FieldsCount, Footer (Lucene94FieldInfosFormat.java:48-50 on main 645d4fe14a20). The writer (:431-456) writes, per field, FieldName, FieldNumber, FieldBits, IndexOptions, a doc-values type byte, a doc-values skip-index byte, DocValuesGen, Attributes, PointDimensionCount, PointIndexDimensionCount and PointNumBytes only when the dimension count is non-zero, then VectorDimension, VectorEncoding and VectorSimilarityFunction; the reader (:147-213) reads the same order.

IndexOptions is typed as a Byte (:58) but never placed; the skip-index byte and PointIndexDimensionCount appear nowhere; the vector elements are described (:104-118) but not placed. The tables miss written values: DocValuesBits is described as a norms nibble plus a doc-values nibble with codes 0..3 (:88-97), but the byte holds one code, and SORTED_SET is 4 and SORTED_NUMERIC 5; FieldBits lists 0x1, 0x2 and 0x4 but 0x8 (soft-deletes field) and 0x10 (parent field) are set; IndexOptions 5 (since 10.5.0) and VectorEncoding 2 (FLOAT16, main only) are missing.

A parser that follows the javadoc reads a text field's IndexOptions byte (3) as "SortedDocValues" and is misaligned from the first field on. The sequence has been wrong since 5.0.0: LUCENE-6013 moved IndexOptions into its own byte and updated the type list, not the sequence. Later changes edited parts of the javadoc (6.0.0 added the point elements to the sequence, 9.0.0 and 9.4.0 described the vector elements) but none placed IndexOptions or brought the sequence and the tables up to date. Documentation only; the fix is javadoc text.

The one-field example, byte by byte

#

For one TextField f = "a", the field record is 01 66 | 00 | 00 | 03 | 00 | 00 | ff ff ff ff ff ff ff ff | 02 ...(2 attributes)... | 00 | 00 | 01 | 00 (dumped by the fix's validation check, which parses it with the corrected grammar exactly to the footer):

  • Lucene reads: FieldName "f", FieldNumber 0, FieldBits 0, IndexOptions 3 (DOCS_AND_FREQS_AND_POSITIONS), doc values 0, skip index 0, DocValuesGen -1, 2 attributes (the per-field postings format and suffix), PointDimensionCount 0, VectorDimension 0, VectorEncoding 1 (FLOAT32), similarity 0 (EUCLIDEAN).
  • The javadoc's order takes 03 as DocValuesBits (low nibble 3 = SortedDocValues), the next 8 bytes, 00 00 ff ff ff ff ff ff, as DocValuesGen (-65536, not -1), and ff ff 02 as the attribute count (49151, not 2); reading 49151 map entries then throws java.io.EOFException at the end of the 153-byte file (the diagram's probe, assertions on and off). An independent verifier's literal-sequence test also measured -65536 for point and vector fields.

Also stale on the same page

#

The first line says "Lucene 9.0 Field Infos format." (:44); the field descriptions call the point elements PointDimensionCount and PointNumBytes (:102) while the sequence says DimensionCount and DimensionNumBytes; and the write() comment "pack the DV type and hasNorms in one byte" (:444) has been wrong since LUCENE-6006 (5.0.0).

Exposure and likelihood201 words
  • Who is hit. Anyone who decodes .fnm from the class javadoc instead of from read(): ports of Lucene to other languages, index inspectors, recovery or forensic tools, and developers learning the format.
  • Default vs opt-in. The default codec: Lucene104Codec installs this format (Lucene104Codec.java:72), and the file-format overview links this class for the .fnm file (lucene104/package-info.java:147, :243). Every field record carries the IndexOptions byte, so the mismatch shows on the first field of every default-codec .fnm with at least one field, whatever the field (a segment with no fields has no field record to misread).
  • Scale. A parser built from the sequence misreads the first field and every later one; one built from the tables rejects or misreads valid codes (any SORTED_SET or SORTED_NUMERIC field, any index with a soft-deletes or parent field). The hunt's grammar check found the documented grammar diverging on 125 of 125 .fnm files from 64 generated default-codec indexes, while the writer's layout parsed all of them to the footer.
  • What it does not do. No wrong results, no index change, no runtime path: Lucene's writer and reader agree, and TestLucene94FieldInfosFormat passes. No earlier report was found. Impact class minor, priority low.

Why it looks unintended

#
  • Written as an exact grammar, every element typed and linked to its writer method; the format overview points readers to it.
  • IndexOptions is typed as a Byte but never placed; the 2014 change that split it out updated only the type list.
  • The tables are wrong, not abbreviated: a norms nibble gone since 5.0.0, only 4 of 6 doc-values codes.
The full argument206 words
  • Contract text. Lucene94FieldInfosFormat.java:48-62: production notation with every element typed and linked to a DataOutput method. lucene104/package-info.java:50: "This document defines the index file formats used in this version of Lucene"; :188: "Details on each of these are provided in their linked pages."
  • History. In LUCENE-6013 (#7075, 2014) the author wrote "I'll update the javadocs for the format changes" and then "New patch, fixing docs"; the type list and the tables were updated, the sequence line was not, and none of the saved issue comments discusses the sequence, so this reads as an omission, not a decision. Later changes that added bytes or values changed the writer and reader together; some edited the javadoc (LUCENE-6861 put the point elements into the sequence, LUCENE-9322 and LUCENE-10577 described the vector elements), but none placed IndexOptions or the newer bytes, and none of their saved PR discussions mentions the stale sequence.
  • Tests. No test compares a format javadoc with the bytes. TestLucene94FieldInfosFormat tests codec behaviour (the BaseFieldInfoFormatTestCase round trips, and testVectorSimilarityFuncs checks SIMILARITY_FUNCTIONS directly) but never compares the javadoc grammar with the written bytes.
  • Precedent. Upstream has fixed file-format documentation errors of this kind before: LUCENE-713 (#1788), LUCENE-3072 (#4145), LUCENE-7532 (#8583, "Add back lost codec file format documentation").
The devil's-advocate check150 words

Strongest case for "intended" (the refute reviewer, the intended-lens cross-model reviewer and the devil's-advocate verifier; rated moderate): the format classes are @lucene.experimental (:121); LUCENE-2946 (#4020, 2012) moved the file-format docs from "bit-for-bit" to "high-level", and package-info.java:54 still says "This document attempts to provide a high-level definition"; the supported way to read .fnm is FieldInfosFormat.read; and the runtime round trip is tested.

Why it fails: in the same LUCENE-2946 thread rmuir wrote (2012-04-25) "we can go into detail, but we can't do bit-for-bit with even StandardCodec... For the simple metadata files, and even stored fields and postings its fine (for now)", and .fnm is such a simple metadata file. The page is presented in exact-looking production notation; its tables are wrong rather than abbreviated; and @lucene.experimental allows the format to change, not the current format to be described wrongly. Every verifier and the adjudication rejected the "intended" reading.

Suggested fix

#

Recommended A. Rewrite the grammar, type list and tables to match write()

Rewrite the class javadoc to match write(): place IndexOptions, the skip-index byte, the conditional point elements and the three vector elements; note how the older format versions differ; make the doc-values byte one code 0..5; add the missing codes. Javadoc only. Validated: it parses a 12-field segment to the footer; the suite and static checks pass.

Trade-offs

  • The ? marks for the two conditional point elements follow the notation the default postings format javadoc already uses (Lucene104PostingsFormat.java:104); the description says they follow only when PointDimensionCount is non-zero.
  • Renaming DocValuesBits to DocValuesType is the one cosmetic choice; keeping the old name gives a smaller diff, but the text must still say the byte is a single code.
  • DOCVALUES_SKIPPER = 0x20 (:479, a leftover of #13449 that #13784 replaced before any release) is never written, so the text leaves it out.
  • The grammar is the current writer layout (format version 2, FORMAT_CURRENT at :467-471, written at :424). read() also accepts versions 0 and 1 (:138-145): it reads the skip-index byte only from version 2 (:189-194) and rejects the 0x10 bit below version 1 (:165-176); FORMAT_CURRENT is 0 at the 9.4.0-9.9.2 tags and 1 at 9.10.0-9.12.3. The fix states this in one paragraph; the validation parses current-format files only.
  • If the open WIP PR #13525 (multi-vector) lands, it adds one more element to the same grammar.

LFV-942, snapshot of 2026-11-10

Registry title
The file-format javadoc of the default field infos format (Lucene94FieldInfosFormat) gives a wrong .fnm grammar: the per-field sequence leaves out IndexOptions, the doc-values skip-index byte, PointIndexDimensionCount and the three vector elements, and the value tables miss written values (doc-values codes 4 and 5, FieldBits 0x8 and 0x10, IndexOptions 5 since 10.5.0, VectorEncoding 2 on main) (documentation defect; the writer and reader agree)
Area
codecs / field infos (Lucene94FieldInfosFormat .fnm file-format javadoc vs its writer and reader)
Priority
Low, rank 1356: The default .fnm grammar has been wrong since 5.0 and misleads a re-implementer on the first field of every index.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so indexing, merging, CheckIndex and search are unaffected in every configuration; the people misled are those who read, inspect or re-implement the .fnm format from this class javadoc (Lucene104Codec installs this format and the default codec's package docs link it for the details), and a parser that follows the documented sequence misreads the first field of every .fnm the default codec writes, then every later field (executed); the sequence has been wrong in every release since 5.0.0 (2015), the doc-values value table since 4.2.0, and no scale or special setting is needed.
Summary
You decode a field infos (.fnm) file of the default codec by following the Lucene94FieldInfosFormat javadoc, which gives each field as FieldName, FieldNumber, FieldBits, DocValuesBits, DocValuesGen, Attributes, DimensionCount, DimensionNumBytes, documents DocValuesBits as a norms nibble plus a doc-values nibble with codes 0..3, and lists only FieldBits 0x1, 0x2 and 0x4. The writer instead puts an IndexOptions byte right after FieldBits, writes a single doc-values code (SORTED_SET = 4, SORTED_NUMERIC = 5) followed by a skip-index byte, writes PointIndexDimensionCount and PointNumBytes only when the dimension count is non-zero, appends VectorDimension, VectorEncoding and VectorSimilarityFunction, and sets FieldBits 0x8 (soft-deletes field) and 0x10 (parent field), so a parser built from the text reads the IndexOptions byte of a text field (3) as 'SORTED doc values' and loses alignment on the first field. Lucene's own reader matches the writer, so nothing breaks at runtime; only the documentation is wrong, and its sequence has been since 5.0.0.
