A RuntimeException while IndexWriter publishes a flushed segment drops the segment, and the next commit silently lacks acknowledged documents

If the IndexWriter's InfoStream throws an unchecked exception while a just-written segment is being added to the index, Lucene drops that segment but keeps the writer open and healthy-looking. The next successful commit() silently leaves out acknowledged documents although its returned sequence number covers them, and a plain close() commits the same loss.

The finding in 30 seconds

#

When a flush has written a new segment, IndexWriter publishes it: it pushes the segment's frozen deletes and updates, then adds it to segmentInfos. The flush queue removes the segment's ticket in a finally, even if publishing threw. A RuntimeException before the add (in practice, from the InfoStream) loses the written segment, and nothing marks the writer broken.

How IndexWriter publishes a flushed segment, in one minute

#
  1. Indexing threads buffer documents in memory. A flush writes each buffer to the directory (on disk, or in memory for a ByteBuffersDirectory) as a new segment and queues a flush ticket for it; the ticket also carries the deletes and doc-values updates frozen at that moment.
  2. Publishing takes the ticket at the head of the queue, pushes its frozen deletes and updates, and adds the segment to segmentInfos, the list a commit writes out. Only then is the segment part of the index.
  3. A failure while writing the segment, or while applying a published delete packet, is tragic: the writer closes itself, so the last commit stays the recovery point.

The finding, step by step

#
  1. Open an IndexWriter with the default config and an InfoStream that throws IllegalStateException once, on the first log message starting with publishFlushedSegment. addDocument returns sequence number 1.
  2. commit() writes the document to the directory as segment _0, then the log call throws while Lucene is adding _0 to the index. The flush queue removes _0's entry anyway.
  3. You expect the writer to close itself, as it does when writing a segment fails, or the next commit to contain every operation its sequence number covers.
  4. Instead isOpen() is true and getTragicException() is null. The retried commit() succeeds and returns 4, yet the index has 0 documents; _0's files sit in the directory unreferenced until the file deleter removes them, and no commit ever lists the segment.

Who is affected

#

Applications that turn on an InfoStream whose logging can throw an unchecked exception, and keep using the writer after the failed call: they retry the commit, keep indexing, or just close() it (default commitOnClose). The writer reports itself healthy. Without an InfoStream (the default) it cannot happen; one document is enough.

Mechanism, terms and numbers697 words

After a flush writes a new segment, IndexWriter publishes it from the flush ticket queue: DocumentsWriterFlushQueue.innerPurge hands the head ticket to IndexWriter's publish consumer (DocumentsWriterFlushQueue.java:99) and removes the ticket in a finally (:104), whether or not the consumer succeeded. The consumer marks the ticket published (IndexWriter.java:6271), writes InfoStream lines, pushes the ticket's frozen deletes and updates, and only then adds the segment to segmentInfos (:2990). A RuntimeException thrown before that add, in practice from an InfoStream whose logging throws, drops the fully written segment, and, before the global packet push, its deletes and doc-values updates. No caller treats a RuntimeException there as tragic, so isOpen() stays true and getTragicException() null, and the next successful commit() persists an index without documents its returned sequence number covers; a plain close() with the default commitOnClose commits the same loss. It reproduces on 11 releases from 4.0.0 to 10.6.0 and on main, and source history shows the same code in between. Making a failure of the publish step tragic fixes it, with two small hardening hunks for a logger that keeps failing; the fix was validated on main 5adff78bb168.

The bug

#
  1. A RuntimeException anywhere between markPublished() (IndexWriter.java:6271) and segmentInfos.add (:2990) leaves the consumer, and innerPurge's finally still removes the ticket (DocumentsWriterFlushQueue.java:104). The written segment is no longer in the queue and never reaches segmentInfos; nothing else refers to it.
  2. No caller treats it as tragic: prepareCommitInternal (IndexWriter.java:3879-3883), doFlush (:4427-4434), getReader (:711-719) and flushNextBuffer (:3765-3769) close the writer only for an Error. The exception simply propagates.
  3. What is lost depends on where the throw lands. Before the global packet push (the consumer's two lines, the first line of publishFlushedSegment), the ticket's frozen deletes and doc-values updates are lost too, so a delete of a committed document stays unapplied. After the push, only the documents are lost.
  4. The window holds six InfoStream call sites (an isEnabled plus a message each): IndexWriter.java:6281-6283, :6285-6287, :2965-2966 and :2985-2987; BufferedUpdatesStream.push (BufferedUpdatesStream.java:81-90), once per pushed packet, so up to twice; and FinishedSegments.finishedSegment (BufferedUpdatesStream.java:351-353), reached from IndexWriter.java:2983 when the segment has no segment-private deletes or updates, as in the repro. A throw at that last site loses the document the same way (executed in an independent fact check, which also showed that the recommended fix covers it). The messages' arguments are built only when the InfoStream is enabled; #6438 once saw segString throw while building such a message during close(). ensureOpen(false) (:2963) throws only on an already closed writer. No other RuntimeException source in the window was identified by reading the code (a reading, not a proof), and an Error there is already tragic.

The numbers

#

One empty document, default config, ByteBuffersDirectory, an InfoStream that throws once on the consumer's first line: addDocument returns 1; commit() throws IllegalStateException; then isOpen=true, getTragicException()=null, getDocStats().maxDoc=0 while getPendingNumDocs()=1, and _0.cfe, _0.cfs, _0.fdm, _0.fdt, _0.fdx, _0.fnm, _0.si are in the directory. The retried commit() returns 4 and the committed index has 0 documents. With the fix the same steps end with isOpen=false, getTragicException() = the IllegalStateException, pendingNumDocs=0.

Exposure and likelihood402 words
  • Who is hit. Applications that enable an InfoStream (off by default: InfoStream.NO_OUTPUT) whose logging can throw an unchecked exception: a custom InfoStream, Lucene's JavaLoggingInfoStream behind a java.util.logging handler or logging bridge that throws, or setInfoStream(PrintStream) with a stream whose println throws. lucene/MIGRATE.md (lines 1155-1168) recommends installing JUL handler wrapper libraries to feed Lucene's log events into the application's logging system, and points to JavaLoggingInfoStream for IndexWriter events; Log4j documents ignoreExceptions=false for passing appender failures to the caller (not executed here). PrintStream suppresses IOException, and the JDK's stream handlers report ordinary failures to their ErrorManager; a custom handler, bridge or InfoStream can still throw.
  • And keep the writer. The application must continue after the failed call: retry commit(), keep indexing, or close() with the default commitOnClose (the try-with-resources idiom). isOpen() is true and getTragicException() is null, the signals an application can check to decide whether the writer is still usable. rollback() right after the failure restores the last commit (assertions off; with them on, rollback() trips the assertion below, and the last commit is still intact).
  • What is lost. The whole flushed segment (every document buffered since the previous flush) and, for a throw before the global packet push, the deletes and doc-values updates frozen on its ticket. Earlier commits stay intact; the index stays structurally valid.
  • Executed entry points. commit() (the repro); flush() and an NRT DirectoryReader.open(writer) at three of the lines; prepareCommit(), flushNextBuffer() and openIfChanged in the fault-injection sweep; close() directly after the failed commit(), with no retry: with assertions off it returns normally and leaves an index with 0 documents; with them on it throws the pendingNumDocs assertion below, and the index still has 0 documents (executed on e1faeba08bde and, in the fact check, on 5adff78bb168).
  • Default vs opt-in. The default IndexWriterConfig apart from the InfoStream, one thread, assertions on or off; the only opt-in is the InfoStream. The repro uses an explicit ByteBuffersDirectory and the test framework's random codec, the plain main() probe the default codec; the window's code does not touch the directory or the codec. No scale is needed.
  • Side effect with assertions on (not claimed separately). When the throw comes before publishFlushedSegment is entered, its published == false fix-up never runs: getPendingNumDocs() stays 1 too high for the writer's life, and a later close() or rollback() fails with AssertionError: pendingNumDocs 1 != 0 totalMaxDoc (IndexWriter.java:2592-2597).

Why it looks unintended

#
  • commit(): "All sequence numbers <= this value will be reflected in the commit". The retried commit returns 4 but lacks the document added at 1.
  • LUCENE-5987: IndexWriter closes itself on an exception "that would otherwise cause silent data loss"; the segment write and the packet apply do.
  • setInfoStream states no no-throw rule; Lucene's own testExceptionDuringRollback throws from InfoStream.message.
The full argument279 words
  • commit(). "it returns the sequence number such that all indexing operations prior to this sequence will be included in the commit point, and all other operations will not" and "All sequence numbers <= this value will be reflected in the commit" (IndexWriter.java:4203-4204, :4208-4209). The retried commit returns 4; the addDocument (1) is not in it.
  • The design rule. LUCENE-5987 (#7049): "IndexWriter will now forcefully close itself on aborting exception (an exception that would otherwise cause silent data loss)." (lucene/CHANGES.txt:11614-11616). In that issue Michael McCandless called it "a ridiculous situation ... that IW can throw an exception and it turns out that exception silently just deleted tons of previously indexed documents and when you close/commit the IW, they are gone". The segment write (DocumentsWriterPerThread.java:585-589, maybeAbort :594-605) and the packet apply (onTragicEvent(t, "applyUpdatesPacket"), IndexWriter.java:2941) follow it; the publish step between them does not.
  • The trigger is legal input. IndexWriterConfig.setInfoStream(InfoStream) and setInfoStream(PrintStream) are public and say only "Must not be null" (IndexWriterConfig.java:426-446). TestIndexWriterExceptions.testExceptionDuringRollback throws a RuntimeException from InfoStream.message during rollback() and then asserts that the writer is closed and the index intact ("we are closed, no locks or files held, index in good state", TestIndexWriterExceptions.java:1980-2048).
  • The class javadoc says the writer closes itself "if you hit an Error, or disaster strikes during a checkpoint" (IndexWriter.java:162-165); nothing says a writer may stay open after silently dropping data.
  • The code expected the window to fail. LUCENE-8043 (#9091, 2017) added the published == false branch that gives back the document count when the segment was not added (IndexWriter.java:3031-3033). It fixed the count, not the dropped segment.
The devil's-advocate check344 words

The argument: a logger that throws breaks JDK conventions (PrintStream never throws IOException; java.util.logging.ErrorManager asks handlers to report problems to it instead of throwing); InfoStream is a "Debugging API" marked @lucene.internal (InfoStream.java:24, :28), and so is JavaLoggingInfoStream; and on open #9738 a maintainer (s1monw) wrote in 2019 that exceptions from doFlush(), getReader(), flushNextBuffer() and prepareCommitInternal() "might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback()". Later in that thread the same maintainer wrote "if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss": calling rollback() after a failed commit is an established maintainer position. A maintainer may also quote addDocument's javadoc ("if an Exception is hit (for example disk full) then the index will be consistent, but this document may not have been added", IndexWriter.java:1465-1466) or close()'s ("If this method throws any other exception, the IndexWriter will be closed, but changes may have been lost", :1351-1352).

Why it fails: (1) no Lucene document states a no-throw rule, the PrintStream overload is a public convenience method, and Lucene's own test throws from InfoStream.message and expects a consistent writer; (2) the rollback() stance is in no javadoc, the same maintainer added "I am all for making it even more strict" and, later in the thread, suggested closing the writer automatically rather than letting users continue, and it does not cover close() with the default commitOnClose, which commits the loss with no retry (executed); (3) the writer tells the caller it is healthy, and with assertions on Lucene's own pendingNumDocs invariant breaks, so this is not a designed state; (4) an Error at the same lines is tragic, so the outcome depends only on the exception's class; (5) the javadoc lines do not apply: addDocument returned normally with sequence number 1, and close() here returns normally. Verdict: not intended, a defect; the trigger is narrow, which the priority reflects.

Suggested fix

#

Recommended A: the publish consumer makes any failure tragic, and the tragic path survives a failing logger

In IndexWriter.publishFlushedSegments, catch any failure of the publish step: give back the pending document count if publishFlushedSegment was never entered, fire onTragicEvent and rethrow; for a logger that keeps failing, also record the tragedy before logging it and log the rollback inside its try. The writer then closes itself. Validated: the repro, the index tests and :lucene:core:check pass.

} catch (Throwable t) {
  // the purge removes this ticket whether or not it was published; a failure before its
  // segment and updates are published would lose them silently, so this is tragic
  if (newSegment != null && publishEntered == false) {
    // once entered, publishFlushedSegment gives back the pending docs itself
    adjustPendingNumDocs(-newSegment.segmentInfo.info.maxDoc());
  }
  onTragicEvent(t, "publishFlushedSegment");
  throw t;
}
// A2, onTragicEvent: this.tragedy.compareAndSet(null, tragedy) before the log call
// A2, rollbackInternalNoCommit: move the "rollback" log line inside the try

How it closes the writer: onTragicEvent records the tragedy and "can be called from any location without respecting any lock order" (IndexWriter.java:6062-6063); the entry point's maybeCloseOnTragicEvent() in its finally then rolls the writer back (for commit(), IndexWriter.java:3883 in prepareCommitInternal). That holds for the repro's one-shot failure. A logger whose output fails (a full log disk, say) may well fail on every message for a while, and two places on that path log before they act: onTragicEvent logs "hit tragic ..." before it records the tragedy, and a throw there is only added as suppressed (IndexWriter.java:6074-6082); rollbackInternalNoCommit logs "rollback" before its try (:2602-2604). A probe whose InfoStream throws on every message from the first publishFlushedSegment line until the failed commit() has returned (assertions off): on stock main and with A1 alone the tragedy is not recorded, the writer stays open and the retried commit returns 4 with 0 documents; with A1 and only the first hardening hunk the writer refuses the retried commit but is left half closed, and close() had not returned after 15 s (shouldClose, :1374-1393); with the whole fix A the writer closes itself, the retried commit throws AlreadyClosedException and close() returns (assertions on and off). Trade-offs

Coarse: it also turns a failure after segmentInfos.add (in checkpoint() or the fully-deleted check, IndexWriter.java:2992-3028), where the segment is kept today, into a tragic close. That is stricter than needed but consistent with the class javadoc's "disaster strikes during a checkpoint". A narrower variant fires the tragic event only when the segment was not added (for example by having publishFlushedSegment report whether it reached the add). For a deletes-only ticket the packet is already in the update stream when either of its log lines runs, and the retried commit still applies the delete (executed); A makes such a throw tragic too.

What the checks validated

With gradle on 5adff78bb168: A1 and the whole fix A each pass the repro on and off, the org.apache.lucene.index tests (1,398 with A1; 1,399 with the whole fix, including the finished packet variant) and :lucene:core:check -x test. A persistent-logger probe shows that A1 alone does not hold when the logger keeps failing and that the whole fix does. An earlier form of the same change passed the repro on main e1faeba08bde, and in a 5,128-case fault-injection re-run with it (plus the fixes for three other commit and flush sites, including LFV-1078's) the publish-step loss rows were gone.

B (not run): remove the ticket only after a successful publish, and retry

#

innerPurge would poll() only when the consumer returned normally; a failed ticket would be published again later.

Trade-offs

Keeps the writer open without loss, but markPublished() asserts a ticket is published once (DocumentsWriterFlushQueue.java:157-160), a partial publish (global packet already pushed) would have to be made idempotent, and a persistent failure would block every later ticket behind the head, so it still needs a bound and a tragic fallback. A larger change.

C (not run): move or guard the log lines in the window

#

Log after segmentInfos.add, or catch exceptions from the InfoStream calls in the window.

Trade-offs

Removes the exercised trigger, but any future RuntimeException between markPublished() and the add brings the loss back; it does not restore the invariant.

D (documentation only): state that callers must rollback() after any exception from commit, flush or reopen

#

Write the stance from #9738 into the javadoc.

Trade-offs

Does not fix close() with the default commitOnClose, which commits the loss, nor the isOpen() and getTragicException() signals that tell the caller the writer is fine.

Downstream note

#

Downstream, a product that routes Lucene's InfoStream into a logging framework set to pass appender failures to the caller, and keeps the writer after a failed commit or reader reopen, could silently lose acknowledged writes.

How it was found

#

A bounded fault-injection sweep threw one exception at each call of a public extension point (every InfoStream call included), one at a time, during commit, flush and NRT reopen, then checked that the writer closed itself or the retried commit kept every acknowledged operation. It flagged the publish step's log lines; code reading gave the mechanism.

The method in full216 words

Method: semi-formal (bounded-exhaustive single-fault injection on the real lucene-core jar), on main e1faeba08bde, 2026-11-02; then code reading and a one-test reduction.

  • The sweep ran a fixed small workload, injected one exception (a RuntimeException or an Error) at the k-th call of a public extension point, every InfoStream.message and InfoStream.isEnabled call of every component included, for six failing APIs (commit, prepareCommit, DirectoryReader.open(writer), openIfChanged, flush, flushNextBuffer) and six writer configurations: 15,072 cases with assertions off. Each case was checked against one oracle: the writer closed itself (tragic), or the retried commit holds every acknowledged operation.
  • 432 cases lost data at the publish step's InfoStream calls (the consumer's two lines, publishFlushedSegment's two, BufferedUpdatesStream.push's one), all with a RuntimeException; the sixth call site, FinishedSegments.finishedSegment, was not reached in the window by the sweep's workload, whose flushed segments all carried segment-private updates; an Error at the same calls was tragic. Reading DocumentsWriterFlushQueue.innerPurge showed why: the ticket is removed in a finally.
  • The case was reduced to the one public-API JUnit test of this page. An independent reproducer wrote its own test from the claim alone (it throws on the last line before the add, "publish sets newSegment") and got the same loss on 20 of 20 seeds.

Searches5 searches

In the documented searches, no Lucene issue, PR, JIRA entry or list thread, and nothing outside Lucene, describes this defect. Related prior items, each about a different defect:

  • #9738 (LUCENE-8692, open, 2019): "IndexWriter.getTragicException() may not reflect all corrupting exceptions (notably: NoSuchFileException)". A test that corrupts index files under a running writer showed exceptions with no tragic event, so Solr did not give up leadership after a failed commit. In its discussion a maintainer (s1monw) lists doFlush(), getReader(), flushNextBuffer() and prepareCommitInternal() among methods whose non-tragic exceptions "might cause documents go missing", with rollback() as the remedy. A general design remark: it names no publish step, no ticket queue, no trigger and no fix, and nothing about a later commit that succeeds while its sequence number covers the lost documents.

History

#

Introduced by LUCENE-2956 (2011), whose flush-ticket queue removed a ticket before publishing it; first release 4.0.0. Since 5.0.0 (LUCENE-5987) a failed segment write closes the writer but this step was left out. It reproduces on 11 releases through 10.6.0 and on main, and source history shows the same code in between; not fixed upstream as of 2026-11-04.

LFV-1082, snapshot of 2026-11-06

Registry title
If the IndexWriter InfoStream throws a RuntimeException while a flushed segment is being published, IndexWriter drops that already written segment (and, for some log lines, the deletes and doc-values updates on its flush ticket) but stays open, so the next successful commit silently lacks acknowledged documents its sequence number covers (every release since 4.0.0)
Area
index / IndexWriter flush publishing (IndexWriter.publishFlushedSegments, IndexWriter.publishFlushedSegment, DocumentsWriterFlushQueue.innerPurge)
Priority
Medium, rank 113: If the opt-in InfoStream throws an unchecked exception inside the flush publish window and the application keeps the writer or closes it without rollback, an already written segment is dropped, so the next successful commit or close silently lacks acknowledged documents, in every release since 4.0.0. The trigger is contrived, but the durable silent data loss keeps it in Medium.
Impact class
data corruption
Impact note
Hits applications that enable IndexWriter's opt-in InfoStream (a custom InfoStream, the shipped JavaLoggingInfoStream behind a java.util.logging Handler or logging bridge, or setInfoStream(PrintStream) with a PrintStream subclass) whose logging throws an unchecked exception on one of the six log call sites while a flushed segment is being published, and that then keep using the writer or close it with the default commitOnClose: the failing commit(), prepareCommit(), flush(), flushNextBuffer() or NRT open is loud, but afterwards isOpen() is true and getTragicException() is null, and the next successful commit() (or close() [exec, -da]) silently lacks the acknowledged documents of the dropped segment, plus its buffered deletes and doc-values updates when the throw comes before the global packet is pushed; no scale is needed, an Error at the same lines is already tragic, the default configuration (InfoStream.NO_OUTPUT) cannot reach it, and every release from 4.0.0 to 10.6.0 and main is affected [exec].
Summary
You enable IndexWriter's InfoStream, add a document and commit, and the logging call for one of the 'publish' lines of that commit throws an unchecked exception (executed: a java.util.logging Handler behind Lucene's JavaLoggingInfoStream that fails once); commit() throws, and the writer stays open with no tragic exception. You expect either the writer to close itself, as it does when the segment flush itself fails or a published delete packet fails to apply, or the next successful commit to contain every operation its returned sequence number covers. Instead the segment was already fully written and its flush ticket is removed from the queue whether or not it was published, so the segment never joins the index: the retried commit returns seqNo 5, above the addDocument's seqNo 2, yet the committed index has 0 documents.
