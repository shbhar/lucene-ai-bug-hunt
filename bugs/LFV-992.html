The analysis-icu overview's tokenizer and collation examples call APIs removed since Lucene 4.0

Four of the ten "Example Usages" on the analysis-icu overview call APIs Lucene removed between 4.0 and 10.0, such as new IndexSearcher(dir, true), so copied code does not compile: 14 error lines on 10.6.0. On main a 2025 re-indent also broke the Serbian example: 5 of 10 blocks, 16 lines.

The finding in 30 seconds

#

The page's "Example Usages" are plain code blocks in the module's javadoc overview; no build step compiles them, so API removals elsewhere never broke the build.

  1. You copy the "Danish Sorting" example from the analysis-icu overview into a project on Lucene 10.6.0. It indexes HAT, HUT, HÅT, HØT and HOT and should list them in Danish order.
  2. You expect it to compile, as the page's short token-filter examples (NFC, case folding, accents, Traditional-Simplified) do.
  3. Instead javac reports 7 errors on 6 lines: Field.Index (removed in 6.0), new IndexSearcher(dir, true) and the int SortField.STRING (4.0), sort.setSort (9.0), search(query, null, 1000, sort) (6.0) and searcher.doc(int) (10.0).
  4. The tokenizer, Farsi range and Turkish case examples fail the same way: 4 of 10 blocks and 14 error lines on 10.6.0. On main the Serbian example's comment became a bare sentence, so 5 of 10 blocks and 16 lines fail.
  5. Renaming alone is not enough: with current names the Danish example compiles but throws IllegalStateException: unexpected docvalues type NONE, because sorting needs doc values. Rewritten with the current API plus an ICUCollationDocValuesField, all 10 blocks compile and the 3 collation examples pass their own checks.

Who is affected

#

Developers who adopt the opt-in analysis-icu module and copy an example from its overview. Every release since 4.0.0-ALPHA (2012) ships at least 3 broken examples, 4 since 5.0.0. Documentation only: nothing in Lucene runs differently, and the errors are loud at compile time.

Mechanism, terms and numbers574 words

The analysis-icu module overview, the first page of the module's javadoc, shows ten Java blocks under "Example Usages". Four of them call APIs that Lucene removed between 4.0 and 10.0: the tokenizer example (new ICUTokenizer(reader)) and the Farsi range, Danish sort and Turkish case collation examples (Field.Index.ANALYZED, new IndexSearcher(dir, true), QueryParser.setAnalyzeRangeTerms, the Filter-taking search(query, null, n[, sort]), Sort.setSort (new Sort() itself still exists), the int SortField.STRING, IndexSearcher.doc(int)). On main a fifth is broken: a 2025 editorconfig re-indent (#14832) left the Serbian transliteration example's comment as // followed by a bare sentence. Compiled verbatim with the imports and the page's two undeclared names supplied, the page gives 16 error lines in 5 of 10 blocks on main and 14 lines in 4 blocks on 10.6.0; the other blocks compile. The examples were last current on trunk in 2011, so every release since 4.0.0-ALPHA has shipped at least three broken ones. Rewritten with the current API, and with doc values for the Danish sort, all ten compile and the three collation examples pass their own assertions. Nothing in Lucene behaves wrongly; only the page is stale.

The Danish sort also needs doc values

#

Sorting by SortField.Type.STRING reads SORTED doc values, and the example indexes the values only as TextField terms. With the names updated and nothing else, it compiles and throws IllegalStateException: unexpected docvalues type NONE for field 'contents' (expected=SORTED). The module's ICUCollationDocValuesField(String, Collator) (ICUCollationDocValuesField.java:50) stores the collation key as a sorted doc value; with it the sort gives the Danish order the example asserts (tracers A, E, B, D, C). vsop-479 made the same doc-values point on #16904 for the java.text copy of this example.

Related, not this bug

#

A current-API Farsi range written with the classic QueryParser gets its bounds from Analyzer.normalize, which for ICUCollationKeyAnalyzer returns UTF-8 bytes instead of collation keys: that is the separate code bug LFV-1053. The suggested fix builds the range as a TermRangeQuery over collation keys, as TestICUCollationKeyAnalyzer.java:44-50 does.

Exposure and likelihood132 words
  • Who. Readers of the analysis-icu javadoc overview who copy an example. No query, document or index file reaches the page, and the page is not in the runtime jar.
  • Default vs opt-in. analysis-icu is an optional module. No configuration or special input is involved.
  • Scale. Every example on the page that indexes or searches is broken: the three collation examples in every release since 4.0.0-ALPHA, the tokenizer example since 5.0.0, the Serbian example on main.
  • Not obvious to repair. The Danish sort also needs doc values (otherwise an IllegalStateException at run time), and the QueryParser form of the Farsi range is affected by the separate bug LFV-1053.
  • Not claimed. Any runtime defect in Lucene. The page leaves reader and tokenizer undeclared; that is normal for fragments and not part of the claim.

Why it looks unintended

#
  • The page offers them as "Example Usages", with no note that they target an old release.
  • Each failing line calls a removed API, except the main-only Serbian lines (a 2025 re-indent slip); the other 5 examples compile.
  • Maintainers fix such snippets: a 2012 commit fixed the java.text copy of these examples, and open PR #16904 is fixing it again.
The full argument204 words
  • Offered as working code. Each section heads its code with "Example Usages" (overview.html:71, :110, ...); nothing on the page says the code targets an old release or is pseudocode.
  • Drift, not design. 308e0bd4a9d (LUCENE-2514/LUCENE-2551, 2011-02-28) last rewrote the collation examples for the then trunk API, and every API they call existed then. Each later removal left the page alone, and none of the removing issues mentions it.
  • Precedent. 647b5091697 (2012-09-12, "code snippet improvements: fix out of date api usage ...") fixed IndexSearcher(dir, true) and Field.Index in the java.text twin of these examples and left this page as it was. On LUCENE-8481 (#9527, 2018), which named this file as a RAMDirectory user, Dawid Weiss wrote "I agree we should fix javadocs too, they're stale" and Adrien Grand "+1 to address consistency issues as a follow-up?". LUCENE-6112 fixed a non-compiling package example as a documentation bug. Open PR #16904 is fixing the java.text twin again.
  • The Serbian break is a slip. #14832 ("style: fix indents inconsistent with editorconfig and validate in CI", 129 files) turned the page's 8 /** ... */ comments into // comments; 7 came out valid, only the Serbian one became an empty // followed by the sentence as code.
The devil's-advocate check150 words

Strongest case for "not a bug": the blocks are fragments without imports that Lucene never promises to compile; the removals were deliberate and documented in CHANGES and MIGRATE; and ICUTokenizer is @lucene.experimental (ICUTokenizer.java:38), so its API may change. A cross-model reviewer (OpenAI GPT-5.6) rated this case "moderate".

Why it fails: with the imports and the two undeclared names supplied, the page's other five blocks and current-API rewrites of the failing ones compile, so the failures come from the page text. Apart from the main-only Serbian lines (a 2025 re-indent slip, #14832), they are calls to APIs that no longer exist, which no reader can fix by adding context. @lucene.experimental allows the API to change; it does not make the shipped example current, and the collation examples use core and queryparser API that is not experimental. Every verifier and the adjudication rejected the case: a documentation defect, minor.

Suggested fix

#

Recommended Rewrite the five blocks with the current API (validated)

One file, +27/-25: ICUTokenizer() + setReader, TextField/StoredField, IndexSearcher(DirectoryReader.open(dir)), search(query, n[, sort]), SortField.Type.STRING plus an ICUCollationDocValuesField for the Danish sort, a TermRangeQuery over collation keys for Farsi, one // line for Serbian. Then all 10 blocks compile, the 3 collation examples pass, and renderJavadoc and the module tests pass.

Rewrite the five blocks with the current API (validated) (recommended)

#

Javadoc only, lucene/analysis/icu/src/java/overview.html, +27/-25:

  • tokenizer: new ICUTokenizer(), then tokenizer.setReader(reader);
  • the three collation examples: TextField / StoredField instead of Field.Index, new IndexSearcher(DirectoryReader.open(dir)), search(query, 1000[, sort]);
  • Farsi: new TermRangeQuery("content", lower, upper, true, true) with bounds new BytesRef(collator.getCollationKey(...).toByteArray()), as TestICUCollationKeyAnalyzer does (not QueryParser, because of LFV-1053);
  • Danish: new Sort(new SortField("contents", SortField.Type.STRING)), an ICUCollationDocValuesField("contents", collator) per document (as vsop-479 pointed out on #16904 for the java.text copy), searcher.storedFields().document(...);
  • Serbian: one line, // This filter will map Serbian Cyrillic to Serbian Latin according to BGN rules.

None for users: documentation only, and no CHANGES entry is strictly needed. The Farsi example no longer shows QueryParser; that is deliberate until LFV-1053 is fixed. Updating the names without the doc values is not enough: the Danish example then throws IllegalStateException at run time.

Registry title
analysis-icu overview page: the ICUTokenizer example and the three collation examples (Farsi range, Danish sort, Turkish case) call APIs removed between Lucene 4.0 and 10.0, and on main the Serbian transliteration example is not valid Java (documentation defect)
Area
analysis-icu / module overview documentation (overview.html 'Example Usages')
Priority
Low, rank 1210: The analysis-icu overview's broken examples are a loud compile-time documentation defect with no runtime effect, on a module page with a small audience, so it is Low.
Impact class
minor
Impact note
Documentation only, with no runtime effect: a developer who adopts the opt-in analysis-icu module by copying the examples on its overview page gets compile errors in 3 of the page's 10 example blocks in 4.0.0-ALPHA to 4.10.4, in 4 blocks from 5.0.0 to 10.6.0 (14 error lines from 10.0.0 on) and in 5 blocks (16 error lines) on main, where a 2025 re-indent also broke the Serbian block's comment; the page's other 5 blocks compile, and no configuration, scale or special input is involved.
Summary
You read the analysis-icu module overview, which offers 'Example Usages' for ICU tokenization, collation and transliteration, and copy one into your code. The tokenizer example and the Farsi range, Danish sort and Turkish case collation examples do not compile on any current release, because they call APIs Lucene removed between 4.0 and 10.0 (new ICUTokenizer(reader), Field.Index.ANALYZED, new IndexSearcher(dir, true), QueryParser.setAnalyzeRangeTerms, the Filter-taking search methods, Sort.setSort, IndexSearcher.doc(int)), and on main the Serbian transliteration example has a bare, uncommented sentence in its code. Rewritten with the current API (and, for the Danish sort, doc values) the examples compile and do what the page says, so only the page is wrong.
