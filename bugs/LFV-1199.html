PackedInts.getWriterNoHeader's documented unknown-count mode (valueCount -1) throws for PACKED once mem is 127 bytes or more, the default buffer included

PackedInts.getWriterNoHeader documents valueCount = -1 for an unknown count, but for PACKED with any mem of 127 bytes or more (default 1024 included) the writer sizes its buffers for 0 (or -1) values and throws, on the first add or in the factory. Only direct callers are hit.

The finding in 30 seconds

#

The writer's buffers hold iterations groups of values. computeIterations first divides mem by the cost of one group, then applies a cap whose comment speaks of readers, which always know their count: never allocate more groups than the values need. With -1 that cap asks for ceil(-1 / 8) = 0 groups, so the buffers are empty.

Background in three steps

#
  1. PackedInts stores numbers with a fixed number of bits each, back to back. At 7 bits per value, 8 values fill exactly 7 bytes: one group, or "iteration".
  2. PackedWriter collects values in two buffers before encoding them, and mem is how many bytes those buffers may use. One iteration at 7 bits costs 7 output bytes plus 8 longs (64 bytes): 71 bytes.
  3. getWriterNoHeader(out, format, valueCount, bitsPerValue, mem) takes valueCount = -1 to mean "unknown: keep accepting values until finish()".

The finding, step by step

#
  1. Create a headerless packed writer for 7-bit values without knowing the count, as the javadoc allows: getWriterNoHeader(out, PACKED, -1, 7, DEFAULT_BUFFER_SIZE), a 1024-byte buffer.
  2. You expect add(5), finish() and a read-back to return 5, as they do with mem = 0 or with a known count.
  3. To size its buffers the writer calls computeIterations(-1, 1024). The budget allows 1024 / 71 = 14 iterations of 8 values, but a cap whose comment speaks of the reader ("don't allocate for more than the size of the reader") treats -1 as a count and returns ceil(-1 / 8) = 0.
  4. Both buffers have length 0, so the first add(5) throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0, with assertions on or off. At 8, 16, ..., 64 bits the cap returns -1 and the factory throws NegativeArraySizeException.
  5. For PACKED every width fails once mem reaches 127 bytes; mem = 0 works. Nothing is written before the throw.

Who is affected

#

Only code that calls the internal PackedInts.getWriterNoHeader itself with valueCount = -1 and, for PACKED, a mem of 127 bytes or more (less for most widths). Lucene never uses the -1 mode: its only caller passes a real count and mem = 1. It fails loudly before writing anything; mem = 0 or a known count avoids it.

Mechanism, terms and numbers456 words

The javadoc of PackedInts.getWriterNoHeader says you can start writing without knowing how many values will follow: "just pass -1 as valueCount" (PackedInts.java:745-746). The writer sizes its buffers with BulkOperation.computeIterations(valueCount, mem), whose cap "don't allocate for more than the size of the reader" (BulkOperation.java:174-176) treats -1 as a real count and returns 0 iterations, or -1 at 8, 16, ..., 64 bits per value.

At 7 bits per value and mem = PackedInts.DEFAULT_BUFFER_SIZE (1024) the writer gets zero-length buffers, and the first add(5) throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 at PackedWriter.java:63, with assertions on and off. It happens whenever mem is at least b + 8v bytes (71 at 7 bits, at most 127 for any PACKED width); mem = 0 and known counts work. No Lucene code uses the -1 mode, so only code that calls this @lucene.internal writer itself is hit, and it fails loudly before writing anything. Every release from 4.0.0-BETA (2012) to 10.6.0 has it.

The mechanism (main 5adff78bb168)

#
  1. The writer (PackedWriter.java:38-49) calls iterations = encoder.computeIterations(valueCount, mem) (:43) and allocates nextBlocks = new byte[iterations * byteBlockCount] and nextValues = new long[iterations * byteValueCount] (:44-45). At 7 bits per value b = 7 bytes and v = 8 values per iteration.
  2. The budget (BulkOperation.java:170): iterations = mem / (b + 8v) = 1024 / 71 = 14.
  3. The cap (:174-176, "don't allocate for more than the size of the reader"): if (iterations - 1) * v >= valueCount, return ceil(valueCount / v). With valueCount = -1 the test 13 x 8 = 104 >= -1 always holds, so it returns (int) Math.ceil(-1.0 / 8) = 0.
  4. The throw: both buffers have length 0, so the first store nextValues[off++] = v (PackedWriter.java:63) fails. At 8, 16, ..., 64 bits v = 1, the cap returns -1, and new byte[-b] (:44, -1 at 8 bits) throws NegativeArraySizeException in the factory.
  5. Exactly when: the cap runs only when iterations >= 1, that is mem >= b + 8v. The largest b + 8v for PACKED is 63 + 64 = 127 (63 bits per value), so from 127 bytes every width fails; at 7 bits it starts at 71 bytes. Below the threshold iterations is 0, the method returns 1 and the mode works: mem = 0 works for all 64 widths, and at mem = 64 the odd widths still work.

PACKED_SINGLE_BLOCK was not tested and has other group sizes (at 1 bit, b + 8v = 8 + 8 x 64 = 520 bytes; BulkOperationPackedSingleBlock.java:28-52), so every threshold here is for PACKED only.

Exposure and likelihood139 words
  • Who: code that calls the public static PackedInts.getWriterNoHeader with valueCount = -1 and mem >= b + 8v (for PACKED, any mem of 127 bytes or more, DEFAULT_BUFFER_SIZE included). PackedInts is @lucene.internal (PackedInts.java:27-34); the method is marked "Expert" and @lucene.internal (:727, :763).
  • Not hit: Lucene itself. The only non-test caller, Lucene90CompressingTermVectorsWriter.java:472-474, passes a real count (numDistinctFields) and mem = 1; the other computeIterations caller, PackedReaderIterator.java:46, always has a real count; TestPackedInts.java:108 draws counts from 1 to 600. No index, codec, query or search path is affected.
  • Effect for a direct caller: an exception on the first add (or in the factory) before any byte reaches the DataOutput; nothing is written wrongly.
  • Since: 4.0.0-BETA, the first release with this API; our keyword searches found no report of it.

Why it looks unintended

#
  • The javadoc offers -1 for an unknown count and describes mem only as a speed setting.
  • The same 2012 commit handles -1 on purpose in four other places; only the cap, whose comment speaks of the reader, treats it as a count.
  • The mode works with mem = 0 for all 64 widths, and fails with assertions off too.
The full argument203 words
  • The contract. "It is possible to start writing values without knowing how many of them you are actually going to write. To do this, just pass -1 as valueCount." (PackedInts.java:745-746). Nothing ties -1 to a buffer size: mem "lets you control how much memory can be used to buffer changes" and "High values of mem are likely to improve throughput" (:751-754); DEFAULT_BUFFER_SIZE is the library's own default (:49).
  • -1 is a designed sentinel. The Writer constructor asserts valueCount >= 0 || valueCount == -1 (PackedInts.java:609), fastestFormatAndBits maps -1 to Integer.MAX_VALUE (:188-190), and PackedWriter.add and finish have valueCount != -1 branches (PackedWriter.java:60, :73). All came with LUCENE-4161, the same commit as the cap.
  • The cap's comment speaks of the reader. It says "the size of the reader", and a reader always has a real count. PackedWriter calls the same method, and the method and that call came in the same commit, so this shows how the cap is phrased, not what its author meant.
  • No restriction anywhere. The mode works at mem = 0 for all 64 widths, and no CHANGES or MIGRATE entry, test or later commit limits it.
The devil's-advocate check172 words

"This is dormant internal documentation." PackedInts and getWriterNoHeader are @lucene.internal, nothing in Lucene or its tests passes -1, and the failure is loud. An independent reviewer from another model family (OpenAI GPT-5.6) returned not real on exactly this scope argument, after reproducing the bug with its own test and agreeing on the cause and the fix, and added that a maintainer "may still choose to fix it as internal cleanup or remove/clarify the dormant internal documentation".

Our answer (a judgment; the maintainers decide): @lucene.internal waives API stability, not correctness, and the -1 mode is spelled out in the method's own javadoc and coded for in four places. The inputs are the documented sentinel and the library's default buffer size, not absurd values, and the failure happens with assertions off. Scope lowers the priority (Low, latent); it does not make the behaviour intended. If the maintainers would rather drop the mode, fix B does that; for an unused internal mode that is at least as likely an outcome as fix A.

Suggested fix

#

Recommended A. Apply the cap only to a known count

Suggested: apply the cap only to a known count, valueCount >= 0 && (iterations - 1) * byteValueCount() >= valueCount, in the generator template, then regenerate BulkOperation.java and its checksums. The repro and all packed tests pass. Dropping the -1 mode and rejecting negative counts (B) is the alternative.

    } else if (valueCount >= 0 && (iterations - 1) * byteValueCount() >= valueCount) {
All options and trade-offs2 options · 505 words

Two options, both run with gradle in a scratch worktree of 5adff78bb168. A keeps the documented mode with a one-condition change; B removes the mode, which Lucene does not use. BulkOperation.java is generated, so A edits the template gradle/regenerate/packed/gen_BulkOperation.py (read by lucene/core/build.gradle:280-288) and runs ./gradlew :lucene:core:regeneratePacked64SingleBlock, which rewrites BulkOperation.java and the SHA-1s in lucene/core/src/generated/checksums/regeneratePacked64SingleBlock.json; check runs regeneratePacked64SingleBlockChecksumCheck. An older copy of the template at lucene/core/src/java/org/apache/lucene/util/packed/gen_BulkOperation.py:78 has the same line; the build does not read it.

A. Apply the cap only to a known count (validated by the checks) (recommended)

#

In computeIterations (template gradle/regenerate/packed/gen_BulkOperation.py:78, generated BulkOperation.java:174), guard the cap; then run ./gradlew :lucene:core:regeneratePacked64SingleBlock:

Trade-offs

  • With -1 the writer uses the full budget (14 iterations at 7 bits and 1024 bytes); known counts and the reader behave exactly as before.
  • The regeneration changes only the template, BulkOperation.java and the two SHA-1s in the checksums file.
  • A variant that avoids the generated file: map -1 to Integer.MAX_VALUE in PackedWriter's constructor, as fastestFormatAndBits does. Not run.

  • With fix A, all of org.apache.lucene.util.packed (TestPackedInts 28, TestDirectMonotonic 9, TestDirectPacked 6, plus the repro): 44 tests, 0 failures, 3 skipped (two @Ignored, one @Nightly), assertions on and again off; the @Nightly backward-codecs TestLegacyPackedInts (getWriterNoHeader with random mem) passes 3 of 3 with -Ptests.nightly=true.

B. Drop the -1 mode: remove the javadoc sentence and reject a negative count (packed tests, validated with assertions on only)

#

In getWriterNoHeader (PackedInts.java:765-768), throw for a negative count, and keep only the padding sentence of the javadoc (:745-749):

    if (valueCount < 0) {
      throw new IllegalArgumentException("valueCount must be >= 0, got " + valueCount);
    }

Trade-offs

  • Matches how Lucene uses the writer (always with a real count), but removes a documented feature: an external caller that uses -1 with mem = 0, which works today, breaks.
  • The -1 branches in PackedWriter become dead code a full clean-up would remove (not in the diff); the PackedInts.Writer assert stays reachable from outside subclasses. A real B change must also turn the regression test into an expectThrows test; the diff does not, so in the runs below the unchanged test fails by design.

Downstream note

#

Only downstream code that calls this internal writer with valueCount = -1 is affected, and it gets an exception, not wrong data; Lucene's own indexing and search paths never use the mode.

How it was found

#

Semi-formal: a proof-obligation audit of BulkOperation.computeIterations against its caller PackedWriter, which must get at least one iteration for every argument that lets values be added (a count >= 1, or -1). The documented valueCount = -1 breaks that obligation once mem covers one iteration; a one-test JUnit repro on stock main witnessed it.

The method in full109 words
  • Obligation: for every valueCount that lets values be added (a count >= 1, or -1) and every mem, computeIterations returns at least 1, so PackedWriter's buffers can hold a value (a count of 0 correctly gets 0 iterations). The reader side states the same thing as assert valueCount == 0 || iterations > 0 (PackedReaderIterator.java:47).
  • Finding: the cap at BulkOperation.java:174-176 divides valueCount by v without excluding -1, so it returns 0 or -1 whenever mem >= b + 8v.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
