PositiveScoresOnlyCollector gets the hits wrong when it wraps a collector that needs no scores

Around a collector that needs no scores, PositiveScoresOnlyCollector checks placeholder scores and lets a counter skip its check: sorted by a field, g:y returns 0 of its 6 positive hits, and counting (f:x)^0, where every score is 0, gives 12. The cause dates from 5.1.0 (the count half from 9.3.0); around a scoring collector it works.

The bug in 30 seconds

#

PositiveScoresOnlyCollector wraps another collector and passes on only the hits whose score is above 0. To check a score it needs real scores, but it tells the searcher it needs whatever the wrapped collector needs, and it hands the wrapped collector the Weight.

  1. Index 12 documents: all have f:x, the 6 even ones also g:y. Wrap a TopScoreDocCollector in PositiveScoresOnlyCollector and search g:y: 6 hits, all scoring above 0. This is the documented use, and it works.
  2. Wrap a TopFieldCollector sorted by a price field instead, the collector IndexSearcher#search(Query, int, Sort) uses. You expect the same 6 hits, sorted by price. You get 0 hits.
  3. Wrap a TotalHitCountCollector to count the hits that score above 0. For (f:x)^0, where every score is 0, you expect 0 and get 12; for (g:y)^2 OR (f:x)^0, with 6 positive hits, you expect 6 and get 12. No error, with assertions on or off.
  4. Why: the wrapper inherits two FilterCollector hooks. scoreMode() passes on the wrapped collector's "no scores", so the search computes none and the > 0 check reads a placeholder 0 (for a function score query a constant 1, so zero-score hits get through). setWeight() hands the counter the Weight, whose count() covers whole segments without the check.

Who is affected

#

Applications that wrap a collector that needs no scores (sort by a field, hit counting, doc-id or aggregation collectors) in PositiveScoresOnlyCollector get wrong hits or counts silently, with default settings and any index size; on main a sort by a field loses every TermQuery hit. Few are exposed: no in-tree or major downstream user is known.

Mechanism, terms and numbers703 words

PositiveScoresOnlyCollector wraps another collector and is documented to make "sure only documents with scores > 0 are collected"; the Collector overview says it "wraps any other Collector". To check a score it reads scorer.score() itself, but it extends FilterCollector and inherits two hooks meant for pure delegators: scoreMode() reports the wrapped collector's needs, and setWeight() forwards the Weight. Around a collector that needs no scores, both go wrong. The search builds scorers without scores, so the > 0 check reads placeholder values: 0 for a TermQuery, so a sort-by-field TopFieldCollector gets 0 of the 6 hits of g:y; a constant 1 for a FunctionScoreQuery over MatchAllDocsQuery, so documents whose score is 0 get through (docs 0-5 instead of 1, 3, 5). And a wrapped TotalHitCountCollector counts whole segments with Weight#count and never runs the check: 12 instead of 0 for (f:x)^0, 12 instead of 6 for (g:y)^2 OR (f:x)^0. No exception is raised, with assertions on or off, with the default codec and settings and 12 documents. The score-mode half dates from LUCENE-6218 (first released in 5.1.0), the count half from LUCENE-10620 / #964 (9.3.0); neither edited the class. Overriding both hooks in PositiveScoresOnlyCollector fixes every repro, and the search-package and queries-module test suites pass with it. Wrapping a scoring collector such as TopScoreDocCollector, the documented use, has always worked, and the class has no known in-tree or major downstream user.

Terms

#
  • ScoreMode: what a collector needs from the scorer. COMPLETE means "visit all matches and get their score"; COMPLETE_NO_SCORES means "scores won't be available"; TOP_DOCS (a sort by a field with the default hit-count threshold) also needs no scores. IndexSearcher builds the query's Weight and scorers for the collector's mode.
  • FilterCollector: a base class for collector delegators. It forwards scoreMode() and setWeight() to the wrapped collector.
  • Weight#count: a per-segment shortcut that returns the number of matches without iterating (-1 when unknown). TotalHitCountCollector uses it when setWeight gave it the Weight, and then skips the segment.

The bug

#

PositiveScoresOnlyCollector (PositiveScoresOnlyCollector.java:26-52 at a9779ef3c193) overrides only getLeafCollector, whose leaf collector does if (scorer.score() > 0) in.collect(doc) (:47). It inherits:

  1. scoreMode() = in.scoreMode() (FilterCollector.java:51-54). Around a collector that needs no scores, IndexSearcher creates the Weight without scores and rewrites the query as ConstantScore(query), whose weight is then the plain inner weight. A TermQuery without scores uses a dummy SimScorer that returns 0 and a constant-0 bulk scorer, so every hit fails > 0. A FunctionScoreQuery without scores returns its inner weight; MatchAllDocsQuery's weight scores 1, so every hit passes, including those whose function value is 0.
  2. setWeight() = in.setWeight(weight) (FilterCollector.java:41-44). A wrapped TotalHitCountCollector asks weight.count(context), adds it and throws CollectionTerminatedException, so the wrapper's leaf collector never runs for that segment. With deletions Weight#count returns -1, collect() runs, and half 1 takes over.

Each half is an independent cause: fixing only scoreMode() still leaves 12 of 24 count searches of the independent reproducer wrong, fixing only setWeight() 16 of 24 in each of its tests; fixing both, all pass.

Exposure and likelihood193 words
  • Who is exposed. Code that wraps a sort-by-field TopFieldCollector (the collector behind IndexSearcher#search(Query, int, Sort)), a TotalHitCountCollector, a custom COMPLETE_NO_SCORES collector or a MultiCollector of such collectors. The count half also bites when the search does compute scores: MultiCollector(PositiveScoresOnlyCollector(TotalHitCountCollector), TopScoreDocCollector) has the right score mode, but the forwarded Weight still lets the counter skip the check (6 of 8 probe cases wrong from 9.3.0).
  • Default vs opt-in. The class is opt-in; everything else is default: codec, IndexWriterConfig, IndexSearcher, both search paths. A plain TermQuery triggers the sort case; a zero boost (legal) or a function score gives zero-score hits.
  • Effect. Wrong hits or counts in both directions: missing hits that score above 0, extra hits that score 0, counts too high (zero-score matches counted) or too low (with deletions). No exception.
  • How likely. Low. Outside its own test nothing in Lucene uses the class, no use was found in Elasticsearch, OpenSearch or Solr, the one user code found upstream (#13499) wraps a scoring collector, which works, and since 8.0 ("Queries are now required to produce positive scores.", LUCENE-7996) the class only removes hits with a score of exactly 0.

Why it is a bug, not intended

#
  • The javadoc promises "only documents with scores > 0 are collected" for "any other Collector"; nothing restricts the wrapped collector.
  • The wrapper reads scores, so it must ask for them, as CachingCollector does since a 2015 fix its commit called "a small bug".
  • The class predates both hooks, its only test wraps a scoring collector, and nothing accepts this.
The full argument305 words
  • Javadoc. Class: "A Collector implementation which wraps another Collector and makes sure only documents with scores > 0 are collected." Collector overview: "PositiveScoresOnlyCollector wraps any other Collector and prevents collection of hits whose score is <= 0.0". Collector#scoreMode: "Indicates what features are required from the scorer." ScoreMode.COMPLETE_NO_SCORES: "scores won't be available". No CHANGES or MIGRATE text restricts the wrapped collector.
  • In-tree precedent. CachingCollector.ScoreCachingCollector.scoreMode() returns COMPLETE: "Ensure the scores are collected so they can be replayed, even if the wrapped collector doesn't need them." It came as a bug fix: LUCENE-6912 (2015-12-04, first released in 5.5.0) added it, and its commit message says "In core, CachingCollector should have always returned true when scores are cached (small bug)."
  • The test framework trips too, through a neighbouring rule. Under AssertingIndexSearcher with assertions on, the assertion "Scorable.score() must not be called inside collect(DocIdStream) or collectRange() ..." fires inside PositiveScoresOnlyCollector.collect for both no-score wrapped collectors the finder's probe tried (3 seeds), and never with the fix. That assertion is about batch collection, not about whether scores were requested: the no-score bulk scorer hands over a DocIdStream, which the wrapper's inherited default collect(DocIdStream) turns into collect(int) calls that read score().
  • Tests. TestPositiveScoresOnlyCollector.testNegativeScores drives a TopScoreDocCollector by hand with a fake scorer; it never runs a search, never wraps a no-score collector and never calls setWeight.
  • History. The class (LUCENE-1575, 2.9) predates both hooks; its CHANGES usage example wraps a TopScoreDocCollector. LUCENE-6218 (2015-02) added needsScores forwarding to FilterCollector; in CachingCollector it only gave the placeholder collector inside CachingCollector.create a needsScores() of true, and it did not touch this class. CachingCollector's own override came ten months later with LUCENE-6912, as the fix of "a small bug"; #964 (2022) added setWeight forwarding and never discusses wrappers that filter collect() (all comments and reviews read).
The devil's-advocate check272 words

The strongest case for "intended" (the intended-behaviour checker): for the count half, #964 met this exact interaction in its own tests. A test wrapper that filters collect() around a TotalHitCountCollector stopped working, and the author moved the test to a test-only counter: "I fixed some tests that were assuming that TotalHitCountCollector would naively iterate over matches". TotalHitCountCollector's javadoc documents the segment skipping. For the score half: the class was built to wrap a scoring collector, and LUCENE-6329 only says score() must not throw when scores were not requested, not that it is meaningful. And Collector and FilterCollector are @lucene.experimental.

Why it fails: the #964 change concerned a private test class and never mentions PositiveScoresOnlyCollector, whose public javadoc the forwarding breaks; it does not touch the score half at all, where hits that really score above 0 are dropped. The component that needs scores is Lucene's own wrapper; in #15239, about a user's collector that wraps a TopScoreDocCollector with a different score mode, a maintainer wrote "It is the responsibility of the collector to prevent such calls, so this is not a bug": the wrapper was at fault, and here the wrapper is Lucene's own. Lucene's sibling wrapper overrides scoreMode for this reason (LUCENE-6912 called the inherited forwarding "a small bug"), and no won't-fix or by-design statement exists. Verdict: not intended (score half: high confidence; count half: medium, because of the #964 precedent). It is a design inference: no javadoc says a FilterCollector subclass must override these hooks, and for the count half documenting the restriction would also be a defensible maintainer choice. Lead the issue with the sort-by-field case.

Suggested fix

#

Recommended Ask for scores, and hide Weight#count from the wrapped collector

Override both hooks in PositiveScoresOnlyCollector: scoreMode() returns COMPLETE when the wrapped collector needs no scores (else its own mode, so score pruning is kept), and setWeight() passes on a FilterWeight whose count() is -1 (+22 lines). All repros pass, and so do 2,340 search-package tests and the 513 queries-module tests, with assertions on and off.

All options and trade-offs6 options · 864 words

Both shapes of the setWeight change were validated on the module test suites; they differ in what the wrapped collector can still do with the Weight.

Ask for scores, and hide Weight#count from the wrapped collector (validated by the checks) (recommended)

#

scoreMode() keeps the wrapped mode when it needs scores and maps TOP_DOCS and COMPLETE_NO_SCORES to COMPLETE. setWeight() wraps the Weight in a FilterWeight whose count() returns -1, so the wrapped collector can no longer count a segment without collect(), but keeps matches, explain and the scorers. This is the finder's fix, in the shape an independent reviewer from another model family proposed.

@Override
public ScoreMode scoreMode() {
  // This collector reads scores itself, even if the wrapped collector does not need them.
  ScoreMode scoreMode = in.scoreMode();
  return scoreMode.needsScores() ? scoreMode : ScoreMode.COMPLETE;
}

@Override
public void setWeight(Weight weight) {
  // The wrapped collector must not count matches with Weight#count and skip collect(): that would
  // also count matches whose score is <= 0.
  in.setWeight(
      weight == null
          ? null
          : new FilterWeight(weight) {
            @Override
            public int count(LeafReaderContext context) {
              return -1;
            }
          });
}

Trade-offs

  • A wrapped TopScoreDocCollector keeps TOP_SCORES pruning. For a wrapped sort-by-field or counting collector the Weight is now built for COMPLETE: scores are computed, which the wrapper needs anyway, and the search is exhaustive, so a query loses any shortcut it takes for a non-exhaustive mode (not benchmarked). By code reading no competitive-iterator skipping is lost: the wrapper's leaf collector does not pass one on today.
  • setWeight() hides Weight#count from every wrapped collector, scoring or not; one that counts with it would count in collect() instead. By code reading the only in-tree collectors that call Weight#count are TotalHitCountCollector and the sandbox HistogramCollector, and neither needs scores.
  • Targeted: it blocks only Weight#count and keeps every other Weight method (matches, explain, scorerSupplier, getQuery) for per-document users (Lucene's monitor module calls weight.matches(ctx, doc) from its own collectors).
  • FilterWeight is @lucene.internal, which is fine inside core.
  • Gap, by code reading only: getQuery() still returns the query, and the sandbox HistogramCollector uses it to bulk-count a PointRangeQuery without collect(). That matters for a point range whose scores can be 0 (a zero boost, or a FunctionScoreQuery around it whose values can be 0: HistogramCollector unwraps both), wrapped through a custom manager (the collector is package-private). Not executed.
  • Not benchmarked; only this class changes.

Ask for scores, and do not forward setWeight (validated by the checks)

#

The same scoreMode() override, and an empty setWeight (+13 lines). This is what downstream engines did for their own min-score wrappers: OpenSearch gave its MinimumScoreCollector (a FilterCollector subclass) a no-op setWeight (PR #16366), and Elasticsearch withholds setWeight under min_score (#97030).

@Override
public void setWeight(Weight weight) {
  // Do not pass the weight on: the wrapped collector could count matches with Weight#count and
  // skip collect(), which would also count matches whose score is <= 0.
}

Trade-offs

Simpler, and closes every Weight-based shortcut, including the HistogramCollector one. Cost: the wrapped collector never gets the setWeight callback (it is skipped, not called with null), so a per-document user of the Weight has none, and a collector that requires the callback breaks: by code reading, the test framework's AssertingCollector asserts that it was called, so one wrapped inside the class would fail with assertions on (not executed).

What the checks validated

Gradle, assertions on: the same selection, 217 classes, 2,340 tests and 52 classes, 513 tests, 0 failures. The finder also ran it on the repro, the upstream test (3 seeds), the 960-check harness and the asserting probe (3 seeds), while it was the finder's only fix: all pass. Not run with assertions off or through the static checks.

Trade-offs

Always return COMPLETE

#

Document the restriction

#

Say in the javadoc that only collectors that need scores may be wrapped, and never a TotalHitCountCollector.

Trade-offs

Workaround without a Lucene change

#

Subclass PositiveScoresOnlyCollector with the two overrides of the recommended fix, or filter by score in the application's own collector.

Trade-offs

Every application has to know about it.

Downstream note

#

An application that uses a score > 0 cut-off to hide documents is not protected by this collector around a no-score collector (zero-score hits can get through); a filter clause is the tool for visibility rules.

How it was found

#

An independent model from another family (OpenAI GPT-5.6), asked for test ideas, wrote a small probe: a wrapped collector that needs no scores got 0 of 6 positive hits, and a wrapped counter reported 12. The finder then checked the wrapper against the truly positive hits on 960 small cases (384 wrong) and reduced it to a JUnit test.

The method in full217 words

Method: semi-formal (a model-written probe, then bounded-exhaustive differential testing of the real core jar, guided by mutation analysis).

  • First signal (2026-10-28). A planning round asked an independent model from another family (OpenAI GPT-5.6) for testing-research leads; one lead's probe ran on the stock main jar: a wrapped collector that needs no scores collected 0 of 6 positive hits, and a wrapped TotalHitCountCollector reported 12 instead of 0 or 6.
  • Hunt. The finder checked the wrapper against an independent reference, the matches whose COMPLETE score is above 0, over 2 segment layouts, 2 deletion states, 8 queries, 3 search paths and 10 wrapped collectors covering 4 of the 5 ScoreMode values (all but TOP_DOCS_WITH_SCORES): 384 of 960 checks wrong, every one with a wrapped collector that needs no scores. Mutants of the wrapper that override only scoreMode(), only setWeight(), or both separated the two causes; a mutant of the reference (>= 0) checked that the oracle was not vacuous.
  • A class-file inventory of the 8 Collector wrapper classes in the non-sandbox jars flagged the same pattern (reads scores, inherits both hooks) only in CachingCollector's classes, a separate hunt finding (LFV-161), partly known upstream.
  • The finder then wrote a public-API JUnit test, which failed on main and on every release run from 8.0.0.

History

#

Score half since LUCENE-6218 (2015-02-05, first release 5.1.0), which made FilterCollector forward the score mode; count half since #964 (2022-06-23, first release 9.3.0), which made it forward the Weight. Neither edited the class. Affects 5.1.0 to 10.5.2, branch_10_6 and main.

Versions tested6 rows

Score half: LUCENE-6218 "don't decode freqs or enumerate all positions, when scores are not needed" (@rmuir, 2015-02-05; branch_5x 8c0dbb90087, trunk 010e352f603; Subversion era, no PR) added Collector#needsScores() and FilterCollector#needsScores() { return in.needsScores(); }. LUCENE-4100 (8.0.0) renamed it to scoreMode() and kept the forwarding. The class had become a FilterCollector subclass in LUCENE-5527 (2014; the change shipped in 5.0.0), harmless while FilterCollector had no hooks.

Bug record

#

LFV-900, snapshot of 2026-10-29

Registry title
PositiveScoresOnlyCollector inherits its wrapped collector's scoreMode() and setWeight(), so a wrapped sort-by-field TopFieldCollector or TotalHitCountCollector silently gets the wrong hits or count instead of exactly the hits that score > 0 (score-mode leg since 5.1.0, count leg since 9.3.0)
Area
core / search collectors (PositiveScoresOnlyCollector; FilterCollector scoreMode and setWeight forwarding; TotalHitCountCollector Weight#count shortcut)
Priority
Medium, rank 203: PositiveScoresOnlyCollector is a stable core class that silently returns wrong hits or counts when it wraps a collector that needs no scores, which makes it Medium, but nothing in-tree or in the major downstream engines uses it and since 8.0 it can only drop zero-score hits.
Impact class
silent wrong results
Impact note
Applications that wrap a collector that needs no scores (a sort-by-field TopFieldCollector, the collector behind IndexSearcher#search(Query, int, Sort); TotalHitCountCollector; a doc-id or other COMPLETE_NO_SCORES collector; or a MultiCollector of them) in the public core PositiveScoresOnlyCollector get silently wrong hits or counts on every search, with no exception under -ea or -da, with the default IndexWriterConfig, codec and searcher and at any index size (12 documents suffice), in every release from 5.1.0 to 10.5.2 and on main; wrapping a scoring collector such as TopScoreDocCollector (the documented use) is correct, the class has no in-tree, Elasticsearch, OpenSearch or Solr consumer, and since 8.0 (no negative scores) it can only remove zero-score hits, so few applications are exposed.
Summary
You wrap a collector in PositiveScoresOnlyCollector, whose javadoc says it 'makes sure only documents with scores > 0 are collected' and which Collector's overview says 'wraps any other Collector', and expect the wrapped collector to see exactly the matches that score > 0: in the repro 6 hits for the TermQuery g:y with a TopFieldCollector sorted by a field, and counts 0 for (f:x)^0 and 6 for (g:y)^2 OR (f:x)^0 with a TotalHitCountCollector. Instead the sort-by-field collector receives 0 hits and the counter reports 12 for both queries, because PositiveScoresOnlyCollector, which reads scorer.score() itself, inherits two FilterCollector hooks: scoreMode() reports the wrapped collector's no-score mode, so the search builds scorers without scores and the > 0 test reads placeholder values (0 for TermQuery, so real hits are dropped; a constant positive value for FunctionScoreQuery over MatchAllDocsQuery, so zero-score hits get through), and setWeight() hands the wrapped TotalHitCountCollector the Weight, so it counts whole segments with Weight#count and never goes through the filter. Overriding scoreMode() to return COMPLETE when the wrapped collector needs no scores, and passing on a Weight whose count() returns -1 (or not forwarding setWeight at all), fixes both.
Introduced
two legs, neither an edit to PositiveScoresOnlyCollector.java (byte-identical in 5.0.0 and 5.1.0, and in 9.2.0 and 9.3.0) [read: git blame -w -M -C and git log -S on the full history; both boundaries confirmed by execution]: (1) score-mode leg: 8c0dbb90087716841b895d839e15a8edfdbb8dae (branch_5x, svn r1657571; trunk 010e352f60301b1ab3967ad70413240163703ec4, r1657554), LUCENE-6218 'don't decode freqs or enumerate all positions, when scores are not needed' (apache/lucene#7280, by rmuir, Subversion era, no PR): it added Collector#needsScores() and FilterCollector#needsScores() { return in.needsScores(); }, which PositiveScoresOnlyCollector (a FilterCollector subclass since LUCENE-5527, 85642f59ddf, 2014, first released in 5.0.0) inherited although it reads scores; LUCENE-4100 (4fc5a872ded, 2017, first released in 8.0.0) renamed the hook to scoreMode() and kept the forwarding. (2) count leg: e983d391d71f3f3a628eb5520e8714623ac05202 (branch_9x; main 4c1ae2a332cb85878310142ebb9fd5beba0345f2), LUCENE-10620 / apache/lucene#964 'Pass the Weight to Collectors' by jpountz: it added Collector#setWeight with forwarding in FilterCollector and MultiCollector and made TotalHitCountCollector count through Weight#count; it has no CHANGES entry (9.3.0's CHANGES does not mention LUCENE-10620 or setWeight). Not born with the class (LUCENE-1575, 2.9): it broke when FilterCollector gained hooks that a filtering subclass must override.
