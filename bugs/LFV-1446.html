Lucene90StoredFieldsFormat's javadoc sets BEST_COMPRESSION with Lucene100Codec, a backward codec since 10.1 that cannot write postings

The Lucene90StoredFieldsFormat javadoc turns on BEST_COMPRESSION with new Lucene100Codec(Mode.BEST_COMPRESSION), but since 10.1.0 Lucene100Codec is a backward codec whose postings format refuses to write. Copied, the line does not compile against lucene-core; with lucene-backward-codecs, the first commit of a document with an indexed (postings) field throws and closes the IndexWriter.

The finding in 30 seconds

#

A two-line code sample in the class javadoc of the default stored-fields format still names the 10.0 codec. It is plain text in a <pre><code> block, which neither javac nor javadoc checks, so moving that codec out of core in 10.1.0 broke nothing in the build.

Background: codecs and backward codecs

#
  1. A codec decides how every part of an index is written. IndexWriterConfig.setCodec picks one; the default is the newest codec, Lucene104Codec on main.
  2. The stored-fields mode, BEST_SPEED or BEST_COMPRESSION, is an argument of the codec's constructor: new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION).
  3. When a new codec arrives, the previous one moves to lucene-backward-codecs, which exists to read old indexes. Old formats that move there with it may refuse to write: here the postings format Lucene912PostingsFormat does, so the codec cannot write a segment that has postings (a field indexed for search, such as a StringField).

The finding, step by step

#
  1. You want smaller stored fields. The Lucene90StoredFieldsFormat javadoc says BEST_COMPRESSION gives a better ratio and shows one line for it: indexWriterConfig.setCodec(new Lucene100Codec(Mode.BEST_COMPRESSION)). You copy it.
  2. With only lucene-core, javac cannot find Lucene100Codec: since 10.1.0 it lives in lucene-backward-codecs, the module for reading old indexes.
  3. With lucene-backward-codecs on the class path it compiles (with the import, and Lucene100Codec.Mode for the sample's bare Mode). You add 1 document with an indexed, stored StringField and call commit(), expecting an index with 1 document.
  4. Instead commit() throws UnsupportedOperationException: This postings format may not be used for writing, use the current postings format: the old codec's postings format refuses to write. The writer is closed and the directory holds no commit. The same code with the current codec, new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION), commits the document.

Who is affected

#

Developers who choose BEST_COMPRESSION (or name BEST_SPEED) by copying this javadoc, the place where the two modes are explained. It is opt-in and needs no scale; the default codec is unaffected. The failure is loud on the first run, and its message points to the fix.

Mechanism, terms and numbers515 words

Lucene90StoredFieldsFormat is the stored-fields format of the current codec (and of every codec since 9.0). Its class javadoc explains the two modes, BEST_SPEED (the default, LZ4) and BEST_COMPRESSION (DEFLATE, a better ratio), and says "These two options can be configured like this:", followed by indexWriterConfig.setCodec(new Lucene100Codec(Mode.BEST_SPEED)) and // indexWriterConfig.setCodec(new Lucene100Codec(Mode.BEST_COMPRESSION)) (Lucene90StoredFieldsFormat.java:47-54).

That was right in 10.0.0. #13968 (10.1.0) added Lucene101Codec and moved Lucene100Codec to lucene-backward-codecs, the module for reading old indexes; Lucene100Codec's default postings format, Lucene912PostingsFormat, refuses writes (Lucene912PostingsFormat.java:366-370). The javadoc kept the old name through 10.6.0 and main, where the current codec is Lucene104Codec.

So the copied line does not compile against lucene-core. With lucene-backward-codecs on the class path (common for applications that read older indexes) it compiles, and the first commit of a document with a postings field (an indexed StringField, for example) throws UnsupportedOperationException: This postings format may not be used for writing, use the current postings format; afterwards IndexWriter.isOpen() is false and the directory has no commit. The same steps with new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION) index and commit the document. The postings format's refusal is by design; the defect is the core javadoc example. #12984 fixed the same kind of staleness at these two lines in 9.10.0.

Side effects (executed probe, not the repro)

#

After the failed commit, IndexWriter.isOpen() is false, getTragicException() is the UnsupportedOperationException, and DirectoryReader.indexExists(dir) is false: no commit that writes postings can succeed with this codec, so no document with a postings field indexed with it was ever durable. A document with only a StoredField (nothing indexed) commits: its stored fields go to the core Lucene90StoredFieldsFormat (Lucene100Codec.java:120-121), and FreqProxTermsWriter.flush returns before it asks for the postings writer (FreqProxTermsWriter.java:103-106). Documents with only points, doc values or vectors were not tested.

Scope

#

On main these two javadoc lines are the only mention of a non-current Lucene9x/Lucene10x codec class in a non-test .java file outside lucene/backward-codecs (grep over lucene/). The sibling test that #13968 did update now uses new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION) (TestLucene90StoredFieldsFormatHighCompression.java:34).

Not claimed

#

The comment "instead for higher performance (but slower)" (it means higher compression) and the bare Mode in the sample (in this class it would mean Lucene90StoredFieldsFormat.Mode): cosmetic.

Exposure and likelihood151 words
  • Who: anyone who sets the stored-fields mode by copying the class javadoc. With lucene-core alone it is only a compile error. With lucene-backward-codecs on the class path, which applications that read older indexes often have, an IDE offers org.apache.lucene.backward_codecs.lucene100.Lucene100Codec and the code compiles.
  • What happens then: the first segment flush or commit that writes postings throws and closes the writer; the failed work is rolled back (IndexWriter.java:6095-6102), so the documents buffered since the last commit never become committed. No commit that writes postings can succeed with this codec, so no document with a postings field indexed with it was ever durable (a fresh directory ends with no index).
  • Not affected: the default codec without an explicit mode, and the documented mode once the current codec is named.
  • How long: every release from 10.1.0 to 10.6.0 (2026-10-29), and main.
  • Priority: Low, like the other stale class-javadoc examples in this list.

Why it looks unintended

#
  • The javadoc presents it as the way to set the modes: "These two options can be configured like this:".
  • The line was updated at earlier codec bumps (#12984, #13585, #13815); #12984 fixed this same staleness in 9.10.0.
  • The closest upstream test configures the corrected line, new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION).
The full argument163 words
  • Contract. "These two options can be configured like this:" (Lucene90StoredFieldsFormat.java:47-48), then the two setCodec lines.
  • History of the line (git log -L): #12984 (a9480316e28, merged 2024-01-25, 9.10.0) replaced the backward codec Lucene87Codec with Lucene99Codec; #13585 (b4a8810b7ae, 2024-07-31) switched it to Lucene912Codec; #13815 (4105c6e686c, 2024-10-01) to Lucene100Codec. #13968 then moved Lucene100Codec out of core without touching the javadoc, and the later bumps (#14333, #15160) left it too.
  • Tests. TestLucene90StoredFieldsFormatHighCompression uses new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION) (:34). #13968 moved it to Lucene101Codec in the same commit that moved Lucene100Codec out of core, and the later bumps (#14333, #15160) moved it on to Lucene104Codec.
  • No text accepts the stale name. Nothing in MIGRATE.md or the javadoc says to write with a backward codec, and Lucene100Codec's own constructor javadoc still reads "stored fields compression mode to use for newly flushed/merged segments" (Lucene100Codec.java:116), with no warning that its postings format refuses writes.
The devil's-advocate check125 words

The case: backward codecs are documented as being for reading old indexes ("Codecs for reading indexes from older versions of Lucene", overview.html:22); codec APIs are @lucene.experimental (Lucene104Codec.java:53); the sample is only a sketch, whose bare Mode would not compile as written anyway; the failure is loud, at the first run, with a message that says "use the current postings format"; and the earlier 9.x instance went unreported for more than two years.

Why it fails: it justifies the backward postings format's refusal to write, which stays as it is, not the core javadoc that sends readers there. The maintainers fixed the identical staleness before (#12984) and updated the line at two later codec bumps, so they treat the sample as live instructions.

Suggested fix

#

Recommended A: name the current codec (validated)

Name the current codec in both javadoc lines: indexWriterConfig.setCodec(new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION)) (and the same for BEST_SPEED). Validated: the corrected lines compile against lucene-core alone, the test written from them passes with the closest stored-fields suites, and the format and javadoc checks pass.

- *   indexWriterConfig.setCodec(new Lucene100Codec(Mode.BEST_SPEED));
+ *   indexWriterConfig.setCodec(new Lucene104Codec(Lucene104Codec.Mode.BEST_SPEED));
  *   // instead for higher performance (but slower):
- *   // indexWriterConfig.setCodec(new Lucene100Codec(Mode.BEST_COMPRESSION));
+ *   // indexWriterConfig.setCodec(new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION));

Trade-offs

The guard catches the linked codec being moved or removed, which is what the codec bumps have done so far (#13968 moved Lucene100Codec when it added Lucene101Codec). Under that pattern the next codec bump cannot compile core until this javadoc is updated, which is the point. It would not force an edit if a newer default codec arrived while Lucene104Codec stayed in core. It ties the lucene90 format's docs to the lucene104 codec on purpose; one fully qualified link in the prose.

What the checks validated

  • With the diff, :lucene:core:compileJava, checkGoogleJavaFormat and renderJavadoc pass, and the page links Lucene104Codec.Mode.
  • Simulated next bump: the same link pointed at org.apache.lucene.codecs.lucene100.Lucene100Codec.Mode, where the class lived until 10.0.0, makes :lucene:core:compileJava fail with Lucene90StoredFieldsFormat.java:49: error: reference not found.

Downstream note

#

No exposure beyond developers who copy the example: the codec is the application's own configuration. Documents only decide whether the refusal is reached (any ordinary document with a postings field reaches it once that codec is set); no crafted document, query or index file is involved.

How it was found

#

Lucene90StoredFieldsFormat's class javadoc says the BEST_SPEED / BEST_COMPRESSION stored-fields modes 'can be configured like this' with indexWriterConfig.setCodec(new Lucene100Codec(Mode...)), but since 10.1.0 Lucene100Codec is a read-only codec in lucene-backward-codecs: the example does not compile against lucene-core, and with backward-codecs on the classpath the first commit of a document with an indexed field throws UnsupportedOperationException and closes the IndexWriter (documentation defect)
Area
core / codecs (Lucene90StoredFieldsFormat class javadoc configuration example)
Priority
Low, rank 1308: Documentation only: the stored-fields compression example names a codec that has been read-only since 10.1.0, so copying it either fails to compile or, with the backward codecs on the classpath, fails the first flush or commit and closes the IndexWriter, losing the documents buffered since the last commit. Picking a stored-fields compression mode is an ordinary opt-in setting, so it is plausible, and the failure is loud on the first run.
Impact class
minor
Impact note
Documentation only: a developer who picks the BEST_COMPRESSION (or BEST_SPEED) stored-fields mode by copying this class javadoc example gets a compile error with lucene-core alone, or, with lucene-backward-codecs on the classpath (usual for applications that read older indexes, and then an IDE resolves the name to the backward codec), an UnsupportedOperationException at the first flush or commit that writes postings, after which the IndexWriter is closed (tragic) and the documents buffered since the last commit are lost [exec]; the failure is loud, comes on the first run, and its message ('use the current postings format') hints at the fix; it needs an explicit codec (opt-in), no scale; every release from 10.1.0 to 10.6.0 and main; the default codec without an explicit mode is not affected.
Summary
The Lucene90StoredFieldsFormat javadoc says you can switch stored fields to the smaller BEST_COMPRESSION mode 'like this': indexWriterConfig.setCodec(new Lucene100Codec(Mode.BEST_COMPRESSION)). Since Lucene 10.1.0, Lucene100Codec is no longer the current codec but a read-only one in lucene-backward-codecs, so the example does not compile against lucene-core, and with backward-codecs on the classpath the first commit of a document with an indexed field throws UnsupportedOperationException ('This postings format may not be used for writing, use the current postings format') and closes the IndexWriter. The same steps with the current codec, new Lucene104Codec(Lucene104Codec.Mode.BEST_COMPRESSION), work, so only the javadoc is wrong.
