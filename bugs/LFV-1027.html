The util.fst package overview's code examples call removed APIs and have not compiled on any release since 9.0.0

The org.apache.lucene.util.fst package overview's examples call three APIs that were removed or changed, so copied code gets 6 compile errors on main and every 10.x release (1 or 2 on 9.x). Only the javadoc is wrong: a small fix makes the remaining examples compile and print their commented values.

The finding in 30 seconds

#

Three of the overview's five examples call APIs that were removed or changed after the page was written.

What you need to know first

#
  1. An FST (finite state transducer) maps sorted keys to outputs in a compact byte array; Lucene uses FSTs for its terms index, synonyms and suggesters. The org.apache.lucene.util.fst classes (FSTCompiler builds one, FST holds it, Util queries it) let you build your own; they are marked @lucene.experimental.
  2. The package overview, the javadoc of the package's package-info.java, is the one place that shows the whole flow end to end: five code blocks that share one FST of cat=5, dog=7, dogs=12 and state their printed values in comments.

The finding, step by step

#
  1. You copy the five examples of the org.apache.lucene.util.fst package overview into one method, in page order, adding only imports. They build an FST of cat=5, dog=7, dogs=12, look up "dog", look up the key whose value is 12, iterate, and ask for the 3 cheapest paths.
  2. You expect it to compile against Lucene 10.5.2 or main and print what the comments say: 7, then dogs, then cat 5 and dog 7.
  3. Instead javac reports 6 errors in 3 of the 5 examples: new FSTCompiler<Long>(INPUT_TYPE.BYTE1, outputs) (that public constructor was removed in 9.9.0), Util.getByOutput(fst, 12) (removed in 9.0.0, with no named replacement), and four reads of .input / .output on Util.Result (a record since 10.0.0, so only input() / output() are public).
  4. Why: the examples sit inside <pre> in a javadoc comment, which nothing compiles. Three API changes updated every caller in the code but not the page; the 9.0.0 change even deleted the page's link to getByOutput and kept the example that calls it.
  5. With FSTCompiler.Builder, the record accessors and the lookup-by-value example removed, the page's own examples compile and print 7, the sorted pairs cat 5, dog 7, dogs 12, then cat 5, dog 7: the values in the page's comments, with the iteration's pairs in between.

Who is affected

#

Developers who build or query FSTs directly with the experimental util.fst API and start from the package overview, its one end-to-end example. Every copy fails to compile, on every release since 9.0.0, and the lookup-by-value example shows a feature that no longer exists. No runtime effect: nothing wrong ever runs.

Mechanism, terms and numbers604 words

The org.apache.lucene.util.fst package overview (package-info.java) is the package's only end-to-end usage example: five code blocks that share one FST built from cat=5, dog=7, dogs=12 (build it, look up a key, look up by value, iterate in sorted order, N shortest paths), with the printed values in comments. Copied in page order with only imports added, they fail to compile on main with 6 javac errors in 3 of the 5 blocks: the public FSTCompiler(INPUT_TYPE, Outputs) constructor was removed in 9.9.0 (#12715; FSTCompiler.Builder is the API), Util.getByOutput was removed in 9.0.0 (LUCENE-8638, #249, which deleted the page's link to it but kept the code block), and Util.Result became a record in 10.0.0 (#13328), so .input / .output are private and need input() / output(). No release since 9.0.0 ships a compiling version of the page (1 error in 9.0.0-9.8.0, 2 in 9.9.0-9.12.3, 6 in 10.0.0-10.6.0 and main). It is a documentation defect only: nothing wrong ever runs. With a javadoc-only fix (three corrections: Builder, accessors, drop the lookup-by-value block, which has no named replacement; plus a one-word comment update) the page's blocks compile and print the values in their comments, with the iteration's sorted pairs in between.

Exposure and likelihood164 words
  • Who. Users of FSTCompiler, FST, Util and BytesRefFSTEnum who build a custom dictionary, suggester or term index and learn the API from the package overview. The published javadoc shows the same page: an independent verifier found the stale lines on the published 10.3.1 and 9.12.0 package-summary pages.
  • Default vs opt-in. No configuration is involved; anyone who copies the examples hits it, every time. The classes are @lucene.experimental, an expert API, which is why the impact class is minor.
  • What they lose. Time: they have to find FSTCompiler.Builder and the record accessors on their own (CHANGES and MIGRATE name them, the page does not). And a wrong belief: "Retrieval by value" advertises lookup by output, which the public API no longer offers.
  • Scale. 3 of 5 examples, 6 errors on main and all of 10.x; the page has not compiled as shipped in any release since 9.0.0 (2021).
  • Not affected. Lucene's behaviour, results and indexes. javac names the missing members at once.

Why it looks unintended

#
  • The page calls the blocks examples and states their printed values (// 7, // dogs); it has no pseudo-code disclaimer, and only imports are missing.
  • Maintainers fixed compile errors on this page before: LUCENE-6112 (2014) and the LUCENE-9089 follow-up (2020).
  • LUCENE-8638 deleted the page's link to getByOutput but kept the example that calls it.
The full argument217 words
  • The contract is the page. Headings "FST Construction example", "Retrieval by key", "Retrieval by value", "Iterate over key-value pairs in sorted order", "N-shortest paths by weight", and the printed values in // x comments (package-info.java:35-96). Every identifier the blocks use is declared on the page.
  • Upstream keeps this page compiling. LUCENE-6112 (#7174, 2014, "Compile error with FST package example code", fixed as "Fix compile error in FST package example code"); the LUCENE-9089 follow-up 59a8e83520e ("update FST usage example", Tomoko Uchida, 2020-04-29), which rewrote the blocks for the then-new FSTCompiler and TopResults; #12831 (2024), which updated line 52 for the compile() change.
  • Oversight. None of #249, #12715, #12831 or #13328 discusses the page's code (threads read). CHANGES and MIGRATE record the removals as deliberate API changes (naming the replacements for the constructor and the record fields), so the page documents APIs the project itself retired.
  • Boundary isolated by execution. Each commit's own page was compiled against core built at that commit. The code blocks are the same at both commits (the 2020 text, which differs from today's at line 52, changed by #12831 in 2024, and in markup). They compile and print the commented values and the sorted pairs at a37844aedd5 (the parent of 666c7a25907) and fail with the getByOutput error at 666c7a25907.
The devil's-advocate check231 words

Strongest case for "not a bug" (built by the intended-behaviour checkers): (a) the FST API is @lucene.experimental; on the #12715 review Mike McCandless wrote that the FST API is internal, so the old constructor could be removed without deprecation; (b) Lucene does not compile javadoc code: LUCENE-8488 (#9534, "Javadoc examples should be kept in sync with actual compiled code") is still open, and on #15225 Robert Muir wrote that code examples should be kept "extremely minimal" because "the maintenance cost is very high and we don't have great validation for these"; (c) the failure is loud, and CHANGES and MIGRATE name the replacements for the constructor and the record fields; (d) the blocks are fragments.

Why it fails: experimental status explains why the API could change, not why the package's own overview keeps showing the removed forms; the lack of validation explains how the drift got in, and nobody upstream has said stale examples are acceptable (LUCENE-8488 and #15225 point the other way); a loud error lowers the impact, but the lookup-by-value block still advertises a removed capability; and the fragments need only imports. Verdict: not intended, a documentation defect (Low). To concede: the example itself uses two @lucene.internal helpers (BytesRefBuilder, IntsRefBuilder), so this is a trivial documentation cleanup that maintainers may reasonably resolve by trimming or deleting the examples instead, in line with the views above.

How it was found

#

No formal method. While checking whether Lucene's javadoc code examples still compile, an AI tool extracted this page's five examples, compiled them against main and every release jar, and used javap to date each API removal.   • Hunt. The hunt extracted the blocks mechanically (HTML entities decoded, only imports added), compiled them with javac against the core jar of every release 8.0.0-10.5.2, a 10.6 build of 4ae946e5a9b (then RC1, now the 10.6.0 tag), branch_10x and main (both with each release's own page and with main's page), scanned the three APIs with javap, and wrote a compile-and-run JUnit test that compares the printed lines with the documented values; a mutant with a wrong documented order fails, so the comparison is not vacuous. LFV-1027, snapshot of 2026-11-05

Registry title
The org.apache.lucene.util.fst package overview's code examples do not compile on any release since 9.0.0: they call Util.getByOutput (removed in 9.0.0), the public FSTCompiler(INPUT_TYPE, Outputs) constructor (removed in 9.9.0) and the Util.Result fields input/output (private record components since 10.0.0) (documentation defect)
Area
core / util/fst (package overview examples, package-info.java)
Priority
Low, rank 1189: The util.fst package overview has several examples that fail to compile, with no runtime effect and only users of the experimental FST API affected.
Impact class
minor
Impact note
Documentation only, with no runtime effect: a developer who copies the util.fst package overview's usage examples (the package's only end-to-end FST example) gets compile errors on every release since 9.0.0 (1 in 9.0.0-9.8.0, 2 in 9.9.0-9.12.3, 6 in 10.0.0-10.6.0 and main) and has to find FSTCompiler.Builder and the record accessors input()/output() on their own, while the 'Retrieval by value' feature the page shows no longer exists at all; the util.fst classes are @lucene.experimental, and no configuration, scale or special input is involved.
Summary
The org.apache.lucene.util.fst package overview shows five usage examples (build an FST, look up by key, look up by value, iterate in sorted order, N-shortest paths) and the values they print. Copied into code on any release since 9.0.0 they do not compile: Util.getByOutput was removed in 9.0.0 (LUCENE-8638, which deleted the page's link to it but kept the code block), the public FSTCompiler(INPUT_TYPE, Outputs) constructor was removed in 9.9.0 (#12715; FSTCompiler.Builder is the API), and Util.Result became a record in 10.0.0 (#13328), so '.input' and '.output' are private and need input() and output(). With those three edits, dropping the lookup-by-value block because it has no replacement, the examples compile on main and print exactly the documented values, so only the javadoc is wrong.
Introduced
666c7a25907 (#249 'LUCENE-8638: remove deprecated FST get by output', by Michael Sokolov (msokolov), approved by dweiss, author date 2021-08-18; umbrella issue LUCENE-8638, migrated as #9684): it removed both Util.getByOutput overloads (deprecated since 8.2.0 by LUCENE-8895) and deleted the page's '{@link Util#getByOutput Lookup-by-output}' bullet, but left the 'Retrieval by value' code block. That was the first break of the example text written by 59a8e83520e (LUCENE-9089 follow-up 'update FST usage example', Tomoko Uchida, 2020-04-29), which compiled against main until then [exec: the page's blocks compile and print the documented values on core built at the parent a37844aedd5 and fail with the getByOutput error at 666c7a25907, with identical block text].
