A doc-values update can be lost during a merge

During a merge, a newer doc-values update still being applied can lose to an older value carried over from disk: doc 0 silently keeps 100 instead of 200, through commit() and a reopen. Unreleased: Lucene main with any overlays setting, and branch_10_6 only with the experimental overlays on.

The bug in 30 seconds

#
  1. Start forceMerge(1) of segments _0 = {doc 0, doc 1} and _1 = {doc 2}. While it runs, set doc 0's ndv to 100 and open an NRT reader: the 100 is written to _0 on disk at delGen 3.
  2. Set doc 0 to 200 and add a delete-by-query; a flush() on another thread freezes both into packet P (delGen 4), which the test holds inside that query. Meanwhile tryUpdateDocValue sets doc 2 = 302 (delGen 5) and doc 1 = 301 (delGen 6); both finish first.
  3. You expect the newest update to win: doc 0 = 200 on the merged segment.
  4. Instead the merge commit gives doc 0's on-disk 100 the delGen 6 - 1 = 5. P then re-applies 200 at delGen 4, below 5, so 100 wins, with no error under -ea or -da, and the loss survives commit() and a reopen.
  5. Without the doc-2 update the 100 gets delGen 4, a tie with P: under -ea a duplicate delGen=4 assertion closes the writer and every uncommitted change is lost; under -da the 100 won in every run observed.

Who is affected

#

Lucene main, whatever maxDocValuesOverlays is set to (0 included); branch_10_6 only with the experimental setMaxDocValuesOverlays(n>0), new in 10.6.0; not 10.5.2. It needs a concurrent merge, an older update to the document written during it, a still-running packet for that document, and a newer update on the same segment and field that finished first. No production rate was measured.

Mechanism, terms and numbers594 words

While a background merge runs, a newer doc-values update that is still being applied can lose to an older value carried over from disk. The merged segment keeps the old value, with no error, and the loss survives commit() and a reopen. It is unreleased code: Lucene main whatever maxDocValuesOverlays is set to, and on branch_10_6 only with the experimental doc-values overlays turned on.

Lucene applies doc-values updates in packets. Each packet gets a number, its delGen; a higher delGen means a newer update. When two updates hit the same document and field, the one with the higher delGen wins.

When a merge finishes, IndexWriter has to carry over the updates that landed on the source segments while the merge was running. Since #16570 it reads back what was already written to disk and collapses it into one packet per source segment and field. A value on disk no longer carries the number of the packet that wrote it, so the merge has to choose one:

  • diskDelGen = minResidual - 1, where minResidual is the smallest delGen among that segment's and field's updates that are finished but not yet written;
  • completedDelGen if there are none. The finished-but-unwritten updates keep their own delGens.

Main's javadoc says this number is "below all residual and still-running ones". That holds only if packets finish in number order, and they do not have to. tryUpdateDocValue, or an ordinary update packet on another indexing thread, can finish while an older packet P is still being applied. So P can end up with delGen(P) <= diskDelGen. When P re-applies on the merged segment:

  • delGen(P) < diskDelGen: the older carried-over value has the higher number and wins. The newer update is silently lost, with assertions on (-ea) and off (-da).
  • delGen(P) == diskDelGen (a tie): with -ea, ReadersAndUpdates.assertNoDupGen throws duplicate delGen, a tragic exception closes the writer, and all uncommitted changes are lost. With -da the old value won in every run observed; the order is unspecified, because DocValuesFieldUpdates.mergedIterator orders updates to one document only by delGen, so two equal delGens have no defined winner.

The example, step by step

#

Segments _0 = {doc 0, doc 1} and _1 = {doc 2}, numeric field ndv:

  1. forceMerge(1) starts on a helper thread; the test pauses the merge at its first output file.
  2. updateNumericDocValue(id:0, 100), then DirectoryReader.open(writer). Opening the reader writes the update (delGen 3) to _0 on disk while _0 is being merged.
  3. updateNumericDocValue(id:0, 200) plus a delete-by-query. Another thread calls flush(), which freezes both into one packet P (delGen 4); P blocks inside its delete-by-query.
  4. tryUpdateDocValue(reader, doc 2, 302) (delGen 5, on _1) and tryUpdateDocValue(reader, doc 1, 301) (delGen 6, on _0). Both finish at once, out of order, and stay pending on the merging segments.
  5. The merge commits. On _0 the only finished-but-unwritten update is doc 1's (delGen 6), so doc 0's on-disk 100 is collapsed at delGen 5. P is released and re-applies doc 0 = 200 at delGen 4 on the merged segment. 4 is below 5, so 100 wins.
  6. Expected doc 0 = 200; actual 100, with -ea and with -da. Without the doc-2 update, doc 1 gets delGen 5, the 100 is collapsed at delGen 4, the same number as P, and -ea closes the writer on duplicate delGen=4.

Exposure and likelihood396 words
  • Who is exposed. Lucene main (the next major version, unreleased) runs the disk carry-over on every merge, whatever maxDocValuesOverlays is set to, 0 included (IndexWriter.java:4531 calls it unconditionally). On branch_10_6 it runs only with the opt-in, experimental IndexWriterConfig#setMaxDocValuesOverlays(n > 0), which is new in 10.6.0; with the default 0 the old buffered path runs, and this bug does not affect it. 10.5.2 is not affected: the code does not exist there.
  • Symptom. An update the application was told succeeded is replaced by an older value. There is no exception, the loss survives commit() and a reopen from disk, also in a separate JVM. In the tie case with -ea the writer closes instead, and every uncommitted change is lost with it.
  • What it takes. All four together: a concurrent merge; an older update to the document written to the merging segment during the merge (for example by an NRT reopen or a commit); a packet that updates the same document and is still being applied when the merge commits; and, on the same merging segment and field, a newer update that finished before that packet. Without the last condition the same schedule is correct.
  • Ordinary scale. Three or four documents are enough. An independent program reproduces it with nothing but updateNumericDocValue on two indexing threads, the default merge policy and scheduler, and FSDirectory; a pause is still needed to pin the interleaving. Without any pause, a study verifier's stress run on main (three updater threads, a slow no-match delete-by-query, a policy that merges whenever two segments exist, a 0.001 MB RAM buffer, an NRT reader opened every 2 ms) hit it in 3 of 3 30-second runs: a tragic duplicate delGen close with -ea, and 54 to 89 already-returned updates missing from NRT readers per run with -da. Pre-#16570 code and the clamp gave none; a milder configuration found nothing in 60-second runs, and no production rate was measured.
  • Tests do not catch it today. On branch_10_6, LuceneTestCase.newIndexWriterConfig turns overlays on in about 4 of 5 random configs, but no CI failure report was found on GitHub or builds@.
  • Release timing. 10.6.0 is not released. On dev@ the release manager wrote that only issues with milestone 10.6 delay a release candidate and planned a 10.6.1 milestone for bug fixes; another participant wrote that 10.6 will be the final 10.x release.

Why it is a bug, not intended

#
  • Main's javadoc names the rule it breaks: the number is "a gen below all residual and still-running ones so newest-wins ordering holds on the merged segment".
  • With -ea, the code's own ReadersAndUpdates.assertNoDupGen fires in the tie case.
  • Without the disk carry-over (branch_10_6 with overlays at 0, or 10.5.2 with an adapted copy) the schedule ends with the newer 200.
The full argument216 words
  • The code states the rule it breaks. Main's javadoc of the carry-over (IndexWriter.java:4564-4569): "the collapsed packet therefore uses minResidualDelGen - 1 (or completedDelGen when there is no residual), a gen below all residual and still-running ones so newest-wins ordering holds on the merged segment." The bug is a still-running packet that is not below that gen.
  • The code's own assertion trips. With -ea, ReadersAndUpdates.assertNoDupGen fires in the tie case, on main and on branch_10_6. On branch_10_6, DocValuesFieldUpdates.mergedIterator also asserts that delGens are unique (assert cmp != 0, under the comment "delGens are unique across our subs"); main's version (DocValuesFieldUpdates.java:163-168) has neither that assertion nor a tie-break.
  • The older path gets it right. On branch_10_6 with overlays at 0, the buffered path keeps the old 100 at its real delGen 3, below P's 4, so the newer 200 wins and the control test passes. The released 10.5.2 jars give doc 0 = 200 for the same schedule (adapted, because 10.5.2 has no overlays setting).
  • Newest wins is the rule the code itself names. The same javadoc chooses the number "so newest-wins ordering holds on the merged segment", and without the disk carry-over (overlays at 0 on branch_10_6, or 10.5.2) the same schedule ends with the newer value.
The devil's-advocate check102 words

No separate intended-behaviour check was run for this bug; its lenses were code-history-fix, exec-branch106, exec-main-1052 and provenance-dups-policy, plus a claim re-check. The strongest case for "intended" in those reports: on branch_10_6 the overlays feature is experimental and off by default. It does not cover main, where the path is unconditional, and it does not touch the javadoc rule above.

The claim re-check's adjudications: the buffered path is "not affected by this bug" rather than "correct" in general, and a possible separate race that the code-history checker described in the finished == false path was not reproduced and stays out of the issue.

Suggested fix

#

Recommended Clamp the invented delGen to completedDelGen

A candidate fix on a local branch: one expression in IndexWriter.buildMappedDVUpdatesFromDisk caps the invented delGen at completedDelGen, so it stays below every residual and every still-running packet, and at or above every number already written. Passes on branch_10_6 (1,398 index tests, 0 failures) and main (TestMergeCarryOverFromDisk 6/6); the independent program is correct in all 32 runs.

final long completedDelGen = bufferedUpdatesStream.getCompletedDelGen();
final long diskDelGen =
    minResidual != Long.MAX_VALUE
        ? Math.min(minResidual - 1, completedDelGen)
        : completedDelGen;

Clamp the invented delGen to completedDelGen (validated by the checks) (recommended)

#

Local branch r106-merge-dv-carryover-race-fix (7f12368ee2, one commit on the test commit) changes the expression in IndexWriter.java:

final long completedDelGen = bufferedUpdatesStream.getCompletedDelGen();
final long diskDelGen =
    minResidual != Long.MAX_VALUE
        ? Math.min(minResidual - 1, completedDelGen)
        : completedDelGen;

Trade-offs

  • Why it is safe: the new number is below every residual, below every still-running packet (a still-running packet's delGen is above completedDelGen), and still at or above every number already written, because writes use maxDelGen = completedDelGen. It changes behaviour only when minResidual - 1 > completedDelGen, which is exactly the risky case.
  • A main PR must also fix main's javadoc at IndexWriter.java:4564-4569, which still describes minResidualDelGen - 1. The commit's CHANGES entry has GITHUB#TBD placeholders and says "With doc-values overlays enabled", which is wrong for main.
  • The hunk applies to main only with git apply -3 (a _ -> versus k -> lambda in the context).
  • Open PR #16571 (jimczi, "Let a merge write more than one segment") edits the same method, so expect a rebase or coordination.

What the checks validated

  • The independent program: all 32 runs correct on the fix jar (overlays default, 1, 4, 8 by v1/v2 by tie/lt by -ea/-da).

How it was found

#

AI tools model-checked the merge carry-over (Alloy 6, TLA+, P), starting from a suspicion formed while reading buildMappedDVUpdatesFromDisk: not a blind find. Alloy found it first; TLA+ and P confirmed it with directed runs; TLC later re-found it without scripted actions (14-state trace, 2-document bound chosen after the fact). Randomized single-threaded testing missed it.

The method in full284 words

Method: model checking of the merge carry-over protocol, with the hypothesis formed while modelling (the study's "semi-formal" tier). On 2026-10-22, against Lucene main 7cecf79523, AI tools wrote three models of IndexWriter's NRT and merge carry-over logic from the code, one each in Alloy 6, TLA+ and P.

  • Alloy came first. While reading buildMappedDVUpdatesFromDisk and its comment, the AI tool suspected the diskDelGen choice and built a merge sub-model to probe it. The solver found a counterexample to the no-duplicate-delGen property in 153 s (8 steps), and its trace was simpler than the AI tool's: a published, not yet applied packet is enough.
  • TLA+. A blind breadth-first run produced a spurious counterexample (a modelling bug). Diagnosing it against the code led to the real hypothesis, confirmed in Java, then shown in the model with a directed witness. A later TLC run with no scripted actions, but with a 2-document bound chosen after the bug was known, found it again: a 14-state (13-step) trace after 21.1M distinct states and 33 minutes.
  • P. Unguided hunt of about 40,000 schedules missed it. A directed scenario with long merges and a late second indexing thread, explored with PCT, reached the bad state in 5 to 33 schedules, and the model's copy of assertNoDupGen fired ("duplicate delGen=4"). The same scenario with the clamp in the model found nothing.
  • Testing missed it. The randomized model-based tester runs one thread with SerialMergeScheduler, so it cannot reach the race.

Not a blind find: each model started from an AI tool's suspicion formed while reading the code. Independent AI verifiers then reproduced it (Alloy, TLA+ and P verifications), and AI tools wrote the Java tests, the standalone repro and the candidate fix.
