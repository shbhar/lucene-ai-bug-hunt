checkSelfIntersections=true accepts a self-crossing polygon once it has more than 80 points

With checkSelfIntersections=true, XYShape and LatLonShape promise to check that a polygon is valid, but above 80 points the Tessellator runs a faster z-order check that does not compare every pair of edges. A self-crossing ring rejected with 7 or 80 points is silently accepted with 81.

The finding in 30 seconds

#

Tessellator.checkIntersection has two paths. Up to 80 points it compares every edge with every other edge. Above 80 it uses mortonCheckIntersection, which finds only edges whose start vertex lies in the edge's z-order box range and never starts from the two edges at the first vertex, so some crossing pairs are never compared.

Background: how a polygon is checked and indexed

#
  1. LatLonShape and XYShape index a polygon as triangles. The Tessellator cuts the ring into triangles by clipping "ears" one by one.
  2. With checkSelfIntersections=true it first compares the ring's edges in pairs and throws IllegalArgumentException("Polygon self-intersection at ...") when two of them cross.
  3. For rings with more than 80 points (holes counted) it also sorts the vertices along a z-order (Morton) curve, so that "which vertices lie in this box?" becomes a short walk in sorted order. The ear cut and the check then both use that walk.

The finding, step by step

#
  1. Take the six-vertex ring (x y) 5 2 → 3 2 → 6 0 → 9 9 → 7 5 → 1 1 → back to 5 2. Its edges (3,2)–(6,0) and (1,1)–(5,2) cross at x = 3.545, y = 1.636.
  2. Index it with XYShape.createIndexableFields("f", polygon, true). Written with 7 points, or with 73 extra points on its straight edge from (5,2) to (3,2) (80 points), it is rejected: IllegalArgumentException: Polygon self-intersection at lat=1.636… lon=3.545….
  3. Add one more point on that edge: 81 points. You expect the same exception: the Tessellator drops collinear points, so it checks the same six-vertex ring.
  4. Instead the call returns 4 triangle fields, the same as with the check off, so a caller indexes the self-crossing polygon as if the check were off. LatLonShape behaves the same.
  5. Why: above 80 points each edge is compared only with edges that start inside its z-order box range, and the two edges at the first vertex are never the edge searched from. (1,1)→(5,2) is one of those two, and (1,1) lies outside the range of (3,2)→(6,0), so this pair is never compared.

Who is affected

#

Applications that pass checkSelfIntersections=true to LatLonShape or XYShape (createIndexableFields or createDocValueField) to reject self-crossing polygons. Above 80 points some such polygons are accepted and indexed as if the check were off; whether the same polygon is caught can depend on its point count (80 or 81) and its start vertex. Opt-in; every release since 9.1.0.

Mechanism, terms and numbers689 words

XYShape.createIndexableFields(name, polygon, true) and its LatLonShape twin document that "the validity of the provided polygon is checked with a small performance penalty" (XYShape.java:92-95, LatLonShape.java:94-97). When the outer ring plus its holes has more than 80 raw points (VERTEX_THRESHOLD, Tessellator.java:75-76, "a dumb heuristic"), the Tessellator links the vertices in z-order (Morton) and runs the self-intersection check on that path (:120-136; XY :183-199). That path never uses the two edges at the start vertex as the edge it searches from, and compares each other edge only with edges whose start vertex has a Morton code inside that edge's bounding-box range (:953-1009). That walk finds every vertex inside a box, which is what the ear test it comes from needs, but not every edge that crosses one, so crossings are missed. The repro's six-vertex ring is rejected with 7 and with 80 points and accepted with 81 points: the call returns the same 4 triangle fields as with the check off. The 74 extra points lie on a straight edge and are removed by the Tessellator before the check (with the closing point), so only the switch to the z-order path differs; natural rings without collinear points fail too, depending on their start vertex. The check and its z-order variant were added together in 9.1.0 (LUCENE-9538, 78c8d7b7ea6); every release through 10.6.0 and main are affected. Replacing the z-order walk with a complete search that sorts the edges by minimum x and sweeps fixes it; rings of up to 80 points keep today's check.

The two paths of the check

#
  • The switch (Tessellator.java:120-133): threshold = VERTEX_THRESHOLD - polygon.numPoints(), minus every hole's points; mortonOptimized = threshold < 0. With 81 raw points (80 distinct plus the closing point) the ring goes to the z-order path. The raw count is taken before collinear points are removed.
  • The call (:134-136, XY :197-199): checkIntersection(outerNode, mortonOptimized) runs before the ear cut.
  • Primary edges (:953-966): for next from a.next up to, but not including, a.previous, the edge next -> next.next is the edge searched from. The two edges at the start node, a -> a.next and a.previous -> a, never are.
  • Plain path (:960-963): the inner loop compares the primary edge with every other edge, so the two start-node edges are still covered as partners.
  • Z-order path (:973-1009): mortonCheckIntersection computes the z-order range [minZ, maxZ] of the primary edge's bounding box and walks the z-sorted vertices p inside that range, testing only the edge p -> p.next. The walk and its comment "now make sure we don't have other points inside the potential ear" come from the ear test mortonIsEar (:738-749), where a complete search for vertices inside a box is all that is needed. Two crossing segments need not have an endpoint inside each other's box (a plus sign is the extreme case), so the walk can miss a crossing edge.

The repro ring

#

After the collinear points and the closing point are removed the ring is (5,2) (3,2) (6,0) (9,9) (7,5) (1,1), starting at (5,2). Its edges (3,2)→(6,0) and (1,1)→(5,2) cross at (3.5454…, 1.6363…).

  • (1,1)→(5,2) is a.previous -> a, so it is never a primary edge.
  • The other crossing edge is primary (3,2)→(6,0) (box x 3..6, y 0..2); its z-order range holds (6,0), (3,2) and (5,2). The walk starts at the z-order neighbours of b = (6,0): (3,2) is the primary edge itself and is skipped, and (5,2)→(3,2) only touches it at (3,2). The z-order predecessor of (6,0) is (1,1), whose code is below the range, so the walk stops there and the edge starting at (1,1) is never tested. An instrumented copy of the method traced the compared pairs: (3,2)→(6,0) is compared only with (5,2)→(3,2).
  • With 80 points the plain loop compares (3,2)→(6,0) with every other edge and throws.

Covering only the two start-node edges is not enough: with that change one of 8 small self-crossing rings found by a bounded search (4 geo, 4 XY) is still accepted, because the walk itself is incomplete.

Exposure and likelihood223 words
  • Opt-in. The two-argument createIndexableFields and createDocValueField pass false (XYShape.java:83-89, LatLonShape.java:85-91).
  • What happens. The call accepts the self-crossing polygon and returns the same triangle fields as with the check off (equal hashes of every field's bytes for the 81-, 82- and 127-point rings, XY and geo), so it is indexed as if the check were off. No other effect was found; what shape queries should match for a self-crossing polygon is not defined. When the ear cut cannot triangulate the ring, the caller still gets an IllegalArgumentException, but the generic "Unable to Tessellate shape" instead of the crossing location.
  • Not only padded rings. The same ring with one edge replaced by a sine arc (no collinear points) is rejected at 17 and 80 points and accepted at 81 and 157 (78 and 154 triangles), on main and 10.6.0. Natural rings of 82 to 127 vertices with exactly one proper crossing are accepted when they start at (5,2), rejected when started at three other vertices, and rejected from every start vertex at 79 points.
  • How often. In 20,000 random long/short-edge rings the z-order walk missed the crossing in 429, but there the ear cut still failed, so only the message changed. The searches under Prior reports found no public report of a miss since 9.1.0 (2022); the registry rates it rare.

Why it looks unintended

#
  • Both public overloads promise that with the flag on "the validity of the provided polygon is checked"; nothing says it is approximate above 80 points.
  • Below 81 points it is a strict validator, and maintainers call the flag "strict validation" (#11690).
  • mortonCheckIntersection's javadoc gives speed as its purpose and documents no approximation limit.
The full argument191 words
  • The contract. XYShape.java:92-95 and LatLonShape.java:94-97: "If checkSelfIntersections is set to true, the validity of the provided polygon is checked with a small performance penalty". The class javadoc requires "No self intersections" (Tessellator.java:43-45); mortonCheckIntersection's javadoc (:969-972) says "Uses morton code for speed to determine whether or not and edge defined by a and b overlaps with a polygon edge": speed is its stated purpose, and no approximation limit is documented.
  • Used as strict validation. BaseXYShapeTestCase filters its random polygons with Tessellator.tessellate(p, true) (BaseXYShapeTestCase.java:229). nknize on #11690: "API guardrails to enable or disable strict validation"; iverase on #11767: with the flag on "it will fail before getting to this place". In the review of the original change (apache/lucene-solr#1907) iverase argued that a polygon that "is invalid but it actually does not fail when it is tessellated" should still fail.
  • Strict below 81 points. With the check off the 7-point ring is triangulated into 4 triangles; with it on, it is rejected.
  • Precedent. #9602 (LUCENE-8556, the z-order ear test diverging from the plain one) and #9605 (LUCENE-8559, isIntersectingPolygon skipping edges) were fixed as bugs in 2018.
The devil's-advocate check135 words

The strongest case for "intended": LUCENE-9538 (#10578) asked for "a better error message for self-intersecting shapes"; the LatLon Polygon javadoc says a polygon "must not be self-crossing, otherwise may result in unexpected behavior" (Polygon.java:34); the Tessellator is @lucene.internal (Tessellator.java:72); and the z-order path is a speed trade-off.

Why it fails: XYPolygon has no such precondition and the repro uses XYShape; a precondition cannot excuse the check whose job is to detect its violation; @lucene.internal is on the Tessellator, not on the public overloads that promise the check; the 80-point threshold is undocumented; and the flag's author argued for failing invalid polygons that would still tessellate. Two executed reviews by another model family (OpenAI GPT-5.6) rated the intended-behaviour case moderate and rejected it; a devil's-advocate verifier found no argument that survives.

Suggested fix

#

Recommended Replace the z-order walk with a complete sort-and-sweep pair search (recommended)

Above 80 points, replace the z-order walk with a complete search: sort the edges by minimum x and compare each with the following ones until one starts right of it, through the existing checkIntersectionPoint. The repro, :lucene:core:check and the geo and shape suites pass (two pinned locations updated); a 100,001-point circle costs about the same as today.

Replace the z-order walk with a complete sort-and-sweep pair search (recommended) (validated by the checks)

#

Above 80 points checkIntersection calls a new sweepCheckIntersection instead of mortonCheckIntersection (Tessellator.java +35/-44, plus two expected messages in TestTessellator); rings of up to 80 points take exactly today's code. It collects the ring's edges, sorts them by minimum x and compares each edge with the following edges until one starts right of its maximum x. Every pair whose x-ranges overlap or touch, adjacent pairs included, goes to the existing checkIntersectionPoint, whose own bounding-box prefilter ignores all other pairs, so the sweep tests every pair the plain loop tests, plus the two adjacent pairs of the start edge a -> a.next that the loop skips.

private static void checkIntersection(Node a, boolean isMorton) {
  if (isMorton) {
    sweepCheckIntersection(a);
    return;
  }
  ... // the existing pairwise loop, unchanged
}

private static void sweepCheckIntersection(Node start) {
  final List<Node> edges = new ArrayList<>();
  Node node = start;
  do {
    edges.add(node);
    node = node.next;
  } while (node != start);
  edges.sort(Comparator.comparingDouble(Tessellator::edgeMinX));
  for (int i = 0; i < edges.size(); i++) {
    final Node a = edges.get(i);
    final double maxX = Math.max(a.getX(), a.next.getX());
    for (int j = i + 1; j < edges.size(); j++) {
      final Node b = edges.get(j);
      if (edgeMinX(b) > maxX) {
        // b starts right of this edge, and so does every later edge
        break;
      }
      checkIntersectionPoint(a, b);
    }
  }
}

Trade-offs

  • Cost: O(n log n) plus the number of x-overlapping edge pairs; on the circles about what the z-order walk costs today (table). The worst case is still quadratic, for many edges that share an x-range (for example a comb of long horizontal teeth); that was not measured. It allocates one list of n edges per check. The timings are local best-of-runs on regular polygons only: no holes, no heavily overlapping x-ranges, no real polygon data.
  • Two TestTessellator tests pin the reported location of a polygon that stays rejected and get the new one in the diff: testComplexPolygon44 ("Polygon self-intersection at lat=34.21159901699837 lon=-83.88790911034258") and testInvalidPolygonOverlap ("Polygon ring self-intersection at lat=52.0923747 lon=6.037857").
  • The break uses >, not >=, so pairs whose x-ranges only touch are still passed on: it stays complete if the fix for LFV-1252 (collinear axis-parallel overlaps skipped by the same prefilter) makes checkIntersectionPoint test such pairs.
  • It completes the pair search for crossings only: LFV-1252 (collinear axis-parallel overlaps skipped by the prefilter) needs its own fix.

How it was found

#

A proof-obligation audit of the Tessellator's contract checked, on both paths of checkIntersection, that with checkSelfIntersections=true every self-crossing ring is rejected. The z-order path takes its candidates from a point-in-box walk, which cannot find every crossing edge. A one-test JUnit witnessed it; a bounded search found 8 small rings rejected at 7-9 points and accepted past 80.

The method in full161 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for every ring passed with checkSelfIntersections=true, if two edges cross, checkIntersection throws. On the plain path the double loop discharges it (every pair of non-adjacent edges is compared). On the z-order path the candidate set is "edges whose start vertex is in the primary edge's z-order box range", and the two start-node edges are never primary; neither covers every crossing pair.
  • A one-test JUnit witnessed the gap on main with assertions on and off; a bounded search padded small self-crossing rings with collinear points past 80 and found 8 (4 geo, 4 XY) that are rejected at 7-9 points and accepted, with the same triangles as with the check off, once padded.
  • An independent reproducer, two executed reviews by another model family (OpenAI GPT-5.6), a devil's-advocate verifier and an adjudication then checked it with their own tests or re-runs.

LFV-1250, snapshot of 2026-11-04

Registry title
Tessellator self-intersection check misses crossings in polygons with more than 80 points, so LatLonShape/XYShape.createIndexableFields with checkSelfIntersections=true accept and index a self-crossing polygon
Area
geo / Tessellator self-intersection check (z-order path above 80 points; LatLonShape and XYShape with checkSelfIntersections=true)
Priority
Low, rank 427: With the opt-in self-intersection check on, a self-crossing polygon of more than 80 points can pass the check and be indexed as if the check were off, in every release since 9.1.0. It needs the opt-in flag and a crossing that the z-order search used above 80 points does not reach, and nothing is stored beyond what the unchecked path already writes.
Impact class
minor
Impact note
Applications that pass checkSelfIntersections=true to LatLonShape or XYShape.createIndexableFields (or createDocValueField) so that self-crossing polygons are rejected are hit when such a polygon has more than 80 points (holes counted) and a crossing the z-order search does not reach: the IllegalArgumentException that is due is not thrown and the polygon is indexed with the same triangles as with the check off (when the ear cut fails instead, the specific 'Polygon self-intersection at ...' message is replaced by the generic 'Unable to Tessellate shape'). The flag is opt-in, the input is invalid geometry, nothing is written beyond what check=false already writes, and whether the same geometry is rejected depends only on its raw point count (80 or 81) and on its start vertex; every release from 9.1.0 through 10.6.0.
Summary
You index the self-crossing ring (x y) 5 2, 3 2, 6 0, 9 9, 7 5, 1 1 with XYShape.createIndexableFields("f", polygon, true), written with 74 extra points on its straight edge from (5,2) to (3,2), so 81 points in all. You expect the IllegalArgumentException 'Polygon self-intersection at ...' that the same call throws for the 7-point and the 80-point forms of the same ring, because the javadoc says that with checkSelfIntersections the validity of the polygon is checked. Instead the call returns triangle fields and the self-crossing polygon is indexed: above 80 points the Tessellator runs the check on its z-order (Morton) path, which never uses the two edges at the start vertex as primary edges and finds other edges only when their start vertex lies in the primary edge's bounding box, so it does not compare every pair of edges.
