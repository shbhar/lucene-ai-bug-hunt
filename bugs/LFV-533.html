CapitalizationFilter never changes the case of letters outside the BMP, so Adlam, Osage and Deseret words are neither capitalized nor lower-cased

CapitalizationFilter changes case one UTF-16 char at a time, so letters stored as two chars (Adlam, Osage and six more scripts) keep their case: PARIS and paris become one term, but an Adlam word in capitals and in small letters stays two, so a query finds 1 of 2 documents.

The bug in 30 seconds

#

processWord changes case with Character.toUpperCase(char) and toLowerCase(char), one 16-bit char at a time (CapitalizationFilter.java:152, :159, :190, :193). A letter outside the BMP is two chars; each half alone has no case and comes back unchanged. LowerCaseFilter and UpperCaseFilter map whole code points.

Background: letters stored as two chars

#
  1. Java stores text as 16-bit char values. Most letters of everyday text, Latin, Greek and Cyrillic included, fit in one char: they are in the Basic Multilingual Plane (BMP).
  2. Letters above U+FFFF, such as those of Adlam, Osage and Deseret, take two chars, a surrogate pair: the Adlam small alif U+1E922 is U+D83A U+DD22.
  3. A surrogate alone is not a letter. Character.toUpperCase(char) returns U+D83A unchanged; Character.toUpperCase(int) on the whole code point U+1E922 returns the capital U+1E900.

The bug, step by step

#
  1. You analyse a field with KeywordTokenizer + CapitalizationFilter (default settings), documented to "make the first letter capital and the rest lower case", and index four values: PARIS, paris, and the Adlam letters alif + daali in capitals (U+1E900 U+1E901) and in small letters (U+1E922 U+1E923).
  2. You expect 2 terms, Paris and U+1E900 U+1E923 (capital alif, small daali), and a query for either Adlam spelling to find both Adlam documents.
  3. You get 3 terms: Paris, U+1E900 U+1E901 and U+1E922 U+1E923. The query paris finds 2 documents; the query U+1E922 U+1E923 finds 1.
  4. Why: each Adlam letter is two Java chars, a surrogate pair. The filter passes each char alone to Character.toUpperCase or toLowerCase; half of a pair has no case and comes back unchanged. BMP letters in the same token are mapped: aB + Osage U+104B0 gives Ab + U+104B0, not Ab + U+104D8.
  5. No exception in any run, and the terms stay valid UTF-16. Every path of the filter does it: the first letter, the rest of the word, later words (onlyFirstWord, on by default) and keep words with forceFirstLetter.

Who is affected

#

Any chain with CapitalizationFilter or the capitalization factory (schemas, CustomAnalyzer). It needs text in one of eight cased scripts outside the BMP, such as Adlam (a living script for Fulani) or Osage; there it happens every time: case variants stay separate terms and facet values (with a case-sensitive keep list, some merge into a kept word instead).

Mechanism, terms and numbers624 words

The javadoc of CapitalizationFilter says "It will make the first letter capital and the rest lower case" (CapitalizationFilter.java:26-28). Its processWord changes case with Character.toUpperCase(char) and Character.toLowerCase(char), one UTF-16 char at a time (:152, :159, :190, :193). Letters outside the Basic Multilingual Plane (BMP) are stored as two chars, a surrogate pair, and each half alone has no case, so the 564 cased code points of Adlam, Deseret, Garay, Medefaidrin, Old Hungarian, Osage, Vithkuqi and Warang Citi are never capitalized and never lower-cased, while BMP letters in the same token are. In a field analysed with KeywordTokenizer + CapitalizationFilter, PARIS and paris become one term, Paris, but the Adlam letters alif + daali in capitals and in small letters stay two terms, neither capitalized, and a query for one spelling finds 1 of the 2 documents. No run threw, and the output is valid UTF-16 of the same length. The char-wise lines come from the Solr original (2007-2008), were moved into Lucene unchanged in 2010 and are in every release since 4.0.0-ALPHA; mapping code points, as LowerCaseFilter and UpperCaseFilter do, fixes it.

Terms

#
  • UTF-16 char: Java stores text as 16-bit char values. Most letters fit in one char: they are in the Basic Multilingual Plane (BMP).
  • Supplementary character: a code point above U+FFFF, stored as two chars, a surrogate pair. The Adlam small alif U+1E922 is U+D83A U+DD22. A surrogate alone is not a letter and has no case.
  • Code-point case mapping: Character.toUpperCase(int) and toLowerCase(int) map a whole code point (U+1E922 to U+1E900). The char overloads cannot: the JDK documents that they "cannot handle supplementary characters".

The bug

#
  1. incrementToken splits the term into words at chars <= ' ' and . and calls processWord on each word, editing the term buffer in place (CapitalizationFilter.java:102-143).
  2. processWord (:145-196) maps case with the char overloads at four places: :152, every char of a later word when onlyFirstWord is true (the default); :159, the first char of a keep word with forceFirstLetter; :190, buffer[offset] = Character.toUpperCase(buffer[offset]);, the first letter; :193, every other char of the word, lower-cased.
  3. For a surrogate both overloads return the char unchanged (all 2,048 surrogate units checked), so a supplementary letter keeps its case. BMP letters in the same word are mapped.
  4. The code-point helpers exist next door: CharacterUtils.toLowerCase and toUpperCase (CharacterUtils.java:54-70, :105-113), used by LowerCaseFilter (:38) and UpperCaseFilter (:48). This filter's own case-insensitive keep set compares per code point too (CharArrayMap.java:231-290).

Exposure and likelihood356 words
  • Who is exposed. Chains built with the constructors, the capitalization factory in a CustomAnalyzer (reached with the stock standard, whitespace and keyword tokenizers: 9 of 9 cases unmapped, while lowercase in the same pipeline lower-cases the capitals) or a schema field type like the factory's javadoc example. Every path that changes case is affected (the default settings, onlyFirstWord=false and a keep word with forceFirstLetter were run). The filter is opt-in and in no stock analyzer.
  • What it takes. Text in Adlam (a living script for Fulani), Osage, or historic or rarely used Deseret, Old Hungarian, Warang Citi, Medefaidrin, Vithkuqi or Garay.
  • What changes for the user. Usually, case variants of such words stay separate terms (3 instead of 2 in the repro), separate facet values, and a query in one case misses the other (1 hit instead of 2). The capitalized display form the filter exists for is never produced for them. In one configuration the opposite also happens: with a case-sensitive keep list and forceFirstLetter, the stock filter turns [a, U+10400] into the kept word [A, U+10400] instead of [A, U+10428], merging case variants that the fixed filter keeps apart (35 stock terms in that configuration of the security probe, none in the other four).
  • What does not happen. In a bounded probe over 7,380 tokens and 5 configurations, assertions on and off: no exception, no change in term length, valid UTF-16; the filter keeps no state across tokens or documents.
  • Scale. Deterministic, with assertions on or off. The result depends only on the token text and the settings, so index size should not matter; only small indexes were run.
  • JDK dependence. Deseret (Unicode 3.1) shows it on every JDK Lucene supported; Adlam and Osage need Unicode 9.0 tables, which first came with JDK 11 (JDK 9 and 10 have Unicode 8.0; JDK 11 has Unicode 10.0, JEP 327). Only JDK 25 was run for the repro; a JDK 11 sanity run maps Adlam and Osage too.
  • How likely. Rare: the documented searches found no public report since Solr 1.3.0 (2008), and it needs those scripts in a field with this filter.

Why it is a bug, not intended

#
  • The javadoc promises "the first letter capital and the rest lower case", with no BMP limit; the JDK says the char overloads "cannot handle supplementary characters".
  • LowerCaseFilter, UpperCaseFilter and this filter's own keep set work per code point; tests require it for Deseret.
  • The same defect was fixed in LowerCaseFilter (LUCENE-2069) and, as bugs, in TruncateTokenFilter (#15900) and DecimalDigitFilter (LUCENE-6914).
The full argument263 words
  • Contract. "A filter to apply normal capitalization rules to Tokens. It will make the first letter capital and the rest lower case." (CapitalizationFilter.java:26-28). No script, BMP or UTF-16-unit limit in the class or the factory javadoc. Where Lucene means UTF-16 units it says so: LengthFilter.java:26, "Length is calculated as the number of UTF-16 code units".
  • The API used cannot do it. The JDK javadoc of Character.toUpperCase(char) and toLowerCase(char): "This method cannot handle supplementary characters. To support all Unicode characters, including supplementary characters, use the toUpperCase(int) method."
  • Siblings and their tests. TestAnalyzers.testLowerCaseFilter and testUpperCaseFilter ("handles entire unicode range correctly") require Deseret to be mapped (TestAnalyzers.java:135-169). The filter's own keepIgnoreCase set folds case per code point.
  • Policy before the class moved in. CHANGES.txt:17927-17928 (3.1.0): "LUCENE-2069: Added Unicode 4 support to LowerCaseFilter. Due to the switch to Java 5, supplementary characters are now lowercased correctly." That commit (2009) is an ancestor of the 2010 move of this class into Lucene, which copied the char loop verbatim.
  • Same defect class treated as a bug. CHANGES.txt:1198-1200 (10.5.0 Bug Fixes): "GITHUB#15899, GITHUB#15900: Improve TruncateTokenFilter to truncate on codepoints not chars and no longer produce half surrogates"; on #15899 uschindler wrote "We modified all other similar filters in the past (like ngrams), they all work correctly". CHANGES.txt:8852: "LUCENE-6914: Fixed DecimalDigitFilter in case of supplementary code points."
  • Nothing presents it as a choice. No test, javadoc, CHANGES or MIGRATE entry, commit message or JIRA discussion (SOLR-248, SOLR-468 and LUCENE-2413, read in full) marks the char loop as BMP-only. TestCapitalizationFilter.testRandomString checks token-stream consistency, not case.
The devil's-advocate check187 words

The strongest case for "intended" (the intended-behaviour check and the cross-model reviewer): a legacy, display-oriented char-buffer filter from Solr 1.3 ("useful to build nice looking facet parameters"), never updated, whose fix changes indexed output; on #15900 uschindler argued at one point that half surrogates from char-based truncation are "expected", "exactly the same like if you use String#substring(n,m)" (earlier in the same thread, uschindler had called that filter "somehow broken in general"), and both LUCENE-2069 and #15900 kept a legacy path.

Why it fails: nothing documents a BMP limit; the JDK documents the overloads used as unable to do the job; the sibling case filters and this filter's own keep set work per code point; on #15900 rmuir wrote "Nobody expects that behavior and doing this based on codepoints is a better api" (before the "expected" remark), and that fix shipped under Bug Fixes. Every verifier who assessed the argument rated it weak (the intended-behaviour check: no intended argument survives). What survives is the narrow reach and the reindex cost: reasons for low priority and a CHANGES note, perhaps a legacy option, not for keeping the behaviour.

Suggested fix

#

Recommended A: map code points, as LowerCaseFilter and UpperCaseFilter do

Map code points, as LowerCaseFilter does: CharacterUtils.toLowerCase for the rest and later words, Character.toUpperCase(int) on the first code point (+11/-9 lines). The repro passes with assertions on and off; the whole analysis-common test task (1,913 tests, assertions on) and lint pass; lone surrogates stay unchanged. Indexed terms change for these scripts: mention reindexing.

Trade-offs

  • Output changes only for supplementary letters; BMP text gives the same chars as before. Indexes built with this filter need reindexing for exact consistency, so a CHANGES note should say so.
  • The in-place edit relies on case mapping keeping each code point's UTF-16 length; that holds for all 1,112,064 non-surrogate code points with JDK 25, and CharacterUtils.toLowerCase (used by LowerCaseFilter) relies on the same.
  • With a case-sensitive keep list, the stock filter maps [a, U+10400] onto a kept word [A, U+10400]; the fixed filter keeps them apart ([A, U+10428]). Worth one sentence in the PR.

How it was found

#

Semi-formal. A bounded-exhaustive comparison ran the stock filter against a per-code-point reference written from its javadoc, on every token of up to 4 code points over a, B, space and two Deseret letters, with both onlyFirstWord settings: 836 of 1,414 checks differed, each at a supplementary letter. A public-API JUnit then confirmed it on the stock jar.

The method in full179 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier). The finder wrote two references for CapitalizationFilter from its javadoc, one that maps case per char and one per code point, and compared the stock filter with them:

  • with the per-char reference, on every token of up to 5 chars over {a, B, space, '.', U+0131} under 1,440 parameter combinations (7,874,496 checks): the mismatches found the sibling word-boundary bug (LFV-535);
  • with the per-code-point reference, on every token of up to 4 code points over {a, B, space, U+10428, U+10400}, with the default parameters and with onlyFirstWord=false, restricted to checks (a token with one onlyFirstWord setting) where the per-char reference agrees, so the sibling bug is excluded: 836 of 1,414 checks differ, each at a supplementary letter; 880 of all 1,562 checks (781 tokens x 2 settings) still differ after the sibling's fix.

A public-API JUnit on the stock main jar then confirmed it (found 2026-10-26). The same reference was used to find and to check, so the exhaustive count is not independent evidence; the verifiers wrote their own tests.

Versions tested9 rows

Bug record

LFV-533, snapshot of 2026-10-29

Registry title
CapitalizationFilter changes case one UTF-16 char at a time, so cased letters outside the BMP (Adlam, Osage, Deseret and five other scripts) are neither capitalized nor lower-cased, while BMP letters in the same token are
Area
analysis-common / miscellaneous (CapitalizationFilter case mapping)
Priority
Low, rank 441: CapitalizationFilter ignores case for supplementary-plane cased scripts such as Adlam and Osage, a tiny share of text in a niche filter, so it follows its sibling LFV-535.
Impact class
silent wrong results
Impact note
Hits applications that put the opt-in CapitalizationFilter (directly, or by its 'capitalization' factory name in a schema or CustomAnalyzer) on a field that holds text in one of the eight cased scripts encoded outside the BMP (Adlam, Osage, Deseret, Old Hungarian, Warang Citi, Medefaidrin, Vithkuqi, Garay): every such letter that should change case keeps its case, on every release since 4.0.0-ALPHA, deterministically with -ea and -da and at any scale, so case variants of one word stay separate terms and facet values and a query in the other case misses; the output stays valid UTF-16, nothing is thrown or corrupted, and BMP text, emoji and CJK ideographs are not affected.
Summary
You add CapitalizationFilter, documented to 'make the first letter capital and the rest lower case', and give it a word in a cased script outside the BMP, for example the Adlam word U+1E922 U+1E923 (two small letters), and expect U+1E900 U+1E923 (capital first letter). Instead every supplementary letter keeps its case: U+1E922 U+1E923 comes out unchanged, U+1E900 U+1E901 is not lower-cased to U+1E900 U+1E923, and 'aB' followed by the Osage capital U+104B0 gives 'Ab' + U+104B0, because processWord applies Character.toUpperCase(char) and toLowerCase(char) to single UTF-16 units and a surrogate unit maps to itself. BMP letters in the same token are mapped, nothing is thrown, and the onlyFirstWord and keep-word forceFirstLetter paths behave the same way.
