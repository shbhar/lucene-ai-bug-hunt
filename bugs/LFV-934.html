The finding in 30 seconds

#

A file-format javadoc that Lucene presents as the definition of the .si file gives a wrong type for its first field and leaves two fields out of the sequence.

Background: the .si file and its javadoc

#
  1. Every Lucene segment has one small .si file: which Lucene version wrote it, how many documents it holds, whether it is a compound file, its file list, diagnostics and attributes.
  2. Lucene documents each index file in the javadoc of the class that writes it, as an ordered list of fields with their types. For .si with the default codec that class is Lucene99SegmentInfoFormat.
  3. A String is written as a variable-length byte count followed by the bytes; an Int32 is four bytes, little-endian since 9.0.

The finding, step by step

#
  1. You write your own reader for a segment's .si file from the Lucene99SegmentInfoFormat javadoc, which the default codec's file-format docs link as the Segment Info format: Header, SegVersion, SegSize, IsCompoundFile, Diagnostics, ..., with SegVersion typed as a String.
  2. You index one document with the default codec on main and parse its .si. You expect SegVersion "11.0.0", SegSize 1 and IsCompoundFile 1, the values SegmentInfo reports.
  3. Instead you get SegVersion = 11 NUL characters, SegSize = 2,817 and IsCompoundFile = 0, and every later field is garbage. On 10.6.0 the version reads as 10 garbage characters.
  4. Why: the writer stores the version as three Int32s, 0B 00 00 00 00 00 00 00 00 00 00 00. readString() takes the first byte, 11, as a length and returns the next 11 zero bytes. Then come a min-version flag byte with three more Int32s and, after IsCompoundFile, a HasBlocks byte; neither is in the documented sequence.
  5. Lucene itself is unaffected: its reader mirrors its writer. The text was right until LUCENE-5992 changed the encoding in 5.0.0.

Who is affected

#

Only people who read, port or re-implement the .si format from this javadoc: their parser fails on the first field of every .si the default codec writes, in the releases since 5.0.0. Applications that read and write indexes through Lucene are not affected: Lucene's reader matches the writer. The recorded searches found no public report.

Mechanism, terms and numbers564 words

The default codec writes each segment's .si file with Lucene99SegmentInfoFormat, and the file-format overview links that class as the Segment Info format and sends readers there for the details. Its javadoc gives the file as Header, SegVersion, SegSize, IsCompoundFile, Diagnostics, Files, Attributes, IndexSort, Footer and types SegVersion and SegMinVersion as DataOutput#writeString Strings. Since Lucene 5.0 the writer stores the version as three Int32s (major, minor, bugfix), then a flag byte and, when it is 1, the minimum version as three more Int32s, then SegSize, IsCompoundFile and a HasBlocks byte. A parser that follows the javadoc reads the first Int32 (major version 11, 0B 00 00 00) as a string length and gets 11 NUL characters instead of 11.0.0; a 1-document segment then reads as SegSize 2,817, and every later field is misaligned. Lucene's own reader matches its writer, so Lucene reads its own files correctly and no runtime effect is expected. The text was correct when written (2012) and went stale in three steps: LUCENE-5992 (5.0.0), LUCENE-7756 (7.0.0, SegMinVersion) and #12685 (9.9.0, HasBlocks). A javadoc-only fix was validated.

The bytes of a one-document segment (executed probe, main)

#

After the 45-byte header the file starts 0B 00 00 00 | 00 00 00 00 | 00 00 00 00 | 01 | 0B 00 00 00 | 00 00 00 00 | 00 00 00 00: version 11.0.0, flag 1, minimum version 11.0.0 (a flushed segment records the current version for both).

  • readString() at SegVersion reads the length byte 0x0B = 11 and then 11 bytes: the rest of the major version and all of minor and bugfix, all zero. It returns 11 NUL characters and stops exactly at the flag byte.
  • readInt() for SegSize then reads 01 0B 00 00 = 2817 (the segment has 1 document); the next byte, 0, is taken as IsCompoundFile (the segment is a compound file, 1); the following zero byte reads as an empty Diagnostics map (the real one has 8 entries). Every later field is garbage.
  • The number of garbage characters is the major version: 10 on 10.6.0, 9 on 9.9.0. Before 9.0 an Int32 was big-endian (00 00 00 05), so the documented read returned an empty string.

Not claimed

#

No runtime, index, merge or search effect. The other .si elements (SegSize, IsCompoundFile, Diagnostics, Files, Attributes, IndexSort) are placed and typed consistently with the bytes, apart from the IndexSort --> writeVInt Int32 count wording (:63), which is cosmetic (it is a VInt). The compound-file value and the 8 diagnostics entries above are properties of this one-document configuration, not of the format.

Why it looks unintended

#
  • It is written as an exact grammar: ordered fields, each type linked to its DataOutput writer.
  • It was right in 2012; LUCENE-5992 (5.0.0) changed the encoding and left the text, and two later changes added fields outside the sequence.
  • segments_N documents the same version exactly ("three vInt: major, minor, bugfix").
The full argument215 words
  • Contract text. Lucene99SegmentInfoFormat.java:48-67 lists the elements in order and links each type to its DataOutput writer method (SegVersion --> {@link DataOutput#writeString String}); nothing marks it as approximate. lucene104/package-info.java:188: "Details on each of these are provided in their linked pages."
  • History. LUCENE-4055 (f330cf65adc, Robert Muir, 2012-05-22) wrote "SegVersion --> String" when the writer wrote the version with writeString (output.writeString(si.getVersion())); 4.10.4 still writes writeString(version.toString()), and the documented grammar parses there. LUCENE-5992 (#7054, a922e891914 / 776682ba9c3, Michael McCandless, 2014-10-06, "encode version using 3 ints, not String") changed the writer and reader, not the javadoc; its 22 comments never mention it (in review uschindler noticed that a different javadoc, Version#write, had become wrong). LUCENE-7756 (23b002a0fdf, 2017) and #12685 (6677109ee60, 2023) added SegMinVersion and HasBlocks to the type list and descriptions but not to the sequence; their reviews do not discuss it.
  • Consistency. SegmentInfos.java:73-77 documents the commit's Lucene version as "three {@link DataOutput#writeVInt vInt}: major, minor, bugfix", and the hunt found those fields match the bytes.
  • Precedent. LUCENE-713, LUCENE-7532 (#8583; fix commit 830a3fdfbf1, "add back lost codec file format documentation") and LUCENE-9353 (#90) fixed or restored file-format documentation.
  • No waiver. No test, CHANGES or MIGRATE entry, review comment or list thread accepts the stale text.
The devil's-advocate check184 words

Strongest case for "intended" (the refute reviewer and the cross-model review rated it moderate; the intended-behaviour check set it out as the strongest case and rejected it): the format classes are @lucene.experimental; the overview says it "attempts to provide a high-level definition of the Apache Lucene file formats", a policy from LUCENE-2946 (2012, "change file format documentation from bit-for-bit to highlevel"); the supported reader is SegmentInfoFormat.read; and the round trip is tested.

Why it fails: a wrong primitive type (String versus three Int32s) and two elements missing from an ordered list are not a high-level simplification. In the LUCENE-2946 thread (#4020, 2012-04-25) Robert Muir wrote "we can go into detail, but we can't do bit-for-bit with even StandardCodec" and "For the simple metadata files, and even stored fields and postings its fine (for now), but e.g. going bit-for-bit with packed integer compression of docvalues isnt very realistic" (their words), and .si is such a simple metadata file. @lucene.experimental allows the format to change, not its description to be wrong. Every verifier and the adjudication called it real, and the audit confirmed it.

Suggested fix

#

Recommended A. Correct the sequence and the two types in Lucene99SegmentInfoFormat

Correct the javadoc: sequence Header, SegVersion, SegMinVersion, SegSize, IsCompoundFile, HasBlocks, Diagnostics, Files, Attributes, IndexSort, Footer; SegVersion as three Int32s (major, minor, bugfix); SegMinVersion as an Int8 flag followed, if it is 1, by three Int32s. Javadoc only, one file. Validated: a parser written from the new text reads a real .si to the footer.

Downstream note

Downstream: only tools that parse .si files themselves from this javadoc are affected; applications that read and write indexes through Lucene are not.

How it was found

#

Semi-formal: a differential check transcribed each default-codec file grammar once from its class javadoc and once from its writer, parsed the real bytes of 64 generated indexes with both and compared every value with Lucene's own reader. All 125 .si files diverged under the javadoc grammar; the writer grammar parsed every file to the footer.

The method in full122 words
  • Each grammar is data in a small grammar language; one interpreter parses the bytes under the documented and the written grammar and compares every value with the real reader.
  • 64 default-codec indexes (3 fixed, 1 dense-vector and 60 seeded random feature configurations), 1,114 file checks over 11 file types, including .si.
  • Positive control: the writer grammars parse every file exactly to the footer. Vacuity check: 14 of 14 writer-grammar mutants with one element dropped are caught.
  • JUnit tests on public Lucene APIs then bridged the finding to the stock jars (later reduced to the one-test repro), and per-release ports dated each of the three stale parts.
  • This is a differential check of documentation against bytes, not model checking or a proof.

LFV-934, snapshot of 2026-11-03

Registry title
The file-format javadoc of the default segment info format (Lucene99SegmentInfoFormat) gives a wrong .si grammar: SegVersion and SegMinVersion are typed as String, but the writer stores three Int32s (and a flag byte plus three Int32s), and SegMinVersion and HasBlocks are missing from the documented sequence (documentation defect; the writer and reader agree)
Area
codecs / segment info (Lucene99SegmentInfoFormat .si file-format javadoc vs its writer and reader)
Priority
Low, rank 1081: The default .si grammar is wrong for a file every segment has, a documentation-only defect.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so indexing, merging, CheckIndex and search are unaffected in every configuration; the people misled are those who read, inspect or re-implement the .si format from this class javadoc (the default codec's package docs link it as the Segment Info format), and a parser that follows the text misreads the very first field of every .si file the default codec writes, then every later field (executed); the text has been wrong in every release since 5.0.0 (2015), and no scale or special setting is needed.
Summary
You decode a segment info (.si) file of the default codec by following the Lucene99SegmentInfoFormat javadoc, which gives the sequence Header, SegVersion, SegSize, IsCompoundFile, Diagnostics, Files, Attributes, IndexSort, Footer and types SegVersion (and SegMinVersion) as a String. The writer instead stores the version as three Int32s (major, minor, bugfix), then a flag byte and, when it is 1, the minimum version as three more Int32s, then SegSize, IsCompoundFile and a HasBlocks byte, so a parser built from the text reads the Int32 major version 11 as a string length and gets 11 NUL characters instead of '11.0.0', and every later field is misaligned. Lucene's own reader matches the writer, so nothing breaks at runtime; only the documentation is wrong, and it has been since 5.0.0.
