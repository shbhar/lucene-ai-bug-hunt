Sandbox numeric multi-range query on a skip-indexed field judges a document without a value by a later document's values

With a doc-values skip index, the sandbox numeric multi-range query can judge a document without a value by the next document's values: values 1, none, none, 50 with the ranges [40, 60] and [100, 200] count 2 hits, not 1. A regression of 10.5.0 (#15989); 10.6.0 and main are affected.

The finding in 30 seconds

#

With a skip index the query first picks whole blocks of documents that may match, documents without a value included, and then checks each one. Its check copes with one value-less document; with two in a row it judges the second by the next document's values.

Background

#
  1. Doc values store one or more numbers per document, and a field can be missing from some documents. A query reads them with a forward-only cursor: advance(d) moves it to the first document at or after d that has a value.
  2. A skip index (indexedField, opt-in) keeps the min and max value of each block of documents. This query's approximation skips blocks whose values cannot match and returns every document of the other blocks, with or without a value; matches() then checks each one.
  3. DocValuesMultiRangeQuery.SortedNumericStabbingBuilder (sandbox, @lucene.experimental) matches a document when one of its values is in any of the ranges. One range builds the core newSlowRangeQuery; two or more build SortedNumericDocValuesMultiRangeQuery.

The finding, step by step

#
  1. Index four documents whose field f is added with SortedNumericDocValuesField.indexedField (doc values plus a skip index), default codec: values 1, none, none, 50 (docs 0 to 3).
  2. Count new DocValuesMultiRangeQuery.SortedNumericStabbingBuilder("f").add(40, 60).add(100, 200).build(). You expect 1, the document with 50; the same data without a skip index, or as two core range queries, gives 1.
  3. You get 2. The skip index says the block of docs 0 to 3 (values 1 to 50) may match, so the query checks all four documents, the two without a value included.
  4. On doc 1 (no value) it moves its value cursor on to doc 3 and says no. On doc 2 the cursor is already past it; the query does not notice and judges doc 2 by doc 3's value 50: a false hit.
  5. On multi-valued fields doc 2's check uses up some or all of doc 3's values, so doc 3 is judged by what is left of them plus the next document's values (a missed or extra hit), or the read runs past the last value and the query throws.

Who is affected

#

Users of the sandbox numeric multi-range builder with two or more ranges on a sparse numeric field with the opt-in skip index (indexedField), on 10.5.0 to 10.6.0 and main. Default codec and skip interval; two consecutive value-less doc IDs inside a matching skip block suffice. Wrong hits with no error, also as a filter, under MUST_NOT and in count.

Mechanism, terms and numbers962 words

DocValuesMultiRangeQuery.SortedNumericStabbingBuilder with two or more ranges builds the sandbox SortedNumericDocValuesMultiRangeQuery, documented as "A union multiple ranges over SortedNumericDocValuesField". Since #15989 (10.5.0), on a field with a doc-values skip index its approximation is a SkipBlockRangeIterator, which returns every document of a block whose [min, max] overlaps the query, documents without a value included. matches() guards with if (values.docID() < doc && values.advance(doc) != doc) return false;, which checks the value cursor only when it is behind: on a first value-less document it advances the cursor to the next document that has a value and returns false, and on a second value-less document right after it the cursor is already past, the check is skipped, and the later document's values are judged for it. Values 1, none, none, 50 with the ranges [40, 60] and [100, 200] count 2, not 1, with assertions on and off. On multi-valued fields the second document's check uses up some or all of the later document's values, so that document is judged by what is left of them plus the next document's, or the read runs past the last value and the query throws. Same data without the skip index, with one range, or on 10.4.0: 1. Fix: advance if behind, then return false unless values.docID() == doc, the check core DocValuesRangeIterator makes.

Terms

#
  • Value cursor: the query's SortedNumericDocValues (values). values.docID() is the document it sits on; advance(d) moves it forward to the next document at or after d that has a value; docValueCount() and nextValue() read the values of the document it sits on.
  • Approximation: the cheap first phase of a two-phase iterator. It may return too many documents; matches() must give the exact answer for the document the approximation is on (TwoPhaseIterator.java:96-102).

The bug (main f794ff5a505c)

#
  1. The approximation. With a skip index, approximation = new SkipBlockRangeIterator(skipper, lowerValue, upperValue) (SortedNumericDocValuesMultiRangeQuery.java:225-228), over the overall span of all ranges (:214-215), here [40, 200].
  2. It returns value-less documents. It "returns all documents within DocValuesSkipper blocks" whose bounds match (SkipBlockRangeIterator.java:24-27); inside a matching block advance returns doc = target (:72). The skipper documents that its block may start after a target that has no value (DocValuesSkipper.java:37-38).
  3. The guard (SortedNumericDocValuesMultiRangeQuery.java:236-239): if (values.docID() < doc && values.advance(doc) != doc) return false;. It checks the cursor only when the cursor is behind doc.
  4. Two value-less documents in a row. On the first, the guard advances the cursor to the next document with a value and returns false. On the second, the cursor is already past it, the guard is skipped, and the value loop (:241-262) reads docValueCount()/nextValue() of that later document as if they were the current document's.
  5. Multi-valued fields. The loop returns true at the first value in a range (:250), so those values are now consumed up to that one (all of them if none is in a range). When the approximation reaches the later document the cursor is still on it, so nextValue() reads its remaining values and keeps reading into the next document's values, against "Do not call this more than docValueCount times for the document" (SortedNumericDocValues.java:28-32): a missed or extra hit, or a read past the last value.
  6. The core has the check. DocValuesRangeIterator.advanceDisi: if (disi.docID() >= target) return disi.docID() == target; (DocValuesRangeIterator.java:296-301). The sibling SortedSetDocValuesMultiRangeQuery goes through it (SortedSetDocValuesMultiRangeQuery.java:206, :216) and is not affected.

Exposure and likelihood235 words
  • Who is hit. Users of DocValuesMultiRangeQuery.SortedNumericStabbingBuilder with two or more ranges on a field indexed with SortedNumericDocValuesField.indexedField or NumericDocValuesField.indexedField, where some documents lack the field. The trigger is two consecutive doc IDs without the field inside the doc-ID span of a skip block whose [min, max] overlaps the query's overall [lowest lower, highest upper] span; a block's span starts and ends at documents with a value, so the pair sits between two documents that have the field. Why it looks unintended

#
  • Documented as "A union multiple ranges": a value-less document is in no range.
  • The same data gives 1 without the skip index, with one range, as core range queries, and on 10.4.0.
  • The skip index may return value-less documents and the caller must check (as iverase noted on #15989); the core iterator does, this query only for the first.
The full argument244 words
  • The contract. "A union multiple ranges over SortedNumericDocValuesField" (SortedNumericDocValuesMultiRangeQuery.java:44-48). The builder: for a single range "it behaves like SortedNumericDocValuesField#newSlowRangeQuery" (DocValuesMultiRangeQuery.java:156-160). TwoPhaseIterator.matches(): "Return whether the current doc ID that approximation() is on matches" (TwoPhaseIterator.java:96-102).
  • Controls on the same four documents (executed on main): the two-range query on a field without a skip index gives 1; a BooleanQuery of the two core newSlowRangeQuery clauses on the skip-indexed field gives 1; the one-range builder gives 1; only the multi-range query on the skip-indexed field gives 2.
  • The caller's obligation. As iverase pointed out in the #15989 review (2026-04-28, on SkipBlockRangeIterator.java): "it can return documents that do not contain values for sparse data. We only care that the docId is inside a matching block and it is up to the caller to check the block match and act accordingly." Core advanceDisi does that check; this query's guard covers one value-less document only.
  • History. Before #15989 the query wrapped its two-phase iterator in core DocValuesRangeIterator, whose approximation advanced the value cursor itself, so the cursor always sat on the document. #15989 swapped in the bare block approximation plus this guard; its CHANGES entry (10.5.0, Improvements) announces no change of results (lucene/CHANGES.txt:1104-1105).
  • Tests. The upstream duel TestSortedDvMultiRangeQuery.testDuelWithStandardDisjunction gives every document 1 to 10 values (TestSortedDvMultiRangeQuery.java:93), so it never builds two value-less documents in a row; testMissingField (:400-413) has no document with the field at all.
The devil's-advocate check172 words

Strongest case for "not a bug": the class is sandbox and @lucene.experimental, and a block approximation is allowed to be coarse; SkipBlockRangeIterator even has Match.YES_IF_PRESENT for blocks where only documents with a value match, so a sparse skip-indexed field could be called a corner case the sandbox query need not handle.

Why it fails: a coarse approximation is fine, but the two-phase contract makes matches() exact for the approximation's document, and the query already tries to handle value-less documents (the guard), just not two in a row. No javadoc of the query, the builder, indexedField or the sandbox package requires every document to have a value; the same data is right without the skip index; and @lucene.experimental marks API instability, not wrong hits. The cross-model reviews (refute and intended-behaviour lenses) rated this defence weak, and the intended-behaviour check found none that survives. What the defence does carry: sandbox status and the opt-in skip index lower the priority and the number of users hit, which is why this is Medium, not High.

Suggested fix

#

Recommended (a) Advance if behind, then require the cursor on the document (recommended, validated)

In matches(), advance the value cursor only if it is behind, then return false unless it sits on the document, the check that core DocValuesRangeIterator already makes. The repro then passes (assertions on and off), as do the multi-range suites at 10 iterations, the sandbox module and the format check; it composes with the LFV-1463 and LFV-1464 fixes.

int doc = approximation().docID();
if (values.docID() < doc) {
  values.advance(doc);
}
if (values.docID() != doc) {
  // doc has no value: the skip-block approximation returns every doc of a block
  return false;
}

(a) Advance if behind, then require the cursor on the document (recommended, validated)

#

The diff: the guard at SortedNumericDocValuesMultiRangeQuery.java:237 split in two, plus a comment (+5/-1 lines).

int doc = approximation().docID();

Trade-offs

  • The same check as core DocValuesRangeIterator.advanceDisi. Without a skip index the approximation is the cursor itself, so values.docID() == doc always holds and nothing changes there.
  • Cost: at most one extra int comparison per matches() call (not benchmarked). No API change.
  • It touches only matches(): combined with the fixes for LFV-1463 and LFV-1464 (other lines of the same class), the three upstream multi-range suites pass (10 iterations, 240 tests run).

(b) Build the query on the core iterator (not run)

#

Add a core DocValuesRangeIterator factory that takes a SortedNumericDocValues, a skipper, the overall [min, max] and a per-document predicate, and use it here as SortedSetDocValuesMultiRangeQuery uses forOrdinalRange/forOrdinalSet.

Trade-offs

  • Shares the core cursor handling and could use the block classification, but it is a new core API for a sandbox caller and a bigger review; (a) is enough to fix the bug. Nothing was run.

Downstream note

#

An application that uses this sandbox query as an access or visibility filter could return documents it should exclude, or under MUST_NOT hide documents it should show; that depends on the application, and Lucene documents no such guarantee.

How it was found

#

While modelling the doc-values skip index and every consumer of it, the sandbox query was seen to repeat the core value-cursor check without its equality test. A four-document JUnit witnessed it, and a bounded-exhaustive comparison of the real jar against an exact reference (8,953,416 checks) confirmed the extra-hit, missed-hit and exception faces.

The method in full223 words

Method: a component model of the doc-values skip index lists each consumer and the obligation the skipper documents for it (blocks contain value-less documents; the caller checks). The core DocValuesRangeIterator.advanceDisi meets it with an equality test; the sandbox query's guard tests only docID() < doc. A four-document public-API JUnit witnessed the gap on main.

The bounded-exhaustive translation validation then ran the real jar on every pattern of 1 to 5 multi-valued documents (each with none, one or two of the values 1, 50 and 150) or 1 to 7 single-valued documents (none or one of them), skip intervals 2, 3 and the default, 9 range sets and 4 query contexts (alone, FILTER beside a dense term query, MUST_NOT, count), 8,953,416 checks on ByteBuffersDirectory with the default codec, against an exact reference semantics and an executable model of the stock cursor (0 mismatches between that model and the stock jar over the modelled cases; 3,463 reads past the last value are not modelled; with the fix the stock model and the fixed jar differ, as they should). It found the faces listed above, nothing without a skip index, and nothing with the fix. The test was then reduced to the repro. The check is bounded (these values and sizes, one Directory, one codec): strong regression evidence, not a proof for every input.

LFV-1462, snapshot of 2026-11-10

Registry title
Sandbox SortedNumericDocValuesMultiRangeQuery on a skip-indexed numeric field judges a document without a value by a later document's values once two value-less documents follow each other in a matching skip block, so it returns extra hits, misses hits or fails with a doc-values read exception (values 1, none, none, 50 with the ranges [40,60] and [100,200] count 2, not 1); since 10.5.0
Area
sandbox / doc-values multi-range query (DocValuesMultiRangeQuery.SortedNumericStabbingBuilder -> SortedNumericDocValuesMultiRangeQuery) over the doc-values skip index (core SkipBlockRangeIterator approximation)
Priority
Medium, rank 199: On a sparse numeric field with the opt-in doc-values skip index, the sandbox numeric multi-range query with two or more ranges silently returns extra hits, and on multi-valued fields also misses hits or fails with a doc-values read exception, whenever two documents without a value sit next to each other in a matching skip block, in released 10.5.0 through 10.6.0. Ordinary sparse data triggers it, but its reach is narrow because it needs both the sandbox-only builder and the opt-in skip index.
Impact class
silent wrong results
Impact note
Users of the sandbox (@lucene.experimental) builder DocValuesMultiRangeQuery.SortedNumericStabbingBuilder with two or more ranges on a numeric doc-values field that has a skip index (SortedNumericDocValuesField.indexedField or NumericDocValuesField.indexedField, an opt-in) get wrong hit sets with no error, with -ea and -da, the default codec and skip interval and no scale, whenever two documents without the field follow each other inside a skip block that overlaps the query's span: a value-less document is returned as a hit, and on multi-valued fields a later document is judged by the next document's values (missing or extra hits) or the read runs past the last value and the query fails (IndexOutOfBoundsException on ByteBuffersDirectory, a RuntimeException wrapping EOFException 'read past EOF' on MMapDirectory and NIOFSDirectory); the same holds as a FILTER, under MUST_NOT and in IndexSearcher.count; one range, no skip index or the SortedSet variant are unaffected; released 10.5.0 through 10.6.0.
Summary
You index four documents whose field f, added with SortedNumericDocValuesField.indexedField (doc values with a skip index, default codec), holds 1, nothing, nothing and 50, and count the hits of new DocValuesMultiRangeQuery.SortedNumericStabbingBuilder("f").add(40, 60).add(100, 200).build(); you expect 1, the document with 50, since the query is documented as the union of its ranges, and that is what the same query gives without a skip index or as a BooleanQuery of the two core range queries. Instead the count is 2: with a skip index the query visits every document of a matching block, matches() on the first value-less document moves the value cursor on to the document with 50 and returns false, and matches() on the second value-less document finds the cursor already past it, skips the presence check and judges it by the value 50. On multi-valued fields that later document's values are then used up, so it is judged by the following document's values, or the read runs past the last value and throws.
