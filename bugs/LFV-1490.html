Results stay right; only the speed-up is lost.

The finding in 30 seconds

#

New in 11.0: the test below fails 1 of 1 on the 11.0 branch (branch_11x daa54f2e0cd3), with assertions on and off, and passes 1 of 1 on 10.6.0, so 10.6.0 does not have this defect and 11.0.0 would be the first release with it. The query cache is split into 16 partitions, each with a sixteenth of the room. An entry's partition is the lowest four bits of the query's hash code, taken as they are. For an exact numeric filter those bits are the same for every value, so all such filters of one kind on a field share one partition.

Background: the query cache in 11.0

#
  1. LRUQueryCache remembers, per segment, which documents a filter matches, so that the next search with the same filter can skip that work. One remembered set is one entry; maxSize limits the number of entries.
  2. In 11.0 the cache is off by default. MIGRATE.md shows how to turn it back on: IndexSearcher.setDefaultQueryCache(new LRUQueryCache(1_000, 50 MB)).
  3. New in 11.0, the cache is split into 16 partitions to reduce lock contention. Each partition gets maxSize / 16 entries and evicts its own least recently used entries. All entries of one query go to one partition.

The finding, step by step

#
  1. Turn the query cache on (it is off by default in 11.0) the way MIGRATE.md shows: new LRUQueryCache(1_000, 50 MB) with the default caching policy. Search one segment of 10,000 documents with 100 different exact filters, IntPoint.newExactQuery("f", 0) to ("f", 99), in turn, three times.
  2. You expect 100 cache hits. The default policy caches a point filter on its second use, so the third use of each filter is served from the cache, and 100 cached sets need only 100 of the 1,000 entries. 10.6.0 counts 100.
  3. On the 11.0 branch and on main, cache.getHitCount() is 0. The cache stored 200 sets, evicted 138 and holds 62.
  4. Why: the cache has 16 partitions of 1,000 / 16 = 62 entries, and picks one from the lowest four bits of the cached query's hash code (hashCode() & 15). For an exact numeric query these bits do not depend on the value, so all 100 filters go to partition 14 and the other 15 stay empty. 62 filters get 62 hits; 63 get 0.
  5. Every search still returns the right hits. A cache with one partition, or with maxSize 1,600, serves all 100. So does mixing the hash code before the partition is picked: the 100 filters then spread over all 16 partitions, at most 10 in one.

Who is affected

#

Applications on 11.0 or main that install an LRUQueryCache and repeat different exact numeric filters of one kind on one field, such as a tenant or status id. With maxSize 1,000, 63 such filters on one segment, or 7 over 10 segments, are never served when used in turn. Opt-in, performance only: results stay right, and no release has it.

Mechanism, terms and numbers959 words

On main and on branch_11x, LRUQueryCache is split into 16 partitions (#15558), each with maxSize / 16 entries and maxRamBytesUsed / 16 bytes and its own eviction. Since #16657 (fadd63e0eb4, merged 2026-09-29) an entry's partition is query.hashCode() & (numberOfPartitions - 1): the lowest four bits of the query's hash code, taken as they are. For an exact numeric filter those bits do not depend on the value: PointRangeQuery.hashCode() is a polynomial in 31, and with equal lower and upper bounds the value's hash is multiplied by 31^3 + 31^2 = 30,752 = 961 x 32. So all exact filters of one kind on one field share one partition; the query class, the field name and the point layout decide which. With the cache MIGRATE.md shows, new LRUQueryCache(1_000, 50 MB), a partition holds 62 entries. In the repro, 100 exact IntPoint filters on a one-segment index, each used three times with the default caching policy, get 0 cache hits on main and on branch_11x (200 sets stored, 138 evicted, 62 held), where 10.6.0, 10.5.2 and 9.12.3 count 100. This is performance only: every search returns the right hits, the cache is off by default in 11.0, and no release contains this code; 11.0.0 would be the first. A change of three lines and one import that mixes the hash code before the mask spreads the 100 filters over all 16 partitions and restores 100 of 100; it was validated with TestLRUQueryCache and the core search tests. The zero-hit symptom also needs the fixed share of each partition, which is a separate finding (LFV-054) with its own fix.

The code (main 781025d6fe32)

#
  1. Always 16 partitions. new LRUQueryCache(maxSize, maxRamBytesUsed) (LRUQueryCache.java:251-253) calls the four-argument constructor, which passes numberOfPartitions = 16 (:145-151). Only the expert six-argument constructor lets the caller choose (:169-175).
  2. Fixed shares. Each partition is created with maxSize / numberOfPartitions entries and maxRamBytesUsed / numberOfPartitions bytes (:191-196): 1,000 / 16 = 62. A partition evicts its own least recently used entries when it alone is over its share (requiresEviction, :1214-1221; evictIfNecessary, :1223-1248).
  3. The routing. get (:420-428) and putIfAbsent (:430-440) compute int partitionNumber = queryHash & (this.numberOfPartitions - 1); (:426, :437), and getPartitionNumber(Query) returns query.hashCode() & (this.numberOfPartitions - 1) (:1273-1279; used by cleanUp, :1409). There is no mixing step: with 16 partitions the partition is the lowest four bits of Query.hashCode().
  4. The hash. IntPoint.newExactQuery(field, value) is newRangeQuery(field, value, value) (IntPoint.java:173-175), a PointRangeQuery. Its hashCode() (PointRangeQuery.java:479-488) is 31^5 C + 31^4 F + 31^3 L + 31^2 U + 31 numDims + bytesPerDim, with C the class hash, F the field hash, L and U the hashes of the two bounds. For an exact query L = U, so the value enters as (31^3 + 31^2) L = 30,752 L = 961 x 32 x L: a multiple of 32. The lowest five bits depend on the query class, the field name and the point layout only, never on the value.
  5. Result. Every IntPoint exact query on field f has hashCode() & 15 == 14. All their entries go to partition 14, which holds 62; the other 15 partitions stay empty. The query that is hashed and stored is the point query itself, not the ConstantScoreQuery the test wraps it in (:422 and :432 assert that; the stored class is a PointRangeQuery). The wrappers have other hash codes (& 15 == 4), which the cache never uses.
  6. Why not one is served. The default policy caches a point query on its second use (UsageTrackingQueryCachingPolicy.java:122-124, :45-54). On the second use the 100 sets are stored one after the other, and from the 63rd on each insert evicts the oldest; filters 38 to 99 remain. On the third use filter 0 is looked up, is not there, is computed and stored again, and that evicts filter 38; and so on. Each lookup misses because its entry was evicted to make room for an earlier one: 200 sets stored, 0 hits.

Before #16657 the partition was queryCacheKey.hashCode() & (numberOfPartitions - 1), and the key's hash was built from identity hash codes of the segment key and of the query object. Those do not depend on the query's value; nothing guarantees how they spread, but the test passes on that commit. In the releases (10.6.0 and earlier) the cache has no partitions: one map, limits for the whole cache.

Exposure and likelihood717 words
  • Who. An application on 11.0 or main that installs an LRUQueryCache and repeats several different exact numeric filters of one kind on one field. The point-query forms (IntPoint.newExactQuery and its siblings) are cached by the default caching policy on their second use, the earliest it caches anything; the IntField/LongField and doc-values forms from the fifth use, a BooleanQuery of two exact filters from the fourth (UsageTrackingQueryCachingPolicy.java:122-137). The policy counts uses among its last 256 tracked filter uses (:109-114, :161-171): in a re-check with 200 different filters used in turn, the IntField forms were never cached.
  • Opt-in. The query cache is off by default on main and branch_11x (IndexSearcher.java:84, #14187; it is on in 10.6.0). The recipe in MIGRATE.md and both ordinary public constructors build the 16-partition cache.
  • No scale needed. What counts is filters times cacheable segments against 62 (with maxSize 1,000). One segment: 63 filters. Ten segments: 6 filters are served (60 of 60 lookups), 7 are not (0 of 70; 10.6.0: 70 of 70).
  • What is lost. Only the benefit of the cache: each use computes and stores the filter's set again and never reuses it.
  • Which filters. A hash probe on the real classes, 4,096 values per family, finds one partition for the exact queries of IntPoint, LongPoint, FloatPoint, DoublePoint, InetAddressPoint, IntField and LongField, the slow doc-values exact queries, and a BooleanQuery of two exact filters. Point set queries of two neighbouring values use one partition for 256 consecutive values.
  • One partition per kind, not per field name. Each kind of exact query has its own partition: on field f, 14 for IntPoint and DoublePoint, 9 for LongPoint, 11 for FloatPoint and InetAddressPoint. On an IntField field f, IntPoint.newExactQuery entries go to partition 14 and IntField.newExactQuery entries to partition 5. So the statement is "all exact filters of one kind on one field". It is about queries that reach the cache: an exact query for a value outside the indexed range is rewritten to MatchNoDocsQuery (PointRangeQuery.java:544-572), which the default policy never caches.
  • Ranges of one width. Int and long point ranges with upper minus lower below 256 use one or two neighbouring partitions (two to four for the larger differences that were run). Whether the cache is lost depends on how the filters split. With the filters used in turn, a filter was served exactly when its partition had to hold at most 62 entries, in each of 30 workloads on main and branch_11x (10.6.0 served every filter of each). Examples: 100 ranges [200+i, 299+i] on one segment split 56 and 44 and are all served; of 100 ranges [i*10, i*10+9] 3 are served; of 100 ranges [i, i+9] none; of 20 LongField ranges [i*550, i*550+500] over 10 segments 2; of 20 doc-values ranges of one width over 10 segments none.
  • "Zero" is for use in turn. Used forwards and then backwards, an overfull partition still served the filters that fit (6 of 7 ranges over 10 segments).
  • Not affected. Search results: 0 wrong hit counts in every probe run, and 120 searches compared with a searcher without a cache showed 0 differences. TermQuery, WildcardQuery and TermRangeQuery keys spread evenly. Exact filters on 20 different fields spread too: the crowding is per query class and field.
  • One partition also means one lock. The class javadoc gives "to reduce lock contention" as the purpose of the partitions (LRUQueryCache.java:66); all exact filters of one kind on a field use the same partition's lock. No timing is claimed: no benchmark was run.
  • Reach beyond the recipe (read, not run). Applications that install their own LRUQueryCache get the partitioned cache when they move to Lucene 11. elastic/elasticsearch#163523 (open) tracks Elasticsearch's adaptation to it.
  • Likelihood: common among those who turn the cache on. A handful of exact numeric filters on one field over several segments is an ordinary workload. This is an assessment, not usage data: no release has the partitioned cache yet.
  • Ways around it today (measured). The expert constructor with numberOfPartitions = 1, or a maxSize 16 times what the filters need (a workload bound by RAM needs a larger maxRamBytesUsed too: each partition gets a sixteenth of both limits).

More files, environment, full output448 words

TestLRUQueryCacheExactPointFilters (58 lines with the license header, package org.apache.lucene.search, public API plus the test framework, one thread, no randomness of its own). It checks cache hits only; it compares no search result, and none is wrong.

Why this shape:

  • One segment, many filters. Every filter has exactly one cache entry, so only the routing of different queries is tested. The rule that all entries of one query share a partition plays no part.
  • 10,000 documents. The two-argument constructor caches only on segments of at least 10,000 documents.
  • One segment, by construction. The default IndexWriterConfig flushes these 10,000 small documents once, at close. The test does not assert the leaf count; a maintainer may ask for that.
  • 100 filters. They need 100 of the 1,000 entries and go round a partition of 62. 63 is the boundary; 100 was taken so the number does not look tuned.
  • The filters are built once and reused. With reused Query objects the test passes on the parent of #16657 and fails from #16657 on.
  • ConstantScoreQuery, the explicit policy, three uses. A top-level query that needs scores is not cached. The test framework replaces the static default policy, so the test sets UsageTrackingQueryCachingPolicy itself. The policy caches a point query on its second use, so only the third use can hit.
  • The expected 100 is the release behaviour, not a documented number. With the fix it holds because these 100 filters land at most 10 in a partition. A maintainer may prefer an assertion on how many partitions a family of exact filters uses; that needs package-private access.
  • The outcome does not depend on the seed: 30 of 30 seeds fail on main, and 30 of 30 pass with the fix and on 10.6.0 (all with assertions on).

Ranges of one width, which the finding also covers, are not part of this test.

Why it looks unintended

#
  • 10.6.0, 10.5.2 and 9.12.3 serve the same 100 filters. The MIGRATE.md recipe "to enable caching back" serves none.
  • The design discussion expects different queries to go to different partitions (#15558). The only crowding it names is one hot query (#16657).
  • The getCacheCount javadoc calls storing sets that are never reused undesirable. Here: 200 stored, 0 hits.
The full argument512 words

There is no hit-rate contract. maxSize is an upper bound ("cache at most maxSize cache entries", LRUQueryCache.java:244-245) and the class is @lucene.experimental (:117). So this is a performance regression against the releases, not a broken API promise. The argument is the release behaviour, the stated purpose and the stated design:

  • The releases serve it. The same test counts 100 on 10.6.0, 10.5.2 and 9.12.3. MIGRATE.md presents its recipe as the way "to enable caching back" (lucene/MIGRATE.md:328-335); with that recipe the test counts 0.
  • The class's own description of a healthy cache. getCacheCount javadoc (:738-742 at main 781025d6fe32): "It is highly desirable to have a hit count that is much higher than the cache count as the opposite would indicate that the query cache makes efforts in order to cache queries but then they do not get reused." Here the cache count is 200 and the hit count 0.
  • The design discussion expects different queries to spread. On #15558, which added the partitions, the PR author wrote in a conversation comment: "divide the cache into multiple partitions(similar to what guava cache does) and each partition has its own read/write lock. So overall for different queries, we go to a different partition(hashkey being "query + segment")". On #16657, which changed the routing to the query alone, they name one trade-off, a single query: "a hot-query segments concentrate in one partition", and benchmark "Single hot query - as it is always routed to the same partition" as the worst case. Neither thread mentions different queries that share low hash bits. These sentences describe what the author expected, not a guarantee that different queries never share a partition.
  • The named model mixes the hash. Guava's cache applies a supplemental hash before it picks a segment (LocalCache.rehash: "defends against poor quality hash functions. This is critical when the concurrent hash map uses power-of-two length hash tables"). Ben Manes's 2019 sketch patch for this class on LUCENE-9038 (#10081) did the same before masking the query's hash code.
  • The hash code is a proper one. The Query.hashCode javadoc asks only to "implement query hash code properly ... so that QueryCache works properly" (Query.java:109-116). PointRangeQuery's is the usual times-31 form, in place since LUCENE-6793 (2016). The query cache of the releases never takes its low bits unmixed.
  • Nothing announces it. MIGRATE.md (:613-621) and the class javadoc (LRUQueryCache.java:66-68) say the cache is partitioned and keyed by (query, segment); the two CHANGES.txt entries (:291, :392-393) name only the refactoring and the hashCode/RAM-accounting fix. Nothing says that a family of different queries may be confined to a sixteenth of the cache.
  • The tests and the benchmark could not see it. No test in TestLRUQueryCache asserts which partition a query uses. The upstream benchmark keys the cache with TermQuery on random terms (LRUQueryCacheBenchmark.java:116), whose hash codes spread.
  • A precedent for fixing a cache that silently never helps. #12140 (type:bug, fixed 2023): the query cache never cached on an index of 34 equal segments.
The devil's-advocate check425 words

The strongest case for "intended": the cache is optional and experimental. maxSize is an upper bound, and no hit rate or hash distribution is promised. Routing by the query alone was chosen on purpose in #16657, so that each partition sees all entries of a query and counts its RAM once (the comment at LRUQueryCache.java:1273-1276 on main 781025d6fe32). Fixed shares per partition are part of the design of #15558. The quality of hashCode() is the query's business, and core masks raw query hash codes elsewhere too: the default policy's frequency table (FrequencyTrackingRingBuffer.java:126). And there are ways out: one partition, or a larger maxSize.

Why it fails: those points defend routing by the query and fixed shares. They do not defend taking the unmixed low bits, so that different queries crowd into one partition. The design discussion expects different queries to go to different partitions, and the only concentration it names is one hot query. The fix keeps the design: the partition is still a function of the query alone. The queries with constant low bits are Lucene's own numeric queries. In the policy's table, which uses open addressing, clustered keys only lengthen a probe; here they cost capacity. The ways out cost a maxSize of 16 times what the filters need (a workload bound by RAM would need a larger maxRamBytesUsed too) or give up the partitions.

What remains: a maintainer may label it an improvement and not a bug, or answer that the fixed shares (LFV-054) are the larger problem; a cache-wide budget would make this test pass too, so the two findings can look like one. The zero is for filters used in turn, and no benchmark was run. All of that is fair for a Low finding in unreleased code.

Maintainers have been divided on weak hash codes. LUCENE-10610 (#11646, open since 2022) is about RunAutomaton.hashCode() giving equal hash codes for different automata. In date order: Uwe Schindler, 2022-06-10: "it is a kind of bug - but only makes lookups ineffective"; Robert Muir, 2022-06-10: "could be considered good enough for a hashcode ... I personally feel a collision is OK"; Uwe Schindler, 2022-06-11: "Which is unfortunate, but not a bug. You just get more hash collisions."; and in Uwe Schindler's last comment there, 2022-06-11: "I would just make the already existing hashCode bug free ... This would make query cache work fine, that's all needed." The issue is still open. It is another defect (different automata with equal full hash codes), yet a similar answer is possible here.

Suggested fix

#

Recommended Mix the hash code before the partition mask (validated)

Mix the query's hash code before taking its low bits: BitMixer.mix(queryHash) & (numberOfPartitions - 1) at the three routing expressions (+4/-3 lines). The partition still depends on the query alone. Validated: the test passes, TestLRUQueryCache and the core search tests pass, the module's checks are clean. It does not change the fixed share per partition.

// get (:426) and putIfAbsent (:437)
int partitionNumber = BitMixer.mix(queryHash) & (this.numberOfPartitions - 1);

// getPartitionNumber (:1278 at main 781025d6fe32)
return BitMixer.mix(query.hashCode()) & (this.numberOfPartitions - 1);

Mix the hash code before the partition mask (validated) (recommended)

#

At the three routing expressions of LRUQueryCache (get, putIfAbsent, getPartitionNumber), pass the query's hash code through BitMixer.mix before the mask. BitMixer (org.apache.lucene.internal.hppc) is already in core; mix(int) is the murmur3 finalizer. One file, +4/-3 lines: one import line and the three expressions.

The partition stays a function of the query alone, so the design of #16657 (one canonical instance of each query per partition, its RAM counted once) is untouched. The idea is not new: Ben Manes's 2019 sketch patch on LUCENE-9038 (#10081) and Guava's cache mix the hash before masking it.

// get (:426) and putIfAbsent (:437)
int partitionNumber = BitMixer.mix(queryHash) & (this.numberOfPartitions - 1);

// getPartitionNumber (:1278 at main 781025d6fe32)
return BitMixer.mix(query.hashCode()) & (this.numberOfPartitions - 1);

Trade-offs

  • Cost: one BitMixer.mix call (two multiplications and three xor-shifts) per get and putIfAbsent, after the query's hash code has been computed anyway. No benchmark was run.
  • Not a cure for fixed shares: it does not change the 1/16 share per partition (LFV-054) and does not remove ordinary imbalance. After mixing, a partition can still get more than its share by chance, and those entries are then lost. In a probe with a tight RAM budget, 53 of 64 filters were served with this fix and 64 of 64 on 10.6.0.
  • Three expressions. A small private helper would keep them in sync; it is not in the validated diff.
  • Not run: nightly tests and the JMH benchmark LRUQueryCacheBenchmark.

A cache-wide budget instead of fixed shares (the fix of LFV-054)

#

Keep the routing, but apply maxSize and maxRamBytesUsed to the cache as a whole. With it in place of the hash mix, the repro test passes with the routing unchanged.

Trade-offs

The larger change (budget and eviction code), and it leaves all exact numeric filters of one kind on a field in one partition, behind one lock. The two fixes are independent: LFV-054's own test still fails with the hash mix alone. Not built for this doc; run earlier.

Change the hash codes of the numeric queries

#

Give PointRangeQuery.hashCode() and the other numeric query classes low bits that depend on the value.

Trade-offs

It touches many classes (point, doc-values, IntField/LongField and prefix queries), changes long-standing hash codes (PointRangeQuery's form dates from 2016), and leaves any Query class from outside Lucene with weak low bits exposed. The routing is one place; the hash codes are many classes. Not built.

Workaround for applications today

#

Build the cache with one partition, new LRUQueryCache(maxSize, maxRamBytesUsed, leavesToCache, skipCacheFactor, 1, null), or with a maxSize 16 times what the filters need. With the 100 filters of the repro: one partition gives 100 hits; maxSize 1,600 gives 100, 1,599 gives 0. The null clean-up parameter is what the ordinary constructors pass too (LRUQueryCache.java:150); with it the caller invokes cleanUp() to remove stale entries (:166-167).

Trade-offs

Not a fix: one partition gives up what the partitions are for, and the larger maxSize raises the limit for every other query too. A workload bound by RAM needs a larger maxRamBytesUsed as well: each partition gets a sixteenth of both limits (:191-192).

Downstream note

#

Read, not run: a product that installs its own LRUQueryCache, as Elasticsearch does, gets the partitioned cache with Lucene 11; whether its filters then crowd into one partition was not tested, and the only possible effect is slower repeated filters.

How it was found

#

Semi-formal. A differential run of the query cache showed exact filters that were cached and never served. A bounded-exhaustive check of the routing on the real classes, 33 filter families with 4,096 values each, then showed which families crowd into few partitions. The case was reduced to one public-API test.

The method in full173 words

Method: semi-formal.

  • Differential run. A differential, model-based run of the query cache's hot loop had a side observation: of 64 exact filters, 16 were cached and none was served. A second probe with the public two-argument constructor and the default caching policy gave 0 of 20 filters served over 10 segments.
  • Bounded-exhaustive check of the routing. For 33 filter families, 4,096 values each (exact filters, set and multi-term filters, conjunctions, sliding ranges of every width from 1 to 64, time windows), the cache key was taken from the real rewrite-and-weight pipeline through a recording QueryCache, and hashCode() & (n - 1) was counted for n from 2 to 64, against the same with the hash mixed. 25 of the 33 families crowd into few partitions with today's routing; none does with the mix.
  • Reduction. First to a public-API test with 20 filters over 10 segments, measured before and after #16657; a later minimality check replaced it with the one-segment test of the repro, in which every filter has exactly one cache entry.

LFV-1490, snapshot of 2026-11-23

Registry title
LRUQueryCache on main and branch_11x picks an entry's partition from the unmixed low bits of Query.hashCode(), so all exact numeric filters of one kind on a field share one of the 16 partitions and evict each other: 100 exact IntPoint filters on one segment get 0 cache hits where 10.6.0 serves all 100 (performance only, unreleased; 11.0.0 would ship it)
Area
search / query cache (LRUQueryCache partition routing: the partitioned cache of #15558 as changed by #16657; main and branch_11x only)
Priority
Low, rank 845: Only on unreleased main and branch_11x, and only when the opt-in query cache is turned on, all exact numeric filters of one kind on a field are routed to the same one of the cache's 16 partitions, each limited to a sixteenth of the cache, so with the 1,000-entry cache of the MIGRATE.md example 100 such filters on one segment get no cache hits where 10.6.0 serves all 100 on their third use. It is Low because search results stay correct (performance only), the cache is off by default, no release has it yet (11.0.0 would be the first), and a one-partition cache, or a maxSize of 16 times what the filters need, avoids it.
Impact class
minor
Impact note
Hits only applications on unreleased code (main and branch_11x; 11.0.0 would be the first release with it) that turn the query cache on (it is off by default there since #14187; the recipe in MIGRATE.md and both ordinary public constructors build the 16-partition cache) and repeat several different exact numeric filters, or numeric ranges of one width, on one field: exact filters of one kind all go to one partition, and int or long ranges of one width (IntPoint, LongPoint, IntField or LongField) to one or two neighbouring partitions (up to four when upper minus lower is above 255, in the runs), each of which holds one sixteenth of the cache, so with the 1,000-entry cache of MIGRATE.md and the default caching policy about 7 exact filters over 10 cacheable segments already overflow it and are computed and stored again on every use instead of being served; no scale is needed, search results stay correct (performance only), the releases serve the same workload from the cache (10.6.0, 10.5.2 and 9.12.3 were run; no release has the partitions), and the expert constructor with one partition, or a maxSize of 16 times what the filters need, avoids it. Update 2026-11-14: for ranges of one width the loss depends on how the filters split over these partitions (executed on main 781025d6fe32 and branch_11x daa54f2e0cd3, with -ea and -da). With the 1,000-entry cache and the filters used in turn, a filter was served exactly when its partition had to hold at most 62 entries (the filters routed to it times the segments), in each of 30 workloads. So such a workload is served in full when every partition it uses fits (100 IntPoint ranges [200+i, 299+i] on one segment split 56 and 44: 100 of 100), not at all when none fits (20 IntPoint ranges [i*400, i*400+100] over 10 segments put 70 and 130 entries into two partitions: 0 of 20; 100 IntPoint ranges [i, i+9] on one segment share one: 0 of 100) and in part otherwise (20 LongField ranges [i*550, i*550+500] over 10 segments split 18 and 2: 2 of 20). Doc-values ranges of one width with bounds from 0 to below 2^32 went to one partition in every case run, as exact filters do (20 over 10 segments: 0 of 20). Used forwards and then backwards instead of in turn, an overfull partition still served the filters that fit (6 of 7 ranges over 10 segments). 10.6.0 serves every filter of these workloads (executed).
Summary
On main or branch_11x you turn the query cache on the way MIGRATE.md shows (new LRUQueryCache(1_000, 50 MB), the default caching policy) and run 100 different exact filters on one int field (IntPoint.newExactQuery) three times each over a one-segment index. You expect the third use of each filter to be served from the cache, as on 10.6.0: the filters need 100 of the cache's 1,000 entries. Instead not one lookup is a cache hit (0 of 100; 10.6.0: 100 of 100), because the cache picks one of its 16 partitions from the lowest four bits of the query's hash code, those bits are the same for every exact numeric filter of one kind on a field, and that one partition holds only 62 entries, so the filters keep evicting each other. No search result is wrong: only the benefit of the cache is lost. No release has this code.
