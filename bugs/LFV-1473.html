query(), tf() and termfreq() function values turn a failed index read into a RuntimeException instead of the declared IOException

If a postings read fails while a FunctionQuery over QueryValueSource scores (or while TFValueSource or TermFreqValueSource iterate their postings), IndexSearcher.search throws a RuntimeException wrapping the IOException that every method on the way declares. Code that catches IOException around the search misses it (no result is wrong); since 7.0.0.

The finding in 30 seconds

#

A function query asks its value source for one number per document. Three value sources read postings to get that number, and when the read fails they hide the declared IOException inside a RuntimeException.

Function queries in brief

#
  1. A FunctionQuery scores every document with a ValueSource. Per segment, the value source returns a FunctionValues, and the scorer calls its floatVal(doc) for each document.
  2. QueryValueSource returns the score of an inner query; TFValueSource and TermFreqValueSource return a term's frequency in the document. All three read postings to do so.
  3. Reading index data can fail. Since 7.0.0 every FunctionValues accessor, and the function query's scorer, declares throws IOException, so the error can reach the caller as it is.

The finding, step by step

#
  1. Index one document with f:a and open it through a reader whose postings read fails with IOException("simulated read failure"), as a failing disk or a corrupt index can.
  2. Run searcher.search(new FunctionQuery(new QueryValueSource(new TermQuery(f:a), 0f)), 10): each document's score is the score of the inner query f:a.
  3. You expect the IOException: FunctionValues.floatVal, the function query's scorer and IndexSearcher.search all declare it, and the core DoubleValuesSource.fromQuery(f:a) path for the same inner query delivers it.
  4. Instead you get RuntimeException: caught exception in QueryDocVals(f:a) doc=0, with the IOException only as its cause. tf() and termfreq() wrap the same way when the read fails while they iterate the postings (caught exception in function tf(f,a) : doc=0); a failure while they open them, as in this test, arrives as the IOException.
  5. Why: these wraps predate 7.0.0, when the methods could not throw IOException. The 7.0 change that let them throw it removed the identical wrap from one other value source and left these three.

Who is affected

#

Applications that score, sort or filter with query(), tf() or termfreq() value sources and handle IOException or CorruptIndexException from a search by type. It takes a postings read that fails while they score (a storage error or a corrupt index). The search still fails and keeps the IOException as cause; no result is wrong.

Mechanism, terms and numbers560 words

Three value sources of the function-query package, QueryValueSource (query(...)), TFValueSource (tf(...)) and TermFreqValueSource (termfreq(...)), catch the IOException from their postings or inner-query reads and rethrow it as new RuntimeException("caught exception in ...", e). The methods they do it in override FunctionValues accessors that declare IOException since 7.0.0, and the function query's scorer and IndexSearcher.search declare it too. So when a read fails while such a function query scores (for tf() and termfreq(): a read while they iterate the postings), the search throws a plain RuntimeException, and code that catches IOException or CorruptIndexException around the search misses it. The search still fails, the IOException stays the cause and no result is wrong. The wraps were required before 7.0.0; the change that made them unnecessary (LUCENE-7407) removed the identical wrap from JoinDocFreqValueSource and left these three.

Terms

#
  • FunctionValues: the per-segment values of a ValueSource. Its accessors (floatVal, intVal, exists, objectVal, toString(int)) and ValueFiller.fillValue declare IOException (FunctionValues.java:48, :52, :100, :106, :135, :149).
  • FunctionQuery: scores each document with vals.floatVal(docID()) in AllScorer.score() throws IOException (FunctionQuery.java:129-131).
  • query(), tf(), termfreq(): how QueryValueSource, TFValueSource and TermFreqValueSource describe themselves (for example tf(f,a)).

The bug

#
  1. QueryValueSource's values class, the package-private QueryDocValues (QueryValueSource.java:89), computes floatVal (:131-138) through exists(doc), which creates the inner query's scorer on first use (weight.scorer(readerContext), :150), advances it (:161) and checks a two-phase match (:166), all inside one try.
  2. When the inner read throws IOException (in the repro: TermQuery's scorer calling TermsEnum.postings), exists catches it (:172) and throws new RuntimeException("caught exception in QueryDocVals(" + q + ") doc=" + doc, e) (:173). floatVal (:135-136) and ValueFiller.fillValue (:207-208, whose one Lucene caller is grouping's ValueSourceGroupSelector) have the same block; objectVal and toString(int) reach it through floatVal.
  3. TFValueSource.floatVal (TFValueSource.java:133-158) and TermFreqValueSource.intVal (TermFreqValueSource.java:122-147) wrap docs.advance(doc), docs.freq() and the out-of-order reset() the same way: new RuntimeException("caught exception in function " + description() + " : doc=" + doc, e) (TFValueSource.java:154-155, TermFreqValueSource.java:143-144). Their first reset(), which opens the postings, runs from the instance initializer in getValues, outside that try (TFValueSource.java:67-69, TermFreqValueSource.java:56-58), so a failure there arrives as the IOException.
  4. Every one of these methods overrides an accessor that declares IOException, so the wrap is not needed. They are the only five catch (IOException blocks in the whole function package; 91 overrides of these accessors in 35 other files of the package declare IOException and let it through.

The numbers

#

One document, f:a; the reader's postings read throws IOException("simulated read failure"). IndexSearcher.search(new FunctionQuery(new QueryValueSource(new TermQuery(f:a), 0f)), 10) throws RuntimeException: caught exception in QueryDocVals(f:a) doc=0 caused by that IOException, with assertions on and off. The core path for the same inner query, FunctionScoreQuery(MatchAllDocsQuery.INSTANCE, DoubleValuesSource.fromQuery(f:a)), throws the IOException itself (executed on main with this reader). TFValueSource and TermFreqValueSource deliver the IOException with this reader, because the failure comes while they open the postings; with a reader whose postings nextDoc/advance throw they give caught exception in function tf(f,a) : doc=0 and termfreq(f,a) : doc=0 (tf() with a ClassicSimilarity searcher, which it requires).

Exposure and likelihood215 words
  • Who is hit. Users of QueryValueSource, TFValueSource or TermFreqValueSource from lucene/queries in a FunctionQuery; by reading, also a ValueSource sort field (its comparator calls doubleVal, which reaches floatVal / intVal), grouping by a value source (ValueFiller.fillValue), FunctionRangeQuery and the asDoubleValuesSource / asLongValuesSource adapters (not executed). A handler that catches IOException or CorruptIndexException around IndexSearcher.search does not run; the failure arrives as an unexpected RuntimeException.
  • Default or opt-in. Opt-in by using these value sources. query() (the repro) and termfreq() need nothing else: the default codec, searcher and configuration, with assertions on and off. tf() needs a TFIDFSimilarity such as ClassicSimilarity on the searcher. One document is enough.
  • What it takes. A postings read that fails while the function query scores: a storage read error on a Directory whose reads can fail after the reader is open, or a broken index (CorruptIndexException is an IOException). For tf() and termfreq() the failing read must come while they iterate the postings, not while they open them.
  • Bounds. The search still fails loudly, the IOException is kept as the cause (callers that unwrap causes find it), and no result is wrong. Storage failures are uncommon on healthy systems, and the recorded searches found no report of it since 7.0.0. Priority Low.

Why it looks unintended

#
  • Since 7.0.0, floatVal, exists and the other FunctionValues accessors declare IOException, and so do the scorer and IndexSearcher.search.
  • The 7.0 change that added those declarations removed the identical wrap from JoinDocFreqValueSource, but left these three classes alone.
  • The rest of the function package, and the core DoubleValuesSource.fromQuery, let the IOException through.
The full argument234 words
  • The contract. The overridden accessors declare IOException (FunctionValues.java:48, :52, :100, :106, :135, :149); IndexSearcher.search(Query, int, Sort) and Weight.scorer document "@throws IOException if there is a low-level I/O error" (IndexSearcher.java:675, Weight.java:127).
  • The change that made the declarations removed the same wrap elsewhere. LUCENE-7407 (f7aa200d406, 2016-09-21, #8460, first released in 7.0.0) added throws IOException to the accessors and, in the same commit, deleted the identical catch (IOException e) { throw new RuntimeException("caught exception in function " + description() + " : doc=" + doc, e); } from JoinDocFreqValueSource.intVal. Its author, Mike McCandless, wrote on the issue: "I also pushed up throws IOException; I think it's silly we mask this today in doc values." The commit did not touch QueryValueSource, TFValueSource or TermFreqValueSource.
  • Consistency. These are the only five catch (IOException blocks in the function package; the other accessor overrides let the IOException through, and so does the core FunctionScoreQuery over DoubleValuesSource.fromQuery for the same inner query (executed; DoubleValuesSource.java:802-834 has no catch). tf() and termfreq() already let an IOException from opening their postings through, so each is inconsistent with itself.
  • Not documented. No javadoc, test, CHANGES or MIGRATE entry mentions the wrap. LUCENE-8103 (#9151, 2020) and LUCENE-8908 (#9951, 2020) later edited QueryDocValues: objectVal now calls floatVal instead of wrapping on its own, and the other three blocks stayed, without any discussion of the exception type.
The devil's-advocate check235 words

The strongest case comes from the refute lens of an independent reviewer from another model family (OpenAI GPT-5.6), which reproduced the behaviour and agreed on the cause and the fix: a throws clause permits IOException but does not promise that it keeps its type; the wrap adds the query and the document to the message; the 2020 rewrite kept it; FunctionQuery is @lucene.experimental, and TFValueSource and TermFreqValueSource's superclass DocFreqValueSource are @lucene.internal; the failure is loud, the cause is kept and no result is wrong; and a fix changes behaviour for callers that catch RuntimeException today.

Why it is weak: the evidence is circumstantial, not an explicit decision about these three classes, but it points one way. The commit that introduced the declarations deleted the identical wrap from JoinDocFreqValueSource (the only such block it removed in the function package), and its author said on the issue that masking the IOException in doc values was silly; nothing records a reason to keep the other three; the rest of the package and the core path propagate. QueryValueSource and TermFreqValueSource themselves carry no stability tag. What survives is the severity bound (Low) and the runtime-behaviour change: a maintainer may treat it as a cleanup of inconsistent legacy behaviour and list the fix under "Changes in runtime behavior", as #12516 (9.8.0) was. Verdict: most likely a leftover rather than a design choice; a defect of Low priority.

Suggested fix

#

Recommended Declare IOException and delete the five try/catch blocks (validated)

Delete the five try/catch blocks and declare IOException on those overrides and on QueryDocValues.objectVal and toString(int): seven methods in three files, no API change (each overrides a method that already declares it). The repro and the whole lucene/queries module then pass. Callers that catch RuntimeException see a different type ("Changes in runtime behavior").

@Override
public float floatVal(int doc) throws IOException {
  return exists(doc) ? scorer.score() : defVal;
}

Declare IOException and delete the five try/catch blocks (validated) (recommended)

#

Add throws IOException to QueryDocValues.floatVal, exists, objectVal, toString(int) and its ValueFiller.fillValue, to TFValueSource's floatVal and to TermFreqValueSource's intVal, and remove the try { ... } catch (IOException e) { throw new RuntimeException(...); } around their bodies (3 files; +7/-29 ignoring whitespace, +67/-89 with the re-indentation). The core of it:

@Override
public float floatVal(int doc) throws IOException {
  return exists(doc) ? scorer.score() : defVal;
}

Trade-offs

  • No API change: each method overrides one that already declares IOException; QueryDocValues is package-private and the other two are anonymous classes.
  • Callers that catch RuntimeException (or match the "caught exception in" message) see a different type; the query and document number leave the message (the stack trace still names the value source).
  • The out-of-order IllegalArgumentException in QueryDocValues.exists is unchanged.

What the checks validated

  • Scratch worktree of f794ff5a505c, gradle: the test fails on the stock tree and passes with the fix, with assertions on and off; :lucene:queries:tidy leaves the fix unchanged; the whole lucene/queries module with the fix (52 suites with the new test, 513 tests, 0 failures, 5 skipped by the framework) passes; :lucene:queries:check -x test (google-java-format check, ecjLint, forbiddenApis) passes.
  • An executed probe with the same change on main: all three value sources deliver the IOException.

Downstream note

#

Code that treats an IOException from a search as a storage or corruption signal (to retry, fail over or mark an index bad) gets an unexpected RuntimeException instead; nothing else changes.

How it was found

#

Semi-formal: a compiler-attributed scan of Lucene's non-core modules for catch (IOException) blocks that throw a RuntimeException. Reading the hit showed the enclosing methods override FunctionValues accessors that declare IOException, so the wrap is not needed; a one-test public-API JUnit on main confirmed the effect.

The method in full105 words

Method: semi-formal.

  • Pattern scan. A javac-attributed AST scan over the non-core modules flagged every catch (IOException) block that throws a RuntimeException.
  • Triage by reading. For each hit, the enclosing method was checked: may it declare IOException? Here every enclosing method overrides a FunctionValues accessor that already declares it, and its callers declare it too.
  • Witness. A one-test public-API JUnit on stock main f794ff5a505c showed the RuntimeException, and a three-site probe showed the same for tf() and termfreq() while the core FunctionScoreQuery path delivers the IOException.
  • Checks. An independent reproducer, cross-model review lenses, a devil's advocate and an adjudication followed (Independent checks).

History

#

Since 7.0.0 (LUCENE-7407, 2016), when the accessors began to declare IOException. Fails on every executed release from 7.0.0 to 10.6.0 and on main; 6.6.6 behaves the same, but there the wrap was required.

Versions tested6 rows

Introduced by LUCENE-7407, f7aa200d406 ("switch doc values usage to an iterator API ...", Mike McCandless, 2016-09-21, migrated issue #8460; JIRA era, no PR), first released in 7.0.0. It added throws IOException to the accessors, which turned the existing wraps from necessary into a contract mismatch, and removed the identical wrap from JoinDocFreqValueSource.intVal only.

The wraps come from the Solr function-query code: QueryValueSource.floatVal (SOLR-349, 2007), exists and fillValue (2011), TFValueSource and TermFreqValueSource (SOLR-1932, 2010). LUCENE-8103 (2020), LUCENE-8908 (2020) and LUCENE-9570 (2020, formatting) kept them.

A bytecode scan of the released lucene-queries jars finds all three wrap messages in every release 6.0.0-10.6.0, and FunctionValues.floatVal declaring IOException in all 75 releases 7.0.0-10.6.0 and in none of the 18 releases 6.0.0-6.6.6. The tf() and termfreq() sites were also executed on releases: the independent reproducer's one-test-per-source JUnit (postings nextDoc/advance throw) failed 3 of 3 on 10.6.0 (assertions off), 10.5.2 (on, off) and 9.12.3 (off), with the tf(f,a) and termfreq(f,a) wrap messages.
