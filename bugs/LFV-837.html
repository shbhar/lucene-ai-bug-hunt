IndexWriter buffers the first doc-values update of each field twice

IndexWriter stores the first doc-values update of each field twice: a 1 MiB binary update counts 2,162,956 bytes against the RAM buffer (1,114,340 with the fix), about twice each later one, and an update matching 10 documents is applied 20 times. Values stay correct; every release since 7.7.0 is affected.

The finding in 30 seconds

#

One update is stored twice when it creates its field's buffer.

Background: buffered doc-values updates

#
  1. updateNumericDocValue, updateBinaryDocValue and updateDocValues do not rewrite documents at once. Each update (a term, a field, a new value) waits in a per-field in-memory buffer until a flush, commit or NRT reopen applies it.
  2. Applying an update means finding the documents that match its term and recording the new value for each of them in memory; the recorded values are written to the index files later.
  3. Buffered updates count toward the writer's RAM buffer (ramBytesUsed(); 16 MB by default), which decides when the writer flushes.

The finding, step by step

#
  1. You add a document with a binary doc-values field payload, commit, then call updateBinaryDocValue twice on payload with 1 MiB values (terms that match no document) and read ramBytesUsed() after each call.
  2. You expect each call to add about 1 MiB (1,048,576 bytes): an update waits in memory, once, until the writer applies it.
  3. Instead the first call adds 2,162,956 bytes and the second 1,048,576. The field's update buffer already stores the update when it is created, and the caller then adds the same update again.
  4. The copy is applied too: one binary update matching 10 documents is added 20 times to the segment's pending in-memory updates (InfoStream: 1 field updates; 20 new updates). The 10 documents still end with the right value, because the copy is identical.
  5. This repeats whenever a field first appears in a batch of buffered updates. With large binary values the RAM buffer fills sooner, and the 2 GiB apply limit of LFV-838 is reached at roughly half the size (in the recorded run, 1,100 documents x 1 MiB).

Who is affected

#

Every application that updates doc values (updateNumericDocValue, updateBinaryDocValue, updateSortedNumericDocValue, updateDocValues, soft deletes), on the default configuration: the first update of each field in every batch is stored twice. It costs something only with large binary values: earlier flushes, twice the apply work, and LFV-838's writer close at roughly half the size. Values stay correct.

Mechanism, terms and numbers719 words

IndexWriter keeps doc-values updates in a per-field buffer (FieldUpdatesBuffer) until it applies them. When an update arrives for a field that has no buffer yet, BufferedUpdates.addNumericUpdate / addBinaryUpdate create the buffer with that update, and the constructor already records it as entry 0; the methods then call addUpdate (or addNoValue) with the same update, which stores it again as entry 1. This happens whenever a field first appears in a buffered-updates packet: the writer's global buffer and each per-thread buffer.

Effects on main 5adff78bb168: the first 1 MiB binary update of a field adds 2,162,956 bytes to IndexWriter.ramBytesUsed() and each later one 1,048,576, so a writer flushes sooner than its RAM buffer setting implies; when the packet is applied the copy is resolved and applied again, so every matching document gets a second pending in-memory update (InfoStream: 1 field updates; 20 new updates for one update matching 10 documents), and for a binary value that roughly halves the size at which LFV-838 closes the writer. Final values stay correct, because the copy is identical and adjacent, and only the last pending value per document is written. A numeric field whose updates all carry one value through one term field, with no unset update (soft deletes normally qualify), skips the copy when applying, but still stores it.

Lucene 7.6.0 stored each update once; the double insert came with LUCENE-8590 (b0e6a92ede3, 7.7.0). Creating the buffer with the first update and not adding that update again fixes it.

Where the copy comes from

#
  1. Public updates reach the buffer through DocumentsWriterDeleteQueue.java:500-511: NUMERIC and SORTED_NUMERIC go to BufferedUpdates.addNumericUpdate (:507), BINARY to addBinaryUpdate (:510).
  2. BufferedUpdates.java:146-156 (addNumericUpdate, :134-144, is the same) creates a missing buffer with fieldUpdates.computeIfAbsent(update.field, _ -> new FieldUpdatesBuffer(fieldUpdatesBytesUsed, update, docIDUpto)) and then always calls buffer.addUpdate(update.term, update.getValue(), docIDUpto) (:151) or buffer.addNoValue(update.term, docIDUpto) (:153); numFieldUpdates.incrementAndGet() (:155) counts the call once.
  3. The constructor already records the update: FieldUpdatesBuffer.java:49 private int numUpdates = 1;, :76 appends the term, :99 stores the numeric value, :111 appends the binary value. addUpdate (:182-200 numeric, :207-212 binary, value appended at :210) and addNoValue (:202-205) call append (:214-217), which appends the term again and returns numUpdates++: the copy is entry 1.

What the copy does

#
  1. RAM: the term bytes (and the value bytes, when the update has a value) are appended twice, so they count twice in ramBytesUsed().
  2. Apply: FrozenBufferedUpdates logs numFieldUpdates as "field updates" (:107, :214-218) but iterates every stored entry (:246-348): for the copy it seeks the term again (:267) and adds the value again for every matching live document (:342-343, counted as "new updates"). A binary value goes into BinaryDocValuesFieldUpdates.add (BinaryDocValuesFieldUpdates.java:94) twice per document, which is what roughly halves the LFV-838 threshold. These are pending in-memory updates: when they are written, the iterator keeps only the last update per document (DocValuesFieldUpdates.java:441-448), so the doc-values file gets each document once.
  3. Exception: finish() sorts the terms only for a numeric buffer with one shared value, no unset updates and one term field (FieldUpdatesBuffer.java:224, hasSingleValue :268-271); that iterator skips equal adjacent terms (:370-388), so there the copy is stored and counted but not applied again.

Exposure and likelihood242 words
  • Who is hit: callers of updateNumericDocValue (IndexWriter.java:1962), updateBinaryDocValue (:1996), updateSortedNumericDocValue (:2037), updateDocValues (:2070) and softUpdateDocument(s) (:1938, :1664), on any configuration, deterministically: one extra copy of the first update per field per packet (the global buffer and each per-thread buffer). tryUpdateDocValue (:1721) does not go through BufferedUpdates and is not affected.
  • Where it costs something: large binary values. The copy counts in the RAM buffer, so the writer flushes sooner than setRAMBufferSizeMB implies, and when applied the value is added twice per matching document to the pending in-memory updates. Through LFV-838 that roughly halves the size at which one binary update closes the writer: in the recorded run 1,100 documents x 1 MiB (1.07 GiB) closed it when the update was the field's first in the packet, and committed when another update of the field came first (assertions off, 8 GB heap; run in the original verification, not re-run for this doc).
  • Where it is cheap: for numeric updates and soft deletes the copy is little more than one term's bytes (an equal value, field and docIDUpto are not stored again while all entries share them, FieldUpdatesBuffer.java:135-180, :189); soft deletes normally carry one shared value, so they are not applied twice.
  • Not affected: final doc values; this bug alone throws nothing.
  • Priority Low: correct results, and the cost is bounded by one extra copy per field per packet.

Why it looks unintended

#
  • The buffer's own test creates it with the first update and adds only later ones; BufferedUpdates adds the first one again.
  • Lucene 7.6.0 stored each update once; the copy arrived with LUCENE-8590 in 7.7.0, and nothing explains it.
  • A reviewer called the same pattern a bug in a proposed vector method (#16214), and the PR's author fixed that method.
The full argument262 words
  • The class's invariant: the constructor records update 0 (numUpdates = 1, FieldUpdatesBuffer.java:49). TestFieldUpdatesBuffer.testBasics (TestFieldUpdatesBuffer.java:35-88), added in the same commit (as testBascis, renamed with the same body in 0650f995f9f), builds the buffer with update id:1, adds four more with addUpdate, and asserts the iterator returns exactly five entries, id:1 first and once.
  • The counter disagrees with the buffer: numFieldUpdates counts one per call (BufferedUpdates.java:143, :155), and InfoStream prints 1 field updates; 20 new updates for one update matching 10 documents.
  • History: 7.6.0 kept one LinkedHashMap<Term, NumericDocValuesUpdate> / <Term, BinaryDocValuesUpdate> per field, keyed by the update term (a repeated term replaced its entry), so each call was stored at most once, and it passes the RAM probe. b0e6a92ede3 (LUCENE-8590, "Optimize DocValues update datastructures", 2018-12-04; backport eaf840867fa in 7.7.0) added FieldUpdatesBuffer and the computeIfAbsent plus unconditional addUpdate pattern in one diff; no CHANGES entry, code comment or review comment on lucene-solr PR #513 mentions storing the first update twice.
  • Reviewers already call the pattern a bug: in the review of the unmerged PR #16214 (in-place vector updates), iprithv wrote on 2026-06-08 (https://github.com/apache/lucene/pull/16214#discussion_r3374995773) about the PR's new addVectorUpdate: "The first update for a field gets added twice ... Harmless due to last-write-wins but wastes memory and looks like a bug". The author fixed that method; its code comment there reads "otherwise the first update would be buffered twice". The review comment also said addNumericUpdate/addBinaryUpdate "have an if/else to avoid this"; they do not: their if/else only picks addUpdate or addNoValue.
The devil's-advocate check119 words

The case for intended: both classes are package-private; setRAMBufferSizeMB says "the account of RAM usage for pending deletions is only approximate" (LiveIndexWriterConfig.java:174); the copy is idempotent, so no documented result changes; and FieldUpdatesBuffer.java:50-54 says terms are stored "without de-duplication".

Why it still holds: the "approximate" note goes on to explain delete-by-Query, whose RAM Lucene cannot measure (:175-177); here a measured value is appended twice, so the bytes really are held twice. The no-de-duplication comment is about separate calls that repeat a term, not one call stored twice. And the copy is really applied, twice the per-document work, which also roughly halves the LFV-838 threshold. This supports calling the impact minor, not calling the code intended.

Suggested fix

#

Recommended Do not add the update the constructor already recorded (validated)

Create the field's buffer with the first update and do not add that update again; add later updates as now (+12/-8 lines in BufferedUpdates, +6/-4 in each method). With it the repro and 14 doc-values-update and soft-delete suites pass (155 tests), assertions on and off, and so do the core format, ECJ and forbidden-apis checks.

FieldUpdatesBuffer buffer = fieldUpdates.get(update.field);
if (buffer == null) {
  // the constructor records this update as the buffer's first entry: do not add it again
  fieldUpdates.put(
      update.field, new FieldUpdatesBuffer(fieldUpdatesBytesUsed, update, docIDUpto));
} else if (update.hasValue) {
  buffer.addUpdate(update.term, update.getValue(), docIDUpto);
} else {
  buffer.addNoValue(update.term, docIDUpto);
}
numFieldUpdates.incrementAndGet();

Do not add the update the constructor already recorded (validated) (recommended)

#

In addNumericUpdate and addBinaryUpdate: look the buffer up; if it is missing, create it with the update (the constructor records it) and stop there; otherwise call addUpdate/addNoValue as now. This is the shape the #16214 author used for the vector method.

FieldUpdatesBuffer buffer = fieldUpdates.get(update.field);
if (buffer == null) {
  // the constructor records this update as the buffer's first entry: do not add it again
  fieldUpdates.put(
      update.field, new FieldUpdatesBuffer(fieldUpdatesBytesUsed, update, docIDUpto));
} else if (update.hasValue) {
  buffer.addUpdate(update.term, update.getValue(), docIDUpto);
} else {
  buffer.addNoValue(update.term, docIDUpto);
}
numFieldUpdates.incrementAndGet();

Trade-offs

  • Changes only what is stored (one entry less per field per packet), not the order in which updates are applied, so results are unchanged.
  • fieldUpdates is a plain HashMap (BufferedUpdates.java:66), so get + put behaves like computeIfAbsent; the extra lookup happens once per field per packet.
  • The constructor already handles both hasValue cases (FieldUpdatesBuffer.java:80-83, :98-103, :110-112).

Make the constructor not record an update (not run)

#

Start every buffer empty and always call addUpdate/addNoValue.

Trade-offs

More invasive: the constructor uses the first update to seed fields[0], docsUpTo[0] and numericValues[0], which the one-field and one-value compaction relies on, and TestFieldUpdatesBuffer builds buffers that way, so it would need changes too.

Downstream note

#

Servers that apply their clients' binary doc-values updates inherit the doubled buffering: results stay correct, but LFV-838's writer close comes at roughly half the update size.

How it was found

#

Semi-formal: while checking the size limit of the related overflow bug LFV-838, a case that should have stayed under 2 GiB (2,000 documents x 1 MiB) still overflowed, which needs more than 2,047 MiB of copies. That pointed to two copies per document; a probe showed the buffer holding the first update twice, and the code confirmed it.

The method in full106 words
  • Arithmetic: one 1 MiB binary update matching 2,000 documents should append 2,000 MiB, below the 2,147,483,631-byte array limit, yet it overflowed at destination index 2^31, which needs 2,047 earlier 1 MiB appends: about two appends per document.
  • Probe: an executed same-package probe of the buffered-updates classes on the stock main jar showed the field buffer iterating the first update twice while counting it once.
  • Code and repro: the root cause was then read in BufferedUpdates and FieldUpdatesBuffer and reduced to the public-API test.
  • Reviews: an independent reproduction, reviews by a model from another family (OpenAI GPT-5.6), an intended-behaviour review and a final review; see Independent checks.

LFV-837, snapshot of 2026-11-10

Registry title
IndexWriter buffers the first doc-values update of each field twice in every buffered-updates packet (BufferedUpdates adds again the update that FieldUpdatesBuffer's constructor already recorded), so that update is RAM-accounted twice and, except on the all-same-value numeric path, applied twice to every matching document (since 7.7.0, LUCENE-8590)
Area
index / buffered doc-values updates (BufferedUpdates, FieldUpdatesBuffer, FrozenBufferedUpdates)
Priority
Low, rank 1047: On default config the first doc-values update of each field is buffered twice in every packet, but final values stay correct and the cost is only extra RAM accounting and apply work.
Impact class
minor
Impact note
Any application that updates doc values (updateNumericDocValue, updateBinaryDocValue, updateDocValues, softUpdateDocument(s)) with a default configuration has the first update of each field in every buffered-updates packet (the global delete queue's and each per-thread writer's) stored and counted twice in ramBytesUsed() and, for binary updates or numeric updates with differing values, resolved and written again to every matching document; final doc values stay correct, so the cost is one extra copy of that update's term and value (a 1 MiB binary update counts 2,162,956 bytes instead of about 1,048,576, so RAM-triggered flushes come earlier), duplicate apply work, and, through the linked capacity defect of BinaryDocValuesFieldUpdates (LFV-838, which has its own fix site), a writer close at half the buffered binary-update size (1,100 documents x 1 MiB); no scale is needed for the duplicate itself.
Summary
You update a doc-values field through IndexWriter (for example updateBinaryDocValue with a 1 MiB value) and expect each update to be buffered once, as every later update of the same field is. Instead BufferedUpdates creates the field's FieldUpdatesBuffer with the update, whose constructor already records it as entry 0, and then adds the same update again, so the first 1 MiB update adds 2,162,956 bytes to ramBytesUsed() while each later one adds 1,048,576, and IndexWriter's InfoStream reports '1 field updates; 20 new updates' for one binary update matching 10 documents. Final values stay correct because the duplicate is identical and adjacent; Lucene 7.6.0 buffered the update once, and the double insert arrived with LUCENE-8590 in 7.7.0.
