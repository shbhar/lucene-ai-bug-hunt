IntObjectHashMap, LongObjectHashMap and CharObjectHashMap ramBytesUsed() count every entry as 256 bytes, whatever its value

Lucene's internal int-, long- and char-keyed object maps size the reused iterator cursor, not each value, in ramBytesUsed(), so every entry counts as 256 bytes: an 8 MiB long[] gives 416 bytes, a null adds 256. Since 9.11.0; in Lucene only a sandbox TermAutomatonQuery with an any-term transition is affected.

The finding in 30 seconds

#

The maps' ramBytesUsed() loops over values() to add each value's size, but hands the estimator the iterator's reusable cursor instead of the value inside it. The estimator does not know that type and guesses 256 bytes, so each entry costs 256 whatever it holds.

Background in three steps

#
  1. IntObjectHashMap, LongObjectHashMap and CharObjectHashMap (package org.apache.lucene.internal.hppc, a trimmed copy of the HPPC library) map primitive keys to objects. They implement Accountable: ramBytesUsed() returns "an estimate of the JVM heap memory used by this object".
  2. RamUsageEstimator.sizeOfObject(o) estimates one object: 0 for null; a formula for Accountables (their own ramBytesUsed()), Strings, primitive arrays and String[], boxed primitives, Query, Map and Collection; and a flat 256 bytes for any other type (an Object[] included).
  3. Iterating map.values() yields an ObjectCursor per entry. The iterator reuses one cursor and only changes its fields; the stored value is cursor.value.

The finding, step by step

#
  1. Make an empty IntObjectHashMap<Object>: ramBytesUsed() is 160 bytes (the object plus its key and value arrays).
  2. Call put(1, null). You expect 160 again: a null holds no heap, and its slot in the value array is already counted.
  3. You get 416. With put(1, new long[1 << 20]), an 8,388,624-byte array, it is also 416, and the same for a 48-byte String: every entry adds exactly 256 bytes, whatever it holds.
  4. Why: the loop meant to add each value's size passes the iterator's reused ObjectCursor to RamUsageEstimator.sizeOfObject instead of cursor.value. The estimator has no formula for a cursor and returns its 256-byte default.
  5. LongObjectHashMap and CharObjectHashMap have the same loop. No exception, assertions on or off. Lucene's own callers store records and BytesRefs that cost 256 either way; apart from a sandbox TermAutomatonQuery with an any-term transition (a null term, 256 bytes too many), only code with its own values sees a wrong number.

Who is affected

#

Mainly code that keeps its own values (primitive arrays, Strings, boxed primitives, Accountables or nulls) in these @lucene.internal maps and reads ramBytesUsed(): its estimate ignores the values. Lucene's own callers' values cost 256 bytes either way, so their numbers do not change, except a sandbox TermAutomatonQuery with an any-term transition: 256 bytes too many.

Mechanism, terms and numbers477 words

IntObjectHashMap, LongObjectHashMap and CharObjectHashMap (org.apache.lucene.internal.hppc) implement Accountable. Their ramBytesUsed() adds a private sizeOfValues() whose loop is meant to add each value's size: for (ObjectCursor<VType> value : values()) size += RamUsageEstimator.sizeOfObject(value);. But value is the iterator's single, reused ObjectCursor, not the stored value value.value. sizeOfObject has no formula for that type and returns its 256-byte default once per entry.

So every entry adds exactly 256 bytes, whatever it holds: an empty IntObjectHashMap reports 160 bytes, and one entry gives 416 whether the value is null, a 48-byte String, an 8,388,624-byte long[1 << 20] or an Accountable reporting 1,000,000. Large values are under-counted, small values and nulls over-counted, with assertions on and off, in every release from 9.11.0 through 10.6.0 and on main. Lucene's own callers store values that also cost 256 (the Lucene99 vectors readers' non-Accountable per-field records, the sandbox TermAutomatonQuery's BytesRef terms), so their numbers do not change, except that a TermAutomatonQuery with an any-term transition stores a null and reports 256 bytes too many. Otherwise only code that keeps its own values in these @lucene.internal maps and reads the estimate is hit. One-token fix per map: sizeOfObject(value.value).

The mechanism (main 5adff78bb168, internal/hppc/IntObjectHashMap.java)

#
  1. ramBytesUsed() returns BASE_RAM_BYTES_USED + RamUsageEstimator.sizeOf(keys) + sizeOfValues() (:440-441).
  2. sizeOfValues() (:444-450) starts from shallowSizeOf(values) and loops for (ObjectCursor<VType> value : values()) size += RamUsageEstimator.sizeOfObject(value); (:446-447). :447 is the fix site.
  3. values() returns a ValuesContainer whose ValuesIterator creates one ObjectCursor in its constructor (:585) and, for every assigned slot, sets cursor.index and cursor.value and returns the same object (:599, :606). ObjectCursor is a plain final class with index and value fields, not Accountable (ObjectCursor.java:25-33).
  4. RamUsageEstimator.sizeOfObject (util/RamUsageEstimator.java:393, body :407-444) returns 0 for null, uses formulas for known types (Accountable, String, primitive arrays, String[], boxed primitives, Query, Map, Collection; switch :412-442), and returns UNKNOWN_DEFAULT_RAM_BYTES_USED (256, :86) in its default branch (:435-437). The cursor takes the default branch.
  5. Result: ramBytesUsed() = BASE + sizeOf(keys) + shallowSizeOf(values) + 256 * size(), independent of the values. LongObjectHashMap.java:444-450 (fix site :447) and CharObjectHashMap.java:446-452 (fix site :449) have the identical loop.

Exposure and likelihood295 words
  • Who: code that stores its own values in one of the three maps and reads ramBytesUsed(), directly or through RamUsageEstimator.sizeOfObject(map) (the map is Accountable, so that call delegates to it, RamUsageEstimator.java:413), when the values are nulls or have a sizeOfObject formula (primitive arrays, String[], Strings, boxed primitives, Accountables and the like). One 8 MiB array counts as 256 bytes; a 48-byte String or a null also counts as 256. A memory budget or cache limit built on that number is wrong. Values with no formula (an Object[], any other plain class) get 256 with or without the fix.
  • Lucene itself: one small case. The in-tree callers are three direct ones, Lucene99FlatVectorsReader.java:197, Lucene99HnswVectorsReader.java:266 and backward-codecs Lucene99ScalarQuantizedVectorsReader.java:363, plus the sandbox TermAutomatonQuery, whose ramBytesUsed() adds sizeOfObject(idToTerm) for its IntObjectHashMap<BytesRef> (TermAutomatonQuery.java:91, :285-291). The readers' private FieldEntry records and the query's BytesRefs are not Accountable, so sizeOfObject charges them 256 with or without the fix. The exception: addAnyTransition stores a null term (TermAutomatonQuery.java:123-124, :241-251), which costs 256 today and 0 with the fix. Executed: the default codec's per-field Lucene99HnswVectorsReader reports 1408 bytes with and without the fix, a two-term TermAutomatonQuery 1801 with and without, and the query foo ANY bar 2153 on main and 10.6.0 but 1897 with the fix. That query number is what LRUQueryCache charges for the query when it caches it (LRUQueryCache.java:468-470, RamUsageEstimator.java:378-380).
  • Reach: the classes are @lucene.internal, and CHANGES for #13422 asks users not to use them, but module-info.java:55-57 still exports the package to all modules.
  • Effect: a wrong estimate only. No exception, no wrong search result, no index damage; assertions on and off alike.
  • Since: 9.11.0, the first release with these maps.

Why it looks unintended

#
  • The loop exists only to size values, calling the estimator once per entry; with the cursor it can only add 256 each, and nothing documents that.
  • Every other values() loop in Lucene reads cursor.value; the replaced code (#13763) used sizeOfMap, which sizes each value.
  • A null adds 256 bytes, though it holds no heap under any reading.
The full argument150 words
  • Contract. Accountable.ramBytesUsed(): "Returns an estimate of the JVM heap memory used by this object in bytes" (util/Accountable.java:35-36). sizeOfObject: "Known types will be estimated according to their formulas" (util/RamUsageEstimator.java:389-391). No javadoc, CHANGES entry, test or review comment on #13392 or #13420 mentions a flat per-entry charge.
  • Convention. IndexWriter.java:4536-4537 (updates.value), PerFieldKnnVectorsFormat.java:261-262 (knnVectorReader.value) and smartcn's BiSegGraph.java:223-224 (segList.value) all read the cursor's value. RamUsageEstimator.sizeOfMap sizes each value (:275); the vectors readers called sizeOfMap(fields, shallowSizeOfInstance(FieldEntry.class)) until #13763 (494b16063e1, 2024-10-31) switched them to fields.ramBytesUsed().
  • Lucene's own code. Upstream HPPC's ramBytesUsed() sizes only the used part of its key and value arrays and has no per-value loop, so the loop was added in #13392.
  • Incoherent. The result matches neither a deep reading (count each value) nor a shallow one (count nothing per value): under both, a null adds 0.
The devil's-advocate check178 words

"The maps are @lucene.internal, CHANGES for #13422 asks users not to use them, Accountable is silent on referenced objects (open #16113), and the numbers Lucene's vectors readers report do not change, so it is not a bug." An independent reviewer from another model family (OpenAI GPT-5.6) returned "not real" on exactly this ground, after reproducing the miscount in all three maps with its own test (long[1] and long[8192] give the same estimate in each map, 416 in the Int map), agreeing on the root cause, and calling the line a typo and the fix correct.

Why it fails: @lucene.internal limits API stability, not correctness. The package is exported, the method is public, and it returns a number its own loop was evidently written to compute differently. The argument is about impact, which is why the priority is Low. It has one fair point: whether ramBytesUsed() should count referenced objects at all is the open question of #16113, so fix A is the likely minimal repair, not the only correct one, and B is a defensible alternative.

Suggested fix

#

Recommended A. Size cursor.value in all three maps (validated)

Size the stored value, not the cursor: RamUsageEstimator.sizeOfObject(value.value) in all three maps, one token each. The repro passes with assertions on and off; the Int, Long and Char map suites (28 of 28 each), TestRamUsageEstimator, TestLucene99HnswVectorsFormat and the lint checks pass.

  private long sizeOfValues() {
    long size = RamUsageEstimator.shallowSizeOf(values);
    for (ObjectCursor<VType> value : values()) {
-      size += RamUsageEstimator.sizeOfObject(value);
+      size += RamUsageEstimator.sizeOfObject(value.value);
    }
    return size;
  }
All options and trade-offs2 options · 439 words

Two options. A was validated with gradle in a scratch worktree of 5adff78bb168; B is by reading. Either makes the repro pass, because a null adds 0 under both.

A. Size cursor.value in all three maps (validated) (recommended)

#

IntObjectHashMap.java:447, LongObjectHashMap.java:447 and CharObjectHashMap.java:449, one token each:

  private long sizeOfValues() {
    long size = RamUsageEstimator.shallowSizeOf(values);
    for (ObjectCursor<VType> value : values()) {
-      size += RamUsageEstimator.sizeOfObject(value);
+      size += RamUsageEstimator.sizeOfObject(value.value);
    }
    return size;
  }

Trade-offs

  • Does what the loop was written to do and matches sizeOfMap. Same number of iterations; per entry the loop now costs whatever sizing the value costs: nothing extra for constant-time values (Lucene's own records and BytesRefs among them), an Accountable value's own ramBytesUsed() (RamUsageEstimator.java:413), or a walk over a Map or Collection value (:433-434).
  • In-tree numbers: the vectors readers' do not change, as their FieldEntry records still get the 256-byte default (before #13763, sizeOfMap charged them their shallow instance size); a TermAutomatonQuery with an any-term transition goes down by 256 (its null term now costs 0).
  • An Accountable value is counted with its full ramBytesUsed(), so a value shared with another owner is counted here too: the general ownership question of open #16113, not new to this fix.
  • Renaming the loop variable to cursor would make the slip harder to repeat.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: on stock the repro fails with assertions on and off; with A it passes, on and off.
  • With A: TestIntObjectHashMap, TestLongObjectHashMap and TestCharObjectHashMap 28 of 28 each, TestRamUsageEstimator 12 (1 skipped), codecs.lucene99.TestLucene99HnswVectorsFormat 60 (3 skipped) and the repro: 157 tests, 0 failures. No existing test asserts the vectors readers' ramBytesUsed().
  • checkGoogleJavaFormat, ecjLintTest, forbiddenApisMain and forbiddenApisTest for lucene/core ran and passed; ecjLintMain was up to date in that run and ran and passed on the same fixed main sources in the first pass (which differs only in the test comment).
  • The probe with A: each value adds exactly its own size (null +0, "x" +48, long[1 << 20] +8,388,624, the Accountable +1,000,000) in all three maps.
  • Not run: the full lucene/core suite.

B. Make the estimate shallow (drop the loop)

#

Keep shallowSizeOf(values) and remove the per-value loop (no per-value term, as in upstream HPPC).

Trade-offs

The repro passes under B too. But in-tree numbers go down (the vectors readers would no longer count their per-field records at all, which sizeOfMap did before #13763), and callers with large values get an estimate that ignores them by design, which would need a javadoc note. By reading, not run.

Downstream note

#

Relevant downstream only to code that keeps its own values in these internal maps and budgets memory on their ramBytesUsed(); forked or vendored copies of these maps found by GitHub code search carry the same loop. Query terms and segment metadata do reach these maps, but the only effect is an estimate off by 256 bytes per entry.

How it was found

#

Semi-formal: a proof-obligation audit of IntObjectHashMap's ramBytesUsed() contract checked that the estimate includes each value's estimated size. The loop's argument is the iterator's cursor, not the value, and a one-test JUnit repro on stock main witnessed the flat 256 bytes per entry.

The method in full92 words
  • Obligation: for every map and value, ramBytesUsed() grows by the value's own estimate (sizeOfObject(value)) when an entry is added without a resize, which is what sizeOfValues() (IntObjectHashMap.java:444-450) sets out to compute.
  • Finding: the loop's argument is the ObjectCursor the iterator reuses (:585, :599, :606), so sizeOfObject takes its default branch (256) for every entry; LongObjectHashMap and CharObjectHashMap carry the same loop.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Mainly code that keeps its own values (primitive arrays, Strings, boxed numbers, Accountables or nulls) in the @lucene.internal IntObjectHashMap, LongObjectHashMap or CharObjectHashMap and reads the map's ramBytesUsed() (directly, or through RamUsageEstimator.sizeOfObject of the map) gets a wrong heap estimate: every entry counts a flat 256 bytes, so large values are under-counted (one 8 MiB long[] is reported as 416 bytes for the whole map) and null or small values over-counted; Lucene's own callers (the per-field maps of Lucene99FlatVectorsReader, Lucene99HnswVectorsReader and the backward-codecs Lucene99ScalarQuantizedVectorsReader) hold non-Accountable records that sizeOfObject charges 256 bytes with or without the fix, so their numbers do not change, except a sandbox TermAutomatonQuery with an any-term transition, whose null term is charged 256 bytes too many; no exception, wrong result or index damage; -ea and -da alike; every release from 9.11.0 through 10.6.0 and main.
Summary
You put a value into an IntObjectHashMap (or a LongObjectHashMap or CharObjectHashMap) and call ramBytesUsed(). You expect the estimate to include that value, which is what the method's own sizeOfValues() loop is for: it walks values() and calls RamUsageEstimator.sizeOfObject once per entry. Instead the loop passes the iterator's reused ObjectCursor rather than cursor.value, sizeOfObject does not know that type and returns its 256-byte default, so every entry adds exactly 256 bytes: a map holding an 8 MiB long[] reports 416 bytes, and putting a null value into an empty map raises the estimate from 160 to 416 bytes.
