SmartChineseAnalyzer.normalize skips the tokenizer's full-width folding, so full-width prefix, wildcard, fuzzy and range queries can miss

SmartChineseAnalyzer indexes full-width letters and digits as plain ASCII (Ｌｕｃｅｎｅ as lucen), but its normalize() only lower-cases, so prefix, wildcard, fuzzy, regexp and range queries with full-width letters or digits can miss: Ｌｕｃ* finds 0 documents, Luc* finds 1. Every release since 6.2.0 has it.

The bug in 30 seconds

#

Chinese text can contain full-width Latin letters and digits (Ｌｕｃｅｎｅ, ２０２６). SmartChineseAnalyzer indexes them as plain ASCII, but the query-time shortcut that the parsers use for partial words leaves that step out.

  1. Index 我们使用Ｌｕｃｅｎｅ ("we use Lucene", the Latin word in full-width letters, which Chinese text can contain) with the stock new SmartChineseAnalyzer(). Its tokenizer turns full-width letters and digits into ASCII and lower-cases them, so the index holds 我们, 使用 and lucen (Porter-stemmed).
  2. Search Ｌｕｃ* with QueryParser. A partial word cannot go through the full analyzer, so the parser calls Analyzer.normalize, documented to return "the representation that it would have in the index".
  3. You expect 1 hit, the same as Luc* and the plain term query Ｌｕｃｅｎｅ get.
  4. You get 0 hits, no error. SmartChineseAnalyzer.normalize only lower-cases, so the query becomes ｌｕｃ*, still full-width, and no indexed term starts with it. Called directly, normalize("ＡＢＣ") returns ａｂｃ and normalize("１２３") returns １２３, while the index holds abc and 123.
  5. The same miss shows for wildcard (Ｌｕ?ｅｎ), fuzzy (Ｌｕｃｅｎ~1), regexp and range ([Ｌｕａ TO Ｌｕｚ]) terms in the classic and flexible parsers and for the simple parser's prefix and fuzzy terms, whichever width the document used; fuzzy terms can still hit when the edit distance absorbs the width difference. Parsed term and phrase queries run the full analyzer and are unaffected.

Who is affected

#

Applications that index Chinese or mixed Chinese-English text with the stock SmartChineseAnalyzer and accept prefix, wildcard, fuzzy, regexp or range syntax through Lucene's query parsers. The query term must hold full-width letters or digits next to an ASCII operator, for example pasted full-width text plus an added *. The only symptom is silently fewer hits.

Mechanism, terms and numbers739 words

SmartChineseAnalyzer does its case and width handling inside the tokenizer: HMMChineseTokenizer's SegTokenFilter turns full-width Latin letters and digits into ASCII and lower-cases A-Z (SegTokenFilter.java:39-62), and createComponents has no LowerCaseFilter (SmartChineseAnalyzer.java:124-134). So 我们使用Ｌｕｃｅｎｅ is indexed as 我们, 使用, lucen. SmartChineseAnalyzer.normalize(), which the classic and flexible query parsers use for prefix terms, wildcard chunks, fuzzy terms, regexps and range bounds (the simple parser for its prefix and fuzzy terms), returns only new LowerCaseFilter(in) (:137-140), although Analyzer#normalize is documented to give "the representation that it would have in the index", without tokenizing or stemming (Analyzer.java:203-208). The result: Ｌｕｃ*, Ｌｕｃｅｎ~1 and [Ｌｕａ TO Ｌｕｚ] find nothing while Luc* and the term query Ｌｕｃｅｎｅ find the document, and normalize("ＡＢＣ") returns ａｂｃ while the index holds abc. A secondary, narrower direction: normalize lower-cases non-ASCII capitals such as É that the index keeps. Parsed term and phrase queries and the indexed data are unaffected. Every release from 6.2.0 to 10.5.2 and main has it. The fix makes normalize() apply the tokenizer's folding; it changes only the query side, so no reindex is needed.

Terms

#
  • Full-width forms: the letters Ａ-Ｚ, ａ-ｚ (U+FF21-U+FF3A, U+FF41-U+FF5A) and digits ０-９ (U+FF10-U+FF19), each as wide as a Chinese character. Chinese input methods produce them in full-width mode, giving mixed text such as 我们使用Ｌｕｃｅｎｅ or ２０２６年.
  • SegTokenFilter: part of HMMChineseTokenizer, so it runs inside the tokenizer, not as a token filter. For full-width tokens it subtracts 0xFEE0 from each character (full-width to ASCII) and then lower-cases A-Z; for ASCII tokens it lower-cases A-Z (SegTokenFilter.java:39-62; javadoc "Full-width latin will be converted to half-width, then all latin will be lowercased"). createComponents adds no LowerCaseFilter: "LowerCaseFilter is not needed, as SegTokenFilter lowercases Basic Latin text" (SmartChineseAnalyzer.java:128).
  • Analyzer.normalize(field, text): what the query parsers call for a partial word, because the full analyzer would tokenize or stem it. It runs the analyzer's normalize(String, TokenStream) override, which should hold the normalizing steps and leave out the tokenizer and the stemmer (Analyzer.java:53-58, :203-212).
  • Multi-term queries: prefix (Ｌｕｃ*), wildcard (Ｌｕ?ｅｎ), fuzzy (Ｌｕｃｅｎ~1), regexp (/ｌｕｃ.*/) and range ([Ｌｕａ TO Ｌｕｚ]). Parsed term and phrase queries run the full analyzer and are not affected.

The bug

#
  1. SmartChineseAnalyzer.normalize() is return new LowerCaseFilter(in); (SmartChineseAnalyzer.java:137-140). Because the folding lives in the tokenizer, which normalize skips, it is lost.
  2. The classic parser passes the prefix through it (QueryParserBase.java:712, BytesRef term = getAnalyzer().normalize(field, termStr);), and likewise the fuzzy term (:729), the regexp (:683), each wildcard chunk (:646, :656) and the range bounds (:550, :556; an open * bound is skipped, :547-557). The flexible parser's processors do the same (range bounds only when they do not parse as dates, TermRangeQueryNodeProcessor.java:100-139). The simple parser has only prefix and fuzzy syntax and normalizes both (SimpleQueryParser.java:573, :605).
  3. Ｌｕｃ* therefore becomes body:ｌｕｃ*. The index holds lucen, so the prefix cannot match any term. LowerCaseFilter also applies Character.toLowerCase to every code point, while the index lower-cases only A-Z, so normalize("É") is é but the index keeps É. This secondary direction matters for single-letter terms, because the tokenizer emits such letters one per token, and for range bounds: [Аz TO Яz] (Cyrillic capitals) built from normalize admits б instead of the indexed Б.
  4. The sibling analyzers fold width in normalization: CJKAnalyzer.normalize is CJKWidthFilter + LowerCaseFilter (CJKAnalyzer.java:101-106), and JapaneseAnalyzer applies CJKWidthCharFilter in initReaderForNormalization (JapaneseAnalyzer.java:130-133).

The numbers

#

One document 我们使用Ｌｕｃｅｎｅ, default SmartChineseAnalyzer, classic QueryParser: Ｌｕｃ* and Ｌｕｃｅｎ~1 find 0 documents; Luc*, Lucen~1 and the term query Ｌｕｃｅｎｅ find 1. normalize("ＡＢＣ") = ａｂｃ (index abc), normalize("１２３") = １２３ (index 123). The hunt's scan found 76 of 285 single-token words that disagree; every one of the 73 that the parser scan checked (the other 3 were not in its word set) was missed by classic and flexible prefix, wildcard, regexp and range queries and by simple-parser prefix queries, while fuzzy still hit 61 within the edit distance. An exhaustive scan of every BMP character indexed as one token found 1,141 of 61,527 disagreeing (the 62 full-width letters and digits and 1,079 non-ASCII capitals) and all 2,704 two-letter full-width words.

Exposure and likelihood410 words
  • Who is exposed. Applications that use the stock SmartChineseAnalyzer, the default constructor included, and pass user text through QueryParser, StandardQueryParser or SimpleQueryParser (prefix and fuzzy only), or call Analyzer.normalize themselves. Analyzer wrappers delegate normalize to the wrapped analyzer (AnalyzerWrapper.java:123-127), so wrapped uses inherit it unless the wrapper adds its own normalization step (as the workaround below does). The class targets "Chinese or mixed Chinese-English text" (SmartChineseAnalyzer.java:33).
  • Default, not opt-in. Default analyzer and default parser settings. The only choices involved are the smartcn analyzer (an optional module, marked @lucene.experimental) and multi-term syntax.
  • What it takes. Full-width letters or digits in the query term next to an ASCII *, ?, ~, / or range syntax: mixed-width input, or an application that appends * or builds a range around user text. By the classic grammar, a full-width ＊ is an ordinary character, so Ｌｕｃ＊ typed entirely in full-width mode becomes the plain term query body:luc, not a prefix query, and does not match lucen (QueryParser.jj:183-187, :208-211; executed). Documents written in full width are still found by half-width queries that fit the stemmed term: Luc* finds both widths, Lucene* neither, because the index holds lucen. The registry rates the likelihood rare; no report was found in the searched public sources.
  • What the damage looks like. Prefix terms, and wildcard or regexp literals, that require a full-width letter or digit cannot match any indexed term: 0 hits, no error, whichever width the document used. Range bounds compare in the wrong form and can drop or add terms ([a TO ｚ] admitted 7 of 8 probe documents; the indexed-form [a TO z] admits 3). Fuzzy terms can still hit within the edit distance, so say "miss", not "never match".
  • Scale. One document and one query are enough. All 62 full-width letters and digits and all 2,704 two-letter full-width words normalize differently from how they are indexed.
  • Downstream (code reading only, nothing run). Elasticsearch's analysis-smartcn plugin registers the stock analyzer, and its query_string parser normalizes range, fuzzy, prefix and wildcard terms with the field's analyzer, so it would inherit the miss; another downstream server's smartcn plugin also registers the stock class.
  • Limit. After the fix, prefixes that run past the Porter stem stay best effort, as with every stemming analyzer (Ｌｕ?ｅｎｅ misses even with the fix, because Lucene is indexed as lucen). This bug is only the width and case mismatch.

Why it is a bug, not intended

#
  • Analyzer#normalize must return "the representation that it would have in the index", minus only tokenizing and stemming. Width and case folding are neither.
  • The index-side folding is documented and tested: testFullWidth asserts Ｔｅｓｔｓ becomes test and １２３４ becomes 1234.
  • The same 2016 commit gave CJKAnalyzer.normalize width folding; SmartChineseAnalyzer is the outlier.
The full argument243 words
  • The contract. Analyzer.java:203-208: "Normalize a string down to the representation that it would have in the index. This is typically used by query parsers in order to generate a query on a given term, without tokenizing or stemming". The class example (:53-58) keeps a filter that is "about normalization" and drops one that is "about stemming".
  • The analyzer documents its folding as index behaviour. SegTokenFilter's javadoc ("Full-width latin will be converted to half-width") and the SmartChineseAnalyzer.java:128 comment; TestSmartChineseAnalyzer.testFullWidth ("Full width alphas and numerics are folded to half-width", :160-170) asserts it.
  • Design intent. On LUCENE-7355 (#8409), jpountz, who added normalize, described it as applying "all normalization filters (lowercasing, ascii folding, etc.) but not transformations (stop word removal, stemming, etc.)".
  • Siblings. The same commit gave CJKAnalyzer.normalize CJKWidthFilter + LowerCaseFilter and JapaneseAnalyzer width folding (today through initReaderForNormalization). SmartChineseAnalyzer, whose folding is hidden in the tokenizer, got only LowerCaseFilter.
  • Tests. No smartcn test calls normalize; BaseTokenStreamTestCase only checks that it does not throw (:1478). Nothing pins the current output.
  • Precedents fixed as bugs. LUCENE-8186 (#9234, fixed in 7.4 and 8.0): CustomAnalyzer with a lower-casing tokenizer did not normalize multi-term queries, fixed so that normalize applies the tokenizer's normalization; LUCENE-7606 (#8657, fixed in 6.4 and 7.0): CustomAnalyzer.normalize applied only the last token filter. Separately, in LUCENE-8022 (#9070, closed as Invalid) a maintainer told a user that their analyzer must override normalize() to mirror its index-time lower-casing.
The devil's-advocate check313 words

The strongest "intended" case (the cross-model reviews rated it moderate; the independent reproducer rated it weak and the devil's-advocate verifier rejected it): SmartChineseAnalyzer is @lucene.experimental; normalize deliberately skips tokenization, and here the folding lives in the tokenizer; the classic parser's javadoc says "normal Analyzers are unlikely to work properly with wildcard templates" (QueryParserBase.java:611, :696; :667 says the same of "regular expression templates"), and a comment in its wildcard code calls keeping wildcard and escaped characters away from normalize a "best effort" (:638); and LowerCaseFilter keeps roughly what the parsers did before 6.2 (lowercaseExpandedTerms).

Why it fails: "experimental" marks API stability, not licence for query and index to disagree; the javadoc excludes tokenizing and stemming, not character folding, and LUCENE-8186 made normalize mirror a tokenizer's normalization; the wildcard javadoc predates LUCENE-7355 and is about splitting templates, while the prefix code a few lines below calls normalize (:712); back-compat with the old lower-casing makes the behaviour long-standing, not intended, since LUCENE-7355 aimed beyond lower-casing and added width folding wherever the index chain visibly folds width. No test, discussion or decision supporting the current output was found. Verdict: a defect. What the counter-case gets right: a fix changes long-standing query behaviour; the recommended fix copies the tokenizer's private folding rules into a second place; full-width text next to ASCII operators is unusual input; and the old parser lower-casing (String.toLowerCase(locale)) is close to, not identical with, LowerCaseFilter (per-code-point Character.toLowerCase; they differ for locale-sensitive and contextual mappings such as the Turkish dotless i and the Greek final sigma). These argue for a careful, tested change, not for keeping the mismatch. For the secondary É direction one could argue the index side deviates (SegTokenFilter's javadoc says "all latin will be lowercased" while the code lower-cases only A-Z), so present that direction as a question.

Suggested fix

#

Recommended normalize() applies the tokenizer's folding (validated)

Make normalize() apply the tokenizer's folding: full-width letters and digits to ASCII, then lower-case A-Z only (a small private filter replacing LowerCaseFilter). It changes only the query side, so no reindex is needed. With it the repro and all 23 smartcn tests pass, and normalize agrees with indexing on all 61,527 single-character BMP tokens tested.

All options and trade-offs4 options · 928 words

Two fixes were built and checked in a scratch worktree of main ea57360912ed; A mirrors the index exactly and is recommended. The other options are a larger refactoring and a workaround.

normalize() applies the tokenizer's folding (validated) (validated by the checks) (recommended)

#

Replace new LowerCaseFilter(in) with a private filter that does what SegTokenFilter does at index time, restricted to the three ranges that Utility.getCharType puts in the full-width classes (U+FF10-U+FF19, U+FF21-U+FF3A, U+FF41-U+FF5A). The LowerCaseFilter import goes; TokenFilter and CharTermAttribute are imported (+36/-2, formatted by tidy). Same logic as the finder's fix sketch. A regression test: the repro's class, or its assertions added to TestSmartChineseAnalyzer next to testFullWidth.

@Override
protected TokenStream normalize(String fieldName, TokenStream in) {
  return new SegTokenNormalizationFilter(in);
}

/**
 * Applies the case and width folding that SegTokenFilter applies at index time: full-width Latin
 * letters and digits become half-width, then only Basic Latin A-Z is lower-cased.
 */
private static final class SegTokenNormalizationFilter extends TokenFilter {
  private final CharTermAttribute termAtt = addAttribute(CharTermAttribute.class);

  SegTokenNormalizationFilter(TokenStream in) {
    super(in);
  }

  @Override
  public boolean incrementToken() throws IOException {
    if (input.incrementToken() == false) {
      return false;
    }
    final char[] buffer = termAtt.buffer();
    for (int i = 0; i < termAtt.length(); i++) {
      char c = buffer[i];
      if ((c >= 0xFF10 && c <= 0xFF19)
          || (c >= 0xFF21 && c <= 0xFF3A)
          || (c >= 0xFF41 && c <= 0xFF5A)) {
        c -= 0xFEE0;
      }
      if (c >= 'A' && c <= 'Z') {
        c += 0x20;
      }
      buffer[i] = c;
    }
    return true;
  }
}

Trade-offs

  • Query side only: the index already holds the folded form, so no reindex.
  • Behaviour change: the tested full-width multi-term queries now hit (the intent); a full-width ＊ or ． stays a literal character (Ｌｕ＊? becomes lu＊?, 0 hits; executed). Non-ASCII capitals are no longer lower-cased in normalize, so É* matches the indexed É instead of é; consistent with the index, but worth raising as a question with maintainers.
  • Cost: one character loop per normalized query term.
  • Maintenance: the filter copies the tokenizer's private folding rules (Utility.getCharType, SegTokenFilter), so the two can drift apart again unless a test pins them together.
  • The override has not changed since 2016, so the same patch should apply to maintained branches; only main was built and tested.
  • Prefixes that run past the Porter stem stay best effort, as with every stemming analyzer.

Reuse CJKWidthFilter, as CJKAnalyzer does (validated, not recommended)

#

TokenStream result = new CJKWidthFilter(in); result = new LowerCaseFilter(result); return result; (+4/-1). The repro passes and :lucene:analysis:smartcn:check passes (23 tests).

TokenStream result = new CJKWidthFilter(in);
result = new LowerCaseFilter(result);
return result;

Trade-offs

Smaller and reuses an existing filter, but it does not mirror the index: with it, the exhaustive scan still finds 1,138 of 61,527 single-character tokens disagreeing. That is the 1,079 non-ASCII capitals as before, plus 59 new ones in U+FF65-U+FF9F, which the index keeps half-width: CJKWidthFilter maps the half-width katakana and middle dot to their full-width forms, and the two half-width sound marks U+FF9E and U+FF9F to the combining marks U+3099 and U+309A, or merges them into a preceding katakana (CJKWidthFilter.java:67-76). It also folds full-width punctuation (U+FF01-U+FF5E), so a full-width ＊ or ． inside a wildcard or regexp term becomes an ASCII operator: Ｌｕ＊? becomes lu*? and /Ｌｕｃ．＊/ becomes /luc.*/, and both match lucen (executed). The independent reproducer's É test still fails.

Move the folding out of the tokenizer into separate filters (not run)

#

The direction of an unmerged 2009 patch on LUCENE-2023 (#3098), written for speed: split SegTokenFilter's lower-casing and full-width conversion into filters, which normalize could then reuse.

Trade-offs

By inference (not run): it could change indexed terms for some inputs and would then need a back-compat story (reindex), so it is a larger change than the query-side fix.

Workaround for users until a fix ships (validated)

#

SmartChineseAnalyzer is final, so wrap it: an AnalyzerWrapper whose getWrappedAnalyzer returns the stock analyzer and whose wrapTokenStreamForNormalization returns new CJKWidthFilter(in) (it runs after the stock LowerCaseFilter). Indexing is unchanged. On the stock main jars, with assertions on and off, Ｌｕｃ*, Ｌｕｃｅｎ~1 and [Ｌｕａ TO Ｌｕｚ] then find the document. Or type multi-term queries in half-width (Luc*).

Trade-offs

No reindex. It carries the CJKWidthFilter caveats of the previous option (half-width katakana; full-width ＊ and ． become operators) and leaves the É direction as it is, because the stock LowerCaseFilter runs first (É* becomes é*, 0 hits; executed).

Downstream note

#

A restriction written as a parsed multi-term query goes through the same normalize(), so a full-width pattern never equals an indexed term, and a MUST_NOT rule such as -Ｌｕｃ* removes nothing. Lucene's SECURITY.md (lines 28, 50) leaves authorization to the application and promises no untrusted-input guarantee here, so it is out of scope; no exploit is known.

How it was found

#

A bounded-exhaustive metamorphic scan of the stock analyzers: normalize(w) must equal the single token indexing stores for w. SmartChineseAnalyzer disagreed on 76 of 285 single-token words (full-width letters and digits, and capitals such as É). A second scan showed the misses through the query parsers, and code reading found the cause.

The method in full227 words

Method: a bounded-exhaustive metamorphic scan on the stock main jars (the study's "semi-formal" tier). A hunt unit, "analyzer normalize consistency", 2026-10-26.

  • Relation N1: Analyzer.normalize(f, w) equals the single full-span token that indexing produces for w, checked over bounded word sets for 99 analyzer configurations (every public stock Analyzer with a no-arg constructor in the module jars, 5 hand-built ones, and stemmer-free variants of 38 language analyzers). SmartChineseAnalyzer disagreed on 76 of 285 single-token words: full-width Latin letters and digits, and non-ASCII capitals such as É, Ø, İ, ẞ.
  • Relation N2 (parser reachability): each disagreeing word, used as a prefix, wildcard, fuzzy, regexp and range query through the classic, flexible and simple parsers, must still find its document. All 73 checked disagreeing words were missed by classic and flexible prefix, wildcard, regexp and range queries and by simple-parser prefix queries; fuzzy still hit 61. Every agreeing word was found. The flexible parser's multi-field mode, which has a separate bug of its own, differs: there prefix and wildcard hit 19 of the 73 and missed 79 agreeing words.
  • Code reading then located the cause: the folding lives in the tokenizer's SegTokenFilter, which normalize skips.
  • An AI finder wrote the public-API JUnit; independent AI tools then reproduced and judged it, and an exhaustive scan over every BMP character confirmed the scope (see the checks).

LFV-565, snapshot of 2026-10-29

Registry title
SmartChineseAnalyzer.normalize only lower-cases, but indexing folds full-width Latin letters and digits to half-width (in the tokenizer's SegTokenFilter), so full-width prefix, wildcard, regexp, range and fuzzy terms from the query parsers miss documents that the same word as a term query finds
Area
analysis-smartcn / language analyzers (SmartChineseAnalyzer normalization: Analyzer#normalize vs the width and case folding inside HMMChineseTokenizer's SegTokenFilter, used by the query parsers for multi-term queries)
Priority
Medium, rank 129: The stock SmartChineseAnalyzer silently misses full-width multi-term query terms, the same normalize() gap as LFV-557 and LFV-534 but with an audit-downgraded rare trigger, so it closes that group.
Impact class
silent wrong results
Impact note
Every application that indexes Chinese or mixed Chinese-English text with the stock SmartChineseAnalyzer and accepts prefix, wildcard, regexp, range or fuzzy syntax through Lucene's classic, flexible or simple query parser (or calls Analyzer.normalize itself) silently gets no hits whenever the query term contains full-width Latin letters or digits (for example 'Ｌｕｃ*', 'Ｌｕ?ｅ*', '[ｌｕａ TO ｌｕｚ]' or '２０２*'), because the index holds only the half-width, lower-cased form and normalize keeps the full-width one; fuzzy queries can still hit when the edit distance absorbs the difference, single-letter multi-term terms with a non-ASCII capital (É*, Б*) disagree in the other direction, term and phrase queries and the indexed data are unaffected, no setting or scale is needed, every release from 6.2.0 to 10.5.2 and main has it (the default classic parser shows the same miss even before, through its own pre-7.0 lower-casing), and by code reading two downstream search servers' smartcn plugins register the stock class unchanged.
Summary
You index the text '我们使用Ｌｕｃｅｎｅ' (or '我们使用Lucene') with the stock SmartChineseAnalyzer and search with the classic QueryParser: the term query 'Ｌｕｃｅｎｅ' and the half-width prefix 'Luc*' find the document, so you expect the full-width prefix 'Ｌｕｃ*' to find it too. Instead it finds 0 documents, with no error: the tokenizer's SegTokenFilter folds full-width Latin letters and digits to half-width and lower-cases A-Z, so the index holds 'lucen', but SmartChineseAnalyzer.normalize, which the query parsers apply to prefix, wildcard, regexp, range and fuzzy terms, is only a LowerCaseFilter, so the query term stays full-width ('ｌｕｃ*'). Likewise Analyzer.normalize returns 'ａｂｃ' for 'ＡＢＣ' and '１２３' for '１２３' (the index holds 'abc' and '123') and 'é' for 'É' (the index keeps 'É').
