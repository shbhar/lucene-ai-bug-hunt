SimpleBindings builds a shared expression binding again for every path that reaches it, so building a source grows exponentially with the depth of sharing

When named expressions bound with SimpleBindings.add(String, Expression) share a sub-expression, getDoubleValuesSource builds it again for every path that reaches it: 196,605 sources for 49 bindings that need 48. Results stay correct; build time and heap roughly double with each layer of sharing.

The finding in 30 seconds

#

Background: expressions and bindings

#
  1. A Lucene expression is a small formula such as X0 + 1, compiled with JavascriptCompiler and computed per document, for example to sort or score hits.
  2. SimpleBindings says what each variable name means: a field, the score, a constant (bound with add(String, DoubleValuesSource)), or another expression (bound with add(String, Expression)).
  3. getDoubleValuesSource(name) turns a name into a DoubleValuesSource: for an expression, an ExpressionValueSource that holds one source per variable.

The finding, step by step

#
  1. You name expressions and use them in other expressions with SimpleBindings.add(String, Expression), the documented way. Two of them share a third: L0 = X0 + 1, R0 = X0 * 2, X1 = L0 + R0. You repeat that diamond 16 times: 49 bindings, 48 of them expressions.
  2. You call bindings.getDoubleValuesSource("X16") and expect each expression to be built about once: 48 sources, which is what the same graph costs when you bind prebuilt sources instead.
  3. Instead Lucene builds 196,605 = 3 x (2^16 - 1). With just 2 diamonds it builds 9 for 6 expressions: X1, and L0 and R0 under it, are built once for L1 and again for R1.
  4. Each extra diamond roughly doubles the count: at 61 bindings the build takes 186 ms instead of 0.2 ms, and at 70 it runs out of a 1 GB heap. Values are right in every tested graph; evaluating such a graph is exponential too (#9620, a separate known issue).

Who is affected

#

Applications on the optional expressions module that use named expressions inside other expressions (add(String, Expression)) in several layers that share sub-expressions. Shallow sharing costs nothing noticeable (16 diamonds build in 8-23 ms); 20 layers cost 130-190 ms per build and 23 exhaust a 1 GB heap. Results, index files and everything else are unaffected.

Mechanism, terms and numbers541 words

SimpleBindings.add(String, Expression) is the documented way to "reference expressions from other expressions" (SimpleBindings.java:62). It stores expression::getDoubleValuesSource (:65), a recipe rather than a built source, and getDoubleValuesSource(name) applies it on every lookup with no memo (:73). The ExpressionValueSource constructor resolves every variable through the bindings (ExpressionValueSource.java:45) and keeps what it gets. So when two expressions use the same named expression, that expression and everything below it is built twice, and with layered sharing the built objects form a tree with one ExpressionValueSource per path: 3 x (2^d - 1) for a chain of d diamonds, 196,605 for 49 bindings, where binding the same graph eagerly with add(String, DoubleValuesSource) builds 48. Values are correct in every tested graph. At 61 bindings the build takes 186 ms instead of 0.2 ms; at 70 it exhausts a 1 GB heap before any document is read. On main, evaluating the same graph is also exponential (the per-hit cost of #9620, whose cache class is unused; #16880) and fails one layer earlier, so this fix alone makes no deeper graph usable. Every release since 4.6.0 (2013) is affected; the fix is to resolve each name once per top-level lookup.

Mechanism (Lucene main 5adff78bb168)

#
  • add(String, Expression) stores map.put(name, expression::getDoubleValuesSource) (SimpleBindings.java:64-66): a function that, for a compiled expression, builds a new source each time. add(String, DoubleValuesSource) stores _ -> source, the same object on every lookup (:55-57).
  • getDoubleValuesSource(name) checks the name and returns map.get(name).apply(this) (:68-74). Nothing remembers what an earlier lookup built.
  • Expression.getDoubleValuesSource(Bindings) returns new ExpressionValueSource(bindings, this) (Expression.java:102-104). Compiled expressions do not override it (JavascriptCompiler generates only a constructor and evaluate, js/JavascriptCompiler.java:363-396); a custom Expression subclass could, so the counts here are for compiled expressions.
  • The ExpressionValueSource constructor resolves every variable, bindings.getDoubleValuesSource(expression.variables[i]) (ExpressionValueSource.java:45), and stores the result in variables (:51). Every built object is kept by its parent, so the cost is heap as well as time.
  • The name-keyed valuesCache in getValues (:66) is local to one getValues call, and a compiled expression lists each variable name once (js/JavascriptCompiler.java:293, :497); it does not reach construction.

Step by step, 2 diamonds

#

Bindings: X0 = constant 3; L0 = X0 + 1, R0 = X0 * 2, X1 = L0 + R0; L1 = X1 + 1, R1 = X1 * 2, X2 = L1 + R1.

  1. getDoubleValuesSource("X2") builds X2, whose constructor looks up L1 and R1.
  2. Building L1 looks up X1: a new X1 is built, which builds a new L0 and a new R0.
  3. Building R1 looks up X1 again: another X1, with another L0 and R0.
  4. Total: 9 ExpressionValueSource objects for 6 expressions. One more diamond on top doubles everything below it: 21 at 3 diamonds, 3 x (2^d - 1) at d, 196,605 at 16.

On a Fibonacci graph built with the recurrence of upstream's testFibonacciExpr (f(i) = f(i-1) + f(i-2); upstream's test goes to f40 and binds eagerly) bound with add(String, Expression), the count is fib(n+1) - 1 for top name fn: 121,392 for f25 (24 expression bindings), growing x1.618 per added name.

Why it looks unintended

#
  • Documented use: add(String, Expression) "can be used to reference expressions from other expressions"; upstream's testValidExternals shares a sub-expression this way.
  • The same graph bound with prebuilt sources builds one source per name; only the lazy path multiplies.
  • Upstream treated the same blow-up at evaluation time as a bug (#9620); a 2020 suggestion to cache repeated names was deferred, not rejected.
The full argument276 words
  • Documented use. The class javadoc's example binds "recency" to myRecencyExpression, commented // another expression (SimpleBindings.java:38-39); add(String, Expression): "This can be used to reference expressions from other expressions." (:62). No precondition limits sharing.
  • Upstream's own test shares a sub-expression this way: TestExpressionValidation.testValidExternals binds valid_e1 = valid_e0 + valid0 and valid_e2 = valid_e0 * valid_e1 with add(String, Expression) (:34-38).
  • One build per name is possible through the same API: bound eagerly with add(String, DoubleValuesSource), as testFibonacciExpr does (TestExpressionValueSource.java:135-156), each expression is built once, when it is bound (24 sources for a 24-expression Fibonacci graph built with the same recurrence, up to f25; upstream's test goes to f40; the lazy path builds 121,392 on it).
  • Cost was the goal of the change that created the pattern. LUCENE-5231 (#6295) moved lookups into the constructor because "Each binding is looked up per-segment, which is bad. we should minimize the lookups to only in the CTOR", keeping "compute subs only once" for values. Shared sub-expressions were not discussed.
  • The same blow-up at evaluation time was treated as a problem: #9620 (LUCENE-8574) describes the same diamond ("The problem is combinatoric") and was resolved as fixed for 8.7 (its cache class is not wired into SimpleBindings, so getValues is still exponential on main).
  • Caching was deferred, not rejected: in the LUCENE-9338 review (apache/lucene-solr#1444, 2020) msokolov wrote "It's also nice to know if the same name occurs multiple times in the dependency tree; maybe one should cache its value in that case", and romseygeek answered "Cacheing is a whole other conversation ... that's for a follow-up really". The searches found no follow-up.
The devil's-advocate check157 words

The strongest case for "intended": no complexity bound is documented; Bindings, SimpleBindings and Expression are @lucene.experimental; SimpleBindings can be read as macro expansion; the eager workaround exists; caching was deferred in 2020; in the same review romseygeek called source building "part of query setup, not query execution" (about containsKey versus get); and a memo changes object identity and adds state.

Why it fails: nothing says by design or won't fix; the deferral was a deferral; upstream accepted the per-hit analogue on the same shape as a bug (#9620, resolved for 8.7); the trigger is the documented use with no precondition violated; and the recommended fix keeps no state beyond one lookup and changes no identity across calls (it does change which Bindings object a custom Expression override receives; see the fixes). It does lower the priority, and the fix can also be read as an improvement. Verdict: a cost defect, not a design decision.

Suggested fix

#

Recommended A. Resolve each name once per top-level lookup (private Bindings wrapper)

Resolve each name once per top-level lookup: getDoubleValuesSource(name) delegates to a private Bindings that remembers what it built during that call, so a shared expression is built once and shared. Validated: the repro passes (48 builds), all 171 expressions-module tests pass, and the module's format, lint and forbidden-API checks pass.

All options and trade-offs3 options · 777 words

Both fixes were validated on 2026-11-05 with gradle in a clean scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF; the module's tests pass with each, and the study checked B's validate() answers on 730,272 enumerated graphs and its values on the 627,313 valid ones. They fix construction only: evaluation (getValues, #9620) and hashCode/equals/isCacheable/rewrite still walk the graph once per path. Making deep graphs usable end to end also needs the per-hit cache of #9620 wired in, a separate change (#16880).

Workaround today: build the sources yourself in dependency order and bind them with add(String, DoubleValuesSource), as testFibonacciExpr does.

A. Resolve each name once per top-level lookup (private Bindings wrapper) (validated by the checks) (recommended)

getDoubleValuesSource(name) creates a ResolvingBindings that builds each name at most once and returns the same object for later references within that call (SimpleBindings.java, +22/-3).

Trade-offs

No state on SimpleBindings and nothing to clear on add(); each top-level call still returns a fresh object, so identity across calls is unchanged. The memo lasts for one SimpleBindings.getDoubleValuesSource call; within it a shared name is one shared object, as with eager binding. An unbound top-level expression (expr.getDoubleValuesSource(bindings) or expr.getSortField(bindings, true), the javadoc usage, SimpleBindings.java:42) resolves each of its variables in a separate call (ExpressionValueSource.java:44-45), so a name shared between them is built once per such variable: compile("L15 + R15").getDoubleValuesSource(bindings) on the 16-diamond chain builds 196,604 stock, 92 with A and 47 with B. That is linear, not exponential, but not eager parity; binding the top-level expression under a name and looking that name up gives one scope. Expression bindings receive the private wrapper instead of the SimpleBindings itself (as validate() already passes its own CycleDetectionBindings), so a custom Expression.getDoubleValuesSource(Bindings) override sees a different Bindings object and gets the same source for a repeated lookup within one call; the module's tests do not cover such overrides. A cycle still ends in StackOverflowError, as today, because a name is recorded only after it is built. computeIfAbsent cannot replace the get/put pair: the recursion modifies the map.

  • The repro fails stock and passes with A, assertions on and off; a count probe shows 48 builds.

  • An independent fact check ran a top-level probe (compile("L15 + R15") on the 16-diamond chain): 196,604 builds stock, 92 with A, 47 with B, and confirmed one shared X1 within a call, fresh objects across calls and a cycle still ending in StackOverflowError.

B. A memo on SimpleBindings, cleared on every add() (validated by the checks)

#

Keep a ConcurrentHashMap<String, DoubleValuesSource> of built sources on SimpleBindings; getDoubleValuesSource returns a cached source when present, and both add methods clear the map (SimpleBindings.java, +14/-1).

Trade-offs

Repeated calls return the same object, an identity change; adds shared mutable state to a class that is otherwise only read after setup, and every add() must clear it. The ConcurrentHashMap does not make SimpleBindings thread-safe (map stays a HashMap, SimpleBindings.java:49).

What the checks validated

  • The whole :lucene:expressions:test with B, repro included: 171 tests, 0 failures, assertions on.
  • The study checked that validate() answers are unchanged with B on all 730,272 enumerated graphs, and values on the 627,313 valid ones.

Not recommended: document the cost and the eager workaround only

#

Say in the javadoc of add(String, Expression) that every reference builds the expression again, and point to add(String, DoubleValuesSource) for shared sub-expressions.

Trade-offs

No code change, but the documented convenience method stays exponential on shared graphs.

Downstream note

#

The downstream bindings checked (Solr's expression parser and two search servers built on Lucene) never bind expressions to other expressions lazily: Solr binds fields, the score and arguments, and the others resolve named fields to prebuilt sources, which is the eager workaround.

How it was found

#

Testing: a timing probe on a chain of diamond-shaped bindings, from an idea by an independent model of another family (OpenAI GPT-5.6), showed build time growing about 4x per two layers. A counting JUnit then gave exact counts, and a cost model (builds = paths in the graph) matched the stock jar on all 627,313 valid enumerated graphs.

The method in full149 words

Method: testing (the hunt's non-formal tier).

  • Lead. An idea from an independent model of another family (OpenAI GPT-5.6): expression bindings that share sub-expressions may be expanded once per path. Its probe timed the build on the stock main jar: 8-9 ms at 49 bindings, 129-138 ms at 61, about 4x per two layers, assertions on and off.
  • Exact count. A JUnit with a counting Expression subclass turned the timing into a count: 196,605 builds for 49 bindings.
  • Cost model. An exact model (builds = number of paths in the binding graph) was checked against the stock jar by bounded-exhaustive enumeration: every graph on 4 names and every DAG with 2 leaves and up to 5 expression names, 730,272 graphs (627,313 valid; on the rest validate() must throw), 79,987,206 checks, 0 mismatches; a linear-traversal mutant of the validate() part of the model is rejected. Values matched on every valid graph.

Low priority, cost only (values are always correct): applications on 4.6.0 through 10.6.0 or main that bind expressions to other expressions with SimpleBindings.add(String, Expression), the documented way, with default settings otherwise, pay one ExpressionValueSource per path through the binding graph every time they build the source, which is negligible for shallow graphs but exponential with layered sharing (196,605 objects at 49 bindings, about 0.13-0.19 s at 61, an OutOfMemoryError under a 1 GB heap from 70 bindings on a diamond chain or 41 names on a Fibonacci graph, before any document is read); on today's main the known per-hit cost of the same graphs (#9620 / #16880) runs out of memory one level earlier, so this leg becomes the visible failure only once per-hit caching is in place.
Summary
You bind named expressions that use each other with SimpleBindings.add(String, Expression), which the class javadoc documents ('This can be used to reference expressions from other expressions'), and some of them share a sub-expression, for example X1 = L0 + R0 with L0 = X0 + 1 and R0 = X0 * 2, repeated in a chain. You expect getDoubleValuesSource to build each binding a bounded number of times, as building the same graph eagerly with add(String, DoubleValuesSource) does. Instead every reference re-applies expression::getDoubleValuesSource, so the shared graph is expanded into a tree with one ExpressionValueSource per path: 3*(2^d - 1) objects for a chain of d diamonds (196,605 for 49 bindings), and building the source of 70 or more such bindings exhausts a 1 GB heap before any document is read, while the computed values stay correct.
