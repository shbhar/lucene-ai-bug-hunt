MultiPassIndexSplitter leaves the output write-locked when a split fails inside addIndexes

When MultiPassIndexSplitter.split fails inside addIndexes (a previous-major input, a corrupted source file, a full disk), it never closes the IndexWriter it opened, so that output directory refuses every new IndexWriter in the JVM until a restart. Every release since 3.0.0 that was run or read has it; the command-line tool is unaffected.

The finding in 30 seconds

#

split() closes the writer it opened only when addIndexes succeeds; there is no try/finally around it.

Background: the splitter, the write lock and addIndexes

#
  1. MultiPassIndexSplitter (module lucene-misc) splits one index into N parts. For each part it opens an IndexWriter on that part's output directory and copies the part's documents in with IndexWriter.addIndexes.
  2. An open IndexWriter holds its directory's write lock (write.lock). A second IndexWriter on the same directory gets LockObtainFailedException until the first one is closed or rolled back.
  3. With the default FSDirectory lock factory, the JVM also records every held lock path in one JVM-wide set; only closing that lock removes the path again.
  4. addIndexes can throw an ordinary exception (a full disk, a corrupted input, an input created by another major version) and leaves the writer open when it does, so whoever opened the writer must close or roll it back.

The finding, step by step

#
  1. You split a 2-document index into out1 and out2 with new MultiPassIndexSplitter().split(reader, new Directory[] {out1, out2}, false). The input was created by the previous major version (10; main is 11).
  2. split() opens an IndexWriter on out1 and calls addIndexes, which rejects the input: IllegalArgumentException: Cannot merge a segment that has been created with major version 10 into this index which has been created by major version 11.
  3. You expect the failed split to close the writer it opened, so a new IndexWriter on out1 (or a retried split with a different input) opens.
  4. Instead split() skipped its w.close(): the writer is still open and nobody can reach it, so new IndexWriter(out1, ...) throws LockObtainFailedException (on FSDirectory: "Lock held by this virtual machine"). On FSDirectory, closing the Directory, System.gc() and reopening do not help; only a JVM restart does.
  5. An I/O error while a part is written (for example a full disk; simulated in the tests), or a corrupted source file (CorruptIndexException), locks the output the same way. Nothing is corrupted: the failed output gets no commit and the source index is unchanged.

Who is affected

#

Applications that call the misc tool's split(...) from Java in a long-running JVM and then reuse an output path after a failed split: a retry once space is freed or with a converted input, or cleanup that opens a writer there. The command-line tool is unaffected. One path stays locked per failed split; nothing is corrupted.

Mechanism, terms and numbers683 words

MultiPassIndexSplitter.split(IndexReader, Directory[], boolean), the misc module's index splitter, opens an IndexWriter on each output directory, copies that part's documents in with addIndexes and calls close() only when addIndexes returns normally. If addIndexes throws, for example because the source index was created by the previous major version, a source file is corrupted or the disk fills up, the writer stays open. No caller can reach it, so the output's write lock is never released: every later IndexWriter on that directory, including a retried split, fails with LockObtainFailedException, and with the default FSDirectory lock factory this lasts until the JVM exits, even after the Directory is closed and garbage is collected. The code dates from the class's first commit (LUCENE-1959, 2009), so every release from 3.0.0 to 10.6.0 that was run or read, and main, have it; the sibling PKIndexSplitter has closed its writer on failure since 2011. The command-line main() is unaffected because its JVM exits on the exception, and nothing is corrupted. A few lines fix it: roll the writer back when addIndexes throws, or wrap it in try-with-resources.

The bug

#

All lines are at 645d4fe14a20; MultiPassIndexSplitter.java unless named.

  1. For each part, split() opens new IndexWriter(outputs[i], new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE)) (:108-109), prints Writing part i ... (:110), calls w.addIndexes(...) (:113) and then w.close() (:114). No try/finally, no rollback(), no try-with-resources; w never leaves the method.
  2. Opening the writer takes the lock: "Opening an IndexWriter creates a lock file for the directory in use. Trying to open another IndexWriter on the same directory will lead to a LockObtainFailedException" (IndexWriter.java:137-139); close() "Closes all open resources and releases the write lock" (:1342).
  3. addIndexes(CodecReader...) catches only Error and makes it a tragic event (IndexWriter.java:3390-3391); an IOException, CorruptIndexException or IllegalArgumentException propagates with the writer still open. Its javadoc lists CorruptIndexException and IOException (:3270-3271) and points to addIndexes(Directory...), which names "disk full" as an expected exception (:3084-3086).
  4. The deterministic trigger: split() always builds its outputs with new IndexWriterConfig(null) (:109), the current major version, and validateMergeReader (IndexWriter.java:3228-3236, called first at :3290) rejects a source leaf with another created-version major. No merge thread starts.
  5. With FSDirectory, NativeFSLockFactory keeps held lock paths in private static final Set<String> LOCK_HELD (NativeFSLockFactory.java:68) and throws "Lock held by this virtual machine" for a path already in it (:119); only NativeFSLock.close() removes the path (:145, :212). The leaked writer's lock is never closed, so the path stays refused until the JVM exits; garbage collection can drop the file handle but not the record. With the handle gone, another JVM could then lock the path (code reading, not run); the refusal is inside the JVM that ran the split.
  6. main() calls split() (:182) and declares throws Exception, so for the command-line tool the exception ends the JVM and the OS releases the lock. A program that calls main() and survives its exception is hit like any other caller (code reading).

Other triggers (executed)

#
  • Corrupted source: one flipped byte in the source's .fdt file makes split() throw CorruptIndexException: checksum failed from the merge; the output, which never had an I/O problem, then refuses a new writer with "Lock held by this virtual machine".
  • Full disk (simulated): an output whose createOutput throws IOException leaves it locked the same way, and a retried split into the same outputs fails with the same message after the fault is removed.
  • With both, the merge runs on a ConcurrentMergeScheduler thread, which also prints an uncaught MergeException to stderr. That is normal behaviour and not part of this bug; split() itself throws the original exception.

Previous-major note: that setIndexCreatedVersionMajor(LATEST.major - 1) behaves like an index really written by the previous release is code reading (both carry created-version major N-1, the only value this check reads; IndexWriterConfig.java:173-180 documents the setter for exactly this addIndexes restriction). That split() cannot split a previous-major index at all is a separate limitation and not part of this bug.

Exposure and likelihood182 words
  • Who is hit. Java callers of MultiPassIndexSplitter.split(...) in a JVM that keeps running after a failed split: a service, a maintenance tool, a test suite. Not the command-line main().
  • Default vs opt-in. The class is in the optional lucene-misc module; inside it nothing else is needed. The default FSDirectory and NativeFSLockFactory give the JVM-lifetime lock; assertions make no difference.
  • Effect. One leaked open IndexWriter per failed split; that output path refuses new writers until the JVM restarts, other paths keep working (a split into fresh directories succeeds in the same JVM).
  • No damage. No hang (the slowest failed split threw in 168 ms), no wrong results, no corruption: the failed output gets no commit, an index already there keeps its previous commit, the source index is unchanged. This was run for the previous-major trigger; for the merge-time triggers it follows from the code: nobody can commit or close the leaked writer.
  • Scale. None needed: 2 documents reproduce it. In the hunt's fault-injection sweep, a one-shot IOException at a single file-system event left the output locked in 18,654 of 18,866 split runs.

Why it looks unintended

#
  • split() creates the writer as a local variable and never hands it out, so only split() can close it; addIndexes leaves the writer open after an ordinary exception.
  • The sibling PKIndexSplitter has closed its writer on failure since 2011 (LUCENE-2919).
  • No comment, test or discussion chose this; the upstream test calls split() directly as a library API.
The full argument188 words
  • Only split() can release the writer. It is a local variable (MultiPassIndexSplitter.java:108-109); the IndexWriter javadoc ties the lock to an open writer (IndexWriter.java:137-139), and addIndexes keeps the writer open after a non-Error exception (:3390-3391), so closing it is the opener's job.
  • A public library API that expects failures. split() documents @throws IOException If there is a low-level I/O error (:68); the upstream TestMultiPassIndexSplitter calls split() directly (testSplitRR, testSplitSeq), not main().
  • The sibling does it on purpose. PKIndexSplitter was added in LUCENE-2919 (bba6b01826d, 2011-06-17) and got failure-path closing the next day (40f5948b3df, Uwe Schindler, IOUtils.closeSafely(!success, w)); today try (IndexWriter w = new IndexWriter(target, config)) wraps the same addIndexes call (PKIndexSplitter.java:117-130, since #14913). IndexRearranger in the same package also uses try-with-resources.
  • Nobody chose it. The LUCENE-1959 thread (#3034, 30 comments) never discusses exceptions, cleanup or the lock; none of the 16 later commits that touched the block added or rejected cleanup; a different leak in this class (the MultiReader) was fixed as a bug in 2012 (1f192290c5a).
The devil's-advocate check195 words

The strongest case for "works as designed" (the devil's-advocate verifier and a reviewer from another model family, OpenAI GPT-5.6): the class is a command-line tool (@SuppressForbidden(reason = "System.out required: command line tool"), and main() never closes its readers either), so it relies on JVM exit for cleanup; split() promises only IOException and nothing about the outputs after a failure; a half-written output must be thrown away anyway; and the first trigger was synthetic fault injection.

Why it fails: split() is a separate public method with full javadoc that the upstream test calls directly; the caller cannot release the writer at all; the lock blocks the path for the JVM's whole life, even for an output that never had an I/O problem (the corrupted-input case); the previous-major trigger needs no fault injection at all, and the corrupted-source one no faulty directory (the test flips one byte of a source file); and the sibling class has handled the same step exception-safely since 2011. Every verifier rated this argument weak; the cross-model fact check of this doc rated it moderate and still called the behaviour a minor bug. It bounds the impact (minor), not the validity.

Suggested fix

#

Recommended B. Roll back on failure, close on success

Roll the writer back when addIndexes throws and close it only on success (catch (Throwable t) { IOUtils.closeWhileSuppressingExceptions(t, w::rollback); throw t; }): the lock is released and a failed output keeps its earlier contents. The repro and the misc module's 317 tests pass. Try-with-resources (as in PKIndexSplitter) also works but commits an empty index on failure.

All options and trade-offs2 options · 738 words

Both options were run through gradle in a scratch worktree of 645d4fe14a20, and both fix the repro and pass the closest suite. They differ in what a failed part leaves in its output directory: a comparison probe split a previous-major input into an output that already held a 3-document index. Stock and B leave the 3 documents; A replaces them with an empty index. B is recommended because it keeps that outcome; A is the smaller change and matches the sibling class.

B. Roll back on failure, close on success (validated by the checks) (recommended)

#

In split() (MultiPassIndexSplitter.java:108-114): wrap the addIndexes step in try/catch (Throwable t), roll the writer back there and rethrow; keep w.close() after it for the success path. +11/-4, including one import (org.apache.lucene.util.IOUtils).

       IndexWriter w =
           new IndexWriter(outputs[i], new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE));
-      System.err.println("Writing part " + (i + 1) + " ...");
-      ...
-      w.addIndexes(sr.toArray(CodecReader[]::new)); // TODO: maybe take List<IR> here?
+      try {
+        System.err.println("Writing part " + (i + 1) + " ...");
+        ...
+        w.addIndexes(sr.toArray(CodecReader[]::new)); // TODO: maybe take List<IR> here?
+      } catch (Throwable t) {
+        // release the output's write lock without committing anything into it
+        IOUtils.closeWhileSuppressingExceptions(t, w::rollback);
+        throw t;
+      }
       w.close();

Trade-offs

  • Keeps today's outcome for the output of a failed part: nothing is committed (rollback() returns the directory to its last commit, IndexWriter.java:2566-2571), so an index already there keeps its documents (probe: 3 before, 3 after), and an empty output stays without an index (probe: no files), which marks the part as failed.
  • An exception from rollback() is added to the original one as suppressed (an Error from rollback() is thrown instead, with the original suppressed into it, IOUtils.java:114-136); after an Error the tragic-event handling has already rolled the writer back (IndexWriter.java:6090-6106), and the second rollback() does nothing (:2576-2584).
  • The same helper as NativeFSLockFactory.tryLock (NativeFSLockFactory.java:139-141); slightly longer than A.

What the checks validated

  • Stock 645d4fe14a20: the repro fails with assertions on and off.
  • With B: the repro passes with assertions on and off; TestMultiPassIndexSplitter passes together with it (2 classes, 3 tests, 0 failures); the comparison probe keeps the 3 documents; the whole :lucene:misc:test with the repro in place passes (24 classes, 317 tests, 0 failures, 9 skipped, all in other classes).
  • The independent reproducer's public-API program on 645d4fe14a20 (plain FSDirectory; a simulated full disk, then a corrupted .fdt), with B: after each failed split a new writer opens, and after the simulated full disk the retried split succeeds, assertions on and off; stock fails.
  • The module's checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest pass with B and the repro in place once the repro's long comment is wrapped onto two lines, which the formatter asks for (comment only; the fixed class was not flagged).

A. try-with-resources, as in PKIndexSplitter (validated by the checks)

#

Wrap the per-part writer in try (IndexWriter w = new IndexWriter(...)) { ... } and drop the explicit w.close() (MultiPassIndexSplitter.java:108-114), +7/-7. This is the hunt's fix.

-      IndexWriter w =

-      ...

+      try (IndexWriter w =
+          new IndexWriter(outputs[i], new IndexWriterConfig(null).setOpenMode(OpenMode.CREATE))) {
+        ...
+        w.addIndexes(sr.toArray(CodecReader[]::new)); // TODO: maybe take List<IR> here?
+      }

Trade-offs

  • The smallest change and the sibling's idiom (PKIndexSplitter.java:117).
  • On failure close() commits: commitOnClose defaults to true (IndexWriterConfig.java:102), close() commits when it is set (IndexWriter.java:1363-1368), and a CREATE-mode writer records a pending change when it opens (IndexWriter.java:1017-1019). So a failed part leaves a valid, empty index in its output (probe: segments_1) and replaces any index that was there (probe: 3 documents before, 0 after).
  • If that commit fails too (for example the disk is still full), close() still closes the writer and releases the lock (IndexWriter.java:1351-1352); its exception is suppressed into the original one.

What the checks validated

  • With A: the repro passes with assertions on and off; TestMultiPassIndexSplitter passes together with it (2 classes, 3 tests, 0 failures); the comparison probe shows the 3 documents replaced by an empty index.
  • Earlier checks of the same edit on main ea57360912ed: the finder's, the reproducer's, the cross-model adversary's and the devil's-advocate verifier's tests all pass with it, and upstream TestMultiPassIndexSplitter passes 2 of 2.

Downstream note

#

A read-only code search found no call to MultiPassIndexSplitter in Elasticsearch, OpenSearch or Solr, so the exposure is applications that use the misc tool's split() directly.

How it was found

#

Semi-formal: a custom bytecode abstract interpreter with explicit exception edges, run over the stock jars, flagged the writer as still open on the exception edge of addIndexes. A fault-injection sweep then found the output lock leaked in 18,654 of 18,866 split runs (0 of 19,020 for the sibling PKIndexSplitter), and a JUnit confirmed it.

The method in full164 words

Method: exception-edge resource scan (the study's semi-formal tier). A hunting AI tool wrote ResourceScan, a bytecode abstract interpreter that tracks acquired resources (directory locks, writers, readers, inputs) along every exception edge, with interprocedural summaries, and ran it over the stock main jars (core, codecs, facet, suggest, misc, replicator: 3,388 classes, 24,094 methods). Vacuity check: all 7 planted leaks were flagged and none of 8 clean idioms.

  • It reported the IndexWriter acquired at MultiPassIndexSplitter.java:109 as live on the exception edge of IndexWriter.addIndexes (:113); the AI tool triaged the group by reading the source.
  • A dynamic single-fault sweep then re-ran a split once per file-system event with a one-shot IOException at that event (seed 1531531531): the output lock leaked in 18,654 of 18,866 MultiPassIndexSplitter.split runs and in 0 of 19,020 PKIndexSplitter.split runs.
  • A JUnit with an injected full disk confirmed it on the stock jars; an independent verifier added the corrupted-input trigger and the devil's-advocate verifier the previous-major trigger, which became the minimal repro.

History

#

Present since the class was added (LUCENE-1959, 7d0d4ecc44c, 2009-10-13), first released in 3.0.0; none of the 16 later commits that touched the block added cleanup. It fails on every release run, from 3.0.0 to 10.6.0, and on main.

Versions tested7 rows

Introduced by 7d0d4ecc44c "LUCENE-1959 Add MultiPassIndexSplitter." (Andrzej Bialecki, 2009-10-13; svn r824798; JIRA LUCENE-1959, now #3034; no PR). The original split() already opened the writer, called addIndexes and closed it only on success. git log -L follows the block through the renames; the 16 later commits that touched it are API migrations and cosmetic changes (among them LUCENE-4246 and LUCENE-5871, which renamed close() to shutdown() and back), and none added try/finally, rollback() or try-with-resources. Up to 5.0.0 the second writer reports "Lock obtain timed out" (the 1 s lock wait of that era); from 5.5.5 on it fails at once with "Lock held by this virtual machine". 2.9.x does not ship the class. Releases not run (3.0.1, most minors) have the same block by reading; 3.0.2, 3.0.3 and 8.8.2-8.11.3 were neither run nor in the history clone. Every run used JDK 25; Windows and x86 were not run.

Registry title
MultiPassIndexSplitter.split never closes the IndexWriter it opened on an output when addIndexes throws, so that output directory stays write-locked and every later IndexWriter or split into it in the same JVM fails with LockObtainFailedException until the JVM restarts
Area
misc / index tools (MultiPassIndexSplitter.split, failure cleanup)
Priority
Low, rank 1085: MultiPassIndexSplitter leaves its output write-locked after a failed addIndexes, only in the rarely used misc tool on same-JVM retry.
Impact class
minor
Impact note
Only programmatic callers of the lucene/misc MultiPassIndexSplitter (split(IndexReader, Directory[], boolean); the command-line main() is unaffected because its JVM exits on the exception) are hit, when a split throws inside addIndexes and the same JVM then reuses that output path. Three executed triggers: an I/O error while an output is written (a full disk), a corrupted source index (CorruptIndexException from the merge's checksum check), and a source index created by the previous major version (IllegalArgumentException, because split() hardcodes the output config). After that, every new IndexWriter or retried split into that path throws LockObtainFailedException 'Lock held by this virtual machine' until the JVM restarts, even after Directory.close() and System.gc() [exec]. Default FSDirectory and NativeFSLockFactory suffice and no scale is needed. One writer leaks per failed split. In the security probe (previous-major trigger) the failed output held nothing but write.lock, a pre-existing index there kept its previous commit, the source index was unchanged, and a split into fresh directories still worked in the same JVM [exec].
Summary
You split an index with MultiPassIndexSplitter.split, the split throws while it writes one of the output parts (for example the disk fills up, a file of the source index is corrupted, or the source index was created by the previous major version), and you then retry the split or open an IndexWriter on that output directory in the same JVM. You expect this to work once the cause is gone, because the failed split should close the IndexWriter it opened on the output. Instead split() calls close() only after addIndexes succeeds, so the writer, which the caller cannot reach, keeps the output's write lock, and every later IndexWriter or split into that directory throws LockObtainFailedException 'Lock held by this virtual machine' until the JVM restarts.
