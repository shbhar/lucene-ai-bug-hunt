ToParentBlockJoinSortField with a STRING field, max-child selection and childMissingValue = STRING_LAST throws IndexOutOfBoundsException: the missing-last marker is looked up as a term

Since 10.5.0, a STRING ToParentBlockJoinSortField with max-child selection and childMissingValue = STRING_LAST throws IndexOutOfBoundsException once a parent has one child with the field and one without. The join code's "missing child won" marker, Integer.MAX_VALUE, is looked up as a term ordinal.

The finding in 30 seconds

#

ToParentBlockJoinSortField sorts parents by a field of their children: the lowest or the highest child value decides. Since 10.5.0, childMissingValue says where a child without the field ranks in that choice. For strings, the join code marks "a missing child, sorted last, won" with a fake ordinal, and the comparator then looks it up.

Background: sorting parents by a child field

#
  1. A block is a group of child documents followed by their parent, added together with addDocuments. ToParentBlockJoinQuery matches children and returns their parents.
  2. ToParentBlockJoinSortField sorts those parents by a child field: reverseChildren = false takes the lowest child value, true the highest. Since 10.5.0, childMissingValue (STRING_FIRST or STRING_LAST for strings) lets children without the field take part in that choice.
  3. A string sort works on ordinals: each distinct value of the field in a segment has a number from 0 to getValueCount() - 1. When a hit enters the top hits, the comparator copies its value with lookupOrd(ordinal).

The finding, step by step

#
  1. You index one block: a child with s = "b", a child without s, and their parent. You sort the parents with ToParentBlockJoinSortField("s", STRING, false, true, null, SortField.STRING_LAST, parents, children): the highest child value decides (reverseChildren = true), and a child without s counts as "missing, sorts last".
  2. You expect 1 hit, the parent. The missing child beats b in the max, so the parent's sort key is "after every value".
  3. You get IndexOutOfBoundsException from the doc-values terms dictionary, with assertions on and off. The 7-argument constructor with reverse = true fails the same way.
  4. Why: the join wrapper reports "a missing child won" as ordinal 2,147,483,647 (Integer.MAX_VALUE). The string comparator treats every ordinal except -1 as a real term and asks for term number 2,147,483,647 of a field that has 1 term.
  5. Only Type.STRING with max-child selection and child STRING_LAST fails, on 10.5.0 to 10.6.0 and main. MIN selection, STRING_FIRST, a null child missing value and parents whose children all lack the field do not throw.

Who is affected

#

Only applications on 10.5.0 or later that combine a STRING field, max-child selection and childMissingValue = STRING_LAST. For them ordinary data triggers it: a parent with one child that has the field and one that does not. Each search that puts such a parent in its top hits fails; nothing is written or corrupted.

Mechanism, terms and numbers510 words

Since 10.5.0 (#15727), ToParentBlockJoinSortField takes a childMissingValue: what a child without the sort field counts as in the min/max choice among its siblings (STRING_FIRST or STRING_LAST for Type.STRING). For strings the join wrapper ToParentDocValues.SortedDVs represents "a missing child, sorted last" by the ordinal Integer.MAX_VALUE, and with max-child selection (reverseChildren = true, or reverse = true on the 7-argument constructor) that marker wins for every parent whose block has a child with a value and a member without one. TermOrdValComparator.copy() treats only -1 as missing and calls lookupOrd(Integer.MAX_VALUE), and the default doc-values format rejects the ordinal with an IndexOutOfBoundsException. One block of three documents is enough; it fails with assertions on and off on main, 10.5.0, 10.5.2 and 10.6.0 (10.5.1 was run with assertions on only). Nothing is written or corrupted. A one-wrapper fix in the sort field stops the crash and passes the join module's tests; where such a parent should then sort, relative to parents with no valued child, is a design choice for the maintainers.

The 7-argument constructor passes reverse as both reverseParents and reverseChildren (:120-128).
  • The marker. BlockJoinSelector.wrap (BlockJoinSelector.java:96-132, @lucene.internal at :34) reaches ToParentDocValues.SortedDVs, which sets missingOrd = sortMissingLast ?   • Executed on the repro's index: at the parent, MAX + missing-last gives ordValue() = 2147483647 with getValueCount() = 1; MIN + missing-first gives -1; the other two combinations give the real ordinal 0.
  • The throw. TermOrdValComparator.copy() (TermOrdValComparator.java:343-358) maps only -1 to its missing state (:345-348), asserts ord >= 0 (:350) and calls termsIndex.lookupOrd(ord) (:354).   • When. TopFieldCollector calls copy() for every hit that enters the top-N queue (TopFieldCollector.java:126, :116); comparisons against the queue bottom use the ordinal without a lookup (TermOrdValComparator.java:324-341). A search fails once an affected parent is copied into its top hits; an affected parent that is never competitive is never copied, so the failure can look data- and top-N-dependent.
  • Not affected: MIN selection (Math.min keeps the real ordinal), STRING_FIRST with MAX (Math.max(ord, -1)), a null child missing value, and parents whose children all lack the field (advanceExact returns false, ToParentDocValues.java:316-328).
Exposure and likelihood202 words
  • Who is hit. ToParentBlockJoinSortField on Type.STRING with reverseChildren = true (or reverse = true on the 7-argument constructor) and childMissingValue = SortField.STRING_LAST, on 10.5.0 or later. Default codec and settings; the SimpleText format also rejects the ordinal. By code reading the index size does not matter; the runs used small indexes.
  • Trigger. A parent block with at least one child that has the field and at least one member without it, which is the data the option exists for. A block member outside childFilter also counts as missing in this code (a separate finding, LFV-220), so a block whose filtered children all have the field but which holds another document type also throws.
  • What goes wrong. The search throws an unchecked IndexOutOfBoundsException instead of returning results. Nothing is written or corrupted, and the same searcher keeps answering other queries and other sorts.
  • Reach. No downstream user of this combination is known (see the downstream note).
  • Workaround. childMissingValue = null or STRING_FIRST, or MIN selection, avoid the crash but give a different order.
  • How likely. Plausible: only users of a new option combination, but for them the first query that copies an affected parent into its top hits fails, every time.

Why it looks unintended

#
  • The javadoc lists STRING_LAST as a child missing value for Type.STRING that "participates in the min/max selection", with no limit on the reverse flags.
  • The marker breaks the SortedDocValues contract: lookupOrd needs 0 <= ord < getValueCount(); here 2,147,483,647 against 1.
  • The only STRING_LAST test is commented "descending" but sorts children ascending.
The full argument265 words
  • Contract. childMissingValue: "The missing value for child documents that lack the sort field. This value participates in the min/max selection among siblings. Type constraints are the same as for parentMissingValue", and for Type.STRING "use SortField#STRING_FIRST or SortField#STRING_LAST" (ToParentBlockJoinSortField.java:139-145, and :106-108 for the 7-argument constructor). Validation accepts STRING_LAST for every reverse flag (:178-198). The 10.5.0 CHANGES entry: children with missing values "now correctly participate in the min/max selection according to the configured missing value" (lucene/CHANGES.txt:1187-1189).
  • SortedDocValues. The ordinal "is dense, starts at 0" (SortedDocValues.java:41-42); lookupOrd needs "ord ... >= 0 and < getValueCount()" (:51).
  • Review history. In the #15727 review the reviewer (romseygeek) asked that the wrapper "still needs to return true from advanceExact() ... And then return an appropriate value from ord()"; the contributor (gmarouli) answered "my initial thought is -1 since any positive number could be confused with an actual ordinal", and the reviewer pointed to TermOrdValComparator's own missingOrd = Integer.MAX_VALUE (2026-02-24). In the comparator that value is internal state, used only for documents without an ordinal (TermOrdValComparator.java:221-228, :345-348); copy() and lookupOrd were not discussed.
  • Tests. TestBlockJoinSorting's only STRING_LAST child case is commented "Sort by descending with missing values last in child level" but passes reverse = false (TestBlockJoinSorting.java:563-572), so max-child selection with STRING_LAST never ran through the sort field.
  • Loud, but not noise. The failure is a clean exception, but it needs no absurd parameter: three documented, validated settings and ordinary data (a block with a child that lacks the field).
The devil's-advocate check107 words

The case: the marker is deliberate. TestBlockJoinSelector pins ordValue() == Integer.MAX_VALUE for MAX with missing-last (:222, :224, :278, :282), the selector is @lucene.internal, and the sort field is @lucene.experimental (ToParentBlockJoinSortField.java:46).

Why it fails: those tests pin the internal selector's value and never call lookupOrd. The public sort field feeds that value, through documented and validated options, to a comparator that cannot handle it. @lucene.experimental allows API changes, not crashes on accepted input. The argument constrains the fix (keep the selector value), not the verdict; the cross-model intended-behaviour review, the devil's advocate and the adjudication all rated it weak.

Suggested fix

#

Recommended Report the parent as having no value (a FilterSortedDocValues in ToParentBlockJoinSortField)

Report a parent whose missing-last child won the max as having no value: for max-child selection with child STRING_LAST, the sort field wraps the doc values so advanceExact returns false on Integer.MAX_VALUE. The test and the whole join module pass (105 tests, the new one included). Such a parent then sorts by parentMissingValue, which matches the javadoc only for STRING_LAST.

final boolean childMissingLast = childMissingValue == STRING_LAST;
SortedDocValues selected =
    BlockJoinSelector.wrap(sortedSet, type, parents, toIter(children), childMissingLast);
if (type == BlockJoinSelector.Type.MAX && childMissingLast) {
  // The selector reports "a child without a value, sorted last, won the max" as
  // Integer.MAX_VALUE, which is not an ordinal: report such a parent as having no value.
  return new FilterSortedDocValues(selected) {
    @Override
    public boolean advanceExact(int target) throws IOException {
      return in.advanceExact(target) && in.ordValue() != Integer.MAX_VALUE;
    }
  };
}
return selected;
All options and trade-offs3 options · 959 words

Three options; A was validated with gradle in a fresh scratch worktree at 645d4fe14a20, B and C were not executed. A stops the crash; B is the complete fix if the maintainers want a parent whose missing child won to keep its own position. Not a fix: clamping the marker to a real ordinal (getValueCount() - 1), which would turn the exception into a silently wrong sort key, the largest real term, in FieldDoc.fields.

Report the parent as having no value (a FilterSortedDocValues in ToParentBlockJoinSortField) (validated by the checks) (recommended)

#

In getStringComparator (ToParentBlockJoinSortField.java:228-229), only when max-child selection meets childMissingValue == STRING_LAST, wrap the selector's doc values in a FilterSortedDocValues whose advanceExact returns false when the selected ordinal is Integer.MAX_VALUE. TermOrdValComparator then applies its own missing handling and never looks the marker up. It is the hunt's crash-avoidance sketch, limited to the one case that produces the marker and with an import instead of a qualified name (diff: +15 / -2 lines, one file).

final boolean childMissingLast = childMissingValue == STRING_LAST;
SortedDocValues selected =
    BlockJoinSelector.wrap(sortedSet, type, parents, toIter(children), childMissingLast);
if (type == BlockJoinSelector.Type.MAX && childMissingLast) {

Trade-offs

  • No change elsewhere: only MAX with missing-last produces the marker, and no wrapper is added otherwise. The selector keeps returning Integer.MAX_VALUE, so TestBlockJoinSelector is untouched.
  • The comparator is built with Pruning.NONE and reads each document's ordinal only through advanceExact then ordValue (TermOrdValComparator.java:309-315), so the filter covers every such read.
  • Order: such a parent sorts where parentMissingValue puts parents without a valued child. That matches the javadoc when parentMissingValue = STRING_LAST, not otherwise. Executed with the fix (blocks P1 = [b, missing], P2 = [c], P3 = [missing]; ascending parents, max child, child STRING_LAST): parentMissingValue = STRING_LAST gives P2, P1, P3; null or STRING_FIRST give P1, P3, P2, where the javadoc implies P3, P2, P1. The cross-model reviewer's own two-parent test shows the same with the hunt's sketch (expected [second, first], got [first, second]). The order probe sorts parents ascending only; with reverseParents = true the hit queue multiplies every comparison by -1 (FieldValueHitQueue.java:68, :144), which was not probed.
  • What the test covers: the minimal (regression) test asserts only the hit count, so it checks the crash, not the order; the order above comes from the separate order probe.
  • By code reading this is what MIN with STRING_FIRST already does: the wrapper returns -1 (executed) and copy() maps -1 to the comparator's missing state (:345-348).

Give the comparator a separate "selected child sorts last" state

#

Keeps the documented order for every parentMissingValue. The raw ordinals cannot carry the third state as they are: within a segment compare (TermOrdValComparator.java:146), compareBottom (:332) and compareTop (:405) subtract one int ordinal from another, and with parentMissingValue null or STRING_FIRST (the cases B is for) the comparator's missing ordinal is -1 (:224-228), so Integer.MAX_VALUE - (-1) overflows to Integer.MIN_VALUE and flips the sign. Executed by the independent fact check (-ea and -da): a stock comparator over the selector, with only lookupOrd(Integer.MAX_VALUE) made non-throwing, one segment, ascending: parents R3 = [missing] then R1 = [b, missing] come back R1, R3, where the marker's meaning gives R3, R1; two other layouts happen to come out right. Only with parentMissingValue = STRING_LAST does no slot hold -1, the case fix A already places correctly. Across segments the slot value is missing too: cross-segment compare and compareValues use values[slot], with null meaning the parent missing value (:149-160, :188-198); FieldDoc.fields come from value(slot) (:183-185); searchAfter maps the top value back through lookupTerm (:230-243). Not executed as a fix.

Trade-offs

A BytesRef has no "after every term" value, so this needs a marker object, overflow-safe comparisons (Integer.compare) and changes to copy, compare, compareBottom, compareTop, compareValues and setTopValue, in TermOrdValComparator or a join-specific comparator. It would also have to settle what MIN with STRING_FIRST (ordinal -1) means when parentMissingValue = STRING_LAST. An API-level design choice for the maintainers.

Map the marker inside ToParentDocValues

#

Return "no value" (or -1) from ToParentDocValues.SortedDVs itself. Avoids the crash for every caller of the public BlockJoinSelector.wrap, with the same order trade-off as A. Not executed.

Trade-offs

Contradicts the TestBlockJoinSelector assertions that pin Integer.MAX_VALUE (:222, :224, :278, :282), which encode the #15727 design.

Downstream note

#

No known downstream product reaches this path: Solr's child-field sort uses the constructor without missing values, and Elasticsearch and OpenSearch implement nested sorting in their own code (read, not executed).

How it was found

#

Found by reading how the 10.5.0 block-join missing-value code reports a missing child to the string comparator, then probing every reverse-flag and child-missing-value combination on the stock main jars: only max child with STRING_LAST threw. An independent reproducer, cross-model reviews, a devil's advocate and an adjudication confirmed it.

The method in full145 words

Method: code reading, then executed tests (the hunt's non-formal tier: the bug was seen in the code, not reported by a model checker).

  • First signal (2026-10-26). A unit studying block-join code read the #15727 missing-ordinal handling in ToParentDocValues (MAX selection against missingOrd = Integer.MAX_VALUE) next to how TermOrdValComparator.copy() treats ordinals. A hand-written probe over every reverse-flag x child-missing-value combination and a JUnit on the stock main jars confirmed it. The unit's bounded-exhaustive sort checker (every layout of up to 5 documents) had to exclude this combination because it throws, and is not credited as the finder.
  • Checks. An independent reproducer, an executed cross-model refute review and a reading-only intended-behaviour review (OpenAI GPT-5.6), an intended-behaviour devil's advocate and an adjudication confirmed it; a follow-up swept the releases, searched for prior reports and assessed security; the repro was then reduced to one block and one search.

LFV-223, snapshot of 2026-11-02

Registry title
ToParentBlockJoinSortField on a STRING field with max-child selection and childMissingValue=STRING_LAST throws IndexOutOfBoundsException when a parent has children both with and without the field
Area
join / ToParentBlockJoinSortField string sort (ToParentDocValues missing-child ordinals, since #15727)
Priority
Low, rank 589: Since 10.5.0 a STRING ToParentBlockJoinSortField with max-child selection and STRING_LAST throws IndexOutOfBoundsException on ordinary data, deterministic for users of that new option, which no downstream uses yet.
Impact class
crash
Impact note
Applications on 10.5.0 or later that sort parents with ToParentBlockJoinSortField on a STRING field with max-child selection (reverseChildren=true, or reverse=true on the 7-argument constructor) and the new childMissingValue=SortField.STRING_LAST get an unchecked IndexOutOfBoundsException instead of results from every search that copies into its top hits a parent whose block has a child with the field and a member without it, with -ea and -da, the default codec and settings and any index size; MIN selection, STRING_FIRST, a null child missing value and parents whose children all lack the field work, nothing is written or corrupted, the same searcher keeps answering other queries, and only 10.5.0-10.5.2, 10.6.0 (by reading) and main are affected because the option is new in 10.5.0.
Summary
You sort parent documents by a string field of their children, descending, with new ToParentBlockJoinSortField("s", STRING, reverse=true, null, SortField.STRING_LAST, parents, children) (or the 8-argument form with reverseChildren=true), and expect the search to return the parents with children that lack the field sorted as missing-last, because the javadoc lists STRING_LAST as a legal child missing value that 'participates in the min/max selection among siblings'. Instead, as soon as the search collects a parent that has one child with the field and another child without it, it throws IndexOutOfBoundsException from the doc-values terms dictionary (Lucene90DocValuesProducer$TermsDict.seekExact via ToParentDocValues$SortedDVs.lookupOrd), with -ea and -da. The cause is that the block-join wrapper reports 'a missing child, sorted last, won the max' as the ordinal Integer.MAX_VALUE, and the string comparator TermOrdValComparator treats every ordinal other than -1 as a real one and looks it up.
