ConjunctionUtils.createConjunction sorts the caller's TwoPhaseIterator list in place, so List.of(a, b) can throw UnsupportedOperationException

ConjunctionUtils.createConjunction puts two-phase iterators cheapest first by sorting the list you pass, in place. With List.of(a, b), a costing 2 and b costing 1, the call throws UnsupportedOperationException (a LinkedList of two or more throws in any order); Lucene's own queries never pass such a list, and every release since 9.0.0 has it.

The finding in 30 seconds

#

A conjunction checks its two-phase iterators cheapest first. It gets that order by sorting the very list you passed in, in place.

Two-phase iterators in 20 seconds

#
  1. A TwoPhaseIterator has a cheap approximation (a DocIdSetIterator that may over-match) and a matches() check that confirms each candidate document.
  2. matchCost() estimates what one matches() call costs. A conjunction of several two-phase iterators calls matches() cheapest first, so it orders them by matchCost().
  3. ConjunctionUtils.createConjunction(allIterators, twoPhaseIterators) is the public factory that builds such a conjunction from two lists the caller supplies.

The finding, step by step

#
  1. Make two two-phase iterators over a one-document range (DocIdSetIterator.all(1)) that both match doc 0: a with matchCost() 2, b with matchCost() 1.
  2. Call ConjunctionUtils.createConjunction(List.of(a.approximation(), b.approximation()), List.of(a, b)).
  3. You expect a conjunction whose nextDoc() is 0. That is what you get when the same list is already cheapest first, List.of(b, a).
  4. Instead it throws UnsupportedOperationException, with assertions on and off: to check b before a, the factory sorts your list itself, and List.of refuses the write.
  5. Other lists: a LinkedList throws IllegalArgumentException ("can only sort random access lists in-place") in either order; an ArrayList works but comes back as [b, a].

Who is affected

#

Only code that calls the public ConjunctionUtils.createConjunction itself with two or more two-phase iterators in an immutable list (List.of, List.copyOf, Collections.unmodifiableList) whose match costs are not in non-decreasing order, or with two or more in a LinkedList. Lucene's own queries pass fresh ArrayLists or an empty list and are not hit. The failure is loud; nothing wrong is returned.

Mechanism, terms and numbers488 words

ConjunctionUtils.createConjunction(List<DocIdSetIterator> allIterators, List<TwoPhaseIterator> twoPhaseIterators) is a public factory whose javadoc calls both arguments "a list of ... to combine" and says nothing else about them (ConjunctionUtils.java:65-77 at 5adff78bb168). To run the cheapest matches() first, the conjunction orders the two-phase iterators by matchCost(), and it does so by sorting the caller's list itself, in place, before copying it (ConjunctionDISI.java:354-357), while the same method copies allIterators before sorting that one (:114-133). So an immutable list of two or more whose match costs are not already in non-decreasing order, such as List.of(a, b) with costs 2 and 1, makes the call throw UnsupportedOperationException, with assertions on and off; Collections.unmodifiableList fails the same way, a LinkedList of two or more throws IllegalArgumentException in any order, and a mutable ArrayList comes back reordered. Lucene's own queries pass fresh ArrayLists or an empty two-phase list and are not hit. The in-place sort dates from LUCENE-6276 (2015), when only lists built inside ConjunctionDISI reached it; #148 (LUCENE-9204, 2021, first released in 9.0.0) made the factory public without a copy. Every release from 9.0.0 through 10.6.0 and main are affected. Fix: sort the array the constructor already copies, as BitSetConjunctionDISI does, and sum the match costs over that array.

Where the caller's list is written (main 5adff78bb168)

#
  1. ConjunctionUtils.java:74-77: the public createConjunction forwards both lists unchanged to the package-private ConjunctionDISI.createConjunction.
  2. ConjunctionDISI.java:114-133: allIterators is copied into new ArrayLists, and only the copy is sorted by cost (:132). The caller's first list is never written.
  3. ConjunctionDISI.java:140-143: the caller's twoPhaseIterators list itself goes to new ConjunctionTwoPhaseIterator(disi, twoPhaseIterators).
  4. ConjunctionDISI.java:354-355: the constructor runs CollectionUtil.timSort(twoPhaseIterators, by matchCost) on that list and only then copies it with toArray (:357). This is the fix site.
  5. CollectionUtil (@lucene.internal) sorts "directly on the supplied lists" (CollectionUtil.java:24-29): it rejects a list that is not RandomAccess with "CollectionUtil can only sort random access lists in-place." (:80-82) and swaps through Collections.swap, that is List.set (:94), which an immutable list refuses. The TimSort reverses a descending run with swaps and writes nothing in a list that is already in non-decreasing order, equal costs included (TimSorter.java:110-123), so List.of(b, a) passes; a one-element list returns before any check (CollectionUtil.java:165).

Exposure and likelihood199 words
  • Not hit: Lucene's own queries. intersectScorers and intersectIterators (ConjunctionUtils.java:38-44, :56-62) and ConjunctionSpans.intersectSpans (lucene/queries, ConjunctionSpans.java:117-124) fill fresh ArrayLists. VectorScorer.java:65, :115, :143 (through ConjunctionUtils) and AbstractVectorSimilarityQuery.java:353 (through the package-private ConjunctionDISI.createConjunction) pass List.of(...), but with an empty two-phase list, which is never sorted.
  • No scale or configuration: two iterators and one document. The exception comes at construction, so no query runs with a wrong conjunction.
  • Can be data-dependent: whether it throws depends only on the order of the matchCost() values. Where a caller derives them from per-segment statistics, as PhraseQuery.termPositionsCost does (PhraseQuery.java:446-451), the same code can pass on one segment and throw on another; no such external caller was found.
  • Side effect: a mutable list (an ArrayList, or the array behind Arrays.asList) comes back reordered by match cost. No consequence of that was shown.
  • Reach: code searches found two direct callers outside Lucene: an Elasticsearch test with an empty two-phase list, and BlackLab's BLConjunctionSpans, a copy of ConjunctionSpans that fills fresh ArrayLists. Neither is affected. No public report of it was found since 9.0.0 (2021). Likelihood rare (an assessment from this evidence), priority Low.

Why it looks unintended

#
  • The javadoc calls both arguments only "a list of ... to combine", with no mutability or RandomAccess requirement; ConjunctionUtils has no @lucene.internal tag.
  • The same method copies allIterators before sorting it; BitSetConjunctionDISI also sorts a copy.
  • The in-place sort (2015) predates the public factory (2021); in-tree code passes List.of(...) to this method (with an empty two-phase list).
The full argument174 words
  • Contract. ConjunctionUtils is a public final class with no @lucene.internal or @lucene.experimental tag. The javadoc of createConjunction says only "@param allIterators a list of DocIdSetIterators to combine" and "@param twoPhaseIterators a list of TwoPhaseIterators to combine" (ConjunctionUtils.java:65-73).
  • Two parameters, two behaviours. allIterators is copied before it is sorted (ConjunctionDISI.java:114-133); BitSetConjunctionDISI copies first too (:240-242).
  • History. LUCENE-6276 (0ed54b3105c, 2015-11-13, "Added TwoPhaseIterator.matchCost()") added the in-place sort when the list-taking createConjunction was private and only lists built inside ConjunctionDISI reached it (git show 5e0e7a5479b^: private static DocIdSetIterator createConjunction). #148 made the factory public without a copy; #148, its issue #10244 and the later rewrite #12328 never discuss the sort or the caller's list.
  • Idiom. In-tree code does pass immutable List.of(...) lists to this very method (VectorScorer), though only with an empty two-phase list: immutable lists are a form Lucene itself uses for these parameters.
  • Tests. No test asserts the reordering; TestConjunctionDISI builds conjunctions only through intersectIterators and intersectScorers, which use their own lists.
The devil's-advocate check102 words

The strongest case for "intended" (the cross-model reviewer rated it moderate): the intended pattern is to fill caller-owned ArrayLists with the public addIterator / addTwoPhaseIterator helpers (ConjunctionUtils.java:79-98), which works; CollectionUtil documents in-place sorting; TwoPhaseIterator is @lucene.experimental.

Why it fails: the javadoc never says the helpers or a mutable list are required; CollectionUtil is @lucene.internal, and nothing on the public class passes its note on; @lucene.experimental is about API stability, not about throwing on a legal argument, and ConjunctionUtils itself has no tag. The pattern argument makes the trigger rare, not illegal. Verdict: not intended, a small defect.

Suggested fix

#

Recommended Copy first, sort the copy (fix A)

Sort the array the constructor already copies, not the caller's list: move the sort after toArray, use ArrayUtil.timSort as BitSetConjunctionDISI does, and sum the match costs over that array. The repro passes, and 77 core tests and 232 spans tests pass with it.

Trade-offs

No new allocation: the constructor already copies the list. It is the same stable TimSort with the same comparator, so the conjunction checks its iterators in the same order as before, and the total matchCost() is summed over the sorted array in the same order as today. That is why the loop changes too: float addition depends on order, and with the sum left on the caller's unsorted list, three iterators with costs 1e8, 4 and 4 in an ArrayList gave matchCost() 1.0E8 instead of main's 1.0000001E8; with the loop change it is 1.0000001E8, as on main (executed in the fact check). The only visible change left is that a caller's mutable list is no longer reordered; no in-tree caller reads its list after the call (ConjunctionUtils.java:34-63, ConjunctionSpans.java:117-124).

Downstream note

#

Downstream products are affected only where their own code calls ConjunctionUtils.createConjunction with an immutable or linked two-phase list; queries and documents alone cannot make the sort fail, because Lucene's own callers always pass it a fresh ArrayList (or no two-phase iterators at all).

How it was found

#

A proof-obligation audit of ConjunctionUtils's contract: the public factory's javadoc against what it does with its two list arguments. It copies one list and sorts the other in place, so an immutable or linked two-phase list cannot be sorted; a public-API JUnit test then witnessed the exception.

The method in full92 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked each public ConjunctionUtils method against its javadoc and followed both list arguments of createConjunction into ConjunctionDISI: allIterators is copied before it is sorted, twoPhaseIterators is sorted where it lies.
  • The finder then wrote a public-API JUnit test and sketched the copy-then-sort fix.
  • An independent reproducer and an executed cross-model review reproduced it with their own tests; a devil's-advocate verifier re-ran the finder's test and an adjudication re-ran the reproducer's ("Prior reports, history and checks").
