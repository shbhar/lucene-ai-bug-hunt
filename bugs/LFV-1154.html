After an AttributeFactory throws, IndexWriter can index later documents of the field with the previous stream's positions and offsets

If your analyzer's AttributeFactory throws while IndexWriter adds attributes, the document is dropped, but the field keeps the previous stream's attribute handles. The next "a b" on that stream lands at positions 1 and 3, not 0 and 1, and stays there in the index: phrase queries silently miss it.

The finding in 30 seconds

#

Background: how IndexWriter reads a field's tokens

#
  1. An analyzer turns a field's text into a TokenStream. Each token carries attributes: the term, its position increment (1 = the next position; 2 = one position skipped, for example by a removed stop word) and its offsets. When the stream ends, it reports a final increment and offset for what it skipped at the end.
  2. Attribute objects come from an AttributeFactory. You can give a tokenizer your own, for example new StandardTokenizer(factory). IndexWriter then asks the stream to add the attributes it needs that the tokenizer did not create, such as TermFrequencyAttribute, and the stream asks the factory.
  3. An analyzer hands back the same reused TokenStream object (per thread) each time. To save work, IndexWriter keeps, for each field, the stream it last read and handles to that stream's attributes, and skips the lookup when the same stream object comes back.

The finding, step by step

#
  1. Add a document whose field f is your own TokenStream, StopFilter(StandardTokenizer("x the the")). The two removed stop words leave a final position increment of 2 at the end of the stream.
  2. Add "a b" through an analyzer whose StandardTokenizer(factory) uses your AttributeFactory, which throws once when IndexWriter asks it for TermFrequencyAttribute. addDocument throws and the document is dropped, as expected.
  3. Add the same "a b" again; the factory works now. You expect a at position 0 and b at 1, so PhraseQuery f:"a b" finds 1 document, as it does without the failure.
  4. Instead it is accepted at positions 1 and 3 and the phrase finds 0 documents, with no error (with offsets indexed: 9-9 for both tokens, not 0-1 and 2-3). IndexWriter had cached the analyzer's stream before fetching its attributes, so it keeps reading the first stream's frozen values for every document that gets that stream back, until the next flush; the documents mis-indexed meanwhile keep their wrong positions.

Who is affected

#

Applications whose tokenizer uses their own AttributeFactory that throws when IndexWriter asks it for TermFrequencyAttribute (one built on the default packed token factory is never asked). No non-test factory in Lucene throws there. The silent case needs the cache to hold another stream's handles, in the repro an earlier document's own TokenStream. Every release examined since 4.9.0.

Mechanism, terms and numbers687 words

For each field, FieldInvertState caches the TokenStream it last inverted together with handles to that stream's attributes, and skips the lookup when the same stream object comes back, which is the normal case because an analyzer hands back the same reused TokenStream object (per thread) each time. setAttributeSource stores the new stream as the cached identity first (FieldInvertState.java:98 at 5adff78bb168) and only then calls addAttribute for TermFrequencyAttribute, PositionIncrementAttribute and OffsetAttribute (:107-109), which asks the stream's AttributeFactory for any attribute the stream lacks. If that factory throws, IndexWriter rejects the document as a non-aborting exception, as documented, but the cache now names the analyzer's stream while the frequency, position, offset and payload handles still belong to the previous stream of that field. Every later document of the field in the same in-memory segment that gets the same stream back reuses those handles, until the next flush or until the field inverts a different TokenStream object, and the documents mis-indexed in that window keep their wrong positions: after a pre-analyzed value that ended in two removed stop words, "a b" is indexed at positions 1 and 3 instead of 0 and 1 and PhraseQuery f:"a b" finds nothing, with no error. With no earlier stream, later documents fail with a NullPointerException instead. Every release examined since 4.9.0 (2014) has it. The trigger is an application-written factory that throws, which no non-test factory in Lucene's source does, so the priority is Low.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/)

#
  1. Getting the stream. IndexingChain.java:1981 calls field.tokenStream(analyzer, tokenStream): for a string value that is the analyzer's reused stream (analysis/Analyzer.java:183-195, document/Field.java:493-498), for a TokenStream value the field's own stream. :1984 calls invertState.setAttributeSource(stream).
  2. The identity is stored first (the fix site). FieldInvertState.java:97 compares the stream with the cached one; :98 stores the new stream; :106 refreshes termAttribute; :107 calls addAttribute(TermFrequencyAttribute.class). StandardTokenizer creates its term, offset, position-increment and type attributes itself (analysis/standard/StandardTokenizer.java:140-144) but not the frequency attribute, so AttributeSource.addAttribute asks the factory (util/AttributeSource.java:218), which throws. :108-110 never run.
  3. The document is rejected, the cache is not. The exception is non-aborting: only this document is marked deleted (DocumentsWriterPerThread.java:392-398; the runs show the rejection with the writer still open). Left behind: identity = the analyzer's stream B, termAttribute = B's, but termFreqAttribute, posIncrAttribute, offsetAttribute and payloadAttribute = the first document's stream A, whose end() left increment 2 and offsets 9-9 (analysis/FilteringTokenFilter.java:72-74, analysis/standard/StandardTokenizer.java:178-184). A probe that reads this state by reflection on main prints exactly that.
  4. Later documents read the old values. The next document gets the same stream B; :97 sees the cached identity and returns early. Every token reads A's frozen values: IndexingChain.java:1996 (increment 2) and :2035-2036 (offsets 9-9). From position = -1 (FieldInvertState.java:84), a lands at 1 and b at 3.
  5. Until the next flush, or a different stream. There is one FieldInvertState per field per in-memory segment, that is per DocumentsWriterPerThread (IndexingChain.java:1416, :1905-1909). A different TokenStream object for the field fails the identity check at :97 and refreshes the handles (executed: a document with its own stream "c d" between the failure and the next "a b" gives PhraseQuery f:"a b" count 1). After a commit the next document is indexed correctly, but the document mis-indexed before it keeps positions 1 and 3 (executed).

Exposure and likelihood260 words
  • Who. An analyzer whose tokenizer was built with an application-written AttributeFactory that throws when IndexWriter requests TermFrequencyAttribute (before 7.0.0: PositionIncrementAttribute), once or always.
  • Reach limits (by reading). The factory is asked only for an attribute the stream does not have yet (AttributeSource.java:209-221). A factory built on the packed token factory, the default, is never asked here, because PackedTokenAttributeImpl already implements all three attributes (PackedTokenAttributeImpl.java:29-40); one that creates a separate implementation per attribute, as one built on AttributeFactory.DEFAULT_ATTRIBUTE_FACTORY does (the repro's), is asked for TermFrequencyAttribute. No non-test AttributeFactory in the Lucene source at 5adff78bb168 throws for these attributes (the default ones in AttributeFactory.java and the two collation factories). The silent variant also needs the field's cache to hold another stream's handles when the factory fails: in the repro, an earlier document in the same in-memory segment that passed its own TokenStream for that field (by reading, another thread's analyzer stream used earlier in the same pooled in-memory segment would do the same; not run).
  • Effect. Silent wrong positions (phrase, span and interval queries miss the documents) and wrong offsets (highlighting), or later documents of the field rejected with a misleading error. New documents are affected until the next flush or until the field inverts a different TokenStream object; the documents already indexed with wrong positions keep them after the flush (executed). The failing document itself is handled correctly.
  • Scale. Three small documents, one thread. Likelihood contrived: no matching public report was found in the documented searches, although every release examined since 4.9.0 (2014) has it.

Why it looks unintended

#
  • IndexWriter's code says a document hit by a non-aborting exception is added "all or none" and an analysis failure "won't cause the DWPT to be stale".
  • LUCENE-1072's test throws from a TokenStream, then: "Make sure we can add another normal document".
  • A 2014 refactor moved the cache's stream store from last to first; no review comment discusses that order.
The full argument203 words
  • Contract. DocumentsWriter.java:76-79: after a non-aborting exception "we immediately mark the document as deleted so that the document is always atomically ("all or none") added to the index." DocumentsWriterPerThread.java:392-398: an exception during analysis "causes the doc to be rejected but won't cause the DWPT to be stale". IndexingChain.java:1988-1994 says the same for an exception in the token loop ("in stream.next below"); this throw comes just before that loop, from setAttributeSource at :1984, and the runs show it is handled the same way. IndexWriter.java:1465: "if an Exception is hit ... the index will be consistent".
  • Tests. TestIndexWriterExceptions.testExceptionFromTokenStream (LUCENE-1072, :493-494) throws from a TokenStream, then: "Make sure we can add another normal document" (:541).
  • History. The cache came with LUCENE-5611 (#6673). Its first, inline form in DefaultIndexingChain.invert stored the identity as its last statement (67ebc26fa97, kept by f0414ff3af7). After the review request "Can we factor this into FieldInvertState?" (Robert Muir on #6673), e7b59c5a211 moved the block into the setter with the identity first; no comment in the thread discusses the setter's order or a throw from its lookups (its commit notices about non-aborting exceptions concern other code). The parent commit does not reproduce; e7b59c5a211 does (executed).
The devil's-advocate check187 words

The strongest case for "not a bug": a throwing AttributeFactory is a broken component. The factory javadoc names only UndeclaredThrowableException and says "attributes should not throw or declare checked exceptions" (AttributeFactory.java:28-35), and #9656 (LUCENE-8610), an NPE from the same cache, was closed Not A Bug as the tokenizer's fault.

Why it fails: that javadoc sentence is about attribute constructors, and createAttributeInstance is a public extension point that IndexWriter itself calls. In #9656 the stream broke the TokenStream contract by adding attributes lazily; here every stream follows the contract, and the failure is reported to the caller, who then continues as LUCENE-1072's test does. IndexWriter documents that such a failure drops one document, not that it changes how later ones are indexed. No javadoc explicitly promises isolation after a throwing AttributeFactory, so the case is that the behaviour is inconsistent with the non-aborting design above, not that it breaks an explicit contract. That bears on likelihood, which is why the priority is Low, not on intent. A credibility audit anticipated the "broken component" objection and still kept the finding, with its small fix and single test.

Suggested fix

#

Recommended Clear the cache first, publish the stream last (fix A)

In FieldInvertState.setAttributeSource, clear the cached stream and handles first and store the stream only after every addAttribute call has succeeded (+9/-8 lines). The repro passes with assertions on and off, and 78 tests of the closest suites pass; the same-stream fast path is unchanged.

      // clear the identity first, so that a failing addAttribute below leaves no stale handles
      this.attributeSource = null;
      termAttribute = null;
      termFreqAttribute = null;
      posIncrAttribute = null;
      offsetAttribute = null;
      payloadAttribute = null;
      if (attributeSource != null) {
        termAttribute = attributeSource.getAttribute(TermToBytesRefAttribute.class);
        termFreqAttribute = attributeSource.addAttribute(TermFrequencyAttribute.class);
        posIncrAttribute = attributeSource.addAttribute(PositionIncrementAttribute.class);
        offsetAttribute = attributeSource.addAttribute(OffsetAttribute.class);
        payloadAttribute = attributeSource.getAttribute(PayloadAttribute.class);

Downstream note

#

Downstream, a search product that loads outside analysis plugins could index a field's later documents with wrong positions and offsets after one plugin's attribute factory fails; those documents stay wrong in the index, and new ones are indexed correctly again after the next flush. The factory is passed only the attribute class, never the document text.

How it was found

#

A proof-obligation audit of FieldInvertState.setAttributeSource's failure atomicity: a failed call must not leave a cache that a later call with the same stream relies on. The stream is stored before the lookups that can throw; a public-API JUnit test then witnessed the wrong positions.

The method in full118 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked setAttributeSource against the obligation that a call which throws leaves no cache a later call with the same source relies on. The identity is assigned at :98, before the addAttribute calls at :107-109, which reach the user's AttributeFactory.
  • The finder then wrote the public-API JUnit test (positions 1 and 3 instead of 0 and 1), two probes (the positions, and the NullPointerException variant with no earlier stream) and the fix that makes the test pass.
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

LFV-1154, snapshot of 2026-11-03

Registry title
When an AttributeFactory throws while IndexWriter adds TermFrequencyAttribute, FieldInvertState keeps the previous stream's attribute handles, so later accepted documents of that field are indexed with the wrong positions and offsets until the next flush
Area
index / IndexingChain inversion (FieldInvertState.setAttributeSource attribute cache)
Priority
Low, rank 648: After an application-written AttributeFactory throws while IndexWriter adds its attributes, later documents of that field in the same in-memory segment can be indexed silently with wrong positions and offsets, in every release since 4.9.0. No stock factory throws there, and the silent case also needs an earlier stream that ended with skipped positions, so the trigger is contrived.
Impact class
minor
Impact note
Hits only applications whose analyzer's tokenizer uses their own AttributeFactory built on the one-implementation-per-attribute default (AttributeFactory.DEFAULT_ATTRIBUTE_FACTORY, not the packed token factory) that throws when IndexWriter requests TermFrequencyAttribute, once or always; otherwise default IndexWriterConfig, codec and ordinary scale: the failing document is rejected as it should be, but later documents of the same field in the same in-memory segment are then accepted with the previous TokenStream's final position increment and offsets (silent: phrase, span and interval queries miss them) when an earlier document supplied its own TokenStream for that field ending with an increment of 2 or more (for example trailing stop words), or are all rejected with the misleading 'first position increment must be > 0' (earlier stream ending with increment 0) or a NullPointerException (no earlier stream), until the next flush; every release from 4.9.0 to 10.6.0 and main.
Summary
You add a document whose field value is your own TokenStream ending in two removed stop words ('x the the' through StopFilter), then a document whose analysis fails because your analyzer's AttributeFactory throws when IndexWriter asks for TermFrequencyAttribute, then the plain-text document 'a b' through the same analyzer with the factory working again. You expect the failed document to be dropped and 'a b' to be indexed at positions 0 and 1, as it is without the failure. Instead 'a b' is accepted at positions 1 and 3 and PhraseQuery f:"a b" finds nothing, with no error, because FieldInvertState.setAttributeSource recorded the analyzer's reused stream as cached before it fetched that stream's attributes, so every later document of the field keeps reading the first stream's position increment (frozen at 2) until the next flush.
