Merges with BpVectorReorderer throw NullPointerException and close the IndexWriter when a segment has no vectors for the field

With BPReorderingMergePolicy and a BpVectorReorderer (main only), merging 100 documents with vectors and 10 without the vector field throws NullPointerException; the IndexWriter closes, loses uncommitted changes and fails again after every reopen. The missing null check, in copy() of the merged vector view, has shipped since 10.2.0.

The bug in 30 seconds

#

During a merge, Lucene reads all the merged segments through one combined view. A segment in which no document has the vector field is an empty slot in that view, and the iterator and ordinal lookup of the merged vector values handle that slot, but copy() does not.

  1. Use BPReorderingMergePolicy(new LogDocMergePolicy(), new BpVectorReorderer("vector")) with the default codec. Index 100 documents with a 2-dimensional float vector and commit, then 10 documents without the vector field and commit: 2 segments, the second with no vectors.
  2. Call forceMerge(1). You expect 1 segment with 110 documents and 100 vectors, each with its document, as when both segments have vectors (that control passes).
  3. Instead the merge throws NullPointerException: Cannot invoke "org.apache.lucene.index.KnnVectorValues.copy()" because "this.sub" is null: BpVectorReorderer calls copy() on the merged view in each thread that takes part in partitioning, and copy() does not skip the empty slot of the segment without vectors.
  4. IndexWriter treats the failed merge as a tragic event and closes: 5 uncommitted documents and 1 uncommitted delete are lost (114 documents visible before, 110 on disk after). A reopened writer fails again at the next merge of that segment (3 of 3 cycles); the committed index stays clean.
  5. With the default reorderer settings it takes 64 vectors in the merge (63 merge fine) and a segment without the field in that merge. addIndexes(CodecReader...) fails the same way but keeps the writer open.

Who is affected

#

Applications on main that opt into BPReorderingMergePolicy with BpVectorReorderer and index documents without the vector field. With default reorderer settings, a merge that includes such a segment and holds 64 or more vectors fails and closes the writer, again after each reopen; the last commit stays clean. On 10.2.0-10.5.2 only custom reorder code copying the merged view hits it.

Mechanism, terms and numbers890 words

During a merge, IndexWriter reads the segments being merged through one combined view (SlowCompositeCodecReaderWrapper) and hands it to OneMerge#reorder. For a vector field the view keeps one slot per segment, and a segment in which no document has the field gets an empty (null) slot. The iterator of the merged vector values skips empty slots and vectorValue()'s ordinal lookup handles them, but copy() calls sub.copy() on each slot and throws NullPointerException: Cannot invoke "org.apache.lucene.index.KnnVectorValues.copy()" because "this.sub" is null. BpVectorReorderer calls copy() in each thread that takes part in partitioning, which with the default settings starts once the merge holds at least 64 vectors, so with BPReorderingMergePolicy and a BpVectorReorderer a merge of 100 documents with vectors and 10 without fails. IndexWriter treats the failed merge as a tragic event: the writer closes, the changes since the last commit are lost, and a reopened writer fails again at the next merge of that segment. The committed index stays clean. The end-to-end failure is on main only (11.0.0-SNAPSHOT); the copy() defect itself came with #14092 and has shipped since 10.2.0, where only custom reorder code that copies the merged view reaches it.

Terms

#
  • Merged view: during a merge, IndexWriter wraps the segments being merged in one CodecReader, SlowCompositeCodecReaderWrapper, and passes it to MergePolicy.OneMerge#reorder, which may return a new document order. With one segment there is no view (wrap() returns the segment, :49-57).
  • Slot: the merged vector values keep one DocValuesSub per segment. A segment without vectors for the field gets a slot whose values are null.
  • BP reordering: BPReorderingMergePolicy (lucene/misc) renumbers the documents of each merged segment. With a BpVectorReorderer (#14097, main only) it sorts documents so that similar vectors sit together, by splitting the vectors in halves recursively on several threads.

The bug

#
  1. getFloatVectorValues of the merged view (SlowCompositeCodecReaderWrapper.java:824-841) asks every segment for its values (:830), which is null for a segment that indexed no vectors (CodecReader.java:235-237; LeafReader.java:215-221), and adds a slot also for null (:831). Byte (:924-941) and float16 (:944-961) are the same.
  2. The iterator skips empty slots (:339, :357), and the ordinal lookup handles them (findSub, :1082 onwards). But DocValuesSub.copy() (:304-309) is return new DocValuesSub<>((T) (sub.copy()), docStart, ordStart); (:307) with no null check, and the three Merged*VectorValues.copy() methods call it for every slot (:903-909, :1003-1009, :1073-1079). (Separate from this bug: the merged values also inherit the dense default ordToDoc(), which returns its argument (KnnVectorValues.java:43-50), and iterator() returns one shared iterator (:887-889); the differential test flagged both, neither is a registered bug, and neither is needed to explain this failure.)
  3. BpVectorReorderer.computeDocMap reads the merged FloatVectorValues (BpVectorReorderer.java:590) and, after a RAM-budget check that the default budget passes (:598-606), each thread that takes part builds one PerThreadState, whose constructor calls vectors.copy() (:110, :620-624). The first one is built in ReorderTask.compute (:217) right after if (halfLength < minPartitionSize) return; (:208-211): with the default minPartitionSize of 32 that needs 64 vectors.
  4. BPReorderingMergePolicy's reorder catches only NotEnoughRAMException (BPReorderingMergePolicy.java:133-145); forced merges are always reordered (:103-105), natural merges from minNaturalMergeNumDocs documents, default 1 (:46).
  5. IndexWriter.mergeMiddle builds the view and calls reorder (IndexWriter.java:5557-5558). The exception reaches merge()'s outer catch (Throwable t) and tragicEvent(t, "merge") (:5109-5113), which calls maybeCloseOnTragicEvent() and so rollbackInternal() (:6090-6106): the writer rolls back to the last commit and closes. addIndexes(CodecReader...) builds the same view (:3561-3562) but calls tragicEvent only for Error (:3390-3392).

Exposure and likelihood309 words
  • Who is hit. Applications on main that opt into the expert lucene/misc combination BPReorderingMergePolicy + BpVectorReorderer (CHANGES 11.0.0, #14097: "Binary partitioning merge policy over float-valued vector field") and whose vector field is optional: documents without embeddings, several document kinds in one index, or a batch without vectors flushed on its own. Applications that put a vector in every document, as the upstream TestBPReorderingMergePolicy does, never hit it.
  • Trigger. A forced or natural merge that includes a segment with no vector for the field and holds at least 64 vectors, and addIndexes(CodecReader...) of such inputs, under the reproduced conditions: default reorderer settings (minPartitionSize 32) and RAM budget (a budget too small for the merge throws NotEnoughRAMException before copy() and the policy skips reordering), no index sort, no document blocks without a parent field. Default codec and IndexWriterConfig; no special values or timing. With the javadoc's suggested minNaturalMergeNumDocs of 2^18, small natural merges are not reordered, but larger ones and every forced merge still are.
  • Effect. Indexing stops: the writer closes, the changes since the last commit are lost (114 documents visible before, 110 on disk after, an uncommitted delete undone), and each reopened writer fails again at the next merge that picks the same segment while the segment count grows. Under those conditions forceMerge(1) over such segments fails every time. The last committed index stays clean (CheckIndex) and searchable; what a near-real-time reader already saw of the uncommitted changes disappears. addIndexes(CodecReader...) throws but keeps the writer open.
  • Scale. None: 64 vectors and one 10-document segment without the field.
  • Released versions. The copy() defect has shipped since 10.2.0, but there no in-tree code calls copy() on the merged view; an application's own OneMerge#reorder that does fails on 10.2.0 and 10.5.2 and passes on 10.1.0.
  • Encodings. float32, byte and float16 merged values all throw; only float32 has an in-tree caller.

Why it is a bug, not intended

#
  • KnnVectorValues#copy has no precondition, and a segment without vectors is a documented state (getFloatVectorValues returns null); the merged view's iterator and ordinal lookup handle that null, but copy() does not.
  • #14092 added the per-slot copy() for this very caller; BpVectorReorderer and its tests support documents without vectors.
  • The same class's null-slot crash for points was fixed as a bug (#12859).
The full argument284 words
  • KnnVectorValues#copy (KnnVectorValues.java:95-99): "Creates a new copy of this {@link KnnVectorValues}. This is helpful when you need to access different values at once, to avoid overwriting the underlying vector returned." No precondition.
  • LeafReader#getFloatVectorValues (LeafReader.java:215-221): "... or null if no {@link FloatVectorValues} were indexed. The returned instance should only be used by a single thread." So a reorderer that reads the vectors from several threads at once needs one copy per thread (or must serialize access), and a segment without vectors is an expected state.
  • OneMerge#reorder (MergePolicy.java:311-325) "will be called when index sorting is disabled on a merged view of the {@link OneMerge}": this view.
  • BPReorderingMergePolicy (:34-39): "When reordering doesn't have enough RAM, it simply skips reordering in order not to fail the merge."
  • Sparse vectors are supported. The merged view stores null slots on purpose (since #12622, 2023) and handles them in its iterator and ordinal lookup. BpVectorReorderer sorts "docs with no value at the end" (BpVectorReorderer.java:743), its checkField returns null for an absent field instead of throwing (:699-713), and TestBpVectorReorderer.testIndexReorderSparse checks that documents without vectors "sort at the end" (:387-428), on a single segment, so without a merged view.
  • History. #14092 (@msokolov, 2024-12-31) added the per-slot copy(); its PR body says the earlier shallow copy "was a bug introduced with #13779 ... I came across test failures when working on reviving a vector-based binary-partitioning merge policy". No review comments; segments without the field are not discussed.
  • Precedents. #12858 / #12859 (2023): "Avoid null PointValues when merging points in SlowCompositeCodecReaderWrapper". #14123 / #14125 (2025): "Add null checks to SortingCodecReader" for a segment without vectors in a reordering or addIndexes merge.
The devil's-advocate check170 words

The strongest case for "intended": the wrapper is package-private and "primarily targeted at merging, not searching" (SlowCompositeCodecReaderWrapper.java:43-47); KnnVectorValues, getFloatVectorValues and OneMerge#reorder are @lucene.experimental; KnnVectorsReader says "The behavior is undefined if the given field doesn't have KNN vectors enabled on its FieldInfo" (KnnVectorsReader.java:64-69); the vector values of SortingCodecReader throw UnsupportedOperationException from copy() (SortingFloatVectorValues.copy(), SortingCodecReader.java:345-348); the policy's javadoc names only BPIndexReorderer; and BpVectorReorderer is new and untested with such segments.

Why it fails: "experimental" allows API changes, not an NPE on legal data built with public API and default settings. The wrapper never asks a segment's KnnVectorsReader about an absent field; it calls CodecReader's guarded getter, which returns null by contract, and stores that null itself. An UnsupportedOperationException is a deliberate signal; this NPE is an accident in the method #14092 wrote for this caller. #14097 made BpVectorReorderer pluggable into BPReorderingMergePolicy, and TestBPReorderingMergePolicy plugs it in. The missing test is a coverage gap. Every reviewer rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Return the empty slot unchanged in DocValuesSub.copy()

Guard the empty slot in DocValuesSub.copy(): if (sub == null) return this; (+4 lines in SlowCompositeCodecReaderWrapper.java). Validated with gradle: both repro classes pass with assertions on and off, and TestAddIndexes, TestSortingCodecReader, TestGetVectorCountCodecWrappers, the whole misc module and the nightly TestBPReorderingMergePolicy pass.

private record DocValuesSub<T extends KnnVectorValues>(T sub, int docStart, int ordStart) {
  @SuppressWarnings("unchecked")
  DocValuesSub<T> copy() throws IOException {
    if (sub == null) {
      // this reader has no vectors for the field: nothing to copy
      return this;
    }
    return new DocValuesSub<>((T) (sub.copy()), docStart, ordStart);
  }
}
All options and trade-offs5 options · 578 words

One fix was built and validated in a scratch worktree; the other options are untested or not recommended. The null guard does not fix two related, separate hunt findings in the same code: LFV-278 (the merged iterator numbers ordinals by position, so a reordered addIndexes of two or more SortingCodecReader inputs writes vectors onto the wrong documents) and LFV-404 (BpVectorReorderer fails with UnsupportedOperationException on SortingCodecReader inputs, whose vector values' copy() throws on purpose, SortingCodecReader.java:345-348).

Return the empty slot unchanged in DocValuesSub.copy() (validated by the checks) (recommended)

#

SlowCompositeCodecReaderWrapper.java only, +4 lines. The record is immutable and an empty slot has no state, so returning it is safe; slots with vectors are copied as before, so #14092's thread-safety fix stays. One place fixes float32, byte and float16 and every consumer of the merged view's copy(): BpVectorReorderer and custom OneMerge#reorder code, whether a merge or addIndexes(CodecReader...) reaches them.

private record DocValuesSub<T extends KnnVectorValues>(T sub, int docStart, int ordStart) {
  @SuppressWarnings("unchecked")
  DocValuesSub<T> copy() throws IOException {
    if (sub == null) {
      // this reader has no vectors for the field: nothing to copy
      return this;
    }
    return new DocValuesSub<>((T) (sub.copy()), docStart, ordStart);
  }
}

Trade-offs

  • No behaviour change for segments with vectors; no extra allocation.
  • The same change applies to the 10.x branches, whose DocValuesSub.copy reads the same (10.x has no float16 values). Add a CHANGES entry under Bug Fixes.
  • A regression test should cover a merge, not only copy(): the end-to-end test checks the vector content and the document mapping after the reordered merge.

Do not store empty slots

#

Skip segments whose values are null when the merged values are built.

Trade-offs

Removes the null state. The remaining slots keep their own docStart and ordStart, so the iterator and findSub look compatible, but that needs validation. The slot list would be empty only if no segment has the field, which the field-info check in CodecReader's getter normally prevents; a direct call on the vectors reader would then make MergedDocIterator's constructor call it.next() on an empty list (:322), so it needs a guard. Touches three getters for the same effect as the null guard. Untested.

Revert #14092 (not recommended)

Go back to the shallow copy of the slot list.

Trade-offs

Work around it in BpVectorReorderer (not recommended)

Trade-offs

Downstream note

#

Downstream: a public code search found no product that wires BpVectorReorderer into a merge policy; an application that adopts it on main loses indexing whenever documents without the vector field end up in a segment of their own.

How it was found

#

A randomized differential test built merged views over random multi-segment inputs, with fields missing from some segments, and compared a broad set of merged-view APIs with the source segments; in 60 iterations it reported, among other mismatches, 102 NullPointerExceptions from copy() of the merged vector values. The failing frame led to BpVectorReorderer, then to an end-to-end repro.

The method in full173 words

Method: randomized differential testing of the merged view against its source segments (no model checker, solver or prover found it).

  • The test builds random multi-segment inputs (a target of 2-5 segments, which it can overshoot) in which some fields are missing from some segments, wraps them in the merged view and compares a broad set of merged-view APIs, the vector values' copy() included, with the source segments. Over 60 random iterations without empty segments it reported 592 mismatches of 5 kinds, among them 102 of the kind "vector-copy-exception: NullPointerException"; the others (getOffHeapByteSize exceptions, the inherited ordToDoc() and the shared iterator()) are not this bug.
  • The failing frame (DocValuesSub.copy) led to the one in-tree caller that copies the merged view, BpVectorReorderer, and an end-to-end JUnit through BPReorderingMergePolicy reproduced it on the stock jars.
  • A Z3 model of the same unit proved the merged view's ordinal lookup (findSub) correct with empty slots; it gave no signal for copy(), so this is not counted as a formal find.

Bug record

LFV-269, snapshot of 2026-10-29

Registry title
The merged vector values of SlowCompositeCodecReaderWrapper throw NullPointerException from copy() when one merged segment has no vectors for the field, so merges through BPReorderingMergePolicy with BpVectorReorderer fail and close the IndexWriter, again after every reopen
Area
index / merged CodecReader view (SlowCompositeCodecReaderWrapper vector values); misc / BP merge-time reordering
Priority
Medium, rank 319: Like LFV-100, this is a merged-view NPE when one segment lacks the vector field, but every BP-vector-reordered merge closes the writer again after each reopen, and the stock path is unreleased.
Impact class
index unusable
Impact note
Applications on unreleased main (11.0.0-SNAPSHOT) that opt into the expert lucene/misc BPReorderingMergePolicy with a BpVectorReorderer and have a segment in which no document carries the (optional) vector field are hit on every forced or natural merge that includes that segment and holds at least 64 vectors (2 x the default minPartitionSize of 32, read from code): the merge throws, IndexWriter closes itself as a tragic event and discards all uncommitted changes, and a reopened writer closes again at the next such merge, while the committed index stays clean and searchable; addIndexes(CodecReader...) under the same policy throws but leaves the writer open; any index size, default codec and IndexWriterConfig otherwise; on released 10.2.0-10.5.2 the same NullPointerException is reachable only through an application's own OneMerge#reorder or IndexReorderer that calls copy() on the merged view.
Summary
You use BPReorderingMergePolicy with a BpVectorReorderer on a float vector field, and one segment holds only documents without that optional field, for example a batch of documents without embeddings that was flushed on its own. You expect merges to combine it with the other segments, as they do when every segment has vectors. Instead the merged view's FloatVectorValues.copy() throws NullPointerException ('Cannot invoke KnnVectorValues.copy() because this.sub is null'), IndexWriter treats the failed merge as a tragic event, closes itself and drops every change since the last commit, and the same merge fails again after each reopen.
