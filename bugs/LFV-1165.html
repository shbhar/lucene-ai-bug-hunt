FloatArrayList.equals treats 0.0f and -0.0f as equal, but hashCode gives them different hash codes

FloatArrayList.from(0.0f).equals(FloatArrayList.from(-0.0f)) is true, yet the two hash codes are 31 and 1832674751, so a HashSet holding one list never finds the other. No Lucene code compares or hashes these internal lists, so nothing in Lucene is affected today.

The finding in 30 seconds

#

Two facts you need first

#
  1. HashSet and HashMap find an entry by its hash code first and only then call equals. That is why Java requires equal objects to have equal hash codes (Object#hashCode javadoc).
  2. A float has two zeros. 0.0f == -0.0f is true, but their bit patterns differ: 0x00000000 and 0x80000000. Float.equals and Arrays.equals(float[], float[]) compare bits, so for them the two zeros differ.

The finding, step by step

#
  1. Build two one-element lists: a = FloatArrayList.from(0.0f) and b = FloatArrayList.from(-0.0f).
  2. a.equals(b) returns true, both ways. Java's Object#hashCode contract then requires a.hashCode() == b.hashCode().
  3. Instead the hash codes are 31 and 1832674751. equals compares elements with ==, where 0.0f == -0.0f; hashCode hashes the raw bits, 0x00000000 and 0x80000000.
  4. So a HashSet holding a says contains(b) is false, a HashMap keyed by a returns null for b, and one HashSet can hold both "equal" lists. Same with assertions on and off.

Who is affected

#

Only code that itself uses Lucene's internal FloatArrayList as a hash key, or relies on its equals and hashCode agreeing, with lists that differ only in a zero's sign. No Lucene code path reaches either method. It would become reachable if LFV-403 were fixed by comparing and hashing PointInSetIncludingScoreQuery's score list with FloatArrayList.equals/hashCode.

Mechanism, terms and numbers310 words

org.apache.lucene.internal.hppc.FloatArrayList is Lucene's internal growable float list. Its equals compares elements with primitive == (FloatArrayList.java:373 at 5adff78bb168), under which 0.0f == -0.0f, but its hashCode mixes Float.floatToIntBits of each element (:350, BitMixer.java:50-52), which differs for the two zeros. So FloatArrayList.from(0.0f) and FloatArrayList.from(-0.0f) are equal with hash codes 31 and 1832674751, which breaks the Object#hashCode contract: a HashSet or HashMap keyed by such lists misses lookups and keeps both. The class says it was forked from HPPC 0.10.0, which compares float elements by their bits. It is in every release from 9.11.0 to 10.6.0 and on main. No Lucene code path reaches FloatArrayList.equals or hashCode and the class is @lucene.internal, so the effect is latent; the fix is one line.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/internal/hppc/)

#
  1. equals (FloatArrayList.java:355-363): "Returns true only if the other object is an instance of the same class and with the same elements", then equalElements.
  2. equalElements (:366-379) tests each pair with if (!((get(i)) == (other.get(i)))) (:373, the fix site): primitive ==, so 0.0f equals -0.0f.
  3. hashCode (:346-353): h = 1, then h = 31 * h + BitMixer.mix(this.buffer[i]) per element (:350).
  4. BitMixer.mix(float) is mix32(Float.floatToIntBits(key)) (BitMixer.java:50-52): 0 for 0.0f, 1832674720 for -0.0f. So the hash codes are 31 and 1832674751.
  5. Effect. HashMap compares the stored hash before it calls equals, so the lookup misses every time. The finder's probe (main(), assertions off): equals true both ways, HashSet.contains false, HashMap.get null, a set holding both has size 2; a separate re-run's own probe gives the same with assertions on and off.

The same == also makes a list holding NaN unequal to its own copy (probe: nanCopyEquals=false). That alone breaks no contract; the bit-equality fix changes it too.

Exposure and likelihood268 words
  • Who. Code that keys a HashSet, HashMap or another hash container by org.apache.lucene.internal.hppc.FloatArrayList, or relies on equals and hashCode agreeing, and holds lists that differ only in the sign of a zero. -0.0f is an ordinary value (for example -1f * 0f).
  • Not Lucene itself. On main the non-test users are MaxScoreCache and MultiNormsLeafSimScorer (only EMPTY_ARRAY), Lucene104ScalarQuantizedVectorsWriter (a buffer) and PointInSetIncludingScoreQuery (a score buffer, left out of its own equals/hashCode, PointInSetIncludingScoreQuery.java:328-350).   • Reach of the class. Why it looks unintended

#
  • Object#hashCode requires equal objects to have equal hash codes; FloatArrayList overrides both, and its own test checks this.
  • The class says it is forked from HPPC 0.10.0, which compares float elements by bits, as do this fork's float-valued maps.
  • The == came from IntArrayList text, where it is right for ints; upstream fixed the same pattern in geo classes (#13301).
The full argument193 words
  • Contract. Object#hashCode: "If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result."
  • Origin. Class javadoc: "Mostly forked and trimmed from com.carrotsearch.hppc.FloatArrayList", "release 0.10.0" (FloatArrayList.java:28-37). HPPC 0.10.0's KTypeArrayList.equalElements calls Intrinsics.equals, whose FLOAT case emits Float.floatToIntBits(a) == Float.floatToIntBits(b). HPPC 0.9.1, the library Lucene used before 9.11.0, keeps the two consistent (executed: equals false for the two zeros).
  • Same fork, bits elsewhere. IntFloatHashMap.java:421 and LongFloatHashMap.java:433 compare float values with Float.floatToIntBits, IntDoubleHashMap.java:434 with Double.doubleToLongBits.
  • Tests. TestFloatArrayList.testHashCodeEquals (TestFloatArrayList.java:304-315) asserts that equal lists have equal hash codes, with ordinary values only; no test uses a signed zero or NaN.
  • History. git blame gives the equalElements text to 444d4e7c42b (#13406, IntArrayList); #13422 made the float list from it. Its review does not discuss float equality, signed zeros or NaN.
  • Precedent. #13301 (2024-04-15) fixed equals-with-== against a bit hash, 0.0 vs -0.0, in five geo classes. #13761 (fixed by #13876 and #13884 in 10.1.0; CHANGES lists #13884 under Bug Fixes) treated another latent difference of this fork from HPPC as a bug.
The devil's-advocate check150 words

The strongest case for "not a bug" (the cross-model reviewer's position; it agreed on the behaviour, the cause and the fix): the class is @lucene.internal, its package export is temporary, CHANGES asks applications not to use it, and nothing in Lucene calls these methods.

Why it fails: @lucene.internal renders as "This API is for internal purposes only and might change in incompatible ways in the next release" (RenderJavadocPlugin.java:506): it warns of API change, not that a public equals/hashCode override may break the Object contract; the class's own upstream test asserts the contract; upstream fixed the equally latent #13761 as a bug. The argument does bear on reach, hence priority Low. Nor does "IEEE == is the right float equality" save the code: then hashCode would have to treat the two zeros alike, and it does not. One of the two lines is wrong either way.

Suggested fix

#

Recommended Compare bits in equalElements (fix A, validated)

Compare bits in equalElements, as HPPC does: if (Float.floatToIntBits(get(i)) != Float.floatToIntBits(other.get(i))) (one line, FloatArrayList.java:373). The repro passes with assertions on and off, and all 430 tests of the 16 hppc suites (the 15 existing ones plus the repro; one run, assertions on) pass, including the 34 of TestFloatArrayList.

Trade-offs

  • [0.0f] and [-0.0f] become unequal, matching their hash codes. A list holding NaN becomes equal to its own copy or clone (today it is not). Float.floatToIntBits maps every NaN to one bit pattern, so any two NaN elements compare equal, as in Float.equals: a deliberate change of meaning, not only a contract repair.
  • Code that relied on [0.0f] being equal to [-0.0f] would see false; no Lucene code compares these lists.

How it was found

#

A proof-obligation audit of FloatArrayList's equals/hashCode pair against the Object#hashCode contract: every pair of lists that equals accepts must hash alike. Float == accepts 0.0f against -0.0f, the bit hash does not; a one-test public-API JUnit then witnessed it.

The method in full128 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder wrote down the obligation that Object#hashCode puts on FloatArrayList, which overrides both methods: a.equals(b) implies a.hashCode() == b.hashCode(). It then compared the relation each side uses: equalElements uses == on float, hashCode uses Float.floatToIntBits. The two differ exactly on 0.0f vs -0.0f (and NaN, where == is stricter, which is harmless for the contract).
  • A one-test public-API JUnit then failed on main with assertions on and off and on the 10.6.0 and 9.11.0 jars; a main() probe showed the HashSet/HashMap effect.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").
