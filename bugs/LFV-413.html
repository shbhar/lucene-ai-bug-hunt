SweetSpotSimilarity's length plateau makes top-k search skip the best hits

With SweetSpotSimilarity.setLengthNormFactors(10, 20, 0.5f), a field shorter than 10 terms has a smaller norm but a lower score, which breaks the rule Lucene's top-k pruning relies on. search(q, 10) then skips the block that holds the best hit (1.414) and returns 1.0 hits instead; every release since 8.0.0.

The bug in 30 seconds

#

SweetSpotSimilarity lets you mark a range of field lengths as ideal; shorter and longer fields score lower. Lucene's top-k search assumes that, at the same term frequency, a shorter field (a smaller norm) never scores lower. Below the plateau that is false.

  1. Score field f with SweetSpotSimilarity and setLengthNormFactors(10, 20, 0.5f): 10 to 20 terms is ideal (length factor 1.0), a 2-term field gets 1/3. Index 3,000 docs: docs 0-1999 "t" + 9 words (score 1.0), docs 2000-2999 "t t" (0.471), except doc 2150, "t t" + 8 words (1.414, the best hit).
  2. Run searcher.search(new TermQuery(new Term("f", "t")), 10). You expect doc 2150 first, as a search that counts every hit returns.
  3. You get docs 0-9 (1.0 each); doc 2150 is missing. Lucene stores the field length as the norm and assumes a greater norm never scores higher. Below the plateau it does: norm 2 scores 0.333, norm 10 scores 1.0.
  4. Trusting that rule, the block of 256 postings that holds doc 2150 keeps only the pair (freq 2, norm 2) and claims a maximum of 0.471. From hit 1,001 on only scores above 1.0 can compete, so the search skips the block.
  5. No error, with assertions on or off, and the returned scores are right. The default plateau (min = max = 1) is safe. Every release since 8.0.0 is affected.

Who is affected

#

Applications that score a field with SweetSpotSimilarity and a plateau minimum of 2 or more, and run the default IndexSearcher#search(q, n) on terms with more than 1,000 matches. Solr's factory is exposed only with minExactCount. The default plateau is safe. How often real corpora lose hits was not measured.

Mechanism, terms and numbers767 words

SweetSpotSimilarity (lucene/misc) lets an application declare a plateau of ideal field lengths with setLengthNormFactors(min, max, steepness): lengths from min to max get a length factor of 1.0, shorter and longer fields less. It keeps the inherited computeNorm, which stores the field length as the norm, so below the plateau a longer field has a greater norm and a higher score. Similarity#computeNorm forbids exactly that ("greater unsigned norms must produce scores that are lower or equal"), because the postings writer keeps, for each block of 256 postings, only the (freq, norm) pairs that can produce the best score under that rule. A short field then hides a better-scoring longer field of the same or lower term frequency: the block claims a too-low maximum, and the default IndexSearcher#search(q, n) skips it once it has counted more than 1,000 hits. In the repro search(q, 10) returns docs 0-9 (1.0) and misses doc 2150 (1.414); Lucene's CheckHits.checkTopScores fails. Scores of returned hits are correct and nothing throws. Every plateau with min >= 2 (and a positive steepness) is affected, the default min = max = 1 is not; every release from 8.0.0 (block impacts, LUCENE-4198) to 10.5.2 and main.

Terms

#
  • Norm: one byte per document and field, written at index time by Similarity#computeNorm; by default the field length (SmallFloat.intToByte4, equal to the length up to 40 terms; Similarity.java:151-161).
  • Plateau: lengthNorm(x) = 1/sqrt(steepness * (|x-min| + |x-max| - (max-min)) + 1), 1.0 for min <= x <= max and lower on both sides (SweetSpotSimilarity.java:97-120). The default min = max = 1, steepness 0.5, is 1/sqrt(x), like ClassicSimilarity.
  • Block impacts: for each block of 256 postings the writer stores the (freq, norm) pairs that can produce the block's best score; top-k search computes the block's maximum score from those pairs and skips the block when it cannot beat the current k-th score.

With setLengthNormFactors(10, 20, 0.5f) (freq 1, idf 1):

Below 10 terms the score rises with the norm; above 20 it falls, as the rule requires.

The mechanism

#
  1. Score. SweetSpotSimilarity overrides lengthNorm (SweetSpotSimilarity.java:110-120) and tf (:127-130, sqrt(freq) with the default tf factors, as in ClassicSimilarity), but not computeNorm, so the norm is the length (Similarity.java:151-161). TFIDFSimilarity#scorer (final) fills normTable[i] = lengthNorm(byte4ToInt(i)) for the norm bytes 1-255 (TFIDFSimilarity.java:426-448) and scores tf(freq) * idf * boost * normTable[norm] (:467-472): freq 1 scores 1.0 at norm 10 and 0.333 at norm 2.
  2. Rule. Similarity#computeNorm: "for a given term-document frequency, greater unsigned norms must produce scores that are lower or equal" (Similarity.java:140-145); SimScorer#score: "Score must not increase when the unsigned norm increases" (:211-213).
  3. Index. Lucene104PostingsWriter adds each posting's (freq, norm) to a CompetitiveImpactAccumulator (Lucene104PostingsWriter.java:280-296). getCompetitiveFreqNormPairs() walks the norms upward and keeps a pair only if its freq beats every freq at a smaller norm (CompetitiveImpactAccumulator.java:101-111). In block 2048-2303 norm 2 has freq 2 (short docs) and norm 10 has freq 2 (doc 2150): the norm-10 pair is dropped, the block's maximum becomes sqrt(2)/3 = 0.4714, and Scorer#getMaxScore(2150) returns 0.47140452 while doc 2150 scores 1.4142135 (executed). The level-1 skip data of every 32 blocks merges these pairs through the same accumulator (Lucene104PostingsWriter.java:482-490), so its bound can be too low the same way.
  4. Search. IndexSearcher#search(q, n) counts 1,000 hits exactly (IndexSearcher.java:100, :597-599), then sets the minimum competitive score to Math.nextUp(1.0) (TopScoreDocCollector.java:154-165), and ImpactsDISI#advanceTarget skips every block whose maximum score is below it (ImpactsDISI.java:67-98). The block of doc 2150 claims 0.471 and is skipped; the top 10 is docs 0-9.
  5. Reach. A document is hidden when a shorter, sub-plateau field in its block has an equal or greater term frequency and a lower score. Plateau fields qualify only with a term frequency below min (without overlapping tokens, freq <= length); fields above the plateau qualify too: for 10..20 a 21-term field with t once (0.707) was hidden by 2-term fields with t once (0.333) in an executed variant, and found with the fix. One short field in the same block is enough (the independent reproducer's layout: doc 2000 "t t" hides doc 2001). A bounded-exhaustive check of every plateau 1 <= min <= max <= 64 with the steepness values 0.1, 0.5, 1 and 2 found 8,064 of 8,320 settings breaking the rule: exactly those with min >= 2 (steepness 0 would flatten the curve).
Exposure and likelihood237 words
  • Who is exposed. Users of org.apache.lucene.misc.SweetSpotSimilarity who call setLengthNormFactors with min >= 2, the plateau the class exists for. Solr ships SweetSpotSimilarityFactory (javadoc example 3/5/0.5) but counts hits exactly unless a request sets minExactCount; Elasticsearch and OpenSearch do not ship the similarity (source reading only).
  • Default or opt-in. Opt-in similarity with a non-default plateau; everything else is default: IndexWriterConfig, codec, plain IndexSearcher, IndexSearcher#search(q, n).
  • Scale. More than 1,000 matches for the default API (3,000 documents in the repro), and the hidden document's block must be reached after the collector has raised its bar (in the one-segment repro: after the first 1,001 hits); callers with a lower total-hits threshold prune sooner. Only postings with stored impacts are skipped (a postings format without impacts serves SlowImpactsEnum, which never skips).
  • Queries. TermQuery top-k executed wrong on main and every release run from 8.0.0 to 10.5.2; 2-clause disjunctions also on main and several releases. Phrase, synonym and other impact-based queries were not run.
  • Symptom. Silent: wrong best hits, correct scores, a correctly labelled hit count, a clean index, no exception with assertions on or off. A hit is lost only when a shorter, lower-scoring field with an equal or higher term frequency shares its 256-posting block and the hidden document beats the current k-th score. In a synthetic probe one short document per 200 postings removed the whole true top 10; real-corpus effect not measured.

Why it is a bug, not intended

#
  • Similarity#computeNorm: greater norms "must produce scores that are lower or equal"; the rule was added in 8.0 for exactly this pruning.
  • IndexSearcher says scoreDocs "is always accurate"; Lucene's own CheckHits.checkTopScores fails on the repro index.
  • The user only calls the public setLengthNormFactors, which documents no limit; BaseSimilarityTestCase checks this rule, but SweetSpot's tests never run it.
The full argument264 words
  • Contracts. Similarity#computeNorm (Similarity.java:140-145): "greater unsigned norms must produce scores that are lower or equal ... for any legal freq", and "1 is the norm that produces the highest scores". SimScorer#score (:211-216): "Score must not increase when the unsigned norm increases". IndexSearcher (IndexSearcher.java:59-67): only the hit count may be a lower bound; "The TopDocs#scoreDocs array is always accurate however." Scorer#getMaxScore must bound the scores it covers; it returns 0.4714 for a document scoring 1.4142.
  • No documented limit. setLengthNormFactors (SweetSpotSimilarity.java:85-95) names no restriction; SweetSpotSimilarity's own javadoc has no @lucene.experimental tag (its base class Similarity is experimental as a whole, Similarity.java:89); no CHANGES or MIGRATE entry warns about plateaus and top-k search.
  • Tests. BaseSimilarityTestCase asserts score(freq, norm-1) >= score(freq, norm) for every norm ("scores non-decreasing as docs get shorter", BaseSimilarityTestCase.java:437-470), and TestClassicSimilarity extends it. TestSweetSpotSimilarity extends only LuceneTestCase and never checks lengths below the plateau or a top-k search. A BaseSimilarityTestCase subclass on random plateaus fails on stock ("score(1.0,1)=0.19876102 < score(1.0,2)=0.20500971") and passes with the fix.
  • History. LUCENE-8119 (#9167) wrote the rule for impacts: "scores must not increase when the unsigned norm increases. The latter is something I need for #5270"; LUCENE-4198 (#5270): "This patch adds the assumption than (unsigned) greater norms produce equal or lower scores". Neither touched lucene/misc. The project fixed or dropped other non-monotone formulas (LUCENE-8010's sweep of core similarities; LUCENE-8015 for DFR; LUCENE-7997, #9045, changed BM25 to guarantee monotonicity, and LUCENE-9071 later sped it up and kept that guarantee; DFR's BE, P and D models were left out for this reason).
The devil's-advocate check179 words

The strongest case for "intended" (built by the devil's advocate, the GPT-5.6 intended-lens reviewer and the adjudication): the plateau and its drop-off below min are the class's documented purpose since 2006 (LUCENE-577); Similarity is a low-level API whose class javadoc says "Lucene makes no assumption about what is in this norm" (Similarity.java:47-48); the Similarity class (:89), ClassicSimilarity#lengthNorm and Similarity#computeNorm are @lucene.experimental; and a user can count all hits instead. So a maintainer could call it "garbage in".

Why it fails: the plateau's scores are intended, wrong top hits are not, and IndexSearcher promises accurate scoreDocs. The user implements nothing; a shipped, non-sandbox class breaks a "must" that core relies on. The later, specific rule (8.0, written for impacts) governs the older general sentence, and experimental status allows API changes, not wrong results. Every verifier and the adjudication rejected the argument. What is fairly conceded: any code fix changes the stored norm and needs re-indexing, so documenting "use min = 1 or count all hits" is a legitimate maintainer choice for a misc class.

Suggested fix

#

Recommended Store a sub-plateau length as the equally distant length above the plateau (validated)

In SweetSpotSimilarity, store a field of min - d terms as max + d (the same length factor) and score every length up to min as on the plateau, so norm order matches score order (+39/-6, one file). The repro, the upstream nightly test and the misc module pass. Short fields need re-indexing; wide plateaus change some scores.

@Override
public long computeNorm(FieldInvertState state) {
  final int numTerms = ...; // as in Similarity#computeNorm
  if (numTerms > 0 && numTerms < ln_min) { // below the plateau: store max + (min - numTerms)
    final long mirrored = (long) ln_max + (ln_min - numTerms);
    return SmallFloat.intToByte4((int) Math.min(Integer.MAX_VALUE, mirrored));
  }
  return SmallFloat.intToByte4(numTerms);
}

Store a sub-plateau length as the equally distant length above the plateau (validated) (validated by the checks) (recommended)

#

computeNorm writes a field of min - d terms (d >= 1) as max + d, which the plateau formula scores the same (both give 1/sqrt(2 s d + 1)), and lengthNorm uses x = max(numTerms, min), so over all 255 norm bytes the factor is 1.0 up to max and falls after it. Lengths >= min and empty fields are encoded as today; new indexes score exactly as before whenever the mirrored length is at most 40 (for example 29 for the plateau 10..20; identical scores for every length 1 to 2,000 on the plateaus 10..20 and 3..5), while wider plateaus change some scores (Precision below). Patch: SweetSpotSimilarity.java +39/-6; the computeNorm body copies Similarity#computeNorm.

Trade-offs

  • Re-indexing. Sub-plateau fields get a new norm (the computeNorm javadoc warns that overriding it needs re-indexing). Until an index is rebuilt, its old sub-plateau fields score like plateau fields, while newly indexed ones keep their penalty; merging copies norms and does not recompute them, so mixed segments score inconsistently until the documents are re-indexed (read, not executed).
  • lengthNorm(int) changes for direct callers: below min it returns 1.0; the drop-off moves into computeNorm. The class javadoc needs a sentence.
  • CombinedFieldQuery requires an additive computeNorm encoded with SmallFloat#intToByte4 (CombinedFieldQuery.java:60-64; the default computeNorm satisfies it); the mirrored encoding is not additive. Today the combination is correct, because its bound score(+Infinity, 1) is +Infinity and no block is skipped; with the fix, a document with two 2-term fields is scored as one 56-term field (28 + 28) instead of 4 terms: 0.5345225 becomes 0.23249526 (executed).
  • Precision (wide plateaus). A mirrored length above 40 keeps 4 significant bits and is rounded down, possibly into the plateau. For the plateau 50..100, 43 of the lengths 1 to 110 score higher than today, none lower; a 47-term field with t once goes from 0.4472136 to the plateau score 1.0 (executed). The norm order stays correct. Not tried: rounding the mirrored length up instead.
  • Not covered by the new tests: IndexOptions.DOCS fields and overlapping tokens (the override copies those branches from Similarity#computeNorm).
  • Backports. The design needs 9.12.0 or later (overridable Similarity#computeNorm; tested on main only). Through 9.11.1 TFIDFSimilarity#computeNorm is final and setLengthNormFactors takes a fourth argument, so 8.x and early 9.x need another design.
  • The long arithmetic also removes a NaN length factor for fields of more than about 1.07 billion terms (an int overflow noticed during the hunt, a separate edge). The BaseSimilarityTestCase subclass needs it because it probes norm byte 255; drop both for the smallest change.

Downstream note

Why: whoever can get documents indexed into such a field can hide other documents from top-k results without touching queries. How it was found

#

Code reading of SweetSpotSimilarity against the Similarity norm rule, then a bounded-exhaustive check on the stock jar: 8,064 of 8,320 plateau settings break the rule, exactly those with min >= 2. A public-API test with search(q, 10) then showed the missed hit.

The method in full131 words

Method: semi-formal. A hunt unit (misc module, 2026-10-26). The finder, an AI tool, read SweetSpotSimilarity against the Similarity#computeNorm rule (the plan's secondary method, "SweetSpotSimilarity monotonicity"), then checked the rule bounded-exhaustively on the stock jar: every plateau 1 <= min <= max <= 64, 4 steepness values, every consecutive pair of norm bytes. 8,064 of 8,320 configurations violate it, exactly those with min >= 2; none with min = 1. It then wrote an end-to-end public-API JUnit with IndexSearcher#search(q, 10) and CheckHits.checkTopScores.

Then: an independent reproducer with its own layout, cross-model reviews (OpenAI GPT-5.6, reading only), a devil's advocate with a plain-IndexSearcher main(), an adjudication, a version sweep with a commit-level bisect, a prior-report search, a document-only security probe, and this doc's fix with gradle validation.

Introduced in 8.0.0 by LUCENE-4198 (f410df81136, 2018, block impacts); the default search(q, n) started pruning with LUCENE-8060. Every release run from 8.0.0 to 10.5.2, and main, is affected; 7.x is clean. Not fixed upstream.

Introduced by LUCENE-4198 "Give codecs the opportunity to index impacts" (f410df81136, jpountz, 2018-01-31; a JIRA patch, now #5270, no pull request): it added the impact accumulator that drops a (freq, greater norm) pair and TermScorer block skipping. Companion commits on the same 8.0 line: LUCENE-8119 (838c604b765, #9167) wrote the rule into Similarity; LUCENE-8060 (99dbe936818, #9108) made search(q, n) prune after 1,000 hits. Latent since 7.0.0: LUCENE-7730 (06a6034d9bc) made the norm the field length; the plateau formula dates from LUCENE-577 (2006).

Not executed: every 8.x release from 8.1.0 to 8.11.3; 9.4.1, 9.4.2, 9.5.0, 9.9.1, 9.9.2 and 9.11.0; 10.1.0 to 10.5.1 (all between affected releases, same code path); the unreleased 10.6 branch; x86. For 2-clause disjunctions, "right" in some releases only means their disjunction scorer did not prune that layout.

Bug record

LFV-413, snapshot of 2026-10-29

Registry title
SweetSpotSimilarity with a length plateau (setLengthNormFactors with min >= 2) breaks Similarity's norm-monotonicity contract, so default top-k search silently misses the best hits
Area
misc / similarities (SweetSpotSimilarity) with core impacts-based TOP_SCORES pruning
Priority
Medium, rank 62: SweetSpotSimilarity with a length plateau has made default top-k search silently lose its best hits since 8.0, which is the same similarity-breaks-pruning profile as LFV-190 and more plausible than LFV-253's Axiomatic plus CombinedFieldQuery pairing.
Impact class
silent wrong results
Impact note
Applications that score a field with lucene/misc SweetSpotSimilarity and call setLengthNormFactors with min >= 2 (the plateau the class exists for; the default min = max = 1 is monotone) can get wrong top hits, with no error, from the default IndexSearcher.search(query, n) once more than 1,000 documents match, whenever a postings block holds a field shorter than the plateau whose term frequency is at least that of a better-scoring plateau-length field; default IndexWriterConfig, codec and searcher, -ea and -da, no scale beyond about 1,000 matches, every release since 8.0.0; returned scores are correct and the index is not damaged; callers that count hits exactly are not affected, and Solr is exposed only when minExactCount is set.
Summary
You score a field with SweetSpotSimilarity and setLengthNormFactors(10, 20, 0.5f), index mostly 10-term fields plus some shorter ones, and run searcher.search(new TermQuery(new Term("f", "t")), 10) on a term with more than 1,000 matches, expecting the same top hits as an exhaustive search. Instead a 10-term document that contains the term twice (score 1.414) is missing and a document that contains it once (score 1.0) comes first. Below the plateau a 2-term field scores lower than a 10-term field although its norm is smaller, which breaks the rule that a greater norm never scores higher; the postings writer relies on that rule, keeps only the short field's (freq, norm) pair for the block, advertises a block maximum of 0.471, and top-k search skips the block.
Introduced
f410df81136291f61b8deaace22bf4bb650de1ad (LUCENE-4198 'Give codecs the opportunity to index impacts', a JIRA patch by jpountz, migrated as apache/lucene#5270; no pull request): it added CompetitiveFreqNormAccumulator (today CompetitiveImpactAccumulator), which drops a (freq, larger norm) pair as dominated, and TermScorer block skipping under TOP_SCORES [exec: commit-level A/B, parent ebb346d5820 TermQuery top-scores SAME, f410df81136 DIFFERENT, controls SAME on both]. Companion commits, same author, same 8.0 development line: 838c604b765 (LUCENE-8119, #9167) wrote the norm-monotonicity rule into Similarity and is the earliest commit with any plateau-specific wrong hit (explicit TOP_SCORES disjunctions; that exposure was removed by LUCENE-8135 before any release); 99dbe936818 (LUCENE-8060, #9108) made the default search(q, n) use TOP_SCORES after 1,000 hits [exec: parent 0dc124aa78e default SAME, 99dbe936818 DIFFERENT]. Latent precondition, harmless before 8.0: 06a6034d9bc (LUCENE-7730, 7.0.0) encodes the field length as the norm; the plateau formula dates from LUCENE-577 (2006) (2018-01-31 (f410df81136; the contract commit 838c604b765 is 2018-01-09 and the default-search commit 99dbe936818 is 2018-08-01))
