SortingCodecReader postings return endOffset() 0 instead of -1 for a field indexed without offsets

Read a plain TextField (positions, no offsets) through SortingCodecReader and ask for offsets: startOffset() correctly says -1, but endOffset() says 0, in every release since 4.3.0. The written index is correct; the 0 reaches code that reads offsets through the sorted view, such as a custom codec during addIndexes or Lucene's Matches API.

The finding in 30 seconds

#

The sorted view re-encodes each document's offsets as deltas from the previous endOffset, and nextDoc() resets that base to 0 even for fields that have no offsets. Nothing overwrites it there, so endOffset() reports 0 next to startOffset() -1.

Background in three steps

#
  1. Postings list, for each term, the documents that contain it and, per document, the term's positions and, if the field indexes them, its character offsets (startOffset(), endOffset()).
  2. A field chooses what it stores with IndexOptions. A plain TextField stores positions but no offsets; asked for offsets anyway, a PostingsEnum returns -1 for both.
  3. SortingCodecReader shows an existing segment in a new document order, for example to re-sort an index through IndexWriter.addIndexes. It re-buffers each term's postings in the new order and serves them from its own enum.

The finding, step by step

#
  1. Index two documents with id 0 and 1 and a plain TextField f = "a": positions are stored, offsets are not. Wrap the segment with SortingCodecReader.wrap(leaf, sort by id descending), which swaps the two documents.
  2. Read the postings of f:a with PostingsEnum.OFFSETS, then call nextDoc() and nextPosition(). You expect startOffset() = -1 and endOffset() = -1 ("-1 if offsets were not indexed"); the unwrapped segment gives exactly that.
  3. You get startOffset() = -1 but endOffset() = 0, at every position of every document, with assertions on or off. No error.
  4. Why: the sorted view stores offsets as deltas and keeps the running base in endOffset. nextDoc() resets that base to 0 for every field; nextPosition() replaces it only when the field stores offsets, so here the 0 is what you read.
  5. Lucene's postings writers and CheckIndex check the field's index options before reading offsets, so the index the default codec writes and the search hits and scores are correct; only offsets read through the sorted view, including those the Matches API reports, are wrong.

Who is affected

#

Code that reads postings through the experimental SortingCodecReader (a custom codec during addIndexes, or a read or search of the wrapped reader, where Lucene's Matches API passes the 0 on), asks for offsets on a field without them, and trusts endOffset() == -1. Lucene's postings writers and CheckIndex check index options first, so the index and hits are correct.

Mechanism, terms and numbers381 words

Postings read through SortingCodecReader, with a sort that reorders the documents, report endOffset() 0 instead of the documented -1 for a field indexed with positions but without offsets, such as a plain TextField, while startOffset() correctly returns -1. The sorted enum, FreqProxTermsWriter.SortingPostingsEnum, delta-decodes offsets and keeps the running base in its endOffset field: nextDoc() always resets it to 0, and nextPosition() overwrites it only when the field stores offsets. Every release since 4.3.0 has it (through SortingCodecReader since 8.7.0). Lucene's postings writers and CheckIndex check IndexOptions first, so the written index and search hits are correct; a custom codec reading offsets during addIndexes, or code reading or searching the wrapped reader (including through Lucene's own Matches API), gets the 0. One-line fix: reset the base to 0 only when offsets are stored.

The mechanism (main 5adff78bb168)

#
  1. SortingCodecReader.terms(field) wraps the segment's terms in FreqProxTermsWriter.SortingTerms with the field's IndexOptions (SortingCodecReader.java:525-532). An index-sorted flush uses the same wrapper (FreqProxTermsWriter.java:113-125). An already sorted reader is not re-sorted (SortingCodecReader.java:458-460), so the enum appears only when the sort reorders documents.
  2. SortingTermsEnum.postings (FreqProxTermsWriter.java:177-203) returns a SortingPostingsEnum for any field with freqs when freqs are requested, with storeOffsets taken from IndexOptions (:200-201): false for a TextField.
  3. reset() buffers each document's positions, writes the offsets (delta-coded) only if (storeOffsets) (:444-450), and sets startOffset = -1; endOffset = -1; (:406-407).
  4. nextDoc() (:487-495): // reset variables used in nextPosition, pos = 0;, endOffset = 0; (:493), with no storeOffsets check. The 0 is the base for the first position's startOffset = endOffset + delta. This is the fix site.
  5. nextPosition() (:498-519) decodes offsets only if (storeOffsets) (:504-507), so for a field without offsets the 0 stays.
  6. startOffset() and endOffset() return the fields as they are (:522-524, :472-474): -1 and 0.

The same nextDoc() also serves freqs-only fields (storePositions == false): read with OFFSETS through the sorted view, such a field reports endOffset() 0 after nextDoc(), where the unwrapped reader gives -1 (executed by a separate re-run's probe). Without positions there is no current position, so this is a side observation, not a second contract break.

Exposure and likelihood307 words
  • A custom codec during addIndexes. IndexWriter.addIndexes(SortingCodecReader...) is the use the class documents. The default FieldsConsumer.merge (FieldsConsumer.java:72-92) hands this enum to the codec through MappingMultiPostingsEnum, whose endOffset() passes the value on unchanged (MappingMultiPostingsEnum.java:136-138). An independent reviewer from another model family (OpenAI GPT-5.6) saw endOffset 0 there through a public FilterCodec (executed).
  • Reading or searching the wrapped reader directly, including through Lucene's own Matches API. TermQuery's Weight.matches asks for OFFSETS (TermQuery.java:105), and TermMatchesIterator.endOffset() passes the 0 on (TermMatchesIterator.java:62-64) as MatchesIterator.endOffset(), documented as "-1 if offsets are not available" (MatchesIterator.java:68-69; executed). Searching the sorted view is outside its documented use.
  • Not a practical route: the index-sorted flush. It uses the same enum (FreqProxTermsWriter.java:113-125), but SortingTermsEnum.postings first passes the caller's flags to the flush enum (:193), which throws IllegalArgumentException("did not index offsets") when OFFSETS is requested on such a field (FreqProxFields.java:236-239), sorted or not. Only a codec that asks for POSITIONS and then calls endOffset() anyway sees the 0, and the same call throws IllegalStateException on every unsorted flush (FreqProxFields.java:530-535; executed by a separate re-run's probe).
  • Not hit: Lucene's postings writers read offsets only when the field writes them (PushPostingsWriterBase.java:92, :152), and CheckIndex's postings checks only if (hasOffsets) (CheckIndex.java:1842, :1970). The index the default codec writes is correct, and no run showed a changed search hit or score; only the offsets the Matches API reports on the sorted view change.
  • Effect: one silent wrong int (0) and an inconsistent pair, startOffset() -1 and endOffset() 0, the same with assertions off. Opt-in: it needs SortingCodecReader (@lucene.experimental) plus a consumer that asks for offsets of such a field. The searches below found no report, though every release since 4.3.0 (2013) has it.

Why it looks unintended

#
  • PostingsEnum promises -1 for both offsets "if offsets were not indexed"; the same enum's startOffset() keeps that promise.
  • Lucene's postings-format test asks a TextField for OFFSETS and ALL and asserts -1 for both; the default codec's enum returns -1.
  • The sorted enum returned -1/-1 until a 2013 compression change (LUCENE-4871) added the reset; its discussion never mentions fields without offsets.
The full argument212 words
  • Contract. PostingsEnum.java:90-94: "Returns start offset for the current position, or -1 if offsets were not indexed." and "Returns end offset for the current position, or -1 if offsets were not indexed." The call order used (nextDoc(), nextPosition(), then the offsets) is the documented one.
  • Tests. BasePostingsFormatTestCase.testPostingsEnumPositions (:885) indexes TextField("foo", "bar bar") (:897), requests OFFSETS and ALL, and asserts both offsets are -1 (:1005-1012, :1036-1043). RandomPostingsTester asserts "endOffset isn't -1" for fields without offsets (:1212-1213). The default codec's enum returns -1 when offsets are not read (Lucene104PostingsReader.java:1321-1334).
  • The enum's own code. reset() sets both offsets to -1, and startOffset() keeps returning -1; only the decoder's base leaks out through endOffset().
  • History. Before LUCENE-4871 the sorted enum stored absolute offsets and returned -1/-1: a commit-pair run over the 4.3.0 jars passes at the parent of the branch_4x commit c5b65d89ef1 and fails at it. LUCENE-4871 (#5936) was a compression change; its issue and comments never mention fields without offsets. On the original sorting-reader issue LUCENE-3918 (#4991), shaie noted that, with a codec that cannot index offsets, the sorting reader "will get -1 for offsets" and need not care, so -1 was the value expected to flow through it.
The devil's-advocate check169 words

"SortingCodecReader is @lucene.experimental and 'should only be used for merging' (SortingCodecReader.java:47-55); the enum's comment says it is written for addIndexes, 'which will ask for everything' (FreqProxTermsWriter.java:194-197); every in-tree merge consumer checks IndexOptions first; and the unsorted flush enum does not return -1 either: it throws IllegalStateException("offsets were not indexed") (FreqProxFields.java:521-534). So nobody is supposed to read these offsets."

Why it fails: the merge-only note gives cost ("very costly and memory intensive"), not correctness, as its reason; addIndexes hands this enum (through MappingMultiPostingsEnum, which passes endOffset() on) to any codec's FieldsConsumer, where the 0 was observed; the unsorted enum fails loudly while this one returns a plausible wrong value; and the enum itself initialises -1. The argument does bound the impact: the merge-only purpose narrows who reads these offsets, and Lucene's own enums are not uniform here (one throws, one returns -1), which is why the priority is Low: it is contract hygiene, not index corruption or wrong search results.

Suggested fix

#

Recommended A. Reset the delta base to 0 only when offsets are stored (validated)

In SortingPostingsEnum.nextDoc(), reset the offset delta base only when offsets are stored: endOffset = storeOffsets ? 0 : -1; (+2/-1). The repro passes with assertions on and off; TestSortingCodecReader, TestIndexSorting, TestPostingsOffsets (78 tests with the repro) and the lint checks pass.

pos = 0;
// the delta base for offsets; -1 ("not indexed") when offsets are not stored
endOffset = storeOffsets ? 0 : -1;
return docs[docIt];
All options and trade-offs3 options · 322 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B and C are by reading. The open PR #12842 rewrites the same decoding and keeps the unconditional endOffset = 0;, so whichever change lands second must keep the fix.

A. Reset the delta base to 0 only when offsets are stored (validated) (recommended)

#

In FreqProxTermsWriter.SortingPostingsEnum.nextDoc() (:487-495), +2/-1:

pos = 0;
// the delta base for offsets; -1 ("not indexed") when offsets are not stored
endOffset = storeOffsets ? 0 : -1;
return docs[docIt];

Trade-offs

  • No change for fields with offsets (the base is still 0); one conditional per nextDoc(), not benchmarked.
  • Also covers freqs-only fields (by reading).

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: the repro fails on stock main with assertions on and off, and passes with A, on and off.
  • With A: TestSortingCodecReader 3 of 3, TestIndexSorting 62 of 62, TestPostingsOffsets 12 of 12 and the repro: 78 tests, 0 failures. checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest for lucene/core pass. Not run: the full lucene/core suite, and codecs other than the default one.

B. Guard the accessors

#

return storeOffsets ? endOffset : -1; in endOffset(), and the same in startOffset(). The default codec's enum guards its accessors similarly, but on needsOffsets, which also depends on whether the caller asked for offsets (Lucene104PostingsReader.java:1321-1334); storeOffsets here depends only on the field.

Trade-offs

Robust to any later change of the decode state, but it touches two methods and adds a branch to every offset read. Not run.

C. Keep the delta base in its own field

#

Reset a separate base field to 0 in nextDoc() and decode from it, so endOffset only ever holds a decoded value or -1.

Trade-offs

The cleanest separation; a slightly larger diff on lines that open PR #12842 also rewrites. Not run.

Downstream note

#

Relevant downstream only to code that reads postings through SortingCodecReader, such as a custom codec used with addIndexes: decide whether offsets exist from the field's IndexOptions, not from endOffset() == -1.

How it was found

#

Semi-formal: a proof-obligation audit checked the sorted postings enum against the PostingsEnum offsets contract (-1 when offsets were not indexed). nextDoc() writes 0 into endOffset without checking whether offsets are stored, and a one-test JUnit repro on stock main witnessed the 0.

The method in full90 words
  • Obligation: for every field the enum serves, after nextDoc() and nextPosition(), startOffset() and endOffset() are the decoded offsets when the field stores them, and -1 otherwise (PostingsEnum.java:90-94).
  • Finding: reset() establishes -1 (FreqProxTermsWriter.java:406-407), but nextDoc() assigns endOffset = 0 unconditionally (:493) and nextPosition() re-establishes the offsets only if (storeOffsets) (:504), so the obligation fails for every field without offsets.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
