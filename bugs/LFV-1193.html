IndexWriter flush stall: an interrupted wait is never deregistered, so with assertions on the same thread's next stalled call fails an assert and closes the writer

An indexing thread interrupted while IndexWriter stalls it gets ThreadInterruptedException, as documented, but stays on the stall's waiter list. With assertions on, its next call in a stall, interrupted or not, fails an internal assert and IndexWriter closes itself, dropping uncommitted documents (since 10.0.0); with assertions off nothing visible happens.

The finding in 30 seconds

#

Lucene registers a stalled thread before it waits and deregisters it after, but an interrupt jumps over the deregistration. The next stall of that same thread trips Lucene's own "registered only once" assert.

Background in two steps

#
  1. IndexWriter buffers documents in RAM and flushes them to segments. If flushing falls behind, so that buffered plus flushing RAM exceeds 2 x the RAM buffer (32 MB with the default 16 MB) while the buffered part stays below that limit, it stalls indexing: each addDocument waits up to 1 s at a time in DocumentsWriterStallControl.waitIfStalled() until flushing catches up.
  2. If you call Thread.interrupt() on a thread inside IndexWriter, for example while it is in a wait(), IndexWriter throws the unchecked ThreadInterruptedException, clears the interrupt status and stays usable (IndexWriter class javadoc). Thread pools do this on Future.cancel(true) or shutdownNow().

The finding, step by step

#
  1. A default IndexWriter is stalled: flushing has fallen behind, so addDocument waits in DocumentsWriterStallControl.waitIfStalled(). The JVM runs with -ea, as test suites do.
  2. Interrupt the thread and call addDocument: it throws ThreadInterruptedException and the writer stays open, as the IndexWriter javadoc promises for an interrupt "in a wait()". But decrWaiters() sits after wait(1000) in the same try, so the interrupt skips it: the thread stays registered as a waiter.
  3. Call addDocument again on the same thread while the writer is still stalled. The repro interrupts it again, only so that the test also ends once the bug is fixed; the failure does not need that second interrupt. You expect ThreadInterruptedException again. Instead incWaiters() fails assert waiting.put(Thread.currentThread(), TRUE) == null before it waits, because the thread is still registered: AssertionError.
  4. IndexWriter treats any Error as tragic (since 10.0.0): it rolls back and closes. isOpen() is false, later updates throw AlreadyClosedException, and the uncommitted documents are gone (a probe with 1 committed and 1 buffered document reads back 1). With -da both calls just throw ThreadInterruptedException.

Who is affected

#

JVMs with assertions enabled (Lucene's and downstream test suites, CI) that interrupt an indexing thread during a flush stall and later index from that thread while the same writer is stalled again: the writer closes and loses uncommitted documents. A real stall needs over 32 MB in flight at the default buffer. Production JVMs (-da) see nothing. Rare.

Mechanism, terms and numbers672 words

When flushing falls behind indexing, IndexWriter stalls indexing threads: addDocument waits in DocumentsWriterStallControl.waitIfStalled() until flushing catches up. That method registers the thread as a waiter (incWaiters()), calls wait(1000) and deregisters it (decrWaiters()), all in one try. If the thread is interrupted during wait(), the catch (InterruptedException) rethrows ThreadInterruptedException and decrWaiters() never runs.

The first interrupted call behaves as documented: ThreadInterruptedException, writer open. With assertions enabled, the next time the same thread waits in a stall, interrupted or not, incWaiters() fails assert waiting.put(Thread.currentThread(), Boolean.TRUE) == null. Since 10.0.0 IndexWriter treats any Error as tragic (#13277), so it rolls back and closes: isOpen() is false, getTragicException() is that AssertionError, and uncommitted documents are lost. Releases 4.0.0-alpha to 9.12.3 throw the same AssertionError but keep the writer open.

With assertions disabled, the production setting, nothing user-visible happens: only a counter read by test-only getters drifts. Low priority. Present since LUCENE-4158 (2012); the fix is a try/finally.

The mechanism

#
  1. DocumentsWriter.preUpdate calls flushControl.waitIfStalled() for every add or update while the writer is stalled (DocumentsWriter.java:386-398, the call at :395; delegate DocumentsWriterFlushControl.java:748-750).
  2. waitIfStalled (DocumentsWriterStallControl.java:60-78): inside synchronized (this) and if (stalled), one try holds incWaiters() (:67), wait(1000) (:70) and decrWaiters() (:71); catch (InterruptedException e) only does throw new ThreadInterruptedException(e) (:72-74). This is the fix site.
  3. incWaiters() (:84-88) does numWaiting++ and assert waiting.put(Thread.currentThread(), Boolean.TRUE) == null (:86); decrWaiters() (:90-94) undoes both. After an interrupted wait() the thread stays in the waiting map (filled only with -ea) and numWaiting stays incremented (both modes).
  4. The next stalled waitIfStalled on the same thread fails the assert at :86, before it waits.
  5. IndexWriter.updateDocuments (IndexWriter.java:1625-1642) catches any Throwable; for an Error it calls onTragicEvent (:1633-1635), then maybeCloseOnTragicEvent() (:1639) rolls the writer back. The class javadoc: "if you hit an Error ... IndexWriter will close itself" (:162-165).

With -da, waitIfStalled decides on the volatile stalled flag only, and numWaiting is read only by package-private getters marked "for tests" (:96-102), so the drift has no visible effect. (In 4.0.0-alpha to 4.10.1 and in 4.10.4 the incWaiters()/decrWaiters() calls themselves sat inside asserts, so there -da leaves no drift at all.) Of the field comments "only with assert" (:39-41), two are stale: numWaiting (:39) since LUCENE-6019 moved the calls out of the asserts, and wasStalled (:40), which updateStalled sets outside any assert (:54) since LUCENE-4158 itself; the one on the waiting map (:41) is correct.

Only the first interrupt matters. A second stalled call on the same thread that is not interrupted fails the same way: AssertionError at incWaiters:86, writer closed, the thrown error is the tragic exception. The repro interrupts both calls only so that it also ends once the bug is fixed (its forced stall is never lifted, so an uninterrupted second call would then keep waiting).

Under a real stall

#

The repro forces the stall through the package-private stall control, which skips DocumentsWriterFlushControl.updateStallState(). A separate, multi-threaded probe that uses public API only (a 1 MB RAM buffer and one ~20 MB document whose flush another thread holds through a blocking directory wrapper) reaches a real stall and gets the same tragic close on main and 10.6.0 with -ea. That probe interrupts the thread before both calls. Because the assert fires before wait(), the second interrupt is still pending, and the tragic rollback trips over it in DocumentsWriterFlushControl.waitForFlush (:366): the caller gets ThreadInterruptedException from the rollback, the writer is closed with getTragicException() the AssertionError, and the thread whose flush was in progress gets AlreadyClosedException. The same probe with no interrupt before call 2 gives the caller the AssertionError itself, and the writer is closed. With -da or with the fix, both interrupted calls end in ThreadInterruptedException and the writer stays open.

Exposure and likelihood250 words
  • Who: JVMs running with -ea (Lucene's own and downstream test suites, CI, staging) whose code interrupts an indexing thread while it waits in a flush stall (directly, or by Future.cancel(true) or ExecutorService.shutdownNow() on an indexing pool) and later indexes from the same thread while the same writer is stalled again, as pooled worker threads can. No second interrupt is needed.
  • Effect with -ea: IndexWriter closes itself (later updates throw AlreadyClosedException from ensureOpen()), and the rollback discards the documents added since the last commit (a probe with 1 committed and 1 buffered document reads back 1). Under a real stall the thread whose flush was in progress gets AlreadyClosedException. Committed data is intact. The caller sees a bare AssertionError from Lucene internals or, in the real-stall probe that interrupts again, a ThreadInterruptedException that does not say the writer is gone.
  • Setup: no special setting is needed, but a real stall needs a lot in flight: buffered plus flushing RAM above 2 x the RAM buffer while the buffered part stays below it (32 MB with the default 16 MB). The public-API probe reached one with a 1 MB buffer and one ~20 MB document whose flush another thread held.
  • Not hit: JVMs with assertions disabled, the production setting: no user-visible effect was found.
  • Likelihood: rare. It needs -ea, one interrupt of a thread that waits in a stall, and a later stalled call from the same thread on the same writer. No public report found since 2012.

Why it looks unintended

#
  • The IndexWriter javadoc names an interrupt "in a wait()" as handled: ThreadInterruptedException, and the writer stays usable. Nothing says a second one is fatal.
  • decrWaiters() runs when wait() returns and is skipped when it throws: a missing finally.
  • With the finally, the repro and the stall-control and IndexWriter suites pass.
The full argument174 words
  • The documented contract covers this case. "If you call Thread.interrupt() on a thread that's within IndexWriter, IndexWriter will try to catch this (eg, if it's in a wait() or Thread.sleep()), and will then throw the unchecked exception ThreadInterruptedException and clear the interrupt status on the thread" (IndexWriter.java:172-175). The first call does exactly that and leaves the writer open; no javadoc, test or CHANGES entry says a later call closes it. The javadoc's "will try to catch" is best-effort wording, but it names a wait() as a case it handles, and the first call shows this one is handled.
  • The cleanup is on the normal path only. The assert at :86 is Lucene's own invariant (a thread registers once) and fires on legal input only because the exception path skips the decrWaiters() the normal path runs.
  • The fix changes nothing else that the runs show. With decrWaiters() in a finally, the repro passes and TestDocumentsWriterStallControl, TestFlushByRamOrCountsPolicy and TestIndexWriter pass; the one other change is that numWaiting stays balanced with -da.
The devil's-advocate check142 words

"This is assert-only test bookkeeping (the fields say 'only with assert'), Lucene supports interrupts only on a best-effort basis, and #16226 recently made TestIndexWriter.testThreadInterruptDeadlock accept an interrupt-driven AssertionError (TestIndexWriter.java:938-939) instead of changing code."

Why it fails: the bookkeeping argument explains why -da is harmless, not why an assert should fire on legal input. The best-effort warnings in FSDirectory, NIOFSDirectory and MMapDirectory are about interruptible channels closing; the repro uses ByteBuffersDirectory, and the IndexWriter javadoc names a wait() as handled. #16226 was a non-deterministic race between a background merge thread and an interrupt-driven rollback at another site (IndexWriter._mergeInit), with no stated policy; here the failure is deterministic, on the calling thread, with a small try/finally fix. Closing on an Error is intended (#13277); this Error is not. It is Low and assertion-only: -da shows nothing.

Suggested fix

#

Recommended A. Deregister in a finally entered after incWaiters() (validated)

Put decrWaiters() in a finally entered after incWaiters(), so every exit of wait(1000), including an interrupt, deregisters the thread (+7/-4 lines in DocumentsWriterStallControl.waitIfStalled). The repro passes with assertions on and off; TestDocumentsWriterStallControl, TestFlushByRamOrCountsPolicy, TestIndexWriter and the core format, lint and forbidden-API checks pass.

try {
  incWaiters();
  try {
    // Defensive, in case we have a concurrency bug that fails to .notify/All our thread:
    // just wait for up to 1 second here, and let caller re-stall if it's still needed:
    wait(1000);
  } finally {
    decrWaiters();
  }
} catch (InterruptedException e) {
  throw new ThreadInterruptedException(e);
}

A. Deregister in a finally entered after incWaiters() (validated) (recommended)

#

In waitIfStalled (DocumentsWriterStallControl.java:66-74):

try {
  incWaiters();
  try {
    // Defensive, in case we have a concurrency bug that fails to .notify/All our thread:
    // just wait for up to 1 second here, and let caller re-stall if it's still needed:
    wait(1000);
  } finally {
    decrWaiters();
  }
} catch (InterruptedException e) {
  throw new ThreadInterruptedException(e);
}

Trade-offs

  • Balances the bookkeeping on every exit of wait(); on the normal path decrWaiters() still runs once, as today (no benchmark was run).
  • With -da the only change is that numWaiting stays correct for the test getters.
  • The stale "only with assert" comments on numWaiting (:39) and wasStalled (:40) could be corrected in the same change; the one on waiting (:41) is correct.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and passes with them off; with fix A it passes, on and off.

  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core: pass with fix A and the test.
  • A real flush stall reached through public API only keeps the writer open with the fix and -ea (both calls end in ThreadInterruptedException).
  • The full lucene/core suite was not run.

B. Call decrWaiters() in the InterruptedException catch (validated)

#

One added line: decrWaiters(); before throw new ThreadInterruptedException(e);.

Trade-offs

Same effect for interrupts, but it covers only that exception type; A covers every exit and is the usual idiom.

What the checks validated

The repro and TestDocumentsWriterStallControl pass with assertions on (4 tests, 0 failures), gradle, seed DEADBEEF.

C. Drop the per-thread waiting map and its assert

#

Remove the waiting map and the registration assert.

Trade-offs

Removes the -ea failure but also Lucene's own check, and leaves numWaiting drifting. Not recommended. By reading, not run.

Downstream note

#

Downstream test suites that run with -ea and cancel indexing tasks by interrupt can see this as a writer that closes itself; production JVMs (-da) are not affected.

How it was found

#

Semi-formal: a proof-obligation audit of DocumentsWriterStallControl, checking that the waiter bookkeeping is balanced on every exit of waitIfStalled. The interrupt exit is not balanced, and a JUnit test on stock main showed what that does with assertions on.

The method in full75 words
  • Obligation: every incWaiters() in waitIfStalled is matched by a decrWaiters() on every exit, normal or exceptional, so that the "registered once" assert at :86 holds for legal call sequences.
  • Finding: the InterruptedException exit rethrows before decrWaiters(); the IndexWriter javadoc makes that exit a legal, handled one.
  • Witness: a JUnit test on stock main, then an independent reproduction, cross-model reviews (OpenAI GPT-5.6), an intended-behaviour review with a public-API probe and an adjudication (see Independent checks).

Versions tested7 rows

Summary
With assertions enabled, you interrupt a thread that is blocked in addDocument because IndexWriter has stalled indexing to let its flushes catch up; as the IndexWriter javadoc documents, the call throws ThreadInterruptedException and the writer stays open. You expect that thread's later calls in a stall to leave the writer open too, interrupted or not. Instead the first interrupt skipped the step that removes the thread from the stall control's waiter list, so the thread's next wait in a stall of the same writer fails the 'registered only once' assert, and IndexWriter treats that AssertionError as a tragic event and closes, discarding the uncommitted documents (since 10.0.0; without assertions nothing visible happens).
