Intervals.nonOverlapping and notWithin hide an or() in their source from the disjunction rewrite, so a phrase or maxgaps over them misses hits

Inside a phrase or maxgaps query, an or() wrapped in Intervals.nonOverlapping or notWithin is not split into its alternatives, so hits are silently lost even when the filter removes nothing. phrase(a, nonOverlapping(or("b c", b), z), d) misses a b c d; without the filter it matches.

The finding in 30 seconds

#

A phrase or max-gaps query has to try every alternative of an or() that is one of its steps, so Lucene rewrites the query into one branch per alternative (single words stay together). Each source reports its alternatives through pullUpDisjunctions(). The source behind nonOverlapping and notWithin reports only itself, so an or() in its first argument is never split.

Background: three pieces

#
  1. An interval source reports where something matches in a document, as ranges of positions. In a b c d (positions 0 to 3), b matches at [1,1] and the phrase b c at [1,2].
  2. Interval sources are minimizing: an or() read as one source drops a match that contains another one. or("b c", b) reports only [1,1]. Alone that is harmless, but a phrase needs the next word right after the match, so it would look for a b d and miss a b c d.
  3. Since 8.1.0 Lucene avoids that miss. A source that is sensitive to gaps (phrase, maxgaps) rewrites itself into one branch per alternative (alternatives that are single words stay together in one or()): phrase(a, or("b c", b), d) becomes or(phrase(a, b, c, d), phrase(a, b, d)). Intervals.or(false, ...) is the documented opt-out for speed over accuracy.

The finding, step by step

#
  1. Index one document: a b c d. Search for the phrase a, then either b c or b, then d: Intervals.phrase(a, Intervals.or(phrase(b, c), b), d). It counts 1.
  2. Wrap the middle step in a filter that removes nothing: Intervals.nonOverlapping(or(...), term(z)), where z is in no document. You expect 1 again.
  3. Instead the count is 0, with assertions on and off. There is no exception.
  4. Why: the phrase asks each step for its alternatives and builds one branch each. The filter answers with itself, so the or() inside stays whole and reports only its shortest match, b at position 1; b c (positions 1 to 2) is dropped. The phrase then needs d at position 2, but d is at position 3.
  5. notWithin, maxgaps(0, ordered(...)) and the query string fn:phrase(a fn:nonOverlapping(fn:or(fn:phrase(b c) b) z) d) miss the same way, and so do containing(filter, c) and containedBy(c, filter). With notContaining in the filter's place, or with the two alternatives split by hand, the count is 1.

Who is affected

#

Applications that put a default Intervals.or() in which one alternative's match can contain another's, such as or("new york", york), into nonOverlapping or notWithin as the source, and that filter inside a phrase, under maxgaps, or as the split operand of containing or containedBy. Default settings, any index size, silent, since 8.1.0. Rare: single-word alternatives and the filter alone are unaffected.

Mechanism, terms and numbers1,287 words

A phrase or max-gaps interval query must try every alternative of an or() that is one of its steps. Since 8.1.0 (LUCENE-8477) Lucene does that by rewriting the query into branches, one per alternative that can span more than one position (single-position alternatives stay together in one or()), and the default Intervals.or is documented to take part: "Automatically rewrites if wrapped by an interval source that is sensitive to internal gaps" (Intervals.java:121 on main 781025d6fe32). A gap-sensitive parent learns the alternatives of a step by calling pullUpDisjunctions() on it. NonOverlappingIntervalsSource, the class behind Intervals.nonOverlapping and Intervals.notWithin, answers with itself (NonOverlappingIntervalsSource.java:36-39), so an or() in the filter's source (its first argument) is never split. It is then read as one minimizing source, which drops every match that contains another alternative's match. So phrase(a, nonOverlapping(or("b c", b), z), d) returns 0 hits for the document a b c d, although z occurs in no document and the same phrase without the filter returns 1. notWithin, a maxgaps parent and the query-string form miss the same way, and so do containing and containedBy with the filter as the operand they split; the sibling filters notContaining, overlapping, containing and maxwidth are split and keep the hit. The miss is silent, needs no special settings and no scale, and is the same with assertions on and off. It is rare, because it needs an or() in which one alternative's match can contain another's, inside one of these two filters, inside a parent that asks for alternatives. It is as old as the rewrite: every release from 8.1.0 to 10.6.0 (21 of the 60 were run, the others read), branch_11x and main; not a regression. A validated one-method fix lets the filter report its source's alternatives, as overlapping and maxwidth already do; it has one trade-off under a notContainedBy parent, described with the fix.

Terms

#
  • Source and reference. Intervals.nonOverlapping(minuend, subtrahend) returns the intervals of its first argument (the source, or minuend) that overlap no interval of its second (the reference, or subtrahend). Intervals.notWithin(minuend, n, subtrahend) is the same filter with the reference widened by n positions on each side (Intervals.java:459-470, :482-497). Both construct a NonOverlappingIntervalsSource directly.
  • Pull-up. IntervalsSource.pullUpDisjunctions() is the expert method through which a source tells a parent "the set of disjunctions that make up this IntervalsSource" (IntervalsSource.java:66-71). A default or() returns its alternatives; or(false, ...) returns itself (DisjunctionIntervalsSource.java:146-152).
  • Gap-sensitive parents. Intervals.phrase builds one phrase per combination of its steps' alternatives (BlockIntervalsSource.java:30-35, Disjunctions.java:33-62); alternatives with a minimum extent of one position are first put back into one or() (Disjunctions.java:75-95). Intervals.maxgaps builds one filter per alternative of its argument (FilteredIntervalsSource.java:31-36); ordered and unordered pass the question on to their steps (OrderedIntervalsSource.java:78-80, UnorderedIntervalsSource.java:78-80). The containment filters ask too: containing and containedBy split their 'big' operand when they are built (ContainingIntervalsSource.java:31-33, ContainedByIntervalsSource.java:28-30).

The bug

#
  1. BlockIntervalsSource.build calls Disjunctions.pullUp(subSources, BlockIntervalsSource::new). The only view it has of a step is source.pullUpDisjunctions() (Disjunctions.java:79-95, the call at :82).
  2. For the middle step nonOverlapping(or("b c", b), z) the answer is Collections.singletonList(this) (NonOverlappingIntervalsSource.java:36-39). The phrase sees one alternative and builds one branch: BLOCK(a,NON_OVERLAPPING(or(BLOCK(b,c),b),z),d).
  3. At search time the filter reads its source as one iterator (DifferenceIntervalsSource.java:38-49). With z in no document it returns that iterator unchanged (:44-47).
  4. The or() iterator is minimizing. It orders the alternatives' current intervals by end (DisjunctionIntervalsSource.java:171-175) and, after returning one, drops every queued interval that contains it (:230-236, contains at :245-247). It returns b at [1,1]; b c at [1,2] contains it and is dropped.
  5. The phrase iterator needs each step to start right after the previous one ends (BlockIntervalsSource.java:126). After [1,1] it needs d at position 2. d is at position 3, so the document does not match.

Six sibling filters report their alternatives: notContaining splits its source when it is built (NotContainingIntervalsSource.java:27-30); overlapping (OverlappingIntervalsSource.java:78-83), containing (ContainingIntervalsSource.java:74-76), maxwidth (FilteredIntervalsSource.java:71-74), extend and fixField (ExtendedIntervalsSource.java:135-143, FixedFieldIntervalsSource.java:60-68) do it in pullUpDisjunctions(). In the filter's place under phrase(a, _, d) each of the six reports 2 alternatives and the phrase counts 1; nonOverlapping and notWithin report 1 and it counts 0. Not every wrapper of the package splits: notContainedBy and atLeast report 1 and count 0 too ("Left out" below).

The filter term z is not a trick. The same miss occurs with a filter term that is in the document and overlaps neither alternative (the row with a).

The alternatives need not be a phrase and one of its words, and need not differ in minimum length (the two rows with ordered(b, d)). What counts is that, in the document, one alternative's match contains another's.

A variant whose result follows the hash seed. When two alternatives match the same interval with different numbers of internal gaps, which one the unsplit or() keeps follows the order in which it holds its alternatives (a HashSet, DisjunctionIntervalsSource.java:58-68), and Lucene seeds its term hash per JVM start (StringHelper.java:141-152; from tests.seed when that is set). maxgaps(0, nonOverlapping(or(ordered(b, d), "b c d"), z)) on a b c d counted 0 under 5 of 12 seeds and 1 under the other 7, where the same query without the filter counted 1 under all 12. With the fix it counted 1 under all 8 seeds run, the 5 that missed among them. The repro is not of this kind: its result was the same under every seed run.

Why it looks unintended

#
  • The default Intervals.or is documented to rewrite itself under a gap-sensitive source; or(false, ...) is the opt-out.
  • Lucene's own test testNestedOrWithinDifference expects both documents for this shape with notContaining. With nonOverlapping in its place, one is lost.
  • The sibling filters notContaining, overlapping, containing and maxwidth are split; this one returns itself, without a comment.
The full argument670 words
  • The documented promise. Class javadoc: "by default, sources that are sensitive to internal gaps (e.g. PHRASE and MAXGAPS) will rewrite their sub-sources so that disjunctions of different lengths are pulled up to the top of the interval tree ... to ensure that documents containing "b c" are matched", with or(boolean, ...) "if you care more about speed than about accuracy" (Intervals.java:47-54). The default or(): "Automatically rewrites if wrapped by an interval source that is sensitive to internal gaps" (:121). The opt-out: "can miss valid hits due to minimization" (:130-131). The repro uses the default.
  • Released as a bug fix. CHANGES 8.1.0, under "Bug fixes": "LUCENE-8477: Interval disjunctions could miss valid hits if some of the clauses of the disjunction are minimized away. We now rewrite intervals if a source contains a disjunction and the internal gaps matter for matching." (CHANGES.txt:6620-6624).
  • Lucene's own test of this shape. TestIntervalQuery.testNestedOrWithinDifference (TestIntervalQuery.java:258-269, added by the LUCENE-8477 commit) asserts that phrase(coordinate, notContaining(or("genome mapping", genome), wibble), research) hits both "coordinate genome mapping research" and "coordinate genome research"; wibble is in no document. On an index of those two documents the query returns both; with nonOverlapping(_, wibble) or notWithin(_, 1, wibble) in the same place it returns only the second, and the built query keeps the or() unsplit. On the test's full corpus, docs 6 and 7 become doc 7 only.
  • The principle for a filter that is not split when it is built. TestDisjunctionRewrites.testNestedMaxWidth: "maxwidth does not automatically pull up disjunctions at construction time, so we need to check that it does the right thing if wrapped by something that does need exact internal accounting" (TestDisjunctionRewrites.java:138-154). testNestedFixField (:156-166) asserts the same for fixField. testDisjunctionRewritePreservesFilters (:98-122) asserts the nested result for maxgaps, which is split when it is built.
  • No sign of a choice. NonOverlappingIntervalsSource.java:36-39 returns itself without a comment; BlockIntervalsSource.java:68-71 does so with the comment "Disjunctions already pulled up in build()". The method is as LUCENE-8477 wrote it; later commits to the file are a module move, a reformat and a pattern-variable clean-up. Six sibling filters report their alternatives (notContaining, overlapping, containing, maxwidth, extend, fixField), and Lucene's tests say of the containment filters that "the 'big' interval should not be minimized" (TestDisjunctionRewrites.java:169, :186); with this filter as the 'big' operand it is. Not every wrapper of the package is split: notContainedBy, atLeast and the source side of containedBy are not (see "Same mechanism, not claimed" and "Left out").
  • No test covers it. Upstream uses the two filters in TestIntervalQuery.java:152-160 and :182-187, TestStandardQPEnhancements.java:137 and :145, and TestMatchHighlighter.java:423, :451 and :455 (two of them with an or() of single words as the source). None puts the filter under a gap-sensitive parent and none has alternatives of different lengths.
  • Maintainers on the rewrite. Alan Woodward on #9523 (LUCENE-8477): the new method "allows this rewriting to work even for filtered intervals like WITHIN or CONTAINING" (2019-03-17); "disjunctions can end up being wrapped multiple times ... My suggestion is that we automatically rewrite things to match accurately" (2019-03-25). On #10244: "Intervals automatically rewrite disjunctions (and have done since LUCENE-8477) so that queries behave as your or I would expect them to" (Alan Woodward, 2021-05-27); "If it's not correct, it's a bug, not a feature" (Jim Ferenczi, 2021-05-28). All four comments are about the rewrite in general; none is about these two filters, and the 2019-03-17 comment describes an earlier patch in which the method was called getDisjunctions(). They support the reading; they do not decide it.
  • What is not claimed. That the javadoc names this filter. It says "wrapped by" a gap-sensitive source and "to the top of the interval tree"; the nested case rests on Lucene's tests and on the comments above. The LUCENE-8477 commit message lists PHRASE, MAXGAPS and the 'big' side of the four containment filters; nonOverlapping is not named either way.
The devil's-advocate check312 words

The strongest case for "intended": intervals implement minimal-interval semantics, under which the filter sees only the minimal alternative b. Jim Ferenczi wrote on #9523 before the rewrite was merged (2019-03-20): "I am sure we can find other pathological cases due to minimum interval semantics. IMO we should document this unintuitive behavior rather than rewriting all queries in a non-optimal form." The or() javadoc says "wrapped by" a gap-sensitive source, and here the or() is wrapped directly by a filter. Standing alone, the filter reports only [1,1], with and without the fix, so one can say a parent should see no more. The expert method's javadoc says "Most implementations can return Collections.singleton(this)" (IntervalsSource.java:66-71), and the package describes its classes as experimental (package-info.java:21).

Why it fails: the project merged the rewrite a week later, listed it under bug fixes and documented the default or() as the accurate mode, with or(false, ...) as the explicit opt-out. The class javadoc says "to the top of the interval tree", and Lucene's tests assert the nested case through notContaining, containing, maxwidth and fixField. That a source alone reports less than a parent can match through is how the rewrite works for a bare or() as well: or("b c", b) alone reports [1,1], and phrase(a, or("b c", b), d) matches through [1,2]. "Most implementations" fits leaf sources; of the filters, notContaining, overlapping, containing, maxwidth, extend and fixField split or delegate, and the ones that do not are named under "Same mechanism, not claimed" and "Left out". The package calls its classes experimental; that documents no exception to what the default or() promises. What remains is a judgement: a maintainer may prefer to document the behaviour, or label a report an enhancement of LUCENE-8477, which is typed "enhancement" on GitHub and listed under "Bug fixes" in CHANGES.

Registry title
Intervals.nonOverlapping and notWithin hide a disjunction in their source from the gap-sensitive rewrite that the default Intervals.or promises, so a phrase or maxgaps over them misses hits: phrase(a, nonOverlapping(or("b c", b), z), d) does not match 'a b c d' although z occurs in no document and phrase(a, or("b c", b), d) matches
Area
queries / intervals (the gap-sensitive disjunction rewrite of LUCENE-8477, IntervalsSource.pullUpDisjunctions, through the filter source NonOverlappingIntervalsSource behind Intervals.nonOverlapping and Intervals.notWithin)
Priority
Low, rank 284: With default settings, in every release since 8.1.0, a phrase or max-gaps interval query silently misses documents when one of its steps is Intervals.nonOverlapping or notWithin over a default or() in which one alternative's match can contain another's (for example a phrase and a word of it), even when the filter removes nothing; containing(filter, x) and containedBy(x, filter) miss the same way.
