CheckIndex's "minTerm is non-null yet we saw no terms" check uses segment-wide term counts, so it never fires for a field checked after one that had terms

CheckIndex's check that a field reporting a smallest term really yields a term tests the segment's running term count instead of the field's own count. Once an earlier field had a term it can never fire, so a broken later field passes CheckIndex (every release checked since 4.9.0).

The finding in 30 seconds

#

CheckIndex's "min term but no terms" check works only until the first field of a segment that has a term; for every later field it is dead.

Background: min/max terms and how CheckIndex counts

#
  1. Terms.getMin() and getMax() return a field's smallest and largest term; their javadoc says they return null when there are no terms.
  2. CheckIndex checks a segment field by field. It counts every term it enumerates in two running totals for the segment: termCount (terms with a live document) and delTermCount (terms with none).
  3. Before each field it saves the current total as termCountStart, so "terms of this field" is the total minus termCountStart.

The finding, step by step

#
  1. Index one document with two keyword fields, a = "x" and b = "y", into one segment. Wrap the reader so that field b's Terms still says its smallest and largest term is "y" but enumerates no terms, as a buggy postings format might.
  2. Run CheckIndex.testPostings. You expect field="b": minTerm is non-null yet we saw no terms. That is what it reports with the fix, and what stock Lucene reports when the same broken Terms is on field a.
  3. You get no error. CheckIndex visits the fields in order and keeps one running term count for the whole segment; after field a it is 1. Before each field it remembers that count as termCountStart (1 for b).
  4. For b the check tests the running count, termCount + delTermCount == 0, that is 1 + 0 == 0: false. The field's own count, 1 + 0 - 1 = 0, is what it should test, and what the method's other per-field checks use.

Who is affected

#

Authors of custom postings formats and reader wrappers who rely on CheckIndex (testPostings, checkIndex() at level 2 or higher) or the test framework's TestUtil.checkReader to catch a Terms that reports a min term but has no terms, on any field after the first one with terms. Lucene's writers never produce this; no index or search result is wrong.

Mechanism, terms and numbers467 words

CheckIndex.checkFields checks a segment's fields one at a time and counts terms in two running totals for the whole segment, status.termCount and status.delTermCount. For each field it records the totals before the field's term loop (termCountStart) and subtracts that baseline in its per-field counts. One check does not: if (minTerm != null && status.termCount + status.delTermCount == 0) should report a field whose Terms.getMin() is non-null although it enumerated no terms (Terms.getMin() "returns null when there are no terms"). Because it reads the segment-wide totals, it can fire only while no earlier field of the segment has had a term. A broken Terms on a field checked after one with terms passes CheckIndex; on the first field it is reported. Lucene's own writers do not produce such a Terms, and the gap itself makes no index, score or search result wrong: it matters to authors of custom postings formats and reader wrappers who rely on CheckIndex. The one-line fix subtracts termCountStart.

The code (main 5adff78bb168, CheckIndex.java)

#
  • checkFields creates one Status.TermIndexStatus per segment (:1491) and loops over the fields (:1498; in the repro in sorted order, SlowCodecReaderWrapper.java:385-397); status.termCount++ / status.delTermCount++ count each term (:1903, :1905).
  • Per field, minTerm/maxTerm come from terms.getMin()/getMax(), with checks that both are null or both are non-null (:1545-1575).
  • termCountStart = status.delTermCount + status.termCount is taken before the field's term loop (:1633). ordExpected (:1717) and fieldTermCount (:2252) subtract it.
  • The check: if (minTerm != null && status.termCount + status.delTermCount == 0) throws field="...": minTerm is non-null yet we saw no terms (:2237-2240). Without - termCountStart it tests "no term in the segment so far", not "no term in this field".

The numbers in the repro

#

Field a has one term, "x"; field b's broken Terms reports min = max = "y" and enumerates nothing. After a, termCount = 1 and delTermCount = 0, so for b termCountStart = 1 and the check evaluates 1 + 0 == 0: false. At the end of the run status.termCount is still 1: field b contributed no term. With the fix the check evaluates 1 + 0 - 1 == 0, true, and reports field="b": minTerm is non-null yet we saw no terms: [79] (0x79 is "y").

Nothing else catches it

#

The unique-term-count check (Terms.size() against the terms enumerated) runs only when fieldTermCount > 0 (:2389-2397), and the zero doc count and frequency sums agree with an empty enumeration, so the broken field passes every other check. The same gate also hides a second inconsistency in the repro: FilterTerms delegates size() (FilterLeafReader.java:118-121), so the broken Terms still reports size() = 1.

Exposure and likelihood283 words
  • Where the check runs. CheckIndex.testPostings(CodecReader, PrintStream) (level 3, CheckIndex.java:2681-2684); checkIndex() at level 2 or higher (:1114-1125; the command-line default is level 1: "CheckIndex only verifies file checksums as default", :4673, :4748, :4854); and TestUtil.checkReader (level 3, TestUtil.java:351-371), which codec test base classes call (for example BaseNormsFormatTestCase.java:792).
  • Who needs it. Authors of custom postings formats and of reader wrappers (FilterLeafReader, FilterCodecReader) that might report a min/max term for a field that enumerates none.
  • Settings and scale. None: one document and two fields are enough; any field checked after a field with terms loses the check.
  • Not affected. Indexing and search: this CheckIndex gap changes no index, score or search result (a custom Terms this broken can misbehave in search on its own; CheckIndex only fails to report it). Lucene's writers do not produce the input: the block-tree writers write a field only when it has terms (if (numTerms > 0), Lucene103BlockTreeTermsWriter.java:1059; the same guard in the blocktreeords and sandbox idversion writers), and the default reader also rejects a field with zero terms when the segment is opened (Lucene103BlockTreeTermsReader.java:162-164, "Illegal numTerms for field number"; likewise the backward-codecs Lucene90BlockTreeTermsReader.java:186-189). The blocktreeords and sandbox idversion readers only assert (OrdsBlockTreeTermsReader.java:123, VersionBlockTreeTermsReader.java:132), so a crafted file could still reach them. No stock Terms that overrides getMin was found to report a min term while enumerating none. Term vectors are not affected: there the min/max checks are off (minTerm and maxTerm are set to null, CheckIndex.java:1547-1551). Other checks (norms, statistics) catch many term-hiding wrappers anyway; the gap is mainly the case where only getMin/getMax are wrong.

Why it looks unintended

#
  • Terms.getMin()/getMax() "returns null when there are no terms"; the check was added in the same commit to enforce that.
  • The check is per field: its message names the field, and the same method subtracts the per-field baseline termCountStart in its other per-field counts.
  • The baseline already existed when the check was written (2014); nothing documents a first-field-only check.
The full argument137 words
  • The contract. Terms.getMin()/getMax(): "This returns null when there are no terms." (Terms.java:138-153). 11ae32183f0 (LUCENE-5610) added this sentence and the check together.
  • The check is per field. Its message names the field; it is in the same per-field loop body as the "has null minTerm but non-null maxTerm" / "has non-null minTerm but null maxTerm" checks (CheckIndex.java:1564-1573), which the same commit added; the method keeps a per-field baseline for exactly this kind of count (:1633, :1717, :2252). With the same broken Terms on the first field, the check fires.
  • The baseline was in scope. At 11ae32183f0, termCountStart sat in the same loop body, and both ordExpected and the unique-term-count check of that revision subtracted it. No javadoc, CHANGES entry, test or discussion describes a first-field-only check.
The devil's-advocate check145 words

CheckIndex is @lucene.experimental (CheckIndex.java:110) and best effort; the input is a Terms that already breaks its own javadoc; no stock codec produces it. An independent reviewer from another model family (OpenAI GPT-5.6) rated the finding not real on these grounds, while reproducing the behaviour and agreeing on the root cause.

Why it fails: catching a Terms that breaks the getMin/getMax contract is evidently what this check is for (its message says so, and the same commit added the javadoc sentence), so "the input is already broken" is circular. The check works for the first field and silently stops after it: a defect in existing code, not a request for a new check. The repro uses only public API (FilterLeafReader, SlowCodecReaderWrapper, CheckIndex.testPostings), and a custom PostingsFormat reaches the same code. Verdict: a real Low bug, a validator coverage gap.

Suggested fix

#

Recommended A. Subtract termCountStart in the condition (validated)

Subtract the per-field baseline, as the sibling checks do: status.termCount + status.delTermCount - termCountStart == 0 at CheckIndex.java:2237. The repro passes with assertions on and off; TestCheckIndex and TestLucene104PostingsFormat pass and the formatter check is clean.

-      if (minTerm != null && status.termCount + status.delTermCount == 0) {
+      if (minTerm != null && status.termCount + status.delTermCount - termCountStart == 0) {
         throw new CheckIndexException(

Trade-offs

No effect on indexing or search; the cost is one subtraction per field, outside the term loop: negligible (not benchmarked). CheckIndex now reports a broken Terms on any field, not only before the first field with terms; a custom codec that was wrong all along will now fail CheckIndex, which is the point.

  • With the fix, TestCheckIndex (9 tests) and TestLucene104PostingsFormat (34 tests, 2 skipped as nightly-only) pass, together with the repro: 44 tests, 0 failures. These are the closest suites, not the full test matrix.
  • :lucene:core:checkGoogleJavaFormat passes with the fix and the repro test in place.
  • Without the fix the same gradle runs fail at assertNotNull(status.error), with assertions on and off.

B. Test fieldTermCount == 0 instead

#

Compute the field's own count once and test it. Same behaviour and arguably clearer, but fieldTermCount is computed later, inside the fieldTerms != null branch (:2242-2252), so the check or the computation has to move.

Trade-offs

A bigger diff for the same result. Not run.

Downstream note

#

Products and plugins that ship their own postings format or reader wrapper and validate it with CheckIndex or Lucene's test framework do not get this check for any field after the first field with terms until the fix lands.

How it was found

#

A proof-obligation audit of CheckIndex's per-field checks: every field whose Terms reports a non-null smallest term must enumerate at least one term. Following the counters that obligation relies on showed they are segment-wide, and a one-test JUnit repro witnessed it: the broken Terms is reported on the first field and missed on the second.

The method in full68 words

The obligation came from the check's own message and the Terms.getMin() javadoc. Tracing which counts the condition reads (CheckIndex.java:2237) back to where they are reset (once per segment, :1491) and to the per-field baseline the sibling checks use (:1633) showed the missing subtraction. The repro then put the same deliberately broken Terms on the second field and, as a control, on the first.
