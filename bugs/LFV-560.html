StandardQueryParser with setMultiFields normalizes field-less wildcards with the wrong analyzer

With setMultiFields and per-field analyzers, the flexible StandardQueryParser normalizes a field-less Luc* before it knows the field, so it searches title:Luc* (0 hits) where typing title:Luc* searches title:luc* (1 hit, the document "Lucene"); with a Map.of per-field map, parse() throws NullPointerException. Every release since 7.0.0 is affected.

The bug in 30 seconds

#

Two steps of the parser run in the wrong order: the step that normalizes Luc* runs before the step that gives a field-less clause its fields.

  1. Index one document titled "Lucene". The analyzer is a PerFieldAnalyzerWrapper: StandardAnalyzer (lower-cases) for title, WhitespaceAnalyzer (keeps case) for other fields. Call setMultiFields({"title"}), then parse("Luc*", null).
  2. You expect the same query as typing title:Luc*, which the parser makes title:luc*: 1 hit. Fuzzy Lucene~1 through the same expansion does become title:lucene~1 and finds it.
  3. Instead you get title:Luc* and 0 hits (Lu?ene too). The parser normalizes Luc one step before the step that gives the clause its field, so it asks the analyzer for field null, and the wrapper answers with its default analyzer.
  4. It also goes the other way. With the wrapper's own javadoc setup (StandardAnalyzer default, KeywordAnalyzer for firstname and lastname), Jo* becomes firstname:jo* lastname:jo*: 0 hits for "John".
  5. With a per-field map from Map.of, the null lookup throws: every field-less prefix or wildcard term with a literal part (Luc*, not a bare *) makes parse() fail with NullPointerException. From 7.0.0 to 10.5.2 and on main; swapping two processors fixes it.

Who is affected

#

Applications that parse field-less queries with the flexible StandardQueryParser in multi-field mode (setMultiFields, parse(query, null)) over fields whose analyzers normalize differently, e.g. a PerFieldAnalyzerWrapper. One document is enough; results are silently wrong, or parse() throws with a Map.of map. The classic MultiFieldQueryParser, explicit fields and one shared analyzer are not affected.

Mechanism, terms and numbers580 words

The flexible StandardQueryParser runs a parsed query through a fixed list of processors. The first one, WildcardQueryNodeProcessor, normalizes the literal parts of prefix and wildcard terms with Analyzer#normalize(field, text); the second one, MultiFieldQueryNodeProcessor, gives a clause without a field the fields set by setMultiFields. So a field-less Luc* is normalized for field null, which a PerFieldAnalyzerWrapper answers with its default analyzer instead of the expanded field's. With a case-keeping default and a lower-cased title, Luc* becomes title:Luc* and misses the document titled "Lucene" that title:Luc* (parsed as title:luc*) finds; with the wrapper's javadoc setup (lower-casing default, keyword name fields) Jo* is lower-cased and misses "John"; with a Map.of per-field map every such term with a literal part throws NullPointerException from parse(). Fuzzy, regexp and range terms through the same expansion are normalized per field and plain terms analyzed per field, and the classic MultiFieldQueryParser normalizes wildcard terms per field. Introduced by LUCENE-7355 together with LUCENE-7429 (both 2016), first released in 7.0.0, still on main; moving MultiFieldQueryNodeProcessor before WildcardQueryNodeProcessor fixes it and passes the whole queryparser module.

Terms

#
  • Multi-field mode: StandardQueryParser.setMultiFields(fields) plus parse(query, null). A clause without a field is expanded into one clause per field (StandardQueryParser.java:102-105, :357-362).
  • Normalization: Analyzer#normalize(field, text) maps a partial word to "the representation that it would have in the index" (lower-casing, folding) without tokenizing; query parsers use it for wildcard and fuzzy terms (Analyzer.java:202-213). It depends on the field.
  • Per-field analyzer: PerFieldAnalyzerWrapper (or any DelegatingAnalyzerWrapper) picks an analyzer by field name with fieldAnalyzers.get(fieldName), else the default (PerFieldAnalyzerWrapper.java:74-77).

The bug (code at ea57360912ed)

#
  1. The pipeline adds WildcardQueryNodeProcessor first and MultiFieldQueryNodeProcessor second (StandardQueryNodeProcessorPipeline.java:48-49); each processor walks the whole tree before the next one (QueryNodeProcessorPipeline.java:75-81).
  2. WildcardQueryNodeProcessor calls analyzeWildcard(analyzer, fqn.getFieldAsString(), text) (WildcardQueryNodeProcessor.java:107-111), which calls a.normalize(field, chunk) on each literal chunk (:66, :76). For a field-less clause getFieldAsString() is still null (FieldQueryNode.java:99-102).
  3. The wrapper is asked for field null (AnalyzerWrapper.java:146): PerFieldAnalyzerWrapper falls back to its default analyzer, and a Map.of map throws NullPointerException on get(null).
  4. Only then does MultiFieldQueryNodeProcessor set the field and clone the node per field (MultiFieldQueryNodeProcessor.java:70-105). Nothing normalizes the text again; the builder makes new PrefixQuery(new Term(field, text), ...) (PrefixWildcardQueryNodeBuilder.java:48).
  5. Fuzzy, regexp and range terms are normalized by later processors with the expanded field (FuzzyQueryNodeProcessor.java:59, RegexpQueryNodeProcessor.java:43, TermRangeQueryNodeProcessor.java:138-139), plain terms are analyzed by AnalyzerQueryNodeProcessor (pipeline :58). Only prefix and wildcard terms see null.

Exposure and likelihood274 words
  • Who is hit. Callers of StandardQueryParser with setMultiFields and parse(query, null) whose fields use analyzers that normalize differently, through PerFieldAnalyzerWrapper or another DelegatingAnalyzerWrapper. Typical setups: the wrapper's javadoc example (lower-casing default, keyword name or ID fields), or a keyword or whitespace default with analyzed text fields.
  • Which queries. A field-less prefix or wildcard term is affected when the default analyzer and the field's analyzer normalize one of its literal chunks differently (whether hits change then depends on the indexed data): an upper-case letter in every hand-written repro and security case; in the finder's scan also accent and width folding (ASCII-folding and ICU-folding chains).
  • Default vs opt-in. Multi-field mode and per-field analyzers are application choices; given those, no other setting is needed. With one field-independent analyzer nothing visible changes.
  • Both directions. Missing normalization (Luc* on a lower-cased field: 0 hits) and wrong normalization (Jo* lower-cased on keyword fields: 0 hits; ABC* selects abc-2 instead of ABC-1).
  • Crash variant. A per-field map that rejects null keys (Map.of, executed; by the JDK contract also ConcurrentHashMap, not executed) makes every such term with a literal part throw an unchecked NullPointerException from parse() instead of a QueryNodeException.
  • Scale. None: one document, a one-word query. Silent: fewer or different hits.
  • Reach. Solr, Elasticsearch and OpenSearch do not call setMultiFields (read-only code search of their default branches, not exhaustive); Lucene's Luke uses the parser without it. Applications that embed the flexible parser directly can be affected; they were not surveyed. No user report was found in the nine years since 7.0.0; the likelihood is rated plausible.
  • Fix cost. Query side only: no reindexing.

Why it is a bug, not intended

#
  • Javadoc: a field-less clause is expanded over the setMultiFields fields; typed with the field, title:Luc* becomes title:luc*.
  • The same parser normalizes fuzzy, regexp and range terms, and analyzes plain terms, per expanded field; the classic MultiFieldQueryParser normalizes wildcards per field.
  • 7.0 removed lowercaseExpandedTerms because expanded terms "are now normalized through Analyzer#normalize" (per field); no test pins the order.
The full argument230 words
  • The contract. StandardQueryParser: "If the field specification is omitted, the query parser will expand the clause over all fields specified by a call to setMultiFields(CharSequence[])" (:102-105); setMultiFields: "Set the fields a query should be expanded to when the field is null" (:357-362). Analyzer#normalize: "Normalize a string down to the representation that it would have in the index ... used by query parsers ... in case of a wildcard or fuzzy query" (Analyzer.java:202-213). PerFieldAnalyzerWrapper "can be used like any other analyzer, for both indexing and query parsing" (:42-43).
  • The 7.0 migration note. "CommonQueryParserConfiguration.setLowerCaseExpandedTerms removed (LUCENE-7355). This option has been removed as expanded terms are now normalized through Analyzer#normalize" (lucene/MIGRATE.txt:94-97 at the 7.0.0 tag).
  • The parser disagrees with itself. Fuzzy, regexp, range and plain clauses through the same expansion get per-field forms (title:lucene~1); the classic MultiFieldQueryParser expands prefix and wildcard terms per field before normalizing (MultiFieldQueryParser.java:251-274).
  • Tests and history. No upstream test combines multi fields, per-field normalization and wildcards; the whole queryparser module (533 upstream tests) passes with the fix. LUCENE-7355 removed LowercaseExpandedTermsQueryNodeProcessor, which ran after the expansion and lower-cased without looking at the field, and put the new normalize() call into the processor that already ran first; its other calls run after the expansion. None of the issue's 34 comments mentions the multi-field path.
The devil's-advocate check260 words

The strongest case for "intended" (a devil's-advocate verifier, reviews by OpenAI GPT-5.6 and a fact check by the same model family, all of which rated it weak): the pipeline javadoc says "The order they are assembled affects the results" (StandardQueryNodeProcessorPipeline.java:32); MultiFieldQueryNodeProcessor expands terms "so the query looks for the same term in different fields" (:31-33), which could mean one identical, already-normalized term; TestMultiFieldQPHelper.testAnalyzerReturningNull says bla*, bla~ and [a TO c] "are not affected as their terms are not analyzed anyway" (:308-315); the NullPointerException could be blamed on the map; and normalizing once before the expansion is cheaper than once per expanded field.

Why it fails: the order warning is generic; the same parser gives fuzzy, regexp, range and plain clones per-field forms, so "same term" means the same input text, analyzed per field; the test comment comes from LUCENE-1567 (2009), seven years before Analyzer#normalize, lumps in fuzzy and range terms that are now normalized per field, and passes in either order; with multi fields set no other clause type passes null; neither normalize nor getWrappedAnalyzer says whether null is allowed, so the API is silent, and the case rests on the disagreement with the explicit-field form; the classic MultiFieldQueryParser already normalizes once per field. Verdict: a defect. For accuracy in the issue: before 7.0 this parser lower-cased expanded wildcard terms without looking at the field, so the regression is the null field (the field-less form disagrees with the explicit-field form, and Map.of maps throw), not the loss of a per-field feature.

Suggested fix

#

Recommended Run the multi-field expansion before wildcard normalization (validated)

Swap two lines in StandardQueryNodeProcessorPipeline: add MultiFieldQueryNodeProcessor before WildcardQueryNodeProcessor, so each expanded clause is normalized for its own field. Query side only, no reindex. The repro passes, the queryparser module passes (538 tests, 0 failures), and nested syntax and boosts match the explicit-field form.

public StandardQueryNodeProcessorPipeline(QueryConfigHandler queryConfig) {
  super(queryConfig);

  add(new MultiFieldQueryNodeProcessor()); // was second: set the fields first
  add(new WildcardQueryNodeProcessor());   // was first: now normalizes per field
  add(new FuzzyQueryNodeProcessor());
  // ... the rest unchanged
All options and trade-offs4 options · 686 words

The root cause is the order of two processors. The swap was built and run in a scratch worktree at ea57360912ed (removed afterwards) and with the standalone runner; the other options are not built.

Run the multi-field expansion before wildcard normalization (validated) (validated by the checks) (recommended)

#

Move add(new MultiFieldQueryNodeProcessor()) above add(new WildcardQueryNodeProcessor()). MultiFieldQueryNodeProcessor works on any FieldableNode (a FieldQueryNode is one), so it clones the raw Luc* per field, and WildcardQueryNodeProcessor then normalizes each clone for its own field. Results: Luc* gives title:luc*, Jo* gives firstname:Jo* lastname:Jo*, and the Map.of map no longer throws.

public StandardQueryNodeProcessorPipeline(QueryConfigHandler queryConfig) {
  super(queryConfig);

  add(new MultiFieldQueryNodeProcessor()); // was second: set the fields first
  add(new WildcardQueryNodeProcessor());   // was first: now normalizes per field
  add(new FuzzyQueryNodeProcessor());
  // ... the rest unchanged

Trade-offs

  • Behaviour change for affected users (the point of the fix): field-less prefix and wildcard terms now match like the explicit-field form; queries that matched only through the default analyzer's normalization see different hits. Worth a CHANGES entry.
  • Pipeline positions change. StandardQueryNodeProcessorPipeline is a public List; code that edits it by index (for example get(0) expecting WildcardQueryNodeProcessor) sees the two processors swapped.
  • Cost. A field-less wildcard term is then normalized once per expanded field instead of once, as the classic MultiFieldQueryParser already does; not measured, and only noticeable with many fields or an expensive normalize().
  • Failure order for invalid configurations. Without setMultiFields, parse(query, null) makes MultiFieldQueryNodeProcessor throw IllegalArgumentException (MultiFieldQueryNodeProcessor.java:79-82); after the swap it throws before the wildcard processor runs, so a Map.of map then gives that exception instead of the NullPointerException. With an empty multi-field list the field stays null in either order.
  • Checked: nested AND/OR/NOT, clause boosts, field boosts (setFieldsBoost), a leading wildcard, quoted text, ranges and fuzzy-on-wildcard all agree with the explicit expansion after the swap (14 shapes x 2 configurations). Not checked: custom pipelines built on this class.

Keep the order and normalize wildcard terms after the expansion (not built)

#

Leave WildcardQueryNodeProcessor first but skip analyzeWildcard while the field is null and multi fields are set, then normalize in a processor that runs after MultiFieldQueryNodeProcessor.

Trade-offs

  • Keeps pipeline positions (and the current failure order) stable; more code, and two places that handle wildcard text. If maintainers want to keep the public pipeline positions, this option deserves equal consideration.

Make PerFieldAnalyzerWrapper return its default analyzer for a null field (not built, partial)

#

Removes the NullPointerException with Map.of maps; the prefix and wildcard terms stay wrong.

Trade-offs

  • It would also bypass a null key that a null-tolerant map holds on purpose (undocumented, but possible). Only useful as hardening next to the swap.

Workaround for users today: reorder the parser's own pipeline (validated) (validated by the checks)

#

After creating the parser, move the wildcard processor behind the multi-field processor; check the order first, so the line does nothing on a fixed release (the probe makes the same check). Or write the fields explicitly, or use the classic MultiFieldQueryParser.

QueryNodeProcessorPipeline p = (QueryNodeProcessorPipeline) qp.getQueryNodeProcessor();
if (p.get(0) instanceof WildcardQueryNodeProcessor && p.get(1) instanceof MultiFieldQueryNodeProcessor) {
  p.add(1, p.remove(0)); // WildcardQueryNodeProcessor now runs after MultiFieldQueryNodeProcessor
}

What the checks validated

  • On main, 10.5.2 and 9.12.3 the scope probe's 28 pairs all agree with the explicit-field form.

Downstream note

#

Applications that write restriction rules as field-less query strings parsed this way get the literal normalized by the analyzer for field null (the wrapper's default), not the field's: a rule can miss the values it names or catch differently-cased ones, and a deny-only rule such as *:* -Confid* returns every document. Writing the fields out avoids it.

How it was found

#

Semi-formal. While building a scan of how query parsers normalize terms, an AI tool noticed the processor order; the bounded scan on the stock jars then showed it: with setMultiFields, 38-92% of prefix and wildcard checks missed for 15 of the 16 analyzers compared, and none with an explicit field. A JUnit test confirmed it.

The method in full237 words

Method: semi-formal (a hypothesis from code reading, then witnessed by a bounded tool run).

  • A hunt unit (analyzer normalize consistency, 2026-10-26). The finder, an AI tool, checked a metamorphic relation: a word's Analyzer#normalize form should equal the token the index holds, and each parser should build its prefix, wildcard, fuzzy, regexp and range terms from that form.
  • While building the parser-reachability scan it read StandardQueryNodeProcessorPipeline and suspected the order. The bounded scan on the stock main jars (2,921,246 query checks: 18 analyzers, words of length 1-3, 4 parser setups, 5 query kinds) used a PerFieldAnalyzerWrapper with a KeywordAnalyzer default and the scanned analyzer on the expanded field.
  • Result: in multi-field mode the flexible parser missed 38-92% of the prefix and wildcard checks for 15 of the 16 analyzer configurations in the comparison, counted over the words for which the analyzer's own normalize() form equals its indexed token (StandardAnalyzer 4,548 of 10,032, an ASCII-folding chain 7,772 of 10,032, an ICU-folding chain 11,167 of 12,198); the 16th, a Ukrainian chain, missed none. With an explicit default field there were no such misses, and fuzzy, regexp and range in multi-field mode had none either. The scan covers a finite set of analyzers and words.
  • A public-API JUnit test then failed on main, 10.5.2 and 9.12.3; an independent reviewer from another model family (OpenAI GPT-5.6) reviewed it, verifiers and an adjudication confirmed it, and the history, prior-report and security checks followed.

History

#

Introduced by LUCENE-7355 (e92a38af90d, 2016-07-12), which put wildcard normalization into the processor that runs before the multi-field expansion, together with LUCENE-7429 (af60048097a, 2016-10-27), which made analyzer wrappers normalize by field name. First release 7.0.0; main and 7 releases up to 10.5.2 were run and fail; 6.6.6 and older pass. Not fixed upstream.

Versions tested6 rows

Introduced by two 2016 commits, both first released in 7.0.0. e92a38af90d "LUCENE-7355: Add Analyzer#normalize() and use it in query parsers" (now #8409, by @jpountz; authored 2016-06-28, committed to master 2016-07-12; a JIRA patch, no PR) removed LowercaseExpandedTermsQueryNodeProcessor, which ran after the expansion and lower-cased without looking at the field, and added the normalize() call to WildcardQueryNodeProcessor, the first processor: this is where field null comes from. It did not touch AnalyzerWrapper, so at that commit a PerFieldAnalyzerWrapper did not yet apply any wrapped analyzer's normalization. af60048097a "LUCENE-7429: AnalyzerWrapper can now wrap the normalization analysis chain too" (now #8482, by @jpountz, 2016-10-27) made wrappers normalize through getWrappedAnalyzer(fieldName), which turns field null into the default analyzer's normalization or the Map.of exception; its 6.x backport (6.3.0) has no effect there because the 6.x flexible parser does not call normalize(). The processor order is older: LUCENE-1792 (565a6d22b5f, 2009) put the wildcard processor first; blame shows 6f66858572c (2010), which only renamed addProcessor to add; no commit message explains the order. The 6.x backport of LUCENE-7355 (6.2.0) did not touch the flexible parser. Not bisected at commit level and neither commit's tree was run: blame, the diffs and ancestry name the commits, and the release runs bound the change to 7.0.0.

What changed for users at 7.0.0: Luc* with a case-keeping default and a lower-cased field matched in 6.x and stops matching; the keyword case was lower-cased in 6.x too, but the same way for the field-less and the explicit form; the Map.of exception is new. Upstream main (a95c754ee003), branch_10x and branch_10_5 have the same processor files (unchanged since 2021). The releases between the ones run were not run; every release tag from 7.0.0 to 10.5.2 in the history clone contains both commits.

Bug record

#

LFV-560, snapshot of 2026-10-28

Registry title
StandardQueryParser with setMultiFields normalizes field-less prefix and wildcard terms with field null, before the multi-field expansion, so per-field analyzers are ignored for them (and a PerFieldAnalyzerWrapper over Map.of throws NullPointerException)
Area
queryparser / flexible StandardQueryParser (processor pipeline order: WildcardQueryNodeProcessor runs before MultiFieldQueryNodeProcessor)
Priority
Medium, rank 36: The flexible StandardQueryParser in opt-in multi-field mode silently mis-normalizes prefix and wildcard terms when per-field analyzers differ, the silent parser profile of LFV-019 and LFV-359 with a narrower setup, so it closes that group.
Impact class
silent wrong results
Impact note
Applications that parse field-less queries with the flexible StandardQueryParser in multi-field mode (setMultiFields plus parse(query, null)) over fields whose analyzers normalize differently (PerFieldAnalyzerWrapper or another wrapper) silently get the wrong prefix and wildcard terms, in either direction: under-normalized (Luc* stays Luc* on a lower-cased title field, 0 hits) or over-normalized (Jo* is lower-cased to jo* on KeywordAnalyzer fields, the PerFieldAnalyzerWrapper class-javadoc setup, 0 hits); with a per-field map that rejects null keys (Map.of) every such query throws NullPointerException from parse(); opt-in mode, no scale needed, every release from 7.0.0 to 10.5.2 and main.
Summary
You give StandardQueryParser a PerFieldAnalyzerWrapper (WhitespaceAnalyzer by default, StandardAnalyzer for 'title'), call setMultiFields({title}) and parse 'Luc*' with no field, expecting what the javadoc promises: the clause expanded over the multi fields, i.e. the same query as 'title:Luc*', which becomes title:luc* and finds the document titled 'Lucene'. Instead the pipeline normalizes the prefix in WildcardQueryNodeProcessor before MultiFieldQueryNodeProcessor has set the field, so Analyzer#normalize is called with field null (the wrapper's default analyzer), the query becomes title:Luc* and finds nothing, while plain, fuzzy, regexp and range clauses in the same setup are normalized with the expanded field. If the per-field map is a Map.of, the null lookup makes parse() throw NullPointerException for every field-less prefix or wildcard clause.
Introduced
e92a38af90d12e51390b4307ccbe0c24ac7b6b4e (master): LUCENE-7355 'Add Analyzer#normalize() and use it in query parsers' by @jpountz (now apache/lucene#8409; a JIRA patch, no PR) [read: blame on the analyzeWildcard/normalize lines, the commit diff and ancestry (an ancestor of 7.0.0, not of 6.6.6); exec: 6.6.6 passes, 7.0.0 fails and passes with the two processors swapped]. It removed LowercaseExpandedTermsQueryNodeProcessor, which ran after MultiFieldQueryNodeProcessor and lower-cased field-independently, and added Analyzer#normalize(fqn.getFieldAsString(), ...) to WildcardQueryNodeProcessor, the first processor of the pipeline; the calls it added to the fuzzy, regexp and range processors run after the expansion. The pipeline order itself dates from 6f66858572c (2010) and was harmless until then. The 6.x backport 7c2e7a0fb80 (6.2.0) did not touch the flexible parser.
