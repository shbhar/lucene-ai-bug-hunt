Loud, at build time; nothing is silently wrong or written.

The finding in 30 seconds

#

Run: an empty text labelled true, StandardAnalyzer, automatic bias or threshold, on each of the 108 releases 5.0.0 to 10.6.0 (third of three documents, batch size 1); punctuation-only and stop-word-only texts on 10.6.0, branch_11x, main and (assertions off) 10.5.2, on no older release. The same document labelled false trains. A training query on the text field's terms avoids it.

Background: three pieces

#
  1. BooleanPerceptronClassifier learns a true/false class from the labelled documents of an index. Its constructor takes the reader, an analyzer, an optional training query, a batch size, a bias (null: computed from the index) and the names of the class field and the text field, and trains right away.
  2. For each training document it classifies the stored text with the weights learned so far. Only when the answer differs from the label does it update the weights, and for that it reads the document's term vector: the document's own terms with their counts, which the text field must store.
  3. IndexWriter stores a term vector for a document only when the field has a term in that document. A text without a token (empty, only punctuation, only stop words) leaves none, and reading it returns null.

The finding, step by step

#
  1. Index two documents with StandardAnalyzer. The text field is stored and stores term vectors, as the classifier needs; class holds the label. Document 0: text fox, class false. Document 1: an empty text, class true.
  2. Call new BooleanPerceptronClassifier(reader, analyzer, null, 1, null, "class", "text"): no training query, batch size 1, the automatic bias (here 1 term occurrence / 1 document with a term = 1.0). You expect a classifier, or at least an error that names document 1. No javadoc says which.
  3. You get java.io.IOException: term vectors must be stored for field text. The field does store them: FieldInfo.hasTermVectors() is true and document 0 has its term vector.
  4. Why: IndexWriter writes no term vector for a document whose field has no token, so document 1 has none. The training loop scores its empty text 0, below the bias 1.0, and assigns it false. Its label says true, so the loop goes on to update the weights, reads the document's term vector, gets null and throws its message about the field.
  5. The same document labelled false is classified right, does not reach that read, and the classifier is built; with the explicit bias -1.0 the two labels swap. !!! and, under EnglishAnalyzer, the stop word the, labelled true, fail the same way (run on 10.6.0 and on builds of branch_11x and main). The training query WildcardQuery(text:*) leaves the document out and the classifier is built.

Who is affected

#

Only an application that trains this opt-in, experimental classifier, when a labelled training text without a token is misclassified at its turn (automatic bias: labelled true). It loses the classifier until that document is found; the message names neither the document nor the cause. Loud, at build time, nothing written. A training query on the text field's terms avoids it.

Mechanism, terms and numbers1,540 words

Small and loud. BooleanPerceptronClassifier (org.apache.lucene.classification) is an opt-in class tagged @lucene.experimental. Its constructor trains the classifier from the labelled documents of an index (in the 5.x releases a separate train() method does). The failure described here is a declared IOException while the classifier is built: nothing is silently wrong, nothing is written, no classifier object exists afterwards, and the reader stays usable.

The class needs a text field that is stored and stores term vectors. For each training document it classifies the stored text with the weights learned so far (BooleanPerceptronClassifier.java:150, lines at main f6e694652c3d); only a misclassified document goes on to updateWeights (:154-163), which reads that document's term vector (:181) and throws IOException("term vectors must be stored for field " + textFieldName) when it is null (:183-185). IndexWriter writes no term vector for a field that has no term in a document (TermVectorsConsumerPerField.java:69-74), so a training document whose text has no token gives null there although the field stores term vectors. The check answers "does this document have a term vector"; its message states a requirement on the field, which the field already meets.

Such a document fails the build only when it is misclassified at its turn. A text without a token has the output 0 (:224-239), so under the automatic bias, which is positive whenever the field has a term, it is assigned false: labelled true it throws, labelled false it trains (run). With the explicit bias 2.0 it is the same, and with -1.0 the two labels swap (run). A labelled document without the text field is passed over (:148), and a field that really stores no term vectors gets the very same message, which is the case the message names (run).

No javadoc sentence says what the constructor does with a training document whose text has no token, so this page does not say that the constructor must return. What it reports is narrower: the missing term vector of one document is read as a missing field configuration, the message asks for a field configuration that is already in place and names neither the document nor the cause, and whether the build fails follows from that document's label and the sign of the bias. A maintainer may pass such a document over or keep a failure that names it.

One shape was run on each of the 108 releases 5.0.0 to 10.6.0: an empty text labelled true as the third of three training documents, StandardAnalyzer, the automatic bias (the automatic threshold in 5.x and 6.x), batch size 1. The other shapes (a punctuation-only text, a stop-word-only text, other analyzers, an explicit bias, batch size 2, the position of the document, several segments) were run on 10.6.0 and on builds of branch_11x and main, and partly on 10.5.2 with assertions off; for the older releases they are by reading. These runs used one analyzer for writing the index and for the constructor. The check and its message came with the class in 2013 (LUCENE-4818). A training query on the text field's terms avoids the failure. One change was validated through Lucene's own build (the test, the module's tests and its lint): ask the document's segment whether the field stores term vectors, and update no weight for a document without a term vector when it does.

The steps in the code (BooleanPerceptronClassifier.java at main f6e694652c3d)

#
  1. The writer. TermVectorsConsumerPerField.finish() returns before addFieldToFlush when the field has no term in the document: if (!doVectors || getNumTerms() == 0) { return; } (TermVectorsConsumerPerField.java:69-74). So what counts is the analysis when the index was written. The other runs of this page use one analyzer for the index and for the constructor. Run with two: a text labelled true that gave no term when it was indexed (the under EnglishAnalyzer) throws although the constructor's StandardAnalyzer finds a token in it; the reverse (indexed under StandardAnalyzer, the constructor with EnglishAnalyzer) trains.
  2. The reader API. TermVectors.get(doc, field) returns the "term vector for this document and field, or null if term vectors were not indexed" (TermVectors.java:56, :62-68).
  3. The field-level check passes. The constructor first asks for the field's terms over the whole reader and throws term vectors need to be available for field ... when there are none (:90-94). One document with a token is enough to pass it.
  4. The automatic bias. A bias of null or 0 becomes getSumTotalTermFreq / getDocCount of the text field (:99-105), positive whenever the field has a term. The first weight of each term is its total term frequency (:119-124).
  5. The training loop (:140-166). The training documents are the hits of WildcardQuery(class:*) plus the caller's query (:130-136). A document without a stored text or class value is passed over (:148). The stored text is classified with the weights so far (:150): assignClass adds up the weights of the text's tokens, starting at 0 (:224-234), and answers output >= bias (:239). The label is Boolean.valueOf of the stored class value (:153): the runs of this page use the words true and false; run also with the empty text: the class values TRUE and True throw as true does, yes and 1 train as false does.
  6. The update. modifier = signum(correctClass.compareTo(assignedClass)) (:154). When it is not 0, the document goes to updateWeights (:155-163), the only call of that method.
  7. The check. updateWeights reads termVectors.get(docId, textFieldName) (:181) and throws IOException("term vectors must be stored for field " + textFieldName) when it is null (:183-185). Nothing in the method reads the field's configuration.

Why it looks unintended

#
  • The message blames the field's configuration, which is right (FieldInfo.hasTermVectors() is true); a field without term vectors gets the same message.
  • It is no rule about empty texts: labelled false the same document trains, and the bias -1.0 swaps the labels (run).
  • No javadoc states the expected outcome: a classifier, or a failure that names the document, are both defensible.
The full argument382 words
  • The message is misleading here. It reads term vectors must be stored for field text, and the field does store them: FieldInfo.hasTermVectors() is true and the document with a token has its term vector (run). Read for the one document the words hold, since no term vector was indexed for it; but the message names neither the document nor the cause, and a field without term vectors gets the same words (run), so the class does not tell the two cases apart.
  • It is not a rule about empty training texts. The same document trains when it is labelled false, and with the bias -1.0 the labels swap (run); a labelled document without the text field is passed over (BooleanPerceptronClassifier.java:148, run). The contrast between the labels is no contradiction in itself, since a correctly classified document does not reach the update. What it shows is that nothing here refuses empty texts as such.
  • No javadoc asks for a token in each training document. The class javadoc (:50-58), the constructor's javadoc with its one @throws sentence (:67-80: "if the building of the underlying FST fails and / or TermsEnum for the text field cannot be found"), the Classifier interface (its @throws sentences say "If there is a low-level I/O error."), package-info.java and overview.html state no condition on the text of a training document.
  • The module's precedent is to pass irregular training documents over. LUCENE-5338 (#6402, fixed in 4.6): "Only labeled (with 'class' field) documents should be used during training and therefore each classifier should filter (and not fail when run against) them." The module's other code that works on a document's term vector, DocToDoubleVectorUtils, gets it as an argument and answers null for a null (DocToDoubleVectorUtils.java:47, :82). Both are about another input: precedents, not statements about a text without a token.
  • No test asserts the exception. No file under lucene/classification/src/test has expectThrows or IOException.class. Of the four tests of TestBooleanPerceptronClassifier, three train on fixed sentences and one on texts of twenty random strings of at most five letters each.
  • History. The check and the message came with the class (commit 05940e34ab8, 2013). Neither the commit nor its issue (LUCENE-4818, #5883) mentions a document without a token.
The devil's-advocate check192 words

The strongest case for "intended": the guard is deliberate and declared. It has been there since the first commit, the exception is the checked IOException of the constructor, the @throws sentence names a TermsEnum that cannot be found, and TermVectors.get documents null as "term vectors were not indexed", which is true of this document. A perceptron with a fixed bias cannot learn a positive example without features anyway, so refusing such a document is defensible, and the class is experimental.

Why it fails: on what the code does, not on a contract. The guard's own words name a field configuration, and that configuration is in place. The code has no policy of refusing such documents: it accepts the same document under the other label or the other sign of the bias (run). And doing what the message asks changes nothing, since the field already stores term vectors; the message names neither the document nor the cause. What stays of the argument limits the wording: this page does not say that the constructor must return. Keeping an exception whose message names the document is as defensible as passing the document over (Suggested fix).

  • It decides the open question. The classifier is then built although one labelled example taught it nothing: with a fixed positive bias it still answers false for an empty text (run).

How it was found

#

Semi-formal: a sweep, then a bounded-exhaustive comparison. Texts that an analyzer turns into no token were given to the classes that consume analysis output, and this constructor threw. The real class was then compared with a reference perceptron over 419,424 training configurations per run: in each, the exception came exactly when a tokenless document was misclassified at its turn.

The method in full364 words

Method: semi-formal (a differential sweep witnessed by running, then a bounded-exhaustive comparison of the real class with a reference; a strict reading that goes by the first signal alone would call it non-formal). No model-checking, SMT or proof tool was involved.

  • Signal. The consumers of an analysis that yields no token were being compared. One cell of that sweep gave this exception: a stop-word-only document under EnglishAnalyzer as one more training document. It was widened to an empty text and !!! under StandardAnalyzer.
  • Bounded comparison. The real class against a reference perceptron in which a text without a token has the empty feature vector: each training sequence of 1 to 4 documents drawn from 8 kinds of document (five texts with tokens, the empty text, !!!, a document without the text field) and 2 classes (69,904 training sets), batch size 1 and 2, bias automatic, 2.0 and -1.0: 419,424 configurations per run, on builds of branch_11x and main and on the 10.6.0 jars, each with assertions on and off. The rule "thrown if and only if a document that has the field and no token is misclassified at its turn" predicts the real class in each configuration of the six runs (163,920 throw it; the 9,324 without a token in any document throw the constructor's other message; 0 mismatches). The naive rule "a document without a token throws", planted in one run, gives 110,640 mismatches. The run was repeated for this page on main f6e694652c3d, with the same counts.
  • Reduction. The case was reduced to one JUnit test with two documents and one constructor call.
  • Met before, unread. An earlier property test of the classifiers had met this exception and counted each IOException of the constructor as expected without reading the message. Re-run with the two messages counted apart (5,000 cases each, on a build of branch_11x), 448 of 5,000 cases in one mode and 1,500 of 5,000 in the other end in this message.
  • Other findings on the same class, each with another line and another fix: LFV-395 (the order in which weights reach the FST), LFV-680 (a batch size above 1 loses updates), LFV-684 (the training filter is scored).
