(Graph quality) A merge that starts from an existing HNSW graph can leave live documents out of reach of a graph search that starts at the graph's entry node: the repair of a node that lost some of its neighbours to deleted documents searches from its surviving neighbours only, so a group whose other links went through deleted documents can stay cut off; in the test the segment before the merge and a merge that builds the graph from scratch return the two documents (10.4.0 to 10.6.0, with the default codec from 10.5.1; branch_11x and main)

Graph quality only: nothing is lost, corrupt or thrown; approximate kNN search promises no recall. A merge that starts from an existing HNSW graph can leave live documents unreachable from the graph's entry node: in the test a document's own vector no longer finds it after one delete and forceMerge(1).

The finding in 30 seconds

#

The limits first; each is in the list below. It is graph quality only. It needs a merge that starts from a segment's existing graph, and a group of nodes that the rest of the graph reaches only through documents that are then deleted. On drawn data there is one measurement, not replicated; on real embeddings none.

The limits, each of them

#
  1. Graph quality only. Nothing is lost, corrupt or thrown, and no wrong document is returned (the test's query returns the nearest two live documents that the graph's entry node reaches; the two nearer ones are missing). Approximate kNN search promises no recall: its results "are not guaranteed to be the true k closest neighbors" (KnnVectorsReader#search). A search that scores every vector still returns the documents.
  2. "Out of reach" means out of reach of a graph search that starts at the graph's entry node, where KnnFloatVectorQuery starts. A graph search that is given other start nodes can still arrive: on the test's index after the merge, the experimental SeededKnnVectorQuery with a seed query that matches A returned [A, B].
  3. It needs a merge that starts from a segment's existing graph. A merge can when the deleted share of that graph's vectors, rounded down to a whole percent, is at most 40 (IncrementalHnswGraphMerger.java:133-135 at main b5a4546a5964: int deletePct = ((graphSize - candidateVectorCount) * 100) / graphSize; and if (deletePct <= DELETE_PCT_THRESHOLD, with the constant 40), the segment's reader offers a graph (:113-118) and the format builds one for the merged field. With the default codec a merge starts from an existing graph from 10.5.1 on; on 10.4.0 and 10.5.0 only when the codec returns an HNSW vectors format directly.
  4. It needs a group of nodes that the rest of the graph reaches only through documents that are then deleted. In the three built layouts whose links were printed (1, 4 and 16 dimensions), every link between the group and the rest goes through one document, which is deleted.
  5. Drawn data: one measurement, not replicated. On drawn Gaussian clusters without repeated vectors (150 one-segment indexes per dimension, 3 to 35 percent deleted; run on branch_11x 75eea467ac52), the indexes with nodes that the graph's entry node does not reach, after the merge against after a rebuild of the surviving documents: 59, 16 and 6 against 0 at 2, 4 and 8 dimensions (0 before the deletes); 24 against 14 at 16 dimensions (21 before the deletes); no clear excess at 32 and 64 dimensions (96 against 94 and 130 against 135; 111 and 142 before the deletes). Graphs built from scratch have such nodes at 16, 32 and 64 dimensions too.
  6. No measurement on real embeddings was made. No rate for real embeddings, large segments or natural merge schedules was measured or is claimed.
  7. A maintainer's public view. That an HNSW graph can hold documents that a search from its entry node cannot reach is on public record upstream, and a maintainer wrote on #14214 on 2026-02-20 that "there can be indexed documents that are impossible to return for any query" and that this is "statistically speaking ... not a problem" (the full sentence is under Prior reports).

The finding, step by step

#
  1. Index 703 documents with a one-dimension vector, default codec, one segment: A at -10, B at -11, C at 0 and 700 more at 10 to 709. In that segment's graph every link between the pair A, B and the rest goes through C.
  2. Delete C. A KnnFloatVectorQuery with A's own vector and k = 2 returns [A, B], 0 and 1 away: the search still walks through the deleted node.
  3. Call forceMerge(1). The merge starts from the segment's graph, drops C and repairs the nodes that lost neighbours beyond a threshold. You expect [A, B] again, as before the merge and as a merge that builds the graph from scratch returns.
  4. Instead the query returns the documents at 10 and 11, 20 and 21 away. A's repair searched only from its one surviving neighbour, B, so A and B now link to each other alone: a search from the graph's entry node reaches 700 of 702 nodes.
  5. Nothing is lost: a search that scores every vector returns [A, B] first. No exception, the same with assertions on and off.

Who is affected

#

Indexes whose vector segments are merged starting from an existing graph: the default codec from 10.5.1. Shown on built layouts where deleting one document cuts a group off. On drawn data one measurement, not replicated, found an excess over a rebuild at 2, 4, 8 and 16 dimensions and no clear one at 32 and 64. On real embeddings none.

What happens. You index 703 documents with a one-dimension vector on a line (A at -10, B at -11, C at 0, 700 more at 10 to 709) with the default codec, delete C and call forceMerge(1). Before the merge a KnnFloatVectorQuery with A's own vector and k = 2 returns [A, B]; you expect the same after the merge, and a merge that builds the graph from scratch gives it. Instead the query returns the documents at 10 and 11, 20 and 21 away. The merge starts from the segment's graph, drops C and repairs the nodes that lost neighbours beyond a threshold. The repair of a node that still has neighbours searches only from those neighbours (HnswGraphBuilder.java:752-762 at main b5a4546a5964; the javadoc of fixDisconnectedNodes states the step), so A, whose one surviving neighbour is B, finds only the pair. No pass that links separate parts of the graph runs afterwards: finish() has its connectComponents() call commented out under a TODO that names #14214 (:583-589). The level rebalancing that follows the repair can link a node that it promotes to an upper level; in the test it promotes none. A and B end linked to each other alone, and no search that starts at the graph's entry node arrives at them. A search that scores every vector still returns [A, B] first. The 10.6.0 release does the same.

The credits are part of the finding. The change that introduced the repair, #15003, describes the step (a graph search that starts from the node's existing neighbours), and its thread mentions disconnectedness after singleton merges. That an HNSW graph can hold documents that a search from its entry node cannot reach is on public record upstream (#12627, #13566, #14436, #14214, an issue that was open when read on 2026-11-23, with its comments of 2026-02-17 and 2026-02-20, #16529). What is new here is the cause that is named (where the repair search starts) and that the repair of a merge that starts from an existing graph can leave a cut-off part.

Terms

#
  • Graph search. An HNSW graph has a few levels. A search starts at one entry node on the top level, moves to the closest node it can reach there, drops a level and repeats; on level 0 it collects the k best nodes it can reach by following links. A node that no chain of links leads to cannot be returned by it.
  • Out of reach. On this page: no chain of links leads from the graph's one entry node to the node, over every level. KnnFloatVectorQuery starts its graph search at the entry node (HnswGraphSearcher.java:218). The experimental SeededKnnVectorQuery starts at the documents that a seed query matches instead (search/SeededKnnVectorQuery.java:31-56, SeededHnswGraphSearcher.java:74-77): on the test's index after the merge it returned [A, B] with a seed query that matches A and [r0, r1] with one that matches r500 (main b5a4546a5964, branch_11x 262e019500ec and 10.6.0, assertions on and off).
  • A search that scores every vector. KnnFloatVectorQuery with k not smaller than the number of vectors makes the reader score each vector instead of walking the graph (codecs/lucene99/Lucene99HnswVectorsReader.java:372-385). It is the comparison for "the documents are still there".
  • A merge that starts from an existing graph. Instead of building the merged segment's graph from scratch, the merge copies the graph of one source segment without its deleted nodes, repairs it, and adds the other segments' vectors. The merge log says which happened: build graph from merging 1 graphs of 702 vectors against build graph from 702 vectors.

The mechanism (main b5a4546a5964, files under lucene/core/src/java/org/apache/lucene/util/hnsw/)

#

Step 1. When a merge starts from an existing graph. A source segment counts only when its reader offers a graph that is not empty (IncrementalHnswGraphMerger.java:113-118), and the default format builds a merged graph only when the field has enough vectors (codecs/lucene99/Lucene99HnswVectorsWriter.java:452-453, :712-722). IncrementalHnswGraphMerger.addReader keeps, as the start of the merged graph, the source graph with the most live vectors among those whose deleted share, as a whole-number percentage, is at most 40 (:133-138; DELETE_PCT_THRESHOLD = 40 at :65; at the 10.6.0 tag :138-143 and :66). The division rounds down, so a graph with fewer than 41 percent deleted qualifies; the constant's javadoc says "more than 40%" (:62-63):

   int deletePct = ((graphSize - candidateVectorCount) * 100) / graphSize;

   if (deletePct <= DELETE_PCT_THRESHOLD
       && (largestGraphReader == null
           || candidateVectorCount > largestGraphReader.liveVectorCount)) {
     largestGraphReader = graphReader;
   }

Step 2. The copy and the flag rule. InitializedHnswGraphBuilder copies the graph without the deleted nodes and flags a node whose loss of neighbours crosses a threshold: it kept less than 0.85 of its neighbours, or it lost one and fell below half of the level's connection budget (InitializedHnswGraphBuilder.java:381-385, :79, :88; at the 10.6.0 tag :383-385). A node that lost no neighbour is not flagged.

Step 3. The repair of a flagged node (HnswGraphBuilder.java:752-762; at the 10.6.0 tag :771-781):

   // Use all existing neighbors as entry points for search
   if (entryPoints.length > 0) {
     // Search from entry points to find candidate neighbors
     graphSearcher.searchLevel(candidates, scorer, level, entryPoints, hnsw, null);
     popToScratch(candidates, scratchArray);
     // Add diverse neighbors using HNSW heuristic (prunes similar neighbors)
     addDiverseNeighbors(level, node, scratchArray, scorer, true);
   } else {
     // Node has no neighbors, add connections from scratch
     addConnections(node, level, scorer);
   }

entryPoints is a copy of the node's surviving neighbours (:734-750). A flagged node that still has neighbours searches from those neighbours only; only a node with none goes through addConnections, which descends from the graph's entry node (:786-798). The javadoc of fixDisconnectedNodes states the step (:698-709 at main b5a4546a5964, :717-728 at the 10.6.0 tag): "Fixes disconnected nodes at a specific level by performing graph searches from their existing neighbors to find additional connections." and "A node with no neighbors is instead connected from scratch via {@link #addConnections}."

Step 4. No pass that links separate parts of the graph runs afterwards. finish() (HnswGraphBuilder.java:583-589; the commented-out call at :587, at :606 at the 10.6.0 tag, at :585 at branch_11x 262e019500ec):

   void finish() throws IOException {
     // System.out.println("finish " + frozen);
     // TODO: Connect components can be exceptionally expensive, disabling
     //  see: https://github.com/apache/lucene/issues/14214
     // connectComponents();
     frozen = true;
   }

One step after the repair can add links: when the graph had deletes, rebalanceGraph() runs (InitializedHnswGraphBuilder.java:309-314, :434-484). For an upper level that has fewer nodes than its target it promotes nodes from the level below and links each promoted node on that level by a descent from the entry node (:476), so a member of a cut-off group that is promoted can be linked to the rest there. In the test it promotes no node: the upper levels have 56 and 2 nodes before and after the merge, and the targets for 702 nodes and the default M = 16 are 43 and 2.

Why it looks unintended

#
  • No javadoc is broken: approximate search promises no recall. What is measured is one kind of merge against the segment before it and against a from-scratch merge.
  • The repair's stated purpose: such nodes "need additional connections to maintain graph connectivity and search performance".
  • A recall loss of this repair pass against a rebuild was handled as a bug before (#16552).
The full argument354 words

No contract is broken, and this page does not say one is.

  • KnnVectorsReader#search (codecs/KnnVectorsReader.java:102-104 at main b5a4546a5964): "The search is allowed to be approximate, meaning the results are not guaranteed to be the true k closest neighbors. For large values of k (for example when k is close to the total number of documents), the search may also retrieve fewer than k documents."
  • The javadoc of fixDisconnectedNodes states the step itself: "performing graph searches from their existing neighbors" (util/hnsw/HnswGraphBuilder.java:698-699).

What is cited is the repair's stated purpose, and one merge path against the other.

The devil's-advocate check453 words

The strongest case for accepted behaviour. Approximate search promises no recall. The step is documented. The pass that links parts of a graph was switched off on purpose for its cost (#14436, the TODO that names #14214). On #14214 one maintainer wrote on 2026-02-17 that the issue is fixed by disabling the pass, and another on 2026-02-20 that indexed documents that are impossible to return for any query are "statistically speaking ... not a problem". On #16529 (2026-08-29): "if they typically cleave into one massive one, and a few tiny pebbles --> acceptable?" The change that introduced the repair measured a recall change of 0.00 to -5.15 percent against its baseline before it was merged (#15003, table of 2025-11-07). The merger's own javadoc says that graphs above its threshold "may have degraded connectivity". Lucene's own tests skip graphs that are not rooted, and its index check accepts such a graph: on main and branch_11x CheckIndex counts, level by level, the nodes that the entry node reaches, prints the count and does not treat it as an error (index/CheckIndex.java:3070-3077); on the test's index after the merge it prints level 0: 702 nodes, 700/702 connected and reports the index as clean (the 10.6.0 release has no such check). On drawn data (one measurement, not replicated) there is no clear excess over a rebuild at 32 and 64 dimensions, and the test's line is a built layout.

How far it holds. Fully for the class: that is why this finding is listed as graph quality, at the lowest priority tier, and not as a wrong result. An executed second opinion voted that it is not a defect on this ground ("the asserted search result and universal connectivity are not contractual guarantees") while it reproduced every fact with a test of its own.

No javadoc of the util.hnsw, codecs.lucene99 and codecs.hnsw packages and no line of CHANGES.txt or MIGRATE.md at main b5a4546a5964 that a search by key word found says that a merged graph can hold nodes its entry node does not reach; that HNSW graphs can hold such nodes is on public record in #14214 and #16529, and the index check makes them visible. Suggested fix

#

No patch is proposed. A shape that was tried: seed the repair search of a node that still has neighbours also from where a search from the graph's entry node arrives. With it the test passes, assertions on and off, and the core module's tests (8,967) show no failure. No cost was measured. The maintainers choose the form.

The shape that was tried: seed the repair search also from the entry node's side

In fixDisconnectedNodes, in the branch for a node that still has neighbours, descend from the graph's entry node through the upper levels, keeping the best candidate of each, and add the node that is reached on this level to the entry points of the repair search. Registry title
(Graph quality) A merge that starts from an existing HNSW graph can leave live documents out of reach of a graph search that starts at the graph's entry node: the repair of a node that lost some of its neighbours to deleted documents searches from its surviving neighbours only, so a group whose other links went through deleted documents can stay cut off; in the test the segment before the merge and a merge that builds the graph from scratch return the two documents (10.4.0 to 10.6.0, with the default codec from 10.5.1; branch_11x and main)
Area
core / util.hnsw: merge-time reuse of an HNSW graph with deleted vectors (the repair of nodes that lost neighbours)
Priority
Low, rank 1131: Graph quality only: a merge that starts from a segment's existing HNSW graph, which the default codec does since 10.5.1, can leave live documents out of reach of a graph search that starts at the graph's entry node when the documents that linked them to the rest were deleted; in the test a kNN query with a live document's own vector no longer returns it after one delete and forceMerge(1), while a search that scores every vector still does; nothing is lost, corrupt or thrown. It is Low because approximate search promises no recall, a maintainer has written in public that 'there can be indexed documents that are impossible to return for any query' and that 'statistically speaking, it's not a problem' (#14214, 2026-02-20), and on drawn data (one measurement, not replicated) an excess over a rebuild was found at 2, 4, 8 and 16 dimensions and no clear one at 32 and 64 (96 against 94 and 130 against 135 of 150 indexes). What speaks for listing it at all: on the built layouts the merge did worse than a rebuild of the same documents in the default configuration of released versions (default codec since 10.5.1), it did so silently, the pair was still cut off after a later merge that started from that graph in the three runs made, and one deleted document suffices on a built layout at each dimension run (1 to 768). No measurement on real embeddings was made.
Impact class
minor
Impact note
Graph quality of an approximate index: after a merge that starts from an existing graph, a graph search that starts at the graph's entry node (the search of a kNN query without a seed) can miss the live documents of a cut-off group; no wrong document is returned (the query returns the nearest live documents that the entry node reaches; the nearer ones of the cut-off group are missing), nothing is lost or corrupt (a search that scores every vector returns them) and nothing is thrown. Summary
Graph quality only: nothing is lost, corrupt or thrown, and approximate kNN search promises no recall. When a merge starts from a segment's existing HNSW graph (it can when the deleted share of the graph's vectors, rounded down to a whole percent, is at most 40) it drops the deleted nodes and repairs the nodes whose loss of neighbours crosses a threshold, and you expect a kNN query to keep finding the live documents it found before the merge and that a merge building the graph from scratch finds. Instead the repair of a node that still has neighbours searches only from those neighbours, so documents whose other links all went through deleted documents can end up linked to each other alone: in the test (703 documents with a one-dimension vector on a line, the default codec, ONE document deleted, forceMerge(1)) a query with a live document's own vector and k = 2 returns two other documents, 20 and 21 away, and neither that document (distance 0) nor its neighbour (distance 1), although both came first before the merge and a search that scores every vector still returns them first; the 10.6.0 release does the same, so it is not new in 11. Credits: the change that introduced the repair, #15003, describes the step (a graph search that starts from the node's existing neighbours) and its thread mentions disconnectedness after singleton merges; that an HNSW graph can hold documents that a search from its entry node cannot reach is on public record upstream (#12627, #14214), and a comment on #16529 says that the fixing of disconnected components during merging was reverted and never restored; none of these four items says, in its description, comments, reviews or inline comments as read on 2026-11-23 (#12627, whose last comment is of 2024, was searched by key words and read at each match), that the repair as merged can still leave a group of live documents cut off, or names where its search starts as the cause.
