The Lucene90TermVectorsFormat javadoc describes three parts of the .tvd chunk as the opposite of what Lucene writes

The default term-vectors format's javadoc contradicts the .tvd bytes three times: the Flags bit is inverted, field numbers are called delta-encoded but are stored plain, and AvgCharsPerTerm is called absent without positions but is written whenever a field has offsets. Documentation only: in normal indexing Lucene's writer and reader agree.

The finding in 30 seconds

#

The javadoc that documents the default term-vectors data file says three things about each chunk that the writer does the opposite of.

Background: a term-vector chunk

#
  1. Term vectors store, per document and field, the field's terms with their frequencies and, if enabled, positions, offsets and payloads. The default format buffers documents and writes them in chunks to the .tvd file; the .tvx index points at each chunk.
  2. A chunk starts with a small header: the first document, the document count, the number of fields per document, the field numbers present, which field each entry belongs to, and the Flags (positions, offsets, payloads) of the fields. Terms, frequencies, positions, offsets and the compressed term bytes follow.
  3. The class javadoc of Lucene90TermVectorsFormat gives this layout as a grammar plus notes, and the default codec's file-format overview links it as the term-vector format. Lucene's own writer and reader do not read the javadoc; in normal indexing they agree with each other.

The finding, step by step

#
  1. You index one document with one term-vector field (f = "x") with the default codec, and decode the one chunk of the 84-byte _0.tvd by following the Lucene90TermVectorsFormat javadoc, the format description the default codec's file-format docs link to.
  2. The javadoc says the Flags Bit is 1 when every field has the same options in every document of the chunk (then one Flag per distinct field follows). One field in one document trivially qualifies, so you expect 1.
  3. Byte 56, the Flags Bit, is 0. The writer writes 0 for "same options" and 1 for "options change" (then one Flag per field instance), and Lucene's own reader agrees with the writer.
  4. Two more statements are wrong the same way: field numbers 1, 3, 6 are stored as 1, 3, 6, not as deltas (summed: 1, 4, 10); and offsets-only fields get AvgCharsPerTerm values the text says are absent (read without them, start offsets 3, 5, 7 come out as -1, -1, -1).
  5. In normal indexing Lucene reads its own files correctly. Only a person or tool decoding .tvd from the javadoc is misled, in every release since 4.2.0 (2013).

Who is affected

#

People who read or re-implement the .tvd format from this javadoc. Contradicted by every chunk with term vectors (Flags), any chunk with two or more term-vector field numbers above 0 (FieldNums), and any chunk where some field has offsets and none has both positions and offsets (AvgCharsPerTerm). In normal indexing Lucene's writer and reader agree, so Lucene itself is unaffected.

Mechanism, terms and numbers841 words

The class javadoc of Lucene90TermVectorsFormat, the term-vectors format of the default codec, presents itself as "a more detailed description of the field data file format" (Lucene90TermVectorsFormat.java:80 on main 645d4fe14a20), and the default codec's file-format overview links it as the term-vector format. Three of its statements say the opposite of what Lucene90CompressingTermVectorsWriter writes and Lucene90CompressingTermVectorsReader reads: the Flags Bit is documented as 1 for "fields have the same options" (:90-92, :125-126) but the writer writes 0 for that and 1 otherwise (writer :519-534); FieldNums are documented as "a delta-encoded list" (:89, :119-120) but are the plain sorted field numbers (writer :466-478); and AvgCharsPerTerm is documented as absent "if no field has both positions and offsets enabled" (:143-144) but is written whenever any field of the chunk has offsets (writer :629, :643-657). In normal indexing the reader matches the writer on all three, so the wrong text breaks nothing at runtime (their one known disagreement, on the AvgCharsPerTerm condition, is the separate code bug LFV-244). The text came with LUCENE-4733 in 2013 for a writer that already did all three things the way it does today, and it has been in every release from 4.2.0 to 10.6.0 and on main.

The other two, as executed

#
  • FieldNums: term-vector fields with field numbers 1, 3 and 6 are stored as [1, 3, 6]; delta-decoding as the javadoc says gives [1, 4, 10].
  • AvgCharsPerTerm: a document with three fields that have offsets but no positions (x at 3-4, y at 5-6, z at 7-8). The javadoc says no AvgCharsPerTerm values are present; the file holds three 4-byte values. Decoding without them gives start offsets [-1, -1, -1]; skipping them gives the indexed [3, 5, 7].

Mechanism

#
  • flushFlags sets nonChangingFlags when every field number has the same flags in every document of the chunk (writer :502-517), then writes writeVInt(0) with the comment "write one flag per field num" (:520-531), else writeVInt(1), "write one flag for every field instance" (:532-545). The reader's case 0 reads one Flag per distinct field and expands it per field instance (:447-458); case 1 reads one per instance (:459-461).
  • flushFieldNums writes a token byte (min(n - 1, 7) << 5) | bitsRequired(max) (:466-468), a VInt when n - 1 >= 7 (:469-471), then writer.add(fieldNum) for each sorted distinct field number (:472-478). The reader assigns fieldNums[i] = (int) it.next() (:435).
  • flushOffsets sets hasOffsets |= fd.hasOffsets over every field instance (:629), returns only when no field has offsets (:643-646), and writes one Float.floatToRawIntBits(charsPerTerm[i]) per distinct field (:655-657). The reader reads them when TotalOffsets, the sum of term frequencies of fields with offsets, is > 0 (:553-566, :589-594). In normal indexing a term-vector field with no terms is not written (TermVectorsConsumerPerField.java:70), so the two conditions agree; they are shown to differ for a zero-term field from addIndexes(CodecReader...), the separate code bug LFV-244 (other ways to hand the writer a zero-term offsets field were not ruled out exhaustively).
Exposure and likelihood260 words
  • Who is hit. Anyone who decodes a .tvd file without Lucene, or checks a codec change against the description, by following the class javadoc. The default codec's overview (lucene104/package-info.java) says it "defines the index file formats used in this version of Lucene" (:50), links this class for term vectors (:168, :293, :298) and says "Details on each of these are provided in their linked pages" (:188).
  • Default vs opt-in. The default codec writes this format (Lucene104Codec.java:71); term vectors are opt-in per field. Which chunks contradict which statement: Flags, every chunk that holds term-vector fields (a chunk with none writes no Flags, writer :401-403); FieldNums, any chunk with two or more distinct term-vector field numbers above 0 (with one field, or field 0 and one other, the plain list and its delta encoding are the same bytes, as in the minimal repro's chunk); AvgCharsPerTerm, any chunk where some field has offsets and no field has both positions and offsets, e.g. one whose term-vector fields have offsets but no positions, a documented option that BaseTermVectorsFormatTestCase exercises (Options.OFFSETS).
  • Scale. The wrong text itself has no runtime effect. A parser that follows the text reads the Flags with the wrong layout, sums plain field numbers as deltas, and loses alignment on chunks with offsets but no positions (all executed). The audience is small and no earlier report was found in the recorded searches, which keeps the impact minor.
  • Rating. Impact class minor, likelihood plausible, priority low.

Why it looks unintended

#
  • The javadoc states bit-level facts (if Bit==1: Flag^TotalDistinctFields), and the writer does the reverse; its own comments say "one flag per field num" for 0.
  • It never matched: the writer it describes was committed 12 days earlier with today's encoding for all three points.
  • "High-level" and @lucene.experimental allow omissions and future changes, not a wrong description of the current bytes.
The full argument178 words
  • Inverted, not simplified. if Bit==1: Flag^TotalDistinctFields and "when true means that fields have the same options" (:91-92, :125-126) state the opposite of the writer, whose comments read "write one flag per field num" for 0 (:520) and "write one flag for every field instance" for 1 (:533).
  • Wrong from the start. LUCENE-4599 (5837fe83bd8, 2013-01-21) wrote the writer; LUCENE-4733 (94b17a28de5 / e3710747d87, 2013-02-02) added the description; the writer file is byte-identical between the two, so the text never described a committed encoding. Not a regression.
  • The page presents itself as the detailed description: "Here is a more detailed description of the field data file format" (:80); the default codec's overview sends readers there for the details (package-info.java:50, :188).
  • Precedent. LUCENE-713 (#1788, 2006, "File Formats Documentation is not correct for Term Vectors") fixed an error in the old term-vector format docs; #129 (2021) re-synced this javadoc with a format change. No test, CHANGES or MIGRATE entry or discussion calls these statements known or non-normative.
The devil's-advocate check221 words

Strongest case for "intended" (the devil's-advocate verifier and the cross-model reviewers): the overview "attempts to provide a high-level definition of the Apache Lucene file formats" (package-info.java:54); the class is @lucene.experimental (Lucene90TermVectorsFormat.java:164); the description is incomplete anyway (no FieldNums token byte, no DirectWriter slice length prefixes, no dirty bit in ChunkDocs), so nobody could write a reader from it alone; the author of #130 remarked that "few people care about the format documentation"; and in normal indexing the writer and reader agree. The refute-lens reviewer rated this moderate, for the encoding only.

Why it fails: "high-level" covers leaving details out, not a statement whose polarity is inverted. @lucene.experimental permits incompatible future changes, "not inaccurate documentation of the current release" (the intended-lens reviewer, who rated the argument weak). "Few people care" explains why nobody noticed; it does not make the text right. Writer/reader agreement in normal indexing is why this is a documentation defect, not a code bug (their one known disagreement, LFV-244, is a separate code bug). The incompleteness argument does shape the claim: it is only that these three statements are wrong, not that a reader built from the javadoc must fail. The reproducer, the devil's advocate and the adjudication all kept the defect, and the separate re-runs of the finder's test for the cross-model reviews failed.

How it was found

#

Code reading: while a file:line table was written for an SMT (Z3) model of the term-vector offsets encoding, the javadoc read next to the writer showed three mismatches; one written chunk was then parsed byte by byte to confirm them. The model encodes the code, not the javadoc, so it gave no signal itself.

The method in full126 words
  • The hunt unit modelled the term-vector offsets encoding of the default format in Z3 and listed, for each modelled step, the code line it came from. Reading the javadoc next to the writer for that table showed the three statements.
  • The finder's JUnit indexes one document with three fields that have offsets but no positions (one term each), parses the single .tvd chunk byte by byte and checks all three statements; its implicit control is that skipping the AvgCharsPerTerm values decodes the indexed start offsets [3, 5, 7]. It failed on main with assertions on and off, on 10.5.2 and on 9.12.3.
  • This is a documentation check against real output, not model checking or a proof: the formal model gave no signal on the javadoc.

LFV-255, snapshot of 2026-11-10

Registry title
The file-format javadoc of the default term-vectors format (Lucene90TermVectorsFormat) contradicts the .tvd bytes in three places: the Flags bit meaning is inverted, FieldNums are called delta-encoded but are the plain field numbers, and AvgCharsPerTerm is called absent without positions but is written whenever a field has offsets (documentation defect; the writer and reader agree)
Area
codecs / term vectors (Lucene90TermVectorsFormat .tvd file-format javadoc vs Lucene90CompressingTermVectorsWriter / Reader)
Priority
Low, rank 1380: The default term-vectors format javadoc contradicts the .tvd bytes while the writer and reader agree, a documentation-only defect for format re-implementers.
Impact class
minor
Impact note
Documentation only: in normal indexing Lucene's writer and reader agree and round-trip exactly, so indexing, merging, CheckIndex and term-vector retrieval are unaffected by the wrong text (their one known disagreement, on a zero-term field from addIndexes, is the separate code bug LFV-244); the people misled are those who read, inspect or re-implement the .tvd format from the javadoc of the default term-vectors format (the default codec's package docs link to it as the format description), and a parser that follows the text reads the Flags with the wrong layout, sums plain field numbers as deltas and loses alignment on chunks with offsets but no positions (all executed); the text has been in every release since 4.2.0 (2013), no scale or special setting is needed.
Summary
You decode a .tvd chunk of the default term-vectors format by following its javadoc, which says the Flags Bit is 1 when all fields of the chunk have the same options, that FieldNums is a delta-encoded list, and that AvgCharsPerTerm is absent unless some field has both positions and offsets. The writer does the opposite on all three: it writes 0 for 'same options' (then one flag per distinct field) and 1 otherwise, it stores the plain sorted field numbers (fields 1, 3, 6 are stored as 1, 3, 6, which summed as deltas give 1, 4, 10), and it writes one AvgCharsPerTerm value per distinct field whenever any field has offsets, so a parser built from the text misreads the chunk. Lucene's own reader matches the writer, so nothing breaks at runtime; only the documentation is wrong, and it has been since it was written in 2013.
