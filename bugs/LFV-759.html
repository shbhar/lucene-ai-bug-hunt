IndexWriter accepts doc-values updates of a field that a custom index sort reads, so a segment can fall out of its declared order

IndexWriter refuses in-place doc-values updates of the index-sort field, but not of another field a custom sort key reads (here price, behind a BinarySortField subclass). The segment then keeps its old order under the declared sort: CheckIndex rejects it, sorted searches return a wrong top hit, merges carry it on.

The bug in 30 seconds

#

IndexWriter refuses doc-values updates of fields "involved in the index sort", because the segment would fall out of its declared order. It takes those fields from each sort field's declared name only. A custom sort key may read other fields: BinarySortField's javadoc invites keys "from the stored bytes and/or other doc-values fields of the segment".

  1. You sort the index with a BinarySortField subclass whose key is the numeric field price, ties broken by sku, the field it is declared on; its javadoc allows keys read from other doc-values fields. You add a (price 5), b (7) and c (8): the segment stores them as a, b, c.
  2. You set c's price to 1 with updateNumericDocValue. You expect IndexWriter to refuse, as it refuses an update of sku ("cannot update docvalues field involved in the index sort"), or the order to become c, a, b.
  3. Instead the update is accepted: the guard knows only the declared name sku. The documents stay a (5), b (7), c (1), and the segment still declares the sort.
  4. A top-1 search sorted by the index sort returns a, not c: it trusts the stored order and compares nothing after b, the first document that cannot compete. CheckIndex at level 2 reports docID=1 sorts after docID=2; the default level 1 does not run that check.
  5. Add d (6) and run forceMerge(1): the merged segment stores a, d, b, c instead of c, a, d, b. It needs 3 documents and fails with assertions on or off. This form reproduces on 10.5.0-10.5.2 and main; the generic form (a custom IndexSorter that reads another field) on every release from 8.6.0 to 10.5.2 and main.

Who is affected

#

Applications with an index sort whose custom sort key reads a doc-values field other than the declared one (a BinarySortField subclass since 10.5.0, any custom getIndexSorter since 8.6.0) and that update that field in place. Default configurations are not affected. For those applications it is deterministic, needs 3 documents, and the misordered segment survives merges.

Mechanism, terms and numbers766 words

IndexWriter refuses in-place doc-values updates of a field "involved in the index sort", because the segment would then no longer be in its declared order. It decides which fields are involved from SortField#getField alone (IndexWriterConfig.java:512-513). Since LUCENE-9330 (8.6.0) a custom SortField#getIndexSorter can read any field, and since 10.5.0 BinarySortField's javadoc explicitly lets a subclass derive its key "from the stored bytes and/or other doc-values fields of the segment". An update of such a field is accepted. In the repro the key is (price, sku), declared on sku; a (5), b (7), c (8) are flushed in that order and updateNumericDocValue(id:c, price, 1) is accepted. The segment keeps the order a, b, c while still declaring the sort: CheckIndex at level 2 or higher reports segment has indexSort=<binary: "sku"> but docID=1 sorts after docID=2, a top-1 search sorted by the index sort returns a instead of c because it compares no document after the first non-competitive one, and after adding d (6) and forceMerge(1) the merged segment stores a, d, b, c instead of c, a, d, b. It is deterministic and needs 3 documents. This BinarySortField form fails on 10.5.0-10.5.2 and on main; the generic form (a custom IndexSorter that reads another field) fails on every release from 8.6.0 to 10.5.2 and on main. It needs an opt-in index sort with a custom sort key that reads another doc-values field, plus an in-place update of that field; default configurations are not affected.

Terms

#
  • Index sort: with IndexWriterConfig#setIndexSort, every flushed and merged segment stores its documents in that order and records the sort in its segment info. Searches and merges rely on the recorded order.
  • Custom sort key: since 8.6.0 a SortField supplies its own IndexSorter, which gets a LeafReader and so can read any field. BinarySortField (10.5.0) sorts by bytes; a subclass may override getSortKeyDocValues to derive the key from other doc-values fields, and registers a SortFieldProvider so the sort can be read back on merge.
  • In-place doc-values update: updateNumericDocValue, updateBinaryDocValue, updateSortedNumericDocValue, updateDocValues, tryUpdateDocValue and softUpdateDocument(s) change a document's doc values without reindexing it. The document keeps its position in the segment.

The bug

#
  1. setIndexSort accepts any sort field with an IndexSorter (IndexWriterConfig.java:506-510) and records the protected fields as SortField::getField only (:512-513). getIndexSortFields is documented as "Returns the field names involved in the index sort" (LiveIndexWriterConfig.java:417-420).
  2. Every update path rejects only those names, with "cannot update docvalues field involved in the index sort": IndexWriter.java:1965 (updateNumericDocValue), :2003 (updateBinaryDocValue), :2041 (updateSortedNumericDocValue) and :2098 (buildDocValuesUpdate, shared by updateDocValues, tryUpdateDocValue and softUpdateDocument(s)).
  3. In the repro the key reads price but is declared on sku (BinarySortField#getIndexSorter passes getSortKeyDocValues to the sorter, BinarySortField.java:178-182). The update of price is accepted, the documents do not move, and the segment still declares the sort.
  4. Code that trusts the declared order goes wrong. TopFieldCollector checks per segment whether the search sort is a prefix of the index sort and then, once the queue is full, compares no document after the first non-competitive one (TopFieldCollector.java:59, :93-104, :151-172; below the hit-count threshold, 1000 by default, it keeps counting hits without ranking them). MultiSorter merges segments on the rule "The documents for each incoming leaf reader must already be sorted by the same sort!" (MultiSorter.java:35-40). CheckIndex reports the first inversion (CheckIndex.java:1274-1282), at level 2 or higher only (:1114, :1146-1149).
  5. The writer can find the fields a sorter reads, and does so elsewhere: when a doc-values field is first indexed into a segment, IndexingChain#initializeFieldInfo calls validateIndexSortDVType for it (IndexingChain.java:1381-1385), which probes each sorter with an empty reader and type-checks whatever field it asks for (:1635-1727). The update guard does not use that.

The numbers

#

Key = (price, sku), declared on sku. Add c (8), a (5), b (7): the segment stores a, b, c. updateNumericDocValue(id:c, price, 1) is accepted, so docs 0, 1, 2 are a (5), b (7), c (1). CheckIndex level 1: clean, the sort check does not run; level 2: segment has indexSort=<binary: "sku"> but docID=1 sorts after docID=2. Top-1 sorted by the index sort: a, after reading the keys of docs 0 and 1 only; the same sort with FIELD_DOC appended, which is not a prefix of the index sort and compares every document: c. Add d (6) and forceMerge(1): the merged segment stores a, d, b, c; the declared order is c, a, d, b.

Exposure and likelihood309 words
  • Who. Applications that configure an index sort (opt-in) with their own sort key that reads a doc-values field other than the declared one, and that update that field in place: a BinarySortField subclass overriding getSortKeyDocValues (10.5.0+, @lucene.experimental), or any custom SortField#getIndexSorter (8.6.0+). The built-in sort fields read only their declared field, so this gap does not apply to them (on 10.5.x a BinarySortField's declared field was itself updatable, a separate gap fixed by #16565). Lucene's own tests derive keys only from the sort's own field (TestBinarySortField's MinValueSortField javadoc: "no companion field is needed").
  • Trigger. Deterministic once both conditions hold: an accepted update of such a field breaks the segment whenever it changes the key order of documents within that segment. Three documents show all three symptoms; no concurrency; assertions on or off. A SORTED_NUMERIC companion (for example the minimum of a multi-valued numeric field) is updatable too, through updateSortedNumericDocValue, which is on main and the 10.x branches but in no release yet (#16581, listed under 10.6.0).
  • Effect. Silent when written. Sorted top-k searches that early-terminate on the index sort return wrong top hits, searchAfter pages are wrong (bounded-exhaustive harness), and merges and later addIndexes write the disorder into new segments. CheckIndex at level 2 or higher reports the segment as broken; the default level 1 does not run the sort check. Documents are not lost, and filtered searches return only matching documents. A code fix does not repair segments that were already written, and a merge does not either (it carries the disorder forward); they have to be rewritten, for example by reindexing.
  • How rare. Registry likelihood "rare" (a judgement): an experimental extension point plus in-place updates of the field it reads; one public downstream subclass reads a companion field but shows no in-place updates of it, and nobody has reported this since 8.6.0.

Why it is a bug, not intended

#
  • setIndexSort promises the sort "for all (flushed and merged) segments", and getIndexSortFields "Returns the field names involved in the index sort".
  • BinarySortField's javadoc invites keys read from other doc-values fields; no javadoc says those fields must not be updated.
  • When indexing doc values, the writer already probes each sorter for the fields it reads; only the update guard ignores them.
The full argument290 words
  • Contracts. setIndexSort: "Set the Sort order to use for all (flushed and merged) segments" (IndexWriterConfig.java:504). getIndexSortFields: "Returns the field names involved in the index sort" (LiveIndexWriterConfig.java:417); a field the key is computed from is involved. The guard's own message says "involved in the index sort".
  • The guard's intent. LUCENE-7581 (#8632, 6.4.0) added it; its CHANGES entry reads "Lucene now prevents updating a doc values field that is used in the index sort, since this would lead to corruption" (lucene/CHANGES.txt:8683-8685), and in that issue a committer asked to "prevent changing any field involved in the index sort". In 2016 a sort could read only its own field, so a name check was complete. #16565 (10.6.0) extended it to updateBinaryDocValue: "Updating a sort field's doc values would make the persisted sort order inconsistent with the values, so it should be rejected up front".
  • The documented pattern. BinarySortField's class javadoc (BinarySortField.java:41-45) lets a subclass derive the key from "other doc-values fields of the segment"; getSortKeyDocValues (:149-158) restricts only the read pattern and the value lifetime. Neither BinarySortField, SortField#getIndexSorter, IndexSorter, SortFieldProvider, setIndexSort nor the update methods say that such fields must not be updated.
  • The inconsistency. IndexingChain#validateIndexSortDVType (IndexingChain.java:1635-1727) treats a field the sorter reads as part of the index sort: a devil's-advocate probe saw a BINARY price rejected under a sort that reads NUMERIC price ("expected field [price] to be NUMERIC"). The update guard does not. CheckIndex, Lucene's own checker, calls the result an error.
  • Tests. TestIndexSorting#testBadDVUpdate asserts the rejection for the declared sort field; no upstream test updates a field that a sorter reads, and none asserts that such an update is allowed.
The devil's-advocate check165 words

The devil's-advocate verifier and the cross-model reviews built the strongest case for "intended": BinarySortField and SortField#getIndexSorter are expert @lucene.experimental hooks (the IndexSorter interface and SortFieldProvider carry no such tag), a SortField exposes one field name, and the writer cannot know what an opaque sorter reads, so keeping companion fields stable is the extension author's job.

Why it fails: no javadoc states that rule; the writer can and does discover the fields a sorter reads (validateIndexSortDVType); the guard's stated intent covers "any field involved in the index sort"; and the outcome is a segment that Lucene's own CheckIndex rejects and that merges propagate, not a documented limitation. Every verifier rated the case at most moderate. Verdict: a defect. What remains is a point about the fix: upstream may prefer a documented rule, or an API for a sort field to declare the fields it reads, over probing; so state the expectation as "reject the update, or document that such fields must not be updated".

Suggested fix

#

Recommended Protect every field the sorters read (validated)

In IndexWriterConfig#setIndexSort, also protect every doc-values field that each sort field's IndexSorter asks an empty probe reader for, like the probe used when indexing doc values (+61/-4, one file). The repro passes with assertions on and off, and the full lucene/core suite passes. Best effort: a sorter that picks its fields from segment state escapes the probe.

for (SortField sortField : sort.getSort()) {
  fields.add(sortField.getField());
  try {
    sortField.getIndexSorter().getDocComparator(probe, 0);
  } catch (IOException | RuntimeException _) {
    // best effort: if a sorter fails here, fields it would read later are not recorded
  }
}
return Collections.unmodifiableSet(fields);

Protect every field the sorters read (validated) (validated by the checks) (recommended)

#

setIndexSort builds indexSortFields from each sort field's name plus every doc-values field its IndexSorter requests from an empty recording DocValuesLeafReader, a probe modelled on the one in validateIndexSortDVType: both call getDocComparator(reader, 0) on an empty doc-values reader, but that one type-checks a single field and throws from getFieldInfos(), while this one records every name requested and returns FieldInfos.EMPTY. Patch:, +61/-4 in IndexWriterConfig.java; updateNumericDocValue and updateDocValues of price are rejected, and the test checks the guard's message for updateNumericDocValue; an unrelated field stays updatable). The finder's earlier sketch (in the hunt folder) is the same logic.

for (SortField sortField : sort.getSort()) {
  fields.add(sortField.getField());
  try {
    sortField.getIndexSorter().getDocComparator(probe, 0);
  } catch (IOException | RuntimeException _) {
    // best effort: if a sorter fails here, fields it would read later are not recorded
  }
}
return Collections.unmodifiableSet(fields);

Trade-offs

  • Best effort: a sorter that chooses its fields from segment state (FieldInfos, maxDoc, values) escapes the probe, and so does any field a sorter would request after it throws on the empty reader (fields requested before the throw stay recorded); a point the cross-model reviewer raised.
  • Cost: each sorter runs once per setIndexSort, with maxDoc 0.
  • The probe calls getIndexSorter() a second time and swallows any RuntimeException it throws, which matters only for a stateful or side-effecting sorter.
  • getIndexSortFields() now returns an unmodifiable set instead of the Collectors.toSet() result (its mutability was never documented).
  • getIndexSortFields() returns more names, which matches its javadoc; a downstream caller of it (one exists in Solr's atomic-update code) would then protect those fields too.
  • The probe could be shared with validateIndexSortDVType instead of duplicated.

Let a sort field declare the fields it reads (not run)

#

For example a SortField method that returns Set.of(getField()) by default and that BinarySortField subclasses override; setIndexSort takes the union.

Trade-offs

Exact and cheap, with no probing. But a subclass that forgets to declare its companion field silently keeps today's behaviour, and it adds API to experimental classes.

Document the rule (not run)

#

State in BinarySortField, getSortKeyDocValues and SortField#getIndexSorter that fields a custom sort key reads must not be updated in place.

Trade-offs

No code change, but the silent misordering stays for anyone who misses the sentence, and CheckIndex at the default level does not catch it.

One "fields the index sort depends on" check for all known gaps (not run)

#

Combine the first or second option with open PR #16810's ensureNotIndexSortField (the sort taken from existing segments when the writer config has none) and with the reserved parent field (hunt row LFV-095), so that one check covers all three.

Trade-offs

Larger change across IndexWriter and IndexWriterConfig; #16810 is open and stale.

Downstream note

How it was found

#

A bounded-exhaustive model-based test ran every index-sort operation script of up to 4 steps (adds, deletes, updates, flushes, merges, addIndexes, reopen) in 26 configurations, 1,975,300 scripts, against an independent reference order. Every failure came from updating the field the key reads. The lead came from the hunt plan, so the test confirmed a suspected gap.

The method in full193 words

Method: bounded-exhaustive model-based testing on the real jar (semi-formal tier).

  • Operations: add, delete first or last, update of the sort field, update of the field the derived key reads, flush, forceMerge(1), addIndexes of a sorted reader, addIndexes(SortingCodecReader.wrap(unsorted)), and commit plus reopen. Every script of length 4 or less, in 26 configurations (default and derived keys, missing first or last, reverse, two multi-field sorts, search only).
  • Oracle after every step: an independent reference order, checked against each segment's physical order, CheckIndex's sort check, top-k with and without the index-sort shortcut, searchAfter pages and the comparator axioms.
  • Result: 1,975,300 scripts and 7,769,228 steps with assertions off; every failure, and only failures, in scripts that update the companion field. The shortest counterexample was minimised into a JUnit.
  • The hypothesis was a planning lead (an unexecuted lead from an earlier unit), so the harness confirmed and pinned down a suspected gap; it was not a blind find. Found 2026-10-27 on main a9779ef3c193; then checked by an independent reproducer, a devil's-advocate verifier, reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a follow-up (history, prior reports, security), the registration check and an audit.

History

#

Introduced in 8.6.0 by LUCENE-9330 (2020), which made index sorting pluggable but kept the update guard keyed on the declared field. BinarySortField (10.5.0, #16202) first documented keys read from other fields. Executed: fails on all 49 releases from 8.6.0 to 10.5.2 and on main; 8.5.x cannot express it.

Versions tested5 rows

Introduced by LUCENE-9330 (#10370), apache/lucene-solr#1440 "Make SortFields responsible for index sorting and serialization" (@romseygeek, approved by @jpountz), merged 2020-05-22 as ad0cefb8ec2 on branch_8x (first released in 8.6.0) and de2bad90390 on master (first released in 9.0.0). Impact note
Hits only applications that opt into an index sort whose SortField reads a doc-values field other than its declared one (a BinarySortField subclass overriding getSortKeyDocValues, which the class javadoc allows since 10.5.0, or any custom SortField#getIndexSorter since 8.6.0) and that update that other field in place (updateNumericDocValue, updateBinaryDocValue, updateSortedNumericDocValue, updateDocValues, tryUpdateDocValue or softUpdateDocument(s)): the update is accepted, the segment keeps its old physical order under its declared sort, CheckIndex at level 2 or higher rejects it (the default level 1 does not run the sort check), sorted top-k searches that terminate early on the index sort return wrong top hits, and later merges write the disorder into new segments; deterministic with -ea and -da, tiny scale (3 documents), released 8.6.0-10.5.2 (generic form) and 10.5.0-10.5.2 (BinarySortField form), and segments already written stay misordered after a code fix.
Summary
You configure an index sort with a BinarySortField subclass whose key is derived from another doc-values field (sort by the numeric field price, ties broken by the binary field sku, declared on sku), index a(5), b(7), c(8), and then change c's price to 1 with updateNumericDocValue; you expect the writer either to reject the update, as it rejects an update of sku itself ('cannot update docvalues field involved in the index sort'), or to keep the segment sorted. Instead the update is accepted, the segment stays in the order a, b, c while still declaring the sort, CheckIndex reports 'segment has indexSort=<binary: "sku"> but docID=1 sorts after docID=2', and a top-1 search sorted by the index sort returns a instead of c because it stops at the first non-competitive document. The cause is that IndexWriterConfig#setIndexSort protects only the SortField#getField names, while a custom index sort may read any field.
