One buffered document makes IndexWriter keep every later delete and doc-values update on the heap until OutOfMemoryError

The finding in 30 seconds

#

Each in-memory segment keeps a pointer into the writer's shared delete queue, a linked list of every delete. The pointer moves only when that segment indexes another document or flushes. Deletes alone never flush it, so everything after the pointer stays on the heap, and nothing counts it.

Background: in-memory segments and the delete queue

#
  1. IndexWriter buffers new documents in in-memory segments, one per indexing thread, and writes a segment to disk when the RAM buffer fills (setRAMBufferSizeMB, 16 MB by default) or on commit(), an NRT reopen or flush().
  2. Deletes and doc-values updates by term go into one shared queue. A buffered segment must apply the deletes that arrive after its documents when it flushes, so it remembers where the queue ended when its last document finished.
  3. When the buffered deletes reach the RAM buffer, the writer pushes them: it applies them to the segments already on disk and drops its own copy.

The finding, step by step

#
  1. Open an IndexWriter with the default config (16 MB RAM buffer) and add one document. Do not commit.
  2. Call deleteDocuments(new Term("id", id)) 2.5 million times with new 16-character ids, in a 256 MB heap.
  3. You expect the heap to stay near the RAM buffer: without that one document the same stream stays at 10-22 MiB, because every 16 MB of buffered deletes is applied and dropped.
  4. Instead the heap grows from 42 MiB at 250,000 deletes to 224 MiB at 1.75 million, then OutOfMemoryError. ramBytesUsed() says 5.6-14.2 MiB the whole time.
  5. Why: the segment holding the document keeps a pointer into the writer's linked list of deletes, and everything after it stays reachable. The pointer moves only when that segment indexes again or flushes, and deletes alone never flush it.

Who is affected

#

Default config, one thread, public API. It hits a writer with a buffered document that then runs a long delete-only or doc-values-update-only stretch, such as a bulk purge or backfill, with no commit, refresh or flush(): about 8-10 million 16-byte-id deletes per GB of heap. It ends in OutOfMemoryError, not wrong results.

Mechanism, terms and numbers763 words

Every in-memory segment of an IndexWriter (a DocumentsWriterPerThread, DWPT) keeps a private DeleteSlice: a pointer into the writer's shared delete queue, a singly linked list of every delete and doc-values update. The pointer moves only when the segment indexes another document or is flushed. After one addDocument, a stream of only deleteDocuments(Term) or doc-values updates therefore keeps every later queue node, with its Term or update, strongly reachable.

The RAM buffer never frees them. A pure delete reaches the flush policy with no per-thread writer, so FlushByRamOrCountsPolicy can only push the global delete buffer, which frees the writer's own copy but not the chain behind the idle segment's pointer, and IndexWriter.ramBytesUsed() counts only that global buffer (reset at every push) plus the segments' own bytes. With the default config and 16-character ids the heap grows about 127 bytes per delete until OutOfMemoryError (256 MB heap: 42 MiB at 250,000 deletes, 224 MiB at 1.75 million) while ramBytesUsed() stays at 5.6-14.2 MiB; with no buffered document the same stream stays at 10-22 MiB. updateNumericDocValue and updateSortedNumericDocValue behave the same way.

Keeping these deletes until the segment flushes is required (its document must see them); the defect is that the kept span is unbounded, uncounted and never released by the RAM buffer. It came with per-thread writers in 4.0.0-ALPHA (3.6.2 flushes the document with the deletes) and is in every release up to 10.6.0 and main. commit(), an NRT reopen or flush() releases it.

Terms

#
  • DWPT: DocumentsWriterPerThread, one in-memory segment. numRamDocs() counts the documents buffered in all of them.
  • Delete queue: DocumentsWriterDeleteQueue, a singly linked list of nodes, each holding a Term[], Query[] or DocValuesUpdate[]. The class javadoc: "the garbage collector takes care of pruning the list for us. All nodes in the list that are still relevant should be either directly or indirectly referenced by one of the DWPT's private DeleteSlice or by the global BufferedUpdates slice" (DocumentsWriterDeleteQueue.java:42-45 at e1faeba08bde).
  • Delete slice: DeleteSlice (DocumentsWriterDeleteQueue.java:333-372), a head and a tail pointer into the queue. Each DWPT has one (DocumentsWriterPerThread.java:134, :165); the global buffer has another.
  • Push: DocumentsWriter.applyAllDeletes freezes the global buffer into a packet that is applied to the on-disk segments, and clears it (DocumentsWriter.java:168-186, DocumentsWriterDeleteQueue.java:262-277).

The bug

#
  1. After a document is added, finishDocuments moves the DWPT's slice so that sliceHead is the queue's tail at that moment: the queue node before the first later delete (in the diagram probe, the sentinel) (DocumentsWriterPerThread.java:361-390). Only this and prepareFlush at flush time (:427-439) move a live DWPT's slice.
  2. Each deleteDocuments(Term) appends a node and advances only the global slice (DocumentsWriterDeleteQueue.java:129-139, :198-215). Through Node.next (:411-412) the idle DWPT's head references every later node.
  3. DocumentsWriter.applyDeleteOrUpdate (DocumentsWriter.java:153-165) calls flushControl.doOnDelete(), which passes no DWPT (DocumentsWriterFlushControl.java:497-501). In FlushByRamOrCountsPolicy.onChange every branch that marks a segment for flushing needs one, so only flushDeletes runs (FlushByRamOrCountsPolicy.java:40-57).
  4. The push frees the global copy only. DocumentsWriterDeleteQueue.ramBytesUsed() is the global buffer (:557-560), reset at each push, and IndexWriter.ramBytesUsed() is that plus the DWPTs' own bytes (DocumentsWriterFlushControl.java:508-516, IndexWriter.java:795-799). None of these counts the chain, and no delete or update call flushes the idle segment; flush(), commit(), an NRT reopen, flushNextBuffer() or a later document in that segment move its slice. A later document does not free the span: finishDocuments copies it into the segment's own, counted pending deletes (DocumentsWriterPerThread.java:380-383, :718-722).

The same path serves deleteDocuments(Query...), updateNumericDocValue, updateBinaryDocValue, updateSortedNumericDocValue and updateDocValues(Term, Field...) (IndexWriter.java:1864-2075); the exception is a deleteDocuments(Query...) call with an exact MatchAllDocsQuery, which becomes deleteAll() (:1886-1890) and drops the buffered document too. Executed: Term deletes, numeric and sorted-numeric updates.

Exposure and likelihood260 words
  • Who is hit. Applications whose IndexWriter still holds at least one added document in RAM and then sends only deletes or doc-values updates for a long time without commit(), an NRT reopen or flush(): a bulk purge by id, a doc-values backfill, a tombstone replay. A buffered document is the normal state right after indexing.
  • Default vs opt-in. Default IndexWriterConfig; nothing to opt into. One thread is enough.
  • Scale. About 110-130 bytes of heap per 16-byte-id delete (127 in the probe), so roughly 8-10 million such calls per GB of heap. The growth is linear and ramBytesUsed() stays under the buffer, so an application that watches ramBytesUsed() (as the flushNextBuffer javadoc suggests, IndexWriter.java:3745-3757) cannot see it.
  • How it ends. OutOfMemoryError, in application code or inside a writer call; in the latter case the writer treats it as tragic and closes, and uncommitted changes may be lost. No wrong results and no damage to the committed index.
  • Why it is rare. Applications that refresh or commit periodically release the span each time, and nobody has reported it since 4.0 (2012). Workaround: flush(), commit() or a refresh every few hundred thousand deletes or updates.
  • Not claimed. When the idle segment finally flushes it copies the whole pinned stream into its private buffer; at 2 GiB of delete terms that throws an "integer overflow" ArithmeticException from prepareFlush (a separate run with an 8 GB heap). Several idle segments after multi-threaded indexing pin the same nodes (no multiplication) but each copies the stream at flush (code reading only).

Why it looks unintended

#
  • setRAMBufferSizeMB: "the writer will flush whenever buffered documents and deletions use this much RAM". Here they use unbounded, uncounted RAM.
  • Without the buffered document the same stream stays at 10-22 MiB, and 3.6.2 releases it: a 4.0 regression.
  • "Deleted terms won't trigger a segment flush" (IndexWriter javadoc) contrasted the removed delete-count setting with the RAM buffer.
The full argument403 words
  • The contract. LiveIndexWriterConfig.setRAMBufferSizeMB (LiveIndexWriterConfig.java:157-165 at e1faeba08bde): "Determines the amount of RAM that may be used for buffering added documents and deletions before they are flushed to the Directory" and "the writer will flush whenever buffered documents and deletions use this much RAM".
  • No place in the internal accounting. DocumentsWriterFlushControl.getDeleteBytesUsed (:503-510): "heap bytes currently consumed by buffered deletes/updates that would be freed if we pushed all deletes". So it counts only what a push frees, the global buffer (a push does free it: in the heap probe ramBytesUsed() drops from 14.2 to 6.6 MiB between 500,000 and 750,000 deletes). The queue nodes an idle slice keeps are freed by no push, so they are counted nowhere. (Its next sentence excludes "already pushed delete/update packets", the frozen packets, not those nodes.)
  • The hedges do not cover it. "just an indicator" is explained by concurrent flushes; the "only approximate" note names delete-by-Query only (LiveIndexWriterConfig.java:167-177). This is Term deletes, one thread, linear growth. The third note (:179-181: "only a subset of the buffered documents are flushed and therefore only parts of the RAM buffer is released") is about which buffered documents a flush writes; here no document is ever flushed, and the pinned span is never part of the counted buffer.
  • Bounded without the document; released in 3.x. The no-document control stays at 10-22 MiB and the minimal test without its addDocument passes. In 3.1.0 and 3.6.2 the same workload flushes the buffered document together with the deletes and frees them.
  • Precedents fixed as bugs. LUCENE-1717 (#2791, uncounted pending-delete RAM: "it's a trap, now. We shouldn't set traps."), LUCENE-3222 (delete-term undercount), LUCENE-3340 (#4413, buffered deletes not flushed by RAM, called a memory leak, its tests "fail on trunk and pass on 3.x"), LUCENE-9478 (#10517, "DWPTDeleteQueue leaks memory", a delete-queue retention leak by another mechanism) and LUCENE-9298 (#10338, RAM accounting in BufferedUpdates when deleted doc IDs and terms are cleared).
  • Design discussion. On #3647 (LUCENE-2573, 2011) McCandless wrote that the flush policy "needs access to the 'global' deletes count (and also the to [sic] per-DWPT deletes count). If a given DWPT has 0 buffered docs, then indeed the buffered deletes in its pool doesn't matter". Here it has one.
  • No test asserts the retention. TestIndexWriterDelete.testIndexingThenDeleting, testFlushPushedDeletesByRAM and testApplyDeletesOnFlush never leave an idle buffered document; the numRamDocs() > 0 asserts of TestPerSegmentDeletes are in a commented-out block (:102-158).
The devil's-advocate check246 words

The strongest case for "intended" (all the reviews from another model family rated it moderate; the devil's-advocate verifier called the javadoc sentence the main risk, with medium confidence on how upstream will receive it): the IndexWriter class javadoc says "In contrast to the other flush options setRAMBufferSizeMB and setMaxBufferedDocs, deleted terms won't trigger a segment flush" (IndexWriter.java:129-131); the 4.0 CHANGES entry says "IndexWriter only applies and flushes deletes if the maxBufferedDelTerms limit is reached during indexing. No segment flushes will be triggered due to this setting." (lucene/CHANGES.txt:15781-15783); the dev@ thread "FlushPolicy and maxBufDelTerm" (2013-08-01) accepted that delete pressure does not write a segment; the kept deletes really are needed until the segment flushes; and the RAM limit is "just an indicator".

Why it fails: the javadoc sentence was added in f47c3e82985 (LUCENE-3023, 2011-04-28) right after a sentence about setMaxBufferedDeleteTerms, contrasting that count setting with the RAM buffer; 58105a203a1 (LUCENE-7868, 2017) removed the count sentence and left this one. The CHANGES entry and the 2013 thread are about the same count setting ("due to this setting"), and in that thread McCandless wrote "if RAM usage of the buffered del Term/Query s is too high, then a segment is flushed along with the deletes being applied". Nothing documents unbounded, uncounted retained heap; "needed until the flush" is why the slice exists, not a reason never to flush or count it. The fix does not need a segment flush per delete (see Suggested fix).

Suggested fix

#

Recommended Flush idle in-memory segments when a pure delete or update pushes the global delete buffer

When a pure delete or doc-values update pushes the global delete buffer, flush the in-memory segments that are idle (only those it can tryLock, never one an indexing thread holds). It sits in DocumentsWriter.applyDeleteOrUpdate, so every delete and update call is covered. +45/-1 in two files; the repro passes, and 356 tests of 17 IndexWriter suites pass on two seeds.

private long applyDeleteOrUpdate(ToLongFunction<DocumentsWriterDeleteQueue> function)
    throws IOException {
  final long seqNo = applyDeleteOrUpdateLocked(function); // the old synchronized body
  if (seqNo < 0) { // this call pushed the global delete buffer
    DocumentsWriterPerThread idle;
    while ((idle = flushControl.checkoutIdleWriterWithDocs()) != null) {
      doFlush(idle); // prepareFlush applies and drops the idle slice
    }
  }
  return seqNo;
}

Flush idle in-memory segments when a pure delete or update pushes the global delete buffer (validated by the checks) (recommended)

#

DocumentsWriter.applyDeleteOrUpdate (DocumentsWriter.java:153-165) keeps its synchronized body as applyDeleteOrUpdateLocked; when that returns a negative sequence number (this call pushed the global buffer, :161-163), it flushes, outside the lock, every DWPT returned by a new DocumentsWriterFlushControl.checkoutIdleWriterWithDocs(). That method takes only DWPTs that have documents, are not flush-pending and can be tryLocked, marks one pending and checks it out, like checkoutLargestNonPendingWriter. The flushed segment is published by the caller's IndexWriter.maybeProcessEvents, which already runs for a negative sequence number (IndexWriter.java:6345-6351). +45/-1 in DocumentsWriter.java and DocumentsWriterFlushControl.java.

private long applyDeleteOrUpdate(ToLongFunction<DocumentsWriterDeleteQueue> function)
    throws IOException {
  final long seqNo = applyDeleteOrUpdateLocked(function); // the old synchronized body
  if (seqNo < 0) { // this call pushed the global delete buffer
    DocumentsWriterPerThread idle;
    while ((idle = flushControl.checkoutIdleWriterWithDocs()) != null) {
      doFlush(idle); // prepareFlush applies and drops the idle slice
    }
  }
  return seqNo;
}

Trade-offs

  • Bound. For every idle DWPT the push can lock, the kept span ends at that push, so it stays within about one RAM buffer of deletes. Skipped DWPTs keep theirs: one whose tryLock() fails (an indexing thread holds it; its slice moves at its next document) or one already flush-pending. Nothing retries them, so a skipped DWPT that then stays idle keeps its span until a later push finds it free. The span is also still uncounted before the first push: in the heap probe the heap reached 83 MiB at 500,000 deletes (16 MB buffer, almost 6 times the counted 14.2 MiB) before the first push released it.
  • Cost. A delete or update call that pushes may now write segments, so it does flush I/O and can throw what a flush throws, as addDocument already can. The flush runs after the delete is queued and pushed, so an exception from it reaches the caller of a delete that has already taken effect; that needs a decision upstream. Each push flushes each idle DWPT it can lock once, and doFlush then also flushes any other DWPT already pending (DocumentsWriter.java:502-580), as the add path does. An idle DWPT's segment holds whatever was buffered when indexing paused; segment sizes and counts were not measured, and no throughput benchmark was run. It happens only when the global delete buffer alone reaches the RAM buffer; with documents being added, the add path's activeRam + deletesRam check usually flushes first (FlushByRamOrCountsPolicy.java:54-55, by reading). With RAM flushing disabled (DISABLE_AUTO_FLUSH), pushes happen only at #16867's 1945 MB cap, so the fix would act only there (by reading).
  • Concurrency. A DWPT held by an indexing thread is skipped. A push never happens during a full flush (DocumentsWriter.java:175-176). If a full flush begins between the push and the checkout, checkout marks nothing: it returns null for a DWPT that is not flush-pending, and for one that is it blocks it and returns the next pending flush (DocumentsWriterFlushControl.java:261-280), the same handling checkoutLargestNonPendingWriter (:789-810, used by flushNextBuffer()) relies on; the pending flag is re-read under the flush-control lock. No concurrency or full-flush test of this path was run.
  • Docs. The IndexWriter javadoc sentence "deleted terms won't trigger a segment flush" would need updating.

Count the span an idle slice keeps and act on it (not implemented)

#

Track the bytes appended to the queue since each DWPT's slice head (for example a running total of the global buffer's bytes at each push, recorded when a slice moves), add it to getDeleteBytesUsed(), and let FlushByRamOrCountsPolicy flush or apply the idle DWPT once it passes the buffer.

Trade-offs

More precise than A: it also bounds the uncounted span before the first push and makes ramBytesUsed() honest. More code on hot paths, and it needs a per-node byte estimate.

Flush every DWPT from IndexWriter after a delete call that pushed (the hunt's sketch)

#

while (docWriter.flushOneDWPT()) {} after the push in five IndexWriter delete and update methods.

Trade-offs

Validates the root cause (the minimal test passes with assertions on and off), but misses updateSortedNumericDocValue, and flushOneDWPT takes the largest DWPT with a blocking lock, including ones indexing threads are using; the adjudication's summary of the reviews calls it too blunt (tiny segments).

Documentation only

#

Say in setRAMBufferSizeMB and the IndexWriter class javadoc that while a document is buffered, every later delete and update is kept until the next flush, commit or refresh, and recommend flush() during long delete-only or update-only runs.

Trade-offs

Cheapest; leaves the trap.

Downstream note

#

Services that run bulk purges or doc-values backfills through one long-lived writer should refresh, commit or flush() every few hundred thousand operations; a service that refreshes on a schedule already releases the kept deletes each time.

How it was found

#

Non-formal. A probe compared retained heap with the RAM buffer during a delete-only stream on the stock jar and saw unbounded growth only when one document was buffered; reading the delete-slice code gave the mechanism. A bounded model-based enumeration of writer operation sequences then matched "kept iff a document is buffered" in all 1,170 runs.

The method in full161 words

Method: non-formal (a measurement first, then code reading; the later bounded enumeration is semi-formal).

  • The hunt (2026-11-02) ran a heap-versus-RAM-buffer probe on the stock main jar: default config, one thread, -Xmx256m, one buffered document, then N deleteDocuments(Term) or updateNumericDocValue calls, sampling heap after GC and ramBytesUsed() every N/8 calls, against a control with nothing buffered. The idle run grew to OutOfMemoryError; the control stayed bounded.
  • A hunt unit read the DeleteSlice code for the mechanism and reduced it to one public-API JUnit test.
  • It then checked the prediction with a bounded model-based enumeration (every sequence of up to 3 of 8 writer operations before a delete or doc-values burst, 1,170 runs, assertions on and off): 380 runs kept the first term, all exactly those with numRamDocs() > 0 when the burst started, 0 mismatches. With its fix sketch as a vacuity control, 0 runs kept it.
  • Commit-level bisection and version ports traced it to the 4.0 per-thread writer landing.

LFV-1077, snapshot of 2026-11-03

Registry title
While a document sits buffered in an idle in-memory segment, IndexWriter keeps every later delete and doc-values update reachable, uncounted by ramBytesUsed() and never released by the RAM buffer, so a delete-only or update-only stream grows the heap until OutOfMemoryError (default config, since 4.0.0)
Area
index / IndexWriter delete queue (DeleteSlice of an idle DocumentsWriterPerThread, flush-by-RAM on pure deletes)
Priority
Low, rank 283: On the default config of every release since 4.0, a long run of only deletes or doc-values updates while some added document is still buffered keeps every delete reachable, outside the RAM accounting, until OutOfMemoryError. It needs millions of calls per GB of heap with no commit, refresh or flush, so it is rare and Low.
Impact class
crash
Impact note
Hits an application on the default IndexWriterConfig that, while at least one added document is still buffered in RAM, issues a long delete-only or doc-values-update-only run (deleteDocuments(Term), updateNumericDocValue and the other update calls that take the same path) with no commit, NRT reopen or flush() in between: about 110-130 bytes of heap stay reachable per 16-byte-id delete (heap probes: 42 -> 224 MiB over 250k -> 1.75M deletes, then OutOfMemoryError in a 256 MB heap) while IndexWriter.ramBytesUsed() stays at 5.6-14.2 MiB, so roughly 8-10 million such calls per GB of heap; one thread suffices, applications that refresh or commit periodically release the span each time, and every release since 4.0.0 is affected. A second, bounded trigger (2026-11-02): after a phase in which two threads indexed at once, a single thread's ordinary updateDocument stream is pinned the same way by the second, now idle, in-memory segment (163 MiB retained vs 14 MiB in a control after 1.5M updateDocument calls with ramBytesUsed() at 5.3 MiB, OutOfMemoryError in 256 MB before 2.5M calls, default 16 MB buffer, tiny documents); the window closes at the active segment's first RAM flush or any full flush, so the overshoot is about 110 bytes per call times the calls that fill the RAM buffer: roughly 20-30 times the buffer for documents that take only a few bytes of indexing RAM each, and below the buffer for ordinary documents.
Summary
You add a document to an IndexWriter with the default config and then, without a commit, NRT reopen or flush(), send a long stream of deleteDocuments(Term) or doc-values update calls, and expect the heap held by those buffered deletes to stay around the RAM buffer, because the writer applies and drops them each time they reach it, as it does when nothing is buffered. Instead the in-memory segment that holds the one document keeps a pointer into the shared delete queue that moves only when that segment indexes again or is flushed, so every later delete stays reachable after it was applied. IndexWriter.ramBytesUsed() does not count it, nothing flushes that segment, and the heap grows with every call until OutOfMemoryError. The same happens without any delete-only run when two threads indexed at once and then one thread keeps calling updateDocument: the second in-memory segment stays idle and pins every later delete term until the active segment fills the RAM buffer and is flushed.
