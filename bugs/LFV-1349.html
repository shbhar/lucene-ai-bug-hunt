SortedSetSelector views re-read ordinals on a no-op intoBitSet: SimpleText FILTER counts throw ArrayIndexOutOfBoundsException

Since 10.6.0, SimpleTextCodec serves single-valued sorted-set doc values through a SortedSetSelector MIN view, which reads the current document's value again on an intoBitSet call that has nothing to do. A two-clause FILTER count over 4,500 documents then throws ArrayIndexOutOfBoundsException instead of returning 1; the default codec does not take this path.

The finding in 30 seconds

#

A SortedSetSelector view caches one value per document and reads it each time it lands on a document with a value. Its intoBitSet also reads after a call that did not move, so the current document's values are read twice, and SimpleText's reader runs off its one-element array.

Background in three steps

#
  1. A SORTED_SET doc-values field stores each document's values as ordinals. Its iterator stands on one document; nextOrd() returns that document's ordinals one at a time and may be called at most docValueCount() times per document.
  2. SortedSetSelector.wrap(field, MIN) presents such a field as single-valued: whenever the view lands on a document with a value it calls nextOrd() and keeps the result as ordValue(). Since 10.6.0, SimpleText shows every single-valued sorted-set field (decided per segment) this way.
  3. intoBitSet(upTo, bits, offset) marks the iterator's documents from the current one up to upTo - 1 and leaves the iterator at or past upTo. If it already stands at or past upTo, the call does nothing.

The finding, step by step

#
  1. Index 4,500 documents with SimpleTextCodec: a single-valued SortedSetDocValuesField f on docs 0 and 4400, a NumericDocValuesField g on docs 1 and 4400.
  2. Call IndexSearcher.count on FILTER FieldExistsQuery(f) + FILTER FieldExistsQuery(g). You expect 1 (doc 4400), as with the default codec and on 10.5.2.
  3. The bulk scorer opens a 4,096-document window at doc 1 (g's first document), so it ends before doc 4097. It moves f to doc 4400, which reads that document's one value, then asks f to mark its matches below 4097. f is already past 4097, so the call should do nothing.
  4. Instead the MIN view reads doc 4400's values a second time. SimpleText holds only one, so count throws ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1, with assertions on and off.

Who is affected

#

Only indexes written with SimpleTextCodec, a debugging codec ("FOR RECREATIONAL USE ONLY"). In practice that is randomized test suites, which rarely draw it at random; Lucene's own CI failed twice with this stack. The default codec does not take this path. The search fails loudly; no wrong results were seen.

Mechanism, terms and numbers643 words

SortedSetSelector.wrap(sortedSet, MIN) (and MAX, MIDDLE_MIN, MIDDLE_MAX) turns a multi-valued sorted-set iterator into a single-valued SortedDocValues view: each time the view lands on a document that has a value it reads that document's ordinals (setOrd()) and caches the chosen one. Its intoBitSet override calls setOrd() after every in.intoBitSet(...), also when upTo <= docID(), where intoBitSet is defined as a no-op and the iterator does not move, so the view reads the current document's ordinals a second time.

Since 10.6.0 (#16714) SimpleTextCodec returns every single-valued SORTED_SET field through such a MIN view, and its nextOrd() indexes a per-document array, so the second read throws. On its bit-set path, DenseConjunctionBulkScorer makes the no-op call when the lead clause's next document lies past the current 4,096-document window: with 4,500 documents, IndexSearcher.count of two FILTER FieldExistsQuery clauses throws ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1 instead of returning 1. The skip-indexed sorted-set range query path makes the same call, and Lucene's own CI has failed twice with that stack. The default codec does not take this path, because its single-valued path is not a selector view.

The mechanism (main 5adff78bb168)

#
  1. SimpleTextDocValuesReader.getSortedSet returns a single-valued field as DocValues.singleton(SortedSetSelector.wrap(multi, SortedSetSelector.Type.MIN)) (SimpleTextDocValuesReader.java:776-783, added by #16714); "single-valued" is decided per segment, from the maximum value count the writer recorded for the field (:691-697). The multi-valued iterator's nextOrd() is Long.parseLong(currentOrds[currentIndex++]) (:849-852).
  2. MinValue.advance is in.advance(target); setOrd(); (SortedSetSelector.java:113-118), and setOrd() is ord = (int) in.nextOrd() whenever docID() != NO_MORE_DOCS (:165-169). Moving to doc 4400 already reads its one ordinal.
  3. MinValue.intoBitSet is in.intoBitSet(upTo, bitSet, offset); setOrd(); (:134-138), with no check that anything moved. MaxValue (:214-218), MiddleMinValue (:298-302) and MiddleMaxValue (:383-387) have the same two lines. This is the fix site.
  4. DenseConjunctionBulkScorer.scoreWindow advances the clauses in turn; g's first document, 1, becomes the window start, and the window ends at min(maxDoc, 1 + 4096) = 4097 (DenseConjunctionBulkScorer.java:178-187, :214; WINDOW_SIZE = 4096 at :66). scoreWindowUsingBitSet advances the lead, exists(f), to the window start, which lands on 4400, then calls lead.intoBitSet(4097, ...) (:274-278). That call must do nothing; the view's setOrd() calls nextOrd() again and reads currentOrds[1] of a one-element array. The window takes the bit-set path, not leap-frog, because the lead's cost is above maxDoc / 4 (:232-253). f leads: both SimpleText iterators report cost maxDoc (SimpleTextDocValuesReader.java:347-349, :810-812), so the scorer's stable sort by cost (DenseConjunctionBulkScorer.java:118-121) does not reorder them, and the stack shows f's MIN view in the lead call at :278. If g led instead, the trace would differ (not run).
  5. The skip-indexed range path makes the same no-op call: DocValuesRangeIterator$BulkBlockRangeIterator.intoBitSet calls disi.intoBitSet(blockEnd, ...) on a YES_IF_PRESENT block even when disi already sits past blockEnd (DocValuesRangeIterator.java:357-366). The two upstream CI failures are on that path.

Not claimed separately: MAX, MIDDLE_MIN and MIDDLE_MAX share the code and the fix but were not run through a public search path (SimpleText uses MIN only). On the default codec a MIN view of a truly multi-valued document reports another ordValue() (0, then 1) after a direct no-op intoBitSet (the mechanism probe, one sorted-set representation). By reading, one more Lucene path can make a no-op call on a selector view, also on the default codec: a SortedSetSortField sort's competitive iterator can install a selector view of a multi-valued field as its docsWithField (SortedSetSortField.java:173-180, TermOrdValComparator.java:600-604), and UpdateableDocIdSetIterator.intoBitSet forwards to it with no upTo check (UpdateableDocIdSetIterator.java:57-64). There the view is used only as an iterator and its ordValue() is not read after the call (by reading), so no visible effect is known on the default codec. Whether that sort path, or a non-lead clause in scoreWindowUsingBitSet (DenseConjunctionBulkScorer.java:292-305), is a further SimpleText trigger was not run.

Exposure and likelihood156 words
  • Who: indexes written with SimpleTextCodec (lucene/codecs; javadoc "FOR RECREATIONAL USE ONLY", SimpleTextCodec.java:35). With tests.codec=random, LuceneTestCase rarely picks SimpleText at random, unless the suite suppresses it (SetupAndRestoreStaticEnv.java:185-190), so Lucene's and downstream randomized test suites are where it shows. Lucene's CI failed on it on 2026-09-30 and 2026-10-26.
  • Trigger: a single-valued SORTED_SET doc-values field as the lead of a FILTER conjunction on the bulk scorer's bit-set path whose next document lies beyond the current 4,096-document window, or a skip-indexed sorted-set doc-values range query. Public API with SimpleTextCodec configured; 4,500 documents.
  • Not hit: the default codec on these paths, whose getSortedSet returns DocValues.singleton(getSorted(...)) for a single-valued field (Lucene90DocValuesProducer.java:2282-2285), not a selector view (see the mechanism for the unexecuted sort path). An application that chose SimpleTextCodec for its own index would be hit.
  • Effect: the search throws ArrayIndexOutOfBoundsException; no wrong count or leak was seen.
  • Since: 10.6.0, a regression from 10.5.2.

Why it looks unintended

#
  • intoBitSet must act "exactly as" the loop for (doc = docID(); doc < upTo; doc = nextDoc()): nothing happens when upTo <= docID().
  • nextOrd(): "illegal to call this more than docValueCount() times for the currently-positioned doc".
  • Lucene's bulk scorer calls intoBitSet right after advance() with no upTo check; for the related #14517 upstream fixed the callee. 10.5.2 passes the test.
The full argument215 words
  • The contract defines the call as a no-op. DocIdSetIterator.intoBitSet: "This should behave exactly as if implemented as below", the loop for (int doc = docID(); doc < upTo; doc = nextDoc()) (DocIdSetIterator.java:187-210). Its only stated preconditions are offset <= docID() and a positioned iterator.
  • The second read is illegal. SortedSetDocValues.nextOrd: "It is illegal to call this more than docValueCount() times for the currently-positioned doc" (SortedSetDocValues.java:35-43).
  • Callers rely on no-op calls being legal. DenseConjunctionBulkScorer.scoreWindowUsingBitSet (:274-278, and :292-305 for the other clauses) and DocValuesRangeIterator (:362-365) call intoBitSet right after advance() with no upTo check, and the test framework's asserting sorted-set wrapper accepts such a call (it asserts docID() >= upTo afterwards, AssertingLeafReader.java:1314-1323). A related precedent with a different cause: #14517 ("Strange stack traces for new bitset focused doc iterators"), a crash inside a callee's intoBitSet reached from the same DenseConjunctionBulkScorer call (there the callee's inner iterator lagged behind offset), was fixed in the callee, TermOrdValComparator's competitive iterator (#14523).
  • History. #16714 added the unconditional setOrd() to fix the opposite problem, a stale cached ordinal after a call that does move (left by #16126); its review discussed only that direction. 10.5.2 passes the same test. TestSortedSetSelector has no intoBitSet test and is @SuppressCodecs({"SimpleText"}) (TestSortedSetSelector.java:32).
The devil's-advocate check156 words

"SimpleText is a debugging codec and intoBitSet is @lucene.internal." True (SimpleTextCodec.java:35-37, DocIdSetIterator.java:203), but the throwing code is in core SortedSetSelector, the caller is Lucene's own bulk scorer reached from IndexSearcher.count with public queries, the test framework sometimes picks SimpleText at random, and #16714 itself was made because "There are occasional build failures resulting from tests assuming all codecs return singleton doc values": upstream fixes SimpleText behaviour that breaks CI.

"intoBitSet resets the per-document ordinal cursor, so reading again is legal." The asserting wrapper does set ordsRetrieved = 0 (AssertingLeafReader.java:1322), but no javadoc says so; the default loop and SimpleText's own iterator leave the cursor alone. Under either reading, an exception out of count is not intended.

A maintainer may still prefer a SimpleText-only fix (option B) or close this at low priority; the case for fixing the views is that they break the intoBitSet contract on every codec.

Suggested fix

#

Recommended A. Call setOrd() only when the call can move (validated)

In each of the four views' intoBitSet, call setOrd() only if docID() < upTo before the inner call (+16/-4 lines in SortedSetSelector.java). The repro passes with assertions on and off, the upstream range test forced to SimpleText stops failing (5 to 7 of 21 runs failed on stock), and the closest suites and lint checks pass.

@Override
public void intoBitSet(int upTo, FixedBitSet bitSet, int offset) throws IOException {
  boolean moves = docID() < upTo;
  in.intoBitSet(upTo, bitSet, offset);
  if (moves) {
    setOrd();
  }
}

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B and C are by reading.

A. Call setOrd() only when the call can move (validated) (recommended)

#

In each of the four views (SortedSetSelector.java:134-138, :214-218, :298-302, :383-387), +16/-4 lines:

@Override
public void intoBitSet(int upTo, FixedBitSet bitSet, int offset) throws IOException {
  boolean moves = docID() < upTo;
  in.intoBitSet(upTo, bitSet, offset);
  if (moves) {
    setOrd();
  }
}

Trade-offs

  • Follows the documented no-op contract and keeps #16714's refresh of the cached ordinal whenever the iterator does move (when docID() < upTo the default loop calls nextDoc() at least once).
  • By reading, it also removes the default-codec wrong ordValue() after a no-op call. One comparison per call.

B. Reset SimpleText's ordinal cursor in intoBitSet

#

Make the SimpleText multi-valued iterator's intoBitSet reset currentIndex, as the test framework's asserting wrapper resets its counter.

Trade-offs

Stops this exception, but the views still read ordinals again on a no-op call on every other codec (the default codec's MIN view of a multi-valued document then reports its second ordinal). Not recommended. By reading, not run.

C. Stop callers from making no-op calls

#

Skip intoBitSet when the iterator already sits at or past upTo (DenseConjunctionBulkScorer.java:278, DocValuesRangeIterator.java:365, ...).

Trade-offs

Leaves the views violating the documented contract, needs every caller, and for the related #14517 upstream fixed the callee, not the caller. Not recommended. By reading, not run.

How it was found

#

Semi-formal: a proof-obligation audit of SortedSetSelector's intoBitSet overrides against the intoBitSet and nextOrd contracts: a call with upTo <= docID() is a no-op and must not read the current document's ordinals again. The unconditional setOrd() breaks that, and a JUnit test on stock main witnessed the crash.

The method in full94 words
  • Obligation: for every positioned view and every upTo <= docID(), intoBitSet leaves the iterator, its cached ordinal and the wrapped iterator's ordinal cursor unchanged (DocIdSetIterator.java:187-210, SortedSetDocValues.java:35-43).
  • Finding: all four views call setOrd(), and so nextOrd(), after every in.intoBitSet(...); then the search paths that make no-op calls (DenseConjunctionBulkScorer, DocValuesRangeIterator) and the codec whose nextOrd() cannot absorb an extra call (SimpleText since #16714).
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

search / SortedSetSelector views (intoBitSet), reached through codecs / SimpleText doc values
Priority
Low, rank 1175: Since 10.6.0, on indexes written with the debug-only SimpleTextCodec, IndexSearcher.count of a FILTER conjunction over a single-valued SORTED_SET field (for some document layouts) and a skip-indexed sorted-set doc-values range query throw ArrayIndexOutOfBoundsException. Production codecs are not affected and the realistic hits are randomized test suites (Lucene's own CI hit it twice), so it is Low.
Impact class
minor
Impact note
Hits only indexes written with SimpleTextCodec (a debugging codec in lucene/codecs, 'FOR RECREATIONAL USE ONLY'), in practice randomized test suites, Lucene's own and downstream ones, that draw it at random: a single-valued SORTED_SET field in a FILTER conjunction whose bulk scorer makes a no-move intoBitSet call on it (for example when the field's next document lies beyond the current 4,096-document scoring window), or a skip-indexed sorted-set doc-values range query, makes IndexSearcher.count throw ArrayIndexOutOfBoundsException instead of returning the count; indexes on the default codec are not affected (its single-valued path is not a SortedSetSelector view); no scale needed (4,500 documents); 10.6.0 and main [exec], a regression from 10.5.2.
Summary
You index 4,500 documents with SimpleTextCodec, a single-valued SORTED_SET field f on docs 0 and 4400 and a numeric doc-values field g on docs 1 and 4400, and call IndexSearcher.count on FILTER FieldExistsQuery(f) + FILTER FieldExistsQuery(g). You expect 1, as on the default codec and on 10.5.2. Instead count throws ArrayIndexOutOfBoundsException 'Index 1 out of bounds for length 1': the conjunction scorer makes an intoBitSet call that cannot move the iterator (upTo <= docID()), which the intoBitSet javadoc defines as a no-op, but the SortedSetSelector MIN view that SimpleText puts in front of the field since 10.6.0 calls nextOrd() again for the current document and runs past its single ordinal.
