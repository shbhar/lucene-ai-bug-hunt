Lucene90CompressingTermVectorsFormat accepts a blockSize its writer cannot use, and the first flush with term vectors throws and closes the IndexWriter

Lucene90CompressingTermVectorsFormat documents its last argument, blockSize, as a chunk count and accepts any value from 1 up, but since 8.5.0 its writer reads it as a shift limited to 2 to 22. Pass 1024 and the first flush with term vectors throws and closes the IndexWriter.

The finding in 30 seconds

#

The constructor checks the value as a chunk count (at least 1), but the writer uses it as a block shift (2 to 22). The two meanings disagree for 1 and for every value from 23 up, and nothing notices until the first flush.

Background: chunks and index blocks

#
  1. The compressing term vectors format compresses the term vectors of several documents together into chunks. A small index records where each chunk starts (its first document and its file position).
  2. That index is written in blocks of chunks. The format's last constructor argument sets the block size. Since 8.5.0 it is given as the exponent of a power of two (the log in base 2 of the chunk count): the stock format passes 10, meaning 2^10 = 1024 chunks per block.

The finding, step by step

#
  1. You build a custom codec with new Lucene90CompressingTermVectorsFormat("TV", "", CompressionMode.FAST, 4096, 128, 1024): 1024 chunks per index block, as the javadoc describes the last argument ("the number of chunks to store in an index block").
  2. You expect the constructor to reject 1024, as the stored-fields twin Lucene90CompressingStoredFieldsFormat does, or the format to work. It only checks blockSize >= 1, so it accepts 1024, and addDocument succeeds.
  3. But since 8.5.0 the writer reads the value as a shift: the stock format passes 10, meaning 2^10 = 1024 chunks. Your 1024 means 2^1024, and the chunk-index encoder (DirectMonotonicWriter) allows only shifts 2 to 22 (4 to 4,194,304 chunks).
  4. The first flush of a segment with term vectors (here DirectoryReader.open(writer)) throws IllegalArgumentException: blockShift must be in [2-22], got 1024. The IndexWriter closes and documents added since the last commit are lost; the last commit stays intact. blockSize 1, the constructor's own minimum, fails the same way.

Who is affected

#

Only applications whose custom codec builds this experimental format with 1 or a value from 23 up, such as a chunk count or 1024 (the stock value up to 8.4.1). Stock codecs pass 10 and are fine. The failure is loud but late: at the first flush, closing the writer and dropping uncommitted documents.

Mechanism, terms and numbers599 words

Lucene90CompressingTermVectorsFormat's last constructor argument, blockSize, is documented as "the number of chunks to store in an index block", and the constructor rejects only values below 1. Since 8.5.0 the writer uses the value as a DirectMonotonicWriter block shift, the log in base 2 of the chunk count, and DirectMonotonicWriter accepts only 2 to 22. So a custom codec that passes a chunk count such as 1024 (the value the stock format passed up to 8.4.1), or 1 (the constructor's own minimum), builds fine and, in the repro, addDocument returns, but the first flush of a segment with term vectors throws IllegalArgumentException: blockShift must be in [2-22], got 1024 and the IndexWriter closes itself, losing the documents added since the last commit.

The stored-fields twin, Lucene90CompressingStoredFieldsFormat, got exactly the missing range check and a "log in base 2" javadoc in the same change that made the value a shift (LUCENE-9147, 2020); the term vectors format file was not part of that change. Stock codecs pass 10 and are not affected; the committed index stays intact, and nothing returns wrong results.

The mechanism (main 5adff78bb168, under lucene/core/src/java/org/apache/lucene/)

#
  1. The constructor documents and checks a count. codecs/lucene90/compressing/Lucene90CompressingTermVectorsFormat.java:68: @param blockSize the number of chunks to store in an index block.; :86-88: the only check, if (blockSize < 1) throw new IllegalArgumentException("blockSize must be >= 1"). This is the fix site. The class is @lucene.experimental (:35).
  2. The value goes on unchanged, as a shift. vectorsWriter (:100-113) passes it as the last argument of Lucene90CompressingTermVectorsWriter, whose parameter is named blockShift (Lucene90CompressingTermVectorsWriter.java:242), and that hands it to new FieldsIndexWriter(..., blockShift, context) (:281-289).
  3. Nothing checks it until the segment is finished. At flush, TermVectorsConsumer.flush calls writer.finish (index/TermVectorsConsumer.java:85), which calls FieldsIndexWriter.finish (Lucene90CompressingTermVectorsWriter.java:725). That writes the shift into the meta file (FieldsIndexWriter.java:116) and calls DirectMonotonicWriter.getInstance(metaOut, dataOut, totalChunks + 1, blockShift) (:125).
  4. DirectMonotonicWriter accepts only 2 to 22. util/packed/DirectMonotonicWriter.java:33-34 (MIN_BLOCK_SHIFT = 2, MAX_BLOCK_SHIFT = 22); :46-54 throws IllegalArgumentException("blockShift must be in [2-22], got " + blockShift).
  5. Outcome. The exception escapes a segment flush, which IndexWriter treats as aborting: the writer closes (isOpen() == false) and documents added since the last commit are lost; the last commit stays readable, and a new writer with the same codec fails the same way at its next flush with term vectors (all executed). Any flush of such a segment fails, so addDocument itself throws when it triggers an automatic flush (index/DocumentsWriter.java:450, :400-404), and a merge that writes term vectors with this codec reaches the same finish (index/SegmentMerger.java:170-171, :261-267; Lucene90CompressingTermVectorsWriter.java:934). A segment without any term-vector field never creates the term vectors writer: finishDocument returns before initTermVectorsWriter when no field has vectors (index/TermVectorsConsumer.java:119-126, :103-110), and flush skips the finish (:78), so it flushes fine.
  6. The twin does it right. Lucene90CompressingStoredFieldsFormat.java:96: @param blockShift the log in base 2 of number of chunks to store in an index block; :117-126 reject anything outside MIN_BLOCK_SHIFT..MAX_BLOCK_SHIFT in the constructor.

Not claimed. Values 2 to 22 are silently read as a shift (asking for "16 chunks" gives 2^16 = 65,536 chunks per block); that is only the documentation mismatch and fails nothing. The exception carries a suppressed CorruptIndexException: checksum passed (...). possibly transient resource issue, or a Lucene or JVM bug for a temp file; it is CodecUtil.checkFooter's generic handling of the earlier exception (FieldsIndexWriter.java:139), not a second defect, though it can mislead.

Exposure and likelihood146 words
  • Who. Code that constructs Lucene90CompressingTermVectorsFormat itself (it is @lucene.experimental) and passes 1 or 23 and above: for example a chunk count, as the javadoc describes the argument, or 1024, the value the stock format used up to 8.4.1. A custom codec that passed 1024 under 8.4.1 compiles unchanged against 8.5.0 and fails at its first flush there. A GitHub code search found no downstream product that constructs the format, and no public report of it was found since 2020, so the likelihood is rare.
  • Default vs opt-in. Opt-in only. Stock code passes 10 (Lucene90TermVectorsFormat.java:170, SortingTermVectorsConsumer.java:40-41).
  • Effect. Loud and deterministic, but late and aborting: the error comes at the first flush instead of at construction, the IndexWriter closes, and the documents added since the last commit are lost. No wrong results, no damage to committed data.
  • Scale. One document; nothing large is needed.

Why it looks unintended

#
  • The javadoc calls it "the number of chunks" per index block, and the check admits any value from 1 up; the writer takes only 2 to 22.
  • The 8.5.0 change that made it a shift gave the stored-fields twin this exact check, but skipped this file.
  • Nothing documents a shift or range for it; no upstream test reaches the gap.
The full argument269 words
  • The constructor's own contract. The javadoc (Lucene90CompressingTermVectorsFormat.java:68) says the value is a chunk count, and the check (:86-88) says every value from 1 up is legal. The writer can use neither 1 nor any value from 23 up.
  • The same change fixed the twin, not this file. LUCENE-9147 (136dcbdbbce, Adrien Grand, 2020-02-05; issue #10187, PR apache/lucene-solr#1179) turned the value into a shift: it renamed the writer's parameter blockSize to blockShift, changed the stock argument from 1024 to 10 (Lucene50TermVectorsFormat), and gave CompressingStoredFieldsFormat the MIN_BLOCK_SHIFT..MAX_BLOCK_SHIFT check and the "log in base 2" javadoc. CompressingTermVectorsFormat.java is not in that commit's file list. The class dates from LUCENE-4599 (5837fe83bd8, 2013); its count javadoc and >= 1 check were added by LUCENE-6153 (55eb8b3da39, 2015), when the value really was a count. LUCENE-9705 (f8be421ae1f, 2021) copied them into Lucene90CompressingTermVectorsFormat.
  • A second leftover of the old meaning. The same commit switched the test codec's main random range for the value from 1..1024 to MIN_BLOCK_SHIFT..MAX_BLOCK_SHIFT, but CompressingCodec.randomInstance(Random, boolean) still draws it from 1..1024 (lucene/test-framework/.../CompressingCodec.java:97-105; no in-tree caller). It points to an oversight rather than a design; it is not claimed as a bug.
  • Tests never reach the gap. The test codec passes one value to both formats (CompressingCodec.java:111-125), so the stored-fields constructor rejects a bad value before the term vectors one sees it. No upstream test passes a term vectors value outside 2 to 22, and no PR review comment, issue comment, MIGRATE or CHANGES entry documents a shift or a range for this argument.
The devil's-advocate check134 words

The strongest counter-argument (a summary of the verifiers' intended-behaviour arguments): since 8.5 the value is meant to be a shift; the writer calls it blockShift and every in-tree caller passes a valid shift, so only the javadoc is stale. The class is experimental and the failure is loud.

Why it does not settle it. The code's validation is wrong too, not just the text, and the authors' intent is visible in the twin, which got the range check in the same commit. @lucene.experimental marks API instability, not permission for the check and the writer to disagree. Loud is not harmless here: the failure comes late, closes the writer and drops uncommitted documents, for a value the javadoc describes (1024) or the constructor's own minimum (1). The argument does hold for impact, hence priority Low.

Suggested fix

#

Recommended Range-check in the constructor, like the stored-fields twin (fix A)

In the constructor, check the value against DirectMonotonicWriter.MIN_BLOCK_SHIFT..MAX_BLOCK_SHIFT and document it as "the log in base 2 of the number of chunks", exactly as the stored-fields twin does. The repro then passes, and with it the two term vectors format suites run 44 tests with 0 failures.

if (blockSize < DirectMonotonicWriter.MIN_BLOCK_SHIFT
    || blockSize > DirectMonotonicWriter.MAX_BLOCK_SHIFT) {
  throw new IllegalArgumentException(
      "blockSize must be in "
          + DirectMonotonicWriter.MIN_BLOCK_SHIFT
          + "-"
          + DirectMonotonicWriter.MAX_BLOCK_SHIFT
          + ", got "
          + blockSize);
}

Downstream note

#

A product that exposed this format's blockSize as a user setting would see a bad value only at the first flush with term vectors, as a closed IndexWriter, not when the setting is applied.

How it was found

#

A proof-obligation audit of the term vectors format's constructor contract: every value its javadoc and check accept must be usable by the writer. Following the value showed it reaches a check that allows only 2 to 22; a one-test public-API JUnit then witnessed the failure on main.

The method in full135 words

Registry title
Lucene90CompressingTermVectorsFormat documents and validates its last argument, blockSize, as a chunk count (>= 1), but the writer uses it as a DirectMonotonic block shift limited to [2, 22], so values such as 1024 or 1 are accepted and the first flush with term vectors throws and closes the IndexWriter (since 8.5.0)
Area
core / codecs: compressing term vectors format (Lucene90CompressingTermVectorsFormat blockSize validation; FieldsIndexWriter, DirectMonotonicWriter)
Priority
Low, rank 713: A custom codec that gives the experimental Lucene90CompressingTermVectorsFormat a blockSize of 1, or a chunk count such as 1024 as its javadoc describes the argument, closes the IndexWriter at the first flush with term vectors and loses the uncommitted documents, in every release since 8.5.0. Stock codecs are unaffected, the failure is loud and comes at the first flush, and the committed index stays intact.
Impact class
minor
Impact note
Only applications with a custom codec that constructs this @lucene.experimental format with blockSize 1 or 23 and above (for example 1024, a chunk count as the javadoc describes and the in-tree value before 8.5.0) are hit, at the first flush of a segment with term vectors, which throws IllegalArgumentException and closes the IndexWriter, so documents added since the last commit are lost [exec, -ea and -da]; stock codecs pass 10 and are not affected, no scale is needed, and every release from 8.5.0 through 10.6.0 is affected. The impact class is minor, not crash: a loud, deterministic first-flush failure of a hand-built codec on an experimental format, with no wrong results and the committed data intact.
Summary
You build a custom codec whose term vectors format is new Lucene90CompressingTermVectorsFormat(..., blockSize) and, as its javadoc says ('the number of chunks to store in an index block'), pass a chunk count such as 1024; the constructor accepts it, since it rejects only values below 1. You expect a format that writes and reads term vectors, or an IllegalArgumentException from the constructor, as the stored-fields twin Lucene90CompressingStoredFieldsFormat gives for the same argument. Instead the value goes unchanged to the writer, which uses it as a DirectMonotonicWriter block shift, so addDocument succeeds and the first flush with term vectors (here DirectoryReader.open(writer) or commit) throws 'blockShift must be in [2-22], got 1024' and closes the IndexWriter; blockSize 1, the constructor's own minimum, fails the same way.
Introduced
136dcbdbbced7c2d32b4d244ca99ace2c59baee8 on the main line (first release 9.0.0) and its branch_8x cherry-pick 597141df6b6a017fced16ec27b8fd180e9a6fcc2 (first release 8.5.0), the same change: LUCENE-9147 'Move the stored fields index off-heap' by Adrien Grand (apache/lucene-solr PR #1179, migrated issue #10187).
