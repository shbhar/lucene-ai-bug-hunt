PackedQuadPrefixTree in a geo context stores a point at longitude +180 in the -180 edge cell but looks it up in the +180 edge cell, so a query for that same point misses the document

With the opt-in PackedQuadPrefixTree in a geo context, a document at longitude +180 is not found by a query for the same point: Pt(180, 10) gets 0 hits from RPT Intersects and Contains (default settings) and from CompositeSpatialStrategy, 1 at -180. Affected since 8.3.0; a small fix needs no reindexing.

The bug in 30 seconds

#

A prefix tree files each indexed shape under grid cells, and a query looks it up by the same cells. Here the two sides pick different cells for one point: indexing files (180, 10) at the west edge of the map, the point query looks at the east edge. Both edges are longitude 180, but they are different cells.

  1. You index one document at Pt(180, 10) with RecursivePrefixTreeStrategy over new PackedQuadPrefixTree(SpatialContext.GEO, 8) and search Intersects, or Contains, with that same point.
  2. You expect 1 hit: a point intersects and contains itself, and a point query has zero distance error, so it is matched at the tree's full depth, where the point was indexed. The same point at -180, QuadPrefixTree at +180, and a rectangle query [179, 180] x [9, 11] all give 1.
  3. You get 0 hits, and CompositeSpatialStrategy over the same tree also gets 0. No error.
  4. Why: +180 and -180 are the same meridian, so both top cells, [-180, 0] x [0, 90] and [0, 180] x [0, 90], contain (180, 10). Indexing keeps the first in Z order, the west one, and ends at the -180 edge: leaf [-180, -178.59] x [9.84, 10.55].
  5. The query walks mid-points instead (since 8.3.0): 180 is east of every mid-point, so it ends at the +180 edge, [178.59, 180] x [9.84, 10.55], a cell with no document in it.

Who is affected

#

Applications that index geo points with RPT, or CompositeSpatialStrategy over it, on the opt-in PackedQuadPrefixTree and search for a point at exactly longitude +180: that document is silently missing. Such data is uncommon; no report was found since 8.3.0. Other longitudes, RPT Intersects with pointsOnly=true and geohash are unaffected; rectangle and circle queries showed no such misses.

Mechanism, terms and numbers903 words

With PackedQuadPrefixTree in a geo SpatialContext, a document indexed at longitude exactly +180 is not found by a query for that same point. For one document at Pt(180, 10) and an 8-level tree, RPT Intersects (with pointsOnly=false), RPT Contains and CompositeSpatialStrategy Intersects return 0 hits instead of 1; the same point at -180, QuadPrefixTree and a rectangle query that touches +180 find it. Indexing and querying use two different point-to-cell rules. PrefixTreeIterator stores the point in the first cell in Z order whose rectangle relate()s to it, and a geo rectangle treats +180 as -180, so the point lands in the cells at the -180 edge. A point query descends with getCell, a mid-point walk that LUCENE-8755 introduced in 8.3.0, and that walk sends x = +180 to the cells at the +180 edge. Every release from 8.3.0 to 10.5.2 and main is affected, with no error and the index intact; 8.2.0 passes. A small fix in getCell (one if: treat +180 as -180 in a geo context) makes the query look where the document is, needs no reindexing, and passes the repro and the module's tests.

Terms

#
  • Prefix tree (grid): PackedQuadPrefixTree splits the world into 4 cells per level (a quad tree) and stores each cell as a term. RecursivePrefixTreeStrategy (RPT) indexes a shape as the terms of the cells it touches; a point is stored as one path of cells, from the top level down to a leaf at the tree's maximum level.
  • Z order: the four children of a cell are visited as NW, NE, SW, SE.
  • Geo wrap: in SpatialContext.GEO, longitude +180 and -180 are the same meridian, and a spatial4j rectangle that starts at -180 relates to x = +180 as if it were -180.

Step 1: indexing keeps the first cell that relates

#

PackedQuadPrefixTree.getTreeCellIterator (PackedQuadPrefixTree.java:183-190 at a9779ef3c193) returns a PrefixTreeIterator. Its hasNext (:468-503) walks the children in Z order, keeps the first whose rectangle relate()s to the shape (:476), and for a Point stops at the first leaf (:489-491). On main, [-180,0] x [0,90] relate Pt(180,10) is CONTAINS, and so is [0,180] x [0,90]. NW comes first, so the point goes west, and in every later level the westmost child again relates first.

Step 2: the point query walks mid-points

#

A point query descends with LegacyCell.getNextLevelCells(Point) (LegacyCell.java:134-143), which calls getSubCell(point), here PackedQuadPrefixTree.getCell(p, level + 1) (PackedQuadPrefixTree.java:342-345). getCell (:90-128) compares the point with each cell's mid-point using QuadPrefixTree.battenberg (QuadPrefixTree.java:223-235): xmid >= xp goes west, otherwise east. 180 is greater than every mid-point, so the walk goes east at every level.

Tree depth (executed at depths 1 to 8 for every strategy and operation; the scope below is at 8 and 26 levels). Contains misses at every depth, a 1-level tree included: ContainsPrefixTreeQuery starts at the world cell and descends with getNextLevelCells(point) (ContainsPrefixTreeQuery.java:88-89, 120), which picks the east level-1 cell. RPT Intersects (pointsOnly=false) finds the document on a 1-level tree, because the visiting queries clamp the scan level to maxLevels - 1 (AbstractVisitingPrefixTreeQuery.java:61) and scan the world cell with relate(), and misses from 2 levels on (the independent reproducer: 30 of 36 misses over levels 1, 2, 5, 12, 20, 29 and six latitudes, the north pole included; the south pole misses too in this doc's probes). The optimized composite Intersects, which uses RPT's default scan level maxLevels - 4 (RecursivePrefixTreeStrategy.java:62-63), finds the document up to 4 levels and misses from 5 on.

Which queries take the mid-point walk

#
  • RPT Intersects with a point (RecursivePrefixTreeStrategy.java:185-188, 216-237): with pointsOnly=true it builds a TermQuery from the index-side iterator and finds the document; with pointsOnly=false it builds an IntersectsPrefixTreeQuery, which descends with getNextLevelCells, and misses.
  • RPT Contains (ContainsPrefixTreeQuery.java:106-142) descends with getNextLevelCells: misses with either pointsOnly value. RPT IsWithin finds the document.
  • CompositeSpatialStrategy optimized Intersects, the default, builds IntersectsRPTVerifyQuery (CompositeSpatialStrategy.java:122-134), a visiting descent: misses with either value, as does composite Contains. Composite IsWithin, Equals, Overlaps and non-optimized Intersects take their candidates from RPT Intersects, so they miss only when the composite's RPT has pointsOnly=false.

Why QuadPrefixTree and other longitudes are fine

#

QuadPrefixTree got the same mid-point getCell in the same commit, but it also indexes points with getCell (LegacyPrefixTree.java:62-83): one rule on both sides. Inside the world both rules break ties the same way (west on an x tie, north on a y tie) and the geo bounds are exact in binary, so only the wrap at +180 separates them. An SMT check (Z3, exact rationals) found the rules agree in every cell without the wrap and, on the level-1 split of the geo world, differ only at x = +180. Executed controls: -180, Math.nextDown(180), 179.9, 0 and 90 are found.

Why it is a bug, not intended

#
  • A point intersects and contains itself, and a point query has zero distance error.
  • Reviewing the change that introduced this, its committer (dsmiley) named "exact point lookup of itself should round-trip" as a use case that must keep working.
  • The same tree finds the point written as -180; QuadPrefixTree finds it at +180.
The full argument363 words
  • Contract. SpatialArgs#getDistErrPct / #getDistErr: the error "effectively inflates the size of the shape but should not shrink it" (SpatialArgs.java:118-119, 134-135). PrefixTreeStrategy#setDistErrPct: "Points don't use this as they are always indexed at the configured maximum precision" (PrefixTreeStrategy.java:102-103), and for a Point query the distance error is 0 (SpatialArgs.java:60-61), so the query runs at the full depth (QuadPrefixTree.java:117-119). SpatialOperation.Intersects.evaluate(p, p) and Contains.evaluate(p, p) are true (the repro asserts it). CompositeSpatialStrategy: "RPT acts as an index to the precision available in SDV" (CompositeSpatialStrategy.java:38).
  • Legal input. Pt(180, y) is inside the SpatialContext.GEO world bounds. spatial4j keeps x = 180: WKT POINT(180 10) gives x = 180, and with normWrapLongitude=true normX(180) and even normX(540) are 180. No Lucene javadoc asks callers to rewrite +180 as -180 (spatial4j's javadoc was not checked).
  • Stated intent. In the review of apache/lucene-solr#824 (the PR behind LUCENE-8755), dsmiley, who then committed the change, asked to keep the old tokenization available because otherwise "some use-cases with existing indexes may break, like exact point lookup of itself should round-trip". Upstream testPackedQuadPointsOnlyBug indexes one point on a packed-quad tree and expects 1 hit for Intersects with that same point (non-geo world, one level, pointsOnly=true, the TermQuery path this bug does not break; TestRandomSpatialOpFuzzyPrefixTree.java:143-152); the randomized checks fail with "Should have matched" when an indexed shape is missed (:416).
  • Precedent. In 2017 a packed-quad "index a point, search by the same point" failure with a different cause was fixed as a bug (LUCENE-7845, fixed by LUCENE-7859, 38741ece587).
  • The rules used to agree. Before 8.3.0 getCell used the same "first relating cell in Z order" search as the iterator. LUCENE-8755 replaced it with the mid-point walk to fix an exception at high-precision cell edges in a non-geo world, and left the iterator unchanged; neither the issue nor the PR mentions the dateline or longitude 180.
  • Why the tests missed it. The randomized packed-quad tests run in a non-geo [0, 256] x [-128, 128] world (TestRandomSpatialOpFuzzyPrefixTree.java:97-112, factory.geo = false); the only geo packed-quad test, TestDistanceStrategy (PackedQuadPrefixTree(ctx, 25) with SpatialContext.GEO, TestDistanceStrategy.java:43, 55), never uses longitude +180.
The devil's-advocate check161 words

The strongest case for "works as designed": +180 and -180 are the same meridian and spatial4j's rectangle relate() deliberately treats them as one, so storing the point at the -180 edge is defensible; an application could normalize to -180; and the classes are @lucene.experimental, with approximate filtering.

Why it fails: no Lucene documentation states a normalization requirement, and spatial4j's own normalization keeps +180; the query uses the very same Point that was indexed, so the library disagrees with itself, not with the caller; a point query has zero distance error, so no documented approximation explains a miss; the change's committer named exact point round trip as something that must keep working; and the same tree finds -180 while QuadPrefixTree finds +180. @lucene.experimental lowers the severity, not the fact that a document cannot find itself. The intended-behaviour devil's advocate found no documented, accepted or misuse argument, and the intended-lens reviewer from another model family (OpenAI GPT-5.6) rated the "intended" argument weak.

Suggested fix

#

Recommended Query side: look up +180 where indexing put it (one if in getCell, no reindexing)

In PackedQuadPrefixTree.getCell, treat x = +180 as -180 when the context is geo, so the query looks in the cell where indexing put the point. One if, no reindexing, no format change. The repro and the whole spatial-extras test suite (123 tests) pass; around the antimeridian it removes all 60 misses and adds none.

Query side: look up +180 where indexing put it (one if in getCell, no reindexing) (validated by the checks) (recommended)

#

At the start of PackedQuadPrefixTree.getCell, map x = +180 to -180 when ctx.isGeo(). Point queries then descend into the -180 edge cells, where PrefixTreeIterator stored the point. The finder wrote this fix; the independent reproducer, the cross-model reviewers and the adjudication ran it.

Trade-offs

  • No reindexing: stored terms do not change, so existing indexes are found again at once.
  • Same answers as the existing TermQuery shortcut. With pointsOnly=true, RPT Intersects already builds its term from the index-side iterator, so on stock main a +180 query matches both a +180 and a -180 document. After the fix RPT with pointsOnly=false gives the same answers: hits for (doc x, query x) = (+,+), (+,-), (-,+), (-,-) go from 0, 1, 0, 1 to 1, 1, 1, 1. A -180 document returned for a +180 query is an RPT candidate: RPT is documented as "a fast approximate spatial search filter" (PrefixTreeStrategy.java:39-40), and its pointsOnly TermQuery path already returns it today; the composite strategy checks the exact geometry and returns only exact matches (0 for mixed signs, before and after).
  • A public method changes its answer at one coordinate: getCell(Point, int) is public; in a geo context it now returns the -180 edge cell for x = +180. Its callers inside spatial-extras are PackedQuadCell.getSubCell and LegacyPrefixTree.getDistanceForLevel (world centre, x = 0, unaffected). The survey covers Lucene's spatial-extras only: code outside Lucene that calls the public getCell and relies on the east cell for +180 would get the west cell.
  • A special case for one meridian, matching what the indexer already does; only the geo wrap can make the two rules disagree. Cost: one comparison per call.
  • A design choice for maintainers: spatial4j's geo rectangles treat +180 and -180 as one meridian, while exact point relations treat Pt(180, 10) and Pt(-180, 10) as different points. Maintainers may prefer a wider policy (normalize point longitudes in one place, or let the index follow getCell); this fix is the smallest change that keeps existing indexes working, not the only defensible design.
  • Same method as another hunt fix: LFV-316 also changes getCell for a different cause (floating-point mid-point drift with non-power-of-two non-geo bounds); with its fix applied this bug still reproduces (3 of 6), so offer the two together or in sequence.

Index side: store a point along the getCell path (needs a reindex)

#

Make PrefixTreeIterator store a Point along the mid-point path (or pick the east cell for +180), so both sides use one rule, as QuadPrefixTree does.

Trade-offs

One rule everywhere, but existing indexes keep the -180 cells and must be reindexed; until then the pointsOnly TermQuery shortcut, which builds its term with the same iterator, would start missing the old documents too. It also changes the stored terms of new documents. Not run.

Fall back to the old relate-based search at the wrap only

In getCell, use the old buildNotRobustly search (still in the class) when ctx.isGeo() and x = +180.

Trade-offs

Same answers as the recommended fix by construction (it is the indexer's rule), more code. Not run.

Workaround for users today (not a fix): write +180 as -180 on both sides

#

Rewrite longitude +180 as -180 before indexing and before querying. On stock main a document at -180 queried at -180 is found in all 216 combinations tried (RPT with either pointsOnly value, the composite strategy optimized and general with either value; Intersects, Contains, IsWithin; six latitudes; 8 and 26 levels).

Trade-offs

Downstream note

How it was found

#

A bounded differential check compared the strategies with exact geometry on a lattice of points, rectangles and circles in the geo context (including +/-180 and the poles) over three tree types. Beyond exact-boundary cases that the quad tree shows equally, the extra packed-quad misses were point queries at +180; a cell probe and an SMT check located the two rules.

The method in full247 words

Method: bounded differential check of the stock main jars against exact geometry (semi-formal tier), in a hunt unit on spatial-extras composite and prefix-tree queries.

  • A harness indexed a lattice of points, rectangles and circles in SpatialContext.GEO (including longitude +/-180 and the poles) and compared CompositeSpatialStrategy (optimized and general path), RecursivePrefixTreeStrategy and TermQueryPrefixTreeStrategy with SpatialOperation.evaluate on the stored shapes, over geohash, quad and packed-quad trees, levels, distErrPct, prune and prefixGridScanLevel settings.
  • Both quad trees showed the same exact-boundary misses (for example a line lying exactly on a circle's rim, which RPT Contains misses with QuadPrefixTree too). On top of those, the packed-quad tree had extra RPT and composite false negatives and term-query vs RPT disagreements on points, for most classes exactly 192 more than the QuadPrefixTree control (the number of +180 point-query cases), and every printed example was a point query at x = +180; the control had none of these extras.
  • A cell-level diagnosis printed the two different leaves, and an SMT check (Z3, exact rationals) showed the index-side and query-side point-to-cell rules agree in every cell without the longitude wrap and, on the level-1 split of the geo world, differ only at x = +180.
  • The finding was reduced to a 6-method public-API JUnit and checked by an independent reproducer, an intended-behaviour devil's advocate, reviews by a model from another family (OpenAI GPT-5.6) that ran their own tests, an adjudication, a history, prior-report and security follow-up, and an audit. Found 2026-10-27 on main a9779ef3c193.

Bug record

LFV-705, snapshot of 2026-10-29

Registry title
PackedQuadPrefixTree in a geo context indexes a point at longitude +180 under the -180 edge cell, but point queries look in the +180 edge cell, so RPT and CompositeSpatialStrategy Intersects/Contains with that same point miss the document
Area
spatial-extras / prefix trees: PackedQuadPrefixTree point-to-cell lookup (RecursivePrefixTreeStrategy and CompositeSpatialStrategy point queries)
Priority
Low, rank 353: The experimental PackedQuadPrefixTree silently misses a point at exactly longitude +180, a boundary-value point miss with the same profile as LFV-316 and LFV-371.
Impact class
silent wrong results
Impact note
Applications that index points with RecursivePrefixTreeStrategy, or CompositeSpatialStrategy over it, on the opt-in, @lucene.experimental PackedQuadPrefixTree in a geo SpatialContext (any maxLevels >= 2; Solr exposes it as prefixTree=packedQuad) silently lose a document stored at exactly longitude +180 when they query that same point: RPT Intersects with pointsOnly=false, RPT Contains with either pointsOnly value, the default (optimized) composite Intersects and Contains with either value, and composite IsWithin/Equals/Overlaps when the composite's RPT is not pointsOnly; nothing throws and the index is intact, while RPT pointsOnly=true Intersects, RPT IsWithin, TermQueryPrefixTreeStrategy, the rectangle and circle queries of the finder's sweep, x=-180, Math.nextDown(180), QuadPrefixTree and geohash are unaffected; default IndexWriterConfig, codec and searcher, any index size, -ea and -da, every release from 8.3.0 to 10.5.2 and main.
Summary
You index a point at longitude +180, for example Pt(180, 10), with RecursivePrefixTreeStrategy over PackedQuadPrefixTree(SpatialContext.GEO, 8) and query Intersects or Contains with that same point; the document must match, since a point intersects and contains itself and the prefix-tree approximation may only add matches (SpatialArgs: the error 'should not shrink' the shape). Instead the query returns 0 hits, and so does CompositeSpatialStrategy's Intersects: indexing keeps the first cell in Z order whose rectangle relate()s to the point, and a geo rectangle treats +180 as -180, so the point is stored in the cells at the -180 edge, while the point query's cell lookup (PackedQuadPrefixTree.getCell, a mid-point walk since LUCENE-8755 in 8.3.0) sends x=+180 to the cells at the +180 edge. The same point at -180, QuadPrefixTree, and a rectangle query touching +180 still find the document.
