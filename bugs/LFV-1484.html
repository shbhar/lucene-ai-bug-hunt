Monitor's term presearchers can silently miss a matching term query on a term that is not UTF-8 text, because TermsEnumTokenStream decodes past the end of the term

A default Monitor can silently miss a TermQuery for a document that contains its term, when the term is not UTF-8 text: a binary key, or the collation key of an ordinary word. The presearcher's decoder reads past the term's end, so query and document can get different tokens.

The finding in 30 seconds

#

A Monitor does not run every registered query against every document. A presearcher first selects candidates by looking up the document's terms among terms extracted from each query. To compare terms it turns each one into a text token, and for some terms that step also reads bytes that do not belong to the term.

Background: three pieces

#
  1. A Monitor holds registered queries. match(document) reports the queries that match the document.
  2. The presearcher makes this fast. At register it extracts a small set of terms from each query, one of which a matching document must contain, and stores them in a query index. At match it looks up the document's terms there, and only the queries it finds are run. Presearcher.NO_FILTERING skips this step and runs every query.
  3. A term is a byte string. Text terms are UTF-8. A binary StringField value and a collation key are terms too, and they need not be valid UTF-8.

The finding, step by step

#
  1. Register one query in a default Monitor: a TermQuery on the field id whose term is the single byte C8, a binary key.
  2. Match a document that holds the same id in a StringField, followed by a second field tag = abc. The document contains the query's term, so you expect 1 match. Presearcher.NO_FILTERING reports 1.
  3. You get 0 matches and no error, with assertions on and off. Without tag, or with tag added before id, the same Monitor reports 1.
  4. Why: the Monitor runs this query only if its presearcher finds the query's term among the document's terms, and it compares the two as text. C8 starts a two-byte UTF-8 character, so the decoder also takes the next byte in memory: 00 for the query (token U+0200), 03 for the document (token U+0203; 03 is the length byte of abc). The tokens differ, so the query is never run.
  5. Ordinary words hit it under a collation analyzer: with ICUCollationKeyAnalyzer at PRIMARY strength, the query for the Russian word день (day) gets 0 matches for a document with день in one field and a second field after it. A term whose last byte is F0 or above can instead make Monitor.register or Monitor.match throw ArrayIndexOutOfBoundsException (F8 and above only without assertions).

Who is affected

#

Applications that run a Monitor with the default or the multipass presearcher over terms that are not UTF-8 text: binary keys, or a stock ICU collation analyzer (without assertions, 164 of the 1,000 most frequent Russian words at PRIMARY strength). Silent, default settings, since 8.2.0. Rare: plain UTF-8 text is not affected.

Mechanism, terms and numbers1,402 words

A Monitor runs a registered query against a document only if its presearcher selects it. The default presearcher (TermFilteredPresearcher, Monitor.java:56-58 on main 781025d6fe32) and MultipassTermFilteredPresearcher compare terms extracted from the query with the document's terms, and both sides first turn each of these terms into a character token in TermsEnumTokenStream with charTerm.append(bytes.utf8ToString()); (TermsEnumTokenStream.java:47; query side TermFilteredPresearcher.java:263, document side :110). UnicodeUtil.UTF8toUTF16 reads whole characters "even if this reads past the length passed" (UnicodeUtil.java:635-637), so a term that ends in the first byte or bytes of a multi-byte sequence is completed with whatever lies behind it in memory: unused zero bytes of the query's term pool on one side, the next term of the document on the other. The same term then becomes two different tokens and the query is never run. With the one-byte id C8 and a second field tag = abc after it, the query index holds C8 80, the document looks up C8 83, and Monitor.match reports 0 matches instead of 1, with no error. The stock ICUCollationKeyAnalyzer produces such terms from ordinary words: at PRIMARY strength the query for the Russian word день (day) is missed the same way, and so are, without assertions, 164 of the 1,000 most frequent Russian words (день among them). A term whose last byte is F0 or above can instead make Monitor.register or Monitor.match throw ArrayIndexOutOfBoundsException: F1..F7 with assertions on and off, F9..FF without assertions, and F0 (and F8 without assertions) depending on the bytes behind the term. Terms that are valid UTF-8 are not affected. The line is as old as the module (LUCENE-8766, 8.2.0); the attached test's one-document layout fails from 8.6.0. A validated fix decodes exactly the term's bytes; a stream that works on bytes only, as the module's author suggested on the review thread of pull request #16998, is the larger alternative.

Terms

#
  • Presearcher: new Monitor(analyzer) uses TermFilteredPresearcher (Monitor.java:56-58). At register it extracts a minimal set of terms from each query, "one of which must be present in a document for that document to match" (package-info.java:73-80), and writes them into the query index (TermFilteredPresearcher.java:244-266). For a conjunction the set holds the terms of one child only (QueryTree.java:202-203); a query from which no term can be extracted is stored under a catch-all token that every document looks up (QueryTree.java:119-129, TermFilteredPresearcher.java:136). At match it builds a disjunction of the document's terms and runs it against that index (:100-147). Only the queries it finds are run against the document.
  • Token: both sides pass their terms through TermsEnumTokenStream, which turns a term's bytes into a character token with charTerm.append(bytes.utf8ToString()); (TermsEnumTokenStream.java:42-49, the decode at :47). The query side uses it at TermFilteredPresearcher.java:263 (MultipassTermFilteredPresearcher.java:151, :156), the document side at TermFilteredPresearcher.java:110.
  • The decoder: BytesRef.utf8ToString allocates char[length] and calls UnicodeUtil.UTF8toUTF16 (BytesRef.java:133-141). Its javadoc: "Full characters are read, even if this reads past the length passed (and can result in an ArrayOutOfBoundsException if invalid UTF-8 is passed). Explicit checks for valid UTF-8 are not performed." (UnicodeUtil.java:635-637). A byte C0..DF takes one more byte (:648-649), E0..EF two (:650-653), F0 and above three (:654-661).

The bug

#
  1. A term that ends in the first byte or bytes of a multi-byte sequence is completed with the bytes behind it in the array it lives in.
  2. Those bytes are not the same on the two sides. The query side reads from the query's own BytesRefHash pool (TermFilteredPresearcher.java:270-278, :281-301; BytesRefHash.java:162-167): behind a query's only term lie unused zero bytes. (When one query holds two terms in one field, one of them has the other behind it: a disjunction of C8 and C9 kept as one query missed a document that holds one of the two alone, C8 in some runs and C9 in others.) The document side reads from the document's MemoryIndex (DocumentBatch.java:55-63, :103-114), whose fields share one byte pool (MemoryIndex.java:423, :743, :1290-1293): behind a term lies the next term that was added to the document, starting with its length byte.
  3. So one term becomes two different tokens, the document's token is not in the query index, and the query is not selected. Nothing is reported and nothing fails.

Why it looks unintended

#
  • The presearcher may only skip queries "that have no chance of matching" (module documentation). Presearcher.NO_FILTERING reports this query.
  • The result flips with an unrelated field: the id matches alone or as the last field, not when another field follows.
  • Upstream's own test asserts a match for a non-string term. It passes only because its bytes are all below 80.
The full argument337 words
  • The presearcher's one job. "Queries that match this disjunction are then run against the document. In this way, the Monitor can avoid running queries that have no chance of matching." The devil's-advocate check174 words

The strongest case for "intended": the decoder documents this. BytesRef.utf8ToString: "May throw an AssertionError or a RuntimeException if the data is not well-formed UTF-8." (BytesRef.java:133-136); UTF8toUTF16 documents the read past the length (UnicodeUtil.java:635-637); the BytesRef class note says Lucene uses the class "to represent terms that are encoded as UTF8 bytes in the index" unless otherwise noted (BytesRef.java:25-29). The Monitor's term stream is a character stream that custom query handlers read, and the one upstream non-string test uses 7-bit bytes only.

Why it fails: that is the contract of a low-level utility and it binds its caller, here the Monitor, whose public API takes arbitrary terms and states no UTF-8 limit. What the decoder documents for bad input is an exception; what happens is a silent miss that flips with the order in which a document's fields are added. The terms need not be exotic: the stock ICU collation analyzer produces them from ordinary words. The argument can excuse the exception outcome as a documented loud failure.

Suggested fix

#

Recommended Decode exactly the term's bytes in TermsEnumTokenStream (validated)

Decode exactly the term's bytes in TermsEnumTokenStream: strict UTF-8, or one char per byte for a term that is not UTF-8. One term then always gives one token. Validated: the test and the monitor module's 182 tests pass, assertions on and off. Tokens of some non-UTF-8 terms change. A bytes-only stream is the larger alternative.

try {
  // strict: reads only the term's own bytes
  charTerm.append(utf8.decode(ByteBuffer.wrap(bytes.bytes, bytes.offset, bytes.length)));
} catch (CharacterCodingException _) {
  // Not UTF-8 (a binary term): one char per byte, so that the same term always gives the same
  // token, on the query side and on the document side
  charTerm.setEmpty();
  for (int i = 0; i < bytes.length; i++) {
    charTerm.append((char) (bytes.bytes[bytes.offset + i] & 0xFF));
  }
}

Decode exactly the term's bytes in TermsEnumTokenStream (validated) (recommended)

#

TermsEnumTokenStream.incrementToken() decodes with a strict UTF-8 CharsetDecoder over exactly the term's bytes. A term that is not UTF-8 becomes one char per byte. The same term then gives the same token on the query side and on the document side, nothing behind the term is read, and nothing throws.

One file, TermsEnumTokenStream.java, +21/-1: five imports, a decoder field (StandardCharsets.UTF_8.newDecoder() with both error actions set to REPORT) and the block below in place of line 47.

try {
  // strict: reads only the term's own bytes
  charTerm.append(utf8.decode(ByteBuffer.wrap(bytes.bytes, bytes.offset, bytes.length)));
} catch (CharacterCodingException _) {
  // Not UTF-8 (a binary term): one char per byte, so that the same term always gives the same
  // token, on the query side and on the document side
  charTerm.setEmpty();
  for (int i = 0; i < bytes.length; i++) {
    charTerm.append((char) (bytes.bytes[bytes.offset + i] & 0xFF));
  }
}

Trade-offs

  • Keeps the character stream. CharTermAttribute stays, so custom query handlers that wrap the term stream keep working (CustomQueryHandler.java:34-35; RegexpQueryHandler.java:89-93 adds a filter that reads chars). That constraint was pointed out by kotman12 on the review thread of pull request #16998 (2026-11-12).
  • Tokens change for some terms. For terms that are not UTF-8 and contain a byte C0 or above: 01 C8 from 01 C8 80 to 01 C3 88; the key of день from 62 1A 28 78 E8 80 80 to 62 1A 28 78 C3 A8 00. Valid UTF-8 terms keep their token, and so do, without assertions, terms whose bytes are all below C0 (with assertions on, a byte 80..BF outside a sequence trips the decoder's assertion today, so such a term has no old token). A persistent query index written before the change holds the old tokens, so queries on such terms would need to be registered again (by reading; not executed).
  • Different terms can still share a token (the invalid one-byte term E9 and the valid C3 A9). For a presearcher that only selects an extra candidate, which the real query then rejects.
  • Cost. One CharsetDecoder per stream and an extra pass for terms that are not UTF-8. No benchmark was run.
  • Java level. The block uses an unnamed catch variable (_, Java 22 and later). That fits main and branch_11x (minimum Java 25; TermFilteredPresearcher.java:274 already uses _). branch_10_6 has minimum Java 21, so a backport there needs a named variable. The diff was compiled on main only.

Downstream note

#

A product that uses the Monitor for alerting or routing on binary keys or collation keys can silently miss a match, or have a register or match call fail, for the terms described here.

How it was found

#

A rule was run as a test: a presearcher may let extra queries through, but it must never drop one that matches. The same query and document went through the default presearcher and through Presearcher.NO_FILTERING, with binary terms. Three terms gave 0 matches for 1. A comparison over 189,056 cases and a byte-level probe then pinned the cause.

The method in full261 words

Method: an executed property check, then a bounded-exhaustive comparison (the study's "non-formal" tier: the first signal came from a test, not from a model).

  • The property. A presearcher may let extra queries through, but it must never drop a query that matches. Presearcher.NO_FILTERING is the reference.
  • First probe. The same TermQuery and document through the default presearcher and through NO_FILTERING, with binary terms: 01 C8, C3 and E2 82 next to a second field gave 0 matches for 1. In a sweep of 2,000 random 8-byte keys without assertions, 480 keys were missed and 14 calls threw.
  • Byte-level probe. It prints the bytes the presearcher indexes for the query and looks up for the document: 01 C8 80 against 01 C8 83, and 81, 84 and 8A for second fields of 1, 4 and 10 bytes.
  • Bounded-exhaustive comparison. Every term of 1 to 3 bytes over a 14-byte alphabet (2,954 terms), 16 document and query shapes and 4 presearcher configurations: 189,056 cases against NO_FILTERING on the stock jars. Without assertions 49,152 fail, every one on a term whose decode reads past its end; 0 fail with the fix.

Registry title
The Monitor's default term presearcher can silently miss a matching TermQuery on a binary (non-UTF-8) term, or throw ArrayIndexOutOfBoundsException from Monitor.register or Monitor.match, because TermsEnumTokenStream's UTF-8 decode reads past the end of the term (every release since 8.2.0)
Area
monitor / presearcher term streams (TermsEnumTokenStream under TermFilteredPresearcher and MultipassTermFilteredPresearcher: binary, non-UTF-8 document and query terms)
Priority
Medium, rank 252: With the default presearcher, a Monitor can silently leave a registered term query out of the matches for a document that contains the term, and register or match can throw, when the term is not UTF-8 text: a binary key, or the key that the stock ICU collation analyzer makes of an ordinary word (without assertions, when another field follows the word, 164 Russian and 165 Arabic of the 1,000 most frequent words of a subtitle frequency list are missed at PRIMARY strength and 52 lower-case Greek at the default strength, but no lower-case English word). It is Medium because the miss is silent, ordinary keys and words can hit it once such terms are used, and the decode is in every release since 8.2.0; it is in Medium because it needs binary keys or a collation analyzer in the optional monitor module and no user report was found.
Impact class
silent wrong results
Impact note
Hits applications that use lucene-monitor with a term-filtering presearcher (the default new Monitor(analyzer), TermFilteredPresearcher or MultipassTermFilteredPresearcher, with or without RegexpQueryHandler) on a field whose terms are not UTF-8 text, and that register term queries on it. Such terms are binary keys (a binary StringField, a custom byte-term token stream) and the collation keys that the stock ICUCollationKeyAnalyzer or ICUCollationAttributeFactory make of ordinary words. A query on a term that ends inside a UTF-8 multi-byte sequence can be silently left out of the matches for a document that contains the term. Examples of such an end, when the decoder reaches the byte as a lead byte: a last byte 0xC0 or above (a quarter of all byte values), or, in an ICU collation key, a byte 0xE0 or above just before the final 00 or a byte 0xF0 or above two bytes before it. Whether the query is left out depends on what lies behind the term in memory: with one document from 8.6.0 on, a field, value or word added after it; with a batch, and before 8.6.0, other values or words of the same field. That is for a query that holds one term: when one query holds two such terms in one field, a document whose only term is one of them can be missed too (a disjunction of {C8} and {C9} kept as one query missed a document that holds one of the two alone: {C8} in some runs, {C9} in others). A term whose last byte is F0 or above can make Monitor.register or Monitor.match throw ArrayIndexOutOfBoundsException: F1..F7 with -ea and -da (in earlier runs Monitor.match also for a document that merely holds a term ending in F4), F9..FF with -da, and F0 (with -da also F8) depending on the bytes behind the term. Measured with ICUCollationKeyAnalyzer (root locale, main 781025d6fe32, without assertions, the word followed by a second field) on the 1,000 most frequent words of a subtitle frequency list per language: 164 Russian and 165 Arabic words are missed at PRIMARY strength and 52 lower-case Greek words at the default strength. Of the English words none is missed in lower case or Capitalized at any strength; in upper case 8 (NEW, NOW, HOW ...) are missed at the default strength with ICU4J 77.1 and 78.3 (10.6.0, the 11.0 branch daa54f2e0cd3 and a40bef9a7870, main 781025d6fe32) and none with ICU4J 79.1 (the 11.0 branch 9d2b5a15427a and main 9965d34e3c77; ICU4J 79.1 came with #17010 on 2026-11-16): which words are hit depends on the collation data of the ICU version, and the Russian, Arabic and Greek counts are the same with ICU4J 77.1, 78.3 and 79.1. Reported in the runs without assertions: the same words as plain UTF-8 terms (StandardAnalyzer and KeywordAnalyzer, 29,912 of 29,912 cases, with assertions too), a document whose only term is the word, the probe's range query with two different bounds over ICU collation keys and, in the runs from 8.6.0 on, the collation doc-values fields. With analysis-common's CollationKeyAnalyzer words were missed only at IDENTICAL strength. Default Monitor settings (the analyzer is the application's choice), one caller thread (a default Monitor also starts its own cache-purge thread), no scale needed. The one-test repro (the binary id {C8}) and the text witness for the Russian word день at PRIMARY strength fail with -ea and -da on 10.6.0, on the 11.0 branch 9d2b5a15427a and on main 9965d34e3c77; the earlier text witness, for NEW, fails with ICU4J up to 78.3 and passes with ICU4J 79.1. The decode is in every release from 8.2.0 to 10.6.0 (the bytecode scan of the 58 release jars), on the 11.0 branch and on main; the versions that were run are listed under affected versions.
Summary
You register a TermQuery on a binary term (for example the one-byte id {C8}, built with Term(String, BytesRef)) in a Monitor with the default presearcher, and match a document that holds the same id in a StringField plus one more field. You expect the query to be reported, as it is with Presearcher.NO_FILTERING, because the document contains the query's term. Instead Monitor.match reports 0 matches with no error: the presearcher turns every term into text with a UTF-8 decoder that, for a term ending in the first byte of a multi-byte character, reads on into whatever bytes lie behind the term, so the query side and the document side get different tokens for the same term and the query is never run; a term whose last byte is F0 or above (F1..F7 with assertions on and off, F9..FF without assertions, F0 and, without assertions, F8 depending on the bytes behind the term) can instead make Monitor.register or Monitor.match throw ArrayIndexOutOfBoundsException. The same miss is reached with ordinary text through a stock analyzer. A default Monitor over ICUCollationKeyAnalyzer (root locale, PRIMARY strength) holds the query that QueryBuilder builds for the Russian word день (day). For a document with день in one field and a second field added after it, it reports 0 matches instead of 1. The collation key of день ends in the bytes E8 00 (the key is 62 1A 28 78 E8 00 with ICU4J 77.1, 78.3 and 79.1). The decoder takes these two bytes for the first two bytes of a three-byte sequence and reads one byte behind the key.
