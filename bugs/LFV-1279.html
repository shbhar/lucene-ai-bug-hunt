CharArraySet.copy(map.keySet()) keeps the map's values, so add() on the copy returns true for a key that is already present

If a CharArrayMap holds a key with a null value, CharArraySet.copy(map.keySet()) returns a set that contains the key, yet the first add of that key returns true instead of false. Only the returned boolean is wrong (membership and size stay right), in every release since 3.1.0.

The finding in 30 seconds

#

A CharArraySet keeps its words as the keys of a CharArrayMap whose values are all one marker, and add reports "new" when put returns a null old value. A copy of a map's key-set view keeps the map's own values, so a key that the map held with null looks new to add.

Background: a CharArraySet is backed by a map with one marker value

#
  1. CharArraySet stores its words in a CharArrayMap<Object>: the words are the keys, and every value is one private marker object, PLACEHOLDER.
  2. add(word) calls map.put(word, PLACEHOLDER) and returns true when put returns null, which in an ordinary set means the word was not there before.
  3. CharArrayMap.keySet() returns a CharArraySet built on the map itself (its add methods throw), so that set's values are the map's real values, which may be null.

The finding, step by step

#
  1. Put one key with a null value into a map, map = new CharArrayMap<>(1, false); map.put("x", null), and copy its key set: Set<Object> copy = CharArraySet.copy(map.keySet()).
  2. copy.contains("x") is true and copy.size() is 1, so you expect copy.add("x") to return false, as java.util.Set.add requires for an element that is already in the set.
  3. Instead copy.add("x") returns true, and addAll(List.of("x")) on a fresh copy reports a change. The size stays 1, and a second add("x") returns false.
  4. Why: a CharArraySet is a map whose values are all one marker, and add returns put(key, marker) == null. keySet() is a set over the map's own table, and copy clones its keys and values, so the copy still holds null for "x" and put returns that null.

Who is affected

#

Only application code that keeps a CharArrayMap with null values, copies its keySet() with CharArraySet.copy, and uses the boolean from add or addAll on the copy, for example to count or de-duplicate new words. Lucene's analyzers are not affected: they wrap every copy read-only and only call contains.

Mechanism, terms and numbers536 words

A CharArraySet is backed by a CharArrayMap<Object> whose values are all one private marker, PLACEHOLDER, and every add overload returns map.put(key, PLACEHOLDER) == null: it decides "new element" from the old value. CharArrayMap.keySet() returns a CharArraySet over the map itself, so that view's values are the map's own values. CharArraySet.copy takes a fast path for any CharArraySet source and clones both the keys and the values of its table. So when the map holds a key with a null value, the mutable copy holds that key with null too, and the first add of the key returns true although contains returns true. addAll reports a change the same way. Membership and size() stay right, the first add replaces the null with the marker, and Lucene's own code never adds to such a copy, so only application code that uses add's result is hit. It is in every release from 3.1.0 to 10.6.0; a 9-line change in copy fixes it.

The numbers

#

A probe on main shows the tables: the map {x=null} has a table of 8 slots with "x" in slot 0 and value null; the copy is a new table with the same key and value null; contains("x") is true and size() is 1. The first add("x") returns true and leaves PLACEHOLDER in slot 0 with size 1; the second returns false; the source map still maps "x" to null. A fresh copy's addAll(List.of("x")) returns true with size 1. Controls return false: a non-null map value, new CharArraySet(map.keySet(), false) (it adds the keys one by one, so every value is PLACEHOLDER), and copy of an ordinary CharArraySet. The add(char[]) and add(CharSequence) overloads return true like add(Object).

Side effect, not a separate claim: a set made with copy(map.keySet()) also keeps references to every value of the source map.

Other routes to the same fast path give the same true: copy(CharArraySet.unmodifiableSet(map.keySet())), and copy of the keySet() of CharArrayMap.copy(map) or of CharArrayMap.unmodifiableMap(map) (executed on main, assertions on and off).

Exposure and likelihood146 words
  • Who is hit. Code that keeps a dictionary-style CharArrayMap whose entries may carry no data (null), takes a mutable copy of its keySet() with CharArraySet.copy, and branches on add's or addAll's result. The first add of each key held with null silently returns true.
  • Default vs opt-in. Default classes, no setting, but a rare call pattern; no public report found since 3.1.0 (2011).
  • Lucene itself. All 41 production calls of CharArraySet.copy in the tree wrap the result in unmodifiableSet (for example StopwordAnalyzerBase.java:55 and EnglishAnalyzer.java:89), and analysis only calls contains, which is right.
  • Scale. None: one key.
  • Not affected. Membership and size(). In-tree, Lucene's own analysis, matching and index are not affected, since no Lucene code adds to such a copy; the direct effect is the wrong boolean returned to application code, which may then act on it.

Why it looks unintended

#
  • CharArraySet.add(Object) overrides java.util.Set.add, which must return false for an element already in the set.
  • null values are legal in a CharArrayMap, and the collection constructor gets the same key set right.
  • The class note about not behaving like a Set "in all cases" lists other deviations, not add's result.
The full argument269 words
  • The contracts. CharArraySet.add(Object) is an @Override of java.util.Set.add (CharArraySet.java:102-105), whose javadoc says: "If this set already contains the element, the call leaves the set unchanged and returns false". Collection.addAll returns "true if this collection changed as a result of the call". copy returns "a copy of the given set as a CharArraySet" (CharArraySet.java:145-153), and keySet() "Returns an CharArraySet view on the map's keys" (CharArrayMap.java:340-343).
  • Null values are legal. CharArrayMap.put accepts a null value, nothing documents a non-null precondition, and EntrySet.contains handles null values explicitly: return v == null ? val == null : v.equals(val); (CharArrayMap.java:492).
  • The class disagrees with itself. new CharArraySet(map.keySet(), false) returns false for the same add; only the copy fast path returns true.
  • History. Before LUCENE-2247, add decided from the key slot: if (entries[slot] != null) return false;. Commit 924d7faa684 (LUCENE-2247, #3323) replaced that with put(..) == null and, in the same commit, made keySet() a values-carrying CharArraySet view and made copy delegate to CharArrayMap.copy, which copies the values. The fast path's comment is about speed, and the #3323 thread does not discuss copies of the view or null values.
  • Tests. No upstream test adds to a copy of a key set: every copy call in TestCharArraySet copies an ordinary CharArraySet, a JDK set or the empty set (TestCharArraySet.java:221-375), and TestCharArrayMap does not test a copy of a key set; its only add assertion is that the view itself rejects add (TestCharArrayMap.java:91-96).
  • Precedent. Lucene fixed an earlier add/contains inconsistency in this class as a bug: LUCENE-1502 (#2576).
The devil's-advocate check152 words

The strongest case for "intended": the class javadoc says CharArraySet "is not a general purpose class" and "implements Set but does not behave like it should in all cases" (CharArraySet.java:24-35); null values in a CharArrayMap are unusual; only a boolean is wrong; and add(String), which copy.add("x") binds to when the copy is typed CharArraySet, has no documented return contract of its own.

Why it fails: the javadoc names its deviations right after that sentence (the Set<Object> element type, toString conversion in add and contains, and the char[] iterator), and a wrong add result is not among them. The repro types the copy as Set<Object>, so it exercises java.util.Set.add itself. The fix is local to copy and costs nothing on add or contains. The cross-model refute pass rated the argument moderate; the adjudication kept medium confidence, noting that a maintainer could point at the class disclaimer.

Suggested fix

#

Recommended A. Reset the copied values in CharArraySet.copy (recommended; validated)

In CharArraySet.copy's fast path, set every copied value to the set's marker where the key is non-null, so the copy is an ordinary set. Validated through gradle: the repro passes with assertions on and off, the core analysis tests (169) and analysis-common (1909) pass, and the formatter check is clean.

     if (set instanceof CharArraySet source) {
-      return new CharArraySet(CharArrayMap.copy(source.map));
+      final CharArrayMap<Object> map = CharArrayMap.copy(source.map);
+      // the source may be a CharArrayMap#keySet() view, whose values are the map's own values;
+      // add() relies on every value of a set being PLACEHOLDER, so reset them
+      for (int i = 0; i < map.keys.length; i++) {
+        if (map.keys[i] != null) {
+          map.values[i] = PLACEHOLDER;
+        }
+      }
+      return new CharArraySet(map);
     }

Trade-offs

One extra pass over the table, in copy only: the same order of work as the two System.arraycopy calls copy already makes. add and contains are unchanged. It resets every copied value, not only the nulls, so the copy stops holding references to the source map's values. For the shared empty map the loop writes nothing.

  • :lucene:analysis:common:test passes with the fix: 339 classes, 1909 tests, 0 failures, 18 skipped (many of its analyzers copy their stop-word and stem-exclusion sets with CharArraySet.copy).
  • :lucene:core:checkGoogleJavaFormat passes with the fix and the test in place.

B. Let add decide from the key slot, as before LUCENE-2247

#

Check for the key first (for example map.containsKey(..), or a package-private CharArrayMap method that reports whether the slot was empty) instead of testing put's old value.

Trade-offs

Not validated. Protects against any other source of non-marker values, but touches all four add overloads, a plain containsKey check costs a second hash on every add, and the copy still holds the source map's values.

C. Document the behaviour on copy and keySet()

#

A javadoc note that copy(map.keySet()) keeps the map's values and that add's result may then be wrong.

Trade-offs

Not recommended: it leaves java.util.Set.add broken for a legal input that a 9-line change fixes.

Downstream note

#

Until a fix ships, code that needs add's result can copy the key set with the collection constructor, new CharArraySet(map.keySet(), ignoreCase), passing the flag the map was built with; it returns false here.

How it was found

#

A semi-formal proof-obligation audit of CharArraySet's contract: java.util.Set.add must return false for an element that is already present, including on a copy of a CharArrayMap key-set view. A public-API JUnit test witnessed the violation on stock main.

The method in full67 words

The obligation comes from java.util.Set.add, which CharArraySet.add(Object) overrides, applied to each way of building a CharArraySet: the constructors, copy of an ordinary set, and copy of a CharArrayMap.keySet() view. Only the last one breaks it. An executable JUnit test on the stock main jars witnessed the violation with assertions on and off; it was then reduced to one method with the copy typed Set<Object>.

History

#

Introduced in 3.1.0 by LUCENE-2247 (924d7faa684, 2010-02-03, #3323), which in one commit made keySet() a values-carrying set view, made copy clone the values and switched add to put(..) == null. Fails on every release run from 3.1.0 to 10.6.0 and on main; 3.0.3 has no CharArrayMap.

Versions tested5 rows

924d7faa684 "LUCENE-2247: Add a CharArrayMap<V> for performance improvements in some stemmers and synonym filters" (Uwe Schindler, 2010-02-03; an SVN commit, no pull request; GitHub issue #3323). Releases before 9.x ran the same steps as a main() written against each era's API. Upstream main f72004515ec2 (2026-11-03) has no commit to either file after 2025-10-10. Not new in 10.6.
