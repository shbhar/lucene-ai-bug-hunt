OpenNLP POS, chunker and lemmatizer filters emit nothing when an earlier filter removes the whole first sentence

When a filter before the OpenNLP POS, chunker or lemmatizer filter removes every token of a value's first sentence (a stop list on Hi., a nouns-only filter on a noun-free sentence), the OpenNLP filter emits no token for the whole value. Affects every release since 9.5.0.

The bug in 30 seconds

#

The OpenNLP tokenizer gives every token the index of its sentence (0, 1, 2, ...). The POS, chunker and lemmatizer filters collect one sentence at a time with a shared helper that assumes the first sentence is number 0.

  1. You keep only nouns and lemmatize them: OpenNLP tokenizer, OpenNLPPOSFilter, TypeTokenFilter allowing NN, NNS, NNP, NNPS, then OpenNLPLemmatizerFilter. They sent him running in the evening. gives [they, evening].
  2. You expect the same [they, evening] for He did not come back. They sent him running in the evening.: its first sentence has no noun, so the type filter removes all of it.
  3. You get []: not a single token for the whole value. No error; the stored text is intact, but none of its terms reaches the index.
  4. Why: the tokenizer numbers sentences 0, 1, 2. The shared helper SentenceAttributeExtractor starts at sentence 0, so when the first token it sees is already in sentence 1 it returns an empty sentence, and all three filters read "empty" as "end of stream".
  5. Same with a stop list {hi, .} before the chunker: Hi. They sent him running in the evening. He did not come back. gives 0 of 12 tokens, while Hi. in the middle gives all 12.

Who is affected

#

Users of the opt-in OpenNLP module whose chain removes tokens (a stop list, a minimum length, a POS type filter) before the POS, chunker or lemmatizer filter. Every value whose first sentence that filter empties, punctuation included (Hi., No., or a first sentence without nouns), indexes nothing. Silent and deterministic; existing indexes need reindexing.

Mechanism, terms and numbers695 words

The OpenNLP POS, chunker and lemmatizer filters read their input one sentence at a time through the shared helper SentenceAttributeExtractor, which starts at sentence index 0. When an earlier filter in the chain removed every token of the value's first sentence, the first token the helper sees belongs to sentence 1, the helper returns an empty first sentence, and the filter takes that as the end of the stream. The whole value then indexes no terms while its stored text stays intact: a nouns-only chain turns He did not come back. They sent him running in the evening. into [] instead of [they, evening]. A removed sentence in the middle is handled correctly. Every release from 9.5.0 to 10.5.2 and main is affected; the 4-line fix in the helper was validated with the module's tests.

Terms

#
  • Sentence index: OpenNLPTokenizer stores, for each token, the number of its sentence in SentenceAttribute: 0 for the first sentence, 1 for the second, and so on (OpenNLPTokenizer.java:31-34; the index starts at -1 at :45 and goes up by one for each detected sentence at :73).
  • Sentence-aware filters: OpenNLPPOSFilter, OpenNLPChunkerFilter and OpenNLPLemmatizerFilter tag or rewrite whole sentences, so they first collect one sentence of tokens through SentenceAttributeExtractor, then emit its tokens one by one.
  • Look-ahead: the helper reads one token past the end of a sentence to see that the index changed, and keeps that token for the next sentence.

The bug, step by step

#
  1. SentenceAttributeExtractor starts with currSentence = 0 (SentenceAttributeExtractor.java:40; reset() sets it back to 0 at :78).
  2. extractSentenceAttributes() (:51-65) reads tokens while currSentence == currSentenceTmp && hasNextToken (:57). Each token it reads is only stored as the look-ahead (:62); the previous look-ahead is added to the sentence (:59-61).
  3. An earlier filter removed every token of sentence 0, so the first token the helper ever sees, They, has index 1. First call: 0 == 1 is false, the loop stops after one token, there is no previous look-ahead to add, and They becomes the look-ahead. The call returns an empty list.
  4. The three filters end the stream when allSentencesProcessed() || nextSentence().isEmpty() is true (OpenNLPPOSFilter.java:52-56, OpenNLPChunkerFilter.java:55-59, OpenNLPLemmatizerFilter.java:66-70). More input is left, but the sentence is empty, so incrementToken() returns false: They and everything after it are lost, and the rest of the input is never read.
  5. In the middle of a stream the look-ahead is never null and only a change of index is tested, so a skipped index (0, 0, 2, 2) still splits correctly. Only the initial value 0 is wrong.
  6. The loss needs a surviving token in a later sentence: if the filter removes every token of a one-sentence value, empty output is correct. If the first two or more sentences are removed, the first index is 2 or more, with the same result.

Exposure and likelihood287 words
  • Who is exposed. Users of the lucene-analysis-opennlp module (factories opennlpPOS, opennlpChunker, opennlplemmatizer, or the classes) whose chain puts a token-removing filter before a sentence-aware OpenNLP filter: StopFilter, LengthFilter and a TypeTokenFilter on POS tags were executed; any filter that can drop every token of a sentence works. The module is opt-in, and no documented example, upstream test or third-party configuration found uses such a chain (they keep the OpenNLP stages together and put TypeTokenFilter last).
  • What it takes. The filter must remove every token of the value's first sentence, punctuation included: a short opener such as Hi. or No. under a stop list or a minimum length, or any first sentence without a noun under a nouns-only filter. Once such a chain exists, it fires on every value of that shape.
  • Effect. The whole value indexes no terms (as long as a later sentence keeps a token): no exception, no log line, CheckIndex clean, stored text intact. Deterministic, with assertions on and off, at any size. In a differential run on 404 generated documents, the POS filter's output in the chain tokenizer, StopFilter, POS differed from the library reference for 17 documents; with the fixes, for none.
  • Query side. If the same chain analyzes queries, a query text whose first sentence is removed builds no query at all (QueryBuilder returns null).
  • Offsets. Values longer than 1024 chars end with a premature final offset (1024 in the repros), which shifts the offsets of later values of a multi-valued field.
  • Lasting. Documents indexed with an affected chain keep the empty field until reindexed.
  • How likely. Rare: it needs a legal but undocumented chain shape, and nobody has reported it since 9.5.0 (2023).

Why it is a bug, not intended

#
  • The POS filter "Tags all terms"; the chunker and lemmatizer only annotate or rewrite terms. None removes tokens, and the chunker only requires an order, not adjacency.
  • A removed sentence in the middle is handled correctly; only the starting value 0 is wrong.
  • #11734, which added this code, fixed these same filters losing tokens or ending the stream early.
The full argument268 words
  • The contracts. OpenNLPPOSFilter.java:32: "Run OpenNLP POS tagger. Tags all terms in the TypeAttribute." OpenNLPChunkerFilter.java:32-36: "Prerequisite: the OpenNLPTokenizer and OpenNLPPOSFilter must precede this filter. Tags terms in the TypeAttribute, replacing the POS tags previously put there by OpenNLPPOSFilter." The lemmatizer "Runs OpenNLP dictionary-based and/or MaxEnt lemmatizers" (OpenNLPLemmatizerFilter.java:34) and replaces each non-keyword term by its lemma (:73-76). No javadoc, CHANGES or MIGRATE entry, code comment or test restricts which filters may sit between the stages. SentenceAttribute only "tracks what sentence a given token belongs to" and promises nothing about index 0.
  • Filters between the stages are expected. The lemmatizer reads KeywordAttribute (OpenNLPLemmatizerFilter.java:49, :74, :87) so that keyword filters between POS and lemmatizer work. Upstream tests put KeywordRepeatFilter between the tokenizer and the POS filter (TestOpenNLPPOSFilterFactory.java:150-160) and between the POS filter and the lemmatizer (TestOpenNLPLemmatizerFilterFactory.java:230-238, :301-308, :323-345).
  • The asymmetry. A fully removed middle sentence works, because the helper only tests for a change of index; the initial currSentence = 0 is the only assumption that breaks. Losing the whole value is not a trade-off anyone chose.
  • History. #11734, "Fix repeating token sentence boundary bug", added the helper and fixed the 9.5.0 CHANGES entries GITHUB#11735 "KeywordRepeatFilter + OpenNLPLemmatizer always drops last token of a stream" and GITHUB#11771 "... sometimes arbitrarily exits token stream" (lucene/CHANGES.txt:3859-3863). Its review did not discuss a first sentence whose index is not 0.
  • Nothing pins the current output. No upstream test puts a token-removing filter before a sentence-aware filter; with the fix all 33 upstream tests of the module pass.
The devil's-advocate check278 words

The checkers built the strongest case for "unsupported chain": (1) no documented or example chain triggers it; the factory javadoc, the Solr reference guide, the upstream tests and the third-party configurations found keep the OpenNLP stages next to each other and put TypeTokenFilter after the last one; (2) the module overview says the tokenizer keeps punctuation because "This is required for the following taggers to operate properly" (overview.html:32-36), and the Solr reference guide ("OpenNLP Integration") says "the same tokenization using the same models must be used at runtime for optimal performance"; POS tagging and chunking use the sentence as context; (3) the chunker is excluded from the random-chain tests because "other filters must precede this one (see docs)" (OpenNLPChunkerFilter.java:37). So a maintainer could call removing tokens before the POS filter or the chunker unsupported, and lower tag quality there acceptable.

Why it fails: those notes are about tagging quality, not about losing every token, and nothing in them explains ending the stream for the whole value. For the dictionary lemmatizer the quality argument has nothing to hold on to in the repro: with fix A nouns-only chain gives the same [they, evening] with and without the noun-free first sentence. Nothing restricts in-between filters, upstream tests use them, and the same code handles a removed middle sentence. The cross-model fact check rated the "intended" case moderate before the POS filter and before the chunker, weak before the dictionary lemmatizer. When filing, lead with POS, a nouns-only TypeTokenFilter, then the dictionary lemmatizer, and say the Solr reference guide recommends TypeTokenFilter with POS lists, not that it recommends the triggering chain (it puts the filter last).

Suggested fix

#

Recommended A. Adopt the first token's sentence index in SentenceAttributeExtractor

Let the first token of the stream set the current sentence: in SentenceAttributeExtractor.extractSentenceAttributes(), when the look-ahead is still null, take the token's sentence index as currSentence (4 lines). Validated: the 3 new tests pass, as do all 36 module tests and check; streams that start at sentence 0 behave as before.

       hasNextToken = input.incrementToken();
       int currSentenceTmp = sentenceAtt.getSentenceIndex();
+      if (prevAttributeSource == null) {
+        // first token of the stream: its sentence is the current one, whatever its index
+        currSentence = currSentenceTmp;
+      }
       hasNext = (currSentence == currSentenceTmp && hasNextToken);

A. Adopt the first token's sentence index in SentenceAttributeExtractor (validated by the checks) (recommended)

#

In extractSentenceAttributes() (SentenceAttributeExtractor.java:54-58), when prevAttributeSource == null (the first call after reset()), set currSentence to the first token's index before the comparison. This is the finder's fix.

What it changes. Only that first call. Streams whose first token has index 0 behave exactly as before; an empty stream still returns an empty list, so the filters still end it. All three filters, and any other user of the public helper, are fixed at once.

       hasNextToken = input.incrementToken();
       int currSentenceTmp = sentenceAtt.getSentenceIndex();
+      if (prevAttributeSource == null) {
+        // first token of the stream: its sentence is the current one, whatever its index
+        currSentence = currSentenceTmp;
+      }
       hasNext = (currSentence == currSentenceTmp && hasNextToken);

Trade-offs

  • The smallest change, at the root cause. Indexed terms change only for values that were losing all their tokens.
  • It does not touch the separate lemmatizer bug with sentence-final keyword tokens (a different fix site): in the exhaustive check fix A removes every first-sentence case and that bug's own fix removes the rest (both fixes: 0 of 55,987 lemmatizer cases).

What the checks validated

  • Through the repro harness with the fix shadowed: the new test 3 of 3, the finder's test 3 of 3, the independent reproducer's 5 of 5 and the cross-model review verification test pass.

B. Skip empty sentences in the three filters instead of ending the stream (validated by the checks)

#

In OpenNLPPOSFilter, OpenNLPChunkerFilter and OpenNLPLemmatizerFilter, replace allSentencesProcessed() || nextSentence().isEmpty() by a loop that ends the stream only when allSentencesProcessed() is true and otherwise reads the next sentence while it is empty (do { if (allSentencesProcessed()) return false; } while (nextSentence().isEmpty());).

Trade-offs

Three call sites instead of one, and every other consumer of the helper must do the same; the helper still returns a misleading empty first sentence. It also retries after other empty batches, but each filter first runs its OpenNLP operation on the empty arrays (OpenNLPPOSFilter.java:70-71, OpenNLPChunkerFilter.java:76-77, OpenNLPLemmatizerFilter.java:94-96); that was validated only for the demonstrated case, with the bundled OpenNLP version. A and B can be combined; A alone covers every case found.

What the checks validated

  • The 3 new tests pass with assertions on and off.
  • All of :lucene:analysis:opennlp:test: 6 classes, 36 tests, 0 failures, assertions on and off.
  • Not run through check or the exhaustive harness.

Workaround: put token-removing filters after the last OpenNLP sentence-aware filter

#

For example tokenizer, POS, lemmatizer, then TypeTokenFilter or StopFilter: the order the documented examples use. No code change.

Trade-offs

Not always possible: the chunker replaces the POS tags with chunk tags, so a POS-based TypeTokenFilter cannot simply move after it. Existing documents still need reindexing.

Downstream note

#

Downstream, a keyword screen or a content-based deny rule over such a field misses a document whose text starts with a sentence the chain removes: MUST_NOT body:evening left the example document visible (executed through Lucene's own query API; not run on a downstream product).

How it was found

#

While building an independent reference that calls the OpenNLP library one sentence at a time, the finder suspected the helper's starting index. A bounded-exhaustive check of the real filters then confirmed it: every sentence-index pattern up to 6 tokens, and every case whose first token was not in sentence 0 gave empty output.

The method in full197 words
  • Method (semi-formal): bounded-exhaustive translation validation of the stock main jar, in the hunt's unit on the OpenNLP filters against the OpenNLP library. The finder built an independent per-sentence reference that calls the OpenNLP operations directly, and formed the hypothesis by reading SentenceAttributeExtractor while doing so.
  • Enumeration. Every sentence-index sequence over {0, 1, 2}^n for n <= 6 (and every keyword pattern for the lemmatizer): 1,093 cases each for POS and chunker, 55,987 per lemmatizer variant. Every case whose first token had a sentence index other than 0 gave empty output: 728 for POS, 728 for the chunker, 37,324 per lemmatizer variant, 0 unexplained; with fix A, 0. These count a diagnostic model space that also enumerates gaps and non-monotone index sequences the tokenizer does not emit; they say nothing about how often real text triggers the bug.
  • Real text. A differential run of 404 generated documents through the tokenizer and 10 chains, with the library called directly as the reference, showed the same defect (the POS stage of tokenizer, StopFilter, POS differed for 17 of 404 documents); with both of the unit's fixes shadowed, 0 mismatches.
  • Then a public-API JUnit; independent checkers followed (see "Independent checks").

Impact note
Hits only applications that use the opt-in analysis-opennlp module with a chain that puts a token-removing filter (StopFilter, LengthFilter or a TypeTokenFilter on POS tags, all executed) before an OpenNLP POS, chunker or lemmatizer filter, a legal chain that the documented examples and upstream tests do not use; for them every field value whose first sentence that filter empties completely, punctuation included (a short opener such as 'Hi.' or 'No.', or under a nouns-only filter any first sentence without a noun), silently indexes no terms at all while its stored text stays intact, deterministically, with -ea and -da, at any size, in every release from 9.5.0 to 10.5.2 and main; values longer than 1024 chars also end with a wrong final offset (1024), which shifts the offsets of later values of a multi-valued field; chains with the OpenNLP stages directly after each other are not affected.
Summary
You build an OpenNLP chain that removes some tokens before a sentence-aware filter, for example tokenizer -> POS tagger -> TypeTokenFilter keeping only nouns -> lemmatizer, and analyze 'He did not come back. They sent him running in the evening.', expecting the lemmatized nouns of the second sentence, [they, evening], as you get for that sentence alone. Instead the whole value yields no token: SentenceAttributeExtractor starts with currSentence = 0, so when the first token it receives already belongs to sentence 1 it returns an empty first sentence, and the POS, chunker and lemmatizer filters all treat an empty sentence as the end of the stream. A fully removed sentence in the middle of the text is handled correctly; only the first one is not.
