XYPolygon computes its winding order in float, so XYShape rejects valid polygons with very large coordinates

XYPolygon decides which way a ring turns from float products, which overflow once coordinates differ by about 1.8e19; then, for example, Infinity - Infinity is NaN and the ring gets the wrong label. XYShape then rejects valid polygons, like the triangle (0,0), (1,1), (2,1) times 2^66, as "Unable to Tessellate shape" (since 8.2.0).

The finding in 30 seconds

#

To index a cartesian polygon, Lucene first works out which way round its corners go, from a sum of products of coordinate differences. It computes those products in 32-bit float, which overflows for very large coordinates, so a valid polygon gets the wrong direction and is rejected.

Background: how XYShape indexes a polygon

#
  1. XYShape.createIndexableFields(field, polygon) indexes an XYPolygon, a ring of float x/y coordinates (any finite float is allowed), by cutting it into triangles with the Tessellator (ear clipping) and indexing each triangle.
  2. Ear clipping must walk the ring in one fixed direction. XYPolygon's constructor computes the ring's direction once, from the sign of a signed-area sum (below 0: Lucene labels it CCW; otherwise CW), and the Tessellator reverses the ring when needed according to that label.
  3. A float holds magnitudes up to Float.MAX_VALUE, about 3.4e38. A larger product becomes Infinity, Infinity - Infinity is NaN, and every comparison with NaN is false.

The finding, step by step

#
  1. Index the triangle (0,0), (1,1), (2,1) as an XYPolygon with XYShape.createIndexableFields: you get 1 triangle field. Lucene labels the ring CCW, because its winding sum is 1x1 - 1x2 = -1, below 0.
  2. Multiply every coordinate by 2^66 (about 7.4e19). That is exact in float, the constructor accepts every finite float, and neither the shape nor its orientation changes. You expect it to index the same way.
  3. Instead the two products of the winding sum are 2^132 and 2^133, both above Float.MAX_VALUE (3.4e38), so in float both are Infinity. Infinity - Infinity is NaN, NaN < 0 is false, and the ring is labelled CW.
  4. The Tessellator links the vertices in the order that label implies, so it walks this ring backwards, finds no ear to cut and throws IllegalArgumentException: Unable to Tessellate shape. Possible malformed shape detected. The document cannot be built.
  5. It starts at 2^64, the square root of Float.MAX_VALUE (about 1.8e19): at 2^63 the triangle still indexes. The same triangle listed the other way round still indexes at 2^66, because NaN happens to give it the right label.

Who is affected

#

Applications that index cartesian polygons with XYShape (default codec and settings, both field factories) whose coordinates differ by about 1.8e19 or more, or that index a whole-plane box at +/-Float.MAX_VALUE listed clockwise. That one document is rejected; the defect is not on the query path, other documents and the index are unaffected, and nothing is silently wrong. Rare.

Mechanism, terms and numbers1,003 words

XYPolygon(float[] x, float[] y, XYPolygon... holes) accepts every finite float coordinate and works out the ring's orientation from a signed-area sum: double windingSum accumulates (x[j] - x[n]) * (y[i] - y[n]) - (y[j] - y[n]) * (x[i] - x[n]), and a sum below 0 is labelled CCW, anything else CW. The accumulator is double, but x and y are float[], so both products are float multiplications. Once coordinate differences reach about sqrt(Float.MAX_VALUE) = 1.8e19 (2^64), the products overflow: in the example triangle both products of a term become Infinity, the term is Infinity - Infinity = NaN, and a NaN sum is labelled CW (infinite terms of opposite sign also give NaN, and a single infinite term can give the wrong sign). Tessellator.tessellate(XYPolygon) links the ring in the order the label implies, so a ring whose correct label is CCW is linked backwards; ear clipping finds no ear and XYShape.createIndexableFields / createDocValueField throw "Unable to Tessellate shape. Possible malformed shape detected." for a valid polygon. A whole-plane box at +/-Float.MAX_VALUE listed clockwise fails the same way, through an overflowing difference. Only that document is affected: no wrong triangulation, index damage or query effect was observed. Present since XY shapes were added (LUCENE-8632, 8.2.0) through 10.6.0 and main. The fix is one statement: cast the differences to double before multiplying, as the lat/lon Polygon already computes the same sum.

Terms

#
  • Winding order: the direction a ring's vertices go round. XYPolygon.getWindingOrder() "Returns the winding order (CW, COLLINEAR, CCW) for the polygon shell" (XYPolygon.java:150-153). Lucene labels a negative sum CCW; with y pointing up such a ring runs clockwise (the example triangle does).
  • Fan term: the constructor sums, for each vertex pair (j, i) and the last vertex n, (x[j] - x[n]) * (y[i] - y[n]) - (y[j] - y[n]) * (x[i] - x[n]), twice the signed area of one fan triangle.

The bug, step by step (main 645d4fe14a20)

#
  1. The constructor (XYPolygon.java:48) checks the first vertex and every vertex the loop visits with checkVal (:93, :95, :101, :103; the closing vertex must equal the first, :64, :73), which rejects only non-finite values (XYEncodingUtils.java:35-41; range -/+Float.MAX_VALUE, :28-29).
  2. double windingSum = 0d; (:98), then windingSum += (x[j] - x[numPts]) * (y[i] - y[numPts]) - (y[j] - y[numPts]) * (x[i] - x[numPts]); (:106-107). x and y are the float[] parameters: the differences and both products are float; only the term's result is widened.
  3. Triangle (0,0), (s,s), (2s,s): the first term is 0, the second s*s - s*(2s). Scale 1: -1, label CCW. Scale 2^66: 2^132 and 2^133 overflow to Infinity in float, the term is NaN (in double it would be -5.44e39).
  4. this.windingOrder = (windingSum < 0) ? CCW : CW; (:113): NaN gives CW.
  5. Tessellator.tessellate(XYPolygon, boolean, Monitor) (Tessellator.java:155) converts the coordinates to double (:162-163) and calls createDoublyLinkedList(..., polygon.getWindingOrder(), ..., WindingOrder.CW) (:160-167), which keeps the vertex order when the label is CW and reverses it otherwise (:227-235). The mislabelled ring is linked backwards.
  6. No vertex of a backwards ring is an ear; after the INIT, CURE and SPLIT passes (:670-689) the Tessellator throws IllegalArgumentException("Unable to Tessellate shape. Possible malformed shape detected.") (:687-688; the same message at :206-207 when no triangle was produced).
  7. XYShape.createIndexableFields (XYShape.java:83-85, :96-106) and createDocValueField (:88-90, :109-112) call the Tessellator at :100 and :112 and pass the exception to the caller, before any IndexWriter call.

Exact trigger

#
  • Overflow needs coordinate differences of about sqrt(Float.MAX_VALUE) = 1.84e19 (about 2^64) or more. Once a float product (or a difference) overflows, the label can go wrong in three ways:
    • Infinity - Infinity inside one term: both products of a term overflow with the same sign, so the term and the sum are NaN, labelled CW. This is the triangle: its products are 2^126 and 2^127 at scale 2^63 (finite: labelled CCW, indexes) and 2^128 and 2^129 at 2^64 (both Infinity: labelled CW, rejected).
    • Infinite terms of opposite sign: a term with one overflowing product is +Infinity or -Infinity, and two such terms of opposite sign add up to NaN. The notched square (0,0), (0,2^65), (2^65,2^65), (2^20,2^64), (2^65,0) has terms -Infinity, +Infinity, -Infinity, none with both products overflowing; it should be CCW but is labelled CW and rejected, while its exact 2^-64 copy indexes (fact-check probe).
    • One infinite term that outweighs the rest: a single +/-Infinity term carries that term's sign, which can be wrong for the ring. This path also mislabels rings whose correct label is CW.
    • One overflowing product does not always break the label: the independent reproduction's quadrilateral at 2^63 has two -Infinity terms, the correct sign, and is labelled right.
  • Or a difference overflows by itself: in a whole-plane box from -Float.MAX_VALUE (-M) to +Float.MAX_VALUE (M) listed (-M,-M), (-M,M), (M,M), (M,-M), the first term starts with (x[0] - x[4]) * (y[1] - y[4]): the y-span M - (-M) is Infinity in float and 0 * Infinity is NaN. That listing is rejected; the opposite listing indexes.
  • Mainly rings whose correct label is CCW are hit, because NaN falls back to CW. In the intended-behaviour check's search over about 81,000 random star polygons per orientation, 18, 7 and 2 rings whose correct label is CW were labelled CCW at scales 2e19, 3e19 and 5e19, all through a single infinite term (the fact check's replay). A few wrong labels come from a finite but wrongly rounded sum: 8 of the 4,115 rejected reversed generator rings in the generator check run for the read-only cross-model review. So the root cause is the float evaluation, not only the overflow to NaN.
  • Holes are linked by their own getWindingOrder() (Tessellator.java:260) and are affected too (shown in an exploratory run).
  • Edges parallel to an axis give zero products, so ordinary axis-aligned boxes mostly avoid it.
Exposure and likelihood306 words
  • Who is hit. Callers of XYShape.createIndexableFields or XYShape.createDocValueField (both overloads, either checkSelfIntersections value) with the default codec and IndexWriterConfig; nothing to opt into. Also anyone who reads the public XYPolygon.getWindingOrder().
  • What it takes. Coordinate differences of about 1.8e19 or more, mostly in a ring whose correct label is CCW (the exact-trigger list above has the rarer cases), or a whole-plane box at +/-Float.MAX_VALUE listed clockwise with y up. Typical projected, CAD and game coordinate systems are far below this magnitude. A plausible boundary case for an indexed geometry is such a whole-plane polygon; an ordinary "match everything" query box (XYShape.newBoxQuery) does not use this code. No user report was found since 2019.
  • What happens. The field factory throws "Unable to Tessellate shape. Possible malformed shape detected.", so that document cannot be built; getWindingOrder() returns CW for a CCW ring.
  • What does not happen. No silent wrong triangulation (0 in the study's 51,240 tessellations; every verifier saw only clean exceptions), no index damage, no effect on other documents. Query geometries never read the winding order (XYShape.newGeometryQuery -> XYGeometry.create -> Polygon2D), so this winding-label defect is not on the query path.
  • Scale in the study's harness. Every simple polygon with 3 to 5 vertices on a 4x4 grid, scaled by 2^66, 2^100 and 2^126 (exact): 21,452 of 51,240 tessellations rejected at each scale, none at scale 1, none with the fix. The share reflects the harness's mix of orientations, not a real-world rate.
  • Why the tests miss it. ShapeTestUtil.nextFloat draws coordinates from the full float range (ShapeTestUtil.java:239-240), but every polygon generator emits the orientation Lucene labels CW, which the NaN fallback gets right, and BaseXYShapeTestCase retries any polygon whose tessellation throws (BaseXYShapeTestCase.java:228-233). Reversed, 4,115 of 10,530 generator rings that index forwards are rejected; 0 with the fix.

Why it looks unintended

#
  • Any finite float is a valid coordinate, and an exact power-of-two scaling cannot change a ring's "winding order".
  • The accumulator is double; float products came in when the original PR made the parameters float[] (its author: "Internally we still use doubles").
  • Tests miss it: their generators emit the orientation NaN gets right, and failed tessellations are retried.
The full argument294 words
  • Any finite float is a valid coordinate. checkVal rejects only non-finite values (XYEncodingUtils.java:34-41); the constructor's other checks are on array lengths, ring closure and nested holes (XYPolygon.java:49-87); upstream TestXYPolygon rejects only NaN and +/-Infinity (testPolygonNaN, testPolygonPositiveInfinite, testPolygonNegativeInfinite, TestXYPolygon.java:81-116).
  • The label describes the ring. getWindingOrder(): "Returns the winding order (CW, COLLINEAR, CCW) for the polygon shell" (XYPolygon.java:150-153; the constructor only ever sets CW or CCW, :113). No javadoc says "scale invariant" in those words; the argument is the meaning of "winding order" plus the accepted range.
  • Both orientations are supported. "should be CCW, but this will correct" (Tessellator.java:157-158), and the linking reverses a ring whose label differs (:227-235). The same triangle listed the other way round indexes at 2^66, so the rejected one is not malformed. The rejected triangle even runs clockwise with y up, the order the lat/lon Polygon javadoc asks for ("Coordinates must be in clockwise order, except for holes", Polygon.java:31); the XYPolygon javadoc names no order.
  • History. Inside the introducing PR (apache/lucene-solr#726, LUCENE-8632), commit 4d0c96f40b8 ("change XYPolygon and XYLine API to accept floats instead of doubles", 2019-06-26) changed the constructor parameters from double[] to float[]; they shadow the then double[] fields and the loop kept reading them. At its parent 1c982b90199 the sum was in double. The author (nknize) wrote in the PR: "Internally we still use doubles for the tessellation but the user must pass floats to the Geometry so it's consistent with the encoding." Nobody discussed the winding sum; the PR was squash-merged. LUCENE-9218 (4a54ffb553a, 8.5.0) made the fields float[] and kept the expression.
  • The lat/lon twin is double. Polygon computes the same sum on double[] (Polygon.java:118-134).
The devil's-advocate check283 words

The strongest case for "intended" (built by two of the study's verifiers): the Tessellator class notes say it is "sensitive to overflow (e.g, subatomic values such as E-200 can cause unexpected behavior)" (Tessellator.java:49-50); XYShape warns that vertex values are indexed "with some loss of precision" (XYShape.java:71-72); coordinates near 1e19 are not realistic, and the failure is loud (one document gets an exception), not silent; and the shape test base class retries polygons that fail to tessellate.

Why it fails: the overflow happens in the public XYPolygon constructor, not in the Tessellator, which works in double and tessellates these exact polygons once the label is right; the note is about tiny values and predates XY shapes (it came with the lat/lon shape indexing of LUCENE-8396, b5ef13330f1, 2018); the precision warning is about converting from double, and the XY encoding stores floats exactly (XYEncodingUtils.encode is floatToSortableInt, XYEncodingUtils.java:50-52); "not realistic" and "loud" are impact arguments, not intent: the API accepts the range, Lucene's own random tests draw from it, and the public getWindingOrder() returns a wrong label; and the retry's own comment says it skips shapes the "random polygon generator created" as malformed. On PR #12287 its author, heemin32, pointed out that this retry hides XY tessellation failures, and a reviewer, nknize (the author of XYShape), replied: "That try-catch is intentional. The evil, esoteric / invalid test geometry generation is also intentional so we can maximize our test coverage across the tessellator and Shape indexing." So the retry is a deliberate choice for malformed generated shapes, not a statement that valid shapes may be rejected. The argument is a fair one for low priority, not for intended behaviour.

Suggested fix

#

Recommended A. Compute the winding-sum products in double (one statement)

Cast the coordinate differences to double before multiplying in the winding sum (XYPolygon.java:106-107), as the lat/lon Polygon does: double products of float differences cannot overflow. With it the repro passes with assertions on and off, as do 270 tests in 30 geo and XY-shape test classes and the core module's static checks.

A. Compute the winding-sum products in double (one statement) (validated by the checks) (recommended)

#

Widen each float difference to double before the multiplication. A difference of two finite floats is at most 2 x Float.MAX_VALUE (6.8e38), so each product is at most about 4.6e77, far below Double.MAX_VALUE (1.8e308). Double arithmetic on the float inputs is also far more precise, which also fixed every rounding case the study found. The comment line is optional.

Trade-offs

  • One statement in the constructor; one double multiply-add per vertex, once per polygon.
  • getWindingOrder() changes only where the float and double sums disagree in sign (NaN included); the upstream geo and shape suites pass unchanged.
  • It avoids the float-product overflow but is not an exact orientation predicate: a nearly degenerate ring can still round in double, and a ring whose float sum had rounded to the wrong sign or to 0 gets a new label, so it may be triangulated differently when indexed again.
  • Same arithmetic as the lat/lon Polygon (Polygon.java:126-128).

B. Let the Tessellator compute the orientation itself (not run)

#

Derive the ring's direction in Tessellator.tessellate(XYPolygon) from the double coordinates it already builds (Tessellator.java:162-163) instead of trusting polygon.getWindingOrder().

Trade-offs

A larger change in shared code (the lat/lon path uses the same linking), and the public XYPolygon.getWindingOrder() would still return the wrong label.

Not recommended: reject coordinates above sqrt(Float.MAX_VALUE)

Tighten checkVal so the products cannot overflow.

Trade-offs

Changes documented behaviour, breaks existing whole-plane boxes at +/-Float.MAX_VALUE, and leaves the rounding cases.

Downstream note

#

Services that index user-supplied cartesian polygons will report such a valid polygon as malformed at index time, with Lucene's generic "Unable to Tessellate shape" error.

How it was found

#

Non-formal: while building a checker that runs the Tessellator on every small simple polygon of a 4x4 grid, an AI tool noticed the float products in the constructor. Scaled by exact powers of two (2^66, 2^100, 2^126), 21,452 of 51,240 tessellations were rejected at each scale; none at scale 1 and none with the sum in double.

The method in full114 words

Method: code reading, then measurement with a bounded-exhaustive translation-validation harness (study unit on the geo Tessellator and shapes, main ea57360912ed, 2026-10-26).

  • The harness enumerates every simple polygon with 3 to 5 vertices on a 4x4 grid (12,810 shells, 51,240 tessellations per run) and checks each tessellation for coverage, overlap and area against the polygon.
  • Scaled by 2^66, 2^100 and 2^126 (exact in float and double): 29,788 ok and 21,452 rejected with IllegalArgumentException at each scale; 0 wrong triangulations (no Steiner points, outside or overlapping triangles, or area mismatches). With the winding sum in double: 51,240 ok, 0 rejected.
  • The finder then wrote a public-API JUnit test; the one-test repro was reduced from it.

History

Introduced with XY shapes by LUCENE-8632 (0c09481374c, 2019-07-08), first released in 8.2.0 in the sandbox module and in core since 8.5.0. Finding record

LFV-219, snapshot of 2026-11-01

Registry title
XYPolygon evaluates its winding sum in float, so valid polygons with large finite coordinates (differences of about 1.8e19 or more) can get the wrong winding order, and XYShape rejects them as 'Unable to Tessellate shape'
Area
geo / XY shapes (XYPolygon winding order, Tessellator.tessellate(XYPolygon), XYShape.createIndexableFields and createDocValueField)
Priority
Low, rank 895: XYPolygon's float winding sum overflows for coordinate differences of about 1.8e19, so valid huge-coordinate polygons are rejected at indexing.
Impact class
crash
Impact note
Hits applications that index cartesian polygons with XYShape.createIndexableFields or XYShape.createDocValueField (default codec, IndexWriterConfig and checkSelfIntersections setting; nothing to opt into) when the polygon's coordinates differ by about 1.8e19 or more, or span more than Float.MAX_VALUE as a whole-plane box at +/-Float.MAX_VALUE does: the valid polygon is rejected with IllegalArgumentException 'Unable to Tessellate shape. Possible malformed shape detected.' while its fields are built, so that one document cannot be added, and the public XYPolygon.getWindingOrder() returns the wrong label; mainly rings whose correct label is CCW (clockwise in the usual y-up sense) flip, because NaN falls back to CW, plus a few rings of either orientation through float rounding; holes are affected too, edges parallel to an axis mostly avoid it, and no silent wrong triangulation, index damage, effect on other documents or query-side effect was observed; released since 8.2.0 (sandbox) and 8.5.0 (core).
Summary
You build an XYPolygon with large but finite float coordinates, which the constructor accepts (any finite float), for example the triangle (0,0), (2^66,2^66), (2^67,2^66), and index it with XYShape.createIndexableFields; you expect it to index exactly like the same triangle at scale 1, because multiplying every coordinate by a power of two is exact and changes neither the shape nor its orientation. The constructor computes the winding sum with float products, which overflow to Infinity once coordinate differences reach about 1.8e19; Infinity minus Infinity is NaN, and a NaN sum is labelled CW. The Tessellator then links the ring the wrong way round, finds no ear to cut, and rejects the valid polygon with 'Unable to Tessellate shape. Possible malformed shape detected.'
