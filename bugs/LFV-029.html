RunAutomaton throws ArrayIndexOutOfBoundsException on a 0-state automaton

new CharacterRunAutomaton(new Automaton.Builder().finish()) should give a matcher that rejects every string, but the constructor throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0. Every release since 5.0.0 is affected; queries are guarded, but pattern tokenizers such as new SimplePatternTokenizer("(a&b){2}") hit it.

The finding in 30 seconds

#

RunAutomaton reserves one placeholder state for an input with no states, then loops over it and asks the input for state 0's transitions. Automaton.next reads states[0], but Builder.finish() allocated that array with exactly 0 entries, so it throws. With spare capacity (new Automaton() reserves 4 slots) the same read silently returns zeros, meaning "no transitions".

Background: automata and run automata

#
  1. An Automaton stores each state's transitions as a pointer and a count: state i uses states[2i] and states[2i + 1]. An automaton with 0 states is legal; Automata.makeEmpty() returns one, the empty language.
  2. A RunAutomaton (CharacterRunAutomaton for strings, ByteRunAutomaton for bytes) copies a deterministic automaton into a flat lookup table for fast matching. Its start state is always state 0.
  3. Queries such as RegexpQuery build theirs through CompiledAutomaton; the pattern tokenizers SimplePatternTokenizer and SimplePatternSplitTokenizer build a CharacterRunAutomaton directly.

The finding, step by step

#
  1. Build an automaton that matches nothing with new Automaton.Builder().finish(): 0 states, deterministic, the empty language.
  2. Wrap it in new CharacterRunAutomaton(a). You expect a matcher that rejects every string, run("") = false, which is what the same call gives for Automata.makeEmpty(), also 0 states.
  3. You get ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 from the constructor, with assertions on and off.
  4. Why: RunAutomaton gives a 0-state input one placeholder start state (size = max(1, 0) = 1) and then asks the input for state 0's transitions. Builder.finish() sized the input's state array exactly, 0 x 2 = 0 slots, so reading slot 0 fails. makeEmpty() survives only because new Automaton() reserves 4 spare slots.
  5. The same crash comes from ByteRunAutomaton, Operations.repeat(empty, 2, 2) and patterns built on a bounded repeat {n} or {n,m} (n >= 1) of something that can never match, so new SimplePatternTokenizer("(a&b){2}") throws too (the same operand under {n,}, * or + does not crash). Queries are safe: CompiledAutomaton swaps a 0-state automaton for a 1-state one first.

Who is affected

#

Code that builds a CharacterRunAutomaton or ByteRunAutomaton itself from an empty-language automaton made by Automaton.Builder, new Automaton(0, 0) or Operations.repeat, and the SimplePattern* tokenizers and factories given a pattern built on a bounded repeat {n} or {n,m} (n >= 1) of something that can never match, like (a&b){2}. Not the default; queries are guarded. Loud: an exception, no wrong results.

Mechanism, terms and numbers765 words

new CharacterRunAutomaton(new Automaton.Builder().finish()) throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 instead of returning a run automaton that accepts nothing. The input is a valid deterministic automaton with 0 states, the empty language. RunAutomaton gives a 0-state input one synthetic, non-accepting start state (size = Math.max(1, a.getNumStates())), but then loops over that synthetic state and asks the source automaton for state 0's transitions; Automaton.next reads states[0] of the source. Automaton.Builder.finish() sizes states[] exactly (numStates * 2 = 0 entries), so the read fails. Automata.makeEmpty(), also 0 states, works only because new Automaton() pre-allocates 4 slots. The same crash comes from ByteRunAutomaton, new Automaton(0, 0), Operations.repeat(emptyLanguage, 2, 2) and string patterns built on a bounded repeat {n} or {n,m} (n >= 1) of an empty-language operand, so new SimplePatternTokenizer("(a&b){2}") throws too (the same operand under {n,}, *, + or plain concatenation does not crash). Queries are protected by CompiledAutomaton's 0-state guard. Every release since 5.0.0 is affected: LUCENE-5959 made finish() allocate exact-size arrays.

  • Automaton.java:690-694: the private next reads states[stateIndex] with stateIndex = 2 * state, so state 0 reads states[0].
  • Automaton() is this(2, 2) (Automaton.java:79-82, "creates an automaton with no states"): states has length 4, so the read returns leftover zeros, "0 transitions". That is why Automata.makeEmpty() (Automata.java:55-60) works.
  • Automaton(int numStates, int numTransitions) allocates states = new int[numStates * 2] (Automaton.java:91-92), and Automaton.Builder.finish() builds its result with exactly new Automaton(numStates, numTransitions) (Automaton.java:889-894, "Create automaton with the correct size."). A Builder with no states yields states.length == 0.
  • Regexp route: every bounded repeat {n} or {n,m} goes through Operations.repeat(a, min, max) (RegExp.java:672-674, Operations.java:291-323). For min == 1 it copies the operand into new Automaton() (:299-301), for min >= 2 it concatenates min copies (:302-308); either way it copies the result into a Builder and returns removeDeadStates(builder.finish()) (:311-312, :322), which hands a 0-state input back unchanged (:1010-1011). So for an empty-language operand such as (a&b), # or [^\D\d] and min >= 1 the result has 0 states, exact-size arrays, and reports itself deterministic: (a&b){1}, (a&b){1,3}, (a&b){2}, #{2,10} crash, while (a&b){2,}, (a&b)*, (a&b)+, (a&b)(a&b), x(a&b){1} and (a&b){0,2} do not. Kleene star and intersection return a 0-state input unchanged (:202-204, :396-401), so ((a&b){2})* and (a&b){2}&(a&b){2} crash too, while ((a&b){2})+ and (a&b){2}|(a&b){2} do not (probes on 645d4fe14a20).
  • Tokenizer route: SimplePatternTokenizer(String) ("See RegExp for the accepted syntax") builds new RegExp(regexp).toAutomaton(), checks only determinism and calls new CharacterRunAutomaton(dfa) (SimplePatternTokenizer.java:75-101); the same in SimplePatternSplitTokenizer.java:64-91. SimplePatternTokenizerFactory parses the pattern in its constructor, which succeeds, and the crash appears when create() is called (SimplePatternTokenizerFactory.java:73-75, 87-88).
  • Why queries are safe: CompiledAutomaton replaces a 0-state automaton with a fresh 1-state automaton before it builds a run automaton (CompiledAutomaton.java:154-157). AutomatonQuery builds one (AutomatonQuery.java:99), and RegexpQuery, WildcardQuery, PrefixQuery and TermRangeQuery extend it; FuzzyQuery uses CompiledAutomaton too (FuzzyAutomatonBuilder.java:63, :73). A search of every non-test source file for run-automaton constructions finds three other query-side places, none of which builds one from an exact-size 0-state automaton: TermInSetQuery (only for 2 or more terms, TermInSetQuery.java:185-195), the unified highlighter (Automata.makeString, or makeStringUnion, which returns makeEmpty() for no terms, Automata.java:642-643) and the sandbox TermAutomatonQuery (rewrites an empty automaton to MatchNoDocsQuery, TermAutomatonQuery.java:491-493).

The numbers

#

For new Automaton.Builder().finish(): getNumStates() = 0, states.length = 0, getStartPoints() = [0], so RunAutomaton sets size = 1 and reads states[0] once: Index 0 out of bounds for length 0. For Automata.makeEmpty(): 0 states but states.length = 4, so the read returns 0 transitions and run("") and run("a") are false. A survey of 15 ways to build a 0-state automaton crashes in exactly the cases with states.length = 0.

Exposure and likelihood170 words
  • Who. (a) Code that constructs a CharacterRunAutomaton or ByteRunAutomaton directly from an empty-language automaton built through Automaton.Builder, new Automaton(0, 0) or Operations.repeat(empty, min >= 1, max); (b) SimplePatternTokenizer, SimplePatternSplitTokenizer and their factories with a pattern built on a bounded repeat {n} or {n,m} (n >= 1) of an empty-language operand, such as (a&b){2}, (a&b){1}, #{2,10}, ([^\D\d]){2} or ((a&b){2})*; the same operand under {n,}, *, + or plain concatenation does not crash. Such patterns are valid RegExp syntax; they can never match.
  • Not default. It needs code that builds a run automaton itself, or a SimplePattern* tokenizer or factory configured with such a pattern. Queries build theirs through CompiledAutomaton or never from an exact-size 0-state automaton (source inventory); RegexpQuery on the same patterns returns 0 hits with no exception.
  • Effect. An unchecked ArrayIndexOutOfBoundsException from a constructor instead of a reject-everything matcher. Through a factory the factory constructor succeeds and create() throws. No wrong results, no corruption, no hang.
  • Scale. One call, no index.

Why it looks unintended

#
  • The constructors document one failure only, IllegalArgumentException for non-deterministic input; a 0-state automaton is deterministic, and Automata.makeEmpty() returns one.
  • RunAutomaton reserves a start state for this case (Math.max(1, a.getNumStates())); Lucene's test framework uses new CharacterRunAutomaton(makeEmpty()) as its empty stop set.
  • Only hidden spare capacity decides: makeEmpty() works, Builder().finish() crashes, and 4.10.4 passes the same check (main() form).
The full argument205 words
  • Contract. RunAutomaton.java:55-60: "Constructs a new RunAutomaton from a deterministic Automaton. ... @throws IllegalArgumentException if the automaton is not deterministic". CharacterRunAutomaton.java:21-25 ("Construct from a DFA") and ByteRunAutomaton.java:22-35 document only the same exception.
  • 0-state automata are first-class. Automaton.java:79 "creates an automaton with no states"; Automata.java:55 "Returns a new (deterministic) automaton with the empty language" (0 states); Operations special-cases getNumStates() == 0 in many places, e.g. Operations.java:202-205, "Repeating the empty automata will still only accept the empty automata".
  • RunAutomaton means to support them. size = Math.max(1, a.getNumStates()) (RunAutomaton.java:68) exists only to give a 0-state input a start state; the class javadoc says "The initial state is always 0" (:38).
  • Lucene relies on it. MockTokenFilter.EMPTY_STOPSET, "Empty set of stopwords", is new CharacterRunAutomaton(makeEmpty()) (test framework, MockTokenFilter.java:43-44); it works only because makeEmpty() carries spare capacity.
  • Tests. TestRegExp.testRepeatWithEmptyLanguage (TestRegExp.java:107-117) builds #{2,10} and checks only toString(); nothing asserts a run automaton must refuse such input.
  • History. The crash appeared with LUCENE-5959 (#7021), a 5.0.0 memory optimization that made finish() exact-size; it did not discuss 0-state automata. 4.10.4 passes the same check (its main() form).
  • Precedent. LUCENE-6054 (#7116, "RegExp.toAutomaton fails on #*"), an earlier empty-language edge case, was fixed under Bug Fixes.
The devil's-advocate check197 words

Strongest case for "not a bug": RunAutomaton and Automaton are @lucene.experimental low-level APIs, and callers should go through CompiledAutomaton, which already handles 0 states; direct construction from a 0-state automaton is unsupported. For the tokenizers, the class javadoc says "The provided regex should match valid token characters" (SimplePatternTokenizer.java:33-34), so a maintainer may see a never-matching pattern as invalid configuration and prefer a clear IllegalArgumentException.

Why it fails: @lucene.experimental is about API stability, not correctness; no javadoc states that precondition; the CompiledAutomaton guard shows the case is known but is not a contract on RunAutomaton; Lucene's own MockTokenFilter and the pattern tokenizers construct run automata directly; and SimplePatternTokenizer is a public, string-configured API that reaches the crash with valid RegExp syntax. That javadoc sentence contrasts token characters with separators; it does not say the pattern must be able to match, and an AIOOBE from inside RunAutomaton is not a validation error. A cross-model reviewer (OpenAI GPT-5.6) built the API argument, rated it weak and voted real with high confidence; a second cross-model fact check rated the intended-behaviour case moderate because of the javadoc sentence and still found fix A the most defensible default.

Suggested fix

#

Recommended A. Loop only over the source's real states

In the RunAutomaton constructor, loop over the source's real states (n < a.getNumStates()), not n < size. The placeholder state 0 already rejects everything, so a 0-state input gets the table makeEmpty() gets today; other automata are unchanged. Validated with gradle: the test fails before, passes after; 404 automaton, query and tokenizer tests show 0 failures.

B. Give Automaton(int, int) / Builder.finish() a minimum capacity

#

Allocate at least 2 states[] slots even for 0 states in Automaton(int, int) (Automaton.java:92), the only place states[] is allocated (Builder.finish() uses it at :894; elsewhere it is only grown, :209, :359). Not run.

Trade-offs

It would cover every way of building a 0-state automaton, and with a 2-slot minimum only 0-state automata get more memory. But it hides the read of a state that does not exist instead of removing it (RunAutomaton would still read state 0 of a 0-state source and rely on spare zeros), and it changes a shared core constructor for a RunAutomaton problem. Not recommended.

C. Guard in the tokenizers, as CompiledAutomaton does

#

Replace a 0-state automaton with a 1-state non-accepting one in SimplePatternTokenizer and SimplePatternSplitTokenizer before new CharacterRunAutomaton(dfa). Not run.

Trade-offs

Fixes the tokenizer path only; direct CharacterRunAutomaton / ByteRunAutomaton users keep the crash. Not recommended alone.

Downstream note

#

Downstream products that build a SimplePatternTokenizer from a user-configured pattern get an unchecked ArrayIndexOutOfBoundsException for a degenerate pattern such as (a&b){2}, not a validation error; queries are not affected.

How it was found

#

Non-formal. A Jazzer fuzzer that compares Lucene regular expressions with java.util.regex and checks run automata against each other crashed on a repeated empty character class. An independent verifier reduced it to the 0-state automaton, mapped the triggers and releases, and tried a fix; the hunt cut it to one test and re-ran it on current main.

Low, rank 1147: RunAutomaton throws ArrayIndexOutOfBoundsException when built directly on a 0-state automaton (queries are guarded by CompiledAutomaton), loud and needing a degenerate empty-language automaton.
Impact class
crash
Impact note
Only code that builds a CharacterRunAutomaton or ByteRunAutomaton itself from a 0-state automaton with exact-size arrays (Automaton.Builder, new Automaton(0, 0), Operations.repeat), or a SimplePatternTokenizer, SimplePatternSplitTokenizer or their factories given a never-matching bounded-repeat pattern such as (a&b){2}; queries are guarded by CompiledAutomaton; released since 5.0.0.
Summary
You build an automaton with zero states through Automaton.Builder and create a RunAutomaton from it. You expect a run automaton that accepts nothing. Instead the constructor throws ArrayIndexOutOfBoundsException.
