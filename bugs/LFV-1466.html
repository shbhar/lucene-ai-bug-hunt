After a doc-values byte pool overflow, the next document's sorted value is stored as another value

After one document overflows an in-memory segment's 2 GiB doc-values byte pool and is rejected, the writer stays open, and a new sorted value in the next document that segment accepts is silently stored as another value: ByteBlockPool.nextBuffer moves to a new block before its overflow check throws.

Summary

Priority
Low, rank 1014On the default IndexWriter, in every release from 9.8.0 to 10.6.0 and on main, one later document's sorted doc value is silently stored as a different value and kept through flush and merges. It is Low because a single indexing call must first push the in-memory segment's doc-values byte pool past 2 GiB, a contrived scale that is itself rejected loudly with an ArithmeticException, the application must keep indexing after that error, and only one document is hit per overflow.

The finding in 30 seconds

#

A failed nextBuffer leaves the pool half-moved: on the new block, but with the old block's offset.

Where sorted doc values live before a flush

#
  1. While a segment is in memory, each SORTED or SORTED_SET field keeps its distinct values in a hash. The bytes of all those values sit in one shared ByteBlockPool per segment.
  2. The pool is a list of 32,768-byte blocks. A value's address is byteOffset + byteUpto: the start of the current block plus the position inside it. The javadoc says byteOffset is always bufferUpto * BYTE_BLOCK_SIZE.
  3. Addresses are int, so at most 65,536 blocks (2^31 bytes) fit. Since 9.8.0, asking for a 65,537th block throws ArithmeticException: integer overflow.

The finding, step by step

#
  1. You index one document whose distinct SortedSetDocValuesField values (65,537 values of up to 32,766 bytes, about 2 GiB) need one block more than the segment's doc-values pool can address: 65,536 blocks of 32,768 bytes, 2^31 bytes.
  2. As intended, addDocument throws ArithmeticException: integer overflow; the document is deleted and the writer stays open. But nextBuffer had already switched to a 65,537th block before the check threw, and its byteOffset still points at the start of the previous block.
  3. You add a second document (the next one that segment takes) with SortedDocValuesField("g", "b"). You expect "b" to be stored (or the call to fail too).
  4. Instead "b" is written into the new block but recorded at the old block's start, so the flushed segment holds the rejected document's last stored value, 32,763 bytes, as document 2's value. No error, with assertions on or off (shown on a model with the pool cap lowered to 64 blocks, so 65 values instead of 65,537; the real-size run, about 3 GB of heap, has not been done; the stock pool test at the real cap shows the same misaddressing).

Who is affected

#

Default IndexWriter users who keep indexing after this ArithmeticException. One call must carry about 2 GiB of distinct sorted values, or at least about 100 MB near the 1945 MB hard limit (with a raised RAM buffer). At most one document per overflow gets a wrong value, flushed and, on the model, kept by a forced merge.

Mechanism, terms and numbers556 words

IndexingChain keeps the SORTED and SORTED_SET values of an in-memory segment in one shared ByteBlockPool of 32,768-byte blocks. Addresses are int, so the pool holds at most 65,536 blocks; since 9.8.0 nextBuffer throws ArithmeticException when a 65,537th block is needed. But it installs that block, increments bufferUpto and resets byteUpto first, and only then runs byteOffset = Math.addExact(byteOffset, BYTE_BLOCK_SIZE) (ByteBlockPool.java:196-199). When the addition throws, byteOffset is one block behind, which breaks the documented invariant that it equals bufferUpto * BYTE_BLOCK_SIZE.

On the doc-values path the overflow is a non-aborting failure: the document is deleted, the writer stays open, and the same segment takes the next document. If that document adds a new sorted value, it is written into the new block, but its address is computed from the stale byteOffset, so it points to the previous block and the segment is flushed with another value. At the real size that document's success also flushes the segment, so at most one document per overflow is hit. With the cap lowered to 64 blocks, the second document's "b" came back as the rejected document's last stored value (32,763 bytes); on stock Lucene at the real cap, a pool test reads "b" back as "a". Every release from 9.8.0 to 10.6.0 and main is affected.

Mechanism (main f794ff5a505c)

#
  1. IndexingChain creates one docValuesBytePool per in-memory segment (IndexingChain.java:164) and gives it to every SortedDocValuesWriter and SortedSetDocValuesWriter (:1428-1437).
  2. BytesRefHash.add -> BytesRefBlockPool.addBytesRef calls nextBuffer() when a value does not fit in the current block (BytesRefBlockPool.java:91).
  3. nextBuffer (ByteBlockPool.java:187-200) installs the 65,537th block (:196), sets bufferUpto to its index 65,536 (:197) and byteUpto = 0 (:198); then Math.addExact(2,147,450,880, 32,768) throws (:199). byteOffset stays 2,147,450,880, the start of the 65,536th block. BytesRefHash has not counted the value yet (BytesRefHash.java:333-334), so the hash is unchanged.
  4. indexDocValue (IndexingChain.java:1456-1462, :1730-1760) has no onAbortingException guard, unlike the postings path (:2066-2101). So the failure is non-aborting: the document is marked deleted (DocumentsWriterPerThread.java:303-306), the writer stays open (only an Error is tragic, IndexWriter.java:1633-1635), and DocumentsWriter skips the call to doAfterDocument (DocumentsWriter.java:434; the per-thread hard-limit check it runs is DocumentsWriterFlushControl.java:247-251) and frees the segment for the next document (:444).
  5. A new sorted value in the next document the segment takes fits in the fresh block (byteUpto is 0), so addBytesRef writes it there but returns textStart = byteUpto + byteOffset (BytesRefBlockPool.java:95) = 2,147,450,880: the start of the previous, full block. Reads (fillBytesRef, :62-64) and the flush take the value from there.
  6. Any document the segment accepts next runs doAfterDocument, which sees the segment above its hard limit and flushes it (DocumentsWriterFlushControl.java:247-251). So at most one document per overflow is hit: that one, and only if it adds a new sorted value; a value that is already in its field's hash gets the existing ordinal and is correct. With several indexing threads, which document the segment takes next is not fixed (DocumentsWriter.java:53-58). This is the real-size behaviour: the 64-block model stays below the limits, so there the segment keeps taking documents.

The same statement order is in IntBlockPool.nextBuffer (IntBlockPool.java:153-157); no consequence was analysed there.

Exposure and likelihood189 words
  • Who: default IndexWriterConfig, codec and directory; any application that catches the ArithmeticException and keeps using the writer. No setting turns it on.
  • Scale: the segment's doc-values pool must pass 2^31 bytes of distinct SORTED/SORTED_SET values. The RAM buffer (16 MB by default) and the per-thread hard limit (1945 MB, IndexWriterConfig.java:93) are checked only between calls, so with the defaults one call must carry about 2 GiB; near the hard limit at least about 100 MB (2,048 - 1,945 MiB), and only when the segment's RAM is almost all doc-values pool.
  • Effect: at most one later document per overflow (the next one that segment accepts, if it adds a new sorted value) is stored with another value already in the pool, with no error under -ea or -da; the value is flushed, and on the same model forceMerge(1) under the default merge policy keeps the wrong value (assertions on and off). Sorting, faceting or grouping on that field then see the wrong value for that document.
  • Likelihood: contrived. Outside reports show the same throw reached for other pools (#15152, elastic/elasticsearch#160939), none for the doc-values pool since 9.8.0.

Why it looks unintended

#
  • IndexWriter.addDocument promises a consistent index after an exception; here a later, ordinary document is changed.
  • The pool's javadoc requires byteOffset to be bufferUpto * BYTE_BLOCK_SIZE; the failed call breaks it. Postings abort on such failures because the hash "is now corrupt".
  • The 2 GB limits explain why the big document is rejected, not why the next one is silently wrong.
The full argument170 words
  • Contract. IndexWriter.addDocument (IndexWriter.java:1465-1467): "if an Exception is hit (for example disk full) then the index will be consistent, but this document may not have been added". ByteBlockPool's byteOffset javadoc (:121-126): "Offset from the start of the first buffer to the start of the current buffer, which is bufferUpto * BYTE_BLOCK_SIZE".
  • Lucene's own rule. The postings path (IndexingChain.java:2066-2101) aborts all buffered documents when the terms hash fails, "on the likelihood that the internal state of the terms hash is now corrupt and should not be flushed to a new segment". The doc-values path to the same kind of pool has no such guard.
  • Tests. TestIndexWriterExceptions.testAddDocsNonAbortingException (:1461-1513) asserts that documents added after a non-aborting failure keep their own content. TestByteBlockPool.testTooManyAllocs, added with the throw, checks only that it throws and that byteOffset did not advance.
  • History. #12392 only replaced byteOffset += BYTE_BLOCK_SIZE with Math.addExact; its one review said "let's fail early when the addition overflows". Nobody discussed the state after the throw.
The devil's-advocate check171 words

The strongest case: the pool classes are @lucene.internal; BytesRefHash says "The internal storage is limited to 2GB total byte storage" (BytesRefHash.java:31-32); the per-thread hard limit is "a safety limit to prevent a DocumentsWriterPerThread from address space exhaustion due to its internal 32 bit signed integer based memory addressing" (IndexWriterConfig.java:376-378); and a maintainer (rmuir) wrote on #15330 that more than 2 GB per segment "is not supported: the limits on IndexWriter are 2GB". An independent reviewer from another model family (OpenAI GPT-5.6), reading only, called it not a bug on these grounds while agreeing on the root cause.

Why it fails: these limits explain why the oversized call is rejected, and it is, loudly. None of them says that a later document within every limit may be stored with another document's bytes while the writer stays open, and no javadoc limits a document's total doc-values bytes (only each value, to 32,766 bytes). A maintainer may still answer that nothing is promised once a segment passes 2 GB.

Suggested fix

#

Recommended A. Check for overflow before changing any field of the pool (validated)

Make nextBuffer failure-atomic: compute Math.addExact(byteOffset, BYTE_BLOCK_SIZE) into a local before growing the array or installing the block, and assign it last. The minimal test passes; 6 closest suites (92 tests, 0 failures) and :lucene:core:check -x test pass. After a failure the pool stays on its last block.

public void nextBuffer() {
  // check for overflow before changing any state, so that a failed call leaves the pool unchanged
  final int newByteOffset = Math.addExact(byteOffset, BYTE_BLOCK_SIZE);
  if (1 + bufferUpto == buffers.length) {
    ... // grow the buffers array (unchanged)
  }
  buffer = buffers[1 + bufferUpto] = allocator.getByteBlock();
  bufferUpto++;
  byteUpto = 0;
  byteOffset = newByteOffset;
}

A. Check for overflow before changing any field of the pool (validated) (recommended)

#

Two lines in ByteBlockPool.nextBuffer: the addExact moves to the top, its result is assigned last.

public void nextBuffer() {
  // check for overflow before changing any state, so that a failed call leaves the pool unchanged
  final int newByteOffset = Math.addExact(byteOffset, BYTE_BLOCK_SIZE);
  if (1 + bufferUpto == buffers.length) {
    ... // grow the buffers array (unchanged)
  }
  buffer = buffers[1 + bufferUpto] = allocator.getByteBlock();
  bufferUpto++;
  byteUpto = 0;
  byteOffset = newByteOffset;
}

Trade-offs

  • No API change and no extra work on the normal path (the same addition, moved).
  • After a failure the pool stays on its last block: a value that still fits there is stored correctly, a value that needs a new block fails with the same ArithmeticException until the segment is flushed (by the next document it accepts, or by an explicit flush or commit; failed documents do not trigger a flush).
  • Upstream testTooManyAllocs keeps passing. The same reorder could harden IntBlockPool.nextBuffer (not analysed, not run).

What the checks validated

  • Stock f794ff5a505c: the minimal test fails with assertions on and off.
  • With the fix: it passes with assertions on and off; TestByteBlockPool, TestBytesRefHash, TestBytesRefArray, TestRecyclingByteBlockAllocator, TestIndexWriterExceptions and TestDocValuesIndexing: 6 classes, 92 tests, 0 failures, 3 skipped (@Nightly); ./gradlew :lucene:core:check -x test passes with the test in place.
  • Earlier, the same change made the IndexWriter test on the 64-block model pass (assertions on and off).

B. Make a doc-values pool failure aborting, like postings

#

Wrap the doc-values path the way IndexingChain wraps termsHashPerField.add (IndexingChain.java:2066-2101).

Trade-offs

Discards every buffered document of the segment on an overflow; heavier than needed. Not run.

C. Flush a segment that a failed document left above its hard limit

#

Today the hard-limit check runs in doAfterDocument, which a failed document skips; open PR #15330 adds a proactive flush there and leaves nextBuffer unchanged.

Trade-offs

Complements A; on its own it leaves the pool state wrong if any value is added before the flush. Not run.

Downstream note

#

Services that accept very large documents and keep indexing after this exception could store bytes from the rejected document as the next document's sorted value; bounding document size avoids it.

How it was found

#

A semi-formal proof-obligation audit of ByteBlockPool's contract: the documented invariant byteOffset == bufferUpto * BYTE_BLOCK_SIZE must still hold after a failed nextBuffer. It does not, and a JUnit test witnessed it. The IndexWriter consequence was traced by reading the code and run with only the pool cap lowered.

The method in full102 words

Method: semi-formal proof obligations, witnessed by executable tests. The audit took each documented invariant of the pool classes and asked whether every method keeps it on every exit path, including exceptions. For nextBuffer, the exceptional exit leaves byteOffset one block behind bufferUpto. A JUnit test at the real 65,536-block cap confirmed it on stock jars.

The consequence for IndexWriter was then traced by reading IndexingChain, DocumentsWriterPerThread and DocumentsWriter, and executed with a public-API test on the stock code with only the pool cap lowered to 64 blocks (the check stays at the same place, after the same mutations).
