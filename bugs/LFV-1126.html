Grouping by a function such as sum(a, b) splits documents without a value into several null groups

Grouping two documents with a = 5 and a = 7 and no b by sum(a, b) returns two groups that both read as null, not one. Lucene's value filler keeps each missing value's partial sum (5 and 7), so each becomes its own null group; affected since 5.0.0.

The finding in 30 seconds

#

A group key is a MutableValueFloat: a value plus an exists flag. Its contract says a missing value must be 0, and its equality compares the value. Lucene's generic value filler sets the two separately, so sum(a, b) with b absent yields keys {missing, 5.0} and {missing, 7.0}: two different null groups.

Background: grouping by a function

#
  1. GroupingSearch(ValueSource, Map) groups the hits of a query by the value of a function, for example sum(a, b) over two doc-values fields.
  2. For each hit, a value filler writes the function's value and an exists flag into a reusable MutableValueFloat; that object is the group key.
  3. Hits for which the value does not exist belong in one null group, as when you group by a plain field they lack.

The finding, step by step

#
  1. Index two documents with a float doc-values field a = 5 and a = 7 and no field b. Group all documents with GroupingSearch by the function sum(a, b).
  2. You expect one null group with 2 hits: sum(a, b) does not exist for either document. Grouping the same documents by the missing field b alone gives exactly that.
  3. You get 2 groups, both null, 1 hit each, and no error. Behind each null is the partial sum: sum says it does not exist but still returns 5 + 0 = 5 (and 7), and the value filler copies both the flag and that value into the group key.
  4. The key class, MutableValueFloat, requires the value to be 0 when it does not exist, and its equality compares the value, so 5.0 and 7.0 make two keys. With assertions on, the search throws AssertionError; since 10.4.0, asking for 1 group throws NullPointerException.

Who is affected

#

Applications that group by a function (GroupingSearch(ValueSource, Map) or ValueSourceGroupSelector) over fields some documents lack, such as sum(a, b). Silent: the group count is wrong and the null groups cannot be told apart; since 10.4.0 a small group limit can fail the search. Default settings, two documents, but an opt-in, rarely used API: priority Low.

Mechanism, terms and numbers508 words

GroupingSearch(ValueSource, Map) groups hits by the value of a function. A document for which the function does not exist should land in the one null group, as it does when you group by a plain field it lacks. With sum(a, b), a document that has a but no b instead keeps its partial sum: sum's exists() is false while floatVal() returns a + 0, and the generic value filler (FloatDocValues.java:95-98) copies both into the group key. MutableValueFloat documents that a missing value must be 0 "for proper operation" and includes the value in equals/hashCode, so two documents with a = 5 and a = 7 give two null groups. Silent with assertions off; AssertionError with them on; since 10.4.0, a group limit of 1 throws NullPointerException in the second pass. Every release from 5.0.0 to 10.6.0 and main.

Terms

#
  • FunctionValues: the per-segment values of a function (ValueSource). floatVal(doc) gives the value, exists(doc) whether the document has one.
  • Value filler: FunctionValues.getValueFiller() returns an object that copies a document's value into a reusable MutableValue. ValueSourceGroupSelector uses it to build the group keys.
  • MutableValueFloat: a float value plus an exists flag. Its class javadoc: "the caller is responsible for ensuring that any instance where exists is set to false must also value set to 0.0F for proper operation" (MutableValueFloat.java:19-23), asserted in toObject, equalsSameType, compareSameType and hashCode (:29, :50, :57, :67).

The bug

#
  1. sum does not exist, but has a value. MultiFloatFunction.exists is MultiFunction.allExists, false when any input is missing (MultiFloatFunction.java:52-53, :87-90). Its floatVal is func(doc, valsArr) (:83-85), for sum the sum of the inputs' floatVal (SumFloatFunction.java:35-41), and a missing FloatFieldSource contributes 0f (FloatFieldSource.java:59-64). For a = 5 and no b: exists = false, floatVal = 5.0.
  2. The filler copies both. FloatDocValues.getValueFiller().fillValue runs mval.value = floatVal(doc); mval.exists = exists(doc); (FloatDocValues.java:95-98), so the key is {exists=false, value=5.0}; for a = 7, {exists=false, value=7.0}.
  3. Two keys, two null groups. equalsSameType compares value (MutableValueFloat.java:49-53) and hashCode hashes it (:66-69), so the first pass's group map (FirstPassGroupingCollector.java:228, :256) holds two keys. Both groups have toObject() == null and print (null), so the caller cannot tell them apart. With assertions on, the hashCode assert fails first.
  4. The NullPointerException (since 10.4.0). #15167 made ValueSourceGroupSelector.setGroups fold every missing top group into one includeEmpty flag (ValueSourceGroupSelector.java:87-97), and advanceTo accepts every missing value when it is set (:63-68). With a group limit of 1, the top group is {false, 5.0}; the document with {false, 7.0} is accepted too, and GroupReducer.collect finds no group for it (GroupReducer.java:71-74). Before 10.4.0 the second pass skipped it and totalGroupedHitCount came out 1 instead of 2.

The Double, Int, Long and Bool fillers have the same two lines (DoubleDocValues.java:160-163, IntDocValues.java:130-133, LongDocValues.java:139-142, BoolDocValues.java:95-98); read, not executed.

Exposure and likelihood245 words
  • Who. Applications that group with GroupingSearch(ValueSource, Map) or ValueSourceGroupSelector by a function that can be missing while its value is not zero and differs between documents. Executed: sum over optional float fields and over optional int doc-values fields, both through FloatDocValues' filler (sum is a float function). Not affected (read): plain numeric field sources (missing value 0), string sources (they clear the value to length 0, as MutableValueStr asks) and product with a missing input (0). A one-input function such as linear(a, m, c) gives the same c for every missing document: one null group, so it trips only the asserts.
  • Effect. With assertions off, no error: one null group per distinct partial value, each holding a slice of the documents that belong together, and inflated group counts (adding two documents with both fields gives 4 groups instead of 3). Since 10.4.0, a group limit below the number of distinct partial values makes the second pass throw NullPointerException; from 5.0.0 to 10.3.2 the same search silently under-counts totalGroupedHitCount.
  • Default vs opt-in. Default index settings, two documents, no scale. The API is opt-in: grouping by a function (GroupingSearch is @lucene.experimental), and open #10409 proposes deprecating grouping by ValueSource.
  • Likelihood: rare. It needs a sum-style function over fields that some matching documents lack. The code has behaved this way since LUCENE-5961 (2014; first released in 5.0.0, February 2015), and the documented searches found no public report of it. Priority Low.

Why it looks unintended

#
  • MutableValueFloat's javadoc: a value whose exists is false must be 0 "for proper operation", checked by four asserts.
  • The issue that added the rule (LUCENE-5790) put that duty on the value setters; here the setter is Lucene's own filler.
  • Grouping's model is one null group: grouping by the missing field b alone gives exactly one.
The full argument190 words
  • Contract. "any instance where exists is set to false must also value set to 0.0F for proper operation" (MutableValueFloat.java:19-23), asserted at :29, :50, :57 and :67. It was added in LUCENE-5790 (#6852, 4.10.0), where Yonik Seeley wrote "Value setters currently ensure that the default value (0 for numerics) is set if exists == false" and Chris Hostetter documented that duty and added the asserts. The setter here is Lucene's filler, not user code.
  • Grouping convention. FirstPassGroupingCollector's javadoc speaks of "putting them in a null group" (:87-88); GroupDocs.groupValue "may be null if hits did not have the groupField" (GroupDocs.java:25-26); #15167 keeps one includeEmpty flag for all missing values; grouping the repro's documents by FloatFieldSource("b") gives one null group with 2 hits.
  • History. The filler lines date from 2011 (Solr code that LUCENE-3249 moved into the queries module). LUCENE-5961 (#7023, 5.0.0) later made sum's exists() false when an input is missing, while floatVal() kept the partial sum. Its discussion covers exists() only; fillers and grouping are not mentioned. The available LUCENE-5961 record does not show this interaction being considered or decided.
The devil's-advocate check122 words

The strongest case for "intended": LUCENE-5961 deliberately changed exists() to false while leaving the nonzero floatVal() computation unchanged; MutableValue is @lucene.internal, GroupingSearch and the value filler are @lucene.experimental; open #10409 wants to deprecate grouping by ValueSource.

Why it fails: LUCENE-5961 changed exists() only, and the contract it collided with puts the zeroing on the setter, which is Lucene's code. Experimental tags allow API changes, not wrong results. #10409 is an open proposal: on main and 10.6.0 nothing here is deprecated, and the grouping package docs list ValueSourceGroupSelector as a selector. This argues for a low priority, not for "works as designed"; the intended-behaviour check rebutted it point by point, the cross-model reviewer rated it weak, and the adjudication agreed.

Suggested fix

#

Recommended Zero the value in the generic fillers when the function does not exist (built; validated)

In Lucene's generic value fillers, set the value to zero when the function does not exist: three lines each in the Float, Double, Int, Long and Bool fillers. Tested with gradle: the repro passes with assertions on and off, the grouping module and the function tests pass, and the 1-group search no longer throws.

// FloatDocValues.getValueFiller(): fillValue (the same in Double/Int/Long/BoolDocValues)
mval.value = floatVal(doc);
mval.exists = exists(doc);
if (mval.exists == false) {
  mval.value = 0.0f; // a missing value must be canonical (see MutableValueFloat)
}
All options and trade-offs3 options · 504 words

Three options; the first was built and tested, the other two were not. The choice is the maintainers'.

Zero the value in the generic fillers when the function does not exist (built; validated) (recommended)

#

After the two existing assignments in fillValue, reset the value to the type's zero when exists is false, in FloatDocValues, DoubleDocValues, IntDocValues, LongDocValues and BoolDocValues (+15 lines, nothing else). The call order is kept, so sources that advance an iterator in exists() (such as FloatFieldSource) see the same calls as today; the adjudication's first sketch set exists first instead.

// FloatDocValues.getValueFiller(): fillValue (the same in Double/Int/Long/BoolDocValues)
mval.value = floatVal(doc);
mval.exists = exists(doc);
if (mval.exists == false) {
  mval.value = 0.0f; // a missing value must be canonical (see MutableValueFloat)
}

Trade-offs

  • The payload of a missing value changes to 0, which the contract already requires. So everything that looks at it changes with it: equals, hashCode and compareSameType, hence maps, sets and any other consumer of these fillers. Anything that orders these values then puts a missing value just before a real 0 (compareSameType breaks the tie on exists), not at its old partial sum.
  • Only the FloatDocValues change is exercised by a test (the independent int-field test also goes through it, since sum is a float function); the Double, Int, Long and Bool edits are the same three lines, checked by reading.
  • Covers these five fillers only. QueryValueSource has its own filler, which writes its defVal for a missing value: one constant value, so it trips only the asserts and forms one null group; that case is not part of this finding. The string fillers (StrDocValues, DocTermsIndexDocValues) and the base FunctionValues filler, which never sets exists and which if and def use, are separate and unchanged.

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, JDK 25, seed DEADBEEF: the repro fails without the fix and passes with it, assertions on and off.
  • With the fix: the whole lucene/grouping test module (57 tests) and org.apache.lucene.queries.function.* (111 tests, 1 skipped) pass under a random root seed; :lucene:queries:check and :lucene:grouping:check without tests (format, ecj lint, forbidden APIs) pass.
  • An independent group-limit-1 test (asserts 1 group and totalGroupedHitCount 2) passes with the fix and throws the NullPointerException without it: once all missing values are equal, the single includeEmpty flag is right.

Canonicalise in ValueSourceGroupSelector.advanceTo (not built)

#

Reset a missing key before grouping uses it.

Trade-offs

Fixes grouping only. advanceTo sees a generic MutableValue, so it needs a type-specific reset, and other users of the fillers stay exposed.

Make MutableValue* equality ignore the value when exists is false (not built)

#

Change equalsSameType, hashCode and compareSameType of the five primitive-value classes in core (MutableValueFloat, -Double, -Int, -Long, -Bool), and drop the asserts.

Trade-offs

Also covers any other non-canonical setter, but changes core classes and reverses the LUCENE-5790 decision: Chris Hostetter offered this alternative there and kept the zero-when-missing rule instead.

Downstream note

#

A service that lets its users pick a group function over sparse fields may show them split null groups, or fail their request with a NullPointerException.

How it was found

#

A proof-obligation audit of MutableValueFloat's contract (a missing value must be 0) traced the code that sets such values and found the generic value fillers copying a nonzero partial value. A one-test JUnit on the public grouping API witnessed it.

The method in full93 words

Method: semi-formal (a contract audit with an executable witness; no model checker or proof).

  • Audit. The obligation "exists == false implies value == 0" from MutableValueFloat's javadoc and asserts was traced to its setters. The generic fillers set value and exists independently, so the obligation holds only if every function's floatVal is 0 whenever its exists is false. sum (and other functions since LUCENE-5961) breaks that.
  • Witness. The one-test JUnit above, on the stock main jars, with assertions on and off; then independent reproductions, release runs and the fix check.

History

#

Introduced in 5.0.0 by LUCENE-5961 (595587963a7, 2014), which made sum report exists() == false while keeping its partial value; the older filler then started writing nonzero missing values. The NullPointerException since 10.4.0 (#15167). Fails on every release run from 5.0.0 to 10.6.0 and on main; 4.10.4 passes.

Versions tested6 rows

Introduced by LUCENE-5961 (#7023, Chris Hostetter, 2014-10-16): 595587963a7 on branch_5x, first released in 5.0.0, and d8146460f0e on trunk; SVN commits, no GitHub PR. It made sum/product (MultiFloatFunction) and pow/div (DualFloatFunction) report exists() == false when an input is missing. Two older pieces met there: the filler lines (0742b30b724, 2011-04-15, Solr; moved into the queries module by LUCENE-3249, a993ae90323) and the zero-when-missing rule with its asserts (LUCENE-5790: 474d846bb5b on trunk, d7bc5944845 on branch_4x, first released in 4.10.0).

The NullPointerException comes from #15167 (a4ebe984087 on main, 898d38a4fd3 on branch_10x, gaobinlong, 2025-10-06, first released in 10.4.0), which made the second pass accept every missing value. Before that, the second pass skipped the extra missing values and under-counted.

Not fixed upstream: the newest upstream commits on the five files involved predate 5adff78bb168 (read 2026-11-02). A tag sweep finds the same code in all 99 release tags from 5.0.0 to 10.6.0.

Summary
