IndexWriter.deleteAll can deadlock with a flushing addDocument and a concurrent tryDeleteDocument or addIndexes

Three threads on one IndexWriter (deleteAll(), a flushing addDocument(), and tryDeleteDocument() or addIndexes()) can each hold one lock and wait for the next one's: all three hang with no exception, and later calls block too. A 3-document test deadlocks on main and on seven releases tried from 8.6.0 to 10.6.0.

The finding in 30 seconds

#

Each thread holds one of the writer's internal locks and waits for the lock the next thread holds.

Three locks inside IndexWriter

#
  1. The IndexWriter lock (the writer's monitor) is held by synchronized writer methods such as tryDeleteDocument, and while a flushed segment is added to the index.
  2. The DocumentsWriter lock is the monitor of the writer's in-memory buffer manager. It is held while a sequence number is handed out, and while deleteAll aborts the in-memory buffers.
  3. The purge lock guards the queue of flushed segments that wait to be added to the index. The thread that publishes them holds it until each one has been added under the IndexWriter lock.

The finding, step by step

#
  1. Open a writer with maxBufferedDocs=2, add 1 document and open an NRT reader. Thread 1 calls tryDeleteDocument(reader, 0): it holds the IndexWriter lock (and the bufferedUpdatesStream lock) while it deletes the document and drops the now-empty segment (the test pauses it there once), and only then asks for a sequence number.
  2. Thread 2 adds 2 documents. The second add flushes a new segment and publishes it itself: it takes the flush queue's purge lock, then waits for the IndexWriter lock, which thread 1 holds.
  3. Thread 3 calls deleteAll(). It takes the DocumentsWriter lock, then waits for the purge lock, which thread 2 holds.
  4. Thread 1 continues. You expect all three calls to return within milliseconds (they do with the fix, 20 of 20 iterations). Instead thread 1's sequence number needs the DocumentsWriter lock, which thread 3 holds: a cycle.
  5. The JVM's deadlock detector reports 3 deadlocked threads, with assertions on and off, in every recorded run. The writer calls throw nothing (the test reports the cycle with an AssertionError), and a probe shows later commit(), getReader(), rollback() and close() calls on that writer blocking too.

Who is affected

#

Applications that call deleteAll() while other threads index and, at the same time, use addIndexes or the Expert tryDeleteDocument/tryUpdateDocValue. By code reading no non-default setting is needed, and no scale. Rare, since three calls must meet in short windows, but when hit the writer is lost: later commit(), getReader(), rollback() and close() calls block too (executed).

Mechanism, terms and numbers546 words

Three threads share one IndexWriter: one calls deleteAll(), one calls addDocument() and that call flushes and publishes a new segment, and one calls tryDeleteDocument() on an NRT reader (or addIndexes(...)). The IndexWriter javadoc says instances are "completely thread safe, meaning multiple threads can call any of its methods, concurrently". Instead they can deadlock: deleteAll() holds the DocumentsWriter monitor (in lockAndAbortAll) and waits for the flush-ticket purge lock, the publishing thread holds that purge lock and waits for the IndexWriter monitor (publishFlushedSegment), and tryDeleteDocument() (or addIndexes()) holds the IndexWriter monitor and waits for the DocumentsWriter monitor to get a sequence number (getNextSequenceNumber). The writer calls throw nothing, with assertions on and off, and later commit(), getReader(), rollback() and close() calls on that writer block too (executed). The edge that closes the cycle came with LUCENE-9304 in 8.6.0 (2020); every release since, through 10.6.0, and main are affected (seven releases and main executed, the rest by code reading).

Exposure and likelihood351 words
  • Effect. The three calls hang with no exception or log line, assertions on and off (executed). The writer is then unusable. A probe that runs after the cycle has formed (main, assertions off, InfoStream off as in a default config) shows later commit(), DirectoryReader.open(w) and a second deleteAll() blocked on fullFlushLock, a fourth lock that the stuck deleteAll took at IndexWriter.java:2764, and rollback() and close() blocked on the IndexWriter monitor in shouldClose (:1374) (executed). With the test framework's InfoStream, commit() blocks on the IndexWriter monitor first, in the synchronized segString() (:5840). Later automatic flushes do not wait for the purge lock (tryPurge gives up, DocumentsWriterFlushQueue.java:128), so their segments stay unpublished (read). Monitor waits and ReentrantLock.lock() ignore interrupts, so no in-process way to recover was found (read).
  • Who. Applications that call deleteAll() while other threads index, and that also call tryDeleteDocument or tryUpdateDocValue (Expert: delete or update by NRT doc id) or addIndexes(...) (not Expert) at the same time. deleteAll's own javadoc anticipates concurrent addIndexes(CodecReader[]) calls (IndexWriter.java:2743-2745). deleteDocuments(new MatchAllDocsQuery()) is routed to deleteAll() (IndexWriter.java:1886-1890), so it is a second way in (read, not executed).
  • Default vs opt-in. By code reading no non-default setting is needed. The indexing thread needs only an automatic flush that it completes and publishes itself (a maxBufferedDocs or RAM-buffer flush); an explicit flush() takes fullFlushLock and publishes on another path (IndexWriter.java:4399-4412). The repro sets maxBufferedDocs=2 (so that the second add flushes) and a merge policy that pauses one thread once, only to fix the schedule; it runs with the test framework's randomized codec and also fails with the plain Lucene104 codec forced (executed).
  • Scale. None: three documents. At the start there is one 1-document segment; at the deadlock it has been dropped and the new 2-document segment is flushed but not yet published.
  • Likelihood: rare. deleteAll must enter lockAndAbortAll while the indexer is publishing, and the third thread must be inside its IndexWriter-monitor section just before it asks for a sequence number. No public report of it was found (see prior reports).

Why it looks unintended

#
  • IndexWriter's javadoc: "completely thread safe, meaning multiple threads can call any of its methods, concurrently".
  • deleteAll's javadoc expects concurrent addIndexes callers and names MergeAbortedException as the outcome, not a hang.
  • It came in 8.6.0 with a sequence-number fix (LUCENE-9304) whose review material does not discuss lock order; an earlier deleteAll deadlock (#6066) was fixed as a bug.
The full argument229 words
  • Contract (IndexWriter.java:167-170): "IndexWriter instances are completely thread safe, meaning multiple threads can call any of its methods, concurrently. If your application requires external synchronization, you should not synchronize on the IndexWriter instance as this may cause deadlock; use your own (non-Lucene) objects instead." The test does not synchronize on the writer.
  • deleteAll's javadoc (IndexWriter.java:2743-2745): "If other threads are running forceMerge, addIndexes(CodecReader[]) or forceMergeDeletes methods, they may receive MergePolicy.MergeAbortedExceptions."
  • The code implies a lock order elsewhere. innerPurge (DocumentsWriterFlushQueue.java:93-98): "if we block on publish -> lock IW -> lock BufferedDeletes we don't block concurrent segment flushes"; publishFrozenUpdates (IndexWriter.java:2931-2932): "Do this as an event so it applies higher in the stack when we are not holding DocumentsWriterFlushQueue.purgeLock". These comments and the implementation imply that the purge lock comes before the IndexWriter monitor (there is no written lock-order contract); lockAndAbortAll takes it under the DocumentsWriter monitor, and edge 3 takes the DocumentsWriter monitor under the IndexWriter monitor.
  • Tests. TestIndexWriterDelete.testDeleteAllNoDeadLock (TestIndexWriterDelete.java:326) runs deleteAll while other threads index; it has no tryDeleteDocument or addIndexes thread. No test or comment accepts this cycle.
  • History. LUCENE-5002 (#6066), an earlier deleteAll deadlock, was fixed in 4.3.1. The edge that closes this cycle came with a fix for a sequence-number race (LUCENE-9304, apache/lucene-solr#1427), whose review material (10 review comments, 6 reviews, 1 issue comment) does not discuss lock order.
The devil's-advocate check149 words

Strongest case: "the test forces a schedule by pausing inside tryDeleteDocument, and tryDeleteDocument is Expert; real windows are tiny."

Why it fails: (1) the pause takes no new lock and is lifted before the deadlock forms. It runs inside the IndexWriter monitor that tryDeleteDocument already holds, which is the window itself: it only lengthens a window that exists anyway (the delete, dropDeletedSegment and checkpoint() run inside the IndexWriter monitor before the sequence number is taken), as preemption or slow file I/O would; after the release only Lucene's own locks are involved and the JVM itself reports the cycle. (2) Expert is not "unsupported": the thread-safety contract covers every method, and a separate executed test with the non-Expert addIndexes(CodecReader...) forms the same cycle. (3) Rare is not intended: Lucene has fixed rare IndexWriter deadlocks before (#6066, #12654). The cross-model reviewers (OpenAI GPT-5.6) rated the "works as designed" case weak.

Suggested fix

#

Recommended A: purge the ticket queue before taking the DocumentsWriter monitor (sketch; validated by the runs below, not proven safe)

In DocumentsWriter.lockAndAbortAll, run the ticket-queue forcePurge before taking the DocumentsWriter lock (+9/-2 lines), which removes one edge of the cycle. Tested, not proven safe: the test passes, and so do 290 tests of the 12 closest suites and the whole org.apache.lucene.index package (1,397 tests). Design it together with LFV-474's fix.

Closeable lockAndAbortAll() throws IOException { // was: synchronized
  // ... infoStream message unchanged
  // Purge before taking this monitor: a thread holding the purge lock may be waiting for the
  // IndexWriter monitor, whose owner may be waiting for this monitor (getNextSequenceNumber).
  assert Thread.holdsLock(this) == false;
  ticketQueue.forcePurge(
      ticket -> {
        if (ticket.getFlushedSegment() != null) {
          pendingNumDocs.addAndGet(-ticket.getFlushedSegment().segmentInfo.info.maxDoc());
        }
      });
  return lockAndAbortAllAfterPurge();
}

A: purge the ticket queue before taking the DocumentsWriter monitor (sketch; validated by the runs below, not proven safe) (recommended)

#

lockAndAbortAll stops being synchronized: it runs ticketQueue.forcePurge(...) first and then calls a new synchronized lockAndAbortAllAfterPurge() with the rest of the old body. This removes edge 1 (DocumentsWriter monitor -> purge lock); edges 2 and 3 stay. The snippet is condensed.

Why it looks safe, and what it changes (read): lockAndAbortAll has one caller, deleteAll (IndexWriter.java:2765), which still holds fullFlushLock during the purge. Tickets are added under the ticket queue's own monitor (DocumentsWriterFlushQueue.java:38), and a segment flush adds its ticket without the DocumentsWriter monitor (DocumentsWriter.java:535), so the purge under that monitor never kept new tickets out: for adding tickets the fix opens no new window. It does open one for the other users of the DocumentsWriter monitor: getNextSequenceNumber, applyDeleteOrUpdate (deletes and doc-values updates) and resetDeleteQueue (DocumentsWriter.java:583, :153, :588) can now run between the purge and the abort. That is exactly what breaks the cycle (tryDeleteDocument gets its sequence number), and fullFlushLock does not restore that exclusion.

Trade-offs

  • A maintainer must confirm that no invariant needs the purge and the abort under one hold of the DocumentsWriter monitor.

The two fixes need one design (moving that purge out too is one option; a maintainer may choose another lock order or serialization); review them together.

B: take sequence numbers without the DocumentsWriter monitor (not tried)

#

Give tryModifyDocument and addIndexes their sequence number inside the IndexWriter monitor without taking the DocumentsWriter monitor (removes edge 3).

Trade-offs

Not recommended. getNextSequenceNumber became synchronized to close the LUCENE-9304 race ("the delete queue might change concurrently"), and later sequence-number work (#13169) relies on it. On 8.6.0, changing tryModifyDocument's call back to deleteQueue.getNextSequenceNumber() makes the deadlock go away, which shows causation but reopens that race.

C: document the restriction (not recommended)

#

Say that deleteAll must not run concurrently with tryDeleteDocument, tryUpdateDocValue or addIndexes.

Trade-offs

Contradicts the class javadoc and deleteAll's own note on concurrent addIndexes.

Downstream note

#

A service that lets clients request a delete-everything operation while it indexes and runs addIndexes or tryDeleteDocument could see its writer hang; whether clients may request that is the service's own choice.

How it was found

#

A proof-obligation audit of DocumentsWriter's lock order (the obligation: the writer's locks are always taken in one order) found three edges that form a cycle. An executable JUnit test witnessed it, and an independent reproducer, cross-model reviews and an adjudication confirmed it.

The method in full138 words

Method: a proof-obligation audit of DocumentsWriter's lock order, witnessed by an executable repro (the hunt's "semi-formal" tier).

  • The audit looked at the places where DocumentsWriter and IndexWriter take one of their locks while holding another, and found three such edges that close a cycle: DocumentsWriter monitor -> purge lock (lockAndAbortAll), purge lock -> IndexWriter monitor (the inline publish) and IndexWriter monitor -> DocumentsWriter monitor (getNextSequenceNumber under tryModifyDocument and addIndexes).
  • The finder then wrote a JUnit test that holds each thread at a point it reaches anyway and showed the cycle on main, 10.6.0 and 9.12.3; the fix sketch made it pass.
  • An independent reproducer wrote its own test from the claim alone, with the single pause in a public merge-policy callback; the minimal repro on this page is a trimmed version of that idea.

History

#

Finding record

LFV-1137, snapshot of 2026-11-06

Registry title
IndexWriter.deleteAll can deadlock with a concurrent flush publish and a concurrent tryDeleteDocument or addIndexes, because DocumentsWriter.lockAndAbortAll waits for the flush-ticket purge lock while holding the DocumentsWriter monitor
Area
index / IndexWriter deleteAll (IndexWriter-DocumentsWriter lock order)
Priority
Medium, rank 109: When deleteAll() meets a concurrent flush publish and a tryDeleteDocument, tryUpdateDocValue or addIndexes call, the writer deadlocks for good with no exception and only a JVM restart recovers, on default settings in every release since 8.6.0. The three calls must meet in short windows and deleteAll during live indexing is uncommon, so the trigger is rare.
Impact class
hang
Impact note
Applications that call deleteAll() while other threads index and that also use tryDeleteDocument() or tryUpdateDocValue() (Expert) or the non-expert addIndexes() are hit when the three calls meet in their short windows: the three threads hang for good with no exception (-ea and -da alike), and the writer is then stuck, since the held IndexWriter and DocumentsWriter monitors and the purge lock block later commit(), close(), getReader() and flush publishes until the JVM restarts [read]; default codec and config suffice (the repro sets maxBufferedDocs=2 only to make the flush deterministic), no scale is needed, and every release from 8.6.0 through 10.6.0 and main are affected.
Summary
Three threads share one IndexWriter: one adds documents and its addDocument() flushes and publishes the new segment, one calls tryDeleteDocument() on an NRT reader (or addIndexes()), and one calls deleteAll(). You expect all three calls to return, because IndexWriter is documented as completely thread safe for concurrent calls of any of its methods. Instead they can deadlock for good: deleteAll() holds the DocumentsWriter monitor (in lockAndAbortAll) and waits for the flush-ticket purge lock, the publishing thread holds that purge lock and waits for the IndexWriter monitor (publishFlushedSegment), and tryDeleteDocument() (or addIndexes()) holds the IndexWriter monitor and waits for the DocumentsWriter monitor to get a sequence number (getNextSequenceNumber).
