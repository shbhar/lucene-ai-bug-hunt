Geo3d spatial context: a line string's buffer is read as radians, so a 1-degree buffer is 57 degrees wide

In the Geo3d spatial context, lineString().buffer(1) builds a corridor reaching 57.3 degrees from the line instead of 1 degree, because the buffer goes to spatial3d as radians without the degrees-to-radians conversion the same factory applies to circles. Buffers above about 1.57 throw Cutoff angle out of bounds.

The bug in 30 seconds

#

spatial4j's geo conventions put distances in degrees, and the Geo3d shape factory converts degrees to radians for circles and rectangle buffers. Its line-string builder hands the buffer to spatial3d unconverted, so buffer(1) means 1 radian: a corridor 57.3 times too wide. Buffers above about 1.57 are rejected.

  1. You make a spatial context with Geo3dSpatialContextFactory and build the line (0,0) to (10,0) with buffer(1). In a geographic spatial4j context distances are in degrees, so you ask for everything within 1 degree (about 111 km) of the line.
  2. You expect the point (5, 20), 20 degrees north of the line, to be outside: spatial4j's own SpatialContext.GEO and this factory's circle(5, 0, 1) both say DISJOINT.
  3. You get CONTAINS. The corridor's bounding box is [-57.3, 67.3] x [-57.3, 57.3]: the buffer was used as 1 radian, 57.3 degrees. A spatial index query with this line returns 3 of 4 points where 1 is right. No error.
  4. Why: Geo3dLineStringBuilder.build() hands the buffer straight to GeoPathFactory.makeGeoPath, whose width is an angle in radians; circle() and rectangle buffers convert degrees first. Reading spatial4j's polyshape string of the line gives the same 57.3-degree corridor.
  5. Any buffer above about 1.5708 throws IllegalArgumentException: Cutoff angle out of bounds, so a 2-degree corridor cannot be built. Every release from 7.1.0 to 10.5.2 and main are affected; the fix is one multiplication.

Who is affected

#

Applications that use the opt-in Geo3d spatial context with buffered line strings, as indexed shapes or as query shapes, through the builder, the polyshape format or GeoJSON's buffer. Every such line is about 57 times too wide, or rejected above about 1.57; unbuffered lines, circles, rectangles and polygons are not affected by this mismatch. Index size does not matter.

Mechanism, terms and numbers669 words

spatial4j's documented geographic conventions put distances in degrees (LineStringBuilder.buffer itself names no unit, so its unit is inferred from those conventions and spatial4j's readers). The spatial-extras Geo3dShapeFactory, the shape factory of the opt-in, experimental Geo3dSpatialContextFactory, converts degrees to radians at its boundary for circles, 2-D points and rectangle buffers, but its line-string builder does not: buffer(distance) stores the value as given and build() passes it to spatial3d's GeoPathFactory.makeGeoPath, whose width "is the width of the path, measured as an angle", in radians. So the line (0,0) to (10,0) with buffer(1) reaches 57.3 degrees from the line: bounding box [-57.3, 67.3] x [-57.3, 57.3] instead of [-1, 11] x [-1, 1], and it contains the point (5, 20), which spatial4j's own geo context and the same factory's 1-degree circle leave outside. The same happens when the Geo3d context reads spatial4j's polyshape string of that line. Any buffer above about 1.5708 throws IllegalArgumentException: Cutoff angle out of bounds. In an index, an Intersects query with the 1-degree line returned 3 of 4 points where 1 is right. The code dates from LUCENE-7951; every release from 7.1.0 (2017) to 10.5.2 and main are affected, and the fix is one multiplication in build().

Terms

#
  • Spatial context: spatial4j's SpatialContext fixes the units and builds shapes through its ShapeFactory. In a geographic context x is longitude, y is latitude, and distances are in degrees (1 degree is about 111 km).
  • Geo3d spatial context: Geo3dSpatialContextFactory in lucene-spatial-extras (@lucene.experimental, opt-in; default planet model: the sphere) makes a context whose Geo3dShapeFactory builds lucene-spatial3d shapes. spatial3d works in radians, so the factory converts at its boundary.
  • Buffered line string: lineString().pointXY(...).buffer(d).build(), the corridor of all points within d of the line. In the Geo3d context it becomes a spatial3d GeoStandardPath.

The bug

#
  1. Geo3dLineStringBuilder.buffer(distance) stores the value unchanged: this.distance = distance; (Geo3dShapeFactory.java:308-312).
  2. build() calls GeoPathFactory.makeGeoPath(planetModel, distance, points.toArray(GeoPoint[]::new)) (:314-319).
  3. makeGeoPath documents its width as "the width of the path, measured as an angle" (GeoPathFactory.java:34), a spatial3d angle in radians, and builds a GeoStandardPath. That constructor rejects widths outside (0, pi/2] with "Cutoff angle out of bounds" (GeoStandardPath.java:80-81).
  4. Elsewhere the factory converts degrees for circles, 2-D points and rectangle buffers: circle() passes distance * DistanceUtils.DEGREES_TO_RADIANS (Geo3dShapeFactory.java:175-197), pointXY converts coordinates (:278-286; pointXYZ has a different boundary bug, LFV-679), and Geo3dRectangleShape.getBuffered converts its distance (Geo3dRectangleShape.java:169-173). The context's distance calculator and circle radii report degrees. normDist is the identity (:114-117).
  5. spatial4j's readers feed the same builder: the polyshape reader passes the same normDist(arg) to a circle's radius and to a line's buffer, and the GeoJSON reader converts a km buffer to degrees before calling buffer(). So one polyshape document gives a 1-degree circle but a 1-radian line. The deprecated lineString(List, double) and the multi-line builder use the same builder too (both executed: the 57.3-degree corridor, CONTAINS (5, 20)). spatial4j registers the GeoJSON reader only when Noggit's org.noggit.JSONParser is on the classpath; it was not on the tested classpaths, so that path was read, not run.

The numbers

#
  • Line (0,0) to (10,0), buffer(1), default sphere: bounding box [-57.3, 67.3] x [-57.3, 57.3] (spatial4j: [-1, 11] x [-1, 1]). Along x = 5 the edge lies between y = 57.0 (inside) and 57.5 (outside): 1 radian is 57.2958 degrees.
  • The same line with buffer(Math.toRadians(1)) is the 1-degree corridor (bounding box [-1, 11] x [-1, 1]).
  • buffer(1.5708) (just above pi/2), buffer(1.6), buffer(2) and buffer(90.01): IllegalArgumentException: Cutoff angle out of bounds; buffer(1.5707) builds. Exactly Math.PI / 2 passes that check and, for the probe's two-point line, fails later with "path too wide". The bounding box of buffer(1.5) spans all longitudes.
  • WGS84 behaves the same: a point 2.98 degrees from the 1-degree line is inside.
  • Not affected: unbuffered lines (a zero width becomes a degenerate path), circles, rectangles, polygons, and spatial4j's default geo context. WKT BUFFER(LINESTRING(...), d) is not supported in the Geo3d context at all.
Exposure and likelihood322 words
  • Who is hit. Users of Geo3dSpatialContextFactory (any planet model) who build buffered line strings: lineString().buffer(d), the deprecated lineString(List, double), multi-line builders (all executed), the polyshape format (executed) or the GeoJSON "buffer" extension when the optional Noggit JSON parser is on the classpath (by code reading). As document shapes or as query shapes ("documents within d of this route"); RecursivePrefixTreeStrategy with Geohash or S2 trees and SerializedDVStrategy all see the wide shape.
  • Default vs opt-in. Opt-in twice: the Geo3d context is not the default, and only buffered lines are wrong. WKT, one of spatial4j's default input formats, cannot express a buffered line in this context.
  • Effect. Buffers below about 1.57: a corridor 57.2958 times wider than requested, with no error. In an index of 4 points an Intersects query with the 1-degree line returned 3 where 1 is right; in a 600-document index (514 live) it matched 359 documents on Geohash and S2 prefix trees and 354 on SerializedDVStrategy, where the fix matches 0 (a synthetic uniform sample of points: the counts show that every strategy sees the wide shape, not how often real queries over-match). Indexed buffered lines can give false positives for intersection queries that touch the extra area. Buffers above about 1.57 (callers mean about 175 km) throw IllegalArgumentException while the shape is built; a 200 km GeoJSON buffer (about 1.8 degrees) is in that range.
  • Still honoured. Other filter clauses and deletions: 0 documents from another tenant and 0 deleted documents were returned.
  • Lasting. SerializedDVStrategy stores the path with its angle and prefix-tree terms encode the wide corridor, so documents indexed while the bug is present stay wide after a fix until they are reindexed (code reading, not executed).
  • How likely. Rare: the context is opt-in and buffered lines need the builder, polyshape or GeoJSON. For those callers every buffered line is wrong, and conspicuously so; no report was found in the nine years since 7.1.0.

Why it is a bug, not intended

#
  • spatial4j: circle distances are in the units of x and y, and its BUFFER argument "is the buffer distance in degrees".
  • The polyshape reader passes one value to circle radii and line buffers: a 1-degree circle, a 1-radian line.
  • The one radian caller, testGeoPathRect, was ported from a direct spatial3d call; its checks ignore the unit.
The full argument242 words
  • Contract (inferred from spatial4j, not quoted from buffer()). spatial4j ShapeFactory.circle: "The units of "distance" should be the same as x & y." lineString(List<Point> points, double buf): "with a buffer distance along the line in all directions". LineStringBuilder.buffer(double) itself has no javadoc. spatial4j's FORMATS.md: "The BUFFER keyword ... The 2nd argument is the buffer distance in degrees."
  • Lucene's description of the bridge. CHANGES: "LUCENE-7951: Spatial-extras has much better Geo3d support by implementing Spatial4j abstractions: SpatialContextFactory, ShapeFactory, BinaryCodec, DistanceCalculator." The package: "Spatial4j stuff that ideally belongs in Spatial4j (isn't related to Lucene)." No javadoc, CHANGES or MIGRATE text says line buffers are radians.
  • The factory itself. Circles, 2-D points, rectangles, rectangle buffers, the distance calculator and circle radii all use degrees at the boundary. Only the line buffer does not. Its own javadoc names the unit for circles: setCircleAccuracy sets "the accuracy for circles in decimal degrees" (Geo3dShapeFactory.java:82-85).
  • The readers. The polyshape reader passes the same normDist(arg) to circles and line buffers, and normDist is the identity here; GeoJSON converts km to degrees before buffer(). A radians-only builder is wrong for every parsed input, whatever is documented.
  • Maintainer remarks. In the LUCENE-8086 review, dsmiley asked whether the factory's circleAccuracy means "decimal degrees as is used in other parts of the Spatial4j API"; in the LUCENE-7951 review they wrote that verification can "assume decimal degrees here (-/+ 180 etc.) since Geo3d assumes this". Nobody discussed the line buffer's unit.
The devil's-advocate check200 words

Strongest case for "intended" (built by a devil's advocate; the reviews from another model family, OpenAI GPT-5.6, rated it moderate and strong): LineStringBuilder.buffer states no unit; spatial3d is radians-native; the bridge is @lucene.experimental; the behaviour has not changed since 2017; and the only caller of the builder's buffer() outside the factory, ShapeRectRelationTestCase.testGeoPathRect, passes (random().nextInt(89) + 1) * DEGREES_TO_RADIANS, a range that lies within GeoStandardPath's (0, pi/2] bound (1 to 89 degrees, at most 1.553 rad).

Why it fails: the radian width is older than the builder. It dates from LUCENE-6196 (2015), when the test built spatial3d's new GeoPath(width) directly, before the Geo3d spatial context existed; in 7.2.0 the test still called GeoPathFactory.makeGeoPath(planetModel, width, points) directly, where radians are right; LUCENE-8086 (2017-12-13, first in 7.3.0) moved it onto the builder and kept the radian width. The same test passes its circle radius in degrees, and it checks relation consistency, which does not depend on the width's unit. spatial4j's readers can only ever pass degrees. @lucene.experimental allows API changes, not wrong results, and nine quiet years speak to compatibility, not intent. Every verdict calls it a defect; what remains is the compatibility cost for callers who already pass radians.

Suggested fix

#

Recommended A: convert in build(), and switch testGeoPathRect to degrees

In Geo3dLineStringBuilder.build(), pass distance * DistanceUtils.DEGREES_TO_RADIANS to GeoPathFactory.makeGeoPath, and switch testGeoPathRect to degree widths so its corridors stay as wide as today. The new test passes, and so do the whole spatial-extras module (120 tests, 0 failures, 5 skipped) and the module checks. Callers who passed radians get narrower lines; stored buffered lines need reindexing.

// Geo3dShapeFactory.Geo3dLineStringBuilder.build()
GeoPath path =
    GeoPathFactory.makeGeoPath(
        planetModel,
        distance * DistanceUtils.DEGREES_TO_RADIANS,
        points.toArray(GeoPoint[]::new));

// ShapeRectRelationTestCase.testGeoPathRect
final double width = random().nextInt(89) + 1; // degrees, like the circle radius above

Trade-offs

  • Behaviour change: callers who already pass radians, as testGeoPathRect does today, get lines 57.3 times narrower. A CHANGES entry should say so (for example under "Changes in Runtime Behavior").
  • Documents indexed with buffered lines keep the wide shape until they are reindexed (code reading, not executed).
  • Without the test update testGeoPathRect still passes (run), but it would build corridors of 0.017 to 1.55 degrees instead of 1 to 89 and stop covering wide paths.
  • Cost: one multiplication per line built.

Document radians instead (not recommended)

#

Keep the behaviour and state on Geo3dShapeFactory that line buffers are radians.

Trade-offs

Downstream note

#

An application that used a buffered-line query as its visibility boundary (a geofence) would admit documents up to 57 degrees from the line instead of 1, while other filter clauses and deletions are still honoured.

How it was found

#

Non-formal: while writing a differential harness that compares the Geo3d bridge with spatial4j's own geo context, the finder read the unit conversion of every Geo3dShapeFactory method and saw that the line-string buffer has none. A differential check then showed the same 1-degree line DISJOINT from a point 20 degrees away in spatial4j and CONTAINS in the Geo3d context.

The method in full128 words

Method: code reading plus differential testing (the non-formal tier), in a hunt unit on the spatial-extras bridge between spatial4j and spatial3d.

  • The unit's harness compares shapes built by the Geo3d context with the same shapes built by spatial4j's SpatialContext.GEO and by the same factory's circles. While writing its line generator the finder checked each factory method's degrees-to-radians handling and found none for line buffers; the harness now passes buffers in radians so that its other checks do not depend on this question.
  • A differential probe and then a JUnit confirmed it on the stock jars: the 1-degree line contains (5, 20) in the Geo3d context and not in spatial4j's, also when read from spatial4j's polyshape string.
  • A later verifier found the second symptom: buffers above about 1.57 throw.

Bug record

LFV-678, snapshot of 2026-10-29

Registry title
Geo3dShapeFactory passes a line string's buffer distance to spatial3d's GeoPathFactory, which takes radians, without the degrees-to-radians conversion its circle() applies, so in the Geo3d spatial context a line buffered by 1 degree is 1 radian (57.3 degrees) wide and buffers above about 1.57 throw
Area
spatial-extras / spatial4j bridge to spatial3d (Geo3dShapeFactory line-string builder, Geo3dLineStringBuilder.build), reached through the public LineStringBuilder API, the deprecated lineString(List, double), multi-line builders and the Geo3d context's polyshape reader (and the GeoJSON reader when its optional parser is present)
Priority
Medium, rank 239: Every buffered line string in the opt-in Geo3d context silently matches a corridor about 57 times too wide, a matching error worse than the heatmap value error but limited to builder or polyshape callers, so it leads the narrow Geo3d wrong-result rows right after LFV-670.
Impact class
silent wrong results
Impact note
Applications on the opt-in, @lucene.experimental Geo3d spatial context (Geo3dSpatialContextFactory) that index or query buffered line strings (builder API, deprecated lineString(List, double), multi-line builders, the polyshape reader; the GeoJSON reader when its optional parser is present, not executed) get a corridor about 57.3 times wider than requested with no error, so indexed corridors and corridor queries match far too much (an Intersects query on a RecursivePrefixTreeStrategy index returned 3 hits where 1 is right; in the security probe a 1-degree buffer matched 359 of 514 live points where the fix matches 0), and any buffer above about 1.5708 (meant as degrees) throws IllegalArgumentException 'Cutoff angle out of bounds'; unbuffered lines, circles and buffered rectangles are unaffected, ordinary scale, every release from 7.1.0 to 10.5.2.
Summary
You use the Geo3d spatial context, build a line from (0,0) to (10,0) with buffer(1), and expect a corridor reaching 1 degree from the line, because spatial4j distances are in the units of x and y (degrees in a geo context) and spatial4j's standard geo context and the same factory's 1-degree circle both say a point at (5, 20) is DISJOINT. Instead the line CONTAINS that point and its bounding box is about [-57.3, 67.3] x [-57.3, 57.3]: Geo3dLineStringBuilder.build hands the buffer straight to GeoPathFactory.makeGeoPath, whose width is an angle in radians, while the factory's circle() and Geo3dRectangleShape.getBuffered convert degrees with DEGREES_TO_RADIANS. The same happens when the Geo3d context reads spatial4j's polyshape string for a 1-degree buffered line, and every buffer above about 1.5708 is rejected with 'Cutoff angle out of bounds', so a buffer of 2 degrees cannot be built at all.
