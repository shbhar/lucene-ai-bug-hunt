BBoxStrategy's overlap-ratio score counts only one of the two overlaps of two dateline-crossing boxes, so the score is too low

When a query box and a document box both cross the dateline and overlap twice, BBoxStrategy's overlap-ratio score counts only the overlap across the dateline: 0.1032 instead of 0.1548 in the example, so the document ranks too low. Confirmed on main and 15 releases since 4.10.0; spatial matching is unaffected.

The bug in 30 seconds

#

BBoxStrategy (spatial-extras) indexes rectangles and can rank documents by how much their box overlaps the query box (makeOverlapRatioValueSource). A box with minX > maxX crosses the dateline and covers everything except one gap. Two such boxes whose gaps are strictly separated (and whose latitudes overlap) meet twice: across the dateline and on the far side.

  1. In the default geo context, index a document box that runs from 170°E east across the dateline to 20°E (rect(170, 20, -10, 10), 210° wide) with BBoxStrategy, and score it with makeOverlapRatioValueSource(rect(10, -170, -10, 10), 0.5): a query box from 10°E across the dateline to 170°W (180° wide).
  2. The two boxes overlap twice: from 170°E to 170°W across the dateline (20°) and from 10°E to 20°E on the far side of the globe (10°). You expect the documented score with an intersection of 30° x 20°: 600/3600 x 0.5 + 600/4200 x 0.5 = 0.1548.
  3. You get 0.1032. When both boxes cross, the code takes the width as min(maxX) - max(minX) + 360 = -170 - 170 + 360 = 20°: only the piece across the dateline.
  4. Move both boxes 30° west, so only the document crosses, and the score is 0.1548: that branch adds both pieces. Sorting by the score puts a worse match, a box overlapping only 10°E to 35°E (0.1389, computed correctly), above this document.
  5. No error: BBoxStrategy's spatial matching is unaffected, this defect throws nothing, and it only ever lowers the score.

Who is affected

#

Applications that rank, sort or boost by BBoxStrategy's overlap ratio in a geo context (an opt-in, experimental spatial-extras API; Solr exposes it as score=overlapRatio), when the query box and a document box both cross the dateline and overlap twice. One document suffices, with default settings. Spatial matching is unaffected; a filter built on this score is affected.

Mechanism, terms and numbers693 words

BBoxStrategy.makeOverlapRatioValueSource scores a document by how much its box overlaps the query box, with the documented formula intersectionArea / queryArea * p + intersectionArea / targetArea * (1 - p). A box that crosses the dateline covers the whole longitude circle except one gap. When the query box and the document box both cross the dateline, their latitudes overlap and their gaps are strictly separated (disjoint and not touching), each box covers the other's gap and the two boxes overlap twice: once across the dateline and once on the far side of the globe (this needs their widths to add up to more than 360°, but that alone is not enough). The both-cross branch of BBoxOverlapRatioValueSource.score computes the width as min(maxX) - max(minX) + 360, which is only the piece across the dateline. Query rect(10, -170, -10, 10) and document rect(170, 20, -10, 10) share 170..-170 (20°) and 10..20 (10°), but the score uses a width of 20 instead of 30: 0.10317460317460317 instead of 0.15476190476190477 at p = 0.5. The same pair moved 30° west, so only the document crosses, scores 0.15476190476190477. Sorting by the value puts a worse match first. BBoxStrategy's spatial predicates and the index are unaffected; a filter an application builds on this score is affected. This defect only ever lowers the score and does not throw. Confirmed on main and on every release run (15, from 4.10.0, the class's first release, to 10.5.2); every release tag read has the line. Fix: add the second piece in the both-cross branch (+9 lines, validated).

Terms

#
  • BBoxStrategy (lucene/spatial-extras, @lucene.experimental): indexes a spatial4j rectangle as four coordinates plus a dateline flag. makeQuery matches documents; makeOverlapRatioValueSource(queryBox, p) returns a DoubleValuesSource for ranking, sorting or boosting by overlap.
  • Overlap ratio: the class javadoc defines intersectionArea as "the area of the intersection between the query and target envelopes", queryRatio = intersectionArea / queryArea, targetRatio = intersectionArea / targetArea, and score = queryRatio * p + targetRatio * (1 - p) (BBoxOverlapRatioValueSource.java:28-48). Areas are width x height in degrees.
  • Dateline-crossing box: spatial4j rect(minX, maxX, minY, maxY) with minX > maxX covers [minX, 180] + [-180, maxX]. Its uncovered gap is (maxX, minX).

What happens, step by step (main a9779ef3c193, lucene/spatial-extras/src/java/org/apache/lucene/spatial/bbox/)

#
  1. makeOverlapRatioValueSource builds new BBoxOverlapRatioValueSource(makeShapeValueSource(), ctx.isGeo(), queryBox, p, 0.0) (BBoxStrategy.java:232-235). For each document, the value source reads the document's box from doc values and calls score.
  2. score (BBoxOverlapRatioValueSource.java:146-265) computes the intersection height, then the width. When both boxes cross or both do not (:163), it takes left = max(a.minX, b.minX) and right = min(a.maxX, b.maxX) (:165-166). For both crossing it sets width = right - left + 360 (:180-181): the arc from left east across the dateline to right.
  3. If the two gaps are strictly separated (touching gaps leave a second piece of width 0) and the latitudes overlap, each box also covers the arc between the gaps, away from the dateline: [a.minX, b.maxX] when b.maxX > a.minX, or [b.minX, a.maxX] when a.maxX > b.minX (at most one holds). That arc is never added.
  4. When only one box crosses (:183-203), the code adds a west and an east piece (:189-195), so the same geometry moved off the dateline is scored in full.
  5. Every later step is non-decreasing in the width (calcArea, :268-270; the ratios, :208-232; the convex combination, :236-238), so this defect only ever lowers the score. explain() prints the same short width (:249).

Exposure and likelihood369 words
  • Who is hit. Users of makeOverlapRatioValueSource (or BBoxOverlapRatioValueSource directly) in a geo context. BBoxStrategy is in the opt-in spatial-extras module and is @lucene.experimental. Within that API nothing special is needed: the default spatial4j SpatialContext.GEO, BBoxStrategy's default field type, the default codec and a plain IndexWriterConfig (executed: a probe with new IndexWriterConfig() on main, assertions on and off, gives the same value). Downstream, Solr's BBoxField exposes the class as score=overlapRatio ("a relevancy sort/boost"), and geo-catalogue software asks for that score; Elasticsearch and OpenSearch do not use it (read-only code search, not run).
  • What it takes. Both boxes cross the dateline, their latitudes overlap and their uncovered gaps are strictly separated (disjoint and not touching). That needs their widths to add up to more than 360° (necessary, not sufficient): for example a map view wider than half the globe centred on the Pacific, against a near-global dataset extent that also wraps. Deterministic, the same with assertions on and off.
  • What goes wrong. The document's score, sort value and explanation are too low by the dropped piece's share, so it ranks below worse matches. For ordinary boxes at p = 0.5 the deficits shown here are 0.052 (the example) and 0.146 (the independent reproducer's pair). The largest deficit on the hunt's probe grid, 0.69 (0.069 instead of 0.759), is a degenerate pair: two zero-height boxes (horizontal lines at latitude -90, scored as a ratio of widths) at p = 0.
  • Not affected. Which documents BBoxStrategy's spatial predicates match: BBoxStrategy.makeQuery never uses this value source (executed: the Intersects query still matches). A filter that an application builds on this score is affected (executed: with a threshold of 0.12 on the example pair, a positive filter drops the document and a deny rule lets it through). Also not affected: the index, deletions, and other documents' scores (a document's value depends only on its own box and the query box). This defect does not throw and cannot push a score above its exact value (so not above 1); the work per document does not change.
  • How likely. Rare: two crossing boxes that together span more than 360° are uncommon, and no prior report was found in the documented searches, 12 years after 4.10.0.

Why it is a bug, not intended

#
  • The javadoc defines intersectionArea as "the area of the intersection between the query and target envelopes"; isGeo means "dateline issues should be attended to".
  • The same method adds both pieces when only one box crosses; the upstream "wrap" test (0.2794117) expects that sum.
  • Moving both boxes 30° west cannot change their overlap, yet the score rises from 0.1032 to 0.1548.
The full argument256 words
  • The contract. BBoxOverlapRatioValueSource.java:35-48 defines intersectionArea as the intersection's area and the score from it; the constructor documents isGeo as "True if ctx.isGeo() and thus dateline issues should be attended to" (:85).
  • The sibling branch and its test. When one box crosses, the code sums a west and an east piece (:183-203). TestBBoxStrategy#testOverlapRatio, case "wrap", expects 0.2794117 (TestBBoxStrategy.java:258-259): query [0, 40] against document rect(30, 10) overlaps in [30, 40] + [0, 10] = 20°, so 800/1600 x 0.5 + 800/13600 x 0.5.
  • Rotation invariance. The same pair scores 0.15476 moved 30° west and 0.10317 in place; a credibility audit's metamorphic test, which uses no hand-computed value, fails the same way and passes with the fix.
  • The computed width means nothing else. 20 is neither the true overlap (30) nor the width of either enclosing envelope (180 or 210).
  • No test pins the current value. Swept over all its (SHIFT, nudge) combinations, the upstream "wrap" case reaches the both-cross branch only twice, both times with a second piece of width 0; stock and fixed code agree there.
  • History. The line is a leftover of the 2012 port (LUCENE-4175, width = right + 360.0 - left in the unreleased AreaSimilarity). LUCENE-5714/5779 (2014) rewrote the one-crossing branch to sum both pieces and kept this one; their threads describe the work as fixing "a variety of dateline related bugs when computing intersection width & height" (#6841). None of the 35 comments on #5247, #6776 and #6841 discusses two crossing boxes that overlap twice.
The devil's-advocate check255 words

The strongest case for intended behaviour (the hunt's intended-behaviour checker; a read-only cross-model reviewer, OpenAI GPT-5.6, which did not run code, rated it weak): the class is an @lucene.experimental relevance heuristic whose javadoc says it works "as envelope on envelope (rect on rect) overlays rather than complex polygon on complex polygon overlays" (:25-26), so "the intersection between the query and target envelopes" could mean one envelope rather than a two-piece region; the formula was already in Lucene's 2012 port, and the class says it was "Originally based on" Geoportal's SpatialRankingValueSource (:61-63); areas are planar degrees anyway (// TODO option to compute geodetic area, :81); the trigger is unusual; and no prior report was found in 12 years.

Why it fails: the same method already counts a two-piece overlap in full when one box crosses, and the upstream "wrap" assertion depends on it, so the single-envelope reading contradicts the class's own code and test. Under that reading the answer would be an envelope 180° or 210° wide, not 20°. The javadoc says dateline issues are attended to in geo mode, yet the result depends on where the dateline falls. The origin is no argument for keeping the formula: the same javadoc says Lucene's version was "modified quite a bit" and that Geoportal's algorithm "had dateline bugs" (:63-65). The planar approximation is applied consistently elsewhere and is not what goes wrong here. When filing, call it a relevance-only error for a rare but legal shape, not wrong matching.

Suggested fix

#

Recommended Add the second overlap piece in the both-cross branch

In the both-cross branch, also add the overlap away from the dateline: max(0, b.maxX - a.minX) + max(0, a.maxX - b.minX); at most one term is positive, so nothing is counted twice (+9 lines). The repro passes 3 of 3 with assertions on and off, and all 120 spatial-extras tests pass.

         } else { // both cross
+          // the overlap that contains the dateline
           width = right - left + 360;
+          // the two boxes can also overlap away from the dateline, when each one covers the gap the
+          // other leaves (at most one of these two terms is positive)
+          if (b.getMaxX() > a.getMinX()) {
+            width += b.getMaxX() - a.getMinX();
+          }
+          if (a.getMaxX() > b.getMinX()) {
+            width += a.getMaxX() - b.getMinX();
+          }
         }

Add the second overlap piece in the both-cross branch (validated by the checks) (recommended)

#

After width = right - left + 360; (the piece across the dateline), add b.maxX - a.minX when it is positive and a.maxX - b.minX when it is positive. For two crossing boxes (a.maxX < a.minX, b.maxX < b.minX) both cannot hold, since together they would give b.maxX > b.maxX. The added arc lies between the two gaps, disjoint from the dateline piece. When the gaps overlap, neither term is positive and the result is unchanged.

Trade-offs

  • Behaviour change: only pairs where both boxes cross the dateline and their gaps are disjoint score higher, up to the exact value; every other pair keeps its score, so rankings change only for those documents.
  • Cost: two comparisons per document that reaches this branch; no benchmark was run. No format or API change.

Compute the both-cross width from the two gaps

#

width = 360 - gapA - gapB + overlap(gapA, gapB), with gap = minX - maxX: everything except what either box leaves uncovered.

Trade-offs

Not run in Lucene. Algebraically the same width as A, but not bit for bit: in double arithmetic it rounds differently, also for pairs A leaves unchanged (a seeded sample of 1,000,000 random both-cross pairs: 285,412 widths differed from A's, 168,407 of them one-piece pairs whose stock value A keeps exactly, by at most 1.1e-13 degrees). It needs its own interval-overlap code and its own tests.

One arc-intersection helper for all branches

#

Treat each box as one or two longitude intervals and sum the pairwise overlaps, replacing the three-way case analysis.

Trade-offs

Not run. Simpler to reason about, but it rewrites the tested one-crossing branch and the "both adjacent to dateline" special case (:170-173), so it needs more review.

Document the limitation

#

Say in the javadoc that, when both boxes cross the dateline, only the overlap across the dateline is counted.

Trade-offs

Not recommended. Keeps the wrong rankings and the dependence on where the dateline falls.

Downstream note

#

Solr's BBoxField exposes this score as score=overlapRatio for relevancy sort and boost, so Solr users who rank wide dateline-crossing extents get the same too-low scores.

How it was found

#

Bounded-exhaustive checking of the real jar against the class-javadoc formula: every ordered pair of 1,245 geo boxes, 4 proportions and 2 minimum side lengths, 12,400,200 checks. 154,000 disagreed, every one a two-piece overlap; the fix, which changes only the both-cross branch, takes them to 0. A public-API JUnit then confirmed it.

The method in full192 words

Method: semi-formal, bounded-exhaustive checking against exact semantics (hunt unit on spatial-extras, 2026-10-26, main ea57360912ed).

  • A harness built 1,245 distinct geo boxes (longitudes from {-180, -170, -100, -90, 0, 10, 90, 100, 170, 180}, latitudes from {-90, -10, 0, 10, 90}) and scored every ordered pair with BBoxOverlapRatioValueSource for queryTargetProportion {0, 0.25, 0.5, 1} and minSideLength {0, 0.1}, with assertions on and off.
  • The reference was an independent evaluation of the class-javadoc formula, with the intersection measured as arcs on the longitude circle.
  • 154,000 of 12,400,200 checks disagreed, all two-piece intersections (counted by the harness); 0 NaN, 0 scores outside [0, 1], 0 assertion failures. With the fix sketch, which changes only the both-cross branch, 0 disagreed, so every mismatch was a pair of two crossing boxes; a later probe through the public indexing path, over the same boxes and proportions with the default minimum side length 0, counts that directly: 0 undercounts outside both-cross, 0 overcounts.
  • The finder then wrote a JUnit on the public indexing path (after a first cross-model review objected to a repro that called the protected score() directly) and confirmed the failure on main, 10.5.2 and 9.12.3.

History

#

Introduced with the class in 4.10.0 by LUCENE-5714/5779 (7e0aff8dabc4, 2014-07-08); the formula itself dates from the 2012 LUCENE-4175 port. Executed on 15 releases from 4.10.0 to 10.5.2 and on main: all affected; 4.10.0 with the fix passes. Not a regression; not fixed upstream.

Versions tested6 rows

Introduced by 7e0aff8dabc4 on trunk (2014-07-08) and its branch_4x backport c608265684cf (2014-07-09, the copy that shipped first), "LUCENE-5714, LUCENE-5779: Enhance BBoxStrategy & Overlap similarity. Configurable docValues / index usage. Add new ShapeAreaValueSource." by @dsmiley; JIRA era, no pull request (LUCENE-5714 is #6776, LUCENE-5779 is #6841). It created BBoxOverlapRatioValueSource with the documented intersection-area formula and rewrote the one-crossing branch to sum both pieces, but kept the both-cross formula. That formula came from 26d3f1f813ea (2012-06-28, "LUCENE-4175: adding bbox strategy", @ryantxu, #5247), whose unreleased AreaSimilarity had width = right + 360.0 - left. First released in 4.10.0 (CHANGES: "Index and search rectangles with spatial BBoxSpatialStrategy using most predicates. Sort documents by relative overlap of query areas ..."). Bug record

LFV-369, snapshot of 2026-10-29

Registry title
BBoxStrategy's overlap-ratio relevance (BBoxOverlapRatioValueSource) undercounts the overlap of two dateline-crossing boxes that intersect in two longitude pieces, so the score is too low
Area
spatial-extras / BBoxStrategy overlap-ratio relevance (BBoxOverlapRatioValueSource.score: intersection width when both boxes cross the dateline)
Priority
Low, rank 361: A spatial-extras overlap-ratio score.
Impact class
silent wrong results
Impact note
Applications that rank or sort by BBoxStrategy's overlap-ratio relevance (makeOverlapRatioValueSource in the opt-in spatial-extras module; Solr's BBoxField exposes the same class as score=overlapRatio, by a read-only code search) in the default geo context get a score that is too low, so the document ranks too low, whenever the query box and the document box both cross the dateline and the longitude stretches they leave uncovered do not overlap, which needs their widths to add up to more than 360 degrees; default BBoxStrategy, codec and IndexWriterConfig, one document suffices, -ea and -da, every release since 4.10.0; matching, filtering and the index are unaffected, the score never goes up and nothing throws.
Summary
You index a dateline-crossing rectangle with BBoxStrategy in the default geo context and score it with makeOverlapRatioValueSource and a query rectangle that also crosses the dateline, and you expect the documented score intersectionArea/queryArea*p + intersectionArea/targetArea*(1-p), where intersectionArea is 'the area of the intersection between the query and target envelopes'. When the two boxes wrap far enough round the globe that they overlap twice, once across the dateline and once on the far side (query rect(10,-170,-10,10) and document rect(170,20,-10,10) share 170..-170 across the dateline, 20 degrees, and 10..20, 10 degrees), the score counts only the piece across the dateline: 0.10317460317460317 instead of 0.15476190476190477 at p = 0.5. The both-cross branch computes the width as right - left + 360, which is only that piece, while the branch for one crossing box already adds up both pieces.
