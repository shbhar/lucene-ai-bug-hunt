CompositeVerifyQuery.visit hides the index query it runs, so term extraction and the nested clause limit miss it

CompositeVerifyQuery runs an index query that every hit must match, but its visit() reports only itself, as a leaf. So QueryVisitor.termCollector finds [] instead of [body:a], and the cumulative clause limit counts a 20-clause index query as 1 clause, while hits stay correct.

The finding in 30 seconds

#

CompositeVerifyQuery finds candidates with a cheap index query and checks each one against a shape. A tool that walks the query with Query#visit never sees that index query.

Background

#
  1. CompositeVerifyQuery (spatial-extras, experimental) pairs an index query, a cheap approximation, with a shape predicate that verifies each candidate. A document is a hit only if it matches both.
  2. Query#visit walks the query tree. A wrapper passes the visitor on to its child queries; a leaf reports its terms (consumeTerms) or, if it matches on no terms, calls visitLeaf.
  3. Two users of visit: QueryVisitor.termCollector (term extraction, for example for highlighting) and IndexSearcher's clause limit, which since 9.0 counts every leaf of the whole tree against maxClauseCount (1024 by default) and throws TooManyNestedClauses past it.

The finding, step by step

#
  1. Wrap TermQuery(body:a) in new CompositeVerifyQuery(indexQuery, shapePredicate) and collect its terms with QueryVisitor.termCollector(terms).
  2. You expect [body:a]: every hit must match the index query, and Query#visit is documented to "visit any child queries". ConstantScoreQuery(TermQuery(body:a)) gives [body:a].
  3. You get []: visit() only calls visitor.visitLeaf(this), and the term collector ignores leaves.
  4. Same line, second effect (9.0 on): with maxClauseCount = 8, a 20-clause DisjunctionMaxQuery alone is rejected with TooManyNestedClauses, but wrapped as the index query it passes IndexSearcher#rewrite and runs, counted as 1 clause.
  5. Hits are correct in every run. One line fixes both effects: visit the index query through a FILTER sub-visitor, as ConstantScoreQuery does. Then a wrapped index query over the limit, which runs today, throws TooManyNestedClauses.

Who is affected

#

Code that builds CompositeVerifyQuery itself around a term-bearing or large index query, then extracts terms through Query#visit or relies on maxClauseCount to reject oversized queries. In-tree, CompositeSpatialStrategy loses at most one binary cell token (points-only prefix tree, IsEqualTo or IsWithin) and its clause count is unchanged. No run shows a wrong hit or count.

Mechanism, terms and numbers662 words

CompositeVerifyQuery (spatial-extras, @lucene.experimental, public constructor) runs an index query as the approximation of every match and verifies each candidate against a shape predicate in TwoPhaseIterator#matches(). Its rewrite rewrites the index query and keeps it in the tree, and its createWeight runs it, so every hit must match it. But visit is visitor.visitLeaf(this); and never visits the index query.

Two consumers go wrong. QueryVisitor.termCollector and other visit-based term extraction (Lucene's UnifiedHighlighter extracts its terms this way) see none of the index query's terms: every release since 8.1.0. IndexSearcher's cumulative clause check, built on Query#visit since 9.0.0, counts the whole wrapper as one clause, so an index query with more clauses than maxClauseCount runs instead of throwing TooManyNestedClauses. No run shows a wrong hit or count, and matching does not use visit. In-tree, CompositeSpatialStrategy loses at most one binary cell token (points-only prefix tree, IsEqualTo or IsWithin on a point) and never changes the clause count. The fix is one line, as in ConstantScoreQuery; it changes admission, since some wrapped queries that run today then throw TooManyNestedClauses.

The code (main 645d4fe14a20)

#
  1. The index query is a real child. CompositeVerifyQuery.java:41 private final Query indexQuery; // approximation (matches more than needed); :44-47 the public constructor accepts any Query.
  2. It is rewritten and kept. :49-56: rewrite calls indexQuery.rewrite(indexSearcher); if that returns a different query it returns a new CompositeVerifyQuery around it, otherwise super.rewrite(indexSearcher), the query itself. Either way the index query stays in the tree.
  3. It is executed as the approximation. :92-118: createWeight calls indexQuery.createWeight(searcher, ScoreMode.COMPLETE_NO_SCORES, boost) directly (:95-97), takes its scorer per segment (:102; no scorer, no hits) and wraps that iterator in the predicate's TwoPhaseIterator (:107-108). A document the index query does not match is never a hit (CompositeVerifyQuery(TermQuery(body:t2), P), with a predicate all 4 documents satisfy, returns 1 of 4 documents).
  4. visit hides it. :87-90: visitor.visitLeaf(this);.
  5. Term extraction sees nothing. QueryVisitor.java:91-98: termCollector overrides only consumeTerms; visitLeaf is a no-op by default (:58). UnifiedHighlighter.extractTerms is query.visit(QueryVisitor.termCollector(queryTerms)) (UnifiedHighlighter.java:481-485; read, not run with this class).
  6. The clause guard counts one. IndexSearcher.java:871-880: rewrite rewrites to a fixed point and then runs query.visit(getNumClausesCheckVisitor()) (:878); the counter (:896-931) adds one per visitLeaf, consumeTerms or consumeTermsMatching call (it tests the limit before counting, :909-912, so at a limit of 8 the 10th leaf throws: the separate off-by-one LUCENE-9299, #10339, which this bug and its fix do not touch). The wrapper is one visitLeaf call whatever it holds, and the class never sends its index query through IndexSearcher#rewrite, so the searcher's clause check never sees it. (AbstractKnnVectorQuery also does not visit its filter, but rewrites it through indexSearcher.rewrite(...), AbstractKnnVectorQuery.java:93, so its filter is still checked.)
  7. What still limits a query. Each BooleanQuery.Builder#add rejects more than maxClauseCount clauses in that one builder (BooleanQuery.java:74-86, "We do the final deep check ... during IndexSearcher.rewrite"). DisjunctionMaxQuery has no build-time check, and nested builders each stay under the limit. A query timeout still applies.

The numbers

#
  • termCollector over CompositeVerifyQuery(TermQuery(body:a), predicate): []; over the bare TermQuery and over ConstantScoreQuery(TermQuery): [body:a].
  • maxClauseCount = 8, index query = DisjunctionMaxQuery of 20 TermQuery clauses: searcher.rewrite(dmq) throws; BooleanQuery(MUST CompositeVerifyQuery(TermQuery(body:t0), predicate), FILTER dmq) throws; searcher.rewrite(new CompositeVerifyQuery(dmq, predicate)) does not. With a BooleanQuery of 4 MUST sub-queries of 5 SHOULD terms each, the wrapped query passes and count() returns the correct 4.
  • In-tree: CompositeSpatialStrategy over a points-only prefix tree (6 levels) and a serialized shape field, IsEqualTo or IsWithin on Pt(10, 20), builds CompositeVerifyQuery(rpt:s5x1g8, shapeDocVal(sdv) Equals Pt(x=10.0,y=20.0)) around a TermQuery on a cell token (RecursivePrefixTreeStrategy.java:216-229): 0 terms instead of 1; 1 leaf either way; the 1 hit is correct. Its other index queries (IntersectsPrefixTreeQuery and the like) visit as one leaf themselves, so recursing changes neither their terms nor their clause count.
Exposure and likelihood202 words
  • Term extraction. QueryVisitor.termCollector, UnifiedHighlighter's term extraction (read) or an application's own visitor (field-based term lists, query logging, cache keys) miss the index query's terms. Every release since 8.1.0. (The classic Highlighter skips every org.apache.lucene.spatial.* query anyway, WeightedSpanTermExtractor.java:266-276, LUCENE-7293.)
  • Clause guard. Since 9.0.0, an index query with more leaf clauses than maxClauseCount (1024 by default), in a DisjunctionMaxQuery or spread over nested builders that each stay under the limit, runs instead of throwing TooManyNestedClauses. Per-builder checks and query timeouts still apply.
  • In-tree reach is small. CompositeSpatialStrategy reaches only the term half, only with a points-only prefix tree and a non-optimized predicate (IsEqualTo, IsWithin; also Intersects after setOptimizePredicates(false): 0 terms instead of 1, executed in the fact check). The lost term is one binary cell token on the spatial field, so the in-tree highlighting effect is small.
  • Default vs opt-in. Default searcher, codec and maxClauseCount suffice; using the class is opt-in. No scale is needed.
  • What does not happen. No run shows a wrong hit or count; the score is the wrapper's constant; no exception; no index change. The documents a query matches do not depend on visit. Nobody has reported it since 8.1.0 (2019).

Why it looks unintended

#
  • Query#visit must "Recurse through the query tree, visiting any child queries"; visitLeaf is for queries "that do not match on terms". ConstantScoreQuery and IndexOrDocValuesQuery recurse.
  • The class was written in 2015 to pass its index query's terms through; a mechanical API sweep dropped that before any release.
  • The same omission elsewhere was fixed as a bug (LUCENE-8849).
The full argument266 words
  • Contracts. Query.java:89 "Recurse through the query tree, visiting any child queries." QueryVisitor.java:54 visitLeaf is "Called by leaf queries that do not match on terms"; :87 termCollector "collects all terms that may match a query". IndexSearcher.java:1194-1195 TooManyNestedClauses is "Thrown when a client attempts to execute a Query that has more than getMaxClauseCount() total clauses cumulatively in all of its children." CHANGES.txt:4681-4684 (9.0.0, LUCENE-8811): the checks "apply to all queries, rather than only booleans"; MIGRATE.md:1533: "on all types of queries".
  • The design rule. The QueryVisitor author, in its review (lucene-solr#581, 2019-02-26): "Yes, all compound queries should pull a sub visitor and call visit on each of their sub queries with it. And visitLeaf is for queries that don't match on terms."
  • Peers recurse. ConstantScoreQuery.java:77-79 (FILTER), BoostQuery.java:105-107 (MUST), IndexOrDocValuesQuery.java:141-145 (MUST, both children), FunctionScoreQuery (MUST).
  • History. LUCENE-5579 (#6641, 489f56def84, 2015-04-10) created the class with extractTerms(terms) { indexQuery.extractTerms(terms); }. The LUCENE-6425 sweep (#7484, f4c05465673, 2015-04-16) moved extractTerms to Weight and dropped that delegation without a replacement, although its own no-op ConstantScoreWeight.extractTerms says "override if your constant-score query does wrap terms"; both landed before 5.2.0. LUCENE-3041 (fbd05167f45, 2019) then wrote visitLeaf(this); none of the 123 comments on lucene-solr#581 mentions this class.
  • Precedent. LUCENE-8849 (#9892, opened by the class's author; 8.6.0 Bug Fixes, CHANGES.txt:5800): "DocValuesRewriteMethod.visit wasn't visiting its embedded query". LUCENE-9050 (#10092, CHANGES.txt:6163): "MultiTermIntervalsSource.visit() was not calling back to its visitor".
  • No test or doc says otherwise. No test in lucene/spatial-extras/src/test calls visit or termCollector; no javadoc, CHANGES or MIGRATE entry calls the class opaque.
The devil's-advocate check258 words

The strongest case for "intended": the class is one atomic, experimental spatial predicate whose approximation is an implementation detail; the 8.1 CHANGES entry for LUCENE-3041 (CHANGES.txt:6469-6475) lets a query "either pass the visitor down to any child queries, or call a visitX() or consumeX() method on it"; Lucene has deliberately opaque composites (block-join queries, DrillSidewaysQuery); before 8.1 the class's extractTerms reported nothing, so visitLeaf(this) kept the old behaviour; the visitor-based clause count was said in LUCENE-8811 (#9855) to be not exact; and LUCENE-7293 (#8348) made the classic Highlighter skip spatial queries.

Why it fails: the index query is a conjunct every hit must match, not an alternative implementation; the old behaviour came from two mechanical sweeps, while the class was written to delegate and its author later filed the same omission elsewhere as a bug; block-join children match other documents, while this index query matches the same ones, and this class is public, takes any Query and stays itself after rewrite; LUCENE-8811's stated goal covers "booleans wrapped in other queries"; LUCENE-7293 is about one highlighter, predates QueryVisitor and says nothing about visit or the clause limit; @lucene.experimental marks API stability, not an exemption. Verdict: a defect, on a case that is persuasive rather than conclusive: no javadoc, test or upstream discussion says what this class must report to visitors. The fact-check reviewer from another model family (OpenAI GPT-5.6, reading only) rated the intended case "moderate" and the bug as clearing the no-noise bar narrowly; a maintainer could call it low-priority housekeeping of an experimental API.

Suggested fix

#

Recommended Visit the index query with a FILTER sub-visitor

Visit the index query instead of reporting a leaf: indexQuery.visit(visitor.getSubVisitor(BooleanClause.Occur.FILTER, this));, as ConstantScoreQuery does. The repro and the two-symptom test pass, and so do the closest suites, the spatial-extras module and lint. It changes admission: wrapped index queries over the limit, which run today, then throw TooManyNestedClauses.

@Override
public void visit(QueryVisitor visitor) {
  indexQuery.visit(visitor.getSubVisitor(BooleanClause.Occur.FILTER, this));
}

Visit the index query with a FILTER sub-visitor (validated by the checks) (recommended)

#

One line plus an import (+2/-1). FILTER matches how the index query runs: required but not scored (COMPLETE_NO_SCORES), as in ConstantScoreQuery.visit.

@Override
public void visit(QueryVisitor visitor) {
  indexQuery.visit(visitor.getSubVisitor(BooleanClause.Occur.FILTER, this));
}

Trade-offs

  • Admission changes (worth the CHANGES line). Some queries that run today start throwing TooManyNestedClauses: with the fix at a limit of 8, the wrapped 20-clause DisjunctionMaxQuery and the 4 MUST x 5 SHOULD shape throw on rewrite and count (executed in the fact check). That is the point of the fix, but applications see it.
  • Visitors see the child. The visitor receives the index query's leaves (consumeTerms or visitLeaf) instead of one visitLeaf for the wrapper, so a visitor that recognised CompositeVerifyQuery through visitLeaf now sees it only as the getSubVisitor parent, and the index query's own acceptField gating starts to apply.
  • From reading only, not run: UnifiedHighlighter.hasUnrecognizedQuery (UnifiedHighlighter.java:1185-1205) sets its unknown-leaf flag only from visitLeaf, and today the wrapper's ungated visitLeaf(this) sets it whatever the field. With the fix and a TermQuery index query (the repro, the in-tree points-only path) the child reports consumeTerms, so the flag is not set; with a prefix-tree index query (a field-gated visitLeaf) it is set only for the spatial field.
  • The shape predicate is no longer reported at all; it reads doc values, not terms. Option C keeps that signal.

Trade-offs

Visit the index query and still report the wrapper as a leaf (validated by the checks)

#

Add visitor.visitLeaf(this); after the line of option A, to report the shape predicate, which does not match on terms.

Trade-offs

Keeps today's signal for visitors that detect the class, or any non-term condition, through visitLeaf; costs one extra counted clause per wrapper, and visitLeaf(this) is not gated by acceptField, so field-filtering visitors still see an unknown leaf on every field.

What the checks validated

The minimal test and the finder's two-symptom test pass (standalone runner, 645d4fe14a20 jars, assertions on); not run through gradle.

Document the class as opaque (not a fix)

#

Say in the javadoc that visit does not descend into the index query.

Trade-offs

At odds with the general Query#visit guidance for a child every hit must match, and leaves the clause guard bypassable through a public constructor. Workaround meanwhile: visit, or IndexSearcher#rewrite, your own index query before wrapping it.

Downstream note

#

Solr's RptWithGeometrySpatialField builds its queries with CompositeSpatialStrategy (read from its source, not run), so only the narrow in-tree term case can reach it; an application that relies on maxClauseCount alone to bound an index query it wraps should bound that query itself.

How it was found

#

A planning probe, from an ideas list on contracts that committers state, showed this class hiding its index query from term collection. The finder re-ran it, then compared what visitors see for CompositeVerifyQuery(I, P) and for I alone over 9 index-query kinds (a model-based differential harness): 3 of 18 checks mismatched. A public-API JUnit confirmed it.

The method in full181 words

Method: semi-formal (the hunt's tier for model-based testing against an explicit model of the contract).

  • Lead. The hunt's planner had an executed lead from an ideas list on committer-stated contracts, written with an independent reviewer from another model family (OpenAI GPT-5.6), and a probe of it, which showed termCollector finding 20 terms for a bare index query and 0 for the wrapped one, and the bare query rejected by the clause limit while the wrapped one ran. The hunt unit re-ran the probe first.
  • Model-based differential harness. For 9 kinds of index query I, it compared QueryVisitor.termCollector and the clause counter's leaf count of CompositeVerifyQuery(I, P) with those of I: 18 checks, 3 mismatches (the TermQuery and the 2-clause BooleanQuery index queries lose their terms, and the BooleanQuery counts 1 leaf instead of 2), 0 with the fix; the same on 10.5.2.
  • JUnit. Reduced to a public-API test with two methods (terms; clause limit), which fails 2 of 2 with assertions on and off and 20 of 20 over 10 random seeds; later minimized to the one-method test above.

LFV-951, snapshot of 2026-11-08

Registry title
CompositeVerifyQuery.visit reports the whole query as a leaf and never visits the index query it rewrites and executes, so QueryVisitor term collection misses the index query's terms and IndexSearcher's cumulative maxClauseCount check does not count its clauses
Area
spatial-extras / composite: CompositeVerifyQuery (Query#visit; consumers: QueryVisitor.termCollector and other visit-based term extraction, IndexSearcher's cumulative clause limit)
Priority
Low, rank 748: CompositeVerifyQuery hiding its index query from QueryVisitor is the same visitor-hiding class as LFV-917 and LFV-916, with hits still correct and impact mostly limited to application-built wrappers, so it closes those rows after LFV-916.
Impact class
minor
Impact note
Applications that build a CompositeVerifyQuery with its public, @lucene.experimental constructor around their own index query get no TooManyNestedClauses for the index query's clauses, because the cumulative check counts the whole wrapper as one clause (from 9.0.0 on; executed with a 20-clause index query under maxClauseCount=8, while with the default limit of 1024 the index query needs more than 1024 clauses, spread over nested queries that each stay under the limit [read]), and QueryVisitor.termCollector and other visit-based term extraction see none of the index query's terms (every release since 8.1.0); CompositeSpatialStrategy's own queries are hit only by the term half and only with a points-only prefix tree and IsEqualTo or IsWithin on a point, where the one lost term is a binary spatial cell token; search hits are always correct; default searcher and codec, ordinary scale.
Summary
You wrap your own index query, for example TermQuery(body:a) or a 20-clause DisjunctionMaxQuery, in new CompositeVerifyQuery(indexQuery, shapePredicate), then collect its terms with QueryVisitor.termCollector or search it after IndexSearcher.setMaxClauseCount(8). You expect [body:a] and an IndexSearcher.TooManyNestedClauses error, because Query#visit is documented to 'recurse through the query tree, visiting any child queries', the wrapper rewrites its index query and runs it as the approximation that every hit must match, and the same 20 clauses as a bare query or as a sibling FILTER clause are rejected. Instead CompositeVerifyQuery.visit only calls visitor.visitLeaf(this): termCollector returns [] and the clause check counts the whole query as one clause, so the over-limit query runs (its hits are correct).
