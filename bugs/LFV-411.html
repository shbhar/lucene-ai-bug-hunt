Grouping DoubleRangeFactory gives the below-min group the lower bound 4.9E-324 (Double.MIN_VALUE), so its label leaves out the group's zero and negative values

The finding in 30 seconds

#

DoubleRangeFactory puts every value below min into one bucket and returns it as a DoubleRange, documented as [min, max). For that bucket it writes Double.MIN_VALUE, 4.9E-324, as the lower end.

Background: grouping by double ranges

#
  1. DoubleRangeGroupSelector groups search results by a double value. A DoubleRangeFactory(min, width, max) defines the buckets: width-wide buckets from min to max, one bucket for every value below min, one for max and above.
  2. Each bucket comes back as the group's value, GroupDocs.groupValue(), a DoubleRange with an inclusive min and an exclusive max.
  3. In Java, Double.MIN_VALUE is 4.9E-324, the smallest positive double. The most negative double is -Double.MAX_VALUE, and below that comes Double.NEGATIVE_INFINITY.

The finding, step by step

#
  1. You group documents by a double field with DoubleRangeGroupSelector and new DoubleRangeFactory(-10, 5, 10): buckets 5 wide from -10 to 10, one bucket for everything below -10, one for 10 and up. The values are -20, -15, -11, -3, 0, 4 and 12.
  2. You expect the bucket of -20, -15 and -11 to carry a [min, max) label that contains them, such as [-Infinity, -10). The long twin does that: LongRangeFactory(-10, 5, 10) gives [Long.MIN_VALUE, -10).
  3. Instead the label is DoubleRange(4.9E-324, -10.0). The code uses Double.MIN_VALUE as the lower end, and in Java that is the smallest positive double, not the most negative one. A range from just above 0 up to -10 contains no number at all.
  4. The group itself is right: the same 3 documents, count and order. But a query built from its bounds, the way Lucene's own selector test rebuilds a group (DoublePoint.newRangeQuery(min, Math.nextDown(max))), finds 0 of the 3.
  5. A positive min does not save it: with Lucene's test config DoubleRangeFactory(100, 100, 900) and the values 0.0, -1.0 and 50.0 below 100, the label DoubleRange(4.9E-324, 100.0) leaves out 0.0 and -1.0, and its query finds 1 of the group's 3 documents.

Who is affected

#

Applications that group with DoubleRangeGroupSelector (opt-in) and read the below-min bucket's lower bound, for a heading or a drill-down query, when that bucket holds 0.0 or a negative value: always when min <= 0. Every such search, any index size, default settings otherwise. Membership, counts and order stay right.

Mechanism, terms and numbers482 words

DoubleRangeFactory(min, width, max) buckets double values for DoubleRangeGroupSelector: "all doubles below" min go "into a single range", and every bucket is returned as a DoubleRange, "a contiguous range of double values, with an inclusive minimum and exclusive maximum". For a value below min, getRange returns [Double.MIN_VALUE, min) (DoubleRangeFactory.java:52-56 on main 645d4fe14a20). Double.MIN_VALUE is 4.9E-324, the smallest positive double, not the most negative one. So with new DoubleRangeFactory(-10, 5, 10) the group of -20, -15 and -11 is labelled DoubleRange(4.9E-324, -10.0), an inverted range that contains no number, and with a positive min the label leaves out 0.0 and every negative member. Membership, counts and order are right, because the selector uses the range only as an equality key; what is wrong is GroupDocs.groupValue() of that one group, and anything built from it: a query rebuilt from the bounds, as Lucene's own selector test does, finds 0 of the group's 3 documents. The twin LongRangeFactory uses Long.MIN_VALUE. Every release since 8.6.0 has it, 10.6.0 included. The fix is Double.NEGATIVE_INFINITY, plus updating the one upstream assertion that pins the old label.

The mechanism (main 645d4fe14a20)

#
  1. The factory (DoubleRangeFactory.java:48-66):
   if (reuse == null) {
     reuse = new DoubleRange(Double.MIN_VALUE, Double.MAX_VALUE);   // :50, always overwritten
   }
   if (value < min) {
     reuse.max = min;
     reuse.min = Double.MIN_VALUE;                                  // :54, the bug
     return reuse;
   }

Double.MIN_VALUE is "the smallest positive nonzero value of type double", 2^-1074 = 4.9E-324 (JDK javadoc).

  1. What the label says. DoubleRange.min is "The inclusive minimum value of this range" and max the exclusive maximum (DoubleRange.java:27-31). With min <= 0, [4.9E-324, min) is inverted and empty. With min > 0 it holds the positive members and leaves out 0.0, -0.0 and every negative member.
  2. Why membership is still right. DoubleRangeGroupSelector.advanceTo calls getRange once per document (DoubleRangeGroupSelector.java:71) and keeps a document in the second pass if a HashSet<DoubleRange> of the first pass's group values contains its range (:75, :89-97); DoubleRange.equals compares min and max (DoubleRange.java:44-50). Every value below min gets the same key, so groups, counts, order and shard merging (SearchGroup.java:195-207) are consistent; only the numbers in the key are wrong.
  3. The twin. LongRangeFactory.getRange is the same code with Long.MIN_VALUE (LongRangeFactory.java:50, :54).

Exposure and likelihood235 words
  • Who is hit. Users of DoubleRangeGroupSelector, through GroupingSearch(Supplier<GroupSelector>) or the grouping collectors, who show the below-min bucket's bounds or build a filter, link or drill-down query from them, and whose values below min include 0.0 or a negative number: always when min <= 0 (temperatures, deltas, balances, scores around zero); with min > 0, for example a free item (0.0) under a price floor.
  • Not hit. Applications that name the open-ended bucket only by its upper end ("below 10"), use the group value only as an opaque key, or whose values below min are all positive; LongRangeFactory.
  • Opt-in, otherwise default. Range grouping must be chosen explicitly; nothing else is needed: default IndexWriterConfig, codec and searcher, any index size, every search whose below-min group holds a value <= 0, deterministic, the same with assertions on and off. GroupingSearch, TopGroups, GroupDocs and SearchGroup (the types whose groupValue carries the label) are @lucene.experimental; the three range classes carry no such tag.
  • Effect. A wrong, too-narrow label: displays show an impossible range, and a query rebuilt from it matches fewer documents than the group holds (0 of 3, 1 of 3), never extra ones. No exception, no hang.
  • Use in the wild. Not established: code searches of three large open-source servers that embed Lucene found no use, but a positive control hit a rate limit, so those zeros are not relied on.

Why it looks unintended

#
  • DoubleRange is "a contiguous range of double values, with an inclusive minimum and exclusive maximum"; DoubleRange(4.9E-324, -10.0) contains no value at all.
  • The twin LongRangeFactory uses Long.MIN_VALUE, the true minimum, in the same place.
  • Lucene's own selector test rebuilds every group from its bounds with DoublePoint.newRangeQuery(min, Math.nextDown(max)); it passes only because all its values are positive.
The full argument264 words
  • Intent. No record states why Double.MIN_VALUE was chosen (see History), so the original intent is not known; the points below are why the evidence favours a defect.
  • Contract. DoubleRange.java:23 ("Represents a contiguous range of double values, with an inclusive minimum and exclusive maximum"), :27 ("The inclusive minimum value of this range"), :33; DoubleRangeFactory.java:30 ("all doubles below this value are grouped into a single range"), :31-33 ("Ranges are inclusive at the lower end, and exclusive at the upper end."), :43 ("Finds the DoubleRange that a value should be grouped into"). No sign or domain restriction anywhere in the class or the package javadoc.
  • The twin. LongRangeFactory.java:54 uses Long.MIN_VALUE. The two factory tests are identical apart from the type. The Double code and its assertion are already in the 2017 Double-only LUCENE-7889 patch; LongRangeFactory first appears in the 2020 commit.
  • Lucene's own test. BaseGroupSelectorTestCase.java:66-71: "Each group should have a result set equal to that returned by the top-level query, filtered by the group value"; the double filter is DoublePoint.newRangeQuery("double", groupValue.min, Math.nextDown(groupValue.max)) (TestDoubleRangeGroupSelector.java:57), already in the feature's commit. Its values are nextDouble() * 1000 (:37-38), so the below-min group (min 100) holds only positive values.
  • Lucene's open-end convention is infinity. Core document/DoubleRange.java:33-34 ("open ended ranges can be defined using Double.NEGATIVE_INFINITY and Double.POSITIVE_INFINITY"); DoublePoint.java:207-208 (half-open range queries via lowerValue = Double.NEGATIVE_INFINITY).
  • History. No discussion chose the value: PR apache/lucene-solr#1484 has no comments, and the 6 comments on #8940 do not mention it. Reading Double.MIN_VALUE as "most negative" is a known Java pitfall (the same mistake was caught in review in elastic/elasticsearch#42035).
The devil's-advocate check157 words

Strongest case (the cross-model reviews rated it moderate): TestDoubleRangeFactory.java:29 pins new DoubleRange(Double.MIN_VALUE, 10); the selector uses the range only as an equality key, so nothing inside Lucene misbehaves; the above-max label [max, Double.MAX_VALUE) is also imprecise, so both open ends could be read as sentinels; and no javadoc spells out the below-min label.

Why it fails: the pinned test uses min = 10 and the value 4, the one shape where the label happens to contain the value, so it pins the implementation, not a stated contract; the javadoc defines min as an inclusive bound; the feature's own selector test treats bounds as membership; a sentinel reading is served just as well by NEGATIVE_INFINITY, which also contains every member; and the above-max gap is limited to Double.MAX_VALUE and +Infinity, while this one drops every value <= 0. The independent reproduction, the intended-behaviour check and the adjudication reject it. A fix must update that assertion.

Suggested fix

#

Recommended Double.NEGATIVE_INFINITY as the lower end

Use Double.NEGATIVE_INFINITY as the below-min bucket's lower end (DoubleRangeFactory.java:54, and the never-returned initializer on :50), and update the one assertion that pins the old label (TestDoubleRangeFactory.java:29). The repro and the grouping module's tests pass.

Trade-offs

  • It changes a returned value: code that stored, displayed or compared the old label sees -Infinity instead of 4.9E-324; say so in CHANGES.
  • The label is also the group's identity (SearchGroup.java:195-207, DoubleRangeGroupSelector.java:75, :89-97). By reading, shards on different Lucene versions during an upgrade would treat the old and the new below-min label as two groups (not executed).
  • No algorithmic or allocation change is expected (two constants are replaced); no benchmark was run.

Downstream note

#

Applications built on Lucene that show range-group bounds, or build drill-down links from them, get a wrong lower bound for the below-min bucket (an inverted, empty range when min <= 0) and drill-downs that return fewer of its documents.

How it was found

#

Code reading during a sweep that compared each range group's reported [min, max) with the documents it holds; a public-API probe put -20 into DoubleRange(4.9E-324, -10.0), and a JUnit followed. A later SMT query plus a bounded-exhaustive check of the real class found the same bug independently.

Summary
You group documents by a double field with new DoubleRangeFactory(-10, 5, 10), meaning buckets 5 wide from -10 to 10 and every value below -10 in one bucket, and expect the bucket returned for -20 to be a [min, max) range that contains -20, the way LongRangeFactory returns [Long.MIN_VALUE, -10). Instead DoubleRangeFactory returns DoubleRange(4.9E-324, -10.0): it uses Double.MIN_VALUE as the lower end, and Double.MIN_VALUE is the smallest positive double, not the most negative one, so the range is inverted and holds none of its members (with min > 0 it leaves out 0.0 and every negative member). Each group still holds the right documents, but its reported bounds are wrong, and a range query built from them, the way Lucene's own selector tests rebuild a group, finds none or only some of the group's documents.
