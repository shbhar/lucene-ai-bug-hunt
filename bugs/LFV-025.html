FixedBitSet and LongBitSet equals depend on the backing array capacity, not only on the bits

Two FixedBitSets with the same length and bits are not equals when one was built over a larger long[], which the constructor allows: equals ends in Arrays.equals(bits, other.bits), which also compares array lengths, while hashCode ignores the extra words. LongBitSet is the same; no Lucene caller found compares such sets.

The finding in 30 seconds

#

A 64-bit set needs one 64-bit word. Back it with one word or with two, and equals gives different answers.

Background: how a FixedBitSet stores its bits

#
  1. A FixedBitSet of n bits keeps them in a long[], 64 bits per word. It needs numWords = n / 64 rounded up: 64 bits need 1 word, 100 bits need 2.
  2. new FixedBitSet(n) allocates exactly numWords words. new FixedBitSet(long[] storedBits, n) uses your array as it is; it may be longer, and the words past numWords must be 0. LongBitSet works the same way.

The finding, step by step

#
  1. Build two empty 64-bit sets: new FixedBitSet(64), backed by exactly one word (long[1]), and new FixedBitSet(new long[2], 64), backed by two. The constructor's javadoc says the array "may be larger" as long as the extra bits are clear; here they are all 0.
  2. Both have length() 64, cardinality() 0 and the same hashCode(), 0x98761234. You expect equals to return true.
  3. It returns false, with assertions on and off. equals checks numBits, then calls Arrays.equals(bits, other.bits), which first compares the array lengths: 1 vs 2. hashCode, cardinality, iteration and the bulk operations read only the words in use.
  4. So a HashSet holding one set misses a lookup with the other, and a clone of an oversized set is unequal to an exact-size copy. LongBitSet.equals, documented as "returns true if both sets have the same bits set", fails the same way.

Who is affected

#

Only code that compares or hashes FixedBitSet/LongBitSet instances where one was built over a larger array (a reused scratch long[], or a clone of such a set). The only non-test bit-set equals call found, in RunAutomaton, uses exact-size sets, so no index or search result is known to change. False negatives only, at any size.

Mechanism, terms and numbers441 words

FixedBitSet(long[] storedBits, int numBits) and LongBitSet(long[] storedBits, long numBits) accept a backing array that is larger than needed, as long as the extra words are clear. Each set remembers numWords, the number of words it actually uses, and hashCode, cardinality, iteration and the bulk operations all stop there. equals does not: after checking numBits it calls Arrays.equals(bits, other.bits), which also compares the two array lengths. So two sets with the same length and the same bits, one over long[1] and one over long[2], have equal hash codes but are not equal; a hash lookup with one misses the other, and a clone of an oversized set is unequal to an exact-size copy. It has been so since 4.0.0. The only non-test call of a bit-set equals found (RunAutomaton) uses exact-size sets, so no index or search result is known to be affected; the fix is one line per class: compare only the first numWords words.

The code (main 645d4fe14a20)

#
  • FixedBitSet.java:146-150: FixedBitSet(int numBits) allocates exactly bits2words(numBits) words, so numWords == bits.length.
  • FixedBitSet.java:152-170: FixedBitSet(long[] storedBits, int numBits) sets numWords = bits2words(numBits), rejects only an array that is too small, and keeps the array as it is, so bits.length may exceed numWords. Its javadoc: "The storedBits array must be large enough to accommodate the numBits specified, but may be larger. In that case the 'extra' or 'ghost' bits must be clear". With assertions on it checks that (verifyGhostBitsClear, :183-193).
  • FixedBitSet.java:833-846, equals: returns false if numBits differ, else return Arrays.equals(bits, other.bits); (:845). java.util.Arrays.equals(long[], long[]) is false whenever the two lengths differ.
  • FixedBitSet.java:848-859, hashCode: for (int i = numWords; --i >= 0; ). Equal numBits means equal numWords, so two sets with the same bits hash the same whatever their capacity. cardinality, nextSetBit, or/and/andNot and the static count helpers also use numWords.
  • FixedBitSet.java:826-830, clone(): copies into new long[this.bits.length], so a clone keeps the extra capacity.
  • LongBitSet.java:85-103, :427-441 (line 440 is the same Arrays.equals), :443-454, :420-424: identical.
  • Not a trigger: ensureCapacity (FixedBitSet.java:81, LongBitSet.java:55) builds the new set with numBits = arr.length << 6, so its array is exact.

The numbers

#

new FixedBitSet(64) and new FixedBitSet(new long[2], 64): length 64/64, cardinality 0/0, hashCode -1737092556/-1737092556 (0x98761234), equals false/false (both directions). The study's variant with bits {0, 7, 63, 64, 99} in 100-bit sets over long[2] vs long[5]: cardinality 5/5, hashCode equal, equals false; HashSet.contains with the roomy set returns false; the same for LongBitSet.

Exposure and likelihood262 words
  • Who is hit. Code that calls equals on, or hashes, these sets when at least one was built with the two-argument constructor over a larger array, or is a clone of such a set, and the other was not. It gets "not equal" for equal sets; HashSet/HashMap lookups miss.
  • No affected Lucene code path found. A bytecode scan of the built Lucene jars finds one direct call of a bit-set equals or hashCode in non-test code, RunAutomaton.equals (RunAutomaton.java:200), whose accept set is new FixedBitSet(size) (:69), always exact. Tests also compare bit sets (TestFixedBitSet.java:274-284, TestLongBitSet.java:201-211, TestScorerPerf.java:131, TestBooleanQuery.java:461), all built with the exact-size constructor. The scan cannot see calls through Object.equals, such as a set used as a collection key; a source search found no map or set keyed by a bit set (as Michael McCandless wrote on LUCENE-3531, crediting Uwe Schindler, FixedBitSet's equals/hashCode are "horribly costly" as cache keys), and downstream code was not checked. Lucene does build oversized sets (bkd/DocIdsWriter.java:276-284, over a reused scratch array) but only iterates them.
  • Default vs opt-in. No index, query or codec setting reaches it; only direct use of these public @lucene.internal classes.
  • Scale. None: any size, from 0 bits up; one spare word in the backing array is enough (executed for 0, 1, 63, 64, 65 and 1000 bits, both classes, -ea and -da).
  • Severity. A wrong boolean, and only ever "not equal": it never makes two different sets equal. No crash and no wrong search results were found.

Why it looks unintended

#
  • LongBitSet.equals is documented as "returns true if both sets have the same bits set"; FixedBitSet.equals said the same until a 2015 doc cleanup.
  • Both constructors allow a larger array; hashCode, cardinality, iteration and bulk operations read only the words in use.
  • LUCENE-4693 (#5758) moved these classes to "the actual bound rather than the size of the array" but missed equals.
The full argument300 words
  • The documented contract. LongBitSet.equals: /** returns true if both sets have the same bits set */ (LongBitSet.java:427). FixedBitSet.equals carried the same sentence (4.2.0 FixedBitSet.java:410) until LUCENE-6427 (701b7ddf3a2, 2015) removed it in a "Deleted obsolete doc comments on @Override methods" cleanup of duplicated javadocs.
  • Oversized arrays are a documented input (FixedBitSet.java:152-159, LongBitSet.java:85-92).
  • hashCode, cardinality, iteration and the bulk operations use the logical bound. LUCENE-4693 (#5758, type:bug, 4.2.0, 44f4f8b9492): with an oversized long[] "the FixedBitSet can return wrong results since we use words.length (bits.lenght) as the bounds ... We should use the actual bound rather than the size of the array" (as Simon Willnauer wrote there). That commit moved hashCode, iteration and the bulk operations to the logical word count; equals stayed on the whole array. Its new test filled the unused words with random longs. A few methods do see the whole array: clear() clears it, ramBytesUsed() counts it, getBits() returns it, clone() copies it, and FixedBitSet.scanIsEmpty compares chunks that can reach past numWords (FixedBitSet.java:710-711). They report memory or representation, or read words the contract keeps clear, so with clear extra words none of them changes a result.
  • Tests. TestFixedBitSet.makeFixedBitSet (:329-333) and TestLongBitSet.makeLongBitSet (:276-280) build oversized sets, but the equality tests (TestFixedBitSet.java:269-310) use exact-size sets only.
  • Precedent. The predecessor OpenBitSet.equals had the same javadoc and explicitly ignored trailing zero words (4.2.0 OpenBitSet.java:869-893); LUCENE-2216 fixed, as a bug, "OpenBitSet.hashCode returned different hash codes for sets that only differed by trailing zeros" (CHANGES.txt:18372).
  • What it is not. Java's equals/hashCode contract is not broken: unequal objects may share a hash code. The defect is that equals disagrees with the value semantics LongBitSet.equals documents, for inputs both constructors allow.
The devil's-advocate check156 words

The strongest case, from the cross-model reviewer (rated "moderate"): both classes are @lucene.internal, expose their array (getBits()), show their capacity in ramBytesUsed, clone and clear, and kept the whole-array equals through LUCENE-4693 and LUCENE-6427; FixedBitSet.equals has no javadoc today, and Object.equals does not itself demand value equality. So capacity could be part of the value.

Why it fails: @lucene.internal renders as "This API is for internal purposes only and might change in incompatible ways in the next release" (RenderJavadocPlugin.java:506), a compatibility notice, not a licence for wrong answers; upstream fixed this very defect family in these classes as bugs. LongBitSet.equals states value semantics in writing; FixedBitSet's identical sentence went in a doc cleanup, and neither issue thread discusses equals. hashCode was deliberately moved off the capacity (LUCENE-4693), which points the same way; the methods that do show the capacity report memory or representation, not which bits are set.

Suggested fix

#

Recommended Compare only the first numWords words (validated)

Compare only the words in use, in both classes: return Arrays.equals(bits, 0, numWords, other.bits, 0, other.numWords);. Equal numBits means equal numWords; sets of the same capacity whose extra words are clear, as the constructors require, compare exactly as before. The repro passes, and Lucene's bit-set and automaton tests pass with assertions on and off.

Trade-offs

  • numBits is already checked equal, so both ranges have the same length; the fix uses the JDK's ranged Arrays.equals overload and compares no more words than before (performance not measured).
  • It relies on clear ghost bits, which the constructors already require and hashCode already assumes; the "Depends on the ghost bits being clear!" comment stays true. The constructors check that only with assertions (assert verifyGhostBitsClear()), and getBits() lets a caller break it later.
  • Sets of the same capacity whose extra words are clear compare exactly as before. Only sets whose extra words are not clear, a state the contract forbids, can compare differently: those words are now ignored. Like hashCode, the fix still compares the unused high bits of the last word in use, which must be clear too.

What the checks validated

  • Scratch worktree of 645d4fe14a20, gradle --offline, OpenJDK 25.0.3, seed DEADBEEF. Stock: the repro fails with assertions on and off. With the fix: the repro passes both ways; TestFixedBitSet, TestLongBitSet, TestSparseFixedBitSet, TestBitSetIterator and the whole org.apache.lucene.util.automaton test package (home of RunAutomaton, the only non-test caller found) pass (assertions on and off: 20 suites, 314 tests, 0 failures, 3 nightly/monster tests skipped); the :lucene:core format, ECJ and forbidden-apis checks pass. No stock run of the same 20 suites was recorded; the second adjudication ran TestFixedBitSet + TestLongBitSet stock and fixed.
  • Earlier runs: the shadowed fix makes the minimal test pass with -ea and -da; the tie-break's LongBitSet test passes; TestFixedBitSet + TestLongBitSet 44/44 with the fix over 2 seeds (tie-break) and 45 tests over 5 seeds (study); on 4.0.0 and 4.2.0 an equivalent fix over the words in use (written for those versions' fields) makes the history probe pass.

Document capacity-dependent equality instead

#

Change LongBitSet.equals' javadoc, and add one to FixedBitSet.equals, saying that sets over different-size arrays are never equal.

Trade-offs

Keeps today's behaviour, but leaves equals inconsistent with hashCode, cardinality, iteration and the bulk operations, and with the "may be larger" constructors. Not recommended; not run.

#

Lucene.NET's port has the same Arrays.Equals(bits, other.bits) line in FixedBitSet.Equals (by reading its source, not run).

How it was found

#

Not a formal find. Error Prone's InconsistentHashCode check, which Lucene's build turns off as noisy, flagged FixedBitSet's equals/hashCode pair for a wrong reason; reading the flagged method found the real gap. An independent verifier reproduced it on the real jar.

The method in full105 words

A static-analysis pass over lucene-core (SpotBugs, Error Prone with its default checks plus 40 that Lucene turns off, CodeQL, PMD, Checker Framework) produced thousands of findings; 62 triage rows were read by hand. Error Prone's InconsistentHashCode reported "hashCode includes the fields [numWords], which equals does not". That reason is wrong: numWords follows from numBits, which equals does check. Reading the method showed the real problem, the whole-array Arrays.equals. The check is OFF in Lucene's build (ErrorPronePlugin.java:493, "noisy").

An independent verifier then wrote its own deterministic tests (4 fail, 3 controls pass) and validated the one-line fix against TestFixedBitSet and TestLongBitSet.

History

#

The equals line dates from FixedBitSet's creation (2011), when every array was exact. LUCENE-4069 (2012) added the oversized-array constructor, so 4.0.0 is the first affected release; all 123 release tags from 4.0.0-beta on carry the code, and every release run up to 10.6.0, and main, fails. LUCENE-4693 (2013) fixed the neighbouring methods but not equals.

Versions tested6 rows

Introduced by LUCENE-4069 ("Segment-level Bloom filters", Mark Harwood), committed 2012-08-02 as ad2cefee00a (trunk) and b889626bc4c (branch_4x): it added the public FixedBitSet(long[] storedBits, int numBits) constructor. The faulty line is older: return Arrays.equals(bits, other.bits); came with FixedBitSet itself (LUCENE-3280, a17df303e9d, 2011, 3.4.0). LongBitSet was created with the same equals (LUCENE-5440, b872f4b5c3c, 4.7.0). Missed fixes: LUCENE-4693 (#5758, 4.2.0) moved hashCode, iteration and the bulk operations to the logical word count; LUCENE-6427 (#7486, 5.2.0) documented the oversized input and edited both equals methods (a direct numBits compare, the "Depends on the ghost bits being clear!" comment, FixedBitSet's javadoc dropped) but kept the whole-array Arrays.equals. Neither issue thread mentions equals.
