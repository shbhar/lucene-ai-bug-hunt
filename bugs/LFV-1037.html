String sort fields accept any missing value, silently treat it as STRING_FIRST, and an index sort with one cannot be reopened

Since 10.4, SortedSetSortField, KeywordField.newSortField and SortField(STRING_VAL) accept a missing value such as "zzz", which string sorts do not support. Documents without a value silently sort as with STRING_FIRST, and as an index sort the value is dropped on write, so the next IndexWriter with the same index sort refuses the index.

The finding in 30 seconds

#

A string sort's missing value says where documents without a value go: STRING_FIRST or STRING_LAST. Three entry points added in 10.4 accept any other value, ignore it, and drop it from a stored index sort.

  1. Index three documents with tags "apple", "banana" and none. Sort them by KeywordField.newSortField("tag", false, MIN, "zzz"), the way you would give a numeric sort a substitute value.
  2. You expect an IllegalArgumentException. String sorts support only STRING_FIRST and STRING_LAST: new SortField("tag", Type.STRING, false, "zzz") throws, and so did the setMissingValue these constructors replaced.
  3. Instead the value is accepted and ignored. toString() shows missingValue=zzz, but the order is (none), apple, banana, as with STRING_FIRST; STRING_LAST gives apple, banana, (none).
  4. Make it the index sort (the probe indexes "apple" and the document without a tag). The first IndexWriter writes the segment with its sort stored as <sortedset: "tag"> selector=MIN, without the value. The next IndexWriter, given a fresh IndexWriterConfig with the same sort, throws cannot change previous indexSort. In the probe nothing was lost: with the value removed from the sort, the index opens.

Who is affected

#

Code that passes a custom string or BytesRef as the missing value of a STRING_VAL sort, a SortedSetSortField or KeywordField.newSortField, on 10.4.0 to 10.6.0 or main, with the default codec and config. Search silently sorts missing documents first; as an index sort, the next writer refuses the index. Rare: documented usage passes the two markers.

Mechanism, terms and numbers504 words

For string sorts Lucene supports two missing values, SortField.STRING_FIRST and SortField.STRING_LAST. #15483 (10.4.0) replaced the validating setMissingValue with constructor parameters and kept the check only for Type.STRING. Since then new SortField(f, Type.STRING_VAL, reverse, x), new SortedSetSortField(f, reverse, selector, x) and KeywordField.newSortField(f, reverse, selector, x) store any x. The comparators and the index sorter of these fields only ask missingValue == STRING_LAST, so x acts as STRING_FIRST, while getMissingValue() and toString() report x.

As an index sort, SortedSetSortField.serialize writes "no missing value" for anything but the two sentinels. SortField.equals compares the missing value, so the next IndexWriter, opened with a fresh config holding the same sort, refuses the index with IllegalArgumentException: cannot change previous indexSort. In the probe no documents were lost, and removing the value from the sort opens the index again. Releases up to 10.3.2 are not affected, and on 10.4 to 10.6 the deprecated setter still rejects the value; on main (11.0) the constructors are the only path.

Terms

#
  • Missing value: the fourth argument of new SortField(field, type, reverse, missingValue), new SortedSetSortField(field, reverse, selector, missingValue) and KeywordField.newSortField(field, reverse, selector, missingValue). It decides where documents without a value in the field sort. Numeric sorts take a substitute number; string sorts take one of two markers, SortField.STRING_FIRST or SortField.STRING_LAST (SortField.java:309-324). null means the default, which sorts like STRING_FIRST.
  • STRING_VAL: a SortField type that compares the BytesRef values of a binary doc-values field. SortedSetSortField sorts a sorted-set field, which is what KeywordField.newSortField returns.
  • Index sort: IndexWriterConfig.setIndexSort(sort) makes every segment store its documents in that order. Each segment records the sort it was written with, and a new IndexWriter checks that its config's sort matches every existing segment's.

What goes wrong

#
  1. SortField.validateField rejects a non-marker value only if (type == Type.STRING) (SortField.java:343-348). The SortedSetSortField constructor passes Type.CUSTOM to super and checks nothing itself (SortedSetSortField.java:74-81); KeywordField.newSortField passes the value on (KeywordField.java:188-193).
  2. The comparators read only missingValue == STRING_LAST (SortField.java:521-523, SortedSetSortField.java:175-176), and so does the index sorter, both when a new segment is sorted at flush (IndexSorter.java:512-519) and at merge (:488-493): any other value sorts like STRING_FIRST.
  3. SortedSetSortField.serialize writes 1 for STRING_FIRST, 2 for STRING_LAST and 0 otherwise (SortedSetSortField.java:124-135), so the stored sort has no missing value.
  4. SortField.equals compares the missing value (SortField.java:451-461), so IndexWriter.validateIndexSort finds the config's sort unequal to the stored one and throws (IndexWriter.java:1213-1239). Each writer needs its own IndexWriterConfig with the same sort; reusing the first writer's config fails earlier, with IllegalStateException: do not share IndexWriterConfig instances across IndexWriters (IndexWriter.java:935-947). Within the first writer session nothing fails: two commits and a forceMerge(1) succeed.

The same comparison runs in addIndexes(Directory...) and addIndexes(CodecReader...) (IndexWriter.java:3152-3158, :3228-3250): adding an index written with the "zzz" sort to a writer with that sort is refused with cannot change index sort through both (run by the fact check).

Exposure and likelihood212 words
  • Who is hit. Callers that expect a substitute value, as the numeric factories document one: IntField.newSortField's missingValue is "a sort value to use for documents with no value in the field" (IntField.java:184). A downstream project's sort DSL lets users pass exactly such a value for string fields, and its tracker (HSEARCH-3254, 2018) notes that it relied on Lucene to throw.
  • Default or opt-in. The default codec, IndexWriterConfig and searcher; any index size; assertions on or off. The trigger is the caller's own argument.
  • Effect. At search time the argument is silently ignored. As an index sort, the first writer session succeeds and writes segments; only the next IndexWriter, with a fresh config holding the same sort, throws cannot change previous indexSort. In the executed probes no documents were lost, CheckIndex was clean, and with the value removed from the sort the index opens.
  • Releases. 10.4.0 to 10.6.0 (the latest release, published 2026-10-29) and main. On 10.4 to 10.6 only callers that moved from the deprecated setter to the constructors are hit; on main the constructors are the only way to set a missing value.
  • How likely. Rare: the documented markers, every upstream test and the downstream migrations that were read (Elasticsearch, Solr) pass STRING_FIRST/STRING_LAST.

Why it looks unintended

#
  • The same check exists one if away: Type.STRING rejects "zzz", added by the same PR with a test (TestSort#testStringMissingValues).
  • The removed setMissingValue rejected it for STRING, STRING_VAL and SortedSetSortField, and BinarySortField and ToParentBlockJoinSortField reject it today.
  • IndexWriter accepts the config, writes segments with it, then refuses that index under a fresh config with the same sort.
The full argument227 words
  • The contract names two values. STRING_FIRST/STRING_LAST: "Pass this as a missingValue constructor parameter to have missing string values sort first" / "last" (SortField.java:309-324). SortedSetSortField: "Like sorting by string, this also supports sorting missing values as first or last, via SortField#STRING_FIRST or SortField#STRING_LAST" (SortedSetSortField.java:41-42).
  • Same check, one type over. #15483 added the rejection for Type.STRING to validateField with TestSort#testStringMissingValues, which asserts "For Type.STRING, missing value must be either STRING_FIRST or STRING_LAST" (TestSort.java:94-104).
  • The replaced API. 10.5.2 SortField.setMissingValue threw "For STRING type, missing value must be either STRING_FIRST or STRING_LAST" when type == Type.STRING || type == Type.STRING_VAL; SortedSetSortField.setMissingValue ("Note that this must be STRING_FIRST or STRING_LAST") threw "For SORTED_SET type, ...". The checks date from 2014; executed on 10.4.0, 10.5.2 and 10.6.0 RC1, the setter still rejects "zzz".
  • Siblings. BinarySortField: "@param missingValue STRING_FIRST, STRING_LAST, or null" plus a constructor check (BinarySortField.java:72-73, :95-98); ToParentBlockJoinSortField rejects too (ToParentBlockJoinSortField.java:178-198), added after a different #15483 side effect (#15548 / #15727).
  • Migration text. "SortField.setMissingValue() has been removed. Missing values should be configured in SortField constructor methods, as they are now final", with a SortedSetSortField example passing SortField.STRING_LAST (MIGRATE.md:258-278). The captured PR metadata and review summaries, the #15483 CHANGES entry and MIGRATE.md announce no widening of the accepted values; #15483's goal was immutability.
The devil's-advocate check147 words

The strongest case (the cross-model lenses, the independent reproduction, the intended-behaviour check and the adjudication): the new constructors and KeywordField.newSortField document no @param or @throws for missingValue, so a non-marker value is unsupported input that Lucene never promised to reject; and 10.4 to 10.6 accept it, so a check changes behaviour.

Why it fails: the missing @param is a real gap (fix A adds it), but the only documentation of the parameter names the two markers; the same code, the removed setters and two siblings reject the same input; nothing in the captured PR history suggests the check was dropped on purpose; and "unsupported input" does not explain an IndexWriter that accepts a config once and then refuses the index it produced. The compatibility point bears on where a fix lands (main / 11.x looks lower-risk; the maintainers decide), not on whether the behaviour is intended.

Suggested fix

#

Recommended Reject non-marker values in both constructors

Reject anything but null, STRING_FIRST and STRING_LAST in SortField.validateField for STRING_VAL too, and in the SortedSetSortField constructor (which KeywordField.newSortField calls), and document missingValue (3 files, +13/-2). The test passes with it, and so do 13 sort and index-sorting suites (193 tests), with assertions on and off.

// SortField.validateField
if (type == Type.STRING || type == Type.STRING_VAL) {
  if (missingValue != null && missingValue != STRING_FIRST && missingValue != STRING_LAST) {
    throw new IllegalArgumentException(
        "For Type." + type + ", missing value must be either STRING_FIRST or STRING_LAST");
  }
}
// SortedSetSortField(String, boolean, SortedSetSelector.Type, Object), after super(...)
if (missingValue != null && missingValue != STRING_FIRST && missingValue != STRING_LAST) {
  throw new IllegalArgumentException(
      "For SortedSetSortField, missing value must be either STRING_FIRST or STRING_LAST");
}

Reject non-marker values in both constructors (validated by the checks) (recommended)

#

The finder's two checks plus the missing @param missingValue javadoc on the three entry points. The Type.STRING message is unchanged, so TestSort#testStringMissingValues still passes.

// SortField.validateField
if (type == Type.STRING || type == Type.STRING_VAL) {
  if (missingValue != null && missingValue != STRING_FIRST && missingValue != STRING_LAST) {
    throw new IllegalArgumentException(
        "For Type." + type + ", missing value must be either STRING_FIRST or STRING_LAST");
  }

// SortedSetSortField(String, boolean, SortedSetSelector.Type, Object), after super(...)

Trade-offs

  • Restores the pre-10.4 behaviour and matches Type.STRING, BinarySortField and ToParentBlockJoinSortField.
  • Code on 10.4 to 10.6 that passes such a value gets an IllegalArgumentException after upgrading, so main / 11.x looks like the lower-risk target; where it lands and any 10.6.x backport are the maintainers' decision.
  • An index already written with such a value has missing-first segments that store no missing value. To keep opening it, the application must rebuild the sort with null as the missing value (run). Keeping the old value, or swapping in STRING_FIRST, is refused: STRING_FIRST sorts the same but is not equal to the stored sort (run by the fact check).

Downstream note

#

Products that map a user's "missing values" sort option onto these fields should pass only STRING_FIRST, STRING_LAST or null; any other string is silently ignored.

How it was found

#

A probe that compares old and new APIs after a migration showed new SortField("s", STRING_VAL, false, "zzz") accepted on main while the 10.6.0 RC1 setter rejects "zzz". A differential check over the string sort fields (5 constructors, 7 missing values, both directions) then found the SortedSetSortField leg and the reopen failure.

The method in full157 words
  • First signal (not formal). A planner's migration probe (2026-10-29) compared setMissingValue, deprecated on 10.x and removed on main, with the constructors that replace it.
  • Differential check. The finder (a hunt unit) ran 70 cells: SortField(STRING), SortField(STRING_VAL), SortedSetSortField, BinarySortField and ToParentBlockJoinSortField, each with null, STRING_FIRST, STRING_LAST, "zzz", "", a BytesRef and an Integer, forward and reversed. Each cell checked acceptance and the position of the document without a value and, where the field can be an index sort, the stored index sort and a reopen with the same sort. KeywordField.newSortField was not a separate row; it calls the SortedSetSortField constructor (KeywordField.java:188-193), and the steps probe uses it. A second differential compared the setter with the constructor on 10.4.0, 10.5.2, 10.6.0 RC1 and main.
  • Reduction. The no-noise gate reduced it to one JUnit class with two methods, each with one expectThrows, one per fix site.

Applications that pass a missing value other than null, SortField.STRING_FIRST or SortField.STRING_LAST (for example a String such as "zzz" or a BytesRef) to new SortField(f, Type.STRING_VAL, reverse, x), new SortedSetSortField(f, reverse, selector, x) or KeywordField.newSortField(f, reverse, selector, x), with the default codec, IndexWriterConfig and searcher, -ea or -da, at any index size, on 10.4.0 through main: at search time the value is silently treated as STRING_FIRST, and when the SortedSetSortField/KeywordField sort is the index sort, the next IndexWriter opened with the identical config throws IllegalArgumentException 'cannot change previous indexSort'; nothing is lost, and the index opens again once the bogus value is removed from the config.
Summary
You build a string sort with a missing value that is not STRING_FIRST or STRING_LAST, for example new SortedSetSortField("tag", false, SortedSetSelector.Type.MIN, "zzz") or the same through KeywordField.newSortField, much as you would give a numeric sort field a substitute value. You expect an IllegalArgumentException when the sort field is built, as new SortField(f, Type.STRING, false, "zzz") throws and as the removed setMissingValue threw for these sorts too. Instead the value is accepted (getMissingValue() and toString() report it) but every comparator treats it as STRING_FIRST, so documents without a value silently sort first; and if the sort is the index sort, the segment is written without the value, so the next new IndexWriter with the very same config refuses the index with 'cannot change previous indexSort'.
