Monitor.register with the same query id twice in one call keeps both versions of the query

Registering two versions of one query id in a single Monitor.register call keeps both. With q = apple OR banana then q = cherry, q matches banana and cherry, which neither version does, and after a restart a persistent Monitor runs the old version while getQuery shows the new one.

The bug in 30 seconds

#

The Monitor (lucene/monitor) reports which stored queries a document matches. It splits each query into branches, one per OR clause, indexes one entry per branch and caches each branch as q_0, q_1, ... An update of q deletes q's entries and adds the new ones. With two versions in one call, the delete runs once and both versions are added.

  1. A Monitor stores queries under ids, and registering an id again replaces its query. You apply a batch of edits in one call, a query created and then edited: register(mq("q", "apple OR banana"), mq("q", "cherry")).
  2. You expect q to behave like its newer version, as two separate calls do: q matches only the document "cherry", and getDisjunctCount() is 1.
  3. Instead the Monitor deletes q once, then adds both versions: its query index keeps apple (q_0) and banana (q_1) from version 1 and cherry (q_0) from version 2. The cache has one slot per name, so cherry overwrites apple in q_0 and banana stays in q_1.
  4. So q matches {banana, cherry}, a set neither version matches, and getDisjunctCount() is 3. No error, with assertions on or off.
  5. A persistent index gives three answers for the same call: live {banana, cherry}; after a reopen {apple, banana}, the old version; a read-only Monitor {apple, banana, cherry}; getQuery("q") says cherry. It lasts until q is registered again on its own or deleted.

Who is affected

#

Users of the optional monitor module who put two versions of one id in one register call, within 5,001 entries: a batch of edits, or ConcurrentQueryLoader draining a create and an edit. Default in-memory settings; two entries suffice. Wrong live matches need the old version to have an extra branch or another filter value; otherwise they appear after a restart.

Mechanism, terms and numbers661 words

Registering a MonitorQuery whose id is already registered replaces the old query. When one Monitor.register call contains two versions of the same id, for example a query created and then edited in one batch, WritableQueryIndex.commitWithoutNotify deletes the id once and then adds every branch of both versions. Both stay in the query index, while the in-memory cache keeps one entry per cache id id_N, so the query runs a mix of the two versions. With q = apple OR banana then q = cherry, q matches {banana, cherry}, which neither version matches, and getDisjunctCount() is 3. On a persistent index the live Monitor, the reopened Monitor ({apple, banana}, the old version) and a read-only Monitor ({apple, banana, cherry}) disagree, and getQuery returns cherry. It is silent, needs only new Monitor(analyzer) with its default configuration for the in-memory case (the persistent views add an index path and a serializer), is reached through Lucene's own ConcurrentQueryLoader, lasts until the id is registered again on its own or deleted, and is in every release that ships the monitor module, 8.2.0 to 10.5.2, and on main.

Terms

#
  • Monitor (lucene/monitor): stores queries under ids and reports which stored queries a document matches. It is backed by its own small Lucene index, the query index.
  • Branches (disjuncts): QueryDecomposer splits a query into branches, one per clause of a disjunction. Each branch becomes one query-index document and one cache entry named id + "_" + ordinal (QueryCacheEntry.java:51-60): apple OR banana gives q_0 = apple and q_1 = banana. getDisjunctCount() counts these documents (Monitor.java:257-262).
  • Matching: the document's terms select candidate query-index documents (the presearcher); for each candidate the Monitor looks its cache name up in the in-memory cache and runs that branch (WritableQueryIndex.java:380-386).

The bug

#
  1. Monitor.register commits its input in chunks of up to queryUpdateBufferSize + 1 = 5001 entries (Monitor.java:152-162, MonitorConfiguration.java:35).
  2. For one chunk, WritableQueryIndex.commitWithoutNotify collects the distinct ids, deletes each once, then adds every branch of every update and puts it in the cache by its cache name (WritableQueryIndex.java:113-125).
  3. With two versions of q, the index keeps all 3 branch documents. Version 2's q_0 (cherry) overwrites version 1's q_0 (apple) in the cache; version 1's q_1 (banana) stays.
  4. Live: "apple" selects version 1's q_0 document, whose slot now runs cherry: no match; "banana" runs q_1 = banana; "cherry" runs version 2's q_0. Result {banana, cherry}; 3 disjuncts.
  5. Reopen: populateQueryCache rebuilds the cache from the first stored document of each id and skips the rest, as "a branch of a query that has already been reconstructed" (WritableQueryIndex.java:152-172). The first document the scan visits is version 1's doc 0 (in this fresh index, the order the documents were added; the code promises no "first update" rule), so every candidate runs version 1: {apple, banana}.
  6. Read-only Monitor: each candidate document's own stored query is deserialized (ReadonlyQueryIndex.java:185-196), so both versions run: {apple, banana, cherry}.
  7. getQuery keeps the stored query of the last document collected (QueryIndex.java:62-72), here version 2's doc 2: cherry.

Main with -ea and -da, and 10.5.2; before 10.3.0 the recorded runs (8.2.0 to 10.2.2, JDK 25) give {apple, cherry} live: the branch order came from a HashSet and was not specified until #14885 (10.3.0) made it stable, so the surviving stale branch may differ on another JVM there.

Exposure and likelihood400 words
  • Trigger: two versions of one query id in the same register call and the same internal chunk of 5001 entries (default queryUpdateBufferSize 5000). Natural sources: an update stream or change log applied in batches (each register call commits and refreshes, WritableQueryIndex.java:127-128, so batching is the cheap way), or ConcurrentQueryLoader, whose worker passes everything it drained to one register call (ConcurrentQueryLoader.java:134-143): a one-thread loader fed a create and an edit reached the mixed state in 20 of 20 and 30 of 30 runs in independent checks (with several workers, both versions must be drained by the same worker into one call).
  • Hidden boundary: the same id 5001 entries apart is handled correctly (executed: q, 5000 other ids, q, so 5002 entries; 5001 queries, 5001 disjuncts), so whether a repeated id breaks depends on a chunk boundary the caller cannot see.
  • Default vs opt-in: the in-memory case uses new Monitor(analyzer), so the default MonitorConfiguration and TermFilteredPresearcher, assertions on or off. The persistent views need an index path and a MonitorQuerySerializer, the read-only view a read-only directory provider, and the metadata case a TermFilteredPresearcher built with a filter field (the default one has none, TermFilteredPresearcher.java:77-79). The monitor module itself is optional and less used.
  • Scale: none; two entries suffice.
  • Damage: silent wrong matches when the old version has a branch the new one lacks (a shrinking edit keeps matching what it removed) or a different filter-field value (the old value keeps selecting the query). When both versions have the same branches and metadata, the live Monitor happens to be right, and the damage shows as an inflated getDisjunctCount(), the old version running after a restart of a persistent Monitor, and both versions running in a read-only Monitor. getQuery names a version the reopened Monitor does not run.
  • Bounds: separate calls are correct; deleteById removes every stale entry; a later single register repairs the id; purgeCache() does not; other ids in the batch are unaffected; repeating the batch does not add entries. No structural index corruption (the index stays readable; it holds stale query documents), hang or effect on IndexSearcher results was observed.
  • How likely: rare (a judgement): it needs edits with repeated ids batched into one call; the two public downstream users found register one query per call (read only), and nobody has reported it since 8.2.0.

Why it is a bug, not intended

#
  • Monitor holds "a set of Query objects with associated IDs", and re-registering an id replaces its query (TestMonitor#testUpdatesOverwriteOldQueries).
  • Nothing says ids must be unique within one call, and Lucene's own ConcurrentQueryLoader passes its queue to one register call.
  • The result is no version at all ({banana, cherry}), and one persistent index gives three answers, whichever entry should win.
The full argument374 words
  • Contracts. Monitor class javadoc: "A Monitor contains a set of Query objects with associated IDs" (Monitor.java:38-41); getQuery: "@return the MonitorQuery stored for this id, or null if not found" (Monitor.java:245-255); register: "Add new queries to the monitor" (Monitor.java:147-151, :168-173). No uniqueness precondition in register, MonitorQuery (MonitorQuery.java:34-49), the package doc, CHANGES or MIGRATE.
  • The chunk size is a buffer setting: setQueryUpdateBufferSize sets "how many queries will be buffered in memory before being committed to the queryindex" (MonitorConfiguration.java:150-160), yet it decides whether a repeated id breaks.
  • Tests. TestMonitor#testUpdatesOverwriteOldQueries (TestMonitor.java:71-86) registers query1 as "this", then as "that" in a second call, and asserts that it matches a "that" document with one query run (it does not by itself show the old entry is gone, since "that" would not select it anyway); TestMonitorPersistence#testCacheIsRepopulated (TestMonitorPersistence.java:54-87) asserts that a reopened Monitor reports the same number of matches (4) and the same query count. No upstream test registers one id twice in one call.
  • The code assumes it. The commit deletes the batch's ids before adding, so a commit is meant to replace each id's earlier documents (this supports the defect, not last-wins in particular); populateQueryCache assumes all documents of an id are branches of one query.
  • History. The loop came with the module (LUCENE-8766, 2019) and moved unchanged in LUCENE-10422 (#679); neither discussion mentions repeated ids. Design context only, not a warning about this bug: in luwak#21 (2014) the author of the predecessor project Luwak explained why it keyed its query cache by the query string, not the id: "Just keying on the ID could result in weird results if a MonitorQuery is updated while a search is in progress - the presearcher could select a query based on it's current index, but then end up fetching an entirely different query from the updated QueryCache. Keying by the query string prevents this". That concern is an update racing a search. Luwak's QueryIndex.commit (the follow-up's copy) has the same delete-then-add-all loop with a hash-keyed cache, so by code reading it would also keep both versions' documents; only the slot overwrite comes from the Lucene module's id_ordinal key, used since its first commit.
The devil's-advocate check157 words

The strongest case for "intended or misuse" (built by the devil's-advocate verifier; the GPT-5.6 reviews rated it moderate): register only says "Add new queries", replace-by-id is tested only across calls, so precedence inside one call is unspecified and callers should deduplicate; ConcurrentQueryLoader is documented as a startup loader ("useful to speed up startup times").

Why it fails: the precedence-free failure needs no rule about which entry wins, since {banana, cherry} is neither version and one persistent index gives three answers while getQuery names a fourth state; the commit loop deletes each id's earlier documents before adding; nothing rejects the input or documents a precondition; the library's own loader produces it (30 of 30 runs with one worker); and the outcome depends on an internal chunk boundary. At most it changes the fix (reject or last-wins), not whether today's state is a defect; last-wins is a proposal that matches consecutive calls, not an existing contract. Verdict: a defect.

Suggested fix

#

Recommended Validate every entry, then keep the last update per id

In WritableQueryIndex.buildIndexables, validate every entry, then keep only the last update of each id (+8/-1), so a later entry replaces an earlier one exactly as across calls. The repro, the whole monitor module (185 tests, assertions on and off) and the static checks pass. Rejecting repeated ids instead makes ConcurrentQueryLoader silently drop the batch.

One fix was built and validated in a scratch worktree at ea57360912ed; the reject alternative was run against the module's tests and a probe. Trade-offs

  • Errors that only a dropped earlier entry would raise while it is serialized, decomposed or indexed are no longer raised, and serializer.serialize is not called for it; only the null-query-string check runs on every entry. Not tested.
  • LinkedHashMap keeps each id at its first position, so surviving entries are indexed in first-occurrence order of their ids (read; no public result here depends on it).
  • MonitorUpdateListener.afterUpdate still receives the full list, duplicates included (unchanged).
  • Unchanged by the fix (read): a cache-only slot left by an earlier separate call (for example q_1 after a two-branch q is replaced by a one-branch q) stays cached until the normal purge; no index document refers to it, so matching is correct.
  • An index written by an affected version keeps its extra documents until each affected id is registered again or deleted (a later single register repairs it, executed). Worth a CHANGES note.
  • Not reviewed by a committer.

Reject a repeated id with IllegalArgumentException (validated by the checks)

#

A Set of ids in buildIndexables throws on the second occurrence (option-reject.diff, +5).

Trade-offs

The check sees one chunk only, so behaviour still depends on the 5001-entry boundary; checking the whole call needs every id of the call in memory, and earlier chunks are already committed. ConcurrentQueryLoader's worker catches only IOException and InterruptedException, so the exception ends it and stays in an unread Future; by code reading, with one worker nothing queued after that is registered, and once every worker has died add() blocks forever when the bounded queue (2000 by default) is full (a pre-existing loader weakness this option routes repeated ids into; not executed).

What the checks validated

The 32 upstream monitor test classes pass (181 tests, 0 failures, 1 skipped), so no upstream test relies on duplicates in one call. Probe: a one-call duplicate throws and registers nothing; the same id 5001 entries apart (q, 5000 other ids, q: 5002 entries) is accepted; ConcurrentQueryLoader (1 thread) fed q, q, r: close() returns normally and no id at all is registered.

Document that ids must be unique within one call

#

A javadoc line on both register overloads and on ConcurrentQueryLoader.

Trade-offs

Leaves the silent mixed state, and the chunk-dependent behaviour, for every caller who does not read it. Not recommended.

Downstream note

#

Downstream: a narrowing update fails open. If the later version drops a topic or moves q to another metadata value (tenant a to b), the dropped part keeps matching, live or after a restart, while getQuery shows the narrowed query. Only the application's own batching triggers it; documents cannot. No exploit or such deployment is known.

How it was found

#

Non-formal. While writing a TLA+ model of the Monitor's commit, purge and search protocol, an AI tool noticed in the code that one commit deletes each id once and then adds every update. The model treats one update per commit and did not find it; a public-API JUnit on the stock jars confirmed it.

The method in full153 words

Method: code reading (the hunt's non-formal tier), in a hunt unit (monitor and presearcher, 2026-10-26).

  • The finder was writing a TLA+ model of the WritableQueryIndex commit, purge and search protocol (QueryIndexConc.tla). Its header says cache ids are modelled as query ids and decomposition is not modelled, and it treats one update per commit, so the model does not witness this bug.
  • Reading commitWithoutNotify for the model, the finder saw the delete-each-id-once-then-add-everything loop and wrote a public-API JUnit, which failed on the stock main jars and on 10.5.2 and 9.12.3.
  • Then: a refute review by an independent reviewer from another model family (OpenAI GPT-5.6, reading only); an independent reproducer writing its own test from the claim alone; a GPT-5.6 "works as designed" review whose two side claims were executed; a devil's advocate; an adjudication; a release sweep, a prior-report search and a security screen; and this doc's own test and fix validation.

LFV-332, snapshot of 2026-10-29

Registry title
Monitor.register with the same query id twice in one call keeps both versions in the query index, so the query matches a mix of both versions, and after a reopen a persistent Monitor runs the older version while getQuery returns the newer one
Area
monitor / query index updates (WritableQueryIndex.commitWithoutNotify and populateQueryCache, reached through both Monitor.register overloads and ConcurrentQueryLoader)
Priority
Medium, rank 70: Default-config Monitor keeps both versions of a query id that is registered twice in one call, but this needs batched edits with repeated ids.
Impact class
silent wrong results
Impact note
Applications of the optional lucene/monitor module that pass two versions of one query id to a single Monitor.register call (an update stream applied in batches, or ConcurrentQueryLoader draining a create and an edit together; both entries must fall into the same internal chunk of queryUpdateBufferSize + 1 = 5001 entries by default) get wrong matches with no error, with the default Monitor and MonitorConfiguration and at any scale (two entries suffice): the query keeps matching what only the older version matched when the older version decomposes into more disjuncts than the newer one or the update changes a presearcher filter field, getDisjunctCount is inflated, a persistent Monitor reopened on the index runs the older version while getQuery returns the newer one, and a read-only Monitor on the same index runs both, until the id is registered again in a separate call or deleted.
Summary
You register query id q twice in one call, monitor.register(List.of(new MonitorQuery("q", apple OR banana), new MonitorQuery("q", cherry))), as an application might when it applies a batch of query edits, and expect q to behave like one version, as it does when the two entries are registered in separate calls (the newer replaces the older). Instead the query index keeps both versions: q is reported for documents containing banana or cherry, a set that neither version matches, and getDisjunctCount is 3 for a one-clause query. With a persistent Monitor (q = apple, then q = cherry, in one call) the newer version runs until the Monitor is reopened, and from then on the older version apple runs instead while getQuery("q") still returns cherry.
