FunctionRangeQuery on a string field compares term ordinals as float, so above 2^24 distinct values in a segment it matches values just outside the range

On a string field, FunctionRangeQuery compares term ordinals as float, so in a segment with more than 2^24 (16,777,216) distinct values it silently matches values just outside the range: asking for exactly 016777217 returns 2 hits. Every release since 8.6.0 has it; changing float to int fixes it.

The finding in 30 seconds

#

For a string field, the query turns both bounds into exact int ordinals, then compares each document's ordinal with them as a float. A float is exact only up to 2^24, so above that a value next to a bound rounds onto the bound's float and is matched.

Background: string ranges by ordinal

#
  1. A string doc-values field (SortedDocValuesField, or SortedSetDocValuesField) keeps, per segment, a sorted dictionary of its distinct values. Each value has a number, its ordinal: 0 for the smallest, 1 for the next, and so on.
  2. FunctionRangeQuery(new BytesRefFieldSource("f"), lower, upper, includeLower, includeUpper) (module lucene/queries) matches the documents whose value lies in the range. For a string field it looks both bounds up in the dictionary once, and then compares each document's ordinal with the two bound ordinals.
  3. A Java float has 24 bits of precision. It holds every whole number up to 2^24 = 16,777,216 exactly; above that only every second one (16,777,218, 16,777,220, ...), then every fourth, up to every 128th near 2^31. Other numbers round to the nearest.

The finding, step by step

#
  1. Index 16,777,220 documents, each with its own value 000000000 ... 016777219 in a SortedDocValuesField f, and merge to one segment. Each value's ordinal, its position in the segment's sorted dictionary, equals its number.
  2. Count FunctionRangeQuery(new BytesRefFieldSource("f"), "016777217", "016777217", true, true). The range holds exactly one value, so you expect 1 hit.
  3. You get 2 hits, 016777216 and 016777217, with no error; [016777217 TO *] gives 4 hits instead of 3. Lucene 8.5.2, running the same program, returns 1 and 3.
  4. Why: the bounds become exact ordinals (lower = upper = 16,777,217), but each document's ordinal is compared with them as a float. Above 2^24 a float holds only every second whole number, so 16,777,216 and 16,777,217 both become 16,777,216.0 and the neighbour passes the bound.
  5. Only values right next to a bound slip in (at most 2 per bound below 2^25 ordinals, up to 128 near 2^31), and no in-range hit is lost. SortedSetFieldSource behaves the same.

Who is affected

#

Code that filters with FunctionRangeQuery over BytesRefFieldSource (SORTED) or SortedSetFieldSource (SORTED_SET) on segments where the field has more than 16,777,216 distinct values, such as a unique id in a large merged segment. Default codec and config, every release since 8.6.0. Only values at the range edges are added, silently; rare in practice.

Mechanism, terms and numbers509 words

FunctionRangeQuery over BytesRefFieldSource on a SORTED field, or over SortedSetFieldSource on a SORTED_SET field, does a string range through DocTermsIndexDocValues.getRangeScorer. That method looks the two string bounds up in the segment's sorted dictionary and gets exact int ordinals, then compares each document's ordinal with them as a float (float docVal = ordVal(doc); return docVal >= ll && docVal <= uu;). A float is exact for whole numbers only up to 2^24 = 16,777,216, so in a segment where the field has more than 2^24 distinct values, a value whose ordinal sits next to a bound rounds onto the bound's float and is matched. On a real single segment of 16,777,220 unique values, the range [016777217 TO 016777217] returns 2 hits, 016777216 and 016777217, with no error. Only extra hits occur, at most 2 per bound below 2^25 ordinals and up to 128 near 2^31; no in-range hit is lost. The compare was int up to 8.5.2; LUCENE-9258 changed it to float while adding multi-valued support, so every release from 8.6.0 to 10.6.0 and main are affected. Changing float back to int fixes it.

The mechanism (main e1faeba08bde, lucene/queries/.../function/)

#
  1. Entry points. BytesRefFieldSource ("for string based fields") returns a DocTermsIndexDocValues for any non-BINARY field (valuesource/BytesRefFieldSource.java:118-119). SortedSetFieldSource ("multi-valued string based fields") returns one over a SortedSetSelector view (valuesource/SortedSetFieldSource.java:59-61). FunctionRangeQuery's scorer is functionValues.getRangeScorer(...) (FunctionRangeQuery.java:172).
  2. Exact bounds. DocTermsIndexDocValues.getRangeScorer converts each bound with termsIndex.lookupTerm(...). A lower bound missing from the dictionary becomes its insertion point, a missing upper bound the ordinal just below it, an exclusive bound moves by one, an absent bound is Integer.MIN_VALUE / Integer.MAX_VALUE; the results are final int ll, uu (docvalues/DocTermsIndexDocValues.java:129-150).
  3. The narrowing. matches(int doc): if (!exists(doc)) return false; float docVal = ordVal(doc); return docVal >= ll && docVal <= uu; (:155-157). ordVal is the exact int ordinal (:79-81); assigning it to float rounds it to the nearest float (ties to even), and binary numeric promotion turns ll and uu into floats for the comparisons too.
  4. The arithmetic. In the one-document repro the document has ordinal 16,777,216 and the lower bound 016777217, absent from the dictionary, has insertion point 16,777,217. Both become 16,777,216.0f, so docVal >= ll is true and the document matches although its value sorts before the bound.

The window (Z3 floating-point model, 10 obligations, all as expected)

#
  • Int-to-float rounding is monotone, so an in-range ordinal is never rejected: only extra hits.
  • No wrong match while every ordinal and bound is at most 2^24, so it needs more than 2^24 distinct values of the field in the segment.
  • For a bound in [2^24, 2^25) at most 2 values outside it are admitted; the overall maximum is 128 values per bound, near 2^31. The model covers the lower bound; the upper bound is the mirror case, shown next.
  • An upper bound admits extras too: on 16,777,224 hex ids, {1000000 TO 1000003] (3 values) returns 6 hits, 1000000 below the range and 1000004, 1000005 above it.
Exposure and likelihood222 words
  • Who is hit. Callers of FunctionRangeQuery (the only caller of getRangeScorer in Lucene's main sources; a test also calls it directly) over BytesRefFieldSource on a SORTED field or SortedSetFieldSource on a SORTED_SET field (the only in-tree users of DocTermsIndexDocValues). A string source has no floatVal, so these queries are used where scores are not needed: a filter clause, ConstantScoreQuery, IndexSearcher.count.
  • Default vs opt-in. Default codec and configuration; the API itself is opt-in (lucene/queries; FunctionRangeQuery is @lucene.experimental).
  • Scale. Only segments in which the field has more than 2^24 distinct values. For SORTED that means more than 16.8 million documents in one segment; for SORTED_SET the distinct values can outnumber the documents. Such segments are legal: IndexWriter.MAX_DOCS is Integer.MAX_VALUE - 128, and SortedSetSelector rejects only fields with Integer.MAX_VALUE or more unique values.
  • Size of the error. Only extra hits, only values next to a range edge: at most 2 per bound below 2^25 ordinals, up to 128 near 2^31. No in-range hit is lost.
  • Silent. No exception and no assertion: the counts are wrong with assertions on and off.
  • Likelihood: rare. It needs this experimental API on a string field and a very large segment, and it only moves the range edges; no public report of it was found, although it has shipped since 8.6.0 (2020).

Why it looks unintended

#
  • The method computes exact int ordinal bounds for a string range, then compares them in float; nothing documents approximate string ranges.
  • Up to 8.5.2 the same method compared int ordinals; LUCENE-9258 (8.6.0) switched to float while adding multi-valued support, never mentioning precision.
  • The sibling IntDocValues.getRangeScorer still compares in int; 8.5.2 counts the same data correctly.
The full argument228 words
  • Contract. FunctionRangeQuery "matches docs in which the values in the value source match a configured range" (FunctionRangeQuery.java:32-33); FunctionValues.getRangeScorer "matches documents with values between the specified range" (FunctionValues.java:224-226), and the comment above it names the string case, "doing a binary search on the StringIndex" (:228-230). For a string source the range is lexicographic, and the override computes it exactly (DocTermsIndexDocValues.java:129-150). No javadoc, package doc, CHANGES or MIGRATE entry says string ranges are approximate.
  • Sibling. IntDocValues.getRangeScorer compares in its native type: int val = intVal(doc); return val >= ll && val <= uu; (IntDocValues.java:113-114).
  • Tests. No test exercises more than 2^24 ordinals or asserts float rounding; TestSortedSetFieldSource checks an "a".."z" range over two documents, and TestFunctionRangeQuery covers numeric sources only.
  • History. Up to 8.5.2 the scorer compared int ordinals: int ord = values.ordValue(); return ord >= ll && ord <= uu; at the 7.0.0, 8.0.0 and 8.5.2 tags, and int ord = termsIndex.getOrd(doc); with the same return at 4.0.0, 5.0.0 and 6.0.0. LUCENE-9258 (b1ec1cd9e0c, 2020-03-11, #10298) replaced its private doc-values lookup with exists(doc) / ordVal(doc) so that it works on SortedSetSelector views, and wrote float docVal = ordVal(doc);, the shape of the float default scorer (float docVal = floatVal(doc);). The commit, its CHANGES entry and the #10298 discussion never mention float or precision.
The devil's-advocate check157 words

The strongest "intended" case (built by the intended-behaviour verifier; a cross-model reviewer rated it moderate): function ranges are float-based by default (Float.parseFloat bounds), the score is documented as a float, DocTermsIndexDocValues is @lucene.internal and FunctionRangeQuery @lucene.experimental, ValueSource is named in the open deprecation proposal #16820, the scale is extreme, and the test's stand-in dictionary has more terms than documents although "Ordinals are dense".

Why it fails: this override exists to do a string range by ordinal and computes exact int bounds, and a string source has no float value at all ("Float scoring does not require float matching", the cross-model reviewer). The trigger goes through public, non-deprecated classes; "experimental" allows API changes, not wrong hits. A plain 16.8M-document single segment reproduces it in under a minute, silently. "Dense" describes the numbering, which the wrapper keeps, and the real-index runs need no wrapper. The deprecation proposal bears on priority, not validity. Verdict: not intended, a regression.

Suggested fix

#

Recommended Compare the ordinal as an int (fix A)

Compare the ordinal as an int: in DocTermsIndexDocValues.getRangeScorer's matches(), change float docVal = ordVal(doc); to int docVal = ordVal(doc);, restoring the pre-8.6 compare. The repro then passes, and so do the whole lucene/queries test suite (513 tests, 0 failures) and :lucene:queries:check -x test.

Compare the ordinal as an int (fix A) (validated by the checks) (recommended)

#

One word in DocTermsIndexDocValues.getRangeScorer: the document's ordinal stays an int, so it is compared exactly with the exact int bounds ll and uu. LUCENE-9258's multi-valued support (exists / ordVal) stays as it is.

Trade-offs

None known. Results change only where they were wrong: values just outside a bound, in segments with more than 2^24 distinct values, stop matching. It also drops the int-to-float conversions per document.

Downstream note

#

Downstream, Solr's {!frange} on a string field appears to use the same class (read in Solr's code, not run), and an application that used a string FunctionRangeQuery as an access filter could admit a few documents whose value sits just outside the range edge.

How it was found

#

An AI code-reading pass over under-tested classes flagged the float compare of exact int ordinals. A probe on a real 16,777,220-document single segment then showed wrong counts on main, 10.6.0 and 8.6.0 against a byte-comparison reference, with 8.5.2 correct. A second lens found it independently; a Z3 model bounded the error window.

You run FunctionRangeQuery(new BytesRefFieldSource("f"), "016777217", null, true, true) as a filter on a segment whose SORTED field f has more than 2^24 distinct values, and expect only documents whose value is at least "016777217". The document holding "016777216" matches too, with no error: getRangeScorer turns the string bounds into exact int ordinals but then compares each document's ordinal as a float, and above 2^24 neighbouring ordinals round to the same float. Only values within one float step of a bound are wrongly added; no in-range document is lost.
