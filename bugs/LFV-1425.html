Util.readCeilArc(FST.END_LABEL, ...) returns null on a non-final arc instead of its first outgoing arc

Util.readCeilArc should return the first arc with a label >= the given one, but for FST.END_LABEL (-1) on a non-final arc it returns null: on the FST {a}, -2 and 0 give 'a', -1 gives null. Every release since 4.1.0; Lucene's own code was not shown to pass -1.

The finding in 30 seconds

#

readCeilArc steps a ceil seek by one arc: of the arcs leaving follow, return the first whose label is >= label. For label == FST.END_LABEL it does not search; it only checks whether follow is final.

Background

#
  1. An FST stores keys as paths of arcs. Each arc has a label; for byte keys a real label is 0 to 255.
  2. An arc is final when a key ends at its target. Reading the arcs after a final arc gives first a virtual end arc with label FST.END_LABEL (-1), then the real arcs, so -1 sorts before every real label.
  3. Util.readCeilArc is a public static helper of the expert class Util (@lucene.experimental); Lucene itself uses it in a terms dictionary and in a suggester.

The finding, step by step

#
  1. Build the FST {a} with the default FSTCompiler. Its start arc is not final (the empty string is not a key) and has one outgoing arc, 'a' (label 97).
  2. On that start arc, ask Util.readCeilArc for the first arc >= -2, >= 0 and >= -1 (FST.END_LABEL).
  3. You expect 'a' all three times: the javadoc promises "the first arc greater or equal than the given label", and BytesRefFSTEnum.seekCeil("") on the same FST returns "a".
  4. You get 'a' for -2 and for 0, but null for -1, with assertions on and off. No exception.
  5. Why: the method's first line sends -1 to FST.readEndArc, which only asks "is this arc final?" and returns null when it is not, without looking at the real arcs.

Who is affected

#

Code that passes FST.END_LABEL (-1) to the expert helper Util.readCeilArc at a non-final arc with outgoing arcs: it silently loses the smallest extension of a prefix that is not a key. Lucene's callers pass bytes (FSTTermsReader) or automaton range minimums (FSTUtil: -1 only for a range starting at -1, none shown in Lucene); no downstream caller was found.

Mechanism, terms and numbers537 words

Util.readCeilArc(label, fst, follow, arc, in) is documented to read "the first arc greater or equal than the given label" and to return null only when there is none. Its first statement sends FST.END_LABEL (-1) to FST.readEndArc, an exact lookup that returns the virtual end arc when follow is final and null otherwise, without reading follow's real arcs. For a final follow that is the right ceil, because the end arc sorts before every real arc. For a non-final follow it is wrong: there is no end arc, and the FST compiler builds only labels >= 0, so the first real arc is the ceil. On the FST {a} the call returns null, while labels -2 and 0 return the arc 'a' and BytesRefFSTEnum.seekCeil("") returns "a". The branch dates from 2012 (LUCENE-3846) and is in every release from 4.1.0 to 10.6.0. Lucene's own callers pass bytes or automaton range minimums and were not shown to pass -1, so it hits application code that walks an FST itself (or hands FSTUtil.intersectPrefixPaths an automaton range starting at -1); a one-condition fix (&& follow.isFinal()) passes the repro and the FST tests.

Terms

#
  • Ceil: the smallest element >= a target. For arcs: the first outgoing arc of follow whose label is >= label.
  • End arc: the virtual arc with label END_LABEL (-1) that readFirstTargetArc puts before the real arcs of a final follow ("Insert \"fake\" final first arc", FST.java:693-699).

The bug (main f794ff5a505c)

#
  1. The branch. Util.java:821-823: if (label == FST.END_LABEL) { return FST.readEndArc(follow, arc); }.
  2. An exact lookup. FST.readEndArc (FST.java:986-1001) returns the end arc if follow.isFinal(), else null. It never reads follow's target node.
  3. A ceil only half the time. For a final follow, the end arc is the first arc >= -1, so the answer is right. For a non-final follow there is no end arc, and the first real arc is the ceil (the compiler builds only labels >= 0, asserted at FSTCompiler.java:581 and :1109; a BYTE1 label is read back as an unsigned byte, FST.java:550), but the branch returns null.
  4. Every other label is a real ceil. Below the branch the method reads the first target arc and searches direct-addressing, continuous, binary-search and list nodes (Util.java:824-888); for -2 or 0 that gives the first real arc (executed for all four node encodings).
  5. Origin. The branch is the exact-match END_LABEL block of FST.findTargetArc (FST.java:1013-1029), copied when readCeilArc was written in 2012. "Is there an end arc?" is the right question for a find, not for a ceil.

label >= 0 is checked by assertions only, so with assertions off a BYTE4 FST is not prevented from storing a negative label (read, not run); BYTE1 and BYTE2 labels are read back unsigned (FST.java:546-562). The fix is right either way: the general search returns the first arc >= -1.

The numbers

#

FST {a}, default FSTCompiler, NoOutputs, start arc not final. readCeilArc on the start arc: -2 -> 'a' (97), -1 -> null, 0 -> 'a', 97 -> 'a', 98 -> null; BytesRefFSTEnum.seekCeil("") -> "a". The same with assertions on and off.

Exposure and likelihood213 words
  • Who is hit. Application code that walks an FST itself and passes END_LABEL to readCeilArc, for example a hand-written ceil seek that, like FSTEnum, uses END_LABEL as the label past the end of its target (BytesRefFSTEnum.java:92-98). At a prefix that is not a key it gets null and misses the prefix's first extension.
  • In-tree callers. FSTTermsReader.doSeekCeil passes target bytes & 0xff, 0..255 (FSTTermsReader.java:590-591, :675). FSTUtil.intersectPrefixPaths forwards an automaton transition's minimum unchecked (FSTUtil.java:82, :105), and Automaton.addTransition does not reject a negative one (Automaton.java:154-182): a deterministic automaton with a range starting at -1 would reach the branch through Lucene's own code, and at a non-final arc the range's real arcs would be skipped (read). No review showed Lucene code that builds such an automaton.
  • Downstream. GitHub code search: readCeilArc in Elasticsearch (1 hit, a back-compat copy of Util.java), OpenSearch (0) and Solr (0); GitHub-wide readCeilArc END_LABEL: only copies or translations of Util.java (a later re-run read all 138 results), no caller.
  • Default vs opt-in. Default FST settings, but the trigger is a direct call of the @lucene.experimental helper class Util with a reserved constant.
  • Scale and visibility. One key is enough. Silent: a null return, with assertions on and off.

Why it looks unintended

#
  • The javadoc is a plain ceil with no exception for any label; END_LABEL is public and the method handles it explicitly.
  • The method answers -2 and 0 with the first real arc; only -1 gets null.
  • Lucene's own ceil seek (FSTEnum) puts END_LABEL below every real label and moves to the first real arc.
The full argument218 words
  • The contract. "Reads the first arc greater or equal than the given label into the provided arc in place and returns it iff found, otherwise return null"; @param label the label to ceil on (Util.java:809-818). No label is excluded. END_LABEL is a public constant (FST.java:139) and the method tests for it itself (Util.java:821).
  • Self-consistency. On the FST {a}: -2 -> 'a', -1 -> null, 0 -> 'a' (executed).
  • Lucene's ceil order. FSTEnum.doSeekCeilList treats a real arc as greater than a target label of END_LABEL and moves to it (FSTEnum.java:286-288); BytesRefFSTEnum.seekCeil("") returns "a" on the same FST (executed). readFirstTargetArc also puts the end arc first (FST.java:693-699). FSTEnum is a separate implementation: it shows Lucene's ceil order, not what readCeilArc meant.
  • History and tests. The branch came in with the method in 2012 as a copy of findTargetArc's block, with no comment; none of the sources reviewed gives END_LABEL an exact-match meaning in readCeilArc: upstream TestUtil passes only real labels (TestUtil.java:55-101), lucene/CHANGES.txt has no readCeilArc or readEndArc entry, and neither the commits in the history nor the prior items found say so.
  • Precedent. An earlier readCeilArc gap was fixed: #9825 (LUCENE-8781), where readCeilArc had not been updated for the direct-addressing encoding; fixed in 8.2.0.
The devil's-advocate check251 words

Strongest case for "not a bug": END_LABEL is a reserved sentinel ("If arc has this label then that arc is final/accepted", FST.java:138), and across the FST API passing it as the label means "give me the end arc if follow is final": findTargetArc does exactly that (FST.java:1013-1029), and hunspell's Dictionary.java:310 and the test framework's FSTTester.java:188 use it so. The branch has behaved this way since 2012, no known caller passes it to readCeilArc, and Util is experimental.

Why it still fails: that protocol is written down nowhere, neither for readCeilArc nor in findTargetArc's javadoc. readCeilArc is named and documented as a ceil, and for a final follow its branch already is the ceil (the end arc sorts first); only the non-final case breaks, against the method's own answers for -2 and 0 and against FSTEnum. The cross-model reviews and the intended-behaviour verifier rated this defence moderate, the independent reproducer weak to moderate. A maintainer could reasonably choose to document the sentinel reading instead (fix option b).

Limits of the rebuttal: on a final follow the general search skips the end arc (readFirstRealTargetArc, Util.java:875), so readCeilArc(-2, ...) there returns the first real arc, not the end arc (executed by a separate probe): the method does not treat the end arc as one of follow's arcs in every branch. This does not touch the non-final case: there is no end arc there, and the first real arc is >= -1 under either reading.

Suggested fix

#

Recommended (a) Gate the END_LABEL branch on follow.isFinal() (recommended, validated)

Take the end-arc branch only when follow is final: if (label == FST.END_LABEL && follow.isFinal()) at Util.java:821, so a non-final arc falls through to the existing ceil search. With it the repro passes (assertions on and off), TestUtil (5 of 5) and the whole FST test package pass, and the format check passes.

    if (label == FST.END_LABEL && follow.isFinal()) {
      return FST.readEndArc(follow, arc);
    }
    // a non-final follow has no end arc: fall through to the ceil search over its real arcs

(a) Gate the END_LABEL branch on follow.isFinal() (recommended, validated)

#

The diff: one changed condition and a comment in Util.readCeilArc (+2/-1 lines).

    if (label == FST.END_LABEL && follow.isFinal()) {
      return FST.readEndArc(follow, arc);

Trade-offs

  • A non-final follow falls through to the existing search, which returns the first real arc for any label below it (direct addressing and continuous: targetIndex < 0 returns the first arc; binary search: index 0; list: the first arc >= label; Util.java:824-888); executed for all four encodings, stock and fixed, by a separate probe.
  • The final-follow case is unchanged (executed by the same probe). The one in-tree path that can pass -1, FSTUtil.intersectPrefixPaths with an automaton range starting at -1, would at a non-final arc enumerate the range's real arcs instead of skipping them (read).
  • Open PR #12688 copies the same branch into a PrimitiveLongFST overload of readCeilArc; the same condition would apply there.

(b) Document the current behaviour instead

#

Say in the javadoc that END_LABEL returns only the end arc, and null when follow is not final.

Trade-offs

  • No code change and no risk, but the method stays a ceil for every label except one, and the doc would contradict FSTEnum's order. Nothing to run.

Downstream note

#

Not security-sensitive: the trigger is the application's own call with -1 (directly, or as the start of an automaton range handed to FSTUtil.intersectPrefixPaths), and the effect is a missed arc. No known downstream caller passes END_LABEL to readCeilArc; translations of Util.java to other languages (.NET, Go) carry the same branch.

How it was found

#

A semi-formal proof-obligation audit of Util.readCeilArc's contract: each javadoc promise was checked against each branch, and the END_LABEL branch broke "the first arc greater or equal". A one-test JUnit witnessed it. The finder first set it aside as a sentinel nit and kept it after a cross-model challenge and a check of FSTEnum's ceil order.

The method in full107 words

Method: list what the javadoc promises (a ceil over follow's arcs, null only when none is >= the label) and discharge it branch by branch. The general search meets it for every node encoding; the END_LABEL branch meets it only when follow is final. The witness is the one-test JUnit, run on main with assertions on and off.

The finder first dropped the lead as a sentinel-argument nit. An independent reviewer from another model family (OpenAI GPT-5.6) challenged that negative and judged it wrong, with high confidence, and FSTEnum.doSeekCeilList's handling of END_LABEL confirmed the ceil order the javadoc implies, so it was kept at Low.
