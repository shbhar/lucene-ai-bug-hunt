DatasetSplitter can silently leave a whole labelled class out of its training, test and cross-validation indexes when some documents have no class value

When some documents have no class value, DatasetSplitter.split can silently drop a whole labelled class from its three output indexes: one unlabelled document before 1,000 each of classes a, b and c loses all 1,000 of class c. A segment without the class field throws NullPointerException, leaving the outputs locked.

The bug in 30 seconds

#

DatasetSplitter.split copies an index into training, test and cross-validation indexes, grouping the documents by their class so that the test and cross-validation shares are taken from each class separately. The class field must be indexed with sorted doc values; nothing says every document must have a value.

  1. Index three documents into one segment: d0 with no class value, d1 of class a, d2 of class b. Call new DatasetSplitter(0.1, 0.1).split(reader, train, test, cv, analyzer, false, "cls").
  2. You expect every document in one of the three new indexes, and both classes present.
  3. You get test = [d0], cross-validation = [d1], training empty: d2, and with it all of class b, is in none of them. split returns normally.
  4. Why: split asks the grouping for as many groups as there are class values (2). Documents without a value form a third group, the null group, and groups are taken in index order: null, a. The group that starts last is cut.
  5. Second symptom: a segment with no class field makes split throw NullPointerException before its try, so its three writers stay open and the output directories stay locked.

Who is affected

#

Anyone who splits an index for classifier work with DatasetSplitter while some documents have no class value, a state the module's classifiers handle on purpose. No option needed. On one segment the loss is deterministic once an unlabelled document precedes the first document of the class that starts last; classes repeated across segments, or deleted documents, can hide it.

Mechanism, terms and numbers830 words

DatasetSplitter.split copies an index into three new indexes (training, test, cross-validation) for classifier work. Since LUCENE-7196 (6.1.0) it groups the documents by the class field with GroupingSearch, so that the test and cross-validation shares are taken from each class separately, and it asks for as many groups as there are class values. Documents without a class value form one more group, the null group (the grouping default), which that count never includes. On a single segment that holds an unlabelled document the limit is one group short (unless a class value left only on deleted documents inflates the count), and the group whose first document comes last in index order is left out of all three outputs. With d0 (no class value), d1 (class a) and d2 (class b) in one segment, d2 and all of class b are missing; with one unlabelled document ahead of 1,000 documents each of classes a, b and c, all 1,000 class-c documents are missing. If the unlabelled documents come last, only they are lost. Separately, a segment with no class field at all makes split throw NullPointerException from terms(classFieldName).size() before its try, so the three writers it opened are never closed and the output directories stay locked. Every release from 6.1.0 to 10.5.2 and main is affected (the NullPointerException since 7.0.0); indexes in which every document has a value of the documented single-valued sorted doc-values class field are not. Counting one extra group, null-checking the terms and opening the writers inside the try fixes both; the repro, the whole classification test suite and the module's checks pass with that change.

Terms

#
  • DatasetSplitter (lucene/classification, org.apache.lucene.classification.utils): "Utility class for creating training / test / cross validation indexes from the original index" (DatasetSplitter.java:44-46). split(reader, train, test, cv, analyzer, termVectors, classFieldName, fieldNames...) copies each document into one of the three outputs; the class field "must be indexed with sorted doc values" (:74-75).
  • Grouping. split runs GroupingSearch on the class field over all documents, groups sorted by index order (the position of each group's first document), and copies the documents of the returned groups group by group (:119-164).
  • Null group. By default the grouping puts documents without the group field into one extra group with the value null; setIgnoreDocsWithoutGroupField(true) leaves them out instead (GroupingSearch.java:63, :393-403). split does not call it.

The bug

#
  1. split opens its three IndexWriters first (:92-94).
  2. It counts the classes: per segment, the value count of the class field's sorted doc values; a segment without them also adds terms(classFieldName).size() ("approximate with no. of terms", :96-115). Documents without a value are never counted.
  3. It asks for that many groups: gs.search(indexSearcher, MatchAllDocsQuery.INSTANCE, 0, noOfClasses) (:126). On one segment with at least one unlabelled document (and an exact count, step 6) there are noOfClasses + 1 groups, so the group whose first document comes last is cut, whole, from all three outputs. That group is a labelled class whenever the first unlabelled document comes before it (in [u, a, b, c] class c goes, class a stays); otherwise it is the unlabelled documents.
  4. For a segment where no document has the class field, terms(classFieldName) is null ("or null if it has none", LeafReader.java:134) and :112 throws NullPointerException. That line is before the try (:117), so the finally that closes the writers and the reader (:176-179) never runs.
  5. Several segments: the count adds up per-segment dictionaries, so when classes repeat across segments it exceeds the real number and the null group fits. [d0 unlabelled, d1 = a] + [d2 = b] still loses d2; [d0, a, b] + [a, b] keeps everything.
  6. Deleted documents: the count is the segment's dictionary size, and a class value left only on deleted documents still counts. One segment [d0 unlabelled, d1 = a, d2 = b, d3 = c] with d3 deleted and not merged copies d0, d1 and d2 (count 3); after forceMerge(1) the count is 2 and d2 is lost again.

Exposure and likelihood347 words
  • Who is exposed. Applications that build training, test and cross-validation indexes with DatasetSplitter.split (opt-in lucene/classification module; not marked experimental) from an index where some live documents have no class value. Nothing in Lucene calls it outside tests, and a code search of the Apache organisation found no caller in Solr.
  • Unlabelled documents are a normal input to the module. Its classifiers skip them on purpose (LUCENE-5338), and its own test base indexes "unlabeled doc" and "second unlabeled doc" (ClassificationTestBase.java:227, :333). That is classifier support, not a statement about DatasetSplitter, which documents no contrary restriction.
  • Default call; one segment exposes it. No setting is involved: any ratios, fieldNames null or not. TestDataSplitter, the class's only regular (non-@Monster) test, force-merges to one segment and passes a single leaf (TestDataSplitter.java:78-80); the originalIndex javadoc still reads "an {@link org.apache.lucene.index.LeafReader} on the source index" (DatasetSplitter.java:68); and from 6.1.0 to 6.3.0 split accepted only a LeafReader. How common each layout is was not studied.
  • Silent. split returns normally and the outputs are well-formed indexes that just lack a class: a classifier trained on them never learns it, and its evaluation never tests it.
  • Realistic data (one workload, not a prevalence study). 500 documents, 4 classes with skewed frequencies (rarest 3%), about 2% unlabelled at random positions, force-merged to one segment: 64 of 100 trials lose labelled documents (1,386 in total). The same data left in several segments: 0 of 100.
  • Bounded. At most one group per split, cut whole; no deleted, duplicated or foreign document appears in any output, CheckIndex is clean and the source index is unchanged (3,000 random indexes).
  • Second symptom. A segment with no class field (for example a flush of only unlabelled documents) throws NullPointerException and leaves the three output directories locked; on a file-system directory the lock is held until the JVM exits, and the caller's reader is left open (on success split closes it).
  • How likely. Plausible: a little-used utility, and multi-segment indexes with repeated classes hide it; nobody has reported it since 6.1.0 (2016).

Why it is a bug, not intended

#
  • The class promises "training / test / cross validation indexes from the original index", and LUCENE-7196 added the grouping for "guaranteed class coverage"; losing a whole class is the opposite.
  • No javadoc requires a class value on every document; the module's classifiers handle unlabelled documents on purpose.
  • Which group vanishes depends only on where the first unlabelled document sits.
The full argument347 words
  • The contract. "Utility class for creating training / test / cross validation indexes from the original index" (DatasetSplitter.java:44-46); the class field "must be indexed with sorted doc values" (:74-75), a property of the field, not a rule that every document has a value; the only documented failure is "@throws IOException if any writing operation fails on any of the indexes" (:78). The contract is implied, not literal: no javadoc promises that every document lands in exactly one output.
  • The grouping exists for class coverage. LUCENE-7196 (#8251, "DataSplitter should be providing class centric doc sets in all generated indexes") added it, committed as "guaranteed class coverage in split indexes through grouping by class". Before that, split copied every hit of a MatchAllDocsQuery (6.0.1), so this is a regression of that change.
  • The count was meant to be enough. The code comment says "get the exact no. of existing classes" (:96); LUCENE-7591 (#8642) calls its fallback "an approximate count (upper bound)".
  • A missing class field was handled before. 6.1.0 checked if (terms != null) and otherwise fell back to 10,000 groups; on main, LUCENE-7591 replaced the later IllegalStateException (the LUCENE-7400 version) with the terms fallback but no null check. The module has fixed the same null-Terms pattern elsewhere: LUCENE-7303 (#8357, "Avoid NPE if classField doesn't exist in SNBC") and LUCENE-7950 (#8999).
  • Unlabelled documents are expected. LUCENE-5338 made the classifiers skip them, and the module's test base indexes them (ClassificationTestBase.java:227, :333). TestDataSplitter, the only regular splitter test, labels every document (TestDataSplitter.java:64-80), which is why it never showed (the other caller, the @Monster Test20NewsgroupsClassification, is skipped by default); no javadoc, CHANGES or MIGRATE entry mentions documents without a class value.
  • Index order alone decides. Of 996 single-segment indexes of 1-5 documents that mix labelled and unlabelled documents, 660 lose a labelled document and 336 lose only unlabelled ones; all 363 fully labelled ones are correct, and the other 5 of the 1,364, with no labelled document at all, throw an exception (not with the fix).
The devil's-advocate check225 words

The strongest "works as designed" case, built by the intended-lens review (another model family) and the devil's advocate: a supervised dataset is fully labelled; the class field "must be indexed with sorted doc values"; the only regular upstream test labels every document; there is no explicit promise of a complete partition; and 6.2.0-6.6.6 deliberately threw IllegalStateException for a segment without sorted doc values.

Why it fails: nothing documents a fully labelled precondition, and the module's classifiers handle unlabelled documents on purpose, with no contrary restriction in DatasetSplitter. The cut group is chosen by index order, so a labelled class can vanish while the unlabelled documents are kept, the opposite of any "ignore unlabelled" design. LUCENE-7591 replaced the old exception with a fallback meant to handle such segments, so the NullPointerException is not an intended rejection, and leaving the writers locked is wrong for any exception. Verdict: a defect (adjudication: confirmed, high; every verifier: real; the cross-model lenses rated the intended-behaviour argument weak; a later fact check by the same model family rated it moderate for the labelled-class loss and weak for the NullPointerException half, and suggested inviting maintainers to choose whether unlabelled documents are kept or left out). File it as "a labelled class can be missing", not "the last class is dropped": the cut group is the one whose first document comes last.

All options and trade-offs3 options · 649 words

Unlabelled documents keep being copied, as today when they are not the cut group. A maintainer may prefer to leave them out on purpose with setIgnoreDocsWithoutGroupField(true) (option B); either removes the labelled loss. The two options are a policy choice (keep or leave out the unlabelled documents), not two ways to the same output. Workaround until a fix ships: give every document a value of the sorted doc-values class field (for example an explicit "none" class), or delete the unlabelled documents and commit before opening the reader for split; that route was run on main for one segment and for a segment without the class field (IndexWriter drops a fully deleted segment); a merge policy that keeps fully deleted segments was not tried.

Trade-offs

  • Unlabelled documents form their own group, so they also get the test and cross-validation ratios. The extra group changes nothing when every document is labelled.
  • It also removes the empty-index topNGroups must be >= 1 (got 0) error seen in PR #12942 (the limit is then 1).
  • A failure while opening a writer now reaches the caller wrapped in IOException by the existing catch, and the finally closes the caller's reader, as for every failure inside the try today (read, not run separately).
  • Not changed: Terms.size() may return -1 when a codec does not store it (the default codec does); a SortedSet or terms-only class field still fails in the grouping even when every document is labelled (a separate lead).

Leave unlabelled documents out on purpose

#

Same as the recommended option, but call gs.setIgnoreDocsWithoutGroupField(true) (added in PR #15167) instead of counting an extra group.

Trade-offs

Fits "classifiers skip unlabelled documents", but changes the outputs: unlabelled documents are never copied, while today they usually are. The empty-index error stays (the limit is still 0; add Math.max(1, noOfClasses)). The flag is honoured by the returned groups, which is all split reads; totalGroupCount still counts the null group. Validated partly: this doc's test passes 2 of 2 with it; the finder's and the independent reproducer's tests then fail only where they expect the unlabelled document to be copied.

Ask for more groups than can exist (for example maxDoc)

#

Pass an upper bound that cannot be short.

Trade-offs

The first grouping pass sizes its comparators and its group map by the limit (FirstPassGroupingCollector.java:116, :121), so memory grows with the index instead of with the number of classes. Not run.

Downstream note

#

A classifier trained on such a split (for example for spam filtering or moderation) never sees the lost class, but that depends on the application's own use; the application makes the call on its own index, and no untrusted input is involved.

How it was found

#

A bounded-exhaustive check ran the real split() on every index of 1-4 documents and checked that every live document lands in exactly one output. 7,680 of 24,816 splits lost documents, each with an unlabelled document; 9,264 threw NullPointerException; none failed when every document was labelled. Independent AI tools then reproduced, reviewed and judged it.

The method in full171 words

Method: semi-formal (the hunt's tier for tool-guided finds that are not a formal tool's own output): a bounded-exhaustive check of the real jar, a hunt unit (classification, k-NN and utils against reference semantics), 2026-10-27, stock main jars.

  • The harness enumerated every index of 1-4 documents: class none, a or b; 1 or 2 values of a stored text field; one segment or one per document; no deletion or the first document deleted; fieldNames null or {id, text, cls}; ratios 0.1/0.1 or 0.5/0.25.
  • At n = 4: 24,816 splits; 7,680 lost documents (every one with a live unlabelled document; none duplicated a document or copied a deleted one; the count mixes unlabelled-only and labelled losses), 9,264 threw NullPointerException (every one with a segment without the class field), and none failed when every document had a class value.
  • It was then reduced to a public-API JUnit test, and independent AI tools reproduced, reviewed and judged it (see the checks). The devil's advocate's enumeration separates the labelled losses: 660 of 996 mixed single-segment indexes.

History

#

Introduced in 6.1.0 by LUCENE-7196 (2016), which replaced "copy every document" with grouping by class and a group limit that never counts the null group; the NullPointerException came with LUCENE-7591 in 7.0.0. Executed on all 93 releases from 5.5.5 to 10.5.2: every one from 6.1.0 on loses the class.

Versions tested8 rows

Labelled-class loss: introduced by LUCENE-7196 (2016-04-08, @tteofili, pushed directly to git, with no pull request and no CHANGES entry): branch_6x commit ff3661abdaa ("guaranteed class coverage in split indexes through grouping by class"), first released in 6.1.0 (release commit of 2016-06-12, tagged 2016-06-16); its trunk twin 112078eaf90 is what git blame on main credits. Later rewrites of the count (LUCENE-6766, LUCENE-7350, LUCENE-7400, LUCENE-7591) kept the missing null group.

NullPointerException: introduced by LUCENE-7591 (87d8b5450a6, 2016-12-12, "approximate to no. of terms when DVs are not available"), first released in 7.0.0 (release commit of 2017-09-08, tagged 2017-09-18). It replaced an IllegalStateException with terms(classFieldName).size() and no null check. The writers have been opened before the try since the class was created (LUCENE-4345, 2012).

Commit isolation (only DatasetSplitter.java swapped into old jars): 6.0.1 jars with the LUCENE-7196 file lose d2, with its parent they keep all three; 6.6.6 jars with the LUCENE-7591 file throw the NullPointerException, with its parent the IllegalStateException.

Bug record

#

LFV-683, snapshot of 2026-10-29

Registry title
DatasetSplitter.split can silently leave a whole labelled class out of all three output indexes when some documents have no class value, and throws NullPointerException, leaving the output writers locked, when a segment has no class field
Area
classification / utils: DatasetSplitter (split: class count used as the GroupingSearch group limit)
Priority
Medium, rank 215: DatasetSplitter can drop a whole labelled class, but only on force-merged indexes that also hold unlabelled documents, and it partly fails loudly with an NPE.
Impact class
silent wrong results
Impact note
Anyone who builds training, test and cross-validation indexes with DatasetSplitter.split from an index in which some live documents have no class value (unlabelled documents, which the module's classifiers skip on purpose) can silently lose every document of one labelled class from all three outputs: on a single-segment index (the upstream test force-merges to one) the class whose first document comes last in index order is dropped whenever an unlabelled document comes before it, while multi-segment indexes whose classes repeat across segments over-count the classes and hide the loss; a segment with no class field at all instead makes split throw NullPointerException and leave the three output directories locked and the caller's reader open; there is no scale condition, -ea and -da behave the same, the source index is not changed, and fully labelled indexes are not affected.
Summary
You split an index with DatasetSplitter.split(reader, train, test, cv, analyzer, false, "cls"), where one segment holds d0 without a class value, d1 of class a and d2 of class b. You expect every live document in one of the three new indexes, and every class present, which is what the grouping by class was added for (LUCENE-7196). Instead d2, and with it all of class b, is in none of the outputs: split asks GroupingSearch for as many groups as there are class values, but the documents without a value form one more (null) group that takes one of those slots; and if a segment has no class field at all, split throws NullPointerException from terms(classFieldName).size() before its try block, so its three IndexWriters are never closed.
Introduced
Labelled-class loss: ff3661abdaa5b4ae33496dc378ae917f7a7a723b (branch_6x, 2016-04-08, 'LUCENE-7196 - guaranteed class coverage in split indexes through grouping by class (cherry picked from commit 112078e)'), the commit that shipped in 6.1.0; its trunk twin 112078eaf909bdda27a092d13a8431c046a82ac0 (same day, same DatasetSplitter.java, first released in 7.0.0) is what git blame on main credits for the GroupingSearch lines and the gs.search(..., 0, noOfClasses) call. It replaced 'copy every hit of a MatchAllDocsQuery' with GroupingSearch by class and a group limit equal to the number of class values, which never counts the null group of documents without a value; the later rewrites of that count kept this (LUCENE-6766 in 6.2.0, LUCENE-7350 in 6.4.0, LUCENE-7400 in 7.0.0). So it is a regression of LUCENE-7196, not inherited behaviour. NullPointerException half: 87d8b5450a6d75fdd4b724b24a3722054b6d00f8 (master, 2016-12-12, 'LUCENE-7591 - approximate to no. of terms when DVs are not available', first released in 7.0.0), which replaced a deliberate IllegalStateException with leave.reader().terms(classFieldName).size() and no null check. The writers have been opened before the try since the class was created (3459b28334e2, LUCENE-4345, 2012); an input can reach that leak only since 6.2.0, when a check that can throw came before the try. All are svn-era commits by @tteofili with no pull request and no CHANGES entry; the issues LUCENE-7196 / #8251 and LUCENE-7591 / #8642 never mention documents without a class value. [exec: commit isolation with only DatasetSplitter.java swapped in: 6.0.1 jars with the ff3661abdaa file lose d2, with its parent f18cb90104a (the 6.0.1 file) they keep all three documents; 6.6.6 jars with the 87d8b5450a6 file throw NullPointerException, with its parent 25c7855bbae (the LUCENE-7400 file) IllegalStateException, both leaving the writers locked. read: git log --follow, git blame and git tag --contains in the history clone] (2016-04-08 (LUCENE-7196, labelled-class loss); 2016-12-12 (LUCENE-7591, NullPointerException half))
First affected version
6.1.0 [exec] (tagged 2016-06-12) for the labelled-class loss; 7.0.0 [exec] (tagged 2017-09-08) for the NullPointerException. Last unaffected release: 6.0.1 [exec], whose split() has no classFieldName parameter and copies every document.
Affected versions
Labelled-class loss: every release from 6.1.0 to 10.5.2 (90 releases) and main a9779ef3c193; not fixed. Segment without the class field: 7.0.0-10.5.2 (74 releases) and main throw NullPointerException and leave all three output directories locked; 6.2.0-6.6.6 (15 releases) throw IllegalStateException ('the classFieldName "cls" must index sorted doc values', the documented precondition) before the try and also leave the three directories locked; 6.1.0 copies that document and releases the locks. Not affected: 5.5.5, 6.0.0 and 6.0.1 (no class-aware split; every document is copied). [exec] the follow-up's version-portable main() probe (core API only, split() overload chosen by reflection, NIOFSDirectory) on all 93 releases 5.5.5-10.5.2 and on main with -ea, plus -da on 10.5.2 and main (104 executed runs with the JUnit and commit-isolation runs): scenario A (one segment: u0 unlabelled, d1=a, d2=b) gives [d1, u0] on every affected version; the fully labelled control gives [d0, d1, d2] everywhere; scenario A2 (unlabelled document last) gives [d1, d2], so then only the unlabelled document is dropped. The finder's JUnit (compiles from 9.5 on) fails 2 of 2 on 9.12.3, 10.5.2 and main (-ea and -da); the independent reproduction's JUnit fails 3 of 4 on main (-ea and -da), 10.5.2 and 9.12.3. [read] lucene/classification and lucene/grouping are unchanged between ea57360912ed and a9779ef3c193; upstream, DatasetSplitter.java last changed in #15499 (2025-12-11, a refactor), and no open PR changes the class count or the null handling (prior-report search against upstream main a95c754ee003, 2026-10-26).
