PatienceKnnVectorQuery over a SeededKnnVectorQuery modifies itself on every search, and overlapping searches of one query on two readers fail

Searching a PatienceKnnVectorQuery that wraps a SeededKnnVectorQuery changes the query object: rewrite stores a searcher-specific seed Weight in its own field, so it no longer equals an identical fresh query, and overlapping searches of one query object on two readers crash. Affects every release from 10.3.0 to 10.6.0.

The finding in 30 seconds

#

PatienceKnnVectorQuery.rewrite handles a seeded delegate by assigning its own field a new SeededKnnVectorQuery that holds a seed Weight built for the current searcher. The sibling SeededKnnVectorQuery.rewrite builds the same thing into a new query and leaves itself unchanged.

Background: queries, rewrite and Weights

#
  1. A Query describes what to find. IndexSearcher first rewrites it into simpler queries, then builds a Weight for that searcher; the Weight holds everything that depends on the searcher and its reader.
  2. So a search does not change the Query object: Weight's javadoc says this is what lets one instance be reused, and BooleanQuery caches its own hash, computed from its clauses, on that assumption.
  3. SeededKnnVectorQuery starts the HNSW graph search from the top hits of a seed query. To find them in each segment it needs a seed Weight built for the current searcher.
  4. PatienceKnnVectorQuery wraps a kNN query, here the seeded one, and stops the graph search early once the top hits stop changing.

The finding, step by step

#
  1. Index one document (id:0, vector [1, 1]) and build PatienceKnnVectorQuery.fromSeededQuery(SeededKnnVectorQuery.fromFloatQuery(knn, seed)): a top-1 kNN query that starts its graph search from the hits of the seed TermQuery(id:0) and stops early once the results saturate.
  2. Run searcher.search(query, 1) once. You expect the query object to be untouched: Weight's javadoc says searching does not modify a Query, so that one instance can be reused, and IndexSearcher is documented thread-safe.
  3. Instead rewrite stored a seed Weight built for this searcher in the query's own delegate field: toString changes from seedWeight=null to seedWeight=weight(id:0), hashCode changes, and the query no longer equals an identical, never-searched copy.
  4. Search one query object from two threads on two different readers at once: the first search picks up the other reader's seed Weight for its second segment and fails with AssertionError: The top-reader used to create Weight is not the same as the current reader's top-reader, or with assertions off ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1 (run with a 2-segment and a 1-segment reader).
  5. Searching it again later, even on another reader, still returns correct hits, because each rewrite rebuilds the seed Weight. The damage is the changed identity (maps keyed on the query lose entries; a BooleanQuery holding it fails its cached-hash assertion) and the crash under overlapping searches.

Who is affected

#

Applications that build PatienceKnnVectorQuery.fromSeededQuery(...) (both classes @lucene.experimental; Solr's DenseVectorField builds this combination). Every search changes the query's identity, which hurts maps or caches keyed on it and a BooleanQuery holding it. The crash needs one query object searched on two different readers at overlapping times.

Mechanism, terms and numbers685 words

PatienceKnnVectorQuery (early termination for HNSW search) can wrap a SeededKnnVectorQuery (HNSW search started from the hits of a seed query); both are @lucene.experimental. A seeded query needs a seed Weight built for the current searcher. SeededKnnVectorQuery.rewrite builds it into a new query, but PatienceKnnVectorQuery.rewrite assigns a new SeededKnnVectorQuery holding it to its own non-final delegate field (PatienceKnnVectorQuery.java:45, :296-312 on main 645d4fe14a20). Because equals/hashCode include that field and the seed Weight, one search changes the query's identity, against Weight's contract that "searching does not modify a Query, so that a Query instance can be reused" (Weight.java:29-32). The field is re-read for every segment, so when one query object is searched on two different readers at overlapping times, a search runs the other reader's seed Weight and fails with an AssertionError (assertions on) or, in the run with a 2-segment and a 1-segment reader, an ArrayIndexOutOfBoundsException (off). Sequential reuse still returns correct hits. #14688 introduced it in 10.3.0 while fixing an NPE on this path; every release from 10.3.0 to 10.6.0 and main are affected. Building the seed Weight into a new query, as SeededKnnVectorQuery.rewrite does, fixes it; the closest kNN suites and the whole core module pass with the fix. It rewrites into a plain PatienceKnnVectorQuery, so a subclass's overrides are skipped for a seeded delegate, and it uses a caller-supplied seed Weight as given (see the fixes).

The code (main 645d4fe14a20)

#
  1. The field. PatienceKnnVectorQuery.java:45: private AbstractKnnVectorQuery delegate;, the class's only non-final field (patience and saturationThreshold at :43-44 are final).
  2. The assignment. rewrite (:296-312): if delegate is a SeededKnnVectorQuery, :301-309 assigns delegate = new SeededKnnVectorQuery(seededKnnVectorQuery.delegate, seededKnnVectorQuery.seed, seededKnnVectorQuery.createSeedWeight(indexSearcher), delegate.field, delegate.k, delegate.filter, delegate.searchStrategy), then super.rewrite runs the per-segment kNN search on this and returns a DocAndScoreQuery. The caller's object keeps the new delegate. createSeedWeight (SeededKnnVectorQuery.java:136-146) rewrites seed MUST + FieldExistsQuery(field) FILTER (plus the filter) and calls indexSearcher.createWeight(...), so the stored Weight belongs to this searcher's top-level reader.
  3. Identity. PatienceKnnVectorQuery.equals/hashCode include delegate (:223-237); SeededKnnVectorQuery.equals/hashCode include seedWeight (SeededKnnVectorQuery.java:181-195); Weight keeps Object identity. So after any search the query no longer equals a fresh twin, and its hashCode includes the new Weight's identity hash: in every recorded run it differed from the twin's after one search and changed again after a second one.
  4. Re-read per segment. approximateSearch (:196-204) calls delegate.approximateSearch(...) for each segment; SeededKnnVectorQuery.approximateSearch (:148-157) wraps the collector manager, and SeededCollectorManager.newCollector runs seedWeight.bulkScorer(ctx) on the caller's segment (:311-321). If another thread's rewrite replaced the field in between, that is the other searcher's Weight: TermQuery's check that the Weight was built for this top-level reader (TermQuery.java:120-122) fails under -ea; under -da, TermStates.get indexes the other reader's per-segment states with this segment's ord (TermStates.java:178-181): Index 1 out of bounds for length 1 when reader B has one segment (the run). The TermQuery path is this data's: every document has a vector, so the seed rewrites to the bare TermQuery; with other data or a kNN filter the seed Weight can be a BooleanQuery's and the failure can look different (read, not run).
  5. The sibling. SeededKnnVectorQuery.rewrite (:119-134): when seedWeight is null it builds new SeededKnnVectorQuery(..., createSeedWeight(indexSearcher), ...) and returns rewritten.rewrite(indexSearcher); the original is untouched.

What a caller observes (executed on main)

#
  • One search: toString of the delegate goes from seedWeight=null to seedWeight=weight(id:0); equals with a fresh twin turns false; hashCode changed (in every recorded run, and again after a second search).
  • A HashMap that stored a value under the query before the search no longer finds it afterwards (get returns null while size() is still 1).
  • A BooleanQuery with the query as a clause, whose hashCode was computed before the search, searched once, fails assert hashCode == computeHashCode() (BooleanQuery.java:770) under -ea; an unseeded Patience clause passes.
  • Searching the same object on reader A, then B, then A again returns the same top 5 as fresh queries each time.
Exposure and likelihood322 words
  • Who. Code that builds PatienceKnnVectorQuery.fromSeededQuery(...) or new PatienceKnnVectorQuery(SeededKnnVectorQuery, ...). Solr's DenseVectorField builds this combination when a request asks for a seed query and early termination, and its normal request parsing builds a fresh query object per request (read; Solr's caches and autowarming were not traced). Default IndexWriterConfig and IndexSearcher; one document is enough.
  • On every search (deterministic). The query's equals/hashCode change. That matters to code relying on query immutability: maps or caches keyed on the query object (a HashMap lookup executed), and composite queries that cache a hash computed before the search (BooleanQuery asserts under -ea; with -da its cached hash silently goes stale, not asserted).
  • Under overlapping searches on two different readers. One request fails with an AssertionError (-ea) or an ArrayIndexOutOfBoundsException (-da). Ways to get there: one cached or constant query object run in parallel against several indexes or shards in one JVM, or served by the old and the new searcher at once around an NRT refresh.
  • Not claimed. Lucene's own LRUQueryCache is not affected: kNN queries always rewrite to DocAndScoreQuery or MatchNoDocsQuery before caching. Sequential reuse on different readers returns correct hits (executed). Concurrent searches on the same reader should not fail (read, not executed); if their two searchers had different similarities, the seed could be scored with the other searcher's (a TermWeight keeps its searcher's Similarity, TermQuery.java:43-58), which can change the HNSW entry points (read, not executed). The assertions-off runs used a 2-segment search A against a 1-segment search B; readers where the other one has as many segments or more were not run, so there is no silent-wrong-results claim. A searched query keeps the last search's seed Weight until the next rewrite; its size was not measured.
  • Likelihood: rare. The identity change is constant but hurts only callers that depend on it; the crash needs one object shared by overlapping searches on different readers.

Minimal repro

#

One JUnit method on the public API: one document, one IndexSearcher.search(query, 1) with a seeded Patience query, then assertEquals against an identical, never-searched query. Deterministic, single thread; fails the same way with assertions on and off.

Expected
After one search the query still equals an identical, never-searched query (seedWeight=null).
Observed
It does not: its delegate now prints seedWeight=weight(id:0), with assertions on and off on main, and on every release from 10.3.0 to 10.6.0 (assertions on; also off on 10.3.0, 10.5.2 and 10.6.0).

Why it looks unintended

#
  • Weight.java:29-32: searching "does not modify a Query, so that a Query instance can be reused"; searcher-dependent state belongs in the Weight.
  • The sibling SeededKnnVectorQuery.rewrite builds the same seed Weight into a new query and leaves itself unchanged.
  • #14688 made the field mutable to fix an NPE, never discussing reuse; BooleanQuery's cached-hash assertion fails on it.
The full argument287 words
  • Contract, current javadoc. Weight.java:29-32: "The purpose of Weight is to ensure searching does not modify a Query, so that a Query instance can be reused. ... IndexSearcher dependent state of the query should reside in the Weight." search/package-info.java:442-445: "Any IndexSearcher dependent state should be stored in the Weight implementation, not in the Query class."
  • Core code relies on it. BooleanQuery caches its hash "since boolean queries are immutable" and asserts the cached value equals a recomputed one (BooleanQuery.java:760-772).
  • The non-mutating shape exists next door. SeededKnnVectorQuery.rewrite (SeededKnnVectorQuery.java:119-134, from #14170) returns a new instance.
  • No decision recorded. #14688 changed final AbstractKnnVectorQuery delegate into a mutable field only to create the seed Weight; its body ("This makes sure those queries are tested together and query rewriting works properly") and its one review ("LGTM") never mention mutation, reuse or thread safety. No upstream test checks a query after searching it: TestPatience{Float,Byte}VectorQuery.testToString asserts toString on a new query and then rewrites it (:96 / :106); with the randomly chosen seeded wrapper that rewrite runs the mutating path, but the test never looks at that object again, so the mutation goes unnoticed rather than being expected.
  • Upstream treats this class of bug as a bug. #10322 (LUCENE-9282, open, type:bug): Surround parser queries change hashCode/equals on rewrite. #8041 (LUCENE-6984, fixed 2016): "queries should be considered immutable once created". #11467 (LUCENE-10431, open): Alan Woodward, "BooleanQuery is expecting all its subqueries to be immutable". On LUCENE-6369 (#7429) jpountz closed with "queries should now be immutable". Historical: lucene/CHANGES.txt:22476-22478 (1.3 RC1), "Queries are no longer modified during a search. This makes it possible, e.g., to reuse the same query instance with multiple indexes from multiple threads."
The devil's-advocate check126 words

Strongest case: both classes are @lucene.experimental; Query.rewrite's javadoc (Query.java:72-83) never promises the query is left alone; sequential reuse still gives correct hits; so this is an internal detail plus a cache-key nit, and sharing one query object across concurrent searches on different readers is the caller's risk. The cross-model reviewers and the intended-behaviour verifier rated it weak.

Why it fails: the reuse guarantee is stated on Weight and in the package docs, not on rewrite, and it is what BooleanQuery's cached hash relies on; IndexSearcher is documented thread-safe (IndexSearcher.java:69-75), and neither class says its query is single-use or bound to a reader. @lucene.experimental waives API stability, not correctness, and the sibling class shows the non-mutating shape was available.

Suggested fix

#

Recommended Build the seed Weight into a new query, as SeededKnnVectorQuery.rewrite does

Make delegate final; when the seeded delegate has no seed Weight, build one into a new SeededKnnVectorQuery and return a new, rewritten PatienceKnnVectorQuery, as SeededKnnVectorQuery.rewrite does (+9/-5). Both tests, the closest kNN suites and the whole core module pass. Trade-offs: subclass overrides are skipped for a seeded delegate; a caller-supplied seed Weight is used as given (untested).

if (delegate instanceof SeededKnnVectorQuery seededKnnVectorQuery
    && seededKnnVectorQuery.seedWeight == null) {
  SeededKnnVectorQuery withWeight =
      new SeededKnnVectorQuery(
          seededKnnVectorQuery.delegate,
          seededKnnVectorQuery.seed,
          seededKnnVectorQuery.createSeedWeight(indexSearcher),
          delegate.field, delegate.k, delegate.filter, delegate.searchStrategy);
  return new PatienceKnnVectorQuery(
          withWeight, field, k, filter, searchStrategy, saturationThreshold, patience)
      .rewrite(indexSearcher);
}
return super.rewrite(indexSearcher);

Build the seed Weight into a new query, as SeededKnnVectorQuery.rewrite does (validated by the checks) (recommended)

#

Make delegate final. In rewrite, when delegate is a SeededKnnVectorQuery whose seedWeight is null, build a new SeededKnnVectorQuery with createSeedWeight(indexSearcher) and return a new PatienceKnnVectorQuery around it, rewritten. The original query is never changed.

if (delegate instanceof SeededKnnVectorQuery seededKnnVectorQuery
    && seededKnnVectorQuery.seedWeight == null) {
  SeededKnnVectorQuery withWeight =
      new SeededKnnVectorQuery(
          seededKnnVectorQuery.delegate,
          seededKnnVectorQuery.seed,
          seededKnnVectorQuery.createSeedWeight(indexSearcher),
          delegate.field, delegate.k, delegate.filter, delegate.searchStrategy);
  return new PatienceKnnVectorQuery(
          withWeight, field, k, filter, searchStrategy, saturationThreshold, patience)
      .rewrite(indexSearcher);
}
return super.rewrite(indexSearcher);

Trade-offs

  • Same pattern as the sibling, and final lets the compiler keep it that way.
  • Caller-supplied seed Weight. A SeededKnnVectorQuery built with the public constructor that takes a seedWeight (#14838) is now used as given, as SeededKnnVectorQuery alone does; the stock code always replaced it. The caller must then build that Weight on the searcher that runs the query: one built on another reader fails the same way, and a TermWeight carries the Similarity of the searcher that built it (TermQuery.java:43-58). This path was not tested; add a test for it if you propose this fix. The next option keeps "always rebuild".
  • Subclasses. It rewrites into a plain new PatienceKnnVectorQuery(...), so for a seeded delegate without a seed Weight a subclass's overrides (getKnnCollectorManager, approximateSearch, ...; possible since #14838 made the constructors public) are no longer used; the stock code ran super.rewrite on the subclass instance itself. Executed: a probe subclass overriding getKnnCollectorManager passes on stock and fails with this fix. SeededKnnVectorQuery.rewrite has the same limitation for its own subclasses. The weight-per-search option would avoid it (not built).
  • Cost. One extra small query object per search, as in SeededKnnVectorQuery.rewrite. No public API change (delegate is private, the 7-argument constructor package-private).

  • TestPatienceFloatVectorQuery, TestPatienceByteVectorQuery, TestSeededKnnFloatVectorQuery, TestSeededKnnByteVectorQuery, TestKnnFloatVectorQuery, TestKnnByteVectorQuery, TestKnnByteVectorQueryMMap and the new test: 8 classes, 278 tests, 0 failures, with assertions on and off.

Keep "always rebuild the seed Weight", without mutation (not built)

#

Build the new PatienceKnnVectorQuery around a SeededKnnVectorQuery with a fresh seed Weight unconditionally, and run AbstractKnnVectorQuery.rewrite on that new instance through a private helper (calling .rewrite on it would loop).

Trade-offs

Keeps the stock behaviour for a caller-supplied seed Weight; slightly more code; not run. Like the recommended fix, it rewrites into a plain PatienceKnnVectorQuery, so a subclass's overrides are not used for a seeded delegate.

Keep the seed Weight out of query objects (not built)

#

Create the seed Weight per search and pass it down through the per-search collector manager instead of storing it in a SeededKnnVectorQuery.

Trade-offs

Fixes the pattern in both classes, takes seedWeight out of equals and keeps rewrite on the caller's instance (so subclass overrides keep working), but reworks SeededKnnVectorQuery, whose constructors that take a Weight are public since #14838. Larger change; not run.

Document the query as not reusable (not recommended)

#

A javadoc note "not reusable, not thread-safe".

Trade-offs

Contradicts Weight.java:29-32 and BooleanQuery's immutability assumption, and leaves the crash in place.

Downstream note

#

Solr's normal request parsing builds a fresh query object per request, so a remote client cannot make two searches share one object that way (Solr's caches and autowarming were not traced); the exposed applications are those that cache or share one query object across indexes or across an NRT refresh.

How it was found

#

Code reading of PatienceKnnVectorQuery.rewrite in an AI-assisted review of the kNN query classes flagged an assignment to the query's own field. A small TLA+ model of two searches sharing that field gave a 4-state counterexample (one search uses the other's seed Weight), and a latch-driven JUnit reproduced both symptoms on the stock jar.

The method in full130 words

Method: code reading, then TLA+ model checking and JUnit (the study's "non-formal" tier, because the first signal was code reading). In a hunt unit (kNN query layer, 2026-10-25), the finder noticed that rewrite assigns the query's own field. It then wrote SharedDelegate.tla (49 lines): two searches share the field, each assigns its own seed Weight and later uses the field. TLC found the invariant OwnWeightOnly (a search only uses the Weight it built) violated by a 4-state trace (A assigns, B assigns, A uses B's Weight), and no error with the fix (16 distinct states). The finder then bridged it to the stock jar with a public-API JUnit that fixes the interleaving with latches. The minimal one-search test of this doc was cut down from that JUnit's first method.

LFV-125, snapshot of 2026-11-05

Registry title
PatienceKnnVectorQuery over a SeededKnnVectorQuery stores a searcher-specific seed Weight in its own field during rewrite, so every search changes the query's equals/hashCode, and searching one query object concurrently on two different readers fails
Area
search / kNN query layer (PatienceKnnVectorQuery over SeededKnnVectorQuery)
Priority
Low, rank 694: Moved down from Medium: PatienceKnnVectorQuery.fromSeededQuery changes its equals/hashCode on every search and crashes only when one query object is searched on two readers concurrently, mostly a cache and immutability problem in experimental code that Solr's per-request objects avoid.
Impact class
crash
Impact note
Applications that compose the @lucene.experimental PatienceKnnVectorQuery.fromSeededQuery over a SeededKnnVectorQuery (Solr 10's DenseVectorField builds this when a seed query and early termination are both requested) see every search change the query object's equals/hashCode, with the default codec, IndexWriterConfig and searcher and one segment; the crash (AssertionError with -ea, ArrayIndexOutOfBoundsException at TermStates.get with -da) additionally needs the application to search the same query object on two different readers at overlapping times, while sequential reuse on different readers returns correct hits; no scale is needed, and it is in every release since 10.3.0.
Summary
You build PatienceKnnVectorQuery.fromSeededQuery(SeededKnnVectorQuery.fromFloatQuery(knnQuery, seedQuery)) and search it with IndexSearcher. You expect the query object to be unchanged by the search (Weight javadoc: 'searching does not modify a Query, so that a Query instance can be reused'), so it can be compared, cached and reused, including by several threads on different readers. Instead rewrite stores a new SeededKnnVectorQuery holding a seed Weight built for the current searcher in the query's own delegate field: after one search the query's hashCode has changed and it no longer equals an identical unsearched query, and when two searches of the same object on different readers overlap, the first one runs the other searcher's seed Weight on its later segments and fails with 'AssertionError: The top-reader used to create Weight is not the same as the current reader's top-reader' (-ea) or 'ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1' at TermStates.get (-da).
