Geo3DPoint.newDistanceQuery accepts a negative radius and silently builds the radius-0 query instead of throwing IllegalArgumentException

Geo3DPoint.newDistanceQuery promises an IllegalArgumentException for a negative radius, as LatLonPoint throws, but never checks the radius: -1 m silently becomes the radius-0 query, so a caller's bad radius gives an empty result instead of an error. In every release since 6.1.0.

The finding in 30 seconds

#

A distance query is a circle on the planet. Geo3D converts the radius to an angle and lets a factory build the shape; nothing checks the sign of the radius on the way.

Background: how Geo3D builds a distance query

#
  1. Geo3DPoint (spatial3d module) indexes points on a 3D planet model such as PlanetModel.WGS84.
  2. newDistanceQuery(field, planet, lat, lon, radiusMeters) matches points within radiusMeters of (lat, lon). Internally the radius becomes an angle: radiusMeters / planet.getMeanRadius().
  3. GeoCircleFactory.makeGeoCircle then builds the shape: a single point (GeoDegeneratePoint) for an angle too small to represent, below 3.1e-12 radians, else a GeoStandardCircle.

The finding, step by step

#
  1. Call Geo3DPoint.newDistanceQuery("f", PlanetModel.WGS84, 0, 0, -1): a radius of -1 metre, for example a computed radius that went below zero.
  2. You expect IllegalArgumentException: the javadoc says the radius "must be non-negative and finite" and promises the exception, and LatLonPoint.newDistanceQuery throws radiusMeters: '-1.0' is invalid for the same value.
  3. Instead nothing is thrown. Geo3DUtil.fromDistance checks only latitude and longitude and turns -1 m into an angle of -1.57e-7 radians.
  4. The circle factory makes a single point of every angle below 3.1e-12 radians (0.02 mm), negatives included, so the circle's own "Cutoff angle out of bounds" check never runs.
  5. The query is equal() to the radius-0 query (Shape: GeoDegeneratePoint), and so are -1000 m, -1e9 m and -Infinity. On a 3-document index each matched 0 documents and raised no error.

Who is affected

#

Applications on the opt-in spatial3d module that let a negative radius reach Geo3DPoint.newDistanceQuery, such as a computed radius that went below zero or an unchecked request value. Default configuration, assertions on or off. Their own mistake shows up as an empty result instead of an error. Valid radii, other queries and the index are unaffected.

Mechanism, terms and numbers462 words

Geo3DPoint.newDistanceQuery(field, planetModel, latitude, longitude, radiusMeters) documents the radius as "must be non-negative and finite" and promises IllegalArgumentException "if ... radius is invalid" (Geo3DPoint.java:116-120). The method only calls Geo3DUtil.fromDistance, which checks latitude and longitude but not the radius, and GeoCircleFactory.makeGeoCircle turns every angle below Vector.MINIMUM_ANGULAR_RESOLUTION (about 3.1e-12 radians), negative ones included, into a GeoDegeneratePoint at the centre. So -1 m, -1000 m, -1e9 m and -Infinity silently build a query equal() to the radius-0 query, where LatLonPoint.newDistanceQuery, whose radius and @throws javadoc lines this one copied in 6.1.0, throws radiusMeters: '-1.0' is invalid. Only a caller's own bad radius reaches it, in the opt-in spatial3d module; the effect is an empty or centre-only result instead of an error. A three-line check, the same as LatLonPoint's, fixes it.

The code (main 5adff78bb168, lucene/spatial3d/src/java/org/apache/lucene/spatial3d/)

#
  1. No radius check at the entry point. Geo3DPoint.newDistanceQuery (Geo3DPoint.java:122-130) calls Geo3DUtil.fromDistance(planetModel, latitude, longitude, radiusMeters) (:128) and newShapeQuery(field, shape), nothing else.
  2. Only the location is checked. Geo3DUtil.fromDistance (Geo3DUtil.java:152-162) calls GeoUtils.checkLatitude and checkLongitude (:157-158), computes radiusRadians = radiusMeters / planetModel.getMeanRadius() (:159) and calls GeoCircleFactory.makeGeoCircle (:160-161). On WGS84 the mean radius is (2 x 6,378,137 + 6,356,752.314245) / 3 = 6,371,008.77 m (geom/PlanetModel.java:35, :142), so -1 m is -1.57e-7 radians.
  3. Every too-small angle becomes a point. makeGeoCircle: if (cutoffAngle < Vector.MINIMUM_ANGULAR_RESOLUTION) return new GeoDegeneratePoint(planetModel, latitude, longitude); (geom/GeoCircleFactory.java:43-45). MINIMUM_ANGULAR_RESOLUTION = Math.PI * MINIMUM_RESOLUTION, with MINIMUM_RESOLUTION = 1.0e-12 (geom/Vector.java:26, :29): about 3.1e-12 radians, or 0.02 mm on WGS84. Every negative angle, and -Infinity, is below it.
  4. The check that would reject it is skipped. Only angles at or above the threshold reach the GeoStandardCircle constructor, which throws IllegalArgumentException("Cutoff angle out of bounds") for cutoffAngle < 0.0 || cutoffAngle > Math.PI (geom/GeoStandardCircle.java:61-62). That is why +Infinity and 1e9 m throw ("Cutoff angle out of bounds"), NaN throws ("Plane could not be constructed!"), and no negative value does.
  5. Result. The shape is the degenerate point at the centre, so the query is equal() to the radius-0 query: PointInGeo3DShapeQuery: field=f: Shape: GeoDegeneratePoint: {planetmodel=PlanetModel.WGS84, lat=0.0(0.0), lon=0.0(0.0)}.

The numbers

#

Probe on main (assertions off): 3 documents at 10/20, 10.001/20 and 40/50, query centre 10/20. Radius 1000 m: both Geo3DPoint and LatLonPoint count 2. Radius -1, -1000, -1e9 m and -Infinity: Geo3DPoint counts 0 each; LatLonPoint throws radiusMeters: '...' is invalid each time. Radius 0 also counts 0 for Geo3DPoint (1 for LatLonPoint): the single-point shape matches only by exact identity (geom/GeoDegeneratePoint.java:149-151, geom/GeoPoint.java:308-312, tolerance 1e-12), and the decoded centre document is 1.32 mm away. That is a separate behaviour, not claimed here; the clean evidence for this bug is the exception test, not these counts.

Exposure and likelihood124 words
  • Who. Users of the spatial3d module, a separate lucene-spatial3d artifact; Geo3DPoint is @lucene.experimental (Geo3DPoint.java:42). Only calls with a negative radius are affected: a computed radius such as limit - offset that went below zero, or a request value passed through unchecked.
  • Silent. The caller gets a query that matches at most points at the centre instead of the documented exception, so the bug in their own code goes unnoticed. Code that moves from LatLonPoint to Geo3DPoint (the API was made to match it, CHANGES 6.1.0) loses a check it may rely on.
  • Scale. One call, no index needed; deterministic; the same with assertions on and off.
  • Blast radius. Query-time only: nothing is persisted, and no other query, document or index is touched.

Why it looks unintended

#
  • The javadoc promises it: radius "must be non-negative and finite"; @throws IllegalArgumentException if "radius is invalid". Latitude and longitude in that sentence are checked.
  • Added in 6.1.0 to match LatLonPoint, which rejects this radius; its shared test says "negative distance queries are not allowed".
  • The single-point branch was made for zero-width and too-tiny circles; the circle class rejects negative angles.
The full argument267 words
  • The javadoc promises the exception. Geo3DPoint.java:116-120: "@param radiusMeters maximum distance from the center in meters: must be non-negative and finite." and "@throws IllegalArgumentException if {@code field} is null, location has invalid coordinates, or radius is invalid." The coordinates are checked (Geo3DUtil.java:157-158); the radius is not. (The sentence also names a null field, which newShapeQuery and the PointInGeo3DShapeQuery constructor do not check either, Geo3DPoint.java:241-243, PointInGeo3DShapeQuery.java:53-58; not claimed or tested here.)
  • It was made to match LatLonPoint, which enforces it. LUCENE-7150 (#8205, bf0e59223d0, 2016-03-31; CHANGES 6.1.0: "Spatial3d gets useful APIs to create common shape queries, matching LatLonPoint") added the method with LatLonPoint's radius @param and @throws lines word for word (its field line adds a WGS84 accuracy note), one month after LUCENE-7057 (2264600ffe4, 2016-03-01) had added exactly this check to the 2D query. Today: if (Double.isFinite(radiusMeters) == false || radiusMeters < 0) throw new IllegalArgumentException("radiusMeters: '" + radiusMeters + "' is invalid") (lucene/core/.../document/LatLonPointDistanceQuery.java:62-64) and /** negative distance queries are not allowed */ testDistanceNegative (lucene/test-framework/.../tests/geo/BaseGeoPointTestCase.java:320-330). TestGeo3DPoint extends LuceneTestCase, not that base (TestGeo3DPoint.java:85), and never passes a negative radius.
  • The point branch was made for zero-width and too-tiny circles. LUCENE-6798 (#7856 "Add geo3d support for zero-width circles"; 049fef3c9a9, 2015-09-11, "handle degenerate (too tiny) circles in geo3d"); negative angles fall into it only because the test is <. GeoStandardCircle itself calls a negative angle "out of bounds" (GeoStandardCircle.java:61-62).
  • Nothing says it is accepted. No test, CHANGES or MIGRATE entry, commit message or upstream thread says a negative radius is meant to work.
The devil's-advocate check143 words

The strongest case: a negative radius is the caller's bug; Geo3DPoint is @lucene.experimental; geo3d collapses sub-resolution shapes on purpose (GeoPathFactory.java:40-42 does the same for path widths, and newPathQuery's pathWidthMeters has no non-negative contract, Geo3DPoint.java:200), so "degenerate shape out" looks like the module's convention; and the result is only a near-empty match set.

Why it fails: newDistanceQuery is the entry point whose own javadoc names the forbidden value and the exception, and it checks the coordinates named in that sentence. @lucene.experimental renders as "This API is experimental and might change in incompatible ways in the next release": a licence to change the API, not to ignore its current @throws. The low-level factory promises no check; the public method does. The argument is about impact, not intent, and the impact is why this is Low. Verdict: a real Low bug.

Suggested fix

#

Recommended A. Check the radius at the top of Geo3DPoint.newDistanceQuery (validated)

At the top of Geo3DPoint.newDistanceQuery, add LatLonPoint's check: throw IllegalArgumentException("radiusMeters: '" + radiusMeters + "' is invalid") when the radius is negative or not finite. Validated: the repro passes with assertions on and off, the spatial3d tests pass (182, 3 skipped, none failed), and a fresh formatter check passes.

       final double radiusMeters) {
+    if (Double.isFinite(radiusMeters) == false || radiusMeters < 0) {
+      throw new IllegalArgumentException("radiusMeters: '" + radiusMeters + "' is invalid");
+    }
     final GeoShape shape = Geo3DUtil.fromDistance(planetModel, latitude, longitude, radiusMeters);

C. Document the behaviour instead (weaker)

#

A maintainer may prefer to change the javadoc of newDistanceQuery (say that a radius below the resolution, negative ones included, gives a single-point query) rather than add the check.

Trade-offs

A legitimate choice, but weaker: the two distance APIs would keep failing differently, and the caller's error stays silent.

Downstream note

#

Services that count on this exception to reject a bad radius from a request return an empty result instead of an error, so they should check the radius themselves before building the query.

How it was found

#

A semi-formal proof-obligation audit of Geo3DPoint's documented contracts: for each documented @throws, is there code that throws it? The radius clause had none. An executable probe comparing Geo3DPoint with LatLonPoint for the same radii witnessed the gap, and it was reduced to one JUnit test.

The method in full73 words

The obligation for newDistanceQuery pairs the conditions of its @throws sentence with checks on the call path: latitude and longitude are checked (Geo3DUtil.java:157-158); the radius has no check anywhere on the path. The probe ran both Geo3DPoint.newDistanceQuery and LatLonPoint.newDistanceQuery on a 3-document index for radii 1000, 0, -0.0, -1, -1000, -1e9 m, NaN, +Infinity, -Infinity and 1e9 m; the negative radii are the only values that Geo3DPoint accepts and LatLonPoint rejects.
