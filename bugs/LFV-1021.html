UpgradeIndexMergePolicy's javadoc example calls an IndexWriterConfig constructor removed in Lucene 5.0

The only code example in the UpgradeIndexMergePolicy class javadoc starts with new IndexWriterConfig(Version.LUCENE_XX, new KeywordAnalyzer()), but IndexWriterConfig has not taken a Version since 5.0.0. Copied as shown, the example does not compile on any release from 5.0.0 to 10.6.0, whatever real version you put in for LUCENE_XX.

The finding in 30 seconds

#

The example sits in a <pre><code> block of the class javadoc. Javadoc does not compile such blocks, so when IndexWriterConfig lost its Version argument in 5.0.0, nothing failed here.

  1. You want to upgrade an old index yourself, so you open the UpgradeIndexMergePolicy javadoc. It says "for a fully customizable upgrade, you can use this like any other MergePolicy and call forceMerge" and shows five lines.
  2. You copy them and put a real constant, say Version.LATEST, in for the LUCENE_XX placeholder. You expect the code to compile and forceMerge(1) to rewrite the old segments.
  3. Instead javac stops on the first line: no suitable constructor found for IndexWriterConfig(Version, KeywordAnalyzer). IndexWriterConfig has only two constructors, () and (Analyzer), so no version constant can help.
  4. The two-argument constructor was removed in 2014 (LUCENE-5871, released in 5.0.0); that change updated IndexUpgrader but not this javadoc. Without the Version argument, the same five lines compile and upgrade every segment of a 10.0.0 index, and the live-document count stays the same.

Who is affected

#

Developers doing a custom index upgrade with this opt-in, experimental policy who start from its only example: one compile error every time, on 5.0.0 to 10.6.0 and main. Main's migration guide now names the class as an upgrade option. Documentation only: nothing runs differently.

Mechanism, terms and numbers349 words

UpgradeIndexMergePolicy (@lucene.experimental) is the merge policy that rewrites segments written by older Lucene versions when you call forceMerge; IndexUpgrader uses it internally. Its class javadoc says "In general one would use IndexUpgrader, but for a fully customizable upgrade, you can use this like any other MergePolicy and call IndexWriter#forceMerge(int):" and shows five lines. The first is IndexWriterConfig iwc = new IndexWriterConfig(Version.LUCENE_XX, new KeywordAnalyzer());. IndexWriterConfig has only IndexWriterConfig() and IndexWriterConfig(Analyzer), so the example fails with no suitable constructor found for IndexWriterConfig(Version,KeywordAnalyzer) on every release from 5.0.0 to 10.6.0 and on main, with any real constant in place of the placeholder. The example was written in 2011 and was valid then; LUCENE-5871 (2014) removed the Version argument across 451 files, including IndexUpgrader, and missed this javadoc. With new IndexWriterConfig(new KeywordAnalyzer()) the example compiles, and run on the 10.0.0 backward-compatibility index it rewrites every segment to the current version and leaves the live-document count (numDocs()) unchanged. Nothing in Lucene behaves wrongly; only the example is stale.

Why nothing caught it

#

Javadoc does not compile <pre><code> blocks. IndexUpgrader, which LUCENE-5871 did update, builds its own config with new IndexWriterConfig(null) (IndexUpgrader.java:138).

Not claimed

#

The placeholder LUCENE_XX itself (the reader is meant to pick a version), the undeclared dir and the missing imports and exception handling (normal for a fragment); the test fills these in, visibly. No runtime defect.

Exposure and likelihood118 words
  • Who. Readers of the UpgradeIndexMergePolicy class javadoc who copy its example. No query, document or index file reaches it.
  • Default vs opt-in. The policy is opt-in and @lucene.experimental, and the javadoc points most users to IndexUpgrader. No configuration or special input is involved: the copied example always fails.
  • Scale. One error on every release from 5.0.0 (February 2015) to 10.6.0, and on main.
  • Slightly more relevant on main. MIGRATE.md's "Relaxed Index Upgrade Policy" section tells users upgrading old indexes: "Optional: Call forceMerge() or use UpgradeIndexMergePolicy to upgrade segment formats immediately".
  • Effect. A compile error, not wrong behaviour; javac lists IndexWriterConfig(Analyzer) as an alternative.
  • Priority. Low; the same kind of defect as other stale javadoc examples.

Why it looks unintended

#
  • The javadoc offers the block as the way to do "a fully customizable upgrade", and every other line in it exists.
  • It was valid when written (2011) and broke by omission: LUCENE-5871 updated 451 files, including IndexUpgrader, but not this one.
  • The same change's javadoc follow-up fixed the identical stale call in core's overview.html.
The full argument198 words
  • Offered as working code. "for a fully customizable upgrade, you can use this like any other MergePolicy and call IndexWriter#forceMerge(int):", then the example.
  • History. LUCENE-3082 (#4155, Uwe Schindler, 2011-05-09) added the class and the example (600a50bb2ae on trunk, first released in 4.0.0; 535d974518b on branch_3x, which reached 3.2.0); IndexWriterConfig(Version, Analyzer) existed then (3.1.0 to 4.10.4). LUCENE-5871 (872bd9145cd, #6933, Ryan Ernst, 2014-08-09) replaced it with IndexWriterConfig(Analyzer) in 451 files, including IndexUpgrader.java, not this one.
  • The project fixed the same call elsewhere. 5e5072d3c2d ("LUCENE-5859, LUCENE-5871: Remove Version.LUCENE_CURRENT from javadocs", Steven Rowe, 2014-08-21) changed new IndexWriterConfig(Version.LUCENE_CURRENT, analyzer) to new IndexWriterConfig(analyzer) in overview.html, the only file it changed. Its title targets Version.LUCENE_CURRENT; this example uses the placeholder LUCENE_XX, which is most likely why it was missed (an inference: how the sweep was done is not recorded).
  • No record accepts it. No issue, PR, CHANGES or MIGRATE text calls the example deliberate; the 25 comments on #6933 never mention the class.
  • Precedent. Issue #12666 (a stale Analyzer class-javadoc example) was fixed by PR #12693, merged by msokolov on 2023-10-18 as an ordinary doc fix. The open outside PR #16949 is a current batch of such fixes.
The devil's-advocate check179 words

Strongest case for "intended" or "noise": the block is schematic (LUCENE_XX is not a constant, dir is undeclared; Uwe Schindler used the same placeholder line as an API sketch on #4155); the class is @lucene.experimental and the javadoc says "In general one would use IndexUpgrader"; Lucene does not compile javadoc code, and the error is loud with the right constructor named; committers edited this javadoc twice in 2026 (#15573 markup, #16255 a typo fix in the sentence just above the example, line 33) and left the example alone.

Why it fails: the placeholder asks for a version, but no version makes a two-argument call to a one-argument constructor compile. Experimental status allows API change; it does not make the class's own example right. The 2026 edits were sweeps over 252 and 282 files. The project fixed the identical call in overview.html in 2014, and main's MIGRATE.md now sends upgrading users to this class. Every verifier and the adjudication called it real; it was kept at Low as "a removed-API call with concrete copy-paste impact (not a wording slip)".

Suggested fix

#

Recommended Drop the Version argument in the example (validated)

Drop the Version argument: new IndexWriterConfig(new KeywordAnalyzer()) (javadoc only, one line). Validated: the patched example compiles on main and on 10.6.0, upgrades every segment of a 10.0.0 index with the live-document count unchanged, and TestUpgradeIndexMergePolicy passes.

- *  IndexWriterConfig iwc = new IndexWriterConfig(Version.LUCENE_XX, new KeywordAnalyzer());
+ *  IndexWriterConfig iwc = new IndexWriterConfig(new KeywordAnalyzer());
