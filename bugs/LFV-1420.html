Test framework: AutomatonTestUtil.getFiniteStringsRecursive, the reference enumerator, returns strings the automaton does not accept, or never returns, for an arc ending at Integer.MAX_VALUE

The test framework's reference enumerator AutomatonTestUtil.getFiniteStringsRecursive walks an arc's labels with an int loop. On an arc ending at Integer.MAX_VALUE the counter wraps to Integer.MIN_VALUE, so a one-string automaton yields 2 strings with limit 1, and the call never returns without a limit (4.8.1 to 10.6.0, main).

The finding in 30 seconds

#

This is a defect in Lucene's test framework, not in production code. getFiniteStringsRecursive is the slow, simple method that tests use to list every string a small automaton accepts. For an arc ending at the largest int label, its loop counter overflows and the loop never sees the arc end.

Background: automata and the reference enumerator

#
  1. A Lucene Automaton has states joined by arcs. Each arc carries a label range [min, max] of int values; addTransition(0, 1, 7) adds an arc with the single label 7.
  2. An automaton without cycles accepts a finite set of strings, each a sequence of labels. An IntsRef prints them in hex: [7fffffff] is the one-label string 2147483647.
  3. The test framework's AutomatonTestUtil.getFiniteStringsRecursive(a, limit) is a slow reference that lists them all; tests compare faster code such as FiniteStringsIterator against it. A limit of -1 means no limit.

The finding, step by step

#
  1. Build an automaton with one arc labelled Integer.MAX_VALUE (2147483647) from state 0 to an accepting state 1. It accepts exactly one string, printed [7fffffff].
  2. Call AutomatonTestUtil.getFiniteStringsRecursive(a, 1). You expect {[7fffffff]}: one string is accepted, within the limit of 1. With the label 2147483646 that is exactly what you get.
  3. Instead you get {[7fffffff], [80000000]}; the second string, the label -2147483648, is on no arc. With limit -1, which every in-tree caller passes, the call never returns: it ran out of a 1 GB heap after about 17-19 s.
  4. Why: the loop for (int n = t.min; n <= t.max; n++) wraps from 2147483647 to -2147483648 after the last label, and n <= t.max stays true. Here only the limit check (line 541) can stop it, and with limit -1 nothing does.

Who is affected

#

Only test code, in Lucene or downstream (lucene-test-framework is published), that enumerates a hand-built automaton whose arc ends at exactly Integer.MAX_VALUE. No production code calls the helper, and no current in-tree caller or test input is known to reach the wrap. The likely victim is a regression test for the same wrap in core FiniteStringsIterator (LFV-1418).

Mechanism, terms and numbers589 words

AutomatonTestUtil.getFiniteStringsRecursive(Automaton a, int limit) is the test framework's "Simple, original implementation of getFiniteStrings" (AutomatonTestUtil.java:501 at f794ff5a505c): "Returns the set of accepted strings, assuming that at most limit strings are accepted. ... If limit<0, then the limit is infinite." (:503-505). It walks each arc's labels with for (int n = t.min; n <= t.max; n++) (:537). When an arc ends at Integer.MAX_VALUE, n++ after the last label wraps to Integer.MIN_VALUE, which is still <= t.max, so the loop goes on with labels that are on no arc. Nothing stops the loop except a return false: the limit check here (:541), which fires only when the arc leads to an accepting state, or a deeper call that returns false (:545-546) because it hit the limit or found a cycle (:534-535). In the repro the destination has no arcs, so only :541 can stop it.

For 0 -[Integer.MAX_VALUE]-> 1 (accepting), which accepts one string, getFiniteStringsRecursive(a, 1) returns {[7fffffff], [80000000]}, assertions on and off. With limit -1, the convention of every in-tree caller, it runs until OutOfMemoryError; for a non-accepting dead end it loops forever. Labels up to Integer.MAX_VALUE - 1 are enumerated correctly.

It is test code only (the published lucene-test-framework), and no current in-tree caller or test input is known to reach the wrap. The concrete victim is a regression test for LFV-1418, the same wrap in core FiniteStringsIterator, because TestFiniteStringsIterator uses this helper as its oracle. The fix is a long loop counter.

The mechanism (main f794ff5a505c, lucene/test-framework/src/java/org/apache/lucene/tests/util/automaton/AutomatonTestUtil.java)

#
  1. getFiniteStringsRecursive (:510-516) calls the private recursive getFiniteStrings (:522-553) from state 0 and returns the collected set whether or not that call reports "more than limit" (:512-515).
  2. For each arc it runs for (int n = t.min; n <= t.max; n++) (:537, the fix site): it appends n to the path (:538), adds the path to the set if the destination accepts (:539-540), returns false once the set holds more than limit strings (:541-542), and recurses into the destination (:545).
  3. With t.min = t.max = 2147483647, the first pass adds [7fffffff]. Then n++ makes n -2147483648 (Java int overflow), and -2147483648 <= 2147483647 is true, so a second pass adds [80000000]. Now 2 > 1, the limit check returns false, and the public method returns both strings.
  4. With limit = -1 the check never fires, and no int is greater than Integer.MAX_VALUE, so the loop condition stays true for ever (in these shapes the destination has no arcs, so the deeper call at :545 always returns true): an accepting destination adds one string per label until the heap is gone; a non-accepting dead end loops with no exit at all.

A probe on main (assertions off, 1 GB heap): limit -1 on the repro's automaton threw OutOfMemoryError after 16.8 s and 18.8 s (the finder's run: 18.0 s); an arc labelled Integer.MAX_VALUE to a non-accepting state with no arcs was still running after 10 s, inside the loop (sampled top frame AutomatonTestUtil.java:537; :545 in the fact check's re-run); the range [Integer.MAX_VALUE - 2, Integer.MAX_VALUE] (3 strings) with limit 10 returned 11 strings, the limit plus one, where the method stops; the single-arc shapes with the label Integer.MAX_VALUE - 1 returned the right result at once (the probe has no MAX - 1 control for the range).

Exposure and likelihood238 words
  • Who. Test code that uses getFiniteStringsRecursive as its reference enumerator on an automaton with a short label range that reaches exactly Integer.MAX_VALUE (for example a single sentinel label). No production code calls it.
  • No known in-tree trigger. The four in-tree callers pass limit -1 on byte, code-point or token-graph automata: TestFiniteStringsIterator.java:197, TestGraphTokenizers.java:609, and BaseTokenStreamTestCase.assertGraphStrings / getGraphStrings (:1598, :1649). No current in-tree call site or test input is known to build a short range ending at Integer.MAX_VALUE; if one did, limit -1 would make it hang or run out of memory rather than return an extra string. A wide range such as makeCharRange('d', Integer.MAX_VALUE) (TestRegExpParsing.java:193, :243) holds about 2^31 strings, so a limit or the heap stops the enumeration long before the wrap; in practice only a short range at the top reaches it.
  • The concrete victim. TestFiniteStringsIterator checks the core iterator against this helper (assertFiniteStringsRecursive, TestFiniteStringsIterator.java:196-201, limit -1). A regression test for LFV-1418 written in that style would hang or die with OutOfMemoryError inside the oracle before it checks anything.
  • Effect. A wrong expected set (with a limit) or a test that never finishes (without one). No index data and no production behaviour are involved. Deterministic: one arc fails every time, with assertions on and off.
  • Likelihood: contrived. No Lucene test enumerates such a label, and the label lies outside the Unicode alphabet the package describes.

Why it looks unintended

#
  • Its javadoc promises "the set of accepted strings": here 1 string and limit 1, yet [80000000], on no arc, comes back.
  • addTransition takes any int label and 2147483646 works; only the top value wraps. An overflow, not a limit.
  • Disputed: the package's "Unicode alphabet" lets a maintainer call labels above 0x10FFFF out of contract.
The full argument222 words
  • Contract. "Returns the set of accepted strings, assuming that at most limit strings are accepted." (AutomatonTestUtil.java:503-505). In the repro that assumption holds (1 string, limit 1), and [80000000] is not accepted: no arc carries the label -2147483648.
  • Automaton accepts the input. Transition.min/max are documented only as "Minimum accepted label (inclusive)" / "Maximum accepted label (inclusive)", plain int (Transition.java:41-45); addTransition(source, dest, min, max) checks only the two state indexes (Automaton.java:153-159). Lucene's own tests build arcs ending at Integer.MAX_VALUE (TestRegExpParsing.java:193, :243). So addTransition takes this non-negative int without checking a Unicode upper bound; whether that puts it in contract is the disputed point (see the devil's-advocate check).
  • An overflow, not a designed limit. Only an arc whose max is exactly Integer.MAX_VALUE can wrap: for any smaller max, n++ ends the loop. The label 2147483646, far above any code point, is enumerated exactly (controls on main, 9.0.0, 4.10.0 and 4.8.1).
  • History. The method is the old recursive core enumerator, moved verbatim into the test framework by LUCENE-5628 (#6690, 2014) as the slow reference for the new iterative code, at Robert Muir's request in that review. Neither #6690 nor LUCENE-3842 (#4915, where the loop was first written in 2012) discusses the label range or overflow, and no test enumerates a label near Integer.MAX_VALUE with it.
The devil's-advocate check276 words

The strongest case for "intended": the package documents "a full DFA/NFA implementation with Unicode alphabet" (package-info.java:33); the Automata factories speak of code points, and Automaton.step / next document their label as a codepoint (Automaton.java:654, :672, :685); the same class's determinizeSimple and subsetOf already treat Character.MAX_CODE_POINT as the ceiling (AutomatonTestUtil.java:491, :681-684); and when this loop was written, Transition was documented as "a Unicode codepoint interval". The method is a test oracle, and Lucene's own open-ended makeCharRange(x, Integer.MAX_VALUE) idiom never reaches the wrap with a limit, and the devil's-advocate verifier's probe showed that subsetOf and determinizeSimple already answer wrongly for labels above 0x10FFFF, so the class as a whole is not a full-int oracle. So a maintainer may call a label above 0x10FFFF out of contract; the devil's-advocate verifier and two of the cross-model reviews took that view.

Why it fails (a judgement): neither this method, Transition nor addTransition states or checks a bound, and the method enumerates 2147483646 correctly, so the failure is the int wrap at one value, not a domain limit. Its own javadoc sentence is broken by a string on no arc, and a reference oracle that hangs or answers wrongly undermines the very test that would check the core fix (LFV-1418). The fix is one line at no cost. The adjudication confirmed it at medium confidence and Low priority, for consistency with LFV-1418 and LFV-1147, LFV-1167, LFV-1180 and LFV-1182, which rest on the same reading. It argues for Low priority, not for intended behaviour. Fix A hardens this one enumerator; it does not make the class correct for the full int domain.

Downstream note

#

Downstream test suites that use this helper as the oracle for their own automata with an Integer.MAX_VALUE label get a wrong expected set or a hung test; production code is not involved.

History

#

Introduced in 2014 by LUCENE-5628 (8c4e8268181), which moved the old recursive core enumerator, loop included, into the test framework; first released in 4.8.1. Every release through 10.6.0 fails. Not fixed upstream.

Versions tested7 rows

Introduced by 8c4e8268181 (Michael McCandless, 2014-05-04), "LUCENE-5628: change getFiniteStrings to iterative impl" (#6690; svn era, no pull request), which added getFiniteStringsRecursive to AutomatonTestUtil with this loop. The 4.8 branch commit c0d92be5095 (2014-05-05) shipped first, in 4.8.1.

The loop itself is older: LUCENE-3842 (#4915, f2f91bae46c, 2012-09-28) wrote it in core SpecialOperations.getFiniteStrings (4.1.0-4.8.0), a predecessor API that wraps the same way (not counted). Since 4.8.1 the loop changed only in form: int states (LUCENE-5752, 4.10.0), the append call (LUCENE-5864), a reformat (LUCENE-9570) and the move to org.apache.lucene.tests.util.automaton (LUCENE-10301, a94fbb79ac6, 9.1.0). All 107 release tags from 4.8.1 to 10.6.0 in the history clone carry the method with the int loop; the clone lacks 8.8.2-8.11.x, and 8.11.4 was executed. Upstream main e0a3a951e7ef (2026-11-09) still has the loop at :537; the file last changed in 7335eb0ad96d (2026-02-26).

Registry title
Test framework: AutomatonTestUtil.getFiniteStringsRecursive steps its int label loop counter past Integer.MAX_VALUE, where it wraps to Integer.MIN_VALUE, so for an arc ending at Integer.MAX_VALUE it returns strings the automaton does not accept (with a limit) or never returns (without one); since 4.8.1
Area
test-framework / util.automaton (AutomatonTestUtil.getFiniteStringsRecursive, the slow reference enumerator of finite strings)
Priority
Low, rank 1297: Test framework only: the reference enumerator getFiniteStringsRecursive returns strings the automaton does not accept, or never returns, for an arc ending at exactly Integer.MAX_VALUE, in every release since 4.8.1. Only a test that enumerates a hand-built automaton with that label hits it, no in-tree caller does, and the label lies outside the package's described Unicode alphabet, so it is contrived.
Impact class
minor
Impact note
Only test code (in Lucene or downstream; lucene-test-framework is a published artifact) that uses AutomatonTestUtil.getFiniteStringsRecursive as its reference enumerator on a hand-built automaton with a short label range reaching exactly Integer.MAX_VALUE (a sentinel label, for example in a regression test for one of the Integer.MAX_VALUE-label wraps in core) is hit: with a positive limit it silently returns strings with labels from Integer.MIN_VALUE upward that the automaton does not accept, and with limit -1 (what every in-tree caller passes) it runs until OutOfMemoryError or forever, with -ea and -da and no scale [exec]; no in-tree caller (TestFiniteStringsIterator, TestGraphTokenizers, BaseTokenStreamTestCase) is affected, because they enumerate byte, code-point or token-graph automata [read]; labels up to Integer.MAX_VALUE - 1 are enumerated correctly [exec]; every release from 4.8.1 through 10.6.0 and main.
Summary
You build an automaton with one arc labelled Integer.MAX_VALUE from the start state to an accepting state, so it accepts exactly one string, [Integer.MAX_VALUE], and call AutomatonTestUtil.getFiniteStringsRecursive(a, 1). You expect the set {[7fffffff]}, as its javadoc promises ('Returns the set of accepted strings, assuming that at most limit strings are accepted'). Instead you get {[7fffffff], [80000000]}: the label loop 'for (int n = t.min; n <= t.max; n++)' wraps from Integer.MAX_VALUE to Integer.MIN_VALUE, the test n <= t.max stays true, and only the limit check stops it; with limit -1 it never stops.
