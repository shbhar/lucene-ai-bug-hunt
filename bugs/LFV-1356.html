Bits.applyMask throws on an empty destination FixedBitSet instead of doing nothing

An empty window (new FixedBitSet(0)) passed to Bits.applyMask should be a no-op, but a segment's live docs and FixedBitSet throw ArrayIndexOutOfBoundsException once the offset is past the end, and the default implementation throws at any offset. Since 10.2.0; no Lucene reader or scorer was found to reach it.

The finding in 30 seconds

#

applyMask ANDs the window with the live docs, then checks that no bit of the window lies past maxDoc by calling nextSetBit at the first position past the end. Past maxDoc that position is negative and is clamped to 0, and nextSetBit(0) on a zero-length set is out of bounds. The default loop makes that call first, unguarded.

Background in three steps

#
  1. A segment's live docs (LeafReader.getLiveDocs()) are a Bits: bit d is set when document d is not deleted. On 10.6.0 and main, live docs read from the index are a DenseLiveDocs or a SparseLiveDocs; a near-real-time reader's not-yet-written deletes are a FixedBits, which delegates to FixedBitSet.applyMask.
  2. Bits.applyMask(bitSet, offset) takes a window of matches, a FixedBitSet whose bit i stands for document offset + i, and clears the deleted ones. Bulk scorers call it once per window, for example of 4096 documents.
  3. FixedBitSet.nextSetBit(i) requires i < length() and checks it only with an assertion, for speed; callers check first.

The finding, step by step

#
  1. A committed segment has 64 documents, one of them deleted, so leafReader.getLiveDocs(), read from the index, is a DenseLiveDocs with maxDoc 64. Mask an empty window that starts just past the end: liveDocs.applyMask(new FixedBitSet(0), 65).
  2. You expect nothing to happen: the window has no bit to clear and no bit past the end. The same call at offset 0 or 64 returns, and so does a 1-bit all-clear window at offset 65.
  3. The override computes length = min(bitSet.length(), maxDoc - offset) = min(0, -1) = -1. Its check for set bits past the end, length < bitSet.length(), is -1 < 0, true, so it asks the empty set for nextSetBit(0).
  4. nextSetBit requires index < length(), here 0, so you get ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 (AssertionError: index=0, numBits=0 with assertions on). The default Bits.applyMask starts with the same unguarded nextSetBit(0) and throws for an empty window at every offset, even 0.

Who is affected

#

Only code that calls applyMask itself with a zero-length window past the end (or at any offset on a Bits with the default body), or that passes a zero-length Bits without an override to AcceptDocs or FixedBitSet.copyOf. No Lucene reader or scorer was found to reach it. The failure is loud, never a wrong result.

Mechanism, terms and numbers739 words

Bits.applyMask(FixedBitSet bitSet, int offset) clears the bits of a window bitSet (bit i stands for document offset + i) whose documents are not in this Bits; for a segment's live docs, the deleted ones. An empty window (new FixedBitSet(0)) has nothing to clear and no bit that could be out of range, so the consistent behaviour is to do nothing. DenseLiveDocs and SparseLiveDocs (what LeafReader.getLiveDocs() returns for a segment whose deletions are read from the index) and FixedBitSet.applyMask (to which a near-real-time reader's FixedBits delegates) do return for an empty window at an offset up to their length (maxDoc), but past it they throw ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 (AssertionError: index=0, numBits=0 with assertions on).

Their check for set bits past the end computes length = min(bitSet.length(), maxDoc - offset) (for FixedBitSet, length() - offset), which is negative there, and then calls bitSet.nextSetBit(0) on the zero-length set, whose precondition is index < length(). The default Bits.applyMask, which the javadoc gives as the reference behaviour, starts its loop with the same unguarded nextSetBit(0) and throws for an empty window at every offset, although it guards its increment against that very precondition. Every release since 10.2.0 is affected. No Lucene reader or scorer was found to reach it: Lucene's own code passes an empty window only at offset 0 for a 0-document maxDoc, where Lucene's own live docs return, so only code that calls applyMask itself, or hands a zero-length Bits without an override to AcceptDocs or FixedBitSet.copyOf, is hit, and it fails loudly with no wrong result. One zero-length guard per body fixes it.

The mechanism (main 5adff78bb168)

#
  1. DenseLiveDocs.applyMask (DenseLiveDocs.java:154-168): length = Math.min(bitSet.length(), maxDoc - offset) (:160). For bitSet.length() 0, maxDoc 64 and offset 65, length = min(0, -1) = -1. The AND is skipped (length >= 0 is false, :161), then the check for set bits past the end runs: length < bitSet.length() is -1 < 0, true, so it calls bitSet.nextSetBit(Math.max(0, length)), which is nextSetBit(0) (:164-165). Fix site.
  2. FixedBitSet.nextSetBit (FixedBitSet.java:351-356) calls nextSetBitInRange(0, numBits = 0) (:411-417): the assert start >= 0 && start < numBits fails (:413), or, with assertions off, bits[0] is read from the long[0] that new FixedBitSet(0) allocates (:146-150, :417).
  3. At offset 0 or 64, length is min(0, 64) or min(0, 0), that is 0, so 0 < 0 is false and the method returns. For any non-empty window 0 <= max(0, length) < bitSet.length(), so nextSetBit is called legally. Only length 0 fails, and only once offset > maxDoc.
  4. The same check, copied: SparseLiveDocs.applyMask (SparseLiveDocs.java:144-156: length :148, check :152-153; fix site) and FixedBitSet.applyMask (FixedBitSet.java:899-911: length = min(bitSet.length(), length() - offset) :903, check :907-908; fix site). The DenseLiveDocs javadoc says "Same structure as FixedBitSet#applyMask" (:148). The other implementations do not have the pattern: FixedBits (FixedBits.java:34-35) and the two asserting wrappers in lucene/test-framework (AssertingLeafReader.java:1884-1888, AssertingLiveDocsFormat.java:98-101) delegate, and ReqExclBulkScorer's WindowBits (ReqExclBulkScorer.java:124-145) never calls nextSetBit. So four bodies fail.
  5. The default body (Bits.java:64-72), also printed in the javadoc as the reference loop (:54-62): for (int i = bitSet.nextSetBit(0); i != NO_MORE_DOCS; i = i + 1 >= bitSet.length() ? NO_MORE_DOCS : bitSet.nextSetBit(i + 1)). The increment is guarded against nextSetBit's precondition, the first call (:65) is not, so any empty window throws, at any offset. Fix site (and the javadoc loop, :55). Every Bits without an override uses it, for example Bits.MatchAllBits, and so did a reader's live docs in 10.4.0 to 10.5.2.

Executed on main (a site probe, assertions on and off): DenseLiveDocs, SparseLiveDocs and FixedBitSet over 64 documents return for applyMask(new FixedBitSet(0), offset) at offsets 0 and 64 and throw at 65 (DenseLiveDocs.java:165, SparseLiveDocs.java:153, FixedBitSet.java:908); new Bits.MatchAllBits(64) throws at 0, 64 and 65 (Bits.java:65); a 1-bit all-clear window at 65 returns; a real reader's live docs (64 documents, one deletion, committed) throw at maxDoc + 1. Why it looks unintended

#
  • The contract constrains only set bits, and an empty window has none: no documented outcome applies.
  • The overrides' comments allow offsets past the end, and they already return for an empty window at offsets 0 to 64.
  • The default loop guards its increment, not its first call, against nextSetBit's index < length() precondition, which Lucene leaves to callers.
The full argument327 words
  • Contract. Bits.java:43-45: "offset must be non-negative. For each index i into bitSet, if bitSet.get(i) is set then offset + i must be less than length()". An empty set has no set bit. For a set bit past the end the javadoc names two outcomes (Bits.java:46-49): IllegalArgumentException from FixedBitSet and the LiveDocs implementations (DenseLiveDocs.java:151-152 and SparseLiveDocs.java:141-142: "unless every set bit of bitSet at index i satisfies offset + i < maxDoc"), and an out-of-bounds get, undefined, from the default body. An empty window has no such bit and the default loop never reaches get, so neither applies; an AssertionError or ArrayIndexOutOfBoundsException from inside nextSetBit is documented nowhere.
  • Offsets past the end are expected. Both LiveDocs overrides: "Some scorers don't track maxDoc and may thus call this method with an offset that is beyond maxDoc" (DenseLiveDocs.java:156-157, SparseLiveDocs.java:146-147); FixedBitSet.applyMask carries the same note ending "beyond bitSet.length()" (FixedBitSet.java:901-902). Upstream TestLiveDocs.testApplyMaskOffsetBeyondMaxDoc (TestLiveDocs.java:735-755) asserts that an all-clear 2048-bit window past maxDoc is a no-op; only the 0-bit case breaks.
  • The reference loop guards the same precondition one line later. Its increment is i + 1 >= bitSet.length() ? NO_MORE_DOCS : bitSet.nextSetBit(i + 1) (Bits.java:57, :67); the first call is not guarded for length() 0.
  • Where the check belongs. On LUCENE-3449 (#4523) Michael McCandless kept nextSetBit's index < length() precondition: "I think performance trumps convenience here for these low level APIs". On LUCENE-6427 (#7486) Adrien Grand suggested that callers write bitSet.length() == 0 || bitSet.nextSetBit(0) == DocIdSetIterator.NO_MORE_DOCS; FixedBitSet.java:704 spells out the same idiom. In the review of #16452 (2026-08-12) javanna flagged new FixedBitSet(0) followed by nextSetBit(0) throwing ArrayIndexOutOfBoundsException in another class, and it was fixed.
  • History. #14134 added both bodies without discussing empty windows; #16593 copied the check into the overrides and its review covered javadoc wording only. No test uses a zero-length window and no CHANGES entry documents the throw.
The devil's-advocate check214 words

"The javadoc says implementations 'should behave the same way as the default implementation', and TestLiveDocs wraps the default as 'the specification that overrides must match'. That specification throws for every empty window, so past maxDoc the overrides behave as specified. Besides, FixedBitSet is @lucene.internal, Bits and LiveDocs are @lucene.experimental, the util package is 'primarily internal', and no Lucene reader or scorer builds an empty window where it fails." (Bits.java:51-52, TestLiveDocs.java:757-772, FixedBitSet.java:29, Bits.java:24, LiveDocs.java:39, util/package-info.java:35.) An independent reviewer from another model family (OpenAI GPT-5.6) made this argument after reproducing the failure with its own test and agreeing on the root cause and the fix.

Why it fails: the reference loop's unguarded first call is the same omission its guarded increment avoids, so it looks like an oversight rather than a design choice (whether to keep it as the specification is the maintainers' call), and the fix changes the reference and the overrides together. The overrides already return for an empty window at offset <= maxDoc, so they do not match the reference anyway. The stability tags warn about API changes; they are not input preconditions, and LeafReader.getLiveDocs() hands these objects to any caller. The argument is about impact, which is why the priority is Low.

Suggested fix

#

Recommended A. One zero-length guard per applyMask body, javadoc loop included (validated)

Guard each body for a zero-length window: add bitSet.length() > 0 && to the past-the-end check in DenseLiveDocs, SparseLiveDocs and FixedBitSet, and start the default loop (and its javadoc copy) with bitSet.length() == 0 ? NO_MORE_DOCS : bitSet.nextSetBit(0). The repro passes, and so do the closest suites (170 tests, 5 nightly skipped, 165 run) and the lint checks.

// Bits.java, default body and javadoc reference loop
for (int i = bitSet.length() == 0 ? DocIdSetIterator.NO_MORE_DOCS : bitSet.nextSetBit(0);
    i != DocIdSetIterator.NO_MORE_DOCS;
    i = i + 1 >= bitSet.length() ? DocIdSetIterator.NO_MORE_DOCS : bitSet.nextSetBit(i + 1)) {

// DenseLiveDocs, SparseLiveDocs and FixedBitSet applyMask
if (bitSet.length() > 0
    && length < bitSet.length()
    && bitSet.nextSetBit(Math.max(0, length)) != DocIdSetIterator.NO_MORE_DOCS) {
  throw new IllegalArgumentException("Some bits are set beyond the end of live docs");
}

B. Return early for an empty window

#

if (bitSet.length() == 0) return; at the top of each of the four bodies (and in the javadoc loop).

Trade-offs

Same behaviour as A, and also one comparison per call; arguably easier to read, slightly larger diff. By reading, not run.

Downstream note

#

Relevant downstream only to custom scorers or collectors that size their windows from a remaining range that can reach zero; such code avoids it by skipping empty windows.

How it was found

#

Semi-formal: a proof-obligation audit of Bits.applyMask's contract checked that every input the javadoc allows either returns or throws the documented IllegalArgumentException. An empty window past maxDoc meets the contract but reaches nextSetBit(0) on a zero-length set, and a one-test JUnit repro on stock main witnessed the exception.

The method in full119 words
  • Obligation: for every offset >= 0 and window bitSet whose set bits satisfy offset + i < maxDoc, applyMask returns after clearing the deleted documents' bits, and calls nextSetBit only with an index inside the window (FixedBitSet.java:413).
  • Finding: the check length < bitSet.length() (DenseLiveDocs.java:164, SparseLiveDocs.java:152, FixedBitSet.java:907) implies 0 <= max(0, length) < bitSet.length() only for a non-empty window; for a zero-length window past the end it reaches nextSetBit(0). The default loop's first call (Bits.java:65) has no check at all.
  • Witness: a JUnit test on stock main, a site probe of all four bodies, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Registry title
Bits.applyMask throws ArrayIndexOutOfBoundsException (AssertionError with -ea) on a zero-length destination FixedBitSet instead of doing nothing: the DenseLiveDocs and SparseLiveDocs overrides (a reader's live docs) and FixedBitSet.applyMask do so at an offset past the end, the default implementation at every offset, because each calls nextSetBit(0) on the empty set (latent: no Lucene code passes an empty destination; since 10.2.0)
Area
util / Bits.applyMask (DenseLiveDocs, SparseLiveDocs and FixedBitSet overrides, default implementation)
Priority
Low, rank 1245: Latent: applyMask on a reader's live docs or on a FixedBitSet throws ArrayIndexOutOfBoundsException (AssertionError with -ea) for an empty destination past the end, and the default implementation does so at any offset, where nothing should happen, in every release since 10.2.0. No Lucene reader or scorer was found to pass an empty destination where it fails, and the failure is loud with no wrong result, so only contrived outside code reaches it.
Impact class
minor
Impact note
Latent: hits only application or extension code that calls applyMask itself with a zero-length destination FixedBitSet, at an offset past maxDoc on a segment's live docs (DenseLiveDocs or SparseLiveDocs, what LeafReader.getLiveDocs() returns for a segment with deletions on 10.6.0 and main) or past length() on a FixedBitSet, or at any offset on a Bits that uses the default body (a reader's live docs on 10.4.0-10.5.2); the call throws ArrayIndexOutOfBoundsException with -da and AssertionError with -ea where a no-op is expected [exec]. No Lucene code path passes such an argument (the bulk scorers use fixed non-empty windows; AcceptDocs.createBitSet and FixedBitSet.copyOf pass offset 0, where the overrides return) [read]; the failure is loud, nothing is changed and no wrong result is returned; any index size; every release 10.2.0 through 10.6.0 [exec + read].
Summary
You call applyMask on a segment's live docs (LeafReader.getLiveDocs() of a segment with deletions) with an empty window past the end of the segment, for example liveDocs.applyMask(new FixedBitSet(0), maxDoc + 1). You expect nothing to happen: the Bits.applyMask contract only restricts set bits and an empty set has none, the overrides' own comments say callers may pass an offset beyond maxDoc, and the same call returns normally at offset maxDoc or with a 1-bit all-clear destination at maxDoc + 1. Instead it throws ArrayIndexOutOfBoundsException 'Index 0 out of bounds for length 0' (AssertionError 'index=0, numBits=0' with -ea), because the check for set bits past the end calls nextSetBit(0) on the zero-length set; the default Bits.applyMask, which the javadoc gives as the reference loop, starts with the same unguarded nextSetBit(0) and throws for an empty destination at every offset.
