The finding in 30 seconds

#

A range end that is the last year of a thousand-year block is printed as that block's first year.

How the date tree stores a range

#
  1. DateRangePrefixTree cuts time into nested cells: million-year blocks, thousand-year blocks (years 1000-1999, 2000-2999, ...), single years, then months, days and so on down to milliseconds.
  2. A range is a start cell and an end cell, each first replaced by the coarsest cell that means the same thing. An end of 1999-12-31 is the last day of 1999, and 1999 is the last year of 1000-1999, so the end becomes that thousand-year block.
  3. ISO dates have no way to write a thousand-year block, so the printer writes a block as a single year.

The finding, step by step

#
  1. Create new DateRangePrefixTree(DateRangePrefixTree.DEFAULT_CAL) and parse a decade: parseShape("[1990 TO 1999]"). The shape is right: it contains 1999-06-15, and searches with it match correctly.
  2. You expect shape.toString() to give a string that parseShape reads back as the same range, such as "[1990 TO 1999]": its javadoc says the result "should be parseable by parseShape(String)".
  3. Instead it prints "[1990 TO 1000]". The tree stores the end 1999 as the whole block 1000-1999, because 1999 is that block's last year, and the printer writes any block as its first year: right for a start, wrong for an end.
  4. Parsing that string throws IllegalArgumentException: Wrong order: 1990 TO 1000. When the start lies at or before the block's first year, it parses without error to a shorter range: [* TO 1999-12-31] prints "[* TO 1000]", which no longer contains 1500-06-15.
  5. Query toString shows the same text: queries built from [* TO 1999-12-31] and from its printed text both print queryShape=[* TO 1000] but are not equal. Matching, query equality and the index use the shape object and are unaffected.

Who is affected

#

Users of the opt-in, experimental DateRangePrefixTree (spatial-extras; Solr's DateRangeField is built on it) with ranges ending on the last year of a thousand-year block: 1999, 2999, 9999, 2999-12-31T23:59:59.999. Query toString and logs show the wrong end; code that stores the text and parses it again gets an exception or a shorter range.

Mechanism, terms and numbers767 words

DateRangePrefixTree (spatial-extras, @lucene.experimental) indexes date ranges. When a range's end is the last year of a thousand-year block (1999, 2999, ..., 9999, at any precision down to 1999-12-31T23:59:59.999) or of a million-year block (2 BC), the range normalization stores that end as the whole block, and toString prints the block as its first year. So [1990 TO 1999] prints as "[1990 TO 1000]", which parseShape rejects with Wrong order, and [* TO 1999-12-31] prints as "[* TO 1000]", which parses to a range that ends 999 years early. The shape object is right, so matching, equality and the index are unaffected; the wrong text shows in the prefix-tree queries' toString, in logs, and in any code that stores or forwards a range as text and parses it again. In every release since 5.0.0.

The mechanism (main 645d4fe14a20)

#
  1. The tree. Level 1 has 586 million-year cells, level 2 has 1,000 thousand-year cells in each, level 3 has 1,000 years in each (only the cells at the tree's maximum date are partial, getNumSubCells, DateRangePrefixTree.java:172-177), then months, days, hours, minutes, seconds and milliseconds (DateRangePrefixTree.java:128-140, YEAR_LEVEL = 3 at :102). The year count is offset by a whole number of million years (:153-154), so the thousand-year cells hold the years 0-999, 1000-1999, 2000-2999, ... (toShape, :315-322). 1999 is year 999, the last, of the cell 1000-1999.
  2. Parsing. parseShape("[1990 TO 1999]") parses both ends as cells and calls toRangeShape (NumberRangePrefixTree.java:205-215).
  3. Normalization. toRangeShape replaces each end with the coarsest equivalent cell: "this normalization/optimization process is actually REQUIRED based on assumptions elsewhere." (:118-119). truncateEndVals (:124, "chops off trailing max-vals"; :160-166) walks up while a value is the last one of its parent, so the end 1999 becomes the level-2 cell 1000-1999. The same holds for 1999-12, 1999-12-31 and so on down to 1999-12-31T23:59:59.999. An end of ISO year -1 (2 BC) or 999999 is the last year of a million-year cell and becomes that level-1 cell ([1 TO 999999] prints "[0001 TO 0000]", executed by the hunt's probe). The shape [1990, 1000-1999] covers exactly 1990-01-01 to 1999-12-31.
  4. Printing. SpanUnitsNRShape.toString prints both ends with the same per-cell printer (:399-406): "[" + toString(minLV) + " TO " + toString(maxLV) + "]".
  5. The per-cell printer. DateRangePrefixTree.toString(UnitNRShape) is toString(toCalendar(lv)) (DateRangePrefixTree.java:380-383). toCalendar adds up only the values the cell has (:357-363), so a level-2 cell gives the block's first year, at year precision (:364-370). The end 1000-1999 prints as 1000. For a range start that is right: [1000 TO 1998] round-trips.
  6. Re-parsing. parseShape("[1990 TO 1000]") throws IllegalArgumentException("Wrong order: ...") (NumberRangePrefixTree.java:126-129, documented at :114-115). If the start lies at or before the block's first year (*, 0500, 1000-03), there is no error and the range now ends on the last day of the block's first year: 999 years early, or about a million years for a million-year end cell.

Not part of this bug: a range that is exactly one block ([2000 TO 2999]) normalizes to a single cell and prints as "2000", which parses back as the single year 2000. The date syntax has no token for such a cell and an upstream test accepts a date-like string for a bare coarse cell, so that may be intended; the fix leaves it unchanged.

Exposure and likelihood328 words
  • Who. Applications that use DateRangePrefixTree from the opt-in spatial-extras module (@lucene.experimental), for example through NumberRangePrefixTreeStrategy. Downstream, Apache Solr's DateRangeField is built on it (read from Solr's code, not run).
  • Trigger. Either built-in calendar (DEFAULT_CAL or JAVA_UTIL_TIME_COMPAT_CAL) and ordinary input: decades or centuries ending in a year X999, [* TO 1999-12-31], and far-future open-end values such as 2999-12-31T23:59:59.999 or 9999. Deterministic, assertions on or off.
  • Misleading text. A query over [* TO 1999-12-31] prints queryShape=[* TO 1000] in IntersectsPrefixTreeQuery, ContainsPrefixTreeQuery and WithinPrefixTreeQuery toString; logs and debug output show a range that is not the one searched, and two different queries print identically.
  • Broken round trip. Code that keeps a range as toString() text and parses it later gets IllegalArgumentException when the start lies inside the end's block after its first year, and otherwise a range that silently ends 999 years early (about a million years for a million-year end cell: [* TO -1] prints "[* TO -1000000]", which parses without error). Over 452,984 legal ranges in two trees (the default and the java.time-compatible calendar; grids of 434 and 839 edge values), the hunt's exhaustive check found 10,430 silent interval mismatches and 4,655 parse exceptions, all with a block end (default tree: 2,464 and 1,477), and none with the fix (the grids are not a usage frequency).
  • Downstream reach (read, not run). Solr stores the client's input string for a DateRangeField value and uses shape.toString() only for values that arrive as a Shape object through the Java API; an atomic update of such a document re-parses that stored text.
  • Not affected. Matching, query equals/hashCode, caching and the index (CheckIndex passes on an index with the affected ranges). No extra cost: a parse-print-re-parse cycle takes 5.8 to 11.1 microseconds, flat.
  • How likely: plausible. Such range ends are ordinary, but the harmful half needs code that re-parses the text, and nothing was reported in the 11 years since 5.0.0.

Why it looks unintended

#
  • NRShape#toString: "The result should be parseable by parseShape(String)". "[1990 TO 1000]" is not parseable at all.
  • The class's author stated the intent on LUCENE-5648 (#6710): "you can round-trip toString() and parseShape() ... or a range".
  • Range optimization only swaps a range for an equivalent one (the upstream optimizer test's examples), and an exact string exists: the block's last year, 1999.
The full argument210 words
  • Contract. NRShape#toString: "The result should be parseable by {@link #parseShape(String)}." (NumberRangePrefixTree.java:84). parseShape: the range syntax "is the same thing as the toString() of the range shape, notwithstanding range optimization." (:199). The per-cell printer: "A string representation of the UnitNRShape that is parse-able by {@link #parseUnitShape(String)}." (:174-178).
  • Author's intent. On LUCENE-5648 (now #6710), David Smiley, who wrote the class, described a patch on 2014-05-21: "Parses calendar ranges. This means you can round-trip toString() and parseShape() wether it's a single Calendar value "2014-05" or a range "[- TO 2013]"." The NRShape#toString javadoc came with their refactoring of 2014-12-14.
  • The optimizer test's examples keep the meaning. TestDateRangePrefixTree.testShapeRangeOptimizer (:262-280) asserts exact strings of optimized ranges (strings only, not containment), each denoting the input range ([2014-01-01 TO 2014-12-31] prints "2014"); none has a block as its end.
  • An exact string exists. A thousand-year end block means "up to the end of its last year", which the syntax writes as 1999; the printer already gets the start case right ([1000 TO 1998] round-trips).
  • No acceptance found. No upstream test, CHANGES.txt or MIGRATE.md entry accepts a lossy or unparseable range string, and the prior-art searches found no issue or list thread that does.
The devil's-advocate check173 words

The strongest case for "intended": the thousand- and million-year levels are internal tree levels that ISO dates cannot express; "should be parseable" does not say "parses back to an equal shape"; "notwithstanding range optimization" admits a different string; the classes are @lucene.experimental; Lucene does not promise that Query#toString parses back; and TestDateRangePrefixTree.java:60 accepts a date-like string for a bare level-1 cell.

Why it fails: "[1990 TO 1000]" is not parseable at all, so even the weakest reading breaks; the optimization only replaces a range by an equivalent one, so it cannot license a string that means a shorter range; the author stated round-trip intent for ranges; and the line-60 test is a "test no underflow" check: level-1 cell 0 prints the full-precision minimum date -292269054-12-02T16:47:04.192 and only its BC sign is asserted, so it says nothing about range ends. Verifiers, the adjudication and the cross-model reviewer of the intended lens rejected the intended reading. Expect a maintainer to ask about the bare-block case; it is left out of this report on purpose.

Suggested fix

#

Recommended Print a block end cell as the block's last year (validated)

Print a thousand- or million-year cell that ends a range as the block's last year: a protected toStringAsRangeEnd hook in NumberRangePrefixTree, used for the end in SpanUnitsNRShape.toString, overridden in DateRangePrefixTree (+26/-1). Bare cells and starts print as before. It passes the repro and the whole spatial-extras module.

// NumberRangePrefixTree: new hook; SpanUnitsNRShape.toString uses it for maxLV
protected String toStringAsRangeEnd(UnitNRShape lv) { return toString(lv); }
// DateRangePrefixTree (condensed)
@Override
protected String toStringAsRangeEnd(UnitNRShape lv) {
  if (lv.getLevel() > 0 && lv.getLevel() < YEAR_LEVEL) { // a block prints as its LAST year
    int[] vals = new int[YEAR_LEVEL];
    for (int level = 1; level <= lv.getLevel(); level++) vals[level - 1] = lv.getValAtLevel(level);
    for (int level = lv.getLevel(); level < YEAR_LEVEL; level++)
      vals[level] = getNumSubCells(toShape(vals.clone(), level)) - 1;
    return toString(toCalendar(toShape(vals, YEAR_LEVEL)));
  }
  return toString(lv);
}

Print a block end cell as the block's last year (validated) (recommended)

#

The change is +26/-1 lines in NumberRangePrefixTree.java and DateRangePrefixTree.java. SpanUnitsNRShape.toString prints its end with a new protected toStringAsRangeEnd(UnitNRShape), which defaults to toString(lv). DateRangePrefixTree overrides it: a million- or thousand-year cell is filled down to the year level with each level's last child (getNumSubCells(...) - 1, which also handles the partial last million-year block) and printed as that year. [1990 TO 1999] then prints as itself, [-9999 TO -1] as "[-9999 TO -0001]", [* TO 1999-12-31] as the equivalent "[* TO 1999]".

// NumberRangePrefixTree: new hook; SpanUnitsNRShape.toString uses it for maxLV
protected String toStringAsRangeEnd(UnitNRShape lv) { return toString(lv); }
// DateRangePrefixTree (condensed)
@Override
protected String toStringAsRangeEnd(UnitNRShape lv) {
  if (lv.getLevel() > 0 && lv.getLevel() < YEAR_LEVEL) { // a block prints as its LAST year
    int[] vals = new int[YEAR_LEVEL];
    for (int level = 1; level <= lv.getLevel(); level++) vals[level - 1] = lv.getValAtLevel(level);
    for (int level = lv.getLevel(); level < YEAR_LEVEL; level++)
      vals[level] = getNumSubCells(toShape(vals.clone(), level)) - 1;
    return toString(toCalendar(toShape(vals, YEAR_LEVEL)));
  }
  return toString(lv);
}

Trade-offs

  • Changes only the printed end of a SpanUnitsNRShape whose end is a million- or thousand-year cell; bare cells and range starts are unchanged, so TestDateRangePrefixTree.java:60 and the optimizer test still hold. Other NumberRangePrefixTree subclasses keep the default.
  • Affects toString only; nothing on the indexing or search path.
  • Adds one protected method to an @lucene.experimental class.

The same rule at another fix site (not written)

#

A maintainer may prefer a range-aware printer inside DateRangePrefixTree, or a SpanUnitsNRShape.toString that asks the tree for the last year of a cell (suggested by the adjudication and a verifier). That moves the code, not the behaviour. Any variant must keep toString(UnitNRShape) printing a bare cell as a unit, as its javadoc requires ("parse-able by parseUnitShape").

Rejected: print every block as a range, or stop truncating the end

#

Printing a bare block as "[first TO last]" (the finder's first variant) breaks the upstream assertion at TestDateRangePrefixTree.java:60 and the unit-string contract of toString(UnitNRShape). Not truncating the end changes the stored shape, its equality and its indexed cells, and the normalization is "REQUIRED based on assumptions elsewhere" (NumberRangePrefixTree.java:118-119); not tried.

Downstream note

#

An application that keeps an exclusion rule as this text and rebuilds it with parseShape would hide fewer documents (a deny rule [* TO 1999-12-31] rebuilt from "[* TO 1000]" stops hiding 1500-06-15); no product is known to do this.

How it was found

#

A hunt on spatial-extras' range trees printed every legal range over edge-date grids of two trees (both built-in calendars; BC, leap and far-future years, every precision), parsed the text again and compared it with a java.time reference. All 15,085 failures of this kind had a thousand- or million-year end; the finder then reduced them to a JUnit.

The method in full140 words

Bounded-exhaustive translation validation of the stock jar: for every legal [a TO b] range over 839 edge units of the java.time-compatible tree (31 years including BC, leap and >9999 years, at every precision; 356,472 ranges) and 434 edge units of the default tree (16 years from 1583; 96,512 ranges), 452,984 ranges in all, the harness re-parses toString() and compares the re-parsed interval with a proleptic-Gregorian java.time reference. It found 10,430 interval mismatches and 4,655 parse exceptions (default tree: 2,464 and 1,477), all with a thousand- or million-year END cell, with assertions on and off; both kinds disappear with the fix. The finder then wrote a three-line public-API JUnit, and the hunt later cut it to the one-input test shown here.

The harness's other mismatch kinds belong to other leads of the same hunt and are not part of this bug.

LFV-610, snapshot of 2026-11-03

Registry title
DateRangePrefixTree prints a date range whose end is the last year of a thousand- or million-year block (a year X999, or 2 BC) with that end shown as the block's FIRST year, e.g. [1990 TO 1999] prints as "[1990 TO 1000]", so parseShape rejects the printed string ('Wrong order') or reads it as a much shorter range ([* TO 1999-12-31] prints as "[* TO 1000]")
Area
spatial-extras / prefix trees (DateRangePrefixTree / NumberRangePrefixTree range-shape string form: SpanUnitsNRShape.toString of a range whose end normalizes to a thousand- or million-year cell; also shown in the 'queryShape=' part of the prefix-tree queries' toString)
Priority
Low, rank 714: DateRangePrefixTree prints ranges that end on a block's last year with the wrong end, which breaks the toString round trip while queries stay correct, so it sits with the niche toString round-trip row LFV-356.
Impact class
minor
Impact note
Hits applications that use the opt-in, @lucene.experimental DateRangePrefixTree of the spatial-extras module (in practice also Solr's DateRangeField, which is built on it) and print, log, store or forward a range shape whose end is the last instant of a year X999 or of 2 BC, with ordinary input and no scale ([1990 TO 1999], [* TO 1999-12-31], [2014 TO 2999], [2020 TO 9999]): matching, query equality and the index are correct because they use the shape object, but the shape's toString and the 'queryShape=' part of IntersectsPrefixTreeQuery / ContainsPrefixTreeQuery / WithinPrefixTreeQuery toString show the wrong end, and code that parses the string again gets IllegalArgumentException 'Wrong order' or, more often, a range that silently ends up to 999 years early (about a million years for an end of 2 BC); deterministic, -ea and -da, every release since 5.0.0.
Summary
You parse an ordinary date range such as [1990 TO 1999] with DateRangePrefixTree.parseShape and print it, expecting a string that parseShape reads back as the same range, as NRShape#toString promises ('The result should be parseable by parseShape(String)'). Instead it prints "[1990 TO 1000]", which parseShape rejects with IllegalArgumentException 'Wrong order', and [* TO 1999-12-31] prints as "[* TO 1000]" ([1990 TO 2999] as "[1990 TO 2000]"), which parses without error to a range that ends up to 999 years early. Range normalization turns an end of 1999 into the thousand-year cell 1000-1999 (an end of 2 BC into a million-year cell), and the per-cell printer writes a cell as its FIRST year, which is right for a range start but wrong for a range end; searches are unaffected, only the text is wrong.
