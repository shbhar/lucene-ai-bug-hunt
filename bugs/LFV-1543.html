The finding in 30 seconds

#

Contrived trigger: the InfoStream must throw at the one message rollback; by reading no InfoStream of lucene-core throws there by itself. Run through rollback() on 25 releases from 2.9.4 to 10.6.0, through close() on 10 of them from 4.10.0 on, and on branch_11x and main; before 4.7.1 only a later close() waits. Interrupt run on 9.1.0, 10.6.0 and both branches.

Background: three pieces

#
  1. An IndexWriter takes the directory's write lock (write.lock) when it is opened and holds it until it is closed. While the lock is held, no other IndexWriter can be opened on that directory.
  2. close() commits (commit on close is the default) and then runs the rollback step, the code that lets go of everything the writer holds, the write lock included. rollback() runs the same step without the commit.
  3. The InfoStream is the writer's diagnostic log. It is off by default; an application turns it on with IndexWriterConfig.setInfoStream (or, for every configuration made afterwards, with the static InfoStream.setDefault). The writer hands it short messages, such as rollback when the rollback step begins.

The finding, step by step

#
  1. Turn on IndexWriter's diagnostic log with a stream that fails at one message: new IndexWriterConfig().setInfoStream(stream), where stream throws RuntimeException("BOOM!") when the message is rollback. Open a writer on an empty ByteBuffersDirectory. The test adds no document; the program behind the numbers below adds 1.
  2. Call close(). It commits, then logs rollback as it starts to release its resources. The stream throws, so close() throws BOOM!. For that case the javadoc of close() says "the IndexWriter will be closed", and that close() "releases the write lock".
  3. Instead the writer is left closing, not closed. dir.obtainLock("write.lock") and new IndexWriter(dir, ...) throw LockObtainFailedException; addDocument and commit throw AlreadyClosedException.
  4. A second close() or rollback() does not return: still waiting after 5 s in the runs, ended by ThreadInterruptedException when its thread was interrupted, the lock still held. One shape differs: after a rollback() that threw with a prepareCommit() pending, a later close() throws IllegalStateException instead (commit on close on, the default).
  5. Nothing is lost: the last commit opens and has that 1 document. The same throw at the next rollback message (rollback: done finish merges) leaves a closed writer and a free lock. The first message stands in front of the try that does the cleanup; the later ones are inside it.

Who is affected

#

Only an application that turns on IndexWriter's InfoStream, when the stream throws at the message rollback during close() or rollback(), a contrived trigger. In that JVM a new writer on the directory fails; closing again waits until interrupted (in one shape it throws instead). Loud first failure, no index damage. By reading, no InfoStream of lucene-core throws there by itself.

Mechanism, terms and numbers1,607 words

Small, and the trigger is contrived. IndexWriter's InfoStream is its diagnostic log. It is off by default (LiveIndexWriterConfig.java:142, lines at main 1ae70c6e45b8), an application turns it on (with IndexWriterConfig.setInfoStream, or for every configuration made afterwards with the static InfoStream.setDefault), and for this failure it must throw at the one message rollback. By reading, no InfoStream of lucene-core throws there by itself; in the runs the exception came from the test's or the program's own code (its stream, or in one earlier check its logging Handler). The first failure is loud, the index is not damaged and its last commit opens.

close() and rollback() both end in the rollback step, rollbackInternalNoCommit. Before it, shouldClose has set closing = true (IndexWriter.java:1379). The step's first statement logs rollback (:2602-2604), in front of the try at :2617. Only the end of that try (:2684) and its handler (:2709-2710) close the write lock and run the small cleanup closure (:2606-2615) that sets closed and resets closing. An exception from the log call skips both.

What is left is a writer that is closing and not closed. The write lock is still held, so Directory.obtainLock("write.lock") and a new IndexWriter on that directory throw LockObtainFailedException; addDocument and commit throw AlreadyClosedException; a second close() or rollback() waits in shouldClose (still waiting after 5 s in the runs) and ends with ThreadInterruptedException when its thread is interrupted, the lock still held. One shape does not wait: after a rollback() that threw while a prepareCommit() was pending, a later close() throws IllegalStateException when commit on close is on (the default).

The javadoc of close() says "Closes all open resources and releases the write lock." and, in its paragraph about commit on close, "If this method throws any other exception, the IndexWriter will be closed, but changes may have been lost." (:1342, :1351-1352). Lucene's own test testExceptionDuringRollback throws from an InfoStream at the next rollback message or at a test point and asserts a closed writer and a free lock; run, the same throw at the next rollback message does leave both. No javadoc sentence says what happens when an InfoStream throws, so a maintainer may call the repair hardening.

What was run where: through rollback() on 25 releases from 2.9.4 to 10.6.0, through close() on 10 of them from 4.10.0 on, and on builds of branch_11x and main. Before 4.7.1 only a later close() waits (a second rollback() throws AlreadyClosedException). The interrupt was run on 9.1.0, 10.6.0, branch_11x and main. The pending-commit shape was run on 10.6.0, branch_11x and main. The statement has stood in front of the try since a logging-only commit of 2010-11-11. One change was validated through Lucene's own build (the test, the IndexWriter suites, the core module's tests and its lint): the log call moved into the try.

The steps in the code (IndexWriter.java at main 1ae70c6e45b8)

#
  1. Who closes. close() calls shutdown() when commit on close is on and rollback() otherwise (:1363-1369). Both begin with shouldClose(true) (:1319, :2581). For the first caller it sets closing = true (:1374-1380); a later caller waits in doWait() as long as closing is set and closed is not (:1383-1387).
  2. The commit of close(). shutdown() logs now flush at close, flushes, waits for merges and commits (:1321-1327), then calls rollbackInternal() (:1337). If that first part throws, its handler calls rollbackInternal() as well and adds what it throws as suppressed (:1328-1336).
  3. The first statement of the rollback step. rollbackInternalNoCommit() begins with if (infoStream.isEnabled("IW")) { infoStream.message("IW", "rollback"); } (:2602-2604). The try begins at :2617.
  4. The only reset of the closing flag. The closure cleanupAndNotify sets writeLock = null, closed = true and closing = false and calls notifyAll() (:2606-2615). It runs, together with the close of the write lock, at the end of the try (:2684) or from its handler (:2709-2710), which also closes the merge scheduler, the reader pool and the deleter and rolls back a pending commit (:2691-2710). closing = false is assigned nowhere else in the file.
  5. The throw. An exception at :2602-2603 leaves the method in front of the try, so neither place runs: closing stays true, closed stays false, and the write lock is not closed.
  6. What later calls see. ensureOpen() throws AlreadyClosedException while closing is set (:913-917, :927-929), which is what commit (:4240-4242) and addDocument (through updateDocuments, :1625-1629) do. isOpen() is false (:6527-6529). A later shouldClose(true) loops on doWait(), a wait(1000) that an interrupt ends with ThreadInterruptedException (:6269-6281) without changing the flag.
  7. The pending-commit shape. shutdown() checks pendingCommit in front of shouldClose(true) (:1313-1316), and the throw has skipped the two places of the rollback step that clear a pending commit (:2642-2650 inside the try, :2697-2705 in its handler). So a later close() with commit on close on throws IllegalStateException there; with commit on close off it goes through rollback() (:1367) and waits.
  8. The neighbours. The step's two later log messages (:2625-2627, :2660-2662) and its test point (:2664) are inside the try, so a throw there takes the handler.

What is not lost, a second process, and what was not run

#

Through close() with one throw, the commit of close() is already made: the last commit opens with the document, and CheckIndex on a copy of the directory's files reports it clean (on the directory itself CheckIndex cannot take the write lock). A second process was run on an FSDirectory (main 1ae70c6e45b8, branch_11x b98f116b3179 and the 10.6.0 jars). With the default lock factory, while the JVM with the stuck writer was alive a second JVM opened the last commit and its new IndexWriter threw LockObtainFailedException; after the first JVM had ended, a new JVM opened and closed a writer. Why it looks unintended

#
  • The close() javadoc (commit on close, the default): "If this method throws any other exception, the IndexWriter will be closed".
  • Lucene's test throws from an InfoStream at the next rollback message (or a test point) and asserts a closed writer and free lock; run, that holds.
  • No javadoc says whether an InfoStream may throw: the repair may be called hardening.
The full argument381 words
  • The javadoc of close() (IndexWriter.java:1341-1361). Its first sentence: "Closes all open resources and releases the write lock." For commit on close, which is the default and the test's configuration, it names two cases: a prepareCommit without commit throws IllegalStateException "and the IndexWriter will not be closed"; and "If this method throws any other exception, the IndexWriter will be closed, but changes may have been lost." The stream's RuntimeException is such an other exception, and the writer is not closed.
  • Lucene's own test of the neighbouring statements. TestIndexWriterExceptions#testExceptionDuringRollback (TestIndexWriterExceptions.java:1980-2052) throws RuntimeException("BOOM!") from an InfoStream at the next rollback message (rollback: done finish merges) or at the test point rollback before checkpoint, then asserts iw.isClosed() and takes the write lock, under the comment "even though we hit exception: we are closed, no locks or files held, index in good state". Its first line reads "currently: fail in two different places". The test on this page is the same technique at the one message in front of the try.
  • Two more tests on the same rule. testOutOfMemoryErrorCausesCloseToFail (:1111-1147) throws an OutOfMemoryError from the stream one message earlier (now flush at close) and requires that a second close() returns. testOnlyRollbackOnceOnException (:2195-2235) puts a writer whose rollback() throws into a try-with-resources block, whose implicit close() must return.
  • CHANGES. "LUCENE-4246: IndexWriter.close now always closes, even if it throws an exception." (lucene/CHANGES.txt:11499-11501); "LUCENE-5544: Exceptions during IndexWriter.rollback could leak file handles and the write lock." (:12826-12827, under the bug fixes of 4.7.1).
  • History. The try and the reset of the closing flag came with LUCENE-1347 (2008: "fix hang in rollback() after previous rollback() call hit exception"). A logging-only commit put the log statement in front of it in 2010. LUCENE-5544 (2014) and #12751 (2023) repaired the handler of that try; the statement stayed where it was.
  • The control. At the next rollback message the same throw closes the writer and frees the lock (run through close() and through rollback()).
  • What no text says. The javadoc of rollback() says nothing about the writer's state after an exception (:2566-2574; its one @throws line names a low-level I/O error), and neither InfoStream nor setInfoStream says whether a stream may throw.
The devil's-advocate check226 words

The strongest case for "intended": InfoStream is described as a "Debugging API" and tagged @lucene.internal; PrintStreamInfoStream and JavaLoggingInfoStream carry the same tag. It is off by default, by reading no InfoStream of lucene-core throws at this statement by itself, and IndexWriter has no general guard around its log calls (one of them, in onTragicEvent, is guarded). Lucene's test that throws from an InfoStream can be read as a tool that injects a failure inside the step, not as a statement that a stream that throws is supported. So a stream that throws is a broken application component, and Lucene promises nothing about a writer whose debugging hook failed.

Why it fails: the argument is about how likely the trigger is, and that is why the finding is Low. It does not make the outcome intended. The close() javadoc speaks of "any other exception" and names no source. The project's own tests throw from an InfoStream inside the rollback step and require a closed writer and a free lock, and the same throw at the step's next log statement gives exactly that. The exception reaches the caller in both cases; only the cleanup differs. What stays of the argument limits the weight: the maintainers may call the repair hardening, and a javadoc sentence that an InfoStream must not throw would be a fair outcome too.

Suggested fix

#

Recommended Move the log call into the try (validated)

Move the three lines of the log call into the try, as its first statement: a throw there then takes the handler that closes the writer and releases the lock. Validated on main 1ae70c6e45b8 through Lucene's own build: the test passes, and the 21 IndexWriter suites, the core module's 8,962 tests and its lint show no failure.
