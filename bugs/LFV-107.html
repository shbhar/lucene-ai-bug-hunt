ByteBuffersDataOutput.copyBytes narrows its length to int: a copy of 2 GiB or more silently copies nothing or only part

Since 9.3.0, ByteBuffersDataOutput.copyBytes keeps its long length in an int, so a copy of 2 GiB (2^31 bytes) or more copies nothing, or only part, and returns normally. A 2 GiB file copied into a ByteBuffersDirectory arrives empty; a copied index then fails to open.

The finding in 30 seconds

#

copyBytes keeps the number of bytes still to copy in an int. From 2^31 bytes on, that int is negative (or a smaller, wrong number), so the copy stops at once and the method returns having copied nothing, or only part.

Background: in-heap outputs and copyBytes

#
  1. ByteBuffersDataOutput is Lucene's in-heap output: it appends bytes to a list of ByteBuffer blocks and can hold more than 2 GiB (size() is a long). ByteBuffersDirectory keeps each file in one of them.
  2. DataOutput.copyBytes(input, numBytes) reads numBytes bytes from an input and writes them to the output; numBytes is a long. Directory.copyFrom uses it to copy a whole file.
  3. A Java int holds at most 2,147,483,647 (2^31-1). Casting a larger long to int keeps only its low 32 bits: 2^31 becomes -2,147,483,648, and 2^32+5 becomes 5.

The finding, step by step

#
  1. You copy 2^31 = 2,147,483,648 bytes into an in-heap ByteBuffersDataOutput: out.copyBytes(in, 1L << 31). Directory.copyFrom makes the same call when a ByteBuffersDirectory receives a file of 2 GiB or more, for example in IndexWriter.addIndexes(Directory...).
  2. You expect out.size() to be 2,147,483,648: copyBytes promises to "Copy numBytes bytes from input to ourself", and Lucene 9.2.0 does exactly that.
  3. But the method starts with int length = (int) numBytes;, which is -2,147,483,648. The copy loop and its fallback run only while length > 0, so it returns at once: no byte read, no exception, with assertions on or off.
  4. You get out.size() 0. Every length from 2^31 to 2^32-1 copies nothing; 2^32+5 copies 5 bytes.
  5. Through addIndexes, a 2,169,703,755-byte _0.fdt arrives as an empty file and commit() succeeds; the next DirectoryReader.open throws CorruptIndexException.

Who is affected

#

Code that copies one file or stream of 2 GiB or more into a ByteBuffersDataOutput, ByteBuffersIndexOutput or ByteBuffersDirectory, for example to load an on-disk index into heap with copyFrom or addIndexes. Opt-in (the default FSDirectory is not affected) and extreme scale for a directory documented for small indexes, but silent at copy time.

Mechanism, terms and numbers570 words

ByteBuffersDataOutput.copyBytes(DataInput input, long numBytes) begins with int length = (int) numBytes; (ByteBuffersDataOutput.java:314 on main 645d4fe14a20). Both the loop that reads straight into the block arrays and the fallback to the long-safe base method run only while that int is positive, and the only check, assert numBytes >= 0, tests the long. So the method copies max(0, (int) numBytes) bytes and returns normally: every length up to Integer.MAX_VALUE is correct, every length from 2^31 to 2^32-1 copies nothing, and 2^32+5 copies 5 bytes. The rest of the input is left unread.

ByteBuffersIndexOutput.copyBytes delegates to it, and ByteBuffersDirectory.copyFrom (from BaseDirectory) copies a file with os.copyBytes(is, is.length()). A file of 2 GiB or more copied into a ByteBuffersDirectory therefore comes out empty or short, with no error. Through IndexWriter.addIndexes(Directory...) into a ByteBuffersDirectory, the copy and commit() succeed and the next DirectoryReader.open throws CorruptIndexException. The override came with LUCENE-10657 (#1034) in 9.3.0 as an optimisation; 9.2.0 copied correctly. Every release from 9.3.0 to 10.6.0 and main is affected; the default FSDirectory outputs are not. The fix is two lines.

The bug, step by step (main 645d4fe14a20, under lucene/core/src/java/org/apache/lucene/)

#
  1. The narrowing. store/ByteBuffersDataOutput.java:311-332: int length = (int) numBytes; (:314), then while (length > 0) { ... } (:315) copies chunk by chunk straight into the current block's array, and if (length > 0) super.copyBytes(input, length); (:329-331) handles blocks without an array. When (int) numBytes <= 0 both are skipped. The only check, assert numBytes >= 0 (:313), tests the long.
  2. What it overrides. DataOutput.copyBytes counts down a long left in 16 KiB chunks and is correct for any length (store/DataOutput.java:280-293). ByteBuffersDataOutput inherited it until 9.3.0.
  3. How users reach it. ByteBuffersIndexOutput.copyBytes delegates (store/ByteBuffersIndexOutput.java:139-143). ByteBuffersDirectory extends BaseDirectory (store/ByteBuffersDirectory.java:50), whose copyFrom calls copyThroughCreateOutput (store/BaseDirectory.java:54-58), which does os.copyBytes(is, is.length()) (store/Directory.java:189-197, line 193). IndexWriter.addIndexes(Directory...) (index/IndexWriter.java:3103) copies each segment file with directory.copyFrom in copySegmentAsIs (:3648, :3692); that directory is the writer's LockValidatingDirectoryWrapper (:958), whose copyFrom checks the lock and delegates (store/LockValidatingDirectoryWrapper.java:47-51). Wrapped destinations reach the same method too (code reading, not run): FilterDirectory.copyFrom goes through its own createOutput (store/FilterDirectory.java:126-128), FileSwitchDirectory.copyFrom delegates to the directory chosen for the file (store/FileSwitchDirectory.java:241-244), and NRTCachingDirectory, a FilterDirectory, writes into an internal ByteBuffersDirectory when the IOContext size estimate fits both maxMergeSizeMB and maxCachedMB (store/NRTCachingDirectory.java:72-84, :155-165, :231-245; for addIndexes the estimate is the whole segment, index/IndexWriter.java:3174-3175), so it needs both limits set above the segment's size.
  4. Not affected. Outside test code, the only copyBytes(DataInput, long) overrides in Lucene are this one, the delegating ByteBuffersIndexOutput and EndiannessReverserDataOutput (backward-codecs), and the base method; the FSDirectory family writes through outputs that inherit the long-safe base method. Copying from a ByteBuffersDirectory to disk is fine.

Exposure and likelihood307 words
  • Who is hit. A direct copyBytes call of 2^31 bytes or more on a ByteBuffersDataOutput or ByteBuffersIndexOutput; Directory.copyFrom of a file of 2 GiB or more into a ByteBuffersDirectory; IndexWriter.addIndexes(Directory...) with a ByteBuffersDirectory as the writer's directory and a source file of 2 GiB or more. That is the "load an on-disk index into RAM" pattern; LUCENE-8624 (#9670) was reported by a user indexing large data sets with ByteBuffersDirectory.
  • Default vs opt-in. Opt-in: the default directory (FSDirectory.open) and copies from a ByteBuffersDirectory to disk are not affected. Nothing else needs to be configured once the destination is heap-based.
  • Scale. One copy of 2^31 bytes or more; every smaller copy is correct.
  • What goes wrong. Deterministic and silent at copy time, with assertions on and off. A directly copied stream or a copied non-index file is empty or truncated with no error. A copied index commits normally and fails only at the next DirectoryReader.open, away from the copy that caused it. The source is never modified, and on this path search results are never silently wrong.
  • Likelihood: contrived. ByteBuffersDirectory is @lucene.experimental; its javadoc says MMapDirectory "is nearly always a better choice" and a heap-based directory can have the advantage for "ephemeral, small, short-lived indexes" (store/ByteBuffersDirectory.java:43-48); lucene/MIGRATE.md says it is "discouraged in favor of the default MMapDirectory". No public report was found in about four years of affected releases.
  • Not claimed: a second caller. The default terms-index builder TrieBuilder.append (10.5.0 and later) bulk-copies a sub-trie buffer with this method (codecs/lucene103/blocktree/TrieBuilder.java:153-156). At unit level (package-private API), appending a 2,176,663,776-byte sub-trie kept 3 of 68,003 entries, a 32 MB control kept all, and the fix kept all 68,003. It was not reproduced through IndexWriter, so it is not part of this report; the same two-line fix covers it.

Why it looks unintended

#
  • DataOutput.copyBytes takes a long and promises to "Copy numBytes bytes"; the base method it overrides works for any length.
  • The class can hold more than 2 GiB: size() is a long, and toArrayCopy() throws a clear error rather than drop data.
  • 9.2.0 copies 2^31 bytes correctly, and the same cast was fixed in the sibling BytesStore.copyBytes in review (#1047).
The full argument307 words
  • The contract. DataOutput.copyBytes: "Copy numBytes bytes from input to ourself." (DataOutput.java:280), with a long parameter and a base loop on a long (:281-293). Directory.copyFrom: "Copies an existing {@code src} file from directory {@code from} to a non-existent file {@code dest} in this directory." (Directory.java:174-175). Neither states a size limit.
  • The class handles more than 2 GiB. ByteBuffersDataOutput.size() returns a long (:349); toArrayCopy() documents and throws a RuntimeException when "the {@link #size()} of the underlying buffers exceeds maximum size of Java array" (:285-298).
  • A regression of an optimisation. LUCENE-10657 (#1034, CHANGES 9.3.0 "Optimizations": "CopyBytes now saves one memory copy on ByteBuffersDataOutput") added the override; its issue names IndexWriter#copySegmentAsIs -> copyFrom -> copyBytes, a whole-file copy, as a target. The review covered the fallback for non-heap buffers and arrayOffset, not the length type; its two tests copy about 8 KiB. 9.2.0, which inherits the base method, copies 2^31 bytes correctly (executed).
  • The sibling fix. In #1047 (LUCENE-10661, the same author's BytesStore.copyBytes override, a week later), reviewer jpountz wrote "We could make len a long and avoid the unchecked cast, couldn't we?", and BytesStore got a long len with a per-chunk (int) Math.min(...), the fix proposed here. ByteBuffersDataOutput was not revisited.
  • Precedent. LUCENE-8624 (#9670, an int overflow in ByteBuffersDataOutput.size()) and LUCENE-8625 (#9671, ByteBuffersDataInput.sliceBufferList) were fixed as bugs in 7.7.0 (CHANGES 7.7.0 "Bug fixes"); LUCENE-8628 (#9674) was closed as a duplicate report of the same overflow.
  • No test tolerates it. We found no upstream test that copies 2^31 bytes or more. The two tests added with the override copy about 8 KiB (TestByteBuffersDataOutput.java:201-233). BaseDirectoryTestCase, which also runs for ByteBuffersDirectory (TestByteBuffersDirectory.java:34), copies files of at most 1,777,777 bytes, in chunks of up to 77,777 bytes (testCopyBytes, BaseDirectoryTestCase.java:799-837).
The devil's-advocate check127 words

The strongest case: ByteBuffersDirectory is experimental and its javadoc points to "ephemeral, small, short-lived indexes", MIGRATE.md discourages it in favour of MMapDirectory, nobody should hold 2 GiB files in heap buffers, and an index copied this way does fail loudly when it is opened.

Why it fails: that is usage advice, not a documented size precondition, and it says nothing about ByteBuffersDataOutput, a public class that is not marked experimental. The method keeps a long signature and returns normally after copying nothing, where 9.2.0 did the copy. "Fails at open" covers only index files, and only later; direct callers and other files get no error at all. The cross-model reviews rated the "intended" case weak, and the devil's advocate verifier and the adjudication rejected it.

Suggested fix

#

Recommended Keep the remaining count in a long (2 lines)

Keep the remaining count in a long and cast only each chunk: long length = numBytes; and int chunk = (int) Math.min(currentBlock.remaining(), length);. With these two lines the test passes (assertions on and off, 4 GB test heap), and the store tests, TestTrie and :lucene:core:check -x test pass.

Keep the remaining count in a long (2 lines) (validated by the checks) (recommended)

#

Each chunk is at most currentBlock.remaining(), an int, so the per-chunk cast is safe, and the fallback super.copyBytes(input, length) already takes a long. This is the pattern BytesStore got in #1047, and the same two lines as the finder's and the independent reproducer's fixes. The study's Z3 model of the copy count does not encode the loop, so it adds nothing here beyond "a long count does not narrow"; the evidence for the fix is the code and the executed tests.

@@ -314 +314 @@ public void copyBytes(DataInput input, long numBytes)
-    int length = (int) numBytes;
+    long length = numBytes;
@@ -322 +322 @@
-      int chunk = Math.min(currentBlock.remaining(), length);
+      int chunk = (int) Math.min(currentBlock.remaining(), length);

Trade-offs

No change for copies below 2 GiB (same code path); copies of 2 GiB or more now really copy and need the heap for it. The one-copy optimisation is kept. Not fixed by it (code reading, not run): a ByteBuffersDirectory built with the non-default OUTPUT_AS_ONE_BUFFER (also OUTPUT_AS_BYTE_ARRAY) factory still cannot keep a file of 2 GiB or more, because closing the output calls toArrayCopy(), which throws (ByteBuffersDirectory.java:64-81, :264-266; ByteBuffersDataOutput.java:285-298). That failure is loud; the default OUTPUT_AS_MANY_BUFFERS (ByteBuffersDirectory.java:111) has no such limit.

Hand copies of 2 GiB or more to the base method (not run)

#

if (numBytes > Integer.MAX_VALUE) { super.copyBytes(input, numBytes); return; } before the loop.

Trade-offs

Correct by construction (the base method is long-safe) and small, but copies of 2 GiB or more lose the one-copy optimisation, and the int arithmetic stays for the next reader to wonder about.

Throw instead of truncating (not run)

#

int length = Math.toIntExact(numBytes); throws ArithmeticException for 2^31 or more.

Trade-offs

Removes the silent part (the adjudication listed it as acceptable), but rejects copies that 9.2.0 performed and that the class otherwise supports, so copyFrom of a large file into a ByteBuffersDirectory would still not work.

Downstream note

#

Products that load an on-disk index with a file of 2 GiB or more into heap through ByteBuffersDirectory see that file copied empty, or a CorruptIndexException at the next open, far from the copy that caused it.

How it was found

#

Code reading while reviewing Lucene's DataInput and DataOutput implementations spotted the (int) numBytes cast. A small Z3 bit-vector model of the copy count then gave the affected lengths (smallest 2^31); a public-API JUnit test confirmed it on the stock jar.

The method in full199 words

Method: non-formal (code reading), with an SMT model used to characterise the inputs, not to find the bug.

  • The finder reviewed ByteBuffersDataOutput as part of a hunt unit on DataInput/DataOutput implementations and strings, and noticed that the copyBytes override narrows its long length.
  • A Z3 bit-vector model of the copy count (5 queries) encodes the override as copying max(0, (int) numBytes) bytes. In that model it found the minimal failing length 2^31, showed every length up to Integer.MAX_VALUE correct, found lengths in [2^31, 2^32) that copy nothing (every such length casts to a negative int) and larger lengths that copy part of the request. Its fix query only confirms that a long count has no narrowing: the model does not encode the copy loop, so the fix rests on the code (each chunk is at most remaining()) and the executed tests.
  • A public-API JUnit on the stock jar (a direct copy, and ByteBuffersDirectory.copyFrom of a sparse 2^31+7-byte file) failed on main with assertions on and off. A cross-model reviewer, an independent reproducer, a second cross-model reviewer, a devil's advocate verifier and an adjudication then confirmed it, and the repro was later cut to the one test above.

Impact note
Applications that copy a single file or stream of 2 GiB or more into an in-heap ByteBuffersDataOutput, ByteBuffersIndexOutput or ByteBuffersDirectory (a direct copyBytes call, Directory.copyFrom, or IndexWriter.addIndexes(Directory...) into a ByteBuffersDirectory-backed writer); non-default directory (the default FSDirectory outputs use the long-safe base copyBytes), extreme scale (one copy of 2^31 bytes or more), deterministic and silent with -ea and -da: direct callers and copied non-codec files end up empty or truncated, and a copied index commits normally but fails at the next DirectoryReader.open with CorruptIndexException (the source is untouched); released 9.3.0-10.6.0 (10.6.0 executed); a second, unverified path through the default terms-index builder (TrieBuilder.append, 10.5.0 and later) was not reproduced through IndexWriter and is not part of this finding.
Summary
You copy 2 GiB or more into an in-heap ByteBuffersDataOutput, for example with Directory.copyFrom or IndexWriter.addIndexes(Directory) into a ByteBuffersDirectory. You expect every byte to be copied, as DataOutput.copyBytes(DataInput, long numBytes) promises ('Copy numBytes bytes from input to ourself') and as Lucene 9.2.0 does. Instead the override stores the length in an int, copies max(0, (int) numBytes) bytes (nothing at all for any length from 2^31 to 2^32-1) and returns normally, so the destination file is empty or truncated with no exception; a copied index then fails to open with CorruptIndexException.
