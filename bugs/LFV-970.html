The .liv grammar in the Lucene90LiveDocsFormat javadoc lists a Generation field that is not written and leaves out the footer

The javadoc of the default live-docs format says a .liv file is IndexHeader, Generation, Bits, but since 5.0.0 the generation is the header's suffix, not a field, and the file ends with a 16-byte checksum footer the grammar leaves out. Documentation only: Lucene reads its own files correctly.

The finding in 30 seconds

#

The class javadoc that documents the default live-docs file names a field the writer does not write, and leaves out one it does.

Background: the .liv file

#
  1. When a segment has deleted documents, Lucene writes a small live-docs file, .liv: one bit per document, set = live. Each new round of deletes writes a new file whose name carries a higher deletes generation: _0_1.liv, _0_2.liv, ...
  2. Like the other index files of the default codec, it starts with an IndexHeader (magic, codec name, version, the 16-byte segment id and a short suffix string) and ends with a 16-byte codec footer (magic, algorithm id, CRC32 checksum).

The finding, step by step

#
  1. You index 2 documents with the default codec and delete doc 0. Lucene writes the live-docs file _0_1.liv, 67 bytes; the segment's deletes generation is 1.
  2. You decode it as the Lucene90LiveDocsFormat javadoc says: IndexHeader, Generation, Bits. After the 43-byte header you expect the Generation: 1.
  3. You get 2. The 8 bytes there, 02 00 00 00 00 00 00 00, are the Bits word (binary 10: doc 1 live, doc 0 deleted). The generation is the header's last byte, its suffix "1" (base 36).
  4. After the Bits, 16 bytes remain that the grammar never mentions: the codec footer with its checksum. Lucene's own reader expects exactly this layout, so only a decoder written from the javadoc goes wrong, on every .liv file the default codec has written since 5.0.0.

Who is affected

#

People who read, inspect or re-implement the .liv format from this javadoc: format inspectors, ports, recovery tools. The default codec's file-format overview links this page for the details. Every .liv file since 5.0.0 is affected, with no setting involved. Lucene's writer and reader agree, so deletes, merges, CheckIndex and search are unaffected.

Mechanism, terms and numbers613 words

When a segment has deleted documents, the default codec writes a .liv file with one bit per document. The class javadoc of Lucene90LiveDocsFormat gives its layout as Deletions (.liv) --> IndexHeader,Generation,Bits (Lucene90LiveDocsFormat.java:45 on main 645d4fe14a20), defines SegmentHeader --> IndexHeader (:48), a name the grammar does not use, and leaves LongCount undefined (:49). The writer (:173-182) stores the deletes generation as the IndexHeader's suffix, in base 36, then the bit words, then a 16-byte codec footer; nothing is written between the header and the bits. A decoder that follows the text and reads Generation as a field of its own (the javadoc gives it no type; before LUCENE-5969 it was an Int64) reads the first bit word where it expects the generation (2 instead of 1 in the repro) and finds 16 trailing bytes the grammar does not mention. LUCENE-5969 (2014, before 5.0.0) moved the generation from an Int64 field into the header suffix and kept the word in the grammar; the footer has never been listed. Lucene's reader (:86-98) matches the writer, so only the javadoc is wrong, in every release from 5.0.0 to 10.6.0 and on main.

The documented grammar (main 645d4fe14a20, Lucene90LiveDocsFormat.java:45-50)

#
Deletions (.liv) --> IndexHeader,Generation,Bits

  SegmentHeader --> IndexHeader      (CodecUtil#writeIndexHeader)
  Bits --> <Int64>^LongCount

Generation has no type line, SegmentHeader does not occur in the grammar, LongCount and the bit meaning are not defined, and there is no Footer.

What the writer writes (writeLiveDocs, :164-194)

#
  • gen = info.getNextDelGen() (:168); the file name carries it (:169).
  • CodecUtil.writeIndexHeader(output, CODEC_NAME, VERSION_CURRENT, info.info.getId(), Long.toString(gen, Character.MAX_RADIX)) (:173-178): the generation is the header suffix, in base 36.
  • writeBits(output, bits) (:180): the bits as Int64 words in batches of up to 1024 bits, bits2words(numBitsToCopy) words per batch (:201-213), the bits past maxDoc cleared (:205-207).
  • CodecUtil.writeFooter(output) (:182): CodecFooter --> Magic,AlgorithmID,Checksum, 16 bytes (CodecUtil.java:396).
  • The reader mirrors it: checkIndexHeader with the same suffix (:86-92), readLongs of bits2words(maxDoc) words (:131-139), checkFooter (:98); a set bit is a live document (:144-145).

The bytes of the repro's file (_0_1.liv, 67 bytes, main)

#
IndexHeader (43 bytes) 3f d7 6c 17 10 4c 75 63 65 6e 65 39 30 4c 69 76 65 44 6f 63 73 00 00 00 00
                       68 a3 41 43 0b 4a 55 52 c2 51 b4 61 f2 1a 24 0e 01 31   <- suffix: length 1, "1"
Bits    (8 bytes)      02 00 00 00 00 00 00 00                                  <- Int64 = 2 = binary 10
Footer  (16 bytes)     c0 28 93 e8 00 00 00 00 00 00 00 00 45 f2 e2 c9

The segment id bytes and the checksum differ per run; the layout does not. Whatever integer type a reader assumes for the untyped Generation (Int64, Int32, VLong, VInt), the bytes 02 00 00 ... read as 2. In the hunt's larger index (200 documents, two deletions, 91 bytes) the same reading gives -9 instead of the generation 1, and with Generation skipped the grammar ends at byte 75 of 91, 16 bytes (the footer) short.

How it went stale

#

15b8b1e66d9 (2014-09-26) added a real output.writeLong(gen) after the header, documented as Generation --> Int64, and the reader compared it with the expected generation ("file mismatch, expected generation=..."). c4bf601b68f (LUCENE-5969, 2014-10-22) moved the generation into the header suffix and removed the write, the reader check and the type line, but kept Generation in the grammar and the label SegmentHeader. The footer was never in the grammar, from the class's first version on.

Exposure and likelihood155 words
  • Who is hit. Anyone who decodes a .liv file without Lucene, or checks one by hand, following the class javadoc: format inspectors, ports to other languages, recovery or forensic tools. The default codec's overview (lucene104/package-info.java) links this class as Live documents (:177, :303), says it "defines the index file formats used in this version of Lucene" (:50) and "Details on each of these are provided in their linked pages" (:188).
  • Default vs opt-in. The default codec, every .liv file it writes, on every release since 5.0.0. No setting changes the layout.
  • Scale. No runtime effect. The symptom is confined to a decoder written from the text: a wrong generation right after the header and 16 unexplained trailing bytes. A careful reader who cross-checks CodecUtil and the overview's footer note can work it out, which keeps the impact minor.
  • Rating. Impact class minor, likelihood plausible, priority low.

Why it looks unintended

#
  • Generation was a real Int64 field until LUCENE-5969 moved it into the header suffix (2014); the write and its type line went, the word stayed.
  • The type list still defines SegmentHeader, a name the grammar no longer uses.
  • The overview sends readers here for format details; sibling grammars (.cfs, .nvm, .fnm) list their Footer.
The full argument200 words
  • History. 15b8b1e66d9 wrote the generation as an Int64 after the header and documented Generation --> Int64; c4bf601b68f (LUCENE-5969) removed both the write and the type line. History suggests the word left in the grammar is what remains of the deleted field; it does not prove an oversight, because the same author revised the line later (5dcd24bf04c) and kept the word. Either way, the comma-separated grammar now lists an element that has no bytes of its own.
  • A half-renamed type list. It defines SegmentHeader, which the grammar no longer uses; no reading makes that definition intended.
  • The contract. lucene104/package-info.java:50 and :188 (quoted under "Who is affected").
  • Convention. Most core grammars list Footer explicitly: .cfs (Lucene90CompoundFormat.java:49, :57), .nvm/.nvd (Lucene90NormsFormat.java:57, :77), .fnm (Lucene94FieldInfosFormat.java:48-50, :62), .si (Lucene99SegmentInfoFormat.java:67); not all do: the .cfe entry-table production (Lucene90CompoundFormat.java:50-51) does not. A .fnm file written for doc-values updates has a generation suffix in its header (ReadersAndUpdates.java:846, :854), and the .fnm grammar folds it into Header with no Generation element.
  • Precedent. File-format doc errors were filed and fixed as ordinary issues, e.g. LUCENE-7532 (#8583) and LUCENE-713 (#1788).
The devil's-advocate check215 words

Strongest case for "intended" (the refute reviewer, the intended-lens reviewer and the devil's-advocate verifier; rated moderate): CodecUtil.writeIndexHeader's javadoc gives "generation" as an example suffix (CodecUtil.java:90-92), so IndexHeader,Generation could be read as one element; the overview says every index file ends with a checksum footer (package-info.java:381-383) and calls itself "a high-level definition" (:54), the policy of LUCENE-2946 (#4020); and LiveDocsFormat is @lucene.experimental. Under that reading (Generation zero-width, footer implicit) the bytes parse exactly: 143 of 143 files in the hunt's grammar check.

Why it fails: the grammar is a comma-separated sequence of elements, and Generation was a separate Int64 element until its type line was deleted; a suffixed header elsewhere (.fnm) is documented as plain Header; "high-level" allows leaving detail out, not listing an element that is not written or defining a name the grammar does not use, and on LUCENE-2946 rmuir wrote that bit-for-bit detail is fine "For the simple metadata files, and even stored fields and postings its fine (for now)"; @lucene.experimental is about API stability. The generous reading lowers the severity; it does not make the text right. Every verifier and the adjudication still concluded that the text is wrong as written; the reviewers rated the case for an intended reading moderate.

Suggested fix

#

Recommended A. Correct the grammar and say what the parts hold

Javadoc only: make the grammar IndexHeader,Bits,Footer, relabel the SegmentHeader type line as IndexHeader, add Footer --> CodecFooter, and note that the header suffix is the deletes generation in base 36, LongCount = ceil(maxDoc/64) and a set bit means live. Validated: the corrected-grammar test, the live-docs suite, core's static checks and the javadoc render pass.

Downstream note

#

It matters only to third-party tools that decode .liv files themselves from this javadoc, which would misread the generation and the trailing footer bytes.

How it was found

#

Semi-formal: a grammar check extracted the .liv production and its type list from the javadoc and interpreted it over the bytes of 143 .liv files from 91 generated default-codec indexes, with Lucene's own reader as the oracle for every bit. Every reading of the text as written failed on all 143 files; the writer's real layout parsed all 143.

The method in full150 words
  • The check extracts the production and type definitions mechanically from the javadoc source, checks them for well-formedness (it reports the undefined element Generation, the undefined count LongCount and the unused definition SegmentHeader) and interprets them over the real bytes, under every typing of the untyped Generation: absent, Int64, Int32, VLong, VInt.
  • Inputs: 91 indexes (11 fixed and 80 seeded random configurations: sizes, flushes, compound files, deletion rates for both live-docs read paths, 1-3 deletion commits, many field types), 143 .liv files, the same results with assertions on and off. LiveDocsFormat.readLiveDocs is the oracle for every bit.
  • Positive control: the writer-layout grammar parses all 143 files exactly. Vacuity: 3 of 3 .liv layout mutants (footer dropped, Int64 generation inserted, LongCount + 1) are killed. Fix check: the corrected text parses 59 of 59 files.
  • This is a differential grammar check of documentation against real output, not model checking or a proof.

History

#

Stale since LUCENE-5969 (c4bf601b68f, 2014-10-22), before 5.0.0: the generation moved into the header suffix and the grammar kept the word; the footer was never listed. Affects every release with this .liv format, 5.0.0 to 10.6.0, and main; in 4.x the default codec writes .del files instead.

Versions tested7 rows
  • Created: afee9af13f2 (2014-09-26): Lucene50LiveDocsFormat, grammar SegmentHeader,Bits, while the writer already appended a footer.
  • Generation added: 15b8b1e66d9 (2014-09-26): writeLong(gen) after the header, documented Generation --> Int64.
  • Introduced: c4bf601b68f (LUCENE-5969 "Add Lucene50Codec", #7031; lucene5969 branch, svn r1633514, Robert Muir, 2014-10-22T04:21Z): the generation moved into the header suffix; the write and the type line removed, the word and the SegmentHeader label kept. Later the same day, 5dcd24bf04c ("fix precommit, improve file format docs", same author) changed the first element to IndexHeader and kept Generation. It reached branch_5x as 0f304eafb93 and trunk as ff50c35fc22 (2014-10-24). svn era: no GitHub PR.
  • Copied: f0a2f1fe039 (LUCENE-9705, apache/lucene-solr#2274, 2021-02-04) created Lucene90LiveDocsFormat with the same text; it is the live-docs format from 9.0.0 on.
  • No release ever had the correct grammar: the Int64 element was added and removed during 5.0 development. All 98 release tags 5.0.0-8.8.1 and 9.0.0-10.5.2 in the release-tag clone, and the 10.6.0 tag, carry the same lines; the clone has no 8.8.2 or 8.9.0-8.11.4 tags (8.11.4's bytes were executed, its javadoc was not read).
  • First affected release: 5.0.0, the first with this binary .liv format (Lucene50LiveDocsFormat); in 4.10.4 the default codec writes .del files through Lucene40LiveDocsFormat (Lucene410Codec.java:57). The SimpleText codec has written its own plain-text .liv files since 4.0.0; that is a different format with no grammar in its javadoc.

The file-format javadoc of the default live-docs format (Lucene90LiveDocsFormat) gives the .liv grammar as 'IndexHeader,Generation,Bits', but no separate Generation has been written since LUCENE-5969 (the deletes generation is the IndexHeader suffix), the codec footer the writer appends is missing, and the type list defines SegmentHeader instead of IndexHeader (documentation defect; the writer and reader agree)
Area
codecs / live docs (Lucene90LiveDocsFormat .liv file-format javadoc vs its writer and reader)
Priority
Low, rank 1114: The .liv grammar has a phantom Generation field and no footer, a documentation-only defect that makes a doc-following parser misread the first bit word of every segment with deletions.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so deleting, merging, CheckIndex and search are unaffected in every configuration; the people misled are those who read, inspect or re-implement the .liv format from this class javadoc (the default codec's package docs link it as the Live Documents format), and a decoder that follows the text cannot account for the bytes of any .liv file the default codec writes (executed); the text has been wrong in every release since 5.0.0 (2015), and no scale or special setting is needed beyond a segment with deletions.
Summary
You decode a live-docs (.liv) file of the default codec by following the Lucene90LiveDocsFormat javadoc, which gives the layout 'IndexHeader, Generation, Bits'. The writer instead stores the deletes generation inside the IndexHeader (as its suffix, in base 36), then the bit words, then a 16-byte codec footer, so there is no Generation field after the header: a decoder that reads one there gets the first word of the bit set, and one that skips it finds 16 bytes the grammar does not mention. The type list also defines 'SegmentHeader' while the grammar says 'IndexHeader'; Lucene's own reader matches the writer, so nothing breaks at runtime, only the documentation is wrong.
