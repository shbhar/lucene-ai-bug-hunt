FilterMergePolicy reports bytes for a wrapped LogDocMergePolicy, so forceMerge(1) keeps rewriting a merged segment

Wrap a LogDocMergePolicy in a FilterMergePolicy and Lucene compares its document count with the 64 MiB byte threshold: a 70,000-document merged segment becomes a compound file, and every later forceMerge(1) rewrites it although nothing changed. Unreleased (main and branch_11x) since #15295; the fix is one line.

The finding in 30 seconds

#

The wrapper passes on the size, but not the unit of that size.

Background: compound files and merge-policy wrappers

#
  1. After a merge, Lucene may pack the new segment's files into one compound file. Since #15295 the rule is a fixed threshold: 65,536 documents for document-count policies (LogDocMergePolicy), 64 MiB for byte-size policies (TieredMergePolicy, the default).
  2. To pick the threshold, Lucene asks the merge policy for the segment's size and for the unit of that size, getSizeUnit(): DOCS or BYTES.
  3. FilterMergePolicy is the base class of policy wrappers such as SoftDeletesRetentionMergePolicy and UpgradeIndexMergePolicy: it forwards calls to the policy it wraps.
  4. forceMerge(1) on an index that is already one segment with no deletions should do nothing. The policy treats a segment as merged only if its compound-file flag matches the same rule.

The finding, step by step

#
  1. You set new FilterMergePolicy(new LogDocMergePolicy()) as the merge policy (or SoftDeletesRetentionMergePolicy or OneMergeWrappingMergePolicy around it), index 70,000 small documents, call forceMerge(1), then call it again.
  2. You expect what the plain LogDocMergePolicy does: the merged segment _1 is not a compound file (70,000 is above the 65,536-document threshold), and the second forceMerge(1) does nothing.
  3. Instead _1 is a compound file, and the second call rewrites it into _2. Every further call rewrites the whole segment again.
  4. Why: the wrapper passes on the inner policy's size, 70,000 documents, but reports its unit as BYTES, so the compound-file check uses the 64 MiB (67,108,864) threshold. The inner policy's "already merged?" check still counts documents, expects no compound file, and merges again.
  5. No wrong hits and no lost data: the cost is extra merge I/O. 10.x, through 10.6.0, delegates the decision and is not affected.

Who is affected

#

Only code that wraps LogDocMergePolicy (not the default) in a FilterMergePolicy subclass, for example SoftDeletesRetentionMergePolicy or OneMergeWrappingMergePolicy, on unreleased main or branch_11x. With default settings, merged segments of 65,537 to 67,108,864 documents become compound files, and each later forceMerge(1) rewrites such an index entirely. IndexUpgrader makes only the wrong compound-file choice, for the segments it upgrades. No wrong results.

Mechanism, terms and numbers517 words

Since #15295 Lucene decides whether a merged segment becomes a compound file by comparing mergePolicy.size(segment) with a threshold chosen by mergePolicy.getSizeUnit(): 65,536 documents for DOCS policies, 64 MiB for BYTES policies. FilterMergePolicy.size() delegates to the wrapped policy, a document count for LogDocMergePolicy, but FilterMergePolicy.getSizeUnit() returns super.getSizeUnit(), the MergePolicy default BYTES, instead of in.getSizeUnit(). So every FilterMergePolicy subclass around a LogDocMergePolicy, with the default compound-file settings, writes merged segments of 65,537 to 67,108,864 documents as compound files (in any merge and in addIndexes(CodecReader...)) and ignores setCfsThresholdDocSize. Because forceMerge asks the inner policy, which still counts documents, whether the index is already merged, the compound segment the wrapper wrote is never "merged": every later forceMerge(1) on a one-segment index with no deletions rewrites the whole segment. No search result, stored data or deletion changes. Main and branch_11x only; every release, through 10.6.0, delegates the compound-file decision and is not affected. Fix: return in.getSizeUnit();.

The code (main 5adff78bb168)

#
  1. FilterMergePolicy.java:78-81: size() returns in.size(info, context); for LogDocMergePolicy that is a document count (LogDocMergePolicy.java:40-43).
  2. FilterMergePolicy.java:83-86: getSizeUnit() returns super.getSizeUnit(), which is SizeUnit.BYTES (MergePolicy.java:581-589); LogDocMergePolicy.getSizeUnit() returns DOCS (LogDocMergePolicy.java:45-48).
  3. CompoundFormat.useCompoundFile(long mergedInfoSize, MergePolicy) (CompoundFormat.java:163-180) takes cfsThresholdDocSize (default 65,536, :39) for DOCS and cfsThresholdByteSize (default 64 MiB, :42) otherwise (:175-179). Its @param: mergedInfoSize is the "document count for DOCS-based policies, bytes for BYTES-based policies" (:157-158).
  4. IndexWriter asks the configured, outer policy: merge() takes config.getMergePolicy() (IndexWriter.java:5070), and mergeMiddle calls useCompoundFile(mergePolicy.size(mergedInfo, this), mergePolicy) (:5682-5691); addIndexes(CodecReader...) does the same (:3607-3617). 70,000 documents is far below 67,108,864, so the wrapper says compound.
  5. FilterMergePolicy.findForcedMerges calls in.findForcedMerges (:56-63). LogMergePolicy.findForcedMerges asks isMerged (LogMergePolicy.java:352, :181-203, :379, :289), which ends in MergePolicy.isMerged (MergePolicy.java:739-747): no deletions to merge and useCompoundFile(size(info), this) == info.getUseCompoundFile(), with this the inner LogDocMergePolicy (DOCS). 70,000 > 65,536 gives false, the segment says true, so it is not merged and is merged again, and the new segment again gets the wrapper's BYTES decision. So only the compound segments the wrapper wrote are at risk; a segment written as separate files stays merged.
  6. Within one call the cascade stops: the new segment is marked non-original (IndexWriter.java:5019-5024) and a single non-original segment counts as merged (LogMergePolicy.java:202). So it is one full rewrite per call, not a loop.

Exposure and likelihood246 words
  • Who is hit: a document-count policy (in Lucene: LogDocMergePolicy) under any FilterMergePolicy subclass: FilterMergePolicy, OneMergeWrappingMergePolicy, SoftDeletesRetentionMergePolicy and UpgradeIndexMergePolicy in core, BPReorderingMergePolicy in misc, MergeOnFlushMergePolicy in sandbox and ForceMergePolicy in the test framework. IndexUpgrader wraps the configured policy in UpgradeIndexMergePolicy (IndexUpgrader.java:180), which merges only segments from older Lucene versions (UpgradeIndexMergePolicy.java:69, :80-99): there it is the compound-file choice for the upgraded segments that is wrong, not a repeated rewrite.   • Cost: with the default CompoundFormat settings (compound files on, default thresholds, no maximum compound-file size), merged segments of 65,537 to 67,108,864 documents are packed into compound files, by any merge and by addIndexes(CodecReader...): an extra copy of their files at merge time (forceMerge asks for 3X free space with compound files instead of 2X, IndexWriter.java:2195-2198); setCfsThresholdDocSize has no effect and setCfsThresholdByteSize is applied to a document count; a periodic forceMerge(1) job on a static index rewrites the whole index on every run instead of returning at once.
  • No damage: one bounded rewrite per call; no wrong hits, no lost or resurrected documents, CheckIndex clean after every rewrite.
  • Shown end to end for FilterMergePolicy, SoftDeletesRetentionMergePolicy and OneMergeWrappingMergePolicy. UpgradeIndexMergePolicy reports BYTES as well but merges nothing on a fresh index; IndexUpgrader on an old index was not run. BPReorderingMergePolicy, MergeOnFlushMergePolicy and ForceMergePolicy: source reading only.
  • Not released: it would first ship in 11.0.0 unless fixed.

Why it looks unintended

#
  • getSizeUnit() is documented as "the unit of measurement used by this merge policy for segment size", and the wrapper's size() is the wrapped policy's document count.
  • FilterMergePolicy forwards every other non-final MergePolicy method; up to 10.6.0 it forwarded the compound-file decision itself.
  • The same wrapper failure, forceMerge re-merging a merged segment, was fixed as a bug before (LUCENE-7008, LUCENE-7010).
The full argument271 words
  • Contract: MergePolicy.getSizeUnit javadoc: "Returns the unit of measurement used by this merge policy for segment size. This is used to determine which threshold to apply when deciding whether to use compound files." (MergePolicy.java:582-583). CompoundFormat.useCompoundFile's @param ties the size to that unit (CompoundFormat.java:157-158). MIGRATE.md: "65,536 documents for document-count based merge policies (e.g., LogDocMergePolicy)" (lucene/MIGRATE.md:324-327).
  • isMerged javadoc: a merged segment "matches the current compound file setting" (MergePolicy.java:736-737), and BaseMergePolicyTestCase.testForceMergeNotNeeded asserts that forceMerge on a merged index schedules no merge (BaseMergePolicyTestCase.java:79-135); it indexes at most 100 documents, where both thresholds agree, so it cannot catch this.
  • Delegation rule: every other non-final MergePolicy method is forwarded to in (FilterMergePolicy.java:43-114; toString(), an Object method, builds its own label). LUCENE-7010 (#8067) introduced the wrapper, then MergePolicyWrapper, with a reflection test, testMethodsOverridden, that fails unless every non-final MergePolicy method is overridden; LUCENE-8248 (#9295) renamed both to FilterMergePolicy and TestFilterMergePolicy and made getMaxCFSSegmentSizeMB overridden too. The test checks only that an override exists (TestFilterMergePolicy.java:25-34).
  • Precedent: LUCENE-7008 (#8065): a wrapper that did not pass the compound-file setting through made forceMerge re-merge the last segment; fixed by LUCENE-7010 (#8067).
  • History: before #15295 the wrapper delegated useCompoundFile and the CFS getters and setters (10.6.0 FilterMergePolicy.java:79-83). #15295 removed them and wrote return super.getSizeUnit(); in the slot of the delegating getMaxCFSSegmentSizeMB() (git blame).
  • A contributor coded around it: open PR #16742 (costin, "Add ProactiveMergePolicy and merge selectors") overrides getSizeUnit() in its new FilterMergePolicy subclass to return in.getSizeUnit(); and tests that a wrapped LogDocMergePolicy reports DOCS; it leaves FilterMergePolicy and the existing wrappers unchanged.
The devil's-advocate check105 words

The case for intended: the explicit super call looks deliberate, NoMergePolicy has the same body (NoMergePolicy.java:79-80), the classes are @lucene.experimental, and CompoundFormat's setter javadoc gives the byte threshold to "merge policies other than LogDocMergePolicy" (CompoundFormat.java:69-71), which a wrapper technically is.

Why it fails: NoMergePolicy wraps nothing, so super is right there; a wrapper whose size() returns documents is document-count based; no review comment on #15295 or #14959 discusses wrappers; and the mismatch breaks the forceMerge no-op that the isMerged javadoc and the test above encode. Independent reviewers, one from another model family (OpenAI GPT-5.6), rated the intended-behaviour case weak.

Suggested fix

#

Recommended FilterMergePolicy.getSizeUnit() returns in.getSizeUnit() (validated)

Delegate the unit: in FilterMergePolicy.getSizeUnit(), return in.getSizeUnit();. Size and unit then always describe the same number, and a wrapper makes the same compound-file choice as the policy it wraps, as in 10.x. With it the repro and the closest merge-policy, compound-file, force-merge and addIndexes suites pass (141 tests, 0 failures), as do the format, ECJ and forbidden-apis checks.

   @Override
   public SizeUnit getSizeUnit() {
-    return super.getSizeUnit();
+    return in.getSizeUnit();
   }

FilterMergePolicy.getSizeUnit() returns in.getSizeUnit() (validated) (recommended)

#

One line in the base class, so every existing wrapper (OneMergeWrappingMergePolicy, SoftDeletesRetentionMergePolicy, UpgradeIndexMergePolicy, BPReorderingMergePolicy, MergeOnFlushMergePolicy, ForceMergePolicy) reports the wrapped policy's unit, matching the size() it already delegates. It also makes the override in open PR #16742 unnecessary.

   @Override
   public SizeUnit getSizeUnit() {
-    return super.getSizeUnit();
+    return in.getSizeUnit();
   }

Trade-offs

  • Restores the 10.x outcome for wrapped policies: as when the wrapper forwarded useCompoundFile, it makes the same compound-file choice as the policy it wraps. The old compound-file settings that #15295 removed stay removed.
  • No hot-path cost; a subclass that changes size() to another unit would also have to override getSizeUnit(), as the javadoc already implies.

Decide compound files on bytes for every policy (not run)

#

An alternative epotyom raised in the #15295 review: always decide on the segment's byte size, so the decision no longer depends on the policy's unit.

Trade-offs

  • Removes this class of unit mismatch altogether.
  • Changes the documented 65,536-document default for LogDocMergePolicy (MIGRATE.md) and is a larger design change than a bug fix.
