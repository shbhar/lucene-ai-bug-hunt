A boost too large for a float parses to Infinity and both query parsers throw IllegalArgumentException

A query such as a^ followed by 39 nines, a boost too large for a float (the largest is about 3.4e38), makes QueryParser.parse() throw IllegalArgumentException instead of its declared ParseException; the flexible StandardQueryParser does the same instead of QueryNodeException. Only the exception type is wrong, in every release since 8.0.0.

The finding in 30 seconds

#

The grammar accepts a boost of any length, such as 39 nines, but that is too big for a float.

Background: boosts in the query syntax

#
  1. In the classic and flexible query syntax, term^N multiplies a clause's score by N: apache^4 makes matches on apache count four times as much. N is plain digits with an optional fraction: no sign, no exponent, no length limit.
  2. Each parser turns N into a Java float with Float.parseFloat and wraps the clause in a BoostQuery. Since 8.0.0, BoostQuery rejects a negative, NaN or infinite boost with IllegalArgumentException.

The finding, step by step

#
  1. Parse a^3 with the classic QueryParser: you get (f:a)^3.0. Even a^340282346638528859811704183484516925440, the decimal value of Float.MAX_VALUE, works: (f:a)^3.4028235E38.
  2. Now parse a^999999999999999999999999999999999999999 (39 nines, about 1.0e39). You expect ParseException, the only exception parse() declares, as you get for the same number after ~.
  3. Instead Float.parseFloat rounds the boost to Infinity without throwing, new BoostQuery(q, Infinity) rejects it, and IllegalArgumentException: boost must be a positive float, got Infinity escapes parse().
  4. The flexible StandardQueryParser fails the same way instead of throwing QueryNodeException. Every boost literal from 2^128 - 2^103 (39 digits) up overflows, at every boost site, in every release since 8.0.0.

Who is affected

#

Applications that parse end-user query strings with the classic QueryParser (or its subclasses) or the flexible StandardQueryParser, with default settings, and catch only the declared exception. The trigger is contrived, a boost literal of at least 2^128 - 2^103, which takes 39 or more digits; one request then fails with the wrong exception, and no query is built.

Mechanism, terms and numbers577 words

The classic and flexible query parsers read the boost after ^ as the grammar's NUMBER token, digits with no length limit, and convert it with Float.parseFloat. For a literal of 2^128 - 2^103 = 340282356779733661637539395458142568448 or more (39 digits), Float.parseFloat returns Infinity without throwing, so QueryParserBase.handleBoost's "invalid boost means no boost" catch never runs. new BoostQuery(q, Infinity) then throws IllegalArgumentException("boost must be a positive float, got Infinity"), and parse(), which declares only ParseException and converts only ParseException, TokenMgrError and TooManyClauses, lets it through. The flexible StandardQueryParser builds a BoostQueryNode with value Infinity and hits the same exception in BoostQueryNodeBuilder.build instead of a QueryNodeException. The same literal after ~ already gets the declared exception in both parsers. No query is built, so nothing is matched or scored wrongly: only the exception type is wrong, and the trigger is contrived. BoostQuery's finite check came with LUCENE-7996 in 8.0.0, which did not touch the parsers; 7.x silently built (f:lucene)^Infinity. A Float.isFinite check in handleBoost and in BoostQueryNodeBuilder fixes both parsers.

Terms

#
  • Classic parser: org.apache.lucene.queryparser.classic.QueryParser (and its subclasses MultiFieldQueryParser, ComplexPhraseQueryParser); parse(String) documents @throws ParseException if the parsing fails.
  • Flexible parser: StandardQueryParser (and PrecedenceQueryParser), which parses in three phases (syntax, processing, build); parse(String, String) documents @throws QueryNodeException.
  • Float.MAX_VALUE: about 3.4028235e38. A decimal literal of 2^128 - 2^103 = 340282356779733661637539395458142568448 or more rounds to Infinity; one less rounds to Float.MAX_VALUE.

The bug

#
  1. The boost token is <NUMBER: (<_NUM_CHAR>)+ ( "." (<_NUM_CHAR>)+ )? > in both grammars (QueryParser.jj:218, StandardSyntaxParser.jj:160).
  2. Classic handleBoost (QueryParserBase.java:813-831) does f = Float.parseFloat(boost.image) (:817) inside a catch whose comment says an invalid boost "defaults to no boost" (:821-823). On overflow Float.parseFloat returns Infinity and does not throw, so that fallback never runs, and q = new BoostQuery(q, f) (:828) throws.
  3. BoostQuery's constructor (BoostQuery.java:40-41): if (Float.isFinite(boost) == false || Float.compare(boost, 0f) < 0) throw new IllegalArgumentException("boost must be a positive float, got " + boost);.
  4. parse() (QueryParserBase.java:129-146) converts only ParseException | TokenMgrError and TooManyClauses into ParseException, so the IllegalArgumentException leaves parse() unwrapped.
  5. Flexible: the Boost production builds new BoostQueryNode(node, parseFloat(boost)) with no check (StandardSyntaxParser.jj:701), and BoostQueryNodeBuilder.build (:48) calls new BoostQuery(...) with Infinity. The neighbouring FuzzyOp production validates its number and throws ParseException (StandardSyntaxParser.jj:716-724), as classic handleBareFuzzy does (QueryParserBase.java:786-795).

The same exception for phrase, group, range, fuzzy, wildcard, regexp and *:* boosts, and in MultiFieldQueryParser, ComplexPhraseQueryParser and PrecedenceQueryParser. A stop word as the boosted term hides it: the term is analysed away, handleBoost skips the BoostQuery, and the^<39 nines> gives an empty query.

Exposure and likelihood219 words
  • Who is hit. Callers of QueryParser, MultiFieldQueryParser, ComplexPhraseQueryParser, StandardQueryParser or PrecedenceQueryParser that handle bad input with catch (ParseException e) / catch (QueryNodeException e). Default configuration, any analyzer that keeps the boosted term, every boost site.
  • What it takes. A boost literal of at least 2^128 - 2^103, which is 39 digits, because the grammar has no exponent syntax. Nobody types that by accident; fuzzers and deliberately odd input produce it (rated "contrived").
  • What happens. The unchecked exception bypasses the application's "bad query" handler, so depending on the application a malformed query becomes an internal error instead of a validation error. Assertions on or off make no difference.
  • What does not happen. No query is returned, so nothing is matched or scored wrongly; no hang, no material resource use, no index effect, no state left behind.
  • Why it can matter more later. #9064 (open) proposes bounding boosts to [2^-10, 2^10]. If BoostQuery enforced that, ordinary literals such as ^2000 would take this same path, so the parsers need their own range check anyway.
  • Related, separate sites (not part of this bug). The surround parser accepts a^<39 nines> (weight Infinity) and the same exception appears later, in SrndQuery.makeLuceneQueryField. Other unchecked exceptions escape parse() for other inputs: an invalid regex (#7761) and a negative phrase slop (LFV-300).

Why it looks unintended

#
  • parse() documents only @throws ParseException (flexible: QueryNodeException) and already converts the runtime TooManyClauses into ParseException.
  • The same 39-digit number after ~ gets the declared exception in both parsers, and handleBoost's own comment says an invalid boost means "no boost".
  • LUCENE-7996 added the finite check to BoostQuery for 8.0.0 without touching the parsers; 7.x returned (f:lucene)^Infinity.
The full argument303 words
  • Contract. QueryParserBase.java:127: @throws ParseException if the parsing fails. StandardQueryParser.java:274 and QueryParserHelper.java:211: @throws QueryNodeException if something wrong happens along the three phases; this exception comes from the build phase. The syntax docs say only "By default, the boost factor is 1. Although the boost factor must be positive, it can be less than 1" (classic/package-info.java:268-269): no upper bound, no failure mode. The flexible BoostQueryNode javadoc says "The boost value may vary from 0.0 to 1.0" (BoostQueryNode.java:29), a stale range that nothing enforces: flexible a^3 builds (f:a)^3.0. The BoostQuery constructor javadoc has no @throws.
  • Tests. Upstream QueryParserTestBase.testBooleanQuery (:985-989) asserts that TooManyClauses comes out as a parse exception, and testException (:976-983) asserts parse exceptions for malformed text. No test expects an IllegalArgumentException from parsing query text; the module's IAE tests cover parser setters and the static MultiFieldQueryParser.parse(String[], String[], ...) overloads, which document it for arrays of different lengths.
  • History. LUCENE-7996 (#9044, a8a63464e7da, 2017-12-06) touched 22 files, none under lucene/queryparser; its MIGRATE note says only "negative boosts are now rejected", which the grammar cannot produce. The issue thread and the dev@ heads-up mention neither the parsers nor infinite boosts. Before it, every 7.x release returned (f:lucene)^Infinity.
  • Precedent (mixed). In LUCENE-950 (#2025, 2007) FuzzyQuery's IllegalArgumentException escaped classic parse() for foo~1. The reporter, Eleanor Joslin, wrote "An application shouldn't blow up just because a user types something silly in a search field". Grant Ingersoll (@gsingers) first wrote "this isn't really an error"; Mark Miller (@markrmiller) later wrote "it seems silly to throw the illegal arg exception in either case". It was closed "Not A Problem" in 2010, the day Robert Muir (@rmuir) noted that the 4.0 fuzzy syntax had made foo~1 legal. Not a ruling that parse() may throw IAE.
The devil's-advocate check189 words

The strongest case for "not a bug" (the noise audit's first triage, and the refutation angles a tie-breaker checked): a throws ParseException clause never excludes unchecked exceptions; the input is absurd (39 digits) and the failure is loud and clear; no query is built, so no result is wrong; and other unchecked exceptions already escape parse() (#7761, LFV-300), so "always ParseException" was never achieved.

Why it fails: the input is end-user query text, for which parse() documents a parse exception as its failure, not a developer-chosen argument, and the grammar's own token accepts it. The parsers already convert a runtime failure and already reject the same literal after ~, and handleBoost intends a bad boost to mean "no boost". The loud failure is exactly what breaks a catch (ParseException e) handler. The other escapes are separate open bugs, not evidence of intent. The argument limits severity (low), not validity; the noise audit's challenger and the tie-breaker both kept the claim as Low. This is an inference from the documented contract and the code, not a maintainer ruling: a maintainer may treat it as a low-priority hardening request.

Suggested fix

#

Recommended A. Reject a non-finite boost in both parsers

Reject a non-finite boost with each parser's own exception: a Float.isFinite check in QueryParserBase.handleBoost (throws ParseException) and in BoostQueryNodeBuilder.build (throws QueryNodeException), +14/-1, no grammar regeneration. The repro passes with assertions on and off, and all 534 queryparser tests and check pass.

// QueryParserBase.handleBoost, now declared "throws ParseException", after Float.parseFloat:
if (Float.isFinite(f) == false) {
  throw new ParseException("Boost " + boost.image + " is out of range");
}
// BoostQueryNodeBuilder.build, before the BoostQuery is built:
if (Float.isFinite(boostNode.getValue()) == false) {
  throw new QueryNodeException(
      new MessageImpl(
          QueryParserMessages.INVALID_SYNTAX, "boost out of range: " + boostNode.getValue()));
}
All options and trade-offs3 options · 635 words

Option A was run through gradle in a scratch worktree of 645d4fe14a20 and is recommended. B and C are the alternatives a maintainer may prefer; B was checked only as a shadowed sketch, C was not tried. No open PR touches these lines.

A. Reject a non-finite boost in both parsers (validated by the checks) (recommended)

#

QueryParserBase.handleBoost gets throws ParseException and a finite check after Float.parseFloat; BoostQueryNodeBuilder.build gets the same check with a QueryNodeException (two imports). Both generated callers of handleBoost already declare throws ParseException, so no generated parser changes. PrecedenceQueryParser uses the same builder; MultiFieldQueryParser and ComplexPhraseQueryParser inherit handleBoost.

// QueryParserBase.handleBoost, now declared "throws ParseException", after Float.parseFloat:
if (Float.isFinite(f) == false) {
  throw new ParseException("Boost " + boost.image + " is out of range");
}
// BoostQueryNodeBuilder.build, before the BoostQuery is built:
if (Float.isFinite(boostNode.getValue()) == false) {
  throw new QueryNodeException(
      new MessageImpl(
          QueryParserMessages.INVALID_SYNTAX, "boost out of range: " + boostNode.getValue()));
}

Trade-offs

  • Matches how both parsers already treat a bad fuzzy number. Finite boosts up to Float.MAX_VALUE are unchanged. Error path only: no API, format or performance change.
  • Stop words: the classic check runs before the stop-word skip, so the^<39 nines> with a stop-word analyzer now gets ParseException instead of an empty query. The flexible parser still returns MatchNoDocsQuery("") there, because its processors drop the boost node before the build phase. Moving the classic check under if (q != null) keeps the old silent behaviour and matches the flexible parser.
  • The flexible message carries the float (Syntax Error: boost out of range: Infinity), because the node keeps only the value. A check in the Boost production (StandardSyntaxParser.jj:701, like FuzzyOp) could quote the literal, but the generated parser would have to be regenerated.
  • The flexible check sits in the builder, so it also sees a non-finite boost from configuration rather than query text (a field boost set with StandardQueryParser.setFieldsBoost becomes a BoostQueryNode in BoostQueryNodeProcessor.java:54-57); an infinite one would then give QueryNodeException instead of IllegalArgumentException (by reading, not run).
  • The surround parser's separate gap is not covered.

What the checks validated

  • outcomes: a^3 and a^<Float.MAX_VALUE> unchanged; a^<39 nines> gives ParseException: Cannot parse 'a^<39 nines>': Boost <39 nines> is out of range (classic) and QueryNodeException: Syntax Error: boost out of range: Infinity (flexible).

B. Fall back to "no boost", as handleBoost's comment says (validated as a classic-only sketch)

#

Set f = 1.0f when Float.parseFloat returns a non-finite value (and the same in the flexible parser).

Trade-offs

Never fails and matches the code's stated intent for an invalid number, but the user's boost is silently ignored, the flexible parser needs its own change, and the repro's assertion must become "parse returns a query".

What the checks validated

Classic only, as a shadowed class: a fix-agnostic variant of the test passes, and the ParseException test fails as expected. The module suite was not run.

C. Convert any IllegalArgumentException in parse() into the parse exception

#

Catch IllegalArgumentException in QueryParserBase.parse (and in the flexible QueryParserHelper.parse) and rethrow it as ParseException / QueryNodeException, as parse() already does for TooManyClauses.

Trade-offs

Also fixes the other escapes of the same kind (#7761 invalid regex, LFV-300 negative slop) in one change, but is broader: an IAE from a bug in a custom subclass or analyzer would also be reported as a syntax error. Not tried.

Downstream note

#

A service that answers ParseException with "bad query" and anything else with a server error turns this 41-character query into an internal error.

How it was found

#

Non-formal: in the 2026-10-22 study, Jazzer fuzzing of the classic, flexible and simple query parsers, with the rule that a parser may only throw its documented exception, hit a boost of many nines. A study verifier reproduced it from scratch, and the hunt cut it to a one-test repro.

The method in full153 words

Method: non-formal (the study's fuzzing baseline, then code reading and executed tests). The study's QueryParserFuzzer (Jazzer, about 470 k executions over three runs) checked that the classic, flexible and simple parsers throw only their documented exception and that parsed queries survive toString, equals, count and rewrite; it reported five query-parser findings, this one among them (a boost of nines that parses to Infinity). The finding was blind: the fuzzer's oracle did not name boosts.

A study verifier then wrote its own deterministic 11-method JUnit test from scratch (2 contract tests fail, 9 characterisation tests pass), found the exact threshold, the other parsers and boost sites and the stop-word mask, and ran it across versions (7.7.3 builds (f:lucene)^Infinity; 8.0.0 to main throw). The 2026-10-29 noise audit replaced that class with the one-test repro, and on 2026-11-01 a reproducer and a tie-breaker re-ran it on main and on the release jars.

History

#

Introduced in 8.0.0 by LUCENE-7996 (a8a63464e7da, 2017-12-06), which added the finite check to BoostQuery without touching the parsers. All 61 releases from 8.0.0 to 10.6.0 and main fail; 7.0.0-7.7.3 instead return (f:lucene)^Infinity. Not fixed upstream.

Versions tested5 rows

Introduced by LUCENE-7996 "Queries are now required to produce positive scores" (#9044, by Adrien Grand, @jpountz; JIRA patch era, no PR), commit a8a63464e7da, 2017-12-06. It added three lines to the BoostQuery constructor and changed no query parser file; at the 7.7.3 and 8.0.0 tags every parser file on the boost path is byte-identical. The overflow itself is older (both parsers convert the boost with Float.valueOf up to 6.4.2 and with Float.parseFloat from 6.5.0 on, after LUCENE-7739 e7b87f5b79f; both return Infinity); only the exception is new. A shadow pair confirms it: 8.0.0 with only those three lines removed returns (f:lucene)^Infinity again, and 7.7.3 with only those lines added throws like 8.0.0. Upstream main 2f424fd428da (2026-10-30) has the same code.

LFV-028, snapshot of 2026-11-03

Registry title
A boost too large for a float parses to Infinity and both query parsers throw IllegalArgumentException
Area
queryparser / classic and flexible
Priority
Low, rank 919: A 39-digit boost literal overflows to Infinity and both query parsers let IllegalArgumentException escape instead of ParseException, an input only fuzzers or hostile queries produce.
Impact class
wrong error
Impact note
Applications that parse untrusted query strings with the classic or flexible parser; one input shape; released since 8.0.0.
Summary
You parse a query whose boost literal is too large for a float (2^128 - 2^103 or more, which takes 39 digits) with the classic or flexible query parser. You expect a parse error or a usable boost. Instead the boost parses to Infinity and BoostQuery's finite check throws IllegalArgumentException out of parse().
