ValueSource#asLongValuesSource() says it needs no scores, so a sort on a score-based function never sees the real score

Sort on asLongValuesSource() of a function that reads the score, and the search runs without scores: a hit with score 3 gets the sort value 1 (0 in the JUnit test with some seeds), never 3, with no error. Every release since 6.4.0; asDoubleValuesSource() of the same function is correct.

The finding in 30 seconds

#

The long bridge feeds the scores into the function but tells the search it does not need them, so the search never computes them.

Background: function values, bridges and needsScores

#
  1. ValueSource is Lucene's older function API (for example LinearFloatFunction, a linear function of another value). DoubleValuesSource and LongValuesSource are the newer per-document value APIs used for sorting, faceting and scoring; asDoubleValuesSource() and asLongValuesSource() bridge a ValueSource to them.
  2. Every values source answers needsScores(): are the hit's scores needed to compute my values? A sort field built from it passes the answer on, and the searcher computes scores only when some sort field says yes.
  3. ValueSource.fromDoubleValuesSource(DoubleValuesSource.SCORES) is a function whose value is the hit's score.

The finding, step by step

#
  1. You index one document and search new BoostQuery(new ConstantScoreQuery(MatchAllDocsQuery.INSTANCE), 3f): the hit scores exactly 3.
  2. You sort on new LinearFloatFunction(ValueSource.fromDoubleValuesSource(DoubleValuesSource.SCORES), 1f, 0f).asLongValuesSource(), the score as a long. You expect the sort value 3.
  3. Instead the sort value is 1, the score without its boost (0 in the JUnit test with some seeds, such as DEADBEEF), never 3, and there is no error. With two hits whose 1000 * score values are 132 and 68, both sort on 0 and come back in index order (doc 0, doc 1) instead of doc 1, doc 0.
  4. Why: the long bridge hands the scores to the function, but its needsScores() returns false (ValueSource.java:156). The sort passes that on, so the search computes no scores and the function reads a placeholder.
  5. asDoubleValuesSource() of the same function answers true ("be on the safe side") and sorts on 3.0.

Who is affected

#

Code that sorts on asLongValuesSource() of a function that reads the score, such as one that reads it through ValueSource.fromDoubleValuesSource(DoubleValuesSource.SCORES), gets wrong sort values and order on every search, silently. Default settings, any index size. Opt-in and rare: no caller in Lucene, Solr, Elasticsearch or OpenSearch.

Mechanism, terms and numbers486 words

ValueSource#asLongValuesSource() wraps a function ValueSource as a LongValuesSource. Its getValues hands the scores it is given to the wrapped function as the "scorer" context entry (ValueSource.java:130-131), but its needsScores() always returns false (:156). A LongValuesSource sort field passes that answer to Sort.needsScores() (LongValuesSource.java:293-296), so IndexSearcher#search(Query, int, Sort) collects in a mode that computes no scores (TopFieldCollector.java:304-310). When the wrapped function reads the score, for example new LinearFloatFunction(ValueSource.fromDoubleValuesSource(DoubleValuesSource.SCORES), 1, 0), every hit gets a sort value that does not come from its real score (in the repro the hit's score is 3 and its sort value is 1, the score without its boost, or 0 in the JUnit test with some seeds) and the hits come back in index order, with no error. asDoubleValuesSource() of the same function answers true and sorts correctly. This breaks the documented LongValuesSource#needsScores contract ("Return true if document scores are needed to calculate values"). It needs an opt-in composition that has no caller in Lucene or the major downstream projects, so it is Low; it is in every release from 6.4.0 through 10.6.0 and on main, and a one-line change fixes it.

The code (main 5adff78bb168)

#
  1. ValueSource.java:111-114: asLongValuesSource() returns new WrappedLongValuesSource(this, null); the javadoc is only "Expose this ValueSource as a LongValuesSource".
  2. ValueSource.java:126-131, WrappedLongValuesSource.getValues: var scorer = new ScorableView(scores); context.put("scorer", scorer);, so the wrapped function can read the scores the caller passes.
  3. ValueSource.java:154-157: needsScores() returns false (:156), the fix site.
  4. ValueSource.java:288-292, FromDoubleValuesSource.getValues: reads context.get("scorer") (:291) and gives it to the wrapped DoubleValuesSource; DoubleValuesSource.SCORES returns that score.
  5. LongValuesSource.java:293-296: LongValuesSortField.needsScores() returns producer.needsScores(); Sort.java:128-136 makes Sort.needsScores() false.
  6. IndexSearcher.java:677-679, :719-740: search(Query, int, Sort) uses a TopFieldCollectorManager (threshold 1000, :100), and TopFieldCollector.java:304-310 picks ScoreMode.TOP_DOCS (or COMPLETE_NO_SCORES when every hit is counted), both without scores. Because no scores are needed, IndexSearcher rewrites the query as new ConstantScoreQuery(query) (IndexSearcher.java:753, :882-888), and that rewrite drops the BoostQuery (ConstantScoreQuery.java:48-49): the query that runs is ConstantScore(*:*), whose scorer scores 1 (MatchAllDocsQuery.java:39-48).
  7. LongValuesSource.java:350-353: the comparator's setScorer hands DoubleValuesSource.fromScorer(scorer) to the bridge, so the function reads that scorer's score: 1 in a plain program. In the JUnit test it is 0 for some seeds, DEADBEEF among them: Lucene's test framework installs an LRUQueryCache whose policy caches at random (SetupAndRestoreQueryCache.java:41-43, LuceneTestCaseParent.java:365-374), and a cached clause scores 0f (LRUQueryCache.java:846, :887-888). Neither value is the real score, and no contract defines it.

The sibling WrappedDoubleValuesSource (asDoubleValuesSource(), :183-186) fills the same "scorer" entry (:203) and answers return true; // be on the safe side (:225-226).

Scope

#

Only the asLongValuesSource() bridge is claimed, and only the sort consumer was executed. Lucene's facet consumers of a LongValuesSource call getValues(..., null) whatever needsScores() says (for example LongValueFacetCounts.java:181, LongRangeFacetCounts.java:149).

Exposure and likelihood169 words
  • Who. Code that sorts on asLongValuesSource() of a ValueSource whose value depends on the score: in Lucene, any function that reads the score through ValueSource.fromDoubleValuesSource(DoubleValuesSource.SCORES), or a custom ValueSource that reads the "scorer" context entry (the pattern TestValueSources.testScorerContext uses, :838-879).
  • Default vs opt-in. An opt-in composition, but no special settings: default codec, IndexWriterConfig and IndexSearcher, any index size (one document), assertions on and off.
  • Scale. Every search with such a sort. In the executed repros every hit gets the same wrong value (0 or 1), so the hits come back in doc-id order.
  • Silent. No exception; the results look normal.
  • Not affected. asDoubleValuesSource() of the same function; DoubleValuesSource#toLongValuesSource() (DoubleValuesSource.java:135, :203-235, which passes needsScores() through); functions that read no score.
  • Likelihood. Rare: asLongValuesSource() has no caller and no test inside Lucene, and code search found none in Solr, Elasticsearch or OpenSearch; no public report found since 2017. A user who hits it sees wrong values on every search, so tests would likely catch it.

The score is fixed by the boost, so the similarity does not matter. The test passes :lucene:queries:checkGoogleJavaFormat and compiles without deprecation warnings.

The wrong value depends on the seed: with DEADBEEF it is 0, because Lucene's test framework installs a query cache that caches at random and a cached clause scores 0; with other seeds, such as 5EED0003, it is 1, the score without its boost, which is also what a plain program gets. It is never 3.

Why it looks unintended

#
  • LongValuesSource#needsScores: "Return true if document scores are needed to calculate values"; the bridge reads the scores it is passed.
  • The sibling asDoubleValuesSource(), added in the same 2017 commit, answers true ("be on the safe side"); nothing documents the long bridge as score-free.
  • Merged #14654 (2025) called the same kind of missing-scores sort on another ValueSource path a bug.
The full argument183 words
  • The contract. LongValuesSource#needsScores: "Return true if document scores are needed to calculate values" (LongValuesSource.java:52-53); getValues: "If scores are not needed to calculate the values (ie needsScores() returns false), callers may safely pass null for the scores parameter" (:44-47).
  • The sibling. LUCENE-7610 (2017) gave asDoubleValuesSource() return true; // be on the safe side (ValueSource.java:225-226). No javadoc, test, CHANGES.txt or MIGRATE.md entry limits asLongValuesSource() to score-free functions.
  • The score wiring is kept on purpose. LUCENE-10252 (#11288, PR #519, commit by David Smiley, 2022) made both bridges compute the score lazily and kept the "scorer" entry; on the issue (LUCENE-10252, migrated as #11288, 2021-11-23) Alan Woodward asked to keep it because third-party code may rely on it. TestValueSources.testScorerContext (:838-879) tests a score-reading ValueSource through the double bridge.
  • Precedent. #14654 (David Smiley, merged 2025, b0f992369ba): "supporting needsScores correctly (fixes a bug)", for a sort on ValueSource.fromDoubleValuesSource(SCORES) through ValueSource#getSortField; the code now says "avoids indirection and supports a better needsScores()" (ValueSource.java:332-334), tested by testFromDoubleValuesSortWithScore (TestValueSources.java:889-912). It did not touch the long bridge.
The devil's-advocate check165 words

The strongest case for "intended", built by an intended-behaviour check and examined by an independent reviewer from another model family (OpenAI GPT-5.6): the bridge was written in 2017 for facet callers that pass null scores; a ValueSource cannot say whether it reads the score; the LUCENE-10252 commit message says the bridges "should not compute the score unless asked to -- typically never"; in SOLR-13126 Alan Woodward wrote that the long bridge is not "actually used anywhere in Solr yet"; ValueSource may be deprecated (#16820); and asDoubleValuesSource().toLongValuesSource() works today.

Why it fails: "typically never" is about when the score is computed (lazily), not about whether the consumer is told to provide scores, and LUCENE-10252 kept the scores flowing into the function. The double bridge resolves the same "cannot know" with true. Neither the restriction nor the workaround is documented, and the failure is silent. These points argue for choosing between the fix and a javadoc change, not for leaving it. Verdict: a real Low bug.

Suggested fix

#

Recommended A. needsScores() returns true (recommended, validated)

Recommended: WrappedLongValuesSource.needsScores() returns true, as the double bridge does (one line). The repro passes, the whole lucene/queries module (513 tests, 5 skipped) runs with 0 failures, and the formatter check passes. Cost: score-free bridged functions then also run in a scoring mode (performance only).

     @Override
     public boolean needsScores() {
-      return false;
+      return true; // the wrapped ValueSource may read the scores through the "scorer" entry
     }
All options and trade-offs2 options · 400 words

Option A was applied in a scratch worktree at 5adff78bb168 and run through gradle (seed DEADBEEF, one seed, no nightly tests, not the full suite). Lucene has no other test that calls asLongValuesSource(), so a scratch check (not the repro) also sorts on a score-free bridged LongFieldSource (values 5, 2, 9): 2, 5, 9 before and after the fix, with sort.needsScores() going from false to true. Workaround for users today: asDoubleValuesSource().toLongValuesSource() passes needsScores() through (DoubleValuesSource.java:233-235) and sorts the repro's hit on 3 (scratch check on stock main); it casts the function's double value to a long: for a float function such as the repro's that is the same long as longVal (FloatDocValues.java:55-57, :65-67), but a long-valued function above 2^53 can lose precision on the way (LongDocValues.java:62-63).

A. needsScores() returns true (recommended, validated)

#

ValueSource.java:154-157, one line, as in WrappedDoubleValuesSource (:225-226).

     @Override
     public boolean needsScores() {
-      return false;
+      return true; // the wrapped ValueSource may read the scores through the "scorer" entry

Trade-offs

Every consumer that honours needsScores(), such as a sort, then runs in a scoring mode (for search(query, n, sort), TOP_DOCS_WITH_SCORES, TopFieldCollector.java:304-310), also for bridged functions that read no score. Such a search also gives up the no-scores rewrite (IndexSearcher.java:882-888) and the query cache, which caches only weights that need no scores (IndexSearcher.java:976-982). Facet consumers pass null scores and do not change. That costs performance, not correctness; the score itself is still computed lazily, at most once per hit (ScorableView, ValueSource.java:80-109, :98). It is the choice the double bridge made in 2017.

What the checks validated

The repro fails before and passes after, assertions on and off; ./gradlew :lucene:queries:test: 513 tests, 5 skipped, 0 failures (includes TestValueSources); :lucene:queries:checkGoogleJavaFormat passes; the score-free scratch check still sorts 2, 5, 9. An independent fact check re-ran it: 513 tests, 5 skipped, and the repro passes with seed 5EED0003 too.

B. Document the restriction

#

Say in the asLongValuesSource() javadoc that the returned source reports needsScores() == false and must not wrap a function that reads the score, and point to asDoubleValuesSource().toLongValuesSource().

Trade-offs

No behaviour or performance change, but the silent wrong result stays for anyone who misses the note, and the bridge still feeds the scores into the function. Not run (text only).

Downstream note

#

A downstream product that ranks results with such a sort would show them in index order instead of by score; nothing else.

How it was found

#

A semi-formal proof-obligation audit of the ValueSource bridge contracts: a bridged function that reads the score must answer needsScores() true, as LongValuesSource#needsScores says. The long bridge broke that obligation, and an executable public-API test witnessed the wrong sort values.

The method in full90 words

The obligation comes from LongValuesSource#needsScores ("Return true if document scores are needed to calculate values") and getValues (callers may pass null scores only when it is false). The audit checked each bridge (asLongValuesSource, asDoubleValuesSource, fromDoubleValuesSource) and its consumers with executable probes over the public API: 3 of 1525 checks failed, all this defect (the bridge answers false for a score-reading function, and the long sort values are 0 while the double-bridge control sorts by 1000 * score). The witness was then reduced to one JUnit test.
