IndexWriter blocks in its own rollback until interrupted after an Error thrown while logging a checked-out merge

With IndexWriter's InfoStream on for merge messages, a throw from the log call right after a merge is checked out (say an OutOfMemoryError) leaves that merge "running" with no thread. The writer's self-close after the Error, or close() after an exception, then waits for it until interrupted.

The finding in 30 seconds

#

IndexWriter hands a merge to the merge scheduler in two steps: it marks the merge as running, then logs it. If the log call throws, the scheduler never receives the merge, but the writer still counts it as running, and everything that waits for running merges waits for it.

Background

#
  1. Pending and running merges. IndexWriter keeps merges the merge policy selected in pendingMerges. The merge scheduler asks for the next one; the writer moves it to runningMerges, and whoever received it must run it or hand it back (mergeFinish).
  2. Waiting for merges. close() waits until no merge is pending or running (waitForMerges). A rollback aborts pending merges and waits until no merge is running (abortMerges).
  3. After an Error (such as OutOfMemoryError) during indexing, IndexWriter closes itself: it rolls back, which includes abortMerges.
  4. InfoStream is IndexWriter's debug log, off by default; setInfoStream(System.out) turns on every component, including the merge scheduler's "MS" messages.

The finding, step by step

#
  1. Turn on IndexWriter's InfoStream for the merge scheduler ("MS"), merge every 2 segments (LogDocMergePolicy, merge factor 2) and flush every 2 documents. Add 3 documents: 1 segment is written, 1 document is buffered.
  2. Add a 4th document. Its flush writes segment 2 and a merge of the 2 segments is selected. IndexWriter marks the merge as running, then logs " checked out merge _0(11.0.0):c2 _1(11.0.0):c2", and that log call throws an OutOfMemoryError.
  3. You expect what the javadoc promises after an Error: addDocument rethrows it and the writer closes itself. The same Error thrown earlier in that scheduler call, before the check-out, does exactly that.
  4. Instead addDocument is still blocked after 10 s, in the writer's own rollback (abortMerges), waiting for a merge that no thread will run. With assertions on and off, on main and on 10.6.0, and the same on every release run since 8.6.0.
  5. If the logger throws an ordinary exception instead, addDocument fails, the writer stays open, and close() waits the same way, in waitForMerges.

Who is affected

#

Applications that turn on IndexWriter's InfoStream for merge messages (off by default) and hit a throw at that one message: an Error such as OutOfMemoryError at that call, or a logging bridge that throws. Both stock merge schedulers; 4 documents suffice. The indexing call or close() then blocks until interrupted; by reading, the last commit is untouched.

Mechanism, terms and numbers734 words

IndexWriterMergeSource.getNextMerge() first calls IndexWriter.getNextMerge(), which moves the next merge from pendingMerges to runningMerges. Only then, when the merge scheduler is verbose (InfoStream enabled for component "MS"), does it build and log " checked out merge " + segString(...). If that statement throws, getNextMerge() throws instead of returning the merge, so no scheduler ever receives it: nobody runs it and nobody calls mergeFinish for it, and it stays in runningMerges. abortMerges() and waitForMerges() wait while runningMerges is not empty.

After an Error (such as an OutOfMemoryError; the repros throw it from the InfoStream, and by reading it can also hit while Lucene builds the message string), the indexing call's tragic handling runs rollbackInternal() -> abortMerges(), which waits for that merge: addDocument blocks until interrupted and the writer does not finish closing itself, although the IndexWriter class javadoc says it "will close itself". After an unchecked exception from the application's InfoStream, addDocument throws, the writer stays open, and close() blocks in waitForMerges() (after a first interrupt, again in the rollback that follows). Both stock merge schedulers are affected; no scale is needed.

The window came with LUCENE-9345 (2020, first released in 8.6.0), which moved this log line out of ConcurrentMergeScheduler.merge's try/finally that called mergeFinish on failure. It is opt-in (the InfoStream is off by default) and rare, so the priority is Low. The recommended fix finishes the merge when the log call throws, as 8.5.x did and as ConcurrentMergeScheduler.merge still does for its own failures.

The code (main 645d4fe14a20)

#
  1. Check-out. IndexWriter.getNextMerge() (IndexWriter.java:2538-2551, synchronized) does pendingMerges.removeFirst() then runningMerges.add(merge) (:2547-2548).
  2. The unprotected statement. IndexWriterMergeSource.getNextMerge() (IndexWriter.java:6859-6869):
MergePolicy.OneMerge nextMerge = writer.getNextMerge();      // pending -> running
if (nextMerge != null) {
  if (writer.mergeScheduler.verbose()) {                      // InfoStream enabled for "MS"
    writer.mergeScheduler.message(
        "  checked out merge " + writer.segString(nextMerge.segments));   // a throw here ...
  }
}
return nextMerge;                                             // ... means no caller gets the merge

verbose() is infoStream != null && infoStream.isEnabled("MS") (MergeScheduler.java:93-95). The stock PrintStreamInfoStream, which IndexWriterConfig.setInfoStream(PrintStream) installs, is enabled for every component (PrintStreamInfoStream.java:60-62).

  1. No caller can hand it back. The throw leaves getNextMerge() before it returns. ConcurrentMergeScheduler.merge calls it (ConcurrentMergeScheduler.java:570) before the try whose catch (Throwable t) { mergeSource.onMergeFinished(merge); throw t; } hands back a merge it could not start (:578-595). SerialMergeScheduler.merge (SerialMergeScheduler.java:32-40) has no hand-back.
  2. The waits. abortMerges() loops while (runningMerges.size() + runningAddIndexesMerges.size() != 0) doWait(); (IndexWriter.java:2849-2861); waitForMerges() loops while (pendingMerges.size() > 0 || runningMerges.size() > 0) doWait(); (:2891-2893). doWait() is wait(1000); an interrupt ends it with ThreadInterruptedException (:5860-5870).
  3. Error path. updateDocuments records an Error as tragic and calls maybeCloseOnTragicEvent() (IndexWriter.java:1630-1641), which sets closing = true through shouldClose(false) and calls rollbackInternal() (:6098-6106, :1374-1393). rollbackInternal takes commitLock (:2589); the abortMerges() call in rollbackInternalNoCommit() (:2590, :2621) waits. Other threads (executed in a fact-check probe): commit() and prepareCommit() fail at once with AlreadyClosedException, because ensureOpen() also rejects a closing writer (:4213-4214, :3735-3736, :913-917); rollback() and a later close() wait in shouldClose for the unfinished self-close (:2581, :1387).
  4. Exception path. A non-Error is not tragic (:1633-1635), so the writer stays open and close() -> shutdown() -> waitForMerges() waits; after a first interrupt, shutdown()'s catch calls rollbackInternal() (:1328-1331), whose abortMerges() waits again, so it takes two interrupts (executed).

A second site with the same gap, by reading: ConcurrentMergeScheduler.MergeThread.run logs "merge thread %s start" after the check-out and before doMerge (ConcurrentMergeScheduler.java:720-726), and its catch (Throwable) (:747-754) neither runs the merge nor calls onMergeFinished/mergeFinish. An unminimised hunt probe reported forceMerge(1) waiting after a throw there; no verifier re-ran it, and the fixes below do not cover it.

A second caller of the same method, by reading (not run): a merge thread that finished its merge calls runOnMergeFinished -> merge(mergeSource, MergeTrigger.MERGE_FINISHED) (ConcurrentMergeScheduler.java:742, :678-686), which checks out the next pending merge through this same getNextMerge(). A throw at "checked out merge" there strands that merge too, but it surfaces in MergeThread.run's catch (Throwable), not in an indexing call: no indexing call needs to see the Error, and a later close() would wait in waitForMerges. The recommended fix covers this caller as well, because it sits inside getNextMerge().

Exposure and likelihood247 words
  • Default or opt-in. Opt-in. A new IndexWriterConfig takes InfoStream.getDefault() (LiveIndexWriterConfig.java:142), which is InfoStream.NO_OUTPUT (InfoStream.java:57) unless the application changed it with InfoStream.setDefault (:74); then verbose() is false, the message is never built and the window is empty.
  • Triggers. An Error such as OutOfMemoryError at this call: every repro injects it from the application's InfoStream, as Lucene's own tests do; by reading (not executed) it can also hit while segString builds the message under heap pressure (IndexWriter.java:5845-5849). Or an exception from an application-supplied InfoStream. The stock PrintStreamInfoStream does not throw (a PrintStream swallows IOExceptions).
  • What breaks. After an Error: addDocument blocks until the thread is interrupted and the writer does not finish closing itself; meanwhile other threads' commit() fails with AlreadyClosedException and rollback() or close() wait. After the interrupt, addDocument throws ThreadInterruptedException, not the OutOfMemoryError. After an exception: the writer stays open and usable (a probe indexed 4 more documents and committed; a reader saw all 8), but close() blocks until it is interrupted twice. All executed. The repros did not run CheckIndex; by reading, the last commit is untouched.
  • Scale. None: 4 empty documents, deterministic, default ConcurrentMergeScheduler and SerialMergeScheduler alike.
  • Existing mitigations. An application that terminates the JVM on OutOfMemoryError is not hit by the Error variant; turning the "MS" component off avoids both.
  • Likelihood. Rare: it needs the opt-in logging and a throw at exactly this statement; no outside report of the hang was found.

Why it looks unintended

#
  • The javadoc: after an Error "IndexWriter will close itself". The same Error thrown before the check-out does close it.
  • Before 8.6.0 this log line sat in a try/finally that handed the merge back; a 2020 refactor moved it out.
  • Lucene's tests throw OutOfMemoryError from InfoStream.message to test recovery; LUCENE-1210 fixed this invariant elsewhere in 2008.
The full argument251 words
  • The contract. IndexWriter.java:162-165: "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself. This is a defensive measure in case any internal state (buffered documents, deletions, reference counts) were corrupted." close() (:1345) is documented as "waiting for any running merges, committing, and closing"; here no merge is running.
  • The control. The same OutOfMemoryError thrown at "now merge" (ConcurrentMergeScheduler.java:558, logged before the loop that checks merges out), while the merge is still pending, closes the writer with the Error as its tragic exception (executed on main with assertions on and off, 10.5.2 and 9.12.3).
  • IndexWriter's own rule. The comment at IndexWriter.java:5110-5111: "Important that tragicEvent is called after mergeFinish, else we hang waiting for our merge thread to be removed from runningMerges". ConcurrentMergeScheduler.merge hands back a merge it cannot start (:592-595).
  • The tests. TestIndexWriterExceptions.testOutOfMemoryErrorCausesCloseToFail (LUCENE-1429, TestIndexWriterExceptions.java:1110-1147) and testOutOfMemoryErrorRollback (:1150) throw OutOfMemoryError from InfoStream.message and assert that the writer recovers or closes.
  • The history. In 8.5.2 the line (then " consider merge ") sat inside ConcurrentMergeScheduler.merge's try { ... } finally { if (!success) writer.mergeFinish(merge); }. LUCENE-9345 (d7e0b906abc, apache/lucene-solr#1451) moved it after the check-out without the hand-back; the PR's two review comments are about the index(source) string. CHANGES: "LUCENE-1210: Fix deadlock case on hitting an exception while starting a merge when using ConcurrentMergeScheduler" (#2287, "mergeInit hits an exception (eg OOME)"); "LUCENE-1171: Fixed some cases where OOM errors could cause deadlock in IndexWriter".
The devil's-advocate check177 words

The strongest case: InfoStream is a "Debugging API" tagged @lucene.internal (InfoStream.java:24-28); MergeScheduler and MergeSource are @lucene.experimental; the stock InfoStreams do not throw; close() promises no bounded wait; so a throwing logger is misuse of a debugging hook. The refute-lens cross-model reviewer (OpenAI GPT-5.6) argued this and said not real, while agreeing with the root cause.

It fails for the Error variant: the class javadoc's promise covers Errors without exception, wherever they are raised, and an OutOfMemoryError is not a misbehaving logger (by reading it can also hit while Lucene builds this message; the repros inject it from InfoStream.message, as Lucene's own tests do); IndexWriterConfig.setInfoStream(InfoStream) and setInfoStream(PrintStream) are public and untagged (IndexWriterConfig.java:430-446), and nothing says message() must not throw; Lucene's own tests inject Errors through InfoStream.message; the code itself treats a merge left in runningMerges at tragedy time as a hang to avoid. It carries weight for the RuntimeException variant, which needs a throwing logger: present that one as secondary hardening. Verdict: not intended (judge confidence medium because of that variant).

Suggested fix

#

Recommended Finish the merge when the log call throws

In IndexWriterMergeSource.getNextMerge, wrap the log call: on any throw, call writer.mergeFinish(nextMerge) and rethrow. That is what 8.5.x did for this line and what ConcurrentMergeScheduler.merge does for a merge it cannot start. Validated: the repro passes, and so do 244 tests in 11 closest suites.

        if (writer.mergeScheduler.verbose()) {
          try {
            writer.mergeScheduler.message(
                "  checked out merge " + writer.segString(nextMerge.segments));
          } catch (Throwable t) {
            // no merge scheduler holds this merge yet: finish it, else abortMerges and
            // waitForMerges keep waiting for it in runningMerges
            writer.mergeFinish(nextMerge);
            throw t;
          }
        }
All options and trade-offs3 options · 733 words

Two fixes were validated in a scratch worktree of 645d4fe14a20; both close the demonstrated cases. A drops the merge (the policy can select it again later); B keeps it for a later pass but, by reading, can leave a merge in an already-cleared pending queue when a rollback runs at the same time. Neither covers the MergeThread.run log line (the same gap by reading, not run) or the throw point open PR #16889 would add. By reading, A leaves two small gaps a maintainer may want closed (below): the verbose() check stays outside its try, and the dropped merge is not closed.

Finish the merge when the log call throws (validated by the checks) (recommended)

#

One file, +9/-2 in IndexWriterMergeSource.getNextMerge(). It restores the pre-8.6 hand-back for the log call and matches ConcurrentMergeScheduler.merge's own catch (Throwable). mergeFinish removes the merge from runningMerges, releases its segments and calls notifyAll() (IndexWriter.java:5375-5391). Code is added only on the verbose path; it also covers a merge thread's own call of getNextMerge().

        if (writer.mergeScheduler.verbose()) {
          try {
            writer.mergeScheduler.message(
                "  checked out merge " + writer.segString(nextMerge.segments));
          } catch (Throwable t) {
            // no merge scheduler holds this merge yet: finish it, else abortMerges and
            // waitForMerges keep waiting for it in runningMerges
            writer.mergeFinish(nextMerge);
            throw t;
          }
        }

Trade-offs

The merge is dropped, not retried; its segments stay unmerged until the merge policy selects them again on a later merge pass (by reading). It does not cover the MergeThread.run site. By reading (not run): (1) not exactly 8.5.2, where the verbose() check (InfoStream.isEnabled("MS")) was inside the protected try as well (8.5.2 ConcurrentMergeScheduler.java:538-541); here it stays outside, so a throw from isEnabled would still strand the merge, and moving the check inside the try closes that. (2) Like ConcurrentMergeScheduler.merge's existing hand-back (onMergeFinished -> mergeFinish), it does not call OneMerge.close, the only place that completes the merge's completion future and calls its mergeFinished hook (MergePolicy.java:192, :285-299): timed waits such as merge-on-commit (IndexWriter.java:739, :3894) return at their timeout, and a caller in the untimed MergeObserver.await() (MergePolicy.java:915, from forceMergeDeletes(false)) for a merge dropped this way would keep waiting. Closing the merge with success=false, as abortMerges does for pending merges (IndexWriter.java:2831, :5133-5136), would avoid that; not written or tested.

Put the merge back into the pending queue (validated by the checks)

#

The hunt's first fix (plus a notifyAll()): on a throw, under the writer lock, runningMerges.remove(nextMerge) then pendingMerges.addFirst(nextMerge), and rethrow.

Trade-offs

It keeps the merge for a later scheduler pass. By reading (not run): if another thread's rollback() is already in abortMerges() (pending queue cleared, waiting for running merges, IndexWriter.java:2824-2861), the merge lands in the cleared queue with its segments still registered, and assert mergingSegments.isEmpty() (:2622-2623) would trip. That is why A is recommended.

Log before the check-out (not validated)

#

Logging the merge before IndexWriter.getNextMerge() moves it would also close the window (a throw would leave the merge pending, like the control), but the message would have to be built from the queue under the writer's lock. Not written or run.

How it was found

#

A fault-injection sweep threw one OutOfMemoryError at each of the 850 InfoStream calls of a small indexing script, one run per call; 9 runs hung at this log call. Code reading then reduced it to a 4-document test on the default merge scheduler.

The method in full109 words

Method: semi-formal (a bounded-exhaustive single-fault sweep, then code reading).

  • The hunt unit on error handlers and errors raised through public callbacks ran its sweep against the real lucene-core jar: a 24-operation script with SerialMergeScheduler, one fresh run per InfoStream call, with an OutOfMemoryError thrown at that call. 9 runs at the merge scheduler's message from IndexWriterMergeSource.getNextMerge hung in IndexWriter.abortMerges, with assertions on and off.
  • The same unit's static scan of catch handlers did not flag the site: no catch handler is involved; the defect is a missing hand-back.
  • Code reading reduced it to a 4-document JUnit on the default ConcurrentMergeScheduler; independent checks then reproduced it (below).

LFV-844, snapshot of 2026-11-05

Registry title
If the merge scheduler's InfoStream throws on the log line right after IndexWriter hands out a merge, that merge stays marked as running with no thread to run it, so the writer hangs in its own tragic rollback after an Error, or in close() after an exception (8.6.0 to main)
Area
index / IndexWriter merge hand-off to the merge scheduler (IndexWriterMergeSource.getNextMerge, runningMerges)
Priority
Low, rank 798: It is the same kind of bug as LFV-208 (a checked-out merge never handed back, so close() or the tragic rollback hangs), but it needs the opt-in merge-scheduler InfoStream to throw at one log statement and only exists since 8.6.0.
Impact class
hang
Impact note
This hits applications that turn on IndexWriter's InfoStream for the merge-scheduler component 'MS' (off by default) when the logging call throws at the one ' checked out merge ...' statement. Realistically that is an OutOfMemoryError while Lucene builds the message, or an exception from a logging bridge. It happens with both stock schedulers (the default ConcurrentMergeScheduler and SerialMergeScheduler). After an Error, the indexing call never returns, because the writer's self-close waits forever in abortMerges. After an unchecked exception, the writer stays open and close() waits forever in waitForMerges. No scale is needed. Every release from 8.6.0 to 10.5.2 and main is affected [exec 8.6.0, 8.11.4, 9.0.0, 9.12.3, 10.5.2, main], and 10.6.0 by reading.
Summary
You turn on IndexWriter's InfoStream for merge-scheduler messages, and the logging call throws once (an OutOfMemoryError, or an exception from the logging backend). It throws on the message the writer prints right after it hands a merge to the merge scheduler. You expect what the IndexWriter javadoc promises: after an Error the writer closes itself, and after an exception close() still finishes, because no merge is actually running. Instead, the merge has already been moved from 'pending' to 'running', and no thread ever runs or finishes it, so after an Error addDocument hangs forever inside the writer's own rollback (abortMerges), and after an exception close() hangs forever in waitForMerges.
Introduced
d7e0b906abcbc43d3737224cadcda7d2c795ccb0 (LUCENE-9345 'Separate MergeSchedulder from IndexWriter', apache/lucene-solr#1451 by s1monw, merged 2020-04-24; branch_8x backport 9598d43bb629). It moved the merge log line out of ConcurrentMergeScheduler.merge's protected try/finally, which called writer.mergeFinish when the merge did not start. The line went into the new IndexWriterMergeSource.getNextMerge, after the pending-to-running check-out, with no hand-back [read: git log -S 'checked out merge' returns only this commit; exec brackets it: 8.5.2 not affected, 8.6.0 affected] (2020-04-24 (author date of d7e0b906abc and of the branch_8x backport 9598d43bb62))
