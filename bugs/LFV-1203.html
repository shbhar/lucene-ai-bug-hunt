LatLonPoint.newGeometryQuery with CONTAINS matches nothing instead of throwing for an empty or null-holding geometry array

LatLonPoint.newGeometryQuery(field, CONTAINS, ...) with no geometries, or with a null one, returns a query that silently matches nothing instead of the IllegalArgumentException its javadoc promises and the other relations throw. The defect needs invalid input; every release since 8.8.0 has it.

The finding in 30 seconds

#

One relation, CONTAINS, takes a shortcut that runs before the argument checks every other relation goes through.

Background: geometry queries on a point field

#
  1. LatLonPoint.newGeometryQuery(field, relation, geometries...) builds a query over indexed points. For INTERSECTS, WITHIN and DISJOINT it builds one LatLonPointQuery (apart from two INTERSECTS shortcuts for a single rectangle or circle), whose constructor checks the arguments ("geometries must not be empty", "geometries[i] must not be null").
  2. CONTAINS asks for documents whose points contain every given geometry. Points can only contain points, so the factory adds one required (MUST) clause per Point, and returns MatchNoDocsQuery for a line or polygon: a choice made on purpose when CONTAINS was added in 8.8.0.

The finding, step by step

#
  1. You build a CONTAINS query on a LatLonPoint field from a list of points that turned out empty: LatLonPoint.newGeometryQuery("f", QueryRelation.CONTAINS) with 0 geometries.
  2. You expect IllegalArgumentException: the javadoc promises it when the geometries are "null, empty or contain a null", and the same call with INTERSECTS or WITHIN throws "geometries must not be empty".
  3. Instead you get ConstantScore(): a ConstantScoreQuery over a BooleanQuery with 0 clauses. On an index with one point at (0,0) it finds 0 hits, where CONTAINS [Point(0,0)] finds 1. No error.
  4. A null slot does the same: CONTAINS [Point(0,0), null] returns MatchNoDocsQuery("... with non-point geometries"), 0 hits, in LatLonPoint and in LatLonDocValuesField.newSlowGeometryQuery; INTERSECTS throws "geometries[1] must not be null".
  5. Why: CONTAINS takes a shortcut before any argument check. Its loop never runs for 0 geometries, and null instanceof Point is false, so the null lands in the branch meant for lines and polygons.

Who is affected

#

Applications that build a CONTAINS query on a point field from a caller-built array that can be empty (no locations picked) or hold a null slot, relying on the documented check. They get zero hits and no error. No setting is involved: any index, assertions on or off. Valid input is not affected by this defect.

Mechanism, terms and numbers442 words

LatLonPoint.newGeometryQuery(field, queryRelation, latLonGeometries...) and LatLonDocValuesField.newSlowGeometryQuery document @throws IllegalArgumentException when the geometry array "is null, empty or contain a null". For INTERSECTS, WITHIN and DISJOINT the query constructors enforce it. For CONTAINS both factories take a shortcut first that checks only the geometry type (instanceof Point), not null or empty input: an empty array gives ConstantScore() over zero clauses, and a null element gives MatchNoDocsQuery("... with non-point geometries"). Both match no document, so a caller's mistake (an empty list of points, a null slot) becomes an empty result with no error. The doc-values factory still rejects the empty array; the null element is silent in both. Valid input is not affected by this defect. Introduced in 8.8.0 by LUCENE-9641; present in every release through 10.6.0 and on main.

The mechanism (main 5adff78bb168, under lucene/core/src/java/org/apache/lucene/)

#
  1. The contract. document/LatLonPoint.java:314-326: "@param latLonGeometries array of LatLonGeometries. must not be null or empty." and "@throws IllegalArgumentException if field is null, queryRelation is null, latLonGeometries is null, empty or contain a null" (:323-324). document/LatLonDocValuesField.java:243-246 has the same clause and adds "or line geometry"; that line part is not claimed here, because under CONTAINS a line gets the MatchNoDocsQuery the introducing PR's review settled for non-point geometries (:255-261).
  2. The checks live in the query constructors. new LatLonPointQuery(...) (LatLonPoint.java:340) goes through SpatialQuery (field and relation, document/SpatialQuery.java:74-85) and LatLonGeometry.create (geo/LatLonGeometry.java:24-45). new LatLonDocValuesQuery(...) (LatLonDocValuesField.java:263) does its own field and relation checks (document/LatLonDocValuesQuery.java:57-62) and calls LatLonGeometry.create (:87).   3. CONTAINS returns before them. LatLonPoint.java:337-338 sends CONTAINS to makeContainsGeometryQuery (:343-355), which adds one MUST clause per Point and returns MatchNoDocsQuery for anything else (:346-348).
    • Empty array: the loop body never runs, and :354 returns new ConstantScoreQuery(builder.build()) over zero clauses, which matches nothing (it prints as ConstantScore(); at search time the empty BooleanQuery rewrites to MatchNoDocsQuery("empty BooleanQuery"), search/BooleanQuery.java:268-271).

  4. The doc-values twin. LatLonDocValuesField.java:255-261 has the same CONTAINS loop and the same null-element outcome; its empty array falls through to LatLonDocValuesQuery and is rejected there.
  5. Not claimed. MatchNoDocsQuery for a valid line or polygon under CONTAINS is intended. The null-array NullPointerException fails loudly (only the exception type differs), and a null field with an empty array needs a second invalid argument.
Exposure and likelihood128 words
  • Who. Code that passes an empty or null-holding array to LatLonPoint.newGeometryQuery (or LatLonDocValuesField.newSlowGeometryQuery, null element) with CONTAINS, for example a list of user-picked points that can be empty. Nothing tells the application its input was invalid.
  • Default vs opt-in. Query construction only: no configuration, any index and codec, assertions on and off. CONTAINS on a point field is a niche relation, and no public report was found since 8.8.0 (2021), so the likelihood is rare.
  • Needs invalid input. This defect changes nothing for valid geometries (valid multi-point CONTAINS on newSlowGeometryQuery has a separate defect, LFV-701). The documented IndexOrDocValuesQuery pairing still throws for the empty array, because the doc-values half rejects it; the null element is silent in both halves.
  • Scale. One call; no index needed; deterministic.

Why it looks unintended

#
  • Both javadocs promise IllegalArgumentException for an array that is "null, empty or contain a null"; the commit that added CONTAINS rewrote and kept that clause.
  • For the same empty array, INTERSECTS, WITHIN and the doc-values twin's CONTAINS throw "geometries must not be empty".
  • The intended MatchNoDocsQuery is for valid non-point geometries; a null reaches it only by failing instanceof Point.
The full argument127 words
  • The contract is explicit and current. The @throws clause names these inputs for every relation, in both factories. LUCENE-9641 (14009f4424d), which added CONTAINS and the shortcut, rewrote the clause in the same diff and kept "null, empty or contain a null" (git blame).
  • The rest of the API enforces it. INTERSECTS, WITHIN, newPolygonQuery and newSlowGeometryQuery(CONTAINS) throw "geometries must not be empty" for the empty array; INTERSECTS throws "geometries[i] must not be null" for a null element (executed). Before LUCENE-9641, on unreleased master, the constructors of the removed LatLonPointInGeometryQuery and LatLonDocValuesPointInGeometryQuery rejected all of these inputs.
  • Tests. No upstream test passes an empty or null-holding array with any relation; BaseGeoPointTestCase.testPolygonNullField (lucene/test-framework/.../tests/geo/BaseGeoPointTestCase.java:472-483) treats these @throws clauses as tested contract for the field argument.
The devil's-advocate check200 words

The case for intended (the devil's-advocate verifier and the cross-model refute lens): (a) @param says the array "must not be null or empty", so the caller misuses the API; (b) in the review of lucene-solr#2155 a reviewer (nknize) suggested throwing for non-point geometries under CONTAINS, and the author (iverase) answered "Still I return a MatchNoDocs query for the Query builders"; (c) LatLonShape.newGeometryQuery(f, CONTAINS) with an empty array also returns ConstantScore(); (d) an empty set matching nothing is common in Lucene.

Why it fails. (a) The javadoc does not stop at the precondition: it promises the exception for exactly these inputs. (b) The review covered valid non-point geometries, a relation points can never satisfy, not invalid arrays. (c) LatLonShape's empty case appears to be a historical consequence of LUCENE-9225 (286d22717b2, 8.5.0), which dropped a CONTAINS && length > 1 guard that XYShape.newGeometryQuery still has (XYShape throws), and for a null element LatLonShape throws "geometries[0] must not be null" while LatLonPoint returns MatchNoDocsQuery (executed). (d) Here the API documents the exception and enforces it on every other path. The cross-model reviewer rated the misuse defence weak against the explicit @throws; it does hold for impact, hence Low.

Suggested fix

#

Recommended Validate every argument before any shortcut, in both factories (fix A)

Check every argument first: a small package-private helper, called as the first line of both LatLonPoint.newGeometryQuery and LatLonDocValuesField.newSlowGeometryQuery, throws IllegalArgumentException for a null field or relation, a null or empty array and a null element, before any shortcut. The repro passes, and the 236 TestLatLon* tests run with 0 failures (19 skipped).

Validate every argument before any shortcut, in both factories (fix A) (validated by the checks) (recommended)

#

Add LatLonPoint.checkGeometryQueryArguments(field, queryRelation, latLonGeometries) (package-private) and call it as the first statement of newGeometryQuery (LatLonPoint.java:327-328) and of newSlowGeometryQuery (LatLonDocValuesField.java:248-249); +27/-0, messages as in LatLonGeometry.create.

  static void checkGeometryQueryArguments(
      String field, ShapeField.QueryRelation queryRelation, LatLonGeometry... latLonGeometries) {
    if (field == null) {
      throw new IllegalArgumentException("field must not be null");
    }
    if (queryRelation == null) {
      throw new IllegalArgumentException("queryRelation must not be null");
    }
    if (latLonGeometries == null) {
      throw new IllegalArgumentException("geometries must not be null");
    }
    if (latLonGeometries.length == 0) {
      throw new IllegalArgumentException("geometries must not be empty");
    }
    for (int i = 0; i < latLonGeometries.length; i++) {
      if (latLonGeometries[i] == null) {
        throw new IllegalArgumentException("geometries[" + i + "] must not be null");
      }
    }
  }

Trade-offs

Implements the null, empty and null-element part of both @throws clauses in one place, before every shortcut; the doc-values clause's "or line geometry" is left as it is. Side effects, all towards the documented behaviour: a null array gives IllegalArgumentException instead of NullPointerException (as newPolygonQuery did in 8.7.0), and so does a null field with an empty CONTAINS array. Callers that pass an empty CONTAINS array today get an exception instead of zero hits: a behaviour change, so consider a CHANGES entry. Cost: one linear null scan per query construction, run first on every path (the single-geometry INTERSECTS shortcuts included); the paths that reach LatLonGeometry.create scan the array again there.

How it was found

#

A proof-obligation audit of the documented @throws contract of LatLonPoint.newGeometryQuery and LatLonDocValuesField.newSlowGeometryQuery: every path that returns a query must first reject a null, empty or null-holding array. The CONTAINS shortcut does not; a one-test public-API JUnit witnessed it.
