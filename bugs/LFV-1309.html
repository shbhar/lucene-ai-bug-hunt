A failed IndexWriter.rollback() leaves the other in-memory segments un-aborted, locked and with open files

If rollback() hits an exception while it discards one of the writer's in-memory segments, it stops there: the other segments stay locked with their stored-fields files open (4 each in the tested runs), and since 4.7.1 the closed writer has no call left that releases them.

The finding in 30 seconds

#

rollback() locks every buffered in-memory segment, then discards them in a loop that unlocks each one in a finally but has no catch. One failure ends the loop, and the segments after it are skipped: not discarded, still locked, files still open.

Background in three steps

#
  1. IndexWriter buffers new documents in in-memory segments (DocumentsWriterPerThreads): each indexing call takes a free one or a new one, so overlapping calls from different threads use different segments. Each one holds open outputs, such as its stored-fields files.
  2. rollback() throws away everything since the last commit and closes the writer. For the buffered documents, DocumentsWriter.abort() locks every in-memory segment, then aborts and unlocks them one by one.
  3. Since LUCENE-5544 (4.7.1), a rollback that hits an exception still closes the writer, and Lucene's tests require that it leaks no file handles or locks.

The finding, step by step

#
  1. Two threads add one document each to the same IndexWriter at the same time, so it buffers 2 in-memory segments, one per thread. The writer's InfoStream throws RuntimeException("BOOM") once, on the first "done abort" message.
  2. You call rollback(). It locks both segments, then discards (aborts) them one at a time; aborting the first one throws BOOM.
  3. You expect rollback() to pass BOOM on but still discard both segments, as Lucene's own testExceptionDuringRollback requires: "we are closed, no locks or files held".
  4. Instead the loop stops at the failure. The other segment is never aborted, stays locked by your thread and keeps 4 outputs open (_1.fdt, _1.fdm and 2 temp files): MockDirectoryWrapper.close() fails with "there are still 4 open files".
  5. The writer is already closed, so a second rollback() does nothing and no writer call releases the handles. Committed data and search results are not affected.

Who is affected

#

Applications whose indexing calls from several threads overlap (no special setting needed) and whose rollback() or tragic self-close hits an exception or Error while aborting a segment: a throwing custom InfoStream, an OutOfMemoryError, or a bug in an abort path. Each skipped segment keeps its stored-fields outputs open (4 in the tested runs); committed data is not affected.

Mechanism, terms and numbers628 words

When indexing calls from several threads overlap, an IndexWriter buffers each concurrent call in its own in-memory segment (a DocumentsWriterPerThread, DWPT; the pool reuses a free one or creates a new one). rollback() calls DocumentsWriter.abort(), which locks every DWPT up front and then aborts them one by one in a loop that has a finally { unlock } but no catch. If aborting one DWPT throws (an unchecked exception or an Error), the loop ends there: every DWPT after it is never aborted, stays registered and locked by the thread that called rollback(), and keeps its stored-fields outputs open (4 per DWPT in the tested runs). rollback() passes the exception on and closes the writer anyway, so a second rollback() is a no-op and the writer has no call left that releases those outputs.

Lucene's own testExceptionDuringRollback (LUCENE-5544) requires the opposite after an exception during rollback: "we are closed, no locks or files held". It indexes from one thread, so it never reaches this case. The loop dates from DWPTs (4.0.0); since 4.7.1 a second rollback() no longer cleans up, and since 8.6.0 the skipped DWPTs also stay locked. The fix is a per-DWPT catch in the loop (+6 lines).

The bug

#
  1. IndexWriter.rollback() (IndexWriter.java:2576-2584) and the tragic self-close (maybeCloseOnTragicEvent, :6097-6105) run rollbackInternalNoCommit, which calls docWriter.close() and then docWriter.abort() (:2633, :2635).
  2. DocumentsWriter.abort() (DocumentsWriter.java:212-243) loops over perThreadPool.filterAndLock(_ -> true) (:218). filterAndLock locks every registered DWPT before it returns the list: "All DWPTs returned from this method are already locked" (DocumentsWriterPerThreadPool.java:161-182).
  3. The loop body is try { abortDocumentsWriterPerThread(perThread); } finally { perThread.unlock(); } (DocumentsWriter.java:218-224), with no catch. A throw unlocks only the current DWPT and leaves the loop: the later DWPTs, already locked, are never aborted or unlocked, and flushControl.abortPendingFlushes() / waitForFlush() (:225-226) are skipped. The outer catch (Throwable t) (:238-243) logs "done abort success=false" (when DW logging is on) and rethrows t; an InfoStream that also threw on that message would replace t (the repro's is enabled for DWPT only).
  4. What can throw inside one DWPT's abort (DocumentsWriterPerThread.java:98-115): its "now abort" and "done abort" InfoStream calls (:103, :112, the second in an outer finally; executed), and an Error that IOUtils.closeWhileHandlingException rethrows (IOUtils.java:155-178) while that DWPT's stored-fields writer is closed (StoredFieldsConsumer.java:112-114, from IndexingChain.abort(), :530-538; read, not executed). A bug in an abort path works the same way: #11637 reports a real NullPointerException escaping one DWPT's abort inside DocumentsWriter.abort on 7.4.
  5. rollbackInternalNoCommit's catch (Throwable throwable) (IndexWriter.java:2686-2724, "we tried to be nice about it: do the minimum") closes the reader pool, deleter and write lock and marks the writer closed; nothing finishes the DocumentsWriter abort. rollback() on a closed writer returns at once (shouldClose, :1374-1393), so no writer call is left that releases the skipped DWPTs' outputs.

What stays behind (executed)

#

In the tested runs, each skipped DWPT keeps 4 stored-fields IndexOutputs open: _N.fdt, _N.fdm and two Lucene90FieldsIndex temp outputs (the test framework's Asserting(Lucene104) codec, whose stored fields are the default Lucene90 format; other codecs may differ). A package-private probe showed it still registered in the pool, held by the thread that called rollback() and not aborted; a second rollback() left the outputs open. Controls pass: one buffered segment with the same throw, and two buffered segments with no throw. So the throw does not leak the segment it comes from, only the ones after it. The directory is in-heap (ByteBuffersDirectory), so the test shows unclosed IndexOutputs; on an FSDirectory each one holds an open file (FSDirectory.java:370-388; read, not executed).

Exposure and likelihood212 words
  • Who: any writer that buffers two or more in-memory segments (concurrent addDocument / updateDocument calls from several threads) when rollback() or the writer's close after a tragic error hits an unchecked exception or Error while aborting a segment that is not the last one in the loop.
  • Triggers: a custom InfoStream or logging bridge that throws (executed), an Error such as OutOfMemoryError while a segment's writers are closed (read), or a bug in an abort path (#11637, a real NPE on 7.4).
  • Effect: per skipped segment, 4 stored-fields outputs stay open in the tested runs; by reading, every segment after the failing one is skipped. The skipped segments stay registered and locked by the rollback thread (since 8.6.0), and abortPendingFlushes() / waitForFlush() are skipped (read). Since 4.7.1 the writer ends closed and a second rollback() is a no-op, so the caller has no IndexWriter call left that releases the handles.
  • Not affected: committed data and search results. The held locks had no observed effect on the closed writer.
  • Likelihood: rare: it needs an error inside an error path, and the result is a few handles on a writer that is already closed, so it is seldom noticed. The executed trigger, a throwing InfoStream, is an @lucene.internal debugging hook (InfoStream.java:23-29).

Why it looks unintended

#
  • LUCENE-5544 (4.7.1) fixed leaked handles after a failed rollback; its test throws from an InfoStream during rollback and requires "no locks or files held", but indexes from one thread.
  • abort() "must discard all currently buffered docs", and filterAndLock hands it every lock.
  • In 2011 this loop caught IOException and continued; that catch went in 2012 and was never restored.
The full argument269 words
  • The contract for this case: LUCENE-5544 (#6607, CHANGES 4.7.1: "Exceptions during IndexWriter.rollback could leak file handles and the write lock") added testExceptionDuringRollback (TestIndexWriterExceptions.java:1980-2051): an InfoStream that throws RuntimeException during rollback, a mock directory because "we want to ensure we don't leak any locks or file handles" (:2004), and "even though we hit exception: we are closed, no locks or files held" (:2042). It adds documents from one thread and opens an NRT reader before the rollback, so it never has two buffered segments in this loop. The repro uses the same oracle with two.
  • The method's javadoc: abort() "must discard all currently buffered docs" (DocumentsWriter.java:208-211); filterAndLock returns every DWPT "already locked" (DocumentsWriterPerThreadPool.java:161-166), so abort() owns every one of those locks.
  • History: LUCENE-3147 (c5f5f67b255, 2011) put catch (IOException ex) { // continue } inside this loop; LUCENE-4172 (2012) removed it as a redundant throws clause, when a DWPT's abort no longer declared IOException; LUCENE-8205 / LUCENE-8212 (7.4.0) let an Error propagate out of a DWPT's abort again, without restoring a per-DWPT catch (read). The same pattern was fixed at sibling sites: #4220 (LUCENE-3147, the full-flush abort: "we were not closing the remaining dwpt in the queues"), #6053 (LUCENE-4989, abortPendingFlushes), #6066 (LUCENE-5002, c0e7a50ab8e, 2013, 4.3.1: lockAndAbortAll unlocks every thread state if aborting fails, if (!success) unlockAllAfterAbortAll(); LUCENE-8212 kept this as its release closure).
  • Nothing allows it: no commit, comment or test says the remaining segments may be left un-aborted; the review of apache/lucene-solr#1397 (LUCENE-9304, which added filterAndLock here) has no comment on the error path.
The devil's-advocate check187 words

The strongest case for "intended": InfoStream is @lucene.internal and documented as a "Debugging API" (InfoStream.java:23-29), so a throwing logger is the application's bug; an Error is a tragedy Lucene does not try to recover from; the rollback error path deliberately does "the minimum"; the writer is closed anyway; and lockAndAbortAll (DocumentsWriter.java:266-324) also stops aborting at the first failure.

Why it fails: Lucene's own test throws from an InfoStream during rollback and requires no leaked handles, so that trigger is in contract; that minimal error path still closes the reader pool and write lock "to prevent leaks"; the leak hits the other, healthy segments, not the failing one; and the same loop is reached by an Error or an abort-path bug (#11637), which are not application code. The argument bears on severity (Low), not intent. Two concessions: testExceptionDuringRollback throws on "rollback: done finish merges" or "rollback before checkpoint" (TestIndexWriterExceptions.java:1982-1983), not on this DWPT "done abort" message; and lockAndAbortAll is a precedent only for unlocking every DWPT on failure, not for continuing to abort every one (it is not part of this claim).

Suggested fix

#

Recommended A. Catch per segment, finish the abort, rethrow (validated)

Catch each segment's failure inside DocumentsWriter.abort()'s loop (IOUtils.useOrSuppress), keep the unlock in finally, still run abortPendingFlushes() and waitForFlush(), then rethrow the first failure (+6 lines; it is lost if those two calls throw first). The repro passes with assertions on and off, and 10 nearby core test classes pass.

All options and trade-offs3 options · 474 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B and C are by reading.

A. Catch per segment, finish the abort, rethrow (validated) (recommended)

#

In DocumentsWriter.abort() (DocumentsWriter.java:218-226), +6 lines:

Throwable th = null;
for (final DocumentsWriterPerThread perThread : perThreadPool.filterAndLock(_ -> true)) {
  try {
    abortDocumentsWriterPerThread(perThread);
  } catch (Throwable t) {
    th = IOUtils.useOrSuppress(th, t); // keep aborting (and unlocking) the others
  } finally {
    perThread.unlock();
  }
}
flushControl.abortPendingFlushes();
flushControl.waitForFlush();
if (th != null) {
  throw IOUtils.rethrowAlways(th);
}

Trade-offs

  • The smallest change; on success nothing changes. It follows the "keep going, rethrow the first, suppress the rest" style of IOUtils.close.
  • An Error such as OOM is still rethrown after the cleanup, and rollback's error path still turns it into a tragic event (IndexWriter.java:2715-2722).
  • It rethrows before the end-of-method asserts and the success=true log line, so the outer catch still logs success=false.
  • It does not remove the skipped segments' files from the directory: a failing rollback never reaches the deleter refresh (IndexWriter.java:2666-2673), with or without this fix (a probe with the fix: no open outputs, four segment files left).
  • Caveat: the saved failure is rethrown only if the two cleanup calls return. An Error from abortPendingFlushes() (it catches only Exception, DocumentsWriterFlushControl.java:694-723) or a ThreadInterruptedException from waitForFlush() (:361-368) would escape first and replace it, as in B. Fix A was tested only on the executed path (active DWPTs, no pending or blocked flushes, no Error during cleanup).
  • CHANGES: a Bug Fixes entry under the next release.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off (4 open files); with the fix it passes, on and off.
  • With the fix and the repro: TestIndexWriterExceptions (incl. testExceptionDuringRollback), TestIndexWriterExceptions2, TestIndexWriterOnError, TestIndexWriterWithThreads, TestRollback, TestIndexWriterDelete, TestDocumentsWriterPerThreadPool, TestTragicIndexWriterDeadlock, TestIndexWriterThreadsToSegments and the repro: 10 classes, 100 tests, 0 failures, 11 skipped (10 @Nightly / @Monster, 1 @Ignore).
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test.
  • Earlier shadowed-class checks: the same change made three other tests pass (the finder's witness test, the independent reproduction's test and the cross-model reviewer's open-outputs test). The full lucene/core suite was not run.

B. Same idea with IOUtils.applyToAll

#

Run the abort-and-unlock body through IOUtils.applyToAll over the locked list, with abortPendingFlushes() and waitForFlush() in a finally.

Trade-offs

Shorter; as in A, an exception from the two cleanup calls would replace the original one. Not run.

C. Guard only the InfoStream calls in DocumentsWriterPerThread.abort()

#

Catch around the "now abort" / "done abort" messages.

Trade-offs

Covers the executed trigger only, not an Error while closing a segment's writers or a bug in an abort path (#11637). Not run; not recommended.

Downstream note

#

Downstream, a service whose InfoStream bridge to its own logger can throw, or that rolls back after an OutOfMemoryError, should not assume a failed rollback() released every file handle.

How it was found

#

Semi-formal: a proof-obligation audit of DocumentsWriter.abort()'s contract, that every in-memory segment filterAndLock locked is aborted and unlocked on every path. The loop without a catch fails the obligation on the exception path, and a JUnit test without package-private access witnessed it on stock main.

The method in full100 words
  • Obligation: for every DWPT returned by filterAndLock(_ -> true) (already locked, DocumentsWriterPerThreadPool.java:161-166), abort() must abort it and release its lock on every path, normal or exceptional, as its javadoc ("must discard all currently buffered docs") and LUCENE-5544's no-leak rule require.
  • Finding: the normal path discharges it; on the exceptional path the finally releases only the current DWPT and the missing catch leaves the loop (DocumentsWriter.java:218-224).
  • Witness: one JUnit test (no package-private access) with a one-shot throwing InfoStream and two buffered segments, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

History

#

Present since per-thread in-memory segments arrived in 4.0.0 (code from 2010-2011). Since 4.7.1, when LUCENE-5544 made a failed rollback close the writer, a second rollback() no longer cleans up; the skipped segments also stay locked since 8.6.0 (LUCENE-9304). Every release run from 4.0.0 to 10.6.0 fails, and main still fails.

Versions tested8 rows

Introduced on the LUCENE-2324 realtime branch: from d1142608ad4 (2010-07-21) its abort looped over every thread state with no per-thread catch (DocumentsWriterThreadPool.abort()), and 2bd8e508dea (2011-01-13) gave the loop its current lock / try / finally-unlock shape; landed on trunk in 2a969f828c1 (LUCENE-3023 "Land DWPT on trunk", 2011-05-01); first GA release 4.0.0. LUCENE-5544 (265809a3556, 2014-03-21, 4.7.1) made a failed rollback close the writer, so the second rollback() that cleaned up on 4.0.0 and 4.7.0 became a no-op. LUCENE-9304 (2602269f3ec on master, 2020-04-11; 8.6.0 ships the backport 83b34d47900) locked every DWPT up front with filterAndLock(_ -> true), so the skipped ones also stay locked. abort() is unchanged on upstream main f72004515ec (2026-11-03) and branch_10_6.

Older releases ran an API-adapted copy of the test (4.x-6.x with assertions on, which their test framework requires).

Impact note
Hits applications that index from more than one thread (so the writer buffers two or more in-memory segments) when rollback() or the writer's tragic self-close gets an unchecked exception or Error while aborting a segment that is not the last one (executed: an application InfoStream that throws on the 'done abort' line; by reading only: an Error such as OutOfMemoryError that IOUtils.closeWhileHandlingException rethrows while that segment's writers are closed): the other segments keep their stored-fields IndexOutputs open (.fdt, .fdm and two stored-fields temp outputs each), stay registered in the pool and locked by the thread that called rollback() (since 8.6.0), and abortPendingFlushes()/waitForFlush() are skipped (by reading); the writer ends closed and a second rollback() is a no-op, so the handles cannot be released; -ea and -da, no scale needed, no committed data or search result affected, and the held locks had no observed effect on the closed writer.
Summary
Two threads add documents to one IndexWriter, so it buffers two in-memory segments, and then you call rollback(); while the first segment is being aborted an exception is thrown (here by the writer's InfoStream). You expect rollback() to pass that exception on but still release everything, which is what Lucene's own TestIndexWriterExceptions#testExceptionDuringRollback requires ('we are closed, no locks or files held'). Instead DocumentsWriter.abort() stops at the failing segment: the other segment is never aborted, stays locked by the thread that called rollback() and keeps its four stored-fields outputs open, and because the writer is now closed nothing can release them.
