SearcherLifetimeManager.prune sorts searchers by first-record time, so PruneByAge can drop the current searcher

When a request records an older searcher after another request has recorded the refreshed one, SearcherLifetimeManager.prune takes the older searcher for the newest, and PruneByAge drops the current searcher even right after record() returned a token for it: acquire(token) returns null. Low impact, in every release since 3.5.0.

The finding in 30 seconds

#

prune should rank the kept searchers newest first, but it ranks them by when each was first recorded. So when an older searcher is recorded late, it is taken for the newest (age 0), and the current searcher is aged from that late record and pruned.

Background: keeping searchers for follow-up requests

#
  1. SearcherManager hands out the current IndexSearcher and, after index changes, opens a new one (maybeRefresh()).
  2. SearcherLifetimeManager keeps older searchers open for follow-up requests: record(searcher) returns a token (the reader version), and acquire(token) returns the same searcher for the next page, or null once it was pruned ("session timed out").
  3. prune(pruner) passes the kept searchers newest first, each with its age, the time since it was the current searcher. PruneByAge(maxAge) drops those older than maxAge, so the newest searcher, age 0, should always stay.

The finding, step by step

#
  1. You follow the class javadoc: each new request takes the latest searcher from SearcherManager and calls record() for a paging token; a reopen thread calls prune(new PruneByAge(maxAge)).
  2. Request A takes searcher S1. One document is added and maybeRefresh() makes S2 current. Request B records S2; then A, still running, records S1, so S1's first record comes after S2's.
  3. You expect prune to pass S2 first with age 0 ("newest to oldest"; age is the time since a searcher was current), so S2 and every token for it survive.
  4. Instead prune sorts by first-record time: S1 gets age 0 and S2 is aged from S1's record. 250 ms after A's record, request C records S2 and gets a token, prune(new PruneByAge(0.1)) drops S2 anyway, acquire(token) returns null, and the older S1 stays open.

Who is affected

#

Users of the opt-in, experimental SearcherLifetimeManager where a request can record an older searcher after the refreshed one was recorded, for example by recording after running the query. They get a spurious "session timed out" null until the next record(), an older reader kept open longer, and count-based pruners keep the wrong searcher. No wrong results.

Mechanism, terms and numbers711 words

SearcherLifetimeManager keeps older searchers open so that a follow-up request (the next page) can reuse the searcher of the first request through the token record() returns. prune(Pruner) is documented to pass the searchers newest to oldest, each with its age, the time since it was the current searcher, and PruneByAge drops only searchers older than the newest by more than maxAge. The code instead sorts by the time each reader version was first recorded. When a request records an older searcher for the first time after another request has recorded the refreshed one, prune takes the older searcher for the newest (age 0) and ages the current searcher from that late record. PruneByAge then drops the current searcher, even right after record() returned a token for it, and keeps the older one. The effect is small and recoverable: acquire(token) returns the documented "session timed out" null until the next record() adds the searcher back, the older reader stays open longer than maxAge, and a count-based pruner keeps the wrong searcher. No search result is wrong. It dates from 3.5.0, when the class was added, and every release tried since then fails.

The mechanism (main 645d4fe14a20)

#
  1. The sort key is the first-record time. SearcherTracker stores recordTimeSec = System.nanoTime() / NANOS_PER_SEC in its constructor (SearcherLifetimeManager.java:97-104), and compareTo is Double.compare(other.recordTimeSec, recordTimeSec) under the comment "Newer searchers are sort before older ones" (:106-110).
  2. It is set once per reader version. record() looks the tracker up by reader version and creates one only if none exists (:146-155); a later record() of the same searcher returns the same token and changes nothing (:156-164). Its javadoc invites repeated calls: "Always call this when you've obtained a possibly new IndexSearcher ... It's fine if you already passed the same searcher to this method before" (:132-134).
  3. Ages come from the sorted neighbour. prune copies and sorts the trackers (:239-243), gives the first age 0 (:248-249) and each later one now - lastRecordTimeSec, the record time of the tracker before it in that order (:251, :263), as the comment says: "First tracker is always age 0.0 sec, since it's still 'live'; second tracker's age (= seconds since it was 'live') is now minus first tracker's recordTime" (:253-256).
  4. What goes wrong. Record S2 at t0, then the older S1 for the first time at t1 > t0. The sorted list is [S1, S2]: S1 gets age 0, S2 gets now - t1. PruneByAge returns ageSec > maxAgeSec (:222-224), so S2 is removed and its reader released (:257-262) once now - t1 > maxAge; acquire(version) then finds no tracker and returns null (:177-185).
  5. Why it heals. The token is the reader version (:164). While S2 is SearcherManager's current searcher its reader stays open, so the next record(S2) creates a new tracker with a fresh record time, which sorts first, and old tokens for S2 resolve again; S1 is then aged from that re-record.

The numbers (executed)

#
  • Minimal test, no sleep: record S2, record S1, record S2 again for a token, prune(new PruneByAge(0)) (which must keep the newest searcher): acquire(token) is null. Fails 1/1 with -ea, 10/10 and 20/20 with -da on main; also on 10.6.0 and 9.12.3.
  • First repro: 250 ms after A's late record of S1, request C records S2 and prune(new PruneByAge(0.1)) drops it.
  • Impact demo: 1.5 s after the two records, prune(new PruneByAge(1.0)): acquire(token of S2) is null while acquire(token of S1) returns the older searcher; with the fix it is the other way round.
  • Bounded-exhaustive test of the real classes over all 8,892 operation sequences of length up to 10: 520 order mismatches and 380 cases where the newest recorded searcher was pruned on stock, all and only in sequences with a late first record; 0 with the fix.
  • With the javadoc's PruneByAge(600.0) the same path drops S2 once 600 s have passed since the late record, whether or not a newer searcher is first recorded in the meantime; if none is, S2 is still the current searcher when it is dropped (by reading the code; the runs above are that path scaled down).
Exposure and likelihood318 words
  • Who. Applications that opt into SearcherLifetimeManager (@lucene.experimental) with the javadoc's per-request acquire-then-record pattern and a time- or count-based Pruner, where one request's acquire-to-record window can span a refresh plus another request's record() of the refreshed searcher, for a searcher no request recorded while it was current. This is a legal variation of the javadoc's acquire-then-record pattern: any delay between acquire() and record() (for example recording after running the query) opens the window, and frequent NRT refreshes with light traffic make it likelier.
  • What goes wrong. Follow-up requests on the current searcher get acquire(token) == null, the documented "session timed out" outcome, until the next record() adds it back, so the user sees a spurious timeout or the application restarts the search. The older reader stays open longer than maxAge: it is dropped only maxAge after a newer searcher gets a new tracker (for example the re-record of S2), and nothing in the class bounds how long that takes. A count-based Pruner ("keep the newest N", the use the design review discussed) keeps S1 and drops S2.
  • Not hit. Lucene returns no wrong hit, count or score, nothing is corrupted and nothing throws (what the application does after a null from acquire() is up to it). Applications that give every searcher its first record from one refresh path (the initial searcher before requests start, then each new searcher right after maybeRefresh(), as ShardSearchingTestBase does) avoid the trigger: a request's later record() then finds the existing tracker and changes nothing, unless that searcher has already been pruned.
  • Default vs opt-in, scale. Opt-in API; no special codec or settings; two searchers and one document are enough. Same failure with assertions on and off.
  • How likely. Rare: it needs the out-of-order first record and, for the current searcher to be dropped, no newer searcher first recorded within maxAge afterwards. The saved searches found no public report.

Minimal repro

#

One JUnit test, one method, single thread, public API, no sleep: record the current searcher, record the older one, record the current one again for a token, prune(new PruneByAge(0)), then acquire(token) must not be null. It fails with assertions on and off on main, and on 10.6.0 and 9.12.3.

More files, environment, full output401 words
  • Deterministic. Each record() of a new version reads System.nanoTime(), so S1's record time is later than S2's, and S2's computed age is positive, whenever the clock advances between the calls, which it did in every run; PruneByAge(0) drops any searcher with age > 0. A correct implementation gives the newest searcher age 0 and keeps it. It failed 10 of 10 with --iters 10; the seeds DEADBEEF and 5EED1066 fail the same way through gradle. nanoTime() only promises values that do not decrease: on a clock so coarse that both records read the same value the test could pass on stock, but it cannot fail on a correct implementation.
  • PruneByAge(0) is legal. The constructor rejects only negative values; with 0 it keeps exactly the searchers whose computed age is 0; a correct implementation gives that age to the newest searcher, so the newest must survive. The study's first repro used a 250 ms sleep against PruneByAge(0.1) and fails the same way; it is supplementary evidence only.
  • The test is the study's minimal test with its one comment reworded onto two lines, so that it passes Lucene's checkGoogleJavaFormat; the code is unchanged, and the assertion moved from line 41 to line 42.
  • Resources. There is no try/finally, so a failing run leaves its readers and the IndexWriter open. With the documented seeds the run reports only the one AssertionError. When newDirectory() picks a file-system directory (rare outside nightly runs; seen in one of ten iterations with seed 1066FAC7, and with seed DEADBEEF when the directory is forced to MMapDirectory) it also reports a suite-level "file handle leaks" failure for write.lock. With a fix it passes and closes everything. As a regression test, use this same test.

Why it looks unintended

#
  • prune promises "newest to oldest"; PruneByAge drops only searchers older "than the newest searcher". S2 is newest by version, by being current and by last record.
  • LUCENE-3639 made age the time since the searcher was replaced, "not how long ago the searcher was first enrolled"; the sort stayed.
  • Nothing requires recording searchers in open order.
The full argument271 words
  • prune: "The entries are passed to the Pruner in sorted (newest to oldest IndexSearcher) order" (SearcherLifetimeManager.java:228-229).
  • Pruner.doPrune: "@param ageSec how much time has passed since this searcher was the current (live) searcher" (:201). S2 is still current yet gets a positive age; S1, which S2 replaced, gets 0.
  • PruneByAge: "drops any searcher older by more than the specified seconds, than the newest searcher" (:208-209). The code comment: "First tracker is always age 0.0 sec, since it's still 'live'" (:253-256).
  • LUCENE-3639 (#4713, 3.6.0). Michael McCandless wrote that the patch makes it "compute age by how long ago the searcher was replaced with a new searcher (not how long ago the searcher was first enrolled)"; lucene/CHANGES.txt says the same ("compute age to be how long ago the searcher was replaced with a new searcher"). The sort by first-record time stayed.
  • The design review relied on the order. On LUCENE-3486 (#4560), Shai Erera noted that a "newest 5 searchers" pruner can count doPrune() calls "because prune(Pruner) guarantees that the searchers are passed newest to oldest".
  • No call-order precondition. Neither the class javadoc nor record() asks callers to record searchers in the order they were opened, and record() is safe to call from concurrent threads (putIfAbsent, "Another thread beat us", :151-155).
  • Tests. TestSearcherManager uses the acquire-then-record pattern from search threads beside a reopen thread but accepts a null and never asserts which searcher is pruned; ShardSearchingTestBase records each node's initial searcher at startup and each new searcher in the reopen thread, which avoids the trigger. No test pins the record-time order.
The devil's-advocate check202 words

The case for intended (made by an executing reviewer from another model family, OpenAI GPT-5.6): record() is the session's recency event; the order has been by record time since 3.5.0, whose javadoc defined age as "how long ago this searcher was recorded vs the most recently recorded searcher"; a null from acquire() is documented; the class is experimental; and pure version order would expire at once a token just returned by the late first record of an older searcher.

Why it fails. (1) LUCENE-3639 replaced the 3.5 wording on purpose with "since this searcher was the current (live) searcher" and "not how long ago the searcher was first enrolled". (2) In the repro S2 is the newest under every reading: highest version, still current, and the most recently recorded (request C records it after A records S1). Stock keeps S2 only if "newest" means "first recorded most recently", the reading the author rejected. (3) The documented null is for searchers that "timed out", and PruneByAge limits that to searchers older than the newest. (4) The token-window point is about a fix, not the bug; the recommended fix keeps that window. The other cross-model lenses, independent verifiers and the adjudication called it real.

Suggested fix

#

Recommended C. Version order; age from the earliest newer record, never from before the searcher's own first record

Sort by reader version, newest first, and age each older searcher from the earliest record of a newer one, but never from before its own first record, so a just-issued token keeps a full window. Validated with gradle: the repro passes, TestSearcherManager 12/12, nightly TestShardSearching, format and lint checks.

All options and trade-offs3 options · 912 words

All options sort by reader version, newest first; they differ in how they age the searchers after the first. This relies on the reader versions of one index growing with every change, which DirectoryReader.getVersion documents ("This version is advanced every time a change is made with IndexWriter"); the class's version keys only need versions to be unique. So the fixes assume that one SearcherLifetimeManager serves the searchers of one index (for example from one SearcherManager). Option C was applied in a scratch worktree of main 645d4fe14a20 and run with gradle; A and B were checked by the study's standalone runs, TLA+ model and bounded-exhaustive test. Which age policy to adopt for a late first-recorded older searcher is the maintainers' call; the claim holds under all three. Workaround today: give every searcher its first record from one refresh path, the initial searcher before requests start and each new searcher right after maybeRefresh(), with all refreshes on that thread (as ShardSearchingTestBase does).

C. Version order; age from the earliest newer record, never from before the searcher's own first record (validated by the checks) (recommended)

#

compareTo becomes Long.compare(other.version, version). In prune, each later searcher's age is now - max(earliest record time of the newer searchers already passed, its own record time). The running minimum ages an older searcher from the earliest first record of any newer searcher, the earliest time the class can see that it had been replaced (it sees only first-record times). The max keeps stock's full maxAge window for a token returned by an older searcher's first record.

Trade-offs

An older searcher first recorded late lives up to maxAge after its own record, not after it was replaced. The old comment "now minus first tracker's recordTime" (:253-256) would need updating; the diff leaves it as is. The root-cause reviewer's coupled case (a newer searcher recorded late between two others) is covered only when the older searcher was first recorded before the newer ones: the reviewer's three-searcher test, whose two older searchers are first recorded 300 ms after the newest, fails with C by design and passes with B. The minimal test covers only the two-searcher order bug; if the running minimum stays, a three-searcher test would pin it.

A. Sort by version only (validated by the checks)

#

Change compareTo to Long.compare(other.version, version) and keep the age loop. One line; fixes the order and never drops the newest searcher.

Ages a late first-recorded older searcher from the newer searcher's earlier record, so the token record() has just returned for it can expire at the next prune; the pairwise "previous tracker" age can keep an older reader too long when a newer one was recorded late between two others.

Downstream note

#

Services that page results with these tokens may show a spurious "session timed out" on the current searcher and keep an older point-in-time reader open longer than maxAge; giving every searcher, the initial one included, its first record from the refresh path avoids it.

LFV-1066, snapshot of 2026-11-04

Registry title
SearcherLifetimeManager.prune orders searchers by the time each was first recorded instead of newest to oldest, so when an older searcher is first recorded after the current one, PruneByAge drops the current searcher (even right after record() returned a token for it) and keeps the older one
Area
core / search: SearcherLifetimeManager (keeping old searchers for follow-up requests such as paging)
Priority
Low, rank 936: When an older searcher is first recorded late, the opt-in experimental SearcherLifetimeManager can prune the current searcher and keep the older one, so paging requests get the documented 'timed out' null. No result is wrong, the timing window is narrow and nobody has reported it since 3.5.0, so it is Low.
Impact class
minor
Impact note
Applications that use the opt-in, @lucene.experimental SearcherLifetimeManager with the class javadoc's per-request pattern (acquire from SearcherManager, then record) and prune(new PruneByAge(maxAge)): when a request records an older searcher for the first time after another request has already recorded the refreshed one, prune treats the older searcher as the newest, so once maxAge has passed with no newer searcher first recorded it drops SearcherManager's current searcher (acquire(token) returns the documented 'session timed out' null for tokens just issued for it, until the next record() adds it back) and keeps the older reader open; a count-based Pruner keeps the wrong searcher; no search result is wrong and nothing is corrupted, it needs no scale and fails the same way with -ea and -da.
Summary
You use SearcherManager with SearcherLifetimeManager as the javadoc shows: request A acquires searcher S1, the manager refreshes to S2, request B acquires and records S2, and then A records S1. You expect prune to pass the searchers newest to oldest, as its javadoc says, so PruneByAge never drops S2, the current searcher. Instead prune sorts them by the time each was first recorded, so S1 goes first with age 0 and S2 is aged from S1's late record: 250 ms later, request C records S2 and gets a token, prune(new PruneByAge(0.1)) drops S2 anyway, acquire(token) returns null, and the older S1 is kept.

cbdaea3486e on trunk (LUCENE-3486 = apache/lucene#4560, author mikemccand, 2011-10-10T22:05:55Z) and its branch_3x backport 346799474a2 the same day, first released in 3.5.0 [read: SearcherTracker.compareTo has sorted by recordTimeSec since the class was added; 05509413d45 (LUCENE-4851, 2013) only rewrote it with Double.compare; exec: 3.4.0 lacks the API, 3.5.0 fails]. The age contract the order now breaks came with LUCENE-3639 (aee83bf7eef on trunk, 906894ad97a on branch_3x, 2011-12-18, first released in 3.6.0), which redefined ageSec as the time since the searcher was the current (live) searcher and kept the record-time sort, so there is no later regression (2011-10-10)
