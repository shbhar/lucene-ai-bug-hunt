SpatialQuery's dense WITHIN/DISJOINT scorers return no hits when a PointValues reports an upper-bound bulk-iterator cost()

A WITHIN or DISJOINT query on multi-valued points (every document has one) counts 0 instead of 1 when a PointValues reports an upper-bound bulk-iterator cost(), as the javadoc allows: a cost counter of 0 is read as "no match". Latent (Lucene's points code reports exact costs); 9.1.0 to 10.6.0, main.

The finding in 30 seconds

#

For WITHIN and DISJOINT on a multi-valued points field in which every document has a value, SpatialQuery starts from "every document matches", clears documents with a point outside the shape, and keeps a counter that starts at the number of points. Each bulk iterator's cost(), which Lucene documents as an estimate, is subtracted from that count, and a count of 0 is read as "no hits".

  1. Index doc 0 with one LatLonPoint (1, 1) and doc 1 with two, (50, 50) and (60, 60): one segment, 2 documents, 3 points.
  2. Read it through a FilterLeafReader whose PointValues delegates everything, but hands each value to the bulk callback visit(DocIdSetIterator, byte[]) as a one-document iterator with cost() = maxDoc = 2, an upper bound.
  3. Count LatLonPoint.newGeometryQuery("p", WITHIN, square 0..10 x 0..10). You expect 1, because doc 0 is inside; with the exact cost 1 the count is 1.
  4. Instead the count is 0, with no error. The scorer starts a counter at 3 points and subtracts each bulk iterator's cost(): doc 1's two outside points take 2 each, 3 -> 1 -> 0. At 0 it returns "no hits" without looking at doc 0's bit, which is still set.
  5. With assertions on, the scorer's own invariant cost[0] > 0 || result.cardinality() == 0 fails at SpatialQuery.java:362. DISJOINT loses its hit the same way when the document that fails has two points (doc 0 at (1, 1) and (2, 2)); with this test's data it still counts 1.

Who is affected

#

Only applications with their own PointValues (an @lucene.experimental API, in a FilterLeafReader wrapper or a custom points format) whose bulk iterators report a wrong cost() (too high, or 0); the default codec and stock readers are never hit. Then LatLonPoint WITHIN or DISJOINT geometry queries (and LatLonShape/XYShape ones) silently return no hits for the segment.

Mechanism, terms and numbers589 words

For WITHIN and DISJOINT on a multi-valued points field in which every document has a value, SpatialQuery's dense scorer starts from "every document matches", clears documents that have a point outside the shape, and keeps a counter that starts at the number of points and goes down as documents are cleared. When the counter is 0 it returns DocIdSetIterator.empty() without looking at the bit set. Since LUCENE-10233 (#499, 9.1.0) the counter is reduced by iterator.cost() of the bulk IntersectVisitor callbacks, and cost() is documented as an estimate, "generally an upper bound ... may be a rough heuristic, hardcoded value, or otherwise completely inaccurate". A PointValues that reports an upper bound can therefore drive the counter to 0 while matching documents are still set: the segment silently returns no hits (LatLonPoint geometry queries, and by the same code LatLonShape/XYShape queries). Every PointValues in Lucene reports exact costs, so only application-written points code is hit.

Terms

#
  • PointValues and IntersectVisitor: a segment's points (here LatLonPoint values) sit in a tree; a query walks it with a visitor. For a leaf cell that crosses the query shape, the tree passes each value to visit(int docID, byte[] value), or several documents with the same value at once to the bulk callback visit(DocIdSetIterator, byte[] value). visit(DocIdSetIterator) is the bulk form for cells wholly inside the visitor's region.
  • DocIdSetIterator#cost(): "Returns the estimated cost ... generally an upper bound of the number of documents this iterator might match, but may be a rough heuristic, hardcoded value, or otherwise completely inaccurate" (DocIdSetIterator.java:178-184).

The bug

#
  1. WITHIN and DISJOINT use the dense scorer getDenseScorer when the segment has more points than documents (SpatialQuery.java:296-300).
  2. When every document has a value, the scorer sets every bit and starts a counter at values.size(), the number of points (:344-350).
  3. The inverse visitor clears documents that have a point outside the shape. Its bulk callback subtracts the iterator's estimate: result.andNot(iterator); cost[0] = Math.max(0, cost[0] - iterator.cost()); (:680-684), and visit(DocIdSetIterator, byte[]) forwards to it (:695-700).
  4. At the end: cost[0] == 0 ? DocIdSetIterator.empty() : new BitSetIterator(result, cost[0]) (:363-364). The bit set is not consulted.

With an upper-bound cost the subtraction removes more points than were delivered, the counter reaches 0 early, and documents whose bits are still set are dropped. The dense INTERSECTS branch (:322-330) adds iterator.cost() instead (:492) and has the same test, so there a cost of 0 loses its hits; so does WITHIN or DISJOINT when some document has no value, where the counter starts at 0 and is summed (:351-361, :557). The per-document decrement cost[0]-- (:667-670) is not clamped, so after a clamped bulk step the counter can reach -1 and new BitSetIterator(result, -1) throws. CONTAINS counts one document at a time and is not affected.

The numbers

#

Two documents, three points: doc 0 at (1, 1), doc 1 at (50, 50) and (60, 60); WITHIN the square 0..10 x 0..10. The counter starts at 3. Each of doc 1's two points is delivered with cost() = maxDoc = 2: 3 -> 1 -> 0. Doc 0's bit is still set, but the query counts 0. With the exact cost 1: 3 -> 2 -> 1, and the count is 1.

Lucene's own points code reports exact costs: BKD passes DocBaseBitSetIterator(bitSet, count, ...) (util/bkd/DocIdsWriter.java:284), DocIdSetIterator.range(start, start + count) (:485), and BKDReaderDocIDSetIterator.cost() returns its run length (util/bkd/BKDReader.java:1074-1077).

Exposure and likelihood226 words
  • Who is hit. Applications that implement PointValues/PointTree themselves and hand the bulk callbacks iterators with a wrong cost(). A cost above the points delivered hits WITHIN and DISJOINT when every document of the segment has a value (this test). A cost of 0 hits the dense INTERSECTS branch, and WITHIN and DISJOINT when some document has no value (executed in a follow-up probe: 0 instead of 1 for both). A wrapper that filters BKD's iterators and passes on the delegate's exact cost does not, by reading, reach it.
  • What breaks. LatLonPoint.newGeometryQuery (executed) and newPolygonQuery (always INTERSECTS, LatLonPoint.java:310-311, so only the dense INTERSECTS branch with a cost of 0, executed), and LatLonShape/XYShape queries, which share the scorers (LatLonShape WITHIN executed in a fact-check probe; XYShape by reading). The segment returns 0 hits instead of the true hits; silent with assertions off. If a per-document callback follows a bulk one that clamped the counter at 0, the query instead throws IllegalArgumentException: cost must be >= 0, got -1 (executed). XYPointField geometry queries use XYPointInGeometryQuery and are not affected.
  • Default vs opt-in. Default codec, IndexSearcher and IndexWriterConfig; the opt-in part is the custom points code.
  • Scale. Two documents and three points suffice; index size does not matter.
  • How likely. Contrived: no producer in Lucene, and no report since 9.1.0. Priority Low.

Why it looks unintended

#
  • DocIdSetIterator#cost() is documented as an estimate that "may be ... completely inaccurate"; the bulk callbacks add no condition.
  • SpatialQuery's own assert, cost[0] > 0 || result.cardinality() == 0, says a 0 counter means an empty set; legal input breaks it.
  • PointRangeQuery uses such a counter only as a cost estimate and keeps its hits under a wrapper that forwards grow().
The full argument208 words
  • The contract allows the input. cost(): "generally an upper bound of the number of documents this iterator might match, but may be a rough heuristic, hardcoded value, or otherwise completely inaccurate" (DocIdSetIterator.java:178-184). visit(DocIdSetIterator) and visit(DocIdSetIterator, byte[]) say nothing about cost (PointValues.java:291-332). maxDoc for a one-document iterator is an upper bound, the case the javadoc names first.
  • The authors' invariant. assert cost[0] > 0 || result.cardinality() == 0; precedes each emptiness test (SpatialQuery.java:327, :362, :377).
  • Siblings. PointRangeQuery and LatLonPointDistanceQuery build the same counter from the same callbacks but pass it only to BitSetIterator as its cost (PointRangeQuery.java:318-319, LatLonPointDistanceQuery.java:157). With a wrapper of the same kind that also forwards IntersectVisitor#grow, PointRangeQuery keeps its hits, also on its counter path (single-valued field; executed in the fact check). Only SpatialQuery uses it as an emptiness test.
  • History. The test came with LUCENE-9523 (fbf8e4f0448, 2020), when every callback counted one document, so it was exact. #499 (5f09bb3fab0, 2021) made the bulk overrides add or subtract iterator.cost(); no review comment on #499 or #1007 discusses whether that cost is exact. #14150 (2025) clamped the visit(IntsRef) counters at 0 to stop negative values and kept the test.
The devil's-advocate check97 words

The case: every Lucene PointValues reports exact bulk costs, TestBKD asserts cost == numberOfPoints (TestBKD.java:990-998, since LUCENE-8885), and the APIs are @lucene.experimental, so a custom implementation is expected to behave like BKD.

Why it fails: that is a property of BKD and a test of BKD, not a documented requirement on PointValues; the only written contract, the cost() javadoc, says the opposite; @lucene.experimental permits API changes, not wrong hits for an implementation that follows the interface. A maintainer may still prefer to document an exact-cost requirement, so the fix section offers that option.

Suggested fix

#

Recommended Decide emptiness from the bit set (validated)

Decide emptiness from the bit set, result.nextSetBit(0) == NO_MORE_DOCS, in the three dense scorers, drop their asserts, and keep the counter only as the cost estimate (+10/-7 lines). Validated: the test passes with assertions on and off, and so do the LatLon and XY spatial suites. Alternative: document that bulk iterators must report exact costs.

-      assert cost[0] > 0 || result.cardinality() == 0;
       final DocIdSetIterator iterator =
-          cost[0] == 0 ? DocIdSetIterator.empty() : new BitSetIterator(result, cost[0]);
+          result.nextSetBit(0) == DocIdSetIterator.NO_MORE_DOCS
+              ? DocIdSetIterator.empty()
+              : new BitSetIterator(result, cost[0]);

Decide emptiness from the bit set (validated) (recommended)

#

In getDenseScorer, the dense INTERSECTS branch and getContainsDenseScorer, test the bit set instead of the counter and drop the three asserts; clamp the per-document decrement of the inverse visitor at 0 (cost[0] = Math.max(0, cost[0] - 1)). The counter stays as BitSetIterator's cost estimate. Changing getContainsDenseScorer is for consistency only.

-      assert cost[0] > 0 || result.cardinality() == 0;
       final DocIdSetIterator iterator =
-          cost[0] == 0 ? DocIdSetIterator.empty() : new BitSetIterator(result, cost[0]);
+          result.nextSetBit(0) == DocIdSetIterator.NO_MORE_DOCS
+              ? DocIdSetIterator.empty()
+              : new BitSetIterator(result, cost[0]);

Trade-offs

One scan of the bit set up to its first set bit; a full scan only when the set is empty, the case the counter shortcut saved. A non-empty result may now carry cost 0, which BitSetIterator accepts; at most it skews cost-based planning, and Math.max(cost[0], 1) would avoid it.

Document an exact-cost requirement on the bulk callbacks

#

State on IntersectVisitor#visit(DocIdSetIterator) and visit(DocIdSetIterator, byte[]) that cost() must equal the number of documents the iterator delivers.

Trade-offs

No code change and the shortcut stays, but it adds a stricter rule than cost()'s own javadoc, and a violation still gives silent wrong hits. Not run.

Count delivered documents in the bulk callbacks

#

Iterate the bulk iterator and count what it delivers instead of reading cost().

Trade-offs

Exact. Iterating the iterator to count gives up the bulk andNot/or speed-up that #499 added; deriving the count from the bit set after the bulk operation would keep it, at the price of a bit count. Not run.

Downstream note

#

A product that runs WITHIN or DISJOINT shape queries over its own PointValues implementation, for example as an exclusion clause, should make sure its bulk iterators report exact costs.

How it was found

#

Semi-formal: a proof-obligation check asked whether each shortcut in SpatialQuery's dense scorers holds for every input the IntersectVisitor and DocIdSetIterator#cost() contracts allow. The shortcut "counter 0 means no match" does not, because the counter is built from cost(). A JUnit test on main turned that into a missed document.

The method in full100 words

Method: semi-formal (a proof-obligation check of SpatialQuery's contract, witnessed by an executable repro, on main 5adff78bb168, 2026-11-04).

  • Obligation. The dense scorers may return "empty" only when no document in the segment matches.
  • Finding. They decide it from a counter, and since #499 the counter is built from DocIdSetIterator#cost(), which the contract lets be any estimate. An over-estimate drives it to 0 while bits are set.
  • Witness. A JUnit test on the stock main jars: a WITHIN count of 0 instead of 1, with assertions on and off; the same wrapper with the exact cost 1 gives 1.

Summary
A PointValues wrapper delegates everything to the default codec's points but hands each visited document to IntersectVisitor#visit(DocIdSetIterator, byte[]) as a one-document BitSetIterator whose cost() is maxDoc, an upper bound that the DocIdSetIterator#cost() javadoc explicitly allows ('generally an upper bound ... may be ... completely inaccurate'). Two documents, one with a single LatLonPoint inside a square and one with two LatLonPoint values outside it: LatLonPoint.newGeometryQuery(WITHIN, square) should count 1, as it does with the exact cost 1. Instead SpatialQuery's dense WITHIN scorer starts a counter at size() = 3 points, subtracts the reported cost 2 for each of the outside document's two points (3 -> 1 -> 0), reaches 0 and returns DocIdSetIterator.empty() although the inside document's bit is still set, so the query counts 0 with -da and trips the internal assert 'cost[0] > 0 || result.cardinality() == 0' (SpatialQuery.java:362) with -ea.
Introduced
