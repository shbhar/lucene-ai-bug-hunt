FieldInfos.hasFreq() says a segment has term frequencies when one of its fields is not indexed

A segment with no term frequencies still reports FieldInfos.hasFreq() == true once it holds one field with IndexOptions.NONE (stored-only, doc-values-only, points-only or vector-only). Lucene's own indexing and search are unaffected: only the getter and the IndexWriter infoStream word "freqs" are wrong, in every release since 5.0.0.

The finding in 30 seconds

#

FieldInfos caches "does any field have X?" flags for each segment. Three of them test a field's IndexOptions so that a not-indexed field (NONE) never counts. hasFreq tests != DOCS instead, and NONE passes that test.

Background in three steps

#
  1. Every field has IndexOptions: NONE for a field without postings (stored-only, doc-values-only, points-only or vector-only; the javadoc calls it "Not indexed"), DOCS for keyword fields such as StringField (no frequencies), and DOCS_AND_FREQS or more for text fields.
  2. A segment's FieldInfos lists its fields and caches "does any field have X?" flags: hasPostings(), hasFreq(), hasProx(), hasOffsets() and more.
  3. Inside Lucene, hasFreq() is read only by the IndexWriter infoStream lines that describe a flushed or merged segment, such as "new segment has no vectors; no norms; no docValues; no prox; freqs".

The finding, step by step

#
  1. Index one document whose only field is new StoredField("f", "v"), with a plain IndexWriterConfig, and open a reader on the one segment.
  2. Its FieldInfos says hasPostings() is false: the field's index options are NONE, documented as "Not indexed". So you expect hasFreq(), documented as "Returns true if any fields have freqs", to be false too.
  3. You get hasFreq() == true, with assertions on and off. The flag is computed as indexOptions != DOCS (FieldInfos.java:116), and NONE passes that test; the sibling flags use != NONE or subsumes(...) and leave it out.
  4. The same happens with a doc-values-only, points-only or vector-only field, and with a keyword StringField (DOCS only) plus a StoredField of another name: false alone, true once the stored field is added (a StringField that is itself stored, or has doc values of the same name, stays false: that is one DOCS field). The flush log line then ends "no prox; freqs". A TextField correctly gives true.

Who is affected

#

Callers of the experimental getter FieldInfos.hasFreq(), and readers of the IndexWriter infoStream, are told "freqs" for every segment whose indexed fields are all DOCS-only (or that has none) once it also holds a field of another name with IndexOptions.NONE (stored-only, doc-values-only, points-only or vector-only). Default settings, one document. Lucene's own logic does not branch on it.

Mechanism, terms and numbers678 words

FieldInfos.hasFreq() is documented as "Returns true if any fields have freqs". The FieldInfos constructor computes it as hasFreq |= info.getIndexOptions() != IndexOptions.DOCS (FieldInfos.java:116), and that test is also true for IndexOptions.NONE, the index options of every field without postings ("Not indexed"; points and vectors have their own index structures but still have NONE). A segment whose only field is a StoredField therefore reports hasPostings() == false but hasFreq() == true, and a segment of DOCS-only keyword fields plus any field that is not indexed for postings (a StoredField, or a doc-values-only, points-only or vector-only field) claims frequencies it does not have. The neighbouring flags hasPostings, hasProx and hasOffsets exclude NONE. PerFieldMergeState.FilterFieldInfos repeats the formula (PerFieldMergeState.java:115).

The method had an explicit "is indexed" guard when it was added in 4.0.0; the 2014 cleanup LUCENE-6041 (first released in 5.0.0) deleted it on this line. Lucene's own indexing, merge and search code does not branch on it: inside Lucene only the IndexWriter infoStream flush and merge lines read the value, and outside code that calls the getter (or a custom doc-values format reading it on its per-field merge view) gets the wrong answer. The fix is one line per site: subsumes(IndexOptions.DOCS_AND_FREQS), like the sibling flags.

The mechanism (main 5adff78bb168)

#
  1. FieldInfos(FieldInfo[]) computes the flags in one loop (index/FieldInfos.java:113-123): :114 hasPostings |= info.getIndexOptions() != IndexOptions.NONE;, :115 hasProx |= info.getIndexOptions().subsumes(IndexOptions.DOCS_AND_FREQS_AND_POSITIONS);, :116 hasFreq |= info.getIndexOptions() != IndexOptions.DOCS;, :117-118 hasOffsets |= info.getIndexOptions().subsumes(IndexOptions.DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS);.
  2. IndexOptions (index/IndexOptions.java) is NONE ("Not indexed", :29-30), DOCS (:36), DOCS_AND_FREQS (:41), the two positional options and DOCS_AND_CUSTOM_FREQS (:56). subsumes() compares ordinals and treats DOCS_AND_CUSTOM_FREQS like DOCS_AND_FREQS (:64-73). NONE has the lowest ordinal, so subsumes(...) and != NONE are false for it, while != DOCS is true.
  3. hasFreq() (index/FieldInfos.java:251-254) returns the flag, so one stored-only, doc-values-only, points-only or vector-only field anywhere in the segment makes it true.
  4. Second site: PerFieldMergeState.FilterFieldInfos (codecs/perfield/PerFieldMergeState.java:77), the view that per-field delegate formats get at merge time, computes its filtered hasFreq with the same formula (:115) and returns it at :151.
  5. Readers in Lucene (grep of the non-test sources under lucene/): only index/DocumentsWriterPerThread.java:534 (the flush line) and index/IndexWriter.java:5654 (the merge line; executed: two stored-only segments merged by forceMerge(1) print "merged segment has no vectors; no norms; no docValues; no prox; freqs; no points"). No codec, query or merge logic in Lucene branches on FieldInfos.hasFreq().
  6. Who sees the FilterFieldInfos view (step 4): PerFieldDocValuesFormat.merge gives each doc-values delegate a view of its doc-values fields only (codecs/perfield/PerFieldDocValuesFormat.java:131-151), and PerFieldPostingsFormat gives each postings delegate a view of fields with postings only (PerFieldPostingsFormat.java:171-191), which never holds a NONE field. With pass-through delegates on the default codec (two segments of StringField or TextField "id" plus NumericDocValuesField "n", forceMerge(1)), the postings view reports correctly, while the doc-values view [n=NONE] reports hasFreq=true in both cases: there a doc-values-only field is enough even when the segment has a text field. With fix A it reports false.

Exposure and likelihood260 words
  • Who is hit: code outside Lucene that calls the public @lucene.experimental getter (FieldInfos.java:42), or a custom doc-values format that reads it on the merge view PerFieldDocValuesFormat gives it (a postings format behind PerFieldPostingsFormat sees the right value); and anyone reading the IndexWriter infoStream, whose flush and merge lines say "freqs" for such segments. GitHub code search found no caller in Solr, Elasticsearch or OpenSearch, only a downstream copy of PerFieldMergeState with the same formula.
  • When: every segment with no freq-bearing field (all indexed fields DOCS-only, such as StringField, or no indexed field at all) that also holds one stored-only, doc-values-only, points-only or vector-only field: an ordinary schema for structured data. Plain new IndexWriterConfig() with the default codec, one document, no scale: a plain-Java run outside the test framework with the production default codec Lucene104 printed hasPostings=false hasFreq=true (assertions on and off), and so did a run under the test framework, whose randomized default codec was Asserting(Lucene104) in that run. A segment with any text field reports the correct true.
  • Effect: a wrong boolean and a wrong log word. Lucene's own indexing, merge and search code does not branch on it; a custom doc-values delegate that did, on its merge view, would get the wrong answer, there even in segments with a text field (executed with pass-through delegates; fix A makes it false).
  • Severity: Low. The closest precedent, LUCENE-10009 (#11048), a wrong "freqs" word on the same merge line, was called a "longstanding cosmetic bug" by Mike McCandless, who still fixed and backported it in 2021.

Why it looks unintended

#
  • hasFreq() is documented as "Returns true if any fields have freqs"; NONE means "Not indexed", and hasPostings() is false.
  • The sibling flags in the same loop (hasPostings, hasProx, hasOffsets) all leave NONE out.
  • The method had an isIndexed() guard from 4.0.0; the 2014 cleanup LUCENE-6041 deleted it here and wrote explicit NONE checks elsewhere.
The full argument179 words
  • Contract. /** Returns true if any fields have freqs */ (FieldInfos.java:251); IndexOptions.NONE is "Not indexed" (IndexOptions.java:29). A not-indexed field has no postings, so no freqs.
  • Siblings. hasPostings (!= NONE), hasProx and hasOffsets (subsumes(...)) exclude NONE (FieldInfos.java:114-118).
  • History. hasFreq() came in 4.0.0 (LUCENE-2048, 1c646d24c9f, 2011) with the guard; 4.10.4 still has hasFreq |= info.isIndexed() && info.getIndexOptions() != IndexOptions.DOCS_ONLY; (FieldInfos.java:75 at that tag). LUCENE-6041 "remove FieldInfo.isIndex/hasDocValues sugar APIs" (#7103, 17ab4645d51, 2014-11-02) turned the other isIndexed() calls into explicit IndexOptions.NONE checks (CheckIndex, the indexing chain, the per-field postings format, the field cache and more), but on the three FieldInfos lines it simply deleted info.isIndexed() &&. That kept hasProx and hasOffsets right (their compareTo(...) >= 0 is false for the lowest ordinal) and changed hasFreq. The issue has four short comments and never mentions hasFreq.
  • Tests. No upstream test calls FieldInfos.hasFreq() (grep for hasFreq() over all of lucene/: only the getter, its override and the two infoStream lines; the tests only use the unrelated Terms.hasFreqs()).
The devil's-advocate check152 words

The strongest case for "intended": read hasFreq() as a coarse "some field is not DOCS-only" capability flag; FieldInfos is @lucene.experimental; the formula has been unchanged for 12 years and was copied into PerFieldMergeState; nothing in Lucene acts on it except log text.

Why it fails: the javadoc says "any fields have freqs", not "not DOCS-only"; the method was created with the guard; the guard was lost in a cleanup whose stated goal was to make the same checks explicit, and that cleanup wrote the explicit NONE check everywhere else; the sibling flags exclude NONE; and no test, CHANGES entry or discussion endorses the current value. Longevity shows only that no report of it was found, not that it was accepted, and "nothing reads it" is why this is Low, not why it is intended. A cross-model review (OpenAI GPT-5.6) and an intended-behaviour review both rated the "intended" case weak.

Suggested fix

#

Recommended A: use subsumes(DOCS_AND_FREQS), like the sibling flags (recommended)

Compute the flag like its siblings: hasFreq |= getIndexOptions().subsumes(IndexOptions.DOCS_AND_FREQS) in FieldInfos and in PerFieldMergeState.FilterFieldInfos, one line each. NONE and DOCS then give false, and custom frequencies still count. Validated: the repro passes, and the nearest suites and the core lint checks pass.

// index/FieldInfos.java:116 and codecs/perfield/PerFieldMergeState.java:115
-      hasFreq |= info.getIndexOptions() != IndexOptions.DOCS;
+      hasFreq |= info.getIndexOptions().subsumes(IndexOptions.DOCS_AND_FREQS);
All options and trade-offs3 options · 413 words

In FieldInfos only segments without any freq-bearing field change, from true to false; in the per-field doc-values merge view, any view whose fields have no freqs changes the same way. No Lucene logic reads the value, so the visible change inside Lucene is the infoStream word.

A: use subsumes(DOCS_AND_FREQS), like the sibling flags (recommended) (validated by the checks)

#

Replace != IndexOptions.DOCS with .subsumes(IndexOptions.DOCS_AND_FREQS) at FieldInfos.java:116 and PerFieldMergeState.java:115. Result per option: NONE false (was true), DOCS false, DOCS_AND_FREQS and the positional options true, DOCS_AND_CUSTOM_FREQS true (subsumes() treats it like DOCS_AND_FREQS, so #15584's custom frequencies still count, as they do today; IndexOptions.java:52-56 says these custom freqs are scores, not term counts).

// index/FieldInfos.java:116 and codecs/perfield/PerFieldMergeState.java:115
-      hasFreq |= info.getIndexOptions() != IndexOptions.DOCS;
+      hasFreq |= info.getIndexOptions().subsumes(IndexOptions.DOCS_AND_FREQS);

Trade-offs

None for Lucene's own logic (only log text reads it). Outside code that relied on the inflated value would now see false.

Downstream note

#

Elasticsearch carries a copy of PerFieldMergeState with the same formula; code search found no reader of hasFreq() there or in Solr and OpenSearch, so downstream code only needs to avoid relying on the flag.

How it was found

#

Semi-formal: a proof-obligation audit of FieldInfos's contract checked the hasFreq() javadoc against how the constructor computes the flag, next to its sibling flags in the same loop. hasFreq() fails the obligation for fields whose index options are NONE; a one-test JUnit repro on stock main witnessed it.

The method in full77 words
  • Obligation: hasFreq() must be true exactly when some field of the segment has freqs (FieldInfos.java:251); a field has freqs only when its index options include DOCS_AND_FREQS.
  • Finding: the constructor's test != DOCS (FieldInfos.java:116) also admits NONE, unlike hasPostings, hasProx and hasOffsets (:114-118); PerFieldMergeState.java:115 repeats it.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

LFV-1208, snapshot of 2026-11-06

Registry title
FieldInfos.hasFreq() returns true for a segment in which no field has term frequencies when the segment holds a field that is not indexed (stored-only, doc-values-only or points-only), because it is computed as indexOptions != DOCS and IndexOptions.NONE passes that test (since 5.0.0, LUCENE-6041)
Area
index / FieldInfos aggregate per-segment flags (FieldInfos.hasFreq; the same formula in codecs/perfield PerFieldMergeState.FilterFieldInfos)
Priority
Low, rank 1220: FieldInfos.hasFreq() reports term frequencies for a segment that has none when all its indexed fields are DOCS-only (or it has no indexed field) and it also holds a stored-only, doc-values-only or points-only field, on default settings in every release since 5.0.0. No Lucene logic reads the value, so the only effect is a wrong diagnostic in the infoStream wording and for outside callers of the experimental getter.
Impact class
minor
Impact note
Code that reads the public @lucene.experimental getter FieldInfos.hasFreq() (no Lucene logic branches on it, and GitHub code search found no caller in Solr, Elasticsearch or OpenSearch, only a downstream copy of PerFieldMergeState with the same formula) gets true, and the IndexWriter infoStream flush line (and, by reading, the merge line) prints 'freqs', for every segment whose indexed fields are all DOCS-only, or that has no indexed field, as soon as it also holds a stored-only, doc-values-only or points-only field, with the default IndexWriterConfig, -ea and -da, one document and no scale, in every release from 5.0.0 through 10.6.0 and on main; nothing is indexed, merged or searched differently, so the effect is a wrong diagnostic value.
Summary
You index one document whose only field is a StoredField and look at the segment's FieldInfos: hasPostings() is false, and you expect hasFreq(), documented as 'Returns true if any fields have freqs', to be false as well. Instead it returns true, because the FieldInfos constructor sets the flag for every field whose index options are not DOCS (FieldInfos.java:116), and a field that is not indexed at all (IndexOptions.NONE) passes that test, while the neighbouring hasPostings, hasProx and hasOffsets flags exclude it. The same happens for doc-values-only and points-only fields and for a segment of DOCS-only StringFields plus any such field, so the IndexWriter infoStream says 'freqs' for segments that have none.
