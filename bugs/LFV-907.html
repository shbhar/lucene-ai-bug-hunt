CachingCollectorManager (new in 10.6.0) does not say it is single-use: a reused instance replays every earlier search

A CachingCollectorManager reused for a second search replays the hits of both searches ([0..9] instead of [3..9] in the repro), and one earlier overflow keeps isCached() false for good. Its javadoc never says an instance serves one search, unlike the sibling managers'; new in 10.6.0, unreleased.

The bug in 30 seconds

#

CachingCollectorManager records the first pass's hits per slice so a second pass can replay them. Its replay state belongs to the instance, not to one search.

Background: replaying a search with CachingCollectorManager

#
  1. IndexSearcher.search(query, manager) asks a CollectorManager for one collector per slice, collects, then calls reduce with those collectors to build the result.
  2. CachingCollectorManager wraps a first-pass manager: each slice's collector also records the doc ids (and optionally scores) it sees, up to a per-slice limit.
  3. After the search, isCached() says whether every slice's cache is intact. If so, replay(secondPassManager) feeds the recorded hits to a second pass; if not, you run the query again.

The bug, step by step

#
  1. Index 10 documents: k:a on docs 0-2, k:b on docs 3-9. Wrap a manager that keeps no state between searches (it collects doc ids) in new CachingCollectorManager<>(ids, false, null, 100) and search k:a: [0, 1, 2].
  2. Search k:b with the same instance: [3..9], correct, and isCached() is true. You expect replay(new IdsManager()) to replay this search: [3, 4, 5, 6, 7, 8, 9].
  3. Instead it returns [0, 1, ..., 9]. The manager appends every search's per-slice caches to one list, never clears it, and replays the whole list, so the second pass also gets docs 0-2, which k:b does not match.
  4. One overflow sticks: with a 5-doc budget, search k:b (7 hits) overflows, then search k:a (3 hits) fits, yet isCached() stays false, so the caller re-runs the query every time. A fresh manager says true. No error anywhere.
  5. Nothing in the javadoc says an instance is single-use, while TopScoreDocCollectorManager and TopFieldCollectorManager say "a new collectorManager should be created for each search". GroupingSearch creates a new manager per search and is not affected.

Who is affected

#

Direct users of the new, experimental CachingCollectorManager who keep one instance for several searches with a reusable delegate, such as their own stateless manager or the grouping module's FirstPassGroupingCollectorManager. The second pass silently gets earlier searches' hits, and after one overflow the query is always re-run. GroupingSearch is not affected. Main and the 10.6.0 RC only.

Mechanism, terms and numbers474 words

CachingCollectorManager is new in 10.6.0 (#16247, @lucene.experimental). It wraps a first-pass CollectorManager, caches each slice's hits and lets a second pass replay them instead of re-running the query. The caches live in one list per instance that newCollector() appends to and nothing clears, while isCached() and replay() read the whole list. So an instance used for a second search replays the hits of both searches, and one earlier overflow keeps isCached() false for every later search, silently. With a delegate that is itself reusable, each search's own result is correct. The javadoc describes one search and never says an instance is single-use, although Lucene says so for TopScoreDocCollectorManager and TopFieldCollectorManager, whose state affects results, and a code comment in TotalHitCountCollectorManager calls reuse generally supported. This is a documentation gap, not a correctness bug: no contract promises reuse. GroupingSearch, the only in-tree non-test caller, creates a new manager per search and is not affected.

The contract

#
  • Class javadoc: the manager "caches all collected documents (and optionally scores) per slice, so they can be replayed to a second-pass CollectorManager without re-running the query" (CachingCollectorManager.java:25-27). The example runs one search, then isCached(), then replay() or a re-run (:35-46). @lucene.experimental (:48).
  • isCached(): "Returns true if the search has been run and all per-slice caches are intact ... false if the search has not yet been run or any cache overflowed" (:103-107).
  • Nothing says what happens on a second search, either way. CollectorManager itself says nothing about reusing a manager (CollectorManager.java:23-46).

The mechanism

#
  1. One list per instance: private final List<CachingCollector> cachingCollectors = new ArrayList<>();, commented "One CachingCollector per slice" (CachingCollectorManager.java:58-59).
  2. newCollector() wraps a new delegate collector in a CachingCollector and calls cachingCollectors.add(cache) (:82-91). No method ever removes an entry.
  3. IndexSearcher.search(Query, CollectorManager) calls newCollector() once per slice and then reduce with exactly those collectors (IndexSearcher.java:750-791). reduce() unwraps them and calls the delegate (CachingCollectorManager.java:95-101), so with a reusable delegate each search's own result is right.
  4. isCached() is "list not empty and every cache intact" (:108-111), and replay() replays every cache in the list into a fresh second-pass collector (:118-130). After search N, both cover searches 1..N.

In the example

#

10 documents in one segment, no executor, so one slice per search. Search k:a adds cache 1 (docs 0-2); search k:b on the same instance adds cache 2 (docs 3-9). isCached() is true (both intact) and replay() replays both caches: [0..9]. With a 5-document budget, cache 1 of a k:b search (7 hits) overflows; cache 2 of a later k:a search (3 hits) is intact, but isCached() checks both and stays false. A reused instance also keeps every earlier cache (4 or 8 bytes per hit, CachingCollector.java:32) reachable (read, not measured).

Exposure and likelihood208 words
  • Opt-in. The class is used only when an application builds it itself (or through GroupingSearch, which creates a new one per search, GroupingSearch.java:167-176). No setting or scale is needed: 10 documents suffice.
  • Which delegates. A reusable first-pass manager: a user manager that keeps no state, or FirstPassGroupingCollectorManager, which the grouping package docs suggest wrapping in CachingCollectorManager (package-info.java:49-58); the intended-behaviour check reproduced the replay of both searches with it. With TopScoreDocCollectorManager or TopFieldCollectorManager as delegate, reuse already breaks their own documented single-use rule.
  • Effect. Silent. The second pass receives documents the latest query does not match, and duplicates where searches overlap (the independent reproduction: 21 entries with 5, 15 and 25 twice instead of 15 odd ids, with one slice and with 3 slices on a 2-thread pool). After one overflow the manager never reports a usable cache again, so the query is re-run every time. Earlier caches stay in memory. Each first-pass result is correct (with a reusable delegate).
  • Releases. None yet: main and the 10.6.0 release candidate. If 10.6.0 ships from RC1, it is the first release with the class.
  • Likelihood: rare. Few direct users of a new experimental class, and reuse with the common stateful delegates is already documented as wrong.

Why it is a bug, not intended

#
  • TopScoreDocCollectorManager and TopFieldCollectorManager say "a new collectorManager should be created for each search due to its internal states"; this class says nothing.
  • A TotalHitCountCollectorManager code comment calls reuse "generally supported" (not a strict requirement).
  • In #13542 javanna, who approved #16247, wrote that a stateful manager must be cleaned between searches or declared non-reusable; this one does neither, silently.
The full argument308 words
  • Lucene documents single use where it applies. TopScoreDocCollectorManager.java:26 and TopFieldCollectorManager.java:27: "Note that a new collectorManager should be created for each search due to its internal states." (added by #240, LUCENE-10002, 2023).
  • A code comment states a reuse norm. TotalHitCountCollectorManager.java:87-89 (an implementation comment in reduce(), not javadoc; #13542, 2024): "Make the same collector manager instance reusable across multiple searches. It isn't a strict requirement but it is generally supported as collector managers normally don't hold state, as opposed to collectors." It is qualified and is no interface contract.
  • The rule a reviewer stated (as javanna wrote in the #13542 review, 2024-07-22). "Because the collector manager holds state, either we clean it in-between searches ... or we declare that collector managers cannot be re-used across multiple searches (potential breaking change)." The same comment goes on: "I am unsure whether it is necessary to make a breaking change for this, perhaps clearing state in reduce is not that bad." So javanna leaned toward cleaning state over a breaking declaration (said of an already released manager; for this unreleased class neither route breaks anything), which supports the code option below at least as much as the javadoc one. javanna also reviewed and approved #16247 (2026-07-08). CachingCollectorManager holds state, does not clean it and does not declare it non-reusable.
  • Never discussed. The #16247 review (39 inline comments) covered the list's concurrency ("looks like this list is needed for the replay functionality"; newCollector is called from one thread), the volatile cached flag and isCached() before any search, never a second search.
  • No test either way. Upstream TestCachingCollectorManager (testCacheOverflow, testNotCachedBeforeSearch, testBasic, testConstructor) uses each instance for at most one search.
  • What is not claimed. No contract promises that a reused manager replays only its latest search, so this is filed as a javadoc gap, not a correctness bug.
The devil's-advocate check225 words

The strongest case (the intended-behaviour check and the refute-lens cross-model review): the class is a per-search result holder by design. Its javadoc speaks of "the search" (CachingCollectorManager.java:104) and shows a single search (:35-46); "caches all collected documents" (:25) is literally what a reused instance does; it is @lucene.experimental; CollectorManager promises nothing about reuse; TotalHitCountCollectorManager calls reuse "not a strict requirement"; and GroupingSearch uses one instance per search. The refute-lens reviewer (OpenAI GPT-5.6) rated it not real, with high confidence, as a correctness bug.

Why it fails against the documentation claim: it defeats a correctness framing, which is not made here, but not the gap. No text says one instance must not serve two searches; Lucene writes that sentence for TopScoreDocCollectorManager and TopFieldCollectorManager, whose state affects results; a code comment calls reuse generally supported; and the failure is silent. The refute-lens reviewer itself agreed that a sibling-style sentence would reduce surprise. Remaining risk: maintainers may find the singular "the search" sufficient (judge confidence medium). The hunt's own noise audit first triaged it as a noise candidate (documented/defensible) before a challenger kept it as a Low documentation claim, and the credibility audit expects a one-line javadoc PR to be welcome but push-back on any bug or regression wording; say so in the issue and keep it a low-priority clarification.

Trade-offs

  • With a reusable delegate, reuse just works: a reused instance replays only its latest search and no longer keeps earlier caches alive. It does not make a stateful delegate (such as TopScoreDocCollectorManager) reusable. GroupingSearch and every single-use caller behave as before.
  • A slightly different edge: after a search that throws before reduce(), isCached() is false (today it may report earlier caches).
  • Two concurrent searches through one instance stay unsupported, as today.
  • Touches the same method as the LFV-910 fix (independent logic, a trivial rebase).
