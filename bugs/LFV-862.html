Word2VecSynonymProvider returns maxSynonymsPerTerm + 1 synonyms when the query word is missing from its own search hits

Word2VecSynonymFilter promises at most maxSynonymsPerTerm synonyms, but the provider asks for k + 1 neighbours, expecting the query word among them, and never caps the result: when it is missing, all k + 1 above the threshold stay. With the defaults, w138 of a 500-word model gets 6, not 5.

The bug in 30 seconds

#

Word2VecSynonymFilter adds, for each word, the nearest words of a word2vec model as synonyms, found by an HNSW search over the model's vectors. maxSynonymsPerTerm caps how many. The provider asks for one neighbour more, as room for the query word itself, and gives that room back only when the query word is among the hits.

  1. Build a Word2VecSynonymFilter with maxSynonymsPerTerm = 1 over a model in which the words a, b and c have the same vector. The javadoc calls the value the "maximum number of result returned by the synonym search", so you expect at most 1 synonym per word.
  2. a and b get 1 synonym each, but c gets 2: [a, b]. The provider asks the HNSW graph for k + 1 = 2 neighbours, expecting c itself to be one of them and dropping it. Ties go to the lower ordinals here, so the 2 hits are a and b; both pass the threshold, nothing is dropped and both are kept.
  3. No ties are needed. In a 500-word model of distinct vectors with the factory defaults (5 synonyms, threshold 0.8), the search for 6 hits stops before it reaches w138 itself, although w138 is its own nearest neighbour (cosine 1.000; the best other word 0.923). All 6 hits pass the threshold, so w138 gets 6 synonyms.
  4. No error: the sixth synonym is the next-best hit (score 0.937 against a threshold of 0.8), so it silently joins the indexed terms or the query expansion on every occurrence of the word. A one-line cap on the result fixes it.

Who is affected

#

Applications that opt in to the experimental Word2VecSynonymFilter, with any model and the factory defaults. A small fixed set of words gets one extra synonym on every occurrence: about 0 to 0.2% of words at the defaults in synthetic clustered models, up to about 0.8% at maxSynonymsPerTerm = 1. Nothing fails.

Mechanism, terms and numbers733 words

Word2VecSynonymFilter (analysis-common, @lucene.experimental) expands each token with the nearest words of a word2vec model, found by Word2VecSynonymProvider.getSynonyms through an HNSW search over the model. The filter documents maxSynonymsPerTerm as the "maximum number of result returned by the synonym search". The provider searches for maxSynonymsPerTerm + 1 neighbours, because the query word is "always the nearest neighbour of itself", then drops the query word and every hit below minAcceptedSimilarity, and never caps the result. When the query word is not among the k + 1 hits and all of them pass the threshold, all of them are returned and emitted: three words with the same vector at k = 1 (c gets [a, b]), or, with distinct vectors and the factory defaults, a word that the search for k + 1 hits stops before reaching, although it is its own strict nearest neighbour (w138 of a 500-word clustered model gets 6 synonyms). The extra synonym is the next-best hit and passes the threshold; nothing fails. It has been there since the filter was added (#12169, first released in 9.7.0), fails on all 24 releases run and on main, and stopping the loop at k fixes it.

Terms

#
  • Word2VecSynonymFilter (org.apache.lucene.analysis.synonym.word2vec, analysis-common, @lucene.experimental; factory SPI name Word2VecSynonym, defaults maxSynonymsPerTerm = 5, minAcceptedSimilarity = 0.8). For every input token it asks a Word2VecSynonymProvider for synonyms and emits each as a SYNONYM token at the same position.
  • Word2VecSynonymProvider builds an HNSW graph over the model's normalised vectors once, then getSynonyms(term, maxSynonymsPerTerm, minAcceptedSimilarity) searches it with the query word's own vector. Each hit has a score (1 + cosine) / 2.
  • HNSW search is approximate: it keeps the best topK hits found so far and stops when no unexplored candidate can beat the worst of them (HnswGraphSearcher.java:177-186, :304-355), so a larger topK can make it explore further (it is not a fixed-size beam), and it can miss true neighbours. That is accepted; returning more than the maximum is a different property.

The bug

#
  1. getSynonyms calls HnswGraphSearcher.search(scorer, maxSynonymsPerTerm + 1, hnswGraph, null, Integer.MAX_VALUE) (Word2VecSynonymProvider.java:82-90), with the comment "When looking for the top-k it's always the nearest neighbour of itself so, we look for the top-k+1" (:85-86).
  2. The loop over the hits keeps every hit that is not the query word and whose score is at least minAcceptedSimilarity (:93-102). There is no cap at maxSynonymsPerTerm.
  3. When the query word is among the hits, at most k others remain. When it is not, all k + 1 remain if they pass the threshold, and Word2VecSynonymFilter emits all of them (Word2VecSynonymFilter.java:95-99, :79-89).
  4. Two legal inputs leave the query word out. Ties: at least k + 2 words with the same normalised vector; equal scores break towards the smaller ordinal (NeighborQueue.java:95-96), but which tied word loses its own slot depends on the order in which the search collects them (in the 3-word repro at k = 1 it is c). Distinct vectors: the search for k + 1 hits stops before it reaches the query node.

Exposure and likelihood314 words
  • Who. Applications that use Word2VecSynonymFilter (directly, through its factory, or by SPI name, for example with CustomAnalyzer) or call Word2VecSynonymProvider.getSynonyms. The classes are @lucene.experimental and opt-in. With any model and any maxSynonymsPerTerm, the factory defaults included; which words are hit depends on the model.
  • Effect. For an affected word, every occurrence gets one synonym more than configured: the (k + 1)-th best hit of the search, a model word that still passes minAcceptedSimilarity. Indexed terms or query expansions differ from what the setting promises; what that does to relevance depends on the application. No exception and no extra search work.
  • Scale. Deterministic per model as long as HnswGraphBuilder.randSeed keeps its default 42 (a public, mutable static field "public to expose for testing"; Lucene's core HNSW tests change it, no analysis-common test does), so the same words are affected every time. Measured on synthetic clustered models only (8 to 64 dimensions, 500 to 10,000 words; no real word2vec model was measured):
    • factory defaults (5, 0.8): 1 of 500 words (finder), 4 of 4,000 (independent reproducer), 0 to 2 of 10,000 in four 10,000-word models; 0 to 4 per model in 27 models of 1,000 to 4,000 words, non-zero in 8 of them;
    • maxSynonymsPerTerm = 1 (threshold 0.8): 0.1% to 0.8% of words in the 27 models (at most 33 of 4,000), 0.2% to 0.55% in the finder's 2,000- and 10,000-word models.
  • Ties. The tie trigger needs at least k + 2 words with one normalised vector (seven at the default k = 5); how often real models have that was not measured. The tie case is the smallest repro, the distinct-vector case the realistic one.
  • How likely. Plausible within the opt-in feature: no special input is needed, but only a small fraction of words is affected, and the extra word looks like a reasonable synonym, so it is easy to miss.

Why it is a bug, not intended

#
  • The filter's javadoc calls maxSynonymsPerTerm the "maximum number of result returned by the synonym search"; the PR's first draft said it of getSynonyms.
  • An upstream test sets 2 and expects exactly 2 synonyms, although 3 hits are searched.
  • The code's comment says the extra hit is room for the query word. Missing neighbours is approximation; exceeding the maximum is not.
The full argument218 words
  • Contract. Word2VecSynonymFilter.java:58: "@param maxSynonymsPerTerm maximum number of result returned by the synonym search". The filter passes the value to getSynonyms (:95-96) and emits everything it gets back.
  • The provider's own contract, originally. In the first revision of #12169 (2abb1ea6de1), a SynonymProvider interface documented getSynonyms(BytesRef term, int maxSynonymsPerTerm, float minAcceptedSimilarity) with exactly this @param. The interface was removed in review as a single-implementation interface, and the sentence survived only on the filter constructor.
  • Upstream test. TestWord2VecSynonymFilter.java:57-81: maxSynonymPerTerm = 2, expected output a plus exactly the two SYNONYM tokens d and e. The query word is among its hits there, so the test supports the bound but does not cover the self-miss case. It passes on stock and with both fixes.
  • The + 1 is only room for the query word. The comment at Word2VecSynonymProvider.java:85-86 says so; the factory validates the value as a positive count (Word2VecSynonymFilterFactory.java:72-76).
  • History. The #12169 review (33 review comments, 38 conversation comments) discussed thread safety, the visited limit, BoostAttribute and the model reader, never the cap or a missing self-hit. No later commit, test, CHANGES or MIGRATE entry accepts k + 1 results. Silence in a review is weak evidence of intent; the contract, the code comment and the original javadoc carry the argument.
The devil's-advocate check190 words

The strongest not-a-bug case (the intended-behaviour devil's advocate): HNSW is approximate by design, so one more approximation artifact is acceptable; the @param may describe the kNN search size rather than the synonym count; getSynonyms has no javadoc and the package is experimental; equal vectors are rare in trained models; and the extra synonym passes the threshold, so it is harmless.

Why it fails: missing some true neighbours is accepted approximation, but returning more than an explicit maximum is a different property, and the code shows the + 1 exists only as room for the query word. Read as "the search size", the sentence is still broken, because the search is called with k + 1. The original interface javadoc ties the sentence to getSynonyms, and the upstream test treats it as the output count (in a case where the query word is among the hits). A read-only reviewer from another model family (OpenAI GPT-5.6) put it as: "Experimental status and approximate-neighbor semantics do not authorize violating an explicit output bound." Only a severity argument survives (one extra, plausible synonym), which is why the bug ranks low. Verdict: not intended.

Suggested fix

#

Recommended A: stop the loop at maxSynonymsPerTerm

Stop the result loop once maxSynonymsPerTerm synonyms are collected (one condition plus a corrected comment). Hits come in score order, so the best k are kept, and nothing changes when the query word is among the hits. With it the word2vec and repro tests pass with assertions on and off, and the whole analysis-common test task passes.

              // The query vector is in the model, so it is usually its own nearest neighbour:
              // look for the top-k+1 and skip it below. It can be missing from the hits (tied
              // vectors, approximate search), so the loop below also stops after k synonyms.
              maxSynonymsPerTerm + 1,
              ...
      for (int i = 0; i < topDocs.scoreDocs.length && result.size() < maxSynonymsPerTerm; i++) {

Trade-offs

  • For positive k (the factory rejects k <= 0; the filter constructor and getSynonyms do not check k), output changes only when the query word is missing from the hits; otherwise at most k others pass anyway.
  • With it, c gets [a], w138 gets [w136, w121, w127, w139, w135], and no word of the 500-word model overruns for any k from 1 to 7.
  • It does not touch the + 1 itself, which overflows at Integer.MAX_VALUE (a separate bug with a search-size clamp as its fix); the two fixes compose.

C: exclude the query's own node from the search and ask for exactly k

#

Pass acceptOrds that rejects the query word's ordinal to HnswGraphSearcher.search(scorer, k, ...) and drop the term comparison.

Trade-offs

States the intent directly, but Word2VecModel has no public term-to-ordinal lookup (it needs a package-private accessor), and the kept hits shrink from k + 1 to k, so the search stops earlier and results can change for every word, not only the overrunning ones. Not run. A wider search alone is not a fix: ties can still push the query word out.

Downstream note

#

Analyzers built by SPI name (for example with CustomAnalyzer) reach this filter as Word2VecSynonym and inherit the extra synonym; which words get it depends only on the configured model.

How it was found

#

Semi-formal: a bounded-exhaustive comparison of the real provider with an exact-cosine reference, over every small model on a grid of vector directions (about 11 million checks), flagged results longer than maxSynonymsPerTerm, all with tied vectors. A second harness on clustered models of distinct vectors showed the overrun without ties; both were reduced to a public-API JUnit test.

The method in full175 words

Method: bounded-exhaustive translation validation (the hunt's "semi-formal" tier): the stock analysis-common jar against an exact-cosine reference of getSynonyms, with the oracles "getSynonyms returns at most maxSynonymsPerTerm" and "the filter emits at most maxSynonymsPerTerm SYNONYM tokens".

  • Scope: every 2-D model of 2 to 4 words on a 30-degree direction grid in all insertion orders, 3-D multisets of 3 to 4 of 26 directions, k = 1 to 5, several thresholds.
  • Result: 385,120 of 11,048,256 provider checks and 144 of 328,320 filter checks fail, all with tied vectors. Mutants of the other oracles were killed, so the comparison was not vacuous.
  • A second harness on clustered models of 2,000 and 10,000 distinct random vectors showed the same overrun without ties: the search for k + 1 hits stops before it reaches the query word itself.
  • Both were reduced to a public-API JUnit test on the stock main jar; an independent reproducer wrote its own test from the claim alone and checked by brute force that every overrunning word is its own strict nearest neighbour.

Only applications that opt in to the @lucene.experimental Word2VecSynonymFilter (or call Word2VecSynonymProvider.getSynonyms directly) are hit, with any model and the factory defaults (maxSynonymsPerTerm=5, minAcceptedSimilarity=0.8): for the terms whose own vector the k+1 HNSW search does not return (about 0-0.2% of terms at the defaults and 0.1-1.1% at maxSynonymsPerTerm=1 in the synthetic clustered models measured; no real model was measured), or that share their normalized vector with two or more other terms, every occurrence at index or query time silently gets exactly one extra synonym, the (k+1)-th best hit, which still passes minAcceptedSimilarity; ordinary scale; every release since 9.7.0.
Summary
You configure Word2VecSynonymFilter with maxSynonymsPerTerm=k, whose javadoc calls it the 'maximum number of result returned by the synonym search', so you expect at most k synonyms per token. Word2VecSynonymProvider.getSynonyms searches the HNSW graph for k+1 neighbours on the assumption that the query term is always its own nearest neighbour, drops only the query term and never caps the result, so when the term is not among the hits it returns all k+1. With three terms that share one vector and k=1, getSynonyms(c) returns [a, b] and the filter emits 2 SYNONYM tokens; with 4000 distinct clustered vectors and the factory defaults, 4 terms get 6 synonyms because the approximate search with a beam of 6 does not reach the query term itself, although it is its own strict nearest neighbour by a margin of more than 0.03.
