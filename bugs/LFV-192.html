AutomatonQuery.ramBytesUsed() is frozen at construction, so a wildcard or regex query that runs on an NFA under-reports its heap and a query cache can far exceed its RAM budget

The finding in 30 seconds

#

AutomatonQuery adds up its heap once, in the constructor, and keeps the sum. A query over a non-deterministic automaton runs on an NFARunAutomaton, which builds DFA states as it meets terms and keeps them on the query. The kept sum never sees those states.

Background

#
  1. ramBytesUsed(). Queries that implement Accountable report an estimate of the heap they hold. LRUQueryCache caches the matching documents of filters, keyed by query, charges each cached query this estimate, and evicts entries once it holds more than maxSize entries or maxRamBytesUsed bytes.
  2. DFA or NFA. A wildcard such as *a????????? compiles to a non-deterministic automaton (NFA). Lucene can turn it into a DFA up front (determinize it), or run it as an NFA that builds DFA states lazily, only for the inputs it meets, and remembers them.
  3. Main changed the default. Up to 10.6, WildcardQuery(Term) and RegexpQuery(Term) determinized up front. On main (#15939, #15961) they run non-deterministic patterns as an NFA. In 10.x only an AutomatonQuery built from a non-determinized automaton, or RegexpQuery(..., doDeterminization=false), ran as an NFA.

The finding, step by step

#
  1. On Lucene main, index all 1,024 ten-letter strings over {a, b} and count new WildcardQuery(new Term("f", "*a?????????")). Before the search the query reports ramBytesUsed() = 5,674 bytes and really holds 5,640: correct.
  2. You expect the number to follow the query's heap: ramBytesUsed() is an estimate of the object's heap, and LRUQueryCache charges it against its maxRamBytesUsed budget.
  3. On main this pattern is not turned into a DFA up front. The search builds DFA states inside the query's NFARunAutomaton and keeps them: the query now holds 205,216 bytes, and its compiled automaton reports 273,273.
  4. Instead ramBytesUsed() still says 5,674, because AutomatonQuery computed it once in its constructor and stored it in a final field: 36x too low here, 310x for a longer pattern on a 20,000-document field.
  5. A cache believes it: LRUQueryCache(1000, 1 MiB) keeps 4 wildcard filters that hold 7.4 MB, accounts 37 KB and evicts nothing. Hits stay correct. Releases 10.0 to 10.6 are hit only through opt-in NFA queries.

Who is affected

#

On main: applications that build default WildcardQuery or RegexpQuery objects (also through the classic QueryParser) and install an LRUQueryCache, which is off by default there. In 10.0 to 10.6: only opt-in NFA queries, and the cache overrun needs a reused query instance. The cache's byte budget no longer bounds the heap these filters retain; hits stay correct.

Mechanism, terms and numbers706 words

AutomatonQuery implements Accountable, but it computes ramBytesUsed() once, in its constructor, and stores the sum in a final field (private final long ramBytesUsed; // cache). When the automaton is not deterministic, its CompiledAutomaton runs it with an NFARunAutomaton, which determinizes lazily and keeps every DFA state it builds for the life of the query. The NFA's own estimate and CompiledAutomaton.ramBytesUsed() follow that growth; the query's stored value does not. On main, WildcardQuery(Term) and RegexpQuery(Term) no longer determinize (#15939, #15961), so the default constructors take this path: after one count over 1,024 terms, WildcardQuery(*a?????????) reports 5,674 bytes while it holds 205,216 (36x); on a 20,000-document field *a???????????? reports 6,714 for 2,081,152 (310x). LRUQueryCache charges a cached query exactly this value, so with a 1 MiB budget 4 cached wildcard filters retain 7,399,536 bytes while the cache accounts 37,368 and evicts nothing. Search hits are always correct. Releases 10.0.0 to 10.6.0 are affected through the opt-in NFA paths (an AutomatonQuery over a non-determinized automaton, RegexpQuery(..., doDeterminization=false)); 9.x is not.

The code (main 645d4fe14a20)

#
  1. Construction. AutomatonQuery.java:93-105: the constructor builds compiled = new CompiledAutomaton(automaton, false, true, isBinary) (:99) and stores BASE_RAM_BYTES + term.ramBytesUsed() + automatonBytes + compiled.ramBytesUsed() in the final field ramBytesUsed (:57, commented "// cache"; :102-104). ramBytesUsed() returns the field (:170-173).
  2. NFA execution. CompiledAutomaton.java:253-257: if neither the automaton nor its UTF-8 form is deterministic, it keeps no DFA and creates new NFARunAutomaton(binary, 0x100); its javadoc says such an automaton "will be executed using NFARunAutomaton" and still calls the class "Immutable" (:36-40).
  3. The states grow during the search. NFARunAutomaton.java:28-31: "It will lazily determinize on-demand, memorizing the generated DFA states that has been explored." New states go into dStateToOrd and dStates under stateRegistryLock (:49-51, findDState :159-177); each state's transitions fill in as terms are stepped (:309-332). Nothing drops them while the query lives.
  4. Who counts them. NFARunAutomaton.ramBytesUsed() (:260-268) and CompiledAutomaton.ramBytesUsed() (:554-561) are live. AutomatonQuery read the compiled estimate once, when the NFA had one state.
  5. The default path on main. WildcardQuery.java:49-60 passes toAutomaton(term) (:67-101, a concatenation, no determinize) to AutomatonQuery; RegexpQuery.java:54-56, :90-101 passes new RegExp(...).toAutomaton(provider). The classic query parser builds both (QueryParserBase.java:512, :579).
  6. The cache. LRUQueryCache.java:465-471 charges RamUsageEstimator.sizeOf(query, 32), which is ramBytesUsed() for an Accountable (RamUsageEstimator.java:378-386); for a filter the key is the constant-score wrapper, whose value is an object header and a reference (16 bytes here) plus the wrapped query's (AbstractMultiTermQueryConstantScoreWrapper.java:52-56). The DocIdSet is built first, so the NFA has already run on that segment (LRUQueryCache.java:609-610); the query is then sized once, at its first reference (:990-999, :1110-1121). UsageTrackingQueryCachingPolicy.java:45-54, :122-125: a MultiTermQuery is cached after 2 uses.

Exposure and likelihood352 words
  • Who, on main (unreleased 11.0). Default WildcardQuery/RegexpQuery objects for non-deterministic patterns (a * or .* followed by more pattern), used as filters or counts, with an application-installed LRUQueryCache. Caching is off by default on main (IndexSearcher.java:82-84, #14187); MIGRATE.md shows how to turn it back on (lucene/MIGRATE.md:227-236). By default the cache only caches on segments of 10,000+ documents (LRUQueryCache.java:251-253).
  • Who, on 10.0.0 to 10.6.0. Only callers that opt into NFA execution: new AutomatonQuery(term, automaton) over an automaton they did not determinize (10.0 stopped determinizing behind the scenes, lucene/MIGRATE.md:922-926), or RegexpQuery(..., doDeterminization=false) (#12767). The default IndexSearcher cache is on there (LRUQueryCache(1000, min(32 MB, heap / 20)), 10.6.0 IndexSearcher.java:95-100), but NFA-backed queries compare by identity, so the overrun needs the application to reuse the same query instance.
  • What happens. The cache's byte budget no longer bounds the heap these keys actually retain: the cache keeps the bytes it records under maxRamBytesUsed, but for these keys those are construction-time values, so in the runs shown only maxSize (1,000 entries by default) limits them. Any other reader of ramBytesUsed() after a search gets the stale value too.
  • How much. It grows with the pattern and the field: about 1.5x to 2x more retained per extra ? on the study's field (18.6 KB for *a????, 2.1 MB for *a????????????, 12.7 MB for *a???????????????), so short patterns leave little unaccounted heap. Main also runs, as an NFA with no work limit, patterns whose determinization with the default limit (the one 10.x's WildcardQuery(Term) applied up front) throws TooComplexToDeterminizeException: for one 16-? pattern on 100,000 documents the study saw the compiled automaton count 39 MB while the query reported 8,162 bytes (run on main, not on a 10.x release; not re-measured).
  • What it does not do. No hit is wrong; nothing is bypassed or exposed. No OutOfMemoryError run was made.
  • How likely: rare. It takes long patterns on fields with many distinct terms, repeated often enough to be cached, with a cache installed (main) or an opt-in NFA API and reused instances (10.x).

Why it looks unintended

#
  • ramBytesUsed() is "an estimate of the JVM heap memory used by this object"; it stays fixed while the query grows 36x.
  • The stored value dates from 2019, when compiled automata were always DFAs; #13741 made the NFA's own estimate live.
  • #16390 fixed a far smaller error here, a double count; its issue says the value "feeds LRUQueryCache eviction decisions".
The full argument230 words
  • The contract. Accountable.java:34-40: "Returns an estimate of the JVM heap memory used by this object in bytes." LRUQueryCache.java:60-62: it evicts "in order to remain under a given maximum size and number of bytes used".
  • The field predates NFA execution. LUCENE-8855 (a76c962ee61, 2019, #9898) cached the value for "finalized" queries to avoid recomputing it, when a CompiledAutomaton was always a DFA. LUCENE-10010 (#225, c972c6a7754, 2021) made the compiled form grow after construction; the field was not revisited.
  • Upstream wants the states counted. On #13715 Robert Muir listed "ramBytesUsed doesn't consider nfaRunAutomaton" as a problem, and Patrick Zhai, the NFA's author, noted that the NFA "will remember all the states that has been determinized". #13741 then made NFARunAutomaton and CompiledAutomaton count them live; only the outer AutomatonQuery copy stayed frozen.
  • Smaller errors here were bugs. #16389/#16390 (a double count in this method, fixed in 10.6.0; "ramBytesUsed() feeds LRUQueryCache eviction decisions"); #16046 (an 18-35% over-count in CompiledAutomaton.ramBytesUsed()).
  • Upstream tests. TestAutomatonQuery.java:289-303 holds the value within 10% of RamUsageTester, TestNFARunAutomaton.java:46-53 within 30%, on fresh objects only; the helper at TestAutomatonQuery.java:305-320 defines the value as shallow size + term + q.getCompiled().ramBytesUsed(), the relation the repro checks after a search.
  • Precedent. LUCENE-9350 (#10390) stopped FuzzyQuery from keeping automata on the query because they "can end up blowing up query caches"; #15097/#15124 and #16405/#16406 fixed other cache under-counts.
The devil's-advocate check273 words

The strongest case: ramBytesUsed() is only "an estimate"; Accountable is @lucene.internal, and AutomatonQuery, CompiledAutomaton and LRUQueryCache are @lucene.experimental; the field is labelled "// cache" on purpose, and LRUQueryCache itself sizes a query only once (LRUQueryCache.java:973-999), so both treat a query's size as fixed; the NFARunAutomaton javadoc documents the growth; the WildcardQuery javadoc warns against a leading *; caching is off by default on main; on #15939 Robert Muir wrote that RegexpQuery "is convenience for a one-off" and that a heavily reused pattern should use AutomatonQuery; and on #16031 (closed unmerged) a contributor argued that FuzzyQuery#ramBytesUsed should return "a stable value" rather than "jump from 0 to N after the first execution".

Why it fails: keeping the states is intended; nothing in the code, the docs or the history says under-reporting them is, and upstream already made the inner estimates live (#13741). The "// cache" was right when written and went stale with #225. The cache's one-time sizing is no excuse: the DocIdSet is built before the key is sized (LRUQueryCache.java:609-610), so a live value would cover the first segment. The leading-* warning is about speed, and a non-leading pattern and the opt-in RegExp path reproduce. The "one-off" remark is about DFA versus NFA speed, while here the reuse comes from Lucene's own cache, which on main shares one key across fresh queries. #16031 concerns a query that holds no automaton and was not merged. No reviewer found the intended-behaviour case convincing: every review that rated its strength called it moderate, and the devil's-advocate review concluded with high confidence that the stale value is not intended.

Suggested fix

#

Recommended A live value, read under the NFA's lock

Keep only the fixed part in a field and return it plus compiled.ramBytesUsed() on every call, and read the NFA's states under the lock that already guards them. The repro and the study's cache test pass, as do 312 tests in the closest suites. The cache still sizes a query once, so later growth stays uncounted.

// AutomatonQuery
private final long fixedRamBytesUsed; // BASE_RAM_BYTES + term + automaton (unless shared)
public long ramBytesUsed() {
  return fixedRamBytesUsed + compiled.ramBytesUsed();
}

// NFARunAutomaton
public long ramBytesUsed() {
  synchronized (stateRegistryLock) {
    return BASE_RAM_BYTES + ... + RamUsageEstimator.sizeOfMap(dStateToOrd) + ...;
  }
}
All options and trade-offs4 options · 677 words

Option A was built and run through gradle. B (bound the NFA's state cache) and C (do not keep the states on the query) change the design and cap what a query can hold; D (re-size cached keys) closes the cache-side gap A leaves. None of B-D was run. Workarounds that need no fix: determinize patterns yourself and use AutomatonQuery (MIGRATE.md's recipe, which also restores a work limit), keep MultiTermQuery filters out of the cache with a custom QueryCachingPolicy, or run without a query cache (the default on main).

A live value, read under the NFA's lock (validated by the checks) (recommended)

#

AutomatonQuery keeps BASE_RAM_BYTES + term + automaton (unless shared) in a field and adds compiled.ramBytesUsed() on every call. NFARunAutomaton.ramBytesUsed() takes stateRegistryLock, which already guards its state map, so a live read cannot iterate dStateToOrd while another thread adds a state. 2 files, +15/-10.

// AutomatonQuery
private final long fixedRamBytesUsed; // BASE_RAM_BYTES + term + automaton (unless shared)
public long ramBytesUsed() {
  return fixedRamBytesUsed + compiled.ramBytesUsed();
}

// NFARunAutomaton
public long ramBytesUsed() {
  synchronized (stateRegistryLock) {
    return BASE_RAM_BYTES + ... + RamUsageEstimator.sizeOfMap(dStateToOrd) + ...;
  }
}

Trade-offs

  • Why the lock. RamUsageEstimator.sizeOfMap iterates the HashMap (RamUsageEstimator.java:260-278), findDState adds to it under stateRegistryLock (NFARunAutomaton.java:163-176), and the class is documented as safe for concurrent stepping (:29-31). Inside Lucene nothing reads the NFA's estimate during a search today; with a live query value the cache would, while other slices of the same query may still be stepping. The study's one-method sketch lacks this part.
  • Cache gap. LRUQueryCache still sizes a query once, at its first reference (LRUQueryCache.java:990-999): the first segment's states are counted, since they are built before the key is sized; states built later, on other segments or by later searches, are not.
  • Cost. A live read is O(number of DFA states) and blocks stepping on that query meanwhile; the cache does it once per admitted query.
  • Javadoc. CompiledAutomaton's "Immutable" (CompiledAutomaton.java:37) could be reworded in the same change.

Bound the NFA's state cache

#

On #225 Patrick Zhai called a limit on "the number of state that NFA can cache" "a feature not implemented yet". A bound (stop caching, or drop states, past a size) caps what one query can hold whatever the accounting does.

Trade-offs

It also limits patterns whose determinization exceeds the default work limit (the limit 10.x's WildcardQuery(Term) applied up front), which main now runs as an NFA without one. A larger design change with performance trade-offs (re-stepping without cached states). Not run.

Do not keep the states on the query

#

Hold the lazily built states per search or per segment instead of on the CompiledAutomaton, as LUCENE-9350 did for FuzzyQuery's automata.

Trade-offs

The query's size then stays fixed and the existing value becomes right, but every search rebuilds its states. Not run.

Re-size a cached query when a later segment references it (complement)

#

LRUQueryCache could refresh a query's bytes when another segment's entry for it is added, so growth after admission is charged.

Trade-offs

Closes the gap option A leaves, but touches the per-distinct-query accounting #16657 just restructured (LRUQueryCache.java:465-467, :973-999). Not run.

Downstream note

#

Services that turn user wildcard or regex text into queries and install a query cache on main should not count on maxRamBytesUsed to bound those queries until a fix ships.

How it was found

#

A hunt unit checked that NFA and DFA execution of wildcard and regex queries agree. While measuring how the NFA's lazily built state cache grows, the finder compared each query's ramBytesUsed() with its measured heap before and after one search, saw the value never move, and confirmed it with a JUnit on the stock main jars.

The method in full126 words

Method: semi-formal (the hunt's tier for systematic checks against an independent measurement). The unit did bounded-exhaustive translation validation of NFA versus DFA execution of WildcardQuery and RegexpQuery against a reference semantics; the lazily built DFA-state cache is the only mutable part of a CompiledAutomaton.

  • Signal. For *a???? to *a??????????????? on a 20,000-document field, RamUsageTester.ramUsed(query) grew from a few KB to 18.6 KB-12.7 MB after one search while ramBytesUsed() stayed at 3.9-7.8 KB.
  • Confirmation. A 2-test JUnit on the stock main jars (the value, and an LRUQueryCache budget under the default caching policy) failed with assertions on and off; independent verifiers, cross-model reviews from another model family (OpenAI GPT-5.6) and an adjudication confirmed it, and a 2026-10-29 minimization cut the repro to the one test above.

History

#

Introduced in 10.0.0 by #225 (c972c6a7754e, 2021), which ran NFAs with lazily built states while AutomatonQuery kept a value computed at construction (LUCENE-8855, 2019). The default WildcardQuery/RegexpQuery path exists on main only, since #15939 and #15961 (2026). 9.x is unaffected; not fixed upstream.

Versions tested6 rows

Root cause c972c6a7754e, apache/lucene#225, LUCENE-10010 "Introduce NFARunAutomaton to run NFA directly" (Patrick Zhai, merged 2021-12-20, first released in 10.0.0). The query's field comes from LUCENE-8855 (a76c962ee61f, 2019-06-26, 8.2.0). Built and run: the parent e79012550444 rejects an NFA in the constructor; c972c6a7754e reports 1,025 bytes before and after a count while the query retains 207,904.

Default path on main: #15939 (650684e6b440, 2026-04-12) and #15961 (86593e51b28d, 2026-04-19) removed the up-front determinization (CHANGES 11.0.0). Reverting only the determinize call #15961 removed makes the minimal repro pass on main.

Later changes that did not fix it: #13741 (10.0) made the NFA's own estimate live; #16046 (10.5.0) and #16390 (10.6.0) fixed over-counts and kept the value computed once.

LFV-192, snapshot of 2026-11-05

Registry title
AutomatonQuery.ramBytesUsed() is computed once at construction, so a query that runs on an NFA (WildcardQuery and RegexpQuery by default on main, opt-in NFA queries since 10.0.0) under-reports the DFA states it builds while searching, and an LRUQueryCache can hold far more heap than its RAM budget
Area
search / AutomatonQuery RAM accounting (NFARunAutomaton lazily built DFA states; LRUQueryCache RAM budget)
Priority
Low, rank 729: AutomatonQuery freezes ramBytesUsed at construction, so NFA-run wildcard and regex queries (default on main, opt-in on 10.x) under-report retained DFA states by 36x to 310x and an installed LRUQueryCache can overrun its budget, while results stay correct.
Impact class
silent wrong results
Impact note
Applications that keep an NFA-executed AutomatonQuery alive after running it, above all as an LRUQueryCache key, are hit: on main every WildcardQuery or RegexpQuery whose automaton is not deterministic (default constructors, also from the classic QueryParser) keeps reporting its construction-time size after it ran (5,674 bytes reported vs 205,216 retained after one count over 1,024 terms; 6,714 vs 2,081,152 for a longer pattern on a 20,000-document field), so an application-installed LRUQueryCache (the IndexSearcher default cache is off on main since GITHUB#14187) charges a few KB per cached key while each key keeps its DFA states (4 keys retained 2.7 to 7.4 MB under a 1 MiB budget, 0 evictions); in 10.0.0-10.6.0 only the opt-in NFA APIs reach it (an AutomatonQuery over a non-deterministic automaton, RegexpQuery(..., doDeterminization=false)), and the cache overrun there also needs the application to reuse the same query instance; search hits are always correct, the harm is heap that the cache budget does not see (an OutOfMemoryError was not executed).
Summary
You run a WildcardQuery or RegexpQuery whose automaton is not deterministic, for example '*a?????????' or 'a*b??????????', and expect its ramBytesUsed() to estimate the heap the query holds, which is what the Accountable javadoc says and what LRUQueryCache uses to stay within maxRamBytesUsed. On main such a query runs on an NFARunAutomaton that builds DFA states lazily during the search and keeps them on the query object, but AutomatonQuery stored ramBytesUsed() in a final field when it was constructed, so after one search the value is 36x to 310x too small (5,674 bytes reported vs 205,216 retained over 1,024 terms; 6,714 vs 2,081,152 on a 20,000-document field). An LRUQueryCache with a 1 MiB budget then keeps 4 such queries as keys that retain 2.7 to 7.4 MB while it accounts about 36 KB in total and evicts nothing; the matching documents are correct.
