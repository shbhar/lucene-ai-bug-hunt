GraphTokenFilter.end() drops the input's end-of-stream attribute values except the final offset and position increment, so FixedShingleFilter loses them

Under FixedShingleFilter (or a GraphTokenFilter subclass reading to the end), an end-of-stream value the input sets on any attribute but the final offset and position increment comes back cleared: flags 42 read 0. Latent (no Lucene component sets or reads such a value); in every release since 8.0.0.

The finding in 30 seconds

#

GraphTokenFilter reads ahead, so it reaches the end of its input before the consumer does. It saves only the input's final position increment and offset, and its end() resets everything else, so any other end-of-stream value the input set is lost.

Background: end() and the end state

#
  1. After the last token the consumer calls end() on the stream. Each component sets its end-of-stream values there: the final offset (here 3, the text length), the trailing position increment, and, as TokenStream#end allows, any other attribute whose end value matters.
  2. A TokenFilter passes end() on to its input, so the values its input set reach the consumer.
  3. A filter that reads ahead, such as a shingle filter, ends its input early, so it must save the input's end state and hand it back in its own end(). ShingleFilter and CachingTokenFilter do exactly that.

The finding, step by step

#
  1. Write a TokenFilter whose end() calls super.end() and then sets its FlagsAttribute to 42, as TokenStream#end allows ("any adjustment of other attributes"). Put it on a WhitespaceTokenizer over "a b".
  2. Read the stream to the end and call end(). With no wrapper, or under ShingleFilter, the flags read 42. Wrap it in FixedShingleFilter(in, 2) (one token, "a b") and you expect 42 again: TokenFilter#end passes end() on to the input.
  3. Instead the flags read 0, the attribute's default. The final offset, 3, is still right.
  4. Why: GraphTokenFilter reads ahead, so it calls input.end() early and keeps only two numbers, the position increment and the offset. Its own end() then resets every attribute and puts back just those two.

Who is affected

#

Only applications whose own Tokenizer or TokenFilter sets an end-of-stream value on another attribute (a flag, a type, a custom attribute), wrap it in FixedShingleFilter (experimental) or their own GraphTokenFilter subclass that reads its input to the end, and read that value after end(). Lucene itself is unaffected: indexing reads only the final offset and position increment, which are kept.

Mechanism, terms and numbers502 words

GraphTokenFilter, the abstract core base class of FixedShingleFilter, reads ahead in its input. When the input runs out, nextTokenInStream() calls input.end() and records only the position increment and the end offset; it does not capture the rest of the input's end state, and later cached tokens overwrite the shared attributes. Once the consumer has read FixedShingleFilter to the end, the read-ahead has already reached the end, so end() takes its else branch: endAttributes() resets every attribute through its own end() (by default clear()), and only the saved position increment and offset are put back. Any other value the input's end() set, a FlagsAttribute, a TypeAttribute or a custom attribute, is lost: flags 42 read 0. ShingleFilter and CachingTokenFilter capture the input's end state and restore it, and GraphTokenFilter's own other branch forwards it, so the loss is at odds with the TokenStream#end javadoc, with those filters and with the class itself. It is latent: no Lucene component sets such a value and Lucene's own consumers read only the two values that are kept, so Lucene's own indexing and search are unchanged. It is in every release since 8.0.0 (since 7.4.0 through FixedShingleFilter's own older end()); a four-line capture/restore change fixes it.

Exposure and likelihood196 words
  • Who is hit. An application that (a) sets an end-of-stream value on an attribute other than the final offset and position increment in its own Tokenizer or TokenFilter, as TokenStream#end allows, (b) wraps it in FixedShingleFilter (@lucene.experimental; chosen explicitly through its constructor or FixedShingleFilterFactory, used by no built-in analyzer) or in its own GraphTokenFilter subclass that reads its input to the end, and (c) reads that value after end() in its own consumer.
  • Not hit. Lucene itself: no shipped component sets such a value, and after stream.end() IndexingChain reads only the position increment and end offset (IndexingChain.java:2105-2110), and a scan of the in-tree end() overrides and call sites found no consumer that reads another attribute after end(). Positions, offsets and what Lucene's own indexing and query analysis see are unchanged.
  • Scale. Deterministic: every fully consumed stream through such a chain, with assertions on or off, on any input, even an empty one (two words is the smallest input that yields a shingle). Silent: no exception, just the attribute's cleared value.
  • How likely. Rare: no public report of it was found since 2018, and it needs all three conditions above.

Why it looks unintended

#
  • TokenStream#end allows end-of-stream "adjustment of other attributes", and TokenFilter#end passes the call on to the input.
  • The other look-ahead filters, ShingleFilter and CachingTokenFilter, capture the input's end state and restore it in end(); ShingleFilter keeps the 42.
  • GraphTokenFilter's own first end() branch, taken when the read-ahead has not reached the end, forwards the input's end state unchanged.
The full argument195 words
  • The contract. TokenStream#end: "any adjustment of other attributes where the end-of-stream value may be important" (TokenStream.java:152-154). TokenFilter#end: "The default implementation chains the call to the input TokenStream" (TokenFilter.java:42-43). The analysis package docs: components "must put accurate values into the token attributes to reflect the situation at the end of the field" (package-info.java:276-279), and a tokenizer must "finish up and other attributes to reflect the end of the stream" (:518-519).
  • The established pattern. ShingleFilter sets endState = captureState() right after input.end() and restores it in end() (ShingleFilter.java:379-381, :400-407; LUCENE-5180, 9a6360e131e, 2013). CachingTokenFilter does the same with finalState (CachingTokenFilter.java:84-96).
  • Self-inconsistency. GraphTokenFilter.end()'s first branch (:153-156) forwards input.end(); only the else branch drops the values.
  • Precedents. The same "clear, then set only the attributes I know" pattern lost custom attributes in other filters and was fixed: #6057 (LUCENE-4993, BeiderMorseFilter) and #4582 (LUCENE-3508, CompoundWordTokenFilterBase); both use capture/restore today.
  • Nothing endorses the loss. No javadoc, test or issue says GraphTokenFilter may drop end-state attributes; the only remark on end() in #9610 (LUCENE-8564) is "Updated patch with improved end() processing".
The devil's-advocate check178 words

Strongest case for "intended": only the offset and position increment have ever mattered after end(). As Robert Muir wrote on #4922 (LUCENE-3849, 2012), "currently offsetAtt is the only thing that we consume from end()" (that issue then added the final position increment, in 4.5). FlattenGraphFilter.end() (FlattenGraphFilter.java:483-498) rebuilds the end state the same lossy way, BaseTokenStreamTestCase checks only the final offset and position increment, FixedShingleFilter is experimental, and the javadoc allows such values without saying in so many words that a filter emitting new tokens must hand on its input's (TokenFilter#end describes only the default implementation).

Why it is weaker than it looks: the javadoc names other attributes explicitly; the filters built to look ahead hand the whole state on; GraphTokenFilter is a public core base class whose two end() branches disagree; nothing documents the loss. It does justify the Low priority and the "latent" framing, and a maintainer could still reasonably call it working as intended (the cross-model review rated that case moderate). FlattenGraphFilter is a separate site, not tested and not claimed here.

Recommended A. Capture and restore the input's end state in GraphTokenFilter (recommended; validated)

Capture the input's end state when the read-ahead calls input.end(), restore it in end(), and clear it in reset(): the ShingleFilter pattern, +4/-3 in GraphTokenFilter. A. Capture and restore the input's end state in GraphTokenFilter (recommended; validated)

#

GraphTokenFilter.java, +4/-3: a State endState field; endState = captureState() right after the read-ahead's input.end() (:227-229); restoreState(endState) instead of the three lines of end()'s else branch (:158-160); endState = null in reset(). Trade-offs

  • One captureState() per stream, once, when the input ends; the same pattern as ShingleFilter (ShingleFilter.java:380-381, :405).
  • It hands on every value in the input's end state, not only flags or type (term, payload, keyword, position length, custom attributes), where endAttributes() reset them.
  • restoreState leaves alone attributes that were added after the capture (as in ShingleFilter), and throws if an attribute in the captured state has since been removed (AttributeSource.java:318-327; only through removeAllAttributes(), the same in ShingleFilter).
  • A second end() call after the first branch (outside the documented workflow) finds endState == null and leaves the attributes as they are, so FixedShingleFilter adds pendingPosInc twice: position increment 1, then 2 (unfixed: 1 both times, but flags 0 the second time). Also capturing endState in the first branch would avoid that (not tested).

What the checks validated

  • Without the fix the repro fails with assertions on and off (gradle, seed DEADBEEF).
  • With the fix: the repro passes with assertions on and off; :lucene:core:test --tests 'org.apache.lucene.analysis.*' passes, 168 tests (TestGraphTokenFilter 4); :lucene:analysis:common:test passes with assertions on and off, 1910 tests, 18 skipped, each (TestFixedShingleFilter 15, TestShingleFilter 45, the repro 1); checkGoogleJavaFormat for core and analysis-common passes (the first run found both tasks up to date; a fresh run in a second worktree also passed).
  • One seed; the full suite and nightly tests were not run. The same change made the other checks' own tests pass, and 8.0.0 with only GraphTokenFilter replaced by it passes the same steps.

B. Document the limitation

#

Say in the GraphTokenFilter javadoc that only the final offset and position increment survive end().

Trade-offs

No behaviour change, but the class stays inconsistent with its own first branch, with the TokenStream#end contract and with ShingleFilter. Not validated (documentation only).

Downstream note

#

No Lucene component sets or reads such a value. For plain (non-graph) input, an application that does can keep it with ShingleFilter(in, 2, 2) and setOutputUnigrams(false), which gives the same shingles in the probe and restores its input's whole end state (flags 42 in the same chain); it is not a drop-in for graph input, where FixedShingleFilter emits stacked shingles.

How it was found

#

A semi-formal proof-obligation audit of GraphTokenFilter's end() contract: its end() must hand on the input's end-of-stream state, as TokenFilter#end and TokenStream#end suggest and as CachingTokenFilter and ShingleFilter do. A one-test public-API JUnit on stock main witnessed the violation.

The method in full55 words

The audit took the obligation that a filter's end() hands on its input's end-of-stream state (TokenFilter#end, TokenStream#end, and the capture/restore in CachingTokenFilter and ShingleFilter) and checked GraphTokenFilter against it: the read-ahead's input.end() is never captured. A one-test JUnit on the stock main jars witnessed the loss with assertions on and off.
