Multi-dimensional PointInSetQuery skips segments that contain matching points

Since 10.3.0, a multi-dimensional PointInSetQuery treats the first and last points of its sorted set as the set's minimum and maximum in every dimension, and skips segments that hold a match. Against one document at (1,0), the set {(0,1), (1,0)} counts 0; the set {(1,0)} counts 1.

The bug in 30 seconds

#

A PointInSetQuery matches documents whose point equals one of a set of points. Since 10.3.0 it skips a segment early when it decides the set cannot match there, by comparing the set's "lowest" and "highest" point with the segment's minimum and maximum in each dimension.

  1. Write a 2-D PointInSetQuery subclass (Lucene's own set queries are all 1-D) and index one document at the point (1,0) with IntPoint, default settings.
  2. Search for the set {(1,0)}: count 1. Search for {(0,1), (1,0)}: you expect 1 again, because (1,0) is still in the set.
  3. You get 0, with no error. The constructor sorts the set point by point, dimension 0 first, so (0,1) comes first and (1,0) last, and the query keeps those two points as the set's "lowest" and "highest" point.
  4. It then checks each dimension against the segment. In dimension 1 the "lowest" value is 1, but the segment's largest value there is 0, so the query decides the segment cannot match and skips it. The real range of the set in dimension 1 is 0 to 1.
  5. So adding a point to a set can remove hits. Ordinary data can trigger it when segments are narrow in a later dimension: 43 of 200 random sets were wrong on day-ordered (entity, day) data, 0 of 200 on uniform data.

Who is affected

#

Only applications that write their own PointInSetQuery subclass with two or more dimensions; every Lucene factory is 1-D, and the recorded code search of Elasticsearch, OpenSearch and Solr found none. There no setting or scale is needed: segments that are narrow in a later dimension, such as small or time-ordered ones, can trigger it with ordinary sets.

Mechanism, terms and numbers628 words

PointInSetQuery finds documents whose single or multi-dimensional point is in a set, and is meant for subclasses. Its constructor requires the packed points in sorted order, which it enforces with BytesRef.compareTo: an unsigned lexicographic order over the whole packed value, in which dimension 0 decides first. Since 10.3.0 (GITHUB#14268, an optimization) the constructor keeps the first and the last point of that order as lowerPoint and upperPoint (PointInSetQuery.java:110-114, :129-134), and scorerSupplier returns null for a segment as soon as, in any dimension, lowerPoint is above the segment's maximum or upperPoint below its minimum (:187-201). Those two points bound only dimension 0. For the set {(0,1), (1,0)} lowerPoint is (0,1); a segment whose only document is at (1,0) has maximum 0 in dimension 1, and 1 > 0, so the whole segment is skipped and count() is 0 instead of 1. Only application-written subclasses with two or more dimensions are hit; every production in-tree factory is 1-D. Used as a MUST_NOT clause or in IndexWriter#deleteDocuments(Query), the skipped segment fails open. Affects 10.3.0 through 10.5.2 and main.

Terms

#
  • Point field: a field indexed with IntPoint, LongPoint and so on; a point has one value per dimension, for example new IntPoint("p", 1, 0) is the 2-D point (1,0). Each segment records, per dimension, the smallest and largest value of the field (PointValues#getMinPackedValue/getMaxPackedValue: "minimum value for each dimension, packed", PointValues.java:473-481).
  • PointInSetQuery: "Abstract query class to find all documents whose single or multi-dimensional point values ... is contained in the specified set"; "This is for subclasses" (PointInSetQuery.java:43-48). The set arrives as a stream of packed points that "must be in sorted order" (:74).
  • Lexicographic order: points compared byte by byte over the whole packed value, so dimension 0 decides first and dimension 1 only breaks ties. (0,1) sorts before (1,0) because 0 < 1 in dimension 0.

The mechanism (main ea57360912ed)

#
  1. The constructor copies the first point into lowerPoint (PointInSetQuery.java:110-114), checks every further point with BytesRef.compareTo against the previous one (equal: skipped; smaller: "values are out of order", :116-121) and copies the last point into upperPoint (:129-134).
  2. scorerSupplier, after the dimension and byte-width checks (:168-185): if the segment has documents, then for every dimension i it returns null when lowerPoint[i] > max[i] or upperPoint[i] < min[i] (:187-201).
  3. In lexicographic order the first point has the set's smallest dimension-0 value and the last point the largest, so dimension 0 is checked correctly. In a later dimension the first point's value can be above the set's minimum and the last point's value below its maximum. The check then rejects a segment that holds a set point.
  4. A null ScorerSupplier means "nothing matches in this segment": count() and search() get no hits from it; BooleanWeight drops a null clause that is not required (BooleanWeight.java:299-306), so a MUST_NOT clause excludes nothing there; delete-by-query runs only when the weight returns a scorer (FrozenBufferedUpdates.java:400-402), so deleteDocuments(Query) deletes nothing there.
  5. The same per-dimension loop in PointRangeQuery (PointRangeQuery.java:263-275), which #14268 followed, is correct: a range's lowerPoint and upperPoint are real per-dimension bounds.

Exposure and likelihood368 words
  • Who is exposed. Applications that subclass PointInSetQuery through its protected constructor with numDims >= 2, the extension point the javadoc names ("This is for subclasses"), for example a lookup of a set of (entity, day), (x, y) cell or (category, label) pairs on a multi-dimensional IntPoint or LongPoint field.
  • Not exposed. Every production in-tree factory passes numDims = 1: IntPoint, LongPoint, FloatPoint, DoublePoint, BinaryPoint and InetAddressPoint.newSetQuery, JoinUtil, and the sandbox BigIntegerPoint and HalfFloatPoint. The only in-tree multi-dimensional factory is the private test helper TestPointQueries#newMultiDimIntSetQuery. A read-only code search of the default branches of Elasticsearch, OpenSearch and Solr found no multi-dimensional subclass (only that summary was kept, not the search output); plugins and private code were not checked.
  • Default or opt-in. Default IndexWriterConfig, codec and searcher; one document is enough. The opt-in is the application-written subclass of a @lucene.experimental class.
  • When it fires. On a segment, when the set's lexicographically first point has a value in some dimension k >= 1 above the segment's maximum in k, or its last point a value below the segment's minimum in k, while the segment holds a set point. That needs segments that are narrow in a later dimension: small segments (near-real-time readers, frequent flushes), ingestion or index sorting by a later dimension (time series), or merges after deletes.
  • How often (measured on small synthetic indexes, not in the field). 2,000 (entity, day) documents indexed in day order and committed every 200: 43 of 200 random sets of 1-8 indexed points return wrong counts. The same with uniform random (x, y): 0 of 200. Deliberately tiny segments: 109 of 300 random 2-D and 150 of 300 random 3-D set queries wrong with one seed (109-154 and 125-159 of 300 over the five seeds run). For a given index and set it is deterministic (20 of 20 iterations).
  • What you see. No error. Whole segments contribute no hits, and adding a point to a set can remove hits that the smaller set returned. Positive use only loses hits; negated use fails open (Downstream note). No hang, resource growth, crash or index damage was observed, and the early-return path suggests none.

Why it is a bug, not intended

#
  • The javadoc promises all documents whose "single or multi-dimensional" point is in the set; its sorted-order precondition is enforced and met.
  • #14268 is an Optimizations entry; its 2-D tests use one-point sets only.
  • No order of {(0,1), (1,0)} is sorted in both dimensions, yet the constructor accepts it; 10.2.2 counts 1.
The full argument279 words
  • Contract. Class javadoc: "Abstract query class to find all documents whose single or multi-dimensional point values, previously indexed with e.g. {@link IntPoint}, is contained in the specified set." and "This is for subclasses and works on the underlying binary encoding" (PointInSetQuery.java:43-48). Besides the field shape (bytesPerDim, numDims and each packed point's length, checked at :76-108), the only precondition is the one the constructor javadoc states, "The {@code packedPoints} iterator must be in sorted order" (:74); it is enforced (:116-121) and met by the repro.
  • An optimization. "GITHUB#14268: PointInSetQuery early exit on non-matching segments. (hanbj)" is listed under 10.3.0 "Optimizations" (lucene/CHANGES.txt:1597, :1605); an optimization must not change results.
  • Upstream tests. TestPointQueries asserts exact multi-dimensional set results (testBasicMultiDimPointInSetQuery, testBasicMultiValueMultiDimPointInSetQuery, testManyEqualValuesMultiDimPointInSetQuery, :1560, :1582, :1610). The first two use multi-point sets, such as {(-7,-7), (17,42)}, which are ordered alike in every dimension, where the first and last points happen to be per-dimension bounds; the third uses one-point sets only. #14268's own test testPointInSetQuerySkipsNonMatchingSegments (:2566) uses 2-D sets of one point only. With the fix every test in lucene/core passes, so no test pins the current behaviour.
  • History. #14268's description gives the premise: "the data in the packedPoints parameter is returned in order, so the maximum and minimum values can be determined". That holds for dimension 0 only. Its review covered tests, asserts, the docCount == 0 check and the CHANGES entry, not sets of several multi-dimensional points. It followed the PointRangeQuery early exit (#13033), where the bounds are real per-dimension bounds. 10.2.2 and older, without the early exit, return the right count.
The devil's-advocate check173 words

The strongest case for "works as designed or misuse" (built by the devil's advocate and checked by the adjudication): the class is @lucene.experimental; every in-tree factory is 1-D; the test helper's comment calls it a "test-only query factory" that could be "graduated" "if there is demand for real usage" (TestPointQueries.java:1491-1493); and "sorted order" could be read as sorted in every dimension.

Why it fails: @lucene.experimental covers API stability, not correctness, and nothing documents approximate results. The class javadoc promises multi-dimensional membership and invites subclasses, the scorer has its own numDims > 1 branch, and upstream tests assert exact multi-dimensional results; the comment calls the factory test-only, not multi-dimensional support. The constructor enforces whole-value lexicographic order and accepts {(0,1), (1,0)}, which no order sorts in both dimensions at once, so a per-dimension reading would make ordinary sets illegal, which the constructor does not do. A reviewer from another model family (OpenAI GPT-5.6, reading only) called the intended-behaviour case weak. What remains is a reach argument (few users), not a correctness one.

Suggested fix

#

Recommended A per-dimension bounding box of the set (+28/-2)

Track the set's real minimum and maximum in every dimension after the first while the constructor reads the sorted points; keep the first and last points for dimension 0 (+28/-2 in PointInSetQuery.java). The repro passes, and so do TestPointQueries, the whole lucene/core suite (8,866 tests) and :lucene:core:check.

Trade-offs

Sound for every set the constructor accepts (sorted, with any duplicates and any BytesRef offset): a segment is skipped only when the set's bounding box misses the segment's box, and a set point inside the segment lies in both. Keeps the early exit in every dimension. Cost, once at construction: per distinct set point 2 x (numDims - 1) unsigned comparisons of bytesPerDim-byte values and at most as many bytesPerDim-byte copies (the loop does not run for 1-D queries), plus one copy of the first point into upperPoint, also for 1-D; nothing per segment. Memory unchanged (the same two arrays). The two arrays become box corners instead of set points; only the constructor, ramBytesUsed, scorerSupplier and a ramBytesUsed test read them, and that test passes. No benchmark was run.

Check each set point against the segment's box (not built)

#

Skip a segment only if no set point lies inside the segment's per-dimension box.

Trade-offs

Prunes more than a bounding box, but costs up to one box test per set point per segment. Not built or run.

Workaround until a fix ships

#

A subclass cannot override createWeight, which builds the check and is final, so the check runs whenever the query itself is executed; a subclass could override rewrite(IndexSearcher), which is not final and which PointInSetQuery does not override, to return the query below instead (not run). For small sets, use a BooleanQuery of SHOULD clauses IntPoint.newRangeQuery(field, p, p), one exact box per point, within the clause limit; or ship a patched copy of the class.

Trade-offs

Slower than a set query for large sets and bounded by the clause limit. Not run as a workaround; the independent reproducer used exactly this OR of exact boxes only as a cross-check of its brute-force counts on main, where it agreed with them.

Downstream note

#

Why: a skipped segment returns no scorer, which Lucene reads as "nothing matches here". BooleanQuery then drops the MUST_NOT clause for that segment and delete-by-query skips it, so negated use fails open. Positive use only loses hits. This class documents no untrusted-input guarantee (SECURITY.md lines 28, 50); no concrete exploit is known.

How it was found

#

An AI finder checked PointInSetQuery against a brute-force reference on every tiny 2-D and 3-D index with 0/1 coordinates (11,088 indexes, 1,282,176 queries): 11,160 mismatches, all multi-dimensional set queries, none with the fix. Code reading found the early exit; in a z3 model of four small cases the shipped check can skip a matching segment, a per-dimension box cannot.

The method in full236 words

Method: bounded-exhaustive translation validation, a hunt unit (bulk-overload precondition matrix), 2026-10-26 (the hunt's "semi-formal" tier).

  • The harness built every 2-D index of 1-4 documents over {0,1}^2 and every 3-D index of 1-3 documents over {0,1}^3, with maxPointsInLeafNode 1-3 and 4 layouts (11,088 indexes, 1,282,176 query cases), on the stock main jars, and compared each result with a brute-force reference over the stored values. The unit's own bulk-versus-per-document oracle found nothing; the brute-force reference flagged 11,160 mismatches, all multi-dimensional PointInSetQuery set queries. With the fix: 0.
  • A z3 model of the check: for (dimensions, set points) = (2,2), (2,3), (3,2) and (3,4), with one-byte dimensions, the shipped check can skip a segment whose box holds a set point (satisfiable, witnesses logged), a per-dimension min/max check cannot (unsatisfiable); a vacuity control is satisfiable and a 1-D control (3 set points) unsatisfiable. Other sizes were not run.
  • Then a public-API JUnit, a review by an independent reviewer from another model family (OpenAI GPT-5.6, reading only: real, high), an independent reproducer, a refute-lens review by the same model family (reading only; its "not real, low" was procedural because it could not run code), a devil's advocate, an adjudication, a history sweep, a prior-report search, a security assessment, a registry re-run and an audit. Neither reviewer from the other model family wrote or ran a test of its own; the refute review's wrapper did run the finder's test, which failed.

Bug record

#

LFV-475, snapshot of 2026-10-29

Registry title
Multi-dimensional PointInSetQuery skips segments that contain matching points, because its segment early exit uses the lexicographically first and last set points as per-dimension bounds
Area
search / points queries (PointInSetQuery segment early exit)
Priority
Medium, rank 83: Since 10.3 the PointInSetQuery early exit silently and deterministically skips whole segments for ordinary multi-point sets, but only multi-dimensional subclasses are hit and none exist in Lucene or major downstreams, the same custom-subclass profile as LFV-006.
Impact class
silent wrong results
Impact note
Only applications that subclass PointInSetQuery with numDims >= 2 are hit (every in-tree builder, IntPoint/LongPoint/FloatPoint/DoublePoint/BinaryPoint/InetAddressPoint.newSetQuery and JoinUtil, is 1-D and unaffected, and no multi-dimensional subclass was found in Elasticsearch, OpenSearch or Solr), on the default IndexWriterConfig, codec and searcher with no scale needed: a whole segment silently contributes no hits whenever the set's lexicographically first point has a value in some dimension k >= 1 above the segment's maximum in k, or its last point a value below the segment's minimum in k, which happens with small (near-real-time, frequently flushed) segments or data ingested in the order of a non-first dimension (43 of 200 random sets wrong on day-ordered (entity, day) data, 0 of 200 on uniform data).
Summary
You subclass PointInSetQuery for a 2-D point field, as Lucene's own tests do, and search for the set {(0,1), (1,0)} in an index whose segment holds one document at (1,0). You expect that document to match, as it does for the one-point set {(1,0)}. Instead, since 10.3.0 the query keeps the first and last set points in sorted order, (0,1) and (1,0), as if they were the set's per-dimension minimum and maximum, concludes from dimension 1 (1 is above the segment's maximum 0) that the segment cannot match, and skips it, so count() is 0 with no error; adding a point to a set can thus remove hits.
