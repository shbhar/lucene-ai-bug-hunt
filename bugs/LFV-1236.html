DisjunctionMaxQuery treats tie-breakers 0.0f and -0.0f as equal but gives them different hash codes

new DisjunctionMaxQuery(q, 0f) and the same query with -0f are equals, but their hash codes differ by exactly 2^31, which breaks Java's equals/hashCode contract. The query cache, HashSet and BooleanQuery then treat one query as two (a cache miss and a duplicate entry), while hits and scores stay the same.

The finding in 30 seconds

#

equals compares the tie-breakers with ==, under which 0.0f == -0.0f. hashCode mixes in Float.floatToIntBits(tie), whose two values for the zeros differ in the sign bit. The constructor's [0, 1] check lets -0.0f through, so two equal queries get hash codes exactly 2^31 apart.

Background: two zeros, and how hash lookups work

#
  1. Java's float has two zeros, 0.0f and -0.0f. 0.0f == -0.0f is true, but their bit patterns differ: Float.floatToIntBits gives 0x00000000 and 0x80000000.
  2. A HashMap, a HashSet or Lucene's query cache first compares hash codes and calls equals() only when they match. So equal objects must have equal hash codes; otherwise the lookup never reaches equals and misses.

The finding, step by step

#
  1. Build a = new DisjunctionMaxQuery(List.of(new TermQuery(new Term("f", "x"))), 0f) and b, the same query with -0f. The constructor accepts -0f: its check tie < 0 || tie > 1 is false for negative zero.
  2. a.equals(b) is true both ways: equals compares the tie-breakers with ==, and in Java 0.0f == -0.0f.
  3. You expect a.hashCode() == b.hashCode(): Java requires it for equal objects, and Query's javadoc asks for it so that the query cache works.
  4. Instead hashCode mixes in the float's raw bits, 0x00000000 for 0.0f and 0x80000000 for -0.0f. The hash codes come out as, for example, 74785687 and -2072697961: exactly 2^31 apart.
  5. So hash lookups miss. In a probe that forces caching (one-segment index), an LRUQueryCache that held the 0f query stored the equal -0f query as a second entry with no hit (size 1 to 2, hits 0); a HashSet keeps both, and two such FILTER clauses are not folded into one. Hits and scores are identical.

Who is affected

#

Applications that build the same DisjunctionMaxQuery with both 0.0f and -0.0f, for example from a computed negative zero or a parsed "-0" (the XML query parser parses its tieBreaker attribute that way). Default configuration, every release since 1.9. The cost is cache misses and duplicate work only; no hit or score changes. Contrived, so priority Low.

Mechanism, terms and numbers731 words

DisjunctionMaxQuery's constructor accepts a tie-breaker of -0.0f (its check tieBreakerMultiplier < 0 || tieBreakerMultiplier > 1, DisjunctionMaxQuery.java:65, is false for negative zero). equals compares the tie-breakers with == (:353), under which 0.0f == -0.0f, so a query with tie-breaker 0.0f and the same query with -0.0f are equal. hashCode mixes in Float.floatToIntBits(tieBreakerMultiplier) (:365), which is 0x00000000 for one and 0x80000000 for the other, so their hash codes always differ by exactly 2^31. That breaks the Object.hashCode contract, which Query's javadoc requires "so that QueryCache works properly" (Query.java:95-116). Hash-based structures then treat the two equal queries as different: LRUQueryCache keeps a second entry and records no hit (in a probe that forces caching), a HashSet keeps both, BooleanQuery rewrite does not fold the duplicate FILTER clause and parent queries compare unequal. Hits, scores and toString were identical in the probes, and by reading the code scores and explain cannot differ. It has been there since the class was added (2005, first released in 1.9) and is in every release through 10.6.0 and on main; comparing the bits in equals, as BoostQuery does, fixes it.

Terms

#
  • DisjunctionMaxQuery(disjuncts, tieBreakerMultiplier): scores a document by its best-scoring disjunct plus tieBreakerMultiplier times the others. With 0 (the XML query parser's default) only the best disjunct counts; -0.0f scores the same.
  • The contract: Object.hashCode ("If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result"), and Query.java:95-116, which asks every query to implement both "properly" because QueryCache relies on them.

The bug

#
// DisjunctionMaxQuery.java (excerpts)
if (tieBreakerMultiplier < 0 || tieBreakerMultiplier > 1) {   // :65  false for -0.0f
  throw new IllegalArgumentException("tieBreakerMultiplier must be in [0, 1]");
}
this.tieBreakerMultiplier = tieBreakerMultiplier;             // :68  -0.0f kept as is

private boolean equalsTo(DisjunctionMaxQuery other) {
  return tieBreakerMultiplier == other.tieBreakerMultiplier     // :353 IEEE ==: 0.0f == -0.0f
      && Objects.equals(disjuncts, other.disjuncts);
}

public int hashCode() {
  int h = classHash();
  h = 31 * h + Float.floatToIntBits(tieBreakerMultiplier);      // :365 0x00000000 vs 0x80000000
  h = 31 * h + Objects.hashCode(disjuncts);
  return h;
}

Why exactly 2^31. The two floatToIntBits values differ only in bit 31; the next step multiplies by 31, an odd number, so the difference stays 0x80000000 modulo 2^32. The absolute values depend on the run configuration: the term's hash is seeded from tests.seed, or outside the test framework from the clock (BytesRef.java:118-119, StringHelper.java:141-152), and the disjunct set's hash starts from getClass().hashCode() (Multiset.java:118), an identity hash. A rerun of the documented command (seed DEADBEEF) gave exactly the same values; the 2^31 difference held in every run.

Where the hash code is used

#
  • LRUQueryCache: the cache key's hash includes query.hashCode() (LRUQueryCache.java:1319, :1327), and entries are kept per segment and query (:66-68). In a probe that caches every DisjunctionMaxQuery on a one-segment index, searching two-disjunct versions of a and then b added a second entry and recorded no hit (size 1 to 2, hits 0); a second probe that caches every query, the term subqueries too, also gave b its own entry (size 3 to 4). Both probes forced caching. The default UsageTrackingQueryCachingPolicy caches a dismax query only after 4 uses (UsageTrackingQueryCachingPolicy.java:122-137) and counts uses by query.hashCode() too (:151, :167), so the two equal queries are also counted separately.
  • BooleanQuery: clauses are kept in a Multiset (SHOULD, MUST) or a HashSet (FILTER, MUST_NOT) (BooleanQuery.java:134-138), used by its equals/hashCode and by rewrite's removal of duplicate FILTER and MUST_NOT clauses (:343-361, which relies on the FILTER HashSet built at :137). BooleanQuery(MUST a) is not equal to BooleanQuery(MUST b), and [FILTER a, FILTER b] keeps 2 clauses after rewrite where [FILTER a, FILTER a] folds into one.
  • DisjunctionMaxQuery keeps its own disjuncts in a Multiset (DisjunctionMaxQuery.java:47), so a parent dismax query that contains a is not equal to one that contains b.
  • Rewrite. A one-disjunct DisjunctionMaxQuery rewrites to its only disjunct (DisjunctionMaxQuery.java:269-270), so the search-time effects need two or more disjuncts, as in the probes; with two or more, rewrite keeps the tie-breaker as given (:305). The repro uses one disjunct because equals and hashCode do not rewrite.
Exposure and likelihood206 words
  • Who is hit. Code that ends up with both zeros for one query. -0.0f arises from arithmetic such as -1f * 0f or from Float.parseFloat("-0"); the XML query parser passes its tieBreaker attribute through Float.parseFloat (DisjunctionMaxQueryBuilder.java:46, :59; DOMUtils.java:126). Executed: tieBreaker="-0" gives a query with tie-breaker -0.0 that equals the tieBreaker="0" query, with hash codes that XOR to 0x80000000.
  • Default vs opt-in. Default configuration; a mainstream public core query; assertions on or off.
  • Effect. Performance and equality only: a query-cache miss and a second cache entry for what is the same query (once the caching policy caches it; the probes forced it), duplicate FILTER clauses not folded, and parent queries that compare unequal (measured in probes). By reasoning, the unfolded clause evaluates the same disjunction twice and the parents' own cache entries miss too. Hits, scores and toString were identical in the probes; by reading the code, the score and explain add otherSum * tieBreakerMultiplier, which is -0.0 for -0.0f and a non-negative sum and leaves the max unchanged (DisjunctionMaxScorer.java:72, DisjunctionMaxQuery.java:239-243).
  • Scale. None needed: one pair of queries.
  • Likelihood: contrived. Queries that all use the same zero are consistent with each other; it takes both zeros for one query.

Why it looks unintended

#
  • Java's Object.hashCode contract and Query's javadoc ("required so that QueryCache works properly") demand equal hash codes for equal queries.
  • Lucene's own QueryUtils.checkEqual asserts equals and hashCode together; BoostQuery compares the float's bits in both.
  • Lucene fixed the same -0.0 mismatch in five geo classes (#13292 / #13301).
The full argument119 words
  • The contract. Object.hashCode (JDK 25 Object.java:81-84) and Query.java:95-116: "Override and implement query hash code properly in a subclass. This is required so that QueryCache works properly."
  • Lucene's test oracle. QueryUtils.checkEqual asserts assertEquals(q1, q2) and assertEquals(q1.hashCode(), q2.hashCode()) together (QueryUtils.java:104-107).
  • The core convention. BoostQuery compares and hashes Float.floatToIntBits in both methods and rejects -0f (BoostQuery.java:40, :63, :70; the rejection came with LUCENE-7996, #9044).
  • Upstream precedent. #13292 / #13301 (2024) fixed the same == versus bit-hash mismatch for -0.0 in Point, XYPoint, Circle, XYCircle and Rectangle2D.
  • History. Both lines date from the original contribution (LUCENE-323, 2005) and were never discussed; no javadoc, test, CHANGES or MIGRATE entry treats -0.0 specially.
The devil's-advocate check89 words

The strongest case: the two zeros really are the same query (the scorer treats them alike), so equals returning true is right; and -0.0f is an odd input that BoostQuery would even reject.

Why it fails: that argument justifies equals being true, not a different hash code. The constructor accepts -0.0f and getTieBreakerMultiplier() returns it, so an input the API takes must still obey the equals/hashCode contract. Every verifier rated the bug real; an executed review by another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak.

Trade-offs

One line; matches BoostQuery. It is a choice of meaning, not only a contract repair: the two zero queries become two different queries (they still score the same), so each gets its own cache entry and two such FILTER clauses stay separate, consistently. Side effect: a NaN tie-breaker query becomes equal to itself, since floatToIntBits maps every NaN to one value.

How it was found

#

A proof-obligation audit of DisjunctionMaxQuery's contract checked that equals and hashCode agree for every value the constructor accepts. The tie-breaker is compared with == but hashed by its bits, which disagree only for the two zeros. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full121 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for all accepted inputs, a.equals(b) implies a.hashCode() == b.hashCode() (Object.hashCode, Query.java:95-116). The proof needs x == y to imply floatToIntBits(x) == floatToIntBits(y) for every tie-breaker in the constructor's domain; that fails only for x = 0.0f, y = -0.0f, and the range check admits -0.0f.
  • A one-test JUnit witnessed it on main with assertions on and off; probes measured the effect on HashSet, BooleanQuery and LRUQueryCache. An independent reproducer and two executed reviews by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier re-ran the repro.

Only applications that build the same DisjunctionMaxQuery once with tie-breaker 0.0f and once with -0.0f (the public constructor's [0, 1] check and the XML query parser's tieBreaker attribute both accept -0.0f) are hit, in the default configuration, with -ea and -da, at any size, in every release since 1.9: the two queries are equal but hash differently, so an LRUQueryCache stores a second entry instead of reusing the first, hash sets keep both, BooleanQuery rewrite does not fold the duplicate FILTER clause and parent queries holding them compare unequal; matching documents, scores, explain and toString are identical for the two zeros, so no search result is wrong.
Summary
You build DisjunctionMaxQuery([f:x], 0.0f) and DisjunctionMaxQuery([f:x], -0.0f): equals returns true both ways (the constructor accepts -0.0f, and equalsTo compares the tie-breakers with ==, under which 0.0f == -0.0f), so by the Object#hashCode contract, which Query's javadoc requires so that QueryCache works, the two hash codes must be equal. Instead they differ by exactly 2^31, because hashCode adds Float.floatToIntBits(tieBreakerMultiplier), which is 0x00000000 for 0.0f and 0x80000000 for -0.0f. Hash-based structures therefore see two different queries: the query cache keeps a separate entry, a HashSet holds both and a BooleanQuery with both as FILTER clauses is not de-duplicated, while hits and scores stay the same.
