The finding in 30 seconds

#

Loud: an exception, no wrong result, nothing written. Run with a DrillSideways without an executor, the search that takes a collector manager per dimension, and a dimension collector that declines a segment from getLeafCollector. With the stock FacetsCollector the facet-counting searches are not this case. The one stock trigger found is a sandbox class. With an executor the call returns.

Background: three pieces

#
  1. A search feeds its hits to a Collector segment by segment: the loop asks the collector for a LeafCollector per segment (getLeafCollector) and hands it the segment's hits.
  2. Some collectors turn a segment down by throwing CollectionTerminatedException from getLeafCollector: core's TotalHitCountCollector and the sandbox histogram collector do. The search loop of IndexSearcher has a handler around that call and goes on with the next segment.
  3. Drill sideways: beside the hits, each drill-down dimension gets a collector of its own, fed with the documents that match the query without that dimension. DrillSideways#search(DrillDownQuery, CollectorManager, List) lets the caller choose each dimension's collector manager. Without an executor one query, DrillSidewaysQuery, feeds them all in one pass; with an executor each dimension gets a search of its own.

The finding, step by step

#
  1. Index two segments of one document each (NoMergePolicy keeps them apart). Both documents have color = red; only the first has the numeric doc-values field price (5).
  2. Search with one drill-down dimension, color = red, through DrillSideways#search(DrillDownQuery, CollectorManager, List) on a DrillSideways built without an executor: TopScoreDocCollectorManager(10, 10) for the hits and the sandbox HistogramCollectorManager("price", 10) as the collector manager of the dimension.
  3. You expect the search to return, with the histogram {0=1} for the dimension: bucket 0 (prices 0 to 9) holds one document. IndexSearcher.search with the same collector manager returns that on the same index, and so does the same call on a DrillSideways built with an executor (run).
  4. Instead the search throws org.apache.lucene.search.CollectionTerminatedException: unchecked, no message, no stack trace, with assertions on and off. Neither the hits nor the histogram are returned. No wrong result is returned and nothing is written.
  5. Why: the histogram collector declines a segment whose field infos lack its field by throwing that exception from getLeafCollector. The search loop of IndexSearcher has a handler around that call for the hit collector. DrillSidewaysQuery asks each dimension's collector for its leaf collector inside Weight#scorerSupplier, which the loop calls after and outside that handler. With price in both segments (5 and 25) the same call returns {0=1, 2=1}.

Who is affected

#

An application that calls the three-argument DrillSideways#search with collector managers of its own choice, without an executor, and puts a collector that declines a segment from getLeafCollector into a dimension's slot. With the sandbox histogram collector the trigger is data: a segment whose field infos lack the field. The search throws; no wrong result. No such application was found. Rare.

Mechanism, terms and numbers2,752 words

The limits first.

  • The failure is loud. An unchecked exception that carries no stack trace comes out of the search, and no result is returned: neither the hits nor the dimensions' results of that call. No wrong result is returned and nothing is written to the index.
  • The shape that was run has three things together: a DrillSideways built without an executor; the search method that takes a collector manager for each drill-sideways dimension, search(DrillDownQuery, CollectorManager, List); and a collector of a dimension that declines a segment by throwing CollectionTerminatedException from getLeafCollector.
  • With Lucene's own FacetsCollector in the slots, the searches of the class that count facets are not this case. That is what these searches put into each dimension's slot unless a subclass gives another collector through a protected method, and FacetsCollector does not throw the exception. With a FacetsCollector subclass that declines a segment, given through that method, the two-argument search threw without an executor and returned with one (run on 2026-11-23 on 9.12.0, 10.6.0, branch_11x 8e4ee3d41386 and main 3cee9ed259e9).
  • One stock collector was found that triggers it, and it is a class of the sandbox module: the collector of HistogramCollectorManager, for a segment whose field infos lack the histogram field. The trigger is the data (in the runs, a segment in which no document was indexed with the field), not a setting.
  • Two calls return the result on the same index: IndexSearcher.search with the same collector manager, and the same call on a DrillSideways built with an executor.
  • That comparison has a limit. Without an executor the query calls getLeafCollector alone on a dimension's collector, and neither setWeight nor scoreMode() (run). So that mode does not drive a dimension's collector as a search does, the javadoc's "any CollectorManagers" is no statement that the collector is driven as IndexSearcher drives it, and this page compares the two modes only for the shapes that were run.
  • The ranges follow the trigger. With stock classes only, as in the test of this page: each of the 11 releases from 10.2.0 (the first with the sandbox histogram collector) to 10.6.0 and the builds of branch_11x and main that were run. With a collector of the caller's own that declines a segment: each build that was run from 9.12.0 on, the first release with this search method. It is not new in 11.0: the 10.6.0 release jars fail the same test.
  • Experimental APIs, and no javadoc sentence for the throw. DrillSideways and Collector are tagged @lucene.experimental. No javadoc sentence says that a collector may throw the exception from getLeafCollector: the exception's javadoc names LeafCollector#collect(int) as the place to throw and IndexSearcher as the one that swallows it.
  • No application that puts such a collector into a drill-sideways slot was found (three searches of public code on 2026-11-22).

You index two segments, of which only the first has a document with the numeric doc-values field price, and call DrillSideways#search(DrillDownQuery, CollectorManager, List) on a DrillSideways built without an executor, with one dimension (color = red) and the sandbox HistogramCollectorManager("price", 10) as the collector manager of that dimension. You expect the search to return with the histogram {0=1}, which IndexSearcher.search returns for the same manager on the same index and which the same call returns when the DrillSideways was built with an executor. Instead the search throws CollectionTerminatedException, an unchecked exception without a stack trace, with and without assertions, and returns nothing. The histogram collector declines the segment without the field by throwing that exception from getLeafCollector; the search loop of IndexSearcher has a handler around that call for the hit collector; DrillSidewaysQuery asks each dimension's collector for its leaf collector inside Weight#scorerSupplier, which the loop calls after and outside that handler.

With the histogram collector manager alone in a dimension's slot the search threw in each of the seven shapes that were run with a segment whose field infos lack the field: that segment as the second and as the first of two; its document matching the dimension or not; a segment in which the base query matches no document; an index of one segment in which no document has the field (the search returns an empty histogram there); two dimensions with a histogram manager in each slot; and a range of the histogram's own field as the dimension. In the same runs it returned what IndexSearcher.search returns in each of the six other shapes, among them: every segment has the field; the two documents in one segment; the two segments after forceMerge(1); and the test's index with the histogram manager beside a hit-count manager in one MultiCollectorManager in the slot, where the hit-count member takes the segment that the histogram collector declines. The same call on a DrillSideways built with an executor returned that result in all thirteen shapes. These shapes were run on the 10.2.0 and 10.6.0 release jars and on builds of branch_11x and main.

The search method came with #13568 (merged 2024-08-12; in 9.12.0 and 10.0.0). The call without a handler has been inside the query's Weight since #12853 (December 2023). The sandbox histogram collector came with #14204 (2025-02-21; in 10.2.0). No report of this defect was found. The same kind of omission at two other drivers of collectors is the subject of two other findings of this list: LFV-154 (core's CachingCollector#replay) and LFV-1581 (the sandbox PostCollectionFaceting). A handler around the one call, as the search loop has one, makes the test pass; with it the facet module's tests show no failure (304 tests) and the facet module's check without tests passes.

Why it looks unintended

#
  • The method's javadoc: "This method can be used with any CollectorManagers". With an executor the same call returns the result.
  • The search loop, MultiCollector and SuggestIndexSearcher have a handler around this very call; core's TotalHitCountCollector throws from it.
  • Limits: no javadoc sentence covers a throw from getLeafCollector; experimental APIs; without an executor a dimension's collector gets neither setWeight nor scoreMode().

The limit of this argument.

  • The javadoc of the exception reads, whole: "Throw this exception in {@link LeafCollector#collect(int)} to prematurely terminate collection of the current leaf." and "Note: IndexSearcher swallows this exception and never re-throws it. As a consequence, you should not catch it when calling the different search methods that {@link IndexSearcher} exposes as it is unnecessary and might hide misuse of this exception." (CollectionTerminatedException.java:19-26 at main 3cee9ed259e9; the same file at the 10.6.0 release tag). It names LeafCollector#collect(int) as the place to throw and IndexSearcher as the one that swallows. It names neither getLeafCollector nor DrillSideways.
  • No javadoc sentence covers a throw from getLeafCollector: the javadoc of Collector#getLeafCollector (lucene/core/src/java/org/apache/lucene/search/Collector.java:48-53) does not name the exception, and neither does the rest of the file. Christoph Kaser wrote the same in 2015 in LUCENE-6326 ("even though this is not documented in the JavaDoc"), and on the java-user list András Péteri asked on 2015-03-02 whether that throw is "an implementation detail"; Adrien Grand answered: "It feels useful to me too, I think we should document this behaviour."
  • DrillSideways and Collector are tagged @lucene.experimental (DrillSideways.java:69, Collector.java:44), and the one stock collector found that declines a segment in a dimension's slot is a class of the sandbox module.
  • When the call was moved to where it is (#12853, December 2023), a dimension's collector could only be a FacetsCollector.
  • The mode without an executor does not drive a dimension's collector as a search does: it calls neither setWeight nor scoreMode() on it (step 10 of the path above), and two comments of the package-private query still speak of FacetsCollectors (DrillSidewaysQuery.java:56-59: "will create new {@link FacetsCollector}s for each {@link LeafReaderContext} using the provided {@link FacetsCollectorManager}s"; :211). So "any CollectorManagers" is no statement that a dimension's collector is driven as IndexSearcher drives it, and a maintainer can take the missing handler as part of the same narrower treatment.
  • The facet module has a test that expects the exception, TestDrillSideways#testCollectionTerminated. By reading, it is about another layer: it drives a DrillSidewaysScorer with a hit collector that throws from collect and asserts that score throws (lucene/facet/src/test/org/apache/lucene/facet/TestDrillSideways.java:299-316), and its comment says that what it checks is that finish was still called (:318-323). It runs no search; in a search that score call is inside the search loop's second handler. Among the test sources of the facet and sandbox modules it is the one file that names the exception (a word search at main 3cee9ed259e9).
  • So this page does not speak of a documented contract. That a collector may decline a segment from getLeafCollector rests on the search loop's handler, on stock collectors, on Lucene's tests and on the repairs at two other classes, not on a javadoc sentence. Whether the driver of the drill-sideways collectors has to handle the exception is the maintainers' call.
The devil's-advocate check409 words

The strongest case for "works as designed": the only sentences that say who handles the exception name IndexSearcher ("IndexSearcher swallows this exception and never re-throws it"), and the place they name for the throw is LeafCollector#collect(int). The collector of a drill-sideways dimension is not driven by the search loop but by DrillSidewaysQuery, a package-private class of an API tagged @lucene.experimental. For a throw from getLeafCollector there is no javadoc sentence at all. When the call was moved into the query's Weight (#12853), a dimension's collector could only be a FacetsCollector, which does not throw. The one stock collector found that throws there is a sandbox class, and a caller has a way out, an executor. And the mode without an executor already treats a dimension's collector differently from a search: it gives it no weight and never reads its score mode. So one could say: a caller that puts a collector that declines segments into a slot has to wrap it.

Why it does not carry the case: the method was opened to other collectors on purpose (the description of #13568: "we had to change DrillSideways to support any type of Collector, not just FacetCollector"), and its javadoc says "any" collector managers and names none that needs a wrapper. The two modes of the one method disagree on the same arguments, and the class javadoc tells them apart by cost. The mode that throws runs through IndexSearcher.search, of which the exception's javadoc says "never re-throws it" and whose callers it tells not to catch the exception. A caller that does catch it has no result, not even the hits. With the histogram manager the outcome follows from the data: whether the call throws depends on the field infos of each segment. The exception reaches the caller without a message and without a stack trace. The missing setWeight and scoreMode() calls are not answered away: they bound what a comparison with a search can mean, and this page compares the two modes only for the shapes that were run; with those calls missing the collectors that were run still returned their result, where a declined segment costs the whole result of the call. What the argument does bound is the weight: an experimental API, a loud failure, one stock trigger in the sandbox module, no known caller. That is why the finding is Low, and why this page does not speak of a documented contract.

A handler around the one call, as the search loop has one (tried; validated by runs) (recommended)

#

In DrillSidewaysQuery.java (one file, +19 -3): the call sidewaysCollector.getLeafCollector(context) inside scorerSupplier goes into a try. When the dimension's collector throws CollectionTerminatedException, the dimension gets a leaf collector that does nothing for that segment, and the hits and the other dimensions go on. That is what MultiCollector does for a collector it wraps, and what the search loop does for the hit collector.

          LeafCollector sidewaysLeafCollector;
          try {
            sidewaysLeafCollector = sidewaysCollector.getLeafCollector(context);
          } catch (CollectionTerminatedException _) {
            // This dimension's collector has no interest in this leaf (the reading IndexSearcher
            // and MultiCollector give the same exception): collect nothing for it here.
            sidewaysLeafCollector =
                new LeafCollector() {
                  @Override
                  public void setScorer(Scorable scorer) {}

                  @Override
                  public void collect(int doc) {}
                };
          }
          dims[dim] = new DrillSidewaysScorer.DocsAndCost(scorer, sidewaysLeafCollector);

Trade-offs

  • The dimension whose collector declined collects nothing in that segment; no result of the call is lost.
  • The leaf collector that does nothing still gets finish() from the query and the scorer; the collector that declined gave no leaf collector of its own, so nothing of its own is finished, as in the search loop, which returns before finish (IndexSearcher.java:816-820).
  • catch (CollectionTerminatedException _) is the form the sources of main and branch_11x use; the 10.x sources use a named variable.
  • The try is entered once for each dimension and segment, not for each document. No benchmark was run.
  • The suites ran with one seed, on one JDK and one platform.

State the limit (not run)

Trade-offs

The method's "any CollectorManagers" would get an exception, and the sandbox histogram manager could then not be a dimension's collector manager without an executor on an index with a segment whose field infos lack the field.

Impact note
Hits applications that call the three-argument DrillSideways#search(DrillDownQuery, CollectorManager, List) with collector managers of their own choice on a DrillSideways built without an executor (its sequential mode) and put into a drill-sideways slot a collector that declines a segment by throwing CollectionTerminatedException from getLeafCollector: the search throws that exception, which is unchecked and carries no stack trace, and returns no result (neither the hits nor the dimensions' results of that call); no wrong result is returned and nothing is written to the index.
