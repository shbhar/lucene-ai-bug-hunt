deleteDocuments(Query) rewrites the query on each segment alone, so it can delete a different set than search returns

IndexWriter.deleteDocuments(Query) resolves the query on each segment separately, so queries whose matches depend on other documents delete a layout-dependent set: on two segments, a kNN query that finds 2 documents deletes 4, and a default FuzzyQuery that finds 50 deletes 60. Silent, and permanent once committed.

The bug in 30 seconds

#

Same query, same documents: only the segment layout changes what is deleted.

  1. Index six documents with vectors (1, 1), (2, 1), ... (6, 1) in two commits, so ids 0-2 and ids 3-5 are two segments (a plain IndexWriterConfig; the test pins the real default codec so the test framework does not randomize it, and turns merges off only to keep the layout). search(new KnnFloatVectorQuery("vector", {0, 1}, 2)) returns ids 0 and 1.
  2. Call deleteDocuments with the same query and commit. You expect ids 0 and 1 to be deleted: it "Deletes the document(s) matching" the query, and k is "the number of documents to find".
  3. You get ids 0, 1, 3 and 4 deleted, the 2 nearest of each segment. No error. With the same six documents in one segment, exactly ids 0 and 1 are deleted. updateDocuments(query, docs) does the same.
  4. Why: when the delete is applied, applyQueryDeletes builds new IndexSearcher(segmentReader) for each segment and rewrites the query there, so kNN's top k, FuzzyQuery's top 50 terms and index statistics are computed per segment, and the deleted set is the union.
  5. Other queries, two segments: a default FuzzyQuery name:lucenex~2 finds 50 and deletes 60; MoreLikeThisQuery and a score range find 6 and 4 and delete none. Term, range and other per-document queries are not affected.

Who is affected

#

Applications that delete or update by a query whose matches depend on other documents: kNN ("delete the k nearest"), a typed fuzzy term (Lucene's own Luke "Delete Docs" passes the search query to deleteDocuments), top-N term rewrites, CommonTermsQuery, MoreLikeThisQuery, score ranges. Default config, indexes with two or more segments. Per-document queries are not affected by this.

Mechanism, terms and numbers744 words

IndexWriter.deleteDocuments(Query...) and updateDocuments(Query, docs) do not run the query over the whole index the way a search does. When the buffered delete is applied, FrozenBufferedUpdates.applyQueryDeletes builds a new IndexSearcher over each segment, rewrites the query there and deletes that segment's matches. For per-document predicates (a term, a range) that changes nothing. For queries whose matches depend on the other documents of the index (kNN's top k, the default FuzzyQuery's top 50 terms and other top-N rewrites, CommonTermsQuery, MoreLikeThisQuery, score ranges) each segment picks its own matches, so the delete removes more or fewer documents than IndexSearcher.search returns for the same query: on two segments a kNN query with k = 2 deletes 4 documents and a default FuzzyQuery deletes 60 where search finds 50, while MoreLikeThisQuery and a score range delete none of the 6 and 4 hits. With the same documents committed in one segment every delete equals the search, so the segment layout alone decides what is deleted, silently and permanently once committed. It is as old as the API (2.4.0, 2008): executed on 22 releases from 2.4.0 to 10.5.2 and on main, all affected, and every release tag since 2.4.0 has the same per-segment code. updateDocuments(Query, ColumnBatch) (since 10.5.0) uses the same delete path (by reading).

Terms

#
  • Segment: an index is a set of independent segments; each commit or flush can add one, and merges combine them. Users do not choose the layout; the default merge policy changes it over time.
  • Rewrite: before a query runs, IndexSearcher.rewrite turns it into a primitive query using the searcher's reader. kNN does its real work here (it finds the top k), and a FuzzyQuery picks its top 50 terms here.
  • Delete packet: deleteDocuments(Query) only buffers the query. It is applied later (at flush, commit, NRT reopen or merge) by FrozenBufferedUpdates.applyQueryDeletes.

The bug

#
  1. applyQueryDeletes loops over the segments the packet applies to and, for each one, runs new IndexSearcher(readerContext.reader()), searcher.rewrite(query) and createWeight (FrozenBufferedUpdates.java:397-400 on main).
  2. So every reader-dependent decision is made per segment: kNN's top k over that segment's vectors (AbstractKnnVectorQuery.rewrite, :75-118), the top 50 fuzzy terms among that segment's terms (FuzzyQuery.java:34-36, 56), CommonTermsQuery's high/low frequency split against that segment's maxDoc (CommonTermsQuery.java:113, 154-155), MoreLikeThis's minDocFreq and idf against that segment (MoreLikeThis.java:634-660), and the BM25 statistics behind a score range.
  3. The deleted set is the union of the per-segment results. An independent check that replaces "search on the index" with "union of one-segment searches" as the expected result passes all 9 of its tests.
  4. One call can even be resolved several times: once for the segments that already exist, and once more for each segment flushed from documents buffered before the call (a segment-private packet always covers exactly one segment). So for ordinary query deletes the writer never builds one searcher over all segments (an exact MatchAllDocsQuery is not resolved at all: it becomes deleteAll()). One segment is not always safe either: in the 2016-cell matrix, when the documents are still buffered at the call and more are added after it, the one flushed segment also holds the later documents, and the default fuzzy query deletes 49 of its 50 search hits, top-terms(5) 2 of 5, kNN k = 2 none of 2 and a score range 31 of 36.

Exposure and likelihood407 words
  • Who is hit. Applications that delete or update by a query whose matches depend on other documents: kNN ("delete the k nearest", or replace them with updateDocuments(Query, docs)), a parsed or typed fuzzy term in a delete-by-query feature, top-N MultiTermQuery rewrites, CommonTermsQuery, MoreLikeThisQuery, and score ranges (FunctionRangeQuery, FunctionMatchQuery).
  • Lucene's own Luke does this. Its "Delete Docs" button asks "Are you sure to permanently delete the documents?", then passes the current search query to IndexWriter.deleteDocuments and commits. By reading (Luke itself was not run), a user who searched name:lucenex~2 on such an index and saw 50 hits would lose 60 documents.
  • Default configuration. Default IndexWriterConfig, codec and merge policy; indexes with two or more segments, the normal case, when a segment's own top k or top terms differ from the index's. The JUnit pins the layout with NoMergePolicy; the independent reproducer also fails with the default TieredMergePolicy, and the 2016-cell matrix shows the same through an NRT reader, through updateDocuments(Query, docs) and with the last segment still buffered.
  • Silent and permanent. No error, with assertions on or off. Over-deletion is data loss once committed; under-deletion leaves documents that a retention or erasure delete was meant to remove.
  • Not affected by this. Per-document predicates. Executed controls: a term, a point range, a default prefix, a fuzzy query whose 1024-term cap is never reached and a boolean of a term and a range matched search in all 1655 layout checks; a term, a point range, a prefix, a wildcard, the same fuzzy query and a vector-similarity threshold matched in all 576 control cells of the matrix. Term-set and field-value function queries were not executed; they are per-document by reading. This covers this mechanism only: stale doc values in delete-by-query (#8398) is a separate, known bug.
  • How likely. Rare: a ranking or statistics query is an unusual delete predicate, no upstream test uses one, and the searches below found no prior report.
  • Workaround. Search a near-real-time reader and delete the hits by a unique id term (or try tryDeleteDocument per hit, an expert best-effort call that returns -1 when it cannot delete); deleting by id removes exactly the search hits. Pre-rewriting a fuzzy query on a whole-index searcher also works, but not a kNN query: the rewritten kNN query throws "This DocAndScore query was created by a different reader" when the delete is applied and closes the writer (a separate, known bug).

Why it is a bug, not intended

#
  • The javadoc promises to delete "the document(s) matching any of the provided queries"; nothing documents per-segment resolution, and no upstream test deletes with such a query.
  • kNN works in rewrite so that "the number of documents it matches doesn't depend on the number of segments" (#11838).
  • Lucene's own Luke deletes search hits by passing the search query to deleteDocuments.
The full argument300 words
  • Contract. deleteDocuments(Query...): "Deletes the document(s) matching any of the provided queries" and "@param queries array of queries to identify the documents to be deleted" (IndexWriter.java:1875, 1879); updateDocuments(Query, docs): "take a query instead of a term to identify the documents to be updated" (:1613-1614); updateDocuments(Query, ColumnBatch) (since 10.5.0): "takes a query instead of a term to identify the documents to be deleted" (:1560-1561). No restriction on the query kind; the only special case is MatchAllDocsQuery, turned into deleteAll().
  • The query classes define matches over the whole reader. KnnFloatVectorQuery: "@param k the number of documents to find"; FuzzyQuery: "Only the top terms are used". On #11838 (2022) a Lucene developer explained that kNN does its work in rewrite to "match the global top k across segments, as opposed to matching k docs per segment. This means the number of documents it matches doesn't depend on the number of segments".
  • Nothing documents per-segment resolution. No javadoc, package doc, MIGRATE.md or CHANGES.txt entry says delete queries are resolved per segment or must be per-document predicates; the only "per segment" wording is the class comment of the package-private BufferedUpdatesStream, about resolving deletes to docIDs.
  • Untested, not decided. Upstream tests delete by query only with per-document predicates.
  • Lucene's own usage. Luke's "Delete Docs" passes the current search query to deleteDocuments: it assumes a delete matches the search.
  • History. Per-segment resolution is as old as the API (LUCENE-1194, 2008); its discussion and the later rewrites of the resolution code (LUCENE-6688, LUCENE-7868, LUCENE-8242) never discussed reader-dependent queries, which mostly arrived later (fuzzy with 50 terms in 4.0.0, CommonTermsQuery in 4.1.0, kNN in 9.0.0); the two that existed in 2008, FuzzyQuery's top-1024-terms rewrite and contrib MoreLikeThisQuery, are not mentioned in the LUCENE-1194 discussion.
The devil's-advocate check263 words

The intended-behaviour checker's strongest case (rated moderate by every checker): per-segment, deferred resolution is the original, deliberate design, and one delete is resolved in several packets, so the writer never has a whole-index view. On #8398 (stale doc values in delete-by-query) a committer wrote that the resolution code "has a hard assumption that segments are write-once as far as queries resolving to docIDs is concerned" and leaned "towards requiring/documenting" a limitation; another suggested "Maybe we should just document the limitation". Query#rewrite depends on the searcher and matching is per leaf, so each deleted document does match the query as rewritten on its own segment; kNN, MLT, CommonTerms and score ranges are ranking tools, not predicates; kNN search is approximate anyway, and the writer exposes no snapshot of the index at the time of the call; an exact way to delete what a search returned is a delete by a unique id.

Why it fails: nothing tells users, the queries are accepted silently, and the result is permanent. It fails in the cleanest case (everything committed, then one delete), where search returns one fixed set on every layout and only the layout changes what is deleted. #8398 is still open as a bug (the same committer opened with "This is indeed a bug"). Luke relies on delete matching search, and for kNN there is no general way to keep the query as the delete query and get the search set: pre-rewriting it on the whole index throws when the delete is applied. Verdict: a real, undocumented, silent defect; the fix may legitimately be documentation.

Suggested fix

#

Recommended Document per-segment resolution in the javadoc (recommended for the filing)

Document it: say in the deleteDocuments(Query...) and updateDocuments(Query, ...) javadoc that each query is resolved on each segment alone, so queries whose matches depend on other documents (kNN, the default FuzzyQuery, score ranges) can delete a different set than search; delete search hits by id. A code alternative (rewrite once per packet) passes the tests but is partial.

 * <p><b>NOTE</b>: each query (other than a {@link MatchAllDocsQuery}, which deletes all
 * documents) is resolved against each segment on its own, with an {@link
 * org.apache.lucene.search.IndexSearcher} over that one segment, not against the whole index.
 * Queries whose matches depend on the other documents of the index or on index statistics, such
 * as {@link org.apache.lucene.search.KnnFloatVectorQuery} (the top k), {@link
 * org.apache.lucene.search.FuzzyQuery} with its default top-terms rewrite, or a range over

Trade-offs

  • Partial. It fixes the clean cases on segments that exist when the delete is applied: everything committed, then a delete (the repro's case), and the NRT and updateDocuments paths. It does not fix documents buffered before the call (still resolved in their own one-segment private packet: in the matrix the "last segment still buffered" path keeps all 28 of its mismatching BM25 cells), documents added after the call (20 of 30 remain), kNN after an earlier delete in the same writer (8 of 30 remain, a separate known bug about stale live docs), or the non-default-Similarity cells. A full fix needs one resolution point over all segments, including the buffered ones: a design change.
  • Inside a private packet, top k is still chosen among all documents of the flushed segment, including those added after the call (then cut by the docID limit): unchanged from today.
  • Cost: one MultiReader and one rewrite per packet instead of one rewrite per segment; no benchmark was run. Concurrency with merges was not reviewed beyond the test runs.
  • A pre-rewritten kNN query still throws when applied and closes the writer (a separate, known bug).

Reject reader-dependent queries

#

Throw from deleteDocuments for queries whose matches depend on other documents. Not run.

Trade-offs

There is no general way to tell this from a Query; a list of known classes (kNN, top-N rewrites, CommonTerms, MLT, score sources) would be fragile and would break code that accepts today's behaviour.

Resolve each delete query against a whole-index view at a single point

#

Resolve the query once against all segments, including the buffered documents, at the delete's point in time. Not run.

Trade-offs

Correct by construction, but it needs an NRT-like view of the buffered documents (or a flush) per delete: a much larger change to the write path.

Downstream note

#

Downstream products that offer delete-by-query with kNN, fuzzy or other ranking queries, or a "delete what I searched" action, inherit the layout-dependent delete set; deleting the search hits by id avoids it.

How it was found

#

A differential test ran the same query through IndexSearcher.search and IndexWriter.deleteDocuments and compared the sets. The idea and first probe came from an ideation round by a model from another family (OpenAI GPT-5.6); a finder then ran a 2016-cell matrix and an exhaustive check of every small segment layout.

The method in full213 words

Method: Differential Query Execution, the database-testing idea of running one predicate as a SELECT and as a DELETE, aimed at Lucene's write path. Non-formal by the hunt's rules: the first signal was an executed probe.

  • Lead. In a cross-model ideation round, an independent model from another family (OpenAI GPT-5.6, testing-research framing) proposed comparing deleteDocuments(Q) with search(Q). Its probe on the stock main jar printed MISMATCH on 3 segments for kNN k = 2 (6 deleted vs 2 searched), the default FuzzyQuery (90 vs 50), TopTerms(5) (15 vs 5) and CommonTermsQuery (13 vs 40), and passed on 1 segment and for the TermQuery control (also on 10.5.2 and 9.12.3). A planning verifier re-ran every number.
  • Hunt. A finder ran a Differential Query Execution matrix: 21 query families (6 per-document controls) x 6 write paths (committed, NRT, updateDocuments, last segment buffered, after an earlier delete, followed by later documents) x 1/3 segments x 2 merge policies x 4 Similarities = 2016 cells, then a bounded-exhaustive layout check (every contiguous layout of 8 documents and every set partition of 6, 4303 checks), and wrote the public-API JUnit.
  • Checks. An independent reproducer, an executed review by a model from another family, an intended-behaviour devil's advocate, an adjudication and a credibility audit (section "Independent checks").

History

#

As old as the API: per-segment resolution came with deleteDocuments(Query) in LUCENE-1194 (5b113c8af63c, 2008), first released in 2.4.0, and every later rewrite kept it. Executed on 22 releases from 2.4.0 to 10.5.2, branch_10_6 and main: all affected. kNN joined the triggers in 9.0.0.

Versions tested8 rows

Introduced by 5b113c8af63c "LUCENE-1194: add IndexWriter.deleteDocuments(Query)" (#2271, svn r634219, 2008-03-06, no PR). The first implementation already ran new IndexSearcher(reader) and query.weight(searcher) for each SegmentReader. Later rewrites of the resolution code (LUCENE-2680 and LUCENE-1076 in 3.1/3.2, QueryWrapperFilter per segment in 3.3-5.2.1, LUCENE-6688 (5d16b973962, backported as 914ba735b56) in 5.3.0, LUCENE-7868 58105a203a1 in 7.0.0, LUCENE-8242 798d3510341 in 8.0.0) all kept the per-segment searcher, with identical executed numbers on both sides of each. Which stock queries trigger it grew over time: MoreLikeThisQuery and the default FuzzyQuery (1024 terms) from 2.4.0, TopTerms rewrites from 3.1, the default FuzzyQuery with 50 terms from 4.0.0, CommonTermsQuery from 4.1.0, score ranges from 5.4.0, kNN from 9.0.0, updateDocuments(Query, docs) from 9.7.0 and updateDocuments(Query, ColumnBatch) from 10.5.0 (not executed). Not fixed upstream: FrozenBufferedUpdates.java last changed on 2026-09-21 (#16581), not in this code.

Bug record

LFV-904, snapshot of 2026-10-29

Registry title
IndexWriter.deleteDocuments(Query) and updateDocuments(Query, ...) rewrite the query separately on each segment, so reader-dependent queries (kNN, the default FuzzyQuery and other top-N term rewrites, CommonTermsQuery, MoreLikeThisQuery, score ranges) delete a set that depends on the segment layout and differs from what IndexSearcher.search returns
Area
core / index write path (delete-by-query: FrozenBufferedUpdates.applyQueryDeletes) x core / search and queries (reader-dependent rewrites)
Priority
Medium, rank 12: This is a new, deterministic, permanent wrong-delete bug in core deleteDocuments/updateDocuments(Query) on default config, but only reader-dependent delete queries trigger it.
Impact class
data corruption
Impact note
Medium by judgement: applications that delete or update by a query whose matches depend on other documents (kNN top-k, the default FuzzyQuery and other top-N term rewrites, CommonTermsQuery, MoreLikeThisQuery, a score-range FunctionRangeQuery) get a deleted set that depends on the segment layout, silently and permanently once committed, with the default IndexWriterConfig, codec and merge policy on any index with 2 or more segments, on every release since 2.4.0 (kNN since 9.0.0) and on main; it over-deletes (kNN k=2 removes 4 documents on 2 segments, a default FuzzyQuery removes 60 where search finds 50) or under-deletes (MoreLikeThisQuery and a score range remove none of the 6 and 4 that search finds), per-document predicates (term, range, set, field-value function queries) are unaffected, and using a reader-dependent query as a delete query is an unusual pattern.
Summary
You call IndexWriter.deleteDocuments(query) (or updateDocuments(query, docs)) on an index with two or more segments and expect it to delete the documents IndexSearcher.search(query) returns, since the javadoc says it 'Deletes the document(s) matching any of the provided queries'. Instead the writer rewrites the query on a separate one-segment IndexSearcher for each segment, so top-k, top-N term expansion and index statistics are computed per segment: a kNN query with k=2 deletes up to 2 documents per segment (4 on two segments), a default FuzzyQuery deletes 60 documents where search finds 50, and MoreLikeThisQuery or a score-range predicate deletes none of the documents search returns. With the same documents committed in one segment before the delete, the delete equals the search result, so the segment layout alone decides what is deleted, and the result is permanent once committed.
