InputStreamDataInput.skipBytes throws EOFException when the stream skips fewer bytes than asked, for example over a BufferedInputStream

InputStreamDataInput.skipBytes(n) calls InputStream.skip(n) once and throws EOFException if it skipped fewer bytes, but Java streams may skip fewer before the end: over a BufferedInputStream, skipBytes(2) with 3 bytes left fails and still consumes a byte. Every release since 9.0.0 has it; no Lucene code at main calls it.

The finding in 30 seconds

#

A short count from InputStream.skip is normal, not the end of the stream. skipBytes treats it as the end.

Background: skipping on a Java stream

#
  1. InputStreamDataInput lets you read Lucene's encodings (vInts, strings, raw bytes) from any java.io.InputStream, for example a file written with OutputStreamDataOutput. skipBytes(n) should move past n bytes without reading them into your code.
  2. InputStream.skip(n) returns how many bytes it actually skipped. The JDK says this may be fewer than n, even 0, before the end of the stream; only -1 from read() means the end.
  3. BufferedInputStream reads ahead into a buffer (8,192 bytes by default). While that buffer holds bytes, its skip(n) skips only those buffered bytes and returns that count.

The finding, step by step

#
  1. Wrap the 4 bytes {0, 1, 2, 3} in a BufferedInputStream with a 2-byte buffer, and that in new InputStreamDataInput(...). readByte() returns 0; the buffer still holds byte 1, and 3 bytes are left.
  2. Call skipBytes(2). You expect bytes 1 and 2 to be skipped and the next readByte() to return 3, as in Lucene 8.x.
  3. Instead it throws EOFException. skipBytes calls is.skip(2) once; BufferedInputStream.skip skips only what it has buffered and returns 1, and skipBytes takes any count below 2 for the end of the stream.
  4. The skipped byte is gone too: the next readByte() returns 2, so the caller has neither skipped nor stayed put. The JDK allows such short counts before the end ("possibly 0"), and InputStream.skipNBytes handles them.
  5. At ordinary sizes: 100,000 bytes behind the default 8,192-byte buffer, readByte(), then skipBytes(10,000) with 99,999 bytes left before the call: it consumes the 8,191 buffered bytes and throws, leaving 91,808.

Who is affected

#

Only applications that call skipBytes on an InputStreamDataInput over a stream that can skip short, such as a BufferedInputStream whose buffer holds fewer bytes than the skip. No Lucene code at main does, and index files are read another way, so Lucene's own search and indexing never reach it. It fails loudly; no setting is involved; rare.

Mechanism, terms and numbers413 words

InputStreamDataInput (lucene-core, public, not @lucene.internal) reads Lucene-encoded data from any java.io.InputStream. Its skipBytes(numBytes) calls is.skip(numBytes) once and throws EOFException when that returns less than numBytes (InputStreamDataInput.java:62-66). The JDK contract of InputStream.skip allows a smaller count before the end of the stream, and BufferedInputStream.skip returns only its buffered remainder when the buffer is not empty. So over a BufferedInputStream, a skip longer than what is left in the buffer throws although the data is there, and the buffered bytes it skipped are consumed. The single skip call came with LUCENE-9794 (2021-02-24), a speed-up that replaced the read-based skip, so every release from 9.0.0 to 10.6.0 is affected; 8.x skipped correctly. is.skipNBytes(numBytes) fixes it (validated). Low impact: no Lucene code calls skipBytes on this class, so only applications that do are hit, loudly.

The bug

#
  1. InputStreamDataInput.skipBytes(long numBytes) (InputStreamDataInput.java:57-67) calls long skipped = is.skip(numBytes); once (:62) and then if (skipped < numBytes) { throw new EOFException(); } (:64-66). There is no loop.
  2. JDK 25 BufferedInputStream.skip(n): with avail = count - pos > 0 buffered bytes it returns min(avail, n) without refilling or asking the wrapped stream. Only with an empty buffer (and no mark) does it pass the call to the wrapped stream.
  3. JDK 25 InputStream.skip javadoc: "The skip method may, for a variety of reasons, end up skipping over some smaller number of bytes, possibly 0. This may result from any of a number of conditions; reaching end of file before n bytes have been skipped is only one possibility."
  4. So whenever the buffer holds some bytes but fewer than the skip, step 1 throws. The bytes skip did pass are not given back.

In the same class

#

readBytes (:39-50) loops while (len > 0) on short reads and throws EOFException only when read returns -1; readByte (:33-37) throws only on -1. Only skipBytes treats "fewer than asked" as the end.

The numbers

#

4 bytes {0, 1, 2, 3}, a 2-byte buffer: readByte() returns 0 and leaves 1 byte buffered; skipBytes(2) with 3 bytes left gets 1 from skip and throws; afterwards 2 bytes are left and readByte() returns 2. 100,000 bytes, the default 8,192-byte buffer: readByte(), then skipBytes(10,000) with 99,999 bytes left before the call: skip returns the 8,191 buffered bytes, skipBytes throws, and 91,808 bytes are left after it. Over a ByteArrayInputStream, or a BufferedInputStream with an empty buffer, the same skips succeed.

Exposure and likelihood250 words
  • Who is hit. Code that calls skipBytes on an InputStreamDataInput, directly or through a public method that skips on the DataInput it is given (for example ByteSequenceOutputs.skipOutput, which calls in.skipBytes(len), ByteSequenceOutputs.java:135-139; not run through that path). Wrapping a stream in a BufferedInputStream is common (Lucene's own FST.read(Path) does it), and then the bug triggers deterministically once a read has partly drained the buffer and a skip asks for more than is left in it.
  • Who is not hit. Lucene itself: its non-test users of the class (FST.read(Path), which wraps a BufferedInputStream, the kuromoji, nori and shared morph dictionary loaders, suggest Lookup.load, MonitorQuerySerializer) only read from it; the skipBytes calls in FST.java are on its own BytesReader. Index files are read through IndexInput, not this class.
  • What happens. One checked EOFException from the skipBytes call although the data is there, and a lost stream position: the bytes skip passed are consumed, so the caller cannot simply retry.
  • What does not happen. Lucene returns no wrong value silently; no hang, no memory growth, no index involvement.
  • Default vs opt-in, scale. No setting is involved; it depends only on the stream the caller wraps. 4 bytes and a 2-byte buffer suffice. Deterministic, the same with -ea and -da.
  • How likely. Rare: no report of it was found since 9.0.0 (2021), and the one downstream skipBytes on this class found in the searches runs over a ByteArrayInputStream, which never skips short.

Why it looks unintended

#
  • DataInput.skipBytes promises "Skip over numBytes bytes"; the call asks for 2 with 3 left.
  • The JDK says InputStream.skip may skip fewer bytes before the end; the class's own readBytes already loops on short reads.
  • Lucene 8.x skipped correctly; the single skip call came from a speed-up whose discussion never mentions short skips.
The full argument219 words
  • Contract. DataInput.java:294-299: "Skip over numBytes bytes. This method may skip bytes in whatever way is most optimal, and may not have the same behavior as reading the skipped bytes." It does not say what a short skip means; read plainly, the freedom is about how bytes are skipped, not how many.
  • JDK contract. InputStream.skip "may, for a variety of reasons, end up skipping over some smaller number of bytes, possibly 0"; the JDK offers skipNBytes (since 12) to skip exactly n bytes. Main needs Java 25 and 10.x Java 21.
  • Inconsistent with its own class. readBytes (InputStreamDataInput.java:39-50) loops on short reads and signals the end only on -1.
  • It worked before. Up to 8.11.4 the class had no skipBytes override and inherited the read-based DataInput.skipBytes; 8.8.1 skips correctly in the probe, and 8.8.1 and 8.11.4 pass both the minimal test (-da, with the 8.x LuceneTestCase package) and its earlier 100,000-byte version.
  • The change was a speed-up. LUCENE-9794 ("Speed up implementations of DataInput.skipBytes()", CHANGES.txt) replaced the read loop with one skip call. Its issue (#10833, 7 comments) and the dev@ thread before it ("GC improvement when skipping bytes in DataInput", 2021-02-17) discuss speed and garbage only. The test it added, TestInputStreamDataInput, uses only ByteArrayInputStream, which never skips short before the end.
The devil's-advocate check177 words

The strongest case for "not a bug": LUCENE-9480 (c51fee9c1a5) loosened the skipBytes javadoc on purpose, from "should have the same behavior as reading the same number of bytes into a buffer and discarding its content" to "may skip bytes in whatever way is most optimal"; LUCENE-9794 then chose one skip call deliberately, and TestInputStreamDataInput.testNoReadWhenSkipping pins "no reads while skipping". The class javadoc also says "A DataInput wrapping a plain InputStream" (:24), which one could read as "a stream that skips exactly".

Why it fails: the javadoc still opens with "Skip over numBytes bytes", so it frees the mechanism, not the count. testNoReadWhenSkipping forbids calls to the DataInput read methods, and the skipNBytes fix keeps it and the other three tests green. "A plain InputStream" excludes nothing: the constructor takes any stream, and Lucene itself wraps a BufferedInputStream in FST.read(Path) (FST.java:540). That no Lucene code skips on this class lowers likelihood, not validity. Still, the cross-model reviews rated the intended-behaviour case moderate: a maintainer could prefer a thin adapter that fails fast.

Suggested fix

#

Recommended Use InputStream.skipNBytes

Replace the single is.skip call and its count check with is.skipNBytes(numBytes), which loops and throws EOFException only at the real end. Validated: the test then passes with assertions on and off, the 778 tests of org.apache.lucene.store pass (assertions on, 0 failures), and the format and forbidden-API checks are clean.

-    long skipped = is.skip(numBytes);
-    assert skipped <= numBytes;
-    if (skipped < numBytes) {
-      throw new EOFException();
-    }
+    // InputStream.skip may skip fewer bytes than requested before the end of the stream;
+    // skipNBytes loops and throws EOFException only at the real end.
+    is.skipNBytes(numBytes);
All options and trade-offs3 options · 418 words

Three options. A was run; B and C were not. Going back to reading the skipped bytes through readBytes is not suggested: it would break testNoReadWhenSkipping and undo LUCENE-9794's speed-up.

Use InputStream.skipNBytes (validated by the checks) (recommended)

#

In skipBytes, replace :62-66 with one call. skipNBytes loops on skip, calls the stream's read() when skip returns 0, and throws EOFException only when the stream really ends. For streams that report a short count at the end, such as the tested ByteArrayInputStream (testSkipOffEnd), a skip past the end still throws as before. A stream whose skip reports bytes beyond the end (the JDK allows this for FileInputStream.skip) did not throw before and does not throw with the fix either; that case was not tested.

-    long skipped = is.skip(numBytes);
-    assert skipped <= numBytes;
-    if (skipped < numBytes) {
-      throw new EOFException();
-    }
+    // InputStream.skip may skip fewer bytes than requested before the end of the stream;
+    // skipNBytes loops and throws EOFException only at the real end.
+    is.skipNBytes(numBytes);

Trade-offs

Needs Java 12+: fine for main (Java 25) and 10.x (Java 21); a fix on the 9.x line (Java 11) needs option B. With the JDK's default skipNBytes, an exact first skip still finishes in one call. When the stream's skip returns 0, skipNBytes reads one byte with the stream's own read(), which may block or cost more than a skip; testNoReadWhenSkipping guards only the DataInput read methods, not the wrapped stream.

A hand-written skip loop (for 9.x)

#

Loop on is.skip; when it returns 0, call is.read() once and throw EOFException on -1, else count that byte.

Trade-offs

Same behaviour as A on Java 11, a few more lines to maintain. Not run.

Document the requirement

#

Trade-offs

Smallest change, but leaves a trap for the most common wrapper, BufferedInputStream, including the one Lucene itself uses in FST.read(Path). Not run.

Downstream note

#

An application that reads records until EOFException and treats that exception as its normal end of data would stop early, without an error, when such a skip fails.

How it was found

#

Semi-formal: a proof-obligation audit of the InputStreamDataInput contract. skipBytes(n) must skip n bytes whenever n bytes remain, and the JDK lets InputStream.skip return fewer; the single skip call fails that obligation, shown with an executable test on main.

The method in full129 words

Method: semi-formal, a proof-obligation audit of InputStreamDataInput's contract, witnessed by an executable repro (2026-11-03, main 5adff78bb168).

  • The obligation: DataInput.skipBytes promises to skip numBytes bytes, and the class signals the end of input with EOFException, so skipBytes(n) with at least n bytes left must return normally.
  • Discharging it against the code fails: the only evidence skipBytes uses is one skip count, and the JDK contract lets that count be short before the end; BufferedInputStream gives such a count whenever its buffer holds fewer bytes than the skip.
  • The witness was an executable test on the stock main jars with assertions on and off (2026-11-03: a 100,000-byte version of the one-test repro above, later cut down to 4 bytes; the 4-byte test fails the same way, 2026-11-05).
