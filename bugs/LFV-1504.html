The finding in 30 seconds

#

New in 11.0, in no release: the test below fails 1 of 1 on the 11.0 branch (branch_11x daa54f2e0cd3) with assertions on and off, and 10.6.0 does not have the Faiss vector format (added by #14178, commit 922ecaa17f61), so 11.0.0 would be the first release with it. The format is sandbox, experimental and opt-in, and needs the Faiss native library.

Background: three pieces

#
  1. FaissKnnVectorsFormat keeps a segment's vector index inside the Faiss native library. To store it, Lucene asks the library to write the index, and the library hands the bytes back through a callback: a small Java method that writes them to the segment's file. Reading works the same way.
  2. Java can give native code a Java method to call (an upcall). The JDK's rule for such a method: it must not throw. If an exception leaves it, the JVM prints the stack trace and exits.
  3. Lucene's file outputs and inputs may throw IOException from any write or read: the disk is full, a quota is hit, or the merge that is writing was aborted. commit(), merges, rollback() and DirectoryReader.open are built to get that exception.

The finding, step by step

#
  1. Open an IndexWriter with FaissKnnVectorsFormat (sandbox, experimental, needs the Faiss native library) and add 1 document with the vector (1, 2).
  2. Call commit() while the directory refuses every write to the Faiss index file (.faissd) with IOException: no space left on device, as a full disk would.
  3. You expect commit() to throw that IOException. With Lucene's default vector format a refused write does that, and the JVM lives.
  4. You get no exception. The JVM prints the stack trace, then Unrecoverable uncaught exception encountered. The VM will now exit, and the whole process ends with exit code 1, with assertions on or off. The test runs this in a child JVM, so only the child exits.
  5. Why: Faiss writes the index by calling back into a Java method, FaissLibraryNativeImpl.writeBytes. The method lets the IOException out, and the JDK ends the JVM when an exception leaves such a callback. rollback() during a merge that writes a Faiss index above 1 MiB, and a read error while a reader opens, end the same way; so does any other call that flushes a segment, such as addDocument when the buffer is due. The last commit stays intact.

Who is affected

#

Only applications that chose FaissKnnVectorsFormat: sandbox, @lucene.experimental, needs the Faiss native library, not the default codec, in no release yet. For them a full disk or quota during a flush or merge, or rollback() during a merge that writes a Faiss index above 1 MiB, ends the whole process and every other index in it. Committed data stays intact.

Mechanism, terms and numbers1,391 words

FaissKnnVectorsFormat is a vector format in Lucene's sandbox module (@lucene.experimental, opt-in, needs the Faiss C library) that is new in 11.0: it was added by #14178 (922ecaa17f61), the 11.0 branch branch_11x daa54f2e0cd3 and main 781025d6fe32 have it (both unreleased), and no release does (10.6.0 has no Faiss format), so 11.0.0 would be the first release with it. The format keeps each segment's vector index inside the Faiss native library. The library writes and reads that index by calling back into two Java methods of Lucene, FaissLibraryNativeImpl.writeBytes and readBytes (FaissLibraryNativeImpl.java:71-111 on main 781025d6fe32; the file is identical on branch_11x), which pass the bytes to the segment's IndexOutput or take them from its IndexInput. Both are handed to native code as upcall stubs (:64-67), are declared throws IOException and catch nothing. The JDK's rule for an upcall target is that it must not throw: "If the target method handle does throw an exception, the JVM will terminate abruptly". So when the Directory throws inside a callback (the disk refuses a write during a flush or a merge, IndexWriter.rollback() aborts a merge that is writing a Faiss index above 1 MiB, a read fails while a reader opens), the exception does not reach the call that started the work: commit(), a merge, rollback() or DirectoryReader.open, and equally addDocument, flush(), close() or a near-real-time reader when one of them flushes a segment. The JVM prints the stack trace and Unrecoverable uncaught exception encountered. The VM will now exit and exits with code 1, with assertions on or off, and every other index and request of that process ends with it. With Lucene's default vector format the same events are an exception the caller gets. The last commit stays intact: after the exit of a rollback() run CheckIndex found no problems and a new IndexWriter opened the index with every committed document. Uncommitted documents are lost, as with any process exit. The fix is small: the callbacks catch the exception, report a short count to Faiss, which then fails its call, and Lucene rethrows the exception to the caller.

The mechanism

#
  1. The callbacks become native entry points. getStub hands a bound method handle straight to Linker.nativeLinker().upcallStub(target, descriptor, arena) (FaissLibraryNativeImpl.java:64-67). It is the only upcallStub call in the Lucene sources.
  2. The write callback. writeBytes(IndexOutput output, MemorySegment inputPointer, long itemSize, long numItems) throws IOException (:71-89) calls output.writeBytes(...) at :79 and :85 with no handler and returns numItems.
  3. The read callback. readBytes(IndexInput input, ...) throws IOException (:91-111) calls input.readBytes(...) at :100 and :106 with no handler and returns numItems.
  4. Where they are bound. Index.write(IndexOutput) binds writeBytes to the output and passes the stub to faiss_write_index_custom (:404-426). readIndex(IndexInput, ...) binds readBytes to the input and passes the stub to faiss_read_index_custom (:242-265). Neither interface method declares an exception (FaissLibrary.java:39, :49).
  5. Who calls them. FaissKnnVectorsWriter.writeFloatField calls index.write(data) (FaissKnnVectorsWriter.java:171), reached from flush (:146) and from mergeOneField (:111). The reader's constructor calls readIndex over a slice of the data file for each field (FaissKnnVectorsReader.java:133-137); its catch (Throwable) (:139-142) never sees the exception.
  6. What the JDK does. "The target method handle should not throw any exceptions. If the target method handle does throw an exception, the JVM will terminate abruptly. To avoid this, clients should wrap the code in the target method handle in a try/catch block to catch any unexpected exceptions." (Linker#upcallStub, OpenJDK 25.0.3 Linker.java:699-702). The handler prints the stack trace and the line Unrecoverable uncaught exception encountered. The VM will now exit and calls System.exit(1) (SharedUtils.java:306-315).
  7. The rollback() path. Under ConcurrentMergeScheduler every output of a merge is a RateLimitedIndexOutput (ConcurrentMergeScheduler.java:286-310). Its writeBytes counts the bytes of each call and, once the bytes handed to that output since the last check (the call in hand included) exceed the limiter's check interval, asks the merge's rate limiter before it writes them (RateLimitedIndexOutput.java:52-60, :84-90). The interval is 1 MiB for a merge that is not throttled, which is the default (MergeRateLimiter.java:66-67), and the limiter throws MergeAbortedException when the merge was aborted (:115-119). The Faiss index is built in native code, where no abort is seen, and the library hands it to the callback in pieces, some of them large. So an abort that arrives during the build is first noticed inside the write callback, on the piece that takes the count past the interval and before that piece is written: with 40,000 vectors of 128 dimensions it was a piece of 5,291,584 bytes, after 480,296 bytes.

Exposure and likelihood627 words
  • Who. Applications that set FaissKnnVectorsFormat as their vector format. It is in lucene/sandbox, tagged @lucene.experimental, and needs the Faiss C library installed. The default codec is not affected. No release has the format; 11.0.0 would be the first, and its change list announces the format under New Features.
  • What is lost. The whole process. The call that started the work neither returns nor throws: commit(), a merge, rollback() or DirectoryReader.open, and any other call that flushes a segment or opens a segment's reader (run on the test's refused write: addDocument when the buffer is due, flush(), close() and a near-real-time reader). No catch or finally block on the stack of that call runs, and every other index and request of that JVM ends with it. The JDK's handler calls System.exit(1): in the runs a shutdown hook ran, and every JVM ended with exit code 1. Uncommitted documents are lost, as with any process exit.
  • What is kept. The last commit. After the exit of the rollback() run the directory still held its segments_2 file and both committed segments, next to the unfinished files of the merge; CheckIndex found no problems in it (2 segments of 20,000 vectors), and a new IndexWriter opened it with all 40,000 documents and left only the committed files when it closed. After the refused flush, which was that run's first commit, a new IndexWriter removed the unfinished files of the segment. The failure is loud: a stack trace and an exit code.
  • A write the operating system refuses (a full disk, a quota, a file-size limit) while a flush or a merge writes the Faiss index. Run with nothing injected, on a stock FSDirectory with a default IndexWriterConfig and only the vector format set, 2,000 vectors of 16 dimensions: under a file-size limit of 256 KiB ("File too large") and on a file system of 384 KiB that fills up ("No space left on device"). Condition: the failing write must be issued inside a callback. In an earlier run with a 64 KiB limit the raw vector file, which Java code writes, failed first: commit() threw and the JVM lived.
  • rollback() during a merge. No fault is needed, only the timing. Conditions: the default ConcurrentMergeScheduler (with SerialMergeScheduler the outputs are not rate-limited, and rollback() returned in the run); a merged segment whose Faiss data file is larger than the rate limiter's check interval, which is 1 MiB for a merge that is not throttled, the default (with the default index and 128 dimensions, 1,560 vectors let rollback() return and 1,600 ended the JVM); and rollback() arriving while the merge builds or writes the Faiss index. Run with nothing injected: rollback() 300 ms into a merge of two segments of 20,000 vectors of 128 dimensions; all earlier timed runs (12, on the 11.0 branch and on main) ended the same way.
  • A read error while a segment's reader opens. Shown by injection only: one failed read of the field's slice of the data file during DirectoryReader.open, while a near-real-time reader opens, and when a merge opens the segments it merges. The same root, not a headline.
  • Not run. Other sources of a merge abort (deleteAll(), a tragic event on another thread, an interrupted merge thread); a throttled or a paused merge, whose check interval can be smaller; a quota; a damaged or truncated data file at open; index types other than the default IDMap,HNSW32 and IDMap,Flat; any platform other than Linux aarch64.
  • Likelihood: plausible for an application that uses the format (an estimate, not usage data): a full disk or a quota, or a rollback() while a merge is running, are not daily events and are ordinary over the life of a deployment.

Why it looks unintended

#
  • The JDK says an upcall target "should not throw any exceptions", or "the JVM will terminate abruptly". Both callbacks are declared throws IOException and catch nothing.
  • Lucene reports I/O failures as IOException, and IndexWriter suppresses an aborted merge's exception itself. Here neither reaches it.
  • Faiss's I/O macros fail a call whose callback returns a short count. The callbacks never do.
The full argument505 words
  • The JDK's contract for the method the callbacks are registered with. Linker#upcallStub: "The target method handle should not throw any exceptions. If the target method handle does throw an exception, the JVM will terminate abruptly. To avoid this, clients should wrap the code in the target method handle in a try/catch block to catch any unexpected exceptions." The callbacks are declared throws IOException and catch nothing (FaissLibraryNativeImpl.java:71-111).
  • Lucene's failure channel is the exception. commit() and rollback() declare IOException (IndexWriter.java:4244, :2575-2578: "@throws IOException if there is a low-level IO error"), and so do KnnVectorsWriter.flush and mergeOneField (KnnVectorsWriter.java:56, :76). addDocument's javadoc: "if an Exception is hit (for example disk full) then the index will be consistent" (IndexWriter.java:1467). getTragicException: "closed as a side-effect of a tragic exception, e.g. disk full while flushing a new segment" (:6523-6527). MergeAbortedException: "Normally this exception is privately caught and suppressed by IndexWriter" (MergePolicy.java:721-724). With this format IndexWriter sees neither exception.
  • What the format's author wrote about errors raised inside Faiss. kaivalnp, in a comment of 2025-01-29 on #14178: "Handled exceptions in Faiss are gracefully rethrown in Lucene, but unhandled signals or bugs (like segmentation faults) cannot be recovered from, and kills the Java process with it!" The sentence is about errors that Faiss raises, and it was written before the pull request had the callbacks, which came with its commit of 2025-02-09. It shows that errors the native side can handle were meant to surface as Java exceptions. It does not speak about the callbacks: that an exception thrown in Lucene's own callback should reach the caller the same way is this page's reading, not the author's statement.
  • The library has an error channel the callbacks do not use. Faiss's I/O macros compare the count a callback returns with the count asked for and throw when it is short (READANDCHECK and WRITEANDCHECK in faiss/impl/io_macros.h of the 1.11.0 headers). With the two index types that were run, the default IDMap,HNSW32 and IDMap,Flat, the native call then fails; other index types were not run. The callbacks return numItems whenever they return.
  • An I/O failure is not a stated limit. The format's javadoc and package-info.java say nothing about I/O failures, the merge scheduler, rollback() or a process exit. No test asserts the exit.
  • No misuse. A Directory may throw IOException from any write or read, and rollback() during a merge is ordinary use.
  • Why upstream's tests pass. Upstream's CI job for the Faiss tests runs TestFaissKnnVectorsFormat with the library. The class inherits testRandomExceptions and does not ignore it. But the test directory throws its random IOException only on the first write to a new file (MockIndexOutputWrapper.java:151-156), and for the Faiss data file that first write is the header Lucene writes itself (FaissKnnVectorsWriter.java:86-87), never one inside a callback. Upstream's 59 tests (10 skipped by their own annotations and assumptions) pass with the defect. This is a test gap, not something a review overlooked.
The devil's-advocate check283 words

The strongest case for "accepted": the risk is on record for an experimental sandbox format. The commit message of #14178: "Note that this is native (C) code, so it's possible it has bugs that trigger SIGSEGV and then the OS rapidly tears down the JVM ... This new format is experimental, might have exciting bugs, and has no promise of backwards compatibility. PRs welcome!". The author's open issue #14875: "This is important because we're dealing with native code, without fine control over memory allocation and error handling -- and could result in the JVM crashing!". The class is tagged @lucene.experimental. And the failure is loud and loses no committed data.

Why it fails: each of those statements is about faults inside the native library, where Java has no control. Here the exception is a Java exception from Lucene's own Directory, thrown in Lucene's own Java callback, where it can be caught, and the JDK documents that it must be. The author's comment describes errors that Faiss handles as rethrown in Lucene (it predates the callbacks and does not speak about them), and Faiss offers a channel for an error inside a callback (a short count). The experimental tag is about API stability; an earlier defect of this format (#14847) is listed under Bug Fixes of 11.0.0, and "might have exciting bugs ... PRs welcome!" calls such defects bugs. That the failure is loud and keeps the last commit is true and is why the priority is Low; it does not make the exit intended. Catch in the callbacks, give Faiss a short count, rethrow after the native call (validated) (recommended)

#

The two upcall targets become wrappers around the existing writeBytes and readBytes. A wrapper catches every Throwable, keeps the first one in a one-field holder that is bound into the method handle next to the output or input, and returns 0. Faiss's I/O macros check the count, and the native call fails (run with the default index and with IDMap,Flat; other index types were not run). Index.write and readIndex then rethrow the kept exception before they look at Faiss's own error code. One file, 77 lines added and 9 removed. Trade-offs

  • How the exception is rethrown. Index.write(IndexOutput) and readIndex(...) declare no checked exception, so the diff rethrows the kept exception through a generic helper. A patch may instead declare throws IOException on the two interface methods; their callers already declare it. That variant was not built.
  • It catches every Throwable, on purpose. By the same JDK rule, an OutOfMemoryError in a callback (it copies up to 256 MiB into a byte array) would leave the upcall the same way today. That case was not run.
  • Not checked. Whether the library releases everything it allocated when a read fails half-way (no leak check was run); index types other than IDMap,HNSW32 and IDMap,Flat; sources of a merge abort other than rollback(); platforms other than Linux aarch64.

MethodHandles.catchException where the stub is made (not built)

#

The combinator the JDK's javadoc names for this purpose: wrap the bound target once in getStub with a handler that stores the exception and returns 0. One place instead of two wrappers.

Trade-offs

It needs the same holder and the same rethrow after the native call, so the behaviour should be that of the recommended option with a little less code. Not built and not run.

No I/O inside the callbacks (not built, not recommended)

#

The callbacks only copy to and from a buffer, and Java code writes or reads the file afterwards, outside the native call.

Trade-offs

A second copy of the index in memory or on disk. The pull request that added the format moved away from temporary files to these callbacks. The callbacks would still need a handler for an error such as OutOfMemoryError.

How it was found

#

Found by reading the format's code: its two I/O callbacks are declared throws IOException and are handed to native code as upcall targets. A directory that fails one write inside the callback, run with the real Faiss library, ended the JVM. Lucene's own random I/O failures in tests never fire inside a callback, so upstream's tests stay green.

The method in full171 words

Method: non-formal (code reading and directed testing; no model checking, constraint solving or proof was involved).

  • The reading. While the format's failure paths were being prepared for testing, the two callbacks stood out: declared throws IOException, with no handler, and registered as upcall targets, for which the JDK documents that an exception ends the JVM.
  • The first run. A FilterDirectory that fails one write or read inside the library's callbacks, run with the real Faiss C library: the JVM exited on a refused write at flush and on a failed read at segment open.
  • A way in with no fault. A second probe reached the same exit with IndexWriter.rollback() during a merge on the default merge scheduler.
  • Why the usual tests do not see it. The test framework's random IOException fires only on the first write to a new file and on opens, never inside a callback.
  • Reduction. The failures were reduced to one test: one document, one refused write, one assertion on the exit code of a child JVM.
