CheckIndex's impacts-vs-postings advance check overflows int on its first step and compares no document for fields with an odd hashCode

CheckIndex's check that a term's impacts iterator advances to the same documents as its postings iterator overflows int on its first step (NO_MORE_DOCS - (-1)). For every field whose hashCode() is odd (id, text, content: about half of all names) it compares no document, so a broken ImpactsEnum.advance passes CheckIndex.

The finding in 30 seconds

#

CheckIndex's impacts-vs-postings check silently compares no document for about half of all field names, because its very first step overflows.

Background: impacts and the check

#
  1. For each term, a postings format gives two iterators over the same documents: a PostingsEnum, and an ImpactsEnum that also exposes per-block score bounds, so top-k queries can skip whole blocks.
  2. Both must agree: advance(target) returns the first document at or after target, or NO_MORE_DOCS (2,147,483,647) when there is none.
  3. CheckIndex verifies this under // Now check advancing: it walks both iterators with a mix of nextDoc() and advance(target) and throws on the first disagreement. The parity of field.hashCode() + doc picks each move.

The finding, step by step

#
  1. Index 200 documents with the term t in field text (default codec). Wrap the segment so that ImpactsEnum.advance(target) returns the document after the right one; plain postings stay correct.
  2. Run CheckIndex.testPostings. You expect "Impacts do not advance to the same document as postings for target 114, postings: 114, impacts: 115". That is what it reports with the fix, and stock main reports the same fault when the field is named body (target 159).
  3. You get no error. The check walks both iterators from doc -1. For text the first move is an advance whose step is min(115, NO_MORE_DOCS - (-1)), and NO_MORE_DOCS - (-1) overflows to -2,147,483,648.
  4. So the first target is -1 + (-2,147,483,648), which wraps to NO_MORE_DOCS. Both iterators return NO_MORE_DOCS, they agree, and the walk ends without comparing a document.
  5. Which fields: the first move is advance exactly when field.hashCode() is odd (id, text, content; not body, title). This holds whenever the walk runs (every term at level 3, sampled terms below it) and in every release since 8.0.0.

Who is affected

#

Anyone relying on CheckIndex to catch a postings format whose impacts disagree with its postings: checkIndex() and the command-line tool at level 2 or 3, testPostings, and the test framework. Which fields lose the check depends only on the name. No Lucene format is known to be affected; a broken custom format's advance goes unreported for those fields.

Mechanism, terms and numbers506 words

CheckIndex cross-checks each sampled term's ImpactsEnum against its PostingsEnum by walking both with a mix of nextDoc() and advance(target). The walk starts at doc -1, and for a field whose String.hashCode() is odd its first move is an advance whose step bound NO_MORE_DOCS - doc overflows int at doc -1. The first target becomes NO_MORE_DOCS, both iterators return it, and the walk ends without comparing a document. About half of all field names are affected (id, text, content), whenever the walk runs and in every release since 8.0.0. No Lucene postings format is known to write impacts that disagree with its postings, so no wrong search result is claimed; the gap only lets a broken custom or future postings format pass CheckIndex. The fix computes the bound in long; RandomPostingsTester has the same overflow-prone bound.

The walk

#
  • The impacts checks run on long postings lists (docFreq > 1024), on every 1024th term, or on every term at level 3 (CheckIndex.java:2090-2094). Level 3 first runs a nextDoc-only loop (:2108-2141); the advance walk (:2143-2233) runs whenever the impacts checks run and is the only code that calls ImpactsEnum.advance. Below level 3 it is also the only check of freqs against the impacts' max freq (:2226-2232).
  • int doc = impactsEnum.docID(); is -1 on a fresh enum (:2150). ((field.hashCode() + doc) & 1) == 1 picks nextDoc (:2153-2155); at doc -1 that is true for even hashes, so odd hashes take advance.

The overflow

#
  • The step is Math.min(1 + ((31 * field.hashCode() + doc) & 0x1ff), DocIdSetIterator.NO_MORE_DOCS - doc) (:2158-2161). At doc -1, NO_MORE_DOCS - doc is Integer.MAX_VALUE + 1, which wraps to Integer.MIN_VALUE; Math.min returns it.
  • target = impactsEnum.docID() + delta = -1 + (-2,147,483,648) wraps to 2,147,483,647 = NO_MORE_DOCS (:2162). For text (hashCode() 3,556,653) the intended step was 115, target 114.
  • The structural part still runs once: advanceShallow(NO_MORE_DOCS), getImpacts() and checkImpacts(impacts, -1) (:2165-2182). Then impactsEnum.advance(NO_MORE_DOCS) and postings.advance(NO_MORE_DOCS) both return NO_MORE_DOCS, the comparison passes (:2190), and the loop breaks (:2199-2201): no real document is compared. Later steps have doc >= 0, so the overflow happens only on the first.

Which names

#

String.hashCode() is odd exactly when the sum of the name's chars is odd. Measured with the repro's reader on stock main: text, id and content give no error; body and title are caught at targets 159 and 169. With the fix the odd names are caught at targets 114, 68 and 166.

Sibling

#

RandomPostingsTester.java:1297, behind BasePostingsFormatTestCase, has the same overflow-prone first-step bound with a random step instead of the hash, Math.min(1 + random.nextInt(512), DocIdSetIterator.NO_MORE_DOCS - doc), and picks each move with random.nextBoolean(): about half of its walks end the same way. It runs the walk for every term it verifies with skipping enabled (:1219-1370), so over a suite many walks still compare documents.

Exposure and likelihood263 words
  • Where it bites. checkIndex() runs testPostings only at level 2 or higher (CheckIndex.java:1114-1125). The command-line tool's default level 1 checks only checksums (:4673, :4837, :4854-4855), and a programmatic CheckIndex has level 0 until setLevel is called (:499-508). So the gap reaches checkIndex() and the command-line tool at level 2 (sampled terms) or 3 (every term), CheckIndex.testPostings(CodecReader, PrintStream) (level 3, :2680-2684), and TestUtil.checkIndex and checkReader (level 3, TestUtil.java:303, :353, :371).
  • What is lost. For odd-hash fields ImpactsEnum.advance is never compared with PostingsEnum.advance on a real document at any level; only the two NO_MORE_DOCS results are compared. Below level 3 the impacts freq-bound check is lost too: with testPostings at level 1 and a 2,000-document term, impacts that understate a frequency are reported for body and title but not for text, id or content (level 3 still catches freq errors through its nextDoc loop).
  • Scale. At level 3 one term is enough. Below level 3 the term must be sampled (docFreq > 1024 or every 1024th term, :2090-2094). No special configuration or data.
  • Not affected. Indexing and search. No Lucene postings format showed a disagreement with the walk fixed: TestCheckIndex, the 12 postings-format test classes run in core and codecs, and TestOrdsBlockTree pass (SimpleText's suite is nightly-only and was skipped). These are the closest suites, not a full codec matrix. A broken custom format is still likely to be caught by its own BasePostingsFormatTestCase run, since only the RandomPostingsTester walks whose random first move is an advance end early.

Why it looks unintended

#
  • The clamp Math.min(..., NO_MORE_DOCS - doc) exists to keep the target in range; it is the clamp that overflows at doc -1.
  • Sampling is per term (long postings, every 1024th term, all terms at level 3), never by field name; the gap exists at level 3 too.
  • A similar slip in another CheckIndex cross-check was fixed as a bug (#9125).
The full argument175 words
  • The clamp shows the intent. Math.min(..., NO_MORE_DOCS - doc) exists only to keep target at or below NO_MORE_DOCS (CheckIndex.java:2158-2161).
  • The check's only job is to throw "Impacts do not advance to the same document as postings" when the enums disagree (:2190-2198); for odd-hash fields it compares only the two NO_MORE_DOCS results, so it cannot report a wrong advance to a document.
  • Sampling is per term. LUCENE-8153 (#9201, 317a2e0c3d1) chose "long postings lists, on every 1024th term or if slow checks are enabled" (:2090-2091). The overflow also removes the document comparison at level 3, the level meant not to sample.
  • Nothing suggests a choice. The expression came verbatim with the walk in f410df81136 (LUCENE-4198, #5270); the inspected issue discussion (29 comments) and the messages of the later commits that touched the walk do not discuss this overflow.
  • Precedent. LUCENE-8077 (#9125): i % 1 == 0 made another CheckIndex cross-check always take one branch; fixed under Bug Fixes as "Fixed bug in how CheckIndex verifies doc-value iterators" (lucene/CHANGES.txt:7682).
The devil's-advocate check198 words

CheckIndex is @lucene.experimental (CheckIndex.java:110), and its javadoc does not promise that every inconsistency of a broken codec is caught; the walk is sampled on purpose; and the repro's miss needs an ImpactsEnum that already breaks DocIdSetIterator.advance's contract, planted through the expert, @lucene.internal CodecReader.getPostingsReader() (CodecReader.java:66-71). An independent reviewer from another model family (OpenAI GPT-5.6) rated the finding not real on these grounds, while agreeing on the mechanism and the fix; a later fact check from the same model family added that a broken custom format would likely be caught by its own BasePostingsFormatTestCase run anyway.

Why it fails: a validator exists to catch exactly an enum that breaks its contract, so "the input is already broken" is circular here; the class javadoc even says that the tool "checks every byte in the index" (CheckIndex.java:107-108). getPostingsReader() is only how the test plants the fault; a custom PostingsFormat loaded through the codec SPI reaches the same code. A format's own test suite does not check an index already written; CheckIndex does. Sampling does not explain a gap keyed on field-name parity at every level. Verdict: a real Low bug, a validator coverage gap.

Trade-offs

No effect on indexing or search. CheckIndex now does for odd-hash fields the walk it already does for even-hash fields, on the same sampled terms (every term at level 3), so its run time grows for those fields. A custom postings format that was wrong all along for an odd-hash field will now fail CheckIndex or its BasePostingsFormatTestCase run, which is the point.

Downstream note

#

Products and plugins that ship their own postings format and validate it with CheckIndex or Lucene's test framework get no impacts-advance document comparison for odd-hash fields until the fix lands.

How it was found

#

A proof-obligation audit of CheckIndex's contract: the impacts-vs-postings advance check must compare the two iterators whatever the field is called. Evaluating the walk's first step at doc -1 exposed the overflow, and a one-test JUnit repro witnessed it: the planted fault is missed for text and reported for body.

The method in full80 words

The obligation came from the walk's purpose (it exists to throw "Impacts do not advance to the same document as postings", CheckIndex.java:2190-2198) and the clamp that keeps its target in range (:2158-2161). Checking that clamp at the walk's start state, doc -1, for both parities of field.hashCode() showed the odd branch wrapping to NO_MORE_DOCS. The repro then planted a wrong ImpactsEnum.advance with a deliberately faulty reader wrapper and compared an odd-hash and an even-hash field name.
