IndexWriter indexes a custom term frequency of 0 unchecked and commits a segment CheckIndex rejects

If your own TermFrequencyAttribute class reports a frequency of 0, IndexWriter stores it unchecked: with assertions off, the commit succeeds and CheckIndex rejects the segment, or, if that is the term's only document, the commit fails and closes the writer. Every release since 7.0.0 has it.

The finding in 30 seconds

#

Background: custom term frequencies

#
  1. Normally a term's frequency in a document is how often it occurs there. Since 7.0.0 a TokenStream can set it directly with TermFrequencyAttribute, for example red|3 through DelimitedTermFrequencyTokenFilter, on a field indexed with DOCS_AND_FREQS.
  2. Lucene's own implementations of that attribute throw for values below 1. An application can register its own implementation with the Expert AttributeSource.addAttributeImpl or an AttributeFactory.

The finding, step by step

#
  1. You index custom term frequencies on a DOCS_AND_FREQS field through your own TermFrequencyAttribute class, plugged in with the Expert addAttributeImpl, that does not copy the stock "1 or greater" check. Doc 0 has foo with frequency 0, doc 1 has foo with frequency 2.
  2. You expect addDocument to reject doc 0 with an IllegalArgumentException and drop only that document, as IndexWriter does for a negative position increment or offsets going backwards.
  3. Instead the indexing chain checks the custom frequency only for overflow and stores the 0 as the posting's frequency. With assertions off, both addDocument calls and commit return normally.
  4. CheckIndex then reports term [66 6f 6f]: doc 0: freq 0 is out of bounds and 1 broken segment containing 2 documents.
  5. If foo occurs only in the frequency-0 document, the commit itself throws cannot write negative vLong (got: -1) and closes the writer; a valid document added after the bad one is lost too.

Who is affected

#

Only applications that index custom term frequencies through their own TermFrequencyAttribute class that skips the stock "1 or greater" check, and emit 0 (for example a weight that rounds down to 0). Stock analysis, including DelimitedTermFrequencyTokenFilter and FeatureField, rejects 0 loudly. Default config and codec otherwise; two one-token documents suffice.

Mechanism, terms and numbers541 words

A field indexed with DOCS_AND_FREQS can take each token's frequency from TermFrequencyAttribute instead of counting occurrences. Lucene's two stock implementations of that attribute reject values below 1, but the interface states no range, and an application can plug in its own implementation through the Expert AttributeSource.addAttributeImpl or an AttributeFactory. IndexingChain.invertTokenStream checks every token's position increment and offsets before adding it, but checks the custom frequency only for overflow (IndexingChain.java:2053-2064 at 5adff78bb168); FreqProxTermsWriterPerField then stores the value as the posting's frequency (:125, :177, :196); on a DOCS_AND_FREQS field the only positivity guard is an assert (:143). With assertions off, a frequency of 0 is committed silently and CheckIndex rejects the segment (freq 0 is out of bounds). When a term's total frequency ends below its document count, the commit instead throws cannot write negative vLong (got: -1), which closes the writer and loses the uncommitted documents. Every release from 7.0.0 to 10.6.0 has it; stock analysis cannot trigger it.

The mechanism (main 5adff78bb168, under lucene/core/src/java/org/apache/lucene/)

#
  1. Only the stock setters check the range. TermFrequencyAttribute (analysis/tokenattributes/TermFrequencyAttribute.java:23-35) states no range. TermFrequencyAttributeImpl.setTermFrequency (:30-36) and PackedTokenAttributeImpl.setTermFrequency (:157-164) throw "Term frequency must be 1 or greater". A custom class plugged in with addAttributeImpl ("Expert", util/AttributeSource.java:176-188) bypasses both; it has to be registered before the default packed implementation claims the interface, as the repro does.
  2. The indexing chain checks the other token values, not this one. IndexingChain.invertTokenStream rejects a bad position increment or position overflow (index/IndexingChain.java:1996-2033) and bad offsets (:2035-2051) with non-aborting IllegalArgumentExceptions before the add. The custom frequency is only added to the field length with Math.addExact, "too many tokens" on overflow (:2053-2064): an upper bound, no lower bound. This is the fix site.
  3. It is stored as is. termsHashPerField.add (:2075, inside the aborting catch (Throwable) at :2098-2100) reaches FreqProxTermsWriterPerField.newTerm / addTerm, which store getTermFreq() as the posting's frequency (index/FreqProxTermsWriterPerField.java:125, :177, :196). getTermFreq() (:208-219) returns termFreqAtt.getTermFrequency() and rejects only freq != 1 when positions are indexed.
  4. On a DOCS_AND_FREQS field the only positivity guard is an assert. assert !hasFreq || postings.termFreqs[termID] > 0 (:143) runs only with -ea, and on the term's next occurrence, not on the document that carries the 0. Other index options do have checks, inside the add: with positions, getTermFreq() rejects any value other than 1 (:208-219); on a DOCS-only field addTerm rejects a custom frequency other than 1 (:147-152).
  5. What the flush writes. The postings get freq 0 (term foo: docFreq 2, totalTermFreq 2, doc 0 freq 0, doc 1 freq 2) and CheckIndex treats freq <= 0 as corruption (index/CheckIndex.java:1735-1739). When a term's total frequency ends below its document count (one document with frequency 0: totalTermFreq 0, docFreq 1), the terms dictionary writes ttf - df as a vLong (codecs/lucene103/blocktree/Lucene103BlockTreeTermsWriter.java:528), which throws at store/DataOutput.java:238 during the commit; the exception is tragic and closes the writer.

With assertions on, an internal assert fires instead: FreqProxTermsWriterPerField.addTerm:143 when the frequency-0 document comes first, Lucene104PostingsWriter.startDoc:290 during flush when it comes second (the devil's-advocate verifier's test).

Exposure and likelihood166 words
  • Who. Code that writes its own TermFrequencyAttribute implementation (an Expert hook) without the stock range check, on a field indexed with frequencies. No public example was found: a GitHub code search for implements TermFrequencyAttribute (top 30 hits) found only copies of Lucene's own class, so the likelihood is rated contrived.
  • Not hit. The two stock attributes throw for values below 1; DelimitedTermFrequencyTokenFilter calls the stock setter, so foo|0 is rejected; FeatureField rejects values below Float.MIN_NORMAL.
  • Effect. Silent in production mode (assertions off): the bad value is committed and only CheckIndex notices. In the single-document case the commit fails and closes the writer: in the probe, after one committed document, a frequency-0 document and a valid one were added; the commit threw, the writer closed, and the index kept only the first document. How search and merge behave on a segment with freq 0 was not run.
  • Default vs opt-in. Custom term frequencies are opt-in; nothing else is configured.
  • Scale. Two one-token documents; deterministic, single thread.

Why it looks unintended

#
  • Nothing documents 0 as valid: both stock implementations throw "Term frequency must be 1 or greater", and CheckIndex calls a 0 out of bounds.
  • IndexWriter already re-checks a negative position increment, which also only a custom attribute can produce, and this frequency's upper bound.
  • The >= 1 check went only into the setters when the feature was added (LUCENE-7854).
The full argument193 words
  • Contract. TermFrequencyAttribute states no range; both stock implementations reject values below 1 (TermFrequencyAttributeImpl.java:30-36, PackedTokenAttributeImpl.java:157-164); FreqProxTermsWriterPerField asserts termFreqs > 0 (:143); CheckIndex reports freq <= 0 as out of bounds (CheckIndex.java:1735-1739). Michael McCandless on dev@ (2020-11-06, "Payloads for each term"): "term frequency 0 is not allowed".
  • IndexWriter guards the index against bad token values. PositionIncrementAttributeImpl (:32-35) and PackedTokenAttributeImpl (:57-62) reject a negative increment, and IndexingChain still checks "position increment must be >= 0" (:2002-2008). Precedents: LUCENE-3874 (#4947, "don't let bogus positions corrumpt [sic] the index"), LUCENE-4127 ("don't let bogus offsets corrupt the index"), LUCENE-5977 (#7039, token stream safety checks in IndexWriter). The custom frequency's upper bound is checked too (6c3ece2b9f9, 2017).
  • Tests. TestCustomTermFreq (15 tests) covers positions, DOCS-only fields, overflow and term vectors, but not a value below 1, because its streams use the stock attribute.
  • History. LUCENE-7854 (d276acfbbcb, 2017) put the >= 1 check only into the setters; none of the 34 comments on #8905 discusses values below 1. The assert at :143 dates from 2012, when a frequency could only be counted up from 1.
The devil's-advocate check131 words

The strongest case for "not a bug": the attribute is an Expert hook, an implementation that accepts 0 is broken, and Robert Muir wrote on #11086 (2021): "If you use custom term frequencies (expert feature), then it is your responsibility to have reasonable values. Otherwise, things can easily overflow, break scoring, cause failures from checkindex."

Why it fails: the interface documents no range; IndexWriter already re-checks the negative position increment, which only the same kind of custom code can produce; and in the same thread (2021-08-13) they wrote "It isn't viable to have an option that says 'allow me to corrupt my index'". The fix is one comparison on a value the chain already reads, and it rejects only the bad document. The argument does bear on likelihood, hence priority Low.

Suggested fix

#

Recommended Reject a frequency below 1 in IndexingChain before the add (fix A)

Check the lower bound in IndexingChain.invertTokenStream next to the position and offset checks, before the aborting add: throw a non-aborting IllegalArgumentException("term frequency must be 1 or greater (got 0) for field 'f'") (+10 lines). Only the bad document is rejected. The repro passes with assertions on and off; 105 tests of the 11 closest suites pass.

Reject a frequency below 1 in IndexingChain before the add (fix A) (validated by the checks) (recommended)

#

Right after the offsets check in IndexingChain.invertTokenStream (IndexingChain.java:2051), read the custom frequency and throw an IllegalArgumentException when it is below 1. Like the position and offset checks above it, this runs before termsHashPerField.add, so it is non-aborting: the document is marked deleted, as for any analysis error, and the writer stays open. The message mirrors the stock setters.

          final int termFreq = invertState.termFreqAttribute.getTermFrequency();
          if (termFreq < 1) {
            throw new IllegalArgumentException(

                    + termFreq
                    + ") for field '"
                    + field.name()
                    + "'");
          }

Trade-offs

One more comparison per token on the indexing hot path (Lucene's SECURITY.md asks that robustness changes not slow hot paths). The value is read again a few lines below (IndexingChain.java:2059, on the branch for fields other than DOCS_AND_CUSTOM_FREQS, which adds it to the field length), so a final version can reuse the local there (not run). No benchmark was run. Scope: as written the check runs before the index-option branches, so it applies to every inverted field, not only DOCS_AND_FREQS. On DOCS-only and position-indexed fields the existing checks inside the aborting add (FreqProxTermsWriterPerField.java:147-152, :208-219) reject a frequency other than 1; the fix would reject a 0 before them, non-aborting. On DOCS_AND_CUSTOM_FREQS (10.5.0) custom frequencies are opaque scores (IndexOptions.java:52-55, FieldInfo.java:717-723), so decide whether 0 is a valid score there before rejecting it. With the fix only DOCS_AND_FREQS was run with a 0, and no repro covers a negative value, so this finding is about 0.

Downstream note

#

Downstream, a product that accepts raw per-token frequencies from users through its own non-checking attribute would let a frequency of 0 break a segment or close the writer; Lucene's stock analysis rejects such input.

How it was found

#

A proof-obligation audit of FreqProxTermsWriterPerField's contract: every posting frequency it stores must be at least 1 (its own assert, and CheckIndex). Tracing where the value comes from showed that only the stock attribute setters enforce it; a one-test public-API JUnit then witnessed a frequency of 0 in a committed segment.

The method in full131 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read FreqProxTermsWriterPerField's obligation that a stored frequency is above 0 (:143, and CheckIndex at CheckIndex.java:1735-1739) and traced each place the value is set (:125, :177, :196) back to TermFrequencyAttribute.getTermFrequency(). The indexing chain discharges the obligation for positions and offsets with explicit checks, but for the frequency it relies on the stock setters, which an application's own implementation does not run.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off, and on 10.6.0 and 9.12.3.
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

History

#

Present since custom term frequencies were added (d276acfbbcb, LUCENE-7854, Mike McCandless, 2017-06-06; first release 7.0.0). Every release run, 7.0.0 to 10.6.0, and main fail; 6.6.x lacks the API. Not a regression and not fixed upstream.

Versions tested6 rows

Introduced by d276acfbbcb "LUCENE-7854: enable indexing custom term frequencies" (Mike McCandless, 2017-06-06; JIRA patch, issue #8905, no PR). It added TermFrequencyAttribute, put the >= 1 check only into the two stock setters, and made FreqProxTermsWriterPerField store whatever getTermFrequency() returns. Before it every occurrence counted 1, so a frequency of 0 could not occur. First release 7.0.0 (2017-09-20).

Later changes near the fix site kept the gap: 6c3ece2b9f9 ("too many tokens", 7.0.0), #12139 (null guard, 9.6.0) and #15584 (DOCS_AND_CUSTOM_FREQS, 10.5.0, which uses the same getTermFreq() path; not run). Not fixed upstream: upstream main 1c2072f02843 (2026-11-02) has no commit since 2026-10-25 on FreqProxTermsWriterPerField.java or TermFrequencyAttribute.java, and on IndexingChain.java only #16734 (columnar vectors). Releases before 9.1.0 ran a main() with the same two documents and CheckIndex, because they lack today's test framework.

LFV-1135, snapshot of 2026-11-05

Registry title
IndexWriter accepts a custom term frequency of 0 without any check: the frequency goes into the postings and the committed segment fails CheckIndex ('freq 0 is out of bounds'), or the commit throws and closes the writer
Area
index / IndexingChain inversion with custom term frequencies (TermFrequencyAttribute, FreqProxTermsWriterPerField)
Priority
Low, rank 677: A custom term frequency of 0 is indexed without a check, so the committed segment fails CheckIndex or the commit throws and closes the writer, in every release since 7.0.0. It needs the opt-in custom-frequency feature with an application-written attribute that skips the stock check, since every stock producer rejects 0, so it is contrived.
Impact class
minor
Impact note
Hits only applications that index custom term frequencies (an opt-in feature) through their own TermFrequencyAttribute implementation, plugged in with the Expert AttributeSource.addAttributeImpl or an AttributeFactory, that skips the stock '1 or greater' check and reports 0 on a field indexed with frequencies; otherwise default IndexWriterConfig and codec at ordinary scale: with -da nothing fails at index time and the committed segment fails CheckIndex, or, when a term's total frequency ends below its document count, the commit throws and closes the writer so uncommitted documents are lost; with -ea an internal assert fires instead; stock analysis (the stock attributes, DelimitedTermFrequencyTokenFilter, FeatureField) cannot reach it; every release from 7.0.0 to 10.6.0 and main. Minor rather than data corruption: the effect is a committed segment that CheckIndex rejects, but it is reachable only through an application-written TermFrequencyAttribute implementation that skips the stock '1 or greater' check, and a maintainer has called sane custom-frequency values the user's responsibility (#11086), so it is a Low missing-input-check bug.
Summary
You index a document through a TokenStream whose TermFrequencyAttribute is your own implementation (plugged in with AttributeSource.addAttributeImpl or an AttributeFactory) and that reports a frequency of 0 for a token, on a field indexed with DOCS_AND_FREQS. You expect IndexWriter to reject that document with an IllegalArgumentException, as it does for a negative position increment, backwards offsets or too many tokens, or at least never to write an index that its own CheckIndex calls broken. Instead the 0 goes into the postings unchecked: with assertions off addDocument and commit succeed and CheckIndex then reports 'term [66 6f 6f]: doc 0: freq 0 is out of bounds' and 1 broken segment, and if the term's only document has frequency 0, the commit instead throws 'cannot write negative vLong (got: -1)', which closes the writer and loses every uncommitted document.
