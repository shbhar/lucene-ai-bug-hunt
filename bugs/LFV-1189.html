A repeated non-UTF-8 binary term in a DOCS_AND_CUSTOM_FREQS field can close IndexWriter instead of skipping the document

A DOCS_AND_CUSTOM_FREQS document that repeats a term should be skipped while the writer stays open. If the repeated term is binary and not valid UTF-8, such as the lone byte 0xC3, building the error message can throw and close IndexWriter, losing all uncommitted documents (10.5.0 to 10.6.0, main).

The finding in 30 seconds

#

The repeat is caught as intended; what fails is the error message, which decodes the term as UTF-8.

Background: term-doc fields and how IndexWriter fails a document

#
  1. DOCS_AND_CUSTOM_FREQS (new in 10.5.0) indexes a custom score per term instead of a count, so each term may occur only once per document.
  2. IndexWriter fails a bad document in one of two ways. A non-aborting rejection throws IllegalArgumentException and skips just that document. An aborting failure closes the writer and rolls back to the last commit, because its in-memory state may be damaged.

The finding, step by step

#
  1. You index raw binary terms into a field with IndexOptions.DOCS_AND_CUSTOM_FREQS, which allows each term once per document. You commit 1 document, add a 2nd, then add a 3rd that holds the one-byte term {0xC3} twice.
  2. You expect what happens when foo is repeated: IllegalArgumentException: Document update skipped due to duplicate termdoc term, the writer stays open, and after the next commit the index holds 2 documents.
  3. Lucene does catch the repeat, but to put the term into the error message it decodes the bytes as UTF-8 (utf8ToString). 0xC3 starts a 2-byte character and there is no 2nd byte, so the decoder reads past the 1-byte array: ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1.
  4. That exception is not one the indexing chain treats as a per-document rejection, so IndexWriter closes itself: isOpen() is false, and the index holds 1 document. The 2nd document, never committed, is lost.

Who is affected

#

Applications on 10.5.0 to 10.6.0 that opt into DOCS_AND_CUSTOM_FREQS for raw binary terms and pass a document that repeats one ending in a truncated UTF-8 sequence. One such document closes the writer and rolls back all uncommitted documents. Terms built from characters, as ordinary analyzers emit them, are valid UTF-8 and are rejected correctly.

Mechanism, terms and numbers637 words

IndexOptions.DOCS_AND_CUSTOM_FREQS (new in 10.5.0, #15584) stores a custom score per term and allows each term only once per document. When a document repeats a term, #15584 made addDocument reject just that document with the non-aborting IllegalArgumentException("Document update skipped due to duplicate termdoc term"); TestCustomTermFreq.testRepeatedTerms asserts the writer stays open. On the way, TermsHashPerField.add re-throws the internal DuplicateTermException with the term appended through termBytes.utf8ToString() (TermsHashPerField.java:203 at 5adff78bb168). For some binary terms that are not valid UTF-8, such as a BytesRef that holds just the byte 0xC3, that decode throws ArrayIndexOutOfBoundsException. The indexing chain treats DuplicateTermException (like a too-long term) as a per-document rejection and every other exception as aborting, so the writer records the AIOOBE as its tragic exception and closes, and every document added since the last commit is lost. A one-line fix renders the term with Lucene's existing Term.toString(BytesRef), which prints non-UTF-8 terms as bytes.

The mechanism (main 5adff78bb168, under lucene/core/src/java/org/apache/lucene/)

#
  1. The rejection starts as intended. For a term-doc field, a term already seen in this document throws DuplicateTermException("field 'f' has duplicate term") (index/FreqProxTermsWriterPerField.java:193-195).
  2. The message decoration decodes the term. TermsHashPerField.add catches it and re-throws new DuplicateTermException(e.getMessage() + " '" + termBytes.utf8ToString() + "'") (index/TermsHashPerField.java:200-204, the call at :203). This is the fix site.
  3. utf8ToString is documented to throw on bad input: "May throw an AssertionError or a RuntimeException if the data is not well-formed UTF-8" (util/BytesRef.java:133-136). For {C3}, a 2-byte lead byte that ends its array, UnicodeUtil.UTF8toUTF16 reads past the end of the 1-byte array (util/UnicodeUtil.java:649).
  4. The indexing chain classifies by exception type. Around termsHashPerField.add (index/IndexingChain.java:2075): MaxBytesLengthExceededException becomes a non-aborting IAE that prints the term's bytes with Arrays.toString (:2076-2094); DuplicateTermException becomes the non-aborting IAE (:2095-2097); every other Throwable goes to onAbortingException (:2098-2100, :176-180). That marks the per-thread writer aborted (index/DocumentsWriterPerThread.java:56-60); its maybeAbort drops the buffered documents and reports a tragic event (:594-605), which IndexWriter records (index/IndexWriter.java:6067-6083); the catch in IndexWriter.updateDocuments then calls maybeCloseOnTragicEvent (:1632-1640), which rolls the writer back and closes it (:6097-6104).
  5. Reach. Field(String, BytesRef, IndexableFieldType) builds an untokenized binary field (document/Field.java:187-226) that is inverted as a token stream (Field.java:460-461), so it takes this path. A custom TokenStream with binary terms reaches it too (the devil's-advocate verifier's probe).

Scope

#
  • Only some non-UTF-8 terms trigger it. With assertions off, the decode throws only when it runs off an array: a truncated multi-byte sequence at the end of the term's backing array, such as [c3] or [41 e2 82]. The decoder reads past BytesRef.length, so the backing array is what counts: a [c3] slice followed by another byte only garbles the message, while a slice that ends in a 4-byte lead byte ([f0] of [f0 90 80 80]) overruns the decoder's output array and closes the writer too.
  • A lone continuation byte such as [80 41] gives a garbled message ('\u0080A': an invisible U+0080, then A) and the writer stays open; with assertions on, that one closes the writer too, through an AssertionError.
  • An ASCII term (foo, [41 42]) or a valid UTF-8 term ([c3 a9], "é") repeated the same way gets the intended rejection, and the writer stays open.
  • Committed data is not affected.
  • Not run: the BINARY invert path (IndexingChain.invertTerm, :2127-2170). StringField and KeywordField fix their index options to DOCS, but a custom IndexableField that returns InvertableType.BINARY, or an untokenized column of the columnar API (10.6.0), can use this option. By reading, invertTerm has neither the duplicate-term catch nor the aborting catch, so there the caller would get the raw exception instead of the IAE.
Exposure and likelihood175 words
  • Who. Code that indexes raw binary terms into a DOCS_AND_CUSTOM_FREQS field (no Lucene field class uses the option) and lets a document repeat one of them, which the option forbids. Only some byte patterns trigger it (see Scope above).
  • Default vs opt-in. An opt-in index option; default IndexWriterConfig and codec otherwise.
  • Effect. Loud, not silent: addDocument throws, the writer closes, later calls throw AlreadyClosedException until a new writer is opened, and all documents added since the last commit are lost. No corruption was observed: the writer rolls back to the last commit, and committed data stays intact.
  • Scale. One document, a one-byte term; fixed input, single thread.
  • Likelihood. Rare: it needs the new option, raw binary terms, a repeated term (a user error) and a byte pattern that makes the decoder run past the end.
  • Text vs bytes. CharTermAttribute terms are encoded to valid UTF-8 (unpaired surrogates become U+FFFD), so they get the intended rejection; a token stream that emits raw bytes (BytesTermAttribute, "if binary terms should be indexed") can reach the bug.

Why it looks unintended

#
  • #15584 made this rejection non-aborting on purpose: its handling "merely skips the doc being indexed (same as for a too-large term)".
  • TestCustomTermFreq.testRepeatedTerms asserts that after a repeated term the writer stays open and only that document is skipped.
  • The decode only builds a message: utf8ToString is documented to throw on non-UTF-8 bytes, and Term.toString exists to print such terms safely.
The full argument140 words
  • Intent of the feature's author. #15584's author, Michael Sokolov, on 2026-03-23 (https://github.com/apache/lucene/pull/15584#issuecomment-4110154752): "found that the exception I raised for duplicate terms in termdoc fields would cause the writer to crash, so added some exception handling that merely skips the doc being indexed (same as for a too-large term)".
  • Test. TestCustomTermFreq.testRepeatedTerms (lucene/core/src/test/org/apache/lucene/index/TestCustomTermFreq.java:106-135) expects the IAE, the cause message "field 'field' has duplicate term 'foo'", then: "ensure IndexWriter remains open and doc was skipped".
  • Binary terms are legal on this option. The same {C3} term once per document is indexed fine; IndexOptions.java:52-56 requires each term once per document, not UTF-8 terms.
  • A safe helper exists. Term.toString(BytesRef): "If the term is not unicode, the raw bytes will be printed instead" (index/Term.java:104-122). The too-long-term handler in the same try prints raw bytes and never decodes (IndexingChain.java:2076-2094).
The devil's-advocate check141 words

The case for intended: repeating a term breaks the option's rule ("Each term can only occur once per document", IndexOptions.java:52-56), so any exception is acceptable. Also raised: the @throws line of Field(String, BytesRef, IndexableFieldType) says it throws if the type "is indexed()" (Field.java:196-197), and IndexOptions is @lucene.experimental (IndexOptions.java:24).

Why it fails: the rule justifies rejecting the document, which Lucene already does without closing the writer for every valid UTF-8 term; nothing documents closing the writer for some byte patterns only. The @throws line is stale: the constructor does not throw for an indexed untokenized type, and the bug reproduces without that constructor through a TokenStream. @lucene.experimental means the API may change, not that misuse may close the writer. Two executed cross-model reviews and a devil's-advocate verifier built this case and all rated the bug real.

Downstream note

#

A product that lets its users supply raw binary terms for such a field could have one malformed, repeated term close its writer; text through an ordinary analyzer becomes valid UTF-8 and cannot trigger it.

How it was found

#

A proof-obligation audit of TermsHashPerField.add's contract: a repeated term in a term-doc field must always end in the non-aborting duplicate-term rejection, for every term byte sequence. The message decoration was the one step that can throw for some bytes; a one-test public-API JUnit then witnessed the writer closing.

The method in full124 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder stated the obligation for TermsHashPerField.add: when positionStreamSlice raises DuplicateTermException, add must raise a DuplicateTermException too, whatever the term's bytes, because IndexingChain keeps the writer open only for that type. Discharging it step by step left one step that can throw: termBytes.utf8ToString(), documented to throw on malformed UTF-8.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off, and on 10.6.0 and 10.5.0, plus a control probe (ASCII repeat, binary term once, binary term twice).
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

Registry title
A term repeated in one document of a DOCS_AND_CUSTOM_FREQS field closes IndexWriter, instead of skipping the document, when the term is a non-UTF-8 binary term such as the single byte 0xC3: the duplicate-term rejection builds its message with utf8ToString, which throws (since 10.5.0)
Area
index / IndexingChain inversion, term-doc (DOCS_AND_CUSTOM_FREQS) duplicate-term rejection (TermsHashPerField.add) x aborting-exception classification
Priority
Low, rank 691: In an opt-in DOCS_AND_CUSTOM_FREQS field, a document that repeats a binary term whose bytes are not valid UTF-8 (such as the single byte 0xC3) closes the IndexWriter and loses uncommitted documents, where it should skip only that document, in releases 10.5.0 through 10.6.0. It needs the new opt-in index option, raw binary terms and a repeated term (a user error the option forbids), not every malformed term triggers it, and committed data stays intact.
Impact class
crash
Impact note
Applications on 10.5.0 through 10.6.0 and main that opt into IndexOptions.DOCS_AND_CUSTOM_FREQS (new in 10.5.0; no core field type uses it) for binary terms and pass a document that repeats a term whose bytes make the UTF-8 decoder run past the end of the term's backing array (for example the single byte 0xC3, or a term ending in a truncated multi-byte lead byte): the repeat, which Lucene is designed to reject by skipping only that document, instead closes the IndexWriter as a tragic event, so the uncommitted buffered documents are lost (executed: committed numDocs 1, the buffered document gone) and later calls throw AlreadyClosedException until a new writer is opened; default IndexWriterConfig, -ea and -da, ordinary scale; with -da other malformed bytes only garble the message and the writer stays open, with -ea more of them close the writer through an AssertionError; committed data is unaffected.
Summary
You index binary terms into a field with IndexOptions.DOCS_AND_CUSTOM_FREQS, which allows each term only once per document, and one document repeats a term that is not valid UTF-8, for example new BytesRef(new byte[] {(byte) 0xC3}) added twice as an untokenized Field. You expect addDocument to reject only that document with the non-aborting IllegalArgumentException 'Document update skipped due to duplicate termdoc term' and the writer to stay open, as happens for an ASCII or valid UTF-8 term and as the upstream test TestCustomTermFreq.testRepeatedTerms asserts.
