The default block tree never sets Stats.indexNumBytes, so CheckIndex prints "index trie: 0 bytes" for every field

Since 10.3.0 the default terms dictionary never fills in Stats.indexNumBytes ("Byte size of the index"), so Terms.getStats() and CheckIndex -verbose report index trie: 0 bytes for every field, even one whose trie takes 1,197 bytes on disk. Only this diagnostic number is wrong; search, indexing and CheckIndex verdicts are unaffected.

The finding in 30 seconds

#

SegmentTermsEnum.computeBlockStats() builds the Stats object by walking the terms dictionary but never sets indexNumBytes, so it stays 0. The size is at hand: FieldReader reads the trie's byte range in .tip (indexStart, indexEnd) and opens exactly that slice. The older Lucene90 copy of the method still has the assignment; #14333 dropped it.

Background: the terms index and its statistics

#
  1. Each field's terms dictionary, the block tree, lives mainly in two files: .tim holds the terms in blocks, and .tip holds a small index that leads a lookup to the right block. Since 10.3 that index is a trie; before, it was an FST.
  2. Terms.getStats(), an expert debugging call, walks the whole dictionary and returns a Stats object with counters such as terms, blocks and suffix bytes. CheckIndex -level 2 -verbose prints it for every field.
  3. Its first lines are index trie: and N bytes: the field Stats.indexNumBytes, documented as "Byte size of the index".

The finding, step by step

#
  1. Index one document with StringField("f", "a") under the default codec. The field's terms index, a trie in the .tip file, takes 10 of that file's 82 bytes; for 10,000 unique ids it takes 1,197 bytes.
  2. Ask for the field's block-tree statistics: Terms.getStats(), or CheckIndex -level 2 -verbose, which prints them per field. You expect indexNumBytes, documented as "Byte size of the index" and printed as index trie: N bytes, to show those sizes.
  3. You get indexNumBytes = 0 and index trie: 0 bytes, for every field that has terms, in every index written with the default codec since 10.3.0, with assertions on or off. CheckIndex still reports the index clean.
  4. Why: when #14333 replaced the FST terms index with a trie, its copy of computeBlockStats() lost the one line that set this field. Nothing else writes it, so it keeps Java's default 0, although FieldReader knows the trie's byte range.
  5. Not a regression of a working number: since 8.6.0 the older block tree printed a fixed heap-accounting constant (56 bytes on 9.12.3 to 10.2.2 in these runs; JVM-dependent shallow object sizes) whatever the field's size. Nothing in Lucene reads the value back.

Who is affected

#

Anyone who reads block-tree statistics of an index written by 10.3.0 or later with the default codec: CheckIndex -verbose at -level 2 or 3 (the default level 1 skips them), or code calling Terms.getStats(). Every field with terms shows 0; no special input is needed. Nothing in Lucene reads the value, so search, indexing, merges and CheckIndex verdicts are unaffected.

Mechanism, terms and numbers511 words

The default terms dictionary since 10.3.0, the Lucene103 block tree, never assigns Stats.indexNumBytes, documented as "Byte size of the index". SegmentTermsEnum.computeBlockStats() creates the Stats object and walks the whole terms dictionary to fill the other counters, but never sets this one, so it keeps Java's default 0. Terms.getStats() therefore reports 0, and CheckIndex -verbose at level 2 or 3 prints index trie: / 0 bytes for every field that has terms, for example for a field of 10,000 ids whose trie takes 1,197 bytes of a 1,269-byte .tip file. FieldReader already holds the trie's byte range (indexStart, indexEnd). The line that set the field was dropped when #14333 copied the Lucene90 block tree to create the Lucene103 one. Nothing else reads the value, so this is a small diagnostic defect; and since 8.6.0 the older block tree printed a size-independent constant there, so it is not a regression of a working number.

  • Contract: Stats.java:34-35, /** Byte size of the index. */ public long indexNumBytes;, printed by Stats.toString under index trie: as N bytes (Stats.java:184-185). Stats is @lucene.internal (Stats.java:31).
  • Nobody writes it: in lucene/core, lucene/backward-codecs, lucene/codecs and lucene/test-framework sources the only write is in the old Lucene90 copy, backward_codecs/lucene90/blocktree/SegmentTermsEnum.java:124-127: if (fr.index != null) { stats.indexNumBytes = fr.index.ramBytesUsed(); }.
  • The size is known: FieldReader reads indexStart, rootFP and indexEnd from the terms metadata (FieldReader.java:80-82) and opens the trie as a slice of indexEnd - indexStart bytes of .tip (:86-87). TrieBuilder.save writes the nodes and 8 padding bytes ("additional 8 bytes for over-reading") to .tip, and records indexStart, rootFP and indexEnd in the terms metadata file (TrieBuilder.java:263-268), so one term gives a 10-byte range.
  • Why the line went missing (a reading of the mechanics, not a stated intent): the Lucene103 FieldReader has no index object to call ramBytesUsed() on; it builds a TrieReader on demand.
  • Where it shows: FieldReader.getStats() ("For debugging -- used by CheckIndex too", FieldReader.java:110-114). CheckIndex stores each field's Stats (CheckIndex.java:2254-2259) and prints them only with verbose output (:2488-2493). It collects them in testPostings, which runs only at level >= MIN_LEVEL_FOR_INTEGRITY_CHECKS = 2 (:1114, :1125, :4754); the command-line default is level 1 (:4748).

Exposure and likelihood194 words
  • Default: the default codec, an ordinary IndexWriter; the smallest case is one document with one term.
  • Effect: one wrong number in debugging output. No wrong results, no index damage, no exception. CheckIndex's checks next to it recompute sumDocFreq and sumTotalTermFreq themselves (CheckIndex.java:2261-2281) and never read the Stats fields. Nor does the 0 hide a resident heap structure: FieldReader keeps only the trie's offsets (FieldReader.java:44-46) and builds a TrieReader over an IndexInput slice of .tip on demand (:86-87); a terms enum allocates only small temporary Node objects while it walks (TrieReader.java:78-82, SegmentTermsEnum.java:58, :177-186). Where the .tip bytes live is up to the Directory (the repro's ByteBuffersDirectory keeps them on the heap).
  • Scale: independent of the index: 0 for a 2-term field and for a 200,000-term field alike.
  • People read this line: 2015-16 JIRA issues (now GitHub #8476 and #7254) paste CheckIndex output with real index FST: N bytes values.
  • Likelihood: every such diagnostic run on a 10.3+ index shows the 0, but these are occasional debugging actions, nothing acts on the number, and nobody has reported it in the roughly 14 months since 10.3.0.

Why it looks unintended

#
  • The javadoc says "Byte size of the index", and the output prints it as index trie: N bytes.
  • The 4.0 block tree set it from the index's size; #14333 copied the code but dropped the assignment.
  • In #13330 (2024) a reviewer caught the same removal in the older block tree, and the author put the assignment back before merge.
The full argument249 words
  • Contract: "Byte size of the index" (Stats.java:34) and the label index trie: N bytes (:184-185). The neighbouring counters are on-disk sizes: totalBlockSuffixBytes "Total number of bytes used to store term suffixes" (:73-74), totalBlockStatsBytes (:86-89), totalBlockOtherBytes (:92-95).
  • History of the field: the first block tree (LUCENE-3030, 4.0.0-alpha) set it with stats.indexNumBytes = index.sizeInBytes(), and the block trees up to 10.2 kept an assignment (a probe reads non-zero values on 7.7.3 to 10.2.2). #14333 created the Lucene103 copy without it.
  • What it means: in a 2013 java-user thread ("Understanding FST Prefix & CheckIndex output") a user asked whether "index FST bytes" is the field's part of the .tip file, and Michael McCandless answered "Yes."
  • Precedent: in #13330 (2024) an earlier revision of the PR removed the same assignment from the then-core Lucene90 block tree; benwtrent asked in review whether that was wanted, and the PR's author, jpountz, put it back before merge, calling the removal "a leftover from a previous change". When LUCENE-6617 (2015) made the FST node and arc counts unavailable, the matching Stats fields were removed rather than left at 0.
  • No sign of intent: no CHANGES or MIGRATE entry, test or code comment says 0 is intended, and no description, review or comment of #14333 or #14563 mentions Stats, indexNumBytes or getStats. The two upstream tests that read this Stats class, testFinalBlock in TestLucene104PostingsFormat and its copy in backward-codecs TestLucene103PostingsFormat, check block counts only.
The devil's-advocate check144 words

The strongest case for "intended": the Lucene90 value was FST.ramBytesUsed(), a heap figure, and the Lucene103 field reader keeps no resident trie on the heap (only its offsets; a terms enum allocates temporary nodes), so 0 could mean "no resident heap"; Stats is @lucene.internal and getStats() a debugging API; and the old number had been a meaningless constant for years. The cross-model reviews (OpenAI GPT-5.6) rated this intended-behaviour argument "moderate", and both still judged the bug real with high confidence.

Why it fails: the javadoc says "Byte size of the index", not heap; the 4.0 original measured the index size; the sibling counters are on-disk bytes; and a field that nobody assigns is not a measurement under any reading. The internal/debug status lowers the severity, not the correctness. The constant-before-10.3 point is real, so this is not a regression of a working number.

Suggested fix

#

Recommended A. Set the field from the trie's byte range

In computeBlockStats(), add stats.indexNumBytes = fr.indexEnd - fr.indexStart;, the field's byte range in .tip (it includes 8 padding bytes). Validated with gradle: the test fails before and passes after, assertions on and off, and 212 codec, CheckIndex and terms tests run with 0 failures (8 skipped). Upstream may prefer excluding the padding or removing the field.

A. Set the field from the trie's byte range (validated by the checks) (recommended)

#

One reasonable reading of "Byte size of the index": the field's part of the .tip file, exactly the slice FieldReader opens (FieldReader.java:86-87), from metadata the reader already holds.

// SegmentTermsEnum.java:88-90
   public Stats computeBlockStats() throws IOException {
     Stats stats = new Stats(fr.parent.segment, fr.fieldInfo.name);
+    stats.indexNumBytes = fr.indexEnd - fr.indexStart;

Trade-offs

  • Includes the 8 padding bytes TrieBuilder.save writes (TrieBuilder.java:266), so one term reports 10 bytes.
  • The added line is O(1), though getStats() itself still walks the whole terms dictionary; debugging output only, no hot path changes.
  • It turns the old heap-accounting figure into an on-disk extent. It fits the javadoc and the 2013 java-user answer, but maintainers may prefer B, a relabelled heading, or C.
  • Lucene103-format segments only: Lucene90-format segments read through backward-codecs keep their old ramBytesUsed() figure (see the aside).

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20, OpenJDK 25.0.3, seed DEADBEEF: the minimal test fails before the change and passes after it, with assertions on and off.
  • :lucene:core:test over org.apache.lucene.codecs.lucene103.*, org.apache.lucene.codecs.lucene104.* (incl. TestLucene104PostingsFormat), TestCheckIndex, TestTermsEnum* and TestTerms: 15 classes (including the new test), 212 tests, 8 skipped, 0 failures.
  • :lucene:core:checkGoogleJavaFormat with only the fix applied: clean.
  • A probe with the fix prints index trie: 1197 bytes for 10,000 ids and 10 bytes for one term; unfixed main prints 0 for both.

B. The same without the padding

#

stats.indexNumBytes = fr.indexEnd - fr.indexStart - Long.BYTES; reports only the trie nodes (2 bytes for one term). Not run.

Trade-offs

More exact, but it ties Stats to a layout detail of TrieBuilder.save that could change.

C. Remove or relabel the field

#

As LUCENE-6617 did for the FST node and arc counts. Not run.

Trade-offs

Stats is @lucene.internal, so the API cost is small, but CheckIndex loses the one per-field terms-index size it prints.

Aside, not this bug: real sizes for old segments

#

The backward-codecs Lucene90 computeBlockStats could use fr.index.numBytes() (FST.java:506-508, the FST's serialized size) instead of ramBytesUsed(), which for an off-heap FST is a constant (FST.java:496-499, OffHeapFSTStore.java:46-47). Not run.

Trade-offs

Changes the output for 9.x-format segments; independent of fix A.

History

#

Introduced by #14333 (878e23f77390, 2025-04-14) and released through its backport #14563 in 10.3.0. Fails on every release from 10.3.0 to 10.6.0 and on main. 10.2.2 and older use the older block tree, which since 8.6.0 printed a size-independent constant. Not fixed upstream as of 2026-11-01.

Versions tested7 rows

Introduced by #14333, "A specialized Trie for Block Tree Index" (Guo Feng, gf2121), merged to main 2025-04-14 as 878e23f77390; it created codecs.lucene103.blocktree as a copy of the Lucene90 block tree. Released through the branch_10x backport #14563 (65fd8648eb63, 2025-05-09); git tag --contains lists exactly 10.3.0 to 10.6.0. No commit-level A/B was run: the release pair 10.2.2 (no Lucene103 package) / 10.3.0 (fails) and the single creating commit pin it.

Before 10.3 the older code stored FST.ramBytesUsed(), which is BASE_RAM_BYTES_USED + fstReader.ramBytesUsed() (FST.java:496-499); for an off-heap FST that is only fixed shallow object sizes, the FST's plus its OffHeapFSTStore's (OffHeapFSTStore.java:46-47): 24 + 32 = 56 bytes on 9.12.3 and 10.2.2. These constants depend on the JVM and platform (all runs: OpenJDK 25.0.3, Linux aarch64). On MMapDirectory the terms-index FST went off heap in 8.0.0 for non-primary-key fields (LUCENE-8635), in 8.1.0 also for ID-like fields such as the probe's two (docCount == sumDocFreq) when the reader is not opened from a writer (LUCENE-8671), and for every reader from 8.6.0 (LUCENE-9257). So the probe (MMapDirectory, a 20,000-term and a 1-term field) still tracked the sizes on 8.0.0 and reads the same value for both fields from 8.1.0 on. On 8.5.2 a heap-backed directory still tracked the size (65 vs 28,716 bytes).

Not fixed upstream (a snapshot): upstream main f815e679bf6 (2026-11-01) has no change in codecs/lucene103/blocktree/ since 645d4fe14a20.
