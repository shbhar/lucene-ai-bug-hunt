DirectoryTaxonomyReader.ramBytesUsed() leaves out the taxonomy arrays since 9.10.0

Since 9.10.0 a taxonomy reader's ramBytesUsed() counts only the small wrapper objects around its parents, children and siblings arrays, not the arrays themselves: it reports 41 bytes (73 with all three arrays loaded) whether the taxonomy has 12 or 100,002 ordinals. Search and facet results are not affected.

The finding in 30 seconds

#

TaxonomyIndexArrays.ramBytesUsed() (TaxonomyIndexArrays.java:281-293) adds RamUsageEstimator.shallowSizeOf(parents), and the same for children and siblings. Since #12995 these fields are ChunkedIntArray objects holding an int[][] (:46, :53, :55-75). shallowSizeOf(Object) measures the storage only of arrays; for any other object just its fields (RamUsageEstimator.java:516-531): 16 bytes per array.

Taxonomy arrays and ramBytesUsed(), in one minute

#
  1. A taxonomy gives every category path an ordinal. Its reader keeps three int arrays on the heap, indexed by ordinal: parents, children (youngest child) and siblings, 4 bytes per ordinal each. getParallelTaxonomyArrays() loads them; facet counting loads at least the parents array.
  2. DirectoryTaxonomyReader implements Accountable since 7.1.0 so that applications can see how much heap it uses: its ramBytesUsed() adds the arrays' size to an estimate for its two caches.
  3. Since 9.10.0 (#12995) each array is stored as chunks of 8,192 ints behind a small ChunkedIntArray wrapper; a reopened reader reuses the previous reader's full chunks instead of copying them (a children chunk that gets a new child is copied first).

The finding, step by step

#
  1. Add 100 categories, dim/v0 to dim/v99, with DirectoryTaxonomyWriter: 102 ordinals with the root and dim.
  2. Open new DirectoryTaxonomyReader(dir) and call getParallelTaxonomyArrays(), as every taxonomy facet count does. The parents array now holds 102 ints: 408 bytes.
  3. You expect ramBytesUsed() to include them, at least 408 bytes. Lucene 9.9.2 does: it reports 4,049 bytes for 1,002 ordinals.
  4. Instead it returns 41. Since 9.10.0 each array is a ChunkedIntArray wrapper around int[][] chunks, and RamUsageEstimator.shallowSizeOf sizes an object that is not an array by its own fields only: 16 bytes, no chunks.
  5. The value never grows: with all three arrays loaded the reader reports 73 bytes at 12, 1,002 and 100,002 ordinals, while the arrays hold 144, 12,024 and 1,200,024 bytes of ints.

Who is affected

#

Only applications that read a taxonomy reader's ramBytesUsed() or getChildResources(), for heap inventories, cache budgets or circuit breakers. For them it is wrong at every taxonomy size with default settings: about 12 bytes of int data per ordinal go unreported (1.2 MB at 100,002 ordinals). No search or facet result changes, and nothing in Lucene reads the value.

Mechanism, terms and numbers486 words

A taxonomy reader keeps three int arrays on the heap, parents, children and siblings, 4 bytes per ordinal each, and DirectoryTaxonomyReader implements Accountable so that applications can track that heap (LUCENE-7972, 7.1.0). Since #12995 (9.10.0) the arrays are ChunkedIntArray objects, a small wrapper around an int[][] of chunks, but TaxonomyIndexArrays.ramBytesUsed() and getChildResources() still size them with RamUsageEstimator.shallowSizeOf, which for an object that is not an array counts only the object's own fields. Each array then counts as 16 bytes, and the reader reports 41 bytes with the parents array loaded and 73 with all three, at any taxonomy size. Search results, facet counts and the index are never wrong, and nothing in Lucene reads the value; only applications that inventory or budget heap with it see a wrong number. Every release from 9.10.0 to 10.6.0 and main are affected; 9.9.2 counted the arrays.

The numbers

#

On a 64-bit JVM with compressed pointers: the method adds a hand-written 12 (header) + 3 x 4 (references) + 1 = 25 bytes for the holder's own fields (:283-284; a fixed sum, not the object's aligned size), and a ChunkedIntArray is 12 + 4 (its one reference) = 16 bytes. With the parents array loaded: 25 + 16 = 41; with children and siblings too: 25 + 3 x 16 = 73. DirectoryTaxonomyReader.ramBytesUsed() (DirectoryTaxonomyReader.java:596-612) adds this (:601) to a fixed estimate per cache entry (BYTES_PER_CACHE_ENTRY, :68-71); both caches are empty in the repro.

TaxonomyIndexArrays.getChildResources() (:295-309) uses the same shallowSizeOf calls, so it reports each array as 16 bytes too (executed in a value probe on main; the test does not assert it).

How the lines became wrong

#

The shallowSizeOf(parents/children/siblings) lines come from LUCENE-7972 (b9a51a16869 on main, 2017; released in 7.1.0 as db95888effb), when the three fields were int[] (9.9.2: TaxonomyIndexArrays.java:45, :52) and shallowSizeOf(int[]) measured the whole array. #12995 (2a0b7f20567, 2024) changed the fields to ChunkedIntArray and left the ramBytesUsed and getChildResources bodies byte-identical; git log -S 'shallowSizeOf(parents)' finds only b9a51a16869.

Exposure and likelihood227 words
  • Who. Code that calls DirectoryTaxonomyReader.ramBytesUsed() or getChildResources() once the arrays are loaded (every taxonomy facet count loads at least the parents array, TaxonomyFacets.java:98). Default settings, deterministic: a reader opened on a Directory fails the test with assertions on and off, and NRT and reopened NRT readers report the same 73 bytes (value probe, run with assertions on).
  • How much. All three arrays hold about 12 bytes of int data per ordinal (array headers and chunk tables come on top) and are reported as 73 bytes: measured 1,200,024 bytes of ints at 100,002 ordinals. By arithmetic, a taxonomy of 10 million categories holds about 120 MB that is reported as 73 bytes. Open issue #11008 (LUCENE-9969) is about these arrays' heap causing an out-of-memory crash (before chunking existed).
  • What does not happen. No wrong search or facet result, no change to the index, no exception. No Lucene code reads the value.
  • How likely. Rare. The recorded searches (see Prior reports) found no report since 9.10.0 (2024). A GitHub code search on 2026-11-08 (four queries: "taxoReader.ramBytesUsed", "taxonomyReader.ramBytesUsed", "DirectoryTaxonomyReader" "ramBytesUsed" language:Java, "getParallelTaxonomyArrays" "ramBytesUsed"; 34, 0, 118 and 89 hits, all read, the last 18 of the third query on 2026-11-09) found no call outside copies of Lucene's own sources, tests and javadocs and code-translation datasets built from them; code search covers only part of GitHub.

Why it looks unintended

#
  • Accountable.ramBytesUsed() is the object's heap estimate; LUCENE-7972 made the reader Accountable "so you can more easily track how much heap it's using".
  • 9.9.2 counted the arrays; #12995 changed their type and kept the shallowSizeOf lines, with no review comment on accounting.
  • A value that stays at 41 bytes at any taxonomy size does not estimate the arrays' heap.
The full argument171 words
  • Contract. Accountable.ramBytesUsed(): "Returns an estimate of the JVM heap memory used by this object in bytes"; "only JVM heap memory should be reported" (Accountable.java:34-40). The three arrays are plain on-heap int chunks.
  • Purpose. CHANGES 7.1.0 for LUCENE-7972 (b9a51a16869): "DirectoryTaxonomyReader, in Lucene's facet module, now implements Accountable, so you can more easily track how much heap it's using."
  • It used to work. A value probe on released jars reports 4,049 bytes at 1,002 ordinals and 400,049 at 100,002 on 9.0.0 and 9.9.2, and 41 for both on 9.10.0 and 10.6.0.
  • An accident, not a decision. The #12995 diff leaves the accounting bodies unchanged, and the review comments of #12995 and #13028 and the comments of #12989 never mention ramBytesUsed, Accountable or shallowSizeOf. No javadoc, CHANGES entry or test says the arrays are left out.
  • Why tests did not catch it. TestDirectoryTaxonomyReader.testAccountable calls getParallelTaxonomyArrays() with the comment "increases memory usage as a side-effect" and then asserts only ramBytesUsed() > 0 (TestDirectoryTaxonomyReader.java:631-632); 41 passes that.
The devil's-advocate check232 words

"Accountable is @lucene.internal, the taxonomy classes are @lucene.experimental, and the value is only an estimate." A value that does not grow with the taxonomy does not estimate the arrays at all, and the feature exists to report exactly these arrays.

"Since #12995 a reopened reader, NRT or not (DirectoryTaxonomyReader.java:216-217), shares the previous reader's full chunks (TaxonomyIndexArrays.java:120-127 copies the chunk references; a children chunk that gets a new child is copied first, :178-185), so counting only the wrapper avoids charging shared chunks twice." A reader opened on a Directory owns every chunk and still reports 41 bytes; even chunks no other reader holds, such as the last chunk, which is always copied (:125-126), are left out; and no comment or document makes that choice. The shared-chunk question only shapes the fix (see Suggested fix).

"A maintainer could drop the accounting instead", as Lucene 9.0 did for index readers (LUCENE-9387: "Lucene index readers are now using so little memory with the default codec") and #13241 / #13255 did for KnnVectorsReader in 2024 (10.0.0). Possible, but the taxonomy arrays still take about 12 bytes per ordinal of heap, and until then the class promises a heap estimate.

Both executed reviews by another model family (OpenAI GPT-5.6, refute and intended lenses) rated the works-as-designed case moderate and concluded "real"; the intended-behaviour verifier and the adjudication agreed.

Suggested fix

#

Recommended A: size the wrapper, its chunk table and every chunk

Fix A: size each ChunkedIntArray as wrapper + chunk table + every int[] chunk, in ramBytesUsed() and getChildResources() (+18/-12 lines). Validated: the repro fails stock and passes with the fix, assertions on and off; :lucene:facet:test (305 tests) and :lucene:facet:check -x test pass. Open choice for NRT readers that share chunks: see the options.

  /** The wrapper, its chunk table and every chunk (a ChunkedIntArray is not an array). */
  private static long sizeOf(ChunkedIntArray array) {
    if (array == null) {
      return 0;
    }
    long size =
        RamUsageEstimator.shallowSizeOf(array) + RamUsageEstimator.shallowSizeOf(array.values);
    for (int[] chunk : array.values) {
      size += RamUsageEstimator.sizeOf(chunk);
    }
    return size;
  }

A: size the wrapper, its chunk table and every chunk (validated by the checks) (recommended)

#

In TaxonomyIndexArrays, replace the three shallowSizeOf(...) calls in ramBytesUsed() and in getChildResources() with a helper that adds the wrapper, the int[][] table and each int[] chunk.

  /** The wrapper, its chunk table and every chunk (a ChunkedIntArray is not an array). */
  private static long sizeOf(ChunkedIntArray array) {
    if (array == null) {
      return 0;
    }
    long size =
        RamUsageEstimator.shallowSizeOf(array) + RamUsageEstimator.shallowSizeOf(array.values);
    for (int[] chunk : array.values) {
      size += RamUsageEstimator.sizeOf(chunk);
    }
    return size;
  }

Trade-offs

Smallest change, and each reader's value is the heap it keeps reachable. A reopened reader is charged for the full chunks it shares with the reader it came from, so summing ramBytesUsed() over several live generations counts those chunks more than once (the ownership question of open issue #16113). The total stays an estimate: the cache part is unchanged and "very coarse" (DirectoryTaxonomyReader.java:67-71).

What the checks validated

The repro fails stock and passes with the fix, assertions on and off; :lucene:facet:test (305 tests, 0 failures, assertions on and off) and :lucene:facet:check -x test pass.

B: count only the chunks this reader allocated

#

Size the chunks from startFrom on (allocateChunkedArray, TaxonomyIndexArrays.java:110-118) plus the children chunks below it that computeChildrenSiblings() replaces copy-on-write (:178-185). Sizing only the chunks from startFrom on would undercount.

Trade-offs

No double counting across NRT generations (the owned-bytes direction of #16113). But a reader's value then depends on its history, and it under-reports what it keeps alive once the older reader is closed. Not built.

C: let ChunkedIntArray implement Accountable

#

Give the wrapper its own ramBytesUsed() with the size of option A and call it from TaxonomyIndexArrays.

Trade-offs

Same behaviour as A with tidier code; keeps the sizing next to the data structure. Not built.

D: drop Accountable from the taxonomy reader

#

As Lucene 9.0 did for index readers (LUCENE-9387) and #13241 / #13255 did for KnnVectorsReader (10.0.0).

Trade-offs

Removes the feature LUCENE-7972 added and is an API change; the arrays still take about 12 bytes per ordinal of heap. Not built.

Downstream note

A product that sizes a heap circuit breaker or cache budget from a taxonomy reader's ramBytesUsed() undercounts the taxonomy arrays by about 12 bytes per ordinal.

How it was found

#

Code reading. Reading TaxonomyIndexArrays.ramBytesUsed() showed the bug; git history and one JUnit test confirmed it.

Only applications that read DirectoryTaxonomyReader.ramBytesUsed() or getChildResources() (heap inventories, cache or circuit-breaker budgets that sum Accountable values) are affected: once the taxonomy arrays are loaded (every taxonomy facet count loads at least the parents array), the reader reports about 41 bytes (73 with children and siblings) instead of about 12 bytes per ordinal, at any taxonomy size, with default settings, -ea and -da alike, for Directory and NRT readers; search results, facet counts and the index are never wrong and no Lucene code reads the value; every release 9.10.0-10.6.0 and main.
Summary
You add 100 categories to a taxonomy (102 ordinals), open a DirectoryTaxonomyReader on its Directory, load its arrays with getParallelTaxonomyArrays() (every taxonomy facet count loads at least the parents array) and call ramBytesUsed(). You expect the estimate to include the parent array it just loaded, at least 4 bytes per ordinal (408 bytes here), as it did up to 9.9.2; instead it reports 41 bytes, and the same constant (73 bytes with children and siblings loaded) for 12 or 100,002 ordinals. Since #12995 (9.10.0) TaxonomyIndexArrays measures its ChunkedIntArray wrappers with RamUsageEstimator.shallowSizeOf, which counts only a wrapper's own fields and none of its int[][] chunks.
