The bug in 30 seconds

#

Thai text often spells Sara Am (ำ) as two pieces, Nikhahit (ํ) + Sara Aa (า), sometimes with a tone mark between them. ThaiNormalizer glues the pieces back, but not when a second slip (an extra tone mark, or a look-alike of Sara Aa) sits inside them.

  1. You index two documents with the default ThaiAnalyzer: "drink water cold" with น้ำ ("water", U+0E19 U+0E49 U+0E33) typed cleanly, and with น้ำ typed as น + Nikhahit + Mai Ek + Mai Tho + Sara Aa: a decomposed Sara Am with a wrong tone mark typed before the right one.
  2. You expect both to index the term น้ำ. ThaiNormalizer says it recomposes Nikhahit + tone mark + Sara Aa into Sara Am, and its own test keeps the last of two different tone marks. A TermQuery for น้ำ should find 2 documents.
  3. You get 1. The typed word is indexed as นํ้า (U+0E19 U+0E4D U+0E49 U+0E32), still Nikhahit + tone + Sara Aa, and Analyzer.normalize, which Lucene's classic query parser uses for prefix, wildcard and fuzzy terms, returns the same. The same five characters with Mai Ek typed first give น้ำ.
  4. Why: the recomposition test runs once, on the characters as typed. After the Nikhahit it sees Mai Ek and then Mai Tho where it needs Sara Aa, and fails; the last step then removes Mai Ek, which leaves exactly the pattern, and nothing tests again. A second normalize() call would fix it.
  5. Without ThaiCharFilter (the filter on its own), two more shapes fail the same way: ท + Nikhahit + Lakkhangyao gives ทํา instead of ทำ, and Mai Tho typed twice inside the decomposed form gives นํ้า.

Who is affected

#

Thai-language indexes on 10.6 code. The default ThaiAnalyzer is hit only by Nikhahit + two different tone marks + Sara Aa (or Lakkhangyao in its place); ThaiNormalizationFilter alone (as in the factory's javadoc example) also by Nikhahit + Lakkhangyao and a doubled tone mark. The word gets a different term, so a query for the clean word misses it. Rare.

Mechanism, terms and numbers795 words

ThaiNormalizer (new in 10.6.0 with ThaiNormalizationFilter, which the default ThaiAnalyzer uses from 10.6.0) documents that it recomposes a decomposed Sara Am, Nikhahit + optional tone mark + Sara Aa, into Sara Am. It also converts Lakkhangyao to Sara Aa, removes a repeated tone mark and keeps the last of two different tone marks. It runs these rules as single forward passes: the recomposition test looks at the next characters as typed, a Lakkhangyao is converted only when the loop reaches it, and an extra tone mark is removed only in the last step. Nothing tests for a decomposed Sara Am again, so a second typo inside one leaves the decomposed form in the output. Through the default analyzer, น้ำ ("water") typed as น + Nikhahit + Mai Ek + Mai Tho + Sara Aa is indexed as นํ้า, and a TermQuery for น้ำ finds 1 of 2 documents; the same marks with Mai Ek first give น้ำ. With the filter on its own, ท + Nikhahit + Lakkhangyao and a doubled tone mark inside the decomposed form fail too. It is deterministic, raises no error and is in no release yet: the 10.6.0 RC1 revision contains it. Re-running the rules while a decomposed Sara Am is left fixes it; all Thai and analysis-module tests pass with that change.

Terms

#
  • Sara Am ำ (U+0E33) is one vowel character. Typists often enter it as Nikhahit ํ (U+0E4D) followed by Sara Aa า (U+0E32); with a tone mark (Mai Ek ่ U+0E48, Mai Tho ้ U+0E49) the tone is often typed between the two pieces. This is the decomposed Sara Am. Issue #16716, which proposed the class, calls it "often typed".
  • Lakkhangyao ๅ (U+0E45) looks like Sara Aa; the class converts it to Sara Aa unless it follows Ru or Lu.
  • The example word is น้ำ, "water": No Nu น U+0E19, Mai Tho U+0E49, Sara Am U+0E33.

The bug

#
  1. Step 2 of ThaiNormalizer.normalize is one forward pass (ThaiNormalizer.java:68-109). At a Nikhahit it tests whether the next character is Sara Aa, or the next two are a tone mark and Sara Aa (:79-94), on the characters as typed.
  2. A Lakkhangyao after the Nikhahit becomes Sara Aa only when the loop reaches it (:103-108), after the test has failed: ท ํ ๅ leaves step 2 as ท ํ า.
  3. With น ํ ่ ้ า the test sees Mai Ek, Mai Tho and fails. Step 4 (:135-147) then keeps the last of the two tone marks ("If two different consecutive tone marks appear, keep the last one", :142), or drops a repeated one (:137-141), and leaves น ํ ้ า.
  4. normalize returns after step 4 (:149): the decomposed Sara Am that steps 2-4 produced stays. Calling normalize on its own output recomposes it.
  5. With Mai Ek typed first (น ่ ํ ้ า) the test at the Nikhahit sees Mai Tho + Sara Aa and recomposes; step 4 then drops Mai Ek, giving น้ำ. So the result depends on the order the marks were stored in.
  6. In the default ThaiAnalyzer, ThaiCharFilter runs first (ThaiAnalyzer.java:119-128). It converts the Lakkhangyao (ThaiCharFilter.java:149-154) and drops a repeated identical tone mark (:97-103), so those two shapes reach the token filter as a plain decomposed Sara Am, which it recomposes. The char filter has no keep-last-tone rule and its own recomposition needs exactly one tone mark (:126-136), so Nikhahit + two different tone marks + Sara Aa reaches ThaiNormalizer unchanged. With a Lakkhangyao in place of the Sara Aa, the char filter converts it and leaves both tone marks, so the same shape arrives.

  • How likely. Rare: it needs two typing anomalies inside one character cluster, and each anomaly on its own is normalized correctly. Why it is a bug, not intended

#
  • The output นํ้า is exactly what the javadoc says the class recomposes: "Nikhahit U+0E4D + optional tone mark + Sara Aa U+0E32"; the upstream test testSaraAmDecomposition uses that very string as its input.
  • The same five characters with Mai Ek typed first are normalized to น้ำ.
  • No test, commit or discussion limits the rules to one typo per cluster.
The full argument189 words
  • The output is the documented input form. "Recomposes decomposed Sara Am (Nikhahit U+0E4D + optional tone mark + Sara Aa U+0E32) into canonical Sara Am (U+0E33)" (ThaiNormalizer.java:29-30). The result นํ้า is Nikhahit + one tone mark + Sara Aa.
  • The upstream tests. testSaraAmDecomposition asserts นํ้า -> น้ำ (TestThaiNormalizer.java:40-41); testConsecutiveDifferentTones asserts "When multiple different tone marks are typed, keep the last one" (:66-69). MIGRATE.md's 10.6 Thai section names "decomposed Sara Am (น + ํ + ้ + า)" as text 10.6 analyzes differently (lucene/MIGRATE.md:768).
  • Keystroke order decides the result. Mai Ek typed before the Nikhahit gives น้ำ, and so does the precomposed two-tone form; the code even has a dedicated rule for the tone-first order (:96-101).
  • The javadoc list is not an execution order. Dangling-mark removal is listed last (:38) but runs before step 2 (:63-66); issue #16716 lists the same rules in another order, deduplication first.
  • No record of a limitation. PR #16717 has no reviews and one thank-you comment; #16716 has no comments; no upstream test combines two anomalies in one cluster.
The devil's-advocate check208 words

The checkers built the strongest case for "intended": the javadoc is a list of best-effort repairs and promises no idempotence; its pattern allows one optional tone mark, so Nikhahit + two tone marks + Sara Aa is not literally the documented pattern; keep-last-tone is stated only in a code comment (ThaiNormalizer.java:142) and a test; and two typos in one cluster could be out of scope for "common orthographic variations" (:24).

Why it fails: the class itself emits the documented pattern, the one its own test treats as input to repair; the same marks in another stored order give a different term; and nothing in the javadoc, tests or history limits the rules to one anomaly per cluster. That makes a bug reading persuasive, not certain: a maintainer could still call combined anomalies an enhancement. The independent reproducer, the devil's advocate, the works-as-designed review and the adjudication rejected the case; the refute review said "not real (low)" only on procedure (it ran no command; it rated the intended case moderate and asked for a re-run), so it was discounted. The case survives as a priority argument (Low). File it without claiming idempotence as a contract, and for the default analyzer claim only the two-different-tones form.

Suggested fix

#

Recommended A. Run steps 2-4 again while a decomposed Sara Am is left

Re-run steps 2-4 of ThaiNormalizer.normalize while the buffer still holds Nikhahit + (tone) + Sara Aa (+24 lines, one file). Only tokens whose output today keeps a decomposed Sara Am change (the whole token is re-run); no allocation. Validated: the new tests, all Thai and analysis-module tests, check, and the bounded check (1,134 mismatches to 0).

A. Run steps 2-4 again while a decomposed Sara Am is left (validated by the checks) (recommended)

#

Steps 2-4 move unchanged into a private normalizeMarks(s, len); normalize repeats it while hasDecomposedSaraAm(s, len) finds Nikhahit + Sara Aa or Nikhahit + tone mark + Sara Aa.

What it changes, by construction. The first pass is today's code, so a token's output differs from today only when today's output for that token still contains a decomposed Sara Am (the loop test also catches tone + Nikhahit + Sara Aa, which contains Nikhahit + Sara Aa). Each extra pass recomposes at least one, which deletes a character, so the loop ends after at most len extra passes. That bounds the passes, not the time: each pass includes step 3, whose scans repeat until nothing moves, so on long tokens its cost can grow with the square of the token length, as it does today. A token without a leftover decomposed Sara Am costs one extra linear scan; nothing is allocated.

Within an affected token, every part is re-run. The extra pass runs all of steps 2-4 on the whole token, so it can also change a part unrelated to the Sara Am: ThaiNormalizer.normalize on ฤๅ่ followed by ทํๅ (0E24 0E45 0E48 0E17 0E4D 0E45) gives 0E24 0E48 0E45 0E17 0E4D 0E32 today and 0E24 0E48 0E32 0E17 0E33 with fix A: the Lakkhangyao of the Ru pair becomes Sara Aa too. The bounded check (5 symbols) has no room for both patterns, so it cannot show this.

New output. Every failing row of the table gives น้ำ or ทำ, through ThaiNormalizer and ThaiAnalyzer.normalize. The malformed ฤๅ่ on its own (Ru + Lakkhangyao + Mai Ek, not claimed) keeps today's ฤ่ๅ.

Trade-offs

  • Targets this bug only: other cases where a later step creates an earlier step's pattern keep today's output when they are alone in a token, such as the malformed Ru + Lakkhangyao + tone class, where step 3 moves the tone mark between Ru and Lakkhangyao; in a token that also holds a leftover decomposed Sara Am they change too (example above).
  • Does not fix the sibling ThaiCharFilter bug (LFV-876), which has the same design at another fix site.
  • Indexed terms change only for tokens whose output today keeps a decomposed Sara Am; after a 10.6.0 release those would need reindexing (a MIGRATE note). No CHANGES entry is drafted; no benchmark was run.

How it was found

#

A bounded-exhaustive check of ThaiNormalizer against its javadoc's rules, written as a rewriting system, over 824,691 inputs (up to 5 symbols of a 21-symbol alphabet starting with one of four initial characters, plus all inputs up to 3 symbols). 1,134 with a unique normal form under the model kept a decomposed Sara Am; iterating the normalizer fixed them all.

The method in full237 words
  • Method (semi-formal): bounded-exhaustive translation validation of the stock main jar, in the hunt's unit on the 10.6 Thai normalizers. The javadoc's rules were encoded as a string-rewriting system (the model's reading of the javadoc, not a Lucene contract); for 824,691 inputs over a 21-symbol alphabet (every input of 1 to 5 symbols that starts with one of four initial characters, ก, น, ฤ or the leading vowel เ, plus every input of up to 3 symbols; all inputs of up to 5 symbols would be 4,288,305) the reference computed all normal forms by exhaustive rewriting, and the real ThaiNormalizer was compared with them.
  • Signal. 1,756 inputs with a unique normal form under the model, passing its simplified well-formedness check, got an output that one of the class's own rules still rewrites: 864 + 270 in this decomposed-Sara-Am class, 622 in a malformed Ru + Lakkhangyao + tone class that is not claimed. Iterating the stock normalizer to a fixed point removed every mismatch. Through ThaiAnalyzer.normalize, 12 inputs of the class remained, all with two different tone marks.
  • First lead. A planning probe before the unit, a bounded idempotence check over 333,453 inputs, had found 4,632 inputs whose output changes on a second call, for example ก ํ ๅ -> กํา -> กำ.
  • Then reading the code gave the mechanism, and the finder wrote the public-API JUnit and the fixed-point sketch; independent checkers followed (see "Independent checks").

LFV-873, snapshot of 2026-10-29

Registry title
ThaiNormalizer looks for a decomposed Sara Am before it converts Lakkhangyao or removes an extra tone mark, so its output can still be the decomposed form (Nikhahit + tone + Sara Aa), and the default ThaiAnalyzer indexes น้ำ ('water') typed with two tone marks inside a decomposed Sara Am as a different term
Area
analysis-common / Thai (ThaiNormalizer.normalize rule order; ThaiNormalizationFilter, the 'thaiNormalization' factory and the default ThaiAnalyzer as consumers; new in 10.6.0)
Priority
Low, rank 410: The same unreleased 10.6 Thai double-typo trigger as LFV-876 but it only changes one indexed term instead of merging words.
Impact class
silent wrong results
Impact note
Thai-language indexes on the unreleased 10.6.0 code (main, branch_10_6 and the 10.6.0 release-candidate revision 4ae946e5a9b) are hit when a word carries two typing anomalies inside one decomposed Sara Am: through the default ThaiAnalyzer only Nikhahit + two different tone marks + Sara Aa reaches the term (ThaiCharFilter repairs the other forms first), while ThaiNormalizationFilter used without the char filter (a setup the factory's javadoc example shows; verified with a whitespace tokenizer) also leaves Nikhahit + Lakkhangyao and a doubled tone mark inside the decomposed form; the term then differs from the clean spelling's, so a query for the clean word misses the document and Analyzer.normalize returns the same unnormalized form for prefix, wildcard and fuzzy terms, deterministically at any index size, with no error and a well-formed index.
Summary
You index Thai text with the default ThaiAnalyzer (or ThaiNormalizationFilter) in which the word น้ำ ('water') is typed with a decomposed Sara Am and an extra tone mark inside it, น + Nikhahit + Mai Ek + Mai Tho + Sara Aa, and you expect the term น้ำ, because ThaiNormalizer documents that it recomposes Nikhahit + tone + Sara Aa into Sara Am and (per its code comment and upstream test) keeps the last of two different tone marks. ThaiNormalizer tests for the decomposed Sara Am in one forward pass over the raw characters, before it converts a following Lakkhangyao and before its last step removes the extra or repeated tone mark, and it never checks again, so the output is นํ้า (U+0E19 U+0E4D U+0E49 U+0E32), still the decomposed form; a query for น้ำ misses the document, while a second normalize() call, or the same two tone marks typed in the other order, gives น้ำ. When the token filter runs without ThaiCharFilter, ท + Nikhahit + Lakkhangyao likewise gives ทํา instead of ทำ, and a doubled tone mark inside the decomposed form gives นํ้า.
