FixedBitSet.ensureCapacityAndClear keeps the old bits when it grows a set into spare words of its long[]

When a set's long[] already has room for the new bit, FixedBitSet.ensureCapacityAndClear reuses that array without zeroing it: a 64-bit set over two words with bit 0 set comes back as a 128-bit set with bit 0 still set. Since 10.4.0; no Lucene caller takes this path.

The finding in 30 seconds

#

ensureCapacityAndClear clears the set when the new bit fits, and allocates a fresh, zeroed array when the old array is too small. In between, when the bit does not fit in length() but the array already has room, it reuses the array and forgets to zero it.

Background in three steps

#
  1. A FixedBitSet keeps its bits in a long[], 64 bits per word. length() is the number of bits it holds, and bits past length() in the last words ("ghost bits") must stay clear.
  2. The array may be longer than needed: new FixedBitSet(new long[2], 64) is a legal 64-bit set over 128 bits of storage, and clone() keeps such an array as long as it is.
  3. ensureCapacity(bits, n) returns a set that can hold bit n and keeps the bits; ensureCapacityAndClear(bits, n), added in 10.4.0, returns one that can hold bit n and is empty.

The finding, step by step

#
  1. Wrap a two-word long[] in a 64-bit set, new FixedBitSet(new long[2], 64) (the constructor allows a larger array if its extra bits are clear), and set bit 0.
  2. Call FixedBitSet.ensureCapacityAndClear(bits, 64) to make room for bit 64. You expect an empty set: the javadoc says "Clear the given bits", and the ensureCapacity + clear() code it replaced returns cardinality 0.
  3. The method sees that two words (128 bits) already have room for bit 64, so it neither clears the array nor allocates a new one: it wraps the same array in a new 128-bit set.
  4. You get length() 128 with bit 0 still set: cardinality() is 1, not 0. No exception and no assertion, with assertions on or off.

Who is affected

#

Only code that calls this @lucene.internal utility directly, with a set over a larger long[] (built with FixedBitSet(long[], int) or cloned from one), and then grows it. Lucene's two callers, the doc-values update scratch set and the HNSW visited set, start from exact-size sets and never take this path, so Lucene's own indexing and search are not affected.

Mechanism, terms and numbers463 words

FixedBitSet.ensureCapacityAndClear(bits, desiredBit) (new in 10.4.0, #15582) promises to "Clear the given bits and ensure it can store a value at desiredBit index". When desiredBit >= bits.length() but the set's backing long[] already has enough words (the FixedBitSet(long[], int) constructor allows an array that "may be larger"), the shared helper ensureCapacityInternal neither clears the array nor allocates a new one: it wraps the same, uncleared array in a new, longer FixedBitSet and returns that, with every old bit still set.

In the repro a 64-bit set over a two-word array with bit 0 set, grown to bit 64, comes back as a 128-bit set with bit 0 still set (cardinality 1, not 0), with assertions on and off. The code it replaced, ensureCapacity(bits, n); bits.clear(), returns an empty set on the same input. Lucene's own two callers start from exact-size sets and never take this branch, so Lucene's own indexing and search never reach it; only code that calls the @lucene.internal utility directly with a larger array is hit.

The mechanism (main 5adff78bb168, FixedBitSet.java)

#
  1. ensureCapacityAndClear (:53-60) and ensureCapacity (:44-51) both call ensureCapacityInternal(bits, desiredBit, preserveData) (:62-83), with preserveData false and true.
  2. In range (desiredBit < numBits, :64-68) the clearing variant calls bits.clear(), which zeroes the whole backing array (Arrays.fill(bits, 0L), :172-175). Correct.
  3. Growth: numWords = bits2words(desiredBit) and arr = bits.getBits() (:72-73). Only if numWords >= arr.length (:74) is a new array made: ArrayUtil.grow when preserving, a fresh zeroed new long[...] when clearing (:75-79). Otherwise the caller's array is kept and return new FixedBitSet(arr, arr.length << 6); (:81) wraps it. No clear happens on this path; this is the fix site. So for a given call the reuse branch runs exactly when desiredBit >= bits.length() and bits2words(desiredBit) < bits.getBits().length.
  4. In the repro bits2words(64) = 1 and arr.length = 2, so 1 >= 2 is false: the two-word array, bit 0 still set, becomes a 128-bit set. A probe on main printed grown: length=128 cardinality=1 get(0)=true sameArray=true.
  5. Reach: a trigger needs a set with spare words, getBits().length > bits2words(length()). The constructor documents that: the array "must be large enough to accommodate the numBits specified, but may be larger. In that case the 'extra' or 'ghost' bits must be clear" (:152-170); the repro's extra word is zero and passes the ghost-bit assertion (:169). clone() keeps an oversized array (:826-831). Every set that ensureCapacity* creates when it grows is exact-size (numBits = arr.length << 6, :81), and the in-range branch returns the caller's own set, so a set that starts exact-size stays exact-size and never takes the branch on a later call.
Exposure and likelihood141 words
  • Who: code that builds a FixedBitSet over a reused, larger long[] with the adopting constructor (or clones such a set) and then grows it past length() with ensureCapacityAndClear. That caller's membership tests and counts are silently wrong.
  • Not hit: Lucene itself. ReadersAndUpdates starts its scratch set as new FixedBitSet(bitSet.length()) (ReadersAndUpdates.java:751, grown at :754); VisitedSet starts with new FixedBitSet(graphSize) (VisitedSet.java:69, grown at :93, reached from HnswGraphSearcher.java:366). In-tree code that wraps a reused, possibly larger scratch array (DocIdsWriter.java:283) never grows it with this method. A code search of the elastic, opensearch-project and apache GitHub organizations found no other caller.
  • Effect: a wrong return value, no exception and no assertion. No in-tree index or search impact was identified, because no in-tree caller reaches the branch.
  • Since: 10.4.0, a regression from the code #15582 replaced.

Why it looks unintended

#
  • Javadoc: "Clear the given bits and ensure it can store a value at desiredBit index"; the constructor allows a long[] that "may be larger".
  • The code it replaced (#15582), ensureCapacity(bits, n); bits.clear(), returns an empty set on the same input.
  • Upstream's TestFixedBitSet.makeFixedBitSet builds sets over larger arrays; LUCENE-4693 fixed wrong results for this shape as a bug.
The full argument190 words
  • Contract. ensureCapacityAndClear: "Clear the given bits and ensure it can store a value at desiredBit index. If the current [#length()] is sufficient, bits is simply cleared and returned. Otherwise, a new, larger bitset is allocated." (FixedBitSet.java:53-56). Neither sentence allows old bits in the result; on this branch the new, larger bitset is a new FixedBitSet over the caller's own, uncleared array. VisitedSet.ensureCapacityAndClear documents "Removes all nodes, and grows the set" (VisitedSet.java:111).
  • The input is legal. The constructor allows a larger array (:152-170). TestFixedBitSet.makeFixedBitSet builds sets over arrays with up to 99 extra words (TestFixedBitSet.java:329-341). LUCENE-4693 (#5758, 2013) fixed wrong results for sets of this shape in other methods.
  • History. #15582 ("Avoid copying bitset that's subsequently cleared", 10.4.0 CHANGES under "Optimizations", CHANGES.txt:1500) replaced ensureCapacity(bits, n); bits.clear() at both call sites; clear() zeroes the whole array, so the old idiom was right for this input. It routed the clearing variant through the reuse branch from LUCENE-5440 (b872f4b5c3c, 2014), written for the preserving ensureCapacity, where keeping the bits is right. The PR thread has no review discussion of this case.
The devil's-advocate check166 words

"FixedBitSet is @lucene.internal and no Lucene code reaches the branch, so it is not a bug." The class is @lucene.internal (FixedBitSet.java:29) and the util package says its "APIs ... are primarily internal and may change between releases" (package-info.java:35). An independent reviewer from another model family (OpenAI GPT-5.6) reproduced the bug, agreed on the root cause and the fix and rated the intended-behaviour defence "weak", yet returned an overall "not real" verdict, with high confidence, on this ground alone: it treats inputs to @lucene.internal APIs as out of contract.

Why it fails: @lucene.internal limits API stability, not correctness. The method is public and static, documents a clear, and returns wrong data on an input the same class documents as legal. The argument is about impact and about whether an internal class is worth a change, which is why the priority is Low; a maintainer may still prefer a javadoc precondition, an assertion, fix B or no change, and that call is theirs.

Suggested fix

#

Recommended A. Zero the reused array when clearing (validated)

In ensureCapacityInternal, when the array is reused and preserveData is false, zero it before wrapping: Arrays.fill(arr, 0L) (+3 lines). The repro passes with assertions on and off; TestFixedBitSet, TestVisitedSet, TestMixedDocValuesUpdates and the lint checks pass.

if (numWords >= arr.length) {
  // unchanged: grow (preserving) or allocate a fresh, zeroed array (clearing)
} else if (preserveData == false) {
  // the backing array is large enough and is reused: clear it, like the in-range branch does
  Arrays.fill(arr, 0L);
}
return new FixedBitSet(arr, arr.length << 6);
All options and trade-offs2 options · 364 words

Two options. A was validated with gradle in a scratch worktree of 5adff78bb168; B is by reading. The same line also holds LFV-137 (the int shift arr.length << 6 wraps for sets of about 1.9e9 bits): its fix changes only the shift and does not clear the array, and this fix does not touch the shift.

A. Zero the reused array when clearing (validated) (recommended)

#

In ensureCapacityInternal (FixedBitSet.java:74-81), +3 lines:

if (numWords >= arr.length) {
  // unchanged: grow (preserving) or allocate a fresh, zeroed array (clearing)
} else if (preserveData == false) {
  // the backing array is large enough and is reused: clear it, like the in-range branch does
  Arrays.fill(arr, 0L);
}
return new FixedBitSet(arr, arr.length << 6);

Trade-offs

  • Keeps #15582's saving (no copy, and no allocation when the array has room). The fill costs what the old ensureCapacity + clear() idiom cost, and only on a branch no in-tree caller takes, so no direct runtime cost is expected on Lucene's own call paths (not benchmarked).
  • It zeroes the shared array in place, so the caller's original bits object is cleared too, as with the in-range branch and with the old idiom on this input. The whole array must be zeroed, because the new set covers all of it (arr.length << 6 bits). bits.clear() in place of Arrays.fill(arr, 0L) is equivalent.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: on stock the repro fails with assertions on and off; with fix A it passes, on and off.
  • With fix A: TestFixedBitSet 34 of 34, hnsw.TestVisitedSet 2 of 2, TestMixedDocValuesUpdates 10 of 11 (1 skipped; it includes testLongRunValuesReset, added with the scratch set in #14552) and the repro: 48 tests, 0 failures.
  • checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest for lucene/core pass.
  • Not run: the full lucene/core suite.

B. Never reuse the array when clearing

#

Allocate a fresh array on every growth with preserveData false: if (numWords >= arr.length || preserveData == false).

Trade-offs

Simpler to reason about, but allocates even when the array has room, which is what #15582 set out to avoid. By reading, not run.

Downstream note

#

Relevant downstream only to code that wraps its own larger long[] in a FixedBitSet and grows it with ensureCapacityAndClear; a code search of the elastic, opensearch-project and apache GitHub organizations found no such caller.

How it was found

#

Semi-formal: a proof-obligation audit of FixedBitSet's contract checked that ensureCapacityAndClear returns a cleared set on every branch of the shared growth helper. The array-reuse branch has no clear, and a one-test JUnit repro on stock main witnessed the surviving bit.

The method in full99 words
  • Obligation: for every legal input set and every desiredBit, the result of ensureCapacityAndClear has cardinality 0 and can hold desiredBit (FixedBitSet.java:53-56), on each of the three branches of ensureCapacityInternal (:62-83).
  • Finding: the in-range branch clears and the allocating branch starts from a zeroed array, but the reuse branch (:74, :81) wraps the caller's array unchanged; it is reachable because the constructor allows a larger array (:152-170).
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Impact class
minor
Impact note
Only code that uses FixedBitSet (an @lucene.internal class) directly is hit: it must build a set with the public FixedBitSet(long[], int) constructor over a long[] with more words than the set needs (documented as allowed), or clone such a set, and then grow it past length() with ensureCapacityAndClear; the returned set silently keeps every bit that was set before the call (no exception and no assertion, -ea and -da alike), so that caller's membership tests and cardinality are wrong; Lucene's own two callers (the soft-deletes scratch set in ReadersAndUpdates and the HNSW VisitedSet) always start from exact-size sets and never take this branch, so no index, search result or Lucene code path is affected; releases 10.4.0 through 10.6.0 and main.
Summary
You wrap a two-word long[] in a 64-bit FixedBitSet (the FixedBitSet(long[], int) constructor says the array 'may be larger' as long as the extra bits are clear), set bit 0, and call FixedBitSet.ensureCapacityAndClear(bits, 64) to make room for bit 64. You expect an empty set, because the javadoc says the method will 'Clear the given bits and ensure it can store a value at desiredBit index', and the two-step code it replaced (ensureCapacity, then clear()) returns one. Instead the method sees that the existing array is already big enough, wraps that same array in a new 128-bit set without zeroing it, and returns a set in which bit 0 is still set (cardinality 1 instead of 0).
