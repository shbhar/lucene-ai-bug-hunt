ICUTransformFilterFactory accepts direction="Forward" but builds the reverse transliterator

Configure the ICU transform filter with direction="Forward" and the factory accepts it, then runs the transform backwards: with Cyrillic-Latin, Федерация stays Федерация instead of becoming Federaciâ, and nothing reports an error. Only exact lower-case forward (or no direction) works; every release since 4.3.0 has it.

The finding in 30 seconds

#

One capitalised letter in an optional setting flips the transform.

The ICU transform filter in two lines

#
  1. ICUTransformFilter rewrites every token with an ICU transliterator named by id: Cyrillic-Latin turns Федерация into Federaciâ.
  2. The optional direction says which way it runs: forward (the default) as named, or reverse, the inverse (here Latin-Cyrillic, which leaves Cyrillic text unchanged).

The finding, step by step

#
  1. Build the ICU transform filter with id=Cyrillic-Latin and direction="Forward" (through new ICUTransformFilterFactory(args), CustomAnalyzer or the SPI name icuTransform) and analyze the token Федерация.
  2. You expect Federaciâ, as with direction="forward" or no direction at all. The factory checks the value case-insensitively, so Forward is accepted; sideways would be rejected with an error.
  3. But the check hands back your own spelling, and the factory then tests "forward".equals(direction). "Forward" is not equal to "forward", so it builds the reverse (Latin-Cyrillic) transliterator.
  4. You get Федерация unchanged, with no exception, at index and query time alike. FORWARD or any other capitalised spelling does the same; every spelling of reverse still works.

Who is affected

#

Users of the opt-in analysis-icu module who configure this filter with a capitalised direction (constructor, CustomAnalyzer, SPI name or a schema). Every token is transformed the wrong way at index and query time, silently. Whether searches still match depends on the transform. The default, forward and any reverse work, so the trigger is rare.

Mechanism, terms and numbers310 words

ICUTransformFilterFactory validates its optional direction argument case-insensitively (get(args, "direction", [forward, reverse], "forward", false), ICUTransformFilterFactory.java:51-52 at 5adff78bb168), so Forward and FORWARD are accepted while sideways is rejected. The validation returns the caller's own spelling (AbstractAnalysisFactory.java:190-191), and the factory then picks the direction with a case-sensitive "forward".equals(direction) (:53). Every accepted spelling other than exact lower-case forward therefore builds the reverse transliterator: with id=Cyrillic-Latin and direction="Forward", Федерация comes back unchanged instead of Federaciâ, at index and query time, with no error and the same result with assertions on and off. Until 4.2.1 the factory compared with equalsIgnoreCase("forward"); the LUCENE-4877 parameter-parsing refactor changed that in 4.3.0, and every release through 10.6.0 has it. A one-line equalsIgnoreCase fix restores the old meaning. The module is opt-in and the trigger is a capitalised optional value, so the priority is Low.

The two lines that disagree

#
  1. ICUTransformFilterFactory.java:51-52: get(args, "direction", Arrays.asList("forward", "reverse"), "forward", false). The last argument is caseSensitive = false, so Forward, FORWARD and FoRwArD pass validation. Values outside the list fail: IllegalArgumentException("Configuration Error: 'direction' value must be one of [forward, reverse]") (AbstractAnalysisFactory.java:195-196).
  2. AbstractAnalysisFactory.java:190-191: on an equalsIgnoreCase match, get returns s, the caller's own spelling, not the allowed value.
  3. ICUTransformFilterFactory.java:53: int dir = "forward".equals(direction) ? Transliterator.FORWARD : Transliterator.REVERSE;. For "Forward" the test is false, so :54 builds Transliterator.getInstance(id, REVERSE).
  4. The one transliterator serves both create() and normalize() (:65-73), so index-time analysis, query-time analysis and Analyzer.normalize all run the reverse transform.

This factory is the only caller in lucene/ that passes caseSensitive=false.

Other transforms flip the same way

#

Hiragana-Katakana with direction="Forward" through CustomAnalyzer returns ひらがな instead of ヒラガナ; Upper with "FoRwArD" turns MiXeD into mixed instead of MIXED. The default, forward, reverse and ReVeRsE behave as documented in the same runs.

Exposure and likelihood136 words
  • Who is hit. Analyzers built from factory arguments: the public Map constructor, TokenFilterFactory.forName("icuTransform", ...), CustomAnalyzer.builder().addTokenFilter("icuTransform", ...) or a schema-driven configuration, with direction spelled with any capital letter.
  • What happens. The stock inverse ICU transform runs on every token, at index and query time. The indexed terms are in the wrong script or form. One analyzer used on both sides applies the same wrong transform to both, so whether searches still match depends on the transform (by reading, not measured).
  • Not affected. The parameter omitted, exact forward, and every spelling of reverse.
  • Scale and likelihood. One token shows it; no data size or load is involved. Rare: the javadoc and the Solr reference guide spell the values in lower case, and the dated searches (2026-11-02 and 2026-11-03) found no report of it since 2013.

Why it looks unintended

#
  • The factory opts into case-insensitive validation (the only caller that does), so Forward is accepted; the javadoc names just two values, with no case rule.
  • Through 4.2.1 it compared with equalsIgnoreCase("forward") under the same javadoc; the 4.3.0 refactor aimed to reject invalid arguments, not to change valid ones.
  • No test, CHANGES or MIGRATE entry pins the current behaviour.
The full argument165 words
  • Contract. Javadoc (ICUTransformFilterFactory.java:32): "direction (optional): Either 'forward' or 'reverse'. Default is forward." The code accepts any case (:51-52) and rejects other values loudly; an accepted spelling of forward that means reverse is documented nowhere.
  • History. The factory was added by SOLR-2210 (5c6b4f4f650, 2010) with direction == null || direction.equalsIgnoreCase("forward") -> FORWARD, equalsIgnoreCase("reverse") -> REVERSE, else an exception; 4.2.1 still has that (ICUTransformFilterFactory.java:56-62 at the 4.2.1 tag). LUCENE-4877 (#5942; 4.3.0 CHANGES: "Throw exception for invalid arguments in analysis factories") replaced it with the two current lines. Its thread proposed the case-insensitive get overload but never mentions this factory or direction.
  • Tests. TestICUTransformFilterFactory uses only the default direction (:41-49) and lower-case reverse (:57).
  • Caveat. No document promises that the values are case-insensitive; the javadoc only spells them in lower case. The case for "not intended" rests on the code's own opt-in (:51-52) and on the pre-4.3 behaviour: strong evidence, not a documented guarantee.
The devil's-advocate check79 words

Strongest case for "intended": the javadoc spells the values in lower case, and sibling factories compare their values case-sensitively (PatternReplaceFilterFactory.java:56, ICUNormalizer2FilterFactory.java:58, :63), so Forward is a user error. Why it fails: those siblings also validate case-sensitively, so a wrong case gets an exception there; this factory alone opts into case-insensitive acceptance and then misreads what it accepted. The same lower-case javadoc stood from 2010 to 2013 beside case-insensitive parsing, so it was never a case-sensitive contract.

Return the canonical value from AbstractAnalysisFactory.get(..., caseSensitive=false) (not built)

Return allowedValue instead of s at AbstractAnalysisFactory.java:191, so callers always see the canonical spelling.

Trade-offs

Would also protect future callers such as the char-filter factory in PR #15, but it changes a public method of lucene/core that downstream factories may call, so it needs its own review; A is the minimal fix.

Make the validation case-sensitive (not recommended, not built)

Trade-offs

Downstream note

#

Solr schemas configure this same factory (its reference guide documents the direction option, read 2026-11-02), so a capitalised value there is hit the same way; as read on 2026-11-02, Elasticsearch and OpenSearch parse their own setting and do not use this factory.
