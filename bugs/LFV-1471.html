Sandbox PhraseWildcardQuery is cached per segment although its expansion budget spans all segments, so the cache serves stale hits after a reopen

PhraseWildcardQuery spends one expansion budget across all segments, smallest first, so a segment's matches depend on the others, yet it lets the query cache reuse each segment's result. After a reopen adds a smaller segment, the cache counts 2 where an uncached search counts 1 (5010 vs 4010 on 10.6.0).

The finding in 30 seconds

#

PhraseWildcardQuery gives each segment only what smaller segments left of one shared expansion budget, but reports each segment's result as cacheable. A query cache, which stores results per segment and reuses them across reopens, then serves a result computed under a different set of segments.

Background

#
  1. PhraseWildcardQuery (sandbox, @lucene.experimental) is a phrase with wildcard parts, such as "a* x". maxMultiTermExpansions caps the total number of expansions across all wildcards and all segments, counted per segment (a term found in two segments counts twice). It visits the segments smallest first; segments after the budget runs out get no expansions and match nothing.
  2. The query cache (LRUQueryCache) stores a query's matching documents per segment, keyed by the segment and the query, and reuses the entry in every reader that shares the segment, for example after openIfChanged. It first asks Weight#isCacheable: a result that depends on anything outside the segment must answer false.

The finding, step by step

#
  1. Index one document, aa x c, as segment 1. Search the phrase "a* x" built with PhraseWildcardQuery.Builder("f", 1), so at most 1 wildcard expansion in total. Through an LRUQueryCache it counts 1 (a* expands to aa), and the cache stores segment 1's hit.
  2. Add one document, ab x, as segment 2 and reopen with openIfChanged. Segment 2 has fewer terms, so it is searched first and takes the only expansion (ab); segment 1 gets none. An uncached search of the new reader counts 1.
  3. You expect the cached search of the same reader to count 1 too. You get 2: the new reader shares segment 1, so the cache hands back segment 1's entry from before the reopen and adds segment 2's hit.
  4. Why: the cache keys an entry on (segment, query) and trusts Weight#isCacheable, which this query inherits as true from PhraseWeight, although its result in a segment depends on the other segments.
  5. On 9.x and 10.x a plain IndexSearcher's default cache is enough: one 20,000-document segment, limit 50, the query run 10 times, then a 10-document segment added: cached 5010, uncached 4010.

Who is affected

#

Applications that build the sandbox PhraseWildcardQuery with a limit that really cuts expansions, keep a query cache across reopens (the default IndexSearcher cache on 9.x and 10.x; an installed one on main) and reopen into a different set of segments. Cached and uncached searches of one reader then silently disagree.

Mechanism, terms and numbers607 words

PhraseWildcardQuery (sandbox, @lucene.experimental) caps the expansions of its wildcard parts with one budget "across all multi-terms and across all segments". createWeight visits the segments smallest first, and once the budget is used up the remaining segments get no expansions and match nothing, so what one segment matches depends on which other segments the reader has. The Weight it returns does not override isCacheable and inherits true from PhraseWeight, against the SegmentCacheable contract ("should return false" for objects that are not segment-immutable). LRUQueryCache keys an entry on the segment core and the query, not on the reader, so after a reopen that adds or drops a segment it serves an entry computed under the old segment set: in the repro the cached count is 2 while an uncached search of the same reader counts 1, and with the 10.6.0 and 9.12.3 IndexSearcher defaults a larger probe counts 5010 vs 4010. Hits can be extra or missing. Every release from 8.4.0 to 10.6.0 and main is affected; reporting the Weight as not cacheable once the budget ran out fixes it and passes the sandbox search tests.

The bug (main f794ff5a505c)

#
  1. One budget, smallest segments first. createWeight copies reader.leaves() sorted by term count, smallest first (PhraseWildcardQuery.java:152-153), starts with remainingExpansions = maxMultiTermExpansions (:179), gives each multi-term an even share (:188) and deducts what it used (:205).
  2. Later segments get nothing. collectMultiTermData walks the segments in that order and gives each what is left of the share (:436-458); collectMultiTermDataForSegment ends the walk once the share is used, shouldStopSegmentIteration.value = remainingExpansions == 0; (:516). A segment after that has no term states, so getPhraseMatcher returns null for it (:277-282).
  3. Still reported cacheable. createPhraseWeight returns an anonymous PhraseWeight (:243-321) without an isCacheable override, so PhraseWeight#isCacheable returns true (PhraseWeight.java:162-165). The only override in the class is the reader-independent no-match weight (:229-240).
  4. The cache trusts it. LRUQueryCache's caching weight checks in.isCacheable(context) (LRUQueryCache.java:816, :903), then looks up get(in.getQuery(), cacheHelper) (:834, :921), keyed on the segment core's cache key and the query (:419-427). A reopen shares unchanged segment cores, so the new reader finds the old entry.

The numbers

#
  • Repro. Segment 1 aa x c (3 terms), query "a* x" with limit 1: count 1 through the cache. Add segment 2 ab x (2 terms) and reopen: segment 2 is visited first and takes the expansion ab; uncached count 1, cached count 2 (segment 1's old entry plus segment 2). The cached result used two expansions under a limit of one.
  • Default searcher cache (10.6.0 and 9.12.3, plain new IndexSearcher(reader)): a 20,000-document segment x bNNN ... with 200 b terms (100 documents each), "x b*" with limit 50, run 10 times: 5000. A reopen adds a 10-document segment with 10 new b terms: uncached 4010 (10 expansions to the small segment, 40 to the big one), cached 5010.
  • Missing hits too. The finder's model-based check of the query cache (every operation sequence up to length 3) also found the other direction: a segment's entry cached under a layout in which it got no expansions is served where it gets them, e.g. after two soft deletes and a reopen, cached=[], uncached=[0] on the same reader through IndexSearcher#search (the check searches a ConstantScoreQuery wrapper; count skips the cache on segments with deletions, LRUQueryCache.java:892-895, so this sequence does not show through count). A reopen that drops a fully deleted small segment triggers it too, and so do the ConstantScoreQuery, BoostQuery and DisjunctionMaxQuery wrappers.
Exposure and likelihood526 words
  • Who is hit. Code that builds the class itself: nothing in the Lucene tree outside its own test builds it, and no use was found in Elasticsearch, OpenSearch or Solr code. The limit must bind on the index, and a reopen must change the segment set, as a reopen after a flush of new documents, a merge, or a dropped fully deleted segment does.
  • What goes wrong. Two searches of the same reader return different hit counts and hit sets depending only on cache state, in both directions, with no error, until the entry is evicted or cleared, or no open reader uses that segment core any more. Both are subsets of the true phrase matches; the cached one can match more terms than the documented limit allows.
  • What does not. The limit still bounds the work: every search expands in createWeight, and a cache hit only skips per-segment matching.
  • The query cache, plainly. LRUQueryCache stores one entry per (segment core, query) and reuses it in every reader that shares the core, as its javadoc expects ("these cache and policy instances can be shared across several queries and readers", LRUQueryCache.java:80). This query's result in a segment is not a property of that segment alone: it depends on how much of the budget smaller segments used first. A reopen changes that share, but not the cache key, so the old entry is served.
  • Default cache on released versions. On 9.x and 10.x every IndexSearcher has a default LRUQueryCache (IndexSearcher.java:95-99 on 10.6.0) that caches a query seen 5 times (UsageTrackingQueryCachingPolicy.java:127 on 10.6.0) on large segments: since 9.6.0, a segment of at least 10,000 documents that holds more than half the average documents per segment (LRUQueryCache.java:175-176, :190, :194-196 on 10.6.0); on 9.0.0 to 9.5.0, at least 10,000 documents and at least 3% of the index (LRUQueryCache.java:150 on 9.0.0). The probe meets both rules: executed, 5010 vs 4010. Main has no default cache (IndexSearcher.java:82-84), so there the application installs one.
  • Related, separate bug. The class's equals/hashCode ignore the limit (PhraseWildcardQuery.java:323-334), so two limits share one cache entry. The recommended fix also stops most of these collisions, since a query whose wildcard used up its share is no longer cached, but not all: when the limit is below the number of wildcards, the first wildcard's share is 0 (:188) and createWeight returns the cacheable no-match weight (:198-202, :229-240), which still shares one entry with an equal query of a larger limit. Fact check, fix applied, assertions on and off: one segment aa bb, a* b*, limits 1 and 100, one shared always-cache LRUQueryCache: cached 1 vs uncached 0, and in the other order 0 vs 1, as on stock; with fix (b) both orders agree. That bug needs its own fix, and that fix alone leaves the earlier form of this test failing.
  • Scale. Two one-document segments with an always-cache policy; with the default cache, one segment of 10,000+ documents that is large next to the others and five uses of the query. Silent, with assertions on and off.

Why it looks unintended

#
  • SegmentCacheable: objects that are not segment-immutable "should return false"; QueryCache#doCache promises an equivalent weight when scores are not needed.
  • The class expects to be a query-cache key (its javadoc, about the key, not per-segment results).
  • Lucene's join module turns caching off for the same kind of reader dependence (GlobalOrdinalsQuery).
The full argument224 words
  • The contract. SegmentCacheable: "Objects that are not segment-immutable, such as those that rely on global statistics or scores, should return false" (SegmentCacheable.java:34-35). QueryCache#doCache: "The returned weight will only be equivalent if scores are not needed" (QueryCache.java:28-30); a count needs no scores.
  • The class expects to be cached. The PhraseTerm javadoc says the query "is immutable and light itself and can be used safely as a key of the query cache" (PhraseWildcardQuery.java:676-680). That is about the query object as a key, not a promise about per-segment results; the contract above is what decides.
  • Precedent. GlobalOrdinalsQuery and GlobalOrdinalsWithScoreQuery return false: "disable caching because this query relies on a top reader context" (the comment gives a second reason too: a bitset of ordinals the cache cannot account for) (GlobalOrdinalsQuery.java:200-204, GlobalOrdinalsWithScoreQuery.java:237-241; LUCENE-8062 #9110, LUCENE-9022 #10065).
  • History. The smallest-first sort, the shared budget and the missing override all come from the introducing commit (8485b5a939c, LUCENE-8983) and are unchanged; PhraseWeight#isCacheable returning true comes from LUCENE-8249 (7d9059ef13d, 2018) and is right for PhraseQuery. The issue and PR discussion (#10026, apache/lucene-solr#889) never mention caching. TestPhraseWildcardQuery (11 tests) searches one fixed reader through newSearcher, which may install a random LRUQueryCache, but never reopens it, so no test shares a cache across a reopen.
The devil's-advocate check159 words

Strongest case for "intended": with a binding limit the result is already an approximation that moves with the segment layout. The class documents a budget "across all segments" (PhraseWildcardQuery.java:61-67, :585-592); jpountz noted on #14168 (2025) that a low maxMultiTermExpansions may "miss matches (possibly all of them)", and called the per-segment optimizations "fragile" on apache/lucene-solr#889. So a cached result could be called one more layout-dependent truncation; and the class is @lucene.experimental.

Why it fails: the documented dependence is between different readers; here one reader gives two answers depending only on whether an entry was cached, which QueryCache#doCache and SegmentCacheable rule out. The cached answer is not any budget-respecting result on that reader either: it uses two expansions under a limit of one. "Experimental" allows API changes, not a cache that changes results. An independent reviewer from another model family (OpenAI GPT-5.6) rated the "intended" case weak, and the intended-behaviour verifier found that no intended-behaviour argument holds.

Suggested fix

#

Recommended (a) Not cacheable once the budget ran out (recommended, validated)

Record in createWeight when a wildcard used up its share of the budget, and let the Weight report isCacheable false only then (+16 lines), so caching stays on when the limit never binds. The repro passes, as do TestPhraseWildcardQuery (11 tests, assertions on and off) and the sandbox search test package (115 tests).

// createWeight, after a multi-term's collectTermData:
if (numExpansions == maxExpansionsForTerm) {
  // The expansion budget ran out: what a segment got depends on the other segments.
  termsData.expansionBudgetReached = true;
}

// createPhraseWeight's PhraseWeight:
@Override
public boolean isCacheable(LeafReaderContext ctx) {
  return termsData.expansionBudgetReached == false;
}

// TermsData: protected boolean expansionBudgetReached;

(a) Not cacheable once the budget ran out (recommended, validated)

#

+16 lines in PhraseWildcardQuery.java. A conservative test, not exact detection: the segment walk stops early (:516) only once a wildcard has used its whole share, so numExpansions == maxExpansionsForTerm covers every such case; it also fires when the share runs out exactly at the last available term, when nothing was cut (:498-516). When no wildcard used its whole share, every segment got all its expansions, its result is its own, and caching stays on.

// createWeight, after a multi-term's collectTermData:
if (numExpansions == maxExpansionsForTerm) {
  // The expansion budget ran out: what a segment got depends on the other segments.
  termsData.expansionBudgetReached = true;
}

// createPhraseWeight's PhraseWeight:
@Override
public boolean isCacheable(LeafReaderContext ctx) {
  return termsData.expansionBudgetReached == false;
}

// TermsData: protected boolean expansionBudgetReached;

Trade-offs

  • Conservative: also off when the share runs out exactly at the last available term (correctness-safe).
  • Adds a field to the protected TermsData class; package-private would do.
  • A query whose wildcard used up its share is not cached, which removes most of the cache collisions of the separate equals/hashCode bug, but not the no-match case of a limit below the number of wildcards; (b) removes them all.

(b) Never cacheable, as the join module does (validated by the checks)

#

+6 lines: isCacheable returns false on the PhraseWeight from createPhraseWeight.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  // The budget spans all segments, so a segment's matches depend on the others.
  return false;
}

Trade-offs

Simplest, but loses caching even when the limit never binds, the common case with a generous limit (the bounded check keeps only 46,656 of 388,800 segment results cacheable, the no-match ones). It also removes every cache collision of the separate equals/hashCode bug (fact check: both orders agree).

What the checks validated

The repro passes (-da), TestPhraseWildcardQuery 11 of 11 (on), checkGoogleJavaFormat passes (gradle, same worktree).

(c) Set the same flag inside collectMultiTermData

#

Set expansionBudgetReached where collectMultiTermData stops the segment walk.

Trade-offs

Equivalent in the bounded check (identical counts) and 40 random seeds of the earlier form of the test pass with it, but a subclass that overrides that protected method would bypass it; (a) sits in createWeight, which every path goes through.

Downstream note

#

Downstream, a filter or exclusion built from this query can silently match a different set of documents when served from the cache. It arises from the application's own query, limit and cache setup; someone who can add documents can shift the segment layout, but only changes this query's hit set, which stays a subset of the true phrase matches.

How it was found

#

Semi-formal: reading isCacheable overrides against the SegmentCacheable contract, with public-API probes and a model-based check of the query cache, then a bounded-exhaustive check on the stock jar: of 388,800 segment checks over small two-segment readers, 26,480 matched differently inside the reader than alone while reported cacheable.

The method in full82 words

Method: translation validation, bounded and exhaustive. For every two-segment reader in scope, each segment's matches inside the reader were compared with the same segment searched alone, where both weights report isCacheable. The shortest counterexample: two identical one-document segments a b<3-byte term> with limit 1; the second segment matches nothing in the pair and its document alone.

With the recommended fix the check finds 0 violations while 169,088 segment results stay cacheable. The finding was reduced to the one-test JUnit shown here.

LFV-1471, snapshot of 2026-11-10

Registry title
Sandbox PhraseWildcardQuery's Weight reports isCacheable true although its one expansion budget is spent across all of the reader's segments (smallest first), so after a reopen changes the segment set a query cache returns hits that differ from an uncached search on the same reader (since 8.4.0)
Area
sandbox / search: PhraseWildcardQuery (PhraseWeight#isCacheable) and the query cache
Priority
Low, rank 936: When its expansion limit binds, a sandbox PhraseWildcardQuery served from a query cache after a reopen that changes the segment set can return extra or missing hits compared with an uncached search of the same reader, in every release since 8.4.0 (on 9.x and 10.x the default searcher cache is enough) and on main with an installed cache. It is Low with minor impact because a binding limit already makes the uncached result depend on segment layout, so the harm is cached and uncached searches disagreeing, and it needs the hand-built sandbox query with a limit that binds.
Impact class
minor
Impact note
Applications that build the sandbox (@lucene.experimental) PhraseWildcardQuery with an expansion limit small enough to bind, keep a query cache across reopens and reopen into a different segment set (a new flush, a merge, or a fully deleted segment that is dropped) get per-segment hits that were computed under the old segment set, with no error: extra hits (2 instead of 1 in the repro) or missing ones, for as long as the entry stays cached; on the 9.x and 10.x releases the default IndexSearcher query cache and caching policy are enough (zero-configuration witness on 10.6.0 and 9.12.3: a 20,000-document segment, the query repeated 10 times, cached 5010 vs uncached 4010), on main only an application-installed cache (main has no default query cache); ordinary scale.
Summary
You build new PhraseWildcardQuery.Builder("f", 1).addMultiTerm(new PrefixQuery(new Term("f", "a"))).addTerm(new Term("f", "x")).build(), count it through an LRUQueryCache on a one-segment reader whose segment holds 'aa x' (count 1), then add a smaller segment holding 'ab x' and reopen. You expect the cached count on the reopened reader to equal the uncached count on that reader (1: the one allowed expansion is spent on the smaller new segment first, as documented), because a weight whose per-segment result depends on the other segments must not report itself cacheable (SegmentCacheable). Instead the query's Weight inherits PhraseWeight#isCacheable == true, the cache reuses the old segment's entry computed when it was the only segment, and the cached count is 2 (in the other direction a segment can also lose its hits).
