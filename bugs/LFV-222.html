A MUST_NOT clause next to a scoring block-join query is checked on the child documents, so excluded parents come back

The bug in 30 seconds

#

Since #16669, Lucene runs MUST x, MUST_NOT y by handing x a per-window set of allowed documents. A scoring block join applies that set to its children, not to the parents it returns.

Background

#
  1. Block join. Each parent is indexed right after its children, in one addDocuments block. ToParentBlockJoinQuery matches children and returns their parents; with ScoreMode Avg, Max, Min or Total the parent's score comes from its matching children.
  2. Bulk scoring. A BulkScorer scores a range of doc IDs and receives acceptDocs, "the allowed documents to match". Until 10.6 that was always the live (not deleted) documents, and a valid block-join index deletes whole blocks.
  3. Since #16669. ReqExclBulkScorer, which runs MUST x, MUST_NOT y, works in 4,096-document windows and passes "live and not matching y" to x's bulk scorer as acceptDocs.

The bug, step by step

#
  1. Index two parent/child blocks with default settings: docs 0-1 are children of p1 (doc 2, visible), docs 3-4 are children of p2 (doc 5, status:hidden). Docs 0 and 3 have skill:java.
  2. Search +ToParentBlockJoinQuery(skill:java, ScoreMode.Avg) -status:hidden and expect [p1]. count() of the same query returns 1, and 10.5.2 returns [p1].
  3. Instead search(q, 10) returns [p1, p2] on main and on the 10.6.0 release candidate, with assertions on or off, for Avg, Max, Min and Total.
  4. Why: since #16669 the MUST_NOT matches reach the join as its set of allowed documents (all but doc 5). The join hands that set to its child scorer, which checks children 0 and 3, both allowed. Parent doc 5 is never checked.
  5. When a block straddles doc 4,096 (6,000 docs in blocks of 3) and its child before the boundary matches, the child check falls below the 4,096-doc window and the search throws: AssertionError with -ea, ArrayIndexOutOfBoundsException: Index -1 with -da. With no matching child there, the excluded parents come back silently instead.

Who is affected

#

Users of main or 10.6 (no release yet) who run a scoring nested search (Avg, Max, Min or Total) as the only required clause next to a MUST_NOT clause or a pure-negative filter such as FILTER(*:* -acl:deny), once the join's child query matches more than about 0.3% of a segment's documents. Default codec and searcher; no deletions needed.

Mechanism, terms and numbers647 words

Since #16669 (main and branch_10_6, listed under 10.6.0), ReqExclBulkScorer runs MUST x, MUST_NOT y in 4,096-document windows and passes "live and not matching y" to x's bulk scorer as acceptDocs. When x is a ToParentBlockJoinQuery with ScoreMode Avg, Max, Min or Total, its BlockJoinBulkScorer forwards that set unchanged to the child scorer (ToParentBlockJoinQuery.java:541, since #13697) and never checks the parents it returns. So a parent excluded by MUST_NOT comes back whenever one of its matching children is allowed ([p1, p2] instead of [p1] in a 6-document repro, while count() says 1), a MUST_NOT that matches only children removes parents, and a block that straddles a window boundary, with a matching child before it, makes the search throw. Default codec and searcher, no deletions needed; every release through 10.5.2 is correct (five run, the others by a source scan).

The code (main 645d4fe14a20)

#
  1. Which scorer runs. With a MUST_NOT clause and a required side costing more than 0.3% of the segment, and exactly one MUST clause and no SHOULD clause, BooleanScorerSupplier takes that clause's own bulk scorer and wraps it in ReqExclBulkScorer (BooleanScorerSupplier.java:203-207, :235-236, :256-265).
  2. What it passes down. Per window [windowMin, windowMin + 4096) it loads the MUST_NOT matches into a bit set, flips it, ANDs in the live docs and calls req.score(collector, windowBits, windowMin, windowMax) (ReqExclBulkScorer.java:59-86). WindowBits.get answers only inside its window: assert index >= windowBase && index < windowEnd (:113-116), although its length() reports the live docs' length, or the caller's max when there are no deletions, not the window end (:85, :119-121).
  3. What the join does with it. A scoring ToParentBlockJoinQuery uses BlockJoinBulkScorer (ToParentBlockJoinQuery.java:166-174; ScoreMode.None uses the default bulk scorer). Its score maps the parent range to the child range [prevParent + 1, lastParent + 1) and calls childBulkScorer.score(wrappedCollector, acceptDocs, prevParent + 1, lastParent + 1) (:533-541). The wrapping collector emits a parent when the next block starts or the batch ends (:586-591, :609-612); nothing tests the parent against acceptDocs.

The repro, step by step

#
  • Six documents: children 0-1 and parent p1 (doc 2), children 3-4 and parent p2 (doc 5, status:hidden); skill:java on docs 0 and 3.
  • Window [0, 4096): the bit set allows docs 0-4 and rejects doc 5. The child scorer asks about docs 0 and 3, both allowed, so p1 and p2 are collected. Doc 5 is never asked about.
  • A MUST_NOT skill:java (children only) rejects docs 0 and 3 instead, so both parents disappear: [] instead of [p1, p2].

The crash

#

In a 6,000-document segment of 3-document blocks whose children all match skill:java, the block of docs 4,095-4,097 straddles the window boundary. In the window [4096, 8192), prevParent is 4,094, so the child range starts at 4,095, one below the window. The child scorer asks acceptDocs only about the children it matches (DocAndFloatFeatureBuffer.java:57); doc 4,095 matches, so WindowBits.get(4095) fails its assertion with -ea, and with -da reads mask bit -1 (ArrayIndexOutOfBoundsException: Index -1 out of bounds for length 64). With only doc 4,095 changed to skill:go, the block still straddles the boundary but nothing below the window is asked: the search returns 2,000 hits, the 1,000 hidden parents included, where count() says 1,000. In large random segments with 2% of children matching, 18 of 20 layouts returned the excluded parents without an exception and 2 threw; with 50% matching, all 20 threw.

Why the other paths are right

#

count(), ConstantScoreQuery and ScoreMode.None build the join with ScoreMode.None (ToParentBlockJoinQuery.java:98), whose default bulk scorer tests acceptDocs on the documents it collects, the parents (Weight.java:296-298). Before #16669, ReqExclBulkScorer passed only the live docs, which agree on children and parents in a valid block-join index, so the forwarding added by #13697 was harmless.

Exposure and likelihood346 words
  • Trigger. A scoring join that, after rewrite, is the only required clause, with no SHOULD clause; a MUST_NOT clause, or a pure-negative filter such as FILTER(*:* -acl:deny), which BooleanQuery.rewrite turns into a MUST_NOT (it drops the *:* FILTER, BooleanQuery.java:387-392, and inlines the rest, :530-560); a join cost above 0.3% of the segment's maxDoc (BooleanScorerSupplier.java:205; the join's cost is its child query's cost, ToParentBlockJoinQuery.java:177-180; the threshold exists only since #16715, and at #16669's own commit any join cost took the bulk path); a search that needs scores, such as the default search(q, n). Default codec, IndexWriterConfig and IndexSearcher, a CheckJoinIndex-valid index, no deletions.
  • Not affected: count(), ConstantScoreQuery, ScoreMode.None and a positive FILTER next to the join (executed); a join used as FILTER (built without scores, so ScoreMode.None) and a second MUST clause next to the join (a conjunction scorer runs instead), by code reading; ToChildBlockJoinQuery (no custom bulk scorer; its MUST join plus MUST_NOT checks in the bounded-exhaustive model, up to 7 documents (8 without deletions), show no mismatch).
  • Effect. Silent wrong results: excluded parents come back with scores and can be the top hit (a search(q, 10) test failed 10 of 10 randomized iterations, each time at an excluded parent that ranks first because all scores tie). At scale: 300 blocks in 6 segments, query cache on, returned 260 parents per scoring mode, 89 of them excluded; count() gave the correct 171. Where a block straddles a 4,096-document window boundary and one of its children before the boundary matches the child query, the request fails instead; without such a match it returns the wrong parents silently. A child-only MUST_NOT removes parents or changes their scores (p1's Total score halved in one test).
  • Versions. No release: main and branch_10_6 (10.6.0 RC1); branch_10x has the same code by reading.
  • Likelihood: plausible. A natural nested-search shape, deterministic once the join is not very selective; a positive filter or second MUST clause next to the join, or ScoreMode.None, avoids it.
  • Not run: concurrent (executor) search, intra-segment partitions, branch_10x builds.

Why it is a bug, not intended

#
  • The class's own comment: "acceptDocs applies (and is checked) only in the parent document space" (ToParentBlockJoinQuery.java:141-142).
  • count(), ScoreMode.None and 10.5.2 return only p1; MUST_NOT clauses "must not appear in the matching documents".
  • #14067 was told checking children is fine because deletions cover whole blocks; since #16669 acceptDocs also carries MUST_NOT matches, which do not.
The full argument311 words
  • The class's own rule. "NOTE: acceptDocs applies (and is checked) only in the parent document space" (ToParentBlockJoinQuery.java:141-142, from 2017). The class javadoc: "You can then use this Query as a clause with other queries in the parent document space" (:56-57); the join package doc: "The resulting query can then be used as a clause in any query that matches parent" (package-info.java:37-38).
  • The contracts. BulkScorer.score: acceptDocs "represents the allowed documents to match" (BulkScorer.java:70-71), and this scorer's matches are parents. Occur.MUST_NOT: clauses that "must not appear in the matching documents ... do not contribute to the score of documents" (BooleanClause.java:58-60); the parent-level case returns documents acceptDocs rejects, and in the child-only case a clause that matches no parent still removes parents and changes their scores.
  • Consistency. The same query gives the right set through count(), ConstantScoreQuery and ScoreMode.None, and on every release through 10.5.2.
  • The crash. WindowBits.length() reports the full length, but get answers only inside its window (ReqExclBulkScorer.java:113-121), so a lookup that Bits allows asserts or reads index -1.
  • Precedent. LUCENE-6588 (#7646, 2015, reported with a patch by Christoph Kaser): ToChildBlockJoinQuery skipped a parent's score when the first child of a block was not in acceptDocs, an acceptDocs that was not block-consistent. jpountz first replied "I don't think we should try to support fine-grained deletion of children documents", then, reminded that the acceptDocs came from a filter, committed the fix as a bug ("I had just forgotten that some child documents could seem deleted because of FilteredQuery"). TestBlockJoin.testParentScoringBug still says "delete documents to simulate FilteredQuery applying a filter as acceptDocs" (TestBlockJoin.java:1539-1541).
  • No test expects it. TestBlockJoin uses MUST_NOT only inside the query a join wraps, never as a clause next to a join; TestReqExclBulkScorer has no join; the #16669 discussion never mentions joins.
The devil's-advocate check161 words

The strongest case: in #14067 (2024), jpountz wrote "Block-joins require deletes to be consistent across parent and child documents. So I wouldn't call it a bug, the implementation should be free to check deletes on child documents or parent documents depending on whichever is more convenient/efficient." So checking children was an accepted design; the join is @lucene.experimental; and a child-only MUST_NOT at the parent level is odd input.

Why it fails: that reply assumed acceptDocs are deletions, which are block-consistent. Since #16669 they also carry MUST_NOT matches, which are not; the BulkScorer javadoc never limited acceptDocs to live docs, the class's own comment says it is checked in parent space, and in LUCENE-6588 the same objection (per-child deletions are unsupported) was dropped once it was clear that a filter applied as acceptDocs need not be block-consistent. @lucene.experimental is about API stability, not wrong results. Lead with the parent-level exclusion and the crash; keep the child-only case secondary. Verdict: not intended.

Suggested fix

#

Recommended Check acceptDocs on parents in BlockJoinBulkScorer (validated)

In BlockJoinBulkScorer.score, pass null acceptDocs to the child scorer and test acceptDocs on each parent before collecting it (+6/-5 lines, essentially the change proposed in #14067). The repro, the window-straddle crash case and all 105 lucene/join tests pass with it.

// BlockJoinBulkScorer.score
BatchAwareLeafCollector wrappedCollector = wrapCollector(collector, acceptDocs);
childBulkScorer.score(wrappedCollector, null, prevParent + 1, lastParent + 1);

// wrapCollector(LeafCollector collector, Bits acceptDocs): in collect() and endBatch()
if (currentParent >= 0 && (acceptDocs == null || acceptDocs.get(currentParent))) {
  in.collect(currentParent);
}

Check acceptDocs on parents in BlockJoinBulkScorer (validated) (validated by the checks) (recommended)

#

In ToParentBlockJoinQuery.BlockJoinBulkScorer, give the child scorer null acceptDocs and pass acceptDocs to the wrapping collector, which tests each parent before in.collect(currentParent) (in collect and in endBatch). Every parent collected lies in [min, max), so the lookup stays inside the WindowBits window.

// BlockJoinBulkScorer.score
BatchAwareLeafCollector wrappedCollector = wrapCollector(collector, acceptDocs);
childBulkScorer.score(wrappedCollector, null, prevParent + 1, lastParent + 1);

// wrapCollector(LeafCollector collector, Bits acceptDocs): in collect() and endBatch()
if (currentParent >= 0 && (acceptDocs == null || acceptDocs.get(currentParent))) {
  in.collect(currentParent);
}

Trade-offs

  • Children of excluded parents are still scored before the parent is dropped, so #16669's push-down does not help this query; no benchmark was run.
  • The child scorer no longer sees the live docs: in an index whose deletions are not whole blocks (unsupported, per #14067) deleted children would count, as they already do on the non-scoring path, whose default bulk scorer checks only the parent (Weight.java:296-298, by code reading).

What the checks validated

  • Scratch worktree of 645d4fe14a20, JDK 25: the minimal test fails on stock and passes with the fix, assertions on and off.
  • The hunt's three tests, including the 6,000-document crash case, pass with the fix (assertions off).
  • The whole lucene/join module with the fix and the test: 105 tests in 17 suites, 3 skipped, 0 failures, assertions on and off; :lucene:join:check -x test (format, ecjLint, forbiddenApis) passes.
  • The bounded-exhaustive model with the fix: 0 mismatches for the ToParent family on every layout up to 5 documents (248,936 checks; stock: only the MUST_NOT mismatches). Earlier: an independent verifier's own fix and the hunt's other repros pass; 9 upstream join test classes (45 tests) pass.
  • Not run: the full Lucene suite, nightly tests, benchmarks.

Translate acceptDocs into child space (untested)

#

Pass the child scorer a Bits that accepts a child when its parent, parents.nextSetBit(child), is accepted. Every such parent lies inside the window.

Trade-offs

Keeps skipping children of excluded parents; costs a nextSetBit per lookup; the same deleted-child semantics as A. Not built.

Apply the exclusion in ReqExclBulkScorer instead (untested)

#

Pass only the caller's acceptDocs to the required clause and apply the window's exclusion mask to what it collects, through a collector wrapper.

Trade-offs

Could address any bulk scorer that maps doc spaces (not built or validated), but gives up #16669's push-down for every query. Making WindowBits answer below its window would remove only the crash, not the wrong results (by code reading).

Downstream note

#

Applications that hide parent documents with a MUST_NOT rule or a pure-negative filter next to a scoring nested query get those parents back: in a 300-block test, 89 of the 260 parents returned were ones the rule excluded.

How it was found

#

An automated bounded-exhaustive check ran every valid single-segment block layout up to 7 documents (8 without deletions), every match set and score mode, through the real queries against a brute-force join (83 million checks). For ToParentBlockJoinQuery only "join MUST plus one MUST_NOT document" failed, in the four scoring modes; the code then showed the cause.

The method in full171 words

Method: bounded-exhaustive translation validation of the block-join queries (BlockJoinTV), on the stock main jar.

  • Every CheckJoinIndex-valid single-segment block layout up to 7 documents with whole-block deletions (79,338,044 checks, assertions on and off) and up to 8 without deletions (3,773,664 checks), times every child and parent match set, every ScoreMode and a plain or two-phase child iterator, against an independent brute-force join.
  • The only failing kind for ToParentBlockJoinQuery was check C8 (BooleanQuery MUST join + MUST_NOT one document): 20,026 result mismatches per scoring ScoreMode, plus score mismatches; ScoreMode.None was clean. 5 seeded mutants were all killed. The same runs also flag other join queries (ToChildBlockJoinQuery, ParentChildrenBlockJoinQuery and ParentsChildrenBlockJoinQuery, in checks C4-C7); those are not this bug.
  • The root cause was then read from ReqExclBulkScorer; the window-straddle crash was found by reasoning about its windows and confirmed by a test. A second hunt unit, modelling ReqExclBulkScorer and scanning the in-tree bulk scorers, found the same bug independently at about the same time (merged into this record).

Bug record

LFV-222, snapshot of 2026-10-29

Registry title
A MUST_NOT clause next to a scoring ToParentBlockJoinQuery is checked against child documents instead of parents, so excluded parents are returned, and the search throws when a parent/child block straddles a 4096-doc window
Area
join / block join (ToParentBlockJoinQuery.BlockJoinBulkScorer) x search / BooleanQuery MUST_NOT bulk scoring (ReqExclBulkScorer, #16669)
Priority
High, rank 4: Since #16669 (main, branch_10_6) a scoring ToParentBlockJoinQuery next to a MUST_NOT clause or pure-negative filter silently returns the excluded parents, or throws when a block straddles a 4096-doc window, with default settings and an ordinary nested-search shape, so like LFV-044 its urgency puts it above the released bugs below although no release has it yet.
Impact class
silent wrong results
Impact note
Applications on unreleased main (11.0.0-SNAPSHOT) or a branch_10_6 / branch_10x build (the future 10.6.0) that run a scoring ToParentBlockJoinQuery (ScoreMode Avg, Max, Min or Total) as the only required clause of a BooleanQuery with a MUST_NOT clause (also a pure-negative filter such as FILTER(: -acl:deny), which BooleanQuery.rewrite turns into one) get back parents the MUST_NOT clause excludes, with the default codec, IndexSearcher and IndexWriterConfig, -ea or -da, on any CheckJoinIndex-valid index once the join's cost exceeds 0.3% of the segment's maxDoc; on segments where a block straddles a 4096-doc window the same search throws instead (AssertionError with -ea, ArrayIndexOutOfBoundsException index -1 with -da), and a MUST_NOT clause that matches only children removes parents or changes their scores; count(), ConstantScoreQuery, ScoreMode.None, a FILTER join and a positive FILTER or MUST clause next to the join are not affected, and no released version (through 10.5.2) is affected.
Summary
You index parent/child blocks and search BooleanQuery(MUST ToParentBlockJoinQuery(skill:java, parentsFilter, ScoreMode.Avg), MUST_NOT status:hidden), expecting only the parents that are not hidden, which is what count() of the same query and ScoreMode.None return. Instead, on main the hidden parent p2 comes back for Avg, Max, Min and Total ([p1, p2] instead of [p1]); a MUST_NOT clause that matches only child documents (MUST_NOT skill:java) removes both parents ([] instead of [p1, p2]); and in a 6,000-doc segment where a block straddles doc 4096 the search throws AssertionError in ReqExclBulkScorer$WindowBits.get with -ea and ArrayIndexOutOfBoundsException (index -1) with -da. The cause is that since #16669 ReqExclBulkScorer folds the MUST_NOT matches of each 4096-doc window into a bit set that it passes to the required clause as acceptDocs, and the join's BlockJoinBulkScorer forwards that acceptDocs unchanged to its child scorer (ToParentBlockJoinQuery.java:541), so the exclusions are tested on child doc IDs, some of them below the window, and never on the parents it collects.
