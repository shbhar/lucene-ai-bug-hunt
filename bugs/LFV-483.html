DateRecognizerFilterFactory shares one DateFormat across threads, so concurrent analysis throws NumberFormatException (since 5.5.0)

An analyzer built from the dateRecognizer filter factory throws NumberFormatException or ArrayIndexOutOfBoundsException on ordinary dates when several threads analyse at once, because the factory gives every thread's filter the same java.text.DateFormat, which is not thread-safe. Affected since 5.5.0; cloning the format in create() fixes it.

The bug in 30 seconds

#

The dateRecognizer filter keeps only tokens that parse as a date. Its factory builds one java.text.DateFormat and passes the same object to the filter of every thread. DateFormat keeps its parse state inside itself and is not thread-safe, so two threads parsing at once corrupt each other's parse, and the exception escapes analysis.

  1. Build an analyzer with CustomAnalyzer: the whitespace tokenizer plus the dateRecognizer filter with datePattern=yyyy-MM-dd, as the factory javadoc shows. On one thread, 2024-01-15 foo 1999-12-31 bar 2001-07-04 baz 1970-01-01 keeps the 4 dates.
  2. Analyse that text from 4 threads at once with the same analyzer, as an IndexWriter's indexing threads do. You expect the 4 dates every time: Analyzer gives each thread its own copy of the filter.
  3. Instead some analyses throw NumberFormatException (multiple points, For input string: "202420024024E202420024024E4") or ArrayIndexOutOfBoundsException: 127 to 249 of 200,000 analyses (4 threads x 50,000, the diagram probe's shorter text 2024-01-15 foo 1999-12-31) per run on main, and a 4-thread test failed in 50 of 50 JVM launches.
  4. The cause: the factory creates one DateFormat and hands that same object to every thread's filter. Two parses at the same moment mix up its internal state, such as the digit buffer of its number parser, and the filter catches only ParseException.
  5. With IndexWriter, that addDocument call throws and the document is not indexed: 3 to 62 of 200,000 concurrent calls per run (the diagram probe), while the writer stays open. One thread, or the filter's public constructor with one DateFormat per thread, works.

Who is affected

#

Applications that build an analyzer with the opt-in dateRecognizer factory (CustomAnalyzer, the SPI name or a Solr-style schema) and use it from more than one thread: any IndexWriter with several indexing threads, or concurrent query parsing. Ordinary dates trigger it, with assertions on or off, on every release since 5.5.0.

Mechanism, terms and numbers813 words

DateRecognizerFilterFactory (SPI name dateRecognizer) builds one java.text.DateFormat in its constructor (DateRecognizerFilterFactory.java:53, :60) and create() passes that same object to every DateRecognizerFilter it creates (:72-74). An Analyzer keeps one set of components per thread (Analyzer.java:91-96), so CustomAnalyzer calls create() once per thread on the same factory (CustomAnalyzer.java:161-168) and every thread's filter parses with the one shared format. The JDK documents DateFormat as not synchronized. When two threads parse at once, DateFormat.parse throws NumberFormatException (multiple points, For input string: "") or ArrayIndexOutOfBoundsException (and, in one launch each on 9.0.0 and 9.12.3, a single ClassCastException), and DateRecognizerFilter.accept() catches only ParseException (DateRecognizerFilter.java:50-61), so the exception escapes incrementToken(). With an IndexWriter, whose indexing threads share one analyzer, that addDocument throws and the document is not indexed; in every run with assertions off the writer stayed open. No special input or scale is needed, and it fails with assertions on and off. It fails on all 10 releases run, from 5.5.0 to 10.5.2, and on main; the code is unchanged since 5.5.0. Passing (DateFormat) dateFormat.clone() in create() fixes it; with that change all of :lucene:analysis:common:test passes (1,911 tests, 18 skipped, 0 failures).

Terms

#
  • DateRecognizerFilter: a token filter in lucene/analysis/common that keeps a token only if a java.text.DateFormat can parse it ("Filters all tokens that cannot be parsed to a date"). DateRecognizerFilterFactory builds it by name (dateRecognizer) for CustomAnalyzer or a Solr-style schema, with optional datePattern and locale arguments.
  • Per-thread components: an Analyzer builds its tokenizer and filters once per thread and reuses them (Analyzer.java:91-96, a CloseableThreadLocal). CustomAnalyzer builds them by calling create() on the same factory objects in every thread (CustomAnalyzer.java:161-168).
  • DateFormat: the JDK's date parser. Its class javadoc says: "Date formats are not synchronized. It is recommended to create separate format instances for each thread."

The bug

#
  1. The factory builds one format in its constructor: private final DateFormat dateFormat; (DateRecognizerFilterFactory.java:53), this.dateFormat = getDataFormat(get(args, DATE_PATTERN)); (:60). getDataFormat (:84-90) returns a SimpleDateFormat for datePattern, else DateFormat.getDateInstance(DateFormat.DEFAULT, locale).
  2. create() passes that same object to every filter: return new DateRecognizerFilter(input, dateFormat); (:72-74). The filter keeps the reference (DateRecognizerFilter.java:42-48).
  3. So with an analyzer used by 4 threads, 4 filters share one DateFormat. The state the race damages is mainly a Calendar and a NumberFormat, the two fields DateFormat.clone() deep-copies (JDK source; SimpleDateFormat.parse also writes a few minus-sign fields in a one-time setup). The JDK's DecimalFormat collects the digits of each number field in one buffer and hands them to Long.parseLong or Double.parseDouble, which is consistent with the garbled strings seen, such as 202420024024E202420024024E4.
  4. accept() (DateRecognizerFilter.java:50-61) calls dateFormat.parse(...) and catches only ParseException, so the NumberFormatException or ArrayIndexOutOfBoundsException escapes incrementToken().
  5. At index time an exception from the token stream is non-aborting: the document is marked deleted (IndexingChain.java:1989-1994, DocumentsWriterPerThread.java:302-307), addDocument throws, and the writer stays open. At query time, building the query fails.

Exposure and likelihood295 words
  • Who is exposed. Users of the dateRecognizer factory: through CustomAnalyzer, the SPI name, or a Solr-style schema such as the factory javadoc's own example. No Lucene analyzer adds it by default, and a read-only code search of Solr, Elasticsearch and OpenSearch found no default configuration that uses it.
  • What it takes. More than one thread using the analyzer: IndexWriter is "completely thread safe" and its indexing threads share the one analyzer of its config (IndexWriter.java:167-168); concurrent query analysis does the same. No special input: with datePattern, any date-shaped token can race; with no datePattern, the default format needs a tokenizer that keeps spaces (keyword): a whitespace token has no ordinary space, so it does not match Jan 15, 2024 (a date written with non-breaking spaces stays one token and does parse on JDK 25).
  • What the damage looks like. An unchecked exception reported to the caller: the document is rejected (marked deleted, other documents indexed, the writer stays open), or the query cannot be built. The caller can retry. No silent wrong tokens were seen. These are observations on JDK 25 with the tested configurations; another JDK could fail differently, for example with an Error, on which IndexWriter closes itself (IndexWriter.java:162-165).
  • Not affected. Single-threaded use, and the filter built through its public constructor with one DateFormat per component.
  • Scale and rate. No data volume needed. Per operation it is rare: in the recorded runs that failed, from about 15 per million (3 of 200,000 addDocument calls) to 0.53% (1,065 of 200,000 analyses), depending on load and configuration, and some runs saw none. Even so, a 4-thread test fails in every launch.
  • How likely. Plausible (registry): ordinary multi-threaded use of an opt-in filter; no report in ten years.

Why it is a bug, not intended

#
  • Analyzer keeps "the same set of components per-thread", and IndexWriter shares one analyzer across its threads: create() output is meant to run concurrently.
  • JDK: "Date formats are not synchronized." The factory hides its instance, so users cannot synchronize it.
  • PhoneticFilterFactory builds a new encoder per create() ("Must be thread-safe"); DateTools keeps per-thread copies.
The full argument282 words
  • create() output runs on many threads by design. Analyzer.java:93-96 ("reusing the same set of components per-thread"), CustomAnalyzer.java:161-168 (one create() per thread on shared factories) and IndexWriter.java:167-168 ("completely thread safe, meaning multiple threads can call any of its methods, concurrently").
  • The JDK contract. "Date formats are not synchronized. It is recommended to create separate format instances for each thread. If multiple threads access a format concurrently, it must be synchronized externally." The factory creates the format privately and never exposes it.
  • Lucene's tests expect it. BaseTokenStreamTestCase.checkRandomData repeats the same analysis in 2-4 threads: "we do the EXACT same thing we did before in each thread, so this should only really fail from another thread if it's an actual thread problem" (BaseTokenStreamTestCase.java:1086-1089). The nightly TestFactories runs it on every SPI factory it can build without arguments, dateRecognizer included, but behind a whitespace tokenizer, whose tokens practically never parse with the default format.
  • Sibling code. PhoneticFilterFactory.getEncoder(): "Must be thread-safe." "Commons-Codec doesn't offer any thread-safe guarantees so we must play it safe and instantiate every time." (PhoneticFilterFactory.java:160-164, called from create()). DateTools keeps per-thread clones of its formats (DateTools.java:55-61; :192 "should be cloned before use, since it's not threadsafe").
  • Precedent. LUCENE-940 (#2015, 2007, "SimpleDateFormat used in a non thread safe manner") and LUCENE-6564 (#7622, 2015, the static shared SimpleDateFormat of PrintStreamInfoStream) fixed a shared SimpleDateFormat as a bug in other components. LUCENE-1472 (#2546) later replaced DateTools' synchronized shared formats with per-thread copies, for performance: those formats were already guarded by a lock.
  • No decision says otherwise. No javadoc restricts the factory to one thread. The introducing issue (LUCENE-6973, #8030, 40 comments) discusses locales and tests, never threads.
The devil's-advocate check187 words

The strongest case for "intended": (a) no javadoc on TokenFilterFactory or this factory promises that create() output is thread-safe, and Analyzer never says "thread-safe" in so many words; (b) the filter's two-argument constructor takes a caller-owned DateFormat, and the JDK says a shared one "must be synchronized externally", so sharing could be called the caller's problem; (c) the default configuration with a whitespace tokenizer practically never parses, so the affected configurations are narrow; (d) nobody reported it in ten years.

Why it fails: (a) the per-thread component design, IndexWriter's shared analyzer, the multi-threaded checkRandomData run on every factory it can build (this one included) and the PhoneticFilterFactory comment all strongly imply that create() output must survive concurrent use (no single javadoc sentence states it); (b) here Lucene's own factory creates the format and hides it, so the user cannot synchronize it; (c) the javadoc's own configuration uses a datePattern, which is enough; (d) the upstream tests never parse dates concurrently and the 2016 review never considered threads. The cross-model reviews, the devil's advocate and the adjudication all rated the intended-behaviour case weak or none.

Suggested fix

#

Recommended A. Clone the DateFormat in create()

Clone the format in create(): return new DateRecognizerFilter(input, (DateFormat) dateFormat.clone());. Each thread's filter then gets its own copy. Validated: the new test passes 10 of 10 repetitions, all of :lucene:analysis:common:test passes (1,911 tests, 18 skipped, 0 failures), and so do the nightly TestFactories and check.

   @Override
   public TokenStream create(TokenStream input) {
-    return new DateRecognizerFilter(input, dateFormat);
+    // DateFormat is not thread-safe: give every filter (one per analysis thread) its own copy
+    return new DateRecognizerFilter(input, (DateFormat) dateFormat.clone());
   }
All options and trade-offs6 options · 610 words

Two options were applied in a scratch worktree of a9779ef3c193 and run through gradle: A with the new test, the module's tests, the nightly TestFactories and check; B with the DateRecognizer tests. The worktree was removed afterwards.

A. Clone the DateFormat in create() (validated by the checks) (recommended)

#

One line in DateRecognizerFilterFactory.create() (DateRecognizerFilterFactory.java:72-74). The factory keeps its instance as a template; every filter gets a deep copy.

   @Override
   public TokenStream create(TokenStream input) {
-    return new DateRecognizerFilter(input, dateFormat);
+    // DateFormat is not thread-safe: give every filter (one per analysis thread) its own copy
+    return new DateRecognizerFilter(input, (DateFormat) dateFormat.clone());
   }

Trade-offs

  • One clone per create() call, not per token or document. With CustomAnalyzer (Analyzer's default GLOBAL_REUSE_STRATEGY) that is once per thread and analyzer; PER_FIELD_REUSE_STRATEGY builds one chain per thread and field, and direct callers of the factory get one copy per call.
  • DateFormat.clone() deep-copies the calendar and the number format, and SimpleDateFormat.clone() the date format symbols, so the copies do not share the calendar and number-format state that parsing changes (the compiled pattern and the century-start date stay shared; parsing does not change them). This holds for the formats the stock getDataFormat builds; an override that returns a custom DateFormat needs a clone() that copies its mutable state.
  • An invalid datePattern still fails when the factory is built.

What the checks validated

  • TestDateRecognizerFactoryThreads passes with assertions off and on, and all 10 repetitions with -Ptests.iters=10; with TestDateRecognizerFilter and TestDateRecognizerFilterFactory: 5 tests, 0 failures (stock: 1 failure).
  • All of :lucene:analysis:common:test with assertions on: 340 classes, 1,911 tests, 18 skipped, 0 failures, 0 errors.
  • TestFactories with -Ptests.nightly=true passes.
  • :lucene:analysis:common:check -x test passes (checkGoogleJavaFormat, ecjLint, forbiddenApis), with the new test file.
  • Earlier: the finder's test, the independent reproducer's 5 tests (numDocs 40,000 of 40,000) and an IndexWriter test pass with the same change; the adjudication's re-run passed 5 of 5.

B. Build a new DateFormat in every create() (validated by the checks)

#

Keep the pattern instead of the format, call getDataFormat(datePattern) in create(), and call it once in the constructor too so an invalid pattern still fails early.

Trade-offs

With the stock getDataFormat the same effect as A, with a few more changed lines and a little more work per create() (the pattern is parsed again). B calls a subclass's override of getDataFormat on every create(), while A clones the result the constructor got from it; an override that returned the same instance every time would bring the race back under B, not under A.

What the checks validated

  • TestDateRecognizerFactoryThreads, TestDateRecognizerFilter and TestDateRecognizerFilterFactory pass with assertions off and on (5 tests, 0 failures). The module suite, check and repetitions were run only for A.

C. Copy the format in DateRecognizerFilter's constructor

#

this.dateFormat = (DateFormat) dateFormat.clone() in DateRecognizerFilter.java:42-48.

Trade-offs

Also protects callers of the public two-argument constructor who share one instance, but changes that constructor's semantics (the filter no longer uses the caller's object). A design decision; not tried.

Not recommended: synchronize parse()

#

Lock the shared format around parse in accept().

Trade-offs

Serializes every analysis thread on one lock; Lucene replaced exactly that in DateTools with per-thread copies (LUCENE-1472). A ThreadLocal would work, but a copy per filter already is one per thread.

Not recommended: catch RuntimeException in accept()

#

Treat any exception from parse as "not a date".

Trade-offs

Turns the race into silent dropping of valid dates, which is worse than an exception.

Out of scope: switch to java.time.format.DateTimeFormatter

#

The JDK's immutable, thread-safe alternative.

Trade-offs

An API change (the public constructor takes a DateFormat) and different, stricter default parsing; not a bug fix.

Downstream note

#

An application that shares one analyzer with this filter across request threads, as IndexWriter does across its indexing threads, would reject documents and fail queries the same way (inferred from the code; no downstream product was run).

How it was found

#

A static inventory of every analysis factory's constructor and create() flagged that this factory hands an object it owns to every filter. A concurrency differential over 210 factory configurations, single-threaded versus 3-8 threads on one analyzer, then found it as the only mismatch; the finder reduced it by hand to a public-API test.

The method in full147 words

Method: a concurrency stress differential (registry tier semi-formal: a hypothesis from a static inventory, witnessed by a differential, not by a formal tool).

  • The hunt unit compared every SPI analysis factory with the public constructor it wraps. A static inventory extracted the constructor and create() bodies of all 167 SPI factory registrations; reading the factory fields showed that DateRecognizerFilterFactory passes one factory-owned DateFormat to every filter.
  • A concurrency differential then ran every constructible factory configuration (210) on the stock main jars: the tokens of a single-threaded run against 3-4 concurrent threads on the same analyzer locally, and 8 on separate build machines. 209 configurations were clean; this was the only mismatch.
  • The finder reduced it to the public-API JUnit with a per-component control, measured the hit rate (50 of 50 JVM launches with assertions on and off) and the exception kinds, and checked the one-line clone fix.

DateRecognizerFilterFactory gives every filter it creates the same java.text.DateFormat, so an analyzer built from it throws NumberFormatException or ArrayIndexOutOfBoundsException when several threads analyse text at the same time
Area
analysis / analysis-common miscellaneous filters (DateRecognizerFilterFactory, DateRecognizerFilter)
Priority
Medium, rank 198: Ordinary multi-threaded indexing or query analysis with the opt-in dateRecognizer factory sometimes throws and leaves that document unindexed, which is plausible in use but loud, so it joins the loud documented-usage rows right after LFV-349.
Impact class
crash
Impact note
Applications that build an analyzer with the opt-in dateRecognizer factory (CustomAnalyzer, the SPI name, or a Solr-style schema as in the factory javadoc) and use it from several threads at once, that is concurrent IndexWriter indexing threads or concurrent query-time analysis, get occasional unchecked NumberFormatException or ArrayIndexOutOfBoundsException out of analysis on ordinary date tokens: that addDocument call throws and the document is not indexed (the writer stays open with -da), or the query cannot be built; it needs no scale and no special input, happens with -ea and -da on default JVM settings, and is in every release since 5.5.0. Each analysis fails rarely (from a few per million to about 0.5% of analyses, depending on load and configuration), but the finder's 4-thread JUnit failed in 50 of 50 JVM launches with -ea and with -da, and the 4-thread x 50,000-analysis history repro in 3 of 3 launches on every release tried. The default format (no datePattern) is reached only with a tokenizer that keeps spaces, such as the keyword tokenizer. No silent wrong tokens were seen. Single-threaded use, and the filter built through its public constructor with its own DateFormat, are not affected.
Summary
You build an analyzer with CustomAnalyzer from a whitespace tokenizer and the dateRecognizer filter (datePattern=yyyy-MM-dd, locale=en-US) and analyse text such as '2024-01-15 foo 1999-12-31' from four threads at once, as IndexWriter does with its indexing threads. You expect every thread to get the same date tokens as a single-threaded run, because Analyzer gives each thread its own set of token stream components. Instead some analyses throw NumberFormatException ('multiple points', 'For input string: ""') or ArrayIndexOutOfBoundsException, because DateRecognizerFilterFactory creates one java.text.DateFormat, which is not thread-safe, and create() passes that same instance to the filter of every thread.
