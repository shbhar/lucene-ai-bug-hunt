Distance-feature boosting queries print the caller's default field as their own field: toString() shows "field=" with no name

LongField.newDistanceFeatureQuery("price", ...) and LatLonPoint.newDistanceFeatureQuery("geo", ...) print field= with no name from toString(), and field=other from toString("other"): they print the default-field argument instead of their own field. Results and scores are fine; only logs and debug text are wrong, in every release since 8.0.0.

The finding in 30 seconds

#

A query's toString(String field) may leave out the field you pass; these two queries print what you pass instead of their own field.

Background: how a Lucene query prints itself

#
  1. Every query has toString(String field). The argument is the default field, which the text may leave out; plain toString() passes "". A TermQuery for title:lucene prints title:lucene, or just lucene with toString("title").
  2. LongField.newDistanceFeatureQuery and LatLonPoint.newDistanceFeatureQuery build queries that boost documents by closeness to an origin (a time, a location). They print as ClassName(field=...,origin...,pivotDistance=...).

The finding, step by step

#
  1. Build a recency boost on the field price, LongField.newDistanceFeatureQuery("price", 1f, 0, 1), and print it with toString().
  2. You expect LongDistanceFeatureQuery(field=price,origin=0,pivotDistance=1). toString() passes the default field "", so nothing should be left out, and the sibling LongField.newExactQuery("price", 5) prints price:[5 TO 5].
  3. Instead you get LongDistanceFeatureQuery(field=,origin=0,pivotDistance=1). The method prints its argument field, here "", which hides the query's own field this.field.
  4. With a default field it names the wrong one: toString("other") prints field=other, and a query on size prints the same text as the one on price, though the two are not equal. LatLonPoint.newDistanceFeatureQuery("geo", ...) does the same.
  5. Only the text is wrong: matching, scores, equals and hashCode use this.field.

Who is affected

#

Anyone who logs, prints or debugs a recency or geo-distance boost built by these two factories, alone or inside a BooleanQuery or BoostQuery: every call, default settings, any field name. The log cannot tell which field the boost is on. Results, scores and caching are unaffected.

Mechanism, terms and numbers412 words

Query.toString(String field) takes the caller's default field, the one the text may leave out, and toString() passes "". The two distance-feature boosting queries, built by LongField.newDistanceFeatureQuery (recency) and LatLonPoint.newDistanceFeatureQuery (geo distance), print that argument after field=, because the method parameter field shadows the instance field this.field. So toString() prints field= with no name, toString("other") prints field=other, and two unequal queries on different fields print the same text. The same text appears inside a BoostQuery (weight other than 1) or a BooleanQuery, and in a BooleanQuery explain for a clause that does not match. Matching, scoring, equals, hashCode, the query's own explain and caching are unaffected. One copied line in two classes, in every release since 8.0.0; the fix is this.field.

The code

#
  1. Contract. Query.java:47-50: "Prints a query to a string, with field assumed to be the default field and omitted." Query.java:55-56: toString() returns toString("").
  2. Fix site 1. LongDistanceFeatureQuery.toString(String field) (LongDistanceFeatureQuery.java:87-96) returns getClass().getSimpleName() + "(field=" + field + ",origin=" + .... Inside the method, field is the parameter; the query's own field is this.field (:46, set at :51).
  3. Fix site 2. LatLonPointDistanceFeatureQuery.toString(String field) (LatLonPointDistanceFeatureQuery.java:94-105) is the same expression, copied (this.field at :46).
  4. Wrappers pass the argument on. The factories wrap the query in a BoostQuery when the weight is not 1 (LongField.java:200-207, LatLonPoint.java:369-377); BoostQuery.toString (BoostQuery.java:110-117) and BooleanQuery.toString (BooleanQuery.java:649, :652) pass their argument to the inner query. The factories' javadoc recommends using the query as a SHOULD clause of a BooleanQuery (LongField.java:197-198). BooleanWeight.explain quotes a clause's toString() for a prohibited clause that matches and for a required or optional clause that does not (BooleanWeight.java:88, :99, :103).
  5. Nothing else uses the parameter. equals and hashCode use this.field (LongDistanceFeatureQuery.java:60-77, LatLonPointDistanceFeatureQuery.java:72-91), and so does the weights' own explain (:109-113, :118-122).

Why it looks unintended

#
  • Query.toString(String field) documents the argument as the default field to omit; these methods print it as the query's own field.
  • The same author's earlier FeatureQuery (same (field= format) prints its own field; LatLonPointDistanceQuery prints this.field unless it equals the argument.
  • No test or CHANGES entry pins the text, and upstream accepted the same fix in other classes (LUCENE-9401, LUCENE-9073).
The full argument189 words
  • The contract. Query.java:47-50: "Prints a query to a string, with field assumed to be the default field and omitted." Printing the argument where the query's field belongs is the opposite of omitting it.
  • The siblings. FeatureQuery (Adrien Grand, LUCENE-8197, 2018-03-20, six months before LUCENE-8340 by the same author) prints "FeatureQuery(field=" + fieldName (FeatureQuery.java:162-170); LongDistanceFeatureQuery uses the same format, but its instance field is called field, so the parameter shadows it. LatLonPointDistanceQuery.toString prints this.field unless it equals the argument (LatLonPointDistanceQuery.java:370-383).
  • Tests and history. No test under lucene/*/src/test contains DistanceFeatureQuery(field, and the stock TestLongDistanceFeatureQuery and TestLatLonPointDistanceFeatureQuery never call toString. The creating issues LUCENE-8340 (#9387) and LUCENE-8482 (#9528) never discuss toString; no CHANGES or MIGRATE entry mentions it.
  • Precedent. Upstream accepted the same fix in other classes: LUCENE-9401 (#10441, ComplexPhraseQuery, a bug fix in 8.7, commit 03a5391e511) and LUCENE-9073 (#10115, IntervalQuery, an enhancement in 8.4, commit eb3a4757ffc) both print the query's field unless it equals the argument. The javadoc sentence itself comes from LUCENE-130 (#1208, 2.0), which rewrote it to say the argument is the default field and is omitted.
The devil's-advocate check177 words

The case for intended: toString is informal debug output (in LUCENE-1819 a committer noted that the javadoc's promise of QueryParser-parsable output had been loosened over the years), both classes are package-private, nobody has complained since 2018, and FeatureQuery always prints its field too, so even the smallest fix (A) does not omit the default field.

Why it fails: the text comes from a public method whose argument has a documented meaning, and these two methods print the argument where the query's own field belongs. The same author's earlier FeatureQuery and the package's other queries print their own field, no test or note asks for the current text, and upstream accepted the same fix for ComplexPhraseQuery and IntervalQuery. Fix A corrects which field is named; fix B also omits the default field. The executed cross-model review (OpenAI GPT-5.6, refute lens) rated the intended-behaviour argument weak; a later cross-model fact check of this doc rated it moderate, for the reasons above. A maintainer may still call it trivial; that is a fair outcome for a Low bug.

How it was found

#

A proof-obligation audit of the Query.toString(String field) contract of the two classes: the text must name the query's field unless it equals the argument. Both methods fail the obligation, and a one-test JUnit on the stock jars witnessed it.

The method in full99 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder took the Query.toString(String field) javadoc (the argument is the default field, to be omitted) as the obligation for both methods and checked each against the code: both print the parameter, which shadows this.field.
  • The finder then wrote the public-API JUnit test and the this.field fix that makes it pass.
  • An independent reproducer, the refute-lens cross-model review and a devil's-advocate verifier reproduced it with their own tests, and an adjudication re-ran the reproducer's test with a new seed ("Prior reports, history and checks").
