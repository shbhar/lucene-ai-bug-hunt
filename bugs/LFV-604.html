Multi-term interval queries skip the positions check and silently return wrong hits (usually none) on a field without positions

On a field indexed without positions, an interval query built from Intervals.term leaves throws as documented, but the same query built from Intervals.prefix, wildcard, regexp, fuzzyTerm, range or multiterm leaves runs on fake positions and silently returns wrong hits, usually none. Every release since 8.0.0 is affected.

The finding in 30 seconds

#

Interval queries need word positions. Lucene checks that a field has them for plain term leaves, but not for multi-term leaves.

Positions and interval queries

#
  1. A text field can be indexed at several levels (IndexOptions): DOCS records which documents hold a word, DOCS_AND_FREQS adds how often, DOCS_AND_FREQS_AND_POSITIONS adds where (in "alpha beta", alpha is word 0 and beta word 1).
  2. Positional queries need those positions: PhraseQuery, span queries and interval queries (IntervalQuery with Intervals.ordered, phrase, unordered, containing, ...). On a field without them, the IndexOptions javadoc says they throw an exception.
  3. Interval leaves come in two kinds: Intervals.term("alpha") for one word, and multi-term leaves such as Intervals.prefix("alph") that expand to every matching word of the index.

The finding, step by step

#
  1. Index one document, body = "alpha beta", with IndexOptions.DOCS_AND_FREQS: Lucene stores which documents hold each word and how often, but not where (alpha is word 0, beta word 1).
  2. Search ordered(term("alpha"), term("beta")), "alpha, then beta". Lucene throws IllegalArgumentException: ... because it has no indexed positions, as the IndexOptions javadoc promises for positional queries.
  3. Write the same query as ordered(prefix("alph"), prefix("bet")); the prefixes expand to exactly alpha and beta. You expect the same exception.
  4. Instead it runs. Both words are reported at position -1, so "beta starts after alpha ends" (-1 after -1) never holds: 0 hits, no error. containing and overlapping err the other way and match documents they should not.
  5. Every interval query whose leaves are all prefix, wildcard, regexp, fuzzy or range leaves skips the check, also through the query parser's fn:wildcard; a plain term leaf in the query usually makes it throw (it throws once it is evaluated).

Who is affected

#

Applications that run interval queries built only from prefix, wildcard, regexp, fuzzy, range or automaton leaves, directly or through the flexible query parser's fn:wildcard and fn:fuzzyTerm, on a field indexed without positions, such as a StringField or a TextField with reduced index options. A schema mistake that Lucene documents as an error for positional queries goes unnoticed.

Mechanism, terms and numbers594 words

On a field indexed without positions (IndexOptions.DOCS or DOCS_AND_FREQS), positional queries are documented to throw. Interval leaves made with Intervals.term do. The multi-term leaves (Intervals.prefix, wildcard, regexp, fuzzyTerm, range, multiterm, all built on MultiTermIntervalsSource) never call Terms#hasPositions(): they run the interval logic on the position -1 that the postings return for every occurrence. On one document alpha beta, ordered(prefix("alph"), prefix("bet")) returns 0 hits with no error where ordered(term("alpha"), term("beta")) throws. The check was lost when LUCENE-8646 added multi-term interval leaves in 8.0.0 (2019); every release since, through 10.6.0, and main are affected.

The check that exists

#

TermIntervalsSource.intervals() reads the field's Terms, returns null if the field is missing, then throws IllegalArgumentException("Cannot create an IntervalIterator over field ... because it has no indexed positions") when terms.hasPositions() is false (TermIntervalsSource.java:54-59), and only then calls its static helper intervals(term, te) (:64, :67). matches() does the same (:151-156, helper at :164). PayloadFilteredTermIntervalsSource has the same check (:51, :157).

The check that is missing

#

Intervals.prefix, wildcard, regexp, range and multiterm return a MultiTermIntervalsSource (Intervals.java:176-180, :206-208, :237-241, :279-295, :369-370); fuzzyTerm goes through multiterm (:335-341). Its intervals() (MultiTermIntervalsSource.java:57-77) reads Terms, returns null for a missing field, and goes straight to automaton.getTermsEnum(terms) and TermIntervalsSource.intervals(term, te) for each expanded term (:64, :68). Its matches() (:79-103) calls TermIntervalsSource.matches(te, doc, field) (:90). Neither calls hasPositions().

Fake positions

#

The helper asks the postings for positions (TermIntervalsSource.java:68). The default postings reader grants them only when the field has them (Lucene104PostingsReader.java:420) and otherwise returns -1 from nextPosition() (:1293-1296), as PostingsEnum.nextPosition documents ("or -1 if positions were not indexed", PostingsEnum.java:84-88). -1 is also the value IntervalIterator uses for "not positioned yet" (IntervalIterator.java:31-33).

ordered needs each leaf to start after the previous one ends: it skips beta intervals while currentStart <= prevEnd (OrderedIntervalsSource.java:131, :145-151). With alpha ending at -1 and every beta starting at -1, no beta qualifies and the document does not match. Other operators turn the same coinciding -1 positions into other answers.

In a tree that mixes both kinds, leaf order matters: ordered and unordered build their sub-iterators in order and return null at the first leaf that returns null (MinimizingConjunctionIntervalsSource.java:42-52; ConjunctionIntervalsSource.java:47-57 likewise), and a multi-term leaf returns null when it expands to nothing in the segment (MultiTermIntervalsSource.java:73-75). So a term leaf throws only once it is reached: ordered(prefix("zzz"), term("beta")) returns 0 hits with no error, while ordered(term("beta"), prefix("zzz")) throws.

Exposure and likelihood171 words
  • Who is hit. Users of the opt-in, experimental intervals API (package-info.java:21) whose query has only multi-term leaves and whose field has no positions. The flexible StandardQueryParser reaches it through fn:wildcard and fn:fuzzyTerm (intervalfn/Wildcard.java:38-40, FuzzyTerm.java:44).
  • What goes wrong. No error: positional shapes return no hits, containment shapes return documents their positional meaning excludes, a lone multi-term leaf returns the documents that hold an expanded word. The same query with a plain Intervals.term leaf would usually have thrown and pointed at the schema (it throws once it is evaluated).
  • What it takes. One document, one query; default codec, IndexWriterConfig and searcher. Deterministic, with assertions on or off. The index is not damaged.
  • How likely: rare. It needs both an all-multi-term interval query and a field without positions. Elasticsearch and OpenSearch guard against it in their own code: OpenSearch checks hasPositions(), and Elasticsearch text fields either throw or recompute positions from the field values (source read); Solr main's unreleased intervals query parser applies no such check (source read).

Why it looks unintended

#
  • The IndexOptions javadoc: without positions, "PhraseQuery and other positional queries will throw an exception"; term leaves obey it.
  • Siblings throw on such a field: PhraseQuery, MultiPhraseQuery, span queries (even a lone span prefix), Intervals.term (even for an absent word).
  • Lucene 4.0 made such queries throw since "previously they silently returned no results"; a 2019 refactoring lost the check.
The full argument229 words
  • Contract. IndexOptions.java:31-36 (DOCS): "Phrase and other positional queries on the field will throw an exception"; :37-41 (DOCS_AND_FREQS): "PhraseQuery and other positional queries will throw an exception". It does not name interval queries; they are positional queries, and TermIntervalsSource and PayloadFilteredTermIntervalsSource apply the rule to interval leaves.
  • The symptom was removed once. CHANGES.txt:15444-15446, 4.0.0-ALPHA: "Positional queries (PhraseQuery, *SpanQuery) will now throw an exception if use them on a field that omits positions during indexing (previously they silently returned no results)".
  • Siblings throw. PhraseQuery.java:504-510, MultiPhraseQuery.java:255-262, SpanTermQuery.java:149-155 (so SpanMultiTermQueryWrapper(PrefixQuery) throws even alone), TermIntervalsSource.java:54-59, PayloadFilteredTermIntervalsSource.java:51. Not every positional query checks: the sandbox TermAutomatonQuery has no check either (TermAutomatonQuery.java:423) and returned 0 hits with no error for alpha (beta | gamma delta) on such a field. Within one interval query, a plain term leaf throws once it is evaluated: ordered(prefix("alph"), term("beta")) throws, ordered(prefix("alph"), prefix("bet")) does not.
  • Test. TestIntervals#testIntervalsOnFieldWithNoPositions (TestIntervals.java:260-270) asserts the exact message for Intervals.term("wibble"), a word not in the index. No test covers a multi-term leaf on such a field.
  • History. LUCENE-8196 (7.4.0) added the check; its review asked that "TermIntervalsSource should check whether positions were indexed" (#9243). LUCENE-8646 (#9692, 8.0.0) split TermIntervalsSource.intervals()/matches() into a checked instance method and an unchecked static helper, and built MultiTermIntervalsSource on the helpers only; its discussion never mentions positions. No later commit added the check.
The devil's-advocate check160 words

The strongest case for "not a bug": the intervals package is experimental; IntervalsSource.intervals may return null "if no intervals for this field exist in this segment" (IntervalsSource.java:39), so an empty result could be within contract; LUCENE-9462 deliberately made Weight#matches of TermQuery, SynonymQuery and MultiTermQuery work without positions (CHANGES.txt:4717); a lone multi-term leaf returns the right documents, so a check changes behaviour; and a positional query on a positions-free field is the user's misconfiguration.

Why it fails: the javadoc names the outcome, an exception, not an empty result; the null rule covers a segment without the field or the words, and Intervals.term throws even for an absent word; LUCENE-9462 changed no interval code and IntervalQuery(term).matches still throws, so it can at most argue for leaving the matches() half lenient; the span wrapper over the same PrefixQuery throws even alone; and the misconfiguration is exactly the input Lucene promises to reject. Verdict: not intended, a missing validation.

Suggested fix

#

Recommended Check positions in both MultiTermIntervalsSource methods

Add the check that TermIntervalsSource has to both MultiTermIntervalsSource methods: when terms.hasPositions() is false, throw the same IllegalArgumentException. 12 added lines; the repro and the queries, highlighter and queryparser suites pass. Main compatibility decision: a lone prefix on a keyword field then throws instead of matching. Guarding matches() too is the maintainers' call (option B).

    if (terms == null) {
      return null;
    }
    if (terms.hasPositions() == false) {
      throw new IllegalArgumentException(
          "Cannot create an IntervalIterator over field "
              + field
              + " because it has no indexed positions");
    }

Trade-offs

  • Multi-term leaves then behave exactly like Intervals.term, with the same message; one hasPositions() call per segment in intervals() and one per matches() call (per Weight#matches request for a document).
  • Behaviour change, the main compatibility decision: a lone multi-term leaf on a positions-free field (for example a prefix on a StringField) throws where it matches today; worth a CHANGES entry.

Downstream note

#

Downstream: an exclusion rule of a positional shape (ordered, unordered, phrase, maxgaps) over prefix or wildcard leaves on a field without positions, such as MUST_NOT(ordered(alph*, bet?)), excludes nothing, where the term version would throw; containing-type shapes and a lone multi-term leaf still exclude the documents that hold the expanded terms.

How it was found

#

Found first by reading the intervals code, where the check sits only in the single-term source, and confirmed with a small probe. A test harness that compares queries across index options later found it independently: every positional query threw on fields without positions, except interval queries built from multi-term leaves.

The method in full162 words

Method: code reading, then differential and metamorphic testing. Neither step is formal verification.

  • First finder (2026-10-26, main ea57360912ed): while writing a reference model of the multi-term interval source for a translation-validation harness, an AI tool read MultiTermIntervalsSource next to TermIntervalsSource, saw that only the latter checks hasPositions(), and confirmed it with a public-API probe and a JUnit on the stock jars ("got intervals [-1,-1]" where or(term, term) throws).
  • Second, independent finder (2026-10-26, main a9779ef3c193): a harness indexes the same documents at 29 index-option levels and checks relations between them. Relation R3: a positional query on a level without positions must throw. Over seeds 41-440 it saw 4,665 silent mismatches and 462 more on a mixed MultiReader, all printed ones on multi-term interval leaves, while PhraseQuery, MultiPhraseQuery, span and Intervals.term queries whose terms were present threw on every positions-free level.
  • The two findings were merged into one record; the hunt then ran the checks listed below.

History

#

Introduced in 8.0.0 by LUCENE-8646 (2019), which built the multi-term leaves on helpers that skip the check. All 60 releases from 8.0.0 to 10.5.2 fail the prefix-based tests, and 10.6.0 and main the minimal test; not fixed upstream.

Versions tested8 rows

It created MultiTermIntervalsSource, Intervals.prefix and Intervals.wildcard, and split TermIntervalsSource.intervals()/matches() into a checked instance method and an unchecked static helper; the new class calls only the helpers. Priority
Low, rank 623: Multi-term interval leaves on a field indexed without positions silently return no hits instead of the documented exception, but this needs a schema mistake that other queries expose and sits in the experimental intervals API.
Impact class
wrong error
Impact note
Applications that run an IntervalQuery built only from multi-term leaves (Intervals.prefix, wildcard, regexp, fuzzyTerm, range or multiterm, also through StandardQueryParser fn:wildcard (executed) and fn:fuzzyTerm (read)) on a field indexed without positions (DOCS or DOCS_AND_FREQS, for example a StringField or a TextField with reduced IndexOptions) get no exception and meaningless hits: ordered, unordered, phrase, maxgaps and similar shapes return no hits, containing, containedBy and overlapping return every document that holds both expansions, a lone source returns the documents containing an expanded term, and a MultiReader that mixes such an index with one that has positions returns only the positioned index's hits; the trigger is a schema misconfiguration that Lucene documents as an error (the Intervals.term, PhraseQuery and span versions throw), default writer, codec and searcher suffice, no scale is needed, and the index is unaffected.
Summary
You index 'alpha beta' into a field with IndexOptions.DOCS_AND_FREQS (no positions) and search IntervalQuery("body", Intervals.ordered(Intervals.prefix("alph"), Intervals.prefix("bet"))). You expect IllegalArgumentException ('... because it has no indexed positions'), because the IndexOptions javadoc says positional queries on such a field throw and the same query written with Intervals.term("alpha") and Intervals.term("beta") does throw. Instead MultiTermIntervalsSource never checks Terms#hasPositions(), runs the interval logic on the position -1 that the postings return, and silently reports 0 hits (1 of 2 on a MultiReader that also holds a positioned copy of the document); wildcard, regexp, fuzzyTerm, range and multiterm leaves behave the same way.
