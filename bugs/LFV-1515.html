Low, explain output only, experimental sandbox class TermAutomatonQuery: under the default BM25 similarity IndexSearcher.explain reports 0.028268427 for a hit that scores 0.13076457, because explain() passes the score to the similarity as the match frequency. The finding in 30 seconds

#

An experimental class of the sandbox module. Who can meet it: code that builds a TermAutomatonQuery itself, or through TokenStreamToTermAutomatonQuery of the same package, and asks for the explanation of a hit. Run on main 781025d6fe32, branch_11x daa54f2e0cd3 and the 10.6.0 jars: the same two numbers on each.

Background: three pieces

#
  1. TermAutomatonQuery matches documents whose term positions spell a path through an automaton that you build with createState, addTransition and setAccept. Example: wifi or wi fi.
  2. Its score is the similarity's score of a match frequency that the scorer counts while it walks the document's positions. In this page's example the automaton matches once and the frequency is 1.
  3. IndexSearcher.explain(query, doc) returns an Explanation: a tree of numbers and labels whose top value is meant to be the hit's score. A query builds it by handing the similarity an explanation of the frequency.

The finding, step by step

#
  1. Index one document, wifi. Search it with a TermAutomatonQuery that accepts wifi or wi fi. The hit scores 0.13076457. That number is right: one match, BM25 idf 0.2876821 times tf 1 / 2.2.
  2. Ask searcher.explain(query, doc) for that hit. You expect an explanation whose value is the hit's score, 0.13076457.
  3. Instead the value is 0.028268427, and the first line reads score(freq=0.13076457). The number shown as the frequency is the hit's score. The real match frequency is 1.
  4. Why: explain() reads the hit's score and hands it to the similarity where the match frequency belongs. The similarity scores it once more: tf = 0.13076457 / (0.13076457 + 1.2) = 0.09826279, and 0.2876821 x 0.09826279 = 0.028268427.
  5. Only the explanation is wrong. The search's hits, order and scores are right, and the search and the explain call return normally. With the match frequency passed instead, the explained value is 0.13076457.

Who is affected

#

Code that builds a TermAutomatonQuery itself, or through TokenStreamToTermAutomatonQuery of the same package, and calls IndexSearcher.explain on a hit. Under the default BM25 similarity the value differed from the score in every run of a query that rewrite() kept, explained on its own. The search's hits, order and scores are unaffected. Low: diagnostic output of an experimental sandbox class.

Mechanism, terms and numbers1,013 words

TermAutomatonQuery is a proximity query of the sandbox module; its javadoc marks it experimental. For a query that rewrite() keeps as an automaton query, TermAutomatonWeight.explain reads the hit's score (TermAutomatonQuery.java:454 on main 781025d6fe32), puts it into the node it names the frequency explanation (:484-485) and hands that node to the similarity (:486). SimScorer.explain takes its first argument as the explanation of the frequency and returns an explanation whose value is the score of it. So the explanation's value is the similarity's score of the score, and under BM25 the text prints the score as freq.

The weight is low. Only the diagnostic explain output is wrong: the defect does not change the search's hits, order or scores, and the search and the explain call return normally. A single term or a chain of terms never reaches this code, because rewrite() turns it into a term, phrase or multi-phrase query. The defect is as old as the method: #12208 (merged 2023-04-08, first released in 9.6.0) wrote its first implementation; before it the method returned null. It is on the released lines: 10.6.0 fails the same test with the same message as branch_11x daa54f2e0cd3 and main 781025d6fe32.

Line numbers are those of main 781025d6fe32; TermAutomatonQuery.java and TermAutomatonScorer.java are the same files on branch_11x daa54f2e0cd3. On the 10.6.0 tag the two statements of explain() are at lines 457 and 487-489.

  1. TermAutomatonQuery.java:443-487, TermAutomatonWeight.explain: it creates the scorer, advances it to the document and reads the score, float score = scorer.score(); (:454).
  2. :463-478: one line per query term that occurs in the document, the term's frequency with a child line "score for term".
  3. :484-485: Explanation freqExplanation = Explanation.match(score, "TermAutomatonQuery, sum of:", termExplanations);. The node named the frequency explanation carries the score.
  4. :486: return stats.explain(freqExplanation, norm);.
  5. Similarity.java:235-247, SimScorer.explain(Explanation freq, long norm): "@param freq Explanation of how the sloppy term frequency was computed". It returns an explanation whose value is score(freq.getValue().floatValue(), norm). BM25Similarity's override (BM25Similarity.java:299-311) computes the same value and prints score(freq=<that value>).
  6. So the reported value is the similarity's score of the similarity's score of the match frequency.
  7. What the search scores: TermAutomatonScorer.java:351-360 at 781025d6fe32, score() returns scorer.score(freq, norm). freq (:57) is the scorer's match count, the frequency that is scored: countMatches (:215-340) adds one for each arrival in an accepting state. In this page's example it is 1, for one match. The scorer has no accessor for it.
  8. rewrite() (TermAutomatonQuery.java:491-569) returns a query that matches nothing for an empty automaton, a TermQuery for a single term, a PhraseQuery or MultiPhraseQuery for a chain of terms (a chain position that carries the any-term becomes a gap in the phrase), and the query itself otherwise: for an automaton with a branch, or one whose accepting state has an outgoing transition. Only the last case reaches this method.

The numbers, by hand

#

One document, one token, one term of the query present. The values are the single-precision numbers that Lucene prints; a calculator gives the same to six or seven digits (0.0982627 and 0.0282684 in the last line).

  • idf = ln(1 + (1 - 1 + 0.5) / (1 + 0.5)) = 0.2876821
  • with frequency 1 and a field of average length: tf = 1 / (1 + 1.2) = 0.45454544, score = 0.13076457
  • with 0.13076457 as the frequency: tf = 0.13076457 / (0.13076457 + 1.2) = 0.09826279, value = 0.028268427

Why it looks unintended

#
  • Weight.explain returns "an Explanation for the score"; the similarity documents its first argument as the explanation of the frequency.
  • The output prints a score as a frequency: score(freq=0.13076457) for a one-token document.
  • Lucene's own CheckHits.checkExplanations fails on this query; PhraseWeight.explain passes the phrase frequency.

The devil's-advocate check274 words

The strongest case for "intended": the class javadoc says "This code is very new and likely has exciting bugs!" and marks the class experimental; the upstream test carries a TODO on explain and checks only isMatch(); IndexSearcher.explain describes itself as an aid for "developing Similarity implementations"; the author of #12208 wrote that "explain has many areas of potential improvement". The strongest fact on that side: the equality assertion was removed in the very commit that first made the test exercise this method, the author wrote the next day that "the scores changed", and the change was approved after that with a test that checks isMatch() only. So the thread can be read this way: the mismatch was seen, and the change was merged as a known first cut with no promise on its numbers.

What is left of that case. These facts lower the weight, and they are why this is Low. None of the texts says that the value may differ from the score: the limitation named in the thread is another matter (which term sequence matched), and the author's sentence on "the true query" is about the rewritten query. An early commit of the pull request asserted that the value equals the score, on a query that was still rewritten to a PhraseQuery; when the test reached this method the assertion was removed, and nobody in the thread comments on that. And the printed freq=0.13076457 is not a rough first cut of a frequency: it is the score in the frequency's place. Whether a first cut of an experimental class is worth a change is for the maintainers to say.

Registry title
Sandbox TermAutomatonQuery's explain() passes the hit's score to the similarity as the match frequency, so IndexSearcher.explain reports a value that is not the hit's score (0.028268427 for a hit that scores 0.13076457); the search's hits and scores are not affected; every release from 9.6.0 to 10.6.0, branch_11x and main
Area
sandbox / search: TermAutomatonQuery (experimental), TermAutomatonWeight.explain
Priority
Low, rank 1144: Since 9.6.0, under the default BM25Similarity, IndexSearcher.explain on a hit of the experimental sandbox TermAutomatonQuery (for automata that rewrite() keeps) reports a value that is not the hit's score and prints the score as the frequency. It is Low because only the diagnostic explain output is wrong: the defect does not change the search's hits, order or scores, the search and the explain call return normally, and the class is sandbox code.
Impact class
minor
Impact note
Applications that call IndexSearcher.explain (or Weight.explain) on an experimental sandbox TermAutomatonQuery that rewrite() keeps as an automaton query (one that is not a single term or a plain chain, which rewrite() turns into a term, phrase or multi-phrase query) get, under the default BM25Similarity, an explanation whose value is not the hit's score and whose text shows the score as 'freq' [exec: in a differential check against a small reference model of the scorer, 0 of 562,484 explained hits have a value equal to the score]; the defect does not change the search's hits, order or scores, the search and the explain call return normally and nothing is lost. Default settings, with -ea and -da, at any scale, in every release from 9.6.0 to 10.6.0, on branch_11x and on main. Limits [exec]: under a similarity whose score ignores the frequency (BooleanSimilarity) the value equals the score and no frequency is printed, so nothing wrong is visible there; inside a BooleanQuery the explanation's top value is the right score and only the automaton clause's own line is wrong, so the clause lines do not add up to it.
Summary
You index one document, 'wifi', search it with a TermAutomatonQuery that accepts 'wifi' or 'wi fi', and ask IndexSearcher.explain for the hit. You expect the explanation's value to be the hit's score, 0.13076457. Instead it is 0.028268427 and its text reads 'score(freq=0.13076457)': explain() gave the similarity the hit's score where the match frequency (1) belongs, so the reported value is the similarity's score of the score; the search itself is right.
