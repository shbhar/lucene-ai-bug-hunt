Flexible StandardQueryParser: (the fox)@1 with a stop-word analyzer, or the boosted group (fox dog)^2@1, throws ClassCastException

The flexible StandardQueryParser builds (...)@N, "at least N of these clauses", by casting the group's query to BooleanQuery. So (the fox)@1 with a stop-word analyzer, or the boosted (fox dog)^2@1, makes parse() throw ClassCastException instead of returning a query, in every release since 9.1.0.

The finding in 30 seconds

#

(...)@N asks for at least N of a group's clauses. Its builder assumes the group's query is a BooleanQuery, so any group that builds something else makes parse() throw.

Background: the @N operator of the flexible parser

#
  1. Since 9.1.0 the flexible StandardQueryParser accepts (blue crab fish)@2: match documents with at least 2 of the 3 clauses. It becomes a BooleanQuery with minimum-should-match 2, printed (body:blue body:crab body:fish)~2.
  2. Parsing has three phases: the grammar builds a tree of query nodes; a pipeline of processors rewrites it (the analyzer runs here, and a Boolean node left with one clause is replaced by that clause); then one builder per node type turns the tree into Lucene queries.
  3. A boost on a group, (fox dog)^2, becomes a BoostQuery around the group's query.

The finding, step by step

#
  1. Create a StandardQueryParser whose analyzer drops the stop word "the". (fox dog)@1, "at least 1 of fox, dog", parses to (body:fox body:dog)~1.
  2. Parse (the fox)@1, the same kind of two-clause OR group. You expect a query for "at least 1 of {fox}", such as (body:fox)~1, or at worst the declared QueryNodeException.
  3. You get ClassCastException: TermQuery cannot be cast to BooleanQuery. The analyzer removed "the", the parser replaced the group's one-clause Boolean node by that clause, body:fox, and the @N builder casts that TermQuery to BooleanQuery without a check.
  4. The boosted group (fox dog)^2@1 fails the same way (BoostQuery cannot be cast), because the grammar puts the boost inside the @N node; the other order, (fox dog)@1^2, is a syntax error, and only ((fox dog)@1)^2 works. One-clause groups such as (fox)@1 or ("quick fox")@1 fail too.
  5. Nothing is searched and no result is wrong, but a valid query is refused with an undeclared exception: with assertions on and off, with operator OR or AND, through PrecedenceQueryParser too, in every release since 9.1.0.

Who is affected

#

Applications that pass query strings with the documented @N operator to the flexible StandardQueryParser or PrecedenceQueryParser, with default settings: a stop word that leaves one clause in a group (needs a stop-word analyzer), a boosted group, or a one-clause group such as a generated (t)@1. The failure is immediate and loud; the classic QueryParser has no @N operator.

Mechanism, terms and numbers671 words

The flexible StandardQueryParser (and PrecedenceQueryParser, which shares its builders) documents a min-should-match operator for disjunction groups, (blue crab fish)@2, and boosts on grouped clauses. MinShouldMatchNodeBuilder builds the @N node by casting the group's query to BooleanQuery without a check. That query is not a BooleanQuery when a stop-word analyzer leaves one clause in the group (the parser then replaces the group's one-clause Boolean node by that clause), when the group carries a boost (the grammar puts the boost inside the @N node), or when the group holds a single term, phrase or prefix. parse() then throws java.lang.ClassCastException instead of returning a query or its declared QueryNodeException.

The failure is immediate and deterministic, with assertions on and off and with either default operator; there are no wrong results and no index effect. Every release with the operator is affected, 9.1.0 (2022) to 10.6.0, and main. A one-file fix in the builder (move the boost outside, accept a lone query as one SHOULD clause) passes the repro and all 534 queryparser tests.

The mechanism (main 645d4fe14a20)

#
  1. Grammar. GroupingExpr is <LPAREN> q = Query(field) <RPAREN> (q = Boost(q))? ("@" minShouldMatch = <NUMBER>)? and then builds new MinShouldMatchNode(parseInt(minShouldMatch), new GroupQueryNode(q)) (StandardSyntaxParser.jj:358-361). The boost is applied first, so in (fox dog)^2@1 the @N node wraps the boost; (fox dog)@1^2 is not in the grammar (a ParseException).
  2. Analysis. AnalyzerQueryNodeProcessor (StandardQueryNodeProcessorPipeline.java:58) turns a term that analyzes to no token into a NoTokenFoundQueryNode (AnalyzerQueryNodeProcessor.java:162-163), a DeletedQueryNode that RemoveDeletedQueryNodesProcessor removes (pipeline :63).
  3. One-child collapse. BooleanSingleChildOptimizationQueryNodeProcessor (pipeline :65) "removes every BooleanQueryNode that contains only one child and returns this child" (:28-34, code :42-58). It is the Boolean node inside the group that is replaced, so the group keeps only the field node body:fox: GroupQueryNode [BooleanQueryNode [FieldQueryNode(body:fox)]] becomes GroupQueryNode [FieldQueryNode(body:fox)] (the diagram probe's trace).
  4. Group builder. GroupQueryNodeBuilder returns the child's query unchanged (GroupQueryNodeBuilder.java:36-39): a TermQuery for (the fox), a BoostQuery for (fox dog)^2, a PhraseQuery for ("quick fox").
  5. The cast. MinShouldMatchNodeBuilder.build reads that query (:38), does BooleanQuery booleanQuery = (BooleanQuery) q; (:40), and copies its clauses into a new BooleanQuery with the minimum set (:41-44). Its javadoc: "Builds a BooleanQuery from a MinShouldMatchNode" (:27).
  6. Escape. QueryTreeBuilder.processNode calls the builder directly (QueryTreeBuilder.java:165), so the ClassCastException leaves StandardQueryParser.parse (:277-279), which declares only QueryNodeException (:274; QueryParserHelper.java:211-213).

PrecedenceQueryParser extends StandardQueryParser and only swaps the processor pipeline (PrecedenceQueryParser.java:35, :41, :50), so it fails the same way.

(the a)@1 never reaches the builder: NoChildOptimizationQueryNodeProcessor (pipeline :62) turns the emptied Boolean node into a MatchNoDocsQueryNode, a DeletedQueryNode (NoChildOptimizationQueryNodeProcessor.java:43-62, MatchNoDocsQueryNode.java:23), and RemoveDeletedQueryNodesProcessor (pipeline :63) deletes the group and the @N node above it and returns a match-no-docs root (RemoveDeletedQueryNodesProcessor.java:38-43, :50-72). The no-argument StandardAnalyzer() has no stop words, so the stop-word trigger needs a stop-word analyzer (an explicit stop set, EnglishAnalyzer or StopAnalyzer); the boost and one-clause triggers need none.

Exposure and likelihood126 words
  • What goes wrong. A valid query is refused with an undeclared ClassCastException. Code that catches only QueryNodeException to answer "invalid query" sees an unexpected runtime exception instead.
  • When. Whenever the group does not build a BooleanQuery: a stop word leaves one clause (users cannot know which words the analyzer drops), the group carries a boost, or a query generator renders a one-element list as (t)@1.
  • Limits. Deterministic and immediate; nothing is searched, so no wrong results; no hang, no index effect, no scale needed. ((a b)@1)^2 is a workaround for the boost case only.
  • Reach is narrow. @N is the flexible parser's own syntax (the classic QueryParser has no such operator), and no public report was found since 9.1.0, released in March 2022.

Why it looks unintended

#
  • (the fox)@1 is written in the documented form, an OR group like the javadoc's (blue crab fish)@2; the parser's own analyzer removes "the".
  • (fox dog)^2@1 is the only boost-plus-@N order the grammar accepts; (fox dog)@1^2 is a syntax error.
  • parse() declares QueryNodeException, and the grammar rejects other bad @ uses that way; no test or review discusses the cast.
The full argument233 words
  • The input is written in the documented form. (the fox)@1 and (the OR fox)@1 are disjunction groups as written, the shape of the javadoc examples (StandardQueryParser.java:195, :198) and of the only upstream test, (f:foo OR f:bar OR f:baz)@2 (TestStandardQPEnhancements.java:55-67). The stop word is removed by the parser's own pipeline; with two survivors, (the quick fox)@2, it works.
  • The boost order is the grammar's own. The same commit wrote GroupingExpr so that (a b)^2@1 is the only accepted boost-plus-@ order, and the class javadoc documents boosts on grouped clauses (StandardQueryParser.java:163-164).
  • The declared failure is QueryNodeException (:274). The grammar already rejects unsupported @ uses that way: (fox dog)@1^2, fox@1 and (fox dog)@x are ParseExceptions. This is a robustness argument, not a broken contract: Java lets any method throw an unchecked exception, and the javadoc does not say what @N does once analysis leaves one clause or when a boost sits inside it. But nothing documents a ClassCastException, and the parser refuses every other unsupported @ use with the declared exception.
  • Nobody discussed it. No test, javadoc, CHANGES or MIGRATE entry, issue or review comment mentions the cast or non-Boolean groups; the only test uses a three-clause unboosted group, which is why it never failed.
  • Precedent. LUCENE-4103 (#5175, fixed 2012), a ClassCastException in the same flexible pipeline, was fixed as a bug.
The devil's-advocate check111 words

The strongest case for "intended" (moderate; raised by every verifier): @N is documented only for "a disjunction Boolean query (a query with only "OR"-subclauses)" (StandardQueryParser.java:190-191) and "Boolean groups" (standard/package-info.java:33), so direct one-clause or one-phrase groups such as (fox)@1 or ("quick fox")@1 are arguably outside the contract, and their meaning is unspecified.

Why it fails: it does not cover the lead triggers, two-clause OR groups reduced by the parser's own analysis and a documented group boost, and even for inputs outside the contract the declared failure is QueryNodeException; nothing documents a ClassCastException. It is a fair reason to accept a QueryNodeException for the direct one-clause shapes.

Suggested fix

#

Recommended Accept any group query in MinShouldMatchNodeBuilder

In MinShouldMatchNodeBuilder, move a group boost outside the min-should-match query and accept a lone non-Boolean query as its one SHOULD clause: (the fox)@1 gives (body:fox)~1, (fox dog)^2@1 gives ((body:fox body:dog)~1)^2.0. One file, +16/-3; the repro and all 534 queryparser tests pass, and queries that built before are unchanged.

float boost = 1f;
while (q instanceof BoostQuery bq) {
  boost *= bq.getBoost();
  q = bq.getQuery();
}
BooleanQuery.Builder builder = new BooleanQuery.Builder();
builder.setMinimumNumberShouldMatch(mmNode.minShouldMatch);
if (q instanceof BooleanQuery booleanQuery) {
  booleanQuery.clauses().forEach(builder::add);
} else {
  builder.add(q, BooleanClause.Occur.SHOULD);
}
Query result = builder.build();
return boost == 1f ? result : new BoostQuery(result, boost);

Accept any group query in MinShouldMatchNodeBuilder (validated by the checks) (recommended)

#

Unwrap any BoostQuery around the group's query and re-apply the boost outside the result; copy a BooleanQuery's clauses as today; otherwise add the query as the one SHOULD clause. BooleanQuery already defines a minimum larger than the SHOULD count (no match), so (the fox)@2 gives (body:fox)~2, like (fox dog)@3 today. Also update the builder javadoc (:27) and add a CHANGES entry.

  boost *= bq.getBoost();

Trade-offs

  • Gives direct one-clause groups such as (fox)@1 a meaning the javadoc does not define (the natural one: at least N of 1 clause).
  • A lone user + is not kept: (+fox)@1 gives (body:fox)~1, as (+fox) without @ gives body:fox today.
  • Every input that built a query before builds the same query: the old code succeeded only when the group's query was an unboosted BooleanQuery, and the new code takes the same path for it (by reading; the shape probe agrees for the controls, (the quick fox)@2, (-fox)@1, (the a)@1 and AND groups).

Reject non-Boolean groups with a QueryNodeException

#

Keep the cast for a BooleanQuery and throw QueryNodeException otherwise (the builder interface allows it, QueryBuilder.java:35).

Trade-offs

Smallest change and turns the crash into the declared failure, but it still refuses (the fox)@1 and (fox dog)^2@1, which are written in documented syntax; acceptable for the direct one-clause shapes only, so it needs the boost unwrap anyway. The builder sees the same TermQuery for (the fox)@1 as for (fox)@1, so it refuses both, and the suggested regression test would have to expect the exception. Not run.

Apply the group boost outside the @N node in the grammar

#

Build Boost(MinShouldMatchNode(...)) in GroupingExpr.

Trade-offs

Fixes only the boost trigger, needs the JavaCC parser regenerated, and still needs a builder change for the stop-word and one-clause triggers. Not run.

Keep a one-child Boolean node under @N

#

Make BooleanSingleChildOptimizationQueryNodeProcessor skip the group of a MinShouldMatchNode.

Trade-offs

Fixes the stop-word trigger only, couples a generic processor to one node type, and leaves the boost and phrase shapes. Not recommended; not run.

Downstream note

#

Not a Lucene security issue; downstream, a service that catches only QueryNodeException to answer "invalid query" returns a generic server error for these user queries instead.

How it was found

#

A differential exploration by an AI tool: 57 edge-case query strings parsed under 6 analyzers, with both flexible parsers and both default operators. The only unchecked exception it produced was this ClassCastException, first on (the fox)@2 with a stop-word analyzer; reading the builder and the grammar then gave the boosted and one-clause triggers.

The method in full141 words

Method: semi-formal (a hunt unit, the flexible parser's analysis processors composed with the rest of the processor pipeline).

  • A probe parsed 57 edge-case query strings (stop words, synonyms, word delimiters, CJK, boosts, phrases, @N groups) under 6 analyzers, each with StandardQueryParser and PrecedenceQueryParser and default operator OR and AND (1,368 parses), and recorded the query or exception of each.
  • The only unchecked exception class in the output was this ClassCastException, on (the fox)@2 with the three analyzers that drop "the" (all four parser variants), while (the fox dog)@2 built normally.
  • An AI tool then read MinShouldMatchNodeBuilder and the grammar and found the analysis-independent triggers (the boosted group and direct one-clause groups), and wrote the public-API JUnit test.
  • So the exploration targeted the analysis pipeline in general; the @N strings were among its edge cases, not a hypothesis about this cast.

History

#

Introduced with the @N operator by LUCENE-10223 (#429, November 2021) and first released in 9.1.0 (March 2022); the builder has not changed since. All 33 releases from 9.1.0 to 10.6.0 and main fail the repro; 9.0.0 has no @N operator. Not fixed upstream.

Versions tested6 rows

queryparser / flexible: standard query builders (MinShouldMatchNodeBuilder for the @N min-should-match operator, composed with the grammar's group boost and the single-child Boolean optimization)
Priority
Low, rank 887: The flexible parser's documented @N operator throws an unchecked ClassCastException on valid groups such as (the fox)@1 with stopwords or a boosted group, which is more reachable than a fractional slop but still only the wrong error type in a niche operator.
Impact class
wrong error
Impact note
Applications that pass query strings with the documented @N min-should-match operator to the flexible StandardQueryParser or PrecedenceQueryParser (default parser settings, documented syntax) get an unchecked ClassCastException from parse() instead of a query or the declared QueryNodeException whenever the group does not build a BooleanQuery: a two-clause group that the stock analysis reduces to one clause (a stopword, as in (the fox)@1), a boosted group such as (fox dog)^2@1, or a group holding one term, phrase, prefix or other non-Boolean query; no wrong results, no hang, no index effect, no scale needed, every release since 9.1.0.
Summary
You parse (the fox)@1 ('at least one of the, fox') with the flexible StandardQueryParser and an analyzer that drops the stopword 'the', or the boosted group (fox dog)^2@1; the class javadoc documents @N for disjunction groups and boosts on grouped clauses, and parse() declares QueryNodeException for failures, so you expect a query (at least one of the remaining clauses, boosted as written). Instead parse() throws java.lang.ClassCastException ('TermQuery / BoostQuery cannot be cast to BooleanQuery') from MinShouldMatchNodeBuilder.build, which casts the group's query to BooleanQuery without a check: after the stopword is removed the one-clause group is collapsed to a TermQuery, and the grammar puts the boost inside the min-should-match node, so the group's query is a BoostQuery. Groups holding a single term, phrase, prefix or other non-Boolean query, such as (fox)@1 or ("quick fox")@1, fail the same way, while (fox dog)@1 works.
