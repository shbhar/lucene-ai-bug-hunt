Axiomatic F1/F3 explanations print the tf formula as 1 + log(1 + log(freq)), but the value is computed on freq + 1

With the Axiomatic F1/F3 similarities, explain says the tf value is 1 + log(1 + log(freq)) of its freq child, but the code first adds 1 to freq: at freq 1 the node shows 1.526589; its formula gives 1.0. Scores are unaffected; only this formula text is stale, since 8.0.0.

The finding in 30 seconds

#

A description "computed as <formula> from:" says the node's value is that formula of its children. The Axiomatic F1/F3 tf node states 1 + log(1 + log(freq)) over its freq child, but its value comes from tf(), which adds 1 to freq first. The printed formula is one step behind the value.

Background: how an explanation reads

#
  1. IndexSearcher.explain(query, doc) returns a tree that shows how a hit's score was computed: every node has a value, a description and child nodes.
  2. A description ending in computed as <formula> from: promises that the node's value is that formula applied to its children; Explanation.match documents the description as "how value was computed".
  3. The Axiomatic similarities score a term as tf x ln x tfln x idf (minus gamma; the rule is in Axiomatic.score, the tree only says "computed from:"), and the tree lists each component, with its formula and inputs, under the score node.

The finding, step by step

#
  1. Index three documents with AxiomaticF1EXP: field f = "a", "a a", "a a a". Search f:a and call IndexSearcher.explain on doc 0, where the term occurs once.
  2. The tf node reads tf, term frequency computed as 1 + log(1 + log(freq)) from: with one child, 1.0 = freq, number of occurrences of term in the document. You expect 1 + log(1 + log(1)) = 1.0.
  3. Instead the node shows 1.526589, which is 1 + log(1 + log(2)): tf() runs freq += 1 before the formula. At freq 2 and 3 it shows 1.7412763 and 1.8697417, the printed formula's values for 3 and 4.
  4. Recomputing the score from the printed parts by Axiomatic.score's rule gives tf 1.0 x ln 1.0 x tfln 1.0 x idf 1.1059324 = 1.106, but the tree and the hit say 1.6883042 (= 1.526589 x 1.1059324). The score, ranking and node value are unaffected; only the text is stale. Same in F1LOG, F3EXP and F3LOG.

Who is affected

#

Anyone who calls explain on searches that use AxiomaticF1EXP, F1LOG, F3EXP or F3LOG, which are non-default, @lucene.experimental similarities. Every explained hit shows the stale formula, whatever the term frequency. A reader who recomputes the node or the score from the printed text cannot make the numbers add up. Scores and ranking are unaffected.

Mechanism, terms and numbers506 words

AxiomaticF1EXP, AxiomaticF1LOG, AxiomaticF3EXP and AxiomaticF3LOG compute the term-frequency component as freq += 1; return 1 + Math.log(1 + Math.log(freq));, that is 1 + log(1 + log(freq + 1)) of the freq they are given (for a term query, the raw count). Their tfExplain shows that value but describes it as "tf, term frequency computed as 1 + log(1 + log(freq)) from:" over one child holding the unshifted freq, so the printed formula on the printed child does not give the printed value: 1.526589 instead of 1.0 at freq 1, 1.8697417 instead of 1.7412763 at freq 3. The defect changes no score, ranking or match and no value in the tree; only the formula text is stale. LUCENE-8011 wrote the text when tf() had no + 1; LUCENE-8010 added the + 1 four weeks later and left the text, so every release from 8.0.0 to 10.6.0 and main shows it. The fix is one string per class.

The bug, step by step (main 645d4fe14a20)

#
  1. The value. AxiomaticF1EXP.tf (AxiomaticF1EXP.java:59-62): freq += 1; // otherwise gives negative scores for freqs < 1 (:60), then return 1 + Math.log(1 + Math.log(freq));. Natural log. The same in AxiomaticF1LOG.java:50-53, AxiomaticF3EXP.java:59-62 and AxiomaticF3LOG.java:48-51.
  2. The explanation. AxiomaticF1EXP.tfExplain (:88-94) returns Explanation.match((float) tf(stats, freq, docLen), "tf, term frequency computed as 1 + log(1 + log(freq)) from:", Explanation.match((float) freq, "freq, number of occurrences of term in the document")): the value carries the + 1, the text (:92) and the child (:93, the unshifted freq) do not. The string is at AxiomaticF1LOG.java:83, AxiomaticF3EXP.java:92 and AxiomaticF3LOG.java:81.
  3. Where it shows. Axiomatic.explain adds the node under "score(<class>, freq=...), computed from:" (Axiomatic.java:162, :129-137); the score node's value uses the same tf() (:125-127), so the top value equals the hit score.
  4. Why no test noticed. CheckHits.verifyExplanation stops at a node ending in "computed from:", which is the Axiomatic score node (CheckHits.java:411-413), and treats any "., computed as . from:" node as consistent with its children (:375, :437-438). No upstream test contains the string.

By the math every legal freq is affected (Similarity.java:218: a "sloppy term frequency, must be finite and positive"): above 1/e both expressions are real and differ; at or below 1/e, which a sloppy PhraseQuery can reach (PhraseWeight.java:82-86, SloppyPhraseMatcher.java:200-202), the printed formula is not a real number while the value stays finite. That is the NaN rmuir found in LUCENE-7997 (#9045), which the + 1 avoids.

Exposure and likelihood145 words
  • Who is hit: callers of IndexSearcher.explain (or anything that prints an explanation) on a search with one of the four similarities, with default IndexWriterConfig, codec and searcher, assertions on or off.
  • Opt-in: non-default similarities; every class involved is @lucene.experimental (AxiomaticF1EXP.java:25, AxiomaticF1LOG.java:25, AxiomaticF3EXP.java:27, AxiomaticF3LOG.java:27, Axiomatic.java:34).
  • What goes wrong: misleading diagnostic text. Checking the tf node against its child, or combining the printed components by Axiomatic.score's rule (1.106 instead of 1.688 in the example), points at a scoring bug that does not exist. The hunt's evaluator, which recomputes explanation formulas from their children, flags it.
  • Scale: four string literals; the searches found no prior report.
  • Not claimed: any effect on scores, ranking, matching, the tf node's value or the top explanation value; in every run the tf value is tf()'s and the top value equals the hit score.

Why it looks unintended

#
  • Explanation.match documents the description as "how value was computed", and Axiomatic.tfExplain promises "how the tf component was computed".
  • The node's only child is labelled "number of occurrences of term in the document" and holds the unshifted freq.
  • The text was exact when LUCENE-8011 wrote it; LUCENE-8010 added the + 1 four weeks later without discussing the tf explanation.
The full argument187 words
  • The contract. Explanation.java:31, :43: "@param description how {@code value} was computed". Axiomatic.java:195: "@return Explanation of how the tf component was computed". SimilarityBase.java:106: subclasses add clauses "to explain details of their scoring formulae".
  • The operand. The child "freq, number of occurrences of term in the document" holds the unshifted freq (AxiomaticF1EXP.java:93; Axiomatic.java:193 documents tfExplain's freq with the same words), so the text cannot mean a shifted freq.
  • The history. In the LUCENE-8011 (#9059) thread jpountz asked that the similarities "include the formula that was used to compute the score"; the strings it added matched tf() then. In LUCENE-8010 (#9058) jpountz asked "Axiomatic similarities add 1 to the freq, is it ok?" and rmuir answered with relevance numbers: the score change was deliberate. No #9058 comment mentions the explanation, and its issue body even lists "internal explanations calculations are sane" as a test requirement.
  • The neighbours. The ln and idf nodes and the F2 tf node match their operands.
  • Precedent. GITHUB#13691 "Fix incorrect exponent value in explain of SigmoidFunction" (0f5359a2ac6), an explain-only fix, is listed under Bug Fixes for 9.12.0.
The devil's-advocate check152 words

The strongest case for "intended" (the devil's-advocate checker): Explanation is an expert diagnostic API with human-readable descriptions, not an expression language; the classes are @lucene.experimental; 1 + log(1 + log(freq)) names the published F1/F3 tf function, so "freq" could mean the shifted local variable; CheckHits deliberately treats "computed as ... from:" nodes as opaque; no CHANGES or MIGRATE entry promises exact explain formulas.

Why it fails: the javadoc says the description is how the value was computed; the child is labelled and filled as the unshifted freq, which rules out the shifted reading; the text was exact until LUCENE-8010 changed the code without a word about the tf explanation; CheckHits' opacity explains why no test noticed, not why the text would be right; and an explain-only formula error was fixed as a bug before (GITHUB#13691). Every reviewer rated the intended case weak; it explains the low priority, not the behaviour.

How it was found

#

Semi-formal: an AI tool's sweep explained 3,178 hits over 79 similarity configurations and recomputed each of 14,554 "computed as" nodes from its own children. 200 tf nodes of the Axiomatic F1/F3 classes disagreed. Ten of ten injected mutants were caught, so the check is not vacuous; a public-API JUnit test then confirmed it.

The method in full124 words

Method: semi-formal, a differential explain-tree evaluation (a hunt unit, explanation formula strings checked against their own operand values), on the stock main a9779ef3c193 jars.

  • A test program explained hits for 79 similarity configurations x TermQuery, PhraseQuery, SynonymQuery and a 2-clause BooleanQuery x 2 boosts, plus the scoring queries: 3,178 explained hits, 14,554 "computed as <formula> from:" nodes, each evaluated on its own labelled children, with assertions on and off.
  • 200 tf nodes over AxiomaticF1EXP, F1LOG, F3EXP and F3LOG disagreed with their stated formula; F2EXP/F2LOG and every other Axiomatic node agreed.
  • The oracle is not vacuous: 10 of 10 injected non-equivalent mutants were detected.
  • The signal was reduced to a public-API JUnit test, then to the one-test repro.
