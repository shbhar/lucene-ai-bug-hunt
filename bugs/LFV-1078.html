A failure inside prepareFlush is not tragic: IndexWriter stays open, and the next commit silently lacks acknowledged documents, deletes and updates

When a commit, flush, forceMerge or NRT reopen fails while Lucene prepares an in-memory segment for flushing, the writer stays open and reports no tragic exception, yet has dropped that segment and the deletes and updates it had just frozen. The next successful commit() or close() silently lacks them.

The finding in 30 seconds

#

Flushing an in-memory segment starts with prepareFlush: it first freezes the writer-wide buffered deletes and updates into a packet and clears them, then applies the segment's own copy of them. If that second step throws, doFlush has no flush ticket to carry the packet, and its finally drops the segment. Nothing marks the writer as broken.

How IndexWriter flushes buffered work, in one minute

#
  1. Each indexing thread fills its own in-memory segment (a DWPT). Deletes and doc-values updates go into one writer-wide queue; each in-memory segment also keeps a slice of that queue (everything since its last document) to apply to its own documents.
  2. To flush a segment, doFlush asks prepareFlush for a flush ticket. The ticket carries, in order, the frozen writer-wide deletes and updates (for the older segments) and, once written, the new segment.
  3. A failure while the segment is written (DocumentsWriterPerThread.flush) is tragic: Lucene aborts the segment and the writer closes itself, so the last commit stays the recovery point.

The finding, step by step

#
  1. Commit one document whose id is a 1 KB term (victim). Add a document buffered; it waits in its own in-memory segment.
  2. Call updateNumericDocValue(victim, "n", i) 2,200,000 times, then deleteDocuments(victim) (sequence number 2,200,005). Every call succeeds; ramBytesUsed() reports 2.6 MB just before the commit (at most 16.8 MB during the updates).
  3. commit() throws ArithmeticException: integer overflow: preparing the in-memory segment copies all 2.2 million updates since buffered into its own buffer, about 2.25 GB, past the 2 GiB a byte pool can address. isOpen() is true, getTragicException() is null.
  4. You expect the writer to close itself, as for any other failure while flushing a segment, or the next commit to hold every operation its sequence number covers.
  5. Instead the next commit() succeeds and returns 2,200,008, yet buffered is missing, victim is still live, and its n is 2,197,624: the document, the delete and the last 2,376 updates are gone.

Who is affected

#

Applications that keep using the writer, or simply close() it (default commitOnClose), after a commit, flush, forceMerge or NRT reopen failed in this step: isOpen() says true, getTragicException() null. The executed trigger needs about 2 GiB of update terms behind an idle in-memory segment; an over-long delete term and a throwing InfoStream reach the same handling.

Mechanism, terms and numbers705 words

Flushing an in-memory segment (a DWPT) starts in DocumentsWriter.doFlush, which creates its flush ticket with ticketQueue.addTicket(() -> new FlushTicket(dwpt.prepareFlush(), true)) (DocumentsWriter.java:534-536). prepareFlush first freezes the writer-wide buffered deletes and doc-values updates into a packet and clears them (DocumentsWriterPerThread.java:429, DocumentsWriterDeleteQueue.java:269-273), then applies the segment's own slice of the delete stream (:434), which can throw. When it does, there is no ticket: the catch skips markTicketFailed (DocumentsWriter.java:556-563), so the packet is lost, and the finally drops the DWPT with its buffered documents (:576-578). doFlush issues no abort and no tragic event for this DWPT, so isOpen() stays true and getTragicException() null, and the next successful commit(), or close() with the default commitOnClose, persists an index without operations its sequence number covers. Every failure inside the segment write itself is tragic (DocumentsWriterPerThread.java:585-604). The executed trigger, about 2^31 bytes of update terms behind one idle in-memory segment, reaches this step since 9.8.0 (#12392 made the overflow throw there; 9.7.0 closed the writer instead); an InfoStream that throws on the flush's first message reaches the same handling in every release since 4.0.0. Making a failure on this path tragic in doFlush fixes both.

Step by step

#
  1. The thread that added buffered then only updates and deletes, so its in-memory segment's slice spans all 2,200,001 later operations. commit() reaches doFlush through prepareCommitInternal (IndexWriter.java:3809) and flushAllThreads / maybeFlush (DocumentsWriter.java:688, :496); flush(), forceMerge() (IndexWriter.java:2248, :4402) and an NRT reopen (:586) take the same path.
  2. freezeGlobalBuffer applies the global slice, builds a FrozenBufferedUpdates packet and clears the writer-wide buffer (DocumentsWriterDeleteQueue.java:217-237, :262-277, clear at :272). Here the packet holds the delete of victim and the updates since the writer-wide buffer was last applied (it is applied whenever it reaches the 16 MB RAM buffer, FlushByRamOrCountsPolicy.java:52-53).
  3. Applying the segment's slice appends each update's 1 KB term to the segment's private buffer: 2.2 million updates need about 2.25 GB, and Math.addExact in ByteBlockPool.nextBuffer throws ArithmeticException at 2 GiB (ByteBlockPool.java:199).
  4. addTicket gives its ticket count back and rethrows (DocumentsWriterFlushQueue.java:48-50). ticket is still null, so nothing holds the packet, and the finally drops the DWPT with buffered. doFlush calls neither flushFailed, abort() nor onTragicEvent for this DWPT (a failed full flush's cleanup, finishFullFlush(false) -> abortFullFlushes(), aborts only other DWPTs still queued or blocked for that flush, DocumentsWriter.java:727-745, DocumentsWriterFlushControl.java:685-723; the one-thread repro has none); getPendingNumDocs() stays one too high (2 for an index of 1 document).
  5. Contrast: DocumentsWriterPerThread.flush treats any Throwable as aborting (:585-587), and maybeAbort aborts and fires the tragic event ("whatever we do here we have to fire this tragic event up", :594-604). Two steps that can throw an ordinary exception run outside that guard: prepareFlush, and flush's first InfoStream message ("flush postings as segment", :479-483, before the try at :485). A non-tragic exception there is dropped the same way; the ticket already exists then, so only the segment's documents are lost.

Exposure and likelihood479 words
  • Who is hit. Applications that keep using an IndexWriter, or close it with the default commitOnClose (the try-with-resources idiom), after commit(), flush(), forceMerge(), an NRT reopen or flushNextBuffer() threw from this step. The writer gives no signal to stop: isOpen() is true and getTragicException() is null, the two signals LUCENE-6217 (#7279) added for that decision (#9738's description says Solr's leader election, for one, decides from getTragicException()). Earlier commits stay intact, and rollback() right after the failure restores the last commit (assertions off).
  • What is lost. The in-memory segment's documents and the deletes and doc-values updates in the frozen packet: in the repro the buffered document, the delete of a committed document (it stays searchable) and the last 2,376 of 2,200,000 updates (a stale value). The index stays structurally valid; no hang.
  • Executed entry points. commit() (the repro); forceMerge(1), after which the next commit lacks the document and the delete; and close() after a failed commit(), which returns normally and commits the same incomplete state. By code reading, flush(), NRT reopen, IndexWriter.flushNextBuffer() (IndexWriter.java:3758-3771, which treats only an Error as tragic, -> DocumentsWriter.flushOneDWPT, DocumentsWriter.java:246-258) and an indexing call whose document makes its DWPT due for flushing (DocumentsWriter.postUpdate, :400-410) reach the same doFlush path.
  • Default vs opt-in. Default IndexWriterConfig, codec and directory, one thread, assertions on or off.
  • Triggers of the same handling. (1) Executed: about 2^31 bytes of doc-values-update (or delete) terms behind one idle in-memory segment, for example 2.2 million updates of a 1 KB id; ramBytesUsed() never comes near the 2 GiB the flush will need (it peaks at about 16.8 MB during the updates and reads 2.6 MB just before the commit), so nothing warns (its root, the unbounded per-segment copy, is LFV-1077). Released 9.8.0 to 10.6.0 and main. (2) An over-long delete term makes prepareFlush's freeze throw (LFV-1046, 9.9.0 and later). (3) An InfoStream whose message() throws on "flush postings as segment": the retried commit has 0 documents (executed on main, 10.6.0, 10.5.2 and 9.12.3, and, in a version-neutral main() form with assertions off, on eight releases from 4.0.0 to 9.0.0: 4.0.0, 4.10.4, 5.0.0, 5.5.5, 6.6.6, 7.7.3, 8.11.4 and 9.0.0). (4) In production, elastic/elasticsearch#160855 (Lucene 10.5.1) logs a non-tragic IllegalStateException out of freezeGlobalBuffer <- prepareFlush <- doFlush <- IndexWriter.flushNextBuffer(), during an indexing-buffer flush inside a bulk request (Elasticsearch logs it with the message "Failed to perform engine refresh"), as a warning.
  • Likelihood: rare. It needs a non-tragic exception out of this step and then an application that continues or just closes. The 2 GiB trigger alone would be contrived; the other triggers and the production log make it rare.
  • Side observation, not part of this finding. With assertions on, a later rollback() or close() fails the internal pendingNumDocs ... != ... totalMaxDoc assertion (#10661 is the generic report).

Why it looks unintended

#
  • commit() promises "All sequence numbers <= this value will be reflected in the commit"; the retried commit returns 2,200,008 but lacks the delete (2,200,005).
  • forceMerge promises "no documents will be lost" on an Exception; forceMerge(1) fails the same way and the next commit lacks the operations.
  • Every other failure while flushing a segment is tragic (LUCENE-5987: no "silent data loss").
The full argument261 words
  • commit(). "it returns the sequence number such that all indexing operations prior to this sequence will be included in the commit point" and "All sequence numbers <= this value will be reflected in the commit" (IndexWriter.java:4202-4204, :4207-4209).
  • forceMerge. "If an Exception is hit, for example due to disk full, the index will not be corrupted and no documents will be lost." (IndexWriter.java:2213-2214). It starts with flush(true, true) (:2248); executed, it throws the same ArithmeticException, the writer stays open and the next commit lacks the operations. (That javadoc paragraph is about merging, :2213-2217; here the exception comes from the flush forceMerge starts with, so this is the weaker of the two contracts.)
  • The design rule. LUCENE-5987 (#7049): "IndexWriter will now forcefully close itself on aborting exception (an exception that would otherwise cause silent data loss)." (lucene/CHANGES.txt:11614-11616). The segment write follows it for every Throwable (DocumentsWriterPerThread.java:585-604); IndexWriter.flushFailed carries "TODO: this really should be a tragic" (IndexWriter.java:6242); getTragicException() names "disk full while flushing a new segment" as its example (:6108-6109).
  • A live upstream test retries after non-tragic commit failures and asserts nothing is lost: TestIndexWriterExceptions.testExceptionDuringSync (LUCENE-1044, TestIndexWriterExceptions.java:943-970, 23 documents). (TestIndexWriterDelete.testErrorAfterApplyDeletes states the same expectation but has been @Ignored since 2017, TestIndexWriterDelete.java:802.)
  • History. Before #12392 (9.8.0) the same workload overflowed later, in FrozenBufferedUpdates applied through IndexWriter.forceApply, which closes the writer: on 9.7.0 nothing is lost. #12392 is correct; it moved the throw into the one flush step that is not tragic.
The devil's-advocate check216 words

The argument: a maintainer wrote on open #9738 (2019) that exceptions from doFlush(), prepareCommitInternal() and others "might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback()", and that "if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss". TwoPhaseCommit says "If the 2-phase commit fails, rollback() is called" (TwoPhaseCommit.java:31), and the class javadoc promises a self-close only "if you hit an Error, or disaster strikes during a checkpoint" (IndexWriter.java:162-165).

Why it fails: that stance is in no javadoc, MIGRATE or CHANGES entry, and the same maintainer called the current behaviour inconsistent ("I am all for making it even more strict especially since it's inconsistent with what we do if addDocument fails with an aborting exception"). forceMerge's javadoc promises the opposite. close() with the default commitOnClose persists the loss with no retry at all, and under the default KeepOnlyLastCommitDeletionPolicy that commit replaces the last good one, so rollback() can no longer help. isOpen() and getTragicException() tell the caller the writer is fine. An executed review by another model family (OpenAI GPT-5.6, intended-behaviour lens) rated the argument weak, and a devil's-advocate verifier rejected it on the same grounds.

Suggested fix

#

Recommended A: doFlush makes a failure the DWPT did not already treat as aborting tragic

In DocumentsWriter.doFlush's catch, when the in-memory segment was not already aborted, give back its document count, abort it and fire onTragicEvent, as DocumentsWriterPerThread.flush does. The writer then closes itself and the last commit stays intact. Validated: the repro passes on and off; the org.apache.lucene.index tests (1,399) and :lucene:core:check pass.

All options and trade-offs4 options · 663 words

Validated with gradle in a clean scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-03): the repro fails stock with assertions on and off and passes with fix A, on and off. A check test for the InfoStream step (an InfoStream that throws on "flush postings as segment"; not part of the repro) fails stock and passes with fix A, on and off. The scratch tree was clean after reverting.

Why one catch covers both unguarded steps: a failure inside DocumentsWriterPerThread.flush's guard has already aborted the DWPT (isAborted() is true), so the new branch runs only for prepareFlush and flush's first InfoStream message; the rest of the block only enqueues events (IndexWriter.java:437-444). The tragic event only records the tragedy; the entry point's maybeCloseOnTragicEvent() in its finally then closes the writer (for commit(), IndexWriter.java:3883 in prepareCommitInternal). This is reasoning from the source plus the runs above; no stress or performance run was made.

A: doFlush makes a failure the DWPT did not already treat as aborting tragic (validated by the checks) (recommended)

#

In DocumentsWriter.doFlush's catch (Throwable t), after the markTicketFailed block: if flushingDWPT.isAborted() == false, subtract the DWPT's documents from the in-RAM count when no ticket was made, call flushingDWPT.abort() (which also gives back the writer's pending document count, DocumentsWriterPerThread.java:98-100) and, in a finally, flushNotifications.onTragicEvent(t, "flush"); then rethrow. 15 lines added, DocumentsWriter.java only. It mirrors DocumentsWriterPerThread.maybeAbort (:594-604).

} catch (Throwable t) {
  if (ticket != null) {
    ticketQueue.markTicketFailed(ticket);
  }
  if (flushingDWPT.isAborted() == false) {
    // prepareFlush, or DWPT#flush's first log line, failed outside DWPT#flush's aborting guard
    try {
      if (ticket == null) { // else the finally above already subtracted them
        subtractFlushedNumDocs(flushingDWPT.getNumDocsInRAM());
      }
      flushingDWPT.abort();
    } finally {
      flushNotifications.onTragicEvent(t, "flush");
    }
  }
  throw t;
}

Trade-offs

An application that today retries commit() after such a failure now gets AlreadyClosedException and must open a new writer: the stance LUCENE-5987 took for every other flush failure. The frozen packet is still dropped, but the writer closes, so nothing incomplete is committed and the last commit stays the recovery point. Not stress- or performance-tested.

Downstream note

#

Products that rely on deletes or updates taking effect (content removal, access changes) and keep using the writer after a failed commit or NRT reopen can serve a deleted document or a stale value after the next commit.

How it was found

#

Code reading next to the recent upstream fix #16867, which caps the writer-wide delete buffer, looked for other unbounded copies of the delete stream and found an idle in-memory segment's own copy. Public-API probes showed a commit failing there and the next commit missing operations; it was reduced to one test and confirmed by model-based fault injection.

The method in full214 words

Method: non-formal (code reading witnessed by executed public-API probes), on main 645d4fe14a20, 2026-11-02; confirmed with a model-based test.

  • #16867 (merged 2026-10-30) caps the bytes of buffered deletes and updates in the writer-wide delete queue at 1,945 MB, because the byte pools use 32-bit offsets. Reading the code around it for other copies of the same stream found the per-segment slice applied in prepareFlush, which has no cap, and the non-tragic handling when that step throws.
  • Public-API probes (default configuration) then showed commit() throwing ArithmeticException there, the writer staying open, and the next commit missing the buffered document, a delete of a committed document and updates. The case was reduced to the one JUnit test of this page.
  • A model-based test enumerated 1,554 operation sequences of up to 4 steps (adds, deletes of committed and buffered documents, doc-values updates) with a fault injected after 0 to 4 nodes of the segment's slice inside prepareFlush (7,770 scenarios, a test-only copy of the class): every one of the 1,176 faults that fired broke the oracle (a tragic close with the last commit intact, or a next commit equal to the model), and none did with the fix.
  • The second unguarded step (DocumentsWriterPerThread.flush's first InfoStream message) was found while testing InfoStream callbacks that throw.

History

Through the executed overflow trigger users can hit it since 9.8.0: #12392 (2023, correct in itself) made this overflow throw inside prepareFlush; on 9.7.0 this workload fails later and closes the writer. LFV-1078, snapshot of 2026-11-09

Registry title
An exception inside DocumentsWriterPerThread.prepareFlush is not tragic: IndexWriter stays open but drops the in-memory segment and the deletes and doc-values updates it had just frozen, so the next successful commit lacks acknowledged operations its sequence number covers
Area
index / DocumentsWriter flush failure handling (DocumentsWriter.doFlush, DocumentsWriterPerThread.prepareFlush, DocumentsWriterDeleteQueue.freezeGlobalBuffer)
Priority
Medium, rank 26: In released 9.8.0 to 10.6.0 on the default IndexWriter, a non-tragic exception inside prepareFlush leaves the writer open, and the next successful commit or close silently lacks acknowledged documents, deletes and updates. The trigger is rare, but such a non-tragic prepareFlush failure has been seen in production and an over-long delete term reaches the same path, so it sits high in Medium.
Impact class
data corruption
Impact note
Hits applications on the default IndexWriterConfig, codec and directory that keep using an IndexWriter, or close it with the default commitOnClose, after a commit, forceMerge, flush or NRT reopen failed with a non-tragic exception inside DocumentsWriterPerThread.prepareFlush: the writer reports itself healthy (isOpen() true, getTragicException() null) and the next successful commit() or close() silently lacks the acknowledged buffered documents, deletes and doc-values updates that its sequence number covers [exec: commit, forceMerge(1), close(); read: flush(), NRT reopen], while earlier commits stay intact and rollback() right after the failure restores the last commit; the executed trigger is extreme (about 2^31 bytes of doc-values-update terms buffered while one in-memory segment sits idle, through the unbounded per-segment copy that LFV-1077 describes), but an over-long delete term (LFV-1046) reaches the same handling and a non-tragic prepareFlush failure was hit in production on 10.5.1 (elastic/elasticsearch#160855); released 9.8.0 to 10.6.0 for this trigger, while 9.7.0 closes the writer instead. A second public-API trigger of the same handling: an InfoStream that throws a RuntimeException on DocumentsWriterPerThread.flush's first message loses the in-memory segment's documents the same way (writer open, the next commit lacks them) in every release since 4.0.0 [exec on 11 releases from 4.0.0 to 10.6.0 and on main; read for the others].
Summary
You buffer a document, a delete and doc-values updates in an IndexWriter, and commit() fails with an ordinary exception while the in-memory segment is being prepared for flushing (executed: ArithmeticException 'integer overflow' after about 2.2 million updateNumericDocValue calls on a 1 KB id); the writer stays open and reports no tragic exception. You expect either the writer to close itself, as it does for every other failure while flushing a segment, or the next successful commit (or close()) to contain every operation its returned sequence number covers. Instead the failed flush has already taken the buffered deletes and updates out of the shared delete queue and then drops them together with the in-memory segment, so the next commit silently lacks the buffered document, keeps the deleted document live and holds a stale doc-values value.
Introduced
b88d3e19889f (apache/lucene#12392 'Catch offset overflows in byte pool (#9660)'; 9.x backport 445b30d421c7) is the exposing change and correct in itself: ByteBlockPool.nextBuffer's Math.addExact makes the 2 GiB overflow of this workload throw inside prepareFlush (non-tragic, silent loss) instead of failing later in FrozenBufferedUpdates.applyDocValuesUpdates via IndexWriter.forceApply (tragic close, nothing lost) [read: the only changed line on that failure path between 9.7.0 and 9.8.0; exec at release level: 9.7.0 passes, 9.8.0 fails; no commit-level bisect]. The handling defect itself (prepareFlush freezes the global buffer before it applies the per-thread slice, doFlush handles a failure only for a non-null ticket, and the finally drops the DWPT) dates from e95097a7c8df (LUCENE-2956 'Support updateDocument() with DWPTs', realtime_search branch, 2011-04-13; trunk with LUCENE-3023), restructured without semantic change by LUCENE-3692 (ed4894dd8fb, 2012-01-16), #12647 (268dd54a869, 2023-10-12) and #14913 (27d1272984f, 2025-07-14) [read: git history in the full-history clone; exec: an injected fault after freezeGlobalBuffer loses the buffered document and the delete on 8.8.1 and 9.7.0 too (shadow class, history check only)] (2023-06-28 (author date of b88d3e19889f and 445b30d421c7, the exposing change); the handling defect 2011-04-13 (e95097a7c8df, LUCENE-2956))
