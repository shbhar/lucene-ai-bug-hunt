A reordered addIndexes can drop the stored fields and term vectors of the document after an empty input reader

When addIndexes(CodecReader...) runs through a merge that reorders documents (for example BPReorderingMergePolicy) and one input has no documents, the first document after it can lose its stored fields and term vectors, with no error. Adding inputs of 3, 0 and 2 documents leaves doc 3 searchable but empty.

The bug in 30 seconds

#

A merged view puts the inputs end to end; document N belongs to the last input that starts at or before N. An empty input starts where the next one starts, and the lookup can stop on the empty one.

  1. You have index A with 3 documents (a0-a2), index B with 2 (b0, b1), and an empty CodecReader with maxDoc() == 0, such as SlowCodecReaderWrapper.wrap(new ParallelLeafReader()). Each document has a stored id and a stored body with term vectors.
  2. You call addIndexes(A, empty, B) on a writer that uses BPReorderingMergePolicy with its defaults. A custom OneMerge#reorder that returns a DocMap triggers it too; the identity is enough.
  3. You expect 5 documents, each with its stored fields and term vectors. Without reordering, the same call gives exactly that.
  4. Instead doc 3 (b0) has no stored fields and no term vectors. To find the input that owns doc 3, Lucene binary-searches the input start offsets [0, 3, 3, 5]. The empty input and B both start at 3, the search stops on the empty input, and nothing is copied.
  5. Nothing reports an error, with assertions on or off, and CheckIndex finds nothing. b0 still matches its id term and keeps its doc values, and the committed new segment keeps the loss.

Who is affected

#

Applications on 9.9.0 through 10.5.2 or main that call addIndexes(CodecReader...) through a reordering merge (opt-in: BPReorderingMergePolicy or a custom OneMerge#reorder) with a maxDoc() == 0 input before a non-empty one. Such inputs are built in memory: IndexWriter never writes empty segments, so segment merges (natural and forceMerge) cannot hit it.

Mechanism, terms and numbers653 words

When a merge reorders documents, IndexWriter.addIndexes(CodecReader...) first glues its inputs end to end into one merged view and copies every document through it. To find which input owns document N, the view binary-searches the inputs' start offsets. An input with maxDoc() == 0 starts where the next input starts, and the search can stop on the empty input. The first document of the next input is then read from the empty one: in the new index it has no stored fields and no term vectors, while its terms and doc values are intact, so searches still find it but it comes back empty. No error, CheckIndex is clean, and every release from 9.9.0 to 10.5.2 and main is affected. The trigger is narrow: a reordering merge (opt-in) plus an empty input reader built in memory, which no real index produces.

Terms

#
  • addIndexes(CodecReader...) copies documents from caller-supplied readers into a new segment of the target index.
  • Reordering merge: a merge whose OneMerge#reorder returns a Sorter.DocMap that renumbers the documents, for example BPReorderingMergePolicy (misc module), which treats addIndexes as a forced merge ("addIndexes is considered a forced merge") and so reorders it whenever the merged view has a live document and the reorderer has enough memory.
  • Merged view (SlowCompositeCodecReaderWrapper): for a reordering merge, IndexWriter glues the inputs into one CodecReader and copies every document through it (IndexWriter.java:3560-3565). It records where each input starts, docStarts, the running sum of maxDoc().

The bug

#
  1. Inputs of 3, 0 and 2 documents give docStarts = [0, 3, 3, 5] (SlowCompositeCodecReaderWrapper.java:70-75): the empty input repeats the start 3.
  2. docIdToReaderId (:100-107) calls Arrays.binarySearch(docStarts, doc) and corrects the result only on a miss (-2 - pos). For doc 3 the search probes index 1 first, finds 3, and returns 1, the empty input. The owner is input 2.
  3. Only the view's stored-fields reader (prefetch, document, :156-165) and term-vectors reader (prefetch, get, :247-263) use this lookup. They ask the empty input for its local doc 0, which yields nothing for an empty ParallelLeafReader, so doc 3 is written with no stored fields and no term vectors.
  4. Postings, doc values, norms and points are merged per input, live docs use ReaderUtil.subIndex (via MultiBits, :97), and vectors use binarySearchStarts (:1093-1106), which already scans to the last equal start. So b0 keeps its terms and doc values and is still found by its id.

Which placements trigger

#

Only a document whose id equals a repeated start can be misrouted, and only when the binary search's probes land on the empty input. Executed: [3, empty, 2] and [2, empty, empty, 2] lose b0; [2, empty, 2, empty, empty, 2] loses b0 and c0; the randomized differential lost doc 0 for [empty, 6, 4, 3]. A plain replay of the Java lookup shows [empty, 3, 2], [3, 2, empty] and [2, empty, 2, empty, 2] are not hit. A trailing empty input and an all-deleted input (numDocs 0, maxDoc 1) are not hit (executed). At most one document per run of repeated starts can be lost: only the document whose id equals that start is looked up there (by reading the lookup; an executed probe with two such runs lost exactly b0 and c0). The merge must also really be reordered: IndexWriter calls reorder only without an index sort (and, with blocks, only when a parent field is set), and BP reorders only when the view has a live document and enough memory.

The numbers

#

addIndexes([a0, a1, a2], empty, [b0, b1]) with BPReorderingMergePolicy or an identity reorder: 5 documents whose stored ids, in document order, are a0, a1, a2, null, b1 (doc 3 lost); the repro fails with AssertionError: doc 3 lost its stored fields. The same call without reordering keeps all 5.

Exposure and likelihood334 words
  • Who is exposed. Applications that reorder addIndexes(CodecReader...) merges (BPReorderingMergePolicy from the misc module, or a custom @lucene.experimental OneMerge#reorder) and pass an input reader with maxDoc() == 0 at a position the binary search lands on. The merge must really be reordered (no index sort; for BP a live document in the view and enough memory). Default merge policies do not reorder.
  • How such an input arises. It must be built in memory: IndexWriter never writes a 0-document segment (SegmentMerger.java:101-103, PendingDeletes.java:88), so readers opened on real indexes cannot provide one. Examples: an empty ParallelLeafReader (upstream TestParallelReaderEmptyIndex passes exactly this to addIndexes), or a custom CodecReader that reports no documents. Segment merges cannot produce such an input unless a custom OneMerge#wrapForMerge returns a 0-document reader (not tested). No downstream caller of this shape was found in limited code searches (not exhaustive). Likelihood: rare.
  • Silent and lasting. No exception with assertions on or off, and CheckIndex reports nothing (the test framework runs it on close; the diagram probe runs it explicitly). The committed target keeps the empty document, and by reasoning later merges copy it as it is. The document is still found by queries and keeps its doc values, but fetching, highlighting or re-indexing from stored fields gets nothing for it.
  • Bounded. At most one document per run of repeated starts (by reading the lookup). In the executed probe no other document's data is substituted, deleted documents stay deleted, and the tested term queries and ACL filter return the same hits as without reordering. By reasoning: addIndexes only reads its inputs, so a fresh target can be rebuilt from them while they exist (with the fix, or without the empty input); repairing an existing target means replacing the affected documents, since a second addIndexes into it adds another copy.
  • Caveat. The silent form was shown with an empty ParallelLeafReader. Another empty reader whose stored-fields or term-vectors reader rejects local doc 0 could make the merge throw instead (not tested).

Why it is a bug, not intended

#
  • The class is documented as "A merged CodecReader view of multiple CodecReader"; the same addIndexes call without reordering keeps all 5 documents.
  • Empty inputs are accepted: nothing rejects a maxDoc() == 0 reader, and upstream TestParallelReaderEmptyIndex passes this exact reader to addIndexes.
  • The class's vector lookup already got this fix (f21ec8414c1, 2024); the stored-fields lookup did not.
The full argument312 words
  • Class javadoc: "A merged CodecReader view of multiple CodecReader" (SlowCompositeCodecReaderWrapper.java:44-45). A view whose document 3 is not input 3's first document is not a merged view of the inputs.
  • OneMerge#reorder: "Extend this method if you wish to renumber doc IDs. This method will be called when index sorting is disabled on a merged view of the OneMerge" (MergePolicy.java:312-314). Renumbering must not lose content.
  • addIndexes(CodecReader...): "NOTE: empty segments are dropped by this method and not added to this index" (IndexWriter.java:3262). No code rejects a maxDoc() == 0 input (validateMergeReader checks versions and the index sort only, :3228-3252), and TestParallelReaderEmptyIndex adds SlowCodecReaderWrapper.wrap(new ParallelLeafReader()) (:50). LUCENE-1918 (2009) already fixed exceptions when an empty ParallelReader was passed to addIndexes.
  • Consistency. The vector lookup in the same class scans to the last repeated start: "Arrays.binarySearch can return any of a sequence of repeated value but we always want the last one" (:1099-1103, added by f21ec8414c1). ReaderUtil.subIndex, used for the same job by MultiBits, scans to the last match too. It was added in 2009 (7fff5a7ea7c, LUCENE-1771) with the loop that 933bac2435e (2002, "Patched to fix a bug when empty indexes or segments exist") had added to the multi-reader lookups it descends from.
  • History. The introducing PR #12622 never discusses empty readers. No javadoc, test, CHANGES or MIGRATE entry restricts reordered inputs to maxDoc() >= 1.
  • Why tests missed it. TestParallelReaderEmptyIndex passes the empty reader alone, so no view is built (SlowCompositeCodecReaderWrapper.wrap returns a single reader as is, SlowCompositeCodecReaderWrapper.java:49-57); TestAddIndexes.testAddEmpty passes no readers; testFakeAllDeleted uses maxDoc 1; MockRandomMergePolicy overrides reorder but not findMerges(CodecReader...), so the randomized coverage that relies on it never reorders an addIndexes merge. The dedicated nightly test TestBPReorderingMergePolicy.testReorderOnAddIndexes does reorder one, but has no maxDoc() == 0 input.
The devil's-advocate check147 words

The strongest case for "works as designed" (made by an intended-behaviour checker, and separately by a reviewer from another model family, who rated it weak): the view is package-private merge infrastructure ("primarily targeted at merging, not searching"), OneMerge#reorder is @lucene.experimental, and IndexWriter never writes 0-document segments (LUCENE-5173), so only synthetic empty inputs reach the lookup; on real inputs the starts are strictly increasing and the plain binary search is correct.

Why it fails: that limits how often it happens, not whether it is wrong. The loss happens during the merge, the view's own purpose, and experimental marks API instability, not permission to drop data. Empty inputs are accepted and tested upstream, the class's other doc-to-input lookups (live docs through ReaderUtil.subIndex, vectors through binarySearchStarts) already take the last equal start, and the fix is the one the vector path received. Verdict: not intended, a defect.

Suggested fix

#

Recommended Use ReaderUtil.subIndex in docIdToReaderId (validated)

Make docIdToReaderId return ReaderUtil.subIndex(doc, docStarts), which picks the last input that starts at or before the document, as MultiBits and the vector path already do (+3/-5 lines). With it all 14 repro tests pass, and 11 neighbouring upstream suites stay green with assertions on and off.

   private int docIdToReaderId(int doc) {
     Objects.checkIndex(doc, docStarts[docStarts.length - 1]);
-    int readerId = Arrays.binarySearch(docStarts, doc);
-    if (readerId < 0) {
-      readerId = -2 - readerId;
-    }
-    return readerId;
+    // docStarts has repeated values when a reader is empty: pick the last reader that starts at or
+    // before doc, which is the only one that can contain it
+    return ReaderUtil.subIndex(doc, docStarts);
   }

Downstream note

#

Apache Solr ships an opt-in BPReorderingMergePolicyFactory, but its index-merge path passes real segments (maxDoc() >= 1), so no downstream caller that reaches this was found (limited code reading, not exhaustive).

How it was found

#

An SMT model (Z3) of the merged view's document-to-reader lookup, with exact Java int and Arrays.binarySearch semantics, showed the lookup correct when every input has documents and produced a counterexample (inputs [a, 0, b], document a) once empty inputs were allowed. A randomized differential test and a public-API JUnit test then reproduced it end to end.

The method in full220 words

Method: SMT solving (Z3, bit-vector logic) of one correctness obligation (the study's "formal" tier). The hunt unit on CodecReader wrappers modelled docIdToReaderId with exact Java int arithmetic and the JDK's Arrays.binarySearch loop, and asked for 2 to 6 inputs: can the returned input fail to contain the document?

  • Q1, every input has maxDoc >= 1: unsat for n = 2 to 6 (the lookup is correct).
  • Q2, inputs may be empty: sat from n = 3; in every witness the document sits at a start shared by an empty input and the next input, and the chosen input has maxDoc 0 (for n = 3: inputs [a, 0, b], document a). An exhaustive plain replay over maxDoc <= 4, n <= 5 found 1,320 of 37,100 lookups wrong, every one on an empty input.
  • Q3, the scan-to-last fix: unsat (the fix is complete for the modelled sizes).

The obligation was posed separately with and without empty inputs, so empty inputs were in the modeller's mind; the failing document and placement came from the solver. By file times the solver log predates the unit's randomized differential harness, which then flagged the same stored-field mismatches independently (through the view and through addIndexes with an identity reorder, only with empty inputs), and the public-API JUnit test.

LFV-318, snapshot of 2026-10-30

Registry title
A reordered addIndexes(CodecReader...) silently drops the stored fields and term vectors of the first document after an empty (maxDoc 0) input reader: SlowCompositeCodecReaderWrapper.docIdToReaderId keeps an Arrays.binarySearch hit on a repeated doc start and reads that document from the empty reader
Area
index / addIndexes reorder path: SlowCompositeCodecReaderWrapper doc-ID-to-reader lookup (stored fields, term vectors), reached through misc BPReorderingMergePolicy or any OneMerge#reorder
Priority
Low, rank 411: A reordered addIndexes permanently drops stored fields after an empty CodecReader, which is durable damage, but like LFV-202 it needs an application-built maxDoc-0 input, so it leads the hand-built-input rows.
Impact class
data corruption
Impact note
Applications on 9.9.0 through 10.5.2 or main that call IndexWriter.addIndexes(CodecReader...) through a merge that reorders documents (misc BPReorderingMergePolicy, which reorders every addIndexes merge, or any custom OneMerge#reorder that returns a DocMap, even the identity) and pass an input CodecReader with maxDoc() == 0 before a non-empty input, at a placement where the binary search lands on the empty input (for example [3 docs, empty, 2 docs]), silently get a new segment in which the first document of that non-empty input has no stored fields and no term vectors while its postings and doc values are intact, so searches still find it but it comes back as an empty document; nothing throws with -ea or -da, CheckIndex reports nothing, the loss is permanent in the target (the inputs are untouched), and no scale is needed, but IndexWriter never writes 0-document segments, so natural merges, forceMerge and readers opened on real indexes cannot trigger it and the empty input must be built in memory (for example SlowCodecReaderWrapper.wrap(new ParallelLeafReader()), as upstream TestParallelReaderEmptyIndex does).
Summary
You call IndexWriter.addIndexes(CodecReader...) with a 3-document reader, an empty reader (maxDoc() == 0) and a 2-document reader on a writer whose merge policy reorders the merge, such as BPReorderingMergePolicy or any OneMerge#reorder that returns a DocMap (the identity is enough), and you expect all 5 documents to keep their stored fields and term vectors, as they do with the same call without reordering. Instead the merged view that IndexWriter builds for the reorder (SlowCompositeCodecReaderWrapper) has doc starts [0, 3, 3, 5], Arrays.binarySearch finds start 3 at the empty reader's index, and docIdToReaderId keeps that exact hit, so merged doc 3 (the first document of the third reader) is read as doc 0 of the empty reader. The new segment is written without any error under -ea and -da: that document is still found by its id term and keeps its doc values, but its stored fields and term vectors are gone.
