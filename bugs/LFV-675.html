Geo3dRectangleShape.reset() keeps the old minX/maxX/minY/maxY, so BBoxStrategy shape values and overlap-ratio scores are wrong in the Geo3d spatial context

In the opt-in Geo3d spatial context, Rectangle.reset() never updates getMinX()..getMaxY(), so BBoxStrategy, which resets one rectangle per document, reads every document's box back as (0, 0, 0, 0). A box equal to the query scores 0.0 instead of 1.0, in every release since 7.1.0.

The bug in 30 seconds

#

A spatial4j Rectangle can be reused: reset(minX, maxX, minY, maxY) overwrites it in place. The Geo3d rectangle keeps its coordinates in four fields, and its reset replaces only the inner spatial3d box. BBoxStrategy reuses one rectangle each time it reads a segment's values, so every document reads back as that rectangle's first value, (0, 0, 0, 0).

  1. You use the Geo3d spatial context (Geo3dSpatialContextFactory) with BBoxStrategy and index two boxes: P = rect(10, 20, 30, 40) and Q = rect(15, 25, 35, 45).
  2. You read each document's box with makeShapeValueSource() and expect P and Q back. You get (0, 0, 0, 0) for both.
  3. You rank by makeOverlapRatioValueSource(rect(10, 20, 30, 40), 0.5) and expect P = 1.0 (it equals the query) and Q = 0.25 (it covers a quarter of it). You get 0.0 and 0.0, and explain says "No intersection".
  4. Why: BBoxStrategy creates one rect(0, 0, 0, 0) each time it reads a segment's values (getValues) and calls reset(...) for each document, and Geo3dRectangleShape.reset rebuilds its inner spatial3d box but never assigns the four fields the getters return. Directly: after rect(-50, -40, -30, -20).reset(10, 20, 30, 40) the rectangle equals rect(10, 20, 30, 40), yet getMinX() is still -50.
  5. No error, with assertions on or off. Lucene never resets the rectangles it queries with or indexes, so matching and the index are fine; distances use the rebuilt inner box. The default spatial4j context returns P, Q, 1.0 and 0.25. Every release since 7.1.0 (2017) has it.

Who is affected

#

Applications that use the opt-in Geo3d spatial context with BBoxStrategy and read its shape values or rank by its overlap ratio, and code that calls reset on a Geo3d rectangle. There every stored box reads back as (0, 0, 0, 0). Matching with freshly built query boxes, distances, the default spatial4j context and Lucene's core geo types are not affected.

Mechanism, terms and numbers878 words

In the opt-in Geo3d spatial context (Geo3dSpatialContextFactory, @lucene.experimental), Geo3dRectangleShape.reset(minX, maxX, minY, maxY) rebuilds the wrapped spatial3d GeoBBox but never assigns the four fields that getMinX()..getMaxY(), getWidth(), getHeight() and getCrossesDateLine() return. The reset rectangle equals the new box but reports the old coordinates. BBoxStrategy's shape-value source reuses one rect(0, 0, 0, 0) per getValues call and resets it for every document, so makeShapeValueSource() reports (0, 0, 0, 0) for every document and makeOverlapRatioValueSource() scores against that point: a box equal to the query scores 0.0 instead of 1.0. No exception. Lucene's own matching and indexing never reset a rectangle, so with freshly built rectangles they are unaffected, and distances use the rebuilt inner box; only a rectangle that application code resets itself and then queries with or indexes carries the stale bounds there. It came in with LUCENE-7951 in 7.1.0 (2017) and is in every release since and on main; a 4-line fix (assign the four fields in reset) passes every repro and the module's tests, and should land together with, or after, the fix for the class's separate getCrossesDateLine bug.

Terms

#
  • Spatial context: spatial4j's SpatialContext builds and relates shapes. Geo3dSpatialContextFactory (opt-in, @lucene.experimental) makes one whose shapes wrap spatial3d (Geo3d) shapes; its rectangles are Geo3dRectangleShape.
  • Rectangle.reset: spatial4j's "Expert: Resets the state of this shape given the arguments. This is a performance feature to avoid excessive Shape object allocation". A caller keeps one rectangle and overwrites it instead of allocating a new one.
  • BBoxStrategy (@lucene.experimental): indexes a box as four numbers (and a dateline flag). makeShapeValueSource() reads each document's box back from doc values; makeOverlapRatioValueSource(queryBox, proportion) scores each document by how much its box and the query box overlap (1.0 when they are equal).

The bug

#
  1. Geo3dRectangleShape keeps minX, maxX, minY, maxY as fields (Geo3dRectangleShape.java:39-42); Geo3dShapeFactory.rect passes the caller's raw bounds into them (Geo3dShapeFactory.java:163-173). getMinX()..getMaxY() return them (:132-150), and getWidth(), getHeight() and getCrossesDateLine() are computed from them (:118-130, :152-155).
  2. reset (:100-111) builds a new GeoBBox into the wrapped shape, clears the center and boundingBox caches, and returns. It never writes the four fields.
  3. So the object contradicts itself: equals and the rectangle's own relate use the new GeoBBox (Geo3dShape.java:55-79, :160-164), and so does getCenter(), but the getters return the old box, and so does any code that reads them (spatial4j's RectangleImpl.relate(Rectangle) reads the other rectangle's getters).
  4. BBoxValueSource creates one rect(0, 0, 0, 0) in each getValues(LeafReaderContext) call (BBoxValueSource.java:55-56, "// reused"; each call reads one segment, and a segment can get several calls) and resets it to each document's four doc values (:74). In the Geo3d context every document read through it therefore reports (0, 0, 0, 0).
  5. BBoxOverlapRatioValueSource.score computes the overlap height from the target's getMinY()/getMaxY() (BBoxOverlapRatioValueSource.java:148-156): for the query (10, 20, 30, 40) and the target (0, 0, 0, 0) it is min(40, 0) - max(30, 0) = -30, so the score is 0 with "No intersection".

Not affected (when the rectangles are built fresh)

#
  • Matching: BBoxStrategy.makeQuery reads the query rectangle's getters but never calls reset, so a freshly built query box matches correctly (code reading). In a 300-document probe with the class's separate getCrossesDateLine fix applied, the 125 queries return exactly the arithmetic truth with and without this fix. Without that fix, stock main already mismatches 62 of the 125 queries because of it, with identical aggregate counts with and without this fix (hit sets not compared query by query).
  • Distances: makeDistanceValueSource measures to getCenter(), which comes from the new GeoBBox (the table's last row). The Geo3d context measures with Geo3dDistanceCalculator, the default context with spatial4j's haversine calculator; both give degrees on the default sphere.
  • The index: documents are indexed from freshly built rectangles, so the stored numbers are right and need no reindex after a fix. Only a rectangle that the application has reset itself would be indexed with stale bounds and a stale dateline flag, and those documents would need a reindex; used as a query box, such a rectangle would also match by its stale bounds (code reading).
  • RecursivePrefixTreeStrategy, the default spatial4j contexts and Lucene's core geo types do not use this method.
Exposure and likelihood381 words
  • Who is hit. Applications that pair the Geo3d spatial context (Geo3dSpatialContextFactory, @lucene.experimental) with BBoxStrategy (@lucene.experimental) and read makeShapeValueSource() or rank by makeOverlapRatioValueSource(); and any application code that calls reset on a Geo3d rectangle. Downstream, by reading Solr's code only (not run): Solr maps spatialContextFactory="Geo3D" to this context, and its BBoxField builds the overlapRatio score on these shape values; one public downstream configuration uses such a field.
  • Default vs opt-in. Opt-in: two experimental pieces together, plus the value-source path. Within that pairing it is deterministic, assertions on or off: every document reads back as (0, 0, 0, 0), so every stored box other than (0, 0, 0, 0) itself is wrong (269 of 269 generated boxes in the probe).
  • What goes wrong. Every shape value is (0, 0, 0, 0). Overlap relevance is computed against the point (0, 0): 0.0 for every document when the query box does not contain that point (all ties, so ranking by overlap does nothing), and wrong in other ways when it does (the box -10..10 x -10..10 scores itself 0.5). Scores are wrong in general; a few can be right by coincidence.
  • At scale (follow-up probe: 300 boxes in 3 segments, 31 deleted, two tenants, 25 query boxes scored by overlap ratio): all 269 live documents report (0, 0, 0, 0). With the class's separate getCrossesDateLine bug fixed to isolate this one, 141 of 141 returned scores and the top-10 order of 16 of 25 queries differ from the default spatial4j context; with both fixes 0 of 141 and 0 of 25.
  • Silent, but contained. No exception or hang; explain says "No intersection". This bug does not change matching with freshly built query boxes, filter clauses or deletions (0 other-tenant and 0 deleted documents in the probe, all scores in [0, 1]), and an index built from fresh rectangles holds the right numbers. On stock main the same probe's matching was already wrong for 62 of 125 queries, and 77 of 218 scored documents did not satisfy the query, because of the class's separate getCrossesDateLine bug; with that fix both are 0.
  • How likely. Rare: the pairing appears little used (no upstream test combines the Geo3d context with BBoxStrategy), and nobody reported it in the nine years since 7.1.0.

Why it is a bug, not intended

#
  • spatial4j's Rectangle.reset: "Resets the state of this shape given the arguments"; spatial4j's own rectangle assigns all four bounds.
  • After reset the Geo3d rectangle contradicts itself: equals sees the new box, getMinX()..getMaxY() the old one.
  • In the introducing PR, reset cleared a bounds cache; a refactor turned the cache into four fields and dropped that line.
The full argument274 words
  • The contract. spatial4j 0.8 Rectangle.reset: "Expert: Resets the state of this shape given the arguments. This is a performance feature to avoid excessive Shape object allocation as well as some argument error checking. Mutable shapes is error-prone so use with care." getMinX(): "The left edge of the X coordinate." spatial4j's RectangleImpl.reset assigns minX, maxX, minY and maxY (four putfields in its bytecode). BBoxValueSource uses reset for exactly the documented purpose, and ShapeValues.value() "Returns a Shape for the current document".
  • The class contradicts itself. After reset, equals and the rectangle's own relate see the new box and the getters the old one.
  • The fields are the coordinates, not a constructor cache. In LUCENE-7951 (#9000) the author explained that the 6-argument constructor exists because wide Geo3d rectangles (more than 180 degrees of longitude) cannot compute their longitude bounds from the GeoBBox, and the reviewer accepted it.
  • History. In the PR's first version of the class (lucene-solr#246, ea31e5ce0f, 2017-09-07) the bounds were computed lazily from a cached LatLonBounds, and reset cleared the cache (bounds = null;). PR commit cfbac2fb00 (2017-09-12) replaced the cache with the four stored fields and removed bounds = null; from reset without assigning them. No review comment on #246 and none of the 43 comments on #9000 mention reset.
  • The sibling resets are complete. Geo3dPointShape.reset and Geo3dCircleShape.reset rebuild the wrapped shape, and their getters read it; only the rectangle caches coordinates, and only it forgets them.
  • Tests. No test under lucene/spatial-extras/src/test calls reset(, and TestBBoxStrategy uses only spatial4j's own contexts. No test, CHANGES or MIGRATE entry accepts the current behaviour.
The devil's-advocate check169 words

The strongest case for "intended" (an intended-behaviour checker): the public Lucene classes involved (Geo3dSpatialContextFactory, Geo3dRectangleShape, BBoxStrategy) are @lucene.experimental, BBoxValueSource is @lucene.internal and reuses the rectangle on purpose, spatial4j calls mutable shapes "expert" and "error-prone", the Geo3d context with BBoxStrategy is untested and partly unsupported (Geo3dShape.getArea throws UnsupportedOperationException), and nobody has reported it since 2017.

Why it fails: the "expert" warning is about callers sharing a mutable object, not a licence for reset to update half of it; experimental status warns about API changes, not wrong values; the wrong values are read right away, for the current document, with ordinary boxes; nothing documents the pairing as unsupported, and where something really is unsupported (getArea) it throws instead of returning wrong numbers; and the direct trigger, reset on a rectangle from the Geo3d factory, needs no BBoxStrategy at all. Verdict: not intended, a defect (the adjudication and independent checks; the cross-model reviewer rated the intended-behaviour argument weak under both of its lenses).

A: assign the four fields in reset (validated by the checks) (recommended)

Add four assignments after the new GeoBBox is built in Geo3dRectangleShape.reset (after line 108). Trade-offs

  • Smallest change, at the defect; the same hunk as the finder's fix. It also makes getWidth() and getHeight() right after a reset, since they read the fields, and gives getCrossesDateLine() the new bounds as input; that getter's formula stays wrong for boxes that span longitude 0 until the class's separate getCrossesDateLine fix lands (with this fix alone: crossesDateLine=true and 19.0 for -10..10 x -10..10; with both: false and 1.0).
  • Fix ordering. On main the stale (0, 0, 0, 0) happens to hide the class's separate getCrossesDateLine bug (it returns maxX > 0 && minX < 0) from the overlap scorer. With only this fix, boxes that span longitude 0 reach the scorer with the wrong flag: the self-overlap of -10..10 x -10..10 is 19.0 with assertions off and an AssertionError: 19.0 from the queryRatio assertion with assertions on; in the 300-document probe 28 of 218 scores fell outside [0, 1] with assertions off and 14 of 25 queries threw with assertions on. With both fixes: 1.0, and 0 and 0. So land it together with that fix (one PR with both lines and both tests is simplest) or after it.
  • No reindex for indexes built from fresh rectangles. Lucene's indexing does not call reset, so existing BBoxStrategy indexes built from factory rectangles hold the right numbers and read back correctly after the fix. An application that indexed rectangles it had reset itself stored stale bounds and needs to reindex those documents (code reading).

B: derive the fields from the new GeoBBox (not built)

#

Call the existing setBoundsFromshape() at the end of reset.

Trade-offs

A reset rectangle would then differ from a freshly built one: bounds derived from a GeoBBox do not round-trip exactly (-50 comes back as -49.999999999999986) and cannot be computed for boxes wider than 180 degrees of longitude, which is why the 6-argument constructor exists. Not recommended.

C: stop reusing the rectangle in BBoxValueSource (not built)

#

Build a fresh ctx.getShapeFactory().rect(...) per document instead of rect.reset(...).

Trade-offs

Fixes only the in-tree path: Rectangle.reset stays broken for application code, and the class keeps contradicting itself. By code reading it costs one extra object per document (reset already builds a new GeoBBox per document). Not sufficient on its own.

D: bring back the PR's first design (not built)

#

Compute the bounds lazily from a cached LatLonBounds and clear the cache in reset.

Trade-offs

Reintroduces the wide-rectangle problem that the stored fields solved. Not recommended.

Downstream note

#

Solr maps spatialContextFactory="Geo3D" to this context and builds its BBoxField overlap-ratio score on these shape values (read in Solr's code, not run), so such a field ranks every document against (0, 0, 0, 0).

How it was found

#

Model-based differential testing of the spatial4j-to-spatial3d bridge (not formal verification). A harness checked that a shape changed with reset reports the same coordinates as one freshly built: 10,000 of 10,000 random resets kept the old ones while equals said the shapes matched; 0 with the hunt's combined fixes applied. A public-API JUnit then showed the BBoxStrategy effects.

The method in full185 words

Method: model-based differential testing (non-formal; the finder tagged it semi-formal), in a hunt unit on the spatial4j bridge to spatial3d.

  • While modelling the shapes' mutators, the finder wrote the rule G6 of the bridge model: a shape changed with reset must equal, and report the same values as, a freshly built shape with the same arguments.
  • The harness Geo3dBridgeDiff checked G6a on 10,000 random rectangle resets (5,000 on the SPHERE and 5,000 on the WGS84 planet model): every reset rectangle kept its old getMinX()..getMaxY() while equals said it matched the fresh one; with the hunt unit's first five fixes applied together (this one among them), 0 of 10,000.
  • The finder then looked for in-tree callers of Rectangle.reset, found BBoxValueSource, and wrote a public-API JUnit on the stock main jar: a direct reset, BBoxStrategy shape values, and the overlap-ratio score compared with the default spatial4j context. It fails 3 of 3.
  • The same rule's circle family (G6d) also flagged Geo3dCircleShape.reset on WGS84 (a reset circle never equals a fresh one); it has no in-tree caller and is recorded as a lead only.

History

#

Introduced in 7.1.0 by LUCENE-7951 (035523ba7a86 on main, 85491401d54c on branch_7x, 2017-09-20). In its PR, reset first cleared a bounds cache; a refactor replaced the cache with four fields and dropped the line. 7.0.x has no Geo3d context; 7.1.0 to 10.5.2 and main fail. Never fixed.

Versions tested5 rows

Introduced by the LUCENE-7951 commit "Spatial4j implementations using Geo3d" (issue #9000, "New wrapper classes for Geo3d"): code from lucene-solr#246 by @iverase (closed without a GitHub merge), committed by @dsmiley on 2017-09-20 as 035523ba7a86 on main (first released in 8.0.0) and the same-day cherry-pick 85491401d54c on branch_7x, which shipped in 7.1.0 (it is in the 7.1.0 tag, not in 7.0.1). Geo3dRectangleShape.java is new in it, and reset has never assigned the four fields; the only later commit on the method is the LUCENE-9570 reformat 2cbf261032d (2021). Inside the PR, the first version ea31e5ce0f cleared a lazy bounds cache in reset (bounds = null;); cfbac2fb00 (2017-09-12) replaced the cache with four stored fields and dropped that line. A source scan of the 63 local release tags from 7.1.0 to 10.5.2 finds the same reset body; 8.8.2 to 8.11.3 are not tagged locally; in their release jars javap shows reset writing only shape, center and boundingBox (8.9.0 and 8.11.4 were also run). Before 7.1.0 the class and the Geo3d context did not exist, and the BBoxStrategy usage that existed then (Geo3d shapes under the default context) is still correct, so this is not an upgrade regression. Upstream main and branch_10x still have the unchanged reset.

Bug record

LFV-675, snapshot of 2026-10-29

Registry title
Geo3dRectangleShape.reset(minX, maxX, minY, maxY) replaces the wrapped spatial3d box but keeps the old minX/maxX/minY/maxY, so with the Geo3d spatial context BBoxStrategy shape values report a stale box for every document and BBoxStrategy overlap-ratio relevance scores are wrong
Area
spatial-extras / spatial4j bridge to spatial3d (Geo3dRectangleShape.reset), read by BBoxStrategy's value sources (BBoxValueSource: makeShapeValueSource, makeOverlapRatioValueSource)
Priority
Low, rank 369: It only affects scores and shape values, never matching, when two rarely combined experimental pieces are used together, the same scoring-only BBoxStrategy class as the Low row LFV-369, so it moves to Low just ahead of LFV-369 because every document is affected.
Impact class
silent wrong results
Impact note
Applications on the opt-in, @lucene.experimental Geo3d spatial context (Geo3dSpatialContextFactory; Solr exposes it as spatialContextFactory="Geo3D" and its BBoxField can score by overlap ratio, read, not run) that read BBoxStrategy value sources get wrong values with no error for every document: makeShapeValueSource reports the per-segment initial box (0, 0, 0, 0) instead of each document's indexed box (executed: 269 of 269 live documents in 3 segments), and makeOverlapRatioValueSource ranks by overlap with that constant (a document box equal to the query scores 0.0 instead of 1.0; in an executed 300-document probe, with the separate getCrossesDateLine sign bug fixed to isolate this one, 141 of 141 returned scores and the top-10 order of 16 of 25 queries differed from the default spatial4j context); application code that calls Rectangle.reset on a Geo3d rectangle itself also reads the old bounds; it is deterministic with -ea and -da, needs no scale and is in every release since 7.1.0; BBoxStrategy matching (makeQuery, executed), distance value sources (code reading), RecursivePrefixTreeStrategy, the default spatial4j contexts and Lucene's core geo types are not affected, and the index is not corrupted.
Summary
You use the Geo3d spatial context (Geo3dSpatialContextFactory) with BBoxStrategy and read each document's box with makeShapeValueSource() or rank by makeOverlapRatioValueSource(queryBox, ...), or you call reset(10, 20, 30, 40) on a Geo3d rectangle yourself. You expect reset to replace the whole rectangle (the spatial4j Rectangle.reset javadoc: 'Resets the state of this shape given the arguments'; spatial4j's own RectangleImpl.reset assigns all four bounds), so getMinX()..getMaxY() return 10, 20, 30, 40, the shape values return each document's indexed box, and a document box equal to the query scores 1.0, as it does with the default SpatialContext.GEO. Instead Geo3dRectangleShape.reset rebuilds only the wrapped GeoBBox and clears the center and bounding-box caches, never assigning the four fields that getMinX()..getMaxY(), getWidth(), getHeight() and getCrossesDateLine() read: the rectangle equals rect(10, 20, 30, 40) but reports its previous bounds, BBoxValueSource (which creates one rect(0, 0, 0, 0) per segment and resets it for each document) reports (0, 0, 0, 0) for every document, and the self-overlap score is 0.0.
