Reused sandbox HistogramCollectorManager returns an empty histogram on the same reader

Run the same sandbox HistogramCollectorManager twice on the same reader and the second histogram is silently empty: the manager remembers which segments it has counted, to avoid double counting within one search, and never forgets them. Since 10.3.0; reuse worked in 10.2.x.

The finding in 30 seconds

#

The manager keeps one map of the segments it has counted from the point tree, meant for the parallel slices of one search, and never empties it. The next search on the same reader finds its segments in the map and skips them.

How the histogram collector counts a segment

#
  1. HistogramCollectorManager(field, width) counts documents per bucket of width values. For each search, IndexSearcher asks it for collectors (newCollector()) and then merges their counts (reduce()).
  2. When the query matches a whole segment, or is a point range on the histogram field, and the field has 1-dimensional points of 4 or 8 bytes with one value per document (and few enough buckets for the segment's size), the collector counts the segment's matching documents in one pass over its point tree.
  3. With intra-segment concurrency several collectors of one search see the same segment. Since 10.3.0 they share a map of segments already counted: the first to add a segment counts it, the others skip it.

The finding, step by step

#
  1. You index one document with new LongField("f", 0, Field.Store.NO) and create manager = new HistogramCollectorManager("f", 2) (bucket width 2).
  2. The first searcher.search(MatchAllDocsQuery.INSTANCE, manager) returns [0=>1]: bucket 0 holds 1 document. The manager also notes the segment in its map of segments already counted from the point tree.
  3. You run the same call again and expect [0=>1] again, as on 10.2.x, where the manager held only its settings.
  4. Instead you get []: the segment is still in the map, so the collector skips it as already counted. No error, with assertions on or off; a new IndexSearcher over the same reader is just as empty.
  5. With 2,000 documents (values i % 10, width 5) the first search puts 1,000 documents in bucket 0 and 1,000 in bucket 1, and the second returns []. Only a reopened reader is counted again, because its segments are new objects.

Who is affected

#

Applications that keep one sandbox HistogramCollectorManager (it looks like plain configuration: field, width, max buckets) and search the same reader with it again, with a match-all query, a whole-segment match or a point range on the field. Every point-tree segment silently drops out. Default settings, one document is enough; an uncommon caller pattern, and no report of it was found.

Mechanism, terms and numbers664 words

Since 10.3.0 the sandbox HistogramCollectorManager keeps a ConcurrentHashMap<LeafReaderContext, Boolean> leafBulkCollected so that, under intra-segment concurrency, only one of the partitions of a segment counts it from the point tree. The map is a field of the manager (HistogramCollectorManager.java:56, created at :83), every collector of every search gets the same map (:88), and reduce (:91-101) never clears it. On the point-tree path, HistogramCollector.getLeafCollector counts a segment only when putIfAbsent adds it and otherwise ends collection on it (HistogramCollector.java:92-98).

So a second search with the same manager on the same reader, through the same or a new IndexSearcher, skips every segment the first search counted from the point tree: [] instead of [0=>1] for one document, [] instead of 1,000 documents in each of two buckets for 2,000. It needs a match-all query, a query that matches a whole segment, or a point range on the histogram field. There is no error. In 10.2.x the manager held only its settings and could be reused; every release from 10.3.0 to 10.6.0 and main is affected. The fix is one leafBulkCollected.clear() in reduce, as core's TotalHitCountCollectorManager does with its own per-leaf map.

Mechanism (main f794ff5a505c)

#
  1. The constructor (HistogramCollectorManager.java:73-84) stores field, bucketWidth, maxBuckets and creates one leafBulkCollected = new ConcurrentHashMap<>() per manager (:56, :83).
  2. newCollector() (:86-89) hands that same map to every HistogramCollector, in every search.
  3. HistogramCollector.getLeafCollector (HistogramCollector.java:86-99) takes the point-tree path when the query matches the whole segment (isMatchAll: weight.count(context) == context.reader().maxDoc(), :376-378) or is a PointRangeQuery on the histogram field (getPointRangeQuery, :401-415, also inside BoostQuery, ConstantScoreQuery, FunctionScoreQuery or IndexOrDocValuesQuery), and PointTreeBulkCollector.canCollectEfficiently holds (PointTreeBulkCollector.java:50-77: the segment has points, 1-dimensional, one value per document (getDocCount() == size(), :54-58), 4 or 8 bytes per dimension (:60-63), and not size() / 512 < leafMaxBucket - leafMinBucket (:65-74); when the earlier checks pass, a segment whose values fall into one bucket passes this last test, as the span is 0). Before that the field must have numeric or sorted-numeric doc values (HistogramCollector.java:77-81, else the collector throws). For MatchAllDocsQuery the count is numDocs() (MatchAllDocsQuery.java:51-53), so a segment with deleted documents does not pass the match-all test; the repro has no deletions.
  4. There, if (leafBulkCollected.putIfAbsent(context, true) == null) counts the segment (:92-95); either way CollectionTerminatedException ends collection on it (:98). The comment (:90-91) gives the purpose: "In case of intra segment concurrency, only one collector should collect documents for all the partitions".
  5. reduce (HistogramCollectorManager.java:91-101) sums the counts and never touches the map. LeafReaderContext has no equals, so keys compare by identity: the next search on the same reader finds every point-tree segment already present and counts nothing for it.

Same root, other faces (executed)

#
  • Empty as well: a new IndexSearcher over the same reader; a bare LongPoint.newRangeQuery on the histogram field after a match-all search; any query whose count equals the segment's maxDoc; a searcher with intra-segment partitions.
  • Right: a reader reopened after a change (new LeafReaderContext objects), and queries that take the doc-values path, so whether reuse works depends on the query path. DirectoryReader.openIfChanged returns null when nothing changed (DirectoryReader.java:227-245), so an application that then keeps its old reader stays affected.
  • The map also keeps every searched LeafReaderContext reachable for the manager's lifetime (sizes 1, 3, 6, 10 over four reopened readers; 0 with the fix): the same root, not a separate claim.
  • The query cache plays no part: the stale state is the manager's own map, not a cache entry. On main IndexSearcher has no query cache by default (IndexSearcher.java:82-84), but the test framework installs one that caches at random for every test (SetupAndRestoreQueryCache.java:37-43), and the repro's new IndexSearcher(reader) picks it up; the repro failed with every seed tried.
Exposure and likelihood141 words
  • Who: an uncommon caller pattern, not an observed user impact: callers that keep a manager, for example one per field and width, and run it again on the same reader, through the same or a new IndexSearcher (a reader held between refreshes). Default IndexWriterConfig, codec and searcher; the class is in lucene/sandbox, so it is opt-in.
  • Effect: every segment on the point-tree path drops out of the second and later histograms: an empty or partial result, no exception, with assertions on or off. Match-all queries, whole-segment matches and point ranges on the histogram field are exactly the cases the point-tree path was added to speed up.
  • Scale: none needed; one document is enough.
  • Likelihood: rare. Every in-tree caller, test and benchmark builds a new manager per search (TestHistogramCollectorManager, HistogramCollectorBenchmark), and no report of it was found.

Why it looks unintended

#
  • The javadoc never says single use; Lucene says so where it applies (TopScoreDocCollectorManager, TopFieldCollectorManager).
  • TotalHitCountCollectorManager clears the same kind of per-segment map in reduce so that reuse keeps working, the option a maintainer chose in #13542.
  • The map was added for the partitions of one search (#14439); reuse was never discussed, and it worked in 10.2.x.
The full argument231 words
  • Contract. The class javadoc (HistogramCollectorManager.java:30-47) says what it computes and nothing about single use. TopScoreDocCollectorManager.java:26 and TopFieldCollectorManager.java:27 say "a new collectorManager should be created for each search due to its internal states". CollectorManager (CollectorManager.java:23-55) neither promises nor forbids reuse.
  • Core's norm and remedy. TotalHitCountCollectorManager.reduce (:85-93) clears its per-leaf map: "Make the same collector manager instance reusable across multiple searches. It isn't a strict requirement but it is generally supported as collector managers normally don't hold state, as opposed to collectors." In that PR's review (#13542, 2024-07-22) javanna wrote: "Because the collector manager holds state, either we clean it in-between searches (reduce is the current place where that can be done, but that may change over time), or we declare that collector managers cannot be re-used across multiple searches (potential breaking change)." Lucene chose to clear. MIGRATE.md:1767-1775 names TotalHitCountCollectorManager as the example for per-segment logic in a collector manager.
  • History. The map was added in the #14439 review after a randomized test with intra-segment concurrency counted segments several times; the review is about the partitions of one search and never mentions reuse. The 10.3.0 CHANGES entry (CHANGES.txt:1725) and MIGRATE.md carry no single-use note, so a manager that could be reused in 10.2.x became silently single use.
  • Tests. TestHistogramCollectorManager builds a new manager for every search; no test asserts single use or the current behaviour.
The devil's-advocate check122 words

The strongest case: CollectorManager never promised reuse, the interface is @lucene.experimental, the class is sandbox, and core managers with internal state are single use by convention.

Our answer (the case is moderate, not settled): that convention is written down where it applies (the two Top* managers), not here; core's closest analogue clears the same kind of map precisely to keep reuse working; the restriction is invisible and depends on the query path (a doc-values-path query on the same manager is still right); and the result is silently wrong, not an error. So this is likely unintended, or at least an undocumented single-use restriction. Documenting single use is a legitimate maintainer choice (option B); today the restriction is neither documented nor enforced.

Suggested fix

#

Recommended A. Clear the map in reduce (validated)

Call leafBulkCollected.clear() at the start of HistogramCollectorManager.reduce, as TotalHitCountCollectorManager does, and add a javadoc note for the cases it leaves open (one instance shared by concurrent searches, reuse after a search that threw). Validated: the repro passes with assertions on and off, the histograms package tests pass (8 tests), and :lucene:sandbox:check -x test passes.

A. Clear the map in reduce (validated) (recommended)

#

One line at the start of HistogramCollectorManager.reduce.

@Override
public LongIntHashMap reduce(Collection<HistogramCollector> collectors) throws IOException {
  // Collection is finished on all leaves of this search: forget which leaves were bulk-collected
  // so that the same manager instance can be reused for another search, as

  ...

Trade-offs

  • No API change. reduce runs only after every leaf of the search is collected (CollectorManager.java:30-32), so de-duplication within one search is unchanged, and old LeafReaderContexts are no longer retained.
  • It does not make reuse safe after a search that failed before reduce, or for two concurrent searches sharing one manager (a TLA+ model of the map's lifecycle shows both; the differential test shows the failed-search case). Add a javadoc sentence for both, for example "Do not share an instance between concurrent searches, and do not reuse it after a search that threw an exception."

What the checks validated

  • Stock f794ff5a505c: the minimal test fails with assertions on and off.
  • With the fix: it passes with assertions on and off; the histograms package tests (TestHistogramCollectorManager, 7 tests, plus the new test) pass, 8 tests, 0 failures; ./gradlew :lucene:sandbox:check -x test (format, ecj lint, forbidden APIs) passes with the test in place.
  • Earlier: the 2,000-document test passes 30 of 30 with the fix, TestHistogramCollectorManager passes 140 of 140 with 20 iterations, and the differential test of reused against fresh managers (742 checks) finds 341 mismatches on stock, 227 of them without an earlier failed search, and 60 with the fix, all after a failed search.

B. Document single use

#

Add "a new collectorManager should be created for each search due to its internal states" to the class javadoc, as TopScoreDocCollectorManager does.

Trade-offs

No code change, but it makes a class that could be reused in 10.2.x single use, and callers who miss the note still get a silent wrong result. Not run.

Downstream note

#

A service that caches histogram managers would show empty or partial counts on repeated requests against an unchanged index; the trigger is the application's own reuse, not request input.

How it was found

#

Non-formal first signal: an independent reviewer from another model family (OpenAI GPT-5.6), reading the sandbox histogram code, named the invariant "a collector manager must not keep per-search state", and an executed public-API probe on main showed the empty second histogram. It was then reduced to one JUnit test and checked with a TLA+ model and a differential test.

The method in full185 words

Method: cross-model critique, then an executed probe, a TLA+ model and a differential model-based test. A read-only review by OpenAI GPT-5.6 of the sandbox histogram collectors named the unchecked invariant "a CollectorManager must not keep per-search state"; a public-API probe on stock main then showed a reused manager returning an empty histogram.

The case was reduced to one JUnit test. The map's lifecycle was modelled in TLA+ and checked with TLC (2 segments with 2 partitions each, 3 searches with one reused manager, up to 2 reopens): the stock code violates "a search that reaches reduce counted each segment once" at the second search; clearing the map in reduce is clean for sequential reuse, including reopens, and still fails after a search that failed before reduce and for concurrent searches. A differential test on the stock jar ran 300 seeded operation sequences with 742 reused-against-fresh comparisons: 341 mismatches on stock, 227 of them without any earlier failed search; with the fix 0 without a failed search (the 60 left all follow one). A reuse check over the other public collector managers was run as well.
