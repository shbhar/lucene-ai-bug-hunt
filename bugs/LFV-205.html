NRTCachingDirectory: an OS crash during commit can leave an index that will not open

NRTCachingDirectory writes a commit's cached segment files to disk only after the directory fsync that makes file names durable. An OS crash or power loss after the segments_N rename, on a file system that persisted the rename first, leaves an index that will not open until someone deletes that segments_N.

The finding in 30 seconds

#

A commit makes file names durable with one directory fsync, then publishes itself by renaming pending_segments_N to segments_N. NRTCachingDirectory writes its cached segment files to disk between the two, so their names are not covered.

Background

#
  1. Bytes and names. A file fsync makes a file's bytes durable. A directory fsync (syncMetaData) makes its names durable: which files exist, and renames. Since LUCENE-8048, Lucene assumes that names in one directory may reach the disk in any order.
  2. Commit. commit() fsyncs the directory, writes pending_segments_N, fsyncs every file the commit references, then renames pending_segments_N to segments_N. The rename publishes the commit, so a crash should leave the old commit or the new one.
  3. NRTCachingDirectory. It keeps small newly flushed or merged segment files in RAM and writes them to the wrapped directory when the commit calls sync.

The finding, step by step

#
  1. Index through new NRTCachingDirectory(dir, 5.0, 60.0) (the class javadoc's example) and commit twice, one document each. The second commit's new segment _1 is tiny, so its 3 files (_1.cfe, _1.cfs, _1.si) sit in the RAM cache.
  2. Commit 2 first fsyncs the index directory, so the 4 names on disk (_0.cfe, _0.cfs, _0.si, segments_1) are durable. Only then does NRTCachingDirectory.sync copy the 3 _1 files to disk; with an FSDirectory delegate only their bytes are fsynced, and it makes no syncMetaData() call.
  3. Commit 2 then renames pending_segments_2 to segments_2 and fsyncs the directory again. You expect a crash at any moment to leave commit 1 or commit 2.
  4. Instead, if the machine crashes when the rename has reached the disk but the 3 _1 names have not (an order the crash model Lucene adopted in LUCENE-8048 allows), segments_2 points at a missing _1.si: DirectoryReader.open, listCommits and new IndexWriter all throw CorruptSegmentInfoException.
  5. A plain FSDirectory opens fine under the same crash model: its _1 files already exist at the first fsync. Deleting segments_2 by hand recovers commit 1.

Who is affected

#

Applications that index through NRTCachingDirectory (opt-in, @lucene.experimental; Solr's default configset uses its factory) and suffer an OS crash or power loss inside commit(), on a file system that persists the rename before earlier creates. A commit with one cached segment suffices. Rare: ext4 data=ordered and XFS are not expected to reorder like this, and a JVM crash cannot cause it.

Mechanism, terms and numbers513 words

NRTCachingDirectory keeps small newly flushed segment files in RAM and writes them to the wrapped directory when IndexWriter.commit() calls Directory.sync. Since LUCENE-8048 (7.2), a commit fsyncs the index directory in SegmentInfos.prepareCommit so that every name it references is durable before pending_segments_N is renamed to segments_N, the step that publishes the commit. IndexWriter.startCommit calls directory.sync only after that fsync, so with NRTCachingDirectory the new segment files are created on disk after the barrier, and the next directory fsync comes only after the rename. On a file system that persists that rename before the earlier creates (the model LUCENE-8048 adopted; ext4 data=ordered and XFS are not expected to do it), an OS crash or power loss in that window leaves a newest segments_N whose files are missing: DirectoryReader.open, listCommits and new IndexWriter all throw until someone deletes it by hand, which recovers the previous commit. A plain FSDirectory passes the same crash test: its files exist before the barrier. One deterministic test shows it on main, 10.6.0 and older releases; all 71 releases from 7.2.0 to 10.5.2 fail the hunt's longer tests. One directory fsync in NRTCachingDirectory.sync when it wrote cached files fixes it.

The code (main 645d4fe14a20)

#
  1. The barrier. SegmentInfos.prepareCommit (SegmentInfos.java:966-972) calls dir.syncMetaData() (:970, added by LUCENE-8048) and then write(dir), which writes and fsyncs pending_segments_N (:620). Every name that exists at :970 is durable from then on.
  2. The order. IndexWriter.startCommit calls toSync.prepareCommit(directory) (IndexWriter.java:5974) and only afterwards filesToSync = toSync.files(false); directory.sync(filesToSync); (:5992-5993).
  3. What is cached. NRTCachingDirectory.createOutput sends a file to the RAM cache when doCacheWrite accepts it (NRTCachingDirectory.java:159-163): a flush or merge whose estimated size is at most maxMergeSizeMB while the cache stays under maxCachedMB (:231-245). So a small new segment is not in the wrapped directory at step 1.
  4. Where the files are created. NRTCachingDirectory.sync (:169-178) calls unCache for each name; unCache creates the file in the wrapped directory with in.copyFrom (:305-323, the copy at :319). Then in.sync(fileNames) (:177) fsyncs the files; with an FSDirectory delegate, their bytes only (FSDirectory.sync, FSDirectory.java:244-251). The class itself never calls syncMetaData.
  5. The publish. SegmentInfos.finishCommit (:996-1012) renames pending_segments_N to segments_N (:1005) and only then fsyncs the directory (:1007).
  6. Result. Between :1005 and the end of :1007, the rename and the creates of step 4 are both pending, with no order between them. If the rename reaches the disk first and the machine crashes, the newest segments_N names files that are not there (in the test: _1.si, _1.cfs, _1.cfe). With a plain directory those files already exist at step 1, so the plain control passes.

Why upstream tests miss it

#

MockDirectoryWrapper.crash() damages or deletes only files whose bytes were never fsynced and never undoes creates, renames or deletes that lacked a directory fsync: "TODO: we should also mess with any recent file renames, file deletions, if syncMetaData was not called!!" (MockDirectoryWrapper.java:339-340, :526). TestNRTCachingDirectory has no crash test.

Exposure and likelihood270 words
  • Who. Applications that write through NRTCachingDirectory, the near-real-time setup its javadoc shows (new NRTCachingDirectory(fsDir, 5.0, 60.0), NRTCachingDirectory.java:50-58). Opt-in and @lucene.experimental (:63); not the default Directory. Per the prior-report search notes, Solr's _default configset uses NRTCachingDirectoryFactory; whether Solr's commit path reaches this was not checked.
  • Trigger. A machine-level failure (OS crash, kernel panic, power loss) inside commit(), between the segments_N rename and the directory fsync after it, on a file system that persists that rename before the earlier creates. POSIX and Linux fsync(2) do not promise that order; it is the model LUCENE-8048 accepted for plain directories. Mainstream ordered-metadata journaling (ext4 data=ordered, XFS) is not expected to reorder like this, and no physical file system was tested. A JVM crash or kill -9 cannot produce the state: completed creates and renames stay visible to the next process whether or not they were fsynced.
  • Effect. Index unusable. In an independent reproducer's probe on the crash state, DirectoryReader.open, DirectoryReader.listCommits and new IndexWriter(CREATE_OR_APPEND) all throw; deleting the newest segments_N by hand recovers the previous commit (after deleting segments_2 the index opens with maxDoc=10). Whoever does that should back up the index first and make sure no reader or writer has it open. Fail-stop: in every enumerated crash state this bug causes, opening throws; none returned wrong or deleted documents. One commit that contains a cached segment is enough; whether a segment is cached depends on the flush or merge context, its estimated size and the cache's free space (NRTCachingDirectory.java:231-245).
  • How likely. Rare; no field report attributable to it was found.

The crash state is the one LUCENE-8048's model allows: the rename reached the disk, and no name created since the last directory fsync did. Every file's bytes are kept, which is generous to Lucene. Why it looks unintended

#
  • Its javadoc says "This is safe to use": on commit, "all cached files will be flushed from the cached and sync'd".
  • commit() promises to "survive an OS or machine crash or power loss"; its protocol is built to leave the old or new commit.
  • LUCENE-8048 added the directory fsync for exactly this failure; it runs before NRTCachingDirectory writes its files.
The full argument262 words
  • Contracts. NRTCachingDirectory: "This is safe to use: when your app calls {IndexWriter#commit}, all cached files will be flushed from the cached and sync'd" (NRTCachingDirectory.java:47-48). IndexWriter.commit: commits "and syncs all referenced index files, such that a reader will see the changes and the index updates will survive an OS or machine crash or power loss", and Directory#sync "should not return until the file contents and metadata are on stable storage" (IndexWriter.java:4188-4201). Directory.sync: "Lucene uses this to properly commit changes to the index, to prevent a machine/OS crash from corrupting the index" (Directory.java:104-112).
  • The design. The commit is published by one rename (Directory.java:131: rename "is used by IndexWriter to publish commits"). LUCENE-8048 (#9096, CHANGES 7.2.0 "Bug Fixes") added dir.syncMetaData() to prepareCommit for this failure on plain directories; its reporter's fix was "sync index directory after all segments have been written", and with NRTCachingDirectory the segments are written to disk only inside sync(), after that barrier.
  • History (read, not executed). In 4.8-4.10 FSDirectory.sync itself fsynced the directory after the files (LUCENE-5588), which covered the files NRTCachingDirectory had just created; 5.0 (LUCENE-5925) moved that fsync after the rename for every directory; 7.2 (LUCENE-8048) restored a barrier only before the point where NRTCachingDirectory creates its files. No javadoc, CHANGES or MIGRATE entry, test or discussion exempts NRTCachingDirectory.
  • Tests. No upstream test models lost directory updates (the MockDirectoryWrapper TODO above). Scope: only the second-commit case is claimed, because a crash during the very first commit may leave a corrupt index by design (LUCENE-4738, TestIndexWriterOnJRECrash.java:164-170).
The devil's-advocate check244 words

The strongest case: Directory.sync promises only file bytes ("any writes to these files are moved to stable storage", Directory.java:105) and names are syncMetaData's job; the crash falls inside an in-flight commit, before commit() returns; the class is @lucene.experimental; and a committer on LUCENE-8048 (Robert Muir) said a file system that behaves this way "is choosing to corrupt users data" and agreed to the barrier "just to be safe" (#9096).

Why it fails: IndexWriter.commit's javadoc asks Directory#sync for "file contents and metadata" (not decisive alone: sync and syncMetaData are separate APIs, Directory.java:104-119), and either way the combination breaks commit's documented promise to survive an OS crash or power loss, and the class's "safe to use"; no javadoc says which commit an interrupted commit leaves, but the pending_segments_N + rename protocol and LUCENE-8048 are built so that it leaves the old one or the new one, and here the index opens to neither, which is what LUCENE-8048 set out to prevent; @lucene.experimental marks API stability, not a durability exemption; and committers still made the barrier part of the protocol. Reachability lowers impact; it does not make the gap intended. Verdict: not intended, a defect. Cross-model reviewers (OpenAI GPT-5.6) rated the case for "intended" moderate and returned "real"; an intended-behaviour devil's advocate found that none of its seven points survives and returned "real". No physical file system was crashed, so the real-world reach may be close to zero on ordered-metadata file systems.

Suggested fix

#

Recommended Fsync the directory in NRTCachingDirectory.sync when it wrote cached files (validated)

In NRTCachingDirectory.sync, call in.syncMetaData() when it wrote cached files to disk, so their names are durable before the rename (+10/-3 lines). The test passes, as do the closest store and commit suites. The alternative, one more directory fsync in SegmentInfos.finishCommit before the rename, also passes; it costs every Directory one more fsync per commit.

boolean created = false;
for (String fileName : fileNames) {
  created |= unCache(fileName);
}
in.sync(fileNames);
if (created) {
  // files created in the delegate here must have durable directory entries before the
  // commit's segments_N rename (the LUCENE-8048 barrier ran before they existed)
  in.syncMetaData();
}
All options and trade-offs2 options · 707 words

Both fix sites were built and run on a scratch worktree of 645d4fe14a20. A keeps the extra fsync to the affected class; B also covers any other Directory whose sync creates files. Offer both; maintainers may prefer either. Neither was benchmarked.

Fsync the directory in NRTCachingDirectory.sync when it wrote cached files (validated) (recommended)

#

unCache returns true when it copied a cached file into the wrapped directory (false when the file was not cached), and sync calls in.syncMetaData() after in.sync(fileNames) when it did. Same change as the hunt's and the independent reproducer's fix.

boolean created = false;
for (String fileName : fileNames) {
  created |= unCache(fileName);
}
in.sync(fileNames);
if (created) {
  // files created in the delegate here must have durable directory entries before the
  // commit's segments_N rename (the LUCENE-8048 barrier ran before they existed)
  in.syncMetaData();
}

Trade-offs

  • One extra directory fsync per commit, only when the commit had cached files to write, in a class meant to cut small-file I/O. It runs inside startCommit, the first phase of the two-phase commit, which the prepareCommit javadoc says "syncs the index files" (IndexWriter.java:3721-3725).
  • Fixes only NRTCachingDirectory; another wrapper whose sync creates files would need the same.
  • Variant: call in.syncMetaData() unconditionally (simpler, but a directory fsync on every sync call, including SegmentInfos.write's sync of pending_segments_N, SegmentInfos.java:620: two per commit).

One more directory fsync in SegmentInfos.finishCommit, before the rename (validated)

#

Call dir.syncMetaData() just before dir.rename(src, dest) in finishCommit (+4 lines with the comment). If it throws, the existing catch rolls the commit back (SegmentInfos.java:1014-1017).

// Directory#sync may create files (NRTCachingDirectory writes its cached files to the
// delegate there), after the directory sync in prepareCommit: make every name this commit
// references durable before the rename publishes it
dir.syncMetaData();
dir.rename(src, dest);

Trade-offs

  • Covers any Directory whose sync creates files, not only NRTCachingDirectory.
  • One extra directory fsync per commit for every Directory, including plain FSDirectory, in the second phase of the two-phase commit.
  • Variant (not run): move the prepareCommit barrier here instead of adding one; that keeps today's fsync count but takes that fsync out of the first phase.

Downstream note

#

Solr's _default configset uses NRTCachingDirectoryFactory; whether Solr's own commit path reaches this gap was not checked.

How it was found

#

A crash-state enumerator replayed real IndexWriter commits over a recording Directory and rebuilt the crash states that LUCENE-8048's out-of-order directory-update model allows (a bounded cover). Through NRTCachingDirectory, 31 of 6,340 states could not be opened (75 more belong to a separate issue), none under the ordered model; a TLA+ model and JUnit tests confirmed it.

The method in full199 words

Method: bounded crash-state enumeration of the real jar (the hunt classes it as semi-formal: the first signal came from the executable enumerator, not from a formal tool).

  • Enumerator (2026-10-26). A recording Directory under IndexWriter logs every create, rename, delete, file fsync and directory fsync. For every crash point it builds each crash state allowed by a bounded cover of the directory operations pending since the last directory fsync, and checks that the index opens to an allowed commit with the right content, that CheckIndex is clean and that IndexWriter recovers. The nrtcaching workload was added after reading NRTCachingDirectory.sync while modelling which Directory wrappers create files late. Under the unordered model 106 of 6,340 states failed (0 of 2,350 under the ordered model); this bug's fix alone removes the 31 reader-open failures, and the remaining 75 belong to a separate IndexFileDeleter durability issue, tracked on its own.
  • TLA+ model. CommitDurability.tla (TLC): ReaderOK is violated for NRTCachingDirectory under unordered persistence and holds under ordered persistence and with the fix.
  • Executed tests. The finder's JUnit, an independent reproducer's JUnit and a cross-model reviewer's JUnit fail on stock main and pass with the fix; the minimal repro above is the smallest of them.

History

#

An NRTCachingDirectory-only gap since 7.2.0: LUCENE-8048 (2017) fixed this failure for plain directories with a directory fsync that runs before NRTCachingDirectory.sync creates its cached files, which it has done since 2011. All 71 releases from 7.2.0 to 10.5.2 fail, as do 10.6.0 and main; 6.2.0 to 7.1.0 fail for every Directory (LUCENE-8048 itself).

Versions tested6 rows

Origin: an NRTCachingDirectory-only gap since 7.2.0; the ordering behind it is older. LUCENE-8048 "Filesystems do not guarantee order of directories updates" (#9096; JIRA patch, no PR) added dir.syncMetaData() at the start of prepareCommit: 2bfe7ed0f2f9 on branch_7x (first shipped in 7.2.0; release tag dated 2017-12-19) and 4a5900728db6 on master (merged by 0688be6c6677), both 2017-12-05. That barrier runs before directory.sync in startCommit (both lines from b83dde502bc8, 2012), so it fixed plain directories but not NRTCachingDirectory, whose sync has created the cached files since the class was added (LUCENE-3092: 3525ba940fa2 on trunk, 8035a5ecf0f on branch_3x, 2011-05-17; first released in 3.2) and has never called syncMetaData. So 7.2.0 did not introduce the failure: it is the part of LUCENE-8048's failure that its fix did not reach.

Earlier gap for every directory: 4.8-4.10 fsynced the directory inside FSDirectory.sync (LUCENE-5588), which covered the files NRTCachingDirectory had just created; 5.0 (LUCENE-5925) moved that fsync after the rename, so from 5.0 the window was open for every directory; 7.2 restored a barrier only before the point where NRTCachingDirectory creates its files (read from git, not executed).

Not fixed on upstream main 716d6f216f52, branch_11x 603af8703753, branch_10_6 7e5aec4370e0 or branch_9_12 (read-only checks 2026-10-26 and 2026-10-30; branch_10x was retired on 2026-10-29, #16911).

Finding record

LFV-205, snapshot of 2026-11-01

Registry title
NRTCachingDirectory.sync creates a commit's cached segment files in the underlying directory after the commit's directory fsync, so an OS crash right after the segments_N rename can leave a newest commit whose files are missing and an index that will not open
Area
store / NRTCachingDirectory (commit durability: IndexWriter.startCommit, SegmentInfos.prepareCommit/finishCommit)
Priority
Low, rank 530: NRTCachingDirectory (Solr's default directory factory) creates a commit's cached files after the directory fsync, so an OS crash can leave an index that will not open until the newest segments_N is deleted by hand, but only on file systems that persist a rename before earlier creates, which ext4 and XFS are not expected to do.
Impact class
index unusable
Impact note
Applications that write through NRTCachingDirectory (opt-in and @lucene.experimental, but the setup its class javadoc recommends for near-real-time search; Solr's _default configset uses NRTCachingDirectoryFactory, and whether Solr's commit path is affected was not checked) whose machine has an OS crash, kernel panic or power loss inside IndexWriter.commit(), in the window between the segments_N rename and the directory fsync that follows it, on a file system that persists that rename before earlier creates in the same directory (allowed by POSIX and by the model Lucene adopted in LUCENE-8048; ext4 data=ordered and XFS are not expected to reorder like this; no physical file system was tested), are left, at any index size and in every release since 7.2.0, with an index that DirectoryReader.open, DirectoryReader.listCommits and new IndexWriter all refuse (CorruptSegmentInfoException on the newest segments_N) until someone deletes that segments_N by hand, which recovers the previous commit; only the in-flight commit is lost.
Summary
You index through NRTCachingDirectory (for example new NRTCachingDirectory(FSDirectory.open(path), 5.0, 60.0), the class javadoc's own example), call IndexWriter.commit(), and the machine crashes during that commit. You expect what Lucene's commit protocol and LUCENE-8048 are built for: after the crash the index opens to the previous commit or to the new one, because SegmentInfos.prepareCommit fsyncs the directory before the commit is published by renaming pending_segments_N to segments_N. Instead the newly flushed segment files are still in NRTCachingDirectory's RAM cache at that directory fsync; NRTCachingDirectory.sync creates them on disk only afterwards and fsyncs their bytes but never the directory, so the rename can become durable before the new files' names do, and in that crash state every open fails (CorruptSegmentInfoException: segment info file _1.si cannot be read), while the same steps on a plain FSDirectory open fine.
Introduced
4a5900728db6a84b4aea42545567a393989f25cf (master, merged by 0688be6c6677) and 2bfe7ed0f2f9 (branch_7x, the copy that shipped first, in 7.2.0): LUCENE-8048 'Filesystems do not guarantee order of directories updates' (committed by Erick Erickson from the JIRA patch; no PR; migrated as #9096) [read: git blame of SegmentInfos.java:970 and git log -S in the full-history clone] [exec: the 7.1.0 / 7.2.0 boundary]. An incomplete fix, not a regression: it added the dir.syncMetaData() barrier at the start of SegmentInfos.prepareCommit, which IndexWriter.startCommit calls before directory.sync(filesToSync) (both lines b83dde502bc8, 2012), while NRTCachingDirectory.sync, which creates the cached files in the delegate inside that sync call (unCache -> copyFrom), has had the same logic since the class was added (LUCENE-3092, 3525ba940fa2 on trunk and 8035a5ecf0f on branch_3x, 2011-05-17) and has never called syncMetaData (git log --all -S syncMetaData on NRTCachingDirectory.java: no commit) (2017-12-05)
First affected version
7.2.0 [exec] (release tag 2017-12-19; CHANGES 7.2.0 'Bug Fixes' lists LUCENE-8048). The 18 releases 6.2.0 to 7.1.0 [exec] fail the same crash test, but so does the plain-FSDirectory control, because no directory fsync preceded the rename at all (LUCENE-8048 itself), so they are not counted as this bug; 6.1.0 and earlier: no verdict (the crash-model hooks Directory.rename and Directory.syncMetaData arrived in 6.2.0 with LUCENE-7373; 6.1.0 does not compile)
Affected versions
every release from 7.2.0 through 10.5.2, 10.6.0 (run later in the bug doc's checks, see below) and main ea57360912ed. [exec] all 71 Maven Central releases from 7.2.0 to 10.5.2 with two independently written JUnit crash-model repros (the finder's, seed DEADBEEF, and the independent reproduction's, seed C0FFEE01): in each, the NRTCachingDirectory second-commit crash state cannot be opened while the plain-FSDirectory control and a never-caching NRTCachingDirectory(0.0, 0.0) control open with all documents; main fails under -ea and -da, and with the fix shadowed main passes. The wrapping exception differs by version (CorruptIndexException 'Unexpected file read error while reading index' on 7.2.0-10.5.2, CorruptSegmentInfoException on main); the cause is always NoSuchFileException for the new segment's .si. [read] not fixed upstream: NRTCachingDirectory.sync still has no syncMetaData on main, branch_10x, branch_10_6 and branch_9_12 (read-only check 2026-10-26); 10.6.0, released from branch_10_6 on 2026-10-29, is affected too: the bug doc's minimal test fails 1 of 1 on the 10.6.0 release jars with -ea and -da [exec, 2026-10-30]. History [read, not executed]: in 4.8-4.10 FSDirectory.sync fsynced the directory after the files (LUCENE-5588), which also covered the files NRTCachingDirectory had just created; 5.0 (LUCENE-5925) moved that directory fsync after the rename, opening the gap for every Directory, and 7.2 (LUCENE-8048) closed it only for files that already exist at prepareCommit. Before 5.0 the commit protocol had no rename and is not analysed. All runs on aarch64 with JDK 25.0.3.
