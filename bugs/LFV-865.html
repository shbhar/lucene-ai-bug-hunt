AutomatonToTokenStream throws ArrayIndexOutOfBoundsException for the empty automaton (Automata.makeEmpty())

Lucene's "matches nothing" automaton has 0 states, and the converter reads the in-degree of state 0 without checking that it exists; every release since 8.10.0 has it.

The finding in 30 seconds

#

Background: automata, the empty language and AutomatonToTokenStream

#
  1. An Automaton is a set of numbered states with labelled transitions. State 0 is always the start state; reaching an accept state at the end of the input means a match.
  2. An automaton that matches nothing has the empty language. Lucene usually represents it with no states at all: Automata.makeEmpty() returns one, and so do operations whose result matches nothing, such as intersecting "a" with "b".
  3. AutomatonToTokenStream.toTokenStream turns an acyclic automaton into a token graph: states at the same distance from the start become one position, and each transition becomes a token. Before that, it checks that the start state has no incoming edges.

The finding, step by step

#
  1. Build an automaton that matches nothing, for example Automata.makeEmpty() or Operations.intersection(Automata.makeString("a"), Automata.makeString("b")). Lucene represents both with 0 states.
  2. Convert it with AutomatonToTokenStream.toTokenStream(automaton). Its only stated precondition, a finite DAG, holds (the automaton has no cycles; that it also has no start state, which the method assumes, is not in the javadoc).
  3. You expect a token stream with 0 tokens, which is what the method already returns for Automata.makeEmptyString() and for the same empty language written as 1 non-accepting state. Or at least an IllegalArgumentException, which the method's own two input checks throw.
  4. Instead it throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0, with assertions on and off. The method sizes int[] indegree to the number of states, here 0, and then reads indegree[0] to check the start state (AutomatonToTokenStream.java:61).
  5. This read has been there since the class was added in 8.10.0 (#157). No Lucene production code calls the converter, so only applications that call it themselves are hit.

Who is affected

#

Only applications that themselves call the public AutomatonToTokenStream.toTokenStream with an automaton that matches nothing, such as an empty string union or an empty intersection. No Lucene query, analyzer or index path calls it (only two test classes do), and no use was found in Solr, Elasticsearch or OpenSearch. That one call fails at once; nothing else breaks. Rare.

Mechanism, terms and numbers598 words

AutomatonToTokenStream.toTokenStream(Automaton) (lucene-core, public, no @lucene.internal or @lucene.experimental tag) turns an acyclic automaton into a token graph; its only stated precondition is "This requires the automaton be a finite DAG" (AutomatonToTokenStream.java:44, :46). Lucene's normal value for the empty language has no states: Automata.makeEmpty() ("a new (deterministic) automaton with the empty language", Automata.java:55-60), an empty makeStringUnion, RegExp #, and empty results of Operations.intersection, minus or removeDeadStates. For such an automaton the method sizes int[] indegree to the number of states, 0 (:52, :54), and reads indegree[0] at :61 to check that the start state has no incoming edges, without checking that a state exists, so the JVM throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 with assertions on and off. The same empty language written as one non-accepting state already gives a stream with 0 tokens, as does Automata.makeEmptyString(). The read dates from the class's introduction in #157 (LUCENE-9963, 8.10.0); every release since fails, and it is not fixed upstream. A 4-line guard that returns the empty-string stream for 0 states fixes it (validated); throwing a clear IllegalArgumentException is the alternative. Low impact: no Lucene production code calls the converter, and no downstream use was found.

Terms

#
  • Automaton (org.apache.lucene.util.automaton, @lucene.experimental): states are integers, "State 0 is always the initial state" (Automaton.java:37-38); transitions carry character ranges; accept states end a match.
  • Empty language: the automaton accepts no string at all. Lucene's usual form has 0 states: Automata.makeEmpty() is new Automaton() plus finishState() (Automata.java:55-60), and Operations.isEmpty calls 0 states the "Common case" of the empty language (Operations.java:799-803). One non-accepting state with no transitions has the same language.
  • AutomatonToTokenStream.toTokenStream (org.apache.lucene.analysis, lucene-core, public): "Nodes that have the same distance from the start are grouped together to form the position nodes for the TokenStream"; "This requires the automaton be a finite DAG" (AutomatonToTokenStream.java:40-47). It was added as a helper for the FlattenGraphFilter tests.

The bug

#
  1. Transition[][] transitions = automaton.getSortedTransitions(); (:52) has one row per state (Automaton.java:116-118): for 0 states, length 0.
  2. int[] indegree = new int[transitions.length]; (:54): length 0. The loop that counts in-degrees (:56-60) runs 0 times.
  3. if (indegree[0] != 0) (:61) checks that the start state has no incoming edges and would throw IllegalArgumentException("Start node has incoming edges, creating cycle"). With no state 0, the read itself throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0, before the check can run.
  4. With 1 non-accepting state, the same empty language passes: indegree is [0], the check passes, the walk (:65-85) puts state 0 at position 0, there are no edges, and the stream has 0 tokens. makeEmptyString() (1 accepting state) takes the same path.

The numbers

#

Automata.makeEmpty(): 0 states, indegree.length 0, exception. Nine public ways to a 0-state automaton all throw the same way: Automata.makeEmpty(), Automata.makeStringUnion of an empty list, RegExp # and a&b (with RegExp.ALL), Operations.intersection(makeString("a"), makeString("b")), Operations.minus of two equal languages, Automata.makeCharRange(5, 4), an empty Automaton.Builder, and Operations.removeDeadStates of one non-accepting state. Controls: the 1-dead-state form and makeEmptyString() give 0 tokens. These nine inputs and two controls ran on main (assertions on and off), 10.5.2 and 9.12.3 (assertions off), all with the same result. makeEmpty() also fails on 10.6.0 (the minimal test, assertions on), and makeEmpty() and the empty intersection fail on all 40 releases from 8.10.0 to 10.5.2 (assertions on), where the controls makeEmptyString() and makeString("abc") give 0 and 3 tokens.

Exposure and likelihood228 words
  • Who is hit. Code that calls AutomatonToTokenStream.toTokenStream with an automaton whose language is empty in its 0-state form, for example (illustrative, not found in any project) a helper that builds an automaton from a possibly empty list of strings with Automata.makeStringUnion, or that intersects two automata and converts the result.
  • Who is not hit. No Lucene production code calls the converter: its only callers in the tree are the tests TestAutomatonToTokenStream (core) and TestFlattenGraphFilter (analysis-common). A GitHub code search found 0 files in Elasticsearch, OpenSearch and Solr, and 53 files overall, all copies of Lucene. No query, analyzer, parser or index path reaches it.
  • What happens. One ArrayIndexOutOfBoundsException whose message ("Index 0 out of bounds for length 0") points into the converter, not at the input.
  • What does not happen. No wrong tokens, no hang, no memory growth; the input automaton is not changed and nothing is written.
  • Default vs opt-in, scale. Opt-in: only an application that uses this utility. No setting is involved, and data size plays no part: the trigger is exactly an automaton with 0 states. Deterministic, with assertions on and off.
  • How likely. Rare. The class was added in #157 as test infrastructure for FlattenGraphFilter (the reviewer called it "helpful infrastructure for future testing" and "a nice utility API"), and no report of this failure was found in the five years since 8.10.0.

Why it looks unintended

#
  • The only documented precondition is a finite DAG; Automata.makeEmpty() is documented as "a new (deterministic) automaton with the empty language".
  • The same empty language with 1 non-accepting state already returns an empty stream; only the 0-state form crashes.
  • The method's two explicit input checks throw IllegalArgumentException, which its tests assert; the crash happens on the first check's own line.
The full argument217 words
  • Contract. AutomatonToTokenStream.java:44: "This requires the automaton be a finite DAG." :46: "@param automaton automaton to convert. Must be a finite DAG to avoid infinite loops!" Nothing says the automaton must have a state. The class has no @lucene.internal or @lucene.experimental tag (the automaton classes it takes, Automaton, Automata and Operations, are @lucene.experimental).
  • A standard input. Automata.makeEmpty(): "Returns a new (deterministic) automaton with the empty language." (Automata.java:55), with 0 states. Operations.isEmpty treats 0 states as the common empty case (Operations.java:799-803).
  • Representation, not language, decides the outcome. The same empty language as 1 dead state gives a stream with 0 tokens (executed); as 0 states it crashes.
  • Its own validation throws IllegalArgumentException. Its two explicit checks reject a start state with incoming edges (:61-63) and leftover cycles (:87-91) with IllegalArgumentException, and the upstream tests assert exactly that (TestAutomatonToTokenStream.java:105-120 and :122-136, expectThrows(IllegalArgumentException.class, ...)).
  • Precedent. Lucene's own topological sort of automata (org.apache.lucene.util.automaton, today Operations.topoSortStates) got an explicit 0-state guard in LUCENE-6365 (ae4723e0b50, 2015, "fix buggy Operations.topoSort; add test"), today Operations.java:1366-1368.
  • No sign of intent. The introducing PR #157 and LUCENE-9963 never mention empty or 0-state automata; no upstream test passes one; no CHANGES or MIGRATE entry.
The devil's-advocate check163 words

The strongest case for "not a bug" (the intended-behaviour checker's and the cross-model reviewers'): the javadoc builds positions from "distance from the start" (:42) and Automaton says "State 0 is always the initial state" (Automaton.java:37-38), so an automaton with no states has no start and could be read as outside the method's domain; and the class is a test-oriented helper.

Why it fails: nothing documents that precondition, while the documented one (a finite DAG) holds; the method already handles the same language when it has one dead state; an input the method does not accept should get the method's own IllegalArgumentException, not an index error from its validation line; and "test-oriented" bears on severity, not on validity, since the class is public API in the lucene-core jar. Residual: a maintainer may prefer to reject 0 states with an IllegalArgumentException rather than return an empty stream. That is a choice of fix (option B), and the repro accepts it.

Suggested fix

#

Recommended A. Return the empty-string stream for 0 states

Return the empty-string stream when the automaton has no states: a 4-line getNumStates() == 0 guard at the top of toTokenStream. The 0-state form then behaves like the 1-dead-state form of the same language. With it the repro passes with assertions on and off, and the core analysis tests, TestFlattenGraphFilter and core's static checks pass.

--- a/lucene/core/src/java/org/apache/lucene/analysis/AutomatonToTokenStream.java
+++ b/lucene/core/src/java/org/apache/lucene/analysis/AutomatonToTokenStream.java
@@ -49,6 +49,10 @@
   public static TokenStream toTokenStream(Automaton automaton) {
     List<IntArrayList> positionNodes = new ArrayList<>();
 
+    if (automaton.getNumStates() == 0) {
+      // the empty language: no tokens (same stream as for the empty string)
+      return new TopoTokenStream(List.of(List.of()));
+    }
     Transition[][] transitions = automaton.getSortedTransitions();
 
     int[] indegree = new int[transitions.length];
All options and trade-offs2 options · 585 words

The choice is the maintainer's: this doc suggests A because the 0-state form then behaves like the 1-dead-state form of the same language; the cross-model fact check of the brief would make B the default, because it states the implicit start-state requirement and does not merge the empty language with the empty string. Both are validated; neither is shown to be better. Fix A was validated through gradle in a scratch worktree of 645d4fe14a20. Option B, the alternative the adjudication asked to offer, was validated with the fix shadowed into the stock jars only.

A. Return the empty-string stream for 0 states (validated by the checks) (recommended)

#

Before reading indegree, return the stream that the method already builds for makeEmptyString() and for the 1-dead-state form: one position layer with no edges.

--- a/lucene/core/src/java/org/apache/lucene/analysis/AutomatonToTokenStream.java
+++ b/lucene/core/src/java/org/apache/lucene/analysis/AutomatonToTokenStream.java
@@ -49,6 +49,10 @@
   public static TokenStream toTokenStream(Automaton automaton) {
     List<IntArrayList> positionNodes = new ArrayList<>();
 
+    if (automaton.getNumStates() == 0) {
+      // the empty language: no tokens (same stream as for the empty string)
+      return new TopoTokenStream(List.of(List.of()));
+    }
     Transition[][] transitions = automaton.getSortedTransitions();
 
     int[] indegree = new int[transitions.length];

Trade-offs

  • The 0-state form of the empty language then behaves like its 1-dead-state form, which already returns this stream. No change for any automaton with at least one state.
  • The stream is the one makeEmptyString() gives, so it cannot tell the empty language from the empty string; that is already true for the 1-dead-state form. In the other direction, TokenStreamToAutomaton turns this stream into an automaton that accepts nothing (executed on the stream of makeEmptyString(), which is this stream). A cross-model reviewer suggested the code comment not imply that the two languages are the same in general.
  • Keep the one empty layer: with List.of() (no layer), end() would call setOffset(-1, -1), because it uses edgesByPos.size() - 1 (:165-170, code reading).

B. Reject 0 states with a clear IllegalArgumentException (validated by the checks)

#

Throw the method's own exception type with a message that names the cause, and document it in the javadoc.

+    if (automaton.getNumStates() == 0) {
+      throw new IllegalArgumentException("Automaton has no states (empty language)");
+    }

Trade-offs

  • Explicit, and it does not equate the empty language with the empty string.
  • The outcome still depends on the representation (1 dead state gives an empty stream, 0 states throws), so the javadoc should say that an automaton with no states is rejected, and callers must special-case empty languages before converting.

What the checks validated

  • Shadowed into the stock 645d4fe14a20 jars (standalone, assertions on): the minimal repro and the upstream TestAutomatonToTokenStream pass, 7 tests, 0 failures. Not run through gradle.

Downstream note

#

No use of AutomatonToTokenStream was found in Elasticsearch, OpenSearch or Solr; an application that may pass an automaton that matches nothing can avoid the crash by checking automaton.getNumStates() == 0 before converting.

How it was found

#

Semi-formal. An AI tool wrote a bounded-exhaustive model of the converter's documented construction to check its output on every small automaton. The model needs a start state; writing that precondition down showed that the code reads indegree[0] without checking that any state exists. A public-API JUnit test on the stock jars then showed the exception.

The method in full169 words
  • Method: bounded-exhaustive translation validation, the hunt's semi-formal tier, in the hunt unit on token-graph and automaton conversion. The unit compared the stock jar's token graphs with an independent model of the documented construction over all small automata with at least one state (for example all 33,554,432 topologically numbered 5-state automata over {a, b}). In every automaton in scope the jar threw nothing other than IllegalArgumentException.
  • The hint: the model needs a start state, so its precondition excluded 0 states; writing that down showed that the code reads indegree[0] with no such check.
  • Witness: a JUnit test on the stock main jar (makeEmpty(), an empty intersection, and a makeEmptyString() control) failed on both empty inputs while the control passed; a shadowed 4-line fix made it pass.
  • Later: an independent reproducer, an intended-behaviour devil's advocate, cross-model reviews and an adjudication checked it (2026-10-28); the history was checked by execution over 40 releases; the test was reduced to one test method (2026-10-29) and re-verified on main 645d4fe14a20.

Impact note
Code that converts an automaton with the public lucene-core utility AutomatonToTokenStream.toTokenStream and passes an empty-language automaton in its 0-state form (Automata.makeEmpty(), Automata.makeStringUnion of an empty list, RegExp "#", or an empty result of Operations.intersection, minus or removeDeadStates) gets an ArrayIndexOutOfBoundsException instead of an empty stream or a clean IllegalArgumentException; the failure is immediate and loud, nothing is corrupted or persisted, no setting is involved, the converter has no in-tree production caller (tests only) and no downstream use was found, in every release since 8.10.0 (executed).
Summary
You convert an automaton whose language is empty, for example Automata.makeEmpty() or Operations.intersection(Automata.makeString("a"), Automata.makeString("b")), with AutomatonToTokenStream.toTokenStream, whose only stated precondition is a finite DAG. You expect a TokenStream with no tokens (what the same method already returns for Automata.makeEmptyString() and for the same empty language written with one dead state) or at least a clear IllegalArgumentException. Instead it throws ArrayIndexOutOfBoundsException 'Index 0 out of bounds for length 0', because these automata have 0 states and the method reads indegree[0], the in-degree of the start state, without checking that a state exists.
