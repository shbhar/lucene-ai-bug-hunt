kNN query rewrite throws instead of matching nothing when a leaf's parent reader has no documents

Rewriting a KnnFloatVectorQuery (k = 3) over new MultiReader(new ParallelLeafReader()) throws instead of returning MatchNoDocsQuery: the leaf's share of its parent is 0 / 0 = NaN, and that turns the leaf's top-k into 0. A regression in 10.3.0; in practice only readers composed in memory have such a leaf.

The finding in 30 seconds

#

Before searching a leaf, a kNN query sizes that leaf's top-k collector by the leaf's share of its parent reader, leaf.maxDoc() / (float) parent.maxDoc(). An empty leaf under an empty parent gives 0 / 0f = NaN, (int) Math.max(1, NaN) is 0, and a collector of size 0 fails.

Background: how a kNN query splits k across leaves

#
  1. A reader is a tree: leaves (segments) under composite readers such as MultiReader. A kNN query searches every leaf and merges the per-leaf hits into one global top k.
  2. Since 10.3.0 a leaf does not collect all k hits. It collects its expected share of them plus a margin, and leaves whose hits all made the global top k are searched a second time. The share is the leaf's maxDoc divided by its parent's maxDoc.
  3. IndexWriter does not write 0-document segments, so in practice a leaf with 0 documents comes from a reader composed in memory, for example new ParallelLeafReader() with no sub-readers.

The finding, step by step

#
  1. Compose a reader with no documents from public API: new MultiReader(new ParallelLeafReader()). Its one leaf has maxDoc 0, and so does that leaf's parent. Rewrite KnnFloatVectorQuery("v", {1, 0}, 3) with new IndexSearcher(reader, Runnable::run).
  2. You expect MatchNoDocsQuery: the rewrite returns it when nothing is found, and 10.2.2 returns it for this reader.
  3. Since 10.3.0 each leaf collects only its share of k plus a margin. The share is the leaf's maxDoc divided by its parent's: a leaf holding 1 of 3 documents gets share 1/3 and a per-leaf k of (int) max(1, 1 + 16 * sqrt(2/3)) = 14. Here the share is 0 / 0f = NaN.
  4. Math.max(1, NaN) is NaN, so the floor of 1 is lost, and (int) NaN is 0. With assertions on, assert perLeafTopK > 0 fails; with them off, the collector's heap throws IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: 0.
  5. KnnByteVectorQuery and a match-all filter fail the same way. A parent with documents is fine (share 0, per-leaf k 1), and IndexWriter does not write 0-document segments.

Who is affected

#

Applications that compose a reader in memory with an empty leaf under an empty parent, such as new MultiReader(new ParallelLeafReader()), and run a kNN query on it. Plain search there already fails through LFV-202, so today it shows through kNN rewrite, explain and search; after LFV-202's fix, unfiltered and match-all-filtered kNN searches still fail. Never a wrong result.

Mechanism, terms and numbers586 words

Since 10.3.0 a kNN vector query sizes each leaf's top-k collector by the leaf's share of its immediate parent reader, leaf.maxDoc() / (float) parent.maxDoc(). For a 0-document leaf under a 0-document parent that is 0 / 0f = NaN; Math.max(1, NaN) keeps the NaN, the int cast gives 0, and a collector of size 0 fails: AssertionError with assertions on, IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: 0 from the heap with them off. So rewriting KnnFloatVectorQuery("v", {1, 0}, 3) over new MultiReader(new ParallelLeafReader()) throws instead of returning MatchNoDocsQuery, which 10.2.2 and 9.12.3 return. It came with #14226 and is in every release from 10.3.0 to 10.6.0. IndexWriter does not write 0-document segments, so in practice only readers composed in memory are affected; the failure is loud, never a wrong result, and ordinary search on such readers already fails through LFV-202.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/search/AbstractKnnVectorQuery.java)

#
  1. Optimistic collection is the default. rewrite wraps the default TopKnnCollectorManager (:305-307) of every KnnFloatVectorQuery and KnnByteVectorQuery in an OptimisticKnnCollectorManager (:106-110) and runs one task per leaf of reader.leaves() (:112-118).
  2. The share divides by the immediate parent. OptimisticKnnCollectorManager.newCollector (:318-333): when the delegate is optimistic and context.parent != null (:324), leafProportion = context.reader().maxDoc() / (float) context.parent.reader().maxDoc() (:326). An empty leaf under an empty parent gives 0 / 0f, NaN.
  3. The floor does not catch NaN (the fix site). perLeafTopKCalculation returns (int) Math.max(1, k * p + LAMBDA * Math.sqrt(k * p * (1 - p))) with LAMBDA = 16 (:343-347, :57). Math.max(double, double) returns NaN when an argument is NaN, and casting NaN to int gives 0.
  4. Only an assert stands guard. The comment "if we divided by zero above, leafProportion can be NaN and then this would be 0" (:328) is followed by assert perLeafTopK > 0 (:329). With assertions off the 0 reaches TopKnnCollectorManager.newOptimisticCollector -> new TopKnnCollector(0, ...) (TopKnnCollectorManager.java:49-53) -> NeighborQueue -> TernaryLongHeap(0), which rejects any capacity below 1 (TernaryLongHeap.java:56-64).
  5. Before any field check. KnnFloatVectorQuery.approximateSearch creates the collector (KnnFloatVectorQuery.java:107-108) before it checks for a missing field (:110-114) or k() == 0 (:115-117), so a leaf without the vector field still gets there. KnnByteVectorQuery is the same (:106-116).
  6. The filtered path is harmless. With a real filter, getLeafResults computes the same share (:272-276), but there a NaN only makes cost <= perLeafTopK (0 <= 0) pick exact search, which returns no hits (:282-285).

Exposure and likelihood224 words
  • Who. Applications that compose a reader in memory in which a 0-document leaf sits under a 0-document parent: new MultiReader(new ParallelLeafReader()), or such an empty composite nested inside a MultiReader that has documents. Standard readers over indexes that IndexWriter created do not reach the trigger: it does not write 0-document segments (IndexWriter.java:5669-5677), and a fully deleted segment still has maxDoc > 0.
  • What shows today. Every reader that triggers this also has a 0-document leaf, and LFV-202 already makes plain search/count and the no-executor IndexSearcher constructor throw on it. On its own, this bug shows through IndexSearcher.rewrite / Query.rewrite and explain(knn, doc) on an executor-backed searcher, and it decides which exception a full kNN search throws, since the rewrite runs before slicing.
  • After LFV-202 is fixed. A searcher whose slices leave out the empty leaf (a stand-in for LFV-202 fixed) counts 3 hits for MatchAllDocsQuery on the nested reader, while the kNN search still throws. So this is the next failure on the same readers.
  • Default vs opt-in. The per-leaf share is the default kNN path since 10.3.0, with no setting involved. The executor constructor is @lucene.experimental.
  • Effect and scale. One loud exception per query; no wrong or missing hits and no index change. No scale or unusual parameter: k = 3 and a 2-d vector. Likelihood: contrived.

Why it looks unintended

#
  • The code floors the per-leaf k at 1 (Math.max(1, ...)) and asserts perLeafTopK > 0; NaN slips past the floor, and nothing documents an exclusion.
  • The rewrite returns MatchNoDocsQuery when nothing matches, as upstream testEmptyIndex asserts; 10.2.2 and 9.12.3 return it here.
  • new ParallelLeafReader() with no sub-readers is legal public API, and upstream tests build one.
The full argument232 words
  • The code's own floor. Math.max(1, ...) in perLeafTopKCalculation (AbstractKnnVectorQuery.java:343-347) shows the intended minimum per-leaf k is 1, and assert perLeafTopK > 0 (:329) states it as an invariant. Here the assert is an internal invariant, not a documented public precondition or failure mode.
  • Contract and tests. The rewrite returns MatchNoDocsQuery when nothing is collected (:153-155), and BaseKnnVectorQueryTestCase.testEmptyIndex asserts that result for an index with no documents (BaseKnnVectorQueryTestCase.java:165-176). The KnnFloatVectorQuery and KnnByteVectorQuery constructors document one error, "if k is less than 1". No javadoc, CHANGES or MIGRATE entry excludes empty leaves or empty parents.
  • The input is legal. ParallelLeafReader has an explicit branch for zero sub-readers (maxDoc = numDocs = 0, ParallelLeafReader.java:96-98), and upstream TestParallelReaderEmptyIndex builds new ParallelLeafReader() (:50).
  • History. 10.2.2 and 9.12.3 return MatchNoDocsQuery for the same input. #14226 replaced the size-k collector per leaf with the share-based size and added the comment and the assert in the same commit; none of its 65 review and issue comments mentions NaN, division by zero or empty readers.
  • Precedents. #15334 (merged 2025-10-14, under Bug Fixes) fixed a null-parent NPE on these same lines (for MemoryIndex) and left the zero divisor alone. LUCENE-10351 (#11387, fixed by #580 in 2022): a kNN heap of capacity 0 on a segment where every document with the kNN field was deleted, fixed to return empty results.
The devil's-advocate check130 words

The strongest case for "intended": the author saw the NaN case (the comment) and accepted it, so a parent with maxDoc 0 is unsupported. Empty leaves are already unsearchable through LFV-202, the executor constructor is experimental and rewrite is expert API.

Why it fails: an assert is not a precondition users can see, nothing documents the exclusion, and with assertions off the result is an internal heap error, not a validation message. LFV-202 has a different fix site, and fixing it leaves this bug in place. The executed cross-model review (OpenAI GPT-5.6) and the devil's-advocate verifier both rated it real. Verdict: not intended, a Low robustness defect. A maintainer may still fold it into LFV-202's fix or call it too minor; that is a fair outcome for a Low bug.

Suggested fix

#

Recommended Clamp after the cast in perLeafTopKCalculation (A, recommended, validated)

Clamp after the cast in perLeafTopKCalculation: Math.max(1, (int) (k * p + LAMBDA * Math.sqrt(k * p * (1 - p)))), so a NaN share gives 1. Every finite share gives the same value as before. The repro passes with assertions on and off, and 237 tests of the closest kNN suites pass.

  private static int perLeafTopKCalculation(int k, float leafProportion) {
    // Clamp after the cast: a parent with maxDoc 0 makes leafProportion 0 / 0f = NaN, and
    // (int) Math.max(1, NaN) would be 0.
    return Math.max(
        1,
        (int) (k * leafProportion + LAMBDA * Math.sqrt(k * leafProportion * (1 - leafProportion))));
  }

Clamp after the cast in perLeafTopKCalculation (A, recommended, validated)

#

In AbstractKnnVectorQuery.perLeafTopKCalculation (:343-347), apply Math.max(1, ...) to the int result instead of to the double, and drop the comment at :328, which no longer holds. The assert at :329 stays and now always holds.

  private static int perLeafTopKCalculation(int k, float leafProportion) {
    // Clamp after the cast: a parent with maxDoc 0 makes leafProportion 0 / 0f = NaN, and
    // (int) Math.max(1, NaN) would be 0.
    return Math.max(
        1,
        (int) (k * leafProportion + LAMBDA * Math.sqrt(k * leafProportion * (1 - leafProportion))));
  }

Trade-offs

Both call sites use the helper (:276, :327), so the filtered path gets the same value. For every finite share the result is unchanged (for x >= 0, (int) max(1, x) == max(1, (int) x)); only NaN changes, from 0 to 1, and the empty leaf then returns no hits. No hot-path cost. Open PR #16847 rewrites the share lines (and keeps the divisor, the comment and the assert).

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, seed DEADBEEF: the repro fails without the fix (assertions on and off) and passes with it (assertions off).
  • With the fix and assertions on: the repro (1), TestKnnFloatVectorQuery (43), TestKnnByteVectorQuery (40), TestKnnByteVectorQueryMMap (40), TestSeededKnnFloatVectorQuery (39) and TestSeededKnnByteVectorQuery (39) in :lucene:core, and the three TestParentBlockJoin*KnnVectorQuery suites (35) in :lucene:join: 237 tests, 0 failures. checkGoogleJavaFormat passes on the fix.
  • Earlier the finder and the cross-model reviewer each checked the same clamp by shadowing the class: their tests passed, and TestKnnFloatVectorQuery passed 43 of 43 in the finder's run.

In OptimisticKnnCollectorManager.newCollector, when context.parent.reader().maxDoc() == 0, return delegate.newCollector(...) instead of the optimistic collector.

Trade-offs

Explicit about the case, but the filtered path (:275) computes the same share and would want the same guard; more lines than A.

Skip leaves with maxDoc 0 in rewrite (C, not run)

#

Create no search task for a leaf with maxDoc 0.

Trade-offs

Saves work on empty leaves, but the rewrite asserts one result per leaf (:148) and the second pass tracks leaves by ord, so it is more invasive.

Downstream note

#

Downstream products are affected only if they compose such readers themselves, since end-user queries and documents cannot create an empty leaf; OpenSearch's k-NN plugin carries a word-for-word copy of the share computation, comment and assert.

How it was found

#

A proof-obligation audit of AbstractKnnVectorQuery's per-leaf top-k: the code asserts perLeafTopK > 0 under a comment that names the NaN case, so the audit asked which public-API readers make a leaf's parent have maxDoc 0. An empty ParallelLeafReader inside a MultiReader does; a one-method JUnit test then witnessed the exception.

The method in full124 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder took assert perLeafTopK > 0 (AbstractKnnVectorQuery.java:329) and the NaN comment above it as a proof obligation: for every reader the public API can build, the per-leaf top-k must be at least 1. It traced the divisor to the leaf's immediate parent and found that new ParallelLeafReader() inside a MultiReader makes it 0.
  • The finder then wrote a public-API JUnit test, a probe of the nested and flat reader shapes, and the clamp that makes the test pass.
  • An independent reproducer, an executed cross-model review and a devil's-advocate verifier reproduced it with their own tests, and an adjudication re-ran the reproducer's test ("Prior reports, history and checks").

Summary
You build a reader that holds an empty leaf under an empty parent, such as new MultiReader(new ParallelLeafReader()), wrap it in an executor-backed IndexSearcher and rewrite a KnnFloatVectorQuery("v", {1, 0}, 3) on it, expecting MatchNoDocsQuery: that is what the rewrite returns when nothing matches, and what 10.2.2 returns for the same input. Instead the optimistic per-leaf collector computes the leaf's share of its parent as 0 / 0f = NaN; Math.max(1, NaN) stays NaN and the int cast gives a per-leaf top-k of 0, so the rewrite fails at 'assert perLeafTopK > 0' with -ea, and with -da the heap behind the collector throws IllegalArgumentException 'initialCapacity must be > 0 and < 2147483630; got: 0'.
