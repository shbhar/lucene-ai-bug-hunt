Flush-time doc-values iterators move only their doc cursor in intoBitSet(), so values read afterwards belong to earlier documents

Since 10.5.0, the iterator IndexWriter hands a doc-values codec at flush moves only its doc cursor in intoBitSet(): over values 10, 11, 12, after nextDoc() and intoBitSet(2, ...) doc 2 reports doc 0's value, 10. Lucene's own codec never reads values after intoBitSet(), so only a custom codec that does so is hit.

The finding in 30 seconds

#

One numeric field, three documents, one flush: after nextDoc() and intoBitSet(2, ...), doc 2 reports doc 0's value.

Background: one iterator, two cursors

#
  1. At flush, IndexWriter passes the codec's DocValuesConsumer one iterator per doc-values field, built over the values buffered in memory.
  2. That iterator has a doc cursor (which documents have the field) and a value cursor that reads the buffered values in order. nextDoc() moves both by one document.
  3. intoBitSet(upTo, bits, offset) is a bulk call: it sets a bit for every document from the current one up to upTo, and must leave the iterator exactly where the equivalent nextDoc() loop would.

The finding, step by step

#
  1. A custom doc-values codec gets, at flush, the iterator over numeric field f, whose docs 0, 1, 2 hold 10, 11, 12. It calls nextDoc() (doc 0), then intoBitSet(2, bits, 0) to collect docs 0 and 1 in one call, then reads the current value.
  2. You expect what the documented nextDoc() loop gives: bits 0 and 1 set, the iterator on doc 2, and longValue() = 12.
  3. Instead the bits and docID() are right, but longValue() returns 10, doc 0's value. intoBitSet() moved only the doc cursor; the value cursor, which only nextDoc() moves, stayed on doc 0.
  4. With more documents it stays shifted: in a 6-document test the next nextDoc() gives doc 3 with 11 instead of 13. BINARY, SORTED, SORTED_NUMERIC and SORTED_SET fields behave the same, with assertions on or off; in this call order nothing reports an error.

Who is affected

#

Only custom doc-values codecs whose consumer calls intoBitSet() on a flush iterator and then reads values from that same iterator; they could write each later value against the wrong document, usually silently. The default codec and norms are not affected, nor are flushes that re-sort documents for an index sort. 10.5.0 to 10.6.0 and main.

Mechanism, terms and numbers694 words

When a segment is flushed, IndexWriter hands the codec's DocValuesConsumer one iterator per doc-values field. Each of the five flush-time iterators (Buffered{Numeric,Binary,Sorted,SortedNumeric,SortedSet}DocValues) has a doc cursor and a sequential value cursor, and only nextDoc() moves the value cursor from one document to the next. Since #16126 (10.5.0) their intoBitSet() delegates to the doc cursor alone, so after nextDoc() and intoBitSet(2, bits, 0) over values 10, 11, 12 the iterator reports doc 2 with doc 0's value 10, and every later value stays shifted by the same two documents. That breaks DocIdSetIterator#intoBitSet's rule that an override "should behave exactly as" the nextDoc() loop. It is latent: Lucene's own consumer calls intoBitSet() only on fresh iterators whose values it never reads, so stock indexes are correct, and only an application-installed custom doc-values codec that mixes the two calls on one iterator could write values against the wrong documents, usually silently. 10.5.0 through 10.6.0 and main are affected; removing the five overrides fixes it.

Terms

#
  • Flush iterators. For each doc-values field of an unsorted segment, the writer's flush passes a producer whose getNumeric (getBinary, getSorted, getSortedNumeric, getSortedSet) returns a new Buffered*DocValues iterator over the in-memory buffers (NumericDocValuesWriter.java:134-172 at 645d4fe14a20). Two routes add a singleton wrapper: a SORTED_NUMERIC field whose documents all have one value is handed over as DocValues.singleton(BufferedNumericDocValues) (SortedNumericDocValuesWriter.java:215-225) and shows the same bug; a single-valued SORTED_SET field as DocValues.singleton(BufferedSortedDocValues) (SortedSetDocValuesWriter.java:274-285), where the wrapper adds its own stale ordinal (LFV-091). With an index sort and a flush that must re-sort, the Sorting* views are used instead; they read values by doc ID and are not affected.
  • Two cursors. docsWithField is DocIdSetIterator.all(n) while every document so far has the field (as in the example), otherwise a BitSetIterator; the values come from a PackedLongValues.Iterator (or a lengths iterator plus a bytes input). Only nextDoc() moves the value side from one document to the next (NumericDocValuesWriter.java:191-198: value = iter.next()); in a multi-valued document nextValue() and nextOrd() also step through that document's values.
  • intoBitSet contract. "This should behave exactly as if implemented as below, which is the default implementation: for (int doc = docID(); doc < upTo; doc = nextDoc()) { bitSet.set(doc - offset); }" (DocIdSetIterator.java:186-210). NumericDocValues#longValue "Returns the numeric value for the current document ID".

The bug

#
  1. #16126 (10.5.0) added the same override to all five iterators: intoBitSet(...) { docsWithField.intoBitSet(upTo, bitSet, offset); } (NumericDocValuesWriter.java:215-218, BinaryDocValuesWriter.java:213-216, SortedDocValuesWriter.java:347-350, SortedNumericDocValuesWriter.java:318-321, SortedSetDocValuesWriter.java:385-388).
  2. docsWithField.intoBitSet (DocIdSetIterator.all(n)'s range iterator in the example, a BitSetIterator for a sparse field) sets the range of bits and advances the doc cursor to upTo; nothing touches the value cursor.
  3. So the doc cursor is ahead of the value cursor by the number of nextDoc() steps the reference loop would have taken: the documents with the field that intoBitSet moved over, counting the one it lands on. Every value read afterwards belongs to that many documents earlier. In this call order (nextDoc(), intoBitSet(), then reads) the value cursor only lags, nothing throws, and the values of the last documents are simply never returned.
  4. Not always silent: intoBitSet() also leaves the per-document count and position alone. If a SORTED_SET consumer has already read the current document's ords, the next nextOrd() reads past BufferedSortedSetDocValues's per-document array: with 2 values per document, nextDoc(), two nextOrd(), intoBitSet(1, ...), nextOrd() throws ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 2 (executed on 645d4fe14a20, assertions on and off; returns doc 1's ords with the fix).

Exposure and likelihood264 words
  • Who is hit. Authors of a custom DocValuesFormat (the codec extension point; DocValuesConsumer is @lucene.experimental) whose consumer calls the @lucene.internal intoBitSet() on a flush-time iterator and then reads values from the same iterator, for example a single pass that writes the docs-with-field bit set and the values together. A custom IndexSorter reads these iterators at flush too and could hit it the same way (code reading only, not executed). Beyond installing the custom codec (IndexWriterConfig.setCodec), no setting is needed.
  • Not hit: stock Lucene. Lucene90DocValuesConsumer calls intoBitSet() only through IndexedDISI.writeBitSet, always on a fresh iterator used only for doc IDs (Lucene90DocValuesConsumer.java:166-174, :472-475, :658-661), and reads values from other fresh iterators with nextDoc(). Soft-delete counting uses nextDoc() only. Norms have no override.
  • Usually silent. Bits and doc IDs are right; only values (and, for SORTED_NUMERIC and SORTED_SET, value counts) are wrong. The one exception found: a SORTED_SET consumer that read the current document's ords before intoBitSet() gets an ArrayIndexOutOfBoundsException from its next nextOrd(). The format test for intoBitSet (BaseDocValuesFormatTestCase#doTestRandomIntoBitSet) runs on a merged segment's reader and checks only docID() and the bits, so no test reads flush-iterator values after intoBitSet().
  • Scale. Every flushed segment with the field; deterministic; 3 documents are enough.
  • How likely. Rare: no in-tree consumer has the pattern and nobody has reported it since 10.5.0. The pattern does exist downstream: one columnar codec folds a value pass into IndexedDISI.writeBitSet and keeps the default intoBitSet() loop on purpose, documenting that delegating it "would advance the underlying cursor behind this iterator's back".

Why it looks unintended

#
  • DocIdSetIterator#intoBitSet "should behave exactly as if implemented as" the nextDoc() loop, and longValue() returns the value "for the current document ID".
  • A regression of an optimisation: #16126 (10.5.0) replaced the default loop to "just delegate"; 10.2.0 to 10.4.0 were correct.
  • Upstream fixed an analogous omission in the SortedSetSelector wrappers from that PR as a bug (#16714).
The full argument301 words
  • The contract is explicit. DocIdSetIterator.java:186-204: an override "should behave exactly as if implemented as" the docID()/nextDoc() loop. These overrides reproduce the loop's doc IDs and bits but not its effect on the values. NumericDocValues#longValue "Returns the numeric value for the current document ID" (NumericDocValues.java:31-37); the documented restrictions on intoBitSet are that offset is at most the current doc ID and the iterator is positioned (DocIdSetIterator.java:196-197) and, for doc-values iterators, not after advanceExact returned false (DocValuesIterator.java:30-31); the repro meets all three, and none says values are undefined afterwards. The argument is an inference: the javadoc gives the reference loop and does not separately say that a subclass's value state must follow it.
  • A regression. #16126 ("Implement #intoBitSet and #docIDRunEnd in DocValuesWriter implementations", iverase, merged 2026-05-26, milestone 10.5.0) says only: "This are mostly iterators wrapping other iterators so we just delegate the method to the underlaying iterators." One approving review, no comments, no tests for these iterators; CHANGES lists it under Optimizations. From 10.2.0 (#14069) to 10.4.0 the inherited loop kept the values right.
  • Precedent. #16714 (dweiss, merged 2026-09-25, 10.6.0) added the missing setOrd() after in.intoBitSet in the four SortedSetSelector wrappers that #16126 added in the same commit: "it also did find a bug in there so it's piggybacked". It did not touch the writers. Analogous, not identical: there a wrapper's cached ordinal was not refreshed; here a direct iterator's value cursor is not advanced.
  • Lucene's other iterators keep their value state coherent. The reader side resets its per-document state in intoBitSet (Lucene90DocValuesProducer.java:2258-2260, set = false), and the test framework's AssertingNumericDocValues leaves longValue() legal after intoBitSet (AssertingLeafReader.java:815-823, :846-850).
  • Nothing permits it. No javadoc, CHANGES or MIGRATE entry, test or PR discussion says values are undefined after intoBitSet.
The devil's-advocate check186 words

The strongest case (cross-model reviews and the devil's-advocate verifier): intoBitSet is @lucene.internal, the codec API @lucene.experimental; the Buffered* iterators are package-private and sequential-only (advance and advanceExact throw); DocValuesConsumer's javadoc lets an implementation "iterate over the values multiple times" (DocValuesConsumer.java:60-64), and the in-tree consumer does exactly that, one fresh iterator per pass. So mixing intoBitSet() and value reads on one iterator is unsupported use of internal API, and the overrides are a fair optimisation for every real caller. A maintainer may also read @lucene.internal as limiting behavioural guarantees, not only compatibility; the cross-model fact check rated this case moderate.

Why it fails: @lucene.internal is about API stability, not a licence for an iterator to report doc 2 with doc 0's value; the method's own javadoc states what an override must preserve. The project fixed an analogous omission in the SortedSetSelector wrappers from the same PR as a bug (#16714). And the error is usually silent: the doc IDs are right, so misplaced values surface nowhere. What survives is the severity: latent and custom-codec only. Verdict: not intended, a minor latent defect.

Suggested fix

#

Recommended A. Remove the five delegating intoBitSet overrides

Remove the five delegating intoBitSet() overrides so the default nextDoc() loop moves both cursors (5 files, +5/-24 lines). Validated: the repro passes, 3032 core index and codecs tests ran with 0 failures (178 skipped), and the lint passes. Cost: gives back #16126's speed-up when the default codec writes sparse fields at flush (not measured).

// NumericDocValuesWriter.BufferedNumericDocValues; the same in the other four Buffered* classes
-    @Override
-    public void intoBitSet(int upTo, FixedBitSet bitSet, int offset) throws IOException {
-      docsWithField.intoBitSet(upTo, bitSet, offset);
-    }
+    // No intoBitSet override: the default nextDoc() loop also advances the value iterator.

One fix was built and validated; the others are sketches with their trade-offs.

A. Remove the five delegating intoBitSet overrides (validated by the checks) (recommended)

#

Delete intoBitSet from BufferedNumericDocValues, BufferedBinaryDocValues, BufferedSortedDocValues, BufferedSortedNumericDocValues and BufferedSortedSetDocValues, so they inherit the default nextDoc() loop, which moves both cursors; drop the four FixedBitSet imports that become unused (5 files, +5/-24 lines with a one-line comment in each class). Keep the docIDRunEnd overrides: they do not move any cursor.

// NumericDocValuesWriter.BufferedNumericDocValues; the same in the other four Buffered* classes
-    @Override
-    public void intoBitSet(int upTo, FixedBitSet bitSet, int offset) throws IOException {
-      docsWithField.intoBitSet(upTo, bitSet, offset);
-    }
+    // No intoBitSet override: the default nextDoc() loop also advances the value iterator.

Trade-offs

  • Gives back #16126's speed-up where the default codec calls IndexedDISI.writeBitSet on these iterators at flush (fields that some but not all documents have): the loop now also decodes each value it passes. Not measured.
  • Restores the 10.2.0-10.4.0 intoBitSet behaviour (the default loop), which was correct; the docIDRunEnd overrides, which 10.4.0 did not have, stay.
  • A single-valued SORTED_SET field flushes as DocValues.singleton(BufferedSortedDocValues); there SingletonSortedSetDocValues.intoBitSet still leaves a one-document stale ordinal (LFV-091, a separate one-line fix).

B. Keep the fast doc path and move the value cursor inside intoBitSet (not run)

#

After docsWithField.intoBitSet(...), advance the value cursor by the number of documents with the field that were passed (for SORTED_NUMERIC and SORTED_SET also the per-document counts), then load the current document's value.

Trade-offs

The iterator does not know that count today (it would need the DocsWithFieldSet bits or a running counter), and PackedLongValues.Iterator has only hasNext() and next() (no skip), so the value side still steps entry by entry: more code in five classes for a gain that was never measured.

Not a fix: document that values are undefined after intoBitSet on flush iterators

#

A javadoc note on the flush producers.

Trade-offs

Contradicts DocIdSetIterator#intoBitSet's "behave exactly as" rule, and a consumer has no way to tell a flush iterator from any other NumericDocValues.

Downstream note

#

Downstream codecs that fold a value pass into the docs-with-field bit set are the pattern at risk; the one found (Elasticsearch's columnar code) keeps the default intoBitSet() loop on purpose and is not affected.

How it was found

#

Bounded-exhaustive checking: a harness ran every sequence of up to 3 iterator calls on segments of up to 5 documents, for 26 doc-values and norms views, and compared each step with a plain nextDoc() walk. The sequence nextDoc(), intoBitSet(), value read mismatched on the flush iterators of all five types; a JUnit test on the stock jars confirmed it.

The method in full161 words

Method: bounded-exhaustive translation validation (the hunt's "semi-formal" tier), hunt unit (doc-values and norms cursor coherence), 2026-10-26, main ea57360912ed.

  • The harness (Coherence.java) enumerated every legal move sequence of depth <= 3 over nextDoc, advance, advanceExact, intoBitSet, docIDRunEnd, intoArray and the bulk value calls, on segments of <= 5 documents, for 26 doc-values and norms views, including the flush-time iterators handed to a pass-through DocValuesConsumer. After every step it compared the iterator state with a fresh nextDoc() enumeration of the same view.
  • The sequence nextDoc > intoBitSet > value read on the flush-time view mismatched for all five doc-values types. The finder reduced it to a public-API JUnit test on the stock main jars (5 of 5 fail, assertions on and off), and the hunt later minimized it to one NUMERIC test.
  • Earlier units had noted the same pattern by code reading (one as a possible latent defect, one as benign), without a repro.

LFV-418, snapshot of 2026-11-07

Registry title
The flush-time doc-values iterators that IndexWriter hands to a DocValuesConsumer move only their doc-ID cursor in intoBitSet(), so values read afterwards belong to earlier documents (NUMERIC, BINARY, SORTED, SORTED_NUMERIC, SORTED_SET; latent: Lucene's own consumers never read values after intoBitSet on the same iterator)
Area
index / doc values flush (DocValuesWriter Buffered*DocValues iterators handed to DocValuesConsumer)
Priority
Low, rank 1206: Only a custom single-pass doc-values consumer that reads values after intoBitSet sees shifted values, and Lucene's own consumers never do.
Impact class
minor
Impact note
Latent: only a custom DocValuesFormat consumer (public codec extension point, @lucene.experimental), or other custom code handed these iterators at flush, that calls the @lucene.internal DocIdSetIterator#intoBitSet on an unsorted flush-time doc-values iterator and then reads values from the same iterator is hit, and it would then silently write every later value of that field in the segment against the wrong document; Lucene's own consumers never do this (Lucene90DocValuesConsumer calls intoBitSet only through IndexedDISI.writeBitSet on a fresh iterator whose values it never reads, and the SimpleText, PerField, Asserting, Cranky and backward Lucene80 consumers never call it), nor do the downstream consumers read, norms are not affected, no scale or non-default IndexWriterConfig is needed, and 10.5.0 to 10.6.0 are affected.
Summary
A custom doc-values codec receives, at flush, the iterator over a field's buffered values; it calls nextDoc(), bulk-loads the next documents into a bit set with intoBitSet(), and then reads the value of the current document, expecting what the documented nextDoc() loop gives. Instead the five flush-time iterators (one per doc-values type) move only their doc-ID cursor in intoBitSet(), so the value read belongs to an earlier document, and every later value of the field in that segment stays shifted by the same number of documents (doc 2 reports doc 0's value, doc 3 reports doc 1's). Lucene's own doc-values consumer never reads values after intoBitSet() on the same iterator, so indexes written by stock Lucene are correct.
