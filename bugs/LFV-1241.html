KnnFloatVectorField's FieldType constructor accepts an empty vector when the type has no vector attributes

new KnnFloatVectorField("v", new float[0], new FieldType()) succeeds, although its javadoc promises an IllegalArgumentException for an empty vector: the only length check compares 0 values with the type's vector dimension, also 0 for a type without vector attributes. Indexing it registers v as a field without vectors.

The finding in 30 seconds

#

KnnFloatVectorField has convenience constructors, which build the field type from the vector, and one that takes a prepared FieldType, normally from KnnFloatVectorField.createFieldType(dimension, similarity). Only the FieldType constructor lets an empty vector through, and only when the type has no vector attributes.

  1. Build a vector field with your own type: new KnnFloatVectorField("v", new float[0], new FieldType()). The vector has 0 values, and new FieldType() has no vector attributes, so its vectorDimension() is 0.
  2. You expect IllegalArgumentException: the constructor's javadoc promises one when "the vector is empty", and the convenience constructor new KnnFloatVectorField("v", new float[0]) throws "cannot index an empty vector".
  3. Instead you get a field. The constructor's only length check is vector.length != fieldType.vectorDimension(), and 0 != 0 is false. A configured vector type cannot have dimension 0 (setVectorAttributes refuses it), so only a type without vector attributes gets through.
  4. addDocument then succeeds and registers v as a field with no vectors, no index, no doc values and nothing stored. A later new KnnFloatVectorField("v", new float[] {1, 2, 3}) in that index is refused: "vector dimension: expected '0', but it has '3'".

Who is affected

#

Only code that passes this constructor a type without vector attributes (new FieldType() or a copy of a non-vector type) together with an empty float[]: two caller mistakes at once. Default configuration, every release since 9.0.0. No wrong hits and no corruption; real vectors for that field name later fail loudly. Contrived, so priority Low.

Mechanism, terms and numbers754 words

KnnFloatVectorField(String, float[], FieldType) documents @throws IllegalArgumentException if any parameter is null, or the vector is empty or has dimension > 1024 (KnnFloatVectorField.java:129-130), but it never checks emptiness: its only length check is vector.length != fieldType.vectorDimension() (:142). A FieldType on which setVectorAttributes was never called, such as new FieldType(), has vector dimension 0 (FieldType.java:49), and setVectorAttributes refuses 0 (:390-391), so an empty vector with such a type passes 0 != 0. The convenience constructors reject the same vector with "cannot index an empty vector" (KnnFloatVectorField.java:47-48). If the document is indexed, addDocument succeeds and the field v is registered with no vectors, no index, no doc values and nothing stored; later real vectors for v in that index are refused by the ordinary per-field schema check. KnnByteVectorField's FieldType constructor has the same gap, reachable only with a custom type that reports BYTE with dimension 0. It needs two caller mistakes at once and causes no wrong hits or corruption, so it is Low; it has been there since the constructor was added (LUCENE-9615, first released in 9.0.0) and is on main. An explicit vector.length == 0 check fixes it.

Terms

#
  • Vector attributes of a FieldType: dimension, encoding (FLOAT32 or BYTE) and similarity, set with setVectorAttributes. A plain new FieldType() has none: dimension 0, encoding FLOAT32 (FieldType.java:49-50, :79). setVectorAttributes refuses a dimension of 0 or less (:390-391), so dimension 0 always means "not a vector type".
  • The two kinds of constructors. new KnnFloatVectorField(name, vector) and (name, vector, similarity) build their type in createType, which throws "cannot index an empty vector" (KnnFloatVectorField.java:42-48). new KnnFloatVectorField(name, vector, fieldType) (:132-152) takes the caller's type and validates the vector against it.

The bug

#
// KnnFloatVectorField.java, main 5adff78bb168
/** ...
 * @throws IllegalArgumentException if any parameter is null, or the vector is empty or has   // :129-130
 *     dimension &gt; 1024.
 */
public KnnFloatVectorField(String name, float[] vector, FieldType fieldType) {                // :132
  super(name, fieldType);
  if (fieldType.vectorEncoding() != VectorEncoding.FLOAT32) { throw ... }                     // :134-140
  Objects.requireNonNull(vector, "vector value must not be null");                           // :141
  if (vector.length != fieldType.vectorDimension()) {                                         // :142  0 != 0 is false
    throw new IllegalArgumentException("The number of vector dimensions does not match the field type");
  }
  if (COSINE && isZeroVector(vector)) { throw ... }                                           // :146-150
  fieldsData = VectorUtil.checkFinite(vector);                                                // :151
}
  1. With new FieldType() (or a copy of any non-vector type, FieldType.java:55-76), the encoding check passes (FLOAT32 is the default), the vector is not null, and the length check compares 0 with 0. No check looks at emptiness, so the field is built.
  2. With new FieldType() the field is neither indexed, nor doc-valued, nor stored. The binary-value Field constructors refuse such a type (Field.java:216-221) and the String-value one refuses a type that is neither indexed nor stored (:250-253), though the Reader-value one accepts it (:102-122). The protected Field(String, IndexableFieldType) used here checks only for null (:81-90).
  3. With new FieldType(), a vector is written at indexing only when fieldType.vectorDimension() != 0 (IndexingChain.java:1466-1468), so nothing is written, but v is still registered in the segment's field infos. A later real vector for v fails the per-field consistency check (FieldSchema.assertSameSchema, IndexingChain.java:2345-2359; in a new writer FieldInfo.verifySameVectorOptions, FieldInfo.java:401-420). That refusal is the ordinary schema rule: a StoredField named v followed by a vector fails the same way. (A copy of an indexed non-vector type, such as StringField.TYPE_NOT_STORED, also passes the constructor, but addDocument then refuses the field: "Non-Tokenized Fields must have a String value", Field.java:489.)
  4. KnnByteVectorField(String, byte[], FieldType) (KnnByteVectorField.java:129-151) has the same javadoc and checks. Its encoding check rejects plain new FieldType() (FLOAT32), so only a custom type that reports BYTE with dimension 0 reaches the gap.

The numbers

#

On main with assertions off: the accepted field has dimension 0, index options NONE, doc values NONE, not stored; addDocument succeeds; the reader shows maxDoc=1, FieldInfo(v) with dimension 0 and getFloatVectorValues("v") null. new KnnFloatVectorField("v", new float[] {1, 2, 3}) is then refused in the same writer ("Inconsistency of field data structures across documents for field [v] of doc [1]. vector dimension: expected '0', but it has '3'.") and in a new writer ("cannot change field \"v\" from vector dimension=0, vector encoding=FLOAT32, vector similarity function=EUCLIDEAN to inconsistent vector dimension=3, ..."). With the 3-dimensional document first, the empty-vector document is the one refused ("expected '3', but it has '0'").

Exposure and likelihood141 words
  • Who is hit. Application code that calls the FieldType constructor with a type that has no vector attributes (new FieldType(), a copy of a non-vector type, or a subclass) and an empty float[]. Types from createFieldType(...) and every convenience constructor reject the empty vector.
  • Default vs opt-in. Default IndexWriterConfig and codec, assertions on or off; a public constructor of a class tagged @lucene.experimental.
  • Effect. The documented exception is missing. With new FieldType(), once indexed, the field name is fixed as a non-vector field in that index, so real vectors for it fail with a loud, accurate schema error. No wrong hits, no corruption.
  • Scale. None needed: one call.
  • Likelihood: contrived. Such a type also rejects every non-empty vector, so an ingestion path that uses it fails on its first real vector. No report since 9.0.0 (2021).

Why it looks unintended

#
  • The constructor's own @throws names it: "if any parameter is null, or the vector is empty".
  • #12281 added this length check as the empty-vector guard: "A zero length vector also causes havoc", then "I added the dimension check to the constructor which uses a predefined field type" (Uwe Schindler).
  • The newest sibling, KnnFloat16VectorField, keeps "or the vector is empty".
The full argument171 words
  • The contract. KnnFloatVectorField.java:129-130 (same at KnnByteVectorField.java:129-130). No precondition on the type is documented, and the constructor does validate the type (encoding, dimension).
  • The intent. #12281 ("Add checks in KNNVectorField / KNNVectorQuery to only allow non-null, non-empty and finite vectors", merged 2023-06-13, 9.7.0). Uwe Schindler wrote on 2023-06-10: "The ctors are currently missing the checks that are mentioned in the javadocs. E.g., theres no null check, which is a bug."; on 2023-06-12: "Before doing that I will only add the \"vector size>0\" check in the API, because that may be missing at some places. A zero length vector also causes havoc."; and later that day: "I added the dimension check to the constructor which uses a predefined field type." The dimension check misses only the dimension-0 type.
  • The promise is live. KnnFloat16VectorField (#16383, 2026) dropped the stale "> 1024" clause but kept "or the vector is empty" (KnnFloat16VectorField.java:67).
  • Tests. Upstream tests assert that empty vectors are rejected, through the convenience constructors only (BaseKnnVectorsFormatTestCase.java:177; testIllegalEmptyVector, :825-836).
The devil's-advocate check146 words

The strongest case: a dimension-0 type is an unconfigured, non-vector type, so the caller is wrong; the constructor is meant for "a predefined field type"; maintainers called a dimension-0 vector type "strange" (#12279, closed unmerged); the class is experimental; and the same @throws sentence is boilerplate that is already wrong elsewhere (a null vector gives NullPointerException; a dimension above 1024 is accepted here since #12436 moved the limit to the codec).

Why it fails: that is a precondition nobody documented. The javadoc names the empty vector explicitly, the same constructor already rejects this very type with any non-empty vector, and the guard the maintainer added was meant to catch exactly this input. The argument lowers the impact (two caller mistakes), not the defect. An executed review by another model family (OpenAI GPT-5.6) rated it "moderate" for the same reason; every verifier rated the bug real.

Suggested fix

#

Recommended Explicit emptiness check in both FieldType constructors

Add if (vector.length == 0) throw new IllegalArgumentException("cannot index an empty vector"); before the dimension comparison in both FieldType constructors, as createType does. Validated: the repro passes with assertions on and off; all 499 tests of :lucene:core's org.apache.lucene.document package and its column subpackage pass, as does :lucene:core:check -x test.

Reject a FieldType whose vectorDimension() is 0 (validated by the checks)

#

In both constructors, throw IllegalArgumentException (for example "the field type of field v has no vector attributes") when fieldType.vectorDimension() == 0, before the length comparison.

Trade-offs

Closest to the design intent ("a predefined field type") and gives a clearer message for a non-empty vector with a non-vector type too, which today gets "The number of vector dimensions does not match the field type"; it changes that message.

What the checks validated

With fix B the repro and TestField (38 tests) pass, assertions on; the wider suites were run only with fix A.

Downstream note

#

Services that index client-supplied vectors are not exposed through the vector values alone: any type built with createFieldType and the convenience constructors reject an empty vector; only the application's own choice of a non-vector FieldType opens the gap.

How it was found

#

A proof-obligation audit of KnnFloatVectorField's contract took the FieldType constructor's @throws ("the vector is empty") as an obligation and checked whether its checks discharge it for every type the API can build. They do not when the type's vector dimension is 0. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full119 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: every empty vector passed to KnnFloatVectorField(String, float[], FieldType) raises IllegalArgumentException (KnnFloatVectorField.java:129-130). The only check that can reject an empty vector is vector.length != fieldType.vectorDimension(), which discharges it only when the dimension is at least 1; new FieldType() and copies of non-vector types have dimension 0.
  • A one-test JUnit witnessed it on main with assertions on and off; a probe measured the indexing consequence and the controls. An independent reproducer and an executed review by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier and an adjudication re-ran the repro.
