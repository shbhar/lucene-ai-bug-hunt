A reused classic Highlighter with SimpleSpanFragmenter cuts the next text differently, because start() does not reset waitForPos

SimpleSpanFragmenter.start() resets every per-text field except waitForPos, its "do not cut yet" position, so after a text that ends with a phrase match a reused Highlighter makes the next text's first 12 words one 70-character fragment, where a new one cuts about every 20 characters. Hits and scores are unaffected.

The bug in 30 seconds

#

The classic Highlighter keeps one fragmenter and calls its start() before every text. SimpleSpanFragmenter remembers in waitForPos a position before which it must not cut, so a phrase match stays whole; start() resets everything except that.

How the classic Highlighter cuts a text into fragments

#
  1. The Highlighter walks the text token by token and, from the second token on, asks its fragmenter: start a new fragment here?
  2. SimpleSpanFragmenter says yes when the text so far passes the next multiple of the fragment size (20, 40, 60 characters, ...), unless a query match is in progress: when a match starts, it sets waitForPos to the position after the match and says no until its counter gets there.
  3. Before each text the Highlighter calls the fragmenter's start(), documented as "Initializes the Fragmenter".

The bug, step by step

#
  1. Build one classic Highlighter with a QueryScorer and SimpleSpanFragmenter(scorer, 20) for the phrase "search library" (StandardAnalyzer), and reuse it for every hit, as Highlighter is designed for.
  2. Highlight hit 1, Lucene is an open source project that ships a search library. At the phrase the fragmenter sets waitForPos = 11: no new fragment until its position counter reaches 11. The text ends first, so waitForPos stays 11.
  3. Highlight hit 2, Highlighting picks short fragments of text around each match so that a reader of the search library manual .... You expect what a new Highlighter gives: Highlighting picks | short fragments of | text around each | match so that a reader | ....
  4. You get Highlighting picks short fragments of text around each match so that a (70 characters), then reader | of | the, one word each: start() reset the counter for hit 2 but not waitForPos, so no cut came before the counter reached 11, and then the fragment count caught up word by word.
  5. No error, and only snippets change, never hits or scores; they depend on what the same Highlighter saw before. In the test's longer case at the default fragment size 100, the best fragment grows from 114 to 491 characters.

Who is affected

#

Code that reuses one classic Highlighter with the opt-in SimpleSpanFragmenter for several hits, fields or values, and highlights a phrase, multi-phrase or span query; term queries never trigger it and the default SimpleFragmenter is safe. Snippet layout only: hits and scores are unchanged. Every release since 2.4.0; rare.

Mechanism, terms and numbers763 words

The classic Highlighter keeps one Fragmenter and calls its start(text, tokenStream), documented as "Initializes the Fragmenter", before every text. SimpleSpanFragmenter, the span-aware fragmenter that keeps phrase matches whole, stores in waitForPos the position just after a match that has started and refuses to start a new fragment until its position counter gets there. Its start() resets the counter, the fragment count, the text size and the attributes, but not waitForPos.

So when a phrase, multi-phrase or span match ends a text, the next text highlighted by the same Highlighter inherits the pending position: no fragment boundary until the counter reaches it, then one-word fragments while the fragment count catches up, a different best fragment, and sometimes a phrase split in two. With the phrase "search library" at size 20 the next text's first fragment is 70 characters; at the default size 100 the best fragment is 491 characters instead of 114. Search hits and scores are unaffected. The omission dates from the class's creation in 2008 (2.4.0) and reproduces on every release to 10.5.2 and on main; the fix is one line.

Terms

#
  • Fragmenter: the policy that cuts a text into fragments. Highlighter holds one (Highlighter.java:44, default SimpleFragmenter; setTextFragmenter, :423-425) and calls start(text, tokenStream) at the start of every getBestTextFragments call (:194), which every getBestFragment(s) method reaches. Fragmenter#start: "Initializes the Fragmenter. You can grab references to the Attributes you are interested in from tokenStream and then access the values in isNewFragment()" (Fragmenter.java:28-35).
  • SimpleSpanFragmenter: "breaks text up into same-size fragments but does not split up {@link Spans}. This is a simple sample class." (SimpleSpanFragmenter.java:26-29). It gets the query's matches in the current text from QueryScorer, which re-extracts them for every text in init (QueryScorer.java:170-181, called at Highlighter.java:175) and stores each as PositionSpan(start, end) with an inclusive end (WeightedSpanTermExtractor.java:332).

The bug

#
  1. isNewFragment() adds the token's position increment to position (SimpleSpanFragmenter.java:63). While waitForPos > position it returns false at once, before the span lookup and the size test (:65-69).
  2. When a span of the current token starts at position, it sets waitForPos = positionSpan.end + 1 (:76-81).
  3. Otherwise a new fragment starts when the token's end offset reaches fragmentSize * currentNumFrags and at least half a fragment of text is left (:84-90).
  4. The Highlighter calls isNewFragment() only when a new token arrives (Highlighter.java:209-224) and flushes the last token group without another call (:241-254). A span that ends the text therefore leaves waitForPos set.
  5. start() resets position = -1, currentNumFrags = 1, textSize and the three attributes (:98-106), not waitForPos (:36). The next text gets no boundary until its counter reaches the old value; then the size test, still at the first fragment's limit, fires at every token until currentNumFrags catches up; and while the stale wait holds, a match that starts is never registered, so it can be cut in two.

Exposure and likelihood263 words
  • Who is exposed. Code that reuses one classic Highlighter with SimpleSpanFragmenter (opt-in; the default is SimpleFragmenter, Highlighter.java:44) for several texts: hits, fields, or the values of a multi-valued field. Reuse is the Highlighter's design (one fragmenter field, start() per text) and the package example's pattern (package-info.java:36-59, one Highlighter for 10 hits and two fields, with the default fragmenter).
  • What it takes. A positional query (phrase, MultiPhraseQuery or span query, also inside a BooleanQuery) whose match ends the previous text (its last token, or with the stock counter also the second-to-last), and a previous text long enough that the stale position lies beyond the next text's first fragment boundary (at size 100 roughly more than one fragment of previous text, by reading). A plain TermQuery or SynonymQuery has no position spans and never sets waitForPos.
  • What the damage looks like. One oversized fragment (70 characters at size 20; 491 instead of 114 at the default size 100), then one-word fragments, a different best fragment, and sometimes a phrase split across fragments (1,632 such splits in the finder's bounded check of tiny texts). Repeating getBestFragments on the same text gives a different answer the second time. Silent: no error.
  • What is not affected. Search hits, counts and scores; SimpleFragmenter and NullFragmenter reused (same output as new ones).
  • How likely. Rare: opt-in fragmenter, reuse, a positional query and a previous text that ends with a match. No user report has been attributed to it in 18 years.
  • Scale. Nothing depends on index size or concurrency; two short strings reproduce it.

Why it is a bug, not intended

#
  • Fragmenter#start "Initializes the Fragmenter"; Highlighter calls it on its one fragmenter before every text (Highlighter.java:44, :194).
  • start() resets every other per-text field; an upstream test reuses one SimpleSpanFragmenter for two documents; its synonym query has no phrase, so it never sees the bug.
  • A "fragment way too long" waitForPos bug was fixed before (LUCENE-2229, 5.4.1).
The full argument261 words
  • Contract. Fragmenter#start: "Initializes the Fragmenter" (Fragmenter.java:28-35). Highlighter keeps one fragmenter (:44, :423-425) and calls start for every text (:194). The contract is implicit: no javadoc says in so many words that a reused fragmenter must cut a text as a new one does; the case rests on start() being the per-text initializer, the one-fragmenter design and the points below.
  • The class itself. start() resets position, currentNumFrags, textSize and the attributes (SimpleSpanFragmenter.java:100-105). waitForPos holds a position of the previous text, which means nothing in the next one: QueryScorer.init re-extracts the spans for every text (QueryScorer.java:170-181). SimpleFragmenter.start resets its own state (SimpleFragmenter.java:47-50).
  • Tests. TestHighlighter#testHighlightingSynonymQuery reuses one Highlighter and one SimpleSpanFragmenter for documents 2 and 3 (TestHighlighter.java:238-258, reuse at :248-256); a SynonymQuery has no position spans, so it never sees the bug. No test or javadoc says a fragmenter is single-use.
  • Intent. Michael McCandless asked on LUCENE-1685 (#2759, 2009-06-12) for a way "to not have to make a SpanScorer (and, by extension, fragmenter) per query, but instead make it up-front", and later "Should we also default the fragmenter to SimpleSpanFragmenter?" LUCENE-1685 made the span-aware QueryScorer reusable in 2.9.0; the fragmenter's own state was not discussed.
  • Precedent. LUCENE-2229 (#3305): "Fix Highlighter's SimpleSpanFragmenter when multiple adjacent stop words following a span can unduly make the fragment way too long" (lucene/CHANGES.txt:9891-9893, 5.4.1), with the test assertion "Fragment must be less than 60 characters long" (TestHighlighter.java:435). It changed the same waitForPos check, within one text.
The devil's-advocate check134 words

The intended-behaviour checker's strongest case: the javadoc calls the class "a simple sample class", and most upstream tests build a new SimpleSpanFragmenter per document, which could suggest single use.

Why it fails: the per-document line in those tests is a leftover of the 2008 design, when the SpanScorer took one text's token stream in its constructor and had to be built per document, together with its fragmenter; in the LUCENE-1685 commit 10b41d2dce2 the HighlighterTest diff moves the scorer and the Highlighter out of the loop and keeps the setTextFragmenter(new SimpleSpanFragmenter(...)) line inside it, changing only its argument. The class is maintained public API (LUCENE-1389 changed it in 2.9.0, LUCENE-2229 fixed it in 5.4.1), "sample" does not license output that depends on an unrelated earlier text, and the cross-model reviewer rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Reset waitForPos in start() (one line)

Add waitForPos = -1; to SimpleSpanFragmenter.start(). All 5 tests then pass, and so does the whole highlighter test task (722 upstream tests), with assertions on and off; the module's lint and format checks pass. A fragmenter's first text behaves as before (the field already starts at -1).

   public void start(String originalText, TokenStream tokenStream) {
     position = -1;
+    waitForPos = -1;
     currentNumFrags = 1;
     textSize = originalText.length();

#

A javadoc note instead of a code change.

Trade-offs

Downstream note

#

Downstream servers whose opt-in plain highlighter keeps one Highlighter with a SimpleSpanFragmenter per field for all hits of a fetch phase, as Elasticsearch's and OpenSearch's do by a reading of their code (not executed), would show it across hits and the values of multi-valued fields.

How it was found

#

Found while modelling the classic Highlighter's fragment loop: writing a corrected copy of SimpleSpanFragmenter showed that start() resets every per-text field except waitForPos. A bounded-exhaustive check on the stock jar then found 160,425 of 1,048,320 small text pairs where a reused Highlighter cuts the second text differently from a new one.

The method in full153 words

Method: model-based, bounded-exhaustive differential check on the stock jar (the study's "semi-formal" tier). A hunt unit, a transducer model of Highlighter.getBestTextFragments composed with SimpleSpanFragmenter, 2026-10-28, main a9779ef3c193.

  • While writing the fix-sketch shadow class for the model, the finder read that start() resets position and currentNumFrags but not waitForPos.
  • ReuseProbe then ran every pair (first text of at most 4 tokens, second text of at most 6 tokens, over {a, c, x}) with PhraseQuery(a c) and fragment sizes 1 to 8 through a reused and a new Highlighter: 160,425 of 1,048,320 second-text results differ, 1,632 of them split the phrase only when reused. Smallest example: size 4, first text a c, second text a a a a: reused |a a a a|, new |a a| a a|.
  • An AI finder then wrote the public-API JUnit; independent AI tools reproduced, reviewed, judged and audited it (see the checks).

Registry title
Classic Highlighter's SimpleSpanFragmenter.start() does not reset waitForPos, so a Highlighter reused for the next text (or for the same text again) keeps suppressing fragment boundaries after a phrase match that ended the previous text: one oversized fragment, then one-word fragments and a different best fragment, depending on what was highlighted before
Area
highlighter / classic Highlighter fragmenting (SimpleSpanFragmenter.start, state carried across texts)
Priority
Low, rank 477: This sibling of LFV-859 in the opt-in SimpleSpanFragmenter only changes snippet layout, and it fires whenever a reused Highlighter's previous text ended in a phrase match, which is more ordinary than LFV-858's overlapping-phrase case.
Impact class
minor
Impact note
Applications that reuse one classic Highlighter with QueryScorer and SimpleSpanFragmenter for several texts (opt-in fragmenter; reusing one Highlighter is the pattern of the package example, and a downstream plain highlighter caches one per field, read not executed) and run a phrase, span or multi-phrase query get different fragment boundaries in a text whenever the previous text ended with a match and was long enough for the stale position to pass the next text's first boundary; highlighting output only (hits and scores are unaffected), no error, no scale needed, in every release since 2.4.0.
Summary
You reuse one classic Highlighter with a QueryScorer and a SimpleSpanFragmenter for several texts (Highlighter keeps one fragmenter and calls its start(), documented as 'Initializes the Fragmenter', for every text) and expect each text to be cut into the same fragments as with a fresh Highlighter.
