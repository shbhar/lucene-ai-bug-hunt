A too-short kNN query vector returns hits instead of an error on mmap-backed Lucene99 scalar-quantized fields with the Panama vector code

With the Panama vector code on, a 7-component KnnFloatVectorQuery on an 8-dimensional Lucene99 scalar-quantized field read through mmap returns 4 hits instead of IllegalArgumentException, each document scored on its first 7 codes. A regression in 10.4.0: this mmap path skips the dimension check that the class's own heap path and its sibling scorers make.

The finding in 30 seconds

#

Lucene picks a vector scorer per format and vectorization provider. For a Lucene99 scalar-quantized field on mmap, the Panama scorer builds its own query scorer and never compares the query's length with the field's dimension.

  1. Index 4 documents with 8-dimensional vectors [i, 1, 2, 3, 4, 5, 6, 7] (i = 0..3) into a Lucene99HnswScalarQuantizedVectorsFormat field (7 bits, EUCLIDEAN), the quantized format that Lucene 9.9 to 10.3 wrote and 10.4+ still reads. Open it from an MMapDirectory with the Panama vector code on (--add-modules jdk.incubator.vector).
  2. Search new KnnFloatVectorQuery("f", new float[7], 4): 7 components for an 8-dimensional field.
  3. You expect IllegalArgumentException "vector query dimension: 7 differs from field dimension: 8" (the message of FlatVectorsScorer.checkDimensions), as Lucene's kNN query tests require for a 1-vs-2 mismatch. The same query gets one with the default vector code (whose message swaps the two numbers), with NIOFSDirectory, and on 10.3.2.
  4. Instead, with assertions off, you get all 4 documents and no error. Doc 0 is stored as 8 one-byte codes [0, 0, 21, 42, 64, 85, 106, 127]; the query becomes 7 zero codes, and the distance is summed over the first 7 only: 24,762 instead of 40,891, score 0.0178 instead of 0.0108.
  5. With assertions on, an internal AssertionError fires in PanamaVectorUtilSupport instead of the expected exception.

Who is affected

#

Applications on 10.4.0 or later that still hold Lucene99HnswScalarQuantizedVectorsFormat fields (written by 9.9 to 10.3), run the opt-in Panama vector code on an mmap directory (the FSDirectory.open default on 64-bit), and send a query vector of the wrong length, a caller error. They get plausible but wrong hits instead of an error. Rare, so Low.

Mechanism, terms and numbers518 words

With the Panama vectorization provider (--add-modules jdk.incubator.vector), a KnnFloatVectorQuery whose vector is shorter than the field dimension is silently accepted on a legacy Lucene99HnswScalarQuantizedVectorsFormat field (written by Lucene 9.9 to 10.3, read through backward-codecs since 10.4.0) opened from an mmap directory. With assertions off the search returns normal-looking hits, each document scored on only the first components of its quantized vector; with assertions on, an internal AssertionError fires in a Panama kernel. The same documents and query get an IllegalArgumentException with the default provider, with a non-mmap directory, and on 10.3.2 (the default provider's message swaps the two numbers). The cause is the mmap branch of Lucene99MemorySegmentScalarQuantizedVectorScorer.getRandomVectorScorer(float[]), added in 10.4.0 by #14863: it never calls FlatVectorsScorer.checkDimensions, which this class's own heap path and the sibling scorers Lucene99MemorySegmentFlatVectorsScorer and Lucene104ScalarQuantizedVectorScorer call (DefaultFlatVectorScorer makes the same check inline). The fix is one line.

Terms

#
  • Lucene99 scalar-quantized format (Lucene99HnswScalarQuantizedVectorsFormat): an opt-in HNSW format of Lucene 9.9 to 10.3 that stores each float vector as one small integer code per component (here 7 bits, one byte each). Since 10.4.0 it lives in backward-codecs and is read-only.
  • Panama provider: Lucene's SIMD vector code, used when the JVM runs with --add-modules jdk.incubator.vector; otherwise the default (scalar) provider is used.
  • mmap: MMapDirectory, which FSDirectory.open returns on 64-bit platforms. Its inputs are MemorySegmentAccessInputs.

The bug

#
  1. With the Panama provider the format's scorer is Lucene99MemorySegmentScalarQuantizedVectorScorer (PanamaVectorizationProvider.java:82-84). Nothing above it checks the query length: KnnFloatVectorQuery, CodecReader.searchNearestVectors and the backward-codecs reader (Lucene99ScalarQuantizedVectorsReader.java:326-343) pass the vector through.
  2. Its getRandomVectorScorer(float[]) has two paths (Lucene99MemorySegmentScalarQuantizedVectorScorer.java:61-73). When the slice holding the quantized vectors is a MemorySegmentAccessInput (:65-66), which is what MMapDirectory hands out, it builds its own scorer (:67-70) without FlatVectorsScorer.checkDimensions. Only the other path, the heap delegate (:72), checks (Lucene99ScalarQuantizedVectorScorer.java:107).
  3. The scorer quantizes the query into new byte[target.length], the caller's length (:222); each stored vector is a segment of the field's real 8 bytes (:182).
  4. The kernel loops over the query's length and compares the two lengths only with assert (PanamaVectorUtilSupport.java:968-970, :996-997). With assertions off, the 7 query codes are compared with the first 7 of each document's 8 codes, and the eighth is ignored.

The numbers

#

In the minimal test the quantizer maps 1..7 to codes 0..127, so doc 0 is [0, 0, 21, 42, 64, 85, 106, 127] and the all-zero query is 7 zero codes. The kernel's sum of squared differences is 24,762 over 7 codes instead of 40,891 over all 8 (the missing 127² = 16,129), and the scores are 0.0178, 0.0178, 0.0175 and 0.0166 for docs 0-3, against 0.0108, 0.0108, 0.0107 and 0.0104 for a correct 8-component zero query.

Scope

#

On the executed paths (7-bit codes; EUCLIDEAN in this test, COSINE in the independent reproduction) only shorter queries are silent. A longer query fails loudly with a bounds-checked IndexOutOfBoundsException (wrong type, but loud). The int4 kernels and the opt-in native dot-product path were only read, not run, and are not claimed.

Exposure and likelihood145 words
  • Who: three choices must meet. The field uses the legacy Lucene99 scalar-quantized format (opt-in when the index was written, 9.9 to 10.3). The JVM enables the Panama code (opt-in; when the vector module is not enabled, Lucene logs a warning that recommends it: "For optimal vector performance, pass '--add-modules jdk.incubator.vector' to enable Vector API."). The index is opened through mmap, which is the default.
  • When: the application sends a query vector of the wrong length, for example one embedded with a different or truncated model.
  • What: plausible top-k hits and no error, where every other configuration fails fast, so the mistake goes unnoticed. In tests (-ea) an AssertionError replaces the IllegalArgumentException Lucene's tests expect.
  • Scale: none needed; 4 documents reproduce it.
  • Not affected: other vector formats (this scorer serves only the Lucene99 scalar-quantized format), the default provider, non-mmap directories, and releases before 10.4.0.

Why it looks unintended

#
  • Lucene's kNN query tests require it: testDimensionMismatch expects IllegalArgumentException "vector query dimension: 1 differs from field dimension: 2".
  • This class's own heap path and its sibling scorers (Lucene99MemorySegmentFlatVectorsScorer, Lucene104ScalarQuantizedVectorScorer) call FlatVectorsScorer.checkDimensions before scoring; #14863 called this scorer "in-line with" one that checks.
  • The same query fails with the default provider, with NIOFSDirectory and on 10.3.2: a 10.4.0 regression.
The full argument211 words
  • Test contract: BaseKnnVectorQueryTestCase.testDimensionMismatch (:273-284) expects IllegalArgumentException with "vector query dimension: 1 differs from field dimension: 2".
  • Siblings check eagerly with FlatVectorsScorer.checkDimensions (FlatVectorsScorer.java:75-80): Lucene99MemorySegmentFlatVectorsScorer.java:88, :113, Lucene104ScalarQuantizedVectorScorer.java:64, :76, :85 and this class's heap delegate (Lucene99ScalarQuantizedVectorScorer.java:107); DefaultFlatVectorScorer makes the same check inline (:64-70). Not every scorer checks up front (the core ScalarQuantizedVectorScorer leaves it to VectorUtil), so this rests on this class's own heap path and its closest siblings. Maintainers treated a missing check as a gap: #14049 ("I standardized bounds checking so we have consistent exception messages for dimension mismatches") and #15355 ("Add missing checkDimension check to Lucene104ScalarQuantizedVectorScorer#getRandomVectorScorer and some cleanup").
  • Introducing PR: #14863 says "This scorer is in-line with Lucene99MemorySegmentFlatVectorsScorer", which already called checkDimensions at that commit's parent, and its stated goal is "avoiding the unnecessary copy to heap". The recorded keyword search of its review comments found no discussion of dropping validation.
  • Configuration-dependent: the same documents and query raise the IAE with the default provider, with NIOFSDirectory and on 10.3.2 ("vector dimensions differ: 8!=7" from VectorUtil); an index written by the released 10.3.2 jars is rejected on 10.3.2 and answered silently on 10.6.0 and main. Behaviour that changes with the provider and the directory strongly suggests an unintended inconsistency.
The devil's-advocate check113 words

The intended-behaviour review built the strongest case: a wrong-length query is a caller error; FlatVectorsScorer is @lucene.experimental and this class is internal; the format is legacy and read-only; and the KnnFloatVectorQuery javadoc documents an IllegalArgumentException only for k < 1 (KnnFloatVectorQuery.java:61, :75).

Why it fails: the test contract pins the exact IAE, every other configuration for this format enforces it (this class's own heap path included), and before 10.4.0 the same index enforced it too, so this is a regression; silently answering a malformed query is worse than any exception. The cross-model reviews rated the intended-behaviour argument weak. What survives is the impact argument, which is why the bug is Low.

Suggested fix

#

Recommended Call checkDimensions at the start of the mmap branch (validated)

Call FlatVectorsScorer.checkDimensions(target.length, quantized.dimension()) at the start of the mmap branch of getRandomVectorScorer(float[]), before the native or Panama scorer is built (+1 line). The test then passes with assertions on and off, and 556 tests of backward-codecs lucene99 and core internal.vectorization pass.

    if (vectorValues instanceof LegacyQuantizedByteVectorValues quantized
        && quantized.getSlice() instanceof MemorySegmentAccessInput input) {
      FlatVectorsScorer.checkDimensions(target.length, quantized.dimension());
      if (Constants.NATIVE_DOT_PRODUCT_ENABLED) {
        return new NativeRandomVectorScorerImpl(similarityFunction, quantized, input, target);
      }
      return new RandomVectorScorerImpl(similarityFunction, quantized, input, target);
    }

Downstream note

#

Applications that accept query vectors from clients should check their length against the field dimension themselves, as Lucene's threat model leaves input validation to the application.

How it was found

#

Semi-formal: a proof-obligation audit of FlatVectorsScorer's contract. Each scorer that takes a float query must reject one whose length differs from the field dimension; in this scorer's mmap branch nothing discharges that obligation. A one-test JUnit on stock main witnessed it.

The method in full81 words
  • Obligation: every FlatVectorsScorer.getRandomVectorScorer(..., float[] target) rejects a target whose length differs from the field dimension, as the shared FlatVectorsScorer.checkDimensions (:75-80) and BaseKnnVectorQueryTestCase.testDimensionMismatch (:273-284) state.
  • Finding: in Lucene99MemorySegmentScalarQuantizedVectorScorer, only the delegate path discharges it; the mmap branch (:65-70) and the kernels below it (assert only, PanamaVectorUtilSupport.java:997) do not.
  • Witness: a one-test JUnit on the stock main jars with the Panama provider, then the independent checks listed under Independent checks, and this minimal test.

Priority

Impact class

Impact note
Only searches that combine the opt-in Panama vectorization provider (--add-modules jdk.incubator.vector), a Lucene99HnswScalarQuantizedVectorsFormat field (written by Lucene 9.9-10.3; read-only through backward-codecs since 10.4.0) and an mmap-backed directory (MMapDirectory, the FSDirectory.open default on 64-bit JVMs) are hit, and only when the application passes a query vector shorter than the field dimension, which is a caller error: with -da the search returns plausible but wrong top-k hits (each document scored on a prefix of its codes) instead of the IllegalArgumentException that the same index raises with the default provider, a non-mmap directory or on 10.3.2 [exec], with -ea an internal AssertionError fires instead [exec], and a longer query fails loudly with IndexOutOfBoundsException [exec, the intended-behaviour check]; no scale is needed, and 10.4.0 through 10.6.0 and main are affected.
Summary
You open a Lucene99 scalar-quantized vector field of dimension 8 (EUCLIDEAN, 7 bits, 50 docs) in an MMapDirectory with the Panama vectorization provider enabled and search it with a KnnFloatVectorQuery whose query vector has 7 components. You expect IllegalArgumentException 'vector query dimension: 7 differs from field dimension: 8', which Lucene's kNN query tests require and which the same index gives with the default provider, with a non-mmap directory and on 10.3.2. Instead, with assertions disabled, the search returns 10 hits and no error: the mmap branch of Lucene99MemorySegmentScalarQuantizedVectorScorer.getRandomVectorScorer(float[]) never calls FlatVectorsScorer.checkDimensions, quantizes the query at its own length, and scores each document on its first 7 codes with Panama kernels that check lengths only with assert.
