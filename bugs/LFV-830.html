Intervals.within and notWithin are documented as opposites, but a phrase only partly inside the window matches neither

within(X, n, Y) needs all of X inside Y widened by n positions, notWithin(X, n, Y) needs none of X there. So in "the new york times", "new york" is neither within 1 of "times" nor not within it, and the docs, which describe them as opposites, never say so.

The finding in 30 seconds

#

Both factories widen the reference by n positions on each side. within is containedBy that window (Intervals.java:510): the whole source interval must lie inside. notWithin is non-overlap with it (Intervals.java:495-496): no position may touch it. A phrase that overlaps the window without lying inside fails both tests; a single term never can.

Background: interval queries

#
  1. An interval is a run of token positions in a field. A term is one position; in "the new york times" the phrase "new york" is the interval 1-2.
  2. Intervals.within(source, n, reference) and Intervals.notWithin(source, n, reference) keep or drop the source's intervals depending on how near they are to the reference's intervals; an IntervalQuery matches the documents where at least one interval is left.
  3. The flexible StandardQueryParser offers the same two functions as fn:within(source n reference) and fn:notWithin(source n reference).

The finding, step by step

#
  1. You index "the new york times" (positions: the 0, new 1, york 2, times 3) and run within(phrase(new, york), 1, times) and notWithin(phrase(new, york), 1, times).
  2. The docs describe the two as opposites ("appear within" / "do not appear within a set number of positions"), so you expect exactly one to match, most likely within: "new york" ends right before "times".
  3. Instead both count 0. Both widen "times" by 1 to positions 2-4; within wants all of "new york" (1-2) inside that window, notWithin wants none of it there.
  4. within needs n = 2 for this phrase, although the documented single-term examples match a term right next to the reference at n = 1. The query syntax fn:within / fn:notWithin behaves the same. A single term cannot touch the window without lying inside it, so it never falls in this gap.

Who is affected

#

Users of within / notWithin (Java API, or fn:within / fn:notWithin in StandardQueryParser since 9.1.0) with a multi-position source such as a phrase. A phrase right next to the reference is missed by within(..., 1, ...), and notWithin(X, n, Y) and MUST(X) MUST_NOT(within(X, n, Y)) return different documents. Default settings; opt-in experimental package.

Mechanism, terms and numbers757 words

Intervals.within(source, n, reference) and Intervals.notWithin(source, n, reference) are documented as opposites: one returns source intervals that "appear within a set number of positions" of the reference, the other those that "do not appear within" it, and the fn:within / fn:notWithin query-parser docs give both the same "maximum positions" parameter. Both widen each reference interval by n positions on both sides, but within keeps a source interval only if it lies entirely inside that window (containedBy), while notWithin drops it if it touches the window at all (non-overlap).

A single term cannot touch the window without lying inside it, so it never falls in this gap (against a single-term reference the pair splits it exactly; with a nested disjunctive reference the hunt's separate LFV-828 can make it match both). For a phrase or near query, an interval that overlaps the window without lying inside it fails both: on "the new york times", within(phrase(new, york), 1, times) and notWithin(...) both count 0, and within needs n = 2. The code has done this since within was added in 8.0.0 and looks deliberate, so this is a documentation / API-contract defect: the proposed fix states the two relations and the gap in the javadoc and the fn: docs, with a one-line behaviour change only as an option.

The mechanism (main 645d4fe14a20)

#
  1. Both factories widen the reference the same way. within returns containedBy(source, Intervals.extend(reference, positions, positions)) (Intervals.java:508-511); notWithin returns new NonOverlappingIntervalsSource(minuend, Intervals.extend(subtrahend, positions, positions)) (Intervals.java:493-497). extend moves each reference interval's start back by n (clamped at 0, ExtendedIntervalIterator.java:61) and its end forward by n. For "times" at position 3 and n = 1 the window is 2-4.
  2. within tests whole containment. ContainedByIntervalsSource returns a source interval a only when the window b it finds has b.end() >= a.end() (ContainedByIntervalsSource.java:53) and b.start() <= a.start() (:59). "new york" is 1-2 and the window starts at 2, so it is dropped.
  3. notWithin tests no contact. NonOverlappingIterator returns a only when the next window with b.end() >= a.start() (NonOverlappingIntervalsSource.java:72) has b.start() > a.end() (:78). The window starts at 2 and "new york" ends at 2, so it is dropped too.
  4. Partly inside means neither. A single position is either inside a window or apart from it, so a single-term source never falls in this gap; against "times" the pair splits it exactly (executed: the, new, york and times, n = 0 to 3, within + notWithin = 1 every time). Over the same window of a single-term reference, overlapping / nonOverlapping and containedBy / notContainedBy are each exact complements; on the repro document overlapping = 1, nonOverlapping = 0, containedBy = 0, notContainedBy = 1. Only the mixed pair that within / notWithin use leaves a gap. With a disjunctive reference, separate defects change this: with nesting alternatives (LFV-828) notWithin reads fewer reference intervals than within, so a single term can match both (executed: on "visit new york", within(visit, 1, or(york, phrase(new, york))) = 1 and notWithin(...) = 1), and for some or() references LFV-291 breaks containedBy / notContainedBy.

Two shapes

#
  • A source that straddles the window edge, as above: a phrase directly before or after the reference at n = 1. within(phrase(new, york), 2, times) = 1, so within needs n = 2 where the documented single-term examples use n = 1 for a term right next to the reference ("dog" after "lazy", intervalfn/package-info.java:533-535).
  • A source that contains the reference and sticks out more than n positions past it. On "new york", within(phrase(new, york), 0, york) and notWithin(phrase(new, york), 0, york) both count 0, and MUST(phrase) MUST_NOT(within(...)) counts 1 while notWithin counts 0, so two common ways of writing "X but not near Y" disagree. A containing source that sticks out by at most n is within (within(phrase(new york), 0, phrase(new york)) = 1). So, for one occurrence of the reference, a source that contains it falls in the gap exactly when it starts more than n positions before the reference interval or ends more than n positions after it; any source wider than 2n + 1 around a single-position reference is one such case.

Through the query parser

#

fn:within and fn:notWithin call the same factories (Within.java:38, NotWithin.java:38). On the docs' own example sentence, "The quick brown fox jumps over the lazy dog", fn:within(fn:phrase(brown fox) 1 jumps) and fn:notWithin(fn:phrase(brown fox) 1 jumps) both count 0; at n = 0 only fn:notWithin matches and at n = 2 only fn:within.

Exposure and likelihood243 words
  • Who. Callers of Intervals.within / Intervals.notWithin with IntervalQuery, and users of fn:within / fn:notWithin in the flexible StandardQueryParser (since 9.1.0), who pass a multi-position source: a phrase, or an ordered or unordered near. A single-term source never falls in this gap; the upstream tests use single-term sources and the fn: doc examples a disjunction of single terms, so none has a multi-position source.
  • Downstream. The Solr 10.1 intervals query parser exposes within / not_within with the same opposite-pair wording; the Elasticsearch and OpenSearch intervals queries do not offer these two filters.
  • Default vs opt-in. Default analyzer, codec and searcher; the relation is decided per source interval inside one document, so index size plays no part (the repro uses one document). The intervals package is opt-in (the queries module) and labelled "experimental classes" (intervals/package-info.java:21).
  • What goes wrong. Fewer hits than the docs describe; splitting a source's matches into "near Y" and "not near Y" silently loses the partly-near ones; an exclusion written two common ways returns different documents. No error, deterministic, nothing written to the index.
  • Age and likelihood. The gap is present from 8.0.0 (2019) through 10.6.0 and on main; the recorded searches found no public report, which suggests that accidental hits are rare (a judgement, not measured).
  • Scope of the evidence. The repro uses a single-term reference with one occurrence; disjunctive, nested or repeated references are not part of this claim (for nesting or() alternatives see the separate LFV-828).

Why it looks unintended

#
  • The docs present the pair as opposites: "appear within" / "do not appear within a set number of positions", and fn:within / fn:notWithin share one parameter text.
  • #9675, which added within, calls it the "inverse of the already available NOT_WITHIN".
  • No doc or test mentions the partly-near case; the code looks deliberate, so the fix is the docs.
The full argument316 words
  • The summaries use the file's own complement vocabulary. In Intervals.java, "appear within" / "do not appear within" describe containedBy (:554) and notContainedBy (:541-542), an exact complement pair for a non-disjunctive reference (the separate LFV-291 breaks it for some or() references); within and notWithin use the same words (:500-501, :485-486), and so does the package overview (intervals/package-info.java:68-70).
  • The query-parser docs differ only by an emphasized not. fn:within: "Matches intervals of the source that appear within the provided number of positions from the intervals of the reference"; fn:notWithin: the same with "do <em>not</em> appear within" (intervalfn/package-info.java:515-516, :544-545). Both take "an integer number of maximum positions between source and reference" (:526, :555), and the source is a "term or other function" (:524, :553), so a phrase is a documented input.
  • Intent at introduction. #9675 / LUCENE-8629 lists "a WITHIN b - inverse of the already available NOT_WITHIN" and, in the same list, "a OVERLAPPING b - inverse of the already available NOT_OVERLAPPING" (as @romseygeek wrote there). Over a non-disjunctive reference, overlapping and nonOverlapping are exact complements.
  • Nothing documents the gap. No javadoc, overview, fn: doc, CHANGES entry or test says that within needs the whole source inside the widened window, that notWithin rejects any contact, or that a partly-near interval matches neither. The upstream tests use single-term sources only (TestIntervals.java:915-922, TestIntervalQuery.java:182-186), and the fn: doc examples a disjunction of single terms (fn:or(fox dog), intervalfn/package-info.java:533-538), so every exercised source is single-position.
  • The parameter text is ambiguous for a phrase. By the docs' single-term convention ("dog" right after "lazy" matches at 1), "brown fox" right before "jumps" would match at 1; it needs 2. That follows only if the distance is measured to the farthest position of the source, which no doc says.
The devil's-advocate check338 words

Strongest case for "intended" (the study's devil's advocate and a cross-model reviewer, OpenAI GPT-5.6): read pointwise, the Java @param texts describe the code: within's "the maximum distance that intervals of the source may occur from intervals of the reference" (Intervals.java:504-505) means every position at most n away, i.e. containment; notWithin's "the minimum distance ..." (:489-490) is a bound on every position, i.e. no contact (the code keeps a position only if it is more than n away). LUCENE-8629 changed notWithin's @param from "maximum" to "minimum" in the same commit that added within. notWithin equals SpanNotQuery(include, exclude, n, n) (executed, n = 0 to 3). The package is experimental, the tests are single-term, and the recorded searches found no complaint since 2019. The reviewer: "within and notWithin are deliberately different endpoint-distance filters, not Boolean negations."

Why it fails: it shows that the code is intended, which is why this is classed as documentation and not as wrong results; it does not show that the documentation describes the behaviour. The gap follows from one reading of the Java @params only, and even under that reading the notWithin text is off by one: "dog" right after "lazy" is 1 position away, yet fn:notWithin(dog 1 fn:or(quick lazy)) drops it (executed in the tie-break; the fn:notWithin doc example shows the same), so the smallest distance notWithin keeps is n + 1, not the stated minimum n. The fn: docs, which document the query-string route, have no maximum / minimum distinction. Before LUCENE-8629, notWithin's @param said "the maximum distance" (LUCENE-8196, 2018); read literally, that describes what within keeps, not what notWithin keeps. The reviewer itself wrote that the parser docs' "symmetric 'maximum positions' wording could reasonably be clarified to state whole containment for within, no contact for notWithin, and that partial intersections match neither": that clarification is the proposed fix. Confidence: high on the behaviour and the documentation gap, medium on how upstream will want to resolve it (a javadoc clarification is the most likely outcome).

Suggested fix

#

Recommended A. Document the two relations and the gap (recommended)

Document what the code does: the reference is widened by n positions on both sides, within needs the whole source interval inside, notWithin needs no overlap, and an interval only partly inside matches neither. No behaviour change. Validated with gradle: the format and javadoc checks pass, and the intervals and flexible-parser suites pass.

Downstream note

#

Products that hand these functions to their own users, such as Solr's intervals query parser (within / not_within), repeat the opposite-pair wording, so their users inherit the gap.

How it was found

#

Semi-formal. A hunt unit checked whether interval filters documented as opposites really split every match, running the real jar over every pair of small interval sets (32,695,520 filter evaluations). Apart from a separately registered notContaining bug, only within / notWithin failed; the case was then reduced by hand to the one-document test.

The method in full210 words
  • Step 1, the documented relation. The unit first settled from the docs which pairs are presented as opposites: within / notWithin ("appear within" / "do not appear within"), containedBy / notContainedBy, overlapping / nonOverlapping.
  • Bounded-exhaustive leg. FilterLawsExhaustive fed every pair of minimal interval sets inside positions 0-6 (1,430 x 1,430 pairs, 32,695,520 filter evaluations) through the real filter classes via a public custom IntervalsSource. containedBy / notContainedBy and overlapping / nonOverlapping over a widened reference were exact complements; apart from a separately registered notContaining defect, the only violations were within / notWithin "neither" (2,530,558 / 645,023 / 106,025 intervals for n = 0 / 1 / 2). That put the gap in the two factories, not in the filter iterators.

LFV-830, snapshot of 2026-11-02

Registry title
Intervals.within and notWithin are documented as opposites, but a multi-position source interval only partly inside the n-position window around the reference matches neither (documentation / API-contract defect)
Area
queries / intervals (Intervals.within / Intervals.notWithin and their javadoc; queryparser fn:within / fn:notWithin docs)
Priority
Low, rank 1006: A documentation and API-contract defect where within and notWithin are documented as opposites but are not exact complements for multi-position sources in this little-used pair.
Impact class
minor
Impact note
Anyone who calls Intervals.within / Intervals.notWithin (directly, through IntervalQuery, or as fn:within / fn:notWithin in the flexible StandardQueryParser since 9.1.0) with a multi-position source (a phrase, ordered or unordered near) and reads the docs, which present the pair as opposites, with default writer, codec, analyzer and searcher settings, at any index size, with -ea and -da, in every release from 8.0.0 to 10.6.0 and on main: a source interval that straddles the edge of the n-position window around the reference, or that contains a single-position reference and is wider than 2n+1 positions, is returned by neither query, so 'X but not within n of Y' written as notWithin(X, n, Y) and as MUST(X) MUST_NOT(within(X, n, Y)) return different documents; single-position sources (the shape of every upstream test and doc example) are exact complements [exec: controls]; the code does what each @param can be read to say, so the defect is classed as documentation, and nothing is written to the index.
Summary
You index 'the new york times' and run within(phrase(new, york), 1, times) and notWithin(phrase(new, york), 1, times), and you expect exactly one of them to match, because the javadoc says within returns source intervals that 'appear within a set number of positions' of the reference and notWithin those that 'do not appear within' it, and the fn:within / fn:notWithin docs give both the same 'maximum positions' parameter. Instead neither matches: within keeps an interval only if all of it lies inside the window [r.start-n, r.end+n] (here [2,4]), while notWithin drops it if any part touches that window, so 'new york' at [1,2], which touches the window without lying inside it, is in neither result (within needs n = 2 for a phrase directly next to the reference). In the same way, on 'new york' both within(phrase(new, york), 0, york) and notWithin(phrase(new, york), 0, york) return nothing, and no doc says that a partly-near interval matches neither.
