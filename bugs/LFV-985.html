TSTLookup throws StackOverflowError on deep trees: a list added in sorted order cannot be stored or loaded, and one long suggestion breaks build()

A TSTLookup filled by add() in sorted order (the 20,992 CJK ideographs) answers lookup(), but store(), load() and ramBytesUsed() throw StackOverflowError, and one 20,000-character suggestion breaks build() itself in a fresh JVM. Each of these methods recurses once per tree level; every release since 3.3.0 has it.

The finding in 30 seconds

#

TSTLookup keeps suggestions in a ternary search tree and walks it with one Java stack frame per tree level whenever it adds, stores, loads or measures. A tree thousands of levels deep runs the thread stack out.

Two things to know first

#
  1. A ternary search tree stores one character per node, with three links: lo to a smaller character at the same position of the key, eq to the key's next character, hi to a larger character at the same position.
  2. The lo/hi links at one position form an ordinary binary search tree with no rebalancing. Insert a, b, c, ... in sorted order and each new node becomes the hi child of the last one: a chain, not a tree.

The finding, step by step

#
  1. You call add() once for each of the 20,992 CJK Unified Ideographs, U+4E00 to U+9FFF, in code-point order, then store() the lookup to save it.
  2. You expect store() to return true, as its javadoc promises (failure is a false return or an IOException), and as it does for the same keys added through build() or in shuffled order.
  3. Instead store() throws StackOverflowError on a 2 MiB thread stack, and so do load() and ramBytesUsed(). get() and lookup() still work: the lookup works in memory but cannot be saved or reloaded.
  4. Why: each larger character hangs off the previous one's hi link, so the tree is one chain 20,993 nodes deep, and store(), load(), ramBytesUsed() and add() itself use one Java stack frame per node.
  5. build() balances only the lo/hi links, and every character of a key adds a level, so one 20,000-character suggestion overflows build() in a fresh JVM, while WFSTCompletionLookup accepts it.

Who is affected

#

Applications using the opt-in TSTLookup whose tree gets deep: a word list with thousands of distinct first characters (a CJK dictionary, say) fed to add() in sorted order, or one suggestion thousands of characters long, even through build(). The error is loud and rare, but such a lookup cannot be saved or reloaded.

Mechanism, terms and numbers829 words

TSTLookup keeps its suggestions in a ternary search tree, one character per node. Four methods walk that tree recursively, one Java stack frame per tree level: TSTAutocomplete.insert (behind add() and build()), TSTLookup.writeRecursively (store()), readRecursively (load()) and TernaryTreeNode.sizeInBytes (ramBytesUsed()). At each key position the lo/hi links form a plain binary search tree with no rebalancing, so add() in sorted order builds a chain about as deep as the number of distinct first characters (that sorted insertion leaves this tree highly unbalanced was noted by the TST's author, Ankul Garg, on SOLR-1316 in 2009, as a speed concern). Every character of a key also adds one level, so one long suggestion is deep even through build().

Adding the 20,992 CJK Unified Ideographs in code-point order gives a tree 20,993 levels deep: add(), get() and lookup() work, but store(), load() and ramBytesUsed() throw StackOverflowError on the JVM's default thread stack (2040 KiB on Linux aarch64). One 20,000-character suggestion makes build() itself overflow in a fresh JVM. Lookup.store and load document failure only as a false return or an IOException, and add() "always returns true" with no order or length limit. The same keys through build(), or add()ed in shuffled order, work. Every release from 3.3.0 to 10.6.0, and main, has the recursive code; 11 of those releases, Solr 3.1.0, the 10.6.0 release commit and main were run and fail. An iterative rewrite of the four walks, in the same byte format, fixes it.

The mechanism (code at 645d4fe14a20)

#
  1. The tree. A TernaryTreeNode holds one character (splitchar) and the links loKid, eqKid, hiKid (TernaryTreeNode.java:27-40). TSTLookup starts from a sentinel root whose splitchar is U+0000 (TSTLookup.java:43, :125, :277).
  2. Insertion recurses once per level. TSTAutocomplete.insert (TSTAutocomplete.java:57-86) calls itself through loKid (:73) and hiKid (:83) without advancing the key position, and through eqKid once per character (:66, :76). add() calls it on the root with no balancing (TSTLookup.java:149-153).
  3. Sorted add() builds a chain. Increasing characters each become the hiKid of the previous one: 20,992 one-character keys give a hiKid chain under the root, depth 20,993. Law T1 (the finder's): add() in increasing or decreasing order gives depth at least 1 + the number of distinct first characters, whatever the key length; checked against the real tree read back through store() for 81 values of n from 0 to 2,960 (every n up to 49, then steps of 97) and 300 random sorted and reverse-sorted dictionaries, 0 mismatches.
  4. build() balances only the lo/hi links. It sorts the input (TSTLookup.java:117-142) and inserts it middle-first through balancedTree (TSTAutocomplete.java:40-46, itself only about log2(n) deep). Law T2 (proved, and checked on every non-empty set of up to 4 of 39 short keys): through build() the depth is at most the longest key length + floor(log2 n) + 1, and the bound is tight. Short keys are safe; each character of a long key adds one eqKid level.
  5. The other walks recurse once per level too. writeRecursively (TSTLookup.java:242-265, calls at :257, :260, :263) for store() (:267-272); readRecursively (:218-239, calls at :229, :233, :237) for load() (:274-280); TernaryTreeNode.sizeInBytes (TernaryTreeNode.java:50-69, calls at :53, :56, :59) for ramBytesUsed() (TSTLookup.java:282-290). get() and lookup() use prefixCompletion (TSTAutocomplete.java:97-148), which already walks with an explicit ArrayDeque: they work even on a 41,002-level tree with a 256 KiB thread.
  6. Side note: the add() javadoc (TSTLookup.java:145) reads "Adds a new node if <code>key</code> already exists, otherwise replaces its value", the inverse of what insert does (since d4aace10381, 2012).

Where the stack runs out

#

Largest tree depth (store, load, ramBytesUsed) or key length (build) that survives; "sorted add" = how many of 41,000 one-character keys, added in sorted order, went in before the first add() threw (> 41,000 = all of them); a fresh JVM per trial, JDK 25.0.3, Linux aarch64, -da, full tiered JIT. "Cold" = no warm-up, "warm" = every entry point compiled first.

Exposure and likelihood319 words
  • Who is exposed. Users of TSTLookup (opt-in, not deprecated; FSTCompletionLookup's javadoc points to it).
  • Trigger 1: sorted add() of a word list with thousands of distinct first characters, in practice a CJK-scale dictionary (for Latin-script words each per-position chain is bounded by the alphabet; a reading of the code, not run). add() has no in-tree caller, but it is public.
  • Trigger 2: one long suggestion, through build() or add(). An independent check reached it through Lucene's own LuceneDictionary over an indexed StringField term of 8,000 bytes: TSTLookup.build threw StackOverflowError on a 1 MiB thread in 8 of 8 runs (main and 10.5.2); 12,000- and 32,000-byte terms failed too.
  • What breaks. The lookup works in memory but cannot be stored or loaded, so it is lost on restart; a load() that fails this way also leaves the lookup half replaced (a separate bug, LFV-979).
  • Scale. Thousands of levels: in a fresh JVM on a 1 MiB thread store()/load() fail from about 5,300 levels and build() from about 5,900 characters; on a 2040 KiB thread from about 10,800-12,500 levels and 12,400 characters. The JIT state moves these numbers.
  • How likely. Rare: it needs a degenerate input shape, and the searches found no public report since 2011. The error is a loud StackOverflowError in the calling thread, with no index damage; but a store() that overflows has already written part of the tree (the count first, then each node before the walk goes below it), so the output it was writing to holds an incomplete copy (a reading of the code, not run).
  • Workarounds. build() instead of sorted add() (short keys only), a cap on suggestion length, or running the steps that walk the tree on a thread with a larger stack: store(), load() and ramBytesUsed(), and for a long suggestion build()/add() too (the sorted add() itself also overflows under C1-only JIT flags).

Why it looks unintended

#
  • add() "always returns true" with no order or length limit; store() and load() name only false or an IOException as failure.
  • Order alone flips it: the same keys pass via build() or shuffled. build() accepts 32,759-byte suggestions, yet a 20,000-character one overflows it (fresh JVM).
  • Lucene fixed the same one-frame-per-character trap in suggester building as a bug (LUCENE-5628, 4.8.1).
The full argument343 words
  • Contract. TSTLookup.add: "This method always returns true", no order or length limit (TSTLookup.java:144-153). Lookup.store: "Persist the constructed lookup data to a directory. Optional operation. ... @return true if successful, false if unsuccessful or not supported. @throws IOException when fatal IO error occurs." Lookup.load: "Discard current lookup data and load it from a previously saved copy", with the same failure modes (Lookup.java:236-252).
  • Lengths the module accepts. build() sorts through OfflineSorter, which rejects entries over 32,767 bytes with a clear IllegalArgumentException (OfflineSorter.java:550-551); with the 8-byte weight, build() accepts suggestions up to 32,759 UTF-8 bytes (run by the fact check: 32,759 bytes accepted, 32,760 rejected with "len must be <= 32767; got 32768"). The 20,000-character suggestion is ASCII, 20,000 bytes. WFSTCompletionLookup builds, stores and loads it on a 1 MiB thread.
  • Order alone flips the result. The same 20,992 keys through build(), or add()ed in the shuffled order tested, complete every step; the limit is tree depth, not key count.
  • Tests. Only TestPersistence and the @Ignored TestLookupBenchmark use TSTLookup, through build() with short keys; no test asserts or excludes deep trees.
  • Precedent. LUCENE-5628, under Lucene 4.8.1 "Bug fixes" (core's automaton code, used when building suggesters): "Change getFiniteStrings to iterative not recursive implementation, so that building suggesters on a long suggestion doesn't risk overflowing the stack; previously it consumed one Java stack frame per character in the expanded suggestion. If you are building a suggester this is a nasty trap." More CHANGES entries that removed or bounded stack-exhausting recursion: GITHUB#16423, #11813, #11537, LUCENE-10181, LUCENE-7914, LUCENE-7956 (listed by the intended-lens reviewer, OpenAI GPT-5.6) and GITHUB#12286, "Toposort use iterator to avoid stackoverflow" (added by the finder).
  • History. On SOLR-1316 (2009) the TST's author, Ankul Garg, wrote that adding strings "in sorted order in TST will make the tree highly unbalanced" and that balancedTree "takes care of that"; Andrzej Bialecki asked whether it could be rebalanced on the fly. They discussed speed; store()/load() (2011) and the recursive size method (2014) did not exist yet.
The devil's-advocate check215 words

The strongest "works as designed" case: (a) the authors knew sorted insertion unbalances the tree and handled it only in build(); add() is a vestige (no longer in the Lookup API since LUCENE-3807, no in-tree caller, not counted by getCount()). (b) Maintainers declined iterative rewrites for very long input before: on LUCENE-5659 (#6721, Won't Fix) Robert Muir declined an iterative isFinite and called such use "abuse of the automaton pkg for what its not designed to do"; on LUCENE-6156 (#7218, Not A Problem) Michael McCandless wrote that making the code non-recursive "makes the code more complex". (c) Lookup is @lucene.experimental and Accountable @lucene.internal (a point from the refute-lens reviewer, OpenAI GPT-5.6).

The answer: nothing in (a) is documented, and the long-key leg needs no sorted input: build(), the path the authors made safe, overflows on one legal suggestion that WFSTCompletionLookup accepts. On (b), both refused code paths were later changed by bounding or removing the recursion (LUCENE-7914 and GITHUB#11813 for isFinite; GITHUB#11537 / PR #12462 for RegExp), and LUCENE-5628 was fixed as a bug. (c) weakens only the ramBytesUsed() leg. This shows the behavior is not documented as intended; it does not settle the design choice: a maintainer could still prefer a length limit, deprecation or no change over a rewrite.

Suggested fix

#

Recommended A. Walk the tree iteratively (validated)

Walk the tree without recursion: insert loops down and appends the rest of the key as an eqKid chain; store, load and sizeInBytes use an explicit ArrayDeque in the same pre-order, so the stored bytes do not change. With it the repro and every suggest-module test pass.

All options and trade-offs5 options · 2,080 words

Option A was applied in scratch worktrees of main 645d4fe14a20 and run through gradle (seed DEADBEEF) and the repro harness. Options B to E were not run.

A. Walk the tree iteratively (validated) (recommended)

#

Three files, +127/-82 lines:

  • TSTAutocomplete.insert: a loop walks down (lo/hi without advancing the key position, eq advancing it) and remembers the parent and the link; at the first missing node it appends the rest of the key as a chain of eqKid nodes. Same signature, return value and tree.
  • writeRecursively / readRecursively become writeTree / readTree: pre-order with an explicit ArrayDeque, kids pushed hi, eq, lo so they come off lo, eq, hi.   • The add() javadoc: "Adds a new node if <code>key</code> does not exist yet, otherwise replaces its value."

Trade-offs

  • The explicit stacks live on the heap: about one entry per pending sibling on the current path, small next to the tree.
  • Nothing is rebalanced: sorted add() still builds a chain and visits about n²/2 nodes for n keys, as today; only stack use changes. No benchmark was run.
  • A load() that fails part-way leaves slightly different garbage (kids are allocated before their bytes are read); either way the lookup is half replaced (LFV-979).

What the checks validated

  • Stock: the repro fails with java.lang.StackOverflowError in add() under Lucene's default local test JVM flags (this step, 2026-10-30) and with ... in store() under the full JIT (TEST_JVM_ARGS=-XX:+UseParallelGC, an earlier run of this step).
  • With option A applied (this step, 2026-10-30): the repro and TestPersistence, the only upstream test that runs TSTLookup, pass under the default flags with assertions on: :lucene:suggest:test (SUCCESS): 3 tests, 0 failures.
  • With option A, an earlier run of this step on the same commit: all of :lucene:suggest:test with the repro added passes (32 classes, 237 tests, 7 skipped, 0 failures); the repro passes with the full JIT; :lucene:suggest:check -x test (format, ecjLint, forbiddenApis) passes with the test and the fix added (not run on stock code plus the test).
  • Repro harness, patched classes shadowed: the repro passes with -ea and -da; the finder's 8-test JUnit passes 8 of 8 (6 of 8 fail stock), covering build() and add() of a 20,000-character key, load() of a stored deep tree and ramBytesUsed() on 1 MiB threads.
  • Byte-level check (400 random dictionaries, 78,005 observations of store() bytes, bytes stored after load(), get, lookup, ramBytesUsed): the same SHA-256 on stock and patched code; a mutant whose readTree pushes lo before hi fails. It covers only trees the stock code can store.

B. Reject over-long suggestions with an IllegalArgumentException (not run)

#

Cap the key length in insert (or in build() and add()), with a clear exception, as OfflineSorter does for entries over 32,767 bytes.

Trade-offs

Smaller, but it covers only the long-key leg: the sorted-add depth comes from the number of distinct first characters, so it would also need a depth limit that rejects add() calls that work today, at a threshold that depends on the stack size.

C. Document the limits (not run)

#

Say in the add() javadoc that it does not rebalance and that keys added in sorted order build a tree that store() and load() may not handle; recommend build().

Trade-offs

No code change, but build() still overflows on one long legal suggestion.

D. Rebalance on add() (not run)

#

Keep the lo/hi links of each key position balanced as add() inserts (rotations, or a periodic rebuild), so sorted adds no longer chain.

Trade-offs

Covers only the sorted-add leg: a long key is one eqKid level per character, which no rebalancing shortens, so build() of a long suggestion still needs option A or B. More invasive than A, and it changes the tree shape that sorted adds give today (a reading of the code, not run).

E. Deprecate TSTLookup (not run)

#

Deprecate it, and later remove it, in favour of the FST-based suggesters, as Michael McCandless suggested for the sibling Jaspell trie on LUCENE-5775 (#6837); Jaspell was removed in 9.0.0 (LUCENE-8638).

Trade-offs

No code fix for current users until they migrate, and FSTCompletionLookup's javadoc still points to TSTLookup.

Downstream note

#

Applications that build a TSTLookup from indexed or user-contributed text should cap the suggestion length, and prefer build() to sorted add(), until this is fixed.

How it was found

#

Semi-formal: a probe that added 5,000 two-character keys in sorted order failed at load(). An independent model of the tree was then compared with the real tree read back through store(), bounded-exhaustively for small inputs (774,462 checks, 0 mismatches), which gave the two depth laws; the bug was then reduced to one public-API test.

The method in full153 words
  • First signal. A planning probe added 5,000 two-character keys in sorted order: load() threw StackOverflowError on a 1 MiB thread (2026-10-28).
  • Method: bounded-exhaustive differential model check. An independent iterative model of the ternary tree against the real tree read back through the public store() output: every add() sequence of up to 4 keys from 12 strings and every non-empty build() set of up to 4 of 39 keys, plus sequential and random scopes (774,462 checks, 0 mismatches; a lo/hi-swap mutant of the model was rejected). That established law T1 (sorted add(): depth at least 1 + distinct first characters) and law T2 (build(): depth at most key length + floor(log2 n) + 1).
  • Then the finder measured the stack threshold of every entry point (fresh JVMs, 512 KiB to 2 MiB, cold and warm JIT), wrote a public-API JUnit (8 tests), and the repro was later minimized to one test.

LFV-985, snapshot of 2026-11-02

Registry title
TSTLookup recurses once per ternary-tree level in add/build, store, load and ramBytesUsed, so a deep tree (short keys added in sorted order, or one suggestion thousands of characters long) throws StackOverflowError, often only when the lookup is stored or loaded (every release since 3.3.0)
Area
suggest / ternary search tree suggester (TSTLookup add, build, store, load and ramBytesUsed; TSTAutocomplete.insert; TernaryTreeNode.sizeInBytes)
Priority
Low, rank 541: The opt-in TSTLookup throws StackOverflowError only for degenerate deep trees such as a large sorted CJK list or a suggestion thousands of characters long, a loud rare-input crash.
Impact class
crash
Impact note
Hits applications that use the opt-in TSTLookup suggester and end up with a deep tree: either they add() a word list in sorted order whose entries start with thousands of distinct characters (for example a CJK dictionary; add, get and lookup still work, but store(), load() or ramBytesUsed() throw StackOverflowError, so the lookup cannot be persisted or reloaded), or one suggestion is thousands of characters long, which already fails in build() or add(); short keys through build() are safe, the threshold depends on the thread stack size and the JIT state (in the measured fresh JVMs about 5,300 tree levels or 6,000-10,000 characters on a 1 MiB thread, about 12,000-16,000 levels or 20,000 characters on a 2 MiB stack), the error is loud, and every release since 3.3.0 has it.
Summary
You add the 20,992 CJK Unified Ideographs to a TSTLookup in code-point order, or build one from a single suggestion of 20,000 characters, and expect to store it, load it back and ask its size, as Lookup.store and Lookup.load promise (they document failure only as a false return or an IOException) and as WFSTCompletionLookup does with the same 20,000-character suggestion. Instead add(), get() and lookup() work, but store(), load() and ramBytesUsed() throw StackOverflowError on the JVM's default thread stack, and for the long suggestion build() itself overflows, because TSTAutocomplete.insert, TSTLookup.writeRecursively and readRecursively and TernaryTreeNode.sizeInBytes each use one Java stack frame per tree level. Adding keys in sorted order turns each level's lo/hi links into a chain (that sorted insertion unbalances this tree was noted by its author, Ankul Garg, on SOLR-1316 in 2009, as a speed concern), so the tree gets about as deep as the number of distinct first characters, and every character of a key adds one more level even in build().
