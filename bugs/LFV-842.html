A logging failure inside IndexWriter.registerMerge leaves a half-registered merge, and the next forceMerge commits duplicated documents

If the InfoStream throws inside registerMerge, the merge stays queued but its segments are never marked as merging. If the application catches it and keeps using the writer, the next forceMerge(1) merges the same segment again and, with assertions off, commits its documents twice (2 live documents instead of 1).

The finding in 30 seconds

#

registerMerge queues the merge (pendingMerges.add) before it writes its IW log lines, and marks the merge's segments in mergingSegments only after them (the last log line runs once per segment, each followed by marking that segment); registerDone comes last. A throw from the logger in between leaves a queued merge whose segments look free, so the next merge request is allowed to take them again.

How IndexWriter avoids merging a segment twice, in one minute

#
  1. A merge policy proposes merges: lists of segments to rewrite as one new segment.
  2. registerMerge accepts a merge only if none of its segments is in mergingSegments, the set of segments already being merged. It then queues the merge in pendingMerges, adds its segments to mergingSegments and sets registerDone.
  3. The merge scheduler takes queued merges and runs them. When a merge commits, its segments are replaced by the new one and leave mergingSegments.

The finding, step by step

#
  1. Add 2 documents (ids 0 and 1), delete id 0 and commit: one segment _0 with 1 live document. The writer logs through Lucene's JavaLoggingInfoStream, and its java.util.logging handler is set to throw once.
  2. Call forceMergeDeletes(). It picks _0, the segment with a deletion; the handler throws IllegalStateException on the log line "add merge to pendingMerges". You get the exception; the writer stays open.
  3. Call forceMerge(1) and close(). You expect 1 live document: nothing was added and the failed call merged nothing.
  4. Instead, with assertions off, the commit holds 2 live documents, both id 1. The failed call had already queued its merge of _0 but not yet marked _0 as merging, so forceMerge(1) queued a second merge of _0, and both ran.
  5. With assertions on, forceMerge(1) fails instead: AssertionError at assert merge.registerDone in IndexWriter._mergeInit, and the writer closes itself. close() or rollback() right after the failure avoids the duplicate.

Who is affected

#

Applications that enable the writer's IW InfoStream (off by default) and whose logging can throw: a throwing handler behind JavaLoggingInfoStream, a custom InfoStream, or an OutOfMemoryError at a log call. The first failure is loud; the duplicates need the application to catch it and keep merging. No scale needed; the default ConcurrentMergeScheduler duplicates only in some runs.

Mechanism, terms and numbers587 words

IndexWriter.registerMerge queues a merge first, then writes its IW InfoStream messages, and marks the merge's segments as merging only after them (the last message runs once per segment, each followed by marking that segment); registerDone is set last. If the InfoStream throws at the first message, for example a failing java.util.logging handler behind the shipped JavaLoggingInfoStream, the exception reaches the caller and the writer stays open, but the queued merge's segments look free. If the application catches the exception and keeps using the writer, the next merge selection may take them again: in the repro forceMerge(1) merges the same segment a second time and commits 2 live documents instead of 1 (with assertions off), or fails assert merge.registerDone (with assertions on). Executed on 17 releases from 3.2.0 to 10.6.0 and on main; from 2.3.0 to 3.1.0 the second merge was rejected instead. close() or rollback() right after the failure leaves the right content.

The order inside registerMerge (IndexWriter.java at 5adff78bb168)

#
  1. The deliberate checks come first: merges disabled throws MergeAbortedException (:5164-5166); a segment already in mergingSegments makes it return false (:5171-5181); ensureValidMerge (:5203).
  2. pendingMerges.add(merge) (:5205): the merge is queued.
  3. The InfoStream messages: "add merge to pendingMerges: ..." (:5207-5215), "registerMerge merging= [...]" (:5233) and then, inside the marking loop, one "registerMerge info=" per segment (:5238), each followed by mergingSegments.add(info) (:5240). A merge of N segments writes 2 + N messages.
  4. addEstimatedBytesToMerge(merge) (:5243), which reads file sizes and can throw IOException.
  5. merge.registerDone = true (:5246).

A throw in step 3 leaves the merge queued with registerDone == false and none (or, at a "registerMerge info=" message, only the earlier) of its segments marked. An IOException in step 4, the trigger in #9738, leaves registerDone == false with every segment marked, so nothing can select them again: no duplication.

What happens in the repro

#
  • forceMergeDeletes() registers its merge of _0, the segment with a deletion, under the writer lock (:2358-2365) and calls the merge scheduler only afterwards (:2367), so the exception leaves before anything runs. A non-tragic exception does not close the writer. After the throw the probe printed isOpen=true tragic=null hasPendingMerges=true mergingSegments=0.
  • forceMerge(1) asks the merge policy for a forced merge (updatePendingMerges, :2454-2518). LogMergePolicy proposes _0 again, because a single segment counts as merged only without deletions (LogMergePolicy.java:378-379, MergePolicy.isMerged at MergePolicy.java:736-747), and the conflict check at :5171 passes because _0 is not marked. The log reads "add merge to pendingMerges: _0(12.0.0):c2/1 [total 2 pending]".
  • getNextMerge (:2538-2551) hands out both merges. With assertions on, the first fails assert merge.registerDone in _mergeInit (:5275) and the writer closes itself.
  • With assertions off, both run: _0 becomes _1 (1 document), then _0 is merged again into _2 (1 document). At the second commit none of the merge's sources is in the index any more, so SegmentInfos.applyMergeChanges inserts _2 at position 0 (SegmentInfos.java:1159-1160). The comment above that branch (:1154-1158) expects it only when every merged segment became fully deleted, "in which case it should be the case that the new segment is also all deleted"; _2 holds a live document. Nothing checks that the source was already merged away. forceMerge(1) then merges _2 and _1 into one segment of 2 documents.
  • mergeFinish (:5374-5390) removes segments from mergingSegments only if (merge.registerDone), so the half-registered merge never cleans up either.
Exposure and likelihood400 words
  • What breaks. Documents that were added once are committed twice: every live document of the segments the failed call had picked (here the one live document; 6 of 10 in the earlier three-segment repro). The calls that commit them (forceMerge(1), close()) report no error; the only error the application saw was the earlier exception from forceMergeDeletes(), which it caught. The index reads normally afterwards. No structural corruption is claimed; CheckIndex was not run on the duplicated index.
  • Who is exposed. The InfoStream is opt-in (IndexWriterConfig.setInfoStream, public; the default is InfoStream.NO_OUTPUT). The throw can come from a java.util.logging handler behind the shipped JavaLoggingInfoStream that throws instead of reporting through its ErrorManager (the repro), from a custom InfoStream, or from an OutOfMemoryError at the same log call (executed earlier with an OutOfMemoryError thrown from InfoStream.message: the writer stays open with no tragic exception and the next forceMerge(1) duplicates the same documents; a real allocation failure while the string is built would land in the same window, not executed). The JDK's own handlers catch format and write failures and report them through ErrorManager, so a stock JDK handler does not trigger it; the repro installs a handler that throws.
  • What else it takes. The application keeps using the writer after the exception and starts another merge over the same segments before the queued one runs: forceMerge in the repro; a natural merge after a flush should do the same if the merge policy selects those segments (by reading, not executed). close() or rollback() right after the failure leaves the 1 live document with assertions off (executed); with assertions on, close() runs the queued merge and trips the same assertion.
  • Default merge scheduler. With ConcurrentMergeScheduler the two merges race. On main a9779ef3c193 (same registerMerge), 5 of 20 and 2 of 10 iterations of two independent repros committed duplicates; the rest failed with NullPointerException ("rld is null"), which closes the writer tragically and loses its uncommitted changes.
  • Another executed path (a fault-injection sweep, not the repro): with maxFullFlushMergeWaitMillis > 0, a throw inside registerMerge during a merge on commit (recorded for commit() and getReader()) made the retried commit fail with NullPointerException, IllegalStateException or IllegalArgumentException "Self-suppression not permitted" (main e1faeba08bde).
  • Likelihood: contrived. A throwing logging path exactly inside a window of a few log statements, then continued use of the writer.

Why it looks unintended

#
  • Registration is meant to be all or nothing: every deliberate throw in registerMerge comes before the merge is queued, and assert merge.registerDone says a queued merge is fully registered.
  • The forceMerge javadoc promises that exceptions do not corrupt the index (IndexWriter.java:2213-2214).
  • Lucene's own tests throw from InfoStream.message on purpose and require a good index (testExceptionDuringRollback).
The full argument217 words
  • All or nothing by design. The registerMerge javadoc says a registered merge is one whose segments "we record ... are now participating in a merge" (:5153-5155). Its deliberate throws (:5164-5166, :5203) all come before pendingMerges.add (:5205); assert merge.registerDone in _mergeInit (:5275) and commitMerge (:4908) states the invariant.
  • No corruption on exceptions. The forceMerge javadoc (:2213-2214) promises that an exception neither corrupts the index nor loses documents. That sentence is about forceMerge's own exceptions; here the exception escapes forceMergeDeletes, and the damage shows up in the next forceMerge, which itself hits no exception. No API documents duplicated documents as a possible outcome.
  • Lucene's tests inject exactly this fault. TestIndexWriterExceptions.testExceptionDuringRollback (:1980) throws RuntimeException("BOOM!") from InfoStream.message; then, under the comment "even though we hit exception: we are closed, no locks or files held, index in good state" (:2042), it asserts that the writer is closed, the write lock is free and the index still has its 10 documents (:2043-2047). testOnlyRollbackOnceOnException (:2195), testOutOfMemoryErrorCausesCloseToFail (:1111) and testOutOfMemoryErrorRollback (:1150) inject through InfoStream.message too.
  • History. LUCENE-1554 (#2628, 2009) and LUCENE-1210 (#2287, 2008) fixed earlier exception-safety gaps in the same bookkeeping (mergeFinish, mergeInit).
The devil's-advocate check202 words

The strongest case for "works as designed": InfoStream is a "Debugging API" tagged @lucene.internal (InfoStream.java:24, :28), and so is JavaLoggingInfoStream itself (JavaLoggingInfoStream.java:30); nothing promises that IndexWriter stays consistent when its logger throws; a well-behaved java.util.logging handler reports through ErrorManager instead of throwing; the OutOfMemoryError form relies on continuing after an Error, which Lucene's own tests never do; and the duplicates need the application to catch a logging exception and keep merging. Two independent reviews from other model families (both reading the code only) rated this argument moderate.

Why it fails: setInfoStream is public and not internal, and no javadoc, CHANGES.txt or MIGRATE.md text says message() must not throw. Lucene points users at JavaLoggingInfoStream despite its tag: MIGRATE.md:1162 names it, and on #14731 Uwe Schindler pointed a user to it as the adapter Lucene ships for java.util.logging (2025-07-10). It passes a handler's exception straight through. Lucene's own tests throw from InfoStream.message and require a consistent index. The repro's exception is an ordinary RuntimeException, after which the writer stays open and accepts further calls. An OutOfMemoryError while Lucene builds its own log string cannot be documented away. The fix is a statement reorder. Verdict: not intended, a defect.

Suggested fix

#

Recommended Log and estimate first, then register with no callback or I/O in between (validated)

Do the logging and the size estimate first, then mark the segments, queue the merge and set registerDone, with no callback or I/O in between (+16/-20 lines in registerMerge). The test passes with assertions on and off, and so do the 1,398 tests of the org.apache.lucene.index.* selection and :lucene:core:check.

ensureValidMerge(merge);
// log and estimate before changing any state: both may throw
if (infoStream.isEnabled("IW")) {
  ... the three messages, unchanged; the count is pendingMerges.size() + 1 ...
}
addEstimatedBytesToMerge(merge);
merge.mergeGen = mergeGen;
merge.isExternal = isExternal;
mergingSegments.addAll(merge.segments);
pendingMerges.add(merge);
merge.registerDone = true;

Trade-offs

  • An IOException from the size estimate (the trigger in #9738) now leaves nothing registered. Today it leaves a queued merge with its segments marked but registerDone == false: no duplication, but an earlier sweep on main e1faeba08bde showed that it trips an assertion with assertions on ("we aborted all merges but still have merging segments", 27 of 27 faults); the reorder covers it (by reading).
  • One isEnabled("IW") check now guards the three log statements instead of one check per statement.
  • It removes every callback and I/O call from the window, but it is not all or nothing against every Throwable: an Error inside mergingSegments.addAll or pendingMerges.add could still interrupt it. Because the segments are marked first, that leaves at worst marked segments with no queued merge (unavailable to other merges until the writer closes), never a queued merge with free segments (by reading).
  • Statements only move inside a synchronized method; no benchmark was run.

Undo the registration when anything after the add throws

#

Keep the order; wrap everything after pendingMerges.add in try/catch (Throwable) and, on a throw, remove the merge from pendingMerges and its segments from mergingSegments before rethrowing (safe, because the conflict check proved none of them was marked before).

Trade-offs

Keeps the current log order and count exactly; more code and a catch of Throwable around logging. Not run.

Document that InfoStream.message must not throw

#

A javadoc note on InfoStream and IndexWriterConfig.setInfoStream.

Trade-offs

Does not cover an OutOfMemoryError while a message is built, does nothing for the IOException from the size estimate, and contradicts Lucene's own tests that throw from InfoStream.message. Not enough on its own.

Treat any throw from merge registration as tragic

#

Close the writer when registerMerge throws.

Trade-offs

Avoids the bad state but turns a logging hiccup into a lost writer and its uncommitted changes, against the #9738 discussion that maybeMerge exceptions need not be tragic. Not recommended.

Downstream note

#

A service that bridges IndexWriter logging into its own logging system inherits this: a logging failure during a merge request can later commit duplicated documents to its index.

How it was found

#

A bounded-exhaustive single-fault sweep of the real lucene-core jar: one OutOfMemoryError at the k-th InfoStream.message call, for every k up to 850, while the script keeps using the writer. It flagged the three registerMerge log lines; reading registerMerge gave the mechanism, which was reduced to one JUnit test.

The method in full97 words

Method: semi-formal (bounded-exhaustive fault injection, then code reading), 2026-10-28, on main a9779ef3c193.

  • The three registerMerge log sites were the ones where the writer stayed open with no tragic exception when reached from forceMergeDeletes and forceMerge, and the next merge call then failed: an AssertionError with assertions on, a CorruptIndexException with assertions off.
  • Reading registerMerge gave the half-registration mechanism: the merge is queued before its segments are marked. It was reduced to a public-API JUnit whose assertions-off run commits duplicated documents, and for this doc to the one-method, one-segment test above, through the shipped JavaLoggingInfoStream.

LFV-842, snapshot of 2026-11-04

Registry title
If the IndexWriter InfoStream throws inside registerMerge, the merge stays queued but its segments are not marked as merging, so the next merge selection picks the same segments again and, with assertions disabled, forceMerge commits duplicated documents (every release since 3.2.0)
Area
index / IndexWriter merge registration (registerMerge, pendingMerges, mergingSegments)
Priority
Medium, rank 110: It commits duplicated documents durably on default -da in every release since 3.2.0, which keeps it in Medium even though its trigger is the same rare opt-in InfoStream throw as the Low hangs LFV-844 and LFV-846, so it closes the fault-driven writer-session cluster LFV-430 to LFV-635, above the loud LFV-013 race.
Impact class
data corruption
Impact note
Applications that enable IndexWriter's InfoStream for 'IW' and whose logging backend throws (for example a failing java.util.logging handler behind the shipped JavaLoggingInfoStream), or that hit an OutOfMemoryError while registerMerge builds a log message, and then keep using the still-open writer: with assertions disabled (production) the next merge over the same segments commits every live document of those segments twice (16 live documents from 10, or 20 from 14), with the default ConcurrentMergeScheduler the outcome depends on timing (duplicates in 5 of 20 and 2 of 10 iterations, otherwise a NullPointerException that closes the writer and loses its uncommitted changes), and with -ea the next merge fails an assertion; no scale is needed, and every release from 3.2.0 to 10.6.0 and main is affected [exec on 17 releases and main; the releases in between by reading].
Summary
You enable IndexWriter's InfoStream, and the logging call throws once (an exception from the logging backend, or an OutOfMemoryError) while forceMergeDeletes() registers its merge; forceMergeDeletes rethrows and the writer stays open, so you expect the index to stay as it was: a following forceMerge(1) and commit should leave the same 10 live documents. But registerMerge had already queued the merge and had not yet marked its segments as merging, so forceMerge(1) selects the same segments again, both merges run, and with -da the committed index holds 16 live documents with id:1 twice. With -ea the next merge fails 'assert merge.registerDone' in IndexWriter._mergeInit instead.
