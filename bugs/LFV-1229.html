IndexWriter#addBatch rejects an untokenized column with positions that addDocument accepts

An untokenized field type with positions indexes fine through addDocument, but the experimental IndexWriter#addBatch rejects the same type and value in a BinaryColumn or DictionaryColumn with an error asking for a TokenStream that no untokenized column can supply. 10.5.0 to 10.6.0 and main.

The finding in 30 seconds

#

An untokenized value is one token: Field indexes it through a one-token stream, so it can carry a position. The column adapter instead sends every untokenized value down Lucene's single-term BINARY path, which has no positions and throws when the type asks for them.

  1. You define an untokenized FieldType that indexes positions (DOCS_AND_FREQS_AND_POSITIONS). addDocument(new Field("f", new BytesRef("x"), type)) indexes term x in doc 0, freq 1, position 0.
  2. You index the same value with addBatch: a one-document batch with a BinaryColumn "f" of that type and value x. Validation accepts the column.
  3. You expect the same index: term x, doc 0, position 0.
  4. Instead addBatch throws IllegalArgumentException: Fields that are tokenized or index proximity data must produce a non-null TokenStream, but f did not. Because the type is untokenized, the column adapter took the single-term path, which cannot store positions.
  5. Same for a DictionaryColumn and for term vectors with positions. The batch adds no documents and the writer stays open.

Who is affected

#

Only users of the experimental addBatch column API (10.5.0 and later) whose untokenized, keyword-style field indexes positions or term-vector positions. That schema cannot be indexed by column at all. The failure is loud, on the first batch: the writer stays open and the batch adds no visible documents.

Mechanism, terms and numbers417 words

IndexWriter#addBatch (experimental, first in 10.5.0) rejects an untokenized BinaryColumn or DictionaryColumn whose field type indexes positions or term-vector positions. The internal BinaryColumnAdapter picks the single-term InvertableType.BINARY path from tokenized() alone (ColumnFieldAdapter.java:249 on main) and supplies no TokenStream; IndexingChain.invertTerm refuses proximity data on that path (IndexingChain.java:2136-2145). addDocument with new Field(name, BytesRef, sameType) indexes the value as one token at position 0, because Field always wraps an untokenized value in a single-token stream. ColumnValidation accepts the type first, and TokenStreamColumn refuses untokenized types, so no column kind can index it.

Terms

#
  • Untokenized field: the whole value is one term, as in StringField. A FieldType may still ask for positions (DOCS_AND_FREQS_AND_POSITIONS) or term vectors with positions; Field(String, BytesRef, IndexableFieldType) accepts that and rejects only offsets and tokenized types (Field.java:209-215 on main).
  • Invertable type: how the indexing chain turns a field into terms. TOKEN_STREAM reads a TokenStream; BINARY takes binaryValue() as a single term with no positions (InvertableType.java:25-32). Field is always TOKEN_STREAM and wraps an untokenized BytesRef in a one-token BinaryTokenStream (Field.java:459-487).
  • Column batch API: IndexWriter#addBatch(ColumnBatch) (@lucene.experimental, 10.5.0) indexes columns instead of documents. package-info.java:35-43 lists term inversion among the uses of both BinaryColumn and DictionaryColumn, and the DictionaryColumn javadoc says "term inversion (tokenized or untokenized)" (DictionaryColumn.java:27-32). Internally each becomes a BinaryColumnAdapter (ColumnFieldAdapter.java:51-62), a Field subclass.

  1. IndexingChain.processBatch validates each column (:730-737). validateBinaryColumn and validateDictionaryColumn (ColumnValidation.java:172-249) never look at positions or term-vector options, so the type passes.
  2. The field's options are registered (initAndValidateFields, :784), then the row pass (:793) creates the adapter. For an untokenized type it answers BINARY (:249).

Exposure and likelihood146 words
  • Who is hit. Applications that index through IndexWriter#addBatch with a BinaryColumn or DictionaryColumn whose untokenized type has DOCS_AND_FREQS_AND_POSITIONS or term vectors with positions, for example a schema they already index with addDocument.
  • Default vs opt-in. Opt-in: the column API is experimental, and most untokenized fields (StringField, KeywordField) index DOCS or DOCS_AND_FREQS, which work.
  • Effect. One IllegalArgumentException from the row pass, after validation accepted the column. The message points at a TokenStream the user cannot supply. The writer stays open and the failed batch adds no visible documents (a reader opened afterwards in the probe shows maxDoc=0). As after any non-aborting failure (a failed addDocument too), the batch's reserved doc IDs stay buffered as deleted docs and no flush is triggered (DocumentsWriterPerThread.java:339-354, :392-415).
  • Scale. None: one document, one value, single thread, with assertions on and off.
  • Likelihood: rare.

Why it looks unintended

#
  • The column package docs list term inversion for BinaryColumn and DictionaryColumn (the DictionaryColumn javadoc adds "tokenized or untokenized"), and nothing discloses a limit on their index options.
  • No column kind accepts this legal type: TokenStreamColumn requires tokenized() == true, so the requested TokenStream cannot be supplied.
  • ColumnValidation rejects other unsupported combinations up front, but not this one.
The full argument170 words
  • The contract. DictionaryColumn.java:27-32: "... for stored binary or string fields, and for term inversion (tokenized or untokenized)." package-info.java:35-43 lists "term inversion" for BinaryColumn and DictionaryColumn; BinaryColumn.java:23-29: "stored/indexed binary or text fields". No javadoc, test, CHANGES or MIGRATE entry restricts the index options of untokenized columns.
  • No column keeps the type untokenized. TokenStreamColumn rejects untokenized types (TokenStreamColumn.java:44-56; TestColumnBatchTokenStreamColumn.testConstructorRejectsNonTokenized); the workaround works only by changing the type to tokenized.
  • Validation is the place for rejections. ColumnValidation already rejects, for example, a DictionaryColumn with BINARY doc values with a specific message (ColumnValidation.java:216-222).
  • Parity is a stated goal. #16224 (Tim-Brooks): without TokenStreamColumn "anyone using user provided token streams would need to fall back to the addDocument path"; #16708 (mayya-sharipova) fixed that "addBatch accepted vectors that addDocument would reject".
  • History. The adapter line is unchanged since #15990 created the column API; its description, 7 comments, 11 reviews and 20 inline review comments never discuss positions on untokenized columns. #16101 lists "inverted tokenized/untokenized fields" among its tested uses.
The devil's-advocate check136 words

The strongest case: InvertableType.BINARY deliberately carries no proximity data, and TestDocumentWriter.testIndexBinaryValueWithoutTokenStream (TestDocumentWriter.java:435, from #12139) asserts that a BINARY field with positions or term-vector positions is illegal ("cannot index positions on a binary field"). Untokenized columns could be meant as plain keywords, with positions left to TokenStreamColumn, and the API is experimental.

Why it fails: that test covers a field that declares BINARY itself; here the user never chooses BINARY, the internal adapter does, from tokenized() alone. Nothing documents a keyword-only reading, and TokenStreamColumn refuses untokenized types, so the workaround (a one-token TokenStreamColumn) means changing the type to tokenized. Even if maintainers decide the type is unsupported, the error belongs in ColumnValidation with a message that says so (fix B). The cross-model reviewer (OpenAI GPT-5.6) rated this defence moderate and not convincing.

Suggested fix

#

Recommended Invert untokenized proximity types through Field's single-token stream

Make BinaryColumnAdapter invert an untokenized type that indexes positions or term-vector proximity through Field's single-token stream, as addDocument does. Validated: the repro passes with assertions on and off, and 182 column-batch and TestDocumentWriter tests pass. Alternative: reject the type up front in ColumnValidation with a clear message.

All options and trade-offs2 options · 569 words

Validated with gradle in a clean scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-03). The suites: the six TestColumnBatch* classes in org.apache.lucene.document.column, TestColumnBatchIndexing and TestDocumentWriter (182 tests).

Workaround until fixed: a TokenStreamColumn with the same index options but tokenized=true, whose stream emits exactly the value's bytes as one token, gives the same index options, norms setting and postings (doc 0, freq 1, position 0; executed). A TokenStreamColumn is inverted-only (TokenStreamColumn.java:29-33): a stored value, doc values or points go in a separate column with the same name. For a multi-valued document it matches the Field(BytesRef) row path only while the analyzer's position increment gap is 0, the default (read from code, not executed).

Invert untokenized proximity types through Field's single-token stream (validated by the checks) (recommended)

#

In BinaryColumnAdapter, compute once whether the type is untokenized but indexes positions or term-vector positions, offsets or payloads (the condition invertTerm checks). Then invertableType() returns TOKEN_STREAM and tokenStream() delegates to Field.tokenStream, which wraps binaryValue() in its one-token stream. DOCS / DOCS_AND_FREQS columns keep the BINARY path.

Trade-offs

About 15 lines in one internal class; addBatch then indexes what addDocument indexes. It also sends offsets types down the single-token stream, while Field(String, BytesRef, ...) rejects offsets; maintainers may prefer to leave offsets out here and reject them in ColumnValidation with Field's message. Not tested with offsets, nor for a DictionaryColumn, term-vector positions or a DENSE column. Using subsumes, not compareTo, keeps DOCS_AND_CUSTOM_FREQS (which sorts after the positional options) on the BINARY path (IndexOptions.java:36-73).

Reject the type up front in ColumnValidation (validated by the checks)

#

In validateBinaryColumn and validateDictionaryColumn, throw when the type is untokenized and indexes positions or term-vector positions, offsets or payloads, with a message that names the column and the alternative, e.g. BinaryColumn "f" is untokenized and cannot index positions, offsets or payloads (indexOptions=DOCS_AND_FREQS_AND_POSITIONS); use a tokenized TokenStreamColumn or addDocument.

Trade-offs

Small, and the error comes from validation, before the field's options are registered, with a message that says what to do. But addBatch still cannot index a type addDocument accepts, so the column javadocs would need to say so. It also rejects such a column when it holds no values, which addBatch accepts today.

Downstream note

#

Relevant downstream only to products that expose addBatch with user-defined field types; the trigger is the field type (configuration), once its column holds a value; no particular document value or query causes it.

How it was found

#

A proof-obligation audit of the column batch API's term-inversion contract compared BinaryColumnAdapter with Field for every field type the column docs allow, and found that untokenized types with positions are routed to a path that refuses them. A public-API JUnit test then witnessed it on main.

The method in full96 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: for every field type a BinaryColumn or DictionaryColumn accepts for term inversion, addBatch inverts the value as Field with the same type would. BinaryColumnAdapter.invertableType decides from tokenized() alone, while invertTerm also depends on positions and term-vector options, so the obligation fails for untokenized proximity types.
  • A one-test JUnit witnessed it on main with assertions on and off. An independent reproducer, an executed review by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier each wrote and ran their own test.
