IndexWriter opened from an older reader's IndexCommit can reuse a newer commit's version, so readers on that commit report isCurrent() == true

A writer opened with setIndexCommit(reader.getIndexCommit()) on an older commit counts versions from that reader, not the newest commit, so it can repeat a newer commit's version (10 and 10 in the repro). A reader on that commit then reports isCurrent() == true and a SearcherManager still on it does not refresh; since 5.3.0.

The finding in 30 seconds

#

Every commit stores a version number, and a plain reader decides whether it is stale by comparing its version with the newest commit's. A writer opened on a reader's commit point copies that reader's version and ignores newer commits, so its commits can repeat a version that a newer commit already has.

Background: commit versions and going back to an old commit

#
  1. Every commit (segments_N) records a version that grows as the index changes. A reader from DirectoryReader.open(dir) treats "the newest commit has my version" as "nothing changed": that is isCurrent(), and openIfChanged and SearcherManager refreshes rely on it.
  2. With a deletion policy that keeps old commits (NoDeletionPolicy, a SnapshotDeletionPolicy snapshot), you can open an IndexWriter on an old commit with IndexWriterConfig#setIndexCommit and continue from there: a rollback.
  3. The commit point can come from DirectoryReader.listCommits(dir) or from an open reader's getIndexCommit(), which lets the writer reuse that reader. Since 5.3.0 the two take different paths in the IndexWriter constructor.

The finding, step by step

#
  1. Keep every commit (NoDeletionPolicy). Commit 1 document (segments_1, version 4) and open reader older on it; add and commit 2 more, one at a time (segments_3: 3 documents, version 10), and open reader newer.
  2. Go back: open a writer with setIndexCommit(older.getIndexCommit()) and commit twice. You expect newer.isCurrent() to turn false: its javadoc says it "checks if any further commits ... have occurred in the directory".
  3. Instead the writer counts on from older's version 4, not from the newest commit's 10. Its commits get versions 8, then 10: segments_5 holds 1 document but carries the same version as segments_3.
  4. isCurrent() compares only versions, so newer.isCurrent() returns true, openIfChanged(newer) returns null and a SearcherManager refreshed only after both commits keeps serving the 3 old documents. The next commit (version 12) ends it.
  5. Control: the same commit taken from DirectoryReader.listCommits keeps the versions above 10, as this very call did in 5.2.1. The index on disk is correct throughout.

Who is affected

#

Applications that roll back through an open reader's commit point (setIndexCommit(reader.getIndexCommit()), Expert) while a reader or SearcherManager stays on a newer commit. Stale only when a new commit hits that commit's version exactly (14 of 96 snapshot-rollback histories) and until the next commit; deleted documents stay findable meanwhile. The index on disk is correct.

Mechanism, terms and numbers754 words

IndexWriterConfig#setIndexCommit can open a writer on an older commit that a deletion policy kept, and its javadoc invites passing an open reader's DirectoryReader#getIndexCommit. Since LUCENE-6524 (5.3.0) such a reader-backed commit takes its own branch of the IndexWriter constructor, which clones the reader's SegmentInfos, version included, and never reads the newest commit on disk; the branch taken for the same commit from DirectoryReader.listCommits keeps the newest commit's version "to preserve write-once. This is important if readers are open against the future commit points." So the new writer's versions restart below commits already in the directory, and one of them can equal the version of a newer commit with different content: in the repro segments_3 (3 documents) and segments_5 (1 document) are both version 10. A reader opened on segments_3 compares only versions, so it reports isCurrent() == true, openIfChanged returns null, a refreshed SearcherManager keeps serving the superseded commit (a deleted and committed document stays findable) and SearcherLifetimeManager.record throws IllegalArgumentException, until a later commit moves the version on. The index on disk is correct. It needs the Expert rollback through a reader's commit point while another reader stays on a newer commit, and an exact version match that depends on operation counts. An 11-line fix that raises the version to the newest commit's passes the repro and the whole core test suite.

Step by step, on the repro

#
  1. Which branch runs. DirectoryReader#getIndexCommit returns a commit that carries the reader (StandardDirectoryReader.java:570-574, getReader() at :644-646). DirectoryReader.listCommits builds the same kind of commit with no reader (DirectoryReader.java:456, :481), so its getReader() returns null; a SnapshotDeletionPolicy.snapshot() commit inherits getReader() == null from IndexCommit (IndexCommit.java:112-118). Both take the commit-point branch.
  2. The reader branch copies the old version. IndexWriter.java:1050 clones the reader's SegmentInfos, so the writer starts at segments_1's version 4. It raises the version only from the reader's own writer (:1062-1071), and only for an NRT reader; a plain reader has none. It never reads segments_3 (version 10).
  3. The writer counts up from there. The constructor adds 2 at open (:1192-1196, "we always assume we are carrying over incoming changes"), and each commit-data commit adds 2 more in the repro:

  1. File names never collide, versions do. IndexFileDeleter.inflateGens (IndexFileDeleter.java:257) raises the generation from the files in the directory, so the new commits are segments_4 and segments_5; nothing repairs the version.
  2. isCurrent() compares only versions. For a reader without a live writer, StandardDirectoryReader.java:529-540 reads the newest commit and returns sis.getVersion() == segmentInfos.getVersion(): 10 == 10. openIfChanged returns null when isCurrent() (:477-482), so SearcherManager.refreshIfNeeded (SearcherManager.java:200) keeps the old searcher, and SearcherLifetimeManager.record, which keys searchers by version, throws IllegalArgumentException for a searcher on segments_5 (SearcherLifetimeManager.java:146-161).

Not every history collides: adding one document instead of commit data gives version 9 and no stale reader. The version restarts from the older reader's on every such open; whether a commit then lands below, exactly on, or above a newer commit's version depends on the operation counts, and only the exact match makes a reader stale.

Exposure and likelihood332 words
  • Who is hit. Applications that go back to an older commit through a reader's commit point, new IndexWriter(dir, new IndexWriterConfig().setIndexCommit(reader.getIndexCommit())), an Expert path the setIndexCommit javadoc documents, while a reader or SearcherManager opened on the directory is still on a newer commit. The older commit must still be on disk, so a deletion policy has to keep it: NoDeletionPolicy, a custom policy, or a SnapshotDeletionPolicy snapshot. The reader whose commit is passed may be a plain reader or an NRT reader whose writer closed before a later writer session committed.
  • A realistic flow. A writer with SnapshotDeletionPolicy snapshots commit 1 (document a) and opens a reader on the snapshot, then commits b and c; a SearcherManager(dir, null) serves segments_3. A rollback writer on the default deletion policy, opened with setIndexCommit(snapReader.getIndexCommit()), adds d and commits. After maybeRefreshBlocking() the SearcherManager still serves segments_3 (version 10, 3 documents) although the only commit on disk is segments_4 (version 10, 2 documents). Run on main 645d4fe14a20 and, over 20 seeds, on a9779ef3c193.
  • How often. It needs an exact version match, which depends on operation counts. An independent enumeration of 96 single-commit rollback histories (snapshot, SearcherManager, default policy on the rollback writer) left the SearcherManager stale in 14 through reader.getIndexCommit() and in 0 through the snapshot commit itself. No report was found in the 11 years since 5.3.0.
  • What goes wrong. Silent and transient: isCurrent() true, openIfChanged null, a refreshed SearcherManager keeps serving the superseded commit, so a document that was deleted and committed is still found, until a later commit moves the version on (the follow-up's stale-searcher probe, main a9779ef3c193, 10.5.2 and 9.12.3). SearcherLifetimeManager.record throws IllegalArgumentException when two commits share a version.
  • What does not go wrong. The index on disk is correct: CheckIndex is clean and a freshly opened reader sees the newest commit. Not the default configuration. Assertions on or off make no difference.
  • Impact class: silent wrong results; priority low (Expert path, rare, transient).

Why it looks unintended

#
  • isCurrent() javadoc: a reader from open "checks if any further commits ... have occurred in the directory"; two did.
  • The other branch of the same constructor keeps the newest version "to preserve write-once", because "readers are open against the future commit points".
  • The same commit from listCommits works, as did this very call in 5.2.1.
The full argument322 words
  • Contract. DirectoryReader.java:628-629 (isCurrent): "If this reader was created by calling #open, then this method checks if any further commits (see IndexWriter#commit) have occurred in the directory." :637-638: "if this returns false, you should call #openIfChanged to get a new reader that sees the changes." :620-621 (getVersion): "This version is advanced every time a change is made with IndexWriter."
  • The API invites the call. IndexWriterConfig.java:235-237: "Expert: allows to open a certain commit point. ... This can also be used to open IndexWriter from a near-real-time reader, if you pass the reader's DirectoryReader#getIndexCommit." Upstream TestIndexWriterFromReader#testAfterCommitThenIndexKeepCommits opens a writer from a reader that is behind the latest commit; that test class never checks isCurrent() of a reader left on the newer commit.
  • Both branches keep the version on purpose. The commit-point branch keeps the version "to preserve write-once" (IndexWriter.java:1088-1092; SegmentInfos.java:1084-1086: replace "keeps generation, version, counter so that future commits remain write once"). The reader branch itself updates the metadata "so we remain write-once" (IndexWriter.java:1067-1068), but only from the reader's own writer.
  • Same commit, two outcomes. The same commit from listCommits gives correct versions, and the same user call did in 5.2.1. Every other open path (create over an existing index, append, a listCommits commit) keeps the version at or above the newest commit's.
  • Precedent. CHANGES.txt:18287-18288, LUCENE-2513 (2010): "when opening writable IndexReader on a not-current commit, do not overwrite \"future\" commits." There a writable IndexReader on an older commit overwrote a future commit's segments_N file (#3587): the file-level form of the same rule; here the file names are safe and the version is reused. Michael McCandless in LUCENE-3607 (#4681): "the version is still comparable across IRs opened at different times against the same index".
  • History: a side effect. LUCENE-6524 (#7582) added the reader branch so the existing call could reuse the open reader; its 16 comments never mention the version, write-once or isCurrent.
The devil's-advocate check188 words

Strongest case for "intended": setIndexCommit is Expert and getIndexCommit is @lucene.experimental, and Lucene never documents commit versions as strictly increasing or unique (LUCENE-2805 only says the version moves on every change, not on every commit). Going back to an old commit starts a new branch of history, and versions across branches are not comparable.

Why it fails:

  1. On main every commit that is written gets a higher version than the writer's previous one (IndexWriter.java:3828-3835, from LUCENE-6523, 2015), and a commit without changes is not written at all (:5934-5936). Here two commits with different content, segments_3 (3 documents) and segments_5 (1 document), share one version, and a reader that the javadoc says detects "any further commits" does not.
  2. Lucene already treats going back as one history in this directory: the commit-point branch keeps the newest version for exactly this reason, and the result must not depend on whether the IndexCommit object came from listCommits or from a reader.
  3. Expert lowers the reach, not the correctness bar; no javadoc, CHANGES or MIGRATE entry, test or issue found documents a weaker guarantee for a reader's commit.

Suggested fix

#

Recommended A. In the reader branch, never go below the newest commit's version (11 lines)

In the reader branch of the IndexWriter constructor, raise the version to the newest commit's before the writer starts, as the commit-point branch already does (11 lines in IndexWriter.java). The repro and 15 related suites pass (294 tests, assertions on and off), as do all 8,898 core tests.

All options and trade-offs3 options · 661 words

One code fix was run; A is recommended. Workaround for users today: pass the matching commit from DirectoryReader.listCommits(dir) (same segments file name as reader.getIndexCommit()) instead of the reader's commit; it takes the commit-point branch, which keeps the versions right. This works for plain readers of a commit; an NRT reader's uncommitted changes are in no listed commit. The writer then opens its own segment readers instead of sharing the held reader's (ReaderPool.java:90-112 pre-enrolls them only for a reader-backed commit).

Trade-offs

It fixes new opens only; commits that already share a version keep it. It compares with the newest commit only, as the commit-point branch does. On an index where an affected release already wrote a newest commit with a lower version than an older one (segments_4 version 8 after segments_3 version 10), a later collision with an older commit's version is not ruled out: through the commit-point branch, which A does not change (a plain commit() right after opening segments_1 from listCommits writes segments_5 version 10, and a reader on segments_3 reports isCurrent() == true, stock and with A), or through the reader branch when the older commit's version is more than 2 above the newest's. In this example the reader branch with A commits at 11 or higher. B, applied to both branches, closes that.

B. Use the highest version over all retained commits

#

Read every segments_N in the listing (or reuse the commits the file deleter loads at init) and take the maximum. Raised by the cross-model root-cause reviewer.

Trade-offs

Also covers indexes already made non-monotonic by an affected release. Costs one read per retained commit at open (many with NoDeletionPolicy), and the commit-point branch would need the same change to stay consistent. Not run.

C. Make isCurrent() compare more than the version

#

For example also the commit generation.

Trade-offs

Hides the isCurrent/openIfChanged symptom but leaves two commits with different content and one version on disk, which SearcherLifetimeManager (keyed by version) still trips on. The hunt's validated isCurrent patch for the sibling LFV-012 leaves all 3 failures of the hunt's class. Not recommended alone.

Downstream note

#

Elasticsearch and OpenSearch pass listCommits commits or their own IndexCommit subclasses to setIndexCommit, which take the unaffected path, and Solr's main code does not call it (code reading of their default branches, not tested).

How it was found

#

Semi-formal: while modelling "open a writer from a reader's commit" for a bounded-exhaustive harness of reader reopen behaviour (every sequence of up to 4 operations, 32 configurations, stock jars), the finder read that this path ignores the newest commit's version. The harness then flagged it on its own, and it was reduced to one JUnit test.

The method in full158 words
  • Method (semi-formal): bounded-exhaustive translation validation in a hunt unit on reopen equivalence. Every sequence of up to k operations over a 22-28-operation alphabet (adds, deletes, doc-values and soft updates, addIndexes, flushes, merges, commits, rollbacks, writer reopens, writers from a reader's commit, NRT reopens) ran on the stock jars in 32 configurations, with oracles for reopen equivalence, isCurrent soundness and write-once commit versions.
  • Signal. The hypothesis came from reading the constructor while modelling the operation "writer from a reader's commit"; the harness then witnessed it independently at k=4 (308 sequences per configuration group; shortest: force-merge, commit, writer from reader commit, commit, giving segments_2 and segments_3 both version 9).
  • Attribution. With this fix sketch shadowed in, together with other bugs' sketches, the "commit versions not increasing" signature disappeared in all 32 configurations; with only the other sketches it remained.
  • Reduction. The finder wrote a public-API JUnit (4 tests, one control); it was later minimized to the one test above.

History

#

Introduced in 5.3.0 by LUCENE-6524 (2015), which sent a reader's commit point down a new constructor branch that copies the reader's version; 5.2.1 runs the same call correctly. Every release run from 5.3.0 to 10.6.0, and main, is affected; unchanged upstream.

Versions tested6 rows

Introduced by LUCENE-6524 "Create an IndexWriter from an already opened NRT or non-NRT reader" (#7582, Michael McCandless): 2d0ac9bb7f2 on trunk (2015-06-28, first released in 6.0.0) and the branch_5x backport 7ab3ca7d608 (first released in 5.3.0). It made the reader's IndexCommit carry the reader and added the reader branch, so the existing call setIndexCommit(reader.getIndexCommit()) left the version-keeping commit-point branch. Later commits only reformatted the branch or changed its messages and checks. 8.8.2-8.11.3 are counted by inference only. Unchanged on upstream main 2f424fd428da and in 10.6.0.

LFV-591, snapshot of 2026-11-02

Registry title
IndexWriter opened from an older reader's IndexCommit takes SegmentInfos.version from that reader, not from the newest commit, so its commits can reuse the version of a newer commit and a reader still open on that commit reports isCurrent()=true and openIfChanged returns null
Area
index / IndexWriter construction from a reader's IndexCommit (SegmentInfos.version; DirectoryReader.isCurrent and openIfChanged)
Priority
Low, rank 760: A stale reader reports isCurrent() as true after an exact version collision, but only on the Expert reader-IndexCommit rollback path, and it clears at the next change while the index on disk stays correct.
Impact class
silent wrong results
Impact note
Hits only applications that go back to an older commit by opening an IndexWriter with the Expert IndexWriterConfig#setIndexCommit(reader.getIndexCommit()) on a reader of a commit that a deletion policy or snapshot still keeps (NoDeletionPolicy, or a SnapshotDeletionPolicy snapshot followed by a rollback writer on the default policy), while a reader, SearcherManager or SearcherLifetimeManager still holds a newer commit; no scale is needed, but the visible symptom needs one of the new writer's commits to get exactly the newer commit's version, which depends on operation counts (it did for commit-data-only commits, for one added document and for some delete and update histories, but not for every history): then isCurrent() stays true, openIfChanged returns null and a refreshed SearcherManager keeps serving the superseded commit (a committed delete or a restricting update stays unseen) until a later change moves the version on, and SearcherLifetimeManager.record throws IllegalArgumentException; the index on disk is correct (CheckIndex clean, a fresh reader sees the latest commit). The same commit taken from DirectoryReader.listCommits, or any IndexCommit not obtained from a reader (what the Elasticsearch and OpenSearch main code pass; Solr's main code has no setIndexCommit call; read, not tested), takes the other constructor branch and is not affected.
Summary
You keep an older commit (for example with NoDeletionPolicy or a snapshot), open a reader on it, and later go back to it by opening a new IndexWriter with setIndexCommit(thatReader.getIndexCommit()) and committing, while another reader is still open on a newer commit. You expect that reader to notice the new commits (isCurrent() false, openIfChanged returning the latest commit), as it does when the same commit is taken from DirectoryReader.listCommits. Instead the writer restarts SegmentInfos.version from the old reader instead of from the newest commit, so one of its commits can get exactly the newer commit's version (segments_3 holding [a, b, c] and segments_5 holding [a] are both version 10), and the stale reader reports isCurrent()=true, openIfChanged returns null and SearcherLifetimeManager.record throws IllegalArgumentException.
