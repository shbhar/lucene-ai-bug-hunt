SimpleNaiveBayesDocumentClassifier returns NaN for every class when one field value has no tokens

SimpleNaiveBayesDocumentClassifier averages each field value's log-likelihood over its tokens, so a value with no tokens (empty, stop words only, punctuation only) gives 0.0 / 0 = NaN for every class and assignClass returns null. The division is in every release tag checked since 6.0.0 (83 of 83).

The bug in 30 seconds

#

SimpleNaiveBayesDocumentClassifier (module lucene/classification) classifies a whole Document. For every class it adds, per value of each configured text field, a log prior plus the value's log-likelihood averaged over its tokens, then normalises the class scores into probabilities that sum to 1.

  1. Train SimpleNaiveBayesDocumentClassifier on three documents with text fields title and body (stock EnglishAnalyzer): apple / "sweet fruit" is fruit, pear / "green fruit" is fruit, car / "four wheels" is vehicle. Classify title "apple": fruit 0.762, vehicle 0.238.
  2. Add a body that carries no words: "", "To be or not to be" (all stop words) or "!!!". You expect fruit again, with probabilities that sum to 1.
  3. You get fruit = NaN and vehicle = NaN, and assignClass returns null. No exception, with assertions on or off; one empty body value next to five "sweet fruit" values does the same.
  4. Why: each value adds its log prior plus the sum of log P(word | class) divided by its token count, here 0.0 / 0 = NaN. It is added to every class, the normalisation spreads it, and NaN > max is never true.
  5. getClasses(doc, 1) then returns the first class name in term order: title "car" alone gives vehicle 0.556, but with an empty body it gives fruit (NaN). Skipping values with no tokens fixes it.

Who is affected

#

Users of the opt-in, @lucene.experimental lucene/classification module who classify documents with SimpleNaiveBayesDocumentClassifier. One value in any configured text field that analyzes to no tokens is enough: an empty value, stop words only, or punctuation only. No setting or scale is needed; empty values in training documents do not trigger it.

Mechanism, terms and numbers692 words

SimpleNaiveBayesDocumentClassifier scores each class by adding, for every value of every configured text field of the input Document, a log prior plus the value's log-likelihood, which is the sum of log P(w|c) over the value's tokens divided by the number of tokens. A value with no tokens, such as an empty TextField or one that the analyzer reduces to nothing (stop words only, punctuation only), gives 0.0 / 0 = NaN. That NaN is added to every class, the log-sum-exp normalisation turns every probability into NaN, assignClass returns null because NaN > maxscore is never true, and getClasses lists the classes in index term order. On three training documents, title "apple" gives fruit 0.762, and the same title with an empty, stop-word-only or punctuation-only body gives NaN for both classes and no class. It is silent, with assertions on or off, needs no setting, and the division is in all 83 release tags checked from 6.0.0 to 10.5.2 and in main; skipping values with no tokens fixes it.

Terms

#
  • Document classifier: new SimpleNaiveBayesDocumentClassifier(reader, query, classFieldName, field2analyzer, textFieldNames...) learns from the labelled documents of an index (the class is a term of classFieldName) and classifies an unseen Document: assignClass(doc) returns the best class with its score, getClasses(doc) all classes sorted by score.
  • Per-value score: the input document's values are analyzed with the field's analyzer (SimpleNaiveBayesDocumentClassifier.java:148-172). For every class and every value, the class score gains log prior + log-likelihood * boost (:121-131).
  • Log-likelihood: the sum of log P(w|c) over the value's tokens, divided by the number of tokens (:201-223). The original comment explains the division: "this is normalized because if not, long text fields will always be more important than short fields" (commit 71cea88773e, 2015).
  • Normalisation: a log-sum-exp turns the class scores into probabilities, "the values transforms to a 0-1 range" (SimpleNaiveBayesClassifier.java:292-318, comment at :294).

The bug

#
  1. An empty value, or one whose tokens are all removed by the analyzer, gives a token array of length 0 (an absent field gives an empty list, so the scoring loop never runs for it).
  2. calculateLogLikelihood then skips its loop and returns result / (tokenizedText.length) with result = 0.0 and length 0 (:222): 0.0 / 0 = NaN.
  3. assignNormClasses adds prior + NaN * boost = NaN to every class (:124-130).
  4. The normalisation takes the top score as smax and sums exp(score - smax): one NaN input makes every output NaN.
  5. assignClass keeps a result only if c.score() > maxscore, starting from -Double.MAX_VALUE (:80-87); with NaN this is never true, so it returns null.
  6. getClasses sorts with Double.compare (ClassificationResult.java:31-33), which treats all NaN values as equal, so the list stays in class-term order and getClasses(doc, n) returns the first n class names (SimpleNaiveBayesDocumentClassifier.java:98-103).

Exposure and likelihood271 words
  • Who is exposed. Applications that classify documents with SimpleNaiveBayesDocumentClassifier ("A simplistic Lucene based NaiveBayes classifier", @lucene.experimental). No other Lucene module uses the class.
  • What triggers it. One value of any configured text field in the document being classified that analyzes to no tokens: an empty description, a title made only of stop words ("To be or not to be" under EnglishAnalyzer), a value of punctuation or symbols. Three training documents and stock analyzers show it; one such value among many non-empty ones is enough.
  • What breaks. Every class probability is NaN and assignClass returns null, so a caller that reads assignClass(doc).assignedClass() throws a NullPointerException later, and a caller that takes getClasses(doc, 1) gets the first class name in index term order whatever the document says. Nothing fails inside Lucene, with assertions on or off.
  • Not affected. Classification after empty values in training documents (they enter only through index statistics; with 50 such training documents in the index a normal document still got finite scores and the right class), later calls on the same instance, the index, and the other classifiers on the same input. A different case, not this bug: if every training value of a configured text field is empty, so the field has no indexed terms, classifying a document with tokens in that field throws a NullPointerException (getTextTermFreqForClass, :233-236); the fact check reproduced it, and it has not been checked for prior reports.
  • How likely. Such values are ordinary in real data and trigger it every time, but the module has few users, and no report of it was found since 6.0.0 (2016).

Why it is a bug, not intended

#
  • assignClass returns "a ClassificationResult holding assigned class ... and score", with no null case; scores are normalised "to a 0-1 range".
  • The upstream test base asserts a non-null class and a score in [0, 1]; nothing requires values to have tokens.
  • On the same input the field-absent path, the text classifier and the k-NN document classifier stay finite.
The full argument239 words
  • Interface contract. DocumentClassifier.assignClass: "Assign a class (with score) to the given Document", returning "a ClassificationResult holding assigned class of type T and score" (DocumentClassifier.java:31-40). Only getClasses mentions null, "if the classifier can't make lists" (:48-49, :62-63). The contract is implied, not explicit: no javadoc promises a finite score, and the implementation already returns null when the index has no class terms at all.
  • Range. "normalization; the values transforms to a 0-1 range" (SimpleNaiveBayesClassifier.java:156, :294). NaN is not in that range.
  • The comment above the division describes a sum, log(P(d|c)) = log(P(w1|c))+...+log(P(wn|c)) (SimpleNaiveBayesDocumentClassifier.java:221), which is 0 for no tokens, not NaN.
  • Tests. DocumentClassificationTestBase.checkCorrectDocumentClassification asserts a non-null class (:61) and 0 <= score <= 1 (:67); ClassificationTestBase asserts a non-null result (:93, a line added on purpose by LUCENE-7981, #9030, 2017) and a non-null class (:95, older). No test uses an empty or stop-word-only value, and both fixes keep the whole module suite green.
  • History. The division is deliberate length normalisation from the commit that created the class (LUCENE-6631, 71cea88773e, 2015); the zero-length case was never handled. LUCENE-5698 (552c367c5d2, 2019) only inlined it. The issue's description and 21 comments do not mention empty values.
  • Legal input. No javadoc says field values must produce tokens; TextField and IndexWriter accept empty values, and stock analyzers remove stop words and punctuation.
The devil's-advocate check213 words

The strongest "intended" case (built by an intended-behaviour checker; a cross-model reviewer rated it weak): the class is @lucene.experimental and "simplistic", the division is deliberate length normalisation, and an average over zero tokens is undefined, so a caller who passes empty values gets what they asked for.

Why it fails: no javadoc, test, CHANGES or MIGRATE entry, issue or list thread states a "values must have tokens" precondition, and such values are legal input; one empty value cancels the evidence of every other field and value, and assignClass returns no class where its javadoc describes a result holding a class and a score; every sibling path (field absent, the text SimpleNaiveBayesClassifier, KNearestNeighborDocumentClassifier) returns a finite score and a class on the same input; @lucene.experimental allows API changes, not results outside the documented range. The independent reproduction, the cross-model review and the intended-behaviour check rated the bug real and the adjudication confirmed it with high confidence; the refute-lens cross-model review gave only a procedural not_real at low confidence (it could not run Java) while agreeing with the root cause. Not settled: whether an empty value should count like an absent one (fix A), keep its prior (fix B) or be rejected with an exception; a maintainer could reasonably choose any of these.

Suggested fix

#

Recommended Skip a value with no tokens (fix A)

Skip a field value that has no tokens in assignNormClasses (3 added lines), so it counts like an absent value: the repro then gives fruit 0.7619, the no-body result. The new test, the closest suites, the whole lucene/classification suite (assertions on and off) and check -x test pass with it.

           for (String[] fieldTokensArray : tokensArrays) {
+            if (fieldTokensArray.length == 0) {
+              continue; // no tokens, no evidence: treat the value as absent
+            }
             fieldScore +=
                 calculateLogPrior(term, docsWithClassSize)
All options and trade-offs3 options · 653 words

Two fixes were built and validated in a scratch worktree of a9779ef3c193. Ask upstream only for finite scores and a class; that an empty value scores like an absent one is fix A's design choice, not a documented promise. Other defensible choices, not built: reject a value with no tokens with an exception, document a precondition, or guard the normalisation against NaN.

Skip a value with no tokens (fix A) (validated by the checks) (recommended)

#

In assignNormClasses (SimpleNaiveBayesDocumentClassifier.java:124), continue when the value's token array is empty; an empty value then adds neither the prior nor a likelihood, exactly like an absent field. The hunt's own fix is the same change.

           for (String[] fieldTokensArray : tokensArrays) {
+            if (fieldTokensArray.length == 0) {
+              continue; // no tokens, no evidence: treat the value as absent
+            }
             fieldScore +=
                 calculateLogPrior(term, docsWithClassSize)

Trade-offs

  • An empty, stop-word-only or punctuation-only body gives the no-body result: fruit 0.7619 for title "apple", vehicle 0.5556 for title "car".
  • A document whose every value is empty gets uniform scores (0.5 / 0.5, assignClass = the first class), which is what a document with no fields at all already gets today; the text SimpleNaiveBayesClassifier returns the prior (0.6667) for empty input instead.

Return 0 from calculateLogLikelihood for zero tokens (fix B) (validated by the checks)

#

At the division (SimpleNaiveBayesDocumentClassifier.java:222), return 0 when the value has no tokens: the empty sum the comment above it describes.

     // log(P(d|c)) = log(P(w1|c))+...+log(P(wn|c))
+    if (tokenizedText.length == 0) {
+      return 0; // empty sum; dividing by the length would give 0.0 / 0 = NaN
+    }
     return result / (tokenizedText.length);

Trade-offs

  • Scores become finite, but the empty value still adds its class prior once more (the per-value prior at :125-126), which pulls the result towards the larger class: title "apple" plus an empty body gives fruit 0.8649 instead of 0.7619, and title "car" plus an empty body gives fruit 0.6154 while "car" alone gives vehicle 0.5556. So an empty value can still change the class.
  • The smallest change at the division; the adjudication noted upstream may prefer it if they see the per-value prior as intended (the audit lists both fixes as acceptable). With equal class priors it gives the same scores as fix A (arithmetic: the extra prior cancels in the normalisation; no run compared the two).

What the checks validated

  • Gradle, JDK 25: the same four suites (15 tests) and the whole :lucene:classification:test with assertions on and off (13 suites, 47 tests, 1 skipped, 0 failures each); check -x test passes; standalone: the new test 4 of 4, the finder's 2 of 2, the independent reproducer's 6 of 6.

Workaround until a fix ships

#

Drop field values that analyze to no tokens before classifying (run the field's analyzer, or at least skip empty strings), or treat NaN scores and a null from assignClass as "unclassified" instead of taking the first entry of getClasses. Lucene itself stores nothing wrong (the classifier only reads the index), so the index needs no repair; an application that stored the returned class (for example through Solr's update processor) may need to reclassify the affected documents.

Trade-offs

Needs one extra analysis pass per value, or a NaN check in the caller.

Downstream note

#

Solr's opt-in classification update processor with algorithm=bayes uses this classifier and writes the returned class names into incoming documents that do not already carry the class field (the default algorithm is k-NN), so there a document with one zero-token field value would get the first class name in term order (code reading only).

How it was found

#

An AI finder listed every division and logarithm in the naive-Bayes classifiers' raw scores and asked an SMT solver (Z3) which of them can produce NaN: the token-count division with zero tokens can, for every class. A bounded check of the real normalisation showed that one NaN spoils every class, and a public-API JUnit confirmed it on the stock jar.

The method in full174 words

Method: semi-formal (an SMT inventory plus a bounded check of the real code), then a JUnit test. A hunt unit (classification), 2026-10-26, main ea57360912ed.

  • The finder wrote a Z3 4.12.2 model (floating-point arithmetic with an uninterpreted log) of every division and log site in the classifiers' raw scores. Site S4, result / tokenizedText.length with length 0, was satisfiable (a NaN field score for every class); with length >= 1 it was proved finite. The site was read in the code while building the inventory, so this was a guided rather than a blind find.
  • 21 of 21 Z3 and cvc5 lemmas characterised normClassificationResults, and a bounded check of the real method over 1,082,400 special-value vectors (0 failures) showed that an output is NaN exactly when an input is NaN or +Inf, or every input is -Inf: one NaN poisons every class.
  • A public-API JUnit on the stock jar then witnessed it (fruit = NaN for an empty and a stop-word-only body), with assertions on and off, on main, 10.5.2 and 9.12.3.

Impact note
Applications that use the opt-in, @lucene.experimental lucene/classification module and classify documents with SimpleNaiveBayesDocumentClassifier are hit whenever one of the classifier's text fields in the document being classified has a value that analyzes to no tokens (an empty TextField value, or a stop-word-only or punctuation-only value under stock analyzers such as EnglishAnalyzer or StandardAnalyzer): with no error, every class score is NaN, assignClass returns null and getClasses(doc, n) returns classes in index term order, whatever the other fields say; no setting or scale is needed, every release from 6.0.0 to 10.5.2 is affected, and empty values in training documents do not trigger it.
Summary
You train SimpleNaiveBayesDocumentClassifier on the fields title and body and classify the document {title: 'apple', body: ''} (or a body such as 'the of and' that the analyzer reduces to stop words), expecting a class with a finite score, as the DocumentClassifier.assignClass javadoc and the '0-1 range' normalisation comment imply and as the same document without the body value gets (fruit). Instead getClasses returns fruit=NaN and vehicle=NaN, and assignClass returns null. calculateLogLikelihood returns result / tokenizedText.length, which is 0.0 / 0 = NaN for a value with no tokens; assignNormClasses adds that NaN to every class, and neither the log-sum-exp normalisation nor the 'score > maxscore' test in assignClass can recover from it.
