Sandbox DrillSidewaysFacetOrchestrator#collect(query, drillSideways, mainCollector) returns the internal MultiCollectorManager's Object[] instead of the main collector manager's result: with a TopScoreDocCollectorManager, assigning the result to TopDocs throws ClassCastException (run also with a hit-count and a sorted top-docs manager; an experimental class; 10.2.0 to 10.6.0, branch_11x and main)

Small, in an opt-in sandbox class marked experimental: DrillSidewaysFacetOrchestrator#collect(query, drillSideways, mainCollector) returns an Object[] holding the hits at element 0, so TopDocs hits = orchestrator.collect(...) throws ClassCastException in the caller's code. The facet results of the example are right, and reading element 0 of the value held as Object works.

The finding in 30 seconds

#

The limits: the class is in the releases from 10.2.0 on. The exception comes where the caller first uses the returned value as a TopDocs, Integer or TopFieldDocs: run with the stock top-docs, hit-count and sorted top-docs collector managers on 10.2.0, 10.6.0 and builds of branch_11x and main. No caller of the returned value was found in Lucene's own sources.

Background: three pieces

#
  1. DrillSideways runs a drill-down query and, for each dimension of the query, the "sideways" counts. Its search(query, drillDownManager, sidewaysManagers) returns a Result whose drillDownResult() is the result of the collector manager it was given.
  2. MultiCollectorManager runs several collector managers in one search. Its result is an Object[] with one element per manager.
  3. The sandbox facet utilities wrap both. DrillSidewaysFacetOrchestrator takes facet builders, runs the search and fills them. Its three-argument collect also takes a "main" collector manager for the hits.

The finding, step by step

#
  1. Index one document with the numeric doc-values field price = 1. Build a DrillDownQuery on price = 1 and a stock DrillSideways over an IndexSearcher.
  2. Ask the sandbox helper for hits and facets in one call: TopDocs hits = new DrillSidewaysFacetOrchestrator().addDrillSidewaysBuilder("price", new LongValueFacetBuilder("price")).collect(query, drillSideways, new TopScoreDocCollectorManager(1, 1));
  3. You expect a TopDocs with 1 hit. The method is declared <T> T collect(..., CollectorManager<..., T> mainCollector): its result type is that of the collector manager you pass. The sibling FacetOrchestrator#collect returns the hits (run).
  4. Instead the assignment throws java.lang.ClassCastException: class [Ljava.lang.Object; cannot be cast to class org.apache.lucene.search.TopDocs. It is thrown in your own code, after the search has finished, with assertions on and off.
  5. Why: collect puts your collector manager at index 0 of an internal MultiCollectorManager, whose result is an Object[], and returns that whole array through an unchecked cast (return (T) result.drillDownResult();). Here the array is Object[1] and holds the TopDocs with 1 hit. The facet result of the same call is right: price 1 has count 1.

Who is affected

#

An application that calls the three-argument collect of this opt-in, experimental sandbox helper and uses the result as a TopDocs, Integer or TopFieldDocs (the types run). It meets the exception when the call first runs. Nothing is written, and the returned value does not touch the facet results. Callers of the two-argument collect are not touched. Rare.

Mechanism, terms and numbers1,620 words

Small, and loud. DrillSidewaysFacetOrchestrator (org.apache.lucene.sandbox.facet.utils) is an opt-in utility of the sandbox module, tagged @lucene.experimental, in the releases from 10.2.0 on. It runs a drill-sideways search and fills facet builders. One of its two collect methods also takes a "main" collector manager, so that one call gives the hits and the facets. Only that method is concerned, and only when its returned value is used with the main collector manager's result type.

The method is declared <T> T collect(DrillDownQuery, DrillSideways, CollectorManager<? extends Collector, T> mainCollector) (DrillSidewaysFacetOrchestrator.java:67-71, lines at main f6e694652c3d). It wraps the main collector manager, at index 0, and the drill-down facet managers into one MultiCollectorManager (:73-74), runs DrillSideways#search with it (:88-89) and returns the whole Object[] of that manager through an unchecked cast (:92). The sibling FacetOrchestrator#collect returns element 0 (FacetOrchestrator.java:59).

So TopDocs hits = orchestrator.collect(query, drillSideways, new TopScoreDocCollectorManager(1, 1)) throws ClassCastException at the caller's statement, after the search has finished, with assertions on and off. The same was run with a hit-count manager assigned to Integer and a sorted top-docs manager assigned to TopFieldDocs, on the 10.2.0 and 10.6.0 release jars and on builds of branch_11x and main.

What still works. The returned value does not touch the facet results: the statement comes after the search. In the runs with one sideways builder they are right, and with a drill-down builder beside it they equal those of the two-argument collect. (More than one sideways builder is another finding, LFV-1542, named further down.) Held as Object, the value is the array, and its element 0 is the main collector manager's result. A call whose value is discarded throws nothing. The two-argument collect, which Lucene's own tests and demo use, returns no value. No caller of the returned value was found in Lucene's own sources.

Where the caller gets no exception. A main collector manager whose own result type is Object[] gets no exception at the call: it receives the internal array, with its own array nested at element 0. Run with five shapes: a MultiCollectorManager of a top-docs and a hit-count manager and one of two top-docs managers, each beside a sideways and a drill-down builder; and, with a sideways builder only, a MultiCollectorManager of two top-docs managers, one of two hit-count managers, and a manager of its own whose result type is Object[].

The statement came with the class (#14237, merged 2025-03-03, first released in 10.2.0). A change of one statement, return (T) result.drillDownResult()[0];, makes the test pass; with it the sandbox module's tests show no failure (426 tests, 72 of them skipped by Lucene itself) and the module's check passes.

Why it looks unintended

#
  • The signature ties the returned type to the collector manager that is passed; the method has no javadoc.
  • The sibling FacetOrchestrator#collect, added by the same pull request, returns element 0; Lucene's demo assigns it to a TopDocs.

The full argument333 words
  • The signature is the contract. Neither collect method has javadoc. T comes from the manager that is passed (DrillSidewaysFacetOrchestrator.java:67-71), so for a TopScoreDocCollectorManager the declared result is TopDocs. An Object[] is a T when T is Object or another supertype of Object[], and not otherwise.
  • The sibling. FacetOrchestrator#collect, added by the same pull request with the same shape of signature, returns element 0 (FacetOrchestrator.java:59). The demo assigns its result to a typed variable: TopDocs topDocs = new FacetOrchestrator()...collect(MatchAllDocsQuery.INSTANCE, searcher, hitsCollectorManager); (SandboxFacetsExample.java:166-170).
  • History inside #14237 (the weakest of these points; the argument does not need it). The first commit of the pull request with this file (13aa0f1ef74, 2025-02-05, titled "TMP: DrillSidewaysFacetOrchestrator.") is an unfinished copy of the sibling that does not compile (its searcher and mcm are not declared in the file); it ends with the sibling's return (T) res[0];.   • No test and no demo uses the value. In Lucene's sources at f6e694652c3d the calls of this class are the two-argument form: TestFacetOrchestrators.java:183, :309, :341, :374 and SandboxFacetsExample.java:207-210. That is also why no test saw it.
  • Nothing documents the array. The devil's-advocate check237 words

The strongest case for "works as designed": the class is a sandbox utility tagged @lucene.experimental, which renders as "This API is experimental and might change in incompatible ways in the next release". The method has no javadoc. The package text sends users to FacetBuilder#getResult() for results. DrillSideways#search itself tells users to wrap managers in a MultiCollectorManager "to collect both hits and facets" (DrillSideways.java:397-404), and the low-level demo reads such a result as (TopDocs) results[0] (SandboxFacetsExample.java:502-503). So one could say: the value is the composite's result, as in the low-level API, and nothing promised more.

Why it fails: a method meant to return the array would be declared Object[], and the type parameter T has no purpose other than to promise the passed manager's result. The experimental tag allows the API to change between releases; it does not make another object the declared result of the current one. The sibling, added at the same time for the same purpose, returns element 0. Where the method returns without a main collector (that needs a drill-down builder), it returns null, not the array of the drill-down results, so the array is not offered as a result either. What the argument does bound is the weight: an experimental helper, a loud failure where the value is first used as the manager's result type, and no known caller. That is why the finding is Low.

Declare what is returned (not built)

#

Change the declared return type to Object[] and document that element 0 is the main result.

Trade-offs

It keeps the hits one index away for every caller, departs from the sibling's signature and is an API change of its own. Not built. Documenting the array without changing the type would not repair the call: TopDocs hits = ...collect(...) would still compile and still throw, because the type check is the cast that the compiler puts into the caller (read in the bytecode of the compiled test: checkcast TopDocs directly after the call).

Workaround on a released version (not a fix)

#

Hold the value as Object and read its element 0, or keep the three-argument call, discard its value and take the hits from a search of the caller's own. Run: held as Object, the value is Object[1]{TopDocs} with a sideways builder only and Object[2]{TopDocs, CountFacetRecorder} with a drill-down builder as well; a discarded value throws nothing and the facet result is there; a search of the same query with a collector manager made the same way returns the hits. The two-argument collect is not a way around for the test's example: with a sideways builder only it throws IllegalArgumentException (run).

Trade-offs

Code written the first way has to change again once the method returns the result itself (the first trade-off of the change above). A discarded value does not.
