The bug in 30 seconds

#

ICUFoldingFilter folds with a compiled table, utr30.nrm. Letters like ҧ have no Unicode decomposition, so only a hand-written Cyrillic block of DiacriticFolding.txt can fold them: 26 lines copied from the 2004 UTR#30 draft (Unicode 4.0), none above U+04CF. The 24 letters of this kind added in Unicode 4.1-7.0, such as ԥ, have no line, so they keep their mark.

  1. You add ICUFoldingFilter with its default settings at index and query time, and index the Abkhaz word "аҧсуа" in its older spelling, with ҧ (PE WITH MIDDLE HOOK).
  2. You expect the modern spelling "аԥсуа", with ԥ (PE WITH DESCENDER), to find it: the filter removes hooks and descenders, it folds ҧ to п, and Unicode's character list cross-references ԥ to ҧ.
  3. Instead the document's term is апсуа and the query's term is аԥсуа: 0 of 1 documents found. The filter leaves ԥ as it is (it only lower-cases the capital Ԥ to ԥ).
  4. The cause: the Cyrillic part of the folding table is a 2010 copy of a 2004 draft made for Unicode 4.0, never extended. Of 48 older Cyrillic hook, stroke and descender letters, 46 fold to their base letter; of the 24 added in Unicode 4.1-7.0, none does.
  5. No error, and each exact spelling still finds itself. Adding 12 lines to the table and regenerating it folds all 24 and changes no other code point.

Who is affected

#

Users of the optional analysis-icu ICUFoldingFilter (default data, no setting needed) who index Cyrillic text in an orthography using one of these letters, such as modern Abkhaz, Yupik, Itelmen or Nenets. A word spelled with the newer letter and the same word with the older or plain letter give two terms. Silent, deterministic, every release since 3.1.0.

Mechanism, terms and numbers865 words

ICUFoldingFilter (module analysis-icu) folds text for search; its javadoc lists "Diacritic removal (including stroke, hook, descender)". Cyrillic letters such as ҧ PE WITH MIDDLE HOOK have no Unicode decomposition, so the only thing that folds them is a hand-written block of DiacriticFolding.txt, compiled into utr30.nrm. That block was copied in 2010 from the 2004 draft data of UTR#30, which was based on Unicode 4.0, and has never been extended: 26 lines, none above U+04CF. So 46 of the 48 Cyrillic letters of this kind from Unicode 1.1-3.2 fold to their base letter (ҷ/Ҷ fold to a wrong letter, a separate bug), while none of the 24 added in Unicode 4.1-7.0 loses its mark: ӷ ӻ ӽ ӿ ԓ ԡ ԣ ꚋ ԥ ԧ ԩ ԯ and their capitals are only lower-cased. In Abkhaz, Unicode's character list marks ҧ as the letter of "older orthographies" and ԥ as "used in modern Abkhaz orthography": the older spelling "аҧсуа" is indexed as апсуа, the modern spelling "аԥсуа" stays аԥсуа, and it finds 0 of 1 documents; a document in the modern spelling is missed by the older and the plain spelling as well. No error is raised, and each exact spelling still matches itself. The file header says "Created from Unicode 5.2 UCD", yet 18 of the 24 code points were already in Unicode 5.2. Every release from 3.1.0 to 10.5.2 and main is affected: the 138 releases ship 13 distinct compiled tables, and a standalone check fails on at least one release of each. The fix is 12 added data lines and a regenerated utr30.nrm; it changes indexed terms for these letters, so affected fields need reindexing.

Terms

#
  • ICUFoldingFilter (module analysis-icu): a token filter for "search term folding". Its normalizer NORMALIZER loads the compiled data file utr30.nrm (ICUFoldingFilter.java:69-77); the one-argument constructor uses it, and so does ICUFoldingFilterFactory (SPI name icuFolding), directly or, with a filter argument, wrapped in a FilteredNormalizer2, which can only exclude characters.
  • utr30.nrm: compiled by the gradle task regenerateUtr30DataFiles from src/data/utr30/*.txt with ICU's gennorm2 and icupkg. The task first regenerates the rule-based parts of the tables from Unicode properties and keeps the data lines after a # Rule: verbatim marker as written.
  • Why only a table line helps: none of the 72 Cyrillic letters of this kind (48 older, 24 newer) has an NFKD decomposition or the Unicode Diacritic property, so neither NFKC nor the [:Diacritic:] rule touches them. A Cyrillic letter with a hook, stroke or descender is folded only if the block has a line for it.

The block

#

DiacriticFolding.txt:597-626, headed "Cyrillic script \"composed\" that do not further decompose, so decompose here", "These are from UTR#30 DiacriticFolding.txt" and "# Rule: verbatim": 26 lines from 047D>0461 to 04CE>043C, for example 0493>0433 (ғ GHE WITH STROKE to г), 04A7>043F (ҧ PE WITH MIDDLE HOOK to п) and 04C6>043B (ӆ EL WITH TAIL to л). The UTR#30 draft data it names is "DRAFT 1 - 2004-07-14", "Base version of Unicode: 4.0.0", and has no line for any of the 24 newer letters. Capitals need no line: nfkc_cf.txt case-folds them to the small letter first (for example 0524>0525). The file's header (:24) says "Created from Unicode 5.2 UCD".

The split

#

Over every Cyrillic letter named "<base> WITH <hook, stroke, descender, tail, tick, upturn or bar>" whose base letter exists: Unicode 1.1, 36 fold to the base letter and 2 (ҷ/Ҷ, CHE WITH DESCENDER) to a wrong letter, a separate bug; 3.0, 2 of 2; 3.2, 8 of 8; then 4.1, 0 of 2; 5.0, 0 of 8; 5.1, 0 of 6; 5.2, 0 of 2; 6.0, 0 of 2; 7.0, 0 of 4. The same check also lists three Unicode 15.0 subscript and modifier letters of this kind (U+1E067, U+1E06B, U+1E06D); they do fold, through their compatibility decomposition to the older ґ, ҫ and ұ, which have block lines.

Not claimed here

#

89 Latin letters with a stroke, bar, hook, descender, tail, curl or similar mark are unfolded too: 76 added in Unicode 6.0-16.0, and 13 older ones (Unicode 1.1-5.1) that the ASCIIFoldingFilter-derived Latin block lists only as commented-out placeholders (such as #019B>, DiacriticFolding.txt:283). That block deliberately leaves many letters out, as ASCIIFoldingFilter does, so they are not part of this report.

Exposure and likelihood203 words
  • Who is exposed. Analysis chains with ICUFoldingFilter: built by hand, with CustomAnalyzer or the icuFolding SPI name, or through a downstream product that wraps the filter. No Lucene analyzer adds it by default; once chosen, its default data is enough.
  • Which text. Cyrillic text in an orthography that uses one of the 24 letters. Unicode's NamesList names modern Abkhaz for ԥ (cross-referenced to ҧ, "older orthographies for Abkhasian"), Yupik for ӷ, Itelmen for ԓ and Nenets for ԯ.
  • Effect. Deterministic, for every token with one of these letters: it keeps its hook, stroke or descender, so the same word written with the older letter form or with the plain base letter (for example on a keyboard without the letter) gives a different term, and the query misses. Either direction misses: a modern-spelling document is missed by the older and the plain spelling too. No exception, no index damage, nothing in the logs; each exact spelling still matches itself.
  • How likely. Rare for most indexes: the text must use one of these minority-language letters and the spellings must differ. Nobody has reported it since 3.1.0 (2011).
  • Fixing it changes indexed terms: fields that contain these letters need a reindex after the fix.

Why it is a bug, not intended

#
  • The javadoc lists "Diacritic removal (including stroke, hook, descender)" with no coverage hedge; the header says "Created from Unicode 5.2 UCD", yet 18 of the 24 letters are in 5.2.
  • Every older letter of the kind folds, including ҧ, the counterpart of ԥ.
  • UTR#30 says its foldings must grow with Unicode; nothing records a decision to exclude these letters.
The full argument308 words
  • Contract. ICUFoldingFilter.java:33: "Diacritic removal (including stroke, hook, descender)". The module overview: search term folding "removes distinctions (such as accent marks) between similar characters" and is "a more thorough replacement for ASCIIFoldingFilter and LowerCaseFilter that applies the same ideas to many more languages". Unlike ASCIIFoldingFilter ("only those characters with reasonable ASCII alternatives are converted"), it has no coverage hedge.
  • The block's stated job. "Cyrillic script \"composed\" that do not further decompose, so decompose here" (DiacriticFolding.txt:597). The 24 letters are exactly such characters.
  • The file claims Unicode 5.2. "Created from Unicode 5.2 UCD" (:24), yet 18 of the 24 code points (Unicode 4.1-5.2) existed when the block was copied in 2010. In that 2010 file the three large sections already had post-4.0 entries (157 in the [:Diacritic:] list, 117 in the Latin block, 113 in "Additional signs and diacritic"); the Cyrillic block had none (as did the small "Additional Arabic/Hebrew decompositions" block).
  • Old and new siblings disagree. ҧ, ғ, ҕ, ҳ, ӆ, ң, ӈ, ҭ and 38 more older letters fold to their base letter; ԥ, the modern counterpart of ҧ, and the 23 other newer letters do not. Only the Unicode version decides.
  • The source expects growth. UTR#30 section 5.3: "As characters are added to [Unicode] many of them need to be added to the definition of foldings described here." Its data file: "Additional instances of such characters are expected to be added over time, so there will be future additions to this table."
  • No decision recorded. Where the maintainers chose not to fold a Latin letter, the file keeps a commented-out placeholder (67 lines such as #019B>); the Cyrillic block has none. No test, CHANGES entry or issue mentions these letters, no upstream test asserts any Cyrillic folding of the filter, and no commit ever had a line for any of them.
The devil's-advocate check353 words

The strongest case for "intended": the javadoc says the filter applies "foldings from UTR#30", and the module overview says it "implements many of the foldings specified in" that report. UTR#30 says its foldings "cover Unicode, Version 4.0" and lists diacritic removal under "Provisional foldings". In its table the source set of "Diacritic removal (includes stroke, hook, descender)" is "Latin/Greek/Cyrillic characters with diacritics <>", where <> means the characters listed in its data file, which covers Unicode 4.0 and lists none of these letters. The report is a withdrawn draft; the javadoc names kinds of folding of a finite table. Maintainers knowingly left the block static: in #4820 (LUCENE-3747) "Other sections were based either on AsciiFoldingFilter or UTR#30, neither of which has changed" and "It doesn't need to be perfect"; in #11274 the verbatim sections are "(basically hacks)"; in #2420 removing diacritics is called "language-specific". ICU's root collation keeps these letters, old and new, primary-distinct from their base letters (70 of the 72; only ґ/Ґ GHE WITH UPTURN is primary-equal). So this is a data-coverage enhancement.

Why it fails: the report did limit its foldings to Unicode 4.0, but it also says its table must grow as characters are added, so its 4.0 listing reads as a provisional snapshot rather than a decision to leave later letters unfolded; this is an argument, not proof. Lucene maintains its own copy: its Latin section comes from ASCIIFoldingFilter, and the file introduced in 2010 already had post-4.0 source code points in its other large sections, while the Cyrillic block had none. "Neither of which has changed" explains why the 2012 automation skipped the block; it is not a decision that newer letters stay unfolded. The language-specific and collation points apply equally to the older letters, which the filter already folds. Verdict: not intended, a coverage defect; the label (bug or improvement) is the committers' call. When filing: say that UTR#30's folding formally lists only its 4.0 data, do not claim the javadoc promises these exact letters, lead with the ҧ/ԥ inconsistency and the 12-line fix, and mention the collation and language-specific counterpoints yourself.

Workaround for users today

#

Map the 24 letters to their base letters before the filter (for example with a MappingCharFilter), or pass a custom Normalizer2 to the two-argument constructor. Not run as a workaround. One pitfall was executed: if the custom normalizer is a fixed utr30.nrm loaded with Normalizer2.getInstance(InputStream, name, mode), give it a name other than "utr30". ICU4J caches these instances by name, so once ICUFoldingFilter.NORMALIZER is loaded, a second load under "utr30" returns the stock normalizer, which leaves ԥ unchanged.

Trade-offs

Both change indexed terms, so they also need a reindex. The factory's filter argument cannot help: it can only exclude characters from folding.

How it was found

#

An exhaustive check over all Unicode scalar values compared each Latin, Greek and Cyrillic letter named "<base> WITH <mark>" with the fold of its base letter, by the Unicode version that added it. For Cyrillic the cut was exact: up to 3.2 every such letter loses its mark, from 4.1 to 7.0 none does.

The method in full218 words

Method: bounded-exhaustive translation validation of the folding data (semi-formal tier), in a hunt unit that checked the scope of ICUFoldingFilter's diacritic removal against the UTR#30 domain and against collation primaries.

  • The harness ran the stock main jar (ICU4J 78.3, Unicode 17) over every Unicode scalar value and, for each Latin, Greek and Cyrillic letter whose name is "<base> WITH <diacritic>" with an existing base letter, compared fold(letter) with fold(base), bucketed by Unicode age. An earlier unit's name oracle had listed the unfolded letters without filing them; the age split was found here (2026-10-28).
  • Cyrillic: 48 of 48 letters of this kind from Unicode 1.1-3.2 lose the mark (46 to the base letter, 2 to a wrong letter, a separate bug), 0 of 24 from 4.1-7.0. The 3 Unicode 15.0 subscript and modifier letters of this kind fold through their compatibility decomposition. Latin has 89 unfolded letters of this kind (76 from Unicode 6.0-16.0, 13 older ones that the Latin block keeps as commented-out placeholders), not claimed because the Latin block deliberately leaves letters out.
  • The finding was reduced to a public-API JUnit and checked by an independent reproducer with its own oracle, reading-only reviews by a model from another family (OpenAI GPT-5.6), an intended-behaviour devil's advocate, an adjudication, a history, prior-report and security follow-up, and an audit.

History

#

Born with the filter: 3599d0c60b17 (LUCENE-1343, 2010-04-22), first released in 3.1.0, copied from the 2004 UTR#30 draft data. The block was never extended; 17 versions from 3.1.0 to main were run, all affected, covering each of the 13 compiled tables shipped in the 138 releases. 20 letters are visible from 3.1.0, the 4 of Unicode 7.0 from 5.0.0.

Versions tested7 rows

Introduced with the filter by 3599d0c60b17 "LUCENE-1343: Add ICUFoldingFilter, normalizes unicode text for search" (2010-04-22, svn trunk r936657; issue #2420, no PR), backported to branch_3x as 534809c2eae (2010-05-06), which shipped in 3.1.0. git blame -w gives 29 of the 30 block lines to 3599d0c60b17 and the marker # Rule: verbatim to 5abc76ea4221 (LUCENE-3747, 2012). The Unicode 6.0 and 7.0 upgrades (LUCENE-2797 d0c3026c316, LUCENE-5995 7a50635bc4c) added mark entries elsewhere in the file but no line for these letters, and git log --all -G finds no commit that ever had one. Wrong from the start, so not a regression.

A letter becomes a gap in the first release whose ICU4J assigns it (unassigned code points pass through unchanged): 20 letters (Unicode 4.1-6.0) from 3.1.0 with ICU4J 4.6, the 4 of Unicode 7.0 from 5.0.0 with ICU4J 54.1. Every other release ships a table that was executed: the 138 releases from 3.1.0 to 10.5.2 carry 13 distinct compiled tables (utr30.nrm in each release's ICU analysis jar, compared by SHA-1), and the main() ran on at least one release of each. LFV-877, snapshot of 2026-10-30

Registry title
ICUFoldingFilter removes the hook, stroke or descender from older Cyrillic letters such as ҧ (U+04A7) but from none of the 24 letters of that kind added in Unicode 4.1-7.0, such as its modern Abkhaz counterpart ԥ (U+0525), so the two spellings of a word give different terms
Area
analysis / icu (ICUFoldingFilter UTR#30 folding data: the hand-written 'Rule: verbatim' Cyrillic block of DiacriticFolding.txt, compiled into utr30.nrm)
Priority
Low, rank 449: The opt-in ICUFoldingFilter leaves the mark on 24 newer Cyrillic hook, stroke and descender letters used in minority-language spelling, which only hurts relevance.
Impact class
minor
Impact note
Relevance only, no error: applications that use the optional analysis-icu ICUFoldingFilter or ICUFoldingFilterFactory (its default normalizer, no setting needed) and index Cyrillic text of a minority-language orthography that uses one of these letters (modern Abkhaz ԥ, Yupik, Itelmen, Nenets, Khanty and others) get a different term for a word spelled with the newer letter than for the same word spelled with the older letter form or the plain base letter, so such queries silently miss the document while the exact spelling still matches itself; no scale is needed, -ea and -da behave the same, every release from 3.1.0 to 10.5.2, branch_10_6 and main are affected, and because a fix changes indexed terms, affected fields need reindexing.
Summary
You index Abkhaz text in the older spelling 'аҧсуа' with ICUFoldingFilter, whose javadoc lists 'Diacritic removal (including stroke, hook, descender)' and which folds ҧ (U+04A7) to п, and you expect the modern spelling 'аԥсуа', written with ԥ (U+0525, the modern-orthography counterpart of U+04A7), to find it. Instead the hand-copied Cyrillic table in DiacriticFolding.txt, taken from the 2004 UTR#30 draft data for Unicode 4.0 and never extended, has no line for ԥ or for any of the other 23 hook, stroke or descender letters added in Unicode 4.1-7.0 (ӷ ӻ ӽ ӿ ԓ ԡ ԣ ꚋ ԧ ԩ ԯ and the capitals), so they are only case-folded and keep the mark, and the query finds 0 documents. All 48 older letters of the same kind lose the mark (46 fold to their base letter; ҷ/Ҷ fold to a wrong letter, the separate bug LFV-855).
