SortField.equals is not symmetric with ToParentBlockJoinSortField: a plain sort equals a block-join sort on the same field, but not the other way round

A plain SortField("price", INT) says it equals a block-join sort on price, but the block-join sort says it does not and their hash codes differ, although the two sort the same parents in opposite orders. Every release since 6.6.0; no Lucene code path gives a wrong result.

The finding in 30 seconds

#

SortField.equals and the block-join subclass's equals follow different rules, so the answer depends on which of the two objects you ask.

Background: sort fields, block joins and equals

#
  1. A SortField names a field, a type such as INT, a direction and an optional missing value; a Sort is a list of them. Both override equals and hashCode, so applications and caches can compare sorts.
  2. With block joins, each parent document is indexed right after its children. ToParentBlockJoinSortField (join module) sorts parents by their children's values: the lowest child value, or the highest when reversed.
  3. Java's Object.equals contract: x.equals(y) must be true exactly when y.equals(x) is, and equal objects must have equal hash codes.

The finding, step by step

#
  1. You build plain = new SortField("price", INT) and join = new ToParentBlockJoinSortField("price", INT, false, parents, children). On two parent blocks, A (own price 10, children 30 and 40) and B (own price 20, child 5), plain sorts the parents A, B and join sorts them B, A, by their lowest child price.
  2. You expect plain.equals(join) and join.equals(plain) to give the same answer, here false: Java's equals contract requires symmetry, and equal objects must have equal hash codes.
  3. Instead plain.equals(join) is true and join.equals(plain) is false, and the hash codes differ. new Sort(plain).equals(new Sort(join)) is true, the reverse false; List.of(join).contains(plain) is true, List.of(plain).contains(join) false. Both print as <int: "price">.
  4. Why: SortField.equals accepts any subclass and compares only field, type, reverse, comparator source and missing value, which the block-join sort passes unchanged to its parent class. The block-join equals also requires the same class, and its hashCode adds the parent and child filters.
  5. Hash-based lookups keep the two apart, and no Lucene code path gives a wrong result. Lucene main already guards this exact symmetry for one other subclass, NonPruningSortField (#16857).

Who is affected

#

Application or framework code that compares sorts with equals outside a hash table, with the plain sort as receiver and a block-join sort on the same field and type as argument: it is told they are equal although they order parents differently. Opt-in (join module) and rare; no Lucene code path and no hash-based cache is affected.

Mechanism, terms and numbers487 words

new SortField("price", INT).equals(new ToParentBlockJoinSortField("price", INT, false, parents, children)) is true, the reverse call is false, and the two hash codes differ. SortField.equals accepts any subclass through instanceof (it excludes only NonPruningSortField) and compares just its five base fields; the block-join sort field passes the same five values to super, but its own equals adds a getClass() check and its hashCode also covers the parent and child filters. Sort.equals compares its fields with Arrays.equals, so new Sort(plain).equals(new Sort(join)) is true and the reverse false. The two sorts are not interchangeable: on two parent blocks the plain one returns A, B and the block-join one B, A. This breaks the java.lang.Object contract that SortField overrides, and that Lucene main already enforces in this method for NonPruningSortField. No Lucene code path gives a wrong result and hash-based caches keep the pair apart, so only application code that compares sorts with equals outside a hash table, with the plain sort as the receiver, is told they are equal. It is in every release from 6.6.0 through 10.6.0 and on main, and a few-line change in SortField.equals fixes it.

The code (main 5adff78bb168)

#
  • SortField.java:478-490, equals: if (!(o instanceof SortField other) || o instanceof NonPruningSortField) return false; (:481, comment "NonPruningSortField is never equal to a plain SortField, which keeps equals symmetric", :482), then it compares field, type, reverse, comparatorSource and missingValue (:485-489). :496-499: hashCode hashes the same five.
  • ToParentBlockJoinSortField.java:158: the constructor passes the real type, here INT, to super(field, type, reverseParents, parentMissingValue); the 5-argument constructor passes null missing values (:71). So the five base fields equal those of new SortField("price", INT), and the plain side answers true.
  • ToParentBlockJoinSortField.java:379-396, equals: super.equals, then false on getClass() != obj.getClass() (:383). :368-377, hashCode: adds childFilter, reverseChildren, parentFilter and childMissingValue. So the block-join side answers false, and the pair the plain side calls equal has different hash codes.
  • Sort.java:114-126: equals and hashCode use Arrays.equals and Arrays.hashCode over the fields and inherit both problems.

The same pattern elsewhere

#

SortedNumericSortField and SortedSetSortField are one-way equal to a plain SortField of type CUSTOM without a comparator source, which cannot sort, so the realistic pair is the block-join one. BinarySortField, LatLonPointSortField, XYPointSortField, FeatureSortField and the two Geo3DPoint*SortFields use the same super.equals-then-getClass() pattern; whether a plain SortField can match their base fields was not checked for each.

Why it looks unintended

#
  • Object.equals requires symmetry and equal hash codes for equal objects; SortField overrides both, and nothing documents one-way equality.
  • Lucene main already enforces it in this method: #16857 excludes NonPruningSortField "which keeps equals symmetric", and its test checks both directions.
  • The block-join side means exact-class equality (getClass()); the base instanceof dates from 2008, before any subclass added state.
The full argument177 words
  • The contract. SortField overrides equals and hashCode; its javadoc (SortField.java:474-477) says "Returns true if o is equal to this" and asks a FieldComparatorSource to implement equals; it says nothing about subclasses. Nothing in the javadoc, MIGRATE.md or CHANGES.txt allows one-way equality.
  • Main applies the rule to this method. #16857 (70a428b5ba9, Alan Woodward, 2026-10-29) excluded NonPruningSortField with the comment "NonPruningSortField is never equal to a plain SortField, which keeps equals symmetric" (SortField.java:481-482); TestNonPruningSortField.java:36-37 asserts inequality in both directions. The older state-adding subclasses were not covered.
  • History. The base instanceof dates from LUCENE-1481 (e0efcd52ea2, 2008). LUCENE-7798 (#8849, 2017) added the subclass's equals and hashCode so the sort field could be part of a query-result cache key (SOLR-10521); its test (TestBlockJoinSorting.java:604-617, notEqual) compares block-join sorts only with each other. LUCENE-1188 (#2265) reported the same mixed instanceof / getClass() asymmetry in Query subclasses; it was resolved in 2.9 "by various other issues" (Uwe Schindler's comment there). The Query hierarchy now uses exact-class equality (Query.sameClassAs, Query.java:126-128).
The devil's-advocate check169 words

The strongest case for "intended", made by an intended-behaviour check and by an independent reviewer from another model family (OpenAI GPT-5.6), who rated it moderate: SortField is public, non-final and has used instanceof for 18 years, so stateless third-party subclasses may rely on being equal to a plain SortField; on the open #7802 (LUCENE-6744) a committer said in 2015 they were "not a fan of changing behavior to conform to abstract principle without there being a demonstrable problem", and a 2022 comment there pointed to Error Prone's EqualsGetClass, which prefers instanceof.

Why it fails: the stateless-subclass point is real, but it is about how to fix it (option B keeps such subclasses equal), not a reason for this pair to be one-way. #7802 lists other classes, is still open and is not won't-fix; Lucene's build switches EqualsGetClass off as "noisy" (ErrorPronePlugin.java:406); and #16857 guarded against this asymmetry for its own new subclass days earlier, also without a demonstrable problem. Verdict: a real Low bug.

Suggested fix

#

Recommended B. Let a subclass argument decide (recommended, validated)

Recommended (option B): in SortField.equals, when the argument is a subclass of this object's class, return its answer (o.equals(this)), replacing the NonPruningSortField special case. The repro passes, the 952 core tests matched by the *Sort* / *TopFieldCollector* filters (41 skipped) and the 104 join tests (3 skipped) run with 0 failures, and stateless subclasses stay equal to plain SortFields.

B. Let a subclass argument decide (recommended, validated)

Trade-offs

Fixes every base-versus-subclass pair (the block-join pair and the two CUSTOM pairs) and makes the NonPruningSortField special case unnecessary, with no new API. A stateless subclass that does not override equals stays equal to a plain SortField both ways, as today. It does not cover two unrelated subclasses, for example an anonymous new SortField("price", INT) {} against a block-join sort field, which stay one-way equal (read, not run). Asking the subclass is an unusual pattern; it only goes from a class to a strict subclass, so it cannot loop unless a subclass's equals calls the argument's equals back.

A. Exact-class equality (validated; breaks one case)

#

if (o == null || getClass() != o.getClass()) return false;, then cast: the Query.sameClassAs convention.

Trade-offs

Simplest and fully symmetric, but a stateless custom subclass is no longer equal to a plain SortField. A stateless subclass inherits SortField's index sorter and its base provider, so its index sort is read back from the segment as a plain SortField (SortedNumericSortField, SortedSetSortField and BinarySortField register their own providers and come back as their own types). So an application that configures setIndexSort(new Sort(new SortField("price", INT) {})) can no longer reopen its index: IllegalArgumentException: cannot change previous indexSort=<int: "price"> (from segment=_0(12.0.0):c1) to new indexSort=<int: "price"> (IndexWriter.java:1213-1229, via isCongruentSort). Main is 12.0, so a MIGRATE.md note could cover it if maintainers prefer this.

What the checks validated

The repro passes, and the same 952 core and 104 join tests run with 0 failures (41 and 3 skipped); only the stateless-subclass index-sort check fails, with the exception above.

C. A canEqual hook (not run)

#

A protected canEqual(SortField other) that SortField.equals asks of the argument, overridden by each state-adding subclass (the pattern of Odersky, Spoon and Venners, "How to Write an Equality Method in Java").

Trade-offs

Covers unrelated subclasses too, but adds API and needs every state-adding subclass, in Lucene and outside it, to opt in.

Downstream note

#

A downstream product that matches cached sort keys with equals in a list could reuse one parent ordering for the other; hash-based caches keep the two apart.

How it was found

#

A semi-formal proof-obligation audit of SortField's equals and hashCode contract: symmetry, and equal hash codes for equal objects, checked for each subclass against the base class. The block-join pair broke both obligations, and a public-API test witnessed it.

The method in full102 words

The obligations come from java.lang.Object, which SortField overrides: for any two sort fields x and y, x.equals(y) == y.equals(x), and x.equals(y) implies x.hashCode() == y.hashCode(). The audit paired the base equals (instanceof, five base fields) with each subclass's equals and hashCode and looked for a subclass whose base fields can match a plain SortField while its own equals rejects it. ToParentBlockJoinSortField passes the real type to its parent class, so it matches new SortField(field, type); the one-test JUnit repro is the witness, and a relations probe added the Sort, List.contains and CUSTOM-type pairs.
