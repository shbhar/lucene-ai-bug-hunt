Sandbox TermAutomatonQuery.visit() gives the QueryVisitor a Term with null bytes for an any-term transition, so UnifiedHighlighter.highlight and Monitor.register throw NullPointerException while the search returns the hit

Low, experimental sandbox class: searching a TermAutomatonQuery with an any-term transition returns its hit, but UnifiedHighlighter.highlight and Monitor.register throw NullPointerException, because visit() hands them a Term with null bytes. It is on the released lines (run: 8.1.0 to 10.6.0), branch_11x and main; only code that builds this query meets it.

The finding in 30 seconds

#

The query keeps its any-term transition under a null key in a private term map. visit() turns every key of that map into a Term for the visitor, the null key too. So the visitor gets one Term with no bytes, and code that reads the bytes of each term fails.

Background: three pieces

#
  1. TermAutomatonQuery (sandbox module, marked experimental) matches documents with an automaton whose transitions are terms, a generalisation of a phrase query. addAnyTransition adds a transition that accepts any term at that position; TokenStreamToTermAutomatonQuery makes one from the token *.
  2. Query.visit(QueryVisitor) is how other code asks a query for its terms. A leaf query calls consumeTerms with "the terms the query will match on".
  3. UnifiedHighlighter and the monitor module's Monitor are two such callers. Both read term.bytes() of every term they are given.

The finding, step by step

#
  1. Index one document a x b. Build a TermAutomatonQuery for a, any term, b: addTransition(s0, s1, "a"), addAnyTransition(s1, s2), addTransition(s2, s3, "b"). searcher.search(q, 10) returns 1 hit.
  2. Give the same query to code that asks a query for its terms: UnifiedHighlighter.highlight("field", q, hits) or Monitor.register(new MonitorQuery(id, q)). You expect the snippet <b>a x b</b> and a registered query. That is what the same query with the concrete middle term x gives.
  3. Instead both throw NullPointerException. A term collector shows why: q.visit(QueryVisitor.termCollector(terms)) collects 3 terms, field:a, field:b and a third Term whose bytes are null. Its text() throws too.
  4. Why: the query keeps "any term" under a null key in its private term map. visit() passes every key of that map to the visitor as new Term(field, key), the null key included. The class's other loops skip that key, and so did extractTerms, the method that visit() replaced in 2019.
  5. 10.6.0, branch_11x and main behave the same. With a three-line null check in visit() the collector gets field:a and field:b, the highlighter returns <b>a x b</b> and the monitor registers the query.

Who is affected

#

Low. Only code that builds the experimental sandbox TermAutomatonQuery with an any-term transition, itself or through TokenStreamToTermAutomatonQuery, and then passes it to something that reads its terms: UnifiedHighlighter, a Monitor, the classic Highlighter with QueryTermScorer, a term collector. The exception is loud. The search returns its hit and nothing is written wrong. No report was found since 8.1.0 (2019).

Mechanism, terms and numbers943 words

TermAutomatonQuery is an experimental class of the sandbox module: a proximity query whose automaton has terms as transitions. addAnyTransition ("Adds a transition matching any term", TermAutomatonQuery.java:122-125 on main 781025d6fe32) stores that transition under the null key of the query's term map (:241-256). visit() (:572-581) loops over every key and calls consumeTerms(this, new Term(field, term)), the null key included, so a QueryVisitor is handed one Term whose bytes are null. The scoring search of such a query returns its hit, because every other loop over the map skips or special-cases the key (the example's automaton is rewritten to a PhraseQuery in which the any term is a position gap). Consumers of the terms fail: UnifiedHighlighter.highlight throws NullPointerException under filterExtractedTerms (UnifiedHighlighter.java:1086), Monitor.register throws it in the default term weightor (TermWeightor.java:128), the classic Highlighter throws it when it is built with QueryTermScorer (not when built with QueryScorer), and a term collector holds a Term whose text() throws. The method that visit() replaced in 2019 (LUCENE-3041), Weight.extractTerms, skipped the key. visit() does this in every release since 8.1.0; UnifiedHighlighter fails for every such query since 9.5.0, before that only for automata that rewrite() keeps. 10.6.0, branch_11x daa54f2e0cd3 and main 781025d6fe32 fail the same way. The weight is Low: an experimental class, a loud failure, a search that returns its hit, nothing written wrong, and a three-line check cures it.

The code path

#

Lines are main 781025d6fe32; the same files are on branch_11x daa54f2e0cd3.

  1. addAnyTransition (TermAutomatonQuery.java:122-125) calls getTermID(null). getTermID (:241-256) puts the null key into the map termToID and remembers its id in anyTermID. The null key is the class's private marker for "any term".
  2. visit() (:572-581) loops over every key: for (BytesRef term : termToID.keySet()) { v.consumeTerms(this, new Term(field, term)); } (:578-580). There is no check for the marker.
  3. new Term(field, null) keeps the null (Term.java:52-55). Its text() throws (Term.java:100-102).
  4. UnifiedHighlighter collects the query's terms with QueryVisitor.termCollector (UnifiedHighlighter.java:374-378) and passes them to filterExtractedTerms (:1044, :1080-1090). Its filteredTerms.add(term.bytes()) (:1086) adds null to a TreeSet: NullPointerException.
  5. Monitor.register analyses the query with a visitor that makes one tree node per term (QueryAnalyzer.java:113-117, QueryTree.java:73-75). The default term weightor reads value.bytes().length (TermWeightor.java:32, :127-131): NullPointerException.
  6. The classic Highlighter, when it is built with QueryTermScorer: the constructor takes the terms from QueryTermExtractor.getTerms (QueryTermScorer.java:49), whose visitor reads term.text() of every term (QueryTermExtractor.java:96-100, :138-141): NullPointerException. Built with QueryScorer it goes another way and does not throw.
  7. The scoring search returns the hit because every other loop over the terms skips or special-cases the marker: rewrite (TermAutomatonQuery.java:539-545), createWeight (:216-217), the Weight's constructor (:380-381), toDot (:330); finish (:152-172) checks the any-term transitions on its own. Which of them a search meets depends on the automaton. The example's is rewritten to the PhraseQuery "a ? b", in which the any term is a position gap, and TermAutomatonQuery.createWeight is not called. An automaton that rewrite() keeps goes through createWeight.

Why it looks unintended

#
  • consumeTerms takes "the terms the query will match on"; Term's javadoc calls null bytes "undefined behavior".
  • extractTerms, which visit() replaced in 2019, skipped the null key; on 8.1.0 and 8.11.4 the two disagree.
  • The input is legal: addAnyTransition is a documented builder method, and the class's other loops skip the key.
The full argument401 words
  • Contract. QueryVisitor.consumeTerms: "Called by leaf queries that match on specific terms", "@param terms the terms the query will match on" (QueryVisitor.java:33-39). Term's constructor: "Note that a null field or null bytes value results in undefined behavior for most Lucene APIs that accept a Term parameter." (Term.java:47-48). The query builds that Term itself; the caller never does.
  • The replaced method had the check. The class's extractTerms had if (text != null) { terms.add(new Term(field, text)); } from the class's first commit (LUCENE-5815, 2014): first as the query's own method, and since LUCENE-6425 (2015, first released in 5.2.0) as TermAutomatonWeight.extractTerms. The change that added visit() (LUCENE-3041, 2019) removed that method on the main line and wrote the new loop without the check. CHANGES for 8.1.0 says of that change: "All locations in the code that called Weight.extractTerms() have been changed to use this API". The 8.x line kept both methods, and on the 8.1.0 and 8.11.4 jars they disagree on the same query object: extractTerms gives a and b, visit gives three terms, one without bytes (earlier runs).
  • Every sibling loop guards the marker: createWeight (TermAutomatonQuery.java:216-217), the Weight's constructor (:380-381), toDot (:330), rewrite (:539-545); finish() (:152-172) checks the any-term transitions on its own.
  • Legal input. addAnyTransition is one of the four builder methods the class javadoc names (:75-77). finish() checks any-term transitions and rejects only a leading or a trailing one (:152-172). TokenStreamToTermAutomatonQuery makes one from the token *, and its own exception message advises it: "cannot handle holes; to accept any term, use '*' term" (TokenStreamToTermAutomatonQuery.java:79). Upstream's testAnyFromTokenStream (TestTermAutomatonQuery.java:337) builds and searches such a query.
  • No test holds the behaviour. No upstream test reads the terms that TermAutomatonQuery.visit reports: TestTermAutomatonQuery has no direct call (the file's only visit is the empty one of a helper query, :626). A search does run visit, through the searcher's clause-count visitor (IndexSearcher.java:858, :896-901; on branch_11x :878, :916-921), which counts the calls and does not read the terms. No source of the highlighter or of the monitor names the class.
  • Not discussed. Of the 107 review comments of the pull request that added visit() (apache/lucene-solr#581), one is on this file, about the sub-visitor being requested inside the loop. None is about the any-term key.
The devil's-advocate check209 words

The strongest case for "intended": the class disclaims itself (@lucene.experimental, "This code is very new and likely has exciting bugs!", the sandbox module). Term permits null bytes and only warns. consumeTerms does not say that a term has bytes, so a visitor could be expected to be defensive, and the null term could be read as the class's marker for "any term". The change was reviewed by several people, and nobody objected to the loop.

Why it fails: the disclaimer is about quality, not a statement that this result is wanted; reported defects of this class were fixed (#12178 with #12208, 2023). Term's warning binds whoever builds the term, and that is visit(), not the caller. A term without bytes is no workable marker: its text() and toString() throw, and no visitor in the tree treats a term without bytes as an any-term marker (some take it without failing, because they do not read it: the searcher's clause count, the term collector). The nearest relative in the tree, the gap clause of SpanNearQuery, reports itself with visitLeaf and passes no term (SpanNearQuery.java:321-324). And the result the test expects was upstream's own until 2019. What the argument does carry is the weight: Low.

Suggested fix

#

Recommended A. Skip the null key in visit() (built and run on main and branch_11x)

Skip the null key in visit(): three lines. Run for this page on main and on branch_11x: the test passes, and for the example's query the term collector gets field:a and field:b, the highlighter returns <b>a x b</b> and the monitor registers it. On main, upstream's TestTermAutomatonQuery and the sandbox module's tests pass with it.

    for (BytesRef term : termToID.keySet()) {
      if (term != null) { // the null key stands for the any-term transition: it is no term
        v.consumeTerms(this, new Term(field, term));
      }
    }
All options and trade-offs3 options · 866 words

Option A was built and run. Options B and C were not built.

One limit of A, run for this page. It does not make every such query highlightable. For an automaton that rewrite() keeps (a, any term, b, or c alone), UnifiedHighlighter.highlight with A then reaches another, separate failure of the same class: IllegalStateException: Cannot call docFreq() when needsStats=false, thrown under createWeight when scores are not needed (in the Weight's constructor, TermAutomatonQuery.java:383). With A, the term collector gets that automaton's three terms and Monitor.register registers it; Monitor.match then reports the same other failure for the query, as it does on the unchanged build for a kept automaton without an any-term transition. That failure has its own cause and its own repair; with both repairs the highlighter returns the passage for such an automaton, without highlight marks (earlier runs).

Not run: the whole check task, modules other than sandbox with the fix, any machine other than Linux aarch64.

A. Skip the null key in visit() (built and run on main and branch_11x) (validated by the checks) (recommended)

#

In TermAutomatonQuery.visit (TermAutomatonQuery.java:578-580), pass a key to consumeTerms only when it is not null. The visitor then gets the query's real terms, which is what Weight.extractTerms gave before 2019. The file is the same on main and on branch_11x, so one patch applies to both.

    for (BytesRef term : termToID.keySet()) {
      if (term != null) { // the null key stands for the any-term transition: it is no term
        v.consumeTerms(this, new Term(field, term));
      }
    }

Trade-offs

  • The any-term position becomes invisible to visitors. A visitor sees a and b and nothing for the position between them. Option B is the alternative.
  • Not a cure for every highlighter call on this class: see the limit above.
  • One clause fewer in the searcher's clause count. visit calls consumeTerms once per key, and the searcher's clause-count visitor adds one per call (IndexSearcher.java:858, :896-901 on main; :878, :916-921 on branch_11x). With A an automaton that rewrite() keeps counts one clause fewer. It shows only at the limit: with IndexSearcher.setMaxClauseCount(2) the search of a, any term, b, or c alone throws TooManyNestedClauses without A and returns its hit with A (run on main and on branch_11x).
  • Safe for the monitor. With A the presearcher indexes the disjunction of the query's real terms (QueryAnalyzer.java:107-109, :113-117). Every accepted path has a real term, because finish() rejects a leading and a trailing any-term transition, so no matching document is filtered out (by reading). Run with A: the registered query a, any term, b matches the document a x b, does not match a b, and is not selected for x y z.
  • No cost: one comparison per key in a method that runs once per visit.

B. Also report the any-term transition to the visitor, in another way (not built)

#

Skip the null key for consumeTerms and tell the visitor about the any-term transition through consumeTermsMatching or visitLeaf. An executed second opinion raised this as a design choice for maintainers.

Trade-offs

  • A visitor that needs to know that the query can match terms it did not list would learn it.
  • It is not an equivalent form (by reading; not built or run). consumeTermsMatching calls visitLeaf by default (QueryVisitor.java:49-51). Through visitLeaf, UnifiedHighlighter.hasUnrecognizedQuery would count the query as having an unrecognized part (UnifiedHighlighter.java:1058-1078), which changes the branch at :1043. The monitor would make an any-term node (QueryAnalyzer.java:119-128) that replaces the disjunction of the terms (QueryTree.java:174-177), so the presearcher would select the query for every document.
  • The test holds for it: a term collector ignores both calls.

C. Guard the consumers against a term without bytes (not built, not suggested)

#

Make UnifiedHighlighter.filterExtractedTerms, the monitor's term weightor and QueryTermExtractor skip a Term whose bytes are null.

Trade-offs

  • It leaves the term without bytes in the visitor API for every other visitor.
  • The consumers trust the terms they are given, and they may: the defect is in the query's visit().

Downstream note

#

An application that builds this query from user text through TokenStreamToTermAutomatonQuery gets the any-term transition from a * token, where its analyzer keeps one, and highlighting that request then throws; no downstream product was run.

How it was found

#

By reading TermAutomatonQuery.visit while another failure of the same class was being checked: the loop passes every key of the term map to the visitor, and the key of the any-term transition is null. A probe on main, branch_11x and 10.6.0 confirmed it, and one test was reduced from it.

The method in full155 words

Method: non-formal (code reading, then an executed probe; no model checking, constraint solving or proof was involved).

  • Signal. While a failure of createWeight in the same class was being verified on the released lines, visit() was read: it is the only loop over the term map that does not skip the null key.
  • Probe. A term collector on the automaton a, any term, b got three terms, one without bytes, on main 781025d6fe32, branch_11x daa54f2e0cd3 and the 10.6.0 release jars. A second probe ran three faces (the collector, UnifiedHighlighter on a query that rewrite() turns into a phrase, and on one that it keeps) over 22 releases from 7.7.3 to 10.6.0 and both branches, which dated each face.
  • Reduction and separation. The probe became one JUnit test; a later check reduced it to one assertion. Runs with each repair alone and with both showed that this defect and the createWeight failure are separate.

History

#

Introduced in 8.1.0 by LUCENE-3041 "QueryVisitor" (2019), which wrote visit() without the null check that extractTerms had. Run on every release from 8.1.0 to 10.6.0, on branch_11x and on main: all fail. Since 9.5.0 (#11807) UnifiedHighlighter fails for every any-term query, before that only for automata that rewrite() keeps.

Versions tested9 rows

Introduced by LUCENE-3041 "QueryVisitor" (Alan Woodward; pull request apache/lucene-solr#581, merged 2019-03-14; issue #4114): ecf86ecab7a on branch_8x, first released in 8.1.0, and fbd05167f45 on the main line, first released on that line in 9.0.0.

  • What it changed here. It added visit() with a loop over every key of the term map and no null check. The method it stood in for, TermAutomatonWeight.extractTerms, had if (text != null). That check is in the class since its first commit (LUCENE-5815, 2014, first released in 4.10.0): first in the query's own extractTerms, and since LUCENE-6425 (2015, first released in 5.2.0) in the Weight's. The main-line commit removes extractTerms in the same diff. The branch_8x commit keeps it, so 8.1.0 to 8.11.4 carry both methods.
  • A dropped check, not a decision. The review of the pull request has one comment on this file, about the sub-visitor; none about the any-term key. The lines of visit() were not changed since.
  • A second date, the reach. #11807 "No need to rewrite queries in unified highlighter" (Alan Woodward; b3541204da1 on the 9.x line, first released in 9.5.0; 6bd8733fdbe on the main line, first released in 10.0.0) made the highlighter visit the query as given. Since then it fails for every any-term query; before, a query that rewrite() turns into a phrase was highlighted. That change is right in itself.
  • On the released lines and on both branches. On 10.6.0 the test fails with the same assertion as on branch_11x daa54f2e0cd3 and main 781025d6fe32, and the consumers throw the same exceptions. Nothing in 11.0 adds or changes it.

Registry title
Sandbox TermAutomatonQuery.visit gives the QueryVisitor a Term with null bytes for an any-term transition, so UnifiedHighlighter.highlight and Monitor.register throw NullPointerException for a query built with addAnyTransition or the any-term token '*', while its search returns the hit; visit since 8.1.0, UnifiedHighlighter for every such query since 9.5.0, through 10.6.0, branch_11x and main
Area
sandbox / search: TermAutomatonQuery.visit (seen through its consumers: highlighter / UnifiedHighlighter and monitor / query analysis)
Priority
Low, rank 692: UnifiedHighlighter throws NullPointerException when it highlights the hits of an experimental sandbox TermAutomatonQuery that has an any-term transition (every such query since 9.5.0, and since 8.1.0 those whose automaton rewrite() keeps), and so does registering such a query in a Monitor (executed on 9.4.0 and newer releases; older ones were not run), while the search of the same query returns its hits. crash

Summary
You build a TermAutomatonQuery for 'a', any term, 'b' (addAnyTransition, or the token '*' through TokenStreamToTermAutomatonQuery); searching with it returns the hit, and you then highlight the hit with UnifiedHighlighter, register the query in a Monitor or collect its terms with QueryVisitor.termCollector, expecting a snippet, a registered query or the terms a and b. The 10.6.0 release fails as branch_11x and main do: visit() does this in every release since 8.1.0, and UnifiedHighlighter fails for every such query since 9.5.0 (before that only for automata that rewrite() keeps).
