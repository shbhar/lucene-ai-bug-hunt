Luke: a sorted search ignores "exact hits count" and shows a lower-bound total ("1001+ hits")

In Luke's Search tab, picking a sort field ticks and locks the "exact hits count" box, yet a sorted search with more than 1,000 hits still shows a lower bound: "1001+ hits" for 1,001 matches, "8301+ hits" for 20,000. Since 8.7.0; the listed result pages are correct.

The finding in 30 seconds

#

The "exact hits count" flag reaches only Luke's unsorted search path. A sorted search goes through core's searchAfter, which counts exactly only up to 1,000 hits, so 1,001 matches come back as "1001+".

Background: exact and lower-bound hit counts

#
  1. To save work, a Lucene search may stop counting matches early. The total is then a lower bound (TotalHits relation GREATER_THAN_OR_EQUAL_TO), printed with a "+": "1001+ hits".
  2. IndexSearcher.searchAfter(after, query, n, sort) counts exactly up to 1,000 hits. A collector built with the threshold Integer.MAX_VALUE counts every hit.
  3. Luke's Search tab has an "exact hits count" box to ask for the full count. Choosing a sort field ticks the box and disables it.

The finding, step by step

#
  1. Index 1,001 documents with a numeric doc-values field n, open the index in Luke and pick n in the Search tab's Sort sub-tab. Luke ticks the "exact hits count" box and greys it out.
  2. Search *:*. You expect "Total docs: 1001 hits": Luke's sorted Search.search documents that with the flag set "the exact total hits count is returned".
  3. You get "1001+ hits", a lower bound. With a LongField sort field (points and doc values) and a term query matching all 20,000 documents, it shows "8301+ hits".
  4. Why: SearchImpl uses the flag only for unsorted searches. The sorted branch calls IndexSearcher.searchAfter(after, query, 10, sort), which since 8.7.0 counts exactly only up to 1,000 hits.
  5. The total is wrong, and its "+" also keeps Next enabled on the last page, where the companion bug LFV-1035 shows an empty page; the listed pages are correct. Giving the sorted branch the threshold the unsorted branch already uses fixes it; the Luke test suite passes.

Who is affected

#

People using the Luke desktop tool who sort a Search-tab query matching more than 1,000 documents: every such search since 8.7.0, with no setting that gives an exact sorted count. With points-indexed sort fields the number is far off. Result pages are correct; the index and core searches are unaffected.

Mechanism, terms and numbers508 words

Luke's Search tab ticks and disables its "exact hits count" checkbox whenever a sort field is chosen, and passes the flag to Search.search(query, simConfig, sort, fieldsToLoad, pageSize, exactHitsCount), whose javadoc says that with the flag set "the exact total hits count is returned". SearchImpl reads the flag only in its unsorted branch. The sorted branch calls IndexSearcher.searchAfter(after, query, pageSize, sort), which always counts with core's 1,000-hit threshold, so a sorted search over 1,001 documents shows "1001+ hits" next to the ticked, greyed-out box; with a points-indexed sort field (LongField) the shown value itself is far too low ("8301+ hits" for 20,000 matches). The Luke code dates from the module's import (8.1.0, 2019), when field-sorted counts were still exact; core's LUCENE-9449 made them a lower bound in 8.7.0, as documented, and Luke was not adapted. 8.6.3 passes; 8.7.0 to 10.6.0 and main fail. Building the sorted search's TopFieldCollectorManager with the unsorted branch's threshold fixes it; the whole Luke module's tests pass. Low priority: a displayed count in a desktop tool; the listed result pages, the index and core searches are unaffected, but the "+" also keeps Next enabled on the last page.

Mechanism (Lucene main 645d4fe14a20)

#
  1. The GUI forces the flag on. Choosing a sort field calls resetExactHitsCnt() (SortPaneProvider.java:201), which disables and ticks the box (:257-258). The Search tab passes the sort, page size 10 and exactHitsCntCB.isSelected() to the model (SearchPanelProvider.java:530-532).
  2. The contract. The Sort overload of Search.search says "exactHitsCount - if set to true, the exact total hits count is returned." (Search.java:104; the unsorted overload says the same at :85).
  3. The flag is read in one branch only. SearchImpl.search() (SearchImpl.java:308-320): the unsorted branch builds TopScoreDocCollectorManager(pageSize, after, exactHitsCount ? Integer.MAX_VALUE : 1000) (:316-318); the sorted branch calls searcher.searchAfter(after, query, pageSize, sort) (:314) and never looks at the flag.
  4. Core counts exactly only up to 1,000. searchAfter builds TopFieldCollectorManager(sort, n, after, TOTAL_HITS_THRESHOLD) with TOTAL_HITS_THRESHOLD = 1000 (IndexSearcher.java:100, :733). Below Integer.MAX_VALUE the collector is non-exhaustive (TopFieldCollector.java:349-350), and at hit 1,001 countHit sets GREATER_THAN_OR_EQUAL_TO (:83-88).
  5. The display. populateResults shows String.valueOf(res.getTotalHits()) (SearchPanelProvider.java:615), and TotalHits.toString() appends "+" for a lower bound (TotalHits.java:53-54): "Total docs: 1001+ hits".

How far off the number is

#
  • Doc-values-only sort field (NumericDocValuesField, the repro): every hit is still counted, so the value is right (1001) and only the "+" is wrong.
  • Sort field with points and doc values (LongField): once the threshold is reached the sort skips non-competitive documents, so counting stops early. A TermQuery matching every document, sorted with the Search tab's sort type, page size 10, exact on: "1010+ hits" for 1,010, "4102+ hits" for 5,000 and "8301+ hits" for 20,000 matching documents (a seeded shuffle of the values; the exact figures depend on the insertion order; the same with a core jar from upstream main 2f424fd428d).

Workaround

#

Clear the sort fields and tick the box: the unsorted branch counts exactly.

Exposure and likelihood286 words
  • Who. Users of the Luke desktop tool (bin/luke.sh, bin/luke.cmd in the binary distribution) who choose a sort field in the Search tab. Also code that calls Luke's Search model with a Sort and exactHitsCount=true, although that package calls itself "Models and internal APIs for Luke" and the Luke module exports no package.
  • Default vs opt-in. Sorting is the user's choice; once a sort field is chosen the exact count is requested automatically and cannot be turned off, so every sorted search over 1,000 hits is affected.
  • Scale. 1,001 matching documents are enough, a modest threshold for many indexes.
  • What is wrong. The total in "Total docs:", and, because of its "+", the end-of-results checks: Next stays enabled on the last page (SearchPanelProvider.java:621-623 enables it for any lower-bound total), and nextPage skips its end-of-results check, which runs only for an exact total (SearchImpl.java:344-346). So on the last page of a sorted search with more than 1,000 hits, clicking Next runs another search; that is where the companion LFV-1035 shows its empty page. With the recommended fix the total is exact and both checks work again. The listed pages are correct: the hunt's bounded model checks each returned page against a reference ranking in its configured scenarios, and fixing this root alone removes exactly the exact-count mismatches. Nothing in the index changes; core searches are not affected.
  • More than a "+". With a points-indexed sort field (for example LongField) the number itself is misleading: "8301+ hits" for 20,000 matches. Counting matches is a basic question people open Luke to answer.
  • Likelihood: plausible. Sorting is a secondary but normal Luke action, and 1,001 matching documents is a modest threshold for many indexes.

Why it looks unintended

#
  • The javadoc of the sorted Search.search says that with the flag set "the exact total hits count is returned", with no exception for sorts.
  • Luke ticks and locks the box for every sort, then shows "1001+ hits" next to it.
  • The code dates from 2019, when sorted counts were exact; core changed that in 8.7.0 and Luke was not adapted.
The full argument215 words
  • The contract. Both Search.search overloads document the flag the same way, "if set to true, the exact total hits count is returned" (Search.java:85, :104).
  • The GUI depends on it. SortPaneProvider.resetExactHitsCnt ticks and disables the box whenever a sort field is chosen (:256-258), so a ticked, greyed-out "exact hits count" sits next to "1001+ hits".
  • The intent, from history. The checkbox, the threshold in the unsorted branch only and the forced tick for sorts came together in the standalone Luke's DmitryKey/luke#163 (mocobeta, 2019-03-21; its body: "This also add a checkbox to the Search tab to return exact hit count (for backward compatibility)."), imported with LUCENE-2562 (3a78c1999a87, 2019-04-10, first release 8.1.0). Then a field-sorted searchAfter still counted every hit (unless it early-terminated on an index sort). LUCENE-9449 (99220677fe40, backport 75421682100, first release 8.7.0) made TopFieldCollector report GREATER_THAN_OR_EQUAL_TO for field sorts once the threshold is reached, as its CHANGES entry (8.7.0, API Changes) states; it touched no Luke file.
  • The announcement. The Luke 8.0.0 announcement on java-user@ describes the checkbox as being there "to return the accurate total hit count".
  • No test covers it. TestSearchImpl's index has 50 documents and testSearchWithSort's query matches 10 of them, far below the 1,000-hit threshold (TestSearchImpl.java:73-143, :305-315).
The devil's-advocate check191 words

The strongest case for "works as intended" (rated weak by the cross-model reviews, the independent reproducer and the devil's-advocate verifier; a later cross-model fact check rated it moderate): core's 1,000-hit threshold for sorted searchAfter is intended and documented, the "+" honestly marks the total as a lower bound, and Luke's models package calls itself internal.

Why it fails: that defends core, not Luke. Luke's own javadoc promises the exact count when the flag is set, Luke's own GUI sets the flag and locks it, and Luke's unsorted branch shows the intended handling of the same flag. The user asked for the exact count, is told they get it, and has no way to get it for a sorted search. "Internal" does not help either: the defect is visible in the GUI, and the repro uses the GUI's sort, page size and flag. The later fact check agreed that core's policy does not override Luke's own contract and locked box, but noted that the argument is fair grounds for Low priority, or for changing Luke's contract instead (the third fix option), rather than proof that the recommended fix is the only answer.

Suggested fix

#

Recommended Give the sorted branch the unsorted branch's threshold (validated)

In SearchImpl.search(), run the sorted search through a TopFieldCollectorManager built with the threshold the unsorted branch already uses (Integer.MAX_VALUE when the exact count is requested) instead of calling searchAfter. +10/-2 lines; the repro and the whole Luke test suite (98 tests, 0 failures) pass with assertions on and off.

int hitsThreshold = exactHitsCount ? Integer.MAX_VALUE : DEFAULT_TOTAL_HITS_THRESHOLD;
if (sort != null) {
  // searchAfter(after, query, n, sort) would count exactly only up to 1,000 hits
  int numHits = Math.min(pageSize, Math.max(1, searcher.getIndexReader().maxDoc()));
  topDocs =
      searcher.search(
          query,
          new TopFieldCollectorManager(
              sort.rewrite(searcher), numHits, (FieldDoc) after, hitsThreshold));
} else {

Trade-offs

  • One threshold rule for both branches; numHits and sort.rewrite mirror what searchAfter does internally.
  • With the exact count requested the collector is exhaustive, so sort skipping is off and a large sorted search is slower; TopFieldCollectorManager's javadoc warns exactly that, and the unsorted branch already pays the same cost when the box is ticked. With the flag off nothing changes (1,000 is core's threshold too).
  • Drops searchAfter's after.doc range check, which cannot fire here: after is the session's own last hit.

What the checks validated

  • Scratch worktree of 645d4fe14a20, gradle --offline, OpenJDK 25.0.3, seed DEADBEEF. Stock: the repro fails with assertions on and off.
  • With the fix: the whole :lucene:luke:test (12 suites, 98 tests, 17 skipped by TestDocumentsImpl's class-level @SuppressCodecs under this seed) passes with 0 failures with assertions on and off, TestSearchImpl 17 of 17 and the repro included; ecjLintMain, ecjLintTest, forbiddenApisMain, forbiddenApisTest pass; checkGoogleJavaFormat flags only the test's comment line, not SearchImpl.java.
  • The hunt's form of this fix (fully qualified class names) passed the repro and TestSearchImpl, and together with the companion paging fix made all 524,640 API call sequences and 37,952 GUI click sequences of the bounded model clean.

Keep searchAfter, then count exactly when needed (validated)

#

SearchImpl.java +4, after the searchAfter call: if exactHitsCount is set and the total is a lower bound, replace it with new TotalHits(searcher.count(query), TotalHits.Relation.EQUAL_TO).

Trade-offs

Keeps the fast, skipping top-k collection, but runs the query a second time whenever there are more than 1,000 hits (IndexSearcher.count is cheap for some queries through Weight#count, a full pass otherwise), again on every next page that has to be fetched; it overwrites the TopDocs field.

What the checks validated

The repro and TestSearchImpl with assertions on: 18 tests, 0 failures.

Change the contract instead (not run, not recommended)

#

Stop forcing the box on for sorts in SortPaneProvider and document on Search.search that sorted searches count exactly only up to 1,000 hits.

Trade-offs

Removes a documented feature: there would be no way to get an exact sorted count in Luke.

Downstream note

#

No downstream search path is affected: core IndexSearcher behaves as documented; only Luke's Search tab and code that calls Luke's internal Search model see the lower bound.

How it was found

#

A probe that clicks only the buttons Luke's Search tab enables saw sorted totals stay a lower bound with "exact hits count" on. A bounded-exhaustive enumeration of Luke's search and paging calls, checked against a reference written from the javadoc, then pinned it to the sorted branch.

The method in full159 words

Method: non-formal first signal, then semi-formal bounded-exhaustive checking.

  • Lead. An earlier probe drove Luke's Search model through only the clicks the Search tab enables and saw sorted totals stay GREATER_THAN_OR_EQUAL_TO with the exact flag on past 1,000 hits.
  • Enumeration. The finder enumerated every call sequence up to length 6 over search, next page and previous page (524,640 sequences over 480 configurations of hit count, page size, sort and segments) and every GUI click sequence up to length 5, on the stock jars, against a pager reference written from the javadoc and the GUI code. Every sorted configuration over 1,000 hits ignored the exact count. Fix variants separated this root from a companion paging bug, and a mutant reference showed the check is not vacuous.
  • Then executing cross-model reviews (OpenAI GPT-5.6), an independent reproducer, a devil's-advocate verifier, an adjudication, version-history runs from 8.6.3 to main, a prior-report search, a security screen, a credibility audit and this doc's gradle runs followed.

History

#

The sorted branch is as old as the Luke module (8.1.0, 2019), written when sorted counts were exact. Core's LUCENE-9449 made them a lower bound past 1,000 hits in 8.7.0; 8.6.3 passes, 8.7.0 through 10.6.0 and main fail. Not fixed upstream.

Versions tested9 rows

Luke code: LUCENE-2562 "Add Luke as a Lucene module" (3a78c1999a87 on main, 9915056cbc83 on branch_8x, Tomoko Uchida (mocobeta), 2019-04-10; first release 8.1.0), written in DmitryKey/luke#163 (2019-03-21). Exposed by LUCENE-9449 "Skip docs with _doc sort and 'after'" (99220677fe40, apache/lucene-solr#1725, mayya-sharipova, 2020-09-08; branch_8x backport 75421682100, #1856, first released in 8.7.0), an intended, documented core change that touched no Luke file. That #1856, not the LUCENE-9384 backport #1610 of the same release, causes the flip is by reading: #1610 is opt-in through SortField#setCanUsePoints, which Luke never calls. Between 8.6.3 and 8.7.0 Luke changes only one test file. On an index sorted by the sort field, early termination gave a lower bound before 8.7.0 too, so that narrower case reaches back to 8.1.0. Not fixed upstream: SearchImpl.java is identical on upstream main 2f424fd428d (2026-10-30) and branch_11x. Core's sort pruning changed there with PR #16857 (70a428b5ba9, merged 2026-10-29), which keeps IndexSearcher's 1,000-hit default and the relation flip in TopFieldCollector.countHit; with a core jar built from 2f424fd428d the repro still fails (fact check, mixed classpath).

Hits only people using the Luke desktop tool (lucene/luke, started with bin/luke.sh or bin/luke.cmd from the binary distribution) who choose a sort field in the Sort tab and run a search that matches more than 1,000 documents: the total is shown as a lower bound ('1001+ hits') next to a ticked, greyed-out 'exact hits count' box, and with a selective query on a sort field that also has points the number can be far below the real count (a scratch run by the independent reproducer on main: '8301+ hits' for 20,000 matches); the sorted result pages are correct, nothing in the index changes, core searches are not affected, no scale beyond 1,000 hits is needed, and every release since 8.7.0 has it.
Summary
You open an index in Luke, pick a sort field in the Sort tab (Luke then ticks and greys out 'exact hits count') and run a search that matches more than 1,000 documents; you expect the exact total, as the javadoc of the Sort overload of Search.search promises ('if set to true, the exact total hits count is returned'). Instead Luke shows a lower bound such as '1001+ hits', and there is no way to get the exact count of a sorted search. The cause is that SearchImpl.search() passes exactHitsCount only to the unsorted collector; the sorted branch calls IndexSearcher.searchAfter(after, query, pageSize, sort), which counts exactly only up to 1,000 hits.
