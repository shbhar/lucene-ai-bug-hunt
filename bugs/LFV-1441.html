MMapDirectory and FSDirectory constructors document a null lock factory that throws NullPointerException

The javadoc of new MMapDirectory(path, lockFactory, maxChunkSize) and of the protected FSDirectory(path, lockFactory) says null means "the default (NativeFSLockFactory)", but since 5.0 null throws NullPointerException. The code is right (5.0 made null illegal on purpose); only these two sentences were left behind.

The finding in 30 seconds

#

Both constructors hand lockFactory unchanged to BaseDirectory, whose only constructor throws NullPointerException for null (BaseDirectory.java:36-37). Nothing maps null to the default any more, so "or null for the default (NativeFSLockFactory)" at MMapDirectory.java:249-250 and FSDirectory.java:114-115 can never come true.

Background in two steps

#
  1. Every file-system Directory in Lucene (FSDirectory and its subclasses such as MMapDirectory) holds a LockFactory, which creates the write lock that keeps two IndexWriters off one index. The default is NativeFSLockFactory, returned by FSLockFactory.getDefault().
  2. Most code never picks one: FSDirectory.open(path), new MMapDirectory(path) and new MMapDirectory(path, maxChunkSize) use the default. Only the constructors that take a LockFactory argument let you choose.

The finding, step by step

#
  1. You want a custom mmap chunk size with the default locking, so, as the javadoc offers, you write new MMapDirectory(path, null, MMapDirectory.DEFAULT_MAX_CHUNK_SIZE).
  2. You expect a directory that locks with NativeFSLockFactory, the default that FSLockFactory.getDefault() returns.
  3. Instead the constructor throws NullPointerException: LockFactory must not be null, use an explicit instance! from BaseDirectory.java:37, with assertions on and off. No directory is returned, and a path that did not exist is not created.
  4. Why: Lucene 5.0 (LUCENE-5953) made null illegal and deleted "or null for the default" from five sibling constructors, but not from these two (MMapDirectory.java:249-250, FSDirectory.java:114-115). On 4.10.4 the same call worked.

Who is affected

#

Only code that calls the three-argument MMapDirectory constructor or writes an FSDirectory subclass, and passes null because the javadoc offers it. FSDirectory.open and the other constructors do not offer null. The failure is immediate and loud, its message names the fix, and no directory or missing path is created; every release since 5.0.0.

Mechanism, terms and numbers259 words

The public three-argument MMapDirectory(Path, LockFactory, long) constructor and the protected FSDirectory(Path, LockFactory) constructor for subclasses both document @param lockFactory the lock factory to use, or null for the default ({@link NativeFSLockFactory});. That was true up to 4.10.

Since 5.0 (LUCENE-5953, #7015) null is rejected on purpose: both constructors pass the argument straight up to BaseDirectory, which throws NullPointerException("LockFactory must not be null, use an explicit instance!"), so no directory is returned. LUCENE-5953 deleted the same clause from five sibling constructors and missed these two. The failure is immediate, its message points to the fix, and a path that did not exist is not even created; the fix is to delete the clause from both javadocs.

The mechanism

#
  1. MMapDirectory.java:249-250 and FSDirectory.java:114-115 carry the stale @param lockFactory the lock factory to use, or null for the default ({@link NativeFSLockFactory});. These two lines are the fix sites.
  2. MMapDirectory(Path, LockFactory, long) calls super(path, lockFactory) (MMapDirectory.java:256); FSDirectory(Path, LockFactory) calls super(lockFactory) (FSDirectory.java:119), before Files.createDirectories (:122-124), so a path that did not exist is not created.
  3. BaseDirectory(LockFactory), documented only as "Sole constructor." (BaseDirectory.java:33-40), throws NullPointerException("LockFactory must not be null, use an explicit instance!") for null (:36-37).
  4. The siblings document no null: the two-argument MMapDirectory (MMapDirectory.java:203), NIOFSDirectory (NIOFSDirectory.java:55) and misc RAFDirectory say only "the lock factory to use"; FSDirectory.open(Path), MMapDirectory(Path) and MMapDirectory(Path, long) pass FSLockFactory.getDefault() themselves (FSDirectory.java:151, MMapDirectory.java:218, :231).
  5. git grep 'null for the default' over lucene/ finds only the two stale lines.
Exposure and likelihood179 words
  • Who: code that calls the public three-argument MMapDirectory constructor (the one way to set a chunk size together with a lock factory) or writes an FSDirectory subclass, and passes null because the javadoc says so. Passing null was still a habit when LUCENE-5953 landed: that day Lucene's own nightly TestLockFactory still passed a null lock factory (to its test helper newFSDirectory, not to these two constructors), failed, and was fixed (e8144f986b4, "LUCENE-5953: Fix null lock factory").
  • Not hit: FSDirectory.open(...), new MMapDirectory(path), new MMapDirectory(path, maxChunkSize) and the public two-argument constructors (MMapDirectory, NIOFSDirectory, misc RAFDirectory), the common entry points; none of them documents null. No in-tree caller passes null; Solr's MMapDirectoryFactory passes its own lock factory.
  • Effect: one exception at construction, with a message that names the fix; no directory is returned and a path that did not exist is not created; no wrong result, no silent fallback.
  • Scale: deterministic, one call. Every release from 5.0.0 to 10.6.0, and main. No public report found (searches of 2026-11-09 and 2026-11-10, see Prior reports).

Why it looks unintended

#
  • The code is intended: 5.0 made null illegal on purpose, and its MIGRATE notes say so and point to FSLockFactory.getDefault().
  • That same change deleted "or null for the default" from five sibling constructors and missed these two.
  • Nothing current contradicts the two sentences, so a reader has only the wrong text.
The full argument151 words

The claim is only that the two sentences are wrong; nobody proposes to change the code.

  • Null was made illegal on purpose. The 5.0 MIGRATE.txt: "It is no longer allowed to pass "null" as LockFactory to FSDirectory implementations. You have to explicitely pass the platform default to the directory (currently always NativeFSLockFactory.INSTANCE, but subject to change!). To get the platform default, call FSLockFactory.getDefault()."
  • The same commit removed this exact clause from five constructors (two-argument MMapDirectory, NIOFSDirectory, SimpleFSDirectory, misc RAFDirectory and WindowsDirectory) and left it on the three-argument MMapDirectory and on FSDirectory.
  • The text was true when written (LUCENE-1877, 2009; LUCENE-4364, 2012), when FSDirectory still did if (lockFactory == null) lockFactory = new NativeFSLockFactory(). On 4.10.4 the documented call works.
  • Nothing current says otherwise: main's MIGRATE.md has no lock factory note, BaseDirectory's constructor javadoc says only "Sole constructor.", and no test asserts either way.
The devil's-advocate check80 words

The rejection is deliberate and was announced in 5.0; the failure is immediate, clearly worded and side-effect free; both constructors are specialised (no in-tree caller passes null); so this is a cosmetic nit.

Why it still counts, as a small cleanup: that defends the runtime, which nobody proposes to change. It does not defend public javadoc that promises a working directory for an argument that always throws. What remains is impact, which is small: that is why this is Low.

Suggested fix

#

Recommended A. Delete the clause from both javadocs (validated)

Delete the clause, as LUCENE-5953 did for the sibling constructors: both @param lines become @param lockFactory the lock factory to use. Behaviour is unchanged; with the change, six store suites (218 tests), google-java-format, ecjLint and the javadoc build of lucene/core pass.

A. Delete the clause from both javadocs (validated) (recommended)

-   *     NativeFSLockFactory});

  • The same wording the sibling constructors have on main (MMapDirectory.java:203, NIOFSDirectory.java:55, misc RAFDirectory.java:53).

B. Say what to pass instead

#

For example "the lock factory to use; must not be null (use {@link FSLockFactory#getDefault()} for the default)".

Trade-offs

A real alternative: it states the precondition and the remedy, which helps the reader more, but differs from the siblings' wording (a reviewer may want all five changed alike), and google-java-format may rewrap it. By reading, not run.

C. Accept null again (not recommended)

#

Map null to FSLockFactory.getDefault() in the constructor.

Trade-offs

Makes the javadoc true and the repro pass, but reverses a deliberate, announced 5.0 decision and splits behaviour between sibling constructors. By reading, not run.

Downstream note

#

Downstream code that sets an mmap chunk size or subclasses FSDirectory should pass FSLockFactory.getDefault() instead of null; the constructor fails closed: a null lock factory never yields a directory (it throws before anything is created).

How it was found

#

Semi-formal: a proof-obligation audit checked each argument value the FSDirectory and MMapDirectory constructors document against BaseDirectory's argument check. The documented null has no code path that honours it, and a one-test JUnit on stock main witnessed the NullPointerException.

The method in full83 words
  • Obligation: for every argument value a constructor's javadoc allows, construction succeeds with the documented effect; here, a null lockFactory yields a directory that uses NativeFSLockFactory.
  • Finding: both constructors pass the argument unchanged to BaseDirectory, whose only constructor throws for null, so the obligation cannot be met.
  • Witness: a one-test JUnit on stock main, then an independent reproduction, an executed review by a model from another family (OpenAI GPT-5.6) under a refute and an intended lens, an intended-behaviour review and an adjudication.
