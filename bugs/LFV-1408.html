A JoinUtil term join that hit the searcher timeout equals the complete join, so the query cache gives its partial hits to later searches

A JoinUtil term join cut short by IndexSearcher#setTimeout holds fewer keys yet equals the complete join, since equality compares the reader, not the keys. A shared query cache serves its partial hits to later score-free searches (counts, filters) without a timeout: 0 of 1 in the repro, 50 of 12,000 with 10.6.0 defaults.

The finding in 30 seconds

#

Term joins identify themselves by the reader they were built on instead of the keys they collected. That was safe while a from-side search on one reader always found the same keys. Since 9.3.0 a timeout can cut that search short, so a partial join and the complete join compare equal and share one cache entry.

Background: term joins, the query cache and the searcher timeout

#
  1. A term join runs in two halves. JoinUtil.createJoinQuery searches the "from" side with fromQuery and collects the join keys (the from field's values); it returns a query that matches the "to" documents having any of those keys.
  2. The query cache stores, per segment, the documents a query matches, keyed on the query's equals and hashCode. A later query that is equal gets the stored documents instead of running. It is used when the query runs without scores: a count, a filter clause, a search sorted by a field.
  3. IndexSearcher#setTimeout (since 9.3.0) makes a search that passes its deadline stop early and return what it found; timedOut() then reports true on that searcher.

The finding, step by step

#
  1. Index 1 "from" document with join key a and 1 "to" document with key a. Two IndexSearchers on one reader share one query cache.
  2. Search 1 has a timeout that has already passed. It builds the join with JoinUtil.createJoinQuery and runs count(): the from-side search stops at once, the join holds 0 keys and counts 0 (documented timeout behaviour).
  3. Search 2 has no timeout and builds the same join, which holds the 1 key. You expect count() to return 1, as it does without the cache.
  4. Instead it returns 0, and timedOut() is false. The two joins compare equal, since equality checks the reader and the from-query but not the keys, so the cache hands search 2 the empty entry search 1 left.
  5. With the 10.6.0 defaults (no cache configured; two segments of 12,000 documents), one timed-out request made the next normal request return 50 of 12,000 hits.

Who is affected

#

Applications that use JoinUtil term joins with IndexSearcher#setTimeout and run them as counts, filters or score-free searches through a query cache shared by later requests. In 9.3.0-10.6.0 the default searcher cache is enough; on main only an installed cache. Later requests that never timed out silently lose hits until the reader is reopened or the entry is evicted or cleared.

Mechanism, terms and numbers655 words

JoinUtil.createJoinQuery (the term variant) first searches the from side with fromQuery and collects the join keys, then returns a TermsQuery (ScoreMode.None) or a TermsIncludingScoreQuery (Total, Max, Min, Avg) that matches the to documents with any of those keys. Their equals and hashCode compare the fields, the fromQuery and the from searcher's top reader-context id, never the collected keys: the id stands in for the keys, which is sound only while a from-side search on one reader always collects the same keys.

Since 9.3.0, IndexSearcher#setTimeout lets that search stop early and return normally. A join built while the timeout fired holds fewer keys, yet it equals the complete join built on the same reader. The query cache keys its per-segment entries on query equality, so whichever of two equal joins fills an entry first decides what every later equal join on that reader gets when it runs without scores (the cache wraps only score-free weights), until the reader is reopened, the entry is evicted or the cache is cleared. A search that never timed out then silently loses hits and reports timedOut() false. The timed-out search's own partial result is documented and is not the bug.

Scope. Every term join: TermsQuery for ScoreMode.None, TermsIncludingScoreQuery for Total, Max, Min and Avg, single- and multi-valued. Not affected, by reading (not executed): the numeric joins (they compare the collected points), the global-ordinals joins (their weights are not cacheable) and the block joins (they collect nothing when the query is built and compare the queries and filter they wrap; the block-join kNN queries rewrite to a DocAndScoreQuery that compares its documents and scores). The equality violation exists without any cache (equal queries whose uncached counts are 0 and 1); only the cache face was executed.

Exposure and likelihood329 words
  • Who is hit. Applications that build JoinUtil term joins (createJoinQuery with a term from-field, any ScoreMode, single- or multi-valued), set IndexSearcher#setTimeout on the from searcher, and run the joins in a non-scoring role (counting, filtering, field-sorted or score-free searches) through a query cache shared by later requests on the same reader. The request that gets wrong hits never timed out and reports timedOut() false, so the application cannot tell.
  • Default vs opt-in. The timeout is opt-in. In 9.3.0-10.6.0 nothing else is needed: IndexSearcher has a static default LRUQueryCache (1,000 queries, at most 32 MB; segments of at least 10,000 documents that hold more than half the average segment size), and the default UsageTrackingQueryCachingPolicy caches a TermsQuery (a MultiTermQuery) from its second use. On main and branch_11x the default cache is off since #14187 (2025, not yet released), so only an installed cache is affected; with the 10.x default cache installed on main the same 50 of 12,000 result appears.
  • When it bites. The timed-out request must be the one that fills the entry (with the default policy: a join repeated on a reader that times out on its second or a later use before an equal join was cached). The deadline has to pass during the from-side collection, as in the repro and the 10.6.0 defaults run. Once filled, the wrong entry serves every equal join (same to-field, from-field and from-query) that runs without scores on that reader, until the reader is reopened, the entry is evicted or the cache is cleared (LRUQueryCache#clear, #clearQuery).
  • Scale. Ordinary: 1 from and 1 to document with an always-cache policy; two 12,000-document segments with the 10.6.0 defaults.
  • kNN from-query. With a KnnFloatVectorQuery as fromQuery, even the timed-out request reports timedOut() false (LFV-115), and the later request still gets 0 of 1 (executed on main and 10.6.0).
  • Narrow population. JoinUtil is @lucene.experimental, the timeout is opt-in, and the recorded searches found no report of it since 9.3.0.

Why it looks unintended

#
  • Query.equals "is required so that QueryCache works properly"; equal queries should filter the same documents, yet these two match 0 and 1.
  • The reader id stood in for the keys (#8861, 2017), sound only while a from-side search always completed; setTimeout (9.3.0) ended that.
  • The victim never timed out and reports timedOut() false; no doc or test accepts that.
The full argument334 words
  • Contract. Query.java:95-102: "Override and implement query instance equivalence properly in a subclass. This is required so that QueryCache works properly. Typically a query will be equal to another only if it's an instance of the same class and its document-filtering properties are identical to those of the other instance."
  • JoinUtil's own doc. JoinUtil.java:64-66: "Execute the returned query with a IndexSearcher to retrieve all documents that have the same terms in the to field that match with documents matching the specified fromQuery and have the same terms in the from field."; the package doc lets the returned query run "with the same IndexSearcher, but also with another IndexSearcher" (package-info.java:84-87); the TermsQuery constructor says the id "Refers to the top level index reader used to create the set of terms" (TermsQuery.java:57-58).
  • Timeout doc. "Set a QueryTimeout for all searches that run through this IndexSearcher" (IndexSearcher.java:612); timedOut() "Returns true if any search hit the timeout" (:647). Partial results are documented for the searches that timed out, not for later ones; no JoinUtil, timeout or cache doc says a join built during a timeout must not be run or cached.
  • Tests. TestJoinUtil.testEquals asserts "identical calls to createJoinQuery" are equal; it stays green with the fix. No JoinUtil test uses a timeout (in the join module only the block-join kNN tests set one).
  • History. On #8861 (2017) the stand-in was chosen because "equality checking the collected terms would be too expensive" (martijnvg), while jpountz wrote that "two queries should only be equal if they matche the same docs and give them the same scores". Then a from-side search could not silently stop: TimeLimitingCollector and ExitableDirectoryReader abort with an exception. #927 (2022, 9.3.0) made silent partial results normal; neither it nor its issue #11188 discussed joins or query identity. They did touch the query cache: Greg Miller's #11188 asks that filling the cache "shouldn't be allowed to overrun the timeout" (a time-bound concern), and jpountz's #927 review is answered below.
The devil's-advocate check281 words

The strongest case: the stand-in is a deliberate speed trade-off, and on #9771 (2019) jpountz called TermsQuery "cheating a bit in its equals/hashCode to be cacheable without having to actually compare the BytesRefHash"; JoinUtil is experimental; main has the cache off; a scored top-level search of the join is not affected; and an application can check timedOut() before running the join. In the #927 review (2022-06-01) jpountz proposed the getter that became timedOut() because "This is important, e.g. to let the user know that some matches were skipped or to know if it's safe to cache results." A maintainer may therefore see a join built by a timed-out search as tainted, for the application to discard.

Why it fails: the trade-off was correct when it was made, because one reader always gave the same keys; setTimeout broke that premise five years later, and no later discussion of join identity was found. jpountz's remark is about an application deciding whether to cache the timed-out search's own results; here Lucene's own query cache stores the partial entry while the join runs, without looking at the flag, and serves it to a different search that never timed out and cannot detect it. To avoid that the application would have to check timedOut() between building and running the join (a timed-out join that is never run leaves the next request correct, executed); nothing in the javadoc asks for that check, it does not help with a kNN from-query, where the flag stays false (LFV-115), and a ScoreMode.Max partial join run on a searcher with no timeout poisons the entry too (executed, the devil's-advocate verifier's controls). The cross-model reviewer rated this case moderate and rejected it.

Suggested fix

#

Recommended A: compare the collected terms (and per-term scores) in equals/hashCode

Make the collected keys part of equals/hashCode: hash the sorted terms once in the constructor, compare them on a hash match, and in TermsIncludingScoreQuery also compare the per-term scores (+51/-4, two files). The repro passes, and so do the whole :lucene:join:test (105 tests) and the format check.

All options and trade-offs3 options · 644 words

One fix was validated with the repro and the whole join module's tests; two alternatives are described, not executed. None has been reviewed upstream. Open PR #16805 rewrites the same JoinUtil method and keeps the reader-context id identity.

A: compare the collected terms (and per-term scores) in equals/hashCode (validated by the checks) (recommended)

#

TermsQuery computes a hash of its sorted collected terms once in the constructor (after terms.sort(), which it already does); equals adds the hash and, on a match, a term-by-term comparison; hashCode adds the hash. TermsIncludingScoreQuery reuses the two helpers and also compares the per-term scores with Float.compare. The reader-context id stays, so joins on different readers never share an entry.

   // TermsQuery
+  private final int termsHash; // hash of the collected terms in sorted order
     ords = terms.sort();
+    this.termsHash = hashTerms(terms, ords);
-        && Objects.equals(indexReaderContextId, other.indexReaderContextId);
+        && Objects.equals(indexReaderContextId, other.indexReaderContextId)
+        && termsHash == other.termsHash
+        && sameTerms(terms, ords, other.terms, other.ords);
-    return classHash() + Objects.hash(field, fromField, fromQuery, indexReaderContextId);
+    return classHash() + Objects.hash(field, fromField, fromQuery, indexReaderContextId, termsHash);
   // TermsIncludingScoreQuery: the same, plus sameScores(other)

Trade-offs

  • One O(#terms) pass at construction, right after the constructor's ords = terms.sort() (TermsQuery.java:68, TermsIncludingScoreQuery.java:75); equals stays O(1) on a hash mismatch and is O(#terms) on a match (a cache lookup of a truly equal join).
  • Equal joins stay cacheable (in the bounded check 190 truly equal pairs stay equal).
  • It does not depend on timedOut(), so it also covers the kNN from-query, where timedOut() stays false.
  • By reading, it also separates two joins that differ only in multipleValuesPerDocument (which equality ignores) when they collect different terms: on a SORTED from field the single-valued collector adds the empty term for a matching from document without a value, the multi-valued one adds nothing; not executed.
  • Not covered: multipleValuesPerDocument stays out of TermsIncludingScoreQuery equality. By reading, it also picks the scorer: SVInOrderScorer gives a to-document matching several terms the last one's score, MVInOrderScorer the first's. Two joins with the same terms and scores but different flags stay equal yet can score such a document differently: a separate, score-only question (scored weights are not cached); not executed.

B: make the term-join weights non-cacheable

#

Return false from Weight#isCacheable for term joins, as jpountz suggested on #9771 in 2019 ("If we were to do this again today, maybe we'd consider disabling caching instead").

Trade-offs

Closes the cache face but gives up caching for every term join, and leaves the equality wrong for other users of equals (for example clause de-duplication). The cached weight of TermsQuery comes from the core MultiTermQuery rewrite wrapper, so this is not a one-line change in the join module. A maintainer may reasonably prefer it: it is conservative for the cache and adds no O(#terms) work to equals. Not executed.

C: have JoinUtil read fromSearcher.timedOut() (not recommended)

#

Return a join that never equals a complete one, or throw, when the from-side search timed out.

Trade-offs

Misses the kNN from-query, where timedOut() stays false (LFV-115), and timedOut() is sticky per searcher (partialResult is never reset), so an earlier unrelated timeout on the same searcher would also mark the join. Not executed.

Downstream note

#

A product that shares readers and a query cache across users and runs term joins as filters under a request timeout can return incomplete filtered results to other users' normal requests.

How it was found

#

Semi-formal: a model-based test of reader-keyed caching flagged a term join answered from the shared cache with fewer hits after a timed-out join. A bounded-exhaustive check of the Query equality contract over 200 generated joins then found 210 equal pairs with different hits, and a deterministic JUnit test followed.

The method in full95 words

The model-based test's term-join operation ran a join through a shared LRUQueryCache after a timed-out join and saw the later join get fewer hits; a skeptic re-ran and minimised it. The bounded-exhaustive check (a translation validation of the Query identity contract on the stock f794ff5a505c jars) ran 200 joins, 400 pairs and 800 cache cases: 210 equal pairs with different hits and 420 cache cases with a wrong count, 120 of them giving fewer hits to the join built without a timeout; with the fix, 0 violations. The one-method JUnit test was written from that.

History

#

Activated in 9.3.0 by #927 (af05550ebfe, 2022), which let IndexSearcher#setTimeout stop a search silently; the equality stand-in dates from #8861 (85c1319c767, 6.6.0, 2017). The test fails on 9.3.0, 9.12.3, 10.0.0, 10.5.2, 10.6.0 and main; 9.2.0 has no setTimeout. Not fixed upstream.

Versions tested6 rows

#927 (LUCENE-10151 "Adding Timeout Support to IndexSearcher", Deepika0510, af05550ebfe, 2022-06-29; branch_9x cherry-pick aa082b46f66, committed 2022-07-15; first released in 9.3.0) made a silently partial search normal API behaviour. The fix site is older: 85c1319c767 (LUCENE-7810, #8861, Martijn van Groningen, 2017-05-22, 6.6.0; branch_6x pick 7f62567609e) made the top reader-context id a stand-in for the collected terms. Before it 6b3823e6a39 (LUCENE-4704, 2013; 4.2.0 pick 74933e3c714) made TermsQuery compare fromQuery on top of MultiTermQuery equality (class, boost, rewrite method, field) and TermsIncludingScoreQuery its field and original from query; in 4.0.0-4.1.x TermsQuery used MultiTermQuery equality and TermsIncludingScoreQuery had no equals of its own. The collected terms were never compared. A two-commit interaction, not a regression of working behaviour. By reading, all 31 releases 9.3.0-10.6.0 have the same equality lines and the same silent catch, and so do branch_10_6 and branch_11x. Zero-configuration reach: 9.3.0-10.6.0 (default cache); main and the unreleased 11.0 only with an installed cache (#14187, 26387b4b00e, 2025-04-02). LFV-1408, snapshot of 2026-11-09

Registry title
JoinUtil term joins (TermsQuery, TermsIncludingScoreQuery) compare equal on the from searcher's reader-context id instead of the collected terms, so after a join whose from-side search hit IndexSearcher#setTimeout, a shared query cache serves the partial join's hits to later requests that did not time out
Area
join / JoinUtil term joins (query identity) and the query cache under IndexSearcher#setTimeout
Priority
Medium, rank 89: In every release from 9.3.0 to 10.6.0, the default shared query cache can keep the partial hits of a JoinUtil term join whose from-side search hit the opt-in IndexSearcher timeout and serve them to later requests on the same reader, which silently lose hits while timedOut() is false, until the reader changes or the entry is evicted. It is Medium because it needs the experimental join module, setTimeout and a timeout on the request that fills the cache entry (with the default policy, a join repeated on segments of at least 10,000 documents), and on unreleased main also a query cache the application installs.
Impact class
silent wrong results
Impact note
Applications that build JoinUtil term joins (createJoinQuery on a term field, any ScoreMode, single- or multi-valued; not the numeric, global-ordinals or block joins) on an IndexSearcher with setTimeout and run them through a query cache that later requests on the same reader share, which in 9.3.0-10.6.0 the default IndexSearcher setup already is (a static LRUQueryCache with UsageTrackingQueryCachingPolicy; executed on 10.6.0: one timed-out request made the next normal request return 50 of 12,000 hits) and on main only an application-installed cache is (#14187); ordinary scale (one from and one to document with an always-cache policy; two 12,000-document segments with the default cache settings); the wrong entry is served, with timedOut() false for the victims, until the reader changes or the entry is evicted; released 9.3.0-10.6.0.
Summary
You run a JoinUtil term join on an IndexSearcher with setTimeout, the deadline passes while the join collects its from-side terms, and later requests build the same join on the same reader without any timeout, all sharing one query cache (the IndexSearcher default in 9.3.0-10.6.0). You expect every later request to get the complete join's hits, as it does without the cache. Instead the partial join compares equal to the complete one, because TermsQuery and TermsIncludingScoreQuery compare the from searcher's reader-context id rather than the collected terms, so the cache hands the later requests the partial join's hits (0 instead of 1 in the repro, 50 of 12,000 with the 10.6.0 defaults) while their timedOut() is false.

The defective equality, which is the fix site, is older: 85c1319c767 (LUCENE-7810, #8861, by martijnvg; branch_6x 7f62567609e; 6.6.0) added the from searcher's top reader-context id as a deliberate stand-in for the collected terms, sound while a from-side search on one reader was always complete [read: git log -S indexReaderContextId]; the collected terms were never compared (4.0.0-4.1.x inherited MultiTermQuery equality, 7cdb8028c10 LUCENE-3602; 4.2.0-6.5.x compared fromQuery, 6b3823e6a39 LUCENE-4704). A two-commit interaction, not a regression of working behaviour.
