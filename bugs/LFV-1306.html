After prepareCommit() and rollback(), an IndexWriter opened from an NRT reader's commit shows the deletion policy the newest commit twice, so KeepLastNCommitsDeletionPolicy(2) deletes a commit it should keep

Abort a prepared commit with rollback(), then open a new IndexWriter from an earlier NRT reader's commit: the deletion policy's onInit is given the newest commit twice. With KeepLastNCommitsDeletionPolicy(2) and 2 commits on disk, opening the writer silently deletes segments_1, leaving 1.

The finding in 30 seconds

#

Opening a writer from an NRT reader after an aborted prepared commit makes the deletion policy see the newest commit twice.

Two generation numbers

#
  1. Each commit is a file segments_N; N is its generation. A writer's SegmentInfos tracks two numbers: lastGeneration, the commit it is on, and generation, the last number it reserved for writing.
  2. prepareCommit() reserves N+1 and writes pending_segments_N+1. rollback() deletes that file, but the closed writer still holds the reserved number N+1 next to the commit it is on, N.
  3. When a writer opens, IndexFileDeleter lists the commits in the directory and hands them, oldest first, to the deletion policy's onInit, which may delete some.

The finding, step by step

#
  1. A writer that keeps every commit commits twice: segments_1 and segments_2. Open an NRT reader on it, add a document, call prepareCommit() and then rollback(). The directory still holds exactly those 2 commits.
  2. Open a new IndexWriter with setIndexCommit(nrtReader.getIndexCommit()) and KeepLastNCommitsDeletionPolicy(2).
  3. You expect both commits to stay: the policy keeps the last 2 and there are 2, so DirectoryReader.listCommits should give generations [1, 2].
  4. Instead it gives [2]. The new writer inherited generation 3, reserved by the aborted prepare, next to the current file's generation 2. IndexFileDeleter looks for commit 3, finds none, and a fallback meant for stale directory listings adds segments_2 again: onInit gets [1, 2, 2] and the policy deletes entry 0, segments_1.
  5. No exception, no log line without infoStream. The newest commit and the index content are intact; only the older commit the policy promised to keep is gone.

Who is affected

#

Applications that abort a prepared commit with rollback(), then open a new writer from an earlier NRT reader's commit (the Expert setIndexCommit path), and keep the last N >= 2 commits by count (the shipped KeepLastNCommitsDeletionPolicy, 10.3.0+, or a custom policy, also inside a snapshot policy). The default policy shows nothing. Every release since 5.3.0; rare.

Mechanism, terms and numbers571 words

When an IndexWriter opens, IndexFileDeleter lists the commits in the directory and hands them to the deletion policy's onInit. After a prepared commit was aborted with rollback(), a writer opened from an earlier NRT reader's commit (IndexWriterConfig.setIndexCommit(reader.getIndexCommit())) inherits the closed writer's two generation numbers: 3, the one the aborted prepare reserved, and 2, the commit it is on. IndexFileDeleter names the current segments file from 2 but matches the current commit by 3, finds no match, and its stale-listing fallback appends segments_2 a second time. onInit gets [1, 2, 2], and KeepLastNCommitsDeletionPolicy(2) deletes segments_1, a commit it should keep. Nothing fails; the newest commit and the index content are intact. Every release since 5.3.0; a one-line fix (compare with getLastGeneration()) passes the repro and the org.apache.lucene.index tests.

The mechanism (main 5adff78bb168)

#
  1. prepareCommit() writes pending_segments_3 and moves generation to 3 (SegmentInfos.java:612); startCommit copies it to the writer "on error or success" (IndexWriter.java:6024-6028). In a commit, lastGeneration moves only when the commit finishes (SegmentInfos.java:1021), so it stays 2.
  2. rollback() deletes pending_segments_3 (IndexWriter.java:2643) and keeps both numbers (:2655). The directory holds segments_1 and segments_2; the closed writer has generation 3, last generation 2 (an infoStream diagnostic on main printed exactly this).
  3. Opening a writer from an NRT reader of that closed writer copies both numbers "so we remain write-once" (IndexWriter.java:1068-1069, updateGenerationVersionAndCounter).
  4. IndexFileDeleter names the current segments file from lastGeneration, segments_2 (IndexFileDeleter.java:120, SegmentInfos.java:251-253), but marks a listed commit as current only if sis.getGeneration() == segmentInfos.getGeneration() (:164): 1 == 3 and 2 == 3 both fail.
  5. With no current commit found, the fallback commented as being for a stale directory listing ("eg when index accessed via NFS", :179-200) reads segments_2 again and appends a second entry. policy.onInit(commits) (:237) gets [1, 2, 2].
  6. KeepLastNCommitsDeletionPolicy.onInit calls onCommit, which deletes every entry but the last N (KeepLastNCommitsDeletionPolicy.java:45-57): entry 0, segments_1.

A SegmentInfos read from a commit has generation == lastGeneration (SegmentInfos.java:361-362). On the other open paths either the two numbers agree, or generation is the newest listed commit: with setIndexCommit to an older commit K, segmentInfos.replace sets lastGeneration to K and keeps the newest commit's generation (SegmentInfos.java:1088-1092, IndexWriter.java:1085-1104), so the match still finds a listed commit and no duplicate appears. Only the open-from-reader path added in 5.3.0 (LUCENE-6524), which copies a closed writer's split numbers, can carry a generation that no commit on disk has.

It lasts beyond the open

#

The duplicate stays in the writer's commit list, so the policy keeps one commit fewer than configured at the open and for the next N-2 commits (with N = 2 only at the open; with N = 3 also after the next commit). Probes with KeepLastNCommitsDeletionPolicy(N) and N commits, listCommits at open and after each next commit: N = 2 [2], then [2, 4]; N = 3 [2, 3], then [3, 5], [3, 5, 6]; N = 4 [2, 3, 4], then [3, 4, 6], [4, 6, 7], [4, 6, 7, 8]. With the fix N = 3 gives [1, 2, 3], then [2, 3, 5]. The generation missing from each sequence (e.g. 4 for N = 3) is the one the new writer inherited from the aborted prepare.

Exposure and likelihood263 words
  • What is lost: an older point-in-time commit the configured policy promised to keep. Applications that keep the last N commits for backups, replica recovery or point-in-time readers lose that margin silently: no exception, and no log line unless infoStream is on.
  • What is not affected: the newest commit and the index content. With the default KeepOnlyLastCommitDeletionPolicy, onInit also gets [1, 2, 2] but nothing visible follows (commits after open [2], a later commit works, 3 documents, CheckIndex clean); NoDeletionPolicy and a snapshot policy wrapping the default policy likewise, because both entries for segments_2 hold the same file references.
  • Snapshot policies pass it on: SnapshotDeletionPolicy.onInit hands the list to its primary policy (SnapshotDeletionPolicy.java:70-72; PersistentSnapshotDeletionPolicy extends it). Wrapping a count-based policy, it loses the commit too: new SnapshotDeletionPolicy(new KeepLastNCommitsDeletionPolicy(2)) gets [1, 2, 2] and keeps [2]; with the fix [1, 2].
  • What it takes: all of these together: an aborted prepared commit (prepareCommit() then rollback()), an NRT reader of that writer opened before the rollback (opened between prepareCommit() and rollback() also works) and still open, a new writer opened from that reader's commit through IndexWriterConfig.setIndexCommit (Expert, but its javadoc names this use), a count-based policy keeping N >= 2 (directly or inside a snapshot policy), and two or more commits on disk when the new writer opens. No scale, one thread, deterministic.
  • How likely: rare. Each step is legitimate and the chain fits a recover-after-failed-commit flow, but no report of it was found, although the code path dates from 2015. Before 10.3.0 only a custom count-based policy shows the loss.

Why it looks unintended

#
  • onInit's javadoc: the writer "locates all index commits present in the index directory". The directory holds 2; the list has 3.
  • The code that adds the duplicate is for when "the directory listing was stale"; here the listing is complete.
  • Lucene's own TestDeletionPolicy asserts strictly increasing generations in onInit, and LUCENE-9980 fixed an inexact policy commit list as a bug.
The full argument218 words
  • Contract. IndexDeletionPolicy.onInit (IndexDeletionPolicy.java:50): "The writer locates all index commits present in the index directory and calls this method." @param commits (:58): "List of current point-in-time commits, sorted by age".
  • The fallback's comment (IndexFileDeleter.java:180-186): "We did not in fact see the segments_N file corresponding to the segmentInfos that was passed in. [...] This can happen when the directory listing was stale (eg when index accessed via NFS client with stale directory listing cache)."
  • The constructor disagrees with itself: it names the current segments file from lastGeneration (:120) and matches the current commit by generation (:164).
  • Test oracle: TestDeletionPolicy.verifyCommitOrder (TestDeletionPolicy.java:46-60), called from its test policies' onInit, fails with "SegmentInfos commits are out-of-order" unless each generation is larger than the one before.
  • Documented trigger: setIndexCommit (IndexWriterConfig.java:235-237): "This can also be used to open IndexWriter from a near-real-time reader, if you pass the reader's DirectoryReader#getIndexCommit". prepareCommit then rollback is the two-phase-commit abort.
  • Precedent: LUCENE-9980 (#11019, PR #158, fixed in 8.9.0) treated already-deleted commits shown to onCommit as a bug.
  • History: up to 5.2.1 every open path took its generation from a commit on disk, so the match always worked; LUCENE-6524 (5.3.0) added the copy of a closed writer's numbers and its discussion (#7582) never mentions deletion policies.
The devil's-advocate check102 words

The case for "intended": IndexDeletionPolicy and setIndexCommit are Expert APIs, the javadoc never literally says "each commit once", and the two entries are equal under IndexCommit.equals (directory and generation), so a policy could de-duplicate.

Why it fails: the javadoc describes the list as the commits in the directory and gives a policy no reason to de-duplicate; Lucene's own KeepLastNCommitsDeletionPolicy does not; Lucene's test oracle requires strictly increasing generations; and the duplicate comes from a fallback whose stated purpose (a stale listing) does not apply. An independent reviewer from another model family (OpenAI GPT-5.6, executing its own tests) rated the intended-behaviour case "weak".

Suggested fix

#

Recommended Compare with getLastGeneration() (validated)

In IndexFileDeleter's constructor, match a listed commit against segmentInfos.getLastGeneration(), the generation of the current segments file, instead of getGeneration() (one line, :164). The repro passes with assertions on and off, and so do the 1,398 tests of org.apache.lucene.index.* and :lucene:core:check.

Compare with getLastGeneration() (validated) (recommended)

Mark a listed commit as current when its generation equals segmentInfos.getLastGeneration(), the number the constructor already uses to name the current segments file (:120). The forced open then runs only for its stated purpose, a commit missing from a stale listing.

Trade-offs

  • Same result as today whenever segmentInfos was read from a commit (generation == lastGeneration, SegmentInfos.java:361-362).
  • On the explicit older-commit path (setIndexCommit(K)), segmentInfos.replace sets lastGeneration to K but keeps the newest commit's generation (SegmentInfos.java:1088-1092, IndexWriter.java:1087-1104). Today currentCommitPoint is then the newest commit; with this fix it is K, consistent with the current segments file. Its only use is startingCommitDeleted (IndexFileDeleter.java:243-247), which makes the writer call changed() (IndexWriter.java:1184-1189); that path already calls changed() unconditionally (:1104), so no visible change is known (by reading; no targeted run of this path). The open PR #16948 skips that call only when K is the newest commit, where this fix changes nothing.

Make the forced open skip a commit already listed (by reading; not recommended alone)

Trade-offs

Not an option: stop copying the generation in the open-from-reader path

#

Its stated purpose is "In case the old writer wrote further segments (which we are now dropping), update SIS metadata so we remain write-once" (IndexWriter.java:1067-1068); the same call also carries the version and the segment-name counter (SegmentInfos.java:924-927). The defect is the comparison at :164, not the copy.

Trade-offs

Would give up that write-once protection to avoid a one-line comparison fix. Reusing the generation as such is not the hazard: a writer opened from the directory after the same abort reuses generation 3 (commits [1, 2, 3]).

Downstream note

#

Services that keep the last N commits for backups, replica recovery or point-in-time reads lose one of them early when they reopen a writer this way; the live index is unaffected.

How it was found

#

A semi-formal proof-obligation check of IndexFileDeleter's constructor contract: the current commit point must be the commit the current segments file names, and onInit must see each commit in the directory once. An executable test on main then showed the second obligation broken.

The method in full83 words

The check wrote down the obligations the constructor must meet (from the onInit javadoc and the constructor's own comments) and looked for an input that breaks one. The split between generation and lastGeneration after prepareCommit() and rollback(), carried into a new writer by the open-from-reader path, breaks the first; the forced open then breaks the second. A single-threaded JUnit test with a policy that records what onInit is given witnessed [1, 2, 2] on main 5adff78bb168, with assertions on and off.

History

#

Introduced in 5.3.0 by LUCENE-6524 (#7582, 2015), which let a writer open from a closed writer's NRT reader and copy its generation numbers. 5.2.1 passes; every executed release from 5.3.0 to 10.6.0 and main fails. Visible with a shipped policy since 10.3.0. Not fixed upstream.

Versions tested7 rows

Introduced: LUCENE-6524, "init IndexWriter from already opened reader" (#7582; an svn-era JIRA patch, no PR), trunk 2d0ac9bb7f2 and branch_5x 7ab3ca7d608 (the released copy), 2015-06-28. It added the open-from-reader path that copies the closed writer's generation and lastGeneration ("so we remain write-once"), the first way IndexFileDeleter can be handed a generation that no commit on disk has.

Both are first in 2.4.0.

Summary
A writer commits twice (segments_1, segments_2), an NRT reader is opened on it, a further change is prepared with prepareCommit() and then abandoned with rollback(), and a new IndexWriter is opened with setIndexCommit(nrtReader.getIndexCommit()) and KeepLastNCommitsDeletionPolicy(2). You expect IndexDeletionPolicy.onInit to be shown the two commits in the directory, [1, 2], and both to stay. Instead onInit is shown [1, 2, 2]: IndexFileDeleter looks for the current commit by the writer's next-write generation (3) instead of the generation of the current segments file (2), finds no match, reads segments_2 a second time through its stale-directory-listing fallback, and the policy deletes segments_1, so DirectoryReader.listCommits returns only [2].
