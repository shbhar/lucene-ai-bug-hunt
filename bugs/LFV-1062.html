An IndexWriter opened from a leaf-sorted reader's commit applies deletes to the wrong segment

Open an IndexWriter with setIndexCommit(reader.getIndexCommit()) on a reader that has a leaf sorter, and the writer pairs each segment with whatever reader sits at the same position in the sorted list. deleteDocuments(id:a) then deletes b, the commit saves it and CheckIndex stays clean, in every release since 8.9.0 (eight executed, the rest read from the code).

The finding in 30 seconds

#

Two features meet here: a leaf sorter, which reorders a reader's segments for faster sorted search, and opening a writer from that reader's commit. The writer lines its segments up with the reader's leaves by position.

Background: segments, leaves and a writer opened from a reader

#
  1. An index is a list of segments in creation order (_0, _1, ...), recorded in the commit's SegmentInfos. A DirectoryReader opens one leaf reader per segment.
  2. A leaf sorter (opt-in, for example newest segment first for time-based data) reorders the reader's leaves. The reader's SegmentInfos stays in segment order.
  3. IndexWriterConfig#setIndexCommit(reader.getIndexCommit()) (Expert) opens a writer at that reader's point in time and reuses the reader's open segment readers, so in-memory deletes of a near-real-time reader carry over.

The finding, step by step

#
  1. Commit two one-document segments: _0 holds id:a, _1 holds id:b. Open DirectoryReader.open(dir, sorter) with a sorter that puts the newer segment first, so its leaves are [_1, _0].
  2. Open an IndexWriter with setIndexCommit(reader.getIndexCommit()), the documented way to start a writer from a reader, then call deleteDocuments(new Term("id", "a")) and commit().
  3. You expect id:a 0 hits and id:b 1 hit, which is what you get without the sorter, or with the same commit taken from listCommits.
  4. You get id:a 1 hit and id:b 0. The writer's segment list is [_0, _1] and it was zipped with the leaves [_1, _0] by position, so _1's slot held a's data and the delete was saved into _1, which removed b.
  5. No error, and CheckIndex is clean. If the swapped segments differ in size, the writer fails to open instead: IllegalArgumentException: numDocs=2 but maxDoc=1.

Who is affected

#

Applications that combine two opt-in options: a leaf sorter (DirectoryReader.open(dir, sorter), the commit overload, or IndexWriterConfig#setLeafSorter) and a writer opened with the Expert setIndexCommit(reader.getIndexCommit()). Silent when the swapped segments have equal maxDoc (and no committed deletions), which two one-document segments already give; with unequal sizes the writer fails to open. Every release since 8.9.0.

Mechanism, terms and numbers786 words

When an IndexWriter is opened from a reader's commit (IndexWriterConfig#setIndexCommit(reader.getIndexCommit())), it pre-enrolls the reader's segment readers and pairs them with its own segment list by position. A leaf sorter reorders the reader's leaves but not the segment list, so each segment gets another segment's reader. Deletes, updates and merges then act on the wrong documents and the next commit saves that, with CheckIndex clean. In the repro, deleteDocuments(id:a) deletes b and keeps a. Every release from 8.9.0, the first with a leaf sorter, through 10.6.0 and main is affected; pairing by segment name fixes it.

The mechanism (main 645d4fe14a20, lucene/core/src/java/org/apache/lucene/index/)

#
  1. IndexWriter.java:982-989: the writer takes config.getIndexCommit(). A commit from DirectoryReader#getIndexCommit is a ReaderCommit (StandardDirectoryReader.java:571-576) whose package-private getReader() returns the reader itself (:644-646). A commit from listCommits is a ReaderCommit built with a null reader (DirectoryReader.java:456, :481), so the same getReader() returns null; that path never pre-enrolls anything and is not affected.
  2. IndexWriter.java:1021-1050: in the reader branch ("Init from an existing already opened NRT or non-NRT reader", :1030), the writer clones reader.segmentInfos, which is in segment order [_0, _1] (:1050), and hands the reader to new ReaderPool(...) (:1149).
  3. BaseCompositeReader.java:75-76: Arrays.sort(subReaders, subReadersSorter). The same reader's leaves are in sorter order [_1, _0].
  4. ReaderPool.java:91-115 pre-enrolls the reader's segment readers "so any in-memory NRT live docs are correctly carried over, and so NRT readers pulled from this IW share the same segment reader". It pairs them by position. The only check that the two lists match is a size assert; the per-pair checks are in step 5:
List<LeafReaderContext> leaves = reader.leaves();          // [_1, _0]
assert segmentInfos.size() == leaves.size();               // ReaderPool.java:95
for (int i = 0; i < leaves.size(); i++) {                  // :96
  SegmentReader segReader = (SegmentReader) leaves.get(i).reader();
  SegmentReader newReader = new SegmentReader(segmentInfos.info(i), segReader, ...);  // :99-106
  readerMap.put(newReader.getOriginalSegmentInfo(), new ReadersAndUpdates(...));

So _0's pool entry gets _1's reader (document b) and _1's entry gets _0's reader (document a).

  1. SegmentReader.java:128-152: the copy constructor takes its identity from si and its data from sr (this.core = sr.core, :151). It rejects only numDocs > maxDoc (:136-138) and a live-docs length mismatch (:139-142). An equal-size swap passes silently; an unequal one throws. Within a cycle of the permutation, unequal sizes always put a bigger reader on a smaller segment somewhere, so a swap passes these two guards exactly when the moved segments have equal maxDoc (a Z3 model of the two guards for 2 to 8 segments agrees). Equal sizes are needed for the silent case but not always enough: with a committed deletion in a swapped segment, the next commit throws (below).
  2. deleteDocuments(id:a) is resolved against the pooled readers. Under _0 it finds nothing (that reader holds b); under _1 it finds doc 0 (that reader holds a) and marks doc 0 of _1 deleted. That delete is in memory, but it makes _1, which holds b on disk, fully deleted, so the commit drops _1 (IndexWriter.java:6750-6756): the new commit lists only _0, with a, no live-docs file is written, and CheckIndex is clean.

Other effects of the same root (executed on main, -ea and -da; not needed for the issue)

#
  • updateDocument(id:a) deletes b and leaves two copies of a; updateNumericDocValue(id:a) sets b's value; softUpdateDocument(id:a) soft-deletes b.
  • forceMerge(2) of three one-document segments a, b, c commits [a, a, b] (LogDocMergePolicy, merge factor 2, minMergeDocs 1): one document lost, one duplicated, CheckIndex clean. With the default minMergeDocs the merge takes all three segments and nothing is lost.
  • From a sorted near-real-time reader that carries one buffered delete, a bare commit() revives the deleted document and deletes a live one, while the new writer's own NRT reader still shows the right documents.
  • With equal sizes and a committed deletion in one of the swapped segments, the next commit throws NullPointerException (-da) or AssertionError (-ea) in PendingDeletes.writeLiveDocs. (Separately, PendingDeletes.java:41-44 counts the other segment's deletions as pending deletes of this one.)
  • An NRT reader pulled from the new writer shows the right documents, but each leaf carries the other segment's name (_0 holds b, _1 holds a). Through that reader, tryDeleteDocument on a's doc id deletes b, and tryUpdateDocValue on it sets b's value: both resolve the segment from the leaf's own segment info (tryModifyDocument, IndexWriter.java:1791-1812), which here is the wrong name. Through the original sorted reader they return -1 and change nothing.
  • Not affected: forceMerge(1) and a commit from listCommits.
Exposure and likelihood310 words
  • Who is hit. Applications that use a leaf sorter, through DirectoryReader.open(Directory, Comparator), the commit overload (DirectoryReader.open(IndexCommit, Comparator) in 8.10.x-8.11.x, open(IndexCommit, int, Comparator) from 9.0.0) or IndexWriterConfig#setLeafSorter for near-real-time readers (the javadoc suggests it for time-based indices: "usually a descending sort on timestamp"), and that open a writer with setIndexCommit(reader.getIndexCommit()), for example to roll back to a reader's point in time or to hand a near-real-time reader over to a new writer. The documented NRT hand-off, combined with the documented setLeafSorter option on both writers, fails the same way: id:a=1 id:b=0 instead of id:a=0 id:b=1. How often applications open a writer from the commit of the same leaf-sorted reader is unknown.
  • Silent and durable. No exception; the commit persists the wrong deletion; CheckIndex reports the index clean, because it is self-consistent, just wrong.
  • No scale needed. Two one-document segments. The test configures no codec, directory or merge policy (the test framework randomizes codec and directory; it failed on every seed tried), and a main() probe with the default codec gives the same result; assertions on and off.
  • Loud otherwise. When the moved segments differ in size, the writer constructor throws IllegalArgumentException: numDocs=N but maxDoc=M (or maxDoc=M but liveDocs.size()=N), so the documented path cannot open that index at all.
  • Upstream tests did not see it. TestIndexWriterFromReader never uses a leaf sorter, and TestIndexWriterReader.testIndexReaderWriterWithLeafSorter never opens a writer from a reader's commit. With a newest-first sorter injected into every config and reader open, TestIndexWriterFromReader.testRandom fails on 3 of 3 seeds (numDocs=N but maxDoc=1) and passes with the fix.
  • How likely. Rare: both options are opt-in, the silent case needs equal sizes, the Elasticsearch, OpenSearch and Solr call sites of setIndexCommit read for two related bugs pass commits that carry no reader (code reading, not run), and no report was found in the five years since 8.9.0.

Why it looks unintended

#
  • deleteDocuments(Term...) "Deletes the document(s) containing any of the terms"; here it deletes the one without the term.
  • setIndexCommit documents opening a writer from a reader's getIndexCommit() and excludes no reader; a listCommits commit deletes correctly.
  • The positional loop predates the 2021 leaf sorter, which never updated it; reader reopen already pairs segments by name.
The full argument276 words
  • Contract. IndexWriter.java:1856: "Deletes the document(s) containing any of the terms."
  • The entry point names this flow. IndexWriterConfig.java:235-237: "Expert: allows to open a certain commit point. The default is null which opens the latest commit point. This can also be used to open IndexWriter from a near-real-time reader, if you pass the reader's DirectoryReader#getIndexCommit." The LUCENE-6524 CHANGES entry: "IndexWriter can now be initialized from an already open near-real-time or non-NRT reader." The leaf sorter is documented only as a search-order option (DirectoryReader.java:76-90; IndexWriterConfig.java:518-520: "A DirectoryReader opened from a IndexWriter with this configuration will have its leaf readers sorted with the provided leaf sorter."). No javadoc, CHANGES or MIGRATE entry, code comment or test restricts the combination.
  • History. The positional loop came with LUCENE-6524 (2d0ac9bb7f2, 2015, #7582), when a reader's leaves always followed segment order; the size assert shows the assumption. LUCENE-8260 (2018) moved it into ReaderPool unchanged. LUCENE-9507 (48715fe898b, 2021, #10546 / #32) made leaves sortable and changed neither ReaderPool.java nor IndexWriter.java.
  • Sibling code pairs by identity. Reader reopen maps old readers by segment name (StandardDirectoryReader.java:249-260), and tryDeleteDocument / tryUpdateDocValue resolve the segment from the leaf reader's own segment info (tryModifyDocument, IndexWriter.java:1791-1812).
  • Why tests never saw it. In the first review of LUCENE-9507 (apache/lucene-solr#2256, 2021-02-09), jimczi suggested a random leaf sorter in LuceneTestCase#newIndexWriterConfig; the author replied that a different order "will break some of our tests that rely on specific docIds", so it was not done.
  • Precedent. LUCENE-8466 (2018), "IndexWriter.deleteDocs(Query... query) incorrectly applies deletes on flush if the index is sorted", treated deletes landing on the wrong documents as a bug.
The devil's-advocate check144 words

Every API involved is marked advanced: setIndexCommit is "Expert", DirectoryReader#getIndexCommit is "Expert" and @lucene.experimental, IndexCommit is @lucene.experimental, and on #214 jpountz called leafSorter one of the "super expert parameters". So a maintainer could call the combination unsupported.

Why it fails: no such precondition is documented; setIndexCommit names exactly reader.getIndexCommit(); setLeafSorter is an IndexWriterConfig option, so the documented NRT hand-off combined with that documented option yields a sorted reader without any misuse, and it fails the same way; "experimental" lets the API change, it does not let deleteDocuments delete a document that lacks the term and commit that silently. The executing reviews from another model family and the independent reproducer rated the intended-behaviour case weak; the devil's advocate found that none of its points survives; the adjudication agreed, and the audit found that deleting a document without the term "cannot be intended".

Suggested fix

#

Recommended Pair each segment with the reader of the same name (validated)

Pair each segment with its own reader by segment name in the ReaderPool constructor (a map keyed by SegmentReader.getSegmentName()), not by position. Validated with gradle: the repro passes with assertions on and off, and so do TestIndexWriterFromReader, TestReaderPool, TestIndexWriterReader, TestDirectoryReader and TestDirectoryReaderReopen.

// ReaderPool constructor, reader != null: pair by segment name, not by position
Map<String, SegmentReader> readersByName = new HashMap<>();
for (LeafReaderContext leaf : leaves) {
  SegmentReader segReader = (SegmentReader) leaf.reader();
  readersByName.put(segReader.getSegmentName(), segReader);
}
for (SegmentCommitInfo info : segmentInfos) {
  SegmentReader segReader = readersByName.get(info.info.name);
  assert segReader != null : "no reader for segment " + info.info.name;
  SegmentReader newReader =
      new SegmentReader(info, segReader, segReader.getLiveDocs(),
          segReader.getHardLiveDocs(), segReader.numDocs(), true);
  // readerMap.put(...) unchanged
}

Pair each segment with the reader of the same name (validated) (recommended)

#

In the ReaderPool constructor, map the reader's leaves by SegmentReader.getSegmentName() and look up each SegmentCommitInfo by info.info.name, instead of taking leaves.get(i). +10/-3 lines in ReaderPool.java; Map and HashMap are already imported.

// ReaderPool constructor, reader != null: pair by segment name, not by position
Map<String, SegmentReader> readersByName = new HashMap<>();
for (LeafReaderContext leaf : leaves) {
  SegmentReader segReader = (SegmentReader) leaf.reader();
  readersByName.put(segReader.getSegmentName(), segReader);
}
for (SegmentCommitInfo info : segmentInfos) {
  SegmentReader segReader = readersByName.get(info.info.name);
  assert segReader != null : "no reader for segment " + info.info.name;
  SegmentReader newReader =
      new SegmentReader(info, segReader, segReader.getLiveDocs(),
          segReader.getHardLiveDocs(), segReader.numDocs(), true);
  // readerMap.put(...) unchanged
}

Trade-offs

  • One HashMap per writer opened from a reader: linear, once, in the constructor.
  • Unchanged for unsorted readers, where position and name agree. It is the rule reader reopen already uses (StandardDirectoryReader.java:249-260).
  • The pool's map is keyed by SegmentCommitInfo, so the insertion order does not matter.

What the checks validated

  • With the fix, assertions on: TestIndexWriterReader (24, one assumption skip), TestDirectoryReader (34) and TestDirectoryReaderReopen (30) pass; :lucene:core:check -x test (format, ecj lint, forbidden APIs) passes with the fix and the test.
  • Earlier, in the repro harness: the independent reproducer's and both reviewers' tests pass; the 5,220-run bounded-exhaustive differential test matches the no-sorter control in every run; with a newest-first sorter injected, TestIndexWriterFromReader passes 12 of 12 on 3 seeds; TestSoftDeletesDirectoryReaderWrapper (5) and TestSoftDeletesRetentionMergePolicy (14) pass.
  • Not run: the full Lucene test suite. The focused suites are enough for an issue and a candidate patch; run the full suite before calling the patch ready to merge.

The same, with an explicit exception for a missing name

#

Replace the assert segReader != null with an IllegalStateException, as one of the reviews suggested.

Trade-offs

A missing name cannot happen when the segment list and the leaves come from the same reader (the NRT path drops fully deleted segments from both), so this only changes how an internal inconsistency would surface. Not run.

Reject the combination

#

Throw IllegalArgumentException in the writer's reader branch when the reader's leaves are not in segment order.

Trade-offs

Small and safe, but it rejects a documented composition of options (rollback or NRT hand-off with a leaf sorter) that today either corrupts silently or fails loudly, instead of making it work, and the javadoc would have to say so. Not run.

Give ReaderPool the readers in segment order

#

Have StandardDirectoryReader or its ReaderCommit keep the segment readers in segment order next to the sorted view, and pre-enroll from that.

Trade-offs

Equivalent to pairing by name, but it changes reader internals for a constructor-local problem. Not run.

Optional: randomize the leaf sorter in tests

#

Setting a random setLeafSorter in LuceneTestCase#newIndexWriterConfig, as jimczi proposed on apache/lucene-solr#2256, would have exposed this through TestIndexWriterFromReader.testRandom.

Trade-offs

Coverage, not a fix; many tests depend on doc ids, which is why it was not adopted in 2021. The regression test for this bug is the one repro test.

Downstream note

#

In a product that takes this path and lets users delete or update their own documents by term, one user's request could remove or change another document.

How it was found

#

A planning pass proposed it and confirmed it with public-API probes on main; a skeptic pass re-ran and widened it. The hunt reduced it to one test and bounded it with a Z3 model of the writer's two size guards and a 5,220-run bounded-exhaustive differential test on the real jar.

The method in full219 words
  • Lead (non-formal). A planning pass of the hunt's round 18 proposed it and witnessed it with public-API main() probes on main: one with a directory reader opened with a newest-first sorter, one with setLeafSorter on both writers and a near-real-time reader. A skeptic pass re-ran it, widened it (forceMerge(2) with minMergeDocs 1 commits [a, a, b]) and found it on 8.9.0, 8.10.0 and 9.0.0. In the same round, injection replays (a newest-first sorter switched on in copied upstream test classes) hit the same root through TestIndexWriterFromReader.testRandom.
  • Hunt. The unit reduced it to one public-API JUnit test. Then two formal legs: a Z3 model of the writer constructor's two guards (2 to 8 segments) separates the leaf orders that pass silently (equal maxDoc) from those that fail loudly; a bounded-exhaustive differential test on the real jar (5,220 runs: 2 or 3 segments of 1 or 2 documents, with and without a deletion, every leaf order, directory and near-real-time readers, no-op, delete, update, doc-values update, forceMerge(1) and forceMerge(2); oracle: the same steps from the same commit without a sorter) matched the model's prediction in every run, and is 5,220 of 5,220 equal to the oracle with the fix.
  • Because the formal legs came after the lead, the hunt counts the bug as found by non-formal means.

History

#

Introduced in 8.9.0 by LUCENE-9507 (48715fe898b, 2021), which made a reader's leaves sortable without touching ReaderPool; the positional loop dates from LUCENE-6524 (2015). Every release from 8.9.0 through 10.6.0 and main is affected; 8.8.2 has no leaf-sorter API.

Versions tested7 rows

Introduced by LUCENE-9507 "Custom order for leaves in IndexReader and IndexWriter" (#32, issue #10546, 48715fe898b, 2021-03-26), released in 8.9.0 through its branch_8x backport 1cfd0df4e7bb (lucene-solr#2473). Latent precondition: the positional pre-enroll loop of LUCENE-6524 (2d0ac9bb7f2, 2015-06-28, #7582, released in 5.3.0), moved unchanged into ReaderPool by LUCENE-8260 (89756929537, 2018-04-23); it was correct while leaves always followed segment order. LFV-1062, snapshot of 2026-11-02

Registry title
An IndexWriter opened from a leaf-sorted reader's IndexCommit pairs each segment with the segment reader at the same leaf position, so deleteDocuments(term) deletes another segment's documents and the commit persists that silently
Area
index / IndexWriter opened from a reader's IndexCommit (ReaderPool pre-enrollment) with a leaf-sorted reader (DirectoryReader leaf sorter, IndexWriterConfig#setLeafSorter)
Priority
Medium, rank 73: This is silent, durable wrong-document deletion in core IndexWriter that CheckIndex does not catch, but like its sibling LFV-593 it needs the Expert setIndexCommit-from-a-reader path plus a leaf sorter and equal-maxDoc reordered segments.
Impact class
data corruption
Impact note
Hits only applications that combine two opt-in options: a leaf sorter (DirectoryReader.open(Directory, Comparator), the IndexCommit overload with a sorter, or IndexWriterConfig#setLeafSorter for NRT readers, for example the newest-first order the javadoc suggests for time-based indices) and an IndexWriter opened with the Expert IndexWriterConfig#setIndexCommit(reader.getIndexCommit()) on such a reader; when the segments the sorter moves have equal maxDoc (two one-document segments suffice, no scale), deletes, updates, doc-values updates and merges act on another segment's documents and the next commit persists that with CheckIndex clean, and when their sizes differ the writer constructor throws IllegalArgumentException 'numDocs=N but maxDoc=M' instead; default codec, directory and merge policy, -ea and -da, every release from 8.9.0 through 10.6.0 and main.
Summary
You commit two one-document segments (_0 holds id=a, _1 holds id=b), open DirectoryReader.open(dir, newestFirst) so that its leaves are [_1, _0], open an IndexWriter with setIndexCommit(reader.getIndexCommit()), call deleteDocuments(new Term("id", "a")) and commit. You expect the index to keep only b, as it does when the reader has no sorter or when the same commit is taken from DirectoryReader.listCommits. Instead the writer deletes b and keeps a: ReaderPool pairs segmentInfos.info(i) (segment order) with reader.leaves().get(i) (sorted order) by position, so each segment's pooled reader carries the other segment's documents, the delete matches a's data but is recorded under _1, and the commit writes _1's live docs, with CheckIndex clean.
