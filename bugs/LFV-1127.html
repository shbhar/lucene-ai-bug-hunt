IndexWriter.prepareCommit() can return the next commit's sequence number

If another thread finishes the commit that prepareCommit() just prepared, and prepares the next one before the first call returns, the first call returns the next commit's sequence number: 6 instead of 3. The index is correct; only the returned number is wrong, in every release since 6.4.0.

The finding in 30 seconds

#

prepareCommit() keeps its commit's sequence number in a field shared by the whole writer, runs a merge step outside the commit lock, and then returns the field instead of its own value. If another thread finishes that commit and prepares a new one during the merge step, the field already holds the new commit's number.

  1. Add one document (sequence number 1). Thread A calls prepareCommit(). It publishes the pending commit, then runs its merge step outside the commit lock, so it is still inside the call.
  2. Meanwhile the main thread calls commit(), which finishes A's prepared commit (1 document) and returns 3. It then adds a document (sequence number 4) and calls prepareCommit() again, which returns 6.
  3. You expect A's prepareCommit() to return 3: its javadoc says every sequence number <= the result is in the commit it prepared, and no other is.
  4. Instead A's call returns 6, because it re-reads a field shared by the whole writer, which the second prepareCommit() overwrote. Operation 4 is not in A's commit. No error, with assertions on or off.

Who is affected

#

Applications that drive one writer's two-phase commit from more than one thread and use prepareCommit()'s number as the exact cut of the commit it prepared, for example to trim their own transaction log. No special codec or setting, no scale. The committed index is correct and nothing throws. Contrived, so priority Low.

Mechanism, terms and numbers548 words

IndexWriter.prepareCommit() stores the sequence number of the commit it prepared in the shared volatile field pendingSeqNo, then runs the post-flush maybeMerge(FULL_FLUSH) outside commitLock, then returns the field again instead of its own value (IndexWriter.java:3735-3743 on main). The prepared commit is already published at that point, so another thread may finish it with commit() (which returns the right number, a local copy), index more and call prepareCommit() again, which overwrites the field. The first call then returns the second commit's number: in the repro 6, while commit() returned 3 for the same commit and operation 4 is not in it. This breaks prepareCommit()'s @return ("All sequence numbers <= this value will be reflected in the commit, and all others will not"). The index contents are correct and nothing throws. It needs one writer's two-phase commit driven from two threads in this interleaving, so it is contrived. The merge step was moved between the store and the re-read by a deadlock fix (LUCENE-7570) first released in 6.4.0; every release since, through 10.6.0, and main are affected. The fix returns the local value.

Terms

#
  • Sequence number: every IndexWriter method that changes the index returns a long that orders the change. commit() and prepareCommit() return one too, "describing which changes are in the commit point and which are not" (IndexWriter.java:117-121).
  • Two-phase commit: prepareCommit() flushes, syncs and writes most of the next segments_N (the commit is now pending); commit() finishes it (:3720-3732). commit() with no pending commit does both phases itself.

The bug

#
// IndexWriter.java:3735-3743
public final long prepareCommit() throws IOException {
  ensureOpen();
  pendingSeqNo = prepareCommitInternal();   // shared volatile field (:280)
  // we must do this outside of the commitLock else we can deadlock:
  if (maybeMerge.getAndSet(false)) {
    maybeMerge(config.getMergePolicy(), MergeTrigger.FULL_FLUSH, UNBOUNDED_MAX_MERGE_SEGMENTS);
  }
  return pendingSeqNo;                      // re-reads the field
}
  1. prepareCommitInternal() holds commitLock (:3775), publishes the pending commit (pendingCommit = toSync, :5984) and returns its number, then releases the lock.
  2. prepareCommit() stores the number and runs the merge step with no lock held: the merge policy picks merges and the merge scheduler gets them (:2442-2452). SerialMergeScheduler runs them on this thread (SerialMergeScheduler.java:32-40); ConcurrentMergeScheduler may stall this thread while merges are backed up (ConcurrentMergeScheduler.java:566, :609).
  3. Meanwhile another thread's commit() takes commitLock, sees the pending commit ("commit: already prepared"), takes seqNo = pendingSeqNo and finishes it (:4253-4260); it returns that local copy (:4268). Its next prepareCommit() is accepted, since no commit is pending now (:3787-3790), and stores the next commit's number in the field.
  4. Thread A leaves the merge step and returns the field (:3742): the next commit's number.

The numbers

#

In the repro: the first addDocument gets 1; the main thread's commit() finishes A's commit (1 document) and returns 3; the next addDocument gets 4; the second prepareCommit() returns 6; A's prepareCommit() returns 6, expected 3. The final commit() returns 6 and holds 2 documents. (Sequence numbers skip values around a full flush; the gaps are normal.)

Related, not claimed (read only; no test targets it, never observed): the field is stored after prepareCommitInternal releases commitLock, so a commit() that takes the lock in that short gap would read the previous value.

Exposure and likelihood283 words
  • Who is hit. Only applications that let a second thread finish a commit another thread prepared, and prepare the next one, while the first prepareCommit() is still in its merge step, and that then trust the first call's number as the cut of that commit. Lucene's own coordinator (TwoPhaseCommitTool) and its threaded tests prepare and commit from one thread or under an application lock.
  • Default vs opt-in. No special codec or setting is needed: the window is the merge step that prepareCommit() runs after a flush with changes (IndexWriter.java:3739-3741), with any merge policy and scheduler. It is longest when merges are picked and SerialMergeScheduler runs them on the caller, or ConcurrentMergeScheduler stalls it. Every executed test that shows the bug held the window open with a latch in a custom merge scheduler (an @lucene.experimental extension point); a stock configuration was not run, and the window's length in practice was not measured.
  • Scale. None: two documents.
  • How bad. Only the returned long is wrong. The committed index is correct and nothing throws, with assertions on or off. If thread A then calls commit(), that call finishes the second commit (the one still pending, prepared by the other thread) and returns the same number, so everything up to it becomes durable (executed). So the harm is an over-stated cut for code that pairs the prepare-time number with the earlier commit. By reasoning only (not executed): an application that trims its log up to 6 once A's commit is durable, and crashes before the second commit finishes, has operation 4 neither in the index nor in its log.
  • Likelihood: contrived. No public report of it was found since 6.4.0 (January 2017).

Minimal repro

#

One JUnit test, two threads (the interleaving is the bug), latches only, no sleeps, deterministic, public API and documented (@lucene.experimental) merge extension points. A merge scheduler holds thread A in prepareCommit()'s merge step while the main thread commits, adds a document and prepares again. Fails with assertions on and off on main and on 10.6.0.

Why it looks unintended

#
  • The @return promises "All sequence numbers <= this value will be reflected in the commit, and all others will not"; commit() returns 3 for it.
  • IndexWriter is documented as "completely thread safe"; commit() finishes any pending commit, whoever prepared it.
  • The wide window is an accident of a 6.4.0 deadlock fix (LUCENE-7570) that put the merge step before the re-read.
The full argument277 words
  • The contract. prepareCommit() @return (IndexWriter.java:3730-3732): "The sequence number of the last operation in the commit. All sequence numbers <= this value will be reflected in the commit, and all others will not." commit() has the same @return (:4207-4209). The class javadoc: "IndexWriter instances are completely thread safe, meaning multiple threads can call any of its methods, concurrently" (:167-168).
  • The trigger breaks no stated rule. The javadoc orders the phases ("After calling this you must call either commit() to finish the commit, or rollback() to revert the commit", :3723-3725; TwoPhaseCommit.java:36-40) but does not say which thread may finish a prepared commit. commitInternal finishes whatever commit is pending, without tracking which call or thread prepared it (:4253-4257), and the second prepareCommit() passes its own "already called" check because the first commit is finished.
  • History. The first sequence-number patch (LUCENE-7302, #8356, 6.2.0) stored and returned the field on adjacent lines (6.3.0: pendingSeqNo = prepareCommitInternal(...); return pendingSeqNo;), so a wrong value needed thread A to be preempted between two adjacent field accesses. LUCENE-7570 (#8621, 6.4.0) moved the merge between them to fix a deadlock; neither the issue nor the commit mentions the return value. commit() kept returning a local copy.
  • Maintainer intent for the number. On java-user@ (2017-08-10, "Storing external transaction log-ids in lucene...") a user planned to let a background commit thread call prepareCommit() and use its number; Michael McCandless replied "That's exactly right! That is the purpose of the sequence numbers ... You can know exactly which ops made it into your commit" (https://lists.apache.org/thread/75rfkqdby1ln96x0g9s6mmn2yh0n46wp).
  • Tests. No upstream test compares prepareCommit()'s return value with a concurrent commit().
The devil's-advocate check268 words

The strongest case (rated moderate by the cross-model reviews and the devil's-advocate verifier): two-phase commit is meant to have one coordinator. TwoPhaseCommit (@lucene.experimental, TwoPhaseCommit.java:21-41) describes commit() as the phase "following" prepareCommit(), and the prepareCommit() javadoc says to call commit() "after calling this" (IndexWriter.java:3723-3725). Lucene's threaded tests serialize under an application lock, around prepareCommit() plus commit() (TestIndexWriterWithThreads.java:568, :599-608) or around commit() alone (TestIndexingSequenceNumbers.java:166, :187). On LUCENE-1335 (#2412, 2008-08-05) Michael McCandless wrote: "I think we should not make any API promises about what it means when these methods (commit, close, rollback, optimize, addIndexes) are called concurrently from different threads, except that the methods all work correctly, IndexWriter won't throw an errant exception, and your index won't become corrupt." Here the index is correct and nothing throws. On dev@ (2014-12-16, "Transactions multiplexing IndexWriter", https://lists.apache.org/thread/w83vmtn0bbncd4dk3byfnmzrv3r6z0b6) they also wrote that "Lucene's IndexWriter only allows one transaction at a time". A maintainer is likely to cite the 2008 statement.

Why it fails: none of this is a documented precondition. The 2008 statement predates sequence numbers (LUCENE-7302, 2016) by 8 years, and "the methods all work correctly" includes the documented @return. The 2014 remark is about isolating the documents of concurrent transactions, which the repro does not need (the contents are correct). The numbers returned for one commit, 3 from commit() and 6 from prepareCommit(), fit no single-threaded order, which is what sequence numbers promise (CHANGES.txt:8995-8997, LUCENE-7302: "the effective equivalent single-threaded execution order"). What survives is a likelihood argument, hence priority Low; the zero-cost fix makes prepareCommit() consistent with commit().

Suggested fix

Store the field under commitLock, return the local value (validated by the checks)

#

In prepareCommitInternal, set pendingSeqNo = seqNo right after startCommit published the pending commit, still inside commitLock; prepareCommit() returns its local value. The field and the pending commit are then written in the same locked section, and the field is read only under that lock.

@@ prepareCommit()
-    pendingSeqNo = prepareCommitInternal();
+    final long seqNo = prepareCommitInternal();
     ...
-    return pendingSeqNo;
+    return seqNo;
@@ prepareCommitInternal(), after startCommit(toCommit)
         if (pendingCommit == null) {
           return -1;
         } else {
+          // publish the pending commit's seqNo while still holding commitLock
+          pendingSeqNo = seqNo;
           return seqNo;
         }

Trade-offs

Also closes the store-after-unlock gap, but no test targets that gap, so this extra benefit is untested. Touches prepareCommitInternal, which commit() also calls when nothing is prepared; the store is harmless there, since the field is read only while a commit is pending.

What the checks validated

  • With this fix the repro passes through gradle, on and off; the same 7 suites: 160 tests, 0 failures, 8 skipped; :lucene:core:check -x test with the license-headed test: passes.
  • Its extra benefit, closing the store-after-unlock gap, has no test: no test targets that gap.

Downstream note

#

Downstream products are exposed only if they use prepareCommit()'s number as a commit cut while more than one thread drives the same writer's two-phase commit; no query, document or index file can trigger it on its own (documents only change how long the merge step lasts).

How it was found

#

A proof-obligation audit of IndexWriter.prepareCommit()'s contract asked whether the returned number is always the cut of the commit the call prepared, and found the re-read of the shared field after the unlocked merge step. A public-API JUnit test then witnessed it on main; independent checks reproduced it with their own tests.

The method in full137 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: the value prepareCommit() returns satisfies its @return for the commit this call prepared, under the class's "completely thread safe" promise. Between the store (:3737) and the return (:3742) no lock is held and another thread can publish a new value, so the obligation is not met.
  • A JUnit test that holds the preparing thread in its merge step with a latch witnessed it on main (assertions on and off; 10 of 10 iterations) and on 10.6.0 and 9.12.3. An independent reproducer, two executed reviews by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier wrote their own tests from the claim; the independent reproducer's test, as cut down in a final repro check, is the repro here.

Versions tested8 rows

Window opened by LUCENE-7570 (#8621, "IndexWriter may deadlock if a commit is running while there are too many merges running and one of the merges hits a tragic exception"), committed by Mike McCandless on 2016-12-09 as ea3f8363319 (branch_6x) and 2b073a2f296 (master): "don't run merges while holding the commitLock to prevent deadlock when merges are stalled and a tragic merge exception strikes". No hook reaches that point; it was not reproduced and is not claimed. Source builds of both LUCENE-7570 commits reproduce; in their parents commit() blocks on commitLock until thread A returns, so the test's window is closed. The releases between those executed contain the change (git merge-base --is-ancestor over the 78 release tags from 6.4.0 to 10.6.0). Upstream main 1c2072f0284 (2026-11-02) is unchanged here. LFV-1127, snapshot of 2026-11-07

Registry title
IndexWriter.prepareCommit() re-reads the shared pendingSeqNo field after its post-commit maybeMerge, so if another thread finishes that commit and prepares the next one meanwhile, prepareCommit() returns the next commit's sequence number
Area
index / IndexWriter two-phase commit (sequence numbers)
Priority
Low, rank 943: A prepareCommit() call can return the next commit's sequence number while the committed index stays correct, in every release since 6.4.0. It needs two threads driving one writer's expert two-phase commit in a specific interleaving and a caller that trusts that number as the commit's exact cut, so it is contrived.
Impact class
silent wrong results
Impact note
Only applications that drive IndexWriter's expert two-phase commit from more than one thread and use prepareCommit()'s returned number as the exact cut of the commit it prepared (for example to checkpoint a transaction log) are hit, and only when another thread finishes that pending commit with commit() and calls prepareCommit() again while the first prepareCommit() is still inside the maybeMerge(FULL_FLUSH) it runs outside commitLock (a window that is long with SerialMergeScheduler or when ConcurrentMergeScheduler stalls the caller): the commit contents are correct and nothing throws (-ea and -da alike), only the returned long is too high; default codec and config suffice, no scale is needed, and every release from 6.4.0 through 10.6.0 and main are affected.
Summary
The main thread adds a document and thread A calls IndexWriter.prepareCommit(); while A is still in the merge step that prepareCommit() runs after publishing its pending commit, the main thread calls commit() (which finishes A's commit and returns 3), adds another document (sequence number 4) and calls prepareCommit() again. You expect A's prepareCommit() to return 3, as its javadoc promises ('All sequence numbers <= this value will be reflected in the commit, and all others will not') and as commit() returned for the same commit.
