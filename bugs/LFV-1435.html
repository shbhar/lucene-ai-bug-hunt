FlatVectorsReader's javadoc says searching it scores every vector, but its search methods return nothing

FlatVectorsReader's class javadoc says searching it "iterates every vector in the index and scores them", but its search methods are empty on purpose. So a codec that uses Lucene99FlatVectorsFormat as its vectors format gets 0 hits instead of 1, with no error, from an unfiltered kNN query.

The finding in 30 seconds

#

The class javadoc promises a brute-force scan. The base class's search methods are empty, Lucene99FlatVectorsReader inherits them, and an unfiltered kNN query takes the reader's empty answer as final.

Background: flat vectors formats

#
  1. A vectors format decides how a field's vectors are stored and searched. The default codec's format stores the vectors plus an HNSW graph, and a kNN query walks the graph.
  2. A flat format stores only the vectors, with no graph. HNSW formats use one inside to hold their vectors; since 9.12.0 a custom codec can also use one directly as its vectors format.
  3. A kNN query asks each segment's vectors reader for the nearest vectors. With a filter it can fall back to scoring the filtered documents itself; without one it uses the reader's answer.

The finding, step by step

#
  1. You build a codec whose knnVectorsFormat() returns new Lucene99FlatVectorsFormat(...), the custom-codec setup the 9.12.0 release notes describe, and index 1 document with the vector {1, 1}.
  2. You run an unfiltered KnnFloatVectorQuery for {1, 1} with k = 1. The reader's javadoc says searching it "iterates every vector in the index and scores them", so you expect 1 hit.
  3. You get 0 hits and no error, with assertions on and off. The reader holds the vector, but its search methods are empty ("If we didn't index it, produce no search results"), and without a filter the query has no fallback.
  4. The empty methods are a deliberate choice (#13469, 9.12.0). The javadoc was written seven months earlier, when the class had no search method, and was never updated. The fix is javadoc only.

Who is affected

#

Only codecs whose vectors format is a stand-alone flat format such as Lucene99FlatVectorsFormat: unfiltered kNN queries on the field return nothing, and so do default-decay vector-similarity queries, filtered or not. Not affected: the default codec, kNN queries whose filter does not rewrite to match-all, similarity queries with decay 1, and the per-field route (it fails loudly). Expert API, since 9.12.0.

Mechanism, terms and numbers544 words

FlatVectorsReader is the base class of the vectors readers that store vectors without a search structure; HNSW formats use one inside to hold their vectors. Its class javadoc says "When searching this reader, it iterates every vector in the index and scores them" and recommends it when "the number of vectors is small" (FlatVectorsReader.java:28-29, :34).

Since 9.12.0 the class is a KnnVectorsReader, and its three search methods are empty on purpose: "don't scan stored field data. If we didn't index it, produce no search results" (:50-66). Lucene99FlatVectorsReader inherits them. 9.12.0's release notes say a flat format "can be configured using a custom Codec". A codec author who configures it that way, reading the javadoc as the promise of a scan, gets 0 hits, with no error, from every unfiltered kNN query on the field, and from vector-similarity queries with the default decay, filtered or not. A kNN query with a filter that does not rewrite to match-all, and a similarity query with decay 1, score the vectors themselves and find the documents.

The empty methods are intended (#13469), and Lucene's own tools treat flat readers as not searchable. Only the javadoc is wrong: it was written in #12729 (9.9.0), when the class had no search method, and nobody updated it. The fix is javadoc only.

What the checks saw

#
  • The leaf's vectors reader is a FlatVectorsReader and holds the vectors; called directly, its search collects 0 results and visits 0 vectors.
  • Unfiltered KnnByteVectorQuery also returns 0, and so does FloatVectorSimilarityQuery.Adaptive (threshold 0) with the default decay, with or without a TermQuery filter; with decay 1 it finds the document, with or without the filter.
  • With a TermQuery filter matching the documents, the same KnnFloatVectorQuery (and KnnByteVectorQuery) finds the nearest one through the exact-search fallback; with a MatchAllDocsQuery filter it gets 0.
  • The same test with the default codec's vectors format finds the document.

Lucene's own tools already treat flat vectors as not searchable: CheckIndex.vectorsReaderSupportsSearch tests the reader (instanceof FlatVectorsReader, CheckIndex.java:3105-3109), and the test framework's supportsVectorSearch tests the format (instanceof FlatVectorsFormat, LuceneTestCaseParent.java:2745-2747).

Exposure and likelihood181 words
  • Who: developers who build a codec whose knnVectorsFormat() is a stand-alone flat format such as Lucene99FlatVectorsFormat (@lucene.experimental, public constructor) and who could read this class javadoc as saying what search does. Lucene itself uses this setup in a test-source benchmark (IncrementalDocValuesUpdatesBenchmark.java:129-137).
  • What happens: silent missing results. Unfiltered KnnFloatVectorQuery and KnnByteVectorQuery return 0 hits, with no error, assertions on and off; so do vector-similarity queries with the default decay, with or without a filter.
  • Not affected: the default codec; kNN queries with a filter that does not rewrite to match-all (exact-search fallback); vector-similarity queries with decay 1, DECAY_MAX_QUALITY (exact scoring); the per-field route, which fails at reader open because Lucene99FlatVectorsFormat is not SPI-registered ("An SPI class of type org.apache.lucene.codecs.KnnVectorsFormat with name 'Lucene99FlatVectorsFormat' does not exist"); and the float32 and float16 paths of Lucene104ScalarQuantizedVectorsReader, which do scan every vector (Lucene104ScalarQuantizedVectorsReader.java:355-367).
  • How likely: rare. It needs an expert custom codec, the empty result shows on the first query, and nobody has reported the javadoc since 9.12.0 (2024).
  • How long: every release from 9.12.0 through 10.6.0, and main.

Why it looks unintended

#
  • The class javadoc, an explicit class-level statement about searching a FlatVectorsReader, says the opposite of the base implementation; no other doc states the no-results behaviour.
  • The sentence dates from #12729 (9.9.0), before the class had any search method; #13469 (9.12.0) added the empty methods and left it.
  • #13469 chose zero results on purpose: that defends the code, not the sentence.
The full argument214 words
  • Contract. FlatVectorsReader.java:28-29: "When searching this reader, it iterates every vector in the index and scores them." The inherited KnnVectorsReader.search javadoc says "Return the k nearest neighbor documents" (KnnVectorsReader.java:96-123). FlatVectorsFormat ("provides a scoring interface for the flat stored vectors"), Lucene99FlatVectorsFormat, the codecs.hnsw package doc, CHANGES and MIGRATE say nothing about search returning no results; only the comments inside the method bodies do.
  • History. The sentence comes from #12729 (a47ba3369f4, Benjamin Trent, 2023-11-10, 9.9.0), when FlatVectorsReader implemented only Closeable, Accountable and had no search. #13469 (487d24ae69f, Michael Sokolov, 2024-06-13, 9.12.0) made it extend KnnVectorsReader with two empty search bodies and did not touch the class javadoc; #16383 (2026-07-27; on main and branch_11x, in no release yet) added the third.
  • Design. On #13469 Michael Sokolov wrote: "I changed this to return zero results from search() rather than throwing UnsupportedOperationException to be more in line with how we treat searches over other kinds of fields that only have stored data that is not indexed" (2024-06-13). No item found in the searches discusses the class javadoc.
  • Tests. CheckIndex and the test framework skip search for flat readers, and the backward-codecs TestLucene99ScalarQuantizedVectorsFormat says "this class always returns no results from search" (:114) and "search not supported" (:253).
The devil's-advocate check148 words

The intended-behaviour check built the strongest not-a-bug case: the code is deliberate and asserted (#13469, CheckIndex, the test framework); only custom-codec users can reach it ("you cannot get access to this stuff at all unless you are willing to create a custom Codec", Michael Sokolov on #13469, 2024-06-11); the sentence predates search() and may describe the reader's storage and scoring role (the scorer an outer structure such as HNSW uses), not the inherited search; it is true for Lucene104ScalarQuantizedVectorsReader's float paths; the API is @lucene.experimental; and the empty result is visible at once.

Why it fails: all of this defends the code. None of it defends a class javadoc that tells a reader the opposite, and an experimental tag does not make a wrong sentence right. Every check, including reviews by a model from another family, found it real, as a documentation defect.

Suggested fix

#

Recommended A: say the base search returns no results (validated)

Correct the class javadoc only: the base search methods produce no results because the vectors are stored, not indexed, and subclasses may override them to score every vector. Validated in a scratch worktree: the format and javadoc checks pass, and the 4 closest suites pass (278 tests, assertions on and off).

B: make the base search methods score every accepted vector

#

The behaviour the javadoc describes. Benjamin Trent on #13910 (2024-10-16): "I still think that the underlying flat format should allow search to be called and it simply iterates all matching vectors. But we can adjust that in a later PR." kaivalnp on the #15979 review (2026-07-28): flat vector formats "are not supposed to" provide a search, "but IMO they should!"

Trade-offs

A design change, not a doc fix: it reverses #13469's choice (Michael Sokolov did not want "to create a trap" for users of a brute-force path); CheckIndex.vectorsReaderSupportsSearch, the test framework's supportsVectorSearch and tests that expect no results would change; each unfiltered query becomes a full scan per segment. It would also settle LFV-468 (the byte path of Lucene104ScalarQuantizedVectorsReader). Not validated here.

C: also say it on the flat format (complement to A)

#

Add a sentence to the Lucene99FlatVectorsFormat or FlatVectorsFormat class javadoc, where a codec author looks first: used directly as a codec's vectors format, the field is stored but kNN queries without a filter find nothing.

Trade-offs

More places to keep in sync. Not validated here.

Rejected: throw UnsupportedOperationException

#

#13469 considered throwing and chose zero results instead, in line with stored-but-not-indexed fields.

Trade-offs

Contradicts the maintainers' explicit choice: every unfiltered kNN query on such a field would then fail instead of returning nothing.

Downstream note

#

Downstream projects that expose a flat vectors format should say how kNN behaves on it; Solr's flat dense-vector field already lists kNN as unsupported, and Elasticsearch's flat format implements its own scan.

How it was found

#

Semi-formal: a proof-obligation check of FlatVectorsReader's class javadoc against the search methods it gives every subclass showed that the promise cannot hold for Lucene99FlatVectorsReader. A public-API JUnit test on main then witnessed it, and independent checks reproduced it with their own tests.

The method in full99 words
  • Obligation: if the class javadoc holds, a search call on any FlatVectorsReader that does not override search scores every vector of the field.
  • Check: the base class's search(float[]), search(byte[]) and search(short[]) bodies are empty, and Lucene99FlatVectorsReader overrides none of them, so the obligation fails for it; since 9.12.0 a codec can make that reader the one a kNN query asks.
  • Witness: a JUnit test on main f794ff5a505c: a codec with Lucene99FlatVectorsFormat as its vectors format, an unfiltered KnnFloatVectorQuery, 0 hits instead of 1, with assertions on and off.
  • Tier: semi-formal (a contract check plus executed tests).
