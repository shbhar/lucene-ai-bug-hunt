The finding in 30 seconds

#

A loud exception, not a wrong hit; the join without scores works on the same reader. It threw in the runs on: an application's own view that reports -1; the merged view handed to MergePolicy.OneMerge#reorder, searched there by a merge policy written for the run; on 6.1.0 and 6.6.6 the misc SlowCompositeReaderWrapper, which left Lucene in 7.0.

Background: three pieces

#
  1. A query-time join (JoinUtil) finds the documents whose key equals the key of documents that another query matched: here the "to" document whose toKey equals the fromKey of a "from" document. With a ScoreMode other than None it also carries the scores across.
  2. A query's scorer reports a cost per segment, an estimate of how many documents it may match, which a search can use for planning. For this join the hits did not depend on it: with other cost values the same hits came back (run).
  3. Terms#size() is the number of distinct terms of a field in a segment. Its javadoc allows one special value: -1 "if this measure isn't stored by the codec".

The finding, step by step

#
  1. Index two documents in one segment: a "from" document with the doc-values field fromKey = k and a "to" document with the indexed field toKey = k. Read the segment through a view that differs in one answer: Terms#size() returns -1, which its javadoc documents as "this measure isn't stored by the codec".
  2. Ask for the join with scores, JoinUtil.createJoinQuery("fromKey", false, "toKey", fromQuery, searcher, ScoreMode.Max), and run searcher.search(join, 10). You expect 1 hit, the "to" document: the plain reader returns it with score 1.0, and the same view returns it for the join without scores (ScoreMode.None).
  3. You get IllegalArgumentException: cost must be >= 0, got -2, with assertions on and off.
  4. Why: to estimate its cost, the join's query multiplies the segment's maxDoc by the to-field's term count, 2 × -1 = -2, and hands the result to a BitSetIterator, whose constructor refuses a negative cost. With the real count the cost is 2 × 1 = 2 and the hit comes back. For segments of 10 and 1000 documents the message says -10 and -1000.
  5. On the same view these returned what the plain reader returns: ScoreMode.None, count(), the join as a FILTER clause, a ConstantScoreQuery around it, a sort by index order, explain(). A search that needs no scores is run as another query and does not reach that line.

Who is affected

#

Applications that run a scoring term join on a reader whose segment reports -1 for the to-field's term count; in the runs on 10.6.0, branch_11x and main that reader was the application's own view or the merged view inside reorder. JoinUtil and Terms are marked experimental. No run returned a wrong hit or score.

Mechanism, terms and numbers1,646 words

Small, and it needs an unusual reader. JoinUtil.createJoinQuery over terms with ScoreMode Max, Min, Avg or Total returns a TermsIncludingScoreQuery. For a search that needs scores, that query estimates its cost per segment as maxDoc * terms.size(), where terms is the segment's Terms of the to-field, and hands the product to a BitSetIterator. Terms#size() may be -1: its javadoc says "or -1 if this measure isn't stored by the codec". The product is then -maxDoc, and BitSetIterator's constructor throws IllegalArgumentException: cost must be >= 0, got -N.

Which reader reports -1. On 10.6.0, branch_11x and main the stock postings formats that were run and the six stock reader views that were run report a real count, and the scoring join returned its hits on each of them. The formats are the 13 on the class path that could write the test index: the default one, five of the codecs module and seven of the test framework; on 10.6.0, run without the test framework, the first six. The readers on which it threw in the runs: an application's own reader view that reports -1; the merged view that IndexWriter hands to MergePolicy.OneMerge#reorder, which is meant for merging and was searched there, during a merge of two segments, by a merge policy written for the run (it caught the exception, and the merge completed); and, on 6.1.0 and 6.6.6, the misc module's stock SlowCompositeReaderWrapper, which left Lucene in 7.0. A codec or an outside postings format that reports -1 was not run. The test's view hides a count that the codec has: it is the smallest form of such a reader, not a reader anybody ships.

What it is and is not. In the runs the failure is a loud exception at the search; no run returned a wrong hit or score. The same join without scores works on the same reader, and so do count(), a FILTER clause, a ConstantScoreQuery around the join, a sort by index order and explain() (run on one segment of 2 documents and on two segments of 5 and 4). JoinUtil and Terms are both marked experimental. The releases 6.1.0 to 10.6.0, each of them run (91), fail the test's first form, which has two checks in front (the plain reader, then the join without scores on the view), at the scoring search; 6.0.1 and the 15 releases before it back to 5.1.0 pass it, because the cost check in BitSetIterator came in 6.1.0 (LUCENE-7262) and met a multiplication that is in the join since 4.3.0 (LUCENE-4607). The 10.6.0 release fails as branch_11x does. That a reader of the count must cope with -1 is a reading: it rests on the javadoc, on sibling code and on a maintainers' exchange of 2017, and nobody upstream has said either way about the join. Two small repair shapes were run; which one is right is for the maintainers.

Why it looks unintended

#
  • Terms#size() javadoc: "or -1 if this measure isn't stored by the codec". The join's javadoc sets no condition on the reader.
  • Lucene kept -1 legal on purpose in 2017 (Robert Muir, Adrien Grand; LUCENE-8007); four stock places test for it, one refuses it.
  • The count feeds only a cost estimate. A reading: maintainers have not said either way.
The full argument470 words

Neither JoinUtil's javadoc nor the join package's documentation says that a reader under a scoring join must report a term count. What follows is the argument; its weak side is in the next block.

  • -1 is the documented value. Terms.java:98-103: "Returns the number of terms for this field, or -1 if this measure isn't stored by the codec."
  • It was kept on purpose. This understanding is the maintainers' own (Robert Muir and Adrien Grand on #9055, LUCENE-8007, 2017). The first patch listed Terms.size() among the statistics that are "now required". Robert Muir: "Do we need the terms.size? I am concerned about a trappy method there: do we need it? I don't see this as an index statistic (e.g. no similarity uses it) but instead a heuristic for sizing datastructures and the like." Adrien Grand: "I can remove that one from the list." and "New patch, allowing Terms.size() to return -1 again." The commit removes the words "or -1 if this measure isn't stored by the codec" from three statistics and leaves them on size(). The same comment can be read as "low value" as well as "must be tolerated".
  • Other stock code tests for the value. AbstractMultiTermQueryConstantScoreWrapper in its own cost estimate (:367-370), CheckIndex (:2387-2389), BPIndexReorderer (:673; the code that the misc module's override of reorder runs on the merged view) and Terms#getMax (Terms.java:153-159). Not every reader of the count does: DatasetSplitter adds it to an approximate count without a test (:112), and DirectPostingsFormat refuses it (:296-299), which is a point for the other side and is in the next block.
  • The join without scores copes with it. Its query takes its estimate from the first class of that list. With 17 and with forty join terms the view returned what the plain reader returns, where the scoring join threw (run).
  • A negative cost is treated as the producer's fault. The test framework asserts cost >= 0 on a scorer supplier's cost (AssertingWeight.java:102-106), and #14150 (merged 2025-01) repaired negative costs of three point queries at the queries that produced them. General evidence only: that assertion does not see this cost, because the scorer is built, and throws, inside scorerSupplier, before a supplier exists.
  • Only an estimate. A cost is documented as an estimate that "may be a rough heuristic, hardcoded value, or otherwise completely inaccurate" (DocIdSetIterator.java:178-184). The numeric join passes the constant 10 (PointInSetIncludingScoreQuery.java:209).
  • History. The multiplication is from 2013 (LUCENE-4607) and the check from 2016 (LUCENE-7262, a change about DocIdSetBuilder that touched no file of the join module). In the releases before 6.1.0 that were run (4.3.0, 4.10.4 and 5.0.0 to 6.0.1) the negative cost was only a wrong estimate. Neither issue thread mentions the join's cost.
The devil's-advocate check338 words

The strongest case for "works as designed" is reach. On 10.6.0, branch_11x and main the stock postings formats and the stock reader views that were run report a real count. The two Terms classes whose size() is the constant -1 (MultiTerms and an inner class of DocValuesRewriteMethod) were not what a searched leaf returned in those runs. The merged view of reorder is documented as meant for merging. The test's view hides a count that the codec has. Both APIs are experimental, and the failure is loud. And there is a stock precedent for requiring the count: DirectPostingsFormat throws IllegalArgumentException("codec does not provide Terms.size()") when it is -1 (DirectPostingsFormat.java:296-299). A maintainer may answer that nothing shipped reports -1 under a searcher, that a custom reader should report a count, and that a reader of the count may require it.

What stands against it: the value is documented on a public abstract method and was kept on purpose; FilterLeafReader, FilterTerms and PostingsFormat are public extension points, and the join's javadoc sets no condition on the reader; sibling code copes with the value; where DirectPostingsFormat refuses it, its message names the cause, while the join's message names a cost; and stock code met it once (the misc SlowCompositeReaderWrapper, run on 6.1.0 and 6.6.6). An earlier run found that TestUtil.checkReader accepts the view whose Terms#size() is -1 and refuses the same view with getDocCount() == -1: that shows that -1 is a legal state of a reader for Lucene's reader checks, not that every query has to accept it.

The reach argument is true. It bounds the weight of the finding (Low) and its wording. As read here, it does not make the input illegal or the exception intended; that is a reading, and no maintainer has said either way about the join. Application side: the view reports the real count, or the search avoids scores (validated by the checks)

#

No Lucene change. An application's own view can report the real count instead of -1. Or it can run the join where no scores are needed.

Trade-offs

  • A way out for one application, not a repair: the exception stays for the next reader that reports the documented value.
  • A view that has no cheap count has no good number to give. With 0 the join returned its hits in the run, but 0 tells other readers of the count that the field has no terms (Terms#getMax returns null for it) and makes the join's cost 0.
