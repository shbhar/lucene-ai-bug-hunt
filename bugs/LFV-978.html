DirectoryTaxonomyWriter.replaceTaxonomy is not failure-atomic: when it throws, close() commits an empty taxonomy and further use commits a broken one

If DirectoryTaxonomyWriter.replaceTaxonomy throws, say on a read error in the new taxonomy, it has already deleted the old one, yet the writer still believes the old categories exist. The usual close() then commits an empty taxonomy (3 categories become 0), and facet counts go silently wrong.

The bug in 30 seconds

#

replaceTaxonomy deletes the old taxonomy first and copies the new one second. If the copy throws, the deletion is already pending, but the writer's ordinal counter and label cache still describe the old categories. Its next commit, for example by close(), saves the deletion, plus any labels added since at the wrong ordinals.

Background: how a taxonomy works

#
  1. Taxonomy facets keep a second index next to the main index. Each category, such as dim/a, is one document there, and its ordinal is its document number. The root category is always ordinal 0.
  2. For counting, main-index documents store these ordinals (they also index the category paths, which drill-down uses). Facet counting adds up ordinals and asks the taxonomy for the label of each, so the two indexes must stay in step.
  3. DirectoryTaxonomyWriter keeps a counter of the next ordinal and a cache from labels to ordinals, so addCategory rarely has to search its index. replaceTaxonomy swaps in another taxonomy, typically a rebuilt one, together with IndexWriter#addIndexes on the main index.

The bug, step by step

#
  1. Commit a taxonomy with one category: root = 0, dim = 1, dim/a = 2, so 3 categories.
  2. Call replaceTaxonomy(source) with a valid, closed taxonomy whose files fail to read. It throws IOException (here on _0.si), and try-with-resources calls close(). You expect the last commit to stay: 3 categories, dim/a at 2.
  3. Instead the committed taxonomy has 0 categories, not even the root, and dim/a is -1. The method had run deleteAll() before the copy failed; the writer still counted 3 categories while an NRT reader on it saw 0, and close() committed the deletion.
  4. Keep using the writer instead and it hands out stale ordinals: addCategory(dim/a) returns 2, which the commit no longer has, and a new dim/c gets 3 but is stored at ordinal 0, the root's slot.
  5. The main index still carries the old ordinals, so later sessions count old documents under new labels, with no error: a=2 b=1 x=1 y=1 comes out as x=3 y=2.

Who is affected

#

Applications that use taxonomy facets (the opt-in facet module) and call replaceTaxonomy, typically to swap in a rebuilt index and taxonomy. One non-fatal exception from that call, then the usual close(), durably destroys the taxonomy; facet counts are silently wrong afterwards. Deterministic, any size. Rare: the method is seldom used, and rollback() after the exception avoids it.

Mechanism, terms and numbers639 words

DirectoryTaxonomyWriter#replaceTaxonomy(Directory) swaps a writer's taxonomy for another one, usually together with IndexWriter#addIndexes on the main index. It calls indexWriter.deleteAll() and then indexWriter.addIndexes(taxoDir), and resets the writer's ordinal counter, label cache, parent arrays and epoch only after both succeed (DirectoryTaxonomyWriter.java:872-891 on main 645d4fe14a20), with no failure handling. When addIndexes throws an exception that is not an Error (an IOException while the source is read, a source with no index, a source still locked by its writer), the internal index is emptied, pending the next commit, while the writer still describes the old taxonomy. close() then commits a taxonomy with no categories at all; continued use returns old ordinals and stores new labels at the wrong ordinals, including the root's slot 0; and facet counts over the main index, which still carries the old ordinals, come out wrong with no error. It has been there since the method was added in 4.0.0-ALPHA (2012). rollback() right after the exception keeps the last commit.

The bug

#
  1. replaceTaxonomy calls indexWriter.deleteAll() (DirectoryTaxonomyWriter.java:874), then indexWriter.addIndexes(taxoDir) (:875), and only then refreshes its reader and resets nextID, the parent arrays, the cache and the epoch (:876-890). There is no ensureOpen() and no try/catch.
  2. addIndexes is all-or-nothing by itself (IndexWriter.java:3084-3086), but the deleteAll() before it is a separate pending change. For a failure inside its try (IndexWriter.java:3114), such as a read error, addIndexes treats only an Error as tragic (IndexWriter.java:3212-3220), so after an IOException the internal writer stays open with every segment about to be dropped; a lock failure on the source is thrown earlier (:3108) and leaves it open as well.
  3. The taxonomy writer stays open too. getSize() returns the stale counter (:575-578); addCategory answers from the stale cache first (:385; the default LRU cache still holds the old labels of this small taxonomy); a new label gets the ordinal nextID.getAndIncrement() (:468-469) but lands at document 0 of the emptied index, the root's place.
  4. close() "commits whatever changes made to it" (:283-294): the deletion, plus whatever was added since.

The numbers

#

Committed taxonomy: root = 0, dim = 1, dim/a = 2. replaceTaxonomy with a valid, closed taxonomy whose _0.si cannot be read throws IOException. Right after it, writer.getSize() is 3 and an NRT reader on the writer sees 0. close() commits size 0; dim/a is -1. Kept open instead: addCategory(dim/a) returns 2, addCategory(dim/c) returns 3, getSize() 4; after close() the commit has size 1, with dim/c at ordinal 0. Over a main index with documents dim/a, dim/b, dim/a, a failed replace and a later session that adds dim/x and dim/y give counts x=3 y=2 instead of a=2 b=1 x=1 y=1: the reopened taxonomy is empty, the next writer adds a root at 0 (:181-185) and gives the old documents' ordinals 2 and 3 to dim/x and dim/y.

When it happens and when not

#
  • Triggers: an I/O error while the source is read or copied (a valid source; the IOException the method declares); a source directory with no index (IndexNotFoundException, for example a rebuilt taxonomy that was never committed); from 4.7.0, a source whose own writer is still open (LockObtainFailedException). The last two are rejected only after deleteAll() ran.
  • Every fault point: failing each of the 36 directory calls of a successful replace in turn breaks the taxonomy under continued use at all 36, and under close() alone at the first 32 (the last 4 fail in the reader refresh after the copy completed, so close() commits the new taxonomy).
  • Not affected: a replace that succeeds; addTaxonomy (safe under all 19 single faults); a caller that calls rollback() right after the exception, which keeps the last commit.
Exposure and likelihood181 words
  • Who is hit. Users of DirectoryTaxonomyWriter who call replaceTaxonomy, as its javadoc suggests, "in conjunction with IndexWriter#addIndexes(Directory...) to replace both the taxonomy and the search index content". No special configuration: the plain DirectoryTaxonomyWriter(Directory) constructor with the writer's own default configuration; the Directory is the caller's choice.
  • What triggers it. An I/O error while the source is read or copied, a wrong or uncommitted source directory, or (since 4.7.0) a source whose writer is still open.
  • Effect. Data corruption that is committed and survives reopen: an empty taxonomy with no root after close(), or one with labels at the wrong ordinals after continued use. Main-index documents that refer to the old ordinals then get no label or another category's label, so facet counts are wrong without any error. Repair needs a taxonomy backup or a re-index of both indexes (inferred, not executed).
  • Scale. Deterministic, single-threaded, any size: the repro has 3 categories.
  • How likely: rare. It needs the rarely used method and an error path. The caller does see the exception, and rollback() right after it keeps the last commit.

Minimal repro

The test shows that a DirectoryTaxonomyWriter.replaceTaxonomy call that throws an IOException while reading a valid, closed source taxonomy has already emptied the taxonomy (deleteAll ran first), while the writer keeps answering from its old cache, and close() commits that emptied index.

Expected vs actual
Expected: addCategory(dim/a) after the failure returns dim/a's existing ordinal (2) and the commit still has dim/a there (a writer that closes itself on the failure is also accepted). Actual: addCategory returns 2, but a reader on the commit gives -1 for dim/a.

Why it is a bug, not intended

#
  • After the throw the open writer breaks its own contracts: addCategory must return an existing category's ordinal, and the root "always has the ordinal 0".
  • The trigger is the declared IOException on a valid source; IndexWriter stays consistent after deleteAll() plus a failed addIndexes (no-index source).
  • Stale writer state after replaceTaxonomy was fixed as a bug twice (LUCENE-4633, LUCENE-5242).
The full argument240 words
  • Contracts. TaxonomyWriter.java:52-53: addCategory "returns its ordinal. If the category was already present in the taxonomy, its existing ordinal is returned." After the failure it returns 2 for dim/a, which the next commit does not have. TaxonomyReader.java:87-92: "The root category (the category with the empty path) always has the ordinal 0"; the writer's constructor says the same (DirectoryTaxonomyWriter.java:183-185). After the failure a new label is stored at ordinal 0. As Shai Erera put it on #5949 (LUCENE-4884), the taxonomy index "has the ROOT document, at doc=0". (#12337 later added a package-private deleteAll() for reindexWithNewOrdinalData, which re-adds every category, root first, before it commits; replaceTaxonomy is unchanged.)
  • A legitimate trigger. A read error on a valid, closed source raises the IOException that replaceTaxonomy declares. After IndexWriter#deleteAll() and an addIndexes that fails on a source with no index (control C2), IndexWriter's maxDoc is 0, matching its pending state; the taxonomy writer instead reports getSize() 3 while an NRT reader on it sees 0.
  • No documented escape hatch. The replaceTaxonomy javadoc (:867-871) says nothing about failure, and nothing says the writer must be rolled back or discarded after one.
  • History. LUCENE-4633 (#5698: the reader was not refreshed) and LUCENE-5242 (#6306: the parent arrays were not reset) fixed stale writer state after a successful replace as bugs, with tests (TestDirectoryTaxonomyWriter.java:400-404, :534-553). The failure path was never discussed (LUCENE-4108, #5180) and has no test.
The devil's-advocate check230 words

The reviews by another model family (OpenAI GPT-5.6) rated this case moderate (the intended-behaviour checker, who built it in full, gave medium confidence for the close()-only part, and the credibility audit pushes back on that part as well): the method was modelled on IndexWriter#deleteAll() + addIndexes() (LUCENE-4108), and IndexWriter's own deleteAll(), failed addIndexes() and close() also commit an empty index; close() is documented to commit "whatever changes made to it"; deleteAll() "can be rolled back using rollback()" (IndexWriter.java:2732-2733) and TwoPhaseCommit#rollback() "Discards any changes that have occurred since the last commit"; a caller who calls rollback() keeps the last commit; two triggers (no index, a locked source) are inputs the method should reject; the class is @lucene.experimental.

Why it fails: the caller made one call, not two, and after a declared, non-tragic exception that call left the writer contradicting its own index, which IndexWriter does not do in the same situation (control C2: deleteAll() + a failed addIndexes leaves its maxDoc and its pending state in step); the committed result is not a valid taxonomy (no root), unlike IndexWriter's empty index; nothing documents rollback() as required; the invalid inputs are rejected only after the deletion. Verdict: a defect. What survives: the close() outcome alone resembles IndexWriter semantics, so an issue should lead with the writer contradicting its index and name rollback() as the workaround.

Suggested fix

#

Recommended Roll back and close on failure; make rollback() safe to repeat

When replaceTaxonomy throws, roll the writer back to its last commit and close it, then rethrow; and make rollback() a no-op on a closed writer, so callers that already call it after a failure keep working. Validated: the repro passes, the whole facet module passes (307 tests) and the module's static checks pass.

public synchronized void replaceTaxonomy(Directory taxoDir) throws IOException {
  ensureOpen();
  try {
    doReplaceTaxonomy(taxoDir); // the old body, unchanged
  } catch (Throwable t) {
    try {
      rollback(); // back to the last commit, and close
    } catch (Throwable t2) {
      t.addSuppressed(t2);
    }
    throw t;
  }
}

One fix was built and validated; two alternatives were not built.

Roll back and close on failure; make rollback() safe to repeat (validated by the checks) (recommended)

#

A change in DirectoryTaxonomyWriter (1 file, +24/-4; tidy leaves it unchanged). The old body of replaceTaxonomy moves to a private doReplaceTaxonomy; replaceTaxonomy adds ensureOpen() and, on any Throwable, calls rollback() (failures there are added as suppressed) and rethrows. Its javadoc gains: "If this method throws an exception, this writer is rolled back to its last commit and closed, as by rollback()."

rollback() drops its ensureOpen() and does nothing on a closed writer, like close() (DirectoryTaxonomyWriter.java:289) and IndexWriter#rollback() ("this acts like close() in closeable", IndexWriter.java:2576-2577). Without that, the fix would break today's workaround: code that calls rollback() in its catch block would get AlreadyClosedException, as a run of the probe with the plain rollback-on-failure sketch shows.

public synchronized void replaceTaxonomy(Directory taxoDir) throws IOException {
  ensureOpen();
  try {
    doReplaceTaxonomy(taxoDir); // the old body, unchanged
  } catch (Throwable t) {
    try {
      rollback(); // back to the last commit, and close
    } catch (Throwable t2) {
      t.addSuppressed(t2);
    }
    throw t;
  }
}

Trade-offs

  • A failure inside replaceTaxonomy rolls the writer back and closes it, like a tragic event in IndexWriter: the caller must open a new one. That held on every tested failure path; if the rollback itself throws, that failure is added as suppressed and the writer may stay open, a corner for maintainers to review.
  • Categories added but not committed before the call are dropped with the rollback.
  • Code that kept using the writer after a failure now gets AlreadyClosedException instead of wrong ordinals.
  • rollback() on a closed writer no longer throws; no upstream test expects it to (testRollback passes).
  • It protects the taxonomy writer only: replacing the taxonomy and the main index together stays a two-writer operation for the application (DirectoryTaxonomyWriter.java:867-871, TaxonomyWriter.java:36-45).

Validate the source before deleting (not built)

#

Check that the source holds an index, that its write lock can be taken and that its segment metadata reads, and only then call deleteAll().

Trade-offs

Keeps the writer usable for bad inputs, but an I/O error later in the copy still leaves the mismatch: on stock code a fault at any of the 32 directory calls inside addIndexes breaks the commit, and a pre-check runs before them. A useful addition to the recommended fix, not a replacement. (A check that reads the source's segment metadata would happen to make the repro pass, since its read error is on _0.si.)

Document rollback() after a failure (not built)

#

A javadoc sentence on replaceTaxonomy: if it throws, call rollback().

Trade-offs

Cheap, but every try-with-resources caller who misses the note still commits an empty taxonomy. Resynchronising the writer from the emptied index instead was considered and not chosen: close() would still commit the deletion.

Downstream note

#

Until a fix ships, applications that call replaceTaxonomy should call rollback() on the taxonomy writer when it throws, instead of close(): that keeps the last commit.

How it was found

#

A planning probe for exception safety saw a failed replaceTaxonomy empty the committed taxonomy. The hunt reduced it to a public-API JUnit, then failed each of the 36 directory calls of a successful replace in turn on the stock jar: every one left the writer out of step with its index. Independent checks then reproduced it.

The method in full205 words

Method: non-formal first signal, then a bounded-exhaustive failure-point enumeration (the hunt's hunt unit for failure atomicity of taxonomy replace and reindex, 2026-10-28, main a9779ef3c193).

  • Lead. LFV-978, snapshot of 2026-10-29

Registry title
DirectoryTaxonomyWriter.replaceTaxonomy is not failure-atomic: if addIndexes throws, the taxonomy is already emptied but the writer keeps its old ordinal counter and cache, so later addCategory calls and the next commit or close() store an empty or broken taxonomy
Area
facet / taxonomy writer (DirectoryTaxonomyWriter.replaceTaxonomy failure path: deleteAll before addIndexes, writer state reset only on success)
Priority
Low, rank 266: Needs the rarely used experimental replaceTaxonomy to throw, followed by close() instead of rollback().
Impact class
data corruption
Impact note
Applications that use the taxonomy facet module with the default DirectoryTaxonomyWriter (default IndexWriterConfig, codec and Directory) and call the rarely used, @lucene.experimental replaceTaxonomy are hit when that call throws a non-fatal exception (an I/O error while a valid, closed source is read or copied; a source directory that holds no index; since 4.7.0 a source still locked by its own writer) and they then close() the writer, as try-with-resources does, or keep using it instead of calling rollback(): close() commits an empty taxonomy with no root, continued use commits a structurally broken one (old ordinals returned for labels the commit no longer has, a new label stored at the root's slot), and main-index documents that still carry the old ordinals then get no labels or other categories' labels, so facet counts are wrong with no error; deterministic, single-threaded, at any size; the caller does see the exception first, and rollback() right after it keeps the last commit.
Summary
You call replaceTaxonomy on a DirectoryTaxonomyWriter to swap in a rebuilt taxonomy, the call throws (in the repro an IOException while a file of a valid, closed source is read, or IndexNotFoundException because the source holds no index), and the application then closes the writer as usual or keeps using it. You expect the failed call to leave the taxonomy that the writer and its last commit describe, so that addCategory returns 'its existing ordinal' for an existing category (TaxonomyWriter.java:53) and the root keeps ordinal 0.
