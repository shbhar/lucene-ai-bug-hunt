DoubleValues.withDefault's block-max bound ignores the default, so FunctionScoreQuery can skip the true top hit

On unreleased main, DoubleValues.withDefault scores a document without a value with the default, but tells top-k search that a block scores at most its largest stored value. With a default of 100 over prices 0-9 (and one document at 50), search(q, 1) returns a document scoring 50 and skips the one scoring 100.

The finding in 30 seconds

#

withDefault gives a document without a value the default score, but its block-max bound is the wrapped field's bound, which only counts documents that have a value. A top-k BooleanQuery trusts that bound, concludes the block cannot reach the top hits and skips it.

Background

#
  1. A value with a default. DoubleValues.withDefault(values, d) (since Lucene 7.0) returns the wrapped value, or d for a document that has none. It reports a value for every document.
  2. Skip index. A numeric doc-values field can opt in to a skip index (NumericDocValuesField.indexedField): for each block of documents (with the default codec normally 4,096 documents that have a value) it stores the smallest and largest value among the documents that have one.
  3. Block-max pruning. For top-k search every clause reports, per block of documents, an upper bound of its scores (getMaxScore). A BooleanQuery of SHOULD clauses adds the clause bounds and skips a block whose sum cannot beat the lowest score still worth collecting.
  4. New in #16431. DoubleValues got getMaxScore; a field source answers with the block's largest value, and FunctionScoreQuery reports (wrapped query's bound) x (value bound) x boost instead of +Infinity. withDefault passes the wrapped bound on unchanged.

The finding, step by step

#
  1. Index 12,288 documents with a price in a numeric doc-values field with a skip index (NumericDocValuesField.indexedField): doc 0 has 50, the others 0-9, and doc 9000 has none. Rank with your own source "price, or 100 when missing": DoubleValues.withDefault(fromLongField("price") values, 100).
  2. Search FunctionScoreQuery(MatchAllDocsQuery, thatSource) OR tag:t with IndexSearcher.search(q, 1). You expect doc 9000: it scores the default 100, every other document at most 50.0018, and explain and an exhaustive search agree.
  3. Instead you get doc 0 with score 50.0018. No error, with assertions on or off.
  4. Why: for pruning, withDefault passes on the field's bound, the largest stored price of each skip-index block: 50, 9 and 9. Doc 9000's block claims "at most 9" although doc 9000 scores 100. Once doc 0 sets the bar at 50.0018, that block's 9 + 0.0018 cannot compete, so it is skipped unseen.
  5. Letting the bound cover the default fixes it: the blocks report 100, 100 and 100, and search(q, 1) returns doc 9000.

Who is affected

#

Applications on main or the 11.0 branch (unreleased, since #16431) that write their own DoubleValuesSource returning withDefault around a field source on a skip-indexed field (opt-in), with a default above some block's largest value, and use it in a FunctionScoreQuery next to another scoring clause. No stock source does this.

Mechanism, terms and numbers600 words

DoubleValues.withDefault(in, missingValue) (LUCENE-7737, Lucene 7.0) returns missingValue for every document the wrapped instance has no value for. #16431 (unreleased, 11.0.0) added block-max bounds to DoubleValues and, in the same diff, a withDefault override of getMaxScore that returns the wrapped instance's bound unchanged. For a field source on a skip-indexed field that bound is the skip-index block's largest stored value, which only counts documents that have a value. When the default is larger, FunctionScoreQuery multiplies the too-low bound into its scorer's bound, and a top-k BooleanQuery skips the block that holds the document without a value, even when it is the true top hit. With the default codec and IndexSearcher.search(q, 1), 12,288 documents return doc 0 (score 50.0018) instead of doc 9000 (score 100). It needs an application-written source that uses withDefault this way; no stock source does. Only main and branch_11x have it. Letting the bound also cover the default fixes it.

The code (main 645d4fe14a20)

#
  1. The default. DoubleValues.java:71-98: withDefault "Wrap[s] a DoubleValues instance, returning a default if the wrapped instance has no value" (:71). advanceExact stores the wrapped answer and returns true (:83-86); doubleValue() returns hasValue ? in.doubleValue() : missingValue (:78-80).
  2. The bound. DoubleValues.java:93-96: getMaxScore(upTo) returns in.getMaxScore(upTo). getMinScore is not overridden, so the lower bound stays -Infinity (:63-69), which is sound; only the upper bound is wrong.
  3. Where the finite bound comes from. fromLongField is fromField(field, v -> (double) v, Monotonicity.INCREASING) and fromIntField returns it (DoubleValuesSource.java:340-347). Its values read the field's DocValuesSkipper (:528-529); advanceShallow returns the current skip interval's last doc (:541-550) and getMaxScore the decoded skipper.maxValue(level) of the first level that covers upTo (:571-584). That covers only documents that have a value, which is right for the plain source: there a document without a value scores 0 (FunctionScoreQuery.java:243-252). Inside withDefault it produces missingValue instead.
  4. The scorer bound. FunctionScoreQuery.java:261-269 returns innerMaxScore * valueMaxScore * boost (it returns +Infinity outright when the value bound is infinite, :265-267); its advanceShallow is the minimum of the wrapped query's and the values' (:254-259). With MatchAllDocsQuery the inner bound is 1.0.
  5. The pruning. For SHOULD clauses under ScoreMode.TOP_SCORES, BooleanScorerSupplier.java:315-328 builds a MaxScoreBulkScorer. Per window it reads each clause's getMaxScore(windowMax - 1) (MaxScoreBulkScorer.java:439); partitionScorers() makes clauses non-essential while their summed bound is below minCompetitiveScore (:474-512, :502), and with no essential clause the window is skipped ("No matches in this window", :133-138). IndexSearcher.search(q, n) collects with a 1,000-hit threshold (IndexSearcher.java:100, :599), so TOP_SCORES is on (TopScoreDocCollector.java:58-60).

The numbers (probe on 645d4fe14a20)

#

Three skip-index blocks: docs 0-4095, 4096-8191 and 8192-12287. withDefault(fromLongField("price"), 100) reports 50.0, 9.0 and 9.0; doc 9000, in the third block, produces 100.0. The function clause's bound there is 1.0 x 9.0 = 9.0, the term clause's 0.0017790452. explain gives doc 9000 100.0 and doc 0 50.001778; the exhaustive top hit is doc 9000 (100.0), search(q, 1) returns doc 0 (50.001778, totalHits "4096+ hits"), and count(q) is 12,288. With the fix the three bounds are 100.0 and search(q, 1) returns doc 9000.

Which compositions

#

Affected (executed): SHOULD + SHOULD disjunctions, MUST function query + SHOULD term, and those under FILTER or MUST_NOT clauses. Not affected (read): a top-level FunctionScoreQuery alone (its FilterScorer does not override setMinCompetitiveScore, so nothing is skipped), and the stock sources: boostByValue wraps the bounded source in withDefault but returns a new DoubleValues without bounds (FunctionScoreQuery.java:294-307); boostByQuery (:371-386) and the five spatial-extras callers wrap DoubleValues that have no bounds.

Exposure and likelihood275 words
  • Who. Applications on main or branch_11x (unreleased 11.0.0) that write their own DoubleValuesSource returning DoubleValues.withDefault(values, d) around a field source with a finite bound (fromLongField, fromIntField, fromFloatField, fromDoubleField, or fromField with a declared monotonicity) on a numeric field with the opt-in doc-values skip index (NumericDocValuesField.indexedField), and use it in a FunctionScoreQuery that is one scoring clause next to another, searched top-k (the default search(q, n)).
  • Trigger. A document without a value in a skip block whose largest stored value is below the default d. A default above the real values (100 over prices 0-9 in the tests) makes that likely; a default of 0 never triggers it for non-negative values. For a fixed index, query and collector the outcome is deterministic: no randomness, no timing.
  • Effect. Silent wrong results: documents without a value, which score the default, are missing from the top hits, including the true top hit; lower-scoring documents are returned in their place. No exception, with assertions on and off, default codec and searcher.
  • Never a superset. In 5 probe runs of 55,848 checks each, no non-matching, filtered-out, excluded or deleted document was returned, and every returned score was exact.
  • Scale. From a few skip-index blocks (12,288 documents in the end-to-end tests); the bound itself is wrong from 2 documents.
  • How likely: rare. It needs custom source code, the opt-in skip index, a default above a block's maximum and a summing composition. No stock source does this, and the only downstream uses found (the lang-expression EmptyMemberValueSource of Elasticsearch and OpenSearch) wrap an instance without a bound (read, not tested). No release has the bug.

Why it looks unintended

#
  • getMaxScore promises "the maximum score that documents between the current position and upTo can produce"; withDefault produces the default for documents without a value.
  • Upstream testMaxScoreBeyondTheCurrentBlock asserts value <= getMaxScore; no upstream test uses withDefault.
  • Before #16431 the bound was +Infinity; every release returns the right top hit, and the #16431 review never mentions defaults.
The full argument184 words
  • The contract. DoubleValues#getMaxScore: "Return the maximum score that documents between the current position and {@code upTo} can produce" (DoubleValues.java:55-58). withDefault produces missingValue for documents without a value and says they have one (:78-86). Scorer#getMaxScore has the same meaning for the scorer (Scorer.java:75-79), and Scorable#setMinCompetitiveScore lets a scorer "safely ignore" only documents that score less (Scorable.java:45-50).
  • Tests. TestDoubleValuesSource.java:412-422 (testMaxScoreBeyondTheCurrentBlock, added by #16697) asserts getMinScore(upTo) <= value <= getMaxScore(upTo) for a produced value. No upstream test calls DoubleValues.withDefault.
  • History. Before #16431 DoubleValues had no bounds and FunctionScoreQuery's bound was +Infinity: always safe. 10.0.0, 10.5.2 and 10.6.0 return the right top hit. The #16431 review discussed the monotonicity of user functions; no comment mentions withDefault, missing values or defaults. The author described the design as "If any layer in the nesting chain is non-monotonic or lacks skip index information, it returns Float.POSITIVE_INFINITY, making nested expressions safe by construction" (rajat315315 on #16431); withDefault is such a layer and does not. The follow-up #16697 fixed other unsound bounds of the same API as defects.
The devil's-advocate check170 words

The strongest case: #16431 added the forwarding override on purpose (it is in the PR's first commit), it keeps the bound tight, and a skip-index bound only has to cover documents that have a value. A second argument: defaults are meant to be neutral (0 or 1). A third: uschindler said in the same review that a user who implements maxScore wrongly for a function like sin() has "your own problem".

Why it fails: "covers only documents with a value" is right for the plain field source, but withDefault reports a value for every document, and the javadoc has no exception for defaults; no review comment chose this trade-off, and a bound below a produced score is not a bound. Nothing documents that defaults must be neutral. The sin() remark is about user code declaring a wrong bound; here the wrong bound is Lucene's own wrapper's, and the user declared nothing. Verdict: not intended, a defect (all verifiers and the adjudication; the cross-model reviewers rated the intended argument only moderate).

Suggested fix

#

Recommended Let withDefault's bound cover the default

In withDefault's getMaxScore, return the larger of the wrapped bound and the default rounded up to float, and keep the wrapped bound for a NaN default. One method in DoubleValues.java; the repro and the 12,288-document test pass, and so do the closest suites and the queries and spatial-extras modules.

float maxScore = in.getMaxScore(upTo);
if (Double.isNaN(missingValue)) {
  return maxScore;
}
// documents without a value produce missingValue, so the bound must cover it too
float missing = (float) missingValue;
if (missing < missingValue) {
  missing = Math.nextUp(missing);
}
return Math.max(maxScore, missing);
All options and trade-offs3 options · 610 words

Option A was built and run through gradle. B would keep more pruning but needs new API; C is safe but gives up pruning for every withDefault user. The sibling fixes in FunctionScoreQuery (LFV-203, LFV-211) do not touch this bug.

Let withDefault's bound cover the default (validated by the checks) (recommended)

#

In DoubleValues.withDefault, getMaxScore (DoubleValues.java:93-96) returns max(in.getMaxScore(upTo), missingValue rounded up to float), and leaves a NaN default out (+10/-1 lines).

float maxScore = in.getMaxScore(upTo);
if (Double.isNaN(missingValue)) {
  return maxScore;
}
// documents without a value produce missingValue, so the bound must cover it too
float missing = (float) missingValue;
if (missing < missingValue) {
  missing = Math.nextUp(missing);
}
return Math.max(maxScore, missing);

Trade-offs

  • Rounding. The bound is a float and the default a double; (float) rounds to nearest, so the value is rounded up when it went down. A default beyond the float range becomes +Infinity, which FunctionScoreQuery treats as no bound.
  • NaN. Math.max(x, NaN) is NaN and would poison the scorer's bound; FunctionScoreQuery scores a NaN value as 0, so the wrapped bound is kept. The hunt's first diff lacked this guard; the adjudication and verifiers flagged it. That bound covers the score 0 only when it is not negative: for a block whose stored values are all negative (and likewise for a negative default) this relies on the sibling LFV-203's clamp of the bound at 0 in FunctionScoreQuery.
  • Cost. The bound rises to the default for every block, also blocks where every document has a value. Sound, but it can switch off pruning for the function clause when the default is above all real values: in the probe the blocks go from 50/9/9 to 100/100/100. Releases never pruned here at all (+Infinity). No benchmark was run.

Add the default only where a document lacks a value (not built)

#

The skipper knows per interval how many documents have a value (DocValuesSkipper#docCount(level)). Compared against the doc range the bound covers, which starts at the shallow-advance target and can begin before minDocID(level) (a document without a value may lie before the interval, DocValuesSkipper.java:37-38), it shows a range without gaps, which could keep the tight bound. The interval's own doc range is not enough: in the minimal repro the level-0 interval is doc 1 alone, with 1 value, while the bound covers docs 0-1 and doc 0 produces 100 (executed by the fact check).

Trade-offs

withDefault only sees a DoubleValues, so this needs a new hook on DoubleValues (for example "may documents up to upTo lack a value?") that the field source implements. More pruning for large defaults, but new API surface for a wrapper. Not built or run.

Drop the override (not recommended)

#

Delete withDefault's getMaxScore override, so it reports the default +Infinity, as before #16431.

Trade-offs

Always safe, but it gives up the pruning #16431 added for every withDefault user, including those with a default of 0. Not run.

How it was found

#

While writing the file-to-line table of an SMT model of FunctionScoreQuery's new bound, the finder mapped each getMaxScore override to the values it must bound and noticed that withDefault forwards a bound that ignores its default. The model itself does not cover withDefault; a public-API JUnit confirmed it, and verifiers then showed the wrong top hit.

The method in full151 words

Method: non-formal (code reading; no formal tool witnessed it). The hunt unit covered function queries and block-max pruning.

  • Reading. The unit's SMT model of the bound pipeline (fsq_bound_smt.py) has a table mapping each model element to code; while filling it, the finder checked every DoubleValues#getMaxScore override against the values it must bound. withDefault is not in the model.
  • JUnit. A public-API test (10 documents, doc 5 without a price, default 100) failed on main with assertions on and off ('value 100.0 of doc 5 > getMaxScore(9) = 9.0') and passed with the fix. The finder first rated it minor and latent.
  • End to end. The first and third verifiers wrote top-hit tests over several skip-index blocks (12,288 documents) and showed a wrong top hit through plain search(q, n), which turned it into a silent-wrong-results bug. The minimal repro above is the finder's test cut down to two documents.

LFV-214, snapshot of 2026-11-08

Registry title
DoubleValues.withDefault's getMaxScore returns the wrapped source's bound, which does not cover missingValue, so a FunctionScoreQuery over such a source can silently drop the true top hit under TOP_SCORES
Area
search / function scoring (DoubleValues.withDefault score bound for FunctionScoreQuery block-max pruning, #16431)
Priority
Low, rank 728: DoubleValues.withDefault forwards a bound that ignores missingValue, so a custom source with a high default can lose its top hit under pruning, unreleased and with no stock source affected.
Impact class
silent wrong results
Impact note
Applications on unreleased main (11.0.0-SNAPSHOT, since #16431) that write their own DoubleValuesSource returning DoubleValues.withDefault(values, d) around a bounded field source (fromLongField and similar) on a numeric field with the opt-in doc-values skip index (NumericDocValuesField.indexedField), with a default d above some skip-index block's maximum, and use it in a FunctionScoreQuery that is a scoring clause next to another scoring clause: the default IndexSearcher.search(q, n) (TOP_SCORES past its 1,000-hit threshold) silently leaves documents without a value out of the top hits, including the true top hit, with the default codec and searcher, -ea or -da, on an index of a few skip-index blocks (12,288 documents in the executed tests); no stock DoubleValuesSource reaches it (boostByValue, boostByQuery and the spatial-extras sources wrap unbounded instances), a top-level FunctionScoreQuery alone does not prune, and no released version is affected.
Summary
You write a DoubleValuesSource that returns DoubleValues.withDefault(DoubleValuesSource.fromLongField("price").getValues(ctx, scores), 100) over a price field indexed with a skip index (NumericDocValuesField.indexedField), and search BooleanQuery(SHOULD FunctionScoreQuery(MatchAllDocsQuery, thatSource), SHOULD TermQuery(tag:t)) for the top hit, expecting the document without a price (which scores the default 100) to win, as it does in an exhaustive search. Instead, with 12,288 documents (prices i % 10, doc 0 = 50, doc 9000 without a price), the plain IndexSearcher.search(q, 1) returns doc 0 (score 50.0018) instead of doc 9000 (score 100). The cause is that withDefault.getMaxScore returns the wrapped source's bound, the skip-index block maximum, which counts only documents that have a value (9 in doc 9000's block), although withDefault itself produces missingValue (100) for documents without one, so pruning skips the block that holds the true top hit.
