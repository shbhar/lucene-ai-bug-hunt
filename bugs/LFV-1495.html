An FSTCompletionLookup build that fails on a full temp disk can leave one temp output open, because ExternalRefSorter.close() writes a footer before it closes its writer

An FSTCompletionLookup build that fails on a full disk can leave one output open: ExternalRefSorter.close() writes a footer before closing its writer; if the disk stays full, that write fails and the close is skipped. The build still throws IOException; one descriptor on a deleted file remains until garbage collection.

The finding in 30 seconds

#

FSTCompletionLookup.build sorts its input through temp files. A helper, ExternalRefSorter, keeps one temp output of its own. Its close() runs CodecUtil.writeFooter(tempOutput) and only then writer.close(), with no try/finally. If the footer write throws, the output is not closed, build ignores the exception, and no code holds a reference that could close it.

Background: the temp files of a build

#
  1. FSTCompletionLookup is a suggester in lucene/suggest. build(InputIterator) writes the suggestions to temp files in the Directory you pass, sorts them on disk and builds an FST from the sorted entries.
  2. build itself opens two temp outputs: its own input file, <prefix>_input_N.tmp, and the output of a helper that sorts the entries once more, ExternalRefSorter, <prefix>_RefSorterRaw_N.tmp. Each is later sorted by OfflineSorter into one more temp file.
  3. Each temp file ends with a 16-byte checksum footer, written just before the file is closed, so that the sort can verify what it reads.

The finding, step by step

#
  1. Build a suggester on a temp directory with no free space: new FSTCompletionLookup(tempDir, "suggest").build(InputIterator.EMPTY). In the test, tempDir is Lucene's MockDirectoryWrapper limited to 1 byte.
  2. build opens two temp outputs, suggest_RefSorterRaw_0.tmp (its sorter's) and suggest_input_1.tmp (its own). Its first write fails and it throws IOException. That is right, and you expect the failed build to have closed both outputs.
  3. It has not. The directory lists no file, but suggest_RefSorterRaw_0.tmp is still open: tempDir.close() throws cannot close: there are still 1 open files: {suggest_RefSorterRaw_0.tmp=1}.
  4. Why: build closes its sorter while cleaning up. ExternalRefSorter.close() first writes a 16-byte checksum footer to that output. The disk is still full, so this write fails too, and the writer.close() on the next line never runs. The file name is then deleted, and build ignores this second exception.
  5. On a real file system it is the same (Linux, OpenJDK 25.0.3): on a 64 KiB tmpfs with 0 bytes free, three builds fail with "No space left on device" and leave 1, 2, 3 descriptors on deleted suggest_RefSorterRaw files. After a garbage collection there are 0. With the fix there are 0 after every build.

Who is affected

#

Applications that build the opt-in, experimental FSTCompletionLookup suggester (the class Solr's FSTLookupFactory builds) on a temp disk that is full and still full while the build cleans up. Minor: the build fails loudly as it should, nothing stays in the temp directory and no suggestion is wrong. One descriptor per failed build stays until garbage collection.

Mechanism, terms and numbers769 words

FSTCompletionLookup.build sorts its input through temp files in the Directory it was given. Before its try block it creates an ExternalRefSorter (FSTCompletionLookup.java:166 on main 781025d6fe32), whose constructor opens a temp output <prefix>_RefSorterRaw_N.tmp (ExternalRefSorter.java:47-51). When a build fails, the only close of that sorter that is reached is the one in the finally of build, IOUtils.closeWhileHandlingException (FSTCompletionLookup.java:248), which ignores every exception; a successful build has already closed the sorter in FSTCompletionBuilder.build() (FSTCompletionBuilder.java:193-195). ExternalRefSorter.close() (:99-108, javadoc "Close the writer and remove any temporary files.") calls closeWriter() (:91-97): CodecUtil.writeFooter(tempOutput); writer.close(); writer = null;, with no try/finally. If the temp disk is still full at that moment, the footer write fails as well: writer.close() is skipped, the file name is deleted, and the second exception is ignored. The caller sees only the first IOException. The output stays open on a file that has no name any more: one file descriptor per failed build on a real file system, until the unreachable stream is garbage-collected (measured on Linux with OpenJDK 25.0.3 and a plain FSDirectory). Nothing stays in the temp directory, no suggestion is wrong and a successful build is not affected. The order comes from LUCENE-7113 (ef7a0125133, 2016), first released in 6.0.0; the same commit guarded the same step with try/finally in OfflinePointWriter.close(). A small change (one file, +5/-3 lines), closing the writer in a try-with-resources around the footer write, fixes it.

Terms

#
  • Temp outputs of a build. build creates an OfflineSorter, an ExternalRefSorter and its own temp input before its try block (FSTCompletionLookup.java:165-168). The ExternalRefSorter constructor opens <prefix>_RefSorterRaw_N.tmp and a ByteSequencesWriter on it (ExternalRefSorter.java:47-51). The sorter is a local variable of build.
  • Footer. CodecUtil.writeFooter writes two ints and a CRC, 16 bytes (CodecUtil.java:410-414, :422-424).
  • Cleanup. The finally of build calls IOUtils.closeWhileHandlingException(reader, writer, externalSorter) (FSTCompletionLookup.java:248; "ignoring all thrown exceptions", IOUtils.java:139-147) and then deletes its temp file names (:249). On a failed build this is the only close of the sorter that is reached; a successful build has already closed it in FSTCompletionBuilder.build() (FSTCompletionBuilder.java:193-195).

The bug

#
  1. ExternalRefSorter.close() (ExternalRefSorter.java:99-108) is try { closeWriter(); } finally { IOUtils.deleteFilesIgnoringExceptions(...) }.
  2. closeWriter() (:91-97) runs CodecUtil.writeFooter(tempOutput); (:93), then writer.close(); (:94), then writer = null; (:95), with no try/finally.
  3. If :93 throws, :94 never runs. close() deletes the file name, build ignores the exception and leaves by throwing its first one. No code holds a reference to the output any more, so no code can close it. On the JDK of these runs the descriptor is released when the unreachable channel is garbage-collected: the JDK's FileChannelImpl registers a cleaner that closes it (FileChannelImpl.java:153-154 in the OpenJDK 25.0.3 sources).
  4. On a file-system directory the footer write fails even for an empty sorter file: writeFooter asks the output for its checksum (CodecUtil.java:687-688), and OutputStreamIndexOutput.getChecksum() flushes the buffered bytes first (OutputStreamIndexOutput.java:102-106). That flush is where the kernel reports the full disk: on the full tmpfs the sorter alone, with no entry added, throws No space left on device from OutputStreamIndexOutput.getChecksum:104, under CodecUtil.writeFooter:413 and ExternalRefSorter.closeWriter:93 (executed). In the repro the test directory throws earlier, at the first footer byte (CodecUtil.writeFooter:411).

Afterwards: 1 open handle, suggest_RefSorterRaw_0.tmp, deleted but open; the directory lists no file.

  • The sorter alone: ExternalRefSorter.close() on the full directory throws fake disk full ... when writing suggest_RefSorterRaw_0.tmp from closeWriter:93 and leaves 1 open handle; a second close() repeats the failed write. This is the exception that build ignores.
  • Control: on a healthy directory the empty build succeeds with 0 open handles.
  • A real disk (a 64 KiB tmpfs with 0 bytes free, a plain FSDirectory, one suggestion, three builds; Linux, OpenJDK 25.0.3): each build throws No space left on device; the process then holds 1, 2, 3 descriptors, on suggest_RefSorterRaw_0.tmp (deleted), _2 and _4; the directory lists no file; after System.gc() there are 0. Under a file-size limit of 0 (File too large) the counts are the same.
  • With the fix: 0 open handles and 0 descriptors in every case above.
Exposure and likelihood404 words
  • Who. Applications that call FSTCompletionLookup.build (lucene/suggest; the class is @lucene.experimental, ExternalRefSorter also @lucene.internal) when writes to the suggester's temp directory fail and still fail at the moment the sorter is closed. In practice a temp disk with no free space. Solr's FSTLookupFactory builds this class on an FSDirectory over java.io.tmpdir (read, not run).
  • Default settings, no scale. No option is involved, and an empty input is enough.
  • What stays. One open output per failed build on an already deleted temp file: on a real file system one file descriptor, released when the unreachable stream is garbage-collected (1, 2, 3 after three failed builds; 0 after System.gc()). This was measured on Linux with OpenJDK 25.0.3 and a plain FSDirectory. The release at collection is JDK implementation behaviour, and System.gc() is only a request: without a collection the descriptor stays.
  • What does not happen. The build fails loudly with the IOException of the first failed write, as it should. Nothing stays in the temp directory. No suggestion is wrong: the lookup's fields are assigned only at the end of a successful build (FSTCompletionLookup.java:242-245), so a lookup built earlier is unchanged. A successful build is not affected.
  • How often a real disk hits it. The footer write fails only if the disk still rejects writes when the sorter is closed. In an earlier sweep over 256 sizes of a size-limited tmpfs (20000 suggestions; not re-run for this doc) the descriptor was left in 88 of 235 failed builds: the sizes that cannot hold the build's own input file, or that it fills exactly. The leaked file was then empty. Of the 148 builds that failed inside OfflineSorter.sort, 147 left nothing open, because the sort deletes its partial files first and the 16 footer bytes then fit; the one exception is the size that the input file fills exactly, which is counted in the 88. A leaked file that holds data needs another writer taking the space during the build (run there: 65536 bytes held until garbage collection).
  • Likelihood: rare. Suggester builds that fail on a full temp directory are reported by Solr users (SOLR-10937, with another suggester), so the trigger is real but exceptional. No report of this leak was found.
  • Not checked. Windows, where deleting a still-open file can fail. Other JDKs and other Directory implementations: whether and when an output that nothing references is released there.

Why it looks unintended

#
  • ExternalRefSorter.close() is documented "Close the writer and remove any temporary files." Here it does not close the writer.
  • The commit that added the footer write (LUCENE-7113) guarded the same step with try/finally in OfflinePointWriter.close().
  • The same order was reported and fixed as a file handle leak in another class (#8056, Robert Muir); Lucene's test directory rejects the state.
The full argument315 words

There is no written contract for a failed build. Lookup.build says only "Builds up a new internal Lookup representation based on the given InputIterator. The implementation might re-sort the data internally." (Lookup.java:178-182). The argument is close()'s own javadoc, the code around it and history:

  • close() says what it does. ExternalRefSorter.close(): "Close the writer and remove any temporary files." (ExternalRefSorter.java:99). On this path the writer is not closed.
  • The same commit guarded the same step. LUCENE-7113 (ef7a0125133, 2016), which put the footer write in front of writer.close() here, wrote OfflinePointWriter.close() as try { CodecUtil.writeFooter(out); } finally { out.close(); closed = true; } (still OfflinePointWriter.java:110-119).
  • The other footer writes of the module sit under a close. SortedInputIterator writes its footer inside a try-with-resources on the writer (SortedInputIterator.java:180-190). FSTCompletionLookup.build and AnalyzingSuggester.build write the footer of their own temp input under a finally that closes the writer (FSTCompletionLookup.java:194-195 with :248; AnalyzingSuggester.java:486-487 with :594).
  • The same order was called a leak and fixed. #8056 (LUCENE-6999, Robert Muir, 2016), on Lucene60PointsWriter.close(): "This will leak a file handle on e.g. disk full or other exceptions", quoting CodecUtil.writeFooter(dataOut); // something bad happens followed by dataOut.close();. It was fixed in 6.0, seven weeks before the footer write was added here.
  • The intent for this build. #5281 (LUCENE-4209, 2012) made build close its sorter (CHANGES.txt:15406-15409). Uwe Schindler's patch note there: "Patch that enforces cleanup of all temporarily generated files on success or failure"; Robert Muir: "Then we can verify everything (including windows correctness and no leaks) with MockDirectoryWrapper." These speak of temp files and are cited as intent, not as a contract.
  • Lucene's test directory rejects the state. MockDirectoryWrapper.close() fails while an output is open; that is the check the repro uses. No test in lucene/suggest makes a temp-file write fail, so this path was never exercised.
The devil's-advocate check205 words

The strongest case for "intended or accepted": both classes are experimental and ExternalRefSorter is internal; no javadoc says what a failed build leaves behind; build closes its helpers with closeWhileHandlingException, so it ignores cleanup errors on purpose; java.io.Closeable only advises releasing resources before throwing; the build has already failed, and the JDK used here closes the descriptor when the stream is collected. And the guarded form is not a rule that all of Lucene follows: one more unguarded footer-write-then-close pair exists today, in the hunspell module (SortingStrategy.java:84-85).

Why it fails as to intent: ignoring an exception is the caller's choice, leaving the output open is the callee's. close() says it closes the writer. The commit that created the order wrote the guarded form of the same two lines in another class, and the same order had been reported and fixed as a handle leak weeks before. Every other footer write in the module sits under a close.

What survives is size, not intent: one descriptor until garbage collection, after a build that has already failed. That is why this bug is ranked at the bottom of Low; a maintainer could reasonably decide that it is not worth a change of its own.

Suggested fix

#

Recommended Close the writer around the footer write (validated)

In ExternalRefSorter.closeWriter(), close the writer in a try-with-resources around the footer write, the guard OfflinePointWriter.close() already has: one file, +5/-3 lines. Validated: the test passes with assertions on and off, the suggest module's 237 tests show no failure, and the module's checks pass.

  private void closeWriter() throws IOException {
    if (writer != null) {
      // close the output even when the footer cannot be written
      try (OfflineSorter.ByteSequencesWriter _ = writer) {
        writer = null;
        CodecUtil.writeFooter(tempOutput);
      }
    }
  }
All options and trade-offs2 options · 728 words

One fix was built and validated with gradle. An alternative was built and checked more lightly.

The neighbouring LFV-1493 and this bug. LFV-1493's recommended fix (creating the sorter inside the try block of build, after the first sort) does not touch closeWriter(), but with it alone the test of this doc passes, because the build then fails before the sorter exists; on the full 64 KiB tmpfs it leaves 0 descriptors after each of three failed builds. The defect stays: ExternalRefSorter.close() alone still leaves its output open on a full directory, and so does a build whose writes start to fail once the sorter exists (executed: 1 open handle each, 0 with both fixes). With LFV-1493's other option, a guard around the second temp-output creation, the test still fails. So if both changes go in together, the regression test for this fix is the check on the sorter alone (under Minimal repro).

Close the writer around the footer write (validated) (recommended)

#

closeWriter() closes the writer in a try-with-resources around the footer write, so the output is closed whether or not the footer can be written. It is the guard that OfflinePointWriter.close() got in the introducing commit, written as a try-with-resources so that an exception from the close is added to the footer's exception as suppressed. One file, +5/-3 lines.

  private void closeWriter() throws IOException {
    if (writer != null) {
      // close the output even when the footer cannot be written
      try (OfflineSorter.ByteSequencesWriter _ = writer) {
        writer = null;
        CodecUtil.writeFooter(tempOutput);
      }
    }
  }

Trade-offs

  • For build nothing changes but the closed output: close() still throws the footer's IOException and build still ignores it; the output is closed first.
  • What changes is the state of the sorter after a failed footer write: it cannot be used again. A second close() returns; add() throws IllegalStateException, with the message written for a sorter whose iterator() has been called; and after a footer write that failed inside iterator(), a second iterator() sorts a file without a footer and fails its checksum check with CorruptIndexException (all executed). Today a second call repeats the failed write.
  • The resource variable must be the unnamed _: Lucene compiles with -Xlint:try -Werror, which rejects a named resource that the body never uses (executed with javac). The file already has try (Closeable _ = ...) at line 78.

What the checks validated

  • Scratch checkout of 781025d6fe32, gradle. Stock: the test fails with assertions on and off; upstream TestBytesRefSorters passes 3 of 3.
  • With the fix: the test passes with assertions on and off.
  • The whole suggest module with the fix (:lucene:suggest:test): 32 classes, 237 tests, 0 failures, 7 skipped. The suggest.fst package also passes with assertions off: 4 classes, 25 tests, 0 failures, 1 skipped.
  • :lucene:suggest:check -x test (format, ecj lint, forbidden APIs) passes with the fix and the test in the tree.
  • Standalone runner with the fixed class in front of the main jars: the test passes with assertions on and off; the evidence probe shows 0 open handles in every case; on the full 64 KiB tmpfs and under a file-size limit of 0 there are 0 descriptors after each of three failed builds.
  • Not run: nightly tests, benchmarks, Windows.

Do not write a footer in close() (validated by the checks)

#

close() deletes the unsorted file right after closing it, so only iterator(), which sorts the file, needs the footer. close() would call IOUtils.close(writer) instead of closeWriter() and clear writer in its finally. One file, +3/-1 lines.

Trade-offs

Saves a write to a file that is about to be deleted, and close() no longer throws when only the footer cannot be written. closeWriter() stays unguarded for iterator(): if the footer write fails there, the output stays open until the caller calls close() (executed: 1 open handle after the failed iterator(), 0 after close()). A slightly larger behaviour change than the first option.

What the checks validated

Checked more lightly than the first option. Standalone runner, with the changed class in front of the main jars: the test passes with assertions on and off and the evidence probe shows 0 open handles in every case. Through gradle the suggest.fst package passes with the change: 25 tests, 0 failures, 1 skipped, the new test included. The whole module and the checks were not run with it.

How it was found

#

Semi-formal. A fault matrix made the temp files of Lucene's offline sorts and suggester builds fail one at a time (359 cases, on main and on 10.6.0) and checked one invariant: after a failed build no temp file is left and nothing is open. FSTCompletionLookup.build broke it when every write to its sorter's temp output failed.

The method in full203 words

Method: semi-formal (bounded-exhaustive fault injection on the real jars against a stated invariant; no model checking, solver or proof tool was involved).

  • The fault matrix. A wrapper around the temp Directory made one thing fail per run: the k-th temp output on create, on every write, on every write from its 40th on, or on close, or the n-th read. 359 cases over OfflineSorter.sort, five suggester builds (AnalyzingSuggester, FuzzySuggester, FSTCompletionLookup, WFSTCompletionLookup, TSTLookup) and BKDWriter's offline sort, on main and on the 10.6.0 release jars.
  • The invariant. After a failed offline sort or suggester build no temp file is left and no output or input is open.
  • First signal, the same on both builds: FSTCompletionLookup.build 1x OUT write: threw Marked | filesLeft=0[] openOutputs=1 openInputs=0 first=[k=0]. With every write to the first temp output the build creates, the sorter's, failing, one output stayed open; with the writes to any other temp output failing, none did. No other build or sort of the seven left an output open in any case.
  • Cause and reduction. Reading closeWriter() gave the cause. The case was reduced to a public-API test and then to the one-method test of the repro.

Introduced by LUCENE-7113 (ef7a0125133, 2016-03-19), first released in 6.0.0 and present in every release since. The test fails on main, on the 11.0 branch (11.0.0-SNAPSHOT) and on 10.6.0. An old defect, introduced in 6.0.0: not a recent regression and not new in 11.0.

Versions tested9 rows

Introduced by ef7a0125133, "LUCENE-7113: add best-effort checksum verification to temp files written by OfflineSorter and BKDWriter" (Michael McCandless, 2016-03-19; issue #8168; committed from the patch on the issue; no CHANGES.txt entry), with the same change on the release branches as e458385b5e9 (6.0.0, 6.0.1) and 70290e89476 (6.1.0 to 6.6.6). It put CodecUtil.writeFooter(input); in front of writer.close(); writer = null; in closeWriter(). Before it the method only closed the writer, so nothing could fail in front of the close. git log -S'CodecUtil.writeFooter' on the file, in the history of main, names only this commit. Since then only a rename touched the line (2e57a405463, LUCENE-10139, 9.0.0).

The same commit wrote the guarded form of the same step in OfflinePointWriter.close().

First affected release: 6.0.0. A variant of the test without the test framework (the same fault, input and observation) fails on the 6.0.0 jars and passes on the same jars with only that one line removed from closeWriter(). 5.5.5 and earlier are not affected: closeWriter() is writer.close(); writer = null; at all 43 release tags from 3.6.0 to 5.5.5.

Affected: every release from 6.0.0 to 10.6.0 (93 releases), the 11.0 branch and main. The releases that were not executed have the same unguarded two lines at their tags.

The 11.0 branch (branch_11x daa54f2e0cd3): both files are identical to main, and the test fails there with assertions on and off, so 11.0.0 would ship it as every release since 6.0.0 has.

LFV-1495, snapshot of 2026-11-20

Registry title
ExternalRefSorter.close() does not close its temp output when the footer write fails, so an FSTCompletionLookup.build that fails on a full disk keeps a file descriptor on a deleted temp file until garbage collection (since 6.0.0)
Area
suggest / FSTCompletionLookup build (ExternalRefSorter: cleanup of the sorter's temp output when a build fails)
Priority
Low, rank 1227: In every release since 6.0.0, an FSTCompletionLookup build that fails on a full temp disk can leave one output open on an already deleted temp file (one file descriptor) until garbage collection. It is Low because the suggester is opt-in, the build already fails loudly, no file is left in the temp directory and no suggestion is wrong.
Impact class
minor
Impact note
Hits applications that build the opt-in, experimental FSTCompletionLookup suggester (lucene/suggest; the class that Solr's FSTLookupFactory builds), with default settings and no scale, when writes to the suggester's temp Directory fail and still fail at the moment the sorter is closed, in practice a temp disk with no free space: the build fails loudly with the IOException of the failed write, as it should, but each such failed build leaves one output open on the already deleted <prefix>_RefSorterRaw_N.tmp (on a real file system one file descriptor, and the deleted file's blocks if it holds data) until the stream object is garbage-collected; nothing stays in the temp directory, no suggestion is wrong, a lookup built earlier is unchanged and a successful build is not affected.
Summary
You build an FSTCompletionLookup suggester and the build fails because the disk under its temp directory is full (a write throws IOException). You expect the failed build to close every temp output it opened: build closes its sorter in a finally block, and ExternalRefSorter.close() is documented as 'Close the writer and remove any temporary files'. Instead close() first writes a checksum footer to the sorter's temp output; on the full disk that write fails too, so the output is never closed and build swallows this second error: the caller sees only the first IOException, while the output on the already deleted <prefix>_RefSorterRaw_N.tmp stays open until the garbage collector reclaims it (one file descriptor per failed build on a real file system). LFV-1493 is the other gap in the cleanup of the same build: a temp-file creation that fails before the cleanup block is entered.
