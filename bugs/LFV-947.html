CompositeVerifyQuery reports itself cacheable without asking its index query, so a query cache keeps old matches after an in-place doc-values update

CompositeVerifyQuery tells the query cache it is cacheable by asking only its shape check, never the index query it runs. If that index query reads a doc-values flag you update in place, the cached query keeps its old matches: [0, 1, 2] instead of [1, 2, 4] in the repro.

The bug in 30 seconds

#

CompositeVerifyQuery finds candidates with a cheap index query, then checks each one against an exact shape. Before reusing a cached result on a segment, the query cache asks the query whether that is safe after doc-values updates; this query answers for its shape check only.

Background: three pieces

#
  1. CompositeVerifyQuery(indexQuery, predicate) in spatial-extras runs indexQuery to find candidate documents, then checks each candidate against an exact shape (the predicate). Its constructor is public and accepts any query.
  2. A query cache (LRUQueryCache) stores a query's matching documents per segment. Before it reuses an entry it asks the query's Weight isCacheable(segment). A Weight that reads doc values must say no once those doc values were updated in place.
  3. IndexWriter#updateNumericDocValue changes a doc-values field without rewriting the segment. The reopened segment can keep its cache key (it does in the repro), and then only that isCacheable answer stops the cache from serving old matches.

The bug, step by step

#
  1. Index six shops at points (0,0) to (5,5) with a CompositeSpatialStrategy; shops 0-2 are open (open = 1, a doc-values field). Search new CompositeVerifyQuery("in the area" AND open == 1, exact shape check) through a query cache: [0, 1, 2].
  2. Shop 0 closes and shop 4 opens: two updateNumericDocValue calls on open, then reopen the reader. You expect [1, 2, 4], and an uncached searcher on the new reader returns [1, 2, 4].
  3. Instead the same search through the cache returns [0, 1, 2]. Asked "is your cached result still valid?", the composite checks only its shape field, which did not change, and never asks its index query, which would say no. The in-place update left the segment's cache key unchanged, so the old entry is served.
  4. It lasts until the segment is merged or the entry is evicted or cleared. On 7.2.0-10.5.2 and the 10.6 branch the default IndexSearcher cache is enough; main has no default cache, so the application must install one. CompositeSpatialStrategy's own queries are not affected.

Who is affected

#

Applications that build CompositeVerifyQuery themselves around an index query that reads a doc-values field (an open or visible flag next to the spatial filter), update that field in place, and keep a query cache across reopens: the default IndexSearcher cache on 7.2.0-10.5.2 and the 10.6 branch, an installed one on main. Rare: no in-tree code builds such a query.

Mechanism, terms and numbers937 words

CompositeVerifyQuery(Query indexQuery, ShapeValuesPredicate predicate) (spatial-extras, public constructor, @lucene.experimental) finds candidates with its index query and verifies each one with the shape predicate. Its Weight iterates the index query's scorer as the approximation of every match, but its isCacheable asks only the predicate (return predicateValueSource.isCacheable(ctx);, CompositeVerifyQuery.java:113-116 on main a9779ef3c193). LRUQueryCache trusts Weight#isCacheable and keys entries on the segment's core cache key, which a doc-values update may leave unchanged (LeafReader allows it, and in the repro it stays the same). So when the index query reads a doc-values field that is updated in place (IndexWriter#updateNumericDocValue or updateBinaryDocValue), the entry cached before the update keeps being served after the reopen: [0, 1, 2] instead of [1, 2, 4] for an "in the area AND open" index query, [0, 1, 2] instead of [1, 2] for a bare newSlowExactQuery, 5025 instead of 5024 hits with the release-default cache settings. The index query on its own is correctly uncacheable on that segment. On 7.2.0-10.5.2 and the 10.6.0 release-candidate branch a plain IndexSearcher reproduces it with zero configuration; main has had no default cache since #14187 (unreleased), so there it needs an installed cache. CompositeSpatialStrategy's own queries (prefix-tree index queries) are not affected. Introduced by LUCENE-8042 (276e317e942), which replaced a never-cacheable "TODO delegate to PredicateValueSource?" with the predicate check and left out the index-query Weight built in the same method. The fix ANDs indexQueryWeight.isCacheable(ctx) in.

Terms

#
  • CompositeVerifyQuery: "A Query that considers an 'indexQuery' to have approximate results, and a follow-on ShapeValuesSource is called to verify each hit" (CompositeVerifyQuery.java:33-35; the field comment at :41 says "approximation (matches more than needed)"). Public constructor (:44), @lucene.experimental (:37). CompositeSpatialStrategy builds it around a prefix-tree (RPT) query; applications can build it around any query.
  • Query cache: LRUQueryCache stores the matching documents of a query per segment, keyed on the query and the segment's core cache key. It asks Weight#isCacheable(leaf) before it reads or writes an entry (LRUQueryCache.java:816-834 and :903-921).
  • In-place doc-values update: IndexWriter#updateNumericDocValue and updateBinaryDocValue change a doc-values-only field without rewriting the segment. The reopened segment may keep its core key: "Two readers that have the same data but different sets of deleted documents or doc values updates may be considered equal" (LeafReader.java:66-70); the test asserts it does. That is why a query that reads an updated doc-values field must say it is not cacheable: "Updated doc values fields are not suitable for caching" (SegmentCacheable.java:30-32).

The bug

#
  1. createWeight builds the index query's Weight once (CompositeVerifyQuery.java:95-97) and feeds its scorer's iterator to the predicate's two-phase iterator (:102-108): every match is an index-query match that the predicate confirmed.
  2. isCacheable returns predicateValueSource.isCacheable(ctx) and nothing else (:113-116).
  3. A doc-values index query such as NumericDocValuesField.newSlowExactQuery("open", 1) reports DocValues.isCacheable(ctx, "open") (SortedNumericDocValuesRangeQuery.java:119-121), false once the field was updated in that segment (DocValues.java:339-346); a small BooleanQuery ANDs its clauses' answers (BooleanWeight.java:272-285). The composite's Weight never asks it.
  4. After the update and reopen, the cache asks the composite's Weight, gets true, finds the old entry under the unchanged core key and returns it. The index query's Weight is not consulted, because the outer entry is served before the composite's scorer is built.

The numbers

#

Six shops at (i, i), one segment, indexed with a CompositeSpatialStrategy; shops 0-2 open. CompositeVerifyQuery(BooleanQuery(FILTER rpt Intersects area, FILTER open == 1), exact shape Intersects area) returns [0, 1, 2]. After updateNumericDocValue(id:0, open, 0), updateNumericDocValue(id:4, open, 1) and openIfChanged: uncached [1, 2, 4], cached [0, 1, 2]: a closed shop returned, an open one missing. The same flag as a sibling clause outside the composite is correct through the same cache. With the bare index query newSlowExactQuery("v", 1) and doc 0 changed from v=1 to v=2: cached [0, 1, 2] instead of [1, 2]. With the release-default cache settings (LRUQueryCache(1000, 32 MB), which is the releases' min(32 MB, heap/20) for heaps of 640 MB or more, and UsageTrackingQueryCachingPolicy; 10,050 documents, query counted 10 times): 5025 instead of 5024. The composite's isCacheable is true on the updated segment while the index query's is false.

When it happens and when not

#
  • Needs: an index query that reads a doc-values field, an in-place update of that field, the composite cached on that segment before the update, and a cache that survives the reopen. The composite must run without scores, as a count, a filter clause or a no-score collector does: only then does IndexSearcher#createWeight wrap it in the cache (IndexSearcher.java:976-982).
  • Affected index queries (model-based harness, 14 stale results): newSlowExactQuery, newSlowRangeQuery, a BooleanQuery with such a FILTER clause, FieldExistsQuery on a doc-values field, SerializedDVStrategy.makeQuery after a binary doc-values update.
  • Not affected, by the code: CompositeSpatialStrategy.makeQuery (Intersects builds an IntersectsRPTVerifyQuery, CompositeSpatialStrategy.java:122-134; the other operations wrap an RPT query, :154-155, whose Weight is always cacheable, AbstractPrefixTreeQuery.java:107-108, or a TermQuery for a point shape on a points-only grid, also always cacheable, RecursivePrefixTreeStrategy.java:185-187, 216-229, TermQuery.java:192-194).
  • No mismatch observed in the harness (its 9 index-query kinds x 9 index operations) for TermQuery, IntPoint range and kNN index queries, an update of the predicate's own shape field, deletes, new segments and updateDocument.
  • The stale entry ends when the segment is merged into a new one, the entry is evicted, the application clears the cache (LRUQueryCache.java:458), or searches switch to another cache; LRUQueryCache#close keeps the entries and only stops an optional cleanup thread (:264-275). The duration in a running application was not measured.
Exposure and likelihood290 words
  • Intended public use. LUCENE-5579 (#6641), which added the class, "Pulled out the inner Query instances to live in the 'composite' package, so that they might be used by users who want to build with these constructs", after asking how users "can put other query/filters in-between RPT and the SerializedDVStrategy". An index query that ANDs the prefix-tree query with a doc-values flag fits that description.
  • 7.2.0 to 10.5.2 and the 10.6 branch: the default configuration. IndexSearcher has a JVM-wide default LRUQueryCache(1000, min(32 MB, heap/20)) with UsageTrackingQueryCachingPolicy (10.5.2 IndexSearcher.java:83-99). It caches only segments of at least 10,000 documents that are large relative to the index (LRUQueryCache.java:251-253, 278-296), and a query only after repeated use. One 10,050-document segment and the query counted 10 times reproduce it with no cache code at all on 7.2.0, 8.11.4, 9.12.3, 10.5.2 and branch_10_6 (5025 instead of 5024); an independent program with 12,000 documents gives 6000 instead of 5999 on 10.5.2 and branch_10_6.
  • main: opt-in. There is no default cache since #14187 (IndexSearcher.java:84, not yet released); MIGRATE.md:227-236 shows how to turn it back on.
  • Effect. Silent wrong hit lists and counts for the documents whose field changed, in both directions; no exception. With the shared default cache, any searcher in the JVM that runs the same query without scores on the same segment core can get the stale entry.
  • Scale. Ordinary: six documents with a cache that accepts every segment; one segment of about 10,000 documents with the default cache (LRUQueryCache.java:251-253).
  • How likely: rare. The only in-tree producer, CompositeSpatialStrategy, passes prefix-tree queries, which cannot change in place; no Lucene query parser builds a CompositeVerifyQuery; no spatial-extras test touches caching; no outside report was found in the documented searches.

Why it is a bug, not intended

#
  • The cache contract says doc-values readers must report updated fields as not cacheable (SegmentCacheable.java:30-32); a core test: "all composites referring to it should be uncacheable".
  • Core wrappers that run an inner query (FilterWeight, ConstantScoreQuery, FunctionScoreQuery) include its answer; LUCENE-8042 left this one out.
  • Nothing restricts the index query; LUCENE-5579 made the inner queries public for users' own compositions.
The full argument276 words
  • Contract. SegmentCacheable.java:30-32: "Objects that depend on doc values should return DocValues#isCacheable(LeafReaderContext, String...), which will check to see if the doc values fields have been updated. Updated doc values fields are not suitable for caching." QueryCache.java:28-30: the caching wrapper "will only be equivalent if scores are not needed"; the repro collects and counts without scores.
  • Upstream test. TestSegmentCacheables.java:84-92: "after field3 is updated, all composites referring to it should be uncacheable". TestLRUQueryCache.java:2222 (testDocValuesUpdatesDontBreakCache) tests the cache against doc-values updates with a test query whose Weight returns DocValues.isCacheable (DVCacheQuery, :2165, :2213): after the update that segment is no longer cached (:2271-2284).
  • Precedent in core and queries. FilterWeight.java:47-50 (return in.isCacheable(ctx)), ConstantScoreQuery.java:192-195 (innerWeight.isCacheable(ctx)), BooleanWeight.java:272-285 and FunctionScoreQuery.java:279-282 (inner.isCacheable(ctx) && valueSource.isCacheable(ctx)). LUCENE-8042 gave FunctionScoreQuery a value-source-only answer too; LUCENE-7736 (#8787; 2a4dd499bbd on master and 03afeb7766a on the 7.x line, both committed 2017-11-15, in 7.2.0) ANDed its inner Weight in: a precedent for the fix.
  • History. LUCENE-8017 (a886a001a4c) made this Weight never cacheable: return null; // TODO delegate to PredicateValueSource?. LUCENE-8042 (276e317e942, by romseygeek, +1 by rmuir, 107 files, 7.2.0) resolved the TODO by delegating to the predicate only; the indexQueryWeight was already in the same method. LUCENE-8017 had already made ConstantScoreQuery, FilterWeight and BooleanWeight delegate to their inner Weights' cache helpers, and LUCENE-8042 kept that delegation in isCacheable. No comment on #9065 or #9090 mentions CompositeVerifyQuery or its index query.
  • Docs. No javadoc, package doc, CHANGES or MIGRATE entry says the index query must be segment-immutable. @lucene.experimental is about API stability, not correctness; the sibling IntersectsRPTVerifyQuery is @lucene.internal.
The devil's-advocate check256 words

The intended-behaviour checker and a reviewer from another model family (OpenAI GPT-5.6) built the strongest case: (a) the composite package was built for RPT plus serialized shapes, and the only in-tree producer passes an RPT postings query, for which asking the predicate only is exactly right; (b) the sibling IntersectsRPTVerifyQuery uses the same predicate-only rule (IntersectsRPTVerifyQuery.java:157-158), and IndexOrDocValuesQuery#isCacheable also asks only one sub-query (IndexOrDocValuesQuery.java:211-214); (c) the class is @lucene.experimental; (d) a user can put the doc-values filter outside the composite as a sibling clause; (e) main has no default cache.

Why it fails: (a) convention is not a contract; the constructor is public, accepts any Query, and LUCENE-5579 contemplated users putting other filters between RPT and the serialized shapes. (b) IntersectsRPTVerifyQuery builds its approximation internally from prefix-tree terms, so predicate-only is correct there; IndexOrDocValuesQuery relies on its documented precondition "Both provided queries must match the same documents" (:61), and the "delegate to the indexQuery" remark on #9065 was about that query; here the two parts are different conditions. (c) Experimental allows API changes, not wrong results. (d) A workaround does not make the wrapping illegal, and nothing tells users to use it. (e) The cache is public, MIGRATE.md shows how to re-enable it, and it is the default in every release since 7.2.0 and on the 10.6 branch. Verdict: not intended: the independent reproducer rated the intended case weak, the second cross-model review moderate and rejected it, the devil's advocate "high that it is not intended".

Suggested fix

#

Recommended Also ask the index query's Weight (validated)

In CompositeVerifyQuery's Weight, also ask the index query: return indexQueryWeight.isCacheable(ctx) && predicateValueSource.isCacheable(ctx); (one line, the shape of FunctionScoreQuery). The new test passes 5 of 5 and the whole spatial-extras module passes, with assertions on and off; the in-tree prefix-tree composite stays cached.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  return indexQueryWeight.isCacheable(ctx) && predicateValueSource.isCacheable(ctx);
}

One fix was built and validated; two alternatives were not built.

Also ask the index query's Weight (validated) (validated by the checks) (recommended)

#

A one-line change in CompositeVerifyQuery.createWeight's anonymous Weight (1 file, +1/-1). It is what FunctionScoreQuery does for its inner query.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  return indexQueryWeight.isCacheable(ctx) && predicateValueSource.isCacheable(ctx);
}

Trade-offs

  • On a segment where a field the index query reads was updated in place, the composite is no longer cached until that segment is merged away. The index query on its own is already treated that way, so no correct result is lost; caching is lost, though, whenever the index query is not cacheable, for any reason (below).
  • The in-tree path is unchanged: prefix-tree query Weights are always cacheable (AbstractPrefixTreeQuery.java:107-108; so is the TermQuery built for a point on a points-only grid, TermQuery.java:192-194), and the control test shows CompositeSpatialStrategy's composite still served from the cache after an unrelated doc-values update.
  • An index query that is not cacheable for another reason (for example a BooleanQuery with more than 16 clauses, BooleanWeight.java:274-280) now also keeps the composite out of the cache: correct, but a change in what gets cached.
  • One extra isCacheable call, on the index query's Weight, per leaf cacheability check. A "Bug Fixes" CHANGES line would be usual; none is drafted.

How it was found

#

A hunt on this class's cache and visitor contracts started from a planning probe, then a model-based differential harness: 162 scenarios comparing cached and uncached search with a reference model found 14 stale results, all for index queries that read doc values after an in-place update, and 0 with the fix. A public-API JUnit confirmed it.

The method in full201 words

Method: semi-formal (the hunt's hunt unit for CompositeVerifyQuery's cache and visitor contracts, 2026-10-28, main a9779ef3c193).

  • Lead. A planning probe from a cross-model ideas pack on committer contracts showed the wrapped query returning [0, 1, 2] where the uncached search returns [1, 2]; the finder re-read its outputs (a planning-stage reviewer had re-run it) and reduced it to a JUnit.
  • Model-based harness. LFV-947, snapshot of 2026-10-29

Registry title
CompositeVerifyQuery's Weight reports itself cacheable from its shape predicate alone and ignores the index query it runs, so after an in-place doc-values update a query cache keeps returning the old matches
Area
spatial-extras / composite: CompositeVerifyQuery (Weight#isCacheable) and the query cache
Priority
Medium, rank 245: It belongs to the same stale-query-cache class as LFV-320, LFV-336 and LFV-308, with silent wrong results released since 7.2, but it needs a hand-built CompositeVerifyQuery plus in-place updates, so it closes that medium group after LFV-308.
Impact class
silent wrong results
Impact note
Applications that build a CompositeVerifyQuery with its public constructor around an index query that reads numeric or binary doc values (for example NumericDocValuesField.newSlowExactQuery, or a BooleanQuery with such a FILTER clause next to an RPT or term clause), update that field in place (IndexWriter#updateNumericDocValue or updateBinaryDocValue) and keep a query cache across reopens get the matches from before the update, with no error: a document that stopped matching is still returned, one that started matching is missing and counts are off, until the segment is merged away or the entry is evicted; on 7.2.0-10.5.2 and the 10.6.0 release-candidate branch the default IndexSearcher cache is enough (zero-configuration repro executed with a segment of 10,000+ documents and the query repeated), on main only an application-installed cache (no default cache since #14187); CompositeSpatialStrategy's own queries (an RPT postings index query) are not affected; ordinary scale.
Summary
You wrap an index query that reads a doc-values field, for example NumericDocValuesField.newSlowExactQuery("v", 1), in new CompositeVerifyQuery(indexQuery, shapePredicate), run it through a query cache, then change that field for one document in place with IndexWriter#updateNumericDocValue and reopen the reader. You expect the reopened searcher to see the new value, because a query that depends on updated doc values must report itself not cacheable (SegmentCacheable), and the index query alone does. Instead CompositeVerifyQuery's Weight#isCacheable asks only the shape predicate, the segment keeps its core cache key, and the cache keeps serving the pre-update result ([0, 1, 2] instead of [1, 2] in the repro; 5025 instead of 5024 hits with the release-default cache settings).
