An NRT replica's merge pre-copy callback locks itself, not the replica, so a primary switch can slip into its install

In NRT segment replication, the callback that installs a pre-copied merged segment on a replica uses synchronized (this) inside an anonymous class, so it locks itself, not the ReplicaNode. A fail-over during the install leaves the old primary's merged files pending and on disk; synchronized (ReplicaNode.this) fixes it.

The finding in 30 seconds

#

launchPreCopyMerge hands the copy job an anonymous CopyJob.OnceDone. Its run() wraps the "primary changed?" check, the renames and pendingMergeFiles.add in synchronized (this), and in an anonymous class this is the callback, which nothing else locks. newNRTPoint and maybeNewPrimary lock the ReplicaNode, so a switch can run between the check and the add.

Background: NRT replication and merge pre-copy

#
  1. In lucene-replicator's NRT segment replication (opt-in, experimental) one PrimaryNode indexes and ReplicaNodes copy its files. Each newly promoted primary gets a higher primary generation.
  2. Before a merged segment becomes visible, the primary pre-copies it to the replicas. On a replica a copy thread fetches the bytes, then runs a callback that renames them into place and lists them as pending until an NRT point uses them.
  3. When a replica sees a new primary generation, newNRTPoint first deletes every pending pre-copied file and clears the list: files from the old primary are not reused for the new one.

The finding, step by step

#
  1. Primary P1 (generation 1) merges, and replica B pre-copies the merged segment _2 (_2.cfe, _2.cfs, _2.si). Once the bytes are in, B's callback checks "did the primary change?" (no, still 1) and starts renaming the files into place.
  2. Right then replica A is promoted to P2 (generation 2), and B receives P2's first point, newNRTPoint(2, v), on another thread.
  3. You expect one of two safe orders: the install finishes and the switch then discards the files ("we defensively discard"), or the switch goes first and the callback cancels ("primary changed during merge copy").
  4. Instead the switch does not wait, because the callback's lock is the callback object. B moves to generation 2 with an empty pending list, then the callback adds P1's files: B follows P2 with pendingMergeFiles=[_2.cfe, _2.cfs, _2.si] and the files on disk, unreferenced.
  5. With assertions on, P2's later pre-copy of a same-named segment fails: file "_2.si" is already being warmed!. In a timing probe the same race also made newNRTPoint throw ConcurrentModificationException; with another pre-copy pending, a re-delivered switch and close() then failed with NoSuchFileException.

Who is affected

#

Users of the opt-in, experimental NRT segment replication with merge pre-copy, in every release run or read from 6.0.0 to 10.6.0, with assertions on or off. It takes a fail-over that reaches a replica during the short install after an old-primary pre-copy's last byte. Rare; no wrong search results or corruption were shown.

Mechanism, terms and numbers820 words

In lucene-replicator's NRT segment replication, ReplicaNode.launchPreCopyMerge gives each merge pre-copy job an anonymous CopyJob.OnceDone callback. The callback checks whether the primary changed, renames the copied files into place and lists them in pendingMergeFiles, all inside synchronized (this); in an anonymous class this is the callback, which nothing else locks. newNRTPoint and maybeNewPrimary, which switch to a new primary and discard the pending files, lock the ReplicaNode. So a fail-over that reaches a replica during the install runs in the middle of it: the replica follows the new primary with the old primary's merged files pending and on disk, a state no serial order of the two locked blocks can produce, against the discard that newNRTPoint's comment describes. With assertions on, the new primary's later pre-copy of a same-named merged segment then fails; in a timing probe the race also made newNRTPoint throw ConcurrentModificationException. No wrong search results or corruption were shown. Present since 6.0.0 (LUCENE-5438); synchronized (ReplicaNode.this) fixes the repro and passes the module's nightly suites.

The normal NRT-point callback does it right: finishNRTCopy runs its check, job.finish() and bookkeeping inside synchronized (this) in a ReplicaNode method (:412-430), so under the node lock. A lambda would also have bound this to the ReplicaNode. Nothing under lucene/ ever locks a OnceDone, and the shipped bytecode of the callback locks itself (aload_0; dup; astore_2; monitorenter).

Step by step, on the minimal repro

#
  1. Pre-copy request. An empty replica starts at generation 1 and gets launchPreCopyMerge(generation 1) for one file, _0.si. The callback records primaryGenStart = 1.
  2. Check. The test thread runs the callback as the copy thread would, without the node lock. It takes the callback's own lock and passes the check: generation is still 1.
  3. Switch. Inside the install (job.finish()), the test's job starts a thread that calls the public newNRTPoint(2, current version) and waits for it (up to 5 s). That thread gets the node lock at once: maybeNewPrimary(2) deletes and clears the still-empty pending set and sets generation 2.
  4. Install. The callback creates _0.si and adds it to pendingMergeFiles. The replica now follows generation 2 with [_0.si] from generation 1 pending.
  5. With the fix the switch thread blocks on the node lock, the 5 s wait times out, the install finishes, and then the switch deletes _0.si: pendingMergeFiles is empty.

What follows (fuller tests and a probe)

#
  • Real copy, two replicas (the study's test: a real forceMerge, Lucene's CopyOneFile, temp-file renames; replica A promoted to P2): replica B follows generation 2 with pendingMergeFiles=[_2.cfe, _2.cfs, _2.si] and the same files on disk, unreferenced. They stay until the next primary change, close(), a restart (:692-696, :716-724, :173), or an NRT point from the new primary that reuses or retires the same file names (:450, :464-472).
  • Assertions on: P2's later pre-copy of a same-named merged segment _2 is rejected by the assert at :742, file "_2.si" is already being warmed!. With assertions off that pre-copy goes through.
  • Unlocked iteration. pendingMergeFiles is a Collections.synchronizedSet (:83), whose iterator must be used under the set's own lock; maybeNewPrimary (:717) and close() (:693) iterate it holding only the node lock, and the callback's add is the one mutation without the node lock. In the tie-breaker's timing probe (no hooks; a copy thread runs the callback while another thread calls newNRTPoint after a random 0-200 microsecond spin; 2000 rounds), with one earlier pre-copy pending at each round start, newNRTPoint threw ConcurrentModificationException in 785 rounds (assertions off). In 781 of them the aborted loop had already deleted that file, which stayed listed, and the generation stayed old: a re-delivered switch then threw NoSuchFileException, and so did close(), which kept the directory's write lock. With the fix: no stale state and no exception in 8000 rounds. The spin makes the two events nearly simultaneous, so these counts are conditional, not production frequencies.
Exposure and likelihood382 words
  • Who is hit. Applications that use lucene-replicator's NRT segment replication with merge pre-copy (PrimaryNode / ReplicaNode / CopyJob subclasses, marked @lucene.experimental). Every release run from 6.0.0 to 10.6.0 fails, and the callback is unchanged in every release tag read; assertions on and off both fail where both were run. The repros use small indexes.
  • What it takes. A switch to a new primary (newNRTPoint, or a pre-copy request from the new primary, both through maybeNewPrimary) reaching a replica while its callback for an old-primary merge pre-copy is between the check and the end of its add loop. Lucene's reference transport allows it: one handler thread per connection (TestSimpleServer.java:344-356, test code) calls newNRTPoint and launchPreCopyMerge (SimpleReplicaNode.java:218, :339), while the job runner thread calls the callback without the node lock (Jobs.java:107). Each step is an ordinary fail-over event, but the window, the renames and bookkeeping after the last byte, is short (not measured). Likelihood: rare; nothing has been reported since 2016.
  • What goes wrong (executed). (1) The old primary's merged files stay pending and on disk under the new primary, against the discard that newNRTPoint's comment describes, until the next primary change, close, restart, or an NRT point from the new primary that reuses or retires those file names; for a large merge that is a whole merged segment's files on disk, unreferenced. (2) With assertions on, the new primary's later pre-copy of a same-named merged segment fails. (3) In the timing probe, newNRTPoint threw ConcurrentModificationException, and when another pre-copy was pending the replica then failed a re-delivered switch and close() with NoSuchFileException and kept its write lock (seen only in that probe variant, not in the minimal or real-copy tests).
  • What does not go wrong. No reader or commit references the stale files, so no searcher sees them (by reading; no executed test checked searchability after the race); a different file with the same name is never mistaken for the local one, because a local file counts as identical only if its header (with the segment's random id) and footer match (ReplicaNode.java:849-873); otherwise it is re-copied. No wrong documents, corrupt commit or hang were shown.
  • Impact class: minor, priority low (opt-in experimental module, rare trigger).

More files, environment, full output495 words

The test thread runs the job's OnceDone as the replica's copy thread would, without the node lock. The OnceDone passes its "primary changed?" check and calls the job's finish() (the install, here creating the file), which starts a thread calling the public newNRTPoint(2, current version) and waits for it with join(5000). With the bug that thread gets the node lock at once; with the fix it waits for the install, so the join times out and the passing run takes about 5 s longer. The wait sits in CopyJob.finish(), a method the integrator implements: it stretches the naturally short install window, and with the correct lock it cannot let the switch in. The NRT point carries the replica's current version, so newNRTPoint needs no copy job: it calls maybeNewPrimary before any version check.

It lives in the module's package because launchPreCopyMerge, start and the CopyJob hooks are protected and pendingMergeFiles is package-private, like the module's own tests. The seed does not change the outcome: 20 of 20 iterations under another seed fail. It rests on a 5-second window: only a switch thread stalled for more than 5 s could let the stock code pass by accident; with the fix it always waits out the 5 s and passes. The job is synthetic (no bytes copied, empty metadata); the study's longer test with a real merge and Lucene's CopyOneFile fails the same way (its nodes run in one JVM with test subclasses; the race was not run through the module's socket-based reference transport). Use this one test as the regression test too.

Why it looks unintended

#
  • newNRTPoint's comment says it discards pre-copied merged segments on a primary change, "defensively" (ReplicaNode.java:536-544); the callback itself cancels on "primary changed during merge copy" (:763-767).
  • The result matches no serial order of the two locked blocks; the NRT-point twin finishNRTCopy runs its check and renames under the replica's lock (:412).
  • No javadoc asks callers to hold that lock.
The full argument300 words
  • The code states the contract (in an implementation comment, not in javadoc). ReplicaNode.java:536-544: "Cutover (possibly) to new primary first, so we discard any pre-copied merged segments up front ... we defensively discard here and re-copy"; maybeNewPrimary deletes and clears pendingMergeFiles (:716-724).
  • The callback guards against this very race. It cancels when "primary changed during merge copy" (:763-767), and its own comment assumes it coordinates with newNRTPoint ("Even though in newNRTPoint we have similar logic, which cancels any merge copy jobs ...", :787-793). The asserts at :742 and :799-800 say a file is never pending twice.
  • No serial order explains the result. Callback first: the switch deletes the files. Switch first: the callback cancels. Observed: generation 2 with generation-1 files pending.
  • The twin path holds the node lock (finishNRTCopy, :412). A contributor read these blocks as the node lock too: in review of #13142 (2024-02-28) its author wrote that "all operations on the 'pendingMergeFiles' in that class are inside synchronized (this) blocks. But this is rather fragile."
  • No locking duty on callers is documented. OnceDone: "Callback invoked by CopyJob once all files have (finally) finished copying" (CopyJob.java:92); launch: "Runs this job async'd" (:516). The module's job runner calls the callback without the node lock (Jobs.java:107, test code).
  • Design intent. The module author's 2017 design post: replicas that switch to a new primary "must delete any files copied or partially copied from the old primary but not referenced by the new primary".
  • History. The lock dates from the commit that added the package (1ae7291429ba, 2016) and no earlier discussion of which monitor it locks was found (the #13142 review read it as the node lock); the only later change is a 2021 reformat.
The devil's-advocate check231 words

Strongest case for "intended" (an independent reviewer from another model family, OpenAI GPT-5.6, refute lens, reading only): the module is experimental and documents no instantaneous pendingMergeFiles invariant; OnceDone must be invoked only after a genuine copy, but the test calls it directly after a synthetic job with empty metadata that creates the file itself; and pendingMergeFiles is package-private state with best-effort cleanup, not a result a search client sees.

Why it fails:

  1. The reviewer agreed with the root cause, could not run anything, called its verdict "not a substantive disproof of the race" and rated its own argument moderate.
  2. Calling the OnceDone from the copy thread is what the module's job runner does. The study's real-copy test (a real merge, Lucene's CopyOneFile with length and checksum checks, temp-file renames) fails the same way, and so does a variant with the old primary closed before the promotion.
  3. The stale files are on disk, not only in a field, and the probe shows the public newNRTPoint throwing.
  4. Two of its three follow-ups were run: a production-like copy path (item 2) and the module's suites with the fix, which pass in nightly mode. After the race the replica still opens P2's NRT point (the independent reproducer's test asserts it); that no searcher sees the stale files is by reading.
  5. @lucene.experimental is about API stability, not about breaking the contract the module's own comments state.

A. synchronized (ReplicaNode.this) in the merge pre-copy callback (validated by the checks) (recommended)

#

The check, the renames and the add become atomic with newNRTPoint / maybeNewPrimary: a switch that arrives during the install waits and then discards the files, or the install sees the new generation and cancels. It also removes the only mutation of pendingMergeFiles that does not hold the node lock, so the unlocked iteration in maybeNewPrimary and close() can no longer race with an add.

Trade-offs

  • The renames now run under the node lock, as they already do for NRT points (finishNRTCopy, ReplicaNode.java:430), so a slow finish() delays newNRTPoint and commit for that long. The study's devil's advocate notes it adds no new lock-order pair: the same launcher thread already takes the node lock in finishNRTCopy (read).
  • An integrator whose launch() blocked until the job finished on another thread would deadlock here, but such an integrator already deadlocks on every NRT point: newNRTPoint calls launch holding the node lock (:654) and its callback needs that lock (:412); launch is documented as async (:516) (read, not run).

What the checks validated

  • Scratch worktree of main 645d4fe14a20 (removed afterwards), seed DEADBEEF: stock, the test fails through gradle with assertions on and off; with A it passes with both (5.03 s each, because the switch waits for the install).
  • With A, the whole :lucene:replicator:test task passes (16 tests: the new one passes; the 14 nightly tests and TestSimpleServer.test, which runs only nested, are skipped).
  • With A and nightly tests enabled: TestNRTReplication 13 tests, 0 failures (48 s); TestStressNRTReplication 1 test, 0 failures (JUnit time 324 s, one seed only; its log has 9 replica-side primary switches ("now change lastPrimaryGen" lines), 127 merge pre-copy callbacks ("done warming merge" lines) and no "already being warmed", ConcurrentModificationException or NoSuchFileException).
  • Earlier, the 2026-10-31 tie-breaker with the fix shadowed into the stock jars: the real-copy test, the P1-closed variant and the independent reproducer's two tests pass; the timing probe shows no stale state and no exception in 8000 rounds; nightly TestNRTReplication 13 of 13 and TestStressNRTReplication 1 of 1 (a randomized run with crashes and closes, planned run time 478 s). The one-line change also fixes the port on 6.0.0.

B. The same lock in a clearer shape (not run)

#

Move the callback's body into a synchronized ReplicaNode method (for example finishMergeCopy(job, fileNames, primaryGenStart), like finishNRTCopy), or pass a lambda, whose this is the ReplicaNode.

Trade-offs

Same semantics as A and harder to get wrong again; a larger diff.

C. A concurrent set for pendingMergeFiles (hardening only, not run)

#

Open PR #13142 changes pendingMergeFiles and mergeCopyJobs to ConcurrentHashMap.newKeySet().

Trade-offs

Removes the ConcurrentModificationException, but not the check-then-act race: the old primary's files would still be registered after the switch. With A, every mutation already holds the node lock.

Downstream note

#

Downstream, the open-source nrtsearch server subclasses ReplicaNode and calls launchPreCopyMerge without replacing the callback, so it inherits the race (code read, not run).

How it was found

#

TLA+ model checking of the NRT replication protocol. While transcribing the merge pre-copy callback into the model, the finder saw that its lock is the callback, modelled check and install as two steps, and TLC found an old-generation file pending under the new generation. A JUnit then replayed the interleaving on the stock jars.

The method in full174 words
  • Method (semi-formal). The replicator hunt wrote a TLA+ model of the NRT replication protocol (NrtReplication.tla). The hypothesis came from code reading while the merge pre-copy callback was being transcribed: because the lock is the callback, the model splits it into two actions (check, then install). TLC found the invariant "every pending file comes from the current primary generation" violated in a 7-state trace (689 distinct states with assertions off, 673 on; also under the module's test-controller discipline, 337 states). With the lock fixed TLC found no violation in the bounded configurations it checked (10,233 distinct states for the merge model, 82,805 for the full model).
  • Executed. A JUnit with in-process nodes and a real forceMerge replayed the interleaving on the stock jars; an independent reproducer wrote its own test and added the assertions-on follow-up; a devil's advocate and an adjudication confirmed it; the one-test repro was then reduced from these tests; the 2026-10-31 re-verification and tie-breaker re-ran everything on 645d4fe14a20 and added the timing probe and the nightly suites with the fix.

LFV-245, snapshot of 2026-11-08

Registry title
An NRT replica's merge pre-copy callback (ReplicaNode.launchPreCopyMerge) synchronizes on itself instead of the ReplicaNode, so a primary change that lands while it installs the merged files leaves the old primary's pre-copied merged files pending and on disk
Area
replicator / NRT segment replication (ReplicaNode.launchPreCopyMerge merge pre-copy, ReplicaNode.newNRTPoint)
Priority
Low, rank 959: The experimental NRT merge pre-copy callback locks the wrong object, so a primary change in a narrow window leaves pre-copied files pending on disk, which is minor and races-only.
Impact class
minor
Impact note
Applications that use lucene-replicator's NRT segment replication with merge pre-copy warming (PrimaryNode/ReplicaNode/CopyJob subclasses, opt-in and @lucene.experimental; the one downstream user found, nrtsearch, calls launchPreCopyMerge without overriding the callback, by reading), in every release since 6.0.0 and at any index size, are hit only when a primary change reaches a replica (newNRTPoint or launchPreCopyMerge with a higher primaryGen) while that replica's merge pre-copy callback for the old primary is between its 'primary changed?' check and the end of its renames plus pendingMergeFiles.add: the old primary's merged files then stay in pendingMergeFiles and on disk after the switch, against the discard that newNRTPoint promises, until a later primary change, close, restart or a re-copy overwrites them, and with -ea the new primary's later pre-copy of a same-named merged segment fails with AssertionError 'file "_2.si" is already being warmed!'; no wrong search results, lost documents or index corruption were shown, and by reading none follow, because a local file is reused only if its header (with the random segment id) and footer match.
Summary
You run Lucene's NRT segment replication with merge pre-copy: the primary asks replica B to pre-copy a merged segment, and just as B has copied the bytes and is renaming the files into place, another node is promoted to primary and B receives its first NRT point (primaryGen 2). You expect B either to install the merged files and then discard them in the switch, or to notice the switch and cancel the pre-copy, because newNRTPoint says it discards the old primary's pre-copied merged segments and the callback itself checks whether the primary changed. Instead the callback's synchronized (this) locks the anonymous CopyJob.OnceDone, not the ReplicaNode, so the switch runs in the middle of it and B follows primaryGen 2 with the old primary's merged files [_2.cfe, _2.cfs, _2.si] still in pendingMergeFiles and on disk (with -ea, the new primary's later pre-copy of a same-named merged segment then fails with 'file "_2.si" is already being warmed!').
